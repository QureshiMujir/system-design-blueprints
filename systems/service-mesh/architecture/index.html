Injection Webhook. Synchronous AdmissionReview HTTPS callback from the API server on pod create; mutates the pod spec to add the sidecar and init containers; fails closed by default (configurable fail-open per namespace).

Discovery Watcher. Long-lived informer watches on Services, Endpoints/EndpointSlices, and the mesh-config CRDs; builds the in-memory cluster-reality model; triggers ConfigSnapshot rebuilds on change, debounced (§13.10 batching).

Policy Compiler. Translates PeerAuthentication and AuthzPolicy CRDs into the evaluatable form the sidecar's authz filter consults; default-deny (I6).

Telemetry Aggregator. In-memory rollup of control-plane-side metrics (xDS push latency, NACK rate, CA issuance rate); exposes Prometheus scrape endpoint; holds no long-term history (§26).

xDS Server. Owns the versioned ConfigSnapshot per node/node-group; serves the ADS bidirectional gRPC stream; tracks per-subscriber ACK state (AckState, §11); implements resource warming (§8.7 below is domain model; mechanism lives here).

mesh-ca. Holds the trust-domain root signing key; validates CSRs against the requester's Kubernetes ServiceAccount token (I9); issues short-lived SVIDs; manages trust-bundle rotation.

Sidecar Proxy. The data-plane process: xDS client subscribes over ADS; listeners accept on 15001 (outbound) and 15006 (inbound); filter chain applies authn/authz/rate-limit/ fault/router in order; cluster manager owns per-endpoint connection pools and the load balancer; admin/metrics bound to loopback only.

Traffic-interception layer. The init container's iptables/eBPF rules (§8.1) redirect all inbound and outbound TCP through the sidecar's two listener ports, excluding the sidecar's own egress by UID (I5).

mTLS engine. Embedded in the sidecar's transport-socket layer (rustls, ADR-06); terminates inbound, originates outbound, validates peer SPIFFE SAN against the trust bundle on every handshake.

8. Domain Model

8.1 Traffic-interception model

Chain Direction Match Action Exclusion Purpose
MESH_OUTPUT outbound tcp, any dst REDIRECT → :15001 owner UID = 1337 (sidecar) → RETURN loop avoidance (I5)
MESH_OUTPUT outbound tcp, dst 127.0.0.1/* RETURN (no redirect) localhost calls unintercepted avoid self-probe breakage
MESH_OUTPUT outbound udp, dst port 53 RETURN DNS unintercepted in v1 avoid resolver breakage; DNS-proxy is PhaseDeferred("§37 Deferred Features Register")
MESH_INBOUND inbound tcp, any dst port REDIRECT → :15006 dst port = 15006 → RETURN loop avoidance (I5)
MESH_INBOUND inbound tcp, kubelet probe ports RETURN kubelet liveness/readiness bypass mTLS documented risk, §24 T4-adjacent

Loop-avoidance mechanism. The sidecar process runs as a fixed UID (1337, kept for compatibility with the Istio convention cited in §5); every ruleset excludes traffic whose socket owner UID equals the sidecar's UID from outbound redirection, and excludes traffic whose destination port equals the sidecar's own inbound port from inbound redirection. The eBPF variant (PhaseDeferred("§13 Phase 1 — Traffic Interception And Loop Avoidance")) achieves the same exclusion via a cgroup/socket map keyed on cgroup id rather than UID.

8.2 xDS resource model and the ACK/NACK sequence

Resource Carries Depends On Update Trigger
LDS listener defs (port, filter chain, transport_socket) CDS (route→cluster refs must resolve) VirtualService/gateway change
RDS route tables (match→cluster, weights, retry/timeout) CDS VirtualService change
CDS cluster defs (LB policy, circuit breakers, outlier detection, TLS context) none (root) DestinationRule change
EDS endpoint lists per cluster (IP, health, weight, locality) CDS (cluster must exist) Pod/Endpoints/EndpointSlice change
SDS TLS secrets (cert, key, trust bundle) none rotation, trust-bundle change

ACK/NACK sequence table:

Step Direction Message Fields
1 Sidecar→Server DiscoveryRequest type_url, resource_names=[], version_info="", node.id
2 Server→Sidecar DiscoveryResponse version_info="v1", nonce="n1", resources=[...]
3 Sidecar applies resources locally —
4 Sidecar→Server DiscoveryRequest (ACK) version_info="v1", response_nonce="n1"
5 Server cluster reality changes —
6 Server→Sidecar DiscoveryResponse version_info="v2", nonce="n2", resources=[...]
7 Sidecar apply fails (invalid LB policy) —
8 Sidecar→Server DiscoveryRequest (NACK) version_info="v1" (unchanged), response_nonce="n2", error_detail
9 Server logs NACK, does not retry the same payload (I8) —
10 Operator fixes source config, re-applies —
11 Server→Sidecar DiscoveryResponse version_info="v3", nonce="n3", resources=[...] (corrected)
12 Sidecar→Server DiscoveryRequest (ACK) version_info="v3", response_nonce="n3"

NACK recovery. Steps 8–11: the control plane never retries the identical rejected payload (I8); recovery requires an operator or automated corrector producing a new, valid version. The sidecar's version_info on NACK always equals its last successfully applied version, never the rejected one — this is how the server knows exactly which version the sidecar is running.

8.3 State-of-the-world vs. delta xDS

Dimension State-of-the-World (SOTW) Delta (Incremental)

Server-side state none (stateless re-send) per-subscriber known-version map
Bandwidth at N=10k endpoints O(N) per push O(Δ) per push

8.4 SPIFFE identity grammar and SVID lifecycle

spiffe-id     = "spiffe://" trust-domain path
trust-domain  = 1*(ALPHA / DIGIT / "-" / ".")
path          = *("/" path-segment)
path-segment  = 1*(ALPHA / DIGIT / "-" / "_" / ".")
// this blueprint's fixed shape:
workload-path = "/ns/" namespace "/sa/" service-account
// example: spiffe://cluster.local/ns/payments/sa/charging-service

SVID issuance/rotation sequence:

Step Actor Action
1 Sidecar (startup or rotation timer) generate ECDSA P-256 keypair in memory (never persisted, ADR-06)
2 Sidecar build CSR, SAN URI = expected spiffe-id
3 Sidecar read projected ServiceAccount token (bound audience = trust domain)
4 Sidecar→CA CreateSvidRequest(csr_pem, sa_token) over SDS-adjacent gRPC
5 CA validate token signature against K8s API server public key
6 CA validate token aud/namespace/service-account claims match requested SAN (I9)
7 CA sign CSR, not_after = now + 24h (§4, I14)
8 CA→Sidecar WorkloadCert{cert_pem, chain_pem, not_before, not_after}
9 Sidecar ArcSwap-install new CertBundle; old connections keep the old cert reference
10 Sidecar schedule re-CSR timer at 50%±10% lifetime jitter (§6 P6, Phase 7 §19)

Rotation reuses steps 1–10 on a timer instead of at startup, with one addition: the old CertBundle stays reachable via existing Arc clones held by live connections until they close naturally — no forced disconnect (I3).

8.5 mTLS handshake and peer-identity validation path

Step Side Action
1 Client sidecar opens TCP to the SO_ORIGINAL_DST-resolved upstream
2 Client sidecar sends ClientHello (SNI = target service, ALPN=[h2])
3 Server sidecar listener filter (TLS inspector) peeks ClientHello, selects filter chain
4 Server sidecar sends ServerHello + Certificate (own SVID) + CertificateRequest
5 Client sidecar validates server cert against trust bundle (RFC 5280), extracts SPIFFE SAN
6 Client sidecar sends Certificate (own SVID) + CertificateVerify
7 Server sidecar validates client cert against trust bundle, extracts SPIFFE SAN → PeerIdentity
8 Server sidecar policy compiler evaluates AuthzPolicy(PeerIdentity, route) → PolicyDecision
9 Server sidecar Deny → TLS close_notify/reset; Allow → proceed to HTTP Connection Manager

8.6 Routing and traffic-split weight arithmetic

Given N WeightedCluster entries with weights w_i summing to W (not required to equal 100 — normalized), selection probability p_i = w_i / W. Implementation model: build a cumulative-weight array, draw uniform r ∈ [0, W), binary-search the first index whose cumulative weight ≥ r. Worked example: clusters v1 (w=90), v2 (w=10), W=100; draw r=45.2 → cumulative [90, 100] → 45.2 < 90 → select v1. Over 10,000 draws, expect v1 ≈ 9,000 ± 190 (binomial, p=0.9, n=10,000, σ ≈ 30, 2σ tolerance ≈ ±2%) — the tolerance used by the Phase 10 (§22) conformance fixture.

8.7 Load-balancer and outlier-ejection state machines

Endpoint health state machine:

State Event Next State Notes
HEALTHY consecutive_5xx ≥ threshold within interval EJECTED subject to I11 cap check
HEALTHY EDS reports NOT_HEALTHY UNHEALTHY control-plane-driven, distinct from local ejection
EJECTED base_ejection_time elapses HEALTHY (probationary) rejoins LB rotation, ejection count decremented
EJECTED new ejection would exceed max_ejection_percent stays EJECTED I11 enforcement, new ejection refused
UNHEALTHY EDS reports HEALTHY HEALTHY control-plane recovery signal
HEALTHY (probationary) consecutive_5xx again before cooldown EJECTED (ejection time doubles) exponential backoff, prevents flapping
any EDS stops reporting the endpoint REMOVED in-flight requests fail, retried per policy

Circuit breaker state machine (connection-pool level, distinct from outlier detection):

State Event Next State
CLOSED pending/active requests within limits CLOSED
CLOSED limit exceeded (max_pending/max_requests/max_connections) OPEN
OPEN new request arrives immediate local 503, no upstream attempt
OPEN in-flight requests drain below limit HALF_OPEN
HALF_OPEN probe request succeeds CLOSED
HALF_OPEN probe request fails OPEN (backoff timer resets)

8.8 Sidecar lifecycle state machine

Injected → Bootstrapping → Warming → Serving → Draining → Terminated, with failure edges:

State Entry Condition Exit Condition Failure Edge
Injected admission webhook adds containers init container starts webhook failure → pod creation rejected (fail-closed default)
Bootstrapping init container running (rule install) rules applied successfully init failure → CrashLoopBackOff, app never starts
Warming proxy started, ADS stream opening first full snapshot ACKed control plane unreachable past timeout → Serving with cached/static fallback (P4)
Serving snapshot applied, listeners accepting SIGTERM received crash → pod restart, Bootstrapping repeats
Draining SIGTERM received, GOAWAY sent drain_timeout elapses or all conns close timeout exceeded → hard-close remaining connections
Terminated process exits (terminal) app container outlives sidecar → app egress connection-refused (mitigated by container ordering)

8.9 Policy evaluation model

AuthzPolicy = (principal_match: SpiffeId pattern, route_match: RouteMatch, effect: Allow|Deny). Evaluation order: most-specific route match first; default effect = Deny (I6). PeerAuthentication mode ∈ {STRICT, PERMISSIVE, DISABLE} is evaluated before any AuthzPolicy — STRICT rejects non-mTLS at the transport layer before an authz rule runs.

8.10 Worked end-to-end example — one request crossing two sidecars with mTLS

App on pod A calls payments.svc.cluster.local/api/charge. (1) Syscall hits the local stack; MESH_OUTPUT redirects to :15001 (§8.1). (2) Outbound listener's HTTP Connection Manager matches route /api/* → cluster outbound|80|payments. (3) Cluster manager selects an endpoint via least-request-power-of-two (ADR-15) from EDS-supplied endpoints. (4) Client sidecar opens TCP + mTLS handshake to the selected pod's :15006 (§8.5, steps 1–9); its own egress is not re-redirected (I5). (5) Server sidecar validates the peer cert, extracts PeerIdentity, evaluates AuthzPolicy (I6, §8.9), forwards to localhost:5000. (6) App responds; path reverses. Added latency: two hops × (TLS overhead + route match + policy eval), budgeted ≤ 6 ms p99 round-trip (§4).

8.11 Malformed-input examples

  • Config referencing an unknown cluster → the LDS resource enters Warming, never promotes, mesh_listener_warming_timeout_total fires (I12).
  • Expired peer certificate → handshake fails at CertificateVerify, mesh_mtls_handshake_failure_total{reason="expired"} (I14-adjacent).
  • xDS version regression (server sends a version_info lower than the client's applied version) → client detects via I2, discards, emits a malformed-response error.
  • Conflicting route match (two HttpMatch rules matching the same request with different clusters) → deterministic tie-break: first-defined wins, logged as a compile-time warning by mesh-config (Phase 4, §16).

8.12 Failure-path example — control-plane unavailability

The ADS stream drops; the xDS client (Phase 3, §15) applies exponential backoff with full jitter (base 1 s, cap 30 s). The Serving state (§8.8) continues on the last-applied ConfigSnapshot indefinitely (P4, I7). The certificate-rotation timer still fires, but CSR requests queue against the unreachable CA; if the outage exceeds the certificate-lifetime ceiling (§4, 24 h), the sidecar's own certificate expires and new connections fail — this is FM-4 (§25), mitigated operationally by control-plane HA (3 replicas, leader election, ADR-23) and alerting on xds_connected=0 well before the cert-expiry window is reached.
