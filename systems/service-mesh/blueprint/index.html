Project Number: 164

Project Name: Service Mesh

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Service Mesh (project 164) specifies a per-pod sidecar data plane and a cluster-scoped control plane that together give every service-to-service call inside a Kubernetes cluster transparent mutual TLS, xDS-driven traffic management, and zero-trust workload identity without any application code change. The sidecar intercepts traffic via kernel-level redirection (iptables NAT in the buildable core; eBPF deferred), terminates and originates mTLS using SPIFFE-formatted X.509 certificates issued by an in-cluster certificate authority, and applies routing, retry, circuit-breaking, load-balancing, and traffic-split decisions driven by configuration streamed from the control plane over the xDS protocol (Envoy's discovery-service family: LDS/RDS/CDS/EDS/SDS). The control plane compiles Kubernetes service-discovery state and user-authored policy into xDS resources, issues and rotates SVIDs, and aggregates telemetry. The system's two irreducible hard problems, named here because every later section returns to them: (1) making the interception layer invisible and loop-free while intercepting only what it should (§8.1, I5); and (2) keeping thousands of independently-updating sidecars converged on a consistent view of cluster reality under a configuration protocol that is eventually consistent by design (§8.2, I2, I4, I7).

Phase-0 deliverable — numbered crate list:

  1. mesh-types — shared wire/domain types (identity, xDS resources, error taxonomy).
  2. mesh-proxy — the sidecar data-plane binary (listeners, filter chain, router, LB, TLS).
  3. mesh-xds-client — xDS client library (ADS stream, ACK/NACK, version tracking).
  4. mesh-xds-server — control-plane xDS server (LDS/RDS/CDS/EDS/SDS snapshot cache).
  5. mesh-ca — certificate authority: SPIFFE SVID issuance, rotation, trust-bundle mgmt.
  6. mesh-discovery — Kubernetes service-discovery watcher (Services/Endpoints/Slices).
  7. mesh-policy — policy compiler (PeerAuthentication, static AuthzPolicy).
  8. mesh-telemetry — metrics/access-log/tracing aggregation and exposition.
  9. mesh-inject — mutating admission webhook + iptables/eBPF init-container generator.
  10. mesh-config — shared config model (VirtualService/DestinationRule analogues).

System boundaries.

  • Provides: transparent L4/L7 interception and forwarding; mTLS termination and origination with SPIFFE identity; xDS-driven dynamic configuration with no proxy restart; CA and SVID issuance/rotation; retries, timeouts, circuit breaking, load balancing, outlier ejection; weighted traffic splitting; static authorization policy; telemetry aggregation and exposition; sidecar injection.
  • Delegates: the Kubernetes API server for cluster state and CRD storage — etcd is the actual durability layer; the control plane holds no independent database (ADR-14); the API server's admission chain for webhook invocation; the Linux kernel's netfilter/ conntrack for NAT (Phase 1, §13); external backends (Prometheus, Jaeger/OTel collector) for long-term telemetry storage — the mesh emits, never stores, telemetry history (§26).
  • Does NOT provide: multi-cluster trust-domain federation (single cluster, single trust domain until un-deferred, PhaseDeferred("§27 Compatibility & Versioning")); WASM filter extensibility (PhaseDeferred("§10 Repository Layout")); non-HTTP/gRPC L7 protocol awareness — no Kafka/MySQL/Redis-aware proxying (PhaseDeferred("§22 Phase 10 — Traffic Splitting, Authorization Policy And Telemetry")); a general policy engine (no OPA/Rego integration, PhaseDeferred("§22 Phase 10 — Traffic Splitting, Authorization Policy And Telemetry")); a web UI (CLI plus Prometheus plus Jaeger is the operator surface); ambient/sidecarless mode (PhaseDeferred("§36 Alternative Architectures")).

Non-goals — named contrasts with sibling projects.

  • Not API-Gateway (165): 165 is north–south edge traffic carrying an API-contract surface — per-API-key rate limiting, request/response transformation, a developer portal. 164 is east–west intra-cluster traffic with no API-contract concept: every workload is a mesh peer, not a published API product.
  • Not Reverse-Proxy (82): 82 is a single L7 proxy instance in the traffic path with static or lightly-dynamic configuration. 164 runs thousands of proxy instances — one per pod — whose configuration is continuously synchronized from a control plane. 82's problem is proxying well; 164's problem is proxying well and keeping N proxies converged under an eventually-consistent protocol.
  • Not Mesh (9): 9 is an OAuth permission graph — authorization relationships between application-layer principals and resources. 164 is network-layer transport security and traffic management between workloads. Despite the name collision there is no shared concern: 164's "policy" is PeerAuthentication and authorization-by-SPIFFE-identity, never OAuth scopes.

Deployment model. Sidecar injection via a mutating admission webhook (mesh-inject) adds a proxy container and an init container to each opted-in pod. The control plane runs as its own Deployment (3 replicas, leader-elected for CA signing, ADR-23) in a dedicated namespace. Ambient/sidecarless is PhaseDeferred("§36 Alternative Architectures").

Users/operators. Platform and infrastructure teams operating a multi-service Kubernetes cluster. The mesh is invisible to application developers by design (§6 P1).

What later phases unlock. Phase 4 (control-plane discovery and xDS server, §16) unlocks dynamic reconfiguration without proxy restart. Phase 5 (CA, §17) unlocks zero-trust identity, on which Phase 6 (mTLS, §18) and Phase 7 (rotation, §19) build. Phases 8–9 (load balancing/health, retries/circuit-breaking, §20–§21) unlock production-grade resilience. Phase 10 (traffic split/authz/telemetry, §22) unlocks progressive delivery and observability. Phase 11 (conformance/chaos/perf, §23) unlocks the production-readiness bar.

Language: Rust. The proxy sits in the security-critical path of every request in the cluster; Envoy's CVE history (§5, §24) is dominated by C++ memory-safety defects (use-after-free, buffer overrun); Rust's ownership model removes that defect class at compile time — Linkerd2-proxy is the existence proof (§5 Reference Implementations). Rejected: C++ (Envoy's own choice — rejected for the CVE class above). Go (Consul Connect and older Istio components use it — rejected because its GC introduces latency-tail variance the sub-millisecond hop budget of §4 cannot absorb, and it lacks the zero-cost abstractions a thread-per-core-capable proxy architecture wants, ADR-05). Java/JVM (rejected for warm-up latency and per-connection object overhead at the endpoint-table scale of §4).

Prerequisites. TCP/IP and the Linux networking stack — netfilter, conntrack, sockets (Stevens/Fenner/Rudoff, §5); TLS 1.3 handshake mechanics (RFC 8446); X.509 certificate validation (RFC 5280); async Rust's task model; gRPC and Protocol Buffers wire format (xDS transport, ADR-11); Kubernetes API machinery — watches, admission webhooks, ServiceAccount tokens.

Timeline. Phase 0 in 2 weeks (skeleton, minimal L4 proxy, CI). Full system (Phases 0–11) in 11–14 months for a 2–3 engineer team — consistent with Istio's and Linkerd's multi-year production-hardening histories; this blueprint's scope is the buildable core, not full feature parity with either.

Deferrals. PhaseDeferred("§36 Alternative Architectures") — ambient/sidecarless mode. PhaseDeferred("§27 Compatibility & Versioning") — multi-cluster trust-domain federation. PhaseDeferred("§10 Repository Layout") — WASM filter extensibility. PhaseDeferred("§22 Phase 10 — Traffic Splitting, Authorization Policy And Telemetry") — OPA/Rego policy engine and non-HTTP/gRPC L7 awareness. PhaseDeferred("§13 Phase 1 — Traffic Interception And Loop Avoidance") — eBPF-based interception. PhaseDeferred("§37 Deferred Features Register") — delta (incremental) xDS.

2. Why Build This

  • Distributed configuration convergence at scale — the control-plane-to-data-plane problem is the same shape as consensus-adjacent coordination (§5 papers) applied to proxy configuration instead of replicated state.
  • Zero-trust workload identity — cryptographic identity replacing IP-based trust; the SPIFFE/SPIRE model is now an industry-standard pattern for workload authentication.
  • Kernel-level transparent interception — iptables/eBPF redirect, conntrack, SO_ORIGINAL_DST; knowledge that transfers directly to CNI plugins, VPNs, and any transparent-proxy design.
  • Tail-latency engineering under a microsecond budget — every filter-chain indirection, every TLS handshake, every allocation is visible at p99 (Dean & Barroso 2013, §5).
  • PKI-as-infrastructure — short-lived certificate issuance and rotation at pod-churn rates is an operationally different regime than traditional long-lived-certificate PKI.
  • Protocol design study — xDS's ACK/NACK/version/nonce state machine is a real-world instance of eventual-consistency-plus-client-acknowledgment config distribution.
  • Direct contrast with sibling projects sharpens architectural judgment: 165 (API-Gateway, edge/API-contract), 82 (Reverse-Proxy, single-instance L7), 9 (Mesh, OAuth graph) — building 164 clarifies what is genuinely mesh-specific (identity plus convergence) versus generically proxy-specific (routing plus filters).
  • Historical lineage: Linkerd 1.x (JVM) → Linkerd2 (Rust) and Istio+Envoy (C++) → ambient/eBPF (Cilium, Istio ambient) traces the industry's cost-of-sidecar reckoning; building the sidecar form first, then studying the alternative in §36, replicates that arc first-hand.

What Mastery Looks Like

  • Diagnose a "listener never receives traffic" bug by tracing iptables rule chains through SO_ORIGINAL_DST resolution to filter-chain match — Phase 1 (§13).
  • Explain, unaided, why xDS needs ADS ordering and resource warming rather than five independent streams — Phase 3 (§15) and Phase 4 (§16).
  • Design a certificate-rotation scheme that survives a CA restart mid-rotation without dropping a single in-flight connection — Phase 7 (§19).
  • Compute, from first principles, the mesh-wide config-push bandwidth and convergence time for a given cluster size, building on the discovery service's design — Phase 4 (§16, §34).
  • Distinguish, for any outage report, whether the fault is control-plane (convergence, Phase 4 §16) or data-plane (proxy, Phase 6 §18) in origin, and name the invariant (§7) it violates.
  • Justify, with named regimes, when ambient/sidecarless beats sidecar-per-pod and when it does not, having built the sidecar form first — Phase 0 (§12, §36).
  • Read an Envoy or Istio postmortem and map it onto this blueprint's own Threat Model (§24) and Failure Modes (§25) rows, tracing each back to the phase (§12–§23) that either introduced or should have caught it.

Injection Webhook. Synchronous AdmissionReview HTTPS callback from the API server on pod create; mutates the pod spec to add the sidecar and init containers; fails closed by default (configurable fail-open per namespace).

Discovery Watcher. Long-lived informer watches on Services, Endpoints/EndpointSlices, and the mesh-config CRDs; builds the in-memory cluster-reality model; triggers ConfigSnapshot rebuilds on change, debounced (§13.10 batching).

Policy Compiler. Translates PeerAuthentication and AuthzPolicy CRDs into the evaluatable form the sidecar's authz filter consults; default-deny (I6).

Telemetry Aggregator. In-memory rollup of control-plane-side metrics (xDS push latency, NACK rate, CA issuance rate); exposes Prometheus scrape endpoint; holds no long-term history (§26).

xDS Server. Owns the versioned ConfigSnapshot per node/node-group; serves the ADS bidirectional gRPC stream; tracks per-subscriber ACK state (AckState, §11); implements resource warming (§8.7 below is domain model; mechanism lives here).

mesh-ca. Holds the trust-domain root signing key; validates CSRs against the requester's Kubernetes ServiceAccount token (I9); issues short-lived SVIDs; manages trust-bundle rotation.

Sidecar Proxy. The data-plane process: xDS client subscribes over ADS; listeners accept on 15001 (outbound) and 15006 (inbound); filter chain applies authn/authz/rate-limit/ fault/router in order; cluster manager owns per-endpoint connection pools and the load balancer; admin/metrics bound to loopback only.

Traffic-interception layer. The init container's iptables/eBPF rules (§8.1) redirect all inbound and outbound TCP through the sidecar's two listener ports, excluding the sidecar's own egress by UID (I5).

mTLS engine. Embedded in the sidecar's transport-socket layer (rustls, ADR-06); terminates inbound, originates outbound, validates peer SPIFFE SAN against the trust bundle on every handshake.

6. Design Principles

P1 — Transparency Above Feature Richness. The mesh is transparent or it is a liability: zero application code change is required. Tradeoff: fewer L7 protocol integrations shipped early. Operational implication: every proposed feature is gated on "does this require an app change?" — if yes, redesign. Violating it: apps couple to sidecar internals, defeating the entire value proposition.

P2 — Identity Is Cryptographic, Never Network-Location-Based. IP addresses are not identities in a scheduler-managed cluster — pods are ephemeral and IPs are reused within minutes. Enforced via SPIFFE SVIDs (§8.4). Tradeoff: every workload needs a certificate, adding PKI operational burden. Violating it: authorization keyed on IP is trivially spoofable or stale after a reschedule.

P3 — Config Distribution Is Eventually Consistent, Design For It. xDS never guarantees synchronized application across sidecars; every sidecar must behave correctly while stale (I7). Tradeoff: momentary routing skew during rollout. Violating it: assuming synchronized config produces split-brain routing decisions during any push.

P4 — Fail Static, Never Fail Open On Security. A sidecar that loses control-plane connectivity keeps serving its last-known-good config rather than falling back to permissive/no-mTLS. Tradeoff: stale config for the duration of a possibly long outage. Violating it: a control-plane blip silently disables mTLS mesh-wide (§24 T4).

P5 — Interception Must Be Loop-Free By Construction. The sidecar's own egress must never be redirected back into itself (I5). Enforced by UID/owner exclusion rules (§8.1). Violating it: an infinite redirect loop, 100% CPU, total outage.

P6 — Certificate Rotation Never Drops A Live Connection. Rotation is additive (a new cert becomes available) not destructive (the old cert is revoked mid-use). Enforced by ArcSwap-style atomic handoff (I3). Violating it: every rotation window becomes a mini-outage.

P7 — Config Push Is Atomic Per Resource Type. A sidecar never observes half of a route table (I4). Enforced via versioned snapshot swap. Violating it: a request mid-push can match a route to a cluster that does not yet exist.

P8 — The Data Plane Degrades Gracefully, The Control Plane Fails Loud. Data-plane failures are locally contained (one pod); control-plane failures must be immediately visible (paged) because their blast radius is latent — it accrues only on the next config change or certificate expiry. Tradeoff: the control plane needs stronger alerting infrastructure than a typical stateless service.

P9 — Policy Denial Fails Closed. An authorization policy that cannot be evaluated (missing identity, expired cert, unreachable policy source) denies by default (I6, Saltzer & Schroeder 1975). Tradeoff: a policy-compiler bug can cause an outage rather than a silent security bypass — chosen deliberately.

P10 — Every Hot-Path Decision Is Lock-Free Or Amortized. Request-path code touches ArcSwap reads, atomic counters, and pre-compiled match structures; never a mutex on the request path. Violating it breaks the p99 latency budget (§4) under contention.

P11 — The Proxy Is Stateless With Respect To Configuration. All behavioral state (routes, clusters, certs) is externally supplied and swappable; only connection/counter state is intrinsic. Enables in-place config updates without restart. Violating it forces a restart per config change, destroying the no-dropped-connections invariant (I3).

P12 — One Trust Domain, One CA Root, No Ambiguity. Within this blueprint's scope every workload validates against exactly one root; cross-domain federation is a deferred, explicitly different problem (bundle exchange). Violating it — implicitly accepting multiple unrelated roots — opens a downgrade/impersonation path.

P13 — Observability Is Cardinality-Budgeted, Not Best-Effort. Metric label sets are fixed at design time (cluster, method, response-code — never raw path); unbounded telemetry is a self-inflicted denial of service (§24 T8). Violating it: a single high-cardinality label field can 10–100x the time-series count.

P14 — Retries Must Carry A Budget, Not Just A Count. A per-request retry count without a cluster-wide budget amplifies load on an already-failing upstream (Nygard, §5). Violating it: retry storms turn partial failure into total failure.

8.1 Traffic-interception model

Loop-avoidance mechanism. The sidecar process runs as a fixed UID (1337, kept for compatibility with the Istio convention cited in §5); every ruleset excludes traffic whose socket owner UID equals the sidecar's UID from outbound redirection, and excludes traffic whose destination port equals the sidecar's own inbound port from inbound redirection. The eBPF variant (PhaseDeferred("§13 Phase 1 — Traffic Interception And Loop Avoidance")) achieves the same exclusion via a cgroup/socket map keyed on cgroup id rather than UID.

8.6 Routing and traffic-split weight arithmetic

Given N WeightedCluster entries with weights w_i summing to W (not required to equal 100 — normalized), selection probability p_i = w_i / W. Implementation model: build a cumulative-weight array, draw uniform r ∈ [0, W), binary-search the first index whose cumulative weight ≥ r. Worked example: clusters v1 (w=90), v2 (w=10), W=100; draw r=45.2 → cumulative [90, 100] → 45.2 < 90 → select v1. Over 10,000 draws, expect v1 ≈ 9,000 ± 190 (binomial, p=0.9, n=10,000, σ ≈ 30, 2σ tolerance ≈ ±2%) — the tolerance used by the Phase 10 (§22) conformance fixture.

8.9 Policy evaluation model

AuthzPolicy = (principal_match: SpiffeId pattern, route_match: RouteMatch, effect: Allow|Deny). Evaluation order: most-specific route match first; default effect = Deny (I6). PeerAuthentication mode ∈ {STRICT, PERMISSIVE, DISABLE} is evaluated before any AuthzPolicy — STRICT rejects non-mTLS at the transport layer before an authz rule runs.

8.10 Worked end-to-end example — one request crossing two sidecars with mTLS

App on pod A calls payments.svc.cluster.local/api/charge. (1) Syscall hits the local stack; MESH_OUTPUT redirects to :15001 (§8.1). (2) Outbound listener's HTTP Connection Manager matches route /api/* → cluster outbound|80|payments. (3) Cluster manager selects an endpoint via least-request-power-of-two (ADR-15) from EDS-supplied endpoints. (4) Client sidecar opens TCP + mTLS handshake to the selected pod's :15006 (§8.5, steps 1–9); its own egress is not re-redirected (I5). (5) Server sidecar validates the peer cert, extracts PeerIdentity, evaluates AuthzPolicy (I6, §8.9), forwards to localhost:5000. (6) App responds; path reverses. Added latency: two hops × (TLS overhead + route match + policy eval), budgeted ≤ 6 ms p99 round-trip (§4).

8.11 Malformed-input examples

  • Config referencing an unknown cluster → the LDS resource enters Warming, never promotes, mesh_listener_warming_timeout_total fires (I12).
  • Expired peer certificate → handshake fails at CertificateVerify, mesh_mtls_handshake_failure_total{reason="expired"} (I14-adjacent).
  • xDS version regression (server sends a version_info lower than the client's applied version) → client detects via I2, discards, emits a malformed-response error.
  • Conflicting route match (two HttpMatch rules matching the same request with different clusters) → deterministic tie-break: first-defined wins, logged as a compile-time warning by mesh-config (Phase 4, §16).

8.12 Failure-path example — control-plane unavailability

The ADS stream drops; the xDS client (Phase 3, §15) applies exponential backoff with full jitter (base 1 s, cap 30 s). The Serving state (§8.8) continues on the last-applied ConfigSnapshot indefinitely (P4, I7). The certificate-rotation timer still fires, but CSR requests queue against the unreachable CA; if the outage exceeds the certificate-lifetime ceiling (§4, 24 h), the sidecar's own certificate expires and new connections fail — this is FM-4 (§25), mitigated operationally by control-plane HA (3 replicas, leader election, ADR-23) and alerting on xds_connected=0 well before the cert-expiry window is reached.

12.2 Detailed Implementation Steps

  • Initialize the workspace Cargo.toml, rust-toolchain.toml (ADR-30); mesh-types with error.rs (MeshError) and identity.rs stubs.
  • mesh-proxy: a Tokio TcpListener accept loop; copy_bidirectional for the byte-copy path (P11 — even this hardcoded version reads the upstream address from configuration, not a compiled constant).
  • Lock ADR-01 (Rust) / ADR-02 (Tokio) as the baseline; document rejected C++/Go/Java per §1 rationale in docs/adr/ADR-01.md.
  • CI (.github/workflows/ci.yml): cargo build --workspace, cargo test --workspace, cargo clippy -- -D warnings.
  • Explicit shutdown-on-EOF for both directions rather than relying solely on copy_bidirectional's default (§12.6).

12.3 Deliverable

curl localhost:8080 reaches a hardcoded backend on localhost:9000 through the mesh-proxy binary; CI green on push.

12.4 Acceptance Criteria

  • 1,000 sequential requests through the forwarder: 0 connection errors, p99 added latency ≤ 1 ms (loopback, no TLS yet — well under the §4 mTLS-inclusive 3 ms budget).
  • cargo test --workspace passes with ≥ 1 test per crate; cargo clippy zero warnings.

12.5 Conformance Fixtures

  • fixtures/phase0/basic-forward.toml — single request, expect 200 passthrough.
  • fixtures/phase0/half-close.toml — client closes write side early, expect graceful upstream half-close, no hang.
  • fixtures/phase0/upstream-unreachable.toml — hardcoded upstream down, expect a clean MeshError, never a panic.

12.6 Pitfalls

  • Missing half-close handling: one direction EOFs, the other hangs — manifests as a slow FD leak; debug via lsof on the proxy process; recovery: explicit per-direction shutdown.
  • Blocking the executor with a synchronous DNS resolve for the hardcoded upstream — manifests as a stalled accept loop under load; debug via task-starvation tracing; recovery: use an async resolver.
  • Treating one connection's copy error as fatal to the whole process — manifests as the entire proxy crashing on one bad peer; debug via panic backtrace; recovery: isolate errors per-connection task.

12.7 Performance Concerns

  • Copy-loop buffer size: too small increases syscall count, too large wastes memory per idle connection (§4 M4/M5 budget starts here) — default 16 KiB per direction.
  • Avoid per-connection heap allocation in the hot copy loop; reuse buffers where possible.

12.8 Edge Cases

  • Zero-byte connection (immediate close) — must not panic or leak an FD.
  • Upstream accepts but never sends data — no timeout exists yet in this phase; documented as a known gap closed in Phase 2 (§14).
  • Connection storm at startup before OS ulimits are tuned — must not exhaust FDs before the configured ceiling.

12.9 Failure Analysis

  • Upstream down at startup: every forwarded connection fails; detection via a connection-error counter (stderr-logged here, structured in Phase 11's telemetry, §23); blast radius: this crate only; recovery: fix upstream, no proxy restart needed since it dials per connection.

12.10 Operational Notes

  • No metrics/tracing yet (Phase 11, §23); stderr logging only, one line per connection lifecycle event.
  • No rollback procedure needed — Phase 0 holds no persistent state; redeploying the binary is the only "rollback."

13. Phase 1 — Traffic Interception And Loop Avoidance

13.1 Objectives

  • Redirect real traffic through the sidecar's inbound/outbound ports (15006/15001) per §3, §8.1, replacing Phase 0's hardcoded upstream.
  • Implement the init-container ruleset generator (mesh-inject, iptables_gen.rs).
  • Resolve SO_ORIGINAL_DST so the proxy recovers the true pre-NAT destination.
  • Prove loop avoidance (I5) with a startup self-test.

13.2 Detailed Implementation Steps

  • mesh-inject/src/iptables_gen.rs: generate the MESH_OUTPUT/MESH_INBOUND chains from §8.1's table, parameterized by sidecar UID (1337) and the inbound/outbound ports.
  • mesh-proxy: on outbound-listener accept, call getsockopt(SO_ORIGINAL_DST) (Stevens, Fenner, Rudoff ch. 7, §5) to recover the pre-NAT destination — without it the proxy cannot distinguish port-80 from port-443 traffic post-redirect.
  • Startup self-test enforcing I5 (P5): the sidecar issues a tagged loopback egress probe and asserts it is not observed arriving on the inbound-redirect port; refuse to start if it is.
  • Exclude localhost destinations and UDP/53 from outbound redirect per §8.1's exclusion column.
  • Lock ADR-03 (iptables); eBPF is PhaseDeferred("§13 Phase 1 — Traffic Interception And Loop Avoidance").

13.3 Deliverable

A pod with the init container applied redirects app-originated traffic through the sidecar transparently; a request from the app container to another pod's Service DNS name reaches its destination via both sidecars' redirect chains (still cleartext — mTLS is Phase 6, §18).

13.4 Acceptance Criteria

  • I5 self-test passes on 100/100 sidecar startups in CI (zero loop detections).
  • SO_ORIGINAL_DST resolves correctly for 100% of 10,000 redirected connections across ports 80/443/8080 in the fixture cluster.
  • Localhost and UDP/53 traffic measurably bypasses redirect (iptables -t nat -L -v packet counters read zero on the mesh chains for that traffic).

13.5 Conformance Fixtures

  • fixtures/phase1/loopback-exclusion.toml — app calls localhost:5000; expect zero redirect-chain packet count.
  • fixtures/phase1/dns-exclusion.toml — app resolves via UDP/53; expect zero redirect-chain packet count.
  • fixtures/phase1/original-dst-multi-port.toml — three concurrent connections to ports 80/443/8080; expect SO_ORIGINAL_DST correctly resolved for each.
  • fixtures/phase1/self-loop-probe.toml — a ruleset missing the UID exclusion; expect the startup self-test to refuse to start (I5 regression fixture).

13.6 Pitfalls

  • Init-container-after-app ordering leaves a window of unmediated traffic — manifests as sporadic cleartext connections at pod startup; debug via packet capture at pod-create time; recovery: enforce init-before-app ordering (native on K8s 1.28+ sidecar containers).
  • Missing the UID exclusion entirely — 100% CPU redirect loop on first sidecar egress; manifests as immediate CPU pin/OOM at startup; debug via the I5 self-test (13.2 exists precisely to catch this); recovery: fix the ruleset generator, redeploy.
  • IPv6 traffic bypassing IPv4-only rules on dual-stack nodes — manifests as intermittent silent breakage; debug via ip6tables -L counters; recovery: mirror the ruleset in ip6tables or force SingleStack.
  • Conntrack table exhaustion under high pod churn — manifests as connection failures unrelated to the app; debug via nf_conntrack_count vs. nf_conntrack_max; recovery: tune conntrack limits or migrate to eBPF (ADR-03's rejected-choice regime).

13.7 Performance Concerns

  • NAT lookups add per-packet overhead proportional to ruleset length; the mesh's chains stay short and jump early (§8.1's design).
  • SO_ORIGINAL_DST is one syscall per accepted connection — negligible against the §4 per-hop budget, but must never be called per-packet.

13.8 Edge Cases

  • A non-meshed pod alongside meshed pods — traffic to it must remain plain, non-mTLS (mixed-mesh boundary, revisited as §24 T4).
  • Partial iptables rule application failure — must not leave the pod half-redirected; recovery: the init container fails the pod create rather than leaving ambiguous rules.
  • Rapid pod restart reusing the same UID before conntrack entries expire — verify no stale redirect state misroutes the new pod's first connections.

13.9 Failure Analysis

  • Missing SO_ORIGINAL_DST kernel support — detection: startup capability probe; blast radius: the pod cannot mesh correctly; recovery: hard-fail at startup — the node is unschedulable for meshed pods until fixed, not runtime-recoverable.
  • A loop-avoidance regression in a mesh-inject update — detection: the I5 self-test catches it before the pod ever serves traffic; blast radius contained to that one pod.

13.10 Operational Notes

  • Emit mesh_intercept_loop_detected (I5 telemetry) and a startup-refusal log line naming the failing rule.
  • This phase is prerequisite reading for the bad-config-rollback runbook (§26).

14. Phase 2 — The L7 HTTP Filter Chain

14.1 Objectives

  • Parse HTTP/1.1 and HTTP/2 (including gRPC framing) atop the Phase 1 interception layer.
  • Introduce the filter-chain abstraction with a terminal router filter.
  • Implement path/host/header-based route matching from static config (xDS-driven config arrives in Phase 3/4).

14.2 Detailed Implementation Steps

  • mesh-proxy/src/hcm.rs: the HTTP Connection Manager parses frames via h2 (RFC 9113) and an HTTP/1.1 parser (RFC 9110); maintains the ordered filter stack [authn|authz|ratelimit|fault|router] (§3) — authn/authz/ratelimit/fault are no-op passthroughs until Phases 6/9/10; router is Envoy's source/common/router/ pattern (§5), the only live filter this phase.

  • Static config loader: YAML-defined Listener/RouteConfig/ClusterConfig (§11), swapped via ConfigSnapshot/ArcSwap (P7, P11) — this proves the atomic-swap mechanism (I4) before Phase 3 adds the network source.
  • Route per request, not per connection: one HTTP/1.1 keep-alive connection can carry requests to different upstreams (P11).

14.3 Deliverable

A YAML-configured proxy routes /api/payments/* to backend A and /api/users/* to backend B over HTTP/1.1 and HTTP/2/gRPC, hot-reloading on file change with zero dropped in-flight requests (I4 exercised without a network control plane).

14.4 Acceptance Criteria

  • 10,000-request routing fixture: 100% correct backend selection by path prefix.
  • Config hot-reload under load: 0 requests observe a half-applied route table (partial-apply-probe fixture, I4).
  • gRPC unary + server-streaming + bidi round-trip: 0 stream resets attributable to the proxy.
  • p99 route-match latency ≤ 50 µs at 5,000 loaded routes (pre-compiled match structure, P10).

14.5 Conformance Fixtures

  • fixtures/phase2/path-routing.yaml — mixed prefixes; expect the exact backend map from §14.4.
  • fixtures/phase2/keepalive-reroute.toml — one HTTP/1.1 connection, sequential requests to different routes; expect correct per-request routing.
  • fixtures/phase2/malformed-http1.toml — truncated/invalid request line; expect a clean local error reply, never a panic (differential-tested per §28).
  • fixtures/phase2/h2-flow-control-stall.toml — a slow-reading client on one HTTP/2 stream; expect window updates respected, no unbounded buffering (ADR-32).

14.6 Pitfalls

  • Buffering a full request/response body before forwarding — manifests as OOM on large uploads; debug via RSS growth correlated with request size; recovery: stream-process or cap body size (ADR-32).
  • Confusing per-stream and per-connection HTTP/2 flow control — manifests as one slow stream stalling unrelated streams; debug via h2 window-size logging; recovery: honor both levels independently.
  • Treating a keep-alive connection as single-route — manifests as stale routing on a reused connection; debug via per-request route-match logging; recovery: re-match every request (P11).
  • Baking filter-order assumptions in before authn/authz exist — manifests as a later phase's filter landing in the wrong position; debug via the ordered filter-stack config diff; recovery: fix the chain order once, in one place (finalized Phase 9/10).

14.7 Performance Concerns

  • Header parsing must not allocate per header (zero-copy where the HTTP library allows).
  • Route matching must be pre-compiled (prefix tree / match-set), never a linear scan, to hold the ≤ 50 µs target at 5,000 routes.
  • Filter-chain dispatch cost is bounded indirect calls (N filters × M phases); keep filter count small until Phase 9/10 add real ones.

14.8 Edge Cases

  • Chunked transfer-encoding combined with a route rewrite must not corrupt chunk framing.
  • HTTP/2 trailers on a gRPC call (status carried in trailers) — router must not treat a trailers-only response as headers-only.
  • An HTTP/1.0 client (no keep-alive) must close cleanly, never hang awaiting a next request.
  • Config hot-reload racing an in-flight request that matched the old table must complete against the table it matched (I4), never the new one mid-flight.

14.9 Failure Analysis

  • Malformed HTTP triggering a parser panic — detection: the differential fuzz corpus (§28, ADR-28) run continuously in CI catches this pre-release; blast radius if it escapes: one connection, isolated per-connection task (carried from Phase 0, §12.6).
  • A route table with a conflicting match — detection: compile-time warning (§8.11); recovery: deterministic first-defined-wins, never a panic.

14.10 Operational Notes

  • Structured stderr logging per request this phase (real access logs land in Phase 11, §23); include the matched route name for debuggability.
  • No metrics exposition yet; route-match latency measured via the benchmarks/ harness (§10), not yet exported.

15. Phase 3 — The xDS Client With ACK/NACK And Version Tracking

15.1 Objectives

  • Replace the Phase 2 file-based config source with a gRPC ADS stream client (mesh-xds-client).
  • Implement the ACK/NACK/version/nonce state machine per §8.2's sequence table.
  • Enforce version-monotonicity (I2) and resource warming (I12) client-side.

15.2 Detailed Implementation Steps

  • mesh-xds-client/src/ads_stream.rs: a tonic bidirectional gRPC client implementing AggregatedDiscoveryService.StreamAggregatedResources (Envoy xDS protocol documentation, §5); reconnect with full-jitter exponential backoff, base 1 s, cap 30 s (P4, §8.12).
  • mesh-xds-client/src/ack_nack.rs: AckState (§11) per resource type; on successful apply, send DiscoveryRequest{version_info=applied, response_nonce=received}; on failure, send {version_info=last_good, response_nonce=received, error_detail} — the exact shape of §8.2 steps 4/8.
  • mesh-xds-client/src/snapshot.rs: assemble the multi-resource-type ConfigSnapshot; install via ArcSwap only when internally consistent (P7, I4) — a listener referencing an unresolved cluster stays in the warming pending-set (I12) rather than entering the active snapshot.
  • Version-monotonicity guard (I2): reject any DiscoveryResponse whose version_info regresses relative to AckState.last_acked_version (Lamport 1978's ordering-without-shared-clocks lesson: version_info is the client's only ordering signal — trust it strictly).
  • Wire this client into mesh-proxy's listener/router/cluster-manager, replacing the Phase 2 YAML loader (retained as a local-dev fallback, not deleted).

15.3 Deliverable

mesh-proxy subscribes over ADS to a stub control-plane test harness (not yet the real mesh-xds-server of Phase 4); it applies pushed config with no restart, ACKs correctly, and NACKs a deliberately malformed push while retaining the last-good config (I8 exercised end-to-end for the first time).

15.4 Acceptance Criteria

  • ACK round-trip latency (push to ACK receipt) ≤ 20 ms p99 against the local test harness.
  • Version-regression fixture: 100% rejection rate (I2) across 1,000 injected regressions.
  • NACK fixture: 100% of subsequent requests continue routing against the pre-push config after a malformed push (0 requests observe the rejected config, I8).
  • Reconnect fixture: kill the stub server for 10 s, restart; proxy reconnects within backoff-cap + 1 s, resumes serving without having dropped its in-memory snapshot.

15.5 Conformance Fixtures

  • fixtures/phase3/initial-ads-handshake.toml — cold start, subscribe to all resource types; expect a full snapshot ACKed.
  • fixtures/phase3/version-regression.toml — server sends a lower version_info; expect I2 rejection, no apply.
  • fixtures/phase3/malformed-push-nack.toml — an invalid LB policy string in a CDS push; expect a NACK with populated error_detail, prior snapshot retained.
  • fixtures/phase3/reconnect-replay.toml — stream drop mid-push; expect clean resubscription with no duplicate or lost resource.
  • fixtures/phase3/dangling-cluster-warming.toml — LDS references an unresolved cluster; expect warming (I12), never promoted, mesh_listener_warming_timeout_total fires past timeout.

15.6 Pitfalls

  • Applying a DiscoveryResponse before validating its version against AckState — manifests as an intermittent I2 violation under network reordering; debug via a version-history log; recovery: validate strictly before any mutation.
  • ACKing a resource that only partially applied — manifests as an inconsistent snapshot the server believes is confirmed; debug via a snapshot-consistency assertion at swap time; recovery: build the candidate snapshot off to the side, validate, then swap atomically — never ACK a partially built snapshot.
  • Reconnect storms after a control-plane restart with no jitter — manifests as a synchronized thundering herd; debug via a connection-attempt timestamp histogram; recovery: full-jitter backoff (specified in 15.2, easy to regress).
  • Re-ACKing a resource already NACKed without an intervening new version — this phase's client-side half of I8; recovery: track pending_nack in AckState and refuse.

15.7 Performance Concerns

  • Snapshot assembly must never block the request path; perform it on a dedicated task and swap via ArcSwap only at the end.
  • A full-cluster snapshot at 5,000 clusters (§4 ceiling) must stay within the gRPC message size limit or the transport must be configured for a larger frame — measured explicitly in this phase's benchmark.

15.8 Edge Cases

  • An empty DiscoveryResponse must not be treated as "clear all resources" — xDS wildcard-subscription semantics forbid deleting resources on an empty push.
  • A duplicate DiscoveryResponse (same version and nonce, e.g. after a reconnect race) must be idempotently ACKed without reapplying side effects twice.
  • Clock skew never affects version_info (a string, per §11, not a timestamp) — the comparator is lexicographic-server-defined, never parsed as wall-clock time.

15.9 Failure Analysis

  • Stub-server crash mid-stream — detection: gRPC stream error; blast radius: this one sidecar continues on last-known-good (P4); recovery: automatic reconnect (15.2), no operator action unless the outage exceeds the cert-lifetime ceiling (§8.12).
  • Snapshot-assembly panic — detection: task panic caught at the task boundary (never crashes the process); blast radius: that one snapshot update drops, previous snapshot stays active; recovery: alert on the assembly-failure counter, fix and re-push.

15.10 Operational Notes

  • Emit mesh_xds_version_regression_total, mesh_xds_nack_total, mesh_listener_warming_timeout_total (I2/I8/I12 telemetry), stubbed as counters here, fully exposed in Phase 11 (§23).
  • This phase's stub control-plane server is throwaway; Phase 4 replaces it with mesh-xds-server without changing the client contract (the ADS protocol itself is the compatibility boundary, ADR-11).

16. Phase 4 — The Control-Plane Discovery Service And xDS Server

16.1 Objectives

  • Build mesh-xds-server: snapshot cache, per-node ACK tracking, LDS/RDS/CDS/EDS/SDS translation.
  • Build mesh-discovery: a Kubernetes watcher translating Services/Endpoints/ EndpointSlices into EDS LoadAssignments.
  • Implement server-side resource-warming gating (I12) and debounced push batching.

16.2 Detailed Implementation Steps

  • mesh-xds-server/src/snapshot_cache.rs: a per-node (or node-group) versioned ConfigSnapshot store, following the snapshot-cache pattern from Istio's pilot/pkg/xds/ (§5) — publish new snapshots, diff per subscriber against last-sent, push only changed resource types.
  • mesh-xds-server/src/lds.rs/rds.rs/cds.rs/eds.rs/sds.rs: translate mesh-config CRDs (VirtualService/DestinationRule) plus mesh-discovery's cluster-reality model into the five xDS resource types per §8.2's table.
  • mesh-discovery/src/k8s_watcher.rs: informers on Services, Endpoints/EndpointSlices, and mesh-config CRDs (ADR-13); endpoint_translator.rs converts to LoadAssignment (§11).
  • Push debouncing: batch cluster-reality changes into ≤ 100 ms windows before triggering a snapshot rebuild — avoids every pod flap triggering an individual push.
  • ADS ordering: CDS before EDS before RDS before LDS on every push (§8.3) — make-before-break, fully shipping new resources before tearing down old ones.
  • Control-plane HA wiring (ADR-23): leader election via the K8s Lease API for the CA-signing role (Phase 5); the xDS server itself is stateless-replicated — any replica serves any node, since the snapshot cache is rebuildable from K8s API state (ADR-14).

16.3 Deliverable

A real mesh-xds-server replaces Phase 3's stub; mesh-discovery watches a live test-cluster's Services/Endpoints and mesh-config CRDs; editing a VirtualService CRD propagates to a subscribed sidecar's route table within the §4 convergence budget.

16.4 Acceptance Criteria

  • xDS push compute+serialize latency p99 ≤ 50 ms for a 500-endpoint change (§4 M9).
  • Convergence time across N = 1,000 simulated sidecars p99 ≤ 5 s (§4 M8; Phase 11 repeats this at full scale).
  • Debounce fixture: 1,000 rapid pod-churn events within 1 s collapse into ≤ 10 snapshot rebuilds.
  • Zero dangling-reference pushes reach any sidecar across the 10,000-request ADS-ordering fixture.

16.5 Conformance Fixtures

  • fixtures/phase4/vs-to-rds-propagation.toml — VirtualService edit; expect an RDS push and correct sidecar-side apply within budget.
  • fixtures/phase4/ads-ordering.toml — simultaneous CDS+EDS+LDS change; expect CDS-before-EDS-before-RDS-before-LDS delivery order.
  • fixtures/phase4/debounce-storm.toml — 1,000 endpoint flaps in 1 s; expect ≤ 10 rebuilds.
  • fixtures/phase4/replica-failover.toml — kill the serving xDS-server replica mid-stream; expect the sidecar's Phase-3 reconnect to land on a healthy replica with an equivalent snapshot.

16.6 Pitfalls

  • Sending EDS before its referencing CDS cluster exists even within ADS — manifests as sidecar-side warming stalls; debug via the ADS send-order log; recovery: enforce CDS-first ordering server-side, not only client-side warming as a backstop.
  • Rebuilding the entire snapshot on every single pod event — manifests as control-plane CPU pinned under normal churn; debug via the rebuild-rate metric; recovery: debounce (16.2).
  • Unbounded snapshot-cache growth across high-cardinality node-groups (per-sidecar unique scoping) — manifests as control-plane memory growth; debug via the snapshot-cache-size metric; recovery: cap node-group granularity, revisit sidecar-scoping in §31.
  • Treating "no NACK received yet" as "config applied" — the server must wait for an explicit ACK, never assume success from silence (I8's server-side half).

16.7 Performance Concerns

  • Per-subscriber diffing at push time must be O(changed resources), not O(total resources), or the §4 control-plane QPS ceiling (5,000 req/s at 10k sidecars) is unreachable.
  • K8s informer resync intervals and watch-cache size trade memory for API-server load; tune per §31's control-plane-QPS analysis.

16.8 Edge Cases

  • A CRD referencing a Service that does not yet exist (create-order race) — held pending like a dangling xDS reference, at the config-compile layer rather than xDS itself.
  • EndpointSlice sharding (a large Service split across multiple slice objects) — the translator must reassemble the full endpoint set correctly.
  • Two xDS-server replicas racing to publish for the same node — resolved via the K8s API server as sole source of truth (ADR-14): both replicas recompute from identical K8s state and converge to the same version deterministically.

16.9 Failure Analysis

  • K8s API server unreachable from the control plane — detection: informer watch-error metric; blast radius: no new config changes propagate, but existing sidecars keep serving (P4 at one remove); recovery: automatic informer reconnect, no data-plane impact.
  • An xDS-server replica crashes mid-push to N sidecars — detection: gRPC stream errors on affected sidecars; blast radius: those sidecars fail over to another replica via Phase-3 reconnect; recovery: automatic, given ADR-23 HA.

16.10 Operational Notes

  • Emit mesh_xds_push_latency_ms, mesh_xds_convergence_seconds, mesh_snapshot_rebuild_total (control-plane telemetry, labeled by resource type only, never by node, per P13).
  • Runbook cross-reference: control-plane-outage-with-data-plane-survival (§26) is first exercisable after this phase.

17. Phase 5 — The CA, SVID Issuance And Identity

17.1 Objectives

  • Build mesh-ca: root key custody, CSR validation against Kubernetes ServiceAccount tokens (I9), SVID signing.
  • Wire the SDS-adjacent CSR flow end to end per §8.4's sequence table.
  • Establish trust-bundle distribution to sidecars (mTLS consumption is Phase 6, §18).

17.2 Detailed Implementation Steps

  • mesh-ca/src/root.rs: generate/load the trust-domain root signing key, custody per ADR-08 (in-memory plus sealed backup, not HSM in this scope).
  • mesh-ca/src/svid_issuer.rs: implement §8.4 steps 5–8 — validate the ServiceAccount token's signature against the API server's public key, validate aud/namespace/ service-account claims match the requested SAN (I9), sign with not_after = now + 24h (§4, I14 enforced as a hard ceiling check before signing).
  • Sidecar side: generate an ECDSA P-256 keypair in memory at startup (never persisted, ADR-06), build the CSR with the SPIFFE URI SAN (§8.4 grammar), read the projected ServiceAccount token, call CreateSvidRequest over the SDS-adjacent gRPC channel.
  • Trust-bundle push: mesh-ca publishes the current root(s) as an SDS resource; sidecars install into their TLS validation context (consumed in Phase 6, delivery proven here).
  • CSR audit logging: log (requester_identity, granted_identity, issued_at, expires_at, requester_source) for every issuance — raw material for the §24 T2 anomaly detection.

17.3 Deliverable

A freshly started sidecar in the test cluster obtains a real, CA-signed SVID with the correct SPIFFE URI SAN within the startup Warming window (§8.8); the CA rejects a CSR whose SAN does not match its ServiceAccount token.

17.4 Acceptance Criteria

  • End-to-end CSR-to-cert latency ≤ 2 s p99 (startup path).
  • 100% rejection rate on 1,000 forged-SAN CSR probes (I9 fixture).
  • Every issued cert satisfies not_after - not_before ≤ 24h (I14) across 10,000 issuances.
  • Audit-log completeness: 100% of issuances produce a matching audit record.

17.5 Conformance Fixtures

  • fixtures/phase5/legit-csr-issue.toml — correct SA token and SAN; expect a signed cert with the correct SPIFFE URI.
  • fixtures/phase5/forged-san-csr.toml — SAN namespace mismatched to token namespace; expect rejection (I9).
  • fixtures/phase5/expired-sa-token.toml — an expired projected token; expect rejection, no signing.
  • fixtures/phase5/lifetime-ceiling-probe.toml — a CSR requesting a longer lifetime than policy; expect the CA to clamp to the ceiling, never honor the request (I14).

17.6 Pitfalls

  • Trusting the CSR's stated SAN without independently deriving it from validated token claims — manifests as a forgeable identity path; debug via a differential test comparing CSR-stated vs. token-derived SAN; recovery: always derive the SAN server-side, never trust the client's claim — this is I9's actual enforcement point.
  • Persisting the sidecar's private key to disk "for debugging" — manifests as a key-exfiltration risk surviving pod restart; debug via a filesystem-write audit in CI; recovery: in-memory only, no exception.
  • Signing with a lifetime longer than the policy ceiling due to a caller-supplied parameter — manifests as an I14 violation; debug via the issuance-audit lifetime field; recovery: server-side clamp, never trust caller input for lifetime.
  • Under-rate-limiting the CA against a compromised or buggy sidecar issuing CSRs in a loop — manifests as CA CPU exhaustion; debug via a per-identity issuance-rate metric; recovery: per-ServiceAccount rate limit at the CA.

17.7 Performance Concerns

  • ECDSA P-256 signing throughput must meet the §34-derived issuance-rate figure (workload count ÷ cert lifetime); benchmark signing ops/sec on the target CPU class.
  • Token-signature validation against the API server's public key should be cached (the key rotates rarely) to avoid a network round trip per CSR.

17.8 Edge Cases

  • A ServiceAccount deleted between token issuance and CSR arrival — the CA must re-validate live, not rely solely on the token's embedded claims, to avoid signing for a now-nonexistent identity.
  • Clock skew between sidecar and CA producing a token that appears not-yet-valid — the CA tolerates a small skew window while never extending trust indefinitely.
  • Two sidecars of the same ServiceAccount replica set requesting SVIDs simultaneously — the CA issues both without treating the second as forgery (SPIFFE IDs here are per-workload-class, not per-instance; instance-level identity is a design note for §37 if ever needed).

17.9 Failure Analysis

  • CA process crash mid-issuance — detection: gRPC error to the requesting sidecar; blast radius: that sidecar retries the CSR (idempotent — a private key is never split, so no partial-signature state exists); recovery: automatic retry with backoff, ADR-23 HA bounds total downtime.
  • Root key corruption or loss — detection: signing-operation failure at startup; blast radius: total mesh identity outage; recovery: restore from sealed backup (ADR-08) — this is the single highest-severity failure mode in the system (§24 T2).

17.10 Operational Notes

  • Emit mesh_ca_csr_rejected_total, mesh_ca_cert_lifetime_violation_total (I9/I14 telemetry) and the full audit-log stream (exported, not stored in-process, §26).
  • Runbook cross-reference: cert-expiry-emergency (§26) draws on this phase's issuance path for its recovery steps.

18. Phase 6 — mTLS Termination And Origination With Peer Validation

18.1 Objectives

  • Consume the Phase 5 SVID and trust bundle to terminate inbound and originate outbound mTLS.
  • Implement peer-identity extraction and validation per §8.5's handshake sequence.
  • Wire PeerIdentity into the pass-through authz filter stub from Phase 2.

18.2 Detailed Implementation Steps

  • mesh-proxy/src/mtls.rs: rustls (ADR-06) ServerConfig/ClientConfig built from the CertBundle/TrustDomain (§11); the inbound listener requires a client cert under MtlsMode::Strict; the outbound cluster presents the workload's own SVID.
  • Peer validation: on handshake completion, validate the peer chain against the trust bundle (RFC 5280), extract the SPIFFE URI SAN, construct PeerIdentity (§11); reject (I1) any peer cert lacking a SPIFFE URI SAN.
  • ALPN negotiation to h2 by default for mTLS connections (RFC 9113), with HTTP/1.1 fallback configurable — matches Phase 2's HCM.
  • Listener-filter TLS inspection: peek the ClientHello (SNI/ALPN) without consuming bytes, to select the correct filter chain before terminating TLS.
  • Wire PeerIdentity into mesh-policy's authz_eval stub — this phase guarantees identity is available to later filters; policy-decision logic itself is Phase 10 (§22).

18.3 Deliverable

Two sidecars in the test cluster complete a full mTLS handshake using real Phase-5-issued SVIDs; the server sidecar extracts the correct SPIFFE identity from the client cert; a connection presenting no client cert or an untrusted-root cert is rejected per I1.

18.4 Acceptance Criteria

  • 100% of 10,000 inbound connections with valid SVIDs extract the correct SPIFFE URI SAN.
  • 100% rejection rate for connections presenting a cert signed by an untrusted root (I1 fixture, 1,000 probes).
  • mTLS full-handshake rate ≥ 4,000/s/core (§4 M6) on the target CPU class.
  • ALPN negotiates h2 in ≥ 99% of mTLS connections in the fixture cluster.

18.5 Conformance Fixtures

  • fixtures/phase6/valid-mtls-roundtrip.toml — two real SVIDs; expect a successful handshake and correct PeerIdentity extraction.
  • fixtures/phase6/untrusted-root-reject.toml — a cert signed by a foreign root; expect handshake rejection (I1).
  • fixtures/phase6/missing-san-reject.toml — a well-formed cert with no SPIFFE URI SAN; expect rejection.
  • fixtures/phase6/no-client-cert-strict.toml — STRICT mode, no client cert; expect rejection at the transport layer before any authz filter runs (§8.9).

18.6 Pitfalls

  • Accepting a cert whose chain validates but whose SAN is absent or malformed — manifests as a "successful" handshake with no usable identity downstream; debug via a PeerIdentity-is-None assertion on every accepted mTLS connection; recovery: treat a missing SAN as a hard reject, never a degraded-identity connection (I1).
  • Excluded-port cleartext bypass — the historical CVE-2020-15104 pattern (§24) — traffic on an operator-excluded port carrying no encryption even under STRICT policy elsewhere; debug via a plaintext-egress canary probe (I1 telemetry); recovery: every exclusion requires explicit audit-logged justification, never a silent default.
  • SNI/path normalization mismatches between the TLS-inspector's peek and the HCM's later parse — the CVE-2021-39156 pattern (§24) — filter-chain selection disagrees with route matching; debug via a normalize-once test; recovery: canonicalize exactly once, at the earliest point, never re-derive downstream.
  • Silently falling back to HTTP/1.1 when h2 negotiation fails unexpectedly — masks a real ALPN misconfiguration; debug via the ALPN-negotiation-outcome metric; recovery: alert on fallback rate exceeding baseline.

18.7 Performance Concerns

  • ECDSA P-256, not RSA-4096, is the mandated key type (§8.4) specifically to hold the §4 handshake-rate targets — verify in the benchmark, not only at code review.
  • Session resumption (TLS 1.3 PSK) is wired from this phase onward to reach the §4 M7 resumed-handshake target; deferring it to Phase 7 would understate this phase's own acceptance criteria.

18.8 Edge Cases

  • A peer cert within its validity window but issued under a since-rotated CA root still present in a stale trust bundle — must still validate (rotation overlap is intentional, §8.4), logging a metric distinguishing old-root vs. new-root validations.
  • Simultaneous handshakes from the same peer during a burst — must not serialize unnecessarily; each handshake is independent.
  • A non-meshed client attempting a plaintext connection to a STRICT-mode inbound listener — rejected at the TLS layer, never accepted and denied only at the application-layer filter (defense-in-depth ordering, §8.9).

18.9 Failure Analysis

  • Trust-bundle push failure leaving a sidecar with a stale bundle during a root rotation — detection: bundle-version-lag metric; blast radius: that sidecar rejects peers signed by the new root until caught up; recovery: retry the SDS push, alert past a lag threshold (foreshadows Phase 7's rotation-without-drop guarantee).
  • A rustls internal panic on a malformed ClientHello — detection: the CI fuzz corpus (ADR-28) targets the TLS-inspector peek path specifically; blast radius: one connection, isolated task; recovery: patch and re-fuzz.

18.10 Operational Notes

  • Emit mesh_mtls_violation_total, mesh_mtls_handshake_failure_total{reason} (I1 telemetry) and ALPN-negotiation-outcome counters.
  • This phase delivers the mesh's core zero-trust promise (§2) — treat its conformance fixtures as release-blocking from here forward.

19. Phase 7 — Certificate Rotation Without Connection Loss

19.1 Objectives

  • Implement re-CSR scheduling at 50%±10% jittered lifetime (§4, §8.4 step 10).
  • Guarantee I3 (rotation never drops an in-flight connection) under continuous load.
  • Implement CA root rotation with dual-root trust-bundle overlap.

19.2 Detailed Implementation Steps

  • mesh-ca/src/rotation.rs: a jittered re-CSR timer per sidecar (P6); trust-bundle rotation publishes both old and new roots simultaneously during an overlap window, dropping the old root only after it has fully aged out (≥ the cert-lifetime ceiling, §4).
  • Sidecar CertBundle swap: build the new bundle fully (cert+key+chain) off to the side, then a single ArcSwap installs it atomically (P6, I3) — never swap cert and key as separate operations (the historical race documented in §19.6).
  • Continuous-load rotation soak harness (benchmarks/ + conformance/): sustained request traffic across a rotation event, asserting zero connection resets attributable to the swap.
  • CA-load jitter (§4, ADR-09): stagger re-CSR timers so N sidecars sharing a lifetime do not all hit the CA within the same second; verify via a CA-request-rate histogram under a 10,000-sidecar simulation.
  • Compromise-response procedure: rotate the cluster CA root, push a trust bundle containing only the new root — old certs become untrusted even though nominally unexpired (§8.4, revocation-by-attrition rather than CRL/OCSP per ADR-09).

19.3 Deliverable

A sidecar under sustained load rotates its certificate at the scheduled jittered time with zero measured connection drops; a simulated CA-root-compromise drill rotates the root and revokes trust in the old root within one push cycle.

19.4 Acceptance Criteria

  • Continuous-load rotation soak: 0 connections dropped across 100 rotation events at 10,000 req/s sustained load (I3, the fixture named in §7's debugging methodology).
  • CA request-rate under a simulated 10,000-sidecar jittered rotation stays within the §4 control-plane QPS ceiling, never spiking beyond a documented multiple of steady-state.
  • Compromise-response drill: old-root-signed certs are rejected mesh-wide within one SDS push cycle (≤ the §4 xDS convergence budget, 5 s p99 at N=1,000).

19.5 Conformance Fixtures

  • fixtures/phase7/rotation-under-load.toml — the I3 continuous-load soak, 100 rotation events, 0 drops required.
  • fixtures/phase7/jitter-distribution.toml — 10,000 simulated sidecars; expect re-CSR timestamps distributed, not thundering-herded.
  • fixtures/phase7/dual-root-overlap.toml — a peer cert signed by the outgoing root during the overlap window; expect successful validation.
  • fixtures/phase7/compromise-response-drill.toml — root rotation plus old-root revocation; expect old-root certs universally rejected post-push.

19.6 Pitfalls

  • Swapping cert and key as two separate atomic operations — manifests as a race window where handshakes see a mismatched cert/key pair; debug via a stress test rotating under maximum handshake concurrency; recovery: single-pointer ArcSwap of the whole CertBundle triple (19.2).
  • Unstaggered rotation timers — manifests as CA request-rate spikes exactly at each cert's lifetime boundary; debug via a request-rate histogram bucketed by time-since-issuance; recovery: jitter (specified already, easy to regress under a refactor).
  • Dropping the old root from the trust bundle before all certs signed under it have expired — manifests as valid, unexpired certs suddenly failing validation; debug via a bundle-version vs. active-cert-age cross-check; recovery: hold the old root until its last dependent cert's not_after has passed.
  • Forcing existing connections to re-handshake on rotation "to be safe" — manifests as unnecessary connection churn, defeating I3's purpose; recovery: never force a re-handshake; let connections age out naturally.

19.7 Performance Concerns

  • The rotation soak must run at the full §4 handshake-rate target concurrently with steady request traffic — rotation may not consume a CPU budget the request path needs.
  • CA signing throughput at scale (§34's derived issuance-rate number) must be validated under this phase's jittered-load fixture, not only a single-request benchmark.

19.8 Edge Cases

  • A sidecar that misses its jittered rotation window (paused, e.g. by a debugger, or a node under memory pressure) as cert expiry approaches — must trigger an out-of-band emergency re-CSR rather than waiting for the next scheduled window.
  • Two rotations overlapping (a slow re-CSR still in flight when the next is already due) — the scheduler must not double-fire; track a single in-flight rotation state.
  • CA temporarily unreachable exactly at a sidecar's scheduled rotation time — falls into the shared exponential-backoff retry path (§8.12), not a distinct code path.

19.9 Failure Analysis

  • A CA outage spanning a large fraction of the cert lifetime — detection: time_to_cert_expiry crossing a warning threshold well before zero; blast radius: sidecars whose rotation window falls inside the outage risk expiry; recovery: CA HA (ADR-23) bounds outage duration; alerting fires long before expiry per §4's RTO figures.
  • A rotation bug causing all sidecars to receive certs with an incorrect SPIFFE URI simultaneously — detection: SAN-mismatch validation failures spiking mesh-wide at once; blast radius: total mesh outage at the shared expiry boundary of the previous (correct) certs; recovery: this is exactly why jitter and canary rollout (rotate 1%, hold, then proceed) are mandatory operational practice, documented in §26.

19.10 Operational Notes

  • Emit mesh_conn_dropped_during_rotation (I3 telemetry — target always zero), CA request-rate histograms, and bundle-version-lag metrics.
  • Runbook cross-reference: cert-expiry-emergency (§26) is written directly against this phase's failure analysis.

20. Phase 8 — Load Balancing, Health Checking And Outlier Ejection

20.1 Objectives

  • Implement least-request power-of-two-choices load balancing (ADR-15) over EDS-supplied endpoints.
  • Implement the outlier-ejection state machine (§8.7) with a capped ejection percentage (I11).
  • Wire active (EDS-reported) and passive (locally observed) health signals together.

20.2 Detailed Implementation Steps

  • mesh-proxy/src/lb.rs: sample 2 endpoints uniformly, pick the one with fewer in-flight requests (Mitzenmacher 2001, ADR-15) — O(1) per selection.
  • OutlierState (§11) per endpoint: an atomic consecutive_5xx counter and ejected_until timestamp; ejection triggers per §8.7's HEALTHY→EJECTED edge, gated by the I11 cap check before every new ejection.
  • Un-ejection: base_ejection_time elapses → HEALTHY (probationary); a repeat offense before cooldown → exponential ejection-time doubling (flap prevention, §8.7's last row).
  • Composed health: an endpoint is LB-eligible only if both the EDS-reported signal and the local ejection state agree it is healthy.
  • Locality-aware selection stub: Endpoint.locality consulted as a same-zone preference weight, never a hard filter (§20.6).

20.3 Deliverable

Under an injected 30% error rate on one endpoint of a three-endpoint cluster, the LB shifts traffic away from the bad endpoint, ejects it past threshold, and un-ejects it once healthy again, with no operator intervention.

20.4 Acceptance Criteria

  • Load spread across 3 equally-healthy endpoints within ±5% of even (10,000-request fixture).
  • Ejection triggers within interval plus jitter of crossing the consecutive-5xx threshold — detection latency ≤ 5 s (M11).
  • I11 cap enforced: with all 3 endpoints failing simultaneously and max_ejection_percent = 50%, at least 1 endpoint remains eligible.
  • Un-ejection restores an endpoint to LB rotation within base_ejection_time ± measurement jitter of recovery.

20.5 Conformance Fixtures

  • fixtures/phase8/power-of-two-spread.toml — 3 healthy endpoints; expect even load spread.
  • fixtures/phase8/outlier-eject-recover.toml — 30% error injection then recovery; expect eject-then-rejoin per §8.7.
  • fixtures/phase8/ejection-cap.toml — all endpoints failing; expect the I11 cap holds ≥ 1 eligible endpoint at a 50% cap.
  • fixtures/phase8/flap-backoff.toml — repeated failure before cooldown elapses; expect doubling ejection time, not a fixed cooldown.

20.6 Pitfalls

  • Ejecting on a tiny sample size — manifests as spurious ejections under low traffic; debug via the consecutive-5xx-to-total-requests ratio; recovery: require a minimum request-count floor before evaluating consecutive_5xx.
  • Un-ejecting without recomputing I11's cap on the resulting state — recovery: recompute eligible-count invariantly on every transition, not only on eject.
  • LB selection reading endpoint state via a lock instead of an atomic — manifests as a p99 regression under high endpoint counts; debug via lock-contention profiling; recovery: P10's lock-free mandate.
  • Locality preference silently starving cross-zone endpoints once same-zone capacity is insufficient — manifests as latent overload; recovery: locality preference is a weight, never a hard filter.

20.7 Performance Concerns

  • Power-of-two-choices sampling cost is O(1) regardless of cluster size — verify at the §4 ceiling (5,000 clusters / 50,000 endpoints), not only at small N.
  • Outlier-state atomics must not become a contention point at the §4 10,000 req/s per-sidecar target — benchmark under full concurrency, not a single-threaded microbenchmark.

20.8 Edge Cases

  • A cluster with exactly one endpoint — LB trivially selects it; ejecting the sole endpoint must still respect I11 (0% eligible is never fabricated as healthy; a fail-fast 503 is the correct outcome, not a bug).
  • An endpoint added mid-flight while ejection state is being evaluated — starts HEALTHY with a fresh OutlierState, never inheriting a removed endpoint's counters.
  • EDS reports UNHEALTHY for an endpoint local ejection logic considers HEALTHY — the composed signal (20.2) correctly excludes it.

20.9 Failure Analysis

  • All endpoints unhealthy simultaneously (a genuine outage, not over-ejection) — detection: cluster_endpoints_healthy / total hitting zero; blast radius: total outage for that cluster, correctly so — I11's cap does not fabricate endpoints that do not exist; recovery: this is an upstream problem, and alerting distinguishes "capped" from "genuinely all down."
  • LB atomic-counter overflow under extreme process longevity — detection: a counter-wraparound test in CI; recovery: a width that cannot realistically overflow within the certificate-lifetime-bounded process lifetime, or periodic reset.

20.10 Operational Notes

  • Emit mesh_outlier_ejection_capped_total (I11), per-endpoint health-state gauges, and load-spread histograms.
  • Runbook cross-reference: mesh-wide-latency-regression (§26) consults this phase's ejection metrics first.

21. Phase 9 — Retries With Budgets, Timeouts And Circuit Breaking

21.1 Objectives

  • Implement the retry filter with budget enforcement (I10, ADR-17).
  • Implement per-request and per-try timeouts.
  • Implement the circuit-breaker state machine (§8.7) at the connection-pool level.

21.2 Detailed Implementation Steps

  • mesh-proxy/src/router.rs extension: retry_on conditions (5xx, connect-failure, reset — Nygard's stability patterns, §5); exponential backoff with jitter between attempts; a per-try timeout distinct from the overall request timeout.
  • RetryBudget (§11): max_retries_percent enforced as a cluster-wide sliding-window ratio of retries to primary requests (ADR-17's 20% figure); once exhausted, fail fast with a local 503 rather than attempting further (I10).
  • Circuit breaker (§8.7's CLOSED/OPEN/HALF_OPEN table): connection-pool limits (max_connections/max_pending_requests/max_requests) trip the breaker; HALF_OPEN admits exactly one trial request.
  • Filter-order lock-in: [authn|authz|ratelimit|fault|retry|router] — authz before retry, so a denied request never retries against the same denial — finalizing the order left open since Phase 2 (§14.6).
  • Timeout composition: per-try timeout ≤ overall request timeout; retries consume the remaining budget of the overall timeout, never resetting it.

21.3 Deliverable

Under an injected 30% error rate, the sidecar retries failed attempts within budget, the circuit breaker trips once connection-pool limits are exceeded, and a request whose overall timeout is exhausted fails cleanly regardless of remaining retry budget.

21.4 Acceptance Criteria

  • Retry rate never exceeds 20% of primary request rate under sustained 30% upstream error injection (I10, ADR-17).
  • Circuit breaker enters OPEN within one polling interval of exceeding max_pending_requests; HALF_OPEN admits exactly 1 probe request per cooldown.
  • 100% of requests exceeding the overall timeout fail by that deadline regardless of in-flight retry state (0 requests exceed overall_timeout + 50 ms tolerance across 10,000 requests).
  • Retries never amplify total upstream load beyond 1.2x baseline RPS under the budget cap (M12).

21.5 Conformance Fixtures

  • fixtures/phase9/retry-budget-cap.toml — 30% error injection; expect ≤ 20% retry-to-primary ratio.
  • fixtures/phase9/circuit-breaker-trip.toml — connection-pool limit exceeded; expect OPEN then HALF_OPEN per §8.7.
  • fixtures/phase9/overall-timeout-hard-deadline.toml — retries in flight when the overall timeout expires; expect clean failure at the deadline.
  • fixtures/phase9/filter-order-authz-before-retry.toml — a denied request; expect zero retry attempts against the denial.

21.6 Pitfalls

  • Resetting the overall-timeout clock on each retry attempt — manifests as a request that should fail at 5 s instead running 5 s-per-attempt × N attempts; debug via a timeline trace of attempt-start times vs. the original deadline; recovery: track the deadline from the original request, never per attempt.
  • Retrying non-idempotent operations by default — manifests as duplicate side effects upstream; debug via upstream-side duplicate-request detection; recovery: retry_on conditions scoped to safe/idempotent methods unless explicitly overridden.
  • The circuit breaker counting retried attempts as new primary requests against the same limits — manifests as the breaker tripping earlier than intended; debug via a request-classification audit (primary vs. retry) feeding the pool-limit counters; recovery: retries count against the retry budget (I10), not the primary connection-pool limits a second time.
  • Filter-order regression (retry ahead of authz again) — manifests as retry-amplified denial logging; debug via a filter-chain-order assertion test in CI; recovery: lock the order as a compile-time-checked constant, not only documentation.

21.7 Performance Concerns

  • Backoff-with-jitter computation uses the monotonic clock (ADR-31), never wall clock, to avoid corruption under NTP steps.
  • Retry-budget accounting (a sliding window) must be O(1) amortized per request, not a full-window rescan.

21.8 Edge Cases

  • A retried request whose retry itself times out at the per-try level while budget remains — must move to the next attempt or fail per the overall deadline, never double-counting the timeout as both a per-try and overall failure.
  • A HALF_OPEN probe request that itself times out (ambiguous outcome) — treated as a failed probe (fail closed toward OPEN, consistent with P9), never assumed successful.
  • A retry budget shared across multiple concurrently-failing routes to the same cluster — the budget is per-cluster, not per-route, so unrelated routes to a healthy cluster are unaffected by one route's retry storm.

21.9 Failure Analysis

  • A downstream at 50% capacity receiving 3x normal load due to retries (the classic retry-storm pattern, FM-6 §25) — detection: the retry-to-primary ratio metric exceeding the 20% budget; blast radius: cascading failure into the downstream; recovery: I10's enforcement is the structural fix; this fixture (21.5) is the regression test preventing recurrence.
  • A circuit breaker that never recovers because the HALF_OPEN probe keeps failing against a genuinely down upstream — detection: time-in-OPEN-state metric; blast radius: correctly contained — the breaker is doing its job, not exhibiting a bug; recovery: the operator investigates the upstream, not the mesh.

21.10 Operational Notes

  • Emit mesh_retry_budget_exhausted_total (I10), circuit-breaker state-transition counters, and per-cluster retry-to-primary ratio gauges.
  • Runbook cross-reference: mesh-wide-latency-regression (§26) — a retry storm is a top suspect when triaging that runbook.

22. Phase 10 — Traffic Splitting, Authorization Policy And Telemetry

22.1 Objectives

  • Implement weighted traffic splitting at the router (§8.6), driven by real VirtualService/DestinationRule config from Phase 4.
  • Implement the authz filter's policy evaluation (§8.9) — the first real, non-stub enforcement point.
  • Implement telemetry exposition: metrics, access logs, tracing.

22.2 Detailed Implementation Steps

  • mesh-proxy/src/router.rs extension: the cumulative-weight draw over WeightedCluster entries (§8.6), sourced from live RDS pushes.
  • mesh-policy/src/authz_eval.rs: evaluate AuthzPolicy against the PeerIdentity established in Phase 6 (§18), most-specific-route-first, default-deny (I6); PeerAuthentication mode checked before AuthzPolicy per §8.9.
  • mesh-telemetry/src/metrics.rs: Prometheus exposition on :15090/stats/prometheus (I13-compliant loopback bind); fixed label set — cluster, method, response_code, peer_principal — never raw path (P13, ADR-21).
  • mesh-telemetry/src/access_log.rs: structured JSON, async buffered write; fields = timestamp, method, path, status, duration_ms, upstream, peer_principal, trace_id.
  • mesh-telemetry/src/tracing.rs: W3C traceparent propagation (ADR-22), spans for inbound and outbound legs.
  • Fault injection and mirroring, rounding out the traffic-management feature set: configurable delay/abort at a percentage probability; mirror traffic to a shadow cluster without blocking the primary path (fire-and-forget on a separate task).

22.3 Deliverable

A 90/10 weighted split between two service versions holds within statistical tolerance over 10,000 requests; an unauthorized SPIFFE identity is denied cleanly; a dashboard shows per-cluster RPS/latency/error-rate from real sidecar-exported metrics; a trace shows one request crossing two sidecars end to end.

22.4 Acceptance Criteria

  • Weighted split holds v1 ≈ 9,000 ± 200 of 10,000 requests (§8.6's binomial tolerance).
  • Authz: 100% of denied-identity requests rejected; 100% of allowed-identity requests pass, across a 10,000-request mixed-identity fixture.
  • Metric cardinality stays within the P13 budget for the fixture cluster (bounded by clusters × methods × response-code-classes × distinct peer principals), never including raw path.
  • Trace propagation: 100% of a 1,000-request sample show a complete two-hop span tree with correct parent/child linkage.

22.5 Conformance Fixtures

  • fixtures/phase10/weighted-split-90-10.toml — the §8.6 worked example at fixture scale.
  • fixtures/phase10/authz-allow-deny.toml — mixed allowed/denied SPIFFE identities against a static policy.
  • fixtures/phase10/cardinality-budget.toml — a high-request-diversity fixture verifying no raw-path label leaks into exported metrics.
  • fixtures/phase10/trace-two-hop.toml — one request through two sidecars; expect a linked two-span trace.
  • fixtures/phase10/mirror-non-blocking.toml — a slow shadow cluster; expect zero added latency on the primary path.

22.6 Pitfalls

  • Evaluating AuthzPolicy before checking PeerAuthentication mode — manifests as an authenticated-looking decision on an unauthenticated (PERMISSIVE-mode plaintext) connection; debug via a policy-decision trace showing PeerIdentity = None reaching the authz evaluator; recovery: enforce the §8.9 ordering as a hard-coded filter position, not configuration.
  • A metrics label accidentally carrying the raw request path — manifests as a 10–100x cardinality explosion (T8, §24); debug via a time-series-count alert; recovery: an allow-listed label schema enforced at the metrics-emission call site, not by convention.
  • Mirror traffic sharing the primary request's connection/timeout budget — manifests as the primary path blocking on a slow shadow cluster; debug via an added-latency-with-mirror A/B comparison; recovery: mirror dispatch is fire-and-forget on a separate task, never awaited by the primary response path.
  • Weighted-split rounding errors at small N compounding into visible skew — manifests as a "should be 90/10" split drifting over many small batches; debug via cumulative-ratio tracking over a long window; recovery: the cumulative-weight draw (§8.6) is inherently unbiased per-request — verify no batching logic reintroduces bias.

22.7 Performance Concerns

  • Access-log writes must be async and buffered (ADR-26); a synchronous write on the request path violates P10.
  • Trace-span creation overhead must be bounded — sampling, not 100% capture, is the production default; the sampling rate is configurable, defaulting conservatively.

22.8 Edge Cases

  • A weighted split where one destination is currently ejected (Phase 8 outlier state) — the split arithmetic must exclude or redistribute weight away from ejected endpoints.
  • An AuthzPolicy with an empty principal_match — must resolve to Deny, never an accidental allow-all via an empty-pattern bug.
  • Trace context missing on an inbound request from a non-meshed caller — the sidecar originates a new trace root rather than failing the request.

22.9 Failure Analysis

  • The policy compiler produces a policy that cannot be evaluated (a malformed principal pattern) — detection: a policy-compile-error metric; blast radius: fail-closed (I6) — every request against that route is denied until fixed, the deliberately safe failure mode (P9).
  • The metrics aggregator is overwhelmed by cardinality despite the budget (a bug bypasses the label allow-list) — detection: mesh-telemetry process memory/CPU spike; blast radius: self-inflicted DoS on the telemetry path only, isolated from the request path by design (P13); recovery: the allow-list enforcement point (22.6) is the actual fix.

22.10 Operational Notes

  • Emit mesh_authz_fail_closed_total (I6), the full metric set from ADR-21's fixed label schema, and per-request access-log lines.
  • This phase completes the mesh's user-facing feature set — everything after this is hardening (Phase 11) and back-matter operational maturity (§24 onward).

23. Phase 11 — Conformance Suite, Chaos And Perf Hardening

23.1 Objectives

  • Assemble the full conformance suite exercising all 14 invariants end to end (§7's debugging methodology).
  • Run differential testing against Envoy on a shared xDS corpus and request set.
  • Run chaos scenarios (control-plane kill, sidecar partition, cert expiry mid-flight, clock skew) and perf-regression gating.

23.2 Detailed Implementation Steps

  • conformance/ harness: one fixture-driven test per invariant (I1–I14), aggregating every Phase N.5 fixture referenced across §12–§22 into a single CI-gated suite.
  • Differential harness (ADR-27): replay a shared xDS-resource corpus and request set through this mesh's data plane and a reference Envoy instance; assert routing/LB/retry decisions match within a documented tolerance (e.g. LB spread within the same ±5% band, §20.4).
  • Fuzzing continuity (ADR-28): confirm the xDS decoder, HTTP/1 and HTTP/2 codec, and policy parser have run under cargo-fuzz continuously since their introducing phases; this phase's gate is zero new crashes over 1,000,000,000 fuzzer-generated inputs, not first-time fuzzing.
  • Chaos scenarios: kill the control plane for 5 minutes under 10,000 req/s sustained load (assert P4/I7 hold); partition one sidecar from its peers; expire a certificate mid-flight (assert graceful connection completion, new-connection rejection); inject clock skew ±5 minutes (assert monotonic-clock-derived timers, ADR-31, are unaffected).
  • Perf-regression gate (ADR-27, §30): every §4/§30 M-table target becomes a CI-blocking check on every merge to the release branch.

23.3 Deliverable

A CI pipeline runs the conformance suite, the differential-vs-Envoy suite, the chaos suite, and the perf-regression gate on every release-branch merge; a 24-hour, 100-service, production-like soak test completes with zero mesh-attributable request loss.

23.4 Acceptance Criteria

  • All I1–I14 conformance assertions pass (0 failures).
  • Differential suite: 0 routing/LB decision mismatches against Envoy on the shared corpus, outside explicitly documented tolerance bands.
  • Chaos suite: the control-plane-kill scenario shows 0 dropped in-flight requests and 0 new-request failures attributable to the mesh during the 5-minute outage.
  • 24-hour production-like soak (100 services, 5 replicas, 1,000 req/s): 0 requests dropped due to mesh malfunction; at least one certificate rotation and one chaos event survived during the window.
  • Every M1–M12 target (§30) holds under the soak's load profile.

23.5 Conformance Fixtures

  • fixtures/phase11/full-invariant-suite.toml — aggregates I1–I14's individual fixtures into one gated run.
  • fixtures/phase11/differential-envoy-corpus.toml — the shared xDS+request corpus and its expected-match tolerance bands.
  • fixtures/phase11/chaos-control-plane-kill.toml — a 5-minute control-plane outage under load.
  • fixtures/phase11/chaos-cert-expiry-midflight.toml — a certificate expiring while a connection is in flight.
  • fixtures/phase11/soak-24h-production-like.toml — the full 24-hour, 100-service soak profile and its acceptance thresholds.

23.6 Pitfalls

  • Treating a passing differential run as proof of absolute correctness rather than consistency with Envoy — Envoy itself has had bugs (T10 lineage, §24); recovery: the differential suite catches divergence, not absolute correctness; pair it with the invariant suite, this system's own independent correctness statement.
  • Running chaos scenarios only in isolation, never combined — real outages compound (a control-plane kill during a cert-rotation window); recovery: include at least one combined-fault scenario before declaring this phase done.
  • A perf-regression gate with thresholds so loose they never block a regression — manifests as gradual latency creep going undetected across many small merges; debug via a historical trend chart of the M-table values, not only pass/fail; recovery: set thresholds at the §4/§30 targets themselves, not a padded margin.
  • Soak-test false confidence from an unrealistic call graph (no fan-out, no partial failures) — manifests as production surprises the soak never exercised; recovery: the call graph must include the realistic front→mid→back fan-out of 23.4, not a flat topology.

23.7 Performance Concerns

  • The full conformance + differential + chaos + perf suite must complete within a CI-budget window; parallelize independent fixture groups.
  • The 24-hour soak is expensive; run it on the release branch only, with the faster invariant/differential/perf-gate suites blocking every PR.

23.8 Edge Cases

  • A flaky fixture (nondeterministic under legitimate scheduling jitter) must be fixed at the fixture level (a tighter but still correct tolerance, or a deterministic simulator per §7/§28), never silenced by disabling it.
  • A chaos scenario revealing a genuine, previously undetected invariant violation is a Phase-11-blocking defect requiring a fix in the originating phase (§12–§22), never a Phase-11 workaround.
  • A differential mismatch traced to an intentional design difference (e.g. ADR-15's LB algorithm vs. Envoy's default) is documented as an accepted divergence with its rationale, never silently excluded from the corpus.

23.9 Failure Analysis

  • A perf-regression gate failure on a release-branch merge — detection: CI red on the M-table check; blast radius: contained to that merge, blocked before release; recovery: bisect to the offending change, fix or revert.
  • A chaos-scenario failure (requests dropped during the control-plane-kill test) — detection: the chaos fixture's own assertions; blast radius: this phase is not done until fixed — trace to the responsible invariant (likely I7/P4) and the originating phase.

23.10 Operational Notes

  • This phase's suites become the standing regression gate for all future changes — every ADR-27/ADR-28 testing-strategy commitment is operationalized here, not merely documented.
  • Runbook cross-reference: all four §26 named runbooks (bad-config-rollback, cert-expiry-emergency, mesh-wide-latency-regression, control-plane-outage-with-data-plane-survival) are drilled against this phase's chaos suite before being trusted in production.

26. Operational Readiness

Metrics (cardinality-budgeted, P13/ADR-21). Fixed label set: cluster, method, response_code (class, not exact code), peer_principal (bounded by workload count, not request count). Core series: mesh_mtls_violation_total, mesh_xds_version_regression_total, mesh_xds_nack_total, mesh_ca_csr_rejected_total, mesh_retry_budget_exhausted_total, mesh_outlier_ejection_capped_total, mesh_listener_warming_timeout_total, mesh_conn_dropped_during_rotation, mesh_authz_fail_closed_total, mesh_admin_bind_violation, mesh_xds_push_latency_ms, mesh_xds_convergence_seconds. Cardinality budget per sidecar is derived in §34.

Tracing spans and propagation. W3C traceparent/tracestate propagation (ADR-22); spans emitted for inbound and outbound legs per hop; sampling rate is configurable, defaulting conservatively — a cost/capacity tradeoff, not a correctness one.

Structured logging. Access logs (§22.2 fields) as async-buffered JSON (ADR-26); control-plane logs include the CSR audit trail (§17.2) and every xDS push/NACK event.

Dashboards. Per-cluster RPS/latency/error-rate (§22.3); mTLS handshake success/ failure rate; certificate time-to-expiry distribution across the fleet; xDS convergence-time distribution; outlier-ejection rate per cluster.

Alerting philosophy. Page on control-plane-side signals (P8): xds_connected=0 fleet-wide, CA issuance failures, any invariant-violation counter (§7) going non-zero. Ticket, not page, on data-plane-local signals contained to one pod, unless they cross a fleet-wide threshold.

SLOs. Added-latency SLO: p99 round-trip ≤ 6 ms (§4) with a documented error budget. Availability SLO: control plane 99.9% (§4). Data-plane availability during a control-plane outage is not an SLO input — by P4/I7 it is, by design, unaffected.

Incident response. First triage question: control-plane-side (convergence) or data-plane-side (proxy) in origin? (§2's mastery bullet). Escalate to the runbook matching the symptom.

Named runbooks (docs/runbooks/).

  • bad-config-rollback.md — trigger: an xDS NACK spike or a post-push error-rate spike. Procedure: identify the offending VirtualService/DestinationRule via the config-diff log, revert the CRD, verify the NACK rate returns to zero (I8).
  • cert-expiry-emergency.md — trigger: time_to_cert_expiry crossing a critical threshold fleet-wide. Procedure: verify CA health (ADR-23), force emergency re-CSR (§19.8), escalate to the CA-root-compromise drill (§19.2) only if the root is suspect.
  • mesh-wide-latency-regression.md — trigger: an added-latency SLO breach. Procedure: check retry-to-primary ratio (FM-6) and outlier-ejection rate (FM-7) first, then mTLS handshake rate, then xDS convergence time — cheapest-signal-first triage.
  • control-plane-outage-with-data-plane-survival.md — trigger: a control-plane availability incident. Procedure: confirm data-plane traffic is unaffected (the expected, correct state per P4/I7), restore control-plane HA (ADR-23), monitor time_to_cert_expiry for any sidecar whose rotation window falls inside the outage.

Backup/restore. The control plane holds no independent durable state (ADR-14) — "backup" is the K8s API server's own etcd backup. The CA root key is the one piece of state requiring its own sealed backup (ADR-08), restored per the cert-expiry-emergency runbook's escalation path.

Deployment topology. Control plane: 3 replicas, leader-elected (ADR-23), in a dedicated least-privilege-RBAC namespace (T9 mitigation). Data plane: one sidecar per meshed pod, injected at admission time (ADR-24).

Canary/rolling-upgrade/rollback/migration. New mesh-proxy versions roll out via the standard Kubernetes rolling-update mechanism, gated by the same maxUnavailable discipline that bounds FM-8. New control-plane versions roll out independently, replica by replica, behind leader election so only the leader signs certificates at any moment. Data-plane and control-plane upgrades are independent and version-skewed in production (ADR-25) — a cluster routinely runs sidecars at version N-1 alongside a control plane at version N (or vice versa mid-rollout), and the xDS protocol's version negotiation (§27) is what makes that safe.

27. Compatibility & Versioning

  • xDS protocol and resource version negotiation. VersionInfo (§11) is an opaque string, not a numeric protocol version — the ADS stream negotiates resource-content versions; wire-protocol compatibility is governed by the protobuf schema (ADR-11), following protobuf's additive-field-only evolution discipline.
  • Config schema evolution with unknown-field handling. mesh-config CRDs follow Kubernetes CRD versioning (v1alpha1→v1beta1→v1); unknown fields are ignored by older control-plane versions rather than rejected (I8 is unaffected — an unknown field is not a malformed resource).
  • Certificate and trust-bundle rotation compatibility. The dual-root overlap window (§19.2) is itself the compatibility mechanism across a CA-root rotation — both roots are simultaneously valid during the transition, so no separate versioning is needed.
  • Data-plane/control-plane version-skew guarantees. ADR-25: the xDS protocol is the compatibility boundary; a control plane at version N must correctly serve sidecars at N and N-1 (the differential and conformance suites, §28, run this skew combination as a release gate).
  • Policy grammar evolution. AuthzPolicy/PeerAuthentication grammar additions are additive only; a compiler encountering an unrecognized field treats it as absent (fail-closed per I6 — an unrecognized match condition never silently widens an Allow).
  • API stability. The mesh-types (§11) wire-adjacent types are the stability boundary; a breaking change to any type there requires a major SemVer bump (§29) and a CHANGELOG.md migration note.
  • Migration. Additive-first: ship a new field/resource type as optional, dual-write/ dual-read across one release cycle, then remove the old path — the same discipline SOTW xDS itself uses for warming (§8.2).
  • Deprecation. A deprecated field/type is marked in docs/adr/ with a removal-target version at least two minor versions out; CHANGELOG.md carries the notice at introduction, not at removal.
  • SemVer. mesh-proxy and the control-plane binaries version independently (ADR-25); a MAJOR bump on either side requires re-running the version-skew test matrix (§28) before that combination is declared supported.
  • Zero-downtime rolling-upgrade guarantees. Guaranteed by: the Draining state (§8.8) providing zero-downtime across a proxy-binary upgrade's process restart; I4 (atomic config swap) ensuring a control-plane upgrade never serves a half-applied resource type; ADR-25's version-skew tolerance ensuring neither side needs the other to upgrade in lockstep.

28. Testing & Verification Strategy

  • Unit. Per-crate pure-logic boundaries: weight arithmetic (§8.6), version comparison (I2), policy-evaluation ordering (§8.9).
  • Integration. Cross-crate: xDS client against a real xDS server (Phase 4 onward, §16); mTLS handshake between two real proxy instances (Phase 6 onward, §18).
  • Property. A config push converges every subscribed sidecar to the same routing decision (I4/I7, via a simulated N-sidecar harness); certificate rotation never drops a connection, proven by the continuous-load rotation test (I3, §19.4); interception never loops (I5, generalized into a property check across randomized rule permutations).
  • Differential. Against Envoy on a shared xDS corpus and request set (§23.2) — the primary defense against silent divergence from the reference implementation.
  • Fuzzing. Primary targets (ADR-28): the xDS decoder (protobuf Any unpacking), the HTTP/1 and HTTP/2 codec, and the policy parser — the dominant historical CVE class in this domain (§5, T10).
  • Chaos. Kill the control plane, assert data-plane survival (I7/P4, §23.2); partition a sidecar; expire a certificate mid-flight (the boundary condition I3 does not directly cover — what happens when rotation itself failed); inject clock skew (validates ADR-31's monotonic-time discipline under adversarial conditions).
  • Deterministic replay. The invariant-debugging methodology (§7) — a deterministic simulator with one assertion per invariant, replayable from a recorded event log.
  • Soak. The 24-hour, 100-service, production-like load test (§23.4) — the test whose primary purpose is surfacing slow leaks no shorter window would catch.
  • Fault injection. The Phase 10 fault-injection filter (§22.2) is dual-purpose: a mesh feature for testing other systems, and — turned on the mesh itself — a chaos-suite tool.
  • Conformance. Every Phase N.5 fixture (§12–§22), aggregated by Phase 11 (§23.2) into the standing CI gate.
  • Performance-regression gating. Every §30 M-table target is CI-blocking on the release branch (ADR-27) — an added-latency regression is a release-blocking gate, not a suggestion, once a target is locked.

29. Build & Release Engineering

  • Reproducible builds. Locked Cargo.lock, pinned rust-toolchain.toml (ADR-30); CI builds from a clean container with no host-toolchain leakage — a given commit hash always produces a bit-identical binary given the same toolchain pin.
  • Artifact signing. Release binaries and container images are signed (keyless signing against the CI identity) before publication.
  • SBOM. Generated per release from the locked dependency graph, attached to the release artifact — the mechanism T10's mitigation depends on.
  • Release channels. stable (SemVer-tagged, §27) and edge (every merge to main, unsigned, dev-cluster use only).
  • CI/CD topology. ci.yml (build/test/lint) on every PR; fuzz.yml scheduled continuously (ADR-28); conformance.yml and perf-gate.yml on every release-branch merge (§23); release.yml on tag push — builds, signs, generates SBOM, publishes.
  • Version stamping. The binary embeds its build commit hash, build timestamp, and Cargo.lock hash into a loopback-only /version admin endpoint (I13) for operational verification of what is actually running.
  • Provenance/attestation. CI produces a build-provenance attestation linking the published artifact to the exact source commit and build environment.
  • Dependency auditing. An audit job runs in CI against the SBOM on every merge (T10 detection); a new CVE against a locked dependency fails the build until patched or explicitly waived with a documented reason.

30. Performance Engineering

Methodology. Allocation: the hot request path (accept→parse→match→forward) is profiled for per-request heap allocations — zero allocations targeted in the steady-state copy loop (§12.7) and O(1) allocations in the L7 path (§14.7). Lock contention: every hot-path structure is ArcSwap or an atomic counter (P10); profiling under the §4 10,000 req/s target must show zero mutex wait time on the request path. Copy avoidance: header and body bytes are parsed zero-copy where the HTTP library allows; the LB/router path references the ConfigSnapshot directly, never cloning route tables per request. Syscall overhead: SO_ORIGINAL_DST is one syscall per connection, not per packet (§13.7); TLS handshake cost is dominated by the crypto operation itself given ECDSA P-256 (§18.7). Tail latency with coordinated-omission avoidance: benchmarks generate load at a fixed target rate independent of response latency (open-loop generation), per Dean & Barroso's warning (§5) that closed-loop benchmarking under-reports tail latency.

31. Scalability Analysis

What stays constant vs. grows. Per-request LB selection is O(1) regardless of cluster size (ADR-15, §20.7); route matching is O(log routes) via pre-compiled structures (§14.7); xDS snapshot-diff push cost is O(changed resources) per subscriber (§16.7) — but full-snapshot assembly and per-node storage is O(total resources subscribed), which is where the real growth lives.

Named bottlenecks, in order. (1) Config size × sidecar count is the classic control-plane killer — a naive design pushes every resource to every sidecar regardless of relevance, so bandwidth and convergence time both scale as O(config size × N sidecars); the §4 50 MB/node ceiling and the sidecar-scoping lever below exist to bound exactly this. (2) CA signing throughput — the single-signer HA model (ADR-23) caps issuance QPS; beyond that ceiling, ADR-23's rejected active-active-signing alternative becomes necessary. (3) Control-plane K8s-API-watch load — informer resync cost grows with cluster object count (§16.7); mitigated by watch-cache tuning, not eliminated.

Horizontal scaling. The xDS server is stateless-replicated (ADR-14) — add replicas to serve more sidecars, bounded only by the shared K8s-API-watch bottleneck above, which replication does not parallelize away.

Sidecar-scoping to shrink pushed config. Limiting which clusters/endpoints a given sidecar receives (Istio's Sidecar resource analogue, §5) turns the O(config size × N) bottleneck into O(config size × sidecars-that-actually-need-it) — the single highest-leverage lever beyond the practical ceiling below; PhaseDeferred("§37 Deferred Features Register") pending real-world need past the §4 5,000-cluster figure.

Coordination overhead. CA root rotation and leader election (ADR-23) are the only points requiring cluster-wide coordination; xDS push, per-workload cert issuance, and LB decisions are embarrassingly parallel across sidecars/replicas by construction (P3/P11).

Practical ceiling and levers beyond it. At the §4 figures, the practical ceiling before sidecar-scoping becomes mandatory is roughly where a cluster's total Service+ Endpoint count times its churn rate exceeds the control-plane's debounced-push capacity (§16.7); beyond that, sidecar-scoping (above) and delta xDS (PhaseDeferred("§37 Deferred Features Register"), ADR-10's deferred alternative) are the two available levers, in that order of implementation cost.

32. Mental Models & First Principles

MM1 — A service mesh is a distributed configuration-convergence problem wearing a proxy costume; the proxy is the easy half. Predicts: most production incidents trace to xDS convergence (staleness, ordering, NACK handling), not proxy parsing bugs. Bug class without it: over-investing in proxy micro-optimization while under-investing in convergence correctness. Resolves §8.2, §16.

MM2 — Identity is not location; a SPIFFE ID is a cryptographic claim, an IP is a lease. Predicts: any authorization check keyed on IP is eventually wrong, because pods are rescheduled. Bug class without it: authz-by-IP bugs after any reschedule. Resolves §8.4, P2.

MM3 — mTLS everywhere turns every deploy into a PKI operation, so certificate lifetime is a latency-and-availability parameter, not only a security parameter. Predicts: shortening cert lifetime for security trades directly against CA load and rotation-related outage risk. Bug class without it: security mandates for short lifetimes shipped without budgeting the CA-QPS cost. Resolves §4, §19, §34.

MM4 — Eventual consistency in config distribution means every sidecar's "now" is actually "recently"; code that assumes synchronized state assumes a lie. Predicts: any code path comparing "is my config the same as my peer's" is a latent bug. Bug class without it: split-brain routing during any config change. Resolves §8.2, P3, I7.

MM5 — Interception is a NAT problem before it is a proxy problem. Predicts: most "the mesh isn't working" bugs at the earliest phases are kernel-level (iptables/ conntrack), not application-level. Bug class without it: debugging proxy logic for a bug that is actually in the redirect rules. Resolves §8.1, §13.

MM6 — A retry without a budget is a load amplifier, not a resilience mechanism. Predicts: adding retries under partial failure can make total failure more likely, not less, absent a budget. Bug class without it: retry storms (FM-6). Resolves §21, I10, ADR-17.

MM7 — The control plane's job is to be boring and observable; the data plane's job is to be fast and quiet; conflating the two makes both worse. Predicts: a control plane optimized for request-path latency under-invests in the alerting and auditability it actually needs. Bug class without it: control-plane incidents going undetected because the team built dashboards for the wrong plane. Resolves P8, §26.

MM8 — Every filter-chain position is a security decision, not just an ordering convenience. Predicts: swapping two filters' order can silently change what "denied" means (e.g. retry-before-authz). Bug class without it: filter-order regressions reintroducing already-fixed vulnerabilities. Resolves §21.6, §8.9.

Consul Connect made the decision to decouple service discovery and identity from Kubernetes entirely, serving VM and container topologies uniformly through its own catalog and intentions model — it wins in hybrid or non-Kubernetes-native infrastructure where a Kubernetes-only control plane (this blueprint's ADR-13 choice) is the wrong fit.

Cilium's ambient/eBPF model made the decision to move L4 enforcement out of the pod entirely, amortizing overhead across the node and eliminating the sidecar's per-pod memory/CPU tax — it wins at high pod-density where the §4 M4/M5 per-sidecar footprint, multiplied across thousands of pods, dominates cluster capacity planning, at the cost of the per-pod isolation this blueprint's ADR-04 explicitly chose to keep.

34. Back-of-Envelope Capacity Model

  1. Total mesh memory overhead = pods × sidecar RSS. At 1,000 pods × 250 MB (§4 M5, loaded) = 250,000 MB = 250 GB mesh-wide at full load; at idle (§4 M4, 40 MB) = 40 GB.
  2. Config push bandwidth and implied convergence. A 500-endpoint change serializes to roughly 100 bytes/endpoint metadata × 500 ≈ 50 KB (§11 Endpoint); pushed to 1,000 sidecars at a debounced ~10 pushes/hour during normal churn: 50 KB × 1,000 × 10 = 500,000 KB/hour ≈ 500 MB/hour ≈ 139 KB/s sustained control-plane egress — trivial against typical control-plane network capacity, and consistent with the §4 M8 ≤ 5 s p99 convergence target since the push is spread across 1,000 concurrent streams.
  3. Per-request added-latency budget decomposition. Round-trip budget ≤ 6 ms p99 (§4 M3) = 2 hops × ≤ 3 ms p99/hop (M2); each hop's 3 ms decomposes as: route match (≤ 50 µs, §14.4) + filter-chain dispatch (bounded indirect calls, sub-µs) + LB selection (O(1), sub-µs) + network/socket I/O (the dominant remaining ~2.9 ms) — the mesh's own compute is under 0.1 ms of the 3 ms hop budget; the rest is legitimately network/kernel/TLS-record overhead.
  4. mTLS handshake CPU and the resumption saving. At §4 M6 (≥ 4,000 full handshakes/s/core), per-handshake cost ≈ 1/4,000 s = 250 µs. For 10,000 new connections/s mesh-wide, full-handshake CPU = 10,000 × 250 µs = 2.5 core-seconds/s = 2.5 cores. With resumption (§4 M7, ≥ 20,000/s/core ⇒ 50 µs/handshake), the same 10,000/s costs 10,000 × 50 µs = 0.5 core-seconds/s = 0.5 cores — resumption saves 2 cores of mesh-wide CPU at this churn rate, a 5x reduction.
  5. Certificate issuance rate = workloads ÷ cert lifetime. 1,000 workloads ÷ 24 h (§4) ≈ 41.7 issuances/hour ≈ 0.012/s — trivial CA load; jittered across the 24 h window (§19.2) this smooths to roughly one issuance every 86 seconds, well under any reasonable CA signing throughput (§17.7).
  6. Endpoint-table memory = endpoints × entry bytes × sidecars. At 5,000 endpoints cluster-wide (under the §4 50,000/sidecar ceiling) × ~100 bytes/entry (§11 Endpoint) = 500 KB per sidecar's full table; across 1,000 unscoped sidecars = 500 KB × 1,000 = 500 MB mesh-wide — exactly the figure sidecar-scoping (§31) exists to shrink once it starts to bite.
  7. FD budget. Per §4, 65,536 FDs per sidecar, 4,096 reserved for xDS/CA/admin, leaving 61,440 for data connections; at ~2 FDs per proxied connection (client-side plus upstream-side) this bounds one sidecar to ~30,720 concurrent proxied connections before FD exhaustion — well above the §4 10,000-connection RSS-budget scenario (M5), confirming RSS, not FDs, is the binding constraint at that load level.
  8. Control-plane discovery-request QPS. At 10,000 sidecars, the §4 ceiling of 5,000 req/s implies an average budget of 0.5 requests/s/sidecar — consistent with the debounced push model (§16.2), where most sidecars are quiescent between config changes rather than polling.

  1. Why does xDS need ADS ordering (CDS before EDS before RDS before LDS) rather than five independent streams, and what invariant would break without it? (§8.2, §16, I12)
  2. Why is certificate rotation implemented as an atomic ArcSwap of the whole CertBundle rather than swapping cert and key independently, and what production incident class does the atomic swap prevent? (§8.4, §19, I3)

  5. Why does a policy denial fail closed while a control-plane disconnection fails static (keeps serving) — are these the same underlying principle or two different ones? (P4, P9, §7)
  6. Trace the exact sequence of events, invariant by invariant, that would need to fail simultaneously for a plaintext connection to succeed against a STRICT-mode listener. (I1, §18, T4)
  7. Why is the retry budget expressed as a percentage of upstream RPS rather than an absolute count, and what happens to that decision as a cluster scales from 10 to 10,000 endpoints? (ADR-17, §21, §31)
  8. What is the actual difference between "a sidecar behaving correctly while stale" (I7) and "a sidecar ignoring a version regression" (I2), and why does the system need both as separate invariants? (§7, §8.2)
  9. Why does sidecar-scoping address the config-size×sidecar-count bottleneck better than simply increasing control-plane replica count? (§31, §16.7, ADR-14)
  10. Derive, from the §4 constraints alone, why session resumption is not optional at mesh scale — what handshake-rate shortfall would an ECDSA-only, no-resumption deployment hit first? (§4, §18.7, §34)
  11. Why does the blueprint reject a library/SDK-based mesh even though it eliminates the extra network hop entirely, and under what organizational conditions would that tradeoff flip? (§36, ADR-04, §1)
  12. What specific mechanism prevents a NACK'd config from being silently retried by the control plane, and why would "just retry" be actively harmful here? (§8.2, I8, §15)
  13. Why is the admin/metrics port's loopback-only bind treated as an invariant (I13) rather than a best-practice recommendation? (§7, T11)
  14. Compare an all-endpoints-unhealthy cluster (I11 correctly refusing to fabricate health) against an over-ejecting cluster bug (FM-7) — how does an operator distinguish the two in the first 60 seconds of an incident? (I11, FM-7, §20.9)

38. Glossary

  • ACK — a DiscoveryRequest confirming successful application of a pushed xDS resource, carrying the applied version_info and the response nonce.
  • Ambient mode — a sidecarless mesh deployment using a per-node L4 proxy plus an optional per-namespace L7 waypoint; deferred here (§36).
  • ArcSwap — a lock-free atomic pointer-swap primitive used for ConfigSnapshot and CertBundle installation on the hot path (P10, P6).
  • AuthzPolicy — the compiled principal×route×effect authorization rule evaluated by the authz filter (§8.9, §11).
  • Blast radius — the scope of impact of a single failure or compromise; a key axis distinguishing sidecar (T1) from ambient (§36.1) architectures.
  • Cardinality budget — the bounded set of metric label-value combinations a telemetry system may emit (P13); exceeding it risks self-inflicted DoS (T8).
  • CDS — Cluster Discovery Service; the xDS resource type carrying cluster definitions (§8.2).
  • Circuit breaker — a connection-pool-level state machine (CLOSED/OPEN/HALF_OPEN) that fails fast once upstream limits are exceeded (§8.7).
  • Config convergence — the process by which all subscribed sidecars eventually apply the same control-plane-pushed configuration (§8.2, §16).
  • ConfigSnapshot — the internally consistent, versioned bundle of listeners/routes/ clusters/endpoints a sidecar holds and swaps atomically (§11, I4).
  • Conntrack — the Linux kernel's connection-tracking table used by iptables NAT; a scalability bottleneck under high pod churn (FM-9).
  • Consistent hashing — a hashing scheme minimizing remapping under membership change (Karger et al. 1997); the rejected alternative to power-of-two-choices (ADR-15).
  • Control plane — the off-data-path component set (discovery, xDS server, CA, policy compiler, telemetry aggregator) that configures the data plane (§3).
  • Data plane — the sidecar proxies on the actual request path (§3).
  • Delta xDS — the incremental xDS variant sending only added/updated/removed resources per push, contrasted with SOTW (§8.3); deferred here (§37).
  • EDS — Endpoint Discovery Service; the xDS resource type carrying per-cluster endpoint lists (§8.2).
  • Fail closed — a design stance where an unevaluable decision defaults to Deny (I6, P9).
  • Fail static — a design stance where loss of control-plane connectivity preserves the last-known-good state rather than degrading permissively (P4).
  • Filter chain — the ordered stack of request/response-processing filters applied by a listener (§3, §11).
  • iptables REDIRECT — a NAT action rewriting a packet's destination port to a local listener, the mechanism underlying transparent interception (§8.1).
  • Least-request — a load-balancing policy selecting the endpoint with fewer in-flight requests, implemented here via power-of-two-choices (ADR-15).
  • LDS — Listener Discovery Service; the xDS resource type carrying listener definitions (§8.2).
  • Loop avoidance — the UID/owner-based exclusion mechanism preventing a sidecar's own egress from being redirected back into itself (§8.1, I5).
  • mTLS — mutual TLS; both connection peers authenticate via X.509 certificates (§8.5).
  • NACK — a DiscoveryRequest rejecting a pushed xDS resource, carrying the last-good version_info and an error_detail (§8.2, I8).
  • Nonce — an opaque, server-generated token echoed by the client to pair an xDS request with its response (§11).
  • Outlier ejection — the per-endpoint health state machine that removes and later restores endpoints based on observed failure rate (§8.7, ADR-16).
  • PeerAuthentication — the policy object controlling whether inbound traffic on a listener must be mTLS (STRICT/PERMISSIVE/DISABLE, §8.9, §11 MtlsMode).
  • PeerIdentity — the SPIFFE identity extracted from a validated peer certificate during an mTLS handshake (§8.5, §11).
  • PERMISSIVE mode — an MtlsMode accepting both mTLS and plaintext inbound traffic; a documented risk surface (T4) relative to STRICT.
  • PolicyDecision — the Allow/Deny outcome of evaluating an AuthzPolicy against a PeerIdentity and route (§8.9, §11).
  • Power-of-two-choices — a load-balancing sampling technique selecting the better of two uniformly-sampled endpoints (Mitzenmacher 2001, ADR-15).
  • Resource warming — holding a newly received xDS resource in a pending state until every resource it references is also present, before promoting it into the active ConfigSnapshot (§8.2, I12).
  • Retry budget — a cluster-wide cap on the ratio of retried to primary requests, preventing retry storms (I10, ADR-17).
  • RDS — Route Discovery Service; the xDS resource type carrying route tables (§8.2).
  • RTO — recovery time objective; the target maximum duration of a specific outage class (§4).
  • SBOM — software bill of materials; a generated manifest of a build's exact dependency graph, used for supply-chain auditing (§29, T10).
  • SDS — Secret Discovery Service; the xDS resource type carrying TLS certs, keys, and trust bundles (§8.2).
  • SemVer — semantic versioning; the MAJOR.MINOR.PATCH scheme governing this blueprint's compatibility guarantees (§27).
  • Sidecar — a proxy process running alongside the application container in the same pod, on the request path for every call (§3).
  • SLO — service level objective; a target value for an availability or latency metric with an associated error budget (§26).
  • SO_ORIGINAL_DST — a Linux socket option exposing a redirected connection's pre-NAT destination address (§8.1, §13).
  • SOTW — state-of-the-world xDS; the variant sending a full resource-type snapshot on every update, contrasted with delta (§8.3).
  • SPIFFE ID — a URI-formatted workload identity of the form spiffe://<trust-domain>/<path> (§8.4).
  • STRICT mode — an MtlsMode rejecting any non-mTLS inbound connection at the transport layer (§8.9, I1).
  • SVID — SPIFFE Verifiable Identity Document; the X.509 certificate embedding a workload's SPIFFE ID as a URI SAN (§8.4, §11).
  • Traffic split — weighted distribution of requests across multiple destination clusters, e.g. for canary rollout (§8.6).
  • Trust domain — the root scope for SPIFFE identities within which a single CA root is authoritative (§8.4, P12).
  • Version skew — the state of a control plane and data plane running different, but mutually compatible, protocol/schema versions simultaneously (§27, ADR-25).
  • VersionInfo — the opaque string identifying an xDS resource's content version, compared for monotonicity on every push (§11, I2).
  • WeightedCluster — a route-table entry pairing a destination cluster with a selection weight, the unit of traffic-split arithmetic (§8.6, §11).
  • xDS — the family of discovery-service protocols (LDS/RDS/CDS/EDS/SDS, aggregated as ADS) by which the control plane configures the data plane (§8.2).
