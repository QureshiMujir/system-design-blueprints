Decisions (§9) · 33 ADRs

ADR-01

Implementation language

Chosen

Rust

Rejected

C++, Go, Java/JVM

When the rejected choice is right

C++ wins when a team already owns a large existing Envoy-based C++ codebase and rewrite cost dominates

Why: memory-safety in the security-critical hot path (Envoy CVE history, §5); no GC tail-latency variance

ADR-02

Async runtime

Chosen

Tokio (multi-thread work-stealing)

Rejected

async-std, smol, Glommio (io_uring thread-per-core)

When the rejected choice is right

Glommio/io_uring wins at >100k conn/core NIC-bound workloads where syscall count dominates scheduling flexibility

Why: mature ecosystem (tonic, h2, rustls integration), sufficient for the §4 budget

ADR-03

Interception mechanism

Chosen

iptables (NAT REDIRECT)

Rejected

eBPF/XDP socket redirect, explicit-proxy env vars

When the rejected choice is right

eBPF wins at high pod-churn rates where conntrack pressure (FM-9, §25) dominates and kernels are ≥5.7

Why: lingua franca, works on any kernel ≥3.x, mature tooling

ADR-04

Deployment topology

Chosen

Sidecar-per-pod

Rejected

Sidecarless/ambient (node L4 + waypoint L7), in-process library/SDK

When the rejected choice is right

ambient wins at extreme pod-density where per-pod sidecar RSS (M4/M5) dominates total cluster memory

Why: per-pod isolation, no polyglot SDK requirement, industry mileage (Istio/Linkerd)

ADR-05

Proxy concurrency architecture

Chosen

work-stealing multi-thread (Tokio default)

Rejected

thread-per-core, share-nothing

When the rejected choice is right

thread-per-core wins for high-core-count bare-metal proxies (ambient node proxy, gateway-class) where cache-line migration dominates

Why: simpler operational model, adequate at single-pod, few-core scale

ADR-06

TLS library

Chosen

rustls

Rejected

OpenSSL (FFI), BoringSSL, s2n-tls

When the rejected choice is right

OpenSSL/BoringSSL wins when FIPS-140-certified crypto modules are a hard compliance requirement

Why: pure Rust, no C FFI attack surface, TLS-1.3-only default (RFC 8446)

ADR-07

Identity format

Chosen

SPIFFE X.509-SVID

Rejected

SPIFFE JWT-SVID, bespoke JWT (RFC 7519)

When the rejected choice is right

JWT-SVID wins for non-TLS transports, e.g. authenticating to an API gateway that terminates TLS externally

Why: works transparently inside the mTLS handshake with no separate token exchange

ADR-08

CA design and key custody

Chosen

in-cluster CA, root key in-memory + sealed backup

Rejected

external CA via cert-manager/ACME (RFC 8555), HSM-backed root

When the rejected choice is right

ACME/cert-manager wins when the org already runs a hardened external PKI across mesh+ingress+non-mesh workloads

Why: keeps the trust-domain root under mesh-operator control, avoids per-cluster ACME rate limits

ADR-09

Certificate lifetime & rotation

Chosen

24 h lifetime, re-CSR at 50%±10% jitter

Rejected

5-minute short-lived SVIDs, 1-year long-lived + CRL/OCSP

When the rejected choice is right

5-minute lifetime wins in high-security zero-trust deployments where CA capacity absorbs the QPS and leak blast radius must be minutes

Why: balances CA load against leak blast radius; avoids CRL/OCSP operational cost

ADR-10

Config protocol shape

Chosen

xDS state-of-the-world, ADS aggregated stream

Rejected

delta (incremental) xDS, bespoke polling protocol

When the rejected choice is right

delta wins once the §4 config-size ceiling (50 MB/node) is regularly exceeded

Why: simpler server-side implementation for Phase 3–4; matches Envoy's most widely deployed mode

ADR-11

Config transport

Chosen

gRPC (HTTP/2, protobuf) bidirectional stream

Rejected

REST+webhook polling, MQTT/pubsub

When the rejected choice is right

REST polling wins for constrained edge devices unable to hold a long-lived HTTP/2 stream

Why: native fit for xDS's streaming ACK/NACK model; multiplexed over one connection

ADR-12

Consistency model

Chosen

eventual consistency per resource type

Rejected

strong consistency (2PC/consensus across all sidecars)

When the rejected choice is right

strong consistency wins for the tiny control-plane-internal store used by CA root rotation itself (ADR-23), not for data-plane fan-out

Why: consensus-per-push does not scale to thousands of sidecars (Ongaro & Ousterhout quorum sizing is the wrong shape for fan-out)

ADR-13

Service discovery source

Chosen

Kubernetes API (watch Services/Endpoints/Slices)

Rejected

Consul catalog, static file, DNS-SD

When the rejected choice is right

Consul catalog wins in non-Kubernetes or hybrid VM+container topologies (Consul Connect, §5)

Why: native informer/watch is the lowest-latency discovery signal for this blueprint's Kubernetes target

ADR-14

Control-plane durability

Chosen

none — K8s etcd via the API server is sole durability

Rejected

independent database (Postgres/etcd-direct) for config CRDs

When the rejected choice is right

an independent store wins only if control-plane state must outlive the API server itself, e.g. federated multi-cluster

Why: avoids a second source of truth and its drift risk

ADR-15

Load-balancing algorithm

Chosen

least-request via power-of-two-choices (Mitzenmacher 2001)

Rejected

round-robin, weighted-random, consistent hashing (Karger et al. 1997)

When the rejected choice is right

consistent hashing wins when sticky session affinity by header/cookie/source-IP is a hard requirement

Why: O(1) sample cost, near-optimal load spread without a full scan

ADR-16

Outlier ejection

Chosen

local per-sidecar consecutive-5xx counting, capped percentage

Rejected

centralized health registry pushed from control plane

When the rejected choice is right

centralized wins when ejection must be globally consistent across all sidecars simultaneously (regulatory-grade failover)

Why: zero control-plane round trip for ejection decisions, matches Envoy's proven model

ADR-17

Retry policy & budgets

Chosen

per-cluster budget capped at 20% of upstream RPS, exponential backoff+jitter

Rejected

unbounded per-request retry count

When the rejected choice is right

unbounded retry is acceptable only for known-idempotent, low-volume, human-triggered operations such as a CLI admin action

Why: prevents retry storms (Nygard, §5) from turning partial failure into total failure

ADR-18

Circuit breaking

Chosen

connection-pool-level limits (max_connections/pending/requests)

Rejected

request-latency-based breaker (trip on p99 threshold)

When the rejected choice is right

latency-based breaker wins for downstreams with a hard SLA where saturation isn't the failure signature but latency degradation is

Why: simpler, deterministic, avoids false trips from natural latency variance

ADR-19

Traffic-splitting mechanism

Chosen

weighted-cluster selection at the router filter (§8.6)

Rejected

DNS-weighted records, L4 weighted target groups

When the rejected choice is right

DNS-weighted wins for coarse infrastructure-level shifting outside any mesh-aware L7, e.g. multi-region failover

Why: L7-aware, per-request not per-connection, supports header/cookie canary alongside weight

ADR-20

Policy language & enforcement point

Chosen

static declarative AuthzPolicy, enforced in-proxy pre-router

Rejected

OPA/Rego with a sidecar ext_authz call-out

When the rejected choice is right

OPA/Rego wins when policy logic needs data outside the mesh's own model, e.g. external business-attribute stores

Why: zero extra network hop, deterministic latency, sufficient for the §1 non-goals

ADR-21

Telemetry collection & cardinality control

Chosen

fixed label set (cluster, method, response_code, peer_principal), pull-model Prometheus

Rejected

push-model StatsD/OTel-metrics with dynamic label sets

When the rejected choice is right

push-model wins for workloads shorter-lived than the scrape interval, where pull scraping would miss data entirely

Why: pull model plus fixed labels bounds cardinality by construction (P13)

ADR-22

Tracing propagation

Chosen

W3C traceparent/tracestate, OpenTelemetry SDK

Rejected

legacy B3 headers, custom trace-id scheme

When the rejected choice is right

B3 wins only for interop with legacy Zipkin-only downstream systems not yet migrated

Why: converged industry standard, post-Dapper lineage (Sigelman et al. 2010)

ADR-23

Control-plane HA & leader election

Chosen

3 replicas, leader election via K8s Lease API, single active CA signer

Rejected

active-active CA signing with distributed key shares

When the rejected choice is right

distributed active-active signing wins once CA-QPS exceeds one signer's capacity (§4 control-plane QPS ceiling)

Why: Lease API is already durable and simple; avoids building bespoke consensus

ADR-24

Injection mechanism

Chosen

mutating admission webhook, opt-in namespace/pod label

Rejected

CNI-plugin-level injection, manual sidecar spec authoring

When the rejected choice is right

CNI-level injection wins when the platform team already controls a custom CNI and wants injection without a webhook round trip

Why: matches Istio/Linkerd's proven operational model, decoupled from CNI choice

ADR-25

Data-plane vs. control-plane upgrade strategy

Chosen

independent, version-skew-tolerant (§27)

Rejected

lockstep upgrade, always same version

When the rejected choice is right

lockstep wins only in small single-operator clusters where a brief full-mesh restart window is acceptable

Why: production clusters cannot pause traffic for a lockstep upgrade

ADR-26

Logging

Chosen

structured JSON access logs, async buffered write to stdout

Rejected

synchronous per-request disk write, plaintext logs

When the rejected choice is right

synchronous write wins in an audit-grade compliance mode willing to trade throughput for a zero-loss guarantee

Why: async plus buffered avoids blocking the request-path hot loop (P10)

ADR-27

Testing strategy

Chosen

property + differential (vs. Envoy) + chaos + fuzz, layered (§28)

Rejected

unit-tests-only

When the rejected choice is right

unit-only is acceptable for a throwaway prototype never destined for production traffic

Why: unit tests alone miss protocol-state-machine and concurrency bugs dominant in proxy CVE history

ADR-28

Fuzzing targets

Chosen

xDS decoder, HTTP/1 and HTTP/2 codec, policy parser, continuous cargo-fuzz in CI

Rejected

manual code review only, no fuzzing

When the rejected choice is right

manual-review-only is acceptable only for a pre-alpha, network-unexposed prototype; any component parsing attacker-reachable bytes requires fuzzing before production traffic

Why: parser/decoder bugs are the dominant historical CVE class (Rapid Reset CVE-2023-44487, §24)

ADR-29

Packaging & release

Chosen

static-linked musl binary in a minimal distroless image, SemVer tags

Rejected

dynamic-linked glibc image, rolling latest tag

When the rejected choice is right

dynamic-linked wins when the base image must share host-provided crypto libraries for FIPS validation

Why: reproducible, small attack surface, no host-libc drift across nodes

ADR-30

Reproducibility

Chosen

locked Cargo.lock, pinned toolchain, deterministic CI build

Rejected

floating dependency versions, best-effort builds

When the rejected choice is right

floating versions are acceptable only on an internal experimental branch never shipped

Why: supply-chain integrity (T10), reproducible SBOM generation

ADR-31

Time source

Chosen

monotonic clock for all interval/timeout/backoff math; wall clock only for cert validity and log timestamps

Rejected

wall clock for everything

When the rejected choice is right

wall-clock-only is acceptable only for pure log-timestamping paths that compute no interval; any duration/backoff calculation requires monotonic time

Why: monotonic time is immune to clock-skew/NTP-step artifacts that would corrupt backoff arithmetic

ADR-32

Backpressure

Chosen

bounded per-connection buffers, HTTP/2 flow-control window propagation

Rejected

unbounded buffering

When the rejected choice is right

unbounded buffering is acceptable only in an offline batch/ETL tool on trusted, size-bounded input with no shared-tenancy memory ceiling

Why: prevents the classic full-body-buffering OOM pattern

ADR-33

Licensing

Chosen

Apache-2.0

Rejected

GPL-family, proprietary

When the rejected choice is right

GPL wins only if the project deliberately wants to force downstream modifications to stay open

Why: matches the CNCF/service-mesh ecosystem norm (Envoy, Istio, Linkerd), enables adoption without copyleft obligations

Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Sidecarless / ambient — per-node proxy plus eBPF waypoint

Node
┌─────────────────────────────────────────┐
│ Pod A     Pod B     Pod C               │
│  app        app        app              │
│   │          │          │               │
│   └────┬─────┴────┬─────┘  (eBPF redirect, no sidecar)
│        ▼          ▼                     │
│  ┌───────────per-node L4 proxy─────────┐│
│  │   (ztunnel-equivalent, mTLS)        ││
│  └───────────────┬─────────────────────┘│
└──────────────────┼───────────────────────┘
                    ▼ optional, opt-in
           ┌────waypoint (L7)────┐
           │ per-namespace proxy │
           └──────────────────────┘

Winning regime: high pod-density clusters where per-pod sidecar memory/CPU (§4 M4/M5, §34's 250 GB-at-load figure) dominates capacity planning, and per-pod isolation is not a hard security requirement. Real embodying system: Cilium Service Mesh, Istio ambient mode. Rejected here because ADR-04 explicitly prioritizes per-pod isolation and existing sidecar-model mileage over the memory savings — a per-node proxy means one compromised node proxy affects every pod on that node, a materially larger blast radius than one compromised sidecar (T1's analysis assumes pod-scoped blast radius).

Library/SDK mesh (in-process, Finagle-style)

Process (app + linked library)
┌───────────────────────────────┐
│  application code              │
│       │                        │
│       ▼                        │
│  mesh SDK (in-process)         │
│  - retry/timeout/circuit break │
│  - mTLS client                 │
│  - xDS-equivalent config pull  │
└───────────────┬─────────────────┘
                ▼ direct call, no extra hop
           upstream service

Winning regime: a single-language (or few well-supported languages) shop willing to accept an SDK dependency in every service, eliminating the extra network hop entirely (§34's per-hop budget collapses to zero mesh-added hops). Real embodying system: Twitter's Finagle, gRPC's built-in client-side LB/retry libraries. Rejected here because P1 ("zero app code change") is the load-bearing non-negotiable requirement — a library approach requires every service, in every language, to adopt the SDK, precisely the polyglot-adoption problem P1 exists to avoid (§1).

Node-level shared proxy (explicit-proxy env vars, non-eBPF)

Node
┌─────────────────────────────────────┐
│ Pod A    Pod B    Pod C             │
│ app:5000 app:5000 app:5000          │
│    │        │        │              │
│    └───explicit HTTP_PROXY env──────┤
│                 ▼                    │
│      ┌────one shared proxy────────┐ │
│      │  process, multi-tenant,    │ │
│      │  routes by pod source IP   │ │
│      └──────────────────────────────┘│
└───────────────────────────────────────┘

Winning regime: resource-constrained edge/IoT-adjacent deployments where even §36.1's eBPF tooling is unavailable but per-pod sidecar overhead is still unaffordable. Real embodying system: the direct ancestor pattern behind ADR-03's rejected "explicit-proxy env vars" alternative — pre-mesh explicit-proxy deployments, not a named product. Rejected here because there is no per-pod trust boundary at all: one pod's traffic is observable/manipulable by another pod on the same node without even a kernel-level redirect to compromise — strictly worse than either the sidecar model or ambient's kernel-enforced per-pod eBPF redirect (§8.1 has no analogue here).

Pure gateway / north–south only, no mesh

        Internet
           │
           ▼
   ┌──API Gateway (165-equivalent)──┐
   └───────────────┬─────────────────┘
                    ▼
        ┌───────────────────────────┐
        │ Service A ── Service B     │  (direct, unmediated calls)
        │      │            │        │
        │      └──Service C─┘        │
        └───────────────────────────┘
        (no mTLS, no xDS, no per-hop east-west policy)

Winning regime: a small service count (single digits) where the operational cost of a mesh control plane exceeds its coordination benefit, and east-west traffic can be secured by coarser mechanisms (NetworkPolicy, a shared VPC boundary) — see 165 (API-Gateway)'s own scope, which stops at the edge. Real embodying system: any early-stage microservices deployment behind a single API gateway with no service mesh — an absence, not a named product. Rejected here because this blueprint's entire premise (§1's two hard problems — transparent interception and zero-trust identity) is a set of concerns a pure-gateway model has no mechanism for at all; it is a different, smaller-scoped problem, the same distinction drawn in §1's non-goals against 165.
