Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does xDS need ADS ordering (CDS before EDS before RDS before LDS) rather than five independent streams, and what invariant would break without it? (§8.2, §16, I12)
  2. Why is certificate rotation implemented as an atomic ArcSwap of the whole CertBundle rather than swapping cert and key independently, and what production incident class does the atomic swap prevent? (§8.4, §19, I3)
  3. Why does the mesh choose local, per-sidecar outlier ejection over a centralized health registry, and under what regime would the centralized alternative be correct? (ADR-16, §20, §8.7)
  4. How does the interception loop-avoidance mechanism (UID exclusion) interact with the eBPF alternative's cgroup-based exclusion, and why can't the iptables approach be ported unchanged? (§8.1, §13, ADR-03)
  5. Why does a policy denial fail closed while a control-plane disconnection fails static (keeps serving) — are these the same underlying principle or two different ones? (P4, P9, §7)
  6. Trace the exact sequence of events, invariant by invariant, that would need to fail simultaneously for a plaintext connection to succeed against a STRICT-mode listener. (I1, §18, T4)
  7. Why is the retry budget expressed as a percentage of upstream RPS rather than an absolute count, and what happens to that decision as a cluster scales from 10 to 10,000 endpoints? (ADR-17, §21, §31)
  8. What is the actual difference between "a sidecar behaving correctly while stale" (I7) and "a sidecar ignoring a version regression" (I2), and why does the system need both as separate invariants? (§7, §8.2)
  9. Why does sidecar-scoping address the config-size×sidecar-count bottleneck better than simply increasing control-plane replica count? (§31, §16.7, ADR-14)
  10. Derive, from the §4 constraints alone, why session resumption is not optional at mesh scale — what handshake-rate shortfall would an ECDSA-only, no-resumption deployment hit first? (§4, §18.7, §34)
  11. Why does the blueprint reject a library/SDK-based mesh even though it eliminates the extra network hop entirely, and under what organizational conditions would that tradeoff flip? (§36, ADR-04, §1)
  12. What specific mechanism prevents a NACK'd config from being silently retried by the control plane, and why would "just retry" be actively harmful here? (§8.2, I8, §15)
  13. Why is the admin/metrics port's loopback-only bind treated as an invariant (I13) rather than a best-practice recommendation? (§7, T11)
  14. Compare an all-endpoints-unhealthy cluster (I11 correctly refusing to fabricate health) against an over-ejecting cluster bug (FM-7) — how does an operator distinguish the two in the first 60 seconds of an incident? (I11, FM-7, §20.9)
  15. Why does the CA design accept a single-signer HA model (leader-elected) rather than active-active signing, and what is the actual cost of that choice at scale? (ADR-23, §31, §34)
  16. Trace how a certificate-lifetime policy change (say, 24h → 5 minutes) ripples through §4's constraints, §19's rotation mechanism, and §34's capacity model — name every number that would need to be recomputed. (§4, §19, §34)
  17. Why is delta xDS deferred rather than adopted from the start, given it is strictly more bandwidth-efficient? (ADR-10, §8.3, §37)
  18. What would have to be true about an organization's traffic patterns for the ambient/sidecarless model to be a strictly better choice than this blueprint's sidecar model, and what would they have to give up? (§36, ADR-04, §33)
  19. Why does the filter-chain order [authn|authz|ratelimit|fault|retry|router] matter for correctness and not only performance — construct a scenario where reordering two adjacent filters changes the security outcome. (§21.6, §8.9, T4)
  20. How does the telemetry cardinality budget (P13) interact with the per-request peer_principal label — why doesn't labeling metrics by peer identity itself become a cardinality problem at scale? (§22.4, §34, P13)

32. Mental Models & First Principles

MM1 — A service mesh is a distributed configuration-convergence problem wearing a proxy costume; the proxy is the easy half. Predicts: most production incidents trace to xDS convergence (staleness, ordering, NACK handling), not proxy parsing bugs. Bug class without it: over-investing in proxy micro-optimization while under-investing in convergence correctness. Resolves §8.2, §16.

MM2 — Identity is not location; a SPIFFE ID is a cryptographic claim, an IP is a lease. Predicts: any authorization check keyed on IP is eventually wrong, because pods are rescheduled. Bug class without it: authz-by-IP bugs after any reschedule. Resolves §8.4, P2.

MM3 — mTLS everywhere turns every deploy into a PKI operation, so certificate lifetime is a latency-and-availability parameter, not only a security parameter. Predicts: shortening cert lifetime for security trades directly against CA load and rotation-related outage risk. Bug class without it: security mandates for short lifetimes shipped without budgeting the CA-QPS cost. Resolves §4, §19, §34.

MM4 — Eventual consistency in config distribution means every sidecar's "now" is actually "recently"; code that assumes synchronized state assumes a lie. Predicts: any code path comparing "is my config the same as my peer's" is a latent bug. Bug class without it: split-brain routing during any config change. Resolves §8.2, P3, I7.

MM5 — Interception is a NAT problem before it is a proxy problem. Predicts: most "the mesh isn't working" bugs at the earliest phases are kernel-level (iptables/ conntrack), not application-level. Bug class without it: debugging proxy logic for a bug that is actually in the redirect rules. Resolves §8.1, §13.

MM6 — A retry without a budget is a load amplifier, not a resilience mechanism. Predicts: adding retries under partial failure can make total failure more likely, not less, absent a budget. Bug class without it: retry storms (FM-6). Resolves §21, I10, ADR-17.

MM7 — The control plane's job is to be boring and observable; the data plane's job is to be fast and quiet; conflating the two makes both worse. Predicts: a control plane optimized for request-path latency under-invests in the alerting and auditability it actually needs. Bug class without it: control-plane incidents going undetected because the team built dashboards for the wrong plane. Resolves P8, §26.

MM8 — Every filter-chain position is a security decision, not just an ordering convenience. Predicts: swapping two filters' order can silently change what "denied" means (e.g. retry-before-authz). Bug class without it: filter-order regressions reintroducing already-fixed vulnerabilities. Resolves §21.6, §8.9.

5. Required Reading

Books

  • Newman, Building Microservices, 2nd ed., ch. 11 "Security" — zero-trust network assumptions, defense in depth for inter-service calls. Applied in §24 Threat Model and Phase 6 (§18).
  • Kleppmann, Designing Data-Intensive Applications, ch. 9 "Consistency and Consensus" — eventual consistency, the cost of strong agreement at fan-out. Applied in §8.2 (xDS consistency model) and Phase 3 (§15).
  • Nygard, Release It!, 2nd ed., ch. 5 "Stability Patterns" — circuit breaker, timeout, bulkhead, fail-fast. Applied in Phase 9 (§21) retries and circuit breaking.
  • Burns, Designing Distributed Systems, ch. 3 "Sidecars" — the sidecar pattern's contract and failure modes. Applied in §1/§3 and Phase 0 (§12).
  • Beyer et al., Site Reliability Engineering, ch. 4 "Service Level Objectives" — SLOs, error budgets. Applied in §26 Operational Readiness.
  • Stevens, Fenner, Rudoff, UNIX Network Programming, vol. 1, ch. 7 "Socket Options" — socket-level options and getsockopt semantics underlying SO_ORIGINAL_DST. Applied in §8.1 and Phase 1 (§13).

Papers

  • Dean & Barroso, "The Tail at Scale," CACM 2013 — why p99, not average, governs multi-hop systems. Applied in §4 and §30.
  • Mitzenmacher, "The Power of Two Choices in Randomized Load Balancing," IEEE TPDS 2001 — near-optimal load spread at O(1) sample cost. Applied in ADR-15 and Phase 8 (§20).
  • Welsh, Culler, Brewer, "SEDA: An Architecture for Well-Conditioned, Scalable Internet Services," SOSP 2001 — staged event-driven architecture, admission control under load. Applied in Phase 9 (§21) circuit breaking.
  • Sigelman et al., "Dapper, a Large-Scale Distributed Systems Tracing Infrastructure," 2010 — trace-context propagation lineage. Applied in ADR-22 and Phase 10 (§22).
  • Saltzer & Schroeder, "The Protection of Information in Computer Systems," 1975 — fail-safe defaults, least privilege. Applied in §6 P9 and §7 I6.
  • Lamport, "Time, Clocks, and the Ordering of Events in a Distributed System," 1978 — logical ordering without shared clocks. Applied in §8.2 xDS version/nonce ordering.
  • Ongaro & Ousterhout, "In Search of an Understandable Consensus Algorithm (Raft)," USENIX ATC 2014 — leader election, log-replication tradeoffs. Applied in ADR-12, ADR-23.
  • Hunt et al., "ZooKeeper: Wait-free Coordination for Internet-scale Systems," USENIX ATC 2010 — coordination-service design lessons. Applied in ADR-14 rationale.
  • Gupta, Chandra, Goldszmidt, "On Scalable and Efficient Distributed Failure Detectors," DSN 2001 (SWIM) — gossip-based failure detection tradeoffs. Applied in ADR-16 (outlier ejection: local vs. centralized).
  • Karger et al., "Consistent Hashing and Random Trees," STOC 1997 — minimal remapping under membership change. Applied in ADR-15 (rejected alternative) and §8.6.
  • Høiland-Jørgensen et al., "The eXpress Data Path," CoNEXT 2018 — eBPF/XDP performance model. Applied in ADR-03 and PhaseDeferred("§13 Phase 1 — Traffic Interception And Loop Avoidance").

Reference Implementations

  • Envoy — source/common/router/ (route matching, retry/timeout policy), source/common/upstream/ (cluster manager, load balancing, outlier detection). Lesson: the filter-chain trait shape (§11 HttpFilter-equivalent contract) generalizes cleanly. Pitfall not to copy: C++ extensibility surfaces (Lua filter) were a recurring CVE source (§24 T10) — Rust's trait objects remove the memory-safety half of that risk but not the logic-bug half. Applied in Phase 2 (§14).
  • Istio — pilot/pkg/xds/ (ADS server, snapshot generation), security/pkg/ (CA, SDS). Lesson: resource warming and sidecar-scoping are what keep xDS payload size bounded at scale (§8.7, §31). Pitfall not to copy: istiod's monolithic component coupling (Galley/Citadel/Pilot merged) made failure isolation hard — keep mesh-ca and mesh-xds-server separately deployable. Applied in Phase 4 (§16), Phase 5 (§17).
  • Linkerd2-proxy — linkerd/app/ (proxy composition root). Lesson: a pure-Rust data plane is production-viable at mesh scale — the existence proof for ADR-01. Pitfall not to copy: early versions under-invested in fuzzing before hardening; run cargo-fuzz from Phase 0 (ADR-28), not retroactively. Applied in Phase 0 (§12), Phase 6 (§18).
  • Cilium — the eBPF-based sidecarless service-mesh model. Lesson: node-level interception amortizes per-pod overhead. Pitfall not to copy: assuming eBPF eliminates L7 concerns — an L7 waypoint proxy is still required for HTTP/gRPC-level features. Applied in §36 Alternative Architectures.
  • SPIRE — the SPIFFE runtime environment's node-attestation and SVID-rotation workflow. Lesson: attestation-based (not token-based) identity binding is stronger for non-Kubernetes workloads. Pitfall not to copy: SPIRE's plugin architecture adds operational surface this blueprint's scope does not need. Applied in Phase 5 (§17), §8.4.
  • Consul Connect — the alternative non-Kubernetes-native service-discovery source. Lesson: a catalog abstraction decoupled from the orchestrator generalizes to VM topologies. Applied in ADR-13 (rejected alternative) and §33.

RFCs / Specifications

  • RFC 9110 / RFC 9113 (HTTP semantics / HTTP/2) — framing, flow control. Applied in Phase 2 (§14).

  • Envoy xDS protocol documentation (envoyproxy.io, "xDS REST and gRPC protocol") — ADS, ACK/NACK, resource warming. Applied in §8.2–§8.3, Phase 3–4 (§15–§16).
  • Rescorla, published design writing on the TLS 1.3 protocol — rationale behind 1-RTT handshake and PSK resumption. Applied in §4 (handshake-rate targets), Phase 6 (§18).
  • William Morgan, published writing on the service-mesh pattern (buoyant.io articles) — the sidecar-vs-library tradeoff framed historically. Applied in §2, §36.

Glossary (§38) · 52 terms · site-wide glossary

ACK
a DiscoveryRequest confirming successful application of a pushed xDS resource, carrying the applied version_info and the response nonce.
Ambient mode
a sidecarless mesh deployment using a per-node L4 proxy plus an optional per-namespace L7 waypoint; deferred here (§36).
ArcSwap
a lock-free atomic pointer-swap primitive used for ConfigSnapshot and CertBundle installation on the hot path (P10, P6).
AuthzPolicy
the compiled principal×route×effect authorization rule evaluated by the authz filter (§8.9, §11).
Blast radius
the scope of impact of a single failure or compromise; a key axis distinguishing sidecar (T1) from ambient (§36.1) architectures.
Cardinality budget
the bounded set of metric label-value combinations a telemetry system may emit (P13); exceeding it risks self-inflicted DoS (T8).
CDS
Cluster Discovery Service; the xDS resource type carrying cluster definitions (§8.2).
Circuit breaker
a connection-pool-level state machine (CLOSED/OPEN/HALF_OPEN) that fails fast once upstream limits are exceeded (§8.7).
Config convergence
the process by which all subscribed sidecars eventually apply the same control-plane-pushed configuration (§8.2, §16).
ConfigSnapshot
the internally consistent, versioned bundle of listeners/routes/ clusters/endpoints a sidecar holds and swaps atomically (§11, I4).
Conntrack
the Linux kernel's connection-tracking table used by iptables NAT; a scalability bottleneck under high pod churn (FM-9).
Consistent hashing
a hashing scheme minimizing remapping under membership change (Karger et al. 1997); the rejected alternative to power-of-two-choices (ADR-15).
Control plane
the off-data-path component set (discovery, xDS server, CA, policy compiler, telemetry aggregator) that configures the data plane (§3).
Data plane
the sidecar proxies on the actual request path (§3).
Delta xDS
the incremental xDS variant sending only added/updated/removed resources per push, contrasted with SOTW (§8.3); deferred here (§37).
EDS
Endpoint Discovery Service; the xDS resource type carrying per-cluster endpoint lists (§8.2).
Fail closed
a design stance where an unevaluable decision defaults to Deny (I6, P9).
Fail static
a design stance where loss of control-plane connectivity preserves the last-known-good state rather than degrading permissively (P4).
Filter chain
the ordered stack of request/response-processing filters applied by a listener (§3, §11).
iptables REDIRECT
a NAT action rewriting a packet's destination port to a local listener, the mechanism underlying transparent interception (§8.1).
Least-request
a load-balancing policy selecting the endpoint with fewer in-flight requests, implemented here via power-of-two-choices (ADR-15).
LDS
Listener Discovery Service; the xDS resource type carrying listener definitions (§8.2).
Loop avoidance
the UID/owner-based exclusion mechanism preventing a sidecar's own egress from being redirected back into itself (§8.1, I5).
mTLS
mutual TLS; both connection peers authenticate via X.509 certificates (§8.5).
NACK
a DiscoveryRequest rejecting a pushed xDS resource, carrying the last-good version_info and an error_detail (§8.2, I8).
Nonce
an opaque, server-generated token echoed by the client to pair an xDS request with its response (§11).
Outlier ejection
the per-endpoint health state machine that removes and later restores endpoints based on observed failure rate (§8.7, ADR-16).
PeerAuthentication
the policy object controlling whether inbound traffic on a listener must be mTLS (STRICT/PERMISSIVE/DISABLE, §8.9, §11 MtlsMode).
PeerIdentity
the SPIFFE identity extracted from a validated peer certificate during an mTLS handshake (§8.5, §11).
PERMISSIVE mode
an MtlsMode accepting both mTLS and plaintext inbound traffic; a documented risk surface (T4) relative to STRICT.
PolicyDecision
the Allow/Deny outcome of evaluating an AuthzPolicy against a PeerIdentity and route (§8.9, §11).
Power-of-two-choices
a load-balancing sampling technique selecting the better of two uniformly-sampled endpoints (Mitzenmacher 2001, ADR-15).
Resource warming
holding a newly received xDS resource in a pending state until every resource it references is also present, before promoting it into the active ConfigSnapshot (§8.2, I12).
Retry budget
a cluster-wide cap on the ratio of retried to primary requests, preventing retry storms (I10, ADR-17).
RDS
Route Discovery Service; the xDS resource type carrying route tables (§8.2).
RTO
recovery time objective; the target maximum duration of a specific outage class (§4).
SBOM
software bill of materials; a generated manifest of a build's exact dependency graph, used for supply-chain auditing (§29, T10).
SDS
Secret Discovery Service; the xDS resource type carrying TLS certs, keys, and trust bundles (§8.2).
SemVer
semantic versioning; the MAJOR.MINOR.PATCH scheme governing this blueprint's compatibility guarantees (§27).
Sidecar
a proxy process running alongside the application container in the same pod, on the request path for every call (§3).
SLO
service level objective; a target value for an availability or latency metric with an associated error budget (§26).
SO_ORIGINAL_DST
a Linux socket option exposing a redirected connection's pre-NAT destination address (§8.1, §13).
SOTW
state-of-the-world xDS; the variant sending a full resource-type snapshot on every update, contrasted with delta (§8.3).
SPIFFE ID
a URI-formatted workload identity of the form spiffe://<trust-domain>/<path> (§8.4).
STRICT mode
an MtlsMode rejecting any non-mTLS inbound connection at the transport layer (§8.9, I1).
SVID
SPIFFE Verifiable Identity Document; the X.509 certificate embedding a workload's SPIFFE ID as a URI SAN (§8.4, §11).
Traffic split
weighted distribution of requests across multiple destination clusters, e.g. for canary rollout (§8.6).
Trust domain
the root scope for SPIFFE identities within which a single CA root is authoritative (§8.4, P12).
Version skew
the state of a control plane and data plane running different, but mutually compatible, protocol/schema versions simultaneously (§27, ADR-25).
VersionInfo
the opaque string identifying an xDS resource's content version, compared for monotonicity on every push (§11, I2).
WeightedCluster
a route-table entry pairing a destination cluster with a selection weight, the unit of traffic-split arithmetic (§8.6, §11).
xDS
the family of discovery-service protocols (LDS/RDS/CDS/EDS/SDS, aggregated as ADS) by which the control plane configures the data plane (§8.2).
