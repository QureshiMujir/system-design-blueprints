4.2 Determinism constraints

  • Fill path (flatten + coverage) uses integer/fixed-point only — no f32/f64. Float allowed only in pre-scale transform composition if the result is rounded to 26.6 deterministically (prefer fixed throughout).
  • No HashMap iteration order in any output path (use sorted/BTreeMap or arrays where order is observable).
  • No platform libm; any needed transcendentals via fixed-point tables or rejected.

Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from the System Constraints (§4). Figures are order-of-magnitude design budgets, not measurements.

  1. Single-glyph coverage buffer (16 px Latin). bbox ≈ ppem × ppem ≈ 16 × 16 = 256 px; Gray8 = 1 byte/px → 256 B/glyph. Pitch padding negligible. Confirms per-glyph alloc is tiny → pool one reusable buffer (§4.1).

  2. Worst-case single-glyph buffer (guard). bbox dim cap = 8192 px (I18, §4.3) → 8192 × 8192 × 1 B = 64 MiB. This is why a per-render bbox guard exists and why banding (§Phase 8) is needed for large glyphs — a naive full-bbox buffer is unacceptable.

  3. ASCII atlas RAM @24 px. 95 printable glyphs × (≈24 × 24 = 576 px) × 1 B ≈ 53 KiB ink, + 1-px padding ≈ 95 × (26 × 26) ≈ 64 KiB packed. A 256 × 256 Gray8 sheet (64 KiB) holds the ASCII set → one sheet suffices (§Phase 10).

  4. Glyph cache occupancy at default budget. Default budget = 8 MB (§4.1). Avg cached bitmap @16 px ≈ 256 B + Arc/key overhead ≈ 320 B → 8 MB / 320 B ≈ 26,000 glyph entries. Far exceeds a single script's glyph count → near-100% hit rate for steady Latin text (SLO ≥95%, §Operational Readiness).

  5. Cache entries for full CJK at 16 px. A large CJK font ≈ 30,000 glyphs × ≈ (bbox 16² = 256 B + 320 B overhead) ≈ 30,000 × 576 B ≈ 17 MB to cache every glyph once → exceeds 8 MB default; either raise budget to ~24 MB or accept LRU churn (§Scalability Analysis, cache memory row).

  6. Throughput vs latency cross-check. Target ≥200k glyphs/s on 1 core (§4.1) ⇒ ≤ 5 µs/glyph average compute. p50 target is ≤3 µs (cache miss, §4.1) → consistent: 1e6 µs/s ÷ 5 µs ≈ 200k. Confirms the throughput and p50 targets are not mutually contradictory.

  7. Edge buffer sizing. Per-glyph edge buffer cap ≤ 64 KB (§4.1); Edge ≈ 4×i32 + dir ≈ 20 B → 64 KB / 20 B ≈ 3,200 edges. A 16-px Latin glyph flattens to tens of segments; 3,200 is ample headroom and bounds adversarial tessellation.

  8. Cell array footprint (16 px). Cell = 12 B (§11.7 / §Performance Engineering). A 16² glyph touches ≤ ~16 × 32 ≈ 512 cells worst-case → 512 × 12 B ≈ 6 KB → fits L1/L2; reused across glyphs, no per-glyph alloc.

  9. Hinting CPU budget ceiling. Instruction budget ≤ 1,000,000 instr/glyph (§4.1). At a generous ~1 ns/instr interpreter step → ≤ 1 ms/glyph absolute worst case before HintBudgetExceeded. This is 250× the 4-µs render budget → hinting must be opt-in and cached (ADR-11), and the budget exists to bound a bomb, not to be hit normally.

  10. Font open cost. Open ≤ 200 µs for a 200 KB font (§4.1), parsing only directory + head/maxp/hhea (lazy, Principle 12). Directory = numTables × 16 B; a 20-table font = 320 B scanned → microseconds. Confirms lazy loading keeps open well under budget; eager full-table parse would blow it.

  11. Service RAM at scale. N worker threads each need 1 Raster (edges 64 KB + cells 6 KB ≈ 70 KB) + shared read-only FontRef (font bytes, ~200 KB) + shared cache (8 MB). 16 threads → 16 × 70 KB + 200 KB + 8 MB ≈ 9.3 MB working set → trivially fits a container; the cache, not the per-thread state, dominates.

  12. Determinism cross-check cost. Cross-arch CI renders a corpus on x86-64 + aarch64 and byte-compares (I21). At ~50 fonts × ~200 glyphs × 5 µs ≈ 50 ms of render per arch → negligible CI time; determinism verification is cheap, so gate it always.
