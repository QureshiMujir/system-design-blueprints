In one paragraph

A disk-backed, page-oriented B+tree key-value engine, embedded as a library inside a host process: it owns one or more files and offers transactional get, put, delete and range scans with crash recovery, a buffer pool, a write-ahead log, latch-coupled concurrent reads and copy-on-write snapshots (§1). It is the storage layer beneath a database, a graph store or an index — not a database server, not a query language, not a replicated system (§1). Systems engineers embed it; the host operator owns supervision, backups and disk choice (§1). One fixed point anchors the design: "a transaction is durable iff its commit record is fsync'd to the WAL"; every other number is tunable against it (§4, I1, I5).

The problem, concretely

Picture a ten-million-key dataset that must stay ordered on disk, answer a point lookup in a bounded number of page reads, scan a range in order, and never lose an acknowledged write (§4, §32 C3, M12). The blueprint lists how storage actually loses data: a pwrite that returned success but did not survive a power cut, an fsync skipped by a virtualised disk, a freed page reused before its prior write was durable (§2). The simple designs each fail one requirement. Fixed-size record arrays cannot hold variable-length keys without rewriting the whole page on every insert (ADR-03). Keeping everything in RAM with periodic snapshots loses the last few seconds of writes and assumes the data fits in memory, which this engine does not (§34 AA4). An LSM-tree's multi-level read amplification and compaction spikes conflict with the point-lookup and p99 read targets (§34 AA1).

The blueprint's answers are a B+tree whose "height is a logarithm", so doubling the data changes height by roughly one level, not proportionally (§30 MM7); a buffer pool whose eviction is "scheduling, not memory management", because safety comes from pin counts (§30 MM6); a log that is the source of truth while "the data file is a cache of it" (§30 MM2); and snapshots that turn concurrency control into a garbage-collection problem (§30 MM4). The hardest part is ordering: writing data-file bytes before the WAL record is durable is "the single invisible-data-loss bug" (§30 MM2, §18.6).

How it works, end to end

The blueprint describes six layers that are "layered, not woven": the tree never touches a raw byte, the buffer pool never knows what a key is, the page codec never knows what a B+tree is, and the pager never knows what a page means (§3):

Each box is one crate: btree-engine (public API and engine), btree-tree, btree-wal, btree-bufpool, btree-page (the codec), btree-pager, with btree-cow holding snapshots and vacuum (§1). Follow one put and commit:

  1. Write. begin_write blocks if another write transaction is live (§8.3, P3). A put never modifies a page in place: btree-tree copies the page to a new page number and copies every page on the path from that leaf to the root (the "ridge") (§21.2).
  2. Through the pool. Every page access goes through btree-bufpool, which pins the frame so it cannot be evicted (I3), verifies the CRC-32C on read (I2), and evicts with a CLOCK sweep on a miss (§17.2). No component but the async flusher writes the data file (P12).
  3. Commit. The engine appends a Commit record and calls flush_through; only when the fsync returns is the transaction durable (§8.3, I1). Then the writer writes whichever of the two meta pages has the older LSN, pointing it at the new root, and fsyncs it (§21.2).
  4. Readers. begin_read never blocks (P3). A reader holds a root page number and read version, so it keeps seeing its own tree while the writer moves on (§21.2, P4, ADR-10).
  5. Flush. The flusher never writes a page whose LSN is ahead of the last durable WAL LSN (I4).
  6. Crash and reopen. Recovery picks the newer valid meta page (I10), buffers each transaction's records, applies them only when its Commit is seen, and discards them on Abort — redo only, no undo, because there is one writer (§8.4, ADR-05). Where the scan starts is stated two ways: §8.4 and §18.2 step 5 scan from meta.last_committed_lsn + 1, while P5 and I5's recovery column say replay runs from the last checkpoint (LSN).

The core ideas

Slotted pages and cells (§8.1)

A page holds a header, a slot array that grows rightwards and stays sorted by key, free space in the middle, cells growing leftwards from the end, and a 4-byte CRC-32C trailer (§8.1). The default page is 4,096 B (§4). §8.1 draws the header as 24 B with the 4-byte trailer separate; §32's capacity model instead uses 24 B for "page-header+trailer overhead" combined. A small trace of the three cell forms (§8.1):

Cell Layout
leaf, inline [u32 key_len][u32 val_len][key][val]
leaf, overflow [u32 key_len][u32 0][u64 first_overflow_pgno][u64 total_len][key]
internal [u32 sep_len][u32 0][u64 child_pgno][sep]

A value above pagesize / 4 (1,024 B by default) goes to an overflow chain (§4, ADR-19). Integers are little-endian regardless of host, and the file header and both meta pages use the same header and trailer as every other page (§8.1). A page whose free_off places the slot array past the trailer is rejected with Error::PageCorrupt before any cell is read: bounds are checked, never trusted (§8.6, P13).

Fanout is amortisation, height is a logarithm (§8.5, §32, MM1, MM7)

With suffix-truncated separators of about 12 B, an internal cell is 24 B and a page holds about 169 children; with prefix-compressed keys and 200 B values a leaf cell is about 212 B and a leaf holds about 19 cells (§32 C1, C2). Ten million keys need about 526,316 leaves; 169³ ≈ 4.8 M is at least that, so three levels sit above the leaves and total height is about 4 (§32 C3). That is why fanout, not height, dominates capacity planning (§30 MM1).

The worked split (fanout 4, illustrative, §8.5): (1) the leaf is full, so allocate leaf R; (2) copy the upper half of L's cells into R; (3) R.next_sibling = L.next_sibling, L.next_sibling = R.pgno; (4) separator = R's first key; (5) insert it into parent P; (6) if P is full, split it and recurse; (7) if the root split, allocate a new root and update the meta page's root_pgno. Updating the sibling link with every split (I7) is what gives range scans their O(result) cost (ADR-02).

The log is the truth; the file is a cache (§8.2, I5, MM2)

A WAL record header is u64 lsn, u64 txn, u8 kind, 3 B pad, u32 plen, u32 crc32c, then the payload; the CRC-32C covers (lsn, txn_id, kind, plen, payload) (§8.2, I12). Kinds are Begin, PageWrite, FullPage, AllocPage, FreePage, SetMeta, Commit, Abort and Checkpoint, and records never span a segment file (§8.2). Group commit lets the first caller to flush_through pay one fsync for a whole batch while the others wait on a condvar with a 10 ms timeout (§18.2).

The blueprint gives two different fsync rates. §4 puts fsync at about 150 µs, from which §32 C6 derives a serial ceiling of about 6,667 commits/s and a required batch of about 225 commits per flush to reach M4's 1,500,000 inserts/s. §18.2 step 3 and MM8 give the raw rate as about 300–1,500 fsyncs/s on the reference NVMe, citing §4. C6 says its 225 "validates" M14, whose target is ≥ 200 commits per flush (§28). A kill -9 between the WAL write and its fsync leaves the record absent or present without a Commit; either way the transaction never happened (§8.7, I1).

Pinning is safety; eviction is scheduling (§17, I3, MM6)

A frame with a pin count above zero is never evicted (I3). The CLOCK sweep skips pinned frames, clears and skips a set reference bit, evicts an unpinned frame whose bit is clear, and returns Error::PoolExhausted after a fully pinned sweep (§17.2). Pin guards decrement on drop (RAII), the mitigation for a panic that would otherwise leak a pin (§22 T7). Which unpinned page to evict is a throughput and fairness choice, not a memory-safety one (§30 MM6, ADR-07).

If all 16,384 default frames hold leaves, they cover about 311,296 keys, about 3.1% of the 10 M dataset; that "hot subset" is what M13's 95% hit-rate target is measured against (§32 C4). M13 itself names the dataset as 2.5 GB (§28), while §32 C9 sizes it at about 2.1 GB.

Latch crabbing (§20, I6, P8, MM3)

A read descent latches the child, releases the parent, and repeats, so at most two latches are held (§20.2, I6). A write descent releases the parent only if the child is "safe": a leaf with free_size > cell_len or an internal page with n_cells < max - 1 (§20.2). Latch levels must be non-decreasing from root to leaf, checked by a debug-build per-thread stack (I6). The blueprint states the bound two ways: P8 says lock coupling "holds at most two latches at once", while P8's own trade-off and §20.2 step 3 say an unsafe child keeps the parent held, so a split that propagates to the root holds latches up the whole path. A latch protects bytes in memory for one page operation; a lock protects a logical entity across a transaction (§30 MM3). Holding a latch across a disk read serialises every other descender behind a millisecond-scale I/O (§20.7).

Copy-on-write snapshots and vacuum (§21, I9, MM4)

A snapshot is { root_pgno, read_version }, costing one u64 and a refcount entry (§21.2, ADR-10). Pages freed by a copy-on-write commit are tagged "free at version V" and move to the active freelist only once no live snapshot's read_version is ≤ V (§21.2, I9). The price is the ridge copy on every commit, whose cost scales with tree height, not dataset size (P4, §21.7). The failure is a leaked snapshot handle pinning every version since it opened, seen as btree_snapshot_count stuck high (FM-6).

The trade-offs — where engineers disagree

Tree variant: B+tree, not LSM-tree (ADR-02)

Chosen: a B+tree — data only in leaves plus sibling links, so a range scan is O(result) (ADR-02). Rejected: a classic B-tree, a B*-tree, an LSM-tree. When the rejected choice is right: a classic B-tree for point-lookup-only, fixed-record workloads with acute per-node space pressure; an LSM-tree for write-dominated, append-heavy ingestion (ADR-02, §34 AA1).

Recovery: redo-only now, full ARIES later (ADR-05)

Chosen: WAL redo only; undo is needed only once concurrent-writer rollback exists, and a single writer makes redo sufficient (ADR-05, I1). Rejected: full ARIES — redo, undo and fine-grained locking — from Phase 0. When the rejected choice is right: "the instant multi-writer txns ship" (ADR-05, §35 row 1).

Concurrency: one writer, many readers (ADR-08)

Chosen: single writer, many readers — no write-write conflict resolution, and readers never block (ADR-08, P3, P4). Rejected: multi-writer two-phase locking; multi-writer optimistic concurrency. When the rejected choice is right: multi-writer 2PL wins once the single writer's WAL append saturates before the disk does (ADR-08).

Read isolation: copy-on-write snapshots, not MVCC chains (ADR-10)

Chosen: a copy-on-write snapshot by root-page swap; cost is one u64 plus a refcount, with zero reader locking (ADR-10). Rejected: MVCC version chains from Phase 0; a global read-write lock. When the rejected choice is right: MVCC once concurrent writers must coexist with long-lived snapshots (ADR-10, §35 row 4). ADR-02, ADR-05, ADR-08 and ADR-10 are the load-bearing four: overturning any one moves the whole architecture (§9).

Eviction: CLOCK, not LRU-K (ADR-07)

Chosen: CLOCK — one reference bit per frame, one sweep cursor, no mutation on every touch (ADR-07). Rejected: strict LRU, LFU, random. When the rejected choice is right: LRU-K under strong recency skew that CLOCK's one bit cannot distinguish (ADR-07).

Torn-write protection: full-page images after a checkpoint (ADR-16)

Chosen: the first write to a page after a checkpoint logs a FullPage image; the double-write buffer is deferred (ADR-16, §18.2). Rejected: shipping a double-write buffer in Phase 0. When the rejected choice is right: once repair cost (full WAL replay) exceeds the buffer's constant-time restore under high dirty-page churn (ADR-16, §35 row 5).

Large values: overflow chains, not a value log (ADR-19)

Chosen: an overflow-page chain, which keeps leaf fanout high so only large-value reads pay the extra I/O (ADR-19). Rejected: always inline with splits absorbing the size; an external value log (WiscKey). When the rejected choice is right: an external value log for large, write-once or rarely read values (ADR-19).

Roads not taken (§34)

An LSM-tree wins for write-dominated, append-heavy ingestion that tolerates read amplification and compaction stalls; rejected because M1 and M9 assume a bounded number of page fetches per read (§34 AA1).

A Bw-tree (lock-free mapping table and delta chains) wins at extreme core counts where even brief latch holds dominate; rejected as the default because its compare-and-swap protocol is much harder to make correct, and a single writer does not need lock-freedom — kept as a stretch path (§34 AA2, ADR-23, §35 row 3).

A fractal tree (message buffers in internal nodes) wins where write amplification must stay near-optimal; rejected because buffered-but-unflushed messages add a second recovery dimension the redo-only model does not need (§34 AA3).

An in-memory store with periodic snapshots wins when data fits in RAM and losing the last few seconds is acceptable; rejected because this engine assumes datasets larger than RAM (§34 AA4).

The deferred register also holds B-link optimistic descent, MVCC chains, zstd page compression, encryption at rest and online backup, each with a named un-defer trigger (§35).

What must never be false

  • I1 — a committed transaction survives any crash after its commit-record fsync; noticed by the crash-injection fixtures (§26).
  • I2 — every page read verifies its CRC-32C first; a failure is Error::PageCorrupt, and the page-codec fuzz target exercises it.
  • I3 — a pinned frame is never evicted; tested by a 1 M-pin stress test, surfaced as Error::PoolExhausted.
  • I4 — the flusher never writes a page whose LSN exceeds the last durable WAL LSN; the kill-mid-pagewrite crash fixture checks it.
  • I5 — the WAL is the sole durability primitive and the data file may lag it without bound; checked by the 24 h soak (M10).
  • I6 — latches are taken in non-decreasing tree-level order; a debug latch-stack assertion panics on violation.
  • I7 — a leaf's sibling pointer is updated atomically with every split; the range-cross-leaf fixture checks it and fsck flags a broken chain.
  • I8 — total pages equal freelist pages plus live pages after every commit; a debug commit-time assertion and the btree_freelist_pages gauge.
  • I9 — a page freed by a CoW commit is not reused while a live snapshot needs it; the snapshot-vacuum fixture and the btree_snapshot_count gauge.
  • I10 — on open, the meta page with the higher verified LSN (tie broken by txn_id) wins; a two-meta-same-LSN crash fixture.
  • I11 — a dirty page's bytes are never partly visible to a reader; prevented by the type system, checked by the concurrent-readers fixture.
  • I12 — every WAL record's CRC-32C covers LSN, transaction id, kind, length and payload; a failure halts replay with Error::WalCorrupt.
  • I13 — key and value sizes never exceed the ceilings without an explicit overflow chain; KeyTooLarge/ValueTooLarge unit tests.
  • I14 — replaying the same WAL range twice gives identical state, because redo applies only if header.lsn < record.lsn; a 24 h soak with forced repeat-replay.

What breaks in production

  • FM-1 — torn page write. Symptom: PageCorrupt after a crash. Cause: power cut mid-pwrite or a missing FullPage rule. Noticed by the CRC mismatch on the next read; the FullPage replay restores the image.
  • FM-2 — truncated WAL tail. Symptom: WalTruncated on open after a crash mid-append. Noticed as a bad CRC or short header at the scan boundary; the tail past the last Commit is discarded (I14).
  • FM-3 — buffer-pool exhaustion. Symptom: PoolExhausted under load, from a pin leak, an undersized pool or a pathological scan. A full CLOCK sweep finds no victim; nothing recovers automatically — raise buffer_pool_pages and audit pin leaks.
  • FM-6 — unbounded growth under a live snapshot. The file grows without bound because a leaked Snapshot pins every version since it opened; btree_snapshot_count stays high, and the fix is to find and close the leaked handle via a registry dump.
  • FM-7 — lying disk. Committed data is missing after a power cut with no error at commit, because a virtualised disk ignored the flush. Nothing in-process detects it; the operator replaces or pre-validates the storage.
  • FM-8 — group-commit stall. p99 commit latency spikes above M8 when the flush leader starves or segment rotation contends; seen in btree_wal_fsync_latency_seconds, and the 10 ms condvar timeout forces a retry.
  • FM-9 — recovery exceeds the RTO. Db::open runs long because checkpoints are too far apart; seen in btree_recovery_duration_seconds. Replay is never truncated for speed; tune checkpoint cadence down.
  • FM-10 — prefix-compression corruption. A stale prefix_len after an insert gives a wrong search result; caught by the BTreeMap oracle test, not by a CRC, which proves only "unchanged since written" (§30 MM5).

Threats worth knowing (§22): T1 and T2, malformed page or WAL bytes from bit rot or a crash, met by CRC-32C and bounded parsing under fuzzing; T3, adversarial key or value sizes from the caller, rejected at the API boundary (I13); T4, fsync reporting success without durability — "the one undetectable-in-process threat"; T7, a pin leak from a panic, met by RAII pin guards.

How it compares

  • SQLite lets the application choose a rollback journal or a WAL, trading a simpler single-file story for a less rigid durability contract (§31). It wins when embeddability and zero configuration matter more than a locked-down recovery model (§31).
  • LMDB uses mmap-backed copy-on-write with no locking on the read path, paying write amplification proportional to tree height on every commit (§31). It wins when reads vastly outnumber writes and the data fits the address space (§31).
  • InnoDB chose full ARIES (redo and undo) plus MVCC from the start, a far larger surface (§31). It wins whenever concurrent write transactions with rollback are a hard requirement, which this engine defers (§31, §35 row 1).
  • BoltDB/bbolt is the smallest copy-on-write B+tree in a garbage-collected language, trading peak throughput and p99 tail latency for simplicity (§31). It wins for embedded config and metadata stores where velocity matters more than raw OLTP throughput (§31).
  • WiredTiger has a pluggable B-tree-or-LSM core with built-in compression and an eviction-server thread pool, trading implementation complexity for tunable amplification (§31). It wins when one storage layer must serve both write-heavy and read-heavy collections (§31).

If you only remember three things

A transaction is durable only when its commit record is fsynced to the WAL; the data file is a cache of the log and may lag it without bound (§4, I5, MM2). Fanout, not height, dominates capacity planning, and ten million keys fit in a tree about four levels tall (MM1, §32 C3). Pin counts make eviction safe, and copy-on-write turns concurrency into garbage collection, so a leaked snapshot grows the file without bound (I3, MM4, FM-6).

Words used here

  • Page / slotted page — the fixed-size unit of disk I/O, laid out as header, slot array and cells.
  • Cell — the variable-length key (plus value or child page number) that a slot points at.
  • Fanout — the number of children or cells one page holds.
  • Separator key — the internal-page key that bounds a child subtree, possibly suffix-truncated.
  • Overflow page — a chained page holding a value too large to fit inline.
  • Buffer pool / frame / pin — the in-memory page cache, one of its slots, and the count that blocks eviction.
  • CLOCK — the one-reference-bit approximate-LRU eviction algorithm.
  • WAL / LSN — the append-only durability log, and a record's monotonic position in it.
  • Group commit — batching many transactions' fsyncs into one.
  • Redo — reapplying a committed change during recovery.
  • Latch / latch crabbing — an in-memory lock for one page operation; holding at most two at a time while descending (§36).
  • Copy-on-write snapshot — a handle on one tree version (root page number plus read version).
  • Vacuum — the delayed reclaim of CoW pages no live snapshot needs.
  • Torn write — a page only partly written before a crash.
  • Meta page — one of two alternating pages holding the root, freelist head and last committed LSN.
