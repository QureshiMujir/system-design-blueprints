Project Number: 184

Project Name: B-Tree Storage

1. Goal & Scope

A disk-backed, page-oriented B+tree key-value storage engine, embedded as a process-local library: it owns one or more files on disk and exposes a transactional get/put/delete/range-scan API with crash recovery, buffer-pool caching, write-ahead logging, latch-coupled concurrent reads, and copy-on-write snapshots. It is the storage layer beneath a database, graph store, query-planner index, or any component needing durable, ordered, on-disk key-value storage — not a database server, not a query language, not a replicated system.

Phase-0 deliverable (numbered modules, one per crate, §10 Repository Layout):

  1. btree-pager — file I/O: pread/pwrite, fsync/fdatasync, allocation, O_DIRECT.
  2. btree-page — page codec: slotted layout, CRC32C, cell encode/decode.
  3. btree-tree — B+tree: search, insert, split, merge, range scan, bulk load.
  4. btree-bufpool — buffer pool: frame table, pin/unpin, CLOCK eviction, async flush.
  5. btree-wal — write-ahead log: append, group commit, redo replay, checkpoint.
  6. btree-cow — copy-on-write snapshots: root-pgno swap, snapshot lifecycle, vacuum.
  7. btree-engine — public crate: Db, ReadTxn, WriteTxn, Error, Telemetry, DbOptions.
  8. btree-cli — btreectl: open, dump, fsck, repair, bulk-load, snapshot, bench.
  9. btree-bench — benchmark binaries (YCSB-A/point-lookup/bulk-load harnesses).

System boundaries.

  • Provides: ordered key-value storage, crash-safe commit, single-writer/many-reader concurrency, snapshot isolation for readers, checkpointing, bulk load, operator tooling.
  • Delegates: SQL/query parsing, query planning, distributed replication, consensus, network protocol, authentication — all out of scope, owned by a caller.
  • Does NOT provide: multi-writer transactions (Phase-0; see Deferred Features Register), ARIES undo/rollback (redo-only in Phase 0), encryption-at-rest, network access.

Non-goals: SQL, a query planner, physical replication, distributed consensus, a network wire protocol, multi-tenant access control. Deployment model: statically or dynamically linked library inside a host process; one open file set per Db::open; no daemon, no network listener. Target users/operators: systems engineers embedding the engine into a larger service; the operator owns the host process's supervision, backup scheduling, and disk selection (§22 T4). What later phases unlock: Phase 6 (§18) unlocks crash recovery; Phase 8 (§20) unlocks concurrent readers during writes; Phase 9 (§21) unlocks snapshot exports and online backup foundations.

Recommended language: Rust, stable, edition 2021. Rationale (ADR-01, §9): the borrow checker gives an auditable safety boundary around the three unsafe modules (Pager, Wal, page codec) without a garbage collector's pause risk, which the p99 targets (§4, M8/M9) require. Rejected: C/C++ (the LMDB/SQLite/InnoDB precedent — rejected because unsafe-by-default raises the audit cost across the whole codebase, not just three modules); Go (the BoltDB precedent — rejected because GC pauses conflict with the p99 read-latency target, M9); Java/JVM (rejected for the same GC-pause reason, compounded by JNI overhead at the syscall boundary).

Prerequisites: B-tree algorithmics (can describe split/merge from memory); intermediate Rust (lifetimes, Send/Sync, unsafe discipline); the storage stack from VFS to block device (page cache, fsync, write barriers); the WAL/ARIES model at the level of Mohan et al. 1992, sections 1 through 3 of that paper; the LMDB and BoltDB source trees as readable references (§5).

Estimated timeline: Phase 0 (§12) — 1 week. Full system (Phases 0–9, §12–§21) — 8–10 weeks at one senior engineer full-time; 4–6 months part-time. Every deferred feature is flagged PhaseDeferred("<anchor>") (the convention detailed in the Deferred Features Register, §35).

2. Why Build This

A storage engine is the component blamed when a database loses data and ignored when it does not. Nearly every real data-loss incident traces to the storage boundary: a pwrite that returned success but did not survive a power cut, an fsync elided by a virtualized disk (§22 T4; Rebello et al. 2020), a freed page reused before its prior write was durable (I8). Building this engine means owning the code that must not have those bugs, not just reading about them.

This project is the smallest engine that still teaches the full surface: the page format and slotted-cell layout (§14), the buffer pool and CLOCK eviction (§17), the write-ahead log and redo recovery (§18), latch coupling for concurrent descent (§20), and copy-on-write snapshots (§21). It builds the calibration to read LMDB's mdb.c, SQLite's btree.c/pager.c, and InnoDB's btr/ and understand exactly which lines execute when an application calls db.put(k, v) then txn.commit(). It deliberately narrows scope — no SQL, no query planner, no replication, no full ARIES undo (§9 ADR-05) — because that focus is the only reason the timeline is weeks, not years, while the transferable knowledge (crash safety, buffer management, latch protocols) is unchanged by the narrowing.

Cross-links: the WAL crate (btree-wal) is a from-scratch reimplementation of the same primitive taught by the workspace's Write-Ahead-Log project rather than a dependency on it — a storage engine that depends on its own durability primitive at compile time from an external crate is not exercising the lesson. The buffer-pool eviction path (§17) is the same problem as the workspace's LRU-LFU-Cache project; EvictionPolicy (§11.6) is the seam where that project's policy can be swapped in behind a feature flag (ADR-07).

What Mastery Looks Like (competency ↔ phase):

  • Explain why "the WAL is the durability boundary, the data file is a cache of it" makes redo-only recovery correct without an undo log — Phase 6 (§18).
  • Trace a leaf split's effect on the parent, the sibling chain, and a concurrent range scan — Phase 4 (§16) and Phase 7 (§19).
  • Derive tree height and buffer-pool hit rate from page size, fanout, and dataset size instead of asserting them — §32 (Back-of-Envelope Capacity Model).
  • Reason about the latch-crabbing safety theorem: why releasing a parent latch before the child is provably safe is safe — Phase 8 (§20).
  • Distinguish a structural checksum (CRC32C proves bytes are what was written) from a semantic one — Phase 2 (§14) and I2 (§7).
  • Explain why copy-on-write turns concurrency control into a garbage-collection problem (deferred reclaim, vacuum) — Phase 9 (§21) and I9 (§7).
  • Compare this engine's tradeoffs against SQLite, LMDB, InnoDB, BoltDB, and WiredTiger with the specific dimension each system chose differently — §31 (Comparative Architecture Table).

Three properties hold throughout: (1) the data path is layered, not woven — the tree never touches a raw byte, the buffer pool never knows what a key is, the page codec never knows what a B+tree is, the pager never knows what a page's meaning is; (2) the WAL is the durability primitive (I5); every other component is an optimization against it — a page never written to disk is still recoverable from the WAL up to the last fsync'd record; (3) every cross-cutting concern (page size, key/value limits, error type, telemetry) is owned by btree-engine::config and threaded through — no layer reaches across another.

Boxes, one paragraph each. Public API is the only surface an embedding application sees; it never exposes a page number, a latch handle, or a buffer-pool-lifetime-bound byte slice. Engine owns the one live WriteTxn at a time and the registry of live Snapshots (I9). Tree is pure algorithm over pages fetched through the buffer pool; it holds latches, never raw file offsets. WAL is append-only bytes plus a replay function; it does not know what a page's contents mean, only that a record is (lsn, txn_id, kind, payload). Buffer Pool is a fixed-size cache with a pin discipline that makes eviction safe under concurrent access. Page Codec is a pure transform between bytes and (header, slots, cells); it never touches disk. Pager is the only file-descriptor owner in the process for a given Db.

6. Design Principles

  1. P1 — Crash safety is the ground truth. Every write that returns success from commit() is recoverable after kill -9 + power cut. Tradeoff: forbids any optimization that reorders the WAL-fsync-before-meta-write sequence (§18.6). Operational implication: crash-injection fixtures (§26) gate every release. Violating it: silent data loss indistinguishable from a correct system until the next crash.
  2. P2 — The page is the unit of work. Buffer pool, WAL, checksum, and recovery all speak in whole pages; sub-page operations live only inside the codec. Tradeoff: some space waste on small values. Operational implication: every I/O is page-aligned, simplifying O_DIRECT (ADR-15). Violating it: partial-page writes reintroduce torn-write risk the CRC (I2) can't catch.
  3. P3 — One writer, many readers. Concurrent writers are a Phase-1+ surface (§35 row 1); begin_write blocks a second caller, begin_read never blocks. Tradeoff: write throughput capped by one thread's WAL-append rate. Operational implication: no write-write conflict resolution code exists in Phase 0. Violating it (accepting concurrent writers without B-link or MVCC, §35 rows 2/4) corrupts the tree under concurrent structural mutation.
  4. P4 — Snapshots are free for readers. A ReadTxn holds a root pgno + read-version; cost is one u64 + a refcount (§21.3). Tradeoff: CoW write amplification (every path from a modified leaf to the root is copied, §21.1). Operational implication: no reader-side locking at all. Violating it: a global lock for consistency defeats the entire design's read-scaling claim (M2).
  5. P5 — The WAL is the durability boundary. A transaction is durable iff its commit record is fsync'd (I1). The data file may lag unboundedly. Tradeoff: recovery must replay from the last checkpoint, bounding startup time by WAL size (§32 C10). Operational implication: checkpoint cadence is an RTO lever (§24). Violating it: writing the meta page before the WAL fsync is the single bug class that loses committed data invisibly (§27 pitfall list).
  6. P6 — No silent corruption. Every page and WAL record carries an independent CRC32C (I2, I12). A bad page surfaces as Error::PageCorrupt, never silently re-read or repaired. Tradeoff: a CRC-verified read costs one extra pass over the page bytes. Operational implication: repair is a separate, explicit btreectl repair subcommand. Violating it: silent auto-repair hides the operator signal that a device is failing.
  7. P7 — No silent fallbacks. A requested O_DIRECT that is unavailable is a hard open error, not a silent downgrade; a short pwrite is a hard error, not a silent retry. Tradeoff: the engine refuses to "just work" on a misconfigured host. Operational implication: operators get one clear error, not a mysteriously slow or unsafe database. Violating it: silent retry under a different durability policy destroys the auditability the whole threat model (§22) depends on.
  8. P8 — Latches do not nest unbounded. Lock coupling holds at most two latches at once (I6, §20.2), releasing the parent once the child is safe. Tradeoff: a split/merge that propagates to the root holds latches up the whole path — bounded but rare. Operational implication: a per-thread debug-build latch-stack assertion catches order violations before they become deadlocks. Violating it: unbounded latch nesting is the direct cause of the B-tree deadlocks that take a week to debug (§27).
  9. P9 — Allocation is bounded. A WriteTxn's dirty-page budget (default 64 MiB) triggers a flush, never an OOM (§4). Tradeoff: a pathological single transaction is throttled, not allowed to run unbounded. Operational implication: budget exhaustion is a metric (btree_buffer_pool_dirty_pages), not a kernel OOM-killer event. Violating it moves the failure mode from "visible in telemetry" to "invisible until the kernel kills the process."
  10. P10 — One config struct, one error enum, one telemetry trait. All knobs on DbOptions; all errors are Error variants; all metrics flow through Telemetry (§11.4). Tradeoff: no plugin runtime — new behavior ships behind a cfg(feature) flag, recompiled. Operational implication: one place to look for every tunable. Violating it (scattering config across ad hoc globals) is what makes production incidents take hours instead of minutes to diagnose.
  11. P11 — Recovery is idempotent. Replaying the same WAL range N times produces the same on-disk state as replaying it once (I14): a redo record applies only if the target page's header.lsn < record.lsn. Tradeoff: every page carries its own LSN, one extra 8-byte field. Operational implication: a stuck recovery can be safely re-run without a special "already partially recovered" state. Violating it makes crash-during-recovery an unrecoverable state.
  12. P12 — The buffer pool is the only path to disk. No component but the async flusher (§17.5) issues a pwrite to the data file after Phase 5 lands. Tradeoff: every read/write, even inside the tree, goes through pin/pin_mut (§11.3). Operational implication: the WAL ordering rule (I4) has exactly one enforcement point. Violating it (a component bypassing the pool) breaks I4 silently — a page can become durable before its log record.
  13. P13 — Checksums are structural, not semantic. CRC32C proves "these bytes are what was written," never "these bytes are meaningful" (a well-formed-but-wrong key still passes CRC). Tradeoff: the codec still needs bounds checks (cell offsets inside the page) independent of the CRC. Operational implication: fuzzing (§26, fuzz_targets/page_codec.rs) targets logic bugs the CRC cannot catch. Violating it (treating a CRC pass as "this page is correct") lets a bounds-check bug slip past code review.
  14. P14 — Every locked on-disk format is versioned. Page size, WAL record layout, and file magic are all read from the header at open (§8.1), never assumed from a compile-time constant alone. Tradeoff: one extra field (format_version) per format. Operational implication: a future format change can detect and refuse (or migrate) an old file instead of misreading it. Violating it turns every future format change into a silent misinterpretation of old files.

Enforced at the type level where possible (public API never exposes a page number, latch handle, or pool-lifetime-bound slice); by code review where not.

8. Domain Model / Protocol / Data Model

8.1 On-disk page byte layout

byte 0                                                      pagesize-4  pagesize
┌────────────────┬──────────────┬───────────────┬───────────┬──────────┐
│ PageHeader(24B)│ Slot array   │  free space   │ Cell area │ CRC32C(4)│
│ pgno,kind,lsn, │ (grows right)│ (shrinks as   │(grows left│ trailer  │
│ n_cells,free_* │ sorted by key│  both grow)   │ from end) │          │
└────────────────┴──────────────┴───────────────┴───────────┴──────────┘

Cell (leaf, inline): [u32 key_len][u32 val_len][key bytes][val bytes]. Cell (leaf, overflow): [u32 key_len][u32 0][u64 first_overflow_pgno][u64 total_len][key bytes]. Cell (internal): [u32 sep_len][u32 0][u64 child_pgno][sep bytes]. All integers little-endian regardless of host (P14). File header (page 0) and the two meta pages (1, 2) use the same PageHeader + trailer layout as every other page (§12.2) — no special case.

8.2 WAL record wire format

+---------+---------+--------+---------+----------+------------+
| u64 lsn | u64 txn | u8 knd | 3B pad  | u32 plen | u32 crc32c |
+---------+---------+--------+---------+----------+------------+
| payload (plen bytes, kind-specific: Begin/PageWrite/FullPage/  |
| AllocPage/FreePage/SetMeta/Commit/Abort/Checkpoint)             |
+------------------------------------------------------------------+

CRC32C covers (lsn, txn_id, kind, plen, payload) (I12). Records never span a segment file; a record that would not fit is deferred to the next segment, padding the residual space of the current one with a kind == 0, plen == 0 sentinel.

8.3 Transaction state machine

From Event To Notes
— begin_write Active blocks if another WriteTxn is live (P3)
Active put/delete Active mutates the CoW ridge (§21.1), no disk I/O required yet
Active commit Committing WAL Commit record appended, flush_through called
Committing flush_through returns Ok Committed I1 satisfied; meta page swap follows
Committing I/O error on flush Aborted WAL Abort implied by absence of Commit durability
Active abort Aborted dirty pages discarded, no WAL record required for redo-only

8.4 Recovery state machine (redo-only, ADR-05)

From Event To
Start meta pages read, newer-valid selected (I10) Scanning
Scanning WAL walked from meta.last_committed_lsn + 1 Buffering
Buffering Commit(txn_id) seen Applying
Applying all buffered records for txn_id applied in LSN order (I14) Scanning
Buffering Abort(txn_id) seen Scanning (txn's records discarded)
Scanning bad CRC / truncated header Truncated (policy-gated, §18.7)
Truncated past last Commit Done (discard tail)
Truncated inside a replayed txn Fail (Error::WalTruncated, StrictRedo)
Scanning EOF on a record boundary Done

8.5 Worked example — insert causing a two-level split

Insert k=500 into a leaf at 100% fill (fanout 4, illustrative): (1) leaf full → allocate leaf R; (2) copy upper half of leaf L's cells into R; (3) R.next_sibling = L.next_sibling, L.next_sibling = R.pgno; (4) separator = R.cell(0).key; (5) insert (separator, R.pgno) into parent P; (6) if P is also full, recurse: allocate P', split, propagate (sep', P'.pgno) to grandparent; (7) if the root split, allocate a new root with two children, update meta root_pgno (§16.1, cites P2, I7, ADR-18).

8.6 Malformed-input example

A page whose header.free_off places the slot array past pagesize - 4 (the CRC trailer) is rejected at PageRef::new with Error::PageCorrupt(pgno) before any cell is dereferenced — bounds are checked against the header fields, never trusted (P13, conformance/corpora/pages/ leaf-bad-slot.bin, §14.8).

8.7 Failure-path example

kill -9 between the WAL pwrite succeeding and its fsync completing: on reopen, recovery reads the meta pages (I10), scans from last_committed_lsn + 1, and finds the un-fsync'd record either absent (if the kernel had not yet flushed the write to its page cache view — indistinguish- able from "never written") or present-but-un-committed (no matching Commit record) — either way the transaction is correctly treated as never-happened (I1, conformance/corpora/crash/ kill-after-pwrite.bin, §18.5).

corpora/pages/02-bad-crc.bin trailing CRC bit-flipped Error::PageCorrupt(FILE_HEADER_PAGE)

12.6 Pitfalls

  • The file header is a page (P2, P14); special-casing its layout hides bugs that later shadow every other page type.
  • repr(C) padding is not zeroed by default; a Box<[u8; 4096]> from MaybeUninit::zeroed() is required — uninitialized padding leaking into the file is a real, Miri-catchable bug class.
  • Skipping fsync "because it's just a smoke test" defeats the point: the recovery path must mean what it says from day one (P1).

12.7 Performance Concerns

A single fsync costs roughly the reference host's 150 µs (§4); at Phase 0 this is irrelevant (one call, one test) but establishes the baseline the group-commit design (§18.3) later amortizes.

12.8 Edge Cases

  • Reopening a file whose page size in the header disagrees with DbOptions::page_size — must be a hard error, not a silent override (P7, P14).
  • A zero-length file (never opened before) vs. a truncated file (crashed mid-format) — both must produce distinct, diagnosable errors, not the same generic I/O error.

12.9 Failure Analysis

A failure here (a bad CRC on the very first read) blocks every later phase, so detection must be immediate and unambiguous: Error::PageCorrupt(FILE_HEADER_PAGE) with the page number named explicitly, not a bare I/O error. Blast radius: total (nothing above Phase 0 can proceed). Containment: the smoke test is the CI gate that catches this before merge.

12.10 Operational Notes

make bootstrap is the only supported first command for a new clone; document its exact output in README.md so a new operator can diagnose environment drift (missing clang/lld, wrong Rust channel) from the first failure message alone.

13. Phase 1 — Pager

13.1 Objectives

Build the engine's only entry point to the filesystem (P2, P12): file I/O, alignment, allocation, and the fsync/fdatasync discipline that every later layer depends on without re-deriving it.

13.2 Detailed Implementation Steps

  1. Implement Pager::open/read_page/write_page/write_pages/allocate_page/fsync/fdatasync (§11, trait in §11.6-adjacent form) using pread64/pwrite64 at explicit offsets (ADR-13) — never seek+read/write.
  2. Batch writes: write_pages coalesces adjacent page numbers into one pwritev2 when the allocator hands out contiguous pgnos (§13.5).
  3. Allocation: pop the freelist head if non-empty, else extend the file by one page via fallocate(FALLOC_FL_KEEP_SIZE|FALLOC_FL_ZERO_RANGE) (Linux) / F_PREALLOCATE+ftruncate (macOS) / zero-pwrite (Windows fallback).
  4. fsync discipline (ADR-14, P5): fdatasync for in-segment WAL appends; fsync on segment rotation or data-file growth.
  5. O_DIRECT (ADR-15): opt-in via PagerOptions::direct_io; asserts page-aligned buffers; a filesystem that rejects O_DIRECT is a hard open error (P7), never a silent fallback.
  6. mmap read-only fallback (PagerOptions::mmap_readonly), mutually exclusive with direct_io — document the choice is per-open, asserted at construction (§13.6 pitfall).

13.3 Deliverable

A Pager openable/readable/writable/fsync-able/closable in tests; a cargo bench baseline for read/write throughput at 4/8/16 KiB with and without O_DIRECT.

13.4 Acceptance Criteria

  • 10,000-iteration smoke test: allocate, write known pattern, read back, assert byte-equality — 100% pass, zero flakes across 10 runs.
  • Read/write throughput baseline recorded in benchmarks/results/<host>/pager.json.
  • A short pwrite (simulated via fault injection) surfaces Error::Io with offset+length in the message — never a silent partial commit (P7).

13.5 Conformance Fixtures

Fixture Purpose Expected Output

corpora/wal/short-write.bin fault-injected EAGAIN mid-write Error::Io at the boundary, no partial commit

13.6 Pitfalls

  • fsync returning success does not prove the underlying device is durable (§22 T4; Rebello et al. 2020) — document this boundary in docs/threat-model.md rather than trusting the kernel's word implicitly.
  • fdatasync does not flush metadata; after extending the file, always fsync, or a power cut can lose the extension itself.
  • Mixing mmap and pwrite on the same file is undefined behavior under Linux page-cache pressure — pick one per open and assert the choice (I11-adjacent structural guarantee).

13.7 Performance Concerns

Batched pwritev2 amortizes syscall overhead for contiguous allocator output; O_DIRECT trades kernel double-buffering for alignment complexity — measure both before choosing a default per deployment (§28).

13.8 Edge Cases

Short read at end-of-file (UnexpectedEof) vs. short read mid-file (fatal, refuse further writes until reopened) must be distinguishable in the returned Error; a file that grew between open and a later allocate_page call (external truncation) must be detected, not silently overwritten.

13.9 Failure Analysis

A pager-level bug (e.g. wrong offset math) corrupts every layer above it silently until a CRC check (I2) surfaces it — far downstream of the actual bug. Containment: the 10K-iteration smoke test plus fuzz_targets (introduced in §14) catch offset arithmetic errors before they reach production.

13.10 Operational Notes

Expose btree_pages_written_total and a pager_fsync_latency_seconds histogram from Phase 1 onward (wired fully into Telemetry in §19.3) so the runbook (§24) has pager-level signal independent of the buffer pool and WAL layers built on top.

14. Phase 2 — Page Codec

14.1 Objectives

Implement the slotted-page transform (§8.1, ADR-03) between raw bytes and (header, slots, cells) — the type the rest of the engine traffics in, with zero disk I/O in this layer (P2).

14.2 Detailed Implementation Steps

  1. PageRef/PageMut (§11.3) expose header(), n_cells(), slot(idx), cell(idx), search(key), checksum(), verify_checksum() (I2, P13) and insert_cell/delete_cell/ defragment/finalise respectively.
  2. Search: binary search over the sorted slot array; the comparator dereferences the cell, reads the key length, compares — with per-page prefix compression (ADR-17) in effect, the comparator tests the shared prefix first and falls through to the suffix only on a match.
  3. Insert: check pagesize/4 inline threshold (ADR-19, I13); if the cell fits, check free_size, defragment-and-recheck if not, append the cell from the page end backward, insert a sorted slot, update n_cells/free_off/free_size.
  4. Delete: remove the slot (shift subsequent slots), mark cell bytes reclaimable, decrement n_cells, increment free_size by the reclaimed extent.
  5. Defragment: walk the slot array in cell order, copy live cells to a scratch buffer, copy back as one contiguous block — the only op touching the whole page, amortized across N inserts.
  6. Checksum: CRC32C (ADR-06, Castagnoli et al. 1993) over bytes[0..pagesize-4], recomputed in finalise, verified in verify_checksum — never computed over stale trailing bytes.

14.3 Deliverable

A PageRef/PageMut pair that round-trips a 1,000-cell page in tests; a proptest harness generating random insert/delete sequences asserting the slot array stays sorted and cells stay inside the cell area.

14.4 Acceptance Criteria

  • Property test: 10,000 random insert/delete sequences, zero invariant violations (slot sort order, cell/slot non-overlap).
  • Microbenchmark: binary search < 200 ns at 200 cells/page on the reference host (§4).
  • leaf-100-cells.bin fixture: n_cells == 100 and search(k) == Found(idx) for all 100 keys.

14.5 Conformance Fixtures

Fixture Purpose Expected Output

corpora/pages/leaf-bad-slot.bin slot offset past pagesize Error::PageCorrupt (I2, P13, §8.6)

14.6 Pitfalls

  • Slot array and cell area grow toward each other; the moment they meet, a split is required — there is no "just allocate more" inside one page.
  • CRC must be the last field written and read — computing it over the page's own stale trailing CRC bytes (not zeroed first) is a subtle, easy-to-reintroduce bug.
  • Host endianness must never leak into the codec (P14); use to_le_bytes/from_le_bytes everywhere.

14.7 Performance Concerns

Binary search dominates read-path CPU; defragment is O(page) but amortized — measure its frequency under a realistic churn workload (§28), not just its per-call cost.

14.8 Edge Cases

A leaf with exactly one cell; the last cell in a leaf where cell area size == free_size + 1; a split that produces a single-cell sibling — property-based tests (§14.3) are required because hand-written fixtures alone miss this long tail (§27).

14.9 Failure Analysis

A codec bug (e.g. an off-by-one in free_off) manifests as PageCorrupt on the next read, not the write that caused it — the fuzz targets (fuzz_targets/page_codec.rs, §26) are the primary detection path since production telemetry alone cannot localize the write.

14.10 Operational Notes

btreectl dump --format jsonl decodes and prints every cell on a page for operator inspection; this is the tool the corruption runbook (§24) reaches for first.

15. Phase 3 — Single-Threaded B+Tree

15.1 Objectives

Land the minimum viable tree — search, insert-without-split, overflow values, range read — atop the pager and page codec directly, no buffer pool or WAL yet (Bayer & McCreight 1972; Comer 1979).

15.2 Detailed Implementation Steps

  1. Tree structure: internal nodes (InternalBPlus) hold (separator, child_pgno) cells; leaves (LeafBPlus) hold (key, value) cells plus header.next_sibling (§8.1, I7).
  2. Meta page: root_pgno, freelist_pgno, n_pages, last_committed_lsn, txn_id — double buffered A/B (I10, §21.2; Chu 2011).
  3. Search (point lookup): descend from root_pgno; at each internal node, binary search for the largest separator ≤ key, follow the child; at the leaf, binary search for the key; resolve overflow chains if present (ADR-19).
  4. Insert without split: descend to the leaf, insert at the sorted position if free_size suffices; otherwise defer to Phase 4's split (§16).
  5. Overflow values: cells whose payload exceeds max_inline_payload (I13, ADR-19) store (key, first_overflow_pgno, total_len); overflow pages chain via next_overflow_pgno.
  6. Range read: descend to the leaf containing the start key, walk next_sibling until past the end key (I7) — the reason a B+tree wins scan-heavy workloads (Comer 1979).

15.3 Deliverable

A tree supporting insert/point-lookup/range-scan; 10,000 random insertions followed by 10,000 random lookups checked against a std::BTreeMap oracle; a 1 GB sequential-key bulk insert measured against a baseline.

15.4 Acceptance Criteria

  • 10K/10K insert-then-lookup: 100% match against the BTreeMap oracle, zero mismatches.
  • 1 GB sequential insert throughput recorded in benchmarks/results/<host>/insert.json.
  • range(100..200) over keys 0..1000 returns exactly 100 entries, in order.

15.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/ops/insert-then-get.jsonl 1,000 inserts + 1,000 gets every read matches the recorded value
corpora/ops/range-scan.jsonl ordered keys 0..1000 range(100..200) returns exactly 100, in order

15.6 Pitfalls

  • The rightmost-child-pointer encoding in internal nodes is a frequent source of off-by-one bugs; pick one convention (last-cell-with-empty-key or header-rightmost) and document it in docs/architecture/page-format.md.
  • Overflow chains must be freed on delete/replace, or the freelist silently leaks (I8) — a debug-build assertion (freelist count + live overflow count conserved) catches this.
  • next_sibling must be updated on every leaf split (I7) — missing it makes a range scan skip entire pages silently.

15.7 Performance Concerns

Point-lookup cost is dominated by tree height × (page fetch + binary search); at this phase every fetch is a syscall (no buffer pool yet) — expect Phase 3's raw numbers to be far below M1 until Phase 5 lands.

15.8 Edge Cases

Empty tree lookup; lookup for a key exactly equal to a separator (must follow the right child per the ≤ convention, §15.2 step 3); a value exactly at the max_inline_payload boundary (inline vs. overflow decision, ADR-19).

15.9 Failure Analysis

A wrong descent decision (off-by-one in the ≤/< comparison) silently returns the wrong value rather than erroring — this is why the BTreeMap oracle differential test (§15.3) is mandatory, not optional; a unit test with a handful of fixed keys would not have caught it.

15.10 Operational Notes

btreectl fsck (introduced fully in §21) begins here as a tree-walk that asserts every leaf is reachable from the root and every next_sibling chain terminates — useful even before the buffer pool and WAL exist.

16. Phase 4 — Splits and Merges

16.1 Objectives

Add the structural mutations that keep the tree balanced under insert/delete churn (Graefe 2011 §5–6; Comer 1979), building on Phase 3's descend logic.

16.2 Detailed Implementation Steps

  1. Leaf split (triggered when insert finds free_size insufficient post-defragment, §14.2): allocate leaf R; copy the upper half of the source's cells into R; truncate the source to the lower half; R.next_sibling = source.next_sibling, source.next_sibling = R.pgno (I7); separator = R.cell(0).key; insert (separator, R.pgno) into the parent, recursing on parent-full (§8.5 worked example).
  2. Root split: allocate a new root with two children; update the meta page's root_pgno (I10).
  3. Internal split: identical to leaf split minus sibling pointers; separator may be suffix-truncated (ADR-18).
  4. Delete + rebalance: delete from the leaf; if below half-full and a sibling can lend a cell, borrow (rotate through the parent separator); if both siblings are also at threshold, merge with the right sibling (chosen consistently for a smaller code path), freeing the sibling page and dropping the parent separator.
  5. Freelist accounting (I8): every allocate/free recorded in the FreeList-kind page chain; allocation pops the head, free pushes to the head; bulk-free during merge appends a contiguous range.
  6. Tree-height bound: for a 4 KiB page at the §32 fanout numbers, the descend stack is bounded (SmallVec<[StackFrame; 8]>, stack-allocated, no heap churn per descent).

16.3 Deliverable

An insert path surviving 10M random inserts without OOM, leak, or lost key (oracle-compared every 1M inserts); a delete path returning a 10M-key tree to empty with n_pages == n_freelist + 3 (I8) and zero orphan pages.

16.4 Acceptance Criteria

  • 10M-insert soak: zero oracle mismatches at each 1M-insert checkpoint.
  • 10M-insert-then-delete-to-empty: n_pages == n_freelist_pages + 3 exactly (I8).
  • Property test: 10,000-op random (insert, get, delete, range) sequences match BTreeMap exactly.

16.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/ops/split-cascade.jsonl keys engineered to cascade splits to 5 levels post-state height == 5
corpora/ops/merge-cascade.jsonl the inverse of split-cascade post-state height == 1
corpora/ops/freelist-balance.jsonl insert/delete workload freelist page count matches recorded expectation

16.6 Pitfalls

  • Parent rebalancing during a split is the easiest place to introduce a slot-array off-by-one; a debug assertion n_cells * sizeof(Slot) <= free_off catches most of them.
  • Borrow interacts with prefix compression (ADR-17): a borrowed cell can break the page's shared prefix; the page must recompute its prefix after any borrow (§19.4 shares this logic).
  • Freeing a page still pinned in the buffer pool (Phase 5, §17) is undefined behavior once the pool lands — the free path must check pin count and error (Error::WriteConflict), never silently free a pinned frame.

16.7 Performance Concerns

Split/merge cost is O(page) per structural mutation, amortized across the inserts/deletes that triggered it (Graefe 2011); the freelist push/pop is O(1) but contends with the CoW ridge-copy path once Phase 9 (§21) lands.

16.8 Edge Cases

A split that produces a single-cell sibling (minimum viable leaf); a merge where both siblings are simultaneously eligible (deterministic tie-break: always merge right, §16.2 step 4); a root that shrinks to a single leaf after a cascade of merges.

16.9 Failure Analysis

A merge bug that frees a page still referenced by a sibling pointer manifests as a dangling next_sibling — detected by fsck's sibling-chain walk (I7) but only on the next full scan, not immediately; this is why the 10M-insert-then-delete soak (§16.4) checks n_pages at every checkpoint rather than only at the end.

16.10 Operational Notes

Expose btree_tree_height as a gauge from this phase onward — a sudden height increase under a workload expected to stay shallow is an early signal of a fanout regression (e.g. a compression bug inflating cell size, cross-referenced with §19's prefix logic).

17. Phase 5 — Buffer Pool

17.1 Objectives

Introduce the buffer pool (P9, P12) as the sole path to disk from this phase onward — no component outside btree-bufpool calls the pager directly after this lands.

17.2 Detailed Implementation Steps

  1. Frame table: fixed array of Frame { pgno, payload: [u8; PAGE_SIZE] (aligned), pin: AtomicU32, dirty: AtomicBool, ref_bit: AtomicBool, lsn: AtomicU64 }, sized from DbOptions::buffer_pool_pages (default 16,384 frames = 64 MiB, §4).
  2. Hash index: page number → frame index (a concurrent map); pin/pin_mut consult it; on miss, the eviction path (below) picks a victim, evicts (write-back if dirty), reads the new page, installs, returns the frame.
  3. Pin/unpin: pin increments a per-frame counter; the returned BorrowedPage decrements on drop (RAII, I3); a frame with pin > 0 is never evicted.
  4. CLOCK eviction (ADR-07; Sacco & Schkolnick 1986): circular sweep — skip pinned frames; clear and skip a set ref_bit; evict an unset-ref_bit, unpinned frame; a fully pinned sweep returns Error::PoolExhausted (I3).
  5. Async flusher: background thread sweeping the dirty bitmap, flushing via the same Pager::write_pages batch path (§13.2) — never bypassing the pager (P12). Policy configurable: OnEviction (default), Periodic, OnCheckpoint.
  6. Dirty bitmap: one bit per frame, set on a mutating pin_mut drop, cleared after a successful flush — also the source for "what was dirty at the last checkpoint" (§18.8).

17.3 Deliverable

A BufPool surviving a 1M-pin randomized workload without leaking pins or losing dirty bits; a microbenchmark of pin/unpin overhead; an eviction-pressure test (pool 16 frames, working set 1024, sequential scan).

17.4 Acceptance Criteria

  • 1M-pin stress test: zero leaked pins, zero lost dirty bits, across 10 repeated runs.
  • Pin/unpin overhead < 50 ns on a hot frame (microbenchmark, reference host).
  • Flush-on-drop test: pin_mut, mutate, drop, restart, mutation persisted — 100% of 1,000 trials.
  • Buffer-pool hit rate ≥ 95% on the declared hot working set at default pool size (M13, §32 C4).

17.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/wal/buf-evict-dirty.bin recorded (pin, mut, evict) sequence on-disk state matches after each evict
corpora/wal/buf-pool-exhausted.bin pins > pool size Error::PoolExhausted

17.6 Pitfalls

  • The hash-map eviction race: between picking a victim and checking its pin count, another thread can pin it — the protocol picks the victim and checks the pin count under the same bucket lock (btree-bufpool/src/clock.rs).
  • A dirty page that is also referenced by a committed WAL record must flush in LSN order (I4); the flusher consults Wal::last_durable_lsn and refuses to write a page whose lsn exceeds it — violating this loses crash safety silently.
  • BorrowedPage<'pool>'s lifetime is tied to the pool guard; do not use unsafe to extend it past the frame's true lifetime — the borrow checker's enforcement here is load-bearing (I11).

17.7 Performance Concerns

CLOCK's single sweep cursor keeps eviction O(1) amortized but can degrade to O(n) under a fully-pinned pool right before PoolExhausted; measure sweep length under contention, not just steady state (§28).

17.8 Edge Cases

A working set larger than the pool (constant eviction pressure); a scan that pins its entire range simultaneously (exhausting the pool by design, not by bug — distinguish this from a leak via the pin-count histogram); a flush racing a concurrent pin_mut on the same frame.

17.9 Failure Analysis

A pin leak (a bug that skips the Drop path, e.g. via mem::forget) exhausts the pool slowly — symptom is a rising btree_buffer_pool_size_pages with no corresponding workload growth; detection is the 1M-pin stress test in CI plus the PoolExhausted alarm in production (§24).

17.10 Operational Notes

btree_buffer_pool_dirty_pages and btree_buffer_pool_size_pages are the two gauges the slow-writes runbook (§24) checks first — a small pool relative to the working set starves it (low hit rate, M13), while a stuck-high dirty count means the flusher is behind.

18. Phase 6 — Write-Ahead Log and ARIES-Style Redo Recovery

18.1 Objectives

Build the durability primitive (P1, P5, I1, I5): WAL append, group commit, redo-only recovery (ADR-05; Mohan et al. 1992), and checkpointing — the longest single phase, and the one every other phase's crash-safety claim depends on.

18.2 Detailed Implementation Steps

  1. WAL file layout: fixed-size segments (wal/000001.log, ...), default 16 MiB (DbOptions::wal_segment_bytes); records never span segments (§8.2).
  2. Append path: WalAppender::append serializes into a 1 MiB in-memory buffer, returns the assigned Lsn; flush_through(lsn) writes the buffer and fsync/fdatasyncs (ADR-14).
  3. Group commit: the first caller to flush_through after a batch of concurrent appends pays one fsync for everyone; others wait on a condvar with a 10 ms timeout (§18.6 pitfall) and return after. Throughput is fsync-rate-bound (~300–1,500/s on the reference NVMe, §4).
  4. PageWrite vs. FullPage (I4): small deltas (< pagesize/4) log as PageWrite; the first write to a page after a checkpoint always logs FullPage — this is what makes a torn page recoverable without a double-write buffer (ADR-16).
  5. Recovery (redo replay, §8.4): pick the authoritative meta page (I10); scan forward from last_committed_lsn + 1; buffer records per txn_id; on Commit, apply all buffered records in LSN order (I14, applying iff header.lsn < record.lsn, P11); on Abort, discard.
  6. Checkpoint: flush every dirty page (§17.5), fsync the data file, append a Checkpoint record, fsync the WAL, update the meta page's last_lsn; reclaimed segments are unlink'd.

18.3 Deliverable

A WAL appender sustaining ≥100,000 records/s at 256 B payload; a recovery loop surviving kill -9 at every byte boundary in a 10,000-write workload; a 24-hour soak with continuous writes, periodic checkpoints, and periodic kills.

18.4 Acceptance Criteria

  • ≥100,000 append records/s at 256 B payload (reference host, §4).
  • Crash-injection at every byte boundary (M12): zero committed writes lost across 10,000 writes.
  • Recovery replay throughput ≥ 50,000 records/s (M7); 24-hour soak (M10): zero unhandled errors.
  • p99 commit latency ≤ 5 ms fsync-on-commit (M8).

18.5 Conformance Fixtures

Fixture Purpose Expected Output

corpora/wal/group-commit.bin 16 interleaved txns post-state matches the committed-only subset

corpora/crash/kill-mid-pagewrite.bin torn data-file pwrite FullPage replay restores the page

18.6 Pitfalls

  • Ordering trap: fsync(WAL); pwrite(data); fsync(data) is correct; reversing the WAL fsync to last breaks recovery (P5, I4) — this is the single bug class that loses committed data invisibly until the next crash (§27).
  • The CRC must cover the LSN (I12); a corrupt-but-plausible LSN read without CRC verification first can walk recovery off into an unbounded range.
  • "First write after checkpoint must be FullPage" is easy to forget; track a per-page last_logged_lsn and assert in debug builds that any PageWrite for a page has last_logged_lsn >= checkpoint_lsn.
  • Group commit's condvar wait must time out (10 ms) to avoid deadlock if the flush leader panics mid-fsync; document the retry policy in docs/architecture/wal-format.md (§18.5 fixture evidence: corpora/wal/group-commit.bin).

18.7 Performance Concerns

fsync rate is the hard ceiling on serial commit throughput (§32 C6); group-commit batch size is the lever — at M4's 1.5M inserts/s target, the required batch size is ≈225 commits/flush (§32 C6), which must be validated under the group-commit condvar design, not assumed.

18.8 Edge Cases

A truncated WAL tail past the last Commit (discard, succeed) vs. inside a replayed transaction (Error::WalTruncated, StrictRedo, §18.2 step 5); both meta pages carrying the same LSN (I10 tie-break); a crash exactly between the WAL fsync and the meta-page write (the transaction is durable via WAL replay even though the meta page hasn't advanced yet).

18.9 Failure Analysis

The disk "lying" about fsync durability (§22 T4; Rebello et al. 2020) is undetectable in-process — this is the one failure class the engine can only document, never recover from; every other failure in this phase (truncated tail, torn page, group-commit stall) has an explicit detection + recovery path (I1, I4, I10, I14).

18.10 Operational Notes

btree_wal_fsync_latency_seconds and btree_recovery_duration_seconds are the two histograms the slow-writes and recovery runbooks (§24) key off; a rising fsync p99 without a corresponding WAL segment-count increase points at the underlying device, not the engine.

19. Phase 7 — Range Scan, Prefix Compression, Suffix Truncation

19.1 Objectives

Wire the leaf-sibling walk (I7) into a production range-scan iterator and add per-page prefix compression (ADR-17) plus separator suffix truncation (ADR-18) — the two techniques that make a B+tree's page budget go 30–60% further on string-shaped keys (Comer 1979).

19.2 Detailed Implementation Steps

  1. RangeIter pins the current leaf (§11.3), yields its cells within bounds, then unpins and pins next_sibling (I7) — repeating until the end bound is passed.
  2. Prefix compression: each leaf carries prefix_len (header flags-adjacent field, max 255); all cells share that prefix, storing only the suffix; recompute on any insert changing the page's first-or-last key — O(n_cells × prefix_len), amortized (ADR-17).
  3. Suffix truncation: an internal separator only needs ≥ max(left subtree) and ≤ min(right subtree) — truncate to the shortest distinguishing prefix between left_max and right_min (ADR-18, §32 C1).
  4. Reverse scan: Phase-0 default walks a stack of internal-node positions (no prev_sibling field); a prev_sibling field is a deferred optimization (§35 row 8).
  5. Read-ahead prefetch: deferred (§35 row 7) — a worker-thread prefetcher issuing Pager::read_page calls for the next N siblings while the current leaf is consumed.

19.3 Deliverable

A range-scan iterator returning ordered results across leaf splits; a test inserting 1M sequentially-prefixed keys asserting ≥30% fewer pages than the uncompressed baseline; a microbenchmark of warm-cache scan throughput.

19.4 Acceptance Criteria

  • Range scan across 7 leaves returns the exact expected count, in order, 100% of trials.
  • Prefix compression: ≥30% page-count reduction on the user:000001..user:1000000 workload vs. the uncompressed baseline.
  • Warm-cache range-scan throughput ≥ 1 GiB/s on the reference host (M5).

19.5 Conformance Fixtures

Fixture Purpose Expected Output

19.6 Pitfalls

  • Prefix recomputation must fire on every insert that changes the first-or-last cell — a stale prefix silently produces wrong reads, not an error (P13's structural-vs-semantic distinction matters here: the CRC still passes on a page with a stale-but-well-formed prefix).
  • Suffix-truncated separators are not real keys — never compare them against user keys in the leaf-level search path (only the descend path uses them, §15.2).
  • Range scans can be invalidated by a concurrent split under multi-writer (deferred, §35 row 1); under single-writer (ADR-08), a reader's root_pgno is fixed at begin_read and sees a consistent tree by construction (§21.2).

19.7 Performance Concerns

Prefix recompute cost is amortized across the inserts that trigger it, but a workload with high first/last-key churn (e.g. random deletes at page boundaries) can make it non-amortized — measure recompute frequency under realistic churn, not just insert-only workloads (§28).

19.8 Edge Cases

A page with zero cells (empty leaf, prefix_len == 0); a key whose entire length is the shared prefix (empty suffix); a separator-truncation input where left_max and right_min share every byte up to the shorter string's length (truncate to the shorter string plus one byte, or the whole shorter string if it is itself the distinguishing bound).

19.9 Failure Analysis

A missed prefix recompute is a silent-wrong-read bug, not a crash — the differential oracle test (std::BTreeMap, §14.3/§16.4) is the only detection path; production telemetry cannot distinguish it from a legitimate empty range result, so this bug class must be caught in CI, not in the field.

19.10 Operational Notes

btreectl dump --format jsonl includes prefix_len per leaf so an operator can spot-check compression effectiveness against the expected 30–60% range without a full benchmark run.

20. Phase 8 — Latch Crabbing and Concurrent Reads

20.1 Objectives

Add per-page latches and the lock-coupling (latch-crabbing) descent protocol (ADR-09; Lehman & Yao 1981) that lets concurrent readers and the single writer (ADR-08) descend the tree without racing, bounding held latches to two at a time (P8, I6).

20.2 Detailed Implementation Steps

  1. Per-frame latch: each Frame carries a parking_lot::RwLock<()> (ADR-12); readers acquire read(), the writer acquires write(); held for one page operation, not a whole transaction — transactions hold zero latches between operations (P8).
  2. Read descent: acquire parent.read(); loop — follow the separator to child, acquire child.read(), release parent, parent = child; stop at a leaf. At most two latches held at any point (I6).
  3. Write descent: same shape with write latches, except the parent's release is conditional on the child being "safe" — a leaf with free_size > cell_len or an internal with n_cells < max - 1 is safe; an unsafe child keeps the parent held so a split/merge can propagate upward under the held latches (§16.1).
  4. Latch-hierarchy assertion: every latch carries a level (root=0, leaf=max); a debug-build per-thread stack asserts levels are monotonically non-decreasing (I6) — an out-of-order acquisition panics rather than silently deadlocking.
  5. B-link optimistic descent (Lehman & Yao 1981) — deferred (§35 row 2): read-latch-only descent with a high-key check per node, following the right-link on a mismatch; requires a right-sibling pointer on internal nodes too, not just leaves.
  6. Optimistic concurrency control (OCC) — deferred (§35 row 12): version-stamped optimistic reads with commit-time validation, documented as a per-workload alternative to crabbing in docs/architecture/concurrency.md.

20.3 Deliverable

32 reader threads + 1 writer thread sustaining a 50/50 read/write workload; a 1M-iteration random-workload test with the latch-hierarchy assertion enabled; a read-scaling microbenchmark to 32 threads.

20.4 Acceptance Criteria

  • 32 readers + 1 writer sustain ≥ 50,000 ops/s on the reference host (M2-adjacent workload variant; pure-read M2 target is ≥ 80,000,000 lookups/s at 16 readers).
  • 1M-iteration randomized concurrency test with the latch-stack assertion enabled: zero panics.
  • Read-only throughput scales near-linearly to 32 threads on a 32-core reference host.

20.6 Pitfalls

  • The brief window between releasing the parent and acquiring the child (in the "release before acquire" trick) means the parent can be split in that window; the safety theorem holds because a split moves cells, never deletes the page — but the child pgno must be re-resolved every iteration, never cached across the gap.
  • parking_lot::RwLock's reader fairness can starve a writer under heavy read load; switch to writer-priority once the writer queue depth passes a documented threshold (docs/architecture/concurrency.md).
  • A per-frame latch guard must not outlive the frame's lifetime — BorrowedPage carries the guard; never let it escape via unsafe lifetime extension (I11 restated at the concurrency layer).

20.7 Performance Concerns

Latch hold time must exclude any syscall (P8) — the descend protocol releases latches before any I/O; a latch held across a page fault (cold buffer-pool miss) would serialize every other descender behind a millisecond-scale disk read.

20.8 Edge Cases

A reader descending through a node the writer is mid-split on (must see either the pre-split or post-split state consistently, never a torn mix, I11); a writer's safe-child chain that reaches the leaf with the root still held (full-height propagation, rare but must not deadlock); a reader starved indefinitely under sustained write pressure (writer-priority threshold, §20.6).

20.9 Failure Analysis

A latch-order violation (I6) is caught by the debug-build assertion as a panic with a full stack trace — converting what would otherwise be an unreproducible production hang into a diagnosable crash; in release builds without the assertion, the same bug manifests as an intermittent deadlock requiring docs/runbook/triage.md's thread-dump procedure (§24).

20.10 Operational Notes

A thread-dump-on-SIGQUIT handler (documented in the triage runbook, §24) is the primary production diagnostic for a suspected latch-order issue, since the debug-only assertion is not compiled into release builds by default.

21. Phase 9 — Copy-on-Write Snapshots, Checkpointing, Bulk Load, Vacuum

21.1 Objectives

Turn the engine into a real snapshot-isolation system (ADR-10, P4): a ReadTxn sees the tree as of begin_read; the writer publishes a new tree on commit; add the bulk-load fast path (ADR-20) and delayed-reclaim vacuum (I9) that make the snapshot model operable at scale.

21.2 Detailed Implementation Steps

  1. CoW semantics: a WriteTxn never modifies a page in place — it copies the page to a new pgno, modifies the copy, and copies every page on the path from the modified leaf to the root (the "ridge," §16.9 restated). Commit is one atomic step: write the new meta page (new root_pgno), fsync.
  2. Root publication: two double-buffered meta pages (I10; Chu 2011); the writer writes the WAL Commit record, fsyncs the WAL, then writes whichever meta page has the older LSN, fsyncs. Open picks the newer-and-CRC-valid meta page.
  3. Snapshot lifecycle: Snapshot { root_pgno, read_version } is a long-lived handle (cost: one u64 + a refcount entry); ReadTxn is an ephemeral handle into either a live snapshot or the current tree.
  4. Vacuum (I9): pages freed by a CoW commit are tagged "free at version V," not immediately reclaimed; vacuum walks these tags and moves a page to the active freelist once no live snapshot's read_version is ≤ V.
  5. Bulk load (ADR-20): consumes sorted (key, value) pairs, builds leaves bottom-up until full, writes them, then builds internal layers one at a time from the accumulated separators, emitting the root last; the whole operation commits as one transaction with a single WAL append.
  6. Checkpoint (§18.2 step 6, restated at the CoW layer): flushes dirty pages, fsyncs the data file, advances the meta last_lsn — purely a performance optimization on top of the CoW commit's own durability, not a durability primitive itself (I5).

21.3 Deliverable

A long-running reader holding a snapshot through 1M concurrent writer inserts with an unchanged view; a snapshot-export diff test; a vacuum test reclaiming a 100K-cell all-deleted database to near-empty; a 100M-sorted-entry bulk load completing in ≤ 5 minutes.

21.4 Acceptance Criteria

  • 1-hour held snapshot across 1M writer inserts: reader's view unchanged at the end, verified byte-for-byte against the begin_read-time dump.
  • Vacuum test: freelist count returns to within 1% of the pre-insert baseline after all keys are deleted and the last snapshot referencing them is dropped.
  • Bulk load: 100M sorted entries in ≤ 5 minutes on the reference host (M6-derived); resulting tree structurally identical (height, fanout/level, page count) to the incremental-insert build.

21.6 Pitfalls

  • A CoW write that copies a page must copy every page on the ridge to the root — missing one leaves a stale parent pointing at a modified leaf, which a concurrent reader can follow into a half-modified state (I11 violated at the tree level).
  • The freelist is itself a tree of pages; freelist updates are CoW too — freeing a freelist page immediately during commit (instead of tagging "free at version V") can recycle it while a snapshot still depends on it (I9 violated).
  • Both meta pages sharing the same LSN (a double power-cut between two consecutive commits, I10 tie case): pick the CRC-valid one; if both verify, pick the higher txn_id; if tied, pick A by convention — document this exact tie-break, do not leave it implicit.
  • Bulk load is one transaction; a crash mid-load loses the entire load — a chunked variant that commits every N entries is deferred (§35 row 13); document the all-or-nothing contract clearly until it ships.

21.7 Performance Concerns

CoW's ridge-copy cost scales with tree height (§32 C3), not dataset size — a deep tree pays more per commit; bulk load's 5–10× speedup over per-key insert comes from skipping the ridge-copy and descend-and-split loop entirely (ADR-20).

21.8 Edge Cases

A snapshot held indefinitely (operational trap, not a bug, cross-referenced at §23 FM6); a vacuum run concurrent with new CoW commits (must not reclaim a page a not-yet-durable commit is about to reference); bulk-load input that is not actually sorted (debug-build assertion k[i] >= k[i-1], release build documents the contract as caller-enforced).

21.9 Failure Analysis

A vacuum bug that reclaims too early corrupts a live snapshot's view invisibly until that snapshot's next read hits a freed-and-reused page — detected as Error::PageCorrupt or, worse, a wrong-but-plausible read if the freed page was reused for structurally similar content; this is why I9's conformance fixture (snapshot-vacuum.jsonl) is a required gate, not optional.

21.10 Operational Notes

btree_snapshot_count is the operational canary for FM6 (§23) — a value that never returns to baseline indicates a leaked Snapshot handle, diagnosable via btreectl's snapshot-registry dump before it grows into an unbounded file-size incident.

25. Compatibility & Versioning

Wire/storage compatibility: format_version in the file header (§8.1, P14) gates on-disk layout changes; an unrecognized format_version is a hard open error, never a best-effort parse. Schema evolution: page-size and WAL-record-kind changes are additive within a major format_version; a breaking layout change bumps format_version and ships a documented migration path (btreectl migrate, out of Phase-0 scope, tracked alongside §35 row 6).

API stability: DbOptions fields are additive-only across minor versions (P10); Error variants are additive, requiring callers to match with a wildcard arm for forward compatibility. SemVer policy: the crate follows SemVer; a MAJOR bump accompanies any format_version bump or a breaking Db/ReadTxn/WriteTxn signature change. Deprecation policy: a deprecated API surface carries a #[deprecated] attribute with the removal-target MAJOR version, held for at least one MAJOR release before removal.

Rolling-upgrade guarantees: because concurrency is single-writer (ADR-08), there is no multi-node rolling-upgrade concern within one Db; an application-level fleet upgrading the engine binary should validate the new binary against a copy of the data file (canary, §24) before pointing the writer at it, since redo-only WAL replay is forward-compatible within a format_version but not guaranteed across one.

29. Scalability Analysis

Constant regardless of dataset size: point-lookup latency's shape (O(log n) descend + O(1) leaf search); latch count held at any instant (≤ 2, I6); per-transaction dirty-page budget (P9). Grows with dataset size (Big-O): tree height — O(log_fanout n) (§32 C3); buffer-pool miss rate as the working set exceeds pool capacity (§32 C4); recovery time as a function of WAL backlog since the last checkpoint, bounded by checkpoint cadence, not dataset size directly (§32 C10).

Named bottlenecks, in order: (1) WAL fsync rate — the hard ceiling on serial commit throughput absent group commit (§32 C6); (2) buffer-pool hit rate once the working set exceeds 64 MiB (default) — every miss costs a syscall-bound page fetch; (3) single-writer serialization (ADR-08) — all writes funnel through one thread's WAL-append path; (4) CoW ridge-copy cost, proportional to tree height, on every commit (§21.7).

Horizontal/vertical scaling: this engine scales vertically only — one process, one host, one writer. Horizontal scale-out (sharding by key range across multiple Db instances) is an application-layer concern, not an engine feature; the engine provides no cross-shard coordination. Sharding/partitioning: an embedding application partitions its keyspace across N Db::open instances and routes writes by key range; this engine's snapshot API (§21.3) composes cleanly with per-shard backup but does not provide a cross-shard consistent snapshot. Coordination overhead: zero within one Db (single-writer, ADR-08 eliminates write-write coordination entirely) — the tradeoff for zero coordination overhead is the single-writer throughput ceiling itself (bottleneck 3, above).

Practical ceiling and levers beyond it: the practical ceiling is the single-writer WAL-append rate (bottleneck 1/3) — roughly M4's 1.5M inserts/s at group-commit optimum (§32 C6). Levers beyond that ceiling: (a) multi-writer transactions via B-link descent + MVCC (§35 rows 1, 2, 4) — removes bottleneck 3 at the cost of write-write conflict handling; (b) the Bw-tree variant (§34 AA2) — removes latch contention at extreme core counts; (c) application-level sharding (above) — removes the ceiling entirely at the cost of cross-shard consistency.

30. Mental Models & First Principles

  1. MM1 — A B+tree is a sorted array that pays O(log n) to stay sorted under mutation. Predicts: fanout, not height, dominates capacity planning (§32 C1–C3). Bug class without it: engineers tune page size for "more levels of caching" instead of fanout, missing that a 4-level tree over 10M keys is already near-optimal (§16, §32).
  2. MM2 — The WAL is the source of truth; the data file is a cache of it. Predicts: the data file can be arbitrarily stale and recovery still works (I5). Bug class without it: writing data-file bytes before the WAL record is durable (§18.6) — the single invisible-data-loss bug.
  3. MM3 — A latch protects bytes in memory; a lock protects a logical entity across a transaction. Predicts: latches must never be held across a syscall (§20.7). Bug class without it: holding a page latch across a disk read, serializing every other descender behind a millisecond-scale I/O (§20).
  4. MM4 — Copy-on-write turns concurrency control into a garbage-collection problem. Predicts: snapshot isolation needs a reclaim policy (vacuum, I9), not a locking policy (§21). Bug class without it: reclaiming a page a live snapshot still needs (FM6, T9).
  5. MM5 — Every checksum is a bet about where corruption enters the system. Predicts: a per-page CRC catches disk-level corruption but not a logic bug that produces a well-formed wrong page (P13). Bug class without it: trusting a CRC pass as proof of correctness instead of proof of "unchanged since written" (§14, FM10).
  6. MM6 — Buffer-pool eviction is scheduling, not memory management. Predicts: eviction policy choice (CLOCK vs. LRU-K, ADR-07) is a throughput/fairness tradeoff, not a memory-safety one (memory safety comes from the pin discipline, I3). Bug class without it: conflating "which page to evict" with "is it safe to evict" — the latter is always I3, regardless of policy (§17).
  7. MM7 — Fanout is an amortization; height is a logarithm. Predicts: doubling dataset size changes tree height by roughly one level, not proportionally (§32 C3). Bug class without it: assuming a 10× larger dataset needs a 10× larger buffer pool to maintain the same hit rate — in fact only the leaf count grows linearly; internal levels barely move.
  8. MM8 — Group commit turns a per-transaction fsync cost into an amortized one. Predicts: commit throughput at high concurrency is bound by fsync rate ÷ batch size, not by transaction count (§32 C6). Bug class without it: fsync-ing on every single commit at high write concurrency, capping throughput at the raw fsync rate (~300–1,500/s, §4) instead of M4's 1.5M/s.

32. Back-of-Envelope Capacity Model

Workload assumption (stated explicitly, chained from §4): 50 B average key, 200 B average value (inline, below the 1,024 B overflow threshold), 10,000,000-key dataset, 4,096 B pages, 24 B page-header+trailer overhead, 4 B slot entry.

  • C1 — Internal fanout. Separator (suffix-truncated, ADR-18) ≈ 12 B + child pgno 8 B + slot 4 B = 24 B/cell → (4096 − 24) / 24 ≈ 169 children per internal page.
  • C2 — Leaf fanout. Key (page-prefix-compressed, ADR-17, avg suffix 8 B) + value 200 B + slot 4 B ≈ 212 B/cell → (4096 − 24) / 212 ≈ 19 cells per leaf.
  • C3 — Tree height for 10M keys. Leaves needed = 10,000,000 / 19 ≈ 526,316. Levels above the leaf = ceil(log₁₆₉(526,316)) ≈ 3 (169² = 28,561; 169³ ≈ 4.8M ≥ 526,316, so 3 internal levels suffice) → total height ≈ 4 (root + 2 internal + leaf).
  • C4 — Buffer-pool coverage. Default pool: 16,384 frames. If all frames hold leaves: 16,384 × 19 ≈ 311,296 resident keys ≈ 3.1% of the 10M-key dataset — this is the "hot subset" M13's 95%-hit-rate target is measured against, not the full dataset.
  • C5 — WAL bandwidth at M4. 1,500,000 inserts/s × (~40 B PageWrite delta + 24 B record header) ≈ 96 MB/s sustained append — well under the reference NVMe's ~2,000 MB/s sequential write, confirming the WAL is not the bandwidth bottleneck at this rate (bottleneck 1 in §29 is the fsync rate, not bandwidth).
  • C6 — fsync-bound commit ceiling and required group-commit batch. Serial ceiling without batching: 1 / 150 µs ≈ 6,667 commits/s. To hit M4's 1,500,000/s: required batch size ≈ 1,500,000 × 150 µs / 1s ≈ 225 commits per flush — validates the group-commit design (§18.3, M14's ≥200 target).
  • C7 — Per-transaction dirty-page ceiling. Dirty budget 64 MiB / 4,096 B page = 16,384 dirty pages before a forced flush (P9).
  • C8 — FD budget. At C5's ~96 MB/s WAL rate and a 5 s checkpoint interval, live WAL ≈ 96 MB/s × 5s ≈ 480 MB ≈ 30 segments (16 MiB each) + 1 data file + 1 lockfile ≈ 32 FDs (§4).
  • C9 — Resident dataset size. 10,000,000 × 212 B (leaf cell) ≈ 2.12 GB of leaf data + negligible internal overhead (≈ 10,000,000/169 ≈ 59,172 internal cells × 24 B ≈ 1.4 MB) → ≈ 2.1 GB total, confirming C4's ~3% pool-to-dataset ratio.
  • C10 — Worst-case recovery RTO. Worst-case WAL backlog at C8's 480 MB / (~64 B/record) ≈ 7.5M records; at M7's 50,000 records/s replay floor: 7,500,000 / 50,000 = 150 s worst-case RTO — the number the §4 RTO row and the recovery runbook (§24) are built against.

34. Alternative Architectures (Roads Not Taken)

AA1 — LSM-Tree (RocksDB/LevelDB-shaped).

Show the original text diagram
writes → memtable (sorted, in-RAM) → immutable memtable → SSTable flush
                                                              │
                                          L0 (unsorted SSTs) → compaction → L1..Ln
                                          reads: memtable → L0..Ln, bloom-filter-gated

Regime where it wins: write-dominated, append-heavy ingestion tolerating read/scan amplification and periodic compaction stalls (Kleppmann 2017 ch. 3; Lu et al. 2016). Real system: RocksDB. Rejected here because point-lookup (M1) and p99 read latency (M9) targets assume a bounded number of page fetches per read (tree height, §32 C3) — an LSM-tree's multi-level read amplification and compaction-induced latency spikes conflict with those targets (§33 Q15).

AA2 — Bw-Tree (lock-free mapping table + delta records).

Show the original text diagram
logical pgno → mapping table → [delta_N → delta_(N-1) → ... → base page]
reads: walk the delta chain; writes: CAS-prepend a new delta; consolidate past a length threshold

Regime where it wins: extreme core-count contention where even brief latch holds (ADR-09) dominate throughput (Levandoski, Lomet, Sengupta 2013). Rejected as the Phase-0 default: the CAS-based delta-chain protocol is substantially harder to make correct and to debug than latch crabbing, and the target workload (single-writer, ADR-08) does not need lock-freedom at all — documented as a stretch path (§35 row 3), not discarded.

AA3 — Fractal/Streaming Tree (TokuDB-shaped).

each internal node carries a message buffer; writes are appended as messages and pushed
down lazily on a full-buffer flush, amortizing the cost of a logical insert across many
buffered messages instead of one immediate leaf mutation

Regime where it wins: write-heavy, sequential-or-random insert-dominated workloads where write amplification must stay near-optimal even at very large fanout (TokuFT/TokuDB). Rejected here because message-buffer flush ordering adds a second recovery dimension (buffered-but-unflushed messages) on top of the WAL (§18) that this engine's redo-only model does not need — the target workload (§4) is read-and-write balanced, not write-amplification-critical.

AA4 — In-Memory with Periodic Snapshot (Redis RDB/AOF-shaped).

Show the original text diagram
all data resident in RAM (hash table or skiplist) → periodic full-image snapshot (RDB) or
append-only command log (AOF) replayed on restart

Regime where it wins: datasets that fit entirely in RAM with relaxed durability requirements (losing the last few seconds of writes is acceptable). Rejected here because the target regime (§4: 10M keys, unbounded value growth via overflow chains, ADR-19) explicitly assumes a dataset larger than RAM is the common case — the buffer pool (§17) exists precisely because "everything fits in memory" is not a safe assumption for this engine's users.

36. Glossary

ARIES — Algorithm for Recovery and Isolation Exploiting Semantics (Mohan et al. 1992); the canonical WAL-based recovery model this engine implements a redo-only subset of. B+tree — a B-tree variant storing all data in leaves, linked by sibling pointers. B-link tree — a B+tree variant adding a high-key and right-sibling pointer to every node for lock-free-ish concurrent descent (Lehman & Yao 1981). Buffer pool — the fixed-size in-memory page cache between the tree and the pager. Bulk load — the sorted-input, bottom-up tree-construction fast path (ADR-20). Bw-tree — a lock-free B-tree variant using a mapping table and delta records (Levandoski et al. 2013). Cell — the variable-length key(+value or +child-pgno) payload referenced by a slot. Checkpoint — the operation that flushes dirty pages and advances the WAL's reclaimable boundary. CLOCK — the one-reference-bit approximate-LRU eviction algorithm. Copy-on-write (CoW) — never mutating a page in place; copying it and its ancestors instead. CRC32C — the Castagnoli CRC-32 variant used for page/WAL checksums. Dirty bit/bitmap — per-frame flag marking a page mutated since its last flush. Double-write buffer — an InnoDB-style fixed staging region providing torn-write protection (deferred here). Fanout — the number of children/cells a page holds. fdatasync — a fsync variant skipping the inode metadata fence. File header — page 0; magic, format version, page size. Freelist — the linked list of reclaimable page numbers. fsync — the syscall fencing a file's writes (and metadata) to durable storage. Frame — one buffer-pool slot holding one page's bytes plus bookkeeping. Group commit — batching multiple transactions' fsync calls into one. Latch — an in-memory mutual-exclusion primitive scoped to one page operation. Latch crabbing / lock coupling — holding at most two latches at a time while descending. LSN (Log Sequence Number) — a monotonic identifier for a WAL record's position. Meta page — the double-buffered page holding root_pgno, freelist_pgno, last_committed_lsn. MVCC — multi-version concurrency control via version chains (deferred here). Overflow page — a chained page holding a value too large to fit inline. Page — the fixed-size unit of disk I/O and buffer-pool caching. Pager — the sole file-I/O owner (pread/pwrite/fsync). Pin/unpin — the reference-counting discipline preventing eviction of an in-use frame. Prefix compression — storing a leaf's shared key prefix once, per page. RTO (Recovery Time Objective) — the maximum acceptable time to reopen and recover after a crash. Redo — reapplying a committed change during recovery. Separator key — the internal-node key bounding a child subtree, possibly suffix-truncated. Slot — a fixed-size array entry pointing at a cell's offset/length. Slotted page — the header+slot-array+cell-area layout. Snapshot — a long-lived handle pinning a tree version for repeated reads. Suffix truncation — shortening a separator to the minimum distinguishing prefix. Torn write — a page partially written before a crash, leaving an inconsistent byte image. Undo — reverting an uncommitted change during recovery (deferred here, ADR-05). Vacuum — the delayed-reclaim process freeing CoW pages no live snapshot needs. WAL (Write-Ahead Log) — the append-only durability log written before data-file changes are made durable. WAL segment — one fixed-size file in the WAL's rotating sequence. Write amplification — extra bytes written per logical byte of user data (CoW ridge-copy, WAL double-write). Write conflict — Error::WriteConflict, surfaced when a structural operation targets a still-pinned page.
