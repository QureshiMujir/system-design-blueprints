32. Back-of-Envelope Capacity Model

Workload assumption (stated explicitly, chained from §4): 50 B average key, 200 B average value (inline, below the 1,024 B overflow threshold), 10,000,000-key dataset, 4,096 B pages, 24 B page-header+trailer overhead, 4 B slot entry.

  • C1 — Internal fanout. Separator (suffix-truncated, ADR-18) ≈ 12 B + child pgno 8 B + slot 4 B = 24 B/cell → (4096 − 24) / 24 ≈ 169 children per internal page.
  • C2 — Leaf fanout. Key (page-prefix-compressed, ADR-17, avg suffix 8 B) + value 200 B + slot 4 B ≈ 212 B/cell → (4096 − 24) / 212 ≈ 19 cells per leaf.
  • C3 — Tree height for 10M keys. Leaves needed = 10,000,000 / 19 ≈ 526,316. Levels above the leaf = ceil(log₁₆₉(526,316)) ≈ 3 (169² = 28,561; 169³ ≈ 4.8M ≥ 526,316, so 3 internal levels suffice) → total height ≈ 4 (root + 2 internal + leaf).
  • C4 — Buffer-pool coverage. Default pool: 16,384 frames. If all frames hold leaves: 16,384 × 19 ≈ 311,296 resident keys ≈ 3.1% of the 10M-key dataset — this is the "hot subset" M13's 95%-hit-rate target is measured against, not the full dataset.
  • C5 — WAL bandwidth at M4. 1,500,000 inserts/s × (~40 B PageWrite delta + 24 B record header) ≈ 96 MB/s sustained append — well under the reference NVMe's ~2,000 MB/s sequential write, confirming the WAL is not the bandwidth bottleneck at this rate (bottleneck 1 in §29 is the fsync rate, not bandwidth).
  • C6 — fsync-bound commit ceiling and required group-commit batch. Serial ceiling without batching: 1 / 150 µs ≈ 6,667 commits/s. To hit M4's 1,500,000/s: required batch size ≈ 1,500,000 × 150 µs / 1s ≈ 225 commits per flush — validates the group-commit design (§18.3, M14's ≥200 target).
  • C7 — Per-transaction dirty-page ceiling. Dirty budget 64 MiB / 4,096 B page = 16,384 dirty pages before a forced flush (P9).
  • C8 — FD budget. At C5's ~96 MB/s WAL rate and a 5 s checkpoint interval, live WAL ≈ 96 MB/s × 5s ≈ 480 MB ≈ 30 segments (16 MiB each) + 1 data file + 1 lockfile ≈ 32 FDs (§4).
  • C9 — Resident dataset size. 10,000,000 × 212 B (leaf cell) ≈ 2.12 GB of leaf data + negligible internal overhead (≈ 10,000,000/169 ≈ 59,172 internal cells × 24 B ≈ 1.4 MB) → ≈ 2.1 GB total, confirming C4's ~3% pool-to-dataset ratio.
  • C10 — Worst-case recovery RTO. Worst-case WAL backlog at C8's 480 MB / (~64 B/record) ≈ 7.5M records; at M7's 50,000 records/s replay floor: 7,500,000 / 50,000 = 150 s worst-case RTO — the number the §4 RTO row and the recovery runbook (§24) are built against.
