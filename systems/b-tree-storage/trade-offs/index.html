Decisions (§9) · 26 ADRs

ADR-01

Core language

Chosen

Rust, stable, ed. 2021

Rejected

C/C++ (LMDB/SQLite/InnoDB precedent); Go (BoltDB precedent)

When the rejected choice is right

C wins extending an existing C DB kernel in place (zero-cost FFI dominates); Go wins when velocity + GC-tolerant latency outweigh p99 (BoltDB's actual niche)

Why: Auditable unsafe boundary (3 modules) + lifetime-checked buffer-pool borrows, no GC pause

ADR-02

Tree variant

Chosen

B+tree

Rejected

classic B-tree; B*-tree; LSM-tree

When the rejected choice is right

classic B-tree wins point-lookup-only fixed-record workloads with acute per-node space pressure; LSM-tree (RocksDB) wins write-dominated append-heavy ingestion (§34 AA1)

Why: leaf-only data + sibling links ⇒ O(result) range scan

ADR-03

Page layout

Chosen

Slotted (header+slots+cells)

Rejected

fixed-size arrays; packed prefix arrays w/o indirection

When the rejected choice is right

fixed arrays win when every key is compile-time fixed-width

Why: supports variable-length keys w/o full-page rewrite per insert

ADR-04

Default page size

Chosen

4 KiB (8/16 KiB configurable, format-locked)

Rejected

512 B; 64 KiB

When the rejected choice is right

16 KiB wins scan-heavy large-key workloads; 512 B wins only on genuine legacy 512 B sectors

Why: matches NVMe LBA / OS page size, minimizes RMW amplification

ADR-05

Recovery model

Chosen

WAL-redo only (Phase 0); ARIES undo deferred

Rejected

full ARIES (redo+undo+fine-grained locking) from Phase 0

When the rejected choice is right

full ARIES wins the instant multi-writer txns ship (§35 row 1)

Why: undo only needed once concurrent-writer rollback exists; single-writer makes redo sufficient (I1)

ADR-06

Structural checksum

Chosen

CRC32C (Castagnoli)

Rejected

CRC32 (non-C); Adler-32; xxHash

When the rejected choice is right

xxHash wins the non-structural dedup-keying path (ADR-24)

Why: hardware-accelerated x86-64/ARMv8, analyzed error-detection bound

ADR-07

Buffer-pool eviction

Chosen

CLOCK

Rejected

strict LRU; LFU; random

When the rejected choice is right

LRU-K wins strong recency-skew workloads CLOCK's 1 bit can't distinguish

Why: one ref-bit/frame, single sweep cursor, no per-touch mutation

ADR-08

Concurrency model

Chosen

single-writer, many-readers

Rejected

multi-writer 2PL; multi-writer OCC

When the rejected choice is right

multi-writer 2PL wins once single-writer WAL-append saturates before disk does (§35 row 1)

Why: avoids write-write conflict resolution; readers never block (P3/P4)

ADR-09

Descent protocol

Chosen

latch crabbing (lock coupling)

Rejected

pure optimistic descent; coarse global lock

When the rejected choice is right

B-link optimistic descent wins once multi-writer contention makes brief latch holds the bottleneck (§35 row 2)

Why: bounds held latches to 2 at a time (I6)

ADR-10

Read isolation

Chosen

copy-on-write snapshot (root-pgno swap)

Rejected

MVCC version chains from Phase 0; global RW lock

When the rejected choice is right

MVCC wins once concurrent writers must coexist with long-lived snapshots (§35 row 4)

Why: snapshot cost = one u64 + refcount, zero reader locking

ADR-11

License

Chosen

Apache-2.0 (engine); ELv2 reserved

Rejected

MIT; GPLv3; proprietary

When the rejected choice is right

ELv2 wins a future hosted control-plane wrapper preventing unattributed re-hosting

Why: matches LMDB/BoltDB/RocksDB norm + explicit patent grant

ADR-12

Latch primitive

Chosen

parking_lot::{Mutex,RwLock} (latches); std::sync::Mutex (telemetry)

Rejected

std::sync everywhere; custom spinlock

When the rejected choice is right

std::sync everywhere wins only under a stricter dependency-minimization constraint than this project has

Why: smaller footprint + faster uncontended path on hot latch path

ADR-13

I/O syscalls

Chosen

pwrite/pread explicit offset

Rejected

seek+read/write

When the rejected choice is right

seek+write wins only strictly single-threaded sequential-only I/O

Why: eliminates shared-file-position race; flusher submits from any thread

ADR-14

fsync discipline

Chosen

fsync on growth/commit; fdatasync in-segment WAL append

Rejected

When the rejected choice is right

fsync-always wins on filesystems where fdatasync gives no speedup (some CoW filesystems)

Why: fdatasync skips metadata fence when file size unchanged

ADR-15

O_DIRECT

Chosen

opt-in, off by default

Rejected

always on

When the rejected choice is right

always-on wins high-throughput workloads where page-cache double-buffering hurts p99 (M8/M9)

Why: avoids alignment/fsync-interaction complexity in the common case

ADR-16

Torn-write protection

Chosen

FullPage-after-checkpoint (Phase 0); double-write buffer deferred

Rejected

double-write buffer shipped in Phase 0

When the rejected choice is right

double-write buffer wins once repair cost (full WAL replay) exceeds its constant-time restore under high dirty-page churn (§35 row 5)

ADR-17

Leaf compression

Chosen

Rejected

none; per-cell compression

When the rejected choice is right

no compression wins random/UUID-shaped keys with no shared prefix (CPU cost, zero savings)

34. Alternative Architectures (Roads Not Taken)

AA1 — LSM-Tree (RocksDB/LevelDB-shaped).

Show the original text diagram
writes → memtable (sorted, in-RAM) → immutable memtable → SSTable flush
                                                              │
                                          L0 (unsorted SSTs) → compaction → L1..Ln
                                          reads: memtable → L0..Ln, bloom-filter-gated

Regime where it wins: write-dominated, append-heavy ingestion tolerating read/scan amplification and periodic compaction stalls (Kleppmann 2017 ch. 3; Lu et al. 2016). Real system: RocksDB. Rejected here because point-lookup (M1) and p99 read latency (M9) targets assume a bounded number of page fetches per read (tree height, §32 C3) — an LSM-tree's multi-level read amplification and compaction-induced latency spikes conflict with those targets (§33 Q15).

AA2 — Bw-Tree (lock-free mapping table + delta records).

Show the original text diagram
logical pgno → mapping table → [delta_N → delta_(N-1) → ... → base page]
reads: walk the delta chain; writes: CAS-prepend a new delta; consolidate past a length threshold

Regime where it wins: extreme core-count contention where even brief latch holds (ADR-09) dominate throughput (Levandoski, Lomet, Sengupta 2013). Rejected as the Phase-0 default: the CAS-based delta-chain protocol is substantially harder to make correct and to debug than latch crabbing, and the target workload (single-writer, ADR-08) does not need lock-freedom at all — documented as a stretch path (§35 row 3), not discarded.

AA3 — Fractal/Streaming Tree (TokuDB-shaped).

each internal node carries a message buffer; writes are appended as messages and pushed
down lazily on a full-buffer flush, amortizing the cost of a logical insert across many
buffered messages instead of one immediate leaf mutation

Regime where it wins: write-heavy, sequential-or-random insert-dominated workloads where write amplification must stay near-optimal even at very large fanout (TokuFT/TokuDB). Rejected here because message-buffer flush ordering adds a second recovery dimension (buffered-but-unflushed messages) on top of the WAL (§18) that this engine's redo-only model does not need — the target workload (§4) is read-and-write balanced, not write-amplification-critical.

AA4 — In-Memory with Periodic Snapshot (Redis RDB/AOF-shaped).

Show the original text diagram
all data resident in RAM (hash table or skiplist) → periodic full-image snapshot (RDB) or
append-only command log (AOF) replayed on restart

Regime where it wins: datasets that fit entirely in RAM with relaxed durability requirements (losing the last few seconds of writes is acceptable). Rejected here because the target regime (§4: 10M keys, unbounded value growth via overflow chains, ADR-19) explicitly assumes a dataset larger than RAM is the common case — the buffer pool (§17) exists precisely because "everything fits in memory" is not a safe assumption for this engine's users.
