Hard questions (§34)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does "exactly-once activity execution" not require exactly-once message delivery, and what specifically must be true of the activity for the claim to hold? (§14, §15)
  2. Why is compensation ordered by completion time rather than scheduling time, and what breaks if it were ordered by scheduling time instead? (§16, §8)
  3. Why must ctx.now() read from history rather than the wall clock, and what specific replay failure does violating this cause? (§14, §18)
  4. Why is a single-writer-per-shard lease insufficient without a fencing token, and what failure does the fencing token close that the lease alone does not? (§13, §19)
  5. Why does SignalWithStart need to be atomic only at the shard level rather than the cluster level, and how does sharding by workflow ID make that sufficient? (§17, §19)
  6. Why is continue_as_new the only sanctioned mechanism for bounding history size, and what quantitative failure occurs if a long-running workflow never calls it? (§18, §33)
  7. Why can the visibility store's eventual consistency never threaten workflow-execution correctness, even though it can mislead an operator? (§20, §3)
  8. Why can a compensation not itself schedule a compensation, and what would go wrong operationally if it could? (§16, §24)
  9. Why does sticky caching change latency but never correctness, and what design mistake would break that guarantee? (§14, §22)
  10. Why is snapshot+delta compaction necessary to hit the 100K-event replay target, and what is the naive-replay cost it replaces? (§22, §33)
  11. Why does this design reject range-partitioning sharding even though it would simplify some operational queries? (§9, §30)
  12. Why is timer tie-breaking done with a logical sequence number instead of arrival order, and what non-deterministic bug would arrival order reintroduce? (§18, §7)
  13. Why does the four-timeout taxonomy exist instead of one timeout, and what failure mode does each one specifically catch that the others miss? (§8, §15)
  14. Why must idempotency keys be engine-assigned rather than caller-supplied by default, and under what regime would a caller-supplied key be preferable? (§9, §14)
  15. Why does this design choose orchestration over choreography for saga coordination, and in what regime would choreography be the better call? (§16, §35)
  16. Why is a workflow engine's replay contract analogous to a database's redo log, and what does that analogy predict about how a replay bug should be debugged? (§14, §31)
  17. Why does Camunda Zeebe's Raft-based partitioning avoid needing an external lease service, and what does this design give up by relying on etcd instead? (§32, §19)
  18. Why doesn't batching event appends into a 5 ms window violate the single-writer-per- shard invariant, and what would break if the batching window spanned a shard-ownership change? (§13, §22)
  19. Why is the 30-day soak gated at the release level rather than at Phase 10's own acceptance criteria? (§22, §27)
  20. Why does this design's DR strategy prefer operator-triggered failover over automatic failover, and what correctness guarantee would automatic failover put at risk? (§19, §24)

31. Mental Models & First Principles

  • MM1 — A workflow is a deterministic replay of a program against a growing log, not a running process. Predicts: worker crashes and restarts are non-events. Bug class without it: engineers assume in-memory state survives a crash, then are shocked when a global variable resets. Applies in §14.
  • MM2 — History is truth; every other store is a cache with a name. Predicts: any disagreement between wf-visibility and wf-history resolves in history's favor. Bug class without it: operators debug the read model when the bug is upstream, or "fix" data by writing directly to the derived index. Applies in §3, §20.
  • MM3 — Compensation is an apology, not an undo. (Helland, §5.) Predicts: every compensation is a new forward action with its own failure mode, never a free rollback. Bug class without it: engineers write a compensating activity assuming it can always succeed instantly, then get paged when the downstream API is down. Applies in §16.
  • MM4 — A shard is a single-threaded program wearing a distributed system's clothes. Predicts: correctness reasoning inside one shard can use ordinary sequential logic; only cross-shard interactions need distributed reasoning. Bug class without it: engineers add unneeded locks inside a shard's fold, or wrongly assume sequential reasoning holds across shards. Applies in §13, §19.
  • MM5 — Idempotency keys turn "at least once" into "effectively once" — only as far as the weakest link. Predicts: a system's exactly-once claim is only as strong as its least-idempotent downstream call. Bug class without it: teams celebrate an "exactly-once" architecture while one activity silently double-charges because its downstream API ignores the idempotency key. Applies in §14, §15.
  • MM6 — Every timer is a promise the log keeps, not the clock. Predicts: timer accuracy is bounded by the log-owning shard's health, not by absolute wall-clock precision. Bug class without it: engineers expect microsecond timer precision from a system whose actual contract is "best-effort within 100 ms." Applies in §18.
  • MM7 — Sticky caching is an optimisation on a system already correct without it. Predicts: disabling all caching should change latency, never correctness. Bug class without it: engineers accidentally make correctness depend on cache presence, producing "works until the worker restarts" bugs. Applies in §14, §22.
  • MM8 — A saga's atomicity is a narrative, not a lock. Predicts: intermediate saga states are visible to the rest of the system and must be designed for, not hidden. Bug class without it: downstream systems (e.g. a reporting dashboard) assume "in progress" never appears and break the first time a saga runs long. Applies in §2, §16.

Glossary (§37) · 54 terms · site-wide glossary

Activity
A unit of non-deterministic work (I/O, side effects) executed by an activity worker; retried at-least-once (§15).
ActivityContext
SDK handle inside an activity exposing activity_id, attempt, heartbeat, deadline (§11).
ActivityId
Engine-assigned UUID identifying one activity invocation; doubles as the idempotency key (I7).
ASL (Amazon States Language)
The JSON DSL AWS Step Functions uses to define workflows as state machines (§5, §32).
At-Least-Once Delivery
A delivery guarantee that may redeliver but never silently drops; the engine's actual guarantee for activities and signals (I6, I11).
BPMN 2.0
The XML-based visual workflow notation Camunda Zeebe uses as its source of truth (§5, §32); this design's deferred DSL frontend target (§36).
CAP Theorem
The impossibility of simultaneous Consistency, Availability, and Partition tolerance; informs the CP-history/AP-visibility split (§4, §32).
Choreography (saga)
A coordination style where each service reacts to prior events with no central coordinator (§35); rejected here in favor of orchestration (P1).
Command
The workflow worker's sole output, translated into history events on append (§8.2, §11.3).
Compensating Transaction
An activity that semantically reverses (not literally undoes) a prior activity's business effect (§16).
Compensation
The reverse-completion-order execution of compensating transactions on workflow failure or cancellation (I8, §16).
Consistent Hashing
The scheme (Karger et al. 1997) mapping workflow IDs to shards with minimal disruption on shard-count change (§19, ADR-04).
Continue-As-New (CAN)
The API closing the current run and opening a fresh run with a new RunId, bounding history growth (P10, I9, §18).
CQRS
Command Query Responsibility Segregation; the write model (wf-history) and read model (wf-visibility) are separate stores (§5, §20).
Cron Workflow
A workflow whose body sleeps then calls continue_as_new, providing cron semantics with no separate scheduler (P10, §18).
Dead Letter
The terminal destination for an activity/compensation that exhausted retries, requiring manual intervention (§15, §24).
Determinism Contract
The requirement that identical history produces an identical command list from workflow code (I5, P3, §14).
Determinism Validator
The CI component replaying recent production histories against proposed code to catch determinism violations before merge (ADR-18, §14).
Event Sourcing
Storing state as an append-only sequence of events and deriving current state by folding them (Fowler, §5; §8, §13).
Exactly-Once Execution
The application-observable guarantee achieved via at-least-once delivery + an idempotency key; distinct from impossible "exactly-once delivery" (Treat, §5; I7).
Fencing Token
A monotonically increasing epoch attached to a shard lease; rejects writes from a stale former owner (I3, §19).
Hard Question
A staff-level self-examination question requiring synthesis of ≥ 2 sections of this document (§34).
HistoryEvent
One immutable, monotonically ordered record of a workflow state transition (§8.1, §11.2).
History Service (wf-history)
The sharded, single-writer component owning the append-only event log, timers, and transfer queue (§3, §13).
Hybrid Logical Clock
A clock combining physical time and a logical counter for cross-node event ordering (Kulkarni et al., §5); deferred cross-region time source (§36).
Idempotency Key
A caller- or engine-supplied token ensuring a retried operation has effect at most once downstream (I7, ADR-14).
Jump Consistent Hash
The specific consistent-hashing algorithm (Lamping & Veach 2014) used to compute shard_for(workflow_id) (§19, ADR-04).
Long-Poll
A dispatch technique where a worker's poll RPC blocks (up to 60 s) until work arrives, avoiding tight poll loops (ADR-06, §15).
MutableState
The folded, in-memory representation of a workflow's current state, derived purely from its history (I1, §11.5).
Namespace
The tenancy/authorization scope every workflow, task queue, and visibility query is bound to (§11.1, §20).
Orchestration (saga)
A coordination style with a central coordinator holding the control flow explicitly, as code (§1, P1); this design's chosen style.
Poison Workflow/Activity
A workflow or activity that deterministically and repeatedly fails, requiring operator intervention (§24).
Query
A synchronous, side-effect-free read of a workflow's current state; produces zero history events (P6, I12, §17).
Replay
Re-executing workflow code against a fixed history to reconstruct state or verify determinism (§14).
Retry Policy
The per-activity configuration (initial interval, backoff coefficient, max interval, max attempts, non-retryable errors) governing retries (§11.5, ADR-12).
RTO (Recovery Time Objective)
The maximum acceptable time to resume service after a failure (row shard_failover_rto, §4).
Saga
A sequence of local transactions with compensations such that any prefix can be unwound to a business-acceptable state (Garcia-Molina & Salem 1987, §5; §16).
SBOM (Software Bill of Materials)
A machine-readable inventory of a build's dependencies, generated per release (§28).
Shard
A partition of the consistent-hash ring owned by exactly one wf-history process at a time (I3, §19).
Shard Lease
The time-bounded ownership grant a history server holds for a shard, renewed against etcd (§11.5, §19).
Side Effect (ctx.side_effect)
A one-off non-deterministic computation recorded once in history and replayed thereafter (P3, §8.1).
Signal
An asynchronous, durably ordered event delivered to a running workflow (P6, I11, §17).
SignalWithStart
The atomic "signal if running, else start with the signal buffered" API (P15, I11, §17).
Single-Writer (per shard)
The invariant that exactly one process may append to a given shard's history at a time (I3, §7).
Snapshot+Delta Compaction
Materialising periodic MutableState snapshots so replay loads snapshot + tail instead of the full history (ADR-11, §22).
Sticky Task Queue
A matching-service routing rule sending a workflow's next task back to the worker that last executed it, avoiding replay on a cache hit (P11, ADR-09, §14).
Task Token
An opaque handle identifying one in-flight activity attempt, used to complete/fail exactly that attempt (§15).
Timer Wheel
A hierarchical data structure (Varghese & Lauck 1987) providing O(1) amortized timer insert/cancel/tick regardless of pending-timer count (§18).
Transfer Queue
The at-least-once internal bus carrying cross-shard work (child workflow starts, cross-workflow signals) (§3, §19).
Two-Phase Commit (2PC)
The classical blocking distributed-transaction protocol this system's saga model replaces for cross-service consistency (§1, §5).
Visibility Store (wf-visibility)
The eventually consistent, denormalised CQRS read index for listing/searching workflows (§20).
Workflow
A durable, replay-based execution of application-defined orchestration code (§1, §11.4).
WorkflowContext
The SDK handle giving workflow code access to deterministic primitives (now, random, sleep, execute_activity, …) (§11.4).
WorkflowId
The caller-supplied, stable identifier for a logical workflow, unique per namespace while a run is open (§11.1).
