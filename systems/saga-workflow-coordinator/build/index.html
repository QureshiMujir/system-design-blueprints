⬜ Phase 0 — Skeleton, Governance & Hello-Workflow §12

Objectives

Land the full repository skeleton (§10) in one commit; stand up an in-memory, single-shard, single-process control plane sufficient to run one workflow that calls one activity and completes (the "Hello, Workflow" trace, §8.4); establish governance scaffolding before any business logic lands.

Deliverable

make bootstrap && make build && make test && make compose-up all return zero; wfctl start Greet --input '"World"' completes with "Hello, World" on the single-node compose stack.

Acceptance
  • make test passes with ≥ 1 integration test (hello_smoke.rs).
  • The resulting history has exactly 11 events, matching the §8.4 trace exactly (assert full sequence, not just terminal status).
  • make compose-up brings up frontend + history + matching + Postgres in ≤ 30 s (relaxed ×6 over row startup_time, §4, for compose/dev mode).
  • ADR-01, ADR-02, ADR-03, ADR-19 (§9) written and merged.
Fixtures
Fixture Purpose Expected Output
hello_smoke.rs End-to-end single workflow + single activity 11-event history; WorkflowExecutionCompleted{result="Hello, World"}
bootstrap_ci (workflow run) CI green on a clean clone All skeleton jobs pass on main
malformed_start_request.rs StartWorkflowExecution with empty workflow_type Rejected InvalidArgument; no event appended
Pitfalls
  • Skipping protobuf for a Rust-native format (bincode) to move faster — resist; ADR-02 (§9) is decided from commit one so schema-evolution bugs surface early.
  • Handling only one of the workflow's two workflow tasks (schedule, then complete) — this passes a naive smoke test but cannot handle anything past §8.4's full trace.
  • Wiring CI jobs as literal no-ops — defeats §10's CI-gate layout; skeleton jobs must at least run cargo check.

⬜ Phase 1 — Event-Sourced History Service §13

Objectives

Replace Phase 0's in-memory wf-history with a durable, storage-backed, single-shard service exercising the real append/fold path; establish the state-machine fold (§8.3) with invariant assertions (I1, I2, I13) enforced in debug builds.

Deliverable

wf-history backed by Postgres survives a process restart with zero data loss; the full happy path (StartWorkflowExecution → RespondWorkflowTaskCompleted → RespondActivityTaskCompleted → GetWorkflowExecutionHistory) round-trips correctly.

Acceptance
  • 100% of §8.3 state-machine transitions have both a positive (legal apply) and negative (illegal apply asserts) unit test.
  • Property test runs ≥ 10,000 generated histories with zero fold non-determinism.
  • hist_append_p99 ≤ 10 ms on the reference cluster (row, §4) over 10,000 appends.
  • A killed-and-restarted wf-history resumes with byte-for-byte identical MutableState for every open workflow.
Fixtures
Fixture Purpose Expected Output
determinism.replay_identity (corpus) Two folds of the same history Byte-identical MutableState
dangling_reference.json ActivityTaskCompleted with unknown scheduled_event_id AppendError::DanglingReference; no append (§8.5)
concurrent_append_race.rs Two writers append with the same expected_last_event_id Exactly one succeeds; other sees AppendError::Concurrency
restart_replay.rs Kill wf-history, restart, replay Identical MutableState pre/post restart
Pitfalls
  • Omitting the expected_last_event_id check "because we're single-shard for now" — two concurrent workers then produce duplicate scheduled_event_ids and the fold panics (I2).
  • Treating event_time as authoritative wall-clock time — it is the history server's clock at append time; skew propagates into ctx.now() (P7) and is accepted, not corrected, until the hybrid-logical-clock stretch item (PhaseDeferred("§36")).
  • Building the fold as a mutable loop with early returns that skip invariant assertions on terminal-state branches — every branch runs the same assertion set (I13).

⬜ Phase 2 — Workflow Worker SDK: The Determinism Core §14

Objectives

Implement the deterministic-replay execution model in wf-worker-sdk-rs: given a fixed history, workflow code emits the same command list every time (I5); implement WorkflowContext primitives as history-driven futures, not ambient runtime calls (P3).

Deliverable

wf-worker-sdk-rs supports Workflow, ctx.now(), ctx.random(), ctx.sleep(), ctx.execute_activity(), ctx.side_effect(); the validator runs as .github/workflows/determinism.yml.

Acceptance
  • Two replays of an identical history against identical code produce byte-identical command lists on 100% of the determinism.replay_identity corpus (≥ 200 cases).
  • A workflow calling SystemTime::now() directly is rejected by the Clippy lint or the validator (both mechanisms exercised by a dedicated negative test).
  • Validator replay of 100 synthetic production histories completes in ≤ 30 s (feeds §29 M12).
Fixtures
Fixture Purpose Expected Output
determinism.cross_compiler Replay across Rust 1.78/1.79/1.80 Identical commands across compiler versions
hashmap_ban.rs Workflow using std::collections::HashMap Clippy lint fails the build
direct_systemtime.rs Workflow calling SystemTime::now() Validator rejects the commit
side_effect_replay.rs ctx.side_effect() evaluated once, replayed twice Recorded result reused; closure not re-invoked
Pitfalls
  • HashMap iteration order (randomized per-process in Rust) is the #1 non-determinism source; ban via lint, not documentation alone (P13).
  • tokio::time::sleep looks innocuous, works on the first run, and hangs forever on replay because it never yields to the engine — ban via lint.
  • The compiler-generated async fn state machine is sensitive to source formatting in pathological cases; replaying across compiler versions in CI (determinism.cross_compiler) catches this class.

⬜ Phase 3 — Activity Worker SDK & Task Queue Protocol §15

Objectives

Implement the activity worker: polling, execution, heartbeating, and the four-timeout taxonomy (§8.1); implement the retry-policy state machine at wf-history (P4, ADR-12).

Deliverable

Activity workers poll, run, heartbeat, complete, and fail against a live wf-matching+wf-history; all four timeouts fire correctly under integration test.

Acceptance
  • A failing_activity fixture fails 3 times under max_attempts=4, succeeds on the fourth; the workflow observes exactly one success.
  • Retry delays match the exponential-backoff-with-jitter formula within ±25% over 100 sampled retries.
  • act_dispatch_p99 ≤ 50 ms (row, §4) over 10,000 dispatches on the reference cluster.
  • Heartbeat timeout fires within heartbeat_timeout + timer_accuracy_p99 (row, §4) of the last heartbeat over 100 induced-timeout cases.
Fixtures
Fixture Purpose Expected Output
exactly_once.activity_runs_once Worker crash mid-activity + retry Downstream sees exactly one effect (idempotency key honoured, I7)
four_timeouts.rs Induce each of the 4 timeout types Corresponding ActivityTaskTimedOut{timeout_type=...}
retry_backoff_jitter.rs 100 retries under a fixed policy Delays within ±25% of the formula
concurrent_task_tokens.rs 2 activities complete concurrently on one worker No cross-token completion mix-up
Pitfalls
  • Mixing task_tokens between concurrently running activities on one worker produces "completed someone else's task" bugs that are hard to reproduce — isolate token state per in-flight activity.
  • Heartbeat RPC failure (network blip) must be best-effort — log and continue, never panic the activity; StartToClose is the real safety net.
  • Multiplicative jitter on small initial intervals collapses toward zero; jitter must be additive, not multiplicative (ADR-12).

⬜ Phase 4 — Sagas via Compensation §16

Objectives

Implement ctx.schedule_compensation::<A>(args) and the automatic reverse-order compensation run on workflow failure/cancellation (Garcia-Molina & Salem 1987, §5; I8, P5).

Deliverable

examples/payments_saga demonstrates: when SendConfirmation fails (retries exhausted), exactly three compensations run in reverse completion order, then WorkflowExecutionFailed{cause=ActivityFailure}.

Acceptance
  • compensation.linear_saga passes for lengths 1–20, failing at every position k, with zero I8 violations across ≥ 1,000 property-test runs.
  • compensation.parallel_saga orders compensations by completion timestamp, not declaration order.
  • compensation.failed_compensation asserts a compensation exhausting retries lands in CompensationFailed, never an infinite retry loop.
Fixtures
Fixture Purpose Expected Output
compensation.linear_saga Linear saga, fail at position k Compensations for 1..k−1 run in reverse order
compensation.parallel_saga Parallel branches, one fails Compensations ordered by completion time per branch
compensation.failed_compensation Compensation itself exhausts retries WorkflowExecutionFailed{cause=CompensationFailed}; page fires
compensation.cancellation_unwind External cancellation mid-saga Same reverse-order compensation run as on failure
Pitfalls
  • Compensation order is the reverse of completion order, not scheduling order — parallel branches (concurrent ctx.execute_activity() calls, §11) require recording completion timestamps, not program order (I8).
  • Capturing local workflow state in a compensation closure is non-deterministic on replay; the pattern is schedule_compensation::<A>(args) with args a serializable snapshot, never a captured reference (P3).
  • "Idempotent compensation" is stronger than "idempotent forward step" — a RefundCard run twice must refund once; use the engine's ActivityId as the idempotency key (I7, P4).

⬜ Phase 5 — Signals and Queries §17

Objectives

Implement asynchronous signal delivery (SignalReceived, SignalWithStart) and synchronous, side-effect-free queries (P6, I11, I12).

Deliverable

Signals deliver to running workflows and land as SignalReceived; SignalWithStart is atomic under a race; queries return current state with zero history mutation.

Acceptance
  • A race between two concurrent SignalWithStart calls on the same WorkflowId produces exactly one execution and exactly two delivered signals over ≥ 500 induced-race trials (I11).
  • QueryWorkflow appends zero events, verified by a pre/post history-length diff on 100 sampled queries (I12).
  • Query latency approaches O(1) on a sticky-cache hit (no full replay), verified by comparing cache-hit vs. cache-miss latency distributions.
  • Signal rate limiting rejects the 101st signal/second to one workflow with ResourceExhausted (row signal_rate_per_wf, §4).
Fixtures
Fixture Purpose Expected Output
signal_query.signal_with_start Race between two SignalWithStart calls Exactly one workflow; exactly two signals
signal_query.signal_before_start_buffered Signal arrives before the first workflow task Signal lands in history before the first workflow-task event
signal_query.query_no_side_effects Query a running workflow Zero events appended between query start and end
signal_query.rate_limit 150 signals/s to one workflow 101st+ rejected ResourceExhausted
Pitfalls
  • A signal handler calling ctx.execute_activity() directly from on_signal can race the main execute loop's own scheduling; the documented pattern is: the handler buffers, the main loop consumes (P6).
  • on_query mutating workflow state (e.g. lazy field init) silently breaks replay — enforced at the type level (&self, not &mut self, I12).
  • Buffered signals via SignalWithStart arrive before the first workflow task starts; execute() must handle signals already pending on its first invocation.

⬜ Phase 6 — Timers, Cron & Continue-As-New §18

Objectives

Implement durable timers backed by a hierarchical timing wheel (Varghese & Lauck, §5), cron-as-self-calling-workflow (P10), and continue_as_new (I9) to bound history growth (row max_history_events, §4).

Deliverable

The timer wheel fires within timer_accuracy_p99 on a quiet host; examples/cron_workflow fires on schedule across a DST boundary; examples/long_running_subscription's CAN variant produces bounded per-run histories.

Acceptance
  • 1,000 timers with deadlines spread across 24 hours fire within timer_accuracy_p99 ≤ 100 ms (row, §4) on a quiet host.
  • A cron workflow "0 2 * * *" in a DST-observing timezone fires exactly once per calendar day across the transition (neither 0 nor 2 times).
  • 100 chained continue_as_new calls produce 100 runs, each referencing the correct parent RunId (I9).
  • Per-run history stays under max_history_events (row, §4) for 3 years of simulated subscription cycles.
Fixtures
Fixture Purpose Expected Output
timers.accuracy 1,000 timers, deadlines over 24h Every timer fires within 100 ms p99
timers.dst_safe Cron timer across a DST transition Correct fire count in the workflow's timezone
continue_as_new.parent_reference 100 chained CAN calls Each new run references the prior RunId
continue_as_new.history_bounded Multi-year simulated subscription Per-run history stays below max_history_events
Pitfalls
  • A naive "0 2 * * *" cron on a DST-observing host skips or duplicates around the transition; the parser must require an explicit timezone.
  • Timer accuracy under host clock skew: the history server's clock is the truth (§13); we promise timer_accuracy_p99 ≤ 100 ms only on a quiet host, degrading under load — state this, do not over-promise.
  • continue_as_new is not retroactive: the parent run's history remains preserved and queryable; code assuming "current state reachable from time zero" is wrong — it must follow the continued_execution_run_id chain.

⬜ Phase 7 — Sharding and Scaling §19

Objectives

Scale wf-history from one hardcoded owner (§13) to a real consistent-hash-sharded fleet with lease-based single-writer ownership and graceful/forceful rebalancing (P8, I3, ADR-04, ADR-20).

Deliverable

A 4-history-server, 1,024-logical-shard cluster runs the full conformance suite end-to-end; a killed shard owner fails over within shard_failover_rto with zero data loss; adding a history server triggers a rebalance that moves shards without corrupting history.

Acceptance
  • Shard failover completes within shard_failover_rto ≤ 30 s (row, §4) with zero workflow data loss over 50 induced failovers.
  • A rebalance triggered by adding a history server, run concurrently with 10,000 in-flight workflows, completes with every workflow finishing correctly.
  • A partitioned old shard owner's writes are rejected 100% of the time once its fencing token is stale, verified by a partition-injection fixture.
  • wf_start_tp_cluster ≥ 18,000/s (row, §4) on the 4-process, 1,024-shard reference cluster.
Fixtures
Fixture Purpose Expected Output
sharding.rebalance_no_loss 10K workflows during a forced rebalance Every workflow completes; zero events lost
sharding.fencing_token_correctness Partitioned old leader writes during failover Writes rejected; new leader's writes are the only ones present
jepsen.history_partition Network partition of wf-history for 30 s All workflows resume after the partition heals; no inconsistent state
jepsen.matching_partition Partition wf-matching from wf-history Workflow tasks redelivered; no duplicate execution
Pitfalls
  • Sharding by WorkflowId alone collides if a popular literal ID (e.g. "singleton") is reused across tenants — lint/document a high-cardinality-component requirement (P8).
  • Shard-ownership churn produces replay storms — the sticky-cache hit rate (row sticky_hit_rate, §4) plummets temporarily; plan for ~2× dispatch latency for 60 s post-rebalance.
  • Skipping the fencing-token check "since partitions are rare" lets a partitioned old leader write for the duration of its TCP timeouts — the check costs one extra column read per append and is non-negotiable (I3).

⬜ Phase 8 — Visibility Store §20

Objectives

Implement the CQRS read model (Young, §5): a denormalised, eventually consistent index for "list/search workflows by status/type/time/custom attributes" (I1, ADR-15).

Deliverable

ListWorkflows supports filtering by workflow_type, status, time range, and custom search attributes; every completed workflow appears in the index within vis_lag_p99.

Acceptance
  • Visibility ingest lag ≤ vis_lag_p99 ≤ 1 s (row, §4) over 10,000 sampled transitions.
  • A property test asserts every completed workflow appears in ListWorkflows(WHERE status = Completed) within 5 s, over 1,000 sampled completions.
  • A cross-tenant query without an explicit namespace filter is rejected at wf-frontend 100% of the time over 1,000 fuzzed queries (§23 T8).
  • The reconciliation job flags drift > 0.1% between wf-visibility and wf-history counts within one 5-minute reconciliation cycle.
Fixtures
Fixture Purpose Expected Output
visibility.ingest_lag 10,000 state transitions p99 ingest lag ≤ 1 s
visibility.completed_appears 1,000 sampled completions Appears in ListWorkflows within 5 s
visibility.namespace_isolation 1,000 fuzzed cross-tenant queries Zero leaks; frontend-layer rejection

Pitfalls
  • The visibility store's replication-lag SLA is not the user's correctness SLA — document explicitly: eventually consistent; use DescribeWorkflowExecution against wf-history for strict consistency.
  • Elasticsearch mapping changes (a new search attribute) are not transparent; gate behind wfctl admin upsert-mapping with a documented migration procedure (§26).
  • A malformed ad-hoc query (regex DoS, unindexed field) can take down the search cluster — a per-query timeout (10 s) and per-namespace rate limit at wf-frontend are mandatory.

⬜ Phase 9 — Multi-Language SDK (Python + TypeScript) §21

Objectives

Port the determinism contract (§14) to Python (wf-worker-sdk-py) and TypeScript (wf-worker-sdk-ts), each enforcing it via language-appropriate mechanisms, with cross-SDK conformance — identical histories for identical inputs across all three SDKs.

Deliverable

Python and TypeScript SDKs run examples/payments_saga end-to-end; a workflow defined once and re-implemented in each SDK produces identical histories for identical inputs.

Acceptance
  • Cross-SDK conformance: the shared corpus produces byte-identical command lists across Rust, Python, and TypeScript implementations, 100% of ≥ 50 shared scenarios.
  • The Python validator rejects a workflow calling time.time() directly (bytecode- inspection catch, verified by a dedicated negative test).
  • The TypeScript isolate's sealed globals make Date.now() structurally unreachable — verified by observing a ReferenceError, not a runtime policy check.
  • asyncio.gather/workflow.parallel resolve in submission order on 100 replayed traces with intentionally reordered completion timing.
Fixtures
Fixture Purpose Expected Output
determinism.cross_sdk (Python) Shared corpus vs. Rust reference Byte-identical commands
determinism.cross_sdk (TypeScript) Shared corpus vs. Rust reference Byte-identical commands
python_time_time_ban.py Workflow calling time.time() Validator rejects the commit
ts_isolate_globals_sealed.ts Workflow calling Date.now() ReferenceError at isolate boundary
Pitfalls
  • Python's asyncio.gather does not resolve futures in a deterministic order when several are immediately ready — override it to resolve in submission order on replay.
  • TypeScript's Promise.all has the identical issue — workflow.parallel(...) is the deterministic replacement.
  • Serialization differences (json.dumps vs. JSON.stringify key ordering) silently break cross-SDK determinism — mandate RFC 8785 canonical JSON.

⬜ Phase 10 — Performance Hardening & Release Gate §22

Objectives

Harden performance to the full §4/§29 target set; implement sticky caching, batched appends, pipelined activity dispatch, snapshot+delta compaction; run the 24-hour and 30-day soak plus the external fault-injection audit that gates release (§27, §28).

Deliverable

The reference cluster meets every §29 M-table target; the 24-hour soak passes with zero data loss and no memory growth; audits/soak/ and audits/jepsen/ hold the evidence the release gate (§27) checks for.

Acceptance
  • Sticky cache hit rate ≥ 95% (row sticky_hit_rate, §4) on a 100,000-active-workflow benchmark.
  • p99 activity dispatch latency ≤ 50 ms (row act_dispatch_p99, §4) on the healthy reference cluster.
  • Workflow start throughput ≥ 5,000/s per wf-history process (row wf_start_tp, §4) on benchmark hardware.
  • A 100,000-event workflow replays in ≤ 1 s using snapshot+delta (row replay_100k_p99, §4).
  • 24-hour soak: zero data loss, no unbounded memory growth (heap high-water mark within 10% across the run).
Fixtures
Fixture Purpose Expected Output
perf.sticky_hit_rate 100K active workflows, steady state ≥ 95% cache hit rate
perf.replay_100k 100K-event history, snapshot+delta ≤ 1 s replay
perf.snapshot_delta_diff fold(history) vs. apply_delta(snapshot, tail) Identical MutableState on a corpus of histories
soak.24h 24-hour continuous run Zero data loss; bounded memory
soak.30day (release gate) 30-day, 1M concurrent workflows Zero data loss; p99 within 2× baseline
Pitfalls
  • Sticky-cache invalidation: a worker holding the lease that crashed without notifying wf-matching delays the next task until lease expiry — tune lease duration against crash-detection latency (default 1-minute lease + 5-second TCP heartbeat).
  • Batch-append latency adds ~5 ms per event; expose a bypass flag on RespondWorkflowTaskCompleted for latency-sensitive workflows.
  • Snapshot bugs are silent: if the snapshot serializer disagrees with the deserializer (a renamed field, a changed default), replay reconstructs a different state than full-history replay — mitigate with the perf.snapshot_delta_diff CI fixture on every snapshot-format change.
