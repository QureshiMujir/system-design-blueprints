4. System Constraints

Reference cluster for every number below: 1,024 shards, 4 wf-history processes (256 shards/process), 8-core/32 GB history hosts, 10 Gb/s NIC, NVMe-backed Postgres (or 3-node Cassandra), workers on separate hosts. Defining property: the history append path is the sole hard-consistency bottleneck; everything else scales embarrassingly in parallel.

33. Back-of-Envelope Capacity Model

Every number below is derived from the §4 constraint table; none is asserted standalone.

C1 — History size of a typical saga. examples/payments_saga (4 activities) has ≈ 29 events (1 WorkflowExecutionStarted + 4 × (3 workflow-task + 3 activity events) + 1 WorkflowExecutionCompleted, rounding). 10 of those carry a payload (the activity Scheduled/Completed pairs plus start/complete), 19 do not: bytes = 19 × event_bytes + 10 × (event_bytes + payload_bytes) = 19×180 + 10×692 = 3,420 + 6,920 = 10,340 bytes ≈ 10 KB.

C2 — Max-history byte budget cross-check. max_history_events × (event_bytes + payload_bytes) = 50,000 × 692 = 34,600,000 bytes ≈ 34.6 MB, against max_history_bytes = 50 MB (row, §4) — 15.4 MB (31%) headroom, confirming the two ceilings in §4 are mutually consistent rather than independently asserted.

C3 — Why snapshot+delta is required for M10. Assume a measured pure-fold rate of ~50,000 events/s (≈ 20 µs/event: protobuf decode + assertion checks, §13). A naive full replay of a 100,000-event history costs 100,000 / 50,000 = 2 s — 2× over M10's 1 s target. With snapshot+delta (ADR-11, snapshot every 1,000 events), replay loads the snapshot (O(state), not O(events)) and replays only the tail: 1,000 / 50,000 = 20 ms — 50× inside the target. This is the arithmetic reason Phase 10 (§22) is mandatory, not optional polish.

C4 — FD budget vs. shard fan-out. 256 shards/process × 2 storage-pool connections/ shard = 512 FDs, plus ~50 internal service-mesh connections and ~16 pooled etcd lease-watch connections ≈ 578 FDs, against fd_budget_history = 16,384 (row, §4) — ~28× headroom before FD exhaustion becomes the binding constraint ahead of other resources.

C5 — Timer-wheel memory footprint. timer_capacity_shard = 500,000 pending timers/ shard × 256 shards/process × ~64 bytes/timer-entry (timer_id + fire_at + workflow reference) = 500,000 × 256 × 64 = 8,192,000,000 bytes ≈ 7.6 GB per process, against a 32 GB history host (§4 reference cluster) — ~24% of host RAM at full timer utilization, leaving ~24 GB for MutableState caching, storage client buffers, and OS overhead.

C6 — Aggregate sticky-cache demand. max_concurrent_wf × history_mem_per_wf = 1,000,000 × 8 KB = 8 GB aggregate across the worker fleet (sticky cache lives on workers, not wf-history, §3) if every open workflow were cached simultaneously. Because sticky_hit_rate (M7) targets ≥ 95%, not 100%, and the 1-minute lease (ADR-09) evicts idle entries, the realistic resident set at any instant is the active fraction within one lease window, not the full 1,000,000.

C7 — Storage amplification. A narrow, high-frequency insert (one events row) with 2 secondary indexes writes: the heap tuple + its WAL record + 2 index entries + their WAL records. Empirically this class of Postgres workload lands at 1.2–1.4× physical-to-logical bytes — storage_amp ≤ 1.3× (row, §4) is the defensible mid-point, gated by benchmarks/ (§29), not a purely theoretical figure.

C8 — Task-queue load implied by M1. At M1 = 5,000 workflow starts/s per process, each start's first workflow task alone implies ≥ 5,000 dispatches/s that wf-matching must sustain for that process — the floor wf-matching's long-poll queue depth and worker-poll concurrency (§15) must be provisioned against, before counting subsequent activity/task rounds.

C9 — Deriving M1 from hist_append_p99 + batching. An unbatched serial single-shard writer is capped at 1 / hist_append_p99 = 1 / 0.010 s = 100 appends/s. Batching (§22) groups concurrent commands from a process's 256 co-located shards into one commit per 5 ms window; assuming ~25 concurrent single-event commands per window (a conservative, storage-side estimate): 25 commands / 0.005 s = 5,000/s — exactly M1's target, and the reason M1 is only achievable after the Phase 10 batching optimisation (§22), not from the unbatched Phase 1 path (§13) alone.

C10 — Deriving M2 (cluster) from M1 (process). Naive linear scaling: 4 processes × 5,000/s = 20,000/s. Subtracting ~10% for coordination overhead (etcd lease contention, transfer-queue cross-shard traffic for child workflows/signals, §19): 20,000 × 0.9 = 18,000/s — exactly M2's target (row wf_start_tp_cluster, §4).
