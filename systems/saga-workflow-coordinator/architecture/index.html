3. Architectural Overview

┌──────────────────────────────────────────────────────────────────────┐
│ Client (operator / application service)                              │
│  StartWorkflow · SignalWorkflow · QueryWorkflow · TerminateWorkflow   │
│  gRPC over mTLS/TLS                          [protocol boundary]      │

                                 ▼
┌──────────────────────────────────────────────────────────────────────┐

              │                                   │  [persistence boundary]
              ▼                                   ▼

┌──────────────────────────────────────────────────────────────────────┐
│ wf-visibility — denormalised read model (CQRS); async from wf-history │
│  Elasticsearch/OpenSearch · list/search by status/type/time/attrs    │
└──────────────────────────────────────────────────────────────────────┘

Client. Issues the four verbs over gRPC; never talks to wf-history or wf-matching directly — wf-frontend is the only entry point (I4, §7).

wf-frontend. Stateless; horizontally scaled behind any L4/L7 balancer. Owns authn/authz, per-namespace rate limiting, and routing: shard = jump_consistent_hash(hash(namespace, workflow_id), shard_count) (ADR-04, §9). No workflow state lives here — restart is free.

wf-history. The truth. Sharded by workflow_id; each shard has exactly one writer, enforced by a lease + fencing token from the coordination service (I3, §7; ADR-20, §9). Owns the append-only event log (§8), the durable timer wheel (§18), and the transfer queue — an at-least-once internal bus for cross-shard work (child workflows, cross-workflow signals).

wf-matching. Holds task queues (one per TaskQueue name) and dispatches to polling workers via long-poll (ADR-06, §9). Sticky queues route a workflow's next task back to the worker that last executed it, avoiding a full replay on cache hit (P11, §6).

wf-storage. The persistence adapter behind wf-history and wf-visibility's write path. Postgres is the default (ADR-03, §9); Cassandra is the high-write-throughput option; RocksDB backs the embedded single-node demo mode with zero external dependencies.

Worker fleet. Operator-run, outside the control-plane trust boundary — the engine never executes application code in-process. Workflow workers replay deterministic code against history (§14); activity workers are the non-deterministic escape hatch for I/O and side effects (§15), retried at-least-once with caller-supplied idempotency keys (I7, §7).

wf-visibility. A CQRS read model (Young, §5), populated asynchronously off the transfer queue. Eventually consistent (≤ row vis_lag_p99, §4); never authoritative — on disagreement with wf-history, wf-history wins (I1, §7) and the index is rebuilt.

Three properties hold everywhere downstream: history is truth, everything else is a derived index (I1); single-writer-per-shard is non-negotiable for saga ordering correctness (I3); the workflow worker is the determinism boundary — activities are the only sanctioned non-determinism (P3, P4, §6).

8. Domain Model, Protocol & Data Model

8.1 Event catalog

Every workflow state transition is one immutable HistoryEvent variant, keyed by a monotonic event_id within (workflow_id, run_id) (I2). Fields shown are the load-bearing ones; every event also carries event_id: u64 and event_time: SystemTime.

8.3 Workflow execution state machine

From Trigger Event To Guard
— WorkflowExecutionStarted Running must be the first event
Running WorkflowExecutionCompleted Completed terminal
Running WorkflowExecutionFailed Failed compensation chain (§16) already exhausted
Running WorkflowExecutionTimedOut TimedOut workflow_execution_timeout/workflow_run_timeout elapsed
Running WorkflowExecutionCanceled Canceled compensation chain runs first (§16)
Running WorkflowExecutionTerminated Terminated operator-forced; no compensation runs
Running WorkflowExecutionContinuedAsNew ContinuedAsNew (this run) / Running (new run) I9; new RunId begins Running
Completed/Failed/TimedOut/Canceled/Terminated/ContinuedAsNew any — terminal; no further events accepted (I13)

Eleven events land in history for this trace: WorkflowExecutionStarted, WorkflowTaskScheduled/Started/Completed (×2 rounds), ActivityTaskScheduled/Started/ Completed, WorkflowExecutionCompleted — exactly the fixture hello_smoke.rs asserts (§12 N.5).

8.5 Malformed-input example

An ActivityTaskCompleted whose scheduled_event_id does not point at a preceding ActivityTaskScheduled in the same (workflow_id, run_id) is malformed: the state-machine fold (§13) refuses the append with AppendError::DanglingReference, the history is left unmodified, and wf_history_integrity_violation_total increments (I2). The fixture conformance/corpora/determinism/dangling_reference.json (§13) encodes this case; the expected output is a rejected append, not a panic that corrupts the shard.

8.6 Failure-path example

A four-activity saga (ReserveInventory → ChargeCard → ShipPackage → SendConfirmation, §16) where SendConfirmation exhausts its retries: the history shows ActivityTaskFailed{retry_state=Exhausted} for SendConfirmation, then three compensation activities appended and completed in reverse completion order — CancelShipment, RefundCard, ReleaseInventory (I8) — then WorkflowExecutionFailed{cause= ActivityFailure}. If RefundCard's compensation itself exhausts retries, the trace instead ends WorkflowExecutionFailed{cause=CompensationFailed} and pages on-call per the poison-workflow runbook (§25).

Design principles (§6)

  • P1 — Workflows are code, not DSL. Orchestration logic is written in a general-purpose language (Rust/Python/TypeScript); the SDK enforces the determinism contract. Tradeoff: loses the visual-editor audience BPMN/ASL serve. Operational implication: refactoring, IDE support, and unit testing come for free. Violate it and you reinvent a worse half-language (Conductor's JSON DSL, §5 Reference Implementations).
  • P2 — Sagas trade serializability for liveness. A saga's contract is "we will not get stuck," not "we are serializable"; intermediate states are visible and business- acceptable, never hidden behind a lock. Tradeoff: callers must tolerate partial-progress reads. Operational implication: every activity author must document what a partial saga looks like externally. Violate it and 2PC's blocking-coordinator failure mode returns (§1).
  • P3 — Deterministic replay is the foundation, not an optimisation. Every WorkflowContext primitive is either deterministic by construction (ctx.now() reads the last recorded event_time) or recorded as a SideEffect event. Tradeoff: workflow code cannot use the ambient language runtime freely. Operational implication: a CI replay-validator gates every commit (§14). Violate it and workflows silently wedge on replay divergence (I5).
  • P4 — Activities are at-least-once with caller-supplied idempotency keys. The SDK retries on every failure class until the retry policy says stop; the activity author is responsible for idempotency, using the engine's ActivityId as the key against downstream services. Tradeoff: activity authors carry real design burden. Operational implication: non-idempotent activities double-charge under retry. Violate it and "exactly-once" becomes "sometimes-twice" (I7).
  • P5 — Compensations are best-effort with their own retry policy; no compensation-of-compensation. A failed compensation (after exhausting retries) ends the workflow in CompensationFailed and pages a human; we never chain "undo the undo." Tradeoff: some sagas terminate in a state needing manual reconciliation. Operational implication: a named runbook (docs/runbook/poison-workflow.md) is mandatory. Violate it and the compensation chain has no natural halting point (§16, §24 FM6).
  • P6 — Signals are async events; queries are pure-function reads. A signal appends a SignalReceived event and mutates state on next replay; a query never appends an event and never mutates. Tradeoff: queries cannot trigger side effects, by design. Operational implication: on_query is typed &self, not &mut self (§11). Violate it and replay determinism breaks silently (§17).
  • P7 — Time travels with the workflow. ctx.now() returns the most recent history event's event_time, never the wall clock; ctx.sleep(d) schedules a durable TimerStarted/TimerFired pair. Tradeoff: sub-second timer precision is not promised (row timer_accuracy_p99, §4). Operational implication: workflow code has no other concept of time. Violate it and replay produces different timers than the first run.
  • P8 — Sharding by workflow ID, never by workflow type. Hashing by ID distributes load evenly; hashing by type creates hot shards for popular types. Tradeoff: cross-shard coordination (child workflows, cross-workflow signals) needs the transfer queue. Operational implication: workflow-ID naming conventions matter (§19, §24 FM8). Violate it and a handful of shards absorb all cluster load.
  • P9 — History events are immutable; state is a deterministic fold. No event is ever modified after append; corrections are new compensating events. MutableState is fold(events), nothing else. Tradeoff: storage grows monotonically until continue_as_new. Operational implication: snapshots are optimisations of the fold, never substitutes (§22). Violate it and replay and live state diverge (I13).
  • P10 — continue_as_new bounds history growth; cron is a workflow that calls itself. No special cron infrastructure exists; a cron workflow's body sleeps then calls ctx.continue_as_new(...). Tradeoff: cron history is bounded per-firing, not per-schedule-lifetime. Operational implication: the history-growth bound is the same problem as any long-running workflow (§18). Violate it and histories become unreplayable (row max_history_events, §4).
  • P11 — Sticky task queues cache workflow execution state. The matching service routes a workflow's next task back to the worker that last executed it, within a sticky lease; cache hit skips replay entirely. Tradeoff: worker crash mid-lease delays the next task until lease expiry. Operational implication: tune lease duration against crash-detection latency (§22). Violate it and every task pays a full replay (row sticky_hit_rate, §4).
  • P12 — At-least-once delivery + idempotency keys ≈ exactly-once from the application's perspective. The engine never promises exactly-once delivery (Treat, §5); it promises exactly-once effect when the idempotency-key contract is honoured. Tradeoff: the promise is only as strong as the weakest activity's idempotency implementation. Operational implication: idempotency-key discipline is documented at every activity call site. Violate it (P4 broken) and retries duplicate side effects.
  • P13 — Workflow code never busy-loops; every wait is durable. A workflow that "waits" must ctx.sleep() or ctx.await_signal(), never spin. Tradeoff: the SDK must detect and refuse tight loops. Operational implication: the replay validator flags unbounded loops without a yield point. Violate it and a worker pins a CPU core forever.
  • P14 — Workers are stateless except for the sticky cache. Restarting a worker is always safe; the sticky lease expires, matching re-routes, replay rebuilds the cache. Tradeoff: worker restarts cost a replay storm if many are cached. Operational implication: rolling worker deploys are safe by construction (§25). Violate it and a worker becomes a single point of failure for its cached workflows.
  • P15 — SignalWithStart is O(1) on the happy path. The most-used production API — atomically "start or signal" — must never take a lock proportional to cluster size. Tradeoff: the atomicity is scoped to a single shard, not the cluster. Operational implication: SignalWithStart throughput is a first-class benchmark (§29 M4). Violate it and the hottest API path becomes the bottleneck.
