ADR-01

Control-plane language

Chosen

Rust 1.78+ (edition 2021)

Rejected

Go, Java, Elixir/Erlang

When the rejected choice is right

Go/Java win for teams prioritizing hiring pool and velocity over allocation control — Temporal's actual choice

Why: Allocation discipline on the history hot path; compile-time determinism enforcement (§1)

ADR-02

Wire format

Chosen

gRPC + protobuf (tonic)

Rejected

JSON/REST, Cap'n Proto

When the rejected choice is right

JSON/REST wins for quick-integration, human-debuggable-traffic use cases (Step Functions' ASL-over-JSON model)

Why: Schema evolution + HTTP/2 streaming for long-poll (§3)

ADR-03

Persistence

Chosen

Postgres default; Cassandra high-throughput; RocksDB embedded

Rejected

Single-engine-only (Cassandra everywhere)

When the rejected choice is right

Single-engine-only wins when the org already runs Cassandra fleet-wide and wants one storage technology (Uber/Cadence)

Why: Matches operator scale without forcing a second storage stack on small deployments

ADR-04

Sharding key

Chosen

workflow_id via jump-consistent-hash (Karger 1997 / Lamping-Veach 2014)

Rejected

Sharding by workflow_type; range partitioning

When the rejected choice is right

Range partitioning wins when co-locating workflows for range scans (e.g. "all started this hour") matters more than load balance

Why: Even load distribution; type-based sharding creates hot shards (P8)

ADR-05

History event encoding

Chosen

Protobuf with explicit reserved-field discipline

Rejected

Schema-less JSON

When the rejected choice is right

Schema-less JSON wins during early prototyping before schema stability matters

Why: Backward compatibility for historical events is non-negotiable (I13)

ADR-06

Worker dispatch

Chosen

Long-poll, 60s

Rejected

Server push (gRPC bidi stream)

When the rejected choice is right

Push wins where inbound connectivity is stable and push infrastructure already exists

Why: Avoids NAT-traversal/connection-management complexity; the Temporal/Cadence default

ADR-07

Signal delivery semantics

Chosen

At-least-once durable; app-level idempotency via signal name + payload hash

Rejected

Exactly-once signal dedup at the engine

When the rejected choice is right

Engine-side dedup wins when signal payloads are cheap to fingerprint and callers want zero idempotency burden

Why: Keeps the engine simple; matches P4's idempotency philosophy

ADR-08

Query consistency

Chosen

Read-your-writes within one client session

Rejected

When the rejected choice is right

Linearizable queries win for compliance-driven audit reads where staleness is unacceptable at any cost

Why: Linearizability is expensive across a sharded fold; documented at the API (§17)

ADR-09

Workflow caching

Chosen

Rejected

No caching — always replay

When the rejected choice is right

Always-replay wins for workflows with huge in-memory state too costly to hold resident on workers

Why: Recovers full-replay cost on the hot path (P11)

ADR-10

History compaction

Chosen

Rejected

In-place truncation

When the rejected choice is right

In-place truncation wins only in a local single-node dev/demo mode where disk pressure outweighs audit guarantees and the operator has explicitly opted out of durability

ADR-11

Snapshot+delta compaction

Chosen

ADR-12

Retry policy shape

35. Alternative Architectures (Roads Not Taken)

Alt. 1 — Choreography (event-driven sagas, no central coordinator).

  OrderSvc --(OrderPlaced)--> bus --> InventorySvc --(Reserved)--> bus
     ^                                     |                        |
     |                                     v                        v
     +---(RefundIssued)<-- PaymentSvc <---(Reserved)--- bus <--(Charged)

Regime where it wins: highly decoupled microservice ecosystems with no single team owning the end-to-end process, where adding a participant should never require touching a central definition. Real system: Eventuate Tram Sagas (Chris Richardson, §5) implements this pattern directly. Rejected here because as step count grows, choreography's implicit control flow — spread across N services' individual event handlers — has no single place to read "what happens on failure," directly contradicting P1 (workflows are code, one place to read) and I1 (one source of truth).

Alt. 2 — Snapshot-only state store (no retained event log).

  saga_state table:  [ saga_id | phase | payload | updated_at ]  — updated in place,
                     no history of prior phases retained after each transition.

Regime where it wins: ephemeral, short-lived task orchestration where audit/replay/ time-travel debugging has zero value and storage cost dominates every other concern — a crashed workflow is simply restarted from scratch rather than resumed exactly. Real system: the plain relational "current-state" saga table Richardson (Ch. 4, §5) describes as the simplest possible orchestration implementation, without event sourcing. Rejected here because without an immutable log, replay-based crash recovery (P3) and time-travel debugging are structurally impossible — a mid-flight crash loses exactly which activities completed, forcing either data loss or a hand-rolled recovery log that reinvents event sourcing badly (I1, I9).

Alt. 3 — Polling-based timers (no timer wheel).

  Poller (fires every N seconds) ──▶ SELECT timer_id, workflow_id FROM timers
                                      WHERE fire_at <= now() AND fired = false

Regime where it wins: very low timer volume and low-precision requirements, where operational simplicity (a single indexed SQL query) outweighs the CPU/DB-load cost of polling — a small deployment with a handful of cron workflows and no SLA on timer_accuracy_p99. Real system: the naive polling approach Varghese & Lauck (1987, §5) explicitly benchmark their hierarchical timing wheel against. Rejected here because polling frequency trades directly against both database load and timer accuracy (row timer_accuracy_p99, §4); at timer_capacity_shard scale (§33 C5) a poll-based design needs either a very tight interval (high DB load) or much worse than 100 ms accuracy — the wheel is O(1) amortized regardless of pending-timer count (§18), which polling is not.
