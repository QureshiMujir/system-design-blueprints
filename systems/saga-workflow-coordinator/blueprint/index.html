Project Number: 97

Project Name: Saga Workflow Coordinator

Status: specification — locked

1. Goal & Scope

Build a durable, distributed workflow orchestration engine (a Temporal/Cadence-class system) that executes long-running business processes as ordinary imperative code, with: (a) event-sourced history as the sole source of truth for workflow state, (b) deterministic replay of workflow code from that history after any crash, restart, or worker migration, (c) at-least-once activity execution with caller-supplied idempotency keys — the only sense in which "exactly-once" is achievable (Treat 2015, §5), (d) automatic saga-style compensation on workflow failure or cancellation (Garcia-Molina & Salem, SIGMOD 1987, §5), and (e) horizontal scalability via consistent-hash sharding of workflow state across a fleet of history servers. Phase 0 (§12) delivers the following numbered services and libraries:

  1. wf-core — event/command/state-machine types shared by every other crate (no I/O).
  2. wf-history — sharded, single-writer-per-shard history service; owns the event log, the timer wheel, and the transfer queue.
  3. wf-matching — task-queue service; long-polls workers, holds sticky and non-sticky queues.
  4. wf-frontend — stateless gRPC gateway; auth, rate-limit, namespace routing.
  5. wf-storage — persistence adapter (Postgres default, Cassandra high-throughput, RocksDB embedded).
  6. wf-replay — deterministic-replay engine and the CI replay validator.
  7. wf-worker-sdk-rs — Rust workflow + activity worker SDK (reference implementation of the determinism contract).
  8. wf-worker-sdk-py / wf-worker-sdk-ts — Python and TypeScript worker SDKs (§21).
  9. wf-cli (wfctl) — operator CLI: start/signal/query/terminate workflows, inspect shards, admin visibility.
  10. wf-visibility — the denormalised, eventually consistent read-model index (§20).

System boundaries. Provides: durable workflow execution, saga compensation, signals, queries, timers, cron, sharded scaling, a denormalised visibility index. Delegates: the business meaning of a compensation — the engine runs the compensating activity, the application decides what "compensate" means (§16); the identity/authorization provider — the engine consumes JWT/mTLS claims, does not issue them; the durability of the underlying storage engine — Postgres/Cassandra/RocksDB's own WAL and replication, not reimplemented (§9 ADR-03). Does not provide: a general-purpose message broker; a BPMN/ASL parser (PhaseDeferred("§36")); a multi-region active-active consistency protocol (PhaseDeferred("§36")); a UI — the CLI and gRPC API are the only interfaces in scope.

Non-goals. Strict serializability across workflow + activity side effects — sagas trade this away by design (P2, §6); exactly-once delivery in the two-generals sense — proven impossible (Treat, §5); a scheduler for ephemeral batch jobs — that is Airflow's niche, not this system's (§32).

Deployment model. A cluster of stateless wf-frontend and wf-matching processes behind a load balancer; a sharded fleet of wf-history processes, each owning a partition of the consistent-hash ring via an external lease service (etcd default); an externally managed Postgres/Cassandra cluster; an externally managed Elasticsearch/OpenSearch cluster for wf-visibility; a worker fleet the operator runs, outside the control-plane trust boundary. Single-region at v1; DR via async cross-region replication (§19) with operator-triggered failover.

Target users/operators. Backend engineers writing long-running business processes (payments, fulfillment, subscription billing, human-in-the-loop approval chains) as code; SRE/on-call operators who run the control plane and respond to poison workflows, shard failovers, and compensation failures (§24, docs/runbook/).

Recommended language + rationale. Rust 1.78+ (edition 2021) for every control-plane crate (wf-core, wf-history, wf-matching, wf-frontend, wf-storage, wf-replay, wf-worker-sdk-rs). Rationale: the history hot path is a pure fold over an append-only log (§8) where allocation discipline and the absence of GC pauses directly bound p99 append latency (row hist_append_p99, §4); the determinism contract (P2, §6) is partially enforceable at compile time in Rust (the ! return type on continue_as_new, Send + 'static bounds ruling out captured non-serializable state) in a way no GC'd language offers. Rejected: Go — Temporal's own choice; mature, GC pauses are a known bounded cost Temporal accepts; rejected here because this blueprint explores the allocation-discipline end of the design space, not a repeat of Temporal's. Java — Cadence's original language; same GC argument, plus slower iteration for a from-scratch build. Elixir/Erlang — the BEAM's actor model fits the worker-supervision problem (§32) but the ecosystem lacks a mature Cassandra/Postgres driver stack at this blueprint's quality bar.

Prerequisites. Event sourcing (Fowler, §5), CQRS (Young, §5), the saga pattern (Garcia-Molina & Salem 1987, §5), CAP/PACELC (Brewer, Abadi, §5), the distinction between "exactly-once delivery" (impossible) and "exactly-once execution" (achievable via idempotency, Treat, §5), consistent hashing (Karger et al. 1997, §5), and hands-on familiarity with at least one production workflow engine (§5 Reference Implementations) sufficient to read its history-replay code path and explain a transfer queue.

Estimated timeline. Phase 0 (§12): 2–3 weeks. Full system through Phase 10 (§22) and the release gate (§27): 10–14 months. Phase 4 (§16, compensation correctness on one shard) is the first externally demoable milestone; Phase 7 (§19, multi-shard rebalance with zero data loss under fault injection) is the first milestone that earns the word "production"; the release gate (§27, 30-day soak + external fault-injection audit) is the sealing gate.

Deferred features (register at §36): BPMN/ASL DSL frontend PhaseDeferred("§36"); multi-region active-active replication PhaseDeferred("§36"); FaaS-backed activity execution PhaseDeferred("§36"); native Kubernetes operator PhaseDeferred("§36"); workflow time-travel debugger UX PhaseDeferred("§36").

2. Why Build This

  • The 2PC dead end. Distributed transactions in the strict two-phase-commit sense (Skeen & Stonebraker 1983, §5) do not scale past a handful of participants in one data centre: the blocking coordinator is a single point of failure, participant locks hold for the protocol's duration, and the model assumes a synchronous network. Every production system that pushed 2PC past four participants across regions degraded to OCC-with-reconciliation or shipped a saga instead. Building the saga's replacement shows why the field moved, not just that it did.
  • Determinism is the actually-hard part. The saga pattern (§5, §16) is conceptually simple; the hard engineering problem is guaranteeing that replaying workflow code against a fixed history produces bit-identical commands every time (§14). This is the same class of problem as deterministic lockstep in RTS-game netcode and deterministic redo logs in database recovery (ARIES) — a transferable skill, not a workflow-engine-only one.
  • Real production lineage. Temporal, Cadence, AWS Step Functions, Camunda 8 Zeebe, and Netflix Conductor (§32) converge on the same three-piece architecture — frontend / history / matching — despite different wire formats and storage engines. Understanding why they converge, not just that they did, is the calibration value: an engineer who has built this can evaluate any workflow engine's marketing claims against the invariants it must actually uphold.
  • Sharding + single-writer discipline (I3, §7; §19) is the same lease-and-fencing pattern behind every leader-elected shard in Kafka, CockroachDB, and Spanner; this blueprint is a self-contained place to get that pattern right once.
  • Compensation is a business-logic discipline, not a mechanical inverse (§16) — building this system forces the distinction between "undo" (rare, only for truly reversible operations) and "compensate" (the norm: issue a refund, not un-charge a card) that every payments/fulfillment engineer eventually internalizes the hard way.
  • Cross-links. Shares the event-sourcing/CQRS split with any CDC pipeline; shares the consistent-hash-sharding + lease/fencing pattern with distributed KV stores; shares the timer-wheel design (§18) with a network stack's retransmission-timeout subsystem; shares the deterministic-replay contract with database recovery logs (ARIES) and RTS-game lockstep networking.

What Mastery Looks Like.

  • Explain, from memory, why "exactly-once delivery" is impossible and what "exactly-once execution" actually requires of the caller (§14, §16).
  • Design a single-writer-per-shard leader-lease-and-fencing scheme for any sharded stateful service, not just this one (§19).
  • Diagnose a "wedged workflow" in a live Temporal/Cadence/Conductor cluster by reasoning about the replay contract, not by guessing (§14, §24).
  • Justify, with a derived number, why a workflow's history must be bounded and what continue_as_new costs if omitted (§18, §33).
  • Distinguish orchestration-style sagas from choreography-style sagas and state, with a real regime, when each wins (§35).
  • Write a saga compensation chain that stays safe under partial failure and partial compensation failure (§16, §24).
  • Reason quantitatively about a workflow engine's capacity ceiling — shard count, event size, replay cost — from first principles (§33).

Client. Issues the four verbs over gRPC; never talks to wf-history or wf-matching directly — wf-frontend is the only entry point (I4, §7).

wf-frontend. Stateless; horizontally scaled behind any L4/L7 balancer. Owns authn/authz, per-namespace rate limiting, and routing: shard = jump_consistent_hash(hash(namespace, workflow_id), shard_count) (ADR-04, §9). No workflow state lives here — restart is free.

wf-history. The truth. Sharded by workflow_id; each shard has exactly one writer, enforced by a lease + fencing token from the coordination service (I3, §7; ADR-20, §9). Owns the append-only event log (§8), the durable timer wheel (§18), and the transfer queue — an at-least-once internal bus for cross-shard work (child workflows, cross-workflow signals).

wf-matching. Holds task queues (one per TaskQueue name) and dispatches to polling workers via long-poll (ADR-06, §9). Sticky queues route a workflow's next task back to the worker that last executed it, avoiding a full replay on cache hit (P11, §6).

wf-storage. The persistence adapter behind wf-history and wf-visibility's write path. Postgres is the default (ADR-03, §9); Cassandra is the high-write-throughput option; RocksDB backs the embedded single-node demo mode with zero external dependencies.

Worker fleet. Operator-run, outside the control-plane trust boundary — the engine never executes application code in-process. Workflow workers replay deterministic code against history (§14); activity workers are the non-deterministic escape hatch for I/O and side effects (§15), retried at-least-once with caller-supplied idempotency keys (I7, §7).

wf-visibility. A CQRS read model (Young, §5), populated asynchronously off the transfer queue. Eventually consistent (≤ row vis_lag_p99, §4); never authoritative — on disagreement with wf-history, wf-history wins (I1, §7) and the index is rebuilt.

Three properties hold everywhere downstream: history is truth, everything else is a derived index (I1); single-writer-per-shard is non-negotiable for saga ordering correctness (I3); the workflow worker is the determinism boundary — activities are the only sanctioned non-determinism (P3, P4, §6).

6. Design Principles

  1. P1 — Workflows are code, not DSL. Orchestration logic is written in a general-purpose language (Rust/Python/TypeScript); the SDK enforces the determinism contract. Tradeoff: loses the visual-editor audience BPMN/ASL serve. Operational implication: refactoring, IDE support, and unit testing come for free. Violate it and you reinvent a worse half-language (Conductor's JSON DSL, §5 Reference Implementations).
  2. P2 — Sagas trade serializability for liveness. A saga's contract is "we will not get stuck," not "we are serializable"; intermediate states are visible and business- acceptable, never hidden behind a lock. Tradeoff: callers must tolerate partial-progress reads. Operational implication: every activity author must document what a partial saga looks like externally. Violate it and 2PC's blocking-coordinator failure mode returns (§1).
  3. P3 — Deterministic replay is the foundation, not an optimisation. Every WorkflowContext primitive is either deterministic by construction (ctx.now() reads the last recorded event_time) or recorded as a SideEffect event. Tradeoff: workflow code cannot use the ambient language runtime freely. Operational implication: a CI replay-validator gates every commit (§14). Violate it and workflows silently wedge on replay divergence (I5).
  4. P4 — Activities are at-least-once with caller-supplied idempotency keys. The SDK retries on every failure class until the retry policy says stop; the activity author is responsible for idempotency, using the engine's ActivityId as the key against downstream services. Tradeoff: activity authors carry real design burden. Operational implication: non-idempotent activities double-charge under retry. Violate it and "exactly-once" becomes "sometimes-twice" (I7).
  5. P5 — Compensations are best-effort with their own retry policy; no compensation-of-compensation. A failed compensation (after exhausting retries) ends the workflow in CompensationFailed and pages a human; we never chain "undo the undo." Tradeoff: some sagas terminate in a state needing manual reconciliation. Operational implication: a named runbook (docs/runbook/poison-workflow.md) is mandatory. Violate it and the compensation chain has no natural halting point (§16, §24 FM6).
  6. P6 — Signals are async events; queries are pure-function reads. A signal appends a SignalReceived event and mutates state on next replay; a query never appends an event and never mutates. Tradeoff: queries cannot trigger side effects, by design. Operational implication: on_query is typed &self, not &mut self (§11). Violate it and replay determinism breaks silently (§17).
  7. P7 — Time travels with the workflow. ctx.now() returns the most recent history event's event_time, never the wall clock; ctx.sleep(d) schedules a durable TimerStarted/TimerFired pair. Tradeoff: sub-second timer precision is not promised (row timer_accuracy_p99, §4). Operational implication: workflow code has no other concept of time. Violate it and replay produces different timers than the first run.
  8. P8 — Sharding by workflow ID, never by workflow type. Hashing by ID distributes load evenly; hashing by type creates hot shards for popular types. Tradeoff: cross-shard coordination (child workflows, cross-workflow signals) needs the transfer queue. Operational implication: workflow-ID naming conventions matter (§19, §24 FM8). Violate it and a handful of shards absorb all cluster load.
  9. P9 — History events are immutable; state is a deterministic fold. No event is ever modified after append; corrections are new compensating events. MutableState is fold(events), nothing else. Tradeoff: storage grows monotonically until continue_as_new. Operational implication: snapshots are optimisations of the fold, never substitutes (§22). Violate it and replay and live state diverge (I13).
  10. P10 — continue_as_new bounds history growth; cron is a workflow that calls itself. No special cron infrastructure exists; a cron workflow's body sleeps then calls ctx.continue_as_new(...). Tradeoff: cron history is bounded per-firing, not per-schedule-lifetime. Operational implication: the history-growth bound is the same problem as any long-running workflow (§18). Violate it and histories become unreplayable (row max_history_events, §4).
  11. P11 — Sticky task queues cache workflow execution state. The matching service routes a workflow's next task back to the worker that last executed it, within a sticky lease; cache hit skips replay entirely. Tradeoff: worker crash mid-lease delays the next task until lease expiry. Operational implication: tune lease duration against crash-detection latency (§22). Violate it and every task pays a full replay (row sticky_hit_rate, §4).
  12. P12 — At-least-once delivery + idempotency keys ≈ exactly-once from the application's perspective. The engine never promises exactly-once delivery (Treat, §5); it promises exactly-once effect when the idempotency-key contract is honoured. Tradeoff: the promise is only as strong as the weakest activity's idempotency implementation. Operational implication: idempotency-key discipline is documented at every activity call site. Violate it (P4 broken) and retries duplicate side effects.
  13. P13 — Workflow code never busy-loops; every wait is durable. A workflow that "waits" must ctx.sleep() or ctx.await_signal(), never spin. Tradeoff: the SDK must detect and refuse tight loops. Operational implication: the replay validator flags unbounded loops without a yield point. Violate it and a worker pins a CPU core forever.
  14. P14 — Workers are stateless except for the sticky cache. Restarting a worker is always safe; the sticky lease expires, matching re-routes, replay rebuilds the cache. Tradeoff: worker restarts cost a replay storm if many are cached. Operational implication: rolling worker deploys are safe by construction (§25). Violate it and a worker becomes a single point of failure for its cached workflows.
  15. P15 — SignalWithStart is O(1) on the happy path. The most-used production API — atomically "start or signal" — must never take a lock proportional to cluster size. Tradeoff: the atomicity is scoped to a single shard, not the cluster. Operational implication: SignalWithStart throughput is a first-class benchmark (§29 M4). Violate it and the hottest API path becomes the bottleneck.

These IDs (P1–P15) are referenced throughout; every phase's Detailed Implementation Steps cites at least one.

8.5 Malformed-input example

An ActivityTaskCompleted whose scheduled_event_id does not point at a preceding ActivityTaskScheduled in the same (workflow_id, run_id) is malformed: the state-machine fold (§13) refuses the append with AppendError::DanglingReference, the history is left unmodified, and wf_history_integrity_violation_total increments (I2). The fixture conformance/corpora/determinism/dangling_reference.json (§13) encodes this case; the expected output is a rejected append, not a panic that corrupts the shard.

8.6 Failure-path example

A four-activity saga (ReserveInventory → ChargeCard → ShipPackage → SendConfirmation, §16) where SendConfirmation exhausts its retries: the history shows ActivityTaskFailed{retry_state=Exhausted} for SendConfirmation, then three compensation activities appended and completed in reverse completion order — CancelShipment, RefundCard, ReleaseInventory (I8) — then WorkflowExecutionFailed{cause= ActivityFailure}. If RefundCard's compensation itself exhausts retries, the trace instead ends WorkflowExecutionFailed{cause=CompensationFailed} and pages on-call per the poison-workflow runbook (§25).

  • Capturing local workflow state in a compensation closure is non-deterministic on replay; the pattern is schedule_compensation::<A>(args) with args a serializable snapshot, never a captured reference (P3).

16.7 Performance Concerns

16.8 Edge Cases

  • A workflow failing before any compensation is registered — zero compensations run; WorkflowExecutionFailed fires immediately.
  • A compensation that itself schedules another compensation is rejected — compensations do not nest (P5; schedule_compensation is unavailable inside a compensation activity's context).
  • A workflow with try { ... } catch (e) { /* swallow */ } around a compensable activity — swallowing the error makes the saga believe the activity succeeded and skips its compensation; the SDK's failure types are structured so only activity-specific failures are catchable without suppressing the compensation trigger.

16.9 Failure Analysis

A failed compensation after exhausting retries leaves the saga in a known, auditable inconsistent state (CompensationFailed) rather than a silent one — history records every attempt (§8.1); blast radius is bounded to the one workflow; the poison-workflow runbook (§25) is the recovery path; forensic reconstruction is a pure read of immutable history (I13).

17.8 Edge Cases

  • A signal sent to a completed workflow is rejected WorkflowNotOpen — never silently dropped or buffered past a terminal state.
  • A query issued mid-workflow-task is queued behind the in-flight task, not raced against it (read-your-writes within one client session, ADR-08).
  • Two conflicting signal names delivered in the same millisecond order by the history's event_id order (I2), never wall-clock arrival order.

17.9 Failure Analysis

A dropped signal (network failure before the RPC is acknowledged) is a client-visible RPC failure, not a silent loss — the client must retry; once wf-frontend acknowledges, the signal is durable (I11). Detection: RPC-level error rates; no server-side data-loss mode exists once acknowledged.

17.10 Operational Notes

Emit wf_signal_received_total, wf_signal_rejected_total{reason}, wf_query_dispatch_latency_seconds{cache}. No schema/wire changes; signal/query semantics are additive to the Phase 1 event log (§13).

18. Phase 6 — Timers, Cron & Continue-As-New

18.1 Objectives

Implement durable timers backed by a hierarchical timing wheel (Varghese & Lauck, §5), cron-as-self-calling-workflow (P10), and continue_as_new (I9) to bound history growth (row max_history_events, §4).

18.2 Detailed Implementation Steps

  • Implement wf-history::timers::TimerWheel — hierarchical buckets (1s/1min/1h/1day tiers, Varghese & Lauck 1987); persist every insertion/removal so a shard failover reloads the wheel from the log, not from memory.
  • Implement tie-breaking on simultaneous deadlines via a logical sequence number (Lamport 1978, I10), never insertion/wall-clock order.
  • Implement cron_schedule parsing with a mandatory explicit timezone; compute the next fire time in the workflow's timezone, convert to UTC for wheel insertion.
  • Implement ctx.continue_as_new(input): close the current run with WorkflowExecutionContinuedAsNew, atomically open a new run with a fresh RunId referencing the prior one (I9, the ! return type from §11.4).
  • Implement per-namespace max_history_size enforcement (row max_history_events, §4) — the validator refuses further non-continue_as_new commands once the ceiling is reached (I14).

18.3 Deliverable

The timer wheel fires within timer_accuracy_p99 on a quiet host; examples/cron_workflow fires on schedule across a DST boundary; examples/long_running_subscription's CAN variant produces bounded per-run histories.

18.4 Acceptance Criteria

  • 1,000 timers with deadlines spread across 24 hours fire within timer_accuracy_p99 ≤ 100 ms (row, §4) on a quiet host.
  • A cron workflow "0 2 * * *" in a DST-observing timezone fires exactly once per calendar day across the transition (neither 0 nor 2 times).
  • 100 chained continue_as_new calls produce 100 runs, each referencing the correct parent RunId (I9).
  • Per-run history stays under max_history_events (row, §4) for 3 years of simulated subscription cycles.

18.6 Pitfalls

  • A naive "0 2 * * *" cron on a DST-observing host skips or duplicates around the transition; the parser must require an explicit timezone.
  • Timer accuracy under host clock skew: the history server's clock is the truth (§13); we promise timer_accuracy_p99 ≤ 100 ms only on a quiet host, degrading under load — state this, do not over-promise.
  • continue_as_new is not retroactive: the parent run's history remains preserved and queryable; code assuming "current state reachable from time zero" is wrong — it must follow the continued_execution_run_id chain.

18.7 Performance Concerns

The hierarchical wheel keeps insert/cancel/tick at O(1) amortized regardless of pending-timer count (row timer_capacity_shard, §4; Varghese & Lauck 1987) — a flat sorted-timer-list design degrades to O(log n)+ per tick and was rejected for this reason.

18.8 Edge Cases

  • A timer whose fire_at is already past when inserted (clock correction, replay catch-up) fires on the next tick, not retroactively at its original instant.
  • A cancelled timer racing its own fire tick loses the race if the tick already committed — the workflow observes TimerFired, not TimerCanceled, and must tolerate it.
  • continue_as_new called with a payload exceeding the payload_bytes budget (row, §4) is rejected before the old run closes, so the workflow never enters a state with no valid continuation.

18.9 Failure Analysis

A shard failover during a pending timer's window: the new owner reloads the wheel from the persisted timer log (§13), not from the dead owner's memory — no timer is lost, though an in-flight fire notification may be redelivered (idempotent on timer_id + started_event_id). Detection: wf_timer_reload_total on failover.

18.10 Operational Notes

Emit wf_timer_fire_latency_seconds, wf_timer_pending_count, wf_continue_as_new_total (I9). docs/architecture/continue-as-new.md documents the parent-chain query pattern for operators debugging "where did my workflow's history go."

19. Phase 7 — Sharding and Scaling

19.1 Objectives

Scale wf-history from one hardcoded owner (§13) to a real consistent-hash-sharded fleet with lease-based single-writer ownership and graceful/forceful rebalancing (P8, I3, ADR-04, ADR-20).

19.2 Detailed Implementation Steps

  • Implement shard_for(workflow_id, total_shards) = jump_consistent_hash(xxh3_64( workflow_id), total_shards) (Karger 1997; Lamping & Veach 2014) at wf-frontend::routing (ADR-04).
  • Implement ShardLease acquire/renew against etcd (§11.5); every append carries the current fencing_token; a stale token is rejected (I3).
  • Implement graceful rebalance: the old owner drains in-flight workflow tasks (≤ shutdown_grace, row §4) before releasing the lease; the new owner acquires, replays open workflows' MutableState from history, resumes.
  • Implement forceful rebalance: lease expiry (10 s default) on owner death; fence the dead owner's writes before the new owner proceeds.
  • Implement the transfer queue: an at-least-once internal bus for cross-shard work (child workflow starts, cross-workflow signals) with dedup on (source_shard, event_id).
  • Implement async cross-cluster replication for DR: a per-shard stream tagged (source_cluster, shard_id, event_id) for destination-side dedup/ordering; failover is operator-triggered only (non-goal: automatic cross-region failover, §1).

19.3 Deliverable

A 4-history-server, 1,024-logical-shard cluster runs the full conformance suite end-to-end; a killed shard owner fails over within shard_failover_rto with zero data loss; adding a history server triggers a rebalance that moves shards without corrupting history.

19.4 Acceptance Criteria

  • Shard failover completes within shard_failover_rto ≤ 30 s (row, §4) with zero workflow data loss over 50 induced failovers.
  • A rebalance triggered by adding a history server, run concurrently with 10,000 in-flight workflows, completes with every workflow finishing correctly.
  • A partitioned old shard owner's writes are rejected 100% of the time once its fencing token is stale, verified by a partition-injection fixture.
  • wf_start_tp_cluster ≥ 18,000/s (row, §4) on the 4-process, 1,024-shard reference cluster.

19.5 Conformance Fixtures

Fixture Purpose Expected Output

19.6 Pitfalls

  • Sharding by WorkflowId alone collides if a popular literal ID (e.g. "singleton") is reused across tenants — lint/document a high-cardinality-component requirement (P8).
  • Shard-ownership churn produces replay storms — the sticky-cache hit rate (row sticky_hit_rate, §4) plummets temporarily; plan for ~2× dispatch latency for 60 s post-rebalance.
  • Skipping the fencing-token check "since partitions are rare" lets a partitioned old leader write for the duration of its TCP timeouts — the check costs one extra column read per append and is non-negotiable (I3).

19.7 Performance Concerns

Shard count is fixed at cluster-creation time (1,024 or 16,384 typical); resharding (hot- shard split) is deferred (PhaseDeferred("§36")) — the mitigation until then is over-provisioning shard count relative to expected hot-key skew (§30).

19.8 Edge Cases

  • A child workflow started on a different shard than its parent may be redelivered by the at-least-once transfer queue; dedup on (source_shard, event_id) prevents a duplicate child.
  • A rebalance racing a continue_as_new — the new run lands on the shard computed from the unchanged workflow_id, so a CAN never causes a mid-flight shard jump.
  • Cross-region replication lag exceeding the DR decision window is documented: failover is operator-triggered specifically so a human can assess recent-data loss before cutover.

19.9 Failure Analysis

A network partition isolating a shard's owner from etcd for longer than the lease TTL causes the owner to self-fence (stop accepting appends) even before a new owner is elected — "fail closed" is preferred over a partitioned owner serving stale reads. Detection: wf_shard_lease_lost_total; recovery is automatic once connectivity restores.

19.10 Operational Notes

Emit wf_shard_owner_changes_total, wf_shard_fence_reject_total (I3), wf_rebalance_duration_seconds. docs/runbook/shard-failover.md walks the operator through confirming a failover completed cleanly via the shard-ownership dashboard.

20. Phase 8 — Visibility Store

20.1 Objectives

Implement the CQRS read model (Young, §5): a denormalised, eventually consistent index for "list/search workflows by status/type/time/custom attributes" (I1, ADR-15).

20.2 Detailed Implementation Steps

  • Implement wf-history::visibility_writer — an async consumer of the transfer queue (§19) projecting lifecycle events into the visibility schema: namespace, workflow_id, run_id, workflow_type, task_queue, start_time, close_time, status, search_attrs, memo, history_length, history_size_bytes.
  • Implement ctx.upsert_search_attributes({...}) — appends a marker event the visibility writer projects into indexed search_attrs (JSON).
  • Implement the query DSL (WHERE customer_id = "C42" AND start_time > NOW() - INTERVAL '24 HOURS') translated to Elasticsearch (default, ADR-15) or Postgres JSONB (small- deployment alternative).
  • Implement per-namespace scoping at wf-frontend: every visibility query is scoped to the caller's namespace at the frontend layer, never left to the backend query (§23 T8).
  • Implement a reconciliation job comparing wf-visibility counts against wf-history per namespace, alerting on drift beyond a threshold (I1).

20.3 Deliverable

ListWorkflows supports filtering by workflow_type, status, time range, and custom search attributes; every completed workflow appears in the index within vis_lag_p99.

20.4 Acceptance Criteria

  • A property test asserts every completed workflow appears in ListWorkflows(WHERE status = Completed) within 5 s, over 1,000 sampled completions.
  • A cross-tenant query without an explicit namespace filter is rejected at wf-frontend 100% of the time over 1,000 fuzzed queries (§23 T8).
  • The reconciliation job flags drift > 0.1% between wf-visibility and wf-history counts within one 5-minute reconciliation cycle.

20.9 Failure Analysis

An extended visibility-store outage degrades or fails ListWorkflows; wf-history and workflow execution are unaffected (I1). 21. Phase 9 — Multi-Language SDK (Python + TypeScript)

21.1 Objectives

Port the determinism contract (§14) to Python (wf-worker-sdk-py) and TypeScript (wf-worker-sdk-ts), each enforcing it via language-appropriate mechanisms, with cross-SDK conformance — identical histories for identical inputs across all three SDKs.

21.2 Detailed Implementation Steps

  • Implement wf-worker-sdk-py on asyncio: install a deterministic event loop intercepting asyncio.sleep, time.time, random.random; override asyncio.gather to resolve in submission order on replay (P3).
  • Implement the Python validator: run dis.dis on the workflow function's bytecode, flag banned calls (time.time, random.random, os.environ, open, socket.*); replay the last 100 production histories in CI (ADR-18 parallel).
  • Implement wf-worker-sdk-ts inside a V8 isolate (isolated-vm): no Node process, no fs, no net; seal the isolate's globals (Object.freeze(globalThis)) so workflow code cannot reach the host's Date.now().
  • Implement workflow.parallel(...) in TypeScript with deterministic resolution order (the Promise.all non-determinism fix, mirroring Python's gather override).
  • Mandate RFC 8785 (JCS) canonical JSON for any cross-SDK payload — json.dumps and JSON.stringify order object keys differently by default (§5 RFCs).
  • Share one conformance/corpora/determinism/ corpus across all three SDKs' CI pipelines; assert bit-identical command lists for identical input histories.

21.3 Deliverable

Python and TypeScript SDKs run examples/payments_saga end-to-end; a workflow defined once and re-implemented in each SDK produces identical histories for identical inputs.

21.4 Acceptance Criteria

  • Cross-SDK conformance: the shared corpus produces byte-identical command lists across Rust, Python, and TypeScript implementations, 100% of ≥ 50 shared scenarios.
  • The Python validator rejects a workflow calling time.time() directly (bytecode- inspection catch, verified by a dedicated negative test).
  • The TypeScript isolate's sealed globals make Date.now() structurally unreachable — verified by observing a ReferenceError, not a runtime policy check.
  • asyncio.gather/workflow.parallel resolve in submission order on 100 replayed traces with intentionally reordered completion timing.

  • Mixed-SDK deployments (one namespace running Python and TypeScript workflows) are supported — the wire contract (protobuf history) is SDK-agnostic (ADR-02).

21.9 Failure Analysis

A cross-SDK determinism divergence (Python and Rust implementations of "the same" workflow logic produce different commands for identical input) is caught by the shared conformance corpus in CI before merge — a CI-time failure class, not a production one, provided the corpus has adequate scenario coverage; expanding the corpus is the standard mitigation for a divergence found in production.

22. Phase 10 — Performance Hardening & Release Gate

22.1 Objectives

Harden performance to the full §4/§29 target set; implement sticky caching, batched appends, pipelined activity dispatch, snapshot+delta compaction; run the 24-hour and 30-day soak plus the external fault-injection audit that gates release (§27, §28).

22.2 Detailed Implementation Steps

  • Implement sticky task queues (P11, ADR-09): matching routes a workflow's next task to its last worker within a 1-minute lease; cache-miss falls back to full replay (§14).
  • Implement batched history appends: wf-history batches event appends per shard per 5 ms window, turning N commands into one transaction instead of N (§13 groundwork).
  • Implement pipelined activity dispatch: eagerly push ActivityTaskScheduled to wf-matching before the workflow task's response is fully acknowledged, dropping per-activity dispatch from two RPC RTTs to one.
  • Implement snapshot+delta compaction (ADR-11): materialise a MutableState snapshot every 1,000 events; replay loads snapshot+delta; a checksum mismatch falls back to full-history replay (§11.5).
  • Run the 24-hour soak (soak/workloads, .github/workflows/soak.yml) and, at release-gate time, the 30-day soak plus an external Jepsen-style fault-injection audit (§27, §28).

22.3 Deliverable

The reference cluster meets every §29 M-table target; the 24-hour soak passes with zero data loss and no memory growth; audits/soak/ and audits/jepsen/ hold the evidence the release gate (§27) checks for.

22.4 Acceptance Criteria

  • Sticky cache hit rate ≥ 95% (row sticky_hit_rate, §4) on a 100,000-active-workflow benchmark.
  • p99 activity dispatch latency ≤ 50 ms (row act_dispatch_p99, §4) on the healthy reference cluster.
  • Workflow start throughput ≥ 5,000/s per wf-history process (row wf_start_tp, §4) on benchmark hardware.
  • A 100,000-event workflow replays in ≤ 1 s using snapshot+delta (row replay_100k_p99, §4).
  • 24-hour soak: zero data loss, no unbounded memory growth (heap high-water mark within 10% across the run).

23. Threat Model

23.1 Trust boundaries

  1. Caller boundary. The caller supplies workflow/activity code, retry policies, and signals; the engine trusts caller code to honour the determinism contract (P3) — the validator + sandbox (§14, §21) catch most violations.

  3. Shard boundary. Each shard has one writer; fencing token + lease enforce it (I3).
  4. Network boundary. All gRPC is TLS by default; authentication is per-namespace (JWT or mTLS, I4).

Metrics. Every wf_* counter/histogram introduced per-phase (§12–§22) is Prometheus- exposed with namespace, shard_id, and (where applicable) activity_type/workflow_type labels, budgeted to avoid label-cardinality blowup (namespace × type, never × workflow_id).

Tracing. OpenTelemetry spans per workflow task and per activity attempt; trace correlation key is (workflow_id, run_id, event_id) so a trace reconstructs directly from history (I1).

Structured logging. One JSON line per RPC and per append, carrying workflow_id, run_id, namespace, shard_id; no unstructured println!-style logging in any control-plane crate.

Dashboards. Cluster health (shard ownership, lease age), workflow health (start/ complete/fail rates), activity health (retry/exhaustion rates), replay health (divergence rate) — one dashboard per §3 architectural box.

Alerting philosophy. Page on invariant-violation telemetry (I1–I14) and on SLO burn against any §4/§29 row; ticket (not page) on capacity-trend warnings (e.g. approaching max_history_events).

SLOs. Control-plane availability 99.95% (row availability_budget, §4); p99 dispatch latency SLOs mirror §4/§29 directly — no separate SLO numbers invented.

Incident response. Severity tied to blast radius: single workflow (FM1/FM2/FM5) → low severity, ticket; single shard (FM3/FM4) → medium, page one on-call; cluster-wide (FM9, a widespread T1 regression) → high, page the full rotation. The on-call rotation owns docs/runbook/.

Named runbooks. triage.md (first-response triage tree), shard-failover.md (FM4), poison-workflow.md (FM1/FM2/FM5), visibility-rebuild.md (FM6) — all under docs/ runbooks/ (§10).

Backup/restore. Postgres/Cassandra native backup (ADR-03) plus daily full + continuous WAL/commit-log shipping; a quarterly restore drill validates the backup is actually restorable, not just taken.

Deployment topology. Control plane single-region at v1 (§1); worker fleet operator-managed and may span regions.

Canary / rolling-upgrade / rollback / migration. wf-history upgrades are rolling, one shard-owner at a time, behind the graceful-rebalance path (§19); worker upgrades are rolling by nature (P14 — workers are stateless except the sticky cache); schema migrations follow §26.

26. Compatibility & Versioning

  • Wire compatibility. Protobuf reserved-field discipline (ADR-05); HistoryEventKind/ Command (§11) evolve additive-only — new variants, never removed/renumbered fields.
  • Storage compatibility. wf-storage schema migrations are additive and forward- compatible; schema.rs (§10) versions the Postgres/Cassandra DDL.
  • Workflow-code schema evolution. getVersion(change_id, min, max) markers (ADR-16) are the only sanctioned mechanism; the replay-validator CI gate (ADR-18) enforces it.
  • API stability. The gRPC service versions by namespace-scoped feature flags, not URL versioning; a breaking change requires a new RPC method, with the old one deprecated per the policy below.
  • Migration tooling. wfctl admin drives schema/mapping migrations (e.g. visibility mapping changes, §20); each component's migration procedure is documented in docs/.
  • Deprecation policy. A deprecated RPC/field is marked in docs/api/, kept for ≥ 2 minor releases, removed only in a major release with a BLUEPRINT_LOG.md entry.
  • SemVer policy. Control-plane crates follow SemVer; a MAJOR bump is required for any wire- or storage-incompatible change. Worker SDKs (Rust/Python/TypeScript) follow SemVer independently per language-ecosystem convention.
  • Rolling-upgrade guarantees. Mixed-version wf-history processes may coexist during a rolling upgrade within one minor-version skew; the fencing-token mechanism (I3) makes concurrent-version shard ownership safe by construction — an old and new binary never both believe they own the same shard.

30. Scalability Analysis

Constant regardless of cluster size. Per-workflow sticky-cached memory footprint (row history_mem_per_wf, §4, ≤ 8 KB) is O(1); history-append latency (hist_append_p99) is O(1) in shard count because each shard has exactly one writer (I3) — it does not degrade as the cluster grows.

Grows with cluster size. Aggregate throughput grows with shard count up to the storage tier's ceiling (§33); visibility-index size grows O(n) in total workflow count; transfer-queue traffic grows with the fraction of workflows using child workflows or cross-workflow signals — the direct rationale for P8's "avoid cross-shard coordination where possible."

Named bottlenecks, in order. (1) Storage-layer commit throughput (Postgres/ Cassandra) — the true ceiling behind M1/M2 (§29). (2) The coordination service (etcd) under high shard-churn (many simultaneous lease renewals) — mitigated by staggered renewal jitter. (3) The visibility store's ad-hoc-query capacity under a pathological query (T12, §23). (4) A single hot shard from low-cardinality workflow-ID naming (§19, P8).

Horizontal scaling. Add wf-history processes and rebalance shards (§19) — the primary lever. Add stateless wf-matching/wf-frontend replicas (P14) — trivial. Add Elasticsearch/OpenSearch nodes for visibility — standard for that technology.

Vertical scaling. Faster storage (NVMe, larger Postgres/Cassandra buffer cache) directly raises the storage-layer ceiling — the single highest-leverage vertical lever given bottleneck (1) above.

Sharding/partitioning. Consistent-hash sharding (ADR-04) is the only partitioning scheme; shard count is fixed at cluster-creation time. Resharding (splitting a hot shard) is deferred (PhaseDeferred("§36")) — today's mitigation for shard skew is over-provisioning shard count relative to expected key-cardinality skew, not dynamic resharding.

Coordination overhead. Shard-lease renewal against etcd (§19) is the only per-shard steady-state coordination cost; it is O(shard count) in aggregate etcd load, which is why very large shard counts (> 16,384) need etcd itself scaled or the renewal interval lengthened.

Practical ceiling and levers beyond it. At the reference cluster's storage tier, the practical ceiling is the aggregate commit throughput of the Postgres/Cassandra tier (§33 derives the number). Beyond it: migrate to Cassandra (ADR-03) for horizontally-scalable write throughput; implement resharding (deferred) to reduce hot-key skew; or federate namespaces across independent clusters — at the cost of losing cross-namespace ListWorkflows in one query (§20).

31. Mental Models & First Principles

  • MM1 — A workflow is a deterministic replay of a program against a growing log, not a running process. Predicts: worker crashes and restarts are non-events. Bug class without it: engineers assume in-memory state survives a crash, then are shocked when a global variable resets. Applies in §14.
  • MM2 — History is truth; every other store is a cache with a name. Predicts: any disagreement between wf-visibility and wf-history resolves in history's favor. Bug class without it: operators debug the read model when the bug is upstream, or "fix" data by writing directly to the derived index. Applies in §3, §20.
  • MM3 — Compensation is an apology, not an undo. (Helland, §5.) Predicts: every compensation is a new forward action with its own failure mode, never a free rollback. Bug class without it: engineers write a compensating activity assuming it can always succeed instantly, then get paged when the downstream API is down. Applies in §16.
  • MM4 — A shard is a single-threaded program wearing a distributed system's clothes. Predicts: correctness reasoning inside one shard can use ordinary sequential logic; only cross-shard interactions need distributed reasoning. Bug class without it: engineers add unneeded locks inside a shard's fold, or wrongly assume sequential reasoning holds across shards. Applies in §13, §19.
  • MM5 — Idempotency keys turn "at least once" into "effectively once" — only as far as the weakest link. Predicts: a system's exactly-once claim is only as strong as its least-idempotent downstream call. Bug class without it: teams celebrate an "exactly-once" architecture while one activity silently double-charges because its downstream API ignores the idempotency key. Applies in §14, §15.
  • MM6 — Every timer is a promise the log keeps, not the clock. Predicts: timer accuracy is bounded by the log-owning shard's health, not by absolute wall-clock precision. Bug class without it: engineers expect microsecond timer precision from a system whose actual contract is "best-effort within 100 ms." Applies in §18.
  • MM7 — Sticky caching is an optimisation on a system already correct without it. Predicts: disabling all caching should change latency, never correctness. Bug class without it: engineers accidentally make correctness depend on cache presence, producing "works until the worker restarts" bugs. Applies in §14, §22.
  • MM8 — A saga's atomicity is a narrative, not a lock. Predicts: intermediate saga states are visible to the rest of the system and must be designed for, not hidden. Bug class without it: downstream systems (e.g. a reporting dashboard) assume "in progress" never appears and break the first time a saga runs long. Applies in §2, §16.

33. Back-of-Envelope Capacity Model

Every number below is derived from the §4 constraint table; none is asserted standalone.

C1 — History size of a typical saga. examples/payments_saga (4 activities) has ≈ 29 events (1 WorkflowExecutionStarted + 4 × (3 workflow-task + 3 activity events) + 1 WorkflowExecutionCompleted, rounding). 10 of those carry a payload (the activity Scheduled/Completed pairs plus start/complete), 19 do not: bytes = 19 × event_bytes + 10 × (event_bytes + payload_bytes) = 19×180 + 10×692 = 3,420 + 6,920 = 10,340 bytes ≈ 10 KB.

C2 — Max-history byte budget cross-check. max_history_events × (event_bytes + payload_bytes) = 50,000 × 692 = 34,600,000 bytes ≈ 34.6 MB, against max_history_bytes = 50 MB (row, §4) — 15.4 MB (31%) headroom, confirming the two ceilings in §4 are mutually consistent rather than independently asserted.

C3 — Why snapshot+delta is required for M10. Assume a measured pure-fold rate of ~50,000 events/s (≈ 20 µs/event: protobuf decode + assertion checks, §13). A naive full replay of a 100,000-event history costs 100,000 / 50,000 = 2 s — 2× over M10's 1 s target. With snapshot+delta (ADR-11, snapshot every 1,000 events), replay loads the snapshot (O(state), not O(events)) and replays only the tail: 1,000 / 50,000 = 20 ms — 50× inside the target. This is the arithmetic reason Phase 10 (§22) is mandatory, not optional polish.

C4 — FD budget vs. shard fan-out. 256 shards/process × 2 storage-pool connections/ shard = 512 FDs, plus ~50 internal service-mesh connections and ~16 pooled etcd lease-watch connections ≈ 578 FDs, against fd_budget_history = 16,384 (row, §4) — ~28× headroom before FD exhaustion becomes the binding constraint ahead of other resources.

C5 — Timer-wheel memory footprint. timer_capacity_shard = 500,000 pending timers/ shard × 256 shards/process × ~64 bytes/timer-entry (timer_id + fire_at + workflow reference) = 500,000 × 256 × 64 = 8,192,000,000 bytes ≈ 7.6 GB per process, against a 32 GB history host (§4 reference cluster) — ~24% of host RAM at full timer utilization, leaving ~24 GB for MutableState caching, storage client buffers, and OS overhead.

C6 — Aggregate sticky-cache demand. max_concurrent_wf × history_mem_per_wf = 1,000,000 × 8 KB = 8 GB aggregate across the worker fleet (sticky cache lives on workers, not wf-history, §3) if every open workflow were cached simultaneously. Because sticky_hit_rate (M7) targets ≥ 95%, not 100%, and the 1-minute lease (ADR-09) evicts idle entries, the realistic resident set at any instant is the active fraction within one lease window, not the full 1,000,000.

C7 — Storage amplification. A narrow, high-frequency insert (one events row) with 2 secondary indexes writes: the heap tuple + its WAL record + 2 index entries + their WAL records. Empirically this class of Postgres workload lands at 1.2–1.4× physical-to-logical bytes — storage_amp ≤ 1.3× (row, §4) is the defensible mid-point, gated by benchmarks/ (§29), not a purely theoretical figure.

C8 — Task-queue load implied by M1. At M1 = 5,000 workflow starts/s per process, each start's first workflow task alone implies ≥ 5,000 dispatches/s that wf-matching must sustain for that process — the floor wf-matching's long-poll queue depth and worker-poll concurrency (§15) must be provisioned against, before counting subsequent activity/task rounds.

C9 — Deriving M1 from hist_append_p99 + batching. An unbatched serial single-shard writer is capped at 1 / hist_append_p99 = 1 / 0.010 s = 100 appends/s. Batching (§22) groups concurrent commands from a process's 256 co-located shards into one commit per 5 ms window; assuming ~25 concurrent single-event commands per window (a conservative, storage-side estimate): 25 commands / 0.005 s = 5,000/s — exactly M1's target, and the reason M1 is only achievable after the Phase 10 batching optimisation (§22), not from the unbatched Phase 1 path (§13) alone.

C10 — Deriving M2 (cluster) from M1 (process). Naive linear scaling: 4 processes × 5,000/s = 20,000/s. Subtracting ~10% for coordination overhead (etcd lease contention, transfer-queue cross-shard traffic for child workflows/signals, §19): 20,000 × 0.9 = 18,000/s — exactly M2's target (row wf_start_tp_cluster, §4).

35. Alternative Architectures (Roads Not Taken)

Alt. 1 — Choreography (event-driven sagas, no central coordinator).

  OrderSvc --(OrderPlaced)--> bus --> InventorySvc --(Reserved)--> bus
     ^                                     |                        |
     |                                     v                        v
     +---(RefundIssued)<-- PaymentSvc <---(Reserved)--- bus <--(Charged)

Regime where it wins: highly decoupled microservice ecosystems with no single team owning the end-to-end process, where adding a participant should never require touching a central definition. Real system: Eventuate Tram Sagas (Chris Richardson, §5) implements this pattern directly. Rejected here because as step count grows, choreography's implicit control flow — spread across N services' individual event handlers — has no single place to read "what happens on failure," directly contradicting P1 (workflows are code, one place to read) and I1 (one source of truth).

Alt. 2 — Snapshot-only state store (no retained event log).

  saga_state table:  [ saga_id | phase | payload | updated_at ]  — updated in place,
                     no history of prior phases retained after each transition.

Regime where it wins: ephemeral, short-lived task orchestration where audit/replay/ time-travel debugging has zero value and storage cost dominates every other concern — a crashed workflow is simply restarted from scratch rather than resumed exactly. Real system: the plain relational "current-state" saga table Richardson (Ch. 4, §5) describes as the simplest possible orchestration implementation, without event sourcing. Rejected here because without an immutable log, replay-based crash recovery (P3) and time-travel debugging are structurally impossible — a mid-flight crash loses exactly which activities completed, forcing either data loss or a hand-rolled recovery log that reinvents event sourcing badly (I1, I9).

Alt. 3 — Polling-based timers (no timer wheel).

  Poller (fires every N seconds) ──▶ SELECT timer_id, workflow_id FROM timers
                                      WHERE fire_at <= now() AND fired = false

Regime where it wins: very low timer volume and low-precision requirements, where operational simplicity (a single indexed SQL query) outweighs the CPU/DB-load cost of polling — a small deployment with a handful of cron workflows and no SLA on timer_accuracy_p99. Real system: the naive polling approach Varghese & Lauck (1987, §5) explicitly benchmark their hierarchical timing wheel against. Rejected here because polling frequency trades directly against both database load and timer accuracy (row timer_accuracy_p99, §4); at timer_capacity_shard scale (§33 C5) a poll-based design needs either a very tight interval (high DB load) or much worse than 100 ms accuracy — the wheel is O(1) amortized regardless of pending-timer count (§18), which polling is not.

37. Glossary

  • Activity — A unit of non-deterministic work (I/O, side effects) executed by an activity worker; retried at-least-once (§15).
  • ActivityContext — SDK handle inside an activity exposing activity_id, attempt, heartbeat, deadline (§11).
  • ActivityId — Engine-assigned UUID identifying one activity invocation; doubles as the idempotency key (I7).
  • ASL (Amazon States Language) — The JSON DSL AWS Step Functions uses to define workflows as state machines (§5, §32).
  • At-Least-Once Delivery — A delivery guarantee that may redeliver but never silently drops; the engine's actual guarantee for activities and signals (I6, I11).
  • BPMN 2.0 — The XML-based visual workflow notation Camunda Zeebe uses as its source of truth (§5, §32); this design's deferred DSL frontend target (§36).
  • CAP Theorem — The impossibility of simultaneous Consistency, Availability, and Partition tolerance; informs the CP-history/AP-visibility split (§4, §32).
  • Choreography (saga) — A coordination style where each service reacts to prior events with no central coordinator (§35); rejected here in favor of orchestration (P1).
  • Command — The workflow worker's sole output, translated into history events on append (§8.2, §11.3).
  • Compensating Transaction — An activity that semantically reverses (not literally undoes) a prior activity's business effect (§16).
  • Compensation — The reverse-completion-order execution of compensating transactions on workflow failure or cancellation (I8, §16).
  • Consistent Hashing — The scheme (Karger et al. 1997) mapping workflow IDs to shards with minimal disruption on shard-count change (§19, ADR-04).
  • Continue-As-New (CAN) — The API closing the current run and opening a fresh run with a new RunId, bounding history growth (P10, I9, §18).
  • CQRS — Command Query Responsibility Segregation; the write model (wf-history) and read model (wf-visibility) are separate stores (§5, §20).
  • Cron Workflow — A workflow whose body sleeps then calls continue_as_new, providing cron semantics with no separate scheduler (P10, §18).
  • Dead Letter — The terminal destination for an activity/compensation that exhausted retries, requiring manual intervention (§15, §24).
  • Determinism Contract — The requirement that identical history produces an identical command list from workflow code (I5, P3, §14).
  • Determinism Validator — The CI component replaying recent production histories against proposed code to catch determinism violations before merge (ADR-18, §14).
  • Event Sourcing — Storing state as an append-only sequence of events and deriving current state by folding them (Fowler, §5; §8, §13).
  • Exactly-Once Execution — The application-observable guarantee achieved via at-least-once delivery + an idempotency key; distinct from impossible "exactly-once delivery" (Treat, §5; I7).
  • Fencing Token — A monotonically increasing epoch attached to a shard lease; rejects writes from a stale former owner (I3, §19).
  • Hard Question — A staff-level self-examination question requiring synthesis of ≥ 2 sections of this document (§34).
  • HistoryEvent — One immutable, monotonically ordered record of a workflow state transition (§8.1, §11.2).
  • History Service (wf-history) — The sharded, single-writer component owning the append-only event log, timers, and transfer queue (§3, §13).
  • Hybrid Logical Clock — A clock combining physical time and a logical counter for cross-node event ordering (Kulkarni et al., §5); deferred cross-region time source (§36).
  • Idempotency Key — A caller- or engine-supplied token ensuring a retried operation has effect at most once downstream (I7, ADR-14).
  • Jump Consistent Hash — The specific consistent-hashing algorithm (Lamping & Veach
    1. used to compute shard_for(workflow_id) (§19, ADR-04).
  • Long-Poll — A dispatch technique where a worker's poll RPC blocks (up to 60 s) until work arrives, avoiding tight poll loops (ADR-06, §15).
  • MutableState — The folded, in-memory representation of a workflow's current state, derived purely from its history (I1, §11.5).
  • Namespace — The tenancy/authorization scope every workflow, task queue, and visibility query is bound to (§11.1, §20).
  • Orchestration (saga) — A coordination style with a central coordinator holding the control flow explicitly, as code (§1, P1); this design's chosen style.
  • Poison Workflow/Activity — A workflow or activity that deterministically and repeatedly fails, requiring operator intervention (§24).
  • Query — A synchronous, side-effect-free read of a workflow's current state; produces zero history events (P6, I12, §17).
  • Replay — Re-executing workflow code against a fixed history to reconstruct state or verify determinism (§14).
  • Retry Policy — The per-activity configuration (initial interval, backoff coefficient, max interval, max attempts, non-retryable errors) governing retries (§11.5, ADR-12).
  • RTO (Recovery Time Objective) — The maximum acceptable time to resume service after a failure (row shard_failover_rto, §4).
  • Saga — A sequence of local transactions with compensations such that any prefix can be unwound to a business-acceptable state (Garcia-Molina & Salem 1987, §5; §16).
  • SBOM (Software Bill of Materials) — A machine-readable inventory of a build's dependencies, generated per release (§28).
  • Shard — A partition of the consistent-hash ring owned by exactly one wf-history process at a time (I3, §19).
  • Shard Lease — The time-bounded ownership grant a history server holds for a shard, renewed against etcd (§11.5, §19).
  • Side Effect (ctx.side_effect) — A one-off non-deterministic computation recorded once in history and replayed thereafter (P3, §8.1).
  • Signal — An asynchronous, durably ordered event delivered to a running workflow (P6, I11, §17).
  • SignalWithStart — The atomic "signal if running, else start with the signal buffered" API (P15, I11, §17).
  • Single-Writer (per shard) — The invariant that exactly one process may append to a given shard's history at a time (I3, §7).
  • Snapshot+Delta Compaction — Materialising periodic MutableState snapshots so replay loads snapshot + tail instead of the full history (ADR-11, §22).
  • Sticky Task Queue — A matching-service routing rule sending a workflow's next task back to the worker that last executed it, avoiding replay on a cache hit (P11, ADR-09, §14).
  • Task Token — An opaque handle identifying one in-flight activity attempt, used to complete/fail exactly that attempt (§15).
  • Timer Wheel — A hierarchical data structure (Varghese & Lauck 1987) providing O(1) amortized timer insert/cancel/tick regardless of pending-timer count (§18).
  • Transfer Queue — The at-least-once internal bus carrying cross-shard work (child workflow starts, cross-workflow signals) (§3, §19).
  • Two-Phase Commit (2PC) — The classical blocking distributed-transaction protocol this system's saga model replaces for cross-service consistency (§1, §5).
  • Visibility Store (wf-visibility) — The eventually consistent, denormalised CQRS read index for listing/searching workflows (§20).
  • Workflow — A durable, replay-based execution of application-defined orchestration code (§1, §11.4).
  • WorkflowContext — The SDK handle giving workflow code access to deterministic primitives (now, random, sleep, execute_activity, …) (§11.4).
  • WorkflowId — The caller-supplied, stable identifier for a logical workflow, unique per namespace while a run is open (§11.1).
