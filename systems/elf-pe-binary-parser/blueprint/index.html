333 — ELF/PE Binary Parser from Scratch

Project Number: 333

Project Name: ELF/PE Binary Parser from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build a byte-precise, bounds-checked parser for the two dominant executable container formats — ELF (Linux/Unix) and PE/COFF (Windows) — that turns an untrusted byte image into a typed, queryable object model: headers, sections, segments, symbols, relocations, dynamic-linking metadata, imports/exports, and (minimal) debug info. Input = a file/&[u8]; output = an immutable BinaryImage model + a CLI (binparse) that dumps it (readelf/dumpbin-style) and re-serializes headers for round-trip checks.

In scope: ELF32/64 (LE/BE), PE32/PE32+ (+ COFF object files); section/segment tables; symbol tables (.symtab/.dynsym, COFF symbols); relocations (REL/RELA, PE base relocs); dynamic section + DT_*; import/export/IAT (PE) + DT_NEEDED/PLT-GOT (ELF); program headers/segments; note/build-id; minimal DWARF + CodeView locators (offsets only, not full debug parse). Zero-copy where safe; full validation of every offset/size.

Explicit non-goals: Mach-O (PhaseDeferred("§Deferred Features Register — Mach-O")); full DWARF/CodeView line+type parsing (PhaseDeferred("§Deferred Features Register — DWARF full parse")); disassembly — handed to #334 (§1 non-goal); loading/relocating into memory — that is #76 Linker/Loader (§1 non-goal); writing/patching binaries beyond header round-trip (PhaseDeferred("§Deferred Features Register — Binary patching")); signature/Authenticode verification (PhaseDeferred("§Deferred Features Register — Authenticode")).

Deployment model: a library crate (binparse-core) + thin binparse CLI. Embeds beneath a disassembler (#334), debugger (#74), or loader (#76).

Target users: reverse-engineering / security tooling authors; loader/linker engineers; learners building the RE pipeline 333→334→335.

Phase 0 deliverable (crates/modules):

  1. bp-types — BinaryImage, Section, Segment, Symbol, Reloc, Arch, Endian, error enum.
  2. bp-read — bounds-checked cursor / zero-copy reader (Reader, Span).
  3. bp-elf — ELF header + section/program headers.
  4. bp-pe — DOS+NT headers + section table.
  5. bp-cli (binparse) — detect format, parse headers, dump.

Later phases unlock: symbols (Phase 2/§14), relocations (Phase 3/§15), ELF dynamic + versioning (Phase 4/§16), PE imports/exports (Phase 5/§17), notes + unwind (Phase 6/§18), unified model + queries (Phase 7/§19), hardening/fuzz (Phase 8/§20), differential/soak/release (Phase 9/§21), triage (Phase 10/§22), archives (Phase 11/§23), public API/C-ABI (Phase 12/§24).

Timeline: Phase 0 = 6–14 weeks; full = 4–6 months.

Recommended language: Rust (edition 2021, ≥1.78). Rationale: (a) parses hostile, attacker-controlled bytes → memory safety without a GC is decisive; (b) slices + lifetimes give true zero-copy views with compile-time aliasing safety; (c) exhaustive enum + match model the format's tagged unions precisely; (d) cargo fuzz/Miri cover the malformed-input surface this project lives on; (e) no runtime → embeddable in any RE tool. Locked ADR-001.

Prerequisites: ELF & PE/COFF specs; virtual vs file offsets (RVA, p_vaddr/sh_offset); linking/loading basics; two's-complement + endianness; relocation semantics; Rust ownership/lifetimes + slice safety.

2. Why Build This

  • Unique knowledge: how programs are physically laid out on disk — the contract between compiler, linker, and loader. Every debugger, disassembler, AV scanner, profiler, and ld starts here.
  • Historical/architectural: ELF (System V ABI, 1990s) and PE (COFF descendant) are the two formats the world's binaries ship in; understanding both demystifies cross-platform tooling.
  • Engineering muscles: defensive parsing of untrusted input; offset/size arithmetic without overflow; zero-copy view design; tagged-union modeling; differential validation against readelf/objdump/dumpbin.
  • Production concepts: bounds checking, integer-overflow safety, fuzzing, deterministic parsing, RVA↔offset translation, string-table handling.
  • Cross-links: #334 Disassembler (primary consumer — needs sections+symbols+entry), #335 Decompiler, #76 Linker/Loader (inverse: consumes relocations/symbols), #74 Debugger / #75 Profiler (symbolization), #228 Binary Exploitation (parses victims), #247 Bytecode Verifier (sibling: structural validation), #173 Image Codec (sibling binary-format parser).
  • Calibration: after this you can read any binary format spec and write a safe parser; you can debug "why won't this load" at the byte level.

What Mastery Looks Like

  • Hostile-input discipline (Phase 8 — Hardening): given a 12-byte file claiming 4 billion sections, you instantly identify the integer-overflow and allocation-bomb vectors and know which invariants (I2, I5) close each; you can write the fuzz target before the parser.
  • Format archaeology (Phase 0 — Skeleton + Phase 1 — Sections): you can hexdump an unknown binary, locate the magic + offset chain, and reconstruct the header layout from the spec for both ELF and PE without tooling; you can explain why e_lfanew exists (DOS/Windows compatibility history) and what e_shnum==0 with the extended count in section[0] means.
  • Address arithmetic fluency (Phase 1 — Sections, §8 Domain Model): given a virtual address and a section table, you compute the file offset by hand, identify whether it falls in a NOBITS section, and explain why RVA and p_vaddr are different concepts; you can debug a "symbol resolves to wrong byte" bug by inspecting the RVA map.
  • Differential debugging (Phase 9 — Differential Conformance): when binparse disagrees with readelf, you know the three most common root causes (endianness read, r_info split, sh_link misresolution) and the exact field to hexdump to isolate each.
  • Zero-copy lifetime design (Phase 13 — Public API): you can explain why BinaryImage<'a> borrows the source buffer, what an OwnedImage wrapper must do, why self-referential structs require an audited crate, and the UB hazard of naive transmute over &[u8].
  • Fuzzing and safety gating (Phase 8 — Hardening): you can set up a cargo fuzz target, interpret a crash minimization, fix the invariant violation it exposed, and add a regression fixture — the full loop that keeps the parser unbreakable on attacker-controlled bytes.
  • API stability and downstream contracts (Phase 13 — Public API): you can write a SemVer policy for a type three downstream projects depend on, decide when a new field is additive-minor vs shape-changing-major, and gate it with cargo public-api in CI.

Per-box: Detector (bp-detect) — sniffs magic (\x7fELF, MZ→PE offset at 0x3C via e_lfanew), refuses ambiguous dual-magic (trust boundary #1, I10); reads ≤ 64 bytes. bp-elf/bp-pe — parse fixed headers into validated raw structs; reject impossible field combinations (wrong e_version, unknown e_class); produce arch/endian/bits metadata. bp-read — the safety core: every (offset, len) pair is checked against file size before a slice is produced; checked_add/checked_mul throughout; the sole unsafe site is mmap initialization; all other code is safe (I1/I2/I9). bp-sym — symbol tables (.symtab, .dynsym, COFF) + their string tables (via sh_link), name resolution, address-sorted index for symbol_at. bp-reloc — relocation entries decoded per arch (x86-64 RELA, AArch64, PE base relocs); addend semantics; unknown types kept with diagnostic. bp-dynamic — ELF .dynamic/DT_* walk; PE Import/Export/IAT directory; GNU symbol versioning (.gnu.version*). bp-note — ELF notes (GNU build-id, arbitrary note types), PE debug directory (CodeView RSDS → PDB GUID/path). bp-model — the canonical BinaryImage<'a> everything downstream reads; owns the RVA↔file-offset RvaMap; immutable, Send+Sync (I4/I12). bp-cli — human dump (readelf/dumpbin parity) + header round-trip check + triage report. bp-debug — locates DWARF/CodeView sections and unwind tables (full parsing deferred to #335). bp-ar — ar archive member iteration and symbol index.

4. System Constraints

Dimension Target
Memory ≤ 2× file size (zero-copy views; owned only for fixups); mmap optional
Parse throughput ≥ 500 MB/s header+section walk; ≥ 1 GB/s detection
Latency (typical 10 MB binary) full parse p95 ≤ 25 ms
Malformed input NEVER panic / OOB / overflow; always Err with offset context
Startup (CLI) ≤ 20 ms cold to first output
Max file ≥ 4 GiB (64-bit offsets); reject sizes exceeding declared bounds
Determinism identical bytes ⇒ identical model + dump (no clock/RNG/HashMap-iter-order in output)
FD budget 1 (the input); mmap unmaps on drop
Concurrency model is Send+Sync immutable; parse single-threaded; readers shareable
Round-trip re-serialized headers byte-identical for well-formed inputs

Scaling: single-process library; parallelism is per-file across many binaries (embarrassingly parallel, BinaryImage: Send). No network, no persistence, no shared mutable state. The one defining property of this system: the entire input is attacker-controlled — every design decision flows from that single constraint. The Reader trait, checked arithmetic (I2), count caps (I5), and cargo fuzz exist precisely because any field in any header may be a crafted exploit.

6. Design Principles

  1. P1 — Parse, don't trust. Every field from the file is hostile until explicitly validated; treat the spec as describing the language of valid inputs, and reject everything outside it. Tradeoff: validation adds a branch per field — acceptable because the branch is predicted and the alternative is exploitable. Violation: one unchecked offset → OOB read / RCE in the tool. Operational implication: bp-read is the sole gate; nothing downstream slices without a checked span.
  2. P2 — Bounds + overflow checks are mandatory, not optional. All offset/size arithmetic uses checked_add/checked_mul; never wrapping. Tradeoff: checked ops return Option — add one .ok_or(Err(Overflow)) per arithmetic site. Violation: offset+len integer overflow wraps on 32-bit usize, bypassing the bounds check; a 4-byte header claims 4 GiB of section data. Operational implication: overflow_guard metric is the canary.
  3. P3 — Zero-copy by default, own only for fixups. Return &'a [u8] / typed views into the source buffer; never copy unless the caller needs ownership (use OwnedImage for that). Tradeoff: lifetimes couple views to the buffer scope; OwnedImage is needed for long-lived consumers. Violation: copying every field blows the ≤ 2× memory ceiling on large binaries.
  4. P4 — Determinism. Same bytes ⇒ same model ⇒ same dump, always. Use ordered collections (Vec, BTreeMap, sorted indices) throughout; no HashMap iteration order in output. Tradeoff: BTreeMap has higher constant factor than HashMap — acceptable for the small tables involved. Violation: non-reproducible dump diffs prevent differential comparison and break I3.
  5. P5 — Total over partial: a parse either yields a fully validated node or a typed error with offset. No half-built struct escapes the parse boundary. Tradeoff: requires validating all fields of a struct before assembling it — adds one validation pass per struct. Violation: downstream code reads uninitialized or partially-filled fields → silent wrong output.
  6. P6 — Format-agnostic core, format-specific edges. All ELF-specific and PE-specific logic lives in bp-elf/bp-pe; bp-model holds only unified types. Tradeoff: requires a normalization step from format-specific to unified — adds one translation layer. Violation: PE IMAGE_ORDINAL_FLAG semantics leak into the ELF symbol path, producing wrong results on ELF inputs.
  7. P7 — RVA↔offset translation is one audited function. All address arithmetic goes through RvaMap::to_offset; no ad-hoc vaddr - section.vaddr + section.file_off expressions elsewhere. Tradeoff: adds one function call per address; negligible. Violation: scattered address math → one site gets it right, three others subtly wrong → wrong import/symbol/reloc addresses.
  8. P8 — Lenient read, strict report. Tolerate benign deviations real toolchains emit (§H.1), but record every deviation as a W.DEVIATION diagnostic with a stable code and rationale. Tradeoff: requires maintaining the allow-list; new deviations need review. Violation (too strict): reject real-world binaries → tool is unusable on production binaries. Violation (too lenient): silently accept corruption → downstream tools receive wrong data.
  9. P9 — No unsafe on the parse path. mmap initialization in bp-read::mmap is the sole audited unsafe site; the CI grep gate enforces this. Tradeoff: occasional ergonomic friction (e.g., cannot use transmute for speed); bounded overhead from safe checked reads. Violation: unsafe slicing in a parser → Miri cannot audit it; a fuzzer input triggers UB.
  10. P10 — Differential correctness. Parser output is validated field-for-field against readelf/llvm-readobj/dumpbin on a large real-world corpus; no field is "probably right". Tradeoff: requires maintaining the oracle pipeline and allow-list. Violation: a subtle endianness or shift error ships undetected and corrupts symbolization in #334.
  11. P11 — Bounded work. Section/symbol/reloc/import counts are capped against what the file can physically contain (file_bytes / MIN_ENTRY_SIZE); cyclic chains use visited sets; no unbounded recursion. Tradeoff: cap checks add O(1) per table; visited sets add O(chain_length) memory. Violation: 12-byte file claims 4×10⁹ sections → OOM or OOB before any meaningful data is read.
  12. P12 — Stable model API + versioned dump. Downstream projects (#334/#335/#74/#76) depend on BinaryImage; every public type is SemVer'd; breaking changes require a major bump and downstream notification. Tradeoff: requires #[non_exhaustive] on all enums and cargo public-api gating in CI. Violation: a field rename ships as a minor version → silent build break in every downstream consumer.

8.6 Malformed / failure-path examples

  • e_shoff past EOF → Err(OffsetOutOfBounds{off,filelen}) (I1).
  • e_shnum * e_shentsize overflows usize → Err(Overflow) (I2).
  • sh_link ≥ section count → Err(DanglingLink) (I7).
  • strtab index ≥ strtab size → name <malformed> + Diag (I6).
  • PE e_lfanew points outside file → Err(BadPeOffset).
  • Import directory RVA in no section → Err(RvaUnmapped) (I4).
  • 12-byte file claiming 4×10⁹ sections → Err(CountCapExceeded) (I5).
  • Both ELF magic and MZ heuristics → Err(AmbiguousFormat) (I10).
  • e_shnum == 0 with extended count in section[0].sh_size — handled as benign deviation (§H.1, W.DEVIATION).
  • .dynamic missing DT_NULL terminator — bounded scan by section size, W.DEVIATION diagnostic emitted.

12. Phase 0 — Skeleton, Reader, Detector, ELF+PE Headers, CLI dump

12.1 Objectives

Bounds-checked Reader (I1/I2), format detection (I10), ELF & PE fixed headers, BinaryImage skeleton, binparse headers. Constraint: no slice escapes unchecked from day one.

12.2 Detailed Implementation Steps

Applies: P1 (parse-don't-trust), P2 (checked arithmetic), P9 (no unsafe outside mmap), I1/I2/I9/I10; ADR-001 (Rust), ADR-002 (hand-written), ADR-003 (zero-copy), ADR-004 (endianness), ADR-005 (mmap); Levine Ch. 3 (mental model), MS PE/COFF spec (PE32/PE32+ header layouts).

  • bp-read: implement Reader trait over &[u8]; span(off,len)→bounds check vs buf.len()→&[u8]; u16/u32/u64 LE/BE via explicit byte reads (no transmute, ADR-004); cstr bounds-checked NUL scan (I6); optional mmap in mmap.rs — the sole unsafe site (I9).
  • bp-detect: read bytes 0–3 + 4-byte PE chain: \x7fELF → Fmt::Elf; MZ → read u32 at 0x3C → check PE\0\0 at that offset → Fmt::Pe; both or neither → Err(AmbiguousFormat) or Err(BadMagic) (I10).
  • bp-elf: decode Ehdr (ELF32/64, LE/BE); validate e_phoff/e_shoff+count*entsize ≤ file_len (I1/I2); decode Phdr[]/Shdr[] into raw validated structs; extract arch, endian, bits, entry.
  • bp-pe: read e_lfanew → validate → PE\0\0 signature; decode IMAGE_FILE_HEADER; decode IMAGE_OPTIONAL_HEADER32/64 (Magic=0x10b/0x20b); decode IMAGE_SECTION_HEADER[].
  • bp-model: assemble BinaryImage{fmt,arch,endian,bits,entry,sections} from validated raw structs; stub out empty symbols/relocs/imports.
  • bp-cli: binparse headers <file> dispatches detect→parse→dump; --format override (ADR-010); exit codes 0/2/3/4.

12.3 Deliverable

binparse headers <file> prints ELF/PE header + section list for real binaries; binparse detect <file> prints format/arch/bits/endian.

12.4 Acceptance Criteria

  • Parses /bin/* (ELF64 LE), a BE ELF (MIPS cross-compiler output), a PE32+ .exe/.dll; header fields byte-exact match readelf -h/dumpbin /headers on all three.
  • Every malformed Phase-0 fixture → typed Err with offset context, never panic; fuzz smoke 1M execs, 0 crashes, 0 OOB (ASAN clean).
  • Detection 100% correct on a 500-binary corpus; ambiguous inputs → Err(AmbiguousFormat).
  • CLI startup ≤ 20 ms cold (M8).

12.6 Pitfalls

  • Unchecked offset+len overflow (I2): e_shoff + e_shnum*e_shentsize wraps on 32-bit usize if e_shnum is huge; use checked_mul then checked_add → Err(Overflow).
  • Host-endian read on BE ELF (ADR-004): reading a u32 at offset 0x18 with native byte order gives garbage on an x86-64 host parsing a SPARC binary; every read must pass the decoded Endian value.
  • PE e_lfanew unbounded (I1): a malformed DOS header has e_lfanew=0xFFFFFFFF; validate < file_len before seeking.
  • SHT_NOBITS data read (I11): .bss has sh_size > 0 but sh_offset points to nothing meaningful; gate Section::data by type, never read file bytes for NOBITS.
  • Extended section count (Appendix H.1): e_shnum==0 means the real count is in section[0].sh_size; forgetting this truncates the section table on large object files.

12.7 Performance Concerns

Single linear pass for Ehdr→Phdr[]→Shdr[]; avoid per-field Vec::push (pre-size with cap after count validation); reuse the Reader across all reads; detection reads ≤ 64 bytes (M1: ≥1 GB/s). Cache: Ehdr is 64 bytes — fits in one cache line; Shdr[] fits in L2 for most binaries.

12.8 Edge Cases

0-byte file; 4-byte file (partial magic); e_shnum==0 with extended count in section[0].sh_size; PE with NumberOfSections==0; padded DOS stub (extra bytes before PE sig); e_shstrndx==SHN_XNUM (extended in section[0].sh_link); Ehdr with e_ehsize < sizeof(Ehdr).

12.9 Failure Analysis

A bad header field produces a localized Err(ParseError{offset,kind}); blast radius = that single file. Root cause is always a hostile or corrupt field. Detection: hexdump at the reported offset. No persistent state; no blast to other files.

12.10 Operational Notes

Metrics emitted: parse_ms (histogram), oob_attempt (counter), detect_fmt (label). Exit codes: 0 success / 2 malformed / 3 ambiguous / 4 I/O error. --verbose surfaces the diagnostics[] from the model. --json emits structured output for pipeline consumers (I3).

13. Phase 1 — Section & Segment Tables, String Tables, RVA Map

13.1 Objectives

Full section/segment model, ELF shstrtab/.strtab, the audited RvaMap (I4), section-data spans (lazy, NOBITS-aware I11). The RVA map is the single most load-bearing artifact in the system — every address-bearing phase depends on it.

13.2 Detailed Implementation Steps

Applies: P4 (determinism), P6 (format-agnostic core), P7 (one audited RVA function), P11 (bounded work); I4/I7/I11; ADR-003 (zero-copy), ADR-009 (lazy string tables); Levine Ch. 3 (section-vs-segment), System V gABI sec. 2 (segment mapping), MS PE/COFF sec. 3 (section layout); Shapiro et al. 2003 (TLS/NOBITS model).

  • bp-sym::strtab: bounds-checked cstr(idx) — validates idx < strtab.len(), scans to NUL, returns &'a str; OOB → <malformed> + Diag (I6).
  • Resolve ELF section names via e_shstrndx → strtab::cstr(sh_name) for each Shdr (I7: validate e_shstrndx < e_shnum).
  • Build RvaMap from ELF PT_LOAD segments (p_vaddr, p_offset, p_filesz) and from PE section headers (VirtualAddress, PointerToRawData, VirtualSize); sort by vaddr; to_offset(rva) binary-searches, checks section.vaddr ≤ rva < vaddr+vsize, returns Err(RvaUnmapped) for gaps (I4).
  • Lazy Section::data: for PROGBITS/similar → Ok(reader.span(sh_offset, sh_size)) (I1); for NOBITS → Ok(&[]) without reading file (I11).
  • PE section: use min(VirtualSize, SizeOfRawData) as data length (alignment-pad tail is not data); record both sizes in Section.
  • binparse sections + binparse rva <addr> + binparse off <foff> CLI subcommands.

13.3 Deliverable

binparse sections <file> outputs section table matching readelf -S field-for-field; binparse rva <file> <addr> prints file offset or error; binparse off <file> <offset> prints vaddr.

13.4 Acceptance Criteria

  • RvaMap::to_offset(vaddr) returns exact file offset for every section's vaddr on a 20-binary ELF+PE corpus; gaps return Err(RvaUnmapped) (I4 round-trip test, property: to_offset(vaddr) == file_off for every mapped address).
  • Section flags (R/W/X/alloc) match readelf -S/dumpbin /headers field-for-field.
  • NOBITS sections produce no file read (M4 memory target held).
  • rva_unmapped metric increments for gap accesses (I4 telemetry).

13.6 Pitfalls

  • e_shstrndx dangling (I7): if e_shstrndx ≥ e_shnum, section-name lookup crashes or reads garbage; validate the index before use.
  • Overlapping sections: two sections sharing a file range → ambiguous to_offset; use deterministic first-match (lowest vaddr) + emit W.OVERLAP diagnostic.
  • PE alignment mismatch (SectionAlignment > FileAlignment): virtual size rounds up to SectionAlignment; file size rounds to FileAlignment; confusing the two produces wrong RVA → file-offset mapping.
  • Zero-VirtualSize PE section: exclude from RvaMap; a vsize-0 section has no mapped range.
  • p_memsz > p_filesz (ELF BSS-like tail): the tail has virtual pages but no file bytes; only map p_filesz worth of file offset.

13.7 Performance Concerns

Sort sections once by vaddr → O(n log n) construction, O(log n) lookup (M7: ≤ 500 ns per to_offset call). Do not allocate per-lookup; binary search is in-place. For huge binaries (thousands of sections), the sort is still negligible vs I/O.

13.8 Edge Cases

.tbss/TLS (NOBITS with nonzero sh_size); ELF sections with sh_addr == 0 (not loadable — exclude from RVA map); PE section where PointerToRawData == 0 (virtual-only, like .bss); a section beyond p_filesz in an ELF load segment (BSS tail — NOBITS semantics apply).

13.9 Failure Analysis

A wrong RVA map is the highest-blast-radius bug in the project: every downstream address computation (symbols, relocs, imports, unwind) is wrong. Detection: I4 round-trip property test plus differential vs readelf -S/dumpbin. Postmortem: dump the sorted RvaMap entries alongside the section table; compare virtual ranges.

14.6 Pitfalls

  • strtab index OOB (I6): st_name ≥ strtab.len() → produce name <malformed> + Diag(E.BAD_STRTAB), never crash; the symbol entry is otherwise kept.
  • SHN_ABS/SHN_COMMON/SHN_UNDEF special section indices misread as real section indices → must branch on these before indexing into the sections array.
  • COFF 8-char vs strtab names: if name[0..4] == 0x00000000, the offset is in name[4..8] LE — getting this backwards produces garbage names.
  • st_info byte split: bind = st_info >> 4; type = st_info & 0xF — off-by-one in the shift is a common mistake.
  • SHN_XINDEX: when st_shndx == 0xFFFF, the real index is in .symtab_shndx[sym_idx]; omitting this breaks large object files.

14.7 Performance Concerns

Symbol index sort is O(n log n), once; symbol_at is O(log n) binary search (M6 ≤ 1 µs). Names are zero-copy &'a str views into strtab (ADR-009); avoid per-symbol String allocation.

14.8 Edge Cases

Empty .symtab (stripped binary) → empty symbols vec + W.DEVIATION diag, not error; huge .dynsym (>1M symbols) → bounded by count cap (I5); versioned symbol names contain @ or @@ — preserve as-is (versioning decoded in Phase 4); local symbols before global in ELF ordering — preserve source order.

14.9 Failure Analysis

Wrong symbolization → misleading disassembly in #334; differential vs nm + readelf -s catches. Blast radius: symbolization fidelity only; does not affect section/reloc decode.

14.10 Operational Notes

Metrics: symbols_n (gauge), bad_strtab_idx (counter). Stripped binaries → symbols_n=0 + diag. Symbol index is the primary handoff to #334.

15. Phase 3 — Relocations (ELF REL/RELA, PE base relocs)

15.1 Objectives

Decode relocation tables with arch-specific kinds + addends; expose for #76 loader and #334 symbolization of references.

15.2 Detailed Implementation Steps

Applies: P1/P5/P11; I1/I2/I5; ADR-007 (checked arithmetic); System V gABI sec. 4 (RELA/REL layouts, Appendix D.1/D.2), MS PE/COFF sec. 6 (base reloc blocks, Appendix D.3).

  • ELF RELA: r_offset (section-relative or vaddr), r_info (ELF32: sym=high24, type=low8; ELF64: sym=high32, type=low32), r_addend (i64 signed); decode per arch from Appendix D.1/D.2 tables; unknown type → keep raw u32 + W.DEVIATION diag (never drop).
  • ELF REL (no addend): same without r_addend field; addend is implicit in the patched location (decoder records 0).
  • PE base relocs: parse .reloc blocks — PageRVA (u32) + SizeOfBlock (u32); iterate (SizeOfBlock-8)/2 16-bit entries; high 4 bits = type (IMAGE_REL_BASED_*, Appendix D.3), low 12 bits = page offset → final RVA = PageRVA + offset; cap iterations by SizeOfBlock (I5).
  • Link each reloc to its target section (via RVA map, I4) and symbol index (r_info >> sym_bits).

15.3 Deliverable

binparse relocs matches readelf -r/dumpbin /relocations.

15.4 Acceptance Criteria

Reloc count/type/offset/addend match readelf -r/dumpbin /relocations on a corpus of 12 binaries (6 x86-64/AArch64 ELF, 6 PE) with 0 field mismatches; PE base-reloc block parsing byte-exact; differential pass; relocs_n metric correct; unknown type entries present in model with raw kind; decode throughput ≤ 200 ms per 1M relocs (M11).

15.5 Conformance Fixtures

conformance/elf/rela_x64, conformance/elf/rel_arm, conformance/pe/basereloc_dll, conformance/malformed/{reloc_sym_oob, bad_block_size, reloc_into_nobits}.

15.6 Pitfalls

  • r_info split differs ELF32 vs ELF64 (I2): ELF32 sym=r_info>>8, type=r_info&0xFF; ELF64 sym=r_info>>32, type=r_info&0xFFFFFFFF — using the wrong shift silently produces wrong symbol indices.
  • PE SizeOfBlock lies: a malicious block claims 0x80000000 bytes; cap iterations by (SizeOfBlock-8)/2 and validate SizeOfBlock ≤ remaining data first (I5/I1).
  • Addend sign: RELA r_addend is a signed i64; misreading as u64 makes negative addends (common in x86-64 PLT) look like huge positive values.
  • R_X86_64_RELATIVE/R_*_IRELATIVE: no symbol index (sym_idx=0); must not index into symbol table.
  • PE ABSOLUTE (type 0): padding entries to align blocks; must be skipped, not decoded as relocations.

15.7 Performance Concerns

Stream relocs without collecting all into a Vec first when memory is tight; cap count vs sh_size / sh_entsize (I5). No per-reloc heap allocation — Reloc struct is Copy. M11: ≤ 200 ms for 1M relocs.

15.8 Edge Cases

R_*_RELATIVE and IRELATIVE/IFUNC (no named symbol); PE ABSOLUTE type-0 padding; relocs referencing NOBITS sections (.bss patch — valid at load time, no file bytes); zero-entry relocation section.

15.9 Failure Analysis

Wrong reloc decode → loader produces corrupt patches (#76) or disassembler misses PLT stub (#334); differential gate catches field-level mismatches. Postmortem: dump raw r_info hex at the failing entry and compare bits.

15.10 Operational Notes

Metrics: relocs_n (gauge), unknown_reloc_type (counter — nonzero on new arch). Unknown types never fatal; surfaced as W.DEVIATION for downstream tooling.

16. Phase 4 — Dynamic Linking: ELF .dynamic/DT_*, PLT-GOT, Symbol Versioning

16.1 Objectives

Parse ELF .dynamic (DT_*), needed libraries, soname, symbol/reloc pointers, PLT-GOT layout; parse GNU symbol versioning (.gnu.version*) so dynamic symbols resolve to their correct version.

16.2 Detailed Implementation Steps

Applies: P6 (format-agnostic), P7 (one RVA function), P11; I4/I5/I7; ADR-004 (endian); Drepper "How To Write Shared Libraries" (DT_* semantics, PLT-GOT model); gABI paper 6 (versioning protocol).

  • Walk PT_DYNAMIC/.dynamic; collect key tags — DT_NEEDED, DT_SONAME, DT_STRTAB (vaddr → RVA→offset via I4), DT_STRSZ, DT_SYMTAB, DT_RELA/DT_RELASZ, DT_JMPREL, DT_PLTGOT, DT_FLAGS/DT_FLAGS_1; terminate at DT_NULL; bound scan (I5).
  • Resolve DT_NEEDED strings via the dynamic strtab (vaddr→file offset via RvaMap::to_offset, I4); collect into Vec<Import{lib,…}>.
  • Map PLT entries to GOT slots to .rela.plt relocs (use DT_JMPREL+DT_PLTGOTSZ + section data).
  • Symbol versioning: locate .gnu.version (Versym — one u16 per dynsym), .gnu.version_d (verdef chain), .gnu.version_r (verneed chain) via DT_VERSYM/DT_VERDEF/DT_VERNEED; build idx → version_string map; join to each symbol via versym index (masking high bit for hidden flag); expose symbol.version: Option<&str>.
  • Validate versym count == dynsym count (I5/I7); bound verdef/verneed chain iteration with visited set (cycle guard).

16.3 Deliverable

binparse dynamic lists needed libs, soname, dyn entries (≈readelf -d).

16.4 Acceptance Criteria

DT_NEEDED list matches ldd/readelf -d on a corpus of 8 dynamically-linked ELF binaries (4 versioned, 4 unversioned), 0 mismatches; PLT-GOT mapping consistent with .rela.plt; binparse syms --versions output matches readelf -V (version strings + default/hidden flags) on all 4 versioned samples; absent versioning handled silently with no error.

16.5 Conformance Fixtures

conformance/elf/{dynamic_pie, needed_multi, versym_libc, verdef_default, verneed_multi}, conformance/malformed/{dt_strtab_oob, dynamic_no_null, versym_count_mismatch, verdef_aux_oob, verneed_cycle}.

16.6 Pitfalls

  • .dynamic not DT_NULL-terminated: bound scan to section size / page limit (I5); never assume termination.
  • DT_STRTAB is a vaddr, not a file offset (I4): must go through RvaMap::to_offset; using it raw produces a garbage pointer.
  • versym length ≠ dynsym count (I5/I7): validate 1:1 before joining; miscount causes an OOB index.
  • verdef/verneed aux offsets are relative to the entry start, not the section start — easy off-by-one.
  • High bit of versym = hidden flag: masking forgotten → wrong index → wrong version name.
  • VER_NDX_LOCAL (0) / VER_NDX_GLOBAL (1): special indices that do not map to verdef/verneed; treat as "no version".

16.7 Performance Concerns

.dynamic is small (< 100 entries); single pass. Versioning tables are also small; build idx→name map once (O(versions)). PLT-GOT mapping is O(plt_entries); no per-entry alloc.

16.8 Edge Cases

Static binary (no .dynamic, no .gnu.version*) → all fields empty + no error; DT_RUNPATH/DT_RPATH → record but do not follow; lazy vs eager binding flags → record in DynEntry; base version definition (self-reference in verdef) → skip cleanly.

16.9 Failure Analysis

Wrong DT_STRTAB translation → garbage library names in import list (security-relevant for dependency analysis); I4 round-trip guards against this. Wrong version join → mis-resolved symbol semantics for #334/#76; differential vs readelf -V catches.

16.10 Operational Notes

Metrics: needed_n (gauge), versioned_syms (gauge), verneed_libs (gauge). binparse dynamic lists DT_* entries; binparse syms --versions shows name@VERSION. Consumed by dependency-analysis and loader (#76) tooling.

17. Phase 5 — PE Imports / Exports / IAT / Delay-Imports

17.1 Objectives

Parse PE Import Directory (ILT/IAT, by-name/ordinal), Export Directory (EAT, forwarders), delay-imports.

17.2 Detailed Implementation Steps

Applies: P1/P5/P7; I1/I4/I5; ADR-007; MS PE/COFF spec sec. 5–sec. 6 (import/export directory structures, Appendix D.5); Sikorski & Honig Ch. 1 (PE imports as malware indicator).

  • Import directory: DataDir[1].VirtualAddress → RVA→offset (I4) → IMAGE_IMPORT_DESCRIPTOR[] (terminated by all-zero entry, bounded by DataDir[1].Size); per-DLL: OriginalFirstThunk (ILT) RVA → array of 64-bit IMAGE_THUNK_DATA; high bit = ordinal; else IMAGE_IMPORT_BY_NAME{Hint,Name} at RVA; IAT entries at FirstThunk RVA.
  • Export directory: DataDir[0] → IMAGE_EXPORT_DIRECTORY; AddressOfFunctions[ordinal-base] RVA; AddressOfNames[i] + AddressOfNameOrdinals[i]; forwarder = RVA in the export section itself (not code) → string DLL.Function.
  • Delay imports: DataDir[13] → ImgDelayDescr[]; follow pIAT/pINT RVAs.
  • All RVAs resolved via RvaMap::to_offset (I4); all array bounds validated vs DataDir.Size (I5).

17.3 Deliverable

binparse imports/exports output matches dumpbin /imports /exports field-for-field; forwarder entries labeled.

17.4 Acceptance Criteria

DLL+symbol lists match dumpbin /imports /exports on a corpus of 10 PE DLLs/EXEs; ordinal-vs-name discrimination correct; forwarder detection on known samples; differential pass; imports_n/exports_n metrics match dumpbin counts.

17.5 Conformance Fixtures

conformance/pe/{imports_byname, imports_ordinal, exports_fwd, delay_import}, conformance/malformed/{import_rva_oob, iat_cycle, export_name_oob}.

17.6 Pitfalls

  • All RVAs must go through RvaMap::to_offset (I4): reading an import descriptor field as a file offset (raw pointer arithmetic) is the most common PE parsing bug.
  • IMAGE_ORDINAL_FLAG (high bit of 64-bit thunk): masking forgotten → tries to treat an ordinal as a name RVA → OOB.
  • Bound imports (pre-resolved IAT): FirstThunk contains loader-patched addresses, not the original thunk; use OriginalFirstThunk (ILT) as the authoritative name source.
  • Forwarder string vs code RVA: a forwarder export has its RVA inside the export section range; comparing against [ExportDir.VirtualAddress, +Size) distinguishes them.
  • Delay import version: old-style delay imports use HMODULE* not RVAs; check the Attributes flag.

17.7 Performance Concerns

Bounded per-DLL iteration (ILT is null-terminated, also bounded by DataDir.Size, I5); no per-entry heap alloc. Import count in real DLLs rarely exceeds 10k.

17.8 Edge Cases

Empty import directory (no DLLs); IMAGE_ORDINAL_FLAG set; export with name == forwarder string; resource-only DLL (no import table); PE with NumberOfRvaAndSizes < 2 (no import dir).

17.9 Failure Analysis

Misparsed IAT → wrong API-resolution for AV/security scanners (security-relevant); differential vs dumpbin is the correctness gate. Postmortem: dump raw thunk values + the RVA map at the failing address.

17.10 Operational Notes

Metrics: imports_n (gauge), exports_n (gauge), forwarder_exports (counter). Import list is the primary malware-triage signal; consumed by #228 Binary Exploitation and AV scanners.

18. Phase 6 — Notes, Build-ID, Debug Locators (DWARF/CodeView offsets), Unwind Index

18.1 Objectives

ELF notes + GNU build-id; PE debug directory; locate (not parse) DWARF/CodeView sections + PDB path; ELF unwind index (.eh_frame_hdr) and PE exception table (.pdata/.xdata).

18.2 Detailed Implementation Steps

Applies: P5/P8 (lenient read, strict report); I1/I4/I11; GNU build-id note spec (paper 5); DWARF v5 sec. 7 (section names + unit structure, book 8); MS PE/COFF sec. 5.8 (debug directory).

  • ELF PT_NOTE/.note.*: parse note structs (namesz/descsz/type, 4-byte-aligned name + desc); extract .note.gnu.build-id (type=3, name=GNU, desc=SHA-1 or hash bytes); bp-note::buildid.
  • PE debug directory: DataDir[6] → IMAGE_DEBUG_DIRECTORY[]; find type=IMAGE_DEBUG_TYPE_CODEVIEW (2); read CV_INFO_PDB70 (RSDS sig + GUID 16B + age u32 + PDB path CStr); validate RVA (I4).
  • bp-debug: record spans of .debug_* sections (DWARF), .pdata/.xdata (PE unwind), .gnu_debuglink for handoff to #335.
  • ELF unwind index: .eh_frame_hdr — version/eh_frame_ptr_enc/fde_count_enc/table_enc header; read fde_count; parse binary-search table of (initial_loc, FDE_ptr) pairs; validate all encoded pointers via RvaMap (I4); record only FDE boundaries — do not decode CFI bytecode (scope discipline).
  • PE unwind: .pdata RUNTIME_FUNCTION[] (BeginAddr,EndAddr,UnwindInfoRVA); validate all RVAs (I4); EndAddr > BeginAddr check (I5); follow UnwindInfoRVA to .xdata header (version/flags/prolog_size/code_count); bounded chained unwind info (UNW_FLAG_CHAININFO).

18.3 Deliverable

binparse notes/buildid/debug prints build-id, PDB path, debug-section inventory; binparse unwind <file> [<addr>] lists function ranges + unwind-record offsets.

18.4 Acceptance Criteria

Build-id matches file/readelf -n; PDB path matches dumpbin /headers; unwind function-range count matches .pdata entry count / .eh_frame_hdr fde_count; address lookup returns correct range on 5 spot checks vs llvm-objdump --unwind-info.

18.5 Conformance Fixtures

conformance/elf/{buildid_sha1, eh_frame_hdr_full}, conformance/pe/{codeview_pdb, pdata_x64}, conformance/malformed/{note_desc_oob, pdata_range_inverted, xdata_rva_oob, ehframe_trunc_fde}.

18.6 Pitfalls

  • Note 4-byte alignment: namesz and descsz are rounded up to 4-byte boundaries for the next entry; forgetting this produces misaligned reads on all subsequent notes.
  • CodeView RSDS vs older NB10 sig: some old binaries use NB10; check signature before assuming RSDS layout.
  • Debug directory with multiple entries: iterate all; don't stop at first.
  • .eh_frame is CFI bytecode — resist decoding here; only record FDE boundaries (Phase 6 scope discipline; full decode is in #335).
  • PE BeginAddr ≥ EndAddr (inverted range): reject entry + W.DEVIATION diag; do not include in unwind index.
  • Chained unwind (UNW_FLAG_CHAININFO): bounded follow with visited set (cycle guard, I5).
  • .eh_frame_hdr table_enc variants (pcrel/datarel/absptr): must apply the correct base address for each encoding.

18.7 Performance Concerns

Notes and debug dir are tiny (single-digit entries); single pass. .eh_frame_hdr table read is O(fde_count); .pdata is O(function_count); both fit in L1/L2 for typical binaries. Index build is O(n log n) sort once.

18.8 Edge Cases

Stripped binary (no debug, no build-id) → empty + W.DEVIATION diag; .gnu_debuglink (split-debug reference to separate .debug file) → record path, do not follow; multiple ELF notes sections; .eh_frame without .eh_frame_hdr; mixed C++/SEH unwind (both .pdata and .eh_frame).

18.9 Failure Analysis

Wrong build-id → symbol-server miss for debuggers/profilers (#74/#75); low blast radius (only affects debug info lookup). Wrong unwind index → wrong function-range attribution in #334/#335; spot-check differential detects.

18.10 Operational Notes

Metrics: has_buildid (bool), has_pdb (bool), unwind_records (gauge), pdata_inverted (counter). Feeds: symbol server lookup (#74), function-boundary discovery (#334), decompilation (#335).

Metrics: differential_mismatch (must be 0 outside allow-list), soak_files (gauge), parse_mbps (gauge). This phase certifies the parser for the full RE pipeline. Release cadence: SemVer minor for new format coverage; major for API shape changes.

22. Phase 10 — Integrity, Overlap/Gap Analysis, Entropy & Anomaly Triage

22.1 Objectives

Produce a structural integrity + anomaly report for triage (packers, corruption, tampering): section overlaps/gaps, header inconsistencies, suspicious entropy, RWX sections, entry-point sanity. Report-only; never rejects a parseable file.

22.2 Detailed Implementation Steps

Applies: P4 (determinism), P8 (lenient read), P11 (bounded work); I3/I5; ADR-023; Sikorski & Honig Ch. 1–2 (PE anomaly indicators).

  • Overlap/gap analysis: sort (file_off, file_off+size) intervals; detect overlaps (adjacent sections sharing bytes) → severity W.OVERLAP; detect gaps (unmapped file ranges > alignment) → W.GAP; both reported with exact byte ranges.
  • Shannon entropy per section: single pass over section.data bytes; H = -Σ p*log2(p) over 256-byte frequencies; H > 7.2 → high entropy hint; apply to: .text, .data, .rsrc, overlay region.
  • Anomaly flags: RWX section (MEM_EXECUTE|MEM_WRITE) → W.RWX; entry outside any executable section → W.ENTRY_IN_NONCODE; PE SizeOfImage doesn't match section layout → W.SIZE_MISMATCH; section with entropy > 7.5 named .text → W.PACKED; overlay bytes after last section → W.OVERLAY with byte count.
  • Sort flags by severity (error > warn > info), then by file offset; stable sort for determinism (I3).
  • Expose via binparse triage --json (deterministic field order) and text output.

22.3 Deliverable

binparse triage <file> emits a ranked anomaly report (JSON + text) with rationale per flag; binparse triage --json for pipeline consumption.

22.4 Acceptance Criteria

  • Flags a known UPX-packed sample (high entropy in all sections, few sections, minimal import stub) with ≥ 2 anomaly flags; clean GCC compiler output → 0 critical flags; deterministic report across 10 runs (I3).
  • Entropy scan ≤ 150 ms for 64 MB file (M12).
  • triage is gated by --triage flag so base parse is not slowed (M2 holds).

22.5 Conformance Fixtures

conformance/triage/{upx_packed, overlay_appended, rwx_section, entry_in_data, clean_gcc, high_entropy_data}.

22.6 Pitfalls

  • Entropy false positives on compressed resources / legit crypto data → report as hint, never verdict; include rationale string.
  • Section overlap is sometimes legal (sections sharing virtual pages at alignment boundaries) → severity tiers (warn, not error).
  • Overlay misattributed: signed Windows installers append signatures after the last section; label as W.OVERLAY with note about AuthentiCode possibility.
  • Nondeterministic flag ordering (I3): use stable sort by (severity, file_offset, flag_code).

22.7 Performance Concerns

Entropy is O(file bytes) single-pass (M12); overlap is O(n log n) on sorted intervals. Gate under --triage flag to keep base parse at M2/M3 targets.

22.8 Edge Cases

Zero-section PE (resource-only DLL); fully high-entropy file (compressed?); a section claiming the entire file; a negative gap (overlap at boundary due to alignment); TLS callbacks as anomaly indicator.

22.9 Failure Analysis

A wrong "malicious" verdict erodes trust in downstream security tooling → output is hints with rationale, never verdicts; downstream (#228, AV scanner) decides. Differential vs known-good / known-packed corpus.

22.10 Operational Notes

Metrics: anomaly_flags (histogram by code), max_section_entropy (gauge), overlay_bytes (gauge). Triage report feeds malware-analysis pipelines (#228 Binary Exploitation, AV integrations).

23. Phase 11 — Archives & Multi-Object (ar static libs, COFF objects, import libraries)

23.1 Objectives

Parse containers-of-objects: Unix ar archives (.a, !<arch>\n), Windows import/static libs (COFF archive), and standalone COFF/ELF relocatable objects — exposing member iteration over the same BinaryImage model.

23.2 Detailed Implementation Steps

Applies: P5 (total parse), P11 (bounded work); I1/I5; ADR-025 (archive in bp-ar); goblin archive.rs ref-impl (ref-impl 5 — member iteration patterns).

  • bp-ar: detect !<arch>\n magic; parse 60-byte ar_hdr per member (name[16]/date/uid/gid/mode/size/fmag); validate fmag == "\\n"; advance by size` (2-byte-aligned) (I1).
  • GNU long names: // member contains long-name table; names are offsets into it prefixed with /; #1/N (BSD) embeds the name in the first N bytes of the data.
  • Archive symbol index: / member (GNU) or __.SYMDEF (BSD) — big-endian u32 count + (symbol_name_off, member_offset)[] + string table; build name → member_offset map.
  • Windows import-lib short imports: Sig1 == 0xFFFF && Sig2 == 0x0000 → IMPORT_OBJECT_HEADER; extract DLL name + symbol name + ordinal/name-type.
  • Per-member parse: re-invoke BinaryImage::parse on the member bytes slice (I1: bounds-checked span).

23.3 Deliverable

binparse ar <lib.a> lists members + archive symbol index; binparse ar --member <n> parses one member as a BinaryImage.

23.4 Acceptance Criteria

Member list + symbol index match ar t / nm / dumpbin /linkermember on a corpus of 6 archives (3 GNU-format, 3 BSD/import-lib), 0 member-list mismatches; import libs resolve DLL+symbol name correctly on all import-lib samples; all member offsets within archive bounds (I1).

23.5 Conformance Fixtures

conformance/ar/{gnu_longnames, bsd_names, symdef, import_lib}, conformance/malformed/{ar_member_size_lie, bad_longname_ref, ar_member_oob}.

23.6 Pitfalls

  • Member 2-byte alignment: after each member, skip an extra byte if size is odd; missing this shifts all subsequent members by 1.
  • GNU vs BSD long names: /offset vs #1/N — confusing them produces garbage names in the other format.
  • Member offset must stay within archive (I1): a lying size field must not advance past EOF.
  • Short-import vs full COFF discrimination: check Sig1/Sig2 before treating as a full object.
  • Thin archives (!<thin>\n) reference external files by path — record as ThinRef, do not attempt to parse the external file.

23.7 Performance Concerns

Lazy member parse (parse-on-demand, not all at once); symbol index built once O(n) for lookup. Zero-copy member spans (&'a [u8] into the archive buffer).

23.8 Edge Cases

Empty archive; duplicate member names (legal in ar); archive with only a symbol index member; mixed-architecture members (e.g., a "fat" cross-build archive).

23.9 Failure Analysis

Wrong member boundary → garbage object parse for every subsequent member; bounded by I1 (archive end) + differential vs ar t catches header-level misparse.

23.10 Operational Notes

Metrics: ar_members (gauge), import_lib_syms (gauge). Static-lib parsing feeds the linker (#76) and dependency-graph analysis tools.

24.4 Acceptance Criteria

  • Rust mock #334 + C example both consume model correctly; cargo public-api diff shows no unintended public surface change; ABI smoke test (open+query+free) passes under ASAN across 1,000 open/query/free cycles with 0 leaks.
  • Doctests on every public type pass (≥ 8 doctests across BinaryImage/Section/Symbol/RvaMap, 0 failures).
  • OwnedImage drop + re-access under Miri: no UB across 100 construct/drop cycles.

24.5 Conformance Fixtures

conformance/api/{borrowed_query, owned_lifetime, capi_roundtrip, ffi_double_free}, doctests on BinaryImage, Section, Symbol, RvaMap.

24.6 Pitfalls

  • Self-referential OwnedImage UB: naive struct { buf: Vec<u8>, img: BinaryImage<'self> } is illegal Rust; use ouroboros/yoke and run Miri — the lifetime fiction must be safe in practice.
  • Leaking &'a str views across FFI: the C boundary must receive a null-terminated copy or a length-prefixed copy, not a raw borrowed pointer into the Rust buffer.

Compatibility & Versioning

SemVer 2.0 (ADR-022) on bp-types::BinaryImage + Reader trait + all public types. Rules:

  • Minor (additive, backward-compatible): new #[non_exhaustive] enum variant (Arch::RiscV32, ErrKind::BadAlign); new optional field on BinaryImage with a Default; new binparse subcommand; new Diag code; new format coverage (Mach-O → Fmt::MachO).
  • Major (breaking): field removal; field type change; variant removal; BinaryImage shape change; Reader trait method signature change; RvaMap::to_offset return type change; removing #[non_exhaustive] from an enum.
  • Dump text format: versioned independently with a binparse-dump-v<N> schema comment in the JSON output; version N increments on any field rename or reorder; parsers must check the schema version.
  • Round-trip guarantee: well-formed ELF/PE headers re-serialize byte-identical to the source bytes within the same major version (I8). This guarantee holds only for headers (Ehdr/NT headers/section headers); section data is zero-copy and never re-emitted.
  • CLI stability: all Phase 0 subcommands stable; new subcommands are additive (minor). Flags: --format, --json, --verbose, --no-mmap are stable; new flags are additive. Exit codes 0/2/3/4 are stable.
  • Diagnostic codes (E.OOB, W.OVERLAP, etc.) are stable identifiers from Phase 7 onward; new codes are additive (minor); code removal is major.
  • No on-disk state → no storage-format migration. The library is purely functional: the same input bytes always produce the same output model.

Testing & Verification Strategy

  • Unit — per decoder (ehdr/shdr/sym/reloc/import) with crafted bytes at known offsets; assert exact field values. Each test is a single #[test] over a hard-coded &[u8]; fast, deterministic, no I/O.
  • Property (proptest) — three properties: (1) round-trip header encode/decode is idempotent; (2) RVA↔offset injectivity: to_offset(vaddr) == file_off for every mapped section vaddr (I4); (3) "any byte string → Ok(BinaryImage) or typed Err, never panic" — the safety property exercised by fuzz.
  • Differential (ADR-012) — for each binary in the corpus: binparse dump --json vs oracle output parsed and normalized; field-by-field comparison; failures vs the allow-list are bugs. This is the primary correctness gate.
  • Conformance — conformance/** golden model + dump per fixture; each fixture has a .expected file; cargo test --test conformance diffs against it. Regenerated by make update-golden after deliberate changes.
  • Fuzzing (cargo fuzz + libFuzzer) — every public entry point; seed corpus from conformance/; 24h nightly in CI; ASAN enabled; minimize crashing inputs; crash = block merge.
  • Miri — cargo miri test on the parse module; catches UB (stacked-borrows violations, invalid reads) before hardware. Runs on every PR.
  • Malformed corpus — conformance/malformed/: truncation at every 16-byte boundary; checked_mul overflow triggers; count bombs (sections/symbols/relocs); cyclic sh_link chains; OOB strtab indices; dual-magic; zero-byte file.
  • Soak — scripts/soak.sh: parse /usr/bin + system DLL directories + compiler output archives; 0 crashes, bounded memory (≤ 2× largest file), throughput ≥ 500 MB/s (M3). Runs nightly.
  • Integration — a tests/mock_334.rs test: given a BinaryImage of a known binary, call symbol_at(entry()) and imports() and assert correct results. Verifies the API contract that #334 depends on.
  • Perf regression (criterion) — benchmarks in benchmarks/; cargo bench run in CI on main; fail if throughput drops ≥ 10% vs last tagged release (M1–M12 targets enforced).

Weighting: fuzz + differential + property carry the most weight because the failure modes that matter are memory-safety violations on hostile input (fuzz catches) and silent field misreads (differential catches). Unit + conformance tests are the debugging tools when fuzz or differential find a failure.

Scalability Analysis

Single-file parsing is the unit; scaling is fan-out across files (a scanner parses thousands in parallel — model is Send/Sync, parse is a pure function, embarrassingly parallel). Bottlenecks in order: (1) large symbol/reloc tables (CPU + memory) → lazy + capped (I5); (2) huge files → mmap + zero-copy keep memory ≤ 2× even at GB scale (§4); (3) string-table scans → bounded by strtab size (I6). Ceilings: 32-bit offset ELF inherently ≤ 4 GiB file offsets; ELF64 + PE32+ handle up to the OS limit. No coordination, no shared state, no persistence → linear scaling with cores for batch workloads. Memory grows with table sizes (symbols/relocs), not file size (zero-copy), so the effective cap is the file's declared table counts (bounded, I5).

Horizontal scaling (fleet scanning): each file is an independent parse; a thread pool of N workers achieves N× throughput with no synchronization. The BinaryImage model is Send — parsed on one thread, consumed on another (e.g., a DB writer thread). Shared mutable state: none. Shared read-only state: the source buffer (&[u8]), which is Sync by construction.

Vertical scaling (single large binary): for a 4 GiB ELF, mmap avoids the full read; zero-copy section views add zero memory beyond the model structs (≈ sections × 200 B + symbols × 48 B). At 1M symbols: 48 MB model + 4096 MB mmap = 4144 MB — within the 2× ceiling (8 GB for a 4 GB file). The bottleneck is symbol-index sort (O(n log n), M5: ≤ 500 ms for 1M).

Practical ceiling: a binary with 100M symbols (hypothetical, never observed) would require 4.8 GB of model memory and 100s sort time — beyond the count cap (I5: symbols ≤ symtab_size / 24 where 24 = sizeof(Elf64_Sym)). The cap enforces the practical ceiling at what the file can physically contain.

Beyond the ceiling: for a corpus of 1M files, the fan-out pattern (each file parsed independently, results streamed to a database) scales linearly. The only shared resource is the thread pool; a work-stealing scheduler (Rayon) eliminates stragglers. No persistent parser state means no warm-up and no cache invalidation between files.

Mental Models & First Principles

MM1 — A binary file is a tree of offsets. Every header contains offsets into the same byte array; a "format" is just a grammar for navigating that tree. Corruption is a broken pointer in the tree; safety is checking every pointer before dereferencing. Applies: §4 System Constraints (bounds checks as first-class), §6 P1/P2, Phase 12 §12.2 (bp-read design), Phase 13 §13.2 (RVA map as the root of the offset tree). Without this model, developers treat offsets as trusted integers and skip checks.

MM2 — Virtual address ≠ file offset; the RVA map is the Rosetta Stone. At link time, sections are assigned virtual addresses; at parse time, you have file offsets. The RvaMap converts between them. Every address-bearing field (symbol values, reloc targets, import RVAs, entry point) is a virtual address that must be translated before reading file bytes. Applies: §8 Domain Model §8.3, Phase 13 §13.2 (RVA map build), Phase 16 §16.2 (DT_STRTAB is a vaddr), Phase 17 §17.2 (all PE import RVAs). Without this model, developers mix the two and produce wrong symbolization or OOB reads.

MM3 — Input is a language; your parser is a recognizer. Following Bratus et al. (LangSec 2015), treat the format spec as a grammar. Your parser either recognizes a valid sentence or rejects with a typed error — there is no middle ground of "partially valid" state. Applies: §6 P1/P5, §7 I1/I5, Phase 20 §20.2 (fuzz as grammar-coverage exercise). Without this model, half-parsed structs escape and downstream code reads garbage.

MM4 — Zero-copy = lifetime algebra. A &'a [u8] view into the source buffer is valid only while 'a is alive. The parser's output (BinaryImage<'a>) borrows the input; the OwnedImage wrapper exists precisely to embed the buffer alongside the view. Applies: §11 Core Schema (lifetime annotations), Phase 19 §19.2 (unified model design), Phase 24 §24.2 (OwnedImage). Without this model, developers copy everything (blowing memory) or produce dangling pointers (UB).

MM5 — The section table and segment table serve different masters. ELF sections serve the linker (names, relocations, symbols); segments serve the loader (loadable address ranges). A well-formed ELF has both; a stripped binary may have only segments; a relocatable object has only sections. Applies: §8 Domain Model §8.1, Phase 12 §12.2 (Ehdr parsing), Phase 13 §13.2 (RVA map uses PT_LOAD segments). Without this model, developers confuse section VAs with segment VAs in the RVA map.

MM6 — Counted arrays + bounded allocation = DoS resistance. Every Vec::with_capacity(n) where n comes from the file is an allocation bomb if n is uncapped. The cap must come from the file size, not the declared count alone: real_cap = min(declared_n, file_bytes / MIN_ENTRY_SIZE). Applies: §6 P11, §7 I5, Phase 20 §20.2/20.6 (cap-before-alloc rule). Without this model, a 12-byte file with e_shnum = 4294967295 causes an OOM.

MM7 — Differential testing is the correctness oracle. There is no ground truth for "what does this binary mean" except what the canonical tools (readelf, llvm-readobj, dumpbin) output. Every field your parser computes must be verified against at least one oracle. A mismatch is a bug, not a disagreement. Applies: §6 P10, ADR-012, Phase 21 §21.2 (differential conformance). Without this model, subtle field misreads ship silently and break downstream tools.

MM8 — Endianness is a per-binary property, not a platform property. ELF can be LE or BE regardless of the host. A parser that reads with native byte order is wrong half the time. Every multi-byte field read must carry an explicit Endian parameter derived from EI_DATA. Applies: §6 P-implicit, ADR-004, Phase 12 §12.2 (endianness decode from e_ident), Phase 15 §15.2 (r_info decoding). Without this model, BE ELF parses as garbage on an LE host.

GNU binutils/BFD: BFD is the canonical ELF/PE implementation and the ground truth for correctness — it implements the full linker chain. Its decision to use a mutable descriptor with internal copies (rather than zero-copy views) reflects its origin as a toolchain component that transforms binaries, not just reads them. BFD wins in any context that requires linking, relocation application, or binary emission — the exact scope that binparse explicitly defers.

LLVM object/llvm-readobj: LLVM's ObjectFile hierarchy uses C++ polymorphism for multi-format support and is the second differential oracle for this project. Its decision to use LLVM's MemoryBuffer abstraction (copies data in by default) is inherited from LLVM's overall IR model. LLVM wins when the consumer is already in the LLVM ecosystem (e.g., writing an LLVM pass, a JIT, or a custom backend) because the format parsing comes "for free" with the LLVM dependency.

LIEF (C++): LIEF's decision to unify parser and builder into a single Binary object makes it the most capable RE instrumentation framework — it can parse, modify, and re-emit ELF/PE/Mach-O in one pipeline. This wins for use-cases like packer construction, binary hardening, or automated patching, where you need write-back. The tradeoff: heavy mutable state makes embedding and concurrent use difficult; no zero-copy; Mach-O coverage that binparse defers.

goblin/object (Rust): The object crate (gimli-rs) and goblin are the closest Rust peers. object uses a zero-copy Object<'a> enum and is the most architecturally similar to binparse. Its key decision to use a heavy trait hierarchy (ObjectFile, ObjectSection, ObjectSymbol) provides format-agnostic iteration but at the cost of opacity — errors are harder to locate, and the trait bounds make concrete use verbose. object wins when you want a single dependency that "just works" for many formats without caring about the internal model; binparse wins when you want a greppable, concrete API with a defined SemVer contract and a fuzz/differential safety story.

Back-of-Envelope Capacity Model

All numbers derived from §4 System Constraints.

1. Memory ceiling for a 100 MB binary. Constraint: ≤ 2× file size (§4 Memory row). 2 × 100 MB = 200 MB. With zero-copy, the only owned allocation is the model structs (not section data); for a binary with 1000 sections + 100k symbols + 500k relocs: 1000 × ~200 B + 100000 × ~48 B + 500000 × ~32 B = 0.2 MB + 4.8 MB + 16 MB ≈ 21 MB. Total: 100 MB (buffer) + 21 MB (model) = 121 MB ≪ 200 MB ceiling. The ceiling is not at risk for realistic binaries; it would only be reached by a binary with a table-heavy structure and near-minimal section data.

2. Parse throughput target — how fast must the reader be? Constraint: ≥ 500 MB/s full parse (§4 + M3). At 500 MB/s, a 10 MB binary parses in 10 / 500 = 20 ms — within the p95 ≤ 25 ms constraint (M2). For a 64 MB binary: 64 / 500 = 128 ms. The throughput budget for the section-walk sub-step (assuming it is 20% of total parse time): 500 MB/s × 0.20 = 100 MB/s — easily achieved by a single sequential pass.

3. Format detection budget. Constraint: ≥ 1 GB/s detection (M1), reads ≤ 64 bytes. At 1 GB/s memory bandwidth (typical L2 speed), 64 bytes takes 64 / (10^9) = 64 ns. Detection is a magic comparison + one u32 read — well under the 64-byte budget and well within the 1 GB/s target.

4. Symbol-table index sort cost. Constraint: symbol-index build for 1M symbols ≤ 500 ms (M5). Rust's sort is O(n log n) comparisons; for 1M elements: 10^6 × log2(10^6) ≈ 10^6 × 20 = 2×10^7 comparisons. At ~10^9 comparisons/s (optimistic for a cache-cold sort): 2×10^7 / 10^9 = 20 ms. Well within 500 ms even with cache pressure. At the 64-bit symbol-value sort key, L3 bandwidth is the true bottleneck: 1M × 16 B (key+idx) = 16 MB — fits in L3 on a modern chip.

5. Relocation-decode cost. Constraint: 1M relocs ≤ 200 ms (M11). Each Elf64_Rela is 24 bytes; 1M entries = 24 MB. At 500 MB/s parse rate: 24 MB / 500 = 48 ms. With cache locality (sequential scan), the practical cost is ≤ 100 ms — well within M11.

6. RVA map binary search latency. Constraint: ≤ 500 ns per lookup (M7). A binary search over 1000 sections: log2(1000) ≈ 10 comparisons. Each comparison loads a (vaddr, vsize, file_off) triple (24 bytes). 10 comparisons × ~5 ns each (L1 cache hit after first) = 50 ns — well within the 500 ns budget. At 10000 sections: log2(10000) ≈ 14 comparisons = 70 ns. Still within budget.

7. Differential soak wall-clock. Constraint: 10k files in ≤ 10 min on 8 threads (M9). Per-file time budget: 10 min × 60 s × 8 threads / 10000 files = 4.8 s/file. Average real binary is 2–10 MB; parse at 500 MB/s → 0.004–0.02 s parse; oracle comparison (readelf + diff) ≈ 0.5 s. Total ≈ 0.52 s/file — well within the 4.8 s budget.

8. Fuzz throughput. Constraint: ≥ 50k execs/s per target (M10). libFuzzer overhead ≈ 5 µs/exec for setup; parse of a small fuzz input (typically ≤ 10 KB) at 500 MB/s → 10 KB / 500 MB/s = 0.02 ms = 20 µs. Total ≈ 25 µs/exec = 40k execs/s. Close to but slightly below M10; the target is achievable with per-exec corpus sharing and avoiding large heap allocs in the parse path.

9. mmap vs read choice threshold. At what file size does mmap beat full read? Full read cost: n / disk_bandwidth. mmap cost: page-fault cost × (n / 4096). On NVMe: disk bandwidth ≈ 3 GB/s; page-fault handler ≈ 1 µs. Crossover: n / 3×10^9 = n/4096 × 10^-6 → n = 4096 × 10^-6 × 3×10^9 = 12 GB. For files < 12 GB, full read is competitive; for files > 12 GB (rare), mmap wins. Conclusion: mmap is the right default for very large files (4 GiB+) but optional for typical ≤ 100 MB binaries.

10. CLI cold-start budget. Constraint: ≤ 20 ms cold to first output (M8). Breakdown: binary load (Rust runtime) ≈ 5 ms; file open + stat ≈ 0.5 ms; format detection ≈ 0.1 ms; header parse ≈ 2 ms; first output ≈ 0.5 ms. Total ≈ 8 ms — well within 20 ms. The budget tightens if rustc link-time optimization is disabled; LTO is therefore enabled in release builds.

Hard Questions (Self-Examination)

  1. Why does this design use a BinaryImage<'a> lifetime rather than an owned BinaryImage? What is the performance + safety tradeoff, and when does the OwnedImage wrapper become necessary? Requires §11 Core Schema (lifetime annotation design) + Phase 24 §24.2 (OwnedImage rationale) + §4 System Constraints (memory ceiling). The lifetime enforces zero-copy (§4) but couples the model to the buffer's scope; OwnedImage embeds the buffer via a self-referential pattern. A caller that needs the model to outlive a function boundary must use OwnedImage — without this, they hit a lifetime error.

  2. How does the RvaMap guarantee injectivity (no two RVAs map to the same file offset), and what breaks if overlapping sections exist? Requires §7 I4 (RVA map injective), Phase 13 §13.6 (overlapping sections pitfall), §8 §8.3 (RVA↔offset formula). Overlapping sections make to_offset ambiguous; the design uses deterministic first-match + a W.OVERLAP diagnostic, which preserves the invariant by fiat. The implication: the file's semantics at the overlap bytes are undefined, and any symbolization in that range may be wrong.

  3. What is the difference between ELF sh_type == SHT_NOBITS and a section with sh_size == 0? What happens when the RVA map includes a NOBITS section? Requires §8 Domain Model §8.1, §7 I11 (NOBITS), Phase 13 §13.6 edge cases. NOBITS has sh_size > 0 (virtual space) but no file bytes; sh_size == 0 has neither. The RVA map must include NOBITS sections for virtual address coverage, but Section::data must return empty (no file read). Confusing them produces either a wrong data span or an OOB read.

  4. How does a forwarder PE export differ from a regular export at the binary level, and how do you detect it? Requires §8 Domain Model §8.2 (PE layout), Phase 17 §17.2/17.6 (export directory + forwarder detection). A forwarder's RVA falls within the export section's VirtualAddress range — not in any code section. Detection: compare the export RVA against [ExportDir.VirtualAddress, +ExportDir.Size); if inside, it's a forwarder string, not a function address. Forgetting this means you try to fetch code at a string offset.

  5. Why does the design mandate checked_add before every Vec::with_capacity, and why is capping by file size (not just by the declared count) the correct guard? Requires §6 P11, §7 I2/I5, Phase 20 §20.6 (count-bomb pitfall), MM6. A declared count of 4×10⁹ causes Vec::with_capacity(4e9) to OOM or wrap even before any parsing. Capping by file_bytes / MIN_ENTRY_SIZE ensures the cap is physically achievable — you cannot have more entries than the file can hold. Both guards together (overflow-check + size-check) are required; either alone is insufficient.

  6. What is the difference between DT_STRTAB and .dynstr's sh_offset, and when can they disagree? Requires Phase 16 §16.2/16.6, §7 I4. DT_STRTAB is a virtual address (needs RVA→offset); sh_offset is already a file offset. On a stripped binary with no section table, DT_STRTAB is the only way to locate the dynamic string table. On a binary with both, they should agree — a mismatch is a sign of manual patching or a linker bug; use DT_STRTAB as authoritative.

  7. How does the GNU symbol versioning model (verdef/verneed/versym) interact with DT_NEEDED, and what happens if versym count ≠ dynsym count? Requires Phase 16 §16.2/16.6, §7 I5/I7. DT_NEEDED lists library names; versioning adds a version suffix to each symbol's name, constraining which version of a library satisfies it. If versym count ≠ dynsym count, every index lookup is off-by-one or OOB; I5 forces rejection of the versioning data with a W.DEVIATION diagnostic while keeping the base symbols.

  8. Explain why r_info decoding differs between ELF32 and ELF64, and what the consequence of using the wrong split is. Requires Phase 15 §15.2/15.6, §8 §8.1, Appendix D.1. ELF32: sym = r_info >> 8; ELF64: sym = r_info >> 32. Using ELF32 split on ELF64 produces a sym index of r_info >> 8 which is wildly wrong (a 32-bit shift instead of 24-bit). Every relocation's symbol reference is wrong; the loader or symbolizer reads the wrong symbol, causing incorrect patching or misleading disassembly.

  9. Under what conditions can mmap produce worse performance than a full sequential read, and how does the design handle this? Requires §4 System Constraints (mmap optional), ADR-005 (when rejected choice wins), Back-of-Envelope Capacity Model item 9. mmap is worse on network-mounted filesystems (each page fault crosses the network), on write-heavy systems where TLB shootdowns are expensive, and for files smaller than ~100 KB where setup cost dominates. The design makes mmap optional (ADR-005, --no-mmap flag); the default picks mmap for files > 64 MB (heuristic) and falls back to full read otherwise.

  10. What is the OwnedImage self-referential hazard, and why does the design require an audited crate (ouroboros/yoke) rather than unsafe raw pointers? Requires Phase 24 §24.2/24.6, §7 I9 (no unsafe outside mmap), §6 P9. A struct holding both Vec<u8> and BinaryImage<'self> where the image borrows the vec is a self-referential struct — illegal in safe Rust because moving the struct would invalidate the borrow. Audited crates use Pin + careful invariants to prevent the move. Raw pointers would bypass this and require audited unsafe outside the mmap site, violating I9.

  11. How does the differential conformance oracle handle benign real-world deviations without generating false failures, and what is the allow-list governance process? Requires Phase 21 §21.2/21.6, §H.1, §6 P8. The allow-list (differential/allow_list.toml) records each known deviation with a rationale (e.g., "MSVC emits SizeOfRawData > VirtualSize for alignment padding — this is correct per the PE spec"). A new deviation requires a review comment explaining why it is benign and not a parser bug. The allow-list is pinned to oracle versions.

  12. Why is the Threat Model's defining property "the entire input file is attacker-controlled", and what threat does this neutralize that a trusted-input parser would not need to address? Requires Threat Model, §6 P1, MM3. In a binary parser, the file is fetched from disk, network, or untrusted storage — any of which can be attacker-supplied. The threat is that a crafted binary triggers OOB, integer overflow, or allocation bomb in the parser, giving the attacker code execution in the tool that calls it (e.g., a disassembler, AV scanner, or CI pipeline). Trusted-input parsers can skip bounds checks; this design cannot.

  13. How does the PE IMAGE_ORDINAL_FLAG work in the Import Address Table, and what is the consequence of misreading it? Requires Phase 17 §17.2/17.6, §8 §8.2, Appendix D.5. The high bit (bit 63 on PE32+) of each ILT/IAT thunk entry signals ordinal import when set; the lower bits are the ordinal number. If you forget to mask this bit and treat the entry as a by-name RVA, you try to read IMAGE_IMPORT_BY_NAME at an invalid address (the high bit makes it a huge RVA), producing an OOB or garbage symbol name.

  14. Explain the complete chain from e_shstrndx to a section name, and identify every invariant that must hold for it to be correct. Requires Phase 12 §12.2, Phase 13 §13.2, §7 I6/I7, §8 §8.1. Chain: (1) e_shstrndx < e_shnum (I7) → section[e_shstrndx] → (2) sh_offset + sh_size ≤ file_len (I1) → strtab bytes → (3) for each section, sh_name < strtab.len() (I6) → scan to NUL → name. Any broken link: shstrndx OOB → Err(DanglingLink); strtab OOB → Err(Oob); sh_name OOB → <malformed> + diag. All three invariants (I1/I6/I7) must hold simultaneously.

  15. How does the ReaderTrait abstract over both &[u8] and mmap without introducing unsafe on the hot parse path? Requires §11 Core Schema (Reader trait), §7 I1/I9, Phase 12 §12.2, ADR-005. Reader::span(off, len) returns Result<&'a [u8], ParseError> — both the slice-backed and mmap-backed implementations do the bounds check identically in safe code; only the mmap initialization in mmap.rs is unsafe. The hot parse path calls span/u32/etc. on the trait object — these are safe functions regardless of the backing store.

  16. Why does the design mandate a stable sorted order for the dump output rather than the order entries appear in the file? Requires §7 I3, §6 P4, ADR-023, Phase 21 §21.6 (locale/sort pitfall). File order is not guaranteed to be consistent across linkers, versions, or optimization levels. Stable sorted output (by section index, then symbol value) makes binparse dump diff-able: re-running on the same file, or comparing two builds of the same binary, produces meaningful diffs. Locale-dependent sort (readelf uses LC_ALL for some fields) is normalized to LC_ALL=C in the differential comparison script.

  17. What is the PE "bound import" feature, and why must OriginalFirstThunk (not FirstThunk) be used for import name resolution? Requires Phase 17 §17.2/17.6. Bound imports have the IAT (FirstThunk) pre-patched at link time with the actual function addresses (for faster loading). These addresses are meaningless for symbol resolution. The OriginalFirstThunk (ILT) always contains the original by-name or by-ordinal thunks that reveal which function is imported. Using FirstThunk on a bound import returns a numeric address, not a name.

  18. How does cargo fuzz find deeper paths than random mutation alone, and why is this the safety gate for hostile input? Requires Phase 20 §20.2/20.4, ADR-013, MM3. libFuzzer uses coverage-guided mutation: it instruments the binary with SanitizerCoverage edge counters and preferentially mutates inputs that reach new edges. This finds deep paths (e.g., a combination of e_shnum==0 + sh_size == 4B + specific sh_link) that random mutation statistically cannot reach. It is the safety gate because memory-safety bugs on the parse path are found by reaching the code that mishandles the edge case — coverage guidance makes this tractable.

  19. What does #[non_exhaustive] do to Arch and ErrKind, and why is it required for SemVer-safe API evolution? Requires Phase 24 §24.2/24.6, ADR-022. #[non_exhaustive] prevents external crates from exhaustively matching on an enum, which would break if a new variant is added (a breaking change). With #[non_exhaustive], adding Arch::RiscV32 or ErrKind::BadAlign is a minor (additive) change — callers must include a wildcard arm. Without it, every new variant is a SemVer major bump, making the API impractical to evolve.

  20. Explain the full data flow from a PE import directory RVA to a resolved DLL name and function name, citing every invariant touched. Requires Phase 17 §17.2, §8 §8.2, §7 I1/I4/I5. Flow: (1) DataDir[1].VirtualAddress → RvaMap::to_offset (I4) → file offset of IMAGE_IMPORT_DESCRIPTOR[]; (2) bounded iteration by DataDir[1].Size (I5); (3) per-descriptor Name RVA → RvaMap::to_offset (I4) → NUL-terminated DLL name bounded by file end (I1/I6); (4) OriginalFirstThunk RVA → thunk array → per-entry: ordinal bit? ordinal : hint+name RVA → RvaMap::to_offset (I4) → IMAGE_IMPORT_BY_NAME{Hint, Name} (I1). Six RVA translations, three invariant checks.

Alternative Architectures (Roads Not Taken)

Alternative 1 — Streaming / SAX-style event parser

file bytes → StreamParser
                │
                ├─ on_section(idx, name, flags, off, size) ─► caller callback
                ├─ on_symbol(name, value, bind, kind)       ─► caller callback
                ├─ on_reloc(offset, sym, kind, addend)      ─► caller callback
                └─ on_import(lib, name, ordinal)             ─► caller callback
    No BinaryImage built; caller accumulates what it needs.

Regime where it wins: streaming a 10 GB binary or a corpus of millions of files where building an in-memory model for each is prohibitive; or feeding a database pipeline that needs to index fields without holding the full model. Real system: readelf --wide in streaming mode; SAX XML parsers; Kafka consumer pipelines. Why rejected: downstream tools (#334, #335) need random-access queries (symbol_at(addr), section_by_name) after the parse; a streaming model cannot serve these without the caller accumulating the data anyway, rebuilding the model. The round-trip test (I8) also requires a complete model. The callback API is harder to test differentially and harder to compose.

Alternative 2 — Generic trait-object model (ObjectFile<F> where F: Format)

trait ObjectFile {
    fn sections(&self) -> Box<dyn Iterator<Item = dyn Section>>;
    fn symbols(&self) -> Box<dyn Iterator<Item = dyn Symbol>>;
    fn entry(&self) -> u64;
}
struct ElfFile<'a> { … }  impl ObjectFile for ElfFile<'a> {}
struct PeFile<'a>  { … }  impl ObjectFile for PeFile<'a>  {}

Regime where it wins: when a plugin system loads format parsers at runtime (unknown at compile time), or when the format list is open-ended (add Mach-O, WASM without recompiling the core). Real system: gimli-rs/object (uses this pattern heavily), IDA Pro's format loaders (dynamic plugins). Why rejected: trait objects incur vtable dispatch on every field access; associated types proliferate; error types become abstract (Box<dyn Error>) losing offset context; the concrete BinaryImage struct is greppable and stable — the primary SemVer contract for #334 works better on a concrete type that can be pattern-matched and doc-tested without trait gymnastics.

Alternative 3 — Lazy-everything / on-demand parser (no upfront parse)

BinaryImage::open(path) -> LazyImage   // reads only magic; no header parse
LazyImage::sections()   -> LazyResult  // reads section table on first call
LazyImage::symbols()    -> LazyResult  // reads symbol table on first call
// Each field parsed only when accessed; results cached.

Regime where it wins: a tool that needs only one field from a binary (e.g., just the build-id, just the entry point) and wants to pay zero cost for the rest; or a REPL-style interactive tool where the user inspects one field at a time. Real system: Python's pyelftools (lazy section parsing); IDA Pro's deferred analysis. Why rejected: caching per-field requires internal mutability (Mutex or OnceCell), breaking Send+Sync simplicity (I12) and making the model non-deterministic in order of initialization. The round-trip test and differential test both need the full model parsed upfront. The complexity of managing a partially-parsed state machine is higher than a single-pass full parse at the throughput targets (M2/M3).

Alternative 4 — Memory-mapped file as the primary zero-copy substrate (no &[u8] slice API)

// Parser takes `*const u8` + `usize` from mmap; all views are raw pointer arithmetic.
// No `Reader` trait; structs are `#[repr(C)]` transmutes directly from the mapping.
unsafe fn parse_elf(base: *const u8, len: usize) -> ElfImage { … }

Regime where it wins: maximum throughput on huge files where even the bounds-checked Reader trait dispatch is measurable overhead; or a kernel-space or no-alloc embedded parser where Rust's safe abstractions are unavailable. Real system: Linux kernel ELF loader (does exactly this), some commercial RE tool backends. Why rejected: violates I9 (no unsafe on the parse path); makes Miri testing difficult; repr(C) transmutes on misaligned data (e.g., a 3-byte-aligned field in a packed ELF section) cause UB on strict-alignment architectures (ARM); endianness is implicit (breaks ADR-004 for BE ELF). The safe Reader trait adds negligible overhead (bounds check = one comparison and branch) and enables Miri + fuzz without special harnesses.
