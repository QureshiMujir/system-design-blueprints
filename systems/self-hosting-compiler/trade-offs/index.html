Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Bytecode VM With A JIT Instead Of An AOT Native Backend

Source -> AST -> Typed IR -> Bytecode -> [Interpreter | JIT Compiler] -> Result
                                              ^                 |
                                              +---- profile ----+

Wins in a regime where startup latency and iteration speed dominate over peak throughput — a REPL-first or notebook-first workflow, or a language whose primary consumers never ship a standalone binary. CPython and early-era V8 embody this: a bytecode interpreter first, a JIT layered on later once hot paths are known via profiling. Rejected here because §1's deployment model targets standalone native executables as the primary artifact (systems programming, CI-produced binaries), and a JIT's warm-up cost and runtime code-generation attack surface (§22) are the wrong tradeoff for that target.

Alt B — LLVM-Backed Backend Instead Of A Custom x86_64/AArch64 Backend

SSA IR (this blueprint) -> LLVM IR translation layer -> LLVM optimizer+backend -> Object File

Wins when backend engineering effort must be minimized and multi-target support (many ISAs, not just two) matters more than build-time backend latency or bootstrap self-containment. Swift and Julia embody this: both target LLVM IR and inherit its instruction-selection and register-allocation maturity. Rejected here because self-hosting (§21) becomes materially harder with an external, non-self-hosted-in-this-language dependency in the trust chain, and the compile-time cost of LLVM IR generation plus LLVM's own optimizer conflicts with §4's cold-compile-throughput budget (M1, §28).

Alt C — Garbage-Collected Runtime Instead Of An Ownership Model

Source -> AST -> Typed IR -> SSA -> Codegen -> Executable
                                        |
                                 GC-managed heap (mark-sweep or generational)

Wins when developer ergonomics and compiler-implementation simplicity matter more than deterministic latency and memory-layout control — most application-level languages take this path. Go's cmd/compile and the OCaml toolchain embody it. Rejected here because §1 explicitly targets systems-programming use cases needing GC-pause-free execution, and because a GC's own allocator and collector would themselves need to be written in a language with no GC — circular for a self-hosting project without first solving the exact ownership problem this blueprint solves directly.

Alt D — Mutable, In-Place IR Instead Of Immutable Arena-Backed IR

AST --mutate--> MIR --mutate in place--> SSA --mutate in place--> Machine IR
        (each pass rewrites the previous stage's nodes directly)

Wins when single-threaded throughput on one large IR dominates and cross-pass concurrency is not needed — a smaller, throughput-only compiler with no incremental-compilation requirement. GCC's tree-SSA/GIMPLE pipeline substantially embodies this model historically. Rejected here because P2 (immutable IR boundaries) and P11 (replayability) both depend on being able to snapshot and diff IR state across passes without racing concurrent mutators (§16), which an in-place-mutation model makes substantially harder to retrofit than to design in from Phase 0.
