33. Hard Questions (Self-Examination)

  • Q1. How does a false-positive borrow rejection in §15 get distinguished operationally from a true optimizer miscompilation reported via the differential oracle in §16, given both can manifest as "the compiler altered a program the user believes is correct"?
  • Q2. If the semantic hash (§14) covers the resolved AST shape rather than source bytes, how does §20's invalidation propagation avoid resurrecting a stale MIR body when only whitespace changed but the arena's AstNodeId allocation order (§11) shifted?
  • Q3. Given P1's determinism principle (§6) and ADR-06's bounded-worker-pool choice (§9), what ordering guarantee makes 256 concurrent workers (§4) not violate I10's diagnostics-ordering invariant (§7)?
  • Q4. §21's stage2==stage3 proof only detects divergence, not root cause — how do §16's optimizer replay logs and §17's backend verifier jointly narrow a bootstrap mismatch to a single phase without re-running the entire pipeline?
  • Q5. §32's C7 shows FD usage at 87.5% of the §4 budget under peak 256-worker concurrency — what happens to §18's linker-subprocess isolation if a pathological package graph (§9's ADR-14) pushes past that ceiling?
  • Q6. §22's threat model treats procedural macros as an attack surface — how does that interact with §15's borrow/lifetime pass, which must analyze macro-expanded MIR it did not directly parse?
  • Q7. §28's M2 target (incremental recompile p99 < 2 s) is phase-gated at §20, alongside an 80% cache-hit-ratio acceptance criterion — what happens to M2 specifically on a cold cache immediately after a §25 schema-version bump?
  • Q8. §31 shows LLVM's mutable-in-place IR as the model ADR-09 (§9) rejects — under what workload does §16's immutable-IR replay-logging cost (P11, §6) exceed the concurrency benefit ADR-09 claims?
  • Q9. §35 defers distributed incremental compilation anchored at §20 — what invariant in §7 (I8, monotonic dependency graph) would need to be re-proven, not merely re-implemented, once cache state is sharded across machines?
  • Q10. §19's runtime uses a deterministic, non-randomized hasher for HashMap — how does that interact with §22's resource-exhaustion threat (hash-flooding), which the randomized-seed convention it deviates from was designed to mitigate?
  • Q11. §17's ADR-11 (§9) picks linear scan over graph coloring for implementation velocity — at what point does §28's spill-rate target (M11) force the documented fallback to graph coloring, and does that fallback threaten §4's per-compilation-unit codegen memory ceiling?
  • Q12. §26's differential-testing strategy against LLVM (§16, ADR-17 in §9) assumes LLVM is a trustworthy oracle — what does §16's own pitfall list imply about the limits of that assumption when a divergence is always attributed to this compiler's bug, never LLVM's?
  • Q13. §29 names trait-solver recursion as a bottleneck — how does that bottleneck compound with §14's fixpoint-cap enforcement (I13 in §7) once §21's self-hosting transition triples the effective source size the solver must process?
  • Q14. §24's SLO for 100% deterministic builds and §12's binary-diff CI gate both assume the CI runner's own toolchain is deterministic — what does §22's supply-chain-poisoning threat (T9) imply about trusting that assumption for the stage0 reference compiler itself?
  • Q15. §32's C9 bounds storage amplification at 3×, but §20's cache-eviction policy is LRU-by-content-address — under what edit pattern does LRU eviction interact badly with §21's bootstrap chain, which needs stage-specific artifacts retained past their last "use"?
  • Q16. §9's ADR-13 (content-addressed caching) and ADR-22 (monotonic time source) both reject timestamp-based mechanisms — does §23's FM-10 (daemon crash mid-write) still require some notion of write-ordering, and if so, where does it come from without violating either ADR?
  • Q17. §34's Alt B considers an LLVM-backed backend instead of the custom x86_64/AArch64 backend in §17 — if that alternative had been chosen, which invariant in §7 (I5, register allocation correctness) would transfer unchanged versus need re-derivation for LLVM's allocator internals?
  • Q18. §30's MM4 (fail-closed cache correctness) and §14's trait-solver-nontermination pitfall both describe systems that must stop rather than guess — what distinguishes a case where §6's P6 (bounded resources) should reject outright from one where §7's I13 depth ceiling should degrade gracefully?
  • Q19. §27's release-channel model and §25's ABI-stability window (I6) together imply a nightly build can break ABI — how does §17's ABI conformance suite avoid gating nightly the same way it gates stable, without silently letting an ABI break reach beta?
  • Q20. §33's own Q9 exposes a gap between §35's deferred-feature register and §7's invariants — does closing that gap belong in §34 (reconsidering a rejected architecture) or in a new §35 entry, and what distinguishes the two?
  • Q21. §4's 128 GB RAM vertical ceiling and §29's horizontal-scaling deferral together mean a 15M-LOC workspace has no supported configuration — does that gap belong to §29's scalability narrative or to §35's deferred-features register as an explicit un-defer trigger?
  • Q22. §19's no-GC runtime and §2's historical grounding both cite Go's self-hosting transition as precedent — what specifically does §19's ownership-based allocator make harder about self-hosting (§21) than Go's GC-backed runtime made it for cmd/compile?

30. Mental Models & First Principles

  • MM1 — Compilation Is A Pure Function Of (Source, Toolchain). Compressed insight: treat the whole pipeline as a pure function from content hash to artifact hash · predicts: any two builds with identical inputs must be byte-identical outputs · bug class without it: "works on my machine" nondeterminism no amount of single-build testing catches · applies in §12 and §20.
  • MM2 — IR Immutability Buys Concurrency For Free. Compressed insight: an IR stage that cannot be mutated after validation can be shared across threads with zero synchronization · predicts: any optimizer data race traces to an accidental mutation, not a missing lock · bug class without it: heisenbugs that vanish under a debugger because a race depends on scheduling timing · applies in §16.
  • MM3 — Dominance Frontiers Are The SSA Contract, Not An Implementation Detail. Compressed insight: phi-placement correctness is dominance-frontier correctness, nothing more · predicts: any "wrong SSA" bug reduces to a dominance-tree bug · bug class without it: patching individual phi symptoms instead of fixing the dominance computation once · applies in §16.
  • MM4 — A Cache's Correctness Is Its Failure Mode, Not Its Hit Rate. Compressed insight: a cache that serves wrong data rarely is worse than one with a low hit rate that never lies · predicts: fail-closed design is a correctness boundary, not a performance tradeoff · bug class without it: "rare" incremental-build bugs that are the cache confidently serving stale data · applies in §20.
  • MM5 — Bootstrap Trust Is Transitive, Not Absolute. Compressed insight: stage2==stage3 proves self-consistency, not correctness against an external spec · predicts: a bug present since stage0 passes the bootstrap proof forever · bug class without it: treating a clean bootstrap as proof of correctness rather than proof of reproducibility · applies in §21.
  • MM6 — Register Allocation Is Resource Scheduling Under a Deadline. Compressed insight: linear scan and graph coloring both trade allocation quality for allocation speed · predicts: spill-rate regressions correlate with live-range width, not code size · bug class without it: "optimize the allocator" efforts that tune the wrong parameter · applies in §17.
  • MM7 — ABI Stability Is A Promise To The Linker, Not To The Compiler. Compressed insight: the compiler's internals can change freely; only the ABI surface is a promise · predicts: an ABI break is invisible in unit tests and only appears at link or load time · bug class without it: shipping an "internal refactor" that silently breaks every downstream consumer · applies in §17 and §18.
  • MM8 — Determinism Is Necessary But Not Sufficient For Reproducibility. Compressed insight: a deterministic function of a non-deterministic input (an unpinned toolchain) still produces a non-reproducible build · predicts: reproducibility bugs often trace to environment capture, not compiler logic · bug class without it: chasing a "flaky compiler" bug that is actually an unpinned dependency · applies in §12 and §27.

5. Required Reading

Books

  • Engineering a Compiler — Cooper & Torczon (2011), ch. 8–10: SSA construction, optimization pipeline ordering, instruction scheduling; applied in §16 and §17.
  • Compilers: Principles, Techniques, and Tools — Aho, Lam, Sethi & Ullman (2006), ch. 4–6: recursive-descent and table-driven parsing, semantic analysis, runtime environments; applied in §13 and §14.
  • Advanced Compiler Design and Implementation — Muchnick (1997), ch. 12–17: dataflow-analysis frameworks, optimizer pass architecture, backend construction; applied in §16 and §17.
  • Linkers and Loaders — Levine (2000), ch. 3–8: ELF relocation semantics, symbol resolution, dynamic-linking edge cases; applied in §18.
  • Modern Compiler Implementation in ML — Appel (1998), ch. 10–12 and 19–20: SSA form, liveness analysis, graph-coloring register allocation; applied in §16 and §17.
  • Types and Programming Languages — Pierce (2002), ch. 22, 26, 30: type soundness proofs, bounded polymorphism, subtyping/coherence; applied in §14.
  • The Garbage Collection Handbook — Jones, Hosking & Moss (2011), ch. 7, 12: allocator design and object-metadata layout, relevant despite a non-GC runtime target; applied in §19.

Papers

  • "Efficiently Computing Static Single Assignment Form and the Control Dependence Graph" — Cytron, Ferrante, Rosen, Wegman & Zadeck, 1991, TOPLAS: dominance-frontier SSA construction → drives phi-node placement and the dominance verifier; applied in §16.
  • "Constant Propagation with Conditional Branches" — Wegman & Zadeck, 1991, TOPLAS: sparse conditional constant propagation (SCCP) → the pass manager's canonical folding pass; applied in §16.
  • "Register Allocation via Coloring" — Chaitin, Auslander, Chandra, Cocke, Hopkins & Markstein, 1981, Computer Languages: graph-coloring allocation as the rejected-alternative baseline → informs ADR-11's tradeoff column; applied in §17.
  • "Improvements to Graph Coloring Register Allocation" — Briggs, Cooper & Torczon, 1994, TOPLAS: optimistic coloring and spill-cost heuristics → the fallback allocator path when linear scan under-performs; applied in §17.
  • "Linear Scan Register Allocation" — Poletto & Sarkar, 1999, TOPLAS: single-pass allocation over SSA live ranges → the Phase 5 allocator's primary algorithm; applied in §17.
  • "LLVM: A Compilation Framework for Lifelong Program Analysis & Transformation" — Lattner & Adve, 2004, CGO: modular optimizer/pass-manager architecture → the differential-testing oracle and pass-manager layout; applied in §16 and §26.
  • "Translation Validation for an Optimizing Compiler" — Necula, 2000, PLDI: per-compilation proof-of-equivalence between pre- and post-optimization IR → the differential-testing methodology; applied in §26.
  • "Formal Verification of a Realistic Compiler" — Leroy, 2009, CACM (CompCert): machine-checked optimizer correctness → the design target for the deferred verified-optimizer-passes feature; applied in §35.

Reference Implementations

  • llvm/llvm-project — study llvm/lib/IR, llvm/lib/CodeGen, llvm/lib/Passes: modular IR and pass-manager separation; pitfall: do not copy LLVM's mutable-in-place IR mutation model — conflicts with P2's immutable-IR-boundary principle; applied in §16.
  • rust-lang/rust — study compiler/rustc_middle, compiler/rustc_query_system, compiler/rustc_borrowck: query-based incremental architecture and region-based borrow checking; pitfall: do not copy the historical AST→HIR duplication without a single stable node-ID scheme; applied in §15 and §20.
  • ziglang/zig — study src/codegen.zig, src/link.zig: single-pass backend lowering with minimal intermediate staging; pitfall: do not copy its historically volatile self-hosting bootstrap chain; applied in §17.
  • golang/go — study src/cmd/compile/internal/ssa, src/cmd/compile/internal/gc: SSA-based backend with a rewrite-rule optimizer; pitfall: do not copy its GC-coupled runtime layout assumptions into a GC-free target; applied in §16 and §19.
  • bytecodealliance/wasmtime — study cranelift/codegen: verification-adjacent backend with an explicit instruction-selection DSL; pitfall: do not copy its WASM-first calling-convention assumptions into native ABI lowering; applied in §17.

RFCs / Specifications

  • System V ABI — AMD64 Architecture Processor Supplement — pins the calling convention, stack alignment, and register-save rules the x86_64 backend must reproduce exactly; applied in §17.
  • DWARF Debug Information Format, Version 5 — pins the debug-metadata section layout the object emitter must produce; applied in §18.
  • Procedure Call Standard for the Arm 64-bit Architecture (AAPCS64) — pins the AArch64 calling convention and register-usage rules; applied in §17.
  • Tool Interface Standard — Executable and Linking Format (ELF) Specification — pins section/symbol/relocation layout for the object emitter; applied in §18.
  • Semantic Versioning 2.0.0 Specification — pins the package manifest's version-constraint grammar; applied in §12.
  • Rust RFC 2094 — Non-Lexical Lifetimes — pins the region-based liveness model the borrow/lifetime pass adapts for MIR; applied in §15.

Glossary (§36) · 52 terms · site-wide glossary

AST
Abstract syntax tree; the immutable, arena-backed parse output (§11).
MIR
Mid-level intermediate representation; the ownership-aware IR between typed AST and SSA (§8, §15).
SSA
Static single assignment; the optimizer-facing IR with explicit phi nodes (§8, §16).
CFG
Control-flow graph; the basic-block graph underlying MIR and SSA.
Dominance
A block A dominates B if every path from entry to B passes through A; the basis of SSA construction (Cytron et al. 1991, §5).
Dominance Frontier
The set of blocks where a definition's dominance "just" stops holding; determines minimal phi placement.
Phi Node
An SSA merge instruction selecting a value based on incoming control-flow edge.
ABI
Application binary interface; the calling-convention and layout contract (§17, I6).
LTO
Link-time optimization; whole-program optimization across translation units.
ThinLTO
A scalable, summary-based variant of LTO (deferred, §35).
DWARF
The debug-information format emitted alongside object code (§18).
Spill
A register allocator's fallback to a stack slot when live values exceed physical registers (§17).
Monomorphization
Generic specialization: one compiled instance per concrete type substitution.
Semantic Hash
A stable, structural hash of resolved program meaning, not source bytes (§14).
Arena Allocation
Bulk allocation with group-lifetime deallocation, avoiding per-node frees.
Trait Solver
The constraint-resolution engine for trait/interface bound satisfaction (§14).
Borrow Graph / Region Graph
The ownership-relation structure the borrow checker builds and verifies (§15).
Replay Build
A deterministic re-execution of a recorded build for debugging (P11).
Incremental Node
A cached, hash-keyed compilation artifact in the Incremental DB (§20).
Bootstrap Compiler
The initial, trusted (stage0) compiler used to build the first self-hosted stage.
Stage0 Compiler
The host-toolchain-built reference compiler that starts the bootstrap chain.
Stage1 Compiler
The compiler produced when stage0 builds the source.
Stage2 Compiler
The compiler produced when stage1 builds the source again.
Stage3 Compiler
The compiler produced when stage2 builds the source a third time, compared bit-for-bit against stage2 (I12).
SCCP
Sparse conditional constant propagation (Wegman & Zadeck 1991, §5).
LICM
Loop-invariant code motion.
Linear Scan
A single-pass register-allocation algorithm over SSA live ranges (Poletto & Sarkar 1999, §5).
Graph Coloring
A register-allocation algorithm modeling allocation as graph coloring (Chaitin et al. 1981, §5).
Content-Addressed Cache
A cache keyed by a hash of its content rather than a name or timestamp (ADR-13).
Lockfile
A deterministic, pinned record of resolved package versions (§11 PackageManifest).
SemVer
Semantic Versioning 2.0.0; the version-constraint grammar for packages (§5 RFCs).
TOML
The configuration/manifest serialization format (ADR-15).
postcard
The deterministic binary serialization format used for the incremental cache (ADR-03).
Distroless
A minimal container base image with no shell or package manager (ADR-19).
cosign
A keyless, OIDC-based artifact-signing tool (ADR-20).
SBOM
Software Bill of Materials; a generated manifest of every dependency in a release (§27).
Differential Testing
Comparing this compiler's output against a reference (LLVM) for behavioral agreement (§26).
Chaos Testing
Fault injection (crash, corruption) to validate recovery paths (§26).
Crash-Only Design
A system whose only recovery path is restart-and-replay, never in-place repair (P7).
NUMA
Non-uniform memory access; informs worker-pool scheduling locality (§4).
FD
File descriptor; a bounded, budgeted OS resource (§4).
RTO / RPO
Recovery Time Objective / Recovery Point Objective; recovery-speed and data-loss budgets (§4).
p50 / p95 / p99
Latency percentiles; p99 bounds the worst case relevant to interactive tools.
Backpressure
Rejecting or delaying work when a bounded queue is full, rather than growing it unboundedly (P6).
Escape Analysis
Detecting whether a borrow outlives its referent's scope (§15).
Move Semantics
Ownership transfer that invalidates the source binding (§8, §11).
Drop Elaboration
Computing explicit destructor-call points from implicit scope-exit semantics (§15).
Coherence Check
Verifying no two trait implementations overlap ambiguously (§14).
Interned Identifier
A deduplicated, O(1)-comparable identifier string (§13).
Trivia
Whitespace and comments preserved losslessly alongside tokens (§13).
Recursive Descent
A top-down, grammar-production-driven parsing strategy (ADR-07).
Pratt Parsing
Operator-precedence expression parsing used within the recursive-descent parser (§13).
