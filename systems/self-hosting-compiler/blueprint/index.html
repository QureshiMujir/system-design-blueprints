1. Goal & Scope

Engineering definition. A self-hosting compiler toolchain for a statically typed, ownership-based, ahead-of-time systems language: lexer → parser → typed MIR → SSA IR → optimizer → machine code → native ELF/Mach-O/PE executable, capable of recompiling its own source tree and reproducing a bit-identical binary at stage2 == stage3. "Self-hosting" is the terminal correctness proof of the entire pipeline — a bug anywhere upstream eventually manifests as a bootstrap divergence.

Phase 0 deliverable — crates/services stood up in §12:

  1. compiler/driver — orchestration skeleton, CLI entry, deterministic exit codes.
  2. compiler/diagnostics — structured diagnostics engine (spans, categories, machine-readable emission).
  3. compiler/incremental (hashing subset only) — semantic hashing library, content-addressed keys.
  4. Source loader abstraction (compiler/driver::loader) — UTF-8 validation, mmap, canonical paths.
  5. Reproducible Docker builder image + pinned toolchain manifest.
  6. Benchmark harness scaffold (benchmarks/) wired into CI.
  7. Fuzz target scaffold (fuzz/) with libFuzzer harness stubs.
  8. Lockfile format definition (consumed later by package-manager/resolver).
  9. Telemetry event schema (tracing spans + structured JSON log fields).
  10. SBOM generation step wired into the release pipeline.
  11. Crash-dump capture path with panic-time flush guarantees.
  12. CI matrix (Linux x86_64, Linux AArch64, macOS) with binary-diff reproducibility gate.

System boundaries.

  • Provides: lexer, parser, AST, semantic analysis, symbol resolution, trait/interface solving, monomorphization, typed MIR, SSA IR, optimizer pipeline, register allocation, x86_64 and AArch64 backends, object emission, external-linker integration, package manager, build-graph engine, test harness, deterministic bootstrap, minimal standard library, runtime support, incremental compilation cache, diagnostics engine, DWARF debug info, observability instrumentation.
  • Delegates: final link step to the host system linker (ld/lld/link.exe), C runtime startup objects to the host toolchain during Phase 0 bootstrap only, OS scheduling/paging to the kernel, container build reproducibility to a pinned Docker base image.
  • Does NOT provide (Phase 0 exclusions): JIT execution, garbage collection, a distributed compilation farm, an IDE, GUI tooling, a full semantic-indexing language server (a minimal LSP textDocument/* surface only), a WebAssembly backend, a GPU backend, a formal verification framework, hot reloading.

Non-goals: dynamic language support, reflection-heavy metaprogramming beyond hygienic procedural macros, cross-language ABI beyond C FFI, a package-registry federation protocol (single canonical registry only in Phase 0).

Deployment model: standalone CLI executable (primary); local daemonized incremental-compilation process communicating over a Unix domain socket (secondary); build-graph orchestration process invoked by CI runners and developer workstations. Primary targets: Linux x86_64, Linux AArch64. Secondary: macOS, Windows (PE/COFF, MSVC ABI compatibility only — no independent Windows backend work in Phase 0).

Target operators: systems programmers and compiler engineers (authors), CI/release engineering teams and package-registry maintainers (operators), compiler-backend/runtime/stdlib maintainers (long-term owners).

What later phases unlock: distributed incremental compilation (§20 extension), profile-guided optimization (§16 extension), ThinLTO cross-module optimization (§18 extension), a WebAssembly backend (§17 extension), verified/formally-checked optimizer passes (§16 extension), and eventually a compiler-as-a-service execution model built on the daemonized incremental core from §20.

Recommended language: Rust. Rationale: deterministic ownership semantics remove an entire class of aliasing bugs from compiler-internal mutable state (arenas, caches, pass pipelines); sum-type (enum) modeling matches AST/MIR/SSA node shapes precisely; the cargo/crates.io ecosystem has mature parser combinators, tracing, criterion, and cargo-fuzz tooling; FFI to the host C toolchain (linker, libc startup objects) is a first-class, zero-cost path; postcard/serde give deterministic binary serialization for the incremental cache. Rejected: C++ (template instantiation and lifetime rules are ambiguous enough to make compiler-internal aliasing bugs a permanent tax); Go (no manual control over allocation layout or cache-line placement in the register allocator's hot path, and a GC pause budget the compiler itself cannot bound); Zig (2020s-era ecosystem too immature for a 10-module, multi-year compiler infrastructure project — comptime is attractive but standard-library and tooling churn is a maintenance risk); OCaml (its own runtime and GC constraints complicate producing a GC-free ownership-based target language, and systems-level FFI/linking ergonomics lag Rust's).

Prerequisites: compiler construction, parsing theory, type systems, graph algorithms, SSA construction (Cytron et al. 1991), register allocation (linear scan and graph coloring), calling- convention/ABI conventions, ELF/Mach-O/PE object formats, CPU architecture (x86_64, AArch64), lock-free data structures, cache-locality reasoning, allocator design, reproducible-build engineering, observability engineering, fuzzing methodology.

Estimated timeline: Phase 0 (§12) — 6 to 14 weeks (repo, CI, hashing, diagnostics scaffold, telemetry). Full production system (all ten phases through self-hosting, §21) — 12 to 24 months, gated by optimizer maturity, ABI stability, and incremental-compilation correctness, not calendar time.

2. Why Build This

A self-hosting compiler is the hardest small-team systems project that forces correctness, determinism, ABI compatibility, reproducibility, optimizer soundness, and backward compatibility to be load-bearing simultaneously — not sequentially. Unlike a toy compiler, it permanently exercises the bootstrap trust chain (stage0 → stage1 → stage2 → stage3), version-skew management across its own releases, runtime-ABI compatibility with itself, incremental-cache schema evolution, binary stability guarantees, and incremental-recompilation correctness under real edit patterns — because the compiler is both the producer and the most demanding consumer of its own output.

Historical grounding. Smalltalk-80, the Lisp machine compilers, GCC, LLVM/Clang, rustc, the Go compiler (cmd/compile), and the OCaml toolchain are the reference class: each became historically significant specifically at the moment it became self-hosting, because self-hosting is the point at which optimizer correctness, ABI stability, and deterministic-build discipline stop being aspirational and start being load-bearing for the project's own survival — a miscompilation in the optimizer no longer just breaks a test suite, it can silently corrupt the next compiler binary.

Engineering muscles developed: graph transformation (CFG/dominance/dataflow), memory-layout reasoning (arena allocation, cache-line-aware structs), protocol design discipline (wire formats for the incremental cache and package manifests), deterministic execution modeling, crash-consistency reasoning (crash-only incremental daemon), large-scale refactoring across a multi-crate workspace, performance engineering under measured budgets (§4/§28), and a debugging methodology built on deterministic replay rather than ad hoc reproduction.

Production concepts exercised: arena allocation, IR canonicalization, dependency-graph invalidation, deterministic hashing, replay debugging, stable serialization, parallel work-stealing scheduling, incremental recomputation, object emission, linker interoperability, DWARF generation, package-integrity verification (signing, lockfiles).

Cross-project calibration. Compiler infrastructure shares architecture with database query planners (cost-based pass ordering, plan/IR canonicalization), distributed DAG schedulers (the build graph engine, §3), transactional storage engines (the incremental cache's content-addressed, fail-closed design), and execution engines (the SSA optimizer's dataflow fixpoints). A team that has built this has effectively built a compiler, a small database engine, and a small distributed scheduler under one roof.

What Mastery Looks Like

  • Dominance-frontier SSA construction from first principles — can derive and debug phi-node placement without a reference implementation open; exercised end-to-end in Phase 4 (§16).
  • Ownership/borrow analysis as a dataflow problem, not a type-system trick — can diagnose a false-positive borrow rejection by reading the region graph; built in Phase 3 (§15).
  • Deterministic incremental recomputation — can explain why a given edit invalidates exactly the nodes it invalidates, no more, no less; built and load-bearing from Phase 8 (§20) onward.
  • ABI-correct code generation — can hand-trace a SysV or AAPCS64 calling-convention lowering and spot a callee-save violation; built in Phase 5 (§17).
  • Bootstrap trust-chain reasoning — can explain what stage0→stage3 comparison actually proves and what it does not; built in Phase 9 (§21).
  • Fail-closed cache design — can design a cache whose corruption mode is "rebuild", never "serve wrong answer"; built in Phase 8 (§20) and stress-tested by the threat model (§22).
  • Differential-testing methodology against a mature reference optimizer (LLVM) — can construct an oracle and interpret a divergence; built in Phase 4 (§16) and used through Phase 9 (§21).

Developer CLI — stateless entry point beyond local config resolution; drives build invocation, package operations, diagnostics formatting, target/profile selection, reproducibility flags. Build Graph Engine — deterministic dependency DAG across packages, modules, cache keys, and backend outputs; owns invalidation propagation and execution ordering (ADR-13, I8). Package Resolver — semantic-version constraint solving, lockfile generation, integrity verification, registry HTTP client; the only subsystem that crosses the network trust boundary. Compilation Orchestrator — the concurrency boundary: bounded worker pool (P6, I9's lock ordering governs its shared structures), phase sequencing, diagnostics aggregation, artifact lifecycle. Source Loader — canonical filesystem load, UTF-8 validation, mmap, source hashing; feeds the Incremental DB's cache keys. Incremental DB — the persistence boundary: content-addressed store keyed by stable semantic hashes, fail-closed on corruption (I11), the only subsystem with on-disk state outside artifacts. Diagnostics — centralized structured diagnostics with deterministic lexical ordering (I10), machine-readable emission for tooling. Lexer/Parser/AST Arena — canonical tokenization → lossless recursive-descent parse → immutable arena-owned AST with stable 64-bit node IDs (I1). Semantic Pass — name resolution, type inference, trait solving, coherence, visibility. Typed MIR / Borrow-Lifetime Pass — ownership-aware IR; the only subsystem permitted to reject a program for aliasing reasons (I3). SSA IR / Optimization Pipeline — dominance-based SSA (Cytron et al. 1991) with a deterministic pass manager (SCCP, DCE, LICM, inlining, CFG simplification). Backend Lowering / x86_64 + AArch64 Codegen — the protocol boundary to target-specific Machine IR; instruction selection, calling-convention lowering, linear-scan register allocation (ADR-11). Object File Emitter — ELF/Mach-O/PE with deterministic section/symbol ordering (I7) and DWARF v5. Linker Integration — the external-interface/subprocess boundary to the host linker (ADR-12). Executable Artifact — the terminal, bit-reproducible output (P1).

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every compilation output must be bit-for-bit reproducible given identical source and toolchain version · Tradeoff: forecloses racing multiple scheduling heuristics for speed · Operational: binary-diff CI gate on every merge · Violated: a non-reproducible output silently poisons the incremental cache (I2) and stage2/stage3 comparison (I12) fails without an obvious cause.
  • P2 — Immutable IR Boundaries. Rule: every IR stage (AST, MIR, SSA, Machine IR) is immutable once validated by its verifier pass · Tradeoff: costs an extra allocation/copy per transformation instead of in-place mutation · Operational: verifier runs post-construction, pre-handoff to the next stage · Violated: concurrent passes race on shared mutable state and produce non-reproducible optimization order, breaking P1.
  • P3 — Stable Hashing Everywhere. Rule: every cache key derives from a stable semantic hash, never a timestamp or pointer address · Tradeoff: hash computation sits on the critical path of every incremental decision · Operational: hash layout is explicitly versioned (ADR-13) · Violated: stale cache entries resurrect under hash-algorithm drift, violating I2 and I8.
  • P4 — Explicit Ownership Transfer. Rule: ownership moves must be visible in the API signature, not inferred from usage patterns · Tradeoff: more verbose call sites inside the compiler's own crates · Operational: borrowck enforces at MIR level (§15) · Violated: hidden aliasing produces double-free-class bugs in the runtime allocator (§19).
  • P5 — Observability By Default. Rule: every pass emits timing, memory, and invalidation-reason telemetry with no opt-in flag · Tradeoff: baseline tracing overhead on every compilation, budgeted in §28 · Operational: tracing spans keyed by pass name (ADR-04) · Violated: a regression stays invisible until a user reports it, with no data to root-cause the slowdown.
  • P6 — Bounded Resource Usage. Rule: no unbounded queues, recursion, allocation, or task spawning anywhere in the pipeline · Tradeoff: pathological inputs are rejected with a diagnostic instead of processed to exhaustion · Operational: worker pool capped at 256 (§4), depth counters at every recursive call site · Violated: a crafted deeply nested generic exhausts the stack before the diagnostic fires (I13).
  • P7 — Crash-Only Incremental Services. Rule: the daemonized incremental process recovers only by restart-and-replay, never in-place partial repair · Tradeoff: every crash costs a bounded replay window (§4) instead of a cheaper targeted fix · Operational: I11's fail-closed cache semantics · Violated: an ad hoc repair path becomes a second, untested recovery code path that itself needs recovery.
  • P8 — Structured Diagnostics. Rule: every diagnostic is machine-readable before it is human-readable · Tradeoff: more upfront schema design than a printf-style error · Operational: compiler/diagnostics is the sole emission point (I10) · Violated: tooling cannot consume free-text errors, breaking the minimal-LSP surface (§1).
  • P9 — Stable Wire and Storage Formats. Rule: every serialized format carries an explicit version tag · Tradeoff: every format change needs an explicit migration path, never a silent reinterpretation · Operational: postcard encoding with a versioned schema (ADR-03) · Violated: a compiler upgrade silently misreads an old cache and hands corrupt MIR downstream (FM-3).
  • P10 — No Hidden Global State. Rule: compiler passes may not mutate hidden singleton/global state · Tradeoff: explicit context threading through every pass signature · Operational: pass functions take an explicit PassContext parameter · Violated: two passes running concurrently on different modules silently interfere, breaking P1's determinism.
  • P11 — Replayability First. Rule: every build supports deterministic replay from its recorded inputs · Tradeoff: replay logs cost storage, bounded by cache compaction (§4) · Operational: optimization replay logs in the SSA pass manager (§16) · Violated: a reported miscompilation cannot be reproduced offline and root-causing regresses to guesswork.
  • P12 — Correctness Before Optimization. Rule: no optimization pass ships until its correctness fixture suite is green, regardless of measured speedup · Tradeoff: leaves measured performance on the table until fixtures exist · Operational: pass gated by fixture suite in the pass registration table (§16) · Violated: an aggressive but unsound fold generates a binary that crashes only under a rare input distribution (FM-4).
  • P13 — External Linker First. Rule: Phases 0 through 6 delegate final linking to the host linker, never an internal one · Tradeoff: subprocess overhead and a host-toolchain dependency in the trust chain · Operational: ADR-12's rejected-alternative-wins regime is a hermetic-build internal linker · Violated: assuming an internal linker exists before it is built stalls Phase 6 on unscoped work.
  • P14 — Fail-Closed Cache Semantics. Rule: any detected cache corruption purges and rebuilds rather than serving a possibly-wrong cached artifact · Tradeoff: a corruption event costs a full rebuild window (RTO, §4) instead of best-effort partial recovery · Operational: checksum verification on every cache read (I11) · Violated: a torn write from a mid-flush crash is served as valid and corrupts a downstream build.

Debugging methodology: every invariant above has exactly one runtime assertion, no more, that fires inside a deterministic simulator harness (conformance/) driving recorded input traces through the pipeline single-threaded and multi-threaded. A violation reproduces byte-for-byte from the trace file alone — no live system access is required to root-cause it (P11). Assertions are compiled into release builds at reduced sampling rate, not stripped, because I6/I11/I12 violations must never ship silently.

8. Domain Model — Source Language, IR Pipeline & Bootstrap Chain

Language model. Statically typed, ahead-of-time compiled, ownership-based, generic, trait-oriented, deterministic. No garbage collector; no runtime reflection beyond hygienic procedural macros expanded at compile time.

Lexical grammar (token categories): identifiers, keywords, literals, delimiters, operators, attributes, comments (preserved as trivia, not discarded).

ident      = (alpha | "_") , { alpha | digit | "_" } ;
literal    = int_lit | float_lit | str_lit | char_lit ;
keyword    = "fn" | "struct" | "enum" | "trait" | "impl" | "let" | "mut" | "match" ;
attribute  = "#" , "[" , ident , [ "(" , arg_list , ")" ] , "]" ;
token      = ident | keyword | literal | delimiter | operator | attribute ;

AST model — core node kinds: Module, Function, Struct, Enum, Trait, Impl, Block, Expr, Pattern, TypeRef. Every node carries a stable 64-bit AstNodeId (I1) and a byte span into its owning SourceFile.

MIR semantics. MIR represents ownership moves, borrows, explicit drops, and explicit control flow as basic blocks with terminators — no implicit destructor ordering, no hidden control flow.

SSA semantics. SSA guarantees single assignment, explicit phi nodes at merge points, and a canonical CFG shape post-simplification (I4).

Canonical lowering pipeline:

Source --lex/parse--> AST --sema--> Typed AST --lower--> Typed MIR
       --borrowck--> Verified MIR --lower--> SSA IR --optimize--> Optimized SSA
       --lower--> Machine IR --select/allocate--> Machine Function
       --emit--> Object File --link--> Executable Artifact

Compilation state machine:

State Meaning Exit Condition
Parsed AST structurally valid semantic pass succeeds
Typed names/types resolved MIR lowering begins
MIR Verified ownership valid (I3) SSA lowering begins
Optimized pass manager converged (I4) codegen begins
Emitted object file generated (I7) linker invocation succeeds
Linked executable artifact produced artifact hash recorded in Incremental DB

Failure-path example — malformed generic recursion: a trait bound of shape trait A<T: A<T>> (unbounded self-referential constraint) must be rejected by recursion-depth detection (I13) in the trait solver with a deterministic diagnostic (P8) — never a stack overflow, never a compiler crash. The bootstrap chain (stage0 → stage1 → stage2 → stage3, I12) treats a crash here as a Sev-1: it means the compiler cannot safely reject its own pathological input, which is a prerequisite for trusting it to reject anyone else's.

11. Core Schema & Types

  • SourceFile — struct SourceFile { file_id: FileId, canonical_path: PathBuf, content_hash: Blake3Hash, utf8_buffer: Arc<str>, line_index: LineIndex } — Ownership: Arc-shared, immutable post-construction · Mutation: none (P2) · Concurrency: safe multi-thread share, no interior mutability · Persistence: not persisted directly, feeds IncrementalKey · Serialization: not serialized whole · Compatibility: hash algorithm version-tagged (ADR-13).
  • Token — struct Token { kind: TokenKind, byte_span: Span, trivia_range: TriviaRange } — Ownership: owned by the token stream, copied by value (small, Copy) · Mutation: immutable once lexed · Concurrency: Send/Sync, freely shared · Persistence: not persisted · Serialization: deterministic binary encoding for parser benchmark corpora · Compatibility: TokenKind enum is additive-only across minor versions.
  • AstNodeId — struct AstNodeId(u64) — Ownership: value type, Copy · Mutation: immutable · Concurrency: trivially shareable · Persistence: keys incremental dependency edges (I8) · Serialization: deterministic binary encoding · Compatibility: allocation scheme fixed by I1, never renumbered across a reparse.
  • TypedNode — struct TypedNode { node_id: AstNodeId, inferred_type: TypeId, borrow_state: BorrowState, scope_id: ScopeId } — Ownership: owned by the type arena · Mutation: write-once during Phase 2 (§14), immutable after · Concurrency: read-shared post-sema · Persistence: cached under IncrementalKey · Serialization: postcard-encoded (ADR-03) · Compatibility: BorrowState variants are additive-only.
  • MirBody — struct MirBody { basic_blocks: Vec<BasicBlock>, locals: Vec<LocalDecl>, drops: Vec<DropPoint>, terminators: Vec<Terminator> } — Ownership: owned by the MIR arena, immutable post-verification (P2) · Mutation: mutable only during construction (§15), frozen after MirVerifier passes (I3) · Concurrency: read-shared across the optimizer's worker pool · Persistence: cached under IncrementalKey · Serialization: postcard-encoded · Compatibility: block/local indices are stable within one compilation, not across recompilation.
  • SsaFunction — struct SsaFunction { blocks: BlockGraph, phi_nodes: Vec<PhiNode>, dominance_tree: DomTree, value_table: ValueTable } — Ownership: owned by the SSA arena · Mutation: immutable post-verification (I4) · Concurrency: read-shared across optimization passes · Persistence: replay logs retain a serialized snapshot per pass (P11) · Serialization: postcard-encoded · Compatibility: ValueTable numbering is per-compilation only.
  • MachineFunction — struct MachineFunction { vregs: Vec<VirtualRegister>, instructions: Vec<MachineInst>, frame_layout: FrameLayout } — Ownership: owned by the backend, one per compilation unit · Mutation: mutable during instruction selection/allocation, frozen after BackendVerifier (I5) · Concurrency: one MachineFunction per worker, no cross-thread sharing needed · Persistence: not cached (regenerated per build) · Serialization: consumed directly by the object emitter · Compatibility: FrameLayout respects the ABI window in I6.
  • PackageManifest — struct PackageManifest { name: PackageName, version: SemVer, dependencies: DepGraph, features: FeatureFlags } — Ownership: owned by the package resolver · Mutation: immutable once parsed from Cargo.toml-equivalent · Concurrency: read-shared during resolution · Persistence: persisted in the lockfile (package-manager/integrity/lockfile.rs) · Serialization: TOML on disk, postcard in the resolver's internal graph · Compatibility: follows SemVer 2.0.0 (§5 RFCs).
  • IncrementalKey — struct IncrementalKey { compiler_version: VersionId, target_triple: TargetTriple, semantic_hash: Blake3Hash } — Ownership: value type, Copy-able composite key · Mutation: immutable · Concurrency: used as a hash-map key under the Incremental DB's lock ordering (I9) · Persistence: the primary key of every cache entry · Serialization: postcard-encoded, version-tagged (P9) · Compatibility: a compiler_version bump invalidates all keys deterministically (never silently reinterpreted).
  • Diagnostic — struct Diagnostic { category: DiagCategory, severity: Severity, primary_span: Span, secondary_spans: Vec<Span>, notes: Vec<Note>, suggestions: Vec<Suggestion> } — Ownership: owned by the diagnostics sink until flushed · Mutation: builder-mutable until emitted, immutable after (P8) · Concurrency: per-worker diagnostic buffers merged under I10's ordering rule at flush · Persistence: not persisted beyond the current build's log · Serialization: machine-readable JSON for tooling, human-readable render for the terminal · Compatibility: DiagCategory is additive-only across releases.
  • CacheEntry — struct CacheEntry { key: IncrementalKey, payload: Bytes, checksum: Crc32, schema_version: u16 } — Ownership: owned by the Incremental DB · Mutation: immutable once written; a mismatch triggers purge, never in-place patch (P14) · Concurrency: read-shared, write-once-per-key under I9's lock ordering · Persistence: on-disk content-addressed store · Serialization: postcard-encoded · Compatibility: schema_version mismatch is a hard fail-closed (I11).
  • WorkerTask — trait WorkerTask { fn phase(&self) -> PhaseId; fn run(self, ctx: &PassContext) -> Result<PhaseOutput, Diagnostic>; } — Ownership: moved into the worker pool queue, consumed on execution · Mutation: not applicable (behavior, not state) · Concurrency: Send, dispatched across the bounded pool (§4, ADR-06) · Persistence: not persisted · Serialization: not serialized · Compatibility: PhaseId enum is additive-only.

  • Implement compiler/diagnostics/emitter.rs: structured diagnostics satisfying P8, deterministic lexical ordering (I10).
  • Add tracing subscriber initialization (ADR-04) emitting spans keyed by pass name; wire into compiler/driver/orchestrator.rs.
  • Implement the lockfile format package-manager/integrity/lockfile.rs — deterministic, sorted-key serialization.
  • Configure benchmarks/ (Criterion-based) and fuzz/ targets (libFuzzer via cargo-fuzz, ADR-16).
  • Add the reproducible Docker builder image (Dockerfile) with a pinned toolchain (rust-toolchain.toml); wire SBOM generation into .github/workflows/release.yml.
  • Implement version-metadata injection: compiler version string embedded at build time, consumed by IncrementalKey.compiler_version (§11).
  • Configure the CI matrix (.github/workflows/ci.yml) across Linux x86_64/AArch64 and macOS, plus .github/workflows/reproducibility.yml's binary-diff gate (I7 precursor).
  • Implement structured crash-dump capture with panic-time flush guarantees (P7's crash-only precursor).
  • Add deterministic filesystem traversal (sorted directory iteration, no OS-order dependence) and path canonicalization.

12.3 Deliverable

A runnable compiler/cli/main.rs driver skeleton: parses arguments (compiler/cli/args.rs), resolves config (compiler/cli/config.rs), loads sources, emits a structured no-op diagnostic, and exits deterministically. Reproducible binary hash across repeated CI builds; telemetry spans visible to any tracing-compatible collector; operator can inspect driver.startup_latency_ms directly.

12.4 Acceptance Criteria

  • CI green on Linux x86_64, Linux AArch64, and macOS.
  • Reproducible binary hashes: 100 consecutive CI builds produce an identical SHA-256 of the driver binary.
  • CLI startup p50 < 70 ms, p99 < 200 ms (§4; enforced by M3/M4, §28).
  • fixtures/path-normalization/ and fixtures/hash-determinism/ suites pass at 100%.

12.5 Conformance Fixtures

  • fixtures/path-normalization/symlink-loop — cyclic symlink must be detected and rejected, not followed into an infinite loop.
  • fixtures/path-normalization/non-utf8-path — malformed path bytes must produce a diagnostic, not a panic (malformed case).
  • fixtures/lockfile/concurrent-write — two concurrent lockfile writers must serialize deterministically (regression case).
  • fixtures/hash-determinism/replay-1000 — 1,000 replayed hash computations over identical input must be byte-identical (replay case).

12.6 Pitfalls

  1. Hidden timestamp usage in build metadata — manifestation: reproducibility CI job flags a diff · root cause: SystemTime::now() leaking into an embedded build string · debugging: binary-diff bisection over build artifacts · signal: I7's reproducibility-success-rate metric drops · recovery: strip wall-clock reads from the build path, inject version metadata explicitly.
  2. Nondeterministic directory iteration — manifestation: intermittent CI flakiness in file-list ordering · root cause: raw readdir order is filesystem-dependent · debugging: diff file-list order across reruns · signal: hash-determinism fixture flakes · recovery: sort every directory listing before use.
  3. Locale-sensitive path handling — manifestation: CI passes on one runner, fails on another · root cause: OS-locale-dependent case folding on path comparison · debugging: reproduce under LC_ALL=C vs. a non-C locale · signal: path-normalization fixture diverges by runner · recovery: force byte-wise path comparison, never locale-aware comparison.
  4. Crash logs truncating on panic — manifestation: forensics postmortem missing the final frames · root cause: buffered log writer not flushed before process abort · debugging: reproduce under a debugger with a breakpoint on the abort path · signal: FM-1-class reports lack the panic message · recovery: register a panic hook that force-flushes before unwind/abort.

12.7 Performance Concerns

  • Startup allocation count: bounded arena pre-sized to avoid per-argument heap churn.
  • Tracing overhead: span creation deferred until after argument parsing, off the cold-start critical path.
  • Hash computation locality: chunked Blake3 hashing over mmap'd pages preserves cache locality (§4 CPU baseline).

12.8 Edge Cases

  • Symlink loops in the workspace tree.
  • Invalid UTF-8 byte sequences in file paths (distinct from file contents).
  • Concurrent lockfile writes from two CI jobs racing on the same cache.
  • Clock skew between CI runners producing spuriously "newer" cached artifacts — mitigated by P3 (no timestamp-based invalidation anywhere in the pipeline).

12.9 Failure Analysis

Failure class: nondeterministic builds (FM-11). Detection: the reproducibility CI job's binary-diff gate. Blast radius: every downstream cache entry keyed on this build's hash is suspect. Containment: block release-channel promotion (§27) until the diff gate is green. Recovery path: bisect the build to the offending timestamp- or order-dependent line. Operator visibility: reproducibility.yml annotates the exact differing byte offset in the job summary.

12.10 Operational Notes

  • Metrics: driver.startup_latency_ms, driver.reproducibility_success_rate, driver.crash_frequency.
  • Tracing spans: driver.load, driver.hash, driver.diagnostics_flush.
  • Structured-log fields: build_id, compiler_version, content_hash.
  • Deployment: ships as a single CLI binary; rollback is "pin the previous compiler_version tag" — no in-place migration exists at this phase.

13. Phase 1 — Lexer & Parser

13.1 Objectives

  • Implement a deterministic lexer and a lossless-syntax-tree parser with error recovery, satisfying I1 (AST node stability) and I13 (bounded recursion depth) from day one.
  • Scope: tokenization, trivia preservation, recursive-descent parsing with Pratt expression parsing, immutable arena-backed AST construction.

13.2 Detailed Implementation Steps

  • Define the token taxonomy in compiler/lexer/token.rs per the EBNF in §8.
  • Implement the UTF-8 scanner compiler/lexer/scanner.rs with lossless trivia preservation (compiler/lexer/trivia.rs) — comments and whitespace round-trip exactly.
  • Implement the interned identifier table compiler/lexer/interner.rs (string interning, O(1) identifier comparison).
  • Build the recursive-descent grammar compiler/parser/grammar.rs and the Pratt expression parser compiler/parser/pratt.rs (ADR-07's ADR rationale: superior diagnostics over a generated LALR parser).
  • Implement error-recovery synchronization sets compiler/parser/recovery.rs — on parse failure, resynchronize at statement/block boundaries rather than aborting the file.
  • Build immutable AST arenas compiler/ast/arena.rs with stable node allocation (I1) via AstNodeId (§11).
  • Implement span tracking through compiler/parser/tree_builder.rs; add parser-internal tracing spans (P5).
  • Build the AST serializer for benchmark corpora and the syntax-tree verifier (structural well- formedness, not semantic).
  • Implement incremental reparsing: an edited byte range invalidates only the AST subtree whose span intersects the edit (I1's contract).
  • Add the parser benchmark corpus under benchmarks/parser_throughput.rs and malformed-token fixtures.
  • Enforce recursion-depth ceilings (I13) at every recursive-descent call site — Appel (1998) ch. 3's recursive-descent formulation, with an explicit depth counter Appel's presentation omits.

13.3 Deliverable

A parser producing stable, span-accurate ASTs for both valid and malformed inputs, exercised over the benchmarks/parser_throughput.rs corpus and fuzzed continuously via fuzz/fuzz_parser.rs.

13.4 Acceptance Criteria

  • 100% pass rate on the grammar fixture suite (≥ 200 fixtures).
  • Zero parser crashes across 10M+ fuzz executions (fuzz/fuzz_parser.rs, ADR-16).
  • AST node IDs stable across whitespace-only edits (I1), verified by fixtures/parser/reparse-stable.
  • Single-file parse p95 < 30 ms (§4; enforced by M5, §28).

13.5 Conformance Fixtures

  • fixtures/parser/malformed-generics — trait A<T: A<T>>-shaped unbounded recursive bound must hit the recursion-depth ceiling (I13), not overflow the stack (malformed case).
  • fixtures/parser/nested-macros — deeply nested procedural-macro invocation sites must parse without quadratic blowup.
  • fixtures/parser/unicode-identifiers — non-ASCII identifier scalars must round-trip through the interner unchanged.
  • fixtures/parser/recovery-resync — a missing closing brace must resynchronize at the next top-level item, not cascade errors through the rest of the file (regression case).
  • fixtures/parser/reparse-stable — replaying 1,000 incremental whitespace edits must not change any AstNodeId outside the edited span (replay case).

13.6 Pitfalls

  1. Exponential parser backtracking — manifestation: pathological input takes seconds instead of microseconds · root cause: unbounded lookahead in an ambiguous expression grammar · debugging: profile with a per-production call counter · signal: parser throughput metric collapses on one fixture · recovery: convert to Pratt-style precedence climbing (already the ADR-07 baseline) and cap lookahead.
  2. Span corruption after recovery — manifestation: diagnostics point at the wrong source location post-recovery · root cause: recovery routine advances the token cursor without re-basing span offsets · debugging: golden-file diff of span output before/after a malformed-input fixture · signal: fixtures/parser/recovery-resync regression · recovery: recompute spans relative to the resynchronization token, not the original error site.
  3. Arena fragmentation — manifestation: memory ceiling (§4, 1.5 GB) exceeded on large workspaces · root cause: many small, short-lived AST nodes freed individually instead of arena-reset · debugging: heap profile via benchmarks/parser_throughput.rs under a 10M-LOC corpus · signal: parser memory metric trends upward across incremental edits · recovery: arena-per-file reset on invalidation instead of per-node deallocation.
  4. Stack overflow from recursive parsing — manifestation: crash, not diagnostic, on deep nesting · root cause: I13's depth ceiling not enforced at every mutually recursive production · debugging: reproduce with fixtures/parser/malformed-generics under ASan · signal: fuzz corpus finds a crash · recovery: thread an explicit depth parameter through every recursive production, not just the top-level entry point.

13.7 Performance Concerns

  • Token allocation churn: interned identifiers avoid per-occurrence string allocation.
  • Branch prediction on token dispatch: token-kind dispatch table ordered by observed frequency from the benchmark corpus.
  • UTF-8 decoding overhead: scanner operates on byte spans, decoding to char only at diagnostic- rendering time, never on the hot tokenization path.

13.8 Edge Cases

  • Unterminated string and block-comment literals at end-of-file.
  • Nested block comments (language permits nesting; naive scanners do not).
  • Invalid Unicode scalar values inside string literals.
  • Deep generic-bound nesting (fixtures/parser/malformed-generics).
  • Concurrent incremental reparse requests racing on the same file (serialized by the orchestrator's lock ordering, I9).

13.9 Failure Analysis

Primary failure: parser divergence (accepting invalid syntax or rejecting valid syntax). Detection: grammar fixture suite plus differential replay against the previous compiler version. Blast radius: a divergence silently changes which programs compile, a backward-compatibility break (§25). Mitigation: synchronization-token recovery contains a single malformed construct to one diagnostic, not a file- wide cascade. Operator visibility: parser.recovery_count spikes flag a grammar regression before users file bug reports.

13.10 Operational Notes

  • Metrics: parser.throughput_loc_per_sec, parser.token_count, parser.recovery_count.
  • Tracing spans: parser.scan, parser.parse_item, parser.recover.
  • Structured-log fields: file_id, recovery_reason, node_count.
  • Deployment: pure library crate, no independent rollout; compatibility tracked via the grammar fixture suite's version tag (§25).

14. Phase 2 — Semantic Analysis

14.1 Objectives

  • Implement name resolution, type inference, trait solving, visibility enforcement, and semantic validation over the parsed AST, producing a typed AST ready for MIR lowering.
  • Establish I2 (semantic hash determinism) as a hard gate before any incremental caching can be trusted.

14.2 Detailed Implementation Steps

  • Build symbol tables and lexical scopes in compiler/sema/resolve.rs; implement module-graph and import resolution.
  • Build the type arena and trait solver compiler/sema/trait_solver.rs — constraint-based resolution with an explicit fixpoint iteration cap (I13) to guarantee termination on pathological trait graphs.
  • Implement generic substitution and monomorphization scaffolding (full monomorphization lands in §17); add coherence checks compiler/sema/coherence.rs (overlapping-impl detection).
  • Build recursive-type detection to reject infinite type expansion before it reaches MIR.
  • Implement overload/method-dispatch resolution with deterministic tie-breaking (P1).
  • Add the borrow-graph representation scaffold consumed by Phase 3's compiler/borrowck (§15).
  • Build visibility enforcement (pub/module-private boundaries) per Pierce (2002) ch. 26's module soundness treatment.
  • Implement semantic hashing compiler/sema/hash.rs (P3) — hashes the resolved AST shape, not source bytes, so formatting-only edits do not invalidate the cache.
  • Add incremental dependency edges into compiler/incremental/graph.rs (I8) as resolution proceeds.
  • Build the semantic verifier: every TypedNode has a resolved TypeId and no dangling ScopeId (§11) before Phase 3 begins.

14.3 Deliverable

A typed AST with deterministic semantic diagnostics, exercised over conformance/simulator.rs traces and gated by the semantic fixture suite.

14.4 Acceptance Criteria

  • Semantic fixture suite passes at 100% (≥ 150 fixtures).
  • Zero unresolved symbols across the valid-program corpus (≥ 500 programs).
  • Deterministic diagnostics ordering verified by fixtures/sema/diagnostic-order-replay across 3 independent worker-pool sizes (I10).
  • Semantic analysis p95 < 200 ms per module (§4; enforced by M6, §28).

14.5 Conformance Fixtures

  • fixtures/sema/recursive-trait — mutually recursive trait bounds must terminate the solver via the fixpoint cap, not loop forever (malformed case).
  • fixtures/sema/shadowing — nested-scope identifier shadowing must resolve to the innermost binding.
  • fixtures/sema/visibility-cycle — a visibility-cycle between two modules must be rejected deterministically.
  • fixtures/sema/generic-inference — ambiguous generic inference must produce a suggestion-bearing diagnostic (P8), not a silent default.
  • fixtures/sema/diagnostic-order-replay — replaying the same corpus at worker-pool sizes 1, 8, and 64 must produce byte-identical diagnostic ordering (replay case, I10).

14.6 Pitfalls

  1. Trait solver nontermination — manifestation: single-module compile hangs · root cause: cyclic trait bound with no fixpoint ceiling · debugging: dump solver iteration trace via trait_solver.iterations span · signal: sema.trait_solver_iterations metric saturates its cap · recovery: enforce I13's depth ceiling inside the solver, not just the parser.
  2. Type inference ambiguity leaks — manifestation: a diagnosable ambiguity instead silently resolves to an arbitrary type · root cause: solver picks the first candidate on tie rather than reporting ambiguity · debugging: fixtures/sema/generic-inference regression replay · signal: downstream MIR type mismatch in Phase 3 · recovery: solver must explicitly enumerate ties and emit a diagnostic rather than pick silently (P8).
  3. Cyclic imports — manifestation: module-graph resolution never converges · root cause: import resolution treats the module graph as a tree, not a general graph · debugging: dump the module dependency graph and look for a cycle via Tarjan's SCC · signal: sema.module_resolution_timeout fires · recovery: detect the cycle explicitly and report it (not treat as depth-limit exhaustion).
  4. Symbol-table lifetime leaks — manifestation: incremental daemon memory grows unbounded across many compiles · root cause: per-module symbol tables retained past their last consumer · debugging: heap profile the daemon after 1,000 simulated incremental edits · signal: sema.symbol_table_count trends upward without bound · recovery: tie symbol-table lifetime to the incremental dependency graph's retention policy (§20).

14.7 Performance Concerns

  • Trait-resolution fanout: bound candidate-impl search by coherence-check locality, not a full-crate scan per query.
  • Type-canonicalization churn: intern canonical type representations to avoid repeated structural comparison.
  • Arena cache locality: type arena laid out so hot trait-solver paths stay within a few cache lines (§4 CPU baseline).

14.8 Edge Cases

  • Mutually recursive generic bounds (fixtures/sema/recursive-trait).
  • Ambiguous method dispatch across multiple applicable trait impls.
  • Cyclic type aliases (type A = B; type B = A;).
  • Diamond-shaped trait inheritance triggering coherence-check combinatorics.

14.9 Failure Analysis

Blast radius: an invalid semantic hash poisons the incremental cache (I2 violation) — every downstream build keyed on that hash silently reuses stale results. Detection: differential hash comparison in CI re-running the same input twice. Containment: I11's fail-closed cache semantics purge on any checksum mismatch. Recovery: rebuild the semantic hash from source, invalidate all dependent IncrementalKey entries (I8). Postmortem guidance: log the exact TypedNode subtree whose hash changed unexpectedly.

14.10 Operational Notes

  • Metrics: sema.trait_solver_iterations, sema.type_inference_retries, sema.cache_hit_rate.
  • Tracing spans: sema.resolve, sema.trait_solve, sema.hash.
  • Structured-log fields: module_id, symbol_count, solver_iterations.
  • Compatibility: a change to trait-solving tie-break order is a semver-relevant behavior change (§25) and must be flagged in CHANGELOG.md.

15. Phase 3 — MIR & Borrow Checking

15.1 Objectives

  • Introduce the typed MIR and ownership semantics: explicit moves, borrows, drops, and control flow, enforcing I3 (MIR ownership correctness) before any optimization is attempted.
  • This is the correctness-critical phase: an unsound borrow acceptance here produces memory-unsafe binaries no later phase can catch.

15.2 Detailed Implementation Steps

  • Design MIR instructions and basic-block terminators in compiler/mir/build.rs; implement explicit drop semantics (compiler/mir/drop_elab.rs) per Appel (1998) ch. 6's translation to an explicit intermediate form, extended with ownership tracking Appel does not cover.
  • Add move tracking and move-path analysis compiler/borrowck/move_paths.rs — every place expression decomposes into a move path, tracked for use-after-move violations (I3).
  • Build borrow regions compiler/borrowck/regions.rs and the lifetime graph — region-based liveness per Rust RFC 2094 (§5), adapted for an ahead-of-time-only compiler with no incremental NLL history to preserve.
  • Add escape analysis compiler/borrowck/escape.rs — detects a borrow outliving its referent's scope.
  • Build the MIR verifier compiler/mir/verify.rs enforcing I3: no mutable-aliasing violation may reach SSA construction (§16).
  • Add the canonical CFG builder and deterministic local-variable numbering (P1) — local IDs assigned in a stable traversal order, not allocation order.
  • Implement region invalidation on borrow-checker rejection (a rejected borrow must not leave a half-built region graph behind for the next compilation unit).
  • Add replay fixtures capturing the exact region-graph state at each rejection for offline debugging (P11).

15.3 Deliverable

An ownership-safe MIR representation: every accepted program has a MIR body whose verifier has proven I3, ready for SSA lowering (§16). Every rejected program carries a diagnostic pinpointing the exact move/borrow conflict.

15.4 Acceptance Criteria

  • 100% of the invalid-borrow fixture suite (≥ 80 fixtures) is rejected.
  • Deterministic MIR serialization: two runs over identical input produce byte-identical MirBody postcard encodings.
  • MIR verifier passes on 100% of the valid-program corpus with zero false positives.
  • Region-graph size stays under a 50,000-node cap per function (§4-derived; see C-series, §32) before falling back to a conservative over-approximation.

15.5 Conformance Fixtures

  • fixtures/borrowck/use-after-move — accessing a moved-from binding must be rejected with a move-path-precise diagnostic (malformed case).
  • fixtures/borrowck/double-mut-borrow — two simultaneous mutable borrows of the same place must be rejected.
  • fixtures/borrowck/lifetime-escape — a reference outliving its referent must be rejected by escape analysis.
  • fixtures/borrowck/region-replay — replaying a rejected borrow's region-graph snapshot must reproduce the identical rejection (replay case).
  • fixtures/borrowck/drop-order-regression — drop order across nested scopes with early returns must match reverse-declaration order exactly (regression case).

15.6 Pitfalls

  1. False-positive borrow errors — manifestation: a memory-safe program is rejected · root cause: region graph over-approximates liveness beyond the true borrow scope · debugging: minimize the rejected program and compare against the RFC 2094 reference model · signal: user-reported false-positive rate in the fixture regression suite · recovery: tighten the region-inference rule that over-approximated, re-run the full valid-corpus regression.
  2. Region graph explosion — manifestation: compile time balloons on deeply nested closures · root cause: each nested closure captures a fresh region set without deduplication · debugging: profile region-graph node count via borrowck.region_graph_size · signal: metric exceeds the 50,000-node cap · recovery: deduplicate region sets structurally before graph construction (ADR-09's immutable- graph representation makes this safe to share).
  3. MIR block instability — manifestation: AstNodeId-adjacent MIR block IDs shift across unrelated edits · root cause: block numbering depends on traversal order that is itself input-order-sensitive · debugging: diff MirBody block IDs before/after an unrelated-function edit · signal: incremental cache over-invalidates (§20) · recovery: number blocks by a stable post-order keyed on MIR construction order, not a mutable worklist order.
  4. Drop-order mismatches — manifestation: destructors run in the wrong order on an early-return path · root cause: drop elaboration misses a control-flow edge introduced by ?-style early return · debugging: fixtures/borrowck/drop-order-regression · signal: runtime stress test in §19 detects a resource double-release · recovery: drop elaboration must walk every terminator edge, not just the fall-through edge.

15.7 Performance Concerns

  • Graph traversal complexity: region graph traversal must stay near-linear in function size; a quadratic borrow-check pass is the single most common compiler-performance regression class in ownership-based languages.
  • Region allocation pressure: region sets allocated from a per-function arena reset alongside the MIR arena (ADR-08's locality rationale extends here).

15.8 Edge Cases

  • Loops with mutable captures across iterations.
  • Nested closures capturing overlapping regions.
  • Panic/unwind paths interacting with drop elaboration.
  • Self-referential struct patterns that must be rejected, not silently accepted with a dangling region.

15.9 Failure Analysis

Incorrect borrow acceptance is the single highest-severity failure class in this blueprint: it generates a memory-unsafe binary that the rest of the pipeline has no way to detect (I3 is the last line of defense). Detection: the invalid-borrow fixture suite plus continuous fuzzing of compiler/borrowck inputs. Blast radius: unbounded — the unsound binary ships and fails at runtime, possibly in a security-relevant way (§22). Containment: no release-channel promotion without a 100%-green invalid-borrow suite (§27). Recovery path: bisect the borrowck commit history against the fixture suite's git-blame. Postmortem guidance: every false-negative borrow acceptance gets a new regression fixture before the fix merges, never after.

15.10 Operational Notes

  • Metrics: borrowck.region_graph_size, borrowck.move_analysis_ms, borrowck.rejection_count.
  • Tracing spans: borrowck.build_regions, borrowck.escape_analysis, borrowck.verify.
  • Structured-log fields: function_id, region_count, rejection_reason.
  • Migration: a change to borrow-check strictness is a breaking compatibility event (§25) requiring a major-version bump, never a silent tightening.

16. Phase 4 — SSA IR & Optimization

16.1 Objectives

  • Implement the optimization-oriented SSA representation and a deterministic pass manager, enforcing I4 (SSA dominance correctness) and P12 (correctness before optimization) as hard gates.
  • Deliver a measurable optimizer: every pass must show a benchmark-corpus improvement before shipping.

16.2 Detailed Implementation Steps

  • Construct the CFG and dominance tree compiler/ssa/dominance.rs using the Cytron et al. (1991) dominance-frontier algorithm (ADR-10).
  • Insert phi nodes compiler/ssa/phi.rs at exactly the dominance-frontier-derived merge points — minimal, not maximal, phi placement.
  • Implement value numbering for redundancy elimination, then sparse conditional constant propagation compiler/opt/sccp.rs per Wegman & Zadeck (1991).
  • Add dead-code elimination compiler/opt/dce.rs and CFG simplification (unreachable-block removal, critical-edge splitting).
  • Add the inliner compiler/opt/inline.rs with a recursion-depth-bounded inline budget (I13 extended to the optimizer).
  • Implement loop analysis and loop-invariant code motion compiler/opt/licm.rs.
  • Build the deterministic pass manager compiler/opt/pass_manager.rs (P1) — pass ordering is fixed and versioned, never heuristically reordered at runtime.
  • Add the IR verifier enforcing I4 after every pass, not just at pipeline boundaries.
  • Build optimization replay logs (P11) — every pass records its before/after IR snapshot for offline differential debugging.
  • Wire the differential-testing oracle: compile the same input through LLVM (via a thin FFI harness) and compare observable execution behavior (ADR-17, Necula 2000's translation-validation framing).

16.3 Deliverable

An optimized SSA pipeline whose IR verifier stays green after every pass, with measured benchmark throughput improvement over the un-optimized baseline, exercised continuously against the LLVM differential oracle.

16.4 Acceptance Criteria

  • SSA verifier stable across 100% of the optimization fixture suite (≥ 120 fixtures).
  • Optimization determinism guaranteed: identical input to the pass manager produces byte-identical optimized SSA across 50 repeated runs.
  • Benchmark throughput improves ≥ 15% over the un-optimized baseline on the benchmarks/ corpus.
  • Zero behavioral divergence against the LLVM differential oracle across the ≥ 500-program conformance corpus.

16.5 Conformance Fixtures

  • fixtures/ssa/dominance-violation — a hand-crafted IR with a use not dominated by its definition must be rejected by the verifier (malformed case).
  • fixtures/ssa/unreachable-cfg — an unreachable block must be pruned without disturbing dominance elsewhere.
  • fixtures/ssa/phi-cycle — a cyclic phi dependency (loop header) must resolve correctly under value numbering.
  • fixtures/ssa/differential-replay — replaying 500 programs through both this optimizer and LLVM must match observable behavior bit-for-bit (replay case).
  • fixtures/ssa/aggressive-fold-regression — a known-historical over-aggressive constant fold must stay fixed (regression case).

16.6 Pitfalls

  1. Invalid phi placement — manifestation: verifier rejects otherwise-correct optimizer output · root cause: dominance-frontier computation miscounts a merge point with more than two predecessors · debugging: dump the dominance tree and cross-check against Cytron et al.'s worked example · signal: fixtures/ssa/dominance-violation-class failures spike · recovery: fix the dominance- frontier iteration, re-verify against the full fixture suite.
  2. Optimization pass-ordering instability — manifestation: two builds of the same source produce different (though both "correct") machine code · root cause: pass manager falls back to a non-deterministic iteration order on tie · debugging: replay logs (P11) diff pass-by-pass · signal: I7's reproducibility gate fails downstream in §18 · recovery: pin pass order explicitly in pass_manager.rs, remove any HashMap-iteration-order dependency.
  3. Miscompilation from aggressive folding — manifestation: LLVM differential oracle disagrees on observable behavior · root cause: a constant-fold rule assumes no-overflow semantics the source language does not guarantee · debugging: minimize the differential-testing counterexample · signal: fixtures/ssa/aggressive-fold-regression · recovery: gate the fold rule behind an explicit no-overflow precondition, verified by the borrow/type system upstream (§14/§15), not assumed.

16.7 Performance Concerns

  • Dominance recomputation: incremental dominance updates on localized CFG edits instead of full recomputation per pass invocation.
  • Allocator churn: pass manager reuses a single arena across passes within one compilation unit (ADR-08's locality rationale).
  • Pass invalidation cost: a pass that touches 1% of a function must not force full re-verification of the other 99% — verifier runs incrementally scoped to the touched region where provable.

16.8 Edge Cases

  • Irreducible CFGs (multiple entry points into a loop) — dominance-frontier algorithm must still terminate correctly.
  • Recursive inlining reaching the inline-budget ceiling.
  • Massive match/switch lowering (thousands of arms) stressing jump-table generation.
  • Loop-invariant code motion hoisting a computation past a potential panic point (must not reorder past an observable side effect).

16.9 Failure Analysis

Detection: differential execution against LLVM (ADR-17) is the primary oracle; the IR verifier (I4) is the secondary, faster gate. Blast radius: a miscompilation silently corrupts every binary built from the optimizer's current version until detected — potentially including the compiler's own next bootstrap stage (§21). Recovery path: bisect the pass manager's pass list with the differential oracle until the offending pass is isolated (PhaseDeferred("§16") covers a future automated bisection tool beyond Phase 4's initial manual tooling). Postmortem guidance: every miscompilation gets a fixtures/ssa/*-regression fixture before the fix merges.

16.10 Operational Notes

  • Metrics: opt.pass_duration_ms per pass, opt.dominance_recompute_count, opt.fold_count.
  • Tracing spans: opt.pass_manager.run, opt.sccp, opt.licm.
  • Structured-log fields: pass_name, function_id, ir_size_before, ir_size_after.
  • Compatibility: a new optimization pass ships behind a feature flag for one release cycle before becoming default (§25), so a regression can be bisected by simply disabling the flag.

17. Phase 5 — Backend & Register Allocation

17.1 Objectives

  • Lower optimized SSA IR to target-specific machine code for x86_64 and AArch64, enforcing I5 (register allocation correctness) and I6 (ABI stability) before any executable is emitted.
  • Establish the target-independent Machine IR boundary (§3) that both backends share.

17.2 Detailed Implementation Steps

  • Build the target-independent Machine IR compiler/codegen/machine_ir.rs; implement instruction selection compiler/codegen/isel.rs as a pattern-matching lowering from SSA ops to machine ops.
  • Implement calling-convention lowering compiler/codegen/abi.rs for SysV (x86_64) and AAPCS64 (AArch64) per the §5 RFC/Specification entries — argument classification, stack-alignment rules, callee-save register sets.
  • Add stack-frame layout computation; build the linear-scan register allocator compiler/codegen/regalloc.rs per Poletto & Sarkar (1999, ADR-11).
  • Implement spill handling — a spilled value's stack slot is assigned deterministically (P1), not by first-fit at allocation time.
  • Add prologue/epilogue generation respecting the ABI's callee-save contract (I6).
  • Build the relocation model consumed by Phase 6's object emitter (compiler/linker/relocation.rs, §18).
  • Implement the x86_64 instruction encoder compiler/x86_64/encoder.rs and the AArch64 encoder compiler/aarch64/encoder.rs.
  • Add the backend verifier enforcing I5: no two simultaneously live virtual registers may map to the same physical register post-allocation.

17.3 Deliverable

Executable machine-code generation for both targets: a MachineFunction (§11) per compilation unit, verified against I5/I6, ready for object emission (§18). Generated binaries are directly runnable on Linux x86_64 and Linux AArch64.

17.4 Acceptance Criteria

  • ABI conformance test suite passes at 100% (≥ 60 fixtures per target, 120 total).
  • Zero overlapping register assignments across the entire benchmark corpus (I5, backend-verifier gate).
  • Generated binaries execute correctly on both targets, verified by fixtures/backend/abi-calling's round-trip execution check.
  • Spill rate stays under 8% of allocated virtual registers on the benchmarks/codegen_throughput.rs corpus (perf target, M11 §28).

17.5 Conformance Fixtures

  • fixtures/backend/abi-calling — a function taking the maximum register-classified argument count plus one (forcing stack-passed arguments) must match the ABI's exact stack layout.
  • fixtures/backend/spill-stress — a function with more live values than physical registers must spill correctly and preserve program semantics.
  • fixtures/backend/stack-alignment — every call site must maintain 16-byte stack alignment (SysV) / the AAPCS64 equivalent at the call boundary.
  • fixtures/backend/tail-call-regression — a self-recursive tail call must not grow the stack frame across iterations (regression case).

17.6 Pitfalls

  1. Stack misalignment — manifestation: SIMD instruction faults at runtime in the generated binary · root cause: prologue computes frame size without rounding to the ABI's alignment requirement · debugging: reproduce with fixtures/backend/stack-alignment under a hardware watchpoint · signal: fixtures/backend/* execution-check failures spike on SIMD-using programs · recovery: round frame size up to the ABI alignment unconditionally, not only when SIMD is detected.
  2. Incorrect callee-save handling — manifestation: caller's register value is corrupted after a call · root cause: prologue/epilogue omits a callee-save register the allocator assigned across the call · debugging: differential-test against LLVM-generated code for the same function · signal: ABI conformance suite regression · recovery: cross-reference the allocator's assigned register set against the ABI's callee-save table before emitting the prologue.
  3. Register allocator starvation — manifestation: excessive spilling on functions with wide live ranges · root cause: linear scan's single-pass heuristic (Poletto & Sarkar 1999) lacks graph coloring's global view · debugging: profile regalloc.spill_count on the benchmark corpus · signal: M11's spill-rate target (§28) breached · recovery: ADR-11's rejected alternative (Chaitin et al. 1981 graph coloring) is the documented fallback for hot functions identified by profiling.

17.7 Performance Concerns

  • Spill amplification: every spilled value costs a load/store pair per use; bound spill rate (M11) rather than accept unbounded degradation.
  • Instruction-cache locality: emit hot-path basic blocks contiguously, cold paths (panics, rare branches) out-of-line.
  • Branch-predictor alignment: align loop headers to reduce mispredict penalties on the §4 CPU baseline.

17.8 Edge Cases

  • Massive basic blocks (thousands of instructions) stressing the linear-scan allocator's live-range tracking.
  • Recursive stack growth near the runtime's guard-page boundary (§19).
  • Tail calls that must not grow the frame (fixtures/backend/tail-call-regression).
  • Functions with zero live registers (pure control-flow) — allocator must not allocate spuriously.

17.9 Failure Analysis

Incorrect backend lowering causes silent corruption — a subtly wrong instruction encoding produces a binary that runs but computes the wrong answer, the hardest class of bug to detect (no crash signal). Detection: ABI conformance suite plus differential execution against LLVM-generated code for the same IR. Blast radius: every program compiled with the buggy backend version is silently wrong. Containment: backend-verifier (I5) catches allocation-level bugs before emission; execution-level bugs require the differential oracle from §16. Recovery: bisect by isolating the exact instruction-selection pattern via minimized reproduction. PhaseDeferred("§17") covers both the WebAssembly backend and a GPU backend — neither ships until this native-backend correctness bar is met and stable for two release cycles.

17.10 Operational Notes

  • Metrics: backend.spill_count, backend.frame_size_bytes, backend.encode_duration_ms.
  • Tracing spans: backend.isel, backend.regalloc, backend.encode.
  • Structured-log fields: function_id, target_triple, spill_count.
  • Compatibility: I6's ABI-stability window means a calling-convention change requires a major-version bump and a documented migration note in CHANGELOG.md (§25).

18. Phase 6 — Object Emission & Linking

18.1 Objectives

  • Generate deterministic object files and coordinate with the host linker to produce runnable native executables, enforcing I7 (deterministic object emission) end-to-end.
  • Scope: ELF primary target, Mach-O and PE/COFF secondary (§1 deployment model).

18.2 Detailed Implementation Steps

  • Implement the ELF writer compiler/object/elf_writer.rs per the ELF specification (§5 RFCs) — section headers, program headers, symbol tables.
  • Add relocation records compiler/linker/relocation.rs consuming the backend's relocation model (§17); implement DWARF v5 emission compiler/object/dwarf.rs (§5 RFCs).
  • Add deterministic section layout and symbol ordering (I7) — sort symbols by a stable key (name, then source location), never by insertion order.
  • Build the linker driver compiler/linker/driver.rs invoking the host linker (ld/lld) as a subprocess (ADR-12, P13's external-linker-first principle).
  • Implement startup-object integration runtime/startup/crt0.rs linkage — the Phase 0 bootstrap bridge to the host C toolchain (§1).
  • Add the Mach-O writer compiler/object/macho_writer.rs and PE/COFF writer compiler/object/pe_writer.rs for secondary-platform support.
  • Wire objdump-based verification into CI: every emitted object file is independently parsed and cross-checked (Levine 2000's relocation-semantics treatment is the correctness reference).

18.3 Deliverable

Runnable native executables on Linux x86_64/AArch64 (primary) with debug symbols inspectable via standard tooling (gdb, objdump), and deterministic binary output verified bit-for-bit across repeated builds.

18.4 Acceptance Criteria

  • 100% of emitted executables launch correctly and return the expected exit code across the conformance/ corpus (≥ 300 programs).
  • Debug symbols inspectable: DWARF line-table round-trips through objdump --dwarf=decodedline without a parse error.
  • Deterministic binary output: 50 consecutive builds of the same source produce identical SHA-256 object-file hashes (I7).
  • Object emission throughput ≥ 500 MB/minute on the benchmarks/ corpus (perf target, M9 §28).

18.5 Conformance Fixtures

  • fixtures/object/relocation-matrix — every relocation type used by both backends must resolve correctly against a synthetic symbol table (malformed + valid matrix).
  • fixtures/object/dwarf-validation — line-table and variable-location DWARF entries must match the source spans exactly.
  • fixtures/object/duplicate-weak-symbol — two weak symbols with the same name across translation units must resolve per the ELF weak-symbol rule, not link-error spuriously.
  • fixtures/object/reproducibility-replay — replaying the same build 50 times must produce a bit- identical object file (replay case, I7).

18.6 Pitfalls

  1. Invalid relocations — manifestation: linker fails or, worse, silently produces a corrupt executable · root cause: relocation type mismatched against the target's addressing mode · debugging: objdump -r diff against the expected relocation matrix · signal: fixtures/object/relocation- matrix regression · recovery: cross-check every relocation type against the ELF spec's addressing- mode table before emission.
  2. Symbol visibility leaks — manifestation: an internal helper symbol is externally visible, causing a link-time collision downstream · root cause: default visibility not overridden for non-pub items · debugging: nm --defined-only diff against the expected public-symbol set · signal: package integration test fails with a duplicate-symbol linker error · recovery: default all non-pub MIR items to hidden/local visibility at emission time.
  3. Non-deterministic section ordering — manifestation: I7's binary-diff CI job flags a diff with no semantic change · root cause: section layout iterates a HashMap instead of a sorted structure · debugging: readelf -S diff between two builds of the same commit · signal: reproducibility gate failure · recovery: sort sections by a fixed key before emission, matching P1's determinism requirement.

18.7 Performance Concerns

  • Linker subprocess overhead: batch multiple translation units into fewer linker invocations where the build graph (§3) permits, rather than one invocation per file.
  • Symbol-table memory usage: intern symbol names once, reference by ID through emission (matches the interner pattern from §13).

18.8 Edge Cases

  • Duplicate weak symbols across translation units (fixtures/object/duplicate-weak-symbol).
  • Massive relocation tables on programs with heavy monomorphization (interacts with §14's monomorphization ceiling, §4).
  • Cross-target object files accidentally mixed in one link (must fail closed with a clear diagnostic, not a linker-level crash).

18.9 Failure Analysis

Detection: objdump/readelf independent-parser verification catches structural corruption; the binary-diff CI job (I7) catches non-determinism. Blast radius: a corrupt object file fails at link time (contained) or, worse, links successfully but crashes at load time (harder to contain). Recovery: bisect the emission commit against the relocation-matrix fixture. PhaseDeferred("§18") covers ThinLTO-style cross-module whole-program optimization — deferred until per-module object emission is provably deterministic and stable, since ThinLTO's cross-module summary format is itself a new compatibility surface (§25) this phase does not yet need.

18.10 Operational Notes

  • Metrics: object.emission_throughput_mb_per_min, linker.failure_classification, object.reproducibility_success_rate.
  • Tracing spans: object.write_elf, object.write_dwarf, linker.invoke.
  • Structured-log fields: object_path, relocation_count, linker_exit_code.
  • Rollback: a linker-driver regression rolls back to the previous compiler_version's pinned linker invocation flags, tracked in docs/adr/0002-build-system.md.

19. Phase 7 — Standard Library & Runtime

19.1 Objectives

  • Implement the minimal runtime and standard-library subset needed for the compiler to eventually compile itself (§21): allocation, panic handling, collections, formatting, IO, synchronization.
  • No garbage collector (§1 exclusion) — ownership-based deallocation only.

19.2 Detailed Implementation Steps

  • Implement allocator APIs runtime/alloc/global.rs and the arena allocator runtime/alloc/arena.rs — the Garbage Collection Handbook's (Jones, Hosking & Moss 2011, §5) allocator-design chapters apply despite the absence of a collector, for layout and fragmentation reasoning.
  • Add the panic runtime runtime/core/panic.rs — unwind-based by default, with an abort-mode compile-time switch for embedded targets (deferred beyond Phase 0 scope, noted here for interface completeness).
  • Build the startup runtime runtime/startup/init.rs bridging crt0.rs (§18) to the language's entry point.
  • Implement core collections stdlib/collections/vec.rs (growable array) and stdlib/collections/hashmap.rs (deterministic-iteration-order hashmap, P1-compliant).
  • Add the formatting subsystem stdlib/core/fmt.rs and IO abstractions stdlib/io/file.rs, stdlib/io/buffered.rs.
  • Add deterministic hashing for HashMap keys (reuses the Blake3-derived hasher from §12, not a randomized seed — a deliberate deviation from typical stdlib practice, justified by P1).
  • Implement synchronization primitives (mutex, bounded channel) backing ADR-06/ADR-21's concurrency model.

19.3 Deliverable

A usable language-ecosystem foundation: allocator, panic runtime, core collections, formatting, IO, and synchronization primitives, all passing allocator-stress and formatting-golden fixture suites.

19.4 Acceptance Criteria

  • Runtime passes stress tests: 10M alloc/free cycles with zero leaks detected (fixtures/runtime/ allocator-stress).
  • Allocator leak checks pass under a debug-mode leak sanitizer across the full conformance/ corpus.
  • Formatting output matches golden files byte-for-byte across ≥ 100 format-specifier combinations.
  • Panic-during-panic (fixtures/runtime/double-panic) aborts cleanly within 50 ms, never hangs.

19.5 Conformance Fixtures

  • fixtures/runtime/allocator-stress — 10M alloc/free cycles across varying size classes must show zero leaked bytes.
  • fixtures/runtime/formatting-golden — every format specifier's output must match a golden file exactly (regression case).
  • fixtures/runtime/double-panic — a panic occurring during another panic's unwind must abort, not recurse indefinitely (malformed case).
  • fixtures/runtime/oom-behavior — an allocation exceeding the process's memory ceiling (§4) must return a diagnosable allocation failure, not a silent OS kill where avoidable.

19.6 Pitfalls

  1. Allocator fragmentation — manifestation: RSS grows without bound under long-running incremental- daemon workloads · root cause: size-class bucketing leaves unreclaimable gaps under a specific allocation pattern · debugging: heap-profile the daemon under fixtures/runtime/allocator-stress at daemon scale (§20) · signal: runtime.alloc_fragmentation_ratio metric trends upward · recovery: add a size-class compaction pass triggered above a fragmentation threshold.
  2. Panic recursion — manifestation: a panic inside a Drop implementation during unwind causes undefined behavior · root cause: no explicit double-panic guard in the panic runtime · debugging: fixtures/runtime/double-panic · signal: process aborts with a corrupted stack trace instead of a clean diagnostic · recovery: track unwind-in-progress state explicitly; a second panic during unwind aborts immediately with both messages captured.
  3. Runtime ABI mismatch — manifestation: a program compiled against one runtime version crashes when linked against another · root cause: runtime/core layout changed without a compatibility window (I6) · debugging: differential-test the runtime's public ABI surface across two versions · signal: ABI conformance suite (§17) extended to runtime symbols fails · recovery: version-gate runtime ABI changes exactly as backend ABI changes are gated (§25).

19.7 Performance Concerns

  • Allocator contention: per-thread free-lists to avoid a global-lock bottleneck under the 256-worker concurrency ceiling (§4).
  • Cache locality: arena allocation groups short-lived compiler-internal allocations contiguously (reuses the ADR-08 pattern from the AST arena).

19.8 Edge Cases

  • Out-of-memory behavior at the exact §4 ceiling boundary.
  • Panic during panic (fixtures/runtime/double-panic).
  • Allocation from within a signal handler (must be lock-free or explicitly disallowed).
  • Formatting of pathological inputs (NaN, infinities, maximum-precision floats).

19.9 Failure Analysis

Runtime corruption may manifest as compiler instability — because the compiler is itself compiled against this runtime (self-hosting, §21), a runtime bug can corrupt the compiler's own execution in a way that looks like a semantic-analysis or backend bug, misdirecting debugging effort. Detection: allocator-stress and formatting-golden fixture suites run on every commit, not just before release. Blast radius: potentially every compilation running against the affected runtime version. Containment: runtime changes require the full stress suite green before merge, no fast-path exception. Recovery: isolate whether a reported "compiler bug" is actually a runtime bug by re-running the reproduction against the previous runtime version first.

19.10 Operational Notes

  • Metrics: runtime.alloc_fragmentation_ratio, runtime.panic_count, runtime.gc_pause_ms (always zero — tracked to prove the no-GC invariant holds).
  • Tracing spans: runtime.alloc, runtime.panic_unwind, runtime.format.
  • Structured-log fields: allocation_size, size_class, panic_message.
  • Deployment: runtime ships statically linked into every executable by default; dynamic-linking mode is a documented but secondary configuration.

20. Phase 8 — Incremental Compilation

20.1 Objectives

  • Implement stable incremental compilation: content-addressed caching, dependency-graph invalidation, and a daemonized compilation mode, enforcing I8 (monotonic dependency graph) and I11 (fail-closed cache).
  • This phase is where P7 (crash-only services) and P14 (fail-closed cache) become load-bearing rather than aspirational.

20.2 Detailed Implementation Steps

  • Build the dependency-graph DB compiler/incremental/graph.rs — nodes keyed by IncrementalKey (§11), edges recording which upstream node's semantic hash a downstream node consumed.
  • Add stable semantic hashing (reuses §14's sema/hash.rs) as the sole cache-key input (P3).
  • Implement invalidation propagation: a changed node invalidates every transitive downstream consumer, and only those (I8) — the classical incremental-compilation correctness property from the rustc query-system lineage (§5 Reference Implementations).
  • Add cache serialization via postcard (ADR-03) with an explicit schema_version (P9).
  • Build the replay verifier conformance/trace_replay.rs — replays a recorded edit sequence and confirms the incremental result matches a from-scratch rebuild exactly.
  • Add the daemonized compilation mode compiler/incremental/daemon.rs communicating over a Unix domain socket, crash-only recovery (P7).
  • Implement cache eviction (LRU-by-content-addressed-key) bounded by the §4 4 GB daemon ceiling.

20.3 Deliverable

An incremental compiler with deterministic cache reuse: isolated single-module edits recompile without touching unrelated modules, verified continuously by the replay verifier against from-scratch rebuilds.

20.4 Acceptance Criteria

  • Isolated single-module edits compile in < 2,000 ms p99 (§4; enforced by M2, §28).
  • Cache hit ratio above 80% on the conformance/trace_replay.rs edit-sequence corpus (≥ 1,000 replayed edits).
  • Zero stale-cache resurrections across 10,000 simulated interleaved edits (I8, fixtures/ incremental/edit-replay).
  • Cache corruption (fixtures/incremental/cache-corruption) triggers a full purge within the 5-minute RTO (§4).

20.5 Conformance Fixtures

  • fixtures/incremental/edit-replay — 10,000 recorded interleaved single-module edits must match a from-scratch rebuild's semantic output exactly at every step (replay case).
  • fixtures/incremental/cache-corruption — a bit-flipped cache entry must be detected by checksum and purged, never served (malformed case).
  • fixtures/incremental/interrupted-write — a daemon crash mid-write to the cache must leave no partially-written entry readable on restart (regression case).
  • fixtures/incremental/version-skew — a cache built by an older compiler_version must be rejected and rebuilt, never partially reused.

20.6 Pitfalls

  1. Stale-cache resurrection — manifestation: an edit's effect silently fails to propagate downstream · root cause: invalidation propagation misses an edge in the dependency graph (I8 violation) · debugging: fixtures/incremental/edit-replay regression, diff the dependency-graph edge set before/ after the missed edit · signal: the replay verifier's semantic-output mismatch · recovery: audit every point where a node reads an upstream value without recording a corresponding graph edge.
  2. Semantic drift — manifestation: an incrementally-compiled result differs subtly from a from-scratch rebuild despite passing the replay verifier's coarse check · root cause: the semantic hash (I2) does not cover a field the downstream consumer actually depends on · debugging: bisect which TypedNode field changed without a corresponding hash change · signal: a rare user report of "incremental build differs from clean build" · recovery: widen the semantic hash to cover the missed field, add a fixture.
  3. Hash instability — manifestation: the same source produces two different semantic hashes across runs · root cause: an unstable iteration order (e.g., a HashSet of trait candidates) leaks into the hash input · debugging: diff the exact byte sequence fed into the hasher across two runs · signal: I2's differential hash-comparison CI job · recovery: sort every collection before it contributes to a hash input, matching P1 across the whole pipeline.

20.7 Performance Concerns

  • Cache lookup contention: shard the dependency-graph DB by IncrementalKey prefix to reduce lock contention under the 256-worker ceiling (I9's lock-ordering rule still applies within a shard).
  • Serialization overhead: postcard's compact encoding (ADR-03) keeps cache-entry read/write off the critical path relative to a verbose format like JSON.

20.8 Edge Cases

  • Interrupted cache writes from a daemon crash mid-flush (fixtures/incremental/interrupted-write).
  • Version skew between the cache's schema_version and the running compiler (fixtures/incremental/ version-skew).
  • Two daemons racing to write the same cache entry after a crash-restart race.
  • A dependency-graph cycle introduced by a pathological macro expansion (must be detected, not silently accepted as a DAG).

20.9 Failure Analysis

A corrupted cache must fail closed (P14, I11) — never serve a possibly-wrong artifact. Detection: checksum verification on every read. Blast radius: without fail-closed semantics, a single corruption event could silently propagate wrong results through every subsequent incremental build. Containment: the daemon's crash-only design (P7) means recovery is always "restart and replay," never a partial in-place repair that could itself be buggy. Recovery path: full purge and rebuild within the 5-minute RTO (§4). PhaseDeferred("§20") covers distributed incremental compilation across multiple machines — deferred until the single-node dependency-graph DB's sharding (§20.7) is proven at the multi-million- LOC scale this phase targets locally.

20.10 Operational Notes

  • Metrics: incremental.cache_hit_rate, incremental.invalidation_count, incremental.corruption_detected_count.
  • Tracing spans: incremental.lookup, incremental.invalidate, incremental.daemon_restart.
  • Structured-log fields: incremental_key, invalidation_reason, schema_version.
  • Migration: a schema_version bump ships with an explicit forward-migration hook or, if none exists, an explicit full-purge instruction in the release notes (§25).

21. Phase 9 — Self-Hosting Transition

21.1 Objectives

  • Recompile the compiler with itself, closing the bootstrap trust chain and proving I12 (bootstrap reproducibility: stage2 == stage3).
  • This phase is the terminal correctness proof for every invariant established in §7 — a failure here means some upstream invariant was violated without being caught earlier.

21.2 Detailed Implementation Steps

  • Port compiler modules (§10's compiler/* crates) from their bootstrap-era subset to the full source language, module by module, verified against the existing fixture suites at each step (P1).
  • Establish bootstrap stages: stage0 (host-toolchain-built reference compiler) → stage1 (stage0 builds the source) → stage2 (stage1 builds the source again) → stage3 (stage2 builds the source a third time).
  • Compare binary outputs: stage2 and stage3 object files and executables must be bit-identical (I12) — this is the historical self-hosting proof technique also used by GCC and rustc (§2).
  • Add trust-chain verification: stage0's provenance (host toolchain version, build flags) is recorded and reproducible independently of this repository.
  • Implement stage-comparison tooling tools/stage_diff.rs — a byte-level diff with symbol-aware annotation for any mismatch.

21.3 Deliverable

A self-hosted compiler pipeline: the compiler, built by itself, reproduces itself bit-for-bit at stage2 == stage3, with the full bootstrap artifact chain retained for audit (§27).

21.4 Acceptance Criteria

  • stage2 == stage3 bit-for-bit reproducibility across 10 consecutive bootstrap runs.
  • The full compiler workspace (§10) builds itself end-to-end in under the bootstrap-duration budget tracked by M10 (§28).
  • Zero fixture regressions across the entire conformance corpus (§13–§20's combined suites, ≥ 1,500 fixtures) when run under the self-built stage2 compiler.
  • tools/stage_diff.rs reports zero byte-level differences between stage2 and stage3 artifacts.

21.5 Conformance Fixtures

  • fixtures/bootstrap/bootstrap-repro — a full stage0→stage3 bootstrap run must reproduce stage2 == stage3 across 10 repetitions (replay case).
  • fixtures/bootstrap/cross-stage-feature-skew — a source-language feature added between stage0 and the current source must not be used by the compiler's own source until stage1 can compile it (regression case guarding against a bootstrap chicken-and-egg break).
  • fixtures/bootstrap/undefined-behavior-divergence — a construct whose behavior depends on optimizer-version-specific UB must be flagged, not silently diverge between stages (malformed case).

21.6 Pitfalls

  1. Bootstrap drift — manifestation: stage2 and stage3 differ in a way that only appears after many bootstrap cycles · root cause: a non-deterministic construct (P1 violation) upstream that happens to be stable within one build but not across the self-compilation boundary · debugging: tools/ stage_diff.rs isolates the exact differing symbol, then bisect which phase (§12–§20) produced it · signal: fixtures/bootstrap/bootstrap-repro fails after N repetitions where N > 1 · recovery: treat as a P1 violation in whichever upstream phase the diff traces to — this pitfall is a symptom, not a root cause, of a phase 0–8 issue.
  2. Undefined-behavior divergence — manifestation: stage2 and stage3 disagree on a construct whose result the language spec leaves unspecified · root cause: the optimizer (§16) makes a different UB-dependent choice when compiling itself vs. compiling user code, because its own code path happens to hit the UB differently · debugging: fixtures/bootstrap/undefined-behavior-divergence · signal: stage comparison flags a diff with no corresponding source change · recovery: eliminate the UB from the language/compiler's own source, or pin the specific choice deterministically (P1).
  3. Runtime ABI mismatches across bootstrap stages — manifestation: stage2 crashes at startup when built by stage1 · root cause: the runtime (§19) changed its ABI between the stage0 reference compiler and the current source without a compatibility window (I6) · debugging: differential-test the runtime ABI surface between stage0 and stage1's output · signal: stage1 build succeeds but stage2's self-build crashes immediately · recovery: bootstrap-sensitive runtime changes require a two-step rollout: land the new ABI as additive, bootstrap once, then remove the old ABI.

21.7 Performance Concerns

  • Bootstrap compile duration: the full stage0→stage3 cycle is bounded by M10 (§28); a regression here blocks every release, so it is measured on every merge to the mainline branch, not just nightly.

21.8 Edge Cases

  • Cross-stage feature skew: a language feature used by the compiler's own source before the bootstrap compiler that builds it supports that feature (fixtures/bootstrap/cross-stage-feature-skew).
  • A stage1 compiler that itself has a latent bug not triggered by the fixture suite but triggered by compiling the compiler's own, larger source tree (a scale-dependent bug).
  • Partial bootstrap failure requiring resumption from stage1 rather than restarting from stage0 (cost optimization, not correctness-critical).

21.9 Failure Analysis

A stage2/stage3 binary mismatch requires a dedicated investigation pipeline: the mismatch is, by construction, caused by some upstream phase (§12–§20) producing non-deterministic or UB-dependent output — it is never a bug local to this phase. Detection: tools/stage_diff.rs's byte-level, symbol-aware diff. Blast radius: blocks every release until resolved (I12 is a release gate, §27). Containment: the previous known-good stage3 artifact remains the release candidate until the new mismatch is root-caused. Recovery: bisect across the phase boundaries using each phase's own replay/fixture tooling (§12.5–§20.5) before assuming the bug is "in bootstrapping" itself.

21.10 Operational Notes

  • Metrics: bootstrap.stage_duration_ms per stage, bootstrap.mismatch_count, bootstrap.fixture_regression_count.
  • Tracing spans: bootstrap.stage0, bootstrap.stage1, bootstrap.stage2, bootstrap.stage3.
  • Structured-log fields: stage_id, artifact_hash, mismatch_symbol.
  • Deployment: bootstrap artifacts are retained permanently (§27's backup strategy) — every release's stage0 provenance must remain reproducible independent of this repository's later history.

24. Operational Readiness

Metrics. Every phase (§12–§21) emits its own namespaced counters/histograms (driver.*, parser.*, sema.*, borrowck.*, opt.*, backend.*, object.*, runtime.*, incremental.*, bootstrap.*) as enumerated in each phase's N.10 Operational Notes. Aggregate dashboards roll these up by build ID for cross-phase correlation.

Tracing. Distributed tracing spans (ADR-04) form one trace per compilation unit, parented under a root span for the invoking CLI command, threaded through the worker pool (§12) so a single slow module is attributable to the exact pass that stalled.

Logging. Structured JSON logs (P8) with build_id, file_id/function_id, and phase-specific fields (each phase's N.10). No free-text-only log lines for anything diagnosable — every log line that matters is also a metric or a span attribute.

SLOs. Incremental compile latency < 2,000 ms p99 (M2, §28); deterministic builds 100% (I7); daemon local availability 99.9% (§4); bootstrap reproducibility 100% across releases (I12).

Backup strategy. Registry package snapshots retained for rollback (§27); bootstrap artifacts (stage0 through the current stage3) retained permanently for audit (§21.10); incremental-cache state is explicitly not backed up — it is always reconstructable from source plus the lockfile (P14), so backing it up would violate the fail-closed-over-fail-open principle it exists to enforce.

On-call runbooks. docs/runbooks/incremental-cache-corruption.md (FM-3) and docs/runbooks/bootstrap-mismatch.md (FM-5) are the two highest-frequency paged incidents; both runbooks open with "do not attempt in-place repair" as the first line, matching P7/P14.

25. Compatibility & Versioning

Wire compatibility. Every serialized format — incremental cache entries (CacheEntry, §11), package manifests, lockfiles — carries an explicit schema_version (P9). A version bump requires either a forward-migration hook or an explicit full-invalidation instruction in CHANGELOG.md; silent reinterpretation of an old format is a defect, not a compatibility strategy.

Schema evolution. All serialized structures use additive-only enum extension by default (DiagCategory, TokenKind, BorrowState, §11); removing or renumbering a variant is a breaking change requiring a major-version bump.

Semantic versioning. The compiler itself follows SemVer 2.0.0 (§5 RFCs) for: the public package manifest API, plugin/LSP interfaces, and the stable subset of compiler-internals crates exposed for tooling (§1). ABI stability (I6) has its own compatibility window, tracked independently of the compiler's own SemVer — an ABI-breaking release always major-bumps, but not every major bump breaks the ABI.

Grammar and language compatibility. A change to what the grammar accepts or the borrow checker rejects (§13, §15) is a semver-relevant behavior change even if no API signature changed — tracked via the fixture-suite version tag referenced in each phase's N.9/N.10.

Bootstrap compatibility. Cross-stage feature skew (§21.8) means a language feature can only be used in the compiler's own source once the bootstrap compiler (one stage behind) supports it — this is a compatibility constraint unique to self-hosting that has no equivalent in a non-self-hosted compiler.

26. Testing & Verification Strategy

Unit testing. Per-subsystem validation for every crate in §10 — lexer, parser, sema, MIR, borrowck, SSA, opt, backend, object, linker, incremental, runtime, stdlib, package-manager.

Integration testing. End-to-end executable generation through conformance/ — source in, running binary with an expected exit code and output, out.

Differential testing. LLVM behavioral comparison (ADR-17, §16) is the primary oracle for optimizer and backend correctness, in the spirit of translation validation (Necula 2000, §5).

Property testing. AST roundtrip invariants (parse → serialize → parse must be a fixpoint), MIR verifier idempotence, SSA dominance-tree properties.

Fuzzing. Continuous libFuzzer-based fuzzing (ADR-16) of the lexer, parser, and IR verifiers (fuzz/fuzz_lexer.rs, fuzz/fuzz_parser.rs, fuzz/fuzz_ir_verifier.rs), gated in .github/workflows/fuzz.yml.

Chaos testing. Cache-corruption injection (fixtures/incremental/cache-corruption, §20.5) and daemon-crash-mid-write injection (fixtures/incremental/interrupted-write) validate P7/P14 under fault injection, not just unit assertion.

Replay testing. Deterministic rebuild replay (P11) — every phase's replay fixtures (§12.5–§21.5) plus the bootstrap replay (fixtures/bootstrap/bootstrap-repro, §21.5) are re-run on every release candidate, not just on the commit that introduced them.

Conformance corpus governance. The conformance/ corpus (≥ 1,500 fixtures by §21.4) is append-only across releases — a fixture is never silently deleted, only marked superseded, so a regression cannot hide behind a shrinking test surface.

27. Build & Release Engineering

Reproducible builds. Pinned toolchain (rust-toolchain.toml, §10) inside a reproducible Docker builder image (Dockerfile); every release artifact's build is independently re-runnable and must match bit-for-bit (I7).

Artifact signing. cosign-based keyless OIDC signing (ADR-20) on every release artifact; signature verification is mandatory for the package registry client (T2, §22) and recommended for end users installing the compiler itself.

SBOM. A Software Bill of Materials is generated for every release (.github/workflows/release.yml) covering the full dependency graph, cross-checked against the lockfile's integrity hashes (§11 PackageManifest).

Release channels. Nightly (every green mainline commit), beta (weekly promotion from nightly after the full conformance corpus and bootstrap replay pass), stable (monthly promotion from beta after a zero-regression window). ABI-breaking changes (I6) are permitted on nightly, gated to a major version on beta/stable (§25).

Release gating. No promotion past nightly without: 100% conformance-corpus pass (§26), I7's binary-diff reproducibility gate green, and I12's stage2==stage3 bootstrap proof green (§21.4). This is the mechanical enforcement of P1 and P12 at the release boundary, not just at the commit boundary.

Rollback. Every release channel promotion is a tag, never a mutation of a previous tag; rollback is re-promoting the previous tag, with the incremental cache treated as fully disposable (§24 backup strategy) so a rollback never needs cache migration.

28. Performance Engineering

Methodology. Every §4 budget has exactly one owning benchmark in benchmarks/ and one metric in some phase's N.10 Operational Notes — no budget exists without a way to measure it continuously in CI (.github/workflows/benchmark.yml). Profiling uses flamegraphs (sampling profiler) for CPU-bound phases (parser, sema, optimizer) and heap profiling for allocation-bound phases (arenas, incremental cache). Tail latency (p99, not just mean) is tracked for every interactive-loop-facing budget — cold compile throughput is a mean/aggregate metric, but incremental recompile and CLI startup are p99 metrics, because interactive tools are judged by their worst case, not their average.

Regression gating. benchmark.yml fails a PR that regresses any M-series target below its Phase Gate's acceptance threshold by more than 5%, requiring an explicit override with written justification rather than a silent merge.

29. Scalability Analysis

Bottlenecks. Monomorphization explosion (§4's 8 GB ceiling, C5 §32) on generics-heavy code; trait-solver recursion (I13's fixpoint cap, §14) on deeply generic trait hierarchies; linker throughput (FM-8, §18) on workspaces with tens of thousands of translation units; incremental-cache DB contention (I9's lock ordering, §20) past roughly 10M LOC on a single machine.

Vertical scaling. The current design targets a 64-core, 128 GB RAM workstation ceiling (§4). Beyond that, single-machine worker-pool scaling (ADR-06) plateaus on trait-solver and linker bottlenecks that do not parallelize further within one process.

Horizontal scaling. Distributed incremental compilation across multiple machines is explicitly deferred (PhaseDeferred("§20"), §35) until the single-node dependency-graph DB's sharding (§20.7) is proven correct and I8 (monotonic dependency graph) is re-provable under a sharded, multi-machine cache — see Q9 (§33) for the specific invariant gap this would need to close.

Metadata scaling. The Incremental DB (§20) requires sharding by IncrementalKey prefix once the dependency graph exceeds roughly 40M nodes (extrapolated from C2 §32's 10M-LOC sizing) — single-shard lock contention under I9's ordering rule becomes the dominant latency source before raw storage size does.

Package-graph scaling. Package resolution (M7, §28) is currently a single-threaded constraint solve over the dependency graph; a workspace with a 50,000+ node dependency graph would need the resolver itself parallelized, which is unscoped for Phase 0 through Phase 9.

30. Mental Models & First Principles

  • MM1 — Compilation Is A Pure Function Of (Source, Toolchain). Compressed insight: treat the whole pipeline as a pure function from content hash to artifact hash · predicts: any two builds with identical inputs must be byte-identical outputs · bug class without it: "works on my machine" nondeterminism no amount of single-build testing catches · applies in §12 and §20.
  • MM2 — IR Immutability Buys Concurrency For Free. Compressed insight: an IR stage that cannot be mutated after validation can be shared across threads with zero synchronization · predicts: any optimizer data race traces to an accidental mutation, not a missing lock · bug class without it: heisenbugs that vanish under a debugger because a race depends on scheduling timing · applies in §16.
  • MM3 — Dominance Frontiers Are The SSA Contract, Not An Implementation Detail. Compressed insight: phi-placement correctness is dominance-frontier correctness, nothing more · predicts: any "wrong SSA" bug reduces to a dominance-tree bug · bug class without it: patching individual phi symptoms instead of fixing the dominance computation once · applies in §16.
  • MM4 — A Cache's Correctness Is Its Failure Mode, Not Its Hit Rate. Compressed insight: a cache that serves wrong data rarely is worse than one with a low hit rate that never lies · predicts: fail-closed design is a correctness boundary, not a performance tradeoff · bug class without it: "rare" incremental-build bugs that are the cache confidently serving stale data · applies in §20.
  • MM5 — Bootstrap Trust Is Transitive, Not Absolute. Compressed insight: stage2==stage3 proves self-consistency, not correctness against an external spec · predicts: a bug present since stage0 passes the bootstrap proof forever · bug class without it: treating a clean bootstrap as proof of correctness rather than proof of reproducibility · applies in §21.
  • MM6 — Register Allocation Is Resource Scheduling Under a Deadline. Compressed insight: linear scan and graph coloring both trade allocation quality for allocation speed · predicts: spill-rate regressions correlate with live-range width, not code size · bug class without it: "optimize the allocator" efforts that tune the wrong parameter · applies in §17.
  • MM7 — ABI Stability Is A Promise To The Linker, Not To The Compiler. Compressed insight: the compiler's internals can change freely; only the ABI surface is a promise · predicts: an ABI break is invisible in unit tests and only appears at link or load time · bug class without it: shipping an "internal refactor" that silently breaks every downstream consumer · applies in §17 and §18.
  • MM8 — Determinism Is Necessary But Not Sufficient For Reproducibility. Compressed insight: a deterministic function of a non-deterministic input (an unpinned toolchain) still produces a non-reproducible build · predicts: reproducibility bugs often trace to environment capture, not compiler logic · bug class without it: chasing a "flaky compiler" bug that is actually an unpinned dependency · applies in §12 and §27.

31. Comparative Architecture

Dimension LLVM/Clang rustc Go (cmd/compile) Cranelift (wasmtime) Zig compiler
IR mutability mutable in-place mostly immutable (query-cached) mutable SSA verification-adjacent, mostly immutable minimally staged
Self-hosting no (C++) yes yes no (hosted in Rust) in progress
Register allocation greedy + graph coloring delegated to LLVM rewrite-rule-based linear scan linear scan ad hoc per target
Incremental compilation none native query-based (Salsa-derived) package-granularity only none (single-shot JIT-oriented) partial
Runtime GC N/A (backend only) no yes N/A (backend only) no
  • LLVM/Clang — chose a mutable-in-place, shared multi-language IR to serve dozens of frontends; wins in ecosystems needing one optimizer shared across many source languages, at the cost of the IR-sharing-safety discipline P2 exists to avoid needing.
  • rustc — chose a query-based incremental architecture over an explicit dependency-graph DB; wins when the invalidation graph is implicit and pervasive across a huge standard library, at the cost of query-cycle debugging complexity the explicit graph in §20 avoids.
  • Go compiler (cmd/compile) — chose GC-coupled runtime layout and a simpler SSA rewrite-rule optimizer over exhaustive dataflow passes; wins for fast compile times on GC-tolerant workloads, at the cost of the manual memory-layout control this blueprint's ownership model requires.
  • Cranelift (bytecodealliance/wasmtime) — chose a WASM-first, verification-adjacent instruction- selection DSL over a native-ABI-first backend; wins for JIT/WASM-hosting scenarios needing fast compile-time codegen, at the cost of native calling-convention ergonomics this blueprint's §17 needs.
  • Zig compiler (ziglang/zig) — chose a single-pass, minimally-staged, comptime-driven backend over an explicit multi-IR pipeline; wins for compile-time-heavy metaprogramming with fast iteration, at the cost of the staged-IR replayability (P11) this blueprint depends on for debugging.

32. Back-of-Envelope Capacity Model

  • C1 — Parser Arena Footprint. 10,000,000 LOC × ~150 B live AST/token bytes per LOC = 1.5 GB, exactly the §4 parser ceiling (arena reset between files bounds peak, not cumulative usage).
  • C2 — Incremental Cache Steady-State Size. 10,000,000 LOC × ~350 B average serialized MIR+SSA cache entry per LOC = 3.5 GB, inside the §4 4 GB daemon ceiling with 500 MB headroom for index overhead.
  • C3 — Cold Compile Wall-Clock. 10,000,000 LOC ÷ 250,000 LOC/minute (§4 throughput floor) = 40 minutes for a from-scratch build of the full workspace.
  • C4 — Worker Pool Sizing. 64 cores (§4 vertical ceiling) × 4 logical workers per core (I/O-bound phases overlap CPU-bound phases) = 256 workers, exactly the §4 concurrency ceiling.
  • C5 — Monomorphization Peak. 8 GB ceiling ÷ ~2 KB average monomorphized-instance footprint = ~4,000,000 concurrently live generic instantiations before fail-closed rejection triggers.
  • C6 — Package Resolution Graph Walk. 5,000 nodes × 1.2 average edges per node × ~80 μs average SemVer-range constraint check per edge = 480 ms, inside the §4 500 ms budget.
  • C7 — FD Budget Under Peak Concurrency. 256 workers × 28 average open FDs per worker (source files + object outputs + linker pipes) = 7,168 FDs, inside the §4 8,192 soft limit with 12.5% headroom.
  • C8 — Incremental Recompile Latency Floor. 2 ms semantic-hash lookup + 200 ms p95 semantic reanalysis (§4) + 400 ms worst-case backend re-lowering = 602 ms, inside the §4 2,000 ms p99 incremental target with 3.3× margin.
  • C9 — Storage Amplification Ceiling. 10,000,000 LOC × ~120 B average source-byte footprint = 1.2 GB source tree, × 3 amplification ceiling (§4) = 3.6 GB maximum incremental-cache-plus-artifact footprint before compaction is forced.
  • C10 — Bootstrap Cycle Cost. 4 stages (stage0→stage3) × 40 minutes per full-workspace cold build (C3) = 160 minutes worst-case sequential bootstrap, amortized in practice because stage1/stage2 run incrementally (C8) rather than cold.
  • C11 — RTO Cache-Rebuild Feasibility. 5-minute RTO (§4) ÷ 40-minute cold-build baseline (C3) = an 8× shortfall, so the RTO target only holds if rebuild reuses a warm on-disk artifact cache — this is why I11's purge scope is per-entry, not global.
  • C12 — Deterministic Rebuild Verification Budget. 10 minutes (§4) ÷ 2 (build once, rebuild once to diff) = 5 minutes per build allowed, 8× less than the 40-minute cold-build baseline (C3), so the reproducibility gate must diff against a warm incremental cache, never a cold rebuild.

33. Hard Questions (Self-Examination)

  • Q1. How does a false-positive borrow rejection in §15 get distinguished operationally from a true optimizer miscompilation reported via the differential oracle in §16, given both can manifest as "the compiler altered a program the user believes is correct"?
  • Q2. If the semantic hash (§14) covers the resolved AST shape rather than source bytes, how does §20's invalidation propagation avoid resurrecting a stale MIR body when only whitespace changed but the arena's AstNodeId allocation order (§11) shifted?
  • Q3. Given P1's determinism principle (§6) and ADR-06's bounded-worker-pool choice (§9), what ordering guarantee makes 256 concurrent workers (§4) not violate I10's diagnostics-ordering invariant (§7)?
  • Q4. §21's stage2==stage3 proof only detects divergence, not root cause — how do §16's optimizer replay logs and §17's backend verifier jointly narrow a bootstrap mismatch to a single phase without re-running the entire pipeline?
  • Q5. §32's C7 shows FD usage at 87.5% of the §4 budget under peak 256-worker concurrency — what happens to §18's linker-subprocess isolation if a pathological package graph (§9's ADR-14) pushes past that ceiling?
  • Q6. §22's threat model treats procedural macros as an attack surface — how does that interact with §15's borrow/lifetime pass, which must analyze macro-expanded MIR it did not directly parse?
  • Q7. §28's M2 target (incremental recompile p99 < 2 s) is phase-gated at §20, alongside an 80% cache-hit-ratio acceptance criterion — what happens to M2 specifically on a cold cache immediately after a §25 schema-version bump?
  • Q8. §31 shows LLVM's mutable-in-place IR as the model ADR-09 (§9) rejects — under what workload does §16's immutable-IR replay-logging cost (P11, §6) exceed the concurrency benefit ADR-09 claims?
  • Q9. §35 defers distributed incremental compilation anchored at §20 — what invariant in §7 (I8, monotonic dependency graph) would need to be re-proven, not merely re-implemented, once cache state is sharded across machines?
  • Q10. §19's runtime uses a deterministic, non-randomized hasher for HashMap — how does that interact with §22's resource-exhaustion threat (hash-flooding), which the randomized-seed convention it deviates from was designed to mitigate?
  • Q11. §17's ADR-11 (§9) picks linear scan over graph coloring for implementation velocity — at what point does §28's spill-rate target (M11) force the documented fallback to graph coloring, and does that fallback threaten §4's per-compilation-unit codegen memory ceiling?
  • Q12. §26's differential-testing strategy against LLVM (§16, ADR-17 in §9) assumes LLVM is a trustworthy oracle — what does §16's own pitfall list imply about the limits of that assumption when a divergence is always attributed to this compiler's bug, never LLVM's?
  • Q13. §29 names trait-solver recursion as a bottleneck — how does that bottleneck compound with §14's fixpoint-cap enforcement (I13 in §7) once §21's self-hosting transition triples the effective source size the solver must process?
  • Q14. §24's SLO for 100% deterministic builds and §12's binary-diff CI gate both assume the CI runner's own toolchain is deterministic — what does §22's supply-chain-poisoning threat (T9) imply about trusting that assumption for the stage0 reference compiler itself?
  • Q15. §32's C9 bounds storage amplification at 3×, but §20's cache-eviction policy is LRU-by-content-address — under what edit pattern does LRU eviction interact badly with §21's bootstrap chain, which needs stage-specific artifacts retained past their last "use"?
  • Q16. §9's ADR-13 (content-addressed caching) and ADR-22 (monotonic time source) both reject timestamp-based mechanisms — does §23's FM-10 (daemon crash mid-write) still require some notion of write-ordering, and if so, where does it come from without violating either ADR?
  • Q17. §34's Alt B considers an LLVM-backed backend instead of the custom x86_64/AArch64 backend in §17 — if that alternative had been chosen, which invariant in §7 (I5, register allocation correctness) would transfer unchanged versus need re-derivation for LLVM's allocator internals?
  • Q18. §30's MM4 (fail-closed cache correctness) and §14's trait-solver-nontermination pitfall both describe systems that must stop rather than guess — what distinguishes a case where §6's P6 (bounded resources) should reject outright from one where §7's I13 depth ceiling should degrade gracefully?
  • Q19. §27's release-channel model and §25's ABI-stability window (I6) together imply a nightly build can break ABI — how does §17's ABI conformance suite avoid gating nightly the same way it gates stable, without silently letting an ABI break reach beta?
  • Q20. §33's own Q9 exposes a gap between §35's deferred-feature register and §7's invariants — does closing that gap belong in §34 (reconsidering a rejected architecture) or in a new §35 entry, and what distinguishes the two?
  • Q21. §4's 128 GB RAM vertical ceiling and §29's horizontal-scaling deferral together mean a 15M-LOC workspace has no supported configuration — does that gap belong to §29's scalability narrative or to §35's deferred-features register as an explicit un-defer trigger?
  • Q22. §19's no-GC runtime and §2's historical grounding both cite Go's self-hosting transition as precedent — what specifically does §19's ownership-based allocator make harder about self-hosting (§21) than Go's GC-backed runtime made it for cmd/compile?

34. Alternative Architectures (Roads Not Taken)

Alt A — Bytecode VM With A JIT Instead Of An AOT Native Backend

Source -> AST -> Typed IR -> Bytecode -> [Interpreter | JIT Compiler] -> Result
                                              ^                 |
                                              +---- profile ----+

Wins in a regime where startup latency and iteration speed dominate over peak throughput — a REPL-first or notebook-first workflow, or a language whose primary consumers never ship a standalone binary. CPython and early-era V8 embody this: a bytecode interpreter first, a JIT layered on later once hot paths are known via profiling. Rejected here because §1's deployment model targets standalone native executables as the primary artifact (systems programming, CI-produced binaries), and a JIT's warm-up cost and runtime code-generation attack surface (§22) are the wrong tradeoff for that target.

Alt B — LLVM-Backed Backend Instead Of A Custom x86_64/AArch64 Backend

SSA IR (this blueprint) -> LLVM IR translation layer -> LLVM optimizer+backend -> Object File

Wins when backend engineering effort must be minimized and multi-target support (many ISAs, not just two) matters more than build-time backend latency or bootstrap self-containment. Swift and Julia embody this: both target LLVM IR and inherit its instruction-selection and register-allocation maturity. Rejected here because self-hosting (§21) becomes materially harder with an external, non-self-hosted-in-this-language dependency in the trust chain, and the compile-time cost of LLVM IR generation plus LLVM's own optimizer conflicts with §4's cold-compile-throughput budget (M1, §28).

Alt C — Garbage-Collected Runtime Instead Of An Ownership Model

Source -> AST -> Typed IR -> SSA -> Codegen -> Executable
                                        |
                                 GC-managed heap (mark-sweep or generational)

Wins when developer ergonomics and compiler-implementation simplicity matter more than deterministic latency and memory-layout control — most application-level languages take this path. Go's cmd/compile and the OCaml toolchain embody it. Rejected here because §1 explicitly targets systems-programming use cases needing GC-pause-free execution, and because a GC's own allocator and collector would themselves need to be written in a language with no GC — circular for a self-hosting project without first solving the exact ownership problem this blueprint solves directly.

Alt D — Mutable, In-Place IR Instead Of Immutable Arena-Backed IR

AST --mutate--> MIR --mutate in place--> SSA --mutate in place--> Machine IR
        (each pass rewrites the previous stage's nodes directly)

Wins when single-threaded throughput on one large IR dominates and cross-pass concurrency is not needed — a smaller, throughput-only compiler with no incremental-compilation requirement. GCC's tree-SSA/GIMPLE pipeline substantially embodies this model historically. Rejected here because P2 (immutable IR boundaries) and P11 (replayability) both depend on being able to snapshot and diff IR state across passes without racing concurrent mutators (§16), which an in-place-mutation model makes substantially harder to retrofit than to design in from Phase 0.

36. Glossary

  • AST — Abstract syntax tree; the immutable, arena-backed parse output (§11).
  • MIR — Mid-level intermediate representation; the ownership-aware IR between typed AST and SSA (§8, §15).
  • SSA — Static single assignment; the optimizer-facing IR with explicit phi nodes (§8, §16).
  • CFG — Control-flow graph; the basic-block graph underlying MIR and SSA.
  • Dominance — A block A dominates B if every path from entry to B passes through A; the basis of SSA construction (Cytron et al. 1991, §5).
  • Dominance Frontier — The set of blocks where a definition's dominance "just" stops holding; determines minimal phi placement.
  • Phi Node — An SSA merge instruction selecting a value based on incoming control-flow edge.
  • ABI — Application binary interface; the calling-convention and layout contract (§17, I6).
  • LTO — Link-time optimization; whole-program optimization across translation units.
  • ThinLTO — A scalable, summary-based variant of LTO (deferred, §35).
  • DWARF — The debug-information format emitted alongside object code (§18).
  • Spill — A register allocator's fallback to a stack slot when live values exceed physical registers (§17).
  • Monomorphization — Generic specialization: one compiled instance per concrete type substitution.
  • Semantic Hash — A stable, structural hash of resolved program meaning, not source bytes (§14).
  • Arena Allocation — Bulk allocation with group-lifetime deallocation, avoiding per-node frees.
  • Trait Solver — The constraint-resolution engine for trait/interface bound satisfaction (§14).
  • Borrow Graph / Region Graph — The ownership-relation structure the borrow checker builds and verifies (§15).
  • Replay Build — A deterministic re-execution of a recorded build for debugging (P11).
  • Incremental Node — A cached, hash-keyed compilation artifact in the Incremental DB (§20).
  • Bootstrap Compiler — The initial, trusted (stage0) compiler used to build the first self-hosted stage.
  • Stage0 Compiler — The host-toolchain-built reference compiler that starts the bootstrap chain.
  • Stage1 Compiler — The compiler produced when stage0 builds the source.
  • Stage2 Compiler — The compiler produced when stage1 builds the source again.
  • Stage3 Compiler — The compiler produced when stage2 builds the source a third time, compared bit-for-bit against stage2 (I12).
  • SCCP — Sparse conditional constant propagation (Wegman & Zadeck 1991, §5).
  • LICM — Loop-invariant code motion.
  • Linear Scan — A single-pass register-allocation algorithm over SSA live ranges (Poletto & Sarkar 1999, §5).
  • Graph Coloring — A register-allocation algorithm modeling allocation as graph coloring (Chaitin et al. 1981, §5).
  • Content-Addressed Cache — A cache keyed by a hash of its content rather than a name or timestamp (ADR-13).
  • Lockfile — A deterministic, pinned record of resolved package versions (§11 PackageManifest).
  • SemVer — Semantic Versioning 2.0.0; the version-constraint grammar for packages (§5 RFCs).
  • TOML — The configuration/manifest serialization format (ADR-15).
  • postcard — The deterministic binary serialization format used for the incremental cache (ADR-03).
  • Distroless — A minimal container base image with no shell or package manager (ADR-19).
  • cosign — A keyless, OIDC-based artifact-signing tool (ADR-20).
  • SBOM — Software Bill of Materials; a generated manifest of every dependency in a release (§27).
  • Differential Testing — Comparing this compiler's output against a reference (LLVM) for behavioral agreement (§26).
  • Chaos Testing — Fault injection (crash, corruption) to validate recovery paths (§26).
  • Crash-Only Design — A system whose only recovery path is restart-and-replay, never in-place repair (P7).
  • NUMA — Non-uniform memory access; informs worker-pool scheduling locality (§4).
  • FD — File descriptor; a bounded, budgeted OS resource (§4).
  • RTO / RPO — Recovery Time Objective / Recovery Point Objective; recovery-speed and data-loss budgets (§4).
  • p50 / p95 / p99 — Latency percentiles; p99 bounds the worst case relevant to interactive tools.
  • Backpressure — Rejecting or delaying work when a bounded queue is full, rather than growing it unboundedly (P6).
  • Escape Analysis — Detecting whether a borrow outlives its referent's scope (§15).
  • Move Semantics — Ownership transfer that invalidates the source binding (§8, §11).
  • Drop Elaboration — Computing explicit destructor-call points from implicit scope-exit semantics (§15).
  • Coherence Check — Verifying no two trait implementations overlap ambiguously (§14).
  • Interned Identifier — A deduplicated, O(1)-comparable identifier string (§13).
  • Trivia — Whitespace and comments preserved losslessly alongside tokens (§13).
  • Recursive Descent — A top-down, grammar-production-driven parsing strategy (ADR-07).
  • Pratt Parsing — Operator-precedence expression parsing used within the recursive-descent parser (§13).
