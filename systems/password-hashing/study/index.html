30. Mental Models & First Principles

MM1 — "A KDF is a hash function wearing a seatbelt." The compressed insight: general-purpose hashes are optimized to be fast; a password KDF exists to make that exact property expensive on purpose. Predicts: any "fast" property proudly advertised for a hash function is a red flag for password use. Bug class without it: reaching for SHA-256 directly on a password because "it's a cryptographic hash" (the LDAP {SSHA} legacy format is a fossil of exactly this mistake). Applied in §6 P1–P4, §18.2 (why {SSHA} is parse-only).

MM2 — "Cost is a knob you must re-turn every year, not a constant you set once." Predicts: a parameter chosen as "secure" in 2020 is measurably weaker in 2026 against the same attacker budget, with no code change required to explain the drift — only hardware improvement. Bug class without it: a cost = 12 hardcoded in 2015 and never revisited. Applied in §6 P10, §25 (annual review), §22 T2–T3.

MM3 — "Constant-time is a property of the whole call graph, not one function." Predicts: a correctly-constant-time comparison can still leak timing if an earlier parse step short-circuits on secret-dependent length or content. Bug class without it: adding a length pre-check "for efficiency" immediately upstream of an otherwise-hardened ct_eq call. Applied in §7 I2, §20.2, §20.6, §23 FM-9.

MM4 — "A hash format is a wire protocol with one writer generation and infinite reader generations across time." Predicts: every format this library ever emits must be parseable forever, because a hash written once may need verifying a decade later. Bug class without it: "cleaning up" a legacy parser because it looks unused in the current test suite, breaking real production rows the test suite never sampled. Applied in §6 P5, §18.2, §25 (deprecation policy).

MM5 — "Memory-hardness taxes bandwidth, not just compute." Predicts: an attacker's advantage from parallel hardware (GPU/ASIC) is capped by how much memory bandwidth that hardware actually has per unit of parallel compute, not by raw core count. Bug class without it: assuming "more cores = proportionally more cracking throughput" for Argon2id/scrypt the way it holds for PBKDF2/bcrypt. Applied in §17.7, §15.7, §22 T2–T3, §32 CM7.

MM6 — "Data-dependent indexing trades a side-channel for a time-memory-trade-off defense." Predicts: there is no indexing strategy that is simultaneously immune to both cache-timing side-channels and TMTO attacks — a real design must pick which regime it defends and say so. Bug class without it: claiming Argon2id has "no side-channel surface" instead of the accurate claim (a partial, structural mitigation on the most-attacked phase). Applied in §17.2, §7 I9, §22 T5–T6.

MM7 — "The salt is not secret; the pepper is." Predicts: a design that tries to keep the salt confidential is solving the wrong problem (salts defeat precomputation, not guessing, and must be retrievable to verify at all); a pepper's entire value is that it is not stored with the hash. Bug class without it: encrypting the salt column "for extra security" while leaving the pepper inline in application config. Applied in §6 P11–P12, §22 T8, T12.

MM8 — "Every verify() call is a race between attacker guesses/second and this library's cost per guess." Predicts: the entire value of this system reduces to one ratio — attacker hardware throughput divided by hash cost — and every parameter choice is a lever on the denominator only (the numerator, attacker hardware, is out of this library's control). Bug class without it: treating parameter selection as a checkbox ("we use bcrypt") instead of an ongoing arms-race calculation. Applied in §32 (the entire Capacity Model), §22, §6 P10.

Required reading (§5)

Books

  • Ferguson, Schneier, Kohno — Cryptography Engineering (2010), ch. 4 (Hash Functions) & ch. 24 (guidance on KDFs). Extract: why a general-purpose hash is the wrong primitive for passwords. Applied in §8 (Domain Model KDF construction) and §6 P1–P4.
  • Aumasson — Serious Cryptography (2nd ed., 2024), ch. 13 (Password Hashing). Extract: the comparative treatment of bcrypt/scrypt/Argon2/PBKDF2 tradeoffs. Applied in §31 (Comparative Architecture Table) and §6.
  • Katz & Lindell — Introduction to Modern Cryptography (3rd ed., 2020), ch. 4 (MACs/HMAC) & ch. 5 (hash functions). Extract: the HMAC construction underlying PBKDF2. Applied in §13.2 (Phase 1).
  • Menezes, van Oorschot, Vanstone — Handbook of Applied Cryptography (1996), ch. 10 (Identification & Entity Authentication), section 10.2.3. Extract: the salted-hash + work-factor pattern's origin. Applied in §8 and §6 P8–P9.
  • Anderson — Security Engineering (3rd ed., 2020), ch. 4 (Access Control) & ch. 20 (Advanced Cryptographic Engineering). Extract: the operational/incident-response framing for credential compromise. Applied in §22 (Threat Model) and §23 (Failure Modes).
  • Boneh & Shoup — A Graduate Course in Applied Cryptography (free online, v0.6, 2023), ch. 4 (Message Integrity) & ch. 21 (definitions of PRFs). Extract: the PRF/PRG formalism behind HMAC-as-PRF, needed to reason about PBKDF2's security reduction. Applied in §13.2.

Papers

  • Provos & Mazières, 1999 — A Future-Adaptable Password Scheme (USENIX ATC). The bcrypt design. Applied in §14 (Phase 2) throughout.
  • Percival, 2009 — Stronger Key Derivation via Sequential Memory-Hard Functions (BSDCan). The scrypt design and the sequential-memory-hardness argument. Applied in §15 (Phase 3) N.2.
  • Biryukov, Dinu, Khovratovich, 2016 — Argon2: New Generation of Memory-Hard Functions for Password Hashing and Other Applications (IEEE EuroS&P; PHC winner 2015). The Argon2 design. Applied in §16–17 (Phase 4–5) throughout.
  • Kaliski (IETF), RFC 8018, 2017 — PKCS #5: Password-Based Cryptography Specification v2.1. The PBKDF2 construction. Applied in §13.2.
  • Percival & Josefsson (IETF), RFC 7914, 2016 — The scrypt Password-Based Key Derivation Function. The normative scrypt spec. Applied in §15.2.
  • Biryukov et al. (IETF), RFC 9106, 2021 — Argon2 Memory-Hard Function for Password Hashing and Other Applications. The normative Argon2 spec, including its section 5 test vectors. Applied in §16.2, §17.2, and §26 (Testing Strategy).
  • Florencio, Herley, van Oorschot, 2014 — An Administrator's Guide to Internet Password Research (USENIX LISA). What passwords users actually pick; grounds the threat model's dictionary-attack assumption. Applied in §22 T1.
  • Dürmuth, Angelstorf, Castelluccia, Perito, Chaabane, 2014/2015 — OMEN: Faster Password Guessing Using an Ordered Markov Enumerator (ESSoS). State-of-the-art guessing-order attack; grounds the assumption that dictionary attacks are smarter than pure brute force. Applied in §22 T1 and §32 CM10.

Reference Implementations

  • P-H-C/phc-winner-argon2 (github.com/P-H-C/phc-winner-argon2) — study src/core.c (fill-segment) and src/blake2/blake2b.c (H′). Lesson: the reference's block-indexing wraparound at segment 0. Pitfall not to copy: the reference's memory-wipe path is best-effort, not audited-constant-time; do not treat it as a zeroization reference. Applied in §16–17.
  • Tarsnap scrypt (github.com/Tarsnap/scrypt) — study lib/crypto/crypto_scrypt-ref.c. Lesson: the ROMix access pattern. Pitfall: the reference's SSE2 path diverges numerically from the portable path only in timing, not output — do not conflate the two when benchmarking. Applied in §15.
  • OpenBSD crypt_blowfish.c (in src/lib/libc/crypt/) — study the Eksblowfish key schedule and the $2a$/$2b$/$2x$/$2y$ version dispatch. Pitfall: the historical $2$ (no version byte) format is obsolete and must be rejected, not silently accepted. Applied in §14.
  • RustCrypto password-hashes workspace (github.com/RustCrypto/password-hashes) — study the argon2, bcrypt, scrypt, pbkdf2 crates' public API shape (not the internals verbatim). Lesson: how a Rust API expresses Params as a typed builder. Pitfall: do not copy their PHC parameter-string parser without adding the legacy-format dispatch this project needs. Applied in §11, §18–19.
  • OpenSSL (github.com/openssl/openssl) — study crypto/evp/p5_crpt2.c (PKCS5_PBKDF2_HMAC). Lesson: the C reference's iteration-count/output-length loop structure. Pitfall: OpenSSL's PBKDF2 has historically had CVEs in edge-length handling (short/zero-length inputs) — the conformance suite includes exactly those edge fixtures (§13.5). Applied in §13, §31.

Argon2i
the data-independent-indexing Argon2 variant (§17.2).
Argon2id

bcrypt
the Eksblowfish-based work-factor password scheme (Provos & Mazières 1999).

scrypt's block-mixing function built from Salsa20/8 (§15.2).
breach triage

crypt(3)

CSPRNG
cryptographically secure pseudorandom number generator; source of salts (§11.3).
dictionary attack
a guessing attack ordered by likely-password probability rather than exhaustive enumeration (§5 Papers, Dürmuth et al.).
dudect
a statistical black-box timing-leak detection methodology (§20).
Eksblowfish
bcrypt's expensive key-schedule variant of Blowfish (§14.2).
EncodedHash
the opaque, caller-persisted string type wrapping a PHC or legacy encoding (§11.4).
enforce_floor
the non-bypassable parameter-floor check (§11.2, I3).
Feistel network
the round-function structure underlying Blowfish (§5 Books).
G / BLAMKA
Argon2's compression function (§16.2).
H′ (Blake2b-Long)
Argon2's arbitrary-output-length hash construction (§16.2).
HMAC
hash-based message authentication code, the PRF underlying PBKDF2 (§13.2).
KAT
known-answer test; a fixed input/output pair from a normative spec (§26).
KDF
key derivation function; the general class PBKDF2/bcrypt/scrypt/Argon2 belong to (§8).
LDAP {SSHA}
a salted-SHA-1 legacy scheme found in directory services (§18.2).
legacy format
any of the six parse-only, never-generated encodings (§6 P5).
Memory-hard function
a KDF whose cost scales with memory footprint, not just compute time (§30 MM1, MM5).
needs_rehash
the boolean signal that a verified hash's parameters are stale versus the current recommendation (§7 I14).
OPAQUE
an asymmetric password-authenticated key exchange protocol (§34 AA1).
Params
the per-algorithm parameter enum (§11.2).
Parameter floor
the minimum acceptable cost setting per algorithm, OWASP-sourced (§4, §6 P9).
PBKDF2
Password-Based Key Derivation Function 2, RFC 8018.
Pepper
a server-side secret added to (not stored with) a password before hashing (§11.3, P12).
PHC
Password Hashing Competition (2013–2015) and, by extension, the PHC-string encoding format it standardized (§8.1).
phpass
the WordPress/phpBB $P$/$H$ legacy hash format (§18.2).
PRF
pseudorandom function; the security abstraction HMAC provides (§5 Books).
Rainbow table
a precomputed hash-to-plaintext lookup structure, defeated by salting (§22 T12).
ROMix
scrypt's memory-hard core, sequential fill then pseudorandom read-back (§15.2).
Salsa20/8
the 8-round-reduced stream cipher scrypt's BlockMix uses (§15.2).
Salt
a per-hash random value preventing precomputation attacks (§11.3, I5).
scrypt
the sequential-memory-hard KDF of RFC 7914 (Percival 2009).
Side-channel
an attack exploiting observable implementation behavior (timing, cache access) rather than cryptanalysis (§22 T4, T6).
Time cost
the number of passes a memory-hard KDF performs over its working memory (§4).
Time-memory trade-off (TMTO)
an attack reducing memory use at the cost of extra compute, defeated in part by Argon2id's Argon2i first pass (§17.2, I9).
VerifyOutcome
the typed result of a successful verify() call (§11.5).
Wycheproof
Google's cryptographic test-vector project (§5 Reference Implementations).
Zeroization
the practice of overwriting secret memory before deallocation (§11.6, P14).
Zeroizing<T>
the zeroize crate's wrapper type providing drop-time zeroization (§11.6).
subtle::ConstantTimeEq
the audited constant-time comparison trait this library uses (§7 I2, ADR-10).
Argon2 lane
one of parallelism independent memory partitions filled concurrently (§8.4).
Argon2 segment
one of four sub-partitions of a lane, the unit of fill-order sequencing (§8.4).
PHC algorithm-id
the string token (argon2id, scrypt, …) identifying an algorithm within a PHC string (§8.1, I12).
Rehash-on-login
the operational pattern of upgrading a stored hash's parameters the next time its owner authenticates (§6 P10, §19.2).
SBOM
