In one paragraph

A password hash is what a service stores instead of the password, built so that guessing a password from a stolen copy is expensive on purpose (MM1). This design is a Rust library plus a thin command-line tool, with no network listener and no storage of its own (§1). It implements four standard constructions (PBKDF2, bcrypt, scrypt, Argon2) behind one hash()/verify() pair. It enforces minimum cost settings, reads seven old hash formats, and tells the caller when a stored hash should be upgraded (§1, §1.2). The embedding authentication service runs it (§1.4). Its defining trade is CPU and memory cost for attacker cost (§4).

The problem, concretely

A service stores a hash of every user's password. One day the user table leaks. The attacker now has "unlimited offline compute" and guesses in order of likely passwords, not at random (§22 T1). They run it on commodity GPUs (T2) and possibly custom silicon (T3). The defender cannot even see it happening (T1, "undetectable by the defender in real time"). Attacker hardware is outside the library's control, so its only lever is the cost of one guess (MM8, §30).

The naive choice is a general-purpose hash such as SHA-256, which is built to be fast. MM1 calls a password KDF "a hash function wearing a seatbelt": the fast property is what it must make expensive on purpose, and the old LDAP {SSHA} format is a fossil of that mistake (MM1).

Three more problems sit on top of that one:

  • The table is a decade of formats. A production database accumulates bcrypt variants, Django, WordPress, LDAP and crypt(3) hashes, which the design must verify and move forward without a mass reset (§2, §22). §1, §2, §18.1 and §18.4 count seven legacy formats; §1.2's non-generation clause, §18.3, §19.4, §25, §31, §36 and §38's Phase 6 deliverable say six.
  • Small slips silently make a weak hash. A config value of "64" must mean 64 MiB, not 64 bytes (P8). A typo or copied stale default enables faster-than-intended cracking (T7). Stored $2a$ and $2b$ bcrypt hashes disagree on high-bit-character passwords (CVE-2011-2483, §2).
  • Strong hashing costs real RAM. An 8 GiB host holds 128 concurrent default Argon2id hashes (CM1, §32), so capacity planning has to budget memory, not only CPU (P1).

How it works, end to end

The blueprint's own layering (§3), lightly condensed:

 Application (registration, login, breach-response tooling)
        │  public API — crate `password-hash`
 Unified API:  hash(pw, Algorithm, Params) -> EncodedHash
               verify(pw, &str) -> Result<VerifyOutcome, AuthError>   [ct_eq boundary]
               verify_with_pepper(pw, pepper, &str)
               PHC-string codec · legacy parsers (parse-only)
        │  trust boundary: secret material crosses here
 Algorithm layer:  PBKDF2 (§13) | bcrypt (§14) | scrypt (§15) | Argon2i/d/id (§16–17)
        │  concurrency boundary: each call owns its working memory
 Primitives (external crates): SHA-256/512 · HMAC · Blake2b · Blowfish · Salsa20/8

Follow one login through those boxes (§8.2, §19.2):

  1. The application wraps the typed password in a Password value, which wipes its bytes on drop and prints Password(REDACTED) under Debug (§11.6, P14). It calls verify() from the umbrella crate password-hash (§10, §19.3).
  2. parse_any in password-hash-core/src/encoded.rs looks at the leading characters of the stored string and picks a parser: PHC string, bcrypt $2[abxy]$, or a legacy prefix (§8.2, §18.3). Unrecognised input becomes AuthError::Malformed and never reaches the compare step, so it leaks no timing signal about secrets (§8.6, §19.8).
  3. The matching crate recomputes the digest from the password plus the stored salt and parameters: pbkdf2-impl, bcrypt-impl, scrypt-impl or argon2-impl (§3, §10). Argon2 asks Memory::allocate for its working memory in a single allocation (§16.7); a refusal returns Error::Alloc, never a panic (§8.7, I4).
  4. verify.rs compares recomputed against stored with subtle::ConstantTimeEq (§10, §20.2, ADR-10).
  5. On a match, upgrade.rs computes needs_rehash by comparing the stored parameters with the live PARAMS_<year> constant, currently PARAMS_2026; a legacy-format hash is always true (§10, I14, I6, §19.2, §19.6, P10).
  6. The caller gets VerifyOutcome::Authenticated { needs_rehash } or AuthError::WrongPassword (§8.2, §11.5). Because both answers come from one call, a single database write per login covers authentication and the rehash (P6).

Registration runs the other way: hash() calls enforce_floor, draws a salt of at least 16 bytes from getrandom, runs the algorithm and serialises to a PHC string or the bcrypt encoding (§19.2, I3, I5). The pwhash binary wraps hash, verify and identify, which prints algorithm and parameters without a password, for DBAs sorting a leaked dump (§19.2, §1.5). The library never touches storage: EncodedHash is an opaque string the caller persists, and legacy formats are re-emitted as PHC on upgrade (§3, P5).

The core ideas

Slow on purpose: the cost knob (§13, §14, MM1, MM2)

Every algorithm exposes a cost setting, and that cost per guess is the only lever this library has against attacker hardware (MM8). Each has a floor the library refuses to go below (§4, P9).

  • PBKDF2 (§13.2): the password is mixed into a keyed hash (HMAC) that is run over and over. Each output block is the XOR-fold of c successive HMAC applications, the first seeded by salt plus the block number. Blocks are concatenated and truncated to the requested length (I8: block count is ⌈dkLen / hLen⌉). Cost is the iteration count c, and the real work is 2 × iterations HMAC calls (§13.6). Floors: 600,000 for SHA-256, 210,000 for SHA-512 (§4).
  • bcrypt (§14.2): instead of one key setup for a cipher (Blowfish), it runs 2^cost + 1 expensive setups that interleave password and salt bytes, then a 64-iteration loop over the fixed text OrpheanBeholderScryDoubt. Cost is therefore exponential: cost 13 roughly doubles cost 12's latency (§14.7). Floor and default cost: 12 (§4). Input beyond 72 bytes is silently dropped, so the library warns exactly once per call (I7).

The parameters are meant to move. Hardware improves, so PARAMS_<year> is a versioned constant reviewed annually (P10, MM2), and it is the yardstick needs_rehash compares against (I14).

Memory-hardness: make the attacker pay for RAM, not just cores (§8.4, §15, §16, MM5)

For PBKDF2 and bcrypt, more attacker cores means proportionally more cracking throughput (MM5). A KDF whose cost scales with memory footprint as well as compute (a memory-hard function, §36) changes that: the attacker's advantage from parallel hardware is capped by the memory bandwidth it has per unit of compute, not by raw core count (MM5, T2, T3).

  • scrypt (§15.2): allocate N = 2^ln blocks of 128r bytes, fill them one after another, then read them back in a data-dependent pseudorandom order (the ROMix step). Memory needed is N × 128 × r. Its read-back phase is bandwidth-bound, not compute-bound (§15.7).
  • Argon2 (§8.4, §8.5): memory is lanes × lane_length blocks of 1,024 bytes. Each lane is cut into 4 segments, and the fill order is pass, then segment, then lane. Memory cost is in KiB (P8, I4): for PARAMS_2026 (t=3, m=65536, p=4) it is exactly 65536 × 1024 = 67,108,864 bytes (§16.4).

The blueprint's own trace of one default Argon2id hash (§8.5):

Step What happens
1 H0 = Blake2b over all inputs (cost settings, password, salt, ...): a 64-byte seed
2–3 per lane, blocks 0 and 1 derived from H0 with the lane number
4 fill_segment runs 3 passes × 4 segments × 4 lanes
5–6 XOR the last block of each lane, then H' reduces it to a 32-byte tag
7 encode as $argon2id$v=19$m=65536,t=3,p=4$<salt>$<tag>

The price shows up as capacity: concurrent sessions = RAM_budget / memory_kib, and for bandwidth about (64 MiB × 3) / 0.1 s = 1,920 MiB/s per concurrent hash (CM1, CM7, §32).

Argon2id's mode switch (§17.2, I9, MM6)

Argon2 picks which earlier block to read in two ways (§17.2). Argon2d uses the first 8 bytes of the previous block; §17.2 says this data-dependent choice resists attacks that trade less memory for more computation (TMTO), but an attacker with co-located compute can observe the access pattern (cache-timing, T6). Argon2i uses a counter-and-constant-seeded pseudorandom block independent of the password, which resists cache-timing (§17.2). MM6: no indexing is immune to both, so a design must say which it defends. Argon2id mixes the two (I9, §17.2).

The blueprint describes the switch in conflicting ways and does not reconcile them:

  • Where it sits. §17.2: the first pass's first-lane segment 0 is Argon2i, everything else Argon2d (I9: "first-pass, first-lane segment"). §17.6: "lane 0, segment 0 only", calling "the whole first pass uses Argon2i" a misreading. But T5 and T6 name a "first-pass Argon2i" mode or segment, §20.2 says "first-pass mitigation", and §36 defines Argon2id as "first-pass Argon2i then Argon2d".
  • Which half stops TMTO. §17.2, §17.6 and MM6 make data-dependent (Argon2d) indexing the TMTO defence; T5 and the §36 TMTO entry credit the Argon2i first pass instead.

The gate is the RFC 9106 section 5.3 known-answer test, not code review alone (§17.5, §17.6).

PHC strings and the verify state machine (§8.1, §8.2, §8.6)

A PHC string stores everything needed to verify later in one self-describing text: algorithm id, version, cost parameters, salt, hash (§8.1). Example from §8.5: $argon2id$v=19$m=65536,t=3,p=4$<b64 salt>$<b64 tag>. Parameters are separated by ,, never & (I10). Because the string describes itself, assessing a leak never needs outside metadata (§22).

verify() is a small state machine (§8.2):

State Does Next
Identify match prefix ($, {, bcrypt $2[abxy]$) ParsePhc / ParseBcrypt / ParseLegacy, else Reject
Parse* build a ParsedHash success Recompute, failure Reject (Malformed)
Recompute run the matching algorithm digest
Compare constant-time compare (I2) Authenticated or Rejected
Authenticated compute needs_rehash (I14) outcome returned

Worked failure (§8.6): m=65536&t=3,p=4 uses &, so the parser fails at param-list with ParseError::Malformed { field: "param-list", pos: 24 }. verify() returns AuthError::Malformed without recomputing, so no secret-dependent comparison occurs.

Constant-time compare (§20.2, I2, P7, MM3)

A comparison whose timing depends on secret data leaks the hash byte by byte (I2) and narrows an attacker's search space call by call (P7). The design compares the whole encoded hash with the audited subtle crate (ADR-10) and folds the length check into the same constant-time path: a fixed-length buffer, zero-padded to the longer of the two, is compared in full (§20.2). MM3: the property belongs to the whole call graph, so an early length check upstream of a hardened compare still leaks. It is gated with dudect, a timing-leak detector, at t-statistic ≤ 4.5 over ≥ 1,000,000 samples per algorithm (M6, §20.4).

Rehash on login (§19.2, P6, P10, I6, I14, MM4)

A stored hash is upgraded the next time its owner logs in (rehash-on-login, §36, §19.2). verify() returns "authenticated" and "needs_rehash" in one call (P6). needs_rehash is recomputed against the current PARAMS_<year> every time, never cached (I14), and any legacy-format hash returns true unconditionally (I6). A user hashed under last year's parameters moves forward at their next login, with no forced reset (§22, §25). Toy trace from §19.4: a hash made under a prior year's PARAMS_<year> verifies with needs_rehash: true, while a fresh hash → store → verify round trip returns Authenticated{needs_rehash:false}. MM4 explains the cost: a hash written once may need verifying a decade later, so a legacy parser is never removed while a known production corpus still contains its format (§25, P5).

The trade-offs — where engineers disagree

Default algorithm: Argon2id (ADR-03)

Chosen: Argon2id as the default for new code, on OWASP and RFC 9106 consensus (P1). Rejected: bcrypt, scrypt, PBKDF2 as the default. When the rejected choice is right: when the memory budget is below 19 MiB per session (embedded, or serverless where cold starts matter).

Conservative default for small machines: bcrypt (ADR-04)

Chosen: bcrypt as the legacy/embedded default: mature, small memory footprint, no allocator dependency (P2). Rejected: Argon2id for that role. When the rejected choice is right: any environment where at least 19 MiB per hash is affordable, because Argon2id wins there. bcrypt's cost is no memory-hardness (T2, P2).

Combined verify result (ADR-09, P6)

Chosen: verify() returns (authenticated, needs_rehash) in one call, so one database write covers both. Rejected: a separate needs_rehash() call, which P6 says doubles login-path latency and can lose the rehash on a crash between the two calls. When the rejected choice is right: when authentication and the upgrade path are already decoupled across separate services.

Floors cannot be bypassed (ADR-11, P9)

Chosen: the public API refuses any hash() call below the OWASP 2026 floor with Error::WeakParameters. Rejected: config-only guidance. When the rejected choice is right: a research or benchmark harness that deliberately tests sub-floor parameters, through a low-level test-only API. The price: a caller who "just wants it fast for tests" must use that explicit test-only path (P9).

Pepper is opt-in and separate (ADR-14, P12)

Chosen: verify_with_pepper(pw, pepper, encoded) as a separate opt-in API. The pepper is a server-side secret that is never stored with the hash (MM7). Rejected: baking a pepper into the default hash(). When the rejected choice is right: when the application already has an HSM-backed envelope-encryption layer, which makes an extra pepper redundant. The operational cost of the chosen design is rotation: a rotation without dual-read support locks users out (FM-7).

Legacy formats are parse-only (ADR-08, P5)

Chosen: old formats are parsed so users can log in and be upgraded, and are never generated. That keeps the parser surface finite. Rejected: also generating them for compatibility. When the rejected choice is right: a migration tool that must emit old-format hashes for a read replica that has not been upgraded yet.

Roads not taken (§34, §35)

OPAQUE, an asymmetric password-authenticated key exchange (§34 AA1): the server holds only an OPRF key and a wrapped envelope, never anything an offline attack can target. It wins in greenfield systems where the client can run the protocol. It is rejected here because this is a drop-in hashing library for existing flows, and OPAQUE is a protocol redesign (§1.2, §1.3).

Client-side pre-hashing (§34 AA2): the client sends SHA256(password) and the server runs Argon2id over that. The blueprint cites no system where it wins as a primary defence: TLS already protects the wire, and a fixed unsalted client digest is weaker per guess than the full KDF.

Balloon Hashing (§34 AA3): a memory-hard function with a simpler security reduction. It wins when a formal proof matters more than raw performance parity. Rejected because Argon2id is standardised, widely deployed and has test corpora (§5, P1).

Pepper held in an HSM or KMS (§34 AA4): wins in regulated environments that need a hardware root of trust. Rejected as the default because it adds a network round trip and external dependency to every call, against the no-network scope (§1.2, §1.4). It remains the extension point of the pepper API.

Eight items sit in the deferred register, each with an un-defer trigger (§35).

What must never be false

  • I1 parse(serialize(x)) == x for every PHC string it emits. Noticed by a property test (§26) and phc_roundtrip_failures_total.
  • I2 the compare step never branches on secret-dependent time. Noticed by the dudect CI gate (M6) and dudect_t_stat; a failure blocks the release.
  • I3 hash() never emits parameters below the floor. Noticed by a unit test per algorithm and weak_param_rejections_total.
  • I4 Argon2 memory allocated equals memory_kib * 1024 bytes exactly. Noticed by an assertion in the KAT harness and argon2_alloc_bytes.
  • I5 every generated salt is at least 16 bytes. Noticed by a property test and salt_len_gauge.
  • I6 a parsed legacy hash always has needs_rehash = true. Noticed by a fixture per format and legacy_parse_total{format}.
  • I7 bcrypt truncates only after byte 72, deterministically, with exactly one warning. Noticed by a 73-byte-password fixture and bcrypt_truncation_warnings_total.
  • I8 PBKDF2 output blocks equal ⌈dkLen / hLen⌉, no off-by-one. Noticed by the RFC 6070 KAT.
  • I9 Argon2id's first-pass, first-lane segment uses Argon2i indexing. Noticed by the RFC 9106 section 5.3 KAT; the build is rejected on mismatch.
  • I10 the PHC parameter delimiter is ,, never &. Noticed by a malformed-input fuzz fixture and phc_parse_errors_total{reason}.
  • I11 a pepper is applied identically at hash() and verify(). Noticed by a hash-then-verify property test; an asymmetry surfaces as failed logins.
  • I12 no two Algorithm variants share a PHC identifier. Noticed at compile time by an exhaustive match.
  • I13 enforce_floor runs on every hash() path. Noticed by a coverage gate and by the parity of hash_calls_total with enforce_floor_calls_total; CI fails on divergence.
  • I14 needs_rehash is computed from the current recommendation, never a cached value. Noticed by a stale-year fixture and the needs_rehash_total trend.

What breaks in production

  • FM-1: login latency spikes and OOM kills. Concurrent Argon2 hashes exceed the host's RAM budget (CM1). Memory::allocate returns Error::Alloc, and argon2_alloc_bytes history shows it. The library never retries silently. Recovery is a lower concurrency cap or more memory.
  • FM-2: multi-second login stalls. A bcrypt cost set far too high, such as 18 instead of 12. The bcrypt_hash_seconds{cost} histogram shows an outlier. The operator corrects the cost, and existing hashes drift back through needs_rehash.
  • FM-4: a legitimate user cannot log in. The stored string was corrupted, e.g. truncated by a too-narrow database column. A parse-failure spike shows it (phc_parse_errors_total{reason= "truncated"}). Recovery is a backup restore or a forced reset for the affected rows.
  • FM-5: old Argon2 hashes never upgrade. needs_rehash was computed from a stale cached comparison (an I14 regression). The tell is a flat needs_rehash_total trend that should be falling. A patch release fixes it, and affected rows heal on their next login.
  • FM-7: mass lockout after a pepper change. Rotation without dual-read means verify() only tries the new pepper; a verify_calls_total{result="wrong_password"} spike follows the deploy. Roll the pepper back, then redeploy with dual-read (try new, fall back to old), deferred (P12).
  • FM-9: a timing leak is reintroduced. A refactor adds a length short-circuit in the compare path (§20.6). The dudect gate fails the release candidate. Revert the diff and re-run.
  • FM-11: long passphrases are silently cut. bcrypt's 72-byte cap truncates input and the warning log level hides it. bcrypt_truncation_warnings_total (I7) should be non-zero if it happened. Surface the warning at WARN.
  • FM-12: rows become unparseable mid-migration. A data migration runs while a code deploy changes the recognised formats. Shows as a phc_parse_errors_total{reason="unrecognized_format"} spike. Never ship a format-generating change before its parser is live (§25).

Threats a reader should know (§22):

  • T1 offline cracking of a leaked table, answered by cost at the floors (§4). T2 and T3 (GPU, ASIC) are answered by memory-hardness, so PBKDF2- and bcrypt-hashed rows are rehashed first.
  • T6 cache-timing side channel on Argon2d and Argon2id. Documented as a structural property, not eliminated; for a co-tenant-hostile environment, choose Argon2id, not Argon2d.
  • T9 the compiler removes a "useless" final write that zeroes the password buffer. Answered by zeroize's volatile write (ADR-16), verified with cargo miri.
  • T11 an attacker submits a crafted legacy string hoping to hit a weaker path. Answered by strict per-prefix dispatch, and legacy hashes always force needs_rehash (I6).

How it compares

Compared in §31 on default algorithm, floors, legacy handling, pepper and memory-hardness:

  • libsodium chose Argon2id as its memory-hard KDF but exposes three fixed presets (interactive, moderate, sensitive) instead of raw parameters. That fits applications where an operator must never be able to mis-set a cost, at the price of the fine-grained annual review this design keeps (P10).
  • OpenSSL treats password hashing as one KDF among many, PBKDF2 historically, with Argon2 through the provider model from 3.2. That suits a system already deep in OpenSSL's provider model that wants one dependency, with no built-in floor (ADR-11 fills that gap).
  • PHP password_hash is the closest design: password_verify auto-detects the algorithm and password_needs_rehash is the equivalent of needs_rehash. It wins through installed base and standard-library inertia, and leaves floors to caller discipline.
  • Django keeps PBKDF2-HMAC-SHA256 as its default even though Argon2 has long been a pluggable hasher. Changing a framework's default breaks deployments, so backward compatibility wins there. P10 and §25's SemVer discipline are this design's answer to that tension.

Questions to test yourself

  1. Why does Argon2id split its indexing strategy across passes instead of using one strategy throughout, and what attack does each half specifically defend against? — Hint: §17.2, then compare T5, T6 and MM6.
  2. At what RAM budget does bcrypt become the correct default instead of Argon2id, and how do you compute that threshold from this document alone? — Hint: P2, ADR-04 and §4, with CM1's formula.
  3. Why does verify() return a compound (authenticated, needs_rehash) result instead of two separate calls, and what failure mode does the combined call prevent? — Hint: P6 and §19.6.
  4. Why must constant-time comparison fold length-checking into the comparison itself rather than short-circuiting on mismatched length first? — Hint: §20.2, I2 and MM3.
  5. Why is a pepper never persisted alongside the hash, and what specific failure mode does that design choice create during a pepper rotation? — Hint: P12, MM7 and FM-7.

If you only remember three things

A password hash is a race between attacker guesses per second and the cost of one guess, so every parameter is a lever on the cost and has to be re-turned as hardware improves (MM8, MM2, P10). Memory-hardness caps how much a GPU or custom chip can help the attacker, but it costs the defender RAM, so capacity is planned in memory (MM5, CM1). Authentication and upgrade are one call: verify() also says whether the stored hash is stale, so a decade of formats migrates at login without a mass reset (P6, I14, MM4, §22).

Words used here

  • KDF (key derivation function): the class the four algorithms belong to; for passwords, a hash made expensive on purpose (§36, MM1).
  • Salt: a random per-hash value that defeats precomputed tables; it is not secret (MM7, I5).
  • Pepper: a server-side secret mixed in before hashing, never stored with the hash (P12, MM7).
  • Memory-hard function: a KDF whose cost scales with memory as well as compute (§36, MM5).
  • Parameter floor: the minimum cost setting per algorithm that the library accepts (§4, P9).
  • PHC string: the self-describing text holding algorithm, parameters, salt and hash (§8.1).
  • Constant-time comparison: a comparison whose duration does not depend on secret content or length (I2).
  • needs_rehash: the flag saying a verified hash's parameters are out of date (I14).
  • Legacy format: an old hash encoding the library reads but never writes (P5).
  • KAT (known-answer test): a fixed input and expected output from a normative spec (§36, §26).
  • TMTO (time-memory trade-off): an attack that uses less memory for more computation (§36, T5).
  • dudect: a statistical black-box tool that detects timing leaks (§20.2, M6).
