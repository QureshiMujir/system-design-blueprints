⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the full workspace (§10) with every crate compiling as an empty shell; land governance docs; establish the Password/Algorithm/Error core types (§11.1, §11.6) with real semantics even though no algorithm is implemented yet; wire CI so every later phase has a gate to land against.

Deliverable

A workspace that builds clean on cargo build --workspace, a placeholder hash()/verify() round trip on a fixed vector, and a green CI pipeline with four jobs (build, test, clippy, fmt).

Acceptance

cargo test --workspace passes with ≥ 8 tests (one per crate stub + Password Debug-redaction test + Algorithm PHC-id uniqueness test, I12). cargo clippy -- -D warnings returns zero warnings. CI wall-clock ≤ 3 minutes. All governance docs (README, SECURITY, CONTRIBUTING) present and non-empty.

Fixtures

fixtures/phase0/password_debug.txt — expected redacted Debug output string, exact match. fixtures/phase0/algorithm_ids.json — the seven Algorithm variants, asserts no duplicate PHC-id mapping (I12). fixtures/phase0/placeholder_roundtrip.json — fixed input/output pair for the placeholder path.

Pitfalls

Skipping the placeholder-feature-gate discipline and letting a stub compute() leak into a non-test build — guard with #[cfg(feature = "placeholder")] and a CI check that the default feature set excludes it. Workspace Cargo.toml dependency-version drift across crates — pin with a workspace-level [workspace.dependencies] table. Forgetting #![forbid(unsafe_code)] (P13) at a new crate root — add a CI grep-gate for it across every src/lib.rs.

⬜ Phase 1 — PBKDF2 (RFC 8018) §13

Objectives

Implement PBKDF2-HMAC-SHA-256 and PBKDF2-HMAC-SHA-512 per RFC 8018 section 5.2; enforce the OWASP 2026 iteration floors (600,000 / 210,000, §4); remove the Phase-0 placeholder.

Deliverable

pbkdf2-impl crate exposing pbkdf2_hmac_sha256/pbkdf2_hmac_sha512 derive functions and their hash()/verify() integration through password-hash-core.

Acceptance

100% pass on RFC 6070 PBKDF2-HMAC-SHA-1-equivalent-adapted vectors re-derived for SHA-256/512 (the project's own KAT, conformance/corpora/rfc6070_pbkdf2/) and 100% pass on the Wycheproof PBKDF2 test set (conformance/corpora/wycheproof_pbkdf2/, ≥ 300 cases). enforce_floor rejects iterations < 600_000 for SHA-256 and < 210_000 for SHA-512 in a dedicated unit test.

Fixtures

rfc6070_pbkdf2/vec-01.json through vec-12.json — input/output pairs, bit-identical match required. wycheproof_pbkdf2/all.json — imported corpus, all cases pass/fail per the corpus's own verdict field. phase1/floor_rejection.json — a below-floor parameter set, expects Error::WeakParameters.

Pitfalls

The i counter in F's definition is 1-indexed (RFC 8018 section 5.2 step 3); an off-by-one produces a wrong derived key that still "looks like" a valid 32-byte string — only the KAT catches it (I8). The per-derivation HMAC cost is 2 × iterations (one HMAC call per U step per iteration, not iterations alone) — under-provisioning benchmark assumptions here silently doubles real latency versus a naive estimate.

⬜ Phase 2 — bcrypt (Eksblowfish) §14

Objectives

Implement Blowfish, the Eksblowfish expensive key schedule (Provos & Mazières 1999), the 64-round OrpheanBeholderScryDoubt final loop, OpenBSD base64 encoding, and the four version dispatch ($2a$/$2b$/$2x$/$2y$).

Deliverable

bcrypt-impl crate producing $2b$<cost>$<22-char-salt><31-char-hash> and parsing all four version prefixes, integrated into hash()/verify().

Acceptance

Bit-identical output to the OpenBSD reference corpus (conformance/corpora/openbsd_bcrypt/, ≥ 1,000 random (password, salt, cost) triples). The CVE-2011-2483 high-bit-character regression fixture set passes (distinguishing $2a$-buggy from $2b$-fixed behavior). enforce_floor rejects cost < 12 (§4). A dudect timing pass (M6-adjacent, tightened fully in Phase 8) shows no gross timing skew across the corpus.

Fixtures

openbsd_bcrypt/corpus-1000.json — triples plus expected hash, bit-identical required. openbsd_bcrypt/cve-2011-2483.json — the documented high-bit-character disagreement cases between $2a$ and $2b$. phase2/version_dispatch.json — one fixture per version byte (a, b, x, y) asserting correct routing. phase2/truncation_73byte.json — a 73-byte password asserting I7's exactly-once warning.

Pitfalls

The OpenBSD base64 alphabet (./0-9A-Za-z) is not standard base64 — decoding a bcrypt salt with a standard-base64 decoder silently produces wrong bytes without erroring. The 64-round final loop is "do not optimize away" — any implementation that shortcuts it produces bcrypt-shaped output no other implementation accepts (a subtle non-interop bug, not a crash). Confusing $2a$ rejection- for-generation with rejection-for-parsing — the library must still parse $2a$ (a decade of production data uses it) while never emitting new ones.

⬜ Phase 3 — scrypt (RFC 7914) §15

Objectives

Implement Salsa20/8, BlockMix, ROMix, and the top-level scrypt construction per RFC 7914; enforce the ln ≥ 17 floor (§4).

Deliverable

scrypt-impl crate producing RFC 7914-conformant output, integrated into hash()/verify() with ln/r/p parameters and PHC-string round trip ($scrypt$ln=17,r=8,p=1$...).

Acceptance

Bit-identical match against the RFC 7914 section 12 KAT (all vectors). 100% pass on the Wycheproof scrypt set if present in the imported corpus, else the RFC vectors alone gate release. enforce_floor rejects ln < 17. Requests requiring > 1 GiB (MAX_SCRYPT_MEMORY default) are rejected with Error::WeakParameters-adjacent Error::ResourceLimit.

Fixtures

rfc7914_scrypt/kat-1.json … kat-4.json — the four RFC 7914 section 12 canonical vectors, bit-identical required. phase3/memory_ceiling.json — an ln value that would require > 1 GiB, expects rejection. phase3/salsa20_8_vs_20.json — a differential fixture proving the 8-round variant is in use (a full-20-round implementation would fail this specific vector).

Pitfalls

Using Salsa20/20 (the common stream-cipher default) instead of Salsa20/8 produces confidently wrong output that still "looks like" a valid hash — only the KAT (§15.5) catches it. r = 8 is conventional but not hardcoded in the type system; a caller passing r = 0 must be rejected before reaching BlockMix (division-by-zero-adjacent malformed-parameter class). Memory allocation for large N can fail — must return Error, never panic (mirrors I4's Argon2 discipline).

⬜ Phase 4 — Argon2 Primitives §16

Objectives

Implement H' (Blake2b-Long), the G compression function (BLAMKA), and the Memory layout (§8.4, §11.7) — the shared substrate all three Argon2 variants build on in Phase 5.

Deliverable

argon2-impl crate exposing h_prime, compress (G), and Memory, each independently unit-tested against RFC 9106 section 5 fixtures before any fill-segment logic (Phase 5) consumes them.

Acceptance

h_prime bit-identical to RFC 9106 section 5 KAT for both ≤64-byte and >64-byte output-length cases (≥ 4 fixtures). compress (G) bit-identical to the reference C implementation (P-H-C/phc-winner-argon2) for 1,000 random 1024-byte input-block pairs. Memory::allocate(65536, 4) produces exactly 65536 * 1024 = 67,108,864 bytes and rejects a request for > 4 GiB (u32 overflow guard) with Error::ResourceLimit.

Fixtures

rfc9106_argon2/h_prime_short.json, h_prime_long.json — the two length regimes. rfc9106_argon2/g_1000_random.json — differential vectors against the reference C implementation. phase4/memory_4gib_overflow.json — the memory-ceiling overflow-guard case.

Pitfalls

H' is not Blake2b — it is Blake2b iterated to produce arbitrary-length output; treating them as interchangeable produces confidently wrong digests that pass a naive smoke test but fail every KAT. The lane/segment partition (§8.4) must round lane_length to a multiple of 4 (segments per lane) before computing per-segment block counts — an unrounded division produces a one-block-short final segment. Memory sizing must reject overflow at the u32 * 1024 multiplication boundary, not silently wrap.

⬜ Phase 5 — Argon2 Fill-Segment & Variants (i / d / id) §17

Objectives

Implement the data-dependent (Argon2d) and data-independent (Argon2i) reference-block index functions, the fill-segment inner procedure, and the Argon2id mode switch; wire the t ≥ 3, m ≥ 19,456 KiB, p = 1 floor (§4).

Deliverable

argon2i/argon2d/argon2id top-level functions in argon2-impl, each producing RFC 9106-conformant tags, integrated into hash()/verify() with the PHC-string round trip (§8.5).

Acceptance

Argon2id bit-identical to RFC 9106 section 5.3 KAT. Argon2i/Argon2d bit-identical to RFC 9106 section 5.1/5.2 KAT. enforce_floor rejects memory_kib < 19_456. Parallel execution at p = 4 is ≥ 3× faster than p = 1 on a 4+ core host (M13, §28). A PARAMS_2026 hash completes within 200 ms single-core (M1).

Fixtures

rfc9106_argon2/argon2id_kat.json, argon2i_kat.json, argon2d_kat.json — the RFC's own vectors, bit-identical required. phase5/mode_switch_boundary.json — a fixture isolating lane 0 segment 0 vs segment 1 to prove the Argon2id mode switch lands exactly where RFC 9106 section 3.4.3 specifies (I9). phase5/parallel_speedup.json — a benchmark fixture recording p=1 vs p=4 wall-clock for the ≥3× acceptance check.

Pitfalls

The "first segment of the first lane" boundary (segment 0, position 0) has a special-case previous-block index — it wraps to the last block of the same lane rather than reading an uninitialized block; implementations that miss this special case read garbage or panic on an out-of-bounds index. Confusing Argon2id's mode-switch granularity (lane 0, segment 0 only — RFC 9106 section 3.4.3) with "the whole first pass uses Argon2i" is a common misreading that silently produces a weaker Argon2id (partial credit against the Argon2d time-memory trade-off defense, not a hard failure — hence why the KAT, not code review alone, is the acceptance gate).

⬜ Phase 6 — PHC Encoding & Legacy Format Parsers §18

Objectives

Implement the PHC-string grammar (§8.1) parser/serializer and the seven legacy-format parsers (bcrypt version family already covered in Phase 2; this phase adds phpass, Django, LDAP {SSHA}/{PBKDF2-SHA256}, and crypt(3) $1$/$5$/$6$ as parse-only, I6-governed inputs).

Deliverable

password-hash-core::encoded module with parse_phc/serialize_phc and a parse_any dispatcher covering all eight recognized prefixes (PHC + bcrypt + 6 legacy), each returning ParsedHash or a typed ParseError.

Acceptance

parse(serialize(x)) == x holds for 100% of PHC strings this library generates (I1, property test, ≥ 10,000 random cases). All seven legacy formats parse correctly on a 10,000-example anonymized corpus (conformance/corpora/legacy_*) with zero false-negatives (a real legacy hash must never be misidentified as malformed). {SSHA} parsing emits exactly one legacy_ssha_parsed_total telemetry increment per call (deprecation-tracking metric, §24).

Fixtures

phc_strings/roundtrip-10000.json — the I1 property-test corpus. legacy_phpass/corpus.json, legacy_django/corpus.json, legacy_ldap/corpus.json — the three named legacy corpora (§10 repo tree). phase6/delimiter_ampersand_malformed.json — the I10 malformed-input fixture (§8.6). phase6/crypt3_identify_only.json — $1$/$5$/$6$ metadata-extraction-only fixtures.

Pitfalls

The PHC parameter delimiter is ,; at least one widely-copied non-conformant implementation uses & — accepting both "to be safe" silently reintroduces ambiguity (I10 exists precisely to forbid this). {SSHA}'s digest-then-salt byte order is easy to reverse by accident (salt-then- digest is a different, incompatible scheme entirely) — a single transposed fixture in 18.5 catches this. Treating $P$ (phpass) and $H$ (an older phpass variant with a different cost-char mapping) as identical formats produces silently wrong cost interpretation.

⬜ Phase 7 — Unified API, Verification & Rehash Upgrade §19

Objectives

Assemble the caller-facing hash()/verify()/verify_with_pepper() surface over all four algorithms and eight parse formats; implement needs_rehash (I14) against the current PARAMS_<year> recommendation; ship the pwhash CLI's hash/verify/identify subcommands.

Deliverable

The password-hash umbrella crate's public surface (hash, verify, verify_with_pepper, Algorithm, Params, PARAMS_2026) and the pwhash binary, both exercised by examples/register.rs, examples/login.rs, examples/upgrade_legacy.rs, examples/identify_format.rs (§10).

Acceptance

End-to-end round trip (hash → store → verify → Authenticated{needs_rehash:false}) passes for all seven generatable algorithm/parameter combinations. A hash generated under a prior year's PARAMS_<year> returns needs_rehash: true (I14 fixture). pwhash identify correctly labels 100% of a 500-example mixed-format corpus (PHC + bcrypt + all six legacy prefixes) without requiring a password argument. CLI cold-start ≤ 50 ms (M14, §28).

Fixtures

phase7/e2e_roundtrip.json — one fixture per generatable algorithm. phase7/needs_rehash_stale_year.json — a hash under a synthetic prior-year params constant. phase7/identify_500_mixed.json — the CLI-identification corpus. phase7/pepper_symmetry.json — hash with pepper, verify with the same pepper (success) and a different pepper (rejection) — I11.

Pitfalls

Computing needs_rehash from a cached parameter comparison instead of the live PARAMS_<year> constant silently stops flagging upgrades once the cache goes stale (I14 exists exactly to forbid this). Applying the pepper before salting versus after is a construction choice that must be fixed and documented once — inconsistency here breaks every existing hash the moment it changes (a de facto breaking change with no version bump to signal it).

⬜ Phase 8 — Constant-Time & Side-Channel Hardening §20

Objectives

Replace the Phase 7 provisional comparison with an audited constant-time core (I2); establish the dudect CI gate (M6); document the Argon2d/id side-channel surface formally.

Deliverable

A hardened verify core passing cargo miri test with zero errors and a dudect CI job producing a recorded t-statistic on every release candidate.

Acceptance

dudect t-statistic ≤ 4.5 across ≥ 1,000,000 timing samples per algorithm (M6). cargo miri test --workspace returns exit code 0. A fault-injection test confirms Password/Pepper buffers are zeroed within one allocator generation after every verify() call, success or failure (no leaked plaintext survives past the call frame).

Fixtures

timing/results/dudect-bcrypt.json, dudect-argon2id.json, dudect-scrypt.json, dudect-pbkdf2.json — one recorded t-statistic per algorithm, checked into timing/ per release (§10 repo tree). phase8/miri_zeroize.json — the fault-injection zeroization proof fixture.

Pitfalls

A compiler optimization can eliminate a "dead" zeroizing write if the compiler proves the buffer is never read again — this is exactly why zeroize's volatile-write primitive (not a plain loop) is mandatory (ADR-16); a hand-rolled zero-loop is not sufficient and must not be substituted for "simplicity." Adding a length short-circuit "just for this one caller" anywhere in the comparison path silently reintroduces the exact leak I2 forbids — this is the single most common regression class post-hardening (tracked as §23 FM-9).

⬜ Phase 9 — Conformance, Fuzzing & Release Hardening §21

Objectives

Assemble the full conformance suite (RFC + Wycheproof + OpenBSD + legacy corpora) into one CI-gated runner; stand up the 24-hour pre-release and 30-day post-tag fuzz canaries; cut the first signed release.

Deliverable

A tagged v1.0.0 release: signed artifact, SBOM, a green 24-hour fuzz canary report, a conformance report covering all fourteen corpora (§10), and a scheduled 30-day canary job.

Acceptance

100% pass across all corpora in conformance/corpora/ (14 named buckets, §10). Zero panics across the 24-hour fuzz canary (M11). cargo deny check returns zero policy violations. Reproducible build verified byte-identical across two independent CI runners. Conformance suite wall-clock ≤ 10 minutes (M10).

Fixtures

conformance/report_schema.json-validated reports for all fourteen corpora (§10 tree: rfc9106_argon2, rfc7914_scrypt, rfc8018_pbkdf2, rfc6070_pbkdf2, openbsd_bcrypt, wycheproof_pbkdf2, phc_strings, legacy_phpass, legacy_django, legacy_ldap, plus the four fuzz-target corpora). audits/fuzz/canary-24h.md — the pre-release canary report.

Pitfalls

A flaky corpus (intermittent failure under load, e.g. a timing-sensitive fixture misfiled into the correctness suite) masks a real regression behind "just re-run it" — correctness fixtures must be fully deterministic; anything timing-sensitive belongs in Phase 8's dudect suite, never here. A fuzz target that only exercises the happy path (valid-looking inputs) because its seed corpus lacks true adversarial examples gives false confidence — seed from the malformed-input fixtures (§8.6, §18.5) explicitly, not only from valid corpora.
