91 — Password Hashing

Project Number: 91

Project Name: Password Hashing

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a memory-safe Rust workspace implementing the four production password-hashing constructions — PBKDF2 (RFC 8018), bcrypt (Provos & Mazières 1999), scrypt (RFC 7914), and Argon2 (RFC 9106, all three modes: Argon2i/d/id) — behind one unified API surface: a PHC-string encoding, a hash()/verify() pair with constant-time comparison, automatic rehash-on-login upgrade signaling, parameter-floor enforcement tied to OWASP/NIST guidance, an optional pepper, and read-only parsers for the seven legacy formats a production user database accumulates over a decade (bcrypt version variants, Django's pbkdf2_sha256$, WordPress phpass, LDAP {SSHA} / {PBKDF2-SHA256}, and crypt(3)'s $1$/$5$/$6$). The system is a library plus a thin CLI, not a service: it has no network listener, no persistence layer of its own, and no user-account model — callers own storage and transport.

1.1 Phase-0 deliverable (numbered)

  1. password-hash-core — algorithm-agnostic types (Algorithm, Params, EncodedHash, ParsedHash, VerifyOutcome, AuthError), salt generation, PHC-string codec, floor enforcement, the constant-time verify core.
  2. pbkdf2-impl — RFC 8018 section 5.2 construction over HMAC-SHA-256/512.
  3. bcrypt-impl — Blowfish, Eksblowfish key schedule, the 64-round OrpheanBeholderScryDoubt loop, OpenBSD base64.
  4. password-hash — the umbrella crate re-exporting the unified hash()/verify() API and PARAMS_2026.
  5. password-hash-cli — the pwhash binary (hash, verify, identify subcommands).
  6. conformance/ — the RFC/Wycheproof/OpenBSD-corpus test runner (Phase 9, stood up skeleton in Phase 0).

1.2 System boundaries

  • Provides: all four KDF constructions; PHC-string serialize/parse; seven legacy-format parsers (parse-only); constant-time verify; rehash-upgrade signaling; parameter-floor enforcement; optional pepper API; a benchmarking/fuzzing/conformance harness.
  • Delegates: password transport (TLS is the caller's job), rate-limiting and account lockout (the application layer's job), credential storage/rotation policy, MFA, session management, CAPTCHA — none of these belong in a KDF library.
  • Does NOT provide: a network service, a user-account schema, a password-strength meter (zxcvbn-style; a sibling project), a key-management system for the pepper (callers supply the pepper from their own secret store), generation (only parsing) of the six deprecated legacy formats.

1.3 Non-goals

MD5-Crypt ($1$), SHA-Crypt ($5$/$6$), DES-Crypt, and phpass are parsed for upgrade detection and never generated. Memory-hard signature schemes, CAPTCHA integration, application-layer rate-limiting, and a full PAKE protocol implementation are out of scope for this system (see Alternative Architectures for why a PAKE is a fundamentally different design, not a parameter tweak).

1.4 Deployment model

A statically or dynamically linked library embedded in an authentication service's process; the CLI (pwhash) is an operator tool for DBA-side hash identification and offline verification during incident response. No daemon mode. No IPC surface. Thread-safety is Send + Sync on all public types; concurrency is the caller's (each hash()/verify() call is independent and allocates its own working memory).

1.5 Target users / operators

Backend engineers building authentication services; SREs performing breach triage (§22); DBAs running the pwhash identify tool against a leaked dump to classify algorithm/parameter exposure; security auditors verifying conformance against RFC 9106 section 5, RFC 7914 section 12, and Wycheproof.

1.6 What later phases unlock

Phase 1–3 (PBKDF2, bcrypt, scrypt) unlock legacy-compatible verification. Phase 4–5 (Argon2 primitives, fill-segment) unlock the new-code default. Phase 6 (PHC + legacy parsers) unlocks cross-format verify() against a decade of accumulated hash formats. Phase 7 (unified API) unlocks the caller-facing surface. Phase 8 (constant-time hardening) unlocks a side-channel-audited release. Phase 9 (conformance/fuzz/release) unlocks the tagged, published crate.

1.7 Language & rationale

Rust 1.78+, edition 2021. Rationale: memory safety without a GC pause (latency-sensitive — §4), a mature audited-crypto ecosystem (subtle, zeroize, blake2, sha2), and no_std capability for the PBKDF2/bcrypt paths (embedded callers, ADR-02). Rejected: C — memory-unsafe by default, the exact defect class (buffer overflows in bespoke KDF glue code) this project exists to avoid; Go — GC pauses are incompatible with constant-time verification guarantees and its crypto stdlib lacks a memory-hard KDF; Python/JavaScript — no realistic path to the allocation control Argon2's memory-hard fill phase needs, and native-extension FFI reintroduces the C-safety problem this project avoids.

1.8 Prerequisites

HMAC and SHA-256/512 internals; the Blowfish Feistel cipher; the salted-hash + work-factor pattern; the timing-attack literature on string comparison; Rust ownership/borrowing. A reader should be able to explain the difference between Argon2i, Argon2d, and Argon2id from RFC 9106 section 3 before starting Phase 4.

2. Why Build This

Password hashing is the cryptographic primitive with the most production exposure and the least production attention. Every user-account database, every "forgot password" flow, every legacy LDAP directory, every /etc/shadow, every CMS, every SSO product hashes passwords, in a smear of languages and vintages: bcrypt in OpenBSD C that everyone vendors verbatim; PBKDF2 reimplemented per-language because RFC 8018 is short enough to get subtly wrong; scrypt in the Tarsnap/Litecoin C lineage; Argon2 in the PHC-winner reference C. Few engineers can explain why bcrypt's $2a$ and $2b$ disagree on high-bit-character passwords (CVE-2011-2483), why 600,000 PBKDF2 iterations is a defensible 2026 floor, why Argon2's memory cost is denominated in KiB and not bytes, or which lines execute when a user logs in. Fewer still can maintain compatibility with the seven legacy formats already sitting in a production database while migrating forward.

This project builds the four algorithms, the seven legacy parsers, the PHC-string codec, the constant-time verifier, the rehash-upgrade flow, the annually-reviewed parameter table, and the RFC/Wycheproof/OpenBSD conformance harness — the complete lifecycle of a password hash from first registration to a breach-response triage session. Sibling systems it calibrates against: the SHA-Hashing project (rank 88, supplies SHA-256/512), an HMAC project (supplies the PBKDF2/ LDAP-PBKDF2 primitive), and any future OPAQUE/PAKE project (§34) that replaces this whole architecture with one where the server never sees a crackable value at all.

What Mastery Looks Like

  • Explain, from memory, why Argon2id's first-pass/first-lane segment uses Argon2i indexing and the rest uses Argon2d, and what attack each half defends against — cemented in Phase 5 (§17).
  • Derive the OWASP parameter floors for all four algorithms from first principles (memory bandwidth, GPU parallelism economics) rather than quoting them — cemented in Phase 1–5 (§13–17) and the Back-of-Envelope Capacity Model (§32).
  • Diagnose, from a $2a$ vs $2b$ version byte alone, whether a stored hash is exposed to CVE-2011-2483 — cemented in Phase 2 (§14).
  • Prove verify() is constant-time with dudect, not by inspection — cemented in Phase 8 (§20).
  • Parse and safely re-hash all seven legacy formats a decade-old user database contains without ever generating one — cemented in Phase 6 (§18).
  • Run a breach-triage session: given a leaked dump's algorithm/parameter distribution, estimate attacker time-to-crack per bucket — cemented in the Threat Model (§22) and Capacity Model (§32).
  • Defend, with rejected-alternative reasoning, why this design is not an OPAQUE/PAKE and when it should be — cemented in Alternative Architectures (§34).

Four boundaries govern every downstream decision. Trust boundary (API → Algorithm layer): plaintext password bytes cross exactly once per call and are zeroized on drop (I14, P14). Concurrency boundary (within Algorithm layer): each hash()/verify() call allocates its own working memory — no shared mutable state, no lock contention (I-driven design, §7). Persistence boundary: the library never touches storage; EncodedHash is an opaque String the caller persists. Protocol boundary: the PHC string is the one wire/storage format this library emits; legacy formats are read-only inputs converted to ParsedHash and, on needs_rehash, re-emitted as PHC. The four algorithm boxes are peers, not a hierarchy — a caller picks one and the library never treats them as interchangeable, because their security properties differ (P1–P4).

6. Design Principles

P1 — Argon2id is the new-code default. Rule: hash() with no explicit algorithm chooses Argon2id. Tradeoff: highest memory footprint of the four (§4). Operational implication: capacity planning must budget RAM, not just CPU (§32 CM1). Violated: callers silently get a weaker algorithm and never learn it.

P2 — bcrypt is the conservative default for legacy/embedded environments. Rule: recommended when memory budget is fixed and small (< 19 MiB per session). Tradeoff: no memory-hardness, so GPU/ASIC parity is worse than Argon2id (§22 T2). Operational implication: cost factor must be re-tuned as hardware improves (P10). Violated: a memory-constrained deployment either OOMs running Argon2id or under-hashes with a stale bcrypt cost.

P3 — scrypt is supported, not recommended, for new code. Rule: available for RFC 7914 interop (e.g. importing a cryptocurrency-style corpus) but never the default. Tradeoff: mature, memory-hard, but less battle-tested against Argon2's PHC-judged cryptanalysis. Operational implication: existing scrypt corpora upgrade to Argon2id via needs_rehash, never regenerate scrypt. Violated: new code silently accumulates a second memory-hard algorithm to maintain forever.

P4 — PBKDF2 is supported only for FIPS-mandated callers. Rule: enforce_floor still applies (600k/210k iterations) but the library documents it as the weakest of the four. Tradeoff: not memory-hard, so GPU cracking is dramatically cheaper per guess (§22 T2, §32). Operational implication: FIPS callers accept a higher offline-crack risk as the cost of validation. Violated: non-FIPS callers use PBKDF2 "because it's simpler" and inherit its weak GPU-resistance.

P5 — Legacy formats are parse-and-upgrade-only. Rule: MD5-Crypt, SHA-Crypt, DES-Crypt, phpass, {SSHA} parse into ParsedHash with needs_rehash = true; the library never emits them. Tradeoff: a decade of legacy code paths to maintain, forever, in read-only form. Operational implication: every legacy format needs its own conformance corpus (§18.5). Violated: silent inability to authenticate existing users during a migration.

P6 — verify() returns (authenticated, needs_rehash). Rule: authentication and parameter-upgrade are two outputs of one call, not two round trips. Tradeoff: callers must handle a compound result type. Operational implication: a single DB write per login covers both authentication and rehash (I14). Violated: a second round trip doubles login-path latency and risks a lost rehash on crash between the two calls.

P7 — Constant-time verification is mandatory. Rule: subtle::ConstantTimeEq over the entire encoded hash, and length comparison is also constant-time (I2). Tradeoff: a few extra cycles per verify — negligible next to KDF cost. Operational implication: dudect runs in CI as a release gate (M6, §20). Violated: a network-observable timing side-channel narrows an attacker's search space call by call.

P8 — Memory cost is denominated in KiB, not bytes. Rule: RFC 9106 section 3.1 defines m in KiB; the library's Argon2Params.memory_kib field name says so explicitly. Tradeoff: none — pure naming discipline. Operational implication: a config value of "64" must mean 64 MiB (65,536 KiB), never 64 bytes. Violated: a units confusion silently produces a catastrophically weak hash (a real, repeatedly-observed footgun in Argon2 wrapper libraries).

P9 — Parameter floors are enforced at the library boundary. Rule: enforce_floor rejects any hash() call below the OWASP 2026 floor with Error::WeakParameters; there is no bypass in the public API. Tradeoff: a caller who "just wants it fast for tests" must use the explicit low-level test-only constructor (ADR-13). Operational implication: weak-parameter regressions are caught at compile-adjacent call time, not discovered post-breach. Violated: I3 breaks and a config typo ships a crackable-in-minutes hash to production.

P10 — Parameters are reviewed annually. Rule: PARAMS_<year> is a versioned constant; PARAMS_2026 is current. Tradeoff: a yearly engineering task with no feature payoff. Operational implication: needs_rehash compares a stored hash's parameters against the current constant, so last year's "current" hashes gradually rehash forward. Violated: parameters ossify against improving attacker hardware (§22 T2–T3).

P11 — Salts are ≥16 bytes, CSPRNG-sourced, never caller-supplied in the high-level API. Rule: Salt::generate(16) via getrandom; the low-level API accepts a caller salt only behind a #[cfg(test)]-gated constructor for KAT reproduction (ADR-13). Tradeoff: no way to derive a "deterministic" hash outside test builds. Operational implication: rainbow-table precomputation against this library's own outputs is infeasible (I5, §22 T12). Violated: predictable or short salts reintroduce precomputation attacks the salt exists to prevent.

P12 — Pepper is a separate, explicit, opt-in API. Rule: verify_with_pepper(pw, pepper, encoded); the pepper is never persisted alongside the hash. Tradeoff: an extra secret-management burden on the caller. Operational implication: pepper rotation requires dual-read support during transition (§23 FM-7); PhaseDeferred("§6") covers an HSM/KMS-backed rotation service. Violated: a pepper baked into the default path becomes an undocumented, unrotatable secret.

P13 — No unsafe in this workspace; SIMD only via vetted upstream crates. Rule: #![forbid(unsafe_code)] at every crate root; SHA/Blake2b/AES acceleration comes from RustCrypto crates that own their own audited unsafe. Tradeoff: a small performance ceiling versus a hand-optimized unsafe core. Operational implication: cargo geiger runs in CI as an ADR-11-style gate. Violated: a memory-safety bug in the one component (a KDF) whose entire purpose is resisting attacker scrutiny.

P14 — Password buffers are zeroized on drop; Debug is disabled on secrets. Rule: the Password newtype wraps Zeroizing<Vec<u8>> and its Debug impl prints a redaction marker, never bytes. Tradeoff: an extra allocation-wrapper type at every call site. Operational implication: a crash dump or log line can never leak a plaintext password (§22 T9). Violated: a stray {:?} in application code becomes a plaintext-password leak into logs.

8. Domain Model

8.1 PHC string grammar (EBNF)

phc-string     = "$" algorithm-id [ "$v=" version ] "$" param-list "$" b64-salt "$" b64-hash ;
algorithm-id   = "argon2id" | "argon2i" | "argon2d" | "scrypt" ;
version        = 1*DIGIT ;                      (* Argon2 only; 19 = v1.3, current *)
param-list     = param *( "," param ) ;
param          = param-name "=" param-value ;
param-name     = "m" | "t" | "p" | "ln" | "r" ;
param-value    = 1*DIGIT ;
b64-salt       = 1*base64-char ;                (* unpadded standard base64 *)
b64-hash       = 1*base64-char ;
base64-char    = ALPHA | DIGIT | "+" | "/" ;

PBKDF2 has no PHC-spec entry; the de-facto Django encoding pbkdf2_sha256$<iters>$<b64salt>$<b64hash> is used for generation, and the Atlassian {PBKDF2-HMAC-SHA256}<iters>:<b64salt>:<b64hash> form is parsed (legacy, §18.3). bcrypt uses its own fixed-field grammar (§8.3).

8.2 verify() state table

State Input Transition Output
Start raw &str dispatch on leading $/{/prefix to Identify —

ParsePhc / ParseBcrypt / ParseLegacy ParsedHash or ParseError success → Recompute; failure → Reject —
Recompute ParsedHash run the matching algorithm over (password, salt, params) recomputed digest
Compare recomputed vs stored digest ct_eq (I2) bool (constant-time)
Authenticated Compare == true compute needs_rehash (I14) VerifyOutcome::Authenticated{needs_rehash}
Rejected (auth) Compare == false — AuthError::WrongPassword

$ 2 b $ 12 $ <22-char-b64-salt><31-char-b64-hash>
│ │ │ │ │  │ └─ 128-bit salt, OpenBSD base64 alphabet (§8.4)
│ │ │ │ │  └─ field boundary is positional, not delimited

│ │ │ └─ field delimiter

│ └─ major version literal "2"

8.4 Argon2 memory layout schema

Memory = lanes × lane_length blocks, block = 1024 bytes
lane_length = memory_kib / (4 * parallelism) * 4     (rounded to a multiple of 4*parallelism)
Each lane partitioned into 4 segments of lane_length/4 blocks.
Block[lane][segment][i] state: { filled: bool, data: [u8; 1024] }
Fill order: pass 0..time_cost, segment 0..4, lane 0..parallelism (segments before lanes: RFC 9106 section 3.4)

8.5 Worked example (Argon2id, PARAMS_2026)

Input: password = b"correcthorsebatterystaple", salt = 16 random bytes, t=3, m=65536, p=4.

Step Operand Result shape
1 H0 = Blake2b(t, m, p, len(P), P, len(S), S, len(K), K, len(X), X) 64-byte seed
2 H'(H0‖0‖lane, 1024) per lane, block 0 1024-byte initial block × lanes
3 H'(H0‖1‖lane, 1024) per lane, block 1 1024-byte initial block × lanes
4 fill_segment × (3 passes × 4 segments × 4 lanes) fully populated Memory
5 XOR last block of each lane 1024-byte final block
6 H'(final_block, 32) 32-byte raw tag
7 PHC-encode $argon2id$v=19$m=65536,t=3,p=4$<b64 salt>$<b64 tag>

8.6 Malformed-input example

Input: $argon2id$v=19$m=65536&t=3,p=4$<salt>$<hash> (uses & instead of ,, violates I10). parse_phc reaches param-list production, fails to match & against the grammar (§8.1), returns ParseError::Malformed { field: "param-list", pos: 24 }. verify() propagates AuthError::Malformed without ever reaching Recompute — no timing signal is leaked because no comparison occurred (distinguish from 8.7, where comparison does occur and must still be constant-time).

8.7 Failure-path example

Argon2id hash() requested with m=1048576 (1 GiB) on a host with 512 MiB free. Memory::allocate receives an allocator failure, returns Err(Error::Alloc) before any password bytes are touched by the fill phase (I4 guards the size, not the failure path itself). The caller sees Error::Alloc, not a panic (P13, §16.9) — the process does not abort, and no partial Memory state persists past the call (no partial write, no partial hash emitted).

13. Phase 1 — PBKDF2 (RFC 8018)

13.1 Objectives

Implement PBKDF2-HMAC-SHA-256 and PBKDF2-HMAC-SHA-512 per RFC 8018 section 5.2; enforce the OWASP 2026 iteration floors (600,000 / 210,000, §4); remove the Phase-0 placeholder.

13.2 Detailed Implementation Steps

Implement the RFC 8018 section 5.2 construction (named, not transcribed as code per the no-code rule): derive T_i = F(P, S, c, i) where F XOR-folds c successive HMAC applications seeded by U_1 = PRF(P, S ‖ INT(i)); concatenate blocks and truncate to dkLen (I8 governs the block-count/truncation arithmetic exactly). Applies P4 (FIPS-only recommendation) and I8 (no off-by-one in block indexing) inline. Wire enforce_floor (ADR-11) for Algorithm::Pbkdf2HmacSha256/Pbkdf2HmacSha512 against the §4 floors. Implement the Django-style PHC-adjacent encoding (pbkdf2_sha256$<iters>$<salt>$<hash>, §8.1) for generation only at this phase (the Atlassian legacy-parse variant lands in Phase 6, §18). Reference Kaliski RFC 8018 and Boneh & Shoup ch. 21 (§5) for the PRF-security argument behind step counts.

13.3 Deliverable

pbkdf2-impl crate exposing pbkdf2_hmac_sha256/pbkdf2_hmac_sha512 derive functions and their hash()/verify() integration through password-hash-core.

13.4 Acceptance Criteria

100% pass on RFC 6070 PBKDF2-HMAC-SHA-1-equivalent-adapted vectors re-derived for SHA-256/512 (the project's own KAT, conformance/corpora/rfc6070_pbkdf2/) and 100% pass on the Wycheproof PBKDF2 test set (conformance/corpora/wycheproof_pbkdf2/, ≥ 300 cases). enforce_floor rejects iterations < 600_000 for SHA-256 and < 210_000 for SHA-512 in a dedicated unit test.

13.5 Conformance Fixtures

rfc6070_pbkdf2/vec-01.json through vec-12.json — input/output pairs, bit-identical match required. wycheproof_pbkdf2/all.json — imported corpus, all cases pass/fail per the corpus's own verdict field. phase1/floor_rejection.json — a below-floor parameter set, expects Error::WeakParameters.

13.6 Pitfalls

The i counter in F's definition is 1-indexed (RFC 8018 section 5.2 step 3); an off-by-one produces a wrong derived key that still "looks like" a valid 32-byte string — only the KAT catches it (I8). The per-derivation HMAC cost is 2 × iterations (one HMAC call per U step per iteration, not iterations alone) — under-provisioning benchmark assumptions here silently doubles real latency versus a naive estimate.

13.7 Performance Concerns

HMAC-SHA-256 throughput is host-SHA-NI-dependent; M5 (§28) targets ≤ 100 ms at 600,000 iterations on a SHA-NI host — a non-SHA-NI host (older ARM without crypto extensions) can be 3–5× slower and must be called out in deployment docs (§24). No memory-hardness means no cache-locality concern beyond a single 32/64-byte working state.

13.8 Edge Cases

Zero-length password (valid per RFC 8018, must not panic). dkLen not a multiple of hLen (I8's truncation path — last block partially used). Iteration count of exactly the floor value (boundary inclusive, not exclusive — >= 600_000 passes).

13.9 Failure Analysis

A WeakParameters rejection at hash() time is the only failure mode this phase introduces (I3/I13); it surfaces as Error::WeakParameters to the caller with no partial state. There is no allocation-failure path (PBKDF2 is no_std, fixed small working buffers only).

13.10 Operational Notes

Metric: pbkdf2_hash_total{algorithm} and pbkdf2_hash_seconds histogram. No migration concerns yet (Phase 6 adds the legacy Django/LDAP parse paths). Document the SHA-NI-host latency caveat in docs/performance/.

14. Phase 2 — bcrypt (Eksblowfish)

14.1 Objectives

Implement Blowfish, the Eksblowfish expensive key schedule (Provos & Mazières 1999), the 64-round OrpheanBeholderScryDoubt final loop, OpenBSD base64 encoding, and the four version dispatch ($2a$/$2b$/$2x$/$2y$).

14.2 Detailed Implementation Steps

Implement Blowfish's 16-round Feistel network with the standard P-array/S-box key schedule (named per Schneier 1993, §5). Implement Eksblowfish: instead of one key schedule, run 2^cost + 1 schedules interleaving password and salt bytes — this is bcrypt's work-factor mechanism (Provos & Mazières 1999, §5, applies P2). Implement the 64-iteration OrpheanBeholderScryDoubt final loop over three 64-bit blocks (§8.3 layout); output truncates to 23 of 24 bytes (the OpenBSD historical quirk, documented not "fixed" — fixing it would break interop, ADR-04). Implement OpenBSD's unique base64 alphabet (§8.4-adjacent; distinct from both standard and URL-safe base64). Implement version dispatch per ADR-18/ADR-19: $2b$ is generated; $2a$ is rejected for generation (CVE-2011-2483, §22 T-adjacent) but parseable; $2y$ treated as $2b$-equivalent; $2x$ parse-only with a mandatory warning. Enforce I7 (72-byte truncation boundary, exactly, with a single warning emission).

14.3 Deliverable

bcrypt-impl crate producing $2b$<cost>$<22-char-salt><31-char-hash> and parsing all four version prefixes, integrated into hash()/verify().

14.4 Acceptance Criteria

Bit-identical output to the OpenBSD reference corpus (conformance/corpora/openbsd_bcrypt/, ≥ 1,000 random (password, salt, cost) triples). The CVE-2011-2483 high-bit-character regression fixture set passes (distinguishing $2a$-buggy from $2b$-fixed behavior). enforce_floor rejects cost < 12 (§4). A dudect timing pass (M6-adjacent, tightened fully in Phase 8) shows no gross timing skew across the corpus.

14.5 Conformance Fixtures

openbsd_bcrypt/corpus-1000.json — triples plus expected hash, bit-identical required. openbsd_bcrypt/cve-2011-2483.json — the documented high-bit-character disagreement cases between $2a$ and $2b$. phase2/version_dispatch.json — one fixture per version byte (a, b, x, y) asserting correct routing. phase2/truncation_73byte.json — a 73-byte password asserting I7's exactly-once warning.

14.6 Pitfalls

The OpenBSD base64 alphabet (./0-9A-Za-z) is not standard base64 — decoding a bcrypt salt with a standard-base64 decoder silently produces wrong bytes without erroring. The 64-round final loop is "do not optimize away" — any implementation that shortcuts it produces bcrypt-shaped output no other implementation accepts (a subtle non-interop bug, not a crash). Confusing $2a$ rejection- for-generation with rejection-for-parsing — the library must still parse $2a$ (a decade of production data uses it) while never emitting new ones.

14.7 Performance Concerns

Eksblowfish's 2^cost + 1 schedule count makes cost the sole latency lever (M3: cost=12 ≤ 250 ms, §28); cost is exponential, so cost=13 roughly doubles latency — capacity planning must account for this non-linearity (§32 CM3). No memory-hardness — GPU parallelism is the primary attacker lever here (§22 T2).

14.8 Edge Cases

Cost at the exact floor (12) and exact ceiling (31, u8 field-width limit — RFC/spec-defined, not arbitrary). A password containing high-bit (>0x7F) characters against $2a$ (CVE-2011-2483 trigger). Salt with non-alphabet characters (malformed input, must reject during parse, not during key schedule).

14.9 Failure Analysis

An unrecognized version byte (e.g. legacy unversioned $2$) is a parse failure (AuthError::Malformed), not a panic — the historical $2$ format predates versioning and is explicitly rejected (§14.2). A cost value outside 4..=31 is a construction-time rejection via enforce_floor/type constraints, never reaching the key schedule.

14.10 Operational Notes

Metric: bcrypt_hash_seconds{cost} histogram (cost as a label enables per-cost latency dashboards, §24). Telemetry emits bcrypt_high_bit_warning_total whenever a $2a$-path high-bit password is parsed, flagging CVE-2011-2483-exposed rows for a migration runbook (docs/runbooks/triage.md).

15. Phase 3 — scrypt (RFC 7914)

15.1 Objectives

Implement Salsa20/8, BlockMix, ROMix, and the top-level scrypt construction per RFC 7914; enforce the ln ≥ 17 floor (§4).

15.2 Detailed Implementation Steps

Implement Salsa20 reduced to 8 rounds (4 double-rounds) — the intentional reduced-round variant Bernstein 2008 describes; scrypt never uses full Salsa20/20 (Percival 2009, §5, applies P3). Implement BlockMix operating over 2r 64-byte blocks by repeated Salsa20/8 application. Implement ROMix: allocate N = 2^ln blocks of 128r bytes, fill sequentially via BlockMix, then read back in a data-dependent pseudorandom pattern (I4-adjacent memory-sizing discipline mirrors Argon2's, applied here as mem_required = N * 128 * r, rejected above MAX_SCRYPT_MEMORY per ADR-11-style floor enforcement). Implement the top-level construction: one PBKDF2-HMAC-SHA-256 pass (single iteration) to derive the initial p * 128 * r-byte buffer, ROMix each 128r-byte chunk, then a final single-iteration PBKDF2 pass keyed by the ROMixed buffer as salt (RFC 7914 section 6, applies P3, I4-style memory-bound check).

15.3 Deliverable

scrypt-impl crate producing RFC 7914-conformant output, integrated into hash()/verify() with ln/r/p parameters and PHC-string round trip ($scrypt$ln=17,r=8,p=1$...).

15.4 Acceptance Criteria

Bit-identical match against the RFC 7914 section 12 KAT (all vectors). 100% pass on the Wycheproof scrypt set if present in the imported corpus, else the RFC vectors alone gate release. enforce_floor rejects ln < 17. Requests requiring > 1 GiB (MAX_SCRYPT_MEMORY default) are rejected with Error::WeakParameters-adjacent Error::ResourceLimit.

15.5 Conformance Fixtures

rfc7914_scrypt/kat-1.json … kat-4.json — the four RFC 7914 section 12 canonical vectors, bit-identical required. phase3/memory_ceiling.json — an ln value that would require > 1 GiB, expects rejection. phase3/salsa20_8_vs_20.json — a differential fixture proving the 8-round variant is in use (a full-20-round implementation would fail this specific vector).

15.6 Pitfalls

Using Salsa20/20 (the common stream-cipher default) instead of Salsa20/8 produces confidently wrong output that still "looks like" a valid hash — only the KAT (§15.5) catches it. r = 8 is conventional but not hardcoded in the type system; a caller passing r = 0 must be rejected before reaching BlockMix (division-by-zero-adjacent malformed-parameter class). Memory allocation for large N can fail — must return Error, never panic (mirrors I4's Argon2 discipline).

15.7 Performance Concerns

ROMix's read-back phase is memory-bandwidth-bound, not compute-bound — this is scrypt's whole security argument (Percival 2009, §5) and directly informs §32 CM7's bandw2idth-demand derivation (shared reasoning with Argon2's fill phase). M4 (§28): ln=17,r=8,p=1 ≤ 200 ms single hash.

15.8 Edge Cases

p > 1 (multiple independent ROMix chunks) — must parallelize correctly without cross-chunk state leakage. ln at the exact floor (17) and at a value producing exactly MAX_SCRYPT_MEMORY (boundary-inclusive test). A truncated $scrypt$ PHC string missing the p parameter — a Phase 6 concern but the scrypt construction itself must reject p = 0 defensively at this phase too.

15.9 Failure Analysis

A memory-ceiling rejection (Error::ResourceLimit) occurs before any BlockMix/ROMix work begins — no partial allocation persists. An allocator failure mid-ROMix (rare, since the ceiling check should have already rejected an oversized request) is caught and returned as Error::Alloc, never a panic (mirrors I4/Argon2's discipline exactly — deliberate consistency, §16.9).

15.10 Operational Notes

Metric: scrypt_hash_seconds{ln,r,p}. Document the memory-ceiling default and its override mechanism in docs/performance/scrypt-memory.md (cross-referenced from the Argon2 memory doc, not duplicated — avoids terminology drift across the Repository Layout, §10).

16. Phase 4 — Argon2 Primitives

16.1 Objectives

Implement H' (Blake2b-Long), the G compression function (BLAMKA), and the Memory layout (§8.4, §11.7) — the shared substrate all three Argon2 variants build on in Phase 5.

16.2 Detailed Implementation Steps

Implement H' per RFC 9106 section 3.3: if the requested output length ≤ 64 bytes, one Blake2b call suffices; otherwise iterate Blake2b, keeping the first 32 bytes of each 64-byte digest and reseeding with the full previous digest, until the remaining length ≤ 64 bytes, then take a final variable-length Blake2b call (Aumasson et al. 2013 BLAKE, §5, applies ADR-16's audited-primitive principle). Implement G, the BLAMKA compression function operating on two 1024-byte input blocks via Blake2b's round function applied column-wise then diagonal-wise (RFC 9106 section 3.6, applies I4). Implement Memory::allocate (§11.7) sized exactly memory_kib * 1024 bytes, partitioned into parallelism lanes × 4 segments (I4, P8's KiB-not-bytes discipline enforced at this exact boundary). Implement the initial-block derivation: H0 from Blake2b(t, m, p, |P|, P, |S|, S, |K|, K, |X|, X), then block 0/1 of each lane from H'(H0 ‖ 0 ‖ lane, 1024) / H'(H0 ‖ 1 ‖ lane, 1024) (§8.5 worked example steps 1–3).

16.3 Deliverable

argon2-impl crate exposing h_prime, compress (G), and Memory, each independently unit-tested against RFC 9106 section 5 fixtures before any fill-segment logic (Phase 5) consumes them.

16.4 Acceptance Criteria

h_prime bit-identical to RFC 9106 section 5 KAT for both ≤64-byte and >64-byte output-length cases (≥ 4 fixtures). compress (G) bit-identical to the reference C implementation (P-H-C/phc-winner-argon2) for 1,000 random 1024-byte input-block pairs. Memory::allocate(65536, 4) produces exactly 65536 * 1024 = 67,108,864 bytes and rejects a request for > 4 GiB (u32 overflow guard) with Error::ResourceLimit.

16.5 Conformance Fixtures

rfc9106_argon2/h_prime_short.json, h_prime_long.json — the two length regimes. rfc9106_argon2/g_1000_random.json — differential vectors against the reference C implementation. phase4/memory_4gib_overflow.json — the memory-ceiling overflow-guard case.

16.6 Pitfalls

H' is not Blake2b — it is Blake2b iterated to produce arbitrary-length output; treating them as interchangeable produces confidently wrong digests that pass a naive smoke test but fail every KAT. The lane/segment partition (§8.4) must round lane_length to a multiple of 4 (segments per lane) before computing per-segment block counts — an unrounded division produces a one-block-short final segment. Memory sizing must reject overflow at the u32 * 1024 multiplication boundary, not silently wrap.

16.7 Performance Concerns

H''s iterated-Blake2b construction for large output lengths (rare in this system — outputs are typically 32 bytes) is O(1) in practice; the dominant cost this phase introduces is Memory::allocate's single large allocation, which should be a single Vec/Box allocation, not per-block allocation (avoids allocator pressure — informs §32 CM7's bandwidth model).

16.8 Edge Cases

Output length exactly 64 bytes (the H' branch boundary — must not double-hash). memory_kib exactly at the 4 GiB u32 boundary (overflow-adjacent). parallelism that does not evenly divide into a valid lane count (must round up per RFC 9106 section 3.2, never truncate silently).

16.9 Failure Analysis

An allocation failure in Memory::allocate returns Error::Alloc before any block is written — no partial Memory is observable by the caller (mirrors §8.7's failure-path example exactly, establishing the pattern Phase 5's fill_segment also follows).

16.10 Operational Notes

No caller-facing metrics yet (these are internal primitives); Phase 5 emits the user-visible argon2_hash_seconds metric once the full construction exists. Document the memory-layout invariant (I4) in docs/architecture/argon2-memory.md so operators sizing container memory limits have one authoritative reference.

17. Phase 5 — Argon2 Fill-Segment & Variants (i / d / id)

17.1 Objectives

Implement the data-dependent (Argon2d) and data-independent (Argon2i) reference-block index functions, the fill-segment inner procedure, and the Argon2id mode switch; wire the t ≥ 3, m ≥ 19,456 KiB, p = 1 floor (§4).

17.2 Detailed Implementation Steps

Implement the Argon2d index function: the reference block is selected from J1 ‖ J2, the first 8 bytes of the previous block, mapped onto the valid reference range via RFC 9106 section 3.4's phi-mapping (data-dependent — resists time-memory trade-off attacks per Biryukov et al. 2016, §5, applies P1). Implement the Argon2i index function: J1 ‖ J2 derived from a counter-and-constant-seeded pseudorandom block, independent of any password-derived data (data-independent — resists cache-timing side-channels, applies P1, cited real-incident class: side-channel cache-timing attacks against data-dependent memory access are a documented general attack class, e.g. against RSA/AES table-lookup implementations — Argon2i's existence is a direct response). Implement Argon2id's mode switch (I9): the first pass's first-lane segment 0 uses Argon2i indexing; every other lane/segment/pass uses Argon2d (RFC 9106 section 3.4.3 exactly — a commonly misread boundary). Implement fill_segment: for each block position in a segment, resolve the reference block via the mode-appropriate index function, apply G (§16.2) to the previous block and the reference block, and write the result (segments-before-lanes fill order, §8.4). Wire enforce_floor for all three variants against §4's t ≥ 3, m ≥ 19,456 floor.

17.3 Deliverable

argon2i/argon2d/argon2id top-level functions in argon2-impl, each producing RFC 9106-conformant tags, integrated into hash()/verify() with the PHC-string round trip (§8.5).

17.4 Acceptance Criteria

Argon2id bit-identical to RFC 9106 section 5.3 KAT. Argon2i/Argon2d bit-identical to RFC 9106 section 5.1/5.2 KAT. enforce_floor rejects memory_kib < 19_456. Parallel execution at p = 4 is ≥ 3× faster than p = 1 on a 4+ core host (M13, §28). A PARAMS_2026 hash completes within 200 ms single-core (M1).

17.5 Conformance Fixtures

rfc9106_argon2/argon2id_kat.json, argon2i_kat.json, argon2d_kat.json — the RFC's own vectors, bit-identical required. phase5/mode_switch_boundary.json — a fixture isolating lane 0 segment 0 vs segment 1 to prove the Argon2id mode switch lands exactly where RFC 9106 section 3.4.3 specifies (I9). phase5/parallel_speedup.json — a benchmark fixture recording p=1 vs p=4 wall-clock for the ≥3× acceptance check.

17.6 Pitfalls

The "first segment of the first lane" boundary (segment 0, position 0) has a special-case previous-block index — it wraps to the last block of the same lane rather than reading an uninitialized block; implementations that miss this special case read garbage or panic on an out-of-bounds index. Confusing Argon2id's mode-switch granularity (lane 0, segment 0 only — RFC 9106 section 3.4.3) with "the whole first pass uses Argon2i" is a common misreading that silently produces a weaker Argon2id (partial credit against the Argon2d time-memory trade-off defense, not a hard failure — hence why the KAT, not code review alone, is the acceptance gate).

17.7 Performance Concerns

fill_segment's inner loop is the system's single hottest path; cache locality of the 1024-byte-block memory array dominates (large m means the working set exceeds L2/L3 cache, turning this into a memory-bandwidth-bound operation — same physical argument as scrypt's ROMix, §15.7, feeding §32 CM7). Parallelism across lanes (via Rayon, ADR-21) must not introduce false sharing across cache lines at lane boundaries.

17.8 Edge Cases

parallelism = 1 (Argon2id degenerates to a single-lane construction — the mode switch still applies to segment 0 of that one lane). time_cost at exactly the floor (3). A memory size that rounds lane_length down to fewer than 8 blocks per lane (degenerate small-memory misuse; must be caught by enforce_floor before reaching fill_segment, not discovered as an array-bounds panic).

17.9 Failure Analysis

An allocation failure surfaces from Phase 4's Memory::allocate before fill_segment ever runs (§16.9) — this phase adds no new allocation failure mode. A logic error in the mode-switch boundary (§17.6) is a silent correctness failure, not a crash — detected only by the KAT, which is why 17.4's bit-identical requirement (not "produces a hash") is the acceptance bar.

17.10 Operational Notes

Metric: argon2_hash_seconds{variant,memory_kib,time_cost,parallelism} and argon2_alloc_bytes (I4-tied gauge). Document the mode-switch invariant (I9) and the segment-0 special case (§17.6) in docs/architecture/argon2-memory.md alongside Phase 4's layout notes — one file, not split, per the naming discipline of §10 and §11.

18. Phase 6 — PHC Encoding & Legacy Format Parsers

18.1 Objectives

Implement the PHC-string grammar (§8.1) parser/serializer and the seven legacy-format parsers (bcrypt version family already covered in Phase 2; this phase adds phpass, Django, LDAP {SSHA}/{PBKDF2-SHA256}, and crypt(3) $1$/$5$/$6$ as parse-only, I6-governed inputs).

18.2 Detailed Implementation Steps

Implement parse_phc per the §8.1 EBNF: split on $, dispatch algorithm-id to Algorithm, parse param-list enforcing the ,-delimiter (I10), base64-decode salt/hash fields. Implement serialize_phc as parse_phc's exact inverse (I1 round-trip). Implement the phpass parser: $P$<cost-char><8-char-salt><22-char-hash> or $H$-prefixed (WordPress/phpBB convention, applies §5 Reference Implementations lesson 4 on API-shape-only borrowing). Implement the Django parser: pbkdf2_sha256$<iterations>$<b64-salt>$<b64-hash> (generation path landed in Phase 1, §13.2; this phase adds acceptance of third-party-generated Django hashes with potentially different iteration counts). Implement the LDAP parsers: {SSHA}<b64(sha1-digest ‖ salt)> (salted SHA-1, legacy, flagged with a loud deprecation warning — SHA-1 is not memory-hard and is a broken general-purpose hash) and {PBKDF2-SHA256}<iters>:<b64-salt>:<b64-hash> (Atlassian-style colon delimiter, distinct from Django's $). Implement crypt(3) prefix recognition for $1$ (MD5-Crypt), $5$/$6$ (SHA-256/512-Crypt) sufficient to identify the algorithm and salt for needs_rehash purposes — full parsing of the SHA-Crypt inner rounds is scoped only as far as extracting metadata for triage (P5: parse-and-upgrade-only, no verification-quality implementation of a deprecated scheme is a goal here). Every legacy parser sets ParsedHash.legacy = true, forcing I6.

18.3 Deliverable

password-hash-core::encoded module with parse_phc/serialize_phc and a parse_any dispatcher covering all eight recognized prefixes (PHC + bcrypt + 6 legacy), each returning ParsedHash or a typed ParseError.

18.4 Acceptance Criteria

parse(serialize(x)) == x holds for 100% of PHC strings this library generates (I1, property test, ≥ 10,000 random cases). All seven legacy formats parse correctly on a 10,000-example anonymized corpus (conformance/corpora/legacy_*) with zero false-negatives (a real legacy hash must never be misidentified as malformed). {SSHA} parsing emits exactly one legacy_ssha_parsed_total telemetry increment per call (deprecation-tracking metric, §24).

18.5 Conformance Fixtures

phc_strings/roundtrip-10000.json — the I1 property-test corpus. legacy_phpass/corpus.json, legacy_django/corpus.json, legacy_ldap/corpus.json — the three named legacy corpora (§10 repo tree). phase6/delimiter_ampersand_malformed.json — the I10 malformed-input fixture (§8.6). phase6/crypt3_identify_only.json — $1$/$5$/$6$ metadata-extraction-only fixtures.

18.6 Pitfalls

The PHC parameter delimiter is ,; at least one widely-copied non-conformant implementation uses & — accepting both "to be safe" silently reintroduces ambiguity (I10 exists precisely to forbid this). {SSHA}'s digest-then-salt byte order is easy to reverse by accident (salt-then- digest is a different, incompatible scheme entirely) — a single transposed fixture in 18.5 catches this. Treating $P$ (phpass) and $H$ (an older phpass variant with a different cost-char mapping) as identical formats produces silently wrong cost interpretation.

18.7 Performance Concerns

Parsing is not the system's bottleneck (M7/M8, §28: ≤ 1 µs per string) but a poorly bounded parser (e.g. unbounded split('$') allocation on an adversarially long malformed string) is a DoS surface (§22 T10) — bound input length before allocating.

18.8 Edge Cases

A PHC string with a version parameter present for scrypt (invalid — only Argon2 carries v=) must reject, not silently ignore the extra field. An empty param-list (zero parameters) for an algorithm that requires at least one. A legacy {SSHA} value with a salt of length zero (valid per the scheme, degenerate security, still must parse without panicking — flagged via telemetry, not rejected).

18.9 Failure Analysis

Every parser failure returns a typed ParseError (never a panic — this is the fuzz-target surface of Phase 9, §21) with a field/pos pair for debuggability (§8.6's malformed-input example is the canonical failure shape). A malformed input never reaches Recompute (§8.2 state table) so no timing signal is leaked by a parse failure — parse-time and comparison-time are two disjoint attack surfaces (T4 covers the latter, T10 the former).

18.10 Operational Notes

Metrics: phc_parse_errors_total{reason}, legacy_parse_total{format} (one label value per format — feeds the breach-triage runbook's format-distribution query, docs/runbooks/triage.md). Migration note: a caller running this phase's parsers against a live legacy database should expect needs_rehash = true on every legacy row (I6) — this is the intended signal, not a bug to suppress.

19. Phase 7 — Unified API, Verification & Rehash Upgrade

19.1 Objectives

Assemble the caller-facing hash()/verify()/verify_with_pepper() surface over all four algorithms and eight parse formats; implement needs_rehash (I14) against the current PARAMS_<year> recommendation; ship the pwhash CLI's hash/verify/identify subcommands.

19.2 Detailed Implementation Steps

Implement hash(password, algorithm, params): call enforce_floor (I3, ADR-11), generate a salt (Salt::generate(16), I5, ADR-13), dispatch to the matching algorithm's compute, serialize via serialize_phc/bcrypt-encode (§18.2). Implement verify(password, encoded): dispatch through parse_any (§18.2, §8.2 state table), recompute, compare via I2's constant-time core (fully hardened in Phase 8, §20 — this phase wires the call path, not yet the timing guarantee), compute needs_rehash by comparing ParsedHash.params/legacy against PARAMS_<year> (I14; a legacy = true hash is unconditionally needs_rehash = true per I6). Implement verify_with_pepper: apply the pepper identically on the recompute path (I11's symmetry invariant — applies P12). 19.3 Deliverable

The password-hash umbrella crate's public surface (hash, verify, verify_with_pepper, Algorithm, Params, PARAMS_2026) and the pwhash binary, both exercised by examples/register.rs, examples/login.rs, examples/upgrade_legacy.rs, examples/identify_format.rs (§10).

19.4 Acceptance Criteria

End-to-end round trip (hash → store → verify → Authenticated{needs_rehash:false}) passes for all seven generatable algorithm/parameter combinations. A hash generated under a prior year's PARAMS_<year> returns needs_rehash: true (I14 fixture). pwhash identify correctly labels 100% of a 500-example mixed-format corpus (PHC + bcrypt + all six legacy prefixes) without requiring a password argument. CLI cold-start ≤ 50 ms (M14, §28).

19.5 Conformance Fixtures

phase7/e2e_roundtrip.json — one fixture per generatable algorithm. phase7/needs_rehash_stale_year.json — a hash under a synthetic prior-year params constant. phase7/identify_500_mixed.json — the CLI-identification corpus. phase7/pepper_symmetry.json — hash with pepper, verify with the same pepper (success) and a different pepper (rejection) — I11.

19.6 Pitfalls

Computing needs_rehash from a cached parameter comparison instead of the live PARAMS_<year> constant silently stops flagging upgrades once the cache goes stale (I14 exists exactly to forbid this). Applying the pepper before salting versus after is a construction choice that must be fixed and documented once — inconsistency here breaks every existing hash the moment it changes (a de facto breaking change with no version bump to signal it).

19.7 Performance Concerns

The unified API's dispatch overhead (match on Algorithm) is negligible next to any of the four KDF costs — no measurable concern here. The CLI's cold-start budget (M14) is dominated by process exec + dynamic linking, not library logic; a statically linked release build minimizes this.

19.8 Edge Cases

verify() against an encoded string this library cannot identify at all (no prefix matches any of the eight known formats) — must return a distinct AuthError::Malformed, never silently treated as WrongPassword (conflating "can't parse" with "wrong password" hides operational bugs behind an auth-failure metric). A pepper of zero length (degenerate but must not panic — treated as an empty pepper, effectively a no-op, with a warning).

19.9 Failure Analysis

Any Recompute-phase failure (e.g. an internal KDF resource error, §15.9/§16.9/§17.9) propagates as AuthError::Alloc/ResourceLimit up through verify() unchanged — the unified API adds no new failure mode, only a single dispatch point (§3's trust-boundary diagram). A needs_rehash miss (§19.6) has no immediate symptom — its blast radius is silent parameter staleness across an entire user base, detected only by an operational metric (needs_rehash_total trend, I14, §24).

19.10 Operational Notes

Metrics: hash_calls_total{algorithm}, verify_calls_total{result}, needs_rehash_total (I14-tied). The pwhash identify output format is stable API for tooling (§25 compatibility concern) — changing its output shape is a SemVer-relevant change. Rollback: reverting this phase's crate version does not affect already-stored hashes (PHC/legacy encodings are self-describing, §8.1–8.3).

20. Phase 8 — Constant-Time & Side-Channel Hardening

20.1 Objectives

Replace the Phase 7 provisional comparison with an audited constant-time core (I2); establish the dudect CI gate (M6); document the Argon2d/id side-channel surface formally.

20.2 Detailed Implementation Steps

Wire subtle::ConstantTimeEq (ADR-10) over the entire encoded hash comparison, including the length check — a naive if a.len() != b.len() { return false } short-circuit leaks length via timing before any byte compares, so length must be folded into the constant-time path itself (a fixed-length intermediate buffer, zero-padded to the longer of the two, is compared in full regardless of the real lengths — applies I2, P7). Instrument dudect (a black-box statistical timing-leak detector) against verify() across a wrong-password/right-password input distribution; gate CI on t-statistic ≤ 4.5 (M6). Document the Argon2d/Argon2id data-dependent-indexing side-channel surface explicitly in the Threat Model (§22 T6) — this is an acknowledged, structural property of Argon2d, not a bug; Argon2id's first-pass mitigation (I9, Phase 5) is the documented defense, not a claim of zero side-channel surface. Zeroize the Password/Pepper buffers on every code path, including early-return error paths (P14) — verified via cargo miri (detects use-after-zeroize and uninitialized-read classes).

20.3 Deliverable

A hardened verify core passing cargo miri test with zero errors and a dudect CI job producing a recorded t-statistic on every release candidate.

20.4 Acceptance Criteria

dudect t-statistic ≤ 4.5 across ≥ 1,000,000 timing samples per algorithm (M6). cargo miri test --workspace returns exit code 0. A fault-injection test confirms Password/Pepper buffers are zeroed within one allocator generation after every verify() call, success or failure (no leaked plaintext survives past the call frame).

20.5 Conformance Fixtures

timing/results/dudect-bcrypt.json, dudect-argon2id.json, dudect-scrypt.json, dudect-pbkdf2.json — one recorded t-statistic per algorithm, checked into timing/ per release (§10 repo tree). phase8/miri_zeroize.json — the fault-injection zeroization proof fixture.

20.6 Pitfalls

A compiler optimization can eliminate a "dead" zeroizing write if the compiler proves the buffer is never read again — this is exactly why zeroize's volatile-write primitive (not a plain loop) is mandatory (ADR-16); a hand-rolled zero-loop is not sufficient and must not be substituted for "simplicity." Adding a length short-circuit "just for this one caller" anywhere in the comparison path silently reintroduces the exact leak I2 forbids — this is the single most common regression class post-hardening (tracked as §23 FM-9).

20.7 Performance Concerns

Constant-time comparison over a fixed-length padded buffer costs a few dozen extra cycles versus a short-circuiting compare — immeasurable next to any KDF's millisecond-scale cost (M6 has no throughput tradeoff, only a correctness one). dudect's own sampling overhead is a CI-time cost only, not a runtime one.

20.8 Edge Cases

Two encoded hashes of identical length but from different algorithms (must still compare constant-time within the shared fixed-length buffer, never branch on algorithm identity during the comparison step itself — algorithm dispatch happens before Recompute, §8.2, never interleaved with the comparison). A verify() call that hits a parse error (§18.9) — this path is not comparison-timing-sensitive (no secret-dependent computation occurred) but must still not leak which field failed via a distinguishable error-path timing signature to an external observer performing high-precision network timing.

20.9 Failure Analysis

A dudect CI failure (t-stat > 4.5) blocks release (RTO < 1 release cycle, §4) — the fix is always in the comparison path, never a suppression of the test. A miri failure indicating a use-after-zeroize is treated as a security-severity defect (§22), not a routine bug.

20.10 Operational Notes

Metric: dudect_t_stat{algorithm} recorded per release, trended over time in docs/performance/ to catch a slow regression before it crosses the gate. No migration concerns — this phase changes internal comparison mechanics only, not any stored format.

21. Phase 9 — Conformance, Fuzzing & Release Hardening

21.1 Objectives

Assemble the full conformance suite (RFC + Wycheproof + OpenBSD + legacy corpora) into one CI-gated runner; stand up the 24-hour pre-release and 30-day post-tag fuzz canaries; cut the first signed release.

21.2 Detailed Implementation Steps

Implement conformance/runner (§10) to execute every corpus in conformance/corpora/ and emit a report_schema.json-conformant result, one row per I# invariant exercised (§7's debugging methodology). Wire cargo-fuzz targets (parse_phc, parse_bcrypt, parse_legacy, argon2_round_trip, §10) seeded from fuzz/corpus/ (derived from the conformance corpora — reuse, not duplicate). Run the 24-hour canary (M11) as a pre-release CI gate; schedule the 30-day canary (M12) as a post-tag background job. Implement reproducible-build verification (ADR-15/§27): cargo build --locked --release produces byte-identical output across two clean checkouts. Generate an SBOM (cargo cyclonedx or equivalent) and sign the release artifact (§27). Run cargo deny check (deny.toml, §10) against license and advisory policy (ADR-15).

21.3 Deliverable

A tagged v1.0.0 release: signed artifact, SBOM, a green 24-hour fuzz canary report, a conformance report covering all fourteen corpora (§10), and a scheduled 30-day canary job.

21.4 Acceptance Criteria

100% pass across all corpora in conformance/corpora/ (14 named buckets, §10). Zero panics across the 24-hour fuzz canary (M11). cargo deny check returns zero policy violations. Reproducible build verified byte-identical across two independent CI runners. Conformance suite wall-clock ≤ 10 minutes (M10).

21.5 Conformance Fixtures

conformance/report_schema.json-validated reports for all fourteen corpora (§10 tree: rfc9106_argon2, rfc7914_scrypt, rfc8018_pbkdf2, rfc6070_pbkdf2, openbsd_bcrypt, wycheproof_pbkdf2, phc_strings, legacy_phpass, legacy_django, legacy_ldap, plus the four fuzz-target corpora). audits/fuzz/canary-24h.md — the pre-release canary report.

21.6 Pitfalls

A flaky corpus (intermittent failure under load, e.g. a timing-sensitive fixture misfiled into the correctness suite) masks a real regression behind "just re-run it" — correctness fixtures must be fully deterministic; anything timing-sensitive belongs in Phase 8's dudect suite, never here. A fuzz target that only exercises the happy path (valid-looking inputs) because its seed corpus lacks true adversarial examples gives false confidence — seed from the malformed-input fixtures (§8.6, §18.5) explicitly, not only from valid corpora.

21.7 Performance Concerns

The conformance suite's wall-clock budget (M10, ≤ 10 minutes) is dominated by Argon2's memory-hard cost multiplied across hundreds of KAT cases — parallelize corpus execution across cores (the corpora are independent, embarrassingly parallel) rather than reducing per-case parameters (which would weaken the KAT itself).

21.8 Edge Cases

A corpus file that fails to parse as valid JSON (a CI/tooling bug, not a cryptographic one) must fail the pipeline with a distinct, actionable error, not be silently skipped. A fuzz target that finds a crash exactly at the 24-hour boundary — the canary must record and block release even on a late-breaking find, not just findings from the first hour.

21.9 Failure Analysis

Any conformance-corpus failure blocks the release tag (RTO < 1 release cycle, §4) — the failing I#/fixture pair is the direct debugging entry point (§7's methodology). A fuzz-canary crash triggers the incident path in docs/runbooks/triage.md, treated with the same severity as a production auth-path panic would be, because this is the pre-production proxy for that failure class.

21.10 Operational Notes

This phase establishes the release cadence and its gates for all future versions (§25, §27); no new runtime telemetry is introduced beyond what Phases 0–8 already emit. The 30-day canary (M12) runs unattended post-tag; its dashboard lives alongside the 24-hour canary's in docs/performance/.

24. Operational Readiness

Metrics (Prometheus-style naming, <crate>_<verb>_total/_seconds/_bytes, established §12.10): hash_calls_total{algorithm}, verify_calls_total{result}, needs_rehash_total, weak_param_rejections_total, phc_parse_errors_total{reason}, legacy_parse_total{format}, argon2_alloc_bytes, dudect_t_stat{algorithm}, bcrypt_truncation_warnings_total.

Tracing: each hash()/verify() call emits one span named pwhash.<verb> with attributes algorithm, outcome, and (for verify) needs_rehash; no password or salt/hash bytes ever appear as a span attribute (P14).

Structured logging: JSON lines at WARN for truncation/legacy-format-detected events, ERROR for parse/alloc failures; DEBUG for per-call parameter dumps (never secret material).

Dashboards: one per algorithm (latency histogram + call-volume), one cross-algorithm parameter-floor-distribution view (breach-triage use, docs/runbooks/triage.md), one fuzz-canary health view (24h + 30-day).

Alerting philosophy: page on dudect_t_stat gate failure (blocks release, not production — this is a CI-time alert), page on a phc_parse_errors_total spike > 3σ over a 5-minute window (possible datastore corruption, FM-4), page on any fuzz-canary crash (T10, FM-6).

SLOs: the library itself carries no independent availability SLO (§4); it inherits the caller's login-path SLO (assume 99.9%). Its own internal targets are the perf-table's M# rows (§28), gated in CI, not monitored as a live SLO.

Incident response: docs/runbooks/triage.md (breach-response: classify a leaked dump's algorithm/parameter distribution, estimate crack-time via §32's capacity model) and docs/runbooks/parameter-upgrade.md (routine annual PARAMS_<year> bump procedure).

Backup/restore: out of scope — this library has no persistence layer; the caller's database backup policy governs (§1.2 delegation).

Deployment topology: embedded in the caller's authentication-service process; no independent deployment unit. Canary/rolling upgrade: a library version bump follows the caller's own rolling-upgrade cadence; because PHC/legacy encodings are self-describing (§8.1–8.3), old and new library versions can coexist across a rolling deploy without a hash-format migration step, unless a phase introduces a new PHC algorithm-id (a SemVer-major event, §25). Rollback: reverting to a prior library version is safe as long as no hash was generated under a PHC algorithm-id the prior version doesn't recognize (§19.10).

25. Compatibility & Versioning

Wire/storage compatibility: the PHC string (§8.1) and the six legacy formats (§18) are the only persisted shapes; all are self-describing, so no external schema-version field is needed. Argon2 version field: v=19 (Argon2 v1.3) is the only version this library generates; v=16 (v1.0) is parsed but unconditionally flagged needs_rehash (an old-version hash is treated as "legacy" in spirit even though it is not one of the six named legacy formats). API stability: Algorithm, Params, EncodedHash, VerifyOutcome, AuthError are the SemVer-stable public surface; adding an Algorithm variant is additive (minor version); removing one, or changing the PHC algorithm-id string a variant maps to, is a breaking (major) change (I12). Migration: a caller upgrading from one PARAMS_<year> to the next needs no code change — needs_rehash (I14) drives the migration organically as users log in; a forced-migration batch job is a caller-side operational choice, not a library requirement. Deprecation policy: a legacy-format parser is never removed while any known production corpus still contains that format; removal requires a documented sunset period (minimum one major version) and a migration runbook update. SemVer policy: patch = bugfix/perf, no API change; minor = additive (new Algorithm variant, new legacy parser); major = any breaking change to Algorithm/Params/the PHC algorithm-id mapping, or a floor tightening that could reject previously-accepted hash() calls (a deliberate, documented major-version event, never silent). Rolling-upgrade guarantee: two adjacent major versions can always verify() each other's PHC-emitted hashes, because the algorithm-id and parameter encoding (§8.1) are additive-only within a major version (I12-adjacent guarantee); this is the compatibility contract Argon2-v2 support (FM-10, PhaseDeferred("§25")) would need to preserve if/when adopted.

26. Testing & Verification Strategy

Unit tests: one per invariant (§7) plus one per algorithm's documented edge case (§13.8–§21.8). Integration tests: the end-to-end hash → store → verify round trip (§19.4) across all seven generatable algorithm/parameter combinations. Property tests: the I1 round-trip (parse(serialize(x)) == x, ≥10,000 cases, §18.4), the I11 pepper-symmetry property, the I8 PBKDF2 block-count arithmetic property. Differential testing: Argon2's G/h_prime against the reference C implementation (§16.4), bcrypt against the OpenBSD corpus (§14.4). Fuzzing: cargo-fuzz targets seeded from the malformed-input fixtures (§18.6), running the 24h pre-release and 30-day post-tag canaries (M11/M12, §21). Chaos/fault injection: simulated allocator failure paths for Argon2/scrypt's large allocations (§16.9, §15.9), verifying Error propagation never panics. Deterministic replay: the conformance/runner (§21.2) replays every corpus fixture byte-for-byte on every CI run — no randomized inputs in the correctness suite (randomness lives only in the property-test generators, seeded and logged for reproducibility). Soak testing: the 24-hour and 30-day fuzz canaries double as soak tests for memory growth (M11/M12). Conformance: the fourteen-corpus suite (§21.4) is the release gate. Performance- regression gating: every M# row in §28 is a CI-enforced threshold, not an advisory dashboard number — a regression below threshold blocks the release exactly like a correctness failure does. Every fixture in this strategy ties back to a named invariant (I1–I14) or a phase's N.5 Conformance Fixtures — there is no test in this suite that does not trace to a specific claim.

29. Scalability Analysis

Stays constant regardless of load: per-call working-memory footprint (each hash()/verify() call is independent, §3) — O(1) per call in caller count, since there is no shared mutable state to contend over. Grows with load: aggregate RAM consumption grows O(concurrent_sessions × memory_kib) (§32 CM1) — this is the dominant capacity constraint for Argon2id at scale, not CPU. Named bottlenecks, in order: (1) RAM budget under concurrent Argon2id hashing (§32 CM1); (2) memory bandwidth during the fill/ROMix phases (§17.7/§15.7, both O(m) in bytes touched per hash); (3) CPU cores for bcrypt/PBKDF2's compute-bound (not memory-bound) cost; (4) FD budget for the CLI/embedding process, a minor constraint (§4). Horizontal scaling: trivial — every hash()/ verify() call is stateless and independent (§3), so adding authentication-service replicas scales linearly with no coordination overhead (no sharding, no partitioning, no consensus — this is the scalability payoff of the no-shared-state design, P13-adjacent). Vertical scaling: more RAM directly raises the concurrent-Argon2id-session ceiling (§32 CM1); more cores directly raises bcrypt/PBKDF2 throughput near-linearly (§32 CM3/CM4) but Argon2id's per-hash parallelism (p=4) already claims 4 cores per in-flight hash, so core scaling for Argon2id specifically caps out at total_cores / p concurrent hashes, not total_cores. Coordination overhead: zero — there is no distributed state in this system (§3). Practical ceiling: the RAM-per-session bound (§32 CM1) is the first wall a high-throughput login service hits; the lever beyond it is either lowering memory_kib toward the floor (§4, at a security cost, governed by P9) or horizontally scaling authentication-service replicas (no coordination penalty, per the horizontal-scaling point above).

30. Mental Models & First Principles

MM1 — "A KDF is a hash function wearing a seatbelt." The compressed insight: general-purpose hashes are optimized to be fast; a password KDF exists to make that exact property expensive on purpose. Predicts: any "fast" property proudly advertised for a hash function is a red flag for password use. Bug class without it: reaching for SHA-256 directly on a password because "it's a cryptographic hash" (the LDAP {SSHA} legacy format is a fossil of exactly this mistake). Applied in §6 P1–P4, §18.2 (why {SSHA} is parse-only).

MM2 — "Cost is a knob you must re-turn every year, not a constant you set once." Predicts: a parameter chosen as "secure" in 2020 is measurably weaker in 2026 against the same attacker budget, with no code change required to explain the drift — only hardware improvement. Bug class without it: a cost = 12 hardcoded in 2015 and never revisited. Applied in §6 P10, §25 (annual review), §22 T2–T3.

MM3 — "Constant-time is a property of the whole call graph, not one function." Predicts: a correctly-constant-time comparison can still leak timing if an earlier parse step short-circuits on secret-dependent length or content. Bug class without it: adding a length pre-check "for efficiency" immediately upstream of an otherwise-hardened ct_eq call. Applied in §7 I2, §20.2, §20.6, §23 FM-9.

MM4 — "A hash format is a wire protocol with one writer generation and infinite reader generations across time." Predicts: every format this library ever emits must be parseable forever, because a hash written once may need verifying a decade later. Bug class without it: "cleaning up" a legacy parser because it looks unused in the current test suite, breaking real production rows the test suite never sampled. Applied in §6 P5, §18.2, §25 (deprecation policy).

MM5 — "Memory-hardness taxes bandwidth, not just compute." Predicts: an attacker's advantage from parallel hardware (GPU/ASIC) is capped by how much memory bandwidth that hardware actually has per unit of parallel compute, not by raw core count. Bug class without it: assuming "more cores = proportionally more cracking throughput" for Argon2id/scrypt the way it holds for PBKDF2/bcrypt. Applied in §17.7, §15.7, §22 T2–T3, §32 CM7.

MM6 — "Data-dependent indexing trades a side-channel for a time-memory-trade-off defense." Predicts: there is no indexing strategy that is simultaneously immune to both cache-timing side-channels and TMTO attacks — a real design must pick which regime it defends and say so. Bug class without it: claiming Argon2id has "no side-channel surface" instead of the accurate claim (a partial, structural mitigation on the most-attacked phase). Applied in §17.2, §7 I9, §22 T5–T6.

MM7 — "The salt is not secret; the pepper is." Predicts: a design that tries to keep the salt confidential is solving the wrong problem (salts defeat precomputation, not guessing, and must be retrievable to verify at all); a pepper's entire value is that it is not stored with the hash. Bug class without it: encrypting the salt column "for extra security" while leaving the pepper inline in application config. Applied in §6 P11–P12, §22 T8, T12.

MM8 — "Every verify() call is a race between attacker guesses/second and this library's cost per guess." Predicts: the entire value of this system reduces to one ratio — attacker hardware throughput divided by hash cost — and every parameter choice is a lever on the denominator only (the numerator, attacker hardware, is out of this library's control). Bug class without it: treating parameter selection as a checkbox ("we use bcrypt") instead of an ongoing arms-race calculation. Applied in §32 (the entire Capacity Model), §22, §6 P10.

libsodium made the same core decision this design did — Argon2id as the sole/default memory-hard KDF — but chose not to expose raw parameter control to most callers, instead offering three fixed cost presets (interactive, moderate, sensitive). That wins in the niche this design's low-level API explicitly carves out an escape hatch for: applications where the operator should never be able to mis-set a parameter, at the cost of losing this design's fine-grained annual-review flexibility (P10).

OpenSSL treats password hashing as one KDF among many generic ones (EVP_PBE), with PBKDF2 as the historical default and Argon2 available only through its newer provider architecture (3.2+). That wins whenever a system is already deeply invested in OpenSSL's provider model for unrelated crypto needs (TLS, general KDFs) and wants one dependency instead of a dedicated password-hashing library — at the cost of no built-in parameter floor (ADR-11's entire rationale is the gap OpenSSL's model leaves open).

PHP's password_hash/password_verify made the closest design to this one among the four compared: an algorithm-agnostic verify() that auto-detects the stored algorithm, a needs_rehash- equivalent (password_needs_rehash), and a migration from bcrypt-default to Argon2i/id-default across PHP versions. That wins in a large existing PHP install base where the standard library is the ecosystem default, making it the correct choice purely by inertia and support surface — this design instead earns adoption on explicit parameter-floor enforcement (ADR-11) that PHP's API leaves to caller discipline.

Django's PBKDF2PasswordHasher remains the default despite Argon2 support existing as a pluggable hasher for years — an explicit ecosystem-inertia tradeoff (changing a web framework's default password hasher is a breaking-adjacent decision affecting millions of deployments). That wins whenever backward compatibility with an enormous existing deployment base outweighs shipping the theoretically-stronger default — exactly the tension P10's annual-review principle and §25's SemVer-major discipline are designed to navigate deliberately rather than by inertia.

32. Back-of-Envelope Capacity Model

CM1 — Concurrent Argon2id sessions per RAM budget. sessions = RAM_budget / memory_kib. For an 8 GiB host and PARAMS_2026 (64 MiB/session): 8,192 MiB / 64 MiB = 128 concurrent sessions (§4).

CM2 — Argon2id login throughput ceiling per core. throughput = 1000 ms / p50_latency. At M1's 200 ms p99 (using p99 as the conservative bound): 1000 / 200 = 5 logins/sec/core-equivalent (a full Argon2id hash claims 4 cores at p=4, so per-hash throughput, not per-core, §29).

CM3 — bcrypt login throughput ceiling per core. At M3's 250 ms: 1000 / 250 = 4 logins/sec/core (§4, §14.7).

CM4 — PBKDF2 login throughput ceiling per core. At M5's 100 ms (SHA-NI host): 1000 / 100 = 10 logins/sec/core (§4, §13.7).

CM5 — scrypt login throughput ceiling per core. At M4's 200 ms: 1000 / 200 = 5 logins/sec/core (§4, §15.7).

CM6 — Storage overhead at 100M-row scale. A PHC-encoded Argon2id hash (§8.1) runs ≈ 90–100 bytes (algorithm-id + params + 16-byte salt + 32-byte tag, all base64'd, plus delimiters) versus a raw 32-byte digest: 100M rows × (95 − 32) bytes ≈ 6.0 GB of encoding overhead versus a hypothetical raw-binary scheme (§4, informs ADR-07's "at scale" rejection-wins clause).

CM7 — Argon2id fill-phase memory bandwidth demand. bandwidth ≈ (memory_kib × 1024 × time_cost) / p50_latency_seconds. At PARAMS_2026 (64 MiB, t=3, ~0.1 s p50 per M1's p50 being roughly half its 200 ms p99 bound): (64 MiB × 3) / 0.1 s = 1,920 MiB/s ≈ 1.9 GB/s of memory traffic per concurrent hash — directly grounding MM5's "memory-hardness taxes bandwidth" claim (§4, §17.7).

CM8 — FD budget → concurrent verify() ceiling. At the §4 FD budget (≤ 64 FDs steady-state for the CLI process) and assuming ~2 FDs per in-flight embedded-library caller connection (a conservative caller-side estimate), the CLI/embedding process itself is not the bottleneck versus CM1's RAM-driven ceiling — FD budget matters only for the pwhash CLI's own operation, not the library embedded in a caller's already-provisioned service (§4, §10).

CM9 — p99 latency headroom before SLA breach. If the caller's login-path p99 SLA budget is, say, 500 ms end-to-end and Argon2id's own p99 is 200 ms (M1), the remaining 300 ms headroom is the caller's network/application budget — a useful sizing check before choosing PARAMS_2026 over a lighter-weight algorithm for a latency-sensitive path (§4, §29).

CM10 — Fuzz corpus coverage growth over the 30-day canary. At an assumed sustained fuzzing rate (a cargo-fuzz target commonly sustains on the order of 10³–10⁴ executions/sec on a single core for a parser this size), a 30-day canary (M12) accumulates on the order of 10¹⁰–10¹¹ total executions — the basis for treating M12's "zero panics" bar as a meaningfully strong claim rather than a token background job (§21.2, §26).

34. Alternative Architectures (Roads Not Taken)

AA1 — OPAQUE asymmetric PAKE.

Client                                   Server
  │  password (never leaves client)        │
  │──── OPRF blind(password) ─────────────►│
  │◄──── OPRF response ────────────────────│  (server holds only an
  │  derive envelope key, decrypt creds     │   OPRF key + wrapped envelope,
  │──── AKE key exchange ──────────────────│   never a crackable hash)
  │◄──── mutual auth, session key ──────────│

Regime where it wins: greenfield systems where the client can run PAKE cryptography and the protocol change is acceptable — the server literally never holds anything an offline dictionary attack can target (Jarecki, Krawczyk, Xu, 2018 — OPAQUE: An Asymmetric PAKE Protocol Secure Against Pre-Computation Attacks, real, peer-reviewed). Rejected here because this project's scope is explicitly a drop-in password-hashing library for existing authentication flows (§1.2); adopting OPAQUE is a protocol redesign, not a parameter or library swap, and requires client-side changes this project's callers do not control (§1.3 non-goals). PhaseDeferred("§34") tracks it as a future, fundamentally different system, not an incremental feature.

AA2 — Client-side password pre-hashing.

Client: h = SHA256(password)  ──over the wire──►  Server: Argon2id(h, salt)

Regime sometimes proposed: reducing plaintext-over-the-wire exposure on a distrusted transport. Rejected — TLS already provides transport confidentiality (§1.2 delegates transport security), and pre-hashing merely moves the crackable target from "password" to "h," which is exactly as crackable if h itself is exfiltrated (the KDF still must run on something, and a fixed, un-salted client-side digest is weaker per-guess than the full construction). The OWASP Password Storage Cheat Sheet (§5) explicitly advises against relying on client-side hashing as a primary defense for this reason. No real system is cited as "winning" with this as a primary mechanism because it is a documented anti-pattern, not a legitimate alternative architecture — included here specifically to record why it was considered and rejected.

AA3 — Balloon Hashing.

Fill phase: sequential dependency chain over m blocks (no random access)
Mix phase:  Argon2d-style pseudorandom mixing rounds, t times
            (provable sequential-memory-hardness reduction, no data-dependent
             branch required for the fill phase itself)

Regime where it wins: environments needing a provably sequential memory-hard function with a simpler security reduction than Argon2's, particularly where a formal proof matters more than raw performance parity (Boneh, Corrigan-Gibbs, Schechter, 2016 — Balloon Hashing: A Memory-Hard Function Providing Provable Protection Against Sequential Attacks, ASIACRYPT, real paper). Rejected here because Argon2id is the PHC-competition-selected, RFC-standardized, far more widely deployed and audited choice (§5, §6 P1) — Balloon Hashing lacks Argon2's ecosystem of reference implementations, Wycheproof-style test corpora, and production track record. PhaseDeferred("§34") tracks it as a future alternative if a CPU-only, provably-sequential regime becomes a hard requirement.

AA4 — HSM/KMS-backed pepper-as-a-service.

Auth service ──(password, salt)──► Argon2id(local) ──► pre-pepper hash
Auth service ──(pre-pepper hash)──► KMS/HSM: HMAC(pepper_key, ·) ──► final stored hash

Regime where it wins: regulated environments (PCI-DSS, FIPS-adjacent compliance programs) requiring a hardware root of trust for any secret key material, where the pepper itself must never exist in application-process memory unencrypted — a pattern widely documented in enterprise envelope-encryption architectures built on AWS KMS / HashiCorp Vault / on-prem HSMs. Rejected as the default architecture here because it adds a network round trip and an external-service dependency to every hash()/verify() call, violating this project's zero-dependency, no-network-listener scope (§1.2, §1.4); kept as the opt-in pepper API's natural extension point (P12, PhaseDeferred("§6")) for callers who need it.
