In one paragraph

A taint analysis engine reads source code without running it and reports where untrusted input (a source) can reach a dangerous operation (a sink) without being cleaned on the way (§1, §8). This design builds one in Rust. It parses several languages into one single-assignment intermediate form, builds a call graph and a model of what each pointer may refer to, and then follows untrusted values with a graph-reachability solver (IFDS/IDE) (§1, §8). It emits deduplicated findings in the SARIF 2.1.0 format (§1, ADR-22). Its users are application-security teams, compiler engineers and static-analysis infrastructure teams, and it runs on one machine or as a sharded cluster (§1).

The problem, concretely

Take the blueprint's own example. A program reads request.get("id"), glues it into the string "SELECT * FROM t WHERE id=" + user_input, and passes the result to execute (§8). The bug is the chain from the first line to the third, traced interprocedurally across up to 15M LOC (§1, §4).

Each obvious shortcut fails in a way the blueprint names:

  • Syntactic pattern matching plus a lightweight intraprocedural taint mode is Semgrep's choice. It forgoes whole-program dataflow precision for fast feedback (§31).
  • Tracking taint at run time requires running the program, unfit for CI-time whole-repo scans (AA-1).
  • Treating taint as a yes/no flag confuses "cleaned for SQL" with "cleaned for HTML", so a value escaped for one sink class looks safe at another (MM1, MM5).
  • Writing an ad hoc interprocedural fixpoint without cached function summaries blows up exponentially on deep call chains (MM2).
  • Letting call strings grow without a bound blows up the graph on mutually recursive functions (MM4).
  • Hard-coding the most precise pointer analysis runs out of memory on a 15M-line repository, and hard-coding the cheapest one floods sinks with false positives (MM3).
  • Naming findings by line number makes every pull request look like all-new findings plus all-resolved ones (MM8, FM-13).

The engine exists to do the precise version of this at scale, and the project also doubles as a tour of compiler theory, graph systems and distributed infrastructure (§2).

How it works, end to end

Follow one repository through the boxes of §3's diagram. This is a compact version, adapted from §3:

Client interfaces (untrusted: CLI, CI runner, REST API ...)
        v
Analysis Orchestrator (trusted: session, scheduler, replay controller, resource governor)
        |                                          |
        v                                          v
Frontend: parser, AST, symbols, CFG, SSA     Persistence: WAL, snapshots, cache
        |                                          |
        v                                          v
Interprocedural graph core, immutable after seal:
  call graph (CHA/RTA) | points-to graph (Andersen/Steensgaard) | heap regions
        |
        v
Taint propagation (IFDS/IDE, exploded supergraph):
  source resolver | PathEdge/SummaryEdge solver | sanitizer engine | sink matcher
        |
        v
Result processing: findings, deduplicator, severity, SARIF export, trace renderer
Observability across all of it: metrics, structured logs, traces
  1. Client interfaces. Requests arrive over an untrusted boundary where inputs and configuration are validated before reaching the core (§3). The cli crate is the driver binary (§1).
  2. Orchestrator. It owns scheduling, replay IDs, cancellation, memory quotas and work stealing (§3). scheduler does shard coordination and leases, and replay-engine is the deterministic replay controller (§1).
  3. Frontend. parser-core loads tree-sitter grammars and builds the AST and symbol tables (§13.2, ADR-10). cfg-engine builds basic blocks and dominators, ssa-engine inserts phi nodes and validates single assignment (§14.2, I1), and ir-core holds the 8 IR node types (§8, §11).
  4. Graph core. callgraph-engine builds the call graph with cha.rs, rta.rs and devirtualize.rs (§15.2). pointsto-engine builds andersen.rs, steensgaard.rs and heap_model.rs (§16.2). Both are sealed and then read-only (I3, I10, P4).
  5. Taint propagation. taint-runtime runs the solver in ifds_solver.rs over the exploded_graph.rs representation (§17.2). rule-engine supplies source, sink and sanitizer catalogs (§18.2).
  6. Results. findings-engine assigns stable IDs and deduplicates in dedup.rs, maps severity in severity.rs, and sarif-exporter writes the report (§21.2).
  7. Persistence and telemetry. storage-engine holds the WAL, snapshots and cache (§1, §19), and telemetry exports metrics and traces (§1, §24).

The data flow in one line: Parser -> AST -> CFG -> SSA -> CallGraph -> PointsTo -> IFDS/IDE Fixpoint -> Findings -> SARIF (§8).

The core ideas

Taint is a lattice value, and a sanitizer transforms it (§8, MM1, MM5)

Instead of a yes/no flag, each fact carries one of five states: Untainted, Tainted(UserInput), Sanitized(SQL), Sanitized(HTML) or Unknown (§8). The states form a lattice, an ordered set where facts can be merged, with Untainted at the bottom and the merged Unknown at the top (§8). Unknown means analysis uncertainty and is fail-closed: ambiguity is reported with downgraded trust, never resolved by a silent best guess (§8, P11). A sanitizer is then a lattice transformer, not a boolean flag (MM5). The blueprint's transition table, copied from §8:

Input State Sanitizer Applied Output State
Tainted(UserInput) SQL_ESCAPE Sanitized(SQL)
Tainted(UserInput) HTML_ESCAPE Sanitized(HTML)
Tainted(UserInput) NONE Tainted(UserInput)
Sanitized(SQL) HTML_ESCAPE (SQL context sink) Sanitized(SQL) (unaffected — not a SQL sink)

(§8). Sanitizer effects count only when declared in the rule catalog, so an uncatalogued third-party sanitizer causes false positives until it is catalogued, where a hidden sanitizer would risk silent false negatives (P9). The rules themselves are a declarative source/sink/sanitizer config, and embedded Lua scripting is the rejected alternative (ADR-20).

The blueprint states this more than one way: §8 writes Sanitized(SQL) with a context name, §11 declares Sanitized(TaintKind, SanitizerId) with TaintKind one of UserInput, FileContent, NetworkResponse, EnvironmentVar, and MM1 speaks of Tainted(SQL-context) (§8, §11, MM1).

Access paths: following fields, with a depth limit (§8, ADR-19, I8)

An access path is a base variable plus a chain of field or index selectors, and k-limiting caps the chain at depth k, default 5 (§8, §36). The grammar, copied from §8:

access_path   ::= base field_chain
base          ::= identifier | "this"
field_chain   ::= ( "." field | "[" index "]" )*
field         ::= identifier
index         ::= identifier | integer | "*"        (* "*" = any-index summary *)

The reason for the cap is termination: unbounded paths hang the fixpoint on deeply nested structures (MM6, I8). The price is precision, since deep chains get merged (MM6). The acceptance test feeds a depth-10 nested path at k=5 and expects a correct merge without an unbounded solve (§18.4).

The second worked example (field sensitivity, ADR-19) stores a request parameter into resp.headers["X-User"], which becomes access path resp.headers["*"] before reaching the sink HttpResponseWrite, verdict Tainted(UserInput) (§8). Two loose ends: the grammar's index has no quoted-string form, though the example indexes with "X-User" (§8). And on overflow, §7 says the recovery is "merge to lattice top at depth k" (I8), while the wire table merges to "*" (§8).

IFDS/IDE: taint as graph reachability (§17, ADR-18, MM2)

The idea is to turn "does taint reach here?" into "is there a path in a graph?". The exploded supergraph has a node for every pair of (program point, dataflow fact) (§36). A PathEdge goes from a procedure's entry fact to a fact that is reachable at some node (§36, §11). A SummaryEdge caches a procedure's net effect from entry to exit, so a function is solved once and not once per call site (§36, P14). The reduction gives a polynomial bound, O(E·D³), in place of a naive exponential fixpoint, and a hand-rolled fixpoint without summary edges blows up exponentially on deep call chains (MM2, §29). IDE is the value-valued extension of IFDS, and the taint states are IDE-valued (§36, §8).

The blueprint's trace for the SQL example, copied from §8, is a chain of PathEdges:

request.get(HttpRequestParam) --Assign--> query --Call(execute)--> SqlExecute[sink]

The solver (§17.2) defines monotone flow functions through trait PropagationRule, keeps a worklist of PathEdges and SummaryEdges, applies sanitizer effects at flow-function boundaries and matches sinks against the catalog. Context sensitivity uses call-string epoch budgets that bound recursion (§17.2); infinite propagation loops are halted by epoch budgets, a breach dumping the exploded-graph state (§17.9, FM-7). Which invariant owns the call-string bound is stated two ways: MM4, §31 and §33 item 1 point to I8, while §7 defines I8 as access-path depth and §17.2 calls the budget "I8-adjacent" (MM4, §31, §7, §17.2). IFDS needs a distributive problem; ADR-18 names non-distributive domains such as numeric intervals as where a pure abstract-interpretation fixpoint wins (ADR-18, §36).

Points-to analysis: which objects can a pointer touch? (§16, ADR-17, ADR-24)

Imprecision here shows up downstream: alias over-approximation cascades into sink false positives (§16.6). The engine ships two solvers behind one dial (ADR-17, P13). Andersen analysis is inclusion-based, solved by a worklist over a constraint graph built from the SSA IR and call graph, for precision; Steensgaard analysis is unification-based, solved with union-find, for speed (§16.1, §16.2). The choice is per analysis profile, with Steensgaard named as the quick-check fallback (§16.1, §29, ADR-17). During an Andersen solve points-to sets only grow, and a shrinking set triggers recomputation from the constraint graph (I9, FM-10). Heap objects are modelled by allocation site, and region collapsing merges regions to bound set growth (ADR-24, §36). Targets per 1M LOC: Andersen converges in ≤90s (M4), Steensgaard in ≤9s (M5) (§28).

Call graph: who can call whom, with honest uncertainty (§15, ADR-16, P11)

CHA (class hierarchy analysis) builds edges from the type hierarchy, a conservative over-approximation (§15.2, §36). RTA (rapid type analysis) prunes the targets to types the program actually instantiates (§15.2, §36). Each edge is tagged Exact, Devirtualized or Unknown (§11). A reflection call is flagged Unknown and never dropped (§15.4, P11), because a dropped edge is a silent false negative (P11). The graph is then sealed (I10).

Seal it, log it, replay it (§19, §20, P1, P3, P4)

Every analysis run must be replayable from identical inputs (P1). Graphs are immutable once published, so an update means a new generation (P4). Workers are crash-only: they may be killed abruptly and recovery is replay, not repair (P3, MM7). Persistence is an append-only write-ahead log with a monotonic order (ADR-15, I2), and runs carry a monotonic replay epoch (I11). A trace of FM-12, a worker dying mid-shard:

  1. The heartbeat times out and the shard is seen as stuck in progress (FM-12).
  2. Its lease, a time-bounded exclusive claim on the shard, expires and the shard is reassigned (FM-12, §36).
  3. If two workers ever claim one shard, the recovery is coordinator fencing (I12, FM-6).

Finding IDs are hashes of the structural path, never of line numbers, so they survive code churn (P12, I15, MM8).

The trade-offs — where engineers disagree

Graph reachability, not a general fixpoint (ADR-18)

Chosen: an IFDS/IDE solver in the style of Heros, because it reduces distributive problems to graph reachability (§9, MM2). Rejected: a pure abstract-interpretation fixpoint (§9). When the rejected choice is right: non-distributive domains, e.g. numeric interval budgets (§9).

Two points-to engines, selectable per profile (ADR-17)

Chosen: dual Andersen plus Steensgaard, for a tunable precision/speed dial (§9, P13). Rejected: Andersen-only (§9). When the rejected choice is right: the table's last column says "Steensgaard-only wins when sub-second whole-program points-to is required" (§9). That names a different alternative from the rejected column, and the mismatch is left as written (§9).

Bounded access paths (ADR-19)

Chosen: k-limited paths, k=5 by default, for a termination guarantee (§9, I8). Rejected: unbounded paths (§9). When the rejected choice is right: small closed codebases (<50K LOC) prioritizing precision (§9).

Lease-based shard ownership (ADR-21)

Chosen: leases, trading sub-second failover consistency for throughput (§9, I12). Rejected: a Raft consensus group (§9). When the rejected choice is right: when sub-second failover consistency outweighs throughput (§9).

A declarative rule language (ADR-20)

Chosen: declarative source/sink/sanitizer config, which is auditable and hot-reloadable (§9, I7). Rejected: embedded Lua scripting (§9). When the rejected choice is right: when rule authors need arbitrary imperative sanitizer heuristics (§9).

Allocation-site heap regions (ADR-24)

Chosen: allocation-site regions, for precision on distinct-allocation-heavy code (§9). Rejected: type-based regions (§9). When the rejected choice is right: when allocation sites vastly outnumber distinct types (§9).

Roads not taken (§34, §35)

Runtime taint tracking (AA-1) wins on dynamic-language or mobile platforms with a small syscall surface, as in TaintDroid. It loses here because it must run the program and its per-instruction overhead conflicts with the §4 targets (§34).

Symbolic or concolic execution (AA-2) wins at confirming a few high-severity candidate flows precisely, as in KLEE. It loses here to path explosion at 15M lines and has no reuse comparable to summary edges, so it stays a deferred confirmation pass (§34, §35).

Type-system information-flow control (AA-3) wins on fully annotated single-language code, as in Jif. It loses here because the target is multi-language, largely unannotated third-party code (§34).

Pure Datalog analysis (AA-4) wins when new analyses must be added as declarative rules, as in DOOP. It loses here because the Souffle engine lacks native incremental re-analysis at the grain Phase 7 needs (§34).

Deferred features each wait for a trigger: symbolic path pruning when the false-positive confirmation rate on high-severity findings exceeds 15%, ML severity ranking when the triage backlog exceeds its SLO for 2 consecutive releases, cache federation when deployments span more than 3 clusters, ML sink classification when the sink-catalog backlog exceeds 200 unclassified APIs, and cross-language call-graph stitching when polyglot repositories exceed 30% of the customer base (§35).

What must never be false

  • I1: every SSA variable is assigned once. Noticed by a validation-pass diff (ssa_validation_fail_total).
  • I2: WAL appends are in monotonic order. Noticed by a sequence-gap metric (wal_gap_total).
  • I3: graph node IDs never change after seal. Noticed by a checksum mismatch (graph_checksum_mismatch_total).
  • I4: sink reports are identical across replays. Noticed by a differential replay diff (nondeterministic_finding_total).
  • I5: the lock hierarchy has no cycles. Noticed by a deadlock watchdog (lock_wait_p99_ms).
  • I6: trace IDs are globally unique. Noticed by a collision counter (trace_id_collision_total).
  • I7: sanitizer semantics are versioned. Noticed by a schema-mismatch check (rule_schema_mismatch_total).
  • I8: access-path depth stays within k. Noticed by a depth-overflow counter (access_path_overflow_total).
  • I9: points-to sets only grow during a solve. Noticed by a non-monotonic delta assertion (pointsto_shrink_total, want 0).
  • I10: call-graph edges never change after seal. Noticed by a post-seal mutation assertion (callgraph_mutation_after_seal_total).
  • I11: the replay epoch only increases. Noticed by an epoch-regression check (replay_epoch_regression_total).
  • I12: each shard lease has one owner. Noticed by a lease-collision detector (lease_collision_total).
  • I13: a shard manifest checksum is verified before replay. Noticed by a Merkle mismatch (shard_manifest_mismatch_total).
  • I14: the parser grammar epoch only increases per language. Noticed by a grammar-epoch check (parser_epoch_mismatch_total).
  • I15: a finding's hash ignores line numbers. Noticed by a line-sensitivity regression test (finding_hash_line_sensitivity_total, want 0).
  • I16: object-sensitivity depth stays within ADR-26's bound. Noticed by a depth overflow counter (object_sensitivity_overflow_total).

All 16 are in §7. One enforcement conflict: §7 puts I3 at the graph allocator in Phase 3 to 4, while a comment in §11 says the IR node lists are sealed at CFG-construction completion and cites I3 (§7, §11).

What breaks in production

FM-4: graph explosion. Symptom: heap-pressure alarms and OOM risk. Cause: edge fanout or alias over-approximation. Detected by the heap-pressure metric. Auto recovery is shard partitioning, the manual step is tuning region collapsing (ADR-24), and the forensic aid is a graph-density snapshot (§23).

FM-7: propagation oscillation. Symptom: the fixpoint never converges. Cause: a non-monotone lattice bug. Detected when the epoch budget is exceeded, and the budget halts the run and dumps the exploded graph for a manual lattice audit (§23, §17.9).

FM-10: points-to non-termination. Symptom: an Andersen solve never converges. Cause: missing k-limiting on recursive types. Detected by the non-monotonic delta assertion (I9). Recovery is recomputation from the constraint graph, and manual tuning of the access-path bound (§23).

FM-12: worker crash mid-shard. Symptom: a shard stays in progress. Cause: a panic or OOM-kill. Detected by heartbeat timeout. Lease expiry and reassignment is automatic, with a manual requeue as backup (§23).

FM-13: finding-identity churn. Symptom: CI shows every finding as new and resolved on each run. Cause: line-number-keyed hashing, an I15 violation. Detected by the line-sensitivity regression test. There is no automatic recovery, and the fix is to recompute IDs from the structural path (§23).

FM-2: WAL corruption. Symptom: replay fails its checksum. Cause: disk corruption or a partial write. Detected by checksum mismatch (I2). The automatic recovery is rollback to the last checkpoint, and the forensic aid is a segment hexdump with a checksum trail (§23).

Threats worth knowing (§22):

  • T1, a parser bomb of deeply nested syntax, is met by a recursion guard and a memory quota; recovery is worker quarantine and input rejection (§22).
  • T6, a rule file crafted to bypass validation, is met by schema validation and "sandboxed eval" (I7), with fallback to the last good rule set (§22). ADR-20 locks a declarative config and rejects embedded Lua scripting, and the Phase 6 steps list JSON Schema validation but no sandbox (ADR-20, §18.2).
  • T13, a crafted type hierarchy that forces object-sensitivity blowup, is met by the context-string depth bound (I16, ADR-26), truncating to k and flagging Unknown (§22).

  • Memory left for the graph. C7 says 512 workers leave "only 4GB" for shared graph structures, while C1 puts the IR alone at 7.68GB (§32 C7, §32 C1).

How it compares

  • CodeQL puts the whole program into a relational database and expresses analyses as declarative QL queries. That is right for organisation-wide custom queries written without touching the engine (§31).
  • Semgrep gives up whole-program dataflow precision for pattern matching and a lightweight intraprocedural taint mode. That is right for fast local or pre-commit feedback (§31).
  • Infer/Pysa analyses on demand, driven by function summaries and working backward, not through an upfront whole-program solve. That is right for CI on pull-request diffs where only changed functions need re-analysis (§31).
  • SVF builds a sparse value-flow graph once and queries it for many client analyses. That is right for research and compiler work that stacks several analyses on one substrate (§31).

Questions to test yourself

  1. How does the system avoid exponential blowup when IFDS context-sensitivity meets recursive call chains, and what caps the exploded supergraph? — Hint: §17.2 and MM4; then check what I8 actually bounds in §7.
  2. How is field-sensitivity bounded so deeply nested access paths cannot stall the fixpoint solver, and what precision is lost by that bound? — Hint: §8, MM6 and §18.4.
  3. What happens to in-flight taint facts when a rule hot-reload changes sanitizer semantics mid-analysis? — Hint: I7, §18.2 and §18.4.
  4. How do access-path k-limiting and heap-region collapsing interact — could over-aggressive collapsing hide a real taint flow? — Hint: ADR-19, ADR-24 and FM-4.
  5. What is the minimum cluster width required to analyze a repository at the 15M-LOC/8GB ceiling, and how is it derived? — Hint: §32 C1 and C10, then §29.

If you only remember three things

Taint is a lattice value with sanitizers as transformers, so partial cleaning is representable and doubt stays visible as Unknown (MM1, MM5, P11). Everything that could run away is capped and cached: access-path depth by k, repeated function work by summary edges, memory by quotas, and non-termination by epoch budgets (I8, P14, P10, FM-7). Graphs are sealed, the log is append-only and finding IDs ignore line numbers, which is what makes a crashed run replayable and CI diffs readable (P4, I2, I15).

Words used here

  • Source: a program point that introduces untrusted data (§36).
  • Sink: a security-sensitive operation that must not receive unsanitized taint (§36).
  • Sanitizer: a lattice transformer that neutralizes taint for one specific context (§36, MM5).
  • Lattice: an ordered set of facts with a join, used to model dataflow states (§36).
  • Access path: a base variable plus a bounded chain of field or index selectors (§36).
  • k-limiting: capping access-path depth so the fixpoint terminates (§36, I8).
  • Exploded supergraph: the graph whose nodes are (program point, fact) pairs (§36).
  • PathEdge / SummaryEdge: a reachable-fact edge from a procedure entry, and a cached entry-to-exit summary (§36).
  • Points-to set: the heap regions a pointer may refer to (§36).
  • CHA / RTA: building a call graph from the class hierarchy, then pruning with instantiated types (§36).
  • Crash-only: components may die abruptly, and recovery is replay, not repair (§36, P3).
  • Lease: a time-bounded exclusive grant over a shard (§36).
  • Structural hash: a finding hash that is stable across line-number churn (§36, I15).
