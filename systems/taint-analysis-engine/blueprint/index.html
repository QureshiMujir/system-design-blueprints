231 — Taint Analysis Engine from Scratch

Project Number: 231

Project Name: Taint Analysis Engine from Scratch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade static and hybrid taint analysis engine performing interprocedural, context-sensitive, field-sensitive, flow-sensitive, and partially path-sensitive dataflow analysis over SSA-form intermediate representation. The engine composes IFDS/IDE graph-reachability dataflow (Reps, Horwitz & Sagiv 1995; Sagiv, Reps & Horwitz 1996; §5, §17) with Andersen inclusion-based and Steensgaard unification-based points-to analysis (§5, §16) to resolve untrusted data flows from declared sources through access-path-abstracted propagation and sanitizer effects into declared sinks, emitting deduplicated, SARIF 2.1.0-compliant findings with deterministic replay guarantees.

Phase 0 deliverable — correctness-kernel modules/crates (numbered, normative; full tree in §10):

  1. parser-core — grammar loading, AST, symbol tables.
  2. ir-core — canonical IR node types.
  3. cfg-engine — basic blocks, dominance.
  4. ssa-engine — phi insertion, SSA validation.
  5. callgraph-engine — CHA/RTA call-graph construction.
  6. pointsto-engine — Andersen/Steensgaard points-to.
  7. taint-runtime — IFDS/IDE solver, taint lattice.
  8. rule-engine — source/sink/sanitizer catalogs, rule DSL.
  9. storage-engine — WAL, snapshot, cache.
  10. scheduler — shard coordination, leases.
  11. replay-engine — deterministic replay controller.
  12. findings-engine + sarif-exporter — dedup, severity, SARIF export.
  13. telemetry — metrics, tracing.
  14. cli — driver binary.

System boundaries:

Provides: multi-language parsing, SSA IR, call-graph construction, points-to analysis, IFDS/IDE taint propagation, sanitizer/sink rule DSL, SARIF findings, incremental analysis, distributed sharded execution, deterministic replay, full observability stack.

Delegates: grammar definitions to tree-sitter upstream grammars (ADR-10); serialization wire format to Protobuf (ADR-03); persistence engine internals to RocksDB (ADR-04); distributed transport to gRPC-over-mTLS (operational, §22).

Does NOT provide: symbolic execution engine, full theorem proving, runtime instrumentation VM, binary lifting, exploit generation, IDE UI implementation, cloud SaaS billing. Each of these is either a rejected Alternative Architecture (§34) or an explicit non-goal below.

Non-goals: dynamic/runtime taint tracking (§34 AA-1), exhaustive soundness proofs (best-effort soundiness, per FlowDroid's design stance — Arzt et al. 2014), general-purpose program verification.

Deployment model: single-node workstation mode; horizontally scalable cluster mode; Kubernetes-native execution; offline air-gapped operation (§22, §24).

Target users: application security teams, compiler engineers, platform security groups, SAST researchers, DevSecOps operators, static-analysis infrastructure teams.

Language: Rust.

Rationale: deterministic ownership semantics for crash-only workers (P3, §6); memory safety under adversarial parsing workloads (T1, §22); strong enum modeling for taint lattice states (§8); mature async ecosystem for the scheduler (ADR-08); zero-cost abstractions for the propagation hot path; stable cross-platform tooling (x86_64 + ARM64, §4); strong fuzzing support (ADR-09).

Rejected languages: Go — weaker sum-type modeling for the taint lattice, GC pauses conflict with p99 propagation-stall target (§4); C++ — memory-safety risk on adversarial parser input (T1) outweighs marginal throughput gain; OCaml — excellent ADT fit but immature distributed-systems and observability ecosystem versus Rust's Tokio/OpenTelemetry stack (ADR-08, ADR-05).

Required prerequisites: compiler construction, graph theory, abstract interpretation, SSA form, dataflow analysis, points-to analysis, concurrency control, lock-free queues, storage-engine internals, distributed-systems fundamentals, Linux process model, observability systems, formal language theory, incremental compilation systems.

Timeline: Phase 0 — 10 weeks. Production-grade single-node engine (Phases 1–6) — 5 months. Distributed cluster support (Phases 7–8) — 8 months cumulative. Enterprise hardening, conformance, and SARIF ecosystem certification (Phase 9 + hardening) — 12–15 months cumulative.

Deferred features (full register: §35):

  • Symbolic-execution-assisted path pruning — PhaseDeferred("§34")
  • Probabilistic finding ranking (ML-assisted severity) — PhaseDeferred("§21")
  • Distributed incremental cache federation — PhaseDeferred("§20")
  • ML-assisted sink classification — PhaseDeferred("§18")
  • Cross-language whole-program call-graph stitching — PhaseDeferred("§15")

2. Why Build This

Taint analysis engines sit at the intersection of compiler theory (IR/SSA/dataflow), graph systems (call graphs, points-to graphs, exploded supergraphs), and distributed infrastructure (sharded, replayable analysis over 15M-LOC monorepos). Few systems force the same engineer to reason simultaneously about lattice soundness (Reps-Horwitz-Sagiv reachability, §5), heap abstraction precision/scalability tradeoffs (Andersen vs Steensgaard, §16), and crash-only distributed scheduling (§20) — this project is a calibrated tour through all three.

Core engineering competencies developed: compiler pipeline construction; interprocedural graph indexing; fixed-point iteration systems; deterministic parallelism; persistent caching and incremental invalidation; alias resolution; protocol compatibility; distributed scheduling; observability-first infrastructure design.

Historically relevant systems: LLVM's dataflow framework, CodeQL, Semmle/GitHub's query engine, Infer (biabduction) and its taint mode Pysa, Clang Static Analyzer, Semgrep, Joern, SVF, Soot + Heros, WALA, DOOP.

Cross-project alignment: compilers (IR lowering, SSA construction — shared with any Self-Hosting-Compiler-style project); databases (persistent graph indexing — shared with any Secondary-Indexing-Engine-style project); distributed systems (sharded work queues, leases — shared with any Geo-Partitioned-Database-style project); kernels (lock-hierarchy discipline); observability (trace stitching); filesystems (append-only WAL semantics, shared with any Write-Ahead-Log-style project).

Calibration value: completing the system permanently upgrades capability in large-scale graph systems, production static analysis, compiler infrastructure, operational reliability engineering, and distributed execution design — the same skill cluster used by CodeQL, Semgrep, and Infer engineering teams in production.

What Mastery Looks Like

  • Derive, from §4's memory ceiling, the maximum IR node count a single shard can hold — and explain why (§32 C1, Phase 4/§16).
  • Explain why IFDS reduces taint propagation to graph reachability and where that reduction breaks down (context-sensitivity without call-string bounding, Phase 5/§17, §30 MM2/MM4).
  • Choose Andersen vs Steensgaard points-to for a given repository size/precision budget and justify the choice against ADR-17 (Phase 4/§16).
  • Design an access-path k-limiting scheme that guarantees fixpoint termination without collapsing semantically distinct fields (Phase 6/§18, §7 I8).
  • Trace a full SQL-injection finding from source declaration through sanitizer catalog to SARIF export, citing every IR transition (§8, Phase 9/§21).
  • Explain how the system survives a worker crash mid-shard without producing a corrupted or non-deterministic finding set (Phase 7–8/§19–§20, §7 I4/I11/I12).
  • Defend, against a staff-level reviewer, why symbolic execution was excluded from the core engine rather than integrated as a confirmation pass (§34 AA-2, §33 Q19).

Client Interfaces — untrusted boundary; protocol normalization, request admission, configuration validation, artifact upload, result streaming; isolates external consumers from internal IR evolution (§25).

Analysis Orchestrator — trusted core; owns deterministic scheduling, replay IDs (I11), cancellation propagation, memory quotas (§4), work stealing, concurrency budgeting.

Frontend Pipeline — transforms source programs into normalized SSA-backed IR; parsing recovery, AST canonicalization, symbol resolution, CFG generation, dominance analysis, SSA insertion (Phases 1–2, §13–§14).

Persistence Layer — persistence boundary; stores replay logs, incremental caches, graph snapshots, findings metadata, deterministic execution manifests; crash-recovery guarantees (Phase 7, §19).

Interprocedural Graph Core — concurrency boundary; canonical call graph, points-to graph, heap-region model. All taint propagation traverses these graphs; immutable after sealing (I3, I10).

Taint Propagation Engine — executes IFDS/IDE fixpoint propagation with configurable taint semantics; field sensitivity via access paths, heap abstractions, taint kinds, sanitizer effects, context windows (Phase 5, §17).

Result Processing — normalizes findings, deduplication, severity mapping, sink aggregation, export formatting (Phase 9, §21).

Observability Platform — distributed traces, propagation counters, queue-depth metrics, scheduler diagnostics, heap-pressure visibility, replay correlation (§24).

6. Design Principles

  1. P1 — Determinism over throughput. Every analysis run must be replayable from identical inputs. Tradeoff: forgoes nondeterministic work-stealing gains for reproducibility. Operational implication: replay IDs (I11) gate every release. Violate it and CI findings diffs become unauditable noise.
  2. P2 — Bounded resource usage. No unbounded queues or recursive traversals. Tradeoff: precision loss via access-path k-limiting (I8, ADR-19). Violate it and a single adversarial repo OOMs the cluster (T7).
  3. P3 — Crash-only worker semantics. Workers may terminate abruptly without corrupting global state. Tradeoff: no graceful-shutdown code paths to maintain. Violate it and ad-hoc cleanup introduces the exact corruption crash-only design exists to avoid (§30 MM7).
  4. P4 — Immutable graph sealing. Graph mutation prohibited after publication (I3, I10). Tradeoff: incremental updates require new graph generations, not in-place edits. Violate it and concurrent readers observe torn graph state.
  5. P5 — Observability by default. Every propagation stage emits metrics and traces. Tradeoff: telemetry cardinality must be actively capped (T5). Violate it and failures are undiagnosable in production.
  6. P6 — Explicit ownership. Shared mutable state minimized; graphs are Arc-shared immutable structures. Tradeoff: some structural-sharing overhead vs raw pointers. Violate it and data races reappear despite Rust's borrow checker (unsafe escape hatches).
  7. P7 — Replayability first. Reconstructable execution traces mandatory (I4, I11). Tradeoff: WAL write volume scales with propagation event count. Violate it and post-incident forensics is impossible (§23).
  8. P8 — Versioned schemas everywhere. Storage and wire evolution must remain compatible (I7, §25). Tradeoff: every schema change carries a migration cost. Violate it and rolling upgrades break mid-fleet.
  9. P9 — No hidden sanitizers. Sanitizer effects require explicit declaration in the rule catalog (§18). Tradeoff: unmodeled third-party sanitizers cause false positives until catalogued. Violate it and silent under-sanitization produces false negatives (a security bug in a security tool).
  10. P10 — Backpressure everywhere. Queue admission tied to memory quotas (§4). Tradeoff: admission control adds latency under load. Violate it and unbounded queue growth causes FM-4.
  11. P11 — Fail closed on parser ambiguity. Ambiguous semantics produce warnings and downgraded trust, never silent best-guess resolution. Tradeoff: more Unknown-taint findings requiring triage. Violate it and a missed dynamic dispatch target becomes a silent false negative.
  12. P12 — Stable finding identity. Findings maintain deterministic IDs across runs, keyed on structural path, not line number (§30 MM8). Tradeoff: ID computation requires structural hashing, not a simple counter. Violate it and every CI run looks like all-new findings.
  13. P13 — Precision is a dial, not a switch. Points-to and context-sensitivity are configurable per analysis profile (ADR-17). Tradeoff: more configuration surface to test. Violate it and the engine either can't scale (Andersen-only) or can't triage precisely (Steensgaard-only).
  14. P14 — Sealed interprocedural summaries over re-derivation. Function summaries are computed once and cached (summary edges, §17), never re-derived per call site. Tradeoff: summary cache invalidation complexity (§19). Violate it and analysis time grows with call-site count instead of function count.

8. Domain Model / Protocol / Data Model

Core entity chain:

Source -> Propagation Edge (Access Path) -> Sanitizer -> Sink

IR node types (canonical, reused §11, Phase 2 §14, Appendix A):

AssignNode · BranchNode · PhiNode · CallNode · ReturnNode · HeapLoadNode · HeapStoreNode · LiteralNode.

Access-path grammar (EBNF; bounded by I8 to depth k, default k=5, ADR-19):

access_path   ::= base field_chain
base          ::= identifier | "this"
field_chain   ::= ( "." field | "[" index "]" )*
field         ::= identifier
index         ::= identifier | integer | "*"        (* "*" = any-index summary *)

Taint states (lattice, IDE-valued per Sagiv-Reps-Horwitz 1996; ⊥ = Untainted, ⊤ = merged Unknown):

State Meaning
Untainted safe
Tainted(UserInput) attacker-controlled
Sanitized(SQL) escaped for SQL context only
Sanitized(HTML) escaped for HTML context only
Unknown analysis uncertainty (fail-closed, P11)

Propagation sequence (Phase-by-phase, §12–§21):

Parser -> AST -> CFG -> SSA -> CallGraph -> PointsTo -> IFDS/IDE Fixpoint -> Findings -> SARIF

Worked example (SQL injection):

user_input = request.get("id")           // AssignNode, source: HttpRequestParam
query = "SELECT * FROM t WHERE id=" + user_input   // AssignNode, access path: query
execute(query)                            // CallNode, sink: SqlExecute

Detected flow (PathEdge chain through the exploded supergraph, §17):

request.get(HttpRequestParam) --Assign--> query --Call(execute)--> SqlExecute[sink]

State-transition table (sanitizer effect application, Phase 6, §18):

Input State Sanitizer Applied Output State
Tainted(UserInput) SQL_ESCAPE Sanitized(SQL)
Tainted(UserInput) HTML_ESCAPE Sanitized(HTML)
Tainted(UserInput) NONE Tainted(UserInput)

Malformed-input example: unresolved dynamic dispatch on execute (reflection) — analysis emits Tainted(UserInput) at Unknown confidence rather than dropping the edge (P11, T1).

29. Scalability Analysis

Constant vs grows (Big-O): parse/SSA cost grows linearly with LOC (Θ(n)); Andersen points-to worst case is near-cubic in program size without region collapsing, near-linear in practice with ADR-24 collapsing; IFDS propagation is bounded by O(E·D³) in exploded-graph edges/distinct-facts per Reps-Horwitz-Sagiv 1995 (§5, §30 MM2).

Named bottlenecks in order: (1) points-to constraint-graph solve (Phase 4, §16) — dominant cost above ~5M LOC; (2) IFDS exploded-graph size without summary-edge reuse (Phase 5, §17); (3) shard-coordination RPC volume at high worker count (Phase 8, §20); (4) SARIF serialization on finding-count spikes (Phase 9, §21).

Horizontal scaling: shard by module boundary (call-graph-aware partitioning, minimizing cross-shard call edges); distributed snapshot store; bounded queue partitions per shard.

Vertical scaling: NUMA-aware worker pinning (dual-socket, §4); larger per-node memory raises the single-shard LOC ceiling (§32 C1).

Practical ceiling: a single shard is capacity-bound at the 2GB serialized-IR limit (§4); the 15M-LOC/8GB single-node ceiling (§4) requires a minimum 4-shard cluster at maximum supported repository size (§32 C10).

Levers beyond the ceiling: Steensgaard fallback for quick-check mode (ADR-17) trading precision for throughput; deferred cross-cluster cache federation (§35) for multi-cluster monorepos; lowering the default object-sensitivity depth (ADR-26) trades precision for the C3 storage headroom needed to push past the single-shard LOC ceiling without adding hardware.

What stays constant regardless of repository size: per-finding SARIF record size (§21), WAL record size (C5, §32), and lease-renewal RPC payload size (C8, §32) — none of these grow with LOC, which is why coordination overhead (§20) does not become the dominant bottleneck even as the cluster scales to the 4-shard minimum derived in C10.

30. Mental Models & First Principles

MM1 — Taint is a lattice fact, not a boolean. Predicts: multiple taint kinds compose without separate analysis passes. Bug class without it: conflating Tainted(SQL-context) with Tainted(XSS-context) causes false sanitization across sink kinds. Resolving: §8, §18.

MM2 — IFDS reduces distributive dataflow to graph reachability. (Reps-Horwitz-Sagiv 1995.) Predicts: polynomial complexity bound O(E·D³) instead of naive exponential fixpoint. Bug class without it: a hand-rolled interprocedural fixpoint without summary edges blows up exponentially on deep call chains. Resolving: §5, §17.

MM3 — Points-to precision is a dial, not a switch. (Andersen vs Steensgaard.) Predicts a tunable precision/speed tradeoff exists and should be exposed, not hardcoded. Bug class without it: hardcoding Andersen-only causes OOM on 15M-LOC repos; hardcoding Steensgaard-only causes a false-positive storm at sinks. Resolving: §16, §9 ADR-17.

MM4 — Context sensitivity without call-string bounding diverges. Predicts unbounded call strings on recursive programs blow the exploded graph. Bug class without it: infinite exploded-graph growth on mutually recursive functions. Resolving: §17, §7 I8.

MM5 — A sanitizer is a lattice transformer, not a boolean flag. Predicts partial sanitization (SQL-safe but not HTML-safe) is representable. Bug class without it: a single "sanitized" bit causes false negatives across sink kinds that weren't the sanitizer's target. Resolving: §8, §18.

MM6 — Field-sensitivity is bounded by access-path k-limiting. Predicts a termination guarantee at the cost of merging deep field chains. Bug class without it: unbounded access paths hang the fixpoint on deeply nested structs. Resolving: §9 ADR-19, §16.

MM7 — Crash-only design turns recovery into replay, not repair. Predicts workers can be killed with SIGKILL safely. Bug class without it: ad-hoc cleanup-on-panic code paths introduce the exact state corruption crash-only design exists to prevent. Resolving: §6 P3, §23.

MM8 — Finding identity must survive code churn or CI drowns in noise. Predicts stable hashing keyed on structural path, not line number. Bug class without it: line-number-keyed IDs make every PR look like all-new-plus-all-resolved findings. Resolving: §21, §25.

32. Back-of-Envelope Capacity Model

C1 — Max IR node count at the memory ceiling. 15M LOC (§4) × ~8 IR nodes/line (typical 3-address SSA form) = 120M nodes. At ~64 bytes/node (NodeId 8B + kind discriminant 8B + operands 32B + span 16B) → 120M × 64B = 7.68GB — against the 8GB peak-resident-memory ceiling (§4), leaving <5% headroom before graph compaction (Phase 4, §16) is mandatory.

C2 — TaintFact memory at scale. ~1.5M functions (15M LOC / 10 LOC per function avg) × ~50 taint facts/function average = 75M facts. At 32 bytes/fact (fact_id 8B + state discriminant 4B

  • source_node 8B + depth 4B + padding 8B) → 75M × 32B = 2.4GB — combined with C1 this exceeds the 8GB ceiling, which is exactly why access-path k-limiting (ADR-19, I8) and summary-edge reuse (§17) are mandatory, not optional.

C3 — Points-to set storage. ~22.5M variables (1.5M functions × 15 vars/fn avg) × ~5 points-to targets/variable (empirical convergence average) × 8B/reference = 900MB — fits inside remaining budget after C1/C2 only because of region collapsing (ADR-24).

C4 — Call-graph edge storage. ~1.5M functions × ~8 call sites/function fanout = 12M edges × 24B/edge (caller NodeId 8B + callee NodeId 8B + CallSiteId 8B) = 288MB.

C5 — WAL sustained write throughput. 5M-edge max queue backlog (§4) × ~48B/PathEdge WAL record = 240MB backlog; draining within the 250ms p99 propagation-stall target (§4) requires ≈960MB/s peak burst write throughput — within a 3x margin of typical NVMe sequential write (~2.5–3GB/s), validating ADR-04's RocksDB WAL choice at this scale.

C6 — Snapshot restore throughput. Snapshot size ≤ 2.5x storage amplification (§4) × 7.68GB (C1) ≈ 19.2GB; restoring within the 5-minute target (§4, M10) requires ≥19.2GB/300s = 64MB/s sequential read — trivially available on NVMe/SATA, meaning restore time is deserialization-bound, not disk-bound (motivates parallel snapshot deserialization design, Phase 7 §19).

C7 — Per-worker memory overhead at max concurrency. 512 workers (§4) × ~8MB/worker (stack + local caches) = 4GB, leaving only 4GB of the 8GB ceiling for shared immutable graph structures — this is why the graph core is Arc-shared, not per-worker-copied (§3, §6 P6).

C8 — Lease-coordination RPC load. 512 workers × 1 lease-renewal request every 5s = ~102 req/s to the lease manager; at 0.5–20ms RTT (§4) this is well under 1% of a single-threaded lease service's theoretical ~1000 req/s capacity — coordination overhead is not the bottleneck at this scale (§29).

C9 — Failure-budget consistency check. 99.9% availability over a 30-day month = 43.2 min/month downtime budget, matching the §4 failure-budget row exactly; one full snapshot restore (5 min, C6/M10) plus one WAL-replay recovery (≤60s, M9) per week = (5+1)min × 4 weeks = 24 min — leaving ≈1.8x margin against the 43.2-minute budget.

C10 — Minimum cluster width at max repository size. 2GB max shard size (§4) as a divisor of 7.68GB total IR (C1) → ⌈7.68GB / 2GB⌉ = 4 shards minimum — the practical floor on cluster width for the largest supported (15M-LOC, 8GB-ceiling) repositories (§29).

34. Alternative Architectures (Roads Not Taken)

AA-1 — Dynamic/runtime taint tracking (instrumentation-based).

[Instrumented Runtime] --shadow-memory taint bits--> [Sink Check at Call Site]

Wins in: dynamic languages / mobile OS platforms with weak static typing and a small, well-defined syscall surface. Real system: TaintDroid (Enck et al., "TaintDroid: An Information-Flow Tracking System for Realtime Privacy Monitoring on Smartphones," OSDI 2010). Rejected because: requires running the program (incompatible with CI-time whole-repo scanning, §1 goal), and per-instruction shadow-memory overhead conflicts with the §4 throughput targets.

AA-2 — Symbolic / concolic execution.

[Path Constraints] --SMT solve--> [Concrete Counterexample per Sink]

Wins in: precise, path-sensitive confirmation of a small number of high-severity candidate flows. Real system: KLEE (Cadar, Dunbar & Engler, "KLEE: Unassisted and Automatic Generation of High-Coverage Tests for Complex Systems Programs," OSDI 2008). Rejected because: path explosion at 15M-LOC scale (§4 ceiling) with no whole-program summary reuse comparable to IFDS summary edges (§17) — retained only as a deferred confirmation pass (§35, PhaseDeferred("§34")).

AA-3 — Type-system-based information-flow control.

[Annotated Source: {L}int x] --type-check--> [Compile-Time IFC Guarantee]

Wins in: fully annotated, single-language codebases wanting zero analysis-time cost after annotation. Real system: Jif (Myers et al., Cornell — language-based information flow via security-typed Java extension). Rejected because: requires exhaustive source annotation, incompatible with the multi-language, largely unannotated third-party code this engine targets (§1).

AA-4 — Pure whole-program Datalog analysis.

[Facts: Assign(x,y), Call(...)] --Souffle/Datalog rules--> [Points-To + Taint Facts]

Wins in: rapid extension with new analyses expressed as declarative rules without engine changes. Real system: DOOP (Bravenboer & Smaragdakis, "Strictly Declarative Specification of Sophisticated Points-to Analyses," OOPSLA 2009). Rejected because: Datalog engines (Souffle) lack native incremental re-analysis support at the granularity Phase 7 (§19) requires, and IFDS/IDE's summary-edge reuse fits the incrementality requirement more directly than re-evaluating recursive rules per change.
