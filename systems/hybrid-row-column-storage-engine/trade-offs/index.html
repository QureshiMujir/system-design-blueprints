Decisions (§9) · 26 ADRs

1

Implementation language

Chosen

Rust 2021, MSRV 1.78

Rejected

C/C++; Go; Java; Zig

When the rejected choice is right

C++ wins when embedding into an existing C++ kernel (DuckDB, ClickHouse) where FFI cost and a second toolchain are prohibitive; Java/JVM wins inside a Spark/Presto-style analytics stack where the engine ships as a managed library and G1/ZGC tail latency is acceptable for OLAP-only workloads.

Why: Byte-layout page/encoding code is unsafe-adjacent over untrusted on-disk bytes → borrow checker + checked bounds. C/C++ memory-unsafe on persistence hot path; Go GC pauses during multi-GiB scans/merges + no zero-cost columnar slices; Java object overhead vs columnar density; Zig immature ecosystem/no MSRV discipline.

2

Code organization

Chosen

Cargo workspace, ten hy-* crates (hy-common, hy-page, hy-row, hy-index, hy-wal, hy-txn, hy-col, hy-store, hy-catalog, hy-cli)

Rejected

Single monolithic crate; two crates (lib+bin)

When the rejected choice is right

A single crate wins for a < 5 k-line prototype or teaching artifact where compile-graph clarity matters less than zero Cargo.toml overhead and trivially shared pub(crate) internals.

Why: Crate boundaries enforce the layering (page→row/index→wal→txn→col→store); independent compile units → faster incremental builds + clear public API surface per layer; cyclic deps caught by cargo. Monolith blurs invariants, slows builds.

3

Page size

Chosen

4 KiB fixed (Page)

Rejected

8/16 KiB; 64 KiB; variable

When the rejected choice is right

16–64 KiB pages win on scan-dominant / append-mostly workloads (time-series, log analytics) where larger pages amortize I/O setup and improve sequential bandwidth; InnoDB defaults 16 KiB for exactly this OLTP-with-bigger-rows regime.

Why: Matches typical OS page + SSD I/O granularity → minimal read amplification for OLTP point ops; small pages keep buffer-pool frame table dense. Larger pages waste cache on point reads; variable pages complicate FileManager offset math + torn-page reasoning. [## 13]

4

Buffer-pool eviction

Chosen

Clock (second-chance) + pin counts (BufferPool)

Rejected

Strict LRU; LRU-K/2Q; ARC

When the rejected choice is right

LRU-K/2Q wins when a recurring large scan would otherwise flush the OLTP hot set (the classic "scan pollution" problem) and clock's single ref-bit can't distinguish frequency; Postgres uses clock-sweep, but DB2/Oracle adopted LRU-K-style schemes for scan resistance under mixed loads.

Why: Clock approximates LRU at O(1) with no per-access list mutation → lock-friendly under concurrent pins. Strict LRU needs a doubly-linked list mutated on every hit (contention); ARC/LRU-K extra metadata + tuning not justified for v1. Pin count is non-negotiable: pinned frames are eviction-ineligible. [## 13]

5

Row heap organization

Chosen

Slotted-page heap (SlottedPage/RowStore): slot directory + heap-from-end

Rejected

Pure append-only log; fixed-width record array

When the rejected choice is right

An append-only log (LSM memtable) wins when the workload is write-saturated and sequential-write bandwidth is the binding constraint — RocksDB/LevelDB choose it because random in-place updates would thrash the device; fixed-width arrays win for an all-fixed-width schema needing O(1) positional addressing.

Why: Slotted pages give in-place slot stability (RowId.slot indirection survives intra-page compaction) → stable RowIds for B+Tree leaves + version chains. Append-only forces an LSM/compaction layer we explicitly reject for the row path; fixed-width can't hold variable Str/Bytes. [## 13]

6

MVCC version metadata placement

Chosen

In-tuple header (TupleHeader{txn_min, txn_max, next_version}), Postgres/HANA-style version chain

Rejected

Separate undo/rollback segment (Oracle-style); UNDO-log time travel

When the rejected choice is right

An undo/rollback segment (Oracle, MySQL InnoDB) wins for update-heavy OLTP where in-place update + undo keeps the heap compact and avoids Postgres-style table bloat and aggressive vacuum; it makes the latest version cheap to read at the cost of older-version reconstruction.

Why: In-tuple versions co-locate visibility metadata with payload → single page read serves visibility check; no second I/O to an undo segment. Undo segments add a second access path + GC coordination; we accept update-bloat, reclaimed by Vacuum. [## 16]

7

Storage macro-architecture

Chosen

Delta/main (SAP HANA model): row DELTA + columnar MAIN + background merge

Rejected

Pure columnar (write-in-place compressed); pure LSM (sorted-run compaction)

When the rejected choice is right

Pure columnar wins for append-only / bulk-load analytics with negligible point updates (ClickHouse MergeTree, Parquet data lakes) where the delta layer is dead weight; pure LSM wins for a write-saturated KV store (RocksDB) with no analytical scan requirement.

Why: Delta/main absorbs OLTP writes in a write-optimized row delta while serving OLAP from compressed main → true HTAP. Pure columnar suffers per-write decompress/recompress; pure LSM optimizes writes but read-merge of many sorted runs kills scan latency + has no native columnar form. [## 21]

8

Delta-store physical format

Chosen

Row format + per-row validity bitmap (DeltaStore)

Rejected

Columnar delta; mini-row-groups

When the rejected choice is right

A columnar (mini-row-group) delta wins when even "recent" data is scan-dominant and rarely point-queried — e.g. a streaming-ingest analytics store where the delta is read by dashboards before it merges; SQL Server's columnstore "delta rowgroups" compress once they fill, biasing toward scan over point write.

Why: Recent writes are point-write dominated → row format gives O(1) in-place MVCC version creation + cheap point lookup before merge. Columnar delta would re-encode on every insert. Validity bitmap marks GC'd/superseded rows without compaction. [## 21]

9

Row group size

Chosen

65 536 rows (RowGroup.n_rows default)

Rejected

8 192; 1 048 576; per-table tunable only

When the rejected choice is right

A larger group (Parquet defaults ~1 M rows/row-group, ~128 MiB) wins for cold, write-once data-lake files where per-group metadata must be amortized over huge files and pruning granularity matters less than fewer file-footer reads; smaller (8 Ki) wins under very high delete/update churn needing fine reclaim.

Why: Unit of column segments, zone maps, delete vectors, encoding selection, merge granularity. 64Ki balances pruning/parallelism granularity vs per-group metadata overhead; fits BitPacked/Dictionary code widths cleanly. Too small → metadata bloat + weak compression; too large → coarse pruning + long merge stalls. [## 17][## 22]

10

Encoding family

Chosen

Plain, Dictionary, Rle, BitPacked, FrameOfReference (Encoding), per-column selection from ColumnStats

Rejected

Single fixed encoding; general byte compressor (zstd/lz4) only; PFor/Gorilla

When the rejected choice is right

A general block compressor (zstd) wins on cold/archival data where storage cost dominates and scans are rare, so a 2–4× ratio gain over lightweight encodings outweighs the full-block decompress penalty; Gorilla wins specifically for float time-series (XOR delta) that FrameOfReference handles poorly.

Why: Lightweight encodings decode O(values), SIMD-friendly, predicate-pushable (dict codes, FoR base) — block compressors require full-block decompress before any access, defeating late materialization + zone-map skipping. Compressor picks smallest valid encoding per segment from stats. [## 18]

11

Scan pruning structure

Chosen

Per-segment ZoneMap{min,max,null_count}

Rejected

Secondary B-tree per column; bitmap indexes; bloom filters

When the rejected choice is right

Bloom filters / secondary indexes win on high-cardinality equality lookups over unsorted data where min/max zone maps prune nothing (the value lies within [min,max] of every segment) — exactly the needle-in-haystack point-on-non-PK case; bitmap indexes win for low-cardinality categorical filters in a star-schema warehouse.

Why: Zone maps are O(1)-per-segment metadata enabling min/max segment skipping with near-zero storage + maintenance cost (rebuilt at merge). Full secondary indexes cost storage + write maintenance against an immutable main; bloom filters help equality only, deferred. [## 19]

12

Durability protocol

Chosen

WAL + ARIES (Wal, Recovery: analysis→redo→undo, CLRs, pageLSN/recLSN)

Rejected

Redo-only (no-undo, force-at-commit); shadow paging

When the rejected choice is right

Redo-only / no-steal wins for an in-memory engine where the working set always fits RAM (Redis AOF, VoltDB command log) so dirty pages are never stolen and undo is unneeded; shadow paging (LMDB copy-on-write B-tree) wins when a simple, mmap-friendly, single-writer crash model is preferred over log complexity.

Why: ARIES allows steal/no-force (dirty pages flush before commit, committed pages need not) → max buffer-pool flexibility; CLRs make undo idempotent across repeated crashes. Redo-only forces no-steal (buffer pressure) or force-at-commit (write amp); shadow paging fragments + can't do fine-grained logging. [## 15]

13

Commit durability batching

Chosen

Group commit (Wal group commit + flush(lsn))

Rejected

fsync-per-commit; async/no-flush

When the rejected choice is right

Async / periodic flush wins for a cache or analytics-ingest tier where bounded data loss on crash is acceptable in exchange for maximum throughput (Kafka acks=1, Redis default); per-commit fsync wins for a low-throughput ledger where every commit must be independently durable and batching latency is unacceptable.

Why: Group commit amortizes one fsync over many concurrent commits → OLTP throughput without sacrificing the log-before-data invariant. Per-commit fsync caps TPS at device fsync rate; async loses the D in ACID. [## 15]

14

Default isolation level

Chosen

Snapshot Isolation (IsolationLevel::SnapshotIsolation); ReadCommitted available

Rejected

Serializable (SSI/2PL); ReadCommitted default

When the rejected choice is right

Serializable (SSI) wins where write-skew anomalies are unacceptable — financial constraints, double-booking, inventory invariants; Postgres offers SSI for exactly these. Read Committed default wins for high-contention OLTP that tolerates non-repeatable reads and wants shorter snapshots / less version retention (Oracle, MySQL default).

Why: SI is the natural fit for MVCC version chains: each txn reads a consistent Snapshot{xmin,xmax,active} with no read locks → readers never block writers (HTAP requirement). SSI/2PL add lock manager + abort complexity beyond single-node v1 scope; RC default would surprise analytical readers. [## 16]

15

Primary index structure

Chosen

B+Tree (BTree) over RowId, ordered keys

Rejected

Hash index; LSM index; ART/trie

When the rejected choice is right

A hash index wins for a point-only KV workload with no range queries (memcached-style), giving O(1) lookup without tree-height latency; an LSM index wins when the index itself is write-saturated and sequential-write amortization beats in-place B+Tree node updates; ART wins for dense string keys needing prefix compression.

Why: B+Tree serves both point lookup AND range scan (OLAP range predicates) with crash-safe page writes; ordered leaves enable index range scans. Hash gives point-only (no ranges); LSM index duplicates the delta/main merge problem; ART deferred (string-key-specialized, complex page format). [## 14]

16

Vectorization unit

Chosen

ColumnBatch of 1024–2048 values + SelectionVector

Rejected

Tuple-at-a-time (Volcano); whole-column materialization

When the rejected choice is right

Tuple-at-a-time (Volcano) wins for OLTP-only point queries returning 1 row, where batching overhead exceeds benefit and the simpler iterator model eases nested-loop joins; whole-column (full materialization) wins inside a query compiler (HyPer/Umbra data-centric codegen) that fuses operators and eliminates per-batch boundaries entirely.

Why: Batch-at-a-time amortizes per-call overhead + fits L1/L2, enabling SIMD kernels and late materialization (only selected rows decoded). Tuple-at-a-time has crippling per-row dispatch overhead; whole-column blows cache + decodes pruned data. [## 20]

17

Deletes against main

Chosen

Delete vector (per-row-group bitmap on MainStore), applied at scan, physical removal at next merge

Rejected

In-place delete (rewrite segment); tombstone rows

When the rejected choice is right

In-place delete wins for a mutable row-store with no immutability constraint (a classic heap) where deletes are rare and immediate space reclaim matters; per-row tombstone rows win in an LSM where deletes are just another sorted-run write reconciled at compaction (RocksDB).

Why: MAIN is immutable → deletes can't mutate compressed segments. Delete vector is O(1) bitmap set, applied as a selection-vector mask at scan time; physical reclaim happens during the merge that rebuilds the row group. In-place delete forces segment rewrite per delete. [## 21][## 22]

18

Delta→main conversion timing

Chosen

Background TupleMover (async, MVCC-safe atomic swap under concurrent readers)

Rejected

Synchronous on-write merge; size-triggered foreground merge

When the rejected choice is right

Synchronous/foreground merge wins for a bulk-load-then-query pattern (ETL job, COPY into a warehouse) where there are no concurrent OLTP writers to stall and a single foreground compaction gives the most compact result fastest; it also removes background-thread scheduling and the pinned-snapshot leak risk.

Why: Background mover keeps OLTP write latency off the encode/compress critical path; atomic RowGroup swap lets readers proceed against the old main until the new one is durable + visible. Synchronous merge stalls writers; foreground merge causes latency spikes. [## 22]

19

Torn-page / corruption detection

Chosen

CRC32C checksum per page (and per column segment)

Rejected

No checksum (rely on WAL); xxHash; SHA-256

When the rejected choice is right

No checksum wins for an in-memory or ephemeral store where on-disk corruption is out of the threat model and the per-read CRC cost is pure overhead; a cryptographic hash (SHA-256/BLAKE3) wins when the data directory is an adversarial-tamper boundary (content-addressed, signed artifacts) where collision resistance, not just bit-rot detection, is required.

Why: CRC32C has hardware acceleration (SSE4.2/ARMv8 CRC) → cheap per-page verification on read, detects torn writes + bit rot before they propagate into recovery. WAL alone can't tell a torn page from a valid one at startup; SHA-256 cryptographic overkill; xxHash not torn-write-standard. [## 24]

20

File layout

Chosen

File-per-segment (FileManager segment files, SegmentId)

Rejected

Single monolithic file; one file per table

When the rejected choice is right

A single monolithic file wins for an embedded, copy-as-one-file database (SQLite, LMDB) where "the database is one file" is a usability and backup requirement and the FD/inode budget must stay at 1; file-per-table wins when per-table DROP/TRUNCATE must reclaim space instantly (one unlink).

Why: Segment files let the TupleMover write a new columnar segment + atomically publish (rename/swap) without rewriting unrelated data, and allow per-segment fsync + reclaim. Single file forces in-place overwrite + complicates atomic main swap; file-per-table too coarse for segment-granular GC. [## 13][## 22]

21

Correctness testing

Chosen

datadriven golden tests + differential testing vs SQLite (OLTP) & DuckDB (OLAP) on identical datasets

Rejected

Hand-written assertions only; reference-impl-free

When the rejected choice is right

Hand-written assertions win when no comparable reference engine exists (a genuinely novel operator/semantics) so a differential oracle is unavailable, or in early prototyping where the spec is still in flux and golden files churn faster than they catch bugs.

Why: Differential testing catches semantic divergence (visibility, aggregation, NULL handling) against mature engines that have no shared code → high-signal oracle. datadriven keeps test corpus declarative + diffable. Assertions-only misses unknown-unknowns. [## 25]

22

Fuzzing

Chosen

cargo-fuzz (libFuzzer) on decoders + page/WAL parsers

Rejected

No fuzzing; AFL; proptest only

When the rejected choice is right

AFL++ wins when fuzzing a native C/C++ dependency outside the Rust toolchain (where libFuzzer integration is awkward) or when persistent-mode/fork-server throughput on a large binary matters more than in-process speed; proptest-only suffices when inputs are structured values, not raw bytes.

Why: Decoders + page parsers consume untrusted on-disk bytes → libFuzzer coverage-guided fuzzing finds panics/OOB/UB the type system can't. cargo-fuzz integrates with the Rust toolchain + sanitizers. proptest complements (structured props) but doesn't explore raw-byte corpora as deeply. [## 25]

23

Benchmarking

Chosen

criterion (micro) + TPC-C-style OLTP mix & SSB/TPC-H-style OLAP scans (macro), with regression gates

Rejected

ad-hoc timing; nightly #[bench]

When the rejected choice is right

The unstable #[bench] harness wins for a nightly-only project already pinned off stable, where its zero-dependency integration with cargo bench beats pulling in criterion; ad-hoc timing suffices for a one-off profiling spike that will never enter CI.

Why: criterion gives statistically rigorous, regression-gated microbench numbers (latency distributions, not means); TPC-C + SSB exercise the HTAP mix end-to-end. Ad-hoc timing is noisy; unstable-only #[bench] breaks MSRV-stable CI. [## 25]

24

Dependency policy

Chosen

Minimal; NO third-party storage-engine/columnar crate (no rocksdb/sled/arrow/parquet/datafusion)

Rejected

Build on RocksDB/sled; use Arrow + Parquet + DataFusion

When the rejected choice is right

Building on Arrow + Parquet + DataFusion wins for a production analytics product where time-to-market and ecosystem interop (Arrow Flight, Parquet data lakes) dominate, and reimplementing encodings/zone maps would be reinventing a battle-tested wheel; RocksDB wins when a proven LSM KV layer is the goal, not the learning.

Why: The point is a from-scratch engine — pulling a storage crate defeats the exercise and hides the invariants under test. Allowed deps limited to leaf utilities (e.g. crc32c, criterion dev-dep, libfuzzer-sys dev-dep). [project identity]

25

CI & MSRV

Chosen

GitHub Actions: build + clippy (deny warnings) + test + miri (unsafe) + fuzz-smoke, pinned MSRV 1.78

Rejected

No CI; latest-stable-only; no miri

When the rejected choice is right

Latest-stable-only (no pinned MSRV) wins for an application or internal service with no external library consumers, where always tracking the newest compiler unlocks features and the support-window cost of MSRV is unjustified; dropping miri is acceptable for a 100%-safe-code crate.

Why: CI gates every merge; clippy -D warnings keeps the unsafe-adjacent code disciplined; miri checks the page/buffer unsafe blocks for UB; MSRV 1.78 pinned so byte-layout code stays portable across the support window. [## 12]

26

License

Chosen

MIT OR Apache-2.0 (dual)

Rejected

GPL; proprietary; MIT only

When the rejected choice is right

GPL/AGPL wins for a product monetized via dual-licensing or one that must prevent proprietary forks (MySQL, MongoDB SSPL); a proprietary license wins for a closed commercial engine where source disclosure is itself the competitive risk.

Why: Dual MIT/Apache-2.0 is the Rust-ecosystem default → maximal downstream embeddability (the engine is embeddable) + Apache patent grant. GPL deters embedding; proprietary blocks reuse.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alternative 1 — Single columnar store with an in-memory write buffer (no persistent row tier)

writes ──> in-RAM write buffer (columnar mini-blocks, optimistic MVCC)
               | flush on size
               v
        immutable columnar row groups (the ONLY persistent form)
               ^
        reads ─┘  point + scan both hit columnar (point = gather across segments)

Regime where it wins: bulk-load-then-analyze workloads with negligible high-rate point updates — interactive analytics over files/data frames, ELT pipelines. The row tier is dead weight when "recent" data is also scan-dominant; removing it halves storage and eliminates the merge's row→column pivot.

Real system that embodies it: DuckDB (columnar end-to-end, optimistic MVCC, transient write buffer).

Why rejected: §1 makes high-rate OLTP point writes a first-class goal; a point get/update on a columnar store gathers across N segments and pays decode on the write path — Performance Engineering quantifies the row layout winning point access by reading ~20× fewer bytes. Without a row delta, every point update would decompress+recompress a block (the exact cost ADR-7 rejects).

Alternative 2 — LSM-tree storage with columnar SSTables

writes ──> in-memory memtable (row/KV) ──flush──> L0 SSTables ──compact──> L1..Ln
                                                       |                     |
                                            (each SSTable: columnar blocks + min/max)
                                                       v
                            reads merge overlapping sorted runs across levels (+ bloom filters)

Regime where it wins: write-saturated workloads where sequential-write amortization is the binding constraint and reads tolerate merging several sorted runs; very large datasets that must spill to disk with tiered compaction managing hot/cold automatically.

Real system that embodies it: RocksDB / LevelDB (LSM); ClickHouse MergeTree is the columnar-SSTable + background-merge analogue (and a reference impl, R5).

Why rejected: a scan must merge overlapping runs across all levels, so scan latency degrades with run count — the opposite of the bounded, single-pass columnar scan the OLAP target demands (§4). LSM read amplification + compaction stalls violate the p99 write-latency target unpredictably (ADR-7 rationale). The delta/main model is the columnar-HTAP analogue of LSM compaction (§2.4, project 68) but with exactly one read-time run (delta+main), not a tower.

Alternative 3 — Two separate systems (OLTP row store + OLAP column store) joined by ETL/CDC

   OLTP row DB  ──change-data-capture / nightly ETL──>  OLAP column DB
   (Postgres)                                            (warehouse)
        |                                                     |
   point reads/writes                                    analytical scans

Regime where it wins: when OLTP and OLAP have wildly different SLAs, hardware, and teams, and minutes-to-hours of analytical staleness is acceptable — the classic separation that lets each engine be best-of-breed and scale independently. Operationally simplest when the two already exist.

Real system that embodies it: the canonical operational-DB + data-warehouse split (e.g. Postgres/MySQL replicated into Snowflake/Redshift/BigQuery via CDC such as Debezium).

Why rejected: this is precisely the architecture §2.2 identifies as the problem HTAP exists to solve — the ETL gap (stale analytics), 2× storage, and 2× operational burden. The entire thesis of this engine is one copy of data, two access paths under one MVCC clock (§6.2, MM2); accepting two systems abandons the learning objective and the freshness guarantee that motivates the project.
