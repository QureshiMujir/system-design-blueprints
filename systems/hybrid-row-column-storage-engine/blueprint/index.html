317 — Hybrid Row/Column Storage Engine

Goal: Build, from scratch in Rust, a single-node HTAP storage engine that keeps data in BOTH a write-optimized row format and a read-optimized columnar format, unified by a delta/main architecture and MVCC: a slotted-page row store + B+Tree, a WAL with ARIES crash recovery, snapshot-isolation MVCC with version chains + vacuum, a compressed columnar main (dictionary/RLE/bit-packing/frame-of-reference encodings + zone maps), a vectorized scan/ aggregate path, a background tuple mover that merges delta into columnar main MVCC-safely, and a hybrid access-path router. Differential-tested against SQLite/DuckDB and crash-tested with fault injection. It is a storage engine, not a SQL parser/optimizer (#21/#52/#316) or a distributed/replicated layer (#36/#86/#102).

1. Goal

Build a from-scratch, single-node, embeddable HTAP storage engine in Rust that keeps every table in BOTH a write-optimized row store and a read-optimized column store, unified by a delta/main architecture under MVCC snapshot isolation, made durable by a WAL + ARIES recovery path, and exposed as a library plus the hydb CLI.

1.1 What is built (precise definition)

A persistent storage engine — no SQL, no network — that ingests typed rows, indexes them, scans them as compressed columns, and survives crashes. Concretely, eight load-bearing subsystems:

# Subsystem Crate(s) Function
1 Slotted-page row store + buffer pool + B+Tree primary index hy-page, hy-row, hy-index OLTP point insert/get/update/delete by primary key
2 WAL + ARIES crash recovery + checkpoint hy-wal log-before-data durability; analysis→redo→undo with CLRs
3 MVCC snapshot isolation: version chains + vacuum GC hy-txn in-tuple txn_min/txn_max/next_version; SI visibility
4 Columnar MAIN store: RowGroup (65 536 rows) → ColumnSegment with light-weight encodings + zone maps hy-col OLAP scans/aggregations over compressed, immutable columns
5 Row-format DELTA store absorbing recent writes + validity bitmap hy-store fast in-place MVCC writes before columnar compaction
6 Unified read path merging DELTA (row) + MAIN (column) under a Snapshot hy-store one consistent view for both get and scan
7 Background TupleMover: delta→main merge, row→column convert, atomic swap, version GC hy-store MVCC-safe compaction under concurrent readers
8 Access-path router + cross-format crash recovery hy-store, hy-wal route point→row+delta, scan→column+delta; rebuild MAIN from WAL + row/delta

Vectorized scan path: predicates produce a SelectionVector; operators touch only surviving rows (late materialization); ColumnBatch (1024–2048 values) is the vectorization unit; SUM/COUNT/MIN/MAX/AVG + GROUP BY hash aggregation.

2. Why Build This

Most engineers have built either a row store or a column store. This project forces both into one engine, sharing one copy of data under one MVCC clock — the hardest part of every real HTAP system, and the part tutorials never reach.

2.2 Why hybrid storage matters — historical + architectural arc

  • Row vs column "wars" (2005-2012). Row stores (Postgres, MySQL, Oracle heap) win OLTP point writes; column stores win OLAP scans by reading only projected columns + compressing them. Neither wins both → enterprises ran two systems + nightly ETL → stale analytics, double storage, double ops.
  • C-Store / Vertica (2005). Read-optimized column store with a Writeable Store (row-ish) feeding a Read-optimized Store via a "Tuple Mover" — the direct ancestor of this design's DeltaStore → MainStore → TupleMover pipeline.
  • SAP HANA delta/main (2010s). The model we follow: writes hit a row-format delta, a background delta merge compresses delta into an immutable columnar main, deletes recorded in a delete vector. HybridTable is HANA's delta/main, single-node.
  • HyPer / Umbra (TU München). Proved one engine can serve OLTP + OLAP at full speed via MVCC + vectorized/compiled scans + Data Blocks (compressed columnar blocks with min/max — our ZoneMap + RowGroup). Direct lineage of the vectorized scan + zone-map pruning here.
  • Oracle Database In-Memory "Dual-Format" (2014). Same rows kept in row format on disk and a columnar in-memory mirror, kept consistent transactionally — the literal "two formats, one truth" idea.
  • SingleStore, TiDB+TiFlash, ClickHouse + OLTP front-ends. Modern productions where a row tier absorbs writes and a column tier serves analytics; this project is the single-node kernel those wrap in a network + distribution layer. HTAP exists because the ETL gap and the 2×-storage/2×-ops tax of split systems are unacceptable for operational analytics — the cost being engine complexity this blueprint makes you own.

2.3 Engineering muscles built

  • Byte-layout precision (Page, SlottedPage, TupleHeader, packed ColumnSegment); buffer-pool mechanics (clock evict, pin/dirty, RAII guard); concurrency (SI, version chains, GC under live snapshots, atomic main-swap); crash-consistency (log-before-data, pageLSN/recLSN, idempotent redo, CLR undo, torn-page); compression/decode (smallest-valid encoding, SIMD bulk decode, late materialization); perf engineering (vectorized ColumnBatch kernels, hash agg, regression gates); Rust-specific (unsafe-adjacent checked layout, borrowed Tuple<'a> lifetimes, exhaustive WalRecord match). 2.5 Calibration value

A single-engine HTAP store is a principal-level capstone: it composes B+Tree, WAL/ARIES, MVCC, columnar compression, and vectorized execution and then adds the part none of them have alone — keeping a row format and a compressed column format transactionally consistent, recoverable, and GC-correct under concurrency. Completing it demonstrates you can reason about a full storage subsystem end-to-end, the bar for designing or owning a production database kernel.

2.6 What Mastery Looks Like

After building this engine, the reader holds these competencies, each cemented by a named phase:

  • Crash-recovery discipline — derive ARIES analysis→redo→undo from first principles, reason about pageLSN/recLSN/CLR idempotency, and explain why repeat-history is required (Phase 3 §15; Phase 12 §24).
  • MVCC visibility math — write the visible(h, snap) predicate by hand, prove ≤1 visible version per chain, and locate a phantom-read or write-skew bug from a version-chain dump (Phase 4 §16).
  • Columnar encoding & decode performance — choose the smallest valid Encoding from ColumnStats, hand-write a SIMD-friendly bit-pack/FoR decoder, and explain why decode speed (not ratio) bounds scan latency (Phase 6 §18; Phase 8 §20).
  • Zone-map pruning correctness — state and defend the zero-false-negative invariant, and debug a silently-dropped result row down to a stale min/max (Phase 7 §19).
  • The HTAP fusion — reason about one logical row living in two physical layouts under one MVCC clock, and prove the no-double / no-loss invariant across the delta↔main boundary (Phase 9 §21; Phase 10 §22).
  • Lock-free reader / atomic-swap concurrency — design an ArcSwap-published immutable main that lets a background merge run under full read load with bounded reader stall (Phase 10 §22).
  • Access-path reasoning — build a stats/rule router that routes point→row+delta and scan→column+delta, and tie a mis-route to a perf (never correctness) regression via q-error (Phase 11 §23).
  • Differential & fault-injection verification — gate correctness against SQLite/DuckDB oracles and durability against per-WalRecord crash injection, and minimize a failing case to a deterministic fixture (Phase 13 §25).

3.2 Cross-Cutting Boundaries

  • Trust boundary — on-disk bytes (pages, WAL records, column segments) and inbound rows/keys are UNTRUSTED. Every decoder (SlottedPage slot directory, WalRecord parser, EncodedColumn decoders, BTreeNode layout) bounds-checks lengths/offsets/codes before deref; corrupt input -> ErrorKind::Corrupt, never UB. CRC/torn-page checks gate page acceptance. Rust chosen precisely to keep this hot path memory-safe.
  • Concurrency boundary — foreground readers (snapshot-stable) vs foreground writers (append to DELTA + WAL) vs the background TupleMover (delta->main merge). MVCC means readers never block writers; the TupleMover publishes a NEW immutable MainStore epoch via an atomic pointer swap, so in-flight scans keep their old RowGroup set until they finish. No reader sees a half-merged main. Lock scope: short latches on BufferPool frames + Wal tail; long-lived state is snapshot-versioned, not locked.
  • Persistence boundary — the WAL is the single durability source of truth (log-before-data). BufferPool pages and hy-col column segments are checkpointed derived state: recoverable by replaying WAL onto the last checkpoint. A committed txn = its Commit record flushed to WAL; everything else (dirty pages, column flushes) is best-effort-eager, recovery-mandatory.

Each later phase references these boundaries: Phase 3 (WAL) owns persistence; Phase 4 (MVCC) owns concurrency; Phase 13 (fuzzing/differential) attacks the trust boundary.

3.3 Component Responsibilities (one per box)

hy-page — BufferPool / FileManager / PageGuard

The byte-and-frame substrate, the only code touching the filesystem. FileManager maps SegmentId→files + aligned 4 KiB I/O; BufferPool is a fixed frame table with clock eviction + per-frame pin/dirty; fetch(PageId)→PageGuard pins, unpins on Drop. Every persistent crate mutates state exclusively through PageGuards, so durability/eviction policy lives here. Invariant: a dirty page is never evicted before its pageLSN is durable in the WAL (flush-on-evict hook); pinned frames never evicted. Phase 0 (shell) + Phase 1 (real).

hy-row — RowStore / SlottedPage / Tuple

The write-optimized row heap and physical home of DELTA. SlottedPage = slot directory from front + payloads heap-from-end; RowStore is a heap addressed by RowId{page,slot} doing insert/get/update-delete-as-new-versions (MVCC, never in-place); TupleHeader carries in-tuple txn_min/txn_max/next_version/null_bitmap, decode driven by the Schema. Invariant: a RowId is stable for a version-chain entry's life (compaction relocates payload, never invalidates a live RowId). hy-txn interprets the header; hy-store uses it as DELTA backing.

hy-index — BTree

Primary B+Tree (primary-key bytes → RowId): O(log n) point lookup + ordered range, node split/merge over PageGuards with WAL-logged structural changes. lookup(key,&Snapshot) returns the chain-head RowId; visibility is resolved separately by hy-txn walking next_version. Invariant: leaf key order == primary-key order; the index holds the chain entry point, never the visible version. Phase 11's router uses it for the point path.

hy-wal — Wal / Recovery

Durability + crash recovery. Wal = append-only log + group commit + flush(lsn); WalRecord enumerates every transition (Begin/Insert/Update/Delete/Commit/Abort/Clr/ColumnFlush/Checkpoint). Recovery is ARIES three-pass: analysis (rebuild ATT+DPT from last Checkpoint), redo (repeat history from recLSN, pageLSN-gated), undo (roll back losers with Clr). Invariant: log-before-data + monotonic Lsn — no committed effect lost, no uncommitted survives. ColumnFlush lets recovery rebuild the column store (Phase 12).

hy-txn — TxnManager / Snapshot / visibility / Vacuum

MVCC under snapshot isolation. TxnManager is the id + commit-ts oracle + active-set; begin captures Snapshot{xmin,xmax,active,ts}, commit assigns a Timestamp + writes Commit, abort triggers undo. visible(&TupleHeader,&Snapshot) is the SI predicate; updates/deletes link a NEW version via next_version; Vacuum reclaims versions older than the oldest live snapshot. Invariant: a committed txn is atomic+durable; a snapshot's visible set is immutable for its lifetime. IsolationLevel = SnapshotIsolation | ReadCommitted. Underpins the unified read path (Phase 9) + merge MVCC-safety (Phase 10).

hy-col — RowGroup / ColumnSegment / Encoding / ZoneMap / vectorized reader

The read-optimized immutable columnar MAIN. A RowGroup (65,536 rows) holds one ColumnSegment/column carrying its Encoding, ZoneMap{min,max,null_count}, n_rows, null_count, SegmentId; Compressor picks the smallest valid encoding from ColumnStats; ColumnReader::scan(&SelectionVector,&mut ColumnBatch) decodes only survivors (late materialization). Invariant: MAIN is immutable — a published segment is never mutated, deletes go to a delete vector applied at scan. ZoneMap skipping (Phase 7); O(values) SIMD decode (Phase 8); targets dict/RLE 4–20×, bit-pack/FoR 2–8×.

hy-store — HybridTable / DeltaStore / MainStore / TupleMover / router

The HTAP unifier. HybridTable composes RowStore+BTree (point), DeltaStore (row writes + validity bitmap), MainStore (immutable columnar + delete vector), Wal, TxnManager. The AccessPath router maps an op to RowLookup/IndexLookup/ColumnScan/DeltaScan via rule + TableStats; get/scan both merge DELTA(row)+MAIN(column) under one Snapshot; the TupleMover background-merges DELTA into compressed MAIN (build, encode, write, atomic swap, GC) MVCC-safely. Invariant: one Snapshot governs both halves of every read → a consistent point-in-time view. Phases 9–12; the engine's public face.

hy-catalog — Schema / TableFormat / Stats

Metadata + policy. Schema (ColumnDef→DataType) drives all encode/decode; TableFormat declares row-vs-column placement + row-group size; TableStats/ColumnStats (cardinality, min/max, null fraction, histograms) feed both the Compressor and the router. Invariant: stats are advisory — wrong stats degrade plan/compression, never correctness (q-error tracked, not trusted for safety). Pure descriptive metadata, no FS/concurrency state.

hy-cli — the hydb binary

Operator-facing entry point: load insert get scan aggregate analyze compact checkpoint recover bench. Thin — parses args, opens a HybridTable, drives the same API tests use (no engine logic). Invariant: every subcommand maps 1:1 to a public API, never a privileged path. Used end-to-end from Phase 0's smoke test through Phase 13's HTAP benchmarks + fault-injection recovery.

4. System Constraints

Single-node, embeddable. No network, no replication, no distributed txn coordinator, no NUMA-awareness budget (treat as one socket; thread-pinning optional, not modeled). Constraints below are the contract every phase tests against; violations are regressions gated in Phase 13 (## 25).

4.2 Concurrency & isolation constraints

  • Default SnapshotIsolation, ReadCommitted per-Transaction; Serializable NOT provided (no SSI/predicate locks). Readers never block writers and vice versa (MVCC); writer/writer on a RowId → first-committer-wins, loser aborts. MAIN immutable — scans during a tuple-mover swap see a consistent pre/post-swap MainStore via atomic pointer swap (no reader latch across merge). One WAL append path (LogWriter serializes Lsn); group commit batches fsync (latency floor ≈ fsync ~50–500 µs SSD).

4.3 Memory & storage budget

  • No GC (Rust). Steady-state heap = pool ceiling + dict/zone-map metadata + per-txn active-set arrays + transient ColumnBatch buffers (≤ scan parallelism × batch width × col width). Per-row-group metadata ≤ 1% of compressed payload. Row store + B+Tree + WAL + segments are separate FileManager files; WAL fsync is the only synchronous commit-hotline write. Delete vector 1 bit/row (8 KiB/65_536-row group), applied at scan, purged at next merge.

4.4 Correctness invariants (non-negotiable)

  • Log-before-data (pageLSN ≤ flushed WAL Lsn before a dirty page flushes). Redo idempotent via pageLSN, undo via CLRs; repeated crashes converge. Unified read path merges DELTA+MAIN under one Snapshot, each row exactly once (delta shadows main per RowId). Tuple mover MVCC-safe (discards only versions < oldest live Snapshot). MAIN fully rebuildable from WAL + row/delta (Phase 12, ## 24) — no unique unrecoverable state.

4.5 Explicit non-budgets (out of scope)

  • No SQL parser/optimizer (21/52/316) — rule+stats router only. No network (33/64), no distribution/replication (36/86/102), no distributed txn coordinator (100/101). No NUMA/GPU/encryption-at-rest; no secondary indexes beyond ZoneMaps + the primary B+Tree. Single embeddable process: programmatic API + hydb CLI.

6. Design Principles

Fifteen non-negotiable principles. Each is a global invariant enforced across all crates; later phases (## 12–## 25) reference these by bold name. Violations are not "bugs" — they are correctness-class regressions caught by Phase 13 (## 25).

6.1 The WAL is the source of truth

  • Rule: no effect is committed until its log record is durable in hy-wal; WalRecord::Commit{txn,ts} reaching disk (Wal::flush(lsn)) is the only durability event (pages/segments/nodes are caches). Log-before-data (§6.6), Commit flushed before ack, group commit batches flushes; durability == "is the LSN flushed?", backup = WAL + last checkpoint. Tradeoff: every commit pays ≥1 fsync (amortized ~µs/txn) vs. zero recovery ambiguity. Violation: ack before Commit flushed → silent lost-update (ACID-D broken); or flush a page ahead of its log → unrecoverable corruption.

6.2 One logical copy, two physical layouts

  • Rule: DeltaStore (row) and MainStore (column) are two physical projections of one logical row set; every live row is in exactly one — visible(delta) XOR visible(main) per RowId under any Snapshot; the TupleMover (§6.13) moves rows as one atomic transition; count(*)=live(delta)+live(main) always (divergence is a hard alarm). Tradeoff: ~1.1–1.4× storage during the delta window vs. HTAP read speed (point→row, scan→column). Violation: a row in delta and re-encoded into main → double-counted / resurrected — the most dangerous merge bug, guarded by §6.13.

6.3 MAIN is immutable

  • Rule: RowGroup/ColumnSegment bytes are write-once — deletes set a per-group delete-vector bit, updates = delete-in-main + new-version-in-delta, physical removal only at next merge. Immutability → latch-free shareable segments (scan holds a ref; merge writes new segments + atomic pointer swap, §6.13), content-addressable/mmap-safe/checksummed-once. Tradeoff: deleted-but-unmerged rows waste scan cycles (O(1)/row skip) until re-merge. Violation: mutate a segment a reader is mid-scan over → torn read / use-after-free → SI broken, possible UB.

6.4 MVCC: never overwrite, always version

  • Rule: updates/deletes create a new tuple version (prior preserved with txn_max stamped); RowStore/DeltaStore append, never destroy a potentially-visible version; chain links via in-tuple txn_min/txn_max/next_version (newest→oldest); version count is monitored (§6.9), Vacuum reclaims not the writer. Tradeoff: write amplification + dead-version bloat vs. lock-free readers. Violation: overwrite a version still visible to an open Snapshot → reader sees a future value → SI violated, non-repeatable read.

6.5 Snapshot isolation is the contract

  • Rule: visibility is a pure function visible(h,snap)->bool — no I/O, global state, or clock read; same (TupleHeader,Snapshot) ⇒ same answer on any thread, in normal ops and recovery. Visible iff txn_min committed-before-snap AND ∉ snap.active AND (txn_max==0 OR committed-after-snap); the commit-ts oracle is read once at snapshot time (frozen into snap.active/snap.ts), so delta and column paths agree by construction (§6.2). Tradeoff: purity forbids caching commit state inside the predicate. Violation: branch on wall-clock/live-oracle → two readers at one Snapshot disagree → SI gone, differential tests diverge.

6.6 Log-before-data (WAL protocol)

  • Rule: a page is flushed only after every WAL record on it is durable (page.lsn ≤ Wal.flushed_lsn), enforced at the BufferPool eviction/flush boundary; PageHeader.lsn tracks the last applied record, checked against the WAL flushed watermark. Tradeoff: flush-ordering constraint vs. always-replayable history. Violation: flush a page whose log isn't durable → effect with no log record → redo can't reproduce, undo can't reverse → unrecoverable.

6.7 Recovery is idempotent

  • Rule: ARIES analysis→redo→undo yields the identical final state run once or interrupted N times — redo gated by pageLSN (skip if record.lsn ≤ page.lsn), undo writes CLRs (Clr{txn,undo_next}) so re-undo resumes; repeated hydb recover is safe + convergent (restartable, not one-shot). Tradeoff: CLR volume + per-page LSN checks vs. crash-during-recovery safety. Violation: redo onto an already-applied page (no pageLSN gate) → double-applied increment; undo without CLRs → re-crash re-reverses reversed work.

6.8 Crash-only

  • Rule: the engine may die at any instruction and must recover to a consistent committed state — no graceful-shutdown path ("clean shutdown" = checkpoint + crash); all multi-step changes are log-protected (§6.6) or atomic-swap (§6.13), partial artifacts detected + discarded at recovery. Tradeoff: no shutdown shortcuts; every transition crash-analyzed. Violation: rely on a destructor/flush-on-exit to persist the active set or delta index → kill -9 → state lost → inconsistent delta+main.

6.9 Bounded resources

  • Rule: every unbounded-by-default structure has a hard cap with a defined back-pressure action:
Resource Cap (default) Trigger Action
BufferPool frames configured N pages all pinned/dirty clock eviction; flush dirty (§6.6)
DeltaStore size e.g. 256 MiB / 1M rows high-water mark schedule TupleMover merge
Version chain length e.g. 64 / oldest-snap age exceeds bound trigger Vacuum
Group-commit buffer e.g. 1 MiB / 2 ms full or timeout force flush
  • Tradeoff: caps add merge/vacuum/eviction work under load vs. bounded memory + predictable latency. Violation: unbounded delta dwarfs main → full row-scan, OOM; unbounded chains → O(versions) visibility walk, point lookups stall.

6.10 Vectorize the scan path, point-optimize the write path

  • Rule: two physically distinct hot paths — scan/aggregate column-at-a-time (ColumnBatch 1024–2048, SelectionVector, branch-light SIMD); point get/insert/update row-at-a-time (BTree + RowStore/DeltaStore); the AccessPath router (§22/§23) is the only meeting point (misroute = perf bug, never correctness, §6.14). Tradeoff: two execution styles vs. neither compromised (one-size row-at-a-time loses ~10–50× on scans, pure-columnar loses on point writes). Violation: aggregates row-at-a-time over decoded tuples → 10–50× slower, blows OLAP SLOs.

6.11 Encodings decode SIMD-friendly and losslessly

  • Rule: every Encoding round-trips bit-exactly (decode(encode(x))==x, incl. NULLs); decode O(values), branch-minimal, contiguous-vectorizable; Compressor picks the smallest valid from ColumnStats, correctness never depends on the choice (pure perf/space knob, re-encode yields identical values). Tradeoff: vectorizable-only forgoes exotic schemes vs. predictable ≥1 GiB/s/core decode. Violation: a FoR base/bit-width overflowing an outlier → silent corruption; non-O(values) decode → throughput collapses, fails §25 gates.

6.12 Zone maps never produce false negatives

  • Rule: a ZoneMap{min,max,null_count} may over-include (scan a non-matching segment) but never under-include — if a predicate could match any row, its zone map must not allow skipping it (min ≤ every non-null ≤ max, exact null_count, recomputed on merge; pushdown skips only when provably disjoint from [min,max], NULL-aware). Tradeoff: conservative pruning may scan more vs. guaranteed-correct results. Violation: a stale/too-tight zone map → a matching segment skipped → rows silently missing, undetectable without differential testing.

6.13 The tuple mover is invisible to correctness

  • Rule: the TupleMover changes only layout, never query results — for any Snapshot, scan returns the identical row set before/during/after a merge; the delta→main transition commits via one atomic pointer swap of MainStore (readers pin the pre-swap immutable main §6.3, swap all-or-nothing + WAL-logged ColumnFlush, GC only past the oldest live Snapshot §6.4); merges pause/throttle/abort with zero result impact. Tradeoff: atomic-swap + retained-versions vs. fully online lock-light merges. Violation: swap in new main while readers see absorbed delta rows → double/vanish (breaks §6.2); GC a needed version → use-after-free.

6.14 Observability by default

  • Rule: every merge/checkpoint/vacuum/eviction-storm/recovery emits structured telemetry — counters (rows merged, bytes reclaimed, segments zone-skipped, group-commit batch), histograms (commit latency, scan throughput, decode time), last-event timestamps — via hydb analyze; q-error of stats tracked to validate the router; "why is delta large / why no prune?" answerable from metrics, not a debugger. Tradeoff: instrumentation <1% on hot paths (sampled) vs. diagnosability. Violation: a silent merge → can't tell a stalled mover from a healthy one until delta overflows (§6.9) and latency cliffs.

6.15 Determinism and total enum coverage

  • Rule: all on-disk dispatch (WalRecord, Encoding, DataType, AccessPath, PageKind) is exhaustive match, no catch-all _ (a new variant is a compile error until handled); recovery/decode/visibility deterministic given inputs (no thread-order / HashMap-iteration dependence in observable results).
  • Tradeoff: more match arms / schema-evolution churn vs. compile-time guarantee that no on-disk case is silently ignored.
  • Violation: a _ => {} over WalRecord → a new record type silently dropped during redo → a class of committed changes never recovers, found only after data loss.

7. System Invariants

Hard rules that must hold at every observable point (commit boundary, crash, scan, merge). Each is named INV-*, asserted in debug_assert! on hot paths and full checks in --cfg slow_asserts test builds. Violation = data-loss/corruption bug, not a perf miss. Telemetry uses structured tracing spans; counters are exported by the engine's stats registry. "Detected" = how an automated invariant probe finds the breach; "Debug" = the methodology to localize it.

Conventions: pageLSN = PageHeader.lsn; flushedLSN = highest WAL LSN durably fsynced; oldest_live = min Snapshot.xmin over active txns; delete vector = per-RowGroup deleted-row bitmap; validity bitmap = per-DeltaStore-row live bit.

7.2 INV-WAL — log-before-data

  • Statement / Why: page P is written only if every WAL record on P is durable (P.pageLSN ≤ flushedLSN); else a crash leaves a logged-less effect → unrecoverable, and the pageLSN gate breaks redo idempotency.
  • Enforce / Detect: BufferPool flush calls Wal::flush(page.pageLSN) before write-out, gated on flushedLSN ≥ page.pageLSN; flush-hook debug_assert!; post-crash, a page with pageLSN > WAL max is a violation.
  • Telemetry / Recover / Debug: span wal.flush, counters wal.flush_forced_by_evict, page.writeout; the rule is the precondition (no write-time recovery); if detected post-crash, halt with Error::WalOrdering. Debug: dump (frameId, pageLSN, flushedLSN) per eviction.

7.3 INV-DUR — committed = durable

  • Statement / Why: before commit() returns success, Commit{txn,ts} is fsynced (LSN ≤ flushedLSN); an acked-then-lost commit breaks ACID-D. Group commit batches fsyncs but never acks ahead of the fsync.
  • Enforce / Detect: TxnManager::commit → append Commit → Wal::flush(commit_lsn) → publish ts + return; kill-after-ack fault injection (Phase 13) + differential vs SQLite on the op log.
  • Telemetry / Recover: txn.commit{txn,ts,commit_lsn,group_size}, hist commit.fsync_latency; redo replays committed, undo removes no-durable-Commit losers. Debug: match acked-txn set vs recovered ATT.

7.4 INV-MULTISET — delta + main = one visible multiset

  • Statement / Why: for any Snapshot S, rows visible via the unified path = the logical rows visible to S, each counted exactly once (never twice = delta+main both live, never zero = lost across the merge boundary) — correctness of every scan/aggregate/get; the merge boundary is the highest-risk window.
  • Enforce / Detect: unified path masks MAIN by delete vector + DELTA by validity bitmap; TupleMover publishes new main and invalidates moved delta rows in one atomic swap (INV-SWAP) keyed by the merge commit-ts barrier. Detect: row-count-conservation probe (count(delta_vis(S))+count(main_vis(S)) invariant across a merge) + double-count probe per PK.
  • Telemetry / Recover / Debug: span store.scan, counter store.double_seen (=0), merge.boundary_ts; on divergence quarantine read-only + rebuild from WAL (INV-REC). Debug: pin S across the merge, diff visible PK set, bisect to merge.boundary_ts.

7.5 INV-IMMUT — MAIN row groups immutable once published

  • Statement / Why: after a RowGroup's segments are published their bytes are never modified (deletes → delete vector only); immutability gives latch-free readers, shared zone maps, pointer-flip swap — in-place edits would race readers and break encoding integrity.
  • Enforce / Detect: MainStore exposes RowGroups as Arc read-only (no &mut on a published segment); physical removal only by building a new RowGroup at merge. Detect: xxh3 content hash at publish, re-checked in test builds (main.segment_rehash_mismatch = 0).
  • Recover / Debug: discard the mutated segment, re-derive from delta + WAL; the diffing byte range localizes the offending writer.

7.6 INV-VIS — SI visibility, single live version per snapshot

  • Statement / Why: a version (txn_min, txn_max) is visible to S iff txn_min committed before S, not in S.active, and (txn_max==0 or uncommitted-to-S or committed-after-S); across one chain ≤1 version visible to any S — two visible = phantom duplicate; next_version must partition visibility by txn-time.
  • Enforce / Detect: hy-txn::visible(&TupleHeader,&Snapshot); chain walk stops at first visible; updates/deletes create a new version. Detect: chain-walk probe asserts ≤1 visible + txn_min/txn_max monotone (vis.multi_visible = 0).
  • Recover / Debug: read-only invariant (no state recovery) — a breach is an oracle/chain-link bug; dump the full chain + Snapshot and replay txn order from WAL Commit timestamps.

7.7 INV-ZONE — zone maps have zero false negatives

  • Statement / Why: if any row in a segment satisfies a predicate, that segment is never pruned — false positives allowed, false negatives forbidden (a single one silently drops result rows); min/max/null_count conservatively bound actual values.
  • Enforce / Detect: ZoneMap updated per value at build; pruning is a conservative range-overlap test only. Detect: differential — each scan run with and without pruning, multisets identical (Phase 7 + 13); fuzz boundary equality (zone.false_negative = 0).
  • Recover / Debug: rebuild ZoneMap from segment data (deterministic), disable pruning until rebuilt; for a missing row check range-overlap arithmetic (NULL, decimal scale, signedness are the usual culprits).

7.8 INV-SWAP — tuple-mover swap atomic w.r.t. readers

  • Statement / Why: the delta→main publish is atomic — a reader sees entirely pre-merge (delta live, old main) or entirely post-merge (delta masked, new main), never a torn mix; else the merge window violates INV-MULTISET. Readers run latch-free over Arc snapshots, so the swap is one pointer publish ordered after the new main + moved-delta mask are staged.
  • Enforce / Detect: TupleMover writes new RowGroups + a ColumnFlush record, then one atomic ArcSwap flips MainStore + delta validity together; readers hold an epoch guard for the scan. Detect: concurrent-reader stress, each reader's PK multiset matches its pinned snapshot (merge.torn_observed = 0).
  • Recover / Debug: a merge failing before the swap is abandoned (new segments unreferenced, GC'd), old state authoritative — restartable + side-effect-free until publish. Debug: correlate a torn read's epoch with the publish epoch.

7.9 INV-VAC — vacuum reclaims only fully-dead versions

  • Statement / Why: Vacuum frees a version only if invisible to all current and future snapshots — successor committed and version older than oldest_live = min(active Snapshot.xmin); reclaiming a still-visible version corrupts a long reader's result.
  • Enforce / Detect: TxnManager recomputes oldest_live on begin/commit/abort; Vacuum skips any version with txn_max==0, txn_max ≥ oldest_live, or uncommitted successor. Detect: pre-free debug_assert!(txn_max != 0 && txn_max < oldest_live); long-reader-vs-tight-vacuum test.
  • Recover / Debug: none — a wrongly-freed version is unrecoverable, so the invariant is strictly preventive (hard pre-free assert). Debug: log oldest_live + active set at reclaim; compare a gapped reader's xmin vs the freed txn_max.

7.10 INV-REC — recovery yields all-committed / no-uncommitted

  • Statement / Why: after Recovery, every committed txn's effects are applied (durability) and no loser's effects are visible (atomicity), independent of how many crashes interrupt recovery; CLRs make undo idempotent so repeated crashes converge.
  • Enforce / Detect: analysis (rebuild ATT+DPT from last Checkpoint) → redo (repeat history from recLSN, pageLSN-gated) → undo (roll back losers, Clr{undo_next} per action); column store rebuilt from ColumnFlush + redone row/delta (INV-MULTISET). Detect: crash-injection harness double-recovers, final state == ideal all-committed projection; differential vs SQLite.
  • Telemetry / Debug: spans recover.{analysis,redo,undo}, counter recover.clr_emitted; idempotent via CLR undo_next; offline deterministic replay, diff redo-applied set vs DPT, trace the CLR chain for undo-too-far.

7.11 INV-IDX — no dangling index entries

  • Statement / Why: every RowId reachable from the BTree resolves to a live tuple or valid chain head, never freed/unallocated heap; a stale RowId yields a wrong/torn read or crash. Index + heap lifecycles stay coupled across update-as-new-version and Vacuum.
  • Enforce / Detect: RowStore update repoints the index entry to the new chain head; Vacuum un-indexes only in the same critical section as freeing the last version; deletes mark txn_max, never orphan a referenced slot. Detect: full index→heap walk (Phase 2 + 13), every leaf RowId dereferences to an allocated slot with a decodable header (idx.dangling = 0).
  • Recover / Debug: rebuild index from heap (deterministic, online against a snapshot); for a failed lookup dump leaf entry + page header + slot free-bit — check Vacuum-freed-before-un-index (ordering) or a split that lost the entry.

7.12 INV-ENC — encoding losslessness

  • Statement / Why: every Encoding must round-trip any value + null combination bit-exactly: decode(encode(x)) == x; the Compressor may change the encoding for a column at each merge without changing semantics. A lossy encode silently corrupts analytical results in a way invisible to the WAL.
  • Enforce / Detect: each encoder has a paired proptest that generates random Datum/null vectors and asserts round-trip equality (10 k cases per type/encoding in CI, 1 M nightly); fuzz_decode feeds arbitrary bytes, asserts either clean Err or bit-exact decode. Compressor::encode_segment post-checks size (if encoded ≥ Plain → fallback), never checks correctness in prod (proptest covers it). Counter col.decode_corrupt = 0.
  • Recover / Debug: a corrupt segment is rebuilt from delta + WAL (Phase 12); localize by --no-prune parity scan: values diverge on exactly the faulty column/encoding. Dump segment bytes + encoded header to fuzz corpus.

7.13 INV-LSN — WAL Lsn strict monotonicity

  • Statement / Why: every WalRecord gets a strictly increasing Lsn (byte offset into the log file); two records never share an Lsn; a page's pageLSN never exceeds the WAL flushed watermark. Non-monotone LSNs break the redo pageLSN gate (could re-apply changes to already-updated pages) and make the CLR undo_next chain ambiguous.
  • Enforce / Detect: LogWriter holds a per-file offset counter incremented atomically; callers receive the Lsn before the record is written; Recovery::analysis asserts increasing Lsn and rejects non-monotone records as WAL corruption (truncate-at-violation). Debug: dump (lsn, prev_lsn, record_type) tuples from analysis; a repeated Lsn = two writers sharing the log latch (concurrency bug); a decreasing Lsn = file seek/positioning bug.
  • Telemetry / Recover: counter wal.lsn_gap_detected (should be 0); if non-monotone, halt analysis at that Lsn (treat as torn tail), undo losers with available history; hydb recover --dump-lsns for forensics.

8. Domain Model — Storage Layouts, MVCC, and the Delta/Main Lifecycle

The on-disk and in-memory shapes below are LOCKED contracts shared across hy-page, hy-row, hy-index, hy-wal, hy-col, and hy-store. All multi-byte integers are little-endian. All page-resident structures are checksummed and lsn-stamped for ARIES redo idempotency. Sizes target a 4 KiB Page default; row group default = 65_536 rows.

8.1 Page (hy-page::Page) — 4 KiB unit of buffering and I/O

Page = 4096 bytes, 4 KiB aligned
+--------------------------------------------------------------+ off
| PageHeader (24 B)                                            | 0
|   lsn        : u64   // pageLSN; last WAL record applied      | 0
|   kind        : u8   // PageKind (see below)                 | 8
|   _pad        : u8                                           | 9
|   free_ptr    : u16  // heap-from-end frontier (SlottedPage) | 10
|   slot_count  : u16  // # slots                              | 12
|   _rsv        : u16                                          | 14
|   checksum    : u32  // crc32c over bytes[20..4096]          | 16
|   gen         : u32  // monotonic write generation (torn-pg) | 20
+--------------------------------------------------------------+ 24
| Body (4072 B) — interpretation depends on kind               | 24
+--------------------------------------------------------------+ 4096

PageKind enum (1 B): Meta=0, RowSlotted=1, BTreeLeaf=2, BTreeInternal=3, WalSegMeta=4, ColSegment=5, FreeSpaceMap=6, Overflow=7. Pageable::page_kind() returns the owning kind. checksum excludes bytes [0..20) (so lsn/kind/free_ptr can be patched in place during recovery without recompute) but covers [20..4096) including gen. gen increments on every flush; pairs with sentinel-at-page-tail for torn-page detection (§8.10).

8.2 SlottedPage (hy-row::SlottedPage) — variable-length tuples, heap-from-end

Slot directory grows forward from byte 24; tuple payloads grow backward from byte 4096. Free space = free_ptr - (24 + slot_count*4).

+-- PageHeader (24 B, kind=RowSlotted) ------------------------+ 0
+-- Slot Directory (slot_count * 4 B), grows ->               | 24
|   Slot { off: u16, len: u16 }  // off=0 => dead/moved slot   |
|   ...                                                        |
|                  <-- free space -->                          |
|   Tuple[N-1] payload                                         |
|   ...                                                        |
|   Tuple[0] payload                          <-- free_ptr     | ..4096
+--------------------------------------------------------------+ 4096

RowId{ page, slot } addresses a tuple; slot indexes the directory. off=0 marks a slot whose tuple migrated (update created a new version elsewhere) or was vacuumed; the slot index is never reused while any version chain references it (stable RowId invariant). Compaction reclaims dead payload space when free space < threshold (default 256 B) by sliding live payloads and rewriting off fields under WAL.

8.3 TupleHeader + payload (hy-row::TupleHeader) — in-tuple MVCC metadata

TupleHeader (fixed prefix of every Tuple payload)
+----------------+------+---------------------------------------+
| field          | size | meaning                               |
+----------------+------+---------------------------------------+
| txn_min        | u64  | creating TxnId (LOCKED: TxnId)        |

Header = 25 B + ceil(ncols/8) B bitmap. Payload encodes only non-null columns; Datum::Null columns occupy zero payload bytes and are signalled by null_bitmap. Split on full, merge/redistribute < 40% occupancy; node writes WAL-logged for crash safety.

Bodies (LOCKED): Begin{txn}, Insert{txn,rid,after}, Update{txn,rid,before,after}, Delete{txn,rid,before}, Commit{txn,ts}, Abort{txn}, Clr{txn,undo_next:Lsn}, ColumnFlush{rg,seg}, Checkpoint(CheckpointRec{att:Vec<(TxnId,Lsn)>, dpt:Vec<(PageId,Lsn)>, ts}). before/after are full payload images (physiological) → redo pageLSN-idempotent, undo via before; Clr.undo_next chains compensation (no double-apply). crc covers [len..crc); a torn tail frame (bad crc / len past EOF) bounds the analysis scan (that frame + all after discarded).

8.6.e Encoding formats with worked examples

Definitions/decode-cost in Glossary + §6.11; the "best for" workload per encoding is ADR-10. Width: Bool 1, I32 4, I64/F64/Date/Timestamp 8, Decimal 16, Str/Bytes = u32-offset array + blob. Worked examples (the unique content here):

Plain        raw fixed-width, n_rows*width B

8.7 MVCC model — visibility predicate

visible(h: &TupleHeader, snap: &Snapshot) -> bool under IsolationLevel::SnapshotIsolation. A version is visible iff its creator is committed and pre-snapshot, AND it is not superseded by a committed-pre-snapshot deleter. Definitions: committed_before(t) ≡ committed(t) && commit_ts(t) <= snap.ts && t ∉ snap.active && t < snap.xmax. Own-write rule: a txn always sees its own uncommitted versions (txn_min == snap.owner).

Truth table (rows = predicate states; * = don't-care):

| txn_min state          | txn_max(=0?) | txn_max state         | VISIBLE? |
|------------------------|--------------|-----------------------|----------|
| own uncommitted        | =0           | *                     | YES      |
| own uncommitted        | own          | (own delete)          | NO       |
| committed_before       | =0           | (live)                | YES      |
| committed_before       | set          | committed_before      | NO       |
| committed_before       | set          | active/own/uncommitted| YES      |
| committed_before       | set          | committed_after(ts)   | YES      |
| in snap.active         | *            | *                     | NO       |
| uncommitted (other)    | *            | *                     | NO       |
| committed_after(ts)    | *            | *                     | NO       |
| aborted                | *            | *                     | NO       |

commit_ts resolved via the TxnManager commit oracle; uncommitted/aborted txns have no commit_ts. ReadCommitted reuses the predicate but takes a fresh Snapshot per statement.

8.8 Delta/main lifecycle — state machine

Per-tuple state DELTA → MAIN → reclaimed:

[Absorbed]  write lands in DeltaStore (row format, in DeltaStore SlottedPages, flags|=DELTA)
    | TupleMover merge (background, Phase 10)
    v
[Merged]    encoded into a new MAIN RowGroup (columnar); delta row marked MOVED
    | commit of new RowGroup + atomic swap (ColumnFlush WAL record)
    v
[InMain]    visible only via column path; delta copy GC-eligible
    | delete against main row
    v
[MarkedDeleted]  delete_vector bit set (main is immutable); still scanned-then-filtered
    | next merge of that RowGroup
    v
[Reclaimed]  physically dropped at re-merge; Vacuum drops versions < oldest live snapshot

Swap atomicity + immutability invariants: §6.3, §6.13 (the swap publishes after ColumnFlush is durable, retires delta rows only once oldest_live_snapshot >= merge_ts). Write→delta→merge→main→vacuum sequence: insert appends a row + Insert WAL → Commit assigns ts → at threshold the mover reads a delta+main merge snapshot, encodes RowGroups, logs ColumnFlush, atomic-swaps the directory pointer (delta rows → MOVED) → later Vacuum drops MOVED + delete-vector'd rows once oldest_live_snapshot advances past merge_ts.

8.8.x Worked scan: 2 delta rows + a 65_536-row main row group under a snapshot

scan(spec) with spec.snap=S, project {c0,c1}, predicate c0 > 100:

1. Plan: AccessPath::ColumnScan(main RG#7) + DeltaScan(delta region)
2. MAIN RG#7: ZoneMap[c0]={min:50,max:9000} -> NOT skipped.
   decode c0 -> ColumnBatch (1024/iter); c0>100 -> SelectionVector (~900/1024);
   AND-out delete_vector; late-materialize c1 only for survivors
3. DELTA: R_a(c0=150,T8@S.ts) visible -> included; R_b(c0=80) fails predicate
4. Merge: dedup by PK — a newer delta version shadows the main copy
5. Emit BatchIter: main-survivors ++ delta-survivors, one snapshot-consistent stream

Cost: ZoneMap + late materialization decode only matching c1; delta merge is an O(delta) PK hash-probe against emitted main keys.

8.9 Domain invariants (LOCKED)

  • RowId stability (slot never reused while a chain references it); single newest head (acyclic, next_version=0 terminator); MAIN immutability (only delete_vector + directory pointer change); WAL ordering (pageLSN ≤ flushed_lsn before flush); encoding fidelity (decode(encode)==, exact n_rows/null_count/ZoneMap); snapshot consistency (one lifecycle state per key per Snapshot).

Per-commit fsync caps TPS at device fsync rate; async loses the D in ACID. [## 15] Async / periodic flush wins for a cache or analytics-ingest tier where bounded data loss on crash is acceptable in exchange for maximum throughput (Kafka acks=1, Redis default); per-commit fsync wins for a low-throughput ledger where every commit must be independently durable and batching latency is unacceptable.
14 Default isolation level Snapshot Isolation (IsolationLevel::SnapshotIsolation); ReadCommitted available Serializable (SSI/2PL); ReadCommitted default SI is the natural fit for MVCC version chains: each txn reads a consistent Snapshot{xmin,xmax,active} with no read locks → readers never block writers (HTAP requirement). SSI/2PL add lock manager + abort complexity beyond single-node v1 scope; RC default would surprise analytical readers. [## 16] Serializable (SSI) wins where write-skew anomalies are unacceptable — financial constraints, double-booking, inventory invariants; Postgres offers SSI for exactly these. Read Committed default wins for high-contention OLTP that tolerates non-repeatable reads and wants shorter snapshots / less version retention (Oracle, MySQL default).
15 Primary index structure B+Tree (BTree) over RowId, ordered keys Hash index; LSM index; ART/trie B+Tree serves both point lookup AND range scan (OLAP range predicates) with crash-safe page writes; ordered leaves enable index range scans. Hash gives point-only (no ranges); LSM index duplicates the delta/main merge problem; ART deferred (string-key-specialized, complex page format). [## 14] A hash index wins for a point-only KV workload with no range queries (memcached-style), giving O(1) lookup without tree-height latency; an LSM index wins when the index itself is write-saturated and sequential-write amortization beats in-place B+Tree node updates; ART wins for dense string keys needing prefix compression.
16 Vectorization unit ColumnBatch of 1024–2048 values + SelectionVector Tuple-at-a-time (Volcano); whole-column materialization Batch-at-a-time amortizes per-call overhead + fits L1/L2, enabling SIMD kernels and late materialization (only selected rows decoded). Tuple-at-a-time has crippling per-row dispatch overhead; whole-column blows cache + decodes pruned data. [## 20] Tuple-at-a-time (Volcano) wins for OLTP-only point queries returning 1 row, where batching overhead exceeds benefit and the simpler iterator model eases nested-loop joins; whole-column (full materialization) wins inside a query compiler (HyPer/Umbra data-centric codegen) that fuses operators and eliminates per-batch boundaries entirely.
17 Deletes against main Delete vector (per-row-group bitmap on MainStore), applied at scan, physical removal at next merge In-place delete (rewrite segment); tombstone rows MAIN is immutable → deletes can't mutate compressed segments. Delete vector is O(1) bitmap set, applied as a selection-vector mask at scan time; physical reclaim happens during the merge that rebuilds the row group. In-place delete forces segment rewrite per delete. [## 21][## 22] In-place delete wins for a mutable row-store with no immutability constraint (a classic heap) where deletes are rare and immediate space reclaim matters; per-row tombstone rows win in an LSM where deletes are just another sorted-run write reconciled at compaction (RocksDB).
18 Delta→main conversion timing Background TupleMover (async, MVCC-safe atomic swap under concurrent readers) Synchronous on-write merge; size-triggered foreground merge Background mover keeps OLTP write latency off the encode/compress critical path; atomic RowGroup swap lets readers proceed against the old main until the new one is durable + visible. Synchronous merge stalls writers; foreground merge causes latency spikes. [## 22] Synchronous/foreground merge wins for a bulk-load-then-query pattern (ETL job, COPY into a warehouse) where there are no concurrent OLTP writers to stall and a single foreground compaction gives the most compact result fastest; it also removes background-thread scheduling and the pinned-snapshot leak risk.
19 Torn-page / corruption detection CRC32C checksum per page (and per column segment) No checksum (rely on WAL); xxHash; SHA-256 CRC32C has hardware acceleration (SSE4.2/ARMv8 CRC) → cheap per-page verification on read, detects torn writes + bit rot before they propagate into recovery. WAL alone can't tell a torn page from a valid one at startup; SHA-256 cryptographic overkill; xxHash not torn-write-standard. [## 24] No checksum wins for an in-memory or ephemeral store where on-disk corruption is out of the threat model and the per-read CRC cost is pure overhead; a cryptographic hash (SHA-256/BLAKE3) wins when the data directory is an adversarial-tamper boundary (content-addressed, signed artifacts) where collision resistance, not just bit-rot detection, is required.
20 File layout File-per-segment (FileManager segment files, SegmentId) Single monolithic file; one file per table Segment files let the TupleMover write a new columnar segment + atomically publish (rename/swap) without rewriting unrelated data, and allow per-segment fsync + reclaim. Single file forces in-place overwrite + complicates atomic main swap; file-per-table too coarse for segment-granular GC. [## 13][## 22] A single monolithic file wins for an embedded, copy-as-one-file database (SQLite, LMDB) where "the database is one file" is a usability and backup requirement and the FD/inode budget must stay at 1; file-per-table wins when per-table DROP/TRUNCATE must reclaim space instantly (one unlink).
21 Correctness testing datadriven golden tests + differential testing vs SQLite (OLTP) & DuckDB (OLAP) on identical datasets Hand-written assertions only; reference-impl-free Differential testing catches semantic divergence (visibility, aggregation, NULL handling) against mature engines that have no shared code → high-signal oracle. datadriven keeps test corpus declarative + diffable. Assertions-only misses unknown-unknowns. [## 25] Hand-written assertions win when no comparable reference engine exists (a genuinely novel operator/semantics) so a differential oracle is unavailable, or in early prototyping where the spec is still in flux and golden files churn faster than they catch bugs.

[## 25] AFL++ wins when fuzzing a native C/C++ dependency outside the Rust toolchain (where libFuzzer integration is awkward) or when persistent-mode/fork-server throughput on a large binary matters more than in-process speed; proptest-only suffices when inputs are structured values, not raw bytes.

Ad-hoc timing is noisy; unstable-only #[bench] breaks MSRV-stable CI. [## 25] The unstable #[bench] harness wins for a nightly-only project already pinned off stable, where its zero-dependency integration with cargo bench beats pulling in criterion; ad-hoc timing suffices for a one-off profiling spike that will never enter CI.

WAL record on-disk frame: [len:u32][lsn:u64][crc32c:u32][type:u8][body…]. CRC over type+body; truncated/torn tail record (CRC fail) = log end during analysis.

  • Ownership/concurrency: Wal owns the append buffer + file (records own their Box<[u8]> images). Group commit batches many Commit records into one fsync; flush(upto) parks waiters until durable; append serialized by a log latch, Lsn = monotonic byte offset.
  • Recovery (ARIES): analysis rebuilds ATT + DPT (recLSN) from the last Checkpoint; redo repeats history from min(recLSN), skipping rec.lsn ≤ page.lsn; undo rolls back losers emitting Clr{undo_next} (re-crash-idempotent). ColumnFlush re-establishes which row-groups were durable.

11.6 hy-txn — MVCC

pub enum TxnState { Active, Committed, Aborted }
pub enum IsolationLevel { SnapshotIsolation, ReadCommitted }

pub struct VersionChain;  // logical: follow RowId.next_version via TupleHeader
pub struct TxnManager { /* id oracle, commit-ts oracle, active set, Vacuum */ }
impl TxnManager {
    pub fn begin(&self, iso: IsolationLevel) -> Transaction;       // snapshots active set
    pub fn commit(&self, txn: &mut Transaction) -> Result<Timestamp>; // WAL Commit + fsync, assign ts
    pub fn abort(&self, txn: &mut Transaction) -> Result<()>;      // undo via CLRs
    pub fn vacuum(&self) -> Result<usize>;                         // GC versions < oldest live snapshot
}
pub fn visible(h: &TupleHeader, snap: &Snapshot) -> bool;

SI visibility predicate (the engine's correctness core):

visible(h,snap) = committed_before(h.txn_min, snap) && h.txn_min ∉ snap.active
                  && (h.txn_max == 0 || !committed_before(h.txn_max, snap) || h.txn_max ∈ snap.active)
  • Ownership: TxnManager owns oracles + global active set; Transaction owns its immutable Snapshot (taken at begin).
  • Mutation: versions never overwritten; commit assigns a Timestamp and atomically removes id from active set. ReadCommitted re-snapshots per statement; SI snapshots once at begin.
  • Concurrency: visibility is lock-free reads against committed metadata; write-write conflicts (two txns set same txn_max) → ErrorKind::Conflict (first-committer-wins).
  • Vacuum: reclaims versions whose txn_max committed before the oldest live snapshot; coordinates with tuple mover (a version merged into MAIN may be GC'd from delta).

16. Phase 4 — MVCC and transactions

4.1 Objectives

  • Add hy-txn: TxnManager (TxnId alloc + commit-Timestamp oracle + active set), Transaction, Snapshot, visible() SI predicate, in-tuple version chains, Vacuum GC. 4.2 Detailed Implementation Steps

  • oracle.rs — TxnManager{next_txn, next_ts: AtomicU64, active: Mutex<BTreeSet<TxnId>>, commit_ts: Mutex<HashMap<TxnId,Timestamp>>} (committed→ts; absent⇒aborted/in-flight); begin(IsolationLevel)/commit/abort/snapshot()/oldest_active(). txn.rs — Transaction{id,snapshot,state:TxnState}, IsolationLevel (RC re-captures snapshot per statement). snapshot.rs — Snapshot{xmin,xmax,active:Box<[TxnId]>,ts} captured under the active lock (xmin=oldest_active, xmax=next_txn).
  • visibility.rs — pub fn visible(h:&TupleHeader, snap:&Snapshot, mgr:&TxnManager)->bool: txn_min committed-before-snap AND ∉ snap.active; txn_max 0/uncommitted OR (committed but in active / ≥ xmax); committed-before = commit_ts(t).is_some() && t<snap.xmax && !active.contains(t); self-writes (t==self.id) visible. VersionChain walk: head → next_version until NULL, first visible() wins.
  • hy-row ext — update(rid,after,txn): new slot + Tuple{txn_min=txn.id, txn_max=0, next_version=rid_old}, old txn_max=txn.id, splice head, index→head; delete: stamp txn_max=txn.id (tombstone). vacuum.rs — Vacuum::run: watermark=oldest_active(), free versions with txn_max!=0 && committed_before(txn_max,watermark), coalesce slots, head intact. Commit: ts=next_ts.fetch_add(1), Commit{txn,ts} → flush(lsn) → publish commit_ts → drop from active (publish-before-unlock, no "active-but-committed" torn state).

17. Phase 5 — Columnar main fundamentals

5.1 Objectives

21. Phase 9 — Delta/main architecture and the unified read path

9.1 Objectives

  • Build DeltaStore (row-format MVCC writes + per-row validity bitmap) and MainStore (immutable columnar RowGroups + per-group delete vector), and the unified read path: under one Snapshot, merge visible delta + non-deleted-visible main for get and scan. Invariant: exactly-one-visible-version per (table, PK) per snapshot — no doubling/loss across the delta↔main boundary. Out of scope: conversion mechanics (Phase 10), router (Phase 11); this phase assumes static main + growing delta.

9.2 Detailed Implementation Steps

  • Files: delta.rs (DeltaStore), main_store.rs (MainStore), read_path.rs (merge + BatchIter), table.rs (HybridTable::get/scan). DeltaStore wraps a RowStore heap, appends Tuples with TupleHeader{txn_min,txn_max,next_version,flags}; validity: RoaringBitmap = physical liveness (cleared only by GC), visibility uses hy_txn::visible NOT validity; delta_index: HashMap<PkBytes,RowId> → chain head for O(1) point access.
  • MainStore: Vec<RowGroup> (immutable, ascending id) + parallel delete_vec: Vec<DeleteVec{deleted: RoaringBitmap, deleter_ts}>; main rows carry no txn_min (commit ts < merge_ts), RowGroupMeta{pk_zone, merge_ts} enables PK pruning. fn recover_hybrid(...) -> RecoverReport {
  let cp = load_master_checkpoint();              // master record -> CheckpointRec
  let (att, dpt) = analysis(cp.begin_lsn);        // rebuild ATT + DPT
  redo(dpt.min_rec_lsn());                         // repeat history: row pages + delta
  undo(att.losers());                              // CLR-protected rollback

  reverify_delete_vectors(); reseat_btree();       // rebuild index leaves from row pages
}

Threat Model

Scope: a single-node, embeddable storage engine. The primary adversary is untrusted on-disk bytes — pages, WAL records, and column segments that may be corrupt (hardware/media faults, partial writes) or adversarial (a tampered data directory). Secondary: untrusted input rows (via the API/hydb CLI) and operator error. Out of scope (other projects own them): network attackers (no protocol, 33/64), authn/authz/multi-tenant isolation, distributed/Byzantine actors (36/86/102), side-channel/timing attacks. We do not assume the data directory is a security boundary against a privileged local user; we assume the OS enforces file permissions.

26.1 Trust boundaries

  trusted: in-RAM engine types (Page after decode, Tuple, ColumnBatch, Snapshot)
  ----------------------------------- ON-DISK FORMAT BOUNDARY -----------------------------------
  UNTRUSTED bytes: segment files (hy-page), WAL file (hy-wal), column segment blobs (hy-col),
                   the manifest/catalog (hy-catalog)
  ----------------------------------- API / CLI INPUT BOUNDARY ----------------------------------
  UNTRUSTED input: caller-supplied rows, keys, predicates, ScanSpec, CLI args
  • Rule: every byte crossing the on-disk boundary is validated before becoming a trusted type — no unsafe transmute without prior checksum + bounds + tag check. Decode is total (from_bytes returns Result, never panics on any input; panics on adversarial bytes are bugs, Phase 13 fuzz gate). The MVCC visible(h,snap) predicate is the single gate for data exposure; no read path bypasses it.

26.2 Security properties (durability/atomicity as security)

Property → enforced by: Integrity (read = last committed write or typed error, never silently wrong) → CRC32C + pageLSN; Atomicity (all-or-nothing across row+delta+main) → WAL log-before-data + ARIES/CLR; Durability (committed survives crash) → flush(lsn) before ack + group commit; Isolation (no uncommitted/GC'd-early version) → visible() + Vacuum watermark; Recoverability (column store rebuildable from WAL+row/delta) → ColumnFlush + idempotent redo.

26.3 Threat catalog

T1 — Corrupt / torn pages

  • Vector / detect: partial 4 KiB write (power loss), bit rot, sector reorder; CRC32C over page body in PageHeader (verified on every buffer-pool load) + pageLSN ≤ WAL tail sanity.
  • Mitigate / recover / telemetry: log-before-data makes the page redo-reconstructible from recLSN; optional double-write buffer (torn_page_guard); if unrecoverable and not in DPT, quarantine + ErrorKind::Corruption{page}. Counters page.checksum_fail, page.torn_repaired.

T2 — Malformed column segments

  • Vector / detect: bad encoding length, out-of-range dict code, BitPacked{bits}>64, RLE run overflowing n_rows, FoR delta exceeding bits, offset past segment end; per-segment CRC32C + bounds-checked decoders validate every offset/length vs segment size + n_rows (dict codes < dict.len()).
  • Mitigate / recover / telemetry: decoders return Result, a failed segment fails only its RowGroup scan (never reads neighbor memory); fuzz target per Encoding (Phase 13); rebuild via forced re-merge from delta+WAL. col.decode_reject{encoding}, col.segment_checksum_fail.

T3 — WAL tampering / truncation

  • Vector / detect: truncated tail, flipped bytes, injected record, reordered LSN; per-record CRC32C + length prefix + monotone Lsn + known-variant tag (exhaustive match rejects unknown tags).
  • Mitigate / recover / telemetry: clean truncation point — first bad-CRC/length/non-monotone record defines EOL, all after discarded (unfinished group commit); a Commit with a bad payload CRC is treated as not committed; redo to the truncation point, undo losers with CLRs. wal.truncated_bytes, wal.checksum_fail_at_lsn. (Durability also assumes fsync truly persists — the documented PostgreSQL "fsyncgate" (2018) showed an fsync EIO can be reported once and lost; we treat an fsync error as fatal and refuse to ack, never retry-and-assume-durable.)

T4 — Resource exhaustion (DoS)

  • Sub-vector → cap: huge tuple → max_tuple_bytes reject at insert; delta overflow → delta_max_{rows,bytes} forced merge + backpressure (DeltaFull above hard cap); unbounded chains (long reader) → Vacuum watermark + chain-length alert + txn_age_max refusal; pathological scan → scan_max_rowgroups + cancellation token; ColumnBatch/hash-agg blowup → batch ≤ 2048 + agg_mem_budget spill; huge-WAL recovery → checkpoint_interval bounds redo span. Telemetry: delta.fill_ratio, vacuum.oldest_snapshot_age, txn.aborted_overflow.

T5 — MVCC visibility leaks

  • Vector / mitigate: a bug exposing uncommitted/aborted/prematurely-GC'd versions; single visible(h,snap) predicate is the only visibility check (get, scan, delta-merge, mover all route through it), Vacuum never reclaims a version newer than the oldest live Snapshot (watermark), aborted txn ids stay in active-set logic until cleaned.
  • Test / telemetry: proptest random interleavings assert SI (no dirty read, no lost-update-vs-SI, no torn delta/main read) + differential vs SQLite serial history; mvcc.visibility_invariant_fail = 0 (CI gate).

T6 — Decoder / parser panics on adversarial bytes

  • Vector / mitigate: OOB index, unwrap/arithmetic panic, infinite loop (RLE run=0, cyclic next_version), allocation panic (length → huge Vec); decode paths deny unwrap_used, gate allocation by validated length ≤ segment/page size, bound the next_version walk by a visited-budget.
  • Fuzz / telemetry: Phase 13 targets for page/WAL/Encoding/BTree-node decode; decode.error{kind}, any fuzz panic = release blocker.

T7 — Integer overflow in offsets / lengths / ids

  • Vector / mitigate: slot off+len wrap, n_rows*width overflow, Lsn/TxnId wrap; checked_*/saturating_* on all untrusted math (overflow ⇒ ErrorKind::Corruption), CI -C overflow-checks=on + overflow test profile; TxnId/Lsn u64 (no realistic single-node wrap, documented).

T8 — Supply-chain risk

  • Mitigate / telemetry: cargo-deny (license allowlist, cargo-audit advisories, banned/dup gates), minimal justified dep set, no proc-macro/network crates in the core, --locked + vendored lockfile; CI fails on any new advisory or non-allowlisted license.

T9 — Operator mistakes

  • Vector / detect: deleting/renaming a segment, hydb recover against the wrong dir, mixing two DBs' segments, partial restore; a signed manifest (hy-catalog) lists every live SegmentId + CRC + per-DB UUID, startup verifies manifest ↔ files (missing/extra/mismatch ⇒ refuse to open), each segment header embeds the DB UUID (cross-DB mixing rejected).
  • Mitigate / recover / telemetry: hydb recover idempotent + dry-run; compact/checkpoint never delete a referenced segment; a missing-but-reconstructible segment re-merges from WAL+delta, else fail loud. manifest.mismatch{kind}, open.refused.

T10 — Stale format reader / version mismatch

  • Vector / detect: an older engine binary opens a data directory written by a newer format version (bumped PageHeader.format_ver, WalFileHeader.wal_ver, or SegmentHeader.format_ver); without a version gate the older reader may silently misparse newer layout bytes as valid old-format data; detected by the per-unit magic+version check at byte 0 of every persisted unit (b"HYPG", b"HYWL", b"HYCS", b"HYMF").
  • Mitigate / recover / telemetry: FMT-1 invariant (Compatibility Guarantees): ErrorKind::FormatTooNew { found, supported }, exit 75, never partial-parse; WAL reader refuses wal_ver > N before analysis begins; MANIFEST version gate at open; all per-unit magic+version checks run before any byte interpretation. Metric open.format_too_new. Recovery: roll back to a prior engine binary or run hydb recover --upgrade (Compatibility Guarantees) with the new binary before opening.

26.4 Cross-cutting controls & residual risk

  • Checksums everywhere: CRC32C (HW-accelerated) on pages, WAL records, segments, manifest — first defense for T1/T2/T3/T9. Defense in depth: checksum (detect) → bounds-checked decode (contain) → WAL redo / re-merge (recover) → quarantine + loud error (fail safe); never read-through corruption silently.
  • Residual risk (accepted): undetected multi-bit corruption inside a CRC collision window (~2⁻³²/segment); a privileged local user can delete the data dir (OS-level, out of scope); no encryption at rest (defer to FS/LUKS). CI security gates (block release): zero fuzz panics, zero mvcc.visibility_invariant_fail, clean cargo-audit/cargo-deny, overflow-checks profile green.

Failure Modes and Recovery

Severity ladder (highest first): S0 wrong-result / silent data loss (returns wrong rows/values, or a committed write vanishes) → S1 unavailability (refuses writes, recovery loops, panics) → S2 degraded (thrash, vacuum lag, throughput cliff) → S3 cosmetic. S0 is the gravest class: a query that answers is worse than one that crashes, because the caller trusts it. Every S0 mode below ties to the no-double / no-loss invariant (each live row visible under a snapshot appears in exactly one of DELTA or MAIN, never both, never neither) and the differential oracle (Phase 13: same dataset vs SQLite/DuckDB, byte-equal result sets modulo ordering).

27.2 Torn page (partial 4 KiB write)

  • Symptom / cause / detect: page-header CRC mismatch on read, or pageLSN inconsistent with payload, from power loss mid-write (HW writes <4 KiB atomically only on some devices); per-page CRC32C verified on BufferPool fault-in + recovery redo finds pageLSN < expected.
  • Recover / operator: discard torn frame, redo from the page's last good pageLSN (log-before-data guarantees every change since last clean checkpoint is in WAL); if the WAL predates the page, restore last checkpoint + replay. hydb recover --verify-checksums; alert on torn-page count > 0; forensic = hydb page-dump + per-512 B-sector CRC to localize the torn boundary.
  • Long-term: double-write buffer or per-sector LSN stamping; prefer advertised 4 KiB-atomic devices. (This is exactly why MySQL/InnoDB ships a double-write buffer — a documented, long-standing defense against torn pages on non-atomic media.)

27.3 Half-applied tuple-mover merge

  • Symptom / cause: new MAIN RowGroups partially written at crash while DELTA still holds the source rows → risk of double-count (rows in both) or loss (rows in neither); the merge is multi-step (build → write segments → swap → GC delta), crash between steps.
  • Detect / auto recovery: ColumnFlush{rg,seg} is the durable commit edge — segments with no committed ColumnFlush are incomplete. Idempotent, all-or-nothing per group: crash before ColumnFlush durable → discard orphan segments (delta authoritative); after → redo the pointer swap, delta GC re-derivable. The swap is one atomic CAS; delta rows invalidated only after the swap is durable → never both, never neither.
  • Manual / forensic / long-term: hydb compact --dry-run / --rebuild-rg; reap segments with no referencing ColumnFlush; forensic = ColumnFlush log scan + ref-map dump. Write segments to temp SegmentIds → fsync → one ColumnFlush + atomic swap (single durable commit edge, MM5).

27.4 WAL full / disk full

  • Symptom / cause / detect: LogWriter::append cannot extend the log (ENOSPC) from unbounded WAL growth (no checkpoint advancing the truncation horizon) or an exhausted volume; free-space watermark check before each append + ENOSPC from fsync.
  • Recover / operator: backpressure — refuse new writes (ErrorKind::WalFull), block until a forced Checkpoint advances recLSN and truncates; reads continue (read path needs no append). hydb checkpoint + free disk + raise reservation; alert at 80% WAL reservation; never share the WAL volume with hot data unquota'd.
  • Long-term: reserve WAL space at init; background checkpointer keyed to bytes-since-checkpoint; never silently drop a write — refusing (S1) beats dropping (S0).

27.5 Buffer-pool thrash / eviction storm

  • Symptom / cause / detect: throughput cliff + pin contention + high fault rate when a full-table OLAP scan touches more pages than the pool holds, churning clock eviction and starving OLTP guards; eviction-rate spike + fault-rate ≈ scan-rate + hit-ratio collapse.
  • Recover / operator / long-term: scan path uses a bounded scan-resistant ring (large sequential scans bypass the general pool) so a scan can't evict the OLTP working set; column scans stream ColumnBatches without pinning whole groups. Size pool to OLTP working set + scan ring, throttle concurrent scans; dashboards hit-ratio / eviction-rate / pinned-frames, alert hit-ratio < 90%; forensic = frame-table dump. Scan-pollution of an LRU/clock pool is the classic problem LRU-K (O'Neil et al.) was designed to fix.

27.6 Version-chain bloat / vacuum lag

  • Symptom / cause / detect: chains grow long (slow point lookups walking next_version), DELTA can't drain into MAIN — a long-running txn pins the oldest live snapshot, so Vacuum can't reclaim newer versions and the mover can't GC merged ones; TxnManager tracks oldest active snapshot, alert on age + chain-length p99.
  • Recover / operator / long-term: no silent recovery (a long txn is a policy choice); identify + optionally abort it, force Vacuum after. hydb analyze exposes oldest-snapshot age + dead-version ratio; forensic = hydb chain-dump. Mitigate with snapshot-age cap + statement timeout + a vacuum-horizon alert. (This is the documented PostgreSQL failure mode where a single long-lived transaction blocks autovacuum and bloats tables; left unchecked it culminates in transaction-ID-wraparound emergencies — publicly post-mortemed by Sentry (2015, "transaction-id wraparound") and others.)

27.7 S0 — data loss / wrong result from a merge-boundary or visibility bug

The flagship failure class. Sub-modes: double-count (a row in DELTA and in newly merged MAIN — violates no-double), loss (merge invalidates a delta row before its MAIN copy is durable/swapped — violates no-loss), visibility bug (visible(h,snap) mis-evaluates txn_min/txn_max/active-set — violates the SI predicate).

  • Symptom / detect: scan/aggregate returns wrong cardinality or sums, a committed row missing, or an aborted/future row visible — often silent. Primary detection: the differential oracle (Phase 13, byte-equal vs SQLite/DuckDB) + aggregation cross-check (Σdelta + Σmain = Σground-truth) + the no-double/no-loss invariant checker after every merge (|live in delta∪main| == expected, intersection == ∅). Secondary: randomized MVCC-schedule SI tests + a merge-fuzzer interleaving merges with concurrent readers.
  • Recover / forensic / long-term: no self-healing — fail closed: invariant assertion → quarantine the RowGroup, re-derive from delta; worst case rebuild MAIN from WAL+row/delta (Phase 12). The canonical S0 forensic path: WAL-replay to the suspect LSN → page-dump row/delta pages → version-chain-dump (txn_min/txn_max/active vs the failing Snapshot) → diff materialized MAIN vs delta+WAL, reproduced under deterministic single-thread replay. The SI predicate + merge swap carry property tests; no merge ships without the post-merge assertion; differential oracle gates every PR.

27.8 Index/heap divergence (dangling RowId)

  • Symptom / cause / detect: BTree::lookup returns a RowId whose slot is empty/free/wrong, from a non-atomic index+heap update (crash between heap and index write, missing WAL ordering); lookup validates fetched header key == search key + hydb analyze --check-index cross-walks every leaf RowId → heap.
  • Recover / long-term: index + heap changes share one WAL mini-txn → redo restores both, mismatched leaves pruned; rebuild B+Tree from heap scan; scheduled consistency check, alert on dangling count; key revalidation on every fetch (defense in depth).

27.9 Decoder corruption

  • Symptom / cause / detect: decode yields out-of-range values, panics, or wrong row count from corrupt segment bytes / wrong Encoding metadata / dangling dict SegmentId; per-segment CRC + decode bounds checks (BitPacked width, FoR base+delta range, dict code < len) + n_rows/null_count cross-check vs ZoneMap.
  • Recover / long-term: segment immutable + reconstructible → discard + re-merge from delta/WAL; --rebuild-rg / quarantine; alert on decode-error count + CRC scrub job; forensic = segment hex dump + header, captured to the fuzz corpus. Decoders are panic-free on adversarial bytes (return Err, never UB).

27.10 Recovery non-termination

  • Symptom / cause / detect: recovery loops, re-undoes the same change, or never reaches durable_lsn, from missing/incorrect CLR undo_next, non-idempotent redo (pageLSN not advanced), or a circular WAL pointer; bound each undo by strictly-decreasing undo_next + watchdog on LSN-monotonicity + max-pass guard.
  • Recover / long-term: CLRs make undo monotone + idempotent (repeated crashes converge; redo skips when pageLSN ≥ record LSN); hydb recover --to-lsn bounded replay; recovery-progress gauge, alert on no progress; exhaustive WalRecord match + CLR undo_next invariant under crash-during-recovery fault injection.

27.11 Cross-cutting recovery doctrine

  • Fail closed, never silent: prefer S1 (refuse/panic) over S0 (wrong/lost). A write is acked only after WAL fsync; a result is served only past the invariant check.
  • Single durable commit edge per state change: Commit for txns, ColumnFlush for merges — recovery is "before edge → discard, after edge → redo".
  • MAIN is always reconstructible from WAL + row/delta state (Phase 12) → any columnar corruption is recoverable, never terminal.
  • Three debugging primitives, always available: hydb recover --dump-* (WAL replay), hydb page-dump (raw bytes + CRC), hydb chain-dump (version chains + visibility). The S0 forensic path is always WAL-replay → page-dump → version-chain-dump.

Backup / Restore

  • Strategy / PITR: WAL archiving + segment snapshot — (1) hydb checkpoint to advance recLSN, (2) copy immutable column + row-store segment files (append/COW at merge granularity), (3) continuously archive WAL past the checkpoint Lsn. PITR restores the snapshot then replays archived WAL to a target Lsn/Timestamp via the standard Recovery (same code path as crash recovery, no special restore engine). The snapshot must be taken at/after a checkpoint; immutable main means concurrent merges only add RowGroups (old ones pinned until backup completes).
  • Restore testing (Phase 13 gate): automated job — snapshot a populated DB, fault-inject crash mid-merge, restore from backup+WAL, differential vs source, assert recovery.duration within RTO and byte-identical contents. A backup that hasn't been test-restored is treated as no backup.

Compatibility Guarantees

Scope: what callers, on-disk artifacts, and operators may rely on across hydb releases. Ordering by blast radius: on-disk format > WAL replay > public API > MVCC contract > MSRV. A break in a higher tier is a strictly more serious incident than a break in a lower one.

29.1 Versioning model

  • Five version stamps: crate API (SemVer per hy-*), page (PageHeader.format_ver:u16), segment (SegmentHeader.format_ver + encoding_tag:u16), WAL (WalFileHeader.wal_ver + per-record discriminant), catalog (CatalogHeader.catalog_ver, schema_epoch:u64). Four independent on-disk axes (page/segment/wal/catalog); a release pins one tuple in a root MANIFEST page (seg 0, PageId 0), and the engine refuses an unrecognized MANIFEST (no layout guessing).

29.2 On-disk format compatibility (most critical guarantee)

Invariant FMT-1: an older engine MUST refuse a newer format cleanly (ErrorKind::FormatTooNew { found, supported }, exit 75) and MUST NEVER misread newer bytes as older layout.

  • Magic + version at byte 0 of every persisted unit: page b"HYPG"+format_ver; segment b"HYCS"+format_ver+encoding_tag; WAL b"HYWL"+wal_ver; manifest b"HYMF".
  • Backward read: engine N reads [min_supported_ver, N] (default min=N-2). Forward read: unsupported (found > N → refuse, never partial-parse). Magic+version at byte 0 of every unit (page HYPG+format_ver+kind, layout per §8.1); headers length-prefixed + append-only, older readers skip trailing unknown bytes iff in window, a field changing existing-byte semantics requires a format_ver bump.

29.2.1 Migration / upgrade path

  • Upgrade is explicit, offline-by-default: hydb recover opens the old store, then hydb compact --rewrite rewrites RowGroups/segments to the new format_ver/encoding_tag via the tuple-mover codepath; in-place page upgrade only for byte-compatible header growth, else rewrite-via-compact. Downgrade NOT supported (<N open of an N-touched store → FMT-1 refusal; back up before upgrade). Migration is journaled — the MANIFEST bump is the last write under a Checkpoint, so a crash mid-migration leaves the old version (atomic flip).

29.3 WAL format + cross-version replay

Invariant WAL-1: recovery replays a WAL from versions [min_wal_ver, N]; wal_ver > N → refuse before analysis.

  • WalRecord is #[non_exhaustive], discriminants append-only and never reused (Begin/Insert/Update/Delete/Commit/Abort/Clr/ColumnFlush/Checkpoint = 0..8, new types 9+). An unknown discriminant during redo of a newer WAL → refuse (never skip a redo — breaks repeat-history). A clean Checkpoint lets a newer engine start replay from there without parsing pre-upgrade tails (if in window). The upgrade procedure (Compatibility Guarantees) drains the WAL to a checkpoint via hydb checkpoint+recover before the version flip, so old-format mid-txn tails are never replayed.

29.5 New encodings without breaking readers

  • Encoding #[non_exhaustive]; on-disk identity is encoding_tag: u16 (not the Rust discriminant). Registry (LOCKED): 0=Plain,1=Dictionary,2=Rle,3=BitPacked,4=FrameOfReference; new encodings claim 5+ and bump segment format_ver. An unknown tag inside the read window is impossible by construction (new encoding ⇒ format_ver bump the old reader rejects via FMT-1); an unknown tag at a supported format_ver = corruption (UnknownEncoding). The Compressor chooser may change freely — only decoders are a compatibility surface.

29.6 Public API stability (SemVer)

  • Stable surfaces (1.0 freeze): HybridTable, get/scan, TxnManager/Transaction/Snapshot, IsolationLevel, ScanSpec, Datum, DataType, hydb subcommands + flags + exit codes (0 ok / 65 data / 74 IO / 75 format-too-new). SemVer: breaking → major, additive-on-#[non_exhaustive] → minor, doc/internal → patch. NOT stable (minor-breakable): BufferPool eviction, TupleMover scheduling, Compressor heuristics, ColumnBatch width, B+Tree fanout, byte-internal helpers; bench/analyze stdout content.

29.7 MVCC / isolation contract

  • Snapshot Isolation (default) + Read Committed are stable contracts — visible(h,snap) + version-chain semantics don't change across minor versions; a committed Snapshot read on D returns the same logical rows on any version that can open D, Vacuum reclaims only < oldest-live-snapshot (never observable). TxnId/Timestamp monotonic, encoded in the page format (Compatibility Guarantees).

29.8 MSRV policy

  • MSRV = Rust 1.78, edition 2021; bump = minor (CHANGELOG-announced, never a patch); CI builds on {MSRV, stable, beta}, an MSRV-raising PR justifies it in its ADR row.

29.9 Differential-parity guarantee

  • DIFF-1: on the supported operation set, hydb results MUST match SQLite (OLTP point/range) and DuckDB (OLAP scan/aggregate) bit-for-bit on the same dataset, modulo documented exceptions. Verified in Phase 13 (## 25).
  • Supported op set: point get, range scan, projection, predicate filter, SUM/COUNT/MIN/MAX/AVG, single-key GROUP BY hash aggregation, INSERT/UPDATE/DELETE, SI/RC visibility.
  • Documented exceptions (NOT parity bugs): F64 aggregation ordering/rounding (IEEE non-associativity → tolerance 1 ulp for SUM/AVG); NULL ordering in min/max (NULLs excluded, matches both); Decimal rounding mode = half-even (banker's), asserted equal to DuckDB, may differ from a SQLite build using a different mode.
  • Parity is a regression gate: a divergence outside the documented exceptions fails CI and blocks release. Differential corpus + seeds are committed for reproducibility.

  • Steady-state scan = zero-alloc: ColumnBatch/SelectionVector pool-allocated once per scan thread, reused per batch (debug allocator hook asserts 0 allocs in the batch loop after warmup). 26.4 Row-vs-column layout: cache locality & SIMD

Row vs column: access — row touches 1 cache line (all cols) vs column = dense contiguous run; point get — row wins (single line, no gather) vs column loses (gather across segments); full scan/agg — row loses (~1 useful B/64 B line) vs column wins (16× i32/line); SIMD — row hard (mixed/padded) vs column natural ([i32;N]→AVX2/512).

  • Quantified: SUM over 1 col of a 20-col table — row reads ~20× the bytes; column decode is SIMD → ≥ 8× speedup (matches OLAP target). SIMD kernels: filter (compare→mask→compact), SUM/MIN/MAX (horizontal reduce), dict decode (gather), BitPacked unpack (shift/mask); std::simd + scalar fallback, runtime AVX2/AVX-512/NEON dispatch. Verify via cargo asm/perf annotate (vpaddd/vpcmpgtd in the loop), regression-gate on cyc/row.

26.5 Lock / latch analysis

Contention → mitigation → target: BufferPool frame table → shard (4×cores) + CAS pins (<2% latch time at 200 K txn/s); BTree nodes → optimistic version-validated reads, pessimistic only on split/merge (≈0 reader stalls absent splits); WAL tail → group commit (Performance Engineering); TupleMover vs readers → immutable main + atomic pointer swap, readers keep old RowGroups via epoch (swap ≤100 µs, zero stall); Vacuum vs scans → epoch reclamation < oldest snapshot (no scan blocked). Lock-free reads; writers serialize only at WAL append + DeltaStore slot alloc.

26.7 Zone-map pruning & encoding effect on scan throughput

  • ZoneMap skips segments when predicate ∉ [min,max] → effective scan = (1−prune_ratio)×data (SSB target ≥80% skip → ≥5× cut). 26.8 Tuple-mover impact on foreground tail latency

  • Risk: background merge steals CPU / I/O / pool frames → inflates OLTP p99. Controls: rate-limited I/O (token bucket ≤ 50% device BW); lower-priority merge threads (½ cores, capped); merge reads via a cold-ring pool hint (no OLTP-hot-set pollution); bounded arena. Gate (under --htap): p99 inflation ≤ 1.5×. Atomic swap (Performance Engineering) means readers never block on merge — only resource contention affects tails, hence the rate limits. Scalability Analysis

Single-node, embeddable engine. "Scale" = vertical (cores, RAM, disk/NVMe bandwidth) + algorithmic growth of metadata/working-set, NOT horizontal. The distributed/replicated/sharded axis is explicitly out of scope (→ #36, #86, #102). This section quantifies how each internal dimension grows and where it caps.

Scaling with data size

Driver / growth / limit: working set vs pool (linear in hot pages; OLTP needs RowStore+BTree resident, target hit-rate >98% when working set ≤ pool); column compression (sublinear; 4–10× over Plain → a 50 GiB raw table fits ~6–12 GiB resident, scanned off-disk); RowGroup metadata (linear in #groups = ⌈rows/65 536⌉; ~few KiB/group → 1e9 rows ≈ 15.3 k groups ≈ tens of MiB resident, pruning O(#groups) SIMD/branch-light); delete vector (1 bit/row, 8 KiB/group worst case; skewed deletes waste scan until merge).

  • Pitfall: too-small row groups → metadata blowup + poor run-length; too-large → coarse pruning + long merge stalls. 65 536 is the locked tradeoff.
  • Cold-data ceiling: when working set > pool, point lookups become disk-bound (eviction thrash). Scans stay viable via sequential RowGroup streaming + prefetch (disk-bandwidth-bound, not IOPS-bound).

Scaling with write rate

LSM-like delta/main dynamic. All writes → row-format DeltaStore; TupleMover periodically merges → compressed MainStore.

write rate W (rows/s) ─┐
                       v
   DeltaStore size grows linearly until merge ──► merge cost ∝ (delta_rows + main_rows touched)
                       │                                         │
            merge trigger: delta_bytes > θ  OR  delta_rows > N    │ write amplification A ≈ rewritten_bytes / new_bytes
                       │                                         │
              higher θ → bigger deltas → slower merge-driven scans, but lower A
              lower θ  → frequent small merges → higher A, fresher main, faster scans
  • Write-amplification / merge-cost: merge rewrites whole touched RowGroups (immutable MAIN), A grows with delta↔main key overlap; mitigate with key-range-partitioned RowGroups (append-mostly → A≈1). Steady state: sustainable W ≤ merge throughput; if W exceeds it, delta grows unbounded → scan degrades linearly (backpressure: throttle writers / parallel merge). Targets: delta insert ≥ 200 k rows/s/core; merge ≥ 1–2 M rows/s aggregate.

Scaling with concurrency

  • Readers scale linearly, lock-free: a Snapshot is taken once, visible() is pure over TupleHeader; N readers ≈ N× throughput until memory-bandwidth-bound. Writer contention: only on the id/commit-ts oracle (atomic, ~tens ns), Wal append (group-commit-amortized), per-page leaf latch — no global lock. Writer↔TupleMover: merge reads a delta snapshot, writes segments, then atomically swaps the MainStore pointer (RCU) — contention only at swap + delta-truncate (hot-leaf skew mitigated by leaf splits / per-group delta). Vacuum runs concurrently on GC-eligible chains only.

Scaling with scan size

  • Vectorized throughput: ColumnReader::scan → ColumnBatch, SIMD kernels, late materialization; ≥ 1 GiB/s/core decoded, ≥ 2–5 G values/s filter on BitPacked/FoR. Parallel row-group scan: independent groups fan out across cores (per-thread hash tables → final combine), near-linear to core count then memory-bandwidth-bound. Pruning amplifies: ZoneMap skip + delete-vector → scan cost ∝ surviving data, not table size.

Vertical-scaling ceiling (single node)

Resource caps / saturation: CPU cores (parallel scan/merge/agg → flattens at memory-bandwidth wall before core exhaustion); RAM (pool + resident MAIN + delta + hash tables → eviction thrash, merge can't keep delta resident); NVMe bandwidth (WAL+checkpoint+segment writes → group-commit latency ↑, merge falls behind); fsync latency (per-txn 0.1–10 ms dominates commit).

Bottlenecks + mitigations

Bottleneck → mitigation: WAL fsync → group commit (≥10–50 k commits/s/device); tuple mover under heavy writes → parallel per-RowGroup merge, range-partitioned groups, writer backpressure; Vacuum lag (long txn pins oldest snapshot) → bounded snapshots (max txn age, snapshot-too-old), xmin-horizon monitor; skewed delete vector → periodic force-compaction on delete-density threshold; oracle/leaf-latch hot spot → atomic counters, leaf split, per-key-range delta partitions.

Where a distributed layer takes over

Vertical limits hit when: dataset > single-node RAM for the desired scan latency, write rate > one node's WAL/merge bandwidth, or HA/geo-replication required. Beyond this, sharding by key range / partition + replication is needed — explicitly out of scope for this engine. A distributed coordinator (#100/#101 distributed txn; #36/#86/#102 replication/distribution) would layer over multiple instances of this storage engine, each owning a shard, with cross-node MVCC and 2PC above the single-node TxnManager. This engine's job ends at the single-node HybridTable API boundary.

Mental Models & First Principles

The compressed insights a storage-engine expert holds. Each: the model, what it predicts, the bug class you write without it, and the resolving § of this blueprint.

MM1 — The WAL is the database; pages are a cache. Insight: cluster state is the replay of the log; data pages, B+Tree nodes, and column segments are reconstructible caches of it. Predicts: durability reduces to one observable — "is the LSN flushed?" — and backup = WAL + last checkpoint, nothing else. Bug class without it: acking a commit before its Commit record is fsynced (silent lost-update on crash), or flushing a dirty page ahead of its log (unrecoverable corruption). Applied in: §6.1, §6.6; I1 (INV-WAL), I2 (INV-DUR); Phase 3 (§15); Phase 12 (§24).

MM2 — One logical row, two physical layouts, one MVCC clock. Insight: DeltaStore (row) and MainStore (column) are projections of one row set, not two datasets; every live row is visible in exactly one. Predicts: count(*) = live(delta) + live(main) always, and the merge boundary is the single highest-risk window. Bug class without it: a row left in delta and re-encoded into main — double-counted in aggregates, resurrected after delete. Applied in: §6.2; I3 (INV-MULTISET); Phase 9 (§21) shadow_filter; Phase 10 (§22) atomic swap.

MM3 — Visibility is a pure function, frozen at snapshot time. Insight: visible(h, snap) reads no clock and no live oracle state inside; the commit-ts oracle is sampled once when the Snapshot is taken and frozen into snap.active/snap.ts. Predicts: row-path and column-path reads of the same RowId agree by construction because they call the identical predicate. Bug class without it: branching visibility on wall-clock or live oracle state → two readers at the same snapshot disagree → differential tests diverge from SQLite. Applied in: §6.5; I5 (INV-VIS); §8.7; Phase 4 (§16).

MM4 — Recovery is repeat-history-then-undo, and it must be idempotent. Insight: ARIES redoes all logged changes (winners and losers) from recLSN, gated by pageLSN, then undoes losers, logging a CLR per undone action. Predicts: a crash during recovery converges to the same state on re-run — the CLR undo_next chain resumes, never re-applies. Bug class without it: redoing a change onto a page that already has it (no pageLSN gate → double-applied increment), or undo without CLRs (re-crash re-reverses already-reversed work). Applied in: §6.7; I8 (INV-REC); Phase 3 (§15); Phase 12 (§24).

MM5 — A single durable commit edge defines the recovery rule. Insight: every multi-step state change has exactly one durable edge — Commit{ts} for a txn, MergeCommit/ColumnFlush for a merge — and recovery's rule is "before the edge → discard, after → redo." Predicts: a half-written tuple-mover merge is always safe — its segments are orphaned and reaped if MergeCommit never became durable. Bug class without it: trimming the delta before MergeCommit is durable → committed rows vanish from both delta and main. Applied in: §27.3, §27.11; Phase 10 (§22); Phase 12 (§24).

MM6 — Zone maps may over-include but must never under-include. Insight: a ZoneMap{min,max,null_count} is an optimization layered over correctness; a false positive (scanning a non-matching segment) wastes time, but a false negative (skipping a matching segment) silently drops result rows. Predicts: pruning may only skip a segment when the predicate range is provably disjoint from [min,max] and NULL-aware. Bug class without it: comparing dictionary codes instead of decoded values, or tightening bounds from the delete vector → a matching segment skipped → rows missing, undetectable without a --no-prune parity run. Applied in: §6.12; INV-ZONE; Phase 7 (§19).

MM7 — Decode speed, not compression ratio, bounds scan latency. Insight: scans are memory-bandwidth- and decode-bound; lightweight encodings (dict/RLE/bit-pack/FoR) are chosen because they decode O(values) SIMD-friendly and are predicate-pushable, not because they compress best. Predicts: a general block compressor (zstd) with a better ratio can be slower on scan because it must decompress a whole block before any value is accessible, defeating late materialization and zone-map skipping. Bug class without it: picking encodings by ratio alone → OLAP SLOs blown despite smaller files. Applied in: §6.10, §6.11; ADR-10; Phase 6 (§18); Phase 8 (§20).

MM8 — Immutability is what makes lock-free reads and atomic swap possible. Insight: because a published RowGroup/ColumnSegment is write-once, concurrent readers scan it without latches, zone maps are freely shareable, and a merge publishes by a single pointer swap (ArcSwap) of new segments — deletes go to a separate delete vector, never edit segment bytes. Predicts: a reader holds an immutable epoch for its whole scan; the swap is all-or-nothing. Bug class without it: mutating a segment a reader is mid-scan over → torn read / use-after-free on shared decoded slices → SI broken. Applied in: §6.3, §6.13; I4 (INV-IMMUT), I7 (INV-SWAP); Phase 5 (§17); Phase 10 (§22).

MM9 — GC safety is one watermark: the oldest live snapshot. Insight: a version may be freed only when invisible to all current and future snapshots — i.e. its successor is committed and it is older than oldest_live = min(active Snapshot.xmin). Predicts: a single long-running reader pins the watermark low and blocks all reclamation, so version-chain bloat and delta-drain stalls are a policy symptom (a forgotten commit/abort), not a GC bug. Bug class without it: freeing a version still visible to a long reader → that reader sees a gap; unrecoverable, hence the hard pre-free assert. Applied in: §6.4, §6.9; INV-VAC; Phase 4 (§16); §27.6.

MM10 — Fail closed: a wrong answer is worse than a crash. Insight: the severity ladder puts S0 (silent wrong result / lost commit) above S1 (unavailability) — a query that answers wrongly is more dangerous than one that refuses, because the caller trusts it. Predicts: every corruption path ends in detect (CRC) → contain (bounded decode) → recover (WAL/re-merge) → else quarantine + loud error; a result is served only past the invariant check. Bug class without it: a _ => catch-all over WalRecord that silently drops a record during redo, or a decoder that returns guessed bytes on corruption. Applied in: §6.15, §27.11; the Threat Model; Phase 13 (§25) differential gate.

SQL Server Columnstore. The one decision it made differently: deletes against the compressed store use a separate delete bitmap (B-tree) and updates are delete+insert-into-delta, with a tuple-mover that only compresses a delta rowgroup once it fills (~1M rows) rather than on a time/size threshold. Oracle Database In-Memory. The different decision: the columnar mirror (the IM column store) is purely in-memory and non-durable — it is repopulated from the durable row store on instance restart, so there is no columnar recovery problem at all (our Phase 12, by contrast, must rebuild MAIN from the WAL). Its niche: it wins when you already run Oracle for OLTP and want to flip analytics on with a memory grant and zero schema change — the row store remains the single source of truth and the column format is a disposable accelerator.

SAP HANA. The architectural ancestor of this design: row delta + columnar main + background delta merge, deletes via a delete vector. The difference at scale is that HANA is in-memory-first and scale-out (data spread across a cluster, the column store is the primary persistent form). Its niche: large enterprise HTAP where the whole working set is held in RAM across many nodes and column-store-as-primary maximizes analytical density; we deliberately keep the same delta/main shape but single-node and disk-resident.

DuckDB. The different decision: no persistent row tier — it is columnar end-to-end with optimistic MVCC, optimized for bulk-load-then-analyze rather than high-rate point writes; its delta is transient. Its niche: it wins decisively as an embeddable OLAP engine for interactive analytics on files/data frames where point-update throughput is irrelevant; it is precisely our OLAP differential oracle (ADR-21, R1) for exactly this reason — same columnar semantics, opposite write bias.

Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from the §4 System Constraints (page 4 KiB; row group 65 536 rows; OLTP ≥ 200 k txn/s; OLAP scan ≥ 1–2 GiB/s/core; commit p99 ≤ 5 ms; compression ≥ 4×). Formulas shown.

1. Row-group on-disk size (Plain i64, 16 columns):

cols × n_rows × width + null_bitmaps + headers
16 × 65 536 × 8 B = 8,388,608 B = 8 MiB values
+ 16 × ceil(65 536/8) B null bitmaps = 16 × 8 KiB = 128 KiB
+ 16 × 32 B segment headers ≈ 512 B
→ ~8.13 MiB/row-group Plain; one row group spans 8.13 MiB / 4 KiB ≈ 2,080 pages

2. Compressed row-group size (target ≥ 4×):

8.13 MiB / 4 (ADR-10 target ratio) ≈ 2.03 MiB/row-group compressed
→ resident pages per group ≈ 2.03 MiB / 4 KiB ≈ 520 pages

3. RowGroup metadata for 1e9 rows:

#groups = ceil(1e9 / 65 536) = 15 259 groups
per-group metadata = ZoneMaps(16 cols × ~40 B) + segment descriptors(16 × ~24 B)
                     + delete vector(ceil(65536/8)=8 KiB) ≈ 8 KiB + ~1 KiB ≈ 9 KiB
15 259 × 9 KiB ≈ 134 MiB metadata, all resident
→ pruning is O(#groups): 15 259 branch-light ZoneMap checks ≈ tens of µs/scan

4. Effective resident footprint of a 50 GiB raw table:

50 GiB raw row form / 4× (compression) ≈ 12.5 GiB columnar
→ fits in a 16 GiB buffer pool: scanned without touching disk after warm-up
→ confirms §4 claim: compression extends the in-memory working set ~4×

5. WAL write bandwidth at OLTP target:

200 000 txn/s × (avg 1 row × ~64 B payload + ~33 B WalRecord header/CRC) ≈ 200k × 97 B
= 19.4 MB/s sequential WAL write
at 64 MiB segment rotation: new segment every 64 / 19.4 ≈ 3.3 s
→ trivial for NVMe (GB/s class); WAL bandwidth is never the OLTP bottleneck — fsync rate is

6. Group-commit fsync amortization needed for 200 k txn/s:

NVMe sustains ~10 000–50 000 fsync/s
required group factor = 200 000 txn/s ÷ 20 000 fsync/s = 10 txns per fsync (minimum)
within the ≤1 ms linger window at 200k txn/s: 200 000 × 0.001 = 200 txns available to batch
→ 200 ≫ 10: group commit (ADR-13) comfortably hits the target; p99 bounded by the 1 ms linger

100e6 rows × 8 B = 800 MB to decode (Plain); compressed (FoR, 4×) ≈ 200 MB read
at decode ≥ 1.5 GB/s/core (decoded bytes): 800 MB / 1.5 GB/s ≈ 533 ms
→ exceeds the §4 "≤250 ms/core" target → REQUIRES either ≥2 cores OR zone-map pruning
   OR ≥3 GB/s SIMD decode; confirms parallel row-group scan is mandatory at 100 M rows

8. Buffer-pool hit-rate requirement for OLTP point get p99 ≤ 50 µs:

warm get ≈ 1.5 µs (in-pool); cold get ≈ 60 µs (1 SSD page read, §13 Phase 1)
to keep p99 ≤ 50 µs, fraction of cold reads f must satisfy: f × 60 µs ≤ ~50 µs at p99
→ p99 is the 99th pct: need < 1% cold ⇒ buffer-pool hit-rate ≥ 99% on the OLTP working set
→ drives the "working set ≤ pool size" sizing rule (Scalability Analysis)

9. Delta size at merge threshold and its scan tax:

default merge trigger = 65 536 rows OR 64 MiB OR 5 s (§22 Phase 10)
at 200 k txn/s, the 65 536-row trigger fires every 65 536 / 200 000 ≈ 0.33 s
→ delta holds ≤ ~65 k rows between merges; a scan pays row-format DeltaScan over ≤65 k rows
   added to a columnar MAIN scan of millions → delta tax < 1% when main ≫ 6.5 M rows (§21 target)

10. Merge (tuple-mover) throughput vs sustainable write rate:

merge cost ≈ pivot(O(rows)) + encode; target encode ≥ 200 MB/s/core (§18), aggregate ≥ 1–2 M rows/s
sustainable write W must satisfy W ≤ merge_throughput else delta grows unbounded
at 1.5 M rows/s merge and 200 k txn/s (≈200 k rows/s) write: headroom 7.5× → mover keeps up
→ if write spikes > 1.5 M rows/s, backpressure (ADR-18 / §27.4) engages; this is the HTAP write ceiling

11. FD budget per open table:

file-per-segment (ADR-20): segments = column segments + dict segments + row-store segments + WAL
for a 1e9-row table: 15 259 groups × 16 cols ≈ 244 k segment files IF one file per segment
→ this is why FileManager packs many segments per physical file (segment = page-run within a file):
   open files ≈ #row-store-segment-files + #column-segment-files (grouped) + 1 WAL + 1 manifest ≈ tens
→ confirms the FD budget needs segment-packing, not literal one-file-per-SegmentId

12. Snapshot capture cost at high txn rate:

Snapshot = {xmin, xmax, active: Box<[TxnId]>}; capture copies the active set under a lock
at 200 k txn/s with avg txn duration 50 µs: steady active set ≈ 200 000 × 50e-6 = 10 active txns
copy of 10 × 8 B TxnId = 80 B per snapshot → negligible (~tens ns)
→ confirms snapshot capture is not a bottleneck until active set ≫ thousands (long-txn pathology, §27.6)

Alternative Architectures (Roads Not Taken)

Three fundamentally different architectures for the same HTAP-storage problem (not parameter tweaks). Each: sketch, regime where it wins, the real system that embodies it, why this blueprint rejected it.

Alternative 1 — Single columnar store with an in-memory write buffer (no persistent row tier)

writes ──> in-RAM write buffer (columnar mini-blocks, optimistic MVCC)
               | flush on size
               v
        immutable columnar row groups (the ONLY persistent form)
               ^
        reads ─┘  point + scan both hit columnar (point = gather across segments)

Regime where it wins: bulk-load-then-analyze workloads with negligible high-rate point updates — interactive analytics over files/data frames, ELT pipelines. The row tier is dead weight when "recent" data is also scan-dominant; removing it halves storage and eliminates the merge's row→column pivot.

Real system that embodies it: DuckDB (columnar end-to-end, optimistic MVCC, transient write buffer).

Why rejected: §1 makes high-rate OLTP point writes a first-class goal; a point get/update on a columnar store gathers across N segments and pays decode on the write path — Performance Engineering quantifies the row layout winning point access by reading ~20× fewer bytes. Without a row delta, every point update would decompress+recompress a block (the exact cost ADR-7 rejects).

Alternative 2 — LSM-tree storage with columnar SSTables

writes ──> in-memory memtable (row/KV) ──flush──> L0 SSTables ──compact──> L1..Ln
                                                       |                     |
                                            (each SSTable: columnar blocks + min/max)
                                                       v
                            reads merge overlapping sorted runs across levels (+ bloom filters)

Regime where it wins: write-saturated workloads where sequential-write amortization is the binding constraint and reads tolerate merging several sorted runs; very large datasets that must spill to disk with tiered compaction managing hot/cold automatically.

Real system that embodies it: RocksDB / LevelDB (LSM); ClickHouse MergeTree is the columnar-SSTable + background-merge analogue (and a reference impl, R5).

Why rejected: a scan must merge overlapping runs across all levels, so scan latency degrades with run count — the opposite of the bounded, single-pass columnar scan the OLAP target demands (§4). LSM read amplification + compaction stalls violate the p99 write-latency target unpredictably (ADR-7 rationale). The delta/main model is the columnar-HTAP analogue of LSM compaction (§2.4, project 68) but with exactly one read-time run (delta+main), not a tower.

Alternative 3 — Two separate systems (OLTP row store + OLAP column store) joined by ETL/CDC

   OLTP row DB  ──change-data-capture / nightly ETL──>  OLAP column DB
   (Postgres)                                            (warehouse)
        |                                                     |
   point reads/writes                                    analytical scans

Regime where it wins: when OLTP and OLAP have wildly different SLAs, hardware, and teams, and minutes-to-hours of analytical staleness is acceptable — the classic separation that lets each engine be best-of-breed and scale independently. Operationally simplest when the two already exist.

Real system that embodies it: the canonical operational-DB + data-warehouse split (e.g. Postgres/MySQL replicated into Snowflake/Redshift/BigQuery via CDC such as Debezium).

Why rejected: this is precisely the architecture §2.2 identifies as the problem HTAP exists to solve — the ETL gap (stale analytics), 2× storage, and 2× operational burden. The entire thesis of this engine is one copy of data, two access paths under one MVCC clock (§6.2, MM2); accepting two systems abandons the learning objective and the freshness guarantee that motivates the project.

Glossary

Terms defined as used in THIS engine; cross-references in italics. Type/crate names are spine-exact.

Term Definition (implementation-relevant)
HTAP Hybrid Transactional/Analytical Processing. One engine serves OLTP point writes/reads and OLAP scans/aggregations over the same data without ETL, via delta/main + dual row/column formats.
OLTP Online Transaction Processing. High-rate point inserts/updates/deletes/lookups, latency-sensitive (target p99 point lookup < 50 µs warm). Served by row store + primary index + delta store.
OLAP Online Analytical Processing. Large scans/aggregations over many rows, throughput-sensitive (target ≥ 1 GiB/s/core decoded). Served by column store via vectorized execution.
row store Write-optimized heap of slotted pages (RowStore, hy-row). Stores whole tuples contiguously; backs point lookup/update; physical home of the delta store.
column store Read-optimized MainStore (hy-col): immutable row groups of column segments, each light-weight encoded, with zone maps. The OLAP scan target.
delta store DeltaStore (hy-store): recent writes in row format + per-row validity bitmap. Absorbs all inserts/updates fast; merged into main by the tuple mover.
main store MainStore (hy-store): immutable compressed columnar row groups + a delete vector. Never updated in place; rebuilt at each delta/main merge.
delta/main merge Background conversion: drain GC-safe delta rows + surviving main rows into new compressed row groups, choose encodings, write column segments, atomically swap, drop merged versions + reset delete vector. SAP-HANA model.
tuple mover TupleMover (hy-store): the component that runs the delta/main merge + row→column conversion + version GC, MVCC-safe under concurrent readers. Triggered by delta-size/age thresholds or hydb compact.
row group RowGroup (hy-col): unit of columnar storage/encoding/zone-map/delete-vector/merge. Default 65 536 rows. Trades scan parallelism + pruning granularity vs per-group metadata overhead.
column segment ColumnSegment (hy-col): one column's values for one row group: { col, encoding, zone, n_rows, null_count, data: SegmentId }. The decode/scan unit.
encoding Per-segment compression scheme (Encoding), chosen by the Compressor from ColumnStats: Plain, Dictionary, Rle, BitPacked, FrameOfReference. Decode must be O(values), SIMD-friendly.
dictionary encoding Dictionary{ dict }: distinct values → small codes + a dict segment. For low-cardinality strings/ints; enables predicate eval on codes.
RLE Run-length encoding (Rle): (value, run-length) pairs. For long runs / sorted or clustered columns.
bit-packing BitPacked{ bits }: pack integers into ceil(log2(range)) bits/value. For small-range integers / dictionary codes.
frame-of-reference FrameOfReference{ base, bits }: store base + small bit-packed deltas. For clustered near-values (e.g. timestamps, IDs).
zone map ZoneMap{ min, max, null_count } per column segment. Enables segment/row group skipping when a predicate cannot match its [min,max].
delete vector Bitmap per row group marking main rows deleted since the last merge. Applied at scan time; physically removed at the next delta/main merge.
selection vector SelectionVector(Vec<u32>): surviving row indices after a predicate. Threaded through operators so later ops touch only selected rows.
late materialization Decode only the surviving rows (per selection vector) of projected columns, and as late as possible — minimizes decode work and memory.
vectorized execution Batch-at-a-time processing: filter/project/aggregate over a column batch (1024–2048 values) + selection vector, amortizing dispatch and enabling SIMD kernels.
column batch ColumnBatch (hy-col): up to 1024/2048 decoded values + a selection vector; the unit of vectorized execution and scan() -> BatchIter output.
slotted page SlottedPage (hy-row): 4 KiB page with a slot directory growing from the front and tuple heap from the end; slots indirect to variable-length tuples, allowing in-page compaction without RowId change.
tuple Tuple{ header, payload } (hy-row): one row's MVCC version; payload decoded against a Schema. Identified by RowId{ page, slot }.
tuple header TupleHeader: in-tuple MVCC metadata { txn_min, txn_max, next_version, flags, null_bitmap }; basis of visibility and the version chain.
buffer pool BufferPool (hy-page): in-memory frame cache over segment files; clock/LRU eviction, pin counts, dirty flags. Enforces log-before-data (no dirty flush before its WAL is durable).
page guard PageGuard (hy-page): RAII pin; derefs to &Page/&mut Page, unpins on drop. Prevents eviction of in-use pages and leaked pins.
pin / eviction Pin = increment frame use count (cannot be evicted while pinned). Eviction = clock sweep selects an unpinned, ideally clean frame; dirty victims flushed (WAL-gated) first.
B+Tree BTree (hy-index): primary index keyed by primary-key bytes; internal separators, leaves hold RowId lists. Supports point lookup + range scan; crash-safe page writes; node split/merge.
primary index The B+Tree mapping primary key → RowId for the row store/delta; the OLTP get/update access path.
point lookup Single-key fetch: lookup(key, snap) -> Option<RowId> then row read, filtered by visibility. Routed to the row+delta path by the access-path router.
range scan range(lo, hi, snap) -> RangeIter: ordered key-range traversal over B+Tree leaves.
write-ahead log Wal (hy-wal): append-only WalRecord stream with group commit + flush(lsn). Source of truth for redo/undo.
log-before-data WAL invariant: a page's change is durable in the WAL (its pageLSN ≤ flushed Lsn) before that dirty page reaches disk.
ARIES The recovery algorithm: analysis → redo → undo, with CLRs and physiological logging. Recovery (hy-wal) implements it.
analysis / redo / undo ARIES phases: analysis rebuilds ATT + DPT from the last checkpoint; redo repeats history from each page's recLSN (idempotent via pageLSN); undo rolls back losers, logging CLRs.
CLR Compensation Log Record (Clr{ txn, undo_next }): logs an undo action so undo is idempotent across repeated crashes; undo_next skips already-undone work.
checkpoint Checkpoint/CheckpointRec: periodic snapshot of ATT + DPT (+ column-flush state) bounding recovery scan length. Fuzzy (non-quiescent).
pageLSN The Lsn of the last update applied to a page, stored in its PageHeader. Gates redo idempotency: skip redo when pageLSN ≥ record.lsn.
recLSN Recovery LSN: the earliest Lsn that may have dirtied a page, recorded in the DPT. Redo starts from min(recLSN).
dirty page table (DPT) Map page → recLSN of unflushed updates; rebuilt in analysis, bounds redo start.
active transaction table (ATT) Map TxnId → state/lastLSN of in-flight txns; rebuilt in analysis, drives undo of losers.
MVCC Multi-Version Concurrency Control: updates/deletes create new tuple versions (no in-place overwrite); readers see a consistent Snapshot. Writers never block readers.
snapshot isolation IsolationLevel::SnapshotIsolation: each txn reads a fixed Snapshot; visibility uses xmin/xmax/active set + commit timestamp.
read committed IsolationLevel::ReadCommitted: a fresh Snapshot per statement, so each statement sees latest committed data.
version chain Logical chain of a row's versions via RowId.next_version in each tuple header; walked under a Snapshot to find the visible version.
visibility visible(h, snap) -> bool: SI predicate — version visible iff txn_min committed before snap AND not in active AND (txn_max=0/uncommitted OR committed after snap).
commit timestamp Monotonic Timestamp assigned by the TxnManager oracle at commit; orders versions and defines snapshot boundaries.
vacuum / GC Vacuum (hy-txn): reclaims tuple versions older than the oldest live Snapshot; also drops delta rows already merged into main.
group commit Batch many txns' Commit records into one WAL fsync to amortize sync cost; raises commit throughput at small latency cost.
torn page A partially written page after a crash (sub-page atomicity). Detected/repaired via WAL redo + page checksum / double-write so recovery never trusts a half-written page.
access path AccessPath: chosen physical read strategy — RowLookup, IndexLookup, ColumnScan(ScanSpec), or DeltaScan.
access-path router hy-store component selecting an access path from the request shape + TableStats (rule + stats based, NOT a cost optimizer): point/get → row+delta; scan/aggregate → column+delta.
hash aggregation Build a hash table keyed by GROUP BY columns over column batches; accumulate SUM/COUNT/MIN/MAX/AVG per group. The OLAP aggregation operator.
table format TableFormat (hy-catalog): per-table config of which columns/row-groups are row vs column and the row group size; drives the tuple mover + access-path router.
q-error Statistics quality metric = max(est/act, act/est); tracked for ColumnStats/TableStats to gauge router/encoding-selection accuracy.
