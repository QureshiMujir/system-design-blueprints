Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If a Cascades OptimizeGroup task carries an upper bound b and the best lower bound for any group expression in the group exceeds b, the group is pruned. What invariant must hold for this to preserve the optimality of the final plan, and where in the codebase is it audited? (§6 P10, §7 I8, Phase 3 §3.6, Phase 5 §5.6, ADR-17, M11)
  2. A join R⋈S on R.id = S.r_id, where R.id is a primary key, has its cardinality bounded by card(S) — not the containment-formula product. Walk through the logical-property derivation that reaches this bound, and explain why omitting it causes q-error to compound multiplicatively on PK-FK schemas. (§8.6, §6 P6, Phase 7 §7.2, I11, MM3, MM7)
  3. The rewrite rule that pushes a predicate below an outer join's null-extended side must be guarded. Specify the exact guard condition in terms of null-rejecting semantics, explain what happens to the result multiset if the guard is absent, and identify which invariants and tests catch the violation. (§6 P1, Phase 4 §4.6, I1, I15, T2, ADR-16)
  4. DPccp generates each connected subgraph pair (S1, S2) exactly once by restricting the complement to a connected subgraph disjoint from S1. Explain why DPsub generates the same pair O(2^|S1|) times, and derive the complexity ratio between the two algorithms on a 12-relation star graph. (Phase 9 §9.2, ADR-07, MM8, M8, Moerkotte & Neumann 2006)
  5. The Cascades task model uses a LIFO stack rather than a FIFO queue. What property of the search does this preserve, and how does it interact with branch-and-bound's requirement that a parent's cost upper bound is known before children are pruned? (Phase 5 §5.2, §6 P10, Graefe 1995, ADR-06, I7)
  6. A HashJoin provides no interesting order on its output. A MergeJoin on the same keys provides the join-key order. Trace the full property-propagation path from a root ORDER BY c.name through a SortAgg to the join group, showing why MergeJoin saves an enforcer only when the join key order is a prefix of the required aggregate-group order. (§8.8, Phase 8 §8.2, Phase 6 §6.2, I5, I14, MM2, MM6, Selinger et al. 1979)
  7. The CardinalityEstimator trait is the seam for learned models (§10.9, ADR-18). What contract must a learned estimator fulfill to be a safe drop-in — specifically, which invariants (I6, I12) must it preserve, and what would a violation of I6 do to the branch-and-bound search? (Phase 2 §2.2, Phase 10 §10.9, ADR-18, I6, I8, I12, MM5)
  8. Describe the full cascade of failures triggered by a single incorrect key claim — specifically, R.a is claimed unique when it is not. Which estimation formula is affected, which plan shape is preferred as a result, and which conformance tests should catch it? (Phase 7 §7.6, Phase 2 §2.3, I11, MM7, P6, Phase 12 §12.4)
  9. A query decorrelates a scalar subquery WHERE c.total > (SELECT AVG(o.total) FROM o WHERE o.cust=c.id) into a left-outer-join with a grouped aggregate (§8.9). Identify the three-valued-logic edge case that makes this transformation non-trivial, state the invariant it must satisfy, and describe the differential test that would catch a violation. (§8.9, Phase 4 §4.6, I15, I1, ADR-16, P1)
  10. Branch-and-bound carries a cost upper bound from the root down to leaf groups. In a 10-relation query where the first OptimizeGroup call has no initial upper bound (the first plan hasn't been costed yet), how does the optimizer bootstrap a useful bound? Trace the task sequence. (Phase 5 §5.2, §5.7, Phase 9, ADR-17, I8, MM5)
  11. The memo's merge_groups operation is called when two groups prove logically equivalent. What must be true of all winners in the merged group, and what is the worst-case complexity of updating the winner map if the merge triggers a cascade of re-optimizations? (Phase 5 §5.2, §5.6, I2, I10, ADR-05, MM1)
  12. The GEQO fallback encodes a join order as a chromosome and evolves it via crossover. What property of crossover makes it possible to explore the bushy join space (not just left-deep), and why must the PRNG be seeded with a fixed value for the optimizer to satisfy I9? (Phase 9 §9.2, §9.6, I9, P9, ADR-19, MM8)
  13. A histogram bucket with lo > hi triggers I13 and causes the optimizer to fall back to uniform selectivity. Trace the path from the I13 audit failure to the final plan change, including which selectivity formulas are affected and what q-error the fallback introduces. (Phase 1 §1.6, Phase 2 §2.2, I13, I12, I6, Phase 7, P7)
  14. The cost model's lower_bound function must be admissible (never exceed true subtree cost). Propose a concrete lower bound for a HashJoin group expression and prove it is admissible. Then propose an inadmissible bound and show which test in Phase 5 catches it. (Phase 3 §3.2, Phase 5 §5.5, I8, ADR-17, MM5, M11)
  15. Extended multi-column statistics correct the independence assumption by using joint MCV / soft-FD-adjusted estimates. Explain the over-damping failure mode (ADR-13 "When Rejected Choice Wins"), state the condition that triggers it, and describe which fixture in Phase 10 is designed to detect it. (Phase 10 §10.6, ADR-13, I12, MM7, Leis et al. 2015)
  16. The optimizer's determinism invariant (I9) requires that identical (plan, catalog, stats, seed) inputs produce identical memo + plan + trace outputs. Identify the three most likely sources of non-determinism in a naive Cascades implementation and the mechanisms that suppress each. (§7 I9, Phase 9 §9.6, Phase 5 §5.6, ADR-19, P9, MM10)
  17. The explain output lists both estimated and true cardinalities in EXPLAIN ANALYZE mode. Describe how a rising p95_qerror metric at the root of the plan tree is a leading indicator of bad plans even before users report them, and trace the runbook path from that metric to the fix. (Phase 2 §2.10, Phase 10 §10.10, Phase 12 §12.6, ADR-23, MM3, Leis et al. 2015)
  18. A new operator TopK (Limit+Sort fused) is added to the physical plan IR. Enumerate every component that must change — IR, rules, property derivation, cost, explain — and identify which invariants' apply() methods must be updated to prove the operator is semantics-preserving. (§8.3, Phase 6 §6.2, Phase 7, Phase 8, I1, I5, I11, P4, ADR-08)
  19. The spill cost model makes a hash join's cost context-dependent on the memory budget. Explain how the cost of HashJoin(build=2M rows) changes as the budget varies from 2 GB to 256 MB to 64 MB, and which operator the branch-and-bound search should prefer at the 64 MB boundary. (Phase 3 §3.2, §3.6, Phase 5, ADR-10, MM5, §4)
  20. The decorrelation rule for NOT IN (subquery with a NULL) is flagged as the "single trickiest rewrite" (Phase 4 §4.6, I15). Construct a minimal three-row example that demonstrates the three-valued-logic difference between the correlated and the unnested plan, and identify which mechanism in the differential harness catches a violation. (Phase 4 §4.6, I15, I1, §8.9, P1, ADR-16)

Mental Models & First Principles

  1. MM1 — The memo is an implicit AND-OR graph: AND-nodes are group expressions (operator + child groups), OR-nodes are groups (equivalent expressions). Predicts: whether memoization shares a subplan across all parents that reference it, and when a group merge propagates new winners up. Without it: you write a planner that re-optimizes the same subtree per parent, wasting exponential time. Applied: §6 P2, Phase 5, ADR-05.

  2. MM2 — Physical properties are required top-down and provided bottom-up; unsatisfied requirements generate enforcers. Predicts: when a merge join eliminates a sort enforcer (provided order satisfies required order), and when a hash join forces one. Without it: you insert redundant sorts everywhere, or worse, run a merge join on unsorted input and produce wrong results (I5, I14). Applied: §6 P5, Phase 8, Phase 11.

  3. MM3 — Q-error compounds multiplicatively up the plan tree: a per-join error of k× over n joins produces k^n× total error. Predicts: that an innocent 4× per-join mis-estimate produces ~10^6× cumulative error over 10 joins, making a hash build sized for 1k rows when 1B rows arrive. Without it: you treat each operator's estimate in isolation and miss why the final plan is catastrophic. Applied: §8.6, Phase 2, Phase 10, D.9.

  4. MM4 — Transformation rules grow a group (logical→logical); implementation rules populate it with costable alternatives (logical→physical). They must never be conflated. Predicts: whether applying a commutativity rule to a physical operator is valid (it is not), and whether a new rule needs a cost model or just an equivalence proof. Without it: you allow physical operators to be transformed logically, generating semantically nonsensical group expressions that never terminate (I4). Applied: §6 P4, Phase 6, ADR-06.

  5. MM5 — Branch-and-bound preserves optimality only when the lower bound is admissible (never exceeds true subtree cost). Predicts: that a single inadmissible bound silently discards the optimal plan — the optimizer produces the wrong "best" plan with no error signal. Without it: you tighten the lower bound for speed and unknowingly start losing optimal plans on the exact queries that matter. Applied: §6 P10, Phase 5 (I8), Phase 3, ADR-17.

  6. MM6 — Interesting orders are the key to avoid re-sorting: a provided order that is a prefix of a required order satisfies it; no enforcer is needed. Predicts: when an index scan or merge join result can feed both the join condition and a downstream ORDER BY for free. Without it: you insert a sort after every join even when an index-provided order is already available — the System-R insight (Selinger et al. 1979) that a naive optimizer misses. Applied: §6 P5, Phase 8, §8.8, ADR-14.

  7. MM7 — The independence assumption (sel(p∧q) = sel(p)·sel(q)) is false on correlated columns; the only defenses are extended multi-column stats, key/FD bounding, and sampling. Predicts: that on real data (city='SF' AND state='CA'), the independent product dramatically under-estimates the conjunction selectivity, causing the optimizer to over-estimate intermediate cardinalities and pick the wrong build side. Without it: you build a textbook estimator that passes TPC-H (near-uniform) but catastrophically fails JOB (correlated, real-world data). Applied: §6 P6, §8.6, Phase 2 §2.6, Phase 10, ADR-13.

  8. MM8 — DPccp enumerates each (S1, S2) join pair exactly once by restricting complements to connected subgraphs; DPsub enumerates each pair 2^k times and is exponentially redundant. Predicts: that a correct DPccp implementation on a 12-relation query visits O(3^n) group expressions rather than O(4^n), and that a bug breaking the csg-cmp ordering causes the optimizer to crawl on 10+ relations. Without it: you implement DPsub, not DPccp, and wonder why the optimizer is 10× slower than expected on medium-sized join graphs. Applied: Phase 9, §9.2, ADR-07, M8.

  9. MM9 — The cardinality of a group is a logical property (shared by all group expressions); the cost of a group expression is a physical property (specific to one operator choice and its children). Predicts: that cardinality needs to be computed once per group (not per group expression) and cached, while cost must be re-derived for every physical alternative. Without it: you recompute cardinality inside the inner cost loop, wasting O(group_exprs) × estimate_cost per search step. Applied: §6 P2, Phase 5 §5.7, Phase 2 §2.7, I11.

  10. MM10 — Semantic preservation (the result multiset is identical) is the single non-negotiable invariant; any optimization that changes results is not an optimization but a bug. Predicts: that a rewrite which is sometimes faster but occasionally returns different rows (e.g. pushing a non-null-rejecting predicate below an outer join's null side) must be rejected unconditionally, regardless of its performance win. Without it: you allow conditional-correctness rewrites that corrupt data silently on the rare cases users care about most. Applied: §6 P1, Phase 4, I1, I15, T2.

Glossary · 57 terms · site-wide glossary

Query optimizer
the component that turns a logical query into an efficient physical execution plan via cost-based search.
Logical plan
a relational-algebra tree/DAG (what to compute), operator-canonical, catalog-bound.
Physical plan
an executable operator tree (how to compute it), with chosen algorithms + properties + cost.
Relational algebra
the operator set (Scan/σ/π/⋈/Γ/τ/…) the logical plan is built from.
Cost-based optimization
choosing a plan by estimated cost, vs heuristic/rule-only optimization.
Cascades / Volcano
the rule-driven, memo-based, top-down optimizer framework (Graefe) this project locks.
System-R
the seminal bottom-up DP optimizer (Selinger 1979); its join DP + interesting orders are embedded here.
Memo
the data structure holding all explored plan alternatives as equivalence groups (the search's working set).
Group (equivalence class)
a set of logically-equivalent expressions in the memo; the unit of memoization.
Group expression
one operator + its child groups (not child plans); the memo's node.
Winner
the lowest-cost physical group expression for a (group, required-properties) pair.
Task scheduler
the Cascades engine driving the search via a stack of tasks (OptimizeGroup/Expr, ApplyRule, …).
Transformation rule
a logical→logical rewrite that grows a group (join commute/associate, predicate move).
Implementation rule
a logical→physical rule producing a costable operator (Join→HashJoin, Scan→IndexScan).
Rewrite / normalization
heuristic, unconditionally-good logical rewrites applied before the cost-based search.
Predicate pushdown
moving filters as close to the scans as possible to reduce intermediate cardinality.
Projection pruning
removing columns no ancestor uses.
Constant folding
evaluating constant subexpressions at optimization time.
Subquery decorrelation / unnesting
rewriting a correlated subquery as a join (avoiding re-execution per outer row).
Transitive predicate inference
deriving new predicates from equalities (a=b ∧ b=c ⟹ a=c).
Common-subexpression (CSE)
a subplan computed once + shared (the plan is a DAG, not a tree).
Join enumeration
searching the space of join orders.
DPccp / DPhyp
dynamic programming over connected (hyper)graph subgraphs; optimal, cross-product-free join enumeration.
DPsize / DPsub
alternative subset DPs (by size / by subset); DPccp is more efficient (each join pair once).
Left-deep / bushy
join-tree shapes; left-deep restricts one input to a base relation, bushy allows two intermediates.
GEQO
a genetic/randomized join-ordering search used past the DP threshold.
Cardinality estimation
estimating the row count an operator produces.
Selectivity
the fraction of rows a predicate passes (∈[0,1]).
Histogram
a per-column row-distribution summary (equi-depth: equal rows per bucket; max-diff: split at frequency gaps).
MCV (most-common values)
a per-column list of frequent values + frequencies, capturing skew.
NDV (number of distinct values)
the distinct-value count, estimated via HyperLogLog.
HyperLogLog (HLL)
a sub-linear, mergeable distinct-count sketch.
Null fraction
the fraction of NULLs in a column (tracked separately from the histogram).
Extended / multi-column statistics
joint distribution stats (joint NDV, soft FDs) defending against the independence assumption.
Independence assumption
sel(p∧q)=sel(p)·sel(q); the #1 source of estimation error on correlated columns.
q-error
max(estimate/truth, truth/estimate) (≥1); the estimation-accuracy metric; compounds multiplicatively up the tree.
Containment assumption
the join-selectivity assumption sel(a=b)=1/max(ndv(a),ndv(b)).
Cost model
the function mapping (cardinality, properties, operator) to a Cost (CPU/IO/memory/network) → scalar.
Calibration
fitting the cost constants (seq_page_cost, random_page_cost, cpu_tuple_cost, …) to a target environment.
Spill
an operator exceeding its memory budget + falling back to an external (disk) algorithm (with a higher cost).
Physical property
a property of a physical plan's output: an order (sortedness) or a distribution (partitioning).
Interesting order
an order the query cares about (ORDER BY, merge-join keys, sort-agg keys); reusing it avoids sorts.
Enforcer
an operator inserted to satisfy a required property (PhysSort for an order, Exchange for a distribution).
Distribution / partitioning
how data is spread across nodes (Single/Hash/Range/Broadcast); the distributed-stub property.
Branch-and-bound
pruning a search branch whose lower-bound cost exceeds the current best (an upper bound).
Admissible lower bound
a lower bound that never exceeds the true cost (required for branch-and-bound to preserve optimality).
Functional dependency (FD)
X→Y: X determines Y; drives key inference + correlation correction.
Key
a column set whose values are unique per row; bounds join cardinality + enables redundant-op elimination.
Logical property
a property of a relation (schema, cardinality, keys, FDs, not-null); shared across a group's expressions.
EXPLAIN / EXPLAIN ANALYZE
the plan-output surface; ANALYZE adds true cardinalities (revealing q-error).
ANALYZE
the command/collector that builds statistics by sampling base tables.
Staleness
stats no longer reflecting the table (the #1 real-world cause of plan regressions).
Fingerprint
the structural key (operator + ordered child group ids + params) used for memo dedup.
Bind / binder
name resolution + type checking, lowering SQL to the logical IR.
Three-valued logic (3-VL)
SQL's TRUE/FALSE/NULL predicate logic; the semantic trap in rewrites + decorrelation.
Robust plan
a plan whose cost is insensitive to estimation uncertainty (preferred when confidence is low).
Hash-consing / interning
mapping structurally-equal expressions/plans to one id (sharing + O(1) equality).
