In one paragraph

A query optimizer takes a SQL query that says which rows are wanted and chooses how to fetch them: which join order, which join algorithm, which index, where to sort. This design is a Rust library (liboptd) plus a command-line tool that turns a bound logical plan into a costed physical plan using four cooperating parts: a rule engine, a join enumerator, a memo-based Cascades search, and a row-count and cost estimator (§1). It produces and explains plans but does not execute them (§1). Its one non-negotiable rule is that the chosen plan returns exactly the rows the input plan would (§4, P1). It is written for engineers learning database internals, authors of analytic engines, and researchers (§1).

The problem, concretely

Take the blueprint's own query: orders of customers in one region, with an order total above 100. The tables are customers (1M rows, region has 5 distinct values) and orders (10M rows) (§8.7). Written naively, the plan joins all 10M orders to all 1M customers first and filters afterwards (§8.7 "INPUT"). Pushing both filters down to the table scans leaves roughly 200k customers and roughly 3M orders to join (§8.7 "AFTER rewrite"). The blueprint's motivation for the whole project is that two logically identical queries can differ 1000× in run time, and that the optimizer, not the executor, is usually to blame for a bad plan (§2).

Fixing the join order is the easy half. The hard half is knowing the row counts: a 2× error at each join becomes 1000× over ten joins (§2), and a perfect cost formula on a wildly wrong row count still picks a catastrophic plan with full confidence (P6). The search space also grows combinatorially, so alternatives must be stored, shared and pruned (§2, P2, P10).

How it works, end to end

Follow the §8.7 query through the boxes of §3. The diagram is adapted from §3, which draws it as two blocks.

 SQL subset ─▶ bind ─▶ LogicalPlan ◀──▶ catalog
                          │
                  rewrite / normalization  (heuristic, before any costing)
                          │
   ┌─ CASCADES SEARCH: task scheduler ─▶ rule engine ─▶ memo ───────────────────────────┐
   │  props (orders, enforcers) · enumerate (DPccp/DPsize/greedy/GEQO) · branch & bound │
   └────────────┬───────────────────────────────────────────────────────────────────────┘
                │ candidate physical expressions
         estimate ◀──▶ stats        cost
                │ best physical expr per (group, required props)
         explain: plan | memo dump | est-vs-true rows | cost breakdown | trace
  1. bind (fixtures only) resolves names, type-checks, and lowers the SQL subset to the LogicalPlan IR in ir. It is the only box that reads untrusted SQL text (§3, §1). catalog supplies schemas, keys, index descriptors and view definitions, read-only (§3).
  2. Rewrite / normalization (in rules) runs first: predicate pushdown, column pruning, constant folding, unnesting, transitive predicates. These are always worth doing and shrink the costed search (§3, P3).
  3. search and memo take over. The task scheduler keeps a LIFO stack of tasks (OptimizeGroup, OptimizeExpr, ExploreGroup, ApplyRule, OptimizeInputs, EnforceProps); the rule engine applies transformation and implementation rules; the memo stores groups, group expressions and per-(group, required properties) winners (§3).
  4. enumerate feeds join orders into the memo through DPccp, with greedy and GEQO past a relation-count threshold (§3, ADR-07). props derives what each expression provides and what each parent requires, inserting PhysSort or Exchange enforcers (§3, §8.3, P5).
  5. estimate and stats supply row counts from histograms, most-common values, distinct counts and multi-column statistics (§3, §8.5); cost turns rows, properties and an operator into a cost (§3). explain prints the plan, memo dump, estimated versus true rows, cost breakdown and trace (§3). In the example the winner is a hash join building on the ~200k filtered customers through an index and probing a sequential scan of orders (§8.7).

Search is bounded by time, step and memory budgets; on exhaustion it returns the best plan so far plus a flag (P8, I7).

The core ideas

Row counts first, cost second (§8.6, P6)

The estimator turns column statistics into a fraction of rows kept (selectivity) and multiplies. From §8.6:

sel(a = const)        = mcv_freq(const)  if const ∈ MCV
                      = (1 - Σ mcv_freq - null_frac) / (ndv - |MCV|)   otherwise   # uniform over remainder
sel(a < const)        = histogram fraction below const (interpolate within bucket)
sel(a = b)  [join]    = 1 / max(ndv(a), ndv(b))                       # containment + uniform
sel(p ∧ q)            = sel(p) · sel(q)                               # INDEPENDENCE (default; corrected by ext-stats)
sel(p ∨ q)            = sel(p) + sel(q) − sel(p)·sel(q)
card(σ_p(R))          = card(R) · sel(p)            (clamped to [1, card(R)] when non-empty)  (I6/I12)
card(R ⋈_{a=b} S)     = card(R)·card(S) · sel(a=b)  (key-join ⇒ ≤ card of non-key side)
card(Γ_group(R))      = min( ndv(group) , card(R) )  (group cols form a key on the output)

Tiny example, all from §8.7: region has 5 distinct values, so sel(region='EU') is 1/5 and the 1M-row customers table becomes about 200k rows. The histogram puts sel(total>100) near 0.3, so the 10M-row orders table becomes about 3M rows. Those two numbers decide which side the hash join builds.

Two things make this the fragile part. First, q-error (max(estimate/truth, truth/estimate), so 1 is perfect) multiplies up the tree (§8.6, MM3). The blueprint's example (Domain Deep Dive D.9): if every join is off by 4×, then 3 joins give 64×, 6 joins give about 4096×, and 10 joins give about 10⁶×. Second, the independence assumption is false on correlated columns, such as city='SF' AND state='CA', and its only defences are multi-column statistics, key and functional-dependency bounds, and sampling (MM7). Estimates are never 0, NaN, infinite or negative (P7, I6). Cost is then a pure function of rows, properties and calibration constants, with spill cost once memory exceeds the budget (§3, Phase 3 acceptance criteria).

The memo: one group per set of equivalent plans (§3, P2, MM1)

A group is a set of logically equivalent expressions. A group expression is one operator plus its child groups, not child plans (§3, glossary). Structural equality is decided by a fingerprint (operator, ordered child group ids, parameters), so no two identical expressions live in one group (glossary, I2, I3). Winners are memoized per (group, required properties) (§3, P2). The blueprint's own example (Domain Deep Dive D.3) for the customers/orders query:

Group Alternatives the rules put in it
Join HashJoin, MergeJoin, NestedLoop (with index on o.cust)
customers scan SeqScan with filter, IndexScan(idx_region, region='EU')
Aggregate HashAgg, SortAgg (requires input sorted on c.name)

Groups are OR-nodes and group expressions AND-nodes of an AND-OR graph; without sharing you re-optimize the same subtree once per parent (MM1). Code refers to integer GroupId/ExprId handles, never raw trees (P2, ADR-05).

Search: tasks, two kinds of rule, and branch-and-bound (§3, P4, P10)

Transformation rules map logical to logical (commute or associate joins, move predicates). Implementation rules map logical to physical (Join to HashJoin, MergeJoin or NestedLoop). The search uses the first to grow a group and the second to fill it with costable alternatives, and they must not be conflated, or a physical operator could be rewritten logically (P4, MM4).

Branch-and-bound carries a cost upper bound down the search and abandons any group expression whose lower-bound cost already exceeds it (P10). It is only safe if every lower bound is admissible, never above the true cost of the subtree; one inadmissible bound silently drops the optimal plan with no error (I8, MM5). In the D.6 trace, an initial greedy plan gave the bound. The HashJoin that builds on orders had a lower bound (build 2M rows) above a competitive bound, so it was pruned without being fully costed. The NestedLoop branch was fully costed (200k index probes) and lost (Domain Deep Dive D.6). Seeding the bound with a greedy plan is "mandatory, not optional" (Capacity model item 1).

Physical properties: required top-down, provided bottom-up (§6 P5, MM2, MM6)

A merge join needs sorted inputs, an index scan provides an order, and a parent such as ORDER BY requires one. If a requirement is unmet, the search inserts an enforcer (PhysSort, Exchange). A provided order that is a prefix of the required one satisfies it for free (MM6). The §8.8 example has clustered indexes on a.k and b.k and ORDER BY a.k: candidate (1) is HashJoin then PhysSort[a.k]; candidate (2) is MergeJoin over two index scans, which provides a.k order with no enforcer, and (2) wins (§8.8). The harder trace, from Domain Deep Dive D.4, for GROUP BY c.name ORDER BY c.name:

  1. The root requires order c.name; HashAgg provides none, SortAgg provides it only if its input is sorted on c.name.
  2. The join below can offer only the join-key order, not c.name, so a sort enforcer is needed somewhere.
  3. Sorting after the aggregation sorts about 200k grouped rows; sorting before sorts the larger join output. Cost picks the first (D.4).

Each group is optimized once per required-property set, not once overall (P5, §9 note on ADR-06).

Join enumeration: DPccp inside the search (§3, ADR-07, MM8)

Relations are nodes and predicates are hyperedges. DPccp walks connected, cross-product-free pairs of subgraphs, producing each pair exactly once; the alternative DPsub enumerates all subsets and reaches the same pair about 2^k times (MM8, glossary). The blueprint states DPccp as an exact method for up to 12 relations and greedy plus GEQO (a seeded genetic search) for 13 to 64 (§4). A cross product is added only as a last resort and flagged in the trace (§8.10). The name of the exact method differs: DPccp/DPsize in §1 and §3, DPccp/DPhyp in ADR-07 and the Phase 9 steps (§1, §3, ADR-07). The §9 note keeps System-R's join DP, run as a rule inside the Cascades memo (§9 note on ADR-06).

Rewrite before search, and decorrelation (§6 P3, §8.9, I15)

Heuristic rewrites run first, and each must be unconditionally good, otherwise it belongs in the cost-based rules (P3). The delicate one is unnesting a correlated subquery. In §8.9, WHERE c.total > (SELECT AVG(o.total) FROM orders o WHERE o.cust=c.id) becomes:

  1. Group orders once by cust, computing AVG(o.total) per customer.
  2. Left-outer-join customers to that result, so customers with no orders survive.
  3. Filter c.total > avg_total. For a customer with no orders the average is NULL, the comparison is NULL, and the row is dropped, which matches the correlated meaning (§8.9, three-valued logic).

Without this the subquery re-runs once per customer; with it one grouped join does the work (§8.9). The equivalence obligation is I15, checked by a differential run against correlated execution (I15).

The trade-offs — where engineers disagree

Search architecture: Cascades top-down (ADR-06)

Chosen: Cascades/Volcano top-down memo search, because the optimizer is meant to be extensible (new rules without rewriting the core), property-driven, and able to share structure across equivalent subplans (§9). Rejected: System-R bottom-up dynamic programming. When the rejected choice is right: a planner with a single operator set (only joins to enumerate), where simplicity and the absence of the inadmissible-bound risk (I8) outweigh the lack of a general memo (ADR-06). The blueprint's wording: the bottom-up DP "cannot have that bug", so bound admissibility becomes a first-class invariant (§9 note).

Join enumeration: DPccp plus a fallback (ADR-07)

Chosen: DPccp/DPhyp up to 12 relations, greedy plus GEQO above, for cross-product-free, provably optimal-in-range search with a graceful fallback (ADR-07). Rejected: DPsub and exhaustive enumeration. When the rejected choice is right: DPsub when the join graph is always a clique and DPccp's ordering effort is not justified; exhaustive enumeration on very small fixed relation counts (five or fewer) where plan quality beats latency (ADR-07).

Selectivity model: independence plus extended statistics (ADR-13)

Chosen: independence as the default, corrected by multi-column statistics, because correlation is the largest source of estimation error on the JOB benchmark (ADR-13). Rejected: independence only. When the rejected choice is right: a simple one-pass heuristic planner where extended statistics are not worth the code, or a workload where column correlation is empirically negligible (ADR-13).

Pruning: branch-and-bound with admissible bounds (ADR-17)

Chosen: branch-and-bound, for a tractable search that keeps optimality (ADR-17). Rejected: full scoring of all plans. When the rejected choice is right: a tiny plan space (three relations or fewer, one operator choice) where maintaining an admissible bound costs more than it saves, or when debugging needs to see every costed alternative (ADR-17).

Subqueries: rule-based unnesting (ADR-16)

Chosen: unnest scalar, EXISTS and IN subqueries by rule; one join replaces repeated re-execution, and soundness is gated by I15 (ADR-16). Rejected: leave them correlated and re-execute. When the rejected choice is right: when the subquery always returns at most one row (point-lookup semantics), or when the unnested join would produce a worse plan because outer-join cardinality blows up under poor estimates (ADR-16).

Roads not taken

System-R bottom-up DP (Alternative Architectures): best plan per relation subset, no memo or pruning. It wins for a small fixed operator set where only join order is searched (PostgreSQL does this). It is rejected here because new operators mean editing the recurrence, the whole subset lattice is materialized, and non-join subexpressions have no memo (Alternative Architectures, ADR-06).

Randomized / genetic join enumeration (Alternative Architectures): evolve relation permutations with a seeded generator. It wins above roughly 20 to 30 relations, where exact DP is infeasible, and can be interrupted at any generation. It cannot prove optimality, which fails the ≤1.3× gate in the exact range, so it is only the fallback beyond 12 relations (Alternative Architectures, §4, ADR-07).

Learned cardinality models (Alternative Architectures): it wins with a large labeled, stationary workload where classical q-error stays above the Phase 10 target. It is rejected for now (no corpus, harder to reproduce, possible overconfident wrong estimates), but the CardinalityEstimator trait keeps the seam open (Alternative Architectures, ADR-18).

Deferred features (Deferred Features Register), each un-deferred by a trigger: distributed enumeration when #316 needs multi-exchange search; a learned estimator when JOB q-error stays above target and a labeled corpus exists; adaptive re-optimization when #318 delivers a feedback API; parallel-degree optimization when #104 / #207 expose a degree-of-parallelism setting; multi-query optimization when a workload-aware planner layer needs shared scans.

What must never be false

Each line gives the plain meaning, then how the system notices (§7).

  • I1: the optimized plan returns the same rows as the input, under three-valued logic. Noticed by differential execution and per-rule equivalence obligations; plan_equiv_fail.
  • I2, I3: each group expression is in exactly one group, and no group holds two identical expressions. Noticed by a duplicate-group audit and per-group fingerprint set; memo_dup_groups, grpexpr_dup.
  • I4: rule application reaches a fixpoint. Noticed by applied-rule sets and a step budget; rule_cycle_detected.
  • I5: every operator's required properties are met by its inputs, directly or by an enforcer. Noticed by a property check on the final plan; prop_unsatisfied.
  • I6, I12: row estimates are finite and non-negative, and selectivity stays in [0,1]. Noticed by range and NaN checks; card_invalid, selectivity_oob.
  • I7: memo memory and search steps stay in budget; over budget returns best-so-far plus a flag. Noticed by step and byte accounting; opt_budget_hit.
  • I8: branch-and-bound lower bounds never exceed the true subtree cost. Noticed by pruned-versus- full spot-checks on small queries; bnb_inadmissible.
  • I9: output is a deterministic function of (plan, catalog, stats, seed). Noticed by replay equality; nondeterminism_detected. (§4 tags determinism P11; §6 states it as P9.)
  • I10: the winner for a (group, required properties) pair has minimum cost among costed alternatives. Noticed by re-deriving it; winner_not_minimal.
  • I11: keys, functional dependencies and not-null facts agree across a group's expressions. Noticed by cross-expression comparison; logprop_mismatch.
  • I13: histogram buckets are ordered, non-overlapping and cover the domain. Noticed by a boundary audit; histogram_malformed.
  • I14: a satisfied required order is preserved through order-preserving operators. Noticed by an order-preservation audit; order_lost.
  • I15: unnesting a subquery gives a join equivalent to the nested meaning. Noticed by a differential run against correlated execution; decorrelate_unsound.

The soundness invariants (I1, I8, I10, I11, I15) each have a checker that can run in a "paranoid mode" after every rule application or winner update, and a failing query is shrunk by delta-debugging (ddmin) over the plan tree and the catalog and stats it touches (§7).

What breaks in production

The Failure Modes table has no IDs, so items are named by class (eight of eleven rows; two merged).

  • Wrong results. The optimized plan returns different rows, from an unsound rewrite, property or decorrelation bug. Detected by the I1 differential and I5/I14 audits. Recovery: refuse the plan and return the input plan; shrink with ddmin, disable the rule (Failure Modes table, T2).
  • Sub-optimal plan. A correct but far costlier plan, from a bad estimate, a lost alternative or an inadmissible bound. Detected by the quality gate, bnb-equals-exhaustive (I8) and the q-error report. No automatic recovery; retune cost or stats, or fix the memo or bound (Failure Modes table).
  • Optimization hang. No plan, spinning, from a rule cycle (I4) or search explosion. Detected by step and time budgets (I7). Recovery: best-so-far plus a flag; lower the DP threshold (Failure Modes table).
  • Memo explosion / optimizer OOM. Memo memory climbs, from DP on too many relations or a lost cross-product-free guard in DPccp. Detected by the memo-bytes budget (I7). Recovery: best-so-far with opt_budget_hit; force --join-method greedy (Failure Modes table).
  • Executor OOM, the optimizer's fault. A hash build sized from an under-estimated cardinality. Detected only post hoc, by the q-error report. Recovery: re-ANALYZE, add extended stats; adaptive re-optimization is deferred to #318 (Failure Modes table, T6).
  • Stale-stats regression. A bad join order after a bulk load because ANALYZE was not re-run. Detected by stats_stale_count and a rising median_qerror. Recovery: re-ANALYZE (Failure Modes table).
  • Corrupt stats. A malformed histogram or impossible selectivity. Detected by the I13 audit and I12 checks. Recovery: fall back to uniform selectivity and flag; rebuild stats (Failure Modes table, §8.10).

Recovery rule: correctness failures refuse to emit a plan; quality and resource failures degrade to best-so-far, greedy or uniform stats, plus a flag (Failure Modes table).

Threats a reader should know (Threat Model): T2 wrong results from a rewrite or property bug, the headline threat because it is silent, answered by the I1 differential and per-rule equivalence obligations; T3 memory exhaustion from an adversarial 30-relation clique query, answered by the DP threshold, greedy/GEQO fallback and the memo budget (I7); T6 a correct plan that exhausts the executor because correlated data defeated independence, answered by extended stats and low-confidence flags; T7 poisoned stats, answered by histogram validation (I13) and versioned snapshots; T11 an inadmissible bound silently losing the optimal plan, answered by the admissibility audit (I8).

How it compares

  • PostgreSQL planner chose bottom-up System-R DP with interesting orders in Path structures, plus GEQO for large joins. That is fine for single-node work where extensibility is not needed and avoiding the bound-admissibility risk matters more than top-down pruning.
  • Apache Calcite (VolcanoPlanner) chose a JVM Cascades-style memo with a rich rule registry. That fits an optimizer shared across many JVM engines (Hive, Flink, Beam), where rule reuse outweighs garbage-collection pauses in the inner loop.
  • Greenplum Orca chose a standalone Cascades optimizer in its own process with a full distribution model. That fits when optimizer crashes must not take down the executor and broadcast-versus- redistribute costing is needed.
  • CockroachDB chose a Go Cascades optimizer with rules generated by the optgen DSL. That fits when compile-time-checked rule patterns and integrated distributed planning matter.
  • DuckDB chose a compact bottom-up DP planner coupled to its vectorized executor. That fits an embedded analytical engine with a fixed operator set, where simplicity beats extensibility (all five: Comparative Architecture Table).

Questions to test yourself

  1. If a Cascades OptimizeGroup task carries an upper bound b and the best lower bound for any group expression in the group exceeds b, the group is pruned. What invariant must hold for this to preserve the optimality of the final plan, and where in the codebase is it audited? — Hint: §7 I8, §6 P10, and the Phase 5 acceptance criteria.
  2. A join R⋈S on R.id = S.r_id, where R.id is a primary key, has its cardinality bounded by card(S) — not the containment-formula product. Walk through the logical-property derivation that reaches this bound, and explain why omitting it causes q-error to compound multiplicatively on PK-FK schemas. — Hint: §8.4 on key derivation, §8.6, and the Phase 7 acceptance criteria.
  3. DPccp generates each connected subgraph pair (S1, S2) exactly once by restricting the complement to a connected subgraph disjoint from S1. Explain why DPsub generates the same pair O(2^|S1|) times, and derive the complexity ratio between the two algorithms on a 12-relation star graph. — Hint: MM8, ADR-07, and the Phase 9 description.
  4. The Cascades task model uses a LIFO stack rather than a FIFO queue. What property of the search does this preserve, and how does it interact with branch-and-bound's requirement that a parent's cost upper bound is known before children are pruned? — Hint: §3 "Cascades search" per-box entry, P10, and the Phase 5 description.
  5. A query decorrelates a scalar subquery WHERE c.total > (SELECT AVG(o.total) FROM o WHERE o.cust=c.id) into a left-outer-join with a grouped aggregate (§8.9). Identify the three-valued-logic edge case that makes this transformation non-trivial, state the invariant it must satisfy, and describe the differential test that would catch a violation. — Hint: §8.9's equivalence comment, I15, and I1.

If you only remember three things

Row-count estimates drive everything, and their errors multiply up the plan, so the design puts cardinality first and cost second (P6, MM3). Alternatives live in a memo of equivalent groups and are pruned by a cost lower bound that must never exceed the true cost, or the optimal plan is lost without any error (P2, P10, MM5). A fast plan that returns different rows is a bug, so correctness failures refuse to emit a plan while quality and resource failures degrade to best-so-far and raise a flag (P1, P8, MM10).

Words used here

  • Logical plan / physical plan: what to compute, as relational algebra, versus how to compute it, with chosen algorithms, properties and cost (§3, glossary).
  • Memo: the structure holding all explored alternatives as equivalence groups (§3, MM1).
  • Group expression: one operator plus its child groups, not child plans (§3).
  • Winner: the cheapest physical expression for a (group, required properties) pair (§3, I10).
  • Transformation rule / implementation rule: logical-to-logical growth of a group versus logical-to-physical filling of it with costable operators (P4).
  • q-error: max(estimate/truth, truth/estimate), at least 1, which multiplies up the plan tree (§8.6, MM3).
  • Independence assumption: treating two predicates as unrelated, sel(p∧q)=sel(p)·sel(q), which fails on correlated columns (§8.6, MM7).
  • MCV / histogram / NDV: the most-common-value list that captures skew, the bucketed row distribution for the rest, and the distinct-value count estimated with HyperLogLog (§8.5).
  • Interesting order: a sort order the query cares about (ORDER BY, merge-join keys) whose reuse avoids a sort (MM6, §8.8).
  • Enforcer: an operator inserted to satisfy a required property, PhysSort for order or Exchange for distribution (§3, P5).
  • Admissible lower bound: a cost lower bound that never exceeds the true cost, required for pruning to preserve the optimum (I8, MM5).
  • DPccp: dynamic programming over connected subgraph pairs, optimal and free of cross products (§3, ADR-07).
  • GEQO: a seeded genetic search for join orders past the exact-DP ceiling (§4, ADR-19).
