313 — Query Optimizer + Cost Estimator

Project Number: 313

Project Name: Query Optimizer + Cost Estimator

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build, from scratch, a cost-based query optimizer that transforms a bound, type-checked logical plan (relational algebra over a known catalog) into an efficient physical plan (executable operator tree) via four cooperating subsystems:

  • a rule engine (rewrite/normalization + transformation/implementation rules),
  • a join enumerator (DPccp/DPsize over the join hypergraph + greedy/randomized fallback),
  • a Cascades/Volcano top-down search (a memo of equivalence groups, group expressions, winners; tasks; branch-and-bound),
  • a cardinality + cost estimator (histograms, MCV, distinct counts, selectivity, join cardinality, error-propagation-aware cost model).

The deliverable is a library liboptd + a CLI that ingests a bound logical plan (its own IR, or a thin SQL-subset frontend for fixtures), produces an optimized physical plan, and emits EXPLAIN-style trees, the memo dump, the estimated/true cardinalities, and the cost breakdown. This is a specification, not an executor: it produces plans; execution is out of scope (delegated to #104/#207).

In scope (Phase 0 deliverable) — crates/modules:

  1. ir — logical/physical plan IR, expression trees, sort/type system, logical properties (keys, FDs, not-null).
  2. catalog — table/column metadata, schemas, sort/type lookups, constraint registry.
  3. bind — a thin binder over a SQL subset (for fixtures): name resolution, type checking, producing the logical IR (full SQL parsing delegated to #21).
  4. stats — statistics schema (histograms equi-depth/max-diff, MCV lists, NDV via HyperLogLog, null fractions, extended multi-column stats), ANALYZE collector.
  5. estimate — selectivity (eq/range/LIKE/IN/conjunction/disjunction), join cardinality, error/q-error propagation, sampling + sketch hooks.
  6. cost — operator cost model (scan, join, agg, sort, exchange), calibration constants, memory budget + spill cost.
  7. rules — rewrite (normalization) rules + Cascades transformation/implementation rules + rule binding/pattern matcher.
  8. memo — groups, group expressions, winners, duplicate detection (group merge), physical-property map.
  9. search — Cascades task scheduler (OptimizeGroup, OptimizeExpr, ApplyRule, ExploreGroup, OptimizeInputs, EnforceProps), branch-and-bound pruning.
  10. props — physical property model: interesting orders, distribution/partitioning, enforcers (Sort, Exchange), derivation + requirement propagation.
  11. enumerate — join graph extraction, DPccp/DPsize connected-subgraph enumeration, greedy + GEQO-style randomized fallback.
  12. explain — plan/memo/estimate/cost pretty-printers, plan diffing, optimizer trace.
  13. cli — optimize, explain, analyze, dump-memo, bench.

System boundaries. Consumes a bound logical plan (catalog-resolved, type-checked); produces a physical plan annotated with cardinality + cost + properties. Optimizes Select-Project-Join-Aggregate-Sort-Limit-SetOp-Window over a single-node, disk+memory cost model. Does NOT include: SQL parsing of the full grammar (subset only; #21 owns the parser), the execution engine (#104/#207), distributed/multi-node planning beyond a single-exchange cost stub (#316), adaptive runtime re-optimization (#318), index creation/maintenance (consumes index metadata; #208/#209 own indexing), materialized-view maintenance (consumes MV metadata for rewrite; #210 owns refresh), and transaction/MVCC semantics.

Non-goals (Phase 0): full distributed enumeration with shuffle/broadcast cost search (single-exchange enforcer stub only), runtime adaptive re-optimization, learned/ML cardinality models (pluggable estimator trait leaves the seam, classical estimators ship), parallel-degree (DOP) optimization, recursive-CTE optimization, full subquery support beyond decorrelation of the common patterns, multi-query optimization, and a SQL-standard-complete binder.

Deployment model. A library (liboptd) + a single CLI binary. Used as: the planner stage of #21 SQL Database; the optimizer behind #52 Query Planner; the cost/property source for #104 Vectorized OLAP Executor and #207 Columnar Vectorized Execution Planner; the classical baseline for #318 Adaptive Query Execution; the single-node core extended by #316 Distributed SQL Query Optimizer. Linux/macOS, x86-64/aarch64, single process, in-memory optimization (no persistence beyond the stats catalog it reads).

Target users. Engineers learning DB internals / query optimization; authors of analytic engines needing an embeddable cost-based optimizer; researchers studying Cascades, join enumeration, and cardinality estimation.

What later phases unlock. Distributed enumeration (full exchange/partitioning search, #316); adaptive execution feedback loops (#318); learned cardinality models behind the estimator trait; parallel-degree optimization; recursive CTE + advanced subquery handling; multi-query / shared-scan optimization; a proper SQL frontend (#21).

Deferred features behind PhaseDeferred("Deferred Features Register"):

  • Full distributed enumeration (multi-exchange, broadcast vs repartition search) — PhaseDeferred("Deferred Features Register").
  • Learned/ML cardinality estimator — PhaseDeferred("Deferred Features Register").
  • Adaptive runtime re-optimization (re-cost from execution feedback) — PhaseDeferred("Deferred Features Register").
  • Parallel-degree (DOP) optimization — PhaseDeferred("Deferred Features Register").
  • Multi-query / common-subexpression-across-statements optimization — PhaseDeferred("Deferred Features Register").

Estimated timeline. Phase 0 (IR + binder + rules + DP join enum + Cascades memo + estimator + cost + EXPLAIN, conformance-green on a JOB/TPC-H subset): 12–14 weeks. Full optimizer hardened (extended stats, GEQO, property enforcement, distributed stub, soak): 6–10 months.

Recommended language: Rust. Rationale: the memo + task scheduler is a graph of index-referenced nodes mutated under a single owner during a CPU-bound search where allocation churn and pointer-chasing dominate optimization latency — Rust gives arena/index-reference control without a GC pausing the optimizer, and its enums model the plan IR (LogicalOp/PhysicalOp/Expr) and three-valued logical properties cleanly with exhaustive matching that makes adding an operator a compile error until handled everywhere. The borrow checker is a mild cost in the cyclic memo (worked around with GroupId/ExprId integer handles, exactly as production optimizers use integer group refs anyway). Portfolio consistency: #52, #206, #207 are Rust; sharing IR/catalog types across the planner/executor portfolio is a goal. Rejected: C++ (the performance peer — most production optimizers are C++ — but arena-lifetime bugs in the memo are a known time sink); Java/Scala (Calcite/Spark Catalyst are the canonical references, but GC pauses and boxing hurt the tight enumeration inner loop, and the portfolio favors Rust); Python (orders of magnitude too slow for DP enumeration over 10–20 relations).

Prerequisites. Relational algebra + SQL semantics; the System-R optimizer + Cascades framework; dynamic programming over subsets/graphs; basic graph theory (connected subgraphs, hypergraphs); probability + statistics (histograms, distinct-count estimation, independence vs correlation); the linear parts of cost modeling (linear cost functions); cache-aware data structures; functional dependencies + key inference.

2. Why Build This

  • The optimizer is the brain of a database, and almost no engineer implements one. It is where declarative SQL becomes an executable strategy. Implementing rule-based rewriting, join enumeration, a memo, and cardinality estimation teaches why two semantically identical queries differ 1000× in runtime — and why the optimizer, not the executor, is usually to blame for a bad plan.
  • Cardinality estimation is the hardest, least-solved problem in databases. Estimates compound multiplicatively up the plan tree; a 2× per-join error becomes a 1000× error over ten joins (the q-error explosion). Building histograms, distinct-count sketches, and selectivity formulas — and watching them fail under correlation — is the single most instructive exercise in applied estimation under uncertainty.
  • Cascades is the architecture behind every modern optimizer (SQL Server, Greenplum/Orca, CockroachDB, Apache Calcite's Volcano planner). Building the memo (groups, group expressions, winners), the task scheduler, transformation vs implementation rules, and branch-and-bound pruning demystifies the entire query-planning stack and the literature around it.
  • Join enumeration is a tour of combinatorial search: DPccp/DPsize over connected subgraphs (provably optimal, cross-product-avoiding), left-deep vs bushy spaces, the commutativity/associativity that generates the space, and the greedy + genetic (GEQO) fallback when the space explodes past ~12 relations. It teaches the brutal tradeoff between plan quality and optimization time.
  • Physical properties + enforcers teach how interesting orders (sortedness) and distribution turn a tree search into a property-satisfaction search — why "sort once, reuse for merge-join and order-by" is the move that separates a naive optimizer from a good one.
  • Cost modeling teaches calibration: cost = f(cardinality, CPU/tuple, IO, memory, network); how spill costs, build/probe asymmetry, and the memory budget make hash-join-vs-sort-merge a context-dependent decision rather than a constant.
  • Cross-links. Predecessor #206 Query Optimizer Cost Model (313 is the full optimizer — rule engine + join enumeration + Cascades memo + cardinality estimation — not just the cost function, which 313 consumes and extends); #52 Database Query Planner (the simpler planner this supersedes); #207 Columnar Vectorized Execution Planner + #104 Vectorized OLAP Executor (consume the physical plan + cost); #208 Adaptive Indexing + #209 Secondary Indexing (supply index metadata for index-scan rules); #210 Materialized View Engine (supplies MV metadata for view-matching rewrite); #213 Query Federation (federated cost stub); #21 SQL Database (owns the parser, embeds this optimizer); #294 Search Query Planner + #295 Workflow DAG Optimizer (sibling cost-based planners); #316 Distributed SQL Query Optimizer (extends this with distributed enumeration); #318 Adaptive Query Execution (extends this with runtime feedback).
  • Calibration. This is where "the database picked a bad plan" stops being a black box. After it, you read an EXPLAIN ANALYZE and see the memo, the estimation error, the missed index scan, the join order the enumerator pruned. It permanently upgrades your ability to reason about cost-based search and estimation under uncertainty.

Per-box.

  • bind — fixtures only; resolves names against the catalog, type-checks expressions, and lowers a SQL subset into the LogicalPlan IR (relational algebra DAG). It is the only component that consumes untrusted SQL text; full SQL parsing is delegated to #21. Downstream sees a validated, typed plan. Out-of-scope SQL features raise PhaseDeferred.
  • catalog — the metadata authority: table/column schemas, declared sorts, primary/unique keys, functional dependencies, NOT-NULL constraints, available index descriptors (#208/#209) and materialized-view definitions (#210). Read-only to the optimizer; supplies logical-property seeds (keys, FDs) and physical alternatives (which indexes exist).
  • rewrite/normalization — heuristic, pre-search simplification that is always beneficial (or made cost-neutral): predicate pushdown, projection pruning, constant folding + expression simplification, subquery decorrelation/unnesting, transitive predicate inference (a=b ∧ b=c ⟹ a=c), outer-join simplification + reordering, redundant-operator elimination, CTE/view inlining, common-subexpression detection. Shrinks the input the cost-based search must explore (§6 P3).
  • Cascades search — the engine. The task scheduler maintains a LIFO stack of tasks (OptimizeGroup, OptimizeExpr, ExploreGroup, ApplyRule, OptimizeInputs, EnforceProps); the rule engine matches transformation rules (logical→logical) and implementation rules (logical→physical) against group expressions via the pattern matcher; the memo stores equivalence groups, their group expressions, and per-(group, required-props) winners with duplicate detection (group merging). Branch-and-bound carries a cost upper bound down the search to prune provably-worse subspaces.
  • props — the physical-property model: interesting orders (sortedness on column lists), distribution/partitioning (single-node default + hash/range partition descriptors for the distributed stub), enforcers (PhysicalSort, PhysicalExchange). Derives properties a physical expression provides and propagates the properties a parent requires down to inputs (§6 P5).
  • enumerate — extracts the join hypergraph (relations as nodes, predicates as hyperedges), then enumerates connected, cross-product-free subgraphs via DPccp/DPsize; left-deep, zig-zag, and bushy spaces are controllable; past a relation-count threshold it falls back to a greedy + GEQO-style randomized/genetic search. Feeds candidate join orders into the memo as group expressions.
  • estimate (cardinality) — the hard part. Computes selectivity for predicates (equality via NDV/MCV, range via histogram, LIKE/IN, conjunction/disjunction under independence with correlation correction from multi-column stats), join cardinality (containment + uniform-distribution assumptions, key/FD-aware), and tracks q-error propagation up the tree. Sampling + sketch hooks and a pluggable estimator trait leave room for learned models (§10.9 deferred).
  • stats — the statistics catalog: per-column equi-depth + max-diff histograms, most-common-value (MCV) lists, number-of-distinct-values (NDV) via HyperLogLog, null fractions, and extended multi-column/correlation statistics. The ANALYZE collector builds these by sampling base tables; staleness is tracked and surfaced.
  • cost — maps (cardinality, properties, operator) → Cost (a vector of CPU, IO, memory, network reduced to a scalar via calibration weights): sequential/index-scan costs, hash-join build/probe asymmetry, sort-merge, nested-loop, hash vs sort aggregate, materialization, and the exchange/shuffle stub. Includes the memory budget + spill-cost model that makes operator choice context-dependent.
  • explain — the operator surface: pretty-prints the chosen physical plan, the full memo dump, estimated-vs-true cardinalities (when true counts are supplied), the per-operator cost breakdown, and the optimizer trace (which rules fired, what was pruned, which winners were chosen). The primary debugging artifact.

Boundaries. Trust: only bind consumes untrusted SQL text; everything else operates on validated IR + trusted catalog/stats. Concurrency: single-threaded optimization Phase 0 (the memo is mutated by one task scheduler; parallel rule application deferred). Persistence: none for optimization (in-memory memo); the stats catalog is the only persisted state the optimizer reads. Protocol: the external contracts are the LogicalPlan/PhysicalPlan IR (consumed/produced) and the EXPLAIN text format.

Correctness (semantic preservation, I1) is the single non-negotiable: a plan that returns different rows than the input query is a total failure regardless of how cheap or fast it is (§6 principle 1). Plan quality is a strong target but a slow-but-correct plan is acceptable; a fast-but-wrong plan is not.

6. Design Principles

  1. P1 — Semantic preservation over everything. Every rewrite, every physical choice must produce a plan whose result multiset equals the input query's, under SQL's three-valued logic + bag semantics. A faster plan that returns different rows is worthless and catastrophic (silent data corruption). Violation: an outer-join reordering that changes null-padding → wrong results, undetected without a differential checker (I1).
  2. P2 — The memo is the single source of plan-space truth. Every logical/physical alternative for a subexpression lives in exactly one group; equivalence is decided structurally (fingerprint); winners are memoized per required-property set. Tradeoff: every component reasons in terms of GroupId/ExprId, never raw trees. Violation: a rule that mutates a plan tree outside the memo desyncs the search → missed alternatives or duplicate work (I2/I3).
  3. P3 — Rewrite before search; search only what rewrite can't decide. Heuristic normalization (pushdown, pruning, decorrelation) shrinks the input deterministically; cost-based search handles only genuinely cost-dependent choices (join order, operator selection, property enforcement). Tradeoff: a rewrite must be unconditionally good (or moved into the cost-based rules). Violation: a "rewrite" that is sometimes worse (e.g. always-decorrelate) bakes a bad plan in before costs are known.
  4. P4 — Transformation and implementation rules are distinct. Transformation rules map logical→logical (commute/associate joins, push predicates); implementation rules map logical→physical (Join→HashJoin/MergeJoin/NLJoin). The search applies transformations to grow the group, implementations to populate it with costable physical exprs. Violation: conflating them lets a physical op be transformed logically → meaningless rewrites + non-termination.
  5. P5 — Physical properties are required top-down, provided bottom-up. A parent operator requires properties of its inputs (merge-join requires sorted inputs on the join keys); each physical expr provides properties (an index scan provides an order). Unsatisfied requirements are met by inserting an enforcer (Sort/Exchange). Tradeoff: the search optimizes each group once per required-property set, not once. Violation: ignoring required orders re-sorts redundantly or, worse, runs merge-join on unsorted input → wrong results.
  6. P6 — Cardinality first, cost second. Cost is a deterministic function of cardinality + properties; the hard, error-prone part is the row estimate. Estimation errors, not cost-formula errors, cause 99% of bad plans. Tradeoff: invest in stats + estimation accuracy + error-bounding over cost-formula precision. Violation: a perfect cost model on a 1000×-wrong cardinality picks a catastrophic plan with full confidence.
  7. P7 — Estimation degrades gracefully and is bounded. When stats are missing/stale or assumptions (independence) break, the estimator uses documented fallbacks (magic constants, clamping) and flags low confidence; it never produces 0, NaN, ∞, or negative cardinalities. Tradeoff: clamped estimates can be far off but never break the search. Violation: a 0-row estimate makes everything downstream "free" → a plan that is optimal only in the estimate's fantasy (I6).
  8. P8 — Bounded optimization, graceful best-effort. Time, search-step, and memory budgets are first-class; on exhaustion the optimizer returns the best plan found so far (or a heuristic plan) and flags it, never hangs or OOMs. Tradeoff: a complex query may get a sub-optimal plan under time pressure — acceptable; a hang is not. Violation: unbounded DP on 30 relations exhausts memory mid-search (I7/P8).
  9. P9 — Determinism by construction. No wall-clock, address order, or hash-iteration order influences a rule firing, a tie-break, or an estimate; a seed fixes any randomization (GEQO). Tradeoff: tie-breaks must be ordered explicitly (e.g. by GroupId then rule id). Violation: non-deterministic plans make regressions un-debuggable and conformance flaky (I9).
  10. P10 — Branch-and-bound, not exhaustive scoring. Carry a cost upper bound down the search; abandon any group expression whose lower-bound cost already exceeds the bound. Tradeoff: requires admissible (never-overestimating) lower bounds. Violation: an inadmissible bound prunes the optimal plan → silently sub-optimal output (I8).
  11. P11 — Separate logical equivalence from physical realization. A group is a set of logically equivalent expressions; the physical winners are a property-indexed overlay. The search never confuses "these compute the same relation" with "this is the chosen way to compute it." Violation: leaking physical cost into logical equivalence merges groups incorrectly → lost alternatives.
  12. P12 — Statistics are an input, not a guess baked into rules. Selectivities/cardinalities come from the stats catalog through the estimate module; rules never hard-code "filters are 10% selective." Tradeoff: the system is only as good as its stats; ANALYZE + staleness tracking matter. Violation: hard-coded selectivities make the optimizer blind to the actual data distribution (the original sin of pre-cost-based optimizers).
  13. P13 — Idempotent, terminating rewrites. Applying the rewrite set to a fixpoint terminates and is confluent enough to be deterministic; the memo's duplicate detection guarantees the cost-based rules cannot cycle (commute(commute(x)) = x is detected as a duplicate). Violation: a rule pair that keeps generating "new" expressions never reaches fixpoint → the optimizer hangs (I4).
  14. P14 — Observability of the search is mandatory. Every rule firing, group creation, winner update, and pruning decision is traceable (--trace), and the memo is dumpable. The optimizer is the hardest DB component to debug; if you can't see why a plan was chosen, you can't fix a bad plan. Violation: an opaque optimizer turns every plan regression into a guessing game.

8. Domain Model / Source Language / Protocol

8.1 Logical plan IR (relational algebra DAG)

LogicalOp ::=
    Scan      { table: TableId, cols: [ColId], pred: Option<Expr> }      # base relation (+ pushed filter)
  | Filter    { input: Plan, pred: Expr }                                 # σ
  | Project   { input: Plan, exprs: [(Expr, Alias)] }                     # π
  | Join      { left: Plan, right: Plan, on: Expr, kind: JoinKind }       # ⋈  (kind below)
  | Aggregate { input: Plan, group: [Expr], aggs: [(AggFn, Expr, Alias)] }# Γ
  | Sort      { input: Plan, keys: [(Expr, Asc|Desc, NullsFirst|Last)] }  # τ  (logical order request)
  | Limit     { input: Plan, n: u64, offset: u64 }                        # λ
  | SetOp     { left: Plan, right: Plan, op: Union|Intersect|Except, all: bool }
  | Window    { input: Plan, fns: [WindowSpec] }                          # ω
  | Values    { rows: [[Expr]] }                                          # inline literal relation

JoinKind ::= Inner | LeftOuter | RightOuter | FullOuter | LeftSemi | LeftAnti | Cross
Plan       = a node id into the plan DAG (shared subtrees via CSE → DAG, not tree)

LogicalPlan is a DAG (common subexpressions are shared, not duplicated). Every node carries a derived schema (ordered list of (name, Type, nullable)) and logical properties (see 8.4). The IR is operator-canonical: e.g. a multi-table comma join from SQL is lowered to a left-deep chain of Join{Inner} with the WHERE predicate split into per-join on conjuncts + residual Filter (the enumerator re-orders later).

8.2 Expression model

Expr ::=
    Col(ColRef)                          # qualified column reference (table.col or alias)
  | Lit(Value)                           # typed literal (Int, Decimal, Float, Str, Bool, Null, Date, ...)
  | Call(ScalarFn, [Expr])               # +,-,*,/, =,<>,<,<=,>,>=, AND,OR,NOT, LIKE, IN, BETWEEN, CAST, COALESCE...
  | Case([(Expr,Expr)], Option<Expr>)    # CASE WHEN ... THEN ... ELSE ...
  | Agg(AggFn, Expr, distinct: bool)     # COUNT/SUM/AVG/MIN/MAX/... (only under Aggregate)
  | Subquery(SubqueryKind, Plan)         # scalar | EXISTS | IN | ANY/ALL  (target of decorrelation)
  | WindowCall(WindowFn, partition:[Expr], order:[Expr], frame)

Type   ::= Bool | Int(width) | Decimal(p,s) | Float | Str | Date | Timestamp | Null
Value  : a typed constant;  NULL is a distinct value with three-valued-logic semantics

Expressions are hash-consed (interned to ExprId) — structural sharing makes equality O(1) (critical for CSE, transitive-predicate dedup, and memo fingerprints). Scalar functions carry monotonicity + null-propagation + determinism flags used by rewrites (e.g. only deterministic, null-rejecting predicates push through outer joins).

8.3 Physical plan IR (executable operator tree)

PhysicalOp ::=
    SeqScan    { table, pred }                          # full table scan + residual filter
  | IndexScan  { table, index, bounds, pred }           # index range/point scan (provides index order)
  | IndexOnlyScan { table, index, cols }                # covering index (no heap fetch)
  | PhysFilter { input, pred }
  | PhysProject{ input, exprs }
  | HashJoin   { build: PhysPlan, probe: PhysPlan, keys, kind, residual }   # build side hashed
  | MergeJoin  { left, right, keys, kind }              # both inputs sorted on keys (requires order)
  | NestedLoop { outer, inner, kind, pred }             # inner re-scanned (index-NL if inner is IndexScan)
  | HashAgg    { input, group, aggs }                   # hash grouping (no order requirement)
  | SortAgg    { input, group, aggs }                   # streaming grouping (requires input sorted on group)
  | PhysSort   { input, keys }                           # enforcer: produces a sort order
  | PhysLimit  { input, n, offset }
  | PhysSetOp  { ... }
  | PhysWindow { input, fns }                            # requires partition+order (may need Sort)
  | Exchange   { input, dist: Hash([Expr]) | Range | Broadcast | Gather }  # distributed enforcer (stub)

Every physical node is annotated, after costing, with: derived physical properties (provided order, provided distribution), estimated cardinality (rows), estimated cost (Cost vector + scalar), and memory estimate (for spill decisions). The output of optimization is a PhysicalPlan tree (the winner DAG flattened along required properties).

8.4 Logical properties (per plan node)

LogicalProps {
  schema:        [(name, Type, nullable)],
  card_estimate: f64,                 # rows (from §estimate)
  keys:          [KeySet],            # sets of columns that are unique (PK/unique/derived)
  fds:           [FuncDep],           # X → Y functional dependencies (declared + derived)
  not_null:      ColSet,              # columns guaranteed non-null
  max_card:      Option<u64>,         # upper bound (e.g. after Limit, or unique-key equality)
  output_cols:   ColSet,              # columns produced (for projection pruning)
}

Properties are derived by operator (Join unions schemas + intersects/propagates keys+FDs; Aggregate's group columns become a key; equality predicate a=const adds {a}→all FD; Filter a IS NOT NULL adds a to not_null). Keys/FDs drive join-cardinality (key-join ⇒ cardinality ≤ child) and redundant-operator elimination (a DISTINCT over a key is a no-op).

8.5 Statistics schema (per column / per table)

TableStats  { row_count: u64, page_count: u64, analyzed_at: Timestamp, sample_rate: f64 }
ColumnStats {
  ndv:         HllSketch | u64,        # # distinct values (HyperLogLog, §stats)
  null_frac:   f64,                    # fraction NULL
  mcv:         [(Value, freq: f64)],   # most-common-value list (top-k + their frequencies)
  histogram:   Histogram,              # equi-depth (default) or max-diff; buckets over non-MCV domain
  min, max:    Value,                  # domain bounds
  avg_width:   u32,                    # bytes (for IO/memory cost)
  correlation: f64,                    # physical-order vs value-order correlation (for index-scan cost)
}
Histogram   { kind: EquiDepth|MaxDiff, buckets: [Bucket] }
Bucket      { lo: Value, hi: Value, count: f64, distinct: f64 }   # rows + NDV per bucket
ExtendedStats {                                                    # multi-column / correlation
  cols:        [ColId],
  ndv:         u64,                    # joint distinct count (for GROUP BY / correlated predicates)
  dependencies:[(ColSet → ColSet, degree: f64)],                   # soft FDs for correlation correction
  mcv:         [([Value], freq)],      # joint MCV (for correlated equality conjunctions)
}

The MCV list captures skew the histogram smooths over (selectivity of a frequent value comes from MCV, of a rare value from the histogram). Extended stats (multi-column NDV + soft dependencies) are the only defense against the independence assumption's failure (§10.7).

8.6 Selectivity + cardinality semantics (the estimator contract)

sel(a = const)        = mcv_freq(const)  if const ∈ MCV
                      = (1 - Σ mcv_freq - null_frac) / (ndv - |MCV|)   otherwise   # uniform over remainder
sel(a < const)        = histogram fraction below const (interpolate within bucket)
sel(a = b)  [join]    = 1 / max(ndv(a), ndv(b))                       # containment + uniform
sel(p ∧ q)            = sel(p) · sel(q)                               # INDEPENDENCE (default; corrected by ext-stats)
sel(p ∨ q)            = sel(p) + sel(q) − sel(p)·sel(q)
card(σ_p(R))          = card(R) · sel(p)            (clamped to [1, card(R)] when non-empty)  (I6/I12)
card(R ⋈_{a=b} S)     = card(R)·card(S) · sel(a=b)  (key-join ⇒ ≤ card of non-key side)
card(Γ_group(R))      = min( ndv(group) , card(R) )  (group cols form a key on the output)

q-error of an estimate ê vs truth t is max(ê/t, t/ê) (≥1, 1 = perfect); the estimator tracks per-operator q-error when true counts are supplied (test/EXPLAIN ANALYZE) and the cost-based search's quality is judged on the product of q-errors up the tree (see Performance Engineering).

8.7 Worked example A — predicate pushdown + index choice + join order

SQL (fixture): SELECT o.id FROM orders o JOIN customers c ON o.cust = c.id WHERE c.region = 'EU' AND o.total > 100; Catalog: customers(id PK, region) 1M rows, region NDV 5; orders(id PK, cust FK→customers.id, total) 10M rows; index idx_cust_region(region), index idx_orders_cust(cust).

INPUT (canonical logical, comma-join lowered):
  Project[o.id]
    Filter[c.region='EU' AND o.total>100]
      Join[Inner, o.cust=c.id]
        Scan(orders o)            -- 10M
        Scan(customers c)         -- 1M

AFTER rewrite (predicate pushdown + projection pruning + transitive infer):
  Project[o.id]
    Join[Inner, o.cust=c.id]
      Scan(orders o, pred: o.total>100, cols:[id,cust])     -- σ pushed; cols pruned
      Scan(customers c, pred: c.region='EU', cols:[id])     -- σ pushed; cols pruned
  # estimate: sel(region='EU')=1/5 → c' ≈ 200k ; sel(total>100) from histogram ≈ 0.3 → o' ≈ 3M

CHOSEN PHYSICAL (Cascades winner; join order flips to build on smaller side):
  PhysProject[o.id]
    HashJoin[Inner, o.cust=c.id]                  cost≈ build 200k + probe 3M
      build: IndexScan(customers idx_cust_region, region='EU')   -- 200k, index point-range
      probe: SeqScan(orders, total>100)                          -- 3M (no useful index on total)
  # alternative pruned by branch-and-bound: NestedLoop with index on orders.cust
  #   (3M outer × index-probe) costed higher than the hash build of 200k.

8.8 Worked example B — interesting orders + merge join reuse

SQL: SELECT a.k, b.v FROM a JOIN b ON a.k=b.k ORDER BY a.k; — a has a clustered index on k, b has a clustered index on k.

Two physical candidates the memo holds for the Join group (required order: a.k ASC for the parent Sort):
  (1) HashJoin → then PhysSort[a.k]                 # sort AFTER join: sort 2M rows
  (2) MergeJoin[a.k=b.k]                             # inputs already sorted by index → NO enforcer
        IndexScan(a, order=k) | IndexScan(b, order=k)
  Winner: (2). The merge join PROVIDES the a.k order for free (P5/I14), so the parent ORDER BY
  needs no Sort enforcer. The optimizer recognizes a.k as an *interesting order* during enumeration
  and propagates the requirement down — the System-R insight (Selinger 1979) that makes (2) win.

8.9 Worked example C — subquery decorrelation

SQL: SELECT c.id FROM customers c WHERE c.total > (SELECT AVG(o.total) FROM orders o WHERE o.cust=c.id);

INPUT (correlated scalar subquery; o.cust=c.id references the outer c):
  Filter[c.total > scalar( Aggregate[AVG(o.total)] over Filter[o.cust=c.id](orders) )]
    Scan(customers c)

AFTER decorrelation (§rewrite; I15 must hold):
  Project[c.id]
    Filter[c.total > avg_total]
      Join[LeftOuter, c.id = agg.cust]            # outer join preserves customers with no orders
        Scan(customers c)
        Aggregate[group: o.cust, AVG(o.total) AS avg_total]    # group the subquery once, per cust
          Scan(orders o)
  # Equivalence obligation (I15): NULL avg for customers with no matching orders → c.total > NULL = NULL
  #   = false (3-VL), matching the correlated semantics (subquery returns NULL ⇒ predicate fails).
  # Without decorrelation: O(|customers|) re-executions of the subquery; with it: one grouped join.

8.10 Malformed / failure-path examples

  • Type mismatch in a predicate (WHERE int_col = 'abc' with no implicit cast) → bind error (column, expected/got type), never reaches the optimizer.
  • Correlated column unresolved (subquery references a name not in any enclosing scope) → bind error.
  • Aggregate without GROUP BY mixing aggregated + non-aggregated columns → bind error (SQL semantics).
  • Stats missing for a column → estimator uses the documented fallback (uniform via ndv if known, else a magic-constant selectivity) and sets low_confidence; never fails (P7).
  • Histogram bucket with lo > hi (corrupt stats) → histogram_malformed (I13); rebuild or fall back to uniform; the optimizer proceeds, flags low confidence.
  • Cardinality estimate overflow (huge cross-product estimate) → cardinalities are f64 with saturation at a documented ceiling; the cost saturates rather than overflowing to ∞/NaN (I6).
  • Join graph with a cross product required (no connecting predicate between two relation sets) → DPccp will not connect them; the enumerator explicitly adds a cross-product join only as a last resort, costed as such; flagged in the trace.
  • A rewrite that would change outer-join semantics (pushing a non-null-rejecting predicate below an outer join's null-padding side) → the rule's guard rejects it (I1/I15); if a bug lets it through, the differential checker catches the wrong result.
  • Optimization budget exhausted on a 25-relation query → DP ceiling exceeded → greedy+GEQO produces a plan, budget_exceeded + geqo_used flagged (I7).

§9-note (ADR-06, the load-bearing decision): Cascades top-down vs System-R bottom-up. Chosen: Cascades/Volcano top-down memo search. The optimizer is asked to be extensible (new operators/rules without rewriting the core), property-driven (interesting orders + distribution for #316), and to share structure across logically-equivalent subplans (the memo). Cascades delivers all three: rules are pluggable, the memo dedups equivalent subexpressions and memoizes winners per required-property set, and branch-and-bound prunes top-down using a cost bound carried from the parent. Rejected: System-R bottom-up DP. System-R's optimalPlan(subset) DP with interesting-orders is simpler and is exactly what the predecessor #206 and PostgreSQL use — but it is operator-set-rigid (adding a new operator means editing the DP recurrence), it materializes the whole subset lattice even where a cost bound would prune, and it lacks a clean memo for arbitrary (non-join) subexpression sharing. We embed the System-R join DP inside Cascades as the join-enumeration rule (DPccp), getting its optimal join ordering while keeping the extensible memo framework around it. This is the modern synthesis (CockroachDB, Orca, Calcite-Volcano). Operational implication: a wrong cost bound prunes the optimum (I8) — the bottom-up DP cannot have that bug, so the bound's admissibility is a first-class invariant. Scaling implication: the memo's per-property memoization is what makes property enforcement tractable but multiplies group entries by the number of distinct required-property sets — bounded by the small number of interesting orders in real queries.

0.1 Objectives

Lay down the workspace, the plan IR (ir: logical + physical + expression model + type system + interner), the read-only catalog, and a thin SQL-subset bind (fixtures only). No optimization yet — just a typed, validated LogicalPlan flowing in and an EXPLAIN of the unoptimized plan flowing out.

0.2 Detailed Implementation Steps

  • Cargo workspace; Makefile; CI; Apache license; governance files; docs/adr stubs (01..30).
  • ir/expr.rs: Expr enum, hash-consing interner (ExprId), ScalarFnMeta (deterministic/null-rejecting/monotonic flags — load-bearing for rewrites). (Graefe 1995; ADR-04)
  • ir/types.rs: Type, Value, three-valued-logic comparison semantics (NULL handling), implicit-cast rules.
  • ir/logical.rs: LogicalOp, the LogicalPlan DAG (shared subtrees via PlanId), schema derivation per operator.
  • ir/physical.rs: PhysicalOp, PhysAnnot (initially unpopulated).
  • ir/props.rs: LogicalProps + derive_props (keys/FDs/not-null per operator; Aggregate group→key; equality→FD; IS NOT NULL→not_null) (I11). (ADR-05; I11)
  • catalog/: tables, columns, schemas, declared keys/FDs, NOT-NULL, index descriptors, MV definitions. Read-only API.
  • bind/: subset lexer + recursive-descent parser (SELECT … FROM … JOIN … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT, set ops, basic window); resolve.rs (scopes, qualified names, correlated-ref detection); typecheck.rs → LogicalPlan. Out-of-scope SQL → PhaseDeferred.
  • explain/plan_fmt.rs: render a LogicalPlan as a text tree.

0.3 Deliverable

cli explain --logical query.sql parses, binds, type-checks, and prints the canonical (unoptimized) logical plan tree + derived schema/properties. cli round-trips a LogicalPlan (parse → IR → print) deterministically.

0.4 Acceptance Criteria

  • Subset binder parses + type-checks the JOB/TPC-H query subset chosen for fixtures; type errors + unresolved names reported with location.
  • Hash-consing: structurally equal expressions share an ExprId (identity test); the plan is a DAG for CSE inputs.
  • derive_props correct on fixtures: PK scan has the key; Aggregate output key = group columns; equality predicate adds the FD (I11 audit).
  • Binder fuzz (cargo-fuzz) survives 5 min, no panic/UB.

0.5 Conformance Fixtures

bind/spja-basic (plan tree), bind/type-error (error + loc), bind/unresolved-col (error), bind/correlated-detect (subquery marks correlation), ir/hashcons-sharing, ir/props-key-derive, ir/props-fd-from-eq.

0.6 Pitfalls

  • Three-valued logic mishandled (NULL = NULL is NULL, not true; NOT (NULL) is NULL) → wrong predicate semantics baked in before optimization. Centralize 3-VL in types.rs; test every comparison against NULL.
  • Not hash-consing expressions → CSE + transitive-predicate dedup + memo fingerprints all break / explode. Intern from day one.
  • Schema derivation drift (a column's nullability wrong after an outer join) → downstream rewrites make unsound decisions. Derive nullability per operator explicitly; outer-join null-extends the inner side.
  • Binder accepting out-of-scope SQL silently → the optimizer receives an IR it can't preserve. Strict subset; unsupported → PhaseDeferred, never a wrong lowering.

0.7 Performance Concerns

Interning is hot (every expr build hits it) — fast hasher, but salted for determinism (I9). Schema/property derivation is O(plan size) and cached on the node. The binder is not perf-critical (fixtures), but deep nested subqueries must not stack-overflow (explicit depth cap).

0.8 Edge Cases

Empty SELECT list (error); SELECT * expansion against the catalog schema; ambiguous column (two tables, same name → error or qualified-required); correlated reference to an outer alias; GROUP BY ordinal vs expression; NULL literal typing; integer/decimal coercion; window function in WHERE (error — wrong clause).

0.9 Failure Analysis

A binder/IR bug mis-encodes the query → every plan is for the wrong query. Blast radius: total (silent wrong results downstream). Containment: round-trip + a differential check that the unoptimized plan executes to the SQL's expected result on a reference (where a fixture executor exists). Forensics: dump the bound IR alongside any optimizer output (--echo-bound).

0.10 Operational Notes

Stats from day one: bind_plans, bind_exprs, intern_hits, props_derive_ms. --echo-bound flag. Deterministic interning order (I9). The IR + property derivation is the teaching artifact for "what a bound query actually is."

  • Staleness: stats record their sample time + table version; a stale flag is surfaced.

1.5 Conformance Fixtures

stats/hll-accuracy (NDV error bound), stats/equidepth-balance, stats/maxdiff-skew, stats/mcv-topk, stats/histogram-audit (I13), stats/extended-joint-ndv, stats/analyze-sample, stats/staleness-flag.

1.6 Pitfalls

  • Equi-width instead of equi-depth on skewed data → every bucket equally wide but wildly unequal counts → range selectivity garbage on skew. Default equi-depth; max-diff for heavy tails.
  • NDV from a small sample extrapolated naively → distinct-count under/over-estimate (the classic "sample sees few distinct, true is many"). Use HLL on a larger pass or a principled estimator (e.g. Chao/Shlosser), not linear scaling.
  • MCV + histogram double-counting → selectivity > 1. MCV values are excluded from the histogram domain; the histogram covers only the non-MCV remainder.
  • Null fraction folded into the histogram → range estimates include nulls. Keep null_frac separate (I13); nulls never satisfy a range/equality (3-VL).
  • Stale stats used silently → the optimizer plans for a table that has since 100×'d. Track + surface staleness; re-ANALYZE policy is an operational lever.

1.7 Performance Concerns

ANALYZE is sampling-bound; one pass for HLL + histogram + MCV (don't re-scan per statistic). HLL registers are small + cache-resident. Histogram sort is the cost on large samples — bound the sample size. Extended-stats joint NDV is combinatorial in the column count — only build for explicitly requested column groups.

1.8 Edge Cases

All-NULL column (null_frac=1, empty histogram); single-value column (NDV=1, one MCV); all-distinct column (NDV=row_count, MCV empty or all freq≈1/n); empty table (row_count=0, estimates default to 1 downstream); a column with huge string values (avg_width drives IO cost); a column whose physical order perfectly matches value order (correlation=1 → cheap index range scan).

1.9 Failure Analysis

Bad stats → bad estimates → bad plans (but not wrong results — semantic preservation holds regardless). Blast radius: plan quality, not correctness. Detection: q-error monitoring (Phase 2) flags estimates far from truth; a corrupt histogram (I13) is caught at build/load. Recovery: re-ANALYZE; fall back to uniform/magic-constant selectivity with a low-confidence flag (P7). Forensics: dump-stats + the q-error report pinpoint which column's stats misled the plan.

1.10 Operational Notes

Stats: analyze_ms, sample_rows, hll_ndv, histogram_buckets, mcv_len, stats_stale_count. cli dump-stats, --sample-rate. Auto-stats policy (re-ANALYZE when a table's row count drifts > threshold since analyzed_at) is an operational knob, documented in runbooks/stale-stats.md. Staleness is the #1 real-world cause of "the plan was good yesterday."

Phase 2 — Cardinality + Selectivity Estimator

2.1 Objectives

The single most important and hardest subsystem: estimate. Selectivity for every predicate form (equality, range, LIKE, IN, conjunction, disjunction), join cardinality (containment + key/FD-aware), correlation correction from extended stats, and q-error propagation up the plan tree. Implement the CardinalityEstimator trait so learned models can later slot in (§10.9).

2.2 Detailed Implementation Steps

  • estimate/selectivity.rs: sel(a=const) via MCV-then-histogram-remainder; sel(a<const) via histogram interpolation; sel(LIKE 'prefix%') via prefix-range on the histogram; sel(a IN (...)) = Σ point selectivities (capped); conjunction = product (independence, ADR-13), disjunction = inclusion-exclusion; all clamped to [0,1] (I12). (Selinger et al. 1979; ADR-13)
  • estimate/join_card.rs: card(R⋈S) = card(R)·card(S)·sel(join); sel(a=b) = 1/max(ndv(a),ndv(b)) (containment); key-aware: a join on a unique key bounds the result to the non-key side's cardinality; FD-aware refinement. (Selinger et al. 1979; I6)
  • estimate/correlation.rs: when a conjunction's columns have an extended-stats dependency, replace the independent product with the joint MCV / soft-FD-adjusted estimate (the only defense against independence failure, §10.7).
  • estimate/propagate.rs: thread estimates bottom-up; record per-operator q-error when true counts are provided (test/EXPLAIN ANALYZE mode); compute the product q-error up the tree (the headline accuracy metric).
  • estimate/sampling.rs: a sample-based fallback hook for predicates stats can't handle (complex expressions) — execute the predicate on a sample, scale up.
  • estimate/trait.rs: the CardinalityEstimator trait; ship the classical estimator as the default impl.

2.3 Deliverable

cli explain --estimate query.sql annotates each logical operator with its estimated cardinality + confidence; --card-report (with true counts supplied) prints per-operator + cumulative q-error.

2.4 Acceptance Criteria

  • Selectivity ∈ [0,1] for every predicate form; cardinalities finite, ≥ 0, clamped to [1, table_card] when output is non-empty (I6/I12 assertions).
  • On TPC-H (uniform-ish data): per-operator q-error ≤ 4 typical with base stats.
  • On JOB (correlated data): per-operator q-error ≤ 4 with extended stats; without, the report documents the independence-assumption blow-up (the teaching point — this is expected to be worse and is the motivation for §10.7).
  • Estimates are deterministic for fixed (plan, stats, seed) (I9).
  • The estimator trait is swappable (a trivial "always 1000 rows" stub passes the integration, proving the seam).

2.5 Conformance Fixtures

estimate/sel-eq-mcv, estimate/sel-eq-histogram, estimate/sel-range, estimate/sel-like-prefix, estimate/sel-in, estimate/sel-conj-independent, estimate/sel-disj, estimate/join-containment, estimate/join-key-bounded, estimate/correlation-extended, estimate/qerror-propagation, estimate/missing-stats-fallback.

2.6 Pitfalls

  • The independence assumption (sel(p∧q)=sel(p)·sel(q)) — the #1 source of catastrophic under-estimation on correlated columns (e.g. city='SF' AND state='CA' — state is determined by city). Manifestation: a join the optimizer thinks produces 10 rows actually produces 10M → a hash build that spills/OOMs. Defense: extended stats (§10.7); flag low confidence when columns are correlated but no extended stats exist.
  • 0-row estimates make everything downstream "free" → the optimizer picks a fantasy plan. Clamp to ≥1 for non-empty-guaranteed outputs (I6).
  • Join-cardinality under independence + uniformity under-estimates many-to-many joins badly; the error compounds multiplicatively (a 4× per-join error over 10 joins → 10⁶×). This is the q-error explosion — there is no clean fix in classical estimation, only damping + sampling + learned models (the honest framing).
  • LIKE selectivity with a non-prefix pattern (%foo%) — the histogram can't help; fall back to a magic constant, flag low confidence.
  • Distinct-count after a filter — NDV doesn't shrink proportionally to selectivity (a filter on column A doesn't reduce NDV of column B by the same factor); track NDV separately from cardinality.

2.7 Performance Concerns

Estimation runs inside the search inner loop (every candidate group expression needs a cardinality) — it must be cheap (O(predicate size), histogram lookups are O(log buckets)). Cache estimates per (group, predicate) — the memo memoizes the logical cardinality of a group once (it's a logical property, same for all group expressions, I11). Sampling fallback is expensive — use it sparingly, only when stats fail.

2.8 Edge Cases

Predicate on a column with no stats (fallback + flag); equality on a value above max/below min (selectivity → 0, but clamp to ≥1 row if the column could have unseen values? — documented policy: 0 selectivity → estimate the floor, flag); join with no NDV on either side (fall back to a default join selectivity); a self-join (same table both sides — NDV is identical); a join on a key×key (one-to-one — cardinality = min of the two); disjunction of overlapping ranges (inclusion-exclusion must not double-subtract).

2.9 Failure Analysis

A systematic estimation bug (e.g. selectivity off by the null fraction) skews every plan. Blast radius: plan quality across all queries. Detection: the q-error report on the conformance corpus — a regression in median q-error fails CI. Recovery: the estimator is swappable (trait); a regression can be isolated to one selectivity function via the per-form fixtures. Forensics: --card-report shows exactly which operator's estimate diverged from truth; ddmin minimizes the query + stats that trigger it.

2.10 Operational Notes

Stats: estimate_calls, estimate_ms, median_qerror, p95_qerror, low_confidence_count, sampling_fallbacks. --card-report, --estimator classical|stub. The q-error histogram per query family is the optimizer's most important health dashboard — rising q-error predicts bad plans before users complain. Document in runbooks/bad-plan.md: bad plan → check q-error → check stats staleness → check for missing extended stats on correlated columns.

Phase 3 — Cost Model

3.1 Objectives

Build cost: the per-operator cost model (Cost vector of CPU/IO/memory/network reduced to a scalar via calibration weights), the memory budget + spill-cost model, and a calibration harness. Cost is a deterministic function of cardinality (Phase 2) + physical properties; this phase makes operator alternatives comparable.

3.2 Detailed Implementation Steps

  • cost/operators.rs: per-PhysicalOp cost formulas — (Ramakrishnan & Gehrke ch. on query optimization; ADR-10)
    • SeqScan: page_count · seq_page_cost + rows · cpu_tuple_cost (+ filter rows · cpu_op_cost · #preds).
    • IndexScan: index-descent + matched-leaf pages × random_page_cost (adjusted by correlation for clustered vs scattered), + per-row heap fetch unless IndexOnlyScan.
    • HashJoin: build-side build_rows · (cpu_tuple + hash) + probe-side probe_rows · (cpu_tuple + probe); asymmetric (build the smaller side); + spill cost if build > memory budget.
    • MergeJoin: linear in both inputs (assumes sorted; the sort cost is on the input, possibly via an enforcer).
    • NestedLoop: outer_rows · inner_cost (index-NL: inner is an IndexScan per outer row).
    • HashAgg: rows · (cpu_tuple + hash) + spill if groups > memory; SortAgg: linear, requires sorted input.
    • PhysSort (enforcer): rows · log(rows) · cpu_op_cost + spill (external merge sort) if > memory.
    • Exchange (stub): rows · (net_byte_cost · avg_width) for the distributed cost (#316).
  • cost/memory.rs: per-operator memory estimate (hash table size, sort buffer); the global memory budget; spill detection → external-algorithm cost.
  • cost/model.rs: the Cost vector → scalar reduction via calibration weights; lower_bound (admissible: a group's lower bound = cheapest possible scan of its inputs, never over-estimates, I8). (ADR-10; I8)
  • cost/calibrate.rs: a harness that fits calibration constants (seq_page_cost, random_page_cost, cpu_tuple_cost, cpu_op_cost, net_byte_cost) against measured operator timings (or documented defaults from a reference system).

3.3 Deliverable

cli cost --physical plan.json annotates a physical plan with per-operator Cost vectors + the scalar total + memory estimates + spill flags. Two physical plans for the same query are comparable by scalar cost.

3.4 Acceptance Criteria

  • Cost is a pure, deterministic function of (cardinality, properties, calibration) — no wall-clock, no randomness.
  • Build-side asymmetry correct: HashJoin(small build, large probe) costs less than HashJoin(large build, small probe).
  • Spill cost engages when an operator's memory estimate exceeds the budget (a 10GB hash build at a 1GB budget shows external-spill cost).
  • lower_bound is admissible on all fixtures (I8): the bound ≤ the actual best cost found, verified by the pruned-vs-full check on small queries.
  • Calibration constants are documented + reproducible; changing them changes plans predictably.

3.5 Conformance Fixtures

cost/seqscan, cost/indexscan-correlation, cost/hashjoin-asymmetry, cost/mergejoin-linear, cost/nestedloop-index, cost/hashagg-spill, cost/sort-external, cost/lower-bound-admissible (I8), cost/exchange-stub.

3.6 Pitfalls

  • Ignoring the memory budget → costing a hash join as in-memory when it spills → choosing a plan that thrashes. Model spill explicitly; the budget is a first-class input.
  • Symmetric hash-join cost → the optimizer doesn't know to build the smaller side → 10× the hash-table memory + build cost. Cost must be asymmetric in build vs probe.
  • random_page_cost = seq_page_cost → index scans always look as cheap as sequential → index thrashing on large scans where a seq scan + filter is better. The seq/random ratio (and the correlation adjustment) is the single most influential calibration constant.
  • Inadmissible lower bound → branch-and-bound prunes the optimal plan → silently sub-optimal output (I8). The bound must never exceed the true subtree cost; when in doubt, use 0 (always admissible, just weak).
  • Double-counting input cost → a parent that re-adds its child's cost inflates everything uniformly (harmless for comparison if consistent, but breaks the lower-bound admissibility and the absolute q-cost report). Define cost as incremental per operator + sum, exactly once.

3.7 Performance Concerns

Cost is computed per candidate in the search inner loop — keep formulas arithmetic-only (no allocation). The Cost vector is a fixed 4-field struct (no heap). Reduction to scalar is a dot product with calibration weights. Memory estimation must not require materializing anything — it's a formula on cardinality + avg_width.

3.8 Edge Cases

Zero-row input (cost → near-zero, but ≥ the fixed operator startup cost); a sort of already-sorted input (the enforcer should not be inserted — Phase 8 handles this via properties, but cost must not reward a redundant sort); an operator whose memory estimate is exactly the budget (boundary — spill or not, documented); a cross-product (huge cardinality → cost saturates, not overflows); Exchange on a single-node plan (cost 0 — no network).

3.9 Failure Analysis

A cost-formula bug systematically biases operator choice (e.g. always prefers nested-loop). Blast radius: plan quality. Detection: plan-quality regression on the conformance corpus (a query family suddenly picks a worse operator); the per-operator cost breakdown in EXPLAIN. Recovery: calibration is a knob — re-fit; the per-operator fixtures isolate which formula regressed. Forensics: cli cost --physical on the two competing plans shows where the cost diverges.

3.10 Operational Notes

Stats: cost_calls, cost_ms, spill_predicted_count, calibration_version. cli cost, --calibration <file>, --memory-budget. Calibration constants are environment-specific (SSD vs HDD changes random_page_cost); document the defaults + the re-calibration procedure in docs/performance/. A miscalibrated cost model is a common cause of "good plan on the dev box, bad plan in prod."

Phase 4 — Rewrite / Normalization Rules (heuristic, pre-search)

4.1 Objectives

Build rules/rewrite/: the heuristic, unconditionally beneficial logical-to-logical rewrites applied to a fixpoint before the cost-based search — predicate pushdown, projection pruning, constant folding + expression simplification, transitive predicate inference, outer-join simplification, redundant-operator elimination, CTE/view inlining, common-subexpression detection, and subquery decorrelation. Each must preserve semantics (I1) and the set must terminate (I4/P13).

4.2 Detailed Implementation Steps

  • rules/rewrite/pushdown.rs: push Filter below Project/Join/Aggregate where the predicate's columns are available; split conjunctive predicates so each conjunct pushes as far as it can; guard outer joins (only null-rejecting predicates push to the null-extended side — the I1/I15 trap). (Selinger et al. 1979; P3)
  • rules/rewrite/prune.rs: projection pruning — remove columns no ancestor uses (top-down required-columns analysis); drop unused Project columns; eliminate whole subtrees producing only unused columns.
  • rules/rewrite/constfold.rs + simplify.rs: constant folding (1+1→2), boolean simplification (x AND true→x, x OR false→x, x AND false→false), CASE short-circuit, COALESCE of a not-null arg, comparison normalization (const OP col → col OP' const).
  • rules/rewrite/transitive.rs: transitive predicate inference (a=b ∧ b=c ⟹ a=c; a=b ∧ a>5 ⟹ b>5) — generates new pushable predicates + join opportunities. Dedup via ExprId to terminate (I4).
  • rules/rewrite/outerjoin.rs: outer-join simplification (a null-rejecting predicate on the null-extended side turns an outer join into an inner join → enables reordering); outer-join reordering where the association is semantics-preserving.
  • rules/rewrite/redundant.rs: redundant-operator elimination — DISTINCT/GROUP BY over a key is a no-op; Sort immediately under another Sort/an order-insensitive parent is dropped; Filter[true] removed; Limit of a known-smaller relation simplified (uses max_card, I11).
  • rules/rewrite/inline.rs: CTE/view inlining (substitute the definition; respect multiplicity — inline only when not referenced multiple times, else keep as a shared DAG node / CSE).
  • rules/rewrite/cse.rs: common-subexpression detection — identical subtrees (same PlanId after interning) become a shared DAG node (avoids re-computing the same scan/join).
  • rules/rewrite/decorrelate.rs: subquery unnesting — scalar (→ outer join with aggregate, §8.9), EXISTS/IN (→ semi-join), NOT EXISTS/NOT IN (→ anti-join, with NULL-handling care). Soundness-gated (I15): the rule carries an equivalence obligation verified differentially. (Seshadri et al. decorrelation lineage; I15)
  • Driver: apply rules to a fixpoint with a step budget; deterministic rule order by promise() (P9).

4.3 Deliverable

cli explain --normalized query.sql shows the plan after rewriting (predicates pushed, projections pruned, subqueries decorrelated, redundancies removed). The normalized plan is the input to the Cascades search (Phase 5).

4.4 Acceptance Criteria

  • Every rewrite preserves semantics: the differential equivalence check (I1) passes on the equiv/ corpus (normalized plan executes to the same multiset as the input).
  • Predicate pushdown reaches the deepest legal point; outer-join guard prevents the unsound push (a fixture proves the guard rejects it, I15).
  • Decorrelation turns the §8.9 correlated query into a single grouped join, and the result is differentially equal to the correlated execution (I15).
  • The rewrite set reaches a fixpoint (no infinite cycle) within the step budget on all fixtures (I4); commute/transitive dedup proven.
  • Projection pruning + CSE reduce the plan's column footprint + node count measurably (≥10% typical, M5).

4.5 Conformance Fixtures

rewrite/pushdown-through-join, rewrite/pushdown-outerjoin-guard (must NOT push), rewrite/projection-prune, rewrite/constfold, rewrite/bool-simplify, rewrite/transitive-infer, rewrite/outerjoin-to-inner, rewrite/distinct-over-key (eliminated), rewrite/cte-inline, rewrite/cse-share, rewrite/decorrelate-scalar (I15), rewrite/decorrelate-exists-semijoin, rewrite/fixpoint-terminates (I4).

4.6 Pitfalls

  • Pushing a non-null-rejecting predicate below an outer join's null side — the classic semantic-corruption bug. A predicate that is true/unknown on NULLs changes which rows the outer join null-pads → wrong results. Guard: only null-rejecting predicates push to the null-extended side (I1/I15).
  • Decorrelation NULL semantics — NOT IN (subquery with a NULL) is not an anti-join naively (a NULL in the subquery makes NOT IN return NULL/false for everything). The unnesting must replicate 3-VL exactly (I15) — the single trickiest rewrite.
  • Non-terminating rewrite cycle — commute then commute-back, or transitive inference generating "new" predicates forever. Guard: dedup generated expressions/plans by ExprId/PlanId (I4); a rewrite that produces an already-seen plan is a no-op.
  • Aggressive CTE inlining of a CTE referenced N times → N× the work (the inverse of CSE). Inline only single-reference CTEs; keep multi-reference ones as shared DAG nodes.
  • Projection pruning breaking a needed column — pruning a column an ancestor (or a correlated subquery) actually uses → wrong schema / unresolved reference downstream. The required-columns analysis must be conservative + complete.

4.7 Performance Concerns

Rewriting is O(plan size × rules × fixpoint iterations) — keep it pre-search (once) and terminating. Pattern matching for each rule is the cost — index plan nodes by operator type so a rule only visits relevant nodes. Transitive inference can generate quadratically many predicates — cap + dedup. Decorrelation is structural (cheap) but the resulting plan is larger (a join replaces a subquery) — that's the point (one join beats N re-executions).

4.8 Edge Cases

A predicate referencing columns from both join sides (can't push to either; stays on the join as the on condition); pushing into a UNION (push into both branches); a Filter[false] (the subtree produces no rows — replace with an empty relation); a CTE that is recursive (out of scope → PhaseDeferred); decorrelation of a subquery in a CASE (correlation in a conditional context — careful with the 3-VL); a self-referential view (cycle detection in inlining).

4.9 Failure Analysis

An unsound rewrite is the worst bug in the system — it silently changes results (I1). Blast radius: every query the rule fires on returns wrong data. Detection: the differential equivalence harness (I1) on equiv/ must run on every rewrite in CI; a property-fuzzer generates random plans + rewrites them + checks equivalence (the highest-value fuzzing here). Recovery: disable the offending rule (rules are individually toggleable), regress the minimal triggering plan. Forensics: --trace-rewrite logs each rule firing + the before/after plan.

4.10 Operational Notes

Stats: rewrite_firings (per rule), rewrite_iterations, plan_nodes_before/after, decorrelations, predicates_inferred. --trace-rewrite, --disable-rule <name>, --no-decorrelate (escape hatch). Each rewrite rule has an ADR documenting its semantic-preservation argument. The outer-join + decorrelation rules are the ones to scrutinize in any review — they are where correctness bugs hide (P1).

Phase 5 — Memo + Cascades Search Skeleton

5.1 Objectives

Build the heart of the optimizer: the memo (groups, group expressions, fingerprint dedup, group merging, per-required-property winners) and the search task scheduler (the Cascades task model + branch-and-bound). Wire in the cost/estimate from Phases 2–3. This phase makes the optimizer cost-based — but with only trivial rules (a single implementation rule per operator), proving the search machinery before the rule set grows.

5.2 Detailed Implementation Steps

  • memo/group.rs + group_expr.rs: Group (logical + physical group-expr lists, shared LogicalProps, winner map); GroupExpr (op + child GroupIds + applied_rules mask).
  • memo/memo.rs: insert with a structural Fingerprint (op + sorted child group ids) → dedup (I3); merge_groups when two groups prove logically equivalent (duplicate detection, I2); group LogicalProps derivation (cardinality is a logical property, computed once per group via Phase 2, I11). (Graefe 1995; I2/I3)
  • memo/winner.rs: the per-RequiredProps winner map (I10) — the best costed physical expr that satisfies a given required-property set.
  • search/scheduler.rs: the LIFO task stack; the budget guard (steps/bytes/wall → best-so-far + flag, I7).
  • search/tasks.rs: the Cascades tasks —
    • OptimizeGroup(g, req, bound): ensure the group is explored, then optimize each group expression for req under bound.
    • ExploreGroup(g): apply all transformation rules to grow the group's logical expressions.
    • OptimizeExpr(e, req, bound): apply implementation rules, then schedule OptimizeInputs.
    • ApplyRule(e, rule, req, bound): match + fire a rule, inserting results into the memo.
    • OptimizeInputs(e, req, bound): recursively optimize children for their required props (propagated down), accumulate cost, update the winner (I10).
    • EnforceProps(g, req, bound): insert an enforcer (Sort/Exchange) if no group expression provides req (I5; Phase 8 fills in the property logic).
  • search/bnb.rs: branch-and-bound — pass the parent's remaining cost budget down as bound; abandon any expr whose lower bound (Phase 3) ≥ bound (I8). (Graefe 1995; I8)

5.3 Deliverable

cli optimize query.sql runs the full Cascades search (with the minimal rule set) and emits the chosen physical plan + the memo dump (--dump-memo) + the optimizer trace (--trace). For simple queries the plan is optimal; for joins it's whatever the trivial enumeration gives (Phase 6 adds real join rules).

5.4 Acceptance Criteria

  • The memo dedups: a query with a shared subexpression has one group for it (I2/I3 audit — no duplicate groups, no duplicate group-exprs).
  • Winners are minimal: re-deriving the winner from the group's costed physical exprs matches the stored winner (I10).
  • Branch-and-bound prunes: with pruning on, the result equals the exhaustive result on small queries (proves admissibility, I8), but visits fewer group expressions (measurable).
  • The budget guard returns a best-so-far plan + budget_exceeded flag when the step budget is artificially lowered (I7) — never hangs.
  • The search is deterministic: same query twice → identical memo + plan + trace (I9).

5.5 Conformance Fixtures

memo/dedup-shared-subexpr (I2/I3), memo/winner-minimal (I10), search/bnb-equals-exhaustive (I8), search/bnb-prunes (fewer exprs), search/budget-best-so-far (I7), search/deterministic-replay (I9), search/single-op-optimal.

5.6 Pitfalls

  • Group-merge cycles — merging group A into B while B references A creates a cycle → infinite loop. Detect + break cycles in merge_groups (I2); a group expression must never reference its own group (no self-recursion in the DAG).
  • Re-optimizing a group from scratch per required-property set — correct but wasteful; memoize per RequiredProps, and reuse the explored logical expressions across property requirements (only the physical winner differs).
  • Inadmissible bound prunes the optimum — the bound carried down must be a true upper bound on what's acceptable, and the lower bound used to prune must never over-estimate (I8). A single inadmissible bound silently loses the best plan — caught only by the bnb-equals-exhaustive fixture.
  • Fingerprint collisions / weak fingerprints — two different group expressions hashing equal → incorrect dedup → lost alternatives. The fingerprint must be a complete structural key (op + ordered child group ids + op params), not a lossy hash.
  • Cost double-counting in OptimizeInputs — accumulating a child's full subtree cost more than once inflates the parent → wrong winner. Accumulate each child's winning cost exactly once.

5.7 Performance Concerns

The memo is the optimizer's working set — keep GroupExpr small (op enum + a SmallVec of child ids, no heap for the common ≤4-child case). The fingerprint hash map is hot (every insert probes it) — fast hasher, salted (I9). The task stack churns — reuse task allocations (a free-list). Branch-and-bound is the primary perf win — a good initial bound (from a quick greedy plan) prunes aggressively. Cardinality is cached per group (logical property), not recomputed per task.

5.8 Edge Cases

A single-table query (one group, one scan implementation — the search must still produce it); a query where the root required-props are empty (no order/distribution needed — no enforcer); a group with no satisfying physical expr for a required order (must insert an enforcer, I5); a budget of 0 (return immediately with a heuristic plan + flag); a self-join (two scans of the same table — distinct groups, same table id).

5.9 Failure Analysis

A memo bug (bad dedup, bad merge) loses plan alternatives → sub-optimal plans (not wrong results — the chosen plan is still semantically correct, just not the cheapest). Blast radius: plan quality. A bnb-admissibility bug loses the optimal plan specifically. Detection: bnb-equals-exhaustive (I8) + winner-minimal (I10) + the dedup audit (I2/I3) in paranoid mode. Recovery: disable pruning (correct but slower); rebuild the memo. Forensics: --dump-memo shows every group + group-expr + winner; --trace shows the task sequence + every pruning decision — the primary debugging tool for "why did it pick this plan?"

5.10 Operational Notes

Stats: groups, group_exprs, memo_bytes, tasks_executed, bnb_pruned, winners_updated, merges. --dump-memo, --trace, --no-prune, --budget-steps N. The memo dump + trace are the optimizer's equivalent of a core dump — every bad-plan investigation starts there (runbooks/bad-plan.md). Memo size is the memory scaling axis (see Scalability Analysis) — monitor memo_bytes vs relation count.

Phase 6 — Transformation + Implementation Rules

6.1 Objectives

Grow the rule set into a real optimizer: the transformation rules that generate the plan space (join commutativity + associativity, predicate placement) and the implementation rules that produce costable physical operators (Join→Hash/Merge/NestedLoop, Scan→Seq/Index/IndexOnly, Aggregate→Hash/Sort, etc.). Now the search explores a meaningful space and the cost model picks among genuine alternatives.

6.2 Detailed Implementation Steps

  • rules/transform/:
    • Join commutativity (A⋈B ≡ B⋈A) — generates the build/probe-side choice; dedup so commute(commute) terminates (I4). (Selinger et al. 1979; I4)
    • Join associativity ((A⋈B)⋈C ≡ A⋈(B⋈C)) — generates join orders; the predicate moves with the relations it references (and only fires where it doesn't introduce a cross product, deferring full enumeration to Phase 9's DPccp).
    • Predicate placement (push a residual filter onto whichever join can evaluate it) — the cost-based counterpart to Phase 4's heuristic pushdown.
    • Aggregate transformations (push an aggregate below a join where a foreign-key relationship makes it valid — "eager aggregation").
  • rules/implement/: (Graefe 1995; ADR-06)
    • Scan → SeqScan (always) | IndexScan (for each applicable index whose key prefix matches a predicate/order) | IndexOnlyScan (covering index).
    • Join → HashJoin (equi-join; build the estimated-smaller side) | MergeJoin (equi-join; requires/provides sorted inputs — interacts with Phase 8) | NestedLoop (any join condition; index-NL when the inner has a usable index).
    • Aggregate → HashAgg (no order requirement) | SortAgg (requires sorted input on group keys — provides the grouped order).
    • Sort → PhysSort (an enforcer, but also a direct implementation of an explicit ORDER BY).
    • SetOp/Window/Limit → their physical counterparts.
  • rules/matcher.rs: the pattern matcher — match a rule's Pattern (operator shape + child patterns) against a group expression, binding the matched sub-plans for apply().
  • Each rule's apply() inserts results into the memo (Phase 5) and must preserve semantics (I1).

6.3 Deliverable

cli optimize now produces real, cost-driven physical plans: join order flips to build on the smaller side, index scans appear where selective, hash vs merge vs nested-loop is chosen by cost. The §8.7 worked example produces the expected hash-join-with-index-build plan.

6.4 Acceptance Criteria

  • Implementation rules cover every logical operator (a logical op with no implementation rule is a compile-time-checked gap — exhaustive match).
  • The §8.7/§8.8 worked examples produce the documented physical plans (index build on the small side; merge join reusing index order).
  • Transformation rules terminate (join commute/associate dedup, I4) — fixpoint reached on all fixtures.
  • Every rule preserves semantics: the differential check (I1) passes on equiv/ for plans the rules produce.
  • Operator choice is cost-driven: lowering the memory budget flips a hash join to a sort-merge / nested-loop where appropriate (a fixture proves cost sensitivity).

6.5 Conformance Fixtures

rules/join-commute-buildside, rules/join-associate-terminates (I4), rules/scan-to-index, rules/scan-index-only, rules/join-to-hash, rules/join-to-merge, rules/join-to-nestedloop-index, rules/agg-hash-vs-sort, rules/eager-aggregation, rules/operator-coverage (every logical op implementable), rules/cost-flips-operator (budget-driven).

6.6 Pitfalls

  • Join associativity without cross-product control — naive associativity generates cross products (joining unrelated relations) → an explosion of useless group expressions. Guard: only associate where a join predicate connects the regrouped relations (full control comes from DPccp in Phase 9).
  • Firing transformation rules on physical expressions — a physical op must never be transformed logically (P4); the matcher must only match transformation rules against logical group expressions. Violation → meaningless rewrites + non-termination.
  • Index-scan rule matching the wrong key prefix — an index on (a,b) helps a predicate on a (and a then b), but not a predicate on b alone. The applicability check must respect the index key order.
  • Merge-join without enforcing/checking the sort — emitting a merge join whose inputs aren't actually sorted on the join keys → wrong results (a merge join requires sorted input, I5/I14). Phase 8 wires the property requirement; until then, merge join must require + verify the order.
  • Build-side chosen by true cardinality the optimizer doesn't have — the build-side choice uses the estimate (Phase 2); a bad estimate builds the wrong (larger) side. This is where estimation error becomes a concrete bad operator choice — the link to the q-error story.

6.7 Performance Concerns

Rule application dominates search time — the matcher must be fast (index group expressions by root operator so a rule only tries matching candidates). The number of group expressions grows with the rules; branch-and-bound (Phase 5) is what keeps it tractable. Transformation rules multiply the logical space; implementation rules multiply the physical space per logical expr — both bounded by dedup (I3) + pruning (I8). Eager aggregation can help or hurt — gate it behind a cost comparison, not always-fire.

6.8 Edge Cases

A join with no equi-condition (only </> — hash + merge don't apply; nested-loop only); a join where one side is a single row (nested-loop or broadcast is cheap); an aggregate with no group-by (a single global aggregate — HashAgg with one group); an index that exactly covers the query (IndexOnlyScan, no heap fetch); a Scan with no applicable index (SeqScan only); a self-join via two index scans of the same table.

6.9 Failure Analysis

An implementation-rule bug that emits a physically-invalid operator (merge join on unsorted input) is a correctness bug (wrong results, I5/I14) — the worst kind. A transformation-rule bug (non-termination, cross-product explosion) is an availability bug (hang/OOM). Detection: I1 differential on rule outputs; I4 termination check; the property-satisfaction audit (I5, Phase 8). Recovery: disable the rule; the per-rule fixtures localize it. Forensics: --trace shows which rule produced the offending group expression.

6.10 Operational Notes

Stats: rule_firings (per transformation/implementation rule), physical_exprs_generated, operator_choices (hash/merge/nl counts). --disable-rule, --trace. Each implementation rule documents its applicability conditions (equi-join for hash/merge, index-prefix match for index scan) in its ADR. The operator-choice histogram is a useful health signal — a sudden swing to nested-loop joins often signals an estimation regression (small estimates make NL look cheap).

Phase 7 — Logical Property Inference (keys, FDs, not-null) at Scale

7.1 Objectives

Make ir/props.rs derivation complete + correct across the full operator set and use it in the search: keys/functional-dependencies/not-null/max-cardinality drive join-cardinality refinement (key joins), redundant-operator elimination, and decorrelation soundness. These are logical properties (shared by all group expressions in a group, I11) and a prerequisite for accurate estimation + safe rewrites.

7.2 Detailed Implementation Steps

  • Key derivation per operator: Scan → declared PK/unique keys; Join → keys depend on join type + which side's key the equality covers (a join on B's key preserves A's keys); Aggregate → the group columns form a key on the output; Project → keys survive if their columns survive; Filter → keys preserved (+ equality on a column to a constant makes the rest a key); Limit n=1 → everything is a (degenerate) key. (P2; I11)
  • FD derivation: declared FDs from the catalog; a=const predicate → {}→a (a becomes constant); a=b join/predicate → a↔b (equivalence); FDs propagate through projections + joins; transitivity computed (closure). (P6; ADR-13)
  • Not-null derivation: declared NOT-NULL; a IS NOT NULL filter → a not-null; inner-join keys are not-null on both sides; outer-join null-extends the inner side (those columns become nullable).
  • max_card derivation: Limit n → max_card = n; equality on a unique key → max_card = 1; Aggregate with no group → max_card = 1.
  • Wire into estimation (join_card uses keys: a join on a unique key bounds the result to the other side's cardinality) + rewrites (redundant DISTINCT/Sort over a key; I11).

7.3 Deliverable

cli explain --props query.sql annotates each operator with its derived keys/FDs/not-null/max_card. Key-aware join cardinality + redundant-operator elimination demonstrably improve plans (a DISTINCT over a primary key is eliminated; a PK-FK join's cardinality is bounded correctly).

7.4 Acceptance Criteria

  • Property derivation correct on fixtures across all operators (I11 audit: properties consistent across a group's expressions).
  • Key-join cardinality: a join on a unique key estimates ≤ the non-key side's cardinality (not the independence-formula product) — measurably tighter q-error on PK-FK joins.
  • Redundant-operator elimination fires correctly (DISTINCT-over-key, Sort-under-order-insensitive-parent) and only when sound.
  • Outer-join nullability correct: columns from the null-extended side are marked nullable (prevents an unsound predicate pushdown, links I1/I15).
  • FD transitivity closure is correct + terminating.

7.5 Conformance Fixtures

props/key-from-pk, props/key-from-aggregate, props/key-through-join, props/fd-from-equality, props/fd-transitive-closure, props/notnull-from-filter, props/notnull-outerjoin-extends, props/maxcard-from-limit, props/maxcard-key-equality, props/distinct-over-key-eliminated (I11), props/keyjoin-card-bounded.

7.6 Pitfalls

  • Claiming a key survives a join when it doesn't — A⋈B preserves A's key only if the join is on B's key (else a row of A can match many rows of B, breaking A's uniqueness). Over-claiming a key → under-estimated cardinality → bad plan. Derive key survival from the join type + the equality coverage precisely.
  • Forgetting outer-join nullability — treating the null-extended side's columns as not-null → an unsound predicate pushdown (the I1/I15 trap, again). Outer joins add nullability; derive it.
  • FD closure non-termination / blow-up — the transitive closure of FDs can be expensive; compute it once per group, cache it, dedup.
  • Redundant elimination that isn't — eliminating a Sort that a downstream merge-join actually requires, or a DISTINCT over a non-key → wrong results. Eliminate only with a proven key/order property (I11).
  • max_card ignored — a Limit 1 makes the output a single row; downstream estimation + operator choice should exploit it (a nested-loop with a single-row outer is trivial). Forgetting it leaves easy wins on the table.

7.7 Performance Concerns

Property derivation is O(plan size) and cached per group (a logical property, computed once, I11) — never recomputed per group expression. FD closure is the potentially-expensive part — bound the FD count, compute closure incrementally. Key sets are small (usually 1–2 columns) — represent as bitsets over column ids.

7.8 Edge Cases

A table with no declared key (no key property — all cardinality estimates use the general formula); a composite key (multi-column key set); a join on a prefix of a composite key (key not fully covered — doesn't survive); an aggregate grouping by an already-unique key (output = input cardinality); a UNION (keys generally don't survive — duplicates eliminated changes cardinality; UNION ALL preserves nothing); a constant column from a=5 (functionally determined by nothing).

7.9 Failure Analysis

An over-claimed key/FD → under-estimated cardinality → a plan sized for far fewer rows than reality (a hash build that OOMs). This is a plan-quality failure that manifests like a correctness/resource failure (the executor spills/OOMs). Detection: the I11 audit + q-error monitoring (a key-join whose estimate is suspiciously low). A redundant-elimination bug is a correctness failure (I1) — caught by the differential harness. Recovery: disable the suspect derivation; the per-property fixtures localize it. Forensics: --props shows the derived properties; cross-check against the catalog's declared constraints.

7.10 Operational Notes

Stats: keys_derived, fds_derived, notnull_derived, redundant_ops_eliminated, keyjoin_bounded_count. --props. Logical properties depend on catalog-declared constraints — a missing PK/unique/NOT-NULL declaration in the catalog leaves cardinality estimation blind to a real key relationship (a common cause of over-estimation; the fix is a DDL/catalog change, not an optimizer change — document in runbooks/bad-plan.md).

Phase 8 — Physical Properties + Enforcers (interesting orders, distribution)

8.1 Objectives

Build props/: the physical-property model (interesting orders + distribution), provided-property derivation, required-property propagation, and enforcer insertion (Sort/Exchange). This turns the search from "find the cheapest operator tree" into "find the cheapest tree that satisfies the required properties" — the System-R interesting-orders insight (Selinger 1979) generalized to Cascades. Required for merge-join reuse, sort-aggregate, ORDER BY satisfaction, and the distributed exchange stub.

8.2 Detailed Implementation Steps

  • props/order.rs: an interesting order is a column list (with asc/desc + nulls placement); order satisfaction (provided satisfies required if required is a prefix of provided); the set of interesting orders for a query = the orders required by ORDER BY, merge joins, and sort aggregates. (Selinger et al. 1979; ADR-14)
  • props/distribution.rs: partitioning descriptors — Single (single-node default), Hash([cols]), Range, Broadcast, Replicated. Satisfaction rules (a hash-partition on the join keys satisfies a hash-join's distribution requirement). (Distributed search is the #316 stub; the model exists now.)
  • props/derive.rs: provided-property derivation per physical operator — IndexScan provides the index's order; MergeJoin provides the merged order; HashJoin provides no order; SortAgg provides the group order; PhysSort provides its sort order; an order is preserved through order-insensitive operators (Filter, some Projects) (I14).
  • props/derive.rs (requirement propagation): a parent's required properties propagate to its inputs — MergeJoin requires both inputs sorted on the join keys; SortAgg requires the input sorted on the group keys; the root requires the ORDER BY order. Requirements flow top-down (the req in the Cascades tasks).
  • props/enforcer.rs: when no group expression in a group provides a required property, the EnforceProps task inserts an enforcer — PhysSort for an order, Exchange for a distribution (I5). The enforcer's cost (Phase 3) is weighed against alternatives that provide the property natively. (Graefe 1995; I5)
  • Wire into the search: OptimizeGroup(g, req) now optimizes per required-property set; the winner map is keyed by RequiredProps (Phase 5's Winner map realized).

8.3 Deliverable

cli optimize now reuses orders: the §8.8 example chooses a merge join over index scans (no Sort enforcer) when that's cheaper than a hash join + sort. --explain shows provided/required properties per operator and where enforcers were inserted.

8.4 Acceptance Criteria

  • Required physical properties are always satisfied in the final plan (I5 audit — every operator's input properties meet its requirements, directly or via an enforcer).
  • Order reuse works: the §8.8 merge-join-over-index plan beats hash-join-plus-sort when the indexes provide the order (a fixture proves the enforcer is not inserted).
  • Sort enforcers appear only where needed (no redundant sort over already-sorted input — I14: order preserved through order-insensitive operators is recognized).
  • Interesting orders are correctly identified (ORDER BY, merge-join keys, sort-agg keys) and propagated.
  • The distribution model + Exchange enforcer are exercised by the distributed stub fixtures (the model works even though full distributed enumeration is deferred, #316).

8.5 Conformance Fixtures

props/order-satisfies-prefix, props/indexscan-provides-order, props/mergejoin-reuses-order (no enforcer, §8.8), props/sort-enforcer-inserted (I5), props/order-preserved-through-filter (I14), props/sortagg-requires-order, props/orderby-root-requirement, props/distribution-hash-satisfies, props/exchange-enforcer-stub, props/no-redundant-sort (I14).

8.6 Pitfalls

  • Order satisfaction with the wrong prefix semantics — provided=(a,b) satisfies required=(a) (prefix) but not required=(b) or required=(a,b,c). Get the prefix direction right (provided must be at least as specific, in order). A wrong check inserts unnecessary sorts or, worse, runs a merge join on the wrong order → wrong results.
  • Forgetting to mark an order as preserved through an order-insensitive operator (a Filter doesn't reorder rows) → a redundant Sort enforcer above it (I14). Conversely, marking an order-destroying operator (HashJoin, HashAgg) as order-preserving → a merge join fed unsorted input → wrong results.
  • Optimizing a group once for "no order" then reusing it for "ordered" — the no-order winner may not provide the order; each required-property set needs its own winner (the per-RequiredProps winner map, Phase 5). A shared winner across incompatible requirements is a correctness bug (I5).
  • Enforcer cost not weighed — always inserting a Sort (instead of considering an index scan that provides the order) → missing the merge-join-reuse win. The enforcer is a costed alternative, not a mandatory wrapper.
  • Nulls-placement in orders ignored — ORDER BY x NULLS FIRST vs NULLS LAST are different orders; an index providing one doesn't satisfy the other. Track nulls placement + asc/desc in the order descriptor.

8.7 Performance Concerns

The number of distinct required-property sets multiplies the group's winner entries — but real queries have few interesting orders (the ORDER BY + a handful of join keys), so it's bounded. Property derivation + satisfaction checks are in the inner loop — represent orders as interned, comparable descriptors (cheap prefix check). The enforcer-vs-native tradeoff is the expensive search decision — branch-and-bound prunes the dominated branch.

8.8 Edge Cases

A query with no order requirement anywhere (no interesting orders — the property dimension is trivial); an ORDER BY on an expression (not a bare column — an index can't provide it unless it's an expression index); a merge join whose keys are a subset of an index's order (prefix satisfies); a sort over an empty interesting-order set (no-op); a distribution requirement on a single-node plan (always satisfied by Single — the Exchange stub is a no-op cost); an order and a distribution both required (the property is a tuple — both must be satisfied).

8.9 Failure Analysis

A property bug splits into two severities. Marking a non-preserving operator as preserving (or a wrong satisfaction check) → a merge join on unsorted input → wrong results (I5/I14, the worst). Forgetting a preservation / always-enforcing → redundant sorts → slower-but-correct plans. Detection: the I5 property-satisfaction audit on the final plan + the I14 order-preservation audit + the differential harness (I1) catches the wrong-result variant. Recovery: the per-property fixtures localize the bad derivation. Forensics: --explain shows provided/required properties at every node + every enforcer — the property mismatch is visible in the plan annotation.

8.10 Operational Notes

Stats: interesting_orders, enforcers_inserted (sort/exchange), order_reuse_count (enforcers avoided), winners_per_group. --explain (property-annotated). Property enforcement is where "sort once, reuse everywhere" lives — the order_reuse_count metric quantifies the optimizer's sophistication. A drop in order reuse (suddenly inserting sorts that were previously avoided) signals a regression in provided-property derivation.

Phase 9 — Join Enumeration (DPccp/DPhyp + greedy + GEQO)

9.1 Objectives

Build enumerate/: principled join-order enumeration. Extract the join hypergraph, enumerate connected, cross-product-free subgraphs via DPccp/DPhyp (provably optimal join order over the connected space, for ≤12 relations), and fall back to greedy + a GEQO-style genetic/randomized search past the relation-count threshold. This replaces Phase 6's ad-hoc associativity with a complete, bounded enumeration — the combinatorial heart of the optimizer.

9.2 Detailed Implementation Steps

  • enumerate/join_graph.rs: build the join hypergraph from the (rewritten, Phase 4) plan — relations are nodes, join predicates are (hyper)edges (binary edges for two-relation predicates, hyperedges for predicates spanning >2 relations). Detect disconnected components (would require a cross product).
  • enumerate/dpccp.rs: the DPccp algorithm (Moerkotte-Neumann) — enumerate csg (connected subgraphs) and their cmp (complementary connected subgraphs) in a specific order so each pair (S1, S2) of a valid join is generated exactly once, building the DP table bestPlan(S) bottom-up over connected subsets; generalize to DPhyp for hyperedges. Cross-product-free by construction (only connected subgraphs). Feed each enumerated join into the memo as a group expression (integrates with Cascades — DPccp is the join-enumeration rule). (Moerkotte & Neumann 2006; ADR-07)
  • enumerate/greedy.rs: greedy join ordering (repeatedly join the pair with the cheapest/smallest result) — O(n²) per step, for 13–~30 relations.
  • enumerate/geqo.rs: a genetic/randomized search (GEQO-style) — encode a join order as a chromosome, evolve via crossover/mutation, evaluate by cost; seeded for determinism (P9/I9). For very large relation counts (>~30) where even greedy's space is large. (PostgreSQL GEQO; I9)
  • Threshold logic: ≤12 relations → exact DPccp; 13–N → greedy (or greedy-seeded GEQO); flag which method was used.
  • Control the search space: left-deep (restrict cmp to single relations) | zig-zag | bushy (full DPccp) — a knob; bushy is the default for the optimal-quality range.

9.3 Deliverable

cli optimize produces optimal join orders for ≤12-relation queries (verified against exhaustive on small cases) and good orders for larger ones via greedy/GEQO. --explain + --trace show the enumerated join order + which method was used; --join-method dpccp|greedy|geqo forces one.

9.4 Acceptance Criteria

  • DPccp produces the optimal join order on ≤12-relation fixtures (matches exhaustive enumeration's best cost, given the same cost/cardinality).
  • No cross products are introduced unless the join graph is genuinely disconnected (a fixture with a connected graph never produces a cross product).
  • DPccp generates each (S1,S2) join pair exactly once (the enumeration-correctness property — no duplicate work, the whole point of DPccp over DPsub).
  • Greedy + GEQO produce valid (correct, if sub-optimal) plans past the threshold; GEQO is deterministic for a fixed seed (I9).
  • On JOB (real, up-to-~17-relation queries), the chosen plan is ≤1.3× the cost of the best plan found by exhaustive-where-feasible / a reference optimizer (§4 quality gate).

9.5 Conformance Fixtures

enumerate/dpccp-optimal-small (vs exhaustive), enumerate/dpccp-no-crossproduct, enumerate/dpccp-pair-once (enumeration correctness), enumerate/dphyp-hyperedge, enumerate/disconnected-graph (cross product only here), enumerate/greedy-valid, enumerate/geqo-deterministic (I9), enumerate/left-deep-vs-bushy, enumerate/job-quality (≤1.3× gate), enumerate/threshold-switch.

9.6 Pitfalls

  • Generating cross products in enumeration — including disconnected subgraphs explodes the space with useless plans (and produces terrible cross-product plans). DPccp's connectedness is the guard — only connected subgraphs are enumerated. A bug that loses connectedness re-introduces the explosion.
  • Enumerating each join pair more than once — DPsub (the naive subset DP) generates (S1,S2) and (S2,S1) and re-derives subsets redundantly; DPccp's csg-cmp enumeration order generates each exactly once. Getting the enumeration order wrong → exponential redundant work (the optimizer crawls on 10 relations).
  • The 2ⁿ DP table on too many relations — DPccp is still exponential in the worst case (a clique join graph); blindly running it on 20 relations exhausts memory. The threshold + greedy/GEQO fallback is mandatory (I7).
  • GEQO non-determinism — an unseeded genetic search gives different plans run-to-run → un-reproducible (I9). Seed the PRNG; the seed is part of the optimizer's deterministic input.
  • Bushy vs left-deep confusion — left-deep restricts one join input to a single base relation (smaller space, index-NL-friendly); bushy allows joining two intermediate results (larger space, better for star/snowflake schemas). Defaulting to left-deep silently caps quality on bushy-favoring queries; defaulting to bushy blows up the space on large queries. The knob must be explicit + the default justified.

9.7 Performance Concerns

DPccp's complexity is O(3ⁿ) in the worst case (clique) but far better on sparse (chain/star) graphs — the graph topology, not just n, determines feasibility. The csg-cmp enumeration must be tight (bit-manipulation over relation subsets, Gray-code-style iteration). The DP table is keyed by relation-subset bitmask — a dense array indexed by the bitmask for small n, a hash map for sparse large n. Memoize bestPlan(S) — it's the DP. Integrate with the Cascades memo so a join subexpression is shared (a group per connected subset).

9.8 Edge Cases

A two-relation query (trivial — one join, commute for build side); a star schema (one fact, many dimensions — DPccp handles it; left-deep is often fine); a chain query (A⋈B⋈C⋈D with only adjacent predicates — sparse graph, DPccp is cheap); a clique (every pair joins — the 3ⁿ worst case, threshold likely triggers); a single relation (no join — no enumeration); a query already past the threshold (greedy/GEQO immediately, flagged).

9.9 Failure Analysis

An enumeration bug splits by type. Losing connectedness / pair-once → an availability failure (explosion → budget hit → degraded plan via fallback, I7). Producing an invalid join order (a join missing a required relation) → a correctness failure — but the memo + property machinery (a join's output schema is checked) catches it. Detection: the dpccp-optimal-small + pair-once + no-crossproduct fixtures; the budget guard (I7) contains the explosion. Recovery: force greedy (--join-method greedy) — always produces a valid plan. Forensics: --trace logs the enumerated subsets + the chosen order; the join graph is dumpable. Deferred: full distributed join enumeration (broadcast vs repartition costing per join) — PhaseDeferred("Deferred Features Register"); deferred: multi-query / shared-join enumeration across statements — PhaseDeferred("Deferred Features Register").

9.10 Operational Notes

Stats: relations, join_method (dpccp/greedy/geqo), csg_enumerated, dp_table_size, geqo_generations, enumeration_ms, crossproducts_introduced. --join-method, --join-space left-deep|bushy, --dp-threshold N, --geqo-seed. The relation count + join-graph topology determine the method; a query that unexpectedly falls back to GEQO (and thus gives a non-optimal plan) is worth flagging to the user (geqo_used in EXPLAIN). The DP-vs-greedy threshold is the central plan-quality-vs-optimization-time knob (see Scalability Analysis).

Phase 10 — Correlation Handling + Estimator Hardening

10.1 Objectives

Attack the q-error explosion: extended (multi-column) statistics, correlation correction for conjunctions, join-cardinality damping, sampling for hard predicates, and error-bounding. This is where the optimizer stops being naive about the independence assumption — the difference between a textbook optimizer and one that survives real (correlated) data (JOB).

10.2 Detailed Implementation Steps

  • estimate/correlation.rs: when a conjunction's columns appear in an ExtendedStats group, use the joint MCV / joint NDV / soft-FD-adjusted estimate instead of the independent product. Soft FDs (city→state with degree 0.95) damp the over-multiplication: sel(city ∧ state) ≈ sel(city) when state is ~determined by city. (Leis et al. 2015; ADR-13)
  • estimate/join_card.rs (hardening): damped join cardinality for many-to-many joins (the pure containment formula under-estimates); use the larger of the two NDV-based estimates + a damping factor for chained joins; key/FD-awareness (Phase 7) bounds key joins exactly.
  • estimate/sampling.rs: index-based / table-sample join sampling for predicates + joins stats can't handle — execute on a sample, scale up with confidence intervals (Leis et al. 2017). (Leis et al. CIDR 2017; P7)
  • estimate/propagate.rs (hardening): clamp + bound the cumulative q-error; when confidence is low (missing/stale stats, correlated columns without extended stats), widen the estimate + flag — and optionally bias the cost model toward robust plans (plans whose cost is less sensitive to the uncertain estimate).
  • stats/analyze.rs (extension): auto-detect candidate column groups for extended stats (columns frequently co-occurring in predicates) and build them.
  • Document the limits honestly: classical estimation cannot fully solve correlation; this phase damps the worst cases and leaves the CardinalityEstimator trait seam for learned models.

10.3 Deliverable

cli optimize on JOB queries produces dramatically better plans than the Phase-2 independence-only estimator; --card-report shows the q-error reduction from extended stats. The estimator trait remains swappable.

10.4 Acceptance Criteria

  • On JOB (correlated): per-operator q-error ≤ 4 with extended stats vs the much-larger independence-only q-error (the before/after is the headline result — quantified in quality.report.json).
  • Correlation correction fires: a city='SF' AND state='CA' conjunction estimates ≈ sel(city) (not the tiny independent product) when the soft FD exists.
  • Sampling fallback produces estimates within its confidence interval on fixtures with complex predicates.
  • Low-confidence estimates are flagged; the robust-plan bias (when enabled) measurably reduces worst-case plan cost on uncertain queries.
  • All estimates remain finite, ≥0, deterministic (I6/I9) — hardening doesn't break the safety invariants.

10.5 Conformance Fixtures

estimate/correlation-mcv-conjunction, estimate/soft-fd-damping, estimate/manytomany-join-damped, estimate/sampling-confidence, estimate/low-confidence-flag, estimate/robust-plan-bias, estimate/job-qerror-improvement (before/after extended stats), estimate/auto-extended-stats.

10.6 Pitfalls

  • Trusting extended stats that are stale/sampled — joint NDV from a small sample is even less reliable than single-column NDV. The same staleness/sampling caveats apply, amplified.
  • Over-damping — assuming correlation where there is none (a spurious soft FD) over-estimates a conjunction → the opposite error. Soft FDs need a confidence degree, and the correction is proportional to it.
  • Join-cardinality damping that breaks key joins — the damping factor for many-to-many joins must not apply to key joins (those are bounded exactly by Phase 7). Apply damping only where no key relationship exists.
  • Sampling cost in the inner loop — sampling executes a predicate on real data; it's far more expensive than a histogram lookup. Use it once per base predicate (cache the result), never per group expression in the search loop.
  • False confidence — reporting a tight estimate when the underlying assumptions are shaky is worse than a wide estimate with a low-confidence flag. The honest move is to propagate uncertainty, not hide it.

10.7 Performance Concerns

Extended-stats lookup is a hash probe on the column group — cheap, but building them at ANALYZE time is combinatorial (only build requested/auto-detected groups). Sampling is expensive (real data access) — strictly a fallback, cached. The robust-plan bias requires costing under a range of cardinalities (best/expected/worst) — more cost evaluations; gate it behind a flag for queries flagged low-confidence, not always.

10.8 Edge Cases

A conjunction whose columns span an extended-stats group and columns outside it (mix joint + independent); a soft FD with degree exactly 0 (no correlation — falls back to independence) or 1 (full determination — sel(a∧b)=sel(a)); a join where both sides have low NDV (the containment formula is unreliable — sample or damp); a predicate too complex for stats and too expensive to sample (fall back to a magic constant, flag low confidence).

10.9 Failure Analysis

An estimation-hardening bug skews plans on the correlated queries it targets. Blast radius: plan quality on real (correlated) workloads — exactly the queries that matter most. Detection: the JOB q-error report regresses; the before/after fixtures quantify the extended-stats contribution. Recovery: the estimator is swappable (trait); a regression isolates to correlation/sampling/damping via the fixtures; the classical Phase-2 estimator is the fallback. Forensics: --card-report per operator + the confidence flags pinpoint which estimate (and which assumption) misled the plan. Deferred: a learned/ML cardinality estimator behind the CardinalityEstimator trait — PhaseDeferred("Deferred Features Register") (the seam exists; training a model is out of Phase-0 scope).

10.10 Operational Notes

Phase 11 — Full Integration, EXPLAIN, and the Optimizer API

11.1 Objectives

Assemble the end-to-end optimizer (bind/rewrite → memo+search → enumerate → props → estimate+cost → physical plan), finalize the EXPLAIN surface (plan tree, memo dump, cardinality report, cost breakdown, optimizer trace), the liboptd API, and plan diffing. This is the phase that makes it a usable, embeddable optimizer with the observability (P14) a hard-to-debug component demands.

11.2 Detailed Implementation Steps

  • search/scheduler.rs (integration): the top-level optimize(root, req) — rewrite to fixpoint (Phase 4), seed the memo with the normalized plan, run the Cascades search with DPccp join enumeration (Phase 9) + property enforcement (Phase 8) + cost-based pruning (Phase 5), extract the winning physical plan for the root's required properties (I1/I5/I7). (Graefe 1995; I1/I7)
  • explain/plan_fmt.rs: the physical-plan text tree (PostgreSQL-style — operator, estimated rows, estimated cost, properties) + a JSON form (ADR-21).
  • explain/card_report.rs: estimated-vs-true cardinality + per-operator + cumulative q-error (EXPLAIN ANALYZE mode, when true counts are supplied).
  • explain/memo_dump.rs: the full memo (groups, group expressions, winners per required-props) — the debugging core dump.
  • explain/trace.rs: the optimizer trace — every task, rule firing, group creation, winner update, and pruning decision, in order (gated; off by default for perf). (P14; ADR-22)
  • Plan diffing: compare two plans (e.g. with/without a rule, across stats versions) and highlight the structural + cost differences — the regression-investigation tool.
  • liboptd API: the Optimizer struct + optimize() + the CardinalityEstimator/CostModel/Rule traits as the stable public contract (SemVer).

11.3 Deliverable

cli optimize query.sql --explain [analyze] [--dump-memo] [--trace] is the complete tool: a query in, a costed physical plan + full diagnostics out. liboptd is embeddable (a fixture host program optimizes a plan via the API). cli diff plan_a plan_b shows plan differences.

11.4 Acceptance Criteria

  • End-to-end: the §8.7/§8.8/§8.9 worked examples produce the documented physical plans through the full pipeline (rewrite + search + enumeration + properties + cost).
  • Every output plan satisfies semantic preservation (I1) + required properties (I5) — the full conformance equiv/ corpus passes.
  • EXPLAIN shows rows/cost/properties per operator; EXPLAIN ANALYZE shows q-error; the memo dump + trace are complete + parseable.
  • The liboptd API optimizes a plan from an external host (the embedding seam works) — proves it's a library, not just a CLI.
  • Plan diffing correctly identifies the structural + cost delta between two plans of the same query.

11.5 Conformance Fixtures

integration/worked-example-a (§8.7), integration/worked-example-b (§8.8), integration/worked-example-c (§8.9), integration/equiv-corpus (I1), integration/props-satisfied (I5), explain/text-format, explain/json-format, explain/analyze-qerror, explain/memo-dump-complete, explain/trace-complete, api/embed-host, explain/plan-diff.

11.6 Pitfalls

  • The integrated pipeline order matters — rewrite before the memo is seeded (heuristic rewrites shouldn't fight the cost-based search); enumeration inside the search (as a rule), not as a separate pre-pass that the memo can't see. A wrong order (e.g. enumerating before rewriting prunes predicates) gives worse plans.
  • EXPLAIN showing estimated, not true, cardinality confuses users into thinking the estimate is reality. Label estimates as estimates; EXPLAIN ANALYZE (with true counts) is what reveals the q-error — make the distinction loud.
  • The trace overhead left on in production — logging every task/rule firing is expensive (allocations in the hot loop). Gate it off by default; the memo dump is on-demand.
  • API instability — exposing internal memo/GroupId types in the public API couples clients to internals. The public contract is optimize(LogicalPlan) → PhysicalPlan + the estimator/cost/rule traits; the memo is private.
  • Plan diff that's structural-only — two plans can be structurally identical but differ in cost (different stats); the diff must compare both structure and annotations.

11.7 Performance Concerns

The integrated path is the full optimization-time budget (§4: ≤10ms p50, ≤200ms p99 for 10 relations) — every phase's inner-loop cost compounds here. EXPLAIN formatting is off the hot path (post-optimization). The trace, when on, must use a pre-allocated ring buffer, not per-event allocation. The optimize() entry point should reuse the memo's allocations across queries where the API allows (a long-lived optimizer instance amortizes setup).

11.8 Edge Cases

A trivial single-table query (the full pipeline must still run + produce the obvious plan fast); a query the rewriter fully resolves (the search has nothing to choose — a degenerate but valid search); a query at the optimization-time budget (best-so-far + flag, surfaced in EXPLAIN); an EXPLAIN ANALYZE with no true counts supplied (q-error report shows estimates only, no error); a plan diff of identical plans (empty diff). Deferred: parallel-degree (DOP) optimization in the integrated plan — PhaseDeferred("Deferred Features Register").

11.9 Failure Analysis

An integration bug (wrong phase order, a dropped property requirement across the seam) can produce a wrong or sub-optimal plan that no single phase's tests catch — it's an interaction bug. Detection: the end-to-end worked examples + the full equiv/ + props-satisfied corpora are the integration tests (I1/I5); the memo dump + trace localize where the pipeline diverged. Recovery: bisect the pipeline (disable rewrite, disable enumeration, disable enforcement) to isolate the stage. Forensics: --trace is the integration-bug microscope — it shows the exact task sequence that produced the bad plan. This is the canonical place to start any "why this plan?" investigation (runbooks/bad-plan.md).

11.10 Operational Notes

Stats: optimize_ms (p50/p95/p99), pipeline_stage_ms (rewrite/search/enumerate/cost), plan_cost, budget_exceeded_count. --explain, --analyze, --dump-memo, --trace, diff. The full optimizer trace + memo dump are the single most important operational artifact — a bad-plan ticket is reproducible from (query + catalog + stats snapshot + seed) and debuggable from the dump. The liboptd API is the contract #21/#104/#207 depend on — SemVer-stable; additive trait methods via defaults.

Phase 12 — Conformance, Plan-Quality Gate, and Soak

12.1 Objectives

Stand up the conformance + plan-quality + soak infrastructure that gates the optimizer: the JOB + TPC-H + TPC-DS corpora, the semantic-preservation differential harness, the q-error tracking, the plan-quality regression gate, the property-fuzzer, and the soak run. This phase makes "the optimizer is correct + good" a continuously-verified, CI-gated property rather than a hope.

12.2 Detailed Implementation Steps

  • conformance/job/, tpch/, tpcds/: load the schemas + generate data + run the query suites; record the chosen plan + estimated/true cardinalities + cost.
  • The semantic-preservation harness: for each query, generate the unoptimized plan + the optimized plan, execute both against a reference (or a minimal embedded executor / a trusted external DB), and assert identical multisets (I1). The single most important test in the project. (I1; P1)
  • quality.report.json: plan cost vs the best-known plan (exhaustive where feasible, or a reference optimizer) per query — the plan-quality metric; the gate fails if a query family regresses beyond a threshold (e.g. >1.5× its baseline). (Leis et al. 2015; M3/M4)
  • The q-error report (conformance/report/): per-query + aggregate q-error, with/without extended stats — tracked over time as the estimation-health KPI.
  • The property fuzzer (fuzz/): generate random valid logical plans (random operators + valid schemas), optimize them, and assert (a) semantic preservation via differential execution (I1), (b) required-property satisfaction (I5), (c) determinism (I9). The highest-value fuzzing — it finds the wrong-plan bugs no fixture anticipated.
  • The binder fuzzer: random SQL-subset text → no panic/UB.
  • Soak: optimize the full corpus repeatedly under the time/step/memory budgets; assert no crash, no wrong plan, no budget violation, bounded memo memory.
  • tools/ddmin: a delta-debugger that minimizes a wrong/sub-optimal-plan-triggering query + its catalog/stats to a minimal reproducer (the regression-corpus feeder).

12.3 Deliverable

make conformance runs JOB + TPC-H + TPC-DS + the equivalence + property fuzzers and produces conformance.report.json + quality.report.json. make quality-gate fails CI on a plan-quality or q-error regression. The soak run is a CI/nightly job.

12.4 Acceptance Criteria

  • 100% of the conformance corpus passes semantic preservation (I1) — every optimized plan returns the same rows as the input (the non-negotiable gate).
  • Required properties satisfied on 100% of the corpus (I5); determinism holds on replay (I9).
  • Plan quality: TPC-H ≤1.1× / JOB ≤1.3× the best-known plan cost (§4); a regression beyond the per-family threshold fails quality-gate.
  • The property fuzzer runs the configured budget with zero semantic-preservation / property / determinism failures; the binder fuzzer survives with no panic/UB.
  • The soak run completes the full corpus N times with no crash, no wrong plan, bounded memo memory (I7), and the q-error within the documented bound.

12.5 Conformance Fixtures

conformance/job-suite, conformance/tpch-suite, conformance/tpcds-subset, conformance/equiv-differential (I1, the core gate), conformance/props-satisfied (I5), conformance/quality-baseline (per-family cost), conformance/qerror-tracking, fuzz/random-plan-equiv (I1), fuzz/random-plan-props (I5), fuzz/binder-noub, soak/corpus-repeat.

12.6 Pitfalls

  • A "conformance" suite that only checks the plan runs, not that it's correct — running without erroring is not correctness; the differential equivalence check (I1) against a reference is what catches wrong plans. Without it, an unsound rewrite ships green.
  • Plan-quality baselines that drift — without a fixed best-known baseline per query, "quality" is unmeasurable and regressions slip in. Pin the baselines (exhaustive-where-feasible costs); update them deliberately, with review.
  • The property fuzzer generating only valid-by-construction-trivial plans — a fuzzer that never generates outer joins / correlated subqueries / multi-column predicates misses exactly the bug-prone cases. Bias the generator toward the hard operators.
  • q-error tracked but not gated — measuring q-error without a CI gate lets estimation silently degrade. The median/p95 q-error per family should be a tracked, alerting metric.
  • Soak that doesn't vary inputs — re-optimizing the same query N times tests determinism but not coverage; soak should cycle the full corpus + fuzzer-generated plans under budgets.

12.7 Performance Concerns

The differential harness executes queries (expensive) — run it on a representative subset in PR CI, the full corpus nightly. The property fuzzer's bottleneck is execution (for the equivalence check) — use small synthetic tables so execution is fast, keeping the focus on the planner not the executor. The quality gate's exhaustive-baseline computation is itself exponential — precompute + cache the baselines, don't recompute per CI run.

12.8 Edge Cases

A query whose true cardinality is 0 (q-error undefined — handle the divide-by-zero in the report); a query the optimizer can't improve (optimized == input plan — still must pass equivalence); a fuzzer-generated plan that's a pure cross product (valid, just expensive — equivalence must still hold); a TPC-DS query past the relation threshold (GEQO path — quality measured against greedy/reference, not exhaustive); a query whose reference plan differs structurally but has equal cost (quality gate compares cost, not structure).

12.9 Failure Analysis

A conformance-infrastructure gap is a meta-failure — it lets real bugs ship. The defense-in-depth: I1 differential (wrong results), I5 property audit (invalid physical plans), the quality gate (regressions), the fuzzers (unanticipated cases), soak (resource + stability). A failure here means the gate is wrong, not the optimizer — fix the gate first. Detection: the gate's own meta-tests (inject a known-bad plan, assert the gate catches it). Recovery: every fuzzer-found bug → ddmin minimize → permanent regression fixture. Forensics: the failing query + its catalog/stats snapshot + the plan diff (vs the baseline) is the complete repro. Deferred: adaptive runtime re-optimization (re-plan from execution feedback) — PhaseDeferred("Deferred Features Register") (#318 owns the adaptive loop; this project ships the classical, statically-costed optimizer it's compared against).

12.10 Operational Notes

Stats: conformance_pass_rate, equiv_failures, quality_regressions, median_qerror, p95_qerror, fuzz_iterations, fuzz_failures, soak_iterations, max_memo_bytes. make conformance, make quality-gate, make soak. The quality.report.json trend over releases is the optimizer's report card — plan quality + q-error are the two numbers that matter. Every minimized bug query becomes a permanent fixture (the regression corpus only grows). This phase is what lets the team change a rule / a cost constant / an estimator with confidence — the gate catches the regression before users do.

Operational Readiness

The optimizer's "operations" are observability of the search + estimation, plan-quality monitoring, resource governance, and reproducibility (it is a library/CLI embedded in a DB, not a standalone service).

Counters + gauges: optimize_ms (p50/p95/p99), pipeline_stage_ms (rewrite/search/enumerate/cost/estimate), groups/group_exprs/memo_bytes, rule_firings (per rule), bnb_pruned, join_method, median_qerror/p95_qerror, low_confidence_plans, budget_exceeded_count, enforcers_inserted/order_reuse_count, plan_cost. JSON dump (--stats json).
  • Tracing. tracing spans per optimization, per pipeline stage, per task; the full optimizer trace (--trace) logs every rule firing / group creation / winner update / pruning decision. Gated off in the hot loop by default (perf).
  • Logging. Structured, leveled; never log inside the search inner loop at default level. The bound IR (--echo-bound), the normalized plan (--normalized), and the chosen plan are echoable for repro.
  • Dashboards. The two report cards: quality.report.json (plan cost vs best-known, per query family) and the q-error report (estimation accuracy, with/without extended stats). Plus optimization-latency percentiles + memo-memory + operator-choice histograms. A rising q-error or a quality regression is the leading indicator of user-visible bad plans.

Alert on plan-quality regression (a family exceeds its baseline threshold), q-error degradation (median/p95 rising), optimization-latency breaching the budget, and budget-exceeded rate climbing (signals queries outgrowing the DP threshold). Estimation degradation is the highest-value alert — it predicts bad plans before they hurt.

Compatibility & Versioning

  • Input IR: the LogicalPlan IR (operators + expression model + type system) is the stable input contract; new operators are additive (an unknown operator → clear error, never a silent mis-optimization). The SQL subset the binder accepts is documented + versioned; unsupported SQL → PhaseDeferred, never a wrong lowering.
  • Output IR: the PhysicalPlan IR (physical operators + annotations) is the stable output contract consumed by #104/#207; new physical operators are additive.
  • EXPLAIN format: the text + JSON EXPLAIN schema is versioned; the JSON form is the machine contract (additive fields only within a major version).
  • Stats catalog format: versioned serialized snapshots; a stats snapshot records its schema version + the catalog version it was built against (staleness + compatibility). An incompatible snapshot → rebuild, never silent misuse.
  • API (liboptd): SemVer; the Optimizer/CardinalityEstimator/CostModel/Rule traits are the stable public contract; additive trait methods via defaults. Internal types (memo, GroupId) are not part of the contract.
  • Determinism: for a fixed version + catalog + stats + seed, the chosen plan is reproducible across runs and platforms (modulo the documented float-determinism caveat — cost is f64; the same inputs produce the same plan, but cross-platform float bit-equality is documented, not guaranteed for the cost values, only for the plan choice which uses comparisons with a tolerance).
  • Estimator/rule extensibility: new estimators plug in via the CardinalityEstimator trait; new rules via the Rule trait — without changing the core (P4/P11/P18). A learned estimator (§10.9) is a drop-in.
  • Deprecation: flags/options + rules deprecated with one-minor-version warning before removal; a removed rule's behavior is documented in CHANGELOG.md (plan changes are user-visible).
  • Plan stability across versions: not guaranteed — a better cost model or estimator should change plans (that's improvement). Plan changes across versions are tracked in quality.report.json; a regression is gated, an improvement is expected. This is the deliberate non-guarantee: the optimizer is allowed to get smarter.

Testing & Verification Strategy

  • Unit: expression interning + 3-VL semantics; property derivation (keys/FDs/not-null); histogram construction + HLL accuracy; selectivity formulas (each form); cost formulas (each operator); the pattern matcher; DPccp enumeration correctness; order-satisfaction checks; memo dedup/merge.
  • Differential (the backbone): semantic preservation (I1) — optimized plan vs input plan executed against a reference, identical multisets, on the full equiv/ + conformance corpora; this is the test that catches wrong-result bugs and runs on every rewrite/rule in CI.
  • Property-based: selectivity ∈ [0,1] (I12); cardinality finite/≥0 (I6); required properties always satisfied (I5); orders preserved through order-insensitive operators (I14); rewrite fixpoint terminates (I4); DPccp generates each join pair exactly once; the chosen winner is minimal (I10).
  • Plan-quality testing: plan cost vs best-known (exhaustive where feasible / reference optimizer) per query family — the quality-gate; TPC-H ≤1.1×, JOB ≤1.3×.
  • Cardinality-accuracy testing: per-operator + cumulative q-error on JOB/TPC-H, with/without extended stats — tracked + gated (median/p95 thresholds).
  • Fuzzing: the binder (random SQL-subset text → no panic/UB); the property fuzzer (random valid logical plans → optimize → assert semantic preservation I1 + property satisfaction I5 + determinism I9) — the highest-value fuzzing, finds the wrong-plan bugs no fixture anticipated.
  • Conformance: JOB + TPC-H + TPC-DS suites → conformance.report.json (plans + cardinalities) + quality.report.json (cost vs baseline).
  • Chaos / fault injection: corrupt a stats snapshot (assert I13 audit catches it + falls back); exhaust the budget mid-search (assert best-so-far + flag, I7); a disconnected join graph (assert cross-product only there).
  • Deterministic replay: same (query, catalog, stats, seed) twice → identical memo + plan + trace (I9).
  • Regression: every minimized bug query (via ddmin) becomes a permanent fixture — the regression corpus only grows.
  • Soak: optimize the full corpus + fuzzer plans repeatedly under budgets; assert no crash, no wrong plan, bounded memo memory.
  • Performance regression: criterion microbenchmarks (DPccp enumeration rate, estimate latency, memo insert rate, optimization p50/p99) in CI; >10% regression fails.

Performance Engineering

  • Benchmarking: DPccp enumeration rate (subsets/s); estimate latency (per predicate, per join); memo insert + fingerprint-probe rate; end-to-end optimization latency (p50/p95/p99) per query family (criterion + suite timing).
  • Profiling: perf/flamegraph on the search inner loop (expect rule matching + cost/estimate evaluation to dominate); cargo-flamegraph integration. Profile a 12-relation query (the DP ceiling) — the worst-case planning latency.
  • Allocator analysis: the memo is the working set — GroupExpr uses a SmallVec for children (no heap for ≤4 children); the task stack reuses allocations (free-list); cardinality cached per group (logical property). Measure memo bytes vs relation count.
  • Cache analysis: the memo's fingerprint hash map + the DP table (subset-bitmask-keyed) are the hot structures; keep GroupExpr small + contiguous. The order/property descriptors are interned for cheap comparison.
  • Branch analysis: the pattern matcher's operator-type dispatch + the order-satisfaction prefix check are the hot branches — keep them predictable (match on a small operator enum, prefix check is a tight loop).
  • Estimation cost: estimation runs per candidate in the search — it's the inner-loop cost after rule matching; histogram lookups are O(log buckets); cache per-group cardinality (computed once, I11). Sampling is the cliff — fallback-only, cached.
  • Branch-and-bound: the primary algorithmic perf win — a good initial bound (a quick greedy plan) prunes aggressively; measure bnb_pruned as a fraction of generated group expressions.
  • Tail latency: the optimization-time budget (I7/§4) bounds the worst case to best-so-far; the DP threshold bounds enumeration; both prevent a pathological query from a multi-second plan.
  • Targets: §4 — ≤10ms p50 / ≤200ms p99 optimization (10-rel), ≤64MB memo (12-rel), q-error ≤4 (with extended stats).

Scalability Analysis

  • Bottleneck #1 join-enumeration search space: DPccp is O(3ⁿ) worst-case (clique join graph) in relation count n; the dominant scaling limit. Mitigations: the connected-subgraph restriction (sparse graphs are far cheaper than the worst case), the DP threshold (≤12 exact), greedy (13–~30), GEQO (>~30). The graph topology (chain/star/clique), not just n, sets feasibility — a 20-relation chain is fine; a 12-relation clique is the worst case.
  • Bottleneck #2 memo memory: groups × group-expressions × required-property sets. Mitigations: fingerprint dedup (I3, no duplicate exprs), branch-and-bound (fewer exprs explored), the bounded number of interesting orders (few required-property sets in real queries), the memo memory budget (I7, best-so-far on breach).
  • Bottleneck #3 estimation error compounding: q-error grows multiplicatively up the plan tree — the accuracy scaling limit (independent of compute). A 4× per-join error over 10 joins → 10⁶× total. Mitigations: extended stats (correlation), join-cardinality damping, key/FD-bounding (exact for key joins), sampling, the robust-plan bias; honestly, classical estimation has a ceiling here — the learned-model seam (§10.9) is the long-term answer.
  • Bottleneck #4 rule-application explosion: more rules → more group expressions → more search. Mitigations: transformation/implementation separation (P4), dedup (I4 termination), pattern-matcher indexing by operator type, branch-and-bound pruning.
  • Bottleneck #5 stats build (ANALYZE) at scale: large tables → expensive sampling. Mitigations: bounded sample size, single-pass multi-statistic construction, mergeable HLL, incremental/auto-stats policy.
  • Horizontal scaling (distributed planning): the single-exchange enforcer + distribution-property model exists (Phase 8); full distributed enumeration (broadcast vs repartition costing per join, multiplying the physical space) is the deferral — #316 owns it. The property framework is built to extend, not rebuild.
  • Vertical scaling: more cores don't help single-query optimization Phase 0 (the memo is mutated by one task scheduler); parallel rule application / parallel enumeration is a future axis (the memo would need concurrent-safe groups). The practical vertical axis is optimizing more queries concurrently (independent optimizer instances) — trivially parallel.
  • The real scaling axis is queries-per-second + plan quality under a latency budget: an embedded optimizer in a busy DB optimizes thousands of queries/s, each under a tight latency budget — the DP threshold + branch-and-bound + the budget guard are what make that tractable. The tradeoff curve (relation count vs optimization time vs plan quality) is the central engineering knob (§9.10).

Mental Models & First Principles

  1. MM1 — The memo is an implicit AND-OR graph: AND-nodes are group expressions (operator + child groups), OR-nodes are groups (equivalent expressions). Predicts: whether memoization shares a subplan across all parents that reference it, and when a group merge propagates new winners up. Without it: you write a planner that re-optimizes the same subtree per parent, wasting exponential time. Applied: §6 P2, Phase 5, ADR-05.

  2. MM2 — Physical properties are required top-down and provided bottom-up; unsatisfied requirements generate enforcers. Predicts: when a merge join eliminates a sort enforcer (provided order satisfies required order), and when a hash join forces one. Without it: you insert redundant sorts everywhere, or worse, run a merge join on unsorted input and produce wrong results (I5, I14). Applied: §6 P5, Phase 8, Phase 11.

  3. MM3 — Q-error compounds multiplicatively up the plan tree: a per-join error of k× over n joins produces k^n× total error. Predicts: that an innocent 4× per-join mis-estimate produces ~10^6× cumulative error over 10 joins, making a hash build sized for 1k rows when 1B rows arrive. Without it: you treat each operator's estimate in isolation and miss why the final plan is catastrophic. Applied: §8.6, Phase 2, Phase 10, D.9.

  4. MM4 — Transformation rules grow a group (logical→logical); implementation rules populate it with costable alternatives (logical→physical). They must never be conflated. Predicts: whether applying a commutativity rule to a physical operator is valid (it is not), and whether a new rule needs a cost model or just an equivalence proof. Without it: you allow physical operators to be transformed logically, generating semantically nonsensical group expressions that never terminate (I4). Applied: §6 P4, Phase 6, ADR-06.

  5. MM5 — Branch-and-bound preserves optimality only when the lower bound is admissible (never exceeds true subtree cost). Predicts: that a single inadmissible bound silently discards the optimal plan — the optimizer produces the wrong "best" plan with no error signal. Without it: you tighten the lower bound for speed and unknowingly start losing optimal plans on the exact queries that matter. Applied: §6 P10, Phase 5 (I8), Phase 3, ADR-17.

  6. MM6 — Interesting orders are the key to avoid re-sorting: a provided order that is a prefix of a required order satisfies it; no enforcer is needed. Predicts: when an index scan or merge join result can feed both the join condition and a downstream ORDER BY for free. Without it: you insert a sort after every join even when an index-provided order is already available — the System-R insight (Selinger et al. 1979) that a naive optimizer misses. Applied: §6 P5, Phase 8, §8.8, ADR-14.

  7. MM7 — The independence assumption (sel(p∧q) = sel(p)·sel(q)) is false on correlated columns; the only defenses are extended multi-column stats, key/FD bounding, and sampling. Predicts: that on real data (city='SF' AND state='CA'), the independent product dramatically under-estimates the conjunction selectivity, causing the optimizer to over-estimate intermediate cardinalities and pick the wrong build side. Without it: you build a textbook estimator that passes TPC-H (near-uniform) but catastrophically fails JOB (correlated, real-world data). Applied: §6 P6, §8.6, Phase 2 §2.6, Phase 10, ADR-13.

  8. MM8 — DPccp enumerates each (S1, S2) join pair exactly once by restricting complements to connected subgraphs; DPsub enumerates each pair 2^k times and is exponentially redundant. Predicts: that a correct DPccp implementation on a 12-relation query visits O(3^n) group expressions rather than O(4^n), and that a bug breaking the csg-cmp ordering causes the optimizer to crawl on 10+ relations. Without it: you implement DPsub, not DPccp, and wonder why the optimizer is 10× slower than expected on medium-sized join graphs. Applied: Phase 9, §9.2, ADR-07, M8.

  9. MM9 — The cardinality of a group is a logical property (shared by all group expressions); the cost of a group expression is a physical property (specific to one operator choice and its children). Predicts: that cardinality needs to be computed once per group (not per group expression) and cached, while cost must be re-derived for every physical alternative. Without it: you recompute cardinality inside the inner cost loop, wasting O(group_exprs) × estimate_cost per search step. Applied: §6 P2, Phase 5 §5.7, Phase 2 §2.7, I11.

  10. MM10 — Semantic preservation (the result multiset is identical) is the single non-negotiable invariant; any optimization that changes results is not an optimization but a bug. Predicts: that a rewrite which is sometimes faster but occasionally returns different rows (e.g. pushing a non-null-rejecting predicate below an outer join's null side) must be rejected unconditionally, regardless of its performance win. Without it: you allow conditional-correctness rewrites that corrupt data silently on the rare cases users care about most. Applied: §6 P1, Phase 4, I1, I15, T2.

Back-of-Envelope Capacity Model

Starting values from §4 System Constraints:

  1. Optimization time budget (p99, 10-rel query). From §4: ≤200 ms p99. DPccp on 12 relations explores O(3^12) ≈ 531k subgraph pairs. At 200 ms / 531k ≈ 0.38 µs/pair budget. With rule matching + cost per pair at ~2–5 µs on a modern core (profiled on Cascades implementations), branch-and-bound must prune ≥ 80–90% of pairs to meet the budget. Design consequence: the greedy initial plan (to seed the upper bound) is mandatory, not optional.

  2. Memo memory per query (12 relations). From §4: ≤64 MB. A GroupExpr is ~80 B (op enum 8 B + SmallVec<GroupId;4> 40 B + applied_rules 4 B + overhead). With 531k subgraph pairs × 3 physical implementations each ≈ 1.6M group expressions × 80 B ≈ 128 MB raw. Branch-and-bound must prune ≥ 50% of physical expressions to stay under 64 MB. Design consequence: the 64 MB bound is tight; the per-(group, req-props) winner map adds ~24 B per winner × up to 5 interesting orders per group × 531k groups ≈ an additional 64 MB. Keep GroupExpr compact (SmallVec, no heap for ≤4 children, ADR-05).

  3. Group fingerprint hash map size. From §4: ≤64 MB memo, combined with the 12-rel estimate above. The HashMap<Fingerprint, GroupExprId> at load factor 0.75 holds ~1.2M entries at ~48 B each (64-bit fingerprint + 4 B id + 40 B HashMap overhead) ≈ 57 MB. Design consequence: use a fast non-cryptographic hasher (hashbrown) and keep the fingerprint compact (128-bit structural hash of op + child group ids).

  4. Cardinality q-error ceiling at the plan root. From §4: per-operator q-error ≤4 with extended stats. For a 10-join plan tree: worst-case root q-error = 4^10 ≈ 10^6×. The §4 target of ≤4 per-operator is the per-join error cap; the cumulative product is the headline risk (D.9). Extended stats + key/FD bounding (Phase 7, Phase 10) are the only mechanisms that prevent compounding. Design consequence: every PK-FK join must be key-bounded (cardinality ≤ non-key side), or q-error compounds freely.

  5. ANALYZE throughput at 1% sample rate, 10M rows. From §4: ≤2 s. At 1% sample rate = 100k rows × ~300 B/row avg = 30 MB to scan. At NVMe sequential read ~3 GB/s: 30 MB / 3 GB/s ≈ 10 ms I/O. Remaining 1990 ms budget for HLL + histogram + MCV construction on 100k rows: 100k × ~1 µs/row (sort + HLL register update + bucket assign) = 100 ms. Design consequence: ANALYZE is CPU-bound on the sample construction, not I/O-bound; a single-pass multi-statistic builder (no re-scan per statistic) is essential.

  6. Stats storage per column. Equi-depth histogram: 200 buckets × (2 Values + 2 f64) × ~32 B/Value ≈ 200 × 72 B = 14 KB/column. MCV list: 100 values × (Value + f64) × 40 B ≈ 4 KB. HLL: 2^14 = 16k registers × 6 bits = 12 KB. Per-column total ≈ 30 KB. For a table with 100 columns: 3 MB stats. Extended multi-column stats (10 column groups): +10 × ~50 KB = +500 KB. Design consequence: the stats catalog fits comfortably in memory for typical schemas; the 200-bucket limit (§4) is the right default.

  7. Throughput target: simple queries. From §4: ≥1000 simple queries/s. At 1 ms/query = 1k queries/s. A single-table query with no joins runs the full pipeline: rewrite (10–50 µs) + memo seed (5 µs) + Cascades search (1 rule, 1 group, 2 implementations) + cost (5 µs) + explain format (10 µs) ≈ 80 µs. ≥1000/s requires ≤1 ms/query; 80 µs leaves a 12× margin. Design consequence: the simple-query path (0-1 join) must be fast enough to not require caching or batch compilation, but the 12× margin tolerates startup overhead.

  8. Throughput target: complex queries. From §4: ≥50 complex (10-rel) queries/s. At 20 ms/query budget. DPccp at 10 relations explores O(3^10) ≈ 59k subgraph pairs. At 50% pruning, 30k pairs × 3 impls × cost (2 µs) + estimate (1 µs) ≈ 90k × 3 µs = 270 ms — over budget. Design consequence: the search budget (§4 ≤200 ms p99) plus branch-and-bound pruning of >85% of physical alternatives are mandatory for 10-rel queries; the ≥50 queries/s target assumes these mitigations are in place.

  9. NDV sketch accuracy. From §4: HLL error ≤2% relative up to 10^9 distinct values. Standard HLL with m=2^14 registers achieves σ ≈ 1.04/√m ≈ 0.81% relative standard error (Flajolet et al. 2007; Phase 1). This leaves 1.2% margin for bias-correction error, which is well within the 2% gate. Design consequence: 2^14 registers = 12 KB/column is the minimum register count; larger sketches (2^16 = 64 KB) achieve 0.4% error but are rarely worth the 4× memory.

  10. Wire format for stats snapshot. From §4 assumptions: a table with 100 columns, ~30 KB/column stats, 10 extended-stats groups. Total per-table stats ≈ 3.5 MB. A typical schema of 20 tables ≈ 70 MB stats catalog. At bincode serialization ≈ 500 MB/s: serialize in ~140 ms. Deserialize at startup excluded from the ≤20 ms startup SLO (§4: catalog + stats load excluded). Design consequence: stats snapshot load can be deferred to first query; the ≤20 ms startup gate is achievable without eager stats deserialization.

  11. Optimizer trace overhead. From §4: throughput ≥50 complex queries/s when tracing is OFF. Tracing every task/rule: at 10 tasks × 50k group expressions per 10-rel query = 500k trace events × 200 B/event = 100 MB/query trace. At 50 queries/s that is 5 GB/s trace throughput — 2–3 orders of magnitude too high for default-on. Design consequence: tracing must be off by default (ADR-22); a ring-buffer bounded at ~10k events prevents OOM during a single-query trace session; trace is always an on-demand diagnostic tool, never a production default.

Alternative Architectures (Roads Not Taken)

System-R Bottom-Up Dynamic Programming

Subset lattice (n relations), filled by increasing |S|:

  {R1}  {R2} ... {Rn}              size-1: base access paths
     \   /                          (SeqScan / IndexScan per Path)
   {R1,R2} {R2,R3} ...             size-2: best join of connected halves
        \   /
      {R1,R2,R3} ...               size-k: min over connected (S1,S2) splits
            \   /
       {R1..Rn}                    size-n: the optimal plan

  bestPlan[S]  : table keyed by relation subset -> cheapest Path
  Path         : carries cost + the interesting order it provides
  No memo / no tasks / no branch-and-bound / no extensible rule trait.

Wins when: the operator set is fixed and small, the plan space is join-order-only (no operator-alternative search), and the absence of an inadmissible-bound risk (no lower-bound pruning that can silently lose the optimum) is more valuable than pruning speed. Ideal for a single-node OLTP planner with a handful of join algorithms.

Embodied by: PostgreSQL planner (src/backend/optimizer/path/, joinrels.c).

Why rejected here: adding a new operator type requires editing the DP recurrence in planner.c rather than registering a Rule; the whole subset lattice is materialized even for prunable subspaces; arbitrary logical-plan sharing (CSE, non-join subexpressions) has no memo representation; property enforcement requires threading interesting-order vectors through the DP table rather than a general required-property mechanism (ADR-06).

Randomized / Genetic Join Enumeration (GEQO-class)

Encoding:  join order = permutation of n relation ids
           permutation -> join tree (left-deep or bushy)

Generational pipeline (seeded PRNG; bounded generation count):

  seeded random      cost model        tournament
  permutations  -->  evaluates    -->  selection    --.
  (population)       each chromo        (survivors)    |
       ^                                               |
       |    swap-mutation  <--  order-crossover (OX) <-'
       |    (rate p_m)          (preserves rel. order)
       '------------------ next generation ------------'

Halt: generation budget reached OR best cost below threshold.
Output: lowest-cost permutation seen (no optimality proof).

Wins when: the relation count is large (>20–30), exact DP is computationally infeasible, and a near-optimal (not provably optimal) plan is acceptable — typical in OLAP workloads with 30+ dimension tables. Also wins when the search must be interruptible (GEQO returns a valid plan at any generation).

Embodied by: PostgreSQL src/backend/optimizer/geqo/ (triggered at geqo_threshold, default 12 relations); the genetic algorithm is based on Ioannidis & Kang (1990) and Bennett & Ferris work on randomized join ordering.

Why rejected here as the primary strategy: GEQO is not optimal even for small relation counts — it cannot prove the plan it finds is the best plan in the search space. For the ≤12-relation range where plan quality is gated at ≤1.3× optimal (§4, M4), a non-optimal algorithm fails the quality gate. DPccp provides the optimality proof that GEQO cannot. GEQO is retained as the fallback for >12 relations (§9.2, ADR-07) where DPccp's memory budget is exceeded.

Learned / ML Cardinality Model (Bao / Neo class)

Offline training:
  workload queries + execution feedback → (plan, true_card) pairs
  model: e.g. TreeLSTM or XGBoost over plan-tree features
  output: per-operator cardinality estimate

Online inference (replaces CardinalityEstimator):
  plan subtree → featurize → model inference → Estimate
  confidence: prediction interval from the model
  fallback: classical estimator if model confidence < threshold

Wins when: a large labeled workload corpus is available (thousands of executed queries with true cardinalities), the workload is stationary enough for the training distribution to match the query distribution, and the q-error from classical estimation consistently exceeds the Phase 10 target on that workload. Marcus et al. (SIGMOD 2021) demonstrated Bao's plan-selection improvements on TPC-DS and JOB.

Embodied by: Bao (Marcus et al., SIGMOD 2021, "Bao: Making Learned Query Optimization Practical") and Neo (Marcus et al., VLDB 2019) as research systems; emerging production ML-assisted estimators in commercial databases.

Why rejected here: the CardinalityEstimator trait (ADR-18, §10.9) is the explicit seam for a learned model — the rejection is scoped to Phase 0, not permanent. The classical estimator ships first because: (a) no training corpus exists at project start, (b) reproducibility and auditability requirements (I9) are harder to satisfy with a neural model, (c) the classical estimator's failure modes are well-understood and bounded (I6, I12), whereas a learned model can produce overconfident wrong estimates that bypass the q-error-propagation safety nets. The seam remains open.

Domain Deep Dive — Anatomy of a Plan Choice (rewrite → memo → properties → cost)

The plan-choice loop is the soul of the optimizer. Walk one all the way through, watching the four subsystems cooperate.

D.1 The query and the catalog

SELECT c.name, SUM(o.total) FROM customers c JOIN orders o ON o.cust=c.id WHERE c.region='EU' GROUP BY c.name ORDER BY c.name; Catalog: customers(id PK, name, region) 1M rows, region NDV 5, index idx_region(region); orders(id PK, cust FK, total) 10M rows, index idx_cust(cust). Memory budget 256 MB.

D.2 Rewrite (heuristic, pre-search)

Push c.region='EU' onto the customers scan (sel=1/5 → 200k); prune columns (c needs id,name,region; o needs cust,total).
Derive properties: customers PK {id}; the join is on c.id (PK) ⇒ each order matches ≤1 customer ⇒ key join,
   card(join) ≤ card(orders)=10M (NOT card(c)·card(o)·sel — the key bound, Phase 7).
Normalized logical: Sort[c.name] / Aggregate[group c.name, SUM(o.total)] / Join[o.cust=c.id] / σ(orders), σ_region(customers)

D.3 Memo seeding + exploration (Cascades)

Each subexpression → a group. The Join group gets transformation rules:
   commute (build/probe choice), associate (trivial here — 2 relations).
Implementation rules populate physical exprs:
   Join group: HashJoin, MergeJoin, NestedLoop(index on o.cust).
   customers-scan group: SeqScan+filter, IndexScan(idx_region, region='EU').
   Aggregate group: HashAgg, SortAgg(requires input sorted on c.name).

D.4 Property requirements propagate top-down

Root requires order (c.name) [from ORDER BY].
  → Aggregate group optimized for required order (c.name):
       SortAgg provides (c.name) order natively IF its input is sorted on c.name.
       HashAgg provides NO order → would need a PhysSort enforcer above it.
  → so the Aggregate's input (the Join) is asked: can you provide (c.name)?
       MergeJoin on o.cust=c.id provides the *join-key* order (c.id/c.cust), NOT c.name → no.
       So c.name order is NOT free from the join → a PhysSort enforcer is needed somewhere.
  Two candidate shapes for the (Aggregate, required c.name) winner:
    (a) HashAgg → PhysSort[c.name]            # group then sort the (small) grouped output
    (b) PhysSort[c.name] → SortAgg            # sort the (large) join output then stream-group
  Sorting AFTER aggregation (a) sorts ~200k grouped rows; sorting BEFORE (b) sorts the join output.
  Cost picks (a) — the grouped output is far smaller than the join output. (P5 + cost.)

D.5 Cost evaluates the join alternatives

Join cardinality = 10M (key bound, D.2) but filtered: only orders whose cust is EU ⇒ ~200k cust × avg orders.
   Estimate: customers after σ = 200k; join on cust ⇒ each EU customer's orders ⇒ ~2M order rows (10M·(200k/1M)).
HashJoin(build customers-200k, probe orders-2M):  build 200k (fits 256MB), probe 2M  → cheap.
HashJoin(build orders-2M, probe customers-200k):  build 2M (still fits) but larger build → costlier.
   → commute picks build=customers (the smaller side). [estimate-driven build-side choice]
MergeJoin: needs both sides sorted on the join key; customers via idx? no (idx is on region, not id-for-join...
   actually PK id is the join key on the customers side; an index on id provides it; orders via idx_cust provides cust order)
   → MergeJoin viable, provides join-key order — but the parent wants c.name, not join-key order, so no reuse benefit here.
NestedLoop(index on o.cust): 200k EU customers × index-probe into orders → 200k index lookups; competitive only if EU set is tiny.
Winner: HashJoin(build=customers σ_region via IndexScan idx_region, probe=SeqScan orders).

D.6 The assembled plan + the branch-and-bound that got there

PhysSort[c.name]                                  # enforcer for ORDER BY (cheap: ~200k grouped rows)
  HashAgg[group c.name, SUM(o.total)]             # no order requirement on its input
    HashJoin[o.cust=c.id]  build=customers
      IndexScan(customers, idx_region, region='EU')   -- 200k
      SeqScan(orders)                                  -- 2M probe
Branch-and-bound: while exploring, the initial greedy plan gave an upper bound. The
   HashJoin(build=orders) branch's lower bound (build 2M) exceeded a competitive bound early → pruned (I8),
   never fully costed. The NestedLoop branch was costed (200k × index-probe) and lost to the hash join.

D.7 Why each subsystem was load-bearing

- rewrite: pushed the filter (200k not 1M customers) + derived the KEY JOIN (bounded card 10M not 10¹²).
- estimate: the 200k / 2M cardinalities drove the build-side choice + the sort-placement (a/b) decision.
- properties: recognized c.name order is NOT free from the join → forced an enforcer, and placed it AFTER
    aggregation (smaller input) — the System-R interesting-orders insight (D.4).
- cost: the asymmetric hash-join cost + the spill check (both fit 256MB) + the sort cost decided the operators.
- memo + bnb: held all alternatives, deduped, and pruned the dominated branches without costing them fully.
Remove any one and the plan degrades: no key-bound → a 10¹²-row estimate → a different (catastrophic) plan;
   no property reasoning → a redundant sort or a wrong sort placement; no estimate → wrong build side.

D.8 Where the bugs hide

Every silent-wrong bug lives in one of three places: (1) an unsound rewrite/property decision — a predicate pushed below an outer join's null side, a merge join fed unsorted input, a DISTINCT eliminated over a non-key (I1/I5/I14) — wrong results; (2) an unsound decorrelation replicating 3-VL incorrectly (I15) — wrong results; (3) an estimate so wrong (independence on correlated columns) that the chosen plan exhausts the executor (T6/§10.7) — correct rows, dead executor. The paranoid-mode audits + the I1 differential + the property fuzzer target exactly (1) and (2); the q-error report targets (3). Master this deep dive and you can debug any cost-based optimizer.

D.9 The q-error explosion, concretely

Suppose every join's true selectivity is mis-estimated by 4× (independence on correlated keys).
   1 join:  4×.   3 joins: 4³ = 64×.   6 joins: 4⁶ ≈ 4096×.   10 joins: 4¹⁰ ≈ 10⁶×.
A plan the optimizer believes produces 1,000 rows actually produces a billion → a hash build sized for 1k
   spills catastrophically or OOMs the executor. The optimizer was "correct" (right rows, eventually) but
   its plan is unusable. THIS is why §6 P6 puts cardinality first: a perfect cost model on a 10⁶×-wrong
   cardinality is worthless. Extended stats (§10.7) damp the per-join error; key/FD bounds (Phase 7) make
   key joins exact; sampling + the learned-model seam (§10.9) are the long game. There is no clean classical
   fix — only damping, bounding the exact cases, and propagating uncertainty honestly.

Glossary

  • Query optimizer — the component that turns a logical query into an efficient physical execution plan via cost-based search.
  • Logical plan — a relational-algebra tree/DAG (what to compute), operator-canonical, catalog-bound.
  • Physical plan — an executable operator tree (how to compute it), with chosen algorithms + properties + cost.
  • Relational algebra — the operator set (Scan/σ/π/⋈/Γ/τ/…) the logical plan is built from.
  • Cost-based optimization — choosing a plan by estimated cost, vs heuristic/rule-only optimization.
  • Cascades / Volcano — the rule-driven, memo-based, top-down optimizer framework (Graefe) this project locks.
  • System-R — the seminal bottom-up DP optimizer (Selinger 1979); its join DP + interesting orders are embedded here.
  • Memo — the data structure holding all explored plan alternatives as equivalence groups (the search's working set).
  • Group (equivalence class) — a set of logically-equivalent expressions in the memo; the unit of memoization.
  • Group expression — one operator + its child groups (not child plans); the memo's node.
  • Winner — the lowest-cost physical group expression for a (group, required-properties) pair.
  • Task scheduler — the Cascades engine driving the search via a stack of tasks (OptimizeGroup/Expr, ApplyRule, …).
  • Transformation rule — a logical→logical rewrite that grows a group (join commute/associate, predicate move).
  • Implementation rule — a logical→physical rule producing a costable operator (Join→HashJoin, Scan→IndexScan).
  • Rewrite / normalization — heuristic, unconditionally-good logical rewrites applied before the cost-based search.
  • Predicate pushdown — moving filters as close to the scans as possible to reduce intermediate cardinality.
  • Projection pruning — removing columns no ancestor uses.
  • Constant folding — evaluating constant subexpressions at optimization time.
  • Subquery decorrelation / unnesting — rewriting a correlated subquery as a join (avoiding re-execution per outer row).
  • Transitive predicate inference — deriving new predicates from equalities (a=b ∧ b=c ⟹ a=c).
  • Common-subexpression (CSE) — a subplan computed once + shared (the plan is a DAG, not a tree).
  • Join enumeration — searching the space of join orders.
  • DPccp / DPhyp — dynamic programming over connected (hyper)graph subgraphs; optimal, cross-product-free join enumeration.
  • DPsize / DPsub — alternative subset DPs (by size / by subset); DPccp is more efficient (each join pair once).
  • Left-deep / bushy — join-tree shapes; left-deep restricts one input to a base relation, bushy allows two intermediates.
  • GEQO — a genetic/randomized join-ordering search used past the DP threshold.
  • Cardinality estimation — estimating the row count an operator produces.
  • Selectivity — the fraction of rows a predicate passes (∈[0,1]).
  • Histogram — a per-column row-distribution summary (equi-depth: equal rows per bucket; max-diff: split at frequency gaps).
  • MCV (most-common values) — a per-column list of frequent values + frequencies, capturing skew.
  • NDV (number of distinct values) — the distinct-value count, estimated via HyperLogLog.
  • HyperLogLog (HLL) — a sub-linear, mergeable distinct-count sketch.
  • Null fraction — the fraction of NULLs in a column (tracked separately from the histogram).
  • Extended / multi-column statistics — joint distribution stats (joint NDV, soft FDs) defending against the independence assumption.
  • Independence assumption — sel(p∧q)=sel(p)·sel(q); the #1 source of estimation error on correlated columns.
  • q-error — max(estimate/truth, truth/estimate) (≥1); the estimation-accuracy metric; compounds multiplicatively up the tree.
  • Containment assumption — the join-selectivity assumption sel(a=b)=1/max(ndv(a),ndv(b)).
  • Cost model — the function mapping (cardinality, properties, operator) to a Cost (CPU/IO/memory/network) → scalar.
  • Calibration — fitting the cost constants (seq_page_cost, random_page_cost, cpu_tuple_cost, …) to a target environment.
  • Spill — an operator exceeding its memory budget + falling back to an external (disk) algorithm (with a higher cost).
  • Physical property — a property of a physical plan's output: an order (sortedness) or a distribution (partitioning).
  • Interesting order — an order the query cares about (ORDER BY, merge-join keys, sort-agg keys); reusing it avoids sorts.
  • Enforcer — an operator inserted to satisfy a required property (PhysSort for an order, Exchange for a distribution).
  • Distribution / partitioning — how data is spread across nodes (Single/Hash/Range/Broadcast); the distributed-stub property.
  • Branch-and-bound — pruning a search branch whose lower-bound cost exceeds the current best (an upper bound).
  • Admissible lower bound — a lower bound that never exceeds the true cost (required for branch-and-bound to preserve optimality).
  • Functional dependency (FD) — X→Y: X determines Y; drives key inference + correlation correction.
  • Key — a column set whose values are unique per row; bounds join cardinality + enables redundant-op elimination.
  • Logical property — a property of a relation (schema, cardinality, keys, FDs, not-null); shared across a group's expressions.
  • EXPLAIN / EXPLAIN ANALYZE — the plan-output surface; ANALYZE adds true cardinalities (revealing q-error).
  • ANALYZE — the command/collector that builds statistics by sampling base tables.
  • Staleness — stats no longer reflecting the table (the #1 real-world cause of plan regressions).
  • Fingerprint — the structural key (operator + ordered child group ids + params) used for memo dedup.
  • Bind / binder — name resolution + type checking, lowering SQL to the logical IR.
  • Three-valued logic (3-VL) — SQL's TRUE/FALSE/NULL predicate logic; the semantic trap in rewrites + decorrelation.
  • Robust plan — a plan whose cost is insensitive to estimation uncertainty (preferred when confidence is low).
  • Hash-consing / interning — mapping structurally-equal expressions/plans to one id (sharing + O(1) equality).
