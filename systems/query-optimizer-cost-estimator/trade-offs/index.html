01

Language

Chosen

Rust (stable)

Rejected

C++, Java/Scala

When the rejected choice is right

Rust is the right choice when arena-lifetime bugs in a C++ memo are the primary implementation risk; C++ wins in a codebase that already has a mature C++ DB engine and cannot afford an FFI boundary.

Why: GC-free memo + exhaustive enum matching; portfolio fit (#52/#206/#207)

02

Build

Chosen

Cargo workspace + Makefile

Rejected

CMake, Bazel

When the rejected choice is right

Bazel wins when the project is embedded in a large monorepo with multi-language dependencies and hermetic remote caching is required; CMake wins for cross-platform portability to legacy build systems.

Why: native, reproducible

03

Dependencies

Chosen

stdlib + minimal (hashbrown, smallvec, ordered-float, a HLL crate)

Rejected

heavy frameworks

When the rejected choice is right

A heavy framework (e.g. Apache Calcite) wins when the optimizer is embedded in a JVM-based engine and rule reuse across dozens of projects outweighs startup/GC costs.

Why: small trusted base

04

Plan IR shape

Chosen

DAG with ExprId/PlanId interning (hash-consing)

Rejected

tree-per-node

When the rejected choice is right

A tree-per-node (copy-on-write) shape wins when the optimizer must be purely functional, e.g. in a language without a safe mutable-graph model, or when immutable snapshotting of plans is a first-class requirement.

Why: CSE sharing + O(1) structural equality

05

Memo references

Chosen

integer GroupId/GroupExprId handles

Rejected

Rc<RefCell<…>>

When the rejected choice is right

Rc<RefCell<>> wins when the optimizer lives in a single-threaded scripting context (Python/Ruby extension) where integer-handle indirection adds friction and the cyclic-graph concern is managed by the host GC.

Why: cyclic graph without borrow-checker fights; relocatable

06

Search architecture

Chosen

Cascades top-down + memo + tasks

Rejected

System-R bottom-up DP

When the rejected choice is right

System-R bottom-up DP wins in a single-operator-set planner (only joins to enumerate, no extensibility needed) where implementation simplicity and absence of the inadmissible-bound risk (I8) outweigh the lack of a general memo.

Why: extensible (rules), property-driven, branch-and-bound; see §9-note

07

Join enumeration

Chosen

DPccp/DPhyp (≤12) + greedy + GEQO (>12)

Rejected

DPsub, exhaustive

When the rejected choice is right

DPsub (enumerate all subsets) wins when the join graph is always a clique and the engineering cost of DPccp's csg-cmp order is not justified; exhaustive enumeration wins on very small fixed relation counts (<=5) where plan quality trumps latency.

Why: cross-product-free, provably optimal in range, graceful fallback

08

Rule representation

Chosen

hand-written Rule trait + pattern matcher

Rejected

a rule-DSL/codegen (optgen-style)

When the rejected choice is right

A rule DSL/codegen (optgen-style) wins at scale when the rule set exceeds ~100 rules and the cost of debugging generated code is lower than the cost of maintaining hand-written rule structs; it also wins when type-safe pattern matching can be enforced at code-generation time.

Why: precise, debuggable Phase 0; DSL deferred

09

Cardinality numbers

Chosen

f64 rows with saturation ceiling

Rejected

u64 / bignum

When the rejected choice is right

u64 cardinality wins when exact row counts are required (e.g. for a cost model that must bit-reproduce across runs) and the plan tree never models partial or probabilistic cardinalities; bignum wins when cardinalities must survive exact cross-product overflow without saturation.

Why: estimates are inherently approximate; saturate not overflow

10

Cost numbers

Chosen

f64 scalar from a Cost vector via calib weights

Rejected

integer microseconds

When the rejected choice is right

Integer microseconds win when cost comparisons must be bitwise reproducible across platforms (avoiding f64 NaN/Inf edge cases) and the cost model has a fixed granularity that maps cleanly to integer units.

Why: smooth comparison; calibratable

11

Histograms

Chosen

equi-depth default + max-diff option

Rejected

equi-width only

When the rejected choice is right

Equi-width histograms win when data is known to be nearly uniform and the simplicity of equal-width buckets reduces implementation risk; max-diff wins as the default when heavy-tail skew is the dominant distribution.

Why: equi-depth handles skew; max-diff for heavy tails

12

NDV estimation

Chosen

HyperLogLog sketch

Rejected

exact distinct count, sampling-only

When the rejected choice is right

Exact distinct count wins when the cardinality fits in memory and deterministic exactness is required for security-sensitive selectivity (e.g. access-control policy cardinality); sampling-only NDV wins when memory is extremely constrained.

Why: sub-linear memory, mergeable, bounded error

13

Selectivity model

Chosen

independence default + extended (multi-col) stats correction

Rejected

independence only

When the rejected choice is right

Independence-only wins when the optimizer is a simple one-pass heuristic planner and the additional code complexity of extended stats is not justified; it also wins when column correlation is empirically negligible for the target workload.

Why: correlation is the #1 estimation error (JOB)

14

Property model

Chosen

interesting orders + distribution + enforcers

Rejected

orders only

When the rejected choice is right

Orders-only wins when the system is single-node and distribution is not a concern; distribution-only wins in a pure MPP system where local sort orders are irrelevant (shuffle-hash join dominates).

Why: needed for merge-join reuse + distributed stub

15

Distributed planning

Chosen

single-exchange enforcer stub

Rejected

full multi-exchange search

When the rejected choice is right

Full multi-exchange search wins when the optimizer is embedded in a distributed engine where broadcast-vs-repartition costing is the dominant plan-quality lever and the additional physical-space explosion is bounded by pruning.

Why: single-node Phase 0; #316 owns distributed

16

Decorrelation

Chosen

rule-based unnesting (scalar/EXISTS/IN)

Rejected

leave correlated (re-execute)

When the rejected choice is right

Leaving correlated subqueries as re-execute wins when the subquery always returns at most one row (point lookup semantics) or when the unnested join would produce a worse plan due to outer-join cardinality explosion under poor estimates.

Why: turns O(n) re-exec into one join; soundness-gated (I15)

17

Pruning

Chosen

branch-and-bound with admissible lower bounds

Rejected

full scoring of all plans

When the rejected choice is right

Full scoring of all plans (no pruning) wins when the plan space is tiny (<=3 relations, single operator choice) and the overhead of maintaining an admissible lower bound exceeds the search savings; it also wins when debugging requires seeing all costed alternatives.

Why: tractable search; preserves optimality (I8)

18

Estimator extensibility

Chosen

CardinalityEstimator trait

Rejected

hard-coded classical only

When the rejected choice is right

Hard-coded classical estimation wins when the training corpus for a learned model is unavailable or the reproducibility/auditability requirement forbids a learned component.

Why: leaves the seam for learned models (§10.9)

19

Determinism

Chosen

seedable PRNG (GEQO), ordered tie-breaks

Rejected

hash/address order

When the rejected choice is right

Hash/address-order tie-breaking wins in a prototype where determinism is sacrificed for implementation speed; it is never acceptable in a production optimizer where plan reproducibility is an SLO.

Why: reproducible plans (P9/I9)

SQL frontend

Chosen

thin subset binder (fixtures)

Rejected

full parser

When the rejected choice is right

A full SQL parser wins when the optimizer is the entry point for end-user SQL (not embedded behind another parser layer) and the binder must handle the full grammar.

Why: #21 owns parsing; subset suffices for the optimizer

A bespoke EXPLAIN format wins when the output is consumed exclusively by a custom UI that requires a schema not expressible in PostgreSQL-style JSON.

Printf-style logging wins in a single-threaded embedded context where the structured-logging crate adds binary size or initialization overhead that violates the startup SLO.

Live-DB-only stats win when a persistent stats snapshot introduces a version-drift risk or when the DB guarantees fresh stats on every query (e.g. an in-memory OLTP engine with cheap exact counts).

System-R Bottom-Up Dynamic Programming

Subset lattice (n relations), filled by increasing |S|:

  {R1}  {R2} ... {Rn}              size-1: base access paths
     \   /                          (SeqScan / IndexScan per Path)
   {R1,R2} {R2,R3} ...             size-2: best join of connected halves
        \   /
      {R1,R2,R3} ...               size-k: min over connected (S1,S2) splits
            \   /
       {R1..Rn}                    size-n: the optimal plan

  bestPlan[S]  : table keyed by relation subset -> cheapest Path
  Path         : carries cost + the interesting order it provides
  No memo / no tasks / no branch-and-bound / no extensible rule trait.

Wins when: the operator set is fixed and small, the plan space is join-order-only (no operator-alternative search), and the absence of an inadmissible-bound risk (no lower-bound pruning that can silently lose the optimum) is more valuable than pruning speed. Ideal for a single-node OLTP planner with a handful of join algorithms.

Embodied by: PostgreSQL planner (src/backend/optimizer/path/, joinrels.c).

Why rejected here: adding a new operator type requires editing the DP recurrence in planner.c rather than registering a Rule; the whole subset lattice is materialized even for prunable subspaces; arbitrary logical-plan sharing (CSE, non-join subexpressions) has no memo representation; property enforcement requires threading interesting-order vectors through the DP table rather than a general required-property mechanism (ADR-06).

Randomized / Genetic Join Enumeration (GEQO-class)

Encoding:  join order = permutation of n relation ids
           permutation -> join tree (left-deep or bushy)

Generational pipeline (seeded PRNG; bounded generation count):

  seeded random      cost model        tournament
  permutations  -->  evaluates    -->  selection    --.
  (population)       each chromo        (survivors)    |
       ^                                               |
       |    swap-mutation  <--  order-crossover (OX) <-'
       |    (rate p_m)          (preserves rel. order)
       '------------------ next generation ------------'

Halt: generation budget reached OR best cost below threshold.
Output: lowest-cost permutation seen (no optimality proof).

Wins when: the relation count is large (>20–30), exact DP is computationally infeasible, and a near-optimal (not provably optimal) plan is acceptable — typical in OLAP workloads with 30+ dimension tables. Also wins when the search must be interruptible (GEQO returns a valid plan at any generation).

Embodied by: PostgreSQL src/backend/optimizer/geqo/ (triggered at geqo_threshold, default 12 relations); the genetic algorithm is based on Ioannidis & Kang (1990) and Bennett & Ferris work on randomized join ordering.

Why rejected here as the primary strategy: GEQO is not optimal even for small relation counts — it cannot prove the plan it finds is the best plan in the search space. For the ≤12-relation range where plan quality is gated at ≤1.3× optimal (§4, M4), a non-optimal algorithm fails the quality gate. DPccp provides the optimality proof that GEQO cannot. GEQO is retained as the fallback for >12 relations (§9.2, ADR-07) where DPccp's memory budget is exceeded.

Learned / ML Cardinality Model (Bao / Neo class)

Offline training:
  workload queries + execution feedback → (plan, true_card) pairs
  model: e.g. TreeLSTM or XGBoost over plan-tree features
  output: per-operator cardinality estimate

Online inference (replaces CardinalityEstimator):
  plan subtree → featurize → model inference → Estimate
  confidence: prediction interval from the model
  fallback: classical estimator if model confidence < threshold

Wins when: a large labeled workload corpus is available (thousands of executed queries with true cardinalities), the workload is stationary enough for the training distribution to match the query distribution, and the q-error from classical estimation consistently exceeds the Phase 10 target on that workload. Marcus et al. (SIGMOD 2021) demonstrated Bao's plan-selection improvements on TPC-DS and JOB.

Embodied by: Bao (Marcus et al., SIGMOD 2021, "Bao: Making Learned Query Optimization Practical") and Neo (Marcus et al., VLDB 2019) as research systems; emerging production ML-assisted estimators in commercial databases.

Why rejected here: the CardinalityEstimator trait (ADR-18, §10.9) is the explicit seam for a learned model — the rejection is scoped to Phase 0, not permanent. The classical estimator ships first because: (a) no training corpus exists at project start, (b) reproducibility and auditability requirements (I9) are harder to satisfy with a neural model, (c) the classical estimator's failure modes are well-understood and bounded (I6, I12), whereas a learned model can produce overconfident wrong estimates that bypass the q-error-propagation safety nets. The seam remains open.
