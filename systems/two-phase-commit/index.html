In one paragraph

Atomic commit is the problem of making several separate machines either all apply a transaction or all drop it. This blueprint builds the two classic answers, Two-Phase Commit (ask everyone, then announce the result) and Three-Phase Commit (add a warning step in between), as state machines with write-ahead logs, crash recovery and a deterministic fault-injecting simulator, all inside one Rust process (§1, §8.3, §8.4). Its purpose is teaching: it reproduces 2PC's blocking problem and 3PC's partition-unsafety as logged, inspectable events (§1, §2). Its users are systems engineers, students and instructors, and it is explicitly not a production resource-manager driver (§1).

The problem, concretely

A transaction touches three machines, A, B and C, each holding part of the data. You want all three to apply the change or none to (§1, §8.5). The naive plan, "tell everyone to commit", breaks the moment B has to refuse, because each machine keeps the right to abort until it has voted (P2, I2): A and C apply the change, B does not, and the three now disagree, which is exactly what atomicity forbids (I1). Asking first fixes that: each machine votes Yes or No, and only a unanimous Yes leads to commit (§8.3). But a Yes is a promise to accept whatever the coordinator decides, so a machine that has voted Yes can no longer back out on its own (P2, I3).

Now crash the coordinator between "all voted yes" and the decision broadcast (§2). Every machine that voted Yes is stuck: it may not abort on its own (I3), and a timeout that let it decide anyway could commit on one node and abort on another (P5). That stuck state is the blocking problem, "the canonical example of blocking in distributed systems" (§2). The votes the coordinator collected were never durable, so a lost decision record cannot be rebuilt from them (P3, MM6). The simulated network may also drop, delay, duplicate or reorder messages (I10), so a vote's reply can be lost (T2) or a Commit delivered twice (T9). The design answers three pressures: never disagree (I1), never forget a promise (P1), and accept blocking where it is the price of staying safe (P5, MM5).

How it works, end to end

Follow one transaction through the boxes of §3's diagram, adapted here:

                         tpc-sim  (SimNetwork, seeded logical clock, FaultInjector)
                                   | in-process messages
        +--------------------------+--------------------------+
        |                          |                          |
  Coordinator              Participant 1 ... k         Participant ...
  (tpc-2pc / tpc-3pc)      (tpc-2pc / tpc-3pc)         (tpc-2pc / tpc-3pc)
        |                          |                          |
   DurableLog                 DurableLog                 DurableLog
   (coordinator)              (participant)              (participant)
  1. Workspace and ids (tpc-core): holds the identifiers NodeId and TxnId, the message enums TwoPhaseMsg and ThreePhaseMsg, the LogRecord type, the DurableLog and LogicalClock traits and TpcError (§1, §10, §11).
  2. Simulator (tpc-sim): owns message delivery order, latency, drop/duplicate/reorder faults and the clock every timeout reads. It is the only component allowed to inject faults (§3, I10). Its files are network.rs (SimNetwork), fault.rs (FaultInjector) and runner.rs, which loads and executes the JSON fixtures (§10, ADR-17).
  3. Coordinator (Coordinator2Pc in tpc-2pc, Coordinator3Pc in tpc-3pc): holds the decision authority. At decision time it reads only its own log and the votes it collected (§3, I4). It starts with begin(), logs BEGIN and broadcasts Prepare (2PC) or CanCommit (3PC) (§8.3, §8.4).
  4. Participants (Participant2Pc, Participant3Pc): each owns its local resource state and its own log, never shared with the coordinator's (§3, I5, I9). Each votes, logs the vote first, then replies (I5, P1).
  5. DurableLog: an append-only record store per node. append() pushes into an uncommitted in-memory buffer and force() is the simulated disk-flush barrier (fsync); a simulated crash keeps only what was forced (§3, §11, §13.2, ADR-08).
  6. Decision and finish: on unanimous Yes the coordinator force-writes the decision, then broadcasts it; participants apply, log and Ack; the coordinator writes DONE (§8.3, §8.5, I4).

The state machines never touch the network or the disk themselves: they return "intents" (send this message, write this record) and only tpc-sim carries them out (P12, §3). Every transition has exactly one cause: a message, a timeout or a replay event (I11).

Concrete trace from the blueprint (2PC, three participants, clean commit, §8.5): t0 coordinator logs BEGIN{A,B,C} and sends Prepare to all three; t1 each participant logs PREPARED and answers Prepared; t2 the coordinator has 3 of 3 Yes, logs COMMIT, sends Commit; t3 each participant logs COMMIT, applies, answers Ack; t4 the coordinator logs DONE. That is two round trips.

The core ideas

Two rounds: collect votes, then announce one outcome (§8.1, §8.3)

Round one is Prepare and the votes (Prepared or VoteAbort); round two is Commit or Rollback and the Acks. The coordinator moves Idle, Preparing, then Committing or Aborting, then Done (§11). A single No short-circuits: in the blueprint's failure-path example B votes No, and the coordinator moves to Aborting at once, logs ABORT and sends Rollback to A and C without waiting for their votes (§8.8). The example calls A and C both "still in Prepared" and "not yet voted"; under the second reading either path converges on abort, because a participant that has not yet voted may abort on its own (I2, §8.8), while a Prepared one may not (I3).

Coordinator state Event Next state Logs Sends
Idle begin() Preparing BEGIN Prepare to all
Preparing all Yes Committing COMMIT Commit to all
Preparing any No or timeout Aborting ABORT Rollback to all
Committing / Aborting all Ack Done DONE nothing

Log first, send second (§6 P1, I4, I5, MM2)

The rule: never tell another node something your own crash could make untrue (MM2). Concretely, a participant force-writes its Yes vote before it replies Prepared (I5), and the coordinator force-writes its decision before it sends Commit or Abort (I4). Tiny example: a participant that replies Yes first and crashes before logging comes back having forgotten a promise it made, which is the violation P1 names (P1). The price is a force() on the critical path of every Prepared/Commit/Abort/PreCommit send (P1).

Presumed abort: silence means no (§6 P4, I8, MM3)

If a restarted coordinator finds a transaction with Begin but no Decision record, it assumes the answer was Abort (presumed abort) and broadcasts Rollback (§16.2, I8). Three-step trace: (1) coordinator logs BEGIN, sends Prepare, crashes; (2) on restart recover() finds BEGIN but no decision (§13.8); (3) it presumes Abort and broadcasts Rollback, which is safe because a commit would have needed a forced COMMIT first (I8, I4). The trick is only a choice of what silence means, not "no logging" (MM3).

The blueprint credits presumed abort with saving at least one log write per aborted transaction against plain 2PC, and says the coordinator "never logs Abort on the pre-vote path — only silence" (P4, M7, §16.7, §32 item 12). Yet its state table logs ABORT on "any No / timeout" (§8.3), and §16.2 has the coordinator force-write Decision{Abort} before broadcasting Rollback on any No. The blueprint states both and does not reconcile them. Its own last row for 2PC also says a restart with "no log record" goes straight to Done with no send (§8.3), while §16.2 broadcasts Rollback.

The blocking problem: a Yes vote is a promise (§6 P2, P5, I3, MM1, FM-1)

After voting Yes a participant is in Prepared and has no transition that aborts (I3). On a timeout its only safe moves are to re-query the coordinator or keep waiting (P5, §17.2). Timeouts decide which safe action to try next; they never authorise a decision that violates a logged commitment (P5). Hence FM-1, a participant stuck in Prepared indefinitely, has no automatic recovery "by design"; the blueprint calls it 2PC's blocking problem (FM-1), and says that block is intentional, not a bug (P5). The Phase 5 fixture demonstrates it: with no coordinator recovery the participant stays exactly Prepared for the whole tick budget (e.g. 10,000 ticks), and unblocks within one round trip once recover() runs (§17.4).

Three-Phase Commit: a warning step before the commit (§6 P6, I6, §8.4, §8.6, MM4)

3PC inserts PreCommit between "all voted Yes" and "commit" (P6). The coordinator's path becomes CanCommitting, PreCommitting, DoCommitting, Done (§8.4), with three request-and-reply exchanges per participant in the happy path instead of two (§32 items 6, 7). A participant that reaches PreCommitted knows that every cohort member voted Yes, so if the coordinator then vanishes and no DoCommit arrives, the participant can commit on its own timeout (I6, §8.6, §18.2). Trace from §8.6: all three participants log PRECOMMIT and reply AckPreCommit; the coordinator crashes; their precommit timeouts fire; each moves PreCommitted to Committed with no coordinator input. The caveat is part of the claim: this holds under fail-stop and no partition, and quoting it without that qualifier is "the single most common textbook error" the project exists to correct (P11). One extra phase buys a witness, not a guarantee (MM4).

The same table has a row the reader should not skip: a coordinator in PreCommitting whose acknowledgements are still partial when its timeout fires moves to Aborting, logs ABORT and sends Abort to all, marked "fail-stop only" (§8.4, P11). I6 says every participant that received PreCommit eventually commits, absent partitions (I6), and §18.2 commits a PreCommitted participant on its own timeout. The blueprint gives both rules and does not say what a PreCommitted participant does with that Abort.

Quorum termination: when the coordinator is gone and the network is split (§6 P7, I7, I13, MM5)

When the coordinator times out, the participants run a termination protocol among themselves. A participant queries its peers; it may decide only if it reaches a quorum (typically a majority, ⌈(N+1)/2⌉, §19.10) and that quorum's states agree (§19.2, P7). A quorum in which any member is still WaitingPreCommit forces Abort; a quorum in which any member is PreCommitted or beyond forces Commit (§19.2). The two "any member" rules overlap when one quorum holds both states, and the step settles that case only by its demand that the states agree. A participant on the minority side of a partition cannot reach a quorum, so it blocks rather than disagrees (I13, §19.4, T8). That is the safety-over-liveness choice: a partition costs liveness first, and costs safety only if someone lets a minority decide (MM5).

The trade-offs — where engineers disagree

Network: a simulated bus, not sockets (ADR-02)

Chosen: an in-process simulated bus, tpc-sim, for determinism and no OS scheduler noise (ADR-02, P10). Rejected: real TCP sockets. When the rejected choice is right: once real transport is un-deferred for multi-host deployment (ADR-02, §35). The same trigger flips ADR-11 (async instead of a synchronous, single-threaded step function), ADR-18 (mTLS instead of no transport security) and ADR-07 (wall-clock timers to measure real latency variance).

Abort cost: presumed abort (ADR-03)

Chosen: presumed abort (Mohan et al. 1986), for fewer log writes on the "(assumed) common abort path" (ADR-03, P4). Rejected: plain 2PC that logs both outcomes. When the rejected choice is right: in workloads where commit vastly outnumbers abort and log-write symmetry simplifies audit tooling (ADR-03). Its mirror, presumed commit, wins where commit vastly dominates abort and is deferred for scope control (ADR-04, §35). How many writes are really saved is the open conflict described under presumed abort above (§8.3, §16.2).

Which non-blocking protocol: Skeen's 3PC (ADR-05)

Chosen: Skeen 3PC (1981), because it matches the canonical textbook description the project teaches from (ADR-05). Rejected: Keidar/Dolev-style quorum 3PC variants. When the rejected choice is right: when partition tolerance, not just non-blocking under fail-stop, is the real requirement (ADR-05, P11).

Fault model: crashes and message loss, never lies (ADR-06)

Chosen: fail-stop plus omission (crash, drop, delay, duplicate, reorder), matching the assumptions of the Gray 1978 and Skeen 1981 proofs (ADR-06, I10). Rejected: Byzantine (arbitrary or malicious) faults. When the rejected choice is right: adversarial multi-organisation deployments (ADR-06, §34). Adopting it here would mean re-deriving every safety argument from scratch (§34).

Write ordering: log before send (ADR-09)

Chosen: log-before-send at both coordinator and participant, required by P1, I4 and I5 (ADR-09). Rejected: send-before-log. When the rejected choice is right: only where occasional heuristic decisions are accepted in exchange for lower per-hop latency, for example a best-effort analytics pipeline with no atomicity SLO (ADR-09).

Cohort membership: fixed at begin() (ADR-10)

Chosen: the set of participants is fixed for the transaction's life, for simplicity and fidelity to the 2PC and 3PC literature (ADR-10, I12). Rejected: dynamic reconfiguration mid-transaction. When the rejected choice is right: in long-lived sagas where membership legitimately changes over the transaction's life (ADR-10, §34).

Who finishes a 3PC transaction when the coordinator dies: the participants (ADR-14)

Chosen: a cooperative quorum query among participants, as in Skeen's original description and without an election protocol (ADR-14, P7). Rejected: an elected backup coordinator. When the rejected choice is right: in systems that already run leader election for other reasons, such as Raft-based systems (ADR-14).

Roads not taken (§34, §35)

Paxos Commit replaces the single coordinator with a group of 2F+1 acceptors, so the coordinator role itself survives crashes. It wins when the coordinator must not block the transaction, as in multi-datacenter deployments, and Spanner's design is the real-world example; it is rejected here because it needs a full consensus implementation, so the project keeps a sketch only (§34, ADR-19, MM8). MM8 states the point: replicating the coordinator and adding a phase are different fixes for different problems, and combining them is a coherent design (MM8).

Sagas run steps forward with a compensating step for each on failure, holding no global lock. They win for long-lived transactions across services that cannot hold resources through a commit round (Temporal is the cited example). Rejected because compensation is not true rollback, and this project studies atomic commit specifically (§34).

Percolator-style decentralized 2PC stores lock and write state in shared storage so any client can resume a stalled transaction. It wins when many concurrent coordinators matter more than a single coordinator's simplicity (TiKV is the cited example). Rejected because it needs a strongly consistent storage layer beneath it and this project deliberately has none (§34, ADR-08).

Byzantine commit (PBFT-style) wins when participants may be malicious, for example permissioned blockchains. Rejected because every invariant and fixture here assumes fail-stop faults (§34, I10, ADR-06).

The deferred register lists six things not built in v1, each with a trigger for building it: real TCP/TLS transport (a real multi-host deployment), a real fsync'd log (durability across process restart), the full presumed-commit variant (a commit-dominant workload), full Paxos Commit (a goal of shipping a production coordinator), multi-host Jepsen-style chaos testing (once real transport lands) and Byzantine fault tolerance (untrusted participants) (§35).

What must never be false

  • I1 — all participants that ever vote Yes reach the same terminal decision. Noticed by cross-node fixture assertions and the decision_mismatch_total counter (§7).
  • I2 — a participant that has not voted may abort on its own. Checked by scanning the state-transition log; unilateral_abort_total counts uses (§7).
  • I3 — a participant that voted Yes cannot abort on its own afterwards. Enforced by there being no such transition, so it is caught at compile time rather than detected at runtime (§7, P8).
  • I4 — the coordinator force-writes its decision before sending Commit or Abort. A log-order fixture assertion plus log_before_send_violations detect a breach; the failure is FM-2 (§7).
  • I5 — a participant force-writes PREPARED before voting Yes. Same fixture and the same counter, log_before_send_violations (§7).
  • I6 — a 3PC participant that received PreCommit eventually commits, absent partitions. A chaos fixture crashes the coordinator after PreCommit; precommit_autocommit_total counts the self-healing (§7).
  • I7 — no two 3PC participants reach conflicting decisions across a PreCommit boundary. A chaos fixture broadcasts PreCommit partially; termination_disagreement_total rises on a breach and recovery is FM-6 (§7).
  • I8 — a recovering coordinator with no log record for a transaction presumes Abort. Recovery fixtures assert it; presumed_abort_total counts it (§7).
  • I9 — log records are append-only. The DurableLog API has no update method, so the type system is the detector (§7).
  • I10 — simulated faults are omission or crash-stop only, never Byzantine. Checked by reviewing the fixture's injected fault set against the FaultInjector variants (§7).
  • I11 — every state transition has exactly one cause: a message, a timeout or a replay event. The FSM method signatures enforce it and code review checks it (§7).
  • I12 — a transaction's cohort is fixed for its lifetime. A fixture rejects a late join and cohort_mutation_rejected_total counts attempts (§7).
  • I13 — 3PC's termination protocol needs quorum contact before it decides. A chaos fixture tries a minority-side decision; minority_decision_blocked_total counts the refusals (§7).

What breaks in production

The blueprint is a simulator, so "production" means the failures its fixtures and metrics are designed to expose (§23).

  • FM-1 — a participant stuck in Prepared indefinitely. Cause: the coordinator crashed inside the decision window and nobody ran recovery (T4, T5). You see the blocked_since_tick gauge pass its SLO. There is no automatic recovery by design (I3); an operator restarts the coordinator so recover() runs, or does a break-glass quorum poll that §17.10 flags as unsafe in general (§17.10).
  • FM-2 — the coordinator log lacks an expected Decision record. Cause: a record was written but force() was never called before the crash (P1 violated). The log-order fixture assertion fails. No automatic recovery: it is a specification-violation bug and the fix is code (§23).
  • FM-3 — a participant re-sends Prepared after restart and gets no reply. Cause: it crashed between logging Voted{Yes} and sending Prepared (§15.9). A recovery fixture diverges. Recovery is automatic: the coordinator handles duplicate Prepared idempotently (P9).
  • FM-5 — the presumed-abort rate spikes. Cause: a crash-looping coordinator (T4 recurring). The presumed_abort_total rate alert fires. Restart stabilises it; the real work is finding the crash-loop's root cause (§23).
  • FM-6 — 3PC termination protocol disagreement. Cause: the quorum check was bypassed or the quorum size misconfigured (P7). The I7 chaos assertion fails. No automatic recovery: it is a safety violation and release-blocking (§21.9); the fix is restoring correct quorum arithmetic.
  • FM-7 — 3PC participants blocked pending quorum. Cause: a partition with no reachable majority. minority_decision_blocked_total stays nonzero. Recovery: wait for the partition to heal, with "no safe manual override" (I13, §23). A chaos cell that stably blocks like this counts as a pass, while any disagreement, FM-6's kind, is release-blocking (§21.6, §21.9).
  • FM-9 — the log grows without bound. Cause: P13 violated, meaning truncation before global ack, rolled back or never attempted. log_entry_count grows. Manual audit of un-acked transactions; it may indicate FM-1 accumulating (§23).
  • FM-10 — recovery replay exceeds the RTO budget. Cause: a log beyond the 10,000-transaction ceiling, the first-named bottleneck (§29). A tpc-bench recovery-time regression shows it. Fix: shard the log or raise the ceiling (§23, §29).

Threats a reader should know (§22): T4 and T5, the two coordinator-crash windows, are answered by presumed abort and by rebroadcasting the logged decision on recovery (§22, P3, I8); T7, a coordinator crash in the middle of the PreCommit broadcast, is answered by the quorum termination protocol (§22, P7); T8, a minority side deciding alone during a partition, is answered by the quorum requirement and recovery is to block until a quorum is reachable (§22, I13); T9, a duplicated Commit applied twice, is answered by idempotent handlers and a no-op ack (§22, P9); T10, a forged log record from the test harness, is out of scope because the model is fail-stop, not Byzantine (§22, I10).

How it compares

  • PostgreSQL PREPARE TRANSACTION does not replicate the coordinator at all, so it keeps 2PC's blocking risk: orphaned prepared transactions hold locks until resolved (§31, §5 R1). That is fine for a single trusted database process, which is the transaction's natural home (§31).
  • Kafka TransactionCoordinator replicates its decision log through an ordinary Kafka topic instead of a bespoke consensus protocol, and blocking is only partial because the log survives a broker crash (§31, §5 R3). That suits a system that already has a durable replicated log to reuse (§31).
  • Spanner puts 2PC on top of per-shard Paxos groups, so the coordinator role is itself replicated and survives a minority crash (§31; Corbett et al. 2012 in §5). It earns its cost at global, multi-datacenter scale, where losing a whole coordinator machine must not block transactions (§31).
  • Percolator / TiKV has no coordinator process; commit state lives as rows in the data store, and any client can resume a stalled transaction through the lock table (§31, §5 R4). It works where the storage layer already gives strong per-row consistency (§31).

This design is the contrast case: no coordinator fault tolerance, presumed abort (ADR-03), blocking in 2PC, non-blocking only under fail-stop in 3PC, and a minority that blocks under partition (§31, I13). Its decision log is an in-memory log with a force() barrier, where Postgres uses a WAL fsync (§31).

If you only remember three things

A Yes vote is a promise that must be forced to the log before it is sent, and that promise is exactly why 2PC blocks when the coordinator dies at the wrong moment (P1, P2, FM-1). 3PC's extra phase lets a participant that holds PreCommit finish on its own, but only under fail-stop and with no partition, so it trades blocking for a quorum rule that makes a split network stall instead of disagree (P6, P7, I13, MM4). The design is a deliberately small, deterministic simulator whose job is to make each of those claims, and each limit, a reproducible fixture (§1, §2, P10).

Words used here

  • Atomic commit — all participants in a transaction reach the same outcome, all commit or all abort.
  • Coordinator — the node that collects votes and makes the decision.
  • Participant — a node that votes on a transaction and applies its outcome.
  • Cohort — the fixed set of participants in one transaction (I12).
  • Vote — a participant's Yes or No answer to Prepare or CanCommit.
  • Prepared — the state after voting Yes and before the decision arrives; a promise, not just a label (MM1).
  • Blocking problem — 2PC's failure: a participant that voted Yes cannot safely proceed without the coordinator's decision.
