73 — Two-Phase + Three-Phase Commit from Scratch

Project Number: 73

Project Name: Two-Phase + Three-Phase Commit from Scratch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch, an in-process implementation of the two classical distributed atomic-commit protocols — Two-Phase Commit (2PC) and Three-Phase Commit (3PC, Skeen variant) — with real coordinator and participant state machines, durable write-ahead logging, presumed-abort recovery, timeout-driven termination, and a deterministic fault-injecting network simulator, in order to empirically demonstrate the safety guarantees, the liveness guarantees, and the specific failure modes (2PC's blocking problem; 3PC's partition-unsafety) that the literature attributes to each protocol.

Phase-0 Deliverable (crates)

  1. tpc-core — NodeId/TxnId identifiers, message enums, DurableLog abstraction, TpcError, logical clock.
  2. tpc-2pc — Coordinator2Pc / Participant2Pc state machines.
  3. tpc-3pc — Coordinator3Pc / Participant3Pc state machines (Skeen pre-commit phase).
  4. tpc-sim — deterministic in-process transport, fault injector, fixture runner.
  5. tpc-bench — performance harness driving the §28 M1–M12 targets.

Non-Goals

Not a production resource-manager driver; not an XA-compliant client library; no query engine, no on-disk B-tree, no real replication. Fail-stop + omission fault model only (I10) — not a Byzantine-fault study.

Deployment Model

Single OS process. All "nodes" are in-process tasks connected by a simulated, fault-injecting message bus (tpc-sim, §14). No real sockets, no real disk; the log is an in-memory append-only structure with an explicit force() barrier standing in for fsync() (ADR-08).

Target Users

Systems engineers and distributed-systems students studying atomic commit internals; implementers evaluating whether to build 2PC/3PC/XA support into a resource manager; instructors needing a runnable, inspectable reference.

Language & Rationale

Rust (ADR-01). Rationale: sum-type enums make state-machine exhaustiveness (P8) a compiler-checked property via match; ownership makes message-passing simulation (no shared mutable state) natural; no GC pauses to confound deterministic-timing tests (P10). Rejected: Go (interface-based states are not exhaustively checked by the compiler); Java (GC pauses complicate deterministic simulation); Python (no compile-time state safety, too slow for the property-test volume in §26).

Prerequisites

Familiarity with: ACID transaction semantics; message-passing concurrency; write-ahead logging; basic distributed-systems failure models (crash-stop vs. Byzantine); Rust ownership/enum pattern matching.

Timeline

10 phases (§12–§21), sequential, no parallel phases (each phase's fixtures gate the next). See Appendix B (§38) for per-phase duration and exit criteria.

2. Why Build This

2PC is the load-bearing primitive underneath every distributed database's cross-shard transaction (Spanner, CockroachDB, TiDB, YugabyteDB) and every message broker's exactly-once write path (Kafka transactions). Its failure mode — the coordinator crashing between "all voted yes" and "decision broadcast" — is the canonical example of blocking in distributed systems, and understanding it is a prerequisite for understanding why Paxos Commit (Gray & Lamport 2006) and Percolator-style lock tables (Peng & Dabek 2010) exist at all. 3PC (Skeen 1981) is the standard teaching example of "adding a phase buys non-blocking-under-fail-stop but not partition tolerance" — a lesson that generalizes directly to the FLP/CAP boundary work students meet later. Building both from scratch, side by side, with durable logs and a real crash-injecting harness, converts "2PC can block" from a slogan into a reproduced, logged, inspectable event.

Cross-links: PostgreSQL's PREPARE TRANSACTION (§31) is textbook 2PC with presumed abort; Kafka's TransactionCoordinator (§31) is 2PC adapted to a log-structured broker; Spanner (§31) layers 2PC on top of per-shard Paxos groups — precisely the Paxos Commit idea generalized. Calibration value: any engineer who has built this project can read the commit-path code of any of those four systems and recognize every state transition.

What Mastery Looks Like

  • Can explain, from the log format alone (§13), why a recovering 2PC coordinator with no decision record is safe to unilaterally abort (I8, Phase 1 §13).
  • Can name the exact message and log-write ordering that makes 2PC's coordinator-crash window "the blocking problem" (Phase 4 §16, Phase 5 §17).
  • Can explain why 3PC's extra PreCommit phase (Phase 6 §18) removes that blocking window under fail-stop but reintroduces risk under partitions (Phase 7 §19).
  • Can trace a Prepare → Prepared → Commit → Ack round and a CanCommit → PreCommit → DoCommit round side by side and point at the exact frame where they diverge (§8).
  • Can articulate why Paxos Commit (Phase 8 §20) replaces the single coordinator with a replicated one instead of adding a phase, and why that is a different fix for a different problem.
  • Can run the chaos suite (Phase 9 §21) and predict, before looking, which injected fault produces a stuck (blocked) participant vs. an auto-committing one.

Boxes: tpc-sim owns message delivery order, latency, drop/duplicate/ reorder faults, and the logical clock all timeouts read (Phase 2 §14); it is the only component with fault-injection authority (I10). Coordinator owns the transaction's decision authority — reads no external state at decision time, only its own log and collected votes (I4). Participant owns local resource-manager state (simulated), and issues its own log writes independent of the coordinator's log (I5, I9). DurableLog per node is an append-only record store; coordinator and participant logs are never shared memory — each is force-written by its own owner (P1). Concurrency boundary: every FSM method is single-threaded and re-entrant only through the sim's message loop (P12) — no FSM performs I/O itself. Persistence boundary: log records survive force(); anything before the last forced record survives a simulated crash, anything after does not (Phase 1 §13). Trust boundary: all nodes are mutually trusted (fail-stop, not Byzantine — I10, ADR-06).

6. Design Principles

  • P1 — Write-Ahead Before Send (WAB). Rule: a node persists (force()) any record that promises or announces a decision before transmitting the message that carries that promise. Tradeoff: extra log-write latency per hop vs. crash-safety. Operational implication: log force() is on the critical path of every Prepared/Commit/Abort/PreCommit send. Violation consequence: a node can promise something it forgets on crash, breaking I4/I5.
  • P2 — Vote Once, Vote Final. Rule: a Yes vote is an irrevocable promise to accept the coordinator's eventual decision; a No vote is a unilateral, unconditional abort right exercised before voting. Tradeoff: removes participant autonomy after voting Yes (source of blocking). Operational implication: no "change my vote" message exists in §11. Violation consequence: two participants could reach opposite terminal states — breaks I1.
  • P3 — Coordinator Decision Is Single Source of Truth. Rule: once the coordinator logs Commit or Abort, that record is final and is rebroadcast (not recomputed) until every participant acks. Tradeoff: no coordinator "changes its mind" recovery path — simpler, but a lost log record cannot be reconstructed from votes alone (they were transient). Violation consequence: two different recoveries could compute two different decisions — breaks I1/I4.
  • P4 — Presumed Abort by Default. Rule: absence of a coordinator log record for a TxnId on recovery is interpreted as Abort (Mohan et al. 1986). Tradeoff: saves a log write for the (assumed) common abort case, at the cost of needing a positive record for commit. Operational implication: coordinator never logs Abort on the pre-vote path — only silence. Violation consequence: without this rule, unresolved log gaps are ambiguous — breaks I8.
  • P5 — Timeout Governs Liveness, Not Safety. Rule: timeouts select which safe action to try next (retry, query, unilaterally abort); they never authorize a decision that violates a logged commitment. Tradeoff: some timeout-triggered actions are themselves blocked (2PC participant post- vote) — that block is intentional, not a bug. Violation consequence: a timeout that overrides a logged Yes vote could commit on one node and abort on another — breaks I1/I3.
  • P6 — Pre-Commit Decouples Vote from Commit (Skeen). Rule: 3PC inserts a PreCommit phase between "all voted yes" and "commit", so no participant is ever one message away from an unrecoverable decision without at least one witness having heard the same thing. Tradeoff: one more round trip and one more log write per transaction (§4). Violation consequence: without it, 3PC degenerates to 2PC's blocking window — this is what removes I6's non-blocking guarantee.
  • P7 — Quorum-Bounded Termination. Rule: 3PC's termination protocol (on coordinator timeout) requires a participant to reach a quorum of peers before deciding, not just query one peer. Tradeoff: needs majority connectivity, so it fails safe (blocks) rather than fails unsafe under a network partition. Violation consequence: deciding from a single minority-side peer risks disagreement with the majority side — breaks I7, and is exactly the domain-guidance-flagged "unsafe under partitions" case if skipped.
  • P8 — State-Machine Exhaustiveness. Rule: every (State, Event) pair has a defined transition; unhandled combinations are a specification defect, never a runtime panic. Tradeoff: larger transition tables up front. Violation consequence: an unhandled message in production becomes a silent stuck transaction (FM-4).
  • P9 — Idempotent Message Handlers. Rule: re-delivery of Commit, Abort, PreCommit, or DoCommit to a node already in the target state is a no-op ack, never a re-execution. Tradeoff: handlers must check current state before acting, adding a branch per handler. Violation consequence: duplicate delivery (I10's reorder/duplicate fault) could double-apply a side effect.
  • P10 — Deterministic Simulation Over Real Time. Rule: all timeouts and scheduling in tpc-sim read a seeded logical clock, never SystemTime::now(). Tradeoff: cannot model true wall-clock skew. Violation consequence: flaky, unreproducible fixture failures (violates §26's determinism requirement).
  • P11 — Fail-Stop Assumption Is Explicit and Bounded. Rule: every safety proof in this spec assumes crash-stop nodes and (for 3PC's non-blocking claim specifically) no network partition; the boundary is stated inline everywhere the guarantee is cited. Tradeoff: none of this protects against a partitioned-but-alive node claiming a stale role. Violation consequence: citing 3PC's non-blocking property without the fail-stop-and-no-partition qualifier is the single most common textbook error this project exists to correct (§2).
  • P12 — Separation of Protocol Logic from Transport. Rule: Coordinator*/ Participant* FSMs return intents (structs describing "send M to peer P"); only tpc-sim performs the actual send/log I/O. Tradeoff: an extra indirection layer. Violation consequence: FSMs become untestable without a live network, defeating §26's deterministic-replay requirement.
  • P13 — Log Truncation Only After Global Completion. Rule: a coordinator garbage-collects a TxnId's log records only after every participant has acked the terminal decision. Tradeoff: log grows until the slowest participant acks. Violation consequence: premature truncation removes the only record a recovering coordinator needs to keep rebroadcast going — breaks I4/I9.

8.5 Worked Example — 2PC, 3 Participants, Clean Commit

Frame-by-frame: t0 Coordinator logs BEGIN{A,B,C}, sends Prepare ×3. t1 A,B,C log PREPARED, reply Prepared. t2 Coordinator collects 3/3 Yes, logs COMMIT, sends Commit ×3. t3 A,B,C log COMMIT, apply, reply Ack. t4 Coordinator collects 3/3 Ack, logs DONE. Total: 2 round trips, 2 coordinator log writes (BEGIN batched with Prepare send, COMMIT, DONE — 3 writes), 2 participant log writes each.

8.6 Worked Example — 3PC, 3 Participants, Coordinator Crash After PreCommit

t0–t2 as above through PreCommit broadcast; all 3 participants log PRECOMMIT and reply AckPreCommit. t3 coordinator crashes before collecting all acks / before sending DoCommit. t4 participants' precommit timeouts fire (I6); Participant3Pc::timeout_recover autonomously transitions PreCommitted → Committed without coordinator input, because every participant that reached PreCommitted knows every other participant voted Yes (Skeen's invariant) — this is the non-blocking property, fail-stop-only (P11).

8.7 Malformed-Input Example

Ack message for a TxnId not present in the coordinator's TxnTable (replay of a stale/duplicated message after DONE+truncation, I10's duplicate fault) → handler returns TpcError::UnknownTxn, logged at WARN, no state change (P9 — idempotent no-op, not a crash).

8.8 Failure-Path Example

Participant B votes No (VoteAbort) while A and C are still in Prepared. Coordinator's Preparing state receives the No, transitions to Aborting immediately (does not wait for A/C's votes — I2 lets a No short- circuit), logs ABORT, sends Rollback to A and C (who have not yet voted, so I2 also lets them apply their own pending pre-vote abort if their timeout fires first — either path is safe, both converge to ABORT).

struct NodeId(u32);                    // Copy, Eq, Hash
struct TxnId(u64);                     // Copy, Eq, Hash, monotonic per coordinator

enum LogRecord {
    Begin { txn: TxnId, cohort: Vec<NodeId> },
    Voted { txn: TxnId, vote: Vote },        // participant-side
    PreCommitted { txn: TxnId },              // 3PC only
    Decision { txn: TxnId, outcome: Outcome },
    Done { txn: TxnId },
}
enum Vote { Yes, No }
enum Outcome { Commit, Abort }

enum TwoPhaseMsg {
    Prepare(TxnId),
    Prepared(TxnId, NodeId),
    VoteAbort(TxnId, NodeId),
    Commit(TxnId),
    Rollback(TxnId),
    Ack(TxnId, NodeId),
}

enum ThreePhaseMsg {
    CanCommit(TxnId),
    YesCanCommit(TxnId, NodeId),
    NoCanCommit(TxnId, NodeId),
    PreCommit(TxnId),
    AckPreCommit(TxnId, NodeId),
    DoCommit(TxnId),
    HaveCommitted(TxnId, NodeId),
    Abort(TxnId),
    AckAbort(TxnId, NodeId),
}
trait DurableLog {                     // owned exclusively by one node; !Send across nodes
    fn append(&mut self, r: LogRecord); // in-memory push
    fn force(&mut self);                // simulated fsync barrier (ADR-08)
    fn entries_for_txn(&self, t: TxnId) -> &[LogRecord];
}

trait LogicalClock {                   // ADR-07
    fn now_tick(&self) -> u64;
    fn advance(&mut self, ticks: u64);
}

enum Coordinator2PcState { Idle, Preparing, Committing, Aborting, Done }
enum Participant2PcState { Idle, Prepared, Committed, Aborted }
enum Coordinator3PcState { Idle, CanCommitting, PreCommitting, DoCommitting, Aborting, Done }
enum Participant3PcState { Idle, WaitingPreCommit, PreCommitted, Committed, Aborted }

enum TpcError { UnknownTxn, DuplicateVote, InvalidTransition { from: String, on: String }, LogForceFailed }

enum FaultInjector {                   // I10 — omission/crash-stop only
    DropMessage { txn: TxnId, kind: &'static str },
    DelayMessage { txn: TxnId, ticks: u64 },
    DuplicateMessage { txn: TxnId },
    ReorderWindow { size: usize },
    CrashNode { node: NodeId, after_tick: u64 },
}

Ownership: each DurableLog instance is owned by exactly one node's FSM wrapper; never shared (I9, §3). Concurrency: FSM step functions take &mut self and a single event — no internal threading (P12). Serialization: LogRecord and both message enums derive a stable tag-based encoding for fixture (de)serialization (ADR-17); wire format is not versioned pre-1.0 (§25).

13. Phase 1 — Durable Log & Recovery Substrate

13.1 Objectives

Implement DurableLog for real (in-memory Vec<LogRecord> + force() barrier, ADR-08); implement recovery-replay (entries_for_txn, full-log scan on restart); establish the crash model (a "crash" discards everything not yet force()-d).

13.2 Detailed Implementation Steps

  1. Implement InMemoryLog: DurableLog (§11) — append() pushes to an uncommitted buffer; force() moves the buffer into the durable Vec (models fsync per P1).
  2. Implement a CrashModel helper in tpc-sim::fault that, on CrashNode, drops the uncommitted buffer and keeps only forced records — this is the mechanism behind I8/I9.
  3. Implement entries_for_txn(TxnId) as a linear scan (bounded by §4's 10,000-txn ceiling; no index needed at this scale, see §29).
  4. Implement recovery-replay: on restart, scan the full log and rebuild the TxnTable (open transactions and their last known record) — feeds Phase 4/7's recover() methods.
  5. Write fixtures/log_replay_roundtrip.json: append N records, simulate crash before/after force(), assert exactly the forced subset survives.

13.3 Deliverable

Working InMemoryLog, CrashModel, and a recovery-replay function usable by both 2PC and 3PC coordinators/participants in later phases.

13.4 Acceptance Criteria

fixtures/log_replay_roundtrip.json passes: records appended-but-not-forced before a simulated crash are absent after replay (0 of N); records forced before the crash are all present (N of N); replay completes in ≤ 200 ms wall-clock for a 10,000-entry log (§4).

13.5 Conformance Fixtures

fixtures/log_replay_roundtrip.json (forced-vs-unforced survival); fixtures/sim_seed_determinism.json (same seed ⇒ identical replay order, feeds P10).

13.6 Pitfalls

Calling force() implicitly inside append() (defeats the whole point of testing the pre-force crash window — I9's "never mutated, but also never assumed durable before forced" distinction collapses). Forgetting that entries_for_txn must return records in log order (append order), not insertion order into any secondary index.

13.7 Performance Concerns

Linear-scan recovery is O(log size); acceptable at the §4 10,000-txn ceiling (≤ 200 ms) but is the first-named bottleneck in §29's scaling analysis if the ceiling is raised.

13.8 Edge Cases

Empty log recovery (fresh node, zero records) must yield an empty TxnTable, not an error. A log containing only a Begin record with no subsequent decision (coordinator crashed before deciding) must replay as an in-flight transaction eligible for I8's presumed-abort path in Phase 4.

13.9 Failure Analysis

LogForceFailed (§11 TpcError) models a hypothetical fsync failure; Phase 1 only defines the error variant — real disk-failure injection is out of scope (PhaseDeferred("§13")'s real-file backing would be needed to make this fault meaningful).

13.10 Operational Notes

Log size is the primary operational metric to watch pre-truncation (P13); expose log_entry_count per node in §24's metrics set from this phase onward.

15. Phase 3 — 2PC Participant State Machine

15.1 Objectives

Implement Participant2Pc (Idle → Prepared → Committed/Aborted) fully, including the pre-vote unilateral-abort path (I2) and idempotent Commit/Rollback handlers (P9).

15.2 Detailed Implementation Steps

  1. Implement handle_prepare(): force-write Voted{Yes} to log (P1/I5) before replying Prepared — this is the row-for-row implementation of I5.
  2. Implement the pre-vote path: if a local force_abort flag is set (test hook) or a local integrity check fails, log Voted{No} and reply VoteAbort instead — exercises I2.
  3. Implement handle_commit() / handle_rollback(): idempotent — if already Committed/Aborted, re-ack without re-applying (P9); apply Outcome, log Decision, reply Ack.
  4. Implement post-vote pre-decision timeout: per P5/I3, the only safe action is to keep waiting or query the coordinator — never unilaterally abort after voting Yes.
  5. Write fixtures/2pc_abort_vote_no.json: 3-participant cohort, one forces VoteAbort, assert all 3 converge to Aborted.

15.3 Deliverable

Participant2Pc FSM passing all example fixtures for commit and abort paths under zero faults, ready to be driven by Coordinator2Pc in Phase 4.

15.4 Acceptance Criteria

fixtures/2pc_abort_vote_no.json passes: all 3 participants reach Aborted (3/3, matching I1); log order assertion confirms Voted precedes any sent Prepared/VoteAbort message (I5) in 100% of traced sends.

15.5 Conformance Fixtures

fixtures/2pc_abort_vote_no.json; a new fixtures/2pc_participant_idempotent_commit.json (duplicate Commit delivery via DuplicateMessage fault → single applied side effect, one re-sent Ack, per P9).

15.6 Pitfalls

Replying Prepared before force() completes (violates I5 — the single most common student bug in this project, per §2's design intent). Re-applying the commit side effect on duplicate Commit delivery instead of detecting already-Committed state (violates P9).

15.7 Performance Concerns

Each handle_prepare() call's force() is on the round-trip's critical path — this is the dominant cost in the §4 p50/p99 latency targets for 2PC; first-named contributor in §28's M targets.

15.8 Edge Cases

A Commit/Rollback arriving for a TxnId the participant never saw Prepare for (possible under ReorderWindow faults) — handled as TpcError::UnknownTxn, not applied (mirrors §8.7).

15.9 Failure Analysis

Participant crash between logging Voted{Yes} and sending Prepared — on restart, replay finds the vote logged but no ack of having sent it; recovery must re-send Prepared (idempotent from the coordinator's side per P9) rather than silently drop it — this is FM-3's originating scenario.

15.10 Operational Notes

Expose participant_state{txn} as a per-transaction gauge from this phase onward (feeds §24 dashboards); this is the primary signal operators watch for "stuck in Prepared" (the blocking problem, formalized in Phase 5 §17).

16. Phase 4 — 2PC Coordinator State Machine + Presumed Abort

16.1 Objectives

Implement Coordinator2Pc (Idle → Preparing → Committing/Aborting → Done) including presumed-abort recovery (ADR-03, P4, I8) per Gray 1978 / Mohan et al. 1986.

16.2 Detailed Implementation Steps

  1. Implement begin(): log Begin{cohort}, broadcast Prepare — note per ADR-03/P4, this is the only pre-decision log write; no Preparing- state record beyond Begin is logged (that's what makes abort "presumed" rather than logged).
  2. Implement handle_vote(): collect votes; on unanimous Yes, force-write Decision{Commit} then broadcast Commit (I4); on any No, force-write Decision{Abort} then broadcast Rollback — short-circuits without waiting for remaining votes (mirrors §8.8).
  3. Implement handle_ack(): track per-participant acks; on all-acked, log Done, eligible for truncation (P13).
  4. Implement recover(): on restart, for each open TxnId found in Begin-only state (no Decision record), presume Abort and broadcast Rollback (I8/P4) — this is the row-for-row implementation of Mohan et al. 1986's presumed-abort optimization.
  5. Write fixtures/2pc_coord_crash_recover.json: crash coordinator after vote collection but before decision-log write; assert recovery presumes Abort and all participants converge to Aborted.

16.3 Deliverable

Coordinator2Pc FSM with presumed-abort recovery, passing commit, abort, and crash-recovery fixtures against the Phase 3 Participant2Pc.

16.4 Acceptance Criteria

fixtures/2pc_coord_crash_recover.json passes: recovery decision is Abort in 100% of runs where the crash occurred before a Decision log write (I8); fixtures/2pc_commit_basic.json passes: 3/3 participants reach Committed in ≤ 500 µs p99 (§4).

16.5 Conformance Fixtures

fixtures/2pc_commit_basic.json; fixtures/2pc_coord_crash_recover.json.

16.6 Pitfalls

Logging a Preparing-state marker "just in case" (defeats presumed abort's log-write savings — ADR-03's whole rationale). Broadcasting Commit before force()-ing Decision{Commit} (violates I4 — the coordinator-side twin of Phase 3's I5 pitfall).

16.7 Performance Concerns

Presumed abort (ADR-03) removes one log write from the abort path relative to plain 2PC — quantify this saving in §28's M targets as a direct before/after comparison.

16.8 Edge Cases

A vote arriving after the coordinator already decided (late Prepared from a delayed participant, DelayMessage fault) — coordinator must resend its already-logged decision (P3) rather than reprocess the vote.

16.9 Failure Analysis

Coordinator crash after logging Decision{Commit} but before broadcasting — recovery must find the logged decision and rebroadcast Commit to all participants (P3), not re-run vote collection. This is the non-blocking recovery case; contrast with Phase 5's actual blocking case (crash before the decision is knowable at all, mid-vote-collection, with a participant stuck in Prepared).

16.10 Operational Notes

Presumed-abort recovery should be logged at INFO with the TxnId and inferred outcome for audit (feeds §24's structured-logging requirement); operators should alert if presumed-abort rate deviates sharply from historical baseline (could indicate a systemic coordinator crash loop, FM-2).

17. Phase 5 — 2PC Timeout, Recovery & the Blocking Problem

17.1 Objectives

Implement participant-side post-vote timeout handling and demonstrate, empirically, 2PC's namesake blocking problem: a participant that voted Yes and then loses contact with the coordinator has no safe unilateral move (P5/I3) until the coordinator (or an operator) resolves it.

17.2 Detailed Implementation Steps

  1. Implement Participant2Pc's post-vote timeout handler: on timeout while Prepared, the only actions available are (a) re-query the coordinator, (b) keep waiting — never (c) unilaterally decide (P5/I3).
  2. Implement a coordinator-query message/response so a blocked participant can at least confirm "coordinator still unreachable" vs. "coordinator responded, here is the decision" — does not resolve the block by itself if the coordinator truly is down.
  3. Instrument Participant2Pc with a blocked_since_tick field, surfaced for the §24 dashboard.
  4. Write fixtures/2pc_coord_crash_recover.json's counterpart: a coordinator crash scenario with no recovery attempted within the fixture's tick budget — assert the participant remains Prepared (blocked) indefinitely, not that it incorrectly resolves itself.
  5. Document, inline at this step, the theoretical result this reproduces: Skeen & Stonebraker 1983's formal statement that no fail-stop atomic commit protocol with a single coordinator round can be non-blocking.

17.3 Deliverable

Demonstrated, fixture-verified 2PC blocking scenario: participant stuck in Prepared with no safe unilateral exit, resolved only by coordinator recovery (Phase 4's recover()) or manual operator intervention (§23/FM-1).

17.4 Acceptance Criteria

Blocking fixture passes: participant state remains exactly Prepared (not Committed, not Aborted) for the entire fixture tick budget (e.g. 10,000 ticks) absent coordinator recovery; the moment Coordinator2Pc::recover() runs (Phase 4), the participant unblocks within one message round trip.

17.5 Conformance Fixtures

New fixtures/2pc_participant_blocked_indefinitely.json (no recovery attempted, assert stuck state); reuse fixtures/2pc_coord_crash_recover.json for the resolved case.

17.6 Pitfalls

"Fixing" the blocking problem by adding an ad-hoc unilateral-decide timeout on the participant (this is not a bug fix — it is a correctness violation of I1/I3, and is precisely the mistake 3PC's extra phase exists to solve correctly).

17.7 Performance Concerns

None new — this phase's contribution is a liveness/availability characterization, not a latency number; recorded qualitatively in §29's bottleneck ranking (coordinator becomes the availability bottleneck for the whole cohort during the blocked window).

17.8 Edge Cases

Multiple participants blocked simultaneously (coordinator down, cohort of 5) — all 5 remain Prepared; recovery must resend the decision to all 5, not just the first responder.

17.9 Failure Analysis

This entire phase is a failure-analysis exercise: the "failure mode" under study is FM-1 (coordinator crash mid-decision-window), and its symptom is exactly this phase's fixture output — one or more participants holding locks/resources indefinitely.

17.10 Operational Notes

Real systems (PostgreSQL's orphaned PREPARE TRANSACTIONs, §5 R1) manifest this exact scenario as long-held locks and a growing vacuum horizon; operational runbooks (§24) must include a manual-resolve procedure (query every participant, if quorum of participants agree on outcome, apply it) — this manual procedure is itself unsafe in general (no coordinator-log guarantee) and is explicitly flagged as a break-glass action.

18. Phase 6 — 3PC Participant State Machine (Skeen Pre-Commit)

18.1 Objectives

Implement Participant3Pc (Idle → WaitingPreCommit → PreCommitted → Committed/Aborted) including the autonomous-commit timeout from PreCommitted (I6) that is 3PC's entire value proposition over 2PC.

18.2 Detailed Implementation Steps

  1. Implement handle_can_commit(): vote Yes/No (mirrors Phase 3's handle_prepare); force-write Voted before replying (P1, same as I5).
  2. Implement handle_pre_commit(): force-write PreCommitted to log before replying AckPreCommit (P6 — this is Skeen's added durability point; the exact analog of I5 one phase later).
  3. Implement handle_do_commit(): apply, log Decision{Commit}, reply HaveCommitted (idempotent, P9).
  4. Implement timeout_recover(): while PreCommitted and timeout fires with no DoCommit received, autonomously transition to Committed (I6) — safe only because reaching PreCommitted at all implies every cohort member voted Yes (P6's structural guarantee).
  5. Write fixtures/3pc_precommit_crash_autocommit.json: coordinator crashes after broadcasting PreCommit but before DoCommit; assert every participant autonomously reaches Committed without further coordinator input.

18.3 Deliverable

Participant3Pc FSM demonstrating the non-blocking property under fail-stop

  • no partition (I6, P11), contrasted directly against Phase 5's 2PC blocking fixture.

18.4 Acceptance Criteria

fixtures/3pc_precommit_crash_autocommit.json passes: 100% of participants that received PreCommit reach Committed within their configured precommit timeout (§4: 150 ticks) with zero further coordinator messages; fixtures/3pc_commit_basic.json passes with p99 ≤ 900 µs (§4).

18.5 Conformance Fixtures

fixtures/3pc_commit_basic.json; fixtures/3pc_precommit_crash_autocommit.json.

18.6 Pitfalls

Allowing timeout_recover() to fire from WaitingPreCommit (pre-vote- completion state) instead of only from PreCommitted — this would reintroduce exactly the blocking-problem-shaped unsafe unilateral decision P6 exists to prevent.

18.7 Performance Concerns

The extra PreCommitted log write (vs. 2PC's Phase 3) is the quantified cost of non-blocking-under-fail-stop; recorded as the 2PC-vs-3PC latency delta in §28's M targets (§4 already budgets 3PC at ~1.8× 2PC's p99).

18.8 Edge Cases

A participant that voted No never reaches WaitingPreCommit at all — verify its log shows Voted{No} → Decision{Abort} directly, with no PreCommitted record ever written (structural guarantee, not just a runtime coincidence).

18.9 Failure Analysis

Participant crash between logging PreCommitted and replying AckPreCommit — recovery must re-send AckPreCommit (idempotent from coordinator's perspective, P9) and remains eligible for timeout_recover() if the coordinator never follows up.

18.10 Operational Notes

Expose precommit_autocommit_total (I6's telemetry counter, §7) from this phase; a nonzero rate is expected and healthy under coordinator churn — unlike 2PC's blocked_since_tick gauge (Phase 5), this counter incrementing is 3PC working as designed, not an incident.

19. Phase 7 — 3PC Coordinator State Machine + Non-Blocking Termination Protocol

19.1 Objectives

Implement Coordinator3Pc (Idle → CanCommitting → PreCommitting → DoCommitting → Done/Aborting) and the quorum-bounded termination protocol (P7/I13) that participants run cooperatively when the coordinator itself times out.

19.2 Detailed Implementation Steps

  1. Implement begin()/handle_vote() mirroring Phase 4's Coordinator2Pc through the CanCommit phase (reuses the same short-circuit-on-No pattern, §8.8).
  2. Implement the PreCommit broadcast on unanimous Yes: force-write Decision-adjacent PreCommitted marker before sending (P1/P6).
  3. Implement handle_ack_precommit(): on all acked, force-write Decision{Commit}, broadcast DoCommit (mirrors I4 one phase later).
  4. Implement the termination protocol entry point invoked by participants (not the coordinator) on coordinator timeout: a participant queries its peers; only if it can reach a quorum and that quorum's states agree does it decide (P7) — reaching a quorum where any member is still WaitingPreCommit (pre-vote-complete) forces Abort; reaching a quorum where any member is PreCommitted or beyond forces Commit (I7).
  5. Implement recover(): on coordinator restart, resume at DoCommitting if a PreCommitted marker was logged, else presume Abort (mirrors P4, adapted to 3PC's extra state).
  6. Write fixtures/3pc_abort_vote_no.json and extend the chaos matrix (Phase 9, §21) with a minority-partition scenario demonstrating I13's "blocks rather than disagrees" partition-safety behavior.

19.3 Deliverable

Coordinator3Pc FSM plus a participant-driven termination protocol, completing the 3PC implementation and exposing the partition-unsafety boundary the domain guidance flags (3PC is non-blocking under fail-stop, not under partitions).

19.4 Acceptance Criteria

fixtures/3pc_abort_vote_no.json passes: 3/3 participants reach Aborted; minority-partition fixture (§21) demonstrates that a minority-side participant running the termination protocol blocks (cannot reach quorum) rather than disagrees with the majority side — i.e., I13 holds: zero disagreement events, nonzero blocked-pending-quorum events.

19.5 Conformance Fixtures

fixtures/3pc_abort_vote_no.json; fixtures/chaos_partition_matrix.json (shared with Phase 9, minority-partition rows specifically exercised here).

19.6 Pitfalls

Letting the termination protocol decide from a single peer's state instead of a quorum (silently reintroduces exactly the disagreement risk P7/I13 exist to prevent — this is the single most common "3PC is non-blocking, period" misconception this phase exists to correct, per §2).

19.7 Performance Concerns

Termination-protocol quorum queries add an extra round of peer-to-peer messages only in the timeout path (not the happy path) — no impact on §4's p50/p99 happy-path targets; quantify separately as a recovery-latency metric in §28.

19.8 Edge Cases

Exactly half the cohort on each side of a partition (no quorum possible on either side) — both sides must block, not just the minority (I13 is symmetric: it protects against disagreement, and a tied split has no majority side either).

19.9 Failure Analysis

This phase's fixture set is the empirical proof of the domain guidance's "3PC unsafe under partitions" claim being about liveness, not safety — I7 (no disagreement) holds throughout every partition fixture; only I6's non-blocking liveness property is what a partition can defeat (participants block instead of making progress, but never disagree).

19.10 Operational Notes

Any real deployment of 3PC-style termination must define its quorum size operationally (typically ⌈(N+1)/2⌉) and alert when a transaction sits in blocked-pending-quorum beyond an SLO threshold (§24) — indistinguishable operationally from 2PC's blocking problem until quorum becomes reachable again.

29. Scalability Analysis

Constant regardless of cohort size N: per-message log-record size (≤ 256 B, §4); per-participant local state machine complexity (O(1) states).

Grows with N (Big-O): coordinator fan-out per round is O(N) messages; vote/ack collection is O(N) coordinator-side bookkeeping; termination protocol quorum query is O(N) peer messages in the worst case.

Named bottlenecks, in order: (1) linear-scan log recovery (§13.7) — the first ceiling hit as transaction-log size grows past §4's 10,000-txn budget; (2) coordinator fan-out — O(N) broadcast cost dominates at large cohort sizes (§4 caps N at 64 for this reason); (3) chaos-matrix suite wall-clock (§21.7) — grows with the product of fault types and crash points, not with protocol cohort size, and is a test-infrastructure bottleneck, not a protocol one.

Horizontal scaling: not applicable to a single coordinator's decision authority (2PC/3PC are inherently single-coordinator-per-transaction protocols by construction, P3) — horizontal scale-out is a different- transaction concern (many concurrent transactions, each single- coordinator), bounded by §4's 10,000 concurrent-txn ceiling, not a within- transaction concern.

Vertical scaling: recovery-replay time (M6) benefits directly from faster linear scan / more memory bandwidth; this is the primary vertical lever before a real index is needed.

Sharding: not modeled — a real deployment shards by TxnId range or hash across independent coordinator instances, each running its own independent 2PC/3PC rounds; out of scope for this single-process simulation (PhaseDeferred("§12")'s multi-host successor would need it).

Practical ceiling and levers: ceiling is §4's N=64 participants/txn and 10,000 concurrent txns; levers beyond it are (a) index the log instead of linear-scanning it (addresses bottleneck 1), (b) tree-structured broadcast instead of flat fan-out (addresses bottleneck 2, at the cost of extra latency hops), (c) parallelize the chaos matrix across CI workers (addresses bottleneck 3, test-infra only).

30. Mental Models & First Principles

  • MM1 — "Prepared is a promise, not a state." Compressed insight: once a participant votes Yes, it has made an external commitment it cannot retract, not merely entered a label called Prepared. Predicts: any design letting Prepared participants "change their mind" is unsafe. Bug class without it: ad-hoc unilateral-abort timeouts (§17.6). Resolving §: §7 (I3), §17.

  • MM2 — "Durability must precede disclosure." Compressed insight: never tell another node something your own crash could make untrue (P1). Predicts: every safe protocol has a force-write immediately before every promise-carrying send. Bug class without it: FM-2's log-order violations. Resolving §: §6 (P1), §13.

  • MM3 — "Silence needs a default, and the default is a design choice." Compressed insight: presumed abort isn't "no logging" — it's choosing which outcome silence means (Mohan et al. 1986). Predicts: any recovery scheme needs an explicit default-on-missing-record rule or it's ambiguous, not merely "simple." Bug class without it: recovery that can't distinguish "never started" from "committed, log lost." Resolving §: §6 (P4), §16.

  • MM4 — "One more phase buys a witness, not a guarantee." Compressed insight: 3PC's third phase doesn't eliminate the coordinator's importance — it ensures a participant is never the sole holder of decision- adjacent knowledge (Skeen 1981). Predicts: 3PC's protection degrades exactly when "ask a witness" becomes impossible (partition). Bug class without it: believing 3PC is unconditionally non-blocking. Resolving §: §6 (P6/P7), §18, §19.

  • MM5 — "Safety and liveness are different axes — partitions attack liveness first, safety only if you let them." Compressed insight: 3PC under partition blocks (loses liveness) by design so it does not disagree (lose safety) (I13). Predicts: any "fix" that makes a blocked minority decide anyway trades a liveness problem for a safety problem — strictly worse. Bug class without it: quorum-bypass "fixes" (FM-6). Resolving §: §7 (I7/I13), §19.

  • MM6 — "The coordinator's crash-recovery decision must be computable from its own log alone." Compressed insight: recovery cannot re-poll votes that were never durable (they're gone) — it can only trust what it wrote (P3). Predicts: any recovery design that "re-asks participants how they voted" as its primary mechanism is solving the wrong problem (that's the termination protocol's job, not ordinary recovery). Resolving §: §6 (P3), §16.

  • MM7 — "Idempotency is a property of the handler, not the transport." Compressed insight: you cannot rely on the network to deliver exactly once (I10); the handler itself must be safe under redelivery (P9). Predicts: any "we'll just make delivery reliable" plan still needs idempotent handlers, because reliable ≠ exactly-once. Bug class without it: FM-8's duplicate-apply bugs. Resolving §: §6 (P9), §15.

  • MM8 — "Adding fault tolerance to the coordinator is a different fix than adding a phase to the protocol." Compressed insight: Paxos Commit (Gray & Lamport 2006) solves coordinator-crash-tolerance by replicating the coordinator; Skeen's 3PC solves participant-blocking by adding a phase — these are orthogonal techniques answering different questions. Predicts: combining them (a replicated 3PC coordinator) is a coherent, real design point, not a contradiction. Resolving §: §20, §31, §34.

32. Back-of-Envelope Capacity Model

  1. Per-transaction log bytes (2PC, coordinator): 3 records (Begin, Decision, Done) × ≤ 256 B (§4) = ≤ 768 B/txn.
  2. Per-transaction log bytes (3PC, coordinator): 4 records (Begin, PreCommitted-marker, Decision, Done) × ≤ 256 B = ≤ 1,024 B/txn — 33% more than 2PC, directly from P6's extra phase.
  3. Per-participant log bytes (2PC): 2 records (Voted, Decision) × ≤ 256 B = ≤ 512 B/txn/participant.
  4. Per-participant log bytes (3PC): 3 records (Voted, PreCommitted, Decision) × ≤ 256 B = ≤ 768 B/txn/participant.
  5. Total log bytes at §4's ceiling (10,000 txns, N=3, 3PC): coordinator 1,024 B × 10,000 + participants 768 B × 3 × 10,000 = 10.24 MB + 23.04 MB = ≈ 33.3 MB — well within a single process's memory budget (in-memory model, ADR-08).
  6. 2PC happy-path message count (N participants): Prepare×N + Prepared/VoteAbort×N + Commit/Rollback×N + Ack×N = 4N messages (matches §20's 2N-round-trip framing: 2 round trips × 2 messages/hop... using the coordinator-fan-out convention, 4N one-way sends).
  7. 3PC happy-path message count (N participants): CanCommit×N + Yes×N + PreCommit×N + AckPreCommit×N + DoCommit×N + HaveCommitted×N = 6N messages — exactly 1.5× 2PC's message count, from one added phase (P6), matching M8's latency-delta budget.
  8. Recovery replay throughput needed to hit M6: 10,000 txns × (4 coordinator-side + up to 3×N participant-side, worst N=64) records ≈ 10,000 × 196 records ≈ 1.96M records scanned in ≤ 200 ms (§4) ⇒ ≥ 9.8M records/sec linear-scan throughput required — informs §29's "index the log" lever if this ceiling is ever raised.
  9. Coordinator fan-out cost at N=64 (§4's cap): 2PC = 4×64 = 256 messages/txn; 3PC = 6×64 = 384 messages/txn — both still far below any single-process message-bus saturation point at §4's 10,000-txn concurrency ceiling, but the O(N) growth (§29) is the reason N is capped at 64 rather than left unbounded.
  10. Termination-protocol worst-case message cost (3PC, N=64, quorum=33): one querying participant × 33 quorum peers × 1 round trip = 66 messages to resolve one blocked transaction — bounded by M11's ≤ 2-round-trip target.
  11. Chaos-matrix cell count (Phase 9): 2 protocols × ~4 crash-boundary points × 5 fault-injector variants ≈ 40 base cells, further multiplied by the minority-partition variants (§19/§21) — informs the §21.7 CI-parallelization lever once this exceeds the 30 s budget (M9).
  12. Presumed-abort log-write savings at scale: if 30% of transactions abort (illustrative workload assumption, not a measured claim) across 10,000 txns, presumed abort saves 1 log write × 3,000 aborted txns = 3,000 avoided force-write barriers versus plain 2PC (ADR-03) — directly informs M7's target.

34. Alternative Architectures (Roads Not Taken)

34.1 Paxos Commit (Replicated Coordinator)

Participant --Prepared--> [Acceptor1] [Acceptor2] [Acceptor3] (2F+1 acceptors)
                                \_________ Paxos instance per participant vote _________/
                                              |
                                         Learners -> Decision

Wins when: the coordinator itself, not just a single participant, must survive crashes without blocking the transaction (multi-datacenter deployments). Real system: Google Spanner's 2PC-over-Paxos-groups design (Corbett et al. 2012, §31). Rejected here: adds a full consensus implementation per decision — out of scope for a from-scratch teaching artifact whose lesson is the phase-count tradeoff (2PC vs. 3PC), not consensus implementation (PhaseDeferred("§20"), ADR-19).

34.2 Sagas (Compensating Transactions)

Step1 --> Step2 --> Step3 --> ... --> StepN   (forward path, no global lock)
  |         |          |                |
  v         v          v                v
Comp1 <-- Comp2 <-- Comp3 <-- ... <-- CompN   (compensation path on failure)

Wins when: transactions are long-lived and span services that cannot afford to hold locks/resources for the duration of a 2PC/3PC round (Garcia-Molina & Salem 1987). Real system: Temporal.io's saga-orchestration pattern for long-running distributed workflows. Rejected here: sagas trade atomicity for availability by design (compensations are not true rollback) — this project's entire purpose is studying atomic commit, so adopting a non- atomic model would erase the thing under study.

34.3 Percolator-Style Decentralized 2PC (Lock Table in Shared Storage)

Client A --prewrite(lock,write cols)--> [Shared Storage: Bigtable/TiKV]
Client B --reads lock col, resumes if A stalled-------------^

Wins when: horizontal scale across many concurrent coordinators matters more than a single dedicated coordinator's simplicity (Peng & Dabek 2010). Real system: TiKV/TiDB (§5 R4). Rejected here: requires a strongly-consistent shared storage substrate to host the lock table — this project deliberately has no storage layer beneath its own log (ADR-08), so there is nothing to put the lock table in.

34.4 Byzantine Commit (PBFT-Style)

Participant --request--> [Primary] --pre-prepare--> [Backup1..3f]
                              |--prepare (2f+1 quorum)-->|
                              |--commit  (2f+1 quorum)-->| --> reply

Wins when: participants may be malicious or arbitrarily faulty, not merely crash-stop (Castro & Liskov 1999) — adversarial multi-organization deployments (e.g., permissioned blockchains). Real system: Hyperledger Fabric's ordering service uses BFT-family consensus. Rejected here: this project's entire proof structure (§7's invariants, every phase's fixtures) assumes fail-stop/omission faults (I10, ADR-06); adopting Byzantine tolerance would require re-deriving every safety argument from scratch — explicitly deferred (PhaseDeferred("§34")).

36. Glossary

2PC — Two-Phase Commit; atomic commit protocol with a Prepare vote phase and a Commit/Abort decision phase (Gray 1978).

3PC — Three-Phase Commit; Skeen's non-blocking-under-fail-stop variant of 2PC adding a PreCommit phase (Skeen 1981).

Ack — acknowledgment message confirming a participant applied the coordinator's decision.

Acceptor — Paxos role that votes on proposed values; used per-decision in Paxos Commit (Gray & Lamport 2006).

Atomic commit — property that all participants in a transaction reach the same outcome (all commit or all abort).

Blocking problem — 2PC's namesake failure mode: a participant that voted Yes cannot safely proceed without the coordinator's decision.

Byzantine fault — arbitrary or malicious node behavior, beyond simple crash-stop (Castro & Liskov 1999); out of scope here (I10).

CanCommit — 3PC's first-phase message asking participants if they can commit (analog of 2PC's Prepare).

Chaos matrix — the Phase 9 fixture set covering every fault-injector variant × crash-boundary combination.

Cohort — the fixed set of participants in a single transaction (I12).

Coordinator — the node driving a transaction's vote collection and decision.

CrashNode — a FaultInjector variant simulating a node crash at a given tick.

DoCommit — 3PC's third-phase message instructing participants to commit after PreCommit acks are collected.

DurableLog — the append-only, force-write-barriered log abstraction each node owns (§11).

Fail-stop — a fault model where nodes either operate correctly or halt completely, never behaving incorrectly while "alive."

Fixture — a JSON file under fixtures/ specifying a scenario and its expected outcome, used for conformance testing.

Force / force() — the simulated durability barrier standing in for a real fsync() call (ADR-08).

FSM — finite state machine; the implementation pattern for both coordinator and participant roles.

Happy path — the zero-fault execution of a protocol round.

Heuristic decision — (historical term, not implemented here) a participant unilaterally deciding without coordinator authority; the scenario 2PC's design forbids (I3).

I1–I13 — this document's numbered system invariants (§7).

Idempotent handler — a message handler safe to invoke multiple times with the same input without changing behavior beyond the first call (P9).

LogRecord — the tagged-union type for every durable log entry (§11).

Logical clock — the seeded, tick-based timing source all timeouts read (P10, ADR-07), never wall-clock time.

M1–M12 — this document's numbered performance targets (§28).

Non-blocking — a protocol property where no correctly-operating node is forced to wait indefinitely for a crashed node, under a stated fault model (here: fail-stop, no partition — I6).

Omission fault — a message drop, delay, duplication, or reorder, but never corruption (I10).

P1–P13 — this document's numbered design principles (§6).

Participant — a node that votes on and applies a transaction's outcome.

Partition — a network fault preventing communication between two node groups while both remain individually alive.

Paxos Commit — Gray & Lamport's (2006) atomic commit protocol replacing the single coordinator with a Paxos-replicated one.

Percolator — Google's lock-table-based decentralized transaction model (Peng & Dabek 2010).

Prepare — 2PC's first-phase message asking participants to vote.

PreCommit — 3PC's second-phase message, sent after unanimous Yes votes, before final commit.

Prepared (state) — a participant's post-Yes-vote, pre-decision state.

Presumed abort — the optimization where a missing coordinator log record on recovery is interpreted as Abort (Mohan et al. 1986, P4).

Presumed commit — the inverse optimization (missing record ⇒ Commit), deferred in this project (ADR-04).

Quorum — a majority (or otherwise defined threshold) subset of a cohort, required by 3PC's termination protocol before deciding (P7).

Recovery — the process of rebuilding FSM state from the durable log after a crash.

Sagas — a compensating-transaction alternative to atomic commit for long-lived transactions (Garcia-Molina & Salem 1987).

Skeen's algorithm — the specific non-blocking commit protocol this project's "3PC" implements (Skeen 1981).

Termination protocol — the cooperative, quorum-bounded procedure participants run on coordinator timeout in 3PC (P7).

TxnId — the unique identifier for a transaction (§11).

Unilateral abort — a participant deciding Abort on its own authority, safe only before voting (I2).

Vote — a participant's Yes/No response to Prepare/CanCommit.

Wire format — the serialized representation of protocol messages, tag-based per ADR-13.

XA — the X/Open Distributed Transaction Processing standard's prepare/commit/rollback verb set (X/Open, 1991).
