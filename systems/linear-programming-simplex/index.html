In one paragraph

A linear-programming solver finds the best value of a linear objective (a cost or a profit) over variables that must obey linear equalities and inequalities, or proves that no such point exists or that the objective can improve forever (§1.1). This design is a from-scratch Rust workspace of 13 crates, usable as a command-line tool or an embedded library, single-threaded and deterministic (§1.4, §1.6, ADR-20, P10). It implements the whole simplex family: dense tableau, revised simplex over a factored basis, two-phase feasibility, bounded variables, dual-simplex warm starts, presolve and sensitivity analysis (§1.1). Its defining rule is that every final answer ships with a checkable certificate (P1, P5). Developers, analysts and students run it (§1.5).

The problem, concretely

Take the three-variable problem the blueprint uses throughout: maximise 5x1 + 4x2 + 3x3 subject to three "less-than" rows with right-hand sides 240, 270 and 420 (§8.7). By hand this is easy. The blueprint's point is that the easy version breaks in four ways once the problem is real.

First, size. Keeping the full table of numbers ("tableau") makes every step touch every cell. The blueprint's own example is Netlib problem SHARE2B (96 rows, 162 columns, 723 nonzeros): a dense step costs 96 × 162 = 15552 operations against roughly 428 per FTRAN (P4 example). Second, looping: on degenerate problems (a step makes zero progress) the textbook rule can revisit the same corners forever, as on Beale's 6-variable, 4-constraint cycling problem (P3, MM5). Third, silent wrongness: floating point drifts, and a solver that merely asserts "optimal" can return a wrong vertex with no warning (P2, P1). Fourth, repeated work: discarding the final basis makes every small data change a full re-solve, 10–100× slower than reusing it (P8 example). The design answers with factored linear algebra, guaranteed termination, verified answers and a saved basis.

How it works, end to end

  1. lp-parse reads MPS or LP files into an LpProblem; it is the only crate that sees untrusted bytes and validates dimensions and bounds before anything leaves it (§3.2, Threat Model).
  2. lp-presolve drops empty rows and columns, substitutes single-variable rows, tightens bounds, removes redundant rows and scales the matrix, pushing each step on an undo stack so postsolve can map the answer back (§3.2, P7, §8.12).
  3. lp-model converts to standard form: negate costs for a maximise, add slack, surplus and artificial columns, split free variables, shift lower bounds; var_map records the way back (§3.2, I10).
  4. lp-simplex is the primal driver. Phase I minimises the sum of artificials to find a feasible start; Phase II improves it. Each iteration asks lp-pricing who enters, lp-bounds how far it may move, and pivots via lp-tableau (dense, reference) or lp-revised (production) (§3.2, P4).
  5. lp-lu holds the factored basis, updates it after each pivot, and refactors when stale (§3.2, P2, P12).
  6. lp-dual re-optimises from a saved Basis after a data change, skipping Phase I (§3.2, P8).
  7. The result is a Solution plus a Certificate; lp-sensitivity then reads the shadow prices and ranges off the basis without re-solving, and lp-cli orchestrates all of it with the subcommands solve, sensitivity, convert and check. The order is fixed: reduce, standardise, solve, recover (§3.2, P7).

The core ideas

Vertices, bases and the pivot (MM1–MM4, §8.7)

The best point of a linear problem is always at a corner of the feasible region, so simplex walks from corner to adjacent corner and never searches the interior (MM1). A corner is described by a choice of m "active" variables, the basis; one pivot swaps one basic variable for one nonbasic one and so moves to an adjacent corner (MM2). Two questions drive every step. Which variable enters? The reduced cost is the objective change per unit of a variable not in the basis; optimal means none improves (MM3), and the default rule (Dantzig) takes the most negative (§3.2). How far can it move? The ratio test divides each right-hand side by the entering column's entry and takes the smallest; that row's variable leaves, and a tie means a zero-length step, called degeneracy (MM4).

The blueprint's trace of the problem above, in the minimise form with slacks s4, s5, s6 (§8.7):

     x1   x2   x3  | s4  s5  s6 | RHS
  [  6    4    2   |  1   0   0 | 240 ]  row0
  [  3    2    5   |  0   1   0 | 270 ]  row1
  [  5    6    5   |  0   0   1 | 420 ]  row2
  [ -5   -4   -3   |  0   0   0 |   0 ]  obj
  • Iteration 1: x1 enters (reduced cost −5, the most negative). Ratios are 240/6 = 40, 270/3 = 90, 420/5 = 84, so row 0 leaves (s4 exits) and x1 becomes 40; the objective row's right-hand side reads 200 (§8.7).
  • Iteration 2: x3 enters (reduced cost −4/3). Ratios are 120, 37.5 and 66, so row 1 leaves (s5 exits). The blueprint gives the objective as 250 after this pivot (§8.7).
  • Iteration 3: x2 enters and all reduced costs become non-negative, so it stops (§8.7). The closing line (x1 = 30, x2 = 0, x3 = 37.5, objective 300) is inconsistent with this trace, since x2 has just entered yet is reported as 0; this explainer does not rely on it (§8.7, ERRATA).

Standard form and the two-phase method (§8.5, §8.3, ADR-10)

The engine wants equalities with non-negative right-hand sides. The blueprint's rule per relation: a Le row gets one slack column; a Ge row gets one surplus and one artificial; an Eq row gets one artificial (§8.5).

A row with a negative right-hand side is multiplied by −1 and recorded in row_signs; a maximise is turned into a minimise by negating c (§8.5, §8.13). Artificials make an easy starting basis but are not real, so Phase I minimises their sum. If the optimum is above the feasibility tolerance the problem is infeasible and a dual ray is emitted (§8.3). The blueprint's failure example has a Phase I optimum of 3.2e-5 against a tolerance of 1e-8, so the verdict is infeasible (§8.8). If an artificial stays in the basis at value zero, pivot it out with a real column, and if none exists the row is redundant and dropped (§8.8). The alternative, one solve with a big penalty M, is rejected because large coefficients are numerically unstable (ADR-10).

Anti-cycling: Dantzig until stuck, then Bland (P3, I7, MM5)

Degenerate steps do not improve the objective, and a bad tie-break can return to an earlier basis forever (MM5). The blueprint's guard (P3): keep the current rule while the count of consecutive degenerate pivots is under STALL_DETECT_WINDOW; at or above it switch to PivotRule::Bland; reset the count and switch back to Dantzig once progress resumes; stop with Status::IterationLimit at MAX_ITER. A degenerate pivot is one whose step size is at most the feasibility tolerance, and the suggested window is 20 (P3). Bland's rule picks the smallest-index entering and leaving variable, which guarantees finite termination at the cost of extra pivots (P3, ADR-09). The check on Beale's cycling problem is termination within 30 pivots under Bland (Phase 6); I7's debug method says within 100, and Phase 14 says ≤ 500 (I7, Phase 14).

The revised simplex: factor the basis, never invert it (P4, MM6, §8.6)

The dense tableau updates every cell every step (O(m·n)). The revised simplex keeps only the basis matrix B in factored form (an LU factorization, a product of lower and upper triangular matrices) and recomputes what it needs (P4, §3.2). Per iteration (§3.2):

  1. BTRAN solves for the dual values y = c_B B^-1.
  2. Price the candidates: r_j = c_j - y a_j.
  3. FTRAN solves d = B^-1 a_j, the entering column's direction.
  4. Ratio test on d, then update the basis.

After each pivot, a Forrest-Tomlin update patches the factors instead of redoing them (§3.2). The patches accumulate, so lp-lu refactors from scratch on three triggers: too many updates, a bad condition estimate, or a large residual (P2, P12). The blueprint states that check must run after every pivot and in the dual and warm-start paths too, since a loaded factorization can be stale without any update count showing it (P12). The dense lp-tableau stays as a test oracle whose results must match the revised path (P4, §4.1).

Bounded variables and the dual simplex (P9, §8.2, P8, ADR-12)

Every variable is Basic, NonbasicLower, NonbasicUpper or Free (P9). The ratio test then has two outcomes: a basic variable hits a bound and leaves, or the entering variable reaches its own opposite bound first, which flips its status with no pivot and no change to the factors (P9, Phase 8). This avoids adding one row per bound, which would inflate the basis (P9).

The dual simplex starts from a basis whose reduced costs already have the optimal signs (dual feasible) and repairs primal infeasibility: pick the most infeasible basic row to leave, choose the entering variable by the dual ratio test so the signs stay right (§3.2). After a small change to the right-hand sides or bounds, the old optimal basis is a good start; solve_warm checks that the dimensions match, the factorization is non-singular, and each status fits the new bounds, and otherwise warns and falls back to a cold primal solve (P8).

Certificates: proof carried with every answer (P1, P5, I8, I12, MM7)

Duality means an optimum has a matching dual solution that proves it, and failures have rays (MM7). Every terminal status therefore carries a checkable witness (P5):

Status Certificate Verification condition
Optimal KktOptimal the KKT conditions (below)
Unbounded PrimalRay(d) c·d < -OPT_TOL, Ad = 0, d ≥ 0
Infeasible DualRay(y) yᵀb < -OPT_TOL, Aᵀy ≥ -OPT_TOL
IterationLimit, Numerical None partial solution only

The KKT conditions are primal feasibility, dual feasibility and complementary slackness (P1). lp-simplex runs verify_kkt before returning and turns a failure into Status::Numerical, "never a silent wrong answer" (P1); lp-cli check re-verifies from outside (P5, I8).

The trade-offs — where engineers disagree

Basis as a sparse LU with eta updates (ADR-06, ADR-07)

Chosen: eta-vector updates over a sparse LU, refactored periodically, which gives stable FTRAN/BTRAN and memory proportional to the nonzeros (ADR-06); the update rule is Forrest-Tomlin because it preserves sparsity better (ADR-07). Rejected: an explicit B^-1, a dense LU (ADR-06); Bartels-Golub and MINOS PFI (ADR-07). When the rejected choice is right: explicit B^-1 for very small bases, dense LU when the basis itself is dense (ADR-06); Bartels-Golub when stability under arbitrary column replacement matters more than sparsity, PFI for simplicity (ADR-07). Note that ADR-06 names its choice "eta-vector product form" while ADR-07 lists MINOS PFI (the product-form inverse) among the rejected options; the blueprint does not reconcile them.

Pricing and anti-cycling: Dantzig with a Bland fallback (ADR-08, ADR-09)

Chosen: Dantzig by default, Bland's index rule as the mandatory fallback, Devex optional (ADR-08); lexicographic perturbation as the second anti-cycling tool, faster but more complex (ADR-09, P3). Rejected: steepest-edge only, random or largest-increase pricing (ADR-08); perturbation only, or no anti-cycling (ADR-09). When the rejected choice is right: steepest-edge or Devex when pivot count, not per-pivot cost, dominates on large problems (ADR-08); perturbation-only when degeneracy is mild and Bland's index scan would dominate runtime (ADR-09).

Two-phase, not Big-M (ADR-10)

Chosen: two-phase, where Phase I minimises the sum of artificials and Phase II optimises the real objective, as it is numerically clean (ADR-10). Rejected: Big-M penalties, which introduce large coefficients (ADR-10, A3). When the rejected choice is right: when a single solve with a safe, problem-bounded M is simpler and the coefficients stay well scaled (ADR-10).

Bounds handled natively (ADR-11)

Chosen: a bounded-variable ratio test in lp-bounds with bound flips and NonbasicUpper status, which keeps the basis at m rows (ADR-11, P9). Rejected: explicit bound constraints as rows. When the rejected choice is right: when the solver lacks a bounded-variable ratio test and added rows are acceptable for small problems (ADR-11).

Dual simplex for warm starts (ADR-12)

Chosen: implement lp-dual so a bound or right-hand-side change avoids a redundant Phase I, which the blueprint calls essential for a branch-and-bound parent node (ADR-12, P8). Rejected: re-solve from scratch. When the rejected choice is right: when no warm-start basis exists, such as a brand-new unrelated problem (ADR-12).

Roads not taken

Interior-point method (A1): wins on very large sparse problems where its polynomial-time barrier beats simplex's exponential worst case and no warm start is needed (HiGHS, Mosek). Rejected for v1 because simplex gives an exact vertex and an easy warm start; deferred with the trigger "large or sparse enough that IPM beats simplex, or warm-start is not needed" (Deferred Features Register).

Dense-tableau only (A2): wins for tiny dense textbook-size problems. Rejected as the core because memory is O(m·n) and it is unusable above about 1000 variables (§4); kept as the oracle (ADR-05). P4, by contrast, suggests switching to the revised path above 200 variables (P4).

Big-M single phase (A3): wins for quick prototypes with a known-safe M. Rejected because a large M corrupts the numerics (MM8, ADR-10).

Exact rational arithmetic (A4): wins where bit-exact optima are required (certified MIP, formal verification; SoPlex). Rejected for v1 because it is orders of magnitude slower and 1e-6 suffices (§4, MM7). Branch-and-bound is the other deferred item, triggered when integer problems must be solved, not just relaxed (Deferred Features Register, ADR-12).

What must never be false

§7 lists twelve invariants (I1–I12), while §2.3 refers to "I1–I10" (§2.3, §7).

  • I1 the basis factorization is a valid non-singular LU. Noticed by a condition estimate over REFACT_COND_THRESHOLD or a pivot under PIVOT_TOL; recovery is refactorization (§7).
  • I2 in primal Phase II every basic variable stays within its bounds. Noticed by check_primal_feas after each pivot (§7).
  • I3 in dual simplex every reduced cost keeps its optimal sign. Noticed by all_correct_sign before each dual pivot (§7).
  • I4 at Optimal no reduced cost has the wrong sign beyond OPT_TOL. Noticed by the KKT verifier, which turns Optimal into Numerical on failure (§7).
  • I5 at Optimal the primal and dual objectives agree. Noticed as a nonzero gap in the KKT verifier (§7).
  • I6 the ratio test yields the maximum feasible step. Noticed by the post-pivot feasibility assertion (§7).
  • I7 the pivot sequence is finite. Noticed by the stall counter and MAX_ITER (§7, P3).
  • I8 a primal or dual ray satisfies its inequalities. Noticed by verify_certificate in lp-cli check (§7).
  • I9 postsolve returns a feasible, equal-objective original solution. Noticed by an objective comparison and an original-space feasibility check in lp-cli (§7).
  • I10 standard form preserves the optimum and var_map recovers every original variable. Noticed by Phase 2 unit tests; there is no runtime recovery path (§7).
  • I11 no pivot is applied that would make the basis singular within PIVOT_TOL. Noticed by the candidate-pivot check, Err(SingularPivot) or Err(NumericallyZero) (§7).
  • I12 only the full KKT bundle may build Certificate::KktOptimal. Noticed by KktReport { primal_viol, dual_viol, cs_viol } (§7, P1).

What breaks in production

The Failure Modes section is a 14-row taxonomy in four families (Correctness and Numerical page, Termination and Operational warn). Six rows that teach the most:

  • Wrong optimum (silent). The symptom is a failed KKT check or an objective more than 1e-6 relative off a reference solver. Causes: basis drift, skipped refactorization, a pivot tolerance that is too loose. Detection is the KKT verifier on every optimal result plus the Netlib suite (P1). Recovery: refactorize and retry; compare dense against revised paths (Failure Modes and Recovery).
  • False infeasible. Infeasible on a feasible problem, from scaling trouble, a presolve error or numerical drift. Detection: the dual ray fails its check (I8). Recovery: retry without presolve or with rescaling; solve with Big-M for comparison (Failure Modes and Recovery).
  • Cycling. The iteration count hits the ceiling and the objective stagnates. Detection: stall detector, MAX_ITERS, optional basis-hash dedup in debug builds. Automatic recovery: switch to Bland (P3, I7).
  • Presolve/postsolve mismatch. The recovered solution is infeasible in the original problem (I9), from a wrong bound reconstruction or substitution order. Detection: re-check the constraints after postsolve. Recovery: --no-presolve and re-solve (Failure Modes and Recovery, T8).
  • Warm-start divergence. The dual simplex cannot reach primal feasibility because the basis does not fit the modified problem. Detection: dimension, bound and hash checks (T11). Recovery: fall back to a cold primal solve (P8).
  • Status::Numerical unresolved. No certificate after all retries. Manual recovery: Curtis-Reid scaling or a smaller problem; interior point is only a stretch goal (Failure Modes and Recovery).

Threats worth knowing (Threat Model): T1 a malformed MPS/LP file, answered by a strict parser with capped dimensions and fuzzing; T3 an oversized declared matrix, answered by limits on rows, columns and nonzeros checked before any allocation; T4 a crafted cycling LP used as a CPU denial of service, answered by Bland, a stall detector and a hard iteration ceiling (I7); T5 NaN or infinity injected into costs or right-hand sides, answered by validating every parsed number; T11 a stale warm-start basis from a different problem, answered by dimension and SHA-256 problem-hash checks.

How it compares

  • GLPK: Dantzig or steepest-edge pricing, basic presolve, MIP built in. It wins as a replaceable open-source baseline and for its MathProg modelling language (Comparative Architecture).
  • HiGHS: dual simplex plus interior point and extensive presolve. Right for large sparse LPs where dual simplex or crossover beats a pure primal method (Comparative Architecture).
  • COIN-OR CLP: Devex or steepest-edge pricing, extensive presolve, the engine behind the Cbc MIP solver. It fits inside a larger branch-and-cut framework (Comparative Architecture).
  • SoPlex: steepest-edge pricing plus an iterative-refinement exact-rational mode. Right when bit-exact LP solutions, not just 1e-6, are required (Comparative Architecture, A4).
  • Gurobi/CPLEX: simplex and barrier run concurrently, with decades of numerical tuning. They win when raw speed and robustness on hard industrial models justify a licence (Comparative Architecture).

If you only remember three things

A simplex solver walks from corner to corner of the feasible region by swapping one basis variable at a time, guided by reduced costs and the ratio test (MM1–MM4). The production version never inverts the basis: it keeps it factored, patches the factors cheaply, and refactors before drift spoils the answer, while a dense tableau survives only as a test oracle (MM6, P4, P12). And the solver never merely says "optimal", "infeasible" or "unbounded": each comes with a certificate anyone can check, and every comparison uses named tolerances (P1, P5, P6).

Words used here

  • Basis: the m variables currently "active"; choosing them fixes one corner (MM2).
  • Pivot: swapping one basic variable for one nonbasic one, moving to an adjacent corner (MM2).
  • Reduced cost: objective change per unit of bringing a nonbasic variable in; the price signal that picks the entering variable (MM3).
  • Ratio test: finds which basic variable hits a bound first and so limits the step (MM4).
  • Slack / surplus / artificial variable: helper columns added to turn inequalities into equalities and to give a starting basis (§8.5).
  • Two-phase method: first find any feasible point by minimising the artificials, then optimise (ADR-10).
  • FTRAN / BTRAN: the two triangular solves against the factored basis that replace tableau row operations (MM6, §3.2).
  • LU factorization: the basis as lower times upper triangular factors; refactorization rebuilds them from the current basis columns to stop drift (MM6, P2).
  • Dual simplex: simplex run from a dual-feasible basis, used to reoptimise after data changes (§3.2, ADR-12).
  • KKT conditions: primal feasibility, dual feasibility and complementary slackness; together they prove optimality (P1).
  • Certificate / ray: a checkable witness of the answer: the KKT bundle, a primal ray for unbounded, a dual (Farkas) ray for infeasible (P5, MM7).
  • Postsolve: undoing presolve reductions in reverse (LIFO) order (P7, §8.12).
