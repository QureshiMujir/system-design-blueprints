Decisions (§9) · 30 ADRs

ADR-01

Implementation language

Chosen

Rust (stable toolchain)

Rejected

C++, Python, Julia

When the rejected choice is right

C++ when integrating with existing solver codebases (CLP/SoPlex); Python/Julia for a research prototype prioritizing modeling expressiveness over runtime

Why: Memory safety without GC; zero-cost abstractions; f64 layout guarantees; ecosystem for numerical crates

ADR-02

Build system

Chosen

Cargo workspace (one workspace root, 13 member crates)

Rejected

Bazel, cmake, buck

When the rejected choice is right

Bazel/cmake when integrating into a polyglot or existing C++ numerical build

Why: Native Rust; per-crate Cargo.toml; workspace-level [profile]; no extra toolchain

ADR-03

Dependency policy

Chosen

Minimal: rayon (optional parallelism), serde+serde_json (solution I/O), clap (CLI), thiserror (error types), criterion (bench)

Rejected

nalgebra, ndarray, faer

When the rejected choice is right

nalgebra/ndarray/faer when you need general dense linear algebra (eigen/SVD) beyond simplex-specific sparse ops

Why: Keep numerical core self-contained; nalgebra/ndarray add overhead without simplex-specific primitives

ADR-04

Matrix storage format

Chosen

Column-major CSC (SparseMatrix in lp-core)

Rejected

Dense Vec<Vec<f64>>, row-major CSR, triplet COO

When the rejected choice is right

Dense Vec<Vec<f64>> for tiny dense problems where simplicity wins; COO for one-time assembly before conversion

Why: Simplex accesses columns (entering variable); CSC gives O(nnz_col) per column operation

ADR-05

Dense tableau engine

Chosen

Plain Vec<f64> row-major 2D array in lp-tableau

Rejected

BLAS, ndarray

When the rejected choice is right

BLAS/ndarray when the dense path must actually be fast (not just a reference) for moderate dense problems

Why: Dense tableau is the reference/test oracle only; clarity and differential-testing matter more than performance here

ADR-06

Revised simplex basis representation

Chosen

Eta-vector product form + sparse LU in lp-lu

Rejected

Full explicit B^-1, dense LU

When the rejected choice is right

Explicit B⁻¹ for very small bases where dense updates are cache-friendly; dense LU when the basis itself is dense

Why: Eta vectors accumulate cheaply; LU gives stable FTRAN/BTRAN; refactorize periodically → O(nnz) memory

ADR-07

LU update algorithm

Chosen

Forrest-Tomlin (spike-based rank-1)

Rejected

Bartels-Golub (column replacement), MINOS PFI

When the rejected choice is right

Bartels-Golub when stability under arbitrary column replacement matters more than sparsity preservation; PFI for implementation simplicity

Why: Forrest-Tomlin preserves sparsity better on rank-1 pivots; Bartels-Golub available as fallback

ADR-08

Pivot pricing (default)

Chosen

Dantzig (most-negative reduced cost) with fallback to Bland

Rejected

Steepest-edge only, random, largest-increase

When the rejected choice is right

Steepest-edge/Devex when pivot count (not per-pivot cost) dominates on large problems — fewer, better-chosen pivots win

Why: Dantzig standard reference; Bland mandatory for anti-cycling (P3/I7); Devex optional for performance

ADR-09

Anti-cycling mechanism

Chosen

Bland's rule (index-based) as primary; lexicographic perturbation as secondary

Rejected

Perturbation only, no anti-cycling

When the rejected choice is right

Perturbation-only when degeneracy is mild and Bland’s per-pivot index scan would dominate runtime

Why: Bland guarantees termination in finite pivots; lexicographic is faster but more complex; both implemented

ADR-10

Two-phase vs Big-M

Chosen

Two-phase (Phase I minimises sum-of-artificials; Phase II optimises original)

Rejected

Big-M penalty

When the rejected choice is right

Big-M when a single solve with a safe, problem-bounded M is simpler and coefficients stay well-scaled

Why: Big-M introduces numerical instability from large coefficients; two-phase is numerically clean

ADR-11

Bounded-variable handling

Chosen

Native ratio-test extension in lp-bounds (bound flips, NonbasicUpper status)

Rejected

Add explicit bound constraints as rows

When the rejected choice is right

Explicit bound rows when the solver lacks a bounded-variable ratio test and added rows are acceptable for small problems

Why: Explicit rows grow m; native BV simplex keeps basis small (P9)

ADR-12

Dual simplex

Chosen

Implemented in lp-dual for warm-start reoptimisation

Rejected

Re-solve from scratch

When the rejected choice is right

Re-solve from scratch when no warm-start basis is available (a brand-new unrelated problem)

Why: Warm-start on bound/RHS changes avoids redundant Phase I; essential for branch-and-bound parent (P8)

ADR-13

Presolve scope

Chosen

Singleton rows/cols, empty rows, bound tightening, redundancy removal, fixed-variable substitution

Rejected

Full network-simplex presolve, interior-point-style presolve

When the rejected choice is right

Full IPM-style/network presolve for problems with heavy structure (network flows) where aggressive reduction pays off

Why: Covers >80% of practical reduction; more complex presolve rules deferred to stretch goals

ADR-14

Scaling

Chosen

Geometric mean scaling (rows then columns); Curtis-Reid iterative as alternative

Rejected

Equilibration, no scaling

When the rejected choice is right

Equilibration when a single max-norm pass suffices; no scaling when the matrix is already well-conditioned (avoids a pass)

Why: Geometric mean is O(nnz) per pass, reduces condition without dense ops; Curtis-Reid available when condition stays high

ADR-15

Serialisation format (solution)

Chosen

JSON via serde_json (default); plain-text summary for CLI

Rejected

CSV, binary protobuf, MessagePack

When the rejected choice is right

protobuf/MessagePack when solution volume is large and compact binary I/O matters; CSV for spreadsheet interop

Why: JSON is human-readable for debugging; basis warm-start uses a compact custom binary (ADR-16)

ADR-16

Basis warm-start format

Chosen

Custom little-endian binary (magic + version + VarStatus bytes)

Rejected

JSON basis, CPLEX .bas format

When the rejected choice is right

CPLEX .bas format when interoperating with CPLEX warm-starts; JSON basis when warm-start readability matters

Why: Minimal size; fast read/write; version field allows forward compatibility

ADR-17

MPS parser

Chosen

Hand-written fixed-field MPS reader in lp-parse

Rejected

nom/pest grammar, regex

When the rejected choice is right

A parser-combinator grammar when the input format is complex/evolving and a declarative grammar eases maintenance

Why: Fixed-field MPS is simple enough; hand-written avoids parser-combinator dependency; covers free-format MPS variant too

ADR-18

LP-format parser

Chosen

Hand-written recursive-descent in lp-parse

Rejected

LALRPOP, pest

When the rejected choice is right

A parser generator (LALRPOP/pest) when the LP grammar grows beyond LL(2) and ambiguity handling is needed

Why: LP format grammar is LL(2); recursive descent is sufficient and avoids code-gen in build

ADR-19

Error handling

Chosen

thiserror-derived error enums per crate; no unwrap in library code

Rejected

anyhow, Box<dyn Error>

When the rejected choice is right

anyhow in the CLI binary where error kinds are never matched

Why: Typed errors allow match on Status and structured propagation; anyhow acceptable in lp-cli binary only

ADR-20

Concurrency model

Chosen

Single-threaded solver core; optional rayon for batch-solve parallelism at CLI level

Rejected

async/tokio, per-pivot threads

When the rejected choice is right

Per-pivot/block parallelism when a single huge LP’s FTRAN/BTRAN can be parallelized (large sparse bases on many cores)

Why: Simplex inner loop is sequential by design; parallelism at problem level (multiple independent solves)

Logging

When the rejected choice is right

The log facade when span-based per-pivot profiling is not needed

Why: tracing supports span-based profiling; spans align to phases and LU refactorizations for perf diagnosis

Alternative Architectures (Roads Not Taken)

A1 — Interior-point / barrier method.

start interior → follow central path (Newton steps) → converge to optimum

Wins for very large, sparse LPs where the polynomial-time barrier method beats simplex's exponential worst case and warm-start isn't needed. Embodied by HiGHS IPM / Mosek. Rejected for v1 because simplex yields an exact vertex (basis) and trivial warm-start for branch-and-bound; IPM is a deferred stretch goal (Register).

A2 — Dense-tableau simplex only (no revised/LU).

[ full m×n tableau ] ── pivot in place ── repeat

Wins for tiny, dense problems (textbook size) where clarity beats scale and the tableau fits in cache. Embodied by classroom Bland's-rule implementations. Rejected as the core because it is O(m·n) memory and unusable above ~1000 vars (§4); kept only as the reference oracle (ADR-05).

A3 — Big-M single-phase method.

minimize  cᵀx + M·Σ(artificials)   in one solve

Wins when a single LP solve with a known-safe M is simpler than running two phases (quick prototypes). Embodied by textbook Big-M presentations. Rejected because a large M corrupts the numerics (MM8, ADR-10); two-phase is numerically clean.

A4 — Exact rational-arithmetic simplex.

pivots over exact rationals (no f64) → bit-exact optimum + certificate

Wins when bit-exact optimality is required (certified MIP, formal verification). Embodied by SoPlex iterative-refinement / exact-LP. Rejected for v1 because rational arithmetic is orders of magnitude slower and the 1e-6 tolerance (§4) suffices; certificate verification (MM7) covers the cases where exactness matters.
