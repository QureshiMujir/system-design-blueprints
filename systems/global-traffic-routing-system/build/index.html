⬜ Phase 0 — Skeleton: domain model, geo lookup, deterministic decision oracle §12

Objectives
  • Stand up the workspace + gtr-core; define Endpoint/Pool/HealthCheck/HealthState/Policy/SteeringDecision/ClientContext.
  • Build geo: a prefix-trie geo DB loader + LPM lookup + ECS struct (parse comes in P6).
  • Implement the deterministic decision evaluator skeleton (health filter + a trivial policy) and the policy oracle (the reference evaluator).
Deliverable
  • Load a geo DB, locate an IP, evaluate a trivial policy deterministically; gtrctl resolve --ip … --policy … prints a DecisionTrace.
Acceptance
  • PrefixTrie::locate returns the correct longest-prefix match (I-LPM) vs a reference lookup — 100% match on geo/lpm_lookup.json.
  • EcsOption::validate accepts valid subnets, rejects bad family / oversized SOURCE / non-zeroed bits (I-ECS-SAFE) — all cases in ecs/ecs_validate.json pass.
  • The trivial decision matches the oracle bit-for-bit (I-DET) on 100% of policy/trivial_decision.json cases.
Fixtures
Fixture Purpose Expected
geo/lpm_lookup.json longest-prefix geo lookup correct location for client subnet (I-LPM)
ecs/ecs_validate.json ECS sanity checks bad family / oversized SOURCE rejected (I-ECS-SAFE)
policy/trivial_decision.json single-endpoint decide decision = oracle, deterministic (I-DET)
policy/health_filter.json unhealthy filtered only healthy endpoints returned
Pitfalls
  • Prefix-trie LPM off-by-one on prefix length (a /24 vs /25 boundary) — test boundaries exhaustively.
  • IPv4-in-IPv6 mapped addresses — normalize before trie insert/lookup.
  • ECS address bits beyond SOURCE not zeroed → cache-key inconsistency — zero on validate.
  • Treating "no geo match" as an error rather than a default → handle GeoMiss as failsafe (I-FAILSAFE).

⬜ Phase 1 — Health checking: active probers (HTTP/TCP/ICMP) + passive §13

Objectives
  • Build the active probers and passive-signal ingest from a single vantage (consensus across vantages is P2): run a HealthCheck against an endpoint, apply hysteresis (k_fail/k_pass), produce a per-vantage verdict.
Deliverable
  • A prober that health-checks endpoints from one vantage and reports verdicts; examples probe a fake endpoint up/down.
Acceptance
  • HTTP/TCP/ICMP checks correctly detect up/down within k_fail × interval — default k_fail=3, interval=5s ⇒ detect ≤ 15s (health/http_check.json, health/tcp_check.json).
  • Hysteresis prevents single-probe flips (needs k_fail consecutive to go DOWN) — verified by health/hysteresis.json.
  • Probe rate ≤ 1 probe/endpoint/vantage/interval (I-PROBE-BUDGET), enforced ≥ 5s default interval — verified by health/probe_budget.json.
Fixtures
  • health/http_check.json, health/tcp_check.json, health/hysteresis.json, health/probe_budget.json.
Pitfalls
  • Probe timeout vs interval (a timeout longer than the interval → overlapping probes) — clamp timeout < interval.
  • ICMP requires raw sockets / CAP_NET_RAW → privilege handling + a fallback to TCP.
  • HTTP redirects/keep-alive confusing the check → follow-or-not policy explicit; fresh connection per probe option.
  • A slow probe blocking the scheduler → each probe is an independent task with its own timeout.

⬜ Phase 2 — Vantage consensus + flap damping §14

Objectives
  • Fuse per-vantage verdicts from V vantages into one stable HealthState via quorum consensus (I-CONS), and suppress oscillation via flap damping (I-DAMP) — the stability heart (principle 4).
Deliverable
  • Consensus + damping over multi-vantage verdicts; examples show one broken vantage not flipping an endpoint, and an oscillating endpoint being damped.
Acceptance
  • A single dissenting vantage does not change HealthState when quorum (≥ ⌈(V+1)/2⌉ of V, e.g. 2-of-3) disagrees (I-CONS) — verified by health/single_vantage_no_flap.json.
  • An endpoint flipping > k times in window W is damped and held until stable (I-DAMP) — verified by health/flap_damp.json.
  • A stopped vantage is excluded from quorum within its timeout (not counted as DOWN forever) — verified by health/stale_vantage.json.
Fixtures
Fixture Purpose Expected
health/consensus_quorum.json quorum DOWN endpoint DOWN only at quorum (I-CONS)
health/single_vantage_no_flap.json one broken vantage endpoint stays UP, no re-steer (I-CONS)
health/flap_damp.json oscillating endpoint held in damped state (I-DAMP)
health/stale_vantage.json stale vantage report excluded; last state held
Pitfalls
  • Even V → quorum ties; define the tie-break (lean to last-known / Healthy per failsafe) explicitly.
  • Damping a recovering endpoint too long (a real recovery looks like a flip) → tune decay; k_pass + damping interact.
  • Vantage clock skew on verdict timestamps → use receipt order / bounded windows, not absolute time.
  • A correlated-failure (all vantages share a broken upstream) → quorum agrees DOWN correctly, but document that consensus assumes independent vantage paths.

⬜ Phase 3 — Latency map: RUM ingestion + aggregation + lookup §15

Objectives
  • Build the latency database: ingest real-user-measurement samples, aggregate into a client_network → endpoint → latency_estimate map, with decay + confidence + a lookup for latency-based routing.
Deliverable
  • Ingest RUM samples, aggregate, look up a client network's per-endpoint latencies; examples/latency_routing shows a network steered to its lowest-latency endpoint.
Acceptance
  • Aggregation produces stable estimates under sample noise (EWMA convergence).
  • Decay down-weights old samples so a regressed endpoint loses its low estimate over the window.
  • Lookup returns estimates with confidence; below threshold → signals fallback (I, §8.10).
Fixtures
  • policy/latency_map_aggregate.json, policy/latency_decay.json, policy/latency_lookup_confidence.json.
Pitfalls
  • Sample skew (a few outlier RTTs dominating) → robust aggregation (trimmed mean / EWMA, not raw mean).
  • Cold-start: a client network with no samples → must fall back (geoproximity), not return garbage.
  • Stale data presented as fresh → confidence + decay must gate it.
  • Memory growth (millions of client networks × endpoints) → bucket coarsely; bound the table; evict cold entries.

⬜ Phase 4 — Policy engine: failover + weighted + failsafe (deterministic) §16

Objectives
  • Implement the first real policies — failover and weighted round-robin — in the deterministic decision engine, with the failsafe fallback (principle 8, I-FAILSAFE), all health-filtered.
Deliverable
  • Failover + weighted decisions, health-filtered, deterministic, with failsafe; examples/failover shows a primary→secondary failover.
Acceptance
  • Failover returns the first healthy target in order; 100% match vs the oracle (I-DET) on policy/failover_primary_secondary.json.
  • Weighted distribution matches weights in aggregate within ±2% over ≥10,000 samples; a given client deterministically maps to one target (seeded) — policy/weighted_distribution.json + policy/weighted_deterministic.json.
  • All-unhealthy → failsafe answer, never empty (I-FAILSAFE) — verified by policy/failsafe_all_unhealthy.json.
Fixtures
Fixture Purpose Expected
policy/failover_primary_secondary.json failover order primary unless unhealthy, then secondary
policy/weighted_distribution.json weighted RR distribution matches weights
policy/weighted_deterministic.json seeded shuffle same seed → same order (I-DET)
policy/failsafe_all_unhealthy.json all endpoints down return all-configured, never empty (I-FAILSAFE)
Pitfalls
  • Weighted determinism: using rand() → non-replayable decisions → must hash (client, qname, seed) (I-DET).
  • Failover order vs health: a healthy primary that just flapped (damped) → treat damped as unhealthy for selection.
  • Failsafe returning a known-dead endpoint vs all-configured — define which (prefer last-known-healthy set).
  • Weight = 0 endpoints (excluded) vs all-zero weights (degenerate → equal-split fallback).

⬜ Phase 5 — Geo, geoproximity, latency, multi-value + composite policies §17

Objectives
  • Add the location-aware policies — geolocation, geoproximity, latency (using P3's map), multi-value answer — and composite/nested policy evaluation (a geo policy whose leaves are pools/failover, §8.4). The full Route-53-class policy set.
Deliverable
  • All policies + arbitrary nesting; examples/geo_routing shows continent-based steering with failover leaves; gtrctl resolve --client-subnet simulates any policy.
Acceptance
  • Geolocation picks the most-specific matching region; default when none; matches the oracle.
  • Geoproximity picks the nearest (with bias) correctly; latency uses the map + falls back to geoproximity.
  • Multi-value returns ≤ max healthy; composite nesting evaluates correctly to depth ≤ 4 (I-DET).
Fixtures
Fixture Purpose Expected
policy/geolocation_specificity.json continent/country/subdivision most-specific match fires
policy/geoproximity_bias.json nearest + bias bias shifts catchment as specified
policy/latency_with_fallback.json sparse latency data falls back to geoproximity
policy/multivalue_max.json multi-value answer ≤ N healthy returned
policy/composite_geo_failover.json nested geo→failover matches oracle AST walk (I-DET)
Pitfalls
  • Geolocation specificity order (subdivision > country > continent > default) — get the precedence exact.
  • Geoproximity bias units + sign (bias toward = larger effective region) — define + test.
  • Composite recursion without a depth bound → stack blowup / cycles → cap depth, detect cycles.
  • Latency fallback to geoproximity must be deterministic + traced (latency_fallback).
  • Multi-value with fewer than max healthy → return what's available (not pad with unhealthy).

⬜ Phase 6 — DNS answer generation + ECS (RFC 7871) — plugs into #162 §18

Objectives
  • Generate the per-query DNS RRset for a SteeringDecision, with full ECS handling (parse on query, validate, geo-from-subnet, echo SCOPE on response), valid RFC-1035/6891/7871 wire output, plugging into #162's server (principle 1, I-WIRE/I-ECS).
Deliverable
  • DNS answers (incl. ECS-scoped) for any policy; a resolver (dig +subnet=…) against #162-with-our-hook gets correctly steered, ECS-echoed answers; examples/resolve.
Acceptance
  • Wire output is RFC-valid (100% parse-back round-trip; vs a reference like dig) (I-WIRE) — verified by dns/wire_roundtrip.json.
  • ECS: geo uses the client subnet; the response echoes the subnet with the correct SCOPE (I-ECS) — ecs/ecs_scope_response.json + ecs/ecs_geo_steering.json; invalid ECS is rejected + falls back (I-ECS-SAFE) — ecs/ecs_invalid_fallback.json.
  • Record-type handling: A/AAAA/CNAME correct; NODATA vs NXDOMAIN correct — verified by dns/nodata_vs_nxdomain.json.
Fixtures
Fixture Purpose Expected
dns/wire_roundtrip.json encode → parse-back RFC-1035/6891-valid (I-WIRE)
ecs/ecs_scope_response.json response SCOPE correct SCOPE echoed (RFC 7871, I-ECS)
ecs/ecs_geo_steering.json ECS-driven geo client subnet drives location
ecs/ecs_invalid_fallback.json malformed ECS strip ECS → resolver-IP fallback (I-ECS-SAFE)
dns/nodata_vs_nxdomain.json negative answers correct NODATA vs NXDOMAIN
Pitfalls
  • DNS name compression (pointers) in encoding → implement or avoid carefully; parse must handle compressed names (and compression-loop attacks) (I-WIRE).
  • ECS SCOPE semantics: SCOPE in the response is the answer-validity prefix, not the query's SOURCE — confusing them breaks resolver caching (§8.6).
  • Zeroing address bits beyond SOURCE/SCOPE (RFC 7871 requires) → cache-key + privacy correctness.
  • EDNS UDP payload size + truncation (TC bit) → respect the requestor's buffer; truncate→TCP.
  • Mismatched FAMILY (v4 ECS for an AAAA query) → handle sanely.

⬜ Phase 7 — TTL strategy + negative caching + answer-cache semantics §19

Objectives
  • Implement the TTL strategy (the reactivity dial, principle 7, I-TTL): steady vs failover-shortened vs floored TTLs; RFC-2308 negative caching; and the failsafe-over-NXDOMAIN choice (§8.7).
Deliverable
  • TTLs that shorten during failover + a floor; negative answers with correct SOA-min; examples show TTL dropping when a pool destabilizes.
Acceptance
  • Steady TTL = configured; during active failover/instability TTL = failover TTL; never below floor (I-TTL).
  • NODATA/NXDOMAIN carry SOA-min TTL (RFC 2308); transient all-unhealthy → failsafe positive, not cached NXDOMAIN.
  • TTL changes are observable + reasoned in the trace.
Fixtures
Fixture Purpose Expected
dns/ttl_steady_vs_failover.json TTL dial short TTL during failover (I-TTL, §4.1)
dns/ttl_floor.json TTL floor never below the configured floor
dns/negative_soa_min.json negative caching SOA-minimum TTL (RFC 2308)
dns/failsafe_not_nxdomain.json uncertainty last-known answer, not NXDOMAIN (I-FAILSAFE)
Pitfalls
  • TTL too short during failover → query/auth storm (the cure becomes the disease) → floor + a bounded failover window.
  • Resolvers that ignore/clamp tiny TTLs → the floor must be realistic; document resolver behavior (#65).
  • Caching a transient NXDOMAIN → an outage that outlives the actual problem (resolvers cache negatives) → prefer failsafe (I-FAILSAFE).
  • SOA-min vs the record TTL confusion in negative caching (RFC 2308 uses SOA-min).

⬜ Phase 8 — Anycast / BGP announcement control §20

Objectives
  • Implement announcement steering: from per-PoP health, decide announce/withdraw of anycast prefixes, emit intents to a BGP control sink (real BGP-4 session deferred §22.2), with catchment-load awareness (§8.8).
Deliverable
  • Per-PoP announce/withdraw intents from health, with a simulated sink; examples show an unhealthy PoP withdrawing and its catchment (coarsely) shifting; integration point for #355's convergence model.
Acceptance
  • An unhealthy PoP withdraws within one damped health transition; a recovered PoP re-announces (idempotent) — verified by propagation/anycast_withdraw_on_unhealthy.json + propagation/anycast_reannounce.json.
  • Withdrawal emits the correct intent to the sink; catchment-load estimate flags an at-risk neighbor — verified by fault/anycast_load_shift.json.
  • No flapping of announcements (reuse health damping, I-DAMP): zero re-announce/withdraw cycles for a damped (held) endpoint across the fixture suite.
Fixtures
  • propagation/anycast_withdraw_on_unhealthy.json, propagation/anycast_reannounce.json, fault/anycast_load_shift.json.
Pitfalls
  • Withdrawing a large PoP overloads a neighbor (thundering herd) → gradual withdrawal + catchment-load check (§8.8).
  • Announcement flapping (a flapping PoP withdrawing/announcing repeatedly) → gate by damped health, not raw (I-DAMP).
  • Anycast is per-PoP, not per-client/endpoint — do not promise fine steering it cannot give (principle 1).
  • A withdrawn-but-still-receiving-traffic window (convergence lag) → clients in flight during convergence; document the #355-modeled lag.

⬜ Phase 9 — HTTP 3xx redirect responder §21

Objectives
  • Implement the per-request-precise steering mechanism: an HTTP responder that answers 302/307 + Location pointing at the decided endpoint (principle 1, §8.9) — for fine control where DNS is too coarse and anycast too blunt.
Deliverable
  • An HTTP redirector that steers each request to the decided endpoint; examples curl → 302 to the right region.
Acceptance
  • A request gets a 302/307 to the policy-decided endpoint; the client IP drives geo directly (no ECS/resolver indirection — most accurate).
  • Cache-Control bounds redirect caching; the decision matches the DNS path's decision for the same client (principle 1, consistency).
Fixtures
  • policy/redirect_decision.json (== DNS decision for same ctx), dns/redirect_cache_control.json.
Pitfalls
  • X-Forwarded-For spoofing → trust only from known proxies; otherwise use the connection IP (a steering-abuse vector).
  • Redirect caching (302 is cacheable) → set Cache-Control to keep per-request precision.
  • The added RTT + TCP/TLS setup is the cost — do not use where DNS suffices (principle 1).
  • Redirect loops (redirecting to a host that redirects back) → guard / cap.

⬜ Phase 10 — Propagation + consistency model + control-plane leader/epoch §22

Objectives
  • Build the propagation engine + consistency model (principle 5, I-PROP/I-ORDER/I-SNAP) and the control-plane leader + epoch (principle 12, I-LEADER): the control plane computes versioned generations, propagates them ordered + bounded-stale to edges, and only one leader advances generations.
Deliverable
  • Control plane propagates versioned state to N edges, ordered + bounded-stale + acked; a leader change fences the old leader; examples/gtrctl prop-status show per-edge generation lag.
Acceptance
  • Edges converge to the leader's generation within the staleness bound (I-PROP); applied in order, no regress (I-ORDER); each query reads one snapshot (I-SNAP).
  • A second leader's generations are fenced by epoch (I-LEADER); no split steering.
  • A stale/partitioned edge serves last-good (principle 3) and is flagged.
Fixtures
Fixture Purpose Expected
propagation/ordered_apply.json generation ordering applied monotonically (I-ORDER)
propagation/staleness_bound.json staleness edge within N gen / T s (I-PROP)
propagation/gen_regress_rejected.json older generation rejected, never regresses (I-ORDER)
propagation/leader_fence.json stale leader fenced by epoch (I-LEADER)
fault/split_steering_bounded.json partial failover bounded, detectable, no split (Principle 5)
Pitfalls
  • Out-of-order delivery applying an old generation over a new one → monotonic compare on apply (I-ORDER).
  • A split-brain control plane (two leaders) → epoch fencing (I-LEADER); without it, conflicting generations → split steering (the worst failure, principle 5).
  • An edge that acks but didn't actually apply → ack only after the Arc-swap; verify via a state hash.
  • Delta propagation losing a generation (gap) → require contiguous generations or re-sync full on gap.
  • Quarantining too aggressively (a briefly-stale edge dropped from rotation) → tune the staleness bound.

⬜ Phase 11 — C / Python ABI §23

Objectives
  • Expose a C ABI (+ a Python-FFI-friendly layer) so a control-plane UI, #326, or tests can author policies, evaluate decisions, and run dry-run queries without the full daemon (I-ARG).
Deliverable
  • libgtr.so + gtr.h; examples/decide_from_c.c evaluates a policy; a Python smoke driver simulates geo steering for a set of client subnets.
Acceptance
  • A C/Python caller gets decisions 100% identical to the Rust engine + the oracle (I-DET), verified by the C integration test + Python steering-simulation test in CI.
  • Bad args → error code, no decision (I-ARG); no unwinding across FFI; handle lifecycle leak-free — verified by badargs/cabi_bad_qtype.json + badargs/cabi_bad_subnet.json.
  • ECS-from-C works (pass a subnet) and matches the DNS path's ECS handling bit-for-bit.
Fixtures
  • badargs/cabi_bad_qtype.json, badargs/cabi_bad_subnet.json, a C integration test + a Python steering-simulation test in CI.
Pitfalls
  • String/buffer ownership across FFI (qname, Location) — who frees, when.
  • Subnet/family marshalling between C and Rust IpAddr.
  • Panic across FFI = UB → catch_unwind.
  • A stale policy handle after a reload → handle generation/validation.
