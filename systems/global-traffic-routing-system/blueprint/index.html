358 — Global Traffic Routing System

Goal: Implement, from scratch in Rust, a Global Server Load Balancing (GSLB) / global traffic management system — the control + data plane that steers each client to the optimal datacenter/PoP by health, proximity (geo/latency), and policy. A distributed health-checking subsystem (active HTTP/TCP/ICMP probes + passive signals from multiple vantage points, with flap damping + vantage consensus); a decision/policy engine (simple/failover, weighted round-robin, latency-based via latency maps, geolocation/geoproximity, multi-value answer, and combinations); three steering data planes — authoritative DNS answers with EDNS Client Subnet (ECS), anycast/BGP announcement control, and HTTP 3xx redirect; a latency-map / RUM database; an IP→geo database; and config + health-state propagation to globally distributed edge responders with a defined consistency model. Crates: gtr-core / health / geo / latencymap / policy / dns / anycast / propagate / runtime / cabi / bench / conformance. It models the Route 53 traffic policies + Cloudflare Load Balancing + Akamai GTM + Google-GSLB family — it is not a generic L4/L7 load balancer (#66), not the anycast simulator (#355), not an authoritative DNS server itself (#162), and not a DNS resolver (#65); it is the global steering brain that uses those mechanisms. Correctness is validated against a deterministic policy oracle and resolver/ECS conformance suites; performance against sub-ms answer generation and detection-to-steering propagation.

1. Goal

1.1 Engineering Definition

  • Build a from-scratch GSLB / global traffic manager: endpoint/pool/health model → distributed health checking (vantage consensus + flap damping) → decision/policy engine → three steering data planes (authoritative DNS+ECS, anycast/BGP control, HTTP 3xx) → config + health-state propagation to edge responders.
  • The system answers one question per client: "which endpoint should this client use right now?" — computed from health, location, latency, and policy.
  • Concurrency model: a sharded async control plane (probers, decision engine, propagation) + an async, lock-free-on-the-hot-path data plane (answer generation per query).

1.2 System Boundaries

  • In scope: endpoint/pool/health-check domain model; active probers (HTTP/HTTPS/TCP/ICMP) + passive signal ingestion from N vantage points; vantage consensus + flap damping; the policy/decision engine (failover, weighted, latency, geo/geoproximity, multi-value, nested/composite); authoritative DNS answer generation with ECS; anycast/BGP announcement steering control (withdraw/announce per PoP health); HTTP 3xx redirect responder; the latency map (RUM aggregation) and IP→geo database; TTL strategy; propagation of policy + health state to edge responders (eventual-consistency model, versioned); observability of every steering decision.
  • Out of scope (non-goals): generic L4/L7 data-plane load balancing → #66 (a downstream that this steers to); anycast/BGP convergence simulation → #355 (we control announcements, we do not simulate the routing fabric); authoritative DNS server internals (zone storage, AXFR/IXFR, DNSSEC signing) → #162 (we generate answers; #162 is the server it plugs into); recursive resolver → #65; CDN edge serving → #159; BGP route computation → #157; service-mesh discovery → #40; generic failure detector → #197 (we reuse its patterns for vantage consensus). Deferred: DNSSEC online signing PhaseDeferred("§18"); real BGP session (BMP/BGP-LS speaker) PhaseDeferred("§22.2"); ML-based anomaly scoring of RUM PhaseDeferred; multi-tenant control plane + RBAC PhaseDeferred.

1.3 Deployment Model

  • A Rust library + three deployable roles: (1) control-plane daemon (gtrd) — owns config, runs the decision engine, aggregates health, drives propagation; (2) edge responder daemon (gtr-edge) — receives propagated state, answers DNS/HTTP at PoPs; (3) prober agent (gtr-probe) — runs at vantage points, reports health upstream. A CLI gtrctl for policy authoring, dry-run answer simulation (gtrctl resolve --client-subnet …), health inspection, and propagation status. Shared-nothing across edges except the propagation channel; control plane is the one semi-central tier (regionally replicated, §22).

1.4 Target Users

  • SREs / network engineers operating multi-region services who must understand how a request is steered to a datacenter and why a failover or geo-decision happened; learners internalizing GSLB, DNS-based steering, ECS, anycast tradeoffs, health-check consensus, and the eventual-consistency of a globally distributed control plane.
  • Downstream portfolio: #66 Load Balancer (the per-PoP L4/L7 target), #159 CDN Edge Node (a consumer of steering), #326 Inference Router (region steering for model serving), #40 Service Discovery (internal analogue).

1.9 Recommended Language & Rationale

  • Rust. (a) it is the portfolio default for networking/systems (#65/#162/#66/#157 lineage) and this reuses all of them; (b) the data plane is a high-QPS async server where safe parsing of DNS wire + ECS options + health-probe responses is exactly Rust's strength (no buffer-overrun on attacker-controlled bytes); (c) ownership/Send/Sync make the prober pool / decision engine / propagation fan-out auditable; (d) no GC pauses to perturb the sub-ms answer-latency tail; (e) extern "C" ABI so a Python control-plane UI / #326 can drive policy evaluation.
  • Rejected: Go (excellent for the control plane + propagation; GC tail jitter hurts the sub-ms answer SLO, and we already have Rust DNS/LB building blocks to reuse); C/C++ (DNS-parsing CVE history is the canonical argument against memory-unsafe steering of internet traffic); Python (control-plane orchestration only — far too slow for the per-query data plane at QPS); Erlang/Elixir (great failure model + distribution, wrong fit for the latency-sensitive DNS/HTTP data plane and the numeric latency-map math).

1.10 Prerequisites

2. Why Build This

2.1 Unique Knowledge Taught

  • Steering-mechanism tradeoffs from first principles. Why DNS-based steering is eventually consistent and slow to react (the resolver cached your answer for the TTL and will not ask again), why anycast/BGP reacts at routing-convergence speed but gives you no per-client control, and why HTTP 3xx redirect is per-request-precise but adds a full round-trip of latency. There is no single best steering mechanism — the system uses all three and exposes the tradeoff.
  • The ECS / resolver-geo-inaccuracy problem. Without EDNS Client Subnet, the GSLB sees the resolver's IP (often a far-away public DNS like 8.8.8.8), not the client's — so geo/latency steering is wrong. ECS carries a client subnet so the answer can be tailored, but it shatters the resolver cache by subnet (a cache-key explosion) and leaks client location. The tension between accuracy, cache efficiency, and privacy is the heart of geo-DNS.
  • Health-check consensus + flap damping. A single vantage point's view of "is this endpoint up?" is unreliable (its own path may be broken). Consensus across N geographically diverse vantages, plus flap damping (an endpoint that oscillates up/down must not thrash the answer), is the difference between a stable GSLB and one that amplifies every transient blip into a global re-steer.
  • The reactivity-vs-stability tension. Short TTLs + aggressive health checks → fast failover but more load, more flapping, more cache misses. Long TTLs + conservative checks → stable + cheap but slow to react. "Stale but available" vs "fresh but flapping" is the defining operational dial.

2.2 Why It Matters

  • Every multi-region internet service — every major site behind Route 53 / Cloudflare / Akamai / NS1 — is steered by this: a control plane deciding, per client, which datacenter to use, propagated to DNS/anycast/redirect data planes. The GSLB is the first hop of every request and the thing that fails a region over without anyone noticing (when it works) or takes the whole site down (when it does not). Understanding it is understanding how global services achieve availability and locality.

2.3 Engineering Muscles

  • DNS wire-format + EDNS0/ECS encoding/parsing (safe, attacker-resistant); distributed health-checking + consensus + damping; eventual-consistency design (versioned state, generation numbers, staleness bounds, propagation fan-out); policy-engine design (composable routing policies, deterministic evaluation); the latency-map / RUM aggregation pipeline; geo-IP prefix-trie lookup; anycast/BGP announcement control; the TTL/cache-staleness reasoning that pervades all DNS systems; high-QPS async data-plane engineering with a sub-ms tail.

2.4 Production Concepts Exercised

  • Multi-mechanism traffic steering (DNS/anycast/redirect); ECS-aware geo/latency routing; health-check consensus + flap damping; eventually-consistent config/health propagation with bounded staleness; TTL strategy + negative caching; composite routing policies; observability of steering decisions (per-answer trace: which policy, which endpoint, why); fail-region-over (the operational headline).

2.7 The eventual-consistency wall — the defining constraint

  • #66 (local LB) sees real-time backend health and steers per-connection; this system's data plane is DNS-cached and eventually consistent — the scarce resource is reactivity, bounded below by detection_time + propagation_time + DNS_TTL + resolver_cache_behavior.
  • Consequence 1: the TTL is the floor on reactivity. Even with instant detection and propagation, a resolver that cached a 300 s answer will keep using the dead endpoint for up to 300 s. The whole system is gated by client-side caching it does not control.
  • Consequence 2: steering is statistical, not per-request (for DNS): you steer the aggregate of clients behind a resolver/subnet, not an individual; per-request precision requires anycast (routing-controlled) or HTTP redirect (latency-costed).
  • Consequence 3: propagation must be fast and consistent — a half-propagated failover (some edges steering away, some still steering to a dead region) is worse than a slow uniform one; generation numbers + staleness bounds make propagation observable and ordered.
  • Consequence 4: health must be stable, not just fast — flap damping trades reactivity for not-thrashing; a flapping endpoint that re-steers traffic every check is a self-inflicted outage amplifier.
  • Consequence 5: ECS shatters the cache — per-subnet answers multiply resolver cache entries; geo-accuracy is bought with cache efficiency and a privacy cost.
  • This single fact — you are steering through a layer of caches you do not control — reorganizes every decision (TTL, propagation, health stability, ECS) and is the sharpest contrast with the real-time local LB (#66).

2.8 What Mastery Looks Like

  • After P2 (Consensus + Flap Damping): can read a vantage verdict log, trace the quorum calculation, and explain why a single broken vantage path did not re-steer traffic — identifying the k_fail × interval detection budget vs the false-positive suppression (I-CONS, I-DAMP, §4.3).
  • After P5 (Composite Policies): can author a nested geolocation → failover policy YAML, predict the exact SteeringDecision for a given ClientContext by hand-tracing the AST walk, and identify which specificity rule fires (continent vs country vs subdivision) — matching the deterministic oracle (I-DET, §8.4–8.5).
  • After P6 (DNS + ECS): can read RFC 7871 §6 (the ECS option encoding) and explain the SOURCE / SCOPE distinction, why the SCOPE in the response controls resolver cache fragmentation (not the SOURCE from the query), and predict the cache-entry count for a given /16 of clients given a /24 SCOPE answer (§4.2, I-ECS).
  • After P7 (TTL Strategy): can decompose the failover RTO into its four additive terms (detect + damp + propagate + TTL), identify which two the GSLB controls, and explain why reducing only the first two terms without lowering the TTL still leaves clients on the dead endpoint for up to the cached TTL (§4.1).
  • After P10 (Propagation): can describe the bounded-staleness model — what a generation is, how I-ORDER prevents stale-overwrites, why I-PROP bounds matter, and what "split steering" looks like in per-edge generation telemetry — and distinguish it from a strong-consistency model (§8.12, §22).
  • After P12 (Performance Hardening): can explain why the edge hot path must be allocation-free, what RCU (Arc-swap) buys vs a read-write lock, and how the ECS SCOPE dial trades geo-accuracy for authoritative QPS (§4.2, principle 2/9).
  • After P13 (Conformance): can construct a fault-injection scenario (e.g. kill 2-of-3 vantages + induce propagation lag + send malformed ECS) and reason from first principles which invariants each perturbation stresses, what the expected safe behavior is, and how the telemetry would confirm it (§25, Threat Model).

3.2 Box Narratives

  • gtrd control-plane facade. Entry points: author/load policies + pools, run the decision engine in compute-the-plan mode, aggregate health from probers, drive propagation to edges. Owns the authoritative config + the global health view. Thin orchestration over the crates below; regionally replicated with a leader (§22).
  • gtr-core. The vocabulary every crate speaks. Endpoint = a steerable target (IP/addr, location, weight, pool membership). Pool = a set of endpoints with a policy + health-check config. HealthCheck = a probe spec (protocol, interval, thresholds). HealthState = the consensus health of an endpoint (Healthy/Degraded/Unhealthy + score). Policy = a routing-policy AST (failover/weighted/latency/geo/multi-value/composite). SteeringDecision = the resolved set of endpoints to return + why. ClientContext = the per-query inputs (source IP, ECS subnet, resolved location, requested record type).
  • health. The distributed health subsystem. Active probers (HTTP/HTTPS status+body, TCP connect, ICMP echo) run from N vantage points; passive signals (edge-observed errors/latency) feed in too. The consensus layer fuses per-vantage verdicts into one HealthState (quorum / weighted by vantage reliability) — one broken vantage cannot flap an endpoint. Flap damping suppresses oscillation (penalty accrues on each flip, decays over time; an endpoint must "earn back" UP). The most operationally subtle subsystem: the false-positive/reactivity dial lives here.
  • geo. IP→location via a prefix trie over a geo DB (longest-prefix-match on the client subnet). Parses + applies ECS: if the query carries a client subnet, that subnet (not the resolver IP) drives geo; the answer is scoped to a returned SCOPE PREFIX-LENGTH. Computes geoproximity distance (great-circle + a per-endpoint bias) for geo-routing policies.
  • latencymap. The RUM / latency database. Ingests real-user-measurement samples (client-network → endpoint latency) and aggregates them into a client_network → endpoint → latency_estimate table (the "latency map"). Lookup powers latency-based routing: steer a client's network to its lowest-latency healthy endpoint. Handles sparse/missing data (fall back to geoproximity) and staleness (decay old samples).
  • policy. The decision engine. Evaluates a Policy AST against a ClientContext + the current HealthState + latency/geo data → a SteeringDecision. Policy kinds: failover (primary, then secondaries by health), weighted RR (distribute by weight), latency (latencymap lookup), geolocation (continent/country/subdivision match), geoproximity (nearest by distance + bias), multi-value answer (return up to N healthy, client picks), and composite/nested (a geo policy whose leaves are failover pools, etc.). Deterministic: same inputs → same decision (modulo the seeded weighted/MV shuffle) — the oracle property.
  • dns. Authoritative answer generation: assemble the A/AAAA/CNAME RRset for the decided endpoints, encode ECS in the response (echo subnet + SCOPE), set the TTL per the TTL strategy, handle negative answers (NXDOMAIN/NODATA). Produces the per-query RRset that the authoritative server (#162) serializes onto the wire — we own the answer, not the zone/server.
  • anycast. Announcement steering: from per-PoP health, decide which PoPs should announce vs withdraw an anycast prefix (a dead PoP withdraws → BGP convergence steers clients to the next-nearest live PoP). Emits announce/withdraw intents to a BGP control sink (a real BGP-4 speaker is deferred — §22.2; we ship a file/simulated sink + the decision logic). Coarse-grained (per-PoP, not per-client) but reacts at routing speed, not TTL speed.
  • http-redirect. A minimal HTTP responder that answers with 302/307 + Location pointing at the decided endpoint. Per-request precise (no caching, no resolver in the loop) at the cost of a full RTT + a TCP/TLS setup to the redirector. Used where DNS granularity is too coarse and anycast control too blunt.
  • propagate. Distributes the control plane's decisions (resolved pool→endpoint plans + HealthState) to all edge responders. Versioned by a monotonic generation number; edges apply generations in order and report their applied generation; staleness bounds define how far behind an edge may be before it is flagged. The eventual-consistency engine — its correctness (ordered, bounded-stale, no split decision) is what makes a global failover safe.
  • runtime. Process/role lifecycle: control-plane (with regional leader + epoch fencing so two leaders never propagate conflicting generations), edge responder, prober agent; config loading; the control→edge channel setup; health/propagation membership.
  • bench / conformance. Answer-latency + propagation-latency harness; the deterministic policy oracle (a reference evaluator — given inputs, the one correct decision); ECS/DNS conformance (wire-format + scope correctness vs the relevant RFCs); fault injection (kill vantages, flap endpoints, partition propagation, stale edges, malformed ECS).

3.3 Boundaries

  • Trust boundary: the public DNS/HTTP query path (untrusted clients/resolvers — malformed packets, spoofed ECS, query floods), the health-probe responses (an endpoint can return anything), the BGP control sink (announcements affect global routing — privileged), and the C ABI. All wire input is length-checked + bounds-validated; ECS is sanity-checked (subnet length caps, address-family).
  • Concurrency boundary: control plane (probers, aggregation, decision-plan compute, propagation fan-out) vs edge (per-query answer generation — read-mostly against a snapshot of propagated state). The edge hot path is lock-free against an atomically-swapped state generation; the control plane is sharded by pool.
  • Consistency boundary: propagation is the one eventual-consistency seam — the control plane is the source of truth, edges are eventually-consistent replicas bounded by a staleness target (I-class invariant). Within an edge, a single query reads one consistent generation snapshot (no torn reads across generations).
  • Coordination boundary: the regional leader + epoch is the only coordination point (who is allowed to advance the propagation generation); the data plane (edge answers) is fully local once state is propagated.

3.4 Data-flow walk — one DNS query steered by geo + health (the canonical path)

  1. A client behind resolver R asks R for app.example.com; R (a recursive resolver, #65) forwards to the authoritative server (#162) which invokes gtr-edge at the nearest PoP (anycast-routed to the edge).
  2. gtr-edge builds a ClientContext: source = R's IP; if R sent ECS, the client subnet (e.g. 203.0.113.0/24) overrides R's IP for geo (I-ECS); geo::locate does a longest-prefix lookup → client location = "EU/DE".
  3. policy::decide evaluates the pool's policy (say geolocation: EU→eu-pool, US→us-pool, default→us-pool) against the location → selects eu-pool; eu-pool's inner policy is failover(primary=eu-west-1, secondary=eu-central-1).
  4. The current propagated HealthState (generation G, staleness < bound, I-PROP) says eu-west-1 = Unhealthy (consensus across vantages, I-CONS), eu-central-1 = Healthy → failover picks eu-central-1.
  5. dns::answer assembles an A record for eu-central-1's IP, sets TTL per the TTL strategy (short during an active failover — §8.7), echoes the ECS subnet with SCOPE = /24, and returns the RRset to #162 to serialize.
  6. R caches the answer for the TTL and serves all its clients in 203.0.113.0/24 that endpoint until the TTL expires (eventual consistency — Consequence 1, §2.7); a DecisionTrace recorded policy path, location, chosen endpoint, health, generation, ECS scope.
  7. When eu-west-1 recovers, the prober vantages re-reach consensus (after flap-damping confirms stability), the control plane advances the generation, propagation pushes G+1 to edges, and new queries (after TTL) steer back — the failover RTO is detect + damp + propagate + TTL (§4).

3.5 Per-role concurrency model (control plane, edge, prober)

  • Prober agent: an async pool of probe tasks (one per (endpoint, check) scheduled at its interval); results batched + reported upstream over a control channel; isolated per-vantage so a slow probe never blocks others.
  • Control plane: sharded by pool — a health-aggregation task per pool fuses vantage reports into HealthState (consensus + damping); a decision-plan compute task recomputes resolved plans on health/config change; a propagation task fans generations out to edges; a regional-leader task holds the epoch lease. No global lock; shards are independent.
  • Edge responder: the hot path is read-mostly — each query reads an Arc-swapped immutable EdgeState snapshot (current generation's pools + health + latency/geo data) → answer generation touches no locks (principle 9). State updates from propagation build a new snapshot and atomically swap the Arc (RCU-style); in-flight queries finish on the old snapshot (no torn reads).
  • Synchronization: the only cross-task coordination is the generation epoch (leader) and the atomic snapshot swap at edges. The answer path is allocation-light and lock-free, which is what permits the sub-ms tail (§4).
  • This separation (probe ≠ aggregate ≠ decide ≠ propagate ≠ answer) is what lets the data plane stay fast and lock-free while the control plane does the heavy stateful work.

4.1 Worked reactivity budget (the failover RTO decomposition)

  • The client-observed failover time is the sum of four independent terms, only the first two of which the GSLB controls:
    • T_detect = health-check detection: k_fail × interval (e.g. 3 × 5 s = 15 s) — but consensus across vantages can shorten if probes are staggered.
    • T_damp = flap-damping confirmation: 0 on a clean hard-down; up to W on an oscillating endpoint (we deliberately wait to avoid thrash).
    • T_propagate = control→edge: < 5 s target (generation push to all edges, I-PROP).
    • T_TTL = resolver cache: up to the TTL the resolver cached (the floor we cannot control, §2.7 Consequence 1).
  • Worked: TTL=300 s steady. A hard-down endpoint: detect 15 s + damp 0 + propagate 3 s = 18 s on the control side, but a resolver that cached 1 s before the failover serves the dead endpoint for ~282 more s → client RTO ≈ 300 s.
  • The lever: lower the TTL (to 30 s) → RTO ≈ 30 s + 18 s ≈ 48 s, at the cost of 10× the query load and 10× the cache misses. This is the GSLB dial (§2.1, §8.7).
  • Anycast escape: for the latency-critical case, anycast withdrawal (§8.8) reacts at BGP convergence (~seconds) with no TTL floor — but only per-PoP, not per-endpoint. The §4 RTO target is stated with a documented TTL because the TTL term dominates and is honest about what the system controls.

4.2 Worked ECS cache-amplification (why ECS is not free)

  • Without ECS, a resolver caches one answer per name (app.example.com → A), shared by all its clients → high cache hit rate, but the answer is geo-located to the resolver, not the client.
  • With ECS, the answer is scoped to a client subnet; the resolver caches one answer per (name, subnet-scope) → if the GSLB returns SCOPE /24, a resolver serving a /16 of clients now holds up to 256 distinct cache entries for one name.
  • Worked: a public resolver (8.8.8.8 scale) serving millions of /24s → its cache for one ECS-enabled name explodes by ~the number of distinct client /24s it sees; the GSLB also serves far more distinct queries (cache misses arrive at the authoritative tier) → authoritative QPS rises with subnet diversity, not just client count.
  • The control: return the coarsest SCOPE that still steers correctly (e.g. /16 if /16-granularity geo suffices) → fewer cache entries, more sharing, but coarser steering. SCOPE 0 means "answer applies to all subnets" (no ECS tailoring) → maximal sharing, no geo precision.
  • Implication: the §4 QPS target must account for ECS subnet diversity; the geo crate exposes a configurable scope-coarsening policy (§8.6) as the cache-vs-accuracy dial.

4.3 Health-consensus budget (the false-positive vs reactivity tradeoff)

  • Detection time ≈ k_fail × interval (consecutive failed probes before declaring DOWN). Smaller k_fail/interval → faster detection but more false positives (a transient blip declared a failure → an unnecessary global re-steer).
  • Consensus decouples detection speed from false-positive rate: require a quorum of V vantages to agree DOWN. A single vantage with a broken path to the endpoint reports DOWN, but quorum (e.g. 2-of-3) is not met → no re-steer. Detection stays fast (any vantage can start suspicion) while false positives drop (quorum confirms).
  • Worked: V=3, interval=5 s, k_fail=2, quorum=2. A real outage: ≥2 vantages see 2 consecutive failures → DOWN in ~10 s. A flaky single-vantage path: 1 vantage DOWN, 2 UP → quorum not met → endpoint stays UP (no false re-steer).
  • The cost of a false positive is high (steer real traffic away from a healthy endpoint → asymmetric load, possible cascade); the cost of slow detection is bounded user impact during the detect window → the default leans toward consensus + a small k_fail (principle 8, I-CONS).
  • The budget is independent of pool size because each endpoint's consensus is local to its vantage set (O(V) per endpoint, not O(endpoints)).

6. Design Principles

  1. Steering is a decision, not a mechanism; mechanisms are pluggable. The policy engine computes which endpoint; DNS/anycast/redirect are interchangeable ways to deliver it. Violation: policy logic baked into the DNS path → can't reuse it for anycast/redirect, can't test it in isolation.
  2. The data plane is read-mostly and lock-free; the control plane does the stateful work. Edges answer from an atomically-swapped immutable snapshot (principle 9). Violation: taking a lock per query → tail-latency collapse under QPS, the sub-ms SLO is gone.
  3. Stale-but-available beats fresh-but-unavailable. An edge with lagging propagation answers from its last-good snapshot rather than failing. Violation: refusing to answer when behind → a propagation hiccup becomes a global DNS outage (the worst failure mode).
  4. Health must be stable, not just fast: consensus + flap damping are mandatory. A single vantage cannot re-steer traffic; an oscillating endpoint is damped. Violation: per-vantage instant re-steer → one broken probe path or a flapping endpoint thrashes global traffic (self-inflicted outage).
  5. Propagation is ordered and bounded-stale; never split. Generations apply in order; staleness is bounded + observable; a partial failover is detectable. Violation: unordered/unbounded propagation → some edges steer to a dead region while others don't (split steering — worse than slow).
  6. Determinism: same inputs → same decision (modulo a seeded shuffle). The decision engine is a pure function of (policy, context, health, generation, seed) — the oracle property. Violation: nondeterministic decisions → untestable, undebuggable steering ("why did this client get that endpoint?").
  7. The TTL is a first-class, policy-controlled output — and an honest one. TTL trades reactivity for cache load; it shortens during failover. Violation: a fixed long TTL → failovers take the full TTL; a fixed short TTL → resolver/auth overload. Pretending TTL doesn't gate reactivity → wrong RTO expectations.
  8. Fail-safe, not fail-open or fail-closed blindly: a steering failure defaults to the safest available answer. No health data → return all-configured (last-known) rather than empty. Violation: empty answer on uncertainty → clients get NXDOMAIN/SERVFAIL → total outage from a control-plane wobble.
  9. The answer hot path is allocation-light and touches no shared mutable state. Geo/latency/policy lookups read immutable structures; the answer buffer is from a per-task pool. Violation: per-query allocation + shared mutation → GC-like pauses, contention, tail blowup.
  10. ECS is honored, sanity-checked, and scope-minimized. Echo the client subnet, validate it (length caps, family), return the coarsest correct SCOPE. Violation: trusting ECS blindly → spoofed-subnet steering abuse + cache poisoning; over-fine scope → cache explosion (§4.2).
  11. Observability of every steering decision. Each answer can emit a DecisionTrace: policy path, client location, ECS scope, chosen endpoint, health state, generation, TTL. Violation: opaque steering → "why did this client hit that region?" is unanswerable in an incident.
  12. The control plane has one writer per generation (leader + epoch). Only the regional leader advances the propagation generation; epoch fencing rejects a stale leader. Violation: two leaders advancing generations → conflicting global state, split steering (principle 5 broken at the source).
  13. Probe load on endpoints is bounded and respectful. A capped probe rate per (endpoint, vantage, interval); shared health, not per-pool re-probing. Violation: unbounded health checks → the GSLB DDoSes its own endpoints (a real outage cause).
  14. Correctness anchored to the deterministic policy oracle + RFC conformance. Every decision is checkable against a reference evaluator; every ECS/DNS wire output against the RFC. Violation: no oracle → steering bugs ship silently and manifest as mysterious regional imbalance in production.

8. Domain Model — Endpoints, Health, Policy, ECS/DNS, Propagation

8.1 Endpoint / pool model

  • An Endpoint is a steerable target: { id, addr (IPv4/IPv6 or CNAME target), location (lat,lon,country,continent), weight, healthcheck_ref, pool_ref }.
  • A Pool groups endpoints under one Policy + one HealthCheck spec: { id, name, endpoints: Vec<EndpointId>, policy: Policy, healthcheck: HealthCheck, ttl }.
  • A PolicySet (Route-53-"traffic-policy"-style) is the top-level: a name → a (possibly nested) Policy whose leaves resolve to pools/endpoints.
  • Endpoints can be shared across pools; health is computed once per endpoint (per its check), not per pool (I-PROBE-BUDGET).

8.2 Health-check model + consensus

  • A HealthCheck = { kind: Http{path,expect_status,expect_body?} | Tcp{port} | Icmp, interval, timeout, k_fail, k_pass }.
  • Each vantage point runs the check independently → a per-vantage verdict {Up|Down, rtt, ts}.
  • Consensus: the control plane fuses vantage verdicts into one HealthState ∈ {Healthy, Degraded, Unhealthy} using a quorum (≥ ⌈(V+1)/2⌉ agree) optionally weighted by per-vantage reliability (I-CONS). Degraded = quorum-Up but elevated RTT / partial failures → eligible but de-preferred.
  • State transitions require k_fail consecutive failing intervals to go Up→Down and k_pass to go Down→Up (hysteresis), and quorum at each step.

8.3 Flap damping (the stability mechanism)

Event Effect
Endpoint flips state (Up↔Down) penalty += flip_cost
Each interval with no flip penalty *= decay (exponential decay)
penalty ≥ suppress_threshold endpoint damped: held in current (usually Down) state, not eligible to re-steer
penalty < reuse_threshold (after decay) damping released; endpoint re-eligible
  • Borrowed from BGP route-flap damping. Prevents an oscillating endpoint from re-steering global traffic every interval (I-DAMP). The thresholds are the reactivity-vs-stability dial (§4.3); too aggressive → a recovering endpoint is held down too long; too lax → thrash.

8.6 ECS handling + scope (RFC 7871)

  • The OPT pseudo-RR (EDNS0) may carry an ECS option: { FAMILY (1=IPv4,2=IPv6), SOURCE PREFIX-LENGTH, SCOPE PREFIX-LENGTH, ADDRESS }.
  • On query: SCOPE = 0; SOURCE PREFIX-LENGTH + ADDRESS carry the client subnet the resolver chose to reveal (e.g. /24).
  • We validate (I-ECS-SAFE): family ∈ {1,2}; SOURCE ≤ caps (default 24 for v4, 56 for v6); address bits beyond SOURCE zeroed.
  • Geo uses that subnet for LPM (I-ECS) instead of the resolver IP.
  • On response: echo the option with SCOPE PREFIX-LENGTH = the granularity at which the answer is valid (the coarsest prefix that still yields this answer — §4.2 cache-vs-accuracy). SCOPE 0 = answer applies to all subnets (no ECS tailoring).
  • Caching: the resolver keys its cache on (name, type, ECS scope) → the scope we return controls cache fragmentation (principle 10).

8.7 TTL + negative-caching strategy

  • Steady-state TTL: configurable per pool (default 300 s) — balances reactivity vs resolver/auth load (principle 7).
  • During an active failover / unstable health: TTL is shortened (default 30 s) so the eventual-consistency window narrows when it matters (§4.1).
  • TTL floor: a minimum (e.g. 5 s) to prevent pathological re-query storms (I-TTL).
  • Negative caching (RFC 2308): NXDOMAIN/NODATA carry the SOA-minimum TTL (we supply it to #162); a transient all-unhealthy must not be cached as NXDOMAIN long — we prefer I-FAILSAFE (return last-known) over an NXDOMAIN that resolvers cache.
  • Anycast vs DNS reactivity: for latency-critical pools, pair a longer DNS TTL with anycast withdrawal (routing-speed reaction) so the TTL floor does not gate failover (§8.8).

8.8 Anycast / BGP announcement control

  • A set of PoPs announce the same anycast prefix; the routing fabric (modeled by #355, real session by #157) delivers each client to its nearest-by-BGP PoP (catchment).
  • Steering = announce/withdraw: an unhealthy PoP withdraws the prefix → BGP converges → its catchment shifts to the next-nearest live PoP. Reacts at convergence speed (seconds), no TTL floor, but per-PoP, not per-client/per-endpoint (coarse).
  • We emit Announce(prefix, pop) / Withdraw(prefix, pop) intents to a BGP control sink. A real BGP-4 speaker is deferred (§22.2, PhaseDeferred); P8 ships the decision logic + a file/simulated sink + a hook to #157.
  • Hazards: withdrawing a PoP shifts its load onto neighbors → a thundering herd / cascade if a large PoP withdraws (a neighbor now over-capacity). The control plane models catchment load (coarsely) and supports gradual/partial withdrawal.

8.9 Steering-mechanism comparison (the core tradeoff, §2.7)

Mechanism Granularity Reactivity Cost Use when
DNS answer per-resolver / per-ECS-subnet TTL-floored (slow) cheap; cache-amplified by ECS default geo/latency/weighted steering
Anycast withdraw per-PoP (coarse) BGP convergence (~s); no TTL floor needs BGP control; load-shift hazard latency-critical failover; DDoS shedding

  • No single best mechanism (principle 1). Many real systems layer them: DNS for coarse geo, anycast for fast regional failover, redirect for per-request precision.

8.10 Worked example — latency-based routing via the latency map

  • Goal: steer client network 198.51.100.0/24 to its lowest-latency healthy endpoint among {us-east-1, us-west-2, eu-west-1}.
  • The latencymap holds RUM-aggregated estimates: 198.51.100.0/24 → {us-east-1: 22 ms, us-west-2: 65 ms, eu-west-1: 95 ms} (decayed real-user samples).
  • policy::decide (Latency policy): filter by health (all Healthy) → look up the client network in the latency map → pick us-east-1 (22 ms).
  • Sparse-data fallback: if the client network has no RUM samples, fall back to geoproximity (nearest by great-circle distance) → and emit latency_fallback=geoproximity in the trace.
  • Staleness: samples decay (an endpoint that got slower must lose its old low estimate) → the map is re-aggregated on a window; stale entries below a confidence threshold trigger the geoproximity fallback.
  • Contrast with §8.5 geolocation: geolocation is a static region→pool map (no measurement); latency is measured and adapts to real network conditions — but needs data and is noisier.

8.12 Propagation + consistency model

  • The control plane is the source of truth: it computes a ResolvedPlan (pools, endpoints, current HealthState, latency-map deltas, policy versions) and stamps it with a monotonic generation number G (advanced only by the leader, I-LEADER).
  • Propagation: push G (full or delta) to all edges; each edge applies in order (I-ORDER), atomically swaps its snapshot (I-SNAP), and acks its applied generation.
  • Staleness: the control plane tracks leader_gen − edge_gen per edge; an edge beyond N generations / T seconds is stale (I-PROP) → flagged, re-pushed, possibly quarantined (stop sending it new clients via anycast).
  • Eventual consistency: edges converge to G; during a push, edges may transiently be at G or G−1 (a query reads one consistent snapshot, never a mix — I-SNAP). A split (some edges at a generation that steers away from a dead region, others still at a generation that steers to it) is bounded by the staleness window and observable via per-edge generation telemetry.
  • Why ordered + bounded: an unordered apply could overwrite fresh health with stale (I-ORDER prevents); an unbounded lag could leave an edge steering to a long-dead region (I-PROP bounds it) — both are the difference between a safe failover and a dangerous one (principle 5).

8.13 State machines

  • Endpoint health: Unknown → (k_pass) Healthy ⇄ Degraded ⇄ (k_fail) Unhealthy; any rapid oscillation → Damped(held) (I-DAMP) → decays back.
  • Edge: Booting → Syncing(catching up to leader gen) → Live(within staleness) → {Stale(flagged) | Quarantined}; Live ↔ Stale by the staleness monitor.
  • Control-plane leader: Follower → Candidate → Leader(epoch e) → {Stepped-down | Fenced(stale epoch)} (I-LEADER).
  • Anycast PoP: Announcing ⇄ Withdrawing(unhealthy) ⇄ Drained.

14. Phase 2 — Vantage consensus + flap damping

14.1 Objectives

  • Fuse per-vantage verdicts from V vantages into one stable HealthState via quorum consensus (I-CONS), and suppress oscillation via flap damping (I-DAMP) — the stability heart (principle 4).

14.2 Detailed Implementation Steps

  • health::vantage — register V vantages; collect their verdicts per endpoint with timestamps.
  • health::consensus — quorum fuser: ≥ ⌈(V+1)/2⌉ agree → that state; weighted by VantageWeights (per-vantage reliability); Degraded when quorum-Up but elevated RTT/partial (I-CONS).
  • health::flap_damp — penalty accrues on each state flip, decays exponentially; ≥ suppress_threshold → damped (held); < reuse_threshold → released (I-DAMP, §8.3).
  • Integrate: an endpoint's published HealthState = consensus, then damping override.
  • Stale-vantage handling: a vantage that stops reporting is excluded from quorum after a timeout.

14.3 Deliverable

  • Consensus + damping over multi-vantage verdicts; examples show one broken vantage not flipping an endpoint, and an oscillating endpoint being damped.

14.4 Acceptance Criteria

  • A single dissenting vantage does not change HealthState when quorum (≥ ⌈(V+1)/2⌉ of V, e.g. 2-of-3) disagrees (I-CONS) — verified by health/single_vantage_no_flap.json.
  • An endpoint flipping > k times in window W is damped and held until stable (I-DAMP) — verified by health/flap_damp.json.
  • A stopped vantage is excluded from quorum within its timeout (not counted as DOWN forever) — verified by health/stale_vantage.json.

14.5 Conformance Fixtures

Fixture Purpose Expected
health/consensus_quorum.json quorum DOWN endpoint DOWN only at quorum (I-CONS)
health/single_vantage_no_flap.json one broken vantage endpoint stays UP, no re-steer (I-CONS)
health/flap_damp.json oscillating endpoint held in damped state (I-DAMP)
health/stale_vantage.json stale vantage report excluded; last state held

14.6 Pitfalls

  • Even V → quorum ties; define the tie-break (lean to last-known / Healthy per failsafe) explicitly.
  • Damping a recovering endpoint too long (a real recovery looks like a flip) → tune decay; k_pass + damping interact.
  • Vantage clock skew on verdict timestamps → use receipt order / bounded windows, not absolute time.
  • A correlated-failure (all vantages share a broken upstream) → quorum agrees DOWN correctly, but document that consensus assumes independent vantage paths.

14.7 Performance Concerns

  • Consensus is O(V) per endpoint per update — cheap; the cost is the latency of waiting for quorum (vs single-vantage instant) — the deliberate stability tax (§4.3).

14.8 Edge Cases

  • V=1 (no consensus, single vantage — document degraded guarantee); all vantages disagree (no quorum → hold last); simultaneous flip + vantage loss.

14.9 Failure Analysis

  • A consensus bug that under-counts → false DOWN → global re-steer (highest-impact health bug) → quorum fixtures + the single-vantage-no-flap test + vantage_votes telemetry.
  • docs/failure-analysis/false-positive-health.md.

14.10 Operational Notes

  • HealthMetric (quorum, vantages_up, flap_penalty, damped); docs/runbooks/flapping-endpoint.md; document the consensus + damping tuning (the reactivity-vs-stability dial).

15. Phase 3 — Latency map: RUM ingestion + aggregation + lookup

15.1 Objectives

  • Build the latency database: ingest real-user-measurement samples, aggregate into a client_network → endpoint → latency_estimate map, with decay + confidence + a lookup for latency-based routing.

15.2 Detailed Implementation Steps

  • latencymap::rum_ingest — accept RumSample{ client_net, endpoint, rtt_ms, ts } (from edge-observed or beacon measurements; the RUM-driven server-selection pipeline of Krishnan et al. 2009, ADR-10).

  • latencymap::lookup — given a client network, return per-endpoint estimates; confidence threshold gating the geoproximity fallback (ADR-10, measured > static).
  • Client-network bucketing — aggregate at /24 (v4) / /48 (v6) granularity (configurable).

15.3 Deliverable

  • Ingest RUM samples, aggregate, look up a client network's per-endpoint latencies; examples/latency_routing shows a network steered to its lowest-latency endpoint.

15.4 Acceptance Criteria

  • Aggregation produces stable estimates under sample noise (EWMA convergence).
  • Decay down-weights old samples so a regressed endpoint loses its low estimate over the window.
  • Lookup returns estimates with confidence; below threshold → signals fallback (I, §8.10).

15.5 Conformance Fixtures

  • policy/latency_map_aggregate.json, policy/latency_decay.json, policy/latency_lookup_confidence.json.

15.6 Pitfalls

  • Sample skew (a few outlier RTTs dominating) → robust aggregation (trimmed mean / EWMA, not raw mean).
  • Cold-start: a client network with no samples → must fall back (geoproximity), not return garbage.
  • Stale data presented as fresh → confidence + decay must gate it.
  • Memory growth (millions of client networks × endpoints) → bucket coarsely; bound the table; evict cold entries.

15.7 Performance Concerns

  • Lookup on the hot path (< 1 µs target) → hashed by client network; the map is part of the edge snapshot (I-SNAP).
  • Ingestion off the hot path (control-plane / async); aggregation batched.

15.8 Edge Cases

  • Single sample (low confidence); all endpoints equidistant in latency (tie → stable tie-break); a new endpoint with no data (fallback); IPv6 networks.

15.9 Failure Analysis

  • A bad aggregation → wrong latency steering → measured-vs-expected fixtures + the geoproximity fallback as a safety net.
  • A memory leak in the map → bounded table + eviction + mem telemetry.

15.10 Operational Notes

  • Per-network/endpoint estimate + confidence + sample-count metrics; document the RUM source, bucketing, decay window, and the fallback threshold.

  • anycast::bgp_sink — the BgpSink trait: a file/simulated sink now; a hook to #157 (real speaker) deferred (PhaseDeferred("§22.2")).
  • anycast::intent — AnnounceIntent emission + idempotency (re-announcing a live PoP is a no-op; ADR-14).
  • Gradual/partial withdrawal: stagger withdrawals to avoid dumping a large PoP's load on one neighbor at once (Schlinker et al. 2018 egress-control lineage, §8.8).

20.3 Deliverable

  • Per-PoP announce/withdraw intents from health, with a simulated sink; examples show an unhealthy PoP withdrawing and its catchment (coarsely) shifting; integration point for #355's convergence model.

20.4 Acceptance Criteria

  • An unhealthy PoP withdraws within one damped health transition; a recovered PoP re-announces (idempotent) — verified by propagation/anycast_withdraw_on_unhealthy.json + propagation/anycast_reannounce.json.
  • Withdrawal emits the correct intent to the sink; catchment-load estimate flags an at-risk neighbor — verified by fault/anycast_load_shift.json.
  • No flapping of announcements (reuse health damping, I-DAMP): zero re-announce/withdraw cycles for a damped (held) endpoint across the fixture suite.

20.5 Conformance Fixtures

  • propagation/anycast_withdraw_on_unhealthy.json, propagation/anycast_reannounce.json, fault/anycast_load_shift.json.

20.6 Pitfalls

  • Withdrawing a large PoP overloads a neighbor (thundering herd) → gradual withdrawal + catchment-load check (§8.8).
  • Announcement flapping (a flapping PoP withdrawing/announcing repeatedly) → gate by damped health, not raw (I-DAMP).
  • Anycast is per-PoP, not per-client/endpoint — do not promise fine steering it cannot give (principle 1).
  • A withdrawn-but-still-receiving-traffic window (convergence lag) → clients in flight during convergence; document the #355-modeled lag.

20.7 Performance Concerns

  • Announcement changes are rare (health-event-driven), not per-query → off the hot path entirely.
  • Convergence latency is the routing fabric's (seconds), modeled by #355 — outside our control.

20.8 Edge Cases

  • All PoPs unhealthy (withdraw all → blackhole? or hold last per failsafe — define); a single-PoP anycast (withdraw = total outage → guard); IPv6 anycast prefix.

20.9 Failure Analysis

  • A withdraw bug → either a dead PoP keeps receiving (no failover) or a healthy PoP withdraws (self-outage) → announce/withdraw fixtures + the load-shift fault test.
  • docs/failure-analysis/thundering-herd.md (catchment load-shift on withdrawal).

20.10 Operational Notes

  • Announcement-state metrics per PoP + catchment-load estimate; document the BGP-sink abstraction + the #157/#355 integration + the real-session deferral.

21. Phase 9 — HTTP 3xx redirect responder

21.1 Objectives

  • Implement the per-request-precise steering mechanism: an HTTP responder that answers 302/307 + Location pointing at the decided endpoint (principle 1, §8.9) — for fine control where DNS is too coarse and anycast too blunt.

21.2 Detailed Implementation Steps

  • http_redirect::server — a minimal async HTTP/1.1 (+ HTTPS) responder; parse the request (Host, path, client IP, optional X-Forwarded-For) (ADR-15).
  • http_redirect::redirect — build a ClientContext from the request (client IP, no ECS — the client IP is the client here), call policy::decide (I-DET), return 302 Found (temporary, cacheable per Cache-Control) or 307 (no-method-change) + Location: https://<endpoint>/<path>.
  • Cache-Control on the redirect: short max-age (the per-request precision is lost if the redirect is cached long).
  • Reuse the same decision engine (Design Principle 1, ADR-4) — the only difference from DNS is the delivery + that the client IP is exact (no resolver indirection).

21.3 Deliverable

  • An HTTP redirector that steers each request to the decided endpoint; examples curl → 302 to the right region.

21.4 Acceptance Criteria

  • A request gets a 302/307 to the policy-decided endpoint; the client IP drives geo directly (no ECS/resolver indirection — most accurate).
  • Cache-Control bounds redirect caching; the decision matches the DNS path's decision for the same client (principle 1, consistency).

21.5 Conformance Fixtures

  • policy/redirect_decision.json (== DNS decision for same ctx), dns/redirect_cache_control.json.

21.6 Pitfalls

  • X-Forwarded-For spoofing → trust only from known proxies; otherwise use the connection IP (a steering-abuse vector).
  • Redirect caching (302 is cacheable) → set Cache-Control to keep per-request precision.
  • The added RTT + TCP/TLS setup is the cost — do not use where DNS suffices (principle 1).
  • Redirect loops (redirecting to a host that redirects back) → guard / cap.

21.7 Performance Concerns

  • A full TCP+TLS handshake + a round-trip per redirect → the latency cost that makes this the precise-but-expensive mechanism; keep the responder itself fast (reuse the lock-free decision path).
  • Connection reuse / keep-alive for the redirector.

21.8 Edge Cases

  • A client behind a proxy chain (which IP?); HTTPS with SNI; a request to a path the endpoint doesn't serve (redirect anyway — the endpoint handles it); HTTP/2.

21.9 Failure Analysis

  • A redirect bug → wrong endpoint or a loop → the same decision engine + the redirect fixtures (consistency with DNS) guard it.
  • XFF-spoof steering abuse → trusted-proxy config + the threat model.

21.10 Operational Notes

  • DecisionMetric reused (mechanism=redirect); document the XFF-trust config + when to prefer redirect vs DNS vs anycast (§8.9).

22. Phase 10 — Propagation + consistency model + control-plane leader/epoch

22.1 Objectives

  • Build the propagation engine + consistency model (principle 5, I-PROP/I-ORDER/I-SNAP) and the control-plane leader + epoch (principle 12, I-LEADER): the control plane computes versioned generations, propagates them ordered + bounded-stale to edges, and only one leader advances generations.

22.2 Detailed Implementation Steps

  • propagate::generation — stamp each ResolvedPlan with a monotonic Generation (leader-advanced, I-LEADER); full + delta encodings.
  • propagate::fanout — push generations to all edges (control→edge channel); retries; per-edge progress.
  • propagate::apply — edge side: apply generations in monotonic order (reject regress, I-ORDER); build a new EdgeState; atomically Arc-swap (I-SNAP).
  • propagate::staleness — track leader_gen − edge_gen + age per edge; flag Stale beyond N gens / T secs (I-PROP); quarantine (stop anycast-routing clients to a too-stale edge).
  • runtime::leader + runtime::epoch — regional leader election + epoch lease; fence rejects a stale-epoch leader's generations (I-LEADER); on leader change the epoch bumps.
  • The real BGP speaker for anycast (§20) and DNSSEC online signing are gated here as PhaseDeferred.

22.3 Deliverable

  • Control plane propagates versioned state to N edges, ordered + bounded-stale + acked; a leader change fences the old leader; examples/gtrctl prop-status show per-edge generation lag.

22.4 Acceptance Criteria

  • Edges converge to the leader's generation within the staleness bound (I-PROP); applied in order, no regress (I-ORDER); each query reads one snapshot (I-SNAP).
  • A second leader's generations are fenced by epoch (I-LEADER); no split steering.
  • A stale/partitioned edge serves last-good (principle 3) and is flagged.

22.5 Conformance Fixtures

Fixture Purpose Expected
propagation/ordered_apply.json generation ordering applied monotonically (I-ORDER)
propagation/staleness_bound.json staleness edge within N gen / T s (I-PROP)

22.6 Pitfalls

  • Out-of-order delivery applying an old generation over a new one → monotonic compare on apply (I-ORDER).
  • A split-brain control plane (two leaders) → epoch fencing (I-LEADER); without it, conflicting generations → split steering (the worst failure, principle 5).
  • An edge that acks but didn't actually apply → ack only after the Arc-swap; verify via a state hash.
  • Delta propagation losing a generation (gap) → require contiguous generations or re-sync full on gap.
  • Quarantining too aggressively (a briefly-stale edge dropped from rotation) → tune the staleness bound.

22.7 Performance Concerns

  • Propagation is event-driven (health/config change), batched; deltas keep it small; the Arc-swap is O(1) (the new state is built off the hot path).
  • Fan-out to many edges → parallel push; the bottleneck is the slowest/farthest edge (bounded by I-PROP).

22.8 Edge Cases

  • An edge joining mid-stream (full sync to current gen); leader crash mid-push (new leader resumes); a generation with no changes (skip); a network partition isolating a region (that region's edges go stale → quarantined).

22.9 Failure Analysis

  • Split steering (some edges steer to a dead region, others away) is the highest-severity failure → ordered + bounded-stale + leader-fenced propagation + per-edge generation telemetry + the bounded-split fault test are the net (principle 5).
  • docs/failure-analysis/split-steering.md; docs/runbooks/stale-edge.md.

22.10 Operational Notes

  • PropMetric (leader_gen, edge_gen, lag, stale, apply_us); tools/prop_status; docs/propagation-protocol.md (versioned); document the leader/epoch + staleness tuning + the quarantine policy.

Threat Model

Attack surface: the public DNS/HTTP query path (untrusted resolvers/clients), the health-probe responses (an endpoint can reply with anything), the BGP control sink (announcements move global traffic — privileged), the propagation channel (control→edge), and the C ABI. Unlike a local LB (#66), this system steers internet traffic, so a malformed-input or steering-abuse bug has global blast radius. The wire (DNS/EDNS/ECS bytes) is the primary trust boundary.

Compatibility & Versioning

  • DNS/EDNS/ECS wire: RFC-1035/6891/7871-conformant; the answer the hook hands to #162 is a stable contract (I-WIRE/I-ECS). The #162 answer-hook ABI is versioned; a break is a major version here.
  • Propagation protocol: versioned (docs/propagation-protocol.md); generation/delta encoding + edge apply/ack; an edge negotiates the protocol version and refuses an incompatible leader (analogue of I-ORDER safety). Propagation version is tracked separately from the library SemVer (ADR-30).
  • Policy spec (the AST): docs/policy-spec.md is the normative grammar (§8.4); the Policy/Target2/Region model is stable; new policy kinds extend via #[non_exhaustive], never break an existing policy's evaluation (I-DET — an old policy decides identically across versions).
  • C/Python ABI: function signatures, error codes (§11.12), and handle semantics are frozen (SemVer-major to change).
  • Decision semantics: deterministic (I-DET) — the same (policy, context, health, generation, seed) decides identically across versions; a change to evaluation that alters a decision is a major version + a CHANGELOG entry + a migrated golden.
  • TTL / negative-caching behavior: the TTL strategy (steady/failover/floor, RFC-2308 negative) is a stable, documented contract (principle 7, I-TTL); changing default TTLs is a minor + CHANGELOG (operationally visible).
  • Geo DB format: the MaxMind-CSV-style loader format is stable; the geo DB content is versioned independently (accuracy goldens pin a DB version — §25.6).
  • Deprecation: one minor-version warning cycle; a mixed-version edge fleet during a rolling upgrade is supported (version negotiation); a mixed-version control-plane leader set is not (leader hand-off, not concurrent mixed leaders).

Testing & Verification Strategy

  • Deterministic policy oracle (the backbone): every decision is checked against an independent reference evaluator — given (policy, context, health, generation, seed) the one correct SteeringDecision (principle 6/14, I-DET). The engine and the oracle must agree bit-for-bit on the chosen endpoint set, TTL, and trace.
  • RFC conformance (the wire backbone): DNS/EDNS/ECS output validated against RFC 1035/6891/7871 — parse-back round-trip, dig/reference cross-check, and exhaustive ECS SCOPE/family/zeroing cases (I-WIRE/I-ECS).
  • Differential / replay: replay a labeled client → expected-region corpus and a recorded query stream; the decision is reproducible from the trace (I-DET) — a steering bug is re-derivable, not a heisenbug.
  • Property (proptest): policy-evaluation totality (always a decision or a typed failsafe, never empty — I-FAILSAFE); consensus monotonicity (more agreeing vantages never flips the verdict the wrong way); LPM correctness (longest match wins, I-LPM); flap-damping convergence (penalty decays to release).
  • Fuzz (cargo-fuzz): dns_parse, ecs_parse, policy_eval, geo_lookup, propagation_apply (I-WIRE/I-ECS-SAFE/I-ARG); ASAN/Miri on the parsers and the FFI boundary; assert no panic, no UB, bounded memory on arbitrary bytes.
  • Fault injection (seeded, reproducible): kill vantages (consensus holds, I-CONS), flap endpoints (damping holds, I-DAMP), partition propagation (bounded staleness + failsafe, I-PROP/I-FAILSAFE), induce two leaders (fenced, I-LEADER), drop/regress generations (rejected, I-ORDER), malformed DNS/ECS + spoofed XFF (I-WIRE/I-ECS-SAFE).
  • Concurrency: TSan on the edge hot path + the RCU Arc-swap (I-SNAP — no torn read across a generation swap under load) and the control-plane shards.
  • Multi-role harness: a docker-compose cluster (control plane + N edges + V probers + fake endpoints) for CI; a resolver (dig) drives the DNS path end-to-end; the propagation seam is exercised with induced lag.
  • Steering-accuracy harness: measure geo-accuracy with and without ECS against a labeled set; hold-out validation to avoid overfitting the geo DB (§24.6).
  • Soak/chaos (deferred): a long fault soak + a large-fleet propagation soak → PhaseDeferred.
  • Performance regression: answer-latency (HDR), propagation-latency, and accuracy gates per query mix (query types × ECS spread × policy shapes).

Performance Engineering

  • Hot path first (the SLO): the edge answer path is the SLO surface — p99 < 1 ms (excl. network) at ≥ 50 k qps/core. Lock-free against the RCU snapshot (I-SNAP), allocation-light (per-task buffer pool, principle 9), with the geo trie + latency map laid out for cache locality.
  • Profiling: flamegraphs on the answer path; HDR latency histograms (the tail, p99, is the metric — not the mean); perf + cache-miss counters on the geo LPM and the DNS encoder; allocator analysis to assert no hot-path allocation.
  • Geo-lookup tuning: a level-compressed (LC-trie style) prefix trie for < 1 µs LPM (I-LPM); warm in cache; measured against the geo-DB scale (§4 assumptions).
  • DNS encoder tuning: pre-sized buffers, reuse, name-compression only where it pays; the encoder is on the hot path (§18.7).
  • Propagation tuning: delta + batch encoding; parallel fan-out; the slowest/farthest edge bounds convergence (I-PROP) — characterized, not assumed.
  • The reactivity/cache tradeoffs: the TTL dial (§4.1) and the ECS SCOPE dial (§4.2) are systemic perf levers (resolver + auth QPS), benchmarked with realistic subnet diversity, not a single client.
  • Targets: §4 — enforced by the bench gate per query mix.

Scalability Analysis

  • Edge (data plane) scaling: answer generation is per-core-shard, lock-free against an immutable snapshot (I-SNAP) → scales horizontally with PoPs/cores; the snapshot is read-only so adding edges adds no coordination (principle 2). The ceiling is per-edge QPS × edge count, and the geo-trie/latency-map memory per edge (bounded, RCU snapshot).
  • The eventual-consistency wall (the defining scaling factor, §2.7): reactivity does not scale down with effort — it is floored by detect + damp + propagate + TTL, and the TTL term is client-side caching we do not control. Scaling clients/regions multiplies the propagation fan-out and the ECS cache cardinality, not the per-decision cost.
  • Propagation scaling: fan-out to E edges is parallel + delta-encoded; the bound is the staleness window (I-PROP), not E directly; for very large E a tree/gossip fan-out (SWIM lineage, #197) keeps per-node load O(1). The control plane is sharded by pool → adding pools adds independent shards (no global lock).
  • Health scaling: consensus is O(V) per endpoint (V = vantages, small + fixed), independent of endpoint count → health scales with endpoints linearly in probe work (bounded by I-PROBE-BUDGET), not super-linearly.
  • ECS cache scaling (the subtle one): finer SCOPE multiplies resolver cache entries and authoritative QPS by subnet diversity (§4.2) → the scope-coarsening policy (§8.6) is the lever; geo-accuracy is traded for cache + QPS scaling.
  • Control-plane scaling: one writer per generation (leader, I-LEADER) is a deliberate serialization point for correctness (no split steering) — generation advance is cheap (a stamp), so it is not a throughput bottleneck; the heavy work (consensus, decision-plan compute) is sharded and parallel.
  • What does NOT scale here (by design): per-PoP L4/L7 connection balancing (that is #66's job); the routing-fabric convergence (that is the network / #355); recursive resolution (that is #65). This system scales the global steering decision + its propagation, not the per-connection data plane.

Mental Models & First Principles

The compressed insights an expert GSLB engineer holds. Each: the model, what it predicts, the bug class you write without it, and where this blueprint applies it.

  • MM1 — Steering is a decision; the mechanism is interchangeable delivery. The policy engine computes which endpoint; DNS/anycast/redirect just deliver it. Predicts: the same decision logic must serve all three mechanisms. Without it: policy logic baked into the DNS path, untestable and unreusable. Applied: Design Principle 1, §3.2, P4–P9.
  • MM2 — You steer through caches you do not control; the TTL is the reactivity floor. Predicts: failover RTO is bounded below by the cached TTL even with instant detection + propagation. Without it: you "fix" failover speed by tuning detection and wonder why clients still hit the dead region. Applied: §2.7, §4.1, I-TTL.
  • MM3 — DNS steering is statistical, not per-request. You steer the aggregate of clients behind a resolver/subnet, not an individual. Predicts: per-request precision needs anycast or HTTP redirect. Without it: you promise per-client DNS steering that physically cannot exist. Applied: §2.7 Consequence 2, P6/P8/P9.
  • MM4 — Without ECS the GSLB sees the resolver, not the client. ECS fixes geo accuracy but shatters the resolver cache by subnet. Predicts: accuracy is bought with cache cardinality + a privacy cost. Without it: you geo-route to 8.8.8.8's location and mis-steer the client. Applied: §2.1, §4.2, I-ECS.
  • MM5 — One vantage's "down" is noise; truth is a quorum. Predicts: a single broken probe path will report DOWN; only consensus should re-steer. Without it: one broken vantage flaps global traffic. Applied: §4.3, I-CONS.
  • MM6 — A flapping endpoint is a self-inflicted outage amplifier; damp it. Predicts: re-steering on every health flip thrashes traffic worse than the original blip. Without it: the GSLB amplifies transient instability into a global incident. Applied: Design Principle 4, I-DAMP.
  • MM7 — A half-propagated failover (split steering) is worse than a slow uniform one. Predicts: unordered/unbounded propagation lets some edges steer to a dead region while others don't. Without it: a failover that half-lands corrupts global state. Applied: Design Principle 5, §22, I-ORDER/I-LEADER.
  • MM8 — Stale-but-available beats fresh-but-unavailable. Predicts: an edge behind on propagation should serve its last-good snapshot, not fail. Without it: a propagation hiccup becomes a global DNS outage. Applied: Design Principle 3, I-FAILSAFE.
  • MM9 — The data plane is read-mostly; an RCU snapshot swap buys the sub-ms tail. Predicts: a per-query lock collapses the tail under QPS. Without it: the p99 SLO dies at load. Applied: Design Principles 2/9, §3.5, I-SNAP.
  • MM10 — One writer per generation (leader + epoch) is deliberate serialization for correctness, not a bottleneck. A generation advance is a cheap stamp; the heavy work is sharded. Predicts: two writers → conflicting global state. Without it: split steering at the source. Applied: Design Principle 12, §22, I-LEADER.

Numbers derived from System Constraints (§4): p99 < 1 ms answer; ≥ 50 k qps/core; geo DB ~4M prefixes; V ≈ 3–9 vantages.

  • E2 — Core saturation at target QPS: 50 k qps × ~20 µs answer-compute = ~1.0 CPU-second/second → one core is the unit of QPS scaling (M3); add cores/edges linearly (principle 2).

  • E4 — ECS cache amplification: SCOPE /24 over a resolver serving a /16 → up to 2^(24−16) = 256 cache entries/name (§4.2); the scope-coarsening dial trades this for accuracy.
  • E5 — Failover RTO: detect (k_fail × interval = 3 × 5 = 15 s) + damp (0 on hard-down) + propagate (<5 s) + TTL (300 s) ≈ 300 s; drop TTL to 30 s → ≈ 48 s at ~10× query load (§4.1, M8).
  • E6 — Consensus detection: V=3, k_fail=2, interval=5 s → real outage DOWN in ~10 s; a single-vantage false DOWN is suppressed by the 2-of-3 quorum (§4.3, M11).
  • E7 — Propagation fan-out: E=50 edges, ~10 KB delta/generation → ~500 KB/generation, parallel fan-out bounded by the slowest edge RTT, not E (I-PROP).
  • E8 — Probe load: 1,000 endpoints × V=3 / 5 s interval = ~600 probes/s aggregate — bounded and respectful (I-PROBE-BUDGET, principle 13).
  • E9 — Latency-map size: ~1M client-networks × top-K (K=5) endpoints × ~8 B ≈ ~40 MB, hashed → sub-µs lookup (M5).
  • E10 — Staleness window: propagate target T=5 s + N generations → an edge > 2 generations or > 10 s behind is flagged stale and may be quarantined (I-PROP).

Alternative Architectures (Roads Not Taken)

Fundamentally different designs for the same goal — not parameter tweaks.

ALT1 — Pure anycast steering (no DNS GSLB).

client ─► nearest-by-BGP PoP (one anycast prefix) ─► PoP withdraws if unhealthy
          (routing fabric decides; no per-client policy, no DNS)

Wins for stateless, latency-critical, per-request steering with no per-client policy (DNS roots, simple CDN edges). Embodied by anycast-only CDNs. Rejected because it offers no geo/weighted/latency per-client control and reacts only at BGP-convergence granularity (no per-endpoint failover).

ALT2 — Pure HTTP-redirect steering (a global redirector tier).

client ─► redirector (302/307 + Location) ─► chosen endpoint
          per-request precise + rich policy, but +1 RTT and a redirector SPOF

Wins when per-request precision + rich policy beats latency (download-mirror selection, request routers). Embodied by classic CDN request routers. Rejected as the sole mechanism: it adds a full RTT + TCP/TLS setup and the redirector tier is itself a global single point of failure.

ALT3 — Strongly-consistent control plane (Raft-replicated global state).

every change ─► cross-region Raft consensus ─► all edges read a strongly-consistent value
          no split steering ever, but consensus latency on the change path

Wins when split steering is intolerable and you can pay cross-region consensus latency on every change. Embodied by etcd-backed config planes. Rejected (deferred) because global steering tolerates bounded staleness (I-PROP) and cross-region consensus would hurt reactivity; this blueprint ships leader + epoch fencing, full Raft deferred (see Deferred Features Register).

ALT4 — Monolithic authoritative GSLB daemon (gdnsd-style).

one process: health probes + geoip + weighted/failover + DNS answer  (no separate control plane)

Wins for a small self-hosted deployment where operational simplicity beats separation. Embodied by gdnsd. Rejected because it couples the decision engine to the DNS server, hides propagation consistency (no explicit generation/staleness model), and cannot reuse the policy engine for anycast/redirect (contra Design Principle 1).

Glossary

  • GSLB (Global Server Load Balancing) — steering each client to the best datacenter/PoP globally, by health/proximity/policy (the system being built).
  • Steering mechanism — the way a decision is delivered: DNS answer, anycast announce/withdraw, or HTTP 3xx redirect.
  • Control plane — gtrd: owns config, runs the decision engine, aggregates health, drives propagation.
  • Edge responder — gtr-edge: answers DNS/HTTP queries at a PoP from a propagated snapshot.
  • Prober / vantage point — gtr-probe: runs health checks from a network location; its verdict is one vote in consensus.
  • Endpoint — a steerable target (IP/CNAME + location + weight + health-check ref).
  • Pool — a set of endpoints under one policy + one health-check spec + a TTL.
  • PolicySet — a top-level, possibly nested, named routing policy (Route-53 "traffic-policy" analogue).
  • Routing policy — the rule selecting endpoints: failover, weighted, latency, geolocation, geoproximity, multi-value, or composite.
  • Failover policy — primary endpoint, then secondaries in order, by health.
  • Weighted policy — distribute clients among endpoints by weight (seeded-deterministic per client).
  • Latency policy — steer a client network to its lowest-latency healthy endpoint (via the latency map).
  • Geolocation policy — map a client's region (continent/country/subdivision) to a target; most-specific wins.
  • Geoproximity policy — pick the nearest endpoint by great-circle distance + a per-endpoint bias.
  • Multi-value answer (MV) — return up to N healthy endpoints; the resolver/client picks.
  • Composite / nested policy — a policy whose targets are themselves policies/pools (bounded depth).
  • HealthState — the consensus health of an endpoint: Healthy / Degraded / Unhealthy / Unknown.
  • Vantage consensus — fusing per-vantage verdicts into one HealthState via a quorum (so no single path flaps an endpoint).
  • Flap damping — a BGP-style penalty/decay that suppresses an oscillating endpoint (stability over reactivity).
  • Quorum — the ≥ ⌈(V+1)/2⌉ agreeing vantages required to set a HealthState.
  • EDNS Client Subnet (ECS) — an EDNS0 option carrying the client's subnet so geo/latency steering targets the client, not the resolver (RFC 7871).
  • SOURCE PREFIX-LENGTH — the ECS query field: how many client-address bits the resolver reveals.
  • SCOPE PREFIX-LENGTH — the ECS response field: the prefix granularity at which the answer is valid (the resolver cache key).
  • Latency map — a client_network → endpoint → latency_estimate table aggregated from RUM, powering latency routing.
  • RUM (Real User Measurement) — client-observed latency samples feeding the latency map.
  • Geoproximity bias — a per-endpoint distance offset that expands/shrinks its effective catchment region.
  • Prefix trie / LPM — the longest-prefix-match structure mapping a client subnet to a location (I-LPM).
  • TTL (Time To Live) — how long a resolver may cache an answer; the floor on DNS-steering reactivity (§2.7).
  • Negative caching — caching NXDOMAIN/NODATA per the SOA-minimum TTL (RFC 2308).
  • Anycast catchment — the set of clients a PoP serves under a shared anycast prefix (shifts on withdrawal).
  • Announce / withdraw — advertising or retracting an anycast prefix from a PoP to steer at routing speed.
  • BGP control sink — the abstraction receiving announce/withdraw intents (a real BGP-4 speaker is deferred, §22.2).
  • Generation — the monotonic version number stamped on a propagated ResolvedPlan (leader-advanced).
  • Staleness bound — the max generations / seconds an edge may lag the leader before it is flagged/quarantined (I-PROP).
  • RCU snapshot (Arc-swap) — the immutable, atomically-swapped edge state a query reads (lock-free, no torn read, I-SNAP).
  • Leader / epoch — the single control-plane writer per epoch; epoch fencing rejects a stale leader (I-LEADER, no split steering).
  • Failsafe — returning a last-known/all-configured answer (never empty) when health/data is missing (I-FAILSAFE).
  • DecisionTrace — the per-query record of why an endpoint was chosen (policy path, location, ECS scope, health, generation, TTL).
  • Split steering — the failure where some edges steer to a dead region while others steer away (the worst failure mode, principle 5).
