Back-of-Envelope Capacity Model

All numbers derived step-by-step from §4 System Constraints. Formula shown; no asserted-only values.

1. Memo size for a 12-table join query

From §4.4: reorderable join count ≤ 32; §4.3 MExpr count / query ≤ 131,072.

  • Groups: each of 12 tables = 1 Scan group; each 2-table join subset = C(12,2) = 66 groups; 3-table = C(12,3) = 220; exploraton adds ~3× alternatives per join = ~858 logical MExprs for join groups alone.
  • MExpr count estimate: N-table query → ~3^N groups explored (worst-case Cascades bushy) = 3^12 = 531,441 but B&B prunes ~80%; practical count ≈ 531,441 × 0.20 ≈ 106,000 MExprs — near the 131,072 cap, explaining why the default reorder_limit = 12 was chosen.
  • RAM per MExpr: MExpr struct = Operator(4B) + SmallVec<[GroupId;3]>(~28B) + Option<ScalarId>(4B) + RuleMask(16B) = ~52 B; round to 64 B with alignment.
  • Memo RAM for 12-table join: 106,000 × 64 B = 6.8 MB — well within the 64 MB memo_byte_budget.

2. Planning latency budget per task

From §4.1: 10-table join p95 target = 30 ms; §4.9 task_budget default = 100,000.

  • Available time per task: 30 ms / 100,000 tasks = 0.30 µs/task.
  • OptimizeGroup is the hottest task; it checks winners (O(1) HashMap lookup) + pushes child tasks. At 0.30 µs, one Group winner lookup + 3 child task pushes must complete in 300 ns — achievable on modern hardware (L1 cache hit ~1 ns, L2 ~5 ns, task Vec push ~10 ns).

3. Histogram storage for a 100-table catalog

From §4.3 plan cache and §5 references: equi-depth histogram default = 100 buckets/column; §4.4 column count/query ≤ ~1024, but a typical 100-table schema has ~10 columns/table.

  • Columns: 100 tables × 10 cols/table = 1,000 columns.
  • Bucket size: Bucket { upper_bound: Datum(~16B), num_eq: f64(8B), num_range: f64(8B), distinct_range: f64(8B) } = 40 B/bucket.
  • Per-column histogram: 100 buckets × 40 B = 4,000 B.
  • Total stats storage: 1,000 cols × 4,000 B = 4 MB — fits in L3 cache; explains why quasar-stats can load stats in < 20 ms (§4.5).

4. Plan cache memory footprint

From §4.3: plan cache default 256 MB; a typical FlowSpec for an 8-table TPC-H query has ~20 processors × ProcessorSpec(~200 B) + 30 streams × Stream(~40 B) = ~5,200 B ≈ 6 KB/plan.

  • Entries at 256 MB: 256 × 1024 × 1024 / 6,144 = 43,690 cached plans — a large prepared-statement workload (10,000 distinct queries × multiple schema versions) fits comfortably.

5. Rule-application throughput bound

From §4.2: simple 1–2 table queries at > 5,000 optimize()/sec/core. A simple query fires ~20 rules.

  • Rule applications/sec: 5,000 × 20 = 100,000 rule applications/sec.
  • Time per rule application: 1 / 100,000 = 10 µs/application — this is the latency budget for ApplyRule including pattern-match + Memo::intern + LogicalProps derivation. Profiling target.

6. Network cost dominance crossover

From §4.1: 10-table join p50 = 10 ms; §9 ADR-A08: total = cpu + io + w_net × net; typical w_net calibrated so 1 MB cross-region = 10 ms latency cost at 100 Mbps inter-region bandwidth.

  • Cross-region row transfer breakeven: if a HashJoin ships 10,000 rows × 100 B/row = 1 MB across regions = 10 ms net cost; a LookupJoin with 10,000 lookups × 0.5 ms/lookup = 5,000 ms CPU cost is worse. Breakeven at ~200 rows × 100 B = 20 KB → above 20 KB shipped, hash shuffle beats per-row lookup; below 20 KB, LookupJoin wins.
  • This explains why LOS prefers LookupJoin when the input cardinality is low (< ~200 filtered rows), which is exactly the OLTP primary-key lookup pattern.

7. ColSet bitset operations per FD closure step

From §11.1: ColSet = 2 × u64 (128-bit); FD closure iterates deps to fixed-point.

  • Bitwise OR of two ColSets: 2 × 64-bit OR = 2 instructions on any modern CPU; negligible.
  • Fixed-point convergence: typical schema has ≤ 10 FD rules; closure converges in ≤ 3 iterations = 3 × 10 × 2 instrs = 60 instructions per FD closure call — under 20 ns at 3 GHz.
  • This confirms §9 ADR-A05 (arena + u32 handles are cache-friendly; ColSet ops stay in registers).

8. Span enumeration ceiling for IN-list predicate

From §4.4: IN-list size before span collapse ≤ 10,000 values; §4.4 index key column count ≤ 16/index.

  • Spans from WHERE a IN (v1…v10000) on a 2-column composite index with range on col2: 10,000 point spans × open range on col2 = 10,000 spans × 2 endpoints = 20,000 key comparisons for span sort/dedup.
  • At 50 ns/comparison: 20,000 × 50 ns = 1 ms just for span normalization — this explains the collapse threshold and the §4.4 cap at 10,000 IN-list values.
