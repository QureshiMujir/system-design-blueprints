Mental Models & First Principles

Expert compressions that predict system behavior. Each: the insight, what it predicts, the bug class written without it, and the §/phase in Quasar where it is applied.

MM1 — A Memo Is a Finite Representation of an Infinite Plan Space The insight: a memo group represents every logically equivalent expression simultaneously; the memo encodes exponentially many alternative plans in polynomial space via structural sharing. What it predicts: join-order enumeration of N tables fits in O(N²) groups and O(N³) MExprs rather than requiring N! separate trees. Bug class without it: building one plan tree per candidate (no sharing) → OOM on 6-table queries, no B&B possible. Resolving §: §15 (Phase 3) memo Group/MExpr arena + interning design; §22 (Phase 10) Cascades task-stack search over memo.

MM2 — Cost Monotonicity Is the Soul of Branch-and-Bound The insight: if adding any operator to a partial plan never decreases total cost (I4), then a partial plan already exceeding the current best complete plan can be safely abandoned — its completion cannot improve. What it predicts: B&B prunes entire subtrees, not just leaves; pruning ratio grows with the number of tables. Bug class without it: a cost function that subtracts from children (e.g., modelling a "cached result discount") invalidates B&B → optimizer returns suboptimal plans while believing they are optimal. Resolving §: §7 I4 (cost monotonicity invariant); §22 (Phase 10 quasar-search B&B pruning logic).

MM3 — Cardinality Error Compounds Multiplicatively Across Joins The insight: if each join's cardinality is estimated with relative error ε, an n-join query accumulates error ~εⁿ; a 3× per-join error becomes 243× on a 5-join query (Leis et al. 2015 JOB result). What it predicts: plans break on multi-join queries long before they break on single-table queries. Bug class without it: calibrating the estimator only on single-table selectivity benchmarks → catastrophically wrong join-order choices in prod. Resolving §: §17 (Phase 5) multi-column stats, q-error acceptance criterion §4.7, Leis et al. 2015 citation.

MM4 — Physical Properties Are Required → Propagated Downward, Provided → Checked Upward The insight: a required ordering/distribution flows top-down from the root; each operator either provides it natively or an enforcer (Sort/Distribute) must be inserted to bridge the gap. Provided properties flow bottom-up from leaves. What it predicts: if a sort is needed, exactly one Sort enforcer appears at the correct place — never "maybe sort somewhere." Bug class without it: checking properties after plan selection rather than during → either wrong results (MergeJoin on unsorted input) or redundant sorts. Resolving §: §21 (Phase 9 PhysProps + enforcers); §22 (Phase 10 EnforceProps task); §7 I5, I12.

MM5 — Normalization, Exploration, and Implementation Must Be Strictly Separated The insight: normalization (always-on, confluent, cost-reducing) is safe to fire unconditionally; exploration (logical→logical, cost-driven) expands the space; implementation (logical→physical, cost-driven) concretizes it. Mixing them corrupts confluence guarantees. What it predicts: a normalize rule that is not confluent causes the plan to depend on insertion order → non-deterministic plans. Bug class without it: placing an exploration rule in the Normalize pass → normalize fires it without cost context → possible plan blowup or infinite loop. Resolving §: §6 Principle 3; §16 (Phase 4) optgen rule-kind tagging; §7 I3.

MM6 — Network Cost Dominates in Geo-Distributed Plans The insight: for a cross-region query, the network cost of transferring rows between regions (milliseconds per round-trip, bandwidth ceiling) dwarfs CPU sort cost or IO seek cost by 1–2 orders of magnitude. What it predicts: locality-optimized plans (LookupJoin over local index vs. HashJoin shuffling rows globally) win on latency even when cardinality naively favors hash. Bug class without it: treating net cost as zero → optimizer always chooses hash joins → every query fans out globally → 10–100× latency. Resolving §: §23 (Phase 11) net-cost model + LOS algorithm; §8 Distribution model; §9 ADR-A08 three-component Cost struct.

MM7 — Structural Deduplication Is the Memo's Correctness Invariant The insight: two expressions with identical (op, children, scalar) must map to exactly one ExprId (I1); otherwise the same expression is explored and costed twice, winner tables diverge, and plan extraction is ambiguous. What it predicts: the intern map is a precondition for correctness of the entire optimizer, not a performance optimization. Bug class without it: duplicate ExprIds for the same expression → B&B computes inconsistent lower bounds → prunes valid plans. Resolving §: §15 (Phase 3) Memo::intern() + MExprKey hash; §7 I1 detail.

MM8 — Generic Plans Are Safe; Custom Plans Are Optimal; Neither Is Both The insight: a generic plan (no specific placeholder values) must be correct for all type-compatible bindings, so it uses conservative cardinality; a custom plan (specific values) is optimal for that binding but wrong for others. The switch point is when value-specific selectivity would change the plan by more than 10× (ADR-A19). What it predicts: for queries with index scans on selective keys, custom plans are materially faster; for queries where selectivity is uniform regardless of value, generic plans are identical quality. Bug class without it: always using generic plans → misses index utilization on selective OLTP lookups by 10–100×. Resolving §: §25 (Phase 13) quasar-cache generic/custom plan logic; §9 ADR-A19; §7 I8.

MM9 — Determinism Is a Property of the Algorithm, Not the Data The insight: an optimizer that gives the same answer for the same inputs (sql, catalog, stats, seed) makes golden testing, replay, and cost-regression attribution possible; any source of non-determinism (HashMap iteration, thread-local RNG, pointer identity as tie-break) destroys that property. What it predicts: if any non-deterministic path exists in quasar-search or quasar-distsql, the replay harness will eventually catch a divergence. Bug class without it: std::collections::HashMap iteration in rule dispatch → plans differ across runs → CI golden files flake, cost regressions cannot be attributed to a specific commit. Resolving §: §6 Principle 4; §7 I10; §25 (Phase 13) replay harness; §9 ADR-A17.

MM10 — Cascade of Failures: Stale Stats → Wrong Cardinality → Wrong Join Order → Catastrophic Plan The insight: the entire cost-based path is only as good as its statistics input; stale stats do not fail loudly — they silently produce wrong cardinality estimates that cascade into wrong join orders that produce plans 100–1000× slower than optimal. What it predicts: plan quality regressions after large data loads are almost always a stats-freshness problem, not an optimizer bug. Bug class without it: logging only OptError failures while ignoring is_estimated=true → silent plan quality degradation after ANALYZE is skipped. Resolving §: §5 Leis et al. 2015; §17 (Phase 5) is_estimated flag propagation; §4.7 q-error targets; §7 Principle 7 Statistics Honesty.

Glossary · 49 terms · site-wide glossary

Bound IR
the typed relational+scalar tree (RelExpr/ScalarExpr) produced by quasar-bind from raw SQL AST; the input to the memo. Names resolved to ColumnId, types checked.
Branch-and-bound (B&B)
the search pruning technique: pass a cost upper bound down; abandon any expression whose lower_bound cost ≥ the current best. Guarantees optimality within budget (I7) and bounds tail latency.
Cardinality
estimated row count of a relational expression. Tracked as a bound (Cardinality{min,max}) in logical properties and as an estimate (Statistics.row_count) from stats.
Cascades
the Graefe optimizer framework Quasar implements: a memo of equivalent expressions explored top-down by cost-based transformation/implementation rules with branch-and-bound. Successor to Volcano.
Coster
the trait (quasar-cost) that assigns a Cost to a physical expression given stats + provided properties; also yields the B&B lower bound.
Cost
{cpu, io, net, total}; total is the sole comparison key. net dominates distributed plans.
Custom plan
a plan re-optimized with concrete placeholder values bound (vs a generic plan). Chosen when value-specific selectivity would change the plan materially (§25).
Distribution (property)
a physical property describing which region(s) a relation's rows reside in: Any | Single(region) | Set(regions). Required at the root (gateway), provided by scans via leaseholder locality.
Distribute (enforcer)
a physical operator inserted to change a relation's distribution (repartition/shuffle) when provided ≠ required. Cost ∝ bytes × region distance.
DistSQL
the distributed physical execution layer; Quasar's output is a FlowSpec for it (processors + streams + routers placed on nodes).
Enforcer
a physical operator (Sort, Distribute) inserted by the search to satisfy a required physical property the input does not already provide.
Equi-depth histogram
per-column stat where each bucket holds ~equal row count; used for range/equality selectivity. Bucket = {upper_bound, num_eq, num_range, distinct_range}.
Exploration rule
a cost-based logical→logical transformation (join commutativity/associativity, GenerateIndexScan) fired during search; expands the memo with equivalent alternatives. Tagged [Explore].
Functional dependency (FD)
a relationship X → Y meaning X-values determine Y-values. Tracked in FuncDepSet (keys, equivalencies, constants, strict deps); drives ordering simplification and key derivation.
FD closure
the full set of columns determined by a column set under a FuncDepSet; used to simplify orderings (I6) and validate keys (I11).
FlowSpec
Quasar's stable wire output: the distributed physical flow (processors, streams, gateway) handed to the execution engine (project 318).
Generic plan
a plan built treating placeholders as unknown-but-typed (default cardinality assumptions), reusable across bindings (§25).
Group
a memo node representing a set of logically equivalent expressions; owns one LogicalProps shared by all members (I2), plus per-required-props winners.
GroupId / ExprId
u32 arena indices into a Memo; valid only within that memo; never serialized raw or compared across memos.
HyperLogLog (HLL)
probabilistic sketch used offline to estimate NDV (distinct count) per column with bounded memory; result stored in ColumnStatistic.distinct_count.
Implementation rule
a logical→physical transformation (InnerJoin→HashJoin/MergeJoin/LookupJoin, GroupBy→HashAgg/StreamAgg) fired during search. Tagged [Implement].
Index constraint
a Constraint (spans over an index key prefix) derived from a filter by the constraint solver, plus a remaining (residual) filter.
Interesting ordering
an ordering that a downstream operator (merge join, stream aggregation, ORDER BY) could exploit; collected and requested from children to avoid sorts.
Leaseholder
the replica of a range that serves reads/writes; its node's locality determines a scan's provided distribution. From quasar-cat placement metadata.
Locality-optimized search (LOS)
for a LIMIT over a globally-distributed table, scan the local region first and fan out only if under-filled; avoids cross-region traffic (§23).
Logical properties
derived facts true of every member of a group: out_cols, not_null, keys, FDs, cardinality bounds, outer_cols, stats. Computed once (I2).
Lookup join
an index nested-loop join: for each input row, look up matching rows via an index. Distributed-favorable (one round trip per row vs shipping a whole table).
Memo
the central data structure: interned arenas of groups and expressions encoding the entire equivalent-plan space compactly with structural sharing.
Memo staleness
a cached memo/plan whose schema or stats version no longer matches the catalog; detected by fingerprint mismatch (MemoStale), triggering invalidation (§25, Compatibility & Versioning).
MExpr
a memo expression (member): an operator + child GroupIds + optional scalar payload + rules_applied mask.
NDV (number of distinct values)
distinct count of a column; the denominator for equality selectivity (≈ 1/NDV) and group-by output cardinality.
Normalization rule
an always-on, confluent, cost-reducing canonicalization fired in the construct factory during memo building (predicate pushdown, constant folding, projection pruning). Tagged [Normalize].
optgen
Quasar's rule DSL compiler (quasar-optgen): parses .opt files and generates Rust match/replace dispatch code at build time. Deterministic codegen.
Optimization goal
a (group, required PhysProps) pair; the unit the search optimizes and memoizes a Winner for.
Ordering choice
OrderingChoice: an FD-simplified required/provided ordering (constant and equivalent columns dropped) so it hashes canonically as a winners key.
Outer columns
columns referenced by a subquery but bound in an enclosing scope; the correlation marker tracked in logical properties.
Physical properties
PhysProps: ordering + distribution + limit hint. Required props pushed top-down; provided props derived bottom-up; gaps filled by enforcers.
Placeholder
a query parameter ($1) bound at execution; typed at bind time, valued at plan/execute time. Drives generic-vs-custom plan choice.
Processor
a DistSQL flow node executing one physical operation on one node (TableReader, HashJoiner, Aggregator, Sorter, …).
Provided vs required properties
provided = what an expression actually delivers; required = what its consumer demands. Search reconciles them, inserting enforcers when provided ⊉ required.
q-error
the multiplicative error of a cardinality estimate (max(est/actual, actual/est)); the standard estimator-quality metric. Target: within an order of magnitude (§4).
Range
a contiguous key span of a table, the unit of distribution/replication; each range has a leaseholder. Scans map to ranges → processors.
Router
directs a processor's output streams: PassThrough, ByHash(cols) (repartition), Mirror (broadcast), ByRange(spans).
Selectivity
the fraction of rows a predicate passes ([0,1]); the multiplier applied to input cardinality to estimate output rows.
Span
a half-open/closed key interval over an index key prefix ({start, start_boundary, end, end_boundary}); the constraint solver's output unit.
Tight constraint
a Constraint that fully captures its source predicate (remaining filter empty); a loose constraint leaves a residual filter to evaluate.
Volcano
Graefe's earlier optimizer-generator framework (bottom-up); the predecessor to Cascades. Quasar uses Cascades (top-down) but shares the rule/property vocabulary.
Winner
the lowest-cost expression for a (group, required props) goal, with its cost and provided props; the unit of the extracted plan tree.
Zone config
per-table/index region affinity + replication settings in quasar-cat; the input that makes plans locality-aware (§23).
