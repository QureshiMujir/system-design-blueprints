Decisions (§9) · 28 ADRs

A01

Implementation language

Chosen

Rust (stable, 2021 edition)

Rejected

Go — GC pauses hurt optimize() tail latency; weaker sum types make rule match non-exhaustive. C++ — memory-unsafe for a shared DAG with many u32 handles. OCaml/Haskell — excellent ADTs; weaker ops/ecosystem for this portfolio.

When the rejected choice is right

Go wins when the optimizer must be embedded into a Go-dominant monorepo (as CockroachDB itself demonstrates); the GC pauses are tolerable when latency SLOs are >10 ms and the organizational cost of a Rust FFI boundary exceeds the performance gain.

Why: Algebraic enums + borrow checker enforce memo append-mostly + owner model at compile time; no GC pauses → predictable latency.

A02

Rust edition + toolchain pin

Chosen

Edition 2021; rust-toolchain.toml with exact nightly-free stable channel pin

Rejected

Nightly — would enable allocator_api, not needed; unstable APIs break reproducibility. Stable without pin — dependency upgrades change MSRV silently.

When the rejected choice is right

Nightly wins when allocator_api or specialization are required for the arena allocator hot path and the team accepts regular nightly-breakage triage overhead.

Why: Reproducible CI; edition 2021 gives let … else, pattern closures, and improved borrow scopes needed for arena traversal.

A03

Build system

Chosen

cargo workspace with 16 member crates under crates/

Rejected

Bazel — full Bazel porting overhead unjustified for a single-org project. CMake — not Rust-native. Meson — N/A.

When the rejected choice is right

Bazel wins in a monorepo with multiple languages (Rust + C++ + Python analytics) where cross-language dependency caching and hermetic remote execution justify the setup cost; Google's F1 query layer exemplifies this.

Why: Cargo workspace provides incremental builds, per-crate unit tests, and the build.rs hook needed for optgen codegen without extra tooling.

A04

Rule engine

Chosen

optgen .opt DSL compiled at build time via build.rs in quasar-optgen → generated Rust match/replace code in quasar-rules

Rejected

Runtime interpreter — no compile-time exhaustiveness; slower; harder to test. Declarative macro (macro_rules!) — unreadable for 200+ rules; poor IDE support. Proc-macro — possible but heavier compile overhead vs build.rs.

When the rejected choice is right

A runtime interpreter wins in systems that require hot-reload of rules without recompilation — e.g., a SaaS optimizer where rule updates must propagate to a running fleet in seconds, or a research optimizer where rules change every iteration of an experiment.

Why: CockroachDB's optgen approach: rules are a separate, readable DSL; generated Rust is fast (no interpreter overhead); build.rs invalidation tracks .opt file changes automatically.

A05

Memo representation

Chosen

Typed arena (Arena<Group>, Arena<MExpr>) + u32 newtype handles (GroupId, ExprId) + HashMap<MExprKey, ExprId> intern table

Rejected

Rc<RefCell<…>> graph — non-deterministic drop order; GC-like cycle risk; no safe cross-thread serialization. petgraph — generic; no structural dedup built in; GroupId/ExprId would need to be petgraph NodeIndex which is usize, losing newtype safety. Index-into-Vec — same as arena but without the Arena abstraction for bounds-checking.

When the rejected choice is right

Rc<RefCell> wins in a prototype or interactive REPL where GC semantics simplify rule authoring and memo sharing; for a research optimizer running fewer than 100-group queries where latency is not a constraint, the cognitive simplicity outweighs allocation overhead.

Why: Pointer-free handles: safe to clone, hash, serialize for replay; arena allocation is cache-friendly; structural sharing via intern table is a O(1) lookup.

A06

Search strategy

Chosen

Cascades top-down branch-and-bound (Graefe 1995 / Orca lineage)

Rejected

Volcano bottom-up — does not naturally support goal-directed search (optimizing for specific physical properties); cost pruning harder. System-R DP join enumeration — fixed join-order DP, not rule-based; cannot express arbitrary transformations via .opt rules. Separate DPccp for join ordering — DPccp is optimal for join ordering but requires a separate phase and integration with the rule framework; transformation-rule enumeration (JoinCommutativity + JoinAssociate + JoinReassociate) integrates naturally into the existing Cascades ApplyRule task and interleaves with other rules.

When the rejected choice is right

System-R bottom-up DP wins when the query workload is strictly join-order-dominated (star schemas, ≤12 tables, all joins inner equi-joins) and the optimizer must be embedded in a resource-constrained environment where Cascades' task-stack overhead and memo memory are prohibitive — PostgreSQL's planner successfully uses this approach for the vast majority of OLTP workloads.

Why: Cascades unifies exploration and implementation in one task-driven engine; B&B pruning avoids full enumeration in the common case; goal-directed search naturally handles physical properties and multi-region distribution requirements.

A07

Join-order enumeration

Chosen

Transformation rules (JoinCommutativity, JoinAssociate, JoinReassociate) within Cascades search

Rejected

Standalone DPccp phase (Moerkotte & Neumann 2006) — adds complexity; doesn't compose with other rule types; would require extracting the join graph before Cascades and re-merging results. Greedy heuristic — non-optimal; not suitable for a cost-based optimizer at this quality bar.

When the rejected choice is right

DPccp wins when the optimizer handles complex join graphs with cross-products and non-inner joins (outer/semi/anti) that transformation rules struggle to enumerate efficiently; HyPer/DuckDB use DPhyp precisely for these cases, achieving exhaustive optimal join ordering for queries that rule-based enumeration under-explores.

Why: Transformation rules enumerate the same plans as DPccp for inner joins when fully applied; they compose with predicate pushdown, index scan generation, and distribution rules in a single search pass.

A08

Cost representation

Chosen

struct Cost { cpu: f64, io: f64, net: f64, total: f64 }

Rejected

Single f64 scalar — loses breakdown needed for distribution-aware tuning (net cost dominates in multi-region; io cost dominates in local scan-heavy plans). Integer cost units (CBO classic) — requires calibration to a fixed unit; f64 allows direct multiplication by row counts and selectivity without overflow.

When the rejected choice is right

A single f64 wins in a single-node optimizer where all queries run locally and network cost is identically zero; the extra fields add struct size and Coster complexity for no discriminating benefit — DuckDB's cost model is effectively single-dimensional for exactly this reason.

Why: Three-component cost makes the Coster implementation readable and testable per component; total is the B&B comparison key and can be tuned (e.g., total = cpu + io + w_net * net) without changing the struct.

A09

NDV estimation

Chosen

HyperLogLog sketch (HLL++) offline → ColumnStatistic.distinct_count: f64

Rejected

Exact COUNT(DISTINCT col) at plan time — too expensive; requires full table scan. KMV sketch — lower accuracy per byte than HLL++. Sampling-based NDV — biased for skewed distributions.

When the rejected choice is right

Sampling-based NDV wins for append-only analytical tables where exact HLL sketches are impractical to maintain and a 5–10% NDV error is acceptable — Amazon Redshift and Snowflake use adaptive sampling in their auto-ANALYZE pipelines for this reason.

Why: HLL++ achieves 0.5–2% relative error at 16KB per column; offline collection (ANALYZE equivalent) matches CockroachDB's stats model; f64 for distinct_count allows fractional estimates for partial stats.

A10

Histograms

Chosen

Equi-depth (equal-frequency) histograms, Bucket { upper_bound, num_eq, num_range, distinct_range }

Rejected

Equi-width — poor resolution for skewed data (frequent values get the same bucket width as sparse regions). Max-diff (Ioannidis-Kang) — optimal for skewed data but complex maintenance; overkill for the 100-bucket default. V-optimal — requires sorting and dynamic programming to build; more expensive than equi-depth.

When the rejected choice is right

Max-diff histograms win when the column value distribution is highly skewed with a few extremely frequent values driving most query plans — e.g., a status column where 99% of rows are 'active'; equi-depth merges rare values into wide buckets with poor selectivity, while max-diff places bucket boundaries at exactly the discontinuities that matter.

Why: Equi-depth provides accurate range selectivity for skewed data; the num_eq / num_range / distinct_range per-bucket model (CockroachDB's Histogram format) supports equality and range predicates.

A11

Multi-column statistics

Chosen

Multi-column ColumnStatistic keyed by ColSet (up to 4-column combos)

Rejected

Full joint distribution — exponential storage. Independence assumption always — inaccurate for correlated columns (e.g., city→zip_code). Foreign-key correlation inference only — too narrow.

When the rejected choice is right

Full joint distribution wins for a small-schema OLAP system (≤10 columns, ≤5 query templates) where the exponential storage is affordable and the correlation between all column pairs is the dominant source of plan instability — as demonstrated by academic systems like IQ (Ilyas et al.) that use full-join-distribution sketches.

Why: Multi-column stats for common join/group-by column sets captures the most important correlations; collected on-demand (ANALYZE with column list); stored in Statistics.col_stats: HashMap<ColSet, ColumnStatistic>.

A12

Selectivity model

Chosen

Per-predicate: equality uses 1/NDV; range uses histogram bucket interpolation; AND chains multiply selectivities (independence); OR uses inclusion-exclusion (2-term); IN uses len(in_list) / NDV

Rejected

MCV (most common values) table — maintained separately; adds storage; integrated in histograms via num_eq. Sampling at plan time — too expensive. Learned selectivity (ML model) — deferred; not stable for a foundational optimizer.

When the rejected choice is right

A learned ML selectivity model wins in systems with stable, high-query-volume workloads where historical feedback can train a neural or gradient-boosted estimator — Bao (Marcus et al. 2021) and Neo show that learned estimators reduce median q-error by 2–5× over histogram-based approaches on JOB-style benchmarks with complex multi-predicate correlation.

Why: CockroachDB's model: histogram-backed range selectivity + NDV-based equality + independence assumption for conjuncts is accurate enough for TPC-H/TPC-DS workloads; simpler to reason about and test.

A13

Constraint solver design

Chosen

Dedicated quasar-constraint crate: predicate analysis → Constraint { cols, spans, tight } + remaining filter

Rejected

Inline in the index scan rule — hard to unit-test independently; couples rule logic with span math. External SMT solver — extreme overkill; adds a heavy dependency. Ad-hoc per-operator — no reuse between IndexScan and LookupJoin key constraint derivation.

When the rejected choice is right

An external SMT solver (e.g., Z3) wins when the predicate language includes disjunctive normal form constraints over computed columns, partial-index predicates with arbitrary arithmetic, or user-defined type constraints — scenarios where exact span derivation is undecidable or too complex to enumerate manually.

Why: Separating constraint solving allows independent unit tests for span arithmetic (intersection, union, inversion); reused by IndexScan rule, LookupJoin key extraction, and ZigzagJoin.

A14

Physical-property framework

Chosen

PhysProps { ordering: OrderingChoice, distribution: Distribution, limit_hint: f64 } with FD-simplification of OrderingChoice

Rejected

Property templates (Volcano style) — less composable; harder to extend for Distribution property. Separate required/provided type variants — adds boilerplate; same information.

When the rejected choice is right

Volcano-style property templates win when the property space is extremely large and heterogeneous — e.g., a multi-model database with document, graph, and relational operators each having incompatible property types that cannot be unified into a single struct without excessive padding.

Why: PhysProps as a value type: hashable, comparable, cloneable; serves as the key in Group.winners: HashMap<PhysProps, Winner>; FD-simplification reduces the number of distinct required-props keys, limiting winner table size.

A15

Distribution property modeling

Chosen

`Distribution::Any

Rejected

Single(RegionId)

When the rejected choice is right

Bit-vector over all nodes — too large; most plans involve ≤ 4 regions. Always-distributed model (ignore locality) — misses the LOS optimization that is Quasar's core value proposition in multi-region settings.

Why: Set(SmallVec<[RegionId;4]>)`

A16

DistSQL flow serialization

Chosen

Rust-native FlowSpec struct (in-process; no protobuf for the optimizer's internal boundary)

Rejected

Protocol Buffers — necessary for wire-protocol to an execution engine; but the boundary between Quasar and exec (project 318) is in-process in this portfolio. JSON/serde — too verbose for large flows; acceptable only for EXPLAIN output.

When the rejected choice is right

Protobuf wins the moment the optimizer and executor run in separate processes or across a network (e.g., a centralized query planning service serving multiple executor clusters) — Impala's statestore-and-planner architecture uses exactly this split, with Thrift/Protobuf as the plan-distribution wire format.

Why: FlowSpec is passed by value to the downstream exec crate; serde + JSON is used only for EXPLAIN (DISTSQL) rendering and for replay event logs. If a network boundary is later needed, protobuf derives from the same struct.

A17

Determinism strategy

Chosen

Sorted iteration over arenas; ExprId-stable winner tie-breaking; no HashMap iteration in plan-affecting hot paths; seeded RNG in Optimizer struct

Rejected

Non-deterministic iteration with sorted output at the end — sorting is a partial fix; any mid-pipeline branch on HashMap order is still non-deterministic. Thread-local RNG — would vary per thread; optimizer is single-threaded per query.

When the rejected choice is right

Non-deterministic-but-sorted wins in an optimizer where plan quality is evaluated statistically (A/B test over thousands of queries) rather than by exact regression; the BTreeMap overhead is measurable at 50k-group memos and the golden-test framework uses cost-range comparisons rather than byte-identical plan text.

Why: Determinism is required for golden tests, replay, and cost-regression attribution (I10). A seeded u64 field in Optimizer allows reproducible bench/fuzz runs.

A18

Concurrency model

Chosen

Single-threaded Optimizer per query (no Sync on Memo); quasar-cat is Arc<Catalog> (read-only, Send+Sync); quasar-cache uses RwLock<PlanCache>

Rejected

Parallel Cascades (multi-threaded task stack) — complex; requires Arc<Mutex<Group>>; GC-like overhead; not needed for single-query optimization budgets ≤ 100ms. Actor model per group — over-engineered; data dependencies between groups require coordination.

When the rejected choice is right

Parallel Cascades wins for extremely complex analytical queries (200+ table joins, multi-hour planning acceptable, plan quality >> planning latency) — Orca/GPORCA explored this with a parallel task scheduler for Greenplum queries that could not complete under a single-threaded budget.

Why: Single-threaded optimizer with per-query arena is the CockroachDB model; parallelism is achieved at the query-concurrency level (many queries, each single-threaded optimizer).

A19

Plan cache + placeholders

Chosen

quasar-cache: generic plan (no specific placeholder values) vs custom plan (specific values); cache key = (sql_fingerprint, schema_version, stats_version); invalidation on schema/stats staleness

Rejected

Only generic plans — may be sub-optimal for highly selective literals. Only custom plans — cache misses on every new literal set; defeats prepared-statement performance. LRU by SQL text — ignores schema/stats staleness; returns stale plans.

When the rejected choice is right

Custom-plan-only wins when prepared statements carry highly selective or correlated placeholder values (e.g., per-customer partition keys in a multi-tenant SaaS) and re-optimization cost is low relative to execution cost — PostgreSQL's plan_cache_mode = force_custom_plan is designed for exactly this scenario.

Why: Generic plan cached; custom plan triggered when placeholder-specific selectivity differs by >10× from generic estimate. Invalidation via schema_version + stats_version epoch counters (CockroachDB's approach).

A20

Error handling

Chosen

enum OptError { … } (typed variants) + thiserror derive

Rejected

anyhow — erases error type; makes matching for recovery impossible in quasar-search. Box<dyn Error> — same erasure problem. Panic — unacceptable in a library crate.

When the rejected choice is right

anyhow wins in a binary or CLI application (not a library) where all errors are ultimately printed to the user and the recovery action is always "exit 1" — the call site simplicity of ? chaining without match-arm boilerplate outweighs the type-erasure cost in that context.

Why: Typed errors allow callers (EXPLAIN, cache, CLI) to handle NoPlanFound vs BudgetExceeded vs CatalogMissing differently; thiserror provides Display + Error derives without boilerplate.

A21

Logging / tracing

Chosen

tracing crate + tracing-subscriber (structured spans per optimize() call)

Rejected

log crate — no structured fields; harder to correlate with a specific query. slog — less ecosystem traction than tracing; awkward async integration. Custom logger — reinventing the wheel.

When the rejected choice is right

log wins in a no-std embedded environment or a resource-constrained system where tracing's span allocation and subscriber registry add unacceptable overhead — e.g., an optimizer running inside a WebAssembly module in a browser query engine.

Why: tracing spans map naturally to optimizer phases (bind, memo-build, search, flow-plan); span fields carry GroupId/ExprId for correlation; quasar-obs replay harness captures events via a custom tracing::Subscriber.

A22

Metrics

Chosen

metrics crate facade (counters/histograms/gauges) + metrics-exporter-prometheus in CLI

Rejected

OpenTelemetry SDK — correct long-term, but heavy; facade allows swapping exporters later. StatsD — UDP unreliable; no histogram support. Custom atomic counters — no labeling; hard to consume.

When the rejected choice is right

OpenTelemetry wins when the optimizer is one component of a broader observability platform that already standardizes on OTLP for traces, metrics, and logs — the unified context propagation across optimizer + executor + storage components eliminates the need for correlation by query ID.

Why: metrics facade is zero-cost when no exporter is registered (optimizer library); CLI wires a Prometheus exporter for quasar bench.

A23

Testing: golden/conformance

Chosen

quasar opt-test datadriven runner (CockroachDB opt-tester style): SQL + directive + expected text diff

Rejected

Unit tests only — miss end-to-end plan quality regressions. Snapshot testing (insta) — good but no directive-based multi-output (norm vs opt vs distsql from one file).

When the rejected choice is right

insta snapshot testing wins for a smaller optimizer (< 20 rules, < 5 plan types) where the full directive language is over-engineered and the primary regression signal is "did the plan tree change?" — the lower setup overhead makes it preferable in early-prototype phases.

Why: Datadriven golden files are human-readable, diff-friendly, and can encode multiple query variants in one file; the directive model (norm/explore/opt/memo/stats/index-constraints/dist) matches CockroachDB's battle-tested test infrastructure.

A24

Fuzzing

Chosen

cargo-fuzz (libFuzzer) + structure-aware Arbitrary impls on RelExpr, ScalarExpr, Memo, Cost, optimizer seeds

Rejected

AFL only — libFuzzer provides better coverage tracking in CI. Random string fuzzing of SQL text — misses deep internal state; most inputs fail parse early.

When the rejected choice is right

AFL with grammar-based mutation wins when the primary attack surface is the SQL parser itself (security audit of a user-facing endpoint) rather than internal optimizer invariants — AFL's fork-server model produces higher SQL-grammar coverage per second for syntactic vulnerability research.

Why: Structure-aware fuzzing directly generates valid memo states and cost inputs, bypassing the SQL parser; finds optimizer invariant violations (I1–I12) not reachable from random SQL strings.

A25

Property testing

Chosen

proptest for statistical/algebraic properties (FD closure, cost monotonicity, constraint soundness, placeholder validity)

Rejected

QuickCheck — less expressive shrinking; proptest's strategy combinators map better to complex domain types.

When the rejected choice is right

QuickCheck wins in a Haskell or Erlang codebase where the type system's Arbitrary instances are already idiomatic and the team's toolchain familiarity reduces the effective discovery time compared to porting strategies to proptest.

Why: proptest shrinking finds minimal counterexamples for violated invariants; combined with cargo-fuzz covers both property violations and memory-safety bugs.

A26

CI

Chosen

GitHub Actions: ci.yml runs cargo test --workspace, cargo clippy -- -D warnings, cargo fmt --check, cargo doc, quasar opt-test conformance/testdata/, TPC-H lite cost ceilings, cargo fuzz run (short budget)

Rejected

Jenkins — not hosted; overkill for a single-repo project. CircleCI — additional cost.

When the rejected choice is right

Jenkins wins in an air-gapped enterprise environment where GitHub Actions is unavailable and the team already operates a Jenkins cluster with custom hardware runners (e.g., bare-metal servers with large memory for fuzzing or cross-compilation for proprietary architectures).

Why: GitHub Actions integrates with the repository; matrix over stable Rust pin; artifact upload for plan goldens and bench results.

A27

License

Chosen

Apache-2.0

Rejected

MIT — less explicit patent grant (relevant for an optimizer with algorithmic novelty). GPL — incompatible with potential embedding in a commercial distribution.

When the rejected choice is right

GPL wins if the project's strategic goal is copyleft — ensuring all derivative optimizers remain open source — rather than maximum embeddability; the FSF's position is that GPL maximizes long-term community benefit by preventing proprietary forks from withholding improvements.

Why: Apache-2.0 matches CockroachDB's optimizer (Pebble/CockroachDB Apache license); explicit patent clause protects users of the optimizer library.

A28

Dependency policy

Chosen

Locked Cargo.lock committed; cargo deny checks for license conflicts and known vulnerabilities; no unsafe in optimizer logic (only in arena allocator, audited separately)

Rejected

Unpinned deps — silent breaking changes in transitive deps. Vendoring all deps — high maintenance burden.

When the rejected choice is right

Vendoring all deps wins in a regulated or air-gapped environment (financial, defense, medical device) where the supply-chain audit requires every byte of every dependency to be checked in, reviewed, and approved before build — the maintenance burden is explicitly accepted as the compliance cost.

Why: Cargo.lock + cargo deny gives reproducible builds and security hygiene; arena's unsafe block is isolated and reviewed per-commit.

Alternative Architectures (Roads Not Taken)

Alternative 1 — Heuristic / Rule-Only Planner (no cost model)

SQL → parse → bind → fixed rule-pass pipeline
 Rule 1: predicate pushdown (always)
 Rule 2: index selection (first applicable)
 Rule 3: join ordering (left-deep, left-to-right)
 Rule 4: aggregation pushdown (if GROUP BY key is indexed)
 → single physical plan (no alternatives explored)

Regime where it wins: embedded systems with ≤ 4 tables, simple OLTP SELECT/INSERT, predictable schema, latency budget < 0.1 ms (RBO fires in microseconds; CBO adds 1–10 ms). Real system: early MySQL query optimizer (pre-5.6); SQLite; many microcontroller-embedded SQL engines. Why this blueprint rejected it: Quasar targets distributed, multi-table analytical queries where join order dominates performance by orders of magnitude — a heuristic planner would pick the wrong join order on >50% of TPC-H queries. The entire value proposition (CockroachDB lineage) is cost-based optimization for geo-distributed workloads.

Alternative 2 — Bottom-Up Dynamic Programming (System R / Selinger style)

            Enumerate all (left, right) join subsets
            bottom-up: smallest subsets first
           ┌──────────────┐
table t1 ──►  DP[{t1}]    │
table t2 ──►  DP[{t2}]    │  join DP[{t1}]+DP[{t2}] → DP[{t1,t2}]
table t3 ──►  DP[{t3}]    │  join DP[{t1,t2}]+DP[{t3}] → DP[{t1,t2,t3}]
           └──────────────┘
            Optimal substructure: DP[S] = min over all splits of S

Regime where it wins: OLTP workloads with ≤ 12 inner equi-joins, no complex physical properties beyond ordering, single-node execution (no distribution property to track). Real system: PostgreSQL planner (Selinger DP + geqo); IBM DB2's join enumerator. Why this blueprint rejected it: bottom-up DP is goal-blind (it computes optimal plans for all subsets, even those the root query never requests); it does not naturally support goal-directed optimization for specific physical properties (Distribution); and it cannot interleave join reordering with predicate pushdown and index-scan generation in a single pass. ADR-A06 captures this.

Alternative 3 — Query Compilation (no Volcano/Cascades interpreter)

SQL → parse → bind → compile to native code
 ┌────────────────────────────────────┐
 │ LLVM IR generation per query       │
 │ • inner loops compiled, not inter- │
 │   preted                           │
 │ • no Volcano iterator overhead     │
 │ • vectorized tight loops           │
 └────────────────────────────────────┘
 → compiled binary (run once per query)

Regime where it wins: ultra-high-throughput OLAP on a fixed schema with repeated query templates where JIT compilation amortizes over millions of executions per query shape; latency budget allows 50–200 ms compile overhead. Real system: HyPer (Neumann 2011 VLDB, "Efficiently Compiling Efficient Query Plans"); Umbra; NoisePage. Why this blueprint rejected it: Quasar is an optimizer, not an execution engine (P12 — no execution coupling); the FlowSpec is handed to project 318 for execution. Query compilation is an execution-engine technique. Additionally, compilation latency (50–200 ms per query) violates the §4.1 optimize() latency targets (p99 < 10 ms for OLTP queries).

Alternative 4 — Learned / ML-Based Cost Model (no hand-calibrated coefficients)

Query features → neural network → predicted cost
 ┌────────────────────────────────────────┐
 │ Features: operator type, cardinality,  │
 │   index selectivity, join depth,       │
 │   data distribution embeddings         │
 │                                        │
 │ Model: gradient-boosted trees or       │
 │   small MLP trained on EXPLAIN ANALYZE │
 │   feedback                             │
 └────────────────────────────────────────┘

Regime where it wins: high-volume SaaS workloads with stable query templates where EXPLAIN ANALYZE feedback accumulates quickly, correlation between features and actual cost is learnable, and the 2–5× q-error reduction (Marcus et al. 2021, Bao system) is worth the ML infrastructure dependency. Real system: Bao (Marcus et al. 2021 SIGMOD); Microsoft's Bao-influenced hints in Azure SQL; Neo (Marcus et al. 2019). Why this blueprint rejected it: ML models require inference runtimes (ONNX, PyTorch), training pipelines, and labeled data — all out of scope for a foundation optimizer library. The calibrated-coefficient model (ADR-A12, costs.toml) is interpretable, tunable by operators, and requires no feedback loop. A learned model defers gracefully to Phase 13+ as an extension via the Coster trait.
