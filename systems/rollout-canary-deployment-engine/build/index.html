⬜ Phase 3 — canary-reconcile §15

Objectives
  • Production-quality level-triggered reconcile loop: reconcile(ctx) → ActionSet; apply_actions(ctx, actions).
  • Rate-limited workqueue with per-item exponential backoff.
  • progressDeadlineSeconds timer: detect no-progress → set Degraded condition.
  • Idempotency verification: apply same ActionSet twice → no duplicate side-effects.
  • Requeue semantics: transient provider error → backoff requeue; permanent error → condition + stop.
  • Integration test: 10 rollouts enqueued concurrently → all reconcile without data races.
Deliverable
  • canary-reconcile with full diff + apply + workqueue; all tests pass.
  • Idempotency test: identical ActionSet applied twice → same final state; no duplicate provider calls.
  • 10-concurrent-rollout integration test passes without data races.
Acceptance
Criterion Measure
Reconcile correctness Diff produces minimal action set (no redundant actions)
Idempotency Double-apply → same state; provider call log deduplicated
Backoff After 3 transient errors: delay ≥ 4 s (base 1 s, factor 2)
Deadline detection No progress for deadline_secs → Degraded condition set
Concurrent safety 10 rollouts × 100 reconciles → zero data races (TSAN or loom)
Requeue Transient error → item re-enqueued with backoff; not dropped
Fixtures
  • conformance/reconcile_noop.yaml: spec == status → empty ActionSet → no provider calls.
  • conformance/reconcile_setweight.yaml: desired_weight=50, observed_weight=20 → ActionSet([SetWeight{50,50}]).
  • conformance/reconcile_deadline.yaml: last_progress_time = now - deadline - 1s → ActionSet([SetCondition{Degraded}]).
Pitfalls
  • Read-modify-write race: reconcile reads status, computes actions, writes status; concurrent reconcile (non-leader) between read and write → StaleGeneration; handle with retry, not panic.
  • Action ordering matters: ScaleWorkload before SetWeight (ensure pods exist before routing traffic); encode ordering in ActionSet::apply_order().
  • Backoff state lost on restart: per-item backoff in-memory → on restart, first attempt has no backoff; acceptable (level-triggered reconcile idempotent).
  • progressDeadline false positive: any status write counts as progress? Define "progress" narrowly: step index advance or replica count change.
  • Tokio task per rollout: 1000 rollouts → 1000 tasks; use bounded semaphore tokio::sync::Semaphore(max_concurrent=200).

Fixtures
  • conformance/rolling_update.yaml: 5 rows {desired, maxSurge, maxUnavailable, tick_by_tick_expected_counts}.

Pitfalls
  • Simultaneous scale-up and scale-down in one reconcile: must compute both atomically (total pods never exceeds max_pods); sequential scale-up then scale-down in one ActionSet tick is correct.
  • Readiness not monotonic: pod can become unready after being ready; re-check readiness each reconcile, do not cache.
  • Promote before old RS scaled down: must emit Promote first (update stable_rs pointer), then scale old RS down in subsequent reconcile — avoid zero-RS window.
  • minReadySeconds interacts with maxUnavailable: a pod that just became ready does not count toward "available" until minReadySecs elapsed — failure to enforce → premature scale-down.

Pitfalls
  • Deterministic replay requires deterministic clock: tools/replay must inject a MockClock that advances per event timestamp; real Instant::now() breaks replay.
  • Conformance harness ordering: YAML vector order matters for stateful tests; run each vector in a fresh store instance.
  • Differential semantic gaps: Argo may promote on inconclusiveLimit hit (configurable); document our behavior divergence explicitly in conformance/README.md.
  • Bench noise in CI: criterion wall-clock sensitive to CI machine load; use criterion::Criterion::sample_size(50) + warm-up; gate on relative regression (±10%) not absolute.
  • Fault injection state machine: FaultInjectingWorkload must consume faults in order; not random; reproducible.
