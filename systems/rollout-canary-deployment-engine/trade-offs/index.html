ADR-01

Language

Chosen

Rust 2021, MSRV 1.78

Rejected

Go, TypeScript, Python

When the rejected choice is right

Go wins when you must vendor k8s.io/client-go and informers directly and ship into an all-Go operator ecosystem where contributor familiarity beats type safety

Why: Exhaustive enums, no nil bugs, async perf

Alternative Architectures (Roads Not Taken)

Three fundamentally different designs for the same problem, each with the regime where it wins and why this blueprint rejected it.

A. Sidecar-per-workload mesh controller (no central reconciler).

  +--------------------+        +--------------------+
  |  workload pod A    |        |  workload pod B    |
  |  [app] [canary     |        |  [app] [canary     |
  |        sidecar]----+--gossip-+------ sidecar]     |
  +---------|----------+        +----------|---------+
            |  local weight + local metric decision   |
            v                                         v
        data-plane proxy                       data-plane proxy

Each workload carries a sidecar that owns its own weight and reads local metrics; promotion is a decentralized, gossip-coordinated decision. Wins at extreme scale / multi-cluster where a single central writer is the bottleneck and the data plane already runs a mesh (closest real embodiment: Istio/Linkerd traffic shifting driven by per-workload config, or service-mesh canary patterns). Rejected because it abandons the single-writer correctness primitive (§6 P6, MM6): decentralized weight decisions reintroduce exactly the split-brain weight thrash this project exists to eliminate, and decentralized verdicts cannot give the global audit trail (§6 P13).

B. Pipeline / DAG-orchestrated delivery (delivery as workflow).

   stage: deploy-canary  --> stage: bake  --> stage: ACA-judge
        |                       |                  |
        v                       v                  v
   [orchestrator persists each stage; manual/auto gates between stages]
                          --> stage: promote OR rollback

Delivery is a multi-stage workflow executed by an orchestrator that persists stage state and inserts judgment/approval gates between stages. Wins for multi-cloud, multi-service release trains with human approval gates and heterogeneous targets (real embodiment: Spinnaker + Kayenta, Orca pipelines + Clouddriver). Rejected because it is edge/stage-triggered rather than level-triggered (§6 P1, MM1): a crash mid-stage needs explicit resume logic, whereas this blueprint's reconciler re-derives state every tick and is crash-safe by construction (Phase 3 — canary-reconcile, Phase 12 replay).

C. Feature-flag / dark-launch progressive delivery (decouple deploy from release).

   deploy 100% new binary (dark)  -->  flag service
                                          |  % rollout, targeting rules
                                          v
                          request path reads flag -> new vs old code path

The new code ships everywhere but stays dark behind a flag; "rollout" is ramping a flag percentage and rollback is flipping it off — no ReplicaSet or traffic-weight machinery. Wins for in-process feature gating, per-user targeting, and instant kill-switch rollback where traffic-level splitting is too coarse (real embodiment: LaunchDarkly-style flag platforms; cross-links to sibling system 167 Feature Flags + A/B). Rejected as the primary model because it conflates deploy with release at the request layer and offers no ReplicaSet-level revision identity (§6 P9, MM5) or readiness gating (§6 P5) — and, per the Knight Capital incident (Failure Modes & Recovery), a repurposed live flag is itself a catastrophic failure mode. The Experiment step (§8 Domain Model §8.4) borrows the idea narrowly without adopting it wholesale.
