274 — Rollout / Canary Deployment Engine

Goal: A from-scratch progressive-delivery controller in Rust driving canary, blue-green, and rolling deployment strategies with automated, metric-driven promotion and rollback. Reconciles a declarative Rollout spec: manages stable + canary workloads, shifts traffic via a pluggable TrafficRouter, runs metric Analysis against pluggable MetricProviders, gates progression on ordered steps, and auto-promotes or rolls back. Level-triggered, idempotent reconciliation; single-writer via leader election.

1. Goal

Precise definition: A Rust 2021 progressive-delivery controller (canaryd) plus CLI (canaryctl) that owns the full lifecycle of a Rollout resource — from spec declaration through traffic shifting, metric analysis, promotion/rollback, and history GC — without being tied to any specific orchestrator, mesh, or metrics backend.

Deployment model: Out-of-process controller; watches a store of Rollout objects; reconciles desired spec → observed status via provider abstractions. Single-writer (leader-elected). Providers (workload, traffic, metric) are pluggable trait impls compiled in or loaded at startup.

Users / operators: Platform engineers deploying versioned workloads; SREs gating promotion on SLOs; automation pipelines calling imperative commands (promote/abort); on-call engineers reading structured audit trails.

Phase-0 deliverable — 10 crates (workspace skeleton, CI green):

  1. canary-model — domain types + state-machine shells
  2. canary-store — desired/observed state persistence stubs
  3. canary-reconcile — reconcile-loop skeleton + workqueue
  4. canary-workload — WorkloadProvider trait + in-memory stub
  5. canary-traffic — TrafficRouter trait + no-op stub
  6. canary-analysis — MetricProvider trait + no-op stub
  7. canary-events — event recorder + notification hook stubs
  8. canary-api — API server stubs (CRUD + command endpoints)
  9. canary-controller — canaryd binary wiring
  10. canary-cli — canaryctl binary stubs

Later phases unlock: full domain types + state machines (Ph1); persistence + history (Ph2); full reconcile loop (Ph3); workload management (Ph4); rolling strategy E2E (Ph5); traffic routing (Ph6); canary steps engine (Ph7); analysis execution (Ph8); promotion/rollback + blue-green (Ph9); API + CLI (Ph10); observability + resilience (Ph11); conformance + bench (Ph12).

Deferred features (gated PhaseDeferred("Deferred Features Register")):

  • Multi-cluster traffic routing → PhaseDeferred("Deferred Features Register")
  • WASM plugin loader for providers → PhaseDeferred("Deferred Features Register")
  • Experiment / A-B test scheduler (beyond Experiment step) → PhaseDeferred("Deferred Features Register")
  • GitOps status-write-back → PhaseDeferred("Deferred Features Register")
  • Admission webhook for spec validation → PhaseDeferred("Deferred Features Register")

Timeline: Phase 0 target 1–2 weeks; full 13-phase arc 6–14 weeks depending on team size.

Language + rationale: Rust 2021, MSRV 1.78, async Tokio.

  • Exhaustive enums → illegal strategy-state transitions unrepresentable at compile time.
  • Precise spec/status typing eliminates nil/zero-value state-machine bugs (Go's primary failure mode in Argo/Flagger).
  • Tokio async → cheap concurrency for ≥1000 concurrent Rollout watches + provider I/O.
  • thiserror / anyhow error taxonomy; serde for serialization; axum for API.
  • Rejected: Go (canonical ecosystem but weaker sum types + nil-pointer state bugs); TypeScript (hot-loop perf); Python (concurrency/perf).

Prerequisites: familiarity with control-loop theory (Kubernetes reconciler pattern), traffic-splitting primitives (SMI, Gateway API), Prometheus query model, and async Rust.

2. Why Build This

Unique knowledge gained:

  • Level-triggered reconciliation: correct convergence without edge-triggered delivery guarantees.
  • Traffic-invariant engineering: stable_weight + canary_weight == 100 across provider restarts, partial failures, and concurrent updates.
  • Metric-gated promotion: translating SLO expressions into binary promotion decisions with bounded inconclusiveness.
  • Optimistic concurrency in a custom store: observedGeneration / resourceVersion preventing split-brain writes.
  • Leader election as a correctness primitive (not just HA): single-writer invariant prevents weight thrash.

Significance: Progressive delivery is the dominant safe-deployment primitive in modern infrastructure. Building it from scratch reveals every implicit assumption Argo Rollouts and Flagger make — provider coupling, edge-trigger debt, nil-state bugs — and forces principled solutions.

Muscles exercised: state-machine design; pluggable provider architecture; idempotent action application; metric windowing + verdict logic; history GC; structured event logging; conformance testing; differential semantic testing vs reference impl.

canary-api: Axum HTTP server exposing Rollout CRUD, imperative command endpoints (/rollouts/{name}/promote, /abort, /pause, /resume, /undo), and a watch/SSE stream. Validates spec on write; rejects illegal strategy combinations. Writes desired state to canary-store.

canary-controller (canaryd): Binary entry point. Acquires leader lease; starts reconcile loop over all Rollouts; fans out per-Rollout reconcile tasks via Tokio; drains workqueue on shutdown. Single-writer invariant enforced here — no other process may mutate provider state.

canary-reconcile: Core reconcile function reconcile(rollout, store, providers) → ActionSet. Computes diff between desired spec + current status and observed provider state. Emits idempotent Action variants (ScaleWorkload, SetWeight, StartAnalysis, AdvanceStep, Promote, Abort). Applies actions; writes updated status. Requeueing + exponential backoff on transient errors.

canary-workload: WorkloadProvider trait: create_revision, scale, ready_count, pod_template_hash. Manages stable RS + canary RS lifecycle. Enforces maxSurge/maxUnavailable arithmetic. Readiness-gates traffic admission.

canary-traffic: TrafficRouter trait: set_weights(stable, canary), set_header_route, set_mirror, get_weights. Providers: in-memory (test), SMI-like, Gateway-API-like, configurable-ingress. Weight drift detection + correction each reconcile.

canary-analysis: MetricProvider trait: query(metric, window) → Measurement. AnalysisRun executor: schedules measurement intervals, evaluates success_condition/failure_condition CEL-like expressions, tracks failureLimit/inconclusiveLimit, emits verdict (Successful | Failed | Inconclusive | Error).

canary-store: Durable map of Rollout desired + status; revision history ring (revisionHistoryLimit GC); optimistic concurrency via resourceVersion; event log (append-only); snapshot/restore for replay.

canary-model: All domain types + transition tables. Canary phase machine, blue-green phase machine, step sequencer. Illegal transitions rejected at type level (exhaustive enum match).

canary-events: Structured event recorder (type/reason/message/timestamp); notification dispatcher (webhook POST, configurable retry); audit trail queryable by rollout/step/time.

6. Design Principles

1. Level-triggered reconciliation Every reconcile recomputes desired state from spec+status+observed provider state; actions are derived, not accumulated. Never rely on receiving every event. Tradeoff: slightly more work per cycle. Operational: controller crash + restart is safe — re-derives identically. Violation: caching "last applied weight" outside store → weight drift after restart.

2. Idempotent action application Every Action variant is safe to apply multiple times with the same outcome. set_weights(30,70) twice == once. Tradeoff: providers must support idempotent writes (check-then-set). Operational: requeueing on transient error never causes double-scale. Violation: scale_up increments instead of sets → runaway replica counts.

3. Illegal state transitions are unrepresentable Phase and AnalysisPhase enums + exhaustive match → compiler rejects transition code that skips states. Tradeoff: more enum variants, more match arms. Operational: no runtime panic! from invalid state. Violation: using String for phase → any typo compiles.

4. Traffic invariant: stable + canary == 100 always Weight split enforced at every observable point. Weight verified after provider apply each reconcile; drift → correction action. Tradeoff: extra provider read per reconcile. Operational: no traffic loss or over-routing visible to users. Violation: setting canary weight without adjusting stable → >100% or <100%.

5. No traffic to not-ready pods WorkloadProvider.ready_count() gates traffic admission. Canary weight set to 0 until at least 1 ready pod on canary RS. Tradeoff: analysis start delayed if canary RS slow to ready. Operational: user-facing error rate not inflated by unready pods. Violation: advancing SetWeight step before readiness check.

6. Single-writer via leader election Only the leader reconcile loop writes provider state. Standby instances watch but do not act. Tradeoff: leader failover gap (≤ TTL). Operational: prevents weight thrash when two controllers disagree. Violation: running two canaryd instances without leader election → competing SetWeight calls.

7. Abort is sticky Once Phase::Aborted, no automatic re-progression. Requires explicit promote/retry command. Canary weight → 0, canary RS → 0 replicas, stable serves 100%. Tradeoff: operator must act to resume. Operational: prevents accidental re-advancement after a bad deploy. Violation: re-advancing from Aborted on next reconcile without operator intent.

8. Analysis verdict gates progression strictly Failed → immediate abort+rollback. Inconclusive → hold (bounded by inconclusiveLimit). Error counts toward failureLimit. Successful → advance step. No partial advancement. Tradeoff: conservative — one failed metric aborts. Operational: SLO regressions never silently promote. Violation: advancing despite Inconclusive verdict.

9. pod-template-hash identifies revision; same template reuses RS Hash computed over PodTemplate spec. Identical template on re-deploy → reuse existing RS (no churn). Different template → new RS, new canary. Tradeoff: hash collisions (cryptographically negligible with sha256). Operational: rollback to previous version is instantaneous (RS already exists). Violation: using RS name or deploy timestamp as revision key.

10. progressDeadlineSeconds is a liveness guarantee If no progress (step advance, scale change, weight change) within deadline → Phase::Degraded condition. Does not auto-abort (operator decision). Tradeoff: must define "progress" precisely (any status field change). Operational: on-call alerted to stalled rollout before it blocks the pipeline. Violation: timer reset on any reconcile (not just progress events).

11. Revision history is bounded revisionHistoryLimit (default 10) caps kept RSes. GC runs after every successful promotion. Tradeoff: cannot rollback beyond limit. Operational: storage bounded; history ring prevents unbounded growth. Violation: deleting RS without removing from revision index → dangling reference.

12. Provider failures are transient until proven permanent Network errors, timeouts → requeue with backoff (not abort). Consecutive failures beyond threshold → Degraded condition. Tradeoff: slow failure detection. Operational: provider blip does not abort a good rollout. Violation: treating first provider error as fatal.

13. Structured events are the audit trail Every state transition, action, verdict, and command emits a structured event (type/reason/message/involvedObject/timestamp). Events are append-only. Tradeoff: event volume at scale. Operational: post-incident replay from events; no grep in logs. Violation: logging instead of recording structured events.

14. Blue-green scaleDownDelay enables fast rollback Old RS kept at full scale for scaleDownDelay after active-service promotion. Rollback = re-promote old RS instantly. Tradeoff: 2× replica cost during delay. Operational: P0 rollback < 1 reconcile if within delay window. Violation: scaling down old RS immediately after promotion.

15. API commands are imperative overlays on declarative spec promote/abort/pause/resume mutate RolloutSpec.paused and RolloutStatus.abort fields in store; reconcile picks them up on next cycle. Commands are not RPC side-effects; they are spec patches. Tradeoff: command takes effect on next reconcile (not synchronous). Operational: commands are idempotent; safe to retry. Violation: commands that directly call provider APIs bypassing reconcile.

8.4 CanaryStep Sequencing

steps: [SetWeight(10), Pause{60s}, Analysis(ref), SetWeight(50), Pause{∞}, SetWeight(100)]
         idx=0          idx=1       idx=2           idx=3          idx=4     idx=5

  • SetWeight(w): emit SetWeight action; complete immediately after provider confirms.
  • Pause{duration}: record pause_start_time; complete when now - pause_start > duration; duration == None → manual gate (wait for promote command).

8.6 Traffic Weight Model

  • Weights expressed as integers 0–100 (percent).
  • stable_weight = 100 - canary_weight always.
  • Weight transitions: one SetWeight action per reconcile; provider applies atomically.
  • Verification: after apply, read back weights from provider; if drift > 1% → emit correction action + traffic_weight_drift metric.
  • Header routing: additional route rule, does not affect weight accounting.
  • Mirroring: shadow traffic, not counted in weight model.

Mental Models & First Principles

The compressed intuitions an expert holds about progressive delivery. Each states the insight, what it predicts, the bug class you write without it, and where this blueprint applies it.

MM1 — A reconciler is a clock, not an inbox. Each tick recomputes the whole desired state from spec + status + observed provider state; events only schedule a tick, they never carry state. Predicts: dropping, duplicating, or reordering events cannot corrupt the system — only delay convergence. Without it: you accumulate actions from an event stream and a missed/duplicated watch event leaves weights stuck or thrashing after restart. Applied: §6 P1 and Phase 3 — canary-reconcile; the Phase 0 smoke test already exercises it.

MM2 — Traffic weight is a conserved quantity; the verifier is the conservation law. stable_weight + canary_weight == 100 is an invariant a provider can silently violate via rounding or external edits, so each reconcile reads weights back and corrects drift. Predicts: the only safe weight operation is "set both sides together, then verify"; any one-sided write is a bug. Without it: you set canary to 70 without lowering stable and route 170% or 30% of traffic. Applied: §6 P4, §7 I1, Phase 6 — canary-traffic.

MM3 — A canary verdict is a hypothesis test with a third outcome. The question is "is the canary meaningfully worse than stable?", answered PASS / FAIL / NONE — never an absolute health score. Predicts: you need an explicit Inconclusive/NONE path (insufficient data, provider gap) distinct from Failed, with its own bound. Without it: a metric gap is miscoded as success (silent bad promotion) or as failure (needless abort). Applied: the §8 Domain Model verdict semantics (§8.5), §6 P8, Phase 8 — canary-analysis; modeled on Google CAS (§5).

MM4 — resource_version is a logical clock; CAS turns a lost update into a retry. Every write carries the version it read; a stale write is rejected, not silently overwritten. Predicts: concurrent reconciles can never produce a torn status — the loser simply re-reads and recomputes. Without it: a non-leader (or racing) write clobbers a fresh status and the rollout regresses a step. Applied: §7 I3, Phase 2 — canary-store; pattern from Zanzibar (§5).

MM5 — A revision is content-addressed by its pod-template-hash. Identity follows the PodTemplate bytes, not a name or timestamp; identical template ⇒ same hash ⇒ same ReplicaSet. Predicts: rollback to a prior version is an O(1) lookup of an RS that already exists, and old/new code can never collide under one key. Without it: re-deploys churn new RSes, and (Knight Capital, 2012) a repurposed identifier conflates two code versions. Applied: §6 P9, §7 I5, Phase 4 — canary-workload.

MM6 — The leader lease is a fence token, and single-writer is a correctness primitive. Leader election here is not just HA; it guarantees exactly one process mutates provider state at a time. Predicts: without a fenced single writer, two controllers issue competing set_weights and the split oscillates. Without it: you treat election as optional HA and ship weight thrash on every failover overlap. Applied: §6 P6, §7 I8, Phase 11 — Observability and Resilience; grounded in Chubby (§5).

MM7 — scaleDownDelay buys an undo window; capacity is its price. Keeping the old ReplicaSet at full scale after promotion makes rollback a pointer-flip instead of a cold-start. Predicts: the fast-rollback window equals the delay, and you pay ~2× replicas for its duration — a deliberate capacity-for-RTO trade. Without it: a post-promotion regression forces a slow scale-up of the old version while users suffer. Applied: §6 P14, Phase 9 — Promotion, Rollback, and Blue-Green.

MM8 — Idempotent actions decouple delivery from correctness. Every Action sets a target (not a delta) and is safe to apply twice, so "did my apply land?" never needs an exactly-once channel. Predicts: retries, requeues, and replay are always safe; correctness never depends on delivery semantics. Without it: a retried scale_up that increments produces runaway replicas. Applied: §6 P2, Phase 3 — canary-reconcile, and the deterministic replay in Phase 12 — Conformance, Fault Injection, Replay, Bench.

Argo Rollouts made the decision to be Kubernetes-native to the core — its Rollout is a CRD reconciled by controller-runtime and every traffic provider is a k8s integration. That wins decisively inside a single Kubernetes cluster: zero abstraction tax, native RBAC, owner-reference GC. canaryd instead pays for a provider trait layer to stay orchestrator-agnostic (see ADR-10 "when the rejected choice wins").

Flagger chose webhook-centric gating with the mesh as the traffic authority — analysis and approval are external HTTP hooks, and weight is owned by Istio/Linkerd/App Mesh. That wins when an org already runs a service mesh and wants delivery logic expressed as composable webhooks rather than embedded analysis. This blueprint embeds the analysis runtime (Phase 8) so it can run standalone without a mesh, accepting more in-process complexity.

Spinnaker + Kayenta chose statistical automated canary analysis (ACA) — Kayenta scores the canary against a control population with non-parametric tests (Mann-Whitney) rather than fixed condition thresholds. That wins at very large scale where hand-tuned thresholds are brittle and a learned similarity verdict generalizes (the CAS lineage, §5). canaryd uses explicit Rhai conditions (ADR-21) for transparency and zero-dependency determinism, deferring statistical scoring as a future MetricProvider/verdict strategy.

AWS CodeDeploy chose managed, alarm-driven blue/green within one cloud — traffic shift and rollback are platform features keyed off CloudWatch alarms, with no controller to operate. That wins for teams that want progressive delivery as a turnkey AWS capability and accept single-cloud lock-in. canaryd is the opposite trade: you run the controller, but it is portable across substrates and metric backends.

Back-of-Envelope Capacity Model

Every number derives from the §4 System Constraints table; formula shown. These are the figures an expert computes before committing to the design.

  1. Controller working-set RAM (steady state). concurrent_rollouts × mem_per_rollout = 1000 × 2 MB = 2 GB. The §4 target of ≥1000 rollouts at <2 MB each sets the controller's baseline heap; node sizing starts here.
  2. Event-log memory ceiling (all rollouts). concurrent_rollouts × event_ring_cap × bytes_per_event. With ~512 B per CloudEvent JSON record: 1000 × 10 000 × 512 B ≈ 5.1 GB if every ring is full — i.e. the event log, not the rollout state, dominates memory, justifying the 10 000-entry ring cap and async batch writes (Scalability Analysis).
  3. Reconcile throughput ceiling (single worker). 1 / p99_reconcile_latency = 1 / 50 ms = 20 reconciles/s worst-case per serialized worker. To converge 1000 rollouts each needing ~6 reconciles, a single worker takes 1000 × 6 / 20 = 300 s — which is why §4's bounded-concurrency workqueue (semaphore ~200) fans reconciles out rather than serializing them.
  4. Steady-state reconcile rate (resync). With a default resync near the 15 s leader TTL: concurrent_rollouts / resync_interval = 1000 / 15 s ≈ 67 reconciles/s baseline load — comfortably under the 20/s-per-worker ceiling once fanned across ~4 workers (67 / 20 ≈ 3.4).
  5. Prometheus query fan-out at peak. concurrent_rollouts × metrics_per_run = 1000 × 3 = 3000 concurrent queries if every rollout analyses at once; the §4 analysis path therefore caps in-flight queries with a semaphore (max_concurrent_queries ≈ 100), bounding provider pressure to 100 / 0.2 s = 500 queries/s at a 200 ms budget.
  6. Analysis scheduling precision. §4 requires analysis jitter <1 s against a measurement interval. For a 60 s interval that is 1 / 60 ≈ 1.7% allowed drift per tick — only achievable with absolute sleep_until, not relative sleeps (Phase 8 — canary-analysis).
  7. Webhook dispatcher saturation. webhook_timeout × max_in_flight bounds tail exposure: at a 10 s per-hook timeout and a fan-out semaphore of 20, a wave of failing hooks costs at most 10 s wall time per batch of 20, so 1000 pending notifications drain in (1000 / 20) × 10 s = 500 s worst case — hence dispatch must be non-blocking to reconcile (§6 P15-adjacent, Phase 11).
  8. Leader renewal overhead. Renew at TTL / 2 = 15 s / 2 = every 7.5 s ⇒ 1 / 7.5 s ≈ 0.13 store writes/s for the lease — negligible against reconcile write volume, confirming store-CAS election (ADR-07) is essentially free.
  9. Failover blast-radius window. Worst-case time with no single writer = one full leader_TTL = 15 s (§4). During this window weights are frozen, not wrong (MM1), so the user-visible impact is delayed convergence, not traffic loss.
  10. Binary + image footprint. canaryd <30 MB stripped (§4); on a distroless cc base (~25 MB) the deployable image is ≈ 55 MB, keeping cold-start pulls fast for the <500 ms startup target in Performance Engineering.
  11. Revision-history storage per rollout. revisionHistoryLimit × rs_record_size. At the default limit 10 and ~4 KB per serialized RS record: 10 × 4 KB = 40 KB/rollout, or 40 MB across 1000 rollouts — trivial, which is why GC targets correctness (no dangling refs, §7 I6) over space.
  12. Watch fan-out memory. watch_subscribers × per_sub_buffer. With a 1024-slot broadcast channel and ~512 B per buffered WatchEvent: 1024 × 512 B = 512 KB per hot rollout's channel — bounded, with lagged subscribers pruned rather than blocking (Scalability Analysis).

Alternative Architectures (Roads Not Taken)

Three fundamentally different designs for the same problem, each with the regime where it wins and why this blueprint rejected it.

A. Sidecar-per-workload mesh controller (no central reconciler).

  +--------------------+        +--------------------+
  |  workload pod A    |        |  workload pod B    |
  |  [app] [canary     |        |  [app] [canary     |
  |        sidecar]----+--gossip-+------ sidecar]     |
  +---------|----------+        +----------|---------+
            |  local weight + local metric decision   |
            v                                         v
        data-plane proxy                       data-plane proxy

Each workload carries a sidecar that owns its own weight and reads local metrics; promotion is a decentralized, gossip-coordinated decision. Wins at extreme scale / multi-cluster where a single central writer is the bottleneck and the data plane already runs a mesh (closest real embodiment: Istio/Linkerd traffic shifting driven by per-workload config, or service-mesh canary patterns). Rejected because it abandons the single-writer correctness primitive (§6 P6, MM6): decentralized weight decisions reintroduce exactly the split-brain weight thrash this project exists to eliminate, and decentralized verdicts cannot give the global audit trail (§6 P13).

B. Pipeline / DAG-orchestrated delivery (delivery as workflow).

   stage: deploy-canary  --> stage: bake  --> stage: ACA-judge
        |                       |                  |
        v                       v                  v
   [orchestrator persists each stage; manual/auto gates between stages]
                          --> stage: promote OR rollback

Delivery is a multi-stage workflow executed by an orchestrator that persists stage state and inserts judgment/approval gates between stages. Wins for multi-cloud, multi-service release trains with human approval gates and heterogeneous targets (real embodiment: Spinnaker + Kayenta, Orca pipelines + Clouddriver). Rejected because it is edge/stage-triggered rather than level-triggered (§6 P1, MM1): a crash mid-stage needs explicit resume logic, whereas this blueprint's reconciler re-derives state every tick and is crash-safe by construction (Phase 3 — canary-reconcile, Phase 12 replay).

C. Feature-flag / dark-launch progressive delivery (decouple deploy from release).

   deploy 100% new binary (dark)  -->  flag service
                                          |  % rollout, targeting rules
                                          v
                          request path reads flag -> new vs old code path

The new code ships everywhere but stays dark behind a flag; "rollout" is ramping a flag percentage and rollback is flipping it off — no ReplicaSet or traffic-weight machinery. Wins for in-process feature gating, per-user targeting, and instant kill-switch rollback where traffic-level splitting is too coarse (real embodiment: LaunchDarkly-style flag platforms; cross-links to sibling system 167 Feature Flags + A/B). Rejected as the primary model because it conflates deploy with release at the request layer and offers no ReplicaSet-level revision identity (§6 P9, MM5) or readiness gating (§6 P5) — and, per the Knight Capital incident (Failure Modes & Recovery), a repurposed live flag is itself a catastrophic failure mode. The Experiment step (§8 Domain Model §8.4) borrows the idea narrowly without adopting it wholesale.
