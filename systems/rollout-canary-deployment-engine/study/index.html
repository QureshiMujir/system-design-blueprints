Mental Models & First Principles

The compressed intuitions an expert holds about progressive delivery. Each states the insight, what it predicts, the bug class you write without it, and where this blueprint applies it.

MM1 — A reconciler is a clock, not an inbox. Each tick recomputes the whole desired state from spec + status + observed provider state; events only schedule a tick, they never carry state. Predicts: dropping, duplicating, or reordering events cannot corrupt the system — only delay convergence. Without it: you accumulate actions from an event stream and a missed/duplicated watch event leaves weights stuck or thrashing after restart. Applied: §6 P1 and Phase 3 — canary-reconcile; the Phase 0 smoke test already exercises it.

MM2 — Traffic weight is a conserved quantity; the verifier is the conservation law. stable_weight + canary_weight == 100 is an invariant a provider can silently violate via rounding or external edits, so each reconcile reads weights back and corrects drift. Predicts: the only safe weight operation is "set both sides together, then verify"; any one-sided write is a bug. Without it: you set canary to 70 without lowering stable and route 170% or 30% of traffic. Applied: §6 P4, §7 I1, Phase 6 — canary-traffic.

MM3 — A canary verdict is a hypothesis test with a third outcome. The question is "is the canary meaningfully worse than stable?", answered PASS / FAIL / NONE — never an absolute health score. Predicts: you need an explicit Inconclusive/NONE path (insufficient data, provider gap) distinct from Failed, with its own bound. Without it: a metric gap is miscoded as success (silent bad promotion) or as failure (needless abort). Applied: the §8 Domain Model verdict semantics (§8.5), §6 P8, Phase 8 — canary-analysis; modeled on Google CAS (§5).

MM4 — resource_version is a logical clock; CAS turns a lost update into a retry. Every write carries the version it read; a stale write is rejected, not silently overwritten. Predicts: concurrent reconciles can never produce a torn status — the loser simply re-reads and recomputes. Without it: a non-leader (or racing) write clobbers a fresh status and the rollout regresses a step. Applied: §7 I3, Phase 2 — canary-store; pattern from Zanzibar (§5).

MM5 — A revision is content-addressed by its pod-template-hash. Identity follows the PodTemplate bytes, not a name or timestamp; identical template ⇒ same hash ⇒ same ReplicaSet. Predicts: rollback to a prior version is an O(1) lookup of an RS that already exists, and old/new code can never collide under one key. Without it: re-deploys churn new RSes, and (Knight Capital, 2012) a repurposed identifier conflates two code versions. Applied: §6 P9, §7 I5, Phase 4 — canary-workload.

MM6 — The leader lease is a fence token, and single-writer is a correctness primitive. Leader election here is not just HA; it guarantees exactly one process mutates provider state at a time. Predicts: without a fenced single writer, two controllers issue competing set_weights and the split oscillates. Without it: you treat election as optional HA and ship weight thrash on every failover overlap. Applied: §6 P6, §7 I8, Phase 11 — Observability and Resilience; grounded in Chubby (§5).

MM7 — scaleDownDelay buys an undo window; capacity is its price. Keeping the old ReplicaSet at full scale after promotion makes rollback a pointer-flip instead of a cold-start. Predicts: the fast-rollback window equals the delay, and you pay ~2× replicas for its duration — a deliberate capacity-for-RTO trade. Without it: a post-promotion regression forces a slow scale-up of the old version while users suffer. Applied: §6 P14, Phase 9 — Promotion, Rollback, and Blue-Green.

MM8 — Idempotent actions decouple delivery from correctness. Every Action sets a target (not a delta) and is safe to apply twice, so "did my apply land?" never needs an exactly-once channel. Predicts: retries, requeues, and replay are always safe; correctness never depends on delivery semantics. Without it: a retried scale_up that increments produces runaway replicas. Applied: §6 P2, Phase 3 — canary-reconcile, and the deterministic replay in Phase 12 — Conformance, Fault Injection, Replay, Bench.

5. Required Reading

Books

  • Designing Distributed Systems — Burns; patterns: level-triggered loops, sidecar, operator. Applied: Design Principles P1 (level-triggered) and Phase 3 — canary-reconcile.
  • Programming Rust (2nd ed.) — Blandy & Orendorff; ownership, async, error taxonomy. Applied: Core Schema and Core Types (ownership annotations) and Phase 1 — canary-model.
  • Kubernetes in Action (2nd ed.) — Lukša; controller pattern, ReplicaSet, owner references. Applied: Phase 4 — canary-workload (RS lifecycle, pod-template-hash) and Phase 5 — Rolling Strategy E2E.
  • Site Reliability Engineering — Beyer et al.; ch. "Canarying Releases", SLO-gating, error budgets. Applied: Design Principle P8 (verdict gating) and Phase 8 — canary-analysis.
  • Database Internals — Petrov; optimistic concurrency, MVCC analogy for resource_version. Applied: Invariant I3 and Phase 2 — canary-store (CAS).
  • Implementing Service Level Objectives — Davies; metric windows, alerting math. Applied: Phase 8 — canary-analysis (measurement windows) and the Operational Readiness alerting rules.

Papers

  • Borg, Omega, and Kubernetes (Burns, Grant, Oppenheimer, Brewer, Wilkes, ACM Queue 2016) — control-loop lineage, level-triggered reconciliation rationale. Applied: Design Principle P1 and Phase 3 — canary-reconcile.
  • Large-scale cluster management at Google with Borg (Verma et al., EuroSys 2015) — task scheduling and health model. Applied: Phase 4 — canary-workload (readiness/health model).
  • Zanzibar: Google's Consistent, Global Authorization System (Pang et al., USENIX ATC 2019) — optimistic-concurrency / versioned-write patterns. Applied: Invariant I3 and Phase 2 — canary-store (resource_version model).
  • The Chubby lock service for loosely-coupled distributed systems (Burrows, OSDI 2006) — lease-based leader election foundations. Applied: Design Principle P6 and Phase 11 — Observability and Resilience (lease election).
  • Monarch: Google's Planet-Scale In-Memory Time Series Database (Adams et al., VLDB 2020) — instant/range metric query semantics. Applied: the MetricProvider trait in Core Schema and Core Types and Phase 8 — canary-analysis.
  • Faults in Linux: Ten Years of Bugs (Palix et al., ASPLOS 2011) — fault taxonomy for fault-injection test design. Applied: Phase 12 — Conformance, Fault Injection, Replay, Bench.
  • Canary Releases (Sato, 2014, martinfowler.com) — conceptual model for traffic-split-based rollout. Applied: Phase 6 — canary-traffic and the canary state machine in §8.
  • Canary Analysis Service (Davidovič with Beyer, ACM Queue vol. 16 no. 1, 2018) — Google's centralized automated canary analysis (PASS/FAIL/NONE verdict, SLO-tied metrics, near-miss impact analysis). Applied: Phase 8 — canary-analysis (verdict aggregation, NONE→Inconclusive) and Design Principle P8.

Reference Implementations

  • Argo Rollouts (github.com/argoproj/argo-rollouts) — primary reference; study: Rollout CRD schema, canary step sequencer, AnalysisRun lifecycle, traffic plugin interface. Pitfall: tightly coupled to Kubernetes API machinery — we abstract providers instead. Applied: §8 step sequencer, Phase 7 — Canary Steps Engine, and Phase 8 — canary-analysis.
  • Flagger (github.com/fluxcd/flagger) — metric analysis design, webhook gates, mesh provider abstraction. Pitfall: edge-triggered watch assumptions — we use level-triggered reconcile. Applied: Phase 8 — canary-analysis (verdict) and the webhook dispatcher in Phase 11 — Observability and Resilience.
  • Kubernetes Deployment controller (pkg/controller/deployment) — rolling update math (maxSurge/maxUnavailable), pod-template-hash, ReplicaSet ownership. Pitfall: Recreate strategy conflated with RollingUpdate — keep strategies cleanly separated. Applied: Phase 4 — canary-workload (surge math, hash) and Phase 5 — Rolling Strategy E2E.
  • SMI TrafficSplit spec (github.com/servicemeshinterface/smi-spec) — traffic weight API semantics; study weight normalization. Applied: the SmiTrafficRouter in Phase 6 — canary-traffic and Invariant I1.
  • Gateway API HTTPRoute (gateway-api.sigs.k8s.io) — header-routing + weight semantics for TrafficRouter design. Applied: the GatewayApiRouter and header routing in Phase 6 — canary-traffic.
  • controller-runtime (sigs.k8s.io/controller-runtime) — workqueue, rate-limiter, leader election patterns (extract concepts, not Go code). Applied: the workqueue in Phase 3 — canary-reconcile and leader election in Phase 11 — Observability and Resilience.
  • Linkerd SMI adapter (github.com/linkerd/linkerd-smi) — real TrafficSplit provider for conformance reference. Applied: Phase 6 — canary-traffic (provider conformance) and Phase 12 — Conformance, Fault Injection, Replay, Bench.
  • Prometheus HTTP API (prometheus.io/docs/prometheus/latest/querying/api/) — range/instant query semantics for MetricProvider. Applied: the PrometheusProvider in Phase 8 — canary-analysis.
  • Temporal workflow SDK (github.com/temporalio/sdk-go) — compensating-transaction pattern for rollback (conceptual). Applied: the abort/rollback path in Phase 9 — Promotion, Rollback, and Blue-Green.

Glossary · 38 terms · site-wide glossary

Progressive delivery
Deploy new version to subset; gate promotion on metrics; rollback on failure
Canary
Strategy: route fraction of traffic to new version via weighted split
Blue-green
Strategy: full new version on preview; switch active service on promotion
Rolling update
Strategy: replace pods incrementally honoring surge/unavailable bounds
Stable ReplicaSet
RS serving 100% traffic on the known-good version
Canary ReplicaSet
RS serving canary traffic on the new version
Revision
Versioned RS snapshot identified by pod-template-hash
pod-template-hash
SHA-256 of PodTemplate canonical JSON; identifies a unique RS
Traffic weight
Integer 0–100 percent allocated to stable or canary RS
Traffic shifting
Progressive increase of canary weight across steps
Traffic mirroring
Shadow copy of requests to canary; not counted in weight model
Header routing
Route requests matching a specific HTTP header to canary RS
SetWeight step
Canary step that updates traffic split to a specified weight
Pause step
Canary step that halts progression for a duration or manual gate
Analysis step
Canary step that blocks on AnalysisRun verdict
AnalysisTemplate
Reusable definition of metrics + conditions for an analysis
AnalysisRun
Execution instance of an AnalysisTemplate; scoped to a rollout
Metric provider
Pluggable backend for querying metric values (e.g., Prometheus)
Success condition
Rhai expression evaluated against metric value; true → success
Failure condition
Rhai expression evaluated against metric value; true → failure
failureLimit
Max failure measurements before AnalysisRun → Failed
inconclusiveLimit
Max inconclusive measurements before AnalysisRun → Inconclusive
Promotion
Transition: canary RS becomes stable RS; old RS GC'd
Abort
Transition: canary weight → 0; canary RS → 0; Phase::Aborted
Rollback
Revert to previous revision; instantaneous if RS still at scale
Level-triggered reconciliation
Reconcile recomputes full desired state each cycle; safe to repeat
Idempotency
Applying same action multiple times produces same result
observedGeneration
Monotonic counter tracking which spec generation status reflects
maxSurge
Max pods above desired during rolling/canary; IntOrPercent
maxUnavailable
Max pods below desired during rolling/canary; IntOrPercent
minReadySeconds
Pod must be ready for N seconds before counted as available
progressDeadlineSeconds
No progress within deadline → Degraded condition
scaleDownDelay
Seconds to keep old RS at scale post-promotion (fast rollback window)
Preview service
Blue-green: service pointing to new RS before promotion
Active service
Blue-green: service pointing to current-production RS
Experiment
Ephemeral workload for A-B testing; spawned and torn down per step
Leader election
Single-writer guarantee via store CAS lease
Requeue / backoff
Delay before re-processing a reconcile item after error
