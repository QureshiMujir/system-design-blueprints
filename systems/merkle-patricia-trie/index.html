In one paragraph

A Merkle Patricia Trie is a key/value store arranged as a tree whose single top hash commits to every key and value in it, so anyone holding that hash can verify a proof about an entry (§1, §36). This design builds the Ethereum-style version in Rust: sixteen-way branching over half-byte path units, Keccak-256 node hashing, canonical RLP serialization, inclusion and exclusion proofs, content-addressed storage, journaled snapshots with rollback, and reference-counted pruning (§1). Its correctness is defined by matching go-ethereum and reth on the same input (P13, ADR-21). It is meant as the state backend of a blockchain execution client, a light-client verifier, or a standalone authenticated key/value store (§1).

The problem, concretely

A light client is handed a proof by a peer it does not trust, and must decide whether to believe it using only a claimed root (§1, §22, T1). The design's answer is a tree where a proof is "exactly enough of the tree to recompute the root, nothing more", so its size grows with depth, not with tree size (MM4).

The naive build fails quietly. The blueprint says getting any of four ideas subtly wrong (content addressing, radix-16 path compression, canonical serialization, stateless proofs) does not crash the program. It silently changes the state root, which only another implementation can reveal (§2). It calls this "correct-looking code producing a wrong answer with no local signal" and names it the project's most valuable lesson (§2).

Some concrete traps the design guards against:

  • Two encodings of one node. Equivalent nodes must serialize to byte-identical RLP, or roots diverge with no local error (P1, FM-1).
  • Adversarial keys. Raw keys chosen by an attacker can produce a maximal shared-prefix chain and exhaust the call stack (T3, P8).
  • A proof that proves nothing. "Silence is not evidence of absence", so an absence proof without a concrete boundary node is rejected (I15, T11).
  • Collecting a node too early. Subtrees are shared across versions, so a node must outlive every live snapshot root that reaches it (ADR-13, P12, T8).
  • A half-written commit. A crash between the WAL append and the data write leaves a partial write visible after restart; journaling every mutation first keeps it recoverable (P3, FM-8).

How it works, end to end

Follow one insert(key, value) through the layers of §3. Each box is a crate or module of the Cargo workspace (§1, §3). The diagram is adapted from §3.

 CLI / Inspector                crates/cli
   |
 Secure Trie / Coordinator      crates/secure-trie   (keccak256(key) | insert | delete | lookup |
   |                                                  commit | rollback)
 Path Encoder | Hashing Engine | Proof Engine
 primitives   | trie-core      | crates/proofs
   |
 Node Graph (branch | extension | leaf | embedded refs | hash refs)
   |
 RLP layer (crates/rlp) -> Journal (crates/journal) -> Storage (crates/storage, NodeStore trait)
   |
 Pruning / GC (crates/gc)
  1. Coordinator. crates/secure-trie takes the raw key and hashes it with keccak256 before anything else. There is no public raw-path bypass (§3, ADR-16, P11). It also owns mutation orchestration: one writer, snapshot-isolated readers (§3, ADR-22).
  2. Path Encoder. The 32-byte hash is expanded into 64 nibbles (a nibble is a 4-bit half byte). The hex-prefix codec in crates/primitives tags a stored path with its node kind and parity (§8, §13.1, I3).
  3. Node Graph. crates/trie-core walks branch, extension and leaf nodes using the state transition table of §8, splitting or collapsing nodes as needed (§15.2 steps 1 to 5).
  4. Hashing Engine. In crates/trie-core::hashing, each changed node is canonically encoded and hashed, and only the mutated path is re-hashed, not the whole tree (§14.3, §15.2 step 6, §14.2, P1, P2).
  5. RLP layer. crates/rlp is the consensus-critical codec. It rejects any non-minimal length prefix instead of warning (§3, I10).
  6. Journal. crates/journal records the mutation in an append-only log before it counts as committed (§3, P3, I5).
  7. Storage. crates/storage puts the node under its own hash, behind the NodeStore trait, so trie-core never imports RocksDB (§3, P7, ADR-04).
  8. Pruning. crates/gc later reclaims nodes that no live snapshot root reaches (§3, I4, P12).

The Proof Engine sits beside this path. It captures the nodes along a lookup, and a stateless verifier re-hashes them to check a claimed root (§3, §17.2 steps 1 and 3, ADR-24).

The core ideas

Nibble paths, three node kinds and hex-prefix tags (§8, I3, I7)

A key becomes a path of nibbles, and the tree has four node shapes (§8):

Node Shape Role
Branch 17 slots: 16 child references (nibble 0 to F) plus 1 optional value fan-out point
Extension (compact_path, child) one shared run of nibbles, one child
Leaf (compact_path, value) the end of a key
Empty RLP 0x80 the canonical empty subtree

An extension is path compression: it replaces a chain of one-child branches with one node (§8, glossary in §36). It is an optimisation over a branch-only trie, not a structural necessity (MM2).

A stored path needs the node kind and its odd or even length. The hex-prefix (compact) encoding packs both into a flag nibble: 0x0 extension even, 0x1 extension odd, 0x2 leaf even, 0x3 leaf odd (§8). For odd length, the first path nibble rides in the low half of the flag byte. For even length, a 0x0 padding nibble fills that slot (§8). A parity bug corrupts the path by one nibble instead of crashing (MM3, I3).

The insert rules, from the state-transition table (§8):

Node at the current path Key relationship What happens
Empty none replace with a new Leaf
Leaf same path replace the value
Leaf shares a prefix split into Extension plus Branch
Extension key shares all of it recurse into the child
Extension key diverges inside it split the Extension at the divergence
Branch path exhausted set the value slot
Branch path continues recurse into children[nibble]

The blueprint's own trace (illustrative nibbles, raw-key mode) inserts "dog" then "do" (§8):

  1. "dog" is the path [6,4,6,f,6,7]. It becomes a single Leaf at the root.
  2. "do" is [6,4,6,f], a prefix of the first path. An Extension covers the shared run and points at a Branch. The Branch's value slot holds hash2 (for "do"), and its nibble-6 child leads to a Leaf holding hash1 (for "dog").

Deletes collapse a branch left with a single child and remove orphan branches and redundant extensions (§15.2 steps 4 and 5), so no branch keeps fewer than 2 live slots (I7). Wrong collapse or split logic during delete is FM-7 (§23).

Canonical bytes, embedding and the root hash (§8, §14, I1, I2, I10)

A node's identity is the hash of its RLP (Recursive Length Prefix) encoding, so two machines must produce byte-identical bytes for equal nodes (P1, P2). A decoder must reject, not tolerate, any non-minimal length prefix (I10, P9). The blueprint's malformed example is a long-string prefix 0xb9 0x00 0x1f that claims a length of 31, which fits the short-string range, so a canonical encoder would never emit it and the decoder returns TrieError::NonCanonicalRlp (§8).

A child node is either inlined or referenced by hash (§8, I2, ADR-19):

Condition Stored as
len(canonical_rlp(node)) < 32 NodeRef::Embedded(bytes), inline in the parent
len(canonical_rlp(node)) >= 32 NodeRef::Hash(h), with h = keccak256(canonical_rlp(node))

The 32-byte threshold matches Appendix D of the Yellow Paper (the Ethereum specification) exactly (ADR-19, I2). The rule applies to the encoded node, not to the value inside it, and a leaf whose value is exactly 32 bytes must not be mistaken for a hash reference (§14.8, §14.6). The test suite covers node sizes 30, 31, 32, 33 and 34 (§14.4).

Hashing is original Keccak-256, not the FIPS-202 SHA3-256 padding. Using the standards-track crate gives "plausible-looking but wrong hashes" (ADR-02, §14.6). The root is the hash of the root node's canonical RLP, and the root must not depend on insertion order (I1, §14.2 step 5).

The secure trie: a fixed depth bound (§8, ADR-16, I9, I11)

In secure-trie mode the path is always keccak256(raw_key), never the raw key (I9). The pipeline is raw key, then a 32-byte hash, then 64 nibbles, then traversal (§8). The effect is that path length is fixed by the digest size, whatever the attacker chooses, so traversal depth is bounded at 64 nibbles (MM6, I11, CM2). Every public API takes a raw key and hashes it internally (P11). The cost is lost key-order locality (P11), and the benefit is a DoS mitigation, not a privacy feature (§2).

Proofs: just enough of the tree to recompute the root (§8, §17, I8, I15)

An inclusion proof is the ordered list of encoded nodes from the root down to the leaf (§8):

Proof.nodes = [ encoded_node_root, encoded_node_1, ..., encoded_node_leaf ]

Verification recomputes the root by hashing encoded_node_leaf up through each parent's reference slot to encoded_node_root and compares it with the claimed root (I8, §8). ProofVerifier::verify is a standalone function with no storage dependency (ADR-24, §17.2 step 3).

An exclusion proof, for a key that is absent, must end at a concrete dead end: a missing branch slot, or a leaf or extension whose path diverges from the query. "No proof" is never acceptable, because silence is not evidence of absence (§17.2 step 2, I15). An embedded child is part of its parent's RLP and is not a separate proof entry (§17.2 step 11, P4).

Journal, snapshots and rollback (§19, P3, I5, I6, I12, MM8)

Every mutation is logged before it counts as committed (P3). Log entries have strictly increasing sequence numbers (I5). A snapshot is a marker in the log, not a copy of the data, so creating one costs O(1) instead of O(state size) (MM8, ADR-12). Rollback replays the journal backward to a checkpoint and restores the recorded root (§19.2 step 4, I6).

On startup the system finds the last fsynced record, replays forward and validates the root against the last-known-good checkpoint (§19.2 step 5). Replay must be idempotent: running the same segment twice gives identical state, because a crash during replay must be safe to retry (I12, §19.2 step 6). Each record carries a CRC32 to catch torn writes (§19.2 step 7, FM-4).

Reference-counted pruning across snapshots (§20, I4, I13, P12, MM7)

Because nodes are addressed by content, identical subtrees are stored once and shared across versions (MM1, ADR-13). So a count of references per hash is kept (§20.2 steps 1 to 3). A node may be deleted only when its count, computed against all live snapshot roots and not just the current one, reaches zero (P12, §20.2 step 4). The pass marks nodes reachable from any live root and collects the rest (ADR-20, §20.2 step 5), and an independent reachability audit flags mismatches (§20.2 step 6). Refcounting only approximates reachability once several snapshots exist: naive counting that ignores open snapshots under- or over-collects at snapshot boundaries (MM7, §2).

The trade-offs — where engineers disagree

Secure trie: hash every key (ADR-16)

Chosen: keccak256(key) as the path, which bounds worst-case depth and defeats adversarial key-prefix attacks (§9, I9, I11). Rejected: a raw-key trie (§9). When the rejected choice is right: trusted-input indexes where raw-key locality matters and keys are not adversarial (§9).

Keep extension nodes (ADR-18)

Chosen: Ethereum-style extension nodes, needed for direct differential compatibility with go-ethereum and reth (§9). Rejected: an extension-free layout (§9). When the rejected choice is right: a greenfield store with no legacy-client interop requirement (§9). The blueprint says the variant is semantically equivalent but yields a different root (MM2).

Embed nodes under 32 bytes (ADR-19)

Chosen: inline a node when its RLP is under 32 bytes, matching the Yellow Paper's n() function (§9, I2). Rejected: fixed-arity inlining decided by node type only (§9). When the rejected choice is right: a non-Ethereum-compatible design free to pick its own inlining heuristic (§9). Proof code pays for the choice, since it must branch on embedded versus hashed at every child (P4).

Content-addressed nodes (ADR-13)

Chosen: a node's address is the keccak of its RLP, giving determinism, dedup and shared-subtree reuse across versions (§9, P6). Rejected: positional or offset addressing (§9). When the rejected choice is right: single-writer log-structured stores where offsets are already unique (§9). The blueprint frames the cost as the refcounting complexity that a version-keyed design avoids (§31, AA3, MM7).

Reference-counted mark-and-collect (ADR-20)

Chosen: collect on snapshot retirement, with a pause proportional to the retired delta, not the database size (§9). Rejected: a full mark-and-sweep over the entire database (§9). When the rejected choice is right: archive nodes that retain full history indefinitely, where a periodic full sweep is acceptable (§9).

Roads not taken (§34, §35)

No-extension trie (AA1, §34) wins when schema simplicity beats cross-client interop, such as substrate chains defining their own state-root rules. The real system named is paritytech/trie-db (Substrate). It is rejected here because it breaks byte-for-byte root compatibility with geth and reth (§34).

Verkle tree (AA2, §34) wins for proof-size-critical stateless clients. The real system named is go-verkle. It needs an elliptic-curve commitment library and different proof math, so it is out of scope and registered as deferred (§34, §35).

Version-keyed tree, the Jellyfish Merkle model (AA3, §34) wins when versioned historical queries are needed without content-addressed dedup complexity. The real system is Diem/Libra jellyfish-merkle. It is rejected because it loses ADR-13's content-addressed dedup guarantee, trading MM7's refcounting complexity for an explicit version-pruning GC design (§34).

Flat KV decoupled from a logical trie (AA4, §34) wins for execution-layer throughput when root computation can be deferred and batched. The real system is Erigon 3. It is rejected here because it gives up per-transaction root availability (§34, §31).

Deferred features (§35) each wait for a named trigger, for example a Verkle backend waits for a stateless-client need beyond CM6, and parallel hashing waits until M3 dominates production load (§35).

What must never be false

Telemetry names come from the §7 table.

  • I1: the root is a pure function of the (key, value) set, independent of insertion order. Noticed by a differential test against geth; root_mismatch_total.
  • I2: a node is embedded iff its canonical RLP is under 32 bytes. Noticed by a boundary-size differential test; embedding_boundary_total.
  • I3: the hex-prefix flag nibble encodes kind and parity correctly. Noticed by the compact_even.json and compact_odd.json fixtures; no telemetry.
  • I4: after GC, every stored node is reachable from some live snapshot root. Noticed by a reachability audit fuzz test; gc_unreachable_total.
  • I5 and I6: journal entries are append-only and strictly monotonic, and restoring a snapshot yields the recorded root. Noticed by a sequence-number gap check (journal_gap_total) and snapshot_restore.json (snapshot_root_mismatch_total).
  • I7: a branch never persists with fewer than 2 live children-or-value slots. Noticed by randomized mutation fuzzing; branch_underflow_total.
  • I8: re-hashing a proof's nodes bottom-up reproduces the claimed root. Noticed by verifier unit tests; proof_verify_fail_total.
  • I9: in secure mode the path is always keccak256(raw_key). Noticed by a property test of raw versus secure depth; no telemetry (structural).
  • I10 and I11: RLP decode rejects non-minimal length prefixes, and traversal depth is at most 64 nibbles. Noticed by malformed_rlp.json (rlp_decode_reject_total) and a depth-counter assertion (traversal_depth_max).
  • I12 and I13: replaying a WAL segment twice yields identical state, and reference counts are conserved across insert/delete pairs. Noticed by a double-replay test (wal_replay_fail_total) and a refcount audit fuzz test (gc_dangling_ref_total).
  • I14: a cache entry is invalidated on any mutation touching its hash. Noticed by a cache-versus-storage consistency test; cache_stale_hit_total.
  • I15: an exclusion proof includes a concrete boundary node. Noticed because the verifier requires a terminating mismatch; exclusion_proof_incomplete_total.

What breaks in production

FM-1, root divergence. The computed root differs from the oracle's. Causes are non-canonical serialization, a hashing bug or an embedding-boundary bug. Detection is a differential test failure (ADR-21). There is no automatic recovery and the commit halts. Manual recovery is a replay from the last known-good snapshot and a bisect using the ADR-21 fixtures (§23).

FM-3, storage corruption. A checksum mismatch on read, from a disk fault, an unclean shutdown or a compaction bug. Detection is the read-path checksum. WAL replay (I12) is the automatic recovery, and restoring the last durable snapshot is the manual one (§23, T4).

FM-5, orphan node leak. Storage grows without bound relative to the reachable set, from a GC refcount bug or a missed pass. A periodic reachability audit detects it, a scheduled GC pass is the automatic fix, and a forced full mark-and-sweep is the manual one (§23).

FM-8, crash during commit. A partial write is visible after restart because the process died between the WAL append and the data write. A startup WAL-versus-data consistency check detects it, and automatic WAL replay (I12) recovers it (§23).

FM-10, optimization-induced divergence. The root was right before an optimization and is wrong after, because a caching or hashing change altered serialization order. A differential A/B test detects it and the recovery is to revert the optimization flag (§23, P10).

Threats worth knowing (§22):

  • T1, a forged inclusion proof from a malicious peer, is stopped by recomputing the root from the proof nodes only (I8); the proof is rejected and the peer blacklisted (proof_verify_fail_total).
  • T3, stack exhaustion from a crafted deep shared-prefix chain in raw-key mode, is stopped by the secure-trie depth bound (I11, P8). The operation aborts with DepthExceeded.
  • T8, premature collection of a reachable node under concurrent snapshot retirement, is stopped by refcounting gated on all live roots (I13). The recovery is to halt GC and rebuild refcounts.
  • T11, a false absence proof from an incomplete boundary, is stopped by dead-end evidence (I15).

How it compares

  • go-ethereum trie is the origin of the hash scheme this design mirrors exactly (ADR-02, ADR-16, ADR-18). Its newer path-based storage scheme changes disk layout, not the root hash, so this design skips it as an optimisation of layout over authentication semantics (§31).
  • Erigon keeps a logical trie for roots and proofs on top of flat physical KV storage and batches root recomputation. That wins for execution-layer throughput. §31 and AA4 say it breaks the per-transaction root availability that P5 requires, while P5 as written in §6 says proof generation is designed alongside node layout and does not mention per-transaction roots (§31, §34 AA4, §6 P5).
  • reth trie made the same core bet, Rust ownership for the node graph and incremental per-mutation hashing, and adds an async sparse-trie layer for parallel root computation. That layer is a concurrency model this design defers, preferring the single-writer ADR-22 until conformance is established (§31, §35, P10).
  • Diem/Libra Jellyfish Merkle Tree addresses nodes by version plus nibble path, not by content hash, and has no extension nodes. It gives up automatic cross-version subtree dedup and gets a pruning model that avoids refcounting (§31, MM7, AA3).

Questions to test yourself

  1. Why is the embedded-node threshold exactly 32 bytes and not, say, the RocksDB block size? — Hint: the embedding rule in §8 and the ADR-19 row of §9.
  2. How does reference counting behave when two live snapshots retain overlapping but non-identical subtrees — walk the exact accounting. — Hint: §20.2 step 4 and MM7.
  3. Why does the no-extension trie variant diverge in root hash from this design even for an identical key/value set? — Hint: MM2 and AA1 in §34.
  4. What is the minimum information an exclusion proof must carry, and why is "no proof" an unacceptable substitute? — Hint: I15 and §17.2 step 2.
  5. What does "canonical serialization" buy that a merely round-trippable serialization does not? — Hint: P1 in §6 and MM5.

If you only remember three things

A node's identity is the hash of its one canonical encoding, so encoder drift silently changes the root and only a second implementation can catch it (P1, P13, §2). Hashing the key first fixes the path length at 64 nibbles, which turns an attacker's choice of keys into a fixed-depth problem (ADR-16, MM6). A proof is just enough of the tree to recompute the root, a snapshot is a journal marker rather than a copy, and a node may be deleted only when no live snapshot root reaches it (MM4, MM8, P12).

Words used here

  • Nibble: a half-byte, 4-bit path unit (§36).
  • Branch node: a 16-way node with one extra value slot (§36, §8).
  • Extension node: one node standing for a shared run of nibbles with a single child (§36, MM2).
  • Hex-prefix (compact) encoding: a path encoding whose first nibble flags node kind and parity (§36, I3).
  • RLP: Recursive Length Prefix, Ethereum's canonical serialization format (§36, §13).
  • Embedded node: a child inlined in its parent's RLP because its encoding is under 32 bytes (§36, I2).
  • Secure trie: a wrapper that hashes every key to fix the path length (§36, ADR-16).
  • Inclusion and exclusion proof: the node list that shows a key is present or absent (§36, I8, I15).
  • Content addressing: a value's identity is derived from its hash, not its location (§36, P6).
  • Snapshot: an O(1) journal checkpoint marker that enables rollback (§36, MM8).
  • Reference counting: tracking how many live roots reference a stored node (§36, I13).
