184 — Merkle Patricia Trie from Scratch

Project Number: 184

Project Name: Merkle Patricia Trie from Scratch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch, a production-grade Ethereum-style Merkle Patricia Trie (MPT): a radix-16 (hexary) authenticated data structure over hex-prefix (compact) encoded nibble paths, with Keccak-256 structural hashing, RLP canonical serialization, secure-trie (hashed-key) semantics, inclusion/exclusion proof generation and verification, content-addressed persistence, journaled snapshots with rollback, reference-counted pruning, and differential conformance against go-ethereum's trie package. The deliverable is a specification-grade authenticated storage engine suitable as the state backend of a blockchain execution client, a light-client verifier, or a standalone authenticated key/value store.

Phase 0 Deliverable

  1. crates/primitives — nibble utilities, Hash wrapper, node-identifier types.
  2. crates/rlp — canonical RLP encoder/decoder with non-canonical rejection.
  3. crates/trie-core — node model, structural hashing, insert/lookup/delete, root tracking.
  4. crates/secure-trie — keccak256(key) wrapper enforcing bounded path depth.
  5. crates/proofs — inclusion/exclusion proof generation and stateless verification.
  6. crates/storage — NodeStore trait, in-memory backend, RocksDB backend.
  7. crates/journal — write-ahead log, snapshot checkpoints, rollback.
  8. crates/gc — reference counting, mark-and-collect pruning.
  9. crates/conformance — differential-test harness against go-ethereum/reth fixtures.
  10. crates/cli — proof inspection, trie visualization, benchmark tooling.

Only items 1–3 and a minimal crates/cli skeleton ship in Phase 0 itself (§12); items 4–10 are built out across Phases 1–9 (§13–§21) as listed above.

System Boundaries

Provides: node model, structural hashing, RLP codec, secure-trie key hashing, proof generation/verification, pluggable storage, journaling/snapshots, pruning, differential conformance tooling.

Delegates: underlying KV durability to RocksDB; network transport of proofs/nodes to the embedding client; consensus rules (which keys/values belong in the trie) to the caller.

Does NOT provide: a full EVM, a P2P networking layer, a consensus engine, account-model semantics beyond raw key/value storage, or (in-scope) Verkle-tree / KZG-commitment support — see §35.

Non-Goals

Not a general-purpose database; not a smart-contract execution engine; not a wire protocol for state sync (only the proof/node encodings it consumes); not zk-SNARK-friendly (no algebraic-hash or vector-commitment variant in scope).

Deployment Model

Embeddable Rust library (crates/trie-core + crates/secure-trie + crates/storage) linked into a host process (execution client, light client, or standalone service); the crates/cli binary ships separately for inspection/benchmarking and is not a runtime dependency of the library.

Target Users

Blockchain execution-engine authors; authenticated-database researchers; stateless / light-client implementers; storage-engine experimenters; execution-layer infrastructure teams building custom state backends.

Language & Rationale

Rust, chosen for ownership-safe recursive node graphs, memory safety under adversarial (untrusted proof/RLP) input, exhaustive enum modeling of node kinds, and a mature crypto/serialization ecosystem (see ADR-01). Rejected: Go (GC pauses under adversarial recursive traversal load, weaker exhaustiveness checking for the node enum) and C++ (no first-class memory-safety guarantee for a security-sensitive parser surface — the RLP decoder is the single most attacker-exposed component in the system).

Prerequisites

Required: hash functions, radix trees, authenticated data structures, serialization formats, storage-engine internals, systems programming, recursion/graph traversal, property-based testing.

Recommended: prior Ethereum trie familiarity, database internals, cryptographic commitment schemes, persistent storage design.

2. Why Build This

The Merkle Patricia Trie is the authenticated-storage backbone of every Ethereum-family execution client. It fuses four ideas that are individually simple but combinatorially hard to get exactly right: cryptographic content addressing, radix-16 path compression, canonical deterministic serialization, and stateless proof generation. Getting any one of these subtly wrong does not crash the program — it silently diverges the state root, which is only detectable by comparing against another implementation (§21, ADR-21). That failure mode — correct-looking code producing a wrong answer with no local signal — is the single most valuable lesson this project teaches, and it generalizes to any content-addressed or consensus-critical system.

Unique systems knowledge: canonical serialization discipline; structural hashing and content addressing; hex-prefix (compact) path encoding; authenticated proof construction; rollback-safe mutation via journaling; reference-counted garbage collection over a shared, hash-deduplicated node graph.

Cross-links to sibling systems (§31, §34): a blockchain VM consumes this trie as its state backend; a distributed KV store shares its authenticated-replication concerns; a generic database engine shares its persistence/indexing layering (§18–§20); a filesystem shares tree-structure and path-compression concerns (§8); git (content-addressed object store) shares §6 P6 "hashes define identity" almost verbatim; a Verkle-trie project (§34 AA2) shares the authenticated-commitment goal with a different cryptographic primitive; a consensus engine depends on this project's determinism (§7 I1) for cross-node agreement on state roots.

Calibration value: serialization discipline, recursive systems design under adversarial input, cryptographic determinism, storage-correctness engineering, and differential testing as a correctness oracle when no other ground truth exists.

What Mastery Looks Like

  • Can explain, from the Yellow Paper's Appendix D n() function, exactly why a node is embedded vs hash-referenced, and defend the 32-byte threshold (Phase 2, §14).
  • Can hand-derive the hex-prefix flag nibble for any (leaf/extension, odd/even) path without a reference table (Phase 1, §13).
  • Can explain why secure-trie key hashing is a DoS mitigation, not a privacy feature (Phase 4, §16).
  • Can construct a minimal exclusion proof and explain why it must terminate at a concrete "dead-end" node rather than at absence-of-evidence (Phase 5, §17).
  • Can trace a root divergence bug from a differential-test failure back to the exact serialization or hashing line that caused it (Phase 9, §21).
  • Can explain why reference counting is only an approximation of reachability once multiple retained snapshots exist, and where that approximation breaks (Phase 8, §20).
  • Can design a WAL replay procedure that is provably idempotent under repeated crashes (Phase 7, §19).

Secure Trie / Coordinator — owns mutation orchestration and the mandatory keccak256(key) boundary (ADR-16); single-writer, snapshot-isolated readers (ADR-22).

Path Encoder — nibble conversion, hex-prefix compact encoding, odd/even parity flag management (§8, I3).

Hashing Engine — node RLP serialization, embedded-vs-hashed decision at the 32-byte threshold (I2, ADR-19), deterministic Keccak-256 root computation.

Proof Engine — inclusion/exclusion proof capture and stateless verification; treats proofs as a first-class output (P5), not a derived afterthought.

Node Graph — the canonical authenticated structure: branch (17-slot), extension (compressed shared path), leaf (terminal), and the NodeRef embedded-vs-hash duality.

RLP Serialization Layer — consensus-critical canonical codec; rejects any non-minimal length prefix (I10) rather than merely warning.

Journal / Snapshot Layer — append-only WAL, O(1) checkpoint markers (not full data copies, MM8), and crash-safe replay.

Storage Backend — backend-agnostic (P7) content-addressed persistence behind the NodeStore trait; in-memory for tests, RocksDB for production (ADR-05).

Pruning / GC — reference-counted mark-and-collect gated on all live snapshot roots (I4, I13, P12).

6. Design Principles

P1 — Canonical Serialization Only. Rule: equivalent nodes serialize to byte-identical RLP. Tradeoff: forbids "convenience" encoder variance (e.g., optional field omission heuristics). Operational implication: every encoder change requires a differential-test gate (ADR-21). Violation: silent root divergence (FM-1) with no local error.

P2 — Structural Hashing Is Deterministic. Rule: hash(node) is a pure function of the node's canonical RLP. Tradeoff: no hash randomization/salting is possible. Violation: cross-run or cross-machine root mismatch (I1).

P3 — Mutations Are Transactional. Rule: every trie mutation is journaled before it is considered committed (I5). Tradeoff: extra WAL-append latency per mutation. Violation: partial-write states become unrecoverable after a crash (FM-8).

P4 — Embedded-Node Optimization Must Preserve Semantics. Rule: inlining a sub-32-byte node (I2) must not change what a proof verifier accepts. Tradeoff: proof construction must branch on embedded-vs-hashed at every child. Violation: boundary-sized nodes forge or reject proofs incorrectly (T5).

P5 — Proofs Are First-Class Outputs. Rule: proof generation is designed alongside node layout, not bolted on. Tradeoff: node encoding choices are constrained by proof-reconstructability. Violation: proofs that are technically correct but economically unusable (excessive size, MM4).

P6 — Hashes Define Identity. Rule: a node's content hash is its address (ADR-13). Tradeoff: no positional/offset addressing shortcut is available. Violation: identity and integrity drift apart, defeating deduplication (MM1).

P7 — Persistence Is Backend-Agnostic. Rule: trie-core never imports a concrete storage engine (ADR-04). Tradeoff: an extra trait-dispatch indirection on every node fetch. Violation: swapping RocksDB for another backend requires touching trie logic.

P8 — Recursive Traversal Must Be Bounded. Rule: traversal depth is bounded by the fixed secure-trie key length (I11). Tradeoff: raw-key (non-secure) mode cannot make this guarantee. Violation: adversarial key sets exhaust the call stack (T3).

P9 — Serialization Errors Are Fatal. Rule: malformed RLP fails closed, never best-effort-parses (I10). Tradeoff: strictness rejects some inputs a lenient parser would accept. Violation: a lenient decoder becomes an injection surface (T2).

P10 — Optimize Only After Conformance. Rule: no performance change lands without a green differential-test run (ADR-21). Tradeoff: slower iteration on hot-path work. Violation: an optimization silently changes the root (FM-10).

P11 — Secure-Trie Key Hashing Is Mandatory At The Boundary. Rule: every public mutation/lookup API takes a raw key and hashes it internally (ADR-16); there is no raw-path bypass. Tradeoff: loses key-order locality. Violation: adversarial key choice defeats the depth bound (T6).

P12 — Reference Counting Precedes Deletion. Rule: a node is only physically deleted once its reference count, computed against all live snapshot roots, reaches zero (I13). Tradeoff: refcount bookkeeping on every insert/delete. Violation: premature collection of a still-reachable node (T8, FM-5).

P13 — Differential Testing Is The Root-Correctness Oracle. Rule: correctness is defined operationally as "matches geth/reth on the same input" (ADR-21), because no formal spec fully pins down every encoding corner case. Tradeoff: requires maintaining an external fixture corpus. Violation: an internally-consistent but externally-wrong implementation ships undetected (FM-1).

8. Domain Model / Protocol / Data Model

Node Types

Node Shape Semantics
Branch 17-slot list: 16 child NodeRef slots (nibble 0–F) + 1 optional value fan-out point
Extension (compact_path, child NodeRef) compresses a shared nibble run with a single child
Leaf (compact_path, value) terminal key/value pair
Empty zero-length RLP (0x80) canonical empty subtree

Hex-Prefix (Compact) Encoding — Flag Nibble

Node Kind Path Nibble-Length Parity Flag Nibble (high nibble of first byte)
Extension even 0x0
Extension odd 0x1
Leaf even 0x2
Leaf odd 0x3

If the path length is odd, the first data nibble is packed into the low nibble of the flag byte; otherwise a 0x0 padding nibble fills that slot (Yellow Paper Appendix C).

Key Processing Pipeline (secure trie)

raw_key (arbitrary bytes)
   -> keccak256(raw_key)              [ADR-16, I9]
   -> 32-byte hash
   -> nibble expansion (64 nibbles)   [§13 Path Encoder]
   -> trie traversal (branch/ext/leaf) [§15]

Node Embedding Rule (I2, ADR-19)

Condition Storage
len(canonical_rlp(node)) < 32 embed inline as NodeRef::Embedded(bytes)
len(canonical_rlp(node)) >= 32 store keccak256(canonical_rlp(node)), NodeRef::Hash(h)

Worked Example — Insertion Producing an Extension

Insert "dog" -> hash1, then "do" -> hash2 (raw-key mode, illustrative nibbles):

Step Nibble Path Structural Result
1 [6,4,6,f,6,7] ("dog" nibbles, illustrative) single Leaf at root
2 [6,4,6,f] ("do" nibbles, illustrative) shares prefix [6,4,6,f]... shared-prefix Extension created, Branch below it separates the two values

Result: an Extension node covering the shared nibble run, pointing at a Branch node whose value slot holds hash2 ("do") and whose nibble-6 (illustrative) child leads to a Leaf holding hash1 ("dog").

State-Transition Table — insert(root, key, value)

Current Node at Path Key Relationship Transition
Empty — replace with new Leaf
Leaf(p, v) key path == p replace value in place
Leaf(p, v) key path shares prefix with p split into Extension/Branch (as above)
Extension(p, child) key path shares all of p recurse into child with remaining path
Extension(p, child) key path diverges within p split Extension at divergence point
Branch(children, value) path exhausted set/replace value slot
Branch(children, value) path continues recurse into children[nibble]

Malformed-Input Example

Input RLP byte 0xb9 0x00 0x1f ... (long-string prefix claiming length 0x001f = 31, which fits the short-string range < 56) is rejected by I10: a canonical encoder would never emit a long-string prefix for a 31-byte payload, so the decoder treats this as TrieError::NonCanonicalRlp rather than silently accepting a decodable-but-non-minimal encoding.

Failure-Path Example

A node fetched from storage decodes successfully but its recomputed hash does not match the NodeRef::Hash that pointed to it (storage bit-rot, T4). The Hashing Engine (§14) raises TrieError::HashMismatch; the caller must treat the subtree as untrusted and trigger WAL/snapshot recovery (§19) rather than proceeding with a possibly-corrupted value.

Inclusion Proof Structure

Proof.nodes = [ encoded_node_root, encoded_node_1, ..., encoded_node_leaf ]

Verification (I8) recomputes the root by hashing encoded_node_leaf up through each parent's NodeRef slot to encoded_node_root, and compares against the claimed root.

  • Hashing the key twice (once at the API boundary, once inside a lower layer that assumes raw keys) — produces a different but internally-consistent wrong root.

  • Fixture inclusion.json: 1,000 random keys, all proofs verify true against the live root.
  • Fixture exclusion.json: 1,000 random absent keys, all proofs verify true (correctly proving absence) and include a concrete boundary node (I15).
  • Fixture malformed_proof.json: ≥ 10 corrupted proofs (byte-flip, node-drop, node-reorder) all rejected.
  • Proof generation p99 ≤ 50 µs at 1M-key trie scale (M5); verification p99 ≤ 20 µs (M6).
  • Cross-implementation check: 100 geth-generated proofs verify true under this project's verifier, and 100 locally-generated proofs verify true under a geth-based checker (groundwork for ADR-21, finalized in §21).

17.5 Conformance Fixtures

Fixture Assertion
inclusion.json valid inclusion proof for a present key
exclusion.json valid exclusion proof for an absent key, with boundary node (I15)
malformed_proof.json corrupted proofs rejected

17.6 Pitfalls

  • Omitting an intermediate node the verifier needs to re-hash up to the root (I8 violation) — proof looks plausible but fails to verify.
  • Mishandling an embedded child during proof capture — including it as a standalone proof entry when it should be inline in its parent's RLP (P4 violation).
  • Exclusion proofs that stop one level too early, failing to prove the actual divergence (I15 violation, MM4).

17.7 Performance Concerns

  • Proof size grows with trie depth (average ~8 nodes at 5×10^8-key scale per §32 CM6) — unavoidable given the Merkle structure, only mitigated by witness compression (deferred, §35).
  • Serialization duplication when a proof includes the same embedded node reachable from two different capture points — dedup in the export step (§17.2 step 6).

17.8 Edge Cases

  • Proof against an empty trie (root is the canonical empty-root constant, §14.8) — every key is provably absent with a trivial one-node "proof".
  • Proof requested for a key that was present, then deleted — must correctly produce an exclusion proof against the current root, not a stale cached inclusion proof.

17.9 Failure Analysis

An unverifiable witness that a peer claims is valid (T1) is either a malicious peer (reject + blacklist, T1 mitigation) or a local generation bug (re-run inclusion.json/exclusion.json fixtures to isolate). Root mismatch during verification is diagnosed via the depth-of-first-divergence diagnostic (§17.2 step 7).

17.10 Operational Notes

proof_verify_fail_total (I8 telemetry) partitioned by inclusion-vs-exclusion in dashboards (§24); a sustained nonzero rate on exclusion proofs specifically often indicates an I15 boundary-node regression rather than a peer attack.

18. Phase 6 — Storage Backend & Content-Addressed Persistence

18.1 Objectives

Implement the NodeStore trait, the in-memory backend, the RocksDB backend, and the decoded-node cache — all behind a backend-agnostic interface (P7).

18.2 Detailed Implementation Steps

  1. Implement NodeStore trait (§11, ADR-04) with get/put/delete keyed by Hash (content addressing, ADR-13, P6).
  2. Implement the in-memory backend (HashMap<Hash, Vec<u8>>) for tests and Phase 0–5 fixtures.
  3. Integrate RocksDB (ADR-05) as the production backend, keyed identically by Hash.
  4. Implement content-addressed persistence: writes are idempotent (same key ⇒ same value, natural dedup, MM1).
  5. Implement the LRU decoded-node cache (ADR-23) sitting in front of NodeStore::get.
  6. Wire cache invalidation on every mutating write (I14) — no stale-read path.
  7. Add persistence benchmarks targeting M7 (batched insert throughput).
  8. Add a cache-vs-storage consistency property test (feeds I14 detection).
  9. Add RocksDB column-family layout: one CF for nodes, one reserved for §19's journal metadata (kept logically separate from node data).
  10. Add storage-level checksum validation on read (T4 mitigation groundwork; full WAL recovery lands in §19).
  11. Add docs/adr/ADR-04.md, ADR-05.md, ADR-13.md, ADR-23.md write-ups.

18.3 Deliverable

crates/storage provides a backend-agnostic, content-addressed persistence layer with an in-memory backend for tests and a RocksDB backend for production, fronted by an LRU cache.

18.4 Acceptance Criteria

  • RocksDB-backed batched insert throughput ≥ 150,000 inserts/sec at batch size 10,000 (M7).
  • Zero stale reads across 100,000 randomized mutation-then-read cycles (I14).
  • Switching NodeStore implementation (in-memory ⇄ RocksDB) requires zero changes to crates/trie-core (P7, compile-time enforced by the trait boundary).

18.5 Conformance Fixtures

Fixture Assertion
storage_dedup.json identical subtrees inserted twice occupy one physical record
cache_consistency.json no stale cache hit across 100,000 mutation cycles (I14)

18.6 Pitfalls

  • Checksum validation added only on the RocksDB path, missed on the in-memory path (inconsistent guarantees between backends).
  • Cache invalidation keyed by the wrong hash (e.g., invalidating the old hash instead of both old and new hash on an update).
  • Column-family confusion between node data and journal metadata (§19) causing compaction to reclaim live journal records.

18.7 Performance Concerns

  • Write amplification inherent to RocksDB's LSM compaction — monitored, not eliminated, via compaction stalls telemetry (§28).
  • Cache locality: a cold cache after restart temporarily degrades lookup latency below the M2 target until the hot set is repopulated.

18.8 Edge Cases

  • Storing a node whose RLP happens to be exactly 32 bytes (boundary with I2's embedding rule — must still be stored by hash, not embedded, since the rule is strict <).
  • RocksDB backend under a nearly-full disk — put must surface TrieError::StorageCorrupt or an explicit I/O error, never silently drop a write.

18.9 Failure Analysis

A cache-vs-storage divergence (FM-6) is diagnosed by replaying the mutation trace against a fresh (cold) cache and diffing results. A RocksDB read returning corrupted bytes (T4) is caught by the checksum check and routed to §19's WAL-recovery path.

18.10 Operational Notes

Dashboards (§24) should track cache hit-rate, RocksDB compaction-stall duration, and cache_stale_hit_total (I14) together — a cache-hit-rate drop concurrent with a compaction stall is expected and not itself an incident.

19. Phase 7 — Journaling, Snapshots, Rollback & Crash Recovery

19.1 Objectives

Implement the write-ahead log, O(1) checkpoint snapshots, transactional rollback, and crash-safe WAL replay (P3, ADR-12).

19.2 Detailed Implementation Steps

  1. Implement JournalEntry/WalRecord (§11) with strictly monotonic sequence numbers (I5).
  2. Implement WAL append with fsync-before-ack (T7 mitigation).
  3. Implement Snapshot creation as an O(1) journal-checkpoint marker, not a data copy (ADR-12, MM8).
  4. Implement rollback: replaying the journal backward to a checkpoint's sequence number, restoring the recorded root (I6).
  5. Implement crash-recovery WAL replay on startup: detect the last fsynced record, replay forward, validate the resulting root against the last-known-good checkpoint.
  6. Prove replay idempotence (I12): replaying the same WAL segment twice yields identical state — required because a crash mid-replay must be safe to retry.
  7. Add WAL record CRC32 validation (WalRecord.crc32) to detect torn writes (FM-4).
  8. Add snapshot-restore fixture comparing restored root to the recorded snapshot root (I6).
  9. Add crash-injection test harness: kill the process at N different points during a commit sequence, restart, verify recovery.
  10. Add persistence-latency benchmarks targeting M8 (checkpoint) and M9 (WAL replay throughput).
  11. Document the recovery flow (replay WAL → validate roots → hand off to §20 for pruning) in docs/runbooks/crash-recovery.md.

19.3 Deliverable

crates/journal provides append-only WAL logging, O(1) snapshot checkpoints, lossless rollback, and idempotent crash recovery.

19.4 Acceptance Criteria

  • Fixture snapshot_restore.json: 500 checkpoint/restore cycles all reproduce the exact recorded root (I6).
  • Fixture wal_recovery.json: crash-injected at 50 distinct commit-sequence points, all recover to a valid, root-consistent state within the ≤ 5 s RTO (§4).
  • WAL replay throughput ≥ 200,000 records/sec (M9); snapshot creation latency ≤ 2 ms (M8).
  • Double-replay of any WAL segment yields byte-identical resulting state (I12).

19.5 Conformance Fixtures

Fixture Assertion
snapshot_restore.json rollback reproduces recorded root (I6)
persistence_root.json root survives a restart with no journal activity
wal_recovery.json crash-injected recovery within RTO (FM-8)

19.6 Pitfalls

  • WAL ordering corruption: appending a record before the previous record's fsync completes, breaking I5's monotonicity guarantee under crash.
  • Stale references: a snapshot recorded before a GC pass (§20) may reference nodes the GC has since collected if refcounting doesn't account for open snapshots (T8 cross-reference).
  • Treating "journal write succeeded" as "commit succeeded" without also confirming the data write landed (races with §18's storage layer).

19.7 Performance Concerns

  • Write amplification: every mutation now costs a WAL append and a storage write; batching multiple mutations into one WAL append is a valid optimization once conformance (P10) is established.
  • Compaction stalls on the RocksDB-backed journal CF can transiently blow the M8/M9 latency budgets.

19.8 Edge Cases

  • Interrupted commit: crash occurs after WAL append but before the storage write lands — recovery must detect this via CRC-valid-but-data-missing and replay the storage write from the journal entry.
  • Huge snapshot count (thousands of retained checkpoints) — journal-checkpoint lookup must stay O(log n) or better, not degrade to O(n) scans.

19.9 Failure Analysis

Recovery flow on crash: (1) locate the last CRC-valid WAL record, (2) replay forward from the last checkpoint, (3) validate the resulting root against any independently recorded root (if available), (4) hand off to §20 for a post-recovery pruning pass. Each step maps to FM-4 (WAL corruption) or FM-8 (crash during commit) in §23.

19.10 Operational Notes

wal_replay_fail_total and RTO-vs-actual-recovery-time should both be tracked per incident in docs/runbooks/crash-recovery.md (§24); any recovery exceeding the 5 s RTO budget is itself an incident even if the final state is correct.

20. Phase 8 — Pruning, Garbage Collection & Reference Counting

20.1 Objectives

Implement reference-counted pruning that reclaims unreachable nodes without collecting anything still reachable from a live snapshot root (P12, I4, I13).

20.2 Detailed Implementation Steps

  1. Implement RefCountEntry (§11) tracking a Hash -> count mapping alongside storage.
  2. Increment reference counts on node insertion/reuse (content-addressed dedup means a shared subtree's count increments rather than duplicating storage, ADR-13).
  3. Decrement reference counts on node replacement/deletion during ordinary mutation (§15/§16).
  4. Gate physical deletion on all live snapshot roots (§19's open Snapshot set), not just the current root (I13, MM7) — this is the crux of correct pruning under multiple retained snapshots.
  5. Implement the mark-and-collect pass: mark nodes reachable from any live root, collect the complement (ADR-20).
  6. Add a periodic reachability audit (independent of refcounting) that walks from all live roots and flags any refcount/reachability mismatch (I4 detection).
  7. Add GC-pause benchmarking targeting M10 (≤ 500 ms per 1M retired nodes).
  8. Add fuzz test: concurrent snapshot retirement + GC pass must never collect a node still reachable from a surviving snapshot (T8).
  9. Wire GC scheduling to the WAL/journal (§19) so a GC pass is itself journaled and crash-safe.
  10. Document the refcount-vs-reachability distinction (MM7) in docs/adr/ADR-20.md.

20.3 Deliverable

crates/gc reclaims physically unreachable nodes via reference counting gated on all live snapshots, with an independent reachability audit as a correctness backstop.

20.4 Acceptance Criteria

  • Fuzz suite: 10,000 randomized insert/delete/snapshot/GC interleavings produce zero I4 violations (no node collected while still reachable from a live root).
  • GC pass duration ≤ 500 ms per 1M retired nodes (M10).
  • Reference-count conservation (I13): for any no-op mutation sequence (equal inserts and deletes of the same keys), refcounts return to their pre-sequence values exactly.

20.5 Conformance Fixtures

Fixture Assertion
gc_reachability.json post-GC storage contains exactly the reachable node set (I4)
refcount_conservation.json refcounts return to baseline after no-op mutation cycles (I13)

20.6 Pitfalls

  • Reference-counting bug under concurrent snapshot retirement (T8) — the single most dangerous pitfall in this phase, since it manifests as silent data loss, not a crash.
  • Forgetting that content addressing means two logically distinct insert calls for identical data share one physical node and one refcount, not two.
  • Running GC without journaling it (§20.2 step 9 omitted), making a GC pass unrecoverable if the process crashes mid-collection.

20.7 Performance Concerns

  • Mark-and-collect pass cost scales with the retired delta, not total DB size (ADR-20) — verify this holds under benchmarking, not just by design intent.
  • Reachability-audit cost (full walk from all live roots) is intentionally more expensive than the incremental refcount path and should run on a slower cadence (§24 runbook).

20.8 Edge Cases

  • A node referenced by exactly one live snapshot that is then retired concurrently with a new mutation that re-creates an identical node (content-addressed collision with a to-be-collected hash) — refcounting must handle the race without a time-of-check/time-of-use gap.
  • Zero live snapshots (only the current root) — GC degenerates to simple reachable-from-root collection.

20.9 Failure Analysis

A dangling-reference finding (FM-5) is root-caused via the reachability audit's diff against the refcount table; a positive diff (refcount says live, audit says unreachable) indicates a missed decrement; a negative diff (audit says live, refcount says zero — collected while reachable) is the critical I4 violation and must halt GC system-wide pending a fix (§20.6).

20.10 Operational Notes

gc_dangling_ref_total and gc_unreachable_total (I13, I4 telemetry) should both be zero in steady state; schedule the independent reachability audit (§20.2 step 6) on a cadence documented in docs/runbooks/gc-audit.md, distinct from the incremental refcount path's continuous operation.

21.6 Pitfalls

  • Optimization-induced divergence (FM-10): the single most likely failure in this phase — any change that alters serialization order, cache key derivation, or traversal order without a full differential re-run.
  • Stale cache roots: a node-hash cache (§21.2 step 8) that fails to invalidate on a content change reintroduces I14-class bugs at the optimization layer.
  • Nondeterministic iteration order (e.g., iterating a HashMap instead of a sorted structure) silently reintroducing I1 violations that P2's design was meant to prevent.

21.7 Performance Concerns

  • Hashing remains the top bottleneck per §29's ordered bottleneck list; disk I/O amplification (§18.7) is second; cache invalidation overhead (I14) is third.

21.8 Edge Cases

  • Million-key tries (near the §4 target scale) — validate M1/M2/M5 latency targets do not degrade superlinearly at this scale.
  • Deeply shared prefixes (adversarially constructed, but now bounded by secure-trie depth per §16) — confirm optimization changes don't reintroduce a depth-dependent slowdown disproportionate to §32's CM1 average-depth model.

21.9 Failure Analysis

Optimization validation procedure on any suspected regression: (1) replay the full fixture corpus, (2) compare roots against both oracles, (3) compare proof outputs, (4) compare serialized node bytes directly (not just hashes, to catch a canonical-but-different-bytes bug that happens to hash-collide-free but still represents non-canonical drift). Any mismatch at step 4 is itself a P1 violation even if steps 1–3 pass.

21.10 Operational Notes

The differential harness (crates/conformance) should run on every PR touching crates/trie-core, crates/rlp, crates/proofs, or crates/gc (§27 CI topology); docs/adr/performance-baseline.md is the canonical reference for detecting future perf regressions in production telemetry (§24, §28).

25. Compatibility & Versioning

Wire compatibility (proofs). The Proof RLP-node-list format (ADR-15) is Ethereum-standard and version-independent; a proof generated by any conformant version verifies under any conformant verifier.

Storage schema evolution. WalRecord and Snapshot carry an explicit schema version field (extends §11's types); a version bump requires a documented migration path (FM-11) before old snapshots can load under a new binary.

API stability. crates/secure-trie's public API (raw-key insert/lookup/delete, root()) is the only supported public surface (P11); crates/trie-core's raw-path APIs are pub(crate)-only and carry no external stability guarantee.

SemVer policy. MAJOR: root-hash-affecting change (any change touching §13/§14 encoding); MINOR: additive API, new storage backend; PATCH: bug fix with no encoding or root-hash impact.

Deprecation. A deprecated API surface is retained for one MAJOR version cycle with a #[deprecated] attribute before removal.

Rolling-upgrade guarantees. WAL format changes (§19) must be additive (old-format records remain replayable) for at least one MINOR version before a breaking WAL format change is allowed, to support rolling upgrades without a full stop-the-world migration.

26. Testing & Verification Strategy

Unit tests. Per-module, covering the §12–§21 phase deliverables directly.

Integration tests. Cross-crate flows: insert → snapshot → crash-inject → recover → verify root (chains §15/§19).

Property-based tests (proptest, ADR-07). Round-trip identities (§13), order- independent roots (I1, §15), refcount conservation (I13, §20).

Differential testing (ADR-21). The primary correctness oracle (P13) — every phase's fixtures feed into the §21 harness; this is not optional supplementary testing, it is the definition of "correct" for this project.

Fuzzing (cargo-fuzz, ADR-06). Targets: RLP decoder (§13), proof verifier (§17), GC/refcount interleaving (§20). 24-hour sustained campaign gates every release (§21.4).

Chaos / crash-injection. WAL-recovery crash-injection harness (§19.2 step 9) run at 50+ distinct commit-sequence points per release.

Deterministic replay. Every fixture in conformance/ is a deterministic replay input — no wall-clock or RNG dependency in the trie logic itself (only the test generators use RNG, seeded and logged).

Soak testing. Sustained multi-hour insert/delete/GC cycling to catch slow memory or refcount leaks not visible in short fuzz runs.

Conformance. Full Ethereum execution-spec state-test corpus (§21.2 step 1) is the release-blocking conformance gate.

Performance-regression gating. Every M1–M12 target (§28) is checked in CI on every release candidate; any regression beyond a documented tolerance blocks release (§21.7).

Traceability to invariants. Every I1–I15 has at least one property test or fuzz target named in its §7 "Detection" column; every phase's N.5 fixtures are the executable form of that traceability.

29. Scalability Analysis

What stays constant. Per-operation traversal depth is O(1) relative to key count once secure-trie mode is enforced (fixed at 64 nibbles, §16) — this is the single most important scalability property of the design.

What grows. Total node count grows O(N) with key count N; proof size grows O(log₁₆ N) on average (§32 CM1/CM6); RocksDB compaction cost grows with total data volume, not directly with N.

Named bottlenecks, in order. 1. Structural hashing (Keccak-256 calls scale with mutated-path length × mutation rate) — §14/§21. 2. Disk seeks / RocksDB compaction (§18.7) under high write churn. 3. Node (de)serialization allocations (§13.7). 4. Decoded-node cache misses under a cold or oversized working set relative to the §4 4 GiB ceiling (§32 CM5).

Horizontal scaling. 16-way sharding by top-level nibble (§4, §32 CM9); cross-shard proofs require a coordinator that composes per-shard sub-proofs — no such coordinator is in scope (§33 Q14, §35).

Vertical scaling. Benefits strongly from SSD throughput (RocksDB write path), memory bandwidth (hashing + cache), and larger caches (directly raises the §4 4 GiB ceiling and the §32 CM5 cache-residency ratio).

Practical ceiling and levers beyond it. At ~5×10^8 keys (§4 target), fixed per-node overhead alone approaches the practical RAM ceiling for full in-memory caching (§32 CM5); levers beyond that point are sharding (above), archive-mode snapshot offloading (deferred, §35), and the Verkle-tree alternative architecture (§34 AA2) which trades hash-tree depth for vector-commitment proof size — out of scope here but the documented escape hatch.

30. Mental Models & First Principles

MM1 — Content addressing collapses identity and integrity into one pointer. Predicts: identical subtrees automatically deduplicate. Bug class without it: separate "ID" and "checksum" fields that silently drift apart. Resolves §11, §18 (ADR-13, P6).

MM2 — Path compression is an optimization on top of a branch-only trie, not a structural requirement. Predicts: an extension-free variant is semantically equivalent but produces a different root and is slower per lookup. Bug class without it: assuming extension nodes are required for correctness, causing incorrect proof comparison against no-extension implementations. Resolves §8, §34 (AA1, ADR-18).

MM3 — Hex-prefix encoding is a length-and-kind tag riding on the path bytes, not a separate structure. Predicts: any nibble-parity bug manifests as a one-nibble path corruption, not a crash. Resolves §8, §13 (I3).

MM4 — A Merkle proof is exactly "enough of the tree to recompute the root," nothing more. Predicts: proof size is O(depth), never O(tree size). Bug class without it: proofs that bloat with unnecessary sibling data or omit a required intermediate node. Resolves §17 (I8), §32 (CM6).

MM5 — Determinism is a whole-pipeline property, not a hashing-function property alone. Predicts: a non-canonical encoder produces divergent roots even with a provably correct hash function. Resolves §13 (P1), §21 (ADR-21).

MM6 — Secure-trie hashing turns an adversarial key-choice problem into a fixed-depth problem. Predicts: raw-key tries are depth-DoS-able via chosen-prefix keys; secure tries are not, because the path length is fixed by the hash digest size regardless of attacker intent. Resolves §16 (ADR-16, I11).

MM7 — Reference counting is a conservative approximation of reachability, exact only for tree-shaped sharing without cross-snapshot awareness. Predicts: naive per-node refcounting that ignores open snapshots under- or over-collects at snapshot boundaries. Resolves §20 (I13, T8, FM-5).

MM8 — A snapshot is a checkpoint in the journal, not a copy of the data. Predicts: snapshot-creation cost is O(1) (a journal marker), never O(state size). Resolves §19 (ADR-12, M8).

32. Back-of-Envelope Capacity Model

CM1 — Average trie depth. depth ≈ log₁₆(N) for N keys, branching factor 16 (secure trie, uniform hash distribution). For N = 5×10^8 (§4 target): ln(5×10^8) / ln(16) ≈ 20.03 / 2.77 ≈ 7.2 → ≈ 8 hops average.

CM2 — Worst-case depth. Fixed at 64 nibbles (32-byte keccak256 key length, §16, I11) — independent of N by construction (MM6).

CM3 — Branch-node RLP size upper bound. A 17-item list: 16 child refs (each ≤ 1 length-prefix byte + 32-byte hash = 33 bytes) + 1 value-slot placeholder + list-header overhead: 16 × 33 + ~3 ≈ 531 bytes.

CM4 — Rehash cost per insert (average case). At M3's 3,000,000 hashes/sec/core (≈ 333 ns/hash) chained to CM1's 8-hop average depth: 8 × 333 ns ≈ 2.7 µs — within M1's p99 budget of 8 µs, leaving margin for allocation and traversal overhead.

CM5 — Cache-residency ratio. 5×10^8 nodes × M12's 96 B fixed overhead/node ≈ 48 GB minimum working-set size, ignoring payload — versus the §4 4 GiB resident cache ceiling. Ratio: 4 / 48 ≈ 8.3% of nodes can be cache-resident at once, so working-set locality (ADR-23's LRU choice) is not an optimization, it is load-bearing.

CM6 — Average inclusion-proof size. CM1's 8-hop average depth × an average blended node size (~200 B across branch/extension/leaf) ≈ 1.6 KB per proof.

CM7 — Initial bulk-load time. At M7's 150,000 inserts/sec (batched RocksDB): 5×10^8 / 1.5×10^5 ≈ 3,333 s ≈ 56 minutes for a single-threaded batch loader to reach full target scale.

CM8 — Maximum recoverable WAL backlog within RTO. M9's 200,000 records/sec × §4's 5 s RTO = 1,000,000 records — the checkpoint interval (§19) must trigger before the unreplayed backlog exceeds this, or crash recovery will exceed its RTO budget.

CM9 — Per-shard scale under 16-way sharding. 5×10^8 / 16 ≈ 31.25×10^6 keys per shard; re-applying CM1's formula: log₁₆(31.25×10^6) ≈ ln(3.125×10^7)/ln(16) ≈ 17.26/2.77 ≈ 6.2 → ≈ 6 hops average within a shard.

CM10 — GC cadence requirement. M10's 500 ms per 1M retired nodes ⇒ throughput 2,000,000 nodes/sec/pass. At a sustained mutation churn of 50,000 mutations/sec, a 1M-node retired backlog accumulates in 1×10^6 / 5×10^4 = 20 s; GC must therefore run at least once per 20 s to keep the backlog bounded under this churn assumption.

33. Hard Questions (Self-Examination)

  1. Why is the embedded-node threshold exactly 32 bytes and not, say, the RocksDB block size? (§8, §9 ADR-19)
  2. What breaks first if secure-trie key hashing is made optional per-call rather than mandatory at the API boundary? (§16, §22 T6)
  3. How does reference counting behave when two live snapshots retain overlapping but non-identical subtrees — walk the exact accounting. (§20, §30 MM7)
  4. Why can proof size be O(depth) rather than O(tree size), and what hash-function property makes that true? (§17, §30 MM4)
  5. If Keccak-256 collision resistance were broken, which invariant fails first, and how would you detect it in production before an attacker exploits it? (§7 I1, §22)
  6. Why does the no-extension trie variant diverge in root hash from this design even for an identical key/value set? (§8, §31)
  7. What is the exact failure mode if WAL fsync is disabled for a throughput gain — trace it through crash recovery step by step. (§19, §23 FM-8)
  8. Why is single-writer concurrency chosen over per-node locking, and at what write-parallelism demand does that choice start to hurt? (§9 ADR-22, §29)
  9. How would you prove, without running a full differential-test pass, that a hashing-engine optimization preserved root equivalence? (§21, §26)
  10. Why must RLP decoding reject non-canonical length prefixes rather than merely warn about them? (§7 I10, §22 T2)
  11. What is the minimum information an exclusion proof must carry, and why is "no proof" an unacceptable substitute? (§7 I15, §17)
  12. Trace the exact node-replacement sequence when a deletion collapses a branch into an extension into a leaf — where can this go wrong? (§15, §23 FM-7)
  13. Why does the Jellyfish Merkle Tree's version-based node key avoid the reference-counting problem this design faces, and what does it give up in exchange? (§31, §34)
  14. If this trie were sharded by top-level nibble across 16 machines, what cross-shard operation becomes impossible without a coordinator? (§29, §32 CM9)

34. Alternative Architectures (Roads Not Taken)

AA1 — No-Extension (Branch + Leaf only) Trie.

   [Branch]------[Branch]------[Leaf]
      |16-way        |16-way
   (one hop per nibble, no compression)

Regime where it wins: schema simplicity favored over cross-client interop; substrate chains that define their own state-root semantics from scratch. Real system: paritytech/trie-db no-extension layout (used by Substrate). Why rejected here: breaks byte-for-byte geth/reth root compatibility, violating ADR-18/ADR-21's differential-oracle requirement.

AA2 — Vector-Commitment (Verkle) Tree.

   [Vector-commitment node, wide fanout]
        |        |        |   ...
   [child]   [child]   [child]   (proof = one commitment opening, not a hash chain)

Regime where it wins: proof-size-critical stateless clients (bandwidth-constrained light clients, statelessness roadmaps). Real system: go-verkle (prototype/testnet Verkle implementation). Why rejected here: requires an elliptic-curve commitment library and different proof math entirely — out of scope for a from-scratch hash-based MPT project; registered as PhaseDeferred("§35").

AA3 — Version-Keyed Authenticated Tree (Jellyfish Merkle Tree model).

   node_key = (version, nibble_path)   [not content-hash keyed]
   -> avoids refcounting, but loses cross-version subtree dedup

Regime where it wins: systems needing versioned historical queries without content-addressed dedup complexity. Real system: Diem/Libra jellyfish-merkle. Why rejected here: loses this project's ADR-13 content-addressed dedup guarantee, trading MM7's refcounting complexity for an explicit version-pruning GC design — a fundamentally different tradeoff than P12/I13 assume.

AA4 — Sharded/Flat-KV State Decoupled from a Logical Trie.

   [Logical Trie view]  <-- periodic batch sync -->  [Flat KV domain, physical]
     (root computed                                    (fast read/write,
      only at sync points)                              no per-tx root)

Regime where it wins: execution-layer throughput where root computation can be deferred/batched rather than done per transaction. Real system: Erigon 3 flat storage. Why rejected here: breaks per-transaction root availability required by P5's "proofs are first-class outputs" principle.
