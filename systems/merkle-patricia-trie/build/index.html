⬜ Phase 0 — Workspace Bootstrap & Primitives §12

Objectives

Stand up the Cargo workspace, CI skeleton, and the correctness kernel: nibble utilities, the Hash wrapper, and the NodeRef type — nothing that depends on RLP or hashing yet.

Deliverable

Compilable workspace with crates/primitives (nibble utilities, Hash, NodeRef skeleton), CI green, no trie logic yet.

Acceptance
  • cargo test -p primitives passes with ≥ 20 property-test cases per nibble round-trip check (proptest default cases = 256 is acceptable; floor is 20).
  • CI pipeline completes in ≤ 5 minutes on GitHub Actions (ADR-10).
  • Zero clippy::all warnings on crates/primitives.
Fixtures
Fixture Assertion
nibble_roundtrip.json byte→nibble→byte identity for 256 random byte strings
hash_wrapper_eq.json Hash equality/ordering matches raw [u8;32] comparison
Pitfalls
  • Off-by-one nibble expansion for odd-length byte inputs.
  • Forgetting unsafe_code = "forbid" before FFI crates (RocksDB, §18) are added, leaving the lint gate ineffective later.
  • Treating Hash as Copy without also deriving Eq/Hash, breaking later HashMap<Hash, _> caches (§18).

⬜ Phase 1 — RLP Serialization & Hex-Prefix Encoding §13

Objectives

Implement the canonical RLP encoder/decoder (crates/rlp) and the hex-prefix (compact) path codec (crates/primitives), including strict non-canonical rejection.

Deliverable

crates/rlp encodes/decodes canonically with non-canonical rejection; crates/primitives encodes/decodes hex-prefix paths correctly for all four (kind, parity) combinations.

Acceptance
  • 100% of conformance/ethereum/rlp/*.json vectors round-trip exactly.
  • Fixture malformed_rlp.json (≥ 12 crafted non-canonical inputs) all rejected with TrieError::NonCanonicalRlp.
  • RLP encode/decode throughput ≥ 5,000,000 ops/sec/core for a leaf-sized payload (M4).
Fixtures
Fixture Assertion
compact_even.json even-length nibble path encodes with flag 0x0/0x2
compact_odd.json odd-length nibble path encodes with flag 0x1/0x3
rlp_leaf.json leaf-node RLP matches geth-derived expected bytes
malformed_rlp.json ≥ 12 non-canonical inputs all rejected (I10)
Pitfalls
  • Nibble-parity flag confusion (swapping the even/odd bit) — silently corrupts every odd-length key's last nibble.
  • Accepting a long-form length prefix for a payload that fits the short form (violates I10).
  • Recursive decoder overflow on deeply nested list inputs without the Phase 0 depth guard wired in.

⬜ Phase 2 — Node Model & Structural Hashing §14

Objectives

Implement the TrieNode enum, the embedded-vs-hashed NodeRef decision, and deterministic Keccak-256 structural hashing.

Deliverable

crates/trie-core::node and ::hashing produce Ethereum-compatible node RLP and Keccak-256 root hashes for hand-built node trees, verified against geth-derived fixtures.

Acceptance
  • Node-hash output matches go-ethereum trie/hasher.go on ≥ 50 hand-picked branch/extension/leaf fixtures, byte-for-byte.
  • Hash throughput ≥ 3,000,000 hashes/sec/core for a 531-byte branch-node payload (M3).
  • Boundary test suite covers node sizes 30, 31, 32, 33, 34 bytes with zero misclassification (I2).
Fixtures
Fixture Assertion
hash_branch.json branch-node hash matches geth reference
hash_extension.json extension-node hash matches geth reference
hash_leaf.json leaf-node hash matches geth reference
embedding_boundary.json 30–34 byte nodes classified correctly (I2)
Pitfalls
  • Using a standards-track SHA3-256 crate instead of original Keccak-256 padding (ADR-02) — produces plausible-looking but wrong hashes.
  • Misapplying the embedding rule to the value size instead of the encoded node size.
  • Re-encoding an already-embedded child before hashing its parent (double-encoding bug).

⬜ Phase 3 — Core Trie Operations §15

Objectives

Implement insert, lookup, delete, and the associated node splitting/collapsing logic against the raw-key (pre-secure-trie) node graph.

Deliverable

crates/trie-core supports insert/update/delete/lookup with deterministic, incrementally recomputed roots (Cooper & Torczon Ch. 4 tree-rewriting parallels, §5).

Acceptance
  • Fixture root_consistency.json: 10,000 random insert/delete sequences all match a reference BTreeMap replay's final key/value set and produce a stable root under re-insertion in different orders (I1).
  • Insert p50 ≤ 1 µs, p99 ≤ 8 µs on the in-memory backend (M1).
  • Lookup p50 ≤ 500 ns, p99 ≤ 4 µs on the in-memory backend (M2).
  • Zero I7 violations (branch_underflow_total stays 0) across the fuzz corpus.
Fixtures
Fixture Assertion
insert_simple.json basic single-key insertion
split_extension.json shared-prefix split produces correct extension/branch
delete_collapse.json deletion correctly collapses orphaned branches
root_consistency.json order-independent deterministic roots (I1)
Pitfalls
  • Extension-path corruption when splitting at a non-nibble-aligned point.
  • Stale hash reuse: forgetting to invalidate a parent's cached hash after a child mutation.
  • Orphan node leakage: deleting a leaf without removing its now-empty parent branch slot.
  • Incorrect branch collapse: collapsing a branch that still has 2 live children (I7 violation).

⬜ Phase 4 — Secure Trie & Root Management §16

Objectives

Wrap crates/trie-core in the mandatory keccak256(key) boundary (secure trie), enforcing the fixed 64-nibble depth bound and finalizing root-management semantics.

Deliverable

crates/secure-trie enforces mandatory key hashing at the API boundary and guarantees a fixed maximum traversal depth of 64 nibbles regardless of input key distribution.

Acceptance
  • Fixture secure_trie_depth.json: 10,000 adversarially chosen-prefix raw keys all produce traversal depth ≤ 64 nibbles.
  • Zero raw-key API surface reachable from outside crates/secure-trie (compile-time enforced via pub(crate) visibility on trie-core's raw-path entrypoints).
  • Secure-trie root matches geth secure_trie.go on the shared fixture set byte-for-byte.
Fixtures
Fixture Assertion
secure_trie_depth.json bounded depth under adversarial key sets (I11)
secure_trie_root.json root matches geth secure_trie.go reference
Pitfalls
  • Leaving a debug-only raw-path API pub by accident, defeating P11.
  • Hashing the key twice (once at the API boundary, once inside a lower layer that assumes raw keys) — produces a different but internally-consistent wrong root.
  • Confusing "secure trie" with encryption — it is a DoS/depth mitigation, not a confidentiality mechanism (see §2 mastery bullet).

⬜ Phase 5 — Inclusion & Exclusion Proof Engine §17

Objectives

Implement proof generation (inclusion and exclusion) and the standalone stateless verifier, treating proofs as a first-class output (P5).

Deliverable

crates/proofs generates and verifies inclusion and exclusion proofs compatible with go-ethereum's proof format, gated by a stateless ProofVerifier (ADR-24).

Acceptance
  • Fixture inclusion.json: 1,000 random keys, all proofs verify true against the live root.
  • Fixture exclusion.json: 1,000 random absent keys, all proofs verify true (correctly proving absence) and include a concrete boundary node (I15).
  • Fixture malformed_proof.json: ≥ 10 corrupted proofs (byte-flip, node-drop, node-reorder) all rejected.
  • Proof generation p99 ≤ 50 µs at 1M-key trie scale (M5); verification p99 ≤ 20 µs (M6).
  • Cross-implementation check: 100 geth-generated proofs verify true under this project's verifier, and 100 locally-generated proofs verify true under a geth-based checker (groundwork for ADR-21, finalized in §21).
Fixtures
Fixture Assertion
inclusion.json valid inclusion proof for a present key
exclusion.json valid exclusion proof for an absent key, with boundary node (I15)
malformed_proof.json corrupted proofs rejected
Pitfalls
  • Omitting an intermediate node the verifier needs to re-hash up to the root (I8 violation) — proof looks plausible but fails to verify.
  • Mishandling an embedded child during proof capture — including it as a standalone proof entry when it should be inline in its parent's RLP (P4 violation).
  • Exclusion proofs that stop one level too early, failing to prove the actual divergence (I15 violation, MM4).

⬜ Phase 6 — Storage Backend & Content-Addressed Persistence §18

Objectives

Implement the NodeStore trait, the in-memory backend, the RocksDB backend, and the decoded-node cache — all behind a backend-agnostic interface (P7).

Deliverable

crates/storage provides a backend-agnostic, content-addressed persistence layer with an in-memory backend for tests and a RocksDB backend for production, fronted by an LRU cache.

Acceptance
  • RocksDB-backed batched insert throughput ≥ 150,000 inserts/sec at batch size 10,000 (M7).
  • Zero stale reads across 100,000 randomized mutation-then-read cycles (I14).
  • Switching NodeStore implementation (in-memory ⇄ RocksDB) requires zero changes to crates/trie-core (P7, compile-time enforced by the trait boundary).
Fixtures
Fixture Assertion
storage_dedup.json identical subtrees inserted twice occupy one physical record
cache_consistency.json no stale cache hit across 100,000 mutation cycles (I14)
Pitfalls
  • Checksum validation added only on the RocksDB path, missed on the in-memory path (inconsistent guarantees between backends).
  • Cache invalidation keyed by the wrong hash (e.g., invalidating the old hash instead of both old and new hash on an update).
  • Column-family confusion between node data and journal metadata (§19) causing compaction to reclaim live journal records.

⬜ Phase 7 — Journaling, Snapshots, Rollback & Crash Recovery §19

Objectives

Implement the write-ahead log, O(1) checkpoint snapshots, transactional rollback, and crash-safe WAL replay (P3, ADR-12).

Deliverable

crates/journal provides append-only WAL logging, O(1) snapshot checkpoints, lossless rollback, and idempotent crash recovery.

Acceptance
  • Fixture snapshot_restore.json: 500 checkpoint/restore cycles all reproduce the exact recorded root (I6).
  • Fixture wal_recovery.json: crash-injected at 50 distinct commit-sequence points, all recover to a valid, root-consistent state within the ≤ 5 s RTO (§4).
  • WAL replay throughput ≥ 200,000 records/sec (M9); snapshot creation latency ≤ 2 ms (M8).
  • Double-replay of any WAL segment yields byte-identical resulting state (I12).
Fixtures
Fixture Assertion
snapshot_restore.json rollback reproduces recorded root (I6)
persistence_root.json root survives a restart with no journal activity
wal_recovery.json crash-injected recovery within RTO (FM-8)
Pitfalls
  • WAL ordering corruption: appending a record before the previous record's fsync completes, breaking I5's monotonicity guarantee under crash.
  • Stale references: a snapshot recorded before a GC pass (§20) may reference nodes the GC has since collected if refcounting doesn't account for open snapshots (T8 cross-reference).
  • Treating "journal write succeeded" as "commit succeeded" without also confirming the data write landed (races with §18's storage layer).

⬜ Phase 8 — Pruning, Garbage Collection & Reference Counting §20

Objectives

Implement reference-counted pruning that reclaims unreachable nodes without collecting anything still reachable from a live snapshot root (P12, I4, I13).

Deliverable

crates/gc reclaims physically unreachable nodes via reference counting gated on all live snapshots, with an independent reachability audit as a correctness backstop.

Acceptance
  • Fuzz suite: 10,000 randomized insert/delete/snapshot/GC interleavings produce zero I4 violations (no node collected while still reachable from a live root).
  • GC pass duration ≤ 500 ms per 1M retired nodes (M10).
  • Reference-count conservation (I13): for any no-op mutation sequence (equal inserts and deletes of the same keys), refcounts return to their pre-sequence values exactly.
Fixtures
Fixture Assertion
gc_reachability.json post-GC storage contains exactly the reachable node set (I4)
refcount_conservation.json refcounts return to baseline after no-op mutation cycles (I13)
Pitfalls
  • Reference-counting bug under concurrent snapshot retirement (T8) — the single most dangerous pitfall in this phase, since it manifests as silent data loss, not a crash.
  • Forgetting that content addressing means two logically distinct insert calls for identical data share one physical node and one refcount, not two.
  • Running GC without journaling it (§20.2 step 9 omitted), making a GC pass unrecoverable if the process crashes mid-collection.

⬜ Phase 9 — Differential Testing, Optimization & Release Hardening §21

Objectives

Build the full differential-test harness against go-ethereum/reth, apply performance optimizations gated by that harness (P10, P13), and produce the release-hardened v1.0 artifact.

Deliverable

A differentially-verified, performance-tuned, release-hardened MPT implementation matching go-ethereum/reth on the full execution-spec state-test corpus.

Acceptance
  • 100% of conformance/ethereum/state_tests/* fixtures produce matching roots against both geth and reth oracles (ADR-21).
  • Zero DiffReport regressions across all optimization changes landed in this phase (P10).
  • 24-hour fuzz campaign (ADR-06) completes with zero crashes and zero new corpus findings requiring a fix.
  • Full M1–M12 differential-suite CI run completes in ≤ 90 s (M11).
Fixtures
Fixture Assertion
ethereum_state.json matches geth/reth on the full execution-spec state-test corpus
random_mutation.json deterministic roots under randomized differential fuzzing
proof_equivalence.json cross-implementation proof verification (§17.2 step 10)
Pitfalls
  • Optimization-induced divergence (FM-10): the single most likely failure in this phase — any change that alters serialization order, cache key derivation, or traversal order without a full differential re-run.
  • Stale cache roots: a node-hash cache (§21.2 step 8) that fails to invalidate on a content change reintroduces I14-class bugs at the optimization layer.
  • Nondeterministic iteration order (e.g., iterating a HashMap instead of a sorted structure) silently reintroducing I1 violations that P2's design was meant to prevent.
