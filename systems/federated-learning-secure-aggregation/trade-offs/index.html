Decisions (§9) · 31 ADRs

1

Language

Chosen

Python 3.11+

Rejected

Rust, C++, Go

When the rejected choice is right

Rust or C++ when the system is CPU-bound (mask PRG > 10⁸ params/s/core target) and the ML portfolio is already in Rust; Python's GIL becomes the bottleneck at extreme cohort sizes

Why: ML-infra portfolio consistency (112/114/115/377); comm-bound, not CPU-bound (§1.10)

2

Tensor backend

Chosen

NumPy

Rejected

pure-Python, PyTorch, JAX

When the rejected choice is right

Pure-Python when correctness tracing across array ops matters more than speed (tiny debug simulations); PyTorch when a production training loop with GPU acceleration is required alongside masking

Why: C-speed vector ops for masks/training without a heavy dep; minimal autograd (112)

3

Autograd

Chosen

minimal reverse-mode (fl_tensor)

Rejected

PyTorch autograd, JAX grad

When the rejected choice is right

PyTorch autograd when a production-grade GPU-accelerated training loop is required; JAX grad when functional composition and JIT across training and masking kernels is desired

Why: "from scratch"; reuse 112; just enough for MLP/CNN/small head

4

Model serialization

Chosen

fixed dtype/shape/endianness byte codec

Rejected

pickle, npz, safetensors

When the rejected choice is right

safetensors when interoperating with HuggingFace-ecosystem models at large model sizes; npz when human-readable debugging of parameter arrays is more important than cross-party determinism

Why: deterministic cross-party wire layout (I15, P4); pickle is unsafe

5

Masking ring

Chosen

Z_R, R=2³² default (power-of-two)

Rejected

F_p prime field, floats

When the rejected choice is right

F_p prime field when the arithmetic must be compatible with Shamir reconstruction in the same field without a separate modulus; floating-point when no masking is used and full precision is preserved

Why: wraparound add is free; sized to avoid true-sum overflow (I6); prime optional

6

Quantization

Chosen

fixed-point + stochastic rounding

Rejected

float masks, no quantization

When the rejected choice is right

Float masks (no quantization) when model size is tiny (m < 10³) and the communication cost is dominated by protocol overhead rather than payload; no-quantization when debugging mask cancellation in cleartext

Why: masking is modular; stochastic round keeps FedAvg unbiased (§8.3)

7

DH key agreement

Chosen

X25519 (cryptography/PyNaCl)

Rejected

classic DH mod p, ECDH P-256

When the rejected choice is right

Classic DH mod p when operating on a platform lacking Curve25519 acceleration; ECDH P-256 when FIPS-140 compliance mandates NIST curves (government/regulated deployments)

Why: fast, constant-time, 32-byte keys (RFC 7748); cross-link 90

8

Mask PRG

Chosen

AES-CTR / ChaCha20 → Z_R^m

Rejected

hash-chain, Python random

When the rejected choice is right

Hash-chain PRG when code simplicity and auditability matter more than throughput and the mask vector is small (m < 10⁴); Python random only ever wins as raw speed in non-security simulations with an explicit insecurity disclaimer

Why: CSPRNG-grade, fast, seedable for tests (RFC 8439 / FIPS-197); excludes random

9

Signatures

Chosen

Ed25519 (cryptography/PyNaCl)

Rejected

ECDSA, RSA

When the rejected choice is right

ECDSA when the deployment already runs a P-256 PKI and signature-batch verification is needed; RSA when legacy infrastructure requires RSA tokens for client identity alongside key signatures

Why: consistency-check sigs (RFC 8032); fast, deterministic

10

Secret sharing

Chosen

Shamir(t,n) + Lagrange over Z_R/F_p

Rejected

additive, replicated

When the rejected choice is right

Additive (2-of-n) sharing when dropout tolerance is not required and the implementation must avoid polynomial arithmetic; replicated sharing when a very small, trusted cohort can afford O(n²) state

Why: threshold dropout recovery (§8.5); sibling to 379

11

SecAgg protocol

Chosen

Bonawitz 2017 4-round (pairwise+double-mask+Shamir)

Rejected

additive-only, pure MPC

When the rejected choice is right

Additive-only masking (no Shamir) when the system guarantees synchronous participation and dropout is operationally impossible (cross-silo, always-on servers); pure MPC (392) when the function is not a vector sum and the generality is worth the cost

Why: the canonical dropout-tolerant single-server protocol (§8.6); MPC 392 is more general/costly

12

Transport

Chosen

gRPC + protobuf (net) + in-proc (sim)

Rejected

REST/JSON, raw sockets, MQTT

When the rejected choice is right

REST/JSON when the client SDK targets browser environments (no gRPC-web) and payload sizes are small; raw sockets when learning the framing layer explicitly; MQTT when device-level publish-subscribe and fan-out broadcast semantics fit the topology

Why: streaming + chunking + schema typing (I15); cross-link 155

13

Async model

Chosen

asyncio (net) + threads (sim)

Rejected

multiprocessing-only, Twisted

When the rejected choice is right

multiprocessing-only when GIL contention at high cohort counts exceeds asyncio overhead; Twisted when the team already maintains a Twisted codebase and the ecosystem integration outweighs the learning curve

Why: mature async I/O; sim uses deterministic scheduling for replay

14

Compression

Chosen

quantization + top-k sparsification + random mask

Rejected

none, full-precision

When the rejected choice is right

No compression when the model is tiny (m ≤ 10⁴) and debugging full-precision mask cancellation is the priority; full-precision when the uplink budget is unconstrained and DP noise already dominates the gradient signal

Why: uplink bytes are the FL bottleneck (P9); pluggable codec

15

DP mechanism

Chosen

per-example clip + Gaussian (DP-SGD)

Rejected

Laplace, PATE, output perturbation

When the rejected choice is right

Laplace mechanism when the query is count/sum over a dataset with L1 sensitivity and non-SGD noise is acceptable; PATE when unlabeled public data exists and teacher-ensemble privacy is preferred over per-step accounting

Why: standard for SGD (Abadi 2016); composes via RDP; cross-link 377

16

DP placement

Chosen

client/example-level + distributed-noise-under-mask

Rejected

central-only, local-only

When the rejected choice is right

Central-only DP when a TEE or trusted noiser is available and distributed noise coordination overhead is unacceptable; local-only DP when there is no trusted party at all and higher noise is an acceptable tradeoff for eliminating trust assumptions

Why: SecAgg enables central-quality noise with no trusted noiser (§8.7, P11)

17

Privacy accountant

Chosen

RDP / moments + subsampled-Gaussian

Rejected

basic/advanced composition, PLD

When the rejected choice is right

Basic composition when only a handful of rounds (T ≤ 5) are run and the loose bound is acceptable; PLD accountant when tight ε at low-T with heterogeneous mechanisms is required and the numerical overhead is justified

Why: tight composition over many rounds (Mironov 2017); PLD deferred Phase 9

18

Aggregation rules

Chosen

FedAvg + FedProx + FedAdam/FedYogi

Rejected

FedAvg-only, SCAFFOLD

When the rejected choice is right

FedAvg-only when the data distribution is known to be nearly IID and adaptive overhead is unjustified; SCAFFOLD when client drift from variable local epochs is the dominant convergence failure and control variates are worth the extra upload

Why: heterogeneity + adaptive server opt (Li 2020, Reddi 2020)

19

Robust rules

Chosen

Krum/Multi-Krum, median, trimmed-mean, norm-bound

Rejected

none

When the rejected choice is right

No robust rules when the deployment is a closed cross-silo environment with vetted participants and the SecAgg tension makes robust rules a liability; gradient-based defenses beyond Krum/median when the Byzantine fraction is known precisely and a tighter guarantee is needed

Why: Byzantine defense (Blanchard 2017, Yin 2018); SecAgg tension documented (P12)

Adversary model

Chosen

semi-honest server + ≤t colluders, static

Rejected

malicious server, adaptive

When the rejected choice is right

Malicious/active security model when the server is untrusted beyond honesty-but-curiosity (e.g., a public aggregation service) and verifiable masking + ZK proofs are affordable; adaptive corruption when the adversary can corrupt clients after observing protocol messages

Why: core target; verifiable/active deferred Phase 13

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Central DP with a Trusted Aggregator (No SecAgg Crypto)

+------------------+        plaintext Δ_u        +---------------------+
|   Client 1       |  --------------------------> |                     |
+------------------+                              |  Trusted Aggregator |
+------------------+        plaintext Δ_u        |  (sees all updates) |
|   Client 2       |  --------------------------> |  clips + adds       |
+------------------+                              |  N(0,σ²C²I) once   |
      ...                                         |  -> noised sum      |
+------------------+        plaintext Δ_u        +----------+----------+
|   Client N       |  --------------------------> |          |
+------------------+                              |          v
                                                  +-------------------+
                                                  |   FL Server       |
                                                  |  FedAvg on noised |
                                                  |  aggregate        |
                                                  +-------------------+

Wins when: the aggregator is a hardware TEE (e.g., SGX enclave) or a contractually trusted party and the deployment cannot afford the 4-RTT SecAgg overhead; single-pass noise is strictly less noisy than distributed noise for the same σ because there is no per-client variance inflation.

Embodied by: Google Gboard production FL (McMahan et al. 2017 original deployment description), which used a trusted server-side aggregator with central DP before SecAgg was deployed; many cross-silo healthcare FL deployments where institutions are the aggregators under data-use agreements.

Why rejected here: the threat model explicitly targets a semi-honest server that tries to learn individual updates (§1.1, Threat Model). A trusted aggregator collapses the privacy guarantee to "trust the aggregator" — removing the SecAgg invariant I8 entirely. The educational goal is to show precisely why and how the cryptographic protocol is necessary; shipping without SecAgg would omit the system's core intellectual content.

Local DP — Each Client Privatizes Before Upload (No Aggregation Secret)

+------------------+    clip + N(0,σ_L²C²I)    +--------------------+
|   Client 1       |  ------------------------> |                    |
|  (noises its     |    noised Δ_u1              |   FL Server        |
|   own update)    |                             |  plain sum of      |
+------------------+                             |  already-noised    |
+------------------+    clip + N(0,σ_L²C²I)    |  updates           |
|   Client 2       |  ------------------------> |  (no crypto layer) |
|  (noises its     |    noised Δ_u2              |                    |
|   own update)    |                             +--------------------+
+------------------+
      ...

Wins when: there is no trusted party at all — not even a TEE aggregator — and the system must satisfy a formal local-DP (LDP) guarantee where every client's upload is privatized before it touches any untrusted infrastructure; examples include Google's Chrome RAPPOR histograms and Apple's emoji/keyboard telemetry where the client is the only trusted boundary.

Embodied by: Apple's local-DP telemetry system (announced WWDC 2016, deployed iOS 10) and Google's RAPPOR (Erlingsson, Pihur, Korolova, ACM CCS 2014), which both operate in the LDP model where σ_L = √m_c × σ_central to match central-DP quality — a noise amplification of √cohort.

Why rejected here: LDP requires √cohort× more noise than central/distributed DP for the same ε (§8.7, §P11), which at cohort = 100 means 10× more noise — destroying convergence on non-trivial models. The §1.1 scope explicitly states "formal LDP guarantee as the default" is a non-goal (§1.3); the design achieves central-quality privacy via the distributed-noise-under-mask scheme (§8.7), which gives the same aggregate noise without a trusted noiser.

Threshold-Paillier Homomorphic Aggregation (MPC-Based)

+------------------+   Enc_{pk}(Δ_u1)         +---------------------+
|   Client 1       | -----------------------> |                     |
|  encrypt update  |   ciphertext              |   FL Server         |
|  under shared pk |                           |   aggregates        |
+------------------+                           |   ciphertexts:      |
+------------------+   Enc_{pk}(Δ_u2)        |   Σ Enc(Δ_u) =      |
|   Client 2       | -----------------------> |   Enc(Σ Δ_u)        |
|  (Paillier enc.) |   ciphertext              |   (homomorphic)     |
+------------------+                           +----------+----------+
      ...                                                 |
                              partial decrypt             v
                        +--------+--------+--------+
                        | Key-   | Key-   | Key-   |   (t-of-n
                        | holder | holder | holder |    threshold
                        |   1    |   2    |   3    |    decryption)
                        +--------+--------+--------+
                                      |
                                      v  plaintext Σ Δ_u

Wins when: the deployment must support arbitrary function evaluation over client inputs (not just a sum), needs post-aggregation operations that SecAgg's modular ring cannot express (e.g., second moments, cross-client statistics), or requires malicious-server security without relying on the semi-honest assumption; threshold-Paillier is the natural fit for GDPR-regulated cross-silo settings where the server is a competing institution.

Embodied by: FATE (WeBank) uses Paillier-based additive HE for specific secure computation tasks in cross-silo finance; cross-link 391 (Homomorphic Encryption project) is the direct sibling.

Why rejected here: Paillier ciphertext operations are ≈ 100–1000× slower than modular ring addition (Performance Engineering); for m = 10⁶ parameters the per-round HE overhead is prohibitive at the educational scale target. More importantly, threshold-Paillier introduces key-ceremony complexity (key generation, partial decryption coordination) that would dominate the implementation surface, obscuring the simpler SecAgg algebraic insight that masks cancel in a sum. The design cross-links 391 and sketches HE aggregation as a deferred Phase 13 alternative (§1.3).
