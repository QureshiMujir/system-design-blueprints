Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If two clients use different values of B (the quantization range) in the same round, the server will receive a wrong aggregate without any error being raised. Which invariant is supposed to catch this, in which phase does it get enforced, and what is the exact mechanism? (§I15, §I6, Phase 4, ADR-4)
  2. The threshold t appears in both the Shamir sharing degree and the survival check. If you set t = cohort − 1 to maximize privacy, what is the dropout tolerance, and how does this interact with the round-deadline straggler policy? Give the exact formula. (§P6, §I4, §8.6, Phase 7)
  3. A client sends its masked input y_u in R2 but the network delivers it after the server has already broadcast (U2, D2) in R3. The server has declared this client dropped and already requested its s_u^{SK} shares. Can the server now unmask this client? Walk through the I2 enforcement and the consistency-check path. (§I2, §I9, §P5, Phase 7)
  4. Under the distributed-noise-under-mask scheme, each client adds N(0, σ²C²I/|U|) before masking. If five clients drop after committing noise but before their y_u arrives, does the post-unmask aggregate carry the right total noise variance? Derive the answer from §8.7. (§8.7, §I1, Phase 8, ADR-16)
  5. The RDP accountant charges the budget using q = cohort/N (§8.8). If the server uses importance sampling instead of uniform sampling, is the amplification formula still valid? Which ADR governs sampling, and what would need to change in fl_accountant? (ADR-21, §8.8, Phase 9, §I13)
  6. Krum requires inspecting individual updates to compute pairwise distances. Yet fl_robust/tension.py is supposed to raise RobustSecAggConflict at config time. Describe exactly what the tension guard checks, what config combination triggers it, and why norm bounding alone is the only SecAgg-compatible defense without ZK. (§P12, Phase 10, ADR-19, ADR-20)
  7. A single client with n_u = 0 (empty shard) participates in a SecAgg round and sends a masked zero vector. What does FedAvg do with this client's weight, and what happens to the I12 weight-sum assertion? (§8.12, §I12, Phase 3, Phase 5)
  8. The PRG expansion prg_expand(seed, R, m) must produce a uniform distribution over Z_R. Why does naive truncation of an AES keystream to Z_R introduce bias when R is not a power of two, and what does the implementation use instead? (§I1, Phase 5 §16.2, ADR-5)
  9. After T = 200 rounds at q = 10⁻⁴ and σ = 1.1, the ledger shows ε = 3.02 against a target of 3.0. The server refuses to start round 201. Is the stated privacy guarantee still valid for the first 200 rounds, and does the refusal of round 201 violate any invariant? (§I13, §P10, Phase 9, §8.8)
  10. Ed25519 signatures in R3 cover hash(U2, D2). If the server broadcasts two different (U2, D2) pairs to two disjoint client groups, what exactly does the consistency check detect, and what does it NOT detect in a semi-honest adversary model? (§I9, §P5, Threat Model, Phase 7)
  11. The TranscriptRng uses a fixed seed for test reproducibility. What is the exact mechanism that prevents it from being used in production, and what would happen to mask secrecy if it were? Trace the check through the design principles and invariants. (§P2, §P13, §I7, Phase 5, ADR-27)
  12. FedProx adds a proximal term at the client. The server only ever sees the aggregate delta, not the individual proximal-adjusted deltas. How does FedProx improve convergence under non-IID data without the server knowing μ per client, and why does this not break the SecAgg privacy guarantee? (§8.2, §P1, Phase 3, Phase 11)
  13. The worked example in §8.10 shows client 3 dropping. Trace what happens if client 3 drops after R1 (shares committed) but before R2 (never sends y_3). Then trace what happens if client 3 drops after R2 (server has y_3) but the server falsely declares it dropped in R3. In which case can the server unmask client 3, and why? (§8.5, §8.10, §I2, Phase 6, Phase 7)
  14. The ring R must satisfy R > cohort × max_quantized (I6). If R is set at system initialization and the cohort fluctuates across rounds due to dropout, when (if ever) can the ring be resized mid-campaign, and what are the coordination implications? (§I6, §I15, Phase 5, ADR-5)
  15. Privacy accounting uses Poisson subsampling amplification formulas. The actual cohort sampling in fl_server/cohort.py is sampling without replacement. When does the mismatch between Poisson and without-replacement subsampling matter, and what does the ADR say about it? (ADR-17, §8.8, Phase 9, §I13)
  16. A client's n_u = 5000 while the cohort median is n_u = 50. FedAvg assigns this client 100× the weight. Could this client act as a semi-honest "weight amplifier" by submitting a large update? Explain how norm bounding interacts with weighting. (§8.9, §P12, Phase 10, §I12)
  17. The fl_telemetry redaction guard rejects any log field that "could carry an update/seed." How does the guard decide what constitutes an update vs a metric? Name two metrics that are safe to log and one value that must be redacted, citing the relevant principle. (§P1, Phase 12, §I8, ADR-23)
  18. Bell et al. (2020) extend SecAgg to a log-degree communication graph. This design defers that extension. What is the specific computational bottleneck it addresses, and at what cohort size does the pairwise-quadratic cost start dominating the total round cost versus the model-size cost? Derive from §4.1 values. (Scalability Analysis, Phase 13, §8.6, MM3)
  19. The BudgetLedger.can_afford(q, σ) method gates each round. If the server changes σ mid-campaign (e.g., applies a different noise level for the last 10 rounds to converge faster), does the composition formula still hold? What part of fl_accountant handles this? (§8.8, §I13, Phase 9, ADR-17)
  20. The simulator (fl_sim) asserts "server view == aggregate only" on every run. Describe the exact assertion — what it computes, what inputs it has, and how it distinguishes a leaky design from a correct one. Reference the relevant invariant and security definition. (§I8, §P3, Phase 7, Phase 13)
  21. FedAdam maintains server-side moment accumulators m_t, v_t. Under SecAgg the server only receives Σ n_u·Δ_u and Σ n_u. Explain whether resetting m_t, v_t between campaigns but not between rounds is correct, and what would happen if they were reset after each round. (§8.2, Phase 3, ADR-18)
  22. The fl_secagg consistency check uses Ed25519 signatures. Suppose a client is Byzantine (out of scope but consider the analysis) and signs a different hash(U2, D2) from the honest set. The server detects the mismatch and aborts. Does this abort reveal which client was Byzantine, and does that violate the semi-honest assumption? (§I9, Threat Model, ADR-20, Phase 7)

Mental Models & First Principles

  1. MM1 — Masks cancel only in the exact sum over the exact set. Predicts: adding or removing any single client's contribution leaves a dangling PRG term that corrupts the aggregate. Without it: developers test "most clients present" and ship a system that silently produces garbage when dropout set differs from the round-3 survivor set. Applied: §8.4 / §8.5 / Phase 5 where the ± sign convention and the surviving-set bookkeeping are defined.

  2. MM2 — One parameter, two opposing guarantees: the threshold t bounds correctness from below and privacy from above. Predicts: raising t strengthens privacy but raises the dropout budget needed to abort; lowering t tolerates more dropout but weakens the colluder bound. Without it: designers set t=1 (generous dropout tolerance) and discover later that one colluding client plus the server can reconstruct an update. Applied: §P6 / Phase 6 / Phase 7 where the threshold appears in every survival check.

  3. MM3 — Communication, not compute, is the FL bottleneck; every design decision is measured in bytes × rounds. Predicts: a 10× training speedup is irrelevant if it does not reduce bytes/round or number of rounds. Without it: engineers profile CPU-bound autograd while the actual campaign time is dominated by 4 SecAgg RTTs × T rounds × cohort clients. Applied: §4.1 (throughput driver) / Phase 4 / Phase 9 (rounds bound by budget).

  4. MM4 — SecAgg and DP are orthogonal, not substitutes; each closes a gap the other leaves open. Predicts: SecAgg blocks gradient inversion against the server, but the aggregate still leaks via membership inference; DP bounds the aggregate's leakage but does not prevent the server from seeing individual updates without SecAgg. Without it: a team ships SecAgg and concludes "privacy is done," ignoring that the aggregate is still a sensitive statistic. Applied: §P11 / Phase 8 / Phase 13 (MIA simulation).

  5. MM5 — Double-masking resolves the dropped-vs-slow ambiguity; without it the server controls who is "dropped" and can unmask any slow client. Predicts: a self-mask PRG(b_u) protects a client whose y_u arrived but whom the server falsely declares dropped, because the server only recovered s_u^{SK} shares, not b_u. Without it: the server equivocates the dropout set, collects the "dropped" client's pairwise shares, and cancels all masks — a full unmask of one client. Applied: §P5 / §8.5 / Phase 6 / Phase 7.

  6. MM6 — The randomness faucet must be single, typed, and auditable; a seeded RNG in production makes masks predictable — worse than no masking. Predicts: any code path that calls numpy.random or random directly outside fl_crypto can be differenced by an observer who knows the seed. Without it: a developer adds a quick numpy.random.randn for distributed noise in a "test" that ships to prod because the config flag is not enforced. Applied: §P2 / §I7 / Phase 5 / Phase 8.

  7. MM7 — Subsampling amplification is the primary lever for privacy efficiency; without it RDP composition grows linearly in T at full rate. Predicts: reducing cohort rate q from 1 to 0.01 can reduce the effective RDP by orders of magnitude, enabling far more rounds for the same ε. Without it: a designer runs T=1000 rounds with q=1 and discovers the budget exhausted after T=10, blaming the noise level rather than the missing amplification. Applied: §8.8 / Phase 9 (subsample.py) / ADR-17.

  8. MM8 — Byzantine robustness and SecAgg are in structural tension; any rule that needs to inspect individual updates cannot run under SecAgg without a ZK or MPC backend. Predicts: fl_robust applied "under SecAgg" is either a privacy breach (it peeked) or a no-op (it ran on the aggregate). Without it: developers add Krum as an aggregation rule without disabling SecAgg, ship a no-op defense, and report "Byzantine-robust FL" incorrectly. Applied: §P12 / Phase 10 / ADR-19 / ADR-20.

  9. MM9 — The 4-round SecAgg protocol is a state machine; any early advancement past a round without a threshold check creates a window for partial unmasking. Predicts: advancing R3 on a timeout without re-checking |U2| ≥ t+1 unmaskes a sum over a set too small to guarantee privacy. Without it: a developer adds a fast-path that skips the survival check when only one client is slow, inadvertently revealing that client's update. Applied: §P7 / §8.6 / Phase 7 / I4.

  10. MM10 — Quantization, ring size, and client ordering are a jointly agreed invariant; any divergence silently corrupts the aggregate without raising an error. Predicts: a client quantizing with a different B or ordering clients by IP instead of by ID leaves a non-zero residual after unmasking that looks like a small gradient noise. Without it: a schema drift between client versions goes undetected because the aggregate merely shifts rather than NaN-ing. Applied: §P4 / §I15 / §I6 / Phase 4 / Phase 5.

Books

  • Kairouz, McMahan et al. — Advances and Open Problems in Federated Learning (2019/2021, FnT ML). The field's reference survey. §3 (SecAgg), §4 (privacy/DP), §5 (robustness), §3.2 (non-IID). Extract: the problem taxonomy, threat models, and where each technique fits. Primary reference. -> applied in §3.2, §8.9, Phase 10, Phase 13.
  • Dwork & Roth — The Algorithmic Foundations of Differential Privacy (2014). Ch 2–3 (definitions, Laplace/Gaussian mechanisms, composition), Ch 3.5 (Gaussian), App (advanced composition). Extract: (ε,δ)-DP, sensitivity, composition — the basis of fl_accountant. -> applied in §8.7, §8.8, Phase 8, Phase 9.
  • Goodfellow, Bengio, Courville — Deep Learning (2016). Ch 5 (ML basics), Ch 8 (optimization/SGD). Extract: the local-training loop, SGD/Adam, generalization for fl_client/fl_tensor. -> applied in §8.2, Phase 1, Phase 3.
  • Katz & Lindell — Introduction to Modern Cryptography (3e). Ch on DH key exchange, PRGs/PRFs, secret sharing, semantic security. Extract: the security foundations the masking + sharing rely on. -> applied in §8.4, §8.5, Phase 5, Phase 6.
  • Lindell — Tutorials on the Foundations of Cryptography (2017), "How to Simulate It". Extract: simulation-based privacy — the methodology behind the "server view == aggregate" invariant (§7). -> applied in §7 (I8), Phase 7, Phase 13.
  • Cramer, Damgård, Nielsen — Secure Multiparty Computation and Secret Sharing (2015). Ch on linear secret sharing + the secure-sum special case. Extract: why SecAgg is a cheap MPC specialization (cross-link 392). -> applied in §2.5, Phase 5 (secure-sum specialization).
  • Shoup — A Computational Introduction to Number Theory and Algebra. Extract: modular arithmetic over Z_R, polynomial interpolation for Shamir (fl_crypto). -> applied in §8.3, §11.2 (Shamir), Phase 6.
  • Murphy — Probabilistic Machine Learning: Advanced Topics (2023). Ch on federated/private learning + variational/optimization background. Extract: convergence under heterogeneity, FedProx/adaptive intuition. -> applied in §8.2, Phase 3, Phase 11.

Glossary · 47 terms · site-wide glossary

Federated Learning (FL)
training a shared model across clients that keep their data local; only updates are exchanged
FedAvg
sample-count-weighted averaging of client models/deltas (McMahan 2017) — the baseline FL algorithm
FedProx
FedAvg + a client-side proximal term (μ/2)‖w−w_t‖² to curb drift under heterogeneity
FedAdam / FedYogi
server-side adaptive optimizer applied to the aggregated pseudo-gradient (Reddi 2020)
Cohort
the subset of clients selected to participate in a given round
Sampling rate q
cohort size / pool size; the subsampling probability used in DP amplification
Weight-delta Δ_u
client's local model change w_local − w_global (the upload, vs a raw gradient)
Secure Aggregation (SecAgg)
a protocol revealing only Σ_u x_u to the server, hiding each x_u (Bonawitz 2017)
Pairwise mask
PRG(s_{u,v}) added by one client and subtracted by the other so it cancels in the sum
Self-mask (double-masking)
PRG(b_u) each client adds to protect against the dropped-vs-slow ambiguity
Mask cancellation
the algebraic fact that pairwise masks telescope to zero in the exact sum over contributors
Diffie–Hellman key agreement
two parties derive a shared seed s_{u,v} from their key pairs (X25519)
PRG
pseudo-random generator expanding a seed into a uniform mask vector in Z_R^m (AES-CTR/ChaCha20)
Ring Z_R
integers mod R; the modular field for quantized updates + masks (addition wraps)
Quantization
mapping float updates to fixed-point integers in Z_R (stochastic rounding keeps it unbiased)
Shamir (t,n) secret sharing
secret = p(0) of a degree-t polynomial; ≥ t+1 shares reconstruct, ≤ t reveal nothing
Threshold t
the Shamir threshold: bounds correctness (≥ t+1 to reconstruct) and privacy (≤ t learn nothing)
Surviving set U
clients whose masked input reached the server before the deadline
Dropped set D
selected clients whose masked input did not arrive (recovered via key reconstruction)
Dropped-vs-slow ambiguity
the server cannot tell a dropped client from a slow one; double-masking + consistency resolve it
Consistency check
survivors sign the same dropout-set hash so the server cannot equivocate about who dropped
Equivocation
a server telling different clients different dropout sets to isolate a victim
Semi-honest (honest-but-curious)
adversary follows the protocol but tries to learn from its view
Simulation-based privacy
the server+≤t view is reproducible from the aggregate alone (the SecAgg security definition)
Differential Privacy (ε,δ)
a bound on how much the output reveals about any single record
Sensitivity
the max change in a function from one record; bounded by the clip C
Clipping bound C
per-example/per-client L2 clip making sensitivity ≤ C
Gaussian mechanism
add N(0,σ²C²I) to a sum to achieve (ε,δ)-DP
Noise multiplier σ
noise std / C; the DP knob (higher σ → smaller ε, more noise)
DP-SGD
clip per-example gradients then add Gaussian noise per step (Abadi 2016)
Client-level vs example-level DP
protect a whole client's participation vs a single training example
Central vs local DP
trusted aggregator noises once vs each client noises its own update
Distributed noise under the mask
each client adds a noise share so the unmasked aggregate carries central-quality noise
Rényi DP (RDP)
a divergence-based DP variant that composes additively; tight for many rounds (Mironov 2017)
Moments accountant
the RDP-based accountant for the subsampled Gaussian mechanism (Abadi 2016)
Subsampling amplification
privacy gain from only a sampled cohort participating each round
Privacy budget / ledger
the cumulative (ε,δ) tracked vs a target; the server stops when it is spent
Krum / Multi-Krum
Byzantine-robust aggregation picking update(s) closest to their neighbors (Blanchard 2017)
Trimmed mean / coord. median
robust per-coordinate aggregation discarding outliers (Yin 2018)
Norm bounding
clipping each update's L2 norm ≤ M (SecAgg-compatible, client-side)
Membership inference
inferring whether a record was in the training set (Shokri 2017)
Deep Leakage from Gradients (DLG)
reconstructing training data from a gradient/update (Zhu 2019)
Non-IID
clients' data distributions differ (heterogeneity); Dirichlet(α) controls skew
Personalization / FedPer
adapting the global model per client; FedPer keeps personalization layers local
Federated evaluation
evaluating the global model via clients reporting local metrics (incl. worst-k)
CSPRNG
cryptographically secure PRNG (production randomness for seeds/keys/noise)
Transcript
the full sequence of a run's messages (seeded + replayable in tests)
