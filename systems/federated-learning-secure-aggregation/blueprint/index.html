1. Goal

1.1 Precise Engineering Scope

Build a self-contained, from-scratch Federated Learning (FL) system in Python in which a central coordinator (server) orchestrates many client trainers to collaboratively train a shared global model without any client raw data leaving the device, and in which the per-round aggregation is performed under a Secure Aggregation (SecAgg) protocol so the server learns only the aggregate of client model updates and nothing about any individual update. The system implements the full stack bottom-up: a minimal tensor + autograd substrate and a local SGD trainer (parameter/state-dict model, weight-delta vs gradient upload, (de)serialization); a server coordinator with cohort selection, global-model versioning, and a round lifecycle FSM (SELECT → BROADCAST → LOCAL-TRAIN → COLLECT → AGGREGATE → UPDATE) with partial participation, deadlines, and a straggler policy; FedAvg sample-count-weighted aggregation (McMahan 2017) plus FedProx (proximal μ) and FedAdam/FedYogi server-side adaptive optimizers (Reddi 2020); a gRPC/protobuf communication layer with chunking, compression (scalar/vector quantization, top-k sparsification, random masking) and bandwidth/RTT accounting; pairwise masking SecAgg core (Bonawitz et al. 2017) using Curve25519 Diffie–Hellman key agreement and a PRG-expanded mask over a modular vector ring Z_R^m; double-masking + t-of-n Shamir secret sharing (cross-link 379) for dropout recovery; a 4-round SecAgg protocol (AdvertiseKeys → ShareKeys → MaskedInputCollection → Unmasking) with signatures and a consistency check against a server that equivocates about who dropped; differential privacy (per-example L2 clipping bound C, Gaussian mechanism N(0,σ²C²I), DP-SGD per Abadi 2016, client-level vs example-level, central vs local, distributed-noise-under-mask); privacy accounting via Rényi DP / moments accountant (Mironov 2017; Abadi 2016) with subsampling amplification and a privacy-budget ledger; robust aggregation (Krum/Multi-Krum, coordinate-wise median, trimmed mean, norm bounding) and an explicit treatment of its fundamental tension with SecAgg; non-IID data partitioning, personalization (FedPer / fine-tuning), and a federated evaluation protocol; and an observability + operational-readiness layer (round metrics, convergence dashboards, dropout/cohort telemetry, privacy-budget consumption, tracing).

The threat-model target is a semi-honest (honest-but-curious) server colluding with up to t clients: parties follow the protocol but try to learn honest clients' updates from their view; SecAgg guarantees the server's view is simulatable from the aggregate alone for ≤ t colluders. Active/malicious robustness (verifiable masking, ZK norm bounds) and TEE/HE-based aggregation are explicitly deferred (sketched, cross-linked to 391). The contract is seeded-deterministic transcripts for tests (reproducible round/mask/noise streams) with all security-relevant randomness drawn from a CSPRNG in real runs; the system is educational and NOT audited / NOT production ML infrastructure.

1.3 Non-Goals

  • No malicious-server / active security: no verifiable masking, no ZK range/norm proofs, no Byzantine-broadcast consistency — PhaseDeferred("FINAL_BLUEPRINT §Phase 13").
  • No simultaneous robust aggregation + SecAgg without trusted help; the tension is analysed and only sketched mitigations are given — PhaseDeferred("FINAL_BLUEPRINT §Phase 10").
  • No homomorphic-encryption or TEE-based aggregation as a shipped path (sketched, cross-linked to 391) — PhaseDeferred("FINAL_BLUEPRINT §Phase 13").
  • No asynchronous FL (FedBuff-style) as a shipped path; synchronous rounds only — PhaseDeferred("FINAL_BLUEPRINT §Phase 13").
  • No production transport security (PKI, device attestation, NAT traversal) — transport is pluggable but reference-grade.
  • No GPU/SIMD acceleration of training or the PRG/mask kernels beyond optional NumPy vectorization; a Rust/C extension for masking is noted but deferred — PhaseDeferred("FINAL_BLUEPRINT §Phase 12").
  • No general autograd library competing with PyTorch; the tensor core is minimal (cross-link 112) — NumPy-backed, just enough to train small models.
  • No formal local-DP (LDP) guarantee as default; central/distributed DP under SecAgg is the primary model.

1.4 Intended Deployment Model

  • Library packages consumed by Python code: construct a Server with a model spec, aggregation rule, SecAgg config, and DP config; construct Clients with local dataset shards; wire them over a Transport; run rounds; collect the converged global model and a privacy-budget ledger.
  • Simulator harness (fl_sim): runs the server and N clients as threads/processes in one process over in-memory channels with a seeded transcript recorder — the primary test/teaching vehicle; deterministic, replayable, dropout-injectable, comm-accounted.
  • Network mode (fl_transport): server and each client are separate processes; gRPC over TCP (optional TLS); a bootstrap/registration endpoint; identical protocol code, different Transport impl.
  • CLI (fl_cli, entry point fl-cli): fl-cli server --rounds 200 --cohort 100 --secagg on --dp on, fl-cli client --server addr --shard k, fl-cli simulate --clients 1000 --noniid dirichlet:0.1, fl-cli bench. Single training campaign per server invocation.

1.6 Phase 0 Deliverable — Locked Packages

Public APIs locked before implementation. Fourteen installable Python packages under one workspace (packages/), import names fl_*:

  1. fl_tensor — Tensor (NumPy-backed ndarray wrapper), minimal reverse-mode autograd (backward()), ModelState parameter dict, init/clone/axpy, fixed-point quantize/dequantize to Z_R, deterministic (de)serialization to bytes. (Cross-link 112.)
  2. fl_data — dataset shards, Partitioner (IID, Dirichlet non-IID α, pathological by-label), LocalLoader (epochs, batches, shuffle seed), per-client sample counts n_u.
  3. fl_client — local SGD/Adam trainer, train_local() → weight-delta Δ_u or gradient, per-example clipping hook (DP), client state machine, model-version pinning.
  4. fl_server — coordinator: client registration, cohort sampling (uniform / importance), global-model store + monotonic version, round lifecycle FSM, deadlines, straggler policy, partial-participation bookkeeping.
  5. fl_aggregate — FedAvg sample-weighted averaging, FedProx (proximal term), FedAdam/FedYogi server optimizers, convergence tracking, aggregation-rule trait.
  6. fl_transport — gRPC/protobuf transport, in-proc channels (sim), model chunking, compression codecs (uniform/stochastic quantization, top-k sparsification, random masking), byte/round accounting.
  7. fl_crypto — CSPRNG (SecureRng) + seeded TranscriptRng (tests); Curve25519 X25519 DH key agreement (cross-link 90); AES-CTR/ChaCha20 PRG; modular vector ops over Z_R; Shamir(t,n) secret sharing + Lagrange (cross-link 379); Ed25519 signatures; domain-separated KDF.
  8. fl_secagg — pairwise mask PRG(s_{u,v}), self-mask PRG(b_u) (double-masking), masked input y_u, the 4-round protocol orchestration, dropout reconstruction, consistency check.
  9. fl_dp — per-example L2 clipping (C), Gaussian mechanism, DP-SGD, client-level vs example-level, central vs local, distributed-noise-under-mask helper.
  10. fl_accountant — RDP accountant (Gaussian + subsampled), moments accountant, composition over rounds, subsampling amplification, (ε,δ) conversion, noise-multiplier calibration to target ε, privacy-budget ledger.
  11. fl_robust — Krum/Multi-Krum, coordinate-wise median, trimmed mean, norm bounding/clipping of updates, anomaly detection; SecAgg-compatibility flags + the tension analysis.
  12. fl_eval — federated evaluation protocol, non-IID metrics (per-client + worst-k), personalization (local fine-tuning, FedPer personalization layers), client sampling under heterogeneity.
  13. fl_telemetry — round metrics, convergence dashboard data, dropout-rate + cohort-size telemetry, privacy-budget consumption telemetry, straggler/latency analysis, structured logging, tracing spans (cross-link 132).
  14. fl_cli — server | client | simulate | bench | account; cohort/round config, SecAgg/DP toggles, non-IID spec, seeds for deterministic transcripts.

Plus the test harness package fl_sim (in-process server+N-client simulator, seeded transcript recorder/replayer, dropout injection, comm/budget asserts).

1.10 Language Selection — Python

FL's binding constraints are communication (round latency + bytes), protocol case-analysis (rounds, dropout sets, share routing — a missed case is a silent privacy bug), and ecosystem fit with the ML-infra portfolio. The portfolio's adjacent projects — Autograd/Mini-PyTorch 112, Transformer Training Loop 114, Distributed Training 115, and the DP Engine 377 — are Python; FL must interoperate with their ModelState, optimizers, and DP primitives, so Python is the consistent choice. Python with NumPy gives vectorized tensor/mask arithmetic at C speed for the hot loops (mask expansion is a vector add over Z_R^m), a mature gRPC + protobuf stack, cryptography/PyNaCl for X25519/Ed25519/AES, and rapid iteration on protocol state machines where correctness review matters more than raw throughput (FL is communication-bound, not CPU-bound). dataclasses + enum + exhaustive match (3.10+) give closed message/round types so adding a SecAgg round or dropout case forces every handler to address it. Rust is rejected as the primary language despite faster mask/PRG kernels: it would fork the ML-infra portfolio, lose the autograd/optimizer reuse, and slow protocol iteration; the performance-critical masking + PRG + transpose-free vector PRG can be dropped to a Rust/C extension later (deferred Phase 12) behind the same fl_crypto API. C++ is rejected for memory-safety/tooling friction at no ecosystem gain. Crypto randomness MUST come from a CSPRNG (os.urandom/secrets/ChaCha20); seeded determinism is allowed only in test transcripts and is refused in production mode.

2. Why Build This

2.1 Unique Systems Knowledge Taught

  • Why "train on data you never see" is concretely achievable: data stays local; only model updates move; and with SecAgg even those updates are hidden from the server in aggregate.
  • How pairwise masks cancel in the exact sum — the central algebraic fact of SecAgg: each unordered pair contributes +PRG(s_{u,v}) to one client and −PRG(s_{u,v}) to the other, so Σ_u y_u telescopes the pairwise terms away.
  • Why dropouts break naive masking and how double-masking + Shamir resolve the dropped-vs-slow ambiguity: the server reconstructs a dropped client's pairwise masks OR a surviving client's self-mask — never both for one client (which would unmask it).
  • Why the threshold t simultaneously bounds correctness (≥ t shares to reconstruct) and privacy (≤ t colluders learn nothing) — one parameter, two opposing guarantees.
  • How differential privacy quantifies leakage that aggregation alone does not stop (the aggregate itself can leak), via clipping bound C, noise multiplier σ, subsampling rate q, and RDP composition over many rounds.
  • Why communication, not compute, is the FL bottleneck, and how compression (quantization, top-k, random masking) and cohort sizing trade bytes against convergence and privacy.

2.2 Historical and Architectural Significance

FL was introduced by McMahan et al. (2017, AISTATS) with FedAvg, motivating on-device training (Gboard) where data cannot be centralized. Bonawitz et al. (2017, CCS) gave Practical Secure Aggregation, the pairwise-masking + double-masking + Shamir protocol this project reconstructs; Bell et al. (2020) scaled it to millions via log-degree communication graphs. Privacy accounting traces to Dwork & Roth (DP foundations), Abadi et al. (2016, CCS) (DP-SGD + moments accountant), and Mironov (2017) (Rényi DP). Optimization variants — FedProx (Li et al. 2020, heterogeneity), FedAdam/FedYogi (Reddi et al. 2020, adaptive server optimization) — and the robustness line — Krum (Blanchard et al. 2017), trimmed-mean/median (Yin et al. 2018) — round out the field; Kairouz et al. (2019/2021) survey the open problems. The attack literature (Shokri et al. 2017 membership inference; Zhu et al. 2019 deep leakage from gradients) is why SecAgg + DP exist. FL + SecAgg now underpins mobile keyboard prediction, health analytics, and cross-silo finance. Rebuilding it demystifies "private collaborative learning" into concrete optimization (FedAvg), cryptography (masking + sharing), and privacy calculus (DP accounting).

2.3 Engineering Muscles Developed

  • Designing a round-based distributed protocol as an explicit state machine with partial participation, deadlines, and dropout handling.
  • Reasoning about information leakage at every boundary and encoding it as invariants (what the server sees, what each share reveals).
  • Implementing cryptographic primitives correctly (DH, PRG, Shamir) and composing them so masks cancel and thresholds hold.
  • Translating a privacy budget into concrete hyperparameters (C, σ, q, rounds) via RDP accounting — and never overspending it.
  • Decomposing FL cost into communication (bytes × rounds) and engineering compression/cohorting against it.
  • Building deterministic, replayable multi-party simulations with injectable dropout for debugging a distributed privacy protocol.

2.4 Production Engineering Concepts Exercised

  • Reproducible seeded transcripts for tests vs CSPRNG in real runs — and never confusing the two (a seeded mask is catastrophic in prod).
  • Communication accounting (bytes/round per client, uplink/downlink) as first-class telemetry — the real FL cost metric.
  • Privacy-budget consumption as a monitored, exhaustible resource with a hard stop (refuse to start a round that would overspend ε).
  • Graceful, loud failure on malformed updates, mask/share mismatch, sub-threshold survival, quantization overflow, and budget exhaustion.
  • A clean trust boundary: the server's view is auditable and the simulator can assert "view reveals only the aggregate" (semi-honest).
  • Straggler/dropout tolerance as a designed property, not an afterthought — the SecAgg protocol is built around it.

2.6 Calibration Value

After this project, "private federated training" becomes a transparent pipeline: partition non-IID data → select a cohort → broadcast the global model → clients train locally and clip → mask updates (pairwise + self) → server sums masked updates → reconstruct only the survivors' self-masks and droppers' pairwise masks → unmask the aggregate → (optionally) the aggregate already carries DP noise → apply FedAvg/FedAdam → version the new global model → charge the privacy ledger. The engineer can quantify a campaign's cost (bytes × rounds × cohort), explain why masks cancel and where the threshold t bites, calibrate σ to a target ε, predict convergence degradation under non-IID α and DP noise, and debug a wrong aggregate by replaying a seeded transcript and inspecting each client's masked contribution.

What Mastery Looks Like — finishing this blueprint means you can:

  • Design and audit a pairwise-masking secure aggregation protocol from first principles, explaining why masks cancel, where the threshold t bites, and what the consistency check prevents (Phase 5, Phase 6, Phase 7).
  • Calibrate (C, σ, q, T) for a target (ε, δ) using RDP composition and subsampling amplification, and read the privacy ledger as a hard contract rather than a suggestion (Phase 8, Phase 9).
  • Explain the SecAgg–robustness tension to a skeptical reviewer: which rules require peeking, what is left under SecAgg, and how ZK norm proofs would resolve it (Phase 10).
  • Implement Shamir(t,n) dropout recovery correctly — reconstructing only one of {b_u, s_u^{SK}} per client — and demonstrate why getting both would unmask an individual (Phase 6).
  • Architect a full FL round lifecycle as an explicit FSM with partial participation, deadlines, and straggler policy, and wire it to a gRPC/protobuf transport layer with measurable byte/round accounting (Phase 2, Phase 4).
  • Run and interpret a non-IID convergence experiment, explaining how Dirichlet(α) heterogeneity, FedProx µ, and DP noise σ interact to set a convergence floor (Phase 3, Phase 8, Phase 11).
  • Operate a live private-FL campaign: read the privacy burn-down, triage a dropout storm via telemetry, and know exactly which runbook applies to a sub-threshold abort (Phase 12, Phase 13).
  • Contrast this design against TFF, Flower, NVIDIA FLARE, FATE, and PySyft, naming the one decision each made differently and the regime where this design wins and where each alternative does (Phase 7).

3.2 Subsystem Descriptions

fl_server (coordinator) — Owns the round lifecycle and is the only globally-stateful component. Holds the registry of available clients, the global model store keyed by a monotonic version, and the round FSM SELECT → BROADCAST → LOCAL-TRAIN → COLLECT → AGGREGATE → UPDATE. Each round it samples a cohort (uniform or importance), broadcasts the current model + a round config (SecAgg keys, DP params, deadline), waits for masked updates until a deadline, enforces survival thresholds (≥ t clients must remain to unmask and to preserve privacy), drives SecAgg unmasking, applies the aggregation rule, and commits a new model version. It never sees an individual cleartext update under SecAgg; it sees only the aggregate. Straggler policy (wait/drop/over-provision the cohort) and partial-participation bookkeeping live here. The server is the trust-boundary apex: semi-honest by assumption, audited by the simulator.

fl_client (trainer) — A participant: pins a global-model version, runs local SGD/Adam over its private shard for E epochs, produces a weight-delta Δ_u = w_local − w_global (or a raw gradient), optionally applies per-example L2 clipping (DP), quantizes Δ_u into the modular ring Z_R^m, then under SecAgg computes its masked input y_u and the Shamir shares of its self-mask seed b_u and DH mask-seed secret key s_u^{SK}. It is the only place raw data and raw updates exist; everything it sends is either masked, aggregated, or a share encrypted to a peer. A client may drop at any round; the protocol tolerates it.

fl_aggregate — Combines client updates into a global-model step. FedAvg: sample-count-weighted mean w_{t+1} = Σ_u (n_u/N) w_u (equivalently the server applies the weighted-mean delta). FedProx adds a proximal term (μ/2)‖w−w_global‖² to each client objective to stabilize non-IID/straggler updates. FedAdam/FedYogi treat the aggregated delta as a "pseudo-gradient" and apply a server-side adaptive optimizer (first/second-moment accumulators) for faster, more robust convergence. Under SecAgg the aggregate arrives as a single unmasked sum of n_u·w_u and a sum of n_u, so the weighting is computed on already-summed quantities. Tracks convergence (loss/accuracy trend, update-norm) for stopping.

fl_secagg — The privacy core. Implements pairwise masking (Bonawitz): for each cohort pair (u,v) a shared seed s_{u,v}=KA(s_u^{SK},s_v^{PK}) is PRG-expanded into a mask vector; client u adds +PRG(s_{u,v}) for v>u and −PRG(s_{u,v}) for v<u, so the pairwise terms cancel in Σ_u y_u. Double-masking adds a per-client self-mask PRG(b_u) so a slow-but-not-dropped client is still protected. Shamir(t,n) sharing (from fl_crypto) lets the server reconstruct dropped clients' pairwise seeds (to cancel dangling masks) and surviving clients' self-masks (to remove them) — guaranteeing it never gets both for one client (I-secagg). Orchestrates the 4-round protocol and the consistency check. Pure protocol logic over fl_crypto + fl_transport.

fl_crypto — The cryptographic + randomness boundary. SecureRng wraps a CSPRNG (os.urandom/ChaCha20) for all security-relevant randomness in real runs; TranscriptRng is a seedable deterministic generator used only in tests (production refuses a seed). Provides X25519 Diffie–Hellman key agreement for mask seeds and share-encryption keys, Ed25519 signatures for the consistency check, an AES-CTR/ChaCha20 PRG that expands a 32-byte seed into a uniform vector in Z_R^m, modular vector arithmetic over Z_R, Shamir(t,n) secret sharing + Lagrange reconstruction (sibling to 379), and a domain-separated KDF so seeds for distinct purposes never collide. Single auditable faucet for all randomness and keys.

fl_dp — Differential privacy. Per-example L2 clipping to bound sensitivity to C (ḡ = g·min(1, C/‖g‖₂)), the Gaussian mechanism adding N(0, σ²C²I) to the sum, DP-SGD (clip-then-noise per minibatch, Abadi 2016), and the client-level variant (clip the whole client delta, noise the aggregate). Distinguishes central DP (trusted aggregator adds noise) from local DP (each client adds noise) and provides the distributed-noise-under-mask helper: each client adds a share of the Gaussian so that, after SecAgg unmasking, the aggregate carries the correct total noise without any single trusted noiser. Emits the per-round sensitivity + σ used, consumed by fl_accountant.

fl_accountant — Privacy accounting. Computes Rényi DP of the (subsampled) Gaussian mechanism — Gaussian is (α, α/(2σ²))-RDP; composition over T rounds is additive in RDP; subsampling amplification (cohort rate q) is handled via the subsampled-Gaussian RDP bound (moments accountant, Abadi/Mironov/Wang). Converts RDP → (ε,δ) via ε = min_α RDP(α) + log(1/δ)/(α−1), maintains a privacy-budget ledger (ε spent vs target), and calibrates the noise multiplier σ to hit a target ε for a given (q, T, δ). The server refuses to start a round that would overspend the budget (I-budget).

fl_robust — Robust aggregation against poisoned/Byzantine updates: Krum/Multi-Krum (pick the update(s) closest to their nearest neighbors), coordinate-wise median and trimmed mean, and norm bounding/clipping of updates plus simple anomaly detection. Crucially, these require inspecting individual updates, which SecAgg forbids — the subsystem exposes this tension explicitly: it runs fully in cleartext-aggregation mode, and under SecAgg only norm-bounding-compatible variants (enforced via deferred ZK/verifiable bounds or a secure sketch) are available. Mitigations are sketched and cross-linked to 392/92; full robust-under-SecAgg is deferred.

fl_eval — Federated evaluation + heterogeneity. Runs the federated evaluation protocol (broadcast model, clients report local metrics on held-out shards, server aggregates weighted + reports the worst-k client metrics — a fairness signal under non-IID). Handles client sampling under heterogeneity and personalization: local fine-tuning of the global model and FedPer (shared base layers + per-client personalization heads). Produces the metrics consumed by the convergence dashboard.

fl_transport — The communication abstraction and cost meter. A Transport interface offers typed send/recv/broadcast between server and clients; an in-process implementation backs the simulator, and a gRPC/protobuf implementation frames length-delimited, chunked model/update payloads over TCP (optional TLS). Compression codecs (uniform + stochastic quantization, top-k sparsification, random masking) reduce uplink/downlink bytes. Every send increments byte/round accounting per client and direction — communication is the dominant FL cost and is first-class telemetry. No protocol semantics beyond framing + accounting.

fl_tensor — The numerics substrate. Tensor wraps a NumPy ndarray with a minimal reverse-mode autograd (backward() over add/matmul/relu/softmax-xent) — just enough to train MLPs/CNNs/a small Transformer head (cross-link 112). ModelState is the canonical parameter dict (ordered name→array) with init/clone/axpy, fixed-point quantize/dequantize to/from Z_R (the masking ring), and deterministic byte (de)serialization (fixed dtype/shape/endianness) so every party agrees on the wire layout of a model.

fl_data — Data partitioning + loading. Holds dataset shards and a Partitioner producing IID, Dirichlet(α) non-IID (lower α = more skew), and pathological by-label splits across clients; a LocalLoader iterates epochs/batches with a per-client shuffle seed; exposes per-client sample counts n_u for FedAvg weighting. The source of controlled heterogeneity for convergence experiments.

fl_telemetry — Observability. Emits per-round metrics (loss/accuracy, update-norm, cohort size, dropout count, round wall-time), convergence dashboard data, dropout-rate + cohort-size telemetry, privacy-budget consumption (ε spent per round, cumulative), straggler/latency distributions, structured logs (never plaintext updates), and tracing spans per round/phase/client (cross-link 132). The operator's window into a campaign.

fl_cli — Operator surface. Subcommands launch the server or a client, run the in-process simulator with a chosen client count/non-IID spec/dropout rate, benchmark kernels, or run the accountant offline (σ↔ε calibration). Configures cohort size, rounds, SecAgg/DP toggles, and a seed for deterministic test transcripts. Single-campaign UX.

6. Design Principles

P1. Data Never Leaves; Only Updates Move; Under SecAgg, Only the Aggregate

Raw client data is never transmitted; clients send model updates, and under SecAgg the server only ever observes Σ_u x_u, never an individual x_u. Tradeoff: more rounds + communication than centralized training. Violation: logging or persisting a single cleartext update defeats the entire premise and is a privacy breach (P8, I8).

P2. The Randomness Faucet Is Single, Typed, and Auditable

All security-relevant randomness (mask seeds b_u, DH keys, DP noise, Shamir polynomials) flows through fl_crypto::SecureRng; tests use TranscriptRng (seeded) and production refuses a seeded RNG. Tradeoff: indirection. Violation: an ad-hoc numpy.random for a mask makes a real run insecure (predictable masks → unmaskable) while tests pass (I7).

P3. SecAgg Privacy Means the Server's View Is Simulatable from the Aggregate

For any coalition of the server + ≤ t clients, the joint view must be simulatable given only the final aggregate and the colluders' own inputs. Tradeoff: extra self-masking/sharing steps that look redundant. Violation: revealing a per-client masked value without the protective self-mask (single survivor case) leaks that client's update (P5, I2).

P4. Masks Cancel Only in the Exact Sum — One Quantization, One Ring, One Ordering

Pairwise masks cancel iff every party uses the identical ring Z_R, identical quantization, identical client ordering for the ± sign, and the identical surviving set. Tradeoff: rigid agreement on encoding. Violation: one client quantizing differently, or disagreeing on u<v, leaves a residual mask and corrupts the aggregate silently (I1, I6, I15).

P5. Double-Masking Resolves the Dropped-vs-Slow Ambiguity

Each client adds a self-mask PRG(b_u) on top of pairwise masks. A client whose y_u arrived but who the server claims dropped cannot be unmasked, because removing its pairwise masks still leaves PRG(b_u). Tradeoff: an extra seed + extra shares. Violation: omitting the self-mask lets a server that lies about a slow client's status recover that client's update (I2, I9).

P6. The Threshold t Bounds Both Correctness and Privacy

Shamir (t,n): reconstruction needs ≥ t+1 shares (correctness — must survive enough to unmask), while ≤ t colluders learn nothing (privacy). One parameter, two opposing pressures. Tradeoff: t too low → weak privacy; t too high → fragile to dropout. Violation: setting t≥cohort makes the round un-completable; t=0 gives no privacy (I3, I4).

P7. Round Discipline Is Explicit and Enforced

SecAgg is exactly four rounds with named messages; no party advances past round r until all round-r messages arrive or the deadline fires, and survival thresholds are checked at each transition. Tradeoff: explicit barriers + a state machine, not fire-and-forget. Violation: consuming round-(r+1) messages early causes desync, wrong unmasking, or a stalled round (I10, P14).

P8. Fail Loud, Before Unmasking Anything

Malformed update, mask/share mismatch, sub-threshold survival, quantization overflow, signature failure, or budget exhaustion are detected and the round aborts before any unmasking. Tradeoff: validation overhead per round. Violation: a half-run unmask may reveal a partial sum over a tiny survivor set, leaking individuals (P3, I4).

P9. Communication Is the Cost Metric, and It Is Measured

Uplink/downlink bytes and round count per client are first-class telemetry; the system reports them and compression targets them. Tradeoff: accounting hooks in transport. Violation: optimizing local-training FLOPs while ignoring a chatty protocol or uncompressed model misses the real FL bottleneck (P1, latency-bound rounds).

P10. The Privacy Budget Is an Exhaustible Resource with a Hard Stop

Cumulative (ε,δ) is tracked in a ledger; the server refuses to start a round that would exceed the target ε. Tradeoff: campaigns end when the budget does, not when accuracy plateaus. Violation: running "a few more rounds" silently overspends ε and breaks the stated privacy guarantee (I13).

P11. DP and SecAgg Are Complementary, Not Substitutes

SecAgg hides individual updates from the server; DP bounds what the aggregate (which the server does see) leaks about any record. Tradeoff: both cost (comm + accuracy). Violation: treating SecAgg as "privacy done" ignores that the aggregate can still leak (membership/reconstruction), and treating DP as "privacy done" ignores that the server sees individual updates without SecAgg.

P12. Robustness and SecAgg Are in Tension; Never Pretend Otherwise

Byzantine-robust rules (Krum/median/trimmed-mean) need to inspect individual updates, which SecAgg forbids. Tradeoff: pick robust-cleartext OR private-SecAgg, unless using deferred ZK/secure-sketch bounds. Violation: silently running a robust rule "under SecAgg" either breaks privacy (it peeked) or is a no-op (it didn't), misleading operators (Phase 10).

P13. Determinism in Tests, Never in Production Security

Seeded transcripts make tests replayable and protocol bugs reproducible; the same seed in a real run makes masks/noise predictable — catastrophic. Build/config enforce the split (P2). Violation: shipping the test RNG (I7).

P14. Message and Round Types Are Exhaustive

Round messages, dropout statuses, and aggregation rules are closed enums matched exhaustively, so adding a round or a status forces every handler to address it. Tradeoff: more match arms. Violation: a catch-all arm hides an unhandled (possibly privacy-relevant) protocol state (P7).

8.2 The Federated Round Model + FedAvg

A campaign runs FL rounds t=0,1,…. Each round, with global weights w_t:

SELECT       : server samples cohort C_t (size m_c) from the pool (rate q = m_c / N)
BROADCAST    : send w_t (+ round config) to every u ∈ C_t        (downlink)
LOCAL-TRAIN  : each u runs E epochs SGD/Adam on its shard -> w_u ; Δ_u = w_u − w_t
COLLECT      : clients upload Δ_u (masked under SecAgg) until the deadline -> U_t
AGGREGATE    : combine {Δ_u} via the aggregation rule
UPDATE       : w_{t+1} = w_t + (server step)      ; version += 1

FedAvg (McMahan 2017), sample-count weighted with n = Σ_{u∈U_t} n_u:

w_{t+1} = Σ_{u∈U_t} (n_u / n) · w_u            (model-averaging form)
        = w_t + Σ_{u∈U_t} (n_u / n) · Δ_u      (delta form; equivalent)

FedProx (Li 2020): each client minimizes F_u(w) + (μ/2)‖w − w_t‖² (proximal term curbs client drift under non-IID / variable local epochs). FedAdam/FedYogi (Reddi 2020): treat the aggregated delta Δ̄_t = Σ (n_u/n) Δ_u as a pseudo-gradient and apply a server-side adaptive optimizer:

m_t = β₁ m_{t-1} + (1−β₁) Δ̄_t
v_t = β₂ v_{t-1} + (1−β₂) Δ̄_t²            (FedYogi: v_t = v_{t-1} − (1−β₂)Δ̄_t² sign(v_{t-1}−Δ̄_t²))
w_{t+1} = w_t + η · m_t / (√v_t + τ)

Under SecAgg the server receives only Σ_{u∈U_t} n_u·Δ_u and Σ_{u∈U_t} n_u, from which it forms Δ̄_t — never an individual Δ_u (P1).

8.3 Update Quantization to the Ring Z_R

Masking is modular, so float updates are mapped to Z_R^m. With per-coordinate range [−B, B] and b-bit precision:

quantize(x)   = round( (clip(x,−B,B) + B) / (2B) · (R−1) )    ∈ {0,…,R−1}   (stochastic-round option)
dequantize(q) = q / (R−1) · 2B − B

R must satisfy R > |U_t| · q_max so the true sum does not wrap (I6); the server dequantizes the summed integer back to a float aggregate. Stochastic rounding makes quantization unbiased (E[quantize]=x), important so FedAvg stays unbiased. The weighting n_u is folded in by sending quantize(n_u·Δ_u) and separately summing n_u (itself masked), or by a fixed-point scale agreed in the round config (P4, I15).

8.4 Pairwise Masking (Bonawitz Core)

For cohort C with a fixed total order on client ids, every pair {u,v} (u<v) shares a seed s_{u,v} = KA(s_u^{SK}, s_v^{PK}) = KA(s_v^{SK}, s_u^{PK}) (X25519, I5), expanded by a PRG into a mask vector PRG(s_{u,v}) ∈ Z_R^m. Client u's pairwise-masked input:

y_u = x_u  + Σ_{v∈C, v>u} PRG(s_{u,v})  − Σ_{v∈C, v<u} PRG(s_{v,u})   (mod R)

Each unordered pair contributes +PRG(s_{u,v}) to the lower-id client and −PRG(s_{u,v}) to the higher-id client (sign by ordering). Summing over the full cohort:

Σ_{u∈C} y_u = Σ_{u∈C} x_u + Σ_{u<v} ( PRG(s_{u,v}) − PRG(s_{u,v}) ) = Σ_{u∈C} x_u   (mod R)

The pairwise terms telescope to zero — but only over the exact set that contributed (P4, I1). If a client drops after others have folded its pairwise masks, those masks do not cancel: hence dropout recovery (§8.5).

8.5 Double-Masking + Shamir Dropout Recovery

Add a per-client self-mask: y_u = x_u + PRG(b_u) + (pairwise terms) (mod R). Each client t-of-|C| Shamir-shares both b_u and its pairwise secret key s_u^{SK} to the cohort (shares encrypted to recipients, I16). After collection the server knows the surviving set U and dropped set D = C\U. To recover Σ_{u∈U} x_u:

Σ_{u∈U} y_u = Σ_{u∈U} x_u + Σ_{u∈U} PRG(b_u)
            + Σ_{u∈U} [ Σ_{v>u} PRG(s_{u,v}) − Σ_{v<u} PRG(s_{v,u}) ]

The pairwise terms among survivors cancel; the dangling terms are those between a survivor and a dropped client. So the server must:

  • reconstruct b_u for every surviving u∈U → remove Σ_{u∈U} PRG(b_u);
  • reconstruct s_w^{SK} for every dropped w∈D → recompute and subtract the dangling pairwise masks PRG(s_{w,u}) between each dropped w and each survivor u. Then Σ_{u∈U} x_u remains. The crux (I2): for any single client the server learns exactly one of {b_u, s_u^{SK}}:
u survived  -> server gets shares of b_u (self-mask), NOT s_u^{SK}  -> pairwise masks still hide x_u individually
u dropped   -> server gets shares of s_u^{SK} (pairwise),NOT b_u    -> but x_u was never submitted; self-mask irrelevant

If the server could obtain both for the same client it could compute all of that client's masks and unmask y_u alone — forbidden by the protocol (only one kind of share is requested per client per round) and by the threshold t (≤ t colluders cannot reconstruct anyway). This is exactly why double-masking resolves the dropped-vs-slow ambiguity: a client whose y_u arrived but whom the server falsely declares dropped still has PRG(b_u) protecting it (the server only got s_u^{SK} shares, not b_u), so it cannot be unmasked (P5).

8.6 The 4-Round SecAgg Protocol

Roles: one server (routes + sums, never trusted with cleartext), |C| clients. Security parameter κ=128. Sequence (--> to server, <-- from server / broadcast):

Round 0  AdvertiseKeys
  client u: gen DH pairs (s_u^PK,s_u^SK)=mask-seed, (c_u^PK,c_u^SK)=share-enc ; sign both with Ed25519
            --> (s_u^PK, c_u^PK, sig_u)
  server : collect ≥ t+1 keys ; assign cohort order ; broadcast all {(v, s_v^PK, c_v^PK, sig_v)}
  client : verify sigs ; abort if < t+1 keys                                  (I4, I9)

Round 1  ShareKeys
  client u: sample b_u ; compute t-of-|C| Shamir shares of b_u and of s_u^SK

            --> { enc_share(u->v) for all v in cohort }
  server : route each enc_share(u->v) to v ; require ≥ t+1 senders else abort  (I4)

8.7 Differential Privacy Mechanism

Per-example L2 clipping (sensitivity bound): ḡ_i = g_i / max(1, ‖g_i‖₂ / C) so ‖ḡ_i‖₂ ≤ C (I14). Gaussian mechanism on the clipped sum (batch B):

M = Σ_i ḡ_i + N(0, σ² C² I)         (noise std = σ·C ;  σ = noise multiplier)
update = M / B                       (DP-SGD step; Abadi 2016)

The L2-sensitivity of Σ ḡ_i to one record is C; the Gaussian mechanism is (ε,δ)-DP when σ ≥ √(2 ln(1.25/δ)) / ε (classic bound, ε<1; the analytic Gaussian of Balle–Wang is tighter and used in practice). Client-level DP (Geyer 2017): clip the whole client delta Δ_u to norm C and add noise to the aggregate — protecting client participation, not just one example. Central vs local: central DP adds noise once at a trusted aggregator (least noise for a target ε); local DP makes each client noise its own update (no trusted party, but √m_c× more noise). Distributed DP under the mask: each client adds N(0, σ²C²I / |U|) to its x_u before masking; after SecAgg unmasking the aggregate carries N(0, σ²C²I) total — achieving central-DP-quality noise with no trusted noiser, because the server only ever sees the noised sum (P11). Discrete analogues (the distributed discrete Gaussian) keep noise in Z_R to remain compatible with modular masking.

8.8 Privacy Accounting (RDP / Moments)

Rényi DP: a mechanism is (α, ρ)-RDP if D_α(M(D) ‖ M(D')) ≤ ρ. The Gaussian mechanism with noise multiplier σ is (α, α / (2σ²))-RDP for all α>1. Composition is additive in RDP: T rounds → (α, T·α/(2σ²))-RDP. Subsampling amplification: with cohort/Poisson sampling rate q, the subsampled Gaussian's RDP is bounded by the Mironov–Talwar–Zhang / Wang et al. expression (numerically evaluated per α) — far below T·α/(2σ²) for small q. Conversion RDP→(ε,δ):

ε(δ) = min_{α>1} [ RDP(α) + log(1/δ) / (α − 1) ]

The accountant tabulates RDP at a grid of α (e.g. {2,3,…,64}), accumulates per round, converts to (ε,δ), and calibrates σ to hit a target ε for (q, T, δ) by binary search. The ledger stores (round, q, σ, RDP-vector, ε-so-far); the server consults it before each round (I13, P10).

8.9 Robust Aggregation Rules (and the SecAgg Tension)

Rule Idea Needs individual updates?
Coordinate-wise median per-coordinate median of {Δ_u} yes
Trimmed mean (β) drop top/bottom β fraction per coordinate, average rest yes
Krum pick the update minimizing sum of distances to its n−f−2 nearest yes (pairwise distances)
Multi-Krum average the m best Krum candidates yes
Norm bounding clip each ‖Δ_u‖₂ ≤ M then average clip needs per-update norm
FedAvg (baseline) weighted mean no (sum suffices)

Tension (P12): every robust rule except plain averaging requires the server to see or compare individual updates, which SecAgg explicitly hides. Options: (a) run robust in cleartext-aggregation mode (no SecAgg) — robust but not private; (b) run SecAgg (private) with only norm-bounding enforced by clients + a verifiable/ZK norm proof (deferred, cross-link 92/392) so the server trusts each ‖Δ_u‖≤M without seeing Δ_u; (c) a secure sketch / multi-round secure median (expensive MPC, cross-link 392). The blueprint ships (a) and (b)-without-ZK (client-side norm clip, server trusts), and defers verifiable robust-under-SecAgg.

8.10 Worked Example — Secure Sum of 3 Vectors with 1 Dropout

Cohort C={1,2,3}, t=1 (need ≥2 shares). Vectors x1,x2,x3 ∈ Z_R^m. Order 1<2<3.
R2 masked inputs (with self masks b1,b2,b3):
  y1 = x1 + PRG(b1) + PRG(s12) + PRG(s13)
  y2 = x2 + PRG(b2) − PRG(s12) + PRG(s23)
  y3 = x3 + PRG(b3) − PRG(s13) − PRG(s23)
Suppose client 3 DROPS after R1 (its shares exist) but never sends y3. Survivors U2={1,2}.
  Σ_{U2} y_u = x1+x2 + PRG(b1)+PRG(b2) + (PRG(s12)−PRG(s12)) + PRG(s13) + PRG(s23)
            = x1+x2 + PRG(b1)+PRG(b2) + PRG(s13)+PRG(s23)        // s12 cancels; s13,s23 dangle
R3: server reconstructs b1,b2 (survivors' self-masks) and s3^SK (dropped client's key).
  from s3^SK: recompute PRG(s13)=PRG(KA(s3^SK,s1^PK)), PRG(s23)=PRG(KA(s3^SK,s2^PK))
  z = Σ_{U2} y_u − PRG(b1) − PRG(b2) − PRG(s13) − PRG(s23) = x1 + x2  ✓
Server learns x1+x2 only — NOT x1 or x2 (each still hid behind b and the cancelled s12) (I2).

12. Phase 1 — Tensor + local-training substrate

12.1 Objectives

Build fl_tensor (NumPy-backed Tensor + minimal reverse-mode autograd, ModelState, fixed-point quantize/dequantize to Z_R, deterministic byte codec), fl_data (shards, IID/non-IID partitioner, LocalLoader, n_u), and fl_client local training (SGD/Adam → weight-delta Δ_u or gradient). Lock the model wire layout (I15, P4) and the randomness faucet usage (P2). This is the numerics foundation everything trains on.

12.2 Detailed Implementation Steps

  • tensor.py/autograd.py: Tensor with requires_grad, ops (add, matmul, relu, softmax-xent), topological backward() accumulating .grad (cross-link 112).
  • nn.py: small MLP/CNN modules + a tiny Transformer head as a ModelState producer; parameter init seeded via SecureRng/TranscriptRng.
  • model_state.py: ModelState (ordered name→array, version), clone, axpy, to_bytes/from_bytes (fixed dtype/shape/endianness, I15).
  • quantize.py: quantize/dequantize to Z_R with stochastic-rounding option (§8.3, I6). (stochastic rounding unbiasedness: §8.3; I6)
  • fl_data/partition.py: Partitioner — IID, Dirichlet(α), pathological by-label; emits per-client index sets + n_u.
  • fl_data/loader.py: LocalLoader — epochs/batches/shuffle with a per-client seed.
  • fl_client/trainer.py: train_local(model,cfg) -> Δ_u; optim.py SGD + Adam; delta vs gradient mode flag. (FedAvg delta form: McMahan et al. AISTATS 2017; P4)

12.3 Deliverable

Train a small model locally on a shard; produce a Δ_u; quantize→dequantize round-trips within tolerance; ModelState serializes byte-identically across processes; pytest packages/fl_tensor packages/fl_data packages/fl_client green.

12.4 Acceptance Criteria

  • Autograd: numerical-gradient check passes (finite-difference vs backward()) with max relative error < 1e-5 on each op (fixture tensor/gradcheck.json).
  • Local training reduces toy-dataset loss by ≥ 50% over 20 epochs at lr=0.01 (sanity convergence).
  • quantize/dequantize unbiased under stochastic rounding: mean error < 1e-3 over a 10⁴-element vector; deterministic under fixed seed.
  • to_bytes→from_bytes is identity for 100% of round-trips; byte layout stable across runs/machines (I15).
  • Dirichlet(α=0.1) partition reproduces the same split for a fixed seed; Σ n_u equals the dataset size exactly.

12.6 Pitfalls

  • Float nondeterminism (BLAS thread order, fma) breaks byte-exact model agreement; pin dtype, avoid order-dependent reductions where wire-exactness is required (I15).
  • Quantization without stochastic rounding biases the FedAvg mean (systematic drift) — keep it unbiased (§8.3).
  • Sharing one shuffle seed across clients correlates "independent" local randomness (P2).
  • Delta vs gradient confusion: mixing Δ_u (post-E-epochs) with a single gradient changes FedAvg semantics; pick one per campaign and record it.

12.7 Performance Concerns

  • matmul/conv are the training hot path; rely on NumPy BLAS; batch where possible. Mask-relevant: quantization is O(m) vectorized.
  • to_bytes should be a single contiguous buffer copy (no per-parameter Python loop).

12.8 Edge Cases

  • Empty shard (n_u=0) → client excluded from cohorts. Single-parameter model (m=1). NaN/Inf in a local update → reject before upload. Quantization clip range smaller than update spread → saturated (logged).

12.9 Failure Analysis

A wrong autograd or codec corrupts every downstream update and aggregate. Detection: gradcheck + codec fixtures; later, mask-cancellation tests. Blast radius: the whole campaign. Containment: fl_tensor is the most-tested foundation; mask-inspect (test-only) dumps a model in cleartext.

12.10 Operational Notes

structlog records per-client local-loss + update-norm (not the update itself, P1). Runbook "wrong aggregate" starts here: verify codec + quantization range + delta/gradient mode. Seeded init logged; prod refuses a fixed init seed where it would weaken privacy.

13. Phase 2 — Server coordinator + round orchestration

13.1 Objectives

Build fl_server: client registration, cohort sampling (uniform/importance, rate q), the global-model store with monotonic version (I11), the round lifecycle FSM (SELECT→BROADCAST→LOCAL-TRAIN→COLLECT→AGGREGATE→UPDATE, P7, P14), per-round deadlines, straggler policy, and partial-participation bookkeeping. No privacy yet — aggregation is cleartext sum here; SecAgg layers on in Phase 5–7.

13.2 Detailed Implementation Steps

  • server.py: Server holding model: ModelState, registry, config; run_round()/run_campaign().
  • cohort.py: uniform + importance sampling without replacement; rate q; min/over-provisioned cohort to absorb dropout. (cohort sampling rate q for subsampling amplification: §8.8; ADR-17)
  • model_store.py: versioned store; version += 1 on commit; pin-and-broadcast current version (I11).
  • round_fsm.py: explicit RoundState machine with guards; deadline timer per round; barrier at COLLECT (P7, I10). (round discipline FSM: P7; Bonawitz et al. CCS 2017 §4 round ordering)
  • straggler.py: policies — WAIT (until deadline), DROP (past deadline), OVER_PROVISION (select extra to hit a target survivor count).
  • Reject stale-version updates at COLLECT (I11); count survivors/dropped → RoundReport.

13.3 Deliverable

Server runs N cleartext rounds against simulated clients: selects a cohort, broadcasts the model, collects updates until a deadline, averages, bumps version; RoundReport emitted per round; pytest packages/fl_server green.

13.4 Acceptance Criteria

  • Cohort sampling hits rate q (size = round(qN)); reproducible under a fixed seed; no duplicates.
  • FSM advances only on guard satisfaction; never AGGREGATEs before the deadline/barrier (P7, I10).
  • Stale-version updates rejected (I11); survivor/dropped counts correct under injected dropout.
  • run_campaign stops at the round limit; RoundReports show monotonic version.

14. Phase 3 — FedAvg aggregation

14.1 Objectives

Build fl_aggregate: FedAvg sample-count-weighted averaging (McMahan 2017, I12), FedProx (proximal μ), FedAdam/FedYogi server-side adaptive optimizers (Reddi 2020), convergence tracking, and the AggregationRule interface. The server now produces a principled global step from collected updates.

14.2 Detailed Implementation Steps

  • rule.py: AggregationRule protocol — aggregate(summed, n_total, server_state) -> ModelState.
  • fedavg.py: weighted mean w_{t+1} = Σ (n_u/n) w_u / delta form w_t + Σ(n_u/n)Δ_u; assert Σ n_u/n = 1 (I12). (FedAvg: McMahan et al. AISTATS 2017; I12)
  • fedprox.py: client-side proximal term (μ/2)‖w−w_t‖² (in fl_client objective) + identical server averaging.
  • fedopt.py: FedAdam/FedYogi — maintain server m_t,v_t; w_{t+1}=w_t+η m_t/(√v_t+τ) (§8.2). (adaptive server optimization: Reddi et al. ICLR 2021; P9)
  • convergence.py: track loss/accuracy trend + aggregate update-norm; early-stop signal.
  • Wire weighting to SecAgg-friendly form: aggregate over Σ n_u·Δ_u and Σ n_u (both summed quantities), divide post-sum (Phase 5 makes these the masked aggregates).

14.3 Deliverable

FedAvg/FedProx/FedAdam selectable; a campaign converges on a toy non-IID task; convergence curve recorded; pytest packages/fl_aggregate green.

14.4 Acceptance Criteria

  • FedAvg equals the exact sample-weighted mean (vs a centralized reference on the same data) within float tolerance (I12).
  • FedProx with μ>0 reduces client-drift variance vs μ=0 on a skewed split.
  • FedAdam converges in ≤ FedAvg rounds-to-target on the benchmark task (or matches, never diverges).
  • Weight-sum assertion Σ n_u/n = 1 holds every round.

  • FedAdam state must persist across rounds on the server; resetting it each round kills adaptivity.

15.1 Objectives

Communication is the FL bottleneck; this phase makes it measurable and cheap.

  • grpc_transport.py: length-delimited streaming; per-message size cap (anti-DoS); optional TLS.
  • chunk.py: split/reassemble models > 4 MiB into ordered chunks; checksum per chunk.
  • compress.py: Compressor codecs — uniform/stochastic quantization (b bits), top-k sparsification (indices+values), random masking (seeded subsampling); error-feedback hook for sparsification. (quantization for SecAgg ring compatibility: P4; I6; ADR-6)

  • CommStats counts bytes/rounds per client exactly (0 discrepancy vs a manual byte count, P9).
  • Top-k(k=10%) reduces uplink bytes to ≈ 0.1× baseline with accuracy loss < 1% vs uncompressed, recovered within 5 rounds by error feedback.
  • Model > 4 MiB → chunked per the §4.1 threshold; a message exceeding the configured per-message size cap → rejected (Malformed); chunk reassembly is order-independent + checksum-verified.

15.6 Pitfalls

15.7 Performance Concerns

  • Serialization of an m-vector dominates per-message CPU; use contiguous buffers + protobuf bytes, not repeated scalars.
  • Compression trades CPU for bytes; on a WAN, bytes win (P9). Coalesce same-round messages.
  • gRPC streaming amortizes connection overhead across chunks.

15.8 Edge Cases

  • Model exactly at the chunk boundary. Zero-byte update. Client disconnects mid-chunk → Closed → treat as dropped (Phase 6). Compression of an all-zero vector (top-k empty). TLS handshake failure → abort connection.

15.9 Failure Analysis

A codec/chunk bug corrupts updates → wrong aggregate; a stats bug hides the real cost. Detection: parity + chunk-reassemble fixtures. Blast radius: the round. Recovery: re-request the chunk; comm-report shows per-client byte/round breakdown; transcript-diff on a seeded run.

15.10 Operational Notes

tracing spans per message + per round emit byte counts → comm-budget telemetry (P9). gRPC connection lifecycle logged. Runbook "slow round" → check uplink bytes, compression ratio, chunking, RTT. Comm budget asserted in the simulator (refuse if a round exceeds its byte/round bound).

16. Phase 5 — Pairwise masking (secure-aggregation core)

16.1 Objectives

Build the fl_crypto primitives (SecureRng/TranscriptRng, X25519 DH, AES-CTR/ChaCha20 PRG → Z_R^m, ring add/sub, KDF) and fl_secagg pairwise masking (Bonawitz core): per-pair seed s_{u,v}=KA(s_u^{SK},s_v^{PK}), PRG-expanded mask, and the masked input y_u whose pairwise terms cancel in the exact sum (§8.4, I1, I5, P2, P4). Single-round secure sum with no dropout yet.

16.2 Detailed Implementation Steps

  • fl_crypto/rng.py: SecureRng over os.urandom/ChaCha20; TranscriptRng seeded; prod refuses a seed (I7); domain-separated kdf.
  • fl_crypto/dh.py: X25519 keypair + agree; assert symmetry KA(sk_u,pk_v)=KA(sk_v,pk_u) (I5). (Diffie–Hellman mask seeds: RFC 7748; Bonawitz et al. CCS 2017 §3; I5)
  • fl_crypto/prg.py: prg_expand(seed,R,m) — AES-CTR keystream → uniform Z_R^m (rejection/modular-reduce to avoid bias).
  • fl_crypto/ring.py: vectorized ring_add/ring_sub mod R (power-of-two or prime).
  • fl_secagg/mask.py: pairwise_mask(u,cohort,sk_u,pubkeys,R,m) = Σ_{v>u}PRG(s_uv) − Σ_{v<u}PRG(s_uv); sign by id order (P4). (pairwise masking telescoping sum: Bonawitz et al. CCS 2017 §4; P4; I1)
  • fl_secagg/mask.py: mask_input(x_u,...) = ring_add(x_u, pairwise_mask, R) (self-mask added in Phase 6).
  • Server secure_sum: Σ_u y_u mod R → pairwise terms telescope → Σ x_u (I1); dequantize.

16.3 Deliverable

N clients each mask a quantized vector; the server sums masked inputs and recovers the exact vector sum (no dropout); pytest packages/fl_crypto packages/fl_secagg::mask green; examples/secure_sum.py runs.

16.4 Acceptance Criteria

  • Σ_u y_u mod R == Σ_u x_u mod R for a cohort of ≥ 2 with all clients present (I1) — bit-exact vs cleartext sum over 1000 random trials.
  • DH symmetry holds for all pairs (I5); PRG output passes a chi-square goodness-of-fit test for uniformity in Z_R at p > 0.01 (fixture masking/prg_uniform.json).
  • The server's view (the y_us) is statistically independent of any individual x_u given the others: mutual information estimate < 1e-3 bits over 1000 trials (masking hides individuals) — leakage test.
  • Seeded TranscriptRng reproduces bit-identical masks across 2 runs at the same seed; prod_rng refuses a seed 100% of the time (I7).

Fixture Purpose Expected

masking/dh_symmetry.json I5 seeds equal both sides
masking/prg_uniform.json PRG uniform in Z_R

16.6 Pitfalls

  • Sign/order disagreement (u<v convention) leaves a residual ±2·PRG(s_uv) and corrupts the sum (P4, I1) — fix a single canonical ordering.
  • PRG modular bias (mapping a keystream to Z_R by truncation when R∤2^k) skews masks; use rejection sampling or a large reduction.
  • Ring too small → the true sum wraps and the aggregate is garbage (I6); size R from cohort × max-quantized.
  • Reusing a seed across rounds reuses masks → differencing attack reveals updates (P2); fresh keys per round.
  • Using numpy.random for any seed is insecure in prod (I7, P2).

16.7 Performance Concerns

  • Mask expansion is O(cohort × m) per client (a PRG stream per partner) — the SecAgg CPU cost; vectorize with NumPy; target ≥ 10⁷ params/s/core. (A Rust/C PRG extension is the deferred speedup, Phase 12.)
  • Pairwise cost is quadratic in cohort at the client; log-degree communication graphs (Bell 2020) cut it — deferred Phase 13.
  • AES-NI via the cryptography backend makes the PRG keystream cheap.

16.8 Edge Cases

  • Cohort of 1 (no pairwise masks) → y_u=x_u → no privacy; rejected/flagged (needs self-mask + ≥2 clients). Self-pair (u=v) excluded. m=1 scalar masks. x_u=0 (valid). R prime vs power-of-two arithmetic both supported.

16.9 Failure Analysis

A masking/ordering/PRG bug corrupts the aggregate or (worse) fails to hide individuals. Detection: cancel_exact + individual_hidden fixtures. Blast radius: every SecAgg round. Containment: mask-inspect (test-only) opens masks against a seeded transcript; never in prod (P1, P13).

16.10 Operational Notes

tracing tags mask-expansion time + cohort size. No mask seed or y_u-to-x_u mapping is ever logged (P1). Runbook "wrong secure sum" → check ordering, ring size, PRG uniformity, DH symmetry. prod_rng refusal logged loudly (P2, I7).

17. Phase 6 — Dropout recovery via Shamir secret sharing

17.1 Objectives

Add double-masking (per-client self-mask PRG(b_u)) and t-of-n Shamir secret sharing (cross-link 379) of each client's self-mask seed b_u AND its pairwise secret key s_u^{SK}, so the server can reconstruct dropped clients' pairwise masks and surviving clients' self-masks — never both for the same client (§8.5, I2, I3, P5, P6). Shares are encrypted peer-to-peer (I16). Resolves the dropped-vs-slow ambiguity.

17.2 Detailed Implementation Steps

  • fl_crypto/shamir.py: shamir_share(secret,t,n) (random degree-t polynomial, p(0)=secret), shamir_reconstruct (Lagrange, needs ≥ t+1) (I3); arithmetic over Z_R/F_p. (Shamir(t,n) dropout recovery: Bonawitz et al. CCS 2017 §4; cross-link 379; I3)
  • fl_secagg/doublemask.py: sample b_u; self_mask=PRG(b_u); full y_u = x_u + PRG(b_u) + pairwise (mod R) (§8.5). (double-masking dropped-vs-slow resolution: Bonawitz et al. CCS 2017 §4; P5; I2)
  • Share both b_u and s_u^{SK} to the cohort; encrypt each share to recipient under KA(c_u^{SK},c_v^{PK}) (I16) via fl_crypto/sign.py+KDF.
  • fl_secagg/recover.py: given survivors U, dropped D — request b_v shares for v∈U, s_w^{SK} shares for w∈D; reconstruct (≥ t+1); recompute dangling pairwise masks PRG(KA(s_w^{SK},s_u^{PK})); subtract self-masks of survivors + pairwise masks of dropped (§8.5).
  • Enforce the one-kind-per-client rule (I2): a client refuses to return both kinds for any id.

17.3 Deliverable

A secure sum completes correctly with injected dropout: the server recovers Σ_{u∈U} x_u after reconstructing dropped keys + surviving self-masks; pytest packages/fl_crypto::shamir packages/fl_secagg::recover green; examples/secagg_dropout.py runs.

17.4 Acceptance Criteria

  • For cohort=100, t=50: up to 49 dropouts still yield unmask == Σ_{u∈U} x_u bit-exact vs cleartext (I1, §8.10).
  • Shamir: any t+1 of n shares reconstruct 100% of trials; any ≤ t shares are statistically indistinguishable from random (I3, marginal-uniformity test, p > 0.01).
  • For every client in 100 sampled rounds the server obtains exactly one of {b_u, s_u^{SK}} — zero both-kind reconstructions (reconstruction audit, I2).
  • A "slow" client (its y_u present but declared dropped) cannot be unmasked in any of 100 injected-equivocation trials — its self-mask survives (P5).

17.5 Conformance Fixtures

Fixture Purpose Expected
sharing/shamir_threshold.json I3 any t+1 reconstruct
sharing/shamir_privacy.json I3 ≤t shares uniform
protocol/dropout_recover.json §8.5 unmask = Σ_U x_u

17.6 Pitfalls

  • Reconstructing both b_u and s_u^{SK} for a client unmasks it — the single most dangerous bug; enforce one-kind-per-client at the client, not just the server (I2, P5).
  • Lagrange over integers instead of mod the ring/field gives wrong reconstruction; all arithmetic in Z_R/F_p.
  • Off-by-one on the threshold (t vs t+1) silently weakens privacy or breaks reconstruction (I3, P6).
  • Sending shares unencrypted lets the server read them and reconstruct everything (I16) — encrypt peer-to-peer.
  • Pairwise key reconstruction must recompute the dangling masks only (dropped↔survivor), not survivor↔survivor (already cancelled).

17.7 Performance Concerns

  • Sharing is O(cohort) per secret per client; reconstruction is O(t²) naive Lagrange (precompute barycentric weights for O(t)).
  • Recovering dropped pairwise masks is O(|D|×|U|×m) PRG expansions at the server — the dominant recovery cost; bounded by dropout rate.
  • Share storage at the server is O(cohort²) (each client shares to all) — bounded; stream/evict after use.

17.8 Edge Cases

  • Exactly t+1 survivors (minimum) → reconstruction just works; one fewer → abort (I4). Zero dropouts → no dropped-key recovery (only self-masks removed). A client drops during R3 (recovery) → if survivors still ≥ t+1, continue; else abort. Duplicate share x-coordinate → DuplicatePoint.

17.9 Failure Analysis

A reconstruction bug yields a wrong aggregate; a one-kind violation leaks an individual update. Detection: dropout_recover + one_kind_per_client + reconstruction audit. Blast radius: correctness (aggregate) or privacy (one client). Recovery: abort + re-run the round with fresh keys; mask-inspect replays a seeded transcript.

17.10 Operational Notes

tracing tags dropout count + reconstruction time + which kind reconstructed per client (counts only, not values). Runbook "dropout storm" → check survivor count vs t, recovery cost, deadline. The reconstruction audit (one-kind-per-client) runs in conformance every build (I2). Threshold t recorded in RoundConfig (I15).

18. Phase 7 — Secure-aggregation protocol orchestration

18.1 Objectives

Assemble the 4-round SecAgg protocol (R0 AdvertiseKeys → R1 ShareKeys → R2 MaskedInputCollection → R3 Unmasking + ConsistencyCheck, §8.6) end-to-end over fl_transport, with per-round survival thresholds (I4), Ed25519 signatures on keys, a consistency check so a malicious-ish server cannot equivocate about who dropped (I9, P5), and abort conditions that fail loud before any unmasking (P7, P8). Wire SecAgg into the server's COLLECT/AGGREGATE.

18.2 Detailed Implementation Steps

  • fl_secagg/messages.py: closed Message set for R0–R3 (keys+sig, enc-shares, masked input, recon shares + consistency sig) (P14, I15). (4-round protocol: Bonawitz et al. CCS 2017 §4; P14; I10)
  • fl_secagg/protocol.py: SecAggServer.run_round driving the §8.6 state machine; barriers + deadlines per round (I10); survival checks ≥ t+1 at each transition (I4).
  • R0: clients gen (s,c) DH pairs, sign with Ed25519; server collects ≥ t+1, assigns cohort order, broadcasts keys; clients verify sigs.
  • R1: clients Shamir-share b_u + s_u^{SK}, encrypt per recipient (I16); server routes; require ≥ t+1 senders.
  • R2: clients compute y_u; server collects until deadline → U2; require |U2| ≥ t+1.
  • R3: server broadcasts (U2, D2); clients verify |U2|≥t+1, sign hash(U2,D2) (consistency, I9), return one-kind-per-client recon shares; server checks all sigs agree on the same dropout-set hash, reconstructs, unmasks, outputs Σ_{u∈U2} x_u (I1).
  • fl_secagg/consistency.py: dropout-set hashing + signature aggregation/verification. (anti-equivocation consistency check: Bonawitz et al. CCS 2017 Section 4.3; I9; P5)

18.3 Deliverable

A full private FL round: cohort runs R0–R3, server obtains only the aggregate, dropout tolerated, equivocation rejected; pytest packages/fl_secagg green; fl_sim runs a SecAgg campaign with injected dropout.

18.4 Acceptance Criteria

  • For cohort=100, t=50: end-to-end round outputs Σ_{u∈U2} x_u (bit-exact vs cleartext over survivors, I1) across the full 0–49 dropout range.
  • Server view across 100 sampled rounds is simulatable from the aggregate (+ ≤t colluders' inputs) — sim-vs-view audit passes 100% of trials (I8, P3).
  • Equivocation (server tells different clients different dropout sets) → consistency check fails and aborts in 100% of 50 injected trials (I9).
  • Any round with < t+1 survivors at any of the 4 SecAgg sub-rounds → abort with no unmasking, verified across all 4 (I4, P8).

Fixture Purpose Expected

18.6 Pitfalls

  • Skipping the consistency check lets a server learn an individual by telling everyone except the victim that the victim dropped (it would then collect the victim's s^{SK} shares as "dropped" while the victim's y is present) — the self-mask + consistency check together prevent this (P5, I9).
  • Advancing a round on a timeout without rechecking the survival threshold can unmask a tiny set → individual leakage (I4, P8).
  • Reusing DH keys across rounds enables cross-round differencing; fresh keys each round (P2).
  • Not verifying R0 signatures lets the server inject fake public keys (man-in-the-middle on seeds) — verify (I9).
  • Consuming R2 messages before R1 routing completes desyncs share availability (I10, P7).

18.7 Performance Concerns

  • Four sequential rounds × RTT is the latency floor; on a WAN this dominates (P9). Batch all per-client R1 shares into one message.
  • Server reconstruction (R3) is O(|D|×|U|×m + |U|×m) PRG work; the dropout-recovery cost. Parallelize across coordinates.
  • Signature verification is O(cohort) per round; Ed25519 verify is fast but batch where possible.

18.8 Edge Cases

  • Server itself drops/restarts mid-protocol → clients time out → round void (semi-honest: clean abort, no recovery). All survive → R3 reconstructs only self-masks. A client sends a malformed share → treated as that client dropping (excluded from senders). t+1 == cohort → zero dropout tolerance.

18.9 Failure Analysis

A protocol-ordering or consistency bug breaks correctness or privacy. Detection: full_round + equivocation + subthreshold_abort + sim-vs-view audit. Blast radius: a round (correctness) or an individual (privacy). Containment/recovery: abort + re-run with fresh keys; transcript-diff per round message; the privacy audit is blocking in CI.

18.10 Operational Notes

tracing span per round (R0–R3) + per client; structured logs record round transitions, survivor/dropout counts, abort reasons — never y_u or seeds (P1). Runbook "secagg abort" → check survival threshold, signatures, consistency hash, deadlines. The sim asserts "server view == aggregate only" every run (I8). SecAgg on/off is a campaign-level config; off = cleartext sum (Phase 5 path) for robust/debug only.

19. Phase 8 — Differential privacy

19.1 Objectives

Build fl_dp: per-example L2 clipping to bound sensitivity to C (I14), the Gaussian mechanism N(0,σ²C²I), DP-SGD (Abadi 2016), client-level vs example-level DP, central vs local DP, and the distributed-noise-under-mask helper so the aggregate carries central-quality noise with no trusted noiser (§8.7, P11). DP bounds what the (visible) aggregate leaks; SecAgg hides individuals — complementary (P11).

19.2 Detailed Implementation Steps

  • clip.py: clip_l2(g,C) = g / max(1, ‖g‖₂/C); per-example (example-level) and per-client (whole-Δ_u) variants (I14). (DP-SGD per-example clipping: Abadi et al. CCS 2016; I14; P11)
  • gaussian.py: gaussian_noise(shape,σ,C,rng) from SecureRng (never numpy.random, I7); discrete-Gaussian option for Z_R compatibility.
  • dpsgd.py: clip-then-noise per minibatch → (Σ ḡ_i + N(0,σ²C²I))/B (§8.7).
  • client_level.py: clip Δ_u to norm C; noise added to the aggregate (central) or per-client (local).
  • distributed_noise.py: each client adds N(0,σ²C²I/|U|) (or a discrete-Gaussian share) before masking so post-unmask total noise = N(0,σ²C²I) (central-quality, no trusted noiser). (distributed noise under mask for central-quality DP: §8.7; P11; ADR-16)
  • Emit (C, σ, q, sensitivity) per round to fl_accountant (Phase 9).

19.3 Deliverable

A DP-FedAvg campaign: clients clip + (distributed-)noise updates; the aggregate is DP; accuracy/ε tradeoff recorded; pytest packages/fl_dp green; examples/dp_fedavg.py runs.

19.4 Acceptance Criteria

  • Post-clip per-record L2 norm ≤ C for 100% of records, verified over 10⁴ sampled gradients (I14).
  • Aggregate noise distribution matches N(0,σ²C²I): sample mean within 0.01σC of 0, sample variance within 5% of σ²C² over 10³ trials — KS-test statistical check.
  • Distributed-noise-under-mask: post-unmask aggregate noise variance within 5% of the central-DP target σ²C² (not |U|× too small/large).
  • Example-level vs client-level produce the documented different sensitivities: example-level uses C per record, client-level uses C per whole Δ_u — verified by two distinct fixtures in dp/levels.json.

19.6 Pitfalls

  • Clipping after averaging (instead of per-record before summing) breaks the sensitivity bound → invalid DP (I14).
  • Continuous Gaussian noise added under modular masking can wrap/round inconsistently; use the discrete Gaussian for Z_R (P4, I6).
  • Distributed noise with the wrong per-client variance (σ²C² instead of σ²C²/|U|) over- or under-noises the aggregate.

  • Discrete Gaussian sampling is costlier than continuous; precompute/cache where possible.

19.8 Edge Cases

  • C larger than all norms → clipping is a no-op (still valid, just less bias). σ huge → noise dominates → no learning. Single survivor + DP → noise on one update (high relative noise). Client-level DP with n_u-weighting → clip the weighted delta consistently.

19.9 Failure Analysis

A clipping/noise bug invalidates the privacy guarantee silently (numbers still look fine). Detection: clip_norm + gaussian_var + distributed_noise fixtures + the accountant cross-check. Blast radius: the stated ε is wrong → privacy breach. Recovery: re-derive σ from the accountant; re-run; never report ε without the accountant agreeing.

tracing tags (C, σ, q) per round; the noised aggregate norm → dashboard. Logs never contain pre-noise updates (P1). Runbook "accuracy collapsed under DP" → check σ vs target ε, C too small, q too small. The DP config and the accountant ledger are coupled (Phase 9): changing σ recomputes ε.

20. Phase 9 — Privacy accounting

20.1 Objectives

Build fl_accountant: Rényi DP accounting of the (subsampled) Gaussian mechanism (Gaussian = (α, α/2σ²)-RDP), composition across rounds (additive in RDP), subsampling amplification (cohort rate q, moments accountant), (ε,δ) conversion, a privacy-budget ledger with a pre-round hard stop (I13, P10), and σ calibration to a target ε for (q,T,δ) (§8.8).

20.2 Detailed Implementation Steps

  • rdp.py: Gaussian RDP α/(2σ²) at an α-grid (e.g. {1.25,1.5,…,64}). (Rényi DP Gaussian mechanism: Mironov CSF 2017; ADR-17)
  • subsample.py: subsampled-Gaussian RDP bound (Mironov–Talwar–Zhang / Wang) per α — numerically evaluated. (subsampling amplification via moments accountant: Mironov–Talwar–Zhang arXiv 2019; Abadi et al. CCS 2016; I13)
  • compose.py: accumulate per-round RDP additively over T rounds (and over microbatches within DP-SGD).
  • convert.py: ε(δ)=min_α RDP(α)+log(1/δ)/(α−1).
  • ledger.py: BudgetLedger(target_eps,δ); step(q,σ) records; can_afford(q,σ) gate consulted by the server pre-round (I13).
  • calibrate.py: binary-search σ s.t. composed ε over T rounds at rate q ≤ target ε.

20.3 Deliverable

The accountant reports cumulative (ε,δ) per round, refuses an over-budget round, and calibrates σ for a target ε; values match a reference (Opacus RDP) within tolerance; pytest packages/fl_accountant green; fl_cli account runs offline.

20.4 Acceptance Criteria

  • RDP/(ε,δ) for a single subsampled-Gaussian step matches Opacus RDPAccountant within 1e-3 (cross-check, ADR-17).
  • Composition over T rounds is monotone increasing and matches summed RDP → converted ε.
  • calibrate_sigma returns σ achieving ≤ target ε over T rounds at rate q (verified by re-accounting).
  • can_afford returns False exactly when the next round would exceed target ε (I13).

20.6 Pitfalls

  • Forgetting subsampling amplification massively over-estimates ε (overspends conservatively) or, if mis-signed, under-estimates (privacy breach) — use the validated subsampled bound.

21. Phase 10 — Robustness / poisoning defense

21.1 Objectives

Build fl_robust: Krum/Multi-Krum (Blanchard 2017), coordinate-wise median + trimmed mean (Yin 2018), norm bounding/clipping of updates, and simple anomaly detection — and make explicit the fundamental tension with SecAgg (the server cannot inspect individual updates, P12). Ship robust cleartext-aggregation mode + client-side norm bounding compatible with SecAgg; defer verifiable/ZK robust-under-SecAgg.

21.2 Detailed Implementation Steps

  • krum.py: per-update score = sum of squared distances to its n−f−2 nearest neighbors; pick the min (Krum) or average the m best (Multi-Krum). (Byzantine-robust aggregation: Blanchard et al. NeurIPS 2017; P12; ADR-19)
  • median.py/trimmed_mean.py: per-coordinate median; trim top/bottom β fraction then mean.
  • norm_bound.py: client-side ‖Δ_u‖₂ ≤ M clip (SecAgg-compatible — the client enforces it, the server need not see Δ_u).
  • anomaly.py: flag updates with extreme norm/cosine vs the running aggregate (cleartext mode only).
  • tension.py: a guard that refuses to run a peek-requiring rule under SecAgg unless a verifiable-bound backend is present (which is deferred) — fails loud rather than silently breaking privacy or being a no-op (P12). (robust↔SecAgg tension: P12; Kairouz et al. FnT 2021 §5; ADR-20)

21.3 Deliverable

Robust rules defend against poisoned clients in cleartext mode; client-side norm bounding works under SecAgg; the tension guard prevents misconfiguration; pytest packages/fl_robust green; examples/robust_poisoning.py runs.

21.4 Acceptance Criteria

  • With cohort=100 and f=20 Byzantine clients (f < cohort/2), Krum/median/trimmed-mean reach within 5% of the non-Byzantine target accuracy vs FedAvg diverging by > 30% (cleartext, fixture robust/krum_defend.json).
  • Client-side norm bounding caps ‖Δ_u‖ ≤ M for 100% of updates and remains bit-exact correct under SecAgg (the masked sum of bounded updates).
  • The tension guard raises RobustSecAggConflict in 100% of 10 tested misconfigurations when a peek-requiring rule is selected with SecAgg on and no verifiable backend (P12).

21.5 Conformance Fixtures

Fixture Purpose Expected

21.6 Pitfalls

  • Running Krum/median "under SecAgg" silently: either it peeked (privacy broken) or operated on the aggregate only (no-op) — the tension guard must catch this (P12).
  • Krum's f parameter must match the true/assumed Byzantine count; wrong f weakens the guarantee.
  • Norm bounding alone does not stop a stealthy poison within the norm ball — document the residual risk.
  • Trimmed mean with too-large β discards honest signal under non-IID heterogeneity (mistakes skew for attack).

  • Krum is O(cohort² × m) (pairwise distances) — the costliest rule; Multi-Krum similar. Median/trimmed-mean are O(cohort × m log cohort).

  • f ≥ cohort/2 → no robustness guarantee possible (majority Byzantine). All-honest cohort → robust rule ≈ mean. Non-IID extreme → honest updates look "anomalous" (false positives). Norm-bound M too tight → clips honest learning signal.

Recovery: switch rule / tune f,β,M; in SecAgg mode, the only honest option is client-side norm bounding (+ deferred ZK). The tension is a documented limitation, not a bug.

Threat Model

The system targets a semi-honest (honest-but-curious) server that may collude with up to t clients (static corruption): all parties follow the protocol but pool their views to infer honest clients' data/updates. The attack surface is (1) the server's view (all masked inputs y_u, public keys, routed shares, the aggregate), (2) colluding clients' views (their own seeds + shares they receive), (3) the transport (network bytes), and (4) the published global model (every round). SecAgg's core property: for the server + ≤ t colluders, the joint view is simulatable from the aggregate alone (P3, I8). Malicious deviation (a lying server beyond equivocation, fake updates passing as honest, active key tampering) is out of scope (deferred Phase 13) and stated loudly in SECURITY.

Metrics strategy — per-round, per-client (sampled at scale): loss/accuracy, aggregate update-norm, cohort size, survivors/dropped, dropout rate, round wall-time, uplink/downlink bytes, compression ratio, ε spent + cumulative, straggler latency distribution, worst-k fairness. Structured logging — structlog JSON; fields (campaign, round, phase, client, event, survivors, eps_spent, abort_reason). A redaction guard makes logging an update/seed/y_u impossible (P1). No prints.

Dashboard design — convergence curve, dropout-rate over rounds, cohort-size, comm matrix (bytes/round per direction), privacy-budget burn-down vs target ε, straggler latency CDF, worst-k fairness gap, abort timeline.

Alerting philosophy — pre-round/inline refusals (loud): sub-threshold survival, ring overflow, budget exhaustion, insecure RNG, comm-budget breach, schema mismatch. SLO definitions — "correct aggregate" SLO: unmask == cleartext sum (bit-exact in Z_R). "Privacy" SLO: sim-vs-view audit passes (server view == aggregate, ≤ t colluders) AND cumulative ε ≤ target. "Predictable cost" SLO: bytes × rounds within the stated budget; rounds complete within the deadline ≥ target fraction.

Incident response / runbooks — docs/runbooks/: dropout-storm, sub-threshold, ring-overflow, budget-exhaustion, equivocation, non-convergence, poisoned-model, comm-budget, schema-mismatch. Each maps symptom → telemetry → cause → fix.

Backup / restore — model checkpoints per version (server); the privacy ledger is append-only and persisted. Seeds (test) + configs make runs reproducible; SecAgg material is per-round and regenerable (never persisted — it is ephemeral by design). Restore = resume from a checkpoint + the ledger.

Deployment topology — simulator: one process, server + N client tasks, in-proc channels (primary test vehicle). Network: server process + one process per client over gRPC, optional docker-compose (one container per party). The server is the single stateful service; clients are stateless per round.

Canary / rolling upgrade / rollback — model versions are checkpoints; a bad global step rolls back to the prior version. Protocol/proto changes are versioned (I15); rolling upgrade requires all cohort members on a compatible proto version (gate at R0). Rollback = pin prior package + proto version.

Migration / compatibility — the proto schema, the Z_R/quantization config, the SecAgg round semantics, the DP/accounting formulas, and the model byte codec are the stable contracts; all versioned (I15).

  • Comm analysis — bytes × rounds per client is the primary cost (P9); compression (quantization, top-k, FedPer) + cohort sizing are the levers; SecAgg adds O(cohort) shares + 4 RTTs.
  • Targets — mask expansion ≥ 10⁷ params/s/core; SecAgg overhead a small multiple of plain aggregation for moderate cohorts; round latency dominated by RTT × 4 on a WAN.

Mental Models & First Principles

  1. MM1 — Masks cancel only in the exact sum over the exact set. Predicts: adding or removing any single client's contribution leaves a dangling PRG term that corrupts the aggregate. Without it: developers test "most clients present" and ship a system that silently produces garbage when dropout set differs from the round-3 survivor set. Applied: §8.4 / §8.5 / Phase 5 where the ± sign convention and the surviving-set bookkeeping are defined.

  2. MM2 — One parameter, two opposing guarantees: the threshold t bounds correctness from below and privacy from above. Predicts: raising t strengthens privacy but raises the dropout budget needed to abort; lowering t tolerates more dropout but weakens the colluder bound. Without it: designers set t=1 (generous dropout tolerance) and discover later that one colluding client plus the server can reconstruct an update. Applied: §P6 / Phase 6 / Phase 7 where the threshold appears in every survival check.

  3. MM3 — Communication, not compute, is the FL bottleneck; every design decision is measured in bytes × rounds. Predicts: a 10× training speedup is irrelevant if it does not reduce bytes/round or number of rounds. Without it: engineers profile CPU-bound autograd while the actual campaign time is dominated by 4 SecAgg RTTs × T rounds × cohort clients. Applied: §4.1 (throughput driver) / Phase 4 / Phase 9 (rounds bound by budget).

  4. MM4 — SecAgg and DP are orthogonal, not substitutes; each closes a gap the other leaves open. Predicts: SecAgg blocks gradient inversion against the server, but the aggregate still leaks via membership inference; DP bounds the aggregate's leakage but does not prevent the server from seeing individual updates without SecAgg. Without it: a team ships SecAgg and concludes "privacy is done," ignoring that the aggregate is still a sensitive statistic. Applied: §P11 / Phase 8 / Phase 13 (MIA simulation).

  5. MM5 — Double-masking resolves the dropped-vs-slow ambiguity; without it the server controls who is "dropped" and can unmask any slow client. Predicts: a self-mask PRG(b_u) protects a client whose y_u arrived but whom the server falsely declares dropped, because the server only recovered s_u^{SK} shares, not b_u. Without it: the server equivocates the dropout set, collects the "dropped" client's pairwise shares, and cancels all masks — a full unmask of one client. Applied: §P5 / §8.5 / Phase 6 / Phase 7.

  6. MM6 — The randomness faucet must be single, typed, and auditable; a seeded RNG in production makes masks predictable — worse than no masking. Predicts: any code path that calls numpy.random or random directly outside fl_crypto can be differenced by an observer who knows the seed. Without it: a developer adds a quick numpy.random.randn for distributed noise in a "test" that ships to prod because the config flag is not enforced. Applied: §P2 / §I7 / Phase 5 / Phase 8.

  7. MM7 — Subsampling amplification is the primary lever for privacy efficiency; without it RDP composition grows linearly in T at full rate. Predicts: reducing cohort rate q from 1 to 0.01 can reduce the effective RDP by orders of magnitude, enabling far more rounds for the same ε. Without it: a designer runs T=1000 rounds with q=1 and discovers the budget exhausted after T=10, blaming the noise level rather than the missing amplification. Applied: §8.8 / Phase 9 (subsample.py) / ADR-17.

  8. MM8 — Byzantine robustness and SecAgg are in structural tension; any rule that needs to inspect individual updates cannot run under SecAgg without a ZK or MPC backend. Predicts: fl_robust applied "under SecAgg" is either a privacy breach (it peeked) or a no-op (it ran on the aggregate). Without it: developers add Krum as an aggregation rule without disabling SecAgg, ship a no-op defense, and report "Byzantine-robust FL" incorrectly. Applied: §P12 / Phase 10 / ADR-19 / ADR-20.

  9. MM9 — The 4-round SecAgg protocol is a state machine; any early advancement past a round without a threshold check creates a window for partial unmasking. Predicts: advancing R3 on a timeout without re-checking |U2| ≥ t+1 unmaskes a sum over a set too small to guarantee privacy. Without it: a developer adds a fast-path that skips the survival check when only one client is slow, inadvertently revealing that client's update. Applied: §P7 / §8.6 / Phase 7 / I4.

  10. MM10 — Quantization, ring size, and client ordering are a jointly agreed invariant; any divergence silently corrupts the aggregate without raising an error. Predicts: a client quantizing with a different B or ordering clients by IP instead of by ID leaves a non-zero residual after unmasking that looks like a small gradient noise. Without it: a schema drift between client versions goes undetected because the aggregate merely shifts rather than NaN-ing. Applied: §P4 / §I15 / §I6 / Phase 4 / Phase 5.

Back-of-Envelope Capacity Model

  1. Uplink bytes per client per round (uncompressed). Start: model size m = 10⁶ params (§4.1 mid-range), 32-bit fixed-point quantization (4 bytes/param). Raw delta: 10⁶ × 4 = 4 MiB/client. With top-k=10% sparsification: 0.1 × 4 MiB + 4-byte indices ≈ 0.8 MiB/client. Design consequence: chunking threshold at 4 MiB per §4.1 is exactly one uncompressed delta; compression is mandatory at the upper model range (m = 10⁷ → 40 MiB uncompressed).

  2. Total uplink bytes per round (cohort). Start: cohort = 100 (cross-device, §4.1), uplink per client = 4 MiB. Total uplink: 100 × 4 MiB = 400 MiB/round. At T=200 rounds: 80 GiB total uplink traffic. Design consequence: subsampling rate q = 100/10⁶ = 10⁻⁴ is the primary cost lever — doubling the cohort doubles the bill linearly.

  3. SecAgg share volume per client per round. Start: cohort = 100 (§4.1), each client shares two 32-byte secrets (b_u, s_u^SK) to all other n−1 = 99 peers via Shamir. Each share ≈ 64 bytes (32-byte point + 32-byte value). Total shares per client: 2 × 99 × 64 = 12,672 bytes ≈ 12.4 KiB. Over cohort: 100 × 12.4 KiB = 1.24 MiB of share traffic. Design consequence: share overhead is ~0.3% of uncompressed model traffic for m = 10⁶; it grows linearly with cohort, not with model size — the Bell-2020 log-degree graph (deferred Phase 13) targets this term at m_c ≥ 10⁴.

  4. Server pairwise bookkeeping memory. Start: cohort = 100, model m = 10⁶, 4 bytes/param, per §4.1 server memory = O(m + cohort²). Model store: 10⁶ × 4 = 4 MiB. Pairwise share store: cohort² × 64 bytes = 100² × 64 = 640 KiB. Total: ≈ 4.6 MiB. At cohort = 1000: pairwise store = 10⁶ × 64 = 64 MiB — still manageable but grows quadratically. Design consequence: O(cohort²) is the SecAgg-specific ceiling flagged in Scalability Analysis; cohort = 10⁴ → 6.4 GB of share state.

  5. PRG mask expansion cost. Start: mask expansion target ≥ 10⁷ params/s/core (§4.1), cohort = 100 clients, model m = 10⁶. Each client must PRG-expand cohort − 1 = 99 pairwise masks: 99 × 10⁶ = 9.9 × 10⁷ params of PRG output per round per client. At 10⁷ params/s/core: 9.9 s/core/client. Vectorized AES-NI can reach ≥ 10⁸ params/s; at that rate: ~1 s/client. Design consequence: the PRG expansion dominates client CPU in SecAgg rounds; the deferred Rust/C PRG extension (Phase 12) targets the 10× speedup needed at m = 10⁷.

  6. Noise multiplier σ for a target ε=3, δ=10⁻⁵ over T=100 rounds. Start: cohort rate q = 100/10⁶ = 10⁻⁴ (§4.1 cross-device pool N=10⁶, cohort=100). Using the subsampled-Gaussian RDP bound (Mironov–Talwar–Zhang 2019), subsampling amplification reduces the effective RDP by ≈ q = 10⁻⁴. A rough calibration (the calibrate_sigma binary search per Phase 9): σ ≈ 1.1 achieves ε ≈ 3 at these parameters where without subsampling the same T and σ would exhaust ε ≈ 300. Design consequence: subsampling amplification is the difference between a practical and an impractical DP campaign; q is the first hyperparameter to tune.

  7. Ring size R to avoid sum overflow. Start: cohort = 100 (§4.1), 32-bit quantization, max per-parameter absolute value after quantization = 2³¹ − 1 ≈ 2.1 × 10⁹ (§4.1 masking ring). True sum maximum: cohort × max_quantized = 100 × 2.1 × 10⁹ = 2.1 × 10¹¹. R = 2³² = 4.3 × 10⁹ — too small! Required: R > 2.1 × 10¹¹ → R = 2⁶⁴ for cohort = 100 at 32-bit quant, OR reduce per-parameter quantization range by clipping updates harder. Design consequence: the §4.1 note "R = 2³² default (or 2⁶⁴)" is load-bearing: cross-silo cohorts at 32-bit quantization mandate R = 2⁶⁴ unless the clip bound B is tightened.

  8. Round latency floor (WAN). Start: SecAgg = 4 sequential rounds (§4.1), each round requires one server↔all-clients RTT. WAN RTT assumption (cross-device, explicit in §4.1 round deadline 60–600 s): assume 100 ms RTT per hop. Latency floor = 4 × 100 ms + serialization/crypto overhead ≈ 400 ms minimum per FL round; with chunking overhead for m = 10⁶ at 4 MiB: chunking adds ≈ 1 × 4 MiB / (10 Mbps uplink) = 3.2 s. Total floor per round: ~4–5 s LAN, 10–600 s WAN. Design consequence: 200-round campaign takes 33–120 min minimum ignoring training time; deadline tuning is the primary latency lever (§4.1 configurable deadline).

  9. Privacy budget burn rate per round. Start: σ = 1.1 (from item 6), q = 10⁻⁴, T = 100 rounds. Gaussian RDP per round ≈ α/(2σ²) = α/2.42 at order α; with subsampling the effective per-round charge is ≈ q²·α/(2σ²) (leading term). Over 100 rounds: total RDP ≈ 100 × 10⁻⁸ × α/2.42. After conversion to (ε,δ), the ledger charges roughly ε/T = 3/100 = 0.03 ε-units/round. Design consequence: the server's pre-round gate (I13) checks the ledger with a one-round look-ahead; running "just 10 more rounds" at the same σ costs ≈ 0.3 additional ε — non-trivial if the target ε is 3.

  10. Cross-device vs cross-silo cohort sizing. Start: cross-silo cohort = 10–50, cross-device cohort = 50–10⁴ (§4.1), pool N = 10⁶. Cross-silo: with cohort = 20, t = 10, dropout tolerance = 9 (up to 9 clients may drop). Cross-device: with cohort = 200, t = 100, dropout tolerance = 99. Comm ratio: cross-device round delivers 200/20 = 10× more gradient signal but generates 200² / 20² = 100× more pairwise share traffic at the server. Design consequence: the cross-device regime is where the O(cohort²) ceiling bites first and the Bell-2020 log-degree graph (deferred) is most urgent.

Hard Questions (Self-Examination)

  1. If two clients use different values of B (the quantization range) in the same round, the server will receive a wrong aggregate without any error being raised. Which invariant is supposed to catch this, in which phase does it get enforced, and what is the exact mechanism? (§I15, §I6, Phase 4, ADR-4)

  2. The threshold t appears in both the Shamir sharing degree and the survival check. If you set t = cohort − 1 to maximize privacy, what is the dropout tolerance, and how does this interact with the round-deadline straggler policy? Give the exact formula. (§P6, §I4, §8.6, Phase 7)

  3. A client sends its masked input y_u in R2 but the network delivers it after the server has already broadcast (U2, D2) in R3. The server has declared this client dropped and already requested its s_u^{SK} shares. Can the server now unmask this client? Walk through the I2 enforcement and the consistency-check path. (§I2, §I9, §P5, Phase 7)

  4. Under the distributed-noise-under-mask scheme, each client adds N(0, σ²C²I/|U|) before masking. If five clients drop after committing noise but before their y_u arrives, does the post-unmask aggregate carry the right total noise variance? Derive the answer from §8.7. (§8.7, §I1, Phase 8, ADR-16)

  5. The RDP accountant charges the budget using q = cohort/N (§8.8). If the server uses importance sampling instead of uniform sampling, is the amplification formula still valid? Which ADR governs sampling, and what would need to change in fl_accountant? (ADR-21, §8.8, Phase 9, §I13)

  6. Krum requires inspecting individual updates to compute pairwise distances. Yet fl_robust/tension.py is supposed to raise RobustSecAggConflict at config time. Describe exactly what the tension guard checks, what config combination triggers it, and why norm bounding alone is the only SecAgg-compatible defense without ZK. (§P12, Phase 10, ADR-19, ADR-20)

  7. A single client with n_u = 0 (empty shard) participates in a SecAgg round and sends a masked zero vector. What does FedAvg do with this client's weight, and what happens to the I12 weight-sum assertion? (§8.12, §I12, Phase 3, Phase 5)

  8. The PRG expansion prg_expand(seed, R, m) must produce a uniform distribution over Z_R. Why does naive truncation of an AES keystream to Z_R introduce bias when R is not a power of two, and what does the implementation use instead? (§I1, Phase 5 §16.2, ADR-5)

  9. After T = 200 rounds at q = 10⁻⁴ and σ = 1.1, the ledger shows ε = 3.02 against a target of 3.0. The server refuses to start round 201. Is the stated privacy guarantee still valid for the first 200 rounds, and does the refusal of round 201 violate any invariant? (§I13, §P10, Phase 9, §8.8)

  10. Ed25519 signatures in R3 cover hash(U2, D2). If the server broadcasts two different (U2, D2) pairs to two disjoint client groups, what exactly does the consistency check detect, and what does it NOT detect in a semi-honest adversary model? (§I9, §P5, Threat Model, Phase 7)

  11. The TranscriptRng uses a fixed seed for test reproducibility. What is the exact mechanism that prevents it from being used in production, and what would happen to mask secrecy if it were? Trace the check through the design principles and invariants. (§P2, §P13, §I7, Phase 5, ADR-27)

  12. FedProx adds a proximal term at the client. The server only ever sees the aggregate delta, not the individual proximal-adjusted deltas. How does FedProx improve convergence under non-IID data without the server knowing μ per client, and why does this not break the SecAgg privacy guarantee? (§8.2, §P1, Phase 3, Phase 11)

  13. The worked example in §8.10 shows client 3 dropping. Trace what happens if client 3 drops after R1 (shares committed) but before R2 (never sends y_3). Then trace what happens if client 3 drops after R2 (server has y_3) but the server falsely declares it dropped in R3. In which case can the server unmask client 3, and why? (§8.5, §8.10, §I2, Phase 6, Phase 7)

  14. The ring R must satisfy R > cohort × max_quantized (I6). If R is set at system initialization and the cohort fluctuates across rounds due to dropout, when (if ever) can the ring be resized mid-campaign, and what are the coordination implications? (§I6, §I15, Phase 5, ADR-5)

  15. Privacy accounting uses Poisson subsampling amplification formulas. The actual cohort sampling in fl_server/cohort.py is sampling without replacement. When does the mismatch between Poisson and without-replacement subsampling matter, and what does the ADR say about it? (ADR-17, §8.8, Phase 9, §I13)

  16. A client's n_u = 5000 while the cohort median is n_u = 50. FedAvg assigns this client 100× the weight. Could this client act as a semi-honest "weight amplifier" by submitting a large update? Explain how norm bounding interacts with weighting. (§8.9, §P12, Phase 10, §I12)

  17. The fl_telemetry redaction guard rejects any log field that "could carry an update/seed." How does the guard decide what constitutes an update vs a metric? Name two metrics that are safe to log and one value that must be redacted, citing the relevant principle. (§P1, Phase 12, §I8, ADR-23)

  18. Bell et al. (2020) extend SecAgg to a log-degree communication graph. This design defers that extension. What is the specific computational bottleneck it addresses, and at what cohort size does the pairwise-quadratic cost start dominating the total round cost versus the model-size cost? Derive from §4.1 values. (Scalability Analysis, Phase 13, §8.6, MM3)

  19. The BudgetLedger.can_afford(q, σ) method gates each round. If the server changes σ mid-campaign (e.g., applies a different noise level for the last 10 rounds to converge faster), does the composition formula still hold? What part of fl_accountant handles this? (§8.8, §I13, Phase 9, ADR-17)

  20. The simulator (fl_sim) asserts "server view == aggregate only" on every run. Describe the exact assertion — what it computes, what inputs it has, and how it distinguishes a leaky design from a correct one. Reference the relevant invariant and security definition. (§I8, §P3, Phase 7, Phase 13)

  21. FedAdam maintains server-side moment accumulators m_t, v_t. Under SecAgg the server only receives Σ n_u·Δ_u and Σ n_u. Explain whether resetting m_t, v_t between campaigns but not between rounds is correct, and what would happen if they were reset after each round. (§8.2, Phase 3, ADR-18)

  22. The fl_secagg consistency check uses Ed25519 signatures. Suppose a client is Byzantine (out of scope but consider the analysis) and signs a different hash(U2, D2) from the honest set. The server detects the mismatch and aborts. Does this abort reveal which client was Byzantine, and does that violate the semi-honest assumption? (§I9, Threat Model, ADR-20, Phase 7)

FedProx FedAvg + a client-side proximal term (μ/2)‖w−w_t‖² to curb drift under heterogeneity
FedAdam / FedYogi server-side adaptive optimizer applied to the aggregated pseudo-gradient (Reddi 2020)
Cohort the subset of clients selected to participate in a given round
Sampling rate q cohort size / pool size; the subsampling probability used in DP amplification
Weight-delta Δ_u client's local model change w_local − w_global (the upload, vs a raw gradient)
Secure Aggregation (SecAgg) a protocol revealing only Σ_u x_u to the server, hiding each x_u (Bonawitz 2017)
Pairwise mask PRG(s_{u,v}) added by one client and subtracted by the other so it cancels in the sum
Self-mask (double-masking) PRG(b_u) each client adds to protect against the dropped-vs-slow ambiguity
Mask cancellation the algebraic fact that pairwise masks telescope to zero in the exact sum over contributors
Diffie–Hellman key agreement two parties derive a shared seed s_{u,v} from their key pairs (X25519)
PRG pseudo-random generator expanding a seed into a uniform mask vector in Z_R^m (AES-CTR/ChaCha20)
Ring Z_R integers mod R; the modular field for quantized updates + masks (addition wraps)
Quantization mapping float updates to fixed-point integers in Z_R (stochastic rounding keeps it unbiased)
Shamir (t,n) secret sharing secret = p(0) of a degree-t polynomial; ≥ t+1 shares reconstruct, ≤ t reveal nothing
Threshold t the Shamir threshold: bounds correctness (≥ t+1 to reconstruct) and privacy (≤ t learn nothing)
Surviving set U clients whose masked input reached the server before the deadline
Dropped set D selected clients whose masked input did not arrive (recovered via key reconstruction)
Dropped-vs-slow ambiguity the server cannot tell a dropped client from a slow one; double-masking + consistency resolve it
Consistency check survivors sign the same dropout-set hash so the server cannot equivocate about who dropped
Equivocation a server telling different clients different dropout sets to isolate a victim
Semi-honest (honest-but-curious) adversary follows the protocol but tries to learn from its view
Simulation-based privacy the server+≤t view is reproducible from the aggregate alone (the SecAgg security definition)
Differential Privacy (ε,δ) a bound on how much the output reveals about any single record
Sensitivity the max change in a function from one record; bounded by the clip C
Clipping bound C per-example/per-client L2 clip making sensitivity ≤ C
Gaussian mechanism add N(0,σ²C²I) to a sum to achieve (ε,δ)-DP
Noise multiplier σ noise std / C; the DP knob (higher σ → smaller ε, more noise)

Client-level vs example-level DP protect a whole client's participation vs a single training example
Central vs local DP trusted aggregator noises once vs each client noises its own update

Trimmed mean / coord. median robust per-coordinate aggregation discarding outliers (Yin 2018)
Norm bounding clipping each update's L2 norm ≤ M (SecAgg-compatible, client-side)
Membership inference inferring whether a record was in the training set (Shokri 2017)
Deep Leakage from Gradients (DLG) reconstructing training data from a gradient/update (Zhu 2019)
Non-IID clients' data distributions differ (heterogeneity); Dirichlet(α) controls skew
Personalization / FedPer adapting the global model per client; FedPer keeps personalization layers local
