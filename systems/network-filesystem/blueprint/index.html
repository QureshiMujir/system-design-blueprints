393 — Network Filesystem (NFS/SMB) from Scratch

Project Number: 393 Project Name: Network Filesystem (NFS/SMB) from Scratch Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

Build a production-grade network filesystem from scratch: a userspace daemon exporting POSIX-like file storage over two wire protocols sharing one VFS and one backing store.

What is built (precise terms):

  • NFSv3 server — ONC RPC/XDR over TCP (UDP optional), RFC 1813 procedure set, MOUNT protocol, stateless ops + Duplicate Request Cache (DRC) for at-most-once non-idempotent ops.
  • NFSv4.1 server — RFC 8881, COMPOUND op arrays, sessions + slot tables (exactly-once), stateful OPEN/CLOSE/LOCK, stateids, leases, read delegations, pseudo-fs, integrated locking.
  • NFS client — mount over FUSE (or loopback vnode shim), attribute cache (TTL), data cache, readahead, write-back, close-to-open (CTO) consistency.
  • SMB2/SMB3 server — second protocol front-end over the same vfs: NEGOTIATE, SESSION_SETUP (NTLMSSP + Kerberos via GSSAPI), TREE_CONNECT, CREATE/READ/WRITE/CLOSE, oplocks/leases, durable handles, SMB3 signing + encryption.
  • Backing store — local on-disk inode_map + data files + write-ahead journal; stable opaque file handles surviving cache eviction and (v3) server reboot.

System boundaries: single-node userspace daemon; one backing store rooted at one or more exports; clients are untrusted on the wire. Server owns all state; clients hold only caches + handles. No kernel module (FUSE bridges client into kernel VFS; server is pure userspace listening on TCP).

Explicit non-goals:

  • NOT a clustered/parallel filesystem (Ceph, Lustre, GlusterFS). Single backing store; no cross-node data striping.
  • NOT pNFS layouts beyond a documented stub (PhaseDeferred("FINAL_BLUEPRINT §1")).
  • NOT a full Active Directory domain controller or Kerberos KDC — we integrate with an external KDC/GSSAPI, never implement key distribution.
  • NOT NFSv2 (RFC 1094) — read for historical context only; not served.
  • NOT SMB1/CIFS — excluded for security (no plaintext dialects, no LANMAN auth).
  • NOT a general object store, block device (iSCSI/NVMe-oF), or FUSE-userspace-FS for arbitrary backends.

Deployment model: server daemon (nfsd-rs) binds TCP/2049 (+ MOUNT/NLM ports, or fixed ports for v4.1) and TCP/445 (SMB); registers v3 with portmap/rpcbind (TCP/111). Client side runs a FUSE mount process (mount.nfs-rs). Single binary per role or one multiplexing daemon.

Target users: storage/protocol engineers, filesystem implementers, distributed-systems learners calibrating against real Linux mount -t nfs / mount.cifs interop.

Phase 0 deliverable (numbered crates/modules):

  1. rpc — XDR codec, record-marking framing, RPC message types, AUTH, dispatch, DRC.
  2. vfs — vnode, path resolution, file-handle abstraction, attribute model.
  3. store — inode map, data files, journal, fsid management.
  4. nfs3 — NFSv3 procedures, fattr/wcc, MOUNT.
  5. nfs4 — COMPOUND, session/slot, state, open/lock, delegation, pseudo-fs.
  6. smb2 — header, negotiate, session_setup, tree, create, read/write/close, oplock, query_dir, ioctl.
  7. lockmgr — byte-range lock manager (NLM + integrated v4).
  8. statemgr — NFSv4 client/open/lock/lease state, SMB handle/oplock state.
  9. auth — AUTH_SYS, RPCSEC_GSS, NTLMSSP, GSSAPI bridge.
  10. client — mount, attr cache, data cache, write-back, FUSE bridge.
  11. server — transport listener, connection lifecycle, per-conn state.
  12. cli — admin/inspection (fhdump, stateview, drcstat).

Later phases unlock: stateful v4.1 sessions, delegations, integrated locking, second protocol (SMB), crash recovery + grace period, conformance + interop. Deferred features (each anchored individually in the Deferred Features Register, PhaseDeferred("FINAL_BLUEPRINT §1") or §8.7): pNFS layouts, NFSv4.2 (server-side copy, sparse, ALLOCATE/DEALLOCATE), SMB Witness/continuous-availability, RDMA transport (SMB Direct / NFS-over-RDMA), referrals/DFS, multichannel.

Timeline: Phase 0 (skeleton + framing + XDR): 8–14 weeks. Full implementation (all 14 phases, conformance, interop): months (estimate 9–14 months for one engineer at staff level; 4–6 months for a small team).

Recommended language = Rust + tokio async.

  • Rationale: memory safety on hostile wire input (every length/offset is attacker-controlled; XDR/SMB parsers are the #1 CVE source in C implementations — bounds-checked slices eliminate the buffer-overflow class). Fearless concurrency for thousands of simultaneous connections + shared state manager (Send/Sync + Arc<RwLock>/sharded locks enforced at compile time). No GC → no tail-latency pauses under load (NFS p99 must stay bounded during fsync storms). Zero-copy via bytes::Bytes + sendfile/splice/io_uring.
  • Rejected — C: CVE-prone manual parsing (decades of nfsd/Samba memory-safety advisories), manual lifetime management of handle/state tables.
  • Rejected — Go: GC stop-the-world pauses inflate p99 under fsync + connection churn; weaker zero-copy story; reflection-based serialization too slow for XDR hot path.
  • Rejected — C++: safety not guaranteed without heavy discipline; build/dependency friction; no clear win over Rust here.

Prerequisites: POSIX filesystem semantics (open/unlink/rename/fsync atomicity); VFS/inode/vnode model; ONC RPC + XDR encoding; TCP + byte-order/wire parsing; distributed-systems consistency (close-to-open, leases, exactly-once); auth basics (Kerberos, GSSAPI, NTLM); concurrency (async runtimes, lock ordering, lock-free state).

2. Why Build This

Unique systems knowledge taught:

  • Stateless vs stateful protocol design — NFSv3 (stateless server, idempotent-where-possible, recover by retransmit) vs NFSv4.1 (stateful server, sessions, explicit state recovery via grace period). The single sharpest lesson in protocol architecture.
  • Idempotency + duplicate-request cache — why non-idempotent ops (REMOVE, RENAME, CREATE-exclusive) need at-most-once semantics over an unreliable retransmitting transport; how a DRC keyed by (xid, proc, client) provides it.
  • File-handle abstraction — opaque, stable, server-minted reference decoupling the wire from on-disk inode numbers; survives cache eviction and reboot; the keystone of NFS statelessness.
  • Close-to-open consistency — the precise, weaker-than-POSIX contract that makes client caching safe-enough; GETATTR-on-open / flush-on-close protocol.
  • Lease/lock recovery — leases as fault-tolerant locks (Gray & Cheriton); grace period after reboot lets clients reclaim state before new conflicting state is granted.
  • XDR wire encoding — 4-byte-aligned big-endian canonical encoding; discriminated unions; opaque/variable arrays; why defensive length-checking is non-negotiable.
  • Compound RPC — batching multiple ops in one round-trip (NFSv4 COMPOUND), current-filehandle threading, partial-failure semantics.
  • Oplocks/leases & delegations — server delegating cache authority to a client and recalling it (oplock break / delegation recall) — distributed cache coherence in practice.
  • Export/auth models — AUTH_SYS (trust-the-uid) vs RPCSEC_GSS/Kerberos; root_squash; per-export access control.

Historical / architectural significance:

  • Sun NFS (1984, Sandberg et al.) — defined network filesystems; introduced stateless server + idempotent ops + ONC RPC + XDR + VFS/vnode layering (the VFS interface itself was invented to support NFS).
  • CIFS → SMB2 redesign (2006) — Microsoft collapsed a chatty, fragile protocol into a compact, compounded, credit-flow-controlled binary protocol; a canonical "protocol v2 done right" case study.
  • NFSv4 statefulness (2003+) / v4.1 sessions (2010, RFC 5661/8881) — folded MOUNT+NLM+ACL into one stateful protocol with exactly-once sessions; a deliberate reversal of the stateless dogma, justified by firewall-friendliness + correctness.

Engineering muscles developed: hostile-input parsing; wire-format reverse-engineering against packet captures; distributed cache coherence; crash-recovery + idempotency reasoning; concurrency at thousands-of-connections scale; protocol versioning + interop with battle-tested clients; performance engineering (zero-copy, syscall batching).

Production engineering concepts exercised: backpressure, bounded resources, observability of distributed state (lease revocations, stale handles), graceful recovery, security hardening of untrusted endpoints.

Calibration value: permanently raises capability in (a) treating every wire byte as adversarial, (b) reasoning about stateless-vs-stateful tradeoffs, (c) building distributed cache coherence, and (d) achieving interop with decades-old reference clients — a bar few engineers clear. This is a "can you build the thing the OS depends on" project.

What Mastery Looks Like:

  • Parse any wire protocol defensively without memory errors — after Phase 0–1, you will write XDR/SMB decoders that validate every attacker-controlled length before allocation; this is the habit that eliminates the buffer-overflow CVE class permanently.
  • Reason precisely about stateless-vs-stateful recovery tradeoffs — after Phase 4 and 7–8, you can articulate exactly when statelessness fails (locks, delegations, exactly-once semantics) and design the minimal state that recovers correctly.
  • Design and implement distributed cache coherence — after Phase 5 + 8 + 11, you will have implemented close-to-open, lease-backed delegation, and SMB oplock break, and can reason about the consistency guarantees each provides and the regime where each is correct.
  • Build crash-only services with journal recovery — after Phase 12, you will be able to design a WAL that guarantees durability without requiring clean shutdown, and reason about fsync ordering, write-verifier rotation, and grace-period reclaim.
  • Achieve real-client interoperability — after Phase 13, you will have validated against Linux kernel NFS, mount.cifs, Connectathon, pynfs, and smbtorture; you will understand that interop is determined by de-facto client behavior, not just RFC text.
  • Engineer authentication and authorization at protocol depth — after Phase 9, you will understand RPCSEC_GSS, GSSAPI/Kerberos, NTLMSSP, and SPNEGO at the message level, including why AUTH_SYS is advisory-only and how root_squash enforces identity at the export boundary.
  • Profile and optimize a system with zero-copy I/O and group commit — after Phase 12, you will be able to measure syscalls/op, implement splice-based zero-copy, tune group-commit batch windows, and own the p99 target on a real NVMe workload.

3.2 Box-by-box responsibilities

  • server::listener — accepts TCP on 2049/445/111/MOUNT/NLM; spawns one tokio task per connection; enforces max-connection cap + per-IP limits; owns connection lifecycle (idle timeout, half-close, RST handling). Invariant: connection state never outlives the socket; closing a connection releases SMB handles + (after lease expiry) v4 state. Concurrency boundary: per-connection task; shared subsystems reached via Arc.
  • rpc::record_marking — frames the byte stream into RPC records: 4-byte big-endian header, top bit = last-fragment, low 31 bits = fragment length; reassembles fragments into one message; caps total message size. Invariant: a message is dispatched only after the last-fragment bit; oversized → connection killed. SMB uses its own 4-byte NetBIOS-style length prefix (smb2::framing).
  • rpc::dispatch + auth::verify + rpc::drc — parses RPC call header (xid, prog, vers, proc, cred, verf); routes to handler; verifies AUTH_SYS/RPCSEC_GSS; consults DRC for non-idempotent ops (cache hit → replay stored reply, no re-execution). Invariant: every non-idempotent op passes through DRC before execution; xid unique per connection in flight. Concurrency: DRC is a sharded LRU behind fine-grained locks.
  • nfs3::proc / nfs4::compound / smb2::command — protocol handlers. nfs3 is stateless per-op. nfs4::compound walks an op array threading a "current filehandle" + "saved filehandle", honoring SEQUENCE slot ordering. smb2::command dispatches by 16-bit command, charges credits. All three lower to vfs. Invariant: handlers never touch the store directly — only via vfs. I/O: in = decoded request struct; out = encoded reply + wcc/attr deltas.
  • vfs::vnode / vfs::handle / vfs::path / vfs::attr — the unifying layer: resolves paths within an export root (containment enforced — no .. escape), maps FileHandle ↔ vnode ↔ inode, computes Fattr3/SMB FILE_INFO, evaluates ACCESS/authorization. Invariant: handle→inode mapping stable + validated (ESTALE on mismatch); path resolution cannot escape export root. Concurrency boundary: per-inode locks for metadata mutation; the single chokepoint both protocols funnel through (ensures consistent semantics).
  • statemgr — owns NFSv4 client records, open/lock stateids, leases, delegations; SMB sessions, tree connects, opens, oplocks; the grace-period state machine. Invariant: lease renew-or-revoke (no split ownership); stateid seqid monotonic; on reboot, only reclaim allowed during grace. Concurrency: global state guarded by sharded locks keyed by client-id; hot path is lease renewal.
  • lockmgr — byte-range lock table; conflict detection; blocking-lock queues + async wakeups; NLM (v3 sidecar) and integrated v4 locking share the core conflict engine. Invariant: lock state consistent across reconnect; no two conflicting locks granted; lock counts bounded. Concurrency: per-file lock list under per-file lock.
  • store::inode_map / data / journal / fsid — on-disk persistence: inode table (mode, uid/gid, size, times, link count, generation number), data files, write-ahead journal for metadata + (optionally) v4 state, fsid registry per export. Invariant: WRITE+COMMIT durability (data on stable storage before COMMIT reply); handle generation number invalidates reused inode numbers; journal replay restores consistency after crash. Concurrency: journal append is serialized; data writes parallel per-file.
  • client:: (fuse, attrcache, datacache, writeback)* — kernel-VFS bridge via FUSE; attribute cache with acregmin/acregmax TTL; data cache + readahead; write-back buffering of UNSTABLE writes flushed by COMMIT; enforces close-to-open (GETATTR on open, flush on close). Invariant: on-close flush completes (or error surfaced) before close returns; cached attrs honored only within TTL. Concurrency: per-inode cache locks; background writeback + readahead tasks.
  • rpc::client / transport — encodes XDR requests, allocates xids, manages a connection pool per mount, retransmits on timeout (triggering server DRC), backs off. Invariant: retransmit reuses the same xid (so DRC recognizes the duplicate). Concurrency: multiplexes many in-flight requests per connection by xid.

6. Design Principles

  1. Idempotency via Duplicate Request Cache. Non-idempotent ops (REMOVE/RENAME/CREATE-excl/SETATTR-with-guard) executed twice on retransmit corrupt state ("REMOVE then re-REMOVE → spurious ENOENT to a retry that actually succeeded"). DRC keyed by (xid, proc, client-addr/clientid) caches the reply; a duplicate replays it without re-execution. Tradeoff: memory + lookup cost on every op. Operational: DRC hit-rate is a health metric. Violation: clients see phantom errors, double-creates, lost renames.

  2. Stable opaque file handles. Handles are server-minted, opaque to clients, and stable: same file → same handle across cache eviction and (v3) server reboot. Encode (export_id, fsid, inode, generation). Tradeoff: generation numbers + persistent fsid cost storage; clients cannot introspect. Operational: ESTALE rate signals handle instability. Violation: clients get ESTALE storms, mounts break, data routed to wrong inode (security hole).

  3. Stateless where possible; explicit state recovery where not. v3 server holds no per-client state → reboot is transparent (client retransmits). v4 holds state → must rebuild it via a bounded grace period (reclaim-only). Tradeoff: statelessness simplifies recovery but cannot express locks/delegations correctly. Operational: grace-period status is a dashboard line. Violation: skipping grace → granting new locks before reclaim → split ownership / data corruption.

  4. Close-to-open consistency contract. Client revalidates attributes (GETATTR) on open and flushes dirty data on close; concurrent writers are NOT guaranteed POSIX-strong consistency. Tradeoff: weaker than local FS, but enables aggressive caching. Operational: document the contract to users; surprises = bug reports. Violation: drop the flush-on-close → readers see stale data → "my file didn't update" incidents.

  5. Crash-only + lease-based recovery. No graceful-shutdown-required code paths; the daemon must recover from kill -9 identically to a clean stop. State is reconstructed from the journal + reclaim. Leases bound how long stale state survives. Tradeoff: every write path must be crash-safe (journaling cost). Violation: assuming clean shutdown → corrupt state after power loss.

  6. Defensive XDR/SMB parsing. Every length, offset, count, and array bound on the wire is attacker-controlled and must be validated before allocation or indexing. Never trust a declared length; cap allocations; reject before reserving. Tradeoff: validation branches in the hot path. Operational: parser-reject counters + fuzzing. Violation: the entire memory-safety CVE class (heap overflow, OOM via huge declared array, integer overflow on offset+len).

  7. Bounded resources everywhere. Cap READDIR cookies, lock counts, DRC size, open handles, in-flight ops per connection, COMPOUND op-array length, connection count. Reject with a defined error when exceeded. Tradeoff: legitimate heavy clients may hit limits. Operational: every cap has a metric + alert. Violation: a single client OOMs the server (DoS).

  8. Wire compatibility is sacred. Once a version is shipped, its wire format never changes; new behavior goes behind new versions/minor-versions/flags. Reference clients (Linux, Windows) are decades-stable and unforgiving. Tradeoff: no field re-purposing; versioning overhead. Violation: a "small" struct change → real clients fail to mount.

  9. Authorization at every operation. Never trust an AUTH_SYS uid implicitly; evaluate access per-op against file mode/ACL + export options (root_squash, all_squash, ro). v4/GSS bind identity to a verified credential. Tradeoff: per-op access checks cost cycles. Violation: uid spoofing → arbitrary file access (AUTH_SYS is advisory only; exports + GSS are the real gate).

  10. Observability of recovery + coherence events. Stale-handle hits, lease revocations, lock conflicts, oplock/delegation breaks, grace-period transitions, DRC hits — all are first-class metrics + traces. Tradeoff: instrumentation overhead. Violation: "the client hangs sometimes" with no signal → undebuggable production.

  11. Path-traversal containment. Path resolution must never escape the export root; .., symlink loops, and absolute symlinks resolved server-side are contained. Tradeoff: resolve symlinks carefully (server-side vs client-side rules differ by protocol). Violation: ../../../../etc/shadow served to a remote client.

  12. Single VFS chokepoint for both protocols. NFS and SMB lower to one vfs layer so semantics (handle mapping, access, attr) are identical regardless of front-end. Tradeoff: the VFS must reconcile two protocol models (e.g., SMB share modes vs NFS advisory locks). Violation: divergent behavior → "works over NFS, corrupts over SMB" cross-protocol bugs.

  13. Durability is explicit, never implicit. Data is on stable storage only after fsync; COMMIT (v3) / FLUSH (SMB) / WRITE-FILE_SYNC reply means durable. UNSTABLE writes may be lost until COMMIT. Tradeoff: throughput (async) vs durability (sync) is the client's choice, honored exactly. Violation: acking COMMIT before fsync → silent data loss on crash (the cardinal NFS sin).

  14. Determinism of error mapping. A given failure always maps to the same protocol error code (errno → NfsStat3 / Nfs4Err / NtStatus), via one table. Tradeoff: none meaningful. Violation: nondeterministic errors → clients misbehave (retry vs fail decisions hinge on exact codes, e.g., NFS4ERR_GRACE vs NFS4ERR_STALE).

  15. Backpressure over buffering. When downstream (disk, state lock, client socket) is slow, apply backpressure (credit limits in SMB, in-flight caps in RPC) rather than unbounded queueing. Tradeoff: clients throttle. Violation: unbounded queues → memory blowup → OOM kill mid-operation.

8.2 Record marking over TCP

 byte:  0        1        2        3      ...payload (fraglen bytes)...
       ┌────────────────────────────────┐
       │ L │      31-bit fragment length │   L=1 → last fragment of this RPC message
       └────────────────────────────────┘
 message = 1+ fragments; reassemble until L=1. Cap Σfraglen ≤ MAX_MSG (e.g., 2 MiB+slop).
 SMB2 transport: 4-byte big-endian length prefix (top byte zero), then SMB2 PDU(s).

8.3 XDR rules (RFC 4506)

  • All types padded to 4-byte boundaries; big-endian (network order).
  • int/unsigned/bool/enum = 4 bytes; hyper/uhyper = 8 bytes.
  • opaque[n] fixed = n bytes + pad to 4; opaque<m> variable = u32 len (≤ m) + bytes + pad.
  • string<m> = u32 len + UTF-8/ASCII bytes + pad (no NUL terminator on wire).
  • arrays: fixed T[n]; variable T<m> = u32 count + elements.
  • union switch(disc) { case … } = disc (4 bytes) + selected arm.
  • optional T* = bool present + (T if present) — used for linked lists (e.g., entry chains).
  • Defensive rule: validate every declared len/count against a cap BEFORE allocating.

8.7 NFSv4.1 (RFC 8881)

COMPOUND = { tag:string, minorversion:u32(=1), argarray:nfs_argop4<> } → { status, tag, resarray:nfs_resop4<> }. Ops execute left-to-right threading a current filehandle (cfh) and saved filehandle (sfh); first non-OK op halts the compound (I14).

Selected op set: SEQUENCE (must be first in v4.1; carries sessionid, slotid, sequenceid, highest_slotid), PUTROOTFH, PUTFH, PUTPUBFH, GETFH, SAVEFH, RESTOREFH, LOOKUP, LOOKUPP, ACCESS, GETATTR, SETATTR, READ, WRITE, COMMIT, OPEN, OPEN_CONFIRM (v4.0 only), OPEN_DOWNGRADE, CLOSE, LOCK, LOCKT, LOCKU, DELEGRETURN, READDIR, CREATE, REMOVE, RENAME, LINK, SECINFO, EXCHANGE_ID, CREATE_SESSION, DESTROY_SESSION, DESTROY_CLIENTID, RECLAIM_COMPLETE, TEST_STATEID, FREE_STATEID, BIND_CONN_TO_SESSION.

Session / slot table (exactly-once semantics, EOS):

 session = { sessionid:opaque[16], fore_channel_attrs{max_slots, max_req/resp size},
             back_channel_attrs, slot_table }
 slot[i] = { sequenceid:u32, cached_reply:opt, in_use:bool }
 rule: req.sequenceid == slot.sequenceid + 1  → execute, cache reply, bump
       req.sequenceid == slot.sequenceid      → replay cached reply (retransmit)
       req.sequenceid <  slot.sequenceid      → NFS4ERR_SEQ_FALSE_RETRY/MISORDERED
       req.sequenceid >  slot.sequenceid + 1  → NFS4ERR_SEQ_MISORDERED

Slot table replaces v3's DRC for v4.1 (bounded, negotiated, client-driven). highest_slotid lets server/client flow-control concurrency.

stateid = { seqid:u32, other:opaque[12] }. Special values: all-zeros (anonymous), all-ones (READ bypass). seqid bumps on each successful state-changing op on that stateid (I12). other identifies the open/lock/delegation owner-state.

OPEN carries: claim type (CLAIM_NULL new, CLAIM_PREVIOUS reclaim during grace, CLAIM_DELEGATE_CUR/PREV), share access/deny (READ/WRITE/BOTH), open owner, seqid, create flags. Returns a stateid + delegation (maybe). OPEN_CONFIRM exists in v4.0 only (v4.1 confirms via EXCHANGE_ID/sessions). CLOSE releases the open stateid.

Pseudo-fs: server presents a synthetic read-only namespace rooted at PUTROOTFH stitching exports together; clients traverse via LOOKUP without a MOUNT protocol. Export boundaries surface as fsid changes.

Delegations (read, Phase 8): server grants a client authority to cache + serve reads locally without revalidation; server recalls (via back channel, CB_RECALL) when a conflicting OPEN/WRITE arrives. Client must DELEGRETURN promptly. Lease-backed: delegation dies with the lease.

Credits (flow control): each request declares a CreditCharge (≥1, ∝ payload/64KB); server grants CreditResponse; client's in-flight is bounded by granted credits (I11, backpressure per principle 15). Sequence-number window (MessageId) validated against credits.

Compounded requests: chained PDUs via NextCommand offset; RELATED_OP flag = use prior op's FileId/SessionId/TreeId (e.g., CREATE+QUERY_INFO+CLOSE in one round-trip).

Oplock levels: NONE, II (shared read), EXCLUSIVE, BATCH. Lease (2.1+): R, RW, RWH (Read/Write/Handle caching) — finer than oplocks, survives handle close (handle-caching lease). Oplock/lease break: server sends OPLOCK_BREAK notification; client flushes + downgrades + acks before server proceeds.

Durable / persistent handles: CREATE with durable-handle context lets a client reclaim an open after a brief network drop (durable v1/v2) or node failover (persistent, CA shares — deferred). Reconnect via CREATE w/ DurableHandleReconnect context.

SMB3 security: signing (mandatory when negotiated; AES-128-CMAC in 3.0, AES-128-GMAC in 3.1.1), encryption (AES-128-CCM in 3.0, AES-128-GCM in 3.1.1), pre-auth integrity (SHA-512 hash chain over NEGOTIATE+SESSION_SETUP in 3.1.1 to thwart downgrade).

 C→S  RPC xid=A1 GETPORT? (skip if cached) ; then LOOKUP{dirfh=ROOT, name="data.bin"}
 S→C  LOOKUP OK {fh=H, obj_attrs, dir_attrs}                       # H minted from (fsid,ino,gen)
 C→S  RPC xid=A2 READ{fh=H, offset=0, count=1048576}
 S→C  READ OK {post_op_attr, count=1048576, eof=false, data=<1MiB>} # zero-copy from page cache
 C→S  RPC xid=A3 READ{fh=H, offset=1048576, count=1048576}
 S→C  READ OK {count=524288, eof=true, data=<512KiB>}              # short read at EOF

(b) UNSTABLE WRITE + COMMIT (NFSv3 async write):

 C→S  WRITE{fh=H, off=0, count=1MiB, stable=UNSTABLE, data} xid=B1
 S→C  WRITE OK {wcc, count=1MiB, committed=UNSTABLE, verf=V0}       # buffered, not fsync'd
 C→S  WRITE{fh=H, off=1MiB, count=1MiB, stable=UNSTABLE} xid=B2
 S→C  WRITE OK {committed=UNSTABLE, verf=V0}
 C→S  COMMIT{fh=H, off=0, count=2MiB} xid=B3
 S→C  COMMIT OK {wcc, verf=V0}                                      # fsync done; verf unchanged → safe
   if reply verf=V1 (≠V0): server rebooted; client MUST resend B1,B2 (buffered data lost)

(c) Silly-rename on open-unlink (NFSv3 client behavior):

 App: open("f") (fh=H, fd held) ; then unlink("f")
 Client: file still open → cannot truly REMOVE (stateless server has no open table)
   C→S RENAME{dir, "f" → ".nfs0000A1B2"}    # silly-rename: hide it, keep inode alive via link count
   App later close(fd) → C→S REMOVE{dir, ".nfs0000A1B2"}   # now actually delete
 Edge: client crash between → orphan .nfsXXXX files (operator cleanup runbook)

(d) Oplock break (SMB): see §8.9 sequence; instrument oplock_break_total{from,to}, break-ack latency.

8.12 DRC state table (xid × proc × client → cached reply)

 key   = hash(client_addr/clientid, prog, vers, proc, xid)
 entry = { key, state:{IN_PROGRESS|DONE}, reply_bytes:opt, ts, size }
 lookup outcomes:
   miss               → insert IN_PROGRESS, execute handler, on completion store DONE+reply
   hit DONE           → return cached reply (replay), refresh LRU ts          # I2
   hit IN_PROGRESS    → duplicate of an op still running → drop (client will retransmit later)
 eviction: LRU when size>cap or count>cap; premature eviction within retention → metric drc_evict_premature_total
 only non-idempotent procs cached (see §8.5 DRC column); idempotent procs bypass

11.1 Handles, inodes, attributes (vfs, store)

// FileHandle: opaque on the wire, structured internally (ADR-8).
struct FileHandle(Bytes);                       // ≤64B (v3) / ≤128B (v4)
struct FhInner { export_id: u16, fsid: u64, inode: u64, generation: u32 }
fn FileHandle::encode(inner: &FhInner) -> FileHandle;
fn FileHandle::decode(&self) -> Result<FhInner, RpcError>;   // validates len + magic

struct Inode {                                  // on-disk + cached
    ino: u64, gen: u32, kind: FileKind, mode: u32, nlink: u32,
    uid: u32, gid: u32, size: u64, blocks: u64, rdev: u64,
    atime: Timespec, mtime: Timespec, ctime: Timespec, fsid: u64,
}
enum FileKind { Reg, Dir, Symlink, Block, Char, Fifo, Socket }
  • FileHandle — ownership: value type, cheap clone (Bytes); mutation: immutable; concurrency: Send+Sync; persistence: none (derived); serialization: opaque<64>/opaque<128>; compat: magic+version byte → handle-format versioning (Compatibility & Versioning).
  • Inode — ownership: store owns canonical copy; mutation: under per-inode lock (I1); persistence: inode_map.rs, journaled (I6); serialization: postcard on disk, derived to Fattr3 on wire; concurrency: generation bump on free→reuse (I13).
struct Fattr3 { kind: FileKind, mode: u32, nlink: u32, uid: u32, gid: u32,
                size: u64, used: u64, rdev: (u32,u32), fsid: u64, fileid: u64,
                atime: Nfstime3, mtime: Nfstime3, ctime: Nfstime3 }
struct Sattr3 { mode: Option<u32>, uid: Option<u32>, gid: Option<u32>,
                size: Option<u64>, atime: SetTime, mtime: SetTime }
enum SetTime { DontChange, SetToServerTime, SetToClient(Nfstime3) }
struct WccData { before: Option<WccAttr>, after: Option<Fattr3> }
struct WccAttr { size: u64, mtime: Nfstime3, ctime: Nfstime3 }
struct Nfstime3 { seconds: u32, nseconds: u32 }
  • Fattr3/Sattr3/WccData — serialization: XDR (§8.4); mutation: built per-op from Inode; compat: field layout frozen by RFC 1813.

  • RpcCall — ownership: per-request, dropped after reply; concurrency: decoded on conn task; serialization: XDR (§8.1); mutation: none post-decode.

  • DrcKey/DrcEntry — ownership: sharded LRU in rpc::drc; concurrency: per-shard lock; persistence: optionally journaled (Phase 12); eviction: LRU under cap (§8.12, I2).

12.9 Failure Analysis

Journal corruption beyond tail → halt + operator fsck (forensic artifact: journal dump). Replay fails → refuse to serve (fail-safe, don't serve corrupt data). Lost UNSTABLE data on crash → client resends (verf rotation) — correct by design. Blast radius bounded by last checkpoint.

Conformance is correctness, not perf — keep a separate perf-regression gate (criterion + fio thresholds, bench.yml); fuzzing throughput (keep targets fast, no I/O in fuzz harness — use in-memory store).

13.8 Edge Cases

Old Linux client quirks (pre-4.x NFSv4.1 bugs); Windows SMB signing-required policy; macOS SMB client (different oplock behavior); jumbo frames; high-RTT links (WAN); mount option permutations.

13.9 Failure Analysis

Conformance regression → block release (CI gate). Fuzzer crash → security bug → embargo + fix + corpus + CVE process (SECURITY.md). Interop break → bisect against client kernel version. Forensic: captured pcap of failing exchange.

Performance Engineering

  • Zero-copy: READ via splice/sendfile (file→socket) bypassing user space; scatter-gather (writev) for XDR header + data payload; bytes::Bytes reference-counted slices avoid copies through the stack.
  • Write coalescing: buffer UNSTABLE writes; merge adjacent ranges; flush at rsize granularity; group-commit fsync (batch window 5 ms/256 ops) amortizes the durability syscall.
  • Readahead: client sizes window from FSINFO rtpref; pipeline next-block READs; server-side prefetch hint.
  • DRC lookup cost: sharded hashmap, O(1) per non-idempotent op; sharding keyed by client to avoid cross-client contention; measure lookup ns in criterion.
  • Lock-free connection state: per-connection task owns its buffers; shared subsystems via Arc + sharded locks; credit/in-flight accounting via atomics; avoid global mutexes on the hot path.
  • io_uring option: tokio-uring backend (feature flag) for batched submission + registered buffers + zero-syscall completion; fallback to epoll.
  • Syscall analysis: count syscalls/op (target: READ ≤ 2, WRITE-UNSTABLE ≤ 1 amortized); batch fsync; vectored I/O.
  • Allocator analysis: per-op allocation budget (target ~0 in steady state via buffer pools); jemalloc/mimalloc evaluation; track with heaptrack.
  • Cache analysis: inode-cache + dir-entry-cache + vnode→fd cache hit ratios; struct layout for cache-line friendliness (hot fields together).
  • Tail latency: p99 is the goal (§4); no GC (Rust); bounded queues prevent latency blowup; isolate fsync from metadata ops; measure under fsync storm + connection churn.
  • Tooling: criterion (micro), fio (macro, real mount), cargo flamegraph / perf (CPU), heaptrack (alloc), bpftrace (syscall/latency), tracing spans (per-op breakdown). Profiles archived in docs/performance/flamegraphs/.

Scalability Analysis

  • Primary bottlenecks: (1) global state-manager locks (v4 clientid/lease tables) → sharded by clientid; (2) DRC contention → sharded; (3) single backing store I/O → the hard ceiling for one node; (4) journal append serialization → group commit; (5) per-file lock-list scan → interval tree for hot files.
  • Connection scaling: tokio work-stealing handles 10k+ conns; memory per conn (buffers + state) bounds count; per-IP caps prevent single-client monopoly; target 4k soft / 16k hard.
  • Metadata scaling: GETATTR/LOOKUP dominate real workloads (P10) → inode + dir-entry caches are the lever; cache hit-ratio is the metadata-throughput knob; READDIRPLUS cuts round-trips.
  • Lock-table growth: bounded (1M global / 64k per client); interval-tree per file; eviction on client death (lease/NSM); memory ∝ active locks.
  • State-table growth (v4): ∝ clients × opens × locks × delegations; bounded per-client; sharded; lease expiry reclaims; journaled deltas bound memory.
  • Horizontal scaling: out-of-scope for data (non-goal: not clustered), but multiple independent exports/fsids can be served by separate daemons/nodes (export-level partitioning, cross-link #98); namespace federation via v4 referrals = PhaseDeferred.
  • Vertical scaling: more cores → more conn tasks (until shared-lock contention); faster NVMe → higher COMMIT throughput; more RAM → larger caches/DRC. The single-backing-store I/O ceiling is the dominant vertical limit.
  • Coordination overhead: none cross-node (single node); intra-node = lock sharding + atomics; lease renewal traffic ∝ clients (batched).
  • Network fanout: delegations/oplocks add back-channel recall traffic on conflict (∝ conflict rate, not steady state); COMPOUND/compound reduce round-trips.
  • Storage growth: journal checkpointed + truncated; inode map grows with file count (compact on free); data ∝ stored bytes.
  • Saturation signals: rising commit_latency (disk), *_at_cap_total (caps), lock-list scan time (hot file), shared-lock wait time (state contention).

Mental Models & First Principles

# Compressed Insight What It Predicts Bug Class Without It Resolving §
MM1 Every wire byte is attacker-controlled. Any declared length, offset, or count in an XDR or SMB message is chosen by the sender, not verified by physics. Validates every length before allocation; caps all arrays; never trusts declared count. Heap overflow, OOM via huge declared array, integer wrap on offset+length, the entire NFS/SMB CVE corpus in C implementations. §6 (P6), §7 (I1), §8.3, §8.11, Phase 0
MM2 Statefulness is a tradeoff, not a goal. v3 eliminated per-client state so recovery is free (retransmit); v4 added state to express locks/delegations correctly, and now must define a bounded recovery protocol (grace period). Each unit of state added must come with a matching recovery path. Any new state object triggers: what happens on server reboot? On lease expiry? On client crash? Grace-period omission: new locks granted before old reclaim completes → two clients believe they hold the same exclusive lock → data corruption. §6 (P3), §7 (I3, I4), §8.7, §8.9, Phase 8
MM3 Idempotency is not the same as safety. An operation is idempotent in effect but not in reply — WRITE at the same offset with the same data produces the same file state, but returns a wcc_data showing the pre-op state. The DRC caches the reply, not just suppresses re-execution, so retransmits see the correct reply for the original context. DRC must cache the full encoded reply, not just skip re-execution. In-progress entries must block duplicate dispatch, not race. WRITE retransmit returns stale wcc → client invalidates cache unnecessarily. REMOVE retransmit hits a fresh inode at the recycled name → wrong file deleted. §6 (P1), §7 (I2, I9), §8.12, Phase 4
MM4 A file handle is a capability, not an address. It encodes (export_id, fsid, inode, generation) but is opaque to the client. The generation number is the security-critical field: it revokes old handles when an inode is freed and reallocated. Without it, handle guessing → serving another user's file. Every handle decode must validate the generation against the live inode map. Old-handle-as-address: freed inode reused, handle resolves to new file, client reads/writes wrong file (security + correctness). §6 (P2), §7 (I1, I13), §8.4, §9 (ADR-08), Phase 2
MM5 Close-to-open is a protocol contract, not an implementation detail. NFS does not promise POSIX strong consistency; it promises that after one client closes and another opens, the opener sees what the closer flushed. The mechanism is GETATTR-on-open (revalidation) plus flush+COMMIT-on-close. Violating either half breaks the contract silently. The client must GETATTR on every open (not just cache TTL), and must block close() until COMMIT completes. Drop flush-on-close → reader opens before data is on stable storage → stale read, zero-length file observed by another client. §6 (P4), §7 (I5), Phase 5
MM6 Lease expiry is a hard boundary, not a hint. After a lease expires without renewal, the server must free all state that depended on that lease — open stateids, locks, delegations — before granting any new conflicting state. There is no middle ground: "probably still alive" is not a valid lease state. After expiry, the server must atomically: revoke state, then allow new grants. Extending lease beyond expiry "just in case" → two holders of the same exclusive lock or delegation → cache incoherence, data loss. §6 (P3), §7 (I4, I15), Phase 8
MM7 Group commit amortizes, not defers, durability. COMMIT (NFS) / FLUSH (SMB) means: by the time the reply is sent, the data is on stable storage. Group commit batches the fsync syscall across many COMMIT requests in a time window, but the reply is sent only after fsync completes. The client is the only one who chooses whether to risk UNSTABLE writes. Reply COMMIT only post-fsync, batch window measured in ms/ops, never in "hope the disk is fast." Replying to COMMIT before fsync completes → power loss between reply and disk write → data acknowledged by server is permanently lost (the cardinal NFS sin). §6 (P13), §7 (I5), §4, Phase 4, Phase 12
MM8 Backpressure must be protocol-visible, not silent. SMB credits and NFS in-flight caps are not internal throttles; they are the protocol's explicit backpressure mechanism. If the server has no more credit to grant, the client pauses. Silent internal queueing hides this and eventually causes OOM. Every cap must map to a defined protocol error or pause, not an internal queue growth. Accepting more in-flight ops than the system can absorb → memory pressure → OOM kill at a point where all in-flight ops are lost, not gracefully rejected. §6 (P7, P15), §7 (I11), §8.8, Phase 10–11

Linux nfsd + lockd uses the kernel VFS as the backing store — the kernel already handles locking, journaling, and metadata. This wins for deployments where the host filesystem (ext4, XFS, Btrfs, ZFS) provides the durability story and the goal is to expose existing data over NFS with minimal translation. The limitation is coupling: handle stability, export semantics, and interop quirks are bound to the host FS behavior, and there is no path to SMB from the same backing store.

NFS-Ganesha is architecturally the closest real system to this design: a userspace NFS server with a pluggable File System Abstraction Layer (FSAL, analogous to our vfs). It wins in heterogeneous environments where one server must front many different storage backends (local FS, object stores, GPFS, Ceph) without code changes. The limitation is that its FSAL abstraction and pthreads + TIRPC concurrency model have well-documented state-lock contention at scale; R3 shows the places to learn from and avoid.

Ceph (CephFS) made the opposite bet: distribute everything. Metadata is served by one or more MDS nodes backed by RADOS, data is striped across OSD nodes via the CRUSH algorithm. This wins for petabyte-scale workloads where no single node can hold the metadata working set and linear data scalability is required. The cost is a much higher operational complexity floor (RADOS, CRUSH tuning, MDS recovery) and latency that is structurally higher (MDS RPC adds one network hop vs local inode lookup). CephFS exposes NFS and SMB via gateways, but they are limited protocol translators, not first-class implementations.

Lustre is optimized for high-performance computing: massive sequential I/O from many clients to many storage targets, with a separate metadata target (MDT) per namespace. It wins for HPC scratch filesystems where aggregate bandwidth is the metric, not metadata rate or POSIX-consistency fineness. Its distributed lock manager (ldlm) is sophisticated but heavyweight; single-client GETATTR is typically slower than NFS due to LNET + MDT RPC. SMB is not a native Lustre protocol.

Samba (smbd) is the reference SMB server, using the host kernel VFS as its backing store, analogous to Linux nfsd but for SMB. It wins for Windows-ecosystem deployments requiring full AD integration, shadow copies, DFS, DFSR, and a mature implementation of every SMB edge case. Its oplock and share-mode implementation is the ground truth against which we test. It does not serve NFS, so cross-protocol consistency is not achievable in isolation.

Back-of-Envelope Capacity Model

All numbers derived step-by-step from System Constraints (§4). Formula shown.

1. Memory for 4,096 concurrent connections:

  • Per-conn buffers: recv buffer (2 MiB max msg) + send buffer (2 MiB) + state struct (~2 KiB) ≈ 4 MiB/conn.
  • 4,096 conns × 4 MiB = 16.4 GiB → approaches the 16 GiB RSS soft cap; hard cap must be ≤ 4,096 when other caches are loaded.

2. DRC memory at 65,536 entries:

  • Average reply size: GETATTR ≈ 200 B; WRITE reply ≈ 80 B; blended ≈ 300 B.
  • DRC entry overhead (key + state + LRU ptrs) ≈ 128 B.
  • 65,536 × (300 + 128) = 28 MiB ≈ 32 MiB cap (§4, confirmed).

3. Inode table memory for 10M files:

  • On-disk inode record ≈ 128 B (mode, uid, gid, size, times, gen = 8 fields × 8–16 B each).
  • In-memory cached inode ≈ 256 B (+ lock, refcount, vnode pointer).
  • Inode LRU cache = 500k hot inodes × 256 B = 128 MiB.
  • Full 10M inodes on disk = 10M × 128 B = 1.28 GB (negligible on NVMe).

4. Lock table memory at 1M global locks:

  • Per lock entry: owner (24 B) + byte range (16 B) + list ptrs (16 B) + state (4 B) ≈ 64 B.
  • 1M × 64 B = 64 MiB → within §4 budget.

5. READ throughput → required NVMe bandwidth:

  • Target: 2.5 GB/s (M5). Zero-copy: kernel page cache → socket, 0 user-space copy.
  • NVMe sequential read bandwidth needed: 2.5 GB/s (assuming warm cache; cold = NVMe bandwidth ÷ rsize amplification).
  • At rsize = 1 MiB, 2.5 GB/s ÷ 1 MiB = 2,500 READ ops/s on the I/O path.
  • Network: 2.5 GB/s × 8 = 20 Gbps → requires 25 GbE (§4 hardware assumption).

6. COMMIT throughput with group commit:

  • Target COMMIT p99 ≤ 15 ms. NVMe fsync latency ≈ 100–500 µs per fsync on NVMe.
  • Group commit window = 5 ms or 256 ops. In 5 ms, at 200k metadata ops/s → up to 1,000 COMMIT-eligible ops.
  • Effective fsync rate = 1 fsync per 5 ms = 200 fsyncs/s → amortizes across 256 COMMITs per fsync batch.
  • Each COMMIT adds ≤ 5 ms batching delay + ≤ 500 µs NVMe fsync = ≤ 5.5 ms p50; ≤ 15 ms p99 at 4× NVMe latency variance.

7. State table memory for 10,000 v4 clients, 64k opens each:

  • Per open state: stateid (16 B) + owner (24 B) + share flags (8 B) + fh ptr (8 B) ≈ 64 B.
  • 10k clients × 65,536 opens × 64 B = 40 GiB → exceeds RAM; therefore per-client cap 65,536 opens is the hard bound, but only a few thousand clients will have thousands of concurrent opens; realistic: 10k clients × 100 opens avg × 64 B = 64 MiB.

8. Grace period size bound:

  • Grace = 90 s = lease time. During grace, server must hold all reclaim state in memory.
  • Reclaim state: list of (clientid, claimed stateids) per client; bounded by pre-reboot state.
  • If state was journaled: replay is O(journal_size), bounded by journal checkpoint cycle (target ≤ 500 ms for 1 GB journal, Phase 12.4 criterion).

9. v4.1 slot table memory for 10k sessions, 128 slots each:

  • Per slot: seqid (4 B) + cached reply ptr (8 B) + in_use (1 B) + pad (3 B) ≈ 16 B.
  • 10k sessions × 128 slots × 16 B = 20 MiB (negligible).
  • Cached slot reply (avg 400 B) × 128 slots × 10k sessions = 512 MiB worst case → cap slot reply cache per session.

10. Portmap/rpcbind registration FD budget:

  • TCP/2049 (NFS), TCP/111 (portmap), TCP/445 (SMB), TCP/MOUNT, TCP/NLM = 5 listener FDs.
  • Per-connection FD: 1 TCP socket + 1 data file (average open per conn) = 2 FDs/conn.
  • 4,096 conns × 2 + 5 listeners = 8,197 FDs → well within 65,536 RLIMIT_NOFILE cap (§4).

Hard Questions (Self-Examination)

  1. Why does NFSv3 use a write verifier instead of a per-write sequence number for crash detection? (Synthesize §8.5 WRITE/COMMIT protocol + §6 P5 crash-only + §8.9 state machines.) A per-write sequence number requires per-client server state (the sequence), making v3 stateful. The write verifier is a server-wide value (boot ID) shared in every reply: clients can detect a reboot by verifier change without the server knowing anything about them. This preserves v3 statelessness. The cost: any UNSTABLE write whose COMMIT has not been confirmed must be resent if the verifier changes, because the server may have lost the buffer on reboot.

  2. If two clients concurrently LOOKUP the same name in a directory, is the result consistent? Under what protocol and conditions? (Synthesize §6 P4 CTO, §8.4 wcc, §8.7 COMPOUND, §7 I7.) Under NFSv3, LOOKUP is stateless and reads the server's current directory. Concurrent LOOKUP is safe (no write conflict), but each client may see a different result if a third client is concurrently creating the entry. Under NFSv4, the same holds but with GETATTR-based revalidation. Close-to-open guarantees only one-way ordering (after a write's close, a subsequent open revalidates) — it does not prohibit two concurrent LOOKUPs from racing with a CREATE.

  3. What is the exact invariant that makes DRC at-most-once for non-idempotent ops, and what breaks it? (Synthesize §6 P1, §7 I2/I9, §8.12 DRC state table.) The invariant is: for any non-idempotent op, the DRC entry is in DONE state before the reply is sent. If DRC is keyed incorrectly (e.g., xid-only without proc+client), two different ops from different clients with the same xid will collide. If eviction is premature (DONE entry evicted before client's retransmit window), the op will re-execute. If an IN_PROGRESS entry is stored before execution completes, a racing retransmit sees IN_PROGRESS and drops the request, but the handler completes — the reply is then stored but the retransmit has already given up; next retransmit will hit DONE correctly if within retention.

  4. Can a client observe a file's unlink while it still holds an open file descriptor? How does NFSv3 handle this differently from NFSv4? (Synthesize §8.10c silly-rename, §8.7 OPEN/CLOSE claims, §6 P3.) In NFSv3, the server has no open-file table. When the client UNLINKs a file it has open, the client must silly-rename it (§8.10c) to keep the inode alive via link count until close. In NFSv4, the server knows the file is open (OPEN stateid), and REMOVE returns NFS4ERR_FILE_OPEN or defers deletion until CLOSE. The stateful model makes server-side unlink deferral correct; the stateless model requires client cooperation.

  5. How does the grace period prevent split ownership of a lock after server reboot? What is the exact race it prevents? (Synthesize §6 P3, §7 I3/I4, §8.7 grace state machine, Phase 8.) Race: client A holds an exclusive lock. Server reboots. Before A reclaims its lock, client B opens the same file and is granted an exclusive lock. A then reclaims and the server grants it too: both hold exclusive — split ownership. Grace prevents this: during grace, only CLAIM_PREVIOUS (reclaim) is allowed; no new conflicting grants. Client B's LOCK gets NFS4ERR_GRACE. A's reclaim succeeds first, then B can attempt after grace ends.

  6. What is the performance implication of per-message integrity (krb5i) vs per-message privacy (krb5p) and when would you choose each? (Synthesize §6 P9, Phase 9.7 performance, Phase 9.2 auth, §4 throughput targets.) krb5i computes an HMAC (MIC) over the RPC call body — CPU cost is ~100–200 MB/s equivalent. krb5p wraps/encrypts the entire body — AES per chunk, roughly 50% of krb5i throughput without AES-NI, near parity with AES-NI. Choose krb5i when data on the wire is non-sensitive (e.g., reading public research data) but mutual authentication is required; choose krb5p when the network is hostile and data privacy is legally required (e.g., HIPAA, PCI-DSS). AUTH_SYS remains the throughput baseline (nearly free).

  7. Why is the slot table EOS mechanism in NFSv4.1 strictly better than the DRC for exactly-once semantics, and what does it trade away? (Synthesize §8.7 session/slot, §7 I10, §8.12 DRC.) The DRC keys on (xid, proc, client), requires the server to look up every incoming op, and has unbounded eviction risk. The slot table bounds the key space to negotiated slots, is client-driven (client knows which slot/seqid it used), requires O(1) lookup by slot index, and caches the reply per slot with no eviction ambiguity (the client drives slot reuse). What it trades: the client must manage slot concurrency explicitly (max_slots bounds in-flight); the server must cache the entire reply per slot (memory ∝ slots × avg reply size).

  8. A client writes 10 GiB in UNSTABLE mode and then sends a COMMIT. The server replies, and 1 second later a power failure occurs. How much data is guaranteed durable? (Synthesize §6 P13, §7 I5, §8.5 COMMIT, Phase 12.) All 10 GiB is guaranteed durable, because COMMIT reply means the data is on stable storage (fsync completed before reply, I5). If the server had not yet replied, no guarantee — but the server will not reply until fsync completes (principle 13). If the server replied COMMIT and then a crash occurs after the reply left the server's NIC, the data is on disk and survives. The durability contract is: reply = durable.

  9. What is the "thundering herd" problem in the lock manager, and how does the block list structure mitigate it? (Synthesize Phase 6.7 performance, §6 P7 bounded resources, lockmgr design.) When a popular file's exclusive lock is released, all blocked waiters could be woken simultaneously to compete for the lock — O(N) wakeups but only one granted, N-1 put back to sleep. The mitigation: the blocked-lock queue is ordered (FIFO or priority); on lock release, wake only the next head (or the subset of compatible readers) rather than all waiters. This converts thundering herd to O(1) per release. Instrumented via lock_blocked_current and lock_grant_latency.

  10. An SMB client holds an RWH (Read+Write+Handle-caching) lease on a file. Another client opens the same file. Walk the break sequence and identify every failure mode. (Synthesize §8.8–8.9 oplock break, §7 I15, Phase 11.2.) Server detects conflict → sends OPLOCK_BREAK to A downgrading RWH → A must flush dirty write-cached data (WRITE ops) → A must close handle-cached opens → A sends ack with new level. Failures: (a) A's network is partitioned → ack never arrives → server waits break_timeout → force-breaks, A's writes are lost (client must handle); (b) A is slow to flush → break_timeout expires → server revokes, second client gets access but A's unflushed writes are discarded; (c) server waits for break while holding a lock needed by A for the flush → deadlock (prevented by careful lock ordering in smb2::oplock).

  11. Why does the file-handle encode an export_id, not just an inode number? What attack does this prevent? (Synthesize §6 P2/P9/P11, §7 I1/I8, §8.4 handle encoding.) Without export_id, a client holding a handle for a file in export A could send it in a request for export B, and if inodes overlap (same inode number, different export), the server might serve B's inode to A's client. Including export_id (and validating it) contains the handle to its original export namespace. Combined with path-traversal containment (I8), this closes the cross-export handle confusion attack.

  12. Can two clients simultaneously read-delegate the same file? What happens when one of them writes? (Synthesize §8.7 delegations, §7 I15, Phase 8.2.) Yes: the server can grant read delegations to multiple clients simultaneously (they do not conflict). When a client (or a third client) attempts a conflicting WRITE (or OPEN with OPEN4_SHARE_DENY_READ), the server must recall all outstanding read delegations before granting the write access. Each delegation recall is independent (CB_RECALL sent per client); the server waits for DELEGRETURN from each or times out before proceeding. After all recalls, the write access is granted. If a delegation holder is unreachable, the server revokes the delegation after the recall timeout (I15, I4).

  13. What is the computational cost of export-root path containment, and how does it interact with symlinks? (Synthesize §6 P11, §7 I8, vfs::path design, Phase 2.6.) Containment requires tracking the current depth below the export root during component-wise resolution. Each .. decreases depth; if depth would go below zero (past the export root), reject. This is O(path_depth) per LOOKUP. Symlinks complicate this: server-side symlink resolution (not all protocols do this — v3 returns symlink targets for the client to resolve) must check that the resolved target, when re-anchored at the current directory, does not escape. Absolute symlinks (target starts with /) are especially dangerous: they must be re-rooted at the export root, not at the system root.

  14. If the DRC is full and must evict entries, what is the worst-case outcome, and how does the system recover? (Synthesize §6 P1, §7 I2, §8.12 DRC eviction, §4 DRC size.) Worst case: a DONE entry for a non-idempotent op (e.g., REMOVE) is evicted before the client's retransmit arrives. The client retransmits; no DRC hit → op executes again. For REMOVE, a second REMOVE of a name that now maps to a different (newly created) file with the same name → wrong file deleted. For RENAME, second execution of a completed rename may fail (name already moved) or corrupt state. Recovery: metric drc_evict_premature_total signals this; operator tunes DRC size up; the architectural lesson is that DRC size must exceed max-concurrent-xids × (2 × max RTT / op latency).

  15. What is the minimum set of on-disk data that must survive a crash to guarantee v3 file-handle stability after restart? (Synthesize §6 P2/P5, §7 I1/I13, store design, Phase 12.2.) Required: (a) the inode table (inode number → {generation, type, mode, uid, gid, size, times}), (b) the fsid registry (export_id → fsid), (c) the free-list/generation counter (so alloc bumps gen on reuse), (d) directory entries (name → inode). The generation is critical: without it, a reused inode number serves the old handle to the new file. The journal ensures these survive: inode-create/update/free records are in the WAL, and replay restores the table to the last committed state. Data files are addressed by inode number; their content need not be in the inode table, but their existence is tracked.

  16. Why is AUTH_SYS uid 0 not root on the server, and what is the precise chain of enforcement? (Synthesize §6 P9, §7 I8, Phase 9.2 auth, Threat Model.) AUTH_SYS sends uid/gid in cleartext — any client can claim uid=0. The enforcement chain is: (1) export ACL restricts which client IPs may access at all; (2) root_squash maps uid=0 to anon_uid before any access check; (3) the file permission check runs against the squashed uid; (4) if sec=krb5 is required, the GSS-verified principal replaces AUTH_SYS uid entirely. Step 2 (root_squash) is the key: even if all else fails, the server's access check never runs as uid=0 from an untrusted client. Without root_squash (no_root_squash), a client claiming uid=0 has root access to the exported tree.

  17. In NFSv4.1 COMPOUND, if OPEN succeeds but the subsequent LOCK fails, what state does the server hold? (Synthesize §7 I14, §8.7 COMPOUND, Phase 8.) I14 specifies partial-failure: the compound halts at the first non-OK op and returns results-so-far. The OPEN succeeded and returned a stateid; that stateid is now live in the server's open table. The LOCK failed (e.g., conflicting lock), so no lock stateid was created. The server holds an open stateid but no lock. The client's application must inspect the per-op status array, discover the LOCK failure, and either retry LOCK separately or issue CLOSE. The open stateid consumes server state until CLOSE or lease expiry.

  18. What is the one scenario where an NFSv3 server correctly sends a COMMIT reply before fsync completes? (Synthesize §6 P13, §7 I5, §8.5 COMMIT.) There is no such scenario. Principle 13 and invariant I5 are absolute: COMMIT reply = data on stable storage. Any implementation that replies before fsync completes is incorrect, not a "one valid exception." The only apparent exception is if the WRITE was FILE_SYNC or DATA_SYNC (fsync before WRITE reply), in which case COMMIT is a no-op and replies immediately — but the fsync happened at WRITE time, not skipped.

  19. How does SMB3.1.1 pre-auth integrity prevent dialect downgrade attacks? (Synthesize §8.8 SMB header, Phase 10.2 negotiate, ADR-12.) Pre-auth integrity builds a SHA-512 hash chain over the NEGOTIATE request and response, then the SESSION_SETUP exchange. This hash is bound to the session key. If a MITM downgrade the NEGOTIATE (e.g., remove 3.1.1 from the client's offered dialects), the resulting hash will differ from what the client computed for the original NEGOTIATE — the session key derivation fails, and the session setup is rejected. The critical insight: the integrity hash includes the NEGOTIATE bytes, so any tampering with the dialect list is detectable.

  20. If a client's SEQUENCE (NFSv4.1) arrives with a slot seqid that is 2 ahead of the server's slot state, what happens, and why is this not the same as a replay? (Synthesize §7 I10, §8.7 slot table EOS, Phase 7.) seqid > expected + 1 → NFS4ERR_SEQ_MISORDERED. This is not a replay (replay = seqid == cached, same request). This indicates the client skipped a slot seqid — possibly because it received an error response and retried with a new seqid without processing the gap. The server has no cached reply for the skipped seqid (it was never executed). The client must detect NFS4ERR_SEQ_MISORDERED and recover by re-establishing the slot seqid to the server's expected value, typically by restarting with DESTROY_SESSION + CREATE_SESSION.

  21. Why does a server's journal checkpoint not immediately reduce the journal's disk space usage? (Synthesize §6 P5, §7 I6, Phase 12.2, store::journal design.) A checkpoint writes a consistent snapshot of the current metadata state (inode table) and records the checkpoint position in the journal. Space cannot be reclaimed until all transactions before the checkpoint are no longer needed for recovery. "No longer needed" means they are older than the latest completed checkpoint and there is no in-progress recovery reading them. The journal can only be truncated (space freed) after the checkpoint is written and fsynced, and only records before the checkpoint's starting LSN can be discarded. Records written during checkpoint (concurrent writes) must be preserved.

  22. What is the practical cost of the VFS single-chokepoint principle (P12) when serving both NFS and SMB simultaneously? (Synthesize §6 P12, §3.2 vfs::vnode, §9 ADR-11, Phase 10.) The cost is that the VFS layer must reconcile two different semantic models: NFS advisory byte-range locks vs SMB share-mode exclusion, NFS case-sensitivity vs SMB case-insensitive name matching, NFS ACLs (POSIX mode bits + NFSv4 ACLs) vs SMB security descriptors (Windows DACL/SACL). Each protocol front-end must translate its semantics into VFS operations that the other protocol can observe correctly. The benefit is that a file written over SMB is immediately readable over NFS with consistent attributes and handles — a property impossible to guarantee with two separate backing stores.

  23. If 10,000 NFS clients all reconnect simultaneously after a 100-second network partition (beyond the 90-second lease time), what is the server's behavior? (Synthesize §7 I4, §8.7 grace, §4 max connections, Phase 8.9.) Leases expired during the 100-second partition. All client state (opens, locks, delegations) was revoked. When clients reconnect, they perform EXCHANGE_ID + CREATE_SESSION. The server is not in grace (grace is triggered by server reboot, not client reconnect). Each client gets a new clientid and must re-OPEN files (CLAIM_NULL, not CLAIM_PREVIOUS — state was revoked, not pending reclaim). The simultaneous reconnect creates a lease-renewal + OPEN storm: this tests the connection cap (4,096 soft, 16,384 hard) and the OPEN processing rate. Each OPEN succeeds with a new stateid, but no data loss occurred — COMMIT semantics ensure durable data survived.

  24. What makes the EXCLUSIVE CREATE mode in NFSv3 safe under retransmit, and what would break it? (Synthesize §6 P1, §7 I2, §8.5 CREATE, Phase 4.2.) EXCLUSIVE CREATE stores the createverf (a client-supplied 8-byte cookie) in the file's atime/mtime fields on the first create. On retransmit, the server finds the file exists, checks whether the stored createverf matches — if so, returns success (the original create), not EXIST. What breaks it: (1) another process writes the file between retransmits, changing atime/mtime, so the verf no longer matches → retransmit gets EXIST → application believes create failed → opens existing file in unexpected state; (2) the createverf is reused across different create attempts → a successful first create is confused for a retransmit of the second.

  25. What is the maximum in-flight write data a single client can have outstanding before a COMMIT is required, and how is this limit enforced? (Synthesize §6 P7/P15, §8.5 WRITE/COMMIT, §4 write throughput, Phase 4/12.) The limit is not protocol-imposed (NFS does not have explicit write credits like SMB). The practical limit is the server's buffer capacity for UNSTABLE writes: bounded by the memory ceiling minus other usage. In practice, clients are expected to COMMIT before the server's buffer pool fills. The backpressure mechanism is indirect: if the server is slow to accept WRITE (socket send buffer full, backpressure via TCP), the client blocks. The explicit bound is the in-flight RPC count per connection (NFS concurrency) × rsize; by design, a client issuing many UNSTABLEs without COMMIT will hit TCP backpressure first, not a protocol error.

Alternative Architectures (Roads Not Taken)

Alternative 1: Microkernel/Message-Passing Architecture

+---------------+       +---------------+       +---------------+
|  NFS3 Server  |  IPC  |  VFS Broker   |  IPC  |  Store Server |
|  (process)    |<----->|  (process)    |<----->|  (process)    |
+---------------+       +---------------+       +---------------+
       |                        ^                      |
       | IPC                    | IPC                  | IPC
       v                        |                      v
+---------------+               |               +---------------+
|  SMB2 Server  |<--------------+               | Journal Proc  |
|  (process)    |                               +---------------+
+---------------+

Regime where it wins: Maximum fault isolation — a crash in the SMB2 server cannot corrupt the VFS broker or the store. Used in real microkernel systems (Minix, QNX, seL4-based systems) where reliability trumps latency.

Real system that embodies it: NFS-Ganesha with FSAL running in separate processes (experimental), or more directly, the Hurd filesystem servers.

Why rejected: IPC latency between processes (even on the same machine) adds 10–50 µs per VFS call vs a function call within the same async task. For a target GETATTR p99 of 400 µs, this budget is spent before a single disk access. The shared-memory optimization brings it close to in-process, at which point you have essentially reinvented tokio channels — with more complexity.

Alternative 2: Log-Structured / Copy-on-Write Backing Store

+------------------+       +-----------------------+
|  Protocol Front  |       |  COW/Log-structured   |
|  (NFS3/v4/SMB2)  +------>|  Backing Store        |
+------------------+       |  (all writes append;  |
                            |   GC compacts)        |
                            +-----------+-----------+
                                        |
                            +-----------v-----------+
                            |  Snapshot / Clone     |
                            |  (free at COW cost)   |
                            +-----------------------+

Regime where it wins: Atomic snapshots, clone-on-write semantics, and write amplification reduction for SSDs — exactly the Btrfs/ZFS design. If the server must serve read-consistent snapshots of the filesystem at a point in time, COW is dramatically simpler than a traditional journal + checkpoint scheme.

Real system that embodies it: ZFS (Zettabyte File System) with its block-pointer tree, and Btrfs with its extent tree. Both back NFS servers in production (ZFS-backed NFS is common in FreeBSD/TrueNAS).

Why rejected: COW backing stores require a garbage collector to reclaim freed blocks, which introduces latency variance. The GC pause competes with the COMMIT p99 target. Additionally, implementing a production COW store from scratch alongside the protocol stack is two simultaneous hard problems. Using ZFS/Btrfs as the backing store (pass-through) remains an option (ADR-07 rejected alternative) but sacrifices handle stability without additional indirection.

Alternative 3: Stateless v4 via Persistent Client State Token

+------------------+       +-----------------------+
|  NFS4 Client     |       |  Stateless NFS4 Svr   |
|  (holds token)   +------>|  (no per-client table)|
+------------------+       |  token = encrypted    |
    |                       |  state blob in fh     |
    | includes:             +-----------------------+
    | { opens, locks,
    |   lease, stateids }

Regime where it wins: If the protocol could encode all state into opaque tokens issued to the client and verified on receipt (similar to JWT/macaroon patterns), the server becomes horizontally scalable — any node can serve any request. This is the design direction of some distributed caching protocols.

Real system that embodies it: HTTP stateless token auth (JWT); in filesystems, pNFS layouts move data-access tokens to clients. Some object stores (S3 pre-signed URLs) are effectively this.

Why rejected: Lock state cannot be safely encoded in a client-held token: if the client crashes, the token cannot be recalled. Mutual exclusion (locks) requires server-side arbitration — the server must know who holds the lock to detect conflicts. Encoding lock state in tokens creates a forgery problem (can the server verify the token without trusting the client?) that defeats the purpose.

Alternative 4: RDMA-First Transport (NFS-over-RDMA / SMB Direct)

+------------------+       +-----------------------+
|  NFS/SMB Client  |  RDMA |  NFS/SMB Server       |
|  (RNIC)          +======>|  (RNIC)               |
+------------------+  DMA  +-----------+-----------+
                    (bypass           |
                     kernel)          v
                               +------+------+
                               |  Store      |
                               |  (pinned    |
                               |   buffers)  |
                               +------------+

Regime where it wins: Ultra-low-latency HPC and AI/ML workloads where TCP/IP adds 50–200 µs of kernel overhead and RDMA delivers sub-10 µs one-way latency. At 100 GbE RDMA (RoCEv2), READ throughput is limited only by the NVMe, not the transport. GPUDirect Storage extends this to direct NIC↔GPU transfer.

Real system that embodies it: Lustre (LNET RDMA), GPFS/SpectrumScale (RDMA), NFS-over-RDMA (RFC 8267), SMB Direct (SMB3 RDMA Channel). All production HPC clusters above a few hundred nodes use some form.

Why rejected: RDMA requires RNIC hardware, specific network fabric (InfiniBand or RoCEv2), and a userspace driver stack (libibverbs/rdmacm) that replaces the tokio TCP path. This is a completely different transport architecture, not a feature flag. For a single-server learning project targeting commodity hardware, TCP is the right baseline. RDMA transport is deferred (PhaseDeferred("FINAL_BLUEPRINT §1")).
