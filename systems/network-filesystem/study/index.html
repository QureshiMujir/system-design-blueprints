Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does NFSv3 use a write verifier instead of a per-write sequence number for crash detection? (Synthesize §8.5 WRITE/COMMIT protocol + §6 P5 crash-only + §8.9 state machines.) A per-write sequence number requires per-client server state (the sequence), making v3 stateful. The write verifier is a server-wide value (boot ID) shared in every reply: clients can detect a reboot by verifier change without the server knowing anything about them. This preserves v3 statelessness. The cost: any UNSTABLE write whose COMMIT has not been confirmed must be resent if the verifier changes, because the server may have lost the buffer on reboot.
  2. If two clients concurrently LOOKUP the same name in a directory, is the result consistent? Under what protocol and conditions? (Synthesize §6 P4 CTO, §8.4 wcc, §8.7 COMPOUND, §7 I7.) Under NFSv3, LOOKUP is stateless and reads the server's current directory. Concurrent LOOKUP is safe (no write conflict), but each client may see a different result if a third client is concurrently creating the entry. Under NFSv4, the same holds but with GETATTR-based revalidation. Close-to-open guarantees only one-way ordering (after a write's close, a subsequent open revalidates) — it does not prohibit two concurrent LOOKUPs from racing with a CREATE.
  3. What is the exact invariant that makes DRC at-most-once for non-idempotent ops, and what breaks it? (Synthesize §6 P1, §7 I2/I9, §8.12 DRC state table.) The invariant is: for any non-idempotent op, the DRC entry is in DONE state before the reply is sent. If DRC is keyed incorrectly (e.g., xid-only without proc+client), two different ops from different clients with the same xid will collide. If eviction is premature (DONE entry evicted before client's retransmit window), the op will re-execute. If an IN_PROGRESS entry is stored before execution completes, a racing retransmit sees IN_PROGRESS and drops the request, but the handler completes — the reply is then stored but the retransmit has already given up; next retransmit will hit DONE correctly if within retention.
  4. Can a client observe a file's unlink while it still holds an open file descriptor? How does NFSv3 handle this differently from NFSv4? (Synthesize §8.10c silly-rename, §8.7 OPEN/CLOSE claims, §6 P3.) In NFSv3, the server has no open-file table. When the client UNLINKs a file it has open, the client must silly-rename it (§8.10c) to keep the inode alive via link count until close. In NFSv4, the server knows the file is open (OPEN stateid), and REMOVE returns NFS4ERR_FILE_OPEN or defers deletion until CLOSE. The stateful model makes server-side unlink deferral correct; the stateless model requires client cooperation.
  5. How does the grace period prevent split ownership of a lock after server reboot? What is the exact race it prevents? (Synthesize §6 P3, §7 I3/I4, §8.7 grace state machine, Phase 8.) Race: client A holds an exclusive lock. Server reboots. Before A reclaims its lock, client B opens the same file and is granted an exclusive lock. A then reclaims and the server grants it too: both hold exclusive — split ownership. Grace prevents this: during grace, only CLAIM_PREVIOUS (reclaim) is allowed; no new conflicting grants. Client B's LOCK gets NFS4ERR_GRACE. A's reclaim succeeds first, then B can attempt after grace ends.
  6. What is the performance implication of per-message integrity (krb5i) vs per-message privacy (krb5p) and when would you choose each? (Synthesize §6 P9, Phase 9.7 performance, Phase 9.2 auth, §4 throughput targets.) krb5i computes an HMAC (MIC) over the RPC call body — CPU cost is ~100–200 MB/s equivalent. krb5p wraps/encrypts the entire body — AES per chunk, roughly 50% of krb5i throughput without AES-NI, near parity with AES-NI. Choose krb5i when data on the wire is non-sensitive (e.g., reading public research data) but mutual authentication is required; choose krb5p when the network is hostile and data privacy is legally required (e.g., HIPAA, PCI-DSS). AUTH_SYS remains the throughput baseline (nearly free).
  7. Why is the slot table EOS mechanism in NFSv4.1 strictly better than the DRC for exactly-once semantics, and what does it trade away? (Synthesize §8.7 session/slot, §7 I10, §8.12 DRC.) The DRC keys on (xid, proc, client), requires the server to look up every incoming op, and has unbounded eviction risk. The slot table bounds the key space to negotiated slots, is client-driven (client knows which slot/seqid it used), requires O(1) lookup by slot index, and caches the reply per slot with no eviction ambiguity (the client drives slot reuse). What it trades: the client must manage slot concurrency explicitly (max_slots bounds in-flight); the server must cache the entire reply per slot (memory ∝ slots × avg reply size).
  8. A client writes 10 GiB in UNSTABLE mode and then sends a COMMIT. The server replies, and 1 second later a power failure occurs. How much data is guaranteed durable? (Synthesize §6 P13, §7 I5, §8.5 COMMIT, Phase 12.) All 10 GiB is guaranteed durable, because COMMIT reply means the data is on stable storage (fsync completed before reply, I5). If the server had not yet replied, no guarantee — but the server will not reply until fsync completes (principle 13). If the server replied COMMIT and then a crash occurs after the reply left the server's NIC, the data is on disk and survives. The durability contract is: reply = durable.
  9. What is the "thundering herd" problem in the lock manager, and how does the block list structure mitigate it? (Synthesize Phase 6.7 performance, §6 P7 bounded resources, lockmgr design.) When a popular file's exclusive lock is released, all blocked waiters could be woken simultaneously to compete for the lock — O(N) wakeups but only one granted, N-1 put back to sleep. The mitigation: the blocked-lock queue is ordered (FIFO or priority); on lock release, wake only the next head (or the subset of compatible readers) rather than all waiters. This converts thundering herd to O(1) per release. Instrumented via lock_blocked_current and lock_grant_latency.
  10. An SMB client holds an RWH (Read+Write+Handle-caching) lease on a file. Another client opens the same file. Walk the break sequence and identify every failure mode. (Synthesize §8.8–8.9 oplock break, §7 I15, Phase 11.2.) Server detects conflict → sends OPLOCK_BREAK to A downgrading RWH → A must flush dirty write-cached data (WRITE ops) → A must close handle-cached opens → A sends ack with new level. Failures: (a) A's network is partitioned → ack never arrives → server waits break_timeout → force-breaks, A's writes are lost (client must handle); (b) A is slow to flush → break_timeout expires → server revokes, second client gets access but A's unflushed writes are discarded; (c) server waits for break while holding a lock needed by A for the flush → deadlock (prevented by careful lock ordering in smb2::oplock).
  11. Why does the file-handle encode an export_id, not just an inode number? What attack does this prevent? (Synthesize §6 P2/P9/P11, §7 I1/I8, §8.4 handle encoding.) Without export_id, a client holding a handle for a file in export A could send it in a request for export B, and if inodes overlap (same inode number, different export), the server might serve B's inode to A's client. Including export_id (and validating it) contains the handle to its original export namespace. Combined with path-traversal containment (I8), this closes the cross-export handle confusion attack.
  12. Can two clients simultaneously read-delegate the same file? What happens when one of them writes? (Synthesize §8.7 delegations, §7 I15, Phase 8.2.) Yes: the server can grant read delegations to multiple clients simultaneously (they do not conflict). When a client (or a third client) attempts a conflicting WRITE (or OPEN with OPEN4_SHARE_DENY_READ), the server must recall all outstanding read delegations before granting the write access. Each delegation recall is independent (CB_RECALL sent per client); the server waits for DELEGRETURN from each or times out before proceeding. After all recalls, the write access is granted. If a delegation holder is unreachable, the server revokes the delegation after the recall timeout (I15, I4).
  13. What is the computational cost of export-root path containment, and how does it interact with symlinks? (Synthesize §6 P11, §7 I8, vfs::path design, Phase 2.6.) Containment requires tracking the current depth below the export root during component-wise resolution. Each .. decreases depth; if depth would go below zero (past the export root), reject. This is O(path_depth) per LOOKUP. Symlinks complicate this: server-side symlink resolution (not all protocols do this — v3 returns symlink targets for the client to resolve) must check that the resolved target, when re-anchored at the current directory, does not escape. Absolute symlinks (target starts with /) are especially dangerous: they must be re-rooted at the export root, not at the system root.
  14. If the DRC is full and must evict entries, what is the worst-case outcome, and how does the system recover? (Synthesize §6 P1, §7 I2, §8.12 DRC eviction, §4 DRC size.) Worst case: a DONE entry for a non-idempotent op (e.g., REMOVE) is evicted before the client's retransmit arrives. The client retransmits; no DRC hit → op executes again. For REMOVE, a second REMOVE of a name that now maps to a different (newly created) file with the same name → wrong file deleted. For RENAME, second execution of a completed rename may fail (name already moved) or corrupt state. Recovery: metric drc_evict_premature_total signals this; operator tunes DRC size up; the architectural lesson is that DRC size must exceed max-concurrent-xids × (2 × max RTT / op latency).
  15. What is the minimum set of on-disk data that must survive a crash to guarantee v3 file-handle stability after restart? (Synthesize §6 P2/P5, §7 I1/I13, store design, Phase 12.2.) Required: (a) the inode table (inode number → {generation, type, mode, uid, gid, size, times}), (b) the fsid registry (export_id → fsid), (c) the free-list/generation counter (so alloc bumps gen on reuse), (d) directory entries (name → inode). The generation is critical: without it, a reused inode number serves the old handle to the new file. The journal ensures these survive: inode-create/update/free records are in the WAL, and replay restores the table to the last committed state. Data files are addressed by inode number; their content need not be in the inode table, but their existence is tracked.
  16. Why is AUTH_SYS uid 0 not root on the server, and what is the precise chain of enforcement? (Synthesize §6 P9, §7 I8, Phase 9.2 auth, Threat Model.) AUTH_SYS sends uid/gid in cleartext — any client can claim uid=0. The enforcement chain is: (1) export ACL restricts which client IPs may access at all; (2) root_squash maps uid=0 to anon_uid before any access check; (3) the file permission check runs against the squashed uid; (4) if sec=krb5 is required, the GSS-verified principal replaces AUTH_SYS uid entirely. Step 2 (root_squash) is the key: even if all else fails, the server's access check never runs as uid=0 from an untrusted client. Without root_squash (no_root_squash), a client claiming uid=0 has root access to the exported tree.
  17. In NFSv4.1 COMPOUND, if OPEN succeeds but the subsequent LOCK fails, what state does the server hold? (Synthesize §7 I14, §8.7 COMPOUND, Phase 8.) I14 specifies partial-failure: the compound halts at the first non-OK op and returns results-so-far. The OPEN succeeded and returned a stateid; that stateid is now live in the server's open table. The LOCK failed (e.g., conflicting lock), so no lock stateid was created. The server holds an open stateid but no lock. The client's application must inspect the per-op status array, discover the LOCK failure, and either retry LOCK separately or issue CLOSE. The open stateid consumes server state until CLOSE or lease expiry.
  18. What is the one scenario where an NFSv3 server correctly sends a COMMIT reply before fsync completes? (Synthesize §6 P13, §7 I5, §8.5 COMMIT.) There is no such scenario. Principle 13 and invariant I5 are absolute: COMMIT reply = data on stable storage. Any implementation that replies before fsync completes is incorrect, not a "one valid exception." The only apparent exception is if the WRITE was FILE_SYNC or DATA_SYNC (fsync before WRITE reply), in which case COMMIT is a no-op and replies immediately — but the fsync happened at WRITE time, not skipped.
  19. How does SMB3.1.1 pre-auth integrity prevent dialect downgrade attacks? (Synthesize §8.8 SMB header, Phase 10.2 negotiate, ADR-12.) Pre-auth integrity builds a SHA-512 hash chain over the NEGOTIATE request and response, then the SESSION_SETUP exchange. This hash is bound to the session key. If a MITM downgrade the NEGOTIATE (e.g., remove 3.1.1 from the client's offered dialects), the resulting hash will differ from what the client computed for the original NEGOTIATE — the session key derivation fails, and the session setup is rejected. The critical insight: the integrity hash includes the NEGOTIATE bytes, so any tampering with the dialect list is detectable.
  20. If a client's SEQUENCE (NFSv4.1) arrives with a slot seqid that is 2 ahead of the server's slot state, what happens, and why is this not the same as a replay? (Synthesize §7 I10, §8.7 slot table EOS, Phase 7.) seqid > expected + 1 → NFS4ERR_SEQ_MISORDERED. This is not a replay (replay = seqid == cached, same request). This indicates the client skipped a slot seqid — possibly because it received an error response and retried with a new seqid without processing the gap. The server has no cached reply for the skipped seqid (it was never executed). The client must detect NFS4ERR_SEQ_MISORDERED and recover by re-establishing the slot seqid to the server's expected value, typically by restarting with DESTROY_SESSION + CREATE_SESSION.
  21. Why does a server's journal checkpoint not immediately reduce the journal's disk space usage? (Synthesize §6 P5, §7 I6, Phase 12.2, store::journal design.) A checkpoint writes a consistent snapshot of the current metadata state (inode table) and records the checkpoint position in the journal. Space cannot be reclaimed until all transactions before the checkpoint are no longer needed for recovery. "No longer needed" means they are older than the latest completed checkpoint and there is no in-progress recovery reading them. The journal can only be truncated (space freed) after the checkpoint is written and fsynced, and only records before the checkpoint's starting LSN can be discarded. Records written during checkpoint (concurrent writes) must be preserved.
  22. What is the practical cost of the VFS single-chokepoint principle (P12) when serving both NFS and SMB simultaneously? (Synthesize §6 P12, §3.2 vfs::vnode, §9 ADR-11, Phase 10.) The cost is that the VFS layer must reconcile two different semantic models: NFS advisory byte-range locks vs SMB share-mode exclusion, NFS case-sensitivity vs SMB case-insensitive name matching, NFS ACLs (POSIX mode bits + NFSv4 ACLs) vs SMB security descriptors (Windows DACL/SACL). Each protocol front-end must translate its semantics into VFS operations that the other protocol can observe correctly. The benefit is that a file written over SMB is immediately readable over NFS with consistent attributes and handles — a property impossible to guarantee with two separate backing stores.
  23. If 10,000 NFS clients all reconnect simultaneously after a 100-second network partition (beyond the 90-second lease time), what is the server's behavior? (Synthesize §7 I4, §8.7 grace, §4 max connections, Phase 8.9.) Leases expired during the 100-second partition. All client state (opens, locks, delegations) was revoked. When clients reconnect, they perform EXCHANGE_ID + CREATE_SESSION. The server is not in grace (grace is triggered by server reboot, not client reconnect). Each client gets a new clientid and must re-OPEN files (CLAIM_NULL, not CLAIM_PREVIOUS — state was revoked, not pending reclaim). The simultaneous reconnect creates a lease-renewal + OPEN storm: this tests the connection cap (4,096 soft, 16,384 hard) and the OPEN processing rate. Each OPEN succeeds with a new stateid, but no data loss occurred — COMMIT semantics ensure durable data survived.
  24. What makes the EXCLUSIVE CREATE mode in NFSv3 safe under retransmit, and what would break it? (Synthesize §6 P1, §7 I2, §8.5 CREATE, Phase 4.2.) EXCLUSIVE CREATE stores the createverf (a client-supplied 8-byte cookie) in the file's atime/mtime fields on the first create. On retransmit, the server finds the file exists, checks whether the stored createverf matches — if so, returns success (the original create), not EXIST. What breaks it: (1) another process writes the file between retransmits, changing atime/mtime, so the verf no longer matches → retransmit gets EXIST → application believes create failed → opens existing file in unexpected state; (2) the createverf is reused across different create attempts → a successful first create is confused for a retransmit of the second.
  25. What is the maximum in-flight write data a single client can have outstanding before a COMMIT is required, and how is this limit enforced? (Synthesize §6 P7/P15, §8.5 WRITE/COMMIT, §4 write throughput, Phase 4/12.) The limit is not protocol-imposed (NFS does not have explicit write credits like SMB). The practical limit is the server's buffer capacity for UNSTABLE writes: bounded by the memory ceiling minus other usage. In practice, clients are expected to COMMIT before the server's buffer pool fills. The backpressure mechanism is indirect: if the server is slow to accept WRITE (socket send buffer full, backpressure via TCP), the client blocks. The explicit bound is the in-flight RPC count per connection (NFS concurrency) × rsize; by design, a client issuing many UNSTABLEs without COMMIT will hit TCP backpressure first, not a protocol error.

Mental Models & First Principles

# Compressed Insight What It Predicts Bug Class Without It Resolving §
MM1 Every wire byte is attacker-controlled. Any declared length, offset, or count in an XDR or SMB message is chosen by the sender, not verified by physics. Validates every length before allocation; caps all arrays; never trusts declared count. Heap overflow, OOM via huge declared array, integer wrap on offset+length, the entire NFS/SMB CVE corpus in C implementations. §6 (P6), §7 (I1), §8.3, §8.11, Phase 0
MM2 Statefulness is a tradeoff, not a goal. v3 eliminated per-client state so recovery is free (retransmit); v4 added state to express locks/delegations correctly, and now must define a bounded recovery protocol (grace period). Each unit of state added must come with a matching recovery path. Any new state object triggers: what happens on server reboot? On lease expiry? On client crash? Grace-period omission: new locks granted before old reclaim completes → two clients believe they hold the same exclusive lock → data corruption. §6 (P3), §7 (I3, I4), §8.7, §8.9, Phase 8
MM3 Idempotency is not the same as safety. An operation is idempotent in effect but not in reply — WRITE at the same offset with the same data produces the same file state, but returns a wcc_data showing the pre-op state. The DRC caches the reply, not just suppresses re-execution, so retransmits see the correct reply for the original context. DRC must cache the full encoded reply, not just skip re-execution. In-progress entries must block duplicate dispatch, not race. WRITE retransmit returns stale wcc → client invalidates cache unnecessarily. REMOVE retransmit hits a fresh inode at the recycled name → wrong file deleted. §6 (P1), §7 (I2, I9), §8.12, Phase 4
MM4 A file handle is a capability, not an address. It encodes (export_id, fsid, inode, generation) but is opaque to the client. The generation number is the security-critical field: it revokes old handles when an inode is freed and reallocated. Without it, handle guessing → serving another user's file. Every handle decode must validate the generation against the live inode map. Old-handle-as-address: freed inode reused, handle resolves to new file, client reads/writes wrong file (security + correctness). §6 (P2), §7 (I1, I13), §8.4, §9 (ADR-08), Phase 2
MM5 Close-to-open is a protocol contract, not an implementation detail. NFS does not promise POSIX strong consistency; it promises that after one client closes and another opens, the opener sees what the closer flushed. The mechanism is GETATTR-on-open (revalidation) plus flush+COMMIT-on-close. Violating either half breaks the contract silently. The client must GETATTR on every open (not just cache TTL), and must block close() until COMMIT completes. Drop flush-on-close → reader opens before data is on stable storage → stale read, zero-length file observed by another client. §6 (P4), §7 (I5), Phase 5
MM6 Lease expiry is a hard boundary, not a hint. After a lease expires without renewal, the server must free all state that depended on that lease — open stateids, locks, delegations — before granting any new conflicting state. There is no middle ground: "probably still alive" is not a valid lease state. After expiry, the server must atomically: revoke state, then allow new grants. Extending lease beyond expiry "just in case" → two holders of the same exclusive lock or delegation → cache incoherence, data loss. §6 (P3), §7 (I4, I15), Phase 8
MM7 Group commit amortizes, not defers, durability. COMMIT (NFS) / FLUSH (SMB) means: by the time the reply is sent, the data is on stable storage. Group commit batches the fsync syscall across many COMMIT requests in a time window, but the reply is sent only after fsync completes. The client is the only one who chooses whether to risk UNSTABLE writes. Reply COMMIT only post-fsync, batch window measured in ms/ops, never in "hope the disk is fast." Replying to COMMIT before fsync completes → power loss between reply and disk write → data acknowledged by server is permanently lost (the cardinal NFS sin). §6 (P13), §7 (I5), §4, Phase 4, Phase 12
MM8 Backpressure must be protocol-visible, not silent. SMB credits and NFS in-flight caps are not internal throttles; they are the protocol's explicit backpressure mechanism. If the server has no more credit to grant, the client pauses. Silent internal queueing hides this and eventually causes OOM. Every cap must map to a defined protocol error or pause, not an internal queue growth. Accepting more in-flight ops than the system can absorb → memory pressure → OOM kill at a point where all in-flight ops are lost, not gracefully rejected. §6 (P7, P15), §7 (I11), §8.8, Phase 10–11

Glossary · 43 terms · site-wide glossary

NFS
Network File System; Sun's stateless (v3) / stateful (v4) RPC-based distributed filesystem protocol
SMB / CIFS
Server Message Block; Microsoft's file-sharing protocol; CIFS = legacy SMB1 (excluded); SMB2/3 = modern binary protocol
ONC RPC
Open Network Computing Remote Procedure Call (RFC 5531); the transport for NFS; call/reply with auth
XDR
External Data Representation (RFC 4506); 4-byte-aligned big-endian canonical wire encoding
file handle
Opaque, server-minted, stable reference to a file; encodes fsid+inode+generation; keystone of NFS statelessness
stateless
Server holds no per-client state (NFSv3); recovery = client retransmit; reboot transparent
stateful
Server holds client/open/lock state (NFSv4); recovery = explicit reclaim during grace
DRC
Duplicate Request Cache; caches replies keyed (xid,proc,client) for at-most-once non-idempotent ops
idempotent
Operation safe to execute multiple times with same effect (GETATTR, READ); vs non-idempotent (REMOVE, RENAME)
wcc
Weak Cache Consistency; pre+post-op attribute pair letting a client validate its cache after a mutation
close-to-open (CTO)
Consistency contract: revalidate on open, flush on close; not strong POSIX consistency
lease
Time-bounded grant of state (lock/delegation); must be renewed or state is revoked; bounds stale-state lifetime
delegation
Server grant of cache authority (read/write) to a client; recalled via back channel on conflict (NFSv4)
oplock
Opportunistic lock (SMB); client cache authority (II/Exclusive/Batch); broken by server on conflict
lease (SMB)
Finer-grained SMB2.1+ caching grant (R/RW/RWH); handle-caching lease survives file close
stateid
NFSv4 identifier {seqid, other} for an open/lock/delegation; seqid monotonic to detect stale use
COMPOUND
NFSv4 op array executed in one round-trip, threading current/saved filehandle; halts on first error
session / slot
NFSv4.1 exactly-once mechanism; slot table with per-slot sequenceid; replaces v3 DRC
EOS
Exactly-Once Semantics; guaranteed by v4.1 sessions/slots
NLM
Network Lock Manager (prog 100021); byte-range advisory locking sidecar for NFSv3
NSM
Network Status Monitor (prog 100024); reboot notification driving lock reclaim
silly-rename
Client renames an open-but-unlinked file to .nfsXXXX so the stateless server keeps it alive until close
ESTALE
Error: file handle no longer valid (inode freed/reused, gen mismatch); client must re-LOOKUP
root_squash
Export option mapping remote uid 0 to an anonymous uid; prevents remote-root privilege
AUTH_SYS
RPC auth flavor sending uid/gid in cleartext; advisory only; must be export-gated
RPCSEC_GSS
RPC security via GSSAPI/Kerberos; krb5 (authn), krb5i (integrity), krb5p (privacy)
NTLMSSP
NTLM Security Support Provider; challenge-response auth for SMB SESSION_SETUP
SPNEGO
Simple and Protected GSS-API Negotiation (RFC 4178); wraps NTLM/Kerberos selection in SMB
credit
SMB2 flow-control unit; bounds client in-flight requests; CreditCharge ∝ payload size
tree connect
SMB binding to a share (\\server\share); yields a TreeId scoping subsequent ops
durable handle
SMB handle that survives a brief network disconnect (durable) or node failover (persistent, deferred)
grace period
Post-reboot window (≥ lease time) where only state reclaim (CLAIM_PREVIOUS) is allowed; prevents split ownership
readdir cookie / verifier
Cursor + dir-version token for directory enumeration; verifier invalidates stale cookies after dir change
COMMIT
NFSv3 op forcing buffered UNSTABLE writes to stable storage; reply = durability acknowledgment
stable write
WRITE with stable=DATA_SYNC/FILE_SYNC (fsync before reply) vs UNSTABLE (buffered)
write verifier
Server-boot cookie returned by WRITE/COMMIT; change signals reboot → client resends UNSTABLE data
fsid
Filesystem identifier; distinguishes exports/mounts; part of the file handle
vnode / VFS
Virtual filesystem abstraction (inode-like in-memory node); the protocol-agnostic chokepoint layer
mount
Bootstrap of an export into a client namespace; v3 via MOUNT protocol, v4 via PUTROOTFH/pseudo-fs
portmap / rpcbind
RPC port directory (prog 100000, TCP/111); maps (prog,vers) → port
pseudo-fs
NFSv4 synthetic read-only root namespace stitching exports without a MOUNT protocol
pNFS
Parallel NFS; separates metadata from data via layouts; deferred (stub only)
BMC
Baseboard Management Controller; N/A to this project (out of scope)
