Decisions (§9) · 31 ADRs

ADR-01

Implementation language

Chosen

Rust (edition 2021, MSRV 1.75)

Rejected

C, C++, Go

When the rejected choice is right

C wins for embedding into existing kernel or C-native projects where FFI cost is prohibitive. Go wins when iteration speed dominates and p99 tail latency is not gated.

Why: Memory safety on hostile wire; fearless concurrency; no GC tail latency; zero-copy

ADR-02

Async runtime

Chosen

tokio (multi-thread scheduler)

Rejected

async-std, glommio, smol, thread-per-conn

When the rejected choice is right

glommio (io_uring + thread-per-core) wins on single-socket NVMe-only workloads where NUMA pinning and submission batching dominate; thread-per-conn wins when connection count is small (< 100) and simplicity matters most.

Why: Mature, work-stealing, io_uring via tokio-uring optional; ecosystem (rustls, tracing)

ADR-03

Project structure

Chosen

Cargo workspace, 12 crates (§1)

Rejected

monolithic crate

When the rejected choice is right

Monolithic crate wins on small one-person projects where compile speed is prioritized over boundary enforcement and the team never grows.

Why: Compile parallelism; enforced module boundaries; testable units

ADR-04

XDR codec

Chosen

Hand-written, trait-based (XdrEncode/XdrDecode)

Rejected

codegen from .x (rpcgen), serde-xdr

When the rejected choice is right

rpcgen-style codegen wins when the XDR schema is enormous and stable, and the team tolerates the generated code being a black box (e.g., internal RPC systems with a locked IDL).

Why: Defensive bounds-checks per field; zero-copy decode; codegen hides validation. Keep .x files as docs

ADR-05

SMB2 codec

Chosen

Hand-written struct (de)serializers

Rejected

nom combinators only

When the rejected choice is right

nom-only wins when the wire format is highly variable-length and recursive (e.g., ASN.1, DNS), and the fixed-offset advantages of SMB do not apply.

Why: Explicit length validation + fixed-offset layout; nom used for sub-parsers

ADR-06

Transport

Chosen

TCP w/ record-marking (RFC 5531); UDP for v3 optional, behind flag

Rejected

UDP-default, QUIC

When the rejected choice is right

UDP wins for legacy v3 clients on high-packet-count metadata workloads where TCP connection setup cost dominates (many short-lived mounts). QUIC wins when firewall traversal and 0-RTT reconnect are the primary constraints.

Why: TCP for large rsize/wsize + reliability; UDP DRC complexity deferred; QUIC = PhaseDeferred

ADR-07

Backing store

Chosen

Custom on-disk inode_map + data files + WAL journal

Rejected

pass-through to host FS, sqlite, LMDB

When the rejected choice is right

Pass-through wins when the host FS (e.g., ZFS or Btrfs) provides strong atomicity guarantees and you are building a pure protocol translator, not a storage engine. SQLite wins for small embedded deployments where operational simplicity outweighs performance.

Why: Need stable handles + generation numbers + crash-consistent metadata; pass-through can't guarantee handle stability across reboot

ADR-08

File-handle scheme

Chosen

encode(export_id:u16, fsid:u64, inode:u64, gen:u32) → ≤32 B, ≤64 cap

Rejected

raw inode, in-memory map, path-hash

When the rejected choice is right

In-memory map wins for a read-only demo server where handle stability across reboot is not a requirement and simplicity is paramount. Path-hash wins when the backing store is content-addressed (IPFS-style).

Why: Stable across reboot + cache eviction; gen defeats inode reuse; map-only loses stability

ADR-09

DRC design

Chosen

Sharded LRU keyed hash(client,prog,vers,proc,xid); per-conn + global cap

Rejected

global mutex map, no DRC

When the rejected choice is right

Global mutex wins when the number of concurrent clients is small (< 50) and memory is extremely constrained. No DRC wins only when all ops are idempotent (read-only exports).

Why: Lock contention avoided by sharding; bounded memory; correctness for non-idempotent ops

ADR-10

v4 state store

Chosen

In-memory tables + journaled deltas; rebuilt on reboot via grace+reclaim

Rejected

fully persistent DB, pure in-mem

When the rejected choice is right

Fully persistent DB (LMDB/RocksDB) wins when the grace period is impractical (many clients with long-lived state) or when instant reboot recovery without reclaim is required. Pure in-mem wins for test/ephemeral deployments.

Why: In-mem speed; journal for crash recovery; reclaim handles the rest (leases bound staleness)

ADR-11

Lock manager

Chosen

Integrated core engine; NLM as v3 front-end, v4 LOCK as another front-end

Rejected

separate NLM daemon, lockd

When the rejected choice is right

Separate lockd wins when you are building a minimal v3-only server that already has a production lockd and cannot replace it (e.g., integrating into an existing HPC cluster stack).

Why: One conflict engine → consistent semantics across protocols (principle 12)

ADR-12

SMB auth

Chosen

NTLMSSP (MS-NLMP) + Kerberos via system GSSAPI (libgssapi/gssapi crate)

Rejected

implement Kerberos, NTLM-only

When the rejected choice is right

NTLM-only wins for air-gapped deployments without an AD or Kerberos KDC where Kerberos infrastructure cannot be deployed. Implementing Kerberos wins only for embedded appliances that must be KDC-independent.

Why: Integrate, don't implement KDC (non-goal); Kerberos for AD interop

ADR-13

NFS auth

Chosen

AUTH_SYS + RPCSEC_GSS (krb5/krb5i/krb5p) via GSSAPI

Rejected

AUTH_SYS only

When the rejected choice is right

AUTH_SYS-only wins for internal-only clusters behind a firewall where all clients are trusted infrastructure and Kerberos operational overhead is prohibitive.

Why: GSS for real authn; AUTH_SYS advisory + export-gated

ADR-14

Client kernel bridge

Chosen

FUSE (fuser crate)

Rejected

custom kernel module, NFS-in-kernel

When the rejected choice is right

Custom kernel module wins for production deployments requiring maximum throughput (no FUSE round-trip overhead) and the team has kernel development expertise and a stable kernel ABI target.

Why: Userspace, portable, debuggable; kernel module out of scope

ADR-15

Serialization (internal)

Chosen

bincode/postcard for journal records; XDR/SMB on wire only

Rejected

JSON everywhere

When the rejected choice is right

JSON wins for operational tooling where human-readability of journal records is required for debugging without specialized tooling, accepting the size/speed cost.

Why: Compact, fast journal; wire formats fixed by spec

ADR-16

Logging

Chosen

tracing + tracing-subscriber (JSON + fmt layers)

Rejected

log crate, println

When the rejected choice is right

The log crate wins for library code that must remain runtime-agnostic; println wins for single-file prototype tools where setup cost is not warranted.

Why: Structured spans per RPC/op; correlation via xid/messageid

ADR-17

Metrics

Chosen

Prometheus via metrics + metrics-exporter-prometheus

Rejected

statsd, custom

When the rejected choice is right

statsd wins in environments where the observability stack is already push-based (e.g., Graphite/Carbon) and switching to pull is not feasible. Custom wins for deeply embedded appliances with no network observability infrastructure.

Why: Pull model; histograms for latency; standard tooling

ADR-18

Conformance testing

Chosen

pynfs (v4), Connectathon (v3+v4), smbtorture (SMB)

Rejected

bespoke only

When the rejected choice is right

Bespoke wins when the target is a protocol subset or extension not covered by existing suites, or when the conformance suite assumes behaviors that conflict with intentional deviations.

Why: Industry-standard suites; catch interop drift early

ADR-19

Fuzzing

Chosen

cargo-fuzz (libFuzzer) on XDR + SMB + handle decoders

Rejected

AFL only, none

When the rejected choice is right

AFL wins on non-Rust codebases. No fuzzing wins only for internal-only read-only services with no hostile wire input (extremely rare).

Why: Coverage-guided on parsers (highest-risk attack surface, principle 6)

ADR-20

Property testing

Chosen

proptest for DRC idempotency, handle stability, lock conflict algebra

Rejected

When the rejected choice is right

quickcheck wins for simpler properties where shrinking is not needed and the test corpus is naturally small; it also has wider language support outside Rust.

Why: Shrinking; model-based tests

ADR-21

Differential testing

Chosen

Decode/encode vs Wireshark dissectors + captured pcaps

Rejected

manual

When the rejected choice is right

Manual wins for extremely novel protocols where no reference dissector exists. It is strictly inferior here since Wireshark dissectors exist and are ground-truth.

Why: Ground-truth wire correctness

ADR-22

CI

GitHub Actions: fmt, clippy(-D warnings), test, fuzz-smoke, conformance, interop matrix

Jenkins wins in air-gapped enterprise environments where GitHub SaaS cannot be used and internal CI infrastructure already exists.

ADR-23

Benchmarking

Custom timers win for extremely tight embedded targets where criterion's statistical overhead is measurable, or for benchmarks that require hardware-counter access not available via criterion.

OpenSSL wins when FIPS 140-2 validation is required and rustls lacks a certified module, or when linking against an existing OpenSSL deployment on the host.

Alternative Architectures (Roads Not Taken)

Alternative 1: Microkernel/Message-Passing Architecture

+---------------+       +---------------+       +---------------+
|  NFS3 Server  |  IPC  |  VFS Broker   |  IPC  |  Store Server |
|  (process)    |<----->|  (process)    |<----->|  (process)    |
+---------------+       +---------------+       +---------------+
       |                        ^                      |
       | IPC                    | IPC                  | IPC
       v                        |                      v
+---------------+               |               +---------------+
|  SMB2 Server  |<--------------+               | Journal Proc  |
|  (process)    |                               +---------------+
+---------------+

Regime where it wins: Maximum fault isolation — a crash in the SMB2 server cannot corrupt the VFS broker or the store. Used in real microkernel systems (Minix, QNX, seL4-based systems) where reliability trumps latency.

Real system that embodies it: NFS-Ganesha with FSAL running in separate processes (experimental), or more directly, the Hurd filesystem servers.

Why rejected: IPC latency between processes (even on the same machine) adds 10–50 µs per VFS call vs a function call within the same async task. For a target GETATTR p99 of 400 µs, this budget is spent before a single disk access. The shared-memory optimization brings it close to in-process, at which point you have essentially reinvented tokio channels — with more complexity.

Alternative 2: Log-Structured / Copy-on-Write Backing Store

+------------------+       +-----------------------+
|  Protocol Front  |       |  COW/Log-structured   |
|  (NFS3/v4/SMB2)  +------>|  Backing Store        |
+------------------+       |  (all writes append;  |
                            |   GC compacts)        |
                            +-----------+-----------+
                                        |
                            +-----------v-----------+
                            |  Snapshot / Clone     |
                            |  (free at COW cost)   |
                            +-----------------------+

Regime where it wins: Atomic snapshots, clone-on-write semantics, and write amplification reduction for SSDs — exactly the Btrfs/ZFS design. If the server must serve read-consistent snapshots of the filesystem at a point in time, COW is dramatically simpler than a traditional journal + checkpoint scheme.

Real system that embodies it: ZFS (Zettabyte File System) with its block-pointer tree, and Btrfs with its extent tree. Both back NFS servers in production (ZFS-backed NFS is common in FreeBSD/TrueNAS).

Why rejected: COW backing stores require a garbage collector to reclaim freed blocks, which introduces latency variance. The GC pause competes with the COMMIT p99 target. Additionally, implementing a production COW store from scratch alongside the protocol stack is two simultaneous hard problems. Using ZFS/Btrfs as the backing store (pass-through) remains an option (ADR-07 rejected alternative) but sacrifices handle stability without additional indirection.

Alternative 3: Stateless v4 via Persistent Client State Token

+------------------+       +-----------------------+
|  NFS4 Client     |       |  Stateless NFS4 Svr   |
|  (holds token)   +------>|  (no per-client table)|
+------------------+       |  token = encrypted    |
    |                       |  state blob in fh     |
    | includes:             +-----------------------+
    | { opens, locks,
    |   lease, stateids }

Regime where it wins: If the protocol could encode all state into opaque tokens issued to the client and verified on receipt (similar to JWT/macaroon patterns), the server becomes horizontally scalable — any node can serve any request. This is the design direction of some distributed caching protocols.

Real system that embodies it: HTTP stateless token auth (JWT); in filesystems, pNFS layouts move data-access tokens to clients. Some object stores (S3 pre-signed URLs) are effectively this.

Why rejected: Lock state cannot be safely encoded in a client-held token: if the client crashes, the token cannot be recalled. Mutual exclusion (locks) requires server-side arbitration — the server must know who holds the lock to detect conflicts. Encoding lock state in tokens creates a forgery problem (can the server verify the token without trusting the client?) that defeats the purpose.

Alternative 4: RDMA-First Transport (NFS-over-RDMA / SMB Direct)

+------------------+       +-----------------------+
|  NFS/SMB Client  |  RDMA |  NFS/SMB Server       |
|  (RNIC)          +======>|  (RNIC)               |
+------------------+  DMA  +-----------+-----------+
                    (bypass           |
                     kernel)          v
                               +------+------+
                               |  Store      |
                               |  (pinned    |
                               |   buffers)  |
                               +------------+

Regime where it wins: Ultra-low-latency HPC and AI/ML workloads where TCP/IP adds 50–200 µs of kernel overhead and RDMA delivers sub-10 µs one-way latency. At 100 GbE RDMA (RoCEv2), READ throughput is limited only by the NVMe, not the transport. GPUDirect Storage extends this to direct NIC↔GPU transfer.

Real system that embodies it: Lustre (LNET RDMA), GPFS/SpectrumScale (RDMA), NFS-over-RDMA (RFC 8267), SMB Direct (SMB3 RDMA Channel). All production HPC clusters above a few hundred nodes use some form.

Why rejected: RDMA requires RNIC hardware, specific network fabric (InfiniBand or RoCEv2), and a userspace driver stack (libibverbs/rdmacm) that replaces the tokio TCP path. This is a completely different transport architecture, not a feature flag. For a single-server learning project targeting commodity hardware, TCP is the right baseline. RDMA transport is deferred (PhaseDeferred("FINAL_BLUEPRINT §1")).
