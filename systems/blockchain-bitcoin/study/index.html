Hard questions (§33)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does the fork-choice rule compare cumulative proof-of-work rather than chain length, and what attack does that prevent? (§16, §9 ADR-08, §30 MM2)
  2. How is a 10-block-deep reorg processed without corrupting the UTXO set mid-transition? (§16, §15, §7 I1/I3)
  3. What guarantees that a transaction valid under mempool-relay policy cannot silently become invalid under block-consensus validity, or vice versa? (§19, §7 I11, §30 MM3)
  4. Why is Bitcoin Script intentionally not Turing-complete, and what specific limit enforces that? (§14, §7 I9, §30 MM6)
  5. How does the [/4, ×4] difficulty-retarget clamp prevent a time-warp timestamp-manipulation attack from under-pricing difficulty? (§16, §7 I7, §22 T9, §32 C6)
  6. What concrete mechanism prevents a double-spend when two conflicting transactions are broadcast to disjoint peer subsets simultaneously? (§15, §22 T5, §7 I1)
  7. Why does headers-first sync verify chain-work before downloading any block body, and what does that decoupling buy? (§18, §30 MM8)
  8. How does the system distinguish a legitimately slow peer from an eclipse attacker isolating the node? (§18, §22 T1)
  9. What is the exact derivation of the maximum sustainable UTXO-set size before RocksDB read-latency degrades past the M7 target? (§4, §32 C1)
  10. Why is coinbase output spending delayed by exactly 100 blocks, and what specific attack does that window defend against? (§15, §7 I4, §9 ADR-18)
  11. What prevents a crafted script from becoming an unbounded-cost denial-of-service vector given Script's lack of loop opcodes? (§14, §7 I9, §22 T6)

  13. What is the precision cost of choosing cumulative-work selection (ADR-08) over GHOST, and in what regime would that choice reverse? (§9 ADR-08, §31, §5 Sompolinsky & Zohar 2015)
  14. How is deterministic, byte-identical serialization enforced across every node despite differing hardware/compiler versions? (§13, §7 I6)
  15. What is the concrete failure path if the UTXO database is corrupted by a torn write during a power loss, and how is it repaired without operator data loss? (§17, §23 FM-1, §7 I12)
  16. Why does the system separate the block DB from the UTXO DB rather than deriving one from live-only state, and what does that buy during a reorg? (§17, §16, §29)
  17. How does the reference nonce-search throughput (M12) relate to real-network mining difficulty, and why doesn't a single CPU core meaningfully compete? (§32 C5, §19)
  18. What stops a malicious rule change in mempool policy from silently altering consensus validity for already-mined blocks? (§7 I11, §25)

30. Mental Models & First Principles

MM1 — The UTXO model is a set of independent spendable facts, not an account balance. Predicts: independent transactions with disjoint inputs can validate in parallel. Bug class without it: treating balances as mutable account state reintroduces the double-spend problem Nakamoto 2008 solved. Resolving: §8, §7 I1.

MM2 — Chain selection is about cumulative proof-of-work, not chain length. Predicts a 5-block chain with less total work loses to a 3-block chain with more (Nakamoto 2008). Bug class without it: a length-based selection rule is trivially attackable by mining low-difficulty blocks fast. Resolving: §16, §9 ADR-08.

MM3 — Consensus rules and relay policy are different layers. Predicts a transaction can be policy-rejected by mempool rules yet still be consensus-valid once mined. Bug class without it: conflating the two makes soft-fork deployment impossible without a hard split. Resolving: §19, §7 I11.

MM4 — Determinism is what makes independent validation possible. Predicts any nondeterministic serialization breaks cross-node agreement on transaction/block hashes. Bug class without it: two honest nodes compute different hashes for the same logical transaction. Resolving: §13, §7 I6.

MM5 — Difficulty retargeting is a lagging control loop. Predicts hashrate shocks cause under/overshoot before the next 2016-block correction (§4). Bug class without it: assuming difficulty tracks hashrate instantaneously mispredicts block-interval variance after a mining migration. Resolving: §16, §32 C6.

MM6 — Script is intentionally not Turing-complete. Predicts no unbounded-loop DoS is possible; cost is bounded by opcode-count limits (I9), not gas metering. Bug class without it: adding a loop opcode reopens the halting-problem-adjacent DoS Bitcoin Script was designed to avoid. Resolving: §14, §7 I9.

MM7 — Reorgs are normal operation, not corruption. Predicts short reorgs must be handled automatically without operator intervention (P5). Bug class without it: treating any reorg as an error condition causes unnecessary node halts on routine network events. Resolving: §16, §23 FM-2.

MM8 — Headers-first sync decouples chain-work verification from block-content download. Predicts a node can commit to the best chain by header chain-work alone before downloading any transaction data. Bug class without it: a node that must download full blocks before comparing chains cannot efficiently discard a long low-work fork. Resolving: §18, §29.

Required reading (§5)

Books

  • Mastering Bitcoin (Antonopoulos, 2nd ed). Chapters: Ch. 6 Transactions, Ch. 7 Advanced Transactions and Scripting, Ch. 8 The Bitcoin Network, Ch. 9 The Blockchain, Ch. 10 Mining and Consensus. Extract: UTXO model, script semantics, wire protocol, PoW/difficulty mechanics. Applied in §8, Phase 2–4 (§14–§16), Phase 6 (§18).
  • Programming Bitcoin (Jimmy Song). Chapters: elliptic-curve cryptography, transaction structure, Script, networking. Extract: ECDSA verification and serialization worked examples. Applied in §5, Phase 1–2 (§13–§14).
  • Designing Data-Intensive Applications (Kleppmann). Chapters: replication, append-only logs, consistency. Extract: crash-recovery and WAL design tradeoffs. Applied in §5, Phase 5 (§17).
  • Database Internals (Petrov). Chapters: WAL, B-tree/LSM storage engines. Extract: RocksDB-style compaction and crash-recovery patterns for the UTXO DB. Applied in §5, Phase 5 (§17).
  • Rust Atomics and Locks (Mara Bos). Chapters: lock-free queues, memory ordering. Extract: mempool concurrent-insertion correctness. Applied in §5, Phase 7 (§19).
  • Zero To Production In Rust (Palmieri). Chapters: observability, structured logging, production service design. Extract: metrics/tracing scaffolding for the RPC/node runtime. Applied in §5, Phase 9 (§21), §24.

Papers

  • Nakamoto — "Bitcoin: A Peer-to-Peer Electronic Cash System" (2008). Contribution: PoW chain selection by cumulative work, UTXO-implicit transaction chaining. Applied in §5, Phase 4 (§16), §1.
  • Eyal & Sirer — "Majority Is Not Enough: Bitcoin Mining Is Vulnerable" (FC 2014). Contribution: selfish-mining strategy exploiting block-withholding. Applied in §5, §22 T2.
  • Heilman, Kendler, Zohar & Goldberg — "Eclipse Attacks on Bitcoin's Peer-to-Peer Network" (USENIX Security 2015). Contribution: peer-connection-slot exhaustion isolating a victim node. Applied in §5, §22 T1, Phase 6 (§18).
  • Decker & Wattenhofer — "Information Propagation in the Bitcoin Network" (IEEE P2P 2013). Contribution: empirical block/tx propagation-latency measurement. Applied in §5, §28 M5.
  • Gervais, Karame, Wüst, Glykantzis, Ritzdorf & Capkun — "On the Security and Performance of Proof of Work Blockchains" (CCS 2016). Contribution: quantitative double-spend/selfish-mining security model as a function of confirmation depth and propagation delay. Applied in §5, §22 T5, §32 C6.
  • Croman et al. — "On Scaling Decentralized Blockchains" (FC 2016). Contribution: identifies block size, propagation, and validation throughput as the binding scalability bottlenecks. Applied in §5, §29.
  • Sompolinsky & Zohar — "Secure High-Rate Transaction Processing in Bitcoin" (FC 2015). Contribution: GHOST heaviest-subtree alternative to longest/most-work chain selection. Applied in §5, §9 ADR-08, §34.
  • Bonneau, Miller, Clark, Narayanan, Kroll & Felten — "SoK: Research Perspectives and Challenges for Bitcoin and Cryptocurrencies" (IEEE S&P 2015). Contribution: systematized survey of Bitcoin's stability, privacy, and network properties. Applied in §5, §31.
  • Karame, Androulaki & Capkun — "Double-spending Fast Payments in Bitcoin" (CCS 2012). Contribution: zero-confirmation race-attack feasibility. Applied in §5, §22 T5.

Reference Implementations

  • Bitcoin Core (bitcoin/bitcoin). Study: src/validation.cpp, src/script/interpreter.cpp, src/net_processing.cpp. Lesson: strict separation of consensus rules from relay policy. Pitfall: conflating the two causes consensus-breaking soft forks. Applied in §5, Phase 3–4 (§15–§16), §7 I11.
  • btcd (btcsuite/btcd). Study: blockchain/validate.go, mining/mining.go. Lesson: independent Go reimplementation validates the protocol spec is language-agnostic. Pitfall: GC-driven latency spikes under load. Applied in §5, Phase 4 (§16), §9 ADR-01.
  • rust-bitcoin (rust-bitcoin/rust-bitcoin). Study: bitcoin/src/blockdata/, bitcoin/src/consensus/encode.rs. Lesson: consensus-encoding serialization patterns in Rust. Pitfall: encoding/decoding asymmetry silently breaks round-trip hashing. Applied in §5, Phase 1 (§13), §7 I6.
  • libbitcoin (libbitcoin/libbitcoin). Study: src/chain/, src/machine/ (script interpreter). Lesson: modular chain/network/wallet library boundaries. Pitfall: over-abstracted layering slows the validation hot path. Applied in §5, §10.
  • bcoin (bcoin-org/bcoin). Study: lib/blockchain/chaindb.js, lib/mempool/mempool.js. Lesson: JS full-node architecture proves the protocol is implementable outside systems languages. Pitfall: single-threaded event-loop mempool contention at scale. Applied in §5, Phase 7 (§19).

Glossary (§36) · 50 terms · site-wide glossary

UTXO
Unspent Transaction Output — the canonical spendable-value unit (I1)
Coinbase
The reward-granting first transaction of a block, subject to 100-block maturity (I4)
Merkle Root
Root hash of a block's transaction Merkle tree (I5)
Difficulty
A measure of how hard it is to find a valid PoW hash below the current target
Target
The 256-bit value a block header's SHA256d hash must be below to be valid (I2)
Bits
Compact 4-byte encoding of the current PoW target (§8)
Nonce
The 32-bit block-header field varied during PoW search
Reorg
Chain reorganization: switching the canonical tip to a higher-cumulative-work branch (I3)
Mempool
The pending, eventually consistent pool of unconfirmed transactions (I11)
P2PKH
Pay-to-Public-Key-Hash — the canonical single-signature script template (§8)
Fork
A point where two or more valid candidate chains diverge
SPV
Simplified Payment Verification — light-client validation via headers + Merkle proofs (§34)
Cumulative Work
Sum of per-block PoW difficulty along a chain, the fork-choice sort key (I3)
Median Time Past
Median timestamp of the last 11 blocks, used to bound timestamp manipulation
Script
The stack-based, non-Turing-complete transaction-locking/unlocking language (ADR-07)
OP_CHECKSIG
Script opcode verifying an ECDSA signature against a public key
OP_CHECKMULTISIG
Script opcode verifying M-of-N signatures against N public keys
Sighash
The transaction-digest algorithm signed by a spending signature
DER
Distinguished Encoding Rules — the strict signature encoding required by BIP-66
Base58Check
Address encoding with a version byte and checksum (ADR-11)
BIP-32
Hierarchical Deterministic Wallets specification
BIP-39
Mnemonic Seed specification for wallet backup
Halving
The every-210,000-block coinbase-reward reduction schedule (I8)
Double-Spend
An attempt to spend the same UTXO more than once (I1)
Orphan Transaction
A transaction referencing a not-yet-seen parent output
Orphan Block
A valid block that lost the fork-choice race to a competing branch
Headers-First Sync
Downloading and chain-work-verifying headers before block bodies (§30 MM8)
Inv/GetData
The P2P inventory-announcement and inventory-request message pair
Address Manager
Component tracking known peer addresses for connection selection (ADR-10)
Misbehavior Score
Cumulative peer-penalty counter driving automatic bans (ADR-23)
Eclipse Attack
Isolating a victim node's peer connections under attacker control (T1)
Selfish Mining
Withholding a valid block for relative mining advantage (T2)
Time-Warp Attack
Falsifying block timestamps to manipulate difficulty retargeting (T9)
WAL
Write-Ahead Log — the append-only durability mechanism preceding UTXO-DB commits (I12)
Fee Rate
Transaction fee divided by size, the mempool/block-inclusion priority key (ADR-12)
Child-Pays-For-Parent
Fee-priority interaction where a high-fee child boosts an unconfirmed parent
Coinbase Maturity
The 100-block delay before a coinbase output becomes spendable (I4)
GHOST
Greedy Heaviest-Observed Sub-Tree — a rejected alternative fork-choice rule (§9 ADR-08)
Compact Block Relay
BIP-152's bandwidth-reduced block-propagation scheme (deferred, §35)
Utreexo
Hash-based UTXO-set accumulator enabling stateless validation (§34 AA-2)
Lightning Network
Off-chain payment-channel layer atop Bitcoin (§34 AA-3)
Zerocash / Zcash
zk-SNARK shielded-transaction-pool construction (§34 AA-4)
Genesis Block
The first, hardcoded block of the chain, with no valid predecessor
Chain Tip
The block currently considered the head of the canonical chain (I3)
RocksDB
The LSM-tree key-value storage engine backing block/UTXO persistence (ADR-04)
CompactSize
Bitcoin's variable-length integer encoding used throughout consensus serialization
SHA256d
Double SHA-256, the hash function used for block/transaction hashing (ADR-05)
RIPEMD160
Hash function composed with SHA256 to produce HASH160 for addresses
secp256k1
The elliptic curve used for Bitcoin's ECDSA key pairs and signatures (ADR-06)
JSON-RPC
The request/response protocol exposing node control methods (ADR-13)
