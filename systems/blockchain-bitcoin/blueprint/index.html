1. Goal & Scope

Build a production-grade Bitcoin-like full-node implementation: double-SHA256 proof-of-work consensus, a UTXO transaction model with Bitcoin Script verification, a gossip-based P2P network with headers-first synchronization, a fee-prioritized mempool, persistent block/UTXO storage, a most-cumulative-work fork-choice rule with reorg handling, and a 21,000,000-coin halving emission schedule (Nakamoto 2008, §5) — implemented independently against the same consensus semantics as Bitcoin Core, without depending on its code.

Phase 0 deliverable — correctness-kernel modules/crates (numbered, normative; full tree in §10):

  1. chain-core — block/transaction/UTXO types, canonical serialization, hashing glue.
  2. chain-crypto — SHA256d, RIPEMD160, ECDSA/secp256k1 verification, Merkle trees.
  3. chain-script — Bitcoin Script stack VM, opcodes, parser, limits.
  4. chain-consensus — PoW target validation, difficulty retarget, fork choice, reorg.
  5. chain-storage — block DB, UTXO DB, indexes, WAL, crash recovery.
  6. chain-p2p — peer handshake, inventory relay, header/block sync, peer scoring.
  7. chain-mempool — transaction pool, fee-rate ordering, orphan handling.
  8. chain-node — full-node runtime, validation pipeline, peer manager, orchestration.
  9. chain-miner — block template builder, nonce search, target validation.
  10. chain-wallet — key management, address derivation, transaction construction/signing.
  11. chain-rpc — JSON-RPC server, node inspection APIs.
  12. chain-cli — wallet ops, mining commands, peer diagnostics driver binary.
  13. conformance/ — transaction/script/consensus vector fixtures.
  14. fuzz/ — transaction, block, and wire-parser fuzz targets.

System boundaries:

Provides: UTXO validation, double-SHA256 PoW consensus, Bitcoin Script interpretation, gossip P2P networking, headers-first sync, fee-prioritized mempool, persistent block/UTXO storage with crash recovery, most-work fork choice and reorg handling, wallet key management, JSON-RPC node control.

Delegates: elliptic-curve arithmetic to libsecp256k1 bindings (ADR-06); on-disk key-value storage internals to RocksDB (ADR-04); async I/O scheduling to Tokio (ADR-02).

Does NOT provide: SegWit/Taproot/Schnorr signature schemes, compact block relay, SPV/light clients, UTXO pruning, Lightning payment channels, parallel script execution, Utreexo accumulators, zk-proof shielded transactions, or a Turing-complete smart-contract VM. Each is either a deferred feature (§35) or a rejected Alternative Architecture (§34).

Non-goals: general-purpose smart-contract execution (§34 AA-3/AA-4 territory belongs to other systems, not this one — see the EVM row in §31); privacy-preserving shielded pools (§34 AA-4); mining-pool stratum protocol implementation (out of scope; single block-template interface only, §19).

Deployment model: single full-node process per host; optional standalone miner process talking to the node's RPC (§21); Docker image for reproducible deployment (§27); testnet/regtest network parameter sets alongside mainnet (§25).

Target users: systems engineers studying distributed consensus, cryptography engineers, blockchain-infrastructure teams, protocol researchers building simulation harnesses.

Language: Rust 1.78+.

Rationale: no garbage-collector pauses during consensus-critical validation (I2, I5); explicit unsafe boundaries around FFI to libsecp256k1 (ADR-06); strong sum-type modeling of the Script/consensus state machines (§8); memory safety against adversarial peer input (T3, T6); mature async ecosystem for the P2P/RPC layers (ADR-02); mature cryptography and RocksDB bindings (ADR-04, ADR-06).

Rejected languages: Go — weaker sum-type modeling for the Script opcode/consensus-state lattice, GC pauses conflict with the p99 block-validation target (§4), though btcd (§5 reference implementations) proves Go viable at lower assurance; C++ — memory-safety risk validating adversarial peer-supplied blocks/scripts (T3, T6) outweighs matching Bitcoin Core's native language; OCaml — strong ADTs but immature RocksDB/async-networking ecosystem versus Rust's Tokio/RocksDB bindings (ADR-02, ADR-04).

Required prerequisites: cryptographic hashing, elliptic-curve public-key cryptography, Merkle trees, TCP networking, distributed-systems fundamentals, Nakamoto consensus, binary serialization formats, async runtimes, LSM/B-tree storage-engine internals, Rust systems programming.

Timeline: Phase 0 — 10–14 weeks. Serialization, Script VM, UTXO engine, and PoW consensus (Phases 1–4) — 5–6 months cumulative. Storage, P2P, mempool/mining (Phases 5–7) — 9–10 months cumulative. Wallet, RPC, and hardening (Phases 8–9) — 12–14 months cumulative.

2. Why Build This

Bitcoin is the most-scrutinized deployed distributed system in existence: it forces one engineer to reason simultaneously about adversarial cryptography (ECDSA/secp256k1 malleability), Byzantine networking (eclipse attacks, Heilman et al. 2015, §5), deterministic state machines (UTXO validation, script execution), and economic-incentive-driven consensus (selfish mining, Eyal & Sirer 2014, §5). Few engineers who use cryptocurrencies can explain UTXO validation, chain reorganization, PoW target encoding, or fork-choice rules from first principles — building this system converts superficial familiarity into calibrated systems knowledge.

Core engineering competencies developed: deterministic consensus-state-machine design; adversarial protocol implementation; cryptographic verification pipelines; gossip-network design; crash-safe append-only storage; UTXO-set indexing; fork-choice and reorg handling; economic mempool policy design.

Historically relevant systems: Bitcoin Core, btcd, libbitcoin, rust-bitcoin, bcoin, Zcash (shielded-pool fork of the same UTXO lineage), Ethereum (account-model contrast, §31), Litecoin and other SHA256d/scrypt derivatives.

Cross-project alignment: Merkle Patricia Trie (inclusion proofs, shared with any state-commitment project); Distributed KV Store (replication vs. gossip propagation contrast); Raft Runtime (leader-based vs. leaderless PoW consensus contrast, §31); P2P Torrent Client (peer discovery and piece-inventory relay, directly analogous to inv/getdata, §18); Virtual Machine (stack-based execution model shared with chain-script, §14); Database Engine (append-only WAL and crash recovery, shared with chain-storage, §17).

Calibration value: completing the system demonstrates distributed-consensus literacy, adversarial-systems engineering, applied cryptography, and deterministic-runtime engineering — the exact skill cluster used by Bitcoin Core, btcd, and libbitcoin maintainers in production.

What Mastery Looks Like

  • Derive, from §4's UTXO-set-size ceiling, the maximum sustainable transaction rate before disk I/O becomes the bottleneck (§32 C1, Phase 3/§15).
  • Explain why the fork-choice rule compares cumulative proof-of-work, not chain length, and construct a counterexample where a longer chain loses (Phase 4/§16, §30 MM2).
  • Trace a P2PKH spend from scriptSig/scriptPubKey through the stack VM to a CHECKSIG verdict, citing every opcode transition (§8, Phase 2/§14).
  • Explain why script is intentionally not Turing-complete and what opcode-count limit enforces that (§7 I9, Phase 2/§14, §30 MM6).
  • Defend, against a staff-level reviewer, why headers-first sync is safe before any block body is downloaded (§18, Phase 6, §30 MM8).
  • Explain how a 10-block reorg is processed without corrupting the UTXO set (Phase 4–5/§16–§17, §7 I1/I3, §23 FM-2).
  • Derive the expected difficulty-retarget overshoot from a sudden 2x hashrate change given the 2016-block window (§32 C6, Phase 4/§16).

Client Interfaces — untrusted boundary; wallets, miners, explorers, and CLI tooling talk only through JSON-RPC (§9 ADR-13); no direct access to consensus or storage internals (§22 T10).

JSON-RPC Interface — request validation, cookie/local-bind authentication, method dispatch to node-runtime queries (Phase 9, §21).

Full Node Runtime — trusted core; owns the validation pipeline, sync-state machine, peer manager, and the bridge feeding accepted transactions into the mempool (Phase 0/§12 skeleton, Phase 6–7/§18–§19 wiring).

Consensus Engine — concurrency boundary; determines the canonical tip via cumulative work (I3), validates PoW (I2), runs difficulty retarget (Phase 4, §16) and reorg logic (§23 FM-2).

Transaction Engine — UTXO lookup, Script VM execution, ECDSA signature verification, fee computation, double-spend rejection (Phase 2–3, §14–§15).

Storage Layer — persistence boundary; block DB, UTXO DB, block/tx indexes, write-ahead log, crash recovery (Phase 5, §17).

Mempool — eventually consistent (P9); fee-rate-ordered pending-transaction pool feeding both RPC relay and the miner's block template (Phase 7, §19).

P2P Network — peer discovery via DNS seeds/address manager (ADR-10), version handshake (I14), inventory (inv/getdata) relay, headers-first synchronization (Phase 6, §18).

6. Design Principles

  1. P1 — Consensus safety over optimization. No performance shortcut may alter deterministic validation outcomes. Tradeoff: forgoes speculative-execution wins. Operational implication: every optimization PR must include a differential-fixture diff (§26). Violate it and nodes silently diverge (§22 T7).
  2. P2 — Validate before propagate. Invalid transactions/blocks are never relayed. Tradeoff: adds validation latency before the fast path to peers. Violate it and the network amplifies attacker-crafted invalid data (§22 T6).
  3. P3 — Canonical serialization. All hashes derive from one deterministic binary encoding (I6). Tradeoff: no schema flexibility without a version bump (§25). Violate it and identical transactions hash differently across nodes.
  4. P4 — Adversarial inputs are the default assumption. Every peer is untrusted (T1–T11 span all subsystems). Tradeoff: every parser needs bounds-checked recovery paths. Violate it and one peer can crash or desync the node.
  5. P5 — Reorgs are normal, not exceptional. Chain forks are expected operational behavior (§30 MM7). Tradeoff: UTXO-set updates must be reversible, not just applied. Violate it and a 2-block reorg corrupts state (§23 FM-2).
  6. P6 — UTXO integrity is sacred. The UTXO set is the sole canonical spend state (I1). Tradeoff: every code path touching balances must go through the UTXO engine, no shortcuts. Violate it and double-spends become possible.
  7. P7 — Persistence must survive crashes. Storage updates are atomic and WAL-backed (I12). Tradeoff: write latency includes a fsync-bound floor. Violate it and a power loss corrupts the UTXO DB (§23 FM-1).
  8. P8 — Networking is bounded. Peer message size, connection count, and bandwidth are capped (I10). Tradeoff: legitimate large batches must be chunked. Violate it and one peer can OOM the node (§22 T3/T4).
  9. P9 — Mempool is eventually consistent, consensus is not. Nodes' mempools may diverge; blocks must not (I11). Tradeoff: RPC callers must not treat mempool state as authoritative. Violate it and relay-policy bugs get mistaken for consensus bugs.
  10. P10 — Determinism over throughput. When correctness and speed conflict, correctness wins (§1). Tradeoff: some parallelism (e.g. §28 parallel script execution) stays deferred (§35) until proven consensus-safe. Violate it and validation becomes racy and unreproducible.
  11. P11 — Fail closed on malformed input. Ambiguous or malformed wire/script data is rejected, never best-effort-interpreted. Tradeoff: stricter parsers reject more edge cases outright. Violate it and a crafted malformed script silently executes with undefined semantics (§22 T6).
  12. P12 — Script is intentionally not Turing-complete. No loop opcodes; bounded op count (I9). Tradeoff: expressiveness is limited to what static analysis can bound. Violate it and a single script can DoS every validating node (§30 MM6).
  13. P13 — Separate consensus rules from relay policy. Consensus validity (block-inclusion) and mempool-acceptance policy are different rule sets (I11, ADR referenced in Bitcoin Core reference implementation, §5). Tradeoff: a transaction can be policy-rejected yet still consensus-valid once mined. Violate it and soft-fork deployment becomes impossible.
  14. P14 — Headers before bodies. Chain-work verification is decoupled from block-content download (§30 MM8). Tradeoff: a node can commit to a chain tip before validating full block contents. Violate it and initial sync cannot distinguish the best chain without downloading everything.

8. Domain Model / Protocol / Data Model

Core entity chain:

Block Header --PoW--> Block --contains--> Transaction[] --spends--> UTXO

Transaction wire layout (consensus encoding, ADR-03; little-endian ints, CompactSize varints):

Field Type Notes
version int32 tx format version
input_count varint (CompactSize) 1–9 bytes
inputs TxInput[] see below
output_count varint (CompactSize) 1–9 bytes
outputs TxOutput[] see below
locktime uint32 height or unix time; threshold 500,000,000

TxInput: prev_txid (32B, internal byte order reversed vs display), prev_index (uint32), script_sig_len (varint) + script_sig (bytes), sequence (uint32).

TxOutput: value (int64, satoshis), script_pubkey_len (varint) + script_pubkey (bytes).

Block header wire layout (80 bytes fixed, hashed via SHA256d, ADR-05):

Field Type Notes
version int32 block format / soft-fork signaling bits
prev_hash 32B hash of previous header
merkle_root 32B root of the block's transaction Merkle tree (I5)
timestamp uint32 unix time, validated against median-time-past
bits uint32 compact PoW target encoding
nonce uint32 PoW search field

Merkle tree construction (Phase 1, §13): binary SHA256d tree over transaction hashes; odd leaf duplicated per Bitcoin's original algorithm — a known Merkle duplicate-leaf block malleability (CVE-2012-2459). It is mitigated in block validation by rejecting any block whose Merkle tree contains a duplicated transaction (the mutated-block check in CheckBlock), a correctness rule independent of the BIP-30/BIP-34 duplicate-txid/coinbase-uniqueness rules (§26, §5).

Script grammar (EBNF; opcodes bounded to MAX_OPS_PER_SCRIPT = 201, I9):

script        ::= ( push_data | opcode )*
push_data     ::= byte_len data                (* len <= 75 for direct push *)
opcode        ::= OP_DUP | OP_HASH160 | OP_EQUALVERIFY | OP_CHECKSIG
                 | OP_CHECKMULTISIG | OP_EQUAL | OP_VERIFY | OP_RETURN | ...
data          ::= byte*

Step Stack (top last) Opcode
0 [] (scriptSig pushed) sig, pubkey
1 [sig, pubkey] OP_DUP
2 [sig, pubkey, pubkey] OP_HASH160
3 [sig, pubkey, hash160(pubkey)] <pubkeyhash> push
4 [sig, pubkey, hash160(pubkey), pubkeyhash] OP_EQUALVERIFY
5 [sig, pubkey] (verified equal, else abort) OP_CHECKSIG
6 [true/false] script succeeds iff top = true and stack non-empty

Worked example (P2PKH spend):

scriptPubKey: OP_DUP OP_HASH160 <pubkeyhash> OP_EQUALVERIFY OP_CHECKSIG
scriptSig:    <sig> <pubkey>
Execution:    push sig, push pubkey, then run scriptPubKey per the table above.

Malformed-input example: non-canonical (non-strict-DER) ECDSA signature encoding — rejected per BIP-66 (§5) at script-verification time (Phase 2, §14) rather than accepted with undefined malleability semantics (P11, I9).

Failure-path example: a block whose merkle_root does not match the recomputed transaction-hash tree (I5) — rejected at block-validation time (Phase 4, §16), the peer that relayed it is score-penalized (§22 T6), and the block is never added to the block DB (§23 FM-7).

29. Scalability Analysis

Constant vs grows (Big-O): script/signature verification cost is O(1) per transaction; UTXO lookup is O(1) amortized (hash-indexed RocksDB, ADR-04); block-validation cost grows linearly with transaction count per block; UTXO-set size grows with cumulative unspent output count, not directly with chain length (deferred pruning, §35, would decouple disk footprint from chain length entirely).

Named bottlenecks in order: (1) UTXO-DB random-read I/O at high validation throughput (Phase 3, §15) — Croman et al. 2016 (§5) identify this class of bottleneck as dominant at scale; (2) signature-verification CPU cost on multisig-heavy blocks (Phase 2, §14); (3) P2P bandwidth for full block relay at the 1MB block-size ceiling (§4) — mitigated in a future phase by deferred compact-block relay (§35); (4) mempool re-sort cost under sustained high-fee-rate churn (Phase 7, §19).

Horizontal scaling: not applicable to a single validating node (each full node independently validates the entire chain by design, per Nakamoto 2008); horizontal scaling instead means more independent full nodes strengthening network-level decentralization, not sharding validation work.

Vertical scaling: more CPU cores parallelize independent-transaction signature verification within a block (deferred parallel script execution, §35, once proven consensus-deterministic); faster storage raises the UTXO-DB read-throughput ceiling (M7).

Practical ceiling: the 1MB block-size cap (§4) bounds per-block transaction count; the UTXO-set size (§32 C1) bounds RocksDB working-set fit in memory before read latency degrades.

Levers beyond the ceiling: pruning (§35) decouples disk footprint from full chain history; Utreexo (§35, §34 AA-2) decouples UTXO-set-size growth from validation-node disk requirements entirely.

30. Mental Models & First Principles

MM1 — The UTXO model is a set of independent spendable facts, not an account balance. Predicts: independent transactions with disjoint inputs can validate in parallel. Bug class without it: treating balances as mutable account state reintroduces the double-spend problem Nakamoto 2008 solved. Resolving: §8, §7 I1.

MM2 — Chain selection is about cumulative proof-of-work, not chain length. Predicts a 5-block chain with less total work loses to a 3-block chain with more (Nakamoto 2008). Bug class without it: a length-based selection rule is trivially attackable by mining low-difficulty blocks fast. Resolving: §16, §9 ADR-08.

MM3 — Consensus rules and relay policy are different layers. Predicts a transaction can be policy-rejected by mempool rules yet still be consensus-valid once mined. Bug class without it: conflating the two makes soft-fork deployment impossible without a hard split. Resolving: §19, §7 I11.

MM4 — Determinism is what makes independent validation possible. Predicts any nondeterministic serialization breaks cross-node agreement on transaction/block hashes. Bug class without it: two honest nodes compute different hashes for the same logical transaction. Resolving: §13, §7 I6.

MM5 — Difficulty retargeting is a lagging control loop. Predicts hashrate shocks cause under/overshoot before the next 2016-block correction (§4). Bug class without it: assuming difficulty tracks hashrate instantaneously mispredicts block-interval variance after a mining migration. Resolving: §16, §32 C6.

MM6 — Script is intentionally not Turing-complete. Predicts no unbounded-loop DoS is possible; cost is bounded by opcode-count limits (I9), not gas metering. Bug class without it: adding a loop opcode reopens the halting-problem-adjacent DoS Bitcoin Script was designed to avoid. Resolving: §14, §7 I9.

MM7 — Reorgs are normal operation, not corruption. Predicts short reorgs must be handled automatically without operator intervention (P5). Bug class without it: treating any reorg as an error condition causes unnecessary node halts on routine network events. Resolving: §16, §23 FM-2.

MM8 — Headers-first sync decouples chain-work verification from block-content download. Predicts a node can commit to the best chain by header chain-work alone before downloading any transaction data. Bug class without it: a node that must download full blocks before comparing chains cannot efficiently discard a long low-work fork. Resolving: §18, §29.

Bitcoin Core made the same core decisions (UTXO, SHA256d PoW, cumulative-work selection) but in C++ with two decades of production hardening; wins wherever maximal ecosystem compatibility and battle-tested edge-case handling matter more than a from-scratch learning exercise.

btcd made the same protocol decisions in Go, proving the specification is language-agnostic; wins in Go-native infrastructure teams valuing GC-managed memory safety over Rust's ownership model.

Ethereum made a fundamentally different decision: account-based state plus a Turing-complete, gas-metered VM (EVM) instead of a constrained stack-based script (ADR-07); wins in the smart-contract/general-computation niche this project explicitly excludes (§1 non-goal, §34 AA territory).

Zcash made a different decision: layer a zk-SNARK shielded transaction pool atop the same UTXO lineage for transaction privacy; wins wherever regulatory or user demand for transaction-graph privacy outweighs the added proving-time and trusted-setup cost (§34 AA-4).

32. Back-of-Envelope Capacity Model

C1 — UTXO-set size at the storage ceiling. ~600 GB chain size at 10 years (§4) with an estimated 1 UTXO per ~300 bytes of chain history retained unspent (empirical Bitcoin-network ratio) → ≈2GB of live UTXO-set data at steady state, comfortably inside RocksDB's working-set fit for the 4GB peak-resident-memory ceiling (§4), leaving headroom for OS page cache before Phase 3's UTXO-DB read latency (M7) degrades.

C2 — Mempool transaction capacity. 300MB default mempool cap (§4) / ~250 bytes average transaction size = ≈1.2M transactions at full capacity — sets the upper bound the fee-rate ordering structure (ADR-12) must index efficiently without O(n) rescans.

C3 — Max transactions per block. 1,000,000-byte block cap (§4) / ~250 bytes average transaction size ≈ 4,000 transactions/block — the input to M2's validation-throughput target: at 4,000 tx/block and a 600s block interval, sustained throughput only needs ≈6.7 tx/s average, meaning M2's 5,000 tx/s target is dominated by burst catch-up during initial block download, not steady-state load.

C4 — Chain growth rate. 1MB/block × 144 blocks/day (600s interval) = 144MB/day ≈ 52.6GB/year — matches the §4 600GB/10-year storage-ceiling row within the same order of magnitude, confirming the retention assumption behind C1.

C5 — Expected PoW search space per block. Target block interval 600s (§4); at a reference single-CPU-core nonce-search rate of 2M H/s (M12, §28), a solo miner at that rate would need 2^32/2,000,000 ≈ 2,147s (~36 min) merely to exhaust the 32-bit nonce field once — confirming real-network mining requires either extra-nonce/timestamp rolling or vastly higher hashrate than a single reference core, which is why mining is modeled as a pool-scale activity, not a single-core loop, beyond the reference implementation in Phase 7 (§19).

C6 — Difficulty-retarget overshoot from a hashrate shock. A sudden 2x hashrate increase mid-window means the 2016-block window is actually solved in ~1008 blocks; the retarget algorithm (Phase 4, §16) computes the correction from the observed timespan, so difficulty roughly doubles at the next retarget boundary — bounded by the [/4, ×4] clamp (I7) even for an 8x+ shock, which is exactly why the clamp exists (Gervais et al. 2016, §5).

C7 — WAL write volume at peak validation rate. 4,000 tx/block (C3) × ~250B average consensus-encoded size ≈ 1MB/block of WAL payload beyond the block itself; at the M1 100ms p50 validation-latency target this implies a WAL write burst of ≈10MB/s sustainable, well within typical NVMe sequential-write bandwidth (~2–3GB/s), confirming disk I/O is not the dominant cost at C3's transaction density.

C8 — Peer bandwidth at max connections. 125 default max peer connections (§4) × 1MB max block size, in the worst case where every peer relays the same block once = 125MB burst bandwidth per block received — this is why inventory-based relay (inv/getdata, not raw block push, §18) exists: it lets a node request each block from only one peer, not all 125.

C9 — Failure-budget consistency check. 99.9% availability over a 30-day month = 43.2 min/month downtime budget (§4), matching the storage-crash-recovery (M9, ≤30s) plus a documented FM-2 deep-reorg-handling pause budget of a few minutes per incident — leaving wide margin under normal operation since M9 alone consumes under 2% of the monthly budget even at one incident per day.

34. Alternative Architectures (Roads Not Taken)

AA-1 — SPV / Light-Client Model.

[Header Chain Only] --compact filter request--> [Full Node] --BIP-157/158 filter--> [Client]

Wins in: mobile/resource-constrained clients that cannot store the full UTXO set. Real system: Neutrino (lightninglabs/neutrino, implementing BIP-157/158 compact block filters). Rejected because: this project's goal is a full validating node (§1); trusting filter-serving peers for transaction relevance is a materially weaker trust model than full validation.

AA-2 — Stateless / Accumulator-Based Full Nodes.

[UTXO Accumulator (hash-based)] --inclusion proof per spend--> [Stateless Validator]

Wins in: nodes needing sub-linear disk footprint instead of a full UTXO-DB copy. Real system: Utreexo (Dryja, "Utreexo: A Dynamic Hash-Based Accumulator Optimized for the Bitcoin UTXO Set," 2019). Rejected because: added proof-size/bandwidth overhead per transaction is unnecessary at this project's Phase 0–9 scope (§1); deferred as a future extension (§35).

AA-3 — Payment-Channel Network Layer.

[On-Chain Funding Tx] --off-chain HTLC updates--> [On-Chain Settlement Tx]

Wins in: high-frequency micropayments where on-chain fees per transaction are prohibitive. Real system: Lightning Network (Poon & Dryja, "The Bitcoin Lightning Network: Scalable Off-Chain Instant Payments," 2016). Rejected because: layer-2 routing, watchtowers, and channel-state disputes are a distinct system with its own consensus-adjacent complexity, out of this project's base-layer scope (§1, §35).

AA-4 — Shielded Transaction Pool (zk-SNARK Privacy).

[Transparent UTXO] --zk-SNARK proof--> [Shielded Pool] --zk-SNARK proof--> [Transparent UTXO]

Wins in: use cases requiring transaction-graph privacy beyond pseudonymity. Real system: Zcash, building on Sasson, Chiesa, Garman, Green, Miers, Tromer & Virza — "Zerocash: Decentralized Anonymous Payments from Bitcoin" (IEEE S&P 2014). Rejected because: zk-SNARK proving time and (for some constructions) trusted-setup requirements conflict with the §4 validation-latency targets and add cryptographic assumptions beyond the ECDSA/secp256k1 baseline (ADR-06).
