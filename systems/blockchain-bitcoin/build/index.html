⬜ Phase 0 — Workspace Bootstrap & Deterministic Build Infrastructure §12

Objectives

Establish a reproducible Cargo workspace, CI/CD, deterministic builds, tracing scaffolding, and the conformance-fixture harness every later phase depends on (P1, P10).

Deliverable

Bootstrapped, reproducible Rust workspace; empty trace-enabled chain-node and chain-cli binaries; CI pipeline (ci.yml) green on an empty crate tree.

Acceptance
  • Byte-identical release builds across 2 independent CI runs of the same commit.
  • All CI checks (lint, empty-test, SBOM) pass.
  • Conformance-fixture harness loads and validates fixtures/bootstrap/minimal.json with 0 errors.
Fixtures
  • fixtures/bootstrap/minimal.json — smallest buildable fixture-harness input.
  • smoke_node.rs — node process boots and exits cleanly.
Pitfalls
  • Nondeterministic timestamps embedded in build artifacts (breaks reproducible builds, §27).
  • Feature-flag incompatibility across crates causing silent link-time divergence.
  • Async-runtime deadlocks introduced before any real async work exists (premature complexity).

⬜ Phase 1 — Core Serialization, Hashing & Merkle Trees §13

Objectives

Implement deterministic consensus encoding (ADR-03), SHA256d/RIPEMD160 hashing (ADR-05), and Merkle-tree construction (§8), establishing I6 as a testable, enforced invariant.

Deliverable

Deterministic serialization/hashing library (chain-core, chain-crypto) — round-trip encode → decode → encode produces byte-identical output for every fixture.

Acceptance
  • 100% of tx_vectors.json and block_vectors.json fixtures round-trip with identical hashes (I6).
  • Merkle-root computation matches the reference value for a 7-transaction fixture block within merkle_vectors.json.
  • Varint boundary cases (0, 252, 253, 65535, 65536, u32::MAX) encode/decode correctly.
Fixtures
  • fixtures/serialize/tx_vectors.json — transaction encode/decode + hash vectors.
  • fixtures/serialize/block_vectors.json — block encode/decode + hash vectors.
  • fixtures/serialize/merkle_vectors.json — Merkle-root vectors including odd-leaf-count cases.
Pitfalls
  • Endianness bugs (Bitcoin mixes little-endian ints with reversed-byte-order hash display).
  • Malformed/oversized varints not bounds-checked (feeds T6).
  • Off-by-one in Merkle odd-leaf duplication producing a wrong root.

⬜ Phase 2 — Script VM & Signature Verification §14

Objectives

Implement the Bitcoin Script stack VM (ADR-07) with opcode/size limits (I9) and ECDSA/secp256k1 signature verification (ADR-06), enforcing P12 (non-Turing-completeness) and BIP-66 strict-DER validation (§5).

Deliverable

Bitcoin-like Script VM (chain-script) executing P2PKH and bare-multisig scripts with BIP-66-compliant signature checking.

Acceptance
  • p2pkh.json fixture: 100% of valid-spend cases verify true; 100% of tampered-signature cases verify false.
  • invalid_sig.json: non-strict-DER signatures rejected per BIP-66 with 0 false accepts.
  • A crafted script exceeding 201 ops is rejected in < 1ms (I9 enforcement latency).
Fixtures
  • fixtures/script/p2pkh.json — valid/invalid P2PKH spend vectors.
  • fixtures/script/invalid_sig.json — non-canonical/malformed signature vectors (BIP-66).
  • fixtures/script/multisig.json — bare-multisig (OP_CHECKMULTISIG) vectors.
Pitfalls
  • Stack underflow on malformed scripts not bounds-checked (crashes the VM, feeds T6).
  • Non-canonical (malleable) signature encodings silently accepted (BIP-66 violation).
  • Opcode-count DoS from a script just under the size limit but packed with cheap ops.

⬜ Phase 3 — UTXO Engine & Transaction Validation §15

Objectives

Implement the UTXO set (I1), double-spend/coinbase-maturity checks (I4), fee calculation, and BIP-30 duplicate-txid rejection (I13), establishing the transaction-validation kernel other phases build on.

Deliverable

Transaction-validation engine (chain-core + chain-storage UTXO integration) rejecting double-spends, immature-coinbase spends, and duplicate txids deterministically.

Acceptance
  • double_spend.json: 100% of double-spend attempts rejected (I1).
  • coinbase.json: immature-coinbase-spend fixture rejected; mature-coinbase-spend fixture accepted (I4).
  • Fee computation matches expected value to the satoshi across 50 fixture transactions.
Fixtures
  • fixtures/utxo/double_spend.json — same-input-twice vectors (I1).
  • fixtures/utxo/coinbase.json — maturity-boundary vectors (I4).
  • fixtures/utxo/duplicate_txid.json — BIP-30 vectors (I13).
Pitfalls
  • Stale UTXO reads under concurrent block/mempool access (race condition, feeds FM-3).
  • Off-by-one on the 100-block maturity boundary (I4).
  • Negative-fee (outputs > inputs) transactions not rejected before fee-rate computation.

⬜ Phase 4 — Proof-of-Work Consensus & Fork Choice §16

Objectives

Implement PoW target validation (I2), difficulty retargeting with clamping (I7), cumulative-work fork choice (I3, ADR-08), and reorg handling, per Nakamoto 2008's original consensus proof (§5).

Deliverable

Consensus-validating chain-selection engine (chain-consensus) correctly reorging between competing branches by cumulative work.

Acceptance
  • pow_vectors.json: 100% of target-boundary vectors validate correctly (I2).
  • reorg.json: a 10-block-deep simulated reorg completes with a UTXO-set checksum matching the expected post-reorg state (I1, I3).
  • Difficulty-retarget fixture with a simulated 4x hashrate spike clamps correctly per I7.
Fixtures
  • fixtures/consensus/pow_vectors.json — target/hash boundary vectors (I2).
  • fixtures/consensus/reorg.json — multi-branch reorg scenario (I3).
  • fixtures/consensus/retarget_clamp.json — [/4, ×4] boundary vectors (I7).
Pitfalls
  • Integer overflow in cumulative-work accumulation on long chains (u128 required, §11).
  • Off-by-one in the 2016-block retarget window boundary.
  • Reorg logic that mutates the UTXO set before confirming the new branch is fully valid (corruption risk, FM-1).

⬜ Phase 5 — Persistent Storage & Crash Recovery §17

Objectives

Implement durable block/UTXO storage (ADR-04/ADR-14) with a write-ahead log guaranteeing atomic, crash-recoverable state transitions (I12), per Kleppmann/Petrov storage-engine theory (§5).

Deliverable

Durable, crash-recoverable block/UTXO database (chain-storage) surviving an unclean shutdown without data loss beyond the last committed WAL entry.

Acceptance
  • recovery.rs: node restarts after a simulated crash mid-apply_block and recovers to a consistent state within the 30s target (§4).
  • snapshots.rs: UTXO-set checksum matches the expected value after 1,000 simulated block-applies.
  • WAL replay handles a truncated final record (partial write) without corrupting prior entries.
Fixtures
  • fixtures/storage/recovery.case — simulated crash mid-write.
  • fixtures/storage/snapshots.case — checksum-consistency corpus.
  • fixtures/storage/torn_write.case — truncated final WAL record.
Pitfalls
  • Torn writes on power loss not detected by a missing checksum (feeds FM-1).
  • Stale secondary indexes surviving a partial recovery.
  • Compaction stalls blocking new WAL appends under sustained load.

⬜ Phase 6 — P2P Networking & Headers-First Sync §18

Objectives

Implement peer handshake (I14), inventory relay, and headers-first chain synchronization, defending against eclipse attacks (Heilman et al. 2015, §5, §22 T1) via peer diversity.

Deliverable

Functional gossip P2P network (chain-p2p) synchronizing headers and blocks across peers with bounded resource usage per connection.

Acceptance
  • handshake.rs: a peer that sends any non-version message before completing the handshake is disconnected within one message (I14).
  • inv_relay.rs: a transaction announced by one node propagates to all connected fixture peers within the simulated network in < 2s (M5, §28).
  • Headers-first sync selects the most-work chain among two competing header sets before downloading any block body.
Fixtures
  • fixtures/p2p/handshake.case — premature-message rejection vectors (I14).
  • fixtures/p2p/inv_relay.case — propagation-latency simulation.
  • fixtures/p2p/headers_first.case — competing-headers chain-selection vectors.
Pitfalls
  • Peer flooding via rapid reconnect cycling (must be rate-limited, T3).
  • Inventory relay loops (re-announcing data just received back to its source).
  • Malformed packet parsing panics instead of rejecting cleanly (I10 violation, feeds T6).

⬜ Phase 7 — Mempool & Mining §19

Objectives

Implement the fee-prioritized mempool (ADR-12), orphan-transaction handling, block-template construction, and reference nonce-search mining, keeping mempool policy separate from consensus validity (I11, P13).

Deliverable

Mineable node (chain-mempool + chain-miner) producing valid, fee-optimized block templates consumable by a reference miner.

Acceptance
  • mempool.rs: fee-rate ordering matches expected priority across a 200-transaction fixture with 0 ordering violations.
  • miner.rs: 100% of template-derived blocks pass full consensus validation (Phase 4, §16) before broadcast.
  • Mempool eviction under simulated flood keeps memory usage under the 300MB cap (§4).
Fixtures
  • fixtures/mempool/mempool.case — fee-ordering corpus.
  • fixtures/mempool/orphans.case — missing-parent-then-arrival resolution vectors.
  • fixtures/miner/miner.case — template-to-valid-block vectors.
Pitfalls
  • Invalid fee accounting from double-counting change outputs.
  • Stale block templates mined against a tip that has since advanced (feeds FM-6).
  • Orphan-pool memory leaks from transactions whose parents never arrive.

⬜ Phase 8 — Wallet & Address Management §20

Objectives

Implement key generation, BIP-32 hierarchical derivation, Base58Check address encoding (ADR-11), and transaction signing, enforcing I15 (encrypted key-at-rest).

Deliverable

Functional wallet (chain-wallet) constructing and signing valid P2PKH transactions from a BIP-32-derived key hierarchy.

Acceptance
  • addresses.json: 100% of derived addresses match reference Base58Check vectors.
  • signing.json: 100% of signed transactions pass Phase 2 script verification (§14).
  • Wallet file on disk contains 0 unencrypted private-key bytes, scanned per I15.
Fixtures
  • fixtures/wallet/addresses.json — BIP-32 derivation + Base58Check vectors.
  • fixtures/wallet/signing.json — sign-then-verify round-trip vectors.
  • fixtures/wallet/encrypted_store.case — I15 plaintext-scan vectors.
Pitfalls
  • Weak entropy source for key generation (catastrophic key-recovery risk).
  • Incorrect sighash computation causing valid-looking but unverifiable signatures.
  • Wallet-file corruption from an unclean shutdown mid-write (feeds FM-9).

⬜ Phase 9 — RPC Interface & Observability §21

Objectives

Implement the JSON-RPC server (ADR-13) exposing node/wallet/miner control, and wire metrics, tracing, and structured logging into a coherent operability layer (§24).

Deliverable

Operable, observable full node (chain-rpc) exposing a stable JSON-RPC surface plus a metrics endpoint for production monitoring.

Acceptance
  • rpc.rs: 100% of documented RPC methods return schema-valid responses across the fixture corpus.
  • metrics.rs: all §24 metrics are present and non-zero after a 60-second simulated run.
  • RPC bound to a non-localhost address without explicit opt-in is rejected at startup (T10).
Fixtures
  • fixtures/rpc/rpc.case — method-response schema vectors.
  • fixtures/rpc/metrics.case — metrics-presence vectors.
  • fixtures/rpc/auth.case — cookie-auth and non-local-bind rejection vectors.
Pitfalls
  • Unauthenticated RPC exposed to the network by a misconfigured bind address (T10).
  • Unbounded RPC handler concurrency causing latency blowup under load (feeds FM-10).
  • Metric-label cardinality explosion from per-peer-ID labels without capping.
