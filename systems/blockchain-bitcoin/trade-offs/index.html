34. Alternative Architectures (Roads Not Taken)

AA-1 — SPV / Light-Client Model.

[Header Chain Only] --compact filter request--> [Full Node] --BIP-157/158 filter--> [Client]

Wins in: mobile/resource-constrained clients that cannot store the full UTXO set. Real system: Neutrino (lightninglabs/neutrino, implementing BIP-157/158 compact block filters). Rejected because: this project's goal is a full validating node (§1); trusting filter-serving peers for transaction relevance is a materially weaker trust model than full validation.

AA-2 — Stateless / Accumulator-Based Full Nodes.

[UTXO Accumulator (hash-based)] --inclusion proof per spend--> [Stateless Validator]

Wins in: nodes needing sub-linear disk footprint instead of a full UTXO-DB copy. Real system: Utreexo (Dryja, "Utreexo: A Dynamic Hash-Based Accumulator Optimized for the Bitcoin UTXO Set," 2019). Rejected because: added proof-size/bandwidth overhead per transaction is unnecessary at this project's Phase 0–9 scope (§1); deferred as a future extension (§35).

AA-3 — Payment-Channel Network Layer.

[On-Chain Funding Tx] --off-chain HTLC updates--> [On-Chain Settlement Tx]

Wins in: high-frequency micropayments where on-chain fees per transaction are prohibitive. Real system: Lightning Network (Poon & Dryja, "The Bitcoin Lightning Network: Scalable Off-Chain Instant Payments," 2016). Rejected because: layer-2 routing, watchtowers, and channel-state disputes are a distinct system with its own consensus-adjacent complexity, out of this project's base-layer scope (§1, §35).

AA-4 — Shielded Transaction Pool (zk-SNARK Privacy).

[Transparent UTXO] --zk-SNARK proof--> [Shielded Pool] --zk-SNARK proof--> [Transparent UTXO]

Wins in: use cases requiring transaction-graph privacy beyond pseudonymity. Real system: Zcash, building on Sasson, Chiesa, Garman, Green, Miers, Tromer & Virza — "Zerocash: Decentralized Anonymous Payments from Bitcoin" (IEEE S&P 2014). Rejected because: zk-SNARK proving time and (for some constructions) trusted-setup requirements conflict with the §4 validation-latency targets and add cryptographic assumptions beyond the ECDSA/secp256k1 baseline (ADR-06).
