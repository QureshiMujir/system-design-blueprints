32. Back-of-Envelope Capacity Model

C1 — UTXO-set size at the storage ceiling. ~600 GB chain size at 10 years (§4) with an estimated 1 UTXO per ~300 bytes of chain history retained unspent (empirical Bitcoin-network ratio) → ≈2GB of live UTXO-set data at steady state, comfortably inside RocksDB's working-set fit for the 4GB peak-resident-memory ceiling (§4), leaving headroom for OS page cache before Phase 3's UTXO-DB read latency (M7) degrades.

C2 — Mempool transaction capacity. 300MB default mempool cap (§4) / ~250 bytes average transaction size = ≈1.2M transactions at full capacity — sets the upper bound the fee-rate ordering structure (ADR-12) must index efficiently without O(n) rescans.

C3 — Max transactions per block. 1,000,000-byte block cap (§4) / ~250 bytes average transaction size ≈ 4,000 transactions/block — the input to M2's validation-throughput target: at 4,000 tx/block and a 600s block interval, sustained throughput only needs ≈6.7 tx/s average, meaning M2's 5,000 tx/s target is dominated by burst catch-up during initial block download, not steady-state load.

C4 — Chain growth rate. 1MB/block × 144 blocks/day (600s interval) = 144MB/day ≈ 52.6GB/year — matches the §4 600GB/10-year storage-ceiling row within the same order of magnitude, confirming the retention assumption behind C1.

C5 — Expected PoW search space per block. Target block interval 600s (§4); at a reference single-CPU-core nonce-search rate of 2M H/s (M12, §28), a solo miner at that rate would need 2^32/2,000,000 ≈ 2,147s (~36 min) merely to exhaust the 32-bit nonce field once — confirming real-network mining requires either extra-nonce/timestamp rolling or vastly higher hashrate than a single reference core, which is why mining is modeled as a pool-scale activity, not a single-core loop, beyond the reference implementation in Phase 7 (§19).

C6 — Difficulty-retarget overshoot from a hashrate shock. A sudden 2x hashrate increase mid-window means the 2016-block window is actually solved in ~1008 blocks; the retarget algorithm (Phase 4, §16) computes the correction from the observed timespan, so difficulty roughly doubles at the next retarget boundary — bounded by the [/4, ×4] clamp (I7) even for an 8x+ shock, which is exactly why the clamp exists (Gervais et al. 2016, §5).

C7 — WAL write volume at peak validation rate. 4,000 tx/block (C3) × ~250B average consensus-encoded size ≈ 1MB/block of WAL payload beyond the block itself; at the M1 100ms p50 validation-latency target this implies a WAL write burst of ≈10MB/s sustainable, well within typical NVMe sequential-write bandwidth (~2–3GB/s), confirming disk I/O is not the dominant cost at C3's transaction density.

C8 — Peer bandwidth at max connections. 125 default max peer connections (§4) × 1MB max block size, in the worst case where every peer relays the same block once = 125MB burst bandwidth per block received — this is why inventory-based relay (inv/getdata, not raw block push, §18) exists: it lets a node request each block from only one peer, not all 125.

C9 — Failure-budget consistency check. 99.9% availability over a 30-day month = 43.2 min/month downtime budget (§4), matching the storage-crash-recovery (M9, ≤30s) plus a documented FM-2 deep-reorg-handling pause budget of a few minutes per incident — leaving wide margin under normal operation since M9 alone consumes under 2% of the monthly budget even at one incident per day.
