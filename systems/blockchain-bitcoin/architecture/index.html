Client Interfaces — untrusted boundary; wallets, miners, explorers, and CLI tooling talk only through JSON-RPC (§9 ADR-13); no direct access to consensus or storage internals (§22 T10).

JSON-RPC Interface — request validation, cookie/local-bind authentication, method dispatch to node-runtime queries (Phase 9, §21).

Full Node Runtime — trusted core; owns the validation pipeline, sync-state machine, peer manager, and the bridge feeding accepted transactions into the mempool (Phase 0/§12 skeleton, Phase 6–7/§18–§19 wiring).

Consensus Engine — concurrency boundary; determines the canonical tip via cumulative work (I3), validates PoW (I2), runs difficulty retarget (Phase 4, §16) and reorg logic (§23 FM-2).

Transaction Engine — UTXO lookup, Script VM execution, ECDSA signature verification, fee computation, double-spend rejection (Phase 2–3, §14–§15).

Storage Layer — persistence boundary; block DB, UTXO DB, block/tx indexes, write-ahead log, crash recovery (Phase 5, §17).

Mempool — eventually consistent (P9); fee-rate-ordered pending-transaction pool feeding both RPC relay and the miner's block template (Phase 7, §19).

P2P Network — peer discovery via DNS seeds/address manager (ADR-10), version handshake (I14), inventory (inv/getdata) relay, headers-first synchronization (Phase 6, §18).

8. Domain Model / Protocol / Data Model

Core entity chain:

Block Header --PoW--> Block --contains--> Transaction[] --spends--> UTXO

Transaction wire layout (consensus encoding, ADR-03; little-endian ints, CompactSize varints):

Field Type Notes
version int32 tx format version
input_count varint (CompactSize) 1–9 bytes
inputs TxInput[] see below
output_count varint (CompactSize) 1–9 bytes
outputs TxOutput[] see below
locktime uint32 height or unix time; threshold 500,000,000

TxInput: prev_txid (32B, internal byte order reversed vs display), prev_index (uint32), script_sig_len (varint) + script_sig (bytes), sequence (uint32).

TxOutput: value (int64, satoshis), script_pubkey_len (varint) + script_pubkey (bytes).

Block header wire layout (80 bytes fixed, hashed via SHA256d, ADR-05):

Field Type Notes
version int32 block format / soft-fork signaling bits
prev_hash 32B hash of previous header
merkle_root 32B root of the block's transaction Merkle tree (I5)
timestamp uint32 unix time, validated against median-time-past
bits uint32 compact PoW target encoding
nonce uint32 PoW search field

Merkle tree construction (Phase 1, §13): binary SHA256d tree over transaction hashes; odd leaf duplicated per Bitcoin's original algorithm — a known Merkle duplicate-leaf block malleability (CVE-2012-2459). It is mitigated in block validation by rejecting any block whose Merkle tree contains a duplicated transaction (the mutated-block check in CheckBlock), a correctness rule independent of the BIP-30/BIP-34 duplicate-txid/coinbase-uniqueness rules (§26, §5).

Script grammar (EBNF; opcodes bounded to MAX_OPS_PER_SCRIPT = 201, I9):

script        ::= ( push_data | opcode )*
push_data     ::= byte_len data                (* len <= 75 for direct push *)
opcode        ::= OP_DUP | OP_HASH160 | OP_EQUALVERIFY | OP_CHECKSIG
                 | OP_CHECKMULTISIG | OP_EQUAL | OP_VERIFY | OP_RETURN | ...
data          ::= byte*

P2PKH state machine (Phase 2, §14; canonical spend path):

Step Stack (top last) Opcode
0 [] (scriptSig pushed) sig, pubkey
1 [sig, pubkey] OP_DUP
2 [sig, pubkey, pubkey] OP_HASH160
3 [sig, pubkey, hash160(pubkey)] <pubkeyhash> push
4 [sig, pubkey, hash160(pubkey), pubkeyhash] OP_EQUALVERIFY
5 [sig, pubkey] (verified equal, else abort) OP_CHECKSIG
6 [true/false] script succeeds iff top = true and stack non-empty

Worked example (P2PKH spend):

scriptPubKey: OP_DUP OP_HASH160 <pubkeyhash> OP_EQUALVERIFY OP_CHECKSIG
scriptSig:    <sig> <pubkey>
Execution:    push sig, push pubkey, then run scriptPubKey per the table above.

Malformed-input example: non-canonical (non-strict-DER) ECDSA signature encoding — rejected per BIP-66 (§5) at script-verification time (Phase 2, §14) rather than accepted with undefined malleability semantics (P11, I9).

Failure-path example: a block whose merkle_root does not match the recomputed transaction-hash tree (I5) — rejected at block-validation time (Phase 4, §16), the peer that relayed it is score-penalized (§22 T6), and the block is never added to the block DB (§23 FM-7).

Difficulty target encoding ("bits", compact format, Phase 4/§16):

Field Bits Meaning
Exponent top byte byte-length of the target's big-endian representation
Mantissa remaining 3 bytes leading significant bytes of the target

State-transition table (chain-tip selection on new block, Phase 4, §16):

Current Tip Work New Block's Chain Work Action
W > W switch tip, reorg from common ancestor (I3)
W == W keep current tip (first-seen tiebreak)
W < W store as alternate branch, no tip switch

Design principles (§6)

  • P1 — Consensus safety over optimization. No performance shortcut may alter deterministic validation outcomes. Tradeoff: forgoes speculative-execution wins. Operational implication: every optimization PR must include a differential-fixture diff (§26). Violate it and nodes silently diverge (§22 T7).
  • P2 — Validate before propagate. Invalid transactions/blocks are never relayed. Tradeoff: adds validation latency before the fast path to peers. Violate it and the network amplifies attacker-crafted invalid data (§22 T6).
  • P3 — Canonical serialization. All hashes derive from one deterministic binary encoding (I6). Tradeoff: no schema flexibility without a version bump (§25). Violate it and identical transactions hash differently across nodes.
  • P4 — Adversarial inputs are the default assumption. Every peer is untrusted (T1–T11 span all subsystems). Tradeoff: every parser needs bounds-checked recovery paths. Violate it and one peer can crash or desync the node.
  • P5 — Reorgs are normal, not exceptional. Chain forks are expected operational behavior (§30 MM7). Tradeoff: UTXO-set updates must be reversible, not just applied. Violate it and a 2-block reorg corrupts state (§23 FM-2).
  • P6 — UTXO integrity is sacred. The UTXO set is the sole canonical spend state (I1). Tradeoff: every code path touching balances must go through the UTXO engine, no shortcuts. Violate it and double-spends become possible.
  • P7 — Persistence must survive crashes. Storage updates are atomic and WAL-backed (I12). Tradeoff: write latency includes a fsync-bound floor. Violate it and a power loss corrupts the UTXO DB (§23 FM-1).
  • P8 — Networking is bounded. Peer message size, connection count, and bandwidth are capped (I10). Tradeoff: legitimate large batches must be chunked. Violate it and one peer can OOM the node (§22 T3/T4).
  • P9 — Mempool is eventually consistent, consensus is not. Nodes' mempools may diverge; blocks must not (I11). Tradeoff: RPC callers must not treat mempool state as authoritative. Violate it and relay-policy bugs get mistaken for consensus bugs.
  • P10 — Determinism over throughput. When correctness and speed conflict, correctness wins (§1). Tradeoff: some parallelism (e.g. §28 parallel script execution) stays deferred (§35) until proven consensus-safe. Violate it and validation becomes racy and unreproducible.
  • P11 — Fail closed on malformed input. Ambiguous or malformed wire/script data is rejected, never best-effort-interpreted. Tradeoff: stricter parsers reject more edge cases outright. Violate it and a crafted malformed script silently executes with undefined semantics (§22 T6).
  • P12 — Script is intentionally not Turing-complete. No loop opcodes; bounded op count (I9). Tradeoff: expressiveness is limited to what static analysis can bound. Violate it and a single script can DoS every validating node (§30 MM6).
  • P13 — Separate consensus rules from relay policy. Consensus validity (block-inclusion) and mempool-acceptance policy are different rule sets (I11, ADR referenced in Bitcoin Core reference implementation, §5). Tradeoff: a transaction can be policy-rejected yet still consensus-valid once mined. Violate it and soft-fork deployment becomes impossible.
  • P14 — Headers before bodies. Chain-work verification is decoupled from block-content download (§30 MM8). Tradeoff: a node can commit to a chain tip before validating full block contents. Violate it and initial sync cannot distinguish the best chain without downloading everything.
