Decisions (§9) · 32 ADRs

1

Core language

Chosen

Rust 2021, std host

Rejected

C, C++, Go, Zig

When the rejected choice is right

C wins for maximum hardware portability to bare-metal RTOS targets with no Rust toolchain; C++ wins for a codebase that already has a large STL+RAII investment and where the team's RT discipline prevents hidden allocs; Go wins for a non-RT signaling/control plane where goroutine ergonomics dominate.

Why: No-GC + RT-path safety + lock-free without UB + strong test tooling.

2

Audio backend (locked)

Chosen

ALSA (alsa-sys / thin bindings)

Rejected

PulseAudio, JACK, PortAudio, cpal-only

When the rejected choice is right

PulseAudio wins when the host is a desktop where the sound server is already running and per-app mixing/routing is required; JACK wins for a pro-audio multi-client session where clients share a single RT graph (DAW-style); PortAudio wins for a cross-platform app that must run unchanged on macOS/Windows without a platform-specific abstraction layer.

Why: Lowest-level Linux PCM; full control of period/buffer/xrun; learn the metal.

3

Video backend (locked)

Chosen

V4L2 (ioctl + mmap)

Rejected

GStreamer src, libcamera, OpenCV

When the rejected choice is right

libcamera wins for modern camera ISP pipelines (Raspberry Pi, mobile) where V4L2 is a low-level implementation detail hidden under an ISP HAL; GStreamer src wins when the capture node must be hot-swappable within an existing GStreamer pipeline; OpenCV wins for a machine-vision pipeline where capture and processing are tightly coupled in OpenCV's API.

Why: Direct kernel capture API; explicit format/streaming control.

4

Buffer strategy

Chosen

Pre-allocated BufferPool, refcounted

Rejected

alloc-per-frame (Vec/Box)

When the rejected choice is right

alloc-per-frame wins for an offline batch processor where latency is irrelevant and variable-size frames are the norm, eliminating pool-sizing upfront work; also wins in a scripting-language media tool where GC pauses are acceptable.

Why: Zero allocation on the RT path; bounded memory.

5

RT↔non-RT data path

Chosen

Wait-free SPSC ring (own impl, loom-verified)

Rejected

mutex+condvar, channels (mpsc)

When the rejected choice is right

mutex+condvar wins when both sides are non-RT (e.g. an off-thread command bus) and the simpler code is worth the occasional contention; mpsc wins for a pure non-RT event fan-in where multiple producers share a standard channel and latency is not a constraint.

Why: Only RT-safe primitive; no priority inversion.

6

RT scheduling

Chosen

SCHED_FIFO via sched_setscheduler; assigned prios

Rejected

default CFS, SCHED_RR-only

When the rejected choice is right

CFS wins on a shared cloud instance where CAP_SYS_NICE is unavailable and the RT thread runs at relaxed latency (≥ 20 ms periods); SCHED_RR wins where time-quantum bounding is preferred over strict FIFO preemption — e.g. multiple equal-priority RT threads that must share time fairly.

Why: Deterministic preemption order for the audio/video threads.

7

Page locking

Chosen

`mlockall(MCL_CURRENT

Rejected

MCL_FUTURE)` + pre-touch

When the rejected choice is right

Eliminates page-fault latency on the RT path.

Why: none

8

Internal DSP format

Chosen

planar F32

Rejected

fixed-point S16 internal

When the rejected choice is right

Fixed-point S16 wins on a microcontroller or DSP ASIC without an FPU, where integer arithmetic is cheaper and accumulator-based 16-bit or 32-bit fixed-point maps directly to hardware multiply-accumulate instructions.

Why: Headroom, simpler filter math; convert at device edges.

9

Resampler

Chosen

polyphase FIR with fractional ratio input

Rejected

linear/cubic interp, libsamplerate-only

When the rejected choice is right

Linear interpolation wins for an embedded device with severe CPU constraints where a two-tap linear interpolator running in tens of cycles per sample is the only viable option; libsamplerate wins when the ratio is fixed (offline file conversion) and quality/simplicity of integration outweighs the fractional-ratio hook.

Why: Quality + drift-compensation hook; cross-link #174.

10

Clock discipline

Chosen

PI controller on buffer-level → resampler ratio

Rejected

open-loop, PLL-only

When the rejected choice is right

A pure PLL wins when the clock source provides a phase-error signal directly (e.g. IEEE 1588 PTP hardware timestamping), making the buffer-level proxy unnecessary; open-loop wins for a short-duration stream (< 60 s) where drift accumulation never reaches one period.

Why: Stable, simple, tunable drift compensation (cross-link #394).

11

Master clock

Chosen

audio-master

Rejected

video-master, wall-master

When the rejected choice is right

Video-master wins in a high-frame-rate display pipeline (e.g. 120 fps gaming capture) where video timing drives everything and audio is a secondary track that can tolerate slight resampling; wall-master wins for a network distribution system where the reference is an external PTP grandmaster clock shared by multiple unrelated AV sources.

Why: Audio glitches are most perceptible; sync video to audio.

12

Scheduling model

Chosen

pull at sinks, push at sources, queue seam

Rejected

all-pull or all-push

When the rejected choice is right

All-pull wins for a demand-driven codec pipeline (e.g. a file demuxer) where every stage requests exactly what it needs; all-push wins for a simple DSP chain with a single source rate and no sink-rate mismatch, eliminating queue management overhead.

Why: Matches device rate-driven render + event-driven capture.

13

Codec

Chosen

PhaseDeferred opaque EncodedFrame

Rejected

bundle a codec now

When the rejected choice is right

Bundling a codec now wins when the project goal is specifically to deliver a complete encoder/decoder (e.g. a learning codec project) and the transport/pipeline complexity is secondary.

Why: Keeps scope bounded; cross-link #380/#173.

14

Transport

Chosen

RTP-style over UDP (later phase)

Rejected

TCP, custom, full WebRTC

When the rejected choice is right

TCP wins for a reliable intra-datacenter stream where loss is rare, retransmit latency is sub-millisecond, and simplicity outweighs jitter; full WebRTC wins for browser-to-server media requiring NAT traversal and DTLS-SRTP by the browser security model.

Why: Standard RT media transport subset; cross-link #161.

Error model

Rejected

When the rejected choice is right

unwrap/panic wins in a short-lived CLI tool or a test harness where any unexpected state truly is a programming error that should abort immediately and leave a clear stack trace.

Why: RT loop must degrade, never crash the stream.

Alternative Architectures (Roads Not Taken)

Fundamentally different ways to build a real-time media pipeline for the same goal — not parameter tweaks. Each: an ASCII sketch, the regime where it wins, the real system that embodies it, and why this blueprint rejected it.

A1 — Server-client IPC graph (the JACK model). A privileged RT server owns the device; independent client processes attach to one shared RT graph over shared memory.

  ┌────────────────────────────────────────────────────────┐
  │  JACK-LIKE SERVER PROCESS  (SCHED_FIFO, mlock)         │
  │  ┌──────────┐   shm ringbuf   ┌──────────────────────┐│
  │  │  ALSA    │<═══════════════>│ RT Graph Scheduler   ││
  │  │  Driver  │                 │ (period callback)    ││
  │  └──────────┘                 └────────┬─────────────┘│
  └───────────────────────────────────────┼───────────────┘
                             shared-memory│
         ┌─────────────────┬─────────────┘
         │                 │
  ┌──────┴──────┐   ┌──────┴──────┐
  │  CLIENT A   │   │  CLIENT B   │
  │ (DSP chain) │   │ (recorder)  │
  │  own process│   │  own process│
  └─────────────┘   └─────────────┘
  • Wins: a pro-audio studio where multiple independent applications (a DAW, a synthesizer, an effects processor) must share one RT audio graph at session level, each in its own process for isolation and independent lifecycle — per-client isolation is the killer feature.
  • Real system: JACK2 (jackd) and PipeWire in JACK-compatibility mode.
  • Rejected because: this project is a single-process learning exercise where the server/client IPC machinery (shared-memory ring, IPC protocol, daemon lifecycle) adds complexity without teaching anything about the pipeline or the RT substrate itself; the in-process design is strictly simpler for the scope while preserving every RT invariant (Invariant 1/2/8).

A2 — Demand-pull transcoder (the FFmpeg filtergraph model). A non-RT thread pulls frames from the sink backward to the source at whatever rate the CPU allows; no device period governs timing.

  ┌─────────────────────────────────────────────────────┐
  │  PULL THREAD (non-RT, throughput-optimized)          │
  │                                                      │
  │  av_buffersink_get_frame()                           │
  │         │ pulls                                      │
  │         ▼                                            │
  │  [scale] ← [convert] ← [decode] ← [demux ← file]   │
  │         │                                            │
  │  write output file / forward to encoder              │
  └─────────────────────────────────────────────────────┘
  (no RT scheduling, no mlockall, no clock discipline)
  • Wins: offline transcoding (file-in → file-out), a streaming server encoding at faster-than-realtime, or any pipeline where throughput (frames/s above realtime) is the goal and there is no physical render device — per-frame allocation is fine, latency is irrelevant.
  • Real system: FFmpeg libavfilter / ffmpeg -vf.
  • Rejected because: the demand-pull model has no device period, no clock discipline, and no RT thread model, so it cannot guarantee frame delivery within a period deadline and cannot produce glitch-free audio to a real sound device — the §4.3 RT model is the only correct one when a real device is the sink.

A3 — Push-only streaming bus (no backpressure, no graph). Each stage pushes into an unbounded channel; there is no bounded queue, no policy, and no negotiation.

  ┌──────────┐      ┌──────────┐      ┌──────────┐
  │  Capture │─────>│  DSP     │─────>│  Render  │
  │  Thread  │ chan │  Thread  │ chan │  Thread  │
  └──────────┘      └──────────┘      └──────────┘
    push at       std::sync::mpsc    (no bounded
    device rate   (unbounded)         queues,
                                      no policy)
  • Wins: a simple audio-monitoring app where the pipeline is one fixed chain with uniform stage throughput, the only failure mode is lag (not xrun), and minimal code is the goal — an std::sync::mpsc push chain with no backpressure is fine when the consumer is always at least as fast as the producer.
  • Real system: many simple audio visualization tools and naive FFT-based spectrum analyzers.
  • Rejected because: unbounded channels grow without limit the moment any stage is slower than the source — exactly the memory blowup and latency creep Design Principle 4 (backpressure) and Design Principle 9 (budgeted latency) forbid; the bounded-queue seam is not optional when a slow consumer must not silently delay the render deadline.

A4 — Hardware-in-the-loop microkernel (the RTOS model). No host OS; DMA-driven ISRs move samples and frames, all memory is static, and worst-case execution time is formally proven.

  ┌────────────────────────────────────────────┐
  │  RTOS KERNEL  (e.g., FreeRTOS / Zephyr)    │
  │  ┌──────────────────────────────────────┐  │
  │  │  Audio ISR (period interrupt)        │  │
  │  │    DMA → ring → DSP task → DAC DMA   │  │
  │  └──────────────────────────────────────┘  │
  │  ┌──────────────────────────────────────┐  │
  │  │  Video task (frame interrupt)        │  │
  │  │    DMA → convert → display DMA       │  │
  │  └──────────────────────────────────────┘  │
  │  All memory static; no heap; WCET proven   │
  └────────────────────────────────────────────┘
  • Wins: an embedded media device (smart speaker, video doorbell, automotive head unit) on a microcontroller/SoC with a hard-RTOS requirement, where WCET must be formally proven and dynamic allocation is wholly prohibited — DMA-driven ISR pipelines on FreeRTOS/Zephyr are the canonical form.
  • Real system: Zephyr RTOS audio pipeline (Bluetooth LE Audio); automotive Linux with PREEMPT_RT + AUTOSAR Adaptive.
  • Rejected because: this project targets a Linux std host, where mlockall + SCHED_FIFO give a soft/firm-RT approximation; a microkernel RTOS removes std, cargo test, proptest, and the offline FileBackend — a fundamentally different environment that §1.3's non-goal "No hard real-time certification / WCET" explicitly excludes.
