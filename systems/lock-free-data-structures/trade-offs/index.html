Roads not taken (§37)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alternative A — Mutex-and-Condvar Baseline

┌─────────────┐     ┌─────────────┐
│  Thread 1   │────▶│  Mutex<T>   │◀────│  Thread N   │
└─────────────┘     │  + Condvar  │     └─────────────┘
                     └─────────────┘

Regime where it wins: low-to-moderate contention (< 4 concurrent threads), where the kernel-mediated blocking wait is cheaper than a spin-based retry loop and priority inversion is not a concern. Real system: the vast majority of std::sync::Mutex<VecDeque<T>> usages in production Rust services today, and Java code before j.u.c's non-blocking collections existed. Rejected because: at the 8–64 thread scale this library targets (§4), blocking-wait latency and priority-inversion risk dominate, and the whole point of this project is teaching the lock-free alternative (§2).

Alternative B — Pure RCU (Read-Copy-Update)

Readers: rcu_read_lock() → deref → rcu_read_unlock()   (no atomics on the read path at all)
Writers: copy → mutate copy → rcu_assign_pointer() → synchronize_rcu() → free(old)

Regime where it wins: read-mostly workloads with a small, bounded number of concurrent writers and where readers can tolerate a bounded staleness window — exactly the Linux kernel's dominant access pattern (McKenney, Required Reading §5). Real system: the Linux kernel's RCU subsystem, and this library's own QSBR scheme (§15.3) is a userspace cousin of it. Rejected as the sole reclamation strategy because this library targets general MPMC data structures with frequent writers, not read-mostly kernel-style data — QSBR is offered as an opt-in, not the architecture's foundation (ADR-02).

Alternative C — Hardware Transactional Memory (HTM)

begin_tx(); { read head; compute new state; write head; } commit_tx();  // abort → retry

Regime where it wins: short transactions with low real-world contention and hardware that reliably supports HTM without frequent spurious aborts (cache-capacity/interrupt-driven) — common in some in-memory database engines on Intel TSX-capable hardware. Real system: early libcds experiments and several in-memory OLTP engines use TSX-gated fast paths with a CAS-based fallback. Rejected as the primary architecture because TSX has been disabled or removed on several recent Intel microarchitectures (security mitigations), Power's equivalent (Power TM) is not portable to x86/ARM, and a design built around HTM would be un-shippable on a meaningful fraction of the target fleet — it remains a documented, deferred stretch (PhaseDeferred("§13.2")) rather than the foundation.
