1. Goal & Scope

Build lockfree, a Rust workspace of composable, reclamation-agnostic lock-free and wait-free data-structure crates — CAS-based stacks, queues, deques, an ordered list, a hash map, a skip list, a wait-free counter, and a gated wait-free queue — each shipped with a written memory-ordering proof, exhaustive/randomised concurrency verification (loom/shuttle), a linearisability oracle, and cross-architecture (x86-64 / aarch64 / Power-model) validation. The library occupies the niche crossbeam, folly::concurrency, and java.util.concurrent occupy: primitives safe to place on the public-request hot path of a service under adversarial concurrent load.

Phase-0 deliverable (numbered; all crates under crates/):

  1. lockfree-atomic — named-ordering atomic wrappers, tagged pointers, backoff ladder.
  2. lockfree-hazard — hazard-pointer safe memory reclamation (default SMR).
  3. lockfree-queue (partial: treiber.rs only in Phase 0's smoke scaffold).
  4. lockfree-verify (partial: loom harness scaffolding, smoke test only).
  5. lockfree — public facade crate re-exporting the above.

System boundaries:

  • Provides: in-process concurrent data structures, safe memory reclamation, a memory-ordering proof per algorithm, a verification harness, cross-architecture validation.
  • Delegates: the underlying allocator (std::alloc::System or a user-supplied GlobalAlloc), OS thread scheduling, process-level crash recovery.
  • Does NOT provide: distributed consensus, on-disk persistence/durability, network transport, a tracing GC for arbitrary Rc/RefCell graphs, a general STM.

Non-goals: not an actor framework; not an async runtime (though WaitFreeCounter and BoundedMpmcQueue are safe to call from async contexts); not a distributed system.

Deployment model: a Rust library crate, statically linked into the consuming binary; a cdylib FFI facade (lockfree-c-abi) for non-Rust consumers. No standalone service, no network listener.

Target users / operators: library engineers building request-handling services, schedulers, and caches who need measured, proof-carrying concurrency primitives; the "operator" is the engineering team vendoring the crate who reads the verification evidence (§29) before adopting a new call site.

What later phases unlock: Phase 3 (§15) unlocks reclamation choice (hazard / epoch / QSBR); Phase 7 (§19) unlocks the hash map; Phase 8 (§20) unlocks wait-free primitives; Phase 9 (§21) unlocks the linearisability oracle as a reusable cross-algorithm contract; Phase 10 (§22) unlocks multi-architecture confidence; Phase 11 (§23) unlocks the performance-gated release process.

Recommended language: Rust 2024 edition. Rationale: Send/Sync express thread-safety at the type level — sharing a Rc<T> across threads is a compile error, not a runtime race (P13); unsafe is a lexical, greppable boundary, so verification effort concentrates on the ~2,000 lines that carry it instead of the whole codebase. Rejected languages: C++ — templated concurrent containers are unsound by convention only, no compiler-checked Send/Sync equivalent (the exact risk folly and libcds carry today, §33); Go — the tracing GC removes the reclamation problem but with it the ability to teach or ship GC-free reclamation, and goroutine scheduling preemption defeats hand-verified interleavings; Java — JIT/GC nondeterminism defeats the assembly-diff technique (§22.6), and Unsafe/VarHandle are call-boxed, not zero-cost.

Prerequisites: comfort with raw pointers and manual memory management; an existing mental model of mutex-based concurrency; undergraduate computer architecture (caches, cache coherence). No prior lock-free experience assumed — Required Reading (§5) supplies it.

Estimated timeline: Phase 0 — 1 week. Full system (Phases 0–12) — 22–23 weeks (~5.5 months).

Deferred features (full table: Deferred Features Register, back matter): DWCAS fast path PhaseDeferred("§13.2"); hardware transactional memory integration PhaseDeferred("§13.2"); persistent (NVM) queue PhaseDeferred("§14.2"); RCU-style reclamation crate PhaseDeferred("§15.2"); wait-free linked list (Timnat–Petrank) PhaseDeferred("§18.2"); OSS-Fuzz integration PhaseDeferred("§23.2"); loom-traces visualiser PhaseDeferred("§21.2"); formal Coq/Iris proof of Michael–Scott PhaseDeferred("§14.2"); NUMA-aware per-node queues PhaseDeferred("§23.2"); SIMD bulk-dequeue and bucket-probe PhaseDeferred("§19.2").

2. Why Build This

A lock-free data structure is the canonical example of code that is correct on one CPU and wrong on the second. The literature gives the algorithm in a page; production reality is the month-long exercise of pairing every load with the right acquire fence, every store with the right release fence, every CAS with the right success/failure orderings, every pointer publication with the right reclamation step, every progress claim with an interleaving argument, every ABA hazard with a counter-stamp or hazard pointer, and every platform quirk (x86 TSO making release-then-acquire free; aarch64's weaker model making it not free; Power's still-weaker model making every fence count) with a validation harness that proves the result lock-free, linearisable, ABA-safe — on every platform that matters.

Teams that hand-roll this discover, usually during an incident, that the in-house "lock-free stack" leaks memory under concurrent pop because a freed node is touched by a CAS that has not yet observed the free (I5); that the "atomic queue" reads tail.next after tail was recycled into a different list (I4); that the "wait-free counter" is wait-free in the benchmark and live-locked under contention because the back-off discipline was never tuned (P9, I2). Teams that already shipped on a focused library — crossbeam's SegQueue, Java's ConcurrentLinkedQueue, folly::MPMCQueue — get throughput that scales linearly with thread count, audited against the C++/Java memory model for a decade.

This project is the smallest library that still teaches the full surface a real lock-free toolkit carries: the atomics primer (P1, §8.1); Treiber/Michael–Scott/Vyukov/Chase–Lev/SPSC (§14, §16, §17); the split-ordered hash map and skip list (§19, §20); hazard pointers, EBR, QSBR (§15); the wait-free counter and Kogan–Petrank queue (§20); loom/shuttle/WGL verification (§21); and cross-architecture CI (§22). It cross-links to sibling systems in this portfolio: the async-runtime blueprint's executor consumes WorkStealingDeque directly; the in-memory cache blueprint consumes LockFreeHashMap; the message-bus blueprint consumes MichaelScottQueue and BoundedMpmcQueue.

What Mastery Looks Like (end state, after building all 13 phases):

  1. Write a memory-ordering proof for a novel CAS-based algorithm from scratch, naming the exact synchronises-with edges — cemented in Phase 2 (§14) and Phase 4 (§16).
  2. Choose the correct reclamation scheme (hazard / epoch / QSBR) for a workload's read/write ratio and cooperation model, and justify the choice numerically — cemented in Phase 3 (§15).
  3. Distinguish obstruction-freedom, lock-freedom, and wait-freedom by constructing an adversarial schedule that breaks a weaker guarantee — cemented in Phase 8 (§20).
  4. Read x86-64, aarch64, and Power assembly for the same synchronisation primitive and explain the cost delta from the memory model alone — cemented in Phase 10 (§22).
  5. Design and run a linearisability check against a sequential oracle for an arbitrary new concurrent object — cemented in Phase 9 (§21).
  6. Diagnose a false-sharing regression from a cache-miss profile and fix it with padding, not guesswork — cemented in Phase 11 (§23).
  7. Explain, with a real incident, why "our lock-free structure passed on x86" is not evidence of correctness — cemented in Phase 10 (§22) and the Threat Model (§25).

Four properties matter throughout. First, every public operation carries a written memory-ordering proof (I7): a push that loads head Acquire and CASes (Release, Relaxed) has a proof paragraph in verification/proofs/<algorithm>.md naming the synchronises-with relation (§8.1); reviewers verify without re-deriving. Second, reclamation is the orthogonal axis (P2): data structures consume a Guard (Core Schema §11) and never embed a reclamation strategy; the ADR-02 (§9) row picks the default per structure, overridable per instantiation. Third, the verification harness is the merge gate, not an afterthought test (P10): every algorithm ships a loom test at thread count 2 and 3 before a benchmark runs; the result is checked into verification/proofs/<algorithm>.loom.json; a regression is a CI failure. Fourth, cross-architecture is non-negotiable (I13): every CI run executes on x86-64, aarch64, and (emulated via herd7) a Power-like weak model; code passing on x86 but failing on aarch64 is the canonical "forgot the release fence" bug, and the three-way matrix is the only reliable filter (§22).

The crate-naming convention lockfree-* is normative — Repository Layout (§10), Core Schema & Types (§11), and Appendix A must name the same crates.

6. Design Principles

  1. P1 — Every algorithm has a written memory-ordering proof. No pop/push/CAS site merges without a verification/proofs/<algorithm>.md paragraph naming the synchronises-with edge (I7). Tradeoff: slows initial authorship. Operational implication: proof review is a first-class PR gate. Violating it: a silent data race surfaces only on a weaker architecture, months later.
  2. P2 — Reclamation is orthogonal to the algorithm. Data structures consume a Guard trait; the reclamation crate supplies the implementation (§11). Tradeoff: one extra generic parameter on every public type. Violating it: a structure hard-codes one scheme and cannot be benchmarked against another.
  3. P3 — Hazard pointers are the default reclamation. Bounded memory, legible failure mode (§15.4). Tradeoff: ~10 ns/access announce cost vs epoch's ~5 ns. Violating it (no documented default): every call site re-litigates the choice.
  4. P4 — Linearisability is the correctness contract. Every operation has a linearisation point; the oracle (§21.3) asserts it in verification builds (I1). Violating it: "eventually consistent" bugs masquerade as lock-free bugs.
  5. P5 — Lock-freedom is the default progress guarantee; wait-freedom is reserved for WaitFreeCounter/WaitFreeQueue. Documented per algorithm (I2, I3). Violating it: an undocumented progress claim cannot be adversarially tested.
  6. P6 — The ABA problem is named explicitly per algorithm. A pointer-CAS-only algorithm without a tag or hazard protection has a named ABA hazard and mitigation (I4). Violating it: the bug reproduces only under a specific allocator-reuse pattern.
  7. P7 — compare_exchange_weak is the default; _strong only when spurious-failure cost dominates. Documented per call site (ADR-13). Violating it: doubled instruction count on LL/SC architectures for no benefit.
  8. P8 — No spinlocks pretending to be lock-free. A structure that spins on a flag is not lock-free and is not shipped. Violating it: the loom progress check catches it, but only if run (§21).
  9. P9 — Backoff is exponential with a documented cap (spin → PAUSE → YIELD → sleep, lockfree-atomic/src/backoff.rs, ADR-23). Violating it: a tight retry loop burns a full core under contention (§31 M9).
  10. P10 — Verification gates merge. No algorithm without a loom pass at TC 2 and 3 merges (I14). Violating it: a correctness regression ships silently.
  11. P11 — Cross-architecture CI gates release. A regression on x86-64, aarch64, or the Power-like harness blocks release (I13). Violating it: "works on my x86 laptop" ships broken to an aarch64 fleet.
  12. P12 — No global state; reclamation domains are values. Multiple domains coexist; tests use a fresh domain per scenario (ADR-22). Violating it: test isolation becomes impossible, and flaky CI follows.
  13. P13 — No unsafe outside the atomics and reclamation layers. The public API is #![forbid(unsafe_code)]; encapsulated unsafe carries a paired safety comment. Violating it: the audit surface balloons past the ~2,000 lines we can hand-verify.
  14. P14 — Errors are typed, never panics, on the hot path. try_send returns Err(SendError::Full(v)). Violating it: a panic under contention takes down a caller that expected backpressure instead.
  15. P15 — Determinism in verification. A loom test reproduces identically per seed; a randomised failure logs and checks in its seed (I14). Violating it: a "flaky" CI failure is dismissed instead of investigated, and a real bug survives.

8. Domain Model — Atomics, CAS/ABA, and the Canonical Algorithms

8.1 Atomics & Memory-Ordering Model

The library targets the C++20/Rust memory model (Boehm & Adve 2008; ISO/IEC 14882:2020 clause 6.9). Named orderings exposed by lockfree-atomic (Core Schema §11):

Ordering Guarantee Cost (x86-64 / aarch64) Used for
Relaxed no ordering beyond same-address modification order ~1 ns / ~1 ns index/counter reads not gating visibility
Acquire no later access reorders before this load free / ~3 ns (LDAR) reading a published pointer
Release no earlier access reorders after this store free / ~3 ns (STLR) publishing a pointer/value
AcqRel both, on a read-modify-write ~5 ns / ~7 ns (CAS) CAS success ordering
SeqCst total order across all SeqCst ops ~20 ns / ~20 ns (fence) hazard-pointer announcement (§15.1)

A synchronises-with edge exists when a Release store is read by an Acquire load of the same location; this is the sole mechanism by which one thread's writes become visible, in order, to another. §8.3–§8.4 name these edges per algorithm.

8.2 CAS, LL/SC, and the ABA Problem

compare_exchange(expected, new, success_order, failure_order) atomically checks a memory location against expected and swaps to new only on match. x86-64 implements CAS natively (cmpxchg); aarch64 and Power implement it as a load-linked/store-conditional (LL/SC) pair, which can fail spuriously even when the value did not change (P7, ADR-13).

The ABA problem: thread A reads location L, observes value X, computes an intended new value based on X's contents (e.g. X.next); meanwhile thread B changes L to Y and back to X (a different, recycled X with different contents) or reuses X's address for an unrelated object. A's later CAS(L, X, new) succeeds because L again equals X by address — but the assumption A made about X's contents is now false. Mitigations: a monotonically incrementing tag packed with the pointer (TaggedPtr, I4), or a hazard pointer that prevents X's address from being reused at all while announced (§15.1).

8.3 Treiber Stack — State Model

State: head: TaggedPtr<Node<T>>           Node<T> { value: T, next: TaggedPtr<Node<T>> }

push(v):  n = alloc(Node{v, head.load(Acquire)})
          loop: h = head.load(Acquire); n.next = h
                if head.CAS(h, n, Release, Relaxed).is_ok() { break }
pop():    loop: h = head.load(Acquire); if h.is_null() { return None }
                if head.CAS(h, h.next, Release, Acquire).is_ok() { return Some(h.value) }

Proof (push). head_load (Acquire) synchronises-with the most recent successful head_cas (Release) — push observes any node pushed before this load. Proof (pop). The Acquire load of head observes the latest push/pop; the Release-CAS to head.next makes the popped value's read happen-before any subsequent push reusing that address. Linearisation: both ops linearise at their successful CAS. ABA: without the tag, A loads head = X; B pops X, pushes Y, pops Y, re-pushes a recycled X (same address, different next); A's stale CAS(head, X, A's-stale-X.next) succeeds wrongly. The monotonic tag on every successful CAS defeats this (I4).

8.4 Michael–Scott Queue — State Model

State: head, tail: TaggedPtr<Node<T>>  (sentinel node always present)

enqueue(v): n = alloc(Node{v, null})
            loop: t = tail.load(Acquire); next = t.next.load(Acquire)
                  if next.is_null() { if t.next.CAS(null, n, Release, Relaxed).ok
                                       { tail.CAS(t, n, Release, Relaxed); break } }
                  else { tail.CAS(t, next, Release, Relaxed) }      // helping
dequeue():  loop: h = head.load(Acquire); t = tail.load(Acquire)
                  next = h.next.load(Acquire)
                  if h == t { if next.is_null() { return None }
                              tail.CAS(t, next, Release, Relaxed) } // helping
                  else if head.CAS(h, next, Release, Acquire).ok { return Some(next.value) }

Proof. The Release store of a new node's next field synchronises-with the Acquire load of tail.next that a concurrent dequeue performs — this is the edge giving dequeue a consistent node-graph view. Linearisation: enqueue at the CAS of tail.next; dequeue at the CAS of head. Helping is not optional (P1, Pitfall §14.6): skipping the tail-advance CAS lets a slow enqueuer permanently stall a fast dequeuer — loom's correctness check will not catch this (it is a progress bug, not a linearisability bug); the dedicated progress check (I2) does.

8.6 Worked Example — Michael–Scott Under Concurrent Helping

Three threads, queue = [sentinel]. T1 begins enqueue(A): reads tail = sentinel, sentinel.next = null, CASes sentinel.next to node A — succeeds, but T1 is preempted before advancing tail. T2 begins enqueue(B): reads tail = sentinel (stale — T1 has not advanced it yet), reads sentinel.next = A (non-null), so T2 helps: CASes tail from sentinel to A. T2 retries its own enqueue: reads tail = A, A.next = null, CASes A.next to node B, then CASes tail from A to B. Final state: sentinel → A → B, tail = B. T1 resumes, attempts its own tail-advance CAS(sentinel→A), which now fails (tail is already B) — T1 simply discards the redundant advance. No data is lost; the helping step is what makes this lock-free rather than blocking on T1's preemption.

8.7 Malformed / Adversarial Input Example

An adversarial scheduler preempts every thread exactly between its tail.load(Acquire) and its tail.next.load(Acquire) in enqueue. Under this schedule, every enqueuer sees a "stale but valid" tail; each one's helping branch fires, and each CAS on tail either succeeds once (advancing it) or fails (because another helper already advanced it) — the algorithm is defined for this schedule by construction, since Acquire/Release ordering guarantees every helper observes a state that was valid at some prior instant. This schedule is exactly what loom's exhaustive TC-2/TC-3 search enumerates (§21.1); it is not a crash case, it is the intended lock-free behaviour under worst-case preemption.

8.8 Failure-Path Example

A T::drop implementation panics while the hazard-pointer scan (§15.6) is freeing a retired Node<T>. The scan is inside a catch_unwind boundary (FM-11, §26); the panic is caught, logged via tracing::error! with the node's address and retiring thread ID, and the node is leaked (not freed) rather than the scan aborting mid-walk and leaving the retire list in an inconsistent state — leaking one node is bounded and diagnosable; corrupting the retire list is not. The runbook (docs/runbook/memory-leak.md) documents the diagnostic: grep tracing output for "drop panicked during reclaim".

The "empty queue" test (head==tail && head.next==null) needs three Acquire loads in sequence; a pathological interleaving where head moves between the head-load and head.next-load requires a retry, not a false-empty return. Tag width (§8.2) must be wide enough that wrap-around is implausible at the target CAS rate (§4 ABA-window row).

14.7 Performance Concerns

SPSC ring indices as u32 wrap in ~4B ops; use u64 for production unless the capacity bound is small and known (§25 T8 analogue). Cache-line padding around head/tail (I11) costs ~256 B/instance metadata but avoids the ~3× false-sharing throughput cut a naive layout would incur (§31.1).

14.8 Edge Cases

A retired node must never be touched post-retire (I5) — the hazard scan (§15.6) is the only gate. A T: Drop node must have drop called exactly once per successful dequeue — the reclamation crate's drop callback is the sole path (I6). The Michael–Scott consistency check between head and tail loads must use Acquire, not Relaxed; on aarch64/Power's weaker model, Relaxed permits observing an inconsistent snapshot (I13).

14.9 Failure Analysis

A missed helping-step CAS manifests as a stalled dequeuer under load — detected by the progress-guarantee proptest (I2), not the linearisability oracle; blast radius is a throughput cliff, not corruption. A use-after-free from a reclamation-scan bug (I5) is detected by ASan/miri in CI before it reaches production; forensic artifact is the tracing "node dereferenced after retire" event with node address + retiring thread ID.

14.10 Operational Notes

tracing::debug! spans on CAS-retry and helping-step execution, gated behind a lockfree/tracing feature flag to avoid cost when disabled (P14). No migration concerns — these are in-process types with no wire format (§28).

15. Phase 3 — Reclamation: Hazard Pointers, EBR, QSBR (Week 4–7)

15.1 Objectives

Ship the three reclamation schemes as independent crates sharing one Guard/Reclaim trait surface (P2, Core Schema §11), with hazard pointers as the shipped default (P3, ADR-02).

15.2 Detailed Implementation Steps

lockfree-hazard: a domain (domain.rs) holds a global slot list; each thread has a 4-slot array (slot.rs, I8); retire.rs batches retired nodes per-thread; reclaim.rs scans (§8.5) when the retire list exceeds 64 (Michael 2004, I5). lockfree-epoch: global.rs holds an AtomicUsize epoch; local.rs per-thread pinned epoch; pin.rs implements pin(); advance.rs advances the global epoch and reclaims the bag at global_epoch − 2 (Fraser 2004, I9). lockfree-qsbr: thread.rs tracks per-thread last-quiescence epoch; quiescent.rs implements quiescent_state() (McKenney RCU background reading). docs/architecture/reclamation.md is the comparison ADR (ADR-02's long form). Deferred here: an RCU-style reclamation crate PhaseDeferred("§15.2") — QSBR already covers the read-mostly niche; a dedicated RCU crate is a stretch.

15.3 Deliverable

Three reclamation crates, each instantiated against a Treiber stack "stress harness" and passing loom at TC 2/3; a microbenchmark table of per-pop overhead per scheme (§8.5, matching §31 M7–M8).

Zero use-after-free (I5) across a 100,000-op proptest per scheme (fixture no_uaf_hazard.rs, no_uaf_epoch.rs, no_uaf_qsbr.rs); hazard-pointer protect overhead ≤ 20 ns/access; epoch pin/unpin overhead ≤ 10 ns/access; hazard-slot overflow path (I8) triggers correctly at the 5th concurrent protected pointer on a 4-slot thread (fixture slot_overflow.rs).

Hazard-pointer announcement must precede the dereference; a compiler reorder breaks the scheme — the announcement uses SeqCst specifically to inhibit this (I8, §8.5). A hazard slot exhausted (more live pointers than the 4-slot budget) falls back to a per-thread overflow allocation (I8) — document the perf cliff this introduces. The epoch's two-epoch lag (not one) is the correctness floor: a thread pinned just before a scan began is still mid-traversal at one-epoch lag, an unsafe reclaim (I9). A T::drop that panics or blocks during a hazard scan is caught (§8.8, FM-11) — it does not abort the scan.

15.9 Failure Analysis

A stalled epoch advance (I9) is visible as a growing retire-bag-size gauge — the runbook (docs/runbook/memory-leak.md) documents identifying the offending pinned thread via per-thread epoch telemetry. A double-free (I6) is a heap-corruption bug; detection is ASan/miri in CI (never expected to reach production given the fixture coverage above); recovery is crash-only — patch and redeploy, no live repair.

16. Phase 4 — Vyukov Bounded MPMC Ring (Week 7–8)

16.1 Objectives

Ship the sequence-numbered bounded ring (Vyukov 2011, ADR-04), the fastest bounded MPMC measurable, with loom verification tractable at small capacities.

16.2 Detailed Implementation Steps

Each slot carries (sequence: AtomicUsize, value: MaybeUninit<T>), initial state sequence[i] = i. try_send: load producer position Relaxed; load the slot's sequence Acquire; if sequence == position, CAS producer to position+1; on success write the value and store sequence = position+1 Release (the Release/Acquire pairing on sequence is the load-bearing synchronises-with edge, §8.1, I7; I1's linearisation point is this successful position-CAS). try_recv mirrors this: reads sequence == position+1, CASes consumer to position+1, stores sequence = position + capacity on completion — the value the next producer at position+capacity will match, closing the cycle. Uses prefetch_read/prefetch_write from Phase 1 (§13.2) to mask slot-load latency ahead of the CAS. Deferred here: NUMA-aware per-node ring variant PhaseDeferred("§23.2") (belongs with the Phase-11 scalability stretch, not this phase).

16.3 Deliverable

BoundedMpmcQueue<T> in lockfree-queue::vyukov; loom-verified at TC 2 (1P/1C) and TC 4 (2P/2C); benchmarked against crossbeam::queue::ArrayQueue.

16.4 Acceptance Criteria

Loom exhaustive pass at TC 2 and TC 4 (fixture loom_vyukov_tc24.rs) with 0 oracle violations; throughput within 10% of crossbeam::queue::ArrayQueue at 16P/16C (§4, §31 M3); construction with a non-power-of-two capacity returns a typed Err(CapacityError), never a panic.

16.5 Conformance Fixtures

Fixture Purpose Expected Output

16.6 Pitfalls

The sequence field is usize; on 64-bit hosts wrap-around is not practically reachable (§4's ABA-window row is about the tag, not this field). A capacity that is not a power of two breaks the & mask indexing — the constructor asserts and returns Err(CapacityError) rather than silently masking wrong. A T whose size exceeds ~64 B minus the sequence-field overhead breaks the one-cache-line-per-slot assumption (I11), reintroducing false sharing.

16.7 Performance Concerns

Cache-line padding between adjacent slots is the false-sharing mitigation (I11); each slot must fit in one 64 B cache line including its sequence field. prefetch_read ahead of the sequence check masks memory latency under high throughput (§13.2); measured gain ~8% at 16P/16C (§31 M3 methodology).

16.8 Edge Cases

A consumer that stalls at a slot before resetting sequence blocks all subsequent producers cycling to that slot — correct under crash-stop, not crash-recover (documented non-goal, §1). A T: !Send cannot be sent through the ring — enforced by the T: Send bound on try_send at compile time (I12).

16.9 Failure Analysis

A full ring under sustained overload returns Err(SendError::Full(v)) (P14) — the caller owns backpressure policy; the library never blocks or drops silently. A consumer crash mid-try_recv (process-level, not thread-level) leaves the slot's sequence in the claimed-but-unwritten state — out of scope for a crash-only, non-persistent library (§4 RTO row); document in the runbook that this requires a fresh ring on process restart.

16.10 Operational Notes

tracing events on full-ring backpressure and slot-claim latency; metrics: send/recv retry-count histogram, full-ring rejection counter. No migration concerns (in-process type, §28).

17. Phase 5 — Chase–Lev Work-Stealing Deque (Week 8–9)

17.1 Objectives

Ship the growable circular-buffer work-stealing deque (Chase & Lev 2005, ADR-05) that every modern task scheduler (Tokio, Rayon, Go, .NET) descends from.

17.2 Detailed Implementation Steps

top (steal end) and bottom (owner end) index a growable Buffer<T>. Owner push writes at bottom, increments. Owner pop decrements bottom first, then resolves a possible single-element race via a five-step two-phase commit (Chase & Lev 2005's formal proof, P1/I7): (1) decrement bottom; (2) read top Acquire; (3) if bottom < top → empty, restore bottom; (4) if bottom > top → no race, read and return; (5) if bottom == top → CAS top to top+1 — success means the owner won (bump bottom to match), failure means a stealer won (owner returns None). Stealer steal reads top, CASes top to top+1 (I1's linearisation point: the CAS of top, or plain decrement of bottom in the non-racing owner case). Growth: allocate double-capacity buffer, copy under owner-only access (no synchronisation needed for the copy itself, P13), Release-swap the buffer pointer, retire the old buffer to the Guard (P2, I5) so an in-flight stealer against the old buffer is not freed under it.

17.3 Deliverable

WorkStealingDeque<T> in lockfree-queue::deque; a "tokio-like" benchmark: one owner pushes 1M items, N stealers consume, throughput scales with N.

17.4 Acceptance Criteria

Loom exhaustive pass at TC 2 (1 owner/1 stealer) and TC 3 (1 owner/2 stealers) (fixture loom_deque_tc23.rs); owner-side push/pop latency ≤ 15 ns, steal ≤ 80 ns (§4, §31 M4); the growable-buffer path is verified by a separate harness because its state space is larger (fixture loom_deque_grow.rs).

17.5 Conformance Fixtures

Fixture Purpose Expected Output
loom_deque_tc23.rs exhaustive TC 2/3 incl. single-element race 0 oracle violations
loom_deque_grow.rs grow-during-steal interleaving old buffer not freed under active stealer
malformed_pop_empty.rs pop on empty deque None, bottom restored correctly
bench_owner_vs_stealers.rs 1 owner, N ∈ {1,4,16} stealers throughput scales with N

17.6 Pitfalls

The growable buffer must retire the old buffer through the Guard (P2); a steal in flight against the old buffer must never see a freed buffer (I5). The owner must never call steal on its own deque — every invariant assumes single-threaded owner access to bottom. Skipping the "restore bottom" step in the empty case (§17.2 step 3) corrupts subsequent pushes.

17.7 Performance Concerns

The steal path costs more than owner push/pop (§4: 80 ns vs 15 ns) because it always pays an Acquire load plus a CAS, whereas the owner's common-case pop pays neither when bottom > top cleanly. Growth is amortised O(1) but each individual grow event copies O(n) elements under owner-only access — document as a latency spike, not a correctness concern.

17.8 Edge Cases

A stealer holding a buffer reference across a grow event must use the Guard (P2); without it, the buffer is freed under it (I5). bottom - top reaching the buffer's capacity triggers growth mid-operation — the owner must complete its current push before observing the new buffer.

17.9 Failure Analysis

A stealer racing the single-element case and losing (§17.2 step 5, CAS fails) returns None from steal — not an error, a normal empty-signal (P14). A buffer-growth bug that frees memory a stealer still references is a use-after-free (I5) caught by ASan/miri in CI before shipping (fixture loom_deque_grow.rs plus a targeted fuzz target, §23.3).

17.10 Operational Notes

tracing events on grow (buffer-size-before/after) and on steal-vs-owner-race outcome; metrics: grow-event counter, steal-success-rate gauge. No migration concerns (in-process type).

18. Phase 6 — Harris–Maged Linked List (Week 9–11)

18.1 Objectives

Ship the marked-pointer ordered linked list (Harris 2001, with Maged Michael's 2002 refinements, ADR-06) that safely handles concurrent deletion via a two-step logical-then- physical protocol.

18.2 Detailed Implementation Steps

next is AtomicPtr<Node<T>> with the low bit encoding "marked for deletion": pack(ptr, marked) = (ptr as usize) | (marked as usize), unpack(packed) = (packed & !1, packed & 1), requiring align_of::<Node>() >= 2 (asserted at construction). find(k) walks from head; a marked next is helped (physically unlinked) before the walk continues — helping is mandatory (P1). insert(k, v): find the position, CAS the predecessor's next from unmarked-succ to the new node. remove(k) is the load-bearing two-step sequence: (1) find(k) yields (pred, curr); (2) CAS curr.next from (succ, 0) to (succ, 1) — logical delete; (3) CAS pred.next from (curr, 0) to (succ, 0) — physical remove; (4) if step 3 fails (a concurrent insert raced pred.next), do not retry — a subsequent find helps. Proof in verification/proofs/harris.md (I7). Deferred here: a wait-free variant (Timnat–Petrank) PhaseDeferred("§18.2") — the lock-free version is the Phase-0 commitment; wait-free is a stretch gated like Kogan–Petrank (§20).

18.3 Deliverable

LockFreeLinkedList<T, R> in crates/lockfree-list; a "concurrent ordered set" benchmark against std::sync::Mutex<BTreeSet<_>>.

18.4 Acceptance Criteria

Loom exhaustive pass at TC 2 and TC 3 (fixture loom_harris_tc23.rs); find/insert/ remove each linearise at their named CAS (§18.2); a concurrent find that encounters a marked node always completes the physical unlink before continuing (fixture helping_mandatory.rs) — an un-helped marked node left behind after 1,000 random ops is a FAIL.

18.5 Conformance Fixtures

Fixture Purpose Expected Output

malformed_remove_absent_key.rs remove a key not present no-op, no panic
concurrent_insert_vs_delete_race.rs insert races a delete at the same position consistent post-state per oracle

18.6 Pitfalls

A find that skips helping leaves dangling marked nodes — correctness holds but performance degrades (helping is mandatory, not optional, §18.2). Mixing a low-bit-in-pointer mark encoding with a separate boolean field in the same code path is a recipe for inconsistency — one encoding, used everywhere (the terminology-lock discipline applied throughout this document, e.g. Core Schema §11).

18.7 Performance Concerns

Walking past marked (not-yet-helped) nodes adds O(marked-nodes-in-path) to find latency under high-delete-rate workloads; the helping step amortises this back down but a delete-heavy adversarial workload (§25 T-series) can still degrade find toward O(n) if helping cannot keep pace.

18.8 Edge Cases

The two-step deletion (§18.2) is not atomic; a finder between steps 2 and 3 must help — this is the contract, not an edge case to special-case around. A node's next pointer is the only mutable field; the key is immutable post-insert, which is why deletion uses mark-then-unlink rather than overwriting the key.

18.9 Failure Analysis

An un-helped marked node accumulating under a workload that only inserts (never finds) is a slow memory leak, not a correctness bug — detected via the retained-marked-node-count metric (§18.10) crossing a threshold; recovery is triggering a full-list scan-and-help pass.

18.10 Operational Notes

tracing events on mark/help/physical-unlink; metric: retained-marked-node count (leading indicator of the leak in §18.9). No migration concerns (in-process type).

19. Phase 7 — Shalev–Shavit Split-Ordered Hash Map (Week 11–13)

19.1 Objectives

Ship the split-ordered-list hash map (Shalev & Shavit 2006, ADR-07): linearisable insert/remove/find with per-bucket lazy resize, avoiding a global rebuild pause.

19.2 Detailed Implementation Steps

Backing store is a Harris–Maged ordered list (§18) keyed by the bit-reversed hash; a bucket-pointer array is indexed by the low bits of the unreversed hash, each bucket pointing at a sentinel node in the list. Insert computes the reversed-bit key, locates the position via the bucket array, inserts via Harris–Maged (§18.2, P1). The split-ordering insight: with a 4-bucket map, bucket B serves keys whose hash mod 4 == B, and because the list is sorted by bit-reversed hash, all such keys form one contiguous suffix (their reversed hashes share a 2-bit prefix). Resize: when load factor crosses threshold, double the bucket array, Release-swap the pointer; new buckets are uninitialised (NULL) and lazily initialised on first access — the accessing thread walks up to the parent bucket and inserts a new sentinel, distributing resize cost across subsequent operations instead of a stop-the-world rebuild (ADR-07's rationale, I1's linearisation points inherit from the underlying Harris–Maged CASes). Deferred here: SIMD bucket-probe acceleration PhaseDeferred("§19.2") — a Phase-2 stretch per §25 M-series.

19.3 Deliverable

LockFreeHashMap<K, V, R> in crates/lockfree-map; benchmarked against dashmap and flurry.

19.4 Acceptance Criteria

Loom exhaustive pass at TC 2 on a small-bucket-count map (fixture loom_map_small_tc2.rs); shuttle randomised pass at TC 4–16, 10,000 schedules, concurrent insert/remove/lookup (fixture shuttle_map_10k.rs); get latency ≤ 50 ns uncontended, ≤ 200 ns at 16-thread contention (§4, §31 M6).

19.5 Conformance Fixtures

Fixture Purpose Expected Output
loom_map_small_tc2.rs exhaustive TC 2, small bucket count 0 oracle violations
shuttle_map_10k.rs 10,000 randomised schedules, mixed ops 0 linearisability violations
resize_during_insert.rs insert races a bucket-array grow new bucket found via lazy sentinel, no miss
malformed_hash_panic.rs a K::hash that panics mid-insert insert aborted before shared-state mutation

19.6 Pitfalls

The sentinel-node lazy-initialisation is the resize protocol's safety net; without it, an insert racing a bucket-array grow can miss the new bucket. The load-factor computation is approximate (a global counter, not exact) — len() is documented as approximate, never relied on for capacity planning. A K::Hash based on memory address (not stable across moves) is undefined behaviour for this map; the bound is Send + Sync + 'static and stable across clone.

19.7 Performance Concerns

The bit-reversed hash is not user-facing; the reversal is one hardware instruction (rbit/bswap-adjacent) on modern CPUs, not a measurable cost (§31.5 SIMD note). Resize cost is amortised across operations rather than paid in one stop-the-world pause, at the cost of slightly higher per-op latency variance immediately after a resize threshold trip.

19.8 Edge Cases

A K::hash implementation that panics mid-insert must not leave the map in an inconsistent state — the insert is aborted (via catch_unwind at the boundary) before any shared-state mutation (documented contract, Threat Model T5). Concurrent resize and remove on the same key must both observe a consistent bucket-array snapshot via the Release/Acquire pointer swap.

19.9 Failure Analysis

A K::hash panic is caught at the boundary and propagated as a typed error to the caller (P14) — the map itself is never corrupted, only the one operation aborted. A missed lazy sentinel insertion (a bug, not a designed case) manifests as a lookup miss for a key that was actually inserted — detected by the shuttle randomised harness (fixture shuttle_map_10k.rs) before merge.

19.10 Operational Notes

tracing events on resize-trip and lazy-sentinel-insert; metrics: approximate len() gauge, resize-event counter, per-bucket depth histogram (a proxy for hash-quality regressions). No migration concerns (in-process type).

20. Phase 8 — Skip List, Wait-Free Counter, Wait-Free Queue (Week 13–16)

20.1 Objectives

Ship the probabilistically-balanced lock-free skip list, the wait-free counter, and the gated Kogan–Petrank wait-free queue (ADR-08) — the three primitives that complete the progress-guarantee spectrum this library teaches (P5, I2, I3).

20.2 Detailed Implementation Steps

Skip list: a multi-level linked list; level 0 always present, level k present with probability 2⁻ᵏ; each level is a Harris–Maged list (§18.2) keyed on the value; insert/ remove/find walk top-down, each level's operation reusing the Harris–Maged CAS protocol — expected search depth O(log n); the top-level pointer is the most-contended site (the alternative, Ben-David/Lev "skipfilter", is more complex and not measurably faster on typical workloads, folded into ADR-07's sibling rationale). Wait-free counter: a per-thread CachePadded<AtomicI64> cell array; fetch_add writes only to the calling thread's cell (wait-free by per-thread isolation, I3); reads sum the array. Wait-free queue (Kogan & Petrank 2011, feature wait-free): each thread announces its pending op in a per-thread slot; every other thread, on its own operation, helps complete any pending announcement before proceeding — bounded steps per op regardless of contention (I3); the helping bound is O(threads) per op, at ~3× Michael–Scott's per-op cost, which is why it is feature-gated (ADR-08) rather than default.

20.3 Deliverable

LockFreeSkipList<K, V, R>, WaitFreeCounter, and WaitFreeQueue<T> (behind feature = "wait-free") in their respective crates; a 16-thread contended benchmark of the counter against a plain contended AtomicI64::fetch_add.

20.4 Acceptance Criteria

Skip list passes loom at TC 2 and 3 and shuttle at TC 4–16 (fixture loom_skiplist_tc23.rs); wait-free counter is ≥ 10× faster than a contended AtomicI64::fetch_add under 16-thread contention (§31 M11); wait-free queue passes loom at TC 2 (fixture loom_kp_tc2.rs) with every announced operation completing in a bounded number of helper-steps (proptest bounded_helping.rs, cap = 3× thread count).

20.5 Conformance Fixtures

Fixture Purpose Expected Output
loom_skiplist_tc23.rs exhaustive TC 2/3 0 oracle violations
bench_counter_vs_atomic.rs 16-thread contended fetch_add ≥ 10× throughput vs plain atomic
loom_kp_tc2.rs exhaustive TC 2 on the wait-free queue 0 oracle violations
bounded_helping.rs every op completes within 3×thread-count helper-steps 0 unbounded ops

20.6 Pitfalls

The skip list's top-level pointer is the contention bottleneck; the algorithm degrades toward a flat linked list under heavy concurrent insert at the top level (documented, not a bug). The wait-free queue's helping mechanism can starve individual operations under specific adversarial schedules even though it is wait-free in the theoretical (bounded-step) sense, not the "always fast" sense — document this distinction for callers. A K::Ord that is not a total order breaks the skip list silently; the type bound enforces at compile time.

20.7 Performance Concerns

The wait-free counter's per-thread cell array is sized for low thread counts; at ~1,000 threads the read-sum cost dominates and the design should shift to a hierarchical reduction (documented as a Phase-11 stretch, not a Phase-8 requirement). The Kogan–Petrank queue's ~3× per-op cost vs Michael–Scott (§20.2) is the load-bearing tradeoff behind ADR-08's feature gate.

20.8 Edge Cases

A skip-list insert racing another insert at the same key across multiple levels must resolve consistently level-by-level (each level's Harris–Maged CAS is independent — a partial multi-level insert is a valid intermediate state, not a bug, since find only requires level-0 presence to consider a key present). A WaitFreeQueue announcement slot exhausted by more concurrent operations than available slots blocks the excess on a documented fallback path (feature-gated, not default-path behavior).

20.9 Failure Analysis

A wait-free-queue operation that exceeds its bounded-helping-step budget (a correctness bug, not contention) is caught by bounded_helping.rs before merge; in production it would manifest as unbounded latency on one operation — detected via a per-op step-count histogram (§20.10). A skip-list level-consistency bug manifests as a find miss for a recently-inserted key — caught by the shuttle harness inherited from §19's map coverage pattern.

20.10 Operational Notes

tracing events: skip-list level-insert-depth, wait-free-queue helper-step count per op, counter per-thread-cell write rate. Metrics: step-count histogram (bounded-helping verification, I3), top-level-contention gauge. No migration concerns (in-process type).

21. Phase 9 — Verification Harness: Loom, Shuttle, Linearisability Oracle (Week 16–18)

21.1 Objectives

Ship the cross-algorithm verification contract: loom exhaustive checking, shuttle randomised checking, the WGL linearisability oracle, property tests, and fuzz targets (P10, I1, I14) — the gate every prior phase's algorithms already depend on.

21.2 Detailed Implementation Steps

Every algorithm gets a loom_test module under cfg(loom) (ADR-09) instantiating it against a sequential oracle and asserting every interleaving is linearisable; wired into make loom. For thread counts above 3, shuttle's PCT-biased randomised scheduler explores more aggressively (ADR-10); failing seeds check into verification/shuttle_seeds/<algorithm>/ for permanent regression coverage. The linearisability oracle (lockfree-verify::oracle, linearise.rs) implements the Wing–Gong–Liu (WGL) algorithm (Herlihy & Wing 1990, I1): record each observed op's start-time/end-time/result; search for a sequential interleaving respecting the partial order (op A ends before op B starts ⇒ A precedes B) that reproduces every result against the sequential reference — a backtracking search, exponential worst-case but poly(N) on typical histories. Property tests (proptest) generate random op sequences per algorithm; cargo-fuzz targets check for panics, UB (via miri), and linearisability violations. Deferred here: a loom-traces visualiser PhaseDeferred("§21.2") — a debugging-ergonomics stretch, not required for correctness.

21.3 Deliverable

lockfree-verify crate wired into every other crate's CI job; every algorithm has a loom test and a shuttle test in CI; the oracle is the reusable cross-algorithm contract any future data structure adopts.

21.4 Acceptance Criteria

100% of shipped algorithms (Treiber, Michael–Scott, Vyukov, SPSC, Chase–Lev, Harris–Maged, hash map, skip list, wait-free counter, Kogan–Petrank) have a passing loom test at their committed thread count (§14–§20's per-phase N.4 rows); the WGL oracle budget is 2 weeks initial development + 1 week per data structure for its sequential reference, tracked against Appendix B; shuttle runs 10,000 random schedules per algorithm per CI run (fixture-level, per §14.5 etc.).

21.8 Edge Cases

A loom test that passes under miri but fails on production aarch64 indicates a missing fence not modelled by loom's abstraction (I13) — the cross-architecture matrix (§22) is the catch-all for this gap. A linearisability history with concurrent ops that overlap exactly at a boundary nanosecond is resolved by the WGL algorithm's partial-order definition, not by wall-clock tie-breaking.

21.9 Failure Analysis

An oracle false-negative (accepting a non-linearisable history) is the single worst failure mode of this phase — oracle_wgl_negative.rs exists specifically to catch a regression in the oracle itself, not just in the algorithms it checks. A shuttle seed that stops reproducing (nondeterminism creeping into the harness, e.g. from wall-clock time or uncontrolled thread IDs) is a I14 violation — recovery is auditing the harness for any non-shuttle-controlled randomness source.

21.10 Operational Notes

CI dashboards surface: per-algorithm loom pass/fail, shuttle schedules-run count, checked-in failing-seed count (should trend toward zero as seeds are fixed and retired). No migration concerns (verification-only crate, no persisted state).

22. Phase 10 — Cross-Architecture Validation (Week 18–19)

22.1 Objectives

Prove every algorithm verified on x86-64 loom also holds on aarch64 (native) and a Power-like weak model (emulated) — closing the exact gap loom's abstraction cannot cover (I13, P11).

22.2 Detailed Implementation Steps

CI matrix: x86-64 native (TSO — release-store/acquire-load pairs free), aarch64 native (weaker model — STLR/LDAR cost, §8.1), Power-like weak model emulated via herd7 over extracted instruction sequences for the highest-risk paths (the Michael–Scott helping step, §14.2; the Vyukov sequence-field claim, §16.2; the Treiber pop, §8.3) — this matrix is the direct enforcement mechanism for I13 (cross-architecture equivalence) and P11 (cross-arch CI gates release). Per algorithm, CI emits x86-64 and aarch64 assembly, checked into audits/codegen/<algorithm>/<arch>.s; a diff between commits is a reviewable CI artefact. Litmus tests (short instruction sequences whose outcome characterises a memory model, Sewell et al. 2010; Maranget/Sarkar/Sewell 2012) are extracted for the three highest-risk paths above and evaluated by herd7 against x86-TSO, aarch64, and Power. Deferred here: full native Power CI (not just herd7 emulation) PhaseDeferred("§22.2") — gated to a later stretch once a Power CI runner is available; the litmus-test coverage is the Phase-0 commitment.

22.3 Deliverable

arch-matrix.yml green on x86-64 and aarch64 for every shipped algorithm; the herd7 litmus suite green for the three named high-risk paths; the codegen-diff artefact checked in.

22.4 Acceptance Criteria

100% pass rate on x86-64 and aarch64 native for every shipped algorithm (§4, §31 M12); ≥ 95% pass rate on the Power-emulated harness (§4 conformance bucket); a code-generation diff between two commits for the same algorithm on the same arch, absent an intentional change, is zero-diff (fixture codegen_stability.rs).

22.6 Pitfalls

Aarch64's load-acquire/store-release map to LDAR/STLR; the compiler's choice between LDAR and a plain load + DMB fence affects performance, not correctness — do not conflate the two. Power's weak model can make a loom-passing algorithm unsafe in practice (loom does not model Power) — the litmus tests are the specific cross-check for this gap. x86-TSO permits store-load reordering; an algorithm depending on a load observing its own thread's prior store (the "store-load fence" pattern) needs an explicit SeqCst fence even on x86 — an Acquire/Release pair alone is not enough there.

22.7 Performance Concerns

A release-store-then-acquire-load pair costs nothing extra on x86 (ordinary instructions), one STLR+LDAR pair on aarch64, and LWSYNC+LWZ+LWSYNC on Power — the per-arch cost difference is visible directly in the bench harness (§31.2) and is the reason §4's latency numbers are qualified "measured per architecture."

22.8 Edge Cases

A litmus test whose outcome set changes because an ISA spec revision changed the memory model (rare, but tracked) is a CI-visible event requiring an ADR to acknowledge the new target version. An algorithm that only the Power-emulated harness (not native aarch64) flags is triaged separately — Power's model is a strict superset of weaknesses aarch64 exhibits, so a Power-only failure narrows the fix to Power-specific fence placement.

22.9 Failure Analysis

A red aarch64 run blocks release (P11, ADR-12) — the canonical root cause is a fence that was inferred as unnecessary from x86 testing alone; the runbook (docs/runbook/livelock.md's cross-arch section) walks the triage: reproduce the litmus test locally, compare against the checked-in expected-outcome set, identify the missing fence. Forensic artifact: the audits/codegen/<algorithm>/aarch64.s diff pinpointing the exact instruction change.

22.10 Operational Notes

CI dashboard: per-arch, per-algorithm pass/fail matrix; codegen-diff review is a required PR check for any change touching lockfree-atomic or an algorithm's CAS site. No migration concerns (verification-only artefacts).

28. Compatibility & Versioning

No wire format, no on-disk schema — compatibility is source-level only (Core Schema §11). API stability: SemVer (ADR-16's ecosystem norm); a breaking type-signature change (e.g. adding a required trait bound to Guard) is a major version bump. Migration: a major-version bump ships a MIGRATING.md documenting the exact call-site diffs. Rolling upgrade: not applicable at the library level — the consuming binary is rebuilt and redeployed as one unit; the library provides no cross-version wire compatibility because it has no wire format. Deprecation policy: a deprecated public item carries #[deprecated(since = "X.Y", note = "...")] for at least one minor version before removal. Feature-flag compatibility: wait-free (Kogan–Petrank, ADR-08) and tracing (P14/§27) are additive, never load-bearing for correctness of the default build.

29. Testing & Verification Strategy

Unit tests — per-crate, standard cargo test, exercising the type-check and construction-time-assertion paths (§13.4, §16.4). Integration tests — cross-crate, exercising a data structure against its default reclamation scheme end-to-end (§14–§20). Property tests (proptest, ADR-17) — random op sequences per algorithm, tied to I1–I14: each invariant maps to one assertion the property test can trigger (§7's debugging methodology). Differential testing — the linearisability oracle's sequential reference (§21.2) is itself a differential-testing artifact: concurrent vs sequential behaviour must match. Fuzzing (cargo-fuzz, ADR-17) — per-algorithm and cross-algorithm targets (§23.2), gated by the 30-day canary (§23.4). 31. Performance Engineering

31.1 Methodology

Benchmarking uses criterion (ADR-18) on a documented, dedicated bench host per benchmarks/results/<host>/; profiling uses perf/cachegrind for allocation, lock (comparator-only), cache-miss, and syscall analysis; tail-latency analysis uses criterion's built-in percentile reporting (p50/p95/p99, §4). Cache discipline: every queue's head/tail (or producer/consumer index pair) is padded to a 128-byte boundary (repr(C, align(128)), I11) — without it, false sharing between producer and consumer cuts throughput by ~3× (measured, §31.2), at a cost of ~256 B/instance metadata overhead.

31.2 Atomic Op Cost (x86-64 / aarch64, calibrated per CI host)

Relaxed load ~1 ns/~1 ns; Acquire load ~1 ns (free)/~3 ns (LDAR); Release store ~1 ns (free)/~3 ns (STLR); successful CAS ~5 ns/~7 ns; SeqCst fence ~20 ns/~20 ns. 31.4 Backoff Tuning

Default ladder: 7 PAUSE, 7 YIELD, then microsecond sleeps (crossbeam-utils research, ADR-23, P9). _mm_pause/aarch64 yield hints the CPU pipeline during spin, avoiding a ~50-cycle branch-misprediction penalty per bare-spin retry. YIELD calls thread::yield_now; the sleep floor is the OS scheduler quantum (~1 ms on most systems). Per-call-site override exists for the rare "tight loop on a slow, uncontended path" case.

32. Scalability Analysis

What stays constant: per-instance fixed metadata (~256 B, I11); per-thread hazard-slot budget (4 slots default, I8). What grows: live-node memory (O(live elements)); retire- list/epoch-bag transient memory (bounded by threshold/2-epoch-lag, I8/I9). Named bottlenecks in order: (1) cache-coherence traffic on the shared head/tail word past ~8 contending threads (§4's 60%/40% linear-scaling-floor row); (2) the skip list's top-level pointer under heavy concurrent insert (§20.6); (3) the wait-free counter's read-sum cost at ~1,000+ threads (§20.7). Horizontal scaling: sharding — multiple independent instances, each with its own reclamation domain (P12), is the lever once (1) is hit; no built-in cross-instance coordination exists or is planned (§1 non-goal). Vertical scaling: more cores helps until LLC/interconnect saturation; NUMA-awareness is deferred (PhaseDeferred("§23.2"), §32's practical ceiling). Coordination overhead: zero cross-instance — each TreiberStack/MichaelScottQueue/etc. is a fully independent value (P12); the only coordination is intra-instance CAS contention. Practical ceiling: tested to 64 threads (§4); beyond that, sharding is the only lever, not a larger single instance.

33. Mental Models & First Principles

  1. MM1 — A CAS is a conversation, not a command. It says "if the world still looks like X, make it Y" — every algorithm is a sequence of such conditional conversations, not imperative steps. Predicts: why retry loops exist at all. Bug class without it: treating a CAS like an unconditional store. Applied in §8.2, §8.3.
  2. MM2 — Acquire/Release is a relay baton, not a lock. A Release store hands off a baton; an Acquire load picks it up — nothing is held in between. Predicts: why two threads can each hold "half" a synchronisation without blocking. Bug class without it: assuming Acquire/Release provides mutual exclusion. Applied in §8.1.
  3. MM3 — Reclamation is deferred destruction, not deferred allocation. The hard part was never "when to free," it's "how do I know no one is still looking." Predicts: why hazard pointers/epochs exist instead of just Arc. Bug class without it: reaching for reference counting and being surprised by its own contention (I5). Applied in §8.5, §15.
  4. MM4 — ABA is a proxy-identity bug, not a value bug. The CAS checks an address, but the programmer's mental model checks a meaning — the two diverge exactly when memory is reused. Predicts: why tagging or hazard-protection (not "checking the value again") is the fix. Bug class without it: adding a redundant re-read that doesn't actually help. Applied in §8.2, I4.
  5. MM5 — Lock-free is a system property, not a per-thread one. "Some thread progresses" says nothing about which thread — a starved thread under lock-freedom is not a bug. Predicts: why wait-freedom is a strictly stronger, separately-earned guarantee (I2, I3). Bug class without it: promising individual-thread latency bounds a lock-free design cannot give. Applied in §7, §20.
  6. MM6 — Helping is how "lock-free" survives preemption. Any thread preempted mid-operation must be completable by someone else, or the guarantee is fiction. Predicts: every lock-free algorithm with more than one CAS site needs a helping mechanism. Bug class without it: shipping an algorithm that is lock-free only when nothing gets preempted (§8.4, §8.6). Applied in §14.2, §20.2.
  7. MM7 — The memory model is the actual hardware contract; the language spec is a promise about it. x86's TSO is not "what C++ requires," it's a stronger guarantee the spec permits weakening — code correct only by TSO's extra strength is latent aarch64/ Power breakage. Predicts: why cross-architecture CI, not code review, is the real gate. Bug class without it: "it works on my machine" as a correctness argument. Applied in §8.1, §22.
  8. MM8 — Linearisability is a real-time constraint on a logical-time property. The operations can be reordered onto any legal sequential timeline, but that timeline must respect wall-clock non-overlap — it's not "eventually consistent," it's "consistent at every instant, from some valid vantage point." Predicts: why the oracle needs start/end timestamps, not just op order. Bug class without it: confusing linearisability with serialisability (no real-time constraint) or sequential consistency (no per-op real-time constraint either). Applied in §8, §21.3.

35. Back-of-Envelope Capacity Model

All numbers chain from §4's constraint table.

  1. Peak aggregate throughput: 20M ops/s/core (uncontended Vyukov, §4) × 16 cores = 320M ops/s aggregate ceiling before contention-scaling loss.
  2. Contention-adjusted throughput at 16 threads: 320M × 60% linear-scaling floor (§4 contention-scaling row) = 192M ops/s realistic ceiling for the Vyukov ring.
  3. Michael–Scott contention-adjusted throughput: 320M × 40% (MS's lower scaling floor, §4) = 128M ops/s ceiling.
  4. Per-instance fixed memory: 256 B metadata (I11 padding) × 1 instance = 256 B floor regardless of workload — the number every sharded-instance count multiplies.
  5. Hazard-pointer memory ceiling per thread: 4 slots (I8 default) × 8 B/pointer = 32 B/thread fixed hazard-slot memory, independent of live-node count.
  6. Hazard-pointer memory ceiling, fleet-wide: 32 B/thread × 64 threads (§4 max tested concurrency) = 2,048 B (2 KB) fleet-wide fixed hazard overhead at max tested concurrency.
  7. Retire-list worst-case retained memory (hazard): 64-op threshold (§15.2) × average node size (assume 32 B payload + 16 B header = 48 B) = 3,072 B (3 KB) worst- case per-thread retained-but-unreclaimed memory before a scan triggers.
  8. Epoch retained memory (2-epoch lag): assume 10K retires/sec sustained × epoch duration ~1 ms (a fast-advancing epoch under low starvation) × 2 epochs lag = 20 retained objects × 48 B = 960 B typical retained-bag size — far below the hazard worst case (7), which is exactly ADR-02's bounded-vs-unbounded tradeoff made numeric.
  9. ABA tag-wrap time-to-exhaustion: 2¹⁶ (default 16-bit tag, §4 ABA-window row) ÷ 10M CAS/s sustained on one word = 6.55 ms to wrap at extreme sustained contention — the exact number behind T8's mitigation trigger (32-bit tag gives 2³² ÷ 10M = 429 s, i.e. ~7 minutes, a three-orders-of-magnitude safety margin).
  10. Cache-line padding overhead at scale: 256 B/instance (4) × 1M concurrent instances (a hypothetical cache-serving fleet) = 256 MB aggregate fixed overhead — the number that justifies NOT padding every field indiscriminately, only the hot head/tail pair (I11's scope is deliberately narrow).

37. Alternative Architectures (Roads Not Taken)

37.1 Alternative A — Mutex-and-Condvar Baseline

┌─────────────┐     ┌─────────────┐
│  Thread 1   │────▶│  Mutex<T>   │◀────│  Thread N   │
└─────────────┘     │  + Condvar  │     └─────────────┘
                     └─────────────┘

Regime where it wins: low-to-moderate contention (< 4 concurrent threads), where the kernel-mediated blocking wait is cheaper than a spin-based retry loop and priority inversion is not a concern. Real system: the vast majority of std::sync::Mutex<VecDeque<T>> usages in production Rust services today, and Java code before j.u.c's non-blocking collections existed. Rejected because: at the 8–64 thread scale this library targets (§4), blocking-wait latency and priority-inversion risk dominate, and the whole point of this project is teaching the lock-free alternative (§2).

37.2 Alternative B — Pure RCU (Read-Copy-Update)

Readers: rcu_read_lock() → deref → rcu_read_unlock()   (no atomics on the read path at all)
Writers: copy → mutate copy → rcu_assign_pointer() → synchronize_rcu() → free(old)

Regime where it wins: read-mostly workloads with a small, bounded number of concurrent writers and where readers can tolerate a bounded staleness window — exactly the Linux kernel's dominant access pattern (McKenney, Required Reading §5). Real system: the Linux kernel's RCU subsystem, and this library's own QSBR scheme (§15.3) is a userspace cousin of it. Rejected as the sole reclamation strategy because this library targets general MPMC data structures with frequent writers, not read-mostly kernel-style data — QSBR is offered as an opt-in, not the architecture's foundation (ADR-02).

37.3 Alternative C — Hardware Transactional Memory (HTM)

begin_tx(); { read head; compute new state; write head; } commit_tx();  // abort → retry

Regime where it wins: short transactions with low real-world contention and hardware that reliably supports HTM without frequent spurious aborts (cache-capacity/interrupt-driven) — common in some in-memory database engines on Intel TSX-capable hardware. Real system: early libcds experiments and several in-memory OLTP engines use TSX-gated fast paths with a CAS-based fallback. Rejected as the primary architecture because TSX has been disabled or removed on several recent Intel microarchitectures (security mitigations), Power's equivalent (Power TM) is not portable to x86/ARM, and a design built around HTM would be un-shippable on a meaningful fraction of the target fleet — it remains a documented, deferred stretch (PhaseDeferred("§13.2")) rather than the foundation.

39. Glossary

  • ABA problem. A CAS succeeds because the observed value is unchanged by address, even though the underlying state changed and was recycled in between (§8.2).
  • Acquire. A memory ordering: no later memory access reorders before this load (§8.1).
  • ADR. Architectural Decision Record — a locked choice plus its rejected alternatives (§9).
  • AcqRel. Acquire-Release combined; used on a successful read-modify-write (§8.1).
  • Backoff. A progression of waits (spin → yield → sleep) used in a contended CAS loop (P9).
  • Bucket array. The index structure over a split-ordered list mapping hash prefixes to sentinel positions (§19.2).
  • CAS. Compare-and-swap — the canonical lock-free read-modify-write primitive (§8.2).
  • Cache-line padding. Layout technique preventing two hot fields from sharing a coherence unit (I11).
  • Chase–Lev deque. The 2005 growable circular-buffer work-stealing algorithm (§17).
  • Conformance bucket. A named pass-rate commitment (e.g. linearisability, ABA) gated in CI (§23.4).
  • DWCAS. Double-width CAS — CAS on 128 bits, x86-only as a single instruction (ADR-15).
  • EBR. Epoch-based reclamation (§15.2).
  • Fence. A memory barrier ordering accesses on either side of it (§8.1).
  • Guard. The reclamation handle returned while a thread observes shared memory (§11).
  • Hazard pointer. A per-thread slot announcing a pointer about to be dereferenced, preventing its reclamation while announced (§15.1).
  • Helping. A technique where one thread completes another's pending or partially-done operation (§8.4, §20.2).
  • Herd7. A memory-model litmus-test checker used for cross-architecture validation (§22.2).
  • Kogan–Petrank queue. The 2011 wait-free MPMC queue via announce-and-help (§20.2).
  • Linearisability. A correctness condition: every operation appears to take effect atomically at one point in real time (I1, Herlihy & Wing 1990).
  • Lock-freedom. A progress guarantee: system-wide, some thread completes in bounded steps (I2).
  • Loom. An exhaustive interleaving model checker for Rust concurrency (§21.2).
  • LL/SC. Load-linked/store-conditional — the RISC alternative CAS implementation strategy (§8.2).
  • Marked pointer. A pointer with a low bit repurposed to signal logical deletion (§18.2).
  • Michael–Scott queue. The 1996 unbounded MPMC lock-free queue (§14.2).
  • MPMC. Multi-producer multi-consumer.
  • Node. A heap-allocated element of a linked structure, retired (not freed directly) on removal (§11).
  • Obstruction-freedom. A progress guarantee weaker than lock-freedom: a thread running alone completes in bounded steps (referenced, §7 context).
  • PCT scheduler. Probabilistic Concurrency Testing — shuttle's bias toward unlikely interleavings (§21.2).
  • QSBR. Quiescent-state-based reclamation (§15.3).
  • Reclamation domain. A value-type context owning a reclamation scheme's global state (P12).
  • Release. A memory ordering: no earlier memory access reorders after this store (§8.1).
  • Retire. Marking a node as logically removed but not yet physically freed, pending reclamation-scheme clearance (§11).
  • SeqCst. Sequentially consistent — the strongest ordering, total order across all SeqCst operations (§8.1).
  • Shalev–Shavit split-ordered list. The 2006 lock-free extensible hash-table design (§19).
  • Shuttle. A randomised interleaving checker for Rust concurrency, using PCT/random/DFS schedulers (§21.2).
  • Skip list. A probabilistically-balanced multi-level ordered structure (§20.2).
  • Slot. A per-thread hazard-pointer announcement cell (§15.1).
  • Spurious failure. A compare_exchange_weak failure despite the compared value being unchanged, permitted on LL/SC architectures (§8.2, ADR-13).
  • SPSC. Single-producer single-consumer.
  • Synchronises-with. The formal relation by which a Release store's effects become visible, in order, to an Acquire load of the same location (§8.1).
  • Tag. A small integer packed with a pointer to defeat the ABA problem (I4).
  • Treiber stack. The 1986 lock-free LIFO stack (§8.3, §14.2).
  • TSO. Total Store Order — the x86-64 memory model (§8.1, §22.5).
  • Two-phase commit (Chase–Lev). The five-step protocol resolving the owner/stealer race on the last element (§17.2).
  • Vyukov ring. Dmitry Vyukov's sequence-numbered bounded MPMC queue design (§16.2).
  • Wait-freedom. A progress guarantee: every thread completes in a bounded number of steps regardless of others (I3).
  • WGL (Wing–Gong–Liu). The backtracking linearisability-checking algorithm this library's oracle implements (§21.2).
  • Work-stealing. A scheduling technique where idle threads pull work from busy threads' deques (§17).
