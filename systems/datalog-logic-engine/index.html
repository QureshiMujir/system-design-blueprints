In one paragraph

A Datalog engine takes known facts (the EDB) and if-then rules (the IDB) and computes every fact the rules imply, which the blueprint calls the minimal model (§1.1). This design builds one from scratch in Rust, in the Soufflé lineage, as a single-process in-memory library and command-line tool (§1.1, §1.4, ADR-01). It parses and safety-checks a program, sorts predicates into layers so negation and aggregation have a defined meaning, then repeats rule firing over only the newly derived facts until nothing changes (§1.1, §3.2). An optional rewrite restricts the work to what one query needs (§1.1). The users are static-analysis authors, application developers, engine developers and students, running on workstations and CI (§1.5, §1.4).

The problem, concretely

The blueprint's running example is a reachability question. Given edge(a,b), edge(b,c) and edge(c,d), what can a reach? The answer to ?- reach(a, Z) is b, c and d (§8.14). That is trivial at three edges. The design exists because each obvious way of computing it breaks as data grows.

  • Redo everything every round. Applying all rules to all known facts until nothing new appears (naive evaluation) repeats earlier work each round, which the blueprint calls a quadratic blow-up (MM4, Phase 5). Reachability over 10,000 nodes can produce up to 1e8 pairs (Capacity Model item 6), so wasted rounds are expensive.
  • Let duplicates in. If derived facts are collected into a list instead of a set, an old fact is counted as new again. The loop then never terminates or stops on the wrong round, and counts and sums come out inflated (P11, MM3).
  • Leave variables free. p(X) :- q(Y). lets X range over every constant, so the derivation grows without bound (P3).
  • Negate something still being computed. p(X) :- q(X), not p(X). derives and removes the same tuple forever (P8).
  • Join in the wrong order. Starting with two unrelated unfiltered relations is a cartesian product, which on a 10K-tuple EDB means 10^8 pairs per round (P6).

The design answers each with a structural rule instead of a runtime timeout: sets, safety checks at load time, layers, deltas and ordered joins (MM8, P2, P3, P4, P5, P6).

How it works, end to end

Follow the reachability program through the boxes of §3.1. The twelve crates are the locked workspace members (§1.7), and dl-core holds the shared types, Sym, PredId, Term, Atom, Literal, Rule and Tuple, with no I/O (§1.7).

  1. dl-parse. Reads facts, rules and queries, checks that each predicate always has the same number of arguments, and checks that every variable in a head, negated literal or comparison also appears in a positive body literal. Violations are rejected with a source location (§3.2, I3).
  2. dl-program. A predicate that never appears in a rule head is EDB, and one that does is IDB (§8.4). It builds the dependency graph, finds strongly connected groups with Tarjan's algorithm and assigns strata (§3.2, §8.5). Here edge is EDB, reach is IDB with a positive self-loop, and both sit in stratum 0 (§8.14).
  3. dl-eval. Walks the strata in order. Per stratum it keeps stable, delta and next-delta tuple sets and loops until the delta is empty (§3.2, §8.6, §8.8). Lower-stratum and EDB relations are read-only inside a stratum (§3.2).
  4. dl-join, dl-relation, dl-negation, dl-aggregate. dl-join walks a rule body left to right, probes an index for each positive literal and projects the result onto the head (§8.7). dl-negation checks absence in a finished lower-stratum relation (§3.2, I8). dl-aggregate reduces a frozen lower-stratum relation into group tuples (§3.2, §8.10).
  5. dl-magic. Given a program and a query goal, produces a transformed program, which dl-eval then evaluates to yield only query-relevant tuples (§3.2, Phase 11).
  6. dl-query, dl-repl, dl-cli. dl-query matches the goal against the computed relation and returns substitutions (§3.2, §8.12). dl-repl offers load, assert, query, explain and stratify. dl-cli offers run, query, explain and stratify (§3.2).

The blueprint's own trace of the reachability program, with delta the tuples new in a round; the query then returns Z=b, Z=c, Z=d (§8.14):

Round New reach tuples (delta) What happened
seed (a,b) (b,c) (c,d) the base rule copied the edges
1 (a,c) (b,d) the recursive rule joined last round's delta with edge
2 (a,d) same again
3 none nothing new, so the fixpoint is reached

The core ideas

A program means its least fixpoint (P1, I1, I3, I6)

Start with only the facts, apply every rule, add what it implies, and repeat. The set you converge on is the least fixpoint of the immediate-consequence operator, written T_P, and the blueprint defines T_P(I) = I ∪ { head(θ) | rule body satisfied under θ in I } (P1). T_P is monotone, so adding facts never removes a derivation, and the limit exists and is unique (P1). Rule order cannot change it (P1, P9).

Termination is structural, not a timeout (MM8). The grammar has no function symbols, so f(x) is a parse error, and every rule must be range-restricted, which gives a finite set of possible facts. The loop then stabilises within that many rounds (P1, P3, I6). The three unsafe examples (P3):

Rule Offending variable Why
p(X) :- q(Y). X in the head, not in a positive body literal
p(X) :- q(X), not r(Y). Y only inside a negation
p(X) :- q(X), X < Z. Z only inside a comparison

Each relation is a set, and Relation::insert(t) returns whether t was newly inserted. Every derivation site must use that boolean before it adds anything to a delta (I2, P11).

Semi-naive evaluation: join only with what is new (P5, MM4)

A tuple derivable only from old facts was already derived in an earlier round, so round r only needs at least one body literal to read from the previous round's new tuples (semi-naive evaluation, P5). Each relation keeps stable (all earlier rounds), delta (new last round) and next_delta (new this round) (§8.6). The merge at the end of a round (§8.6):

  1. A derived tuple enters next_delta only if it is in neither stable nor delta.
  2. stable ∪= delta, then delta = next_delta, then next_delta = ∅.
  3. converged = (delta is empty).

Cost per round is proportional to the delta, not the total size (MM4). At the §4 budget of under 10 ms for a delta below 100K tuples, that is about 100 ns per tuple, which the capacity model reads as one hash lookup (Capacity Model item 5). Naive evaluation stays in the build as the oracle that the fast path must equal (ADR-11, I5).

The blueprint disagrees with itself on how many rule variants fire per round. P5 and §8.8 generate one variant per body literal, so k variants, and §8.16 says a self-join gets two (P5, §8.8, §8.16). Phase 7.2 step 3 and I11 say 2^k - 1 variants, and Phase 7.4 tests that k=3 gives 7, although the same Phase 7.2 step also says each variant fixes exactly one literal to delta (Phase 7.2 step 3, I11, Phase 7.4). Both are given here, unresolved.

Strata: negation and aggregation need a finished relation (P4, I4, I8)

not p(t) means "p(t) is not derivable", which is only decidable once p is final (negation as failure, MM6, I8). So predicates are put into layers (strata) and a rule may negate or aggregate only over a strictly lower layer (P4). Each positive, negated or aggregated body literal adds a labeled edge, Pos, Neg or Agg (§8.5). The layering from §8.5 is:

  • every stratum starts at 0
  • a Pos edge from q to p sets stratum[p] = max(stratum[p], stratum[q])
  • a Neg or Agg edge sets stratum[p] = max(stratum[p], stratum[q] + 1)
  • repeat until stable, and reject if any cycle contains a Neg or Agg edge (§8.5)

Tarjan's SCC pass in O(V+E) is the check (P4, I4). The blueprint's example: reach is recursive but purely positive, so it sits in stratum 0, and count_reach(X, count<Y>) :- reach(X, Y) has an Agg edge, so it sits in stratum 1 (§8.15). Rejected outright (P4): p :- not p., p :- not q. q :- not p. and p(X) :- count{ X : p(X) } > 0.. Rejection is a hard gate with no runtime fallback and no partial evaluation (P12, Failure Mode Interaction Notes). Aggregation groups by the non-aggregate head variables, applies count, sum, min or max, and emits one tuple per group (§8.10).

The edge direction is drawn body-to-head in §8.5 and head-to-body in P4 and §3.2; the layering result is the same (§8.5, P4, §3.2).

A rule body is a join, and the order decides the cost (P6, MM2)

A rule body is a relational join and the head is a projection, so join order and indexes dominate cost as in SQL (MM2). The index-nested-loop join processes literals left to right (§8.7). For a positive literal it computes which argument positions are bound, looks up the matching tuples in an index keyed on those positions, and extends the variable bindings. A repeated variable is checked for conflict and the branch is pruned on a mismatch. Comparisons filter, and at the end the bindings project onto the head (§8.7). The index is a map from the values at the bound positions to the matching tuples, built lazily on first use (§8.6, ADR-07).

Ordering sorts literals by estimated output size, |relation(L)| divided by selectivity factors for the bound variables, and puts a literal with no bound variable last to avoid a cartesian product (P6). The blueprint states three versions of the search. P6 uses dynamic programming for k ≤ 6 literals and greedy above that. ADR-14 locks a greedy most-bound-first heuristic once per rule and defers full dynamic programming. The capacity model calls the search O(k!) capped by the heuristic (P6, ADR-14, Capacity Model item 9).

Magic sets: ask only for what the query needs (P7, I9)

Full bottom-up evaluation builds the whole model even when the user asks one question. Magic sets rewrites the program so the query's known arguments flow into the rules as extra "demand" facts (MM7). The steps from P7:

  1. For ?- p(a, X) the adornment is p^{bf}, where b is bound and f is free.
  2. Add the seed fact magic_p_bf(a).
  3. For p(X, Y) :- q(X, Z), r(Z, Y). add magic_q_bf(X) :- magic_p_bf(X). and put magic_p_bf(X) into the original rule's body.
  4. Repeat for every reachable adorned predicate.

It runs only if the goal has at least one bound argument, the goal predicate is IDB and the program is recursive over it. Otherwise full evaluation runs (P7, ADR-15). The answer set must be identical with and without it (I9), and --no-magic is the fallback if it is not (I9).

The trade-offs — where engineers disagree

Semi-naive bottom-up as the default (ADR-11)

Chosen: semi-naive bottom-up, with naive kept as a reference and diff-test target, because semi-naive is the standard efficient strategy (§9, P5, I5). Rejected: top-down SLD resolution, tabling, magic-sets-only (§9). When the rejected choice is right: top-down tabling for highly selective queries that touch a small fraction of the model, where bottom-up over-derives (§9). The blueprint's answer is that magic sets recovers demand-driven behavior without a second engine (Alternative Architectures A1).

Stratified negation only (ADR-12)

Chosen: stratified negation-as-failure under the closed-world assumption, which is decidable, well understood and sufficient for the target workloads (§9). Rejected: well-founded semantics, stable-model semantics, three-valued logic (§9). When the rejected choice is right: when programs have negation through cycles that must still carry a defined meaning (§9). That is the trigger for un-deferring well-founded semantics (Deferred Register).

A hash set for every relation (ADR-06)

Chosen: hashbrown::HashSet<Tuple>, because deduplication is the core invariant and membership test is the most frequent operation (§9, I2). Rejected: BTreeSet, columnar storage, an arena of sorted vectors (§9). When the rejected choice is right: columnar storage when scans and aggregation over huge relations dominate, BTreeSet when ordered iteration or range scans are needed (§9). On the crate, ADR-06 locks hashbrown while §4.1 says std::collections::HashMap is sufficient (ADR-06, §4.1).

Greedy join ordering, once per rule (ADR-14)

Chosen: selectivity from relation sizes, most-bound-first, reordered once per rule at evaluation start, because a simple greedy heuristic avoids worst-case cartesian products (§9). Rejected: exhaustive dynamic programming, query-graph min-cut, no ordering (§9). When the rejected choice is right: full dynamic programming when bodies are large and a bad greedy choice triggers a cartesian-product blow-up in complex analytic queries (§9).

Magic sets as an optional, per-query rewrite (ADR-15)

Chosen: applied at query time per adornment, with a fall-back to full evaluation for fully free queries, because it adds complexity and does not affect correctness (§9, P7, I9). Rejected: always-on magic sets, OLDT tabling, demand-driven tabling (§9). When the rejected choice is right: always-on when every query is bound-heavy and the rewrite always pays, and OLDT tabling when top-down is the base engine (§9).

One thread (ADR-16)

Chosen: single-threaded evaluation with no async and no rayon in Phases 1 to 13, because parallel semi-naive needs careful delta-merge synchronization and correctness comes first (§9). Rejected: async Tokio, an actor model, parallel semi-naive from Phase 1 (§9). When the rejected choice is right: when relations are huge and stratum-level parallelism gives near-linear speedup on multicore (§9). The scope lists conflict on timing: ADR-16 says Phase 14 evaluates rayon, §1.2 and §1.3 put parallel evaluation out of scope, and the Deferred Register says "Phase 14 / post-v1" (§9, §1.2, §1.3, Deferred Register).

Roads not taken (Alternative Architectures, Deferred Register)

Top-down tabling (A1, XSB) wins for queries touching a small fraction of the model. It lost because the target workloads materialize most of the IDB (Alternative Architectures A1).

Incremental dataflow (A2, Differential Datalog) wins when inputs change continuously and only deltas should recompute. It lost for version one because evaluation is batch, load once and query (Alternative Architectures A2, §4).

Compile to native (A3, Soufflé) wins for huge static analyses run repeatedly, where compile-once pays off. It lost because an interpreter gives a REPL, and the §4 sizes fit an interpreter (Alternative Architectures A3).

Worst-case-optimal joins (A4, Leapfrog Triejoin) win on cyclic many-way joins where binary-join plans explode. They lost for simplicity, since hash joins with ordering suffice for bodies of 12 literals or fewer (Alternative Architectures A4, §4).

Deferred features each wait for a trigger: on-disk persistence when the working set exceeds RAM, parallel fixpoint when rounds are CPU-bound on multicore, well-founded semantics for non-stratifiable programs, multi-query magic sets when queries share structure, and rule retraction with full incremental view maintenance when inputs change continuously and re-derive cost dominates (Deferred Register).

What must never be false

  • I1: the returned IDB equals the least fixpoint. Noticed only by differential tests against the naive evaluator; there is no runtime recovery (I1).
  • I2: no duplicate tuple in any relation. The HashSet enforces it, with a debug-build disjointness assertion after each delta (I2).
  • I3: every head, negated or compared variable appears in a positive body literal. Noticed at load by SafetyError, counted by parse.safety_errors_total (I3).
  • I4 and I12: no Neg or Agg edge inside any SCC, so strata have one fixed total order. Noticed at load by StratificationError, counted by program.stratification_failures_total (I4, I12).
  • I5 and I11: semi-naive equals naive. I5 is random-program fuzzing (test.semi_naive_divergence_total), I11 the named-fixture gate on every CI build (test.fixture_diff_failures_total) (I5, I11).
  • I6: every safe, function-symbol-free program terminates. Backed by an optional --max-rounds breaker, default 10 * |EDB|, which emits MaxRoundsExceeded and signals a dl-eval bug (I6).
  • I7 and I8: monotone within a stratum, and not p(t) reads a finished lower-stratum p. Both follow structurally from I4, with property and conformance tests, and no runtime telemetry (I7, I8).
  • I9: magic sets never changes the answers. Noticed by comparing with and without the rewrite, counted by magic.transform_applied_total (I9).
  • I10: answers are exactly the minimal-model substitutions. Noticed by Phase 14 conformance against known models, and by provenance tracing (I10).

What breaks in production

Unstratifiable program. Symptom: StratifyError with a cycle of predicates. Cause: mutual recursion through negation or aggregation. Detected by SCC analysis at load. No automatic recovery: restructure the rules, with dl-cli stratify --explain dumping the cycle as DOT (Failure Modes: Unstratifiable program).

Fixpoint non-termination. Symptom: rounds exceed max_rounds, giving FixpointTimeout. Cause: a rule that derives new tuples every round. Detected by a per-stratum round watchdog. The stratum is killed and a partial-model error is returned (Failure Modes: Fixpoint non-termination, TH-01).

Tuple cap or out-of-memory. Symptom: TupleLimitExceeded or an OS kill. Cause: a large recursive derivation or a high fan-out EDB. Detected by the dl_relation_size gauge. Further insertions are rejected, and the engine must return an error and never a truncated model presented as complete (Failure Modes: OOM / tuple cap exceeded, Failure Mode Interaction Notes).

Semi-naive divergence. Symptom: different results from naive and semi-naive. Cause: a stable/delta bookkeeping bug (I5). Detected by the CI diff test. Auto-recovery falls back to the naive driver for that stratum, and --naive is the operator switch (Failure Modes: Semi-naive divergence).

Magic-sets answer divergence. Symptom: --magic and --no-magic return different tuples. Cause: an adornment or rewrite bug that breaks I9. Detected by the conformance diff. Recovery is always to disable magic sets and run full evaluation, a path the blueprint says must be tested explicitly (Failure Modes: Magic-sets answer divergence, Failure Mode Interaction Notes).

Aggregate overflow. Symptom: a wrong number or AggregateOverflow. Cause: a sum exceeding u64. Detected by checked arithmetic. The error must be handled, not treated as a warning, since a wrong aggregate propagates upward (Failure Modes: Aggregate overflow, TH-13, Failure Mode Interaction Notes). The blueprint disagrees with itself: §3.2 and Phase 9 hold sums as i64 with a checked add returning AggError::Overflow (§3.2, Phase 9.2, Phase 9.4), and §8.16 says a sum "wraps at i64 boundary" with a warning (§8.16).

Threats worth knowing, by trust boundary (Threat Model):

  • TH-01, a crafted recursive program that never converges, is met by a per-stratum round ceiling and a per-relation tuple cap (Threat Model, T3).
  • TH-02, an adversarial fact file of millions of tuples, is met by a per-relation cap, default 10M (Threat Model, T4).
  • TH-05, an unsafe rule slipped in, is met by the safety check before any AST is promoted (Threat Model, T1, I3).
  • TH-11, a magic-sets rewrite that silently changes answers, is met by diff tests and a --no-magic fallback (Threat Model, T5, I9).
  • TH-14, a cross-product exhausting RAM before any filter, is met by cost-based ordering and a per-join row ceiling (Threat Model, T3).

How it compares

  • Soufflé compiles each program to specialized C++ with purpose-built relation containers and OpenMP. That is right for large, repeated static-analysis runs where compile-once beats an interpreter (Comparative Architecture).
  • Differential Datalog (DDlog) is built on differential dataflow, so it is incremental by construction. That is right for streaming or reactive inputs, where this design re-derives from a single-fact delta (Comparative Architecture, Phase 13).
  • Datomic stores immutable datoms with covering indexes and answers a Datalog query subset. That is right when you need an auditable, time-travel database whose query language happens to be Datalog (Comparative Architecture).
  • Nemo targets existential rules (datalog±) with bottom-up materialization. That is right for knowledge-graph and ontology reasoning that needs the existentials this engine deliberately excludes (Comparative Architecture).
  • LogicBlox made Datalog a transactional database language with aggregation and updates. That is right for enterprise applications wanting declarative business logic and persistence in one engine (Comparative Architecture).

Questions to test yourself

  1. Why is set semantics required for termination, not merely for correct counts (MM3, I2, I6)? — Hint: P11's "Why duplicates are not merely wasteful" paragraph (Hard Questions item 2).
  2. A program contains a negative cycle. Why must it be rejected at load (I4, MM5, Phase 4) rather than caught at runtime? — Hint: P12 and the Failure Mode Interaction Notes (Hard Questions item 4).
  3. Sketch why magic-sets preserves the answer set (I9, MM7, Phase 11) while changing which tuples get derived. — Hint: §8.11 and P7's Correctness paragraph (Hard Questions item 6).
  4. Why is join ordering a most-bound-first heuristic rather than full DP (ADR-14, Phase 10, Capacity Model), and when does that choice hurt? — Hint: the last column of ADR-14 and P6 (Hard Questions item 10).
  5. Why does incremental assert do a full semi-naive re-derive from a single-element delta (Phase 13, §4) rather than true incremental view maintenance (Deferred Register)? — Hint: Phase 13's retract design and the Deferred Register trigger (Hard Questions item 16).

If you only remember three things

A program means the least fixpoint of its rules, and that is the only thing every strategy must agree on, so naive, semi-naive and magic sets differ only in cost (MM1, I1, I5, I9). Termination and soundness are structural, from sets, safety and strata checked at load, and not from timeouts (MM8, I3, I4). Evaluation is joins over the newest facts, so join order and indexes set the speed (MM4, MM2, P6).

Words used here

  • EDB: the predicates defined only by base facts, never derived (§8.4, Glossary).
  • IDB: the predicates defined by rule heads, computed by evaluation (§8.4, Glossary).
  • Minimal model: the unique least Herbrand model, in which every IDB tuple is derivable from EDB facts by the rules (Glossary, I1).
  • Range restriction (safety): every variable in a head, negation or comparison also appears in a positive body literal (I3, P3).
  • Stratum: one layer of predicates, finished completely before a higher layer reads it (P4, Glossary).
  • Delta: the tuples added in the last round, which the current round joins against (§8.6).
  • Semi-naive evaluation: fire rules only when a body literal reads from a delta (P5, Glossary).
  • Negation as failure: not p(t) holds when p(t) is absent from a finished relation (I8, MM6).
  • Index-nested-loop join: a join that probes an index on the already-bound argument positions (§8.7, Glossary).
  • Adornment: a bound/free string such as bf marking which arguments of a goal are known (P7, Glossary).
  • Magic sets: a rewrite that adds demand predicates so only query-relevant tuples are derived (P7, I9).
  • Provenance: the derivation tree showing why a tuple is in the model (P10, Glossary).
