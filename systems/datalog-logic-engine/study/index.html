Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why do naive, semi-naive, and magic-sets all yield the same model (MM1, I1, Phases 5/7/11), and what does that imply about where to optimize?
  2. Why is set semantics required for termination, not merely for correct counts (MM3, I2, I6)?
  3. Derive why semi-naive's per-round cost is proportional to delta size, not total size (MM4, Phase 7, Capacity Model).
  4. A program contains a negative cycle. Why must it be rejected at load (I4, MM5, Phase 4) rather than caught at runtime?
  5. Why can NAF be evaluated only after a stratum is fully closed (MM6, I8, Phase 8), and what unsound result follows from violating that?
  6. Sketch why magic-sets preserves the answer set (I9, MM7, Phase 11) while changing which tuples get derived.
  7. Range-restriction + no function symbols guarantees termination (MM8, I3/I6, Phase 2). Which would you relax to support lists, and what breaks?
  8. Compute the worst-case derivation count for transitive closure on 10K nodes / 100K edges and reconcile it with the < 2 s budget (Capacity Model, §4).
  9. Why is the join index keyed on bound positions and built lazily per join (ADR-07, Phase 10), and when would eager indexing win?
  10. Why is join ordering a most-bound-first heuristic rather than full DP (ADR-14, Phase 10, Capacity Model), and when does that choice hurt?
  11. Why store Vec<Sym> tuples in a HashSet rather than columnar storage (ADR-06/08, MM2/3), and which workload flips that decision?
  12. The differential test asserts semi-naive ≡ naive (I5, Phase 14). Why keep naive purely as an oracle, and what bug class does it catch?
  13. Why stratified negation over well-founded/stable-model semantics (ADR-12, MM5), and in which regime would WFS be required?
  14. How does aggregation fit the stratification framework (ADR-13, Phase 9), and why must an aggregate see a closed relation (MM5/6)?
  15. Derive the EDB and IDB memory ceilings from §4 and explain the ≤ 2× index-overhead budget (Capacity Model).
  16. Why does incremental assert do a full semi-naive re-derive from a single-element delta (Phase 13, §4) rather than true incremental view maintenance (Deferred Register)?
  17. Why does the interner use Arc<str> + append-only Vec with no global state (ADR-05, MM1), and how does that aid testing and termination reasoning?
  18. Why forbid function symbols entirely (MM8, I6), and how does that bound the Herbrand base (Capacity Model)?
  19. Compare this interpreter to Soufflé's compile-to-C++ approach (Comparative): which §4 constraint makes the interpreter acceptable here?
  20. When does Differential Datalog's incremental-by-construction model (Comparative, Deferred Register) beat this engine's re-derive approach, and what §4 assumption rules it out for v1?

Mental Models & First Principles

  • MM1 — Datalog separates declarative meaning from operational strategy. The least fixpoint of the rules is the answer; naive, semi-naive, and magic-sets are merely ways to compute it. Predicts: every correct strategy yields the identical model. Bug without it: mistaking an optimization (magic-sets) for a semantic change. Applied: §2, I1, Phases 5/7/11.
  • MM2 — A rule is relational algebra: body = join + select, head = projection. Evaluation is repeated relational joins to a fixpoint. Predicts: join order and indexing dominate cost, exactly as in SQL. Bug without it: treating Datalog as logical interpretation → row-at-a-time slowness. Applied: Phase 6, Phase 10, ADR-07.
  • MM3 — Sets, not bags: duplicates are a semantic error, and dedup is what guarantees termination. Predicts: without set semantics the fixpoint may never close. Bug without it: bag semantics → inflated counts and non-termination. Applied: I2, ADR-06, Phase 3.
  • MM4 — Semi-naive evaluation joins only with last round's NEW tuples (the delta). Never recompute what didn't change. Predicts: per-round cost ∝ delta size, not total size. Bug without it: naive re-derivation every round → quadratic blow-up. Applied: I5, Phase 7, MM2.
  • MM5 — Stratification is a topological layering so each non-monotone op sees a CLOSED relation. Predicts: a negative cycle means an undefined program (reject at load). Bug without it: negating a relation still being computed → unsound/oscillating fixpoint. Applied: I4/I8, Phases 4/8, ADR-12.
  • MM6 — Negation is closed-world (NAF): "not p(x)" means p(x) is not derivable, decided only after p's stratum completes. Predicts: NAF needs a fully materialized relation first. Bug without it: evaluating NAF mid-fixpoint → wrong negatives. Applied: I8, Phase 8.
  • MM7 — Magic-sets is a provably answer-preserving program rewrite that pushes the query's bindings into the rules. It turns bottom-up into goal-directed. Predicts: it changes performance, never the answer set. Bug without it: believing magic-sets can drop answers → unsound rewrites. Applied: I9, Phase 11, ADR-15.
  • MM8 — Termination is structural, not runtime-checked. Range-restriction (every head var bound in a positive body literal) + no function symbols bounds the Herbrand base, so the fixpoint must close. Predicts: reject unsafe rules at load, not via a timeout. Bug without it: relying on a step limit → false non-termination or missed answers. Applied: I3/I6, Phase 2.

5. Required Reading

Books

B1 — Abiteboul, Hull, Vianu: Foundations of Databases (1995)

  • Chapters: 12 (Datalog syntax + model-theoretic semantics), 13 (bottom-up evaluation, naive + semi-naive algorithms, termination), 14 (stratified negation + aggregation, unique minimal model theorem), 15 (magic sets, query-subquery, counting).
  • Concepts to extract:
    • Formal definition of T_P (immediate-consequence operator); monotonicity proof on the powerset lattice.
    • Theorem 13.1: naive fixpoint terminates in finitely many rounds for function-symbol-free Datalog.
    • Semi-naive derivation rule (Definition 13.3): a tuple is new iff it uses at least one tuple from the previous round's delta.
    • Stratification algorithm (Definition 14.1): stratum assignment via PDG + SCC; uniqueness of the perfect model.
    • Magic-sets correctness theorem (Theorem 15.6): the transformed program answers the query correctly.
  • Why it matters: every invariant I1–I10 has a theorem number here. Read end to end before Phase 5. All algorithm pseudocode in Phases 5–11 must be traceable to a definition or theorem in this book.

B2 — Ullman: Principles of Database and Knowledge-Base Systems, Vol. 1–2 (1988/1989)

  • Chapters: Vol. 1 Ch. 3 (relational algebra operators), Vol. 2 Ch. 12 (naive evaluation pseudocode), Ch. 13 (semi-naive pseudocode, delta rule), Ch. 14 (recursion in SQL contrast), Ch. 15 (magic sets, supplementary magic, counting method).
  • Concepts to extract:
    • Naive fixpoint loop pseudocode (Algorithm 12.1): the exact loop implemented in Phase 5.
    • Delta derivation rule (Section 13.2): for each rule with k body literals, k delta-variants are generated (one per literal replaced by delta); the semi-naive engine fires each variant.
    • Magic-sets construction (Section 15.2): adorned predicates, seed magic facts, modified rules; the bf/bb/ff adornment notation used in dl-magic.
    • Supplementary magic (Section 15.3): optimization that avoids re-generating magic predicates multiple times.
  • Why it matters: the delta-variants insight from Ch. 13 is the precise specification for DeltaRelation firing logic in Phase 7. Many Datalog engine bugs trace to misapplying this rule.

B3 — Ceri, Gottlob, Tanca: Logic Programming and Databases (Springer, 1990)

  • Chapters: Ch. 3 (EDB/IDB classification; predicate dependency graph construction), Ch. 5 (evaluation strategies: push vs pull vs mixed), Ch. 6 (range restriction definition with counterexamples), Ch. 7 (stratified negation formalization; uniqueness of stratified model).
  • Concepts to extract:
    • Formal EDB/IDB split: a predicate is EDB if it appears in the head of no rule; IDB otherwise.
    • Dependency graph construction: for each rule h :- b1, ..., bn, add edge (h, bi) labeled Pos; for not bi, add edge labeled Neg.
    • Non-stratifiable example programs: mutual negation cycles; use for Phase 2 error message test cases.
    • Range-restriction counterexamples: p(X) :- q(Y). (X unbound), p(X) :- q(X), not r(Y). (Y in negation unbound).
  • Why it matters: Ch. 3 maps directly to dl-program (Phase 4). Ch. 7 provides the stratification uniqueness theorem used to justify that dl-program's stratum assignment is canonical.

B4 — Ramakrishnan & Gehrke: Database Management Systems (3rd ed., 2003)

  • Chapters: Ch. 12 (query optimization: cost estimation, histogram-based selectivity, join ordering), Ch. 13 (join algorithms: index-nested-loop, sort-merge, hash join), Ch. 14 (catalog statistics).
  • Concepts to extract:
    • Index-nested-loop join (Section 13.2): for each outer tuple, probe the inner relation's index for matching tuples. This is exactly dl-join's algorithm.
    • Selectivity estimation (Section 12.3): for an equality predicate on attribute A, selectivity = 1 / |distinct values of A|. For multi-attribute: product of per-attribute selectivities (independence assumption).
    • Join ordering: reorder as a left-deep tree; enumerate using dynamic programming or greedy; cost = sum of intermediate sizes.
    • B-tree vs hash index tradeoff: hash index for equality lookups (used in dl-relation Index); B-tree for range queries (not needed in standard Datalog — CmpOp is evaluated inline).
  • Why it matters: Sections 13.2 and 12.3 are the direct specification for dl-join Phase 6 and cost-based Phase 10.

B5 — Garcia-Molina, Ullman, Widom: Database Systems: The Complete Book (2nd ed., 2009)

  • Chapters: Ch. 15 (recursive query processing; recursive SQL; Datalog semantics contrast), Ch. 16 (parallel query; fixpoint parallelism sketch).
  • Concepts to extract:
    • Mutual recursion handling: multiple IDB predicates in the same SCC must be co-evaluated in the same stratum; the stratum fixpoint requires all co-recursive predicates to stabilise together.
    • Recursion + aggregation interaction: why count in a recursive rule is non-monotone; why it requires a lower-stratum input.
    • Parallel fixpoint: partitioning tuples across workers; merge at round end. Informative for Phase 14 performance design even if Phase 14 targets single-threaded.
  • Why it matters: co-recursive stratum evaluation (multiple IDB predicates per stratum) is an edge case in Phase 4 and 7 that must be handled correctly.

B6 — Date: An Introduction to Database Systems (8th ed.)

  • Chapters: Ch. 4–6 (relational algebra, tuple relational calculus, domain relational calculus), Ch. 24 (deductive databases: Datalog, CWA).
  • Concepts to extract:
    • Closed-world assumption (CWA): atoms not in the model are false; contrast with open-world assumption (OWA) used in description logics.
    • CWA formalization: not p(t) in Datalog means p(t) ∉ lfp(T_P), not "unknown".
    • Relational operators as Datalog rule fragments: selection = positive body literal with CmpOp; projection = head variables; join = multiple positive body literals.
  • Why it matters: CWA is why dl-negation evaluates not p(t) as definite absence (I8). Without CWA, the not operator would need three-valued logic.

B7 — Fitting: Computability, Complexity, and Languages (2nd ed., 1996)

  • Chapters: Ch. 2–3 (propositional + first-order logic; Horn clauses), Ch. 9 (logic programming), Ch. 10 (SLD resolution; Prolog semantics).
  • Concepts to extract:
    • Horn clause normal form: a clause with at most one positive literal. Datalog rules are definite Horn clauses (exactly one positive literal — the head).
    • SLD resolution (top-down): contrast with bottom-up fixpoint. SLD may loop; Datalog bottom-up always terminates (P3).
    • PTIME data complexity: Datalog query evaluation is in PTIME in the size of the EDB (data complexity). Use as a bound for performance targets.
  • Why it matters: understanding the top-down/bottom-up duality clarifies why dl-query uses the computed minimal model (bottom-up) rather than goal-directed SLD resolution.

B8 — Nielson, Nielson, Hankin: Principles of Program Analysis (Springer, 1999)

  • Chapters: Ch. 1 (reaching definitions; live variables; dataflow frameworks), Ch. 2 (constraint-based analysis), Ch. 5 (control-flow analysis; type-based analysis).
  • Concepts to extract:
    • Dataflow analysis as fixpoint computation: dataflow equations are Datalog rules over a lattice; the analysis result is the least fixpoint.
    • Constraint-based analysis: the constraint system for points-to analysis is a Datalog program over an EDB of syntactic facts.
    • Monotone framework: a dataflow analysis is correct iff the transfer functions are monotone — same as P8.
  • Why it matters: provides context for portfolio cross-references #363 (semantic code intelligence) and #231 (taint analysis). Demonstrates that Datalog engines are not academic toys — they back industrial static analysers.

Papers

P1 — Ceri, Gottlob, Tanca (1989), IEEE TKDE 1(1): What You Always Wanted to Know About Datalog (And Never Dared to Ask)

  • Core contribution: compact survey unifying syntax, semantics (model-theoretic + fixpoint), safety, stratified negation, and evaluation strategies in ~40 pages.
  • Implementation relevance: canonical terminology used throughout this specification. The EDB/IDB split, range restriction definition, and stratification algorithm are all cited from here. Read before writing any code.
  • Key tables: Table 1 (safe vs unsafe rules); Table 3 (evaluation strategy comparison: naive, semi-naive, top-down, magic sets).

P2 — Bancilhon, Maier, Sagiv, Ullman (1986), PODS: Magic Sets and Other Strange Ways to Implement Logic Programs

  • Core contribution: original magic-sets algorithm; adornment notation (bf, bb, ff, etc.); sideways information passing (SIP) rules; correctness proof.
  • Implementation relevance: the definitive specification for dl-magic (Phase 11). The adornment bf directly maps to the Adornment type. The SIP rules generate the modified rules in the transformed program. Worked example on ancestor/path programs is the primary test case for Phase 11.

P3 — Balbin & Ramamohanarao (1987), JLP 4(3): A Generalization of the Differential Approach to Recursive Query Evaluation

  • Core contribution: generalised semi-naive evaluation; correctness proof for the delta-firing rule; extension to mutual recursion.
  • Implementation relevance: grounds the delta-only firing rule in Phase 7. The generalisation covers programs where multiple IDB predicates are mutually recursive in the same stratum. The correctness proof is the formal basis for I5.

P4 — Van Gelder, Ross, Schlipf (1991), JACM 38(3): The Well-Founded Semantics for General Logic Programs

  • Core contribution: well-founded semantics via alternating fixpoints; three-valued logic for unstratifiable programs.
  • Implementation relevance: defines the boundary — programs accepted by this engine are a strict subset of well-founded programs. Use when authoring error messages for non-stratifiable programs: explain that the program might have a well-founded model but is outside this engine's scope.

P5 — Green, Karvounarakis, Tannen (2007), PODS: Provenance Semirings

  • Core contribution: semiring abstraction for why/where/how-provenance; annotation propagation through joins (semiring product) and unions (semiring sum).
  • Implementation relevance: the ProvenanceStore in dl-repl is the why-provenance instance (Boolean semiring). The semiring framework explains why provenance composes correctly through chains of rule derivations. Phase 13 explain command renders the why-provenance tree.

P6 — Greco, Spezzano, Trubitsyna (2015), TPLP 15(4–5): Stratification and Rewriting of Datalog Programs with Aggregates

  • Core contribution: formal stratification conditions for count/sum/min/max aggregates; when aggregate strata are well-defined; rewriting unsafe aggregate programs.
  • Implementation relevance: formal basis for dl-aggregate (Phase 9) safety rules. The aggregate-stratum condition extends the PDG check: an aggregate edge from p to q is treated like a negative edge (I4). Provides test cases where aggregation requires a new stratum.

P7 — Shkapsky, Yang, Zaniolo (2015), ICDE: Optimizing Recursive Queries with Monotone Aggregates in DeALS

  • Core contribution: monotone aggregation (min/max) inside recursive rules; convergence conditions; non-monotone count/sum require stratification.
  • Implementation relevance: justifies I7 for aggregate operators. This engine takes the simpler path: all aggregates require a lower-stratum input (no recursive aggregation). This paper confirms that is the safe default.

P8 — Aref et al. (2015), SIGMOD: Design and Implementation of the LogicBlox System

  • Core contribution: production Datalog system: differential delta evaluation, index selection at scale, multi-stratum scheduling, query-driven evaluation.
  • Implementation relevance: architectural lessons for dl-eval + dl-join. Multi-stratum scheduler maps to the stratum-ordered evaluation loop. Index selection heuristics inform Phase 10. The paper's discussion of "stratified aggregation at scale" is a useful Phase 9 reference.

P9 — Seo, Guo, Lam (2018), VLDB: Incremental Evaluation of Datalog Queries

  • Core contribution: incremental non-recursive and recursive EDB update propagation; delta merging without full recompute.
  • Implementation relevance: Phase 13 incremental fact addition. The key insight: adding EDB facts produces a new delta; run semi-naive from that delta rather than restarting. Retract (EDB fact removal) requires re-derivation and is harder; Phase 13 only supports assert (add), not retract.

P10 — Bravenboer & Smaragdakis (2009), OOPSLA: Strictly Declarative Specification of Sophisticated Points-to Analyses

  • Core contribution: Doop framework; complete Java points-to in Datalog; 10K+ rules; empirical semi-naive behavior at scale.
  • Implementation relevance: motivates Phase 2 safety check UX (informative error messages with source spans). Shows that large Datalog programs are debugged via stratification visualisation and incremental rule addition. Doop's rule set is a Phase 14 conformance candidate.

P11 — Jordan, Scholz, Subotic (2019), PLDI: Specialized Parallel Datalog Evaluation

  • Core contribution: Souffle's RAM (Relational Algebra Machine) IR; compilation to C++; parallel semi-naive with locking.
  • Implementation relevance: study the RAM IR design for the dl-join JoinPlan structure. The SEARCH / PROJECT / MERGE RAM operations map directly to dl-join's JoinStep. The SCC-to-stratum mapping in the Souffle compiler maps to dl-program's stratification. Do not copy the C++ code generation.

P12 — Zhao & Ramamohanarao (1998), VLDB: Constraint-Based Query Optimization for Recursive Databases

  • Core contribution: constraint pushing through recursive rules; selectivity estimation for recursive predicates.
  • Implementation relevance: Phase 10 selectivity for recursive IDB predicates. Pushing bound constants through recursive rules reduces the effective search space before evaluation — connects to the magic-sets transform conceptually.

P13 — Gottlob, Grau, Kupke et al. (2012), ACM Computing Surveys: Datalog± : A Family of Logical Knowledge Representation Languages

  • Core contribution: Datalog± extensions (TGDs, EGDs, existential quantification); chase procedure; decidability conditions.
  • Implementation relevance: defines what this engine explicitly does NOT support. Use when emitting UnsupportedFeatureError for existential head variables or equality-generating dependencies.

P14 — Rojas, Pérez, Reutter (2015), ISWC: Recursion in SPARQL

  • Core contribution: transitive closure and fixed-point queries in SPARQL 1.1 property paths; semantic equivalence with Datalog fragments.
  • Implementation relevance: provides formal conformance queries (transitive closure, reachability, same-generation) with known expected results for Phase 14. The SPARQL property-path semantics must agree with Datalog semantics for the shared fragment.

Reference Implementations

R1 — souffle-lang/souffle (C++, GitHub)

  • Files: src/interpreter/Engine.cpp (semi-naive loop); src/interpreter/Relation.h (relation base class + typed subtypes); src/ram/ (RAM IR nodes: Search, Project, Merge, Loop, Sequence); src/ast2ram/TranslationUnit.cpp + AstToRamTranslator.cpp (Datalog AST → RAM lowering); src/analysis/SCCGraph.cpp + Stratifier.cpp (SCC condensation, stratum assignment); src/analysis/IOType.cpp (EDB detection).
  • Architectural lessons: RAM IR cleanly separates logical rule from physical evaluation loop. Per-relation btree/brie/hash index selection driven by access pattern analysis. SCC condensation drives stratum ordering. The SEARCH loop in RAM maps to dl-join's index-nested-loop.
  • Pitfalls: do not copy C++ code-generation path (Souffle generates C++ and compiles it; this engine interprets). Do not copy the btree/brie pointer-heavy data structures; use Rust BTreeMap/HashMap. Avoid conflating the RAM layer with the Datalog AST — they are separate abstractions.

R2 — frankmcsherry/crepe (Rust proc-macro, GitHub)

  • Files: crepe/src/lib.rs (proc-macro expansion); inspect generated Rust code with cargo expand.
  • Architectural lessons: the generated run() function is a clean semi-naive loop expressed as nested Rust iterators. The delta/stable tracking pattern (two HashSets, swap at round end) is directly applicable to DeltaRelation.
  • Pitfalls: proc-macro approach is not applicable to a runtime engine. The macro-expanded code is for study only; do not use crepe as a dependency.

R3 — s-arash/ascent (Rust, GitHub)

  • Files: ascent/src/semi_naive.rs; ascent_macro/src/codegen.rs; ascent/src/relation.rs.
  • Architectural lessons: semi-naive loop as Rust iterators with lifetime-managed borrows. The relation.rs delta/stable split is the most instructive part. Shows how Rust ownership interacts with mutable delta and immutable stable within the same round.
  • Pitfalls: again macro-level; the runtime types are the useful part. Do not use as a dependency.

R4 — cozodb/cozo (Rust, GitHub)

  • Files: cozo-core/src/query/eval.rs (semi-naive fixpoint driver); cozo-core/src/query/stratify.rs (SCC + stratification); cozo-core/src/query/aggr.rs (aggregation: count/sum/min/max/mean); cozo-core/src/data/tuple.rs (tuple representation); cozo-core/src/data/value.rs (value enum).
  • Architectural lessons: production-quality semi-naive in Rust. Aggregate stratification is a separate pass. The Tuple as SmallVec<[DataValue; 8]> (small-vector optimization for short tuples) is worth adopting in Tuple = Vec<Sym> (consider SmallVec for arity ≤ 8). The stratum-ordered evaluation loop structure is clean and directly translatable.
  • Pitfalls: CozoDB's DataValue enum is richer than Sym(u32) (supports integers, floats, strings, JSON); do not copy the value type. Their storage backend (RocksDB / in-memory) is irrelevant.

R5 — vmware-archive/ddlog (Rust + Haskell, GitHub)

  • Files: src/Language/DifferentialDatalog/ (Haskell: EDB.hs stratification; Type.hs type checking; Rule.hs rule normalization); rust/template/ddlog.rs (Rust runtime skeleton).
  • Architectural lessons: DDlog's Haskell frontend has a clean stratification checker with good error messages; the SCC + negative-edge check is the relevant part. The Rust runtime's delta-handling structure is worth studying even though it layers over Differential Dataflow.
  • Pitfalls: DDlog uses Timely Dataflow + Differential Dataflow internally — a far heavier abstraction than semi-naive Datalog. Do not conflate the two models. Focus on the frontend stratification logic, not the Rust runtime.

R6 — timely-dataflow/differential-dataflow (Rust, GitHub)

  • Files: src/operators/iterate.rs (delta iteration operator); src/operators/join.rs (arranged join); src/trace/ (arrangement / index abstraction: TraceReader, BatchReader).
  • Architectural lessons: the arrange/trace abstraction is an instructive model for the Index type in dl-relation — an indexed, immutable snapshot of a relation that can be probed efficiently. The iterate operator's delta-stability contract maps to the DeltaRelation invariant.
  • Pitfalls: Differential Dataflow is a general incremental dataflow framework with a significant runtime overhead. Use it only as a design reference for Index; do not use it as a dependency.

R7 — mthom/scryer-prolog (Rust, GitHub)

  • Files: src/machine/ (WAM implementation); src/forms.rs (Term type); src/atom_table.rs (atom interning with a dense u64 ID).
  • Architectural lessons: symbol interning with a dense integer ID is directly applicable to Sym(u32). The atom table uses a HashMap<&str, u64> for lookups and a Vec<Box<str>> for reverse lookup — the same pattern as dl-core's interner. The Term enum variants map to Term::Const and Term::Var.
  • Pitfalls: WAM = SLD resolution (top-down); do not conflate with bottom-up fixpoint. The WAM machinery (choice points, environments, heap structure) is irrelevant.

R8 — Doop framework (Souffle Datalog, Bravenboer & Smaragdakis group)

  • Files: souffle-fact-generator/ (fact extraction from Java bytecode); logic/main/ (.dl rule files for points-to, call graph, etc.).
  • Architectural lessons: a large rule set (10K+ rules) for a real static analysis. Useful for Phase 14 conformance: translate a subset of Doop rules (e.g., the basic context-insensitive points-to) to this engine's syntax and verify the same points-to facts are derived.
  • Pitfalls: the Java bytecode analysis parts are irrelevant. The Souffle .dl syntax is close to but not identical to this engine's grammar (Souffle uses .decl / .type declarations); adapt accordingly.

Glossary · 41 terms · site-wide glossary

Adornment
Pattern string (b/f per argument position) marking which args are bound vs free in a magic-sets adorned predicate; drives demand-predicate generation.
Aggregation
Grouped reduction (count/sum/min/max) over a completed lower-stratum relation; non-monotone over its stratum boundary, so always stratified.
Atom
{ pred: PredId, args: Vec<Term> } — a predicate applied to an argument list; head of a rule or a positive body literal.
Body
The conjunction of Literals on the right-hand side of a Horn clause (h :- b1, b2, …).
Bottom-up evaluation
Repeatedly apply rules to derive new ground facts until the least fixpoint is reached; opposite of top-down/SLD resolution.
Comparison literal
Literal::Cmp(Term, CmpOp, Term) — a built-in constraint (<, <=, =, !=) applied during join; never derives tuples, only filters.
Datalog
A declarative logic programming language: function-symbol-free Horn clauses over relations; guaranteed termination; basis for deductive databases.
Delta relation
DeltaRelation { stable, delta } — the delta component holds tuples newly derived in the current round; used by semi-naive to restrict rule firing.
Dependency graph
Directed graph over predicate nodes with positive edges (rule uses predicate in positive body) and negative edges (negated/aggregate use); stratification is SCC condensation of this graph.
EDB (Extensional Database)
Predicates defined only by base facts (no rule head); stored as Relation in Program.edb; never derived.
Fact
A ground atom (no variables) asserted directly; element of the EDB; written p(a,b).
Fixpoint
The state where another round of rule application adds zero new tuples; the least fixpoint is the smallest such state — the minimal model.
Ground tuple
A Vec<Sym> with no variables; element of a relation; satisfies arity = predicate arity.
Horn clause
Logical implication with exactly one positive head and a conjunction of literals as body; the syntactic form of every Datalog rule.
IDB (Intensional Database)
