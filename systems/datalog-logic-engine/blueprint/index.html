1. Goal

1.1 What Is Built

A from-scratch Datalog engine in the Souffle / classic deductive-database lineage, implemented in Rust. The engine accepts a program of ground facts (EDB) and Horn-clause rules (IDB), parses and safety-checks it, stratifies the predicate dependency graph for well-defined negation and aggregation, and evaluates the least fixpoint bottom-up using semi-naive (delta) iteration over indexed relations. A relational join engine with cost-based join ordering drives each derivation round. An optional magic-sets transform restricts evaluation to query-relevant tuples. The query interface returns the minimal model as a set of ground substitutions.

1.3 Non-Goals (explicit)

  • No function symbols; no infinite Herbrand universe.
  • No Prolog cut, assert/retract of rules, side effects in rules.
  • No bag semantics; duplicates are always collapsed.
  • No parallel or concurrent fixpoint (single-threaded evaluation loop).
  • No on-disk storage; the minimal model lives in process memory.
  • No probabilistic or fuzzy extensions.
  • No codegen to C++/LLVM (unlike Souffle); evaluation is interpreted.
  • No streaming / continuous query; evaluation is batch per query.

1.4 Intended Deployment Model

Single-process Rust binary or library. Embedded in a larger tool (static analysis, program verification, knowledge-base reasoning) via the dl-core / dl-eval crate API, or driven interactively through dl-repl / dl-cli. No network layer; no multi-tenant isolation. Target: developer workstations and CI pipelines.

1.6 Recommended Language: Rust — Rationale

Datalog evaluation is a join-heavy least-fixpoint loop over relations of interned tuples: the cost is dominated by index lookups, delta maintenance, and set deduplication, and a single non-monotone step or duplicate breaks the minimal-model guarantee. Rust gives interned symbol ids (dense u32), hash/sorted relation indexes with no GC pressure on the fixpoint hot loop, exhaustive enums for the term/literal/rule taxonomy that the compiler checks for exhaustiveness, and zero-copy tuple slices. The parser, relation store, semi-naive evaluator, join engine, stratified negation, aggregation, and magic-sets transform are all Rust.

2.2 Historical and Architectural Significance

  • Datalog is the theoretical foundation of: Datomic (immutable EDB + Datalog queries), Souffle (program analysis), Differential Dataflow (incremental IVM), LogicBlox (enterprise analytics), Cascalog (Hadoop Datalog), and nearly all static-analysis frameworks (points-to analysis, taint analysis, race detection).
  • The bottom-up fixpoint model directly anticipates dataflow / reactive systems: each stratum is a batch dataflow stage; semi-naive mirrors incremental stream processing.
  • Understanding stratification is prerequisite to understanding why SQL window functions require a separate evaluation phase, why recursive CTEs have restrictions, and why aggregate-then-recurse is forbidden without care.
  • Magic sets is the prototypical demand/push-down optimization: every query optimizer that pushes predicates into subqueries applies a weaker version of this idea.

2.3 Engineering Muscles Developed

  • Modeling semantics as types: Literal::Neg vs Literal::Pos forces correct stratum placement at the type level.
  • Property-based testing of semantic equivalence: semi-naive ≡ naive on randomly generated programs is a non-trivial fuzz target.
  • Incremental algorithm design: semi-naive delta bookkeeping is the simplest instance of the broader incremental view-maintenance problem.
  • Index design under set semantics: choosing hash vs sorted multimap per join pattern; measuring collision rates on Sym(u32) keys.
  • Compiler-like pipeline hygiene: parse → check → lower → optimize → evaluate; each stage has explicit invariants and a typed IR.

2.6 Calibration Value

Building this engine makes the following concepts concrete and testable rather than abstract:

  • The difference between declarative semantics and operational evaluation strategy.
  • Why duplicates are a semantic error, not a performance issue, in logic programming.
  • How stratification cleanly partitions non-monotone operations without sacrificing the fixpoint guarantee.
  • That demand-driven optimization (magic sets) is a provably correct program transformation, not a heuristic.

An engineer who has built this engine can read the Souffle, Differential Dataflow, or Datomic source and understand architectural decisions at the level of their tradeoffs, not just their API.

3.2 Subsystem Descriptions

dl-parse (AST + safety check). Receives raw program text. Tokenizes and parses facts (p(a,b).), rules (h :- b1, not b2, X < Y.), and queries (?- p(X).) into an untyped AST using a recursive-descent or PEG grammar. Performs two static checks before emitting: (1) arity consistency — every occurrence of a predicate symbol uses the same argument count; (2) range restriction / safety — every variable in the rule head, in a negated literal, or in a comparison literal appears in at least one positive body literal. Rejects and reports violations with source location. Emits Vec<Rule> + Vec<Tuple> (EDB facts) into dl-program. No I/O after this stage; all string symbols are interned into Sym(u32) via dl-core's interner.

dl-program (EDB/IDB classification, dependency graph, stratification). Receives parsed rules + facts. Classifies each PredId as EDB (appears only in facts, never in a rule head) or IDB (appears in at least one rule head). Builds the predicate dependency graph: a directed graph where p → q exists if some rule has p in the head and q in the body; the edge is labeled negative if q appears under not, and aggregate if q is the input to a count/sum/min/max. Computes SCCs (Tarjan's algorithm); any SCC containing a negative or aggregate back-edge is unstratifiable — the engine rejects the program. Topologically sorts the condensation DAG to produce strata: Vec<Vec<PredId>>. Emits a fully stratified Program struct. This is the only stage that may reject a well-formed (parseable but unsafe) program.

dl-eval (semi-naive fixpoint driver). Receives a stratified Program. Iterates strata in order S0 .. Sk. For each stratum, initializes DeltaRelation entries (stable + delta) for all IDB predicates in the stratum. Runs rounds: per round, fires each rule whose body includes at least one delta literal; derived new tuples are added to next_delta; at round end, stable absorbs delta and delta ← next_delta; terminates when all deltas are empty (fixpoint). Lower-stratum relations are read-only within a stratum; EDB relations are always read-only. Also houses the naive baseline evaluator (fire all rules every round, compare against stable; used in Phase 5 and Phase 14 fuzz).

dl-join (index-nested-loop join engine). Receives a rule body (ordered Vec<Literal>) and the current relation / delta snapshot. Implements variable binding: processes literals left to right; for each positive Literal::Pos(atom), looks up the matching Index for the already-bound argument positions, iterates candidate tuples, extends the Substitution, filters by Literal::Cmp predicates. Delegates negative literals to dl-negation (which checks against the closed lower-stratum relation). Projects the final Substitution onto the head Atom's arguments to produce a new Tuple. Handles repeated variables (implicit equality constraints) and constant arguments (trivial index key). Join order is supplied by dl-eval (Phase 10 adds cost-based ordering).

dl-relation (tuple sets + indexes). Core storage primitive. Relation wraps a HashSet<Tuple> for set-semantic deduplication; provides O(1) average insert / contains; iterates in unspecified order. Index is a multimap keyed on a subset of argument positions (the "bound columns"): given a partial key (the bound values in join order), returns an iterator over matching tuples. Indexes are built lazily on first access and updated incrementally on insert. DeltaRelation pairs a stable: Relation and a delta: Relation; the semi-naive driver promotes delta → stable at round boundaries. No persistence; all state is in process memory.

dl-negation (NAF vs lower strata). Implements negation-as-failure: given Literal::Neg(atom) and a Substitution, grounds the atom using current bindings and checks absence in the predicate's fully-computed (lower-stratum) Relation. Returns true (literal satisfied) iff the ground atom is absent. Relies on stratification invariant I4 and I8 — the relation is never partially-computed when checked. No modification of any relation; read-only access to the lower-stratum model snapshot.

dl-aggregate (grouped count / sum / min / max). Receives an input relation (frozen, lower-stratum) and a grouping specification (which argument positions are group keys, which position is the aggregated value, which aggregate function). Iterates the input relation once, accumulates per-group state (HashMap<Vec<Sym>, AggState>), and emits result tuples. Result tuples are inserted into the target IDB relation before the current stratum's fixpoint begins (they are EDB-like within the stratum). Monotone-per-stratum because the input is frozen. Supports count (no value argument), sum / min / max (single numeric Sym argument encoded as i64).

dl-magic (optional program rewrite). Takes a Program + a Query goal and produces a transformed Program using the magic-sets algorithm. Adorns predicates with bound/free argument patterns (e.g., reachable^{bf}). Generates magic predicates (magic_reachable^{bf}) and seed facts from the query's bound arguments. Rewrites IDB rules to filter derivation through magic predicates (sideways information passing, SIPS). The transformed program is evaluated by dl-eval to yield only query-relevant tuples. Correctness invariant: answer set of the transformed program equals the answer set of the original (I9). Falls back to unmodified program when the query is fully free (no bound positions).

MINIMAL MODEL → dl-query (goal-directed answers). After dl-eval completes all strata (or after magic-sets-restricted evaluation), the minimal model is the union of all IDB relations. dl-query matches the query goal atom against the computed relation for its predicate: bound arguments act as filters (index lookup); free arguments enumerate. Returns Vec<Substitution> — the set of ground assignments to the goal's free variables that make the goal true.

dl-repl / dl-cli. dl-repl: a readline-driven REPL that accepts :load <file>, :assert fact., :query ?- goal., :explain pred(args)., :stratify. Incremental fact assertion triggers semi-naive re-derivation from the new delta rather than full recompute. dl-cli: a clap-based CLI with subcommands run (load + evaluate a program file), query (run a goal against the computed model), explain (print a derivation tree for a tuple), stratify (print the stratum assignment of each predicate).

B2 — Ullman: Principles of Database and Knowledge-Base Systems, Vol. 1–2 (1988/1989)

  • Chapters: Vol. 1 Ch. 3 (relational algebra operators), Vol. 2 Ch. 12 (naive evaluation pseudocode), Ch. 13 (semi-naive pseudocode, delta rule), Ch. 14 (recursion in SQL contrast), Ch. 15 (magic sets, supplementary magic, counting method).
  • Concepts to extract:
    • Naive fixpoint loop pseudocode (Algorithm 12.1): the exact loop implemented in Phase 5.

B3 — Ceri, Gottlob, Tanca: Logic Programming and Databases (Springer, 1990)

  • Chapters: Ch. 3 (EDB/IDB classification; predicate dependency graph construction), Ch. 5 (evaluation strategies: push vs pull vs mixed), Ch. 6 (range restriction definition with counterexamples), Ch. 7 (stratified negation formalization; uniqueness of stratified model).
  • Concepts to extract:
    • Formal EDB/IDB split: a predicate is EDB if it appears in the head of no rule; IDB otherwise.
    • Dependency graph construction: for each rule h :- b1, ..., bn, add edge (h, bi) labeled Pos; for not bi, add edge labeled Neg.
    • Non-stratifiable example programs: mutual negation cycles; use for Phase 2 error message test cases.
    • Range-restriction counterexamples: p(X) :- q(Y). (X unbound), p(X) :- q(X), not r(Y). (Y in negation unbound).
  • Why it matters: Ch. 3 maps directly to dl-program (Phase 4). Ch. 7 provides the stratification uniqueness theorem used to justify that dl-program's stratum assignment is canonical.

B4 — Ramakrishnan & Gehrke: Database Management Systems (3rd ed., 2003)

  • Chapters: Ch. 12 (query optimization: cost estimation, histogram-based selectivity, join ordering), Ch. 13 (join algorithms: index-nested-loop, sort-merge, hash join), Ch. 14 (catalog statistics).
  • Concepts to extract:
    • Index-nested-loop join (Section 13.2): for each outer tuple, probe the inner relation's index for matching tuples. This is exactly dl-join's algorithm.
    • Selectivity estimation (Section 12.3): for an equality predicate on attribute A, selectivity = 1 / |distinct values of A|. For multi-attribute: product of per-attribute selectivities (independence assumption).
    • Join ordering: reorder as a left-deep tree; enumerate using dynamic programming or greedy; cost = sum of intermediate sizes.
    • B-tree vs hash index tradeoff: hash index for equality lookups (used in dl-relation Index); B-tree for range queries (not needed in standard Datalog — CmpOp is evaluated inline).
  • Why it matters: Sections 13.2 and 12.3 are the direct specification for dl-join Phase 6 and cost-based Phase 10.

6. Design Principles

P1. Declarative Least-Fixpoint Semantics

Statement: a program denotes its unique minimal model — the least fixpoint of the immediate-consequence operator T_P. Evaluation computes that model and nothing more, independent of rule order.

Formal grounding:

  • T_P(I) = I ∪ { head(θ) | Rule(head, body) ∈ P, θ ground substitution, body(θ) ⊆ I }
  • T_P is monotone: I ⊆ J → T_P(I) ⊆ T_P(J) (adding facts never removes derivations).
  • Knaster-Tarski: the least fixpoint lfp(T_P) = ⋃_{n≥0} T_P^n(∅) exists and is unique.
  • Termination: for function-symbol-free Datalog with range restriction, the Herbrand base is finite, so T_P^n(∅) stabilises in at most |Herbrand base| rounds.

Tradeoffs:

  • Rule-order independence prevents exploiting user-provided priority hints; any "priority" extension requires a proof that it does not alter the result set.
  • Least-fixpoint semantics is weaker than stable-model semantics (Answer Set Programming); programs requiring multiple stable models are out of scope.

Operational implications:

  • dl-eval applies all rules at each round; no rule is skipped based on index availability or current model size.
  • Semi-naive (P5) restricts how derivations fire, not which rules are applied.
  • Phase 14 fuzz: run each program with 5 random rule orderings; assert result set equality.

Violation effect: if any rule is silently dropped (e.g., an incorrectly guarded delta prevents a base-case EDB rule from firing), the derived model is incomplete — query answers are missing with no error indicator.

P2. Set Semantics

Statement: every relation is a set of ground tuples. A derived tuple is present once or not at all. Derivation is idempotent.

Representation:

  • Relation.tuples: HashSet<Tuple> — insert is a no-op on duplicates.
  • DeltaRelation.delta is built with new_tuples.difference(&stable) — only genuinely new tuples enter delta.

Consequences:

  • Aggregation (count/sum/min/max) operates on sets, not bags. A tuple derivable via multiple rules is counted once. This matches Datalog semantics, not SQL bag semantics.
  • Join results collected in any intermediate structure must be deduplicated before insertion into a relation; in practice, inserting into a HashSet achieves this automatically.

Tradeoffs:

  • SQL-style bag semantics would ease some aggregate implementations but violates Knaster-Tarski convergence (duplicates re-enter delta indefinitely) and produces wrong counts.
  • Choosing HashSet<Tuple> (O(1) insert) over BTreeSet<Tuple> (O(log n)) favours insertion speed over ordered iteration; ordered iteration is not required by the semantics.

Operational implications:

  • No separate dedup pass is needed or permitted after derivation.
  • The DeltaRelation type must enforce delta ∩ stable = ∅; enforcement: delta.insert(t) checks !stable.contains(&t) before insertion.

Violation effect: if intermediate join results are stored in a Vec<Tuple> and the dedup step is skipped, duplicates may persist in delta, causing infinite re-derivation loops and wrong aggregate results.

P3. Safety Guarantees Termination

Statement: pure Datalog has no function symbols. Every rule must be range-restricted. Unsafe rules are rejected at load time.

Safety check algorithm:

pos_vars(rule) = ⋃ { vars(lit) | lit ∈ rule.body, lit = Pos(_) }
require: vars(rule.head) ⊆ pos_vars(rule)
for each Neg(atom) in rule.body: vars(atom) ⊆ pos_vars(rule)
for each Cmp(t1, op, t2) in rule.body: vars(t1) ∪ vars(t2) ⊆ pos_vars(rule)
on violation: emit SafetyError { rule_span, offending: Vec<VarName> }

No function symbols: the grammar for Term is Const(Sym) | Var(u32) — f(x) is a parse error. This enforces a finite Herbrand base.

Unsafe rule examples (all rejected):

Rule Offending variable Reason
p(X) :- q(Y). X X appears in head but not in positive body
p(X) :- q(X), not r(Y). Y Y appears in negation but not in positive body
p(X) :- q(X), X < Z. Z Z appears in comparison but not in positive body

Tradeoffs: prohibiting function symbols excludes Prolog-style list cons; this is the intentional scope boundary. The engine targets deductive databases, not logic programming.

Violation effect: a rule like p(X) :- q(Y). with X unbound lets X range over all possible constants; T_P^n(∅) grows without bound and the fixpoint is never reached.

P4. Stratification Makes Negation Well-Defined

Statement: negation and aggregation may only reference relations fully computed in a strictly lower stratum. Negation-as-failure is applied to a closed, final relation.

Dependency graph construction:

  • Nodes: all PredId values in the program.
  • Edges: for each Rule { head, body }:
    • Pos body literal → edge (head.pred, lit.pred, Pos)
    • Neg body literal → edge (head.pred, lit.pred, Neg)
    • Aggregate → edge (head.pred, aggregated.pred, Aggr)

Stratification algorithm:

  1. Compute SCCs (Tarjan's algorithm, O(V+E)).
  2. For each SCC: if any internal edge is Neg or Aggr, emit StratificationError { scc_preds, offending_edge } and reject.
  3. Stratum assignment: topological sort of the condensation DAG; assign stratum indices; a Neg/Aggr edge crossing strata requires stratum(head_pred) > stratum(body_pred).

Non-stratifiable programs (test cases for Phase 4):

Program Issue
p :- not p. Self-negation cycle
p :- not q. q :- not p. Mutual-negation cycle
p(X) :- count{ X : p(X) } > 0. Self-aggregation cycle

Tradeoffs: stratified negation is less expressive than well-founded or stable-model semantics; the scope boundary is explicit and documented via P13.

Violation effect: evaluating negation on p before p's fixpoint is reached yields unsound results — absent-now-but-derivable-later tuples would incorrectly satisfy the negated literal, producing spurious conclusions.

P5. Semi-Naive Over Naive

Statement: each round, a rule fires only using at least one delta (new-this-round) literal. Tuples derivable solely from already-stable inputs are not re-derived.

Delta firing rule (for rule with body literals L1, L2, ..., Lk):

  • Generate k delta variants: variant i replaces Li with delta_Li, keeps all other Lj as stable_Lj ∪ delta_Lj.
  • Fire all k variants each round; union the results into new_delta.
  • This is exactly Balbin & Ramamohanarao's generalised semi-naive (P3 in the papers list).

Round lifecycle:

for each stratum s in order:
  while true:
    new_delta_s = ∅
    for each Rule r with head pred in stratum s:
      for each delta-variant of r:
        derive head tuples using ≥1 delta literal
        new_delta_s ← new_delta_s ∪ { t | t ∉ stable_s }
    stable_s ← stable_s ∪ new_delta_s
    delta_s ← new_delta_s
    if new_delta_s = ∅: break

Correctness obligation: semi-naive yields the same model as naive (I5). Phase 5 implements naive; Phase 7 implements semi-naive; Phase 14 diff-tests them.

Tradeoffs: delta bookkeeping adds complexity. A bug in delta-difference (new_tuples.difference(&stable) inadvertently including stable tuples) inflates future work without affecting correctness; a bug in delta-generation (missing a delta variant) causes missed derivations and an incomplete model.

Violation effect: if delta contains tuples already in stable, those tuples re-trigger derivation in the next round, degrading performance to naive or worse. If a delta variant is missing, some rule firings are skipped, producing an incomplete model.

P6. Joins Are the Engine

Statement: a rule body is a relational join. Performance is determined by join order and index selection — explicit, cost-guided decisions recorded in a JoinPlan.

Join algorithm (index-nested-loop):

for each JoinStep { literal, index_key, bound_vars, free_vars }:
  probe Index(literal.pred, index_key) with current Substitution values for bound_vars
  for each matching Tuple: extend Substitution with free_vars bindings
  apply CmpOp filters inline
project final Substitution onto head variables to produce head Tuple

Join ordering heuristic:

  • For each body literal L at step k, estimate selectivity as |relation(L)| / (product of selectivity factors for each bound variable).
  • Sort literals ascending by estimated output size (most selective = smallest output = execute first).
  • Penalty for cartesian product (a literal with zero bound variables): placed last.
  • Dynamic programming over subsets is O(2^k); for k ≤ 6 body literals, use DP; for k > 6, use greedy.

Index construction:

  • Index key = set of argument positions that will be bound at join time.
  • Structure: HashMap<Vec<Sym>, Vec<Tuple>> (hash multimap).
  • Build on demand; cache per (PredId, Vec<usize>) key pattern.
  • Rebuild when stable grows by > 50% since last build (amortised cost).

Tradeoffs:

  • Building an index has upfront cost O(|relation|); for |relation| < 64, linear scan may be cheaper. Phase 10 applies a threshold.
  • Left-deep join tree (sequential steps) vs bushy tree (parallel subjoins): left-deep is simpler and correct; bushy is an optimization deferred to a future phase.

Violation effect: a wrong join order (free × free cartesian product first) degrades to O(|R|·|S|) per step. On 10K-tuple EDB, transitive-closure evaluation becomes infeasible (10^8 pairs per round).

P7. Demand-Driven When It Pays

Statement: the magic-sets transform restricts bottom-up evaluation to query-relevant tuples while provably preserving the answer set (I9). It is an optimization layered on the same semantics.

Adornment procedure:

  1. For goal ?- p(a, X), adornment is p^{bf} (b = bound, f = free).
  2. Generate seed fact: magic_p_bf(a).
  3. For each rule p(X, Y) :- q(X, Z), r(Z, Y). with p^{bf}: generate magic rule magic_q_bf(X) :- magic_p_bf(X). (propagate bound X sideways); add magic_p_bf(X) to body of the original rule.
  4. Repeat for all reachable adorned predicates (fixed point over adornments).

Activation condition:

  • Apply magic-sets if: query goal has ≥1 bound argument AND goal predicate is IDB AND the program contains recursive rules over that predicate.
  • Skip and run full evaluation if: all arguments are free, or the goal predicate is EDB, or the program is non-recursive.

Correctness: transformed program P' satisfies: { θ | goal(θ) ∈ lfp(T_{P'}) } = { θ | goal(θ) ∈ lfp(T_P) ∧ goal(θ) matches query }. Proof: Ullman Vol. 2 Theorem 15.4.

Tradeoffs:

  • Transformed program has more predicates and rules; rewrite cost amortises over large EDB and recursive programs.
  • For small EDB (< 1000 tuples) or non-recursive goals, skip the transform.
  • Magic-sets is strictly an optimization; query answers must be identical with or without it (verified by Phase 14 fuzz).

Violation effect: incorrect adornment (treating a free variable as bound) over-restricts derivation → missing answers (violates I9, I10). Treating bound as free → full evaluation instead of magic-sets (correct but slow).

P8. Monotonicity Within a Stratum

Statement: every operator inside a stratum is monotone. Non-monotone steps are quarantined across strata.

Monotone operators (safe within a stratum): positive rule derivation (join → head tuple), projection onto head variables, union into stable, delta difference.

Non-monotone operators (forbidden within a stratum): negation-as-failure (dl-negation), grouped aggregation (count/sum can decrease if the input set shrinks — but input is frozen in a lower stratum, so it cannot shrink from within the current stratum).

Structural enforcement: I4 (stratification check) ensures no cycle through Neg/Aggr edges. If I4 holds, no rule in stratum s references a predicate in stratum s via a Neg or Aggr edge — so all within-stratum operators are monotone.

Within-stratum fixpoint proof: let f_s be the T_P restricted to stratum s predicates, treating lower-stratum relations as fixed constants. f_s is monotone (all operators are monotone). Knaster-Tarski: lfp(f_s) exists. Since the within-stratum Herbrand base is finite, f_s^n(∅) stabilises. QED.

Tradeoffs: strict stratification rejects programs where well-founded semantics would define a model. This is an explicit scope decision (the engine is stratified Datalog, not Answer Set Programming).

Violation effect: without I4 enforcement, p(X) :- q(X), not p(X). creates an oscillating fixpoint — derivation and removal cycle forever, the engine loops, the round counter hits the circuit-breaker (I6 guard).

P9. Determinism

Statement: the computed model is a deterministic function of the program and EDB. Index iteration order and join order affect speed, never the result set.

Hash non-determinism: Rust HashSet uses random hashing (randomised SipHash-1-3 seed per process). Iteration order is non-deterministic across runs. This is acceptable — the result of inserting all join outputs into a HashSet<Tuple> is the same set regardless of insertion order (P2 guarantees set equality).

Join order determinism: the JoinPlan cost function is a deterministic function of |relation| and arity (integers). Given the same EDB, the same plan is produced every run. Different EDB → different plan → same model (P1 guarantees model independence of evaluation order).

Rule application order: within a round, the order in which rules fire does not affect stable at fixpoint. It may affect which tuples appear in delta mid-round, but the fixpoint is the same set.

Operational implications:

  • Phase 14 fuzz: run each program with 5 random rule permutations; assert result-set equality.
  • Phase 14 fuzz: run each program with and without magic-sets; assert answer set equality.
  • Do not rely on iteration order for correctness in any part of dl-join, dl-eval, or dl-query.

Violation effect: a non-deterministic answer set makes the engine untestable (flaky tests) and untrustworthy for production use in static analysis.

P10. Explainability

Statement: every derived tuple has a derivation. The engine can produce a proof tree (provenance) for any IDB tuple on demand.

Provenance data model:

enum Provenance { Edb, Derived { rule_id: RuleId, body: Vec<(PredId, Tuple)> } }
ProvenanceStore: HashMap<(PredId, Tuple), Provenance>

Proof tree construction: recursive traversal — base case Provenance::Edb (EDB fact); recursive case expands each (PredId, Tuple) in body. The tree is finite because the model is a finite set and every IDB tuple was derived from a finite body (no function symbols).

Memory model: provenance recording is opt-in (--explain flag or set provenance on in the REPL). When disabled, ProvenanceStore is not allocated. When enabled, memory usage grows proportional to the number of derived IDB tuples.

Lazy provenance alternative: instead of recording during evaluation, re-derive the proof tree on demand by simulating the evaluation for the target tuple only. Slower (O(model size) per explain call) but uses O(1) extra memory. Phase 13 offers both modes.

Operational implications:

  • dl-repl: explain p(a, b) → recursive tree render.
  • dl-cli: explain --goal 'p(a,b)' → indented text or JSON tree to stdout.
  • Provenance for recursive derivations may be deep (e.g., transitive closure of depth k → tree of depth k); render with depth limit and truncation indicator.

Violation effect: without provenance, incorrect query answers cannot be traced to the responsible rule or EDB fact. Users lose the ability to debug rule logic errors, making the engine unsuitable for production use in analysis pipelines.

P11. Set Semantics / Duplicate-Free Derivation

Statement: the evaluator is the guarantor of set semantics at the algorithmic level, not just the data-structure level (P2): every derivation step — naive round, semi-naive delta-variant firing, aggregate grouping, magic-sets seed — must reach the relation store through a path that rejects an already-present tuple before it is counted as "new work." No component of dl-eval, dl-join, or dl-aggregate may materialize a duplicate tuple and treat it as a fresh derivation.

Where duplicates would otherwise enter:

  • Naive round: T_P^{n+1}(I) = I ∪ {...} — the ∪ is set union; a bare Vec-collect-then-append of join outputs (Phase 5, Phase 6) would silently accumulate duplicates across rounds if not folded through Relation.tuples: HashSet<Tuple> (P2) before the next round starts.
  • Semi-naive delta variants (Phase 7): the same head tuple can be produced by multiple delta-variants of the same rule in one round (e.g., a symmetric join); new_delta must be deduplicated by construction (HashSet insert), not by a downstream pass.
  • Magic-sets rewrite (Phase 11): a magic seed predicate re-derived by two different adorned rules must collapse to one magic fact; the demand relation is a Relation, subject to the same invariant.

Why duplicates are not merely wasteful: Knaster-Tarski fixpoint counting (P1) assumes T_P^n(∅) is monotonically non-decreasing in set size; if a "new" delta batch recounts an existing tuple as new, the semi-naive round-termination test (new_delta = ∅) never observes true emptiness in implementations that track counts instead of set membership, and the fixpoint loop either never terminates or terminates on the wrong round. Aggregation (Phase 9) is even more directly affected: count/sum over a bag instead of a set silently double-counts a tuple derived by two different rules, which is a correctness bug, not a performance one.

Enforcement: Relation::insert(t) -> bool returns whether t was newly inserted (the HashSet::insert contract); every derivation call site (naive fire, semi-naive delta-variant fire, magic seed insertion, aggregate group emission) must use the boolean return value to decide whether to propagate t into delta/new_delta/telemetry — never insert into an intermediate Vec and defer dedup to a later, optional pass.

Tradeoffs: deduplicating at every insertion point (rather than once at the end of a round) costs a hash lookup per candidate tuple; batching candidates into a Vec first and deduping once per round is cheaper per-tuple but reintroduces the risk of counting a duplicate as "new" if the round-termination check runs before the dedup pass. The engine accepts the per-insertion hash cost as the price of an unconditionally correct termination check.

Operational implications: Phase 14's fuzz harness includes a dedicated duplicate-injection test: replay a program with a rule whose body is satisfiable by two disjoint substitutions producing the same head tuple; assert stable and delta both contain exactly one copy and that the round count is unaffected by the duplicate path.

Violation effect: if any join-output collection point (Phase 6 index-nested-loop, Phase 9 group finalization, Phase 11 magic-rule firing) buffers into a Vec<Tuple> and inserts into stable/delta without an insert-returns-bool check, the fixpoint either loops forever (round-count-based termination on a growing-but-not-actually-new delta) or produces inflated aggregate results (P8 violation) — both are silent-until-fuzzed failures, which is why the Phase 14 duplicate-injection fixture is mandatory, not optional.

P12. Stratified Negation Discipline

Statement: negation-as-failure and grouped aggregation are non-monotone operators (P8); the engine's only guarantee of a well-defined, deterministic model is that every not p(t) or aggregate-over-p literal reads p from a stratum strictly below the stratum computing the current rule's head. A negation or aggregate edge that lies inside a stratum (a cycle through Neg/Aggr in the predicate dependency graph, I4) is not a degraded case to evaluate cautiously — it is a program the engine must refuse to load.

Why "inside a stratum" breaks the fixpoint: stratified evaluation processes strata in a fixed order, computing each stratum's fixpoint to completion before the next stratum reads it (P4, I7). If a Neg/Aggr edge closes a cycle within a single stratum, there is no order in which to compute that stratum: evaluating not p(t) requires p's relation to already be final, but p's relation cannot be final until the same stratum's fixpoint — which itself depends on the negated read — has converged. Forcing an evaluation order onto such a program (e.g., "just run negation against whatever p looks like this round") makes the round-to-round result depend on iteration order: two runs of the identical program over identical EDB can converge to different models, or oscillate (p :- not p. derives and un-derives p every round) and never converge at all.

Detection is structural, not a runtime fallback: dl-program's stratifier (Phase 4) computes SCCs over the predicate dependency graph (Tarjan, O(V+E)) and rejects any SCC containing an internal Neg/Aggr edge with StratificationError before dl-eval ever runs. There is no runtime "detect the cycle and pick a semantics" path — well-founded or stable-model semantics for such programs are explicitly out of scope (P4's tradeoffs; see paper P4, Van Gelder/Ross/Schlipf, in the papers list, for the semantics this engine deliberately does not implement).

Tradeoffs: rejecting all non-stratifiable programs is strictly less expressive than well-founded semantics (which assigns a three-valued model to some cyclic-negation programs); the engine accepts this scope boundary in exchange for a decidable, single evaluation order, and a model that is a deterministic function of program + EDB (P9) with no three-valued "undefined" truth value to propagate through downstream joins.

Operational implications: every aggregate edge is checked by the same SCC-cycle test as negation (Phase 9 stratum placement re-uses Phase 4's depgraph.rs classification, tagging aggregate dependencies as EdgeKind::Aggr); a program that stratifies cleanly for negation but has a same-stratum aggregate cycle must still be rejected — the two operators share one discipline, not two.

Violation effect: if the stratifier's SCC scan only inspects Neg edges and skips Aggr edges (or vice versa), a self-aggregating program (p(X) :- count{ Y : p(Y) } > 0.) is accepted, and the evaluator either infinite-loops (round count never stabilizes because the aggregate result depends on its own not-yet-final input) or returns a result that depends on which round the aggregate happened to sample — a non-deterministic model that breaks I1, I7, and I9 simultaneously, and is only caught by the Phase 14 differential fuzz harness rather than at load time where it belongs.

8.3 Grammar (EBNF)

program    ::= statement* EOF
statement  ::= fact | rule | query | directive
fact       ::= pred_sym '(' arg_list ')' '.'
rule       ::= head ':-' body '.'
query      ::= '?-' atom '.'
directive  ::= '.decl' pred_sym '(' type_list ')' '.'
             | '.input' pred_sym '.'
             | '.output' pred_sym '.'

head       ::= atom
body       ::= literal (',' literal)*
literal    ::= atom | neglit | cmpexpr
neglit     ::= 'not' atom
cmpexpr    ::= term cmpop term
cmpop      ::= '<' | '<=' | '>' | '>=' | '=' | '!='
atom       ::= pred_sym '(' arg_list ')'
arg_list   ::= term (',' term)*
term       ::= CONST | VAR
CONST      ::= lowercase ident | quoted string | integer literal
VAR        ::= uppercase ident | '_' ident
pred_sym   ::= lowercase ident
  • _ (wildcard) generates a unique anonymous Var per occurrence; never equality-constrained.
  • Integer literals interned as Sym; comparisons require both sides to resolve at ground time.
  • .decl optional; arity inferred from first occurrence when absent.

8.4 Predicate Classification

Classification algorithm (dl-program):
  appearing_in_head = { r.head.pred | r in rules }
  EDB = { p | p not in appearing_in_head }
  IDB = appearing_in_head

  EDB predicates: loaded from .input / assert; immutable during evaluation.
  IDB predicates: derived by rules; cleared before re-evaluation.
  Mixed (p in both EDB facts and rule heads): treated as IDB; seed with EDB facts.

8.5 Dependency Graph and Stratification

Nodes: one per predicate in program.
Edges:
  for each rule r:
    for each Pos(a) in r.body: add Pos-edge  a.pred -> r.head.pred
    for each Neg(a) in r.body: add Neg-edge  a.pred -> r.head.pred
    for each aggregate over p: add Agg-edge  p -> r.head.pred

Stratification (Ullman layer algorithm):
  stratum[p] = 0  for all p
  repeat until stable:
    for each Pos-edge  q -> p:  stratum[p] = max(stratum[p], stratum[q])
    for each Neg-edge  q -> p:  stratum[p] = max(stratum[p], stratum[q] + 1)
    for each Agg-edge  q -> p:  stratum[p] = max(stratum[p], stratum[q] + 1)
  if any cycle contains a Neg or Agg edge: REJECT (not stratifiable)

Strata = [ { p | stratum[p] == k } for k in 0..max ]

8.6 Relation Storage Layout

Relation {
  arity:   usize
  tuples:  HashSet<Tuple>                          // set semantics, O(1) membership
  indexes: HashMap<Vec<usize>, HashMap<Vec<Sym>, Vec<Tuple>>>
           //              ^-- bound positions    ^-- matching tuples
}

Index key encoding:
  bound_positions = [0, 2]  for a 3-arity relation: key = [tuple[0], tuple[2]]
  value           = all tuples where those positions match the key

Delta bookkeeping (DeltaRelation):
  stable:      all tuples from previous rounds  (never shrinks)
  delta:       tuples added in the last round   (current Δ)
  next_delta:  accumulates new tuples this round (becomes delta next round)

Merge protocol (end of semi-naive round):
  for each new tuple t derived this round:
    if t not in stable and t not in delta:
      insert t into next_delta
  stable ∪= delta
  delta = next_delta
  next_delta = ∅
  converged = (delta is empty)

8.7 Join Execution Model

Rule body join sequence (index-nested-loop):
  input:  body = [L0, L1, ..., Lk], empty Substitution σ
  for i in 0..=k:
    case Li = Pos(a):
      bound_positions = { j | a.args[j] is Const or σ[a.args[j]] is known }
      lookup key = [ resolve(a.args[j], σ) for j in bound_positions ]
      candidate_tuples = index_lookup(relation[a.pred], bound_positions, key)
        (or full scan if no index covers bound_positions)
      for each candidate t:
        σ' = extend(σ, a.args, t)   // unify free vars; reject if conflict
        recurse with σ', i+1
    case Li = Neg(a):
      assert all vars in a.args are bound in σ  (I3 / safety)
      ground_tuple = [ resolve(a.args[j], σ) for j in 0..arity ]
      if ground_tuple in stable[a.pred]: prune this branch (NAF)
      else: continue with σ, i+1
    case Li = Cmp(t1, op, t2):
      assert both t1, t2 bound in σ
      evaluate; prune if false
  at i == k+1 (all literals satisfied):
    head_tuple = [ resolve(h.args[j], σ) ]
    emit head_tuple

8.8 Semi-Naive Evaluation Protocol

Outer loop (per stratum S):
  seed: for all EDB predicates p in S, delta[p] = stable[p] (initial round)
  round = 0
  repeat:
    for each rule r whose head.pred in S:
      // At least one Pos body literal must use a delta relation.
      // Generate one "delta variant" per Pos literal position.
      for i in 0..r.body.len() where body[i] is Pos and body[i].pred in S:
        evaluate r using delta[body[i].pred] for position i
            and stable[body[j].pred] for all j != i
        collect new head tuples -> candidate_set
      for t in candidate_set:
        if t not in stable[r.head.pred]:
          insert t into next_delta[r.head.pred]
    merge: stable ∪= delta; delta = next_delta; next_delta = ∅
    round++
    if all delta[p] empty for p in S: break   // fixpoint reached
  • Correctness: every tuple in the minimal model is derived; no tuple outside is ever added.
  • Termination: each round adds ≥1 new tuple to some stable relation, and the domain is finite (I6).

8.9 Negation-as-Failure (NAF) Semantics

Condition Result
not p(t) and p is EDB, t absent literal succeeds
not p(t) and p is EDB, t present literal fails; prune branch
not p(t) and p is IDB in lower stratum p fully computed; same as EDB case
not p(t) and p in same stratum REJECTED at stratification (I4)
not p(t) with unbound variable in t REJECTED at safety check (I3)

Closed-world assumption: absence from a fully-computed relation == logical negation.

8.10 Aggregation Model

Aggregate rule form:
  h(X, agg<Y>) :- p(X, Y), ...   where agg ∈ {count, sum, min, max}

Evaluation:
  1. Evaluate body (without aggregate literal) against lower-stratum stable relations.
  2. Group resulting tuples by the non-aggregate head variables (X).
  3. Apply aggregate function to the Y-column within each group.
  4. Emit one head tuple per group: (X, agg_result).

Stratum placement:
  aggregate rule's head predicate stratum > stratum of all body predicates (Agg-edge).
  This ensures the input relation is fully computed before aggregation.

count: integer count of tuples in group (always defined, min 0).
sum:   integer sum (Sym must resolve to integer; type error otherwise).
min / max: lexicographic minimum / maximum of Sym values in group.

8.11 Magic-Sets Transform

Adornment notation: p^{bf} means predicate p with first arg bound, second free.
  b = bound (value known from caller context)
  f = free  (value to be computed)

Transform steps (given query ?- q(c1, c2, ...) with pattern bf...):
  1. Create magic predicate magic_p^{adornment} for each adorned predicate.
  2. Rewrite each rule for p^A:
     a. Add magic_p^A(bound_args) as first body literal.
     b. For each body literal r^A', emit magic_r^A'(bound_args_of_r) :-
            magic_p^A(bound_args_of_p), [earlier body lits].
  3. Seed: magic_q^{initial_adornment}(c1, c2, ...) as a fact.
  4. Evaluate the transformed program; magic predicates propagate demand downward.

Preservation: transformed program answer set for q = original answer set for q (I9).
Fallback: if adornment produces no bound arguments for any predicate (fully free query),
  skip transform and run full bottom-up evaluation.

8.12 Query Evaluation Sequence

Query ?- p(X, a, Y):
  adornment: p^{fbf}  (arg0=free, arg1=bound=a, arg2=free)
  Step 1: optionally apply magic-sets transform for this adornment.
  Step 2: run semi-naive fixpoint for relevant strata.
  Step 3: in relation[p], lookup tuples where args[1] == sym("a").
           For each matching tuple t:
             emit Substitution { X -> t[0], Y -> t[2] }
  Returns: Vec<Substitution>

Ground query ?- p(a, b):
  adornment: p^{bb}
  Step 3: membership test in relation[p]; returns [{} ] if member, [] if absent.

8.13 Provenance / Derivation Model

ProvenanceNode:
  fact: (pred, Tuple, source=EDB|rule_index)
  rule_firing: (rule_index, head_tuple, [body_tuple provenance_node, ...])

Derivation tree for tuple t in relation p:
  if t in EDB[p]: leaf node (asserted fact)
  else: find all rule firings that derived t; return forest (multiple derivations possible)

Storage (optional, enabled by --explain flag):
  proof_forest: HashMap<(PredId, Tuple), Vec<RuleFiring>>
  RuleFiring: { rule_idx: usize, body_witnesses: Vec<(PredId, Tuple)> }

dl-cli explain p(a,b):
  look up (p, [sym(a), sym(b)]) in proof_forest
  print derivation tree (BFS, depth-limited to avoid infinite display on mutual recursion)

8.14 Worked Example — Transitive Closure

Program:

.decl edge(x: symbol, y: symbol)
.decl reach(x: symbol, y: symbol)
edge(a, b).  edge(b, c).  edge(c, d).
reach(X, Y) :- edge(X, Y).
reach(X, Z) :- reach(X, Y), edge(Y, Z).
?- reach(a, Z).

EDB: edge = { (a,b), (b,c), (c,d) } IDB: reach Dependency graph: edge -Pos-> reach, reach -Pos-> reach (self-loop, positive only — stratifiable, stratum 0 for edge, stratum 0 for reach since no neg/agg edge).

Semi-naive rounds:

Round delta(reach) stable(reach) after merge
seed { (a,b),(b,c),(c,d) } { (a,b),(b,c),(c,d) }
1 { (a,c),(b,d) } { (a,b),(b,c),(c,d),(a,c),(b,d) }
2 { (a,d) } { all above + (a,d) }
3 ∅ (converged)

Query result: reach(a, Z) → { Z=b, Z=c, Z=d }.

8.15 Malformed / Failure-Path Examples

Unsafe rule (rejected at load):

bad(X) :- not good(X).
// X appears only in negated literal → violates I3 (range restriction).
// dl-parse emits: SafetyError { rule: 0, unbound_vars: [X] }

Non-stratifiable program (rejected at stratification):

a(X) :- b(X), not a(X).
// a -Neg-> a: negative self-dependency → SCC contains Neg edge.
// dl-program emits: StratificationError { cycle: [a], neg_edge: (a,a) }

Arity mismatch (rejected at parse/type-check):

.decl p(x: symbol, y: symbol)
p(a, b, c).    // 3-tuple for arity-2 predicate
// ArityError { pred: p, declared: 2, actual: 3 }

Aggregate over recursive predicate in same stratum:

count_reach(X, count<Y>) :- reach(X, Y).
reach(X, Z) :- reach(X, Y), edge(Y, Z).
// count_reach needs reach fully computed → Agg-edge: reach -> count_reach.
// reach is recursive (self Pos-edge, stratum 0).
// count_reach stratum = max(stratum[reach] + 1) = 1. Valid stratification.
// (This is the correct case — shown to contrast with invalid cases above.)

Empty-body IDB rule (rejected):

p(a).   // valid (EDB fact)
q(X) :- .  // body empty, X in head unbound → SafetyError + EmptyBodyError

8.16 Edge Cases

Case Handling
Wildcard _ repeated in same atom each occurrence generates distinct anonymous Var; never unified
Self-join: p(X,Y) :- p(X,Z), p(Z,Y) both literals use same relation; delta variant generates two delta-rule variants
Empty EDB for a rule's input predicate join immediately yields empty; no head tuples derived; no error
Zero-arity predicate (proposition) Tuple = []; Relation contains at most one element []; valid
Predicate used only in query, never in rule head or facts arity inferred from query; treated as EDB; empty relation
Integer overflow in sum aggregate defined behavior: wraps at i64 boundary; emits warning
Duplicate facts in input deduped on insertion into HashSet<Tuple>; silent
Circular positive-only recursion (ok) stratification accepts; semi-naive terminates (finite domain)
Very large programs (1M+ rules) stratification: O(E) where E = rule-body-literal count; index build: lazy
Query for predicate not in program returns empty Vec<Substitution>; no error

1.7 Performance Concerns

  • Interner intern() called on every parsed token; use HashMap::entry to avoid double-hash; if symbol count is large (>1M) consider string_interner crate or arena for the Vec<String> id-to-name side.

1.8 Edge Cases

  • Empty symbol string "" — valid; must intern without panic. PredId or Sym id = 0 must be a valid, usable ID (not a sentinel).
  • Rule with empty body — valid (fact as rule); must not panic. Literal::Cmp with two Term::Const is evaluable statically; not rejected at type level.
  • Tuple of arity 0 (nullary predicate) — valid for boolean flags; Vec<Sym> length = 0.
  • Very long argument lists (arity > 64) — no hard limit in core types; arity consistency enforced later in dl-parse.

1.9 Failure Analysis

  • Interner overflow (> 2^32 symbols): intern() returns CoreError::InternerOverflow; upstream sees Err; no panic.
  • Poisoned interner mutex (if Arc<Mutex> is used): propagate PoisonError; log and abort session cleanly.
  • Corrupt Tuple length (tuple shorter than predicate arity): detected in dl-relation Phase 3, not here; dl-core is not the enforcement point.
  • Blast radius of a bug here: total — every other crate depends on dl-core; fix requires coordinated rebuild but no data migration.

1.10 Operational Notes

  • No runtime observability in Phase 1 (no I/O, no metrics); in later phases expose interner.len() as a gauge metric dl_core_symbol_count.
  • Log interner stats at program load time (symbol count, predicate count) at DEBUG level.
  • No migration concerns: Sym/PredId IDs are session-local (not persisted) in Phase 1.
  • RUST_LOG=dl_core=debug enables future tracing; tracing crate dependency added now (no instrumentation yet) so downstream crates can add spans without changing dl-core's public API.

Grammar (EBNF):

program     ::= statement*
statement   ::= fact | rule | query
fact        ::= atom '.'
rule        ::= atom ':-' body '.'
query       ::= '?-' atom '.'
body        ::= literal (',' literal)*
literal     ::= atom | 'not' atom | term cmp_op term
atom        ::= IDENT '(' term_list ')' | IDENT          -- 0-arity
term_list   ::= term (',' term)*
term        ::= CONST | VAR
CONST       ::= [a-z][a-zA-Z0-9_]*
VAR         ::= [A-Z_][a-zA-Z0-9_]*
IDENT       ::= [a-z][a-zA-Z0-9_]*
cmp_op      ::= '=' | '!=' | '<' | '<=' | '>' | '>='

Parsing: tokenize src → Vec<(Token, Span)>; dispatch per statement on lookahead (?-→query, :-→rule, else fact); intern predicate name→PredId, each arg→Term::Const(Sym)/Term::Var(u32) (per-rule VarTable); record arity in ArityTable, reject mismatch; run check_safety after each Rule. Safety algorithm (safety.rs): pos_vars = vars in positive body literals; head_vars/neg_vars/cmp_vars from head, Literal::Neg, Literal::Cmp; require (head_vars ∪ neg_vars ∪ cmp_vars) ⊆ pos_vars; emit SafetyError::UnsafeVar{rule_span, var_name} per violation. ParseCtx: shared Interner refs (Sym, PredId), ArityTable, error accumulator (collects all errors, not just first). RawProgram:

pub struct RawProgram {

    pub rules:   Vec<Rule>,

}
pub struct Query { pub goal: Atom }

2.8 Edge Cases

  • Zero-arity predicates (flag., done.) — valid; args: vec![]; arity = 0.
  • Comparison-only body (h(X) :- X < X.) — rejected: X must appear in a positive atom.
  • Self-referential fact (p(p).) — p as constant, not predicate; valid Datalog.
  • Duplicate facts (edge(a,b). edge(a,b).) — parse succeeds; dedup is dl-relation's job.
  • Very long rules (>100 body literals) — no hard limit; tested with 200 literals.
  • Nested not (not not p(X)) — invalid Datalog; rejected as UnexpectedToken.
  • Whitespace-only input — RawProgram { facts:[], rules:[], queries:[] }, no error.
  • Trailing comma in term list (p(a,b,).) — rejected as UnexpectedToken.

2.9 Failure Analysis

  • Panic in parser: no unwrap()/expect(); all ?-propagated, Result-clean.
  • Infinite loop in error recovery: lexer must advance ≥1 token per error; assert this.
  • Safety false negative: unsafe var accepted → wrong model at eval time; caught by conformance fixtures (Phase 14).
  • Arity-table state after error: on ArityMismatch, abort that predicate's table update; downstream stays consistent.
  • Blast radius: parse errors are compile-time (program load); no runtime data corruption.

2.10 Operational Notes

  • RUST_LOG=dl_parse=debug emits token stream and rule spans.
  • ParseError carries (line, col) span for user-facing messages.
  • dl-cli stratify (Phase 13) calls dl-parse first; parse errors propagate as non-zero exit.
  • No migration concerns: parser is stateless, re-parses from source on any change.
  • Future: serde-cache RawProgram behind a parse-cache feature flag (Phase 14).

pub struct DeltaRelation {

Phase 4 — Program Model + Stratification

4.1 Objectives

  • Classify every predicate as EDB or IDB from loaded rules and facts.

  • Detect and reject any program with a cycle through a negative or aggregate edge (not stratifiable).

  • Enforce I4 (stratification well-formedness): reject PDG cycles through a negative/aggregate edge.

  • Guarantee termination for all safe, function-symbol-free programs via the finite-domain argument.
  • Produce the complete minimal model: all IDB relations populated; EDB unchanged.
  • Oracle for diff-testing Phase 7 (semi-naive) and future Phase 11 (magic sets).
  • Validate I1 (minimal-model correctness), I2 (set semantics), I6 (termination).

5.2 Detailed Implementation Steps

Module: dl-eval/src/naive.rs; shared trait in lib.rs; model type in model.rs. Types:

trait Evaluator {
    fn run(&mut self, program: &Program) -> Result<Model, EvalError>;
}
struct NaiveEvaluator { round_limit: usize }
struct Model {
    relations: HashMap<PredId, Relation>,
}
impl Model {
    fn tuple_count(&self) -> usize;
    fn relation(&self, pred: PredId) -> &Relation;
    fn relation_mut(&mut self, pred: PredId) -> &mut Relation;
    fn assert_no_duplicates(&self);   // test-mode invariant check
}

Top-level algorithm:

initialize model: for each PredId p in program.predicates:
    model[p] = program.edb[p].clone()  // EDB seed (empty Relation if IDB-only)

for stratum_idx in 0..program.strata.len():
    rules = program.rules_by_stratum[stratum_idx]
    round = 0
    loop:
        new_tuples: HashMap<PredId, Vec<Tuple>> = {}
        for rule in rules:
            for θ in evaluate_body(rule.body, &model):
                t = project_head(rule.head, &θ)
                if !model[rule.head.pred].contains(&t):
                    new_tuples[rule.head.pred].push(t)
        if new_tuples.is_empty(): break
        for (pred, tuples) in new_tuples: model[pred].extend(tuples)
        round += 1
        if round > self.round_limit: return Err(EvalError::RoundLimitExceeded)

Body evaluation (naive, no indexing): recursive evaluate_body(literals, model, θ) -> Vec<Substitution>; base case empty literals yields θ. Literal::Pos(atom): scan full model[atom.pred], extend θ with free-var bindings on match, recurse. Literal::Neg(atom): all vars pre-bound (I3); prune if model[atom.pred].contains(apply(θ,atom.args)) (NAF). Literal::Cmp(t1,op,t2): evaluate both terms under θ, prune on failure. No index lookup — linear scan is intentional for correctness-reference status. Model init: EDB predicates copy fact tuples at startup; IDB predicates start empty; mixed predicates start with EDB tuples, IDB derivations accumulate on top. Termination (formalised): Sym domain finite (bounded by interner size, no new Syms introduced); arity fixed, so possible tuples per relation ≤ |domain|^arity. Monotonicity per stratum (I7): each round only adds tuples. Convergence: each round adds ≥1 tuple or breaks; total rounds ≤ Σ|domain|^arity over IDB relations. round_limit default max(1000, Σ|dom|^arity), configurable via NaiveEvaluator{round_limit}; if hit, return Err(EvalError::RoundLimitExceeded) (only reachable on unsafe programs — rejected in Phase 2 — or misconfiguration).

5.9 Failure Analysis

  • EvalError::StratumOrderViolation{rule_id, dep_stratum, head_stratum}: body references a higher-stratum predicate — indicates a Phase 4 bug; debug_assert! at eval entry.
  • EvalError::SafetyViolation{rule_id, var}: unbound variable at head projection; should be rejected by Phase 2; defense-in-depth debug_assert! in project_head.
  • EvalError::RelationOverflow{pred, limit}: configurable tuple ceiling exceeded, return early, allow partial-result inspection; RoundLimitExceeded{stratum, round} is abnormal only with function symbols (rejected by parser) or round_limit too low.
  • Silent wrong result if round_limit hit and ignored: always propagate as Err; never silently truncate.

Phase 6 — Relational Join Engine

6.1 Objectives

  • dl-join: evaluate a rule body as a planned sequence of indexed join steps, threading Substitution through body literals left-to-right, applying CmpFilter/NegCheck inline, and projecting bound substitutions onto head variables → candidate Tuples via project_head; handles repeated variables (self-join), constants in body/head args, mixed bound/free positions.
  • Replaces naive linear-scan body evaluation (dl-eval) from Phase 6 on; fixed left-to-right literal order for now — cost-based reordering is Phase 10.

JoinPlan/JoinStep (plan.rs):

struct JoinPlan { steps: Vec<JoinStep> }
enum JoinStep {
    IndexLookup {
        pred: PredId,
        bound_positions: Vec<usize>,   // positions whose values come from current θ
        free_positions:  Vec<usize>,   // positions that introduce new variable bindings
        vars_at_free:    Vec<u32>,     // variable id for each free position
    },
    CmpFilter  { lhs: Term, op: CmpOp, rhs: Term },
    NegCheck   { pred: PredId, bound_positions: Vec<usize>, args: Vec<Term> },
}

Plan construction: iterate rule.body in order, growing bound_vars: HashSet<u32> across steps. Literal::Pos(atom): bound_positions = args that are Const or already-bound Var; free_positions = rest; free vars added to bound_vars after the step. Literal::Cmp(t1,op,t2): both terms must be pre-bound (I3) → CmpFilter step. Literal::Neg(atom): all vars pre-bound (I3) → NegCheck step. Repeated variable in one atom, second occurrence already bound → emit an equality CmpFilter for the duplicate position. Executor (index-nested-loop):

evaluate_body(steps, model, θ):
    if steps is empty: yield θ; return
    match steps[0]:
        IndexLookup { pred, bound_pos, free_pos, vars_at_free }:
            key = [resolve(θ, atom.args[i]) for i in bound_pos]
            rel  = model.relation(pred)
            iter = if bound_pos.is_empty(): rel.full_scan()
                   else: rel.index_lookup(bound_pos, key)
            for tuple t in iter:
                θ' = θ.clone()
                for j in 0..free_pos.len(): θ'.insert(vars_at_free[j], t[free_pos[j]])
                evaluate_body(&steps[1..], model, θ')  // recurse / yield
        CmpFilter { lhs, op, rhs }:
            if eval_cmp(resolve(θ, lhs), op, resolve(θ, rhs)):
                evaluate_body(&steps[1..], model, θ)
        NegCheck { pred, bound_pos, args }:
            key = [resolve(θ, args[i]) for i in bound_pos]
            if !model.relation(pred).index_lookup(bound_pos, key).any():
                evaluate_body(&steps[1..], model, θ)

resolve(θ,term): Const(s)→s; Var(v)→θ[v] (debug-panics if unbound; I3 prevents this in release). project_head:

fn project_head(head: &Atom, θ: &Substitution) -> Tuple {
    head.args.iter().map(|t| match t {
        Term::Const(s) => *s,
        Term::Var(v)   => θ[v],
    }).collect()
}

Precondition: all Var ids in head.args bound in θ (I3). Index interop: Relation::index_lookup(bound_positions, key) -> impl Iterator<Item=&Tuple> builds+caches the Index on demand if missing; Relation::iter() is the full-scan path when bound_positions is empty. dl-eval integration: build_join_plan runs once per rule at eval start (or lazily); Vec<JoinPlan> stored parallel to Vec<Rule>; replaces Phase 5's evaluate_body with evaluate_rule_body(rule, model, plan). JoinPlan::validate() (run at load time, → EvalError::InvalidPlan on failure): every IndexLookup's bound_positions ⊆ vars bound by preceding steps; every CmpFilter/NegCheck's terms/args resolvable/bound under the accumulated set; else JoinError::UnboundVariable{var_id, step_index}.

Anchors: P8 (monotonicity within a stratum — aggregation is the non-monotone operator P8 quarantines across strata); I4 (stratification well-formedness — the aggregate-edge SCC check re-uses I4's cycle detection); see paper P6, Greco/Spezzano/Trubitsyna, in the papers list, for the formal aggregate-stratification conditions this step implements.

Phase 11 — Magic-Sets Transformation

11.1 Objectives

  • Implement dl-magic: adorn each query-relevant predicate with bound/free (b/f) patterns.
  • Generate magic (demand) predicates magic_p_bf and modified rules that push bindings sideways.
  • Rewrite the program so bottom-up evaluation only derives tuples reachable from the query goal.
  • Preserve I9 (magic-sets answer preservation): transformed program answers identical to original.
  • Fall back to full evaluation when transformation is not beneficial (all arguments free, or no recursion).

11.6 Pitfalls

  • Adornment explosion: a predicate with arity 4 has 16 possible adornments; worklist can grow quadratically. Cap at 64 adornments per predicate; warn and fall back.
  • Incorrect binding propagation order: if a variable is bound in literal 3 but treated as free in literal 2, the magic rule carries wrong bound positions. Strict left-to-right propagation; unit-test every permutation in small rules.
  • Non-linear recursion: rules with two recursive literals require careful sideways-information-passing; the standard algorithm handles one recursive literal per rule cleanly; flag multi-recursive rules and use conservative (all-free) adornment.
  • Magic predicate naming collision: auto-generated names like magic_p_bf may clash with user predicates. Prefix with __magic__ or use a private PredId namespace (IDs ≥ MAGIC_PRED_BASE).
  • Answer equivalence under aggregation: magic-sets is not defined for aggregation across strata; disable magic for rules feeding an aggregate stratum.
  • Seed fact scope: seed EDB fact must be in the transformed program's EDB, not the original; failing to include it means the magic relation is empty and no IDB tuples derive.

11.7 Performance Concerns

  • Transformation is O(|rules| × arity²) — negligible vs evaluation.
  • Magic predicates add new IDB relations; their index construction cost is proportional to the demand set size, which is the goal.
  • For queries with many bound positions, magic predicates are tiny; index builds are fast.
  • Transformation overhead dominates for trivially small programs; is_beneficial gate avoids this.
  • Re-transformation per query (different bound args) is cheap; cache (PredId, Adornment) -> Program for repeated identical queries.

11.8 Edge Cases

  • Query with all arguments bound (bb...b): magic relation is a single tuple; result is yes/no membership test.

  • Empty program (no rules): transform is identity; seed fact produces no IDB tuples.
  • Circular adornment: predicate adorned bf in its own body through recursion — handled by worklist seen-set, not re-enqueued.
  • Rule with no body literals (unconditional fact as rule): treat as EDB; skip magic rewrite for it.

Provenance store (dl-repl::provenance): every new-tuple derivation records (head_tuple, rule_id, body_tuples) into HashMap<(PredId, Tuple), Vec<Derivation>>; assert appends, retract flushes provenance for all re-derived strata; explain does a recursive lookup, cycle-detected via a HashSet<(PredId,Tuple)> guard. dl-cli (src/main.rs): clap-based, subcommands run | query | explain | stratify.
  • run: load + eval + print all IDB tuples as Datalog facts.
  • query --goal "ancestor(X,bob)": load + eval + answer + print.
  • explain --tuple "ancestor(alice,bob)": load + eval + print derivation tree.
  • stratify: load + classify + print strata table, no evaluation. REPL loop (dl-repl::repl_loop): rustyline-backed line editor with history file ~/.dl_history; prompt dl> , parses input, dispatches to Session methods, prints result/error; .help prints command list, unknown input yields a parse-error message with no session mutation.

Anchors: P10 (explainability — the provenance store here is P10's ProvenanceStore realized in dl-repl); P5 (semi-naive over naive — eval_incremental reapplies the delta-firing rule from an asserted fact's seed delta); see paper P9, Seo/Guo/Lam, in the papers list, for the incremental-update propagation strategy eval_incremental follows.

13.7 Performance Concerns

  • Provenance store allocation: one Vec<Derivation> per new tuple; use an arena allocator (bumpalo) for batch eval.
  • Incremental re-derivation scope: coarse stratum granularity may re-derive large strata; future work is predicate-level dirty tracking.
  • REPL line rendering: rustyline sync I/O is not a bottleneck, but avoid holding the Session lock during render.
  • retract full re-eval: for large programs with many strata, retract is O(full eval); documented as acceptable for Phase 13.
  • Derivation-tree pretty-print is recursive; limit depth for deep trees (e.g. long transitive-closure chains) and print ... continuation.

13.8 Edge Cases

  • Assert duplicate tuple: idempotent; HashSet insert returns false; no re-derivation triggered.
  • Retract non-existent tuple: no-op with warning message; model unchanged.
  • Load file not found: error printed, session remains in prior state.
  • Query against undefined predicate: parse error or "unknown predicate" message; no crash.
  • explain on EDB fact: base case — return leaf node with no rule, just the fact itself.
  • Assert fact for IDB predicate (in-head of a rule): reject with error; IDB is derived-only.
  • REPL Ctrl-D / EOF: clean shutdown, flush history file.
  • Program load when session already has a program: replace session; warn user of state reset.

Failure Mode Interaction Notes

  • Semi-naive divergence + negation soundness error can mask each other; always test both independently.
  • OOM can occur mid-stratum; partial models must not be presented as complete; engine must return an error, not a truncated model.
  • Magic-sets failure is always recoverable by falling back to full eval; this fallback path must be tested explicitly.
  • Stratification rejection is a hard gate; no partial evaluation is attempted on an unstratifiable program.
  • Aggregate overflow + wrong model: a silently wrong aggregate propagates through dependent IDB strata; checked arithmetic prevents this; but callers must handle AggregateOverflow and not treat it as a soft warning.
  • Index eviction + join correctness: LRU eviction of an index does not change the result set; the engine falls back to full scan; only performance is affected, not correctness (P2, I2).
  • Partial OOM (cap hit mid-stratum): the engine must not return a partial model as if it were complete; the TupleLimitExceeded error must propagate through the entire eval stack.
  • REPL reload semantics: reload discards all IDB and re-derives from EDB; it is always safe to use as a recovery action; side-effect: any in-flight query is invalidated.

Tracing Strategy

  • Tracing crate: tracing; subscriber: tracing-subscriber with EnvFilter.
  • Span hierarchy: program.load > parse > stratify > eval.stratum[n] > join.rule[id] > relation.insert.
  • Structured fields per span: stratum_index, rule_id, pred_id, round, delta_size, mode.
  • Log levels:
    • ERROR: invariant violations, OOM, overflow, divergence events.
    • WARN: degraded operation (index eviction, fallback from magic to full eval).
    • INFO: program load, stratum completion, query result counts.
    • DEBUG: per-round delta sizes, join plan selection, index builds.
    • TRACE: per-literal binding in join, per-tuple insertion.
  • Environment variable control: RUST_LOG=dl_eval=debug,dl_join=trace.
  • OTLP export: optional via feature = "tracing-otlp"; exports span tree to collector.

Structured Logging

  • Format: JSON lines in non-interactive mode; human-readable tracing-subscriber::fmt in TTY mode.
  • Required fields on every log event: timestamp (RFC3339), level, target (crate path), span_name, span_id.
  • Error events add: error_kind, pred_id or rule_id, source_location (file:line).
  • REPL audit log: separate append-only file (default ~/.dl_repl_audit.log); captures every load, assert, retract, query command with ISO timestamp and full argument text; never truncated.

Alerting Philosophy

  • Alert on correctness invariant events (overflow, magic divergence, semi-naive diff) immediately; page on-call.
  • Alert on resource exhaustion approaching limits (relation size, join intermediate rows) with headroom margin; allow time to investigate before impact.
  • Do not alert on user-caused parse/safety errors; log and surface via error return only.
  • All alert thresholds configurable at runtime via environment variables or dl-cli.toml config file.
  • Suppress alerts during known bulk-load windows (operator-set maintenance flag).
  • Alert severity mapping: correctness violations → P1 (immediate); resource at cap → P2 (warn); performance degradation → P3 (investigate); user errors → no alert.

Health Check Interface

  • Binary exposes --health-check flag: exits 0 if engine can parse a trivial test program and evaluate it; exits 1 otherwise.

Incident Response

  1. Triage: classify severity: (a) correctness (wrong model), (b) availability (timeout/OOM), (c) performance (slow but correct).
  2. Correctness incident: stop serving query results; collect program text + EDB snapshot; enable --naive fallback; file bug with minimal reproduction; add to conformance suite.
  3. Performance / OOM incident: inspect dl_relation_size, dl_join_intermediate_rows, dl_eval_rounds_total; enable join debug logging; identify high-cost rule or large relation; apply tuple cap or rewrite rule.
  4. Operator mistake: reload in REPL from source EDB; verify audit log for incorrect retract/assert sequence; re-run queries.
  5. Post-incident: add failing program as a regression test; update conformance suite; update runbook if gap found.

Backup / Trace-Management Strategy

  • EDB is ground truth: persist as .dl fact files (one file per predicate, one tuple per line); version-controlled or operator-managed.
  • IDB is fully derived: never back up; re-derive on reload; deterministic given EDB + program.
  • REPL audit log: append-only; rotate daily; retain minimum 30 days; store alongside EDB files.
  • Program text: version-controlled by rule author; engine does not store a copy.
  • Tracing spans: OTLP export if configured; in-process ring buffer (last 10,000 spans) as fallback.
  • Conformance fixtures (programs + expected models): version-controlled in tests/conformance/; serve as semantic ground truth.
  • Model snapshot cache (optional, Phase 14): binary file tagged with DL_MODEL_V<N> header; treat as ephemeral; delete and re-derive on version mismatch.

Deployment Topology

  • Default: single-process binary (dl-cli); reads EDB from files; writes model to stdout or file; no network.
  • Library embedding: dl-eval + dl-query as Rust crate; caller manages program lifecycle; no global state.
  • REPL mode: long-lived process; EDB loaded into memory; incremental assert/retract; no persistence across process restart unless EDB files are updated.
  • Future (out of scope for Phase 1–14): thin JSON-RPC or Unix socket interface for IDE integration; not designed in current phases.
  • No distributed state, no replication, no cluster in scope.

Deprecation Policy

  • Deprecated features announced in MINOR release: #[deprecated(since = "X.Y.0", note = "...")] attribute + CHANGELOG.md entry.
  • Deprecated features supported for at least two MINOR releases before removal in the next MAJOR.
  • Deprecated CLI flags: emit runtime warning on use; removed in next MAJOR.
  • Deprecated grammar constructs: parse successfully with WARN log for one full MAJOR cycle; removed in following MAJOR.
  • No deprecation of core type names (Sym, PredId, Term, Atom, Literal, Rule, Tuple, Substitution) post-1.0; these are invariant identifiers across portfolio projects #363, #231, #366.
  • Deprecation notices must include a migration path and a link to the replacement API or grammar construct.
  • CI enforces zero use of deprecated items in engine source code; deprecation warnings from user code are not CI failures.

Rolling-Upgrade Guarantees

  • Engine is stateless between runs: IDB re-derived on every load; no in-flight state to migrate across binary versions.
  • EDB files written by version N are readable by version N+1 (any MINOR) without conversion.
  • Model snapshot binary cache is version-tagged (DL_MODEL_V<N>): version mismatch triggers silent re-evaluation, never a crash or silent wrong result.
  • dl-cli --output=json format is stable within a MAJOR version; consumers should pin MAJOR and parse with unknown-field tolerance.
  • REPL audit log format (JSON lines) is forward-compatible: readers must tolerate unknown fields per JSON spec.
  • Concurrent use of two binary versions against the same EDB file directory is safe: EDB files are read-only during eval; writes (new fact files) are atomic file renames.
  • Library crate ABI: Rust crates do not have a stable C ABI; callers must recompile on version update; no #[no_mangle] or extern "C" surface in public API.

API Evolution Constraints

  • Sym(u32) and PredId(u32) are newtype wrappers; their integer value is never serialized in public formats (always mapped to string symbol); internal representation may change without format version bump.
  • Tuple = Vec<Sym> — length is always equal to predicate arity; consumers must not assume a fixed length.
  • Substitution = Map<u32, Sym> — variable indices are rule-local; not stable across reparsing; do not serialize a substitution with variable indices as a cross-session key.
  • Rule struct: adding optional fields (e.g., provenance annotation) is a MINOR change if optional with a default.
  • Program struct: adding a new metadata field is a MINOR change; removing or renaming existing fields is MAJOR.
  • Trait implementations (EvalDriver, RelationBackend, MetricsHandle): new required methods are MAJOR; new methods with default implementations are MINOR.
  • #[non_exhaustive] applied to all public enums and structs that may gain new variants/fields in MINOR releases.
  • Error types are #[non_exhaustive]; match arms must include a wildcard to remain forward-compatible.
  • Feature flags are additive; enabling a feature never removes functionality; disabling a feature always compiles (no mandatory features except std).
  • no_std compatibility: dl-core targets no_std + alloc; all other crates require std; this split is a post-1.0 stability guarantee.
  • Semantic version of the Datalog grammar is tracked separately from the binary version in grammar_version: u32 field of ParseConfig; allows grammar updates without a full crate version bump in library use cases.
  • Public re-exports: all types in dl-core are re-exported from a top-level dl facade crate (future); facade version = binary version; crate-internal version bumps are transparent to facade users.

Vertical Scaling

  • Single-threaded engine scales with CPU frequency and L3 cache size.
  • Practical ceiling: ~10M-tuple IDB relations on a modern workstation (64 GB RAM) within 30 s for 5-step transitive closure.
  • HashMap resize events cause periodic latency spikes; pre-size relations to expected cardinality when EDB size is known.
  • Tuple Vec<Sym> allocation pressure limits throughput at high tuple counts; mitigation: arena allocator for Tuple in eval loop (Phase 14 candidate).

Horizontal Scaling

  • Out of scope for this implementation.
  • Architectural note: strata are inherently sequential; intra-stratum parallelism is possible (parallel rule application) but requires join-output deduplication across threads — a non-trivial coordination cost.
  • Reference: Souffle's parallel mode uses OpenMP over rule groups within a stratum; can be adopted in a future phase behind a parallel feature flag.

Pathological: star-join (one large center, many small peripheral predicates) — Phase 10 must place center last.

Stratification Depth Ceiling

  • Each stratum requires a full fixpoint; k strata → k sequential fixpoints.
  • Programs with k > 20 strata are unusual; > 100 strata indicate a design smell (rule proliferation, recursive negation misuse) — emit a warning.
  • Memory: only the current and immediately-lower stratum must be live simultaneously; previous stratum relations can be dropped after the current stratum is stable (GC hook in dl-eval).

Recursion Depth / Round Count

  • For a transitive closure on a diameter-d graph: semi-naive converges in d rounds.
  • Rounds are not stack frames; recursion is unrolled iteratively — no stack overflow.
  • Worst case: linear chain of n nodes, d = n; semi-naive: n rounds each adding 1 tuple → O(n²) total work. Magic-sets with start-node binding reduces to O(n).

Index Memory Scaling

  • Per-predicate, per-bound-pattern index: HashMap<Vec<Sym>, Vec<Tuple>>.
  • Memory per index entry: ~48 bytes overhead + key allocation + tuple pointer.
  • For an n-tuple relation of arity k with m distinct index patterns: memory ≈ n × m × (48 + k × 4) bytes.
  • Phase 10 must prune redundant indexes (subsumable patterns); assert index count ≤ 2 × arity per predicate in benchmarks.

Incremental Update Scaling (REPL / Phase 13)

  • Assert-fact cost: O(1) insert + O(Δ-derivations) semi-naive from the single new delta tuple.
  • Retract-fact cost: requires re-derivation from scratch (no deletion propagation implemented); document limitation; full re-eval fallback.
  • Scaling pressure: repeated interleaved assert/retract cycles on large EDB → repeated full re-eval; recommend batch-assert patterns in dl-repl docs.
  • Long-term IDB growth: IDB is monotone under assertion-only workloads; size bounded by the minimal model, which is finite for safe programs (I6).

Metadata Scaling

  • Symbol interner (dl-core): HashMap<String, Sym> + Vec<String>; scales to 10M symbols before memory concern (< 500 MB).
  • PredId space: u32 → 4 × 10⁹ predicates; not a practical ceiling.
  • Dependency graph: |V| = predicate count, |E| = rule count × avg body size; for programs with ≤ 10 000 rules, PDG fits trivially in memory.
  • Stratification SCC: Tarjan's algorithm O(V + E); negligible for all realistic programs.

Mental Models & First Principles

  • MM1 — Datalog separates declarative meaning from operational strategy. The least fixpoint of the rules is the answer; naive, semi-naive, and magic-sets are merely ways to compute it. Predicts: every correct strategy yields the identical model. Bug without it: mistaking an optimization (magic-sets) for a semantic change. Applied: §2, I1, Phases 5/7/11.
  • MM2 — A rule is relational algebra: body = join + select, head = projection. Evaluation is repeated relational joins to a fixpoint. Predicts: join order and indexing dominate cost, exactly as in SQL. Bug without it: treating Datalog as logical interpretation → row-at-a-time slowness. Applied: Phase 6, Phase 10, ADR-07.
  • MM3 — Sets, not bags: duplicates are a semantic error, and dedup is what guarantees termination. Predicts: without set semantics the fixpoint may never close. Bug without it: bag semantics → inflated counts and non-termination. Applied: I2, ADR-06, Phase 3.
  • MM4 — Semi-naive evaluation joins only with last round's NEW tuples (the delta). Never recompute what didn't change. Predicts: per-round cost ∝ delta size, not total size. Bug without it: naive re-derivation every round → quadratic blow-up. Applied: I5, Phase 7, MM2.
  • MM5 — Stratification is a topological layering so each non-monotone op sees a CLOSED relation. Predicts: a negative cycle means an undefined program (reject at load). Bug without it: negating a relation still being computed → unsound/oscillating fixpoint. Applied: I4/I8, Phases 4/8, ADR-12.
  • MM6 — Negation is closed-world (NAF): "not p(x)" means p(x) is not derivable, decided only after p's stratum completes. Predicts: NAF needs a fully materialized relation first. Bug without it: evaluating NAF mid-fixpoint → wrong negatives. Applied: I8, Phase 8.
  • MM7 — Magic-sets is a provably answer-preserving program rewrite that pushes the query's bindings into the rules. It turns bottom-up into goal-directed. Predicts: it changes performance, never the answer set. Bug without it: believing magic-sets can drop answers → unsound rewrites. Applied: I9, Phase 11, ADR-15.
  • MM8 — Termination is structural, not runtime-checked. Range-restriction (every head var bound in a positive body literal) + no function symbols bounds the Herbrand base, so the fixpoint must close. Predicts: reject unsafe rules at load, not via a timeout. Bug without it: relying on a step limit → false non-termination or missed answers. Applied: I3/I6, Phase 2.

  • Soufflé compiles each program to specialized C++ with purpose-built relation containers (Brie, B-tree) and OpenMP — it wins for large static-analysis workloads where compile-once-run-fast on millions of tuples beats interpreter flexibility.
  • Differential Datalog (DDlog) is built on differential dataflow, so the engine is incremental by construction: change inputs and only affected outputs recompute — it wins for streaming/reactive workloads with continuously changing inputs (network config, IDE analysis).
  • LogicBlox made Datalog a full transactional database language with aggregation and updates — it wins for enterprise applications wanting declarative business logic and persistence in one engine.
  • Datomic stores immutable datoms with EAVT covering indexes and answers a Datalog query subset — it wins when you need an auditable, time-travel database whose query language happens to be Datalog.
  • Nemo targets reasoning over existential rules (datalog±) with bottom-up materialization — it wins for knowledge-graph/ontology reasoning needing the existentials this engine deliberately excludes.

Back-of-Envelope Capacity Model

All inputs are taken from §4 (System Constraints); arithmetic is shown.

  1. EDB RAM. 10M tuples × ≤32 B/tuple = ≤320 MB; arity-2 Sym pairs ≈ 160 MB (§4). Formula: tuples × bytes/tuple.
  2. IDB RAM ceiling. 50M derived × 32 B = 1.6 GB peak across all strata (§4 IDB bound).
  3. Index overhead. ≤ 2× stored tuples (§4) → at 10M EDB, indexes add ≤ 20M tuple-refs ≈ ≤ 640 MB.
  4. Interner. 10K predicates → PredId Vec ≈ 40 KB (§4); the symbol interner for D distinct constants ≈ D × ~40 B (Arc<str> + entry).
  5. Semi-naive round cost. ∝ delta size; delta < 100K tuples → p50 < 10 ms (§4) → ~100 ns/tuple join-probe budget (one hash lookup).
  6. Transitive closure work. TC of N nodes / E edges → up to N×N reachable pairs; 10K nodes → up to 1e8 pairs, bounded < 2 s (§4) → ~20 ns/pair.
  7. Fixpoint rounds. bounded by min-model height = longest derivation chain; for TC = graph diameter (≤ N). Each round joins the delta against the edge relation (MM4).
  8. Join probe rate. hash-set membership is O(1) ≈ tens of ns; a round over delta D against relation R builds one index (O(|R|)) then probes |D| times.
  9. Rule-body join. ≤ 12 literals (§4) → join-ordering search O(k!) capped by the most-bound-first heuristic, which shrinks intermediate relation sizes.
  10. Stratification. SCC over the PDG with V = predicates ≤ 10K, E = rules × avg-body ≤ 100K × 12 = 1.2M → Tarjan O(V+E) ≈ 1.2M ops < 50 ms (§4).
  11. Magic-sets rewrite. linear pass over ≤ 1K rules < 100 ms (§4); output bounded by rule count × adornments.
  12. Provenance. ≤ 10K derivation steps traceable (§4); explain walks the derivation DAG with memory ∝ chain depth × tuple size.

Alternative Architectures (Roads Not Taken)

A1 — Top-down SLD resolution with tabling (memoized Prolog-style).

Show the original text diagram
query goal → resolve against rule heads → table sub-goals → reuse memoized answers

Wins for queries touching a small fraction of the model (highly selective goals) where bottom-up over-derives. Embodied by XSB / tabled Prolog. Rejected because bottom-up semi-naive is simpler to make complete and the target workloads materialize most of the IDB; magic-sets recovers demand-driven behavior without a second engine (Phase 11).

A2 — Incremental dataflow (differential dataflow).

Show the original text diagram
inputs as collections → arranged operators → only deltas propagate downstream

Wins for continuously-changing inputs where only deltas should recompute (reactive/streaming). Embodied by Differential Datalog / timely. Rejected for v1 because batch evaluation (§4) targets load-once-query workloads; full incremental view maintenance is deferred (Register).

A3 — Compile-to-native (rule program → specialized C++/LLVM).

Show the original text diagram
.dl program → codegen → specialized relation containers + loops → native binary

Wins for huge static analyses run repeatedly where compile-once amortizes. Embodied by Soufflé. Rejected because an interpreter gives REPL interactivity and faster iteration (Phase 13), and the §4 sizes (≤ 10M facts, < 2 s TC) fit an interpreter comfortably.

A4 — Worst-case-optimal join over sorted columns (Leapfrog Triejoin).

Show the original text diagram
relations as sorted tries → multi-way variable-at-a-time join → WCOJ bound

Wins for cyclic/many-way joins where binary-join plans explode (graph-pattern queries). Embodied by LogicBlox / Soufflé's Brie. Rejected for v1 simplicity; hash-join with most-bound-first ordering suffices for ≤ 12-literal bodies (§4), with WCOJ a Phase-14 option.
