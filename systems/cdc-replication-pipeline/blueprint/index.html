215 — CDC Replication Pipeline End-to-End

Project Number: 215

Project Name: CDC Replication Pipeline End-to-End

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

This project builds, from scratch in Rust, a production-grade change-data-capture (CDC) replication pipeline: a connector process that tails one source database's write-ahead log (WAL) or binary-log replication stream, decodes committed row-level mutations (insert/update/delete, plus DDL) into a canonical ChangeEvent envelope, assigns each event a total order derived from the source log-sequence-number (LSN), transforms and routes events by table/key, and applies them to one or more heterogeneous sinks (a relational database, a search index, a data warehouse, a message log) with exactly-once effect delivered on top of an at-least-once transport. The pipeline bootstraps a new sink from a consistent point-in-time snapshot and hands off seamlessly to the live stream at a coordinated watermark (the Netflix DBLog algorithm), tracks and propagates source schema evolution, exercises backpressure end-to-end, and exposes lag/health telemetry an operator can act on without attaching a debugger.

Phase-0 deliverable (crate list — the full repository skeleton is stood up in Phase 0, §12; each crate's logic is built out across Phases 1–11):

  1. pipeline-core — shared types, error taxonomy (§11).
  2. capture-postgres — PostgreSQL logical-decoding / pgoutput reader.
  3. capture-mysql — MySQL binlog row-based-replication reader.
  4. decode-engine — WAL/binlog frame → ChangeEvent decode, transaction reassembly.
  5. lsn-tracker — Lsn/Offset/Txid bookkeeping, total-order assignment.
  6. snapshot-reader — chunked, consistent initial-snapshot reader.
  7. handoff-coordinator — DBLog watermark-based snapshot-to-stream handoff.
  8. schema-registry — TableSchema/SchemaVersion tracking, compatibility modes.
  9. transform-engine — Transform pipeline (rename, filter, mask, derive).
  10. router — table/key → sink-set routing.
  11. sink-runtime — Sink trait, ApplyResult, IdempotencyKey, DLQ plumbing.
  12. sink-db — relational-sink applier (idempotent upsert).
  13. sink-search — search-index applier.
  14. sink-warehouse — warehouse applier (batched merge).
  15. sink-log — message-log applier (append-only).
  16. offset-store — Checkpoint persistence, atomic offset commit.
  17. backpressure — credit-based flow control across stages.
  18. lag-monitor — LagMetric computation and export.
  19. admin-api — operator control plane (pause/resume/rewind/status).
  20. correctness-harness — Jepsen/Elle-style fault-injected end-to-end verifier.

System boundaries:

  • Provides: log tailing, decode, ordering, snapshot bootstrap, handoff, transform, routing, idempotent multi-sink apply, checkpointing, schema-evolution propagation, backpressure, lag telemetry.
  • Delegates: durable transport of already-decoded events to an external log (Kafka-Messaging, project 27) when configured in via-log mode (ADR-18); a saga/workflow layer (Saga-Workflow-Coordinator, project 97) for cross-service compensating transactions; general pub/sub fan-out (PubSub-Messaging, project 206); a generic replication wire protocol library (Replication-Protocol, project 208) for byte-level framing this pipeline consumes rather than reimplements.
  • Does NOT provide: ownership of the source database (it never writes to the source) or the sink databases (it applies changes but does not manage their schemas, backups, or query planning); it is not a stream-processing query engine — no windowed joins, no SQL-on-stream, no stateful aggregation beyond per-key dedup.

Non-goals, named against siblings:

  • Not CDC-Engine (103): that project owns log-decode/capture only — a library that turns raw WAL/binlog bytes into typed change records. This project consumes an equivalent decode layer (decode-engine) but is the full pipeline: it also snapshots, hands off, transforms, routes, applies to sinks, checkpoints, and monitors lag end-to-end.
  • Not Kafka-Messaging (27): that project builds a durable log/broker. This project may use one as an optional transport (ADR-18) but does not build a broker itself.
  • Not Replication-Protocol (208): that project specifies/implements the wire-protocol bytes. This project is a protocol consumer.
  • Not PubSub-Messaging (206): that is generic topic fan-out infrastructure; this project's routing (router, §11) is CDC-specific — table/key → sink-set, not general pub/sub.
  • Not Saga-Workflow-Coordinator (97): that project coordinates multi-step compensating transactions across services; this project's "exactly-once effect" (I1–I6, §7) is single-hop idempotent apply, not saga compensation.
  • Not a stream-processing query engine (no Flink/ksqlDB equivalent): transforms are per-event, stateless-by-default (bounded per-key dedup state only, §8).

Deployment model: one connector process per source (a capture-* + decode-engine + lsn-tracker + snapshot-reader + handoff-coordinator instance), reading one source's log; a fleet of such processes coordinates through an external coordination store (etcd/Consul-class, ADR-19) for slot ownership, rebalancing, and fleet-wide schema-registry state. Each connector process owns exactly one source; sinks are addressed by the router from any connector.

Users/operators: platform data-infrastructure teams standing up a change feed off an OLTP database; SREs who page on replication lag or a stuck pipeline; backend engineers writing new Sink implementations.

What later phases unlock: exactly-once-effect apply (Phase 4), consistent bootstrap of new sinks without downtime (Phases 5–6), live schema evolution without pipeline restart (Phase 7), horizontal fleet scaling with rebalancing (Phase 10), and a fault-injected correctness proof that the sink is a faithful replica (Phase 11).

Language: Rust. Rationale — the decoder sits directly on untrusted, attacker-reachable network bytes (the replication stream) and must not fault under malformed input; predictable tail latency (no GC pause) matters for the lag SLOs in §4; the crate/trait system gives a zero-cost Sink abstraction across heterogeneous appliers (§11). Rejected: Go — GC pauses show up in p99 apply latency (§4) and its interface-based abstraction costs a dynamic-dispatch-plus-boxing tax at the per-event rate this pipeline runs at; Java/JVM (Debezium's own language) — proven for this exact domain, but GC tuning and JIT warm-up work against the crash-resume time target (§4), and this project intentionally does not reuse the JVM stack; C++ — no ownership/borrow-checker guarantee against the use-after-free class of bug that a hand-rolled decoder over untrusted WAL bytes is prone to.

Prerequisites: WAL/binlog internals (checkpoint records, page LSNs), replication protocols (PostgreSQL streaming/logical replication, MySQL binlog), transaction-log semantics, distributed checkpointing, idempotence and dedup, schema-evolution compatibility theory, async Rust (Tokio), backpressure/flow-control theory, basic lease-based coordination.

Timeline: Phase 0 (skeleton + mock source log + CI) — 2 weeks. Phases 1–4 (capture, decode, first sink, offset-commit/resume) — 8 weeks. Phases 5–6 (snapshot + handoff) — 5 weeks. Phases 7–9 (schema evolution, DDL/multi-sink, backpressure/DLQ) — 6 weeks. Phases 10–11 (HA/rebalancing, correctness harness/perf hardening) — 7 weeks. Full system: ~7 months to production hardening.

Deferrals: Oracle XStream/MongoDB oplog/SQL-Server-CDC/DynamoDB-streams/Cassandra-commit-log source connectors — PhaseDeferred("Deferred Features Register"); cross-region active-active replication — PhaseDeferred("Deferred Features Register"); a stream-processing query layer atop the event bus — PhaseDeferred("Deferred Features Register") (out of scope per the non-goals above, listed here for completeness).

2. Why Build This

  • Write-ahead logs as the single source of truth: every CDC system is a parser and total-order-assignment problem before it is anything else.
  • Exactly-once effect is the central honest answer to "exactly-once delivery": idempotent apply + atomic offset commit, never a "magic" transport.
  • The snapshot-to-stream handoff is the hardest correctness point in any CDC system — get it wrong and every downstream sink silently diverges from day one.
  • Schema evolution under live traffic: propagating add/drop/rename/type-change without downtime or data loss.
  • Backpressure across heterogeneous sinks with wildly different apply latencies (search index vs warehouse batch).
  • Operating a replication slot: the source-side blast radius (unbounded WAL retention) when the pipeline falls behind.
  • Historically underpins Kafka Connect + Debezium, LinkedIn Databus, AWS DMS, Netflix DBLog, and Materialize's ingestion layer — CDC is how "the database escapes the database" (Kreps).
  • Calibration: an engineer who ships this can reason about log-structured storage, replication protocols, idempotence, and operational recovery under corruption — the exact skill Kingsbury's Jepsen analyses exist to test.

What Mastery Looks Like

  • Derive the DBLog watermark handoff algorithm from first principles and explain why a naive "snapshot then stream" ordering silently loses or duplicates rows (Phase 6, §17).
  • Explain why "exactly-once delivery" is unachievable but "exactly-once effect" is, and implement the idempotent-upsert + atomic-offset-commit pattern that makes it true (Phase 4, §16).
  • Diagnose a stuck pipeline from slot_retained_wal_bytes alone, before checking anything else (Phase 10, §22; §26).
  • Propagate an ALTER TABLE ADD COLUMN to three sinks with three different schema models without restarting the pipeline (Phase 7, §19).
  • Build and read a Jepsen/Elle-style differential harness that proves a sink converges to the source under fault injection (Phase 11, §23).
  • Reason about per-key ordering vs global ordering tradeoffs when parallelizing sink apply (Phase 9/10, §21–§22; §31).
  • Explain the source-side risk of an unbounded replication slot and design the safeguard that prevents it from taking down the primary (Phase 1, §13; T2, §24).

Source Database: external trust boundary; this pipeline never writes to it; the WAL/binlog ordering it produces is authoritative and cannot be second-guessed downstream.

capture-postgres/capture-mysql: one task per source, holds the ReplicationSlot handle, speaks the source's native replication protocol over TLS, converts network bytes into raw frames; boundary between untrusted network input and this process's memory (T4, §24).

decode-engine: reassembles frames into per-transaction ChangeEvent sets, validates frame checksums, buffers open transactions bounded by memory quota (P6).

lsn-tracker: assigns the total order (lsn, txid, event_seq) (§8) to every event; the single authority resume/dedup/ordering all derive from (P1).

snapshot-reader: chunked, lock-minimal consistent reader of a table's current rows for bootstrap; persistence boundary is the source's own MVCC/consistent-read mechanism, not this pipeline's.

handoff-coordinator: runs the DBLog watermark algorithm (§8) per table; the concurrency boundary between the snapshot path and the stream path; owns HandoffState.

schema-registry: durable, fleet-replicated; gates DML behind DDL application (I9); persistence boundary between in-memory schema cache and the durable registry store.

transform-engine: stateless-by-default per-event transform pipeline (rename/filter/ mask/derive); a Transform failure routes to the DLQ, never blocks the stream (I11).

router: maps table/key to a sink-set; the fan-out boundary — one event may address 0..N sinks.

sink-db/sink-search/sink-warehouse/sink-log: heterogeneous Sink implementations; each owns its own apply protocol boundary (SQL transaction, HTTP bulk API, batched merge, append) and idempotency mechanism (§8 sequence table).

offset-store: durable persistence boundary for Checkpoint; the atomic-commit boundary that makes exactly-once effect possible (P5, I5, I6, I8).

backpressure: cross-cutting credit-based flow-control boundary spanning every queue between decode-engine and the sink appliers (P6, I13).

lag-monitor: read-only observer computing LagMetric from offset-store and slot state; the operational-visibility boundary (P11, §26).

6. Design Principles

P1 — The LSN is the clock. The source log is the single source of truth; every event's position is its LSN; resume, ordering, and dedup all derive from it (Lamport 1978). Violate it and two connectors can disagree on "what happened when."

P2 — Exactly-once effect, never a cleverer transport. Idempotent apply + atomic offset commit; at-least-once is the only delivery the transport actually gives (Helland 2007). Violate it and duplicates or gaps appear at the sink under any retry.

P3 — The handoff must stitch without gap or overlap. The snapshot-to-stream watermark handoff is the hardest correctness point in the system (DBLog). Violate it and a new sink silently diverges from day one.

P4 — No implicit ownership. A replication slot or partition has exactly one active reader, and that lease is externally observable. Violate it and two readers double-apply.

P5 — Persist before acknowledge, acknowledge before advance. An offset commit (durable) precedes the corresponding slot/binlog-position advance (I6). Violate it and a crash between the two loses events irrecoverably.

P6 — Backpressure is mandatory everywhere. No unbounded queue anywhere in the pipeline. Violate it and a slow sink causes unbounded upstream memory growth, which then bloats the replication slot on the source.

P7 — Schema is versioned data, not code. Every event carries its SchemaVersion; compatibility is checked at the registry boundary, not assumed. Violate it and a renamed column silently misapplies.

P8 — DDL is a first-class event. It flows through the same ordered stream as DML so sinks see it at the correct position, not an out-of-band side channel. Violate it and a sink applies post-DDL rows against a pre-DDL schema.

P9 — Per-key ordering survives parallelism. Global total order (by LSN) may relax to per-key order for throughput, never the reverse. Violate it and a delete-then-insert on the same key can apply out of order.

P10 — Crash-only design. Every component assumes ungraceful termination is normal; no distinguished "clean shutdown" path is load-bearing for correctness. Violate it and recovery logic tested only on clean shutdown fails in production.

P11 — Observability is a first-class output. Every pipeline-lifecycle transition (§8) emits a metric and trace span. Violate it and the two alerts that matter (§26) — slot lag and end-to-end lag — arrive too late to act on.

P12 — Poison events are contained, not fatal. A malformed or unappliable event goes to the DLQ, not to a halted pipeline. Violate it and one bad row becomes a fleet-wide outage.

P13 — Slot retention is a source-side liability. The pipeline actively bounds WAL retention because the source primary's disk is at risk, not just the pipeline's SLA (T2). Violate it and a stalled connector can take down the source database.

P14 — Wire compatibility is additive-only. New envelope fields are optional and ignorable by older consumers; no field is ever repurposed. Violate it and a rolling upgrade breaks an in-flight consumer.

LSN/Offset Model & Ordering

total_order(e)   = (e.lsn, e.txid, e.event_seq)                 // lexicographic, I1/I4
resume_point(s)  = max { c.committed_lsn : c in Checkpoints(s) }              // I5
slot_advance_lsn = min { resume_point(s) : s in AllSinks(connector) }         // I6

The slowest-committing sink gates the slot advance — the mechanism behind I6/I10.

Snapshot-Plus-Stream Bootstrap: the DBLog Watermark Handoff

Named steps (per table, per chunk):

  1. Low Watermark — before scanning chunk C, handoff-coordinator inserts a low watermark W_lo into the stream buffer at the then-current LSN.
  2. Chunk Select — snapshot-reader reads chunk C = { pk in [k_start, k_end] } via a single consistent-read query, no long-held lock (ADR-06).
  3. High Watermark — after C is read, handoff-coordinator inserts a high watermark W_hi into the stream buffer at the then-current LSN.
  4. Window Dedup — any stream event for a row in C with LSN in [W_lo, W_hi] is buffered ("the window"). After W_hi, for each row in C: if a window event exists for that key, it wins (it postdates the snapshot read); else the snapshot row wins. Exactly one image per key is emitted.
  5. Advance — repeat 1–4 per chunk until the table is covered; the final chunk's W_hi becomes the table's handoff LSN; HandoffState flips to Streaming for that table.

Worked example (chunk of keys {10,11,12}):

  • LSN 100: W_lo emitted.
  • Snapshot read returns rows for keys 10, 11, 12 as of a consistent read.
  • LSN 105: stream UPDATE key=11 arrives (falls in the window).
  • LSN 108: W_hi emitted.
  • Reconciliation: key 10 → snapshot image (no window event). Key 11 → window UPDATE image (LSN 105 postdates the read). Key 12 → snapshot image.
  • Result: exactly 3 rows emitted, no duplicate, no missing row (I7).

Exactly-Once-Effect Protocol

Step Actor Action Crash Here → Effect
1 decode-engine decode ChangeEvent, assign IdempotencyKey = hash(table, pk, lsn) event never produced; resume re-decodes from last slot position, no duplicate risk
2 router/transform-engine route + transform, forward to sink-runtime event lost pre-sink; resume re-decodes and re-routes from checkpoint (I5)

4 sink-runtime if key seen, skip (I2); else idempotent upsert by primary key into the sink crash mid-upsert: the sink's own transaction atomicity (or an idempotent PUT) guarantees the row is either fully applied or not — never partially
5 sink-runtime record IdempotencyKey in the sink's dedup store (same transaction as step 4 where possible, ADR-09) crash between 4 and 5: retry re-applies step 4 as a no-op upsert (same after-image, safe) and re-records the key
6 offset-store atomically commit Checkpoint{sink_id, lsn} only after step 5 acks crash before commit: resume redelivers from last committed LSN, replaying 1–5; step 4's upsert-by-key absorbs the replay (I5)
7 lsn-tracker advance the replication slot position to min(committed offset) across sinks (I6) crash before advance: slot retains more WAL than strictly needed, bounded by I10 — never loses events

DDL Handling Rules

  • DDL arrives in the same ordered stream as DML at its true source LSN (P8).
  • decode-engine emits Op::Ddl carrying the raw statement plus a parsed schema diff.
  • schema-registry validates the diff against its compatibility mode (§27) before accepting.
  • router blocks DML for the affected table until the DDL is applied to schema-registry (I9), bounded by backpressure (I13), never indefinitely.
  • Each sink independently maps the abstract schema diff to its own DDL dialect (table above) — sinks are never required to change in lockstep.

Dead-Letter / Poison-Event Handling

A DeadLetter record captures {event, error, first_seen, retry_count}. sink-runtime retries a failing apply with bounded exponential backoff (ADR-16) up to a retry ceiling, then routes to the sink-log-backed DLQ and continues the stream for unrelated keys (I11). An event that fails schema validation at decode is DLQ'd immediately, no retry (unrecoverable-by-retry class).

Worked End-to-End Example

Source UPDATE orders SET status='shipped' WHERE id=42 commits at LSN 5000, txid 900. decode-engine emits ChangeEvent{lsn:5000, txid:900, op:Update, table:orders, before:{status:"pending"}, after:{status:"shipped"}}. lsn-tracker assigns total_order=(5000,900,0). router sends it to sink-db and sink-search per the routing rule for orders. sink-db upserts by pk=42; sink-search updates document id=42. Both record IdempotencyKey=hash(orders,42,5000). offset-store commits Checkpoint{sink-db,5000} and Checkpoint{sink-search,5000}. lsn-tracker advances the slot to LSN 5000 once both checkpoints commit (I6).

Malformed / Failure-Path Examples

  • Schema change mid-stream without a matching DDL event (e.g. wal2json misconfigured without DDL capture): schema-registry detects column drift via a mismatched RowImage field set, halts DML for that table, alerts (I14, FM-7, §25).
  • Slot falling behind and dropped by the source (retained-WAL breach; admin runs pg_drop_replication_slot): capture-postgres sees a "slot does not exist" error on next poll, transitions the pipeline to Failed, requires a full re-snapshot (I10, FM-2, §25).
  • Sink apply failure (e.g. a unique-constraint violation from a bad transform): retried per the DLQ policy above; after the retry ceiling, DLQ'd, pipeline continues (I11, FM-5, §25).
  • Duplicate delivery (a connector restart replays an already-applied LSN range): sink-runtime's step-3 IdempotencyKey lookup absorbs it as a no-op (I2).
  • Out-of-order arrival (a transform re-orders within a batch): router's per-key sequencer re-orders before sink-runtime sees it; if it cannot (cross-partition), reject + DLQ + alert (I4, FM-6, §25).
  • A transaction spanning a chunk boundary during handoff: window dedup (Step 4 above) guarantees the newest-LSN image per key wins regardless of which side of the chunk boundary its commit lands on — the mechanism is per-key, not per-transaction (I7).
  • Failure-path example: the connector crashes mid-apply (step 4 of the sequence table above). On restart, lsn-tracker reads the last committed Checkpoint (LSN 4990), decode-engine resumes the replication stream from the corresponding slot position and re-decodes LSN 5000's event; sink-runtime's dedup lookup (step 3) finds no prior key (step 5 never completed) and safely re-applies the idempotent upsert — net effect identical to a single apply (I2, I5).

11. Core Schema & Types

// Identifiers — Copy, Ord; persistence: fixed-width ints; serialization: fixed-width wire
// encoding; compatible across versions (append-only IDs, never repurposed, P14).
type SourceId = u32;
type Lsn = u64;                 // monotonic per source; the ordering key (P1, I1)
type Offset = Lsn;               // alias: the offset IS the source LSN (ADR-05)
type Txid = u64;
type SchemaId = u32;
type SchemaVersion = u32;        // monotonic per SchemaId

// ChangeEvent — owned by decode-engine at creation, immutable after; Send+Sync;
// persistence: transient (not itself persisted; fields feed Checkpoint/DLQ);
// wire: Protobuf (ADR-12).
struct ChangeEvent {
    source_id: SourceId,
    lsn: Lsn,
    txid: Txid,
    event_seq: u32,
    op: Op,
    table: TableId,
    schema_version: SchemaVersion,
    before: Option<RowImage>,
    after: Option<RowImage>,
    meta: SourceMeta,
    idempotency_key: IdempotencyKey,
    checksum: u64,
}

// Op — Copy, exhaustively matched everywhere; compatibility: a new variant requires a
// major version bump (ADR-24 / §27).
enum Op { Insert, Update, Delete, Truncate, Ddl }

// RowImage / BeforeAfter — owned by ChangeEvent; immutable; serialization: column-name-
// keyed map, forward-compatible (unknown columns preserved, P14).
struct RowImage { columns: Map<ColumnId, Value> }
struct BeforeAfter { before: Option<RowImage>, after: Option<RowImage> }

// SourceMeta — small, Copy-ish; commit_ts is informational only, never used for
// ordering (ADR-24).
struct SourceMeta { source_id: SourceId, table: TableId, commit_ts: Timestamp }
// TableSchema / ColumnDef — owned by schema-registry; mutation: append-only new
// SchemaVersion per change, never edited in place; persistence: durable table in the
// registry's backing store; compatibility: BACKWARD default (ADR-15).
struct ColumnDef { name: String, ty: ColumnType, nullable: bool, default: Option<Value> }
struct TableSchema { table: TableId, version: SchemaVersion, columns: Vec<ColumnDef> }

// SchemaRegistry — shared, internally Arc<RwLock<..>>; concurrency: readers never block
// on a lookup longer than a version swap; persistence: durable, fleet-replicated (ADR-19).
trait SchemaRegistry {
    fn resolve(&self, table: TableId, version: SchemaVersion) -> Option<TableSchema>;
    fn propose(&self, diff: SchemaDiff) -> Result<SchemaVersion, SchemaViolation>;
}

// SnapshotChunk / Watermark / HandoffState — owned by handoff-coordinator;
// SnapshotChunk immutable once selected; Watermark is a point-in-time LSN marker
// injected into the stream (§8); HandoffState mutation is single-writer per table.
struct SnapshotChunk { table: TableId, key_range: (Value, Value), rows_read: u64 }
struct Watermark { table: TableId, lsn: Lsn, kind: WatermarkKind /* Low | High */ }
enum HandoffState { Snapshotting, WindowReconciling, Streaming }

// DecoderStream / ReplicationSlot — owned by capture-postgres/capture-mysql; not Send
// across tasks (single reader task per slot, P4); persistence: the slot itself lives in
// the source DB, not this process.
trait DecoderStream { fn next_frame(&mut self) -> Result<RawFrame, CaptureError>; }
struct ReplicationSlot { name: String, source_id: SourceId, retained_wal_bytes: u64 }
// Sink trait — implemented by sink-db/sink-search/sink-warehouse/sink-log; object-safe;
// concurrency: one apply-batch in flight per (sink, partition), enforced by
// sink-runtime, not the trait itself.
trait Sink {
    fn apply(&self, batch: &[ChangeEvent]) -> ApplyResult;
    fn idempotency_check(&self, key: &IdempotencyKey) -> bool;
}

// ApplyResult — returned per batch; mutation: none (value type); serialization:
// internal only, never on the wire.
enum ApplyResult { Applied(u32), PartialFailure(Vec<(ChangeEvent, ApplyError)>), Rejected(ApplyError) }

// IdempotencyKey — Copy, Hash, Eq; derived deterministically from (table, primary_key,
// lsn), never randomly generated (I2).
struct IdempotencyKey { table: TableId, pk_hash: u64, lsn: Lsn }

// OffsetStore / Checkpoint — offset-store crate; Checkpoint persistence: durable,
// CAS-write only (I8, monotonic); concurrency: one writer per (sink_id, partition) at a
// time (P4).
struct Checkpoint { sink_id: SinkId, source_id: SourceId, committed_lsn: Lsn, updated_at: Timestamp }
trait OffsetStore {
    fn commit(&self, cp: Checkpoint) -> Result<(), OffsetRegression>;
    fn read(&self, sink_id: SinkId) -> Option<Checkpoint>;
}

// Router / Transform — router owned by the pipeline-core runtime; stateless per event
// (bounded per-key dedup state only, §1 non-goals); Transform is a pure fn-object, no
// shared mutable state across calls.
trait Router { fn route(&self, e: &ChangeEvent) -> Vec<SinkId>; }
trait Transform { fn apply(&self, e: ChangeEvent) -> Result<ChangeEvent, TransformError>; }
// DeadLetter — owned by sink-runtime on apply failure; persistence: durable in the
// sink-log-backed DLQ (ADR-14); retained 7 days (§4).
struct DeadLetter { event: ChangeEvent, error: ApplyError, first_seen: Timestamp, retry_count: u32 }

// Backpressure — backpressure crate; concurrency: the credit counter is atomic, shared
// across producer/consumer tasks (ADR-16).
struct Backpressure { credits: AtomicI64, threshold: u64 }

// LagMetric — lag-monitor crate; recomputed on a fixed interval (<=1s); a read-only
// snapshot type, no shared mutable state exposed externally.
struct LagMetric { source_id: SourceId, sink_id: SinkId, lag_events: u64, lag_ms: u64 }

// PipelineState — pipeline-core; mutation: single-writer state machine (§8),
// transitions validated (I12); persistence: durable, stored alongside Checkpoint metadata.
enum PipelineState { Snapshotting, Handoff, Streaming, Paused, Resuming, Failed }

// Error taxonomy — pipeline-core; exhaustive; compatibility via wrapping (ADR-24 / §27).
enum PipelineError {
    CaptureError(CaptureError), SchemaViolation, ReplayMismatch, OffsetRegression,
    SinkBackpressure, SerializationFailure, HandoffReconcileMismatch, InvalidStateTransition,
}

  • pg-wal-valid.bin — a known-good pgoutput stream, expected: N frames, a specific LSN sequence.
  • pg-wal-corrupt.bin — a truncated frame, expected: quarantine + CaptureError::TruncatedFrame.
  • pg-wal-split-tcp.bin — a frame split at a byte boundary, expected: correct reassembly.
  • pg-slot-timeout-replay.bin — a heartbeat gap > 30 s, expected: SlotLost transition.

13.6 Pitfalls

  • Treating a Relation message's column list as static — it can change under concurrent DDL (formal Op::Ddl handling is Phase 7, but the parser must not crash on it now).
  • Long-running open transactions holding back the confirmed-flush LSN, inflating slot_wal_bytes even though the connector itself is keeping up — distinguish "connector lag" from "held-open-transaction lag" in telemetry (§26).
  • Off-by-one in LSN byte-order parsing (PostgreSQL LSNs are {high:u32}/{low:u32}) — a documented historical bug class in hand-rolled parsers; verify against the fixture corpus.
  • Assuming a single TCP read yields a whole frame — test explicitly with an artificially small read-buffer size.

13.7 Performance Concerns

  • Per-frame heap allocation for RawFrame — pool/reuse buffers to keep decode latency under the 2 ms p99 target (§4).
  • Syscall density from per-message recv() — batch reads with a buffered reader.
  • Heartbeat-response contention with the main decode loop — run heartbeats on a separate lightweight task, never blocking decode.

13.8 Edge Cases

  • A replication slot already existing from a prior crashed run — attach, don't recreate.
  • Clock skew between connector and source hosts — commit_ts is informational only (ADR-24), never used for ordering, so skew cannot break I1/I4.
  • A source failover to a new primary holding the same slot — detect via a protocol-level reconnect and resume from the last confirmed LSN.

13.9 Failure Analysis

A dropped or corrupted slot is the single highest-severity failure class in the system (T2, FM-2, §25) — it can force a full re-snapshot (Phase 5/6) and, if retained WAL was already large, threatens the source's disk (I10). Detection must be sub-second (heartbeat timeout) and paging, not just logged.

13.10 Operational Notes

Export slot_wal_bytes, capture_lag_seconds, frames_decoded_total, heartbeat_last_ack_ts. This telemetry becomes the backbone of the "two alerts that matter" (§26): slot lag and end-to-end lag both originate here.

14. Phase 2 — Change-Event Decoding & the Envelope

14.1 Objectives

Implement decode-engine: transaction reassembly and RawFrame → ChangeEvent conversion producing the canonical envelope (§8), per the Debezium envelope design (applied per §5).

14.2 Detailed Implementation Steps

  • Implement transaction buffering: accumulate Insert/Update/Delete messages between Begin and Commit, assign event_seq in arrival order (P1, §8).
  • Implement rollback handling: an aborted transaction (no Commit observed) discards its buffered events without emitting them (I3).
  • Implement RowImage construction from pgoutput tuple data, honoring column types from the Relation message (a local best-effort TableSchema cache; formal schema-registry integration is Phase 7).
  • Implement IdempotencyKey derivation (hash(table, pk, lsn), §8/§11), sourcing the primary-key list from the Relation message's replica-identity flag.
  • Implement checksum computation over the encoded envelope (§11 integrity field).
  • Implement a bounded per-transaction memory quota with spill-to-disk overflow for unusually large transactions (a documented DBLog/Debezium pitfall, per §5).
  • Add cargo-fuzz targets (ADR-23) for the frame parser and envelope encoder, replacing Phase 0's fuzz-smoke stub.

14.3 Deliverable

decode-engine consumes capture-postgres's RawFrame stream and emits a correctly ordered ChangeEvent stream, verified against pg-wal-valid.bin at the envelope level.

14.4 Acceptance Criteria

  • Decode latency < 2 ms p99 on the standard fixture corpus (§4, M2).
  • Zero events emitted for an aborted transaction across 1,000 injected-rollback test transactions (I3).
  • Fuzz corpus (fuzz/decode_engine.rs, fuzz/event_parser.rs) runs 1M executions with zero panics/crashes in CI.
  • A 100,000-row transaction (spill-to-disk case) decodes without exceeding the 512 MB per-connector memory ceiling.

14.5 Conformance Fixtures

  • tx-interleaved.bin — two concurrent transactions' frames interleaved, expected: correctly separated per-tx event sets.
  • tx-rollback.bin — a transaction that aborts, expected: zero emitted events.
  • tx-large-100k-rows.bin — spill-to-disk regression fixture.
  • envelope-malformed-checksum.bin — a bit-flipped envelope, expected: SerializationFailure, routed to DLQ (I11 groundwork).

14.6 Pitfalls

  • Assuming replica identity is always FULL — REPLICA IDENTITY DEFAULT omits unchanged columns from the before image on Update, breaking a naive full-row-diff transform; document the actual before-image completeness contract.
  • Spill-to-disk overflow files not cleaned up on crash — orphaned temp files accumulate; add a startup sweep.
  • Checksum computed over a non-canonical field order — non-reproducible checksums across restarts; fix the serialization order once, per P14's spirit, and never change it.

14.7 Performance Concerns

  • RowImage's column map allocating a new HashMap per row — consider a small-map/inline representation for tables with < 16 columns (the common case).
  • Spill-to-disk I/O amplification for large transactions — batch writes, avoid one syscall per row.

14.8 Edge Cases

  • A transaction with a DDL statement only, zero DML rows (Phase 8 formally routes Op::Ddl, but decode must not drop the event here).
  • A table with no primary key (REPLICA IDENTITY NOTHING) — IdempotencyKey falls back to a full-row hash with a documented weaker uniqueness guarantee, flagged in telemetry.
  • Nested savepoints within one transaction — treated as a single flat transaction (savepoint rollback resolves server-side before frames reach the wire).

14.9 Failure Analysis

A tx-reassembly bug (I3 violation) is silent at this phase — no crash, just a wrong-order or missing event — surfacing only later as a differential mismatch (§28). This phase's fixture corpus (14.5) and the "no committed source tx is lost or duplicated" property test (§28) are the primary defenses; a production incident requires deterministic WAL replay (§28) to reproduce.

14.10 Operational Notes

Export tx_reassembly_error_total, spill_to_disk_bytes, envelope_checksum_failures_total. Any nonzero envelope_checksum_failures_total is a page — it indicates either a decode bug or on-the-wire corruption (T4, §24).

15. Phase 3 — First Sink Applier with Idempotent Upsert

15.1 Objectives

Implement sink-runtime's Sink trait and the first concrete applier, sink-db, with the idempotent-upsert half of the exactly-once-effect protocol (§8 steps 3–5; the offset-commit half lands in Phase 4).

15.2 Detailed Implementation Steps

  • Implement the Sink trait (§11) and ApplyResult for sink-db over a connection pool.
  • Implement sink-db's idempotent upsert (INSERT ... ON CONFLICT (pk) DO UPDATE), keyed by the source table's primary key — I2/P2 made concrete for the first time.
  • Implement the sink-local dedup store (a (table, pk, lsn) seen-set), co-located in the same SQL transaction as the upsert where supported (ADR-09) — §8 steps 3–5.
  • Implement router's minimal single-sink routing rule (table → sink-db) as a placeholder; multi-sink routing is Phase 8.
  • Implement batching: group ChangeEvents per table into upsert batches (default 100 rows, §4) to hit the apply-latency SLO.
  • Add the per-key ordering guarantee (I4) inside sink-db: same-key events within a batch apply in LSN order even if the batch arrived out of program order.

15.3 Deliverable

An end-to-end path: mock-source-log (or real capture-postgres) → decode-engine → sink-db, applying inserts/updates/deletes idempotently to a target Postgres table, observable via row-count and checksum comparison against the source.

15.4 Acceptance Criteria

  • Replaying a 10,000-event fixture twice against an empty sink-db target produces identical final state to replaying it once (I2, byte-for-byte row comparison).
  • Apply latency < 10 ms p99 per 100-row batch (§4, M3).
  • A deliberately duplicated LSN range (simulated redelivery) produces zero duplicate rows.
  • sink_dedup_hit_total increments exactly once per intentionally duplicated event.

15.5 Conformance Fixtures

  • apply-insert-update-delete-sequence.bin — a canonical mixed-op sequence with an expected final-state hash.
  • apply-duplicate-lsn-range.bin — a replayed LSN range, expected: zero net duplicate effect.
  • apply-out-of-key-order-batch.bin — same-key events shuffled, expected: LSN-ordered apply regardless of arrival order (I4).

15.6 Pitfalls

  • ON CONFLICT DO UPDATE silently overwriting a newer row with an older one if a stale, out-of-order batch is retried without the I4 defensive reorder — exactly why 15.2's in-sink ordering guarantee exists, not just upstream.
  • Connection-pool exhaustion under batch concurrency — bound pool size explicitly, don't let it float with load (feeds into backpressure design, Phase 9).
  • Treating Delete as a no-op error when the row is already absent (a prior partial apply) — it must be a true no-op, or every crash-resume replay (Phase 4) becomes a false failure.

15.7 Performance Concerns

  • Row-by-row INSERT instead of multi-row batched upserts — batch per the 100-row default (§4) to amortize round-trip cost.
  • Index-maintenance cost on the sink table during high-throughput upsert bursts — document as a sink-side tuning concern, not a pipeline-side one.

15.8 Edge Cases

  • A batch containing both an Insert and a later Delete for the same key — net effect must be "row absent," not "row present then a failed delete."
  • A Truncate op (table-level) — implemented as a sink-side TRUNCATE or bulk delete, must not race with concurrently in-flight per-row upserts for that table.
  • NULL vs missing-column semantics in RowImage — different states, must map to different SQL behavior.

15.9 Failure Analysis

An apply failure here (e.g. constraint violation) is currently fatal to the whole batch — this phase has no DLQ isolation yet (that's Phase 9); document this as a known temporary limitation and surface the batch-level failure in admin-api status, never silently.

15.10 Operational Notes

Export sink_apply_latency_ms (histogram), sink_apply_batch_size, sink_dedup_hit_total, sink_rows_applied_total. These become the model every later sink-* crate (search/ warehouse/log, Phase 8) follows for consistent operator dashboards (§26).

16. Phase 4 — Offset Commit & Crash-Resume by LSN

16.1 Objectives

Implement offset-store's atomic Checkpoint commit and connector-wide crash-resume, completing the exactly-once-effect protocol (§8 steps 6–7; P2, P5, I5, I6, I8).

16.2 Detailed Implementation Steps

  • Implement OffsetStore::commit as a CAS write (I8 — reject any write whose committed_lsn is not strictly greater than the stored value, per row).
  • Implement OffsetStore::read for connector startup, feeding lsn-tracker's resume point (§8 equations).
  • Wire lsn-tracker to compute slot_advance_lsn = min(resume_point(sink)) over AllSinks, issuing the slot advance only after that minimum crosses a checkpointed boundary (I6, P5).
  • Implement the commit-cadence policy (§4: every 1,000 events or 500 ms, whichever first) as a background task independent of the apply hot path.
  • Implement crash-resume: on startup, read the last Checkpoint, reattach the replication slot at that LSN, replay from there — relying on sink-db's I2 dedup (Phase 3) to absorb the replay.
  • Add the resume-gap audit (I5): after resume, compare offset-store's committed LSN against sink-db's dedup store's max recorded LSN; any gap pages.
  • Extend admin-api with /checkpoint (read committed offsets) and /pause//resume stubs (full semantics land with Phase 9's PipelineState wiring).

16.3 Deliverable

A connector that can be killed with SIGKILL at any point during steady-state streaming and, on restart, resumes from the last committed LSN with zero net data loss and zero unbounded duplication (verified against the fixture corpus below).

16.4 Acceptance Criteria

  • 100 randomized kill-and-restart trials against the standard fixture corpus produce a sink final-state hash identical to an uninterrupted run, in every trial (I5).
  • Recovery/resume time < 30 s from process start to PipelineState::Streaming (§4).
  • offset_regression_total remains 0 across all trials (I8).
  • slot_advance_before_commit_total remains 0 across all trials (I6).

16.5 Conformance Fixtures

  • crash-resume-kill-at-n.bin — killing the process after N events, N in {0, 1, 100, 9999, 10000}.
  • checkpoint-cas-conflict.bin — two competing commits with a stale committed_lsn, expected: the stale one rejected (I8).
  • resume-gap-injected.bin — an artificially introduced gap between offset-store and sink dedup state, expected: audit failure detected and alerted.

16.6 Pitfalls

  • Committing the offset before the sink apply is durably acknowledged (violates P5) — a subtle ordering bug that only shows up under crash injection, never under a clean test run; this is why 16.4's kill-and-restart matrix is mandatory.
  • Advancing the slot based on one sink's checkpoint while a second, slower sink hasn't committed yet — violates I6; the min() in 16.2 exists specifically to prevent this.
  • A commit-cadence background task racing the apply hot path on the same in-memory offset cache — use a single-writer discipline (P4) even for offsets local to one connector.

16.7 Performance Concerns

  • Committing on every single event instead of batching per the cadence policy — collapses throughput to the offset-store's write latency; the 1,000-event/500 ms cadence (§4) is a deliberate latency/durability tradeoff (§34).
  • OffsetStore CAS-write contention if multiple sink workers commit concurrently for the same sink_id — serialize per (sink_id, source_id).

16.8 Edge Cases

  • A crash exactly between the offset-store commit and the slot advance (I6's own crash window) — the slot retains slightly more WAL than strictly needed; bounded by I10, never unbounded.
  • A checkpoint read on startup finding no prior checkpoint (first-ever start) — routes to PipelineState::Snapshotting, never attempts a stream resume from LSN 0.
  • Two connector processes accidentally started against the same source (operator error, pre-Phase-10 HA) — detected via a slot-ownership conflict at the source, never a silent double-apply.

16.9 Failure Analysis

A violation of I5 or I6 discovered in production is a correctness incident, not an availability one — data may already have silently diverged. Forensics rely on the resume-gap audit (16.2) and, if insufficient, a full deterministic WAL replay (§28) against the source's retained WAL to reconstruct exactly what should have happened.

16.10 Operational Notes

Export checkpoint_commit_latency_ms, checkpoint_age_seconds (time since the last successful commit — a leading indicator before slot_wal_bytes itself grows), resume_count_total. A rising checkpoint_age_seconds with flat slot_wal_bytes is the earliest signal of an offset-store problem, before the source-side risk (I10) materializes.

17. Phase 5 — The Consistent Snapshot Reader

17.1 Objectives

Implement snapshot-reader: chunked, consistent, lock-minimal bootstrap reads of a table's current rows, laying the groundwork for Phase 6's handoff (ADR-06, DBLog per §5).

17.2 Detailed Implementation Steps

  • Implement chunk selection: partition a table's primary-key range into SnapshotChunks of a configurable target size (default sized to hit the 1M-rows/90s target, §4).
  • Implement the consistent-read query per chunk using the source's native MVCC snapshot (a single SELECT ... WHERE pk BETWEEN ... ORDER BY pk inside one implicit transaction) — no explicit table lock (ADR-06's rejection of lock-based snapshotting).
  • Implement parallel chunk readers (≥10 concurrent, §4) with a bounded worker pool, respecting the same connection-pool ceiling as sink-db (Phase 3) to avoid source overload.
  • Implement SnapshotChunk → ChangeEvent synthesis: each snapshot row becomes an Op::Insert-shaped event carrying a synthetic pre-handoff LSN marker (formally consumed by handoff-coordinator in Phase 6).
  • Implement resumable chunk progress: a crash mid-snapshot resumes from the last fully-read chunk boundary, not from scratch (extends P10 to the snapshot path).
  • Add snapshot throughput telemetry (snapshot_rows_read_total, snapshot_chunks_remaining).

17.3 Deliverable

snapshot-reader reads a full table's current state in parallel chunks, producing a synthetic ChangeEvent stream consumable identically to the streaming path (same envelope type, §8/§11), verified against the source's actual row count and checksum.

17.4 Acceptance Criteria

  • 1M-row table snapshots in ≤ 90 s with ≥10 parallel chunk readers (§4).
  • A snapshot killed at a random chunk boundary and restarted completes with the same final row count as an uninterrupted run.
  • Source connection-pool usage during snapshot never exceeds the configured ceiling under concurrent chunk load.
  • Zero source-side table locks held longer than a single chunk's read duration (verified via pg_locks inspection in the test fixture).

17.5 Conformance Fixtures

  • snapshot-1m-rows.fixture — a 1M-row synthetic table, canonical throughput benchmark.
  • snapshot-crash-mid-chunk-37.bin — a crash injected during chunk 37 of 100, expected: resume from chunk 37, not chunk 0.
  • snapshot-empty-table.fixture — a zero-row table, expected: immediate handoff-ready state, no chunks.
  • snapshot-skewed-key-distribution.fixture — a table with a hot key range, expected: chunk sizing still meets the throughput target.

17.6 Pitfalls

  • Chunking by a fixed row-count offset (LIMIT/OFFSET) instead of a primary-key range — OFFSET paging degrades to O(n²) on a large table and is unsafe under concurrent writes (rows can be skipped or duplicated as the table changes underneath the scan); primary-key range chunking is the DBLog-recommended approach (per §5) for exactly this reason.
  • A chunk boundary landing mid-transaction at the source is not a pipeline problem yet — reconciliation is Phase 6's job; this phase must not attempt to solve it prematurely.
  • Skewed key distributions producing wildly uneven chunk sizes — sample the key distribution before fixed-size chunking, or use adaptive chunk boundaries.

17.7 Performance Concerns

  • Each parallel chunk reader competing for the source's shared buffer cache — cap concurrency below the level that causes cache thrashing (tunable, docs/performance/).
  • Synthetic event synthesis allocating a fresh RowImage per row without pooling — same allocation discipline as Phase 2's decode path applies here.

17.8 Edge Cases

  • A table empty at snapshot start that receives its first row during the snapshot window — must appear correctly via the stream path post-handoff (Phase 6), never missed entirely.
  • A composite (multi-column) primary key — chunk range comparison must use the composite key's defined ordering, not a single column.
  • A chunk read that times out against a slow source — retried with backoff, not treated as a fatal snapshot failure.

17.9 Failure Analysis

A snapshot-reader bug that undercounts or overcounts rows is invisible until Phase 6's reconciliation (I7) or a differential check (§28) catches it — this phase's own acceptance criteria (17.4) are necessary but not sufficient; full correctness is only provable once Phase 6 lands.

17.10 Operational Notes

Export snapshot_rows_read_total, snapshot_chunks_remaining, snapshot_throughput_rows_per_sec. Surface snapshot progress percentage on admin-api for operator visibility during long-running bootstraps of large tables.

18. Phase 6 — The Watermark-Based Snapshot-to-Stream Handoff

18.1 Objectives

Implement handoff-coordinator's DBLog watermark algorithm (§8, named steps 1–5) end-to-end, closing the single hardest correctness gap in the system (P3, I7).

18.2 Detailed Implementation Steps

  • Implement Watermark injection into the live stream buffer at the current LSN, both Low and High kinds (§8 Steps 1/3), coordinated with lsn-tracker so watermarks get real, ordered LSNs, not synthetic ones.
  • Implement the window buffer: stream events for keys within the current chunk's range, arriving between W_lo and W_hi, are held (not forwarded downstream) until reconciliation (§8 Step 4).
  • Implement reconciliation: for each key in the chunk, prefer the window event's image over the snapshot image if a window event exists; emit exactly one image per key (I7).
  • Implement HandoffState transitions (Snapshotting → WindowReconciling → Streaming) per table, independently — one table finishing handoff never blocks another.
  • Implement the post-handoff reconciliation audit (I7 telemetry): compare the emitted row set's count/hash against an independent row-count query at the handoff LSN.
  • Wire router to hold all downstream delivery for a table until that table's HandoffState == Streaming, preventing partial-handoff visibility at sinks.

18.3 Deliverable

A new sink can be bootstrapped from empty and reach full streaming parity with a source table under concurrent write load throughout the entire snapshot, with the worked example from §8 passing as a live integration test.

18.4 Acceptance Criteria

  • A 1M-row table under a concurrent synthetic write workload (mixed insert/update/delete at 1,000 ops/sec) hands off with zero duplicate and zero missing rows, verified by full-table hash comparison (I7).
  • Handoff reconciliation completes within the same wall-clock envelope as the underlying snapshot (§4, no added latency beyond snapshot throughput itself).
  • handoff_reconcile_mismatch_total is 0 across 50 randomized handoff trials with injected concurrent writes at varying rates.
  • A transaction whose commit lands exactly on a chunk boundary during the trial matrix above is resolved correctly in every trial (the §8 worked example, generalized).

18.5 Conformance Fixtures

  • handoff-worked-example.bin — the exact §8 worked example (keys 10/11/12, LSN 100/105/
    1. as an executable regression test.
  • handoff-concurrent-writes-1kops.fixture — the 1,000 ops/sec concurrent-write trial.
  • handoff-boundary-transaction.bin — a transaction spanning a chunk boundary, expected: resolved per-key by newest LSN (I7).
  • handoff-reconcile-mismatch-injected.bin — a deliberately corrupted window buffer, expected: mismatch detected and alerted, never silently accepted.

18.6 Pitfalls

  • Forwarding window events downstream immediately instead of holding them for reconciliation — the single most common naive-implementation bug in watermark-based snapshotting (a documented pitfall of DBLog-style systems, per §5); it causes exactly the "reorder rows crossing a chunk boundary" failure mode called out in the Netflix DBLog reference-impl notes.
  • Choosing the snapshot image over the window image when both exist for a key — backwards; the window event is always newer (Step 4, §8) and must win.
  • Running handoff reconciliation synchronously on the critical decode path, adding latency to unrelated tables' streaming — reconciliation must be scoped per-table and run off the hot path.

18.7 Performance Concerns

  • Window-buffer memory growth if a chunk's read takes unusually long under source load — bound the window buffer and shrink chunk size adaptively when the bound is approached (feeds into Phase 9's backpressure).
  • Reconciliation's per-key lookup cost — use an indexed structure (not linear scan) for the window buffer, since chunk sizes can be large (§4 sizing).

18.8 Edge Cases

  • A Truncate-adjacent operation on a table mid-handoff — treated as an immediate abort-and-restart of that table's handoff (the chunked snapshot's assumptions no longer hold).
  • A key deleted at the source, then a new row inserted with the same primary key, both within one window — reconciliation must resolve to the final state (the insert), not the intermediate delete, by strict LSN order.
  • Two tables handing off concurrently with a foreign-key relationship between them — each table's handoff is independent (P3's scope is per-table); cross-table referential consistency during the handoff window is a documented limitation, not silently assumed away (surfaced in §35, Hard Questions).

18.9 Failure Analysis

A handoff correctness bug is the exact scenario the whole system is at greatest risk from (P3) — it corrupts a sink from its very first moment of existence, silently, and is expensive to detect after the fact (requires a full differential, §28). This phase's reconciliation audit (18.2) is the first line of defense; the correctness-harness (Phase 11, §23) is the second, deeper line.

18.10 Operational Notes

Export handoff_state{table}, handoff_reconcile_mismatch_total, handoff_window_buffer_size, handoff_duration_seconds{table}. Any table stuck in WindowReconciling beyond a configured timeout pages — it indicates either a stalled stream or a reconciliation bug.

19. Phase 7 — Schema Tracking & Evolution Propagation

19.1 Objectives

Implement schema-registry fully: TableSchema/SchemaVersion tracking, compatibility-mode enforcement (ADR-15), and the DDL-gated propagation rule (I9, P7, P8).

19.2 Detailed Implementation Steps

  • Implement SchemaRegistry::propose and resolve (§11) backed by a durable store, replacing Phase 2's local best-effort cache with the authoritative registry.
  • Implement compatibility-mode checking (BACKWARD default, ADR-15) against the schema-evolution decision table (§8): reject a proposed change that would break a locked sink contract (I14).
  • Wire decode-engine's Op::Ddl events (already passed through since Phase 1/2 without being dropped) into SchemaRegistry::propose, completing P8's "DDL is a first-class event" principle.
  • Implement the I9 gate in router: DML for a table is held (bounded by backpressure, I13) until that table's DDL has been applied to the registry.
  • Implement per-sink schema-diff mapping per the §8 decision table (add/drop/rename/ type-change), starting with sink-db's concrete ALTER TABLE translation.
  • Add the grace-period mechanism for drop-column propagation (§8 table) as a configurable delay counted in events, not wall-clock time (so it scales with actual traffic, not idle time).

19.3 Deliverable

An ALTER TABLE orders ADD COLUMN discount_pct numeric issued against the source propagates to sink-db automatically, with DML referencing the new column applied correctly and no DML lost or misapplied during the transition, without a pipeline restart.

19.4 Acceptance Criteria

  • Schema-change propagation latency < 2 s from DDL commit to registry visibility fleet-wide (§4).
  • All four decision-table change types (add/drop/rename/type-widen) verified end-to-end against sink-db, each with a before/after row-count and value-correctness check.
  • Zero schema_incompatible_total false positives against a corpus of 50 real-world-style migration scripts (additive-only changes).
  • A deliberately breaking change (e.g. a narrowing type change) is rejected at the registry with SchemaViolation, not silently applied (I14).

19.5 Conformance Fixtures

  • ddl-add-column.bin / ddl-drop-column.bin / ddl-rename-column.bin / ddl-type-widen.bin — one fixture per decision-table row, each with an expected sink-side DDL translation.
  • ddl-breaking-narrow-type.bin — a narrowing type change, expected: SchemaViolation at the registry boundary.
  • ddl-mid-stream-during-backpressure.bin — a DDL arriving while the pipeline is already backpressured, expected: DDL gate still enforced (I9), no starvation.

19.6 Pitfalls

  • Applying a DDL to the registry but forgetting to gate the specific sink's own schema migration behind it — I9 is about ordering at the registry, not a guarantee that every sink has physically migrated yet; sink-db's own ALTER TABLE must complete before its DML gate releases, a subtlety easy to under-specify.
  • Treating "backward compatible" as "safe to apply immediately" for every sink type — a compatible change at the registry (e.g. add nullable column) can still require a non-trivial backfill at sink-warehouse (§8 table); compatibility and propagation cost are different axes.
  • Grace-period counters reset by a connector restart — must be checkpointed alongside Checkpoint state (Phase 4), not held only in memory.

19.7 Performance Concerns

  • Registry lookups on the DML hot path (router's I9 gate) — cache the current SchemaVersion per table with a short-TTL invalidation on DDL, not a lock-and-fetch per event.
  • Compatibility-mode checking cost scaling with schema size for wide tables — bound check cost, since it sits directly in the DDL-propagation latency budget (§4).

19.8 Edge Cases

  • Two DDL statements on the same table in rapid succession (a batched migration) — each gets its own SchemaVersion; DML between them must reference the intermediate version correctly, not skip to the final one.
  • A DDL statement the parser doesn't recognize (an exotic source-specific extension) — treated as an unrecoverable-by-retry DLQ case (§8), not a crash.
  • A schema change compatible for sink-db but incompatible for sink-search (per-sink divergence) — I14's rejection is per-sink-contract, so the registry supports a DDL being accepted for some sinks and held/rejected for others, never an all-or-nothing decision.

19.9 Failure Analysis

A missed or misapplied DDL is the archetypal cause of "DML referencing an unknown schema" incidents (§8's malformed-example list); this phase's registry-gate telemetry (schema_gate_block_total, schema_incompatible_total) is the primary detection surface, and the runbook docs/runbooks/schema-drift-reconciliation.md (§26) is the primary remediation path.

19.10 Operational Notes

Export schema_version{table}, schema_gate_block_total, schema_incompatible_total, ddl_propagation_latency_ms. Every accepted or rejected DDL is logged with a full before/ after diff for auditability (T7, §24).

20.2 Detailed Implementation Steps

  • Implement each sink's DDL translation per the §8 decision table (mapping mutations, reindex-with-alias, deprecate-don't-drop, dual-field-emission respectively).
  • Implement router's full routing-rule model: table/key → a set of SinkIds, configurable per table, replacing the single hardcoded target.
  • Implement fan-out delivery semantics: a single ChangeEvent is applied independently to each addressed sink, each with its own checkpoint (Phase 4's per-sink Checkpoint model already supports this — this phase exercises it under N>1 for the first time).
  • Implement partial-fan-out-failure handling: one sink's apply failure does not block another sink's apply for the same event (I11 groundwork, ADR-13).
  • Add routing-rule conformance tests: verify a table configured for 3 sinks reaches parity on all 3 independently.

20.3 Deliverable

A single source table replicates simultaneously to sink-db, sink-search, and sink-warehouse, each independently caught up and correctly checkpointed, with DDL correctly propagated to all three per their own translation rules.

20.4 Acceptance Criteria

  • All three sinks reach full parity with the source (checksum match) after a mixed DML+DDL workload, independently verified per sink.
  • A sink-warehouse outage (simulated) does not stall sink-db/sink-search — their checkpoints continue advancing (I11).
  • DDL translation correctness verified per sink type against the §8 decision table's four change types, ×3 sinks = 12 verified combinations.
  • Multi-sink apply latency stays within each sink's own p99 target from §4 — fan-out adds no cross-sink latency coupling.

20.5 Conformance Fixtures

  • multisink-fanout-3-sinks.bin — one workload, three sink targets, expected: independent parity per sink.
  • multisink-partial-outage-warehouse-down.bin — warehouse unavailable mid-run, expected: db/search unaffected.
  • multisink-ddl-matrix.bin — the 12-combination DDL×sink matrix, expected translation per combination.

20.6 Pitfalls

  • Sharing one IdempotencyKey derivation across sinks with fundamentally different natural keys (e.g. search's document id vs the relational primary key) — each Sink implementation must define its own key mapping, not assume the source primary key is universally meaningful.
  • Coupling fan-out delivery order across sinks (waiting for sink A before starting sink B) — defeats I11's isolation goal; fan-out must be concurrent, not sequential, by default.
  • sink-warehouse's batched-merge apply accidentally batching across a DDL boundary (mixing pre- and post-schema-change rows in one merge) — the DDL gate (I9) must apply per-sink, not just at the registry.

20.7 Performance Concerns

  • N-way fan-out multiplying total apply work — document the linear cost explicitly (§31, scalability) rather than let it surprise an operator adding a fourth sink.
  • sink-warehouse's micro-batch merge cost growing with batch size — tune the 5,000-row default (§4) against actual warehouse merge-statement cost.

20.8 Edge Cases

  • A table routed to zero sinks (a misconfiguration) — detected and alerted at config-load time, never silently discarded events.
  • A table routed to the same sink twice via two overlapping routing rules — deduplicated at the router level before fan-out, not left to the sink's own idempotency to silently absorb.
  • sink-log's append-only model receiving a Delete — represented as a tombstone record (§38 glossary), not a physical removal, since the sink is append-only by design.

20.9 Failure Analysis

A routing misconfiguration (missing sink, duplicate sink) is a data-completeness incident that can go undetected for a long time if the misconfigured sink itself looks "healthy" (empty because it never received data, not because it's failing) — admin-api's per-table routing-rule display and periodic row-count cross-checks (§26) are the primary defenses.

20.10 Operational Notes

Export router_fanout_count{table}, sink_partial_failure_total{sink_id}. Dashboards must show per-sink checkpoint lag independently — a fleet-wide average lag metric would mask exactly the "one slow sink" scenario this phase's isolation work exists to handle.

21. Phase 9 — Backpressure, DLQ & Poison-Event Handling

21.1 Objectives

Implement backpressure's credit-based flow control end-to-end (ADR-16, I13) and full DLQ isolation for poison events (P12, I11), replacing Phase 3/8's "batch failure is fatal" placeholder.

21.2 Detailed Implementation Steps

  • Implement the credit protocol: each sink advertises available credit (queue headroom) upstream; decode-engine/router throttle event forwarding when a sink's credit is exhausted (I13).
  • Implement the backpressure-activation threshold (§4: queue depth > 10,000 events or

    64 MB) and the corresponding PipelineState::Paused transition when sustained (§8 lifecycle table).

  • Implement retry-with-backoff for a failing apply (bounded ceiling, ADR-16), then DLQ routing via sink-log's DLQ topic (ADR-14), completing the §8 dead-letter mechanism.
  • Implement DLQ isolation: a poisoned event's table/key is quarantined without blocking unrelated tables/keys in the same batch or stream (I11).
  • Implement immediate (no-retry) DLQ routing for the unrecoverable-by-retry class (schema-validation failures at decode, per §8).
  • Add DLQ replay tooling (tools/dlq-replay) for operator-triggered reprocessing after a root cause is fixed.

21.3 Deliverable

A pipeline that, under a sustained slow-sink condition, throttles smoothly (bounded memory, no crash) and, under a poison-event injection, quarantines only the affected keys while continuing to stream everything else.

21.4 Acceptance Criteria

  • Backpressure activates within one credit-refresh interval (≤500 ms) of a threshold breach (I13), verified by injected slow-sink latency.
  • Max in-flight events under sustained backpressure stays ≤ 50,000 events/node (§4).
  • A poison-event injection affecting 1 key out of 10,000 in-flight keys results in exactly 1 DLQ entry and zero disruption to the other 9,999 (I11).
  • DLQ replay tool successfully reprocesses a quarantined event after a simulated fix, with correct final sink state.

21.5 Conformance Fixtures

  • backpressure-slow-sink-injection.bin — an artificially slowed sink, expected: smooth throttle, no unbounded memory growth.
  • poison-event-isolated-key.bin — one malformed event among many valid ones, expected: isolated DLQ entry, unaffected neighbors.
  • dlq-replay-after-fix.bin — a DLQ'd event replayed post-fix, expected: correct final state.
  • backpressure-sustained-pause-resume.bin — sustained breach triggering Paused, then recovery triggering Resuming → Streaming (§8 lifecycle).

21.6 Pitfalls

  • Credit accounting drifting from actual queue depth under high concurrency (a classic flow-control bug class) — reconcile credit counters against real queue depth periodically, don't trust the counter alone indefinitely.
  • DLQ isolation implemented at too coarse a granularity (whole-table instead of per-key) — defeats I11's intent; verify isolation granularity explicitly in the fixture above.
  • Retry backoff without a ceiling — an indefinitely retrying poison event can starve legitimate work on the same worker pool; the retry ceiling (ADR-16) is not optional.

21.7 Performance Concerns

  • Credit-protocol messaging overhead at high event rates — batch credit updates rather than signaling per-event.
  • DLQ write path competing with the primary apply path for the same sink connection pool — isolate DLQ writes on a separate pool/queue.

21.8 Edge Cases

  • All sinks simultaneously backpressured (a fleet-wide slow period, e.g. a shared network issue) — the pipeline must still make forward progress on decode/order assignment up to the bounded in-flight limit, never deadlock.
  • A poison event that is poison specifically because of a bug in transform-engine (not the data itself) — a bad deploy can convert an entire table's worth of otherwise-valid events into poison; the retry ceiling must not mask this as "just some bad data," and dlq_depth's rate-of-growth (not just its value) must be alertable.
  • Backpressure activating during an in-progress handoff (Phase 6) — the handoff's window buffer must respect the same bounds, never be treated as exempt.

21.9 Failure Analysis

A stuck pipeline (the "poison event stalls everything" failure mode) is exactly the DoS-class risk named in the threat model (T6, §24); this phase's isolation guarantees are the structural defense, and docs/runbooks/stuck-pipeline-poison-event.md (§26) is the operator-facing remediation path when isolation itself has a bug.

21.10 Operational Notes

Export backpressure_active{stage}, credit_available{sink_id}, dlq_depth{table}, dlq_growth_rate, retry_count_histogram. dlq_depth and end-to-end lag are the two metrics an on-call engineer checks first when a "why is nothing moving" page fires.

22. Phase 10 — Distributed HA, Connector Rebalancing & Slot Management

22.1 Objectives

Implement fleet mode (ADR-17): multiple connector processes coordinating slot ownership, rebalancing, and fleet-wide schema-registry state via the external coordination store (ADR-19), plus the active slot-retention safeguard (I10, P13, T2).

22.2 Detailed Implementation Steps

  • Implement lease-based slot ownership: exactly one connector process holds the lease for a given source's slot at a time (P4), renewed on the coordination store, with a bounded lease-expiry-triggered failover.
  • Implement rebalancing: when a connector joins/leaves the fleet, table-level ownership (for a sharded-by-table deployment) redistributes without dropping in-flight checkpoints (extends Phase 4's per-sink Checkpoint model to per-(table,sink)).
  • Implement the active slot-retention safeguard: when slot_retained_wal_bytes (I10) crosses the alert threshold (§4), automatically throttle-alert and, at the hard-abort threshold, force a controlled slot drop with alerting (never silently) rather than let the source's disk fill.
  • Implement fleet-wide schema-registry replication so every connector observes the same SchemaVersion for a table regardless of which connector currently owns it.
  • Implement failover: a lease expiring without renewal (crashed node) triggers another fleet member to acquire it and resume from the last committed Checkpoint (Phase 4's crash-resume, now cross-process).
  • Add fleet-topology observability: admin-api's /fleet/status listing every connector, its owned sources/tables, and lease health.

22.3 Deliverable

A 3-node connector fleet that survives a node kill: the affected source's ownership fails over to another node within the lease-expiry window, streaming resumes from the last committed checkpoint, and no other node's ownership is disturbed.

22.4 Acceptance Criteria

  • Failover completes within 30 s of lease expiry (§4-consistent RTO target).
  • Zero dual-ownership windows observed across 50 randomized node-kill trials (P4/I6 consistency under HA).
  • Coordination-store QPS stays ≤ 2,000 at a simulated 100-connector fleet size (§4).
  • A slot crossing the hard-abort WAL threshold triggers a controlled, alerted drop — never a silent one — in 100% of injected trials.

22.5 Conformance Fixtures

  • fleet-node-kill-failover.bin — a 3-node fleet, one node killed, expected: failover within 30 s, no dual ownership.
  • fleet-rebalance-node-join.bin — a 4th node joining, expected: table ownership redistributes without checkpoint loss.
  • slot-wal-hard-abort-trigger.bin — retained WAL crossing the hard-abort threshold, expected: controlled, alerted slot drop.
  • fleet-coordination-store-qps-100nodes.fixture — simulated 100-connector load, expected: QPS within budget.

22.6 Pitfalls

  • Lease renewal racing with a rebalance decision — a connector renewing its lease at the exact moment a rebalance reassigns its table produces a brief dual-write window unless renewal and reassignment share the same coordination-store transaction/CAS primitive.
  • Treating slot ownership and table ownership as the same lease — a fleet sharded by table still has exactly one slot reader per source (P4), but table-level sink ownership can be finer-grained; conflating them causes unnecessary failovers.
  • Auto-dropping a slot at the hard-abort threshold without first attempting a throttle/alert step at the softer threshold — the alert threshold (§4, 10 GB) exists precisely to give an operator a window to intervene before the destructive hard-abort (50 GB) fires.

22.7 Performance Concerns

  • Coordination-store QPS growing linearly with fleet size and lease-renewal frequency — tune renewal interval against the QPS budget (§4), don't renew more often than the lease expiry actually requires.
  • Fleet-wide schema-registry replication latency under high DDL churn — bound propagation latency (§4, 2 s) even as fleet size grows.

22.8 Edge Cases

  • A network partition splitting the fleet such that two sub-fleets each believe they hold a lease (split-brain) — the coordination store's own consensus (not this pipeline) is the authority; the pipeline must treat a lease it cannot renew as lost, never assume it still holds it.
  • A rebalance triggered while a table is mid-handoff (Phase 6) — handoff state must migrate with the table's ownership, not restart from scratch on every rebalance.
  • A coordination-store outage — connectors must fail safe (stop advancing, do not guess at ownership) rather than fail open (assume ownership and risk dual-write).

22.9 Failure Analysis

Dual ownership is the single worst HA failure mode — it violates P4 and can cause I4/I6 violations at the sink. This phase's lease-renewal-plus-rebalance atomicity (22.2, 22.6) is the structural defense; docs/runbooks/slot-bloat-emergency.md and a fleet-status dashboard (§26) are the operator-facing tools when a lease anomaly is suspected.

22.10 Operational Notes

Export lease_holder{source_id}, lease_renewal_latency_ms, rebalance_count_total, coordination_store_qps, slot_wal_bytes (carried over from Phase 1, now fleet-aggregated). The fleet-status view on admin-api is the first place an on-call engineer checks during a suspected split-brain incident.

23. Phase 11 — Correctness Harness, Conformance & Performance Hardening

23.1 Objectives

Implement correctness-harness: a Jepsen/Elle-style fault-injected end-to-end verifier (applied per §5, Kingsbury's Jepsen analyses) proving the sink converges to the source under adversarial conditions, plus the final conformance and performance-regression gates.

23.2 Detailed Implementation Steps

  • Implement a synthetic source workload generator (mixed insert/update/delete/DDL at configurable rates) driving the full pipeline end-to-end.
  • Implement fault injection: kill the connector mid-snapshot, drop the replication slot, fail a sink apply, partition the offset store, inject a schema change mid-stream — each a named scenario exercised by the harness (§28).
  • Implement the differential checker: after a workload run (with injected faults), compare the sink's final state to the source's final state; assert exact convergence (I1–I14 as the assertion set, §7).
  • Implement Elle-style dependency-trace visualization for a failed run, so a violated invariant is diagnosable from the trace, not just a boolean fail.
  • Wire the harness into CI as a named gate (ci/e2e-correctness), blocking merge on any invariant violation (§28).
  • Implement the final performance-regression suite (Criterion benchmarks, §30) gated against the M-target table (§30) in CI.
  • Implement deterministic WAL replay tooling (tools/replay) for reproducing a specific production incident from a recorded WAL segment.

23.3 Deliverable

A CI-gated correctness harness that runs the full fault-injection matrix nightly (and on every release-candidate build) and blocks release on any invariant violation; a performance-regression suite blocking release on any M-target miss.

23.4 Acceptance Criteria

  • The full fault-injection matrix (6 named scenarios × 3 workload profiles) passes with zero invariant violations across 20 consecutive nightly runs before this phase is considered complete.
  • Deterministic replay of a recorded WAL segment reproduces byte-identical sink state across 3 independent replay runs.
  • Every M-target in §30's table is met on the reference hardware profile documented in docs/performance/.
  • ci/e2e-correctness blocks a deliberately introduced regression (a mutation-tested I2 violation) in a canary CI run.

23.5 Conformance Fixtures

  • harness-fault-matrix-6x3.fixture — the full 6-scenario × 3-profile fault-injection matrix.
  • harness-mutation-i2-violation.bin — a deliberately broken dedup check, expected: the harness catches it (validates the harness itself, not just the pipeline).
  • replay-recorded-incident-2026-postmortem.wal — a recorded WAL segment from a real (or realistic synthetic) incident, used for deterministic reproduction drills.

23.6 Pitfalls

  • A correctness harness that only checks final-state convergence without also checking per-key ordering (I4) mid-run — a bug that self-corrects by the end of the run (e.g. a transient reorder later overwritten) would pass a final-state-only check while still being a real defect; the trace-based Elle-style check (23.2) exists to catch exactly this.
  • Fault injection that is too gentle to be meaningful (e.g. always killing at a quiet point in the workload) — randomize injection timing against the workload's own event clock, not wall-clock time, so faults land mid-transaction and mid-handoff, not just between them.
  • Treating a harness pass as permanent — re-run the full matrix on every release candidate (23.3), not just once at this phase's completion, since regressions can reappear.

23.7 Performance Concerns

  • The fault-injection matrix's own runtime cost (nightly CI budget) — parallelize scenarios, cap total nightly runtime, and reserve the full matrix for release candidates if nightly budget is tight.
  • Deterministic replay's I/O cost for large recorded WAL segments — stream the replay rather than loading the full segment into memory.

23.8 Edge Cases

  • A fault injected during another fault's recovery window (compound failure, e.g. a sink outage during a fleet rebalance) — the harness must support composing scenarios, not just running them in isolation, since real incidents compound.
  • A workload that never triggers backpressure (Phase 9) — the harness must include a profile specifically engineered to saturate backpressure, or that whole subsystem goes untested by this gate.
  • A flaky harness result (non-deterministic due to a timing-dependent bug rather than the fault injection itself) — flakiness in a correctness harness is itself a bug to root-cause, never suppressed with a retry-until-green policy.

23.9 Failure Analysis

A harness failure at this phase is the last line of defense before a release — it is treated with the same severity as a production incident, with a mandatory root-cause writeup in docs/failure-analysis/ before the release candidate proceeds, per the debugging methodology closing §7.

23.10 Operational Notes

Export harness_run_result{scenario}, harness_invariant_violation_total{invariant_id}, perf_regression_detected{metric_id}. The harness's own dashboard becomes part of the release-readiness checklist alongside the standard operational dashboards (§26).

26. Operational Readiness

Named metrics (fleet-wide, aggregated from every phase's per-phase exports, §12–§23): end_to_end_lag_ms (p50/p95/p99), slot_retained_wal_bytes (the leading source-health indicator, I10), events_per_second, sink_apply_errors_total, dlq_depth/ dlq_growth_rate, schema_change_events_total, checkpoint_commit_latency_ms/ checkpoint_age_seconds, backpressure_active, lease_renewal_latency_ms (fleet mode).

Tracing: every ChangeEvent carries a trace context propagated from capture-* through to the final sink apply (P11); a single trace spans decode → order → transform → route → apply, letting an operator follow one event's full path.

Structured logging (ADR-21): JSON only, mandatory fields source_id, table, lsn, trace_id, error_class on every warning/error log line — never free-text-only errors.

Dashboards: per-source and per-sink lag broken out independently (never a fleet-wide average that masks a single slow component, §20.10); slot health (slot_retained_wal_bytes trend); DLQ depth and growth rate; handoff progress for any table currently bootstrapping; fleet topology (Phase 10).

Alerting philosophy: slot lag and end-to-end lag are the two alerts that matter. Every other metric is diagnostic once one of those two fires. slot_retained_wal_bytes crossing the 10 GB alert threshold (§4) is a source-protection page (T2, I10); end-to-end lag p99 crossing 5 s (§4) is a pipeline-health page. All other alerts (schema incompatibility, DLQ growth, lease anomalies) are secondary and page only on sustained breach, not a single sample.

SLOs: 99.95% availability (§4-consistent), RTO ≤ 2 minutes, RPO 0 events lost in effect (I2/I5). An SLO breach triggers the incident-response process below, not just a dashboard annotation.

Incident response: on a slot-lag or end-to-end-lag page, the on-call engineer's first action is admin-api's /fleet/status and /checkpoint — the two views that answer "is this a source problem, a connector problem, or a sink problem" fastest. Escalation to the relevant runbook follows.

Named runbooks (docs/runbooks/):

  • slot-bloat-emergency.md — I10 breach response, controlled slot-drop procedure.
  • stuck-pipeline-poison-event.md — DLQ triage, tools/dlq-replay usage (§21).
  • snapshot-restart.md — resuming a crashed or corrupted snapshot (§17).
  • schema-drift-reconciliation.md — FM-7 remediation (§19, §25).
  • sink-failover.md — recovering a sink outage without stalling unaffected sinks (§20/§21).
  • offset-rewind.md — operator-initiated rewind for a bad deploy or corrupted downstream state, using offset-store's CAS write (I8) under explicit operator authority (a logged, audited override of the normal monotonicity guard).

Backup/restore: offset-store and schema-registry are backed up on the same cadence as any durable metadata store; a restore replays from the restored checkpoint, relying on I2/I5 to absorb any resulting replay.

Deployment topology: one connector process per source, a fleet coordinator (Phase 10) for multi-connector deployments; sinks are independently deployed and scaled from the pipeline itself.

Canary/rollback/migration: a new connector version deploys to a canary source first, validated against the correctness-harness's lighter-weight smoke profile (§23) before fleet-wide rollout; rollback is a version downgrade plus a checkpoint-compatible resume (§27); migrations follow the compatibility rules in §27.

27. Compatibility & Versioning

Event-envelope versioning: the ChangeEvent envelope (§8/§11) is additive-only (P14) — new fields are optional, ignorable by older consumers; a breaking change requires a major envelope version, negotiated at connector startup, never silently.

Schema-registry compatibility modes: BACKWARD (default), FORWARD, FULL, and NONE, per Avro/Confluent Schema Registry semantics (applied per §5) — configurable per table, enforced at I14's compatibility check.

Source-version support matrix: PostgreSQL 12+ (logical decoding with pgoutput requires 10+; this system targets 12+ for stable replica-identity behavior); MySQL 5.7+/8.0+ (row-based binlog format ROW, binlog_row_image=FULL required for complete before-images).

Offset format versioning: Checkpoint's on-disk/wire format is versioned independently of the envelope; an offset-store migration tool converts old-format checkpoints on upgrade, never silently misreading them as LSN 0.

Sink-connector API stability: the Sink trait (§11) is the stability boundary for third-party sink implementations — SemVer 2.0.0 applies to the trait itself; a minor version may add a default-implemented trait method (non-breaking); a major version may change the trait's required methods.

Migration: a schema-evolution change follows the §8 decision table per sink; a connector-version migration follows the canary path in §26.

Deprecation: a deprecated envelope field or Sink trait method is marked and supported for at least one major version cycle before removal, per SemVer.

Rolling-upgrade guarantees: within one major version, an old connector and a new connector can both be in a fleet simultaneously (Phase 10) without producing inconsistent sink state, because envelope additivity (P14) and offset-format backward-compatibility hold across the upgrade window.

28. Testing & Verification Strategy

Unit: per-crate logic (LSN comparison, envelope field encoding, credit-counter arithmetic) — every crate in §10 carries its own unit suite.

Integration: cross-crate paths exercised via docker-compose fixtures (§12.3) — capture-postgres → decode-engine → sink-db is the canonical integration path, extended per phase.

Property tests, tied to invariants (§7):

  • "No committed source transaction is lost or duplicated in effect at the sink" (I2, I3) — driven by randomized transaction workloads against the Phase 2/3 fixture corpus (14.5, 15.5).
  • "Per-key order at the sink matches source-LSN order" (I4) — driven by apply-out-of-key-order-batch.bin (15.5) generalized to randomized shuffles.
  • "A resume from any committed offset neither replays nor drops an effect" (I5) — driven by crash-resume-kill-at-n.bin (16.5) generalized across the full fixture corpus.
  • "The snapshot+stream handoff yields exactly the handoff-LSN row set" (I7) — driven by handoff-worked-example.bin and handoff-concurrent-writes-1kops.fixture (18.5).

Differential testing: after any workload, compare the sink to the source; they must converge (byte-for-byte row/document/record equality) — the correctness-harness's core check (Phase 11, §23).

ci/e2e-correctness — the named CI gate: a Jepsen/Elle-style end-to-end correctness harness (Kingsbury's Jepsen analyses, applied per §5) runs a source workload through the full pipeline under fault injection and checks the sink is a correct replica; every I1–I14 is an assertion in this harness (§7, §23). This gate blocks merge to main and blocks any release candidate.

Fuzzing (ADR-23): fuzz/decode_engine.rs and fuzz/event_parser.rs target the log decoder and event parser directly, since they sit on untrusted network bytes (T4, §24); a 1M-execution corpus runs in CI (14.4).

Chaos (Phase 11's fault-injection matrix, §23.2): kill the connector mid-snapshot, drop the replication slot, fail a sink apply, partition the offset store, inject a schema change mid-stream — each named and composable (23.8).

Deterministic replay: tools/replay reproduces a specific recorded WAL segment byte-for-byte across runs (23.4), used both for incident reproduction and as a standing regression check.

Soak: a 1-hour continuous-ingest run (13.4) at sustained throughput (§4) with zero LSN regressions, extended to a multi-day soak before a major release.

Fault injection: see Chaos above; every named scenario maps to a Phase 11 fixture (23.5).

Performance-regression gating: Criterion benchmarks (§30) gated against the M-target table in CI, blocking a release candidate on any miss (23.4, ADR-23).

29. Build & Release Engineering

Reproducible builds: a locked Cargo.lock, a pinned rust-toolchain.toml, and a hermetic build environment ensure byte-identical artifacts from the same source commit.

Artifact signing: every release artifact (container image, binary) is signed (cosign/sigstore-class tooling); the signature is verified by the deployment pipeline before rollout.

SBOM: generated per release (cargo-cyclonedx-class tooling), covering every crate dependency, feeding the dependency-audit gate (§24, T10).

Release channels: nightly (every main commit, unsupported), candidate (tagged release candidate, runs the full Phase 11 fault-injection matrix), stable (promoted from a candidate that passed 20 consecutive nightly harness runs, §23.4), LTS (a stable release receiving backported fixes only).

CI/CD topology: lint (cargo fmt/clippy) → unit/integration test → fuzz-smoke → ci/e2e-correctness (the Jepsen/Elle gate, §28) → performance-regression gate (§30) → packaging → signing → SBOM generation → publish.

Version stamping: every build embeds its git SHA, build timestamp, and dependency-lock hash, exposed on admin-api's /version (Phase 0, §12.10).

Provenance/attestation: build provenance (an SLSA-style attestation) records the exact CI job, inputs, and toolchain version that produced each signed artifact.

Dependency auditing: cargo audit runs on every CI build (T10, §24); a new advisory affecting a pinned dependency blocks merge until triaged.

31. Scalability Analysis

What stays constant: per-event decode cost (O(1) amortized per frame, Phase 2); IdempotencyKey derivation cost (O(1) hash); the credit-protocol's per-signal cost (O(1), Phase 9).

What grows: decode throughput scales linearly with WAL bytes/sec (Phase 1) — the source's own single-writer WAL is the ultimate throughput ceiling (P1's flip side: the log is authoritative, and it is also serial); snapshot time scales linearly with table size divided by chunk parallelism (Phase 5, O(n/k)); coordination-store QPS scales with fleet size × lease-renewal frequency (Phase 10, roughly O(fleet_size)); DLQ storage scales with poison-event rate × retention window (Phase 9).

Named bottlenecks, in order: (1) the source's single-writer WAL — no amount of pipeline parallelism increases the rate at which the source itself produces log bytes; (2) per-key ordering (I4/P9) — parallelizing sink apply across keys is safe, but a hot key serializes; (3) the coordination store at very large fleet sizes (Phase 10, M11); (4) a single slow sink's backpressure signal propagating upstream (Phase 9) and throttling the whole connector, even though other sinks could go faster.

Horizontal scaling: additional connector processes shard by source (one source per connector, always) and, within fleet mode, by table for sink-ownership (Phase 10); this does not increase a single source's own WAL production rate.

Vertical scaling: more CPU/memory on one connector node raises its decode/apply concurrency ceiling up to the point where the source's WAL production rate or a hot key's serialization becomes the limit instead.

Sharding: by table (Phase 10's rebalancing) for sink ownership; by source (always, one connector per source) for capture.

The slot-lag feedback limit: if sinks fall behind the source's write rate for long enough, slot_retained_wal_bytes (I10) grows until the hard-abort threshold (§4, 50 GB) forces a re-snapshot — this is the system's hard practical ceiling, not a soft degradation; it is the mechanism, not a bug, that prevents unbounded source-side risk (P13).

Practical ceilings and levers beyond them: a single source's throughput ceiling is fixed by its own WAL production rate — the only lever is reducing per-event pipeline latency (faster decode/apply) to keep slot_retained_wal_bytes flat, not increasing raw throughput past what the source produces; a fleet's aggregate ceiling is the sum of its per-source ceilings, scaled by adding more sources (never more connectors per one source, since P4 forbids that); the coordination-store ceiling (M11) is addressed by sharding the coordination store itself, deferred beyond this blueprint's baseline design (§37).

32. Mental Models & First Principles

MM1 — CDC is the database's write-ahead log escaping the database. Everything downstream is a materialized view over that log (Kreps). Predicts: every sink is a different materialization strategy of the same log, not a bespoke integration. Bug class without it: treating each Sink as a one-off instead of a uniform trait over one canonical stream. Applies in §8, §11.

MM2 — Exactly-once delivery is a myth; exactly-once effect is achievable. The trick is always idempotence plus atomic offset commit, never a cleverer transport (Helland). Predicts: any "exactly-once" claim not backed by an idempotency key and an atomic commit boundary is wrong. Bug class without it: chasing transport-level guarantees that don't exist instead of building idempotent apply. Applies in §8, §16, P2.

MM3 — The LSN is the only clock that matters. Wall-clock timestamps are for humans, not ordering (Lamport). Predicts: a bug blamed on host clock skew is a red herring if the pipeline correctly orders by LSN, not commit_ts. Bug class without it: subtle reordering under multi-host clock skew. Applies in §8, §11, ADR-24.

MM4 — The snapshot-to-stream handoff is the one place a replica can silently diverge. It deserves more test effort than the whole streaming path (DBLog). Predicts: an under-tested handoff is the most likely source of "my new sink doesn't match the source." Bug class without it: a naive lock-based or fixed-cutover snapshot silently drops/duplicates rows under concurrent writes. Applies in §8, §17, §18.

MM5 — A replication slot is a liability the source carries on the pipeline's behalf. Every second of pipeline lag is a second of the source's disk at risk (a DBLog/Databus operational lesson). Predicts: watching only pipeline-side lag metrics leaves an operator blindsided by a source-side outage. Bug class without it: alerting on end-to-end lag alone and missing the slot-retention risk until the source pages first. Applies in §4, I10, §26.

MM6 — Schema is just another stream. DDL is data about data and must be ordered exactly like every other event (Debezium's envelope design). Predicts: any system treating DDL as an out-of-band side channel will eventually apply DML against the wrong schema version. Bug class without it: a race between a schema migration and in-flight DML. Applies in §8, §19.

MM7 — Per-key order is the invariant; global order is a convenience. Relax the convenience for throughput, never the invariant (Bernstein & Goodman). Predicts: naive "just parallelize by shard" designs that drop per-key order will corrupt data under concurrent updates to the same row. Bug class without it: a delete-then-insert on the same key applying out of order under parallel apply. Applies in §8, §20, §31.

MM8 — Backpressure is a contract, not an accident. An unbounded queue anywhere is a promise the system cannot keep (a queueing-theory first principle). Predicts: any component without an explicit bound eventually becomes the one that exhausts memory under a slow downstream. Bug class without it: unbounded growth cascading into a replication-slot bloat incident. Applies in §21, I13, P6.

34. Back-of-Envelope Capacity Model

  1. End-to-end lag budget = decode + transport + apply = 2 ms (M2) + 10 ms (intra-region network, §4) + 10 ms (M3, sink-db worst case) = 22 ms typical — roughly 9x headroom under the 200 ms p50 target (§4), the remainder absorbed by batching/queueing delay.

  2. Slot retained-WAL growth if the pipeline stalls = source_write_rate × avg_event_size × stall_duration. At 50,000 events/sec (M1) × 500 bytes/event = 25 MB/s WAL production. Time to the 10 GB alert threshold (§4, I10) = 10×10⁹ / 25×10⁶ = 400 s (≈6.7 min); time to the 50 GB hard-abort = 50×10⁹ / 25×10⁶ = 2,000 s (≈33 min).

  3. Snapshot wall clock = (rows × per_row_read_time) / chunk_parallelism. From the §4 target (1M rows / 90 s at 10 workers): per_row_read_time ≈ (90 s × 10) / 1,000,000 = 0.9 ms/row/worker. A 10M-row table at the same parallelism: (10,000,000 × 0.9 ms) / 10 = 900 s (15 min).

  4. Throughput ceiling from the single-writer source log = source_wal_bandwidth / avg_event_size. At a typical NVMe-backed OLTP write ceiling of ~100 MB/s: 100×10⁶ / 500 = 200,000 events/sec — 4x this pipeline's own per-connector target (M1), meaning the pipeline's decode/apply path, not the source, is the binding constraint at that hardware profile until the fleet scales out (§31).

  5. Offset-commit overhead vs lag = commit_latency / (commit_cadence_events). At the 500 ms/1,000-event cadence (§4) and 50,000 events/sec, each commit batches ≈25,000 events; at a 5 ms commit latency, per-event overhead = 5 ms / 25,000 = 0.0002 ms/event — negligible next to the 2 ms decode latency, validating the cadence choice (§16.7).

  6. Sink apply workers needed to keep up = source_rate / (batch_size / batch_latency). At the sink-db target (100 rows / 10 ms, M3): 100/0.01 = 10,000 rows/sec/worker; to sustain 50,000 events/sec (M1) requires ≥5 concurrent apply workers.

  7. DLQ growth under a poison-event rate = event_rate × poison_rate × avg_dlq_entry_size. At an isolated-bug rate of 0.01% (1/10,000) and 50,000 events/sec: 5 events/sec × 2 KB = 10 KB/s (≈864 MB/day) — comfortably inside the 5 GB/7-day budget (§4). At a systemic 1% rate (FM-10): 500 × 2 KB = 1 MB/s (≈86.4 GB/day), blowing the budget within 90 minutes — the exact reason dlq_growth_rate, not just dlq_depth, must be alertable (§21.10, §25).

  8. Memory for in-flight events under backpressure = max_in_flight_events × avg_event_footprint. At the 50,000-event/node bound (§4) and ~1 KB/event: 50,000 × 1 KB = 50 MB — well inside the 512 MB per-connector ceiling, leaving headroom for the window buffer (Phase 6) and connection-pool overhead.

  1. Why is "exactly-once delivery" an incorrect claim for this system, and what does the pipeline actually guarantee instead? (§8, §16)
  2. Walk through a crash immediately after step 4 (idempotent upsert) but before step 5 (recording the dedup key) in the exactly-once-effect sequence table — why is the net effect still correct? (§8, §16)
  3. Why does the slot advance use min() across all sinks rather than any single sink's committed offset? What breaks with max() instead? (§8, I6)
  4. Why is primary-key-range chunking preferred over LIMIT/OFFSET paging for the snapshot reader, and what concretely goes wrong with OFFSET under concurrent writes? (§17, §5)
  5. In the DBLog watermark handoff, why must a window event always win over the corresponding snapshot image, never the reverse? Construct the resulting failure if reversed. (§8, §18)
  6. Why is DDL modeled as a first-class ordered stream event rather than an out-of-band side channel, and what incident class does this prevent? (§8, §19, FM-7)
  7. The system relaxes global LSN order to per-key order for sink-apply parallelism. Why is this relaxation safe, and what invariant breaks if relaxed further to no ordering guarantee at all? (I4, §31)
  8. Why does a replication slot represent a source-side risk rather than a pipeline-side inconvenience, and what two-threshold mechanism contains that risk? (I10, T2, §22)
  9. Compare the crash-window analysis at step 4 vs step 6 of the exactly-once-effect sequence table — why is a crash at step 6 recoverable without data loss, but a naive implementation without idempotent apply would not be? (§8, §16)
  10. Why does schema-compatibility enforcement happen at the registry boundary rather than at each sink, and what breaks with a per-sink-only design? (ADR-10, §19)
  11. Why are transform-engine failures DLQ'd rather than retried indefinitely, and how does this connect to the poison-event denial-of-service threat? (§8, §21, T6)
  12. Why is the coordination-store QPS bound a function of fleet size and lease-renewal frequency, and what two independent levers keep it under budget as the fleet grows? (§22, §31, §34)
  13. If a table's handoff is interrupted by a Truncate, why must the handoff abort and restart rather than reconcile the truncate into the window buffer? (§8, §18.8)
  14. Why does this design reject two-phase commit as the default exactly-once mechanism, and under what sink condition would 2PC actually be correct? (ADR-08)
  15. Why is a fleet-wide average lag metric rejected as a dashboard design in favor of per-source/per-sink breakdowns, and what failure would an average mask? (§20.10, §26)
  16. Why is commit_ts excluded from the ordering model despite being in every envelope, and what bug appears if a future engineer "optimizes" ordering to use it? (§8, §11, ADR-24, MM3)

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Trigger-Based Capture

Source DB
  +-------------------+
  | Application write  |
  +---------+---------+
            v
  +-------------------+       +----------------------+
  | Table (row)        |------>| AFTER trigger          |
  +-------------------+       | writes a shadow row     |
                               +-----------+----------+
                                           v
                               +----------------------+
                               | Shadow "changes" table |
                               | (same database)         |
                               +-----------+----------+
                                           v
                               +----------------------+
                               | Poller reads shadow     |
                               | table, ships events      |
                               +----------------------+

Winning regime: sources with no logical-decoding/binlog access at all, or where DB-portability across many different engines matters more than write-path overhead. Real embodying system: homegrown "audit table" ETL pipelines and CDC tools for databases lacking log access. Rejected here because it adds synchronous write latency to every source transaction and — critically — cannot capture DDL, which §8/§19's schema-evolution propagation depends on as a first-class ordered event (P8); a trigger-based source would need an entirely separate, unreliable DDL-detection mechanism.

Alternative 2 — Query-Based Polling on an updated_at Column

  +-------------------+
  | Poller (interval)  |
  +---------+---------+
            v
  SELECT * FROM t WHERE updated_at > last_poll_ts
            v
  +-------------------+
  | Emit as events      |
  +-------------------+

Winning regime: sources with genuinely no log/trigger access, where near-real-time (not sub-second) latency is acceptable and hard deletes are rare or soft-deleted. Real embodying system: many SaaS-API-based connectors with only a REST endpoint and an updated_at filter (e.g. early Airbyte incremental-sync connectors, §5). Rejected here because it cannot detect hard deletes without a separate tombstone convention, has a latency floor bounded by the poll interval (violates the p50 < 200 ms target, §4), and cannot preserve per-transaction atomicity — two rows updated in the same source transaction can land in different poll windows, breaking I3.

Alternative 3 — Durable Log (Kafka) as the Transport Backbone

  Source -> capture -> decode -> [[ durable log/Kafka topic ]] -> sink-connectors
                                          |
                          durable, replayable, multi-consumer fan-out

Winning regime: multiple independent consumer teams need durable, replayable fan-out of the same change stream, or capture and sink-apply must scale/fail independently at large organizational scale. Real embodying system: Kafka Connect / Debezium's own deployment model (§33). Rejected as the default here (though supported optionally, ADR-18) because it adds an extra hop and an extra system to operate for the common single-team, single-pipeline case this design optimizes for by default; the direct in-process path meets the p50/p95/p99 lag targets (§4) with less operational surface area, and via-log remains available for the regime above.

Alternative 4 — Dual-Write (the Anti-Pattern)

  Application code
     |          |
     v          v
  Source DB    Sink DB      <- two independent writes, no shared commit boundary

Winning regime: none — named specifically as the anti-pattern to reject, not a legitimate alternative. Real embodying system: an extremely common but incorrect pattern in application code that writes to its primary database and a secondary system (cache, search index) in the same request handler with no log-based reconciliation. Rejected here because the two writes have no atomicity relationship — a crash between them, or a reordering under retries, produces permanent, silent divergence with no mechanism to detect or repair it; this is precisely the "dual-write inconsistency" this entire project exists to replace with a single source of truth (the log) and a total order derived from it (P1).

38. Glossary

  1. Change Data Capture (CDC) — the practice of identifying and capturing row-level changes made to a database so they can be propagated elsewhere.
  2. Write-Ahead Log (WAL) — the durable, append-only log a database writes before applying a change; the authoritative record this pipeline tails.
  3. Logical Decoding — PostgreSQL's mechanism for interpreting WAL bytes as a stream of logical row-level changes, rather than physical page changes.
  4. Replication Slot — a PostgreSQL server-side object retaining WAL until a consumer confirms processing it; the mechanism behind the slot-retention risk (I10).
  5. LSN (Log Sequence Number) — the monotonic position of a change within the source's log; this system's total-order key (P1).
  6. Binlog — MySQL's write-ahead-log equivalent, read in row-based format for CDC.
  7. Oplog — MongoDB's operation log; the log-based capture source for a MongoDB connector (deferred, §37).
  8. Change Event — the canonical unit this pipeline emits per source mutation (§8).
  9. Before Image — a row's state prior to a mutation, carried in ChangeEvent.before.
  10. After Image — a row's state following a mutation, carried in ChangeEvent.after.
  11. Tombstone — a marker record representing a deletion in an append-only sink that cannot physically remove data (§20.8).
  12. Snapshot — a consistent, point-in-time read of a table's current rows, used to bootstrap a new sink (§17).
  13. Bootstrap — bringing a new sink from empty to caught-up, combining snapshot and handoff.
  14. Watermark — a point-in-time LSN marker injected into the stream to bound a snapshot chunk's reconciliation window (§8).
  15. Handoff — the coordinated transition from snapshot-sourced events to live-stream-sourced events for a table (§8, §18).
  16. Exactly-Once Effect — the property that every change is applied at most once in observable effect at a sink, even though the transport is only at-least-once (P2).
  17. Idempotent Apply — an apply operation producing the same end state no matter how many times it is repeated with the same input.
  18. Upsert — an insert-or-update operation keyed by a unique identifier; the mechanism behind idempotent apply at relational sinks.
  19. Offset — a position marker (here, an LSN) recording how far a sink has consumed the stream.
  20. Checkpoint — a durably committed offset; the unit of crash-resume state (§8, §16).
  21. At-Least-Once — a delivery guarantee that a message may be delivered more than once but never zero times.
  22. At-Most-Once — a delivery guarantee that a message may be lost but is never duplicated.
  23. Dead-Letter Queue (DLQ) — a durable holding area for events that cannot be applied, isolating them from the healthy stream (§8, §21).
  24. Poison Event — an event that repeatedly fails to apply, whose unbounded retry would starve the pipeline.
  25. Backpressure — a flow-control signal throttling upstream production when downstream consumption falls behind (§21).
  26. Schema Evolution — a source table's structure changing over time (add/drop/rename/type-change) and that change propagating downstream.
  27. Schema Registry — the durable, versioned store of table schemas used to gate and translate DDL (§8, §19).
  28. Compatibility Mode — a policy (BACKWARD/FORWARD/FULL/NONE) governing which schema changes are considered safe (§27).
  29. DDL Propagation — the mechanism by which a source's data-definition-language statement reaches and is applied at every sink (§8, §19).
  30. Replication Lag — the delay between a change committing at the source and its effect becoming visible at a sink.
  31. Connector — the process instance running capture, decode, snapshot, handoff, and dispatch for one source (§1).
  32. Rebalance — the redistribution of table/source ownership across a connector fleet when membership changes (§22).
  33. Sink — a downstream system this pipeline applies changes to (database, search index, warehouse, log).
  34. Source — the upstream database this pipeline tails; never written to by this pipeline (§1).
  35. Total Order — a complete, transitive ordering of all events from a source, derived from LSN (§8).
  36. Per-Key Order — the guarantee that events for the same primary key apply in source order at a sink, even if global order is relaxed elsewhere (I4).
  37. Idempotency Key — a deterministic identifier derived from table, primary key, and LSN used to detect and drop duplicate effects (§11).
  38. Coordination Store — an external, consensus-backed store (etcd/Consul-class) used for slot-ownership leases and fleet state (§22).
  39. Lease — a time-bounded, renewable ownership claim over a slot or table enforcing single-writer semantics (P4).
  40. Split-Brain — a failure state where two nodes each believe they hold the same lease/ownership, risking dual-write (§22.8).
  41. Fleet — the set of connector processes coordinating across multiple sources/sinks (§1, §22).
  42. Watermark Window — the LSN interval between a chunk's low and high watermark, during which stream events for that chunk's keys are buffered for reconciliation (§8).
  43. Reconciliation — merging a snapshot's row image with any newer window event for the same key (§8).
  44. RPO (Recovery Point Objective) — the maximum acceptable amount of data loss, measured here in events (§4).
  45. RTO (Recovery Time Objective) — the maximum acceptable time to restore service after a failure (§4).
