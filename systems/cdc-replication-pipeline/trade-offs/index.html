ADR-01

Language

Chosen

Rust

Rejected

Go, Java, C++

When the rejected choice is right

a JVM-staffed team with a <3-month deadline: Java (Debezium's own choice) wins — ecosystem maturity outweighs tail-latency gains

Why: no-GC tail latency, memory safety on untrusted decode input (§1)

Chosen

When the rejected choice is right

Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alternative 1 — Trigger-Based Capture

Source DB
  +-------------------+
  | Application write  |
  +---------+---------+
            v
  +-------------------+       +----------------------+
  | Table (row)        |------>| AFTER trigger          |
  +-------------------+       | writes a shadow row     |
                               +-----------+----------+
                                           v
                               +----------------------+
                               | Shadow "changes" table |
                               | (same database)         |
                               +-----------+----------+
                                           v
                               +----------------------+
                               | Poller reads shadow     |
                               | table, ships events      |
                               +----------------------+

Winning regime: sources with no logical-decoding/binlog access at all, or where DB-portability across many different engines matters more than write-path overhead. Real embodying system: homegrown "audit table" ETL pipelines and CDC tools for databases lacking log access. Rejected here because it adds synchronous write latency to every source transaction and — critically — cannot capture DDL, which §8/§19's schema-evolution propagation depends on as a first-class ordered event (P8); a trigger-based source would need an entirely separate, unreliable DDL-detection mechanism.

Alternative 2 — Query-Based Polling on an updated_at Column

  +-------------------+
  | Poller (interval)  |
  +---------+---------+
            v
  SELECT * FROM t WHERE updated_at > last_poll_ts
            v
  +-------------------+
  | Emit as events      |
  +-------------------+

Winning regime: sources with genuinely no log/trigger access, where near-real-time (not sub-second) latency is acceptable and hard deletes are rare or soft-deleted. Real embodying system: many SaaS-API-based connectors with only a REST endpoint and an updated_at filter (e.g. early Airbyte incremental-sync connectors, §5). Rejected here because it cannot detect hard deletes without a separate tombstone convention, has a latency floor bounded by the poll interval (violates the p50 < 200 ms target, §4), and cannot preserve per-transaction atomicity — two rows updated in the same source transaction can land in different poll windows, breaking I3.

Alternative 3 — Durable Log (Kafka) as the Transport Backbone

  Source -> capture -> decode -> [[ durable log/Kafka topic ]] -> sink-connectors
                                          |
                          durable, replayable, multi-consumer fan-out

Winning regime: multiple independent consumer teams need durable, replayable fan-out of the same change stream, or capture and sink-apply must scale/fail independently at large organizational scale. Real embodying system: Kafka Connect / Debezium's own deployment model (§33). Rejected as the default here (though supported optionally, ADR-18) because it adds an extra hop and an extra system to operate for the common single-team, single-pipeline case this design optimizes for by default; the direct in-process path meets the p50/p95/p99 lag targets (§4) with less operational surface area, and via-log remains available for the regime above.

Alternative 4 — Dual-Write (the Anti-Pattern)

  Application code
     |          |
     v          v
  Source DB    Sink DB      <- two independent writes, no shared commit boundary

Winning regime: none — named specifically as the anti-pattern to reject, not a legitimate alternative. Real embodying system: an extremely common but incorrect pattern in application code that writes to its primary database and a secondary system (cache, search index) in the same request handler with no log-based reconciliation. Rejected here because the two writes have no atomicity relationship — a crash between them, or a reordering under retries, produces permanent, silent divergence with no mechanism to detect or repair it; this is precisely the "dual-write inconsistency" this entire project exists to replace with a single source of truth (the log) and a total order derived from it (P1).
