⬜ Phase 0 — Repository Skeleton, Mock Source Log & CI §12

Objectives

Stand up the Cargo workspace, all 20 crates as empty skeletons (§10), CI, a mock source-log generator for local development (real Postgres/MySQL wiring lands in Phase 1), and the shared error taxonomy (PipelineError, §11).

Deliverable

cargo build --workspace compiles all 20 crate skeletons; mock-source-log emits a deterministic 10,000-frame sequence; CI green on a trivial commit; docker-compose up brings up an empty cluster shell with metrics/tracing endpoints reachable.

Acceptance
  • cargo test --workspace passes with 0 failures on a clean checkout.
  • mock-source-log --seed 42 --frames 10000 produces byte-identical output across two runs.
  • CI pipeline completes in < 5 minutes.
  • /healthz on the stub admin-api returns 200 within 2 s of process start.
Fixtures
  • fixtures/mock-log-seed42-10k.bin — canonical deterministic mock-log output, regression baseline.
  • fixtures/config-valid.toml / fixtures/config-invalid.toml — connector-config validation cases.
  • fixtures/empty-workspace-build.log — expected build output for CI drift detection.
Pitfalls
  • Non-deterministic crate feature flags leaking into mock-source-log output, breaking the regression fixture — pin feature sets per profile.
  • A dependency cycle between sink-runtime and sink-db/sink-search/etc. — enforce a one-directional dependency (sink-* depends on sink-runtime, never the reverse).
  • Tracing-context propagation forgotten at a crate boundary, silently dropping spans — verify with an integration test asserting trace continuity across two crates.

⬜ Phase 1 — Logical-Decoding Reader & LSN Tracking §13

Objectives

Implement capture-postgres against a real PostgreSQL logical-replication slot using pgoutput (ADR-04), and lsn-tracker's total-order assignment (P1, §8 equations).

Deliverable

capture-postgres sustains continuous ingestion from a live PostgreSQL instance (docker-compose fixture), emitting RawFrames with monotonically increasing LSN; lsn-tracker exposes the current position via admin-api.

Acceptance
  • Sustained ingest ≥ 50,000 events/sec against a synthetic write workload (§4, M1).
  • Zero LSN regressions across a 1-hour soak run (I1 assertion never fires).
  • Slot survives a 30-second network partition without being dropped (§4 heartbeat).
  • slot_wal_bytes tracks within 5% of pg_replication_slots.confirmed_flush_lsn lag.
Fixtures
  • pg-wal-valid.bin — a known-good pgoutput stream, expected: N frames, a specific LSN sequence.
  • pg-wal-corrupt.bin — a truncated frame, expected: quarantine + CaptureError::TruncatedFrame.
  • pg-wal-split-tcp.bin — a frame split at a byte boundary, expected: correct reassembly.
  • pg-slot-timeout-replay.bin — a heartbeat gap > 30 s, expected: SlotLost transition.
Pitfalls
  • Treating a Relation message's column list as static — it can change under concurrent DDL (formal Op::Ddl handling is Phase 7, but the parser must not crash on it now).
  • Long-running open transactions holding back the confirmed-flush LSN, inflating slot_wal_bytes even though the connector itself is keeping up — distinguish "connector lag" from "held-open-transaction lag" in telemetry (§26).
  • Off-by-one in LSN byte-order parsing (PostgreSQL LSNs are {high:u32}/{low:u32}) — a documented historical bug class in hand-rolled parsers; verify against the fixture corpus.
  • Assuming a single TCP read yields a whole frame — test explicitly with an artificially small read-buffer size.

⬜ Phase 2 — Change-Event Decoding & the Envelope §14

Objectives

Implement decode-engine: transaction reassembly and RawFrame → ChangeEvent conversion producing the canonical envelope (§8), per the Debezium envelope design (applied per §5).

Deliverable

decode-engine consumes capture-postgres's RawFrame stream and emits a correctly ordered ChangeEvent stream, verified against pg-wal-valid.bin at the envelope level.

Acceptance
  • Decode latency < 2 ms p99 on the standard fixture corpus (§4, M2).
  • Zero events emitted for an aborted transaction across 1,000 injected-rollback test transactions (I3).
  • Fuzz corpus (fuzz/decode_engine.rs, fuzz/event_parser.rs) runs 1M executions with zero panics/crashes in CI.
  • A 100,000-row transaction (spill-to-disk case) decodes without exceeding the 512 MB per-connector memory ceiling.
Fixtures
  • tx-interleaved.bin — two concurrent transactions' frames interleaved, expected: correctly separated per-tx event sets.
  • tx-rollback.bin — a transaction that aborts, expected: zero emitted events.
  • tx-large-100k-rows.bin — spill-to-disk regression fixture.
  • envelope-malformed-checksum.bin — a bit-flipped envelope, expected: SerializationFailure, routed to DLQ (I11 groundwork).
Pitfalls
  • Assuming replica identity is always FULL — REPLICA IDENTITY DEFAULT omits unchanged columns from the before image on Update, breaking a naive full-row-diff transform; document the actual before-image completeness contract.
  • Spill-to-disk overflow files not cleaned up on crash — orphaned temp files accumulate; add a startup sweep.
  • Checksum computed over a non-canonical field order — non-reproducible checksums across restarts; fix the serialization order once, per P14's spirit, and never change it.

⬜ Phase 3 — First Sink Applier with Idempotent Upsert §15

Objectives

Implement sink-runtime's Sink trait and the first concrete applier, sink-db, with the idempotent-upsert half of the exactly-once-effect protocol (§8 steps 3–5; the offset-commit half lands in Phase 4).

Deliverable

An end-to-end path: mock-source-log (or real capture-postgres) → decode-engine → sink-db, applying inserts/updates/deletes idempotently to a target Postgres table, observable via row-count and checksum comparison against the source.

Acceptance
  • Replaying a 10,000-event fixture twice against an empty sink-db target produces identical final state to replaying it once (I2, byte-for-byte row comparison).
  • Apply latency < 10 ms p99 per 100-row batch (§4, M3).
  • A deliberately duplicated LSN range (simulated redelivery) produces zero duplicate rows.
  • sink_dedup_hit_total increments exactly once per intentionally duplicated event.
Fixtures
  • apply-insert-update-delete-sequence.bin — a canonical mixed-op sequence with an expected final-state hash.
  • apply-duplicate-lsn-range.bin — a replayed LSN range, expected: zero net duplicate effect.
  • apply-out-of-key-order-batch.bin — same-key events shuffled, expected: LSN-ordered apply regardless of arrival order (I4).
Pitfalls
  • ON CONFLICT DO UPDATE silently overwriting a newer row with an older one if a stale, out-of-order batch is retried without the I4 defensive reorder — exactly why 15.2's in-sink ordering guarantee exists, not just upstream.
  • Connection-pool exhaustion under batch concurrency — bound pool size explicitly, don't let it float with load (feeds into backpressure design, Phase 9).
  • Treating Delete as a no-op error when the row is already absent (a prior partial apply) — it must be a true no-op, or every crash-resume replay (Phase 4) becomes a false failure.

⬜ Phase 4 — Offset Commit & Crash-Resume by LSN §16

Objectives

Implement offset-store's atomic Checkpoint commit and connector-wide crash-resume, completing the exactly-once-effect protocol (§8 steps 6–7; P2, P5, I5, I6, I8).

Deliverable

A connector that can be killed with SIGKILL at any point during steady-state streaming and, on restart, resumes from the last committed LSN with zero net data loss and zero unbounded duplication (verified against the fixture corpus below).

Acceptance
  • 100 randomized kill-and-restart trials against the standard fixture corpus produce a sink final-state hash identical to an uninterrupted run, in every trial (I5).
  • Recovery/resume time < 30 s from process start to PipelineState::Streaming (§4).
  • offset_regression_total remains 0 across all trials (I8).
  • slot_advance_before_commit_total remains 0 across all trials (I6).
Fixtures
  • crash-resume-kill-at-n.bin — killing the process after N events, N in {0, 1, 100, 9999, 10000}.
  • checkpoint-cas-conflict.bin — two competing commits with a stale committed_lsn, expected: the stale one rejected (I8).
  • resume-gap-injected.bin — an artificially introduced gap between offset-store and sink dedup state, expected: audit failure detected and alerted.
Pitfalls
  • Committing the offset before the sink apply is durably acknowledged (violates P5) — a subtle ordering bug that only shows up under crash injection, never under a clean test run; this is why 16.4's kill-and-restart matrix is mandatory.
  • Advancing the slot based on one sink's checkpoint while a second, slower sink hasn't committed yet — violates I6; the min() in 16.2 exists specifically to prevent this.
  • A commit-cadence background task racing the apply hot path on the same in-memory offset cache — use a single-writer discipline (P4) even for offsets local to one connector.

⬜ Phase 5 — The Consistent Snapshot Reader §17

Objectives

Implement snapshot-reader: chunked, consistent, lock-minimal bootstrap reads of a table's current rows, laying the groundwork for Phase 6's handoff (ADR-06, DBLog per §5).

Deliverable

snapshot-reader reads a full table's current state in parallel chunks, producing a synthetic ChangeEvent stream consumable identically to the streaming path (same envelope type, §8/§11), verified against the source's actual row count and checksum.

Acceptance
  • 1M-row table snapshots in ≤ 90 s with ≥10 parallel chunk readers (§4).
  • A snapshot killed at a random chunk boundary and restarted completes with the same final row count as an uninterrupted run.
  • Source connection-pool usage during snapshot never exceeds the configured ceiling under concurrent chunk load.
  • Zero source-side table locks held longer than a single chunk's read duration (verified via pg_locks inspection in the test fixture).
Fixtures
  • snapshot-1m-rows.fixture — a 1M-row synthetic table, canonical throughput benchmark.
  • snapshot-crash-mid-chunk-37.bin — a crash injected during chunk 37 of 100, expected: resume from chunk 37, not chunk 0.
  • snapshot-empty-table.fixture — a zero-row table, expected: immediate handoff-ready state, no chunks.
  • snapshot-skewed-key-distribution.fixture — a table with a hot key range, expected: chunk sizing still meets the throughput target.
Pitfalls
  • Chunking by a fixed row-count offset (LIMIT/OFFSET) instead of a primary-key range — OFFSET paging degrades to O(n²) on a large table and is unsafe under concurrent writes (rows can be skipped or duplicated as the table changes underneath the scan); primary-key range chunking is the DBLog-recommended approach (per §5) for exactly this reason.
  • A chunk boundary landing mid-transaction at the source is not a pipeline problem yet — reconciliation is Phase 6's job; this phase must not attempt to solve it prematurely.
  • Skewed key distributions producing wildly uneven chunk sizes — sample the key distribution before fixed-size chunking, or use adaptive chunk boundaries.

⬜ Phase 6 — The Watermark-Based Snapshot-to-Stream Handoff §18

Objectives

Implement handoff-coordinator's DBLog watermark algorithm (§8, named steps 1–5) end-to-end, closing the single hardest correctness gap in the system (P3, I7).

Deliverable

A new sink can be bootstrapped from empty and reach full streaming parity with a source table under concurrent write load throughout the entire snapshot, with the worked example from §8 passing as a live integration test.

Acceptance
  • A 1M-row table under a concurrent synthetic write workload (mixed insert/update/delete at 1,000 ops/sec) hands off with zero duplicate and zero missing rows, verified by full-table hash comparison (I7).
  • Handoff reconciliation completes within the same wall-clock envelope as the underlying snapshot (§4, no added latency beyond snapshot throughput itself).
  • handoff_reconcile_mismatch_total is 0 across 50 randomized handoff trials with injected concurrent writes at varying rates.
  • A transaction whose commit lands exactly on a chunk boundary during the trial matrix above is resolved correctly in every trial (the §8 worked example, generalized).
Fixtures
  • handoff-worked-example.bin — the exact §8 worked example (keys 10/11/12, LSN 100/105/
    1. as an executable regression test.
  • handoff-concurrent-writes-1kops.fixture — the 1,000 ops/sec concurrent-write trial.
  • handoff-boundary-transaction.bin — a transaction spanning a chunk boundary, expected: resolved per-key by newest LSN (I7).
  • handoff-reconcile-mismatch-injected.bin — a deliberately corrupted window buffer, expected: mismatch detected and alerted, never silently accepted.
Pitfalls
  • Forwarding window events downstream immediately instead of holding them for reconciliation — the single most common naive-implementation bug in watermark-based snapshotting (a documented pitfall of DBLog-style systems, per §5); it causes exactly the "reorder rows crossing a chunk boundary" failure mode called out in the Netflix DBLog reference-impl notes.
  • Choosing the snapshot image over the window image when both exist for a key — backwards; the window event is always newer (Step 4, §8) and must win.
  • Running handoff reconciliation synchronously on the critical decode path, adding latency to unrelated tables' streaming — reconciliation must be scoped per-table and run off the hot path.

⬜ Phase 7 — Schema Tracking & Evolution Propagation §19

Objectives

Implement schema-registry fully: TableSchema/SchemaVersion tracking, compatibility-mode enforcement (ADR-15), and the DDL-gated propagation rule (I9, P7, P8).

Deliverable

An ALTER TABLE orders ADD COLUMN discount_pct numeric issued against the source propagates to sink-db automatically, with DML referencing the new column applied correctly and no DML lost or misapplied during the transition, without a pipeline restart.

Acceptance
  • Schema-change propagation latency < 2 s from DDL commit to registry visibility fleet-wide (§4).
  • All four decision-table change types (add/drop/rename/type-widen) verified end-to-end against sink-db, each with a before/after row-count and value-correctness check.
  • Zero schema_incompatible_total false positives against a corpus of 50 real-world-style migration scripts (additive-only changes).
  • A deliberately breaking change (e.g. a narrowing type change) is rejected at the registry with SchemaViolation, not silently applied (I14).
Fixtures
  • ddl-add-column.bin / ddl-drop-column.bin / ddl-rename-column.bin / ddl-type-widen.bin — one fixture per decision-table row, each with an expected sink-side DDL translation.
  • ddl-breaking-narrow-type.bin — a narrowing type change, expected: SchemaViolation at the registry boundary.
  • ddl-mid-stream-during-backpressure.bin — a DDL arriving while the pipeline is already backpressured, expected: DDL gate still enforced (I9), no starvation.
Pitfalls
  • Applying a DDL to the registry but forgetting to gate the specific sink's own schema migration behind it — I9 is about ordering at the registry, not a guarantee that every sink has physically migrated yet; sink-db's own ALTER TABLE must complete before its DML gate releases, a subtlety easy to under-specify.
  • Treating "backward compatible" as "safe to apply immediately" for every sink type — a compatible change at the registry (e.g. add nullable column) can still require a non-trivial backfill at sink-warehouse (§8 table); compatibility and propagation cost are different axes.
  • Grace-period counters reset by a connector restart — must be checkpointed alongside Checkpoint state (Phase 4), not held only in memory.

⬜ Phase 8 — DDL Handling & Multi-Sink Routing §20

Objectives

Extend DDL propagation (Phase 7) across all four sink types, and implement router's full multi-sink fan-out (one event to N sinks), replacing Phase 3's single-sink placeholder.

Deliverable

A single source table replicates simultaneously to sink-db, sink-search, and sink-warehouse, each independently caught up and correctly checkpointed, with DDL correctly propagated to all three per their own translation rules.

Acceptance
  • All three sinks reach full parity with the source (checksum match) after a mixed DML+DDL workload, independently verified per sink.
  • A sink-warehouse outage (simulated) does not stall sink-db/sink-search — their checkpoints continue advancing (I11).
  • DDL translation correctness verified per sink type against the §8 decision table's four change types, ×3 sinks = 12 verified combinations.
  • Multi-sink apply latency stays within each sink's own p99 target from §4 — fan-out adds no cross-sink latency coupling.
Fixtures
  • multisink-fanout-3-sinks.bin — one workload, three sink targets, expected: independent parity per sink.
  • multisink-partial-outage-warehouse-down.bin — warehouse unavailable mid-run, expected: db/search unaffected.
  • multisink-ddl-matrix.bin — the 12-combination DDL×sink matrix, expected translation per combination.
Pitfalls
  • Sharing one IdempotencyKey derivation across sinks with fundamentally different natural keys (e.g. search's document id vs the relational primary key) — each Sink implementation must define its own key mapping, not assume the source primary key is universally meaningful.
  • Coupling fan-out delivery order across sinks (waiting for sink A before starting sink B) — defeats I11's isolation goal; fan-out must be concurrent, not sequential, by default.
  • sink-warehouse's batched-merge apply accidentally batching across a DDL boundary (mixing pre- and post-schema-change rows in one merge) — the DDL gate (I9) must apply per-sink, not just at the registry.

⬜ Phase 9 — Backpressure, DLQ & Poison-Event Handling §21

Objectives

Implement backpressure's credit-based flow control end-to-end (ADR-16, I13) and full DLQ isolation for poison events (P12, I11), replacing Phase 3/8's "batch failure is fatal" placeholder.

Deliverable

A pipeline that, under a sustained slow-sink condition, throttles smoothly (bounded memory, no crash) and, under a poison-event injection, quarantines only the affected keys while continuing to stream everything else.

Acceptance
  • Backpressure activates within one credit-refresh interval (≤500 ms) of a threshold breach (I13), verified by injected slow-sink latency.
  • Max in-flight events under sustained backpressure stays ≤ 50,000 events/node (§4).
  • A poison-event injection affecting 1 key out of 10,000 in-flight keys results in exactly 1 DLQ entry and zero disruption to the other 9,999 (I11).
  • DLQ replay tool successfully reprocesses a quarantined event after a simulated fix, with correct final sink state.
Fixtures
  • backpressure-slow-sink-injection.bin — an artificially slowed sink, expected: smooth throttle, no unbounded memory growth.
  • poison-event-isolated-key.bin — one malformed event among many valid ones, expected: isolated DLQ entry, unaffected neighbors.
  • dlq-replay-after-fix.bin — a DLQ'd event replayed post-fix, expected: correct final state.
  • backpressure-sustained-pause-resume.bin — sustained breach triggering Paused, then recovery triggering Resuming → Streaming (§8 lifecycle).
Pitfalls
  • Credit accounting drifting from actual queue depth under high concurrency (a classic flow-control bug class) — reconcile credit counters against real queue depth periodically, don't trust the counter alone indefinitely.
  • DLQ isolation implemented at too coarse a granularity (whole-table instead of per-key) — defeats I11's intent; verify isolation granularity explicitly in the fixture above.
  • Retry backoff without a ceiling — an indefinitely retrying poison event can starve legitimate work on the same worker pool; the retry ceiling (ADR-16) is not optional.

⬜ Phase 10 — Distributed HA, Connector Rebalancing & Slot Management §22

Objectives

Implement fleet mode (ADR-17): multiple connector processes coordinating slot ownership, rebalancing, and fleet-wide schema-registry state via the external coordination store (ADR-19), plus the active slot-retention safeguard (I10, P13, T2).

Deliverable

A 3-node connector fleet that survives a node kill: the affected source's ownership fails over to another node within the lease-expiry window, streaming resumes from the last committed checkpoint, and no other node's ownership is disturbed.

Acceptance
  • Failover completes within 30 s of lease expiry (§4-consistent RTO target).
  • Zero dual-ownership windows observed across 50 randomized node-kill trials (P4/I6 consistency under HA).
  • Coordination-store QPS stays ≤ 2,000 at a simulated 100-connector fleet size (§4).
  • A slot crossing the hard-abort WAL threshold triggers a controlled, alerted drop — never a silent one — in 100% of injected trials.
Fixtures
  • fleet-node-kill-failover.bin — a 3-node fleet, one node killed, expected: failover within 30 s, no dual ownership.
  • fleet-rebalance-node-join.bin — a 4th node joining, expected: table ownership redistributes without checkpoint loss.
  • slot-wal-hard-abort-trigger.bin — retained WAL crossing the hard-abort threshold, expected: controlled, alerted slot drop.
  • fleet-coordination-store-qps-100nodes.fixture — simulated 100-connector load, expected: QPS within budget.
Pitfalls
  • Lease renewal racing with a rebalance decision — a connector renewing its lease at the exact moment a rebalance reassigns its table produces a brief dual-write window unless renewal and reassignment share the same coordination-store transaction/CAS primitive.
  • Treating slot ownership and table ownership as the same lease — a fleet sharded by table still has exactly one slot reader per source (P4), but table-level sink ownership can be finer-grained; conflating them causes unnecessary failovers.
  • Auto-dropping a slot at the hard-abort threshold without first attempting a throttle/alert step at the softer threshold — the alert threshold (§4, 10 GB) exists precisely to give an operator a window to intervene before the destructive hard-abort (50 GB) fires.

⬜ Phase 11 — Correctness Harness, Conformance & Performance Hardening §23

Objectives

Implement correctness-harness: a Jepsen/Elle-style fault-injected end-to-end verifier (applied per §5, Kingsbury's Jepsen analyses) proving the sink converges to the source under adversarial conditions, plus the final conformance and performance-regression gates.

Deliverable

A CI-gated correctness harness that runs the full fault-injection matrix nightly (and on every release-candidate build) and blocks release on any invariant violation; a performance-regression suite blocking release on any M-target miss.

Acceptance
  • The full fault-injection matrix (6 named scenarios × 3 workload profiles) passes with zero invariant violations across 20 consecutive nightly runs before this phase is considered complete.
  • Deterministic replay of a recorded WAL segment reproduces byte-identical sink state across 3 independent replay runs.
  • Every M-target in §30's table is met on the reference hardware profile documented in docs/performance/.
  • ci/e2e-correctness blocks a deliberately introduced regression (a mutation-tested I2 violation) in a canary CI run.
Fixtures
  • harness-fault-matrix-6x3.fixture — the full 6-scenario × 3-profile fault-injection matrix.
  • harness-mutation-i2-violation.bin — a deliberately broken dedup check, expected: the harness catches it (validates the harness itself, not just the pipeline).
  • replay-recorded-incident-2026-postmortem.wal — a recorded WAL segment from a real (or realistic synthetic) incident, used for deterministic reproduction drills.
Pitfalls
  • A correctness harness that only checks final-state convergence without also checking per-key ordering (I4) mid-run — a bug that self-corrects by the end of the run (e.g. a transient reorder later overwritten) would pass a final-state-only check while still being a real defect; the trace-based Elle-style check (23.2) exists to catch exactly this.
  • Fault injection that is too gentle to be meaningful (e.g. always killing at a quiet point in the workload) — randomize injection timing against the workload's own event clock, not wall-clock time, so faults land mid-transaction and mid-handoff, not just between them.
  • Treating a harness pass as permanent — re-run the full matrix on every release candidate (23.3), not just once at this phase's completion, since regressions can reappear.
