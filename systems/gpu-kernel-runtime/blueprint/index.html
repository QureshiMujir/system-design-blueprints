Project Name: GPU Kernel Runtime (CUDA-like) from Scratch

Status: specification — locked

1. Goal & Scope

Build, from scratch, a CPU-hosted CUDA-like GPU kernel runtime and functional simulator: a PTX-like virtual ISA interpreted on the CPU, a thread/warp/block/grid execution hierarchy, a grid scheduler with explicit occupancy accounting, a device-memory model spanning global/shared/register/constant/local spaces with coalescing accounting, warp divergence via active-mask reconvergence, block-level barriers, and a host runtime API (launch, streams, events, synchronization) fronting a virtual command-queue driver layer. No real GPU hardware, PTX-JIT, or vendor driver is targeted in this scope; the system is a deterministic, debuggable, single-machine functional model of CUDA's execution semantics, built to teach the execution architecture that a black-box CUDA install hides. The deliverable is a specification-grade heterogeneous-runtime simulator usable as a teaching platform, a CUDA-semantics conformance oracle, or a functional-correctness harness for future real-hardware backends.

Phase 0 Deliverable

  1. gpu-ir — PTX-like intermediate representation: SSA basic blocks, register model, kernel metadata (register/shared-mem budgets).
  2. gpu-parser — kernel-language front end: lexer, recursive-descent parser, IR lowering, diagnostics.
  3. gpu-runtime — host runtime API: kernel launch, stream/event management, synchronization primitives.
  4. gpu-memory — device allocator, unified virtual address space, host↔device transfer engine.
  5. gpu-scheduler — thread-block scheduler, warp formation, divergence masks, barriers, occupancy accounting.
  6. gpu-emulator — CPU SIMT execution backend: instruction interpreter, register files, deterministic stepping.
  7. gpu-driver — virtual device abstraction: command buffers, queue submission, DMA abstraction.
  8. gpu-cli — compile / inspect-IR / launch / profile command-line tool.
  9. gpu-profiler — timeline tracing, occupancy metrics, memory-bandwidth statistics.
  10. gpu-common — shared error types, IDs, and cross-crate primitives.

Only items 1, 2 (skeleton), and a minimal gpu-cli version stub ship in Phase 0 itself (§12); items 3–9 are built out across Phases 1–9 (§13–§21) as listed above.

System Boundaries

Provides: PTX-like IR + verifier, kernel-language front end, SIMT scheduler with occupancy/divergence accounting, CPU interpreter execution backend, device-memory simulation, host runtime API (CUDA-like semantics), virtual driver/command-queue layer, profiler, conformance/fuzzing harness.

Delegates: real GPU execution to a future hardware backend (out of scope, §35); process isolation and OS scheduling to the host OS; wall-clock timing realism to a simplified latency model (§4), not cycle-accurate timing.

Does NOT provide: a real CUDA/PTX-JIT/SASS backend, a Vulkan/Metal compute backend, a shader compiler front end, tensor-core modeling, multi-GPU or distributed scheduling, or a debugger/profiler GUI — see §35.

Non-Goals

Not a drop-in CUDA runtime replacement (no binary compatibility with real .cubin/PTX object files); not a cycle-accurate timing simulator (functional correctness only, no microarchitectural timing model — that is GPGPU-Sim's role, §5, §31); not a general SIMD library (SIMD-Library is a sibling project, §2); not a compiler optimizing framework (IR is deliberately simple, no register-allocation-quality claims).

Deployment Model

Embeddable Rust workspace: gpu-runtime + gpu-scheduler + gpu-emulator + gpu-memory link into a host process (test harness, teaching REPL, or CI conformance runner); gpu-cli and gpu-profiler ship as standalone binaries. No network service, no persistent daemon — every run is a single-process, single-machine simulation.

Target Users

Systems engineers learning GPU execution architecture without hardware access; compiler/runtime engineers prototyping scheduler or IR designs before targeting real silicon; educators building CUDA-semantics teaching tools; portfolio engineers calibrating heterogeneous-systems competency (§2).

Language & Rationale

Rust, chosen for: enum-exhaustive modeling of the Instruction and MemoryType spaces (ADR-01), ownership-checked device-buffer lifetimes across host/device boundaries (P7), fearless-concurrency guarantees for the multi-warp scheduler, and no_std-capable low-level layouts for the register file. Rejected: C++ (no compiler-enforced buffer-lifetime safety across the host/device boundary — exactly the bug class real CUDA runtimes spend the most debugging effort on) and Go (GC pauses interfere with the deterministic-stepping guarantee, P2, and its weaker enum modeling makes an exhaustive Instruction match unenforceable).

Prerequisites

Required: operating systems, CPU architecture and cache hierarchies, compiler construction (lexing/parsing/IR), SIMD/SIMT execution concepts, synchronization primitives, scheduling theory, Rust ownership, binary/bitfield encoding.

Recommended: prior exposure to any real CUDA/OpenCL programming, familiarity with the NVIDIA CUDA C++ Programming Guide's execution model chapter, basic queuing theory.

2. Why Build This

Modern compute is heterogeneous by default: training, inference, rendering, and HPC all delegate their inner loop to an accelerator that most engineers treat as a black box. Understanding CUDA's execution model — thread hierarchies, warp scheduling, memory coalescing, occupancy, synchronization barriers, command dispatch — requires building each piece, not reading a vendor whitepaper. This project forces that construction under the exact constraint that makes it valuable: no real GPU, so every semantic (divergence, coalescing, occupancy) must be modeled explicitly rather than delegated to silicon.

Unique systems knowledge: SIMT-vs-SIMD distinction; active-mask divergence and reconvergence; occupancy as a three-way resource-packing problem (registers, shared memory, warp slots); memory-coalescing accounting as a pure function of a warp's collective address pattern; command-queue/stream asynchrony as a DAG, not a free-for-all.

Cross-links to sibling systems (§31, §34): a SIMD-Library project shares the lane-masking mechanics (§2, MM1) with a fixed-width, compile-time-gang model instead of this project's dynamic warp scheduling; a Vector-Database project's batched similarity kernels are exactly the workload this runtime is built to host; a tensor-compiler project would target this runtime's IR (§11) as a lowering destination; a distributed-training-engine project depends on this project's occupancy/scheduling model scaled to multi-device; a Ray-Tracer project's compute kernels map directly onto this runtime's launch model (§17).

Calibration value: heterogeneous-scheduling literacy, compiler/runtime integration, low-level memory-model reasoning, concurrency correctness under adversarial divergence patterns, and performance-engineering literacy grounded in Volkov's occupancy analysis (§5, MM6).

What Mastery Looks Like

  • Can explain why a warp is SIMD-with-per-lane-masking, not true MIMD, and derive the divergence-cost formula from first principles (Phase 3, §15).
  • Can compute occupancy by hand from register/shared-memory/warp-slot budgets without a calculator tool (Phase 3, §15; §32).
  • Can trace a memory-coalescing accounting bug from a wrong bandwidth number back to the exact access-pattern classification that caused it (Phase 2, §14).
  • Can explain why Volkov's "Better Performance at Lower Occupancy" (2010) is not a contradiction of the occupancy model but a refinement of it (Phase 9, §21; MM6).
  • Can hand-derive the immediate-dominator reconvergence point for a divergent branch without a reference table (Phase 3, §15).
  • Can explain why streams model a partial order, not a total order, and why that distinction breaks naive synchronization code (Phase 5, §17).
  • Can design a differential-conformance fixture that would have caught a specific known-class emulator bug before it shipped (Phase 8, §20).

Host Runtime API — exposes CUDA-like host semantics: launch configuration, device allocation, stream/event control, synchronization; the only surface client code calls (P3, ADR-02).

Virtual Driver / Command Queue — accepts host API calls as dispatch packets on a per-stream command buffer, submits them to queues in enqueue order (I9, I12); models the DMA engine as an explicit-latency copy (ADR-17).

Grid Scheduler — owns block dispatch, warp formation, occupancy accounting (I15), divergence-mask bookkeeping (I13), and barrier rendezvous (I3); the single component that must "think in warps" (MM1).

Memory Manager — implements the five memory spaces (§8), unified virtual addressing, host↔device transfer, and the coalescing-accounting model (MM4) that drives bandwidth telemetry.

Execution Backend — the CPU interpreter that steps one warp-instruction at a time per active lane (P1, P2); the only component that actually "executes" IR.

PTX-like IR Layer — canonical kernel representation; every frontend (only gpu-parser today) lowers into it (P5); the verifier (I7) is the single gate between untrusted kernel source and the scheduler/emulator.

Profiler / Instrumentation — first-class observability (P9): timeline traces, occupancy metrics, and memory-bandwidth statistics consumed by gpu-cli.

6. Design Principles

P1 — SIMT Correctness Before Performance. Rule: execution semantics (divergence, reconvergence, lockstep lanes) must be modeled exactly before any optimization pass exists. Tradeoff: the Phase-4 interpreter (§16) is intentionally slow. Violation: "fast but wrong" execution silently produces incorrect kernel outputs indistinguishable from correct ones without a conformance oracle (FM-3).

P2 — Deterministic Emulation. Rule: identical (kernel, inputs, launch config) always produces an identical execution trace, including instruction-step order. Tradeoff: forecloses free-running multi-threaded warp interleaving inside one simulated SM. Violation: bug reports become unreproducible (FM-9).

P3 — Explicit Synchronization Only. Rule: no implicit barriers or memory fences; every synchronization point is a named IR instruction or runtime API call. Tradeoff: kernel authors must reason about every sync point manually, exactly as in real CUDA. Violation: a hidden sync point masks real divergence/race bugs that would surface on real hardware (T6).

P4 — Occupancy Is Computed, Not Assumed. Rule: the scheduler derives occupancy from register/shared-memory/warp-slot budgets (I15) on every launch, never from a programmer-supplied guess. Tradeoff: launch-time cost of a small accounting pass. Violation: silent over-subscription causes resource-budget violations invisible until a launch fails on tighter fixtures (FM-11).

P5 — IR Is the Only Lowering Target. Rule: every frontend, including future ones, lowers into the canonical gpu-ir representation (§11); no frontend talks to the scheduler or emulator directly. Tradeoff: an extra lowering pass even for the single current frontend. Violation: a second frontend would duplicate verifier/scheduler integration and drift from canonical semantics.

P6 — Fail-Closed Kernel Validation. Rule: the IR verifier rejects any structurally invalid kernel (unreachable blocks, invalid SSA refs, budget overflow) before it reaches the scheduler. Tradeoff: strictness rejects some inputs a lenient loader would run anyway. Violation: an invalid kernel reaches the emulator and produces undefined-behavior-class corruption instead of a clean rejection (T1).

P7 — Memory Ownership Crosses Boundaries Explicitly. Rule: every host↔device transfer and every device allocation has an explicit, validated owner and lifetime; there is no implicit unified-memory migration. Tradeoff: no "just works" unified-memory convenience API. Violation: use-after-free across the host/device boundary (T3, FM-4).

P8 — Hardware Independence via Backend Trait. Rule: gpu-scheduler and gpu-runtime depend on an execution-backend trait, never on gpu-emulator concretely. Tradeoff: one extra trait-dispatch indirection on every instruction step. Violation: a future hardware backend (§35) would require rewriting scheduler internals instead of implementing a new trait impl.

P9 — Observable Execution Is First-Class. Rule: timeline tracing, occupancy metrics, and memory statistics are wired in from Phase 0 onward, not bolted on at the end. Tradeoff: every hot-path component carries instrumentation overhead (bounded by M8). Violation: a scheduler or memory bug becomes undiagnosable without a profiler rebuild.

P10 — No Hidden Scheduling Decisions. Rule: every block-dispatch, warp-formation, and divergence-mask decision is derived from a named, documented policy (ADR-18, ADR-19), never from incidental iteration order. Tradeoff: policy changes require an ADR, not an ad hoc tweak. Violation: nondeterministic-looking scheduling that actually hides an undocumented ordering dependency (FM-5).

P11 — Divergence Is Modeled With Explicit Masks. Rule: every warp carries an explicit active-lane bitmask (I2) updated only at documented divergence/reconvergence points. Tradeoff: mask-stack bookkeeping on every branch instruction. Violation: a divergent branch silently executes lanes that should be masked off, corrupting shared state (FM-2).

P12 — Streams Establish Partial Order, Not Total Order. Rule: operations in different streams have no ordering guarantee absent an explicit event dependency (I9, I10). Tradeoff: multi-stream kernels require explicit event synchronization, exactly as real CUDA. Violation: code that assumes cross-stream ordering races silently (T7).

P13 — Command Submission Is Asynchronous by Default. Rule: every host API call enqueues a dispatch packet and returns; synchronous behavior is opt-in via explicit sync/wait calls. Tradeoff: callers must track completion themselves. Violation: a caller that assumes synchronous completion reads device memory before the DMA/kernel that produces it has run (FM-6, FM-7).

P14 — Differential Conformance Gates Every Optimization. Rule: no scheduler, emulator, or memory-model performance change lands without a green differential-test run against the Phase-8 fixture corpus (§20). Tradeoff: slower iteration on hot-path work. Violation: an optimization silently changes kernel output without a local error signal (FM-3, FM-9).

Worked Example — Vector-Add Warp Trace

Kernel vecadd(a: ptr global, b: ptr global, c: ptr global), launched with gridDim=(1,1,1), blockDim=(32,1,1) (exactly one warp, no divergence):

Step Instruction Effect (all 32 lanes active, mask=0xFFFFFFFF)
1 ld.global.u32 r1, [a + tid*4] each lane loads its a[tid]
2 ld.global.u32 r2, [b + tid*4] each lane loads its b[tid]
3 add.u32 r3, r1, r2 each lane computes a[tid]+b[tid]
4 st.global.u32 [c + tid*4], r3 each lane stores its c[tid]
5 ret warp retires, block completes

Coalescing classification (I14): step 1/2/4 access base + tid*4 — a unit-stride, 32-lane pattern — classified Coalesced (single memory transaction per warp).

Malformed-Input Example

Kernel source declaring ld.global.u32 r1, [a] where a is declared ptr shared in the parameter list: the parser accepts the syntax (structurally valid), but the IR verifier (I7) rejects it at lowering time — ld.global on a shared-space pointer is a state-space mismatch, raised as GpuError::StateSpaceMismatch, not silently reinterpreted as a global address.

Failure-Path Example

A kernel with two divergent branches whose reconvergence points are not the same immediate-dominator block (a verifier bug or a hand-crafted adversarial IR sample, T1) reaches the scheduler. I13's dominator-tree check at verify time is the intended gate; if it is bypassed (fuzzing target, §20), the scheduler's mask-restoration logic executes lanes that should remain masked, corrupting shared-memory state — this is FM-2, and the only way to have caught it earlier is the differential fixture corpus (P14).

  • Barrier deadlock fixture barrier_deadlock.json triggers the watchdog within the §4 2-second timeout and reports FM-1.
  • Warp-dispatch throughput ≥ 20M warp-instructions/sec/core (M2) on matmul.gpu.

15.5 Conformance Fixtures

Fixture Assertion
divergence_if_else.json mask sequence matches hand-derived trace (I2, I11)
occupancy_budget.json occupancy matches hand-computed value (I15)
barrier_deadlock.json watchdog fires within timeout (I3, FM-1)
mask_stack_balance.json every mask push has exactly one matching pop

15.6 Pitfalls

  • Restoring the wrong mask on reconvergence because the dominator target from §13 was computed on the AST-level CFG instead of the final lowered IR CFG.
  • Counting a thread that never reaches a bar.sync (e.g., trapped in a divergent branch with no reconvergence) as "arrived" — this is exactly FM-1's root cause.
  • Implementing occupancy as a sum instead of a min() across the three resource dimensions (I15) — always overestimates achievable occupancy.

15.7 Performance Concerns

  • Mask-stack allocation per warp per divergent branch — acceptable at Phase 3 scale; arena-pool reuse deferred to §21 (P14).
  • Greedy-then-oldest bookkeeping (ADR-18) requires an age counter per resident warp — bounded overhead, verified against M2.

15.8 Edge Cases

  • A block with blockDim not a multiple of 32 — the last warp is partially populated; inactive lanes beyond blockDim must be masked off from warp formation, not merely from execution.
  • Nested divergence (an if inside an if) — mask-stack depth must handle arbitrary nesting without a hardcoded stack-depth ceiling shorter than the kernel's actual CFG depth.
  • A barrier reached inside a still-divergent region — this is itself invalid CUDA-like usage; the verifier (§13) should flag bar.sync inside a divergent scope as a reconvergence-ordering hazard where feasible, otherwise it surfaces as FM-1 at runtime.

15.9 Failure Analysis

A mask-restoration bug is the highest-leverage bug class in this entire project: it produces plausible-looking wrong output (some lanes silently write when they should be masked) with no crash and no local error signal — discoverable only via the divergence-trace fixtures (P14) or a differential run (§20). This directly mirrors MPT's root-divergence lesson in a different domain.

15.10 Operational Notes

barrier_timeout_total and occupancy_miscalc_total are the two scheduler metrics that should page on-call (§24) if nonzero against the conformance corpus in CI.

16. Phase 4 — CPU SIMT Emulator Backend

16.1 Objectives

Implement gpu-emulator: the tree-walking instruction interpreter, per-thread register files, deterministic warp-instruction stepping, and trace capture/replay.

16.2 Detailed Implementation Steps

  1. Implement the register file (Vec<u64> per ThreadState) sized to a kernel's max_registers (I4).
  2. Implement the tree-walking interpreter dispatch over the Instruction enum (ADR-09), one match arm per §11 variant.
  3. Implement per-lane execution: for each active lane in the warp's mask (I2), execute the current instruction against that lane's register file.
  4. Implement Load/Store dispatch through gpu-memory's space model (§14), routing by Address variant.
  5. Implement bar.sync as a call into the §15 scheduler's barrier unit — the emulator never implements its own ad hoc barrier (P3).
  6. Implement deterministic warp-instruction stepping: a fixed, documented order of which resident warp steps next (feeds I11).
  7. Implement exception handling: an interpreter fault (e.g., GpuError::InvalidAddress from §14) aborts the issuing kernel, not the whole process.
  8. Implement trace capture: append (warp_id, pc, active_mask) per step to a replay-log (ADR-08 — postcard-encoded).
  9. Implement replay: given a captured trace and identical inputs, re-execute and diff step-for-step (I11).
  10. Add differential fixtures: matmul.gpu and reduction.gpu against hand-computed expected outputs.
  11. Add property test: replaying a captured trace twice yields byte-identical replay logs.
  12. Add benchmark benchmarks/criterion/interp_throughput.rs targeting M2.

16.3 Deliverable

A runnable CPU SIMT emulator executing verified gpu-ir kernels lane-accurately, with deterministic stepping and trace replay.

16.4 Acceptance Criteria

  • matmul.gpu (16×16) produces output matching a hand-computed reference to bit-exact floating-point equality (fixture matmul_16x16.json).
  • reduction.gpu (sum of 1024 elements) matches the expected scalar exactly.
  • Replaying any conformance fixture's captured trace twice yields identical logs (I11) — fixture replay_determinism.json.
  • Interpreter throughput ≥ 20M warp-instructions/sec/core (M2, shared target with §15).

16.5 Conformance Fixtures

Fixture Assertion
matmul_16x16.json matrix-multiply output matches hand-computed reference
reduction_sum.json reduction output matches expected scalar
replay_determinism.json two replays of one trace are byte-identical (I11)

16.6 Pitfalls

  • Executing an inactive lane "for simplicity" and discarding its result afterward instead of skipping it — subtly wrong for any instruction with a side effect (store, register write visible to a later divergent path).
  • Nondeterministic warp-step order (e.g., iterating a HashMap of resident warps) breaking I11 silently — only a Vec or explicitly sorted iteration order is acceptable (P10).
  • Treating a floating-point reduction as associative for test-fixture purposes when the actual summation order matters for bit-exact comparison — fixtures must pin the exact reduction tree shape.

16.7 Performance Concerns

  • Tree-walking dispatch overhead per instruction (ADR-09 accepts this tradeoff over JIT); revisit only after §20 conformance and only as a PhaseDeferred("§35") JIT backend, never as an in-place rewrite of the interpreter (P1, P14).
  • Trace-capture allocation per step — bounded by capping trace length per kernel launch and streaming to disk for long-running fixtures.

16.8 Edge Cases

  • A kernel that never issues a memory instruction (pure register arithmetic) — must still produce a valid (empty-memory-touching) trace.
  • Integer overflow in arithmetic instructions — must wrap per the declared operand type (u32 wraps, no undefined behavior), never panic in release builds.
  • A kernel whose only active lane count reaches zero mid-execution (all lanes diverged to a path that immediately returns) — warp retires cleanly, not as a fault.

16.9 Failure Analysis

A wrong-but-plausible arithmetic or masking bug here is caught only by fixture comparison (P14) — there is no crash. This is the direct analog of Nickolls et al.'s (2008) observation that GPU program correctness is fundamentally a lockstep-execution correctness problem, not a memory-safety problem in isolation.

16.10 Operational Notes

replay_mismatch_total (I11) is the emulator's single most important telemetry counter — any nonzero value in CI indicates a determinism regression and blocks release (ADR-10 gate).

17. Phase 5 — Host Runtime API

17.1 Objectives

Implement gpu-runtime: the CUDA-like host API surface — launch(), stream creation and synchronization, event record/wait, and host-side synchronization primitives.

17.2 Detailed Implementation Steps

  1. Implement launch(): validate LaunchConfig against §4 dimension limits (I8), then enqueue a DispatchPacket::KernelLaunch (§18) on the caller's stream.
  2. Implement stream creation/destruction; default (Stream(0)) semantics matching CUDA's implicit stream.
  3. Implement stream.sync(): blocks the host caller until every packet enqueued to that stream before the call has completed (P12, I9).
  4. Implement event.record()/event.wait() per I10's cross-stream completion-order semantics.
  5. Implement async host↔device memcpy entrypoints delegating to §14's transfer engine through a DispatchPacket::MemcpyH2D/MemcpyD2H.
  6. Implement launch validation errors surfaced as GpuError::InvalidLaunchConfig (I8), never a silent clamp.
  7. Implement error propagation: every fallible API call returns Result<_, GpuError>, no panics on caller-supplied bad input (P6, ADR-23).
  8. Add differential fixtures: two kernels on separate streams with an event dependency, assert correct completion order.
  9. Add property test: stream.sync() never returns before all of that stream's enqueued work has completed (I9).
  10. Add benchmark benchmarks/criterion/launch_overhead.rs targeting M1.
  11. Document the CUDA-like async-by-default model (P13) inline in launch.rs, citing Nickolls et al. (2008).

17.3 Deliverable

A CUDA-like host runtime API: launch validation, multi-stream async dispatch, event- based cross-stream synchronization, exhaustive error propagation.

17.4 Acceptance Criteria

  • Fixture streams_independent.json: two independent streams' kernels may interleave in completion order (no false ordering guarantee asserted).
  • Fixture event_dependency.json: stream B's kernel that event.wait()s on stream A's event never observes stream A's output before it is written (I10).
  • Launch overhead p50 ≤ 5 µs, p99 ≤ 25 µs (M1) measured over 10,000 launches.
  • 100% of invalid-launch-config fixtures return GpuError::InvalidLaunchConfig, zero panics (I8).

17.5 Conformance Fixtures

Fixture Assertion
streams_independent.json no false cross-stream ordering assumed
event_dependency.json event wait enforces correct completion order (I10)
invalid_launch_config.json oversized grid/block dims rejected cleanly (I8)

17.6 Pitfalls

  • Implementing stream.sync() as a fixed sleep-then-check instead of a real completion signal — breaks under load and violates I9's exact-order guarantee.
  • Allowing an event to signal "complete" based on enqueue time rather than actual completion of prior work — directly violates I10.
  • Silently clamping an oversized blockDim instead of rejecting it (I8) — hides a caller bug that would fail loudly on real hardware.

17.7 Performance Concerns

  • Per-launch validation cost (I8 dimension checks) — bounded and amortized; measured against M1's p99 budget.
  • Stream-sync polling overhead — implemented as a real async notification (ADR-02: tokio), not a busy-wait, to keep host-side CPU usage low.

17.8 Edge Cases

  • launch() called on a stream that has a pending event.wait() for an event that will never be recorded (caller bug) — must not deadlock the host; document as a caller-responsibility case in §24 runbooks.
  • Zero-size memcpy request — must be a documented no-op, not a rejected call.
  • stream.sync() called on a stream with zero enqueued work — returns immediately.

17.9 Failure Analysis

An event-ordering bug at this phase is invisible in single-stream tests and only manifests under multi-stream fixtures (P14) — this is why §17.5's event_dependency.json fixture is mandatory, not optional, coverage.

17.10 Operational Notes

stream_order_violation_total and event_order_violation_total (I9, I10) are the runtime's release-blocking metrics (ADR-10 gate); both must be zero against the conformance corpus.

18.1 Objectives

  4. Implement the virtual-device abstraction behind the §11/ADR-21 driver trait (P8).
  5. Implement the DMA abstraction wrapping §14's transfer engine with an explicit overlap check against other in-flight transfers (I16).
  6. Implement queue-full backpressure: reject new submissions past the §4 ring-buffer ceiling rather than growing unboundedly.
  7. Implement queue synchronization primitives consumed by §17's stream.sync().

  10. Add fuzz target fuzz_targets/queue_fuzz.rs (randomized submission interleavings).

  • Fixture queue_order.json: 1,000 packets submitted to one queue complete in exact submission order (I9, I12).
  • Fixture dma_overlap_serialize.json: two overlapping transfers without a declared dependency execute serially, verified via a byte-level race fixture.

Fixture Assertion

18.6 Pitfalls

  • Implementing the ring buffer with a size that silently wraps and overwrites unconsumed packets instead of applying backpressure.
  • Detecting DMA overlap by pointer equality instead of by interval overlap — misses partially-overlapping regions (I16).
  • Allowing queue submission from multiple host threads without a documented ordering rule, silently violating I9 under concurrent callers.

18.7 Performance Concerns

  • Overlap-check cost scales with the number of in-flight transfers; acceptable at §4's bounded ring-buffer scale, revisited only post-conformance (P14).
  • Tracing-span overhead per packet — bounded by sampling in production-scale benchmarks, full tracing in conformance runs.

18.8 Edge Cases

  • A queue submission racing a concurrent queue-drain (shutdown path, §24) — must not leave a packet half-submitted.
  • Two transfers to fully disjoint regions of the same allocation — must not be misclassified as overlapping (off-by-one interval bug).
  • A DMA transfer larger than any single ring-buffer packet can describe — must be chunked, not silently truncated.

18.9 Failure Analysis

A queue-order violation (FM-8) or DMA race (FM-6) both produce data corruption that looks like an application bug from the caller's perspective — this is precisely why I9/I12/I16 have dedicated telemetry counters rather than relying on caller-side symptoms for detection.

18.10 Operational Notes

Queue depth and dma_overlap_total feed the §24 dashboards; a sustained near-full queue depth is an early warning for the FM-8 corruption class under load.

25. Compatibility & Versioning

Wire/IR Compatibility

The gpu-ir binary/textual representation is versioned independently of the crate SemVer; a kernel compiled against IR version N must declare that version in its KernelMetadata, and the verifier rejects a version mismatch rather than attempting best-effort forward compatibility (mirrors P9/I7's fail-closed philosophy).

API Stability

gpu-runtime's public launch()/stream/event API follows Rust SemVer: breaking changes (parameter/return-type changes) require a major version bump; new optional parameters are added via builder-pattern extension, never by silently changing an existing signature's meaning.

Trace Format Compatibility

Replay traces (ADR-08, postcard-encoded) are tagged with a format version; the replay engine (§16) refuses to load a trace from a newer format version than it understands, rather than misinterpreting bytes.

Deprecation Policy

A deprecated API surface (e.g., a superseded DispatchPacket variant) is marked with a #[deprecated] attribute for one minor version cycle before removal, and every deprecation is cross-referenced against §35's deferred-features register if the replacement is itself deferred.

Rolling-Upgrade Guarantees

Not applicable — this is not a distributed or long-lived service (§24 deployment topology); each run is a fresh process. The only "upgrade" concept is: recompile against a new crate version and re-run the §20 conformance corpus before trusting the new binary.

26. Testing & Verification Strategy

Unit Testing

Per-crate unit tests for every type in §11 (construction, invariant assertions where feasible in-process); gated by ADR-10 (cargo-nextest).

Integration Testing

Cross-crate flows: parse→lower→verify→schedule→execute→profile, exercised end-to-end against every conformance/kernels/*.gpu fixture (§20).

Property-Based Testing

proptest-driven properties for: nibble/bit-level encoding invariants (none here, but analogous CFG/mask-stack balance properties per §12.2/§15.2), mask-stack push/pop balance (I13), coalescing classification purity (I14), replay determinism (I11).

Differential Testing

The project's primary correctness oracle (P14): compares interpreter output against a slow, independently-implemented reference evaluator for a subset of fixtures where one exists, and against hand-computed expected values everywhere else (§16.4, §20.4).

Fuzzing

Four coordinated cargo-fuzz targets (ADR-13): parser, IR verifier, scheduler, command queue (§20.2); nightly extended-budget runs plus PR-gating short runs.

Chaos / Deadlock Testing

Barrier-deadlock fixtures (§15.5 barrier_deadlock.json) and randomized-submission queue fuzzing (§18.10) exercise the watchdog and backpressure paths under adversarial timing.

Deterministic Replay Testing

I11's replay-regression suite (§20.4) re-runs the full fixture corpus's captured traces on every merged PR, diffing step-for-step.

Soak Testing

A nightly extended run of the full conformance corpus plus the M1–M12 benchmark suite, watching for memory growth (allocator leak class, FM-4) over a multi-hour window.

Conformance Testing

Every phase's N.5 fixtures are consolidated into the single §20 runner; 100% pass rate is a release gate (ADR-10).

Perf-Regression Gating

Every M-ID (§28) has a CI-enforced threshold; a benchmark run that regresses past its threshold fails the build (§21.4, ADR-05/ADR-10).

29. Scalability Analysis

What Stays Constant

Warp width (I1, fixed at 32); the five memory-space model (§8); the IR instruction set (§11) — none of these grow with input scale.

What Grows (Big-O)

Grid/block/warp counts grow with kernel launch parameters (O(gridDim × blockDim)); occupancy-pass cost is O(1) per launch (M3) but scheduler bookkeeping is O(resident warps) per simulated-SM tick; device-memory footprint grows O(allocated bytes) bounded by the §4 8 GiB ceiling; queue depth grows O(in-flight packets) bounded by the §4 4,096-packet ring buffer.

Named Bottlenecks, In Order

  1. Interpreter dispatch cost (ADR-09 tree-walking) — dominates M2 at high warp-instruction counts (§16.7).
  2. Scheduler mask-stack/occupancy bookkeeping — grows with divergence depth and resident-warp count (§15.7).
  3. Memory-allocator size-class fragmentation under highly variable allocation-size workloads (ADR-16, FM-4).
  4. Command-queue serialization under high submission-rate multi-stream workloads (§18.7).

Horizontal / Vertical Scaling

Vertical only in this scope: more CPU cores let independent kernel launches on different streams execute concurrently at the OS-thread level, but a single simulated device is single-process (§4). Horizontal (multi-device, distributed) scaling is explicitly deferred (§35 — multi-GPU scheduling, distributed GPU fabric).

Sharding

Not applicable to a single-simulated-device model; a future multi-device backend (§35) would shard by device id, mirroring real multi-GPU CUDA's device-context model.

Practical Ceiling and Levers Beyond It

Ceiling: single-process CPU throughput for warp-instruction interpretation (M2) and the §4 8 GiB simulated device-memory bound. Levers beyond it: a JIT execution backend (deferred, §35) for raw throughput; a real hardware backend (deferred, §35) to remove the CPU-interpretation ceiling entirely; multi-process device sharding (deferred, §35) for horizontal scale.

30. Mental Models & First Principles

MM1 — SIMT Is SIMD With Per-Lane Masking, Not True MIMD. Compressed insight: a warp executes one instruction stream; divergence doesn't create independent instruction streams, it masks lanes out of a shared one (Lindholm et al. 2008). Predicts: divergent code costs proportional to the number of distinct paths taken, not the number of threads. Bug class without it: assuming divergent branches parallelize for free. Resolving §: §15.

MM2 — Occupancy Is a Resource-Packing Problem, Not a Tuning Knob. Compressed insight: occupancy is the min() of three independent resource ceilings (registers, shared memory, warp slots) — you cannot "turn it up" without freeing one of the three (I15). Predicts: reducing register usage per thread can increase occupancy even with no other code change. Bug class without it: tuning block size blindly without checking which resource is binding. Resolving §: §15, §32.

MM3 — Warp Divergence Cost Is Proportional to Path Count, Not Thread Count. Compressed insight: a fully-divergent 32-lane warp taking 32 distinct paths costs roughly 32× a non-divergent warp — the branch, not the thread, is what serializes (Fung et al. 2007). Predicts: data-dependent branching on tid % 32 is far worse than on tid % 2. Bug class without it: writing "parallel" code that is actually 32-way-serialized under the hood. Resolving §: §15.

MM4 — Memory Coalescing Is a Warp-Collective Property, Not a Per-Thread Property. Compressed insight: bandwidth depends on the shape of a warp's 32 simultaneous addresses, not on any single thread's access pattern in isolation (I14). Predicts: transposing a matrix access pattern can change measured bandwidth by an order of magnitude with identical per-thread code. Bug class without it: optimizing a single thread's memory access and missing the warp-level pattern that actually matters. Resolving §: §14.

MM5 — A Barrier Is a Rendezvous, Not a Checkpoint. Compressed insight: bar.sync requires every participant to arrive — it is not a "mark progress" operation that tolerates stragglers (I3). Predicts: any code path that can skip the barrier for some threads deadlocks the whole block. Bug class without it: an early-return inside a conditional that some threads take, skipping a barrier the rest still need. Resolving §: §15.

MM6 — Latency Hiding via Oversubscription, Not Maximal Occupancy, Is the Real Goal. Compressed insight: Volkov (2010) showed that lower occupancy can outperform maximal occupancy when register pressure enables instruction-level parallelism (ILP) that substitutes for warp-level parallelism in hiding memory latency. Predicts: a kernel tuned to 100% occupancy is not automatically faster than one tuned to 50% with more ILP. Bug class without it: chasing the occupancy-calculator's maximum as an end in itself. Resolving §: §29, §21.

MM7 — Streams Model a Partial Order, Not a Free-For-All. Compressed insight: operations across streams have no ordering guarantee except where an explicit event dependency exists (P12) — it is a DAG, not chaos and not a total order. Predicts: code that "usually works" across streams without explicit events will eventually race. Bug class without it: assuming launch order implies completion order across streams. Resolving §: §17.

MM8 — The IR Is a Stable Contract, Never a Bypass Target. Compressed insight: every frontend and every backend agrees only on the canonical gpu-ir shape (P5) — bypassing it to "optimize" a special case reintroduces the exact drift-between-implementations failure MPT-class systems are known for. Predicts: a second frontend that talks directly to the scheduler will desynchronize from verifier guarantees. Bug class without it: an optimization shortcut that skips verification. Resolving §: §13, §20.

32. Back-of-Envelope Capacity Model

  1. Warps per simulated SM at max occupancy. §4: 64 resident warps/SM, 32 threads/warp → 2,048 resident threads/SM (matches real Volta-class SM thread ceilings, a useful sanity check against Lindholm et al. 2008's architecture description).

  2. Register-limited occupancy for a 64-register/thread kernel. §4 register-file budget model: assume a simulated 65,536-register file per SM (standard CUDA-generation figure) ÷ 64 registers/thread = 1,024 threads = 32 warps. Register-limited waves = 32, below the 64-warp slot ceiling → register-bound (I15).

  3. Shared-memory-limited occupancy for a 16 KiB/block kernel. §4: 48 KiB/block shared-mem budget per simulated SM ÷ 16 KiB/block = 3 resident blocks. At 256 threads/block (8 warps/block) → 24 warps. Shared-mem-limited waves = 24 — the binding constraint (min(32, 24, 64) = 24, I15).

  4. Achieved occupancy for the above kernel. min(32 reg-limited, 24 smem-limited, 64 slot-limited) = 24 warps = 768 threads/SM = 37.5% of the 2,048-thread ceiling — demonstrates MM2's resource-packing lesson concretely.

  5. Simulated memcpy time for a 64 MiB transfer. M4 target ≥ 5 GB/s → 64 MiB / 5 GB/s = 64×2^20 bytes / 5×10^9 B/s ≈ 13.4 ms modeled transfer time.

  6. Warp-instruction throughput ceiling from M2. 20M warp-instructions/sec/core × 32 lanes/warp = 640M lane-instructions/sec/core — the CPU-interpretation ceiling this project's ADR-09 tree-walking design accepts (§29 named bottleneck #1).

  7. Time to execute a 1M-instruction kernel (single warp, no divergence). 1M instructions ÷ 20M warp-instructions/sec = 50 ms — the baseline any optimization in §21 is measured against.

  8. Queue-depth drain time at M7 throughput. §4 max in-flight packets = 4,096 ÷ M7 target (≥ 1M packets/sec) ≈ 4.1 ms worst-case full-queue drain time.

  9. Divergence cost multiplier for a fully-divergent warp (MM3). 32 distinct paths × (per-path instruction count) vs. 1 non-divergent path × (same count) → up to 32× serialization cost in the worst case, matching Fung et al.'s (2007) motivating observation.

  10. Device-memory allocation headroom. §4 ceiling 8 GiB ÷ a typical 64 MiB per-kernel working set (reasoning-example scale) ≈ 128 concurrent kernel working sets before exhaustion (FM-4) — a sizing sanity check for conformance-fixture memory budgets.

  11. Barrier watchdog margin. §4 timeout 2 s ÷ (7) 50 ms baseline single-warp kernel execution time ≈ 40× margin before a legitimately slow (non-deadlocked) kernel would false-positive-trigger the FM-1 watchdog — informs the timeout choice.

  12. Fuzzing coverage budget. M12 target ≥ 5,000 iterations/sec × 4 targets × 8-hour nightly window ≈ 576M total fuzz iterations/night — the coverage baseline §20's crash-discovery claims are measured against.

34. Alternative Architectures (Roads Not Taken)

AA1 — Hardware PTX-JIT Backend.

Show the original text diagram
kernel source -> gpu-ir -> PTX-JIT compiler -> SASS -> real GPU driver -> silicon

Wins in the regime where actual GPU throughput matters more than pedagogical clarity — i.e., production ML/HPC workloads. Real system: the actual NVIDIA CUDA driver's PTX-to-SASS JIT pipeline (ptxas). Rejected here because this project's explicit scope (§1) excludes real hardware entirely; this is exactly the PhaseDeferred("§35") hardware-readiness boundary formalized in §21.

AA2 — Vulkan/SPIR-V Compute Backend.

Show the original text diagram
kernel source -> gpu-ir -> SPIR-V lowering -> Vulkan compute pipeline -> GPU driver

Wins in the regime where cross-vendor portability (not CUDA-specific semantics) is the goal — a single compute shader can target any Vulkan-capable GPU. Real system: Vulkan's compute-shader pipeline. Rejected here because it targets a genuinely different execution/memory model (subgroups, not warps; descriptor sets, not raw device pointers) that would dilute the CUDA-specific SIMT semantics this project exists to teach (§2).

AA3 — Trace-Based Whole-Graph JIT.

Show the original text diagram
kernel graph -> trace capture -> whole-graph fusion -> single compiled kernel -> execute

Wins in the regime where a small set of workload shapes recur constantly and fusion overhead amortizes across many executions — the dominant pattern in ML-training frameworks. Real system: tinygrad's lazy-graph JIT, XLA's fusion compiler. Rejected here because whole-graph fusion obscures the individual-kernel SIMT execution model (§8) this project is built to expose step-by-step (MM8).

AA4 — Cycle-Accurate Microarchitectural Timing Simulator.

Show the original text diagram
kernel + config -> functional model -> cycle-level pipeline/memory timing model -> IPC/latency report

Wins in the regime where the research question is performance prediction, not functional correctness — architecture research, design-space exploration. Real system: GPGPU-Sim (Bakhoda et al. 2009). Rejected here because this project's non-goals (§1) explicitly exclude cycle-accurate timing; adding a full timing model would roughly double the implementation surface without serving the teaching goal (§2) this project targets.
