In one paragraph

This is a design for a CPU-hosted simulator of how a CUDA-style GPU runs programs, written in Rust (§1, ADR-01). It reads a small kernel language, compiles it to a PTX-like intermediate form, and interprets that form on the CPU, 32 threads at a time (I1), while modelling thread blocks, divergence, barriers, occupancy, memory-access patterns and streams (§1). It targets no real GPU and models no cycle-accurate timing (§1). It ships as an embeddable library plus command-line tools, with no network service (§1). Its users are people learning GPU architecture without hardware, compiler and runtime engineers prototyping, and educators (§1). The goal is a deterministic, debuggable teaching platform and CUDA-semantics conformance oracle (§1, P2).

The problem, concretely

Modern compute hands its inner loop to an accelerator that most engineers treat as a black box, and learning the execution model means building each piece (§2). With no real GPU, every behaviour (divergence, coalescing, occupancy) has to be modelled explicitly instead of delegated to silicon (§2). The blueprint names the bugs that a naive picture of the GPU produces:

  • Divergence treated as free. A warp runs one instruction stream, and a branch only masks lanes out of it (MM1). A fully divergent 32-lane warp taking 32 distinct paths costs roughly 32 times a non-divergent one (MM3). Branching on tid % 32 is far worse than on tid % 2 (MM3).
  • A barrier treated as a checkpoint. An early return inside a conditional that only some threads take skips a barrier the rest still need, and the block deadlocks (MM5). The symptom is a launch that hangs (FM-1).
  • A mask restored wrongly. Lanes that should be masked off silently write, and the output looks plausible with no crash and no error signal (§15.9, FM-2). The blueprint calls this the highest-leverage bug class in the project (§15.9).
  • Occupancy treated as a knob. It is the min() of three independent ceilings, so tuning block size without asking which resource binds is blind (MM2).
  • Streams assumed to be ordered. Across streams there is no order unless an event creates one, and code that "usually works" will eventually race (MM7, T7).
  • Speed before correctness. "Fast but wrong" execution cannot be told apart from correct execution without a conformance oracle (P1).

How it works, end to end

Follow one launch of the blueprint's vecadd kernel, gridDim=(1,1,1) and blockDim=(32,1,1), so exactly one warp with no divergence (§8). The boxes below are adapted from §3's diagram (names are the blueprint's crates):

  1. Front end. gpu-parser lexes and parses the kernel source with a hand-written recursive-descent parser and lowers it into the IR (ADR-06, §37). The IR is the only lowering target, so no front end talks to the scheduler directly (P5). It is an SSA basic-block graph (control flow graph, CFG) (ADR-07).
  2. Verifier. gpu-ir's verifier.rs is a separate pass and the single gate between untrusted source and the scheduler (ADR-15, §3, P6). A launch starts Submitted; if the verifier accepts it becomes Queued, else it is Rejected (§8). Source that declares a pointer ptr shared but loads it with ld.global is parsed fine and then rejected with GpuError::StateSpaceMismatch (§8). §8 says the verifier (I7) rejects it "at lowering time", and the Phase 1 fixture table again names the verifier (§13.5). Yet I7's own text names only unreachable blocks and dangling SSA references (§7), and §13.2 step 8 builds the detection into lowering.
  3. Runtime. gpu-runtime (launch.rs) validates the LaunchConfig against the §4 limits (I8), enqueues a DispatchPacket::KernelLaunch on the caller's stream and returns, because every host call is asynchronous by default (§17.2 step 1, P13).
  4. Driver. gpu-driver holds the command buffer and a ring-buffer queue of at most 4,096 in-flight packets, consumed in the order received (§4, ADR-22, I12). The device sits behind a trait (virtual_device.rs, ADR-21, P8).
  5. Scheduler. gpu-scheduler runs the occupancy pass (Queued to Scheduled, I15), forms warps of 32 (Scheduled to Running, I1), keeps the mask stack and barrier unit, and picks the next warp with greedy-then-oldest (§8, §15.2, ADR-18).
  6. Emulator and memory. gpu-emulator steps one warp-instruction at a time for each active lane (§3, P1, P2). Loads and stores go through gpu-memory, which checks each access against a live allocation (§16.2 step 4, §14.2 step 4, I6). The five vecadd steps are traced in the first core idea.
  7. Completion. When all blocks finish the launch is Completed, and events waiting on it may signal (§8, I10). gpu-profiler records timeline, occupancy and bandwidth, which gpu-cli consumes (§3).

The blueprint is inconsistent about the instruction set. §8's table lists mad, cvt and bra.uni forms, but the Instruction enum in §11 has no variant for mad or cvt, and its Branch variant carries only an optional condition and a target, with no uniform flag (§8, §11).

The core ideas

Warps and the active mask (§8, I1, I2, MM1)

A launch is a grid of blocks, and each block is split into groups of 32 threads called warps (§8, I1). The warp is the unit of lockstep execution (§36). The hierarchy, drawn from §8:

A warp has one instruction stream. Each lane has an on/off flag, and the 32 flags together form the active mask, exactly 32 bits wide (I2, P11). This is SIMT: SIMD with per-lane masking, not independent threads (MM1, §36). A block size that is not a multiple of 32 leaves the last warp partly filled, and lanes past blockDim are masked off at warp formation (§15.8). Execution touches only active lanes, and running an inactive lane and discarding the result is a named pitfall because stores and register writes have side effects (§16.2 step 3, §16.6). The vecadd trace (§8):

Step Instruction Effect (all 32 lanes active, mask=0xFFFFFFFF)
1 ld.global.u32 r1, [a + tid*4] each lane loads its a[tid]
2 ld.global.u32 r2, [b + tid*4] each lane loads its b[tid]
3 add.u32 r3, r1, r2 each lane computes a[tid]+b[tid]
4 st.global.u32 [c + tid*4], r3 each lane stores its c[tid]
5 ret warp retires, block completes

Divergence, reconvergence and barriers (§15, I13, I3)

A branch is divergent when lanes of one warp take different paths (§36). The scheduler keeps a stack of (mask, target) pairs per warp (reconverge_stack, §11, P11). On a divergent bra it pushes (inactive_mask, reconverge_target), where the target comes from the §13 dominator analysis (§15.2 step 4, I13). When the warp's program counter reaches that target it pops (§15.2 step 5). Every push must have exactly one matching pop (§15.2 step 9, §15.5), nesting must not hit a hard-coded stack-depth ceiling shorter than the kernel's CFG depth (§15.8), and a warp whose active lanes drop to zero retires cleanly (§16.8). The blueprint names the reconvergence point as the immediate dominator (I13, §36). If a kernel has no unique one, the verifier rejects it (I13, ambiguous_reconverge.gpu in §13.4).

The Phase 3 fixture runs an if/else on tid < 16 and asserts the exact mask sequence, lane for lane (§15.2 step 8, §15.4). The blueprint calls the expected result a "hand-derived expected trace" and does not print it (§15.4).

A barrier (bar.sync) is a rendezvous: it releases only when every live thread in its scope has arrived (I3, MM5). A thread that is trapped in a divergent branch must not be counted as arrived, since that is FM-1's root cause (§15.6). A barrier inside a still-divergent region is itself invalid usage, which the verifier should flag where feasible and which otherwise surfaces as FM-1 at runtime (§15.8). Deadlock is caught by a fixed 2 s wall-clock watchdog (§4, I3), and the blueprint poses the choice of a timeout over cycle detection as an open question (§33 item 14).

Occupancy is a min of three limits (§32, I15, ADR-20, MM2)

Occupancy measures how much of a simulated SM's warp-slot capacity a kernel fills (§36). It is the min() of the register-limited, shared-memory-limited and warp-slot-limited "waves" (I15). The scheduler computes it on every launch from the kernel's declared budgets and never from a guess (P4). The blueprint's worked example (§32 items 1 to 4):

Limit Blueprint's arithmetic Warps
Warp slots 64 resident warps per SM (§4); at 32 threads each that is 2,048 threads 64
Registers, 64 per thread 65,536-register file ÷ 64 = 1,024 threads = 32 warps 32
Shared memory, 16 KiB per block, 256 threads per block 48 KiB ÷ 16 KiB = 3 blocks, 8 warps per block 24
Achieved min(32, 24, 64) = 24 warps = 768 threads, 37.5% of the 2,048-thread ceiling 24

Two wording problems sit in this example. The 65,536-register file is an assumption ("standard CUDA-generation figure"), and §4 gives only the 255-registers-per-thread cap (§32 item 2, §4). And §32 item 3 divides the 48 KiB by per-block usage as if it were a per-SM total, while §4 lists the row as "Max shared memory per block" with the value "48 KiB (simulated SM budget)" (§32 item 3, §4). OccupancyReport carries the three limits and achieved_occupancy as a u32, commented "min of the three" (§11), whereas the glossary calls occupancy a fraction of warp-slot capacity (§36); §32 item 4 states both, 24 warps and 37.5%.

Reserving resources per block matches the CUDA occupancy calculator exactly (ADR-20). Computing a sum instead of a min() always overestimates (§15.6, FM-11). MM2 predicts that cutting registers per thread can raise occupancy with no other change, and MM6 adds that maximal occupancy is not automatically fastest (MM2, MM6). Whether I15 must change because of that is left as a question (§33 item 10).

Memory spaces and coalescing (§8, §14, I6, I14, MM4)

There are five memory spaces: global, shared, constant, local and register (§3, §11). Every access is checked against a live DeviceAllocation and aborts the kernel with GpuError::InvalidAddress otherwise (I6). The allocator uses slab/bump arenas per size class (ADR-16), and host-device copies use an explicit latency that depends on size, not a fixed constant (ADR-17, §14.6).

Coalescing is judged on the warp's whole address set for one instruction, not thread by thread (MM4, §14.6). The classifier takes the active lanes' addresses and returns Coalesced, Strided or Scattered (§14.2 step 6, §14.8). It must be a pure function of that pattern (I14). In vecadd, steps 1, 2 and 4 access base + tid*4, a unit-stride 32-lane pattern, classified Coalesced with a single memory transaction per warp (§8). Phase 2's fixture requires unit stride to be Coalesced and a random permutation of the same size to be Scattered (§14.4). The blueprint defines only those two cases and does not say what makes an access Strided (§14.2). MM4 says transposing an access pattern can change measured bandwidth by an order of magnitude with identical per-thread code (MM4).

Streams, events and the command queue (§17, §18, I9, I10, P12)

Operations in one stream run in enqueue order (I9). Operations in different streams have no order unless an event adds one, so streams form a partial order, a DAG (P12, MM7). An event signals only after everything enqueued before it in its own stream has finished, not when it was enqueued (I10, §17.6). The packet kinds are KernelLaunch, MemcpyH2D, MemcpyD2H, EventRecord and EventWait (§11). The Phase 5 fixture puts two kernels on separate streams with an event dependency (§17.2 step 8). In event_dependency.json, stream B's kernel, which event.wait()s on stream A's event, must never observe stream A's output before it is written (§17.4, I10). Its companion streams_independent.json asserts the opposite case: two independent streams' kernels may finish in either order, and no ordering is assumed (§17.4, §17.5).

stream.sync() waits on a real completion signal (a tokio notification), never a sleep (§17.6, §17.7, ADR-02). The queue is a bounded ring buffer: the 4,097th packet on a 4,096-capacity queue is rejected with a documented error, not a panic (§18.4, §18.2 step 6). Two DMA transfers with overlapping address intervals and no declared dependency are serialized, and overlap is tested by interval, not pointer equality (I16, §18.4, §18.6).

Determinism and replay (§16, P2, I11)

The same kernel, inputs and launch config must give the same instruction-step trace on every run (I11, P2). That needs a fixed, documented order in which resident warps step, and a HashMap iteration order is explicitly unacceptable (§16.2 step 6, §16.6, P10). The emulator appends (warp_id, pc, active_mask) per step to a postcard-encoded log (§16.2 step 8, ADR-08), and replaying one captured trace twice must give byte-identical logs (§16.2 step 11, §16.5). The price is that warps cannot free-run in parallel inside one simulated SM (P2).

The trade-offs — where engineers disagree

Mask stack with static reconvergence (ADR-19)

Chosen: an active-mask stack with immediate-dominator reconvergence, because it is simpler to implement and verify first (P1), with dynamic warp formation deferred (§9). Rejected: dynamic warp formation (Fung et al. 2007) (§9). When the rejected choice is right: a throughput-maximizing production simulator willing to absorb DWF's extra bookkeeping complexity (§9).

Per-block resource reservation (ADR-20)

Chosen: reserve resources per block, which matches the CUDA occupancy-calculator model exactly (I15, §32). Rejected: a per-wave running estimate (§9). When the rejected choice is right: a scheduler experimenting with sub-block resource sharing, which per-block reservation cannot express (§9).

Tree-walking interpreter (ADR-09)

Chosen: a tree-walking interpreter, for simplicity and determinism-first correctness, with the JIT deferred (P1, P2, §9). Rejected: threaded-code or JIT execution (§9). When the rejected choice is right: a performance-critical deployment willing to trade determinism-under-debugging for raw throughput (§9). The blueprint names interpreter dispatch as bottleneck number 1 (§29).

SSA control-flow graph IR (ADR-07)

Chosen: an SSA basic-block CFG, which enables dominator-based reconvergence analysis (I13) and standard verifier techniques (§9). Rejected: stack-machine bytecode (§9). When the rejected choice is right: an interpreter-only design with no static analysis needs, where stack bytecode is simpler (§9).

A standalone verifier pass (ADR-15)

Chosen: one explicit verifier pass, a single auditable gate between untrusted source and the scheduler (P6, I7, §9). Rejected: inline checks during lowering (§9). When the rejected choice is right: a closed, trusted-input-only pipeline where inline checks suffice (§9).

A ring buffer for commands (ADR-22)

Chosen: a ring buffer of dispatch packets, for bounded memory (§4) and cache-friendly sequential consumption (I12, §9). Rejected: a linked list (§9). When the rejected choice is right: a queue with highly variable, unbounded packet lifetimes, where a linked list's flexibility wins (§9).

Greedy-then-oldest warp scheduling (ADR-18)

Chosen: greedy-then-oldest, a throughput-oriented policy grounded in Narasiman et al. (2011), which needs an age counter per resident warp (§9, §15.7). Rejected: round-robin (§9). When the rejected choice is right: a fairness-critical teaching demo where round-robin's predictability is preferred (§9).

Roads not taken (§34, §35)

A hardware PTX-JIT backend (§34 AA1) wins when real GPU throughput matters more than pedagogy, as in production ML and HPC. The real system is NVIDIA's PTX-to-SASS JIT (ptxas). It is rejected because scope excludes real hardware (§34, §1).

A Vulkan/SPIR-V compute backend (§34 AA2) wins when cross-vendor portability, not CUDA semantics, is the goal. Its subgroups and descriptor sets would dilute the CUDA-specific SIMT semantics this project teaches (§34, §2).

A trace-based whole-graph JIT (§34 AA3) wins when a few workload shapes recur and fusion amortizes, as in ML training frameworks such as tinygrad's lazy graph or XLA. It would obscure the individual-kernel execution model the project exposes (§34, MM8).

A cycle-accurate timing simulator (§34 AA4) wins when the question is performance prediction, as in GPGPU-Sim. The blueprint says a full timing model would roughly double the implementation surface (§34, §1).

Deferred features (§35) each carry an un-defer trigger next to the phase they would extend. A real GPU backend waits for a concrete GPU target with driver access, SPIR-V lowering waits for the Vulkan backend, a profiling GUI waits until JSON and flamegraph export prove insufficient, and cycle-accurate timing waits for a performance-prediction research goal (§35).

What must never be false

  • I1, I2: warps are exactly 32 wide and the active mask is exactly 32 bits. Noticed by a width assertion at warp formation and a mask-width assertion; warp_width_violation_total (I2 is structural, with no counter) (§7).
  • I3: a barrier releases only when every live thread in scope has arrived. Noticed by the 2 s watchdog; barrier_wait_total, barrier_timeout_total (§7).
  • I4, I5: register and shared-memory use stay within the declared and simulated budgets. Noticed by a static check at verify time plus a launch-time re-check (I4) and a launch-time budget check (I5); register_budget_violation_total, shared_mem_budget_violation_total (§7).
  • I6: every device access is validated against a live allocation. Noticed by a per-access bounds and liveness check; oob_access_total (§7).
  • I7, I13: the verifier rejects unreachable blocks and dangling SSA references, and a divergent branch has a unique reconvergence point. Noticed by CFG, SSA and dominator-tree analysis; verifier_reject_total, reconvergence_ambiguous_total (§7).
  • I8: grid and block dimensions respect the §4 limits. Noticed by a check in launch(); launch_dim_violation_total (§7).
  • I9, I12: same-stream work, and queue packets at the driver, keep their order. Noticed by sequence-number checks; stream_order_violation_total, queue_order_violation_total (§7).
  • I10: an event signals only after prior work in its stream finished. Noticed by a completion-order assertion; event_order_violation_total (§7).
  • I11: identical inputs give an identical step trace. Noticed by a replay-diff test; replay_mismatch_total (§7).
  • I14: coalescing classification is a pure function of the warp's address pattern. Noticed by a property test (same pattern, same class); coalescing_classification_total (§7).
  • I15: occupancy equals the min of the three limits. Noticed by recomputation against a fixture; occupancy_miscalc_total (§7).
  • I16: overlapping DMA transfers never run concurrently without a declared dependency. Noticed by an interval-overlap check at submission; dma_overlap_total (§7).

What breaks in production

FM-1: a launch hangs. The root cause is a subset of threads that never reach bar.sync because of unbalanced divergence (I3). The 2 s watchdog detects it and faults the kernel automatically. An operator inspects the divergence trace, and the forensic aid is the captured mask-stack trace (§23).

FM-2: correct-looking but wrong shared-memory output. The active mask was restored incorrectly (I13 violation). A differential fixture mismatch detects it. There is no automatic recovery because it is silent by nature, so bisect with the §15.5 divergence fixtures and diff the mask sequence against the expected trace (§23).

FM-6: corrupted device memory after concurrent transfers. Overlapping DMA regions ran together without a declared dependency (I16). A byte-level race fixture catches it. Recovery is manual: bisect with dma_overlap_serialize.json-style fixtures, using the overlap-interval log taken at submission (§23, §18.4).

FM-7: a cross-stream read sees stale data. Event ordering was violated (I10). The event_dependency.json fixture fails. Nothing recovers automatically; patch the event-completion logic and add a regression fixture (§23).

FM-9: identical inputs give different traces. The causes are a nondeterministic warp-step order or unordered iteration in the scheduler or emulator (I11). The replay-regression suite detects it. It has to be fixed, not auto-recovered, and the aid is a step-by-step diff of the two traces (§23).

FM-11: a launch is rejected or under-scheduled despite enough resources. The occupancy formula is wrong, such as a sum instead of min(), or a stale budget (I15). An occupancy fixture mismatch detects it, and the rejection itself is the safe failure. The aid is an OccupancyReport dump against the hand-computed §32 expectation (§23).

FM-12: two streams deadlock on each other's events. A circular event-wait, made by the caller or by a runtime bug. Detection is a stream-sync timeout that "mirrors the §4 watchdog pattern", and the fault comes after the watchdog window (§23). §4 lists only the barrier timeout (2 s) and gives no separate value for stream sync (§4, §23).

Threats worth knowing (§22):

  • T1, adversarial IR that slips past the verifier, such as a kernel with ambiguous reconvergence, is met by the dominator check (I13) and by fuzzing; verifier_reject_total (§22).
  • T3, use-after-free when a caller frees a DeviceAllocation still used by an in-flight kernel, is met by ownership-validated allocation and a liveness check on each access (P7, I6); the kernel aborts with InvalidAddress (§22).
  • T8, queue flooding by submitting faster than the queue drains, is met by the bounded ring buffer and a queue-full rejection; queue_full_reject_total (§22, ADR-22).
  • T10, scheduler starvation by a mix of low-occupancy launches, is met by occupancy-aware admission and fairness accounting, which §22 and FM-5 attribute to ADR-18, although §9 defines ADR-18 as the greedy-then-oldest policy (§22, §23, §9).
  • T12, a path-traversal-style write through a caller-controlled profiler export filename, is met by filename validation and a configured export directory; export_path_reject_total (§22).

How it compares

  • NVIDIA CUDA chose real silicon timing and throughput, at the cost of being a black box for the exact semantics this project teaches. That is right whenever real GPU throughput is the goal (§31).
  • AMD ROCm/HIP chose source compatibility with CUDA at a different lockstep width, 64-lane wavefronts against a 32-lane warp. That is right when portability across AMD and NVIDIA hardware without a rewrite matters, though ported code with wavefront-width assumptions needs re-validation (§31, I1).
  • GPGPU-Sim chose to model cycle-accurate timing, not just function (Bakhoda et al. 2009). That is right when the research question is "how fast", which is exactly what this project's non-goals exclude (§31, §1).
  • Intel ISPC chose a SIMD gang width fixed at compile time, targeting real CPU SIMD with no runtime warp scheduler. That is right when the target is genuine CPU vectorization, at the cost of losing the warp-formation and occupancy story (§31).

Questions to test yourself

  1. Why is occupancy a min() across three resource dimensions rather than a weighted sum, and what real kernel shape would break if it were a sum instead? — Hint: §32 items 2 to 4 and the §15.6 pitfalls.
  2. Why does the active-mask stack need the immediate dominator specifically, rather than any block that happens to be reachable from both divergent branches? — Hint: I13, the §8 failure-path example and §13.9.
  3. Why is the emulator required to skip inactive lanes entirely rather than execute them and discard results, given that both approaches produce the same visible register state for a pure-arithmetic instruction? — Hint: §16.6 and P11.
  4. Why does stream.sync() need a real completion signal instead of a fixed-delay sleep, given that this is a simulator with no real hardware latency? — Hint: §17.6, §17.7 and I9.
  5. Why does the DMA overlap check (I16) operate on address intervals rather than allocation identity, and what bug would interval-based-by-identity checking miss? — Hint: §18.6, §18.8 and T9.

If you only remember three things

A warp is one instruction stream with per-lane on/off masks, so cost follows the paths taken, and every mask push, pop and barrier must be modelled exactly (MM1, MM3, P11, I13). Occupancy and coalescing are collective facts, a min() of three limits and the shape of a whole warp's addresses, never per-thread guesses (I15, I14, MM2, MM4). Correctness comes before speed, so runs are deterministic and replayable, synchronization is explicit, and differential fixtures gate every optimization (P1, P2, P3, I11, P14).

Words used here

  • SIMT: one instruction stream per warp with per-lane masking (§36, MM1).
  • Warp: the fixed 32-thread lockstep group and the scheduler's basic unit (§36, I1).
  • Active mask: the per-warp bit-per-lane flags saying which lanes execute now (§36, I2).
  • Divergence: lanes of one warp taking different control-flow paths, which requires masking (§36).
  • Reconvergence: the point where diverged lanes resume together, the immediate dominator in this design (§36, I13).
  • Occupancy: how much of a simulated SM's warp-slot capacity a kernel fills (§36, I15).
  • Memory coalescing: classifying a warp's collective access pattern for bandwidth accounting (§36, I14).
  • Barrier (bar.sync): a block-scoped rendezvous where all participants must arrive (§36, I3).
  • Stream: an ordered, asynchronous sequence of enqueued operations (§36, P12).
  • Event: a marker of completion of prior work in a stream, used for cross-stream order (§36, I10).
  • Dispatch packet: one encoded operation (launch, memcpy, event) submitted to a queue (§36).
  • DMA: the simulated transfer engine that moves data without host CPU involvement in the model (§36).
  • Verifier: the pass that gates untrusted kernels before scheduling (§36, I7).
  • Watchdog: a timeout that detects a stalled operation such as a barrier deadlock (§36, FM-1).
