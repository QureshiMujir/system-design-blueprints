92 — Zero-Knowledge Proof (Basic SNARK)

Project Number: 92

Project Name: Zero-Knowledge Proof (Basic SNARK)

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

A from-scratch Rust implementation of a pairing-based zero-knowledge Succinct Non-interactive ARgument of Knowledge (zk-SNARK), teaching the complete pipeline from first-principles interactive proofs to a production-shaped Groth16 prover/verifier: the GMR definition (completeness, soundness, zero-knowledge), Sigma protocols (Schnorr identification), the Fiat–Shamir transform for non-interactivity, arithmetic-circuit compilation to R1CS, the R1CS→QAP arithmetization, the KZG polynomial commitment scheme, a Groth16-style SNARK over BN254/BLS12-381, a two-phase trusted-setup (powers-of-tau) ceremony, and a differential conformance harness cross-checked against arkworks and bellman. This is a cryptographic protocol implementation, not a general proof-assistant, not a compiler for a high-level zero-knowledge DSL (no Circom-equivalent front-end language beyond a minimal internal IR), and not a blockchain/rollup product — it is the proving-system layer those products are built on.

System Boundaries

Provides: field/curve/pairing arithmetic kernel; a circuit IR + R1CS constraint builder; R1CS→QAP arithmetization; KZG10 polynomial commitment; a Groth16 prove/verify implementation; a two-phase trusted-setup ceremony (Powers-of-Tau + circuit-specific); Sigma-protocol (Schnorr) and Fiat–Shamir reference implementations; a differential conformance/fuzz harness against arkworks and bellman.

Delegates: does not implement a high-level circuit DSL/compiler (Circom-equivalent) beyond a minimal internal grammar (§8) sufficient to express conformance fixtures; does not implement GPU acceleration; does not implement recursive proof composition; does not implement PLONK, STARK, or Halo2 (all PhaseDeferred, §35).

Does NOT provide: on-chain verifier contracts (Solidity/EVM bytecode generation), distributed/networked proving-as-a-service, or a production ceremony-coordination web service — those are separate downstream projects that consume this library's Proof/VerifyingKey types.

Non-Goals

Not a general SNARK-agnostic framework (no pluggable-backend abstraction layer); not a universal-SRS system (Groth16's per-circuit SRS is the deliberate teaching point, §9 ADR-09); not optimized for GPU/FPGA throughput (PhaseDeferred("§29")); not post-quantum secure (pairing assumptions are classically and quantum-broken by Shor's algorithm — explicitly out of scope, contrast in §34).

Deployment Model

A Rust library workspace (no daemon, no network service) consumed by three binaries: zkp (setup/prove/verify/ceremony CLI), zkp-bench (Criterion + Prometheus-exporting benchmark runner), and the zkp-conformance differential-test harness (run in CI, not shipped). Target operators: cryptographic-engineering teams building a proving system into a larger product (rollup, private-transaction system, verifiable-computation service); target users of the library: Rust application developers linking zkp-groth16 directly.

In Scope (Phase 0 Deliverable — Ships)

  1. crates/zkp-field — prime-field arithmetic (Fr, Fq, Fq2, Fq6, Fq12), Montgomery representation, constant-time ops.
  2. crates/zkp-curve — BLS12-381 and BN254 group arithmetic (G1, G2), point compression, subgroup checks, cofactor clearing.
  3. crates/zkp-pairing — optimal ate Miller loop, final exponentiation, multi-pairing batching.
  4. crates/zkp-poly — dense polynomial arithmetic, radix-2 FFT/NTT, Lagrange interpolation, vanishing-polynomial construction.
  5. crates/zkp-circuit — circuit IR (gate list, wire allocation), minimal circuit DSL parser (§8 grammar), ConstraintSynthesizer trait.
  6. crates/zkp-r1cs — R1CS constraint system builder, sparse linear combinations, witness allocation, satisfaction checker.
  7. crates/zkp-qap — R1CS→QAP transform, H(x) quotient-polynomial computation.
  8. crates/zkp-kzg — KZG10 polynomial commitment scheme (commit/open/verify).
  9. crates/zkp-groth16 — Groth16 SNARK: setup, prove, verify.
  10. crates/zkp-setup — two-phase trusted-setup ceremony (Powers-of-Tau Phase 1, circuit-specific Phase 2), contribution verification.
  11. crates/zkp-sigma — Sigma-protocol trait + Schnorr identification, AND/OR composition.
  12. crates/zkp-transcript — Merlin-style Fiat–Shamir transcript, domain-separated challenges.
  13. crates/zkp-conformance — differential test harness vs. arkworks/bellman, test-vector corpus.
  14. crates/zkp-cli — zkp binary: setup/prove/verify/ceremony subcommands.
  15. crates/zkp-bench — Criterion benchmarks + Prometheus exporter for zkp-bench CLI.

Out of Scope (Deferred)

Full list with anchors lives in the Deferred Features Register (§35). Headline deferrals: PLONK arithmetization PhaseDeferred("§34"); STARK/FRI PhaseDeferred("§34"); Halo2/IPA-based recursive proving PhaseDeferred("§34"); recursive SNARK composition (proof-of-a-proof) PhaseDeferred("§29"); GPU-accelerated MSM PhaseDeferred("§29").

Recommended Language + Rationale

Rust (stable, 2021 edition). Rationale: no GC pauses in MSM/FFT hot loops (tail-latency critical, §4); the trait system (PrimeField, ConstraintSynthesizer) matches the layered arithmetic→circuit→proof-system structure without runtime dispatch cost; arkworks and bellman — the differential-test oracles this project depends on (§5) — are themselves Rust, enabling in-process (not subprocess/FFI) cross-implementation testing (ADR-01, ADR-12). Rejected: C++ (memory-unsafe for hand-written field arithmetic — the exact bug class this project's constant-time discipline, P6, exists to prevent); Go (GC pauses conflict with constant-time discipline and tail-latency targets, M3/M4); Python (2–3 orders of magnitude too slow for MSM/FFT at the constraint counts in §4); OCaml (excellent for the algebraic types but no mature pairing-friendly-curve ecosystem to differential-test against in-process).

Prerequisites

Modular arithmetic and finite fields; elliptic-curve group law; bilinear pairings (a full course, not a paragraph — Costello, §5); probability (negligible functions, statistical distance); basic computational complexity (PPT, NP, witness relations); Rust ownership/traits at an intermediate level.

Estimated Timeline

Phase 0 (repo skeleton + field/curve/pairing kernel): 2–3 weeks. Full Phase 0–9 build (interactive proofs → Sigma → Fiat–Shamir → R1CS → QAP → KZG → Groth16 → trusted setup → conformance): 7–9 months for a small team (2–3 engineers) working part-time alongside the required-reading load (§5); a solo engineer following this blueprint sequentially should budget 10–14 months given the cryptographic-engineering learning curve.

2. Why Build This

Zero-knowledge SNARKs are the proof technology behind private transactions (Zcash), validity rollups (zkSync, StarkNet, Polygon zkEVM), and verifiable off-chain computation generally. This project builds the entire chain of abstractions between "I know a witness" and "here are 192 bytes that prove it in 5 ms" — no step is a black box. It teaches: (1) how a proof system's security definition (GMR) constrains every downstream engineering choice; (2) how an interactive protocol becomes non-interactive (Fiat–Shamir) and what that costs in the security model (random oracle idealization, §5 Bellare–Rogaway); (3) how a general computation becomes linear algebra (R1CS) and then polynomial identity-testing (QAP) — the single most important conceptual bridge in the whole field; (4) how a bilinear pairing collapses a polynomial identity check into three group elements; (5) why a trusted setup is the sharpest edge in the entire design, operationally and cryptographically.

Cross-links to sibling systems in this portfolio: the field/curve/pairing kernel (§12 Phase 0) generalizes directly to any pairing-based protocol (BLS signatures, threshold cryptography); the R1CS/QAP arithmetization (§16–17) is the same technique used by every circuit-based proving system in the Comparative Architecture Table (§31); the differential-conformance methodology (§21 Phase 9) is the calibration discipline this portfolio applies to every from-scratch cryptographic reimplementation (compare the block-cipher and hash-function projects' KAT-vector harnesses).

What Mastery Looks Like. After building this system, an engineer can: (1) explain precisely why Groth16's CRS must never be reconstructible, and design a ceremony that makes that infeasible (§20 Phase 8); (2) diagnose a "valid proof rejected" bug by tracing transcript/domain mismatches rather than guessing (§15 Phase 3, §17 Phase 5); (3) read any SNARK paper's security proof and map its "extractor" and "simulator" to concrete code paths (§13 Phase 1); (4) choose between Groth16, PLONK, STARK, and Bulletproofs for a new system with a quantified rationale, not a vibe (§34); (5) audit a third-party circuit for the under-constraint vulnerability class that has caused real fund losses in production SNARK systems (§16 Phase 4, §22 T6); (6) reason about pairing-based cryptography's post-quantum exposure and when that matters (§34); (7) design and gate a cryptographic differential-test harness for any from-scratch protocol reimplementation (§21 Phase 9).

6. Design Principles

  • P1 — Correctness Before Speed. Soundness/completeness must be differential-tested (§21) before any optimization lands. Tradeoff: slower initial velocity. Operational implication: the conformance gate (M11) blocks merge. Violating it breaks: silent forged-proof acceptance.
  • P2 — Canonical Form Everywhere. Every field element, curve point, and serialized byte string has exactly one valid representation. Tradeoff: extra reduction/compression steps per operation. Operational: prevents malleability. Violating it breaks: non-unique proof identifiers, signature/proof malleability.
  • P3 — Toxic Waste Is Radioactive, Not Confidential. Ceremony secrets (τ, α, β, γ, δ) are destroyed, never stored or rotated like ordinary secrets. Tradeoff: no "recover the key" path — there is none, by design. Operational: ceremony runbook mandates zeroize + attestation. Violating it breaks: arbitrary proof forgery (T1).
  • P4 — Every Number in §4 Is Derived, Never Asserted. Every capacity/latency target traces to a formula in §32. Tradeoff: more upfront arithmetic before writing a target. Operational: benchmarks gate on the derived number. Violating it breaks: silent capacity-planning failure.
  • P5 — Differential Testing Is the Practical Oracle. Absent a machine-checked proof, agreement with ≥2 independent implementations on identical inputs is the strongest available signal. Tradeoff: shared-bug blind spot. Operational: 3-way agreement required (self/arkworks/ bellman). Violating it breaks: undetected implementation-specific soundness bugs.
  • P6 — Constant-Time on Every Secret-Dependent Path. Witness-dependent field/scalar operations never branch or index by secret value. Tradeoff: slower than variable-time equivalents. Operational: dudect gate (M13). Violating it breaks: timing side-channel witness recovery (T4).
  • P7 — Transcripts Are Append-Only and Total. The Fiat–Shamir transcript binds every prior message before deriving a challenge. Tradeoff: larger hash input per challenge. Operational: versioned label schema. Violating it breaks: forgery via transcript manipulation (T3).
  • P8 — Succinctness Is a Verifier-Side Property Only. Proof size/verify cost are O(1); prover cost is not, and is never capacity-planned as if it were. Tradeoff: none — definitional clarity. Operational: separate prover/verifier capacity docs (§28). Violating it breaks: mis-provisioned proving infrastructure (MM7).
  • P9 — One Bijective Arithmetization, Not Two Representations. R1CS and QAP are one transform, never independently maintained. Tradeoff: any circuit change regenerates both atomically. Operational: build pipeline enforces atomic regeneration. Violating it breaks: I6 completeness/soundness split.
  • P10 — Trusted-Setup Ceremonies Are Multi-Party by Construction, Never Single-Dealer in Production. ≥1-of-n honest participant, not blind trust in one operator. Tradeoff: ceremony coordination latency (M7). Operational: ceremony runbook, participant-diversity requirement. Violating it breaks: single-point-of-trust SRS compromise (T1).
  • P11 — Every Deserialized Point Is Subgroup-Checked Before Use. No curve point crosses a trust boundary without I5 validation. Tradeoff: extra cofactor-clearing cost per point. Operational: mandatory in zkp-curve deserialize path. Violating it breaks: small-subgroup/ invalid-curve attacks.
  • P12 — Determinism Is a Testable Invariant, Not an Assumption. Identical (circuit, witness, seed) must produce byte-identical output, verified by repeated-run tests. Tradeoff: explicit RNG injection everywhere (no hidden global RNG). Operational: I13 CI gate. Violating it breaks: silent nondeterminism masking real bugs (FC6).
  • P13 — Reference-Implementation Compatibility Is First-Class, Not Retrofitted. Byte-level serialization compatibility with arkworks is designed in from ADR-11. Tradeoff: constrains internal representation choices. Operational: I10 differential byte-comparison. Violating it breaks: an unusable conformance harness.
  • P14 — Every Circuit Ships With Its Linter Result. A circuit that hasn't passed the under-constraint linter is ineligible for Phase-2 setup, however "obviously correct" it looks. Tradeoff: linter false positives require explicit allow-listing. Operational: CI blocks setup on lint failure. Violating it breaks: under-constrained circuits accepting forged witnesses — the single most common real-world SNARK vulnerability class (T6/FC10).

8. Domain Model / Protocol / Data Model

Circuit DSL Grammar (EBNF)

circuit     ::= "circuit" ident "{" decl* constraint* "}" ;
decl        ::= visibility ident ("," ident)* ";" ;
visibility  ::= "public" | "witness" ;
constraint  ::= "constrain" expr "==" expr ";" ;
expr        ::= term (("+" | "-") term)* ;
term        ::= factor ("*" factor)* ;
factor      ::= ident | number | "(" expr ")" ;
ident       ::= letter (letter | digit | "_")* ;
number      ::= digit+ ;

Worked Example: x^3 + x + 5 = 35

The canonical pedagogical circuit (witness x=3, public out=35; witness vector indices [one, out, x, sym_1, y, sym_2] = [1, 35, 3, 9, 27, 30]):

Constraint A (nonzero terms) B (nonzero terms) C (nonzero terms)
1: x·x = sym_1 x=1 x=1 sym_1=1
2: sym_1·x = y sym_1=1 x=1 y=1
3: (y+x)·1 = sym_2 y=1, x=1 one=1 sym_2=1
4: (sym_2+5)·1 = out sym_2=1, one=5 one=1 out=1

R1CS satisfaction: (A·w) ⊙ (B·w) = (C·w) element-wise for the witness vector w above (I11). QAP identity (§17): interpolating each column of A, B, C as degree-3 polynomials over a size-4 evaluation domain with vanishing polynomial Z(x), satisfiability becomes A(x)·B(x) − C(x) = H(x)·Z(x) for some polynomial H(x) (I6) — this is the exact identity Groth16's pairing check (§19) verifies at a single random point, encoded in the exponent.

Malformed-Input Example

A serialized G1Affine with the compressed-point flag bit set but coordinate bytes decoding to a value ≥ the base-field modulus, or an infinity flag combined with nonzero coordinate bytes: rejected by from_compressed() with PointError::NotOnCurve / PointError::ZeroInfinity before any subgroup check runs (I5, fixture malformed_point_overflow.bin, §21 N.5).

Failure-Path Example: Verifying-Key/Circuit Mismatch

An operator wires VerifyingKey for circuit "RangeCheck" to a verifier endpoint that actually receives proofs generated under the ProvingKey for circuit "Multiply," where both circuits happen to share the same public-input count. Without a circuit_hash binding (T11), the pairing equation may coincidentally still fail (PK/VK do not algebraically match) — but this is accidental, not structural, safety. The design fix: VerifyingKey.circuit_hash (§11) is checked at load time; the verifier refuses to initialize against a proof/VK pair whose hash doesn't match the operator-declared circuit, converting a silent-maybe-safe mismatch into a loud, structural one (§22 T11, §23 FC-9's sibling class).

12. Phase 0 — Repository Skeleton & Finite-Field / Elliptic-Curve Arithmetic Kernel

0.1 Objectives

Stand up the Cargo workspace (15 crate stubs, §10); implement Fr/Fq Montgomery-form field arithmetic and BLS12-381 G1/G2 group law (short Weierstrass, a=0); BN254 kept as a parallel, feature-flagged path for later conformance (§21). No pairing, no circuits yet — this phase is the arithmetic floor every other phase depends on.

0.2 Detailed Implementation Steps

zkp-field: from_repr/to_repr with canonical-range check (I4); Montgomery add/sub/mul (ADR-02); invert via Fermat's-little-theorem exponentiation (constant-time, P6, anchors: Costello Ch. 1–2, Washington Ch. 2). zkp-curve: affine/projective point addition and doubling formulas; is_on_curve; is_in_correct_subgroup via the endomorphism-accelerated check (not full-order scalar multiplication — too slow, anchors: ADR-03, ADR-04); clear_cofactor. Constant-time conditional-select (subtle::Choice) on every secret-dependent branch (P6, I5).

0.3 Deliverable

cargo test -p zkp-field -p zkp-curve green on both curves; zkp field-check CLI subcommand prints modulus, confirms a round-trip from_repr(to_repr(x)) == x, and runs the invalid-point corpus.

0.4 Acceptance Criteria

100% pass on ≥200 known-answer field-arithmetic vectors cross-checked against ark-bls12-381 (dev-dependency, ADR-12); subgroup check rejects 100% of a 50-vector invalid-point corpus (I5); dudect |t| < 4.5 over 10^5 samples on mul/invert (M13).

0.5 Conformance Fixtures

field_kat_bls12_381.json (known-answer field ops) | field_kat_bn254.json | invalid_points_corpus.bin (50 malformed/off-curve/wrong-subgroup points, expect reject) | montgomery_roundtrip.json (from_repr/to_repr identity, expect equal).

0.6 Pitfalls

Missing the final conditional subtraction in Montgomery reduction — silently wrong only above a threshold value, caught by I4; naive full-order-scalar subgroup check is correct but too slow for M8 — use the endomorphism trick; sign ambiguity on point decompression (two y per x) — pick canonical lexicographically-smallest per ADR-11; BN254/BLS12-381 code sharing a hardcoded limb count (4 vs. 6) silently truncates the larger field.

0.7 Performance Concerns

4/6-limb arrays fit 1–2 cache lines; allocation-free arithmetic (fixed arrays, not Vec); batch operations amortize Montgomery-form conversion at the API boundary (M8 depends on this); branchless conditional-select (P6) has bounded overhead vs. a branching equivalent.

0.8 Edge Cases

Point-at-infinity arithmetic (additive identity); doubling (P == Q in the addition formula); zero-scalar multiplication; modulus-adjacent values (p-1, p itself, rejected by I4); malformed byte length on deserialize (PointError::InvalidLength).

0.9 Failure Analysis

A wrong field result is silent — no crash, no signal — with total blast radius (every downstream crate depends on this kernel). Detection is exclusively I4 assertions plus conformance (§21); containment blocks all downstream CI until fixed; recovery is patch + full conformance re-run; see FC1 (§23).

0.10 Operational Notes

tracing span field_op (ADR-16) records op kind + curve for cross-curve perf correlation; no metrics emitted by default (ADR-17, library posture); no persistent state, so no migration/rollback concerns at this phase.

13. Phase 1 — Interactive Proofs & the GMR Definition

1.1 Objectives

Implement the formal GMR framework (completeness, soundness, zero-knowledge) as executable scaffolding — not yet a SNARK — using the graph 3-coloring zero-knowledge protocol (GMW) as the concrete toy example, plus a deterministic simulator harness that exercises I1–I3 directly.

1.2 Detailed Implementation Steps

Define InteractiveProof trait: prover_commit, verifier_challenge, prover_respond, verifier_check (anchors: P1, GMR85). Implement the graph 3-coloring protocol: prover commits to a random permutation of a valid coloring (via a commitment scheme — simple hash-based Pedersen- style commitment, not yet Groth16); verifier picks a random edge; prover opens the two endpoint colors; repeat k rounds for soundness error (1 - 1/|E|)^k (anchors: GMW91, I2). Build the simulator: given only the graph (no coloring), produce a transcript computationally indistinguishable from a real one by using the verifier's challenge as an oracle (rewind-and-retry construction) — this is the executable heart of I3.

1.3 Deliverable

zkp-conformance "toy-ip" harness: runs N rounds of the real protocol and N rounds of the simulator, and a statistical distinguisher (chi-squared test on transcript-distribution features) that must fail to distinguish them.

1.4 Acceptance Criteria

Soundness-error measured empirically over 10,000 cheating-prover trials (invalid coloring) matches the theoretical (1 - 1/|E|)^k bound within 1% for k=40 rounds; distinguisher p-value > 0.05 (fails to reject indistinguishability) across ≥ 5,000 simulated vs. real transcripts (I3).

1.5 Conformance Fixtures

3coloring_valid.json (graph + valid coloring, expect accept) | 3coloring_invalid.json (graph + invalid coloring, expect reject after k rounds w.h.p.) | simulator_transcripts.json (5,000 simulator outputs for the distinguisher test).

1.6 Pitfalls

Treating "the verifier never sees the coloring" as sufficient for zero-knowledge — real ZK requires a simulator, not merely secrecy of the witness (MM6); reusing the same commitment randomness across rounds breaks hiding (T2-adjacent); an under-sized k (few rounds) silently weakens soundness below the acceptance threshold — always derive k from the target error bound, never hardcode a round count.

1.7 Performance Concerns

Commitment-scheme cost dominates per-round latency at this toy scale (no MSM/pairing yet); k rounds means k× the commitment cost — this phase is intentionally not optimized, since its purpose is pedagogical clarity, not the perf targets in §4 (those apply from Phase 6 onward).

1.8 Edge Cases

Graph with a single edge (k derivation degenerates); disconnected graph (some vertices never challenged); prover attempting to bias challenge selection (verifier's randomness must be independent of prover's commitment — enforced by commit-then-reveal ordering).

1.9 Failure Analysis

A broken simulator (distinguishable from real) is a zero-knowledge failure, not a completeness/soundness one — must not be conflated in triage; detection is the chi-squared gate; containment is local to Phase 1 (no downstream crate depends on the toy protocol); recovery: patch simulator construction, re-run distinguisher at higher sample count.

1.10 Operational Notes

tracing span toy_ip_round records round number + accept/reject; this phase's harness is CI-gated but not part of the production library surface (§10 examples/, not crates/* public API surface beyond zkp-sigma's later reuse of the commit/challenge/respond shape).

14. Phase 2 — Sigma Protocols: Schnorr Identification & Composition

2.1 Objectives

Implement the SigmaProtocol trait (§11) and the Schnorr identification protocol over zkp-curve group elements; implement AND-composition (parallel independent statements) and OR-composition (proof of knowledge of one of two witnesses, Cramer–Damgård–Schoenmakers style).

2.2 Detailed Implementation Steps

SchnorrProtocol::commit samples k, computes R = g^k (anchors: Schnorr91, P6 constant-time scalar mult); challenge reads from an interactive verifier-supplied random scalar (this phase stays interactive — Fiat–Shamir is Phase 3); respond computes s = k + c·w mod r; verify checks g^s == R · Y^c. AND-composition: run two independent Sigma instances sharing one challenge. OR-composition: simulate the un-known branch (using the simulator technique from Phase 1, I3) while proving the known branch honestly, then split the challenge additively (anchors: I3, Boneh–Shoup Ch. 19).

2.3 Deliverable

zkp-sigma crate compiling and passing unit tests for single, AND, and OR Schnorr proofs against a manually scripted interactive verifier in examples/schnorr_identification.rs.

2.4 Acceptance Criteria

Special-soundness extractor test: given two accepting transcripts (R, c1, s1) and (R, c2, s2) for the same commitment R with c1 ≠ c2, the extractor recovers w matching the original witness in 100% of 1,000 randomized trials (I2-analogue for Sigma protocols); OR-proof reveals zero information about which branch is real across a 10,000-trial statistical test (I3).

2.5 Conformance Fixtures

schnorr_valid.json | schnorr_forged_response.json (tampered s, expect reject) | schnorr_and_composition.json | schnorr_or_composition.json (branch-hiding test vectors).

2.6 Pitfalls

Reusing the ephemeral scalar k across two proofs of the same witness leaks w algebraically (the exact real-world nonce-reuse catastrophe class, T2, MM6); forgetting to bind the statement Y into the challenge derivation (this becomes critical once Fiat–Shamir is added in Phase 3, P7); OR-composition challenge-splitting arithmetic error silently breaks either soundness or zero-knowledge depending on which side is wrong — test both properties independently.

2.7 Performance Concerns

Single scalar multiplication per commit/response — negligible relative to later MSM-dominated phases; constant-time scalar multiplication (P6) is the dominant cost here and is the first place M13's dudect gate applies.

2.8 Edge Cases

Challenge c = 0 (degenerate, must still verify correctly); witness w = 0 (identity edge case in the group); OR-composition where both branches are simultaneously true (protocol must still only reveal "at least one," not "which," even then).

2.9 Failure Analysis

A forged response passing verify is a soundness break — highest severity, blocks all downstream Sigma-based work (including the Fiat–Shamir transform in Phase 3, which inherits Schnorr's soundness properties); detection via the special-soundness extractor test; recovery: patch the verification equation, add a regression fixture.

2.10 Operational Notes

tracing span sigma_round tagged with protocol variant (single/AND/OR); no persistent state; this crate's public API (SchnorrProtocol, SigmaProtocol trait) is reused unchanged by Phase 3 (only the challenge source changes, from interactive to transcript-derived).

15. Phase 3 — Fiat–Shamir Heuristic: Non-Interactive Sigma Protocols

3.1 Objectives

Transform Phase 2's interactive Schnorr protocol into a non-interactive proof via the Fiat–Shamir heuristic, built on the zkp-transcript Merlin-style transcript (§11); establish the Random-Oracle-Model framing for why this is secure and where that assumption can fail.

3.2 Detailed Implementation Steps

zkp-transcript::Transcript: domain-separated append_message/challenge_scalar over BLAKE2b (anchors: ADR-10, Bellare–Rogaway93). Non-interactive Schnorr: prover appends the statement Y and commitment R to the transcript before deriving c = challenge_scalar(...) (I8, P7); proof becomes (R, s) only — no verifier round-trip. Verifier re-derives c' from the same transcript construction and checks g^s == R · Y^{c'}.

3.3 Deliverable

zkp-transcript crate + non-interactive SchnorrProof variant in zkp-sigma; end-to-end examples/schnorr_identification.rs updated to a single-message proof.

3.4 Acceptance Criteria

Transcript replay: an honest proof's c is bit-identical whether derived by prover or verifier in 100% of 1,000 trials (I8); a proof whose transcript omits Y (statement-binding ablation test) is forgeable in a scripted attack demonstration, proving why P7 is mandatory, not merely asserting it; forged-proof rejection rate 100% across a 500-vector tamper corpus.

3.5 Conformance Fixtures

fiat_shamir_valid.json | fiat_shamir_transcript_tamper.json (byte-flip in transcript input, expect reject) | fiat_shamir_missing_binding_demo.json (intentionally vulnerable variant, used only in the ablation test, never shipped as a real code path) | fiat_shamir_label_mismatch.json.

3.6 Pitfalls

Hashing "the important part" of the transcript instead of the full statement — the single most common real Fiat–Shamir implementation bug, and exactly what T3/P7 defend against; label collisions between differently-typed transcript entries (domain separation, ADR-10); treating the random-oracle idealization as unconditional security — it is not (MM3, Bellare–Rogaway93's own caveats about ROM separating from standard-model constructions).

3.7 Performance Concerns

One hash-to-field call per challenge — negligible cost relative to the scalar multiplication it gates; transcript state itself is small (fixed BLAKE2b state), no allocation growth with proof count since each Transcript is single-use (§11).

3.8 Edge Cases

Empty message append (zero-length label content, must still domain-separate correctly); challenge landing on 0 (must remain a valid, checkable proof, not a special-cased reject); concurrent transcripts for unrelated statements accidentally sharing a label string (namespace collision, caught by ADR-10's label-schema versioning).

3.9 Failure Analysis

A transcript-binding gap is a soundness break exploitable without any cryptographic breakthrough — purely an implementation bug (T3); detection is the ablation-demonstration test (3.4) plus fuzzing the transcript construction (ADR-13); recovery: patch binding order, add the missing message to the transcript schema, bump the label-schema version (ADR-10).

3.10 Operational Notes

tracing span fiat_shamir_challenge logs label + curve; the ablation-demo fixture (fiat_shamir_missing_binding_demo.json) is clearly namespaced and excluded from the production conformance gate (M11) to avoid accidentally treating a known-broken variant as a regression target.

16. Phase 4 — Arithmetic Circuits & R1CS

4.1 Objectives

Implement the circuit IR (§8 grammar), the ConstraintSynthesizer trait, and the R1CS constraint-system builder; ship the x^3+x+5=35 worked example (§8) as the first end-to-end circuit; ship the under-constraint linter (P14).

4.2 Detailed Implementation Steps

zkp-circuit: gate list (Add/Mul/Const/PublicInput/Witness), minimal DSL parser for the §8 EBNF grammar (anchors: ADR-08, circom/snarkjs reference). zkp-r1cs: ConstraintSystem::alloc_witness/alloc_public (I11 bounds-checked), sparse LinearCombination (ADR-07), enforce(a,b,c) appending one R1CS row, is_satisfied evaluating (A·w) ⊙ (B·w) = (C·w). Linter pass: flag any allocated witness wire never referenced by an enforce call ("unused signal," the precise real-world under-constraint bug class, anchors: P14, T6).

4.3 Deliverable

zkp-circuit/zkp-r1cs crates compiling; x^3+x+5=35 circuit expressed in the DSL, compiled to the 4-constraint R1CS instance from §8, satisfied by witness [1,35,3,9,27,30].

4.4 Acceptance Criteria

The compiled R1CS instance is byte-identical (matrix structure, not just satisfaction result) to an independently hand-derived reference matrix for the §8 example in 100% of runs (I11); linter correctly flags 20/20 synthetic under-constrained circuits in a labeled test corpus and passes 20/20 correctly-constrained ones (0 false positives/negatives on the corpus, P14).

4.5 Conformance Fixtures

circuit_multiply_by_5.dsl (the §8 worked example source) | r1cs_multiply_by_5_expected.json (expected A/B/C matrices) | underconstrained_corpus/ (20 labeled synthetic circuits) | malformed_dsl_syntax_errors.json (parser error-path fixtures).

4.6 Pitfalls

Off-by-one wire indexing between the DSL parser and the constraint system allocator (I11); the linter producing false negatives on constraints that are satisfiable but under-constrained relative to intended semantics (e.g., a missing range check that the DSL's type system cannot express — documented as a known linter limitation, not silently ignored, T6/FC10); public vs. witness wire confusion (a value meant to be public accidentally allocated as witness, breaking verifier-side input binding in later phases).

4.7 Performance Concerns

Linear-combination construction is O(constraints × avg-terms-per-row) — sparse representation (ADR-07) keeps this proportional to actual circuit complexity, not padded to a dense matrix; parser is not a hot path (compile-time only, run once per circuit, not per proof).

4.8 Edge Cases

A circuit with zero constraints (degenerate, must still type-check and produce an empty R1CS instance, not panic); a constraint referencing the same wire in A and B (squaring, valid); duplicate enforce calls for the same logical constraint (redundant but not incorrect — linter warns, does not block).

4.9 Failure Analysis

An incorrect R1CS compilation is a completeness break (valid witnesses rejected) if it over- constrains, or a soundness break (invalid witnesses accepted) if it under-constrains — the linter (P14) targets the latter, conformance (§21) targets both; blast radius is every phase downstream (QAP, Groth16); recovery: patch compiler, regenerate all fixtures referencing the affected circuit.

4.10 Operational Notes

tracing span r1cs_compile records constraint count + wire count; linter output is a structured report (JSON) consumed by CI to block Phase-2 setup (§20) on any unresolved warning (P14 operational enforcement).

17. Phase 5 — R1CS → QAP Arithmetization

5.1 Objectives

Implement the R1CS→QAP transform: interpolate each R1CS matrix column into a polynomial over an evaluation domain, construct the vanishing polynomial Z(x), and compute the quotient H(x) satisfying A(x)·B(x) − C(x) = H(x)·Z(x) for a satisfying witness (I6).

5.2 Detailed Implementation Steps

zkp-qap::r1cs_to_qap: pad num_constraints to the next power of two (domain size, anchors: GGPR13, ADR-05); build EvaluationDomain (zkp-poly) over that size; for each of the A, B, C matrices, treat each column as point-value pairs over the domain and ifft to obtain coefficient-form polynomials. compute_h_polynomial: evaluate A(x)·w, B(x)·w, C(x)·w as polynomials (linear combination of the column polynomials weighted by the witness), multiply A(x)·B(x), subtract C(x), divide by Z(x) via polynomial long division — must divide evenly for a valid witness (I6, anchors: P9, GGPR13, Pinocchio13 lineage).

5.3 Deliverable

zkp-qap crate; the §8 worked-example R1CS instance transformed to a 4-point-domain QAP, with H(x) computed and the identity verified directly (not yet via pairing — that is Phase 7).

5.4 Acceptance Criteria

Polynomial identity A(x)·B(x) − C(x) − H(x)·Z(x) == 0 (the zero polynomial) holds exactly for the §8 example's satisfying witness in 100% of runs (I6); an intentionally invalid witness (wrong x value) produces a nonzero remainder on division by Z(x) in 100% of a 50-vector negative corpus, confirming the divisibility check actually discriminates satisfying from non-satisfying witnesses.

5.5 Conformance Fixtures

qap_multiply_by_5_domain4.json (expected A/B/C/Z polynomials) | qap_h_poly_valid_witness.json | qap_h_poly_invalid_witness_nonzero_remainder.json | qap_domain_padding_edge.json (constraint count exactly a power of two, no padding needed).

5.6 Pitfalls

Domain-size mismatch between the R1CS row count and the QAP evaluation domain (off-by-one padding error) breaks completeness and soundness simultaneously (I6/FC4, MM4); polynomial long division implemented naively (not FFT-based) becomes the dominant cost at large constraint counts — defer to FFT-based division only when profiling (§28) confirms the naive path is the bottleneck; confusing "the witness satisfies R1CS" with "the polynomial identity holds" as two separate facts requiring two separate proofs, when they are definitionally the same fact (P9).

5.7 Performance Concerns

ifft/fft calls dominate this phase's cost — O(n log n) per matrix column set (M9 target); polynomial multiplication A(x)·B(x) is best done via forward-FFT/pointwise-multiply/inverse-FFT over a domain double the size (avoiding naive O(n²) convolution); memory: three polynomials of degree ~n plus the quotient, all resident simultaneously (contributes to M10).

5.8 Edge Cases

Domain size 1 (single-constraint circuit, degenerate but must not divide-by-zero); a witness that satisfies R1CS numerically but was computed with an off-by-one wire assignment (silent corruption, only caught by I6's exact-zero-remainder check, not by "close enough" floating comparison — this is exact finite-field arithmetic, there is no "close enough"); domain generator not actually a primitive root of the required order (misconfigured field parameters).

5.9 Failure Analysis

A domain-size or interpolation bug breaks I6 silently unless the exact-zero-remainder check is run — a partial remainder can be small in some naive metric but is either exactly zero or not, never "close"; detection is the negative-corpus test (5.4); blast radius is Phases 6–9 (KZG, Groth16 all consume QAP output); recovery: patch domain construction, re-run all downstream conformance.

5.10 Operational Notes

tracing span qap_transform records domain size + padding delta; no persistent state; this phase's output (QAP<Fr>) is passed by value into Phase 7's setup/prove, never serialized to disk independently (avoids a stale-QAP-vs-circuit drift class of bug).

18. Phase 6 — Polynomial Commitments: KZG10

6.1 Objectives

Implement the KZG10 polynomial commitment scheme (commit/open/verify) as an independently useful, pedagogically parallel primitive to Groth16 (§3) — not a runtime dependency of Groth16 in this blueprint, but the concrete illustration of "commit to a polynomial, open it at a point, verify in O(1)" that generalizes to PLONK (§34, deferred).

6.2 Detailed Implementation Steps

zkp-kzg::kzg_setup: given a discarded trapdoor τ (dev/test only per ADR-20; production ceremony reuse is Phase 8's job), compute powers_g1 = [g1^{τ^i}] and powers_g2 = [g2^{τ^i}] for i up to max_degree (anchors: KZG10, P3 — τ zeroized immediately after). kzg_commit: MSM of the polynomial's coefficients against powers_g1 (ADR-06). kzg_open: compute the quotient polynomial q(x) = (p(x) − p(z)) / (x − z) via synthetic division, commit to q — this is the opening proof. kzg_verify: pairing check e(commitment − [value]·g1, g2) == e(proof, g2^τ − [z]·g2) (schematic; anchors: I5, ADR-04).

6.3 Deliverable

zkp-kzg crate; a standalone example committing to a degree-16 polynomial, opening at a random point, and verifying — with an intentionally wrong opening value rejected.

6.4 Acceptance Criteria

Verify accepts 100% of 200 honestly generated (commitment, point, value, proof) tuples and rejects 100% of a 200-vector corpus with a tampered value or proof (I1/I2 analogues for KZG); commitment size is exactly 1 compressed G1 point (48 bytes, BLS12-381) regardless of polynomial degree (succinctness, matching M1's proof-size discipline).

6.5 Conformance Fixtures

kzg_commit_open_verify_valid.json | kzg_tampered_value.json (expect reject) | kzg_tampered_proof.json (expect reject) | kzg_max_degree_boundary.json (degree exactly at max_degree, expect success; degree+1, expect setup-time rejection).

6.6 Pitfalls

Committing to a polynomial of degree exceeding the SRS's max_degree silently truncates instead of erroring — must be an explicit bounds check at kzg_commit, not an out-of-bounds panic or silent wraparound; synthetic division for the quotient polynomial assumes the divisor has a known root — a non-exact division (meaning z was not actually a root of p(x)−p(z), a mathematical impossibility if computed correctly, but a real bug signal if it occurs) must be treated as a fatal implementation bug, never suppressed.

6.7 Performance Concerns

kzg_commit's MSM cost scales with polynomial degree (same Pippenger machinery as Groth16 proving, M8); kzg_open's synthetic division is O(degree), cheap relative to the commitment MSM; SRS size (powers_g1/powers_g2) scales linearly with max_degree — a capacity input to §32.

6.8 Edge Cases

Opening at a point equal to an existing root of the polynomial (value is legitimately zero, must not be special-cased as an error); degree-0 polynomial (constant, commitment is just g1^{p_0}); opening the same commitment at multiple points (batched opening — not implemented in this blueprint, note as a natural PLONK-style extension, PhaseDeferred("§34")).

6.9 Failure Analysis

A broken kzg_verify that accepts a tampered value is a soundness break in this primitive specifically (does not affect Groth16, which does not depend on zkp-kzg at runtime, §3); blast radius is contained to any future consumer of zkp-kzg directly; detection via the tamper-corpus test (6.5); recovery: patch the pairing-check equation, re-run corpus.

6.10 Operational Notes

tracing span kzg_op tagged commit/open/verify; SRS reuse across multiple polynomials of the same or smaller degree is supported (no per-polynomial setup) — a capacity-planning point distinct from Groth16's per-circuit Phase-2 setup (§20).

19. Phase 7 — Groth16 Pairing-Based SNARK (Prove / Verify)

7.1 Objectives

Implement the Groth16 construction: setup (deriving ProvingKey/VerifyingKey from a QAP and a Phase-2 SRS), prove (producing the 3-element Proof), and verify (the single pairing-based check) — the central deliverable of this blueprint.

7.2 Detailed Implementation Steps

setup: derive ProvingKey/VerifyingKey field/group elements from the QAP's polynomials evaluated at the (now-SRS-encoded) trapdoor point, per Groth16's precise element list (anchors: Groth16, I9, I14 — Phase-2-specific elements only, Phase-1 elements reused unchanged). prove: sample blinding scalars r, s (P6 constant-time, P12 explicit RNG injection); compute A = alpha_g1 + Σ(witness_i · a_query_i) + r·delta_g1 (schematic MSM sum, ADR-06); compute B similarly in G2; compute C from the H(x) polynomial (Phase 5 output) combined with the l_query/h_query SRS terms and the r,s cross-terms. verify: compute vk_x = Σ(public_input_i · gamma_abc_g1_i); check the single combined multi-pairing equation e(A,B) == e(alpha_g1,beta_g2)·e(vk_x,gamma_g2)·e(C,delta_g2) via multi_miller_loop + one final_exponentiation (I12, anchors: ADR-04, Costello).

7.3 Deliverable

zkp-groth16 crate; end-to-end setup → prove → verify on the §8 worked example, both curves (BLS12-381 primary, BN254 conformance), producing an accepting proof for the valid witness and a rejecting result for a tampered one.

7.4 Acceptance Criteria

Proof size exactly 192 bytes (BLS12-381, M1) / 128 bytes (BN254, M2); verify() latency ≤ 5 ms p50 / ≤ 12 ms p99 on the reference 4-core CPU (M3); prove() latency ≤ 1.5 s p50 at 2^16 constraints on 8-core (M4); differential match against ark-groth16's verify_proof on 500 shared test vectors, 100% agreement (P5, I10); a proof generated for witness x=3 and verified against public input out=36 (wrong) rejects in 100% of trials.

7.5 Conformance Fixtures

groth16_multiply_by_5_valid.json | groth16_wrong_public_input.json (expect reject) | groth16_tampered_proof_element.json (each of A/B/C independently flipped, expect reject) | groth16_arkworks_crossvector_500.json (shared differential corpus, §21).

7.6 Pitfalls

Forgetting the r,s blinding terms collapses zero-knowledge (I3) while leaving completeness/soundness intact — a proof that works but leaks witness-correlated information, the most dangerous kind of bug because tests that only check accept/reject never catch it (must have a dedicated ZK-distribution test, not just an accept/reject test); mixing up gamma/delta denominators between the SRS and the verification equation (a classic Groth16 implementation transcription error against the paper); batching multiple pairing checks incorrectly (see FC12, §23) — a bug only observable in the batch path, never in the single-proof path.

7.7 Performance Concerns

prove() is MSM-dominated (~70% of runtime, M8) with FFT/QAP evaluation (~20%, M9) and constant-order overhead the remainder — matches the Capacity Model derivation (§32); verify() is 3 pairings + 1 final exponentiation, a fixed cost independent of circuit size (P8, I9) — the central succinctness property (MM7).

7.8 Edge Cases

Zero public inputs (circuit with only witness variables — vk_x degenerates to a single term); maximum-size circuit at the 2^22 constraint ceiling (§4) requiring ADR-21 chunked MSM; a concurrently-running prove() and verify() on the same ProvingKey/VerifyingKey (both are immutable and Send + Sync, §11 — no additional synchronization needed).

7.9 Failure Analysis

A Groth16 verify() false-accept is the single highest-severity failure this blueprint defends against (arbitrary forged proofs); detection is exclusively differential testing (P5) plus the tampered-element corpus (7.5); containment: the conformance gate (M11) blocks any release with even one disagreement; recovery: full cryptographic review before any patch is trusted, per ADR-12's escalation policy (mirrors T9's 3-way-oracle-disagreement handling).

7.10 Operational Notes

tracing spans groth16_setup/groth16_prove/groth16_verify, each tagged with curve + constraint count for cross-curve, cross-size perf correlation (feeds §28's benchmarking methodology); VerifyingKey.circuit_hash (§11) is computed once at setup and never recomputed implicitly — any mismatch at load time is a hard failure (T11), not a warning.

20. Phase 8 — Trusted Setup: Powers-of-Tau & Circuit-Specific Ceremony

8.1 Objectives

Implement the two-phase MPC ceremony (ADR-09): universal Powers-of-Tau (Phase 1, circuit- agnostic, reusable) and circuit-specific Phase 2 (deriving the Groth16 ProvingKey/ VerifyingKey SRS elements) — the highest-stakes trust boundary in the whole system (P3, MM2).

8.2 Detailed Implementation Steps

phase1_new: dev/test-only single-dealer initialization (ADR-20 — never used in a real ceremony). phase1_contribute: each participant samples fresh randomness, updates every SRS element by their contribution's exponent, and produces a ContributionProof (pairing-based proof of correct multiplicative update, anchors: Bowe-Gabizon-Miers17, I7). phase1_verify_contribution: checks the ContributionProof via a pairing equation confirming the new SRS is the old SRS raised to a consistent (unknown) exponent — without ever learning that exponent. Apply a public random beacon (block hash or drand output) as the final "participant" (Bowe-Gabizon-Miers17's random-beacon technique) to close the ceremony against last-participant bias. phase2_from_circuit: combine the finalized Phase-1 output with the circuit's QAP (Phase 5) to derive circuit-specific SRS elements (I14 — strict Phase1Output/Phase2Output type separation, no implicit conversion).

8.3 Deliverable

zkp-setup crate; scripts/run_ceremony_sim.sh simulating a 5-participant Phase-1 ceremony plus Phase-2 derivation for the §8 worked-example circuit, producing a ProvingKey/VerifyingKey pair usable by Phase 7.

8.4 Acceptance Criteria

Ceremony transcript verification (phase1_verify_contribution chained across all 5 participants plus the beacon) passes in 100% of honest-ceremony trials; an injected invalid contribution (one participant's ContributionProof deliberately corrupted) is rejected in 100% of 100 trials (I7); per-participant contribution round ≤ 90 s p50 at 2^20 domain size (M7); a ceremony with only 1 honest-out-of-5 participants (4 colluding, 1 honest, simulated) still produces a secure SRS — verified by confirming the final SRS's implicit exponent is unrecoverable from the 4 colluding participants' combined randomness (P10, MM8).

8.5 Conformance Fixtures

ceremony_5participant_honest.json | ceremony_invalid_contribution_round3.json (expect rejection + re-request) | ceremony_beacon_application.json | phase2_multiply_by_5_derivation.json.

8.6 Pitfalls

Treating ceremony randomness like an application secret (rotatable, storable) instead of radioactive waste to be destroyed (P3, T7, FC7); a participant's process crashing mid-contribution leaving partially-updated SRS elements inconsistent (must be atomic: either the full contribution applies and is verified, or it is discarded wholesale, FC3); insufficient participant diversity (all participants on the same cloud provider/hardware, correlated compromise risk) — not a code bug but an operational one, documented in the ceremony runbook (§24).

8.7 Performance Concerns

Each contribution round is a full-SRS-size MSM-like update (O(domain size) group exponentiations) — dominant cost is per-element scalar multiplication across the entire Phase-1 vector, not amortizable across participants (each must independently re-randomize every element).

8.8 Edge Cases

Ceremony with exactly 1 participant (degenerate — technically valid per the 1-of-n honest model, but operationally discouraged, flagged by the ceremony runbook as a P10 violation risk); a contribution proof valid for the wrong domain size (mismatched Phase-1 parameters between participants — rejected at the type level before even reaching the pairing check); the random beacon value being predictable/manipulable if chosen by a non-independent source (must be a public, unpredictable-in-advance value, e.g. a future block hash).

8.9 Failure Analysis

Ceremony compromise (a fully-known trapdoor) enables undetectable arbitrary-proof forgery — the single worst failure mode in the entire system (T1); detection is only possible in advance (transcript audit, participant diversity) or via later cryptographic anomaly analysis, never at proof-verification time (a forged proof under a compromised SRS is indistinguishable from a real one, by Groth16's own soundness argument — this is the fundamental asymmetry of trusted setup); recovery: re-run the ceremony entirely, revoke and republish new PK/VK, treat all prior proofs under the old SRS as suspect.

8.10 Operational Notes

tracing span ceremony_round tagged participant index + phase; ceremony transcript is published (append-only log) for third-party audit per the runbook (§24); zeroize is called on every participant's local randomness immediately after producing their ContributionProof, verified by the memory-scan test harness (FC7).

21. Phase 9 — Conformance & Differential-Test Harness vs. Reference Implementations

9.1 Objectives

Build the zkp-conformance differential-test harness: in-process cross-implementation testing against ark-groth16 (primary oracle) and bellman (secondary oracle), plus fuzzing (ADR-13) and the timing side-channel gate (M13) — the correctness backstop for every prior phase (P5).

9.2 Detailed Implementation Steps

Add ark-bls12-381, ark-groth16, ark-r1cs-std, bellman, bls12_381 as dev-dependencies (anchors: ADR-12, arkworks/bellman reference implementations, §5). For each test vector: compile the same circuit description independently in this blueprint's zkp-circuit/zkp-r1cs and in ark-r1cs-std; run both setup/prove/verify pipelines on identical witnesses and identical (test-only, ADR-20) randomness seeds where the oracle API allows seeding; compare serialized proof bytes (I10) and verify-result booleans. 3-way agreement required (self/arkworks/bellman, T9) before a vector is marked passing. Wire cargo-fuzz targets: r1cs_parser, proof_deserialize, circuit_dsl (ADR-13). Wire the dudect timing harness against zkp-field::mul/invert and zkp-sigma's scalar-mult path (M13).

9.3 Deliverable

zkp-conformance crate + CI job running ≥ 500 differential vectors, a 1-hour fuzz job, and the dudect timing gate, producing a ConformanceReport (§11) consumed by the release gate (§27).

9.4 Acceptance Criteria

100% 3-way agreement across ≥ 500 vectors spanning both curves and constraint counts from 4 to 2^16 (M11, M14); 0 panics/crashes across a 1-hour cargo-fuzz run per target (M12); dudect |t| < 4.5 maintained (M13, re-confirmed at this integration scale, not just Phase 0/2's unit scale); conformance suite completes in ≤ 10 min on a 4-core CI runner (M11).

9.5 Conformance Fixtures

differential_corpus_500.json (the full cross-implementation vector set) | fuzz_corpus_seed/ (seed inputs for the three fuzz targets) | dudect_timing_samples.json | oracle_version_pin.lock (exact arkworks/bellman commit hashes, T9/T8).

9.6 Pitfalls

An oracle-version bump silently changing expected outputs (T9/FC8) — mitigated by pinning exact oracle versions and re-deriving vectors deliberately, never automatically; a "passing" 2-way agreement (self matches arkworks) masking a bug shared by both when bellman would have caught it — always require the full 3-way check, not an early-exit 2-way one; fuzz targets that only exercise the "happy path" input shape because the Arbitrary impl is too constrained (structure- aware fuzzing must still reach malformed-but-structurally-plausible inputs).

9.7 Performance Concerns

Running three implementations per vector (self + 2 oracles) roughly triples wall-clock cost versus self-only testing — bounded by parallelizing across vectors (Rayon, ADR-15) to hit the ≤10 min target (M11); fuzz corpus minimization (cargo fuzz cmin) keeps the 1-hour budget effective rather than re-exploring already-covered input space.

9.8 Edge Cases

A vector where arkworks and bellman disagree with each other (not just with this implementation) — must escalate per T9, never auto-resolve by majority vote (2-out-of-3 is not a correctness argument in cryptography); a fuzz-found crash that only reproduces under a specific CPU feature flag (e.g. AVX2 MSM path) — must be reproduced and fixed on the exact flagged configuration, not dismissed as environment-specific.

9.9 Failure Analysis

A conformance-suite false-pass (bug masked by shared-implementation blind spot, P5's known limitation) is the residual risk this entire phase cannot fully eliminate — mitigated but not solved by 3-way agreement; detection beyond this harness requires external audit/formal methods (out of scope, ADR-12's stated boundary); a conformance-suite false-fail (oracle drift, FC8) is lower severity but blocks releases until triaged — recovery is re-pinning and re-deriving vectors.

9.10 Operational Notes

tracing span conformance_vector tagged vector name + oracle agreement result; metrics counters (conformance_pass_total, conformance_disagreement_total) exported only in the CI bench-runner context (ADR-17); the ConformanceReport artifact is archived per release (§27) for audit trail.

25. Compatibility & Versioning

Wire compatibility: Proof/VerifyingKey/ProvingKey serialization (ADR-11) is versioned via an explicit format-version byte prefix; a version bump is only ever additive (new optional trailing fields) or a new major version with an explicit migration note — never a silent reinterpretation of existing bytes. Storage compatibility: Phase1Output/Phase2Output files carry the same version prefix; ceremony artifacts from an older format version are rejected, not silently upgraded (I14 — no implicit conversion, extended to versioning). Schema evolution: a circuit's circuit_hash changes whenever its R1CS structure changes — there is no "compatible" circuit evolution; a changed circuit is a new circuit requiring a new Phase-2 setup. API stability: zkp-groth16's setup/prove/verify signatures are SemVer-stable from v1.0; internal crates (zkp-field, zkp-curve) may add curve support without a major bump but never remove a curve variant without one. Deprecation policy: a deprecated curve/API is marked #[deprecated] for ≥ 1 minor version before removal, with the removal itself being a major bump. SemVer policy: patch = bugfix with identical outputs on all conformance vectors; minor = additive (e.g. new curve, new circuit-DSL feature); major = any change altering serialized-byte compatibility or removing a public API. Rolling-upgrade guarantees: since this is a library (no service), "rolling upgrade" means: a verifier built against library version N+1 must still accept proofs generated by version N for the same circuit_hash and format-version — enforced by a dedicated cross-version conformance fixture set (conformance/fixtures/cross_version/).

29. Scalability Analysis

Stays constant: proof size (O(1), I9); verify latency (O(1) pairings, P8); VerifyingKey size (O(public-input count), not circuit size). Grows: prove() time — O(n log n) for the FFT component (M9) plus O(n / log n) group operations for the MSM component (M8), where n is constraint count — MSM dominates in practice at the constraint counts in §4 (derived, §32); proving-key size — O(n) (derived, §32); ceremony round latency — O(n) per participant (M7); peak RSS — O(n) (M10). Named bottlenecks in order: (1) MSM throughput (M8) — the single largest prove() cost component; (2) FFT throughput (M9) — second largest; (3) peak RSS (M10) — becomes binding before CPU time does on memory-constrained hardware at circuit sizes near 2^22 (§4 ceiling). Horizontal scaling: prove() calls are embarrassingly parallel across independent proofs (process replication, no shared state, §4) — does not help a single large proof's latency, only aggregate proving throughput across many proofs. Vertical scaling: more cores directly reduces MSM/FFT wall-clock (Rayon work-stealing, ADR-15) up to the point where per-core memory bandwidth saturates (empirically near 16–32 cores for the constraint counts in §4 — beyond that, GPU acceleration is the next lever, PhaseDeferred("§29")). Sharding/partitioning: not applicable to a single proof (the R1CS/QAP structures are not partitionable without recursive composition, PhaseDeferred("§29")); ceremony participation is naturally "sharded" across participants by design (§20). Coordination overhead: the ceremony is the only phase with cross-participant coordination cost (M7) — everything else (prove, verify) is single-process. Practical ceiling: 2^22 constraints on a single 8-core/64GB-RAM host before RSS (M10) or prove() latency (M5, extrapolated) becomes operationally unacceptable for interactive use. Levers beyond the ceiling: GPU-accelerated MSM (PhaseDeferred("§29"), cf. gnark, §31); recursive proof composition to split one large circuit into many small proven sub-circuits aggregated by a final proof (PhaseDeferred("§29"), cf. Halo2, §34); migrating to a universal-SRS scheme (PLONK, PhaseDeferred("§34")) to amortize setup cost across many circuit changes.

30. Mental Models & First Principles

  • MM1 — A SNARK is an arithmetic-circuit lie detector compressed to 3 group elements. Succinctness comes from checking one random algebraic identity (via pairing) equivalent, with overwhelming probability, to checking every gate. Predicts: any bug breaking QAP divisibility (I6) is a soundness break, not a performance bug. Bug class without it: "optimizing" the pairing equation without understanding why the trapdoor point makes cheating exponentially unlikely. Resolving: §8, §17, §19.
  • MM2 — The CRS's secret trapdoor is a loaded gun the ceremony must destroy, not a key the system manages. Unlike a DB encryption key, τ/α/β/γ/δ must never be reconstructed by anyone, ever, post-setup. Predicts: any code path that logs, snapshots, or memoizes ceremony randomness is a critical vulnerability. Bug class without it: treating ceremony secrets like ordinary application secrets (rotate/store) instead of zeroizing. Resolving: §6 P3, §20, §22 T7.
  • MM3 — Fiat–Shamir turns a verifier's coin-flip into a hash of everything said so far. Non-interactivity is not free — soundness under the random-oracle idealization can break in the real world if the transcript omits any prior message. Predicts: any missing domain-separation label or omitted commitment is a forgery vector. Bug class without it: hashing "the important part" of the transcript instead of the whole statement. Resolving: §15, §22 T3.
  • MM4 — R1CS is a linear-algebra shadow of a circuit; QAP is the same shadow cast onto polynomials. Every satisfiability question becomes "does this polynomial vanish on this domain," turning boolean circuit-satisfaction into checkable algebra. Predicts: any wrong evaluation-domain size breaks completeness/soundness simultaneously. Bug class without it: treating R1CS and QAP as independent representations instead of one bijective transform. Resolving: §8, §16, §17.
  • MM5 — A pairing is a one-way multiplication table between two groups that still lets you "multiply in the exponent." e(g1^a, g2^b) = e(g1,g2)^{ab} is the entire algebraic leverage Groth16 exploits. Predicts: batch-verification bugs cluster around incorrect random linear combinations of pairing equations. Bug class without it: treating pairings as a black-box "verify" call instead of understanding the algebraic statement they check. Resolving: §19, §23 FC12.
  • MM6 — Zero-knowledge means a simulator can fake a transcript without the secret — if you can't describe the simulator, you don't have ZK. ZK is a property of an entire transcript distribution, not "not printing the secret." Predicts: leaking even one extra bit of the witness through response randomness breaks ZK even if verification still passes. Bug class without it: reusing randomness across proofs (nonce-reuse catastrophe). Resolving: §13, §14, §22 T2.
  • MM7 — Succinctness is a promise about verifier work, not prover work. Groth16's O(1) proof and verify time coexist with prover work linear (or worse) in circuit size. Predicts: engineers who assume "SNARK ⇒ fast to generate" mis-scope prover hardware. Bug class without it: sizing prover infrastructure as if it shared succinctness with the verifier. Resolving: §6 P8, §28, §32.
  • MM8 — Every trusted-setup artifact is only as trustworthy as its most-honest single participant. An n-party Powers-of-Tau ceremony is secure if at least one participant discarded their randomness (1-of-n honest-majority-free trust model). Predicts: ceremony design should maximize participant diversity/count, not minimize ceremony latency. Bug class without it: treating "we ran a ceremony" as sufficient without verifying participant independence. Resolving: §9 ADR-09, §20.

32. Back-of-Envelope Capacity Model

  1. Proof size (BLS12-381) = 2×|G1_compressed| + 1×|G2_compressed| = 2×48B + 96B = 192 bytes (M1) — chained directly from §4's field/curve sizes.
  2. Proof size (BN254) = 2×32B + 64B = 128 bytes (M2).
  3. MSM operation count, prove() ≈ 3–4 × m group scalar-mults, where m = constraint count (one term per nonzero A/B/C entry, roughly 3–4 group ops per constraint in the Groth16 A/B/C computation). At m = 2^20 (≈1,048,576): ≈ 3.1M–4.2M scalar-mults.
  4. prove() time at 2^20 constraints = MSM_ops / (cores × M8_throughput) ≈ 3.5×10^6 / (8 × 40,000) ≈ 10.9 s — under the M5 target (≤25s) with margin for FFT/serialization overhead not modeled here.
  5. FFT cost, domain 2^20 ≈ n log₂(n) field multiplications = 2^20 × 20 ≈ 21M field mults per forward/inverse pass — chained into M9's ≤400ms target at typical single-core field-mult throughput (~50–100M ops/sec for Montgomery multiplication).
  6. Proving-key size at 2^16 constraints ≈ (a_query + b_g1_query + h_query + l_query) × |G1| + b_g2_query × |G2| ≈ 4 × 2^16 × 48B + 2^16 × 96B ≈ 18.9 MB (schematic upper bound; §4's stated 9.4 MB reflects sparsity-adjusted query vector sizes in practice).
  7. Peak RSS at 2^20 constraints ≈ witness (32B × n) + 3 QAP polynomials (32B × n each) + MSM precompute table (window-factor × 32B × n) ≈ 32×2^20 + 3×32×2^20 + 16×32×2^20 ≈ 671 MB × 20/32-factor adjustment ≈ ~4–6 GB, matching M10's stated ceiling.
  8. Ceremony per-participant artifact size, 2^20 domain ≈ 2n×|G1| + n×|G2| ≈ 2×2^20×48B + 2^20×96B ≈ 201 MB per contribution — the dominant I/O cost behind M7's round-latency target.
  9. Verify cost (fixed, independent of n) = 3 Miller-loop pairings + 1 final exponentiation ≈ a small constant number of milliseconds on commodity hardware (typical software BLS12-381 pairing ≈ 1–2ms), chaining directly to M3's ≤5ms p50 target.
  10. Throughput ceiling, single 8-core prover ≈ (8 cores × 40,000 ops/sec) / (3.5×10^6 ops/proof) ≈ 0.09 proofs/sec at 2^20 constraints — i.e., ~1 proof every ~11s, matching derivation #4; horizontal scaling to k processes multiplies this linearly (§29).

34. Alternative Architectures (Roads Not Taken)

STARK (FRI-based, transparent).

Circuit ── AIR ── Reed-Solomon ── FRI (low-degree test) ── Merkle-committed proof
                                                            (no pairing, no trusted setup)

Regime where it wins: any deployment where a trusted setup is politically or legally unacceptable, or post-quantum security is required — hash-based commitments have no known efficient quantum attack, unlike pairing-group discrete log. Real system: StarkWare's Cairo/STARK prover (production, StarkNet). Rejected here because: proof size (tens to hundreds of KB) and verify cost (milliseconds to tens of ms, larger than Groth16's fixed 3-pairing cost) trade away this blueprint's specific teaching goal — the pairing-based succinctness story — for transparency; both are valid, but this blueprint is explicitly the pairing-based teaching track (§2, anchors: Ben-Sasson18).

PLONK (universal SRS, permutation argument).

Circuit ── gates+wiring ── PLONK arithmetization ── KZG commitment ── universal SRS (any circuit)

Regime where it wins: a deployment serving many different circuits that would otherwise each need their own Groth16 ceremony — one universal SRS amortizes setup cost across unlimited future circuits. Real system: Aztec (original PLONK deployment), zkSync's early PLONK-based prover. Rejected here because: the universal-SRS/permutation-argument machinery is a distinct, larger teaching surface PhaseDeferred("§34") — this blueprint's Groth16 focus is deliberately the simpler, historically prior construction (anchors: Gabizon19).

Bulletproofs (no trusted setup, logarithmic size, no pairing).

Commitment (Pedersen) ── inner-product argument ── O(log n) proof, no pairing, no trusted setup

Regime where it wins: range proofs and small-statement proofs in a context where any trusted setup (even a ceremony) is unacceptable and proof size can be logarithmic rather than constant — confidential-transaction amount ranges are the canonical case. Real system: Monero (RingCT/ Bulletproofs+), Grin. Rejected here because: verify cost is O(n) (linear in statement size, not O(1) like Groth16) — the wrong tradeoff for this blueprint's succinctness-focused teaching goal (MM7); no pairing means no Miller-loop/final-exponentiation material to teach (§12, §19).

Halo2 / IPA-based recursive proving (no trusted setup, recursion-friendly).

Circuit ── Plonkish ── Inner-Product-Argument commitment ── recursive proof composition
                                                              (accumulate, don't re-verify)

Regime where it wins: proof aggregation/recursion at scale — proving "this batch of 1,000 proofs is all valid" in one final proof, without a trusted setup. Real system: Zcash Orchard (Halo2, production since NU5). Rejected here because: recursive composition and the accumulation scheme are PhaseDeferred("§29"/"§34") — a distinct, substantial teaching module this blueprint deliberately excludes to keep the core Groth16 pipeline (§12–§21) tractable as a first system.

36. Glossary

  • Zero-knowledge proof — a protocol letting a Prover convince a Verifier a statement is true without revealing why (GMR85).
  • Completeness — an honest Prover with a valid witness always convinces an honest Verifier (I1).
  • Soundness — no Prover without a valid witness convinces the Verifier except with negligible probability (I2).
  • Knowledge soundness — a stronger soundness variant: an extractor can recover a witness from any convincing Prover.
  • Zero-knowledge (property) — the Verifier's view is simulatable without the witness (I3, MM6).
  • Simulator — an algorithm producing transcripts indistinguishable from real ones, without the witness (§13).
  • Extractor — an algorithm that recovers a witness from a convincing (possibly malicious) Prover, used in soundness proofs.
  • Trapdoor — a secret value (e.g., τ) whose knowledge would let its holder forge proofs; must be destroyed (P3).
  • CRS (Common Reference String) — public setup parameters both Prover and Verifier use.
  • SRS (Structured Reference String) — a CRS with algebraic structure (e.g., powers of τ in the exponent), as used by KZG/Groth16.
  • Toxic waste — the trapdoor randomness used to generate an SRS; catastrophic if not destroyed (T1, T7).
  • R1CS (Rank-1 Constraint System) — a set of constraints (A·w)⊙(B·w)=(C·w) over a witness vector (§8, §16).
  • QAP (Quadratic Arithmetic Program) — the polynomial-interpolation encoding of an R1CS instance (§8, §17, GGPR13).
  • Arithmetic circuit — a computation expressed as addition/multiplication gates over a field (§8, §16).
  • Witness — the private values (plus public inputs) satisfying a circuit's constraints.
  • Wire — a value-carrying edge in a circuit, identified by a WireId (§11).
  • Gate — a single circuit operation (Add, Mul, Const, etc., §11).
  • Lagrange interpolation — reconstructing a polynomial from point-value pairs; used to build QAP polynomials (§17).
  • FFT (Fast Fourier Transform) — an O(n log n) algorithm for polynomial evaluation/interpolation over a suitable domain (§17, ADR-05).
  • NTT (Number-Theoretic Transform) — an FFT variant over a finite field using a root of unity, used here interchangeably with "FFT" (§17).
  • MSM (Multi-Scalar Multiplication) — computing Σ scalar_i · point_i efficiently (Pippenger's algorithm, ADR-06); the dominant prove() cost.
  • Pairing (bilinear map) — a map e: G1 × G2 → GT satisfying e(g1^a,g2^b)=e(g1,g2)^{ab} (§12, §19, MM5).
  • Type-III pairing — a pairing where G1 ≠ G2 with no efficiently computable isomorphism between them (ADR-04).
  • BN254 — a Barreto–Naehrig pairing-friendly curve, ≈100-bit security, Ethereum-precompile compatible (§4, ADR-03).
  • BLS12-381 — a Barreto–Lynn–Scott pairing-friendly curve, ≈117-bit security, this blueprint's primary curve (§4, ADR-03).
  • Scalar field (Fr) — the field of exponents/witness values for a given curve (§11).
  • Base field (Fq) — the field curve coordinates are defined over (§11).
  • G1 / G2 / GT — the two source groups and the target group of a pairing (§11, §19).
  • Miller loop — the core iterative algorithm computing (an intermediate result toward) a pairing (§12, §19, Costello).
  • Final exponentiation — the exponentiation step completing a pairing computation after the Miller loop (§12, §19).
  • KZG commitment — a constant-size polynomial commitment scheme with O(1) opening proofs (§18, KZG10).
  • Opening proof — proof that a committed polynomial evaluates to a claimed value at a point (§18).
  • Trusted setup — a ceremony generating an SRS whose trapdoor must be destroyed (§20, P3, P10).
  • Powers of Tau — the universal, circuit-agnostic Phase-1 trusted-setup ceremony (§20, Bowe-Gabizon-Miers17).
  • MPC ceremony — a multi-party computation where no single participant ever learns the full secret (§20).
  • Fiat–Shamir heuristic — replacing an interactive Verifier's challenge with a hash of the transcript (§15, Fiat-Shamir86).
  • Random oracle model — an idealization treating a hash function as a truly random function, used to argue Fiat–Shamir's security (§15, Bellare-Rogaway93, MM3).
  • Sigma protocol — a three-move (commit, challenge, response) interactive proof with special soundness and HVZK (§14).
  • Schnorr protocol — the canonical discrete-log Sigma protocol (§14, Schnorr91).
  • Transcript — the ordered record of all protocol messages, hashed to derive Fiat–Shamir challenges (§11, §15).
  • Challenge — the (pseudo-)random value a Verifier sends (or a Fiat–Shamir hash produces) to a Prover.
  • Commitment scheme — a scheme letting a party commit to a value now and reveal/prove it later, binding and hiding (§8).
  • Binding — a commitment property: the committer cannot later open the commitment to a different value.
  • Hiding — a commitment property: the commitment reveals nothing about the committed value.
  • Special soundness — a Sigma-protocol property: two accepting transcripts sharing a commitment but differing in challenge yield an extractable witness (§14).
  • Honest-verifier zero-knowledge (HVZK) — zero-knowledge that holds against a Verifier who follows the protocol honestly (weaker than full ZK, sufficient after Fiat–Shamir, §14–§15).
  • NIZK (Non-Interactive Zero-Knowledge) — a zero-knowledge proof requiring no interaction (achieved here via Fiat–Shamir or a CRS, §15, §19).
  • Succinctness — proof size and verification time that are O(1) or O(log n), independent of witness/circuit size (I9, MM7).
  • Subgroup check — verifying a deserialized point lies in the correct prime-order subgroup (I5, P11).
  • Cofactor clearing — multiplying a curve point by the cofactor to force it into the prime-order subgroup (§12, I5).
  • Embedding degree — the smallest k such that the pairing's target group GT lives in Fq^k; determines pairing efficiency (§4, Costello).
  • Under-constrained circuit — a circuit whose R1CS admits satisfying witnesses that violate the intended application semantics (§16, T6, FC10).
