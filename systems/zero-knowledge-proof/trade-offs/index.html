Decisions (§9) · 24 ADRs

ADR-01

Implementation language

Chosen

Rust, stable, 2021 edition

Rejected

C++ (memory-unsafe field arithmetic); Go (GC pauses); Python (2–3 orders of magnitude too slow)

When the rejected choice is right

C++ wins when embedding into an existing libsnark-based audit toolchain already standardized on that stack

Why: No GC pauses in MSM/FFT hot path; ownership model prevents the exact memory-safety bugs libsnark's C++ exhibits

ADR-02

Field representation

Chosen

Fixed-width 4/6-limb arrays, Montgomery multiplication

Rejected

GMP arbitrary precision; num-bigint

When the rejected choice is right

GMP wins for a research prototype exploring mixed/variable field sizes across many curves

Why: Fixed-width avoids heap allocation in the hot loop; Montgomery form avoids repeated modular reduction

ADR-03

Primary curve

Chosen

BLS12-381 (≈117-bit security)

Rejected

BN254 as primary; secp256k1

When the rejected choice is right

BN254 wins as primary when the deployment target is an existing EVM chain whose precompiles (EIP-196/197) fix the curve

Why: BLS12-381 is the modern, higher-security choice (Zcash Sapling, Eth2, Filecoin); BN254 kept as secondary for Ethereum-precompile conformance

ADR-04

Pairing type

Chosen

Type-III asymmetric (G1 ≠ G2)

Rejected

Type-I symmetric (supersingular curves)

When the rejected choice is right

Type-I wins in a symmetric-key-flavored academic pairing course valuing G1=G2 elegance over performance

Why: Type-III enables the smaller/faster BN/BLS instantiations Groth16 is standardized on

ADR-05

FFT algorithm

Chosen

Iterative Cooley–Tukey radix-2 NTT, precomputed twiddle tables

Rejected

Naive O(n²) Lagrange interpolation; mixed-radix FFT

When the rejected choice is right

Naive interpolation wins for constraint counts < 64 where FFT setup overhead exceeds its savings

Why: O(n log n) dominates QAP interpolation cost at the constraint counts in §4

ADR-06

MSM algorithm

Chosen

Windowed Pippenger bucket method

Rejected

Naive double-and-add; Straus's algorithm

When the rejected choice is right

Naive double-and-add wins for MSM instances < 256 points where bucket setup exceeds the saving

Why: O(n / log n) group ops — the dominant cost of Groth16 proving (§32)

ADR-07

R1CS matrix representation

Chosen

Sparse Vec<(WireId, F)> per linear combination

Rejected

Dense matrix

When the rejected choice is right

Dense wins for tiny (< 32-constraint) unit-test circuits where sparsity bookkeeping costs more than it saves

Why: Real circuits are sparse (few nonzero terms per gate)

ADR-08

Circuit IR

Chosen

SSA-style gate list (Add/Mul/Const/PublicInput/Witness)

Rejected

Stack-based bytecode; direct-to-R1CS macro DSL

When the rejected choice is right

A direct-to-R1CS DSL (circom's approach) wins when minimizing compile-time indirection for very large templated circuits

Why: Analyzable, supports an optimization pass, mirrors arkworks' ConstraintSystem pattern

ADR-09

Trusted-setup architecture

Chosen

Two-phase: universal Powers-of-Tau (Phase 1) + circuit-specific (Phase 2)

Rejected

Single-phase circuit-specific only; fully trusted single dealer

When the rejected choice is right

Single-dealer setup wins for an internal, already-trusted, air-gapped audit tool where ceremony coordination isn't justified

Why: Phase-1 SRS is reusable across circuits; MPC reduces single-point-of-trust

ADR-10

Transcript hash

Chosen

BLAKE2b-based Merlin-style transcript, domain-separated labels

Rejected

Raw SHA-256 concatenation; Poseidon (circuit-friendly hash)

When the rejected choice is right

Poseidon wins when the hash itself must be provable inside another circuit (recursive composition, deferred §35)

Why: Strict-ordering transcript prevents injection/malleability (P7)

ADR-11

Serialization format

Chosen

Custom compact binary matching arkworks' CanonicalSerialize byte layout

Rejected

bincode generic; Protobuf; JSON

When the rejected choice is right

JSON wins for a debugging/inspection tool where human-readability outweighs 3–8× size overhead

Why: Enables byte-for-byte differential testing (I10)

ADR-12

Testing strategy

Chosen

In-process differential testing vs. arkworks (primary), bellman (secondary)

Rejected

Unit tests only; formal/symbolic verification only

When the rejected choice is right

Formal verification (e.g. EasyCrypt) wins in a safety-critical deployment (legally binding financial settlement) justifying its cost

Why: SNARK bugs break soundness silently; cross-implementation agreement is the strongest practical guarantee short of a formal proof

ADR-13

Fuzzing

Chosen

cargo-fuzz (libFuzzer), structure-aware Arbitrary on R1CS/proof types

Rejected

AFL; random-byte fuzzing

When the rejected choice is right

AFL wins when the primary attack surface is a network-facing serialized-proof parser (not this library's default posture)

Why: Structure-aware fuzzing reaches deep circuit-builder state random bytes cannot

ADR-14

CI/CD

Chosen

GitHub Actions matrix (BN254 + BLS12-381 feature flags)

Rejected

Jenkins; CircleCI

When the rejected choice is right

Jenkins wins in an air-gapped research lab without external network access to hosted runners

Why: Free hosted runners, native Rust caching action

ADR-15

Concurrency model

Chosen

Data-parallel Rayon work-stealing for MSM/FFT

Rejected

Tokio async runtime; single-threaded

When the rejected choice is right

Tokio wins if later wrapped in a proving-as-a-service HTTP API where request concurrency dominates over per-proof internal parallelism

Why: Proving is CPU-bound batch computation, not I/O-bound; Rayon maps directly onto MSM/FFT parallelism

Why: Structured spans let the conformance harness correlate timing per phase across curves

Packaging

Chosen

Cargo workspace, per-crate boundaries

Rejected

Single monolithic crate

When the rejected choice is right

A monolith wins for a small teaching-only single-binary distribution where workspace overhead isn't worth it

Why: Layering (field/curve/proof-system) must be independently testable and reusable

ADR-19

Reproducible builds

Chosen

Cargo.lock committed + cargo-deny audit + pinned rust-toolchain.toml

Rejected

Unpinned dependencies

When the rejected choice is right

Unpinned deps win in a rapid-research fork wanting upstream field-arithmetic optimizations immediately

Why: Cryptographic correctness must not silently shift with a transitive dependency bump

ADR-20

Randomness source

Chosen

OS CSPRNG (getrandom) + zeroize for ceremony randomness

Rejected

User-supplied/deterministic seed for production setup

When the rejected choice is right

A deterministic seeded RNG wins strictly within the conformance/test-fixture ceremony (Phase 8 test fixtures only), where a reproducible test SRS is required and no production trust is implied

Why: Deterministic setup randomness would make the SRS trapdoor reconstructible

ADR-21

Batch sizing / backpressure

Chosen

Chunked MSM/FFT bounded by max_batch_constraints (default 2^20)

Rejected

Unbounded single-pass processing

When the rejected choice is right

Unbounded single-pass wins on a dedicated high-memory ceremony server (≥ 256 GB RAM) proving up to 2^26 constraints, where chunking is pure coordination overhead

Why: Witness/QAP vectors for > 2^22 constraints exceed default container RAM budgets (§4)

ADR-22

Licensing

Chosen

MIT OR Apache-2.0 dual license

Rejected

GPL; AGPL

When the rejected choice is right

AGPL wins if the strategic goal is preventing proprietary SaaS forks of a novel proving scheme

Why: Matches arkworks/bellman convention, maximizing adoption as a reference/teaching library

ADR-23

Dependency policy on primitives

Chosen

Hand-rolled field/curve/pairing arithmetic (Phase 0–3), cross-checked (never replaced) against arkworks

Rejected

Depend on arkworks directly for all arithmetic from day one

When the rejected choice is right

Depending on arkworks directly wins for any non-pedagogical production system — reimplementing audited pairing arithmetic in production is a security anti-pattern

Why: The project's explicit purpose (§2) is teaching the arithmetic from scratch

ADR-24

Error handling

Chosen

Typed enum ZkpError via thiserror, no panics in library paths

Rejected

anyhow; Box<dyn Error>; panics

When the rejected choice is right

anyhow wins in the CLI-only bench binary (not the library) where every error terminates the process identically

Why: Callers (conformance harness, CLI) must pattern-match specific failure classes

34. Alternative Architectures (Roads Not Taken)

STARK (FRI-based, transparent).

Circuit ── AIR ── Reed-Solomon ── FRI (low-degree test) ── Merkle-committed proof
                                                            (no pairing, no trusted setup)

Regime where it wins: any deployment where a trusted setup is politically or legally unacceptable, or post-quantum security is required — hash-based commitments have no known efficient quantum attack, unlike pairing-group discrete log. Real system: StarkWare's Cairo/STARK prover (production, StarkNet). Rejected here because: proof size (tens to hundreds of KB) and verify cost (milliseconds to tens of ms, larger than Groth16's fixed 3-pairing cost) trade away this blueprint's specific teaching goal — the pairing-based succinctness story — for transparency; both are valid, but this blueprint is explicitly the pairing-based teaching track (§2, anchors: Ben-Sasson18).

PLONK (universal SRS, permutation argument).

Circuit ── gates+wiring ── PLONK arithmetization ── KZG commitment ── universal SRS (any circuit)

Regime where it wins: a deployment serving many different circuits that would otherwise each need their own Groth16 ceremony — one universal SRS amortizes setup cost across unlimited future circuits. Real system: Aztec (original PLONK deployment), zkSync's early PLONK-based prover. Rejected here because: the universal-SRS/permutation-argument machinery is a distinct, larger teaching surface PhaseDeferred("§34") — this blueprint's Groth16 focus is deliberately the simpler, historically prior construction (anchors: Gabizon19).

Bulletproofs (no trusted setup, logarithmic size, no pairing).

Commitment (Pedersen) ── inner-product argument ── O(log n) proof, no pairing, no trusted setup

Regime where it wins: range proofs and small-statement proofs in a context where any trusted setup (even a ceremony) is unacceptable and proof size can be logarithmic rather than constant — confidential-transaction amount ranges are the canonical case. Real system: Monero (RingCT/ Bulletproofs+), Grin. Rejected here because: verify cost is O(n) (linear in statement size, not O(1) like Groth16) — the wrong tradeoff for this blueprint's succinctness-focused teaching goal (MM7); no pairing means no Miller-loop/final-exponentiation material to teach (§12, §19).

Halo2 / IPA-based recursive proving (no trusted setup, recursion-friendly).

Circuit ── Plonkish ── Inner-Product-Argument commitment ── recursive proof composition
                                                              (accumulate, don't re-verify)

Regime where it wins: proof aggregation/recursion at scale — proving "this batch of 1,000 proofs is all valid" in one final proof, without a trusted setup. Real system: Zcash Orchard (Halo2, production since NU5). Rejected here because: recursive composition and the accumulation scheme are PhaseDeferred("§29"/"§34") — a distinct, substantial teaching module this blueprint deliberately excludes to keep the core Groth16 pipeline (§12–§21) tractable as a first system.
