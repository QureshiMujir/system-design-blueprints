⬜ Phase 0 — Repository Skeleton & Finite-Field / Elliptic-Curve Arithmetic Kernel §12

Objectives

Stand up the Cargo workspace (15 crate stubs, §10); implement Fr/Fq Montgomery-form field arithmetic and BLS12-381 G1/G2 group law (short Weierstrass, a=0); BN254 kept as a parallel, feature-flagged path for later conformance (§21). No pairing, no circuits yet — this phase is the arithmetic floor every other phase depends on.

Deliverable

cargo test -p zkp-field -p zkp-curve green on both curves; zkp field-check CLI subcommand prints modulus, confirms a round-trip from_repr(to_repr(x)) == x, and runs the invalid-point corpus.

Acceptance

100% pass on ≥200 known-answer field-arithmetic vectors cross-checked against ark-bls12-381 (dev-dependency, ADR-12); subgroup check rejects 100% of a 50-vector invalid-point corpus (I5); dudect |t| < 4.5 over 10^5 samples on mul/invert (M13).

Fixtures

field_kat_bls12_381.json (known-answer field ops) | field_kat_bn254.json | invalid_points_corpus.bin (50 malformed/off-curve/wrong-subgroup points, expect reject) | montgomery_roundtrip.json (from_repr/to_repr identity, expect equal).

Pitfalls

Missing the final conditional subtraction in Montgomery reduction — silently wrong only above a threshold value, caught by I4; naive full-order-scalar subgroup check is correct but too slow for M8 — use the endomorphism trick; sign ambiguity on point decompression (two y per x) — pick canonical lexicographically-smallest per ADR-11; BN254/BLS12-381 code sharing a hardcoded limb count (4 vs. 6) silently truncates the larger field.

⬜ Phase 1 — Interactive Proofs & the GMR Definition §13

Objectives

Implement the formal GMR framework (completeness, soundness, zero-knowledge) as executable scaffolding — not yet a SNARK — using the graph 3-coloring zero-knowledge protocol (GMW) as the concrete toy example, plus a deterministic simulator harness that exercises I1–I3 directly.

Deliverable

zkp-conformance "toy-ip" harness: runs N rounds of the real protocol and N rounds of the simulator, and a statistical distinguisher (chi-squared test on transcript-distribution features) that must fail to distinguish them.

Acceptance

Soundness-error measured empirically over 10,000 cheating-prover trials (invalid coloring) matches the theoretical (1 - 1/|E|)^k bound within 1% for k=40 rounds; distinguisher p-value > 0.05 (fails to reject indistinguishability) across ≥ 5,000 simulated vs. real transcripts (I3).

Fixtures

3coloring_valid.json (graph + valid coloring, expect accept) | 3coloring_invalid.json (graph + invalid coloring, expect reject after k rounds w.h.p.) | simulator_transcripts.json (5,000 simulator outputs for the distinguisher test).

Pitfalls

Treating "the verifier never sees the coloring" as sufficient for zero-knowledge — real ZK requires a simulator, not merely secrecy of the witness (MM6); reusing the same commitment randomness across rounds breaks hiding (T2-adjacent); an under-sized k (few rounds) silently weakens soundness below the acceptance threshold — always derive k from the target error bound, never hardcode a round count.

⬜ Phase 2 — Sigma Protocols: Schnorr Identification & Composition §14

Objectives

Implement the SigmaProtocol trait (§11) and the Schnorr identification protocol over zkp-curve group elements; implement AND-composition (parallel independent statements) and OR-composition (proof of knowledge of one of two witnesses, Cramer–Damgård–Schoenmakers style).

Deliverable

zkp-sigma crate compiling and passing unit tests for single, AND, and OR Schnorr proofs against a manually scripted interactive verifier in examples/schnorr_identification.rs.

Acceptance

Special-soundness extractor test: given two accepting transcripts (R, c1, s1) and (R, c2, s2) for the same commitment R with c1 ≠ c2, the extractor recovers w matching the original witness in 100% of 1,000 randomized trials (I2-analogue for Sigma protocols); OR-proof reveals zero information about which branch is real across a 10,000-trial statistical test (I3).

Fixtures

schnorr_valid.json | schnorr_forged_response.json (tampered s, expect reject) | schnorr_and_composition.json | schnorr_or_composition.json (branch-hiding test vectors).

Pitfalls

Reusing the ephemeral scalar k across two proofs of the same witness leaks w algebraically (the exact real-world nonce-reuse catastrophe class, T2, MM6); forgetting to bind the statement Y into the challenge derivation (this becomes critical once Fiat–Shamir is added in Phase 3, P7); OR-composition challenge-splitting arithmetic error silently breaks either soundness or zero-knowledge depending on which side is wrong — test both properties independently.

⬜ Phase 3 — Fiat–Shamir Heuristic: Non-Interactive Sigma Protocols §15

Objectives

Transform Phase 2's interactive Schnorr protocol into a non-interactive proof via the Fiat–Shamir heuristic, built on the zkp-transcript Merlin-style transcript (§11); establish the Random-Oracle-Model framing for why this is secure and where that assumption can fail.

Deliverable

zkp-transcript crate + non-interactive SchnorrProof variant in zkp-sigma; end-to-end examples/schnorr_identification.rs updated to a single-message proof.

Acceptance

Transcript replay: an honest proof's c is bit-identical whether derived by prover or verifier in 100% of 1,000 trials (I8); a proof whose transcript omits Y (statement-binding ablation test) is forgeable in a scripted attack demonstration, proving why P7 is mandatory, not merely asserting it; forged-proof rejection rate 100% across a 500-vector tamper corpus.

Fixtures

fiat_shamir_valid.json | fiat_shamir_transcript_tamper.json (byte-flip in transcript input, expect reject) | fiat_shamir_missing_binding_demo.json (intentionally vulnerable variant, used only in the ablation test, never shipped as a real code path) | fiat_shamir_label_mismatch.json.

Pitfalls

Hashing "the important part" of the transcript instead of the full statement — the single most common real Fiat–Shamir implementation bug, and exactly what T3/P7 defend against; label collisions between differently-typed transcript entries (domain separation, ADR-10); treating the random-oracle idealization as unconditional security — it is not (MM3, Bellare–Rogaway93's own caveats about ROM separating from standard-model constructions).

⬜ Phase 4 — Arithmetic Circuits & R1CS §16

Objectives

Implement the circuit IR (§8 grammar), the ConstraintSynthesizer trait, and the R1CS constraint-system builder; ship the x^3+x+5=35 worked example (§8) as the first end-to-end circuit; ship the under-constraint linter (P14).

Deliverable

zkp-circuit/zkp-r1cs crates compiling; x^3+x+5=35 circuit expressed in the DSL, compiled to the 4-constraint R1CS instance from §8, satisfied by witness [1,35,3,9,27,30].

Acceptance

The compiled R1CS instance is byte-identical (matrix structure, not just satisfaction result) to an independently hand-derived reference matrix for the §8 example in 100% of runs (I11); linter correctly flags 20/20 synthetic under-constrained circuits in a labeled test corpus and passes 20/20 correctly-constrained ones (0 false positives/negatives on the corpus, P14).

Fixtures

circuit_multiply_by_5.dsl (the §8 worked example source) | r1cs_multiply_by_5_expected.json (expected A/B/C matrices) | underconstrained_corpus/ (20 labeled synthetic circuits) | malformed_dsl_syntax_errors.json (parser error-path fixtures).

Pitfalls

Off-by-one wire indexing between the DSL parser and the constraint system allocator (I11); the linter producing false negatives on constraints that are satisfiable but under-constrained relative to intended semantics (e.g., a missing range check that the DSL's type system cannot express — documented as a known linter limitation, not silently ignored, T6/FC10); public vs. witness wire confusion (a value meant to be public accidentally allocated as witness, breaking verifier-side input binding in later phases).

⬜ Phase 5 — R1CS → QAP Arithmetization §17

Objectives

Implement the R1CS→QAP transform: interpolate each R1CS matrix column into a polynomial over an evaluation domain, construct the vanishing polynomial Z(x), and compute the quotient H(x) satisfying A(x)·B(x) − C(x) = H(x)·Z(x) for a satisfying witness (I6).

Deliverable

zkp-qap crate; the §8 worked-example R1CS instance transformed to a 4-point-domain QAP, with H(x) computed and the identity verified directly (not yet via pairing — that is Phase 7).

Acceptance

Polynomial identity A(x)·B(x) − C(x) − H(x)·Z(x) == 0 (the zero polynomial) holds exactly for the §8 example's satisfying witness in 100% of runs (I6); an intentionally invalid witness (wrong x value) produces a nonzero remainder on division by Z(x) in 100% of a 50-vector negative corpus, confirming the divisibility check actually discriminates satisfying from non-satisfying witnesses.

Fixtures

qap_multiply_by_5_domain4.json (expected A/B/C/Z polynomials) | qap_h_poly_valid_witness.json | qap_h_poly_invalid_witness_nonzero_remainder.json | qap_domain_padding_edge.json (constraint count exactly a power of two, no padding needed).

Pitfalls

Domain-size mismatch between the R1CS row count and the QAP evaluation domain (off-by-one padding error) breaks completeness and soundness simultaneously (I6/FC4, MM4); polynomial long division implemented naively (not FFT-based) becomes the dominant cost at large constraint counts — defer to FFT-based division only when profiling (§28) confirms the naive path is the bottleneck; confusing "the witness satisfies R1CS" with "the polynomial identity holds" as two separate facts requiring two separate proofs, when they are definitionally the same fact (P9).

⬜ Phase 6 — Polynomial Commitments: KZG10 §18

Objectives

Implement the KZG10 polynomial commitment scheme (commit/open/verify) as an independently useful, pedagogically parallel primitive to Groth16 (§3) — not a runtime dependency of Groth16 in this blueprint, but the concrete illustration of "commit to a polynomial, open it at a point, verify in O(1)" that generalizes to PLONK (§34, deferred).

Deliverable

zkp-kzg crate; a standalone example committing to a degree-16 polynomial, opening at a random point, and verifying — with an intentionally wrong opening value rejected.

Acceptance

Verify accepts 100% of 200 honestly generated (commitment, point, value, proof) tuples and rejects 100% of a 200-vector corpus with a tampered value or proof (I1/I2 analogues for KZG); commitment size is exactly 1 compressed G1 point (48 bytes, BLS12-381) regardless of polynomial degree (succinctness, matching M1's proof-size discipline).

Fixtures

kzg_commit_open_verify_valid.json | kzg_tampered_value.json (expect reject) | kzg_tampered_proof.json (expect reject) | kzg_max_degree_boundary.json (degree exactly at max_degree, expect success; degree+1, expect setup-time rejection).

Pitfalls

Committing to a polynomial of degree exceeding the SRS's max_degree silently truncates instead of erroring — must be an explicit bounds check at kzg_commit, not an out-of-bounds panic or silent wraparound; synthetic division for the quotient polynomial assumes the divisor has a known root — a non-exact division (meaning z was not actually a root of p(x)−p(z), a mathematical impossibility if computed correctly, but a real bug signal if it occurs) must be treated as a fatal implementation bug, never suppressed.

⬜ Phase 7 — Groth16 Pairing-Based SNARK (Prove / Verify) §19

Objectives

Implement the Groth16 construction: setup (deriving ProvingKey/VerifyingKey from a QAP and a Phase-2 SRS), prove (producing the 3-element Proof), and verify (the single pairing-based check) — the central deliverable of this blueprint.

Deliverable

zkp-groth16 crate; end-to-end setup → prove → verify on the §8 worked example, both curves (BLS12-381 primary, BN254 conformance), producing an accepting proof for the valid witness and a rejecting result for a tampered one.

Acceptance

Proof size exactly 192 bytes (BLS12-381, M1) / 128 bytes (BN254, M2); verify() latency ≤ 5 ms p50 / ≤ 12 ms p99 on the reference 4-core CPU (M3); prove() latency ≤ 1.5 s p50 at 2^16 constraints on 8-core (M4); differential match against ark-groth16's verify_proof on 500 shared test vectors, 100% agreement (P5, I10); a proof generated for witness x=3 and verified against public input out=36 (wrong) rejects in 100% of trials.

Fixtures

groth16_multiply_by_5_valid.json | groth16_wrong_public_input.json (expect reject) | groth16_tampered_proof_element.json (each of A/B/C independently flipped, expect reject) | groth16_arkworks_crossvector_500.json (shared differential corpus, §21).

Pitfalls

Forgetting the r,s blinding terms collapses zero-knowledge (I3) while leaving completeness/soundness intact — a proof that works but leaks witness-correlated information, the most dangerous kind of bug because tests that only check accept/reject never catch it (must have a dedicated ZK-distribution test, not just an accept/reject test); mixing up gamma/delta denominators between the SRS and the verification equation (a classic Groth16 implementation transcription error against the paper); batching multiple pairing checks incorrectly (see FC12, §23) — a bug only observable in the batch path, never in the single-proof path.

⬜ Phase 8 — Trusted Setup: Powers-of-Tau & Circuit-Specific Ceremony §20

Objectives

Implement the two-phase MPC ceremony (ADR-09): universal Powers-of-Tau (Phase 1, circuit- agnostic, reusable) and circuit-specific Phase 2 (deriving the Groth16 ProvingKey/ VerifyingKey SRS elements) — the highest-stakes trust boundary in the whole system (P3, MM2).

Deliverable

zkp-setup crate; scripts/run_ceremony_sim.sh simulating a 5-participant Phase-1 ceremony plus Phase-2 derivation for the §8 worked-example circuit, producing a ProvingKey/VerifyingKey pair usable by Phase 7.

Acceptance

Ceremony transcript verification (phase1_verify_contribution chained across all 5 participants plus the beacon) passes in 100% of honest-ceremony trials; an injected invalid contribution (one participant's ContributionProof deliberately corrupted) is rejected in 100% of 100 trials (I7); per-participant contribution round ≤ 90 s p50 at 2^20 domain size (M7); a ceremony with only 1 honest-out-of-5 participants (4 colluding, 1 honest, simulated) still produces a secure SRS — verified by confirming the final SRS's implicit exponent is unrecoverable from the 4 colluding participants' combined randomness (P10, MM8).

Fixtures

ceremony_5participant_honest.json | ceremony_invalid_contribution_round3.json (expect rejection + re-request) | ceremony_beacon_application.json | phase2_multiply_by_5_derivation.json.

Pitfalls

Treating ceremony randomness like an application secret (rotatable, storable) instead of radioactive waste to be destroyed (P3, T7, FC7); a participant's process crashing mid-contribution leaving partially-updated SRS elements inconsistent (must be atomic: either the full contribution applies and is verified, or it is discarded wholesale, FC3); insufficient participant diversity (all participants on the same cloud provider/hardware, correlated compromise risk) — not a code bug but an operational one, documented in the ceremony runbook (§24).

⬜ Phase 9 — Conformance & Differential-Test Harness vs. Reference Implementations §21

Objectives

Build the zkp-conformance differential-test harness: in-process cross-implementation testing against ark-groth16 (primary oracle) and bellman (secondary oracle), plus fuzzing (ADR-13) and the timing side-channel gate (M13) — the correctness backstop for every prior phase (P5).

Deliverable

zkp-conformance crate + CI job running ≥ 500 differential vectors, a 1-hour fuzz job, and the dudect timing gate, producing a ConformanceReport (§11) consumed by the release gate (§27).

Acceptance

100% 3-way agreement across ≥ 500 vectors spanning both curves and constraint counts from 4 to 2^16 (M11, M14); 0 panics/crashes across a 1-hour cargo-fuzz run per target (M12); dudect |t| < 4.5 maintained (M13, re-confirmed at this integration scale, not just Phase 0/2's unit scale); conformance suite completes in ≤ 10 min on a 4-core CI runner (M11).

Fixtures

differential_corpus_500.json (the full cross-implementation vector set) | fuzz_corpus_seed/ (seed inputs for the three fuzz targets) | dudect_timing_samples.json | oracle_version_pin.lock (exact arkworks/bellman commit hashes, T9/T8).

Pitfalls

An oracle-version bump silently changing expected outputs (T9/FC8) — mitigated by pinning exact oracle versions and re-deriving vectors deliberately, never automatically; a "passing" 2-way agreement (self matches arkworks) masking a bug shared by both when bellman would have caught it — always require the full 3-way check, not an early-exit 2-way one; fuzz targets that only exercise the "happy path" input shape because the Arbitrary impl is too constrained (structure- aware fuzzing must still reach malformed-but-structurally-plausible inputs).
