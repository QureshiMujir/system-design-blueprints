In one paragraph

This is a batch program, written in Rust, that reads a directed graph (pages and the links between them) and works out how important each node is from the link structure alone (§1). The main score is PageRank, the long-run chance that a random surfer following links lands on each page (§8.1), and the same engine also produces HITS, SALSA, Personalized PageRank and TrustRank rankings (§1). It runs on one host, keeps the whole graph in memory, and is sized for graphs up to about 10⁹ edges (§1, §4). It ships as a command-line tool, prank, plus library crates, run by information-retrieval engineers, graph-ML practitioners and anti-spam teams (§1).

The problem, concretely

PageRank itself is one line, r = G·r; the trouble is everything wrapped around it (§2).

Take the blueprint's four-page fixture tiny-4node: edges A→B, A→D, B→C, C→A, and page D has no outgoing links (§8.4). A page like D is a dangling node. The first mistake is to ignore D: its probability vanishes each round (§8.2), so the scores add to less than 1 and the ranks are biased (P2). The blueprint calls the fix "the single most-omitted correctness step" (§2).

The second mistake is the direction of storage. Rank flows into a page from the pages that link to it, so the loop wants each page's in-links, not its out-links (§2, §8.1). Store only out-links and the loop either mis-attributes mass or does random reads across the whole structure (MM3, P3).

The third is treating this as a maths problem when it is a memory problem. The expensive part is the random read rank_in[row_idx[k]], not the multiplication, so hand-tuned arithmetic does nothing while the cache thrashes (MM2, §2).

The fourth is trusting the input. Graph files and cached binaries are untrusted (§22), and a crafted header claiming far more edges than the file holds can drive an out-of-bounds read (T4, §8.9). Ranking is a security surface too: link farms and tightly knit cliques attack it (§2, T8, T9).

How it works, end to end

Follow one run of prank rank through the boxes of §3's diagram. Each box is a crate in the Cargo workspace (§1, §3).

 untrusted input -> cli (clap, format detect, JSON/TSV out, stderr iteration log)
 ------------------------ TRUST BOUNDARY ----------------------------
 graph-io  : snap / webgraph / adj_list parsers + remap  -> RawEdgeList + dangling[]
 graph-repr: CsrGraph (out-links) + CscGraph (in-links) + DanglingBitVec + mmap binary
 pagerank-core: dangling pre-pass -> SpMV(CSC) -> damp -> teleport -> converge -> normalize
 pagerank-parallel: rayon par_chunks_mut over disjoint destination ranges
 hits . salsa . personalized-pr . trust-rank : share the RankAlgorithm trait
 bench (criterion): GFLOP/s, MB/s, ms
  1. cli parses arguments with clap, detects the input format, runs load, build, rank, emit, and streams one structured report per iteration to stderr (§3, ADR-12, I9). It owns the exit codes and holds no graph invariants (§3).
  2. graph-io is the only code that touches untrusted bytes. It parses SNAP, WebGraph BV and adjacency text, turns labels into dense u32 ids (ADR-17), and computes the dangling set. Every failure is a typed GraphIoError, never a panic (§3).
  3. graph-repr owns the in-memory graph. CsrGraph holds out-links and CscGraph holds in-links plus the src_out_deg_recip array laid out next to row_idx. DanglingBitVec is a Roaring bitmap (§3, ADR-07). The binary cache is loaded through mmap and bytemuck only after a length and checksum check (I12, P6).
  4. pagerank-core is the mathematical heart. One iteration is the dangling-mass pre-pass, a pull sparse matrix-vector multiply over the CSC, a scale by d, the teleport term, the convergence check and a renormalize. It hosts the RankAlgorithm trait every variant implements (§3, P8).
  5. pagerank-parallel swaps the multiply for a Rayon par_chunks_mut over disjoint destination ranges and makes the dangling sum a tree reduction, with no locks. It is checked against the sequential version (§3, P5, I5).
  6. hits, salsa, personalized-pr, trust-rank sit behind the same trait: HITS needs CSR and CSC, personalized-pr has exact and local-push modes, and trust-rank is Personalized PageRank over trusted seeds (§3).
  7. bench is the Criterion harness. It is the only crate allowed to read data/ and it emits the numbers the CI regression gate compares (§3, P12).

The run is a small state machine: IDLE, LOADED, REPR_BUILT, INITIALIZED, ITERATING, then CONVERGED (emit JSON/TSV, exit 0) or TIMED_OUT (exit 2, best vector plus a warning) (§8.6, I15). A parse failure raises GraphIoError and exits 1 (§8.6).

The core ideas

The random surfer and the Google matrix (§8.1, §8.2)

PageRank r is the long-run probability that a surfer who keeps following links is on each page (§8.1). The link matrix H has H[i][j] = 1/outdeg(j) when j → i is an edge, so each page splits its mass evenly over its out-links (§8.1). A dangling page makes a column of zeros, so the blueprint patches the matrix to treat a dangling page as linking to every page equally (§8.2).

That patched matrix still might not have one unique answer, so the surfer also teleports. With probability 1−d they jump to a uniformly random page, and d is the damping factor, standard value 0.85 (§8.2, §36). The result is the Google matrix G = d·S + (1−d)·(1/n)·1·1ᵀ, and r = G·r with ‖r‖₁ = 1 (§8.2). Teleportation is a regularizer that makes the chain well behaved, not a hack (MM9, MM1). With d = 1.0 there is no teleport and power iteration need not converge, so it is rejected at argument parsing, and so is d = 0.0 (§8.9, §14.8, I7, T6).

One iteration: pre-pass, pull multiply, one scalar (§8.3, §8.4)

Start from r⁽⁰⁾ = 1/n everywhere and repeat the recurrence (§8.3):

r(k+1) = d·H·r(k) + [ d·dmass/n + (1−d)/n ]·1       dmass = sum of r over dangling nodes

The bracket is one number, c = (d·dmass + (1−d))/n, added to every node, so the teleport and dangling terms cost one scalar add per node (§8.3, P10). Iteration stops when ‖r(k+1) − r(k)‖₁ < ε (§8.3, P7). The pre-pass runs before every multiply (I2, P2).

The blueprint's trace on tiny-4node (edges A→B, A→D, B→C, C→A; d = 0.85, n = 4), copied as printed, including its last row, which sits one column to the right of its labels (§8.4):

Step dmass =r[D] scalar c r[A] r[B] r[C] r[D]
k=0 0.250 (0.85·0.25+0.15)/4 = 0.0906 0.250 0.250 0.250 0.250
k=1 0.250 0.0906 0.303 0.197 0.197 0.197
k=2 0.197 0.0794 0.270 0.208 0.247 0.196
… … … converges ≈ A:0.275 B:0.198 C:0.230, D:0.166

These numbers do not add up as printed. Do not use them as a correct trace. The blueprint says Σr = 1 at every step (§8.4, I1), but the k=1 row sums to 0.894, the k=2 row to 0.921 and the converged values to 0.869 (§8.4). The same section says D has "no in-links beyond teleport", while its own edge list contains A→D (§8.4). The blueprint does not reconcile either point. The fixture's .expected file is the NumPy/NetworkX value at ε = 1e-12, not this table (§8.4).

How many iterations, and why d matters (§8.5)

The error shrinks like dᵏ because the second-largest eigenvalue of G has modulus at most d (§8.5, MM4). Solving dᵏ < ε gives k > ln(ε)/ln(d), which is about 85 for d = 0.85 and ε = 1e-6, whatever the graph size (§8.5, §32 item 4). That is why iteration count does not grow with the graph but wall time does: each iteration still costs O(m) (§29).

Raising d toward 1 ranks more faithfully but converges slower and conditions worse (§8.5). The blueprint's cautionary example is setting d = 0.99, then blaming the solver for 1000 iterations (MM4). The iteration cap max_iter (default 200) is a safety guard and not a tuning knob. Convergence is declared by the delta, never by hitting the cap (§4, P4, I15).

The blueprint is not consistent about the 85. §8.5 writes "k > 85", while §32 item 4 computes ⌈85.0⌉ = 85 and §4 says "≈ 85"; Phase 2 accepts an iteration count within ±1 of the estimate, and M11 caps it at 90 (§8.5, §32 item 4, §4, §14, M11).

Pull multiply on in-links, with a co-located array (§11.3, P3, ADR-03)

The kernel is a sparse matrix-vector multiply (SpMV) in pull form: each destination j reads the ranks of its in-neighbors and adds rank[i] · src_out_deg_recip (§11.3). The in-links are stored as CSC (compressed sparse column: a col_ptr array plus a row_idx array of in-neighbors) (§11.3, §36). The reciprocal 1/outdeg of each in-neighbor is stored in a parallel array src_out_deg_recip, so the inner loop reads it in order instead of doing a second random read (§11.3, P3). The cost is one extra m-length array of f64 (P3, §32 item 1).

For the parallel version, rank_out is cut into chunks with par_chunks_mut. Each worker owns a disjoint destination range and reads the shared rank_in immutably, so the borrow checker proves there is no data race (§15, ADR-03). The chunk size is max(1000, n/(threads·4)), rounded to a multiple of 8 f64 so chunks do not share a cache line (§15). rank_in and rank_out must be distinct buffers, or the delta compares a vector with itself and reports false convergence (I8, §14). Thread count follows physical cores, because hyperthreads do not help a bandwidth-bound kernel (§4, P3).

Float adds are reordered in the parallel dangling reduction, so the parallel result may differ from the sequential one. The blueprint specifies that difference instead of hiding it: it must stay within n·f64::EPSILON (P5, I5). Sequential output is bit-identical across runs (P5).

Local push: Personalized PageRank without touching the whole graph (§8.7)

Personalized PageRank (PPR) teleports back to a chosen seed set instead of to uniformly random pages, so scores measure closeness to the seeds (§36, I14). LocalPushPpr keeps an estimate p and a residual res, starting with p = 0 and res[s] = 1 for the seed s (§8.7). While some node u has res[u] ≥ ε·outdeg(u), push it (§8.7):

p[u]  += (1−d)·res[u]
res[w] += d·res[u]/outdeg(u)     for every out-neighbor w of u
res[u]  = 0

This ends after O(1/ε) pushes independent of n, with an L1 error of at most ε·m (§8.7, MM5). The threshold must be ε·outdeg(u) and not ε, or the O(1/ε) bound breaks. A dangling u satisfies ε·0 always, so it needs its own handling or the loop never ends (§17, C9). The blueprint gives two push counts for ε = 1e-5 and does not reconcile them: §32 item 11 says about 10⁵ pushes times the average degree, about 10⁶ edge-touches, while §17 says about 10⁴ pushes at average degree 10 (§32 item 11, §17).

The other rankings reuse the same machinery (§16, §17, §18)

HITS gives each node a hub score (as a link source) and an authority score (as a link destination) (§36). It computes auth[j] = Σ hub[i] over in-links through the CSC, then hub[i] = Σ auth[j] over out-links through the CSR, so it is the one variant needing both layouts (§16, P3). It normalizes with the L2 norm each half-iteration, not L1, because the eigenvector reading needs it (I13, §16). It converges only when both deltas fall below ε (§16).

TrustRank is Personalized PageRank with the teleport vector 1/|S| on a trusted seed set (§18, I14). AntiTrustRank does the same from a spam seed set, and spam[i] = anti[i]/(trust[i]+anti[i]) combines them (§18, §36). Trusted seeds are chosen by hand, or by running PageRank on the reversed graph, which needs a separate reverse CSC that never mutates the original (§18, P11).

The trade-offs — where engineers disagree

Custom CSR+CSC instead of a sparse-matrix library (ADR-04)

Chosen: custom CSR and CSC, for full control of layout, degree sort, the co-array and the binary form (§9). Rejected: sprs, nalgebra-sparse, SciPy (§9). When the rejected choice is right: when you need many matrix operations rather than one tuned SpMV (§9).

f64 ranks by default (ADR-05)

Chosen: f64, with an f32 flag, because ranks fall below 1e-8 on graphs of 10⁸ nodes and f32 loses them (§9, §4). Rejected: f32 as the default, f16, arbitrary precision (§9). When the rejected choice is right: f32 on small graphs, to halve bandwidth and double SIMD width (§9). An f32/packed-id mode is deferred until a graph hits the RAM ceiling but is under twice it (§35).

Rust over C++ and others (ADR-01)

Chosen: Rust 1.78 or later, for layout control, compile-time data-race freedom in the parallel multiply, and no garbage-collection jitter (§9, §1). Rejected: C/C++, Go, Java, Python (§9). C++ is as fast, but aliasing and undefined behavior make a correct parallel multiply and a fuzz-hardened BV decoder far costlier to get right (§1). When the rejected choice is right: C++ when an existing tuned SpMV/MPI stack must be reused, and Python for a teaching prototype of at most 10⁶ nodes (§9). Python/NumPy is still used as the reference oracle (§1, §5).

Rayon for parallelism (ADR-03)

Chosen: rayon, because work-stealing over par_chunks_mut maps exactly to disjoint destination ranges (§9). Rejected: tokio, std::thread, OpenMP through FFI (§9). When the rejected choice is right: tokio, if the workload were IO-bound or async serving instead of CPU-bound SpMV (§9). The blueprint defers an HTTP serving layer until online ranked-query serving is required (§35).

Roads not taken (§34, §35)

Vertex-centric BSP (Pregel, Giraph, GraphX) (§34 A1) wins when the graph exceeds one host's RAM (≫10⁹ edges). Below that, barriers and serialization dominate and in-core CSC is far faster; it is the deferred distributed lever (§34, §35).

Edge-centric streaming (X-Stream) (§34 A2) wins when the graph is far larger than RAM and sequential disk bandwidth far exceeds random; it loses whenever the graph fits (§34).

A GraphBLAS backend (§34 A3) wins when you want many graph operations, portability, or a GPU multiply for free. It loses here to one hand-tuned pull multiply with a co-array (§34, P3).

Monte-Carlo random-walk PageRank (§34 A4) wins for fully personalized PPR over all sources, edge arrival streams, or trivially parallel approximate ranks; power iteration is exact and faster for one full-graph batch rank (§34).

Deferred features (§35) each wait for a stated trigger, for example distributed SpMV once the working set passes the 32 GB ceiling (§35, §4).

What must never be false

  • I1: the ranks sum to 1 within 1e-10 after every iteration. Noticed by a sum check, reported as iter.l1_sum. It forces a renormalize, and drift above 1e-6 twice aborts (§7).
  • I2: dangling mass is redistributed before every multiply. Noticed by comparing dmass with the sum over the dangling set, reported as iter.dangling_mass (§7).
  • I3, I4: every rank is positive after iteration 1, and every out-degree reciprocal is finite (1/outdeg, or 0 for a dangling node). Noticed by a minimum scan in debug builds (iter.min_rank) and an is_finite scan at build, which rejects the graph (§7).
  • I5: the parallel result stays within n·f64::EPSILON of the sequential one. Noticed by the CI diff test, reported as bench.par_seq_linf (§7).
  • I6, I10, I11: col_ptr is monotonic and ends at m, every index is below n, and in-degree and out-degree totals both equal m. Noticed by build-time scans and a cross-check, written to the build log. The graph is rejected on failure (§7).
  • I7: the damping factor is strictly between 0 and 1. Noticed by a range check at argument parsing, and 0.0 or 1.0 are rejected (§7, T6).
  • I8: the multiply's input and output buffers are distinct. Noticed by a pointer compare in debug builds. In release it is a documented contract (§7, C7).
  • I9: every iteration emits an IterationReport. Noticed by checking the report count against the iteration count, on stderr (§7).
  • I12: the binary header's n and m agree with the file length and checksum before any cast. Noticed by a length plus SHA-256 header check, written to the load log (§7, T4).
  • I13: HITS hub and authority vectors have L2 norm 1 each half-iteration. Noticed by a norm check and reported as iter.hub_norm and iter.auth_norm (§7).
  • I14: a custom teleport vector sums to 1 within 1e-10. Noticed by a sum check when the config is built, which rejects a bad one (§7).
  • I15: every run stops within max_iter iterations. Noticed by the loop guard, reported as final.iterations. On a timeout it emits the best vector and exits 2 (§7, §19).

What breaks in production

The blueprint numbers its failure classes C1 to C12 (§23); each runs symptom, cause, detection, fix.

C2, convergence failure. The symptom is exit code 2 with a best-effort vector. The causes are d close to 1, a degenerate spectrum, or too low a max_iter. Detection is the TimedOut state (I15). The engine emits the best vector with a warning; the forensic aid is the per-iteration L1 trace (§23, P9). The manual fix is stated two ways: raise --max-iter or "lower ε" (C2), versus raise --max-iter or "relax --epsilon" (§14).

C3, out of memory. The symptom is an abort or an OutOfMemory error. The cause is a graph larger than RAM. Detection is a failed try_reserve. There is no automatic recovery. The operator uses a bigger host or, later, an out-of-core design (§23, §35). Its "≈20 B/edge effective" disagrees with the 16 B/edge of §4 and §32 item 1 (see the bytes-per-edge note under the numbers).

C4, numerical divergence. The symptom is Σr drifting past 1e-6. The causes are a bug in the teleport term or a bad reciprocal (I4). Detection is the l1_normalize warning (I1). The engine renormalizes once, and the operator fixes the term and checks I4. The forensic aid is the dangling_mass curve (§23, I1).

C6, determinism breach. The symptom is a parallel result differing from the sequential one past 1e-14. The cause is a chunk-index bug, not float reordering. Detection is the diff test (I5). The automatic recovery is to fall back to the sequential kernel (§23, P1). The blueprint gives three tolerances for this check: n·f64::EPSILON (I5), which §32 item 12 puts at about 2.2e-8 for 10⁸ nodes; within 1e-12 in tests (P5, §26); and an L∞ below 1e-14 (M4, §15, C6). It does not reconcile them.

C9, the dangling loop in local push. A push never ends because the ε·outdeg(u) threshold is met forever when outdeg is 0. A push-count ceiling detects it, the engine aborts with the residual, the operator handles the dangling case, and the forensic aid is the residual histogram (§23, §17).

C11, spectral capture. The symptom is implausible top ranks. The causes are a link farm (T8) or a tightly-knit clique (T9). Detection is the trust and TKC diagnostics. The engine flags it, and the operator switches to TrustRank or SALSA (§23, T8, T9).

Threats worth knowing (§22):

  • T1, an allocation attack through a declared edge count near 10¹², is stopped by capping m (default 10 billion) before allocating. It rejects the file and exits 1 (§22).
  • T4, a crafted binary cache whose header claims far more edges than the file holds, is rejected by a length and checksum check before any cast (I12, §22, §8.9).
  • T8, a link farm, meaning a dense ring of artificial hubs that inflates a rank, is met by TrustRank and AntiTrustRank with inverse-PageRank seeds, and the detection is the spammicity score (§22, §18).

How it compares

  • NetworkX chose developer ergonomics over scale: pure Python and dict-backed, so it cannot hold a web crawl. That is right for notebook-sized graphs, and the blueprint uses it as the ground-truth oracle, borrowing its formula and not its data model (§31).
  • Ligra chose shared-memory CSR with a frontier switching between sparse push and dense pull by threshold. That is right when you want maximum single-node throughput across many graph algorithms. This design specializes to the PageRank family and fixes the pull direction (§31, ADR-04).
  • Spark GraphX chose the cluster, with vertex and edge RDDs and a Pregel-style API over BSP supersteps. That is right when the graph is part of a larger distributed ETL pipeline already in Spark, even though JVM, serialization and shuffle costs dominate below about 10⁹ edges (§31, §34).
  • PowerGraph (GraphLab) chose vertex-cut partitioning for power-law graphs, a gather-apply-scatter model, and an optional asynchronous mode. That is right on skewed billion-edge graphs across a cluster, and the asynchronous path gives up determinism, which this design refuses (§31, P1, MM7).

Two phase-level conflicts. Phase 0's acceptance asks that tiny-4node output match its expected file and that the SNAP fuzzer run 100k times without a crash, although the ranking kernel is Phase 2 and the fuzzers are Phase 9 (§12, §14, §21). Separately, salsa is a shipped crate with its own files, and T9 and C11 point to it as the defense, yet no phase builds it: §16 mentions it only as a "Phase 4 sibling" (§1, §37, §16, T9).

Questions to test yourself

  1. Why CSC and not CSR for the PageRank kernel, and what changes for HITS? — Hint: §8.1, MM3 and §11.
  2. Show how the dangling pre-pass preserves Σr=1, and what specific bias appears if you drop it. — Hint: §8.2, P2, and C4 in §23.
  3. Why is parallel output allowed to differ from sequential, and by how much — and why doesn't that break the convergence test? — Hint: P5, I5 and §32 item 12.
  4. When does LocalPushPpr beat ExactPpr, and what error do you accept for the speedup? — Hint: §8.7, MM5 and §17.
  5. Trace a crafted CSR binary with m ≫ file length through the load path; which invariant stops the OOB and where? — Hint: §13.2, §8.9 and the T4 row of §22.

If you only remember three things

Probability is conserved or the ranking is wrong, so dangling mass is put back before every multiply and the sum is checked every iteration (MM6, I1, I2). Rank flows opposite to links, so the kernel iterates in-links, and it is a memory-bandwidth problem, so layout matters more than arithmetic (MM3, MM2, P3). The fast parallel path is only trusted against the sequential oracle within a stated bound, and untrusted bytes are validated before they are used (MM7, I5, MM8, I12).

Words used here

  • PageRank: the long-run chance that a random link-following surfer is on each page (§8.1, §36).
  • Dangling node: a page with no out-links, which leaks probability unless handled (§8.2, P2).
  • Damping factor: the chance of following a link instead of teleporting, standard 0.85 (§36, I7).
  • Teleportation: the jump to a uniform or seed vector that keeps the chain well behaved (§36, MM9).
  • Google matrix: the damped, dangling-patched transition matrix whose principal vector is the PageRank (§8.2, §36).
  • Power iteration: repeatedly applying the matrix until successive vectors differ by less than ε (§8.3, §36).
  • CSR / CSC: sparse storage by row (out-links) or by column (in-links) (§11.3, §36).
  • SpMV: sparse matrix-vector multiply, the core cost of every iteration (§36, MM2).
  • Co-array: the reciprocal array laid parallel to row_idx so it is read in order (§36, P3).
  • L1 / L2 norm: sum of absolute values, or square root of the sum of squares (§36, P7, I13).
  • Personalized PageRank: PageRank whose teleport goes to a seed set (§36, I14).
  • Local push: a residual-driven way to compute PPR in O(1/ε) work (§8.7, §36).
  • TKC effect: a tightly-knit clique hijacking HITS hub and authority mass (§36, T9).
  • Spammicity: anti_trust/(trust+anti_trust), a combined spam signal (§36, §18).
  • Trust boundary: the line behind which only graph-io handles untrusted bytes (§3, MM8).
