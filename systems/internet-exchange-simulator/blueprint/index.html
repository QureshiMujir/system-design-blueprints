1. Goal

1.1 What Is Built

A discrete-event simulator of a single Internet Exchange Point (IXP): a shared Layer-2 peering fabric with MAC learning and flooding, member networks that establish BGP sessions bilaterally or multilaterally through an RFC 7947 route server, mandatory prefix filtering (max-prefix, RPKI, IRR, prefix-list), and a data-plane traffic matrix that drives frame forwarding through the fabric to produce port-utilization statistics.

System boundary — one IXP instance: one peering LAN (broadcast domain), N member networks (ASes), one or more route-server instances, one traffic-matrix engine. Driven by a deterministic discrete-event clock (VirtualClock). All state (MAC table, RIBs, session FSMs, flow counters) is in memory; no external network I/O required.

1.5 Language Rationale (Rust — locked)

An IXP simulator couples a Layer-2 switching fabric (MAC learning, flooding, a shared broadcast domain) with a Layer-3 control plane (per-member BGP sessions and a route server), and must scale to hundreds of members with large peering meshes; Rust gives precise frame/RIB data layout, strong typing for the L2/L3 boundary, and fast deterministic event processing.

Additional: zero-cost abstractions enable a hot event loop without GC pauses; the type system enforces MemberId / PortId / Asn newtype distinctions at compile time; unsafe-free for correctness; excellent tooling for property-based and fuzz tests (Phase 14).

2.2 Historical and Architectural Importance

  • IXPs are the physical/logical substrate of the commercial internet; AMS-IX, DE-CIX, LINX each carry multi-terabit aggregate traffic from hundreds to thousands of members.
  • The route-server model (RFC 7947) solved the O(N²) bilateral session scalability problem that constrained early IXP growth in the 1990s.
  • RPKI and IRR filtering at IXPs are the primary operational deployment point for routing-security improvements (MANRS); a misconfigured RS affects every member simultaneously.
  • The L2 shared-fabric model is a conscious design choice with explicit security tradeoffs (broadcast exposure, ARP spoofing) that large IXPs mitigate via port isolation and proxy-ARP.
  • IXP design deepens understanding of BGP policy as a distributed agreement protocol: each member's filter is a local policy that collectively produces global reachability.

3.2 Subsystem Descriptions

ixp-core (identity layer) — all newtype primitives (Asn, MemberId, MacAddr, IpAddr, PortId, PeeringLan, Prefix, Community). No logic; only type definitions, Display/From/PartialOrd impls, serialization. Every other crate depends on this. No I/O, no mutable state.

ixp-sim (discrete-event engine) — owns VirtualClock (monotonic u64 nanoseconds), the priority-queue event heap (BinaryHeap<SimEvent>), and the dispatch loop. Accepts event injectors from all subsystems; delivers events in deterministic (time, seq) order. Drives session timers (ConnectRetry, Hold, Keepalive), MAC aging callbacks, traffic-matrix ticks. Concurrency boundary: single-threaded dispatch; reproducibility requires a fixed initial seed for all random elements (traffic rates, jitter).

ixp-fabric (L2 switching fabric) — maintains one MacTable (per broadcast domain) mapping MacAddr → (PortId, last_seen_time). On Frame ingress: record src_mac → ingress_port; look up dst_mac; if learned → unicast forward; if unknown or broadcast → flood to all other member ports (split-horizon). Aging: ixp-sim injects aging events at configured interval; entries older than mac_age_secs are evicted. Per-port byte/frame counters. Trust boundary: each port belongs to exactly one member; port-MAC association enforced at admit time (I3, I9). No L3 awareness.

ixp-peering (member BGP FSM) — one BgpSession per peer pair (member–member or member–RS). State machine: Idle → Connect → OpenSent → OpenConfirm → Established. Timer events from ixp-sim; state transitions emit SessionUp / SessionDown / RecvUpdate events. OPEN capability negotiation modeled (4-byte ASN, multiprotocol extensions). Hold-timer expiry or explicit NOTIFICATION tears down the session and triggers route withdrawal. Adj-RIB-In / Adj-RIB-Out per session. Data in: RouteAdvertise from ixp-routeserver or peer; out: RecvUpdate events to route processing.

ixp-routeserver (RFC 7947) — one logical RS instance (redundant in Phase 10). Maintains rib_per_member: HashMap<MemberId, LocRib>. On RecvUpdate from a member session: apply import filter (via ixp-policy); store in that member's Loc-RIB; run best-path per member; for each other member, apply export filter; if passes → advertise as RecvUpdate on that member's session. Transparency invariants I1, I10: RS ASN never prepended; NEXT_HOP is the originating member's peering LAN IP. Each member's Loc-RIB is independent (I8). No persistent storage; all state in memory.

ixp-policy (filter pipeline) — stateless filter functions applied by ixp-routeserver and bilateral sessions. Filter chain per direction: prefix_list_check → max_prefix_check → rpki_validate → irr_as_set_check → bogon_check → community_policy. max_prefix: counts accepted prefixes per session; breach → emit SessionDown(MaxPrefixExceeded) (I4). rpki_validate: lookup ROA table (loaded from fixture); return Valid | Invalid | NotFound; drop Invalid when RPKI strict mode enabled (I5). irr_as_set: precomputed transitive as-set expansion; accept only prefixes with origin ASN in the set. Community-based selective announcement: RS checks announce-to / do-not-announce communities before exporting to a given member (Phase 7).

ixp-traffic (traffic matrix + data plane) — holds TrafficMatrix: HashMap<(MemberId, MemberId), TrafficFlow>. Each tick: for each active flow, resolve destination prefix via active BGP routes → obtain NEXT_HOP LAN IP → ARP lookup → MacAddr → inject Frame events into ixp-fabric. Accounts bytes per PortId. Only generates flows between members with active sessions and mutually accepted routes (I6 enforcement in data plane). Port utilization ratio = bytes_sent / (port_speed_gbps × tick_interval_s).

ixp-metrics (observability) — aggregates counters from ixp-fabric, ixp-peering, ixp-routeserver, ixp-traffic. Emits: peering density (active sessions / max possible), routes per member, fabric utilization, per-port utilization, unknown-unicast flood rate, leak/invalid-route counts. Consumed by ixp-scenario assertion engine and ixp-cli report formatter.

ixp-scenario (scenario DSL + assertions) — parses TOML/YAML scenario files; constructs initial member/port/policy/prefix state; feeds fault-timeline events into ixp-sim; after simulation completes, evaluates assert clauses (RIB state, traffic reachability, route counts, session states) and reports pass/fail. Single input surface for operators and researchers.

ixp-cli (command-line interface) — binary entry point. Subcommands: run <scenario>, dump rib <member>, dump mac, dump traffic, report. Formats output as JSON or human-readable tables. Consumes ixp-scenario for run, ixp-metrics for report.

4.3 Scalability Assumptions

  • Session count growth: multilateral (RS) is O(N); bilateral mesh is O(N²/2). Phase 12 benchmarks both.
  • RIB growth: O(N × prefixes_per_member) for RS views; compact prefix interning required above N=500.
  • MAC table: bounded by member count × ports_per_member; does not grow with prefix count.
  • Traffic matrix: O(N²) flows worst-case; sparse matrix representation for large N.
  • Discrete-event queue: heap size bounded by active timer count (~3 timers × N sessions + aging events); O(log N) dispatch per event.

6. Design Principles

P1 — Settlement-Free Peering, Not Transit

Statement. An IXP is a shared fabric where members exchange traffic directly; no member's routes may be used to forward traffic on behalf of a third party through the IXP.

Explanation. Routes learned from member A are announced only to members with a direct peering relationship with A. The IXP carries no transit obligation; this reflects commercial reality: peering is cost-shared, transit is a paid service outside IXP scope.

Tradeoff. Strict settlement-free enforcement reduces reachability a single IXP provides but eliminates route-leak liability and unintended traffic engineering.

Operational implications. ixp-policy must implement a default-deny export posture (RFC 8212). Any relaxation — e.g., allowing one member to provide partial transit — must be an explicit, audited policy exception.

Violation consequence. If the RS re-advertises A's routes to C without a peering relationship, C can send traffic to A's destinations via the IXP, making the IXP a de-facto transit AS. Causes billing disputes, route leaks, and traffic asymmetry. Invariant I6 enforces this.

P2 — Route-Server Transparency (RFC 7947)

Statement. The route server must not insert its own ASN into the AS-path and must preserve the originating member's next-hop address.

Explanation. A standard BGP speaker prepends its own ASN; a route server explicitly omits this step. Next-hop transparency means the RS forwards the next-hop attribute as received from the announcing member, so the receiving member's data-plane points directly to the announcer's LAN IP.

Tradeoff. Transparency simplifies data-plane resolution (receiver contacts announcer directly) but means the RS ASN never appears in AS-path, making loop detection rely entirely on the receiving member's own AS-path check.

Operational implications. ixp-routeserver must keep the RS ASN out of every UPDATE it generates. The per-member Loc-RIB stores routes with the originating member's next-hop intact. Any code path that calls prepend_asn() on an RS-originated UPDATE is a bug.

Violation consequence. Inserting the RS ASN breaks loop detection for members whose ASN happens to equal a previously inserted hop. Rewriting next-hop forces traffic to hairpin through the RS, creating a single point of failure and O(N) RS bandwidth load. Invariants I1 and I10 encode this.

P3 — Shared Broadcast Domain, L2 Correctness

Statement. The peering LAN is one shared Ethernet broadcast domain; all data-plane correctness properties derive from IEEE 802.1D MAC learning and flooding semantics, not from IP routing.

Explanation. All member ports are on the same LAN segment. A frame with an unknown destination MAC is flooded to all other ports. MAC learning maps source MAC addresses to ingress ports. IP-layer reachability is irrelevant to the fabric forwarding decision.

Tradeoff. A single broadcast domain simplifies provisioning (one VLAN) but makes broadcast containment and unknown-unicast flood rate critical to scaling; flood scope grows linearly with member count.

Operational implications. ixp-fabric must implement per-broadcast-domain MAC tables with age-out timers. Frame forwarding is MAC-keyed, not IP-keyed. ARP broadcasts exercise the flooding path. Phase 11 adds flood containment and storm control.

Violation consequence. Treating the peering LAN as a routed segment skips MAC learning, breaks ARP, and violates IEEE 802.1D semantics. Flood rate without containment causes broadcast storms that saturate all member ports simultaneously.

P4 — Per-Member Policy Independence

Statement. Each member's import and export filters, and the RS's per-member Loc-RIB view, are computed independently; one member's policy must not affect another member's RIB state.

Explanation. The RS maintains a separate Loc-RIB for each member. When computing routes to advertise to member X, only X's export filter and the announcing member's import filter are evaluated. Member Y's policy is invisible to this computation.

Tradeoff. Per-member views multiply memory proportional to member count but are essential for correctness: shared RIB computation creates policy interference.

Operational implications. ixp-routeserver stores Map<MemberId, LocRib>. Route computation for member X reads only X's filters and the source member's export filter. ixp-policy filter evaluation must be stateless with respect to other members.

Violation consequence. Sharing a single global best-path and advertising it to all members ignores per-member import/export policy. A restrictive member silently receives routes it should have filtered, or fails to receive routes it should have accepted. I8 enforces member isolation.

P5 — Filtering is Mandatory

Statement. Max-prefix limits, RPKI origin validation, and IRR as-set filtering are non-optional; an unfiltered RS is an active security hazard.

Explanation. Without max-prefix enforcement, a misconfigured or malicious member can inject a full BGP table, leaking routes to all other members. RPKI drops hijacked prefixes at the RS before propagation. IRR filters restrict announcements to the member's documented address space.

Tradeoff. Strict filtering increases RS configuration complexity and requires accurate ROA/IRR data. Loose filtering (accept unknown RPKI state) widens the attack surface; strict filtering (reject unknown) may drop legitimate routes during ROA publication lag.

Operational implications. ixp-policy must implement all three filter types in the import pipeline. Default max-prefix values must be conservative (configurable per member). RPKI mode must default to drop-invalid. IRR as-set must be resolved and cached.

Violation consequence. A member without max-prefix enforcement can inject 900 000+ prefixes, exhausting RS memory and degrading all sessions. A hijacked prefix that passes RPKI-invalid routes causes other members to forward traffic to the hijacker. I4 and I5 encode these constraints.

P6 — Multilateral Peering Scales

Statement. One BGP session from each member to the route server replaces O(N^2) bilateral sessions; the simulator must model and report this difference explicitly.

Explanation. With N members, full bilateral mesh requires N(N-1)/2 sessions. Multilateral peering via the RS requires N sessions. For N=200, bilateral = 19 900 sessions vs. multilateral = 200 sessions.

Tradeoff. Multilateral reduces session overhead but concentrates policy complexity and fault risk in the RS. An RS failure affects all N members; a bilateral failure affects only one pair.

Operational implications. ixp-metrics must report session count under both models. ixp-scenario must support a --bilateral-mesh comparison flag. Phase 12 explicitly benchmarks RIB memory and convergence time under both regimes.

Violation consequence. Defaulting all sessions to bilateral mode in a large scenario makes the simulator O(N^2) in memory and event count, rendering Phase 12 scale tests infeasible and obscuring the RS's core value proposition.

P7 — Control Plane and Data Plane are Distinct

Statement. BGP (control plane) determines reachability and next-hop resolution; the L2 fabric (data plane) forwards frames; the simulator models both layers and their interaction via ARP.

Explanation. BGP sessions run over the peering LAN as TCP connections. The data plane uses ARP to resolve next-hop IPs to MACs, then sends Ethernet frames through ixp-fabric. These are independent event streams in ixp-sim but interact: ARP resolution depends on fabric flooding; BGP session establishment depends on ARP succeeding.

Tradeoff. Modelling both planes increases simulator complexity but is essential for traffic-matrix validation: a route may be installed but traffic may still not flow if ARP fails or the MAC table has aged out.

Operational implications. ixp-sim must dispatch Frame events (data plane) and SessionUp/RecvUpdate events (control plane) on the same VirtualClock. ixp-traffic must resolve dst IP via BGP RIB → MAC via ARP → port via MacTable before generating Frame events.

Violation consequence. Conflating layers (e.g., treating a BGP route as sufficient to forward a frame) skips ARP, makes flood events invisible, and produces incorrect port-utilization statistics. Phase 8 and Phase 11 both depend on this separation.

P8 — Deterministic Simulation

Statement. Given the same seed configuration and event sequence, the simulator must produce bit-identical output on every run.

Explanation. The discrete-event engine uses a (time, seq) priority key. Seq is a monotonically increasing tie-breaker assigned at event insertion time, ensuring total ordering when events share a timestamp. No random-number generators with uncontrolled seeds; no non-deterministic OS calls in the hot path.

Tradeoff. Determinism constrains parallelism: the event loop must be single-threaded or use a deterministic parallel-dispatch model. Acceptable because ixp-sim is a simulation, not a production router.

Operational implications. VirtualClock must advance only via event dispatch, never via wall-clock reads. ixp-scenario asserts are reproducible. Fuzz corpus in Phase 14 relies on deterministic replay.

Violation consequence. Non-deterministic ordering causes flaky scenario asserts that pass on one run and fail on another, making regression testing unreliable and conformance claims unverifiable.

P9 — Leak Containment is Observable

Statement. The simulator must surface when a misconfiguration would cause a route leak or provide unintended transit, not silently accept or silently drop routes.

Explanation. A route leak occurs when routes received from one peer are re-advertised to another in violation of policy. The simulator must emit a named metric/event whenever such a condition is detected.

Tradeoff. Emitting leak events adds instrumentation overhead in ixp-metrics but is the primary value of the simulator for operational training and policy validation.

Operational implications. ixp-metrics must define LeakEvent { src_member, dst_member, prefix, reason }. ixp-scenario asserts must include assert_no_leak and assert_no_transit clauses. Phase 13 exposes these counters via ixp-cli.

Violation consequence. Silent acceptance of misconfigured routes means operators cannot use the simulator to validate policies before deploying them on production RS hardware. The simulator becomes untrustworthy as a policy sandbox.

P10 — Member Isolation

Statement. One member's policy configuration, filter state, or fault event must not corrupt, modify, or delete any other member's RIB view or session state.

Explanation. ixp-routeserver's per-member Loc-RIB is strictly private. Filter evaluation for member X uses only X's filters plus the source member's export filter; it must not read or mutate Y's Loc-RIB. A PortDown for member A's port (I9) flushes only A's MAC entries and resets only A's sessions.

Tradeoff. Strict isolation requires per-member data structures rather than shared tables. This costs memory (O(N) Loc-RIBs) but is non-negotiable for correctness.

Operational implications. ixp-routeserver must use HashMap<MemberId, LocRib> with no shared mutable state across members. Port-flush code must be keyed by PortId, not broadcast-domain-wide. Phase 10 fault tests must assert that non-affected members' RIBs are unchanged.

Violation consequence. Shared mutable RIB state means a mass-withdrawal from member A (e.g., PortDown) can trigger spurious withdrawals in member B's view, causing unnecessary route churn and potentially routing blackholes for B.

P11 — Fault Recovery Is Bounded, Not Instantaneous

Statement. Every fault path (PortDown, session teardown, RS failover, flap damping) must converge to a known state within a stated time budget; "eventually consistent" is insufficient without an explicit bound.

Explanation. A PortDown event must flush MAC entries, reset sessions, and withdraw routes within one dispatch cascade (I9); RS failover must promote a standby without a full re-convergence; flap damping suppresses a flapping session but must decay predictably. Each has a stated ceiling in §4.1 (e.g., PortDown → session reset ≤ 5 s simulated time), so "the system recovers" is falsifiable, not aspirational.

Tradeoff. Bounding recovery time constrains implementation choices — RS failover cannot recompute the full RIB from scratch (that blows the bound at scale), so it must maintain a live/near-live standby snapshot instead, trading memory for recovery latency.

Operational implications. Phase 10 must implement and test against the numeric fault-recovery ceilings in §4.1; ixp-scenario's fault timeline and assert framework (Phase 13) must assert "converged within T ticks of fault injection," not merely "eventually converged."

Violation consequence. An unbounded recovery path (e.g., RS failover that always rebuilds every Loc-RIB from GlobalRib) passes correctness tests at small N but silently fails the recovery-time budget at scale, hiding a production-relevant defect until Phase 12 load testing — or until a real IXP outage.

P12 — Conformance Is Regression-Tested Continuously, Not Asserted Once

Statement. RFC 7947 transparency, filtering correctness, and determinism are re-verified on every change via an automated conformance/fuzz/soak gate (Phase 14); a one-time manual check at Phase 5 completion is not sufficient evidence of correctness for the life of the project.

Explanation. Invariants I1, I5, I6, I8, I10 are exactly the properties a single implementation bug can silently break while unit tests still pass (e.g., a refactor that reintroduces an as_path.push(rs_asn) call). Only a fixed, deterministic conformance suite run on every commit (ADR-15, ADR-16, ADR-18 CI matrix) catches such regressions before they reach a tagged release.

Tradeoff. Continuous conformance/fuzz/soak testing costs CI wall-clock time (fuzz jobs run nightly, not per-PR, per ADR-16) and requires maintaining a growing fixture and corpus set, but it is the only way determinism (P8) and transparency (P2) remain load-bearing guarantees rather than one-time claims.

Operational implications. Phase 14's conformance harness and fuzz targets must run in CI on every PR (fast conformance suite) and nightly (fuzz + soak); Build & Release Engineering's release-channel gates must block a tagged release on any conformance or fuzz regression.

Violation consequence. Treating conformance as a one-time Phase-5 milestone rather than a standing gate lets a later phase (e.g., Phase 12's RIB-compaction rewrite) silently reintroduce an RFC 7947 transparency violation that only a live audit — or a real operator — would catch.

Loc-RIB[member] Prefix RsRoute (post-filter) one per receiving member
Adj-RIB-Out[member] Prefix RsRoute (ready to advertise) derived from Loc-RIB

Loc-RIB[M] invariant (I8): ∀ r ∈ Loc-RIB[M]: import_filter(r, M) ∧ export_filter(r, M) hold. Evaluated at every UPDATE and at session teardown (I7 quiescent point).

8.5 Prefix Filter Pipeline (EBNF + evaluation order)

Grammar:

filter-rule      ::= action WS match-clause
action           ::= 'permit' | 'deny'
match-clause     ::= prefix-expr | as-path-expr | community-expr
prefix-expr      ::= cidr-prefix [' le ' mask-len] [' ge ' mask-len]
as-path-expr     ::= 'as-path' WS as-set-name
community-expr   ::= 'community' WS community-value
community-value  ::= u32 ':' u32
cidr-prefix      ::= ipv4-cidr | ipv6-cidr

Import evaluation order (step wins on first match; implicit deny any at end):

Step Check Drop condition Invariant
1 Bogon prefix prefix ∈ bogon_set (RFC 5735/3849) I5, P5
2 Too-specific v4 > /24 or v6 > /48 P5
3 IRR as-set origin_asn ∉ expand(sender.irr_as_set) P5
4 RPKI state == Invalid ∧ rpki_mode == Strict I5
5 Import prefix-list prefix ∉ sender.import_filter.prefix_list I7
6 Max-prefix count(Adj-RIB-In[sender]) > sender.max_prefix I4
7 Export prefix-list prefix ∉ receiver.export_filter.prefix_list I7
8 Community selective community deny-to or deny-all applies §8.7

8.6 RFC 7947 RS Processing Pipeline

Member UPDATE →
  [1] RS import filter (steps 1-6 from §8.5) → accept/reject
  [2] Store RsRoute in Adj-RIB-In[sender]
  [3] For each member M ≠ sender:
        a. Apply sender's export community rules for M  (§8.7)
        b. Apply M's import prefix-list
        c. If passes: upsert Loc-RIB[M][prefix]
        d. If Loc-RIB[M][prefix] changed: generate UPDATE toward M
  [4] INVARIANTS enforced throughout:
        as_path unchanged (I1) | next_hop unchanged (I10)
        Loc-RIB[M] independent from Loc-RIB[K], M≠K (I8)

Session count: O(N) sessions total (each member → one RS session); N-1 bilateral baseline = O(N²); difference observable in Phase 12 (P6).

8.7 Community-Based Selective Announcement

Community (large-community RS_ASN:func:param) Resolution
RS_ASN:0:0 Do not announce to any member
RS_ASN:0:M Do not announce to member with ASN M
RS_ASN:1:M Announce only to member with ASN M
RS_ASN:65535:65535 Announce to all (default; absent = this)

Resolution order: explicit deny-all (0:0) > explicit deny-to (0:M) > explicit announce-only (1:M) > default announce. Contradiction (0:0 + 1:M): deny-all wins.

8.8 Peering Policy Matrix

PeeringKind RS import default RS export default Bilateral session
Open accept (post-filters) export to all allowed
Selective accept only whitelisted prefixes export per community rules allowed
Restrictive reject unless explicit permit no export unless whitelisted only bilateral

Export filter applies at step 3c of §8.6 for each target member M. No transit path is created: next_hop in each exported route is originating member's LAN IP, never RS or intermediate member (I6, I10).

8.9 Discrete-Event Scheduler Semantics

VirtualClock: monotone u64 nanoseconds; wall-clock never accessed.

Priority queue order: (time, seq) — min-heap; seq is a per-nanosecond monotone counter assigned at event creation; ensures deterministic tie-breaking (P8).

Dispatch loop contract:

while let Some(ev) = queue.pop_min():
    assert ev.time >= clock.now()
    clock.advance(ev.time)
    dispatch(ev.kind)            // may enqueue future events
    // no mutation of past events

IxpEvent taxonomy:

Variant Payload Source module
Frame Frame + ingress PortId ixp-traffic, ixp-fabric
SessionUp BgpSession id ixp-peering
SessionDown BgpSession id + NotifyCode ixp-peering
RecvUpdate session_id + routes_added + routes_withdrawn ixp-peering
SendUpdate member_id + routes + withdrawn ixp-routeserver
PortDown PortId fault injection, ixp-fabric
PortUp PortId fault injection
MacAgeCheck BroadcastDomainId ixp-fabric
TrafficTick TrafficFlow + bytes ixp-traffic
MaxPrefixBreached MemberId + count ixp-policy
FlapDamp BgpSession id + penalty:f64 ixp-peering
ScenarioAssert assert_id + predicate ixp-scenario

No event mutates past state; all effects append to NDJSON event log for deterministic replay (P8).

8.10 Traffic Matrix and Frame Resolution

TrafficFlow resolution:
  1. src member has route to dst_prefix in Loc-RIB[src] (RS) or Adj-RIB-In (bilateral)
  2. next_hop_ip ← route.next_hop  (I10: dst member's LAN IP)
  3. dst_mac ← ARP table lookup(next_hop_ip)
  4. Frame { src_mac=src_port.mac, dst_mac, ethertype, payload_len }
  5. Inject Frame event at src_port ingress
  6. ixp-fabric: MacTable lookup → unicast or flood (I2)
  7. byte-account: src_port.tx_bytes += payload_len; dst_port.rx_bytes += payload_len
  8. No route → drop; emit NoRoute metric (P9)
  9. Flow only generated if src and dst are peered (I6 check)

Port utilization model:

  • Budget per tick: speed_gbps * 1e9 / 8 * tick_ns / 1e9 bytes.
  • Excess bytes dropped (tail-drop); port.drops++.
  • Congestion threshold: util > 0.95 → emit HighUtilization event.
  • LAG aggregate budget = sum of member port budgets; flow hashed to one port.

Phase 1 — Sim Engine + IXP Entity Model

1.1 Objectives

  • Implement ixp-sim: deterministic discrete-event queue with VirtualClock, monotonic (time_ns, seq) ordering.
  • Implement ixp-core: all canonical identity types (Asn, MemberId, MacAddr, IpAddr, PortId, PeeringLan).
  • Implement ixp-scenario: config loader (TOML/YAML) → Member, Port, PeeringLan, prefix lists, peering policy.
  • Construct broadcast domains from config; produce stable PeeringLan with member membership.
  • Deterministic dispatch: tie-break by seq; no wall-clock dependency; fully replayable.

1.2 Detailed Implementation Steps

ixp-core/src/lib.rs

Type Representation Key invariant
Asn(u32) newtype 1–4294967294 valid; 0 and 4294967295 reserved
MemberId(u32) newtype assigned at config load; stable for session lifetime
MacAddr([u8;6]) newtype all-zeros = invalid; FF:FF:FF:FF:FF:FF = broadcast
PortId(u32) newtype unique across the fabric
Prefix { addr: IpAddr, len: u8 } len ≤ 32 (v4) / 128 (v6)
PeeringLan { id, subnet: Prefix, members: Vec<MemberId> } subnet is the shared /24 or /64
Port { id: PortId, member: MemberId, mac: MacAddr, speed_gbps: u32, up: bool }
Member { asn, ports, policy, announced: Vec<Prefix>, peering_kind }

ixp-sim/src/engine.rs

  • SimEvent { time_ns: u64, seq: u64, kind: IxpEvent } — Ord by (time_ns, seq).
  • BinaryHeap<Reverse<SimEvent>> as the event queue.
  • VirtualClock { now_ns: u64, next_seq: u64 } — schedule(delay_ns, kind) -> SimEvent.
  • Dispatcher trait: fn dispatch(&mut self, ev: SimEvent, state: &mut IxpState).
  • IxpState aggregates all subsystem state refs; passed by mutable ref to each dispatcher.
  • Event loop: while let Some(ev) = queue.pop() { clock.advance(ev.time_ns); dispatch(ev, state); } — single-threaded, deterministic dispatch per ADR-05/ADR-06, giving the bit-identical replay required by P8.
  • No real-time sleep; VirtualClock::advance is a monotonic assignment (ADR-07).

ixp-scenario/src/loader.rs

  • Parse TOML scenario file → ScenarioDef { members, links, policy, fault_timeline, asserts }.
  • Validate: each port belongs to exactly one member; each member has ≥1 port; no ASN duplicates.
  • BroadcastDomainBuilder: group ports by peering_lan_id; construct PeeringLan; assign member IPs from subnet sequentially.
  • Emit SimEvent::MemberJoin for each member at t=0 to bootstrap sessions.

1.3 Deliverable

  • ixp-core, ixp-sim, ixp-scenario compile without warnings.
  • CLI: ixp-cli run <scenario.toml> --dry-run loads config, builds broadcast domains, emits member/port/LAN summary.
  • Event queue processes a synthetic 1000-event workload in deterministic order; replayed run produces identical event log.

1.6 Pitfalls

  • u64 overflow on time_ns: nanosecond accumulation past 584 years wraps; use saturation arithmetic on VirtualClock::advance.
  • Non-determinism from HashMap iteration: any HashMap<MemberId,_> iterated for event emission must be BTreeMap or sorted before dispatch.
  • Seq counter reset between runs: next_seq must be seeded to 0 per simulation run; leaking across tests causes ordering divergence.
  • Port MAC collision: two ports with identical MacAddr in the same LAN produce ambiguous MAC table entries; validate at config load.
  • PeeringLan subnet overlap: two LANs sharing an IP prefix cause silent ARP collisions in Phase 8; validate disjointness at load time.

1.7 Performance Concerns

  • BinaryHeap push/pop is O(log N); for 10^6 events acceptable; avoid cloning IxpEvent payloads — box large variants.
  • BTreeMap for member/port maps: O(log N) at ≤1000 members; HashMap faster but non-deterministic iteration breaks replay.
  • Config deserialization: parse once, validate once; do not re-parse per event.

1.8 Edge Cases

  • Member with zero announced prefixes: valid at load; must not cause BGP session panic.
  • PeeringLan with a single member: valid; no sessions possible; no error.
  • Scenario fault timeline referencing unknown MemberId: return UnknownMember at validation, not at runtime.
  • time_ns values in fault timeline must be monotonically non-decreasing; out-of-order faults rejected at load.

1.9 Failure Analysis

Failure Detection Blast radius Recovery

  • Log field { time_ns, seq, kind } at DEBUG for every dispatch.

2.1 Objectives

  • Implement ixp-fabric: per-PeeringLan MAC learning, unicast forwarding, unknown-unicast and broadcast flooding.

enum ForwardDecision { Unicast(PortId), Flood(Vec<PortId>), Drop(DropReason) }

Algorithm (in order):

  1. Reject if ingress port up == false → Drop(PortDown).
  2. Reject src_mac == 00:00:00:00:00:00 → Drop(InvalidSrcMac).
  3. mac_table.learn(frame.src_mac, ingress, now_ns).
  4. Broadcast (dst_mac == FF:FF:FF:FF:FF:FF) → flood all up LAN ports except ingress.
  5. mac_table.lookup(frame.dst_mac, now_ns):
    • Some(egress) and egress != ingress → Unicast(egress).
    • Some(egress) and egress == ingress → Drop(Hairpin).
    • None → flood all up LAN ports except ingress.
  6. Update PortCounters on each path.

ixp-fabric/src/aging.rs

  • AgingScheduler schedules first AgingTick at t = aging_ns / 2; reschedules each tick.
  • Tick interval = aging_ns / 2 (ensures entries do not linger more than 1.5× aging_ns).

2.6 Pitfalls

  • MAC flap without flush: member reconnects on new port; stale entry routes to old (down) port until aging. Mitigate: flush MAC entries for a port on PortDown (I9).
  • Split-horizon omission: originator receives own broadcast → ARP storm in Phase 11. Assert ingress ∉ egress_list in every test.

  • Flood to down port: filter up==true after split-horizon exclusion; omission wastes counter budget and masks real delivery.
  • Per-LAN isolation: MacTable keyed only by MacAddr without LAN scope causes cross-LAN MAC collisions. Key by (LanId, MacAddr).
  • aging_ns = 0: every lookup returns None; all frames flood. This is valid behavior; code must not panic.

2.7 Performance Concerns

  • MacAddr is 6 bytes; use FxHashMap<MacAddr, MacEntry> for fast fixed-size-key hashing.

  • Flood list: pre-allocate Vec<PortId> with LAN member count as capacity; reuse per call.
  • PortCounters: plain u64 fields; no atomics needed in single-threaded sim.

3.6 Pitfalls

  • Stale timer handle after cancel / Hold not reset on Keepalive: TimerExpiry dispatch must check CancelSet first (omission causes invalid transitions from cancelled timers); RecvKeepalive in Established must reschedule Hold (omission causes spurious HoldExpiry teardown).

  • AS_TRANS mishandling: ASN > 65535 without FourByteAsn must send 23456 in 2-byte OPEN field; wrong value causes OPEN error and session failure.
  • Duplicate SessionStart: config reload calling create_session twice → conflicting timer handles; guard with idempotency check.
  • Route withdrawal on Hold expiry: routes advertised in Established must be withdrawn when session returns to Idle; omission leaves phantom routes in RIBs (I7 violation).

3.7 Performance Concerns

  • BTreeMap<SessionId, BgpSession> at bilateral mesh with 1000 members = O(N^2) = 10^6 sessions; O(log N) lookup per dispatch is acceptable.
  • CancelSet: HashSet<TimerHandle> for O(1) membership; never scan the event queue to remove cancelled events.
  • Timer scheduling: 1000 members × 3 timers = 3000 live timers in heap (manageable); route withdrawal on teardown for large announced sets (≥10 k prefixes) batches into one WithdrawAll(SessionId) event rather than per-prefix events.

7.6 Pitfalls

  • Asymmetric policy not modeled: A's ExportFilter and B's ImportFilter are independent; both must pass for a route to appear in B's Loc-RIB. Forgetting the import side causes phantom accepts.
  • Community wildcard collision: (IXP_ASN, 65281) announce-all and (IXP_ASN, PEER_ASN) are both set; resolution order must be deterministic (specific wins over wildcard). Missing precedence rule causes flapping RIB views.
  • Loc-RIB rebuild cost at scale: rebuilding every member's view on each UPDATE is O(members × routes); for Phase 12 scale, incremental diff is required. Signal: rib_rebuild_us histogram spike.
  • Community leak to downstream: if community_strip is not applied before forwarding, internal IXP communities leak to member routers — violates RFC 7948 sec. 5. Debug: dump-rib community field on forwarded routes.
  • Restrictive member with no whitelist silently drops all routes: no error emitted; operator may believe filtering is misconfigured. Emit WARN policy.restrictive.empty_allowlist asn=X log.

7.7 Performance Concerns

  • PolicyResolver::resolve_export called per (route, src, dst) pair per UPDATE; cache last result keyed by (route.communities_hash, src, dst) — cache invalidated on policy reload.
  • HashSet<MemberId> for allow-lists: prefer SmallVec<[MemberId;8]> + linear scan for entries ≤8; avoids heap allocation for typical selective lists.
  • Community matching: store as sorted Vec<Community> + binary search; avoid per-route HashMap allocation.
  • Policy reload (SIGHUP or scenario fault): swap Arc<PolicySet> atomically; no stop-world.

7.8 Edge Cases

  • Route carries both (IXP_ASN, 0) (do-not-export) and (IXP_ASN, 65281) (announce-all): do-not-export takes precedence (deny-wins rule).
  • Member submits UPDATE with >32 communities: accept up to configured max_communities (default 32), strip excess, log WARN.
  • Policy changed mid-session: existing Loc-RIB entries re-evaluated against new policy on next quiescence; no session teardown required.
  • Selective allow-list references ASN not present in the IXP: treated as future-peer entry, no error, routes simply never match.
  • RS receives route with community referencing its own IXP ASN but unrecognized value: pass-through (do not drop); log at TRACE.

7.9 Failure Analysis

  • Incorrect community parsing → routes accepted/rejected incorrectly → member loses reachability. Detection: policy.reject_reason=community_mismatch counter spike. Recovery: reload policy config; counter resets.
  • Policy resolver panic on unknown community value → RS thread crashes → all multilateral sessions lose route propagation. Containment: return Result::Err; log + skip route rather than panic. I8 ensures blast radius = affected route only.
  • Whitelist desync (two RS instances with stale config): one RS accepts, other rejects same route — asymmetric reachability. Detection: cross-RS Loc-RIB diff in metrics. Recovery: config push to both instances atomically.

Rate enforcement algorithm (per PortQueue):

  • Per tick window (util_window_ms, default 100 ms simulated), accumulate queued_bytes.
  • capacity_bytes_per_window = speed_gbps × 1e9 / 8 × (util_window_ms / 1000).
  • If queued_bytes > capacity_bytes_per_window × (1 + queue_burst_factor) — drop frame; drop_bytes += payload_len; emit IxpEvent::PortDrop { port, bytes }.
  • Otherwise enqueue; at window end flush counters and report to ixp-metrics.

LAG group forwarding (lag.rs):

  • LagGroup::select_port(frame: &Frame) -> PortId — CRC32 of (src_mac || dst_mac) or (src_ip || dst_ip) per LagHashPolicy; result modulo active_ports.len().
  • LagGroup::active_ports() — excludes ports where Port.up == false (I9).
  • MacTable maps MacAddr to LagGroup or single PortId; learning records the LAG ID if ingress port is a LAG member.

Utilization tracking (ixp-fabric::utilization.rs):

  • Rolling window: VecDeque<(SimTime, bytes)> per port; evict entries older than util_window_ms.
  • util_pct = window_bytes / capacity_bytes_per_window × 100.0.
  • Hotspot threshold: hotspot_util_pct (default 80.0); emit IxpEvent::PortHotspot { port, util_pct } on crossing.
  • Sustained hotspot: hotspot persisting beyond hotspot_sustain_ms (default 1000 ms) — emit WARNING log + metric fabric.hotspot_sustained.

  • IxpEvent::PortWindowReset { port } fires every util_window_ms; PortQueue counters archived to metrics and reset.

9.6 Pitfalls

  • LAG hash imbalance on small member sets: XOR hash with only 2 peers produces high imbalance if MACs share common bits. Mitigation: apply CRC32(src_mac || dst_mac) % n instead of raw XOR.
  • Utilization window boundary artifact: bytes straddle two windows; a frame injected just before reset adds to old window but egresses in new window — util double-reported. Fix: account at ingress time, not egress.
  • LAG port up=false not reflected in MacTable: MAC still maps to downed LAG member; unicast frames sent to dead port. Enforce I9 — port-down event must call lag.evict_port(port) and flush MacTable entries pointing to it.
  • PortQueue counter not reset between scenarios: bytes accumulate across scenario runs in tests. Enforce: Port::reset() called in scenario teardown.
  • Hotspot threshold hysteresis missing: util oscillates around threshold causing flood of metric events. Add hysteresis: alert on cross above hotspot_util_pct, clear on drop below hotspot_util_pct - 5.0.
  • LAG with single active port treated as non-LAG: must still use LagGroup::select_port path to avoid code divergence; select_port with len=1 always returns the one port.

9.7 Performance Concerns

  • Rolling utilization window (VecDeque) per port: at 10k frames/sec per port times 100 ports, 1M pushes/sec; bound window to ceil(window_ms / min_frame_interval_ms) entries; use pre-allocated ring buffer.
  • PortQueue hot path: single-threaded per sim step; no locking; only one writer per PortId at a time (enforced by sim's single event dispatcher).
  • LAG select_port CRC32: use crc32fast crate; under 5 ns per call; amortized over payload_len bytes.
  • util_pct computed on-demand at window flush, not per-frame — avoids floating-point division in hot path.
  • Metric flush (ixp-metrics) batched at window boundary; avoid per-frame metric write.

9.8 Edge Cases

  • speed_gbps = 0.0: error at scenario load; reject config.
  • All LAG ports down simultaneously: active_ports().len() = 0; select_port returns Err(LagAllDown); frame dropped; emit IxpEvent::LagAllDown { lag_id }.
  • util_window_ms smaller than sim tick resolution: clamp to tick resolution; log WARN.
  • queue_burst_factor < 0.0: reject at config parse; must be >= 0.0.
  • Frame payload_len = 0: accept (valid Ethernet); counts as 1 frame for frame counters; 0 bytes for utilization.
  • LAG member added mid-scenario (hot-join): mark port up=true in LagGroup.ports; hash modulus changes — existing flows may shift ports; acceptable (stateless hash).
  • Port speed downgrade mid-scenario (simulated SFP swap): recalculate capacity_bytes_per_window at next window start.

Phase 10 — Fault Handling

10.1 Objectives

  • Model PortDown event: flush MacTable entries on that port, reset all BgpSessions traversing it, withdraw all routes learned via those sessions.
  • Implement route-server failover: redundant RouteServer instances; promote standby on primary failure without full RIB re-computation.
  • Flap damping: suppress session re-establishment for members with excessive session transitions; track penalty/half-life per session.
  • Session re-establish: schedule ConnectRetry after configurable backoff; re-announce member's prefixes on Established.
  • Invariant gate: I9 (port-down flushes MAC + resets sessions); I4 (max-prefix re-checked on re-establish).

10.2 Detailed Implementation Steps

ixp-sim / event dispatch

  • Add IxpEvent::PortDown(PortId) and IxpEvent::PortUp(PortId) to SimEvent.
  • On PortDown(pid): call ixp_fabric::MacTable::flush_port(pid) — removes all (MacAddr, PortId) entries where port = pid; emit IxpEvent::MacFlushed(pid, count) (I9).
  • Query ixp-peering for all BgpSessions with local_port == pid or remote_port == pid; for each, inject IxpEvent::SessionDown(session_id, Reason::PortDown).

ixp-peering / session teardown

  • SessionDown handler: transition SessionState → Idle; withdraw all routes in Adj-RIB-Out by emitting IxpEvent::WithdrawAll(member_id); cancel Hold and Keepalive timers.
  • ConnectRetry timer: exponential backoff [1s, 2s, 4s, … 64s] capped; governed by FlapDampState.

ixp-policy / flap damping (module ixp_policy::flap)

FlapDampState { penalty: f64, last_update: SimTime, suppressed: bool }
  • On session down: penalty += 1000; on session up: penalty += 500 (asymmetric); half-life decay τ = 15 min sim-time.
  • Suppress re-dial when penalty > suppress_threshold (default 2000); un-suppress when penalty < reuse_threshold (default 750).

ixp-routeserver / RS failover

  • Two RouteServer instances: primary and standby; each holds a rib_per_member: Map<MemberId, LocRib>.
  • Standby mirrors primary's LocRib via periodic IxpEvent::RsRibSnapshot; diff applied per phase.
  • On IxpEvent::RsDown(primary_id): ixp-sim promotes standby; re-announces its current LocRib views to all members; no full re-convergence needed if snapshots are current.

ixp-peering / route withdrawal cascade

  • WithdrawAll(member_id) propagates: bilateral sessions receive UPDATE with all of member's prefixes in WITHDRAWN_ROUTES; RS calls RouteServer::withdraw_member(member_id) → removes member's routes from all per-member LocRib views, emits UPDATE withdrawals to remaining members.

10.3 Deliverable

  • ixp-sim processes PortDown → MAC flush → session reset → route withdrawal in a single deterministic event cascade.
  • Redundant RS promotion observable via ixp-cli dump rs-failover-log.
  • Flap-damped sessions remain suppressed until penalty decays below reuse threshold.
  • Session re-establishes after backoff; member re-announces prefixes; RIB converges to pre-fault state.

Phase 11 — Broadcast-Domain Hygiene

11.1 Objectives

  • Model ARP/ND (RFC 826 / RFC 4861) on the peering LAN: members issue ARP requests to resolve peer LAN IPs; fabric floods the request; target replies unicast.
  • Contain unknown-unicast flooding: track flood rate per broadcast domain; enforce storm-control threshold; drop excess flood frames.
  • Detect and surface proxy-ARP hazards: a member answering ARP on behalf of another is flagged.
  • MAC-table overflow: cap MacTable entries per broadcast domain; handle insertion at capacity.
  • One-MAC-per-port enforcement: if a port presents a new MAC different from its registered MAC, flag the violation.
  • Invariant gate: I2 (unicast to learned port only; unknown floods), I3 (MAC aging), I9 (port-down flush).

11.2 Detailed Implementation Steps

ixp-fabric / ARP modeling

  • Add Ethertype::Arp and Ethertype::Ipv6Nd to Frame payload metadata.
  • ArpEvent { op: Request|Reply, sender_mac, sender_ip, target_ip } injected by ixp-traffic when a member needs to resolve a peer's LAN IP.
  • Fabric floods ArpEvent (op=Request) to all ports in the broadcast domain except source (split-horizon).
  • Target member emits ArpEvent (op=Reply) unicast back to requester; fabric learns both MACs (I2, I3).

ixp-fabric / flood containment (module ixp_fabric::storm)

StormControl { token_bucket: TokenBucket, threshold_pps: u64, drop_count: u64 }
  • One StormControl instance per broadcast domain; token refill rate = threshold_pps.
  • On unknown-unicast or broadcast frame: consume 1 token; if bucket empty — drop frame, increment drop_count, emit IxpEvent::StormDrop.
  • Configurable: storm_control_pps in scenario DSL (default 10 000 pps).

ixp-fabric / proxy-ARP detection

  • On ArpEvent(op=Reply): check if sender_ip is registered as the LAN IP of the member owning sender_mac.
  • If mismatch: emit IxpEvent::ProxyArpDetected { responder: MemberId, claimed_ip: IpAddr, actual_owner: MemberId }.
  • Flag does not drop by default (configurable); increment proxy_arp_count metric.

ixp-fabric / MAC-table overflow

MacTableConfig { max_entries: usize, overflow_policy: Drop | EvictLru }
  • On insertion when len == max_entries: if EvictLru, remove least-recently-seen entry; if Drop, reject insertion, treat frame as unknown-unicast, increment mac_overflow_count.
  • Log WARN mac_table_full domain=D entries=N on first overflow per domain.

ixp-fabric / one-MAC-per-port

  • Port carries registered_mac: Option<MacAddr> from ixp-core config.
  • On Frame ingress: if src_mac != registered_mac && registered_mac.is_some() — emit IxpEvent::MacViolation { port: PortId, seen: MacAddr, expected: MacAddr }; do not learn the new MAC.

  • Emit structured, queryable metrics from every subsystem: ixp-metrics aggregates from ixp-fabric, ixp-peering, ixp-routeserver, ixp-traffic, ixp-policy.
  • Define a scenario DSL (TOML/YAML) in ixp-scenario: declare members, ports, peering policy, announced prefixes, fault timelines, and post-run assertion blocks.
  • Expose CLI commands in ixp-cli to dump metrics snapshots, RIB views, MAC tables, and traffic summaries.
  • Constraints: metrics collected in-sim via VirtualClock timestamps; no wall-clock dependencies; all counters 64-bit monotonic; scenario asserts evaluated deterministically after replay.

13.6 Pitfalls

  • Assert tick alignment / monotonicity of counters: assert evaluated before fault event at same tick → order FaultEvent before Assert within a tick; simulation rewind (replay from snapshot) double-counts → snapshot must save+restore counter state, never accumulate across replay boundaries.
  • Peering density division by zero: N=1 member → max_pairs = 0; guard with if N < 2 { return 0.0 }.
  • TOML prefix parsing: IPv6 :: in TOML string triggers TOML-spec escaping edge case → use raw string literals in test fixtures; validate round-trip.
  • Large RIB dump in CLI / assert at_tick beyond scenario end: 100k routes as JSON OOMs small environments → stream line-delimited JSON; out-of-range assert silently passes → treat as parse-time error, validate all ticks <= scenario end.

13.7 Performance Concerns

  • MetricsStore uses AtomicU64 per counter, batch-read via snapshot to avoid per-read locking; snapshot ring buffer is a fixed-size array, no heap growth after init.
  • Scenario DSL parse (serde+toml): large prefix lists parsed once at startup, not per-tick; peering density computed once per snapshot interval, not per event.
  • CLI JSON serialization: serde_json with BufWriter; avoid to_string for large RIBs.

13.8 Edge Cases

  • Zero-prefix member: valid; rs.routes_per_member[m] = 0; no assert should assume non-zero without explicit setup.
  • Duplicate assert IDs / member in assert but not in scenario members list: both reject at parse time (named error / not a runtime panic).
  • Fault timeline events out of chronological order: sort at load time; emit warning.
  • Metric key collision from two crates registering the same string: MetricsStore::register returns Err on duplicate; crate init fails fast.
  • Tick overflow (u64 wraps): VirtualClock is u64; document max simulation ticks; assert at u64::MAX - 1 handled gracefully.

14.6 Pitfalls

  • RS ASN leakage via AGGREGATOR / next-hop rewrite on IPv6: AGGREGATOR may carry the RS's ASN even when AS-path is clean (I1 check must also inspect AGGREGATOR/AS4_AGGREGATOR); MP_REACH_NLRI next-hop differs from IPv4 NEXT_HOP (transparency test must cover both AFIs).
  • Fuzz corpus staleness: seeded corpus not expanded → libFuzzer coverage plateaus; add cargo fuzz cmin step in CI to minimize + deduplicate corpus.
  • Soak memory leak via retained SimEvent queue: completed events not dropped → heap grows linearly; VecDeque::pop_front after dispatch; verify with --features leak-check build flag.
  • Stuck BGP FSM after fault injection: PortDown cancels ConnectRetry but session remains in Connect → verify transition to Idle within one timer cycle; soak checks this.
  • Flap damping hides convergence / determinism break in soak: aggressive flap rate damps all prefixes, RIB appears empty (assert distinguishes damped vs. legitimately absent); HashMap iteration order affects same-tick event ordering (use BTreeMap or sort by (tick, seq), P8).

14.7 Performance Concerns

  • RFC 7947 conformance tests are micro-scale (5-10 members); run in < 100 ms each; no batching needed.
  • Fuzz targets must parse in < 1 us per input (no allocation in Frame::parse hot path, stack buffer for short frames); BGP UPDATE parser NLRI iteration must be O(n_prefixes) not O(n^2), malformed length short-circuits without scanning full buffer.
  • Soak: 1M ticks x 100 members; event queue churn is the bottleneck; BinaryHeap<SimEvent> with batched drain; target < 10 s wall-clock. Memory accounting samples ixp_metrics.memory_rss every 1 000 ticks; alert if slope > threshold.

14.8 Edge Cases

  • BGP UPDATE with zero-length NLRI field: valid; parser must return empty prefix list, not error. AS-path length 0 (ORIGIN only): valid for directly-connected originators; RS must not add its own ASN in this case.
  • RPKI ROA with max-length = 0: treat as exact-match only; no covering-prefix validation.
  • Soak member joins with same ASN as departed member (ASN reuse): session re-establishment must not inherit stale RIB entries from prior member.
  • Fuzz input with valid TOML but semantic contradiction (member references undefined port): scenario DSL must return Err, not panic. Frame with src_mac = broadcast (FF:FF:FF:FF:FF:FF): reject at ingress, log, do not learn into MAC table.
  • Soak tick budget exhausted with events still queued: drain remaining events, mark soak as TruncatedRun; do not silently pass memory assertions.
  • RPKI validation when ROA store is empty: all prefixes are unknown; policy applies unknown treatment (accept by default); log warning.

Tracing Strategy

  • Span per SimEvent dispatch: {event_kind, sim_time, seq}.
  • Child spans: BGP UPDATE parse, RIB update, MAC table operation, filter evaluation.
  • Sampling: 100 % for fault events (PortDown, SessionDown, MaxPrefixExceeded); configurable rate for Frame events (default 1:1000).
  • Trace IDs stable within a scenario run; tied to scenario name + run seed for reproducibility.
  • Output: JSON-lines to stderr (or file via --trace-output); OpenTelemetry-compatible field names.

Structured Logging

  • Format: JSON-lines; fields: ts_sim_ns, ts_wall_rfc3339, level, crate, event, member, prefix, port, msg.
  • Levels: ERROR (invariant violations, panics prevented), WARN (policy drops, mac moves, flap damping), INFO (session state changes, scenario milestones), DEBUG (per-frame, per-UPDATE).

Compatibility & Versioning

Scope of Guarantees

Applies to: scenario DSL files (.ixp.toml), RIB snapshot JSON, metric output format, CLI flags, and the public Rust API surface of ixp-core and ixp-scenario.

Does NOT apply to: internal crate APIs (ixp-fabric, ixp-peering, ixp-routeserver, ixp-policy, ixp-sim internals); these are semver-internal.

Semantic-Versioning Policy

Version Increment Trigger
MAJOR (X.0.0) Breaking change to scenario DSL schema; removal of CLI flag; incompatible RIB snapshot format; removal of ixp-core public type
MINOR (0.Y.0) New scenario DSL field (backward-compatible default); new CLI flag; new metric label; new ixp-core public type or function
PATCH (0.0.Z) Bug fix; conformance fix with no observable output change; doc update

No MAJOR increments during Phase 1–14 development unless a fundamental type rename is unavoidable. Public API surfaces are locked at Phase 1 completion for ixp-core types.

Scenario DSL (.ixp.toml) Compatibility

  • Schema version declared as schema_version = 1 in every scenario file.
  • All new fields in MINOR releases carry defaults; old scenarios parse without modification.
  • Removed fields in MAJOR releases: parse with deprecation warning for one MINOR cycle before hard error.
  • Scenario DSL EBNF versioned in ixp-scenario/schema/v1.ebnf; v2 EBNF ships in MAJOR release alongside shim that rewrites v1 to v2 on load.

RIB Snapshot JSON Compatibility

  • Schema: { "schema_version": 1, "members": [ { "asn": ..., "loc_rib": [ { "prefix": ..., "as_path": [...], "next_hop": ..., "communities": [...] } ] } ] }.
  • Field additions: MINOR; field removals: MAJOR with one-cycle deprecation warning.
  • as_path is Vec<u32> (ASN list); prefix is CIDR string; next_hop is dotted-quad or IPv6 string.
  • Regression fixtures pin schema_version; CI fails on unexpected schema change.

Migration Guarantees

  • v1 to v2 scenario DSL: ixp-cli migrate --from 1 --to 2 <file> rewrites in-place; dry-run with --dry-run.
  • RIB snapshot v1 to v2: ixp-cli snapshot migrate command; lossless for all fields present in v1.
  • No in-place state migration required (sim is stateless between runs); all migration is file-level.

Deprecation Policy

  • Deprecation notice in CHANGELOG.md and as #[deprecated] attribute on Rust items.
  • Minimum deprecation window: one MINOR release cycle.
  • Deprecated items emit WARN-level log on use during the deprecation window.
  • Hard removal only at next MAJOR version boundary.

Rolling-Upgrade Guarantee

  • No rolling-upgrade concern for batch simulation tool (single-process, single-run).
  • For CI pipelines using pinned binary: old binary + new scenario files triggers compatibility shim if schema_version mismatch detected; explicit error if shim cannot handle the delta.
  • Artifact stores (RIB snapshots, event logs) remain readable by tools one MAJOR version older; no guarantee beyond one MAJOR boundary.

  • Random PortDown events during steady-state traffic; assert RIB consistency after each.

  • All randomness seeds threaded through VirtualClock + SimEvent queue.

  • parking_lot Mutex/RwLock throughout; no std::sync::Mutex (no poisoning overhead).
  • Lock contention profiling: mutrace on Linux; report contention percentage per lock site.
  • Critical path (event dispatch loop): no locks held across event boundaries.
  • MacTable owned per-broadcast-domain inside a single-threaded sim tick; no lock needed in sim core.
  • RS rib_per_member: RwLock<HashMap<MemberId, LocRib>>; reads dominate; write only on UPDATE receipt.

Cache Analysis

  • perf stat -e L1-dcache-load-misses on MAC-table benchmark; target: <5% miss rate for working-set ≤ 1K MACs.

  • Prefix-list stored as sorted Vec<Prefix> for binary-search locality; not BTreeMap.
  • RIB per-member: Vec<RsRoute> sorted by prefix for iteration; not nested HashMap.
  • Hot structs annotated with #[repr(C)] and pad to cache-line boundaries where measured to matter.

Scalability Analysis

Dominant Scaling Pressure

Primary: RS per-member Loc-RIB size — O(N × P) where N = member count and P = unique prefixes. At N=200, P=500K, naive full-copy RIBs are infeasible; mitigation is policy-filtered shared Arc<BgpRoute> with per-member filter bitmaps.

Secondary: bilateral session mesh grows O(N²); the O(N) route-server model is the structural mitigation (P6).

Tertiary: unknown-unicast flood events grow O(N) per frame until MAC is learned; storm control bounds aggregate flood rate (Phase 11).

  • MAC table memory is dominated by hash map overhead, not entry size; FxHashMap chosen for lower overhead.

Coordination Overhead

  • Single-threaded deterministic sim core (ixp-sim event loop): no inter-thread coordination; eliminates synchronization overhead.
  • Parallelism at scenario batch level only (multiple independent scenarios in parallel processes).
  • ixp-metrics collector runs in a separate thread reading from a lock-free ring buffer written by the sim core; no blocking of sim loop.
  • RS best-path recompute: per-member, independent; rayon parallel iterator applicable if N > 100 and wall-clock latency matters; Phase 12 decision point.
  • No shared mutable state between members during a single sim tick; member-local data accessed only by sim core.

Vertical vs Horizontal Scaling

  • Vertical: increase heap size; RSS budget set via --max-rss CLI flag; sim aborts with structured error if exceeded.
  • Horizontal: not applicable to a single deterministic simulation; applies only to batch scenario execution (run M scenarios on M cores via process pool).
  • Sharding: RS RIB partitioned by address family (IPv4/IPv6) into separate LocRib shards; independent best-path per shard; no cross-shard coordination.

Scheduler / Storage Growth

  • VirtualClock advances monotonically; no wall-clock dependency; no GC pauses.
  • Event log (for replay): append-only file; grows O(E) where E = total events; bounded by --max-events scenario parameter.
  • Metrics time-series: circular buffer of fixed depth (configurable, default 10K samples); no unbounded growth.
  • MAC aging: timer fires O(M) per aging interval; at 64K entries aging every 300 s simulated, cost is dominated by hash iteration — acceptable and bounded.
  • IRR as-set graph: loaded once at startup; held in read-only memory; O(|as-set graph|) fixed cost; no runtime growth.

Scaling Regression Tests

  • Phase 12 includes a parameterized benchmark: N ∈ {10, 50, 100, 200}; assert convergence time grows sub-linearly with RS, super-linearly with bilateral mesh.
  • Memory growth test: join 200 members sequentially; assert RSS growth is monotone-bounded and ≤ 2 GB at completion.
  • Event throughput test: 1M frames injected; assert wall-clock ≤ 2 s; assert no event queue depth spike > 10K.
  • Session-count vs convergence-time curve plotted and stored in profiles/scaling/; regression if curve shape changes.

Mental Models & First Principles

The compressed insights an expert in IXP/BGP simulation holds. Each predicts a bug class. Every cited § resolves to a real heading.

MM1. A discrete-event simulator is a clock driven by a priority queue, not a loop over wall-time. Time advances to the next scheduled event; nothing happens "between" events. Predicts: deterministic, reproducible ordering from a fixed seed. Bug without it: polling or wall-clock sleeps introduce nondeterminism that breaks regression replay (P8). Applied: Phase 0–1 (event loop), ADR-05/ADR-06, §4.1 (event throughput).

MM2. Determinism is a property of total event order, and a tie-break makes it total. Two events at the same virtual time must order by a deterministic secondary key (time, seq). Predicts: identical output for identical seed+scenario. Bug without it: heap ties resolve by insertion-order luck → divergent runs flagged as determinism violations (§4.2). Applied: ADR-06 (Reverse min-heap), ADR-26 (seeded RNG), §4.1 (determinism).

MM3. A route server is the star that collapses a quadratic mesh. A bilateral full mesh is O(N²/2) sessions; an RS gives every member one O(N) session while preserving per-member policy via separate Loc-RIB views. Predicts: the N=1000 memory/convergence inflection. Bug without it: sharing one RIB across members leaks routes that policy should have hidden. Applied: Phase 6 (RS), §4.1 (session counts), §4.3 (scaling).

MM4. BGP path selection is a deterministic tie-break ladder, not a metric minimization. LOCAL_PREF → AS_PATH length → origin → MED → eBGP>iBGP → … applied in fixed order. Predicts: which route wins and why. Bug without it: treating selection as "lowest cost" produces wrong best-paths and route oscillation. Applied: Phase 4–5 (decision process), §8 (domain), I-invariants.

MM5. The RIB is three stages, not one table. Adj-RIB-In (received) → Loc-RIB (selected) → Adj-RIB-Out (advertised, post-export-policy). Predicts: where a filter applies and what a peer actually sees. Bug without it: filtering only at Loc-RIB leaks routes a peer should never receive. Applied: §8 (RIB model), Phase 5–7, §4.1 (RIB entries).

MM6. A withdrawal is as important as an announcement. Convergence is reached only when withdrawals have fully propagated; a lost withdrawal is a black hole. Predicts: PortDown→withdraw→reconverge timing. Bug without it: tracking only announcements leaves stale routes after a member leaves. Applied: Phase 9–10 (convergence/fault), §4.1 (fault recovery), MM4.

MM7. RPKI origin validation answers one question: is this (prefix, origin-AS) authorized? A ROA maps a prefix + maxLength to an authorized origin; the verdict is Valid / Invalid / NotFound. Predicts: route-origin-validation filtering behaviour. Bug without it: ignoring maxLength accepts more-specific hijacks under a valid ROA. Applied: Phase 7 (RPKI), ADR-11, §8.

MM8. The L2 fabric is a shared broadcast domain with learned, aging MAC state. Frames flood until a MAC is learned; entries age out; the table is bounded per domain. Predicts: MAC-table overflow and storm behaviour. Bug without it: unbounded MAC learning or never aging → table overflow and incorrect forwarding. Applied: Phase 2–3 (fabric), §4.1 (MAC table), §11.

MM9. Filtering is layered and order-dependent: prefix-list, AS-path, max-prefix, RPKI, IRR. Each filter can reject; max-prefix is a circuit breaker that tears the session. Predicts: which member's bad announcement is contained where. Bug without it: applying max-prefix after import wastes memory the limit was meant to bound. Applied: Phase 7 (policy), §4.1 (max-prefix breach), MM5.

MM10. Simulated time and wall-clock time are different currencies. Throughput is "events per wall-second"; latency targets are "simulated seconds to converge." Predicts: why a 1-hour simulation runs in ≤ 600 s wall-clock. Bug without it: conflating the two makes performance and correctness budgets incomparable. Applied: ADR-07 (VirtualClock), §4.1 (sim vs wall-clock targets), MM1.

Back-of-Envelope Capacity Model

Numbers an expert computes before designing, each derived from §4.1.

  • C1 — Bilateral session count (N=1000). N(N−1)/2 = 1000×999/2 = 499 500 sessions (§4.1); the O(N²) blow-up that motivates the route server (MM3) and the 16 GB full-bilateral RSS budget.
  • C2 — RS session count (N=1000). N = 1000 multilateral sessions — a 500× reduction vs C1, the core scaling argument for an RS (§4.3).
  • C3 — RS RIB size. N × prefixes_per_member = 1000 × 15 000 (10k IPv4 + 5k IPv6) = 15 M route entries per full view; the ≤ 50 M route×member ceiling (§4.1) requires prefix interning (≤ 3× amplification, §4.1).
  • C4 — Peak RSS, multilateral. ≤ 4 GB for N=1000 (§4.1): 15 M interned prefixes + per-member Loc-RIB + MAC table + event heap — interning is what keeps this under 4 GB rather than 16 GB (C1 regime).
  • C5 — Event-loop throughput. ≥ 1 M events/s (§4.1) at ≤ 200 ns p50 dispatch ⇒ a 1-hour simulation with ~Hz-scale per-session timers (≈ 3 × N) processes its heap well within the ≤ 600 s wall-clock budget (MM10).
  • C6 — Convergence (N=1000, RS). ≤ 30 s simulated time (§4.1) for all members to receive best-paths; bounded by UPDATE processing (≤ 5 µs each) × routes propagated, not by wall-clock.
  • C7 — MAC table bound. ≤ 10 000 entries/broadcast domain (§4.1) = one MAC per member port; grows with members, not with prefix count (MM8) — decoupling that bounds L2 memory.
  • C8 — Event-heap working set. ~3 timers × 1000 sessions + aging events ≈ ~3 000–10 000 live events; with the active RIB slice it fits the ≤ 8 MB L3 hot-path budget (§4.1).
  • C9 — RPKI table load. 600 K ROA entries in ≤ 200 ms (§4.1) ⇒ ≥ 3 M ROA/s parse+index at scenario start; a one-time hermetic cost, not on the hot path (ADR-11).
  • C10 — IRR as-set expansion. Transitive closure over 50 K ASNs in ≤ 1 s (§4.1) via BFS — precomputed and cached so policy checks are O(1) set lookups (ADR-12).
  • C11 — Trace volume. A 1-hour N=1000 run emits ≤ 500 MB NDJSON (§4.1); one event per line keeps it grep/jq-streamable rather than requiring a database (ADR-09).
  • C12 — FD budget. ≤ 32 FDs (§4.1): scenario file + report + log only — no sockets, because BGP is modeled as internal PDUs (ADR-10), a direct consequence of being a simulator not a router.

Alternative Architectures (Roads Not Taken)

Alt-A — Real-time emulator over a network namespace / container fabric.

each member = container running a real BGP daemon <--veth--> linux bridge (the "fabric")

Wins when: you need behavioural fidelity to real daemon bugs, kernel forwarding, and real timing. Embodied by: GNS3, Containerlab, Kathará. Rejected because: real time and real sockets destroy determinism (MM1–MM2) and reproducible regression; this project's value is replayable, assertable scenarios.

Alt-B — Analytical / steady-state model (no event simulation).

topology + policies --> solve for converged RIB state directly (fixed-point), no event timeline

Wins when: you only care about the final converged state, not the transient (route-leak reachability analysis). Embodied by: Batfish-style configuration analysis. Rejected because: convergence dynamics, withdrawal propagation, and fault timing (MM6) are core teaching goals that a steady-state solver hides.

Alt-C — Parallel/distributed discrete-event simulation (PDES).

partition members across worker threads; synchronize via conservative/optimistic time windows (Time Warp)

Wins when: a single core cannot sustain the event rate for very large N (millions of nodes). Embodied by: ROSS, ns-3 MPI. Rejected because: PDES synchronization reintroduces ordering complexity and threatens determinism (MM2) at the N≤1000 scale this targets, where a single core suffices (§4.1).

Alt-D — Packet-level simulation (model every frame/packet).

generate individual packets; simulate queues, serialization delay, drops per link

Wins when: you study congestion, queueing, and microburst behaviour at the data plane. Embodied by: ns-3 packet mode, OMNeT++/INET. Rejected because: the focus is the control plane (BGP/RIB/policy) and L2 reachability, not data-plane queueing; packet-level detail would explode event counts beyond the ≥ 1 M events/s budget without serving the goal.

Glossary

Alphabetical. Each term is implementation-relevant and operationally precise.

Term Definition
Adj-RIB Per-session routing table (Adj-RIB-In / Adj-RIB-Out) held by a BGP speaker. In ixp-peering, each bilateral session has its own Adj-RIB; the route server maintains per-member Loc-RIBs serving the same role.
ARP (Address Resolution Protocol) RFC 826 protocol mapping IP addresses to MAC addresses on a shared L2 segment. On the peering LAN, ARP requests flood to all member ports; ixp-fabric models this flooding path, and ixp-traffic resolves dst MAC via simulated ARP.
AS-path Sequence of ASNs a BGP route has traversed. Under RFC 7947, the route server must not prepend its own ASN, so the path visible to a receiving member is identical to the path the originator sent (invariant I1).
AS-set An IRR object enumerating the ASNs (and nested AS-sets) that a member is authorised to originate. ixp-policy expands an as-set recursively to derive the set of valid origin ASNs for IRR filtering.
Bilateral peering A direct BGP session between two member ASes. Session count scales O(N²) with member count. Modelled in ixp-peering; compare multilateral peering.
BGP community A 32-bit tag (u32,u32) attached to a BGP route. ixp-policy uses communities for selective announcement via the route server: announce-to-peer and do-not-announce-to-peer semantics (Phase 7).
BGP FSM The five-state finite state machine (Idle → Connect → OpenSent → OpenConfirm → Established) governing a BGP session. Timers: ConnectRetry, Hold, Keepalive. Modelled as SessionState in ixp-peering (Phase 3).
Bogon An IP prefix that is not legitimately routable on the public Internet (RFC 1918, documentation prefixes, unallocated space). ixp-policy's bogon filter drops announcements of such prefixes.
Broadcast domain The set of ports that receive a broadcast or unknown-unicast frame. At an IXP the peering LAN is a single broadcast domain; modelled as PeeringLan with all member ports in scope.
LACP Link Aggregation Control Protocol. A mechanism for bundling multiple physical ports into one logical link. ixp-fabric models LACP-like aggregation groups; traffic hashes across member ports of a LAG (Phase 9).
Loc-RIB Local RIB; a BGP speaker's post-import, post-best-path routing table. The route server maintains one Loc-RIB per member (rib_per_member in RouteServer) so each member receives a distinct policy-filtered view (I8).
MAC aging Automatic expiry of learned MAC-table entries after a configured inactivity interval. Prevents stale unicast forwarding state. ixp-fabric enforces aging; a port-down event triggers immediate flush (I3, I9).
MAC learning Process by which an L2 switch records the source MAC of an ingress frame and maps it to the ingress port. Drives unicast forwarding. Keyed per broadcast domain in MacTable.
MANRS Mutually Agreed Norms for Routing Security. A framework of routing-hygiene actions (prefix filtering, AS-path filtering, RPKI). ixp-policy's filtering primitives are aligned with MANRS recommendations.
Max-prefix A per-session limit on the number of prefixes a peer may announce. Breach triggers session teardown (invariant I4), modelled in ixp-policy (Phase 6).
Multilateral peering BGP sessions formed via a route server; each member holds exactly one session to the RS rather than N-1 bilateral sessions. Session count scales O(N). Modelled in ixp-routeserver; principle P6 quantifies the difference.
Next-hop preservation RFC 7947 requirement that the route server not rewrite the BGP NEXT_HOP attribute; the receiving member sees the originating member's LAN address as next-hop (invariant I10).
NOTIFICATION BGP error message that terminates a session immediately. ixp-peering emits a NOTIFICATION on policy violations (e.g., max-prefix breach) and transitions the FSM to Idle.
Peering LAN The shared Ethernet segment at an IXP to which all members connect. Provides L2 connectivity and the medium over which BGP control-plane sessions are established. Modelled as PeeringLan.
Peering policy A member's stance on which other members it will exchange routes with. Three modes: Open (peer with all), Selective (whitelist), Restrictive (blacklist/default-deny). Encoded in PeeringPolicy.
Prefix-list An ordered set of prefix/length-range match clauses used in import or export filters. ixp-policy evaluates prefix-lists before accepting or propagating a BGP route.
ROA (Route Origin Authorisation) A cryptographically signed object in the RPKI that states which AS is authorised to originate a given prefix. ixp-policy checks ROAs to classify routes as valid, invalid, or unknown.
Route leak Accidental re-advertisement of a route beyond its intended scope, potentially providing unintended transit. ixp-policy and invariant I6 prevent the IXP from becoming a transit AS; I4 limits leak volume; P9 makes leaks observable.
Route server (RS) A BGP speaker at the IXP that maintains multilateral peering sessions and distributes routes among members without inserting its own ASN. Specified in RFC 7947. Implemented in ixp-routeserver.
RPKI Resource Public Key Infrastructure. A hierarchical PKI that binds IP prefixes to ASNs via ROAs. ixp-policy performs origin validation against an RPKI dataset; invalid routes are dropped when rpki_mode is enforced (I5).
Settlement-free peering Exchange of traffic between two networks without monetary compensation, based on mutual benefit. The default semantic at an IXP; principle P1 prohibits transit-style re-advertisement.
Split-horizon Rule preventing a switch port from forwarding a frame back out the port it arrived on. Applied in ixp-fabric to prevent loops on the peering LAN.
Storm control Rate-limiting mechanism that suppresses broadcast/unknown-unicast floods when they exceed a threshold. ixp-fabric applies storm control to bound flooding overhead (Phase 11).
Traffic matrix An N×N table of inter-member traffic rates (Mbps). TrafficMatrix drives flow generation in ixp-traffic; only member pairs with a valid route and peering relationship generate traffic (I6).
Transit Carrying traffic for a third party between two external ASes. An IXP provides peering, not transit; routes received from one member must not be used to provide transit to another member by default (P1, I6).
Unknown unicast A unicast frame whose destination MAC is not in the MAC table. The fabric floods such frames to all ports in the broadcast domain (I2). Containment is critical for scalability (Phase 11).
VirtualClock The monotonic simulation clock in ixp-sim. Advances by dispatching SimEvent records in (time, seq) order. Provides determinism (P8).
