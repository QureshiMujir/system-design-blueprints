Decisions (§9) · 28 ADRs

ADR-01

Implementation language

Chosen

Rust (stable, 2021 edition)

Rejected

Go, C++, TypeScript/Node

When the rejected choice is right

Go: when team productivity and fast iteration outweigh tail-latency; C++: when embedding in an existing C++ editor client or plugin; TypeScript/Node: when the entire stack is browser-first and server load is light

Why: Memory safety without GC; zero-cost async; ownership prevents data races in multi-actor room design; crate ecosystem for async + CRDT

ADR-02

Build system

Chosen

Cargo workspace (single Cargo.toml at root, 12 member crates)

Rejected

Bazel, Buck2, Meson

When the rejected choice is right

Bazel/Buck2: when the repo is polyglot (Rust + Go + Proto + Python) and hermetic caching across languages saves CI hours; Meson: when cross-compiling to embedded targets with unusual toolchains

Why: Cargo is the Rust standard; workspace sharing of deps + lockfile; no cross-language build needed

ADR-03

Async runtime

Chosen

Tokio (multi-thread scheduler)

Rejected

async-std, smol, single-threaded

When the rejected choice is right

smol: when binary size and startup time matter most (embedded or serverless cold-start); single-threaded: when deterministic replay and reproducible fuzz are required; async-std: when std-compatible API surface matters more than performance

Why: Tokio dominates ecosystem; tokio::spawn per-room actor; tokio::select! for fan-out; best profiling/tracing integration

ADR-04

WebSocket transport

Chosen

tokio-tungstenite

Rejected

axum ws, warp, actix-web

When the rejected choice is right

axum ws: when the server also exposes REST/HTTP APIs and a unified router reduces boilerplate; actix-web: when the team already uses the Actix ecosystem and wants integrated actor dispatch

Why: Thin wrapper over tungstenite; direct integration with Tokio; minimal abstraction over framing; easy to test with mock streams

ADR-05

Serialization (wire + log)

Chosen

bincode (v2, little-endian, fixed-width integers)

Rejected

MessagePack (rmp-serde), JSON, Cap'n Proto, FlatBuffers

When the rejected choice is right

Cap'n Proto/FlatBuffers: when cross-language client SDKs are required and schema-first codegen reduces integration bugs; MessagePack: when partial schema evolution across major versions is needed without rewriting serialization; JSON: when human-readability of the op log is more important than parse speed

Why: Deterministic byte layout required for CRC integrity; bincode v2 explicit config; fast; no schema file needed for evolution at this stage

ADR-06

Serialization (config + meta.json)

Chosen

serde_json + serde derive

Rejected

TOML, YAML, RON

When the rejected choice is right

TOML: when end-users edit config files directly and the TOML format is more familiar; YAML: when config is generated by Kubernetes/Helm and YAML anchors are needed for DRY config; RON: when Rust-native type serialization and comments in config are valued over portability

Why: meta.json is human-readable ops metadata; serde_json universally supported; TOML for any user-facing config files

ADR-07

Sequence CRDT algorithm

Chosen

YATA (origin_left + origin_right, Lamport tie-break)

Rejected

RGA (tombstone linked list), OT (transform matrix), Logoot/LSEQ (position identifiers)

When the rejected choice is right

RGA: when integration with Automerge's existing RGA-based encoding is required; OT: when the server must arbitrate content (e.g., for undo-redo parity with Google Docs semantics) and a linear server history is acceptable; Logoot/LSEQ: when position identifiers need to survive arbitrary tree restructuring without a server authority

Why: YATA: O(concurrent-inserts) integration; simpler than RGA linked list; better convergence proof than Logoot under adversarial concurrency; matches Yjs reference impl

ADR-08

LWW register for FS metadata

Chosen

Custom LWWReg<T> with (Lamport, SiteId) tie-break

Rejected

CRDT-lib, automerge Map

When the rejected choice is right

automerge Map: when the workspace metadata schema is complex enough to justify map-level CRDT semantics (e.g., nested settings with concurrent-field-edit resolution); CRDT-lib: when the project's dependency audit prefers a reviewed external CRDT library over custom code

Why: Trivial to implement correctly; no external dep for this pattern; tie-break rule is explicit in spec

ADR-09

Op-log persistence

Chosen

Append-only flat file, length-prefixed + CRC32 per entry

Rejected

SQLite, RocksDB, sled, redb

When the rejected choice is right

SQLite: when the op log needs ad-hoc queries (e.g., fetch ops by time range or by client) and the WAL overhead is acceptable; RocksDB: when the op log exceeds hundreds of GB and LSM-tree compaction is preferable to the snapshot-based compaction model; sled: when the Rust-native transactional API is valued and the team wants MVCC without an external process

Why: Crash-only model (P11); no transaction overhead; sequential write maximizes throughput; recovery = scan to last valid CRC; no WAL-on-WAL

ADR-10

Snapshot format

Chosen

bincode blob + separate .crc sidecar

Rejected

Embedded CRC in same file, SQLite blob

When the rejected choice is right

Embedded CRC: when the filesystem does not support atomic rename (e.g., some NFS mounts) and a single-file format with internal CRC is safer; SQLite blob: when snapshots need indexing by multiple criteria (doc_id, seq, timestamp) and ad-hoc partial loads are common

Why: Atomic rename guarantees: .snap written fully before .crc appears; presence of .crc = valid snap; simple recovery logic

ADR-11

In-memory op index

Chosen

Per-site BTreeMap<u64, usize> (seq -> arena slot)

Rejected

HashMap (no ordering), B+ tree lib

When the rejected choice is right

HashMap: when the op rate is so high that O(1) random access dominates over range scans; B+ tree lib: when the op index must be persisted to disk for fast cold-start without a full log scan

Why: BTreeMap gives O(log n) range scan for delta computation; ordered iteration for sequential replay; std only

ADR-12

Position skip-list

Chosen

skiplist crate or hand-rolled for PosList

Rejected

Vec<usize> (O(n) insert), BTreeSet

When the rejected choice is right

Vec: when document size is bounded at a few thousand items and simpler code outweighs the asymptotic cost; BTreeSet: when a stable std-only structure is preferred and document mutation rate is low

Why: O(log n) insert/delete/rank for item ordering; needed for offset<->OpId mapping at scale

ADR-13

Inter-task message passing

Chosen

tokio::sync::mpsc (bounded) for all actor channels

Rejected

crossbeam-channel, flume, unbounded channels

When the rejected choice is right

crossbeam-channel: when the producer runs outside a Tokio runtime (e.g., a blocking thread driving a C FFI) and non-async sends are needed; unbounded: when the producer and consumer are co-located with provable max-message guarantees and eliminating send-side blocking is worth the memory trade

Why: Bounded enforces backpressure (P7); tokio native; back-pressure on full queue is first-class

ADR-14

Concurrency model for session room

Chosen

Single tokio::task per workspace room; all doc mutation serialized through it

Rejected

Lock-per-document, STM, actor framework (Actix)

When the rejected choice is right

Lock-per-document: when a workspace has many independent documents and parallel doc integration would reduce per-doc latency; Actix: when the team prefers a full actor framework with typed mailboxes and supervision trees over raw Tokio tasks

Why: Eliminates data races on Document without locks; fan-out is simple iteration over send_queues; single task = natural ordering authority (P3)

ADR-15

Logging

Chosen

tracing crate with tracing-subscriber (JSON formatter in prod, pretty in dev)

Rejected

log crate, slog

When the rejected choice is right

log crate: when the binary must be embedded in a host that already provides a log backend and the overhead of span context is not justified; slog: when deeply nested key-value structured logging without span context is the primary requirement and the team prefers its composability model

Why: tracing provides structured spans; integrates with tokio-console; span per op for latency attribution

ADR-16

Metrics

Chosen

metrics crate facade + metrics-exporter-prometheus

Rejected

Prometheus client (official), StatsD, OpenTelemetry SDK

When the rejected choice is right

Prometheus client (official): when Prometheus-specific features (exemplars, native histograms) are needed and the facade abstraction is not worth the indirection; OpenTelemetry SDK: when metrics must be exported to multiple backends simultaneously (Prometheus + Datadog + OTLP) without code changes; StatsD: when UDP push is preferred over HTTP pull in a high-ephemeral-container environment

Why: Facade decouples instrumentation from exporter; Prometheus pull model suits single-server deployment; minimal dep surface

ADR-17

Distributed tracing

Chosen

opentelemetry + tracing-opentelemetry bridge

Rejected

Jaeger client direct, Zipkin

When the rejected choice is right

Jaeger client direct: when the deployment uses Jaeger exclusively and removing OTLP indirection reduces latency; Zipkin: when the existing observability stack is Zipkin-based and Zipkin's HTTP reporter has lower operational overhead

Why: OTLP export to any collector; bridge reuses existing tracing spans; no code duplication

ADR-18

Property-based / fuzz testing

Chosen

proptest for convergence properties; cargo-fuzz (libFuzzer) for op-log reader and frame codec

Rejected

quickcheck, honggfuzz, AFL

When the rejected choice is right

quickcheck: when test logic maps naturally to Arbitrary impls and shrinking quality is secondary; honggfuzz: when coverage-guided fuzzing with hardware performance counters is available and honggfuzz's branch coverage metrics provide better fuzzer guidance than libFuzzer

Why: proptest shrinking is superior for CRDT counterexample minimization; cargo-fuzz is standard Rust fuzz harness; both run in CI

ADR-19

Unit + integration testing

Chosen

cargo test with tokio::test for async; rstest for parameterized cases

Rejected

nextest only, custom harness

When the rejected choice is right

nextest: when test suite runtime dominates CI wall-time and nextest's parallel-by-default execution and test retries are the primary concern; custom harness: when tests must interoperate with a non-Rust test orchestrator or produce JUnit XML with custom metadata

Why: Standard toolchain; rstest reduces boilerplate for phase matrix tests; nextest used for parallel execution in CI

ADR-20

CI/CD

Chosen

GitHub Actions; matrix: (stable, nightly) x (linux-x86_64, linux-aarch64)

Rejected

GitLab CI, CircleCI, Buildkite

When the rejected choice is right

GitLab CI: when the source repo is self-hosted on GitLab and access to GitLab Runners with custom hardware (e.g., bare-metal M-series Apple for aarch64 native) is available; Buildkite: when CI must run on on-premise GPU or FPGA nodes inaccessible to cloud CI

Why: GitHub Actions native for most open-source Rust projects; nightly needed for cargo-fuzz; matrix catches arch-specific endianness bugs

ADR-21

Benchmarking

Chosen

criterion (statistical, HTML report) + custom wall-clock harness via lcide-cli bench

Rejected

Iai (instruction count), hyperfine

When the rejected choice is right

Iai: when benchmarking on noisy VMs where wall-clock variance obscures regressions and instruction-count stability is needed; hyperfine: when benchmarking CLI startup time or shell-command round-trips rather than library microbenchmarks

Why: Criterion gives p50/p99/stddev; lcide-cli bench replays scripted edit sequences for end-to-end latency; both run on dedicated CI runner

ADR-22

Language server protocol

Chosen

lsp-types crate for LSP structs; tokio::process to spawn LS

Rejected

tower-lsp server (not needed — we are the client), raw JSON

When the rejected choice is right

tower-lsp client: when the application also serves as an LSP server (not just a client) and the tower service abstraction is reused; raw JSON: when schema flexibility is needed to forward unknown LSP extensions without deserialization errors

Why: lsp-types is the standard serde-derived LSP type library; process spawn via Tokio is sufficient; no extra RPC framework needed

ADR-23

Dependency policy

Chosen

Minimal; each crate's Cargo.toml lists only direct deps; no * version pins; cargo-deny enforces license + duplicate detection

Rejected

Vendoring, cargo-vendor

When the rejected choice is right

cargo-vendor: when the build environment has no internet access (air-gapped CI or corporate proxy) and vendored sources are the only option; vendoring with patch: when a critical upstream crate has an unfixed bug and a local fork is needed before an upstream release

Why: cargo-deny in CI catches GPL contamination and duplicate semver versions; lockfile committed for reproducibility

ADR-24

Reproducible builds

Chosen

Committed Cargo.lock; pinned toolchain via rust-toolchain.toml; Docker image built from same toolchain

Rejected

Nix flake, Guix

When the rejected choice is right

Nix flake: when the project must produce identical binaries across macOS, Linux, and Windows from the same source and Nix's hermetic closures are the only way to achieve bitwise reproducibility; Guix: when the team requires freedom-respecting toolchain provenance auditing

Why: rust-toolchain.toml + locked Cargo.lock sufficient for deterministic binary given same OS/glibc; Nix adds complexity without benefit for this project stage

ADR-25

Containerization

Chosen

Single Dockerfile (multi-stage: rust:1.xx-slim build -> debian:slim runtime); published to GHCR

Rejected

Docker Hub, custom registry, Nix container

When the rejected choice is right

Docker Hub: when existing internal tooling (e.g., Kubernetes cluster) authenticates to Docker Hub and re-platforming is not justified; Nix container: when the deployment requires SBOM-traceable container layers with reproducible hashes and Nix's layer builder is already in use

Why: Multi-stage minimizes image size; GHCR free for open-source; no proprietary registry dependency

ADR-26

Licensing

Chosen

MIT OR Apache-2.0 (dual)

Rejected

GPL-2.0, BSL, proprietary

When the rejected choice is right

GPL-2.0: when the project is a derivative of GPL-licensed code and license compatibility requires GPL; BSL: when the project is a commercial product that needs a time-delayed open-source conversion and non-compete protections during the proprietary window; proprietary: when IP protection and revenue from source access are primary goals

Why: Standard Rust ecosystem dual-license; compatible with all major dependency licenses; cargo-deny enforces no GPL deps

ADR-27

CRDT op ordering authority

Chosen

Server room actor assigns order_clock: Lamport for fan-out sequencing; CRDT integration order determined by (Lamport, SiteId) from op metadata, not server assignment

Rejected

Pure peer-to-peer (no server order), OT server transformation

When the rejected choice is right

Pure peer-to-peer: when the system must operate fully offline with no server (e.g., local-first desktop editor) and all ordering authority derives from clients; OT server transformation: when the application requires server-arbitrated undo semantics (e.g., last-write-wins on a shared whiteboard object) that CRDTs cannot provide

Why: Server clock improves reproducibility of integration order across clients; CRDT correctness is independent of it (P3); simplifies replay and debugging

ADR-28

Auth mechanism

Chosen

Token (opaque bearer, 256-bit random) on Hello handshake; server validates against workspace ACL store

Rejected

JWT (adds key management), mTLS (complex for browser clients), OAuth (out of scope)

When the rejected choice is right

JWT: when tokens must carry verifiable claims (expiry, role, workspace_id) without a server-side lookup on every connection and the key management overhead is acceptable; mTLS: when the deployment is within a zero-trust network requiring mutual certificate authentication at every hop; OAuth: when the application integrates with an existing enterprise identity provider (Okta, Azure AD) and SSO is a hard requirement

Why: Simple; stateless token validation; sufficient for Phase 13 scope; JWT/OAuth upgrade path left open via handshake version field

Alternative Architectures (Roads Not Taken)

Four fundamentally different designs for the same system, not parameter tweaks.

Alt-A — Operational Transform, server-authoritative (Google Docs / ShareDB / Live Share).

clients --ops--> [ central transform server ] --transformed ops--> clients
                  (canonical op log, transforms concurrent edits)

Wins when: a central always-on server is a given, clients are thin, and the document model is simple JSON/text. Embodied by: Google Docs, ShareDB, VS Code Live Share. Rejected because: transform composition is O(n²) in concurrent ops and historically error-prone for rich/tree structures (the difficulty that sank Google Wave); CRDTs (MM1) move correctness into the data type and enable offline edits (MM9).

Alt-B — Pessimistic region locking (collaborative DB style).

client --lock(region)--> server --grant--> client edits --release--> next waiter

Wins when: edits are coarse-grained (whole-cell, whole-section) and strong single-writer-per-region consistency is required, e.g. structured form editing. Embodied by: locking document stores, some wiki engines. Rejected because: concurrent character-level editing of the same line is the core requirement; locking serializes typing and adds RTT-bound latency to every keystroke (violates §4.1 fan-out targets).

Alt-C — RGA + columnar log (Automerge model).

each replica: append-only change log (columnar) --sync(SV)--> merge, full history retained

Wins when: time-travel, branching, and blame over the whole edit history are first-class needs (legal docs, research notebooks). Embodied by: Automerge. Rejected because: retaining full history conflicts with the IDE op-log growth rate (Capacity C5) and the need for tombstone GC and compaction (MM4, Phase 10); YATA linked items integrate more cheaply for the live-typing path.

Alt-D — Peer-to-peer mesh, no central server (WebRTC).

client A <==WebRTC==> client B
   \\==WebRTC==>  client C  (every pair connected; CRDT sync over data channels)

Wins when: there is no trusted server, censorship resistance or zero server cost matters, and sessions are small and ephemeral. Embodied by: y-webrtc, Conclave. Rejected because: a hosted IDE needs durable history, server-side LSP processes, auth/ACL (Phase 13), and NAT traversal/relay fallback erodes the "no server" benefit; the single room actor (MM5) gives a clean durability and ordering point.
