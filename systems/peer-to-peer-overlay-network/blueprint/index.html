360 — Peer-to-Peer Overlay Network

Goal: Implement, from scratch in Rust, a structured peer-to-peer overlay / Distributed Hash Table (DHT) with key-based routing (KBR) over a 256-bit key space, modelled primarily on Kademlia (XOR distance metric, k-buckets, parallel-α iterative lookup, the BitTorrent-DHT / IPFS lineage), with Chord (ring + finger tables, consistent hashing) and Pastry studied as compared alternatives. The system provides lookup(key) / find_node (iterative, α-parallel, O(log N) hops), DHT store / get with k-replication near the key, join (bootstrap + self-lookup to populate routing tables), graceful and implicit leave, plus maintenance under churn (bucket/table refresh, value republish/expiry, repair), and Sybil / Eclipse resistance (ID-generation cost, bucket diversity, node-ID = hash of IP||key) with a deferred NAT-traversal layer. Crates: p2p-core / routing / rpc / lookup / storage / bootstrap / churn / security / nat / runtime / cabi / bench / conformance. It models the Kademlia + Chord + Pastry family — not the BitTorrent wire protocol (#80, which uses a DHT like this one), not a gossip/unstructured overlay (#72), not onion routing (#222), not a blockchain gossip net. Correctness is validated against a simulated network oracle (deterministic discrete-event harness with N nodes in-process), differential tests vs the Kademlia/Chord papers' invariants, and churn/Sybil/eclipse fault injection; performance against the O(log N) hop bound and measured hop/latency distributions.

1. Goal

1.1 Engineering Definition

  • Build a from-scratch structured P2P overlay / DHT: a 256-bit key space (SHA-256 node + key IDs) → an XOR-metric routing substrate (Kademlia k-buckets) → α-parallel iterative key-based routing (find_node/find_value) → a replicated key-value store (store/get, k replicas) → bootstrap/join + churn maintenance + Sybil/eclipse defenses, over a from-scratch UDP/TCP RPC transport.
  • Primary locked design = Kademlia (XOR metric, k-buckets, parallel lookup, churn tolerance). Chord (ring + finger tables + successor list) and Pastry (prefix routing + leaf set) are implemented as compared alternatives behind a RoutingScheme trait, not as the production default.
  • Identifiers: NodeId/Key = 256-bit ([u8;32]), produced by #88 SHA-256; the metric is XOR (d(a,b)=a⊕b) for Kademlia, ring-successor distance for Chord, numeric-prefix for Pastry.
  • Concurrency model: single logical node, many concurrent in-flight RPCs; the overlay is fully peer-to-peer (no central coordinator on the data path; a bootstrap node is only an entry point).

1.2 System Boundaries

  • In scope: key space + distance metrics; Kademlia k-buckets (LRU, liveness-preferring eviction) + Chord finger tables/successor lists + Pastry leaf set/routing table; iterative α-parallel lookup (find_node, find_value) with convergence; DHT store/get with k-replication, republish, and expiry; join (bootstrap + self-lookup), graceful + implicit leave; churn maintenance (bucket refresh, table refresh, stabilization for Chord, value repair); Sybil/eclipse defenses (ID-gen cost, bucket diversity, ID=hash(IP||r)); a reliable-enough UDP RPC (PING/STORE/FIND_NODE/FIND_VALUE) + TCP fallback for large values; deterministic simulation harness (N in-process nodes); the O(log N) hop-bound analysis + measured distributions.
  • Out of scope (non-goals): the BitTorrent file-transfer wire protocol → #80 (a consumer of a DHT like this; we are the overlay substrate, not the swarm/piece protocol); unstructured gossip/flooding overlays → #72 (compared, §8.13, not built as the primary); membership/anti-entropy gossip detail → #197 SWIM (we borrow liveness intuition); onion/privacy routing → #222 Tor (a different overlay); Merkle anti-entropy of stored values → #71 (cited for value integrity; we ship hash-checked values, full Merkle sync deferred); a blockchain P2P gossip net (different problem). NAT traversal beyond a stub (hole-punching state machine + relay fallback) → PhaseDeferred("FINAL_BLUEPRINT §22.2"); DHT-level confidentiality/onion layering → PhaseDeferred("FINAL_BLUEPRINT §39"); persistent on-disk value store beyond an LSM-stub → PhaseDeferred("FINAL_BLUEPRINT §39").

1.3 Deployment Model

  • A Rust library + a per-node daemon (p2pd) bound to a UDP socket (+ TCP for large values), one process per overlay node; many processes across many hosts form the overlay. A node joins by contacting one or more bootstrap addresses (well-known entry points), then self-lookups to populate its routing table. A CLI p2pctl for: lookup tracing, routing-table inspection, store/get, bucket/finger dumps, and a single-process simulation mode that spins up N virtual nodes over an in-memory transport for deterministic testing.

1.4 Target Users

  • Engineers building or operating DHT-backed systems (content addressing, peer discovery, decentralized storage) who must understand how XOR routing, k-buckets, iterative lookup, replication, and churn actually work; learners internalizing the O(log N) routing argument, the Kademlia/Chord/Pastry tradeoffs, and Sybil/eclipse threats.
  • Downstream portfolio: #80 BitTorrent (uses the DHT for trackerless peer discovery — the canonical consumer), content-addressed stores (IPFS-style), service discovery (compare #359), and any system needing decentralized key→value/peer location.

1.9 Recommended Language & Rationale

  • Rust. (a) The overlay parses untrusted peer messages on every RPC → memory safety without GC is decisive (a malformed FIND_NODE from a hostile peer must never cause UB); (b) async UDP/TCP RPC with thousands of concurrent in-flight lookups maps cleanly onto Rust's async + ownership model, and Send/Sync make the per-node concurrency (socket I/O, lookup state machines, maintenance timers) auditable; (c) reuses #88 SHA-256 (IDs), and shares transport patterns with #80 / #72; (d) no GC pauses to perturb lookup-latency tails or heartbeat timing; (e) the modern DHT lineage (libp2p-rust, rust-libp2p kad, BitTorrent DHT impls) is Rust/C — extern "C" ABI lets #80 (a swarm client) drive it.
  • Rejected: C/C++ (the historical DHT language — Vuze/libtorrent — but manual memory management on an untrusted-input parser is exactly the footgun Rust removes; ABI/build pain); Go (excellent for the networked daemon and the GC is tolerable here, but weaker for the byte-exact untrusted-parser safety story and we want the no-GC-jitter discipline shared with the rest of the portfolio); Erlang/Elixir (a superb actor/failure model for P2P — genuinely tempting — but the per-RPC parsing-safety and the #88/#80 reuse tip it to Rust); Python (orchestration/prototyping only; far too slow for the lookup data plane and unsafe for untrusted parsing at speed).

2. Why Build This

2.1 Unique Knowledge Taught

  • Key-based routing from first principles. Why a routing table holding O(log N) carefully-chosen contacts lets any node reach the node responsible for any key in O(log N) hops — the structured-overlay insight that makes a network of millions of unreliable peers behave like a single hash table.
  • The XOR metric (Kademlia's idea). Why treating IDs as points under XOR distance gives a symmetric, unidirectional metric (d(a,b)=d(b,a); exactly one node per distance at each bit) that turns routing into a binary-trie descent, makes k-buckets self-organizing, and lets a node learn about closer nodes from every message it receives (the elegance Chord lacks).
  • Consistent hashing / key ownership. Why each key is "owned" by the node(s) closest to it under the metric, why this minimizes churn-induced key movement (only O(K/N) keys move when a node joins/leaves), and the lineage to #402.
  • Iterative vs recursive routing + parallelism. Why Kademlia's iterative α-parallel lookup (the requester drives, querying α nodes at a time) trades message overhead for robustness and tail-latency control, versus Chord's classic recursive option; and how α hides the latency of a slow/dead hop.
  • Churn — the defining P2P problem. Why a structured overlay must continuously repair its routing tables and re-replicate its data as nodes join and leave at high rates, and why "correct lookup under churn" (not under a static membership) is the real bar.
  • Sybil and eclipse attacks. Why cheap identities (Sybil) and adversarial neighbor placement (eclipse) are the fundamental security limits of an open overlay, and why they are mitigated, not solved (ID-generation cost, bucket diversity, disjoint lookups).

2.2 Why It Matters

  • The DHT is one of the most influential distributed data structures: it powers the BitTorrent Mainline DHT (trackerless torrents, tens of millions of nodes), IPFS/libp2p content routing, Kad/eMule, S/Kademlia-secured overlays, and the conceptual ancestor of many decentralized systems. The O(log N) key-based-routing result (Chord, Kademlia, Pastry, Tapestry, all 2001) is a foundational systems idea. Understanding the DHT is understanding how to build a global, self-organizing, server-less lookup service that survives massive churn and partial adversaries.

2.3 Engineering Muscles

  • Network protocol design (UDP RPC, framing, timeout/retry, request correlation); concurrent state-machine engineering (many in-flight α-parallel lookups); data-structure invariants under concurrency + churn (k-buckets, finger tables); probabilistic reasoning about routing/replication; eventual-consistency + repair design for a churning store; adversarial/security thinking (Sybil/eclipse threat modeling); deterministic discrete-event simulation for testing a distributed system in one process; parsing untrusted input safely.

2.4 Production Concepts Exercised

  • Structured key-based routing + consistent hashing; replication + repair under churn; self-organizing routing tables (LRU/liveness eviction, refresh); iterative parallel lookup with convergence; failure detection via RPC timeouts; Sybil/eclipse mitigation; NAT traversal (deferred core); deterministic simulation testing of a distributed protocol; wire-protocol versioning for an open network.

2.6 Calibration Value

  • You leave able to read the Kademlia, Chord, and Pastry papers and a real DHT implementation (rust-libp2p kad, BitTorrent DHT, IPFS) and explain every routing-table choice, lookup parallelism decision, replication/repair policy, and Sybil/eclipse mitigation — and to reason about why a DHT lookup is slow, why data went missing under churn, or how an adversary could eclipse a target.

2.7 The churn wall — the defining constraint

  • #402 (consistent hashing) assumes a known, slowly-changing member set; this overlay assumes continuous, high-rate, adversarial-tolerant membership change (churn) — the scarce resource is fresh, live routing information.
  • Consequence 1: the routing table is never fully correct. At any instant some contacts are stale/dead; lookup must succeed anyway by parallelism (α) + the metric's redundancy (k-buckets hold k backups per distance).
  • Consequence 2: replication is mandatory, not optional. A single copy of a value disappears the moment its owner leaves; data survives only if stored on k nodes and re-replicated as the closest-k set shifts under churn.
  • Consequence 3: maintenance is continuous, not one-shot. Buckets refresh, values republish, Chord stabilizes — forever; the steady-state bandwidth of just staying correct is a first-class cost.
  • Consequence 4: the metric must tolerate staleness. XOR's "learn closer nodes from every message" + iterative lookup's "ask the closest known, repeat" degrade gracefully as entries rot; a brittle exact-pointer scheme (naive Chord without a successor list) loses correctness under churn.
  • Consequence 5: the adversary is part of the membership. Sybil/eclipse are churn weaponized — an attacker joins many cheap identities or positions them around a target; defenses are diversity + cost + redundancy, never a single gate.
  • This single fact reorganizes every decision (replication factor k, refresh intervals, α, bucket eviction policy, successor-list length) and is the sharpest contrast with the static-membership world of #402.

2.8 What Mastery Looks Like

  • Derive the O(log N) hop bound from the metric, not from memory — explain why each XOR hop fixes ≥1 high-order bit and why only ~log₂N prefix levels are populated; built in Phase 3 (§15, the find_node convergence) and proven against the oracle (§25).
  • Choose a replication factor from an availability target — turn "≥99 % at 50 % simultaneous loss" into 1−(1−p)^k and read off k=20; built in Phase 4 (§16 store/replication) and Phase 6 (§18 republish/repair).
  • Engineer correctness under churn, not under static membership — keep lookups ≥99 % correct while nodes join/leave at ≥50 %/h via redundancy (k-buckets) + parallelism (α) + continuous maintenance; built in Phase 6 (§18) and gated in Phase 13 (§25).
  • Reason about a structured overlay's whole design space — state when Kademlia, Chord, Pastry, CAN, or an unstructured flood each wins, and what each trades; built across Phase 7 (§19 Chord), Phase 8 (§20 Pastry) and the Comparative/Alternatives back-matter (§35, §38).
  • Mitigate Sybil/eclipse and state the residual risk honestly — apply ID-cost + bucket diversity + disjoint lookups, then quantify capture probability vs adversary fraction f and admit f<1 is unreachable (Douceur); built in Phase 9 (§21) and measured in Phase 13 (§25).
  • Parse untrusted peer input safely — frame/length/version/ID validation so no hostile datagram causes UB; built in Phase 1 (§13 RPC) and fuzzed in Phase 13 (§25).
  • Build a deterministic distributed-systems test harness — a seeded in-process N-node simulator with a brute-force oracle that makes every churn/lookup bug reproducible; built in Phase 0 (§12) and the backbone of Phase 13 (§25).
  • Tune the latency/robustness/bandwidth knobs from numbers — pick α and timeouts against a measured success-vs-churn curve rather than folklore; built in Phase 12 (§24, §4.5).

3.2 Box Narratives

  • p2p facade. Entry points: join(bootstrap_addrs), lookup(key) -> k closest NodeInfo, store(key, value), get(key) -> value, leave(). Validates IDs/args, selects the configured RoutingScheme (Kademlia default), and drives the lookup/storage subsystems. Thin orchestration; no protocol logic of its own.
  • p2p-core. The vocabulary every crate speaks. NodeId/Key = 256-bit ([u8;32]) from #88 SHA-256. The Metric/Distance abstraction: XOR (a⊕b, Kademlia), ring-distance ((b−a) mod 2^256, Chord), shared-prefix length (Pastry). NodeInfo{id, addr, last_seen, rtt}. The RoutingScheme trait abstracts "given a target, return the next contacts to query and ingest observed nodes" so Kademlia/Chord/Pastry are interchangeable. Defines all error types.
  • routing. The routing table(s). Kademlia k-buckets: one bucket per distance bit (256 buckets, sparsely populated), each holding up to k=20 NodeInfo, ordered by last-seen, evicted LRU with a liveness preference (a live old contact beats a fresh unknown — Kademlia's churn-resistance trick). Chord: a finger[i] table (finger[i] = successor(n + 2^i)) + a successor list (r successors for fault tolerance) + predecessor. Pastry: a routing table (rows by shared-prefix length) + a leaf set (numerically closest nodes) + neighborhood set. Maintains itself from every RPC observed (Kademlia) or via stabilization (Chord).
  • lookup. The iterative, α-parallel key-based routing engine. Maintains a shortlist of the k closest known nodes to the target; queries α (=3) of them in parallel with FIND_NODE/FIND_VALUE; each response returns closer nodes; repeats until no closer node is found (convergence) → returns the k closest (the responsible set). For find_value, terminates early when a node returns the value. A recursive variant (the queried node forwards) is implemented for comparison. Hides slow/dead hops behind α-parallelism.
  • storage. The DHT key-value store. store(key,value) runs a find_node(key) then STOREs to the k closest nodes (k-replication, k=20). get(key) runs find_value(key). Values carry a TTL and are republished periodically (the original publisher refreshes; replica holders also republish to keep the closest-k set populated as it shifts). Expired values are evicted. Each value is hash-checked on receipt (integrity, #71 lineage); a value-id may be hash(value) (content-addressed) or an arbitrary key (mutable, last-writer-wins with a sequence/version).
  • rpc. The data plane. Four core RPCs (Kademlia): PING, STORE, FIND_NODE, FIND_VALUE, each a request with a random transaction id correlating the response. UDP datagrams (one RPC per datagram where it fits); TCP fallback for large values exceeding the datagram budget. Timeout + bounded retry per RPC (a missed response → the contact is suspected, then dropped — the failure detector). Parallel α dispatch: issue α requests concurrently, collect the first responses. Every inbound message is parsed defensively (length-checked, ID = valid 32 bytes, version-checked) — the trust boundary.
  • bootstrap. join: contact one or more configured bootstrap nodes (well-known entry points), insert them, then perform a self-lookup (find_node(my_id)) — which, by querying progressively closer nodes, populates the node's k-buckets with its neighborhood; followed by refreshing each bucket farther than the closest neighbor. Handles cold-start (the very first node = the seed) and multiple bootstrap addresses for resilience.
  • churn. Continuous maintenance. Bucket refresh: any bucket not touched in an hour gets a find_node for a random ID in its range (keeps it fresh). Routing-table refresh generally. Value republish/expiry: republish every hour, expire after 24h (Kademlia defaults). Value repair / re-replication: when the closest-k set to a key changes (a closer node joined, or a replica left), re-STORE to restore k replicas. Chord stabilization: periodic stabilize (verify successor, notify), fix_fingers, check_predecessor. Leave: graceful (hand off keys, notify neighbors) or implicit (detected by RPC timeout → eviction + repair).
  • security. Sybil/eclipse mitigations. ID generation cost: a node's ID must equal hash(IP || nonce) satisfying a (static or PoW) constraint, raising the cost of minting many identities and binding ID to network position. Eclipse resistance: bucket diversity (limit how many contacts in one bucket share an IP prefix), disjoint parallel lookups (S/Kademlia — run d independent lookups via disjoint paths, intersect), and preferring long-lived contacts. Routing-table poisoning checks (validate that a returned contact is plausibly closer; rate-limit unsolicited adds). Rate limiting per source. Mitigations, explicitly not guarantees (Threat Model).
  • nat. NAT classification (full-cone/restricted/symmetric heuristics via a STUN-like probe) + traversal: a hole-punching handshake (coordinated simultaneous send) and a relay fallback (a third reachable node forwards). Core hole-punch state machine is in scope; the full ICE-like negotiation + a production relay (TURN) are PhaseDeferred("§22.2").
  • runtime. Node lifecycle (New → Joining → Active → {Leaving → Left | Failed}), the async event loop (socket read → dispatch to handler → routing-table update → reply; plus timers for maintenance/lookup timeouts), config (k, α, ID space, intervals), and the simulation transport (an in-memory message bus letting N virtual nodes run in one process with deterministic, controllable message scheduling/loss/delay). Ships p2pd (daemon) + p2pctl (CLI).
  • bench / conformance. Hop-count, lookup-latency, and lookup-success-rate harness (vs the O(log N) bound and under churn); the simulation oracle (an authoritative, slow, centralized computation of "the true k closest nodes to key X given the current membership" — the trusted answer every lookup is checked against); Kademlia/Chord invariant differential tests; churn/Sybil/eclipse fault injection.

3.3 Boundaries

  • Trust boundary: the network — every inbound RPC is from a potentially malicious peer. Messages are framed, length-checked, version-checked, and IDs validated (32 bytes) before use; a peer may be slow, dead, lying about routing (poisoning), or a Sybil. The overlay is open (anyone can join) → all peers are untrusted; defenses are diversity + cost + redundancy, never authentication of a known set.
  • Concurrency boundary: per node — the socket I/O task(s), the set of in-flight lookup state machines (each tracking its shortlist + α outstanding RPCs), the maintenance timers (refresh/republish/stabilize), and the request/response correlation table. No shared mutable routing table without a lock discipline (§3.5).
  • Persistence boundary: the value store (in-memory + a WAL-stub now; persistent LSM deferred). Routing tables are soft state — reconstructed by re-bootstrapping after a restart (a node that restarts re-joins; its old contacts may still know it).
  • Coordination boundary: there is none on the data path — fully peer-to-peer. The only semi-central element is the bootstrap node (an entry point), used once at join and never again; multiple bootstrap addresses remove the single point of failure.

3.4 Data-flow walk — one store(key, value) then get(key) (Kademlia)

  1. store(key,value): the node runs lookup::find_node(key) — an iterative α-parallel walk (§3.5) that returns the k closest live nodes to key (I3/I7).
  2. It sends STORE(key, value, ttl) to each of those k nodes (k-replication, I9); each recipient validates the value (hash check, I10) and stores it with an expiry.
  3. The stored value now lives on the k nodes numerically/XOR-closest to key; the closest-k set is the responsible set.
  4. Later, get(key): the node (possibly a different node) runs find_value(key) — same α-parallel walk, but a queried node holding the value returns it immediately (early termination, I8).
  5. The walk reaches the responsible set in O(log N) hops (I1); the value is returned; the requester optionally caches it at the last node that didn't have it (Kademlia's get-side caching, accelerating popular keys, §16).
  6. Throughout, churn maintenance (P6) re-replicated the value as the closest-k set shifted (a new closer node joined → it gets a replica on the next republish); the value survives the original publisher leaving as long as ≥1 replica + republish persists (I9).
  7. Every RPC the node sent/received updated its k-buckets (Kademlia learns from all traffic, I5); LookupTrace recorded hops, parallelism, RTT, and convergence.

3.5 Per-node concurrency model + the iterative lookup state machine

  • Socket I/O task(s): read datagrams, parse defensively, correlate responses to in-flight requests by transaction id, dispatch inbound requests to handlers, send replies. Never blocks on application logic.
  • In-flight lookups: each lookup(key) is an async state machine holding: a shortlist (k closest known nodes to the target, sorted by distance), a set of queried nodes, and ≤ α outstanding RPCs. On each response: ingest returned contacts into the shortlist (and the routing table, I5), mark the responder queried, and issue new RPCs to the α closest un-queried shortlist nodes. Termination: when the k closest nodes in the shortlist have all been queried and no response yielded anything closer (convergence, I7). A per-RPC timeout bounds a dead hop; α-parallelism means one dead node never stalls the lookup.
  • Maintenance timers: bucket-refresh, value-republish, expiry-sweep, and (Chord) stabilization fire on intervals; they run as low-priority tasks issuing their own lookups/STOREs.
  • Routing table is shared state, guarded by a lock (or sharded per-bucket lock); updates are frequent (every RPC) but cheap; lookups read it. Lock ordering: routing-table lock is a leaf (never held across an .await on the network) to avoid stalls (principle 9).
  • Failure detection is implicit: an RPC timeout marks a contact unresponsive; repeated timeouts → eviction. No separate heartbeat thread for k-buckets (traffic is the liveness signal); Chord adds an explicit check_predecessor ping.
  • This separation (I/O ≠ lookup logic ≠ maintenance ≠ table updates) is what lets thousands of concurrent lookups and continuous maintenance coexist without head-of-line blocking.

3.6 Why XOR — the metric that organizes everything

  • Symmetry: d(a,b) = a⊕b = b⊕a → if A is close to B, B is close to A → a node learns useful contacts from everyone who queries it, not just from nodes it queries (Chord's clockwise ring is asymmetric — this is Kademlia's headline advantage).
  • Unidirectionality: for any point x and distance Δ, exactly one y satisfies d(x,y)=Δ → no two routing entries at the same distance compete; the routing table is a clean binary trie (bucket i = nodes sharing a (256−i−1)-bit prefix with us, differing at bit i).
  • The lookup as trie descent: querying a node in bucket i returns nodes that share more prefix bits with the target → each hop fixes ≥1 more high-order bit → O(log N) hops to the target (I1). Worked in §8.5.
  • Self-organizing tables: because every message reveals a contact at a known distance, k-buckets fill and refresh from ordinary traffic; explicit maintenance (P6) only covers buckets that traffic doesn't exercise.

4.1 Worked hop-count (the O(log N) argument, Kademlia XOR)

  • Model: N nodes, IDs uniform in 2^m space (m=256). A lookup for target t maintains the closest known node; each query to a node in the target's "direction" returns nodes sharing ≥1 more high-order prefix bit with t.
  • Claim: expected hops ≈ log₂ N. Intuition: each hop at least halves the XOR distance to the target (fixes the highest differing bit), and there are ≈ log₂ N "populated" prefix levels between a random node and the target (below that, the target's neighborhood is sparse).
  • Numeric example: N = 1,000,000 ≈ 2^20. Expected hops ≈ 20 (not 20 of 256 — only the top ~20 bits matter because below that the space is empty of nodes). With k-buckets holding the k closest at each level, the last few hops land directly in the target's neighborhood.
  • With parallelism α=3: the number of hops is unchanged, but per-hop latency is min over α queries → a slow/dead node among the α doesn't add a round-trip. Expected lookup latency ≈ log₂N × RTT_effective, where RTT_effective < RTT because the fastest of α responses advances the walk.
  • Tail: w.h.p. hops ≤ log₂N + O(1); the constant covers the sparse final approach. Under stale routing entries (churn), a few extra hops occur as dead contacts are skipped (the α backups absorb them).
  • Implication: the §4 targets are stated against log₂N; the conformance harness measures the actual hop distribution in the simulation oracle and asserts it tracks log₂N (I1), never a hardcoded constant.

4.2 Worked replication / availability (why k=20)

  • A value is stored on the k closest nodes to its key. It is lost only if all k simultaneously leave before any republish.
  • Model: each node independently alive with probability p over a republish interval. Probability all k replicas dead = (1−p)^k. Availability = 1 − (1−p)^k.
  • Numeric: p = 0.5 (a brutal 50 % of nodes vanish before republish), k = 20 → loss probability 0.5^20 ≈ 9.5×10^−7 → availability ≈ 99.9999 %. At k = 8, loss ≈ 0.004 → 99.6 %. At k = 3, loss 0.125 → only 87.5 %.
  • Why k=20 (not 3): churn is severe and correlated (a network partition kills many at once); k=20 buys ~6 nines against 50 % independent loss and is Kademlia's empirically-chosen value (matches the bucket size, so the closest bucket is the replica set). Cost: 20× storage per value — acceptable for small DHT values (peer lists, content hashes), the design's intended payload.
  • Repair restores k: between republishes, churn drops some replicas below k; the republish (P6) re-STOREs to the current closest-k, restoring the count. The availability above assumes republish faster than the churn timescale (§4.4).
  • Implication: the §4 "≥99 % at 50 % simultaneous failure" target is met by k=20 with margin; the harness injects correlated failure (kill 50 % at once) and asserts get still succeeds (I9).

4.3 Worked routing-table size (Kademlia vs Chord)

  • Kademlia: 256 buckets, but only ≈ log₂N are non-empty (a random node has neighbors only at the populated prefix levels); each holds ≤ k. So routing state ≈ k · log₂N. N=10^6, k=20 → ≈ 20×20 = 400 contacts (~tens of KB). The buckets near our own ID are full; far buckets hold few/one node (the space is sparse far away, dense near us — the trie is unbalanced toward us).
  • Chord: m=256 fingers, but again only ≈ log₂N distinct (finger[i] for small i all point to the immediate successor) → effective ≈ log₂N fingers + an r-entry successor list (r ≈ log N for fault tolerance) → ≈ 2·log₂N ≈ 40 contacts. Smaller table than Kademlia, but less redundancy (one finger per level vs k per bucket) → more fragile under churn → needs aggressive stabilization.
  • Pastry: routing table ≈ (2^b − 1)·log_{2^b}N rows (b≈4 → 15 per row) + a leaf set (2^b entries) + neighborhood set → larger constant, proximity-aware.
  • Tradeoff: Kademlia's k·log N buys churn resilience (k backups per level) at more state; Chord's log N is leaner but brittle; this motivates choosing Kademlia as the locked default (§9 ADR-3) and the churn target (§4).

4.4 Worked churn / maintenance budget (steady-state cost of staying correct)

  • Let per-node lifetime be exponential with median T_med (e.g. 30 min — measured BitTorrent-DHT churn is brutal). Churn rate ≈ 1/T_med.
  • Bucket refresh: Kademlia refreshes a bucket only if untouched for t_refresh (1 h). Ordinary lookup/store traffic refreshes most buckets for free; only idle buckets cost a find_node each → O(log N) refresh lookups/hour worst case (a few hundred small RPCs — negligible bandwidth).
  • Value republish: every value re-STOREd every t_republish (1 h) to its closest-k → cost ∝ (values held × k × value-size) / hour. For a node holding V values: V·k small messages/hour. This is the dominant maintenance cost for a value-heavy node.
  • Detection lag vs republish: a value is at risk only in the window between a replica's death and the next republish. With republish=1h and k=20, the loss math (§4.2) holds; shortening republish raises availability at more bandwidth — the tunable tradeoff.
  • Chord stabilization: stabilize+fix_fingers+check_predecessor every ~t_stab (seconds) → more frequent than Kademlia refresh because Chord's single-pointer fingers rot faster → higher steady-state cost, the price of the leaner table.
  • Implication: §4's "bounded maintenance bandwidth" target is O(log N) refresh + O(V·k) republish per node — measured in the churn harness (P13) and asserted to not grow super-linearly with N (I-class steady-state behavior).

4.5 Worked α tradeoff (parallelism vs message overhead)

  • α = concurrent outstanding RPCs per lookup. Higher α → more robust to slow/dead hops + lower tail latency; but more total messages (some wasted on nodes a smaller α would have skipped).
  • Latency: with α queries per hop, the walk advances on the fastest response → effective per-hop RTT ≈ the α-th-order statistic minimum → hides a straggler. α=3 hides up to 2 slow/dead nodes per hop.
  • Messages: total RPCs ≈ α × hops × (some convergence factor). α=3 vs α=1: ~3× messages for a large robustness/latency win; α=10 buys little extra robustness for 3× more messages → diminishing returns.
  • Kademlia's choice: α=3 is the empirical sweet spot (the paper's value); the cost model / config exposes it. Under heavy churn, a higher α compensates for more dead contacts (the harness sweeps α vs churn, §4 target).
  • Implication: §4 sets α=3 default; success-rate-under-churn is measured across α to validate the choice, never assumed.

6. Design Principles

  1. Structured routing: O(log N) hops, not flooding. Every lookup converges via a routing table of O(log N) chosen contacts; the metric guarantees each hop makes progress. Violation: falling back to broadcast/flooding (the #72 unstructured model) → O(N) traffic, no scaling — defeats the entire point of a DHT.
  2. The XOR metric is the organizing law (Kademlia default). Distance = a⊕b; symmetric + unidirectional → self-organizing k-buckets that learn from all traffic. Violation: an asymmetric/brittle metric (naive Chord pointers) → tables can't self-heal from observed traffic → fragile under churn.
  3. Routing tables are soft state; correctness comes from redundancy, not exactness. k-buckets hold k backups per distance; lookups parallelize over α. Violation: a single exact pointer per level (Chord without a successor list) → one dead contact breaks routing → lost lookups under churn.
  4. Replicate every value k-fold and repair continuously. A value lives on the k closest nodes and is re-replicated as that set shifts. Violation: a single copy → data vanishes the instant its owner leaves → no durability in an open, churning network.
  5. Lookups are iterative and α-parallel (the requester drives). The originator queries α nodes at a time and steers the walk; a slow/dead hop is hidden by parallelism. Violation: purely recursive routing with no parallelism → one slow node stalls the lookup; no tail-latency control; harder to detect lies.
  6. All peers are untrusted; every inbound byte is validated. Frames are length/version-checked, IDs are exactly 32 bytes, returned contacts are sanity-checked. Violation: trusting peer input → a malicious FIND_NODE poisons the table, crashes the parser, or eclipses the node.
  7. Sybil/eclipse are mitigated by cost + diversity + redundancy, never eliminated. ID=hash(IP||nonce), bucket IP-diversity, disjoint lookups. Violation: assuming an honest majority or a single defense → a cheap Sybil swarm or a positioned eclipse owns the target (Douceur's result).
  8. Bounded resource usage everywhere. Per-lookup state ≤ shortlist size; routing ≤ k·log N; in-flight RPCs ≤ α; values rate-limited per source. Violation: unbounded shortlists/connections/stores → memory exhaustion DoS from one peer.
  9. Never hold the routing-table lock across the network. The table lock is a leaf (taken to read/update, released before any .await). Violation: holding it across an RPC → a slow peer freezes all of a node's lookups + maintenance.
  10. Failure detection is implicit in RPC timeouts; never hang. A missed response → suspect → evict; lookups time out per-hop. Violation: waiting unboundedly for a dead contact → a single dead node hangs a lookup forever.
  11. Determinism in simulation: a seed + a message schedule reproduce any run. The in-process N-node harness is fully deterministic. Violation: nondeterministic simulation → a churn/lookup bug is unreproducible → undebuggable distributed behavior.
  12. Observe every hop and every byte moved. Emit per-lookup hop count, parallelism, RTTs, convergence; per-store replica count; per-bucket fill. Violation: opaque lookups → can't diagnose a slow lookup, a missing value, or an eclipse in progress.
  13. Stable, versioned wire protocol on an open network. Frames carry a version; incompatible peers are ignored, never trusted-and-misparsed. Violation: silent protocol drift across a global, never-fully-upgradable population → corruption and crashes.
  14. Correctness anchored to a centralized oracle in simulation. The harness computes the true k-closest set for any key from full membership; every lookup is checked against it. Violation: no oracle → "did the lookup find the right nodes?" is unanswerable → distributed bugs ship.
  15. Delegate hashing to #88; the overlay owns routing/storage, not crypto primitives. IDs = SHA-256(payload). Violation: a bespoke hash → non-uniform IDs (clustering, hot spots) or weak collision resistance (ID forgery).

8. Domain Model — Key Space, Metric, Routing, Lookup, Storage, Protocol

8.1 Key space & identifiers

  • The key space is [0, 2^256); both node IDs and keys are [u8;32] produced by #88 SHA-256 (uniform, collision-resistant). A node and a value-key live in the same space → "the node closest to a key owns it."
  • Collision probability is negligible (birthday bound on 2^256 is astronomically large) → IDs are treated as unique.
  • A node's ID may be random hash(random) (open mode) or hash(IP||nonce) constrained (secure mode, I13) to raise Sybil cost.

8.2 Distance metrics (the three schemes)

Scheme Distance d(a,b) Routing primitive Properties
Kademlia (default) a ⊕ b (XOR, big-endian magnitude) k-buckets per distance bit symmetric, unidirectional, self-organizing
Chord (b − a) mod 2^256 (clockwise ring) finger table + successor list asymmetric (directed ring)
Pastry shared-prefix length, then numeric leaf set + prefix routing table proximity-aware
  • All three implement the Metric/RoutingScheme trait (§11.1) so the lookup engine + harness are scheme-agnostic; Kademlia is the locked production default (ADR-3).
  • XOR metric axioms (I2): d(x,x)=0; d(x,y)=d(y,x) (symmetry); d(x,y) > 0 for x≠y; unidirectionality — for any x,Δ exactly one y with d(x,y)=Δ (the property that makes routing tables clean).

8.3 Kademlia k-buckets (the routing table)

  • 256 buckets indexed by the most-significant differing bit between our ID and a contact's ID. Bucket i holds nodes whose distance to us is in [2^i, 2^(i+1)) — i.e. sharing the top 255−i bits with us, differing at bit i.
  • Each bucket holds ≤ k=20 NodeInfo, ordered most-recently-seen last (I4).
  • Insert/eviction (the churn trick): on seeing a node, if its bucket has space → add at tail (most-recent). If full → ping the least-recently-seen contact; if it responds → keep it (move to tail), discard the new node; if it doesn't → evict it, add the new node. → long-lived nodes are preferred (they statistically stay longer — the heavy-tailed lifetime observation), which makes the table churn-resistant.
  • Buckets near our ID are full (the space is dense around us); far buckets hold few nodes (sparse) — the trie is unbalanced toward us, giving fine resolution near us and coarse far away (exactly what O(log N) routing needs).

8.4 Chord finger table + successor list (compared scheme)

  • successor(id) = the first node clockwise from id on the ring; a key k is owned by successor(k).
  • finger[i] = successor(n + 2^i mod 2^256) for i ∈ [0,256) → exponentially-spaced shortcuts → O(log N) routing (each hop ≥ halves the clockwise distance).
  • Successor list (r entries, r≈log N): the r nodes following n → fault tolerance (if the immediate successor dies, use the next) — without this Chord loses correctness under a single failure (the lesson of P7/principle 3).
  • Predecessor pointer: maintained by stabilize/notify.
  • Stabilization (the churn protocol, I6): periodically ask the successor for its predecessor; if it's a closer node, adopt it as the new successor; notify the successor; fix_fingers refreshes one finger per round; check_predecessor pings the predecessor.

8.5 Worked lookup — Kademlia iterative find_node (N=16, m=4 for illustration)

Our id=0000, target t=1011. Goal: the k=2 closest nodes to t.
Shortlist init = k closest in our buckets, say {1010(d=0001), 0011(d=1000)} (sorted by XOR dist to t).
Round 1 (α=2): query 1010 and 0011 in parallel.
  1010 returns {1011(d=0000!), 1001(d=0010)}  ← knows the target's neighbor
  0011 returns {1010(d=0001), 0111(d=1100)}
  Shortlist now (closest first): 1011(0000), 1010(0001), 1001(0010), ...
Round 2: query 1011, 1001 (the new α closest un-queried).
  1011 returns {1011, 1010, 1001}  ← no node closer than 1011 itself
  1001 returns {1011, 1010}
  No node closer than the current k-closest found → CONVERGED (I7).
Result = {1011, 1010} = the true 2 closest to t (verified vs oracle, I3).
Hops ≈ 2 ≈ log₂16/2 (the last hop lands in the neighborhood). Each round fixed ≥1 high bit.
  • Real run: m=256, α=3, k=20; each round the closest-known distance strictly decreases until the responsible set is reached; the responder's returned contacts also populate our buckets (I5).

8.6 Worked lookup — Chord recursive (contrast)

n=10 seeks key k=54 (ring size 64). n consults its finger table for the finger
preceding k: finger pointing to 42. Forward to 42 (recursive: 42 continues, or
iterative: 42 returns its best finger to n). 42's finger preceding 54 → 51.
Forward to 51. 51's successor = 56 = successor(54) = owner of k. Done.
Hops: 10→42→51→56 ≈ 3 ≈ log₂64/2. Each hop ≥ halved the clockwise distance to k.
  • Iterative vs recursive (principle 5): iterative (Kademlia) — the originator drives, sees every hop (good for detecting lies + parallelism); recursive (classic Chord) — each node forwards (fewer round-trips to the originator, but the originator is blind to intermediate nodes and can't parallelize easily). This system uses iterative + α-parallel as the default and implements recursive for comparison (P7).

8.7 DHT store / get + replication

  • store(key, value) = find_node(key) → STORE(key,value,ttl) to each of the k closest (I9). Value-id may be hash(value) (content-addressed, immutable) or an explicit key (mutable; carries a (seq, value) for last-writer-wins, I10).
  • get(key) = find_value(key): like find_node, but a queried node holding a non-expired copy returns the value (early termination, I8). The requester may cache the value at the closest queried node that didn't have it (get-side caching for hot keys, §16).
  • Republish (P6): the publisher re-STOREs every t_republish(1h); replica holders also republish to the current closest-k (so a newly-joined closer node receives a replica). Expiry: values dropped after t_expire(24h) unless republished (I9). Repair: detecting under-replication (a replica left) triggers re-STORE.

8.8 Wire protocol (RPC)

  • Frame: [magic(2) | version(1) | type(1) | txn_id(8) | sender_id(32) | payload | checksum(4)]. UDP datagram; TCP fallback when payload (a large value) exceeds the datagram budget (~1200 B safe MTU).
  • Types (Kademlia core): PING/PONG (liveness), STORE/STORE_ACK, FIND_NODE(→ k closest NodeInfo), FIND_VALUE(→ value | k closest). Chord adds GET_SUCCESSOR/GET_PREDECESSOR/NOTIFY/STABILIZE. Pastry adds prefix-route messages.
  • Correlation: the random txn_id matches a response to its in-flight request; an unmatched/late response is dropped (I11). Timeout + retry: no response within rpc_timeout → retry up to max_retries → declare the contact unresponsive (failure detection, I10/principle 10).
  • Validation (I11): magic/version/type checked; sender_id is exactly 32 bytes; payload lengths bounded; returned NodeInfo count ≤ k; a returned contact's claimed distance is sanity-checked (anti-poisoning, P9).
  • BitTorrent-DHT note: the deployed reference (BEP 5) uses bencoded KRPC with ping/find_node/get_peers/announce_peer + a write token (a node must echo a token from a prior get_peers to announce_peer, preventing address-spoofing stores) — our STORE adopts the token idea in secure mode (P9).

8.9 State machines

  • Node lifecycle: New → Joining(bootstrap+self-lookup) → Active → {Leaving(handoff+notify) → Left | Failed(detected by peers' timeouts)}.
  • Lookup: Init(seed shortlist) → Querying(≤α outstanding) → (ingest responses, re-issue) → {Converged(k-closest stable) | ValueFound | TimedOut(return best-so-far)} (I7).
  • Contact (in a bucket): Unknown → Inserted(seen) → {Fresh(responding) ↔ Stale(missed pings)} → Evicted(LRU/dead) (I4).
  • Stored value: Stored(ttl) → {Republished(ttl reset) | Expired(dropped) | Repaired(re-replicated)} (I9).
  • Chord successor: Guess → stabilize(verify) → {Confirmed | Updated(closer found)} (I6).

8.12 Consistency model of the value store

  • Immutable (content-addressed) values (key = hash(value)): trivially consistent — any returned copy that passes the hash check (I10) is correct; replicas can't diverge.
  • Mutable values (explicit key): last-writer-wins by a monotonically-increasing seq (or timestamp) the publisher includes; a get that sees multiple versions returns the highest seq; replicas converge as republish propagates the latest. This is eventual consistency — no global ordering, no transactions (out of scope).
  • Conflict under partition: two partitions may accept different writes to a mutable key; on heal, the higher seq wins (or, if equal, a deterministic tiebreak on value hash) → convergent, but a write can be silently lost (the inherent AP-system tradeoff; documented).
  • Read-your-writes is not guaranteed across nodes (a get from a node that hasn't yet received the republish may see stale data) → the contract is eventual convergence within ~t_republish, not linearizability.
  • #71 lineage: full replica reconciliation via Merkle-range anti-entropy (compare digests, sync only differences) is the deferred path; we ship per-value hash checks + republish-based convergence.

8.14 The Sybil & eclipse attack model (P9 framing)

  • Sybil attack (Douceur): an adversary mints many cheap identities (node IDs). With enough IDs it can populate a victim's routing table, win lookups, or censor keys. Root limit: without a trusted identity authority, this is impossible to fully prevent — only made costly.
    • Mitigations: ID = hash(IP||nonce) with a constraint (PoW / static) → minting an ID costs work + binds it to an IP (limiting IDs per address); bucket IP-prefix diversity (I14) → one /24 can't fill a bucket; rate-limit unsolicited contact additions.
  • Eclipse attack (Singh et al.): a (possibly Sybil-backed) adversary positions its nodes so they surround a victim in the routing table, controlling its view of the overlay → can censor/redirect the victim's lookups.
    • Mitigations: disjoint parallel lookups (S/Kademlia — run d independent lookups over node-disjoint paths and intersect; the adversary must control all d paths); prefer long-lived/observed contacts over freshly-advertised ones; constrained routing table (Castro) limiting how attacker-chosen IDs enter buckets; the metric's redundancy (k backups per bucket) raises the number of nodes that must be controlled.
  • Defense posture (principle 7): layered mitigation — cost + diversity + redundancy + disjoint paths. Quantified as "the adversary must control a fraction f of well-positioned IDs to eclipse a target with probability p"; the harness (P13) measures capture probability vs adversary fraction. We do not claim Sybil-proofness (the threat model states this plainly).

8.15 Bootstrap & self-lookup protocol (P5)

  • A joining node J knows ≥1 bootstrap address (a well-known long-lived entry node) + its own ID (random or constrained).
  • Step 1: J inserts the bootstrap node(s) into its buckets and PINGs to confirm liveness.
  • Step 2 (self-lookup): J runs find_node(J.id) — querying progressively closer nodes to itself. Each response populates J's buckets with nodes in its neighborhood; by the time it converges, J knows its k closest neighbors (who also now know J, I5) → J is reachable.
  • Step 3 (bucket refresh): J runs a find_node for a random ID in each bucket farther than its closest neighbor → fills the rest of the table with well-distributed contacts (so far-away lookups also route well).
  • Cold start: the first node is a seed (its bucket are empty; the overlay grows as others join via it). Multiple bootstrap addresses tolerate a dead entry point (principle: no single point of failure on join).
  • Target: a usable routing table in < 5 s (§4); the joining node is queryable as soon as self-lookup completes.

11.1 Identifiers, metric, scheme

}

12.7 Performance Concerns

  • None yet (oracle is intentionally O(N log N) — it is the slow ground truth, never on a hot path).

12.8 Edge Cases

  • distance(x,x)=0; identical IDs (treat as collision → effectively impossible, but handle); N=1; empty membership.

12.9 Failure Analysis

  • A wrong metric/bucket-index corrupts every routing decision → exhaustive bit-level tests + the oracle guard it from day one (I2/I3).

13. Phase 1 — RPC transport: UDP request/response, correlation, timeouts, α-parallel dispatch

13.1 Objectives

  • Build the data plane: a framed UDP request/response RPC with transaction-id correlation, per-RPC timeout + bounded retry, a TCP fallback for large values, parallel α dispatch, and defensive parsing of untrusted messages (I11).

13.2 Detailed Implementation Steps

  • Theory anchors: defensive untrusted-input parsing (principle 6 → I11); timeout-as-failure-detector (principle 10 → I10, ADR-11/12, SWIM intuition #197); α-parallel dispatch (principle 5, ADR-7); BEP-5 KRPC as the deployed wire reference (§8.8); bounded resources (principle 8 → I15).
  • rpc::frame + codec — the frame format (§8.8): magic/version/type/txn-id/sender-id/payload/checksum; encode/decode for Rpc/RpcResp (NodeInfo lists, values).
  • rpc::udp — bind a UDP socket; send datagrams; receive loop; map inbound to handlers.
  • rpc::correlate — a transaction table mapping txn_id → oneshot responder; drop unmatched/late responses (I11).
  • rpc::timeout — per-RPC deadline + max_retries; a timeout → P2pError::Timeout (failure-detection signal, I10).
  • rpc::parallel — call_parallel: issue α requests concurrently, collect responses as they arrive (the lookup primitive, principle 5).
  • rpc::tcp_fallback — for payloads exceeding the safe UDP MTU (~1200 B): negotiate + transfer over TCP.
  • rpc::validate — strict inbound validation: magic/version/type, sender_id length, payload bounds, NodeInfo count ≤ k (I11).

13.3 Deliverable

  • Two nodes exchange PING/PONG + FIND_NODE/Nodes over UDP, with correlation + timeout; examples ping/echo; α-parallel call returns the first responses.

13.4 Acceptance Criteria

  • Requests correlate to responses by txn_id; timeouts fire on a dead peer (I10).
  • Malformed frames are dropped without panic (I11); a fuzzer (P13) finds no crash.
  • call_parallel(α) issues α concurrent RPCs and returns as they complete.
  • Large values use the TCP fallback transparently.

13.5 Conformance Fixtures

  • badframes/truncated.json, badframes/bad_version.json, badframes/oversize_nodeinfo.json, lookup/parallel_dispatch.json.

13.6 Pitfalls

  • UDP packet loss is normal → retry/timeout must be correct or lookups stall; don't assume delivery (principle 10).
  • Datagram size: exceeding the path MTU → silent fragmentation/loss → enforce a payload budget + TCP fallback.
  • Transaction-id reuse/collision → use a large random txn_id; expire stale entries (memory, I15).
  • Parsing untrusted input without bounds → buffer over-read/panic (the security crux, I11) → validate every length.
  • A late response arriving after the lookup moved on → must be ignored, not misapplied.

13.7 Performance Concerns

  • Syscall overhead per datagram → batch recvmmsg/sendmmsg where available; reuse buffers (no per-RPC allocation).
  • TCP_NODELAY on the fallback for small control; avoid head-of-line blocking by keeping UDP the default.
  • The correlation table is hot → a fast concurrent map; bounded size (I15).

13.8 Edge Cases

  • Zero-length payload; response with no matching request; duplicate response (retry race); socket buffer full (backpressure); a peer on a different protocol version (I11).

13.9 Failure Analysis

  • A parsing bug = a remote-crash/UB vector from any peer (the highest-severity bug class here) → defensive parser + frame fuzz + ASAN/Miri (I11).
  • Lost-RPC handling wrong → lookups hang or falsely declare nodes dead → timeout/retry fixtures + the failure-detection invariant (I10).

13.10 Operational Notes

  • TableTrace/per-RPC metrics: timeouts, retries, parse drops; document the wire protocol (versioned, I11) in docs/wire-protocol.md.

14. Phase 2 — Kademlia k-buckets + routing-table maintenance

14.1 Objectives

  • Implement the Kademlia routing table: 256 k-buckets, LRU eviction preferring live-old contacts (I4), insertion from every observed node (I5), and the closest-k query that feeds lookups.

14.2 Detailed Implementation Steps

  • Theory anchors: k-buckets + LRU-prefer-live eviction (Kademlia paper, Maymounkov & Mazières 2002 → I4, ADR-13, principle 3); learn-from-all-traffic (principle 2 → I5); the heavy-tailed-lifetime justification for preferring old contacts (Stutzbach & Rejaie 2006, §8.3); leaf-lock discipline (principle 9, ADR-25).
  • routing::kbucket — a single bucket: entries (≤ k, MRU-ordered) + replacements; insert/touch/evict logic (§8.3, I4).
  • routing::kademlia_table — 256 buckets; insert(NodeInfo) routes to the right bucket by MSB-differing bit; closest(target,k) walks buckets nearest the target's distance.
  • Eviction (the churn trick, I4): on a full bucket, PING the least-recently-seen entry; keep it if it responds (discard newcomer), else evict + insert.
  • observe (I5): the RPC handlers call table.insert for the sender of every inbound message + every NodeInfo returned in responses — the self-organizing property.
  • routing::maintenance — needs_refresh (buckets idle > t_refresh); the refresh hook (a find_node for a random ID in the bucket's range — wired in P6).

14.3 Deliverable

  • A node maintains a correct k-bucket table; p2pctl table-dump shows populated buckets + fill; inserting observed nodes populates the trie correctly.

14.4 Acceptance Criteria

  • Each bucket holds ≤ k entries (I4); eviction prefers live-old over fresh-new (verified by a liveness-injection test).
  • closest(target,k) returns the k closest known nodes (vs a brute-force over the table).
  • Every observed node is offered to the table (I5); buckets near the local ID fill, far buckets stay sparse (§8.3).

14.5 Conformance Fixtures

  • routing/bucket_size_bound.json, routing/eviction_prefers_live.json, routing/closest_k.json, routing/observe_populates.json.

14.6 Pitfalls

  • Bucket index from the distance (MSB set bit), not the raw ID → off-by-one corrupts routing (the §12.6 bug, again — test).
  • Eviction that drops live long-lived nodes for churning newcomers → loses Kademlia's churn resistance (I4) — the policy is the whole point.
  • closest must merge across adjacent buckets when one bucket has < k — don't return fewer than k if more are known.
  • Inserting self or duplicates → guard.

14.7 Performance Concerns

  • insert is on every RPC → must be O(bucket) cheap; the per-bucket lock is a leaf (ADR-25, principle 9).
  • closest is on every lookup hop → a bounded scan of ~log N buckets; keep buckets cache-friendly (small ArrayVec).

14.8 Edge Cases

  • Table with < k total nodes (early overlay) → closest returns all; a single far node in an otherwise-empty bucket; the bucket containing the local ID (distance 0 — special).

14.9 Failure Analysis

  • A table bug → wrong closest → lookups don't converge or converge wrong → vs brute-force closest + the lookup oracle (I3) catch it; per-bucket assertions (I4).
  • Eviction policy regression → churn tests (P6/P13) show degraded success rate → docs/failure-analysis/lost-lookup.md.

14.10 Operational Notes

  • TableTrace: populated buckets, total contacts, evictions, refreshes; tools/table_inspect visualizes the bucket fill (the unbalanced trie).

15. Phase 3 — Iterative α-parallel lookup: find_node + convergence

15.1 Objectives

  • Implement the headline operation: iterative, α-parallel find_node that converges to the true k closest nodes to any target in O(log N) hops (I1/I3/I7) — the Phase-0-done bar (§1.11).

15.2 Detailed Implementation Steps

  • Theory anchors: iterative α-parallel lookup + the convergence/termination rule (Kademlia paper, Maymounkov & Mazières 2002 → I1/I3/I7, ADR-7, principle 5); learn-from-all into the table (principle 2 → I5); the O(log N) hop argument (§4.1, the Chord proof, Stoica et al. 2001/2003); bounded per-lookup state (principle 8 → I15).
  • lookup::shortlist — the bounded sorted set of k closest known nodes to the target + a queried-set (I15).
  • lookup::iterative — the state machine (§8.11): seed the shortlist from table.closest; issue α FIND_NODE (via rpc::call_parallel); on each response, ingest returned contacts (→ shortlist + table, I5), mark queried, re-issue to the α closest un-queried.
  • lookup::convergence — converged() (I7): the k closest shortlist nodes are all queried and the last round found nothing closer; termination on convergence or a global lookup deadline (TimedOut → best-so-far).
  • lookup::find_node — the public entry: returns the converged k closest NodeInfo.
  • lookup::recursive — the recursive variant (the queried node forwards) for the P7 comparison (§8.6).
  • Wire it: a dead/slow node among the α just times out (I10); the walk advances on the others (principle 5).

15.3 Deliverable

  • node.lookup(target) returns the k closest nodes; in SimNetwork (N nodes) it matches true_closest (I3) and the hop count tracks log₂N (I1); examples/lookup + p2pctl lookup --trace.

15.4 Acceptance Criteria

  • lookup result == true_closest(target,k) in the oracle for all targets, all N (I3).
  • Hop count ≈ log₂N (measured distribution, I1); converges (I7) — no infinite loops, no premature stop.
  • A lookup with up to α−1 dead nodes per hop still succeeds (robustness, principle 5).

15.5 Conformance Fixtures

  • lookup/find_node_vs_oracle.json (I3), lookup/hop_distribution.json (I1), lookup/convergence.json (I7), lookup/dead_nodes_robust.json.

15.6 Pitfalls

  • Termination is subtle: stopping too early (before querying the k closest) → wrong result; never stopping (always "maybe closer") → infinite lookup. The converged predicate (I7) must be exactly right.
  • Not ingesting returned contacts into the table (only the shortlist) → the table never self-organizes (I5) — both must happen.
  • α book-keeping races: counting outstanding RPCs wrong → either too few in flight (slow) or unbounded (I15).
  • Re-querying an already-queried node → wasted RPCs + possible loops → the queried-set guards it.
  • A lying node returning itself as "closest" forever → distance-must-strictly-decrease check (anti-stall, P9 hardens).

15.7 Performance Concerns

  • Lookup latency = hops × effective-RTT; α hides slow hops (§4.5) → tune α vs message overhead.
  • Shortlist operations are per-response → keep them O(log k); avoid re-sorting the whole list.
  • Each hop reads table.closest (cheap, P2) + issues α RPCs (the real cost) → minimize redundant rounds.

15.8 Edge Cases

  • Target == an existing node ID (lookup finds it exactly); target with a sparse neighborhood (the last hops); N=1 (lookup returns self); a totally fresh node with only the bootstrap in its table (still converges via learned contacts).

15.9 Failure Analysis

  • A convergence/termination bug is the highest-severity correctness issue → vs the oracle across all targets + the convergence fixture (I3/I7); the hop-distribution gate catches a routing-quality regression (I1).
  • Lookups that stall → the global deadline returns best-so-far + flags it (I7); docs/failure-analysis/lost-lookup.md + docs/runbooks/slow-lookup.md.

15.10 Operational Notes

  • LookupTrace (hops, total RPCs, α, rounds, converged, RTTs); tools/lookup_trace renders the walk (distance-to-target per hop — visibly halving). Document the O(log N) argument in docs/performance/hop-distribution.md. This phase defines the Phase-0-done bar (§1.11).

16. Phase 4 — DHT store/get: find_value, k-replication, value integrity, caching

16.1 Objectives

  • Build the DHT key-value layer: find_value (lookup with early termination on a value hit, I8), store to the k closest nodes (k-replication, I9), value integrity checks (I10), and get-side caching for hot keys.

16.2 Detailed Implementation Steps

  • Theory anchors: k-replication + get-side caching (Kademlia paper, Maymounkov & Mazières 2002 → I8/I9, ADR-9, principle 4); availability math 1−(1−p)^k (§4.2); per-value integrity (#71 Merkle lineage → I10, ADR-15); LWW for mutable keys (ADR-14, §8.12); provider-record/republish lineage (IPFS / go-libp2p-kad-dht).
  • lookup::find_value — like find_node, but a queried node holding a non-expired copy returns the value → terminate early (I8); otherwise it returns closer nodes (the walk continues).
  • storage::store — find_node(key) → STORE(key,value,ttl) to each of the k closest live nodes; return the achieved replica count (I9).
  • storage::value + integrity — Value{bytes,seq,integrity=SHA-256(bytes)}; verify on receipt before storing/returning (I10, #71 lineage); reject mismatches (P2pError::ValueIntegrity).
  • storage::lww — mutable-key last-writer-wins by seq (§8.12); content-addressed keys (key=hash(value)) are immutable.
  • storage::store (handler side) — accept a STORE only if the key is plausibly in this node's responsibility range (anti-spam; hardened in P9 with the token, §8.8).
  • Get-side caching: after a successful get, STORE the value at the closest queried node that lacked it → popular keys migrate toward queriers, cutting future hops (Kademlia's caching, §3.4 step 5).

16.3 Deliverable

  • node.store(key,value) replicates to k nodes; node.get(key) retrieves it; in SimNetwork, stored values are retrievable from any node (I8/I9); examples/store_get.

16.4 Acceptance Criteria

  • get(key) returns the stored value from any node iff a non-expired replica exists (I8) — vs the store oracle.
  • store places the value on the k closest nodes (replica count == k when ≥ k live, I9).
  • A corrupted value is rejected on receipt (I10), never stored or returned.
  • Get-side caching measurably reduces hops for a repeatedly-fetched key.

16.5 Conformance Fixtures

  • storage/store_replicates_k.json (I9), storage/find_value_hit.json (I8), storage/value_integrity_reject.json (I10), storage/lww_seq.json, storage/get_caching.json.

16.6 Pitfalls

  • find_value must still return closer nodes when no value is found (so the walk converges) — not just "not found" at the first miss.
  • Storing on the k closest at store time — but the closest set shifts under churn (P6 republish handles the drift); a one-shot store without republish loses data (principle 4).
  • Integrity check on content-addressed keys must use the key (= hash) as the expected digest; on mutable keys, the embedded integrity field (and trust is weaker → P9 token).
  • Get-side caching can serve stale mutable values → cache respects TTL + seq (don't cache below the freshest seen seq).
  • Last-writer-wins clock/seq source: a misbehaving publisher with a huge seq wins forever → P9 bounds/validates.

16.7 Performance Concerns

  • store = one lookup + k STORE RPCs → the k STOREs parallelize; large values use TCP fallback (P1).
  • get early-terminates → usually fewer hops than find_node; caching amortizes hot keys.
  • Value size budget: small DHT values (peer lists, hashes) are the design point; large blobs → TCP + chunking (or out of scope, store a pointer).

16.8 Edge Cases

  • get for a never-stored key (miss, I8); store when < k live nodes exist (replica count < k — accepted, repaired later); two concurrent stores to one mutable key (LWW resolves); a value exactly at the MTU boundary (UDP vs TCP).

16.9 Failure Analysis

  • Data loss (a get misses a value that should exist) → store/get oracle differential (I8/I9) + the under-replication detector → docs/failure-analysis/data-loss-under-churn.md + docs/runbooks/missing-value.md.
  • An integrity-check gap → a poisoned value propagates → fuzz the value decoder + the integrity fixture (I10).

16.10 Operational Notes

  • StoreTrace (replicas, want, hops, bytes); get_hit/get_miss/value_integrity_fail counters; document the value model (immutable vs mutable, LWW) in docs/wire-protocol.md.

17. Phase 5 — Bootstrap / join: entry points + self-lookup + table population

17.1 Objectives

  • Implement join (§8.15): contact bootstrap node(s), self-lookup to learn the neighborhood, refresh buckets to populate the table; handle cold-start and multiple entry points (I13-adjacent, principle: no single join SPOF).

17.2 Detailed Implementation Steps

  • Theory anchors: join-by-self-lookup to populate buckets + bucket refresh (Kademlia paper, Maymounkov & Mazières 2002, §8.15 → I5); no-single-join-SPOF (principle 6 ethos, ADR-21); learn-from-all so neighbors discover the joiner (principle 2 → I5).
  • bootstrap::entry_points — manage configured bootstrap addresses; PING to find a live one; retry across multiples.
  • bootstrap::join — insert the bootstrap node(s) into buckets; trigger self-lookup.
  • bootstrap::self_lookup — find_node(my_id): queries progressively closer nodes to self → populates the k-buckets with the local neighborhood (the joining node becomes known to its neighbors, I5).
  • Bucket refresh on join: find_node for a random ID in each bucket farther than the closest neighbor → well-distributed table.
  • bootstrap::cold_start — the first node (empty table, it is the seed); the overlay grows as others join through it.

17.3 Deliverable

  • A new node joins an existing SimNetwork/multi-node overlay via a bootstrap address and ends with a populated, well-distributed routing table; queryable within < 5 s (§4); examples/join_overlay.

17.4 Acceptance Criteria

  • After join, the node's table is populated (neighbors known) and it answers/issues lookups correctly (vs oracle).
  • The joining node is discoverable by others (a lookup for its ID from elsewhere finds it) — confirming self-lookup made it known (I5).
  • Join completes in < 5 s for N ≤ 1024 (sim) (§4); a dead bootstrap address is skipped for a live one.

17.5 Conformance Fixtures

  • lookup/join_populates_table.json, lookup/joined_node_discoverable.json, lookup/bootstrap_failover.json (dead entry point).

17.6 Pitfalls

  • Self-lookup is the mechanism of table population — skipping it leaves the table empty except the bootstrap node → no real routing.
  • A single bootstrap address = a join SPOF → support a list; the cold-start (first node) is a special case (no bootstrap).
  • Joining nodes can momentarily skew load onto the bootstrap node → it's only used once (then ordinary peers take over).
  • Refreshing every bucket (256) on join is wasteful → only buckets beyond the closest neighbor have useful range.

17.7 Performance Concerns

  • Join cost = one self-lookup (O(log N) hops) + a bounded set of bucket-refresh lookups → small; the < 5 s target is generous.
  • The bootstrap node sees join traffic O(join rate) → bounded; not on the steady-state data path.

17.8 Edge Cases

  • The first node (no bootstrap, empty overlay); all bootstrap addresses dead (BootstrapFailed); a node re-joining after a restart (its old ID may still be in peers' tables — re-learned, I5); joining a single-node overlay.

17.9 Failure Analysis

  • A join bug → an isolated node (empty table) → lookups fail → the joined-node-discoverable fixture + the < 5 s target catch it → docs/runbooks/bootstrap-failure.md.
  • All entry points dead → BootstrapFailed (no silent hang) → caller tries alternates / waits.

17.10 Operational Notes

  • Document the bootstrap-address convention + cold-start; LookupTrace for the self-lookup; expose "time-to-usable-table" as a join metric.

18. Phase 6 — Churn maintenance: refresh, republish, expiry, repair, leave

18.1 Objectives

  • Make the overlay correct under continuous churn (the defining problem, §2.7): bucket/table refresh, value republish + expiry, value repair/re-replication, graceful + implicit leave, and per-contact failure detection (I9, principle 4).

18.2 Detailed Implementation Steps

  • Theory anchors: the churn wall (§2.7, principle 4 → I9); refresh/republish/expiry intervals + reactive-vs-periodic recovery and α/timeout tuning (Rhea et al., "Handling Churn in a DHT," USENIX ATC 2004); detect-vs-transient ambiguity (FLP intuition, Lynch; principle 10 → I10); measured heavy-tailed churn timescales (Stutzbach & Rejaie 2006; Steiner et al. 2007, §4.4).
  • churn::refresh — periodic: any bucket idle > t_refresh (1h) → find_node for a random ID in its range (keeps contacts fresh, fills gaps).
  • storage::republish — periodic (t_republish, 1h): re-STORE each held value to its current closest-k → newly-joined closer nodes receive replicas; the publisher refreshes the TTL (I9).
  • storage::expiry — sweep: drop values past t_expire (24h) not republished (bounds storage).
  • churn::repair — detect under-replication (a find_node(key) shows the value should be on a node that lacks it, or a replica left) → re-STORE to restore k (I9).
  • churn::detect — a contact that times out on max_retries RPCs → suspected → evicted from its bucket (implicit leave, I10); promote a replacement.
  • churn::leave — graceful: hand off stored values to the new closest-k + notify neighbors (faster repair than waiting for detection).

18.3 Deliverable

  • The overlay sustains correct lookups + data availability under continuous join/leave in SimNetwork; examples/churn_sim + p2pctl churn show success rate vs churn rate.

18.4 Acceptance Criteria

  • Lookup success ≥ 99 % at ≥ 50 % per-hour churn (k=20, α=3) (§4, I7).
  • Key availability ≥ 99 % at 50 % simultaneous node failure (k=20) (§4, I9) — repair restores replicas.
  • A dead contact is detected within max_retries × rpc_timeout (I10) and evicted; a graceful leave hands off values.
  • Expired values are dropped; republish keeps live values on the current closest-k.

18.5 Conformance Fixtures

  • churn/lookup_success_vs_churn.json (I7), churn/availability_50pct_failure.json (I9), churn/republish_to_new_closest.json, churn/repair_restores_k.json, churn/graceful_leave_handoff.json, churn/implicit_leave_detect.json (I10).

18.6 Pitfalls

  • Republish to the current closest-k, not the original — the set shifts under churn; republishing to stale nodes wastes effort and loses durability (principle 4, I9).
  • Repair storms: aggressive repair on every transient timeout → bandwidth amplification → rate-limit + confirm-dead before repairing.
  • A flapping node (up/down) → repeated evict/re-add churn in buckets → hysteresis / suspicion before eviction (I10).
  • Expiry vs republish race: a value expiring exactly as a republish arrives → republish resets TTL atomically.
  • Distinguishing "node left" from "transient network" is fundamentally ambiguous (the FLP intuition) → bound + confirm, never instant.

18.7 Performance Concerns

  • Steady-state maintenance bandwidth: O(log N) refresh + O(V·k) republish per node (§4.4) — must not grow super-linearly; tune intervals vs churn rate.
  • Republish dominates for value-heavy nodes → batch STOREs to the same closest-k set; consider Merkle-diff (deferred, §8.12) to republish only changed values.
  • Detection cost is per-contact timeout (no extra heartbeat thread for k-buckets, ADR-12) → cheap.

18.8 Edge Cases

  • All replicas of a key leave before republish (rare loss, §4.2); a node leaves then immediately re-joins (flap); 100 % churn (overlay dissolves — document); simultaneous leave of a whole bucket's contacts (replacements + refresh recover).

18.9 Failure Analysis

  • Data loss under churn = the signature failure → the availability-under-failure fixture (I9) + repair + republish are the net; escapes → docs/failure-analysis/data-loss-under-churn.md + docs/runbooks/churn-storm.md.
  • A maintenance bug that lets the table rot → lookup-success-vs-churn regression (I7) → docs/failure-analysis/lost-lookup.md.

18.10 Operational Notes

  • ChurnTrace (joins, leaves, detected_dead, repairs, lookups_failed, availability); document refresh/republish/expiry intervals + the detection bound; alert on availability or success-rate dips.

19. Phase 7 — Chord: ring, finger table, successor list, stabilization (compared scheme)

19.1 Objectives

  • Implement Chord behind the RoutingScheme trait (ADR-4): ring distance, finger table, successor list, predecessor, and the stabilization protocol (I6) — a compared alternative to validate the design space and the O(log N) result, and to demonstrate the churn-fragility tradeoff (§4.3, principle 3).

19.2 Detailed Implementation Steps

  • Theory anchors: ring + finger table + successor list + stabilization, and the successor-list fault-tolerance proof (Stoica et al., "Chord," SIGCOMM 2001 and the IEEE/ACM ToN 2003 extended version → I6, ADR-4); the successor list mandated by principle 3; iterative-vs-recursive contrast (principle 5, §8.6).
  • routing::chord_finger — finger[i] = successor(n + 2^i); closest_preceding(target) = the next hop (§8.6).
  • routing::chord_successor — the r-entry successor list (fault tolerance) + predecessor pointer.
  • lookup over Chord — both recursive (the queried node forwards, §8.6) and iterative variants, reusing the lookup engine via the trait.
  • churn::stabilize (I6) — periodic stabilize (ask successor for its predecessor; adopt if closer; notify the successor); fix_fingers (refresh one finger/round); check_predecessor (ping; clear if dead).
  • Key ownership: a key k is owned by successor(k); store/get route to successor(key) + the successor list for replication.

19.3 Deliverable

  • A Chord overlay in SimNetwork routes lookups in O(log N) hops and stabilizes under churn; p2pctl --scheme chord runs the comparison; bench compares Chord vs Kademlia hop counts + churn resilience.

19.4 Acceptance Criteria

  • Chord lookup == true_closest (owner = successor(key)) (I3); hops ≈ log₂N (I1).
  • After stabilization, the first successor is the true successor + the successor list is non-empty (I6).
  • Under churn, Chord with a successor list maintains correctness; without it (a deliberate test) loses lookups — demonstrating principle 3.

19.5 Conformance Fixtures

  • routing/chord_lookup_vs_oracle.json (I3), routing/chord_stabilize_consistency.json (I6), routing/chord_successor_list_fault_tolerance.json, routing/chord_vs_kademlia_churn.json.

19.6 Pitfalls

  • Without a successor list, a single successor failure breaks the ring (the classic Chord fragility) → the list is mandatory (principle 3, §8.4).
  • Stabilization race: concurrent joins between two nodes → transient incorrect successors → converges via repeated stabilize, but lookups during the window may miss (document; Kademlia's redundancy avoids this).
  • closest_preceding must return a node strictly preceding the target on the ring → off-by-one wraps incorrectly (modular arithmetic on 2^256).
  • Finger fixing one-at-a-time is slow to converge after a big membership change → acceptable (steady-state), but note the cold-join lag.

19.7 Performance Concerns

  • Chord's table is smaller (log N fingers vs k·log N buckets, §4.3) → less memory, but stabilization is more frequent (ADR-12) → higher maintenance bandwidth; the tradeoff is the lesson.
  • Recursive routing has fewer originator round-trips but no parallelism → higher tail latency than Kademlia's α-parallel iterative (principle 5).

19.8 Edge Cases

  • Ring of size 1 (successor = self); two nodes (each is the other's successor + predecessor); a join exactly between two nodes; wrap-around at 2^256 − 1 → 0.

19.9 Failure Analysis

  • A stabilization bug → an inconsistent ring → lookups route wrong → the stabilize-consistency fixture (I6) + the oracle (I3) catch it; the successor-list test proves fault tolerance → docs/failure-analysis/partition.md.
  • Demonstrating Chord's churn-fragility vs Kademlia is itself a deliverable (the comparison fixture) — it justifies ADR-3.

19.10 Operational Notes

  • TableTrace for Chord (fingers, successor-list length, predecessor); succ_consistent telemetry; document the stabilization protocol + the Kademlia-vs-Chord tradeoff in docs/performance/.

20. Phase 8 — Pastry: prefix routing, leaf set, neighborhood set (compared scheme)

20.1 Objectives

  • Implement Pastry behind the RoutingScheme trait (ADR-4): prefix-based routing table, a leaf set (numerically closest nodes), a neighborhood set (proximity), and prefix-route forwarding — the third compared scheme, demonstrating the prefix-routing point in the design space and a basic proximity metric (principle 1).

20.2 Detailed Implementation Steps

  • Theory anchors: prefix routing + leaf set + neighborhood (proximity) set, and the base-2^b hop/table-size tradeoff (Rowstron & Druschel, "Pastry," Middleware 2001 → I1/I3, ADR-4, §4.3); structured-routing-not-flooding (principle 1); FreePastry as the reference impl (§5.3).
  • routing::pastry_table — rows indexed by shared-prefix length; row r, column c holds a node sharing an r-digit prefix with us and differing at digit r = c (base 2^b, b≈4 → 16 columns/row).
  • routing::pastry_leafset — the L numerically-closest nodes (L/2 above, L/2 below the local ID) — Pastry's analogue of Kademlia's closest bucket; the destination-determination set.
  • Neighborhood set — the M proximity-closest (by network RTT) nodes; informs proximity-aware route-table population (basic only; full proximity deferred §1.7).
  • Prefix routing (route(target)): if target ∈ leaf-set range → forward to the numerically-closest leaf (final hop); else use the routing-table entry sharing a longer prefix with target; else (rare) forward to any node closer numerically and sharing ≥ the current prefix.
  • Reuse the lookup engine via the trait; key ownership = the numerically-closest node (leaf set).

20.3 Deliverable

  • A Pastry overlay in SimNetwork routes in O(log_{2^b} N) hops; p2pctl --scheme pastry; bench compares hop counts + route-table size vs Kademlia/Chord (§4.3).

20.4 Acceptance Criteria

  • Pastry lookup == true_closest (owner = numerically-closest node) (I3); hops ≈ log_{2^b}N (I1) — fewer hops than Kademlia/Chord at b>1, larger table (the tradeoff).
  • Leaf set correctly identifies the final-hop destination; routing table fills by prefix length.
  • The base-2^b knob trades hop count vs table size (measured across b).

20.5 Conformance Fixtures

  • routing/pastry_lookup_vs_oracle.json (I3), routing/pastry_hop_distribution.json (I1), routing/pastry_leafset_destination.json, routing/pastry_base_tradeoff.json (b sweep).

20.6 Pitfalls

  • Prefix-matching the wrong digit base → routes diverge; fix b + digit extraction (big-endian, the §12.6 byte-order discipline again).
  • The leaf-set boundary condition (target just inside vs just outside the set) → the single trickiest Pastry case; off-by-one routes past the owner.
  • Neighborhood set vs leaf set confusion: leaf set = numeric closeness (correctness), neighborhood = network closeness (proximity/perf) — different roles.
  • Empty routing-table cell (no known node with that prefix) → fall back to a numerically-closer leaf, never drop the route.

20.7 Performance Concerns

  • Larger base b → fewer hops (log_{2^b}N) but a wider routing table ((2^b−1)·rows, §4.3) → memory-vs-latency knob; b=4 is Pastry's typical choice.
  • Proximity-aware population (neighborhood set) reduces physical RTT per hop — the Pastry advantage Kademlia lacks by default; basic here, full deferred.

20.8 Edge Cases

  • Target sharing a full prefix with the local ID (it is the owner); a node at the leaf-set boundary; base 2^b where b doesn't divide 256 evenly (handle the last partial digit); a tiny overlay (leaf set = whole network).

20.9 Failure Analysis

  • A prefix-routing bug → wrong owner → vs the oracle (I3) + the leaf-set-destination fixture catch it; the base-sweep validates the hop/size tradeoff that motivates ADR-3.
  • Pastry vs Kademlia/Chord comparison is itself a deliverable (the three-scheme bench justifies the Kademlia default).

20.10 Operational Notes

  • TableTrace for Pastry (rows populated, leaf-set size, neighborhood size); document the prefix-routing rule + the base/hop/size tradeoff in docs/performance/; the three-scheme comparison closes the routing design-space study.

21. Phase 9 — Security: Sybil & eclipse mitigation, routing-poisoning checks, secure routing

21.1 Objectives

  • Implement the practical Sybil/eclipse mitigations (§8.14, principle 7): ID-generation cost (ID = hash(IP||nonce), I13), bucket IP-prefix diversity (I14), disjoint parallel lookups (S/Kademlia), routing-table-poisoning checks, the STORE write-token (BEP-5 idea), and per-source rate limiting (I15) — mitigation, not elimination (Douceur).

21.2 Detailed Implementation Steps

  • Theory anchors: crypto-puzzle node IDs + disjoint parallel lookups (Baumgart & Mies, "S/Kademlia," ICPADS 2007 → I13/I14, ADR-16/17); the constrained-table + redundant-routing eclipse defenses (Castro et al., "Secure routing," OSDI 2002); degree-bounding (Singh et al., "Eclipse Attacks," INFOCOM 2006); the residual-risk impossibility (Douceur, "The Sybil Attack," IPTPS 2002 → principle 7, §26.3); the BEP-5 write-token (§8.8); bounded per-source rate (principle 8 → I15).
  • security::sybil_id (I13) — secure-mode ID = SHA-256(IP || nonce) satisfying a constraint (static prefix-zeros, or a tunable PoW cost); validate a contact's ID against its source address on insert; reject/penalize mismatches (raises cost + binds ID to network position).
  • security::diversity (I14) — per-bucket quota: ≤ D contacts sharing an IP /prefix (e.g. /24) → one subnet can't fill a bucket (the eclipse-via-bucket-capture defense).
  • security::disjoint_lookup — run d independent lookups over node-disjoint paths (each excludes the others' nodes), intersect/union the results → the adversary must control all d paths to eclipse (S/Kademlia, §8.14); used for security-critical lookups.
  • security::poison_check — a returned contact must be plausibly closer to the target than the responder (else it's a lie/redirect); rate-limit unsolicited contact additions; prefer long-lived/observed contacts over freshly-advertised ones.
  • security::token — STORE requires a token previously issued by the target node in a FIND_NODE/get reply (echo-back), preventing third parties from storing under a spoofed source address (the BEP-5 announce_peer token, §8.8).
  • security::rate_limit (I15) — per-source-IP RPC + store-rate caps; drop/throttle floods (resource-exhaustion defense, principle 8).

21.3 Deliverable

  • Secure mode raises Sybil/eclipse cost measurably in SimNetwork; examples + the fault harness show capture probability vs adversary fraction; p2pctl --secure enables ID constraints + diversity + disjoint lookups.

21.4 Acceptance Criteria

  • ID-constraint validation rejects IDs not matching hash(IP||nonce) (I13); the PoW knob measurably raises mint cost.
  • Bucket diversity (I14) caps same-/prefix contacts; an IP-prefix flood can't capture a bucket.
  • Disjoint lookups succeed when ≤ d−1 paths are adversary-controlled (eclipse resistance); the harness measures capture probability vs adversary fraction f and matches the S/Kademlia analysis.
  • The STORE token blocks spoofed-source stores; rate limiting bounds per-source load (I15).

21.5 Conformance Fixtures

  • security/id_constraint_reject.json (I13), security/bucket_diversity_quota.json (I14), security/disjoint_lookup_eclipse.json, security/poison_contact_rejected.json, security/store_token.json, security/rate_limit_flood.json (I15).

21.6 Pitfalls

  • Sybil-resistance is not a solution (Douceur): without a trusted authority, a sufficiently-resourced adversary still mints IDs → the threat model must state the residual risk plainly (principle 7).
  • Diversity quotas can hurt legitimate NAT'd users behind one IP (many real peers share an address) → the quota must be tuned, not absolute (false-positive cost).
  • Disjoint lookups cost d× messages → reserve for security-critical lookups, not every lookup (perf vs security knob).
  • The poison "plausibly closer" check can be gamed by an adversary returning genuinely closer Sybil nodes → diversity + disjoint paths are the backstop, not the distance check alone.
  • A PoW ID constraint set too high → legitimate joins are slow; too low → no Sybil deterrence → calibrate against the threat model.

21.7 Performance Concerns

  • ID-constraint PoW adds a one-time join cost (acceptable); per-RPC ID validation is a cheap hash compare.
  • Disjoint lookups multiply message count by d → bounded, applied selectively.
  • Diversity checks are O(bucket) on insert → cheap; rate limiting is a per-source counter (bounded memory, I15).

21.8 Edge Cases

  • Many legitimate peers behind one NAT IP (diversity false positive — tune D); an adversary controlling exactly d paths (eclipse succeeds — document the bound); a node changing IP (ID becomes invalid in secure mode → re-mint); a PoW constraint of zero (open mode, no Sybil cost).

21.9 Failure Analysis

  • An eclipse in progress → diversity skew (bucket_prefix_skew, I14) + disjoint-lookup divergence are the detection signals → docs/runbooks/eclipse-suspected.md + docs/failure-analysis/routing-poisoning.md.
  • A Sybil flood → rate-limit + diversity quotas contain it; the capture-probability fixture quantifies residual risk; the threat model (below) states the limit honestly.

21.10 Operational Notes

  • id_constraint_fail, bucket_prefix_skew, store_rate, proto_drop telemetry; document the secure-mode knobs (PoW cost, diversity D, disjoint d) + the residual Sybil/eclipse risk in docs/threat-model.md; alert on bucket-prefix skew (eclipse signal).

22. Phase 10 — NAT traversal: classification, hole punching, relay fallback (core in scope; full deferred)

22.1 Objectives

  • Implement the core NAT-traversal mechanics needed for real deployment: NAT-type classification (STUN-like probe), a coordinated hole-punching handshake, and a simple relay fallback (I-class reachability). The full ICE-like negotiation + a production TURN relay are PhaseDeferred("§22.2") (ADR-18, §1.7).

22.2 Detailed Implementation Steps

  • Theory anchors: NAT classification + hole-punch + relay scoped per ADR-18 (principle: reachability), with full ICE/TURN deferred; references RFC 5389 (STUN), RFC 8445 (ICE), RFC 8656 (TURN) (§5.4); the deferral is registered at the Deferred Features Register (§39).
  • nat::classify — a STUN-like probe (send from the same socket to two server addresses; compare observed external addr/port) to heuristically classify full-cone / restricted-cone / port-restricted / symmetric NAT.
  • nat::hole_punch — the rendezvous-coordinated handshake: two NAT'd peers, learning each other's external (ip,port) via a mutually-reachable third node, send simultaneous datagrams to open the path (works for cone NATs; symmetric-to-symmetric needs relay).
  • nat::relay_stub — a fallback: a third reachable node forwards datagrams between two otherwise-unreachable peers (a minimal TURN-like relay; production hardening + selection deferred, §1.7).
  • Integrate with rpc: a contact's NodeInfo carries its observed external address; lookups/stores to NAT'd peers trigger hole-punch (then relay) transparently.
  • PhaseDeferred("FINAL_BLUEPRINT §22.2"): full ICE candidate gathering/prioritization, symmetric-NAT prediction, a scalable relay infrastructure, IPv6/dual-stack nuances.

22.3 Deliverable

  • Two simulated-NAT peers (a NAT model in SimNetwork) establish connectivity via hole-punch or fall back to relay; examples + a NAT-scenario fixture; real-internet hardening is gated.

22.4 Acceptance Criteria

  • NAT classification correctly distinguishes the modeled NAT types in simulation.
  • Cone-NAT peers connect via hole-punch (no relay); symmetric-to-symmetric falls back to the relay stub.
  • The deferred items are explicitly gated behind PhaseDeferred("§22.2") and surfaced (not silently missing).

22.5 Conformance Fixtures

  • routing/nat_classify.json, routing/hole_punch_cone.json, routing/relay_fallback_symmetric.json (against the SimNetwork NAT model).

22.6 Pitfalls

  • Hole-punch timing: both peers must send near-simultaneously (the rendezvous coordinates this) → a skew misses the window → retry with backoff.
  • NAT classification is heuristic + flaky in reality (NAT behavior varies wildly) → never assume a classification is exact; degrade to relay on doubt.
  • A relay is a bandwidth + privacy liability (it sees all forwarded traffic) → minimize, select carefully (deferred); never route bulk data through it by default.
  • Symmetric NAT defeats naive hole-punching (port changes per destination) → relay is the honest fallback, not a clever prediction (deferred).

22.7 Performance Concerns

  • Hole-punch adds a one-time setup RTT (via the rendezvous) → amortized over the connection.
  • Relay'd paths have higher latency + consume the relay's bandwidth → a last resort; the bulk of an overlay should be directly reachable.

22.8 Edge Cases

  • Both peers symmetric (relay required); a peer behind CGNAT (carrier-grade — relay likely); the rendezvous node itself NAT'd (must be publicly reachable); IPv6 peers (often no NAT — direct).

22.9 Failure Analysis

  • A peer is unreachable (NAT defeats both punch + relay) → it's effectively a leaf/consumer, not a full routing node → document; the overlay tolerates it (it can query but not be queried).
  • Relay overload → bounded by rate limits (P9); a relay leaving mid-forward → the connection drops → re-establish (treated as a transient failure).

22.10 Operational Notes

  • NAT-type + hole-punch/relay-rate telemetry; document the NAT model + the deferred ICE/TURN scope in docs/runbooks/; this phase is where the real-internet gap is made explicit (sim works; production NAT is hard, §1.7).

23. Phase 11 — C ABI: lookup/store/get from C and Python

23.1 Objectives

  • Expose a stable C ABI (+ a thin Python-FFI-friendly layer) so external callers — chiefly #80 BitTorrent (a swarm client driving trackerless peer discovery) — can join/lookup/store/get/leave over the overlay (ADR-21, ADR-26), with all errors as codes and no panic across the boundary (I11).

23.2 Detailed Implementation Steps

  • Theory anchors: no-panic-across-FFI + codes-not-panics (ADR-26 → I11); frozen ABI / separate-from-wire versioning (ADR-30); bounded buffers (principle 8 → I15); the #80 BitTorrent consumer as the headline caller (§2.5).
  • cabi::node_ffi — p2p_node_new(config) -> handle, p2p_node_join(handle, bootstrap[]), p2p_node_leave(handle), p2p_node_free(handle); opaque handle, no Rust types leak.
  • cabi::lookup_ffi — p2p_lookup(handle, key[32], out_nodes, out_len) -> errno; returns the k closest NodeInfo (id+addr) into a caller buffer.
  • cabi::store_ffi — p2p_store(handle, key[32], value, len, ttl) -> errno (returns replica count via out-param); p2p_get(handle, key[32], out_value, out_len) -> errno.
  • cabi::errno — the frozen P2P_E* code mapping (§11.12); catch_unwind at every boundary → an internal panic becomes P2P_EINTERNAL, never UB (I11).
  • include/p2p.h — the hand-maintained header (opaque p2p_node_t*, fixed [32] IDs, length-prefixed values, the errno enum); a thin Python wrapper over it.
  • Document the buffer-ownership contract (caller allocates out_*; lengths are in/out; IDs are exactly 32 bytes).

23.3 Deliverable

  • A C program (examples/run_from_c.c) joins an overlay, stores a value, and gets it back; a Python wrapper does the same; #80 can drive peer discovery via the ABI.

23.4 Acceptance Criteria

  • The C example links against p2p.h and round-trips a store/get; all errors surface as P2P_E* codes (no panic, I11).
  • ABI is C-callable + Python-ctypes-friendly; 32-byte IDs + length-prefixed values cross cleanly.
  • A fuzzer on the FFI args (bad lengths, null pointers, oversize buffers) finds no UB (I11/I15).

23.5 Conformance Fixtures

  • badframes/ffi_bad_args.json (null/oversize/short buffers), lookup/ffi_roundtrip.json, storage/ffi_store_get.json.

23.6 Pitfalls

  • Panics across FFI = UB → catch_unwind at every extern "C" entry (I11) — the single most important ABI rule.
  • Buffer-length contract ambiguity (who allocates, in/out lengths) → document + validate; a short out buffer must error, not overflow (I15).
  • ID length: anything but exactly 32 bytes is invalid → validate at the boundary (P2P_EPROTO).
  • Async runtime ownership: the C caller is synchronous → the ABI must drive the async node on an internal runtime, blocking the FFI call until completion (no leaked tasks).
  • Returning Rust-allocated memory to C without a matching p2p_free → a leak/ABI mismatch → length-into-caller-buffer or paired alloc/free only.

23.7 Performance Concerns

  • The FFI boundary is not on the per-hop hot path (it's per-lookup/store) → blocking is acceptable; avoid per-call allocation where the caller provides buffers.
  • A synchronous ABI over an async core means one runtime thread services FFI calls → bounded; document the concurrency model for the caller.

23.8 Edge Cases

  • Null handle/pointers; zero-length value; out buffer exactly the right size vs one short; concurrent FFI calls from multiple C threads on one handle (must be safe or documented single-threaded); a key of all-zeros.

23.9 Failure Analysis

  • An ABI break silently corrupts a caller (#80) → frozen codes + SemVer-major gate (ADR-30) + the FFI fuzz/roundtrip fixtures; p2p.h is the contract.
  • A leaked task / blocked runtime thread → the FFI hangs → bounded by the internal lookup deadline (I7) surfacing as P2P_ETIMEOUT.

23.10 Operational Notes

  • Version the ABI separately from the wire protocol (ADR-30); document the header + buffer contract; #80 integration is the headline consumer (§2.5). Codes frozen at the ABI.

24. Phase 12 — Performance hardening: lookup latency, parallelism tuning, caching, table layout

24.1 Objectives

  • Drive the system to the §4 targets: lookup latency near hops × effective-RTT, the O(log N) hop distribution, α/timeout tuned for churn, get-side caching for hot keys, and cache-friendly routing-table layout (principle 8, §4.1/§4.5).

24.2 Detailed Implementation Steps

  • Theory anchors: the α/timeout calibration against measured churn (Rhea et al. 2004, §4.5, ADR-7); leaf-lock / never-await-holding discipline (principle 9, ADR-25); bounded resources (principle 8 → I15); the O(log N) hop target as the gate, never a hardcoded constant (§4.1 → I1).
  • Lookup-latency profiling: flamegraph + per-hop RTT histograms (LookupTrace); identify whether latency is RTT-bound (expected) or stalled by serialization/lock contention (a bug).
  • α/timeout sweep: measure success-rate + latency vs (α, rpc_timeout, max_retries) across churn rates → calibrate the §4 defaults (α=3, ~1 s timeout); expose as config, never hardcode (§4.5).
  • Get-side caching tuning (P4): cache placement (closest queried node lacking the value), cache TTL, and eviction → measure hop reduction for popular keys (§3.4 step 5).
  • Routing-table layout: keep KBucket entries in a small contiguous ArrayVec (cache-friendly closest scans, P2); shard per-bucket locks (ADR-25) to remove contention; ensure the table lock is never held across .await (principle 9).
  • RPC batching: recvmmsg/sendmmsg, buffer reuse (no per-RPC allocation, P1); the correlation map as a fast bounded concurrent structure.
  • Optional: parallel-lookup pipelining (issue the next round's α before the current round fully settles) — bounded by the convergence predicate (I7).

24.3 Deliverable

  • Lookup latency + hop distribution meet §4 targets in SimNetwork + a small multi-host overlay; benches report latency/hops/success vs α + churn; caching measurably cuts hot-key hops.

24.4 Acceptance Criteria

  • Hop count tracks log₂N (I1); lookup latency ≈ hops × effective-RTT (no serialization stalls).
  • The calibrated (α, timeout) meet the §4 success-rate-under-churn target (≥ 99 % at 50 %/h churn).
  • No routing-table lock contention on the lookup hot path (profile shows the lock as a leaf, principle 9).
  • Get-side caching reduces hops for a repeatedly-fetched key (measured).

24.5 Conformance Fixtures

  • lookup/latency_vs_rtt.json, lookup/hop_distribution_large_n.json (I1), churn/success_vs_alpha.json, storage/caching_hop_reduction.json, plus the perf-regression gates (P13).

24.6 Pitfalls

  • Optimizing message count at the cost of robustness (lowering α) → worse under churn → tune against the churn target, not in a static network (§4.5).
  • A lock held across the network (principle 9 violation) → a single slow peer stalls all of a node's lookups → the highest-impact perf bug; profile for it explicitly.
  • Per-RPC allocation in the hot loop → GC-free but still allocator pressure → reuse buffers (P1).
  • Cache serving stale mutable values (P4 pitfall) → respect TTL + seq; a perf optimization must not break consistency (§8.12).
  • Over-pipelining lookups → issuing RPCs to nodes the convergence predicate would have pruned → wasted messages; bound by I7.

24.7 Performance Concerns

  • Tail latency: the α-th-order-statistic min hides stragglers (§4.5) — measure p99 hop latency, not just p50; a long tail signals dead-contact accumulation (churn) → refresh tuning.
  • Cache locality: closest scans ~log N small buckets per hop → contiguous ArrayVec + small k keep them in cache.
  • Syscall overhead per datagram → batch; the correlation-table lookup is per-response → keep it O(1).

24.8 Edge Cases

  • A pathological target whose neighborhood is one slow node (latency tail); a hot key fetched by all nodes (caching storm — bound cache writes); a very large N where even log N hops × RTT is seconds (document the latency floor).

24.9 Failure Analysis

  • A latency regression → the perf-regression gate (P13) + flamegraph diff localize it (lock contention, allocation, or extra hops) → docs/performance/lookup-latency.md + docs/runbooks/slow-lookup.md.
  • α mis-tuned for the deployment's churn → success-rate dip → the success-vs-α fixture + the churn alert (P6).

24.10 Operational Notes

  • LookupTrace (p50/p99 RTT, hops, rounds) drives the perf dashboards; document the α/timeout calibration procedure + the caching policy in docs/performance/parallelism-tuning.md; perf gates run in CI (P13).

26. Threat Model

Trust boundary: the network. The overlay is open — anyone may join, every inbound RPC is from a potentially hostile peer. Defenses are cost + diversity + redundancy + validation; an honest majority is not assumed (principle 6/7).

26.1 Attack surface

  • The UDP/TCP RPC parser (untrusted frames from any peer) — the primary memory-safety surface.
  • The routing table (poisoning: an attacker injects crafted contacts to steer lookups).
  • The lookup engine (an attacker on the path lies to redirect/stall).
  • The value store (spoofed/poisoned STOREs; resource exhaustion via mass stores).
  • Node identity (Sybil: cheap mass identities; eclipse: adversarial neighbor placement).
  • The C ABI (malformed args from the caller).
  • The bootstrap node(s) (a poisoned entry point seeds a bad table).

27.1 Blast radius

  • A single hostile peer: bounded — defensive parsing (I11) + rate limits (I15) + the distance/integrity checks contain it to dropped frames + a little wasted bandwidth; it cannot crash a node or corrupt a result.
  • A node failure: bounded — k-bucket redundancy + α-parallelism route around it; its stored values survive via the other k−1 replicas + repair (I9).
  • A Sybil/eclipse campaign: bounded by the quantified capture probability (P9) — mitigated, with stated residual risk; the rest of the overlay is unaffected (the attack is target-local).
  • A partition: each side remains a functioning sub-overlay; mutable values may diverge → LWW reconcile on heal; immutable values never diverge (§8.12).

  • Span per store/get (replica placement, integrity result); structured logs at protocol-event granularity (join/leave/evict/repair).

28.3 Dashboards

  • Routing health: hop distribution vs log₂N, lookup success rate, p99 lookup latency, table fill.
  • Durability: replica counts, availability, repair rate, republish backlog.
  • Churn: join/leave/detect rates, lookups-failed under churn.
  • Security: bucket-prefix skew (eclipse), id-constraint-fail + join-rate spikes (Sybil), integrity-fail + parse-drop rates.

28.4 Alerting philosophy

  • Page on availability drop (data loss risk) and lookup-success drop (routing broken) — the two correctness SLOs.
  • Warn on bucket-prefix skew (possible eclipse), id-constraint-fail spike (possible Sybil), p99 latency climb (churn/contention).
  • Never page on a single dead contact (expected, churn-normal) — only on aggregate degradation.

28.5 SLOs

  • Lookup success ≥ 99 % (≤ 50 %/h churn); key availability ≥ 99 % (50 % simultaneous failure, k=20); lookup p99 ≈ log₂N × RTT × small constant; join < 5 s to a usable table.

28.6 Runbooks (docs/runbooks/)

  • slow-lookup (hop trace → contention vs dead-contact tail vs over-large N); missing-value (replica check → repair → republish lag); eclipse-suspected (prefix skew → disjoint re-lookup → diverse re-bootstrap); bootstrap-failure (entry-point liveness → alternates); churn-storm (raise α/republish, watch availability).

28.7 Deployment topology, upgrades, rollback

  • One p2pd per node; many across hosts; bootstrap addresses are the only shared config. Soft-state tables → a restarted node re-joins (re-bootstrap) and is re-learned by peers (I5).
  • Rolling upgrade on an open network: the wire protocol is versioned (I11/ADR-20/30); a node ignores incompatible-version frames (never trusts-and-misparses) → mixed versions coexist; a breaking change bumps the wire version + a deprecation window. Rollback = redeploy the prior binary; soft state self-heals.

29. Compatibility Guarantees

  • Wire protocol (ADR-20/30): every frame carries a version; a node accepts only known versions and ignores (never misparses) others (I11). Adding an RPC type or an optional payload field is backward-compatible; changing a field's meaning or the frame layout is a wire-version-major change with a deprecation window (an open, never-fully-upgradable population demands this).
  • C ABI (ADR-30): the P2P_E* codes + function signatures + [32]-byte ID convention are frozen; changing them is SemVer-major. New functions are additive (minor). p2p.h is the contract; #80 depends on it.
  • Routing/storage semantics: k, α, and interval defaults may change in a minor release (they are config), but the protocol (k-bucket eviction, lookup convergence, k-replication, republish/expiry) is stable; a semantic change is documented + versioned.
  • Value format: the Value{bytes,seq,integrity} layout is versioned with the wire protocol; content-addressed values (key=hash(value)) are format-stable by construction.
  • Scheme interoperability: Kademlia/Chord/Pastry do not interoperate on one overlay (different metrics/tables) — a deployment picks one scheme; this is a deployment-time choice, not a runtime negotiation (the compared schemes are pedagogical, ADR-4).
  • Deprecation policy: a deprecated wire version is supported for ≥ one minor cycle with a proto_version warning before removal; SemVer governs the library + ABI; the wire version is tracked separately (ADR-30).

30. Testing Strategy

  • Unit: per-crate — XOR/ring/prefix metric axioms (I2), k-bucket insert/evict (I4), shortlist/convergence (I7), frame codec (I11), value integrity (I10), LWW (§8.12), cost/interval logic.
  • Integration: multi-node SimNetwork flows — join → lookup → store → get → leave; cross-crate (rpc↔routing↔lookup↔storage).
  • Differential: every lookup/get vs the centralized oracle (true_closest/store oracle, I3/I8) across all targets, schemes, memberships — the headline correctness method (principle 14).
  • Property: metric axioms (I2); "a converged lookup returns the true k-closest" (I3); "republish restores k replicas" (I9); "bucket holds ≤ k" (I4) — proptest over random IDs/memberships.

32. Performance Engineering

  • Benchmarking (benches/): hop-count distribution (vs log₂N, I1), lookup latency (p50/p99, vs hops×RTT), success-rate-under-churn (vs α + churn), store/get availability (vs k + failure %), scaling curves (N=10^3…10^6 sim). All measured against §4 bounds.
  • Profiling: flamegraphs of the lookup hot path → confirm RTT-bound (expected), catch serialization stalls or lock contention (a bug); per-hop RTT histograms from LookupTrace.
  • Tracing methodology: the per-lookup span (distance-to-target per hop, α outstanding, convergence rounds) is the primary perf + correctness lens (tools/lookup_trace).
  • Allocator analysis: no per-RPC allocation (buffer reuse, P1/P12); compact NodeInfo + ArrayVec buckets keep closest cache-resident; large-N sim memory profiled (compact node state).
  • Lock analysis: the routing-table lock must be a leaf (never held across .await, principle 9) — profiled explicitly; sharded per-bucket locks remove contention (ADR-25).
  • Cache analysis: closest scans ~log N small contiguous buckets/hop → keep k small + entries contiguous; the correlation table is O(1) per response.
  • Syscall analysis: recvmmsg/sendmmsg batching; TCP_NODELAY on the fallback; UDP default avoids head-of-line blocking.
  • Tail-latency analysis: the α-th-order-statistic min hides stragglers (§4.5) — measure p99 hops × RTT; a climbing tail signals dead-contact accumulation → refresh tuning.
  • Throughput targets: RPC throughput ≥ 90 % of UDP-achievable; lookup latency ≈ log₂N × effective-RTT; maintenance bandwidth O(log N) refresh + O(V·k) republish/node (§4.4).

33. Scalability Analysis

  • Hop count: O(log N) (I1, §4.1) — scales to ~10^6 nodes at ~20 hops; the headline scaling property. Pastry's base 2^b trades hops (log_{2^b}N) for table size.
  • Routing-table size: Kademlia ≈ k·log N; Chord ≈ 2·log N; Pastry larger constant (§4.3) — all O(log N), scaling comfortably (tens of KB at N=10^6).
  • Per-lookup state: O(k) shortlist + ≤ α outstanding RPCs (I15) — N-independent, bounded.
  • Message volume per lookup: ≈ α × log N (with α=3) — scales logarithmically; disjoint lookups (security) multiply by d, applied selectively.
  • Maintenance bandwidth (steady state): O(log N) refresh lookups + O(V·k) republish per node (§4.4) — must not grow super-linearly with N; the value-republish term dominates for value-heavy nodes (the scaling pressure, mitigated by Merkle-diff deferred §8.12).
  • Bottlenecks & ceilings:
    • Bootstrap fan-in: all-to-coordinator is O(N) per entry node → use multiple bootstraps + a tree-broadcast of the peer table (target < 5 s at N≤1024, §8.13).
    • Republish cost: the dominant per-node steady-state cost for value-heavy nodes → batch + (deferred) Merkle-diff.
    • Churn rate: at extreme churn the table can't stay fresh faster than it rots → α + refresh interval + k are the levers; beyond a churn ceiling, success degrades (measured, §4).
    • Hot keys: a popular key concentrates get load on its closest-k → get-side caching (P4/P12) spreads it toward queriers.
    • Sybil/eclipse: the adversary's required fraction f to capture a target scales with the diversity + disjoint-path parameters (P9) — security and scalability interact.
  • Horizontal scaling: the overlay is horizontal scaling — adding nodes adds capacity + redundancy; the structured routing keeps lookup cost O(log N) regardless of N (the design's whole point, principle 1).
  • No central bottleneck: the data path is fully peer-to-peer (principle 9) — the only semi-central element (bootstrap) is touched once at join, removing the single-point-of-failure scaling wall of registry/coordinator designs (contrast #359, #250).

34. Mental Models & First Principles

The compressed insights an expert holds before touching the code. Each: the model, what it predicts, the bug class you write without it, and the resolving § where this blueprint applies it.

  • MM1 — "An ID is a point; routing is descent through a binary trie." The 256-bit ID space is a complete binary tree; a node's neighbors are leaves, and bucket i is the subtree you'd reach by flipping bit i of your own prefix. Predicts: each correct hop fixes ≥1 high-order bit, so lookups take ~log₂N hops (only the populated top ~log₂N levels matter, not all 256). Bug without it: indexing buckets off the raw ID instead of off the distance's most-significant set bit (the §12.6/§14.6 off-by-one) — every routing decision silently wrong. Applied: §3.6, §8.3, §4.1, Phase 2 (§14).
  • MM2 — "Distance is XOR, and XOR is a metric, not a direction." d(a,b)=a⊕b is symmetric and obeys the triangle-like ordering that makes "closer" well-defined; unidirectionality (exactly one y at each distance from x) is what makes the trie clean. Predicts: a node learns useful contacts from everyone who queries it (symmetry), so tables self-organize from ordinary traffic; Chord's clockwise ring lacks this and must stabilize explicitly. Bug without it: treating distance as a signed/directional quantity → asymmetric tables that can't heal from observed traffic. Applied: §3.6, §8.2 (axioms, I2), Phase 0 (§12 metric).
  • MM3 — "Consistent hashing: a key is owned by its closest node, so membership change moves only O(K/N) keys." Keys and nodes share one space; ownership is proximity, not a modulo bucket, so adding/removing a node disturbs only its neighborhood. Predicts: the overlay scales without global reshuffling; the cost of a join/leave is local. Bug without it: a hash-mod-N placement → every node's keys move on any membership change → churn becomes catastrophic. Applied: §2.5, §4.3, Phase 4 (§16 ownership); foundation cited via Karger et al. 1997 (§5.2 paper 5) and #402.
  • MM4 — "Routing tables are a probability distribution over a churning population, never a fact." At any instant some fraction of contacts are dead; correctness is bought by redundancy (k per bucket) + parallelism (α) + the metric's tolerance of staleness. Predicts: a lookup succeeds despite stale entries because α backups absorb dead hops and XOR still points roughly right. Bug without it: a single exact pointer per level (naive Chord, no successor list) → one dead contact breaks routing → lost lookups under churn. Applied: §2.7 (the churn wall), §3.5, principle 3, Phase 6 (§18).
  • MM5 — "Availability is 1−(1−p)^k; pick k from a target, don't fold-cargo-cult 20." Each replica is an independent (or correlated) coin; loss requires all k dead before republish. Predicts: k=20 buys ~6 nines at 50 % loss, k=8 only ~2.5 nines, k=3 fails (87 %) — and that republish must beat the churn timescale or the math is a lie. Bug without it: a single copy (loses data the instant the owner leaves) or a k chosen by folklore that misses the availability SLO. Applied: §4.2, Phase 4 (§16 replication, I9), Phase 6 (§18 republish/repair).
  • MM6 — "Without a trusted identity authority, identity is free, so Sybil/eclipse are costed, never closed (Douceur)." Cheap IDs defeat any pure-redundancy scheme; defenses raise the adversary's required fraction f but can never reach f=1 impossible. Predicts: every security claim is a probability vs f, not a guarantee; honest mitigation states the residual risk. Bug without it: assuming an honest majority or that one defense (a distance check) suffices → a positioned Sybil swarm eclipses a target. Applied: §8.14, principle 7, §26.3 (residual risk), Phase 9 (§21); foundation Douceur 2002 (§5.2 paper 11).
  • MM7 — "Iterative + α-parallel turns latency and lies into a min over α, not a single point of failure." The originator drives and advances on the fastest of α responses, so a slow/dead/lying hop costs at most one parallel slot, not the whole lookup. Predicts: tail latency ≈ the α-th-order-statistic minimum per hop; lie-detection is possible because the originator sees every intermediate result. Bug without it: recursive-only, α=1 routing → one slow node stalls the lookup; the originator is blind to who lied. Applied: §3.5, §4.5, principle 5, Phase 3 (§15 lookup).
  • MM8 — "Maintenance is a steady-state rate, not a one-shot setup cost." Buckets refresh, values republish, Chord stabilizes — forever; the bandwidth of just staying correct is O(log N) refresh + O(V·k) republish per node. Predicts: a value-heavy node's dominant cost is republish, and shortening the interval trades bandwidth for availability; a leaner table (Chord) costs more maintenance, not less, because single pointers rot faster. Bug without it: treating join/repair as one-time → the table rots, success-under-churn silently decays. Applied: §4.4, Phase 6 (§18), Phase 7 (§19 stabilization).
  • MM9 — "Every inbound byte is hostile until framed, versioned, and length-checked." The network is the trust boundary; a FIND_NODE from a stranger can be malformed, oversized, lying, or a replay. Predicts: the parser is the highest-severity surface (a bug there is remote UB from any peer), and validation must precede any use of the bytes. Bug without it: a buffer over-read on an untrusted length, or trusting a returned contact's claimed distance → crash or table poisoning. Applied: §3.3, principle 6, I11, Phase 1 (§13 RPC), fuzzed in Phase 13 (§25).
  • MM10 — "If you can't compute the right answer centrally, you can't tell whether the distributed one is correct." The brute-force true_closest oracle over full membership is the trusted ground truth every lookup is differentially checked against. Predicts: without it, "did the lookup find the right nodes?" is unanswerable and distributed bugs ship; with it, every convergence/termination bug is caught deterministically. Bug without it: self-consistency-only testing that passes while routing is subtly wrong. Applied: principle 14, I3, Phase 0 (§12 oracle), the backbone of Phase 13 (§25).

36. Back-of-Envelope Capacity Model

The numbers an expert computes from the System Constraints (§4) before designing. Each derived step-by-step with the formula shown — no asserted-only numbers.

  1. Routing-table size (Kademlia). Formula: contacts ≈ k · log₂N. From §4 (k=20) at N=10^6 (≈2^20): 20 × 20 = 400 contacts. At ~56 B/NodeInfo (32-B id + 18-B IPv6 socket + ~6-B timing) → 400 × 56 ≈ 22 KB of routing state per node. Why it matters: confirms §4's "O(log N) state, tens of KB" — routing is never the memory bottleneck.
  2. Lookup hop count. Formula: hops ≈ log_{2^b}N; Kademlia b=1 → log₂N. From §4 at N=10^6 → ≈20 hops; at N=10^3 → ≈10. Pastry b=4 → log₁₆(10^6) ≈ 5. Why it matters: the §4 hop target is log₂N, not a constant — the bench asserts the distribution tracks it (I1, §4.1).
  3. Messages per lookup. Formula: RPCs ≈ α · hops · c (c ≈ 1.2 convergence factor). From §4 (α=3) at N=10^6 → 3 × 20 × 1.2 ≈ 72 RPCs per lookup; a disjoint security lookup (d=3, §8.14) multiplies by d → ≈216. Why it matters: sizes the per-lookup network budget and the §33 message-volume scaling (O(α·log N)).
  4. Lookup latency. Formula: latency ≈ hops · RTT_eff, RTT_eff = α-th-order-statistic min of per-hop RTT. From §4 (RTT tens-to-hundreds ms) at N=10^6, RTT≈100 ms, α-min≈60 ms → 20 × 60 ms ≈ 1.2 s. Why it matters: shows lookups are RTT-bound (§4) and that α buys a RTT→RTT_eff reduction, not fewer hops (§4.5).
  5. Per-value availability. Formula: A = 1 − (1−p)^k. From §4 (k=20) at p=0.5 survival/republish-interval → 1 − 0.5^20 = 1 − 9.5×10⁻⁷ ≈ 99.9999 %. At k=8 → 1 − 0.5^8 = 99.6 %. Why it matters: derives the §4 "≥99 % at 50 % simultaneous failure" target and ADR-8's k choice (§4.2).
  6. Storage per node. Formula: bytes ≈ (total_keys / N) · k · value_size. For a 10^6-node overlay holding 10^8 small values (≈256 B peer-lists), k=20 → (10^8/10^6) × 20 × 256 B = 100 × 20 × 256 ≈ 512 KB/node. Why it matters: small DHT values are the design point (§4); a storage-DHT product (large blobs) would blow this up → persistent LSM deferred (§39).
  7. Republish bandwidth (steady state). Formula: BW ≈ (V · k · value_size) / t_republish. From §4 (t_republish=1h) for V=100 values/node, k=20, 256 B → (100 × 20 × 256 B)/3600 s ≈ 142 B/s ≈ 1.1 kbit/s/node. Why it matters: confirms §4.4 "republish dominates but stays bounded"; halving t_republish doubles this for more availability (§4.4 tradeoff).
  8. Refresh bandwidth (steady state). Formula: BW ≈ (log₂N · RPCs_per_refresh · msg_size) / t_refresh. From §4 (t_refresh=1h) at N=10^6, ~72 RPCs/refresh-lookup, ~100 B → (20 × 72 × 100 B)/3600 s ≈ 40 B/s. Why it matters: refresh is negligible vs republish (§4.4) — ordinary traffic refreshes most buckets for free.
  9. Failure-detection latency. Formula: t_detect = max_retries · rpc_timeout. From §4 (3 × 1 s) → 3 s worst-case to declare a contact dead. Why it matters: bounds the staleness window and the repair-trigger lag (§4, I10); shorter raises false positives under transient loss (§18.6 FLP ambiguity).
  10. FD / socket budget. Formula: one UDP socket + bounded TCP-fallback connections + ≤ α·in-flight-lookups outstanding. From §4 (α=3) with, say, 50 concurrent lookups → 1 UDP + ~150 logical in-flight RPCs (multiplexed on one socket by txn-id) + a small TCP pool. Why it matters: UDP multiplexing means the FD budget is ~constant, not O(peers) — the §3.5 correlation-table design, not a connection per peer.
  11. Join cost. Formula: RPCs ≈ (1 self-lookup) + (refreshed buckets) ≈ α·log₂N + log₂N·(α·c). At N=10^6 → 72 + ~20×3.6 ≈ 144 RPCs, completing in ≈ 2 hops-worth of serial rounds × RTT_eff → well under the §4 "< 5 s to usable table" target (§8.15, §4).
  12. Eclipse adversary fraction. Formula (S/Kademlia intuition): to eclipse a target with disjoint-lookup parameter d and bucket-diversity quota D, the adversary must control all d disjoint paths → capture probability ≈ f^d for adversary fraction f of well-positioned IDs. From §8.14 at f=0.3, d=3 → 0.3^3 ≈ 2.7 %; at d=1 (no disjoint paths) → 30 %. Why it matters: quantifies the §26.3 residual risk and the disjoint-lookup payoff (§8.14, Phase 9 §21) — and shows f→1 is never reachable (MM6).

Fundamentally different designs for the same "decentralized key→node/value lookup" problem (not parameter tweaks). Each: sketch, the regime where it wins, the real system that embodies it, why this blueprint rejected it.

Alt-1 — Unstructured gossip / flooding overlay (the #72 model).

        ┌──peer──┐      flood/random-walk a query
   peer─┤  P  ├─peer    with a TTL; no ID-based structure;
        └──peer──┘      membership is a random partial view
   lookup(k): ask neighbors → they ask theirs (TTL hops) → maybe hit
  • Regime where it wins: disseminating to all nodes, or searching for popular items where any-copy-will-do; inherently churn-robust (no structure to repair); keyword/partial-match search that a DHT's exact-key model can't express.
  • Real system: Gnutella (flooding), and gossip/epidemic membership as in Birman's work (§5.1 book 6) and #72.
  • Why rejected here: the DHT's job is exact key→node/value lookup (find this content hash, this peer-list); flooding gives no guarantee a rare item is found and costs O(N) traffic — defeats the whole O(log N) point (principle 1, §8.13). We borrow gossip's maintenance epidemic idea (§18) but not its routing.

Alt-2 — d-dimensional coordinate space (CAN torus).

   ┌───┬───┬───┐   keys + nodes are points in a d-dim torus;
   │   │ ● │   │   each node owns a zone; routing = greedy walk
   ├───┼───┼───┤   toward the target coordinate via 2d neighbors
   │ ● │   │ ● │   hops ≈ (d/4)·N^(1/d); state = O(d), N-independent
   └───┴───┴───┘
  • Regime where it wins: when per-node state must be a small constant (2d) regardless of N, or when the key/locality model is genuinely multi-dimensional (geographic, multi-attribute range queries); zone-based ownership makes range-ish queries natural.
  • Real system: CAN (Ratnasamy et al., SIGCOMM 2001, §5.2 paper 4).
  • Why rejected here: O(N^{1/d}) hops is worse than O(log N) unless d ≈ log N — at which point it converges to the trie/ring designs but with messier zone-maintenance under churn; the XOR trie gives O(log N) with self-organizing tables and no zone-split/merge bookkeeping (§4.3, §35).

Alt-3 — One-hop / O(1) DHT with full membership replication.

   every node holds the WHOLE membership table (all N nodes);
   lookup(k) = local computation of successor(k) → ONE hop to the owner
   maintenance = a hierarchical event-dissemination tree keeps tables current
  • Regime where it wins: lookup latency must be a single hop (latency-critical, e.g. a financial or ad-serving locator) and the membership is large-but-not-huge with affordable bandwidth to flood membership changes; trades maintenance bandwidth for zero-hop lookups.
  • Real system: the one-hop DHT design of Gupta, Liskov & Rodrigues (and the "Structured Superpeers"/EpiChord family of low-hop DHTs).
  • Why rejected here: full-membership replication costs O(N) state per node and O(N · churn_rate) dissemination bandwidth — it does not scale to the 10^6-node, high-churn target (§4), and the whole pedagogical point is the O(log N) routing argument, not buying it away with bandwidth (principle 1, §33).

Alt-4 — Centralized / hierarchical tracker (the registry model).

   clients ───lookup(k)───► [ central tracker / coordinator cluster ]
                            holds key→node mapping authoritatively
  • Regime where it wins: a closed/operated environment where a small team runs the infrastructure, strong consistency and instant lookups matter, and decentralization is not a requirement — a service registry or a torrent tracker.
  • Real system: the original BitTorrent tracker (pre-DHT), and service registries (compare #359).
  • Why rejected here: a coordinator is a single point of failure, a scaling wall, and a censorship/control point — the exact properties the DHT exists to eliminate; the Mainline DHT was created precisely to make BitTorrent trackerless (§2.2, §33). This blueprint is the decentralized substrate, not the registry it replaces.

40. Glossary

  • DHT (Distributed Hash Table): a decentralized key→value store + key→node lookup over a structured overlay; no central coordinator.
  • Structured overlay: a P2P network whose topology is determined by node IDs + a metric (vs unstructured/random, #72), giving O(log N) key-based routing.
  • Key-based routing (KBR): routing a message toward the node responsible for a key, in O(log N) hops, via a routing table of O(log N) contacts.
  • Kademlia: the locked design — XOR distance metric, k-buckets, α-parallel iterative lookup; the BitTorrent-DHT/IPFS lineage.
  • XOR metric: distance d(a,b)=a⊕b; symmetric + unidirectional → self-organizing k-buckets that learn from all traffic.
  • k-bucket: a Kademlia routing-table slot for one distance range (bit prefix), holding ≤ k contacts, LRU-evicting preferring live-old over fresh-new (I4).
  • k (replication / bucket factor): 20 (Kademlia default) — the bucket size and the replica count (the closest bucket is the replica set).
  • α (alpha): the lookup parallelism — concurrent outstanding RPCs per lookup (default 3); hides slow/dead hops (§4.5).
  • Iterative lookup: the originator drives, querying α nodes at a time and steering the walk (vs recursive, where nodes forward); Kademlia's default (principle 5).
  • Shortlist: the bounded sorted set of the k closest known nodes to a lookup's target, plus the queried set; the lookup's working state.
  • Convergence (lookup): the termination condition — the k closest known nodes are all queried and no response yielded anything closer (I7).
  • Responsible set: the k nodes closest to a key under the metric — the nodes that store its value and answer its lookups.
  • Chord: a compared scheme — ring + consistent hashing + finger table + successor list + stabilization; asymmetric, leaner table, churn-fragile without the successor list.
  • Finger table: Chord's routing table — finger[i]=successor(n+2^i), exponentially-spaced shortcuts for O(log N) routing.
  • Successor list: Chord's r following nodes — fault tolerance against a successor's failure (mandatory under churn, principle 3).
  • Stabilization: Chord's periodic churn-repair protocol (stabilize/notify/fix_fingers/check_predecessor, I6).
  • Pastry: a compared scheme — prefix routing + leaf set (numerically closest) + neighborhood set (proximity); O(log_{2^b}N) hops.
  • Leaf set: Pastry's set of numerically-closest nodes — determines the final routing hop + key ownership.
  • Consistent hashing: mapping keys + nodes into one space so each key is owned by its closest node; minimizes key movement under membership change (#402 lineage).
  • Churn: continuous node join/leave; the defining P2P problem (§2.7) — the overlay must stay correct + available under churn, not just in a static network.
  • Republish: periodically re-STOREing a value to its current closest-k so it survives churn (the closest set shifts); default 1 h.
  • Expiry / TTL: values are dropped after t_expire (24 h default) unless republished — bounds storage.
  • Repair / re-replication: restoring a value's replica count to k after a replica leaves (under-replication detection → re-STORE, I9).
  • Bootstrap node: a well-known entry point a joining node contacts first; used once at join, never on the data path; multiple removes the SPOF.
  • Self-lookup: a joining node's find_node(my_id) — populates its k-buckets with its neighborhood + makes it known to neighbors (§8.15).
  • Sybil attack: minting many cheap identities to gain disproportionate overlay influence; mitigated (ID cost + diversity), not eliminated (Douceur).
  • Eclipse attack: an adversary surrounding a target in its routing table to control its overlay view; mitigated by diversity + disjoint lookups (S/Kademlia).
  • S/Kademlia: Sybil-resistant Kademlia — crypto-puzzle node IDs + disjoint parallel lookups over node-disjoint paths.
  • Disjoint lookup: running d independent lookups over non-overlapping node paths; the adversary must control all d to eclipse (P9).
  • Write token (BEP-5): a value echoed from a prior reply that a STORE must include, preventing spoofed-source stores (§8.8).
  • Iterative vs recursive: who drives the lookup — the originator (iterative, parallelizable, lie-detecting) vs each forwarding node (recursive, fewer round-trips, blind).
  • Hole punching: a NAT-traversal handshake — two NAT'd peers send simultaneous datagrams (coordinated by a rendezvous) to open a path (cone NATs).
  • Relay (TURN-like): a third reachable node forwarding traffic between two unreachable peers — the NAT fallback (production deferred).
  • Simulation oracle (true_closest): the centralized, brute-force, authoritative computation of a key's true k-closest set from full membership — the ground truth every lookup is checked against (I3, principle 14).
  • Soft state: routing tables, reconstructed by re-bootstrapping after a restart (not persisted); vs the value store (persisted-ish).
  • Last-writer-wins (LWW): mutable-value conflict resolution by the highest seq — eventual consistency, no global ordering (§8.12).
  • RoutingScheme: the trait abstracting Kademlia/Chord/Pastry behind one interface so the lookup engine + harness are scheme-agnostic (ADR-4).
  • Transaction id (txn-id): the random per-RPC identifier correlating a response to its request; an unmatched/late response is dropped (I11).
  • NodeInfo: the routing-table/shortlist entry — {id, addr, last_seen, rtt}.
