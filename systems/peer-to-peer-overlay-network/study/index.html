Hard questions (§37)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does Kademlia's table need k·log N contacts while Chord needs only log N, and why does the larger table make the system cheaper to maintain under churn? (Synthesize §4.3 + §4.4 + MM8 §34.)
  2. Derive the O(log N) hop bound from the XOR metric without citing the constant — show why only ~log₂N of the 256 prefix levels are populated and why each hop fixes ≥1 high-order bit. (Synthesize §3.6 + §4.1 + §8.3.)
  3. Choose k for a "≥99.9 % availability at 40 % simultaneous loss with republish=2h" target, and explain why the answer also depends on whether failures are independent or correlated. (Synthesize §4.2 + §36 #5/#7 + §18.)
  4. Why is find_value required to still return closer nodes on a miss, and what breaks in the lookup state machine if it returns only "not found" at the first miss? (Synthesize §8.7 + §15 + §16.6.)
  5. Explain why holding the routing-table lock across a network .await is the single highest-impact performance bug, and trace exactly which subsystems stall when it happens. (Synthesize principle 9 §6 + §3.5 + §24.6.)
  6. Reconstruct the convergence/termination predicate (I7) and explain both failure modes — stopping too early and never stopping — and which fixture catches each. (Synthesize §8.11 + §15.6 + §11.5.)
  7. Why does preferring live-old contacts over fresh-new ones (the k-bucket eviction trick) actually help under churn, and on what empirical property of session lengths does that argument rest? (Synthesize §8.3 + ADR-13 §9 + Stutzbach & Rejaie §5.2 paper 13.)
  8. Walk a value's life from store through the closest-k set shifting under churn to a later get from a different node — naming every mechanism that keeps it available. (Synthesize §3.4 + §8.7 + §18.2 + I9.)
  9. Why is Sybil resistance fundamentally mitigation rather than prevention, and what single assumption would have to change to make it prevention? (Synthesize §8.14 + §26.3 + MM6 §34 + ADR-16 §9.)
  10. Contrast iterative-α-parallel and recursive routing on four axes — tail latency, lie-detection, originator round-trips, and parallelism — and state the regime where recursive wins. (Synthesize §8.6 + principle 5 §6 + ADR-7 §9 + §35.)
  11. Explain how disjoint parallel lookups convert an eclipse from "control a few well-placed nodes" into "control all d paths," and compute the adversary's capture probability as a function of d. (Synthesize §8.14 + §36 #12 + §21.2.)
  12. Why does the system tolerate a routing table that is never fully correct, and which three mechanisms jointly substitute for exactness? (Synthesize §2.7 + MM4 §34 + §3.5 + principle 3 §6.)
  13. Trace what a single malformed FIND_NODE datagram can and cannot do to a node, and name every defense layer it must pass. (Synthesize §3.3 + I11 §7 + §13.2 + MM9 §34.)
  14. Why is the centralized oracle "obviously correct" by construction, and why would a clever oracle be a liability rather than an asset? (Synthesize principle 14 §6 + §11.9 + §25.6 + I3.)
  15. Explain why republish must target the current closest-k rather than the original set, and what failure appears if it doesn't. (Synthesize §8.7 + §18.6 + I9 + MM3 §34.)
  16. Why does Chord need a successor list and not just a successor pointer, and how does the journal-version (ToN 2003) fault-tolerance argument formalize this? (Synthesize §8.4 + §19.6 + §5.2 paper 6 + principle 3.)
  17. Derive the steady-state maintenance bandwidth for a value-heavy node and explain why it does not grow super-linearly with N. (Synthesize §4.4 + §36 #7/#8 + §33.)
  18. Why is α=3 the sweet spot rather than α=1 or α=10 — quantify the latency, robustness, and message-overhead tradeoffs across the three. (Synthesize §4.5 + ADR-7 §9 + §24.2.)
  19. Explain how the value store can be eventually consistent for mutable keys yet strongly consistent for content-addressed keys, and what reconciliation is deferred. (Synthesize §8.12 + ADR-14 §9 + §39 + #71 lineage.)
  20. Why does the design have no central bottleneck on the data path, and what is the only semi-central element — and how is its single-point-of-failure removed? (Synthesize §3.3 + §8.15 + §33 + ADR-21 §9.)
  21. Walk the full failure-and-recovery path for "a get misses a value that should exist," naming detection, auto-recovery, and the forensic artifacts. (Synthesize §27 + §18.9 + I9 + §16.9.)
  22. Why is NAT traversal partly deferred, what is shipped, and what real-world gap does the simulation not close? (Synthesize §22 + §1.7 + §39 + ADR-18 §9.)

34. Mental Models & First Principles

The compressed insights an expert holds before touching the code. Each: the model, what it predicts, the bug class you write without it, and the resolving § where this blueprint applies it.

  • MM1 — "An ID is a point; routing is descent through a binary trie." The 256-bit ID space is a complete binary tree; a node's neighbors are leaves, and bucket i is the subtree you'd reach by flipping bit i of your own prefix. Predicts: each correct hop fixes ≥1 high-order bit, so lookups take ~log₂N hops (only the populated top ~log₂N levels matter, not all 256). Bug without it: indexing buckets off the raw ID instead of off the distance's most-significant set bit (the §12.6/§14.6 off-by-one) — every routing decision silently wrong. Applied: §3.6, §8.3, §4.1, Phase 2 (§14).
  • MM2 — "Distance is XOR, and XOR is a metric, not a direction." d(a,b)=a⊕b is symmetric and obeys the triangle-like ordering that makes "closer" well-defined; unidirectionality (exactly one y at each distance from x) is what makes the trie clean. Predicts: a node learns useful contacts from everyone who queries it (symmetry), so tables self-organize from ordinary traffic; Chord's clockwise ring lacks this and must stabilize explicitly. Bug without it: treating distance as a signed/directional quantity → asymmetric tables that can't heal from observed traffic. Applied: §3.6, §8.2 (axioms, I2), Phase 0 (§12 metric).
  • MM3 — "Consistent hashing: a key is owned by its closest node, so membership change moves only O(K/N) keys." Keys and nodes share one space; ownership is proximity, not a modulo bucket, so adding/removing a node disturbs only its neighborhood. Predicts: the overlay scales without global reshuffling; the cost of a join/leave is local. Bug without it: a hash-mod-N placement → every node's keys move on any membership change → churn becomes catastrophic. Applied: §2.5, §4.3, Phase 4 (§16 ownership); foundation cited via Karger et al. 1997 (§5.2 paper 5) and #402.
  • MM4 — "Routing tables are a probability distribution over a churning population, never a fact." At any instant some fraction of contacts are dead; correctness is bought by redundancy (k per bucket) + parallelism (α) + the metric's tolerance of staleness. Predicts: a lookup succeeds despite stale entries because α backups absorb dead hops and XOR still points roughly right. Bug without it: a single exact pointer per level (naive Chord, no successor list) → one dead contact breaks routing → lost lookups under churn. Applied: §2.7 (the churn wall), §3.5, principle 3, Phase 6 (§18).
  • MM5 — "Availability is 1−(1−p)^k; pick k from a target, don't fold-cargo-cult 20." Each replica is an independent (or correlated) coin; loss requires all k dead before republish. Predicts: k=20 buys ~6 nines at 50 % loss, k=8 only ~2.5 nines, k=3 fails (87 %) — and that republish must beat the churn timescale or the math is a lie. Bug without it: a single copy (loses data the instant the owner leaves) or a k chosen by folklore that misses the availability SLO. Applied: §4.2, Phase 4 (§16 replication, I9), Phase 6 (§18 republish/repair).
  • MM6 — "Without a trusted identity authority, identity is free, so Sybil/eclipse are costed, never closed (Douceur)." Cheap IDs defeat any pure-redundancy scheme; defenses raise the adversary's required fraction f but can never reach f=1 impossible. Predicts: every security claim is a probability vs f, not a guarantee; honest mitigation states the residual risk. Bug without it: assuming an honest majority or that one defense (a distance check) suffices → a positioned Sybil swarm eclipses a target. Applied: §8.14, principle 7, §26.3 (residual risk), Phase 9 (§21); foundation Douceur 2002 (§5.2 paper 11).
  • MM7 — "Iterative + α-parallel turns latency and lies into a min over α, not a single point of failure." The originator drives and advances on the fastest of α responses, so a slow/dead/lying hop costs at most one parallel slot, not the whole lookup. Predicts: tail latency ≈ the α-th-order-statistic minimum per hop; lie-detection is possible because the originator sees every intermediate result. Bug without it: recursive-only, α=1 routing → one slow node stalls the lookup; the originator is blind to who lied. Applied: §3.5, §4.5, principle 5, Phase 3 (§15 lookup).
  • MM8 — "Maintenance is a steady-state rate, not a one-shot setup cost." Buckets refresh, values republish, Chord stabilizes — forever; the bandwidth of just staying correct is O(log N) refresh + O(V·k) republish per node. Predicts: a value-heavy node's dominant cost is republish, and shortening the interval trades bandwidth for availability; a leaner table (Chord) costs more maintenance, not less, because single pointers rot faster. Bug without it: treating join/repair as one-time → the table rots, success-under-churn silently decays. Applied: §4.4, Phase 6 (§18), Phase 7 (§19 stabilization).
  • MM9 — "Every inbound byte is hostile until framed, versioned, and length-checked." The network is the trust boundary; a FIND_NODE from a stranger can be malformed, oversized, lying, or a replay. Predicts: the parser is the highest-severity surface (a bug there is remote UB from any peer), and validation must precede any use of the bytes. Bug without it: a buffer over-read on an untrusted length, or trusting a returned contact's claimed distance → crash or table poisoning. Applied: §3.3, principle 6, I11, Phase 1 (§13 RPC), fuzzed in Phase 13 (§25).
  • MM10 — "If you can't compute the right answer centrally, you can't tell whether the distributed one is correct." The brute-force true_closest oracle over full membership is the trusted ground truth every lookup is differentially checked against. Predicts: without it, "did the lookup find the right nodes?" is unanswerable and distributed bugs ship; with it, every convergence/termination bug is caught deterministically. Bug without it: self-consistency-only testing that passes while routing is subtly wrong. Applied: principle 14, I3, Phase 0 (§12 oracle), the backbone of Phase 13 (§25).

  • BitTorrent Mainline DHT (BEP 5) + impls (libtorrent kademlia/, the mainline Rust crate) — the largest deployed Kademlia. Lesson: the wire protocol (bencoded KRPC), the write token for announce_peer, real-world robustness. Applied: §8.8 (wire shape & token), Phase 9 (§21 token), §4/§36 (scale reality). Pitfall: BitTorrent-specific RPCs (get_peers/announce_peer) we generalize to FIND_VALUE/STORE.
  • IPFS / go-libp2p-kad-dht — content + provider routing on Kademlia; the provider-record + republish/reprovide model. Applied: Phase 4 (§16 store/value) & Phase 6 (§18 republish, I9). Pitfall: Go GC + IPFS-specific record types — we ship a generic Value.
  • Chord reference (MIT chord / the i3/Chord codebase) — the original Chord + stabilization. Lesson: finger table + successor list + the stabilization protocol. Applied: Phase 7 (§19, I6). Pitfall: research-grade; brittle under real churn without the successor list — that fragility is the lesson (principle 3).
  • FreePastry — the Pastry reference. Lesson: leaf set + routing table + proximity (neighborhood set). Applied: Phase 8 (§20). Pitfall: Java, dated, complex — we implement only the core prefix-routing + leaf set, proximity basic.
  • Vuze (Azureus) DHT — a long-lived production Kademlia variant. Lesson: practical churn handling, replication, operational reality. Applied: Phase 6 (§18 churn) & §28 (operational readiness). Pitfall: idiosyncratic protocol divergences we don't copy.

Glossary (§40) · 39 terms · site-wide glossary

DHT (Distributed Hash Table):
a decentralized key→value store + key→node lookup over a structured overlay; no central coordinator.
Structured overlay:
a P2P network whose topology is determined by node IDs + a metric (vs unstructured/random, #72), giving O(log N) key-based routing.
Key-based routing (KBR):
routing a message toward the node responsible for a key, in O(log N) hops, via a routing table of O(log N) contacts.
Kademlia:
the locked design — XOR distance metric, k-buckets, α-parallel iterative lookup; the BitTorrent-DHT/IPFS lineage.
XOR metric:
distance d(a,b)=a⊕b; symmetric + unidirectional → self-organizing k-buckets that learn from all traffic.
k-bucket:
a Kademlia routing-table slot for one distance range (bit prefix), holding ≤ k contacts, LRU-evicting preferring live-old over fresh-new (I4).
k (replication / bucket factor):
20 (Kademlia default) — the bucket size and the replica count (the closest bucket is the replica set).
α (alpha):
the lookup parallelism — concurrent outstanding RPCs per lookup (default 3); hides slow/dead hops (§4.5).
Iterative lookup:
the originator drives, querying α nodes at a time and steering the walk (vs recursive, where nodes forward); Kademlia's default (principle 5).
Shortlist:
the bounded sorted set of the k closest known nodes to a lookup's target, plus the queried set; the lookup's working state.
Convergence (lookup):
the termination condition — the k closest known nodes are all queried and no response yielded anything closer (I7).
Responsible set:
the k nodes closest to a key under the metric — the nodes that store its value and answer its lookups.
Chord:
a compared scheme — ring + consistent hashing + finger table + successor list + stabilization; asymmetric, leaner table, churn-fragile without the successor list.
Finger table:
Chord's routing table — finger[i]=successor(n+2^i), exponentially-spaced shortcuts for O(log N) routing.
Successor list:
Chord's r following nodes — fault tolerance against a successor's failure (mandatory under churn, principle 3).
Stabilization:
Chord's periodic churn-repair protocol (stabilize/notify/fix_fingers/check_predecessor, I6).
Pastry:
a compared scheme — prefix routing + leaf set (numerically closest) + neighborhood set (proximity); O(log_{2^b}N) hops.
Leaf set:
Pastry's set of numerically-closest nodes — determines the final routing hop + key ownership.
Consistent hashing:
mapping keys + nodes into one space so each key is owned by its closest node; minimizes key movement under membership change (#402 lineage).
Churn:
continuous node join/leave; the defining P2P problem (§2.7) — the overlay must stay correct + available under churn, not just in a static network.
Republish:
periodically re-STOREing a value to its current closest-k so it survives churn (the closest set shifts); default 1 h.
Expiry / TTL:
values are dropped after t_expire (24 h default) unless republished — bounds storage.
Repair / re-replication:
restoring a value's replica count to k after a replica leaves (under-replication detection → re-STORE, I9).
Bootstrap node:
a well-known entry point a joining node contacts first; used once at join, never on the data path; multiple removes the SPOF.
Self-lookup:
a joining node's find_node(my_id) — populates its k-buckets with its neighborhood + makes it known to neighbors (§8.15).
Sybil attack:
minting many cheap identities to gain disproportionate overlay influence; mitigated (ID cost + diversity), not eliminated (Douceur).
Eclipse attack:
an adversary surrounding a target in its routing table to control its overlay view; mitigated by diversity + disjoint lookups (S/Kademlia).
S/Kademlia:
Sybil-resistant Kademlia — crypto-puzzle node IDs + disjoint parallel lookups over node-disjoint paths.
Disjoint lookup:
running d independent lookups over non-overlapping node paths; the adversary must control all d to eclipse (P9).
Write token (BEP-5):
a value echoed from a prior reply that a STORE must include, preventing spoofed-source stores (§8.8).
Iterative vs recursive:
who drives the lookup — the originator (iterative, parallelizable, lie-detecting) vs each forwarding node (recursive, fewer round-trips, blind).
Hole punching:
a NAT-traversal handshake — two NAT'd peers send simultaneous datagrams (coordinated by a rendezvous) to open a path (cone NATs).
Relay (TURN-like):
a third reachable node forwarding traffic between two unreachable peers — the NAT fallback (production deferred).
Simulation oracle (true_closest):
the centralized, brute-force, authoritative computation of a key's true k-closest set from full membership — the ground truth every lookup is checked against (I3, principle 14).
Soft state:
routing tables, reconstructed by re-bootstrapping after a restart (not persisted); vs the value store (persisted-ish).
Last-writer-wins (LWW):
mutable-value conflict resolution by the highest seq — eventual consistency, no global ordering (§8.12).
RoutingScheme:
the trait abstracting Kademlia/Chord/Pastry behind one interface so the lookup engine + harness are scheme-agnostic (ADR-4).
Transaction id (txn-id):
the random per-RPC identifier correlating a response to its request; an unmatched/late response is dropped (I11).
NodeInfo:
the routing-table/shortlist entry — {id, addr, last_seen, rtt}.
