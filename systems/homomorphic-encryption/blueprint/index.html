1. Goal & Scope

1.1 Precise Engineering Scope

Build, from scratch in Rust, two homomorphic encryption (HE) schemes sharing a common cryptographic substrate:

  1. Paillier — a partially homomorphic public-key cryptosystem. Plaintexts are integers mod n; ciphertexts live in Z_{n²}*. Additively homomorphic: Dec(E(a)·E(b) mod n²) = a + b mod n; supports plaintext-scalar multiply Dec(E(a)^k) = k·a. Security rests on the Decisional Composite Residuosity Assumption (DCRA). Exact, unbounded number of additions.

  2. BFV-lite — a leveled / somewhat fully homomorphic scheme over the polynomial ring R_q = Z_q[x]/(x^n + 1) (n a power of two). Supports homomorphic addition and a bounded number of homomorphic multiplications (multiplicative depth L) before the accumulated noise destroys the plaintext. Multiplication uses tensoring followed by relinearization (key switching); depth is extended by modulus switching and tracked by an explicit noise budget. Security rests on Ring-LWE (RLWE).

The substrate underneath both: a vetted big-integer layer (modexp, modular inverse, GCD, CRT, Montgomery/Barrett reduction), a number-theory layer (Miller–Rabin primality, safe-prime generation, CSPRNG sampling), and — for BFV only — a polynomial / lattice layer (R_q arithmetic, the Number-Theoretic Transform (NTT) for O(n log n) negacyclic multiplication, RNS/CRT representation across small moduli, discrete-Gaussian / uniform / ternary sampling).

The contract is educational-grade correctness with documented constant-time intent: every homomorphic property holds within a stated noise budget and is validated against analytic identities and an external reference (python-paillier; Microsoft SEAL BFV test vectors). Cryptographic randomness comes from a CSPRNG; test vectors are reproducible under a fixed seed in a --insecure-deterministic test mode only. This is NOT an audited or production secrets system — it is a from-scratch learning implementation of HE internals.

1.3 Non-Goals

  • No bootstrapping (noise refresh to unlimited depth) — PhaseDeferred("FINAL_BLUEPRINT §Phase 13"). BFV-lite is leveled/somewhat-FHE only.
  • No CKKS (approximate arithmetic on reals/complex) — PhaseDeferred("FINAL_BLUEPRINT §Phase 9").
  • No production hardening / audit. Constant-time is a documented goal with targeted measures, not a certified guarantee.
  • No threshold or distributed key generation for Paillier or BFV.
  • No GPU/accelerator path; CPU only — PhaseDeferred("FINAL_BLUEPRINT §Phase 12").
  • No arbitrary cyclotomic rings; only x^n + 1, n a power of two (negacyclic NTT).
  • No general-purpose bignum library beyond the cryptographic primitives needed (or a single vetted dependency with rationale, ADR 2).
  • No TFHE / gate-bootstrapping, no fully-dynamic FHE compiler.
  • No network protocol; library + CLI; ciphertexts are files/blobs, not a wire service.

1.4 Intended Deployment Model

  • Library crates consumed by Rust code: generate keys, encrypt plaintexts, evaluate a homomorphic circuit (add/mul/scale), decrypt.
  • CLI tool (he-cli): paillier keygen --bits 2048; paillier enc --pk pk.json 42; paillier add c1 c2; bfv params --depth 3 --sec 128; bfv keygen; bfv eval circuit.json; bfv noise c.ct (print remaining noise budget).
  • Single process, single host. Heavy kernels (NTT, RNS conversion, poly-mul) optionally multithreaded within a host (rayon). No network surface; inputs (plaintexts, circuit descriptions) are trusted as data, not executed.

1.6 Phase 0 Deliverable — Locked Crates

Public API signatures locked before implementation. Twelve crates under a Cargo workspace:

  1. he-bignum — big-integer modular arithmetic: modexp, modinv (extended GCD), gcd/lcm, CRT combine, Montgomery & Barrett reduction contexts; or a thin wrapper over a vetted bignum dep (ADR 2). Constant-time variants for secret-dependent paths.
  2. he-numtheory — primality (Miller–Rabin, Baillie–PSW optional), safe-prime generation (p, (p−1)/2 prime), random Z_n* / coprime sampling, Jacobi symbol, L-function helper for Paillier.
  3. he-rng — CSPRNG abstraction (getrandom→ChaCha20), rejection sampling for uniform ranges, discrete Gaussian sampler (CDT / Karney), ternary sampler; --insecure-deterministic seeded mode for tests.
  4. he-paillier — keygen (n=pq, λ, μ), encrypt (g^m r^n mod n²), decrypt (L-function), hom-add (ct-mul), plaintext-mul (ct-exp), re-randomization, plaintext encode/decode (signed via n/2 split).
  5. he-ring — polynomial ring R_q = Z_q[x]/(x^n+1): coefficient Poly type, add/sub/negacyclic-mul (schoolbook fallback), modular coeff reduction, sampling into R_q.
  6. he-ntt — negacyclic NTT/INTT: primitive 2n-th root tables, forward/inverse transform, pointwise multiply, Montgomery butterflies; round-trip identity INTT∘NTT = id.
  7. he-rns — RNS/CRT representation: ciphertext modulus q = Πqᵢ of NTT-friendly primes, per-residue arithmetic, base conversion (fast/approximate + exact), RnsContext.
  8. he-bfv — BFV scheme bound to BfvParams (ring degree n, modulus chain, plaintext modulus t): SK/PK keygen, relinearization & Galois keys, encrypt, decrypt, add, mul (tensor→relin), mod-switch.
  9. he-noise — noise model: per-operation noise growth bounds, noise budget estimate (bits remaining), invariant-mul/-add accounting, abort-before-exhaustion guard.
  10. he-params — parameter selection: choose (n, q, t, σ) for a target multiplicative depth L and security level λ_sec (128/192/256); reference the LWE estimator's published tables; validate against attack cost.
  11. he-encode — encoding layer: integer encode/decode, batch (CRT slots via t ≡ 1 mod 2n), scalar encode; CKKS-style fixed-point explicitly deferred.
  12. he-cli — paillier {keygen,enc,dec,add,mul} + bfv {params,keygen,enc,dec,eval,noise} subcommands; JSON key/ciphertext I/O, circuit descriptions.

1.10 Language Selection — Rust

HE is two performance- and correctness-critical kernels stacked on big-integer and modular arithmetic: Paillier is dominated by modular exponentiation in Z_{n²}, BFV by the NTT and RNS base conversion over polynomials of degree n = 4096…32768. Both are the project. Rust gives: exact control of memory layout (Vec<u64> coefficient/residue arrays, contiguous, cache-friendly), zero-cost abstractions for the butterfly and CRT index arithmetic, exhaustive enums (ciphertext kind, key kind, error) that make match-completeness a compile-time guarantee, fearless data-parallelism (rayon) over independent RNS limbs and NTT strata, no GC pauses on the hot loop, and a strong story for constant-time secret-dependent code (subtle crate, no secret-dependent branches/indexing). crypto-bigint / num-bigint supply vetted big-integer primitives (ADR 2) so the cryptographic logic — not a from-scratch general bignum — is the deliverable. Python rejected: the NTT/poly-mul/RNS kernels are the point and interpreter overhead forces a C extension, defeating "from scratch"; also weak constant-time guarantees. C++ rejected for memory-safety and tooling friction at equal performance; Go rejected for GC pauses and weaker generic/SIMD ergonomics. All twelve crates are Rust.

2. Why Build This

2.1 Unique Systems Knowledge Taught

  • Why homomorphism is a ring homomorphism: Paillier maps plaintext addition to ciphertext multiplication (E(a)·E(b)=E(a+b)), and how g^m r^n mod n² plus the L-function L(x)=(x−1)/n invert each other.
  • Why RLWE ciphertexts are noisy and every homomorphic operation grows that noise — multiplication multiplicatively — so FHE without bootstrapping is leveled: a finite depth budget you spend.
  • Why the NTT (not the FFT) is the right transform: exact integer arithmetic mod a prime, no floating-point error, O(n log n) negacyclic convolution that makes poly-mul (the BFV bottleneck) fast.
  • Why ciphertexts are stored in RNS across many small NTT-friendly primes: a single huge modulus q (hundreds of bits) is split into machine-word residues so every coefficient op is a native u64 multiply.
  • How relinearization turns a quadratic (3-component) ciphertext back into a linear (2-component) one using an encrypted version of s² — key switching — and why this is where most of FHE's engineering lives.
  • How parameter selection is a security↔depth↔performance trilemma: bigger q buys depth but lowers security (must grow n), and the LWE estimator quantifies it.
  • Why constant-time matters: a decryption whose timing depends on the secret key leaks it; secret-dependent branches/table lookups are vulnerabilities.

2.2 Historical and Architectural Significance

Rivest, Adleman, Dertouzos (1978) posed "privacy homomorphisms"; Paillier (1999) delivered a clean additively-homomorphic scheme still used in private voting, aggregation, and federated learning. Gentry (2009) proved fully homomorphic encryption possible via bootstrapping — arbitrary computation on encrypted data — launching a field. BFV (Brakerski 2012; Fan–Vercauteren 2012) is a practical RLWE leveled scheme implemented in Microsoft SEAL, PALISADE/OpenFHE, and Lattigo. Rebuilding Paillier and BFV-lite from scratch demystifies "compute on encrypted data" into concrete algebra: modular exponentiation for PHE, and noisy ring elements + NTT + relinearization for SHE/FHE. It also grounds post-quantum lattice cryptography (the same RLWE that underlies Kyber/Dilithium).

2.3 Engineering Muscles Developed

  • Big-integer and modular-arithmetic kernels (Montgomery/Barrett) and their testing.
  • The NTT butterfly and bit-reversal — the modular cousin of the FFT.
  • RNS/CRT representation and base conversion (the subtle correctness trap of FHE).
  • Reasoning about and measuring noise growth; turning a probabilistic bound into an operational budget.
  • Constant-time programming discipline for secret-dependent code paths.
  • Security parameter selection from published attack-cost tables.

2.4 Production Engineering Concepts Exercised

  • Invariants under approximate arithmetic (noise budget monotone, abort before exhaustion).
  • Determinism vs cryptographic randomness (seeded test mode strictly separated from real keygen).
  • Observability: noise-budget telemetry per op, ciphertext size, modulus-chain level, op counts.
  • Conformance against analytic identities and a reference implementation as the trust gate.
  • Fail-loud on parameter/security violations, depth overflow, malformed ciphertexts.
  • Supply-chain care for cryptographic dependencies (pinned, audited).

2.6 Calibration Value

After this project, "homomorphic encryption" becomes a transparent pipeline: for Paillier, modular exponentiation in Z_{n²} with the L-function as the trapdoor; for BFV, encode → noisy RLWE ciphertext → NTT-accelerated poly-mul → relinearize → mod-switch → decrypt-within-budget. The engineer can predict why depth is finite, why ciphertexts are megabytes, why the NTT dominates the profile, and can reason about IND-CPA and parameter security rather than treating HE as a black box.

2.7 What Mastery Looks Like

  • Implement Montgomery and Barrett reduction from Montgomery (1985) / HAC Ch 14 and state precisely when each wins (fixed vs varying modulus) — Phase 1.
  • Generate safe primes, bound Miller–Rabin error (≤ 4⁻ᵏ), and explain why ROCA-class keygen shortcuts (CVE-2017-15361) destroy security without any functional bug — Phase 2.
  • Derive the full Paillier scheme from (n+1)^m = 1+mn mod n² and prove its homomorphic identities (I4) on paper before running them — Phase 3.
  • Build a negacyclic NTT from root selection (ψ, q≡1 mod 2n) through Montgomery butterflies, and debug it with only round-trip + vs-schoolbook fixtures (I7) — Phases 4–5.
  • Implement RNS base conversion (Bajard et al. 2016), explain its correction term, and name the input classes that expose a wrong one (I8) — Phases 6, 8.
  • Predict the noise-budget trajectory of a depth-L circuit from (n, q, t, σ) before executing it, within the calibrated margin (I1–I3) — Phase 9.
  • Select 128/192/256-bit-secure parameters from the HE-Standard tables and defend the choice against the depth↔security↔performance trilemma (I12) — Phases 9, 11.
  • Harden every secret-dependent path to constant time and demonstrate it with a timing harness, knowing exactly which paths may stay variable-time and why (I9) — Phase 11.

3.2 Subsystem Descriptions

he-bignum — The arithmetic floor. Big-integer modular operations: modexp (square-and-multiply, sliding-window), modinv (extended Euclid / Fermat), gcd/lcm, CRT combine, and reduction contexts — Montgomery (for repeated mul mod a fixed odd modulus, as in Paillier's Z_{n²}) and Barrett (for arbitrary modulus reduction). Either hand-built or a thin wrapper over crypto-bigint/num-bigint (ADR 2). Provides constant-time variants (subtle) for secret-dependent paths (e.g. Paillier decryption). No scheme logic.

he-numtheory — Number theory on top of bignum: Miller–Rabin probabilistic primality (with a configurable round count → error ≤ 4⁻ᵏ), optional Baillie–PSW, safe-prime generation (p prime and (p−1)/2 prime, required for Paillier's structure), Jacobi/Legendre symbols, uniform sampling of Z_n* / coprime elements, and the L-function L(u)=(u−1)/n used in Paillier decryption. Pure number theory; no NTT/lattice content.

he-rng — Randomness. A CSPRNG abstraction seeded from the OS (getrandom → ChaCha20), rejection sampling for uniform integers in a range (no modulo bias), a discrete Gaussian sampler (cumulative-distribution-table or Karney) for RLWE error, and a ternary sampler ({−1,0,1}) for secret/error distributions. A strictly separated --insecure-deterministic mode (fixed seed) exists only for reproducible tests/fixtures and is never used for real keys (I11).

he-paillier — The PHE scheme. Keygen: choose safe primes p,q, n=pq, λ=lcm(p−1,q−1), generator g (often n+1), μ=(L(g^λ mod n²))⁻¹ mod n. Encrypt E(m)=g^m·rⁿ mod n² with fresh r∈Z_n*. Decrypt m=L(c^λ mod n²)·μ mod n. Homomorphic add = ciphertext multiply mod n²; plaintext-mul = ciphertext exponentiation; re-randomization multiplies by r'ⁿ. Signed plaintexts via the [−n/2, n/2) convention. IND-CPA under DCRA.

he-ring — The polynomial ring R_q = Z_q[x]/(x^n+1), n a power of two. A Poly type (coefficient vector mod q), add/sub, negacyclic schoolbook multiply (the x^n=−1 wrap introduces sign flips), coefficient reduction, and sampling polynomials from uniform/Gaussian/ternary distributions into R_q. The schoolbook multiply is the correctness reference for the NTT path.

he-ntt — The negacyclic Number-Theoretic Transform: precomputed tables of a primitive 2n-th root of unity ψ mod each NTT prime (negacyclic via ψ twisting), forward NTT, inverse NTT (INTT, with n⁻¹ scaling), and pointwise multiply so that INTT(NTT(a)∘NTT(b)) = a·b in R_q. Montgomery-form butterflies (Cooley–Tukey forward, Gentleman–Sande inverse). Round-trip identity INTT∘NTT = id is the core invariant (I7).

he-rns — RNS/CRT representation. The ciphertext modulus q = q₀·q₁·…·q_{k−1} is a product of distinct NTT-friendly primes (qᵢ ≡ 1 mod 2n); a polynomial is stored as k independent residue polynomials, each with native-word coefficients, so all coefficient arithmetic is u64. Provides per-residue add/mul, base conversion (fast/approximate via floating or integer, plus an exact CRT reconstruction) used in BFV multiplication and mod-switching. RnsContext holds the moduli, NTT tables per prime, and precomputed CRT constants. The base-conversion correctness (I8) is the subtlest part of the system.

he-bfv — The leveled scheme. BfvParams fixes plaintext modulus t, ring degree n, and the modulus chain. SK keygen samples a ternary secret s; PK is (−(a·s+e), a). Relinearization keys and (deferred) Galois keys are encryptions of s²/permuted s under a special modulus. Encrypt: (c0,c1)=(Δ·m + a·s + e ... ) form (FV scaling Δ=⌊q/t⌋). Decrypt: ⌊(c0+c1·s) · t/q⌉ mod t. Add: componentwise. Multiply: tensor (c0,c1)⊗(c0',c1') → 3-component, scale by t/q, then relinearize the c2·s² term back to 2 components via the relin key, then optional mod-switch down the chain to control noise. Noise budget tracked via he-noise.

he-noise — The noise model. Closed-form (and empirical) bounds for fresh-encryption noise and the growth per add (additive), per mul (multiplicative + relin/mod-switch terms), and per mod-switch (reduction). Computes a noise budget in bits (log2(q/(2·‖noise‖))-style), exposes remaining_budget(ct), and the abort-before-exhaustion guard (I2/I3): refuse an operation that would drive the budget below the decryption-correctness threshold rather than silently returning garbage.

he-params — Parameter selection. Given a target multiplicative depth L and security level (128/192/256-bit), choose (n, q, t, σ): n a power of two large enough that RLWE at modulus q and error σ meets the security bound (per the LWE estimator's published tables, e.g. Albrecht et al.), q (a product of primes) large enough to hold L multiplications' noise, t the plaintext modulus (with t ≡ 1 mod 2n for batching). Validates the chosen params against tabulated attack costs and emits a parameter report.

he-encode — The encoding layer. Integer encoding (plaintext as a constant or base-t polynomial), batch encoding (CRT slots: when t ≡ 1 mod 2n, R_t factors into n slots, packing n integers into one plaintext for SIMD-style homomorphic ops), and scalar encoding. CKKS-style approximate/fixed-point encoding is explicitly out of scope (deferred).

he-cli — The driver. paillier subcommands (keygen/enc/dec/add/mul) and bfv subcommands (params/keygen/enc/dec/eval/noise). JSON I/O for keys and ciphertexts; bfv eval runs a small circuit description (a DAG of add/mul/scale) and reports the final noise budget; bfv noise prints remaining budget for a ciphertext.

6. Design Principles

P1. Correctness Within a Stated Noise Budget

Decryption is exact if and only if the accumulated noise stays below the threshold q/(2t)-style bound; the system never claims correctness it cannot guarantee. Tradeoff: depth is finite and must be budgeted. Violation: a "successful" op that overflows noise returns a uniformly random plaintext with no error — silent, total corruption.

P2. Homomorphism Is the Defining Invariant

Every operation must satisfy its homomorphic identity: Paillier Dec(E(a)·E(b))=a+b; BFV Dec(add)=a+b, Dec(mul)=a·b (within budget). These identities, not internal representation, define correctness. Violation: a kernel bug that breaks the identity makes encrypted compute meaningless.

P3. Noise Budget Is Monotone and Guarded

The noise budget only decreases across homomorphic operations; the system tracks it and aborts before an operation would exhaust it (P9). Tradeoff: conservative bounds may refuse a borderline-OK op. Violation: an un-guarded depth overflow yields garbage that looks like a valid ciphertext.

P4. Fresh Randomness Per Encryption (IND-CPA)

Every Paillier encryption draws a fresh r∈Z_n*; every BFV encryption draws fresh a, e. Re-using randomness breaks semantic security (identical plaintexts → identical or linkable ciphertexts). Violation: deterministic encryption is trivially distinguishable — IND-CPA lost.

P5. NTT Round-Trip Is Exact

INTT(NTT(p)) = p exactly (integer arithmetic mod the NTT prime — no float error), and INTT(NTT(a)∘NTT(b)) = a·b in R_q. Validated against the schoolbook multiply. Violation: a wrong root table or missing n⁻¹ scaling silently corrupts every BFV multiply.

P6. RNS Representation Is Faithful

A polynomial in RNS form must reconstruct (via CRT) to the same R_q element; base conversion between moduli sets is correct (exact reconstruction; the fast variant's error is bounded and corrected). Violation: a base-conversion bug corrupts BFV multiply/mod-switch in ways that pass small tests but fail at scale.

P7. Secret-Dependent Code Is Constant-Time

Decryption and key-dependent operations must not branch or index on secret data; use subtle's constant-time primitives. Tradeoff: some micro-optimizations forbidden. Violation: a timing side channel leaks the secret key — the worst failure in crypto.

P8. Scheme Logic Is Separate From Arithmetic Kernels

he-bignum/he-ntt/he-rns are arithmetic; he-paillier/he-bfv are scheme logic. Adding a scheme is composition; optimizing a kernel is local. Violation: entangling them makes both kernel optimization and scheme correctness risky.

P9. Fail Loud, Before Computing

Non-prime "primes", insufficient security parameters, depth overflow, malformed ciphertexts, and modulus mismatches are detected at keygen/parameter/validation time, not after producing wrong output. Violation: a half-valid key or over-budget circuit produces unfalsifiable garbage.

P10. Observability by Default

Every BFV operation reports noise-budget bits before/after, modulus-chain level, ciphertext component count, and op type; Paillier reports modulus size and op counts. Violation: a depth-exhausted or slow computation with no telemetry is undebuggable.

P11. Deterministic Test Mode Is Quarantined From Real Keys

The seeded --insecure-deterministic RNG exists only for fixtures/tests and is structurally prevented from generating real keys (explicit flag, loud warning, never the default). Violation: a deterministic "secret" key is no secret at all.

P12. Reference-Validated, Not Self-Certified

Conformance compares against analytic identities AND an external reference (python-paillier; SEAL BFV vectors). The system is "educational, not audited" and says so. Violation: a self-consistent but wrong implementation passes its own tests and misleads users into trusting it for secrets.

8.2 Paillier Algebra

Z_{n²}* has order n·φ(n); with g=n+1, (n+1)^m = 1 + m·n mod n² (binomial), so L((n+1)^m mod n²)=m. Keygen, encrypt, decrypt (normative definitions, Paillier 1999):

Signed integers: encode m∈(−n/2, n/2] as m mod n; decode > n/2 → m−n.

8.3 The Polynomial Ring R_q

R_q = Z_q[x]/(x^n+1), n=2^k. Multiplication is negacyclic convolution: (a·b)_k = Σ_{i+j=k} a_i b_j − Σ_{i+j=k+n} a_i b_j (the wrap is subtracted because x^n=−1). Schoolbook is O(n²); the NTT reduces it to O(n log n). Elements: ternary (secret), discrete-Gaussian (error), or uniform (mask a).

8.4 The Number-Theoretic Transform (NTT)

For an NTT prime qᵢ ≡ 1 mod 2n, let ω be a primitive n-th root and ψ a primitive 2n-th root (ψ²=ω). Negacyclic NTT pre-multiplies coefficients by powers of ψ so ordinary cyclic convolution computes the negacyclic product:

Step Formula Meaning
Forward NTT â_j = Σ_i (a_i · ψ^i) · ω^{ij} mod q twist + DFT (Longa & Naehrig 2016)
Pointwise multiply ĉ = â ∘ b̂ elementwise product in transformed domain
Inverse NTT c_k = n⁻¹ · ψ^{-k} · Σ_j ĉ_j · ω^{-kj} mod q DFT⁻¹ + untwist
Result c = a · b in R_q negacyclic convolution holds exactly (I7)

Forward via Cooley–Tukey (decimation-in-time), inverse via Gentleman–Sande, butterflies in Montgomery form. Bit-reversal permutation between natural/transformed order. Round-trip INTT(NTT(a))=a exactly (P5).

8.5 RNS / Double-CRT Representation

The coefficient modulus q = q₀·q₁·…·q_{k−1} (distinct primes, each ≡1 mod 2n). A polynomial is stored as k residue polys; coefficient x ↔ (x mod q₀, …, x mod q_{k−1}). Combined with the per-prime NTT, this is the double-CRT form: every coefficient op is a native u64 op, all multiplies are NTT-pointwise.

Operation Definition Meaning

From RNS from_rns(residues) → x mod q exact CRT reconstruction (I8)

Base conversion (changing the modulus set) underlies BFV multiply scaling and mod-switching; its correctness (I8) is the system's subtlest property.

Phase 1 — Big-integer modular arithmetic + Montgomery/Barrett

1.1 Objectives

Establish the arithmetic floor: modexp, modinv, gcd/lcm, CRT combine, and Montgomery + Barrett reduction contexts, on a vetted big-integer backend (ADR 2). Constant-time variants for secret-dependent modexp (I9). Everything above depends on this.

1.2 Detailed Implementation Steps

  • bignum/modexp.rs: square-and-multiply with sliding-window (4-bit) exponentiation (HAC Ch 14); integrate Montgomery for fixed-modulus repeated use (ADR 8).
  • bignum/modinv.rs: extended Euclid (HAC Ch 14); Fermat-based variant (a^{p−2}) for prime moduli; Option (None if non-invertible).
  • bignum/gcd.rs: binary GCD (HAC Ch 14); lcm via a·b/gcd.
  • bignum/crt.rs: combine (rem,mod) pairs (pairwise CRT, von zur Gathen & Gerhard) → reconstruct mod the product; feeds I8's reconstruction later.
  • bignum/montgomery.rs: MontgomeryCtx::new precomputes r=2^k, r², n'=−n⁻¹ mod r; mul (REDC), pow — per Montgomery (1985), ADR 8.
  • bignum/barrett.rs: precompute μ=⌊2^{2k}/m⌋; reduce arbitrary products (HAC Ch 14 Barrett method, ADR 8).
  • bignum/ct.rs: subtle-based constant-time modexp (fixed-window, conditional-select, no secret branch/index) (I9, P7, ADR 13).

1.3 Deliverable

modexp/modinv/gcd/crt correct on test vectors; Montgomery mul/pow match schoolbook; Barrett reduces correctly; CT modexp matches non-CT result. cargo test -p he-bignum green.

1.4 Acceptance Criteria

  • modexp(g,e,m) matches a reference (Python pow) on 1000 random triples.
  • modinv(a,m)·a ≡ 1 mod m whenever gcd(a,m)=1; None otherwise.
  • Montgomery pow == modexp for fixed odd modulus.
  • CRT reconstructs the unique residue mod the product for coprime moduli.
  • CT modexp: no secret-dependent branch (audit) + equal output to plain.

1.6 Pitfalls

  • Montgomery requires an odd modulus; Z_{n²} is odd (n odd) — assert.
  • n' computation (−n⁻¹ mod r) sign/width bugs corrupt every REDC silently.
  • Non-constant-time modexp leaks the exponent (secret λ) via timing; the CT path must be branch- and index-independent (I9).
  • CRT with non-coprime moduli is undefined; validate coprimality.

1.7 Performance Concerns

  • Modexp dominates Paillier; Montgomery removes per-multiply division. Sliding-window cuts multiplies ~25%. Keep operands in Montgomery form across a key's lifetime.
  • Barrett vs Montgomery: Barrett for one-off reductions (NTT prime products); Montgomery for repeated same-modulus loops.

1.8 Edge Cases

  • exp=0 → 1; base=0 → 0; modulus=1 → 0. modinv of 0 → None. Single-modulus CRT → identity.

1.9 Failure Analysis

A wrong n' or window bug corrupts all higher layers. Detection: modexp/Montgomery equivalence fixtures. Blast radius: every scheme. Containment: this crate is the most-tested foundation; CT path separately audited.

1.10 Operational Notes

tracing span per modexp records bit-length + time → the Paillier latency profile. The ct-inspect tool can dump a Montgomery context's constants for debugging.

Phase 2 — Number theory: primality, safe primes, sampling

2.1 Objectives

Implement Miller–Rabin primality (configurable rounds, I6), safe-prime generation, uniform Z_n*/coprime sampling, Jacobi symbol, the L-function, and the CSPRNG + discrete-Gaussian + ternary samplers in he-rng — including the quarantined deterministic test mode (I11, P11).

2.2 Detailed Implementation Steps

  • numtheory/primality.rs: Miller–Rabin with k rounds (error ≤ 4⁻ᵏ; default k=40) per HAC Ch 4 (I6); optional Baillie–PSW (Crandall & Pomerance) for fewer false-positives.
  • numtheory/safe_prime.rs: sample odd candidate, test q=(p−1)/2 and p both prime; loop until found (I6, P9).
  • numtheory/sampling.rs: random_coprime(n) via rejection (gcd=1); uniform [0,n) (no modulo bias, ADR 12).
  • numtheory/jacobi.rs, numtheory/lfunc.rs: Jacobi symbol (HAC Ch 2); L(u,n)=(u−1)/n per Paillier (1999).
  • rng/csprng.rs: ChaCha20 (RFC 8439) seeded from getrandom (ADR 12); rng/uniform.rs: rejection sampling (no modulo bias); rng/gaussian.rs: discrete Gaussian, CDT for small σ / Karney for arbitrary (ADR 10); rng/ternary.rs (ADR 11).
  • rng/det_mode.rs: DetRng behind --insecure-deterministic; loud warning; refuses to be used by real keygen (I11, P11).

2.3 Deliverable

Safe primes generated at 1024/1536 bits; Miller–Rabin matches a reference on known primes/composites; samplers produce correct distributions; deterministic mode reproducible and quarantined.

2.4 Acceptance Criteria

  • Miller–Rabin: 0 false negatives on known primes; composite-detection on Carmichael numbers; k-round error bound documented.
  • gen_safe_prime(bits): both p and (p−1)/2 pass primality; correct bit length.
  • Discrete Gaussian: empirical mean ≈ 0, std ≈ σ over 10⁶ samples (χ² within tolerance).
  • Uniform sampler: no modulo bias (statistical test).
  • DetRng refuses real keygen path; CSPRNG is default (I11).

2.9 Failure Analysis

A composite passing as prime yields an invalid Paillier modulus → decryption silently wrong. Detection: MR rounds + post-keygen homomorphic-identity check (I4). Recovery: regenerate. A weak sampler is caught by statistical fixtures.

2.10 Operational Notes

Phase 3 — Paillier: keygen, encrypt, decrypt, homomorphic ops

3.1 Objectives

Implement the full Paillier PHE scheme: keygen (n=pq, λ, μ), encrypt (g^m r^n mod n², fresh r, I10/P4), decrypt (L-function, constant-time, I9/P7), homomorphic add (I4), plaintext-scalar multiply, re-randomization, and signed-integer encoding. First working homomorphic computation.

3.2 Detailed Implementation Steps

  • paillier/keygen.rs: two safe primes → n, n²; λ=lcm(p−1,q−1); g=n+1; μ=modinv(L(g^λ mod n²), n) — normative per Paillier (1999), ADR 3 (I6).
  • paillier/encrypt.rs: c=(g^m mod n²)·(modexp(r,n,n²)) mod n²; fresh r=random_coprime(n) per call (I10, P4).
  • paillier/decrypt.rs: m=L(ct^λ mod n²)·μ mod n (Paillier 1999); use ct_modexp for the secret-exponent step (I9, P7, ADR 13).
  • paillier/homomorphic.rs: add=ct1·ct2 mod n² (I4, P2); mul_plain=modexp(ct,k,n²); rerandomize=ct·modexp(r',n,n²) (§8.2 table).
  • paillier/encode.rs: signed encode/decode via [−n/2,n/2) centered representative (§8.2).

3.3 Deliverable

E(7)·E(5) decrypts to 12; E(6)^4→24; signed E(−3)·E(10)→7; re-randomized ciphertext decrypts unchanged but is byte-different. End-to-end he-cli paillier works.

  • Dec(E(m))=m for 1000 random m∈[0,n) at n=3072 bits (correctness, paillier/roundtrip.json).
  • Dec(E(a)·E(b))=a+b mod n (I4); Dec(E(a)^k)=k·a mod n (paillier/hom_add.json, paillier/scalar_mul.json).
  • Signed arithmetic correct across zero (paillier/signed.json).
  • Two encryptions of the same m differ (fresh r, I10); both decrypt to m (paillier/ind_cpa_distinct.json).
  • Decryption timing independent of key bits within a 5% coefficient-of-variation bound (CT audit + timing harness, I9).

  • Forgetting fresh r per encryption → deterministic, IND-CPA broken (I10, P4).
  • μ undefined if gcd(L(g^λ),n)≠1; with g=n+1 it is invertible — assert and document.
  • Plaintext m≥n wraps silently; range-check (PlaintextOutOfRange).
  • Secret-exponent modexp in decrypt must be constant-time (I9); a fast non-CT path leaks λ.
  • Overflow: all arithmetic mod n² (twice the bit-length); ensure the bignum width is sufficient.

3.7 Performance Concerns

  • Encryption = two modexps (g^m cheap with g=n+1 via binomial shortcut 1+mn; r^n the cost). Decryption = one modexp ct^λ. Montgomery in Z_{n²} across a key's lifetime.
  • g=n+1 lets g^m mod n² = 1 + m·n (no modexp) — a real speedup; implement the shortcut.

3.8 Edge Cases

  • m=0 → E(0)=rⁿ. Add with E(0) is identity. mul_plain by 0 → E(0). Re-randomize preserves plaintext, changes ciphertext.

3.9 Failure Analysis

A wrong μ or L-function gives systematically wrong decryption. Detection: roundtrip + vs-phe fixtures (P12). A non-CT decrypt is a timing vulnerability — caught by the CT audit + timing test. Blast radius: all Paillier results.

3.10 Operational Notes

Phase 4 — Polynomial ring R_q + schoolbook negacyclic multiply

4.1 Objectives

Implement the ring R_q = Z_q[x]/(x^n+1): the Poly type, add/sub, negacyclic schoolbook multiply (the correctness reference for the NTT, P5/P8), coefficient reduction, and sampling polynomials from uniform/Gaussian/ternary into R_q. The lattice substrate beneath BFV.

4.2 Detailed Implementation Steps

  • ring/poly.rs: Poly{coeffs:Vec<u64>, modulus, n}; constructors from coefficient vectors / samplers (§8.3, ADR 5).
  • ring/negacyclic.rs: schoolbook multiply with the x^n=−1 wrap (subtract the high-degree overflow into the low coefficients); O(n²); the correctness reference for I7 (P5, P8).
  • ring/reduce.rs: per-coefficient reduction mod q (Barrett, ADR 8); centered representative helpers.
  • ring/sample.rs: sample uniform mod q, discrete Gaussian (rounded into coeffs, ADR 10), ternary (ADR 11), into a Poly — the RLWE distributions of LPR (2010).

4.3 Deliverable

poly_add/poly_mul_schoolbook correct on hand-computed examples; negacyclic wrap verified (x^{n−1}·x = −1 constant term); samplers fill polynomials with correct distributions.

4.4 Acceptance Criteria

  • poly_add componentwise mod q.
  • poly_mul_schoolbook: (x^{n−1})·(x) → −1 (i.e. q−1) constant term, rest 0 (negacyclic).
  • Multiply matches a hand-computed small example (n=4).
  • Sampled polynomials have correct coefficient distributions.

4.6 Pitfalls

  • Forgetting the sign flip on the wrap turns negacyclic into cyclic convolution — a silent, scheme-breaking bug (P5).
  • Coefficient overflow before reduction: products of two <q values need a u128 accumulator when q is near 62 bits.

4.7 Performance Concerns

  • Schoolbook is O(n²) — only a reference/fallback for small n; the NTT (Phase 5) replaces it for real sizes. Keep it simple and obviously correct.
  • u128 accumulation per coefficient pair; reduce once at the end of each output coefficient.

4.8 Edge Cases

  • n=1 degenerate ring. Zero polynomial. Multiply by the constant 1 (identity) and by x (cyclic shift with sign flip at wrap).

4.9 Failure Analysis

4.10 Operational Notes

tools/ct-inspect can dump a Poly's coefficients (centered) for debugging. Schoolbook multiply remains available behind a flag for cross-checking the NTT in conformance.

Phase 5 — NTT / INTT (negacyclic) + pointwise multiply

5.1 Objectives

Implement the negacyclic NTT/INTT (§8.4): primitive-2n-th-root tables per NTT prime, forward (Cooley–Tukey) and inverse (Gentleman–Sande) transforms with Montgomery butterflies, and pointwise multiply, so INTT(NTT(a)∘NTT(b)) = a·b in R_q (I7, P5). The performance heart of BFV.

5.2 Detailed Implementation Steps

  • ntt/roots.rs: find a primitive 2n-th root ψ mod q (q≡1 mod 2n, I14); precompute ψ^i, ψ⁻ⁱ, ω=ψ² powers, n⁻¹ — all in Montgomery form (Longa & Naehrig 2016).
  • ntt/butterfly.rs: Montgomery butterfly (a±ω·b mod q), branch-light (Montgomery 1985, ADR 8).
  • ntt/forward.rs: Cooley–Tukey decimation-in-time, bit-reversed access; pre-twist by ψ^i for negacyclic (§8.4, Longa & Naehrig 2016).
  • ntt/inverse.rs: Gentleman–Sande, post-untwist by ψ⁻ᵏ, scale by n⁻¹ (§8.4; I7).
  • ntt/pointwise.rs: elementwise Montgomery multiply of two transformed polys — realizes INTT(NTT a∘NTT b)=a·b (I7, P5, ADR 6).

5.3 Deliverable

INTT(NTT(p))=p exactly for random p; INTT(NTT(a)∘NTT(b)) equals poly_mul_schoolbook(a,b) in R_q; transforms run for n up to 32768.

5.4 Acceptance Criteria

  • Round-trip identity INTT∘NTT = id exact (I7) for 10⁴ random polys.
  • NTT-multiply == schoolbook multiply in R_q (P5) across random pairs.
  • Negacyclic property: result respects x^n=−1 (matches Phase 4 wrap).
  • Works for every NTT prime in a parameter set (I14).

5.5 Conformance Fixtures

Fixture Purpose Expected

5.6 Pitfalls

  • Missing n⁻¹ scaling in INTT → result off by a factor of n (silent for a·1 if n=1).
  • Wrong root order (ω vs ψ) or forgetting the negacyclic twist → cyclic instead of negacyclic convolution.
  • Bit-reversal permutation mismatch between forward and inverse → scrambled output.
  • Montgomery butterfly using non-Montgomery roots → wrong values; keep tables in Montgomery form consistently.
  • q² overflow in the butterfly product — use u128 (or 62-bit primes with care).

5.7 Performance Concerns

  • NTT is O(n log n) and the BFV bottleneck; the inner butterfly must be branch-light, cache-friendly, and division-free (Montgomery). Precompute all twiddle factors once. This kernel is the prime target for Phase 12 SIMD.
  • Memory-access pattern (strides per stage) drives cache behavior — the classic FFT locality problem.

5.8 Edge Cases

  • n very small (degenerate). All-zero poly (transforms to zero). Multiply by the constant 1 (transform of [1,0,…]).

5.9 Failure Analysis

A wrong root table corrupts every BFV multiply while add still works — a subtle partial failure. Detection: round-trip (I7) + vs-schoolbook (P5) on every NTT prime. Recovery: dump root tables via ct-inspect; verify ψ^{2n}=1, ψ^n=−1.

5.10 Operational Notes

tracing span per transform records n, prime, time → the NTT profile (the dominant cost). bench_ntt tracks throughput vs n. Runbook "slow-ntt" → check n, prime count, SIMD flag.

Phase 6 — RNS / double-CRT representation + base conversion

6.1 Objectives

Implement the RNS representation (§8.5): ciphertext modulus q=Πqᵢ of NTT-friendly primes, per-residue polynomial arithmetic (each prime carries its own NttCtx), exact CRT reconstruction, and base conversion between modulus sets — the subtlest correctness property in the system (I8, P6). The double-CRT layout that makes BFV practical.

6.2 Detailed Implementation Steps

  • rns/context.rs: RnsContext{moduli, NttCtx per prime, CRT constants}; choose k distinct primes ≡1 mod 2n (I14, ADR 7/9).
  • rns/rns_poly.rs: RnsPoly{residues:Vec<Vec<u64>>}; per-residue add/sub/NTT-mul (independent, rayon-parallel, ADR 27; P8).
  • rns/crt_recon.rs: exact CRT reconstruction from_rns(residues)→BigUint mod q; precomputed (q/qᵢ)·((q/qᵢ)⁻¹ mod qᵢ) (von zur Gathen & Gerhard CRT; I8, P6).
  • rns/convert.rs: base_convert(from→to): fast approximate variant per Bajard et al. (2016) / Halevi–Polyakov–Shoup (2019) with the floating/integer correction term, plus an exact-CRT fallback for validation (I8).

6.3 Deliverable

from_rns(to_rns(x))=x mod q exactly; per-residue NTT-multiply matches single-modulus result; base conversion between two prime sets is exact (validated against the exact-CRT path).

6.4 Acceptance Criteria

  • CRT reconstruction exact for 10⁴ random x<q (I8, rns/crt_recon.json).
  • RNS multiply (per-residue NTT) == reconstruct-then-single-modulus multiply for k=3–8 limbs (rns/rns_mul_equiv.json).
  • base_convert fast variant == exact-CRT variant, correction term verified to 0 reconstruction error (rns/base_convert.json).
  • Parallel per-limb arithmetic == serial, bit-for-bit, across 100 randomized limb counts (reassociation-free; integer exact, rns/parallel_equiv.json).

6.5 Conformance Fixtures

Fixture Purpose Expected
rns/crt_recon.json I8 exact reconstruction
rns/rns_mul_equiv.json per-residue == single-modulus
rns/base_convert.json I8 fast == exact
rns/parallel_equiv.json ADR 27 == serial

6.6 Pitfalls

  • Base conversion is the classic FHE bug source: the fast variant's correction term (handling the q-overflow ambiguity) is easy to get wrong and fails only for some inputs — always cross-check vs exact CRT (I8).
  • Forgetting a prime must be ≡1 mod 2n breaks its NTT (I14).
  • Mixing Montgomery and normal form across residues.
  • Integer overflow in CRT constants (q/qᵢ is large — keep as BigUint or reduce per modulus).

6.7 Performance Concerns

  • RNS is the reason coefficient ops are native u64: each residue's multiply is one NTT, all k residues parallel (rayon over limbs, ADR 27). Base conversion is O(k²·n) — non-trivial; the fast variant avoids full reconstruction.
  • Keep residues contiguous per prime for cache locality; the per-limb loops are independent (no false sharing if chunked).

6.8 Edge Cases

  • k=1 (single prime) → RNS degenerates to plain modular arithmetic; still correct. Converting to a superset/subset of primes. Reconstruction of x near q (overflow boundary).

6.9 Failure Analysis

A base-conversion bug corrupts BFV multiply/mod-switch for some ciphertexts — passes small tests, fails at scale (the worst kind). Detection: fast-vs-exact equivalence over random + boundary inputs (I8); later BFV depth-L conformance. Recovery: fall back to exact-CRT conversion; bisect the correction term.

6.10 Operational Notes

param-report lists the RNS prime set and per-prime bit-sizes. tracing records base-conversion time (a real cost in BFV multiply). Runbook "wrong-decrypt at depth" → suspect base conversion first.

7.1 Objectives

Phase 8 — BFV multiply: tensoring, relinearization, modulus switching

8.1 Objectives

Implement homomorphic multiplication (§8.6): tensor two ciphertexts into a 3-component product, scale by t/q (RNS base conversion, I8), relinearize the c2·s² term back to 2 components using the relin key (key switching), and modulus-switch down the chain to extend depth. The core of leveled FHE; bounded-depth Dec(mul)=a·b (I5, within budget, I1/I3).

8.2 Detailed Implementation Steps

  • bfv/keygen.rs (extend): build the relin key = encryption(s) of s² in a decomposition/RNS basis (controls key-switch noise; Fan–Vercauteren 2012 relin v1, ADR 14).
  • bfv/mul.rs: tensor (c0,c1)⊗(c0',c1') → (d0,d1,d2)=(c0c0', c0c1'+c1c0', c1c1') via NTT-multiply (Brakerski 2012 tensoring); scale all by t/q with rounding (RNS base conversion per Bajard et al. 2016 / HPS 2019, I8).
  • bfv/relin.rs: key-switch d2 (would need s²) into (c0'',c1'') using the relin key (ADR 14); add into (d0,d1) → 2-component ciphertext (P2, I5).
  • bfv/modswitch.rs: divide the modulus chain by a prime (RNS drop + rescale, rounding) — the BGV (2012) mod-switch idea; reduces noise, lowers level (I13).
  • Wire he-noise::after_mul + guard (abort if budget would go ≤0 before computing, I3/P3).

8.3 Deliverable

Dec(Enc(3)·Enc(4))=12 with budget>0 (I5,I1); a depth-L multiply chain stays correct until the budget runs out; mod_switch extends achievable depth; mul past budget aborts with NoiseExhausted (I3).

8.4 Acceptance Criteria

  • Dec(mul)=a·b mod t for random a,b at depth 1 (I5).
  • Depth-L chain (L per params) decrypts correctly; L+1 aborts (I3).
  • Relinearized ciphertext is 2-component and decrypts correctly (key-switch noise within budget).
  • mod_switch lowers level, reduces ciphertext size, and increases or preserves budget headroom for further mults.
  • Matches SEAL BFV multiply vectors (P12).

8.6 Pitfalls

  • The t/q scaling after tensoring is a base conversion — the #1 BFV bug; cross-check vs exact CRT (I8).
  • Relin key with too-coarse decomposition injects too much noise → unexpected depth loss; tune the decomposition base.
  • Forgetting the abort guard → a multiply past budget returns a valid-looking but garbage ciphertext (I3, P3).
  • Mod-switching at the bottom of the chain (no prime to drop) must error (ModSwitchAtBottom), not panic.
  • Mismatched levels in mul (one ciphertext switched, the other not) → wrong result; align levels first.

8.7 Performance Concerns

  • Multiply is the expensive op: tensoring is ~3 NTT-multiplies, scaling is a base conversion, relinearization is ~(k+1) more NTT-multiplies per limb. Stay in NTT form; parallelize over RNS limbs (ADR 27). This dominates any BFV circuit's cost.
  • Mod-switch shrinks k → subsequent ops are cheaper; a well-placed mod-switch is both a noise and a performance win.

8.8 Edge Cases

  • Multiply by Enc(0) → decrypts 0 but consumes budget. Multiply by Enc(1) (encrypted one) ≠ free (still consumes budget). depth=1 params (one mult, no mod-switch needed). t=2 (boolean) BFV.

8.9 Failure Analysis

The deepest failure surface: a base-conversion or relin bug corrupts results only at depth, after small tests pass. Detection: depth-chain conformance + vs-SEAL (P12) + the exact-CRT cross-check (I8). Recovery: isolate — test tensor, scale, relin, mod-switch independently against SEAL intermediate values; suspect base conversion first.

8.10 Operational Notes

noise-trace logs budget before/after each mul/relin/mod-switch (P10) — the primary tool for diagnosing depth exhaustion. he-cli bfv eval runs a circuit DAG and prints the budget trajectory + final level. The abort guard's NoiseExhausted{remaining} tells the operator exactly how much depth was left.

Phase 9 — Noise model + parameter selection

9.1 Objectives

Make depth predictable: implement the he-noise growth model (fresh/add/mul/relin/mod-switch bounds), the noise budget in bits (I2), the abort guard (I3/P3), and he-params selection of (n,q,t,σ) for a target depth L and security level via the LWE-estimator tables (I12/P9). Closes the loop between "what circuit" and "what parameters."

9.2 Detailed Implementation Steps

  • noise/model.rs: closed-form (worst-case + average-case) noise bounds per operation (§8.7), parameterized by (n,q,t,σ) — derived from the Fan–Vercauteren (2012) noise analysis (P1).
  • noise/budget.rs: budget_bits ≈ log2(q) − log2(2·t·‖noise‖); fresh_budget, after_add, after_mul, after_modswitch (I2, P3).
  • noise/guard.rs: guard(planned) → Err(NoiseExhausted) if predicted post-budget ≤ 0 (I3, P9).
  • params/tables.rs: embed HE-Standard (2018) / Albrecht–Player–Scott (2015) (n,q)↔security-bits tables (128/192/256) (ADR 16).
  • params/select.rs: given L + sec level, pick the smallest n, build a q (prime product) large enough for L mults' noise, choose t (≡1 mod 2n if batching, ADR 17), σ=3.2 (ADR 10) (I12, I14).
  • params/security.rs + params/validate.rs: check_security→estimated bits; validate asserts I12/I13/I14 (P9).

9.3 Deliverable

For a requested depth L and 128-bit security, select returns parameters that (a) pass the security check (I12) and (b) actually support L multiplications (verified by running a depth-L chain and confirming budget>0 throughout, then 0 at L+1).

9.4 Acceptance Criteria

  • Predicted noise budget after each op matches the measured budget (decrypt-succeeds boundary) within a small margin.
  • select(L, 128) params support exactly ≥L multiplications (chain conformance) and meet ≥128-bit security (I12).
  • guard aborts precisely when (and only when) the next op would make decryption fail (no false aborts at budget>0; no false passes at budget≤0) (I3).
  • validate rejects insecure / malformed params (I12/I13/I14) loudly (P9).

9.6 Pitfalls

  • Worst-case noise bounds are conservative; pure worst-case wastes depth. Document the chosen model (worst vs average) and its failure probability.
  • A too-optimistic model passes the guard but decryption fails — worse than a conservative one (silent garbage, P1/P3). Calibrate against measured boundaries.

Real incident — Li & Micciancio (Eurocrypt 2021), "On the Security of Homomorphic Encryption on Approximate Numbers." They showed that CKKS, the approximate-arithmetic scheme, is not IND-CPA secure once decryption results are shared: because CKKS decryption returns plaintext plus residual noise, an adversary who sees decrypted outputs can solve a linear system for the secret key (the IND-CPA^D gap between security with and without a decryption oracle). The disclosure prompted Microsoft SEAL, OpenFHE, and HEAAN to add noise-flooding countermeasures (adding extra noise before releasing a decryption). This blueprint sidesteps the attack class structurally: BFV is exact (decryption returns the plaintext with no residual noise, I1), so there is no decryption-leakage surface — one concrete reason CKKS is deferred (ADR 4; Alternative Architectures B) rather than shipped naïvely. If CKKS is ever un-deferred (Deferred Features Register), noise-flooding before any decryption disclosure is mandatory.

Recovery philosophy: security and resource failures (insecure params, composite key, noise overflow, timing leak) fail loud at keygen/parameter/validation/pre-op time (P9, I3); correctness failures surface through analytic + reference conformance (P12), never silently; noise is probabilistic, so the abort guard is calibrated conservatively (Phase 9) — better a refused op than a garbage plaintext (P1). The approximate-decryption leak (Li & Micciancio 2021) is the one failure with no in-design recovery for an approximate scheme — it is avoided by the exact-arithmetic choice (ADR 4), not patched.

Mental Models & First Principles

The compressed intuitions an expert carries into HE work. Each model states the insight, what it lets you predict, the bug class you write without it, and where this blueprint applies it.

MM1 — A ciphertext is a budget, not a value. Every RLWE ciphertext carries noise that grows with each operation; you are spending a finite noise budget, and (since bootstrapping is deferred) there is no refill. Predicts: depth is bounded; a circuit either fits the budget or it does not, set before keygen. Bug without it: designing an "unbounded" homomorphic loop that silently returns garbage past the budget. Applied: §8.7 (noise growth), Phase 9 (budget model), I1/I2/I3.

MM2 — Homomorphism is a ring homomorphism, so the map is the contract. Paillier sends plaintext + to ciphertext × (Dec(E(a)·E(b))=a+b); BFV preserves + and × within budget. Correctness is defined by these identities, never by the byte layout. Predicts: any kernel change is correct iff the identity still holds — so the identity is the test oracle. Bug without it: "optimizing" a kernel while breaking Dec(mul)=a·b and trusting unit tests that never check the identity. Applied: §8.2, P2, I4/I5, Phase 3 / Phase 8.

MM3 — The NTT is the modular FFT; multiply is pointwise in the frequency domain. Convolution (polynomial multiply) becomes elementwise multiply after an NTT, turning O(n²) schoolbook into O(n log n). Predicts: the NTT, not the multiply, dominates the BFV profile, and exact integer roots (not floats) keep it error-free. Bug without it: a missing n⁻¹ scale or a cyclic-instead-of-negacyclic twist that corrupts every product silently. Applied: §8.4, P5, I7, Phases 4–5.

MM4 — A big modulus is a tuple of small ones (RNS/CRT). A coefficient mod q=Πqᵢ is the same information as its residues (x mod q₀,…,x mod q_{k−1}); arithmetic is independent per residue, so every coefficient op is a native u64 multiply. Predicts: per-op cost and ciphertext size scale linearly in the limb count k, and limbs are embarrassingly parallel. Bug without it: treating base conversion as a no-op rather than the subtlest correctness trap in the system. Applied: §8.5, P6, I8, Phase 6.

MM5 — Multiplication is the expensive, noisy, structure-breaking op. Tensoring two 2-component ciphertexts yields a 3-component one whose c2 term needs s²; relinearization (key switching) folds it back to 2 components, and noise grows multiplicatively there. Predicts: depth, key sizes, and latency are all driven by multiply, not add — so add is "free," multiply is the budget line. Bug without it: forgetting relinearization and watching ciphertexts grow a component per multiply until decryption is impossible. Applied: §8.6, Phase 8, I5.

MM6 — Parameters are a trilemma: security ↔ depth ↔ performance. Bigger q buys depth but lowers security at fixed n, so n must grow, which slows everything. Predicts: you cannot have deep circuits, strong security, and small fast ciphertexts at once — pick the corner the workload needs. Bug without it: choosing q for depth and shipping sub-128-bit parameters without rechecking security. Applied: §4, Phase 9 (select iterates n until security holds), I12, ADR 16.

MM7 — Fresh randomness per encryption is what makes encryption encryption. Each Paillier r and each BFV (u,e) is drawn fresh; reuse makes equal plaintexts produce linkable ciphertexts and destroys IND-CPA. Predicts: deterministic encryption is trivially distinguishable, and a seeded RNG must never reach real keygen. Bug without it: a "cache the randomness" optimization that silently breaks semantic security. Applied: P4, P11, I10/I11, Phases 3 and 7.

MM8 — Exactness is a security property, not just a convenience. BFV decryption returns the plaintext with no residual noise; CKKS returns plaintext plus noise, and sharing those noisy decryptions leaks the key (Li & Micciancio 2021, the IND-CPA^D gap). Predicts: an approximate scheme needs noise-flooding before any decryption is disclosed; an exact scheme does not. Bug without it: deploying CKKS-style approximate HE and releasing decryptions, leaking the secret key. Applied: Failure Modes & Recovery, ADR 4, Alternative Architectures B, I1.

MM9 — Secret-dependent timing is a side channel; constant-time is mandatory on secret paths only. Decryption and keygen touch the secret (λ, s); branching or indexing on it leaks bits through timing. The bulk eval kernels (NTT/RNS over public ciphertexts) need no such protection. Predicts: exactly which paths must be branch-free, and where constant-time costs buy nothing. Bug without it: an early-exit or secret-indexed table in decrypt that recovers the key (the Brumley–Boneh 2003 attack class). Applied: P7, I9, Phase 11, ADR 13.

MM10 — Fail before you compute, not after. Composite "primes," insecure parameters, depth overflow, and parameter mismatch are all detectable before producing output; a half-valid key or over-budget circuit yields unfalsifiable garbage. Predicts: the right place for every guard is keygen/parameter/pre-op validation, and a refused op is a success while a garbage plaintext is a failure. Bug without it: discovering a composite modulus only by a wrong decryption in production. Applied: P9, I3/I6/I12, Phases 2 / 9 / 11.

Alternative Architectures (Roads Not Taken)

Fundamentally different designs for "compute on encrypted data," each embodied by a real system, with the regime where it wins and why this blueprint rejected it. Labels A–D are referenced from §5 (Required Reading) and ADR 3/4.

A — Bootstrapped FHE (unbounded depth). Refresh noise homomorphically so any circuit depth is possible.

  Enc(m) --eval--> noisy ct --[budget low]-->  BOOTSTRAP
     ^                                            |  (homomorphic decrypt
     |                                            v   under encryption)
     +----------------- refreshed ct <------------+   resets noise budget

Wins when: the circuit depth is unbounded or unknown at parameter-selection time (deep ML, arbitrary programs). Real system: Gentry's original construction (STOC 2009); FHEW/TFHE and CKKS bootstrap in OpenFHE. Rejected here because: bootstrapping is the single most complex and costly FHE component; this blueprint teaches the leveled core first and defers it (PhaseDeferred §Phase 13, Deferred Features Register, Comparative table).

B — Approximate FHE (CKKS, real/complex arithmetic). Encode reals/complex with a scaling factor; treat rounding noise as acceptable.

  real vec --encode(scale Δ)--> R_q ct --add/mul--> ct --decode--> approx real vec
                                                          (plaintext + residual noise)

Wins when: the workload is numerical and error-tolerant — encrypted ML inference, statistics, signal processing — where approximate results are fine and throughput matters. Real system: HEAAN (Cheon–Kim–Kim–Song, Asiacrypt 2017), CKKS in SEAL/OpenFHE. Rejected here because: (1) scope — this blueprint is integer-exact; (2) security — sharing CKKS decryptions leaks the key (Li & Micciancio 2021, the IND-CPA^D gap) unless noise-flooded, a real footgun. Deferred (PhaseDeferred §Phase 9, ADR 4, Failure Modes, MM8).

C — Bit-wise fast-bootstrapping (TFHE). Encrypt bits; every Boolean gate bootstraps, so depth is effectively free but there is no SIMD batching.

  bits --enc--> LWE ct/bit --GATE(bootstrap)--> LWE ct/bit --...--> dec
                              (programmable bootstrap = gate + noise reset)

Wins when: the circuit is comparison/branching/lookup-heavy rather than arithmetic-heavy — decision trees, sorting, table lookups — where word-wise batched arithmetic is a poor fit. Real system: Zama TFHE-rs / Concrete (Chillotti–Gama–Georgieva–Izabachène, Asiacrypt 2016 / J. Cryptology 2020). Rejected here because: it is a different scheme with different primitives (programmable bootstrap, torus arithmetic) and no batching; this blueprint targets word-wise batched BFV (Comparative table, ADR 4).

D — Partially-homomorphic single-operation schemes. One algebraic operation only, no noise, no depth limit — extreme simplicity.

  Paillier (additive):     E(a)·E(b) = E(a+b)      # multiply ciphertexts -> add plaintexts
  exponential ElGamal:     E(a)·E(b) = E(a+b)      # additive in the exponent, small message space
  (textbook) RSA (mult.):  E(a)·E(b) = E(a·b)      # multiplicative only

Wins when: the application needs exactly one operation on encrypted data — private summation, voting, federated aggregation (additive), or a multiplicative-only mask — where a full RLWE stack is wasted overhead and ciphertexts must stay small (Paillier ≈ 768 B at n=3072, Capacity C6). Real systems: Paillier (1999) — kept in this design as the PHE half; exponential ElGamal for tiny tallies. Rejected as the BFV substitute because: a single operation cannot evaluate a·b + c-style circuits; BFV is required for bounded-depth arithmetic. This blueprint ships both — Paillier for the additive niche, BFV-lite for general leveled compute (ADR 3, §1.1).
