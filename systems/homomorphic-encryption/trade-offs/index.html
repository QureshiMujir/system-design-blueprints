Alternative Architectures (Roads Not Taken)

Fundamentally different designs for "compute on encrypted data," each embodied by a real system, with the regime where it wins and why this blueprint rejected it. Labels A–D are referenced from §5 (Required Reading) and ADR 3/4.

A — Bootstrapped FHE (unbounded depth). Refresh noise homomorphically so any circuit depth is possible.

  Enc(m) --eval--> noisy ct --[budget low]-->  BOOTSTRAP
     ^                                            |  (homomorphic decrypt
     |                                            v   under encryption)
     +----------------- refreshed ct <------------+   resets noise budget

Wins when: the circuit depth is unbounded or unknown at parameter-selection time (deep ML, arbitrary programs). Real system: Gentry's original construction (STOC 2009); FHEW/TFHE and CKKS bootstrap in OpenFHE. Rejected here because: bootstrapping is the single most complex and costly FHE component; this blueprint teaches the leveled core first and defers it (PhaseDeferred §Phase 13, Deferred Features Register, Comparative table).

B — Approximate FHE (CKKS, real/complex arithmetic). Encode reals/complex with a scaling factor; treat rounding noise as acceptable.

  real vec --encode(scale Δ)--> R_q ct --add/mul--> ct --decode--> approx real vec
                                                          (plaintext + residual noise)

Wins when: the workload is numerical and error-tolerant — encrypted ML inference, statistics, signal processing — where approximate results are fine and throughput matters. Real system: HEAAN (Cheon–Kim–Kim–Song, Asiacrypt 2017), CKKS in SEAL/OpenFHE. Rejected here because: (1) scope — this blueprint is integer-exact; (2) security — sharing CKKS decryptions leaks the key (Li & Micciancio 2021, the IND-CPA^D gap) unless noise-flooded, a real footgun. Deferred (PhaseDeferred §Phase 9, ADR 4, Failure Modes, MM8).

C — Bit-wise fast-bootstrapping (TFHE). Encrypt bits; every Boolean gate bootstraps, so depth is effectively free but there is no SIMD batching.

  bits --enc--> LWE ct/bit --GATE(bootstrap)--> LWE ct/bit --...--> dec
                              (programmable bootstrap = gate + noise reset)

Wins when: the circuit is comparison/branching/lookup-heavy rather than arithmetic-heavy — decision trees, sorting, table lookups — where word-wise batched arithmetic is a poor fit. Real system: Zama TFHE-rs / Concrete (Chillotti–Gama–Georgieva–Izabachène, Asiacrypt 2016 / J. Cryptology 2020). Rejected here because: it is a different scheme with different primitives (programmable bootstrap, torus arithmetic) and no batching; this blueprint targets word-wise batched BFV (Comparative table, ADR 4).

D — Partially-homomorphic single-operation schemes. One algebraic operation only, no noise, no depth limit — extreme simplicity.

  Paillier (additive):     E(a)·E(b) = E(a+b)      # multiply ciphertexts -> add plaintexts
  exponential ElGamal:     E(a)·E(b) = E(a+b)      # additive in the exponent, small message space
  (textbook) RSA (mult.):  E(a)·E(b) = E(a·b)      # multiplicative only

Wins when: the application needs exactly one operation on encrypted data — private summation, voting, federated aggregation (additive), or a multiplicative-only mask — where a full RLWE stack is wasted overhead and ciphertexts must stay small (Paillier ≈ 768 B at n=3072, Capacity C6). Real systems: Paillier (1999) — kept in this design as the PHE half; exponential ElGamal for tiny tallies. Rejected as the BFV substitute because: a single operation cannot evaluate a·b + c-style circuits; BFV is required for bounded-depth arithmetic. This blueprint ships both — Paillier for the additive niche, BFV-lite for general leveled compute (ADR 3, §1.1).
