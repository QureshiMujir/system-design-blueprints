Project Number: 148

Project Name: Virtual Memory + Paging Subsystem

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Build a virtual-memory and paging subsystem — the kernel-level component that translates virtual to physical addresses, manages multi-level page tables, drives the page-fault path (demand paging, copy-on-write, swap-in, file-backed faults), maintains per-CPU TLB coherence via batched shootdown, and implements page replacement, swapping, huge pages, memory-mapped files, and per-process address-space isolation — targeting x86-64 and aarch64 as first-class instruction set architectures, implemented as a no_std Rust workspace runnable under QEMU as a bootable kernel image and as a userspace-hosted conformance target.

Phase-0 deliverable (numbered):

  1. vm-core — architecture-neutral types (PhysAddr, VirtAddr, PageFrameNumber, PageSize, PteFlags).
  2. vm-arch-x86_64 — 4-level page-table walker/mapper for x86-64.
  3. vm-arch-aarch64 — 4-level page-table walker/mapper for aarch64 (4K granule).
  4. vm-buddy — physical page allocator (buddy + per-CPU magazines).
  5. vm-vma — per-process VMA manager (red-black tree).
  6. vm-fault — page-fault dispatcher (anonymous + COW paths only in Phase 0).
  7. vm-harness — QEMU + software-walker conformance driver.
  8. conformance/ — fixture-driven test buckets for the six crates above.

System boundaries:

  • Provides: virtual-to-physical translation, page-table management, page-fault handling, VMA bookkeeping, physical page allocation, TLB invalidation, page replacement, swap, page cache, huge pages, NUMA placement, W^X/KASLR/KPTI security primitives.
  • Delegates: process scheduling (owns only the address-space handle, not the scheduler); the block-device driver backing swap/file I/O (consumes a BlockDevice trait); the interrupt controller/timer (consumes an InterruptController trait); the ELF loader for exec (Phase 6 consumes an already-parsed image).
  • Does NOT provide: a filesystem (the page cache indexes by (inode_id, offset) supplied by an external FS layer); a hypervisor (EPT/NPT nested translation is PhaseDeferred("§24")); a userspace runtime or libc.

Non-goals: 32-bit non-PAE address spaces; embedded MMU-less (no-MMU) targets; RISC-V (the architecture-crate pattern generalizes but a RISC-V crate is out of scope for this blueprint).

Deployment model: statically-linked no_std kernel image booted by a minimal loader under QEMU (-machine q35 for x86-64, virt for aarch64) for conformance; the same crates are designed to be vendored, unmodified, into a host kernel (bare-metal or hypervisor guest).

Target users/operators: kernel engineers integrating this subsystem into a host kernel; SRE/on-call operators running the resulting kernel in production, consuming the runbooks in Operational Readiness (§27) and the metrics in Performance Engineering (§31).

What later phases unlock: Phase 3 (§15) unlocks mmap/munmap/mprotect; Phase 5 (§17) unlocks demand paging and file-backed faults; Phase 6 (§18) unlocks fork/COW/exec; Phase 7 (§19) unlocks safe multi-core TLB coherence; Phases 8–9 (§20–§21) unlock memory overcommit via replacement + swap; Phase 10 (§22) unlocks memory-mapped files; Phase 11 (§23) unlocks huge pages and NUMA; Phase 12 (§24) unlocks the security posture (W^X, KASLR, KPTI, Meltdown/Spectre mitigations).

Recommended language: Rust, no_std (core + alloc). Rationale: ownership eliminates use-after-free on the exact object class (physical pages, PTEs) responsible for the majority of historical VM CVEs; the borrow checker statically rejects the aliased-mutable-access pattern behind double-free and TOCTOU page-table races; unsafe is localized to the arch crates' raw MMU register access, auditable in isolation (ADR-01). Rejected: C — no structural mitigation for the CVE classes in §25/§26 (ADR-01's sixth column names the regime where C still wins). Rejected: C++ — RAII helps but aliasing/UB rules are not statically enforced at the granularity concurrent PTE mutation needs. Rejected: Zig — weaker static memory-safety story than Rust's borrow checker for concurrent structures; no_std OS-kernel tooling less mature as of 2026.

Prerequisites: computer architecture (MMU, cache hierarchy, interrupts), concurrent programming (memory ordering, lock-free structures), operating system fundamentals (processes, scheduling, syscalls), familiarity with at least one production kernel's mm subsystem (Linux preferred).

Estimated timeline: Phase 0 — 3 weeks. Full system (Phases 0–12) — 9 months at one senior engineer full-time, or 5 months with a two-engineer team split by architecture (one owns x86-64 + core, one owns aarch64 + NUMA/huge pages).

Deferred features (registered in full at Deferred Features Register, §38):

  • Multi-Gen LRU replacement — PhaseDeferred("§20").
  • KSM (kernel same-page merging) — PhaseDeferred("§18").
  • userfaultfd-equivalent userspace fault interception — PhaseDeferred("§17").
  • DAX (persistent-memory direct access) — PhaseDeferred("§22").
  • EPT/NPT hypervisor nested paging — PhaseDeferred("§24").

  • Core-scheduling / SMT co-tenancy isolation — PhaseDeferred("§24").

2. Why Build This

Virtual memory is the substrate every other kernel subsystem stands on: the scheduler context-switches address spaces, the filesystem's page cache is a VM data structure, the network stack's zero-copy paths pin VM pages, and the security model's core guarantee — one process cannot read another's memory — is the page-table boundary. Building this from scratch teaches concurrent systems programming at its hardest: the same physical page is simultaneously a target of a page-fault handler on core A, a writeback daemon on core B, and a TLB-invalidation IPI handler on core C, with a sub-millisecond budget before the application-visible hiccup.

Historically this is where OS architecture was invented. Multics (1965) introduced segmentation-with-paging; Corbató's paging experiments set the latency/thrashing vocabulary still used today; Denning's working-set model (1968) is still the mental model production replacement algorithms approximate; the 2018 Meltdown/Spectre disclosures rewrote the field's threat model around speculative execution crossing page-table-enforced boundaries. This project walks that entire arc: pure translation → demand paging → replacement → security isolation → speculative-execution defense.

Engineering muscles built: lock-free/per-CPU data-structure design (buddy magazines, TLB pending sets); distributed-consensus-shaped reasoning applied within one machine (TLB shootdown is N-replica invalidation with an ACK protocol); reference-counting discipline under concurrency (COW); latency-budget engineering (page-fault p99 in microseconds); threat modeling against a hardware trust boundary that leaks through cache timing rather than a logical bug.

Cross-links to sibling systems in this portfolio: the buddy allocator's per-CPU magazine design generalizes directly to project #112 (Concurrent Allocator); the TLB-shootdown IPI-batching pattern is the same "batch cross-core invalidation" shape used by project #131 (Distributed Cache Invalidation); the page-fault dispatcher's state-machine shape recurs in project #140 (Async Runtime Scheduler)'s poll loop; the differential-testing methodology mirrors project #103 (Consensus Protocol Verifier).

Calibration value: after this project an engineer can read any production kernel's mm/ or sys/vm/ tree and map every function to one of the eleven concepts this blueprint names (walker, mapper, VMA, buddy, fault dispatcher, TLB pending set, replacement queue, swap tier, page cache, huge-page promoter, security primitive) — the single highest-leverage skill for kernel-adjacent systems work generally (database buffer pools, JIT compilers, GPU driver memory managers).

What Mastery Looks Like:

  • Trace a mprotect(W→R) call through VMA split, PTE permission downgrade, and TLB shootdown without consulting source — Phase 3 (§15), Phase 7 (§19).
  • Explain why a COW fast path (refcount==1) is safe without a lock, and where the lock is actually required — Phase 6 (§18).
  • Diagnose a stale-TLB bug from a crash dump by naming the missing happens-before edge — Phase 7 (§19), invariant I3.
  • Compute page-table memory overhead for an arbitrary resident-set size from first principles — Back-of-Envelope Capacity Model (§35).
  • Design a page-replacement policy for a novel access pattern by reasoning from Denning's working-set model, not by copying Linux's LRU — Phase 8 (§20), MM5.
  • Explain Meltdown and Spectre well enough to review a kernel patch's speculative-execution safety — Phase 12 (§24), Threat Model (§25).
  • Redesign this subsystem around an inverted page table or a single-address-space capability model and state exactly what is traded — Alternative Architectures (§37).

VMA Manager — owns the per-process address-space description; every mmap/munmap/mprotect mutates this tree first (§15). Huge Pages / NUMA — cross-cutting placement and promotion policy consulted by the fault dispatcher and allocator (§23). Security Layer — cross-cutting enforcement consulted by the mapper (W^X), the boot sequence (KASLR), and the syscall/interrupt entry trampoline (KPTI) (§24). 6. Design Principles

  1. P1 — Page-table walker is pure. No side effects; deterministic function of (root, vaddr). Tradeoff: forbids caching state inside the walker itself. Operational implication: any two calls with the same inputs are diffable in a crash dump. Violating it: a stateful walker makes stale-TLB bugs indistinguishable from walker bugs.
  2. P2 — VMA is immutable until torn down. Mutation creates a new VMA and replaces (rbtree swap), never edits in place. Tradeoff: extra allocation per mprotect/split. Operational implication: a VMA pointer captured under a read lock is safe to read after the lock is dropped. Violating it: reintroduces the exact in-place-mutation race this principle exists to remove.
  3. P3 — Allocation decoupled from replacement. The buddy allocator has zero eviction-policy knowledge (ADR-24). Tradeoff: replacement must go through an explicit "free candidate" handoff. Operational implication: allocator and replacement policy are independently benchmarkable and independently swappable. Violating it: couples the fastest-path code (alloc/free) to the most-complex-to-change code (policy).
  4. P4 — Per-CPU fast paths before global locks. Magazines (§16), lazy TLB (§19), per-CPU pending sets. Tradeoff: memory overhead of N per-CPU structures. Operational implication: contention metrics are per-CPU, not global. Violating it: a single global lock on the hot allocation path caps throughput at one CPU's worth of work.
  5. P5 — TLB shootdowns batched at epoch boundaries. One IPI per epoch, not per modification (§19, ADR-26). Tradeoff: bookkeeping cost of the pending set. Operational implication: bulk munmap cost is O(1) IPIs, not O(pages). Violating it: a 1 GiB munmap costs 5 orders of magnitude more IPIs (§35 item 4).
  6. P6 — W^X enforced unconditionally. No PTE has WRITABLE and EXECUTABLE simultaneously (I6). Tradeoff: JIT compilers need a write-then-switch-to-exec dance. Operational implication: closes an entire exploit class structurally. Violating it: reopens the dominant code-injection primitive of the 2000s–2010s.
  7. P7 — Determinism in panic/fault paths. Crashes are reproducible from the same trace. Tradeoff: no randomized backoff in the fault path itself (randomization lives only in KASLR's one-time boot choice). Operational implication: a kdump reproduces bit-for-bit under the same input trace. Violating it: "flaky" kernel panics are undebuggable.
  8. P8 — The verifier asserts invariants, not comments. Every I# (§7) has an automated detector in vm-verifier. Tradeoff: verifier overhead in debug builds (disabled in release). Operational implication: an invariant violation is a test failure, not a postmortem discovery. Violating it: invariants rot silently as the codebase changes.
  9. P9 — Multi-target from day one. x86-64 and aarch64 both first-class from Phase 0. Tradeoff: ~30% more Phase-0 implementation work. Operational implication: no architecture-specific assumption can leak into vm-core because a second arch immediately contradicts it. Violating it: a single-arch-first design bakes in x86-specific assumptions (e.g. INVPCID availability) that break aarch64 porting later.
  10. P10 — Reference counting is the sole authority for shared-page lifetime. COW pages, page-cache pages (I5). Tradeoff: every mapping path must remember to increment/decrement. Operational implication: a page's refcount is the single source of truth for "can this be freed." Violating it: double-free or premature-free races (§26 FM classes).
  11. P11 — NUMA locality preferred, never mandatory. First-touch + fallback list, no forced interleave by default (ADR-28). Tradeoff: node imbalance under adversarial access patterns. Operational implication: the common case (local access) is fast; the rare case (cross-node) is correct but slower, never wrong. Violating it: forced locality either wastes memory (over-replication) or produces starvation on a busy node.
  12. P12 — Every invariant has a telemetry signal, not just an assertion. Each I# emits a counter on violation-adjacent conditions (near-miss), not only on hard failure. Tradeoff: metric cardinality. Operational implication: an on-call engineer sees a trend (rising near-misses) before a hard failure. Violating it: the first signal of a brewing invariant violation is the crash itself.
  13. P13 — Fail loud in debug, fail safe in release. Debug builds panic on invariant violation; release builds degrade (SIGSEGV the offending process, or contain to the smallest blast radius) per §26. Tradeoff: behavioral divergence between debug and release requires the conformance suite to run both. Operational implication: production never silently corrupts on a caught violation. Violating it: either debug builds are too slow to run the full fuzz canary, or release builds crash the whole machine for a single process's bug.
  14. P14 — Telemetry before optimization. Fragmentation, eviction rate, fault rate, and TLB-shootdown rate are exposed (§27) before any tuning work begins. Tradeoff: instrumentation overhead must itself be budgeted (kept < 1% per M-table §31). Operational implication: every performance claim in this document is falsifiable against a live counter. Violating it: tuning decisions made on guesswork regress silently.

8. Domain Model

8.1 Address Translation Model

Translation is the pure function walk: (root: PhysAddr, vaddr: VirtAddr) -> Result<PhysAddr, WalkFault> (P1). A VirtAddr on x86-64 must be in canonical form: bits 63–48 equal bit 47 (sign-extended); a non-canonical address faults before any table is consulted (§8.7). The hardware MMU caches walk's result in the TLB; vm-tlb never re-derives the result, only invalidates it (§8.3).

8.6 Worked Example: fork() + COW Write Fault

  1. Parent process P has one Anonymous VMA [0x1000, 0x2000) mapped PRESENT+WRITABLE, frame F, refcount(F)=1.
  2. fork() clones the VMA rbtree (§18, P2); for each present user PTE, clears WRITABLE in both parent's and child's PTE; refcount(F) → 2.
  3. TLB shootdown (§19) invalidates any cached WRITABLE translation of F on every CPU that had it cached (I3).
  4. Child writes to 0x1000. Hardware raises a Protection { attempted_write: true } fault (§8.4 row 5).
  5. vm-fault checks refcount(F): 2 ⇒ slow path. Allocates frame F', copies F→F', maps F' WRITABLE in the child, decrements refcount(F) → 1 (ADR spans: I5, P10).
  6. Parent's next write to 0x1000 faults identically; refcount(F)=1 at that point ⇒ fast path: re-mark F WRITABLE in place, no copy (I5 satisfied without an allocation).

8.8 Failure-Path Example

Page-cache writeback races a truncate(): writeback thread samples a dirty page's (inode, offset) at t0; truncate() shrinks the file at t1, invalidating that offset's page-cache entry; writeback's write-out at t2 targets a now-invalid region. Detection: the page-cache entry carries a generation counter bumped by truncate; writeback re-checks the generation immediately before issuing I/O and aborts on mismatch (§22, I8's atomic- dirty-sample principle extended to generation-checking). Recovery: the aborted write is dropped (the page is legitimately gone); no corruption because the check-then-act window is closed by the generation compare happening under the same lock that truncate takes to invalidate entries.

13. Phase 1 — Core Types & Address Translation Primitives

13.1 Objectives

Define PhysAddr, VirtAddr, PageFrameNumber, PageSize, PteFlags in vm-core (§11); enforce construction-time invariants so no later phase can build an invalid address (P1's purity depends on inputs already being valid).

13.2 Detailed Implementation Steps

Implement PhysAddr::new rejecting values above the 52-bit MAXPHYADDR ceiling (§4, I1); implement VirtAddr::new rejecting non-canonical values (§8.1, §8.7); implement vpn_indices per the §8.2 table, parameterized on Arch so vm-core itself never branches on architecture (P9); document every PteFlags bit against the Intel SDM Vol. 3A / Arm ARM VMSA chapter it comes from (§5 Required Reading, applied here).

13.3 Deliverable

vm-core compiles standalone (no arch crate dependency); construction functions reject every malformed input in §8.7's first two rows.

13.4 Acceptance Criteria

Property test: 100,000 random u64 values through PhysAddr::new / VirtAddr::new — zero panics, and every accepted value round-trips through Display (hex, 0x-prefixed) losslessly; a compile_fail test asserts an unaligned PhysAddr literal is rejected at construction, not at use.

13.5 Conformance Fixtures

fixtures/addr/canonical_boundary.json — the exact bit-47 boundary values (pass/fail pairs). fixtures/addr/maxphysaddr_boundary.json — 52-bit boundary. fixtures/addr/malformed_batch.json — the §8.7 malformed-input table as executable cases.

13.6 Pitfalls

  • PhysAddr(u64) is a 64-bit container but only 52 bits are ever valid (I1); a checker that forgets the ceiling accepts garbage silently.
  • PteFlags bit layout differs between x86-64 and aarch64 (§8.5); a shared bit-position constant reused across arches is a latent bug — per-arch tables are separate and re-exported, never unified.

13.7 Performance Concerns

Construction functions are #[inline], zero-allocation, branch-predictable (single range check) — dominates nothing measurable; not on any hot path directly but called on every fault (§17), so a mispredicted branch here is amplified system-wide.

13.8 Edge Cases

Zero address (VirtAddr(0)) is canonical and valid — must not be special-cased as "null" (unlike userspace convention); a bit-47 value of exactly the boundary (0x0000_7FFF_FFFF_FFFF / 0xFFFF_8000_0000_0000) is the property test's designed edge (13.5).

13.9 Failure Analysis

A PteFlags bit added for one architecture without cross-checking the other's re-export breaks that architecture's build silently until the conformance suite's per-arch bucket runs — mitigated by requiring both arch buckets green before merge (ADR-20).

13.10 Operational Notes

No runtime observability yet (types only); docs/adr/ADR-05.md and docs/adr/ADR-30.md get authored here since this phase is where the multi-arch decision first has code behind it.

14. Phase 2 — Page-Table Walker & Multi-Level Mapper

14.1 Objectives

Implement the pure walk function and the map/unmap mutators per architecture (§8.1, §8.2), satisfying P1 (purity) and I1/I11 (frame-range and ownership invariants).

14.2 Detailed Implementation Steps

vm-arch-x86_64::walk(root, vaddr) -> WalkResult descends PML4→PDPT→PD→PT consulting PRESENT at every level (P1); map(root, vaddr, phys, flags) allocates intermediate levels from vm-buddy (§16 dependency) as needed and sets I11's ownership tag; unmap(root, vaddr, len, tlb_strategy) removes mappings and hands off to vm-tlb (§19) per the requested strategy. Mirror for vm-arch-aarch64 across all three granules (§8.2 table). A software-walker (in vm-harness) duplicates the logic for cross-checking in conformance without touching hardware state.

14.3 Deliverable

walk/map/unmap for both arches; vm-harness's software walker; a pretty_print(root) debug dump (ASCII tree of addresses + flags).

14.4 Acceptance Criteria

Property test: insert N=10,000 random mappings, walk every one and assert translation matches; remove half, walk and assert NotPresent. Walk latency on a warm-TLB miss < 50 ns p50 (§4, M1). Map of a single page < 500 ns p50 (dominated by intermediate-level buddy allocation, amortized).

14.5 Conformance Fixtures

buckets/pagetable/insert_walk_remove.json — the property-test corpus. buckets/pagetable/four_level_boundary.json — index-extraction boundary values per §8.2 row. buckets/pagetable/malformed_walk.json — non-canonical and out-of-range inputs from §8.7, expecting WalkFault, never a panic.

14.6 Pitfalls

  • A walker that checks only the last level for PRESENT misses early exits at intermediate levels — must consult every level (P1, 14.2).
  • Forgetting the GLOBAL bit on kernel mappings causes them to flush on every ASID/PCID context switch (§8.5); set explicitly at map time for every kernel-space mapping.
  • The mapper allocating intermediate levels without registering I11's ownership tag lets a later unmap from a different root free a still-shared table.

14.7 Performance Concerns

Walk latency dominates every fault path measurement in §4/§31; the intermediate-level buddy allocation on map is the only allocation in the hot path — batching consecutive map calls (e.g. for a multi-page fault) to amortize one intermediate-level allocation across several leaf entries is the primary lever (ties to P4).

14.8 Edge Cases

A map call that lands exactly at a huge-page-eligible boundary but with PageSize::Small4K requested must not silently promote — promotion is Phase 11's (§23) explicit responsibility, never implicit in the mapper.

14.9 Failure Analysis

An off-by-one in the descent recursion (descends one level too few) returns the intermediate page-table's own physical frame as if it were the leaf translation — manifests as random-looking zeroed memory (freshly-zeroed intermediate tables) rather than a crash; caught only by vm-verifier::validate_pagetable's leaf-is-leaf assertion (I1), which is why that assertion runs on every conformance bucket, not just pagetable/.

14.10 Operational Notes

pretty_print is the primary on-call tool for a translation-looks-wrong report; vm_pt_range_violation (I1 telemetry) is the alerting signal for this phase's class of bug in production.

15. Phase 3 — VMA Manager

15.1 Objectives

Implement the per-process address-space model: the rbtree of VmAreaStructs and its four primitives (§8, P2), enforcing I4 (no overlap).

15.2 Detailed Implementation Steps

find_vma(mm, addr) — O(log n) rbtree lookup by containment. insert_vma — rejects on overlap (I4) per §8.7 row 3. split_vma_at — P2: removes the original, inserts two new immutable VMAs (never edits in place). merge_adjacent — called after mprotect when two neighbors become protection-compatible; removes two, inserts one. Half-open interval semantics [start, end) fixed once (§8.4) and used identically in every caller (terminology lock: the same name for the same concept everywhere in this document).

15.3 Deliverable

vm-vma crate exposing the rbtree + four primitives; a vma_dump(mm) debug printer ([start..end) prot kind).

15.4 Acceptance Criteria

1,000-VMA process: insert < 1 µs p50, find < 200 ns p50 (§4). Property test: random insert/split/merge sequences never produce an overlapping pair (I4 exhaustively checked after every operation).

15.5 Conformance Fixtures

buckets/vma/insert_find_merge_split.json — the property-test corpus. buckets/vma/overlap_rejection.json — §8.7 row 3 malformed-insert cases. buckets/vma/boundary_semantics.json — two VMAs meeting exactly at one address, asserting half-open ownership.

15.6 Pitfalls

  • Two VMAs meeting at an address must agree which owns the boundary — the half-open convention (right VMA owns its start, left VMA does not own its end) must be enforced identically in find_vma and insert_vma or a one-byte gap/overlap silently appears.
  • A VMA inserted at the same address as an existing one must error (I4), never silently replace — the caller is responsible for an explicit merge/replace decision.

15.7 Performance Concerns

The rbtree's rebalancing cost after split_vma_at/merge_adjacent is amortized O(log n); a workload doing many small mprotect calls on adjacent regions (fragmenting then re-merging) is the pathological case — tracked via a vm_vma_churn_rate counter (P14).

15.8 Edge Cases

split_vma_at at exactly start or end (a no-op split) must be idempotent, not produce a zero-length VMA; merge_adjacent across a VMA with a different file mapping must refuse (§8's aliasing pitfall) even if protections match.

15.9 Failure Analysis

A merge that combines two VMAs with different vm_file backings silently aliases file-backed ranges — the guard is an explicit file-identity check in merge_adjacent before the protection-compatibility check, ordered so the file check can never be short-circuited out.

15.10 Operational Notes

vma_dump output is the first thing attached to any address-space-related bug report; vm_vma_overlap_rejected (I4 telemetry) distinguishes "caller bug" (rejected, handled) from a real invariant breach (would mean I4's insert-time check itself failed, a P0).

16. Phase 4 — Buddy Allocator & Physical Memory

16.1 Objectives

Implement the physical page allocator: per-order free lists, buddy coalescing (I10), and per-CPU magazines (P4, ADR-04), decoupled entirely from replacement policy (P3).

16.2 Detailed Implementation Steps

alloc(order, node_hint) pops from the calling CPU's magazine (§35 item 5's

99% hit-rate target) or falls to the global per-order free list, splitting a higher-order block if needed. free(pfn, order) pushes to the magazine or, on magazine-full, half-drains to the global list (Bonwick & Adams's magazine paper, §5 Required Reading, applied here) and coalesces with the buddy (buddy_of, I10) when the buddy is also free at the same order. NUMA-aware: each node gets its own free lists + magazines; cross-node fallback follows the SLIT-derived order (§23 dependency, forward reference resolved there).

16.3 Deliverable

vm-buddy::alloc/free; magazine refill/drain; buddy_dump() debug printer (per-order freelist length + per-CPU magazine state).

16.4 Acceptance Criteria

Hot path (magazine hit) < 100 ns p50, < 300 ns p99 (§4, M4). Cold path (global list) < 500 ns p50. Cold path with split < 1 µs p50. Property test: 10,000 random alloc/free sequences never leave two free buddies at the same order un-coalesced (I10) and never double-allocate a PFN (I7).

16.5 Conformance Fixtures

buckets/buddy/alloc_free_property.json — the alloc/free property corpus. buckets/buddy/coalesce_boundary.json — buddy-pair coalescing edge cases. buckets/buddy/double_free_detection.json — §8.7 row 6's misaligned-order double-free, expecting vm_double_free_detected.

16.6 Pitfalls

  • The buddy of PFN p at order k is p XOR (1 << k); if p isn't aligned to 2^k the XOR produces a nonsense address outside the region (16.5 fixture; ties to §8.7 row 6).
  • Coalescing requires the buddy to be free and the same order — the per-page order metadata is the load-bearing structure that makes this checkable at all (P8).
  • A magazine drain that fails to coalesce before pushing to the global list produces avoidable external fragmentation, visible only in the fragmentation-histogram metric (P14), not in correctness tests.

16.7 Performance Concerns

The half-drain heuristic (drain to 32 of 64 slots, not to empty) avoids the refill-immediately-after-drain thrash; NUMA cross-node fallback costs an extra 50–100 ns for the L3 miss (§4) — acceptable because it's the rare path (P11).

16.8 Edge Cases

A node-local allocation request when the local node is fully exhausted must fall through the SLIT-derived order, never fail outright while remote memory exists (P11); an order-11 (max, §35 item 5) request larger than any single free block must fail cleanly (None), never attempt an unsupported cross-block merge.

16.9 Failure Analysis

Double-free (I7 violation): the freelist contains the same PFN twice; subsequent alloc hands the same physical page to two independent callers — the exact class of bug that produced historical VM CVEs; caught by the per-PFN tracking bitmap in debug builds (P13) and refused (not silently accepted) in release builds via the "expected next pointer" freelist invariant.

16.10 Operational Notes

vm_coalesce_failure and a fragmentation histogram (requested-order vs. satisfied-order) are the two counters an on-call engineer checks first for an "OOM despite free memory" report (§27, §36 Q on this exact scenario).

17. Phase 5 — Page-Fault Handler & Demand Paging

17.1 Objectives

Implement handle_fault (§11) as the single dispatch point from a hardware trap, covering anonymous demand-paging and dispatch stubs for the paths later phases complete (file-backed, swap-in, COW), satisfying I12 (bounded retry, no infinite fault loop).

17.2 Detailed Implementation Steps

Save the trap frame; classify FaultKind (§8.4); find_vma(mm, addr) (Phase 3, §15 dependency); no VMA or protection violation ⇒ fatal per §8.4's table; not-present + Anonymous ⇒ vm-buddy.alloc a zeroed page, vm-arch-*::map, return (P1's walker stays pure; the fault handler, not the walker, does the allocation side-effect). Retry counter (I12) caps at 8 attempts per fault before escalating to FaultError::KernelOops. File-backed and swap-in branches are stubbed to FaultError::KernelOops in this phase (completed in Phase 9 §21 and Phase 10 §22 respectively) — a stub is a correctly-erroring placeholder, never a silent no-op, so the retry-counter invariant (I12) holds even before those phases land.

17.3 Deliverable

vm-fault::handle_fault covering the Anonymous row of §8.4's dispatch table; per-fault tracing (ADR-17 tracepoints) at vm_fault=trace level.

17.4 Acceptance Criteria

Fault on a present page: 0 µs (handled by hardware, never reaches this code — asserted via a counter that should read zero in the property test). Fault requiring anonymous allocation: < 5 µs p50, < 15 µs p99 (§4, M3). Bucket fault/anonymous_dispatch.json green; zero instances of the retry counter reaching 8 in 100,000 fixture replays.

17.5 Conformance Fixtures

buckets/fault/anonymous_dispatch.json — the demand-paging happy path. buckets/fault/no_vma_fatal.json — §8.4 row 1. buckets/fault/ protection_violation.json — §8.4 row 6. buckets/fault/retry_exhaustion.json — a synthetic permanently-failing mapping, asserting escalation at exactly retry 8 (I12).

17.6 Pitfalls

  • A user-space fault on a kernel address must be classified fatal before any VMA lookup — checking VMAs first on a kernel address risks interpreting kernel VMAs (if any are visible in that lookup path) under user-fault semantics.
  • A stub path that returns Ok(()) without actually mapping violates I12 immediately (an unbounded silent retry loop) — every stub in 17.2 returns Err, never a fake success.

17.7 Performance Concerns

The anonymous path's only allocation is the buddy call (Phase 4, §16); the zero-fill itself (writing zeros to the fresh page) is the dominant cost at larger page sizes and is why huge-page zero-fill (Phase 11, §23) uses non-temporal stores to avoid cache pollution.

17.8 Edge Cases

A fault at the exact boundary between two VMAs (address equals one VMA's end, which per §15's half-open convention belongs to neither or the next) must resolve to exactly one VMA, never both or neither ambiguously — this is find_vma's contract (§15), exercised here as a fault-path integration case, not re-implemented.

17.9 Failure Analysis

A fault handler that returns "handled" without mapping the page produces an infinite hardware-fault loop at the same instruction — I12's retry counter converts this from "hung core" to "diagnosable KernelOops with retry-count telemetry" within 8 iterations, bounding the blast radius to microseconds instead of a wedged CPU.

17.10 Operational Notes

RUST_LOG=vm_fault=trace (ADR-17) is the first on-call step for a fault-related report; vm_fault_retry_exhausted (I12 telemetry) is the alerting signal that distinguishes "expected occasional retry" from "a systemic mapping bug."

18. Phase 6 — Fork, Copy-on-Write & Exec

18.1 Objectives

Implement fork()'s VMA-tree clone + COW marking and the write-fault COW resolution path (§8.6's worked example), satisfying I5 (refcount-tracks- mapping-count) and P10 (refcounting as sole lifetime authority).

18.2 Detailed Implementation Steps

fork: clone the rbtree (P2 — cloning immutable VMAs is a cheap structural copy); for each present user PTE in the parent, clear WRITABLE in both parent's and child's PTEs (§8.5), incrementing the shared frame's refcount (I5); issue a batched TLB shootdown (Phase 7, §19 dependency) for every downgraded mapping before fork returns to either process. Write fault on a COW-marked page: allocate a new frame (vm-buddy, §16), copy contents, map the new frame WRITABLE in the faulting process only, decrement the original frame's refcount (I5). Fast path: if refcount reads 1 at fault time, skip the copy — re-mark the existing frame WRITABLE in place (§8.6 step 6). Pinned pages (DMA targets, a separate VMA flag) never enter COW — fork deep-copies pinned VMAs immediately rather than marking read-only.

18.3 Deliverable

COW integrated into vm-fault; fork's VMA-clone + PTE-downgrade path in vm-vma/vm-arch-*.

18.4 Acceptance Criteria

Fork of a 1 GiB process: < 10 ms p50 (page-table clone dominates, §4). First write fault per page after fork: < 5 µs p50. Property test: after N random fork+write sequences, every frame's refcount exactly equals its read-only-PTE count (I5, exhaustively checked).

18.5 Conformance Fixtures

buckets/cow/fork_downgrade.json — the PTE-downgrade + refcount-increment path. buckets/cow/write_fault_slow_path.json — refcount>1 copy path. buckets/cow/write_fault_fast_path.json — refcount==1 in-place path (§8.6 step 6). buckets/cow/pinned_page_no_cow.json — a pinned VMA fork, asserting deep-copy not COW-marking.

18.6 Pitfalls

  • Pinning (DMA) must not COW; a pinned page marked read-only by an oblivious fork breaks an in-flight transfer the instant the DMA engine writes to what it believes is still its buffer.
  • A page with refcount 1 at write-fault time should take the fast path (re-mark writable in place, no copy) — always taking the slow path is correct but wastes an allocation+copy on every single-owner page touched after a fork whose sibling already faulted and released its share.
  • A refcount decrement that races two children's near-simultaneous COW faults on the same original frame must be atomic (I5) — a read-modify-write without atomicity briefly under-counts, permitting a premature free while a translation still points at the frame.

18.7 Performance Concerns

Fork's page-table clone is O(resident pages); the PTE-downgrade + shootdown is the dominant cost at large RSS — batching every downgraded page into one shootdown epoch (P5, Phase 7 dependency) rather than one shootdown per page is what keeps the 10 ms/GiB target (18.4) achievable.

18.8 Edge Cases

Two children of the same parent both write-fault the same inherited page "simultaneously" (a fork-fork chain, §8.6): each must independently observe a consistent refcount via the atomic decrement (18.6) — neither may observe a torn intermediate state that lets both take the fast path.

18.9 Failure Analysis

A COW refcount that misses the atomicity requirement (18.6) produces multiple writers on "the same" page — a silent miscompile of user-space data, not a crash, making it the hardest class of bug in this phase to detect without the refcount-vs-PTE-scan verifier cross-check (I5's detection column, §7).

18.10 Operational Notes

vm_cow_refcount_mismatch (I5 telemetry) is the alerting signal; a production report of "child process sees parent's post-fork writes" (or vice versa) is diagnosed by replaying the fork+write trace through vm-verifier against this phase's fixtures.

19. Phase 7 — TLB Management & Shootdown

19.1 Objectives

Implement the per-CPU pending-invalidation set and batched shootdown protocol (§8.3, P5, ADR-08), satisfying I3 — the invariant every prior phase (14, 15, 18) has been depending on as a forward reference.

19.2 Detailed Implementation Steps

PendingSet::record(cpu, req) accumulates a (asid, range) tuple in the modifying CPU's per-CPU bitmap on every page-table write that changes permission or presence (§11). flush_epoch(cpu) runs at epoch boundaries (syscall exit, explicit munmap/mprotect completion) — issues one IPI per peer CPU carrying the accumulated bitmap; each peer's IPI handler executes invlpg/TLBI for every entry and ACKs. The modifying CPU blocks the "write is now visible" state transition (§8.3 diagram, step 6) until every ACK arrives (I3). is_lazy(cpu) — a CPU not currently running under the affected asid (e.g. idle or running a different process) is skipped; its TLB is implicitly stale-safe because it will re-walk on next use of that asid. x86's INVPCID (Intel SDM Vol. 3A, §5 Required Reading) invalidates by PCID without a full flush where available (Haswell+); falls back to full-flush-on-context-switch otherwise.

19.3 Deliverable

vm-tlb::PendingSet, flush_epoch, is_lazy; the shootdown IPI handler.

19.4 Acceptance Criteria

IPI latency per peer: < 1 µs p50, < 3 µs p99 (§4, M6). Batched shootdown for N invalidations in one epoch: < 1 µs fixed cost + ~0 marginal per entry after the first (bitmap already prepared) — verified against the naive 262,144-IPI baseline computed in §35 item 4. Property test: no consumer observes a page-table write as "visible" before every targeted peer's ACK (I3, exhaustively checked via a simulated multi-core interleaving).

19.5 Conformance Fixtures

buckets/tlb/ordering_invariant.json — the write-then-shootdown-then-visible ordering property corpus. buckets/tlb/lazy_skip.json — asserts an idle CPU under a different asid receives no IPI. buckets/tlb/batch_vs_naive.json — measures IPI count for a bulk munmap, asserting the batched count.

19.6 Pitfalls

  • An IPI that logically arrives (network/interrupt delivery) before the underlying page-table write is architecturally visible to the peer (a missing release/acquire fence pairing) lets the peer's invlpg run against the old PTE, then re-cache it — the shootdown "succeeds" but leaves the stale entry behind.
  • Lazy-TLB tracking that forgets to re-check is_lazy on a context switch (a CPU that was idle becomes active under the affected asid mid-epoch) can skip a peer that now actually needs the invalidation.

19.7 Performance Concerns

This phase is where P5's payoff is measured directly: the 262,144× reduction factor computed in the Back-of-Envelope Capacity Model (§35 item 4) is the headline number; INVPCID's incremental benefit over full-flush is secondary (single-digit percent on top of batching, not a multiplier).

19.8 Edge Cases

A shootdown epoch that spans a CPU hot-unplug (peer disappears mid-wait) must not block forever waiting for an ACK that will never arrive — the epoch's ACK-wait has a bounded timeout, escalating to the soft-lockup detector's territory (§26, §36's stuck-mmap runbook) rather than hanging.

19.9 Failure Analysis

A missing fence between page-table write and IPI emission (19.6) is the single highest-value bug class this phase exists to prevent — it is P1/I3's entire reason for being; detection is exclusively via the ordering property test (19.5), because the bug is invisible to any single-threaded test and most multi-threaded tests that don't specifically interleave at the instruction level.

19.10 Operational Notes

vm_tlb_shootdown_latency_us (I3 telemetry) feeds the "TLB shootdown storm" runbook (§36); a sustained high-percentile spike here is the leading indicator of an unbatched mprotect/munmap caller upstream, not a bug in this phase itself.

20. Phase 8 — Page Replacement (Active/Inactive + Clock)

20.1 Objectives

Implement the two-queue active/inactive LRU with second-chance clock sweep (§5 Required Reading: Denning 1968, Belady 1966; ADR-06), satisfying I8 (no eviction without writeback) and I9 (no pinned page queued), decoupled from allocation (P3).

20.2 Detailed Implementation Steps

Every page fault that resolves to a mapping promotes the frame to Active (§11 PageState). A periodic daemon (default 100 ms interval, more frequent under memory pressure) sweeps Inactive: for each page, check the ACCESSED bit (§8.5); if set, clear it and promote to Active (second chance); if clear, mark as an eviction candidate. Demotion from Active to Inactive happens on the same sweep when a page's access-bit has been clear across a full prior cycle. Eviction dispatches by page type: clean anonymous ⇒ discard (re-zero on next fault); dirty anonymous ⇒ writeback to vm-swap (§21) first (I8); clean file-backed ⇒ discard (re-read from vm-pagecache's backing file, §22); dirty file-backed ⇒ writeback to the file first (I8). Working-set estimation (Denning's model, applied here per §5) samples access bits at the same 100 ms cadence to bias eviction away from a process's estimated working set.

20.3 Deliverable

vm-replacement's two queues + sweep daemon; promote/scan_inactive (§11).

20.4 Acceptance Criteria

Eviction scan throughput: 1,000 pages/ms p50 (§4, M7). Property test: no Pinned-state page ever appears in either queue across 10,000 random pin/unpin/fault sequences (I9). No eviction proceeds past the dirty-check without a completed writeback acknowledgment (I8), verified by fault- injecting a writeback failure and asserting the page remains queued, not freed.

20.5 Conformance Fixtures

buckets/replacement/sweep_promote_demote.json — the clock-sweep property corpus. buckets/replacement/pinned_exclusion.json — I9 corpus. buckets/replacement/dirty_writeback_gate.json — I8 corpus, including a fault-injected writeback failure.

20.6 Pitfalls

  • Pinned pages omitted from queue-membership checks at insertion time (not just eviction time) can still get queued by a code path that doesn't consult PageState::Pinned before enqueue — the check belongs at enqueue, not only at evict.
  • A thrashing workload (resident set slightly exceeds available RAM) produces constant swap-in/swap-out; the mitigation is "swap weight" (throttling swap-in bandwidth, §21 dependency) so the workload backs off rather than the daemon spending all cycles re-faulting what it just evicted.

20.7 Performance Concerns

The sweep's per-page cost is dominated by the ACCESSED-bit check (a page-table read, not a full walk since the PTE location is cached in the PageDescriptor); 1,000 pages/ms (20.4) assumes this cached-location fast path — a design that required a full walk per swept page would be roughly two orders of magnitude slower (§35 item 2's walk-latency numbers).

20.8 Edge Cases

A page promoted to Active by a fault the same instant the sweep daemon is mid-scan of Inactive must not be evicted by that in-flight scan — the sweep takes a per-page compare-and-swap on PageState before evicting, losing the race gracefully (page survives) rather than racing to a double free.

20.9 Failure Analysis

Evicting a page that is the destination of in-flight DMA (a pin that was never registered, a P8/I9 process failure rather than a policy failure) corrupts the transfer silently — this is why I9 is enforced structurally at enqueue (20.6), not only checked defensively at evict time.

20.10 Operational Notes

vm_pinned_page_queued (I9 telemetry) and vm_evict_without_writeback (I8 telemetry) are both P0-alerting counters — either firing in production indicates a structural invariant breach, not a performance tuning question.

21. Phase 9 — Swap (Zswap + Disk Tiering)

21.1 Objectives

Implement the two-tier swap backing store (zswap compressed pool + disk, ADR-07) and the swap-in fault path, satisfying I13 (no cross-mapping slot aliasing outside MAP_SHARED).

21.2 Detailed Implementation Steps

Swap-out (called from Phase 8's eviction path, §20 dependency): compress the dirty anonymous page via LZ4 (target ≥2.5:1, §4) into the zswap pool (a bounded in-RAM hash table keyed by SwapEntry); on pool pressure, demote the oldest zswap entries to disk. Swap-in (a vm-fault dispatch row, §17 dependency, now completed): check zswap first, then disk; on hit, decompress/read, allocate a frame (vm-buddy, §16), map, and clear the swap PTE. Swap-slot allocation is unique per non-shared mapping (I13); a MAP_SHARED swap-backed region is the sole exception, tracked via an explicit shared-slot refcount. Compression is time-bounded: cap at 10 µs per page (§4-derived budget) — a page that fails to compress under budget is routed directly to disk uncompressed rather than blocking the evicting core.

21.3 Deliverable

vm-swap's zswap pool + disk tier + swap-in fault completion in vm-fault.

21.4 Acceptance Criteria

Zswap evict: < 5 µs p50, < 15 µs p99 per 4 KiB page (§4, M8). Zswap swap-in: < 5 µs p50. Disk swap-in: bounded by device (SSD 80/200 µs p50/p99, NVMe 30/80 µs, §4). Property test: no two non-MAP_SHARED present PTEs ever reference the same SwapEntry slot across 10,000 random swap-out/swap-in sequences (I13).

21.5 Conformance Fixtures

buckets/swap/zswap_roundtrip.json — compress/evict/swap-in/decompress corpus. buckets/swap/disk_roundtrip.json — same for the disk tier. buckets/swap/slot_aliasing.json — I13 corpus, including the MAP_SHARED exception path. buckets/swap/mixed_tier.json — pages crossing from zswap to disk under pool pressure.

21.6 Pitfalls

  • A page present in zswap that is also dirtied again in RAM (re-faulted, written, then re-evicted before the stale zswap copy is invalidated) has stale-data semantics if the old zswap entry isn't invalidated first — tracked via an explicit "superseded" flag on the old SwapEntry.
  • The 10 µs compression time-bound (21.2) is a real-time budget, not a best-effort target — a compression implementation that occasionally spikes past it under adversarial input (e.g. incompressible encrypted pages) must fall back to uncompressed disk write, not block.

21.7 Performance Concerns

Zswap's effective capacity (§35 item 6, derived from the compression ratio) is the primary lever against disk-tier latency exposure — the "swap weight" throttle (Phase 8, §20 dependency) exists precisely to keep the disk tier's tail latency (200 µs SSD p99) from dominating the aggregate fault-latency distribution.

21.8 Edge Cases

A swap-in racing a concurrent swap-out of the same page (rare but possible under aggressive replacement-daemon tuning) is serialized via a per-SwapEntry lock with backoff — the lock's existence, not its absence, is the correct design (contrasted with the lock-free hot paths elsewhere in this blueprint, because swap-in/out is not the hot path).

21.9 Failure Analysis

A swap-out that loses the dirty bit before the write completes (an ordering bug symmetric to §8.8's page-cache writeback race) produces silent data loss — detection mirrors §8.8: the dirty bit is sampled atomically at writeback-enqueue time (I8), never re-sampled after the I/O has been issued.

21.10 Operational Notes

A "swap thrashing" alert (sustained high swap-in rate) triggers the same "swap weight" throttle referenced in Phase 8's pitfalls (20.6); the zram-style deferred alternative (§38) is the escalation path for a fleet that hits this ceiling structurally rather than transiently.

22. Phase 10 — Page Cache & Memory-Mapped Files

22.1 Objectives

Implement the file-backed page cache: the (inode, offset)-keyed radix tree, writeback queue, and MAP_SHARED/MAP_PRIVATE memory-mapped-file semantics, completing the file-backed row of §8.4's dispatch table.

22.2 Detailed Implementation Steps

PageCacheEntry (§11) keyed by PageCacheKey { inode, offset }; lookup is O(1) amortized via the radix tree's offset-indexed structure. File-backed fault (Phase 5, §17 dependency, now completed): lookup-or-read-through to the backing BlockDevice, map the cached frame — MAP_SHARED maps the same physical frame into every mapper (shared writes visible across processes); MAP_PRIVATE triggers COW semantics identical to Phase 6 (§18) on first write, backed by the file's clean copy as the COW source instead of an anonymous zero page. Writeback: a dedicated thread drains the dirty queue in LRU order, sampling each entry's dirty bit and generation counter atomically immediately before I/O (§8.8, I8) to avoid the truncate race. truncate/file-shrink invalidates affected cache entries by bumping the generation counter (§8.8's guard).

22.3 Deliverable

vm-pagecache's radix tree + writeback thread; MAP_SHARED/MAP_PRIVATE completion in vm-fault/vm-syscall.

22.4 Acceptance Criteria

Cache lookup: < 200 ns p50, < 500 ns p99 (§4, M9). Property test: a concurrent writeback + truncate sequence (10,000 random interleavings) never writes to a region the truncate has invalidated (§8.8's generation check, exhaustively verified).

22.5 Conformance Fixtures

buckets/pagecache/lookup_readthrough.json — cache-miss-then-hit corpus. buckets/pagecache/shared_vs_private.json — MAP_SHARED cross-process write visibility vs. MAP_PRIVATE COW divergence. buckets/pagecache/ writeback_truncate_race.json — the §8.8 failure-path fixture, made executable.

22.6 Pitfalls

  • Aliasing: two file mappings of the same file at different virtual addresses (or in different processes) share one page-cache entry by design — a truncate must invalidate every affected cache entry, not just the one a particular caller happened to touch.
  • Writeback racing a concurrent write-fault that re-dirties the page requires the dirty-bit sample to be atomic with the writeback-enqueue decision (I8) — a non-atomic sample can lose a write that happened in the gap.

22.7 Performance Concerns

Radix-tree lookup at 200 ns (22.4) assumes a warm, low-depth tree for typical file sizes; a sparse file with pages scattered across a huge offset range increases tree depth and is the pathological case tracked via a vm_pagecache_depth histogram (P14).

22.8 Edge Cases

A MAP_SHARED mapping of a file truncated to a size shorter than the mapping's extent must SIGBUS on access past the new end-of-file, not silently zero-fill (distinguishing this from the anonymous demand-paging zero-fill path in Phase 5, §17) — the two "absent page" cases resolve differently precisely because their semantics differ.

22.9 Failure Analysis

The writeback/truncate race (§8.8) is this phase's canonical failure example; its resolution (generation-counter check under the same lock truncate uses to invalidate) is the template this blueprint uses for every other check-then-act race in the document (fork/COW's atomic refcount, §18; swap's atomic dirty-sample, §21).

22.10 Operational Notes

vm_pagecache_depth and the writeback queue's drain-lag metric are the two dashboards (§27) for a "writes not reaching disk fast enough" report; DAX (persistent-memory direct access, deferred §38) is the escalation path for workloads that want to bypass this layer's writeback latency entirely.

23. Phase 11 — Huge Pages & NUMA

23.1 Objectives

Implement transparent huge page (THP) promotion/demotion (opt-in per ADR-09) and NUMA-aware placement with first-touch + SLIT fallback (ADR-10), resolving the forward references from Phase 4 (§16) and Phase 8 (§20).

23.2 Detailed Implementation Steps

THP promoter scans for 512 contiguous, physically-contiguous, identically- mapped 4 KiB pages eligible for promotion to a 2 MiB huge page (PD-level HUGE bit, §8.5); promotion is triggered only by explicit madvise(MADV_HUGEPAGE) (ADR-09), never eagerly, and requires a TLB shootdown of all 512 constituent entries (Phase 7, §19 dependency) before the huge mapping is installed. Demotion (triggered by MADV_DONTNEED on a huge page, or by a COW fault that only needs one constituent 4 KiB page) is symmetric: shootdown the huge entry, install 512 4 KiB entries. NUMA: vm-buddy's per-node free lists (Phase 4, §16 forward reference now resolved) allocate from the requesting CPU's local node first; on local exhaustion, fall through the SLIT-derived (ACPI, §5 Required Reading) fallback order; a background migration daemon relocates pages accessed disproportionately from a non-local node, gated behind a per-process policy flag (P11 — locality preferred, never mandatory).

23.3 Deliverable

vm-thp-numa's THP promote/demote + per-node buddy extension + migration daemon.

23.4 Acceptance Criteria

THP promotion cost: < 100 µs p50, < 300 µs p99 (§4, M10; dominated by the 512-entry shootdown). Per-node allocation: statistically indistinguishable latency from single-node (§4). Migration: < 50 µs p50 per page. Property test: a MADV_DONTNEED on a huge page always demotes before any constituent page is freed (no free-while-still-huge-mapped state, an extension of I1/I11 to the huge-page case).

23.5 Conformance Fixtures

buckets/thp_numa/promote_demote.json — the promotion/demotion property corpus (§8.7 row 5's contiguity-check malformed case included). buckets/thp_numa/numa_fallback.json — SLIT-order cross-node allocation corpus, run on a multi-node QEMU topology. buckets/thp_numa/ migration_correctness.json — asserts every PTE referencing a migrated page is updated (no aliasing).

23.6 Pitfalls

  • Promotion of a 2 MiB region requires every constituent 4 KiB page to be physically contiguous and unmapped from any other process — skipping the cross-process check promotes a page another process still expects at 4 KiB granularity underneath it.
  • MADV_DONTNEED on a huge page must demote before freeing — freeing at huge granularity while another core's stale TLB still holds the huge translation is a 512-page-wide version of the ordinary stale-TLB bug (I3), with 512× the blast radius.
  • Migrate-on-fault (an alternative to the background daemon) adds fault-path latency for every migrated page; gating behind a per-process policy (P11) avoids imposing that cost on processes that don't opt in.

23.7 Performance Concerns

THP's coverage benefit is exactly the §35 item 3 calculation (huge-page TLB coverage vs. 4 KiB coverage) — the 100 µs promotion cost (23.4) is amortized against a working set large enough that the coverage improvement pays for itself within a few thousand accesses; promoting a rarely-reused region is a net loss, which is why ADR-09 keeps promotion opt-in rather than eager.

23.8 Edge Cases

A THP promotion request racing a concurrent mprotect on one of the 512 constituent pages must abort the promotion (the region is no longer uniformly-protected, violating the huge-page's single-PTE-covers-512-pages protection model) rather than promoting a stale protection snapshot.

23.9 Failure Analysis

A promotion that does not invalidate all 512 constituent 4 KiB TLB entries (23.6) produces stale reads at up to 512× the single-page blast radius of an ordinary TLB bug (§19) — this is why THP promotion is exclusively implemented on top of Phase 7's batched-shootdown primitive, never as an independent invalidation path.

23.10 Operational Notes

vm_thp_promotion_rate and vm_numa_migration_rate (§27 dashboards) are the tuning signals for whether opt-in THP and background migration are earning their cost on a given fleet's workload; CXL/tiered-memory-aware placement (deferred, §38) is the escalation path once NUMA's binary local/remote model stops matching the hardware.

24. Phase 12 — Security Primitives & Speculative-Execution Defenses

24.1 Objectives

Implement W^X enforcement (I6, P6), KASLR (I14), and KPTI, plus the Meltdown/Spectre-class mitigations that depend on this subsystem's page-table boundary (§25 Threat Model T6/T7), and close out the differential-testing + fuzz-canary program (ADR-12, ADR-13).

24.2 Detailed Implementation Steps

W^X: the mapper (Phase 2, §14) refuses any map/mprotect request that would set both WRITABLE and EXECUTABLE (I6); enforcement scans for dual mappings of the same physical frame at different virtual addresses with conflicting permissions (§8.7's W^X-bypass malformed case), not just single-mapping requests. KASLR: at boot, the kernel's load address is offset by a random multiple of 2 MiB, drawn from a boot-time entropy source verified to meet a minimum-entropy floor (I14) before the offset is committed; every static kernel pointer is relocated via position-independent linking. KPTI (Lipp et al. 2018, §5 Required Reading, applied here): two top-level page tables per process — one kernel-visible, one user-only (omitting all kernel mappings except the syscall-entry trampoline page) — swapped on syscall/interrupt entry and exit. Spectre v1 mitigation: array_index_nospec-equivalent barriers on every kernel code path that indexes an array with a user-influenced, bounds-checked index (Kocher et al. 2019, applied here). Differential test: replay the curated syscall corpus against both this subsystem and Linux mm/, asserting matching observable results (page-fault counts, error codes, final page-table contents). Fuzz canary: continuous 24 h rolling run, escalating to a 30-day soak before any release tag.

24.3 Deliverable

vm-security's W^X/KASLR/KPTI + Spectre-barrier helpers; the differential-linux bucket; the fuzz canary CI job.

24.4 Acceptance Criteria

KPTI overhead: ~10 ns/syscall p50, bounded to < 30% p99 syscall-latency regression versus no-KPTI (§4 baseline recorded in Performance Engineering, §31). Zero W^X violations across the entire conformance suite (I6, exhaustively checked, including the dual-mapping bypass case). Differential corpus: 100% observable-result match against Linux mm/, corpus runtime < 10 minutes in CI. Fuzz canary: 0 panics over 24 h rolling (M12, §31).

24.5 Conformance Fixtures

buckets/security/wx_enforcement.json — direct + dual-mapping-bypass cases. buckets/security/kaslr_entropy.json — I14's entropy-floor assertion. buckets/security/kpti_isolation.json — asserts no kernel mapping beyond the trampoline is visible in the user-mode table. buckets/differential-linux/corpus.json — the curated syscall trace set.

24.6 Pitfalls

  • W^X bypass via dual mapping: mapping a frame writable at one virtual address and executable at another defeats a check that only inspects the current request in isolation — the check must scan for existing conflicting mappings of the same frame at map time, not just validate the new request's own flags.
  • KPTI's user-mode table must expose the syscall trampoline page and nothing else kernel-side — leaking any additional kernel address via that table reintroduces exactly the Meltdown-adjacent info-leak KPTI exists to close, and independently breaks KASLR if the leaked address is used to infer the kernel's randomized base.
  • A Spectre-barrier omitted from one kernel code path that indexes user-influenced data is invisible to every functional test (the bug is a timing side-channel, not a correctness bug) — the only detection is a systematic audit of every bounds-checked, user-influenced array index (24.2), not a fixture.

24.7 Performance Concerns

KPTI's ~10 ns/syscall cost (24.4) is the direct tradeoff named in ADR-11; it is paid on every syscall unconditionally because the alternative (opt-out) reopens Meltdown-class kernel-memory disclosure, which the project's threat model (§25, T6) treats as unacceptable at any syscall-rate cost this subsystem is designed for.

24.8 Edge Cases

A JIT compiler's write-then-switch-to-exec dance (P6's documented W^X accommodation) must never have both the writable and executable mappings simultaneously valid, even momentarily — the switch is mprotect enforced through a single VMA transition (Phase 3, §15), never two independently-toggled mappings that could overlap in time under preemption.

24.9 Failure Analysis

A W^X bypass (24.6) or a KASLR entropy-floor failure (I14) is treated as a security incident, not a correctness bug — both escalate through the Threat Model's (§25) detection/telemetry/recovery columns rather than the ordinary Failure Modes process, because the blast radius is confidentiality or code-injection, not availability.

24.10 Operational Notes

vm_wx_violation and vm_kaslr_entropy_low (I6/I14 telemetry) are P0 security alerts routed independently of the standard on-call rotation (§27); the differential-against-Linux and 30-day fuzz canary results are the release-gating evidence recorded in Build & Release Engineering (§30).

27. Operational Readiness

Metrics. Every vm_* counter named in §7 (I# telemetry) and §25/§26 (T#/FM# telemetry) is exported via the ADR-18 shared-page mechanism; aggregated per-CPU on read. Tracing. ADR-17 static tracepoints, toggled at runtime, covering fault dispatch (§17), shootdown epochs (§19), and eviction decisions (§20). Structured logging. ADR-16's lock-free per-CPU ring buffer, drained by a userspace-visible log daemon; log lines carry the invariant/threat ID (I#/T#/FM#) they relate to when applicable, so a log grep doubles as a cross-reference into this document.

Dashboards. Three tiers: (1) fault-path latency (M1–M3, §31) — the primary SLO surface; (2) memory-pressure (fragmentation histogram, zswap-pool occupancy, eviction rate) — the capacity-planning surface; (3) security (vm_wx_violation, vm_kaslr_entropy_low) — the P0-alert surface, routed independently (§24.10).

Alerting philosophy. Invariant-violation counters (I1–I14 telemetry) are P0 regardless of rate — a single non-zero reading is a structural bug, not a threshold-crossing event. Performance counters (M1–M12, §31) alert on sustained percentile regression against the M-table's targets, not on single-sample spikes.

SLOs. Anonymous fault p99 ≤ 15 µs; TLB shootdown p99 ≤ 3 µs; zero invariant violations per rolling 30-day window; fuzz canary zero panics per rolling 24h window (§4, §31).

Incident response. Security-class incidents (T6, T7, T12) page an on-call security responder directly, bypassing the general kernel on-call rotation; correctness-class incidents (FM-1, FM-4, FM-5) page the owning phase's engineer per the BLUEPRINT_LOG.md ownership map; capacity-class incidents (FM-2, FM-7, FM-9) page general on-call with the relevant runbook (§36) attached automatically.

Named runbooks (full text in docs/runbooks/, summarized in §36): stuck-mmap, persistent-OOM-despite-headroom, TLB-shootdown-storm.

Backup/restore. Swap-slot metadata and page-cache dirty-state are the only persistent state this subsystem owns across a reboot; both are versioned independently (ADR-23) and restorable from the last consistent writeback checkpoint.

Deployment topology. Vendored source into the host kernel build (ADR-21); no independent deployment unit of its own — its rollout topology is whatever the host kernel's is.

Canary/rolling-upgrade/rollback/migration. A kernel image upgrade carrying a new on-disk swap-slot or page-cache metadata version runs the Compatibility & Versioning (§28) migration path before any swap slot from the prior version is trusted; rollback requires the prior version's metadata reader to still be present (N-1 compatibility, §28).

28. Compatibility & Versioning

Wire/on-disk format. Swap-slot metadata and page-cache dirty-state records carry an independent format version (ADR-23), separate from crate SemVer, because they outlive any single kernel-image release across a reboot. Schema evolution. A new format version must read the prior version's records (N-1 compatibility) for at least one release cycle before the reader for the old format may be removed. API stability. Crate public APIs (§11) follow SemVer; a breaking change to a load-bearing type (e.g. VmAreaStruct's field set) is a major version bump and requires an ADR amendment. Migration. An on-disk format bump ships a one-shot migration pass invoked at first boot after upgrade, converting existing swap slots/page-cache metadata to the new format before any fault path touches them. Deprecation policy. A deprecated API is marked at least one minor version before removal, with the replacement named in the deprecation notice. SemVer policy. Patch: bugfixes, no API change. Minor: additive API surface (new optional fields, new functions). Major: any change to a type listed in §11 that isn't purely additive. Rolling upgrade. Because address-space state (VMAs, page tables) is entirely in-memory and process-lifetime-scoped, a rolling upgrade of the host kernel requires either a full reboot (dropping and rebuilding address-space state) or a live-migration path (out of scope; see EPT/NPT deferral, §38, for the hypervisor-assisted alternative).

32. Scalability Analysis

Stays constant. Per-fault latency (M3) is O(1) in resident-set size — the walker's depth is fixed at 4 levels regardless of how much memory is mapped (§8.2). Per-CPU magazine hit-rate is independent of core count by design (P4). Grows. Page-table memory overhead is O(resident pages) (§35 item 1); VMA-tree operations are O(log n) in VMA count (§15, §4's 65,530 ceiling); TLB-shootdown IPI fan-out is O(CPU count) per epoch (bounded by batching to O(1) epochs, not O(1) IPIs — the batching reduces the constant, not the asymptotic class, §35 item 4).

Named bottlenecks in order. (1) TLB-shootdown IPI fan-out at very high core counts (>512, §4's stated ceiling) — the batching strategy's constant factor eventually still dominates at extreme scale; (2) the buddy allocator's global-list mutex on the cold path — mitigated but not eliminated by magazines; (3) the page-cache radix tree's depth on sparse files (§22.7); (4) NUMA cross-node traffic under adversarial access patterns (§16.7).

Horizontal/vertical scaling. This subsystem scales vertically (more cores, more NUMA nodes on one machine) by design; it has no horizontal (multi-machine) scaling story of its own — that is the hypervisor/ distributed-systems layer's problem, explicitly out of scope (§1 non-goals).

Sharding/partitioning. Per-NUMA-node buddy instances (§16, §23) are the system's only partitioning; per-CPU magazines and pending sets are the finer-grained partitioning beneath that.

Coordination overhead. TLB shootdown is the sole cross-core coordination point in the steady-state hot path (P5); everything else (VMA tree, buddy allocator) is either per-process (VMA tree, no cross-core coordination needed) or per-CPU-then-occasionally-global (buddy).

Practical ceiling and levers beyond it. The 512-CPU shootdown fan-out ceiling (§4) is the practical scaling limit for this design as specified; beyond it, the lever is INVPCID-class hardware support becoming universal (removing the full-flush fallback's cost) or a hierarchical shootdown protocol (regional IPI aggregators) — noted here as a lever, not built, because no target in scope (§4's 512-CPU ceiling) requires it yet.

33. Mental Models & First Principles

  • MM1 — A page table is a memoized pure function. Translation is a deterministic (root, vaddr) -> phys computation (P1); the TLB is just a cache of that function's results. Predicts: any TLB bug is a cache-coherence bug (a stale cached result), never a translation-logic bug (the function computed the wrong answer) — the two are diagnosed completely differently. Bug class without it: chasing a "translation bug" in the walker when the actual defect is a missing shootdown. Applied in §8.1, §19.
  • MM2 — The VMA is the unit of intent; the PTE is the unit of mechanism. A mmap call expresses intent at VMA granularity; the page tables realize it at PTE granularity, lazily (demand paging). Predicts: intent-level races (two overlapping mmaps) are VMA-tree bugs (§15); mechanism-level races (a stale TLB) are PTE-level bugs (§19) — conflating the two layers when debugging wastes time in the wrong crate. Applied in §15, §8.4.
  • MM3 — Reference counting is the only truth for shared physical memory. No other bookkeeping (a comment, a convention) can substitute (P10). Predicts: every double-free/use-after-free bug in this subsystem traces to a refcount operation that was skipped, non-atomic, or double-counted — never to a "forgot to check" bug at a higher level. Applied in §18, I5, I7.
  • MM4 — TLB shootdown is a distributed-consensus problem with N=core- count replicas. The writer is a coordinator; peers are replicas; the IPI+ACK protocol is the consensus round (§8.3). Predicts: every stale-TLB bug is a broken happens-before edge, structurally identical to a distributed system losing a linearizability guarantee — the same debugging vocabulary (missing acknowledgment, split-brain-adjacent partial-ACK state) applies. Applied in §19, I3.
  • MM5 — Eviction policy is a bet on future access; the page-table walker is a statement about past access. The ACCESSED bit is backward-looking (Denning's working-set model, §5); the replacement policy's promotion/ demotion is a forward-looking bet built on that backward-looking signal. Predicts: thrashing occurs exactly when the bet is structurally wrong — a moving working-set boundary the sampling cadence (100 ms, §20.2) can't track. Applied in §20.
  • MM6 — Speculative execution respects architectural permission bits but not observable microarchitectural state. The CPU's architectural contract (a privilege check) is honored; the microarchitectural side-effects of the speculated-but-squashed path (cache-line residency) are not rolled back. Predicts every entry in the Meltdown/Spectre/MDS family (§25 T6/T7) — any security boundary relying solely on architectural checks without a microarchitectural-state argument is incomplete. Applied in §24, Threat Model (§25).
  • MM7 — Fragmentation is deferred cost, not eliminated cost. Buddy coalescing defers a hard fragmentation problem to the next high-order request rather than solving it at free time (§16). Predicts the "OOM despite free memory" failure mode (FM-2, §26) is not a bug but an inherent property of any power-of-two allocator under adversarial allocation-order patterns. Applied in §16, §26.
  • MM8 — An address space is a lazily-materialized promise. A VMA is a promise ("this range behaves as X"); PTEs materialize the promise one page at a time, on fault (demand paging, §17). Predicts: mmap "success" is a promise accepted, not memory reserved — a subsequent fault can still fail (OOM) even though the mmap call itself returned success. Applied in §17, §21.

35. Back-of-Envelope Capacity Model

  1. Page-table memory overhead per resident page. overhead ≈ 8 + 8/512 + 8/512² + 8/512³ bytes ≈ 8.06 B/page (one leaf PTE amortized with its fractional share of three upper levels, entries-per-table = 512 per §8.2). For a 4 GiB resident set (1,048,576 × 4 KiB pages): 1,048,576 × 8.06 B ≈ 8.45 MiB — about 0.2% overhead, chained from §4's 4 KiB base page size.
  2. TLB coverage, 4 KiB pages. coverage = entries × page_size. L1 DTLB: 64 × 4 KiB = 256 KiB. STLB: 1536 × 4 KiB = 6 MiB — both directly from §4's TLB-entry row.
  3. TLB coverage, 2 MiB huge pages. Assuming ~32 huge-page-capable TLB entries: 32 × 2 MiB = 64 MiB covered — a >10× improvement in address range covered per entry over item 2, the number that justifies THP (§23) for large working sets.
  4. IPIs avoided by batching a 1 GiB munmap. Naive: (region / page_size) × (N_cpus − 1) = (1 GiB / 4 KiB) × 511 = 262,144 × 511 ≈ 134,000,000 IPIs at the §4 512-CPU ceiling. Batched: 1 × 511 = 511 IPIs. Reduction factor: region / page_size = 262,144× — the headline number for P5/ADR-08, measured directly in §19.7.
  5. Buddy allocator max practical order. total_pages = physical_memory / page_size = 16 TiB / 4 KiB = 2^32 pages (§4's 16 TiB ceiling); the design caps representable single-block order at 11 (2^11 × 4 KiB = 8 MiB blocks) per ADR-04 — larger contiguous regions are represented as multiple order-11 blocks, a design choice traded off in §16.10, not a derived number.
  6. Zswap effective capacity. effective_capacity = pool_size × compression_ratio. With a 2 GiB RAM pool and the §4 target ratio of 2.5:1: 2 GiB × 2.5 = 5 GiB of anonymous pages held compressed before any disk-tier fallback — the number ADR-07 is justified by.
  7. Fault-handling throughput ceiling per core. rate = 1 / p50_latency = 1 / 3 µs ≈ 333,333 faults/sec/core (§4's anonymous-fault p50). Aggregate at the 512-CPU ceiling: rate × N_cpus ≈ 1.7 × 10^8 faults/sec system-wide theoretical ceiling, ignoring lock contention (a bound, not an achieved number).
  8. Page-fault queue memory at saturation. queue_mem = depth × N_cpus × record_size = 256 × 512 × 128 B ≈ 16.8 MiB total pending-fault bookkeeping (§4's 256-deep-per-core fault queue).
  9. VMA metadata memory ceiling per process. vma_mem = max_vmas × sizeof(VmAreaStruct) = 65,530 × 96 B ≈ 6.29 MiB worst case (§4's 65,530-VMA ceiling; 96 B is VmAreaStruct's §11 field-set estimate).
  10. Swap-tier latency ratio. disk_p99 / anon_p99 = 200 µs / 15 µs ≈ 13.3× (§4's SSD swap-in p99 vs. anonymous-fault p99) — the ratio that motivates zswap (item 6) absorbing the bulk of swap traffic to keep the system's overall fault-latency distribution close to the anonymous p99 rather than the disk-bound tail.

37. Alternative Architectures (Roads Not Taken)

Alt 1 — Inverted (hashed) page table.

VirtAddr ──► hash(pid, vpn) ──► Hash Table ──► {pfn, pid, vpn, chain-ptr}
                                   (one entry per PHYSICAL frame,
                                    not per virtual page)

Regime where it wins: extremely sparse 64-bit address spaces where a forward-mapped table's upper levels (allocated even for mostly-empty regions) waste memory disproportionate to the resident set. Real system: PowerPC and UltraSPARC's hashed page tables (TSB — Translation Storage Buffer). Rejected because: this design targets x86-64/aarch64, whose hardware walkers are natively forward-mapped 4-level — an inverted table would require software-walked TLB misses on hardware built for the opposite, forfeiting the hardware walker entirely (ADR-05).

Alt 2 — Software-managed TLB (no hardware walker).

TLB miss ──► trap to software handler ──► handler consults its own
             (arbitrary format) table ──► loads TLB entry ──► resume

Regime where it wins: research systems and exokernels wanting a completely custom translation-table format unconstrained by any hardware walker's assumptions. Real system: MIPS R4000, DEC Alpha. Rejected because: x86-64 and aarch64 both provide hardware page-table walkers; software-managed TLB adds a trap-latency cost on every miss with no compensating flexibility benefit on hardware that already walks tables for free (ADR-30's multi-arch rationale implicitly assumes hardware walking).

Alt 3 — Single-address-space, capability-based protection (no per-process page tables).

┌─────────────────────────────────────────────┐
│         One global address space              │
│  Process A's caps ──► [region 1] [region 3]   │
│  Process B's caps ──► [region 2] [region 3]   │  (region 3 shared
│                                                │   via capability,
│  Protection = capability possession,          │   not via a second
│  not a second page table                      │   page table)
└─────────────────────────────────────────────┘

Regime where it wins: microkernel/capability systems where the security model itself is being co-designed with paging, and where cross-process sharing without any TLB-visible boundary crossing is valuable. Real system: seL4, historically Mach's early single-address-space experiments. Rejected because: this project's scope is a traditional per-process-address-space POSIX-compatible model (§1); adopting capabilities is a bigger redesign than paging alone and forfeits direct comparability to Linux/FreeBSD for the differential-testing program (ADR-12).

Alt 4 — Segmentation-based memory management (no paging).

VirtAddr = (segment_selector, offset)
Segment Table: [base, limit, permissions] per segment
   translation = base + offset, bounds-checked against limit
   (no fixed-size page granularity at all)

Regime where it wins: workloads whose objects are naturally variable-sized and contiguous, avoiding a fixed-page-size internal-fragmentation cost. Real system: Multics' segment+page hybrid; x86 real-mode/early-protected- mode pure segmentation. Rejected because: variable-sized segments reintroduce external fragmentation — exactly the problem paging's fixed-size units exist to solve (§16, MM7); segmentation-only management was abandoned industry-wide for this reason by the 1990s.

39. Glossary

  • ASID — Address Space ID (aarch64); tags TLB entries by address space, analogous to x86's PCID.
  • buddy allocator — physical-page allocator using power-of-two block-pair (buddy) coalescing.
  • CLOCK / second-chance — page-replacement approximation of LRU via a circular access-bit sweep.
  • CLOCK-Pro — CLOCK extension tracking eviction history to distinguish resident vs. non-resident pages (Jiang & Zhang 2005).
  • COW (copy-on-write) — sharing pages with deferred copying until first write.
  • CR3 — x86 register holding the physical address of the top-level page table.
  • CXL — Compute Express Link; tiered/pooled memory interconnect.
  • DAX (Direct Access) — bypassing the page cache for persistent-memory- backed file mappings.
  • demand paging — populating page-table entries only on access, not at mmap time.
  • dirty bit — PTE bit indicating the page was written since last clear.
  • EPT (Extended Page Table) — Intel's hardware-assisted nested page table for virtualization.
  • fallback list — NUMA cross-node allocation preference order, derived from the SLIT.
  • first-touch — NUMA allocation policy: place a page on the node of the CPU that first accesses it.
  • generation counter — a per-page-cache-entry counter bumped on truncate/invalidate, used to detect writeback races (§8.8).
  • GLOBAL bit — PTE bit exempting a mapping from TLB flush on PCID/ASID context switch.
  • huge page — a 2 MiB or 1 GiB mapping installed at a higher page-table level than the base 4 KiB leaf.
  • inactive list — page-replacement queue holding eviction candidates.
  • INVPCID — x86 instruction for PCID-tagged TLB invalidation without a full flush.
  • invlpg / TLBI — x86 / aarch64 instructions to invalidate a single TLB entry.
  • IPI (inter-processor interrupt) — an interrupt one CPU sends another, the delivery mechanism for TLB shootdown.
  • KASLR — kernel address space layout randomization.
  • KPTI — kernel page-table isolation (Meltdown mitigation).
  • KSM — kernel same-page merging; content-based page deduplication.
  • lazy TLB — skipping shootdown IPIs to a CPU not currently running under the affected address space.
  • LRU (least recently used) — the replacement-policy family this design's active/inactive queues approximate.
  • magazine — per-CPU array of pre-freed physical frames for the buddy allocator's hot path (Bonwick & Adams 2001).
  • MDS (Microarchitectural Data Sampling) — speculative-execution side-channel family leaking store/fill-buffer contents.
  • Meltdown — CVE-2017-5754; speculative load crossing the user/kernel boundary, leaked via cache timing.
  • MGLRU (Multi-Gen LRU) — Linux 6.1+ replacement policy generalizing active/inactive to multiple generations.
  • NUMA — non-uniform memory access; multi-node memory with node-dependent access latency.
  • NX / XD / PXN / UXN — no-execute PTE bit variants (x86 / aarch64).
  • OOM killer — mechanism for terminating processes when memory is exhausted beyond recoverable pressure.
  • page cache — in-memory cache of file contents, indexed by (inode, offset).
  • PCID (Process Context ID) — x86 TLB tag identifying an address space.
  • PFN (Page Frame Number) — a physical page's index (PhysAddr >> PAGE_SHIFT).
  • PML4 — x86-64's top (level-4) page-table structure.
  • PTE (Page Table Entry) — a single translation-plus-permission record in a page table.
  • PendingSet — this design's per-CPU accumulator of not-yet-flushed TLB invalidations (§11, §19).
  • replacement policy — the algorithm selecting which resident page to evict under memory pressure.
  • RSS (Resident Set Size) — the subset of a process's virtual memory currently backed by physical frames.
  • second-chance — see CLOCK.
  • shootdown — the IPI-mediated protocol invalidating a translation across every CPU that may have cached it.
  • SLIT (System Locality Information Table) — ACPI table describing inter-NUMA-node access-latency distances.
  • Spectre — CVE-2017-5753/5715 family; speculative execution past a mispredicted branch or indirect call, leaked via cache timing.
  • SSBD (Speculative Store Bypass Disable) — mitigation for Spectre v4 (CVE-2018-3639).
  • swap-in / swap-out — fault-driven retrieval from, and eviction-driven write to, the swap backing store.
  • THP (Transparent Huge Pages) — opt-in automatic promotion of contiguous small pages to a huge-page mapping.
  • TLB (Translation Lookaside Buffer) — per-CPU hardware cache of recently used translations.
  • TSX Async Abort — CVE-2019-11135; MDS-adjacent leak via the TSX transactional-abort path.
  • VMA (Virtual Memory Area) — a contiguous virtual-address range with uniform protection/backing (VmAreaStruct, §11).
  • W^X (write XOR execute) — the invariant that no mapping is simultaneously writable and executable.
  • working set — the set of pages a process has referenced within a recent time window (Denning 1968).
  • writeback — flushing a dirty page-cache or anonymous-swap page to its backing store.
  • zswap — a compressed in-RAM pool absorbing swap-out traffic before any disk I/O.
