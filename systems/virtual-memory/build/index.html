⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the Cargo workspace, CI matrix, and QEMU harness; land the correctness kernel (vm-verifier) before any feature code, per P8. No feature crate is implemented; this phase's job is to make every later phase falsifiable from day one.

Deliverable

Workspace builds on stable Rust; CI green on both boot lanes; a "hello kernel" stub boots under QEMU and prints via the ADR-16 log ring to the serial console.

Acceptance

cargo build --workspace --all-targets exits 0 on both target JSONs; QEMU boot-to-serial-output latency < 50 ms (§4 startup budget); all 14 verifier stubs present and individually invokable (even if Unimplemented).

Fixtures

fixtures/boot/x86_64_smoke.trace — expects serial line "kernel: alive" within 50 ms. fixtures/boot/aarch64_smoke.trace — same, aarch64. fixtures/ verifier/stub_completeness.json — asserts all 14 I# stub names present.

Pitfalls
  • The no_std target JSON is easy to under-specify (missing panic-strategy: abort); pin every field explicitly.
  • QEMU's -machine flag matters: q35 (modern chipset) vs. microvm (Firecracker-style) boot differently; document which the CI lane targets.
  • A CI matrix that silently skips aarch64 on a runner without QEMU aarch64 support looks green while testing nothing; assert the lane actually ran.

⬜ Phase 1 — Core Types & Address Translation Primitives §13

Objectives

Define PhysAddr, VirtAddr, PageFrameNumber, PageSize, PteFlags in vm-core (§11); enforce construction-time invariants so no later phase can build an invalid address (P1's purity depends on inputs already being valid).

Deliverable

vm-core compiles standalone (no arch crate dependency); construction functions reject every malformed input in §8.7's first two rows.

Acceptance

Property test: 100,000 random u64 values through PhysAddr::new / VirtAddr::new — zero panics, and every accepted value round-trips through Display (hex, 0x-prefixed) losslessly; a compile_fail test asserts an unaligned PhysAddr literal is rejected at construction, not at use.

Fixtures

fixtures/addr/canonical_boundary.json — the exact bit-47 boundary values (pass/fail pairs). fixtures/addr/maxphysaddr_boundary.json — 52-bit boundary. fixtures/addr/malformed_batch.json — the §8.7 malformed-input table as executable cases.

Pitfalls
  • PhysAddr(u64) is a 64-bit container but only 52 bits are ever valid (I1); a checker that forgets the ceiling accepts garbage silently.
  • PteFlags bit layout differs between x86-64 and aarch64 (§8.5); a shared bit-position constant reused across arches is a latent bug — per-arch tables are separate and re-exported, never unified.

⬜ Phase 2 — Page-Table Walker & Multi-Level Mapper §14

Objectives

Implement the pure walk function and the map/unmap mutators per architecture (§8.1, §8.2), satisfying P1 (purity) and I1/I11 (frame-range and ownership invariants).

Deliverable

walk/map/unmap for both arches; vm-harness's software walker; a pretty_print(root) debug dump (ASCII tree of addresses + flags).

Acceptance

Property test: insert N=10,000 random mappings, walk every one and assert translation matches; remove half, walk and assert NotPresent. Walk latency on a warm-TLB miss < 50 ns p50 (§4, M1). Map of a single page < 500 ns p50 (dominated by intermediate-level buddy allocation, amortized).

Fixtures

buckets/pagetable/insert_walk_remove.json — the property-test corpus. buckets/pagetable/four_level_boundary.json — index-extraction boundary values per §8.2 row. buckets/pagetable/malformed_walk.json — non-canonical and out-of-range inputs from §8.7, expecting WalkFault, never a panic.

Pitfalls
  • A walker that checks only the last level for PRESENT misses early exits at intermediate levels — must consult every level (P1, 14.2).
  • Forgetting the GLOBAL bit on kernel mappings causes them to flush on every ASID/PCID context switch (§8.5); set explicitly at map time for every kernel-space mapping.
  • The mapper allocating intermediate levels without registering I11's ownership tag lets a later unmap from a different root free a still-shared table.

⬜ Phase 3 — VMA Manager §15

Objectives

Implement the per-process address-space model: the rbtree of VmAreaStructs and its four primitives (§8, P2), enforcing I4 (no overlap).

Deliverable

vm-vma crate exposing the rbtree + four primitives; a vma_dump(mm) debug printer ([start..end) prot kind).

Acceptance

1,000-VMA process: insert < 1 µs p50, find < 200 ns p50 (§4). Property test: random insert/split/merge sequences never produce an overlapping pair (I4 exhaustively checked after every operation).

Fixtures

buckets/vma/insert_find_merge_split.json — the property-test corpus. buckets/vma/overlap_rejection.json — §8.7 row 3 malformed-insert cases. buckets/vma/boundary_semantics.json — two VMAs meeting exactly at one address, asserting half-open ownership.

Pitfalls
  • Two VMAs meeting at an address must agree which owns the boundary — the half-open convention (right VMA owns its start, left VMA does not own its end) must be enforced identically in find_vma and insert_vma or a one-byte gap/overlap silently appears.
  • A VMA inserted at the same address as an existing one must error (I4), never silently replace — the caller is responsible for an explicit merge/replace decision.

⬜ Phase 4 — Buddy Allocator & Physical Memory §16

Objectives

Implement the physical page allocator: per-order free lists, buddy coalescing (I10), and per-CPU magazines (P4, ADR-04), decoupled entirely from replacement policy (P3).

Deliverable

vm-buddy::alloc/free; magazine refill/drain; buddy_dump() debug printer (per-order freelist length + per-CPU magazine state).

Acceptance

Hot path (magazine hit) < 100 ns p50, < 300 ns p99 (§4, M4). Cold path (global list) < 500 ns p50. Cold path with split < 1 µs p50. Property test: 10,000 random alloc/free sequences never leave two free buddies at the same order un-coalesced (I10) and never double-allocate a PFN (I7).

Fixtures

buckets/buddy/alloc_free_property.json — the alloc/free property corpus. buckets/buddy/coalesce_boundary.json — buddy-pair coalescing edge cases. buckets/buddy/double_free_detection.json — §8.7 row 6's misaligned-order double-free, expecting vm_double_free_detected.

Pitfalls
  • The buddy of PFN p at order k is p XOR (1 << k); if p isn't aligned to 2^k the XOR produces a nonsense address outside the region (16.5 fixture; ties to §8.7 row 6).
  • Coalescing requires the buddy to be free and the same order — the per-page order metadata is the load-bearing structure that makes this checkable at all (P8).
  • A magazine drain that fails to coalesce before pushing to the global list produces avoidable external fragmentation, visible only in the fragmentation-histogram metric (P14), not in correctness tests.

⬜ Phase 5 — Page-Fault Handler & Demand Paging §17

Objectives

Implement handle_fault (§11) as the single dispatch point from a hardware trap, covering anonymous demand-paging and dispatch stubs for the paths later phases complete (file-backed, swap-in, COW), satisfying I12 (bounded retry, no infinite fault loop).

Deliverable

vm-fault::handle_fault covering the Anonymous row of §8.4's dispatch table; per-fault tracing (ADR-17 tracepoints) at vm_fault=trace level.

Acceptance

Fault on a present page: 0 µs (handled by hardware, never reaches this code — asserted via a counter that should read zero in the property test). Fault requiring anonymous allocation: < 5 µs p50, < 15 µs p99 (§4, M3). Bucket fault/anonymous_dispatch.json green; zero instances of the retry counter reaching 8 in 100,000 fixture replays.

Fixtures

buckets/fault/anonymous_dispatch.json — the demand-paging happy path. buckets/fault/no_vma_fatal.json — §8.4 row 1. buckets/fault/ protection_violation.json — §8.4 row 6. buckets/fault/retry_exhaustion.json — a synthetic permanently-failing mapping, asserting escalation at exactly retry 8 (I12).

Pitfalls
  • A user-space fault on a kernel address must be classified fatal before any VMA lookup — checking VMAs first on a kernel address risks interpreting kernel VMAs (if any are visible in that lookup path) under user-fault semantics.
  • A stub path that returns Ok(()) without actually mapping violates I12 immediately (an unbounded silent retry loop) — every stub in 17.2 returns Err, never a fake success.

⬜ Phase 6 — Fork, Copy-on-Write & Exec §18

Objectives

Implement fork()'s VMA-tree clone + COW marking and the write-fault COW resolution path (§8.6's worked example), satisfying I5 (refcount-tracks- mapping-count) and P10 (refcounting as sole lifetime authority).

Deliverable

COW integrated into vm-fault; fork's VMA-clone + PTE-downgrade path in vm-vma/vm-arch-*.

Acceptance

Fork of a 1 GiB process: < 10 ms p50 (page-table clone dominates, §4). First write fault per page after fork: < 5 µs p50. Property test: after N random fork+write sequences, every frame's refcount exactly equals its read-only-PTE count (I5, exhaustively checked).

Fixtures

buckets/cow/fork_downgrade.json — the PTE-downgrade + refcount-increment path. buckets/cow/write_fault_slow_path.json — refcount>1 copy path. buckets/cow/write_fault_fast_path.json — refcount==1 in-place path (§8.6 step 6). buckets/cow/pinned_page_no_cow.json — a pinned VMA fork, asserting deep-copy not COW-marking.

Pitfalls
  • Pinning (DMA) must not COW; a pinned page marked read-only by an oblivious fork breaks an in-flight transfer the instant the DMA engine writes to what it believes is still its buffer.
  • A page with refcount 1 at write-fault time should take the fast path (re-mark writable in place, no copy) — always taking the slow path is correct but wastes an allocation+copy on every single-owner page touched after a fork whose sibling already faulted and released its share.
  • A refcount decrement that races two children's near-simultaneous COW faults on the same original frame must be atomic (I5) — a read-modify-write without atomicity briefly under-counts, permitting a premature free while a translation still points at the frame.

⬜ Phase 7 — TLB Management & Shootdown §19

Objectives

Implement the per-CPU pending-invalidation set and batched shootdown protocol (§8.3, P5, ADR-08), satisfying I3 — the invariant every prior phase (14, 15, 18) has been depending on as a forward reference.

Deliverable

vm-tlb::PendingSet, flush_epoch, is_lazy; the shootdown IPI handler.

Acceptance

IPI latency per peer: < 1 µs p50, < 3 µs p99 (§4, M6). Batched shootdown for N invalidations in one epoch: < 1 µs fixed cost + ~0 marginal per entry after the first (bitmap already prepared) — verified against the naive 262,144-IPI baseline computed in §35 item 4. Property test: no consumer observes a page-table write as "visible" before every targeted peer's ACK (I3, exhaustively checked via a simulated multi-core interleaving).

Fixtures

buckets/tlb/ordering_invariant.json — the write-then-shootdown-then-visible ordering property corpus. buckets/tlb/lazy_skip.json — asserts an idle CPU under a different asid receives no IPI. buckets/tlb/batch_vs_naive.json — measures IPI count for a bulk munmap, asserting the batched count.

Pitfalls
  • An IPI that logically arrives (network/interrupt delivery) before the underlying page-table write is architecturally visible to the peer (a missing release/acquire fence pairing) lets the peer's invlpg run against the old PTE, then re-cache it — the shootdown "succeeds" but leaves the stale entry behind.
  • Lazy-TLB tracking that forgets to re-check is_lazy on a context switch (a CPU that was idle becomes active under the affected asid mid-epoch) can skip a peer that now actually needs the invalidation.

⬜ Phase 8 — Page Replacement (Active/Inactive + Clock) §20

Objectives

Implement the two-queue active/inactive LRU with second-chance clock sweep (§5 Required Reading: Denning 1968, Belady 1966; ADR-06), satisfying I8 (no eviction without writeback) and I9 (no pinned page queued), decoupled from allocation (P3).

Deliverable

vm-replacement's two queues + sweep daemon; promote/scan_inactive (§11).

Acceptance

Eviction scan throughput: 1,000 pages/ms p50 (§4, M7). Property test: no Pinned-state page ever appears in either queue across 10,000 random pin/unpin/fault sequences (I9). No eviction proceeds past the dirty-check without a completed writeback acknowledgment (I8), verified by fault- injecting a writeback failure and asserting the page remains queued, not freed.

Fixtures

buckets/replacement/sweep_promote_demote.json — the clock-sweep property corpus. buckets/replacement/pinned_exclusion.json — I9 corpus. buckets/replacement/dirty_writeback_gate.json — I8 corpus, including a fault-injected writeback failure.

Pitfalls
  • Pinned pages omitted from queue-membership checks at insertion time (not just eviction time) can still get queued by a code path that doesn't consult PageState::Pinned before enqueue — the check belongs at enqueue, not only at evict.
  • A thrashing workload (resident set slightly exceeds available RAM) produces constant swap-in/swap-out; the mitigation is "swap weight" (throttling swap-in bandwidth, §21 dependency) so the workload backs off rather than the daemon spending all cycles re-faulting what it just evicted.

⬜ Phase 9 — Swap (Zswap + Disk Tiering) §21

Objectives

Implement the two-tier swap backing store (zswap compressed pool + disk, ADR-07) and the swap-in fault path, satisfying I13 (no cross-mapping slot aliasing outside MAP_SHARED).

Deliverable

vm-swap's zswap pool + disk tier + swap-in fault completion in vm-fault.

Acceptance

Zswap evict: < 5 µs p50, < 15 µs p99 per 4 KiB page (§4, M8). Zswap swap-in: < 5 µs p50. Disk swap-in: bounded by device (SSD 80/200 µs p50/p99, NVMe 30/80 µs, §4). Property test: no two non-MAP_SHARED present PTEs ever reference the same SwapEntry slot across 10,000 random swap-out/swap-in sequences (I13).

Fixtures

buckets/swap/zswap_roundtrip.json — compress/evict/swap-in/decompress corpus. buckets/swap/disk_roundtrip.json — same for the disk tier. buckets/swap/slot_aliasing.json — I13 corpus, including the MAP_SHARED exception path. buckets/swap/mixed_tier.json — pages crossing from zswap to disk under pool pressure.

Pitfalls
  • A page present in zswap that is also dirtied again in RAM (re-faulted, written, then re-evicted before the stale zswap copy is invalidated) has stale-data semantics if the old zswap entry isn't invalidated first — tracked via an explicit "superseded" flag on the old SwapEntry.
  • The 10 µs compression time-bound (21.2) is a real-time budget, not a best-effort target — a compression implementation that occasionally spikes past it under adversarial input (e.g. incompressible encrypted pages) must fall back to uncompressed disk write, not block.

⬜ Phase 10 — Page Cache & Memory-Mapped Files §22

Objectives

Implement the file-backed page cache: the (inode, offset)-keyed radix tree, writeback queue, and MAP_SHARED/MAP_PRIVATE memory-mapped-file semantics, completing the file-backed row of §8.4's dispatch table.

Deliverable

vm-pagecache's radix tree + writeback thread; MAP_SHARED/MAP_PRIVATE completion in vm-fault/vm-syscall.

Acceptance

Cache lookup: < 200 ns p50, < 500 ns p99 (§4, M9). Property test: a concurrent writeback + truncate sequence (10,000 random interleavings) never writes to a region the truncate has invalidated (§8.8's generation check, exhaustively verified).

Fixtures

buckets/pagecache/lookup_readthrough.json — cache-miss-then-hit corpus. buckets/pagecache/shared_vs_private.json — MAP_SHARED cross-process write visibility vs. MAP_PRIVATE COW divergence. buckets/pagecache/ writeback_truncate_race.json — the §8.8 failure-path fixture, made executable.

Pitfalls
  • Aliasing: two file mappings of the same file at different virtual addresses (or in different processes) share one page-cache entry by design — a truncate must invalidate every affected cache entry, not just the one a particular caller happened to touch.
  • Writeback racing a concurrent write-fault that re-dirties the page requires the dirty-bit sample to be atomic with the writeback-enqueue decision (I8) — a non-atomic sample can lose a write that happened in the gap.

⬜ Phase 11 — Huge Pages & NUMA §23

Objectives

Implement transparent huge page (THP) promotion/demotion (opt-in per ADR-09) and NUMA-aware placement with first-touch + SLIT fallback (ADR-10), resolving the forward references from Phase 4 (§16) and Phase 8 (§20).

Deliverable

vm-thp-numa's THP promote/demote + per-node buddy extension + migration daemon.

Acceptance

THP promotion cost: < 100 µs p50, < 300 µs p99 (§4, M10; dominated by the 512-entry shootdown). Per-node allocation: statistically indistinguishable latency from single-node (§4). Migration: < 50 µs p50 per page. Property test: a MADV_DONTNEED on a huge page always demotes before any constituent page is freed (no free-while-still-huge-mapped state, an extension of I1/I11 to the huge-page case).

Fixtures

buckets/thp_numa/promote_demote.json — the promotion/demotion property corpus (§8.7 row 5's contiguity-check malformed case included). buckets/thp_numa/numa_fallback.json — SLIT-order cross-node allocation corpus, run on a multi-node QEMU topology. buckets/thp_numa/ migration_correctness.json — asserts every PTE referencing a migrated page is updated (no aliasing).

Pitfalls
  • Promotion of a 2 MiB region requires every constituent 4 KiB page to be physically contiguous and unmapped from any other process — skipping the cross-process check promotes a page another process still expects at 4 KiB granularity underneath it.
  • MADV_DONTNEED on a huge page must demote before freeing — freeing at huge granularity while another core's stale TLB still holds the huge translation is a 512-page-wide version of the ordinary stale-TLB bug (I3), with 512× the blast radius.
  • Migrate-on-fault (an alternative to the background daemon) adds fault-path latency for every migrated page; gating behind a per-process policy (P11) avoids imposing that cost on processes that don't opt in.

⬜ Phase 12 — Security Primitives & Speculative-Execution Defenses §24

Objectives

Implement W^X enforcement (I6, P6), KASLR (I14), and KPTI, plus the Meltdown/Spectre-class mitigations that depend on this subsystem's page-table boundary (§25 Threat Model T6/T7), and close out the differential-testing + fuzz-canary program (ADR-12, ADR-13).

Deliverable

vm-security's W^X/KASLR/KPTI + Spectre-barrier helpers; the differential-linux bucket; the fuzz canary CI job.

Acceptance

KPTI overhead: ~10 ns/syscall p50, bounded to < 30% p99 syscall-latency regression versus no-KPTI (§4 baseline recorded in Performance Engineering, §31). Zero W^X violations across the entire conformance suite (I6, exhaustively checked, including the dual-mapping bypass case). Differential corpus: 100% observable-result match against Linux mm/, corpus runtime < 10 minutes in CI. Fuzz canary: 0 panics over 24 h rolling (M12, §31).

Fixtures

buckets/security/wx_enforcement.json — direct + dual-mapping-bypass cases. buckets/security/kaslr_entropy.json — I14's entropy-floor assertion. buckets/security/kpti_isolation.json — asserts no kernel mapping beyond the trampoline is visible in the user-mode table. buckets/differential-linux/corpus.json — the curated syscall trace set.

Pitfalls
  • W^X bypass via dual mapping: mapping a frame writable at one virtual address and executable at another defeats a check that only inspects the current request in isolation — the check must scan for existing conflicting mappings of the same frame at map time, not just validate the new request's own flags.
  • KPTI's user-mode table must expose the syscall trampoline page and nothing else kernel-side — leaking any additional kernel address via that table reintroduces exactly the Meltdown-adjacent info-leak KPTI exists to close, and independently breaks KASLR if the leaked address is used to infer the kernel's randomized base.
  • A Spectre-barrier omitted from one kernel code path that indexes user-influenced data is invisible to every functional test (the bug is a timing side-channel, not a correctness bug) — the only detection is a systematic audit of every bounds-checked, user-influenced array index (24.2), not a fixture.
