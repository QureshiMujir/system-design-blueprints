86 — Distributed File System

Project Number: 86

Project Name: Distributed File System

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Definition. A cluster-scale distributed file system in the GFS/HDFS lineage: one logical Master (metadata server — namespace tree, file→chunk map, chunk→replica map, operation log, checkpoints) coordinating many chunkservers, each storing fixed-size chunks (default 64 MiB, optional 128 MiB) as flat files on local disk. Clients resolve metadata from the Master and stream chunk bytes directly to/from chunkservers; the write path is coordinated by a primary-replica lease, not by consensus; durability defaults to 3-way replication; the Master is made highly available by a replicated log (Raft) in Phase 10. The system exposes one wire protocol (gRPC/protobuf) and one client library. It does not aim for POSIX completeness, a FUSE mount, an S3 façade, or HDFS wire compatibility in-scope — those are deferred (Deferred Features Register, §36).

Phase-0 deliverable — numbered modules:

  1. dfs-core — shared types: ChunkId, FileId, Path, Inode, Lease, ReplicaSet (§11).
  2. dfs-proto — protobuf schemas for the Master↔client and Master↔chunkserver RPCs.
  3. dfs-master — single-node Master binary: in-RAM namespace tree, chunk map, replica map (no WAL yet — Phase 2 adds it).
  4. dfs-chunkserver — chunkserver binary: flat-file chunk store, no replication yet (Phase 3+).
  5. dfs-client — client library: create/write/read/close against the Phase-0 surface.
  6. dfs-cli — operator CLI: dfs ls, dfs cat, exercised by the Phase-0 smoke test.

System boundaries.

  • Provides: hierarchical namespace, chunked storage, configurable replication, primary-replica writes, record-append, snapshots, checksummed reads, heartbeat-driven failure detection and re-replication, Master HA, background scrubbing.
  • Delegates: transport encryption is out of scope for Phase 0–9 (assume a private, trusted network — TLS is a deferred item, §36); ordinary block I/O syscalls (the chunk layout uses plain O_RDWR file I/O; there is no custom on-disk allocator).
  • Does NOT provide: POSIX semantics (locking, hard links), a FUSE mount, an S3/HDFS-compatible façade, multi-region replication, tiered/cold storage, client-side encryption, erasure coding (all deferred, §36).

Non-goals: small-file efficiency (sub-chunk files work but are not optimized — that is Colossus/Tectonic territory, not Phase 0–10); strict linearizable reads (the default consistency model is GFS-weak, §8.5); multi-tenant billing/quota UX.

Deployment model: one Master process (Phase 0–9: single instance; Phase 10: 3- or 5-node Raft group) plus N chunkserver processes, one per disk/host, on commodity Linux hosts over a private TCP network. Operators run dfs-cli/dfs-admin from any host with network access to the Master.

Target users/operators: systems engineers building or operating cluster storage for batch/analytics workloads — the niche GFS was built for: large sequential writes, large sequential reads, shared producer/consumer record-append logs.

What later phases unlock: crash-durable metadata (Phase 2); production-grade chunk I/O with checksums (Phase 3); coordinated multi-replica writes (Phase 4); a caching read path and shared-log record-append (Phase 5); automatic failure detection and healing (Phase 6); background integrity scrubbing (Phase 7); point-in-time snapshots (Phase 8); a namespace that scales past one Master's RAM (Phase 9); a Master that survives host failure (Phase 10).

Recommended language + rationale: Rust (stable toolchain, 2021 edition). The chunkserver and Master are long-running, memory-safety-critical, high-concurrency network services; Rust's ownership model removes the use-after-free/data-race bug class that dominates C/C++ distributed-storage CVE histories, with no GC pause on the data path. Rejected: Go — simpler concurrency model, but GC pauses interact badly with p99 write-latency targets (§4); Java — the HDFS reference language, but JVM tuning/GC tax is a poor fit when the goal is systems mastery, not ecosystem reuse; C++ — the Ceph precedent, but manual memory management reintroduces the exact bug class Rust removes, for no compensating benefit at this project's scope.

Prerequisites: OS file I/O and the page cache (Arpaci-Dusseau, §5); replication/consensus fundamentals (Kleppmann ch. 5/9, §5); a full read of the GFS paper before writing code (§5).

Estimated timeline: Phase 0 — 2 weeks. Full system (Phase 0–10) — 7–9 months, one engineer, full-time.

Deferred features (anchors resolve per §5.4; full table at §36): Reed-Solomon erasure coding PhaseDeferred("§36"); CRUSH placement PhaseDeferred("§36"); FUSE mount PhaseDeferred("§36"); HDFS-RPC compatibility PhaseDeferred("§36"); S3 gateway PhaseDeferred("§36"); Kerberos/SPIFFE auth PhaseDeferred("§36"); TLS transport PhaseDeferred("§36"); multi-region replication PhaseDeferred("§36"); tiered/cold storage PhaseDeferred("§36"); client-side encryption PhaseDeferred("§36").

2. Why Build This

A distributed file system is the substrate every higher-level distributed system quietly depends on: a warehouse's columnar files, a stream processor's checkpoints, a training pipeline's shards all resolve to "read these bytes from that host." When the substrate is a vendored black box, an incident ends at "file a ticket." When it is one you built, it ends at a Merkle-diff trace and a fix.

The literature is unusually mature and legible. Ghemawat, Gobioff, and Leung's 2003 GFS paper (§5) is still, in 2026, the cleanest description of the single-Master/many-chunkserver topology, the lease-coordinated write pipeline, and record-append semantics — the same shape reappears, with variation, in HDFS, Ceph, Tectonic, and JuiceFS. Building this project is not "implement an old paper"; it is acquiring the vocabulary every later cluster-storage system — including ones that reject GFS's choices (Ceph's CRUSH, Tectonic's disaggregated metadata) — is written against.

This project teaches, specifically: separating a control plane from a data plane so neither bottlenecks the other (P1); coordinating concurrent writers without a consensus round trip on the hot path (P3, the lease); making replication, placement, and repair operate on one atomic unit (P2, the chunk); making a small, fast, in-RAM structure (the namespace tree) crash-durable via a write-ahead log and checkpoints (Phase 2) without it becoming the bottleneck it protects; and staying available and correct while hosts fail continuously (Phase 6, Phase 10) — the normal condition of a large cluster, not an edge case.

It calibrates against sibling projects in this portfolio: the local file system project supplies the on-disk primitives chunkservers build on; the write-ahead-log project supplies the Master's durability primitive; the Raft-consensus project supplies Phase 10's HA story; the gossip-protocol project is the natural alternative to the heartbeat-only membership model built here (named explicitly at §35).

The historical arc matters as much as the current state: every cluster file system built after GFS has had to choose, explicitly, which of its centralizing assumptions to keep and which to discard — HDFS kept nearly all of them and optimized operability; Ceph discarded the central placement table; Tectonic discarded the single metadata service entirely. Building this project from the GFS starting point, and then reading why each successor changed what it changed, is what turns "I copied a paper" into "I can defend every one of these choices to the engineers who made the opposite one."

What Mastery Looks Like:

  • Explain why the Master must never sit on the data path, and why this holds regardless of replica count or chunk size (Phase 0, Phase 4).
  • Derive why a time-bounded lease suffices to coordinate concurrent writers without consensus, and name the exact failure mode it guards against that "primary by convention" does not (Phase 4).
  • Trace one chunk from client write call through primary, through pipelined replication, through heartbeat confirmation, to on-disk bytes on three hosts, citing every invariant it satisfies (Phase 3, Phase 4, Phase 6).
  • Explain why record-append is at-least-once, and why that is load-bearing, not incidental (Phase 5).
  • Diagnose, from a heartbeat trace alone, whether a chunk is under-replicated from a transient blip or a permanent disk failure, and the differing recovery path for each (Phase 6, Phase 9).
  • Reproduce the argument for why a single-Master namespace eventually bottlenecks, and evaluate federation vs. disaggregated metadata (Tectonic) as competing fixes (Phase 9, §32).
  • Explain how Raft's read-index protocol closes the "stale leader" read-linearizability gap a naive design leaves open (Phase 10).

Client (dfs-client). Owns two independent RPC relationships: metadata (Master) and data (chunkservers). Caches chunk-list/replica-list per open file (§8.5, Phase 5); never talks to a chunkserver it did not first resolve through the Master. Concurrency boundary: one client session, many in-flight chunk RPCs.

Master (leader). Sole writer of the namespace tree, chunk map, and replica map (I5, I6). Persistence boundary: every mutation is logged to the operation log before being applied and before any RPC acknowledgement (I7). Trust boundary: the Master is the only process a client's metadata RPC crosses into; chunkservers never see namespace paths, only ChunkIds.

Chunkserver (primary). Holds the write lease for a chunk (I3) for the lease window; serialises the write order for all replicas of that chunk; is otherwise a plain block store identical to a replica chunkserver. Concurrency boundary: one lease holder per chunk at a time.

Chunkserver (replica). Accepts writes only at the serial number the primary assigns; never originates a write order. Persistence boundary: data.bin/crc.bin/meta.bin are written and fsynced independently per chunk (§8.2).

Master (standby) / Raft group. Phase 0–9: absent (single Master, single point of failure, documented and accepted until Phase 10). Phase 10: a 3- or 5-node Raft group replicates every operation-log entry before it is considered committed (I12); standbys apply the same log and can be promoted on leader failure.

Every later section stays consistent with this diagram: the write path (§8.4) is the Client→Master→primary→secondaries chain; the read path (§8.5, Phase 5) is Client→Master (once, cached)→chunkserver (direct, repeated); the heartbeat/chunk-report arrows are the sole channel by which the Master learns chunkserver state (Phase 6).

Protocol boundary. Every arrow in the diagram is one gRPC/protobuf service (§9 ADR-12, §11); there is no shared-memory or filesystem-level channel between Master and chunkserver processes, even when co-located on the same host — this keeps the deployment topology (single-host dev cluster vs. multi-rack production cluster, §25) identical in code path, differing only in network latency.

Queueing. The under-replicated queue (Phase 6, §18.3) and the scrub schedule (Phase 7, §19.2) are the only persistent work queues in the system; the write pipeline and read path are synchronous request/response, never queued, which is why their latency (§4) is directly attributable to the RPC chain rather than to queueing delay.

The one defining property: the Master answers metadata questions in single-digit milliseconds off pure RAM state (I5, I6, I7) while chunkservers move hundreds of MB/s of data the Master never touches (P1) — the entire architecture exists to keep those two costs decoupled; every later phase that threatens this decoupling (e.g., a metadata operation that would require touching chunk bytes) is rejected at the ADR level (§9).

6. Design Principles

  1. P1 — Metadata is small and hot; data is large and cold-relative.
    • Rule: the Master answers from RAM; chunkservers move bytes the Master never touches.
    • Tradeoff: the Master's RAM ceiling caps namespace size (§4, §33).
    • Violation consequence: routing data through the Master makes metadata latency inherit data-plane jitter.
  2. P2 — The chunk is the atomic unit.
    • Rule: replication, placement, repair, and rebalance all operate on whole chunks, never partial ones.
    • Tradeoff: internal fragmentation on small files.
    • Violation consequence: partial-chunk repair logic multiplies every failure-path's state space.
  3. P3 — Writes are lease-coordinated, not consensus-coordinated.
    • Rule: a primary holds a time-bounded lease and serialises writes within it (I3).
    • Tradeoff: a lease-holder crash stalls writes to that chunk until expiry.
    • Violation consequence: routing every write through consensus makes write latency inherit consensus round-trip cost.
  4. P4 — Clients cache metadata; the Master is off the steady-state read path.
    • Rule: a client resolves chunk-list/replica-list once per TTL window and reads directly thereafter.
    • Tradeoff: a small staleness window (§4, lease/TTL values).
    • Violation consequence: every read becomes a Master round trip, destroying P1.
  5. P5 — Consistency is explicit and regime-scoped.
    • Rule: regular writes are last-writer-wins within a lease epoch; record-append is atomic, at-least-once, bounded to one chunk.
    • Tradeoff: applications needing exactly-once must dedupe by record id.
    • Violation consequence: promising exactly-once makes every crash-recovery path undecidable.
  6. P6 — Failures are the common case.
    • Rule: every subsystem — heartbeat, lease, replica, Master — has an explicit detection and recovery story (§18, §22, §24).
    • Tradeoff: engineering cost up front.
    • Violation consequence: mean-time-to-detect becomes unbounded.
  7. P7 — Placement is deterministic given the same inputs.
    • Rule: the same (chunk_id, topology, durability) always yields the same replica set (I2, §21.1).
    • Tradeoff: rebalancing on topology change is bounded but non-zero churn.
    • Violation consequence: two clients can disagree about where a chunk lives.
  8. P8 — Durability mode is configurable per namespace subtree, transitions are asynchronous.
    • Rule: 3-way replication is the default; erasure coding is deferred (§36) but the Durability enum (§11) already accommodates it.
    • Tradeoff: per-subtree mode tracking adds bookkeeping the Master must persist and enforce.
    • Violation consequence: making mode changes synchronous means a large subtree conversion blocks writers.
  9. P9 — The Master's state machine is replicated for HA; chunk data is never routed through consensus.
    • Rule: Raft covers Namespace + ChunkMap + ReplicaMap (Phase 10) only.
    • Tradeoff: chunk data durability relies on replication (I1), not consensus, so it inherits the lease model's weaker ordering guarantee.
    • Violation consequence: running data through Raft collapses write throughput to metadata-op throughput.
  10. P10 — All wire and on-disk data carries integrity metadata independent of the medium.
    • Rule: per-block CRC32C on disk (I4); checksums on the wire are implied by TCP but not trusted alone (chunkservers re-verify on read).
    • Tradeoff: CRC computation cost on every write and read (§15.7).
    • Violation consequence: silent bit rot is invisible until a client notices corrupt bytes.
  11. P11 — Every mutating operation is idempotent or made idempotent via a monotonic epoch/version.
    • Rule: lease epochs (I10), WAL replay (I8), chunk allocation counters (I6) all follow this.
    • Tradeoff: every mutation path must carry and check a version/epoch field, not just perform the mutation.
    • Violation consequence: crash-recovery replay can double-apply an operation.
  12. P12 — Operational tooling is a first-class deliverable.
    • Rule: fsck, balancer, decommission ship with their own phase and acceptance criteria (§20, §25), not as an afterthought.
    • Tradeoff: engineering time spent on tools that don't move data-path benchmarks.
    • Violation consequence: the system is undebuggable in production regardless of its data-path correctness.
  13. P13 — Wire and on-disk format compatibility is a versioned contract.
    • Rule: every protobuf message and on-disk record carries a version field; a schema change bumps it (§26).
    • Tradeoff: additive-only evolution discipline slows down schema iteration.
    • Violation consequence: a rolling upgrade corrupts state silently.
  14. P14 — The data plane favors partition tolerance and availability over strict consistency.
    • Rule: a partitioned chunkserver keeps serving reads of what it has; the Master keeps serving metadata for chunks unaffected by the partition.
    • Tradeoff: readers may observe stale or partition-local state during a network split.
    • Violation consequence: blocking on every partition means a single rack outage halts the whole cluster.

Debugging methodology. A deterministic single-process simulator (conformance/runner) drives the Master + N simulated chunkservers through a scripted fault schedule (kill, partition, corrupt, delay) and asserts one invariant per check after every simulated step — the same technique the Testing & Verification Strategy (§27) formalizes as differential/property testing. Any invariant violation halts the simulator and dumps the operation log window that produced it.

The simulator's determinism is itself load-bearing: the same fault schedule and the same initial seed must produce the same sequence of invariant checks and the same failure (if any) on every run, so a CI-caught invariant violation is reproducible locally by re-running the same seed — a flaky, non-reproducible invariant test is treated as a bug in the simulator's determinism, not tolerated as "expected flakiness."

8. Domain Model

8.1 Master state: namespace, chunk map, replica map

The Master holds three co-located structures, all covered by one operation log (§14, Phase 2): the namespace tree (FileId → Inode, directory → children map), the chunk map (FileId → ordered ChunkId list, ChunkId → ChunkMeta), and the replica map (ChunkserverId → chunk-set, the inverse index used for decommission and rebalance). All three are mutated only through the operation log's "log, then apply" sequence (I7).

8.2 Chunk and block model

A chunk is a fixed-size (64/128 MiB) unit identified by a 64-bit ChunkId, stored on a chunkserver as a small file group:

${CS_DATA_DIR}/<chunk_id>/
  data.bin     # chunk bytes, padded to chunk size
  meta.bin     # version, epoch, durability mode, primary/peers
  crc.bin      # CRC32C per 64 KiB block

Each chunk is divided into fixed 64 KiB blocks for checksum granularity (I4); a corrupt block invalidates only that block's read, not the whole chunk.

8.3 Namespace, replication, and the lease state machine

A chunk's lease cycles through four states:

State Entered when Exits when Held by
Unleased chunk allocated, no writer yet a client requests a write none
Leased Master grants lease to a replica lease expiry or explicit revoke one chunkserver (primary)
Expiring renewal window entered, no renewal received renewal arrives (→ Leased) or timer fires (→ Unleased) current primary
Revoked Master failover or explicit admin revoke a fresh lease is granted (→ Leased) none

This mirrors Frangipani's separation of a lock service from the data store (Thekkath et al., §5) — the Master plays the lock-service role for chunks without running a general distributed lock service.

8.4 The write pipeline (worked example)

Client writes 64 MiB to a new file /logs/service-a/2026-08-02.log:

  1. create(path) → Master allocates FileId, logs it (I7), returns.
  2. allocate_chunk(file) → Master picks a replica set via the placement function (P7, §21.1), e.g. {cs-04 (primary), cs-11, cs-19}, logs the allocation, returns (ChunkId, ReplicaSet, Lease).
  3. Client pushes data to the pipeline: cs-04 → cs-11 → cs-19 (chained forwarding, not client fan-out — halves client upload bandwidth cost).
  4. Client sends WriteChunk{chunk_id, epoch, offset, data, crc} to cs-04 (the primary).
  5. cs-04 assigns serial number S, applies locally, forwards (S, data) to cs-11 and cs-19.
  6. cs-11, cs-19 apply at serial S, acknowledge to cs-04.
  7. cs-04 acknowledges to the client once all replicas confirm (I3, I9 do not apply here — regular write, not append).
  8. Client calls complete_chunk(chunk_id, len, crc); Master transitions ChunkState::Open → Closed.

8.5 Consistency model

Write type Guarantee Bound
Regular write (§8.4) last-writer-wins within a lease epoch epoch-scoped; a stale-epoch write is rejected (I10)
Record-append (Phase 5) at-least-once, atomic at record granularity ≤ MAX_RECORD_SIZE (16 MiB), one chunk
Read (any replica) may observe a write not yet visible on every replica during pipeline propagation bounded by pipeline completion (§4 p99 write latency)
Read after complete_chunk read-your-writes for the writer's own session (client cache invalidation on close) immediate

8.6 Malformed-input example

A WriteChunk RPC arrives at a secondary replica with a serial number lower than the last-applied serial for that chunk (a duplicate or reordered delivery). The secondary must reject with StaleSerial, not silently re-apply — re-applying would violate I9 if the data payload differs due to a retried, mutated request. The primary treats StaleSerial from a secondary as a signal to re-sync that secondary via anti-entropy (§19, Phase 7) rather than retry the same write blindly.

8.7 Failure-path example: primary dies mid-write

cs-04 (primary, holding the lease for chunk C) crashes after step 5 above but before step 7 (secondaries applied serial S, client never got an ack). The client's write RPC times out; it re-resolves the chunk's replica-list from the Master, which detects cs-04's heartbeat absence (Phase 6), revokes the lease (Revoked state, §8.3), and — once the under-replicated queue restores 3-way replication (I1) — grants a fresh lease at a higher epoch (I10) to one of cs-11/cs-19. The client retries the write against the new primary; because serial S was already applied on cs-11/cs-19, the new primary's next_serial (recovered from meta.bin, not reset to zero — I6-analogue for serials) continues from S+1, and the retried write is logically a fresh append/write at the new serial, not a re-application of S.

8.8 Worked example: record-append with a padded retry (I9)

Two writers (W1, W2) append to a shared log chunk L concurrently, primary cs-07:

  1. W1 sends record_append(L, data=1 KiB); primary assigns serial 41, computes offset 6.29 MiB (the current end of the log), forwards (41, offset=6.29 MiB, data) to secondaries cs-13, cs-22.
  2. Concurrently, W2 sends record_append(L, data=2 KiB); primary serializes it after W1's request (single primary, I3), assigns serial 42, offset 6.291 MiB.
  3. cs-13 applies both successfully. cs-22 applies serial 41 but its disk write for serial 42 fails (a transient I/O error, not a crash).
  4. The primary detects cs-22's failed apply for serial 42 via the fan-out acknowledgement. Per §14.2's protocol, it pads cs-22's view at the offset serial 42 would have occupied (so cs-22's byte layout stays aligned with cs-13's for future records) and retries W2's record at a fresh offset (6.30 MiB) on every replica, including cs-13 (which already had it at 6.291 MiB).
  5. The result: cs-13 physically holds W2's record at two offsets (6.291 MiB, orphaned by the retry, and 6.30 MiB, the winning copy); cs-22 holds it only at 6.30 MiB. Every replica that successfully applied the record agrees it lives at offset 6.30 MiB (I9) — cs-13's earlier, orphaned copy is a duplicate the reader-side record_id (§17.6) is expected to deduplicate, the concrete instance of P5's at-least-once guarantee.
  6. The primary returns offset 6.30 MiB to W2 as the append's result; W1's record at 6.29 MiB is unaffected and uncontested throughout.

12. Phase 0 — Repository Skeleton & Correctness Kernel

12.1 Objectives

Stand up the repository (§10), the workspace build, and a single-replica smoke path: create a file, write one chunk, read it back, with no replication, no WAL, no leases. Establish the invariant-testing harness (§7 methodology) skeleton so every later phase has somewhere to register its checks.

12.2 Detailed Implementation Steps

  • Land Cargo.toml workspace and every crate in §10 with stub lib.rs.
  • Implement dfs-core types (§11) as compile-only definitions (P13: version fields present from day one, even if unused).
  • Implement dfs-proto with the minimum viable RPCs (Create, AllocateChunk, Write, Read).
  • Implement a stub dfs-master holding Namespace (§8.1) in a single RwLock, no WAL.
  • Implement a stub dfs-chunkserver storing chunks as flat files under ${CS_DATA_DIR}/<chunk_id>/data.bin, no CRC yet.
  • Implement dfs-client wiring create + write + read + close; implement dfs-cli with dfs ls / dfs cat.
  • Wire docker-compose.yml for a single Master + three chunkservers (only one is used by the smoke path; the other two exist so Phase 3 has them ready).

12.3 Deliverable

make compose-up brings up a one-Master, three-chunkserver cluster; dfs cat after a dfs-driven write returns the exact bytes written.

12.4 Acceptance Criteria

  • make test passes with tests/three_node_smoke.rs: create a 1-byte file, write it, read it back, assert byte-identity.
  • Repo matches §10's tree exactly (find crates -maxdepth 1 diff-clean against the layout).
  • ADR-01, ADR-02, ADR-03, ADR-12, ADR-22 recorded under docs/adr/.

12.5 Conformance Fixtures

conformance/corpora/namespace/create_one_file.json — expected: one inode, one chunk, byte-identical read. conformance/corpora/chunk-io/single_byte_roundtrip.json — expected: data.bin contains exactly the written byte.

12.6 Pitfalls

  • Chunkservers must register their externally-reachable address with the Master, not 127.0.0.1 — a bug here creates a cluster that writes but cannot read back; signal: dfs cat times out only from off-host clients.
  • Resist replicating in Phase 0 (P2, P3 land in Phase 3–4) — the smoke test is deliberately single-replica; a "just in case" second copy now creates an untested code path Phase 3 must later unwind.
  • Protobuf field numbers committed now are a wire-compatibility promise (P13) — get them right before Phase 1 extends the schema; a renumbered field later breaks every already-written chunk's meta.bin version negotiation.
  • docker-compose.yml's network aliasing must match what chunkservers self-report — a mismatch between the compose network name and the registered address is the single most common Phase-0 debugging session.

12.7 Performance Concerns

  • None gated yet — Phase 0 has no throughput target (§4's numbers first bind at Phase 3).
  • Avoid premature buffering choices (fixed-size vs. streaming buffers) that would need rework once CRC (Phase 3) and pipelining (Phase 4) land — pick an API shape (Bytes-based, not raw Vec<u8>) that both can extend without a signature break (P13).

12.8 Edge Cases

  • Empty file (zero chunks) must still resolve via open, returning an empty chunk list, not an error.
  • A create on a path whose parent does not exist must fail with a typed error, not panic.
  • A dfs cat on a path that does not exist returns NotFound, not an empty read.
  • A create on a path that already exists must fail with a typed AlreadyExists, not silently overwrite (namespace correctness groundwork for I5, formalized in Phase 1).

12.9 Failure Analysis

  • A crashed Master at this phase loses all state (no WAL yet, by design — Phase 2 fixes this; document the gap explicitly in BUILD_PLAN.md so it is never mistaken for a Phase-0 bug).
  • A crashed chunkserver loses only unflushed writes; there is no replication to fail over to yet.

12.10 Operational Notes

  • make compose-up / make compose-down are the only operator surface at this phase.
  • Structured logging (JSON lines to stdout) is wired from the first commit so every later phase's telemetry (§25) has a consistent sink to write to.

13. Phase 1 — Namespace Tree & Metadata Operations

13.1 Objectives

Implement the full namespace tree, chunk map, and replica map (§8.1) as in-RAM structures with real concurrency control, replacing Phase 0's single-lock stub with the production data structures the rest of the system depends on (P1).

13.2 Detailed Implementation Steps

  • Implement Namespace (crates/dfs-master/src/namespace.rs) as BTreeMap<FileId, Inode> plus a BTreeMap<FileId, BTreeMap<String, FileId>> children index, root at FileId(1).
  • Implement iterative (not recursive — stack-overflow risk on deep paths) path resolution.
  • Implement ChunkMap and ReplicaMap (§8.1) as separate RwLock-guarded structures so chunk-map reads (common) don't contend with namespace-tree writes (rarer, per P1).
  • Wire allocate_chunk to call the Placement trait (§11, P7) — DefaultPlacement for Phase 1, rack-aware per ADR-15.
  • Hold both directory locks in a deterministic (lower-FileId-first) order during rename to avoid deadlock (I5: no orphan inodes tolerates no half-applied rename).

A Master serving create/open/list/rename/delete/allocate_chunk/complete_chunk against the real namespace tree, still without a WAL (Phase 2 adds durability).

  • ≥ 5,000 metadata ops/sec sustained on a 100K-file namespace, single host (§4).

  • namespace/bulk_100k.json — expected: zero orphan inodes (I5) post-mutation.

13.6 Pitfalls

  • The namespace tree is the hottest structure in the Master; a single RwLock is correct at Phase 1 scale but throughput-limited — do not partition it prematurely (Phase 9 does this when §33's numbers justify it).
  • rename is the trickiest RPC: a half-applied rename (removed from source, not yet added to destination) is a permanent I5 violation; both directory locks must be held for the operation's duration.
  • Lock-ordering by raw FileId value (not insertion order) is required to avoid deadlock when two concurrent renames target each other's parent directories — an ad hoc "lock whichever I see first" ordering reintroduces the deadlock the fixed ordering was meant to prevent.
  • list results must be a consistent snapshot of the children map at one instant — iterating while another thread mutates it under a lock-discipline gap silently produces a corrupted listing rather than an error, making the bug hard to notice.

13.7 Performance Concerns

  • Lock contention on the namespace RwLock is invisible below a few thousand ops/sec and becomes the dominant cost above it — instrument lock-wait time from day one (§25) rather than guessing later.
  • Chunk allocation is sequential per file (a writer holds the file's lock while allocating) but concurrent across files — a workload of many small files parallelizes well; one huge file's chunk allocations do not.

13.8 Edge Cases

  • A rename where source and destination share a parent directory (single-lock case) must not double-acquire the same lock.
  • A list on a directory concurrently being deleted must return either the full prior listing or NotFound, never a partial listing (P11: idempotent-or-versioned).
  • A create racing a delete of the same parent directory must resolve deterministically — either the create fails with NotFound or succeeds before the delete completes, never both partially.
  • A deeply nested path (thousands of components) must resolve in bounded stack space — the iterative resolver (§13.2) exists precisely because a recursive one would risk stack overflow here.

13.9 Failure Analysis

  • Without a WAL (still true at Phase 1), a Master crash loses the namespace entirely — an accepted, documented gap until Phase 2.
  • A chunk-allocation that reserves a ChunkId but never reaches complete_chunk leaves the chunk in Allocating state indefinitely at this phase; Phase 2's checkpoint/recovery and Phase 6's sweep close this gap.

13.10 Operational Notes

  • Expose namespace_ops_total{op} and namespace_lock_wait_ms counters (§25) from Phase 1 onward.
  • These are the primary signal Phase 9's federation decision (§21) is later justified against.

14. Phase 2 — Operation Log, Checkpoints & Crash Recovery

14.1 Objectives

Make the Phase-1 Master durable: every namespace/chunk-map/replica-map mutation is logged before being applied (I7), and the Master can restart and reconstruct exact prior state (I8).

14.2 Detailed Implementation Steps

  • Implement the operation log (dfs-wal) as an append-only, fsync-per-entry log of MasterWalOp variants (Create, Rename, Delete, AllocateChunk, CompleteChunk, UpdateReplica, Snapshot) — the log-structured pattern from Petrov (§5).
  • Enforce the strict sequence: append + fsync, then apply to in-RAM state, then acknowledge (I7).
  • Implement periodic checkpointing: serialize Namespace + ChunkMap + ReplicaMap to metadata.snapshot every 1M ops or 1 GiB of WAL (§4), then truncate the WAL to entries since that point.
  • On restart: load the latest snapshot, replay WAL entries from the recorded offset, refuse RPCs (RetryLater) until replay completes (I8).

14.3 Deliverable

A Master that survives kill -9 and reconstructs bit-identical namespace + chunk map + replica map on restart.

14.4 Acceptance Criteria

  • WAL append throughput ≥ 50,000 ops/sec on commodity NVMe (§4).
  • A test creates 10K files, kills the Master, restarts it, and asserts namespace bit-identity (fixture conformance/corpora/ha/crash_10k_files.json).
  • A test allocates 1K chunks, partially replicates some, kills the Master, restarts, and asserts each chunk lands in the correct ChunkState (Open for fully replicated, UnderReplicated otherwise).

14.5 Conformance Fixtures

  • ha/crash_10k_files.json — expected: identical namespace pre/post crash.
  • ha/replay_idempotent.json — replay the same WAL segment twice; expected: identical resulting state (I8).

14.6 Pitfalls

  • The WAL must be fsynced before acknowledgement — an O_DIRECT-without-fsync or async-writeback shortcut is a correctness bug (I7), not a performance tradeoff.
  • Monotonic counters (FileId, ChunkId allocators, I6) must have their allocated values recorded in the log entry, not re-derived at replay time, or replay diverges from the original run (violates I8).
  • A checkpoint that captures Namespace and ChunkMap at slightly different instants (two separate locks, not one) can produce a checkpoint where a chunk references a file the namespace half doesn't yet know about — the checkpoint must be taken under one consistent quiesce point covering all three structures.
  • Truncating the WAL before the corresponding checkpoint is confirmed durable (fsynced) on disk is a classic off-by-one that loses the very entries the checkpoint was supposed to have captured — truncate only after the checkpoint's own fsync returns.

14.7 Performance Concerns

  • Checkpoint-taking from a quiesced state (brief write-pause) is simpler than copy-on-write snapshotting and is the Phase-2 choice (ADR-10); it costs a bounded pause proportional to namespace size, acceptable at the §4 namespace ceiling (§33 C10 derives the worst-case pause).
  • WAL fsync latency dominates metadata-op p99 (§4, M1) more than any in-RAM data-structure cost — batching multiple pending log entries into one fsync (group commit) is the standard lever if throughput (M12) falls short before latency does.

14.8 Edge Cases

  • A crash between WAL-append and in-RAM-apply must be safe to apply on replay (P11).
  • A crash mid-checkpoint-write must never leave a corrupt/partial metadata.snapshot — write to a temp path and atomically rename on completion.
  • A restart that finds a checkpoint but no WAL segment newer than it (a clean shutdown) must skip replay entirely and serve immediately, not stall waiting for a non-existent segment.
  • A WAL segment whose final entry is truncated exactly at a checksum boundary (ambiguous: valid-but-incomplete vs. corrupt) must be treated as incomplete and discarded, never partially parsed.

14.9 Failure Analysis

  • A torn WAL entry (partial write, e.g. power loss mid-append) is detected by a per-entry checksum; replay stops at the first invalid entry and the Master starts from the last valid one, accepting the loss of the torn tail (documented as an accepted RPO gap — the client's write was never acknowledged, per I7's ordering).

14.10 Operational Notes

  • Expose wal_fsync_latency_ms, checkpoint_duration_ms, and replay_duration_ms (§25).
  • A runbook (docs/runbook/master-failover.md, extended in Phase 10) documents the manual restart procedure until Phase 10 automates it.

15. Phase 3 — Chunkserver Storage, Block Checksums & Chunk Layout

15.1 Objectives

Turn the Phase-0 flat-file chunkserver stub into the production chunk store: fixed-layout chunks with per-block CRC32C (I4, ADR-13), ready for the replication pipeline Phase 4 adds.

15.2 Detailed Implementation Steps

  • Implement ChunkStore/ChunkHandle (crates/dfs-chunkserver/src/chunk_store.rs) managing the three-file-per-chunk layout (§8.2): data.bin, meta.bin, crc.bin.
  • Compute CRC32C (RFC 3720, §5) per 64 KiB block at write time; verify at read time.
  • On mismatch, return BlockCorrupt (I4) and surface it to the Master via the next heartbeat's failed_replicas list (feeds Phase 6).
  • Use ordinary buffered I/O with posix_fadvise(POSIX_FADV_DONTNEED) after large sequential writes/reads rather than O_DIRECT (McKusick et al., §5) — avoids write-amplification foot-guns on misaligned writes while still not polluting the page cache with cold data.

15.3 Deliverable

A chunkserver serving write/read against the real on-disk layout, with CRC verified on every read.

15.4 Acceptance Criteria

  • ≥ 500 MB/s sustained write, ≥ 800 MB/s sustained read on a single NVMe disk (§4).
  • A test corrupts one 64 KiB block on disk and asserts the next read of that block returns BlockCorrupt, while reads of other blocks in the same chunk succeed (block-granular fault isolation, §8.2).

15.5 Conformance Fixtures

  • chunk-io/crc_mismatch_single_block.json — one block corrupted; expected: BlockCorrupt on that block only.
  • chunk-io/full_chunk_roundtrip.json — write 64 MiB, read back, byte-identical.

15.6 Pitfalls

  • crc.bin must be fsynced in the same durability window as data.bin — an asymmetric fsync order produces a chunk that reads fine until the next verification pass discovers CRC/data disagreement.
  • O_DIRECT on misaligned offsets is a common write-amplification trap; the posix_fadvise approach avoids it (§15.2).
  • A chunk-directory rename or atomic-swap trick borrowed naively from single-file atomic-write patterns does not extend cleanly to a three-file-per-chunk layout — all three files must move together with respect to any single logical mutation, which is why meta.bin records a confirmed-flushed offset rather than relying on directory-level atomicity.
  • Reusing a freed chunk's on-disk directory for a new ChunkId without fully clearing crc.bin/merkle.bin first leaves stale checksums that pass verification against stale data — I6's "never reuse a ChunkId" invariant exists partly to make this class of bug structurally impossible.

15.7 Performance Concerns

  • Per-block CRC computation is on the write hot path; use a SIMD CRC32C implementation, not a naive table-free bit-loop, or it becomes the throughput bottleneck before disk I/O does.
  • Reading crc.bin (a small, hot file) on every read RPC should stay page-cache-resident even under memory pressure — its small size relative to data.bin (1/16,384th) makes this cheap to guarantee explicitly rather than leave to the OS's default eviction policy.

15.8 Edge Cases

  • A write that spans a block boundary must update CRC for both affected blocks.
  • A read of length zero must return an empty buffer, not an error.
  • A chunk directory that exists but is missing one of its three files (partial delete, crash mid-create) must be treated as corrupt and reported, not silently served.
  • A read that requests bytes past the chunk's recorded logical length (but within the padded 64 MiB allocation) must return OutOfRange, not the padding bytes.

15.9 Failure Analysis

  • Disk-full during a chunk write must fail the write cleanly and leave no partially-written data.bin region unaccounted for — the chunkserver truncates back to the last confirmed-flushed offset recorded in meta.bin.

15.10 Operational Notes

  • Expose chunk_write_bytes_total, chunk_read_bytes_total, crc_mismatch_total (I4's telemetry, §7) per chunkserver.
  • These feed the Performance Engineering targets table (§29, M3–M4).

16. Phase 4 — Primary-Replica Lease & Write Pipeline

16.1 Objectives

Implement the GFS-style write pipeline (§8.4): lease-coordinated primary, chained replication, ordered application across replicas — the write-side realization of P3 and I3.

16.2 Detailed Implementation Steps

  • Implement LeaseHolder (crates/dfs-chunkserver/src/lease_holder.rs): accepts a lease from the Master, tracks next_serial per chunk, rejects writes from any process that isn't the current primary (NotPrimary, enforcing I3).
  • Implement the pipeline per §8.4 steps 3–7: client pushes data along a chain (primary → secondary₁ → secondary₂), not client fan-out, halving client egress (Ghemawat et al., §5, §3.1).
  • Primary assigns the serial number (I9's ordering basis), applies locally, forwards (serial, data) to secondaries, acknowledges the client once every replica confirms.
  • Wire lease issuance/renewal RPCs against LeaseManager (§8.3 state machine) on the Master side, respecting epoch monotonicity (I10).

16.3 Deliverable

A three-replica write pipeline: a client write to a new chunk lands identical bytes at the same serial number on all three chunkservers.

16.4 Acceptance Criteria

  • 64 MiB chunk replicated to two secondaries in ≤ 100 ms over a 10 Gbps LAN (§4, matches the p50 write-latency row).
  • A test kills a secondary mid-write and asserts: the primary surfaces the error, the Master marks the chunk UnderReplicated, and re-replication is queued (feeds Phase 6's queue, I11).

16.5 Conformance Fixtures

  • replication/kill_secondary_mid_write.json — expected: primary error surfaced, chunk UnderReplicated.
  • replication/stale_epoch_write_rejected.json (I10) — a write at an old epoch; expected: StaleEpoch rejection, not silent application.

16.6 Pitfalls

  • A careless await ordering in the pipeline doubles tail latency — read GFS §3.1's data-flow/control-flow split twice (§5) before implementing.
  • The primary's serial number must be monotonic per chunk, not per chunkserver process; a failed-over primary inherits the serial cursor from meta.bin, not from zero (§8.7's worked failure path).
  • Acknowledging the client before every replica confirms (rather than waiting for the full set) silently downgrades the replication factor's durability guarantee without anyone noticing until a replica-loss incident reveals fewer confirmed copies than expected.
  • A lease renewal that races the lease's own expiry (the renewal RPC arrives one tick after the Master already revoked it) must be rejected cleanly by the Master, not accepted and then immediately contradicted by a concurrent Revoked transition.

16.7 Performance Concerns

  • The pipeline overlaps network transfers (chained forwarding starts before the prior hop fully completes) specifically to reduce tail latency — a naive "wait for full receipt then forward" implementation misses this and roughly doubles p95/p99 (§4).
  • Chaining through the topologically-farthest replica last (rather than a fixed order) reduces worst-case cross-rack hops; the chain order should be topology-aware, not simply the order the Master listed replicas in.

16.8 Edge Cases

  • A secondary that receives a write with a serial number lower than its last-applied serial rejects with StaleSerial (§8.6's malformed-input example) rather than silently re-applying.
  • A lease that expires mid-write must cause the primary's next write attempt to fail with NotPrimary, forcing client re-resolution.
  • A client that disconnects mid-pipeline-write (after the primary applied but before acknowledging) must not cause the primary to roll back its already-applied write — the write stands; the client's next open sees it.
  • Two clients racing to write the same new chunk (a rare allocation race) must be resolved by the Master issuing exactly one lease per chunk (I3) — the losing client's attempt fails with NotPrimary against the winner's primary, never silently interleaving bytes from both.

16.9 Failure Analysis

  • Primary death mid-write is the canonical Phase-4 failure — traced in full at §8.7: client timeout → re-resolve → Master detects heartbeat absence (Phase 6) → lease revoked (Revoked, §8.3) → re-replication restores 3-way (I1) → fresh lease at higher epoch (I10) → client retries at next_serial continuation, never re-applying the original serial.

16.10 Operational Notes

  • Expose lease_grants_total, lease_conflicts_total (I3's telemetry).
  • Expose pipeline_write_latency_ms histograms (§25, feeds M1–M2 in §29).

17. Phase 5 — Read Path, Client Cache & Record-Append

17.1 Objectives

Implement the read path (P4: Master off the steady-state read path) and record-append (P5's second consistency regime, I9), the two remaining pieces of the GFS-style client surface.

17.2 Detailed Implementation Steps

  • Implement ChunkCache (crates/dfs-client): per-file chunk-list/replica-list cache, invalidated on Stale/NotFound RPC errors or a 60 s TTL (ADR-20).
  • Implement topology-aware replica selection (same rack > zone > region > anywhere) and read-time failover: a failed read against one replica retries the next in topology order before falling back to a fresh Master resolution.
  • Implement record_append (§8.4's sibling protocol) per the primary-serial-number discipline of Phase 4.
  • Implement the padding/retry behavior of I9: if a secondary fails to apply at the primary's chosen offset, the primary pads that replica's view and retries the whole record at a fresh offset on every replica — guaranteeing every replica that successfully applies the record does so at the same offset (I9), while permitting at-least-once duplication (P5, Cachin/Guerraoui/Rodrigues's broadcast-primitive framing, §5).

17.3 Deliverable

A client that reads a 1 GiB file at ≥ 1 GB/s (network-limited) from a three-node cluster, and a record-append RPC usable by concurrent writers to one shared log chunk.

17.4 Acceptance Criteria

  • p50/p95/p99 read latency for a 4 KiB warm read: ≤ 0.4 ms / 1.5 ms / 6 ms (§4).
  • A test kills the chosen replica mid-read and asserts client failover completes the read.
  • A record-append test drives 1,000 parallel writers against one chunk and asserts every record appears at least once, at a consistent offset across every replica that applied it (I9).

17.5 Conformance Fixtures

  • chunk-io/read_failover_kill_replica.json — expected: read completes via a surviving replica.
  • chunk-io/record_append_1k_writers.json — expected: zero I9 offset-mismatch across replicas; every writer's record recoverable.

17.6 Pitfalls

  • The chunk cache's 60 s TTL (the GFS default, ADR-20) trades staleness for Master load — do not tune it down reflexively; measure Master RPC volume first.
  • Record-append's at-least-once nature (P5) must be documented for application authors, not just implemented — a record_id field is the standard dedup remedy and belongs in every append-log's schema.
  • Topology-aware replica selection that always prefers the "closest" replica can starve the other replicas of read traffic entirely, hiding a slowly-degrading disk on a rarely-read replica until a scrub (Phase 7) happens to touch it — occasional read-traffic sampling across all replicas surfaces this earlier.
  • A client that caches a chunk-list on a long-lived, idle connection can silently outlive the TTL's intended staleness bound if invalidation is triggered only by an active RPC error, not a background timer.

17.7 Performance Concerns

  • The page cache is shared between the chunkserver process and the OS; normal reads should not bypass it, but very large sequential reads should posix_fadvise(POSIX_FADV_DONTNEED) afterward to avoid evicting hotter working-set data (§15.2's technique reused here).
  • Record-append's padding-and-retry path (§8.4, I9) is strictly more expensive than a regular write's single-attempt path — pre-emptively rolling to a fresh chunk slightly before exhaustion trades a little space for fewer retries.

17.8 Edge Cases

  • A record-append that would exceed the chunk's remaining capacity must force-close the current chunk (padding to chunk-end on every replica), allocate a new chunk from the Master, and retry there — never split a record across two chunks (bounded by MAX_RECORD_SIZE, §4).
  • A read spanning a corrupt block (I4) must surface BlockCorrupt for that portion and let the client failover, not return partial silently-wrong bytes.
  • A record-append of exactly MAX_RECORD_SIZE bytes into a chunk with exactly that much free space must succeed (an off-by-one here either wastes a chunk prematurely or overflows it).
  • Concurrent record-appends from the same client (pipelined, not sequential) must each still receive a distinct, correctly-ordered offset — client-side pipelining must not be mistaken for a single logical writer that can skip the primary's serialization.

17.9 Failure Analysis

  • A client whose cached replica-list is entirely stale (all three replicas moved, e.g. post-rebalance) exhausts its failover list and must fall back to a fresh Master resolution rather than error out — the fallback is the recovery path, not an edge case to special-case away.

17.10 Operational Notes

  • Expose client_cache_hit_ratio, record_append_retries_total, read_failover_total (§25).
  • A chunk-cache hit-ratio drop is the first signal operators check before assuming a Master-side regression.

18. Phase 6 — Heartbeats, Failure Detection & Re-Replication

18.1 Objectives

Close the loop P6 promises: turn chunkserver loss into detected, queued, throttled re-replication (I1, I11), the mechanism every earlier phase's failure paths (§8.7, §16.9) depend on.

18.2 Detailed Implementation Steps

  • Implement HeartbeatTracker (crates/dfs-master/src/heartbeat.rs): every chunkserver heartbeats every 3 s (§4) carrying free/used bytes, a delta chunk-report, and locally-detected failed replicas.
  • Three missed heartbeats → Suspect; ten → Dead (§4's thresholds), at which point every chunk that chunkserver held is marked UnderReplicated (I1).
  • Implement UnderReplicatedQueue (under_replicated.rs) as a priority queue ordered by (fewest replicas remaining, oldest file, largest chunk) — HDFS's under-replicated-blocks precedent (Shvachko et al., §5).
  • Implement the re-replication worker pool: pick a healthy source and a placement-compliant destination (P7, re-evaluating placement at repair time, not just at initial allocation), throttle to 5 concurrent streams per source chunkserver (§4) to bound fabric saturation.

18.3 Deliverable

A cluster that detects a dead chunkserver within 30 s and restores 3-way replication for its chunks without operator intervention.

18.4 Acceptance Criteria

  • Dead-chunkserver detection ≤ 30 s (§4).
  • Re-replication of a 100-chunk dead chunkserver completes in ≤ 5 minutes on a 10 Gbps LAN (§4).
  • A chaos test kills a chunkserver and asserts: detection, queuing, completion, and post-repair placement-constraint compliance (I2) all hold — fixture chaos/kill_chunkserver_full_cycle.json.

18.5 Conformance Fixtures

  • chaos/kill_chunkserver_full_cycle.json — expected: I1 and I2 both hold within the 5-minute SLA.
  • replication/heartbeat_missed_transitions.json — expected: Live → Suspect → Dead transitions occur at exactly 9 s / 30 s.

18.6 Pitfalls

  • Aggressive heartbeat/dead-threshold tuning (e.g., 1 s/5 s) detects failures faster but generates spurious dead-detections under ordinary network jitter — keep the §4 defaults conservative; let operators override.
  • Re-replication traffic is a fabric-saturation risk: a 1 PB cluster at 30% utilization losing a 10%-of-capacity chunkserver generates a proportional wave of repair traffic; the per-source throttle (§4) is not optional tuning, it is a required safety valve.
  • Prioritizing the under-replicated queue purely by "fewest replicas remaining" without the secondary (file age, chunk size) tie-breakers can starve a large, old file's last chunk behind an endless stream of newly-created single-replica-loss chunks — the full three-key ordering (§18.2) exists to prevent this.
  • A re-replication destination chosen without checking existing disk utilization can create a new hotspot chunkserver — destination selection must weigh both placement compliance (I2) and current free capacity (feeds FM-5).

18.7 Performance Concerns

  • The placement function (P7) must be re-evaluated at repair time against current topology, not reused from initial allocation — picking "any live chunkserver" instead of "a placement-compliant one" silently reintroduces I2 violations under repair.
  • The heartbeat handler's chunk-report-delta application must stay O(delta size), not O(full inventory) — a chunkserver rejoining after a long absence and sending a full report is the one case allowed to be more expensive, and should be rate-limited separately from steady-state heartbeats.

18.8 Edge Cases

  • A chunkserver that flaps (misses heartbeats, then resumes before Dead) must not have its chunks needlessly re-replicated during the Suspect window — only Dead triggers queuing.
  • Two chunkservers dying simultaneously, each holding a replica of the same chunk, must not deadlock the repair worker pool (source selection must skip any not-yet-recovered chunk gracefully).
  • A chunkserver returning from Dead (fully re-replicated elsewhere in its absence) must have its now-stale local copies garbage-collected, not silently treated as extra, unaccounted-for replicas.
  • A heartbeat claiming a chunk-report for a chunk the Master has no record of (e.g. a decommissioned-then-repurposed disk) must be rejected and logged, not silently absorbed into the replica map.

18.9 Failure Analysis

  • A permanent majority-replica loss (e.g., 2 of 3 replicas dead simultaneously, one recoverable) is detected when the under-replicated queue cannot find a healthy source for a chunk within a bounded number of attempts — this degrades to a Corrupt/unrecoverable-chunk alert (feeds Failure Modes FM-3, §24) rather than looping silently forever.

18.10 Operational Notes

  • Expose chunkserver_status{status}, under_replicated_queue_depth (I11's telemetry), rereplication_bytes_total.
  • The docs/runbook/under-replicated.md runbook walks an operator through interpreting a sustained non-zero queue depth.

19. Phase 7 — Scrubbing, Anti-Entropy & Data Integrity

19.1 Objectives

Close the silent-corruption gap I4's read-time check alone leaves open (data corrupted between reads goes undetected until the next read touches it) with background scrubbing and Merkle-diff anti-entropy (ADR-09, ADR-14).

19.2 Detailed Implementation Steps

  • Implement a Merkle tree over each chunk's 1 MiB pages (merkle.bin, §8.2's layout extended); the root hash rides in every chunk-report heartbeat (Phase 6's channel, reused).
  • On a discrepancy between the Master's recorded root and a chunkserver's reported root, trigger a Merkle-diff: walk both trees in lockstep, descending only into subtrees whose hashes differ (bounding repair bandwidth to the divergent region, ADR-09).
  • Implement a background scrub loop that reads every chunk's blocks at a throttled rate such that the full cluster is revisited within 14 days (§4), independent of and lower-priority than the under-replicated queue (Phase 6) and any client-driven reads.

19.3 Deliverable

A scrub job that finds and repairs a single-page (1 MiB) divergence between two replicas of a 64 MiB chunk while transferring only that page, not the whole chunk.

19.4 Acceptance Criteria

  • A test intentionally diverges two replicas by one byte and asserts anti-entropy converges them within one scrub cycle, transferring ≤ 1 MiB (not 64 MiB) of repair bandwidth.
  • Full-cluster scrub throughput is throttled such that client I/O p99 latency (§4) degrades by ≤ 10% during a scrub pass.

19.5 Conformance Fixtures

  • chaos/single_page_divergence.json — expected: convergence within one scrub cycle, ≤ 1 MiB transferred.
  • chunk-io/scrub_throttle_client_impact.json — expected: client p99 read latency stays within 10% of baseline during active scrubbing.

19.6 Pitfalls

  • A naive Merkle-diff that transfers the whole tree at every level is O(N log N) in bytes; the streaming, divergence-only variant is O(K log N) where K is the divergence size (ADR-09) — implement the streaming form or the "bounded repair bandwidth" claim (§4, §19.4) is false.
  • The Merkle root must be updated atomically with chunk writes (merkle.bin alongside crc.bin, §15) — a torn write that updates data but not the tree looks like divergence to every future scrub pass and is a permanent false positive until manually reconciled.
  • Scrubbing a chunk concurrently being re-replicated (Phase 6) against a destination that hasn't finished its initial full copy can flag a false divergence against a legitimately-incomplete replica — the scrub loop must skip in-progress-repair destinations, not just chunks under an open write lease.
  • Comparing Merkle roots computed under two different page-size assumptions (e.g. after a configuration change) produces spurious full-tree divergence — the page size (1 MiB) is a fixed constant (§8.2), never a per-cluster tunable, specifically to avoid this.

19.7 Performance Concerns

  • Scrub I/O competes with client I/O and re-replication (Phase 6) for disk bandwidth; the throttle must be tunable independently of the under-replicated-queue throttle (§4) since the two serve different urgency levels (correctness-preserving repair vs. proactive detection).
  • Merkle-tree construction cost is amortized by building it incrementally as blocks are written (Phase 3), not recomputed wholesale at first scrub — deferring tree-building to scrub time pays an unnecessary full-chunk read.

19.8 Edge Cases

  • A chunk under active write (open lease) should not be scrubbed mid-write — the scrub loop skips chunks in ChunkState::Open and revisits them next cycle.
  • A scrub that discovers a CRC-verified-good block whose Merkle leaf still disagrees (a merkle.bin write was lost, not the data) must self-heal by rebuilding the Merkle tree from verified-good data rather than treating it as data corruption.
  • A scrub cycle interrupted by a chunkserver restart must resume from a persisted last-scrubbed-offset, not restart the full 14-day cycle from zero.
  • Two replicas whose Merkle roots agree but whose CRC-verified block contents actually differ (an astronomically unlikely hash collision) must still be caught by the independent CRC check (I4) — the two integrity mechanisms are deliberately layered, not redundant.

19.9 Failure Analysis

  • If every replica of a chunk reports a different Merkle root and none can be established as authoritative, the scrub job halts on that chunk and raises an alert (feeds FM-6, §24) rather than picking an arbitrary "winner" — silent majority-vote reconciliation without human review risks discarding the one intact replica.

19.10 Operational Notes

  • Expose scrub_chunks_per_hour, merkle_diff_bytes_transferred, scrub_alerts_total.
  • Scrub progress (last-scrubbed timestamp per chunk) is queryable via dfs-admin for audit purposes.

20. Phase 8 — Snapshots, Quotas & Copy-on-Write

20.1 Objectives

Implement point-in-time, copy-on-write snapshots (I14) and directory quotas, the two operator-facing namespace features layered on the Phase-1 tree without touching chunk bytes at snapshot time (ADR-18).

20.2 Detailed Implementation Steps

  • Implement SnapshotManager (crates/dfs-master/src/snapshot.rs): a snapshot captures a shadow copy of the namespace subtree's inodes (not chunk bytes) and increments a reference count on every chunk the subtree references.
  • A chunk deletes only when its reference count reaches zero (I14) — the chunk-map's delete path (§13) is extended to check-then-decrement rather than unconditionally freeing.
  • Implement QuotaTracker: a directory quota (bytes and/or file count, Quota/QuotaUsage, §11) is checked at create and allocate_chunk time.
  • An operation that would exceed the quota fails atomically with QuotaExceeded before any chunk is allocated (P11: no partial application).

20.3 Deliverable

dfs admin snapshot create /path name produces a shadow copy in O(inode count), not O(data size); a subsequent delete of the live subtree does not free any chunk still referenced by the snapshot.

20.4 Acceptance Criteria

  • Snapshotting a 1M-inode directory completes in ≤ 30 s (§4-adjacent target, namespace-bound not data-bound).
  • A quota test caps a directory at 100 GB; a write that would exceed it fails atomically with QuotaExceeded, and no partial chunk allocation is observed (fixture namespace/quota_exceeded_atomic.json).

20.5 Conformance Fixtures

  • namespace/snapshot_then_delete_live.json — expected: snapshot's chunks remain readable after the live subtree is deleted (I14).
  • namespace/quota_exceeded_atomic.json — expected: zero chunks allocated on a rejected over-quota write.

20.6 Pitfalls

  • The transition from "delete frees the chunk" (pre-snapshot) to "delete decrements a refcount" (post-snapshot) is exactly the kind of change that reintroduces I1/I14 violations if the two code paths are not unified — there must be one delete path, always refcount-aware, not a snapshot-only special case.
  • A quota check performed against a cached usage total that is updated asynchronously (rather than checked-and-incremented atomically) allows a burst of concurrent writers to collectively exceed the quota before any single one observes the breach.
  • Nesting snapshots (a snapshot of a directory that already contains a snapshot) must be explicitly decided one way or the other — silently allowing it without considering refcount double-counting risks a chunk appearing referenced by more snapshots than actually exist.
  • Renaming a directory that has live snapshots must preserve the snapshot's ability to resolve its shadow inodes — a naive rename that only updates the live tree's path bookkeeping can orphan a snapshot's path-based lookups.

20.7 Performance Concerns

  • Snapshot creation must not pause the whole namespace tree — only the subtree being snapshotted needs its write lock held, and only for the shadow-copy duration (namespace-tree-size-bound, not chunk-count-bound, per §20.4's target).
  • Quota-usage accounting recomputed from scratch on every check (rather than maintained incrementally) turns an O(1) create into an O(subtree size) operation — maintain a running counter per quota-bearing directory instead.

20.8 Edge Cases

  • A snapshot of a directory that is concurrently being renamed must resolve to a consistent view (either fully-pre-rename or fully-post-rename, never a mix).
  • A quota check on a directory with an in-flight quota change (an admin lowering the limit mid-write) must use the quota value in effect at the start of the operation, not a value that changes mid-flight.
  • Deleting the last snapshot referencing a chunk while a scrub (Phase 7) is mid-verification of that same chunk must not free the chunk out from under the scrub — the refcount decrement and any in-flight read must be serialized against each other.
  • A quota expressed in file count (not bytes) must account for chunk-allocation failures correctly — a create that succeeds but whose first allocate_chunk then fails a different (byte) quota must not have already incremented the file-count quota.

20.9 Failure Analysis

  • A crash mid-snapshot-creation must not leave a partially-shadow-copied namespace subtree — the snapshot manager writes its shadow inodes through the same operation log (I7) as every other mutation, so crash recovery (Phase 2's replay) naturally rolls it back or completes it atomically.

20.10 Operational Notes

  • Expose snapshot_count, snapshot_chunk_refs_total, quota_violations_total.
  • dfs admin snapshot list /path and dfs admin quota show /path are the operator-facing read surfaces.

21. Phase 9 — Metadata Scaling: Sharded Namespace / Federation

21.1 Objectives

Address the single-Master RAM/throughput ceiling (§4, §30) before it is hit in production, via static namespace federation (ADR-17) — the mechanism P1's decoupling promise depends on remaining true past one Master's capacity.

21.2 Detailed Implementation Steps

  • Partition the namespace by a configured top-level-directory-to-Master mapping (static federation, the HDFS Federation precedent, Shvachko et al. §5, vs. Ceph's dynamic subtree partitioning or Tectonic's fully disaggregated metadata, both evaluated and deferred at ADR-17).
  • Give each federated Master a disjoint namespace subtree, its own operation log, and its own chunk/replica map for chunks under that subtree.
  • Have chunkservers register their chunk reports with whichever Master(s) own chunks they hold (a chunkserver may serve chunks for multiple federated Masters).
  • Implement client-side path resolution against a small, rarely-changing "mount table" (which top-level directory maps to which Master) before issuing the real RPC — this mount table, not a single Master, is now the one thing every client must agree on (documented explicitly as the new coordination point this phase introduces).
pub struct MountTable { pub routes: BTreeMap<String, MasterEndpoint> }  // top-level dir -> Master

21.3 Deliverable

A two-Master federated cluster where /tenant-a/* and /tenant-b/* are served by independent Masters, each independently durable (Phase 2) and independently HA (Phase 10), with client resolution transparently routing to the correct one.

21.4 Acceptance Criteria

  • Aggregate metadata throughput across N federated Masters scales linearly to at least N=4 (§4's per-Master 8,000 ops/s target × 4 ≈ 32,000 ops/s aggregate, measured, not asserted).
  • A test creates files under two federated subtrees concurrently and asserts zero cross-contamination of namespace state (each Master's tree contains only its own subtree's inodes).

21.5 Conformance Fixtures

  • namespace/federation_two_masters_isolated.json — expected: zero cross-Master namespace leakage.
  • namespace/federation_mount_table_routing.json — expected: every client resolution routes to the correct Master per the mount table.

21.6 Pitfalls

  • Federation does not solve cross-subtree operations (a rename from /tenant-a/x to /tenant-b/y) — this is explicitly out of scope for static federation and must fail with a typed CrossFederationRename error, not attempt a two-phase-commit-like partial rename that could violate I5 across two independent operation logs.
  • Federation is a scaling lever, not a consistency lever — do not let it become an implicit sharding-for-multi-tenancy security boundary without an explicit ADR revisiting ADR-11's deferred auth story.
  • Assigning federated subtrees purely by creation order (first-come, first-Master) rather than by measured load produces an unbalanced federation where one Master accumulates most of the namespace — subtree-to-Master assignment should be an explicit, revisitable operator decision.
  • A chunkserver that serves chunks for multiple federated Masters must heartbeat each independently — conflating them into one combined heartbeat stream reintroduces the single-hot-path problem federation exists to remove.

21.7 Performance Concerns

  • The mount table must be small and cacheable client-side (kilobytes, refreshed rarely) — if it grows proportional to file count instead of top-level-directory count, federation has reintroduced the single-hot-structure problem it was meant to solve.
  • Aggregate throughput scaling (§21.4's linearity claim) holds only while workload is roughly balanced across federated subtrees — a workload concentrated in one tenant's subtree still bottlenecks on that one Master, no matter how many others exist.

21.8 Edge Cases

  • A top-level directory not yet present in the mount table (a race between an admin adding a new federated subtree and a client's stale cached table) must fail with a retryable UnknownMount, not silently route to a default Master.
  • Decommissioning a federated Master requires migrating its subtree's namespace to another Master — an explicitly manual, operator-driven, out-of-band procedure (not automated in this phase; flagged as a Phase-10-adjacent operational gap).
  • Two federated Masters independently allocating ChunkIds from overlapping ranges (a configuration bug — each allocator is meant to be globally unique by construction, e.g. a Master-id prefix) would violate I6 across the federation; the prefix scheme must be validated at Master startup, not assumed.
  • A client mid-session when a subtree is reassigned to a different Master must have its in-flight RPCs fail cleanly with a re-routable error, not hang against a Master that no longer owns the path.

21.9 Failure Analysis

  • If a federated Master fails independently (not yet HA — Phase 10 covers that per-Master), only its subtree becomes unavailable; the rest of the namespace continues serving (P14: partition tolerance over global availability) — this blast-radius containment is the entire point of federation over a single larger Master.

21.10 Operational Notes

  • Expose federation_master_id as a label on every existing Phase-1–8 metric so per-Master dashboards compose the same way single-Master ones did.
  • docs/runbook/master-failover.md gains a federation-aware section (which subtree is affected).

22. Phase 10 — Master HA, Partition Recovery & Split-Brain Prevention

22.1 Objectives

Remove the single-Master (or single-federated-Master) point of failure via Raft-replicated consensus (ADR-07, ADR-19) over the operation log, with fencing to prevent split-brain during failover (P6, P9).

22.2 Detailed Implementation Steps

  • Run each Master (and, post-Phase-9, each federated Master independently) as a 3- or 5-node Raft group (Ongaro & Ousterhout, §5); every committed MasterWalOp (Phase 2's log entry type) is now a Raft log entry — Raft is the WAL, not a second log kept in lockstep (a single source of truth per §22.6).
  • Serve reads via the read-index protocol: the leader confirms its leadership (a round of heartbeats to a majority) before serving a read from local state, closing the "stale leader" gap a naive "read from whoever thinks it's leader" design leaves open (§2's mastery bullet, P9).
  • On failover, have the new leader re-issue every outstanding lease at a higher epoch (I10).
  • Fence the old leader (network-isolate or kill before the new leader acts) to prevent two Masters from both believing they hold write authority (split-brain, FM-1 in §24).

22.3 Deliverable

A 3-node Raft-replicated Master group that survives a kill -9 of the current leader, elects a new leader, and resumes serving both reads (read-index-verified) and writes within the RTO target.

22.4 Acceptance Criteria

  • Leader failure to new-leader-serving: ≤ 5 s (§4's RTO).
  • A test asserts zero committed-operation loss across ten consecutive forced failovers (I12).
  • A test asserts an in-flight writer whose lease was held against the old leader reconnects, receives a fresh lease at a higher epoch, and completes its write without re-applying an already-applied serial (§8.7's worked failure path, now under Raft).

22.5 Conformance Fixtures

  • ha/leader_kill_ten_cycles.json — expected: zero I12 violations across ten failovers.
  • ha/read_index_stale_leader_rejected.json — expected: a partitioned-minority node never serves a read-index-verified read.

22.6 Pitfalls

  • Running Raft's log and a separately-maintained WAL in lockstep is a two-log consistency bug waiting to happen — Raft's committed log is the operation log; there is exactly one log (a direct instance of P9).
  • A naive read-from-local-state implementation without the read-index round trip is wrong the instant a network partition creates a leader that does not yet know a new term has started elsewhere — this is not a rare edge case, it is the read path's correctness argument.
  • Fencing implemented as a "best-effort" kill signal (rather than a durable, verified isolation of the deposed leader) leaves a window where the old leader can still apply a write it believes is valid — fencing must be confirmed, not merely attempted, before the new leader proceeds.
  • Re-issuing every outstanding lease at a higher epoch on failover (§22.2) must actually reach every affected chunkserver before that chunkserver's local next_serial state is trusted again — a chunkserver that misses the epoch-bump notification could otherwise accept a write from a now-fenced old primary.

22.7 Performance Concerns

  • The read-index round trip (a leader-confirmation heartbeat) adds latency to strongly-consistent reads relative to Phase 5's cached, uncoordinated read path — reserve read-index reads for metadata operations that need it (e.g., a fresh open after a suspected federation/mount-table change), not every read.
  • Raft log replication to a geographically distant follower (if the 3/5-node group spans more than one rack) adds commit latency proportional to that follower's RTT — keeping the Raft group within one low-latency network segment (§4's intra-rack RTT assumption) is what makes the ≤5 s failover target (M10) achievable.

22.8 Edge Cases

  • A 3-node Raft group that loses two nodes simultaneously (no majority) must refuse writes cleanly (NoQuorum), never silently continue in a minority partition — this is the split-brain-prevention property, not a bug to work around.
  • A network partition that isolates the leader from a majority (but the leader does not yet know it) must be caught by the read-index heartbeat failing to reach a majority, causing the isolated leader to step down.
  • A follower that rejoins after a long partition with a far-stale log must catch up via log replication (or a snapshot install, §14, if the gap exceeds the retained log) before participating in quorum, never voting or serving reads from its stale state in the interim.
  • Two near-simultaneous leader elections (a split-vote scenario) must resolve to exactly one leader within a bounded number of retried election rounds — unrandomized election timeouts risk a livelock of repeated split votes.

22.9 Failure Analysis

  • Split-brain — two processes both believing they hold write authority for the same chunk or namespace subtree — is prevented structurally by Raft's single-leader-per-term guarantee plus explicit fencing of a deposed leader before the new one proceeds (FM-1, §24); this is the hard failure mode this phase exists to close, not a residual risk accepted after the fact.

22.10 Operational Notes

  • Expose raft_term, raft_committed_index, raft_leader_changes_total, read_index_latency_ms.
  • docs/runbook/master-failover.md is finalized with the fencing procedure and the ten-cycle chaos test as its validation reference.

23. Threat Model

The threat surface is dominated by Phase 0–9's deliberate deferral of transport encryption and authentication (ADR-11, §1); the mitigations below are therefore weighted toward network isolation and structural invariant-checking rather than cryptographic access control. Structural defenses the design itself already provides, independent of any added auth layer: monotonic lease epochs (I10) make replayed or reordered write RPCs self-rejecting; per-block CRC (I4) and Merkle scrubbing (§19) make silent data tampering detectable without a trust boundary around the storage medium; the single-writer-per-chunk lease (I3) makes two processes racing for write authority a structurally-checked condition, not merely a documented expectation; and Raft's fencing (§22) makes a stale leader's writes rejectable by construction rather than by convention.

25. Operational Readiness

Metrics. Every phase's telemetry (Phase N.10 sections) is exported via Prometheus (ADR-24); dashboards group by subsystem (Master namespace ops, lease/pipeline, heartbeat/re-replication, scrub, HA/Raft).

Tracing. OpenTelemetry spans wrap every Master RPC, every chunkserver write/read/append, and every replication fan-out hop, so a single slow write's latency is attributable to a specific pipeline stage (§16).

Structured logging. JSON lines to stdout from Phase 0 onward (§12.10); every log line carries chunk_id/file_id/lease_id where applicable for correlation with metrics and traces.

Dashboards. Per-subsystem Grafana boards: namespace throughput/latency (§13), WAL/checkpoint health (§14), chunk I/O and CRC (§15), lease/pipeline (§16), read-path/cache (§17), heartbeat/re-replication (§18), scrub (§19), snapshot/quota (§20), federation (§21), Raft/HA (§22).

Alerting philosophy. Alert on invariant-violation telemetry (§7's "detection"/"telemetry" columns) and on Failure Mode symptoms (§24), not on raw resource thresholds alone — a crc_mismatch_total increase pages; a momentary CPU spike does not.

SLOs. Metadata op p99 ≤ 5 ms (§4); Master availability 99.9% (§4, Phase 10); dead-chunkserver detection ≤ 30 s (§18.4); re-replication of a 100-chunk loss ≤ 5 min (§18.4).

Incident response. Named runbooks (below) are the first response artifact; each links its triggering alert to a decision tree ending in either automatic recovery confirmation or an escalation path. Severity is tiered: Sev-1 (data-loss risk or split-brain — FM-1, FM-3, FM-6) pages immediately, 24/7; Sev-2 (availability degraded but self-healing in progress — FM-5, FM-8, FM-10) pages during business hours, auto-escalates if unresolved past its SLA (§25's SLOs); Sev-3 (cosmetic/accounting drift — FM-11, FM-12) files a ticket, no page.

Named runbooks: docs/runbook/triage.md (general first-response), docs/runbook/under-replicated.md (FM-3/I11), docs/runbook/master-failover.md (FM-1, Phase 10), docs/runbook/decommission.md (T9-aware decommission procedure).

Backup/restore. The Master's periodic checkpoint (§14) plus WAL segments since it constitute the metadata backup; chunk data's "backup" is its replica set plus any snapshot holding it (I14) — there is no separate offline backup path in Phase 0–10 (flagged as a Phase-14-adjacent gap alongside multi-region replication, §36).

Deployment topology. One Master (or federated Master set, Phase 9) per logical namespace shard, 3–5 Raft peers per Master (Phase 10), N chunkservers one-per-disk across as many racks as the replication factor (I2) requires.

Canary / rolling-upgrade / rollback / migration. A chunkserver binary upgrade is rolled one host at a time, decommission-then-rejoin style (reusing T9's decommission safety check) so no under-replication window opens cluster-wide; a Master binary upgrade in Phase 10 is a standard Raft rolling restart (one follower at a time, then a deliberate leader step-down); any wire/on-disk schema bump follows the versioning policy of §26 before either upgrade path is attempted.

26. Compatibility & Versioning

Wire compatibility. Every protobuf message (§11) reserves field numbers permanently once shipped (P13); a breaking change ships as a new message variant behind a version field, never a field-number reuse.

Storage compatibility. meta.bin/crc.bin/merkle.bin (§8.2, §15, §19) each carry a version byte; a chunkserver reading a chunk written by a newer format either upgrades in place (additive fields) or refuses with a typed UnsupportedFormatVersion rather than silently misinterpreting bytes.

Schema evolution. New Inode/ChunkMeta fields are additive with documented defaults for old readers; field removal requires a two-release deprecation window (a field marked #[deprecated] for one release, removed the next).

API stability. MasterService/ChunkserverService/Placement (§11) are the stability boundary; a signature change is a major-version bump (SemVer) and requires an ADR.

Migration. A durability-mode change (replication → erasure coding, §36) migrates chunk-by-chunk as a background job (P8), never as an atomic whole-namespace flip.

Deprecation policy. A deprecated RPC or field remains functional for at least one minor release cycle with a logged warning before removal.

SemVer policy. MAJOR.MINOR.PATCH: MAJOR = wire/storage breaking change; MINOR = additive field/RPC; PATCH = bug fix, no schema change.

Rolling-upgrade guarantees. A cluster running a MINOR-version-mixed set of Master/chunkserver binaries operates correctly (older binaries ignore additive fields they don't understand); a MAJOR-version mix is unsupported and blocked at the handshake RPC (version negotiated at connection setup).

Federation version skew (Phase 9+). Different federated Masters may run different MINOR versions during a rolling upgrade; the mount table (§21.2) itself is versioned so a client can detect and tolerate skew across the Masters it talks to.

Raft version skew (Phase 10+). A Raft group's peers must agree on the MasterWalOp schema version before a log entry proposed by a newer peer is applied by an older one — the handshake RPC's version negotiation (above) extends to peer-to-peer Raft RPCs, not just client-facing ones.

27. Testing & Verification Strategy

Unit tests cover every pure function in dfs-core (path normalization, epoch comparison, placement determinism per P7).

Integration tests bring up a real multi-process cluster (docker-compose.yml, §10) and exercise the RPC surface end to end, per-phase (each phase's N.5 fixtures, §12–§22).

Property tests assert invariants (§7) hold across randomized operation sequences — e.g. a property test that any sequence of create/rename/delete never produces an orphan inode (I5).

Differential tests compare this Master's namespace-operation results against a reference in-memory-only implementation for the same operation sequence, catching subtle semantic drift.

Fuzzing targets RPC deserialization (dfs-proto) and the on-disk parsers (meta.bin/crc.bin/merkle.bin readers) for malformed-input robustness (§8.6).

Chaos tests (conformance/corpora/chaos/) drive the deterministic simulator (§7 methodology) through kill/partition/corrupt/delay schedules; every chaos fixture asserts specific invariants recover within their stated SLA (§18.4, §22.4).

Deterministic replay re-runs any captured WAL segment (§14) and asserts identical resulting state (I8) — the primary tool for diagnosing FM-4.

Soak tests run the three-node cluster under sustained mixed load (metadata + chunk I/O) for ≥72 hours, watching for slow leaks in FD counts, RAM, or lease/serial-number bookkeeping.

Fault injection at the RPC layer (dropped/delayed/reordered/duplicated messages) validates the malformed-input and stale-serial handling of §8.6/§16.8 without requiring an actual process kill.

Conformance (conformance/runner, §10) is the harness every phase's N.5 fixtures execute against, emitting conformance.report.json gated in CI.

Performance-regression gating. Every M-target in §29 is measured in CI on every release candidate; a regression beyond a configured tolerance blocks release (§28).

This strategy ties directly back to the System Invariants (§7) — every invariant has at least one property test, one chaos fixture, or one differential test asserting it — and to each phase's Conformance Fixtures (N.5), which are the concrete, named artifacts this strategy's abstract categories cash out to. 28. Build & Release Engineering

Reproducible builds. Pinned rust-toolchain.toml + committed Cargo.lock (ADR-23) ensure the same source produces bit-identical binaries across maintainer machines and CI.

Artifact signing. Release binaries and container images are signed (e.g. cosign); the signature is verified before any docker-compose.yml-driven deployment pulls a new image.

SBOM. A software bill of materials is generated per release, listing every dependency and its license (cross-checked against ADR-22's Apache-2.0 choice for license compatibility).

Release channels. stable (tagged releases only) and edge (every main commit that passes CI) — operators run stable by default.

CI/CD topology. ci.yml (build + unit + integration), conformance.yml (full fixture suite, §27), chaos.yml (nightly chaos schedule), security.yml (fuzzing + dependency audit), release.yml (tag-triggered build, sign, SBOM, publish).

Version stamping. Every binary embeds its git SHA and SemVer (§26) via a build-time env! constant, surfaced in dfs-cli version and in every RPC's negotiated-version handshake.

Provenance/attestation. CI publishes a build-provenance attestation (source commit → artifact hash) consumed by T11's mitigation.

Dependency auditing. cargo audit runs in security.yml on every commit; a new advisory affecting a workspace dependency blocks merge until triaged.

Release cadence. Minor releases every 4–6 weeks off main; patch releases as needed for Sev-1/Sev-2 fixes (§25); major releases only alongside a documented migration guide (§26).

29. Performance Engineering

Methodology.

  • Benchmarks (benchmarks/, §10) run in CI on every release candidate against fixed hardware profiles.
  • Profiling uses perf/flamegraphs for CPU-bound paths (CRC, Merkle-tree construction) and strace-based syscall counting for I/O-bound paths (chunk read/write).
  • Lock-contention analysis instruments every RwLock/Mutex acquisition in the Master (§13.7) with wait-time histograms.
  • Allocation profiling (heaptrack or equivalent) tracks per-RPC allocation counts on the chunkserver write/read paths (§15, §16) to catch regressions before they show up as GC-free-language "mystery latency."
  • Tail-latency analysis reports p50/p95/p99/p999 for every RPC, not averages alone (matches the format of every latency row in §4).

30. Scalability Analysis

Stays constant as the cluster grows: per-chunk metadata footprint (§11's ChunkMeta), per-RPC latency for a cache-hit read (P4), CRC computation cost per block.

Grows with cluster size: Master RAM (O(inode count) — I5, §33 C1), heartbeat fan-in at the Master (O(chunkserver count) — §33 C2), re-replication fabric load under correlated failure (O(failed chunkservers × chunks/chunkserver) — FM-10).

Named bottlenecks, in the order they bind:

  1. Master metadata-op throughput (§4's 8,000 ops/s single-instance ceiling) — the first ceiling hit as file-create rate grows (addressed by Phase 9 federation).
  2. Master RAM (§33 C1's ~65 GB for 50M inodes) — binds next as namespace size (not op rate) grows.
  3. Heartbeat fan-in (§33 C2's ~4,800-chunkserver ceiling under heartbeat-only membership, ADR-08) — binds as chunkserver count (not data volume) grows, motivating the deferred gossip alternative (§35).
  4. Re-replication fabric bandwidth under correlated failure (§33 C7) — binds as per-chunkserver capacity grows faster than fabric bandwidth.

Horizontal scaling: add chunkservers for capacity/throughput (linear up to bottleneck 3 above); add federated Masters for namespace scale (Phase 9, linear up to the mount-table coordination cost, MM7).

Vertical scaling: a single Master's ceiling is RAM and single-threaded lock contention (§13.7) — more CPU cores help less than expected past the point where the namespace RwLock is the bottleneck.

Sharding/partitioning: static federation (Phase 9, ADR-17) is this design's answer; Ceph's dynamic subtree partitioning and Tectonic's disaggregated metadata (§32) are the paths not taken, evaluated at §35.

Coordination overhead: grows with Raft group size (Phase 10, more peers = more heartbeat/commit round trips per operation) and with federation count (more Masters = a larger but still small mount table, MM7).

Practical ceiling and the levers beyond it: this design's practical ceiling, as built through Phase 10, is roughly the point where federation's mount-table coordination itself becomes a bottleneck (§21.7) — the lever beyond it is disaggregated metadata (§35's Alternative 2, Tectonic-style), deliberately out of scope per ADR-17's rationale.

Growth-rate summary:

Quantity Growth Governing §/formula
Master RAM O(inode count) §33 C1
Heartbeat processing O(chunkserver count) §33 C2
Re-replication fabric load O(failed chunkservers × chunks/chunkserver) §33 C7
Scrub I/O O(logical capacity) §33 C8
Federation aggregate throughput O(federated Master count), until mount-table coordination binds §21.4, §21.7
Raft commit latency O(peer RTT), not O(peer count) below ~5 peers §22.7

31. Mental Models & First Principles

  • MM1 — The Master is a cache of ground truth, not the truth itself.
    • Insight: the operation log is ground truth; in-RAM state is a materialized cache rebuilt by replay.
    • Predicts: any in-RAM-only optimization needs a WAL-replay equivalent.
    • Bug class without it: a field added to Inode in RAM but never logged vanishes on restart.
    • Applies at: §14 (Phase 2), I8.
  • MM2 — A lease is a clock, not a lock.
    • Insight: unlike a mutex, a lease's validity is time-bounded and must be renewed.
    • Predicts: every write path must check epoch/expiry, not just "did I get the lease once."
    • Bug class: a writer keeps writing after silent lease expiry, producing a split-brain-like double-writer scenario.
    • Applies at: §16 (Phase 4), I3, I10.
  • MM3 — The chunk is the file system's transaction boundary.
    • Insight: replication/repair/checksums are chunk-granular because that unit is small enough to move over a LAN quickly and large enough to amortize metadata overhead.
    • Predicts: any sub-chunk-atomicity feature fights the architecture.
    • Bug class: reinventing whole-chunk transfer badly by trying to repair "just the changed bytes" without the Merkle structure.
    • Applies at: §8.2, §19 (Phase 7).
  • MM4 — At-least-once is a promise about the log, not about your application.
    • Insight: record-append guarantees a record lands somewhere, once, per replica — not that your reader processes it once.
    • Predicts: any consumer without a dedup key double-processes under retry.
    • Bug class: double-counted downstream aggregates fed by an append log.
    • Applies at: §17 (Phase 5), P5, I9.
  • MM5 — Every failure detector is a bet between speed and false positives.
    • Insight: heartbeat interval and dead-threshold are a tuned tradeoff, not free parameters.
    • Predicts: tightening detection without handling flapping causes repair storms.
    • Bug class: an aggressive-detection "fix" that triggers ten spurious re-replication waves.
    • Applies at: §18 (Phase 6), §4.
  • MM6 — Determinism is what makes crash recovery a checkable property, not an act of faith.
    • Insight: WAL replay and placement are deterministic by design so recovery is testable (replay-twice-and-diff), not merely hoped for.
    • Predicts: any hidden nondeterministic step (wall-clock read, unordered-map iteration) breaks the replay-equality test.
    • Bug class: "recovery worked in staging, diverged in prod."
    • Applies at: I7, I8, §21.1.
  • MM7 — Federation trades one hot spot for a routing problem.
    • Insight: splitting the Master relocates coordination to whatever tells clients which Master to use.
    • Predicts: the mount table becomes the next thing that must stay available and consistent.
    • Bug class: assuming federation removed the single point of coordination instead of shrinking it.
    • Applies at: §21 (Phase 9).
  • MM8 — Consensus buys you exactly one property: everyone agrees on one order.
    • Insight: Raft exists solely to produce an agreed-upon operation sequence — it says nothing about data-plane latency/throughput, which is why data never runs through it here.
    • Predicts: routing bulk data through the consensus log collapses throughput to metadata-op speed.
    • Bug class: "replicate everything through Raft for simplicity" designs that can't explain their own throughput ceiling.
    • Applies at: P9, §22 (Phase 10).

GFS / Colossus. GFS's single-master design traded a hard scaling ceiling for radical 2003-era simplicity; Colossus, its internal successor, kept the chunk/replica shape but disaggregated metadata into a sharded, curator-driven service specifically to remove that ceiling. The regime where GFS's original simplicity still wins is this project's own scope: a single team's cluster where "one Master, understandable by one engineer" outweighs exabyte-scale metadata throughput.

HDFS. HDFS made the same core bet as GFS but optimized for operability inside the Hadoop ecosystem — Federation is a coarser-grained cousin of this blueprint's Phase 9, and QJM (rejected here at ADR-07) is the HA mechanism of choice where an org already runs ZooKeeper-based failover tooling. HDFS wins whenever interoperability with the existing Hadoop client ecosystem outweighs a from-scratch simplicity argument.

Ceph. Ceph rejected a centralized namenode entirely: CRUSH lets any client compute placement without asking anyone. Ceph wins in exactly the regime this project defers CRUSH to (§35, §36) — very large, rapidly-changing clusters where a central placement table's staleness or hot-path load is worse than upfront placement-function complexity.

JuiceFS. JuiceFS decouples metadata (any transactional KV store) from data (any object store), betting neither needs a purpose-built server. It wins when an organization already operates a durable KV store and S3-compatible storage and wants a POSIX layer cheaply, at the cost of an extra network hop and giving up the tight chunk/lease co-design this project uses to hit its p99 write-latency target (§4).

MooseFS. MooseFS keeps GFS's single-master, fixed-chunk shape almost unchanged but replaces a fixed replication factor with a per-directory "goal" (a configurable copy count and placement class), and its master runs a goal-driven chunk-loop scheduler closely analogous to this design's under-replicated queue (§18.2). It wins as the closest like-for-like reference implementation when validating this blueprint's own Phase 6 behavior against a real, operable GFS-lineage system — at the cost of the same single-master ceiling this design defers to Phase 9 federation.

33. Back-of-Envelope Capacity Model

  • C1 — Master RAM ceiling. 50,000,000 inodes × 1.3 KiB/inode = 65 GB (chained from §4's "Master namespace capacity" row).
    • Significance: this is the number that ultimately forces Phase 9 federation — RAM, not CPU or disk, is the first hard wall a single Master hits (§30 bottleneck 2).
  • C2 — Heartbeat-membership chunkserver ceiling. Reserve 20% of the §4 metadata-ops budget for heartbeat processing: (0.20 × 8,000 ops/s) × 3 s heartbeat interval = 4,800 chunkservers before heartbeat fan-in alone saturates that reserved budget (chained from §4's ops/s and heartbeat-interval rows; motivates ADR-08's gossip alternative past this point, §30 bottleneck 3).
    • Significance: this is the concrete trigger condition written into the Deferred Features Register (§36) for un-deferring gossip-based membership.
  • C3 — Chunk-RPC FD floor. 4,096 max concurrent chunk RPCs (§4) × 3 files/chunk (data.bin/meta.bin/crc.bin, §8.2) = 12,288 FDs minimum, before connection-socket FDs are added.
    • Significance: comfortably inside a default Linux ulimit -n of 1,048,576 — this is a sizing sanity-check, not a binding constraint at Phase-0–10 scale.
  • C4 — Aggregate write-bandwidth ceiling, 100-chunkserver cluster. 100 × 500 MB/s (§4 per-disk write target) = 50 GB/s cluster-wide write ceiling (data plane, independent of the Master per P1).
    • Significance: this is the number a capacity planner compares against expected ingest rate to size the cluster — it is never bounded by Master throughput (M11), by construction.
  • C5 — Aggregate read-bandwidth ceiling, 100-chunkserver cluster. 100 × 800 MB/s (§4 per-disk read target) = 80 GB/s.
    • Significance: the read/write asymmetry (80 vs. 50 GB/s) reflects the page-cache assist on reads (§15.2) that writes cannot benefit from equivalently.
  • C6 — Logical (post-replication) capacity. 100 chunkservers × 10 TB/disk = 1,000 TB raw; ÷ 3 (§4 replication factor) = 333 TB usable.
    • Significance: the 3× storage tax this number makes visible is exactly what erasure coding (deferred, ADR-04) would shrink to 1.5×, at the repair-bandwidth cost quantified in C7's method.
  • C7 — Re-replication time for one dead 10 TB chunkserver. §18.4's benchmark (100 lost chunks × 64 MiB = 6.4 GB repaired in ≤ 300 s) gives an effective worker-pool rate of 6.4 GB / 300 s ≈ 21.8 MB/s; scaling to 10 TB: 10,485,760 MB / 21.8 MB/s ≈ 481,000 s ≈ 5.6 days at that pool's baseline rate — the number that motivates operators to raise concurrency (§18.6) rather than accept it as-is.
    • Significance: this is the single starkest illustration in the whole document of why the per-source throttle (§4) must be tunable, not fixed.
  • C8 — Minimum sustained scrub throughput. C6's 333 TB logical capacity ÷ 14-day scrub cycle (§4): 333,000,000 MB / 1,209,600 s ≈ 275 MB/s aggregate minimum scrub rate cluster-wide.
    • Significance: at 275 MB/s against an 80 GB/s read ceiling (C5), scrubbing consumes well under 1% of read bandwidth headroom — justifying the §19.4 target of ≤10% client-latency impact.
  • C9 — Lease-renewal RPC load at 1,000 concurrent writers. 1,000 writers ÷ 20 s renewal interval (§4) = 50 renewal RPCs/s — well inside the single-Master 8,000 ops/s budget (C2's reservation logic leaves ample headroom).
    • Significance: lease renewal is never the reason a Master's ops budget is exhausted — namespace operations (creates/renames/lists) dominate that budget instead.
  • C10 — Worst-case quiesced-checkpoint pause. C1's 65 GB namespace ÷ an assumed 200 MB/s RAM-to-disk serialization rate = 65,000 MB / 200 MB/s ≈ 325 s (5.4 minutes) — the number ADR-10 accepts as the ceiling for the quiesced-checkpoint approach before copy-on-write checkpointing would need to be reconsidered.
    • Significance: 5.4 minutes of write-unavailability is inside most operators' tolerance for a rare, scheduled event but would fail an availability SLO if it happened on every checkpoint — checkpoint frequency (§4) is tuned to keep this rare.

35. Alternative Architectures (Roads Not Taken)

Alt 1 — CRUSH-based tableless placement (no central chunk-placement map).

client --hash(chunk_id, cluster_map)--> deterministic replica set
   (no placement RPC to Master; Master/MDS still resolves namespace only)

Regime: very large (1,000+ node), rapidly-changing clusters where a centrally-managed placement table's hot-path load or staleness dominates. Real system: Ceph. Rejected here because it adds placement-function complexity and a harder-to-debug locality story than this project's Phase 0–10 scope (tens to low-hundreds of nodes) needs — deferred, not dismissed (§36, ADR-02).

At this project's scale (§33 C2's ~4,800-chunkserver heartbeat ceiling), the centrally-managed map's simplicity dominates; CRUSH's cost (a harder-to-audit placement function, no single table an operator can just read) only pays for itself once the ceiling itself becomes the binding constraint.

Alt 2 — Fully disaggregated metadata (layered Name/File/Block services over an external KV store).

client -> Name layer -> File layer -> Block layer -> chunkservers
          (each layer independently sharded over a distributed KV store)

Regime: exabyte-scale, multi-tenant deployments. Real system: Meta/Facebook Tectonic. Rejected because it requires an external distributed KV-store dependency and a layered metadata service this project's from-scratch-mastery scope (§1) doesn't need — static federation (Phase 9) captures the scaling lesson at far lower engineering cost (ADR-17).

The tradeoff is engineering surface, not correctness: Tectonic's layering buys near-unlimited horizontal metadata scale at the cost of three services to build, deploy, and reason about instead of one — a cost this project's mastery goal (§2) explicitly declines to pay before the simpler federation lesson is learned.

Alt 3 — No dedicated chunkserver; direct client-to-object-store data plane with an external KV metadata store.

client -> [KV store: metadata] + [S3-compatible object store: data]
          (no chunkserver process; no lease/pipeline co-design)

Regime: organizations already operating a durable KV store and S3-compatible object storage that want a thin POSIX-ish layer on top. Real system: JuiceFS. Rejected because it gives up the co-designed chunk/lease write pipeline that hits this project's own p99 write-latency target (§4), and reintroduces exactly the "quietly depend on an opaque substrate" problem §2 argues against.

The extra network hop to an external object store (versus this design's direct chunkserver write pipeline, §16) is the concrete latency cost of this alternative — acceptable when the object store is already amortized across many other systems, unacceptable when this project's own p50/p99 write targets (§4) are the point.

Alt 4 — Peer-to-peer, masterless placement via distributed hash table, no metadata server at all.

client --DHT hash(path)--> responsible node set
   (no hierarchical namespace; flat keyspace)

Regime: flat object stores with no hierarchical-namespace requirement. Real system: GlusterFS (DHT translator). Rejected because this project's domain explicitly requires a POSIX-ish hierarchical namespace (§1) with rename/quota/snapshot semantics a pure DHT cannot express without bolting a namespace layer back on top — at which point it has reinvented a Master.

DHT placement wins precisely where this design's requirements (§1's snapshot/quota/rename semantics, §20) do not apply — a flat object-keyspace workload with no directory semantics gets simpler, more uniform load distribution than any of this design's rack-aware placement machinery (§21.1) needs to provide.

37. Glossary

Fifty-two terms, alphabetized by concept group (core identifiers first, then protocol/consistency terms, then operational and testing vocabulary); every term is used identically wherever it appears in §1–§39.

  • Master — the metadata server: namespace tree, chunk map, replica map, operation log, checkpoints; called NameNode in HDFS, MDS in Ceph.
  • Chunkserver — a host storing fixed-size chunks and serving direct read/write/append RPCs.
  • Chunk — the fixed-size (64/128 MiB) atomic unit of storage, replication, and repair.
  • Block — the 64 KiB checksum granularity within a chunk.
  • ChunkId — the 64-bit, never-reused cluster-scope chunk identifier.
  • FileId — the 64-bit, never-reused namespace-scope inode identifier.
  • Inode — the per-file/directory metadata record (mode, owner, timestamps, chunk list).
  • Namespace tree — the hierarchical FileId-keyed structure of directories and files.
  • Operation log (WAL) — the append-only, fsync-per-entry durability log every Master mutation passes through before being applied.
  • Checkpoint — a periodic full serialization of Master state used to bound WAL replay time.
  • Lease — a time-bounded grant of write authority for one chunk to one chunkserver (the primary).
  • Lease epoch — a monotonically increasing counter per chunk rejecting stale-authority writes.
  • Primary replica — the chunkserver currently holding a chunk's write lease.
  • Secondary replica — a non-primary member of a chunk's replica set.
  • ReplicaSet — the ordered set of chunkservers holding copies of a chunk.
  • Replication factor — the configured number of replicas per chunk (default 3).
  • Placement function — the deterministic function mapping (chunk_id, topology, durability) to a replica set.
  • Failure domain — a rack/zone/region boundary replicas must be spread across (I2).
  • Heartbeat — the periodic (3 s) chunkserver→Master liveness + chunk-report message.
  • Suspect state — a chunkserver status after 3 missed heartbeats.
  • Dead state — a chunkserver status after 10 missed heartbeats, triggering re-replication.
  • Under-replicated queue — the Master's priority queue of chunks below target replication factor.
  • Re-replication — the background process restoring a chunk's replica count.
  • Record-append — the atomic, at-least-once, one-chunk-bounded shared-log write RPC.
  • GFS-weak consistency — this design's default: last-writer-wins within a lease epoch, at-least-once append.
  • CRC32C — the per-block checksum algorithm (RFC 3720) detecting corruption.
  • Merkle tree — the per-chunk hash tree over 1 MiB pages enabling bandwidth-bounded anti-entropy diffs.
  • Anti-entropy — background reconciliation of divergent replicas via Merkle-tree comparison.
  • Scrubbing — the periodic full-cluster read-and-verify background job (§19).
  • Snapshot — a point-in-time, copy-on-write capture of a namespace subtree.
  • Copy-on-write — sharing underlying chunk bytes across a live subtree and its snapshot until one diverges.
  • Reference counting — the mechanism preventing chunk deletion while a snapshot still references it (I14).
  • Quota — a configured byte/file-count cap on a namespace subtree.
  • Federation — static, per-top-level-directory partitioning of the namespace across multiple Masters (Phase 9).
  • Mount table — the client-side map from top-level directory to owning federated Master.
  • Raft — the leader-election + log-replication consensus protocol used for Master HA (Phase 10).
  • Read-index — Raft's protocol for confirming leadership before serving a linearizable read.
  • Split-brain — two processes simultaneously believing they hold write authority for the same state (FM-1).
  • Fencing — forcibly preventing a deposed leader from acting before a new leader proceeds.
  • RTO — Recovery Time Objective, the target maximum outage duration.
  • RPO — Recovery Point Objective, the target maximum acceptable data/operation loss window.
  • Durability mode — the per-subtree choice between replication and (deferred) erasure coding.
  • Erasure coding — a parity-based durability scheme trading storage overhead for repair bandwidth (deferred, §36).
  • CRUSH — Ceph's deterministic, tableless placement algorithm (deferred alternative, §35).
  • FUSE — the Linux userspace file-system protocol (deferred client surface, §36).
  • Client chunk cache — the client-side cache of a file's chunk-list/replica-list, TTL-bounded.
  • Stale epoch — a rejected write whose lease epoch is lower than the chunk's current epoch (I10).
  • Pipeline write — the chained primary→secondary→secondary write-forwarding protocol (§8.4).
  • Serial number — the primary-assigned, per-chunk-monotonic ordering token for pipeline writes.
  • Conformance fixture — a named, versioned test case with expected input/output driving the harness (§27).
  • Chaos test — a fault-injection scenario asserting invariant recovery within an SLA.
  • Deterministic simulator — the single-process fault-injection harness used for invariant/replay verification (§7 methodology).
