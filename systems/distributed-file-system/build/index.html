⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the repository (§10), the workspace build, and a single-replica smoke path: create a file, write one chunk, read it back, with no replication, no WAL, no leases. Establish the invariant-testing harness (§7 methodology) skeleton so every later phase has somewhere to register its checks.

Deliverable

make compose-up brings up a one-Master, three-chunkserver cluster; dfs cat after a dfs-driven write returns the exact bytes written.

Acceptance
  • make test passes with tests/three_node_smoke.rs: create a 1-byte file, write it, read it back, assert byte-identity.
  • Repo matches §10's tree exactly (find crates -maxdepth 1 diff-clean against the layout).
  • ADR-01, ADR-02, ADR-03, ADR-12, ADR-22 recorded under docs/adr/.
Fixtures

conformance/corpora/namespace/create_one_file.json — expected: one inode, one chunk, byte-identical read. conformance/corpora/chunk-io/single_byte_roundtrip.json — expected: data.bin contains exactly the written byte.

Pitfalls
  • Chunkservers must register their externally-reachable address with the Master, not 127.0.0.1 — a bug here creates a cluster that writes but cannot read back; signal: dfs cat times out only from off-host clients.
  • Resist replicating in Phase 0 (P2, P3 land in Phase 3–4) — the smoke test is deliberately single-replica; a "just in case" second copy now creates an untested code path Phase 3 must later unwind.
  • Protobuf field numbers committed now are a wire-compatibility promise (P13) — get them right before Phase 1 extends the schema; a renumbered field later breaks every already-written chunk's meta.bin version negotiation.
  • docker-compose.yml's network aliasing must match what chunkservers self-report — a mismatch between the compose network name and the registered address is the single most common Phase-0 debugging session.

⬜ Phase 1 — Namespace Tree & Metadata Operations §13

Objectives

Implement the full namespace tree, chunk map, and replica map (§8.1) as in-RAM structures with real concurrency control, replacing Phase 0's single-lock stub with the production data structures the rest of the system depends on (P1).

Deliverable

A Master serving create/open/list/rename/delete/allocate_chunk/complete_chunk against the real namespace tree, still without a WAL (Phase 2 adds durability).

Acceptance
  • ≥ 5,000 metadata ops/sec sustained on a 100K-file namespace, single host (§4).
  • A test creates 100K files, lists every directory, renames half, deletes a third, and asserts namespace consistency (I5) at the end — fixture conformance/corpora/namespace/bulk_100k.json.
  • A chunk-allocation test allocates 10K chunks across 1K files and asserts the file→chunk index is exactly the identity permutation.
Fixtures
  • namespace/rename_deadlock_order.json — two renames that would deadlock under naive lock ordering; expected: both complete.
  • namespace/bulk_100k.json — expected: zero orphan inodes (I5) post-mutation.
Pitfalls
  • The namespace tree is the hottest structure in the Master; a single RwLock is correct at Phase 1 scale but throughput-limited — do not partition it prematurely (Phase 9 does this when §33's numbers justify it).
  • rename is the trickiest RPC: a half-applied rename (removed from source, not yet added to destination) is a permanent I5 violation; both directory locks must be held for the operation's duration.
  • Lock-ordering by raw FileId value (not insertion order) is required to avoid deadlock when two concurrent renames target each other's parent directories — an ad hoc "lock whichever I see first" ordering reintroduces the deadlock the fixed ordering was meant to prevent.
  • list results must be a consistent snapshot of the children map at one instant — iterating while another thread mutates it under a lock-discipline gap silently produces a corrupted listing rather than an error, making the bug hard to notice.

⬜ Phase 2 — Operation Log, Checkpoints & Crash Recovery §14

Objectives

Make the Phase-1 Master durable: every namespace/chunk-map/replica-map mutation is logged before being applied (I7), and the Master can restart and reconstruct exact prior state (I8).

Deliverable

A Master that survives kill -9 and reconstructs bit-identical namespace + chunk map + replica map on restart.

Acceptance
  • WAL append throughput ≥ 50,000 ops/sec on commodity NVMe (§4).
  • A test creates 10K files, kills the Master, restarts it, and asserts namespace bit-identity (fixture conformance/corpora/ha/crash_10k_files.json).
  • A test allocates 1K chunks, partially replicates some, kills the Master, restarts, and asserts each chunk lands in the correct ChunkState (Open for fully replicated, UnderReplicated otherwise).
Fixtures
  • ha/crash_10k_files.json — expected: identical namespace pre/post crash.
  • ha/replay_idempotent.json — replay the same WAL segment twice; expected: identical resulting state (I8).
Pitfalls
  • The WAL must be fsynced before acknowledgement — an O_DIRECT-without-fsync or async-writeback shortcut is a correctness bug (I7), not a performance tradeoff.
  • Monotonic counters (FileId, ChunkId allocators, I6) must have their allocated values recorded in the log entry, not re-derived at replay time, or replay diverges from the original run (violates I8).
  • A checkpoint that captures Namespace and ChunkMap at slightly different instants (two separate locks, not one) can produce a checkpoint where a chunk references a file the namespace half doesn't yet know about — the checkpoint must be taken under one consistent quiesce point covering all three structures.
  • Truncating the WAL before the corresponding checkpoint is confirmed durable (fsynced) on disk is a classic off-by-one that loses the very entries the checkpoint was supposed to have captured — truncate only after the checkpoint's own fsync returns.

⬜ Phase 3 — Chunkserver Storage, Block Checksums & Chunk Layout §15

Objectives

Turn the Phase-0 flat-file chunkserver stub into the production chunk store: fixed-layout chunks with per-block CRC32C (I4, ADR-13), ready for the replication pipeline Phase 4 adds.

Deliverable

A chunkserver serving write/read against the real on-disk layout, with CRC verified on every read.

Acceptance
  • ≥ 500 MB/s sustained write, ≥ 800 MB/s sustained read on a single NVMe disk (§4).
  • A test corrupts one 64 KiB block on disk and asserts the next read of that block returns BlockCorrupt, while reads of other blocks in the same chunk succeed (block-granular fault isolation, §8.2).
Fixtures
  • chunk-io/crc_mismatch_single_block.json — one block corrupted; expected: BlockCorrupt on that block only.
  • chunk-io/full_chunk_roundtrip.json — write 64 MiB, read back, byte-identical.
Pitfalls
  • crc.bin must be fsynced in the same durability window as data.bin — an asymmetric fsync order produces a chunk that reads fine until the next verification pass discovers CRC/data disagreement.
  • O_DIRECT on misaligned offsets is a common write-amplification trap; the posix_fadvise approach avoids it (§15.2).
  • A chunk-directory rename or atomic-swap trick borrowed naively from single-file atomic-write patterns does not extend cleanly to a three-file-per-chunk layout — all three files must move together with respect to any single logical mutation, which is why meta.bin records a confirmed-flushed offset rather than relying on directory-level atomicity.
  • Reusing a freed chunk's on-disk directory for a new ChunkId without fully clearing crc.bin/merkle.bin first leaves stale checksums that pass verification against stale data — I6's "never reuse a ChunkId" invariant exists partly to make this class of bug structurally impossible.

⬜ Phase 4 — Primary-Replica Lease & Write Pipeline §16

Objectives

Implement the GFS-style write pipeline (§8.4): lease-coordinated primary, chained replication, ordered application across replicas — the write-side realization of P3 and I3.

Deliverable

A three-replica write pipeline: a client write to a new chunk lands identical bytes at the same serial number on all three chunkservers.

Acceptance
  • 64 MiB chunk replicated to two secondaries in ≤ 100 ms over a 10 Gbps LAN (§4, matches the p50 write-latency row).
  • A test kills a secondary mid-write and asserts: the primary surfaces the error, the Master marks the chunk UnderReplicated, and re-replication is queued (feeds Phase 6's queue, I11).
Fixtures
  • replication/kill_secondary_mid_write.json — expected: primary error surfaced, chunk UnderReplicated.
  • replication/stale_epoch_write_rejected.json (I10) — a write at an old epoch; expected: StaleEpoch rejection, not silent application.
Pitfalls
  • A careless await ordering in the pipeline doubles tail latency — read GFS §3.1's data-flow/control-flow split twice (§5) before implementing.
  • The primary's serial number must be monotonic per chunk, not per chunkserver process; a failed-over primary inherits the serial cursor from meta.bin, not from zero (§8.7's worked failure path).
  • Acknowledging the client before every replica confirms (rather than waiting for the full set) silently downgrades the replication factor's durability guarantee without anyone noticing until a replica-loss incident reveals fewer confirmed copies than expected.
  • A lease renewal that races the lease's own expiry (the renewal RPC arrives one tick after the Master already revoked it) must be rejected cleanly by the Master, not accepted and then immediately contradicted by a concurrent Revoked transition.

⬜ Phase 5 — Read Path, Client Cache & Record-Append §17

Objectives

Implement the read path (P4: Master off the steady-state read path) and record-append (P5's second consistency regime, I9), the two remaining pieces of the GFS-style client surface.

Deliverable

A client that reads a 1 GiB file at ≥ 1 GB/s (network-limited) from a three-node cluster, and a record-append RPC usable by concurrent writers to one shared log chunk.

Acceptance
  • p50/p95/p99 read latency for a 4 KiB warm read: ≤ 0.4 ms / 1.5 ms / 6 ms (§4).
  • A test kills the chosen replica mid-read and asserts client failover completes the read.
  • A record-append test drives 1,000 parallel writers against one chunk and asserts every record appears at least once, at a consistent offset across every replica that applied it (I9).
Fixtures
  • chunk-io/read_failover_kill_replica.json — expected: read completes via a surviving replica.
  • chunk-io/record_append_1k_writers.json — expected: zero I9 offset-mismatch across replicas; every writer's record recoverable.
Pitfalls
  • The chunk cache's 60 s TTL (the GFS default, ADR-20) trades staleness for Master load — do not tune it down reflexively; measure Master RPC volume first.
  • Record-append's at-least-once nature (P5) must be documented for application authors, not just implemented — a record_id field is the standard dedup remedy and belongs in every append-log's schema.
  • Topology-aware replica selection that always prefers the "closest" replica can starve the other replicas of read traffic entirely, hiding a slowly-degrading disk on a rarely-read replica until a scrub (Phase 7) happens to touch it — occasional read-traffic sampling across all replicas surfaces this earlier.
  • A client that caches a chunk-list on a long-lived, idle connection can silently outlive the TTL's intended staleness bound if invalidation is triggered only by an active RPC error, not a background timer.

⬜ Phase 6 — Heartbeats, Failure Detection & Re-Replication §18

Objectives

Close the loop P6 promises: turn chunkserver loss into detected, queued, throttled re-replication (I1, I11), the mechanism every earlier phase's failure paths (§8.7, §16.9) depend on.

Deliverable

A cluster that detects a dead chunkserver within 30 s and restores 3-way replication for its chunks without operator intervention.

Acceptance
  • Dead-chunkserver detection ≤ 30 s (§4).
  • Re-replication of a 100-chunk dead chunkserver completes in ≤ 5 minutes on a 10 Gbps LAN (§4).
  • A chaos test kills a chunkserver and asserts: detection, queuing, completion, and post-repair placement-constraint compliance (I2) all hold — fixture chaos/kill_chunkserver_full_cycle.json.
Fixtures
  • chaos/kill_chunkserver_full_cycle.json — expected: I1 and I2 both hold within the 5-minute SLA.
  • replication/heartbeat_missed_transitions.json — expected: Live → Suspect → Dead transitions occur at exactly 9 s / 30 s.
Pitfalls
  • Aggressive heartbeat/dead-threshold tuning (e.g., 1 s/5 s) detects failures faster but generates spurious dead-detections under ordinary network jitter — keep the §4 defaults conservative; let operators override.
  • Re-replication traffic is a fabric-saturation risk: a 1 PB cluster at 30% utilization losing a 10%-of-capacity chunkserver generates a proportional wave of repair traffic; the per-source throttle (§4) is not optional tuning, it is a required safety valve.
  • Prioritizing the under-replicated queue purely by "fewest replicas remaining" without the secondary (file age, chunk size) tie-breakers can starve a large, old file's last chunk behind an endless stream of newly-created single-replica-loss chunks — the full three-key ordering (§18.2) exists to prevent this.
  • A re-replication destination chosen without checking existing disk utilization can create a new hotspot chunkserver — destination selection must weigh both placement compliance (I2) and current free capacity (feeds FM-5).

⬜ Phase 7 — Scrubbing, Anti-Entropy & Data Integrity §19

Objectives

Close the silent-corruption gap I4's read-time check alone leaves open (data corrupted between reads goes undetected until the next read touches it) with background scrubbing and Merkle-diff anti-entropy (ADR-09, ADR-14).

Deliverable

A scrub job that finds and repairs a single-page (1 MiB) divergence between two replicas of a 64 MiB chunk while transferring only that page, not the whole chunk.

Acceptance
  • A test intentionally diverges two replicas by one byte and asserts anti-entropy converges them within one scrub cycle, transferring ≤ 1 MiB (not 64 MiB) of repair bandwidth.
  • Full-cluster scrub throughput is throttled such that client I/O p99 latency (§4) degrades by ≤ 10% during a scrub pass.
Fixtures
  • chaos/single_page_divergence.json — expected: convergence within one scrub cycle, ≤ 1 MiB transferred.
  • chunk-io/scrub_throttle_client_impact.json — expected: client p99 read latency stays within 10% of baseline during active scrubbing.
Pitfalls
  • A naive Merkle-diff that transfers the whole tree at every level is O(N log N) in bytes; the streaming, divergence-only variant is O(K log N) where K is the divergence size (ADR-09) — implement the streaming form or the "bounded repair bandwidth" claim (§4, §19.4) is false.
  • The Merkle root must be updated atomically with chunk writes (merkle.bin alongside crc.bin, §15) — a torn write that updates data but not the tree looks like divergence to every future scrub pass and is a permanent false positive until manually reconciled.
  • Scrubbing a chunk concurrently being re-replicated (Phase 6) against a destination that hasn't finished its initial full copy can flag a false divergence against a legitimately-incomplete replica — the scrub loop must skip in-progress-repair destinations, not just chunks under an open write lease.
  • Comparing Merkle roots computed under two different page-size assumptions (e.g. after a configuration change) produces spurious full-tree divergence — the page size (1 MiB) is a fixed constant (§8.2), never a per-cluster tunable, specifically to avoid this.

⬜ Phase 8 — Snapshots, Quotas & Copy-on-Write §20

Objectives

Implement point-in-time, copy-on-write snapshots (I14) and directory quotas, the two operator-facing namespace features layered on the Phase-1 tree without touching chunk bytes at snapshot time (ADR-18).

Deliverable

dfs admin snapshot create /path name produces a shadow copy in O(inode count), not O(data size); a subsequent delete of the live subtree does not free any chunk still referenced by the snapshot.

Acceptance
  • Snapshotting a 1M-inode directory completes in ≤ 30 s (§4-adjacent target, namespace-bound not data-bound).
  • A quota test caps a directory at 100 GB; a write that would exceed it fails atomically with QuotaExceeded, and no partial chunk allocation is observed (fixture namespace/quota_exceeded_atomic.json).
Fixtures
  • namespace/snapshot_then_delete_live.json — expected: snapshot's chunks remain readable after the live subtree is deleted (I14).
  • namespace/quota_exceeded_atomic.json — expected: zero chunks allocated on a rejected over-quota write.
Pitfalls
  • The transition from "delete frees the chunk" (pre-snapshot) to "delete decrements a refcount" (post-snapshot) is exactly the kind of change that reintroduces I1/I14 violations if the two code paths are not unified — there must be one delete path, always refcount-aware, not a snapshot-only special case.
  • A quota check performed against a cached usage total that is updated asynchronously (rather than checked-and-incremented atomically) allows a burst of concurrent writers to collectively exceed the quota before any single one observes the breach.
  • Nesting snapshots (a snapshot of a directory that already contains a snapshot) must be explicitly decided one way or the other — silently allowing it without considering refcount double-counting risks a chunk appearing referenced by more snapshots than actually exist.
  • Renaming a directory that has live snapshots must preserve the snapshot's ability to resolve its shadow inodes — a naive rename that only updates the live tree's path bookkeeping can orphan a snapshot's path-based lookups.

⬜ Phase 9 — Metadata Scaling: Sharded Namespace / Federation §21

Objectives

Address the single-Master RAM/throughput ceiling (§4, §30) before it is hit in production, via static namespace federation (ADR-17) — the mechanism P1's decoupling promise depends on remaining true past one Master's capacity.

Deliverable

A two-Master federated cluster where /tenant-a/* and /tenant-b/* are served by independent Masters, each independently durable (Phase 2) and independently HA (Phase 10), with client resolution transparently routing to the correct one.

Acceptance
  • Aggregate metadata throughput across N federated Masters scales linearly to at least N=4 (§4's per-Master 8,000 ops/s target × 4 ≈ 32,000 ops/s aggregate, measured, not asserted).
  • A test creates files under two federated subtrees concurrently and asserts zero cross-contamination of namespace state (each Master's tree contains only its own subtree's inodes).
Fixtures
  • namespace/federation_two_masters_isolated.json — expected: zero cross-Master namespace leakage.
  • namespace/federation_mount_table_routing.json — expected: every client resolution routes to the correct Master per the mount table.
Pitfalls
  • Federation does not solve cross-subtree operations (a rename from /tenant-a/x to /tenant-b/y) — this is explicitly out of scope for static federation and must fail with a typed CrossFederationRename error, not attempt a two-phase-commit-like partial rename that could violate I5 across two independent operation logs.
  • Federation is a scaling lever, not a consistency lever — do not let it become an implicit sharding-for-multi-tenancy security boundary without an explicit ADR revisiting ADR-11's deferred auth story.
  • Assigning federated subtrees purely by creation order (first-come, first-Master) rather than by measured load produces an unbalanced federation where one Master accumulates most of the namespace — subtree-to-Master assignment should be an explicit, revisitable operator decision.
  • A chunkserver that serves chunks for multiple federated Masters must heartbeat each independently — conflating them into one combined heartbeat stream reintroduces the single-hot-path problem federation exists to remove.

⬜ Phase 10 — Master HA, Partition Recovery & Split-Brain Prevention §22

Objectives

Remove the single-Master (or single-federated-Master) point of failure via Raft-replicated consensus (ADR-07, ADR-19) over the operation log, with fencing to prevent split-brain during failover (P6, P9).

Deliverable

A 3-node Raft-replicated Master group that survives a kill -9 of the current leader, elects a new leader, and resumes serving both reads (read-index-verified) and writes within the RTO target.

Acceptance
  • Leader failure to new-leader-serving: ≤ 5 s (§4's RTO).
  • A test asserts zero committed-operation loss across ten consecutive forced failovers (I12).
  • A test asserts an in-flight writer whose lease was held against the old leader reconnects, receives a fresh lease at a higher epoch, and completes its write without re-applying an already-applied serial (§8.7's worked failure path, now under Raft).
Fixtures
  • ha/leader_kill_ten_cycles.json — expected: zero I12 violations across ten failovers.
  • ha/read_index_stale_leader_rejected.json — expected: a partitioned-minority node never serves a read-index-verified read.
Pitfalls
  • Running Raft's log and a separately-maintained WAL in lockstep is a two-log consistency bug waiting to happen — Raft's committed log is the operation log; there is exactly one log (a direct instance of P9).
  • A naive read-from-local-state implementation without the read-index round trip is wrong the instant a network partition creates a leader that does not yet know a new term has started elsewhere — this is not a rare edge case, it is the read path's correctness argument.
  • Fencing implemented as a "best-effort" kill signal (rather than a durable, verified isolation of the deposed leader) leaves a window where the old leader can still apply a write it believes is valid — fencing must be confirmed, not merely attempted, before the new leader proceeds.
  • Re-issuing every outstanding lease at a higher epoch on failover (§22.2) must actually reach every affected chunkserver before that chunkserver's local next_serial state is trusted again — a chunkserver that misses the epoch-bump notification could otherwise accept a write from a now-fenced old primary.
