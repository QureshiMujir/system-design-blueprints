3. Architectural Overview

                                   +----------------+
                                   |     Client     |
                                   |  (dfs-client)  |
                                   +--------+-------+
                                            |
                     metadata RPC (gRPC)    |    chunk I/O RPC (gRPC)
                     create/open/lease      |    read/write/append
                            +---------------+----------------+
                            |                                |
                     +------v------+                  +------v------+
                     |    MASTER   |  heartbeat (3s)  | CHUNKSERVER  |
                     | namespace   |<-----------------+  (primary,  |
                     | chunk map   |  chunk report    |  lease-held)|
                     | replica map |----------------->|  chunk store|
                     | lease mgr   |  lease grant/rev |  block CRC  |
                     | op log(WAL) |                  +------+------+
                     | checkpoints |                         |
                     +------+------+                  replication pipeline
                            |                          (primary->secondary)
                       Raft group                             |
                    (Phase 10, 3/5 nodes)             +--------+--------+
                            |                          |                 |
                     +------v------+           +-------v-----+   +-------v-----+
                     |   MASTER    |           | CHUNKSERVER |   | CHUNKSERVER |
                     | (standby)   |           |  (replica)  |   |  (replica)  |
                     +-------------+           +-------------+   +-------------+

Client (dfs-client). Owns two independent RPC relationships: metadata (Master) and data (chunkservers). Caches chunk-list/replica-list per open file (§8.5, Phase 5); never talks to a chunkserver it did not first resolve through the Master. Concurrency boundary: one client session, many in-flight chunk RPCs.

Master (leader). Sole writer of the namespace tree, chunk map, and replica map (I5, I6). Persistence boundary: every mutation is logged to the operation log before being applied and before any RPC acknowledgement (I7). Trust boundary: the Master is the only process a client's metadata RPC crosses into; chunkservers never see namespace paths, only ChunkIds.

Chunkserver (primary). Holds the write lease for a chunk (I3) for the lease window; serialises the write order for all replicas of that chunk; is otherwise a plain block store identical to a replica chunkserver. Concurrency boundary: one lease holder per chunk at a time.

Chunkserver (replica). Accepts writes only at the serial number the primary assigns; never originates a write order. Persistence boundary: data.bin/crc.bin/meta.bin are written and fsynced independently per chunk (§8.2).

Master (standby) / Raft group. Phase 0–9: absent (single Master, single point of failure, documented and accepted until Phase 10). Phase 10: a 3- or 5-node Raft group replicates every operation-log entry before it is considered committed (I12); standbys apply the same log and can be promoted on leader failure.

Every later section stays consistent with this diagram: the write path (§8.4) is the Client→Master→primary→secondaries chain; the read path (§8.5, Phase 5) is Client→Master (once, cached)→chunkserver (direct, repeated); the heartbeat/chunk-report arrows are the sole channel by which the Master learns chunkserver state (Phase 6).

Protocol boundary. Every arrow in the diagram is one gRPC/protobuf service (§9 ADR-12, §11); there is no shared-memory or filesystem-level channel between Master and chunkserver processes, even when co-located on the same host — this keeps the deployment topology (single-host dev cluster vs. multi-rack production cluster, §25) identical in code path, differing only in network latency.

Queueing. The under-replicated queue (Phase 6, §18.3) and the scrub schedule (Phase 7, §19.2) are the only persistent work queues in the system; the write pipeline and read path are synchronous request/response, never queued, which is why their latency (§4) is directly attributable to the RPC chain rather than to queueing delay.

8. Domain Model

8.1 Master state: namespace, chunk map, replica map

The Master holds three co-located structures, all covered by one operation log (§14, Phase 2): the namespace tree (FileId → Inode, directory → children map), the chunk map (FileId → ordered ChunkId list, ChunkId → ChunkMeta), and the replica map (ChunkserverId → chunk-set, the inverse index used for decommission and rebalance). All three are mutated only through the operation log's "log, then apply" sequence (I7).

8.2 Chunk and block model

A chunk is a fixed-size (64/128 MiB) unit identified by a 64-bit ChunkId, stored on a chunkserver as a small file group:

${CS_DATA_DIR}/<chunk_id>/
  data.bin     # chunk bytes, padded to chunk size
  meta.bin     # version, epoch, durability mode, primary/peers
  crc.bin      # CRC32C per 64 KiB block

Each chunk is divided into fixed 64 KiB blocks for checksum granularity (I4); a corrupt block invalidates only that block's read, not the whole chunk.

8.3 Namespace, replication, and the lease state machine

A chunk's lease cycles through four states:

State Entered when Exits when Held by
Unleased chunk allocated, no writer yet a client requests a write none
Leased Master grants lease to a replica lease expiry or explicit revoke one chunkserver (primary)
Expiring renewal window entered, no renewal received renewal arrives (→ Leased) or timer fires (→ Unleased) current primary
Revoked Master failover or explicit admin revoke a fresh lease is granted (→ Leased) none

This mirrors Frangipani's separation of a lock service from the data store (Thekkath et al., §5) — the Master plays the lock-service role for chunks without running a general distributed lock service.

8.4 The write pipeline (worked example)

Client writes 64 MiB to a new file /logs/service-a/2026-08-02.log:

  1. create(path) → Master allocates FileId, logs it (I7), returns.
  2. allocate_chunk(file) → Master picks a replica set via the placement function (P7, §21.1), e.g. {cs-04 (primary), cs-11, cs-19}, logs the allocation, returns (ChunkId, ReplicaSet, Lease).
  3. Client pushes data to the pipeline: cs-04 → cs-11 → cs-19 (chained forwarding, not client fan-out — halves client upload bandwidth cost).
  4. Client sends WriteChunk{chunk_id, epoch, offset, data, crc} to cs-04 (the primary).
  5. cs-04 assigns serial number S, applies locally, forwards (S, data) to cs-11 and cs-19.
  6. cs-11, cs-19 apply at serial S, acknowledge to cs-04.
  7. cs-04 acknowledges to the client once all replicas confirm (I3, I9 do not apply here — regular write, not append).
  8. Client calls complete_chunk(chunk_id, len, crc); Master transitions ChunkState::Open → Closed.

8.5 Consistency model

Write type Guarantee Bound
Regular write (§8.4) last-writer-wins within a lease epoch epoch-scoped; a stale-epoch write is rejected (I10)
Record-append (Phase 5) at-least-once, atomic at record granularity ≤ MAX_RECORD_SIZE (16 MiB), one chunk
Read (any replica) may observe a write not yet visible on every replica during pipeline propagation bounded by pipeline completion (§4 p99 write latency)
Read after complete_chunk read-your-writes for the writer's own session (client cache invalidation on close) immediate

8.6 Malformed-input example

A WriteChunk RPC arrives at a secondary replica with a serial number lower than the last-applied serial for that chunk (a duplicate or reordered delivery). The secondary must reject with StaleSerial, not silently re-apply — re-applying would violate I9 if the data payload differs due to a retried, mutated request. The primary treats StaleSerial from a secondary as a signal to re-sync that secondary via anti-entropy (§19, Phase 7) rather than retry the same write blindly.

8.7 Failure-path example: primary dies mid-write

cs-04 (primary, holding the lease for chunk C) crashes after step 5 above but before step 7 (secondaries applied serial S, client never got an ack). The client's write RPC times out; it re-resolves the chunk's replica-list from the Master, which detects cs-04's heartbeat absence (Phase 6), revokes the lease (Revoked state, §8.3), and — once the under-replicated queue restores 3-way replication (I1) — grants a fresh lease at a higher epoch (I10) to one of cs-11/cs-19. The client retries the write against the new primary; because serial S was already applied on cs-11/cs-19, the new primary's next_serial (recovered from meta.bin, not reset to zero — I6-analogue for serials) continues from S+1, and the retried write is logically a fresh append/write at the new serial, not a re-application of S.

8.8 Worked example: record-append with a padded retry (I9)

Two writers (W1, W2) append to a shared log chunk L concurrently, primary cs-07:

  1. W1 sends record_append(L, data=1 KiB); primary assigns serial 41, computes offset 6.29 MiB (the current end of the log), forwards (41, offset=6.29 MiB, data) to secondaries cs-13, cs-22.
  2. Concurrently, W2 sends record_append(L, data=2 KiB); primary serializes it after W1's request (single primary, I3), assigns serial 42, offset 6.291 MiB.
  3. cs-13 applies both successfully. cs-22 applies serial 41 but its disk write for serial 42 fails (a transient I/O error, not a crash).
  4. The primary detects cs-22's failed apply for serial 42 via the fan-out acknowledgement. Per §14.2's protocol, it pads cs-22's view at the offset serial 42 would have occupied (so cs-22's byte layout stays aligned with cs-13's for future records) and retries W2's record at a fresh offset (6.30 MiB) on every replica, including cs-13 (which already had it at 6.291 MiB).
  5. The result: cs-13 physically holds W2's record at two offsets (6.291 MiB, orphaned by the retry, and 6.30 MiB, the winning copy); cs-22 holds it only at 6.30 MiB. Every replica that successfully applied the record agrees it lives at offset 6.30 MiB (I9) — cs-13's earlier, orphaned copy is a duplicate the reader-side record_id (§17.6) is expected to deduplicate, the concrete instance of P5's at-least-once guarantee.
  6. The primary returns offset 6.30 MiB to W2 as the append's result; W1's record at 6.29 MiB is unaffected and uncontested throughout.

Design principles (§6)

  • P1 — Metadata is small and hot; data is large and cold-relative. - Rule: the Master answers from RAM; chunkservers move bytes the Master never touches. - Tradeoff: the Master's RAM ceiling caps namespace size (§4, §33). - Violation consequence: routing data through the Master makes metadata latency inherit data-plane jitter.
  • P2 — The chunk is the atomic unit. - Rule: replication, placement, repair, and rebalance all operate on whole chunks, never partial ones. - Tradeoff: internal fragmentation on small files. - Violation consequence: partial-chunk repair logic multiplies every failure-path's state space.
  • P3 — Writes are lease-coordinated, not consensus-coordinated. - Rule: a primary holds a time-bounded lease and serialises writes within it (I3). - Tradeoff: a lease-holder crash stalls writes to that chunk until expiry. - Violation consequence: routing every write through consensus makes write latency inherit consensus round-trip cost.
  • P4 — Clients cache metadata; the Master is off the steady-state read path. - Rule: a client resolves chunk-list/replica-list once per TTL window and reads directly thereafter. - Tradeoff: a small staleness window (§4, lease/TTL values). - Violation consequence: every read becomes a Master round trip, destroying P1.
  • P5 — Consistency is explicit and regime-scoped. - Rule: regular writes are last-writer-wins within a lease epoch; record-append is atomic, at-least-once, bounded to one chunk. - Tradeoff: applications needing exactly-once must dedupe by record id. - Violation consequence: promising exactly-once makes every crash-recovery path undecidable.
  • P6 — Failures are the common case. - Rule: every subsystem — heartbeat, lease, replica, Master — has an explicit detection and recovery story (§18, §22, §24). - Tradeoff: engineering cost up front. - Violation consequence: mean-time-to-detect becomes unbounded.
  • P7 — Placement is deterministic given the same inputs. - Rule: the same (chunk_id, topology, durability) always yields the same replica set (I2, §21.1). - Tradeoff: rebalancing on topology change is bounded but non-zero churn. - Violation consequence: two clients can disagree about where a chunk lives.
  • P8 — Durability mode is configurable per namespace subtree, transitions are asynchronous. - Rule: 3-way replication is the default; erasure coding is deferred (§36) but the Durability enum (§11) already accommodates it. - Tradeoff: per-subtree mode tracking adds bookkeeping the Master must persist and enforce. - Violation consequence: making mode changes synchronous means a large subtree conversion blocks writers.
  • P9 — The Master's state machine is replicated for HA; chunk data is never routed through consensus. - Rule: Raft covers Namespace + ChunkMap + ReplicaMap (Phase 10) only. - Tradeoff: chunk data durability relies on replication (I1), not consensus, so it inherits the lease model's weaker ordering guarantee. - Violation consequence: running data through Raft collapses write throughput to metadata-op throughput.
  • P10 — All wire and on-disk data carries integrity metadata independent of the medium. - Rule: per-block CRC32C on disk (I4); checksums on the wire are implied by TCP but not trusted alone (chunkservers re-verify on read). - Tradeoff: CRC computation cost on every write and read (§15.7). - Violation consequence: silent bit rot is invisible until a client notices corrupt bytes.
  • P11 — Every mutating operation is idempotent or made idempotent via a monotonic epoch/version. - Rule: lease epochs (I10), WAL replay (I8), chunk allocation counters (I6) all follow this. - Tradeoff: every mutation path must carry and check a version/epoch field, not just perform the mutation. - Violation consequence: crash-recovery replay can double-apply an operation.
  • P12 — Operational tooling is a first-class deliverable. - Rule: fsck, balancer, decommission ship with their own phase and acceptance criteria (§20, §25), not as an afterthought. - Tradeoff: engineering time spent on tools that don't move data-path benchmarks. - Violation consequence: the system is undebuggable in production regardless of its data-path correctness.
  • P13 — Wire and on-disk format compatibility is a versioned contract. - Rule: every protobuf message and on-disk record carries a version field; a schema change bumps it (§26). - Tradeoff: additive-only evolution discipline slows down schema iteration. - Violation consequence: a rolling upgrade corrupts state silently.
  • P14 — The data plane favors partition tolerance and availability over strict consistency. - Rule: a partitioned chunkserver keeps serving reads of what it has; the Master keeps serving metadata for chunks unaffected by the partition. - Tradeoff: readers may observe stale or partition-local state during a network split. - Violation consequence: blocking on every partition means a single rack outage halts the whole cluster.
