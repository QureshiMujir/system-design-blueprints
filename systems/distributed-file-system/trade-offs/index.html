ADR-01

Implementation language

Chosen

Rejected

Go, Java, C++

When the rejected choice is right

ADR-02

Metadata topology

Chosen

Rejected

When the rejected choice is right

35. Alternative Architectures (Roads Not Taken)

Alt 1 — CRUSH-based tableless placement (no central chunk-placement map).

client --hash(chunk_id, cluster_map)--> deterministic replica set
   (no placement RPC to Master; Master/MDS still resolves namespace only)

Regime: very large (1,000+ node), rapidly-changing clusters where a centrally-managed placement table's hot-path load or staleness dominates. Real system: Ceph. Rejected here because it adds placement-function complexity and a harder-to-debug locality story than this project's Phase 0–10 scope (tens to low-hundreds of nodes) needs — deferred, not dismissed (§36, ADR-02).

At this project's scale (§33 C2's ~4,800-chunkserver heartbeat ceiling), the centrally-managed map's simplicity dominates; CRUSH's cost (a harder-to-audit placement function, no single table an operator can just read) only pays for itself once the ceiling itself becomes the binding constraint.

Alt 2 — Fully disaggregated metadata (layered Name/File/Block services over an external KV store).

client -> Name layer -> File layer -> Block layer -> chunkservers
          (each layer independently sharded over a distributed KV store)

Regime: exabyte-scale, multi-tenant deployments. Real system: Meta/Facebook Tectonic. Rejected because it requires an external distributed KV-store dependency and a layered metadata service this project's from-scratch-mastery scope (§1) doesn't need — static federation (Phase 9) captures the scaling lesson at far lower engineering cost (ADR-17).

The tradeoff is engineering surface, not correctness: Tectonic's layering buys near-unlimited horizontal metadata scale at the cost of three services to build, deploy, and reason about instead of one — a cost this project's mastery goal (§2) explicitly declines to pay before the simpler federation lesson is learned.

Alt 3 — No dedicated chunkserver; direct client-to-object-store data plane with an external KV metadata store.

client -> [KV store: metadata] + [S3-compatible object store: data]
          (no chunkserver process; no lease/pipeline co-design)

Regime: organizations already operating a durable KV store and S3-compatible object storage that want a thin POSIX-ish layer on top. Real system: JuiceFS. Rejected because it gives up the co-designed chunk/lease write pipeline that hits this project's own p99 write-latency target (§4), and reintroduces exactly the "quietly depend on an opaque substrate" problem §2 argues against.

The extra network hop to an external object store (versus this design's direct chunkserver write pipeline, §16) is the concrete latency cost of this alternative — acceptable when the object store is already amortized across many other systems, unacceptable when this project's own p50/p99 write targets (§4) are the point.

Alt 4 — Peer-to-peer, masterless placement via distributed hash table, no metadata server at all.

client --DHT hash(path)--> responsible node set
   (no hierarchical namespace; flat keyspace)

Regime: flat object stores with no hierarchical-namespace requirement. Real system: GlusterFS (DHT translator). Rejected because this project's domain explicitly requires a POSIX-ish hierarchical namespace (§1) with rename/quota/snapshot semantics a pure DHT cannot express without bolting a namespace layer back on top — at which point it has reinvented a Master.

DHT placement wins precisely where this design's requirements (§1's snapshot/quota/rename semantics, §20) do not apply — a flat object-keyspace workload with no directory semantics gets simpler, more uniform load distribution than any of this design's rack-aware placement machinery (§21.1) needs to provide.
