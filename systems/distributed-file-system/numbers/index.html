The one defining property: the Master answers metadata questions in single-digit milliseconds off pure RAM state (I5, I6, I7) while chunkservers move hundreds of MB/s of data the Master never touches (P1) — the entire architecture exists to keep those two costs decoupled; every later phase that threatens this decoupling (e.g., a metadata operation that would require touching chunk bytes) is rejected at the ADR level (§9).

33. Back-of-Envelope Capacity Model

  • C1 — Master RAM ceiling. 50,000,000 inodes × 1.3 KiB/inode = 65 GB (chained from §4's "Master namespace capacity" row).
    • Significance: this is the number that ultimately forces Phase 9 federation — RAM, not CPU or disk, is the first hard wall a single Master hits (§30 bottleneck 2).
  • C2 — Heartbeat-membership chunkserver ceiling. Reserve 20% of the §4 metadata-ops budget for heartbeat processing: (0.20 × 8,000 ops/s) × 3 s heartbeat interval = 4,800 chunkservers before heartbeat fan-in alone saturates that reserved budget (chained from §4's ops/s and heartbeat-interval rows; motivates ADR-08's gossip alternative past this point, §30 bottleneck 3).
    • Significance: this is the concrete trigger condition written into the Deferred Features Register (§36) for un-deferring gossip-based membership.
  • C3 — Chunk-RPC FD floor. 4,096 max concurrent chunk RPCs (§4) × 3 files/chunk (data.bin/meta.bin/crc.bin, §8.2) = 12,288 FDs minimum, before connection-socket FDs are added.
    • Significance: comfortably inside a default Linux ulimit -n of 1,048,576 — this is a sizing sanity-check, not a binding constraint at Phase-0–10 scale.
  • C4 — Aggregate write-bandwidth ceiling, 100-chunkserver cluster. 100 × 500 MB/s (§4 per-disk write target) = 50 GB/s cluster-wide write ceiling (data plane, independent of the Master per P1).
    • Significance: this is the number a capacity planner compares against expected ingest rate to size the cluster — it is never bounded by Master throughput (M11), by construction.
  • C5 — Aggregate read-bandwidth ceiling, 100-chunkserver cluster. 100 × 800 MB/s (§4 per-disk read target) = 80 GB/s.
    • Significance: the read/write asymmetry (80 vs. 50 GB/s) reflects the page-cache assist on reads (§15.2) that writes cannot benefit from equivalently.
  • C6 — Logical (post-replication) capacity. 100 chunkservers × 10 TB/disk = 1,000 TB raw; ÷ 3 (§4 replication factor) = 333 TB usable.
    • Significance: the 3× storage tax this number makes visible is exactly what erasure coding (deferred, ADR-04) would shrink to 1.5×, at the repair-bandwidth cost quantified in C7's method.
  • C7 — Re-replication time for one dead 10 TB chunkserver. §18.4's benchmark (100 lost chunks × 64 MiB = 6.4 GB repaired in ≤ 300 s) gives an effective worker-pool rate of 6.4 GB / 300 s ≈ 21.8 MB/s; scaling to 10 TB: 10,485,760 MB / 21.8 MB/s ≈ 481,000 s ≈ 5.6 days at that pool's baseline rate — the number that motivates operators to raise concurrency (§18.6) rather than accept it as-is.
    • Significance: this is the single starkest illustration in the whole document of why the per-source throttle (§4) must be tunable, not fixed.
  • C8 — Minimum sustained scrub throughput. C6's 333 TB logical capacity ÷ 14-day scrub cycle (§4): 333,000,000 MB / 1,209,600 s ≈ 275 MB/s aggregate minimum scrub rate cluster-wide.
    • Significance: at 275 MB/s against an 80 GB/s read ceiling (C5), scrubbing consumes well under 1% of read bandwidth headroom — justifying the §19.4 target of ≤10% client-latency impact.
  • C9 — Lease-renewal RPC load at 1,000 concurrent writers. 1,000 writers ÷ 20 s renewal interval (§4) = 50 renewal RPCs/s — well inside the single-Master 8,000 ops/s budget (C2's reservation logic leaves ample headroom).
    • Significance: lease renewal is never the reason a Master's ops budget is exhausted — namespace operations (creates/renames/lists) dominate that budget instead.
  • C10 — Worst-case quiesced-checkpoint pause. C1's 65 GB namespace ÷ an assumed 200 MB/s RAM-to-disk serialization rate = 65,000 MB / 200 MB/s ≈ 325 s (5.4 minutes) — the number ADR-10 accepts as the ceiling for the quiesced-checkpoint approach before copy-on-write checkpointing would need to be reconsidered.
    • Significance: 5.4 minutes of write-unavailability is inside most operators' tolerance for a rare, scheduled event but would fail an availability SLO if it happened on every checkpoint — checkpoint frequency (§4) is tuned to keep this rare.
