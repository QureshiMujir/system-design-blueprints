Decisions (§9) · 30 ADRs

ADR-01

Language

Chosen

Rust (edition 2021, MSRV pinned)

Rejected

C, Go, C++

When the rejected choice is right

C wins when the deliverable must be an in-kernel module or a phc2sys-class tool linking the kernel PTP/PHC C API directly — the kernel is C, and native C removes the FFI shim and matches the existing linuxptp toolchain (the world ptp4l/phc2sys live in).

Why: No GC jitter (servo); safe hostile-packet parsing; precise syscall control; reject C (unsafe parse, CVE history), Go (GC pauses corrupt timestamps), C++ (manual safety)

ADR-02

Time-critical execution

Chosen

Single dedicated thread, no async, no alloc in loop

Rejected

tokio in hot loop

When the rejected choice is right

async hot loop wins when the target is a pure SNTP/NTP server with no local discipline (no servo to keep jitter-free, §8.2 mode 4 only) and tens of thousands of concurrent flows where an async reactor's connection scaling beats a hand-pinned thread.

Why: Determinism + bounded latency; async scheduling adds jitter to servo (P15 of §6)

ADR-03

I/O model

Chosen

tokio (or mio) on a SEPARATE I/O thread, lock-free SPSC channel to time thread

Rejected

I/O in time thread

When the rejected choice is right

I/O in the time thread wins for a single-source embedded SNTP client (libclocksync one-shot, §1) polling at minutes-scale: one socket, no servo-jitter budget, and the extra thread + channel are pure complexity.

Why: Isolate syscall/wakeup jitter from control loop; batch via recvmmsg (I4)

ADR-04

Wire timestamp repr

Chosen

NTP u64 32.32; PTP (u48,u32) fixed-point

Rejected

f64 on wire

When the rejected choice is right

f64 seconds win on the display/export surface (ntpx status JSON, §Operational Readiness): human-readable µs precision suffices there and exactness is not a wire-interop requirement, so float is the right representation for the operator-facing boundary even though it is wrong on the wire (I14).

Why: f64 loses precision at large seconds (>µs error); fixed-point is exact (I14)

ADR-05

Servo math repr

Chosen

f64 internal only

Rejected

fixed-point everywhere

When the rejected choice is right

fixed-point servo math wins when the discipline loop must itself be bit-reproducible across architectures for differential conformance (the determinism bar a sibling like #393 Congestion-Control imposes); f64 FMA/libm differences then break cross-arch trace equality.

Why: Float fine for gains/integrator; never serialized (I14)

ADR-06

RX timestamping

Chosen

kernel SO_TIMESTAMPING (SOFTWARE+RAW_HARDWARE), SW clock_gettime fallback

Rejected

userspace-only

When the rejected choice is right

userspace-only timestamping wins on platforms with no SO_TIMESTAMPING support (macOS, older/embedded kernels, containers without the socket option) where a post-recvmmsg clock_gettime is the only portable option and ms-class NTP accuracy is acceptable.

Why: Kernel stamp removes scheduler latency; HW behind PhaseDeferred §Phase 13 (I2)

ADR-07

NTP loop filter

Chosen

Hybrid PLL/FLL (Mills)

Rejected

pure PI, pure PLL

When the rejected choice is right

pure PI wins for high-rate PTP discipline (ADR-08): with Sync at 16–128/s the loop runs far below its time constant and a PI servo (linuxptp) converges faster and is simpler than the FLL machinery the long NTP poll needs.

Why: PLL good transient, FLL good steady-state long-poll; matches RFC 5905

ADR-08

PTP servo

Chosen

PI controller (linuxptp-style) + linreg option

Rejected

PLL

When the rejected choice is right

a PLL/FLL servo wins for very long PTP intervals or PDV-dominated WAN profiles (G.8275.2 over the public Internet) where averaging over many intervals (FLL behaviour) beats a fast PI that would amplify packet-delay-variation into the clock (P4 of §6).

Why: PTP high-rate Sync ⇒ PI converges fast; linreg for jittery profiles

ADR-09

Source selection

Chosen

Marzullo / intersection + clustering

Rejected

simple median, single source

When the rejected choice is right

single-source (no selection) wins for a PTP ordinary clock locked to one BMCA-elected grandmaster (§8.12), where there is exactly one timing source by protocol design and intersection over a one-element set is meaningless overhead.

Why: Byzantine tolerance (P3 of §6); median fails with ≥2 colluding liars near each other

ADR-10

Filter window

Chosen

8-sample shift register (NTP)

Rejected

larger window, Kalman

When the rejected choice is right

a regression / Kalman filter wins on highly jittery WAN paths (chrony's sourcestats.c linear regression, §5): regression over a longer history converges faster and estimates frequency directly where the 8-sample min-delay pick leaves accuracy on the table (Veitch et al., IMC 2004).

Why: RFC 5905 normative; bounded mem; min-delay heuristic proven

ADR-11

OS actuation

Chosen

clock_adjtime/ntp_adjtime (timex)

Rejected

manual settimeofday

When the rejected choice is right

settimeofday/step wins at first-boot cold start (-g) when the clock is wildly wrong (e.g. dead RTC battery, offset ≫ 1000 s) and a single hard set is the only sane action — slewing a 50-year error would take millennia at 500 ppm; this is exactly the bounded -g exception in §8.6.

Why: Kernel does the slewing; ADJ_FREQUENCY/ADJ_OFFSET/ADJ_SETOFFSET (I1)

ADR-12

Step vs slew policy

Chosen

slew < 125 ms, step 125 ms..1000 s, panic ≥ 1000 s

Rejected

always step / always slew

When the rejected choice is right

always-step wins for a stateless one-shot SNTP set-and-exit (ntpx query --set, §1): there is no running clock to keep monotonic and no servo, so a single immediate step is correct and slewing is pointless. always-slew wins for hosts that forbid any backward step (databases under strict MVCC) regardless of offset.

Why: Monotonicity (I1) vs convergence balance

ADR-13

Leap-second source

Chosen

IERS leap-seconds.list (NIST mirror) + LI bits; smear optional

Rejected

hardcoded, OS-only

When the rejected choice is right

OS-only (kernel STA_INS/STA_DEL) wins on an air-gapped host with no IERS feed and a trusted upstream NTP server already asserting LI bits — the kernel applies the leap from the upstream signal without a local table to maintain.

Why: Authoritative; smear preserves monotonicity (I8)

ADR-14

Test clock backend

Chosen

virtual_clock (oscillator model), no syscalls

Rejected

only integration tests

When the rejected choice is right

integration-only testing wins for the syscall-actuation layer itself (clock/sys_clock, Phase 5): the clock_adjtime/timex/STA_* mapping is exactly the part the virtual clock cannot exercise, so a real-kernel integration test is the only thing that catches a wrong ADJ_* flag.

Why: Deterministic, fast, reproducible servo tests (P15 of §6)

ADR-15

Security: auth

Chosen

NTS (RFC 8915, TLS 1.3 KE + AEAD) + symmetric AES-CMAC

Rejected

Autokey

When the rejected choice is right

symmetric-key (no NTS) wins for closed PTP/NTP fabrics with pre-shared keys and no PKI — datacenter or telecom links where a shared AES-CMAC key (RFC 5905 Appendix) is operationally simpler than running NTS-KE/TLS and certificate management. (The third rejected option, Autokey, is excluded outright as cryptographically broken — no regime, hence not locked.)

Why: Autokey broken/deprecated (reject outright); NTS modern, PFS (P7 of §6)

ADR-16

Abuse prevention

Chosen

Rate-limit + KoD RATE; no mode 7; response≤request

Rejected

open responder

When the rejected choice is right

an "open responder" (no rate-limit) wins only inside a trusted, isolated network segment (lab, single-tenant fabric) with no internet exposure, where the rate-limit table is pure overhead and reflection/amplification (CVE-2013-5211) is not in the threat model.

Why: Anti-amplification (P8 of §6); CVE-2013-5211 lesson

ADR-17

Packet parser

Chosen

hand-written bounded zero-copy parser

Rejected

nom/serde on wire

When the rejected choice is right

nom/declarative parser wins for the non-hot-path, non-adversarial config and NTS-KE record formats (§8) where parser-combinator clarity and maintainability beat hand-rolling, and the per-packet allocation/latency cost is irrelevant (KE happens rarely, §8.7).

Why: Full control over bounds; no alloc; constant-time MAC; fuzz-targeted (I15)

ADR-18

Async runtime crate

Chosen

tokio (I/O + timers only)

Rejected

async-std, smol

When the rejected choice is right

smol/mio wins for the embeddable libclocksync (§1) where pulling in the full tokio dependency tree is unacceptable for a small static library and a minimal reactor (or raw mio) covers the one or two sockets needed.

Why: Ecosystem, recvmmsg via socket2, mature

ADR-19

Logging

Rejected

When the rejected choice is right

the plain log facade wins for the embedded library build where structured spans and the tracing-subscriber machinery are overkill, and the host application just wants log records routed into its own logger.

Why: Spans for per-poll context; JSON export (§Operational Readiness)

ADR-20

Metrics

push/statsd (or OTLP) wins in environments without a Prometheus scraper — short-lived jobs or NAT'd/firewalled hosts the collector cannot reach, where the daemon must push metrics out rather than expose a /metrics endpoint to be pulled.

ADR-21

Sim/conformance

live testing wins for the final HW-timestamping/PHC integration (PhaseDeferred §Phase 13) that clknetsim cannot model — only real NIC hardware on a real LAN with a real grandmaster validates sub-µs PTP, where simulation has no fidelity.

Why: Deterministic offset/jitter; differential vs chrony/ntpd (P15 of §6)

Alternative Architectures

Fundamentally different ways to synchronize clocks for the same goal. Each: ASCII sketch, the regime where it wins, the real system that embodies it, why this blueprint rejected it.

A1 — Hardware-reference time (GPS/atomic clock per node, no network sync loop). Each node (or each datacenter) carries a GPS receiver and/or atomic clock; the "sync" is local disciplining to a physical reference, and the network carries only an authenticated bound, not the time itself.

   [GPS antenna]──┐        [GPS antenna]──┐
                  ▼                        ▼
   ┌── node A: local atomic/GPS ──┐  ┌── node B: local atomic/GPS ──┐
   │  disciplines its own clock   │  │  disciplines its own clock   │
   └──────────────┬───────────────┘  └──────────────┬──────────────┘
                  └──── exchange only [earliest,latest] bounds ──────┘
  • Wins: when sub-µs absolute accuracy with a tight, trustworthy uncertainty bound is required fleet-wide and the operator can afford GPS/atomic hardware in every datacenter — network PDV and path asymmetry (MM4) are removed from the accuracy path entirely.
  • Real system: Google TrueTime / Spanner (Corbett et al., OSDI 2012) puts GPS + atomic clocks in every datacenter and exposes TT.now()→[earliest,latest]; Amazon's Time Sync Service / ClockBound is a comparable bounded-interval offering.
  • Rejected because: this blueprint's scope is explicitly software sync over commodity networks with no special hardware (§1 non-goals: "NOT a GPS/PPS reference-clock driver", "NOT a full Stratum-1 appliance"). ntpx builds the same uncertainty accounting (I2, MM1) but obtains time over the network; GPS/PPS refclock is PhaseDeferred §Phase 12.

A2 — Physical-layer / in-network synchronization (sync rides the link, not packets). Time is distributed at the physical or switch layer — every switch is timing-aware and corrects residence time in hardware, or the clock is recovered from the link's bit stream — so accuracy is bounded by hardware, not packet-delay variation.

   GM ──PHY sync──▶ [switch: HW timestamp + correctionField] ──PHY──▶ [switch] ──▶ slave
        (every hop is timing-aware; residence time removed in hardware)
  • Wins: when sub-nanosecond accuracy is required and the entire path can be specialized hardware — particle-physics timing, telecom 5G fronthaul, power-grid synchrophasors — where even kernel timestamping's µs floor (C1) is far too coarse.
  • Real system: White Rabbit (CERN) achieves sub-ns over Ethernet by combining PTP with Synchronous Ethernet and phase measurement; PTP transparent clocks (IEEE 1588) and DTP (Lee et al., SIGCOMM 2016, physical-layer sync) embody the in-network approach.
  • Rejected because: it requires timing-aware hardware on every hop — out of scope for a commodity-network daemon (§1 non-goals: "NOT a hardware NIC PHC driver", transparent clock PhaseDeferred). ntpx targets the SW/kernel-timestamp regime (ADR-06) and treats the HW/PHY floor as the documented ceiling (§Scalability Analysis).

A3 — Probe-flooding statistical estimation (many coded probes + regression/ML, not a filter pipeline). Instead of an 8-sample filter and Marzullo, blanket the network with a high rate of timestamped probes and recover offset/skew with regression or a learned model that exploits correlations across many probes and paths.

   sender ──▶▶▶▶▶▶ (burst of coded probe packets) ▶▶▶▶▶▶──▶ receiver
                       │  regression / SVM over the whole probe cloud │
                       ▼                                              ▼
                  estimate offset+skew jointly, reject PDV statistically
  • Wins: at datacenter scale with fine-grained sync requirements and spare bandwidth — exploiting the law of large numbers over thousands of probes drives the offset estimate below what a small min-delay filter achieves on a jittery path.
  • Real system: Huygens (Geng et al., NSDI 2018) uses coded probes + SVM to reach tens-of-ns sync in software; chrony's linear-regression estimator (sourcestats.c) is the lightweight, deployed cousin of the same statistical idea.
  • Rejected because: it trades bandwidth and a heavier estimator for accuracy this blueprint obtains more simply, and the probe flood is unfriendly to the WAN/general-Internet regime ntpx must serve (P8 of §6 anti-abuse). The regression variant is captured as ADR-10's regime-bounded alternative; the full probe-cloud approach is a different system class (Sundial/Huygens, §5 Papers).
