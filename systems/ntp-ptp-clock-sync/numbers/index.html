Performance Engineering

  • Timestamp capture latency: budget < 10 µs SW, < 1 µs kernel (M1); measure RX cmsg→sample. Pin RX thread; isolate NIC IRQs (irqaffinity); consider busy-poll (SO_BUSY_POLL) for PTP.
  • Syscall overhead: clock_adjtime ~1 µs, once/loop (not per packet), inside the < 50 µs sample-to-actuation budget (M9); recvmmsg/sendmmsg batch to amortize; count syscalls/sec.
  • Jitter minimization (servo): pin time-critical thread to an isolated core (isolcpus/cset); no allocation in hot loop (preallocated arenas); no locks (SPSC channel, seqlock for now()); no GC (Rust); avoid syscalls between sample and correction.
  • Allocation: zero per-packet heap; fixed [Option<NtpAssoc>;MAX_ASSOC], response template reuse, bounded ForeignMaster vec.
  • Cache locality: assoc arena contiguous; hot fields packed; avoid pointer chasing in filter/select.
  • Branch prediction: sanity checks ordered common-case-first; parse is straight-line.
  • Tail latency: histogram of capture→correction; p99 < 50 µs (M9); flamegraph (perf/cargo-flamegraph) on hot path.
  • Server throughput: stateless response path; target 10k req/s/core (M6); criterion + load test (scripts); measure response_bytes_total.
  • Profiling methodology: perf record for CPU, perf c2c for false sharing, heaptrack/dhat to confirm no hot-path alloc, criterion for micro, offset/jitter histograms for end-to-end.
  • Memory profiling: confirm < 16 MB RSS (M7); track arena sizes; no leak (ASAN/valgrind in CI).
  • Client CPU budget: ≤ 1% of one core at 8 sources, poll 64 s (M5); PTP servo load bounded by logSyncInterval (M10) × per-update cost (M9) — see Capacity Model C12.

Back-of-Envelope Capacity Model

Numbers an expert computes from §4 (System Constraints) before designing. Each is derived step-by-step; the §4 input is named and the formula shown.

  • C1 — Offset error from timestamp-capture jitter. Input: §4 "Timestamp capture jitter < 10 µs SW, < 1 µs kernel" (M1). Capture jitter enters θ as ±jitter/2 per timestamp on both T2 and T4. With SW capture at 10 µs: θ_error ≈ jitter ≈ 10 µs, dominating the < 1 ms LAN budget by 100×-headroom but setting the floor — you cannot beat ~10 µs with SW stamps, the exact reason kernel (1 µs) and HW (ns, deferred) stamping exist. Confirms §4's tiered accuracy targets.
  • C2 — Asymmetry-induced offset bias. Input: §4 WAN RTT < 250 ms + MM4. A path-delay asymmetry of Δ_asym injects a constant bias = Δ_asym / 2. For a satellite/asymmetric WAN with 10 ms forward/reverse difference: bias = 10 ms / 2 = 5 ms — undetectable from timestamps, and exactly the §4 "WAN < 10 ms" target's limiting term. This is why PTP targets engineered-symmetric LANs (C1 floor) and NTP WAN accuracy is ms-class.
  • C3 — Servo slew-out time for a sub-step offset. Input: §4 "Frequency tolerance ±500 ppm" (M2) + "Step threshold 125 ms" (M3). Slewing at the 500 ppm cap, draining offset o: t = o / 500e-6. For the maximum slew-eligible offset (just under 125 ms): t = 0.125 / 5e-4 = 250 s to slew out. Confirms §8.6's "125 ms takes ≥ 250 s to slew" and bounds how slow convergence can be before a step is justified.
  • C4 — Holdover error growth rate. Input: §4 "Holdover drift budget < 1 ppm" (M4) + I2/MM10. Error grows at the residual frequency error: error(t) = freq_err × t. At 1 ppm residual: 1e-6 × t → 3.6 ms after 1 h, 86 ms after 1 day, 2.6 s after 30 days. This is the curve holdover/controller must report honestly (P9 of §6); it tells an operator a 1-day holdover blows a 1 ms SLO ~24× over and a 100 µs PTP SLO ~36× over.
  • C5 — Client steady-state CPU / packet rate. Input: §4 "CPU < 1% of one core, 8 sources, poll 64 s" (M5). At poll 64 s, 8 sources: 8 / 64 = 0.125 packets/s RX+TX. Per-packet work (parse + filter + maybe select/combine) at, say, ≤ 10 µs: 0.125 × 2 × 10 µs ≈ 2.5 µs/s of CPU = ~0.00025% — three orders under the 1% ceiling, confirming the client is I/O-trivial and the budget exists for crypto (NTS AEAD, §8).
  • C6 — Server throughput vs per-request cost. Input: §4 "scale to 10k req/s/core" (M6). Budget per request = 1 s / 10,000 = 100 µs/core. A stateless mode-4 response (precomputed template, echo origin, stamp T2/T3, sendmmsg) is ~1–5 µs of CPU, so 100 µs leaves the path I/O-bound, not CPU-bound — confirming §Scalability's "bottleneck = packet I/O" and that recvmmsg/sendmmsg batching (ADR-03) is the lever, matching Meta's stateless ptp4u model.
  • C7 — Daemon memory at max associations. Input: §4 "Memory < 16 MB RSS" (M7) "; ≥ 64 NTP assoc; ≥ 16 PTP foreign masters" (M8) + §11.3. Per NtpAssoc ≈ filter (8 × FilterSample ~48 B = 384 B) + state ~128 B ≈ 512 B. 64 × 512 B = 32 KiB for all associations; 16 × sizeof(ForeignMaster) adds a few KiB. Association state is < 0.5% of the 16 MB ceiling — the budget is dominated by buffers/runtime, confirming the fixed arena (§11.3) is cheap and "no per-packet heap alloc" is the real constraint, not arena size.
  • C8 — RX socket buffer for a server burst. Input: §4 "10k req/s/core" (M6) + a worst-case scheduling gap. If the time/IO thread is delayed g = 10 ms, inbound packets buffer: 10,000 req/s × 0.010 s × ~90 B/packet ≈ 9 KB. A default 212 KB SO_RCVBUF absorbs ~23× that, so a 10 ms stall costs zero dropped requests — but a 250 ms stall (225 KB) would overflow it, quantifying why the IO thread must not block (ADR-02/03) and why recvmmsg drains in batches.
  • C9 — NTP era lifetime and rollover horizon. Input: §4 "NTP timestamp resolution: 64-bit 32.32 since 1900-01-01" (32-bit seconds field) + §8.3 "seconds field wraps every 2^32 s". 2^32 s = 4,294,967,296 s ÷ 31,556,952 s/yr ≈ 136.1 years. Era 0 (from 1900) ends 1900 + 136 = 2036 (precisely 2036-02-07). With the explicit era: i8 (§11.1), range = 256 × 136 ≈ 34,800 years of representable eras — confirming I6's "> 8 billion years" claim is actually bounded by the i8 era count, and that 2036 is the first real rollover an implementation must test (Phase 0/7).
  • C10 — Leap-smear frequency offset. Input: §4 "Frequency tolerance ±500 ppm" (M2, the ceiling this must respect) + §8.15 "spread −1 s over a window" + I1. Smearing 1 s over a window W: freq_offset = 1 s / W. Over a ±1000 s (≈ 33 min total) window: 1 / 2000 = 500e-6 = 500 ppm — at the §4 frequency-tolerance ceiling (M2). Over Google's documented ~24 h smear: 1 / 86400 ≈ 11.6 ppm, comfortably small. This derives §8.15's "~11.6 ppm" figure and shows why a narrow smear window is dangerous (hits the M2 clamp) while a day-long one is gentle.
  • C11 — Filter staleness horizon (MAXDISP). Input: §4 "Poll interval (NTP) 2^4..2^17 s" (bounds how fast a fresh sample re-arrives) + §8.5 "discard if ε > MAXDISP 16 s" + §8.4 "φ = 15 ppm" dispersion growth. A sample's dispersion reaches MAXDISP after t = MAXDISP / φ = 16 / 15e-6 ≈ 1.07e6 s ≈ 12.3 days. So a single sample is theoretically usable for ~12 days of source outage before age alone disqualifies it — but C4's holdover error (86 ms/day at 1 ppm) makes it useless for accuracy long before that, confirming holdover, not stale filter samples, is the real outage mechanism.
  • C12 — PTP Sync-rate servo load. Input: §4 "logSyncInterval −7..+4 (1/128 s .. 16 s)" (M10) + §4 "Servo update latency < 50 µs" (M9). At the fastest rate (128 Sync/s): 128 × 50 µs = 6.4 ms/s of servo CPU = 0.64% of one core for the discipline path alone, plus message handling. Confirms a single time thread sustains max PTP rate on one core (§Scalability) with headroom, and that sharding ports across threads is only needed at many high-rate ports (deferred).
