Decisions (§9) · 24 ADRs

ADR-01

Language split

Chosen

Python (quantize/calibrate/eval) + Rust/CUDA (runtime), joined only by the Q-file

Rejected

PyO3 binding Rust into one process

When the rejected choice is right

A single-binary research prototype with no production runtime requirement, where iteration speed dominates

Why: GIL serializes inference; heavier deployment artifact; harder build matrix

ADR-02

Phase-0 scheme

Chosen

Per-tensor symmetric INT8, weight-only

Rejected

Per-channel INT8 from day one

When the rejected choice is right

A model whose per-tensor weight distribution is already known-uniform (rare) and per-channel adds only overhead

Why: Per-tensor is the smallest correct surface to validate the whole pipeline before adding granularity

ADR-03

INT4 group size

Chosen

128 default, 32/64/256 supported

Rejected

Per-channel INT4 only

When the rejected choice is right

k=32 wins when accuracy is paramount and storage is not (e.g. archival, not deployment)

Why: Per-channel INT4 loses too much accuracy; k=32 has excess scale overhead (3.5 bits/weight); 128 matches llama.cpp Q4_K

ADR-04

Symmetry policy

Chosen

Symmetric weights (INT8), asymmetric INT4

Rejected

Asymmetric everywhere

When the rejected choice is right

Asymmetric weights win when a layer's weight distribution is measurably skewed (rare, detectable via calibration stats)

Why: Trained weights are near-zero-mean; symmetric costs nothing there; INT4's narrow range needs the recovered headroom

ADR-05

INT4 packing

Chosen

Two values/byte, little-endian nibble

Rejected

Big-endian nibble

When the rejected choice is right

Big-endian nibble wins only inside a closed system with zero gguf interop requirement

Why: Matches gguf Q4_0/Q4_K exactly, preserving llama.cpp interop

ADR-06

NF4 grid

Chosen

QLoRA's 16-level quantile grid, verbatim

Rejected

A custom-fit grid per model

When the rejected choice is right

A custom grid wins for a single very-large, very-scrutinized deployment where 0.05 extra perplexity justifies bespoke tuning

Why: Verbatim grid is reproducible and cross-tool comparable; a custom grid would need re-derivation and re-validation per model

ADR-07

Accumulator dtype

Chosen

fp32 in every quantized matmul

Rejected

INT32 (TensorRT's INT8 default)

When the rejected choice is right

INT32 wins in a narrowly bounded short-sequence, single-scale deployment where the overflow bound is provably unreachable

Why: INT32 overflows at the sequence lengths and per-channel scales this system targets

ADR-08

Q-file format

Chosen

gguf-compatible with a TLV metadata extension

Rejected

A bespoke binary format

When the rejected choice is right

A bespoke format wins when no interop is needed and the extra 15% storage efficiency from a non-gguf layout matters

Why: llama.cpp ecosystem compatibility is worth the layout constraints

ADR-09

Default INT4 PTQ method

Chosen

GPTQ

Rejected

AWQ as the default

When the rejected choice is right

AWQ wins when calibration wall-clock matters more than the last 0.1–0.3 perplexity (no Cholesky, ~2× faster)

Why: GPTQ is more thoroughly studied and is the literature's baseline comparator

ADR-10

Default W8A8 outlier handling

Chosen

SmoothQuant

Rejected

LLM.int8() decomposition as default

When the rejected choice is right

LLM.int8() wins when the architecture has non-foldable layers (no preceding LayerNorm/Linear) preventing the SmoothQuant fold

Why: Zero runtime overhead once folded; LLM.int8() carries a permanent fp16 side-path cost

ADR-11

LLM.int8() availability

Chosen

Ships as an explicit alternative, not default

Rejected

Removing it entirely

When the rejected choice is right

Removing it wins only if every supported architecture is fold-compatible (not true for all transformer variants)

Why: Needed exactly where SmoothQuant's fold is impossible

ADR-12

Calibration corpus

Chosen

128 sequences × 2048 tokens, C4 validation, seed 42

Rejected

32 sequences (faster) / 512 sequences (more accurate)

When the rejected choice is right

32 sequences wins for rapid iteration during method development, not for a shipped accuracy number

Why: 128 is the GPTQ paper's choice and the point the accuracy curve flattens

ADR-13

Simulation numeric mode

Chosen

fp32 with explicit round-to-nearest-even hooks

Rejected

Bit-exact fixed-point simulation

When the rejected choice is right

Fixed-point simulation wins when validating a new kernel's bit-exactness before trusting the fp32 approximation

Why: Fast enough (P1) and matches kernel output at the precision the kernel emits

ADR-14

CUDA kernel language

Chosen

CUDA C++ with CUTLASS templates

Rejected

Triton

When the rejected choice is right

Triton wins for rapid kernel prototyping before the layout is locked (ships as an alternative backend, deferred)

Why: CUTLASS gives fine-grained Tensor Core layout control needed for W4A16 packing

ADR-15

Runtime concurrency model

Chosen

std::thread pool + mpsc dispatch, no async runtime

Rejected

tokio

When the rejected choice is right

tokio wins if the runtime later serves many concurrent streaming requests per process (not this system's Phase-0–9 scope)

Why: Request/response, not streaming; tokio's scheduler overhead is unjustified for this workload

ADR-16

License

Chosen

Apache-2.0 for the toolchain

Rejected

A permissive-with-field-of-use license

When the rejected choice is right

A field-of-use license wins if a hosted calibration service (deferred, §1) needs commercial protection

Why: Maximizes ecosystem adoption and interop with bitsandbytes/llama.cpp licensing

ADR-17

Determinism

Chosen

Bit-for-bit reproducible Q-files for identical inputs

Rejected

Best-effort determinism

When the rejected choice is right

Best-effort wins only in an exploratory research loop where reproducibility is not yet required

Why: Accuracy comparisons across runs are meaningless without it (P9, I9)

ADR-18

Eval harness compute target

Chosen

CPU-only fp32 simulation

Rejected

GPU-accelerated eval

When the rejected choice is right

GPU eval wins when evaluating at a scale (70B+, full MMLU) where CPU wall-clock is prohibitive — still cross-checked against CPU on a sample

Why: Reproducible across machines without depending on specific GPU/driver/cuBLAS versions

ADR-19

FP8 formats

Chosen

E4M3 (weights/activations), E5M2 (gradients)

Rejected

E4M3-only everywhere

When the rejected choice is right

E4M3-only wins for pure PTQ inference with no gradient path (Phase 0–7, 9 inference-only paths)

Why: E5M2's wider exponent range is needed for QAT gradient dynamic range

ADR-20

QAT method

Chosen

Learned Step-Size Quantization (LSQ)

Rejected

Plain straight-through estimator (STE)

When the rejected choice is right

Plain STE wins for the fastest possible QAT prototype before committing to LSQ's extra scale-gradient bookkeeping

Why: LSQ outperforms STE on every literature benchmark at comparable implementation cost

ADR-21

GPTQ Hessian computation

Chosen

Column-wise, Cholesky-cached inverse

Rejected

Naive per-column Hessian recomputation

When the rejected choice is right

Naive recomputation wins only on toy models (< 10M params) where O(N³) is still fast in absolute terms

Why: Cholesky-cached is O(N²) amortized per layer vs O(N³) naive — non-negotiable at 7B+ scale

ADR-22

AWQ scaling search

Chosen

Fixed 20-value grid search (α ∈ [0,1], step 0.05)

Rejected

Learned α via gradient descent

When the rejected choice is right

Learned α wins when the accuracy budget is exceeded by the grid search's best point and extra calibration time is available

Why: Grid search is deterministic (I9) and cheap; learned α gives marginal accuracy gain at real calibration-time cost

ADR-23

Q-file metadata extension

Chosen

A single forward-compatible TLV block

Rejected

Multiple ad hoc key-value entries

When the rejected choice is right

Multiple ad hoc keys win only inside a closed system with no requirement to stay gguf-parseable by unmodified readers

Why: Readers that don't understand the TLV skip it cleanly, preserving gguf compatibility (P5)

ADR-24

Mixed-precision assignment

Chosen

Per-layer QSchema override table (§11.5)

Rejected

A single global scheme for the whole model

When the rejected choice is right

A single global scheme wins for the fastest possible Phase-0 smoke test where per-layer tuning is not yet justified

Why: Layers differ enormously in accuracy sensitivity (embeddings, lm_head vs bulk attention/MLP)

34. Alternative Architectures (Roads Not Taken)

Alt 1 — Fully dynamic (runtime-computed) quantization, no offline PTQ/QAT step.

input batch --> [compute scale per-batch, on the fly] --> INT8 matmul --> output
                        (no Q-file, no calibration corpus)

Regime where it wins: rapidly-changing weights (online/continual learning) or no representative calibration corpus exists at all. Real system: PyTorch's torch.quantization.quantize_dynamic, which computes activation scales per forward call. Rejected because per-batch scale computation adds real-time overhead incompatible with the < 5 ms kernel-launch budget (M3) and forfeits calibration reproducibility (P9) entirely — there is no Q-file to record provenance in.

Alt 2 — Sparse + ultra-low-bit hybrid (extract salient weights to an fp16 sparse side- tensor, quantize the rest at 2–3 bits).

weight --> [split: salient (sparse, fp16)] --> add
       \-> [bulk (dense, 2-3 bit)]        --/

Regime where it wins: extreme compression targets (< 3.5 bits/weight average) where a small sparse side-channel absorbs the highest-sensitivity weights. Real system: SpQR (Dettmers et al. 2023) and SqueezeLLM (Kim et al. 2023). Rejected as the Phase-4 default because sparse- tensor GEMM kernels are a separate, less mature kernel-engineering problem than the dense INT4 GEMM this system's ADR-14/CUTLASS investment assumes, and the accuracy gain over GPTQ/AWQ at this system's 4-bit target (§4) is marginal — documented as a deferred first-class scheme (PhaseDeferred("§15"), Deferred Features Register).

Alt 3 — Neural-architecture co-design (train the model to be quantization-native from scratch, e.g. ternary weights).

pretrain(architecture co-designed for {-1,0,+1} weights) --> ternary model, no PTQ/QAT needed

Regime where it wins: greenfield pretraining where architecture and numerics are co-designed from step zero, reaching 1–2 bit weights with no retrofit. Real system: BitNet (ternary-weight transformers) and the earlier Binarized Neural Networks line (Courbariaux et al.). Rejected outright — this system is explicitly a post-hoc toolchain for existing fp16/bf16 checkpoints (§1 scope); co-design requires owning the pretraining loop, abandoning the entire existing library of checkpoints this project targets.
