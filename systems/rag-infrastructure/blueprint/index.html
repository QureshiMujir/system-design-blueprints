251 — Retrieval-Augmented Generation (RAG) Infrastructure from Scratch

Project Number: 251

Project Name: Retrieval-Augmented Generation (RAG) Infrastructure from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition: a Retrieval-Augmented Generation infrastructure platform is a distributed system that ingests heterogeneous documents into canonical form, segments and embeds them deterministically, persists vectors and metadata under crash-safe durability guarantees, serves hybrid lexical + semantic retrieval under bounded latency, reranks and assembles context under a token budget, and dispatches the assembled prompt to an inference provider while recording a replayable trace of every decision. The system is not a wrapper around a hosted vector database — storage, indexing, ranking, scheduling, and observability are implemented and owned directly, so that every correctness and performance property is verifiable rather than assumed.

1.1 Phase 0 Deliverable — Crates and Services

Phase 0 stands up the following crates/services (workspace member per row); later phases add implementation depth to each, they do not add new top-level services beyond §1.6:

  1. api-gateway — TLS termination, auth, tenant quota admission.
  2. ingest-gateway — multipart/streaming upload intake, manifest persistence.
  3. document-normalizer — MIME detection, OCR fan-out, canonicalization.
  4. chunk-engine — tokenizer-aware semantic segmentation.
  5. embedding-orchestrator — batched embedding provider fan-out.
  6. vector-storage-engine — WAL, mmap segments, snapshots, tombstones.
  7. metadata-plane — PostgreSQL-backed tenant/collection/lineage catalog.
  8. retrieval-api — query lifecycle, planning, deadline enforcement.
  9. lexical-index-engine — inverted index, BM25, postings compression.
  10. rerank-service — cross-encoder reranking abstraction.
  11. context-assembler — dedup, token budgeting, citation lineage.
  12. inference-gateway — LLM provider abstraction, streaming.
  13. scheduler-runtime — cooperative async job scheduling, leases.
  14. observability — metrics/tracing/log bootstrap shared by all crates.
  15. replay-engine — deterministic trace capture and replay CLI.
  16. evaluation-runner — offline ranking/latency regression harness.
  17. admin-control-plane — RBAC, tenant lifecycle, operator APIs.
  18. tenant-isolation — quota enforcement, cache/shard partitioning.
  19. compaction-engine — segment and vector-store compaction scheduling.
  20. snapshot-manager — snapshot creation, shipping, restore tooling.
  21. auth — token verification, API-key management shared library.
  22. config — typed config loading, validation shared library.
  23. trace-context — correlation-ID propagation shared library.
  24. protocols — Protobuf schema crate (wire contracts).
  25. test-fixtures — golden fixtures and property-test generators.

1.2 System Boundaries

Provides: ingestion canonicalization, chunking, embedding orchestration, vector + lexical storage, hybrid retrieval, reranking, context assembly, inference dispatch, replay/evaluation, multi-tenant operational isolation.

Delegates: embedding and completion model execution (external providers, §3.13); TLS certificate issuance (cert-manager); container orchestration (Kubernetes); object storage durability (S3/MinIO); transactional storage engine internals below the SQL boundary (PostgreSQL).

Does NOT provide: foundation model training, GPU kernel authoring, custom transformer runtimes, internet-scale web crawling, distributed SQL consensus, petabyte-scale sharding beyond §29's ceiling, online reinforcement learning, multi-region active-active replication, general workflow orchestration (Airflow-class), or a custom LLM serving runtime — see Non-Goals below and §35.

1.3 Non-Goals (Phase 0)

Training foundation models; GPU kernel development; custom transformer implementations; internet-scale crawling; distributed consensus databases; petabyte-scale indexing; online reinforcement learning; multi-region active-active replication; multimodal retrieval beyond metadata placeholders; vector compression research; generalized workflow orchestration; custom LLM serving runtimes. Five of these recur as deferred (not abandoned) features — see §35.

1.4 Deployment Model

Production: Kubernetes on Linux/AMD64, containerized OCI images, object-storage-backed ingestion, SSD-backed vector nodes, PostgreSQL metadata plane, gRPC internal RPC, HTTP/JSON external API, OpenTelemetry export. Development: docker-compose single-node topology with local object-store emulation (MinIO) and an embedded (in-process, mmap) ANN index mode requiring no external services.

1.5 Target Operators

Operators (deployment, index lifecycle, scaling, incident response, backup/restore, migration); Application Developers (retrieval workflows, embedding selection, prompt templates, evaluation); Platform Engineers (tenancy isolation, auth, quotas, storage lifecycle, SLOs); ML Engineers (embedding/reranker experimentation, retrieval quality analysis). Each role owns a disjoint set of runbooks in §24.

1.6 What Later Phases Unlock

Distributed shard routing beyond a single collection; cross-cluster federation; retrieval personalization; adaptive reranking; retrieval result caching; embedding migration orchestration; online canary retrieval evaluation; semantic agent-memory retrieval; streaming (token-incremental) retrieval. None of these are Phase 0 scope; each requires the correctness kernel (§1.1 items 6–8, 13) to be load-bearing first.

1.7 Recommended Language

Rust, chosen for: deterministic memory management without GC pause tail-latency risk (binds directly to the p99 < 450 ms target in §4); an ownership model that makes the WAL/mmap invariants in §7 checkable at compile time; a mature async ecosystem (Tokio, ADR-02) suited to the 20,000-connection concurrency budget in §4; and first-class fuzzing/property-testing tooling (cargo-fuzz, proptest, ADR-12/ADR-13) needed for the parser and WAL-decoder attack surface in §22.

Rejected: Go — simpler concurrency model but GC pauses violate the p99 ANN-search budget under sustained allocation pressure from graph traversal (§28); Java/JVM — same GC-pause risk, plus heavier per-connection memory overhead against the 20k-connection budget; C++ — comparable performance ceiling but no ownership-checked concurrency, raising the cost of the WAL/mmap invariants in §7 to a discipline problem instead of a compiler-enforced one. Secondary languages: Python (experimentation harnesses, offline evaluation notebooks), SQL (metadata-plane migrations), Bash (operational scripts), TypeScript (admin control-plane UI).

1.8 Prerequisites

Distributed systems fundamentals; indexing and information-retrieval theory (inverted indexes, BM25); approximate nearest-neighbor algorithms (graph and quantization families); async runtimes; Linux systems programming (mmap, fsync, io_uring-class syscalls); NUMA behavior; concurrency control (optimistic locking, lease-based coordination); WAL design and compaction strategy; RPC protocol design (gRPC/Protobuf); OpenTelemetry semantics; tokenizer internals; vector math (cosine/dot-product distance); cache locality; scheduling theory; memory allocators; structured logging; SLO engineering.

1.9 Estimated Timeline

Phase 0 (repository foundation + correctness kernel): 10–14 weeks, 3–6 engineers. Full production system (all ten phases, §12–§21, to operational-readiness bar in §24): 9–18 months with multiple subsystem owners — the WAL/ANN storage boundary and the metadata plane each warrant a dedicated owner past month 4.

2. Why Build This

2.1 Systems Knowledge Developed

Retrieval system architecture; vector index design and operational behavior; hybrid ranking system design; retrieval consistency semantics between the vector and metadata planes; ingestion determinism; replayable distributed workflows; retrieval-debugging methodology; context-window optimization; embedding lifecycle management; storage/index synchronization; distributed observability under multi-tenant load.

Unlike an API-wrapper RAG prototype (a chat loop calling a hosted vector DB and a hosted completion API), this project forces reasoning about: correctness boundaries between derived and authoritative state (§6, P12); operational scaling under quota pressure (§29); retrieval degradation modes under partial failure (§23); vector/metadata consistency under crash recovery (§7, I2); replay diagnostics for silent ranking regressions (§21); compaction safety under concurrent readers (§18, FM rows); schema evolution across rolling upgrades (§25).

2.2 Historical and Practical Importance

RAG systems function as the retrieval substrate for AI copilots, enterprise search, internal reasoning systems, long-term agent memory, and AI observability platforms. Production AI systems degrade more often from retrieval-quality regressions (stale embeddings, silent tokenizer drift, metadata/vector divergence) than from raw model-capability limits — a failure class this blueprint treats as first-class (§21, §23) rather than as an afterthought. Retrieval infrastructure engineering is therefore a foundational, not peripheral, skill for AI platform work.

2.3 Engineering Muscles Developed

Storage-engine design (append-only WAL, mmap segments, compaction); indexing structures (inverted index, HNSW graph); distributed scheduling (lease-based job queues); memory-layout optimization (cache-line-aware graph traversal, §28); operational debugging (deterministic replay, flamegraphs); observability-first design (correlation IDs from ingestion through inference); schema-compatibility management across two major WAL versions (§25); async systems engineering under backpressure (P2); fault-tolerant ingestion (poison-document isolation); deterministic replay systems (§21).

2.4 Cross-Project Relationships

Overlaps with: distributed databases (WAL, compaction, consistency — Bigtable, Dynamo lineage); search engines (Lucene/Tantivy inverted-index lineage); observability pipelines (OpenTelemetry); stream processing (bounded queues, backpressure); storage engines (RocksDB-class LSM concepts, applied to the vector store's segment model); inference-serving systems (provider abstraction, streaming); compilers (multi-stage pipeline transformations — ingestion → chunk → embed → index is a compilation pipeline in spirit); filesystems (WAL/compaction semantics); networking (gRPC flow control); runtime schedulers (cooperative async). Related systems studied directly in §5 and §31: Lucene, Elasticsearch, Tantivy, Milvus, Weaviate, Vespa, Pinecone, Kafka, ClickHouse, RocksDB.

2.5 Calibration Value

A successful implementation exercises nearly every modern infrastructure concern simultaneously: indexing, scheduling, distributed coordination, persistence, replication, latency management, memory pressure, backpressure, replayability, and consistency — making this project a systems-engineering calibration benchmark comparable in scope to building a small storage engine plus a small search engine plus a small scheduler, wired together under one correctness contract.

What Mastery Looks Like

  • Can explain why WAL durability must precede query-visibility (I1) and name the exact failure this prevents — dirty reads of unfsynced vectors — after implementing §17 (Phase 5).
  • Can diagnose a recall regression by reading a replay diff instead of re-running production traffic, because §21 (Phase 9) replay/evaluation infrastructure exists and is trusted.
  • Can size an ANN shard's resident-memory footprint from first principles (§32, C2) rather than by trial-and-error, after implementing the HNSW engine in §18 (Phase 6).
  • Can articulate the tenant-isolation blast radius of a shared cache miss and where quota enforcement must sit (metadata filter vs. shard routing vs. cache partition) after §20 (Phase 8) and §13.5 (I5).
  • Can distinguish a tokenizer-drift bug from an embedding-provider-drift bug using lineage metadata alone, after §15 (Phase 3) and §16 (Phase 4).
  • Can defend, with numbers, why compaction amplification and WAL amplification are separate budgets that both bound storage cost, after §18 (Phase 6) and §28.
  • Can design a deferred-feature contract (PhaseDeferred) that keeps an un-implemented capability architecturally reachable instead of silently precluded, after reading §35.

3.2 API Gateway

Terminates TLS, validates auth tokens, applies tenant quotas, enforces request-size budgets, injects correlation IDs, performs coarse admission control. Stateless except bounded rate-limit token buckets. First trust boundary — malformed/oversized requests never reach internal orchestration.

3.3 Ingest Gateway

Receives documents/streams/batch uploads and persists an upload manifest before processing begins (replayability, P3). Never mutates indexes directly; enqueues immutable jobs onto scheduler-runtime, so retries and forensic replay are deterministic.

3.4 Document Normalizer

Converts heterogeneous formats into canonical structured documents: MIME detection, OCR fan-out, encoding normalization, metadata extraction, attachment traversal, malformed-content quarantine. All downstream hashes derive from this canonical form — the normalizer is the canonicalization authority.

3.5 Chunk Engine

Tokenizer-aware semantic segmentation. Deterministic across software versions (chunk IDs derive from document lineage + byte range) so replay compatibility holds across a tokenizer upgrade window.

3.6 Embedding Orchestrator

Batches chunk requests, manages provider adapters, applies retry/idempotency semantics, records embedding lineage. Decouples vector storage from provider-specific embedding semantics — a provider swap never touches the storage engine.

3.7 Retrieval API

Owns query lifecycle: lexical query planning, ANN planning, filter compilation, deadline enforcement, cancellation propagation, instrumentation. The only subsystem permitted to fan a query out to shards.

3.8 Hybrid Retrieval Coordinator

Merges BM25 lexical results, ANN semantic matches, metadata filters, and reranker candidates; normalizes heterogeneous score distributions under a deterministic merge order (I8).

3.9 Lexical Index Engine

Inverted index optimized for metadata-aware retrieval; segment compaction, postings compression, and query caching evolve independently of vector indexing (ADR-24).

3.10 Vector Storage Engine

Owns vector WAL, ANN indexes, tombstones, snapshots, compaction metadata, shard-routing metadata. This is the primary persistence and retrieval-performance boundary and the concurrency boundary for shard-local writers vs. concurrent readers (§18).

3.11 Metadata Storage Plane

PostgreSQL-backed: tenants, collections, document lineage, ingestion manifests, embedding versions, chunk metadata, ACLs, audit records. Strongly consistent — this is the authoritative store (P12); ANN indexes are derived state that can always be rebuilt from it.

3.12 Context Assembly Service

Transforms retrieved fragments into model-ready prompts: dedup, token budgeting, citation generation, conflict resolution, ordering, prompt formatting.

3.13 Inference Gateway

Abstracts external model providers: retry semantics, streaming, timeout management, provider failover, quota enforcement, auditability. This is the protocol boundary to systems this blueprint does not own (§1.2, delegates).

3.14 Evaluation and Replay Plane

Captures retrieval traces, ranked candidate sets, reranker outputs, latency metrics, prompt lineage, evaluation fixtures — enabling deterministic offline debugging without replaying live traffic.

3.15 Observability Stack

Aggregates structured logs, metrics, distributed traces, replay identifiers, ingestion lineage, and query-lifecycle telemetry. Every subsystem crosses this boundary — no subsystem may emit unlabeled telemetry (P5).

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every ingestion transformation (normalize, chunk, embed-request) must be replayable byte-for-byte given the same input · Tradeoff: forgoes non-deterministic "smart" heuristics (e.g., adaptive OCR retries with jitter) that could improve average-case quality · Operational: replay CLI (§21) diffs traces against goldens on every deploy · Violated: retrieval drift becomes undebuggable — a ranking regression cannot be distinguished from noise.
  • P2 — Backpressure Everywhere. Rule: every queue (ingest buffer, embedding batch queue, WAL writer channel) is bounded with an explicit capacity · Tradeoff: producers must handle rejection or block, adding caller-side complexity · Operational: queue-depth gauges alert before saturation · Violated: unbounded queues convert transient slowness into cascading memory exhaustion (FM-6).
  • P3 — Immutable Lineage. Rule: documents, chunks, embeddings, and retrieval traces are immutable once written; corrections are new versions, not mutations · Tradeoff: storage grows monotonically until retention/compaction reclaims it · Operational: lineage tables (§8) are append-only · Violated: mutation destroys replay guarantees (P1) retroactively.
  • P4 — Crash-Only Recovery Semantics. Rule: every subsystem must recover correctly from abrupt SIGKILL with no reliance on graceful-shutdown code paths having run · Tradeoff: forgoes shutdown-time optimizations (e.g., deferred flush) that assume clean exit · Operational: recovery scanners (§17.2) run on every startup, not just after a detected crash · Violated: partial shutdown coordination becomes a second, untested recovery path that diverges from the tested one.
  • P5 — Observability by Default. Rule: no retrieval stage may execute without emitting trace ID, stage timing, candidate count, and filter diagnostics · Tradeoff: instrumentation overhead on the hot path (bounded in §28) · Operational: trace_id is mandatory on every span, enforced by a lint · Violated: opaque stages make §21 replay diffs meaningless — there is nothing to diff.
  • P6 — Explicit Resource Ownership. Rule: every buffer, mmap region, cache, and channel has one named owner responsible for its lifecycle · Tradeoff: more boilerplate ownership-transfer code at subsystem boundaries · Operational: ownership documented in the trait contracts of §11 · Violated: use-after-free-class mmap bugs or double-free-class cache eviction races.
  • P7 — Bounded Resource Usage Per Tenant. Rule: no tenant may consume unbounded CPU, memory, storage, or ANN traversal depth · Tradeoff: a legitimate high-volume tenant is throttled the same as a runaway one without an explicit quota increase · Operational: quota checks at admission (§13.2) and at shard fanout (§20.2) · Violated: noisy-neighbor collapse (FM-6) for co-located tenants.
  • P8 — Stable Wire Compatibility. Rule: protocol evolution (Protobuf schemas) is additive-only across a rolling upgrade window · Tradeoff: cannot remove a deprecated field for at least two major versions (§25) · Operational: schema-compatibility CI gate blocks breaking changes · Violated: rolling upgrades split-brain between old and new wire formats.
  • P9 — Storage Correctness Before ANN Acceleration. Rule: the WAL/snapshot correctness kernel (§17) must be verified before any ANN acceleration work (§18) begins · Tradeoff: delays recall/latency optimization work by one phase · Operational: Phase 5 exit criteria (§17.4) gate Phase 6 start · Violated: an ANN index built atop an unverified storage layer inherits silent corruption that recall metrics alone will not surface.
  • P10 — Replayability First. Rule: every retrieval decision (plan, candidate set, rerank score, assembled context) must be reconstructable from captured lineage · Tradeoff: capture overhead and retention cost (§28, §32) · Operational: replay-engine (§21) is exercised in CI, not just ad hoc · Violated: incident postmortems degrade to guesswork.
  • P11 — Isolation Before Tenancy Density. Rule: tenant correctness (no cross-tenant leakage) is prioritized over shard-packing density optimizations · Tradeoff: lower hardware utilization than a fully shared-index design · Operational: tenant isolation verified by fixture fixtures/tenancy/cross-tenant-access.json before any density optimization ships · Violated: a density optimization becomes a confidentiality incident (T6).
  • P12 — Metadata Authority. Rule: the metadata plane is the source of truth; ANN and lexical indexes are derived state that can always be rebuilt from it · Tradeoff: rebuild-from-metadata is slower than trusting the index directly, but that is the point · Operational: consistency scanners (§13.2) treat metadata as ground truth when reconciling · Violated: an ANN index becomes unverifiable — there is no way to tell corruption from a legitimate update.
  • P13 — Structured Failure Surfaces. Rule: every failure is categorized (failure class, §23), observable (telemetry field), replayable (trace-linked), and actionable (has a named recovery path) · Tradeoff: requires failure taxonomy discipline up front rather than ad hoc error strings · Operational: FM-# rows in §23 are the only sanctioned failure vocabulary · Violated: incident response degrades into log archaeology with no shared vocabulary.

State Meaning Exit Condition
RECEIVED request admitted past API Gateway validation complete

8.4 ANN Query Semantics

Inputs: embedding vector, top_k, filter predicate, timeout budget, recall target. Outputs: ranked candidates, traversal statistics, recall metadata, shard diagnostics — all four outputs are mandatory even on a degraded (partial-shard) response, so the caller can distinguish "fewer candidates because of a tight filter" from "fewer candidates because a shard timed out."

8.5 Failure Example — Malformed Query Rejection

Input: top_k = -1, empty vector. Expected behavior: reject before the planner stage; emit validation_failure_total{reason="negative_top_k"}; no shard fanout occurs; the rejected-request trace is still archived (P10 applies even to rejections).

8.7 Context Budgeting Example

12. Phase 0 — Repository Foundation & Correctness Kernel

12.1 Objectives

Stand up reproducible build infrastructure and the correctness kernel every later phase depends on: repository topology (§10), CI/CD, dependency policy (ADR-04), observability bootstrap (P5), workspace lint policy, and the deterministic-simulator harness (§7) that later phases plug invariant assertions into. No retrieval or storage logic ships in this phase — only the scaffolding that makes every later phase's claims machine-checkable.

12.2 Detailed Implementation Steps

Initialize the Cargo workspace (Cargo.toml, rust-toolchain.toml pinned per ADR-22); wire crates/observability first since every other crate depends on it for trace_id propagation (P5). Configure workspace-level clippy deny rules and rustfmt lockstep formatting. Introduce crates/protocols as the Protobuf schema crate (ADR-06); generate bindings via build.rs at compile time, not checked-in generated code. Add crates/trace-context implementing the correlation-ID middleware referenced by I13. Add Makefile/Justfile targets wrapping docker-compose.yml (local PostgreSQL + MinIO). Configure the CI matrix (.github/workflows/ci.yml): Linux, pinned-stable compiler, a nightly fuzz lane feeding fuzz/fuzz_targets/. Add cargo-deny (ADR-04) and SBOM generation (ADR-19, SPDX output) to release.yml. Stand up the test-fixtures crate holding proptest generators (ADR-12) and the deterministic-simulator scaffold that later phases attach I# assertions to — this is the mechanism referenced throughout §7's debugging-methodology paragraph.

12.3 Deliverable

A runnable development environment: docker-compose up brings up PostgreSQL + MinIO + a stub observability collector; every scaffolded crate compiles, exposes /healthz, and emits a Prometheus /metrics endpoint with zero real business metrics but correct label cardinality discipline (P5). CI passes on a clean checkout.

12.4 Acceptance Criteria

Clean bootstrap on Linux/AMD64 in under 15 minutes (CI wall-clock, matches §4's build budget intent); zero-warning clippy policy across the workspace; reproducible Cargo.lock hash across two consecutive CI runs on the same commit; structured JSON logs visible in docker-compose logs containing trace_id on every line (I13); fixtures/build/minimal-config.toml parses without error.

12.5 Conformance Fixtures

fixtures/build/minimal-config.toml — smallest valid config crate input, expected: clean parse. fixtures/logging/trace-propagation.json — a synthetic request with a pre-set trace_id, expected: identical trace_id on every emitted span. fixtures/config/invalid-runtime.toml — malformed TOML (unterminated string), expected: a typed ConfigError, not a panic.

12.6 Pitfalls

Dependency drift: nondeterministic CI failures from an unpinned transitive dependency; root cause is a missing Cargo.lock commit; debug by diffing lockfile hashes across CI runs; signal is a lockfile-mismatch CI alert; recovery is re-vendoring and re-locking (ADR-22). Telemetry cardinality explosion: Prometheus instability from unbounded label values (e.g. raw tenant_id as a label on a histogram); root cause is a missing bounded-label review at PR time; debug via Prometheus scrape_samples_scraped growth; signal is collector OOM; recovery is converting the label to a bounded enum or dropping it to the trace layer instead of the metrics layer.

12.7 Performance Concerns

Compile-time explosion from an oversized shared "utils" crate anti-pattern — mitigated by keeping crate boundaries aligned to the trait contracts in §11, not to convenience. Oversized container images from unstripped debug symbols in release Docker layers (ADR-19). Tracing overhead on the hot path from synchronous span export — mitigated by batching the OTel exporter (ADR-15) off the request path.

12.8 Edge Cases

Broken local Docker DNS resolution between docker-compose services; missing CPU AVX2 support on a developer laptop (fails the SIMD baseline in §4, must degrade to a scalar fallback build flag, not a hard failure); unsupported kernel versions lacking the io_uring surface later phases assume optionally.

12.9 Failure Analysis

Blast radius of a bootstrap failure is local to a single developer/CI runner — no shared state is at risk in this phase. If bootstrap fails: verify Protobuf codegen ran (crates/protocols/build.rs); verify OpenSSL/rustls linkage for the gRPC transport (RFC 7540); inspect cargo-deny reports for a newly-introduced disallowed license. Operator visibility is CI logs only in this phase — no production telemetry exists yet.

12.10 Operational Notes

Every scaffolded service exposes /healthz and a Prometheus /metrics endpoint from day one (P5) — this is enforced by a compile-time lint added in this phase, not by convention. Metric namespace convention locked here: <crate>_<subsystem>_<metric> (e.g. wal_fsync_lag_ms, used from §17 onward). Rollback is git revert at this phase — no data migration exists yet.

13.1 Objectives

Add metadata inheritance (ACL propagation from document to chunk) and chunk-level deduplication (identical chunk_id from two ingestion paths collapses to one storage write, not two). A stable chunk-generation pipeline: Chunk records with deterministic IDs, stable across replay, and a tokenizer-drift detector that fails CI on an unpinned version bump.

chunk_id stable across 5 replay runs of fixtures/chunks/replay-golden.json; tokenizer-drift detection fails CI if EmbeddingVersion is unchanged but token-count checksum diverges by more than 0 tokens; multilingual handling verified against fixtures/chunks/multilingual.txt with zero UTF-8-boundary token splits.

fixtures/chunks/multilingual.txt — mixed CJK/Latin/RTL text, expected: no mid-codepoint splits. fixtures/chunks/emoji.txt — multi-codepoint emoji sequences, expected: grapheme-cluster-safe boundaries. fixtures/chunks/replay-golden.json — a pinned tokenizer-version golden, expected: byte-identical chunk_id sequence on replay.

16. Phase 4 — Embedding Orchestrator

16.1 Objectives

Implement batched, replayable embedding generation: provider abstraction, retry/idempotency semantics, and embedding lineage — decoupling vector storage from any single provider's API shape.

16.2 Detailed Implementation Steps

Build crates/embedding-orchestrator: define the EmbeddingProvider trait (§11) once; implement an external-API adapter and a local-model adapter behind it (ADR-05 does not apply here — this is a runtime pluggability boundary, not a storage-format decision). src/batching.rs implements adaptive batching (batch size grows/shrinks against observed provider latency, bounded by the 25k chunks/minute throughput target in §4) and idempotency keys derived from chunk_id + EmbeddingVersion so a retried batch never double-embeds. src/provider.rs adds dimensionality validation and embedding-checksum validation before a vector is handed to vector-storage-engine — rejecting a dimension mismatch here is far cheaper than discovering it at ANN-index build time (§18). Add provider health scoring and failover (Dynamo-style hinted-handoff intuition, DeCandia et al. 2007, applied to provider selection rather than replica selection). Add embedding-lineage records satisfying I2's downstream consistency requirement, and a bounded embedding cache keyed on content_hash to avoid re-embedding identical chunks across collections sharing an embedding profile.

16.3 Deliverable

A reliable embedding subsystem: batched requests with provider failover, replayable via captured lineage, with rejected-input validation happening before storage rather than after.

16.4 Acceptance Criteria

Zero duplicate embeddings after 50 injected retry-storms in the chaos harness (idempotency-key verification); provider failover completes within 2 provider-timeout intervals; dimensionality mismatches rejected with a typed error before reaching vector-storage-engine, verified against fixtures/embeddings/dimension-mismatch.json.

16.5 Conformance Fixtures

fixtures/embeddings/dimension-mismatch.json — a vector with the wrong declared dimensionality, expected: rejected pre-storage. fixtures/embeddings/retry-replay.json — a batch replayed after a simulated provider timeout, expected: exactly one embedding per chunk, not two.

16.6 Pitfalls

Provider rate limits: cascading retries amplify load on an already-degraded provider; root cause is retry backoff not being adaptive to the provider's own Retry-After signal; debug via embedding_provider_retry_total correlated with provider-side 429 responses; signal is retry-storm shaped traffic in the provider dashboard; recovery is adaptive backoff keyed to the provider's advertised limit, not a fixed exponential schedule. Embedding drift: a provider silently updates its underlying model without a version bump, changing embedding semantics; detection is a distributional shift in the recall-benchmark corpus (I11); recovery is treating the provider's model update as a new EmbeddingVersion even though the provider did not signal one, then re-embedding.

16.7 Performance Concerns

Batch sizing tradeoff — larger batches amortize per-request overhead but raise tail latency for the last chunk in a slow batch; serialization overhead from Protobuf-encoding large batches; network RTT to external providers (30–300 ms, §4) dominating end-to-end embedding latency far more than local compute.

16.8 Edge Cases

Partial batch failures (3 of 50 chunks in a batch fail validation — the other 47 must still commit, not roll back the whole batch); timeout races between a retry firing and the original request's late success arriving; invalid vectors (NaN/Inf components) from a misbehaving local-model adapter.

16.9 Failure Analysis

Recovery: replay unfinished jobs from the last durable checkpoint in scheduler-runtime; invalidate any lineage record whose embedding checksum failed validation rather than persisting it optimistically. Blast radius is bounded to the affected EmbeddingVersion's pending batch, not the whole collection.

16.10 Operational Notes

Metrics: embedding_batch_size_histogram, embedding_provider_latency_ms, embedding_provider_retry_total. Spans: embed.batch, embed.provider_call. Provider-specific dashboards required per the EmbeddingProvider adapter boundary (§11); token-consumption metrics feed the cost-attribution work in §24.

17. Phase 5 — WAL and Vector Storage Engine

17.1 Objectives

Implement the durable vector-persistence correctness kernel (I1, I4, I6, I9): binary WAL, mmap segments, tombstones, and snapshot manifests. This phase must be verified before ANN acceleration work begins (P9) — recall metrics cannot detect a corrupt storage layer.

17.2 Detailed Implementation Steps

Build crates/vector-storage-engine: src/wal.rs defines the binary WAL format (ADR-10) — length-prefixed, checksummed (CRC32C) records per WalRecord (§11); a monotonic sequence allocator enforces I4. src/mmap_segment.rs implements the mmap segment allocator and shard partitioning; append-only vector files with tombstone records satisfying I9 (Bigtable-style SSTable immutability, Chang et al. 2006, applied to vector segments rather than key-value rows). Add fsync grouping (batch multiple appends per fsync call, bounded by a max-batch-age timer to keep I1's durability-before- visibility guarantee tight under load). Add the WAL replay engine and corruption detectors (truncated-tail detection via length-prefix validation). Add src/snapshot.rs: snapshot manifests with checksum coverage satisfying I6, WAL-truncation policy (only truncate WAL entries covered by a verified snapshot), and bounded replay windows so recovery time stays inside the RTO in §4. Add shard-recovery planner sequencing recovery across shards to avoid a thundering-herd of concurrent mmap cold-loads (§4's cold-mmap-init budget).

17.3 Deliverable

A crash-safe vector storage engine: kill -9 at any point during a write burst, restart, and the shard recovers to the last fsynced state with zero silent data loss and zero resurrected tombstones.

17.4 Acceptance Criteria

Power-loss replay correctness verified across 500 randomized kill-points in the chaos harness (§26); checksum-mismatch detection on fixtures/wal/corrupted-checksum.wal within one replay pass; snapshot recovery succeeds from fixtures/wal/replay-golden.json with byte-identical post-recovery state; WAL amplification stays under the 2.5× budget from §4 under the 25k chunks/minute embedding-throughput load.

17.5 Conformance Fixtures

fixtures/wal/truncated.wal — a WAL file cut mid-record, expected: clean truncated-tail detection, no panic. fixtures/wal/corrupted-checksum.wal — a record with a flipped bit, expected: checksum failure surfaced as a typed error, record skipped, replay continues past it. fixtures/wal/ replay-golden.json — a full write/snapshot/restart sequence, expected: identical shard state on replay.

17.6 Pitfalls

Torn writes: a partial write during a crash leaves a syntactically-plausible but semantically corrupt record; root cause is writing length-prefix and payload as two separate syscalls; debug via replaying against fixtures/wal/truncated.wal; signal is a checksum failure at a record boundary that parses as valid length but invalid payload; recovery is checksums plus length-prefix framing written atomically via a single pwritev call (Mara Bos, Rust Atomics and Locks ch. 5, on avoiding torn concurrent writes). mmap exhaustion: unbounded segment growth exhausts the 8,192 mmap-segment FD budget from §4; root cause is missing segment-rotation policy; debug via mmap_segment_count trending toward the budget ceiling; recovery is bounded segment rotation with proactive compaction scheduling (§18) before the ceiling is reached, not reactive rotation after.

17.7 Performance Concerns

fsync latency dominating write-path tail latency under the SSD-first assumption (§4) — mitigated by fsync grouping, at the cost of a slightly wider durability window (bounded by the max-batch-age timer). Page faults during cold mmap initialization (the 5-minute cold-init budget in §4 exists precisely because first-touch page faults are expensive at shard scale). NUMA locality: shard-pinned memory access avoids cross-socket page-fault latency (§4's NUMA policy).

17.8 Edge Cases

Partial WAL writes interrupted by process termination mid-fsync-group; replay interruption from a second crash during recovery itself (recovery must itself be idempotent and resumable, per P4); disk- full conditions mid-append (must fail the append cleanly, not corrupt the WAL tail).

17.9 Failure Analysis

Blast radius is shard-local by construction — WAL corruption in one shard never propagates to another shard's file. Recovery: WAL replay from the last verified snapshot plus rollback of any uncommitted tail. Detection is the corruption-detector's checksum-mismatch counter; forensics use the replay-engine to reconstruct the exact write sequence leading to the corrupted record.

17.10 Operational Notes

Metrics: wal_fsync_lag_ms, wal_seq_gap_total, snapshot_checksum_fail_total, mmap_segment_count. Spans: storage.wal_append, storage.snapshot, storage.replay. SSD-only deployment is a hard requirement (§4); snapshot cadence every 30 minutes; WAL readers must remain backward-compatible for two major versions (§25) across a rolling upgrade.

18. Phase 6 — ANN Index (HNSW) Implementation

18.1 Objectives

Implement HNSW-based approximate nearest-neighbor retrieval (Malkov & Yashunin, 2018) atop the verified storage kernel from §17 (P9): graph construction, bounded-ef_search traversal, and recall-vs-latency instrumentation feeding the recall floor in I11.

18.2 Detailed Implementation Steps

Extend vector-storage-engine (this phase does not introduce a new crate — HNSW is a storage-engine concern per ADR-05's control-over-invariants rationale): graph-node layout with layered proximity links (M=16 default, per Malkov & Yashunin §4); an insertion planner assigning new nodes to layers probabilistically; search traversal with bounded ef_search (§4's ANN p95 budget gates the default value — larger ef_search trades latency for recall, tunable per collection). Add SIMD distance kernels (AVX2 baseline, AVX512 optional per §4) for cosine/dot-product distance, with cosine normalization applied at insertion time, not at query time, to avoid repeated normalization cost. Add tombstone skipping during traversal (never resurrect a deleted vector, I9) and graph compaction with neighbor pruning to bound degree growth. Add mmap-backed graph loading (reuses §17's segment allocator) and shard-local insertion locking with concurrent lock-free readers (Mara Bos ch. 6–7, on avoiding writer-starves-readers patterns). Add recall benchmarking against a fixed corpus (benchmarks/ann_recall.rs) and graph-rebuild tooling triggered when I11's recall floor is breached.

18.3 Deliverable

A functional ANN engine meeting the recall and latency targets in §4, with replay-safe graph reconstruction from the WAL alone (no separate graph-specific durability path).

18.4 Acceptance Criteria

Recall@10 > 0.93 on the fixed benchmark corpus (I11's floor); ANN search p95 < 40 ms per §4; replay- safe graph reconstruction verified against fixtures/ann/sift-small.bin producing an identical graph topology across two independent rebuilds from the same WAL.

18.5 Conformance Fixtures

fixtures/ann/sift-small.bin — a standard SIFT-derived small benchmark corpus, expected: recall@10 > 0.93 at the default ef_search. fixtures/ann/graph-corruption.bin — a graph with a dangling neighbor pointer, expected: the corruption validator flags it before it reaches query traffic.

18.6 Pitfalls

Graph degeneration: recall collapses after many deletions because tombstoned nodes still occupy neighbor slots, starving live candidates; root cause is missing periodic rebuild thresholds; debug via the recall-vs-latency dashboard trending down at flat ef_search; signal is recall_regression_ delta (I11) crossing the floor; recovery is a background graph rebuild past a tombstone-ratio threshold. Lock contention: shard-local insertion locking serializes all writers behind one mutex under high ingestion concurrency; root cause is a single coarse lock instead of layer-local locking; debug via lock-wait-time histograms; recovery is shard-local insertion queues (bounded, per P2) decoupling insertion admission from traversal locking.

18.7 Performance Concerns

Cache misses during graph traversal (working-set-vs-L3 mismatch, §4's L3 locality target) — mitigated by node-layout packing that keeps a node's neighbor list contiguous. Branch prediction degradation from data-dependent traversal order (inherent to graph search, bounded not eliminated). Heap allocations during traversal — a naive implementation allocates a visited-set per query; mitigated by a pooled, reusable visited-set bitmap sized to the shard's node count.

18.8 Edge Cases

Duplicate vectors (identical embeddings from two chunks) — must not distort recall metrics or double- count in top_k; zero vectors (a degenerate embedding from a provider failure that passed dimension validation but not a zero-vector check — add the check here as a second gate); quantization mismatch between a query vector's precision and the stored graph's quantization profile.

18.9 Failure Analysis

Detection: recall-regression alerts from the evaluation-runner (§21) comparing live recall against the I11 floor. Recovery: background graph rebuild from the WAL, which is always possible because the graph is derived state (P12) — the WAL, not the graph, is authoritative. Blast radius is shard-local; a degenerating shard degrades recall only for the collections routed to it.

18.10 Operational Notes

Metrics: ann_recall_at_10, ann_search_latency_ms, ann_ef_search_effective, graph_tombstone_ratio. Spans: ann.traverse, ann.insert, ann.rebuild. Graph-rebuild windows are configurable per collection to avoid rebuild storms across a shared cluster during a bulk-deletion event.

19. Phase 7 — Lexical Index and Hybrid Retrieval

19.1 Objectives

Implement the BM25 lexical index (independent lifecycle from the vector store, ADR-24) and the hybrid retrieval coordinator that merges lexical and semantic candidates under deterministic fusion (I8).

19.2 Detailed Implementation Steps

Build crates/lexical-index-engine: src/postings.rs implements postings lists with a token dictionary and compression codecs (Manning/Raghavan/Schütze ch. 5); src/bm25.rs implements BM25 scoring with tunable k1/b parameters (Robertson & Zaragoza, 2009). Add segment-flush logic and a background merge scheduler (Lucene-style, studied in §5) so merges never pause query traffic. Extend crates/retrieval-api: src/planner.rs adds the metadata-filter compiler (EBNF in §8.6) and shard fanout; src/deadline.rs implements deadline budgeting and cancellation propagation satisfying I7. Implement hybrid score normalization and reciprocal rank fusion (RRF) as the deterministic merge function required by I8 — score distributions from BM25 and cosine-distance ANN are not directly comparable, so fusion operates on rank, not raw score. Add query parsing, stopword handling, and stemming behind a pluggable analyzer boundary (kept separate from the tokenizer in §15, which segments for embedding, not for lexical analysis). Add a bounded query cache and postings mmap reuse from §17's segment allocator pattern.

19.3 Deliverable

A hybrid retrieval subsystem: BM25 + ANN fusion producing a single deterministically-ordered candidate list, with metadata filters compiled once per query and reused across all shard legs.

19.4 Acceptance Criteria

Lexical + ANN fusion produces identical ordering across 3 replay runs of fixtures/retrieval/hybrid- query.json (I8); metadata filters deterministic under fixtures/retrieval/filter-replay.json; cancellation propagates to all shard-fanout legs within 100 ms of a deadline expiry (I7).

19.5 Conformance Fixtures

fixtures/retrieval/hybrid-query.json — a query exercising both lexical and ANN legs, expected: deterministic RRF-fused ordering. fixtures/retrieval/filter-replay.json — a filter expression from §8.6's EBNF, expected: identical compiled-filter bytecode across two compilations.

19.6 Pitfalls

Score-distribution collapse: naively summing BM25 and cosine scores produces meaningless rankings because their scales are incomparable; root cause is skipping rank-based normalization; debug by plotting the score histogram per leg before and after fusion; recovery is RRF or a learned fusion weight, never raw score addition (this is why I8 mandates deterministic merge semantics, not just any merge). Segment-merge pauses: a naive foreground merge blocks query traffic during a large segment compaction; root cause is merge scheduling on the query thread pool instead of a background pool; recovery is background merges with a bounded concurrent-merge limit.

19.7 Performance Concerns

Postings decompression cost on the hot path — mitigated by block-compressed postings with skip lists (Manning/Raghavan/Schütze ch. 5) rather than whole-list decompression per query. Query fanout latency across shards — bounded by the intra-cluster RTT budget in §4. Cache locality of the query cache under a high-cardinality filter workload (cache-key includes the compiled filter, which can explode cardinality if filters are highly parameterized — bound the cache by an LRU with a fixed entry cap).

19.8 Edge Cases

Empty postings for a valid-but-rare term (must return zero lexical candidates cleanly, not error); malformed filter expressions caught by the EBNF-based compiler before shard fanout; cancellation races where a shard's response arrives just as its deadline expires (must discard the late response, not race it into the merge step).

19.9 Failure Analysis

Recovery: shard-local lexical-index rebuild from the metadata plane's chunk catalog (P12 — the lexical index, like the ANN graph, is derived state). A single shard's postings corruption degrades recall for that shard's collections only; the hybrid coordinator's deterministic merge (I8) means a degraded shard is detectable by comparing its candidate-count distribution against its historical baseline.

19.10 Operational Notes

Metrics: lexical_postings_decompress_ms, hybrid_fusion_candidates_total, filter_compile_ms, retrieval_deadline_overrun_total. Spans: retrieval.plan, retrieval.fanout, retrieval.fuse. Retrieval dashboards are mandatory before this phase's exit — the hybrid path is the system's primary customer-facing SLO surface (§4).

20. Phase 8 — Reranking, Context Assembly & Inference Gateway

20.1 Objectives

20.2 Detailed Implementation Steps

Build crates/inference-gateway: src/provider_adapter.rs abstracts external providers with retry semantics, streaming response support, deadline propagation from the retrieval deadline (I7 extends end-to-end), and provider failover mirroring the health-scoring pattern from §16. Add partial-stream recovery (a dropped connection mid-stream resumes from the last acknowledged token where the provider API supports it, or fails cleanly where it does not) and output-redaction hooks for compliance-sensitive tenants.

20.3 Deliverable

An end-to-end context-generation and dispatch pipeline: deterministic prompt assembly, cross-encoder reranking with a bounded fallback path, and streaming inference dispatch with cancellation propagation.

20.4 Acceptance Criteria

Deterministic prompt assembly verified against fixtures/context/dedup-golden.json (byte-identical assembled prompt across 3 runs); reranker-timeout fallback engages within 1 reranker-timeout interval and is observable via a dedicated metric; streaming responses remain stable under fixtures/inference/stream-interrupt.json with cancellation completing within 1 second (§4's shutdown-drain-adjacent budget).

20.5 Conformance Fixtures

fixtures/context/token-overflow.json — a candidate set exceeding the 11k retrieved-token budget, expected: deterministic truncation by reranker-score priority, recorded in the trace. fixtures/ context/dedup-golden.json — overlapping chunks from adjacent byte ranges, expected: single deduplicated span. fixtures/inference/stream-interrupt.json — a mid-stream provider disconnect, expected: clean partial-stream recovery or clean failure, never a hung connection.

20.6 Pitfalls

Token-budget miscalculation: an off-by-one in reserved-completion-budget accounting causes provider rejection at dispatch time; root cause is computing the retrieved budget from the wrong base (total context minus completion budget minus system prompt, in that order — reversing the subtraction order under-reserves); debug by replaying fixtures/context/token-overflow.json; recovery is a budget-accounting unit test pinned to §8.7's worked example. Duplicate-context inflation: near- duplicate (not byte-identical) chunks from two ingestion paths both survive deduplication because dedup keys on exact chunk_id, not semantic similarity; impact is reduced effective context density; recovery is a semantic-similarity dedup pass bounded by a similarity threshold, applied after exact dedup.

20.7 Performance Concerns

Reranker GPU contention under the 200-concurrent-request cap (§4) — mitigated by request batching and a queue-depth-based backpressure signal to the retrieval-api caller (P2). Serialization overhead assembling large candidate sets into the reranker's batch format. Prompt-formatting cost scaling with citation count — bounded by capping citations per assembled prompt.

20.8 Edge Cases

Multilingual prompts interacting with provider-side tokenization (the assembler's token count is an estimate against the chunk-tokenizer, not the provider's tokenizer — document this gap explicitly rather than presenting a false-precision budget); oversized individual citations that alone exceed the retrieved budget (must truncate the citation, not drop it silently); reranker failures mid-batch (partial batch succeeds, the fallback path covers only the failed subset, not the whole request).

20.9 Failure Analysis

Blast radius of a reranker outage is provider-local — the fallback to hybrid ordering (§19's RRF output) keeps the pipeline functional at reduced ranking quality, never a hard failure. Blast radius of an inference-provider outage is also provider-local given multi-provider failover (§20.2); a single-provider deployment has no such fallback and must alert distinctly.

20.10 Operational Notes

Metrics: rerank_timeout_fallback_total, context_truncation_total, inference_stream_cancel_ms, inference_provider_failover_total. Spans: rerank.score, context.assemble, inference.dispatch. Prompt-lineage retention is mandatory (P10) — a compliance audit must be able to reconstruct any assembled prompt from its citation lineage alone.

21. Phase 9 — Replay Diagnostics, Evaluation & Operational Hardening

21.1 Objectives

Close the loop: deterministic replay/evaluation infrastructure (P10, I8, I11) and the multi-tenant operational hardening (P7, P11) required before this system is production-ready per §24.

21.2 Detailed Implementation Steps

Build crates/replay-engine: src/replay.rs captures retrieval traces, planner decisions, candidate sets, reranker outputs, and prompt lineage into an append-only replay store; a replay CLI (tools/replay-cli) replays a captured trace and diffs it against a golden via src/diff_visualizer.rs. Build crates/evaluation-runner: src/ranking_metrics.rs computes recall/precision-at-k and latency-regression tracking against a query corpus, with deterministic seeds (P1) so an evaluation run is itself replayable; canary-comparison mode diffs two EmbeddingVersions' ranking output on the same query corpus. Build crates/admin-control-plane: src/rbac.rs implements role-based access for operator APIs (van Steen, Distributed Systems ch. 8, on authorization in distributed control planes); tenant lifecycle and quota-policy management. Extend crates/tenant-isolation: src/quota.rs enforces P7 at both admission (api-gateway) and shard-fanout (retrieval-api) layers — two independent enforcement points, not one, so a bypass at either layer is still caught (I5, I12). Add shard-balancing, canary deployment support, rolling-upgrade compatibility checks (P8), snapshot shipping (crates/snapshot-manager, src/snapshot_shipper.rs), and disaster- recovery drill tooling.

21.3 Deliverable

A replayable evaluation framework plus a production-hardened multi-tenant deployment: any retrieval decision from the last retention window can be replayed and diffed against a golden; a rolling upgrade completes with zero cross-version wire incompatibility.

21.4 Acceptance Criteria

Deterministic replay reproducibility verified against fixtures/replay/golden-query-set.json (I8); ranking-diff visibility surfaces any nonzero delta from fixtures/replay/ranking-regression.json within one evaluation run; rolling upgrades complete with zero downtime across fixtures/tenancy/cross-tenant-access.json's isolation check remaining green throughout; disaster- recovery drill restores from fixtures/recovery/disaster-replay.json within the metadata RTO (§4, < 30 min).

21.5 Conformance Fixtures

fixtures/replay/golden-query-set.json — a fixed query corpus with pinned expected rankings, expected: zero-diff replay. fixtures/replay/ranking-regression.json — a deliberately regressed ranking, expected: the diff visualizer flags it. fixtures/tenancy/cross-tenant-access.json — an attempted cross-tenant read, expected: rejected at both enforcement layers (I5). fixtures/recovery/ disaster-replay.json — a full-cluster recovery scenario, expected: RTO met, zero data loss beyond the declared RPO (§4).

21.6 Pitfalls

Non-deterministic ranking: two replay runs of the same trace produce different orderings; root cause is an unseeded random tie-break in the reranker or fusion step (P1 violation); debug via replay-drift alarms comparing consecutive replay runs of the same golden; recovery is seeding every source of randomness and asserting seed-determinism in CI. Fixture rot: golden fixtures drift out of sync with an intentional ranking-algorithm change, producing false-positive regression alerts; mitigation is fixture versioning tied to EmbeddingVersion/algorithm-version, with an explicit fixture-regeneration step reviewed in the same PR as the algorithm change. Noisy-neighbor retrieval collapse: one tenant's burst starves shared-shard capacity for co-located tenants; mitigation is shard quotas enforced at both layers per §21.2.

21.7 Performance Concerns

Replay-storage growth from append-only trace capture (P3) — bounded by the retention policy from §13, not by capturing less. Benchmark execution cost for the full evaluation corpus — run on a schedule (nightly) rather than per-commit, with a smaller smoke corpus gating CI. Scheduler saturation and shard imbalance under autoscaling — mitigated by shard-balancing metrics feeding the autoscaler rather than raw CPU utilization alone.

21.8 Edge Cases

Missing replay dependencies (a replayed trace references an EmbeddingVersion that has since been garbage-collected — must fail the replay explicitly, not silently substitute a newer version); incompatible schema versions between a captured trace and the current replay-engine version (P8 governs this the same as wire compatibility); partial region outages during a rolling upgrade; expired credentials mid-drill.

21.9 Failure Analysis

Containment for a tenant-overload incident is tenant-local throttling (P7) — verified not to affect co-located tenants' p99 (the noisy-neighbor pitfall above). Recovery for a failed rolling upgrade is rolling rollback, gated by the same compatibility checks that gated the forward roll. Forensics for any incident in this phase route through replay-engine first — the replay store is the canonical incident record.

21.10 Operational Notes

Metrics: replay_order_mismatch_total, recall_regression_delta, quota_reject_total, rolling_upgrade_compat_fail_total. Spans: replay.compare, evaluation.run, admin.rbac_check. Weekly restore drills are mandatory (§24); benchmark history is retained indefinitely to support long-horizon regression analysis, distinct from the bounded-retention replay-trace store.

25. Compatibility & Versioning

Wire compatibility: Protobuf schemas are additive-only (P8); reserved field IDs are mandatory on any removed field, never reused. A schema-compatibility CI gate (ADR-06-adjacent) blocks any breaking change from merging.

Storage compatibility: vector-store snapshots are versioned; WAL readers remain backward-compatible for two major versions (§17.10, I10), so a rolling upgrade never requires a synchronized fleet-wide restart.

API stability: semantic versioning is enforced on retrieval-api and inference-gateway's external surfaces; deprecation windows are a minimum of 6 months.

Embedding-version compatibility: an EmbeddingVersion bump is required for any tokenizer change (I3), provider-model change (§16.6), or quantization-profile change — never an implicit, undocumented shift. Old and new EmbeddingVersions coexist in the same collection during a migration window managed by evaluation-runner's canary-comparison mode (§21.2).

Rolling-upgrade compatibility checks (§21.2) run as a deploy-pipeline gate, not a post-deploy observation — an incompatible change is caught before traffic shifts.

26. Testing & Verification Strategy

Unit testing required for: parsers (§14), tokenizers (§15), WAL codecs (§17), ANN traversal (§18) — each crate's tests/ directory (§10) holds these.

Integration testing validates end-to-end ingestion (§14→§16), replay fidelity (§21, I8), and retrieval determinism (§19, I8) across crate boundaries.

29. Scalability Analysis

Horizontal scaling: retrieval nodes scale by shard partitioning behind stateless query coordinators (retrieval-api); adding a node adds shard capacity without a coordination-protocol change, up to the 64-shards/collection ceiling from §4.

Vertical scaling: ANN memory locality benefits from large-memory instances (§4's 220 GB ceiling) more than from additional cores past the CPU-core-pinned async worker count.

Scaling ceilings: reranker GPU throughput (§4's 200-concurrent-request/node budget) and metadata- plane coordination (single-writer-per-hot-row contention, §13.6) are the two hard bottlenecks — ANN memory residency degrades gracefully (falls back to disk-backed mmap with higher latency) while the other two fail hard.

Replication pressure: larger embedding dimensionality increases WAL bandwidth (§32, C1) and snapshot-transfer cost (§32, C9) superlinearly with collection count, because each collection's shard set replicates independently — federation across collections (§1.6, deferred) is the eventual answer, not larger per-shard replicas.

Distributed-systems lineage: the shard-routing and quorum intuition (van Steen ch. 6–7) applies directly once cross-cluster federation (§1.6) is built — Phase 9 (§21) deliberately stops short of that to keep the correctness kernel (§17) verifiable within a single-cluster blast radius first.

30. Mental Models & First Principles

  • MM1 — WAL Is Truth, Everything Else Is a View. Compressed insight: the ANN graph, the lexical index, and even query-time caches are all rebuildable projections of the WAL + metadata plane · Predicts: a corrupted derived index is always recoverable without data loss · Bug class avoided: treating index corruption as a data-loss incident instead of a rebuild-time incident · applies in §17 and §18.
  • MM2 — Determinism Is a Debugging Feature, Not a Purity Test. Compressed insight: replayability (P1, P10) exists to make incidents diagnosable, not to satisfy an abstract correctness aesthetic · Predicts: any non-deterministic code path becomes the first place an on-call engineer gets stuck · Bug class avoided: shipping an "obviously fine" random tie-break that later makes a regression unreproducible · applies in §21.
  • MM3 — Backpressure Converts Overload Into Latency, Not Loss. Compressed insight: a bounded queue turns a burst into queuing delay; an unbounded queue turns it into an OOM · Predicts: the system degrades gracefully (slower) under load rather than catastrophically (crashing) · Bug class avoided: an unbounded channel that "worked in testing" because testing never generated a burst · applies in §12 and §20.
  • MM4 — Metadata Authority Makes Corruption Detectable. Compressed insight: if the metadata plane is trusted and the index is derived, any divergence between them is by definition a bug, not an ambiguity · Predicts: consistency scanners (I2) can run continuously without a human deciding what "correct" means each time · Bug class avoided: treating metadata/index disagreement as "eventually consistent, ignore it" · applies in §13 and §18.
  • MM5 — Tail Latency Is a Distribution, Not a Number. Compressed insight: p50 and p99 are answering different engineering questions (typical experience vs. worst-case budget) · Predicts: optimizing only p50 can make p99 worse (e.g. a cache that helps the common case but adds a miss penalty) · Bug class avoided: shipping a "faster on average" change that blows the p99 SLO · applies in §28.
  • MM6 — A Fixed Recall Floor Turns Silent Regressions Into Loud Ones. Compressed insight: recall is not self-evidently visible the way latency is — a system can be "working" (responding fast) while quietly returning worse results · Predicts: any recall regression without I11's floor check ships undetected until a user notices · Bug class avoided: judging retrieval health by latency dashboards alone · applies in §18 and §21.
  • MM7 — Two Independent Enforcement Points Beat One Correct One. Compressed insight: tenant isolation (I5) enforced only at the filter layer is one bug away from a leak; enforcing it redundantly at filter, routing, and cache makes a leak require simultaneous bugs in all three · Predicts: defense-in-depth costs a small constant overhead and buys a large reduction in single-point-of-failure risk · Bug class avoided: a single well-reviewed filter check being treated as sufficient · applies in §21.
  • MM8 — Derived State Should Never Outlive Its Source of Truth's Confidence. Compressed insight: an ANN graph or lexical index that has drifted from its metadata source should be rebuilt, not patched · Predicts: patch-in-place "fixes" for derived-state corruption tend to recur because they treat a symptom · Bug class avoided: a growing pile of one-off index patches instead of a trusted rebuild path · applies in §18 and §19.

32. Back-of-Envelope Capacity Model

  • C1 — WAL write bandwidth. 25,000 chunks/min × (768-dim fp32 vector = 3,072 B + 64 B header) = 25,000 × 3,136 B = 78.4 MB/min raw; × 2.5× WAL amplification (§4) = 196 MB/min = 3.27 MB/s sustained WAL write bandwidth, well inside SSD sequential-write throughput.
  • C2 — ANN resident RAM per shard. 10M vectors/shard × (3,072 B vector + 256 B HNSW neighbor overhead at M=16 × 2 links × 8 B) = 10M × 3,328 B = 33.3 GB/shard; × 70% ANN cache budget (§4) fitting inside the 220 GB ceiling supports ≤ 4 shards/node before eviction pressure.
  • C3 — Metadata cache coverage. 10 GB metadata cache (§4) ÷ ~2 KB/ChunkDescriptor row ≈ 5M cached rows = ~1 day of ingestion at the 5M chunks/day baseline (§4).
  • C4 — Retrieval concurrency (Little's Law). 500 QPS/node baseline (§4) × p95 180 ms (§4) = 90 concurrent in-flight queries typical; at p99 450 ms, 500 × 0.45 s = 225 in-flight worst-case per node, well inside the 2,000 concurrent-pipeline logical cap (§4) across a multi-node cluster.
  • C5 — Per-query transient memory. 225 worst-case concurrent queries (C4) × 64 MB per-query ceiling (§4) = 14.4 GB transient working set, ≈ 7% of the 220 GB ceiling outside the ANN cache.
  • C6 — File-descriptor budget. 2,000 concurrent pipelines (§4) × 32 FDs/query ceiling (§4) = 64,000 FDs, inside the 262,144 FD limit (§4) with room for the 8,192 mmap-segment budget on top.
  • C7 — Cluster node count. 10,000 QPS cluster target (§4) ÷ 500 QPS/node baseline (§4) = 20 retrieval nodes minimum; + 2 for rolling-upgrade headroom (P8) = 22 nodes provisioned.
  • C8 — Ingestion headroom. 5,000,000 chunks/day (§4) ÷ 86,400 s = 57.9 chunks/s sustained average; 25,000 chunks/min = 416.7 chunks/s embedding-throughput ceiling (§4) = 7.2× average-to-peak headroom.
  • C9 — Snapshot transfer time. 33.3 GB/shard (C2) × 4 shards/node (C2) = 133.2 GB snapshot size ÷ ~1.25 GB/s (10 Gbps replication link) = 107 s transfer time, inside the < 5 min shard-restart RTO (§4).
  • C10 — Compaction rewrite volume. 78.4 MB/min base growth (C1) × 3× compaction amplification (§4) = 235.2 MB/min rewritten during compaction windows, budgeted against SSD write endurance.
  • C11 — Availability error budgets. 99.95% retrieval SLO (§4) = 21.6 min/month; 99.5% ingestion SLO = 3.6 h/month; 99.0% evaluation SLO = 7.3 h/month — the evaluation plane deliberately absorbs the largest budget since it is offline.
  • C12 — Reranker throughput ceiling. 200 concurrent reranker requests/node (§4) × ~25 ms assumed cross-encoder batch latency = 200 ÷ 0.025 s = 8,000 rerank ops/s/node theoretical ceiling, gating the hybrid fanout width in §19.

34. Alternative Architectures (Roads Not Taken)

Alt A — External Vector Database Composition

 Ingestion Pipeline --> Embedding API --> External Vector DB (Pinecone/Weaviate-managed)
                                                 |
                                          Retrieval API (thin client)

Regime where it wins: small teams (< 3 engineers, ADR-05) or an MVP timeline under a month, where the cost of owning WAL/ANN correctness (§17–§18) outweighs the value of controlling it directly. Real system embodying it: Pinecone (fully managed, §31). Rejected here because §1.2 commits to owning the correctness kernel directly — this blueprint's entire value proposition (§2) is systems mastery over storage and ranking internals, which a managed external DB makes unnecessary and unobservable.

Alt B — Single-Node Embedded Index

 Application Process
   +-- embedded ANN index (in-process, no network hop)
   +-- embedded metadata store (SQLite-class)

Regime where it wins: single-tenant, single-node deployments where network-hop latency matters more than horizontal scale (§29) — e.g. a local developer tool or an air-gapped edge deployment. Real system embodying it: Chroma's local/embedded mode. Rejected here because §4's 10,000 QPS cluster target and multi-tenant isolation requirements (P11, I5) require the horizontal shard-routing and tenant-isolation layers this blueprint builds — a single-node embedded index has no shard-routing concept to isolate tenants at.

Alt C — GraphRAG-First Architecture

 Ingestion --> Entity/Relation Extraction --> Knowledge Graph Store --> Graph-Traversal Retrieval

Regime where it wins: corpora where relationships between entities matter more than raw semantic similarity — multi-hop reasoning over structured domain knowledge. Real system embodying it: Microsoft's GraphRAG. Rejected as the primary architecture here (though deferred as an add-on, PhaseDeferred("§20"), §35) because entity/relation extraction quality varies heavily by domain and would have made the Phase 0–9 correctness kernel (§17–§19) dependent on an unreliable extraction step rather than on deterministic chunking (I3) — the hybrid lexical+semantic baseline is a more defensible foundation to build the graph layer on top of later, not instead of.

36. Glossary

  • ANN — approximate nearest-neighbor retrieval; trades exactness for bounded latency.
  • BM25 — the probabilistic lexical-relevance scoring function used by the lexical index engine.
  • Canonicalization — the deterministic normalization process producing a Document's content hash.
  • Chunk — a deterministic retrieval fragment derived from a document's byte range.
  • Chunk lineage — the ancestry metadata linking a chunk back to its source document and hash.
  • Compaction — the background merge/cleanup process reclaiming space from tombstoned records.
  • Compaction amplification — the ratio of bytes rewritten during compaction to logical data size.
  • Correlation ID — see trace_id; the identifier propagated across every span for a request.
  • Cross-encoder — a reranker architecture scoring a query-document pair jointly, not independently.
  • Deadline budget — the per-query timeout allocated across the retrieval pipeline's stages.
  • Deterministic replay — re-executing a captured trace to reproduce identical output.
  • ef_search — the HNSW traversal-breadth parameter trading latency for recall.
  • EmbeddingVersion — the versioned identifier tying an embedding to its producing model/tokenizer.
  • Fanout plan — the per-shard execution plan produced by the retrieval planner.
  • Hinted handoff — Dynamo's technique for accepting writes during a temporary replica outage.
  • HNSW — Hierarchical Navigable Small World graph, the ANN index's graph structure.
  • Hybrid retrieval — combined lexical (BM25) and semantic (ANN) candidate retrieval.
  • Idempotency key — a deterministic key preventing duplicate effect from a retried operation.
  • Lease — a time-bounded ownership grant used by the scheduler for job assignment.
  • Metadata authority — the principle that the metadata plane, not any derived index, is ground truth.
  • Poison document — a malformed ingestion payload that would otherwise crash or hang a worker.
  • Postings list — the per-term list of document/chunk occurrences in the lexical index.
  • Prompt lineage — the provenance chain from an assembled prompt back to its source citations.
  • Quantization profile — the precision/compression scheme applied to a stored vector.
  • Recall@K — the fraction of true top-K relevant items actually retrieved.
  • Reciprocal Rank Fusion (RRF) — a rank-based method for merging heterogeneous ranked lists.
  • Replay fidelity — the property that replay reproduces identical output for deterministic input.
  • RPO — Recovery Point Objective; the maximum acceptable data loss window.
  • RTO — Recovery Time Objective; the maximum acceptable recovery duration.
  • Segment — an immutable unit of the lexical or vector index subject to compaction.
  • Shard — a partitioned unit of storage and query routing within a collection.
  • Snapshot — a checksummed, point-in-time persisted index state.
  • SPLADE — a learned sparse lexical expansion model, source of the deferred sparse-retrieval feature.
  • Tail latency — high-percentile (p95/p99/p999) request latency, tracked separately per stage.
  • Tenant isolation — the guarantee that no retrieval path returns cross-tenant candidates.
  • Tombstone — a deletion marker preventing a removed vector from reappearing after compaction.
  • Tombstone dominance — the invariant that tombstoned entries never resurface post-compaction.
  • top_k — the number of candidates requested from an ANN or lexical query.
  • Trace ID — the unique identifier propagated across every span of a single request.
  • WAL — Write-Ahead Log; the append-only durability mechanism preceding query visibility.
  • WAL amplification — the ratio of physical bytes written to logical bytes committed.
