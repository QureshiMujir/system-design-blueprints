In one paragraph

A retrieval-augmented generation (RAG) platform lets a language model answer from your own documents. It cuts documents into pieces, turns each piece into a list of numbers that captures its meaning, stores them, and at question time finds the best pieces and hands them to the model (§1). This blueprint builds that whole stack in Rust instead of wrapping a hosted vector database. It owns storage, indexing, ranking, scheduling and observability so each property can be verified (§1, ADR-05), and it records a replayable trace of every decision (§1). It runs on Kubernetes with a PostgreSQL metadata store (§1.4). Its roles are operators, application developers, platform engineers and ML engineers (§1.5).

The problem, concretely

The simple version is a chat loop that calls a hosted vector database and a hosted completion API (§2.1). It works in a demo. The blueprint's claim is that production AI systems degrade more often from retrieval-quality regressions than from limits of the model itself: stale embeddings, silent tokenizer drift, and metadata and vector stores that disagree (§2.2). Six ways the simple version fails, each answered by a rule the design adds:

  1. A tokenizer library is upgraded and nobody notices. An unpinned dependency changes how text is tokenized (FM-5). Without deterministic, replayable processing a ranking regression "cannot be distinguished from noise" (P1). The design catches it by a replay-hash mismatch (I3, FM-5).
  2. A crash lands in the middle of a write. A reader could see a vector that was never flushed to disk, and the crash then takes it away: the "dirty read of unfsynced data" that I1 prevents (I1). A partly written record can also look plausible but be corrupt (§17.6).
  3. One customer sends a burst. A single tenant's burst starves shared shard capacity for its neighbours (FM-6), so every tenant needs a bounded share (P7).
  4. A queue has no limit. A bounded queue turns a burst into waiting; an unbounded one turns it into an out-of-memory crash (MM3, FM-10).
  5. A deleted vector comes back. After compaction, a removed vector must never reappear (I9).
  6. The index and the catalog disagree. Without a single trusted record, a disagreement is ambiguous instead of a bug (MM4).

The targets that frame all of this are a retrieval p99 under 450 ms and a 10,000 QPS cluster target (§4).

The ingest path

  1. api-gateway terminates TLS, validates tokens, applies tenant quotas, enforces request-size budgets and injects a correlation ID. It is the first trust boundary (§3.2).
  2. ingest-gateway writes an upload manifest before processing begins and enqueues immutable jobs onto scheduler-runtime. It never mutates an index directly (§3.3, P3).
  3. document-normalizer detects the file type, fans out to OCR and converts everything into one canonical form. All later hashes derive from that form (§3.4).
  4. chunk-engine cuts the canonical text into tokenizer-aware pieces whose IDs come from document lineage plus byte range (§3.5, §8.1).
  5. embedding-orchestrator batches the chunks, calls the model providers with retry and idempotency, and records lineage. Swapping a provider never touches storage (§3.6).
  6. vector-storage-engine holds the write-ahead log, the ANN index, tombstones and snapshots (§3.10). metadata-plane (PostgreSQL) holds tenants, lineage, manifests and ACLs (§3.11). lexical-index-engine holds the inverted index (§3.9).

The query path. The blueprint's own lifecycle is one line (§8.2):

Client Request -> Query Validation -> Metadata Filter Compilation -> Lexical Query Planning
   -> ANN Candidate Retrieval -> Candidate Merge -> Reranking -> Context Assembly
   -> Prompt Generation -> Inference Dispatch -> Streaming Response
  1. retrieval-api owns the query lifecycle: planning, filter compilation, deadlines, cancellation. It is the only subsystem allowed to fan a query out to shards (§3.7).
  2. The Hybrid Retrieval Coordinator merges BM25 results, ANN matches, metadata filters and reranker candidates under a deterministic merge order (§3.8, I8). §1.1 lists no separate crate for it, and §19.2 builds the fusion while extending retrieval-api.
  3. rerank-service scores the merged candidates with a cross-encoder, and falls back to the hybrid ordering if it times out (§20.2).
  4. context-assembler removes duplicates, applies the token budget and generates citations (§3.12).
  5. inference-gateway hides the external model providers and streams the answer back (§3.13).

Beside the pipeline, replay-engine and evaluation-runner capture and diff traces (§3.14), and observability covers every stage (§3.15, P5). A request moves through these states: RECEIVED, VALIDATED, PLANNED, RETRIEVING, RERANKING, ASSEMBLING, INFERENCE, then COMPLETE or FAILED (§8.3).

The core ideas

One source of truth, everything else rebuildable (P12, MM4, I2)

The metadata plane is "the source of truth"; the ANN and lexical indexes are derived state that can always be rebuilt from it (P12, §3.11). That makes any disagreement between catalog and index a bug rather than an ambiguity, so a scanner can run continuously without anyone deciding what "correct" means (MM4, I2). A tiny example is the blueprint's fixture orphan-detection.sql: a vector reference with no matching chunk row must be flagged by the I2 scanner within one scan interval (§13.5). When a lexical or vector segment is corrupted, the repair is to rebuild it from the metadata plane (FM-7, §19.9).

The blueprint contradicts itself on what the authority is. P12 and §3.11 say the metadata plane. MM1 says "WAL Is Truth, Everything Else Is a View", and §18.9 says the graph is derived state (P12) and that "the WAL, not the graph, is authoritative" (MM1, §18.9). Q1 in §33 repeats the WAL reading while citing P12 (§33). The repair direction differs too: I2 recovers an orphan vector by re-deriving it from metadata or tombstoning it, while §13.6 recovers metadata drift by re-deriving from the vector store's own checksum manifest (I2, §13.6). This explainer does not pick one.

Same input, same IDs, same order (P1, I3, I8, §15, §16)

A chunk ID is a hash of the document ID and the chunk's byte range, never a counter, so identical canonical content always gives identical IDs whatever order work happens in (§8.1, §15.2, I3). The embedding step builds an idempotency key from the chunk ID and the embedding version, so a retried batch cannot embed twice (§16.2). The tokenizer is wrapped so that upgrading it is an explicit EmbeddingVersion bump, never a silent change (§15.2). A three-step trace:

  1. The same document arrives by two ingestion paths. Both produce the same chunk IDs, so they collapse into one storage write instead of two (§15.2).
  2. An embedding batch is retried after a provider error. The idempotency key is the same, so the vector is not duplicated (§16.2). The phase gate is zero duplicates after 50 injected retry storms (§16.4).
  3. A tokenizer library is bumped while EmbeddingVersion stays put. CI fails if the token-count checksum moves by even one token (§15.4).

On the query side, the replay CLI re-runs a captured trace and diffs it against a golden (§21.2, I8).

Nothing is visible before it is durable: the write-ahead log (I1, I4, I6, I9, §17)

A write-ahead log (WAL) is an append-only file that records each change before it is applied. Each record is length-prefixed and checksummed with CRC32C, and sequence numbers only increase (§17.2, ADR-10, I4). Appends are grouped so one fsync covers many records, with a maximum-batch-age timer keeping the delay bounded (§17.2). A vector becomes searchable only after its record is flushed (I1). The blueprint notes the grouping costs "a slightly wider durability window" (§17.7). A three-step recovery trace:

  1. The process is killed with kill -9 during a write burst (§17.3).
  2. On restart the shard replays from the last verified snapshot (§17.9). A file cut mid-record is recognised by length-prefix validation as a truncated tail, with no panic (§17.2, §17.5).
  3. A record with a failed checksum is reported as a typed error, skipped, and replay continues past it (§17.5). The shard ends in its last flushed state with no resurrected tombstones (§17.3).

Two details matter. Length and payload are written in one pwritev call so a torn write cannot leave a plausible-looking half record (§17.6). And the WAL is truncated only up to entries covered by a verified snapshot, with snapshots every 30 minutes (§17.2, §17.10). The gate is correct replay across 500 randomized kill-points (§17.4).

Finding neighbours in a graph (HNSW) and keeping it honest (ADR-23, I11, §18)

HNSW is a graph built in layers, where each stored vector links to nearby vectors and new nodes are assigned to layers at random (§36, §18.2). A search walks the graph greedily (§5), and the ef_search parameter sets how wide the walk is: wider means better recall but more latency (§36, §18.2). The default is M=16 links, and vectors are normalised at insertion time rather than at query time (§18.2). Deleted vectors are skipped during traversal (§18.2, I9).

The trap is that tombstoned nodes still occupy neighbour slots, so after many deletions live candidates get starved and recall collapses (FM-2, §18.6). The guard is a fixed-corpus recall floor, Recall@10 above 0.93, checked by evaluation-runner; crossing it triggers a background graph rebuild from the WAL (I11, §28 M7, §18.9). The size arithmetic is in the blueprint: 10M vectors per shard at 3,328 B each is 33.3 GB per shard (§32, C2).

From question to prompt: fuse, rerank, budget (I7, I8, §19, §20, §8.7)

Keyword (BM25) scores and vector-distance scores are on incomparable scales, so summing them gives "meaningless rankings" (§19.6). The design fuses by rank using reciprocal rank fusion (RRF), and the merge must be deterministic (§19.2, I8). Filters are compiled once per query and reused on every shard leg (§19.3). The reranker is limited to 200 concurrent requests per node, and on timeout the pipeline falls back to the hybrid order instead of blocking; if it fails mid-batch only the failed subset falls back (§4, §20.2, §20.8). Every query carries a deadline, and an expired pipeline must stop and cancel all shard legs (I7).

The context budget is the blueprint's worked example: a 16k-token model limit, 4k reserved for the completion, a 1k system prompt, and 11k left for retrieved text (§8.7). The assembler removes overlapping chunks and truncates oversized candidates by reranker-score priority, recording every truncation in the trace instead of dropping a citation silently (§8.7, §20.2). Its token count is an estimate against the chunk tokenizer, not the provider's (§20.8).

Three locks on every tenant's door (I5, I12, P7, P11, MM7)

I5 says no retrieval path may return another tenant's candidates, and it is enforced at three independent layers: metadata filtering, shard routing and cache partitioning (I5). The reasoning is that a single check is one bug from a leak, while three make a leak need simultaneous bugs (MM7). If a leak is detected the query fails closed with an immediate alert, and cross_tenant_candidate_total must always read 0 (I5). Isolation is verified by a fixture before any density optimisation ships (P11, §21.4). Quotas are enforced at admission and again at shard fan-out (§21.2, I12).

Three places where the blueprint does not line up. MM7's title says "Two Independent Enforcement Points" while its text and I5 say three layers (MM7, I5). §21.2 calls the quota checks "two independent enforcement points" and cites I5, and the §21.5 cross-tenant fixture expects rejection "at both enforcement layers (I5)", while I5 lists three layers (§21.2, §21.5, I5). And §13.9 says that if the metadata plane is down, retrieval may serve "metadata-filter-less" results if configured, although metadata filtering is one of I5's three layers (§13.9, I5).

The trade-offs — where engineers disagree

Build the storage engine yourself (ADR-05)

Chosen: a custom mmap append-only vector engine, for direct control of the WAL and mmap invariants in §7, which an external database cannot expose (§9). Rejected: an external vector database such as Milvus or pgvector (§9). When the rejected choice is right: a team of under 3 engineers, or an MVP timeline under one month (§9). The blueprint itself sizes Phase 0 at 3 to 6 engineers (§1.9).

HNSW graph versus compressed clusters (ADR-23)

Chosen: HNSW, for higher recall at the memory budget in §4 for the collection sizes targeted (§9). Rejected: IVF-PQ (§9). When the rejected choice is right: memory-constrained deployments beyond 1B vectors per collection, where PQ's smaller footprint outweighs HNSW's recall edge (§9). Q15 asks where the blueprint's own memory arithmetic reaches that regime (§33).

Own the inverted index (ADR-24)

Chosen: a custom inverted index, for deterministic ownership of the postings format and compaction cadence (§9, P1). Rejected: embedded Elasticsearch or Lucene (§9). When the rejected choice is right: a team already running Elasticsearch at scale that wants unified operations tooling over a bespoke engine (§9). §31 says the same of Elasticsearch (§31).

A binary WAL (ADR-10)

Chosen: a length-prefixed, checksummed binary log, for fsync efficiency and torn-write detection (§9, I1, §17.6). Rejected: a JSON WAL (§9). When the rejected choice is right: a low-volume audit log where human readability outweighs write throughput (§9).

Cooperative async, not actors (ADR-11)

Chosen: a cooperative async scheduler, because shared mutable index state such as the ANN graph does not map cleanly onto isolated actors (§9). Rejected: an actor framework in the Actix style (§9). When the rejected choice is right: workloads dominated by isolated stateful actors with no shared index to coordinate (§9). The runtime itself is Tokio, ADR-02 (§9, §1.7), though §4 labels it ADR-07, which is the RPC choice (§4, §9).

Roads not taken

External vector database composition (§34 Alt A) wins for small teams under 3 engineers or an MVP under a month, where owning WAL and ANN correctness costs more than it returns (§34, ADR-05). Pinecone embodies it (§34). It loses here because §1.2 commits to owning the correctness kernel (§34).

Single-node embedded index (§34 Alt B) wins for single-tenant, single-node cases where a network hop matters more than scale, such as a local developer tool or an air-gapped edge deployment; Chroma's embedded mode is the example (§34). It loses here because the 10,000 QPS target and tenant isolation need shard routing (§4, P11, I5, §34).

GraphRAG-first (§34 Alt C) wins on corpora where relationships between entities matter more than raw similarity, as in multi-hop reasoning; Microsoft's GraphRAG is the example (§34). It is rejected as the base because extraction quality varies by domain and would make the correctness kernel depend on an unreliable step (I3, §34). It is deferred, not abandoned (§35).

The deferred register (§35) holds five features, each with a trigger: multimodal embeddings once more than 20% of a corpus is non-text; GPU or FPGA ANN search once the ANN p95 target cannot be met by CPU SIMD (M4); learned sparse retrieval (SPLADE) once BM25 recall plateaus; GraphRAG once a corpus shows multi-hop wins in evaluation; and online active learning for reranking once feedback volume allows it without breaking P1.

What must never be false

Each line gives the invariant, how the system notices a violation, and the metric (all from §7).

  • I1: nothing is searchable before its WAL record is flushed. Replay checksum divergence; wal_seq_gap_total.
  • I2: every vector points at valid metadata lineage. Orphan-vector sweep; orphan_vectors_total.
  • I3: identical canonical content gives identical chunk IDs. Replay hash mismatch; chunk_hash_mismatch_total.
  • I4: sequence IDs never go backwards in a shard. Monotonicity assertion on append; wal_seq_regression_total.
  • I5: no cross-tenant candidates. Tenant-mismatch assertion; cross_tenant_candidate_total (must be 0).
  • I6: snapshots are atomic states. Checksum and WAL-continuity checks; snapshot_checksum_fail_total.
  • I7: an expired query stops within its deadline budget. Deadline-overrun counter; deadline_overrun_total.
  • I8: the same inputs replay to the same candidate order. Ordering diff; replay_order_mismatch_total.
  • I9: deleted vectors never return after compaction. Tombstone audit; tombstone_resurrection_total (must be 0).
  • I10: old readers survive additive schema fields. Compatibility test in CI; schema_compat_check_fail_total.
  • I11: recall never drops below the verified floor. Recall-vs-baseline delta; recall_regression_delta.
  • I12: tenant usage stays within quota at every enforcement point. Quota rejection counter; quota_reject_total.
  • I13: every span carries a non-empty trace_id. Missing-trace-id linter; span_missing_trace_id_total.

What breaks in production

FM-1: WAL replay fails on shard restart. The cause is a torn write, disk corruption or a truncated tail. It is detected as a checksum mismatch during replay (I1). Automatic recovery skips the corrupted record and resumes past it; manually, restore the shard from the last verified snapshot, and use replay-engine to reconstruct the write sequence up to the corruption (§23).

FM-2: ANN recall collapses on a shard. The cause is graph degeneration from unbounded tombstone buildup. It is detected when the recall-regression metric crosses its floor (I11). A scheduled background rebuild is the automatic fix; if the floor is breached by more than 10 points, force a rebuild immediately (§23).

FM-5: tokenizer drift. An unpinned dependency upgrade changes tokenization. Detection is a replay-hash mismatch (I3) or a tokenizer compatibility-test failure. There is no automatic recovery, because it needs human review; pin the version and re-chunk and re-embed the affected range (§23).

FM-6: a noisy neighbour. One tenant's burst starves shared shard capacity. Symptoms are elevated p99 for co-located tenants and a rising quota-reject counter. Tenant-local throttling engages by itself (P7); if it is too aggressive, adjust the quota policy by hand (§23).

FM-9: split-brain during shard recovery. Two recovery processes race to claim one shard lease. The scheduler's lease table detects the conflict, the loser backs off and retries, and a repeated race goes to manual lease-table inspection (§23).

FM-10: cascading queue collapse. An unbounded queue slipped past review, a violation of P2. The queue-depth gauge trends upward without limit. There is no automatic recovery, because it is a design defect; hotfix the bound and redeploy (§23). P2 itself points at FM-6 for this failure, not FM-10 (P2, §23).

The threats worth knowing (§22):

  • T1, a parser-bomb document with deeply nested markup or archives, is met with recursion limits and parser timeouts, then quarantine of the document (§22).
  • T5, prompt injection through retrieved text, is mitigated by provenance tagging on every citation and output-redaction hooks. The blueprint says it is mitigated, not eliminated, with no automatic detection (§22).
  • T6, cross-tenant leakage through a bug in filtering or routing, is met by the three layers of I5, and the system fails closed (§22, I5). §33 Q13 observes that §23 has no failure-mode row for it (§33).
  • T7, an oversized top_k that amplifies ANN traversal into a denial of service, is rejected at admission and never reaches shard fan-out (§22).

How it compares

  • Milvus splits query nodes from data nodes with an external metadata store, and offers HNSW or IVF-PQ. That wins in GPU-accelerated bulk similarity search where query and storage scaling needs diverge sharply (§31).
  • Weaviate embeds the object store and the inverted index in one process with GraphQL-style filters. That wins when developer ergonomics beat a split architecture and one binary is preferred (§31).
  • Vespa unifies content storage and a general rank-expression language in one node (proton). That wins when ranking logic must be customisable per query beyond fixed BM25 plus ANN fusion (§31).
  • Elasticsearch is a mature JVM inverted-index engine with ANN added later by plugin. It wins when an organisation already runs it at scale and wants one set of operational tools, which is exactly ADR-24's rejected regime (§31, ADR-24).
  • Pinecone is fully managed with opaque internals. It wins for teams that want to hand storage and indexing off entirely, which is the regime ADR-05 rejects for this project (§31, ADR-05).

  3. §6's P9 (storage correctness before ANN acceleration) gates §18 on §17's exit criteria — but §18.2 says HNSW lives inside vector-storage-engine, not a separate crate; does that make P9's phase gate enforceable in code, or only in process discipline? — Hint: P9 in §6, §17.4 and §18.2.
  4. §22's T6 (cross-tenant leakage) and §7's I5 name the same failure — why does §23 not list a corresponding FM-# row, and should it? — Hint: T6 in §22, I5 in §7 and the table in §23.
  5. §18's tombstone-skipping traversal and §17's WAL truncation policy both reference "covered by a verified snapshot" — could a tombstone be truncated from the WAL before the ANN graph has actually applied it during a slow rebuild, and what would §23's forensics reveal if so? — Hint: §17.2's truncation rule, §18.2's tombstone skipping and I9.

If you only remember three things

Nothing becomes visible before it is durable, and anything derived can be rebuilt from something durable (I1, P12, MM1). The same input must give the same IDs, the same order and the same prompt, so a ranking regression can be replayed instead of guessed at (P1, I3, I8, P10). Every queue, buffer, tenant and wait has a bound, and tenant isolation is checked in three places, not one (P2, P7, I5, MM7).

Words used here

  • WAL: a write-ahead log, the append-only record kept before a change becomes visible (§36).
  • Tombstone: a marker that stops a deleted vector reappearing after compaction (§36).
  • HNSW: a layered graph of nearby vectors used to find approximate nearest neighbours (§36).
  • ef_search: how wide the graph walk is; wider trades latency for recall (§36).
  • Recall@K: the share of the true top K results that were actually retrieved (§36).
  • BM25: the keyword-relevance score used by the lexical index (§36).
  • RRF: reciprocal rank fusion, a way to merge ranked lists by position (§36).
  • Cross-encoder: a reranker that scores a query and a document together (§36).
  • Shard: a partition of storage and query routing within a collection (§36).
  • EmbeddingVersion: the version tag linking an embedding to its model and tokenizer (§36).
  • Metadata authority: the principle that the metadata plane, not an index, is ground truth (§36, P12).
