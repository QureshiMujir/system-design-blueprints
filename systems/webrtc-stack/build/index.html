⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the Cargo workspace (§10), CI matrix (ADR-19), and the correctness kernel: rtc-verifier's deterministic simulator plus the shared fuzz harness scaffolding (rtc-fuzz) that every later phase's parser plugs into (P13). No protocol logic yet — this phase proves the process (build, test, fuzz, bench, conformance-bucket runner) works end to end before any wire format is implemented.

Deliverable

cargo build --all-targets green on the 3-OS matrix; conformance/cli run --all executes zero buckets (none populated yet) and reports "0/0 PASS" without erroring; rtc-verifier's SimulatedNetwork unit-tested standalone.

Acceptance

Cold workspace build < 120 s (§4 startup budget analogue); cargo build --all-targets exits 0 on linux/mac/windows; SimulatedNetwork fixture sim_loss_10pct.toml produces a measured loss rate within ±1% of the configured 10% over 10,000 synthetic packets.

Fixtures
Fixture Purpose Expected Output
sim_loss_10pct.toml validate loss injection accuracy measured loss 9–11%
sim_jitter_30ms.toml validate jitter injection stddev of delay within 5 ms of 30 ms target
ci_matrix_smoke.yml validate CI matrix runs all 3 OSes 3/3 green
Pitfalls
  • Workspace-wide cargo fuzz requires nightly; pin a nightly toolchain file (rust-toolchain.toml) so stable and fuzz jobs don't drift (ADR-22).
  • An empty conformance bucket silently reporting "0/0 PASS" can mask a runner bug; the CLI must distinguish "no buckets found" (error) from "buckets found, 0 tests" (warn).
  • Cross-platform UDP socket options (SO_REUSEPORT semantics differ mac/linux) bite later phases if not abstracted now.

⬜ Phase 1 — STUN Protocol Codec §13

Objectives

Implement the STUN message codec (rtc-stun, RFC 8489) — encode/decode of the 20-byte header, TLV attributes, MESSAGE-INTEGRITY, and FINGERPRINT — as the foundation both ICE connectivity checks (Phase 4) and TURN (Phase 3) build on.

Deliverable

rtc-stun library passing RFC 8489 Appendix B test vectors; fuzz_stun_decode running continuously in CI (60 s smoke, nightly 8 h extended per §26).

Acceptance

100% of RFC 8489 Appendix B test vectors byte-match; encode/decode round-trip < 500 ns p99 (single-threaded, no allocation on the decode hot path per P11); zero panics across 1M fuzz iterations of fuzz_stun_decode (M10 basis).

Fixtures
Fixture Purpose Expected Output
stun_rfc8489_vectors.bin RFC Appendix B vectors byte-exact decode
stun_truncated_len.bin malformed: length exceeds datagram StunDecodeError::TruncatedAttribute, no panic (§8.2)
stun_bad_integrity.bin MESSAGE-INTEGRITY mismatch rejected, IntegrityError (P5)
stun_replay_fingerprint.bin regression: FINGERPRINT XOR const decode succeeds, matches vector
Pitfalls
  • Attribute padding to 4-byte multiples must exclude the pad bytes from the value length but include them in the overall message length — an easy off-by-one.
  • MESSAGE-INTEGRITY is computed with a placeholder message length that includes the MESSAGE-INTEGRITY attribute's own length, before FINGERPRINT is appended.
  • XOR-MAPPED-ADDRESS for IPv6 XORs the full 128 bits against cookie‖transaction-ID, not just the cookie — a common interop bug against naive implementations.

⬜ Phase 2 — ICE Candidate Gathering §14

Objectives

Implement candidate gathering (rtc-ice): host candidates from local interfaces, server-reflexive via STUN Binding Requests, relayed via the TURN client stub (full TURN client lands Phase 3; this phase gathers relay candidates via a minimal allocate-only path). Establishes I9's priority computation.

Deliverable

IceAgent::gather() produces a Vec<LocalCandidate> (host+srflx) emitted incrementally via a trickle callback; rtc-verifier scenario gather_behind_nat demonstrates srflx candidate differs from host candidate under a simulated NAT.

Acceptance

Gathering completes ≤ 300 ms p95 against 2 STUN servers at 100 ms RTT each queried in parallel (§32 CM8 basis, contributes to M1's 3,000 ms ICE-connect budget); priority values match RFC 8445 5.1.2.1 reference table for all 4 candidate kinds; trickle callback fires within 10 ms of each candidate's availability.

Fixtures
Fixture Purpose Expected Output
gather_single_interface.toml one NIC, one STUN server 1 host + 1 srflx candidate
gather_multi_interface.toml 3 NICs 3 host candidates, foundations distinct
gather_stun_timeout.toml STUN server unreachable srflx omitted, host-only after 5 s timeout
gather_priority_table.toml regression vs RFC 8445 5.1.2.1 exact priority match, all 4 kinds
Pitfalls
  • Link-local IPv6 addresses must carry a scope ID or connectivity checks silently fail later (Phase 4) with no useful error at gather time.
  • STUN retransmission timing for gathering (RTO doubling, RFC 8489 7.2.1) must not block Trickle emission of already-gathered candidates (P3).
  • Foundation computation (RFC 8445 5.1.1.3) must be stable across a session or pair freezing/unfreezing (Phase 4) misbehaves.

⬜ Phase 3 — TURN Relay Client §15

Objectives

Implement the full TURN client (rtc-turn, RFC 8656): allocation lifecycle, permissions, ChannelBind/ChannelData, and refresh — completing the relay-candidate path Phase 2 stubbed.

Deliverable

rtc-turn::TurnClient allocates against a live coturn instance (docker-compose, §10) and relays a synthetic UDP payload end-to-end in the conformance bucket.

Acceptance

Allocate completes in 1 RTT p95 (§4); refresh fires at 480 s for a 600 s lifetime (80%, I13) with 0 missed refreshes over a 6 h soak; ChannelData overhead measured at exactly 4 bytes vs 36+ for a full Send Indication.

Fixtures
Fixture Purpose Expected Output
turn_allocate_coturn.toml live allocate against coturn XOR-RELAYED-ADDRESS returned
turn_refresh_cycle.toml 6 h soak, 600 s lifetime refresh at 480s, 960s, ... no gaps
turn_permission_denied.bin relay to non-permitted peer dropped server-side, no client crash
turn_channelbind_vs_send.toml overhead comparison ChannelData 4 B header confirmed
Pitfalls
  • A missed refresh silently drops the relay mid-call; the 80%-lifetime pre-emptive refresh (I13) must tolerate one dropped refresh response via retry, not just fire-once.
  • Long-term credential NONCE can expire server-side (stale nonce error 438); client must retry with the fresh nonce from the error response, not fail permanently.
  • ChannelBind requires an active permission to the same peer; binding before CreatePermission succeeds is a spec violation some servers silently accept and others reject — always sequence Permission before ChannelBind.

⬜ Phase 4 — ICE Connectivity Checks & Nomination §16

Objectives

Complete the ICE agent (§8.2 state table): candidate pairing, priority-ordered connectivity checks, frozen/waiting/in-progress scheduling, role-conflict resolution, and nomination — the piece that actually selects the (local,remote) pair media flows over.

Deliverable

IceAgent drives a full P2P connectivity-check cycle against a second in-process agent (loopback, rtc-verifier scenario ice_full_handshake) and against a browser (Chrome headless) in the interop bucket, ending in IceState::Completed.

Acceptance

ICE connect time ≤ 3,000 ms p95 against 2 STUN + 1 TURN server at 100 ms RTT (M1, §4); role-conflict resolution completes within 1 additional RTT when both peers start Controlling; 0 invariant-I1 violations across 10,000 rtc-verifier simulated sessions with 0–20% induced loss.

Fixtures
Fixture Purpose Expected Output
ice_full_handshake.toml loopback P2P full cycle reaches Completed, selected_pair set
ice_role_conflict.toml both agents start Controlling tie-breaker resolves, 1 agent switches
ice_symmetric_nat_no_turn.toml no relay, symmetric NAT both sides IceState::Failed at 10 s timeout (§8.2 failure path)
ice_triggered_check.bin inbound check from unlisted pair pair added, responded immediately
interop_chrome_headless.toml real-browser interop Completed within M1 budget
Pitfalls
  • Regular nomination requires waiting for the check list to "settle" — nominate too early and a higher-priority pair that later succeeds is ignored, violating I9's intent.
  • Frozen-pair unfreezing logic (RFC 8445 6.1.2.6) is the single most error-prone part of ICE; a bug here manifests as "sometimes connects, sometimes doesn't" flakiness.
  • Triggered checks must not bypass I1 — an inbound Binding Request response confirms only one direction; the pair still needs the reverse check to be marked Succeeded.
  • STUN retransmission (Phase 1's RTO doubling) interacting with the 50 ms pacing timer can starve later-priority pairs if not bounded.

⬜ Phase 5 — DTLS Handshake Over UDP §17

Objectives

Implement DTLS framing over UDP (rtc-dtls, RFC 9147 primary / RFC 6347 (DTLS 1.2) fallback, ADR-05) on top of rustls's record-layer primitives (ADR-06): fragmentation, retransmission, and the certificate-fingerprint trust anchor (I8).

Deliverable

DtlsConnection completes a full handshake over a lossy simulated UDP channel (rtc-verifier scenario dtls_handshake_10pct_loss) and against a real Chrome peer in the interop bucket, reaching DtlsHandshakeState::Established.

Acceptance

Handshake completes in ≤ 2 RTT p95 at 0% loss, ≤ 4 RTT p95 at 10% induced loss (M2, §4); 100% of fingerprint-mismatch fixtures result in connection teardown, 0 established sessions; retransmission timer backoff verified at 1 s, 2 s, 4 s (capped 60 s per §4 SCTP-RTO-consistent ceiling) across 3 induced-loss iterations.

Fixtures
Fixture Purpose Expected Output
dtls_handshake_0pct_loss.toml clean handshake Established in 1 RTT
dtls_handshake_10pct_loss.toml lossy handshake Established in ≤ 4 RTT via retransmit
dtls_fingerprint_mismatch.toml wrong cert vs SDP fingerprint teardown, FingerprintMismatch (I8)
dtls_fragmented_certificate.bin large cert requiring fragmentation reassembled correctly
interop_chrome_dtls13.toml real-browser DTLS 1.3 interop Established, profile negotiated
Pitfalls
  • DTLS 1.3's ConnectionID extension changes epoch/sequence semantics vs 1.2 — do not reuse 1.2 anti-replay logic unchanged (ADR-05 fallback path needs its own tests).
  • Retransmission timer interacting with ICE consent-freshness checks (STUN keepalive, Phase 4) can double-send if not coordinated on the same clock source (ADR-23).
  • Certificate fingerprint comparison must be constant-time to avoid a timing side channel, even though WebRTC's threat model already assumes the fingerprint is public (defense in depth, §22 T3).

⬜ Phase 6 — DTLS-SRTP Key Export & SRTP/SRTCP §18

Objectives

Implement the DTLS exporter key derivation (rtc-srtp, RFC 5764 4.2) and the SRTP/SRTCP authenticated-encryption path (RFC 3711) — the layer that turns the DTLS session into per-packet media protection.

Deliverable

rtc-srtp::encrypt/decrypt round-trips against RFC 3711 test vectors; full DTLS-handshake-to-first-encrypted-RTP-packet pipeline demonstrated in rtc-verifier scenario key_export_to_first_packet.

Acceptance

Encrypt+decrypt of a 200-byte payload ≤ 2 µs p99 with AES-NI (M3, §4); key derivation ≤ 100 µs; 100% RFC 3711 Appendix B test-vector match; 0 packets accepted outside the 64-packet replay window across 1,000 out-of-order-injection fuzz iterations (I3).

Fixtures
Fixture Purpose Expected Output
srtp_rfc3711_vectors.bin RFC test vectors byte-exact encrypt/decrypt
srtp_replay_window.toml out-of-order + duplicate injection duplicates dropped, in-window accepted (I3)
srtp_wrong_export_label.bin regression: mistyped exporter label divergent keys, 100% auth-tag failure (§8.3)
srtp_seq_wrap.toml sequence number wraps past 65535 ROC increments, no replay false-positive
srtcp_encrypt_decrypt.bin SRTCP variant round-trips correctly
Pitfalls
  • AES-GCM nonce reuse is catastrophic (full plaintext recovery); the SSRC-derived nonce construction must be verified never to repeat within a session (P5, ADR-07).
  • The exporter label typo class of bug (§8.3) produces no crash and no error — every symptom is downstream auth-tag failure, making root-cause discovery slow without the srtp_wrong_export_label.bin regression fixture pinned in CI.
  • ROC increment timing: it must increment exactly once per sequence-number wrap, not once per packet near the wrap boundary — an off-by-one here silently corrupts the nonce for every subsequent packet.

⬜ Phase 7 — RTP/RTCP Media Transport & Jitter Buffer §19

Objectives

Implement the RTP packetizer/depacketizer (rtc-rtp, RFC 3550), RTCP SR/RR/SDES/BYE generation, and the adaptive jitter buffer that reorders packets into presentation order (I10) — the layer that turns encrypted packets into playable media frames.

Deliverable

End-to-end Opus audio flows through packetize → jitter-buffer → depacketize in rtc-verifier scenario audio_e2e_30ms_jitter, measuring one-way latency against M4.

Acceptance

One-way audio latency (capture-equivalent to playout-equivalent in the simulator) ≤ 150 ms p95 under 30 ms network jitter (M4, §4); jitter-buffer steady-state depth ≤ 60 ms p50, ≤ 150 ms p99 (M5); 0 I10 violations (out-of-order emission) across 10,000 simulated packets with 30% reordering.

Fixtures
Fixture Purpose Expected Output
audio_e2e_30ms_jitter.toml full pipeline latency ≤ 150 ms p95 (M4)
jitter_buffer_depth_adaptive.toml depth tracks measured jitter converges to 60 ms ± 10 ms (M5)
rtp_csrc_overrun.bin malformed CSRC count vs payload RtpDecodeError::TruncatedCsrc, no panic (§8.4)
rtcp_sr_rr_roundtrip.bin SR/RR generation + parse byte-exact round trip
jitter_buffer_reorder_30pct.toml 30% packet reordering I10 holds, 0 out-of-order emissions
Pitfalls
  • RTP timestamp clock rate differs per codec (48 kHz Opus vs 90 kHz VP8); a jitter buffer that assumes a single clock rate across streams corrupts inter-stream sync.
  • The jitter estimator's EWMA (RFC 3550 6.4.1) reacts slowly to sudden jitter spikes (network path change); pairs with the §20 GCC trendline filter for faster reaction.
  • Growing the jitter buffer to absorb jitter directly increases latency (Pa4/Pa5's bufferbloat lesson) — depth must be capped at 300 ms (§4) even under sustained jitter.

⬜ Phase 8 — Loss Recovery & GCC Congestion Control §20

Objectives

Implement RTCP feedback (NACK/PLI/FIR, RFC 4585/5104), FEC, and the GCC sender-side bandwidth estimator (rtc-gcc, ADR-09, Pa1) — closing the adaptive-bitrate loop sketched in §8.4.

Deliverable

rtc-gcc::CongestionController converges to within ±20% of a simulated available bandwidth in rtc-verifier scenario gcc_convergence_step_change under a stepped bandwidth profile (1 Mbps → 500 kbps → 2 Mbps).

Acceptance

Convergence to ±20% of true available bandwidth ≤ 5 s after a step change (M6, §4); FEC recovers ≥ 95% of single-packet losses at 10% random loss with 0 added latency (M7); NACK retry ceiling enforced at exactly 2 retries per lost sequence number (I11) verified across 500 induced-loss iterations.

Fixtures
Fixture Purpose Expected Output
gcc_convergence_step_change.toml bandwidth step 1M→500k→2M ±20% within 5 s each step (M6)
fec_10pct_loss_recovery.toml 10% random loss, FEC on ≥ 95% single-packet recovery (M7)
nack_retry_ceiling.toml sustained loss of one seq num exactly 2 retries then give up (I11)
pli_keyframe_request.bin undecodable video frame PLI sent, keyframe requested
gcc_feedback_timeout.toml TWCC feedback stops arriving fallback to loss-based, then freeze (§8.4 failure path)
Pitfalls
  • Aggressive NACK without I11's ceiling amplifies congestion under already-lossy conditions — the original draft's pitfall #6 (excessive NACKs amplify congestion).
  • GCC's trendline filter has many tunable parameters (Pa2); under-tuning causes slow convergence (fails M6), over-tuning causes rate "flapping" that visibly stutters video.
  • FEC's parity window trades recovery rate against bandwidth overhead (10–30%, a well-documented WebRTC FEC/RTX tradeoff) — sizing it without reference to the current GCC estimate risks the FEC overhead itself triggering the overuse detector it's meant to protect against.

⬜ Phase 9 — SCTP Data Channel & Peer-Connection State Machine §21

Objectives

Implement SCTP-over-DTLS (rtc-sctp, RFC 4960 WebRTC subset + RFC 8261), the DataChannel API with DCEP (RFC 8832), and complete the PeerConnection FSM (rtc-core, I12) tying every prior phase's layer into the W3C-enumerated connection lifecycle.

Deliverable

A DataChannel opens, exchanges reliable-ordered and unreliable-unordered messages, and closes gracefully over the same DTLS connection as an active audio stream, in rtc-verifier scenario datachannel_concurrent_with_media; full offer/answer/renegotiate cycle demonstrated against aiortc in the interop bucket.

Acceptance

DataChannel throughput ≥ 50 Mbps on loopback, message latency ≤ 20 ms p95 (M8, §4); graceful SCTP shutdown (SHUTDOWN/SHUTDOWN-ACK) completes ≤ 250 ms (§4); 0 I5 violations (TSN gap) across 10,000 simulated messages under 5% induced loss; PeerConnection never observed in a non-enumerated state (I12) across the full interop bucket.

Fixtures
Fixture Purpose Expected Output
sctp_four_way_handshake.bin association establishment reaches Established (§8.5)
datachannel_concurrent_with_media.toml DC + audio simultaneously media latency (M4) unaffected by DC load (P6)
dcep_bad_type.bin malformed DCEP channel-type byte stream reset (RFC 6525), not association abort (§8.5)
sctp_path_failure_abort.toml 5 consecutive RTO expiries association aborts, PathFailure, media unaffected
pc_renegotiation_add_video.toml add video m-line mid-call I14 holds, new m-line appended not reordered
interop_aiortc_datachannel.toml real cross-implementation DC messages exchanged both directions, 0 loss (reliable mode)
Pitfalls
  • SCTP's own retransmission timer and DTLS's replay/record-loss handling can both retransmit the same logical data, producing application-visible duplicates if the SCTP layer doesn't dedupe by TSN (I5) — the original draft's pitfall #4 in miniature.
  • A PeerConnection observing a DTLS failure must not jump straight to Closed; I12 requires transitioning through Failed first so the application can distinguish "never connected" from "was connected, then died."
  • DCEP races: both peers opening a data channel with the same negotiated stream ID simultaneously (original draft's "DCEP race" pitfall #10) — resolved by even/odd stream-ID parity keyed on DTLS role (client picks even, server picks odd, RFC 8832 6).
