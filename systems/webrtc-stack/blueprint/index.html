161 — WebRTC Stack

Project Number: 161

Project Name: WebRTC Stack

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Definition. Build a from-scratch, memory-safe WebRTC peer-connection stack in Rust that establishes NAT-traversed, encrypted, real-time audio/video/data sessions between two or more endpoints: SDP offer/answer negotiation (RFC 4566, RFC 8829 JSEP), ICE connectivity establishment with STUN/TURN (RFC 8445, RFC 8489, RFC 8656), a DTLS handshake that exports SRTP keys (RFC 9147, RFC 5764), SRTP/SRTCP media encryption (RFC 3711), an RTP/RTCP transport layer with a jitter buffer and NACK/PLI/FIR/FEC loss recovery (RFC 3550, RFC 4585, RFC 5104), Google Congestion Control bandwidth estimation (GCC/transport-cc), and an SCTP-over-DTLS reliable/unreliable data channel (RFC 8831, RFC 8261, RFC 4960). The system is a library + reference binary, not a browser: it implements the wire protocols an implementation team can embed in a native app, an SFU, or a headless test harness.

Phase-0 deliverable — numbered modules (crates):

  1. rtc-core — PeerConnection, RtcConfiguration, session orchestration.
  2. rtc-stun — STUN message codec (RFC 8489).
  3. rtc-ice — ICE agent: gathering, pairing, checks, nomination (RFC 8445).
  4. rtc-mux — single-UDP-port demultiplexer (RFC 7983).
  5. rtc-dtls — DTLS 1.3/1.2 handshake framing over UDP (RFC 9147).
  6. rtc-srtp — SRTP/SRTCP encrypt/decrypt + key export (RFC 3711, RFC 5764).
  7. rtc-rtp — RTP/RTCP packetizer, jitter buffer (RFC 3550).
  8. rtc-verifier — deterministic simulator exercising every invariant (§7).

System boundaries.

  • Provides: ICE/STUN/TURN client, DTLS-SRTP session security, SRTP/SRTCP media crypto, RTP/RTCP transport with jitter buffering and loss recovery, GCC bandwidth estimation, SCTP-over-DTLS data channels, SDP offer/answer + JSEP state machine, conformance/differential/fuzz harnesses.
  • Delegates: raw TLS/DTLS record cryptography to rustls; codec bitstreams to opus/libvpx/openh264 FFI wrappers (encode/decode only, not RTP framing); a TURN server to coturn (we ship the client only, ADR-14); browser UI/capture/render.
  • Does NOT provide: a SIP/signaling server (transport-agnostic signaling only), a media server topology (SFU forwarding logic is a downstream consumer of this stack, not built here), video encoding/decoding implementations (wrapped, not written).

Non-goals. Not a drop-in libwebrtc replacement for browsers (no JS bindings in Phase 0–9); not a WebAssembly target (deferred, PhaseDeferred("§35")); not a multi-homed SCTP implementation (PhaseDeferred("§35")); not H.265/AV1 codec support in the initial phases (PhaseDeferred("§35")).

Deployment model. A statically-linked Rust binary or library embedded in: (a) a native P2P calling app, (b) a headless SFU forwarding process (ICE-Lite mode, host-only candidate gathering per §14, §15), (c) a conformance/interop test harness run in CI against real browsers. Target users: systems engineers building real-time communication products; operators running SFU fleets who need getStats()-equivalent telemetry.

Language + rationale (ADR-01). Rust 1.78+ MSRV. Rationale: the attack surface is almost entirely untrusted-network parsers (STUN, DTLS, RTP, SCTP, SDP) where a single out-of-bounds read is a remote compromise; Rust's ownership model eliminates that class without sacrificing the zero-copy performance real-time media needs. Rejected: C++ (libwebrtc's choice — mature ecosystem, but a documented history of memory-safety CVEs, §22 T1); Go (Pion's choice — memory-safe, but GC pauses of 1–10 ms conflict with the sub-millisecond SRTP/RTP hot path, M3/M4).

Prerequisites. UDP/IP networking fundamentals, NAT/firewall behavior, public-key cryptography (X.509, ECDHE), state-machine design, familiarity with real-time systems (jitter, RTT, tail latency).

Estimated timeline. Phase 0 (repo skeleton + correctness kernel): 2 weeks. Full system (Phases 0–9, conformance + differential + 24 h fuzz canary): 11 months.

Deferred features (registered in full at §35, each anchor resolves): PhaseDeferred("§35") for: simulcast/SVC, E2EE insertable streams, AV1/H.265 codecs, hardware codec offload, MLS group-call security, QUIC/WebTransport datagram transport, ICE-TCP candidates (RFC 8839 TCP), SCTP multi-homing, extended RTCP reports (RTCP XR).

2. Why Build This

Unique systems knowledge. WebRTC is the canonical example of composed real-time protocols under adversarial network conditions: NAT traversal (ICE), key exchange over an unreliable transport (DTLS-over-UDP), authenticated encryption at wire-speed (SRTP), adaptive transport (RTP/RTCP + GCC), and a reliable/unreliable multiplexed channel (SCTP) — all sharing one UDP 5-tuple. No other system teaches NAT traversal, real-time congestion control, and datagram-transport security in one coherent stack.

Why it matters architecturally. The dominant failure mode in production WebRTC deployments is not "the crypto is broken" — it is architectural coupling: teams that fuse the ICE state machine with the DTLS handshake, or the RTP packetizer with the codec, cannot ship a custom congestion controller or a hand-tuned SFU without a rewrite. libwebrtc, Pion, mediasoup, and str0m each earned their production trust by keeping ICE ⊥ DTLS ⊥ SRTP ⊥ RTP ⊥ codec (P1) — a structural guarantee, not a coding convention.

Engineering muscles built. Table-driven state machines under partial/adversarial input (§8.2, §8.5); zero-copy wire-format parsing with fuzz-verified safety (§14, P13); sender-side bandwidth estimation from noisy one-way-delay signal (§20); reliable multiplexed messaging on top of an unreliable transport (§21).

Cross-links to sibling systems. Shares its jitter-buffer/backpressure problem with any streaming-media pipeline (RTMP/HLS packagers); shares its NAT-traversal problem with any P2P overlay (BitTorrent DHT, libp2p); shares its congestion-control problem with any custom transport (QUIC congestion controllers, TCP BBR).

Calibration value. A team that has built this stack can read libwebrtc's p2p/base/p2p_transport_channel.cc or Pion's icetransport.go and immediately locate the ICE state machine, because they built the same state machine from RFC 8445 6.1.2 directly.

What Mastery Looks Like

  • Can trace a single audio frame from microphone capture to the remote decoder, naming every header added, key derived, and state transition crossed (§8, §19).
  • Can explain why GCC moved bandwidth estimation from receiver (REMB) to sender (TWCC) and defend the RTCP-overhead tradeoff with numbers (§20, Pa1, Pa9).
  • Can debug a "call won't connect" incident using only ICE candidate-pair telemetry (§16.10, §24 Runbook R1).
  • Can derive the memory and bandwidth budget for a 500-connection SFU from the System Constraints table alone (§4, §32).
  • Can defend the DTLS-SRTP key-export design against "why not just use TLS+SRTP over TCP" (§8.3, §2).
  • Can name the concrete regime where each rejected ADR alternative (§9) would in fact be the right call.

Per-box description. PeerConnection FSM: the only component the application touches; owns SDP negotiation and exposes the W3C-enumerated connection states (§8.1, I12). ICE Agent: gathers three candidate kinds, exchanges them (Trickle, P3), runs priority-ordered connectivity checks, nominates one pair (§8.2, I1, I9). UDP mux: one socket per PeerConnection; demuxes by first byte per RFC 7983 so ICE/DTLS/RTP share one 5-tuple (P2, ADR-04). DTLS layer: one handshake establishes a session; framing, fragmentation, and retransmission are implemented on top of rustls's record layer (ADR-06). SRTP/SRTCP: every media packet is authenticated-encrypted; keys come from the DTLS exporter, never renegotiated per-packet (I2, I8). RTP/RTCP + jitter buffer: packetizes codec output, reassembles on receive, reorders into presentation order (I10). GCC BWE: sender-side estimator consuming TWCC arrival-time feedback, producing a target bitrate consumed by the bitrate allocator (P8, I6). Codecs: pluggable encode/decode behind a uniform trait; the rest of the stack is codec-agnostic (P1). SCTP-over-DTLS: an independent reliable/partial-reliable multiplexed channel riding the same DTLS connection as media, never blocking it (I5, I7).

3.1 Concurrency & trust boundaries

Each PeerConnection owns one tokio task per socket; the ICE/DTLS/SRTP/RTP layers are sans-IO state machines (P4, ADR-03) driven by that task — they receive &[u8] and emit &[u8]/events, never touching the socket directly, which is what makes them independently fuzzable (P13) and embeddable in any executor. The trust boundary sits at the UDP socket: everything past it is untrusted bytes until STUN MESSAGE-INTEGRITY, the DTLS handshake, or the SRTP auth tag validates it (§8.6 malformed-input walkthrough).

6. Design Principles

  1. P1 — Layered protocol independence. ICE ⊥ DTLS ⊥ SRTP ⊥ RTP ⊥ codec; each testable and fuzzable in isolation. Tradeoff: more crate-boundary glue code. Operationally: a codec bug can never corrupt ICE state. Violate it and a congestion controller cannot be swapped without touching the RTP layer.
  2. P2 — Single-port first-byte demux (RFC 7983). One UDP 5-tuple serves STUN/TURN/DTLS/RTP/RTCP. Tradeoff: the mux is a single point of dispatch bugs. Operationally: simplifies firewall/NAT config to one port. Violating it breaks BUNDLE (RFC 8843) compatibility with every modern browser.
  3. P3 — Trickle ICE by default. Never block signaling on full candidate gathering. Tradeoff: more asynchronous signaling-channel traffic. Violating it adds seconds to connect time (M1).
  4. P4 — Sans-IO core (str0m-inspired). Protocol state machines take bytes/events in, emit bytes/events out; no socket ownership in rtc-ice/rtc-dtls/rtc-srtp/rtc-rtp. Tradeoff: callers must drive an event loop correctly. Operationally: enables independent fuzzing (P13) and embedding in any async runtime. Violating it couples protocol correctness to I/O timing, making bugs non-reproducible.
  5. P5 — Fail-closed cryptography. A DTLS or SRTP verification failure drops the packet; there is no plaintext fallback path. Violating it is a silent MITM (§22 T3).
  6. P6 — Asymmetric backpressure. Media drops under backpressure (loss-tolerant); the data channel blocks with SCTP flow control (ADR-24). Violating it either stalls video indefinitely or silently drops a file-transfer chunk.
  7. P7 — Deterministic, fixed-memory replay windows. SRTP/SCTP anti-replay uses a fixed-size sliding bitmask, never an unbounded set. Violating it is an unbounded memory-growth DoS vector (§22 T4).
  8. P8 — Congestion control ⊥ codec. GCC computes a target bitrate; the encoder adapts to it; neither owns the other's internal state. Violating it recreates the libwebrtc anti-pattern where BWE changes require touching every codec wrapper.
  9. P9 — Explicit table-driven state machines. PeerConnection, IceAgent, DtlsConnection, SctpAssociation are each an enumerated transition table, never ad hoc branching. Violating it is the #1 root cause of "call state got stuck" bugs.
  10. P10 — No global mutable state. Every session's state lives in that session's struct; no process-wide singletons. Enables multi-tenant SFU embedding. Violating it makes 500-connection concurrency (M11) impossible without lock contention.
  11. P11 — Zero-copy media hot path. RTP encode/decode operate on Bytes/BytesMut; no packet copied more than once between socket and cipher. Violating it blows the 2 µs SRTP budget (M3) at scale.
  12. P12 — Observable by default. Every state transition emits a tracing span and a metric. Violating it means "why did the call fail" is unanswerable in production.
  13. P13 — Fuzz every parser from Phase 0. STUN/DTLS/RTP/SCTP/SDP parsers are fuzz targets from the first commit, not appended later. Violating it defers discovery of memory-safety bugs to production traffic.
  14. P14 — Conformance before optimization. A phase's conformance bucket (N.5) must be green before its performance budget (N.7) is tuned. Violating it optimizes code that is still incorrect.

8. Domain Model / Protocol / Data Model

8.1 SDP Offer/Answer Model

SDP (RFC 4566) under the JSEP profile (RFC 8829) is the negotiation envelope. Grammar sketch (session-level + one media-level fragment):

session-description = proto-version origin-field session-name-field
                       time-field *media-description
media-description   = media-field connection-field *attribute-field
attribute-field      = "a=" (att-fingerprint / att-ice-ufrag / att-ice-pwd /

8.4 RTP/RTCP Wire Model & Congestion-Control Feedback Loop

RTP header (RFC 3550 5.1), 12-byte fixed portion:

 0                   1                   2                   3
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|V=2|P|X|  CC   |M|     PT      |       sequence number        |
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|                           timestamp                           |
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|                 synchronization source (SSRC)                 |
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

GCC feedback loop (Pa1, ADR-09): sender tags outgoing packets with a transport-wide sequence number (RFC 8285 extension); receiver batches arrival timestamps into RTCP-TWCC feedback; sender's trendline filter (Pa2) classifies inter-arrival delay gradient as Normal/Overusing/Underusing; the loss-based estimator (Pa1 §III) combines with the delay-based signal; the lower of the two becomes the target bitrate (I6), consumed by the bitrate allocator feeding the codec (P8).

Malformed-input example. An RTP packet with CC (CSRC count) claiming 15 sources but a payload shorter than 12 + 4·CC bytes is rejected at header-parse with RtpDecodeError::TruncatedCsrc — fixture rtp_csrc_overrun.bin (§19.5).

Failure-path example. TWCC feedback stops arriving (receiver crashed or link down): GCC's trendline filter has no new samples; after feedback_timeout (2× RTCP interval) the estimator falls back to the loss-based estimate only, and after a second timeout freezes the bitrate at its last-known-good value rather than ramping to zero (§23 FM-6).

8.5 SCTP-over-DTLS Data Channel Model

Association State Entry Exit Next
Closed initial INIT sent CookieWait
CookieWait INIT sent INIT-ACK received CookieEchoed
CookieEchoed COOKIE ECHO sent COOKIE ACK received Established
Established four-way handshake done SHUTDOWN sent/received ShutdownPending/Sent

DCEP (RFC 8832) opens a channel: an DATA_CHANNEL_OPEN message on a fresh stream negotiates label, reliability (reliable / partial-reliable-rtx / partial-reliable-timed), and ordering; the peer replies DATA_CHANNEL_ACK. Each DataChannel maps 1:1 to one SCTP stream (I5 governs per-stream TSN ordering).

Malformed-input example. A DCEP DATA_CHANNEL_OPEN message with an unrecognized channel-type byte is rejected with DcepError::UnknownChannelType, the stream is reset (RFC 6525) rather than the association torn down — fixture dcep_bad_type.bin (§21.5).

Failure-path example. A network MTU drop mid-association causes SCTP fragmentation retries; if the SCTP RTO (§4, 1,000 ms initial) expires 5 consecutive times the association aborts and rtc-core surfaces DataChannel::onclose with an SctpAbortReason::PathFailure — the media path is unaffected (P6, I5 isolation).

8.6 Cross-Layer Worked Example

Alice → Bob, audio-only call, Alice behind a symmetric NAT (TURN required), Bob on a public IP (ICE-Lite): (1) SDP offer/answer exchanges ICE credentials + DTLS fingerprint (§8.1); (2) Alice gathers host+srflx+relay, Bob gathers host-only, ICE-Lite (§14); (3) connectivity checks find only the TURN-relayed pair reachable, it nominates (§8.2, I1); (4) DTLS handshake over the relayed path exports SRTP keys (§8.3); (5) Opus-encoded RTP flows encrypted through the TURN relay with GCC adapting to the relay's added latency (§8.4); (6) a DataChannel opens on the same DTLS connection for chat (§8.5) without affecting the audio jitter buffer (P6).

13.1 Objectives

13.4 Acceptance Criteria

100% of RFC 8489 Appendix B test vectors byte-match; encode/decode round-trip < 500 ns p99 (single-threaded, no allocation on the decode hot path per P11); zero panics across 1M fuzz iterations of fuzz_stun_decode (M10 basis).

13.6 Pitfalls

  • Attribute padding to 4-byte multiples must exclude the pad bytes from the value length but include them in the overall message length — an easy off-by-one.
  • MESSAGE-INTEGRITY is computed with a placeholder message length that includes the MESSAGE-INTEGRITY attribute's own length, before FINGERPRINT is appended.
  • XOR-MAPPED-ADDRESS for IPv6 XORs the full 128 bits against cookie‖transaction-ID, not just the cookie — a common interop bug against naive implementations.

13.7 Performance Concerns

Decode allocates zero heap memory per message (attributes borrow from the input slice, P11); target < 500 ns p99 encode+decode round trip on a 200-byte message (§4 basis for downstream ICE check pacing).

13.8 Edge Cases

Unknown attribute type with the "optional" bit set (per RFC 8489 14) is skipped, not rejected; unknown with "required" bit set aborts decode with UnknownRequiredAttribute; zero-length attribute value; message length of exactly 0.

13.9 Failure Analysis

A decode bug here is remotely triggerable pre-authentication (any UDP packet reaches the mux, §12.2); contained by P5 fail-closed + P13 fuzz coverage; blast radius limited to "packet dropped" given Rust's memory safety — no OOB read/write class of bug survives to production (§22 T1 mitigation).

13.10 Operational Notes

Emit stun_decode_error_total{reason} counter (P12); log at debug level per malformed packet (not warn — malformed STUN from internet background noise is expected and must not page an operator).

16. Phase 4 — ICE Connectivity Checks & Nomination

16.1 Objectives

Complete the ICE agent (§8.2 state table): candidate pairing, priority-ordered connectivity checks, frozen/waiting/in-progress scheduling, role-conflict resolution, and nomination — the piece that actually selects the (local,remote) pair media flows over.

16.2 Detailed Implementation Steps

Form all local×remote candidate pairs; compute pair priority per the §8.2 formula (I9); implement pacing (RFC 8445 14, Ta = 50 ms default) so checks don't burst; implement triggered checks — an inbound Binding Request from an unrecognized pair adds it to the check list with Triggered priority and responds immediately (P4: this is pure state-machine logic, no direct socket I/O); implement freezing per foundation (RFC 8445 6.1.2.4); resolve role conflicts via the ICE-CONTROLLED/CONTROLLING tie-breaker (lower value switches roles, I1 unaffected by role, only by validated pairs); implement regular nomination — the controlling agent nominates the highest-priority Succeeded pair only after checks settle (RFC 8445 8.1.1), never aggressive nomination. Enforce I1: selected_pair is None until a pair transitions to Succeeded.

16.3 Deliverable

IceAgent drives a full P2P connectivity-check cycle against a second in-process agent (loopback, rtc-verifier scenario ice_full_handshake) and against a browser (Chrome headless) in the interop bucket, ending in IceState::Completed.

16.4 Acceptance Criteria

ICE connect time ≤ 3,000 ms p95 against 2 STUN + 1 TURN server at 100 ms RTT (M1, §4); role-conflict resolution completes within 1 additional RTT when both peers start Controlling; 0 invariant-I1 violations across 10,000 rtc-verifier simulated sessions with 0–20% induced loss.

  • Regular nomination requires waiting for the check list to "settle" — nominate too early and a higher-priority pair that later succeeds is ignored, violating I9's intent.
  • Frozen-pair unfreezing logic (RFC 8445 6.1.2.6) is the single most error-prone part of ICE; a bug here manifests as "sometimes connects, sometimes doesn't" flakiness.
  • Triggered checks must not bypass I1 — an inbound Binding Request response confirms only one direction; the pair still needs the reverse check to be marked Succeeded.

16.7 Performance Concerns

16.8 Edge Cases

17. Phase 5 — DTLS Handshake Over UDP

17.1 Objectives

Implement DTLS framing over UDP (rtc-dtls, RFC 9147 primary / RFC 6347 (DTLS 1.2) fallback, ADR-05) on top of rustls's record-layer primitives (ADR-06): fragmentation, retransmission, and the certificate-fingerprint trust anchor (I8).

17.2 Detailed Implementation Steps

17.3 Deliverable

17.4 Acceptance Criteria

Handshake completes in ≤ 2 RTT p95 at 0% loss, ≤ 4 RTT p95 at 10% induced loss (M2, §4); 100% of fingerprint-mismatch fixtures result in connection teardown, 0 established sessions; retransmission timer backoff verified at 1 s, 2 s, 4 s (capped 60 s per §4 SCTP-RTO-consistent ceiling) across 3 induced-loss iterations.

17.6 Pitfalls

  • DTLS 1.3's ConnectionID extension changes epoch/sequence semantics vs 1.2 — do not reuse 1.2 anti-replay logic unchanged (ADR-05 fallback path needs its own tests).
  • Retransmission timer interacting with ICE consent-freshness checks (STUN keepalive, Phase 4) can double-send if not coordinated on the same clock source (ADR-23).
  • Certificate fingerprint comparison must be constant-time to avoid a timing side channel, even though WebRTC's threat model already assumes the fingerprint is public (defense in depth, §22 T3).

17.8 Edge Cases

17.9 Failure Analysis

A handshake that never completes (peer silent after ClientHello) times out at the overall connection-establishment budget and surfaces ConnectionState::Failed with the last-sent handshake message type attached; a fingerprint mismatch is logged at warn (security-relevant, unlike STUN noise) and increments dtls_fingerprint_mismatch_total (§22 T3 detection signal).

18.1 Objectives

19. Phase 7 — RTP/RTCP Media Transport & Jitter Buffer

19.1 Objectives

Implement the RTP packetizer/depacketizer (rtc-rtp, RFC 3550), RTCP SR/RR/SDES/BYE generation, and the adaptive jitter buffer that reorders packets into presentation order (I10) — the layer that turns encrypted packets into playable media frames.

19.2 Detailed Implementation Steps

Packetize codec output into RTP per §8.4's wire schema; implement Opus packetization (one packet per 20 ms frame, RFC 7587) and VP8 packetization (descriptor-based fragmentation for frames exceeding MTU, RFC 7741); implement the jitter buffer as a priority queue keyed on RTP timestamp with an adaptive depth (20–300 ms, §4) computed from measured inter-arrival jitter (RFC 3550 6.4.1's jitter estimator, EWMA); enforce I10 — the buffer emits frames strictly in timestamp order, holding later-timestamp frames rather than reordering; implement RTCP SR (sender report, NTP+RTP timestamp mapping for lip-sync) and RR (receiver report, loss fraction + jitter) per RFC 3550 6.4 (P12 — RR statistics feed directly into Phase 8's GCC loss-based estimator, Pa1).

19.3 Deliverable

End-to-end Opus audio flows through packetize → jitter-buffer → depacketize in rtc-verifier scenario audio_e2e_30ms_jitter, measuring one-way latency against M4.

19.4 Acceptance Criteria

One-way audio latency (capture-equivalent to playout-equivalent in the simulator) ≤ 150 ms p95 under 30 ms network jitter (M4, §4); jitter-buffer steady-state depth ≤ 60 ms p50, ≤ 150 ms p99 (M5); 0 I10 violations (out-of-order emission) across 10,000 simulated packets with 30% reordering.

19.5 Conformance Fixtures

Fixture Purpose Expected Output

  • The jitter estimator's EWMA (RFC 3550 6.4.1) reacts slowly to sudden jitter spikes (network path change); pairs with the §20 GCC trendline filter for faster reaction.
  • Growing the jitter buffer to absorb jitter directly increases latency (Pa4/Pa5's bufferbloat lesson) — depth must be capped at 300 ms (§4) even under sustained jitter.

19.8 Edge Cases

19.9 Failure Analysis

20.1 Objectives

Implement RTCP feedback (NACK/PLI/FIR, RFC 4585/5104), FEC, and the GCC sender-side bandwidth estimator (rtc-gcc, ADR-09, Pa1) — closing the adaptive-bitrate loop sketched in §8.4.

  • GCC's trendline filter has many tunable parameters (Pa2); under-tuning causes slow convergence (fails M6), over-tuning causes rate "flapping" that visibly stutters video.

20.8 Edge Cases

20.9 Failure Analysis

21.6 Pitfalls

  • SCTP's own retransmission timer and DTLS's replay/record-loss handling can both retransmit the same logical data, producing application-visible duplicates if the SCTP layer doesn't dedupe by TSN (I5) — the original draft's pitfall #4 in miniature.
  • A PeerConnection observing a DTLS failure must not jump straight to Closed; I12 requires transitioning through Failed first so the application can distinguish "never connected" from "was connected, then died."
  • DCEP races: both peers opening a data channel with the same negotiated stream ID simultaneously (original draft's "DCEP race" pitfall #10) — resolved by even/odd stream-ID parity keyed on DTLS role (client picks even, server picks odd, RFC 8832 6).

21.7 Performance Concerns

SCTP association overhead (COOKIE mechanism, RFC 4960 5.1.3) is a one-time cost; per-message overhead thereafter is dominated by DTLS record framing, not SCTP itself; throughput budget (M8) assumes the reliable, ordered fast path with no retransmission.

21.8 Edge Cases

DataChannel opened before ICE/DTLS complete (buffered, sent once Established, RFC 8831 6.2); message exactly at the negotiated max-size boundary (I7's precheck uses >, not >=, so boundary-exact messages succeed); PeerConnection closed while a DataChannel send is in flight (graceful drain vs hard abort, configurable).

21.9 Failure Analysis

An SCTP path failure (§21.5) tears down only the data channel, never the media path (P6, I5's isolation); a PeerConnection stuck in Connecting beyond the aggregate ICE+ DTLS timeout is force-transitioned to Failed with full sub-state telemetry attached for the §24 R1/R4 runbooks.

21.10 Operational Notes

sctp_association_state_total{state}, datachannel_open_total, and pc_state_transition_total{from,to} (P12, I12) are the top-level telemetry an operator reads first when triaging any call-quality incident (§24).

24. Operational Readiness

Metrics & tracing. OpenTelemetry (ADR-16) exports every P12 counter/histogram/gauge named throughout §12–§21 (e.g. ice_pair_state_total, srtp_auth_failure_total, bwe_target_bps) plus tracing spans per state transition (ADR-15), correlated by a per-PeerConnection trace ID.

Dashboards. One dashboard per SLO: ICE-connect-time (M1), DTLS-handshake (M2), media-quality (M4/M5/M6/M7), data-channel (M8), SFU-capacity (M9/M11).

Alerting philosophy. Page only on SLO-threshold breach sustained > 5 minutes (M1–M12); log-only (no page) for expected background noise (malformed STUN from internet scanners, §13.10).

SLOs. Media path 99.9% monthly (§4); signaling control plane 99.95% monthly (§4); error budget burn alerts at 2×/6×/10× burn rate (standard multi-window burn-rate alerting).

Incident response. Named runbooks, each keyed to the failure mode it addresses:

  • R1 — Call Won't Establish (FM-1, FM-2, FM-3): inspect candidate gathering (host? srflx? relay?), inspect candidate-pair states, verify STUN/TURN reachability. Remediation: deploy/verify TURN, verify signaling delivery.
  • R2 — Video Quality Degrades (FM-5, FM-6): inspect GCC stats (target bitrate, RR loss fraction, RTT). Remediation: lower codec bitrate, reduce resolution/framerate.
  • R3 — Echo (not a failure mode table entry — codec-adjacent, deferred AEC scope, PhaseDeferred("§35")): verify capture/render device geometry, enable AEC when the deferred feature lands.
  • R4 — DTLS Handshake Fails (FM-3): check SDP fingerprints match, check a=setup role assignment (both sides actpass is a config bug).
  • R5 — DataChannel Disconnects (FM-7): check SCTP RTO aggressiveness, force MTU discovery, inspect path-failure reason code.

Backup/restore. No persistent media-path state to back up (§4); conformance/fuzz corpora are the only durable artifact, backed up via the CI artifact store (§27).

Deployment topology. One PeerConnection per call (P2P) or per SFU-forwarded leg; SFU deployment runs N processes behind a signaling load balancer, each independently crash-isolated (P10, FM-10).

Canary / rollout. Canary 1% of new SFU processes for 24 h (M10's fuzz-canary duration doubles as the operational canary window) before full rollout; rollback is a version-pinned redeploy (no in-place state migration needed, §25).

25. Compatibility & Versioning

Wire compatibility. STUN/DTLS/RTP/SCTP/SDP wire formats are IETF-standardized (§5 RFCs); this implementation never deviates from the RFC wire format, guaranteeing interop with libwebrtc/Pion/str0m/aiortc/mediasoup (ADR-17 differential harness, M12).

API stability. rtc-core's public API (PeerConnection, RtcConfiguration, §11) follows SemVer; a breaking change to any public struct field requires a major version bump and a migration note in CHANGELOG.md.

Schema evolution. RtcConfiguration additions are always optional fields with documented defaults, never required, to keep minor-version upgrades non-breaking.

Deprecation policy. A deprecated API is marked #[deprecated] for ≥1 minor version before removal, with the replacement documented at the deprecation site.

Rolling-upgrade guarantees. Because there is no persistent shared state across PeerConnection instances (P10), a rolling SFU-process upgrade drains in-flight calls (graceful SCTP/DTLS teardown, §4 250 ms budget) rather than migrating live sessions; live-session migration is out of scope (no cross-process state to migrate).

26. Testing & Verification Strategy

Unit. Per-crate, per-function correctness (e.g. XOR-MAPPED-ADDRESS encode/decode, §13.2).

Property-based (ADR-17). proptest generates random valid+invalid STUN/RTP/SCTP messages; asserts decode-then-encode round-trips and decode never panics (ties to P13).

Differential (ADR-17, M12). Every conformance bucket runs against libwebrtc, Pion, and str0m reference outputs for the same input; divergence is a defect until proven otherwise (a legitimate RFC ambiguity is documented, not silently accepted).

Fuzzing (ADR-18, P13). cargo-fuzz target per wire parser from Phase 0 (§12); 60 s CI smoke, 8 h nightly extended, 24 h pre-release canary (M10).

Chaos / fault injection. rtc-verifier's SimulatedNetwork (§12.2) injects loss, jitter, reordering, and TURN/DTLS-peer crashes into every phase's conformance bucket.

Deterministic replay. Every rtc-verifier scenario runs from a fixed seed; a failing assertion (§7 methodology) reproduces byte-for-byte on replay.

Soak. 24 h continuous synthetic-call canary (M10) plus a 6 h TURN-refresh soak (§15.4) validating no allocation leak across many refresh cycles.

Conformance & performance-regression gating. Every phase's N.5 fixtures must be green and every M-target (§28) met before a PR merges (P14); a performance regression

10% against the previous release fails CI.

This strategy ties directly back to the System Invariants (§7): every invariant has at least one rtc-verifier scenario asserting it, and the debugging methodology (§7, final paragraph) is this section's deterministic-simulator approach applied continuously.

29. Scalability Analysis

Constant regardless of scale. Per-packet SRTP/RTP processing cost (O(1), §18.7, §19.7); per-connection memory footprint (§4, M9) — does not grow with total connection count because P10 forbids shared mutable state.

Grows with scale (Big-O). Total process memory: O(n) in connection count n (§32 CM3); total CPU: O(n) for SFU forward-only (no transcode, §32 CM5) vs O(n·k) if k codecs were transcoded per connection (avoided by design, §1 scope); FD count: O(n) (§32 CM4).

Named bottlenecks, in order. (1) CPU at high connection-count on a transcoding SFU (avoided by forward-only default, but present if transcoding is added — deferred scope); (2) TURN relay egress bandwidth when a large fraction of connections require relay (§32 CM6); (3) single-process FD limits before OS tuning (ulimit -n); (4) the signaling control plane (out of this stack's scope, §1) as call-setup rate grows.

Horizontal scaling. SFU processes shard by connection (P10 makes this trivial — no cross-process coordination needed for media); a signaling load balancer assigns new calls to the least-loaded process using the rtc-stats CPU/connection-count gauge.

Vertical scaling. More cores raise the per-process connection ceiling roughly linearly (§32 CM5's CPU-per-connection basis) until NUMA cross-socket memory latency degrades the jitter-buffer's cache locality (§19.7).

Sharding / partitioning. By call ID, hashed to an SFU process; no partitioning needed within a single call (P1 keeps a call's layers independent, not distributed).

Coordination overhead. Zero inter-process coordination for media (P10); the only cross-process coordination is TURN-server capacity planning (a fleet-level, not per-connection, concern).

Practical ceiling & levers beyond it. ~500 connections/process/8-core (M11) is the practical ceiling at the current CPU budget (§32 CM5); levers beyond it: (a) hardware codec offload (deferred, PhaseDeferred("§35")) shifting encode cost off the CPU budget entirely; (b) horizontal process scaling (no ceiling, P10-enabled); (c) simulcast/SVC (deferred, PhaseDeferred("§35")) trading forwarding CPU for encode CPU at the sender.

30. Mental Models & First Principles

  1. MM1 — ICE is a distributed consensus on one fact. Both agents must agree, without a coordinator, on which single (local,remote) pair is usable. Predicts: nomination must wait for check-list settlement, not race to the first success. Bug class without it: premature pair selection on a low-priority pair (§16.6). Applies at §16.
  2. MM2 — DTLS-SRTP is a key-agreement protocol wearing a media-transport costume. The handshake's only real job is producing symmetric keys; everything else (record framing) is TLS's usual job repurposed for datagrams. Predicts: the exporter label (§8.3) is the single most fragile string in the whole stack. Bug class without it: "SRTP just doesn't work" debugged as an RTP bug instead of a key-derivation bug. Applies at §18.
  3. MM3 — The jitter buffer is a queueing-delay budget, not a storage buffer. Growing it doesn't "fix" jitter; it trades network-jitter latency for buffer-induced latency (Pa4/Pa5's bufferbloat lesson). Predicts why depth is capped at 300 ms even under sustained jitter (§4). Bug class without it: unbounded depth growth chasing an unreachable "zero loss" goal. Applies at §19.
  4. MM4 — GCC is a control loop, not a formula. It has poles, gain, and stability margins like any feedback controller; treating its output as a one-shot calculation guarantees oscillation under real network noise. Predicts the tuning tradeoff in §20.6. Bug class without it: bitrate "flapping" visible as periodic quality dips. Applies at §20.
  5. MM5 — Multiplexed streams need an explicit fairness policy. SCTP streams share one association the way threads share a CPU; without an explicit policy one stream can starve another. Predicts why DataChannel message-size limits (I7) exist independent of association-level flow control. Bug class without it: a large unreliable stream starving a small reliable one. Applies at §21.
  6. MM6 — NAT traversal is probabilistic, not deterministic. No client-side algorithm guarantees P2P connectivity through an arbitrary NAT; TURN is mandatory infrastructure, not a rare fallback. Predicts the ~80% P2P failure rate without traversal cited in the domain literature. Bug class without it: shipping without a TURN deployment plan and discovering it in production. Applies at §15, §1.
  7. MM7 — Every layer boundary is a trust boundary until proven otherwise. Decrypted does not mean authenticated; parsed does not mean valid. Predicts where P5's fail-closed checks must live (every layer transition in §3). Bug class without it: trusting DTLS-decrypted-but-not-yet-Finished-verified data (I2). Applies at §8.6.
  8. MM8 — Reliability and congestion-safety are orthogonal axes. SCTP's reliability modes (§8.5) and DTLS's congestion behavior are independent knobs, not one dial; conflating them is why naive "just make media reliable" proposals break real-time latency. Predicts ADR-12's SCTP-over-DTLS choice over a simpler always-reliable transport. Bug class without it: adding TCP-like reliability to the media path and reintroducing head-of-line blocking. Applies at §21, ADR-12.

32. Back-of-Envelope Capacity Model

  1. CM1 — Audio bandwidth/connection. BW = codec_bitrate + header_bytes×8×pps. Opus 32 kbps + (12 RTP + 8 UDP + 20 IP = 40 B)×8×50 pps = 32 + 16 = 48 kbps/direction ⇒ 96 kbps bidirectional (chained from §4's Opus 6–64 kbps range).
  2. CM2 — Video bandwidth/connection. VP8 720p30 @ 1 Mbps target (§4), ~125 pps at ~1,000 B/packet ⇒ overhead = 125×40 B×8 = 40 kbps ⇒ ≈1.04 Mbps total.
  3. CM3 — Memory/connection. jitter buffer (300 ms×1.04 Mbps/8 ≈ 39 KB) + DTLS session state (~16 KB) + SCTP send/recv buffers (64 KB+64 KB) + Opus state (~50 KB)
    • VP8 decoder frame buffers (~2 MB @ 720p) ⇒ ≈2.2 MB/connection, well inside the ≤10 MB budget (§4) which reserves headroom for jitter spikes.
  4. CM4 — FD budget at 500 connections. FDs = connections × sockets_per_connection = 500×1 (muxed, §4) + active TURN allocations ⇒ ≈500–600 FDs for a full SFU process, well under typical ulimit -n (65536).
  5. CM5 — CPU/connection (SFU, forward-only). SRTP 2 µs×2 (enc+dec, M3) × (50 audio pps + 125 video pps) ≈ 2 µs×2×175 = 700 µs of CPU-second per wall-clock second per connection ⇒ negligible core-fraction, which is why M11's 500-connections/8-core target is achievable — the SFU forwards ciphertext, it never re-encodes (§1 scope).
  6. CM6 — TURN relay bandwidth overhead. overhead = connections × relayed_fraction × 2 × per_connection_bitrate (2× because relay doubles ingress+egress). At 1.04 Mbps (CM2) and 20% relayed of 500 connections: 500×0.2×2×1.04 Mbps ⇒ ≈208 Mbps additional TURN-server egress capacity required.
  7. CM7 — Fuzz corpus growth. libFuzzer typical throughput ~1,000 exec/s ⇒ 86.4M execs/24 h canary (M10); corpus is minimized (corpus_minimize.sh, §10) to stay inside the ≤500 MB storage budget (§4).
  8. CM8 — ICE gathering time. 2 STUN servers queried in parallel + 1 TURN allocate (1 RTT each) at 100 ms RTT ⇒ gathering ≈ 150–300 ms, leaving ≈2.7 s of the 3,000 ms M1 budget (§4) for connectivity-check pacing (Ta=50 ms × ~20 pairs ⇒ ≤1,000 ms worst-case serial, §16.7).
  9. CM9 — SCTP dead-peer detection ceiling. At RTO_max=60 s (§4), worst-case silent failure detection via SCTP alone takes up to 60 s; mitigated by ICE's STUN consent-freshness keepalive (every 15 s, §16.10) detecting failure roughly 4× faster.

Regime where it wins: a single deployment target (a browser process) needing tight scheduling coordination with capture/render threads. Real system: libwebrtc. Rejected because: ADR-03's embedding goal (this stack must plug into any host application's existing tokio runtime) is structurally incompatible with an owned event loop; also loses P4's independent-fuzzing benefit.

34.2 FFI-Wrap an Existing C/C++ Stack

┌───────────────┐    cxx bridge    ┌─────────────────┐
│  Rust app code│ ◄──────────────► │  libwebrtc (C++) │
└───────────────┘                  └─────────────────┘

Regime where it wins: hard deadline pressure with no budget for a from-scratch reimplementation; an existing team already ships C-linkable binaries and accepts an unsafe FFI boundary. Real system: several commercial products wrap libwebrtc via a Rust webrtc-sys-style bridge. Rejected because: it forfeits ADR-01's memory-safety goal at the FFI boundary and makes custom congestion-control experimentation (ADR-09) require patching a multi-GB C++ build.

34.3 QUIC/WebTransport-Native Transport

┌────────────────────────────────────────────┐
│  QUIC connection (built-in encryption,      │
│  congestion control, stream multiplexing)   │
│  — replaces ICE+DTLS+SRTP+SCTP entirely     │
└────────────────────────────────────────────┘

Regime where it wins: browser-to-server only, greenfield deployment, no legacy WebRTC interop requirement. Real system: Media over QUIC (MoQ) / WebTransport experimental deployments (Meta, Cloudflare). Rejected because: QUIC has no P2P NAT-traversal story equivalent to ICE, and (as of this writing) browser support is not universal enough to drop WebRTC interop (§1 scope requires interop with real browsers, §16.5).

34.4 GStreamer webrtcbin-style Plugin Pipeline

┌───────────────────────────────────────────────┐
│  glib main loop → GStreamer element graph       │
│  (webrtcbin, dtlssrtpenc, rtpbin, ...)          │
└───────────────────────────────────────────────┘

Regime where it wins: an organization already standardized on GStreamer media pipelines wanting to add WebRTC as one more element graph, reusing existing pipeline tooling. Real system: GStreamer's webrtcbin. Rejected because: it is glib-event-loop-native, not Rust/tokio-native, requiring a bridge thread to embed in this stack's target applications (ADR-02), and its element-graph model obscures the sans-IO testability this design prioritizes (P4, P13).

36. Glossary

  • AEC — Acoustic Echo Cancellation; deferred (§35).
  • ADR — Architecture Decision Record; this document's §9 table.
  • BUNDLE — RFC 8843 multiplexing of multiple m-lines onto one transport.
  • BWE — Bandwidth Estimation; GCC's output (§20).
  • Candidate — an ICE-gathered address/port pair a peer might be reachable at (§8.2).
  • CandidatePair — a (local,remote) candidate combination under connectivity check.
  • DCEP — DataChannel Establishment Protocol (RFC 8832); opens a DataChannel (§8.5).
  • DTLS — Datagram Transport Layer Security (RFC 9147); TLS adapted for UDP.
  • DTLS-SRTP — the key-export binding of DTLS session keys into SRTP master keys (§8.3).
  • FEC — Forward Error Correction; parity-based loss recovery without retransmission (§20).
  • Fingerprint — a certificate hash exchanged via SDP as the DTLS trust anchor (I8).
  • FIR — Full Intra Request; forces a video key frame (RFC 5104).
  • Foundation — an ICE grouping key for candidates sharing type/base/protocol (RFC 8445).
  • GCC — Google Congestion Control; sender-side bandwidth estimator (§20, Pa1).
  • ICE — Interactive Connectivity Establishment (RFC 8445); NAT-traversal protocol.
  • ICE-Lite — a simplified ICE mode for server-side endpoints with a public IP (§1).
  • JSEP — JavaScript Session Establishment Protocol (RFC 8829); SDP negotiation model.
  • Jitter buffer — a reordering/delay buffer smoothing network jitter into steady playout (§19).
  • MESSAGE-INTEGRITY — a STUN attribute authenticating the message via HMAC (§13.2).
  • MTU — Maximum Transmission Unit; the largest packet size a path carries unfragmented.
  • NACK — Negative Acknowledgment; a receiver's request to retransmit a lost RTP packet.
  • Nomination — the ICE step selecting the final candidate pair for media (§8.2).
  • PLI — Picture Loss Indication; a receiver's request for a key frame (RFC 4585).
  • Reflexive candidate (srflx) — a candidate reflecting a peer's NAT-mapped public address.
  • Relayed candidate — a candidate at a TURN server forwarding traffic (§15).
  • REMB — Receiver Estimated Maximum Bitrate; the predecessor bandwidth estimator to GCC.
  • Replay window — a fixed-size bitmask rejecting duplicate/out-of-window packets (I3).
  • ROC — Rollover Counter; tracks RTP/SRTP sequence-number wraps (§8.3).
  • RTCP — RTP Control Protocol; carries SR/RR/feedback (RFC 3550 6).
  • RTO — Retransmission Timeout; SCTP's retransmit timer (RFC 4960 6.3).
  • RTP — Real-time Transport Protocol (RFC 3550); the media wire format.
  • RTX — Retransmission; resending a lost RTP packet on NACK request.
  • SCTP — Stream Control Transmission Protocol (RFC 4960); the DataChannel transport.
  • SDP — Session Description Protocol (RFC 4566); the negotiation envelope (§8.1).
  • SFU — Selective Forwarding Unit; a server that forwards media without transcoding.
  • SRTP — Secure RTP (RFC 3711); authenticated-encrypted media transport.
  • SRTCP — the SRTP-analogous encryption of RTCP.
  • SSRC — Synchronization Source; the per-stream RTP identifier (I4).
  • STUN — Session Traversal Utilities for NAT (RFC 8489); the ICE probing protocol.
  • Trickle ICE — incremental candidate exchange overlapping gathering and checking (P3).
  • TSN — Transmission Sequence Number; SCTP's per-stream ordering counter (I5).
  • TURN — Traversal Using Relays around NAT (RFC 8656); the relay protocol (§15).
  • TWCC — Transport-Wide Congestion Control; per-packet arrival-time feedback for GCC.
  • use_srtp extension — the DTLS ClientHello/ServerHello extension negotiating SRTP profile.
  • XOR-MAPPED-ADDRESS — a STUN attribute encoding a reflexive address obfuscated by XOR.
