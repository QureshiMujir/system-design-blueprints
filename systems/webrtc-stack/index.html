In one paragraph

WebRTC is the set of protocols that lets two programs exchange live audio, video and small data messages directly, even when both sit behind home routers, and encrypts all of it (§1, §2). This blueprint designs a from-scratch WebRTC peer-connection stack in Rust: call negotiation, path finding through NATs, a key-setting handshake, encrypted media transport with loss recovery and bandwidth adaptation, and a data channel (§1). It is a library plus a reference binary, not a browser (§1). Its users are systems engineers building real-time products and operators running forwarding-server fleets who need getStats()-style telemetry (§1).

The problem, concretely

Take the blueprint's own call: Alice is behind a symmetric NAT and Bob has a public IP (§8.6). Alice and Bob must first swap an SDP offer and answer carrying their ICE credentials and DTLS certificate fingerprints (§8.6 step 1). Alice then collects three kinds of address, tests pairs of them, and finds that only the pair that goes through a TURN relay works (§8.6 steps 2 and 3). Only then can keys be agreed over that path and audio flow through the relay, with a chat channel riding the same connection (§8.6 steps 4–6).

A naive "open a UDP socket and send packets" design fails at each step:

  • No path. NAT traversal is probabilistic, not guaranteed. The blueprint says TURN is mandatory infrastructure, not a rare fallback, and cites a P2P failure rate of about 80% without traversal that it attributes only to "the domain literature" (MM6). With host candidates only, behind symmetric NATs and no TURN, every pair fails and the connection ends in Failed (§8.2 failure path, FM-1).
  • No trust. Everything past the UDP socket is untrusted bytes until a STUN integrity check, the DTLS handshake or an SRTP auth tag validates it (§3.1). "Decrypted" does not mean "authenticated" (MM7).
  • Wrong delay trade. Making media reliable like TCP brings back head-of-line blocking (MM8). Growing a buffer to hide jitter only swaps network delay for buffer delay (MM3).
  • No feedback. Without a sender-side estimate of available bandwidth the sender cannot match its bitrate to the path, and the blueprint treats this as a control loop, not a one-shot formula (MM4).
  • Coupling. Teams that fuse the ICE state machine with the DTLS handshake, or the packetizer with the codec, cannot ship a custom congestion controller without a rewrite (§2, P1).

The blueprint's teaching claim is that no other single system covers NAT traversal, real-time congestion control and datagram-transport security together (§2).

How it works, end to end

Follow Alice's call through the boxes of §3's diagram. Everything below runs on one UDP port per PeerConnection (P2, §3). The diagram is adapted from §3, with crate names added from §10.

Application (native app / SFU / test harness)
  v
PeerConnection FSM   rtc-core (+ rtc-sdp, rtc-jsep)
  v  canonical SDP
ICE Agent            rtc-ice (+ rtc-stun, rtc-turn): gather -> pair -> check -> nominate
  v  selected (local,remote) pair
UDP mux              rtc-mux: first-byte demux (RFC 7983)
  |-- STUN/TURN bytes back to the ICE Agent
  v  DTLS bytes
DTLS layer           rtc-dtls: handshake, then key export (RFC 5764)
  v
SRTP/SRTCP           rtc-srtp  <-- TWCC/NACK/PLI feedback (rtc-rtcp-fb)
  v
RTP/RTCP + jitter    rtc-rtp  --> GCC (rtc-gcc) --> bitrate allocator (rtc-bwe)
  v
Codecs               rtc-codec-opus / -vp8 / -h264
SCTP-over-DTLS       rtc-sctp, rtc-datachannel: rides the same DTLS connection
  1. rtc-core, rtc-sdp, rtc-jsep. The PeerConnection finite-state machine is the only part the application touches. It owns the offer/answer text exchange (SDP, with the JSEP rules) and exposes the W3C connection states (§3, I12, I14).
  2. rtc-ice, rtc-stun, rtc-turn. The ICE agent gathers host, STUN-derived and TURN-relayed addresses, exchanges them as they appear (Trickle ICE), runs priority-ordered checks and nominates one pair (§3, P3, I1, I9).
  3. rtc-mux. It looks at the first byte of each datagram so ICE, DTLS and media share one 5-tuple (§3, ADR-04). The first-byte ranges in §3's diagram are DTLS 20–63 and STUN/TURN 0–19 and 64–79 (§3).
  4. rtc-dtls. One handshake establishes the session. Framing, fragmentation and retransmission are built on rustls's record layer (§3, ADR-06).
  5. rtc-srtp. Every media packet is authenticated and encrypted with keys from the DTLS exporter, never renegotiated per packet (§3, I2, I8).
  6. rtc-rtp, rtc-rtcp-fb. Packetizes codec output, reassembles on receive and reorders into presentation order in the jitter buffer (§3, I10). The feedback crate makes NACK, PLI, FIR and TWCC messages (§10).
  7. rtc-gcc, rtc-bwe. The sender-side estimator turns arrival-time feedback into a target bitrate that the allocator hands to the codec (§3, P8, I6).
  8. rtc-codec-opus, -vp8, -h264. Codecs are wrapped behind a uniform trait, so the rest of the stack is codec-agnostic (§3, §10, P1).
  9. rtc-sctp, rtc-datachannel. An independent reliable or partially reliable channel on the same DTLS connection, never blocking media (§3, I5, I7).

How these are driven: each protocol layer is a sans-IO state machine. It takes &[u8] and events in and emits bytes and events out, and never touches the socket. One tokio task per socket drives them (§3.1, P4, ADR-03). That is what makes each layer independently fuzzable (§3.1, P13). rtc-verifier is a deterministic simulator with one assertion per invariant (§7), and rtc-stats is the telemetry crate (§10, §24).

The core ideas

ICE: agreeing on one working path (§8.2, §16, I1, I9, MM1)

Each peer lists the addresses it might be reachable at (candidates): its own interface addresses (host), the public address a STUN server reports (server-reflexive), and an address on a TURN relay (relayed) (§3, §36). Every local address is combined with every remote address into a candidate pair (§16.2). The two sides rank pairs without talking to each other, because the formula is deterministic (§8.2):

priority = 2^32·MIN(G,D) + 2·MAX(G,D) + (G>D ? 1 : 0)

where G and D are the controlling and controlled agents' candidate priorities (§8.2). A candidate's own priority is a pure function of type preference, local preference and component ID, never changed after gathering (I9). Checks are paced at Ta = 50 ms by default (§16.2). The agent's states are (§8.2):

State Moves on when
New → Gathering gathering starts
Gathering → Checking gathering-complete event, or timeout (10 s)
Checking → Connected at least one pair Succeeded (first valid pair, I1)
Connected → Completed the controlling agent sets USE-CANDIDATE (nomination)
Disconnected all pairs stop responding; back to Checking if a pair recovers, else Failed on timeout

The key rule is I1: no pair is selected before a bidirectional STUN Binding check validates it. A response to one inbound check proves only one direction, so triggered checks cannot skip it (I1, §16.6). Nomination is regular, not aggressive: the controlling agent picks the highest-priority Succeeded pair only after checks settle (§16.2). The blueprint's model is that ICE is a consensus on one fact reached without a coordinator, so racing to the first success picks a low-priority pair (MM1, §16.6). In Alice's call, only the relayed pair answered, so it is nominated (§8.6 step 3).

DTLS-SRTP: a handshake whose product is keys (§8.3, §18, I2, I8, MM2)

The handshake's only real job is to produce symmetric keys (MM2). Once both sides have verified Finished, the DTLS exporter is called with the label "EXTRACTOR-dtls_srtp", its output is split into client and server write keys and salts, and rtc-srtp derives per-direction session keys from them (§8.3, §18.2).

Three checks guard it. Application data is decrypted only after Finished is verified (I2). The peer's certificate must match the SDP a=fingerprint byte for byte, which is the trust anchor and ties security to signaling (I8, T3). A failed check drops or tears down, with no plaintext fallback (P5). The exporter label "EXTRACTOR-dtls_srtp" must be exact. A typo produces no crash, only divergent keys and a 100% auth-tag failure rate downstream, so the blueprint pins a regression fixture for it (§8.3, §18.5, §18.6). The default cipher is AES-128-GCM (ADR-07).

Replay protection is a fixed-size sliding bitmask: ReplayWindow holds highest_seq and a 64-bit mask for a fixed 64-packet window, and SrtpContext keeps a 32-bit rollover counter (ROC) beside it for sequence-number wraps (§11, §18.2, P7). A packet outside the window is dropped, never processed (I3). Fixtures check that duplicates are dropped, in-window out-of-order packets are accepted, and the ROC increments on a wrap without a false replay (§18.5). The fixed size is deliberate: an unbounded set is a memory-growth DoS vector (P7, T4).

Jitter buffer: a delay budget, not a store (§19, I10, MM3)

Packets cross the network with uneven delay, so the receiver holds them briefly and plays them in order. The buffer is a priority queue keyed on RTP timestamp, with an adaptive depth of 20–300 ms driven by a smoothed estimate of inter-arrival jitter (an EWMA, RFC 3550 6.4.1) (§19.2, §4). It emits frames strictly in timestamp order and holds later frames rather than reordering (I10). A frame that arrives after its presentation deadline is dropped, not played late (§19.8). Insert and extract are O(log n) on a heap, and the blueprint puts the target depth at about 15 entries (300 ms ÷ 20 ms frames) (§19.7).

The reason for the 300 ms cap is MM3: growing the buffer trades network jitter for buffer-induced latency, so depth is capped even under sustained jitter (MM3, §4). Excess jitter then shows as dropped frames, not unbounded delay (§19.9, P6). Opus is packetized as one packet per 20 ms frame, and clock rates differ per codec (48 kHz for Opus, 90 kHz for VP8), so one clock rate cannot be assumed across streams (§19.2, §19.6).

GCC: a feedback loop that sets the bitrate (§8.4, §20, I6, I11, MM4)

The sender tags each outgoing packet with a transport-wide sequence number. The receiver batches arrival timestamps into RTCP feedback (TWCC). The sender runs a trendline filter over the inter-arrival delay gradient and labels the path Normal, Overusing or Underusing. A loss-based estimator runs alongside, and the lower of the two becomes the target bitrate (§8.4, I6). The allocator passes it to the codec, and neither side owns the other's state (§8.4, P8). Treating GCC as a control loop, not a formula, is MM4: a one-shot calculation oscillates under real noise.

Loss recovery sits beside it. A NACK is sent only for an observed gap and at most 2 times per lost sequence number (I11, §20.4). PLI and FIR ask for a new key frame when video is unrecoverable, and FEC parity packets cover up to 10% random loss (§20.2). If feedback stops, the estimator falls back to the loss-based value after a feedback_timeout of 2× the RTCP interval, then freezes at the last good rate after a second timeout instead of ramping to zero (§8.4, FM-6). The Phase 8 test steps available bandwidth 1 Mbps → 500 kbps → 2 Mbps and expects convergence within ±20% (§20.3).

Data channels: SCTP inside the same DTLS connection (§8.5, §21, I5, I7, MM5)

SCTP packets ride the already-established DTLS connection and never touch a raw UDP socket (§21.2). The association has a short state machine: Closed → CookieWait (INIT sent) → CookieEchoed (INIT-ACK received) → Established (COOKIE ACK received), ending with SHUTDOWN, SHUTDOWN ACK and Closed (§8.5).

A channel opens with a DATA_CHANNEL_OPEN message (DCEP) on a fresh stream that fixes label, reliability (reliable, partial-reliable by retransmit count, or partial-reliable by time) and ordering, and the peer replies DATA_CHANNEL_ACK. Each channel maps to exactly one SCTP stream (§8.5). A message over the negotiated maximum size is rejected before fragmentation (I7). MM5 explains why that limit exists apart from association-level flow control: streams sharing one association need an explicit fairness policy, or a large unreliable stream can starve a small reliable one (MM5). Backpressure is asymmetric: media drops but the data channel blocks on SCTP flow control (P6, ADR-24). A path failure after 5 consecutive RTO expiries aborts only the association, and the media path is unaffected (§8.5, §21.9).

The trade-offs — where engineers disagree

Rust, not C++ or Go (ADR-01)

Chosen: Rust 1.78+, because the attack surface is almost entirely untrusted-network parsers where one out-of-bounds read is a remote compromise, and ownership removes that class without GC pauses (§1, §9). Rejected: C++ (libwebrtc's choice, with a documented history of memory-safety CVEs) and Go (Pion's choice, whose 1–10 ms GC pauses conflict with the sub-millisecond SRTP/RTP path) (§1, T1). When the rejected choice is right: C++ wins with an existing mature codebase and no rewrite budget; Go wins when development velocity matters more than sub-millisecond tail latency (§9).

Sans-IO core with a tokio shim (ADR-03)

Chosen: protocol state machines take bytes and events and own no sockets, driven by a thin tokio layer. This enables independent fuzzing and embedding in any executor (§9, P4). Rejected: an I/O-owning core in libwebrtc's style (§9). When the rejected choice is right: exactly one deployment target that needs tight event-loop control, such as a browser process scheduled alongside capture and render threads (§9, §34.1). The cost of the chosen design is that callers must drive the event loop correctly (P4).

One UDP port by first-byte demux (ADR-04)

Chosen: RFC 7983 demultiplexing, for BUNDLE compatibility and a single firewall port (§9, P2). Rejected: separate ports per component (§9). When the rejected choice is right: legacy SIP/H.323 gateways that must not multiplex one 5-tuple (§9). The cost is that the mux is a single point of dispatch bugs (P2).

GCC, sender-side (ADR-09)

Chosen: send-side GCC over TWCC, for faster convergence, less feedback overhead and analytical tunability (§9). Rejected: REMB-only, NADA, and learned or data-driven controllers (§9). When the rejected choice is right: REMB for compatibility with pre-2016 endpoints; NADA under highly variable cellular links that its delay scaling handles better; a learned controller offline against a known, stable network profile where retraining cost is acceptable (§9).

SCTP over DTLS for data channels (ADR-12)

Chosen: SCTP-over-DTLS (RFC 8831/8261), giving multiplexed streams with per-stream reliability on the same DTLS connection as media (§9, §21.2). Rejected: raw DTLS datagrams and QUIC datagrams (§9). When the rejected choice is right: QUIC datagrams win once WebTransport is universal, because that removes head-of-line blocking (§9). The blueprint's frame for this choice is that reliability and congestion-safety are separate knobs (MM8).

Client-only TURN, delegate the server (ADR-14)

Chosen: ship the TURN client and validate against coturn, to avoid duplicating a mature server (§9, §1). Rejected: an embedded TURN server (§9). When the rejected choice is right: a single-binary edge appliance with no separate TURN operations surface (§9). The blueprint lists the embedded server as a deferred feature with that trigger (§35).

Media drops, data blocks (ADR-24)

Chosen: per-channel policy that matches reliability semantics: media drops, data channels block (§9, P6). Rejected: dropping everything uniformly (§9). When the rejected choice is right: a fire-and-forget telemetry channel with no reliability need (§9). Getting this wrong either stalls video indefinitely or silently drops a file-transfer chunk (P6).

Roads not taken (§34, §35)

An I/O-owning monolithic core (§34.1) wins when there is a single deployment target, such as a browser process, that needs tight scheduling with capture and render threads. Its real-world example is libwebrtc. It loses here because ADR-03's goal of plugging into any host's tokio runtime is structurally incompatible with an owned event loop, and it gives up P4's independent fuzzing (§34.1).

FFI-wrapping an existing C/C++ stack (§34.2) wins under hard deadline pressure with no budget for a rewrite, where the team already accepts an unsafe boundary. It loses here because it forfeits ADR-01's memory-safety goal at the boundary and makes congestion-control experiments mean patching a very large C++ build (§34.2).

A QUIC/WebTransport-native transport (§34.3) wins browser-to-server, greenfield, with no legacy WebRTC interop need. Media over QUIC is the blueprint's example. It loses here because QUIC has no P2P NAT-traversal story equal to ICE and browser support is not universal (§34.3).

A GStreamer webrtcbin-style pipeline (§34.4) wins in an organization already standardized on GStreamer. It loses here because it is native to the glib loop, not Rust or tokio, and its element-graph model obscures sans-IO testability (§34.4).

Deferred features (§35) each wait for a trigger. Examples: simulcast/SVC when per-viewer quality tiers are needed, E2EE insertable streams when the SFU must not see media, ICE-TCP when a target blocks all UDP egress, and hardware codec offload when CPU becomes the binding SFU constraint (§35).

What must never be false

  • I1: no pair is selected before a bidirectional STUN check validates it. Noticed when pair state is not Succeeded and nomination is blocked; ice_pair_state.
  • I2: DTLS application data is decrypted only after Finished is verified. Noticed by an epoch gate; dtls_handshake_state.
  • I3: SRTP/SRTCP packets outside the replay window are dropped. Noticed by a bitmask check; srtp_replay_drop_total.
  • I4: each SSRC maps to exactly one RtpSession. Noticed by a duplicate-SSRC check; rtp_ssrc_collision_total.
  • I5: SCTP TSN is strictly monotonic per stream. Noticed by a TSN gap detector; sctp_tsn_gap_total. The blueprint is not consistent here: I5, §21.2 and the glossary say per stream, while §11 keeps a single next_tsn on SctpAssociation (I5, §21.2, §36, §11).
  • I6: send bitrate never exceeds min(GCC estimate, encoder max). Noticed by a rate comparator; bwe_target_bps.
  • I7: an oversized DataChannel message is rejected before fragmentation. Noticed by a size precheck; dc_oversized_msg_total.
  • I8: the DTLS certificate fingerprint matches SDP a=fingerprint byte for byte. Noticed by a byte compare; dtls_fingerprint_mismatch_total.
  • I9: ICE priority is a pure function, never mutated after gathering. Noticed by an immutability check in tests; no telemetry because it is structural.
  • I10: the jitter buffer never emits frames out of timestamp order. Noticed by a monotonic-timestamp assert; jitter_reorder_violation_total.
  • I11: a NACK is sent only for an observed gap and within the retry ceiling. Noticed by a retry counter; nack_retry_exhausted_total.
  • I12: PeerConnection moves only along W3C-enumerated edges. Noticed by a transition-table lookup; pc_invalid_transition_total.
  • I13: every TURN allocation is refreshed before expiry or torn down. Noticed by an expiry countdown; turn_alloc_expiring, with a pre-emptive refresh at 80% of lifetime.
  • I14: SDP m-line order and count are preserved between offer and answer. Noticed by an ordinal comparison; sdp_mline_mismatch_total.

What breaks in production

FM-1: ICE failure, no valid pair. The connection reaches Failed before media starts. The cause is symmetric NATs on both sides with no TURN configured. Detection is the check-list snapshot showing all pairs Failed. There is no automatic recovery; the operator configures TURN (§23, §16.9).

FM-2: TURN allocation loss. Media stalls only on the relayed path after a TURN server crash or partition. The turn_allocation_active gauge drops. Failover is deferred, so the fix is an ICE restart with a fresh allocation (§23, §15.10, §35).

FM-3: DTLS handshake timeout. The call sticks in Connecting. Causes are a firewall blocking the DTLS byte range or a fingerprint mismatch. dtls_handshake_state stays non-Established. Retransmission runs until the timeout and then Failed; the operator checks a=setup and the fingerprint (§23, §17.10). Runbook R4 notes that both sides set to actpass is a configuration bug (§24).

FM-4: SRTP auth-tag failure spike. Audio and video are silent although the call is "connected". Causes are the exporter-label bug, an active MITM or a key mismatch. srtp_auth_failure_total spikes, and a sustained rate above 1% is the primary signal. There is no auto recovery because it fails closed (P5); the operator verifies the DTLS-SRTP profile negotiation (§23, §18.9).

FM-5: jitter buffer overflow. Glitches and dropped frames appear when sustained jitter exceeds the 300 ms cap. jitter_buffer_overflow_total counts it. Recovery is automatic bounded frame drop, because the design accepts media loss over unbounded latency (§23, §19.9, P6).

FM-6: GCC feedback starvation. Bitrate is frozen or slow to adapt after TWCC feedback loss or a receiver crash. A feedback-timeout counter detects it. The estimator falls back to loss-based and then freezes; the operator verifies the RTCP return path (§23, §20.9).

FM-7: SCTP path failure. The DataChannel closes while media continues, after 5 consecutive RTO expiries or an MTU blackhole. The application is notified through onclose; the operator can retry with a smaller MTU or a new association (§23, §21.9). §23 detects it as association state Aborted, a state that neither §11's AssociationState enum nor the §8.5 table lists (§23, §11, §8.5).

FM-10: process crash mid-call. Abrupt termination from OOM or a codec FFI crash escaping its boundary (T11). A supervisor restart event detects it, and the peer notices through consent-freshness timeout and re-establishes. Each process is crash-isolated (§23, §24, P10).

Threats worth knowing (§22):

  • T1, malformed packets aimed at any wire parser, is met by Rust ownership and fuzz-verified decoders. The packet is dropped and the process is unaffected; parser_decode_error_total (P13).
  • T3, a man-in-the-middle certificate swap in the DTLS handshake, is met by the fingerprint trust anchor tied to signaling (I8). The connection is torn down; dtls_fingerprint_mismatch_total.
  • T4, replay of captured packets, is met by the fixed replay window and TSN monotonicity (I3, I5, P7). The packet or segment is discarded; srtp_replay_drop_total, sctp_tsn_gap_total.
  • T7, disclosure of local or private IPs through host candidates, is met by a relay-only IceTransportPolicy. The operator enforces the Relay policy; ice_candidate_kind_total (§11).
  • T8, forged TWCC feedback to push the sender above the real bandwidth, is met by the loss-based cross-check and the min() rule (I6). Recovery is to clamp to the conservative estimate; bwe_estimator_disagreement.

The blueprint disagrees with itself in several places, left unresolved here:

  • Why 500? CM5 calls the per-connection CPU cost negligible and says that is why 500 connections per 8-core is achievable (§32 CM5). Hard question 4 calls CPU the binding constraint, and §29 sets the ceiling by the CPU budget (§33 item 4, §29). §4 also cites CM5 for the VP8 encode row, yet CM5 counts only SRTP (§4, §32 CM5).
  • The ICE timeout. §8.2 and a Phase 4 fixture put IceState::Failed at a 10 s timeout and cite §4 for it, but §4 has no such row. §16.9 gives a default 30 s aggregate (§8.2, §16.5, §16.9, §4).
  • What M1 measures. §4 and §28 define M1 as host+STUN, while Phase 4 tests it against 2 STUN + 1 TURN servers (§4, §28, §16.4).
  • ICE-Lite. §4 gives an ICE-Lite budget and §1 points to §14 and §15, but those phases describe host-only gathering (§14.8), not an ICE-Lite agent (§4, §1, §33 item 9).

How it compares

  • libwebrtc owns its whole event loop and threading model end to end. That is right when you control the entire browser process and need tight scheduling with render and capture threads (§31).
  • Pion chose Go's memory safety and small composable packages. That is right in teams already standardized on Go, where 1–10 ms GC pauses are acceptable (§31).
  • str0m is the closest sibling and pioneered the sans-IO pattern; it has an even more minimal API with no built-in signaling helpers. That is right for integrators who want zero opinionated glue and accept more integration work (§31).
  • mediasoup chose ICE-Lite only and pure forwarding, with no transcoding and no P2P. That is right for large conferencing where server CPU is the constrained resource (§31, §29).
  • aiortc chose Python/asyncio for approachability. That is right for research and prototyping where clarity beats the latency budgets this design holds as hard (§31).

If you only remember three things

Keep the layers independent, with sans-IO state machines that never touch a socket, so each can be fuzzed and swapped alone (P1, P4, P13). Trust nothing past the socket: a certificate fingerprint, a verified Finished, an auth tag and a replay window each gate the next layer, and failures drop or tear down (P5, I2, I3, I8). Real-time means bounded delay beats completeness for media, so the jitter buffer is capped and loss is repaired only within limits, while data channels block instead (MM3, I11, P6).

Words used here

  • NAT: a router that rewrites addresses, which hides a peer from direct contact (§1, MM6).
  • Candidate: an address and port a peer might be reachable at (§36).
  • ICE: the protocol that gathers candidates, tests pairs and nominates one (§36, §8.2).
  • STUN / TURN: STUN reports your public address; TURN relays traffic through a server (§36).
  • SDP / JSEP: the text envelope and the rules for offer/answer negotiation (§36, §8.1).
  • DTLS: TLS adapted for UDP; here its job is to produce the media keys (§36, MM2).
  • SRTP / SRTCP: authenticated-encrypted media and control packets (§36).
  • RTP / RTCP: the media wire format and its control and feedback channel (§36).
  • Jitter buffer: a reordering and delay buffer that smooths uneven arrival into steady playout (§36).
  • NACK / PLI / FEC: ask for a resend, ask for a new key frame, or repair loss with parity (§36).
  • GCC / TWCC: the sender-side bandwidth estimator and its per-packet arrival-time feedback (§36).
  • SCTP / DCEP: the data-channel transport and the message that opens a channel (§36, §8.5).
  • SFU: a server that forwards media without transcoding (§36).
  • Sans-IO: a state machine that takes bytes in and emits bytes out, owning no socket (P4, §3.1).
