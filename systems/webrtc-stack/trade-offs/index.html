Decisions (§9) · 25 ADRs

ADR-01

Language

Chosen

Rust 1.78+ MSRV

Rejected

C++ (libwebrtc), Go (Pion)

When the rejected choice is right

C++ wins with an existing mature codebase and no rewrite budget; Go wins when dev velocity > sub-ms tail latency

Why: memory safety on untrusted-input parsers without GC pauses

ADR-02

Async runtime

Chosen

tokio

Rejected

async-std, bare epoll

When the rejected choice is right

bare epoll wins in a no_std embedded target with no allocator

Why: ecosystem maturity, rustls/quinn interop

ADR-03

Core I/O ownership

Chosen

sans-IO core + tokio IO shim

Rejected

IO-owning core (libwebrtc-style)

When the rejected choice is right

IO-owning core wins with exactly one deployment target needing tight event-loop control

Why: independent fuzzing/embedding (P4)

ADR-04

Port multiplexing

Chosen

first-byte demux (RFC 7983)

Rejected

per-component separate ports

When the rejected choice is right

separate ports win for legacy SIP/H.323 gateways that must not multiplex one 5-tuple

Why: BUNDLE compatibility, firewall simplicity

ADR-05

DTLS version

Chosen

Rejected

DTLS 1.2-only

When the rejected choice is right

1.2-only wins for interop with legacy endpoints lacking 1.3

Why: latest security, RFC 9147 improvements

ADR-09

Congestion control

Chosen

GCC (send-side, TWCC)

Rejected

REMB-only, NADA, learned/data-driven CC (Remy-style, Pa6)

When the rejected choice is right

REMB wins for compatibility with pre-2016 endpoints; NADA wins under highly variable cellular links its delay-scaling handles better; learned CC wins offline against a known, stable network profile where retraining cost is acceptable

Why: faster convergence, less feedback overhead, analytically tunable (Pa1)

Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

IO-Owning Monolithic Core (libwebrtc-style)

┌─────────────────────────────┐
│  Single owned event loop    │
│  (ICE + DTLS + SRTP + RTP   │
│   all scheduled by one      │
│   thread pool, no external  │
│   IO handoff)                │
└─────────────────────────────┘

Regime where it wins: a single deployment target (a browser process) needing tight scheduling coordination with capture/render threads. Real system: libwebrtc. Rejected because: ADR-03's embedding goal (this stack must plug into any host application's existing tokio runtime) is structurally incompatible with an owned event loop; also loses P4's independent-fuzzing benefit.

FFI-Wrap an Existing C/C++ Stack

┌───────────────┐    cxx bridge    ┌─────────────────┐
│  Rust app code│ ◄──────────────► │  libwebrtc (C++) │
└───────────────┘                  └─────────────────┘

Regime where it wins: hard deadline pressure with no budget for a from-scratch reimplementation; an existing team already ships C-linkable binaries and accepts an unsafe FFI boundary. Real system: several commercial products wrap libwebrtc via a Rust webrtc-sys-style bridge. Rejected because: it forfeits ADR-01's memory-safety goal at the FFI boundary and makes custom congestion-control experimentation (ADR-09) require patching a multi-GB C++ build.

QUIC/WebTransport-Native Transport

┌────────────────────────────────────────────┐
│  QUIC connection (built-in encryption,      │
│  congestion control, stream multiplexing)   │
│  — replaces ICE+DTLS+SRTP+SCTP entirely     │
└────────────────────────────────────────────┘

Regime where it wins: browser-to-server only, greenfield deployment, no legacy WebRTC interop requirement. Real system: Media over QUIC (MoQ) / WebTransport experimental deployments (Meta, Cloudflare). Rejected because: QUIC has no P2P NAT-traversal story equivalent to ICE, and (as of this writing) browser support is not universal enough to drop WebRTC interop (§1 scope requires interop with real browsers, §16.5).

GStreamer webrtcbin-style Plugin Pipeline

┌───────────────────────────────────────────────┐
│  glib main loop → GStreamer element graph       │
│  (webrtcbin, dtlssrtpenc, rtpbin, ...)          │
└───────────────────────────────────────────────┘

Regime where it wins: an organization already standardized on GStreamer media pipelines wanting to add WebRTC as one more element graph, reusing existing pipeline tooling. Real system: GStreamer's webrtcbin. Rejected because: it is glib-event-loop-native, not Rust/tokio-native, requiring a bridge thread to embed in this stack's target applications (ADR-02), and its element-graph model obscures the sans-IO testability this design prioritizes (P4, P13).
