Project Number: 167

Project Name: Feature Flags + A/B Testing Service

Status: specification — locked

1. Goal & Scope

Build, from scratch in Rust, a feature-flag and controlled-experimentation system: a deterministic flag/segment/rule evaluation engine that runs identically inside every SDK process; a control plane that authors flags, segments, and experiments and persists them transactionally with an append-only audit log; a config compiler that turns authored state into an immutable, versioned, internally-consistent ConfigDocument; a delivery service that fans that document out to SDK instances over a streaming transport with a polling fallback; an exposure/assignment event ingestion path that records what each evaluation context actually saw; and a statistics pipeline that turns exposure and goal events into experiment results under sequential-testing guardrails so that peeking does not manufacture false winners. The engineering core is Kohavi, Tang & Xu's thesis in Trustworthy Online Controlled Experiments (2020): trustworthiness is a property of the whole pipeline — deterministic bucketing, correct exposure logging, and valid-under- peeking inference — not of any one component in isolation.

1.1 Phase-0 deliverable — initial crate skeleton

  1. ff-core — domain types (Flag, Variant, Segment, EvaluationContext) and the evaluation trait surface; no I/O.
  2. ff-bucketing — the hash-to-bucket function and salt/seed model; no I/O.
  3. ff-rules — the targeting-rule grammar, parser, and typed AST; no I/O.
  4. ff-config — ConfigDocument schema and versioning types.
  5. ff-xtask — workspace build/lint/fixture-generation automation (cargo xtask pattern).
  6. ff-conformance-vectors — the (initially empty) shared cross-language fixture corpus.
  7. CI workflow skeleton (.github/workflows/ci.yml) running cargo fmt --check, cargo clippy -D warnings, cargo test across the above five crates.

1.2 Boundaries

Provides: flag/segment/rule storage and CRUD; deterministic local evaluation; versioned config compilation and delivery (streaming + polling); an embeddable SDK runtime; exposure-event collection with deduplication; experiment lifecycle management; a frequentist-sequential statistics pipeline with guardrail and SRM checks; an append-only audit log; a threat-model-scoped auth/authz boundary for the control plane.

Delegates: goal-event collection to the host application's existing analytics stack (the platform ingests goal events over a defined schema, it does not instrument business logic); long-term columnar storage operations (backup, compaction tuning) to the operator's chosen store; TLS termination to the deployment's ingress (PhaseDeferred("§26 Operational Readiness") for the mTLS-everywhere posture); notification/paging integration to the operator's existing on-call tooling.

Does NOT provide: a general analytics platform (Amplitude/Mixpanel replacement); a multi-armed-bandit auto-optimizer (PhaseDeferred("§36 Alternative Architectures") notes why a decision-theoretic layer is a different system); a user-profile/CDP ingestion pipeline; a multi-region active-active control plane with automatic conflict resolution (single-primary with read replicas only, PhaseDeferred("§31 Scalability Analysis")).

1.3 Non-goals

Not a general-purpose remote-config service for non-flag data; not a permissions system beyond the three-role model needed for audit correctness; not a machine-learning targeting engine; not a mobile-app build-time toggle system (that is compile-time, this is runtime).

1.4 Deployment model

Three tiers: (1) control plane — stateful, holds the transactional store and audit log, exposes the authoring API; (2) edge delivery service — stateless, holds the compiled ConfigDocument in memory, terminates SDK streaming/polling connections, horizontally scaled independent of control-plane load; (3) embedded SDK — a library linked into the host application process, holding a local copy of the config and evaluating with zero network calls per evaluation. Statistics pipeline and ingestion queue run as separate worker tiers reading from the exposure-event queue.

1.5 Users / operators

Flag authors (product/eng, use the control-plane UI/API); SDK integrators (backend and client engineers embedding ff-sdk); experiment analysts (read StatsResult, decide ship/rollback); platform operators (run control plane, delivery service, ingestion queue, stats workers; own the kill-switch runbook).

1.6 What later phases unlock

Phase 0's skeleton unlocks Phase 1's rule engine; Phase 2's deterministic bucketing unlocks Phase 3's config compiler emitting stable variant assignments; Phase 4's SDK unlocks Phase 5's streaming delivery; Phase 6's exposure collector unlocks Phase 8's experiments, which unlock Phase 9's statistics, which Phase 10 extends with overlapping layers; Phase 11 hardens the whole pipeline to conformance and perf gates.

1.7 Why Rust, and rejected languages

Rust gives the SDK's hot evaluation path (target: sub-microsecond, §4) allocation-free, panic-free (via #![forbid(unsafe_op_in_unsafe_fn)] and exhaustive Result handling) execution with no GC pause risk — a GC pause on the evaluation path is a latency-SLO violation embedded in every request of every host application. Go was rejected: GC pauses are directly on the hot path the SDK is embedded into, and the reference implementations (LaunchDarkly's Go SDK, Unleash's Go core) already show this tradeoff accepted, not avoided. Java/JVM was rejected for the embedded-SDK case for the same GC reason, though acceptable for the control plane; the spec keeps one language across the workspace for shared fixture/property-test infrastructure. Node/TypeScript was rejected as the core implementation language (acceptable as an SDK binding target, Phase 11) because single-threaded event-loop evaluation cannot guarantee the p99 latency budget under host-application load. Python was rejected outright for anything on the evaluation path — GIL and interpreter overhead violate the sub-microsecond target by two to three orders of magnitude.

1.8 Prerequisites

Working knowledge of Rust ownership/concurrency (Arc, ArcSwap), basic probability and hypothesis testing, HTTP/gRPC and Server-Sent Events, and a relational store (Postgres) plus a columnar store (ClickHouse) at an operational level.

1.9 Timeline

Solo engineer, evenings/weekends pace: Phase 0–2 (schema, rules, bucketing) 3 weeks; Phase 3–5 (config compiler, SDK, delivery) 4 weeks; Phase 6–8 (ingestion, control-plane API, experiments) 4 weeks; Phase 9–10 (stats, overlapping layers) 4 weeks; Phase 11 (conformance + perf hardening) 2 weeks. ~17 weeks to a god-bar-complete system.

1.10 Deferrals

PhaseDeferred("§26 Operational Readiness") — automatic mTLS certificate rotation across the fleet; PhaseDeferred("§31 Scalability Analysis") — multi-region active-active control plane; PhaseDeferred("§36 Alternative Architectures") — bandit auto-optimization; PhaseDeferred("§30 Performance Engineering") — SIMD-vectorized clause evaluation for very-high-cardinality rule sets.

2. Why Build This

  • Distributed-configuration-cache correctness: agreement over freshness.
  • Deterministic bucketing as a pure function — the single hardest invariant to keep.
  • Streaming delivery under partition: offline-safe evaluation, not "the API is down."
  • Statistical validity under continuous monitoring — peeking is not a bug, it is the default failure mode of naive A/B testing.
  • Kill-switch as a latency- and trust-critical control path, not a UI feature.
  • Audit-as-forensics: every production behavior change must be attributable.
  • Cross-language parity: the same bucket decision on every SDK, every language, forever.
  • Overlapping-experiment layers as a scarce-resource allocation problem (traffic is the resource).

What Mastery Looks Like

  • Writing an evaluator that is provably side-effect-free and allocation-free on the hot path — demonstrated in Phase 1's rule engine and Phase 4's SDK local evaluator.
  • Proving bucketing stability under weight changes and reshuffling under salt changes with a worked equation, not an assertion — demonstrated in Phase 2.
  • Building a config document that is versioned, internally consistent, and diffable — demonstrated in Phase 3's config compiler.
  • Implementing SSE streaming with a correct reconnect/backoff/polling-fallback state machine under a thundering-herd restart — demonstrated in Phase 5.
  • Implementing exposure-event deduplication that survives replay without inflating experiment sample size — demonstrated in Phase 6.
  • Implementing a sequential test (always-valid confidence sequence) that gives a provably valid stopping rule under daily peeking — demonstrated in Phase 9.
  • Designing an overlapping-layer allocation model that lets independent teams run experiments on shared traffic without interaction — demonstrated in Phase 10.
  • Building and passing a third-party-consumable conformance suite across languages — demonstrated in Phase 11.

Control-plane API: the only trust boundary allowed to mutate flag/segment/experiment state; every mutation is authenticated, authorized, and appended to the audit log before it can reach the config compiler.

Flag/experiment store: Postgres, transactional, the single source of truth for authored (not yet compiled) state; Flag, Segment, Experiment rows keyed by (environment_id, key).

Config compiler: pure transformation from authored state to an immutable ConfigDocument at a monotonically increasing ConfigVersion; never partially applies.

Delivery service (streaming + polling fallback): stateless, holds the current ConfigDocument per environment in memory, terminates the concurrency boundary between one control-plane publish and N SDK connections.

SDK local evaluator: runs inside the host application process; holds the last-known ConfigDocument; evaluates offline; is the trust boundary between untrusted request attributes and the flag decision.

Bucketing function: a pure function of (salt, unit id); no I/O, no mutable state; the one component whose output must never change silently.

Exposure-event collector: SDK-side batching and shipping of ExposureEvent records; crosses the persistence boundary into the ingestion queue.

Ingestion queue: durable, at-least-once, the concurrency boundary between many SDK producers and one stats-pipeline consumer.

Stats pipeline: reads exposure and goal events, computes StatsResult per experiment under a SequentialBoundary, runs SRM and guardrail checks.

Results store: ClickHouse, append-only, columnar, holds exposures, goal events, and computed results.

Audit log: append-only, hash-chained, the forensic trust boundary for "who changed what."

Telemetry: metrics, traces, and structured logs emitted at every tier boundary crossing above (§26 names the concrete signals).

6. Design Principles

P1 — Evaluation is local, deterministic, and offline-safe. Rule: evaluation never performs I/O and never blocks on the delivery service being reachable. Tradeoff: the SDK may serve a stale config during a partition. Operational implication: a network partition serves the last-good config, never an error. Violating it: any evaluation that calls out to the control plane turns every partition into an outage.

P2 — Bucketing is a pure function of (salt, unit id). Rule: bucket(salt, unit_id) takes no other input and has no side effects. Tradeoff: cannot incorporate live traffic-shaping without changing the salt (which reshuffles). Operational implication: the same user lands in the same variant on every host, every language, forever. Violating it: any hidden dependency on evaluation order or wall-clock time breaks cross-request consistency (I2).

P3 — A served config is always internally consistent. Rule: the config compiler emits ConfigDocument atomically; SDKs never observe a document with some flags at version N and others at N+1. Tradeoff: compilation is all-or-nothing, occasionally higher latency than incremental patching. Operational implication: SDK swaps are single atomic pointer stores. Violating it: partial application produces flags whose targeting rules reference a segment version that no longer exists (I3).

P4 — A flag's default is returned on any evaluation error, never a panic. Rule: every evaluation path returns Result-shaped outcomes internally but the public API signature always yields a value, falling back to the caller-supplied default. Tradeoff: silent masking of authoring bugs unless telemetry is watched. Operational implication: EvaluationReason::Error must be observable even though the value returned is the default. Violating it: an unhandled panic in a flag evaluation call inside a request handler takes down the host application (I5).

P5 — Exposure is emitted exactly once per evaluation that reaches an experiment variant. Rule: the SDK emits one ExposureEvent per (flag, unit id, evaluation context) combination that resolves through an experiment-bound rule, deduplicated within a bounded window. Tradeoff: a dedup window bounds memory but can under- or over-count at the boundary. Operational implication: sample-ratio mismatch detection depends on this being right. Violating it: exposure-event spam inflates apparent sample size and corrupts SRM detection (I4, T4).

P6 — An experiment's read is only valid once its guardrail says so. Rule: a StatsResult is not surfaced as decision-ready until SRM passes and the sequential boundary has been evaluated. Tradeoff: analysts must wait even when they are impatient. Operational implication: the UI must show "not yet valid," not merely delay the number. Violating it: a naive daily t-test surfaced without SRM/sequential gating leads to a ~30% effective false-positive rate under routine peeking (Johari et al. 2017).

P7 — Config delivery degrades to polling, never to silence. Rule: if the streaming transport fails past a bounded retry budget, the SDK falls back to polling; it never simply stops updating. Tradeoff: polling has higher propagation latency (§4). Operational implication: version-drift telemetry must distinguish "polling, on time" from "stuck." Violating it: an SDK stuck on a stale ruleset with no fallback is indistinguishable from a working one until an incident (FM-3).

P8 — The bucketing function's output is a permanent compatibility commitment. Rule: the hash function, its input concatenation order, and its modulus are frozen once shipped; any change is a new named bucketing version, not a silent update. Tradeoff: cannot "fix" a suboptimal hash without a coordinated migration. Operational implication: cross-language conformance vectors pin this forever (§27, §28). Violating it: silently changing the hash reshuffles every running experiment's assignments (FM-1).

P9 — Rules evaluate in a total, documented order. Rule: targeting rules are evaluated by explicit priority, first match wins, with a fully specified precedence for clause conjunction/disjunction (§8 EBNF). Tradeoff: authors must understand priority semantics; ambiguity is not allowed. Operational implication: two rules that look "equally specific" still have a deterministic winner. Violating it: nondeterministic rule ordering makes evaluation traces non-reproducible (I1).

P10 — Unknown rule constructs fail closed to "does not match," not to a crash. Rule: an SDK that receives a config referencing an operator or field it does not recognize treats that clause as non-matching and continues evaluating the remainder. Tradeoff: forward compatibility trades off against silent behavior changes on old SDKs. Operational implication: rule-language evolution (§27) requires this contract explicitly. Violating it: shipping a new Operator variant crashes every SDK that has not yet upgraded (FM-9).

P11 — Audit is append-only and independent of application privilege. Rule: the database role the application uses has no DELETE/UPDATE grant on the audit table; only a separate retention job (time-boxed, itself audited) may prune past the retention window. Tradeoff: storage grows monotonically absent that job. Operational implication: compliance exports are always reconstructable. Violating it: an application bug or a compromised credential could otherwise erase the forensic trail (T6).

P12 — Overlapping experiments share traffic through explicit layers, not implicit independence. Rule: two experiments only run concurrently on the same traffic without interaction if they are declared in non-conflicting layers of a domain (Tang et al. 2010). Tradeoff: layer administration is extra authoring overhead. Operational implication: mutual exclusion is a first-class object, not a convention. Violating it: unmanaged concurrent experiments on correlated metrics corrupt each other's estimates (§10 layer model).

P13 — Statistics are computed off the hot path, never inline with evaluation. Rule: the stats pipeline consumes exposure/goal events asynchronously; it has no call-path dependency from evaluation. Tradeoff: results always lag reality by the freshness-lag budget (§4). Operational implication: "live" experiment dashboards are near-real-time, not real-time. Violating it: coupling stats computation to the evaluation path reintroduces the exact latency risk P1 exists to prevent.

P14 — Every destructive control-plane action requires typed confirmation and is maximally audited. Rule: flag/segment/environment deletion requires an explicit confirmation token and produces an audit entry with full before-state serialized. Tradeoff: friction on legitimate bulk cleanup. Operational implication: a 24-hour soft-delete/undo window is the compensating control. Violating it: an accidental one-click deletion becomes unrecoverable (§25 FM-7, informed by the GitLab 2017 incident).

Debugging methodology. Every invariant above is exercised by (a) a targeted unit or property test in the owning phase's N.5 fixtures, (b) a piece of telemetry that fires the instant the invariant is violated in production, and (c) a documented recovery path that does not require code changes under incident pressure. The standing debugging loop when an invariant appears broken: reproduce with the exact (flag, context, ConfigVersion) triple from telemetry, replay it against the pinned conformance vectors (Phase 2/11), and only then suspect the rule authoring rather than the evaluator.

8.2 Targeting-rule grammar (EBNF)

rule        := clause_list , priority ;
clause_list := clause , { "AND" , clause } ;
clause      := attribute , operator , value_list , [ "NEGATE" ] ;
operator    := "EQ" | "NEQ" | "IN" | "GT" | "LT" | "CONTAINS"
             | "STARTS_WITH" | "ENDS_WITH" | "MATCHES" | "SEGMENT_MATCH"
             | "SEMVER_EQ" | "SEMVER_GT" | "SEMVER_LT"
             | "DATE_BEFORE" | "DATE_AFTER" ;
attribute   := identifier ;
value_list  := value , { "," , value } ;
value       := string | number | boolean | semver | date ;

Operator / type-coercion table

Operator Valid types Coercion Missing attribute
EQ / NEQ any none false unless NEGATE
IN any none false unless NEGATE
GT / LT number, semver, date numeric compare false unless NEGATE
CONTAINS/STARTS_WITH/ENDS_WITH string none false unless NEGATE
MATCHES string (RE2-class regex) none false unless NEGATE
SEGMENT_MATCH segment key resolves to Segment evaluated against segment's own clauses
SEMVER_* string parsed as semver invalid string → non-match false unless NEGATE
DATE_* string parsed as RFC 3339 invalid string → non-match false unless NEGATE

Evaluation-order precedence: clauses within a rule are AND-combined, evaluated left-to-right with short-circuit on first false; clauses within a segment are OR-combined; rules within a flag are walked by descending priority, first full match wins (I6); an unknown operator value evaluates to non-match per P10/I7.

8.3 Deterministic bucketing model

Given salt s, unit id u, and rollout entries with weights w_1..w_k summing to W = 100000:

h(s, u)  =  MurmurHash3_32( s || "." || u )
bucket(s, u)  =  h(s, u) mod 100000

Variant assignment: accumulate weights A_i = Σ_{j≤i} w_j; assign variant i where A_{i-1} ≤ bucket(s,u) < A_i.

Worked example — stability under weight change. s = "exp-42", u = "user-777", h(s,u) mod 100000 = 61,204. Weights [50000, 50000] (50/50): A_1=50000, bucket 61204 falls in [50000, 100000) → variant 2. Weights change to [40000, 60000] (rebalance toward variant 2): A_1=40000, bucket 61204 still falls in [40000, 100000) → variant 2 — unchanged, because bucket 61204 never crossed a boundary that moved away from it. A user near the old boundary (e.g. bucket 45000) would move from variant 1 to variant 2 — this is the documented, acceptable "boundary users move" cost of weight changes, not a bug.

Worked example — reshuffle under salt change. Same u, new salt s' = "exp-42-v2": h(s', u) mod 100000 = 8,431 → a completely uncorrelated bucket, landing in variant 1 under the same [50000,50000] split. Changing the salt is the only supported way to intentionally re-randomize a population (§9 experiment lifecycle, "restart").

8.7 Statistics model — display equations

Variance estimation (per-variant sample mean/variance for a continuous metric):

x̄_v = (1/n_v) Σ x_i,      s_v² = (1/(n_v - 1)) Σ (x_i - x̄_v)²

CUPED adjustment (Deng et al. 2013), using pre-experiment covariate Y:

X_cuped = X - θ(Y - Ȳ),     θ = Cov(X, Y) / Var(Y)

reducing post-adjustment variance to Var(X_cuped) = Var(X)(1 - ρ²) where ρ is the correlation between X and Y — the mechanism by which CUPED shortens days-to-significance without inflating Type-I error.

Sequential-test boundary (time-uniform confidence sequence, Howard et al. 2021 form, mixture-based per Johari et al. 2017):

CS_t = [ θ̂_t ± ( σ̂_t / √n_t ) · √( 2 (n_t ψ + 1) / n_t² · ln( (n_t ψ + 1) / α² ) ) ]

where θ̂_t is the running effect estimate, ψ a tuning parameter for the mixing distribution, and α the desired always-valid Type-I error rate. An experiment may be concluded the instant 0 ∉ CS_t, at any t, with the Type-I error still bounded by α — the property naive fixed-horizon t-tests do not have under repeated peeking.

8.8 Worked evaluation trace

Context {unit_id: "u-9", country: "US", plan: "pro"}; flag checkout-v2 enabled, rule R1 {country EQ "US" AND plan EQ "pro"} priority 10 → variant treatment; rule R2 {country EQ "US"} priority 5 → 50/50 rollout. Evaluation: flag enabled → walk rules descending priority → R1 (priority 10) clauses both match → return treatment, EvaluationReason::TargetMatch{rule_id: R1}. R2 never evaluated (first-match-wins, I6).

8.9 Malformed-rule examples

{attribute: "plan", operator: "SEGMENT_MATCH", values: ["nonexistent-seg"]} — segment key does not resolve → clause is non-match (P10), not an error. {operator: "FUTURE_OP_V9"} from a newer control plane read by an older SDK — unrecognized operator → non-match (I7). Rollout weights [30000, 30000] summing to 60,000 — rejected at save time (I13), never reaches an SDK.

8.10 Failure-path example

Delivery service publishes ConfigVersion(118) but the SDK's TCP write for the streaming delta times out mid-flight. SDK detects an incomplete frame (length-prefixed delta parse failure), discards the partial delta, and requests a full document resend at its last-known-good version rather than applying a corrupt partial state — preserving I3.

12. Phase 0 — Skeleton + Flag Schema + CI

12.1 Objectives

Stand up the Cargo workspace, the ff-core flag/variant/segment schema (no evaluation logic yet), and a CI pipeline that gates every subsequent phase on fmt/clippy/ test. This phase produces no evaluator — it produces the types §11 signatures the rest of the system compiles against.

12.2 Detailed Implementation Steps

Define FlagKey, Flag, Variant, VariantId, FlagType, Segment per §11's signatures, satisfying P1 (no I/O in ff-core — enforced by the crate having zero runtime dependencies beyond serde). Add rust-toolchain.toml pinning the compiler (ADR-03 reproducibility). Add the initial ff-xtask command xtask fixtures generate (stub, populated in Phase 2).

12.3 Deliverable

A workspace that builds (cargo build --workspace), a green CI run on an empty-logic PR, and Flag/Variant/Segment types with round-trip serde (de)serialization tests.

cargo test --workspace passes with ≥15 unit tests across ff-core; CI completes in under 3 minutes; cargo clippy reports zero warnings; a Flag with 2 variants round-trips through JSON serialization byte-for-byte-equivalent after re-parse.

None yet measurable — this phase has no hot path. The concern to pre-empt: keep Flag's field layout #[repr(Rust)] simple (Vecs, no nested Box<dyn Trait>) so Phase 1's evaluator can walk it without indirection surprises later.

A Flag with a single variant (edge of "2+ for non-boolean" rule) — reject at construction. A FlagKey containing non-ASCII characters — accept (UTF-8 throughout) but document that delivery-service HTTP headers (Phase 5) will percent-encode it.

12.9 Failure Analysis

If CI silently stops running clippy (workflow YAML regression), the earliest signal is a merged PR with dead code — mitigated by branch protection requiring the specific clippy job as a required check, not just "CI / build."

12.10 Operational Notes

No production deployment yet. BUILD_PLAN.md gets its first phase-tracking row here; BLUEPRINT_LOG.md records the workspace-crate-boundary decision for future phases to respect.

13. Phase 1 — Rule Language + Evaluation Engine

13.1 Objectives

Implement the targeting-rule EBNF grammar (§8.2) as a typed AST, the clause-matching operator table, and the pure evaluate() function satisfying P1 (no I/O), P4 (infallible public surface), and I6 (total, documented rule order).

13.2 Detailed Implementation Steps

Build ff-rules::ast types (Rule, Clause, Operator) per §11. Implement the parser from the EBNF grammar in §8.2 using a hand-written recursive-descent parser (no external parser-combinator dependency, keeping ff-rules dependency-light per ADR-03). Implement clause_match per the operator/type-coercion table (§8.2), with unknown Operator variants matching P10/I7 (non-match, never a parse error that propagates to the caller). Implement evaluate(): (1) disabled flag → off_variant (EvaluationReason::FlagOff); (2) walk targeting sorted by descending priority, first full match wins (I6); (3) fall through to top-level rollout if present; (4) else default_variant. Regex clauses (Matches) use an RE2-class engine (non-backtracking) to close the ReDoS class of bug documented in FM-6.

13.3 Deliverable

ff-rules crate with a parser and ff-core::evaluate() passing the worked trace from §8.8 and the malformed-rule cases from §8.9.

13.4 Acceptance Criteria

100% of §8.9's malformed-rule fixtures evaluate to non-match rather than panicking; evaluate() completes the worked trace (§8.8) returning treatment via R1; property test asserts evaluation never allocates on the matched-first-rule fast path (checked via a custom allocator counter in the test harness).

13.5 Conformance Fixtures

fixtures/phase1/worked_trace.json — the exact §8.8 scenario, expected output variant=treatment, reason=TargetMatch{rule_id=R1}. fixtures/phase1/malformed_unknown_operator.json — a clause with operator="FUTURE_OP_V9", expected non-match. fixtures/phase1/malformed_segment_missing.json — SEGMENT_MATCH referencing an absent segment key, expected non-match. fixtures/phase1/priority_tiebreak.json — two rules at equal priority, expected deterministic winner by declaration order (documented tiebreak, extends I6). fixtures/phase1/regex_redos_candidate.json — a catastrophic-backtracking-shaped pattern, expected rejection at parse time, not slow evaluation.

13.6 Pitfalls

Using a backtracking regex engine — manifests as CPU spikes under adversarial input (FM-6); root cause is accepting arbitrary regex syntax; debug via CPU profiling under fuzzed regex inputs; fixed by adopting an RE2-class engine at parse time. Silent operator-list drift between the EBNF grammar (§8.2) and the Operator enum — root cause: two sources of truth; debug by a doc-test that asserts enum variant count matches grammar operator count. Treating "first match wins" as "highest specificity wins" — a common misreading; root cause: no explicit priority documented by the author; debug by requiring priority to be non-optional at the type level.

13.7 Performance Concerns

Clause evaluation must not allocate per call — string comparisons borrow, never clone, attribute values compared by reference. Rule-list sort-by-priority must happen once at config-compile time (Phase 3), not per evaluation — evaluation always receives a pre-sorted Vec<Rule>.

13.8 Edge Cases

A rule with zero clauses (vacuously true) — accepted, matches unconditionally; a rare but valid "always this variant to remaining N%" authoring pattern. A flag with zero targeting rules and no rollout — falls straight to default_variant. Duplicate priority values across many rules — deterministic tiebreak by declaration order, tested explicitly (priority_tiebreak.json).

13.9 Failure Analysis

A rule referencing a segment that is later deleted — the compiled ConfigDocument (Phase 3) must reject the segment deletion while a live reference exists, but if it somehow reaches the evaluator, SEGMENT_MATCH treats a missing key as non-match (P10), never a panic — this is the last line of defense, not the primary control.

13.10 Operational Notes

Ship the operator/type-coercion table (§8.2) as generated documentation from the Operator enum via a doc-comment lint, so the grammar and the docs cannot drift silently — referenced by ADR-24's testing-strategy gate.

14. Phase 2 — Deterministic Bucketing + Cross-Language Parity Vectors

14.1 Objectives

Implement the bucketing function (§8.3) satisfying P2 (pure function of salt+unit id) and I2/I8 (cross-language, cross-version stability), and produce the first shared conformance vector corpus other language SDKs will be measured against.

14.2 Detailed Implementation Steps

Implement ff-bucketing::hash(salt, unit_id) -> u32 using MurmurHash3 (ADR-06), concatenating salt || "." || unit_id exactly as specified in §8.3 — the concatenation order and separator are part of the frozen contract (P8). Implement pick_variant(rollout, bucket) via the cumulative-weight walk in §8.3. Generate ≥100,000 (salt, unit_id) pairs and record (pair, expected_bucket) into conformance/bucketing_vectors.json — this file, not any language's implementation, becomes the source of truth (lesson from the Flagsmith reference-impl pitfall, §5). Write the chi-square uniformity property test (bucket distribution within tolerance across 1,000,000 synthetic unit ids, tied to §34's derivation). Implement the two worked-example assertions from §8.3 (weight-change stability, salt-change reshuffle) as literal unit tests, not just prose.

14.3 Deliverable

ff-bucketing crate, conformance/bucketing_vectors.json (≥100,000 rows), and a passing chi-square uniformity test at the tolerance derived in §34.

14.4 Acceptance Criteria

Bucket distribution across 1,000,000 synthetic unit ids passes a chi-square goodness- of-fit test at p > 0.01 against a uniform null (tolerance derived in §34); the weight-change worked example (§8.3) reproduces variant 2 unchanged for user-777 under both [50000,50000] and [40000,60000]; the salt-change worked example reproduces an uncorrelated bucket for the same unit id.

14.5 Conformance Fixtures

conformance/bucketing_vectors.json — the ≥100,000-row cross-language parity corpus (salt, unit_id, expected_bucket, expected_variant for a fixed 2-variant 50/50 rollout). fixtures/phase2/weight_change_stability.json — the §8.3 worked example, both weight sets. fixtures/phase2/salt_reshuffle.json — the §8.3 salt-change worked example. fixtures/phase2/uniformity_1e6.json — the 1,000,000-unit-id sample used for the chi-square test, checked into the fixture corpus for regression stability (re-running must reproduce the same bucket assignments byte-for-byte, per I8).

14.6 Pitfalls

Changing the salt-and-unit-id concatenation order (e.g. unit_id || "." || salt) during a "cleanup" refactor — manifests as every existing bucket assignment silently reshuffling (a direct P8/I8 violation); root cause: treating the hash input format as an implementation detail instead of a frozen contract; debug via the conformance vectors failing en masse; recovery requires a new named bucketing version, never an in-place fix. Off-by-one in the cumulative-weight walk (<= vs <) causing the last variant to be unreachable or double-counted at a boundary — debug via a boundary-value unit test at bucket == A_i exactly. Assuming MurmurHash3's reference C implementation and a Rust port agree bit-for-bit without testing — verify against the vectors, not by inspection.

14.7 Performance Concerns

The hash call must be branch-predictable and allocation-free; benchmark with criterion.rs against the §4 target (bucketing math ≤ 50 ns of the ≤150 ns p50 evaluation budget). Concatenating salt and unit_id should use a pre-sized stack buffer, not a heap-allocated String, on the hot path.

14.8 Edge Cases

Empty unit_id (should be rejected upstream by the SDK, but the bucketing function itself must not panic — empty string hashes to a valid, if useless, bucket). Unicode unit_id values — hashed as raw UTF-8 bytes, no normalization (documented, since normalization would itself be a silent-reshuffle risk if changed later). Rollout with a single variant at weight 100,000 — every bucket maps to it, degenerate but valid.

14.9 Failure Analysis

If the conformance vectors ever need regeneration (e.g. discovering the original 100,000-row sample had a generation bug), the regeneration event itself must be recorded in BLUEPRINT_LOG.md and treated as equivalent in severity to a bucketing- version bump, because any SDK that already shipped against the old vectors is now divergent (I8) until it re-tests against the corrected ones — mitigated by never regenerating without a version-tagged corpus.

14.10 Operational Notes

Publish conformance/bucketing_vectors.json alongside every release artifact (§29); every language SDK binding's CI must run the differential test against this exact file before it can be released (§28).

15. Phase 3 — Config Compiler + Versioned Documents

15.1 Objectives

Transform authored Flag/Segment rows into an immutable, versioned ConfigDocument (§8.4), satisfying P3 (always internally consistent) and I11 (monotonic ConfigVersion).

15.2 Detailed Implementation Steps

Implement ff-config::compiler reading all Flag/Segment rows for an environment inside a single serializable Postgres transaction (ADR-11), sorting each flag's targeting by descending priority once at compile time (feeding Phase 1's evaluator a pre-sorted list, per 13.7). Validate segment-reference cycles (I9) and rollout weight sums (I13) at compile time as a second gate beyond the control-plane save- time check (defense in depth). Assign ConfigVersion via a DB sequence inside the same transaction that reads the source rows, so version assignment and content are atomically paired (I11). Serialize to Protocol Buffers (ADR-09), gzip-compress, and write the resulting ConfigDocument to a content-addressed blob store keyed by (environment_id, version) — the document is immutable once written, never edited in place (P3).

15.3 Deliverable

ff-config compiler producing a ConfigDocument for a 3-flag, 1-segment fixture environment, with byte-identical repeat-compilation given identical source state (compiler is a pure function of DB state at a snapshot).

15.4 Acceptance Criteria

Compiling the same source state twice under the same transaction snapshot produces byte-identical ConfigDocument payloads (excluding compiled_at); a segment-cycle fixture is rejected with EvalError::SegmentCycleDetected-shaped compiler error before producing a document; ConfigVersion strictly increases across 1,000 consecutive compiles in a property test.

15.5 Conformance Fixtures

fixtures/phase3/three_flag_compile.json — expected ConfigDocument for a fixed 3-flag/1-segment source snapshot. fixtures/phase3/segment_cycle_A_B_A.json — a compile-time cycle rejection case. fixtures/phase3/weight_sum_invalid.json — a rollout summing to 60,000, rejected at compile time as the second gate behind the control-plane's own check. fixtures/phase3/version_monotonic_1000.json — regression fixture asserting 1,000 sequential compiles never repeat or regress a version number.

15.6 Pitfalls

Compiling from a non-serializable transaction isolation level — manifests as a ConfigDocument that reflects a torn read across two concurrent control-plane writes (a P3 violation in disguise); root cause: assuming Postgres's default READ COMMITTED is sufficient; debug by reproducing under concurrent writers; fixed by requiring SERIALIZABLE for the compile transaction. Recompiling on every single flag edit at high write volume — manifests as compiler thrash and blob-store write amplification; mitigate with debounced/batched compilation windows (documented, not implemented as code here). Forgetting to re-validate weight sums at compile time because "the control-plane API already checked it" — a defense-in-depth gap; a direct DB write bypassing the API (e.g. a migration script) could otherwise ship invalid weights.

15.7 Performance Concerns

Compilation time scales with flag count × average rule count (§34); target: a 5,000-flag environment compiles in under 2 seconds. Blob-store writes should be async relative to the transaction commit — the transaction only needs to durably record "version N is authoritative," not block on the blob write completing.

15.8 Edge Cases

An environment with zero flags — compiles to a valid, empty ConfigDocument, not an error. A flag referencing a segment from a different environment (should be impossible via the API, but the compiler must defensively reject it as a data- integrity violation, not silently include it). Concurrent compiles for two different environments — must not serialize against each other (per-environment lock granularity, not a global compiler lock).

15.9 Failure Analysis

If the blob store is unreachable after the transaction commits (version N recorded as authoritative but the document body never lands), the delivery service (Phase 5) must detect a missing blob for its polled version and retry against the compiler's re-publish path rather than serving a 404 to SDKs — documented as FM-2's root scenario.

15.10 Operational Notes

Every successful compile emits a structured log line with (environment_id, version, flag_count, compile_duration_ms), feeding the config-apply-version gauge referenced in I3's telemetry column and the delivery-service dashboards in §26.

16. Phase 4 — SDK Local Evaluator + Offline Safety

16.1 Objectives

Embed the Phase 1 evaluator and Phase 2 bucketing function inside ff-sdk, holding a ConfigDocument behind an atomically-swappable pointer, satisfying P1 (offline safety) and P4 (infallible public API with default fallback).

16.2 Detailed Implementation Steps

Hold the current ConfigDocument in Arc<ArcSwap<ConfigDocument>> (per §11's ff-config note). Implement typed public methods (bool_variation, string_variation, number_variation, json_variation) per ADR-18, each taking a caller-supplied default and never returning Result to the caller — internally routing through evaluate() (Phase 1) and mapping any EvalError to the default (P4, I5). Implement cold-start behavior: if no ConfigDocument has ever been fetched, the SDK returns the caller default immediately rather than blocking host- application startup (documented default; blocking is opt-in via an explicit wait_for_ready(timeout) call). Implement a bootstrap-from-disk cache: on process restart, load the last-persisted ConfigDocument from a local file before any network round-trip, so a restarted host process is warm immediately.

16.3 Deliverable

ff-sdk crate exposing typed variation methods, an ArcSwap-backed evaluator, and a disk-backed bootstrap cache, demonstrated against the Phase 3 fixture ConfigDocument.

16.4 Acceptance Criteria

bool_variation on an unknown flag key returns the caller default in under 200 ns (no allocation, no I/O — verified by the allocator-counting harness from 13.4); a cold SDK with a valid disk-cached ConfigDocument serves correct variants within 5 ms of process start, before any network connection is established; a fuzz run of 1,000,000 (flag_key, EvaluationContext) pairs against an arbitrary ConfigDocument produces zero panics.

16.5 Conformance Fixtures

fixtures/phase4/cold_start_no_cache.json — asserts default-value return with EvaluationReason::Error(EvalError::UnknownFlag); fixtures/phase4/cold_start_disk_cache.json — asserts correct variant served from a pre-populated disk cache before network readiness; fixtures/phase4/typed_mismatch.json — calling bool_variation against a String-typed flag, asserts default returned, never a type-confusion panic (closing the "variant value vs. variant key confusion" pitfall from the pre-v2 draft).

16.6 Pitfalls

Blocking host-application startup on the first config fetch by default — manifests as slow application boot under network jitter; root cause: conflating "fresh" with "required"; fixed by making blocking opt-in via wait_for_ready. Returning a panic instead of a default when a flag's authored type doesn't match the caller's typed method — root cause: unchecked downcast; fixed by exhaustive type-tagged Value matching. Disk-cache corruption on an unclean shutdown mid-write — manifests as a cold-start crash reading a torn file; fixed by writing to a temp file and atomically renaming (never appending in place).

16.7 Performance Concerns

ArcSwap::load() must be lock-free on the read path (the whole point of choosing ArcSwap over a RwLock); benchmark contention under 32 concurrent reader threads against zero writers to confirm no false sharing. Disk-cache reads happen once at startup, not on the hot path — must not be reachable from evaluate().

16.8 Edge Cases

A ConfigDocument fetched successfully but for the wrong environment_id (a misconfigured SDK key) — the SDK must detect the mismatch and refuse to apply it, serving defaults and raising EvalError-shaped telemetry rather than silently mixing environments. A host process with two independent ff-sdk instances pointed at different environments in the same process — must not share global mutable state (no process-wide singletons).

16.9 Failure Analysis

If the disk cache and the in-memory ConfigDocument disagree after a delivery-service partition heals (memory has version N+3, disk cache was last written at N), the SDK must persist the newer document to disk on every successful apply, not just at shutdown — otherwise a crash-restart loop could resurrect a stale document repeatedly, which is the seed of FM-1 (config rollback resurrecting a stale assignment).

16.10 Operational Notes

SDK telemetry (Phase 12/§26) reports config_version_applied and fallback_rate per instance; operators alert when fallback_rate exceeds 1% for more than 5 minutes, per the §4 RTO budget.

17. Phase 5 — Streaming Delivery + Polling Fallback

17.1 Objectives

Implement the delivery service's SSE fan-out and polling endpoint (§3, ADR-08), satisfying P7 (degrade to polling, never to silence) and the §4 fan-out/latency targets.

17.2 Detailed Implementation Steps

Implement the SSE endpoint per the HTML Server-Sent-Events specification: on connect, if the client's Last-Event-Id (or query-param version) is absent or far behind, stream a full ConfigDocument; otherwise stream forward RuleSetUpdate deltas as they are published. Implement heartbeats every 30 seconds (: keepalive\n\n) to survive idle-connection timeouts at intermediary proxies (RFC 7231 connection semantics). Implement the polling endpoint using If-None-Match: <ConfigVersion> returning 304 Not Modified when unchanged (RFC 7231 conditional requests). Implement SDK-side reconnect: 1 s initial backoff, exponential to 60 s cap; after 5 minutes of failed reconnects, switch to polling every 60 s and periodically retry SSE every 5 minutes (P7). Implement server-side per-subscriber backpressure: a full channel drops the event for that subscriber (ADR-28), relying on the next full-document resend to resynchronize rather than blocking the fan-out loop for all subscribers.

17.3 Deliverable

ff-delivery crate serving both SSE and polling for a fixture environment, with a load-tested fan-out to 10,000 concurrent simulated SDK connections on one node.

17.4 Acceptance Criteria

A published config change reaches p50 of 10,000 connected SDKs within 500 ms and p99 within 2 s (§4 target); a forced SSE disconnect triggers reconnect within the documented backoff schedule and falls back to polling within 5 minutes if reconnects keep failing; polling under an unchanged version returns 304 with a payload of 0 bytes (beyond headers).

17.5 Conformance Fixtures

fixtures/phase5/sse_full_then_delta.json — a connect-at-old-version-then-delta sequence, expected final applied state. fixtures/phase5/reconnect_backoff_schedule.json — asserts the 1s→2s→4s...→60s-capped backoff sequence over 8 consecutive failures. fixtures/phase5/polling_304_unchanged.json — asserts conditional-request semantics. fixtures/phase5/thundering_herd_restart.json — 10,000 simulated reconnects within 2 seconds of a delivery-node restart, asserts bounded concurrent full-document sends (§7.6-style throttling) rather than an unbounded burst.

17.6 Pitfalls

Treating heartbeats as data the SDK must parse — manifests as SDK-side parse errors on comment lines; fixed by explicitly ignoring SSE comment frames. Unbounded full-document resends on a mass-reconnect event (thundering herd) — manifests as delivery-node OOM or CPU saturation right after a routine deploy; root cause: no admission control on cold-cache fan-out; fixed by throttling full-resend rate and returning 503 Retry- After past a bound. SDKs that reconnect in a tight loop on a persistent error (bad SDK key) — a DoS-shaped bug; fixed by per-key reconnect-rate tracking and connection throttling server-side, not just client-side backoff (defense in depth against a misbehaving or compromised SDK).

17.7 Performance Concerns

Memory per open SSE connection (§34 derives ~4–10 KB); 100,000 connections per node is the modeled ceiling (§4) — validated by an fd-limit and buffer-tuning benchmark, not assumed. Delta computation (diffing ConfigDocument N vs N+1) must be O(changed flags), not O(total flags), to keep fan-out latency flat as the environment's flag count grows.

17.8 Edge Cases

A brand-new SDK connecting with no prior version — always receives a full document, never a delta assumed against nothing. A delivery node restarting mid-fan-out — in- flight subscriber channels are dropped cleanly; reconnecting clients land on a different node via the load balancer and receive a full resend. A client whose Last-Event-Id refers to a version older than the compiler's retention window (very old) — server responds with a full document rather than attempting a very large delta chain.

17.9 Failure Analysis

A delivery node that appears healthy (accepting connections) but has stopped receiving compiler publish events (e.g. a stuck subscription to the internal change bus) will silently serve a frozen ConfigVersion forever — this is FM-3's root scenario; detection requires a delivery-node-side "time since last publish observed" gauge, not merely connection-count health checks.

17.10 Operational Notes

Dashboard: SSE connection count per node, reconnect rate, version-drift histogram (seconds behind latest per connected SDK), full-vs-delta resend ratio. Runbook: docs/runbooks/delivery-node-failover.md documents graceful drain (stop accepting new connections, keep serving existing ones until they naturally reconnect elsewhere).

18. Phase 6 — Exposure-Event Collection + Dedupe

18.1 Objectives

Implement SDK-side exposure batching and server-side ingestion satisfying P5 (exactly-once-per-context emission) and I4 (SRM-correctness-preserving dedup).

18.2 Detailed Implementation Steps

Implement SDK-side ExposureEvent emission at the point evaluate() resolves through an experiment-bound rule (not on every evaluation — only experiment-bound ones, per ADR-14). Implement an in-SDK bounded dedup window keyed by DedupKey = hash (unit_id, flag_key, window_bucket), suppressing repeat emissions within the same window (default window: one hour) to bound both storage and the "spammed inside a tight loop" pathology documented in the pre-v2 draft's pitfalls. Batch emission every 100 ms or 1,000 events, whichever first (ADR-13), shipping to ff-ingest's collector endpoint. Implement ff-ingest's queue producer with at-least-once delivery into the durable queue; downstream dedup is defense-in-depth against duplicate delivery from queue retries, keyed by the same DedupKey.

18.3 Deliverable

ff-ingest collector endpoint plus SDK-side batching, demonstrated against a 1,000-evaluation-per-second synthetic load producing a bounded, deduplicated exposure stream.

18.4 Acceptance Criteria

A synthetic load of 1,000,000 evaluations against 100 unique unit ids within one dedup window produces exactly 100 exposure events (one per unit id), not 1,000,000; queue producer sustains ≥1,000,000 events/sec cluster-wide in a load test (§4 target); a forced at-least-once queue redelivery of the same event is deduplicated downstream without double-counting in the stats pipeline's later input.

18.5 Conformance Fixtures

fixtures/phase6/dedup_window_collapse.json — the 1,000,000-into-100 collapse case above. fixtures/phase6/queue_redelivery_dedup.json — simulated at-least-once redelivery, asserts single logical exposure downstream. fixtures/phase6/non_experiment_flag_no_exposure.json — evaluating a flag with no bound experiment, asserts zero exposure events emitted (closing the "exposure events on paths the user never saw" failure class before it starts, since only experiment-bound resolutions emit at all).

18.6 Pitfalls

Emitting exposure on every evaluation regardless of experiment binding — manifests as exposure-event volume disproportionate to actual experiment traffic, corrupting downstream SRM math with irrelevant records; root cause: conflating "evaluated" with "exposed to an experiment"; fixed by gating emission on experiment binding explicitly. Dedup window too short — manifests as inflated sample counts resembling an SRM symptom without an actual bucketing bug; debug by checking whether SRM resolves after widening the window. Dedup window too long — manifests as under-counting exposures for legitimately returning users across sessions; the tradeoff is explicit and documented, not silently chosen.

18.7 Performance Concerns

The dedup structure (likely a time-windowed bloom filter or LRU set) must be bounded in memory regardless of unit-id cardinality — an unbounded HashSet of all-time-seen DedupKeys is a memory leak at scale; use a rotating window structure sized from §34's memory-ceiling derivation.

18.8 Edge Cases

A unit id that crosses a dedup-window boundary mid-session (evaluated at 59:59 and again at 60:01 of the window) — two exposure events are legitimate and expected, not a bug; documented explicitly so operators don't misdiagnose it as a duplicate. An anonymous unit id that later resolves to a logged-in identity mid-experiment — produces two distinct exposure records under two different unit ids; documented as an accepted eventual-consistency cost (mirrors the pre-v2 draft's finding), not silently merged.

18.9 Failure Analysis

If the queue backs up faster than ff-ingest can drain (a producer-consumer mismatch), SDK-side buffers eventually hit their cap and begin dropping the oldest unsent batch — an explicit, telemetered loss path (loss-tolerant by design, per ADR-28), never an unbounded buffer that eventually OOMs the host application.

18.10 Operational Notes

Metrics: exposure_events_emitted_total, exposure_events_deduped_total, exposure_queue_lag_seconds. Alert when queue lag exceeds the §4 freshness-lag budget (5 minutes p95) for longer than 10 minutes.

19. Phase 7 — Control-Plane API + Audit Log

19.1 Objectives

Build the authenticated REST/gRPC admin API for flag/segment/experiment CRUD and the append-only, hash-chained audit log, satisfying P11 (audit independent of application privilege) and P14 (typed confirmation on destructive actions).

19.2 Detailed Implementation Steps

Implement REST endpoints for flag/segment CRUD with request validation enforcing I9 (segment-cycle rejection) and I13 (weight-sum validation) at save time — the first of the two defense-in-depth gates completed by Phase 3's compiler-side check. Implement the audit-log writer: every mutation appends an AuditEntry inside the same transaction as the mutation itself, computing entry_hash over (prev_hash, actor, action, entity_id, diff) (hash-chain per P11/I10). Configure the Postgres role used by the application to have INSERT-only privilege on the audit_log table (no UPDATE/DELETE grant, enforced at the database level, not just application logic). Implement destructive-action confirmation: deleting a flag, segment, or environment requires a typed confirmation string matching the entity's key, and produces an audit entry serializing the full pre-deletion state, with a 24-hour soft-delete/undo window before physical deletion (P14).

19.3 Deliverable

ff-control-plane REST API with flag/segment/experiment CRUD, a working hash-chained audit log, and a soft-delete/undo path for flag deletion.

19.4 Acceptance Criteria

Attempting to save a segment-cycle (A references B references A) is rejected with HTTP 422 before any row is written; a hash-chain verification job run against 10,000 sequential audit entries reports zero breaks; a flag deleted via the API is fully restorable via undo within the 24-hour window and produces two audit entries (delete, restore); the application's Postgres role, when tested with a direct DELETE FROM audit_log, is rejected by a database-level grant error, not merely an application- layer check.

19.5 Conformance Fixtures

fixtures/phase7/segment_cycle_rejected_at_api.json — API-level rejection mirroring Phase 3's compile-time check (first of the two defense-in-depth gates). fixtures/phase7/audit_hash_chain_10000.json — regression fixture verifying chain integrity across 10,000 entries. fixtures/phase7/soft_delete_undo_window.json — delete-then-restore-within-window sequence with expected audit entries. fixtures/phase7/destructive_action_wrong_confirmation.json — a delete request with a mismatched confirmation string, expected rejection with no audit entry for the (non-)deletion beyond the rejected-attempt log.

19.6 Pitfalls

Granting the application's Postgres role UPDATE/DELETE on audit_log "just in case" during initial schema setup — manifests as a latent privilege that defeats P11's entire purpose; caught by a CI-run privilege-audit script asserting the grant set exactly matches the intended minimal set. Computing entry_hash outside the same transaction as the mutation — manifests as a race where two concurrent writers could both read the same prev_hash and produce a valid-looking but effectively forked chain; fixed by serializing audit writes per environment. Allowing an approver to approve their own change (pre-v2 draft's documented pitfall, §9.3-equivalent) — fixed by enforcing approver_id != actor_id at the API layer, not just UI.

19.7 Performance Concerns

Audit-log writes are on the mutation path (not the read-hot evaluation path), so correctness dominates over raw throughput; still, batched audit reads for compliance exports (§19.10) must use the (entity_type, entity_id, timestamp) index, not a full table scan.

19.8 Edge Cases

A mutation that fails mid-transaction (e.g. a constraint violation after the audit entry is drafted but before commit) — must roll back both the mutation and the audit entry atomically; no orphaned audit rows for a mutation that never actually happened. An emergency-bypass mutation (kill-switch flip without approval) — still produces a full audit entry, flagged emergency=true, notifying all admins (mirrors the pre-v2 draft's break-glass workflow).

19.9 Failure Analysis

If the hash-chain verification job detects a break, the immediate response is to halt new audit writes pending investigation (rather than silently continuing to chain onto a known-broken link), escalate via the incident process (§26), and reconstruct the true history from the Postgres WAL/backup if the break indicates tampering rather than a bug.

19.10 Operational Notes

Compliance export endpoint: filterable, paginated CSV export of audit entries by (entity_type, entity_id, actor, date_range), documented in docs/runbooks/compliance-export.md so it is never improvised at incident/subpoena time.

20.1 Objectives

20.2 Detailed Implementation Steps

Implement Experiment CRUD binding to an existing Flag's variants, requiring ≥1 guardrail metric before the Draft → Running transition is permitted (§8.6, P6). Implement each lifecycle transition from the state table as an explicit guarded state machine, rejecting invalid edges (e.g. conclude without a crossed sequential boundary or reached fixed horizon → PrematureConclusion). Implement the SDK-side binding: when evaluate() resolves a flag that has a Running experiment attached, the resulting EvaluationResult carries the experiment_id forward into the exposure emission path built in Phase 6. Implement per-experiment allocation via Rollout.salt set to Experiment.allocation_salt, defaulting to the experiment's own id (closing the pre-v2 draft's "seed reuse across experiments" pitfall) so two experiments never silently share correlated bucket assignments unless explicitly configured to (Phase 10's mutual-exclusion layers).

20.3 Deliverable

Experiment CRUD and lifecycle transitions in ff-control-plane, plus SDK-side experiment_id-tagged exposure emission demonstrated end-to-end from a Draft experiment through Running to a mock Concluded state.

20.4 Acceptance Criteria

Starting an experiment with zero guardrail metrics is rejected (NoGuardrailDeclared); concluding a Running experiment before its sequential boundary crosses or its declared fixed horizon is reached is rejected (PrematureConclusion); two experiments created with default (id-derived) salts produce provably uncorrelated bucket assignments for the same 10,000 synthetic unit ids (chi-square independence test, p > 0.01).

20.5 Conformance Fixtures

fixtures/phase8/lifecycle_transitions_valid.json — every valid edge in §8.6's table exercised once. fixtures/phase8/lifecycle_transitions_invalid.json — every documented failure edge exercised, asserting the correct rejection reason. fixtures/phase8/ salt_independence_10000.json — the two-experiment independence check above. fixtures/phase8/exposure_carries_experiment_id.json — asserts an experiment-bound evaluation's exposure event has a populated experiment_id, and a non-bound evaluation does not.

20.6 Pitfalls

Allowing an experiment to reuse another experiment's salt by copy-pasted authoring mistake — manifests as correlated assignments silently violating independence assumptions in later pairwise analysis (the pre-v2 draft's documented "seed reuse" bug); fixed by defaulting to a per-experiment-id salt and surfacing the salt prominently in the UI. Allowing conclude to bypass the guardrail/boundary guard via an internal admin override without extra audit weight — mitigated by requiring the same emergency-bypass audit treatment as Phase 7's kill-switch override. Rebinding an experiment to a different flag mid-run — silently invalidates all prior exposure data's meaning; rejected at the API level once status != Draft.

20.7 Performance Concerns

Lifecycle-transition checks are control-plane, low-QPS operations — no hot-path concern. The one latency-sensitive piece is the SDK-side branch that checks "is this flag experiment-bound" during evaluation; implemented as an O(1) lookup on the compiled ConfigDocument's flag record, not a separate join at evaluation time.

20.8 Edge Cases

An experiment bound to a flag that is later toggled enabled = false (killed) — the lifecycle state machine transitions the bound experiment to Concluded (invalid) via the emergency_stop edge automatically, never leaving a Running experiment silently attached to a disabled flag. A flag with multiple variants but only two bound into the experiment (a partial binding) — rejected at experiment creation; the experiment's variant set must be a subset validated against the flag's actual variants, not assumed.

20.9 Failure Analysis

If a Running experiment's underlying flag is deleted (should be blocked by the pre-v2 draft's documented invariant, re-adopted here: "can't delete a flag with an active experiment"), the control plane rejects the deletion with a clear error naming the blocking experiment — this is enforced at the API layer as a foreign-key-shaped application check, not left to be discovered via a broken dashboard later.

20.10 Operational Notes

Dashboard: experiments by status, guardrail-metric declaration completeness across all experiments, salt-collision detector (a background job flagging any two Running experiments that accidentally share a salt — closing the same pitfall as 20.6 with a runtime safety net, not just an authoring-time default).

21. Phase 9 — Stats Pipeline + Sequential Guardrails

21.1 Objectives

Implement the statistics worker computing StatsResult per experiment from exposure and goal events, including variance estimation, CUPED adjustment, SRM detection, and the sequential boundary, satisfying P6/I12 (not decision-ready until guardrail and boundary both pass).

21.2 Detailed Implementation Steps

Implement a periodic worker joining ExposureEvents with GoalEvents by unit_id per experiment, per §8.7's variance-estimation equations, computing per-variant x̄_v, s_v². Implement CUPED adjustment (Deng et al. 2013, §8.7) using a pre-experiment covariate window, reducing variance by 1 - ρ². Implement the sequential-boundary computation (Howard et al. 2021 form, §8.7), recomputed on every worker pass, gating decision_ready (I12) on 0 ∉ CS_t. Implement the SRM check: a chi-square goodness-of-fit test on realized vs. planned variant-assignment proportions, flagging srm_detected at p < 0.001 and driving the Running → Peeking-Blocked lifecycle transition (§8.6) automatically. Implement Benjamini- Hochberg FDR correction (ADR-16) across an experiment's declared secondary metrics before surfacing any as significant.

21.3 Deliverable

ff-stats worker producing a StatsResult for a fixture experiment with synthetic exposure/goal data, correctly gating decision_ready and correctly triggering SRM detection on an injected-bug fixture.

21.4 Acceptance Criteria

A synthetic experiment with a true 2% lift and 10,000 users/variant reaches decision_ready = true within the expected days-to-significance derived in §34 (within ±20% of the derived figure in a Monte Carlo simulation); an injected 47/53 assignment split against a planned 50/50 triggers srm_detected at the documented p < 0.001 threshold in ≥95% of 1,000 simulated trials; CUPED-adjusted variance is measurably lower than unadjusted variance on a fixture with ρ = 0.5 correlated covariate data, matching the 1 - ρ² reduction within numerical tolerance.

21.5 Conformance Fixtures

fixtures/phase9/synthetic_2pct_lift.json — the Monte Carlo days-to-significance fixture. fixtures/phase9/srm_injected_47_53.json — the SRM-detection fixture. fixtures/phase9/cuped_variance_reduction.json — the CUPED adjustment fixture. fixtures/phase9/fdr_correction_5_secondary_metrics.json — Benjamini-Hochberg applied across 5 secondary metrics with 2 true positives injected, asserting correct significance flagging under correction versus without it.

21.6 Pitfalls

Surfacing a naive fixed-horizon p-value alongside the sequential boundary without clearly marking which is peeking-valid — manifests as analysts using the wrong number under continuous monitoring (the exact failure Johari et al. 2017 documents); fixed by never computing or displaying a naive p-value in the primary UI path. Running SRM detection only once at experiment conclusion instead of continuously — manifests as weeks of corrupted data before detection; fixed by recomputing SRM on every worker pass alongside the boundary. Forgetting FDR correction when an experiment declares many secondary metrics — manifests as an inflated false-discovery rate exactly analogous to uncorrected peeking, but across metrics instead of across time; fixed by making FDR correction unconditional whenever secondary_metrics.len() > 1.

21.7 Performance Concerns

The exposure/goal join for a 100,000-user, 7-day experiment must complete in under one minute on modest hardware (mirrors the pre-v2 draft's benchmark) — driven by ClickHouse's MergeTree ordering ((environment_id, experiment_id, timestamp)) matching the query's filter predicate. Worker scheduling is hourly per experiment by default, bounded by the §4 freshness-lag budget (≤5 min p95 is the ingestion lag; the stats recompute cadence is a separate, coarser operational parameter documented here explicitly to avoid conflating the two).

21.8 Edge Cases

An experiment with zero goal events recorded for a variant (nobody converted) — variance estimation must handle a zero-variance degenerate case without dividing by zero; documented explicit guard, not a silent NaN propagating into StatsResult. A guardrail metric that itself has an SRM-shaped anomaly independent of the primary metric — the platform surfaces guardrail-specific warnings distinctly from primary- metric SRM, since a guardrail regression is actionable even when SRM overall is clean.

21.9 Failure Analysis

If the sequential-boundary computation is fed exposure timestamps with unbounded clock skew (a client with a wildly wrong local clock), the boundary's n_t progression can appear non-monotonic — this is FM-8's root scenario; mitigated by clamping accepted exposure timestamps to a bounded window around server-received time and rejecting (with telemetry) events far outside it rather than silently ingesting them.

21.10 Operational Notes

Dashboard: per-experiment decision_ready status, SRM p-value trend, sequential- boundary width over time (narrowing width is the visual "getting closer to a valid stop" signal operators are taught to watch for, per the pre-v2 draft's "wait until the gold star" framing).

22. Phase 10 — Overlapping-Experiment Layers + Mutual Exclusion

22.1 Objectives

Implement the domain/layer allocation model (Tang et al. 2010) so independent experiments can share traffic without uncoordinated interaction, satisfying P12 and ADR-17.

22.2 Detailed Implementation Steps

Implement a Layer type: a named partition of traffic within a Domain, where every experiment in the platform is assigned to exactly one layer. Implement layer-level bucketing as a first hash-and-split step (using the same frozen bucketing function, §8.3, with a layer-specific salt) that determines which layer a unit id falls into before any experiment-level bucketing runs — experiments within the same layer are mutually exclusive (a unit id in layer L only ever sees one experiment from L); experiments in different layers of the same domain run concurrently on independent sub-partitions of traffic and are, by construction, statistically independent of each other. Implement the "experiment groups" convenience API from the pre-v2 draft (§8.8-equivalent) as sugar over creating a layer with N experiments and no overlap. Implement a validation check rejecting an experiment's assignment to a layer if doing so would exceed the layer's traffic budget (sum of experiment traffic allocations within one layer ≤ 100%).

22.3 Deliverable

ff-control-plane layer/domain CRUD plus SDK-side layer-first bucketing, demonstrated with two experiments in the same layer (mutually exclusive) and two experiments in different layers of the same domain (running concurrently, statistically independent).

22.4 Acceptance Criteria

10,000 synthetic unit ids bucketed into a 2-experiment layer show zero units assigned to both experiments (mutual exclusion is exact, not approximate); two experiments in separate layers of the same domain show independence (chi-square test, p > 0.01) on the same 10,000-unit-id set; an attempt to over-allocate a layer's traffic budget beyond 100% is rejected at the API level.

22.5 Conformance Fixtures

fixtures/phase10/mutual_exclusion_same_layer.json — the zero-overlap assertion above. fixtures/phase10/independence_cross_layer.json — the cross-layer independence assertion. fixtures/phase10/layer_budget_overallocation.json — the rejected- over-100%-budget case. fixtures/phase10/experiment_group_sugar_equivalence.json — asserts the "experiment groups" convenience API produces byte-identical layer configuration to the equivalent hand-authored layer.

22.6 Pitfalls

Running two experiments on overlapping metrics in different layers assuming independence is automatic — layers guarantee traffic-partition independence, not metric independence; two experiments can still interact through the metric itself (e.g. both affect page-load time) even on disjoint traffic if the analysis later pools results incorrectly; documented as an analyst-education gap this system's layering cannot fully close by construction alone. Forgetting layer-level bucketing must use a different salt than any individual experiment's salt — reusing a salt here would correlate layer assignment with experiment assignment, a subtle violation of the mutual-exclusion guarantee's independence assumption.

22.7 Performance Concerns

Layer-first bucketing adds one additional bucketing-function call per evaluation ahead of the experiment-level call — within the same ≤150 ns p50 budget (§4), since it is the identical pure function (§8.3) applied twice with different salts, not a new algorithm.

22.8 Edge Cases

An experiment with no explicit layer assignment (legacy, pre-Phase-10 authoring) — defaults to a synthetic "default layer" occupying the full domain, preserving prior independent-assignment behavior for experiments authored before layering existed (§27 backward-compatibility concern). A domain with a single layer holding a single experiment at 100% traffic — degenerates correctly to the pre-Phase-10 behavior, confirming layering is a strict superset, not a breaking change.

22.9 Failure Analysis

If a layer's traffic-budget validation is bypassed (e.g. a direct DB write during a migration), two experiments could receive overlapping traffic within a layer that was assumed mutually exclusive — detected by an SRM-adjacent background check: a "layer-assignment audit" comparing observed variant-assignment cardinality against the layer's declared experiment count, alerting if any unit id appears in more than one same-layer experiment's exposure stream.

22.10 Operational Notes

Dashboard: per-domain layer map (visual traffic-partition tree), per-layer budget utilization, cross-layer independence spot-check job run nightly against a sample of recent exposure data.

23. Phase 11 — Conformance Suite + Perf Hardening

23.1 Objectives

Assemble the full cross-language conformance suite (bucketing parity, rule-evaluation parity, malformed-input handling) as a third-party-consumable artifact, and drive every §4/§30 performance target to a benchmark-gated green state.

23.2 Detailed Implementation Steps

Package conformance/ (bucketing vectors from Phase 2, rule-evaluation vectors newly added here covering the full §8.2 grammar and §8.9 malformed-rule corpus) as a versioned, publishable artifact any language SDK binding's CI can pull and run against (closing the gap the Flagsmith reference implementation's historical divergence illustrates, §5). Implement the differential-testing harness comparing this Rust reference implementation's stats engine (Phase 9) against a known-good external statistical reference (e.g. a scipy/statsmodels-computed t-test and chi-square on the same fixture data) to catch numerical-implementation drift. Run cargo-fuzz targets against the rule parser (Phase 1) and config decoder (Phase 3) for a sustained 24-hour soak as a release gate. Run criterion.rs benchmarks against every §30 M-numbered target, wiring failures into perf-regression.yml (ADR-25).

23.3 Deliverable

A versioned conformance/ release artifact, a green 24-hour fuzz soak report, and a passing perf-regression CI gate against all §30 targets.

23.4 Acceptance Criteria

The published conformance suite, run against this reference implementation, passes 100% of its own vectors (a tautological but necessary self-check before external publication); a 24-hour fuzz soak of the rule parser and config decoder produces zero crashes and zero out-of-bounds/undefined-behavior reports under cargo-fuzz with AddressSanitizer; every §30 M-numbered benchmark target is met with less than 10% regression tolerance enforced in CI.

23.5 Conformance Fixtures

conformance/rule_evaluation_vectors.json — full-grammar coverage vectors, newly published alongside the Phase 2 bucketing vectors. fixtures/phase11/stats_engine_differential.json — the scipy/statsmodels cross-check fixture set. fixtures/phase11/fuzz_soak_report_24h.json — the recorded soak-run summary (crash count, coverage delta). fixtures/phase11/perf_regression_baseline.json — the pinned baseline every future PR's benchmark run diffs against.

23.6 Pitfalls

Treating "passes our own conformance suite" as sufficient validation before publishing it externally — it only proves self-consistency, not correctness against an independent reference; mitigated by the stats-engine differential test against an external statistical library, which is an actually independent check. Fuzz soaks that only run the happy-path grammar and never generate deeply nested or pathologically long rule trees — manifests as production crashes on inputs the fuzzer's corpus never explored; mitigated by seeding the fuzz corpus explicitly from the malformed-rule fixtures accumulated across all prior phases (§8.9, 13.5, etc.), not starting from scratch.

23.7 Performance Concerns

This phase is entirely about performance concerns — see §30 for the full target table; the phase-specific addition is gating those targets in CI so a regression fails a PR rather than being caught after release.

23.8 Edge Cases

A conformance vector that passes on the release machine's architecture but fails on a different target architecture (e.g. an ARM host with different float-rounding behavior in the stats engine) — mitigated by running the conformance suite in CI across both x86_64 and aarch64 runners before publishing a release.

23.9 Failure Analysis

If the published conformance suite is later found to contain an incorrect expected value (discovered by a third-party SDK implementer), the correction must be versioned (a new conformance-suite release, never a silent overwrite of the existing version), and every downstream SDK that validated against the incorrect vector must be flagged for re-validation — mirroring the bucketing-vector regeneration discipline from Phase 2.9.

23.10 Operational Notes

The conformance suite's version is stamped into every release's SBOM (§29); operators consuming third-party SDKs should verify the SDK's last conformance-suite version against the currently published one before trusting cross-SDK experiment consistency.

27. Compatibility & Versioning

Config document versioning: ConfigVersion is a monotonic per-environment u64 (I11); the wire schema itself carries a separate schema_version field, incremented only on breaking wire-format changes, following SemVer 2.0.0 for the schema's own compatibility contract.

Rule-language grammar evolution: new Operator variants are additive; old SDKs treat any unrecognized operator as non-match (P10/I7) — this is the forward- compatibility contract, tested explicitly in Phase 11's conformance suite and never allowed to regress.

SDK↔delivery protocol versioning: the SSE/polling wire protocol version is negotiated at connect time; a delivery service supports the current and one prior protocol version simultaneously to allow rolling SDK upgrades across a fleet without a synchronized cutover.

Bucketing-function stability: the hash function, concatenation order, and modulus (§8.3) are a permanent compatibility commitment (P8/I8) — any change requires a new, explicitly-named bucketing version, never an in-place modification, and is treated with the same severity as a cryptographic key rotation.

Schema evolution: Postgres migrations follow an expand/contract pattern — add nullable columns, backfill, make non-nullable, only then drop old columns in a later release — so a rolling deploy never has a writer and a reader disagreeing on schema shape mid-migration.

Deprecation: a flag/operator/API endpoint marked deprecated remains functional for at least two minor releases before removal, surfaced via CHANGELOG.md and a runtime deprecation-usage counter so operators can measure blast radius before removal.

SemVer: applied to the ff-sdk public API, the wire protocol schema version, and the conformance-suite artifact version independently — a breaking SDK API change does not imply a wire-protocol break, and vice versa.

Rolling-upgrade guarantees: any two adjacent minor versions of ff-sdk and the delivery service can run concurrently in the same fleet without evaluation inconsistency, guaranteed by the operator-additive rule-language contract and the dual-protocol-version delivery support above.

28. Testing & Verification Strategy

Unit: per-crate coverage of the §11 type constructors and the §8.2 operator table, gating on I5 (no panics) and I7 (unknown-operator non-match).

Integration: end-to-end control-plane-mutation → compile → delivery → SDK-apply flows exercised against a docker-compose stack (Postgres + queue + ClickHouse).

Property tests: evaluation determinism — the same (flag, context, config) triple always yields the same EvaluationResult across 100,000 randomized inputs (ties to I1, I2); bucket-distribution uniformity within the §34-derived chi-square tolerance across millions of unit ids (ties to I8, Phase 2's N.5 fixtures); weight- change stability — a unit that stays within its existing variant's cumulative-weight range under a weight change never moves (ties to I13, Phase 2's N.5 fixtures).

Differential testing: cross-language SDK parity against the shared conformance vectors (I2, I8, Phase 2/11's N.5 fixtures); the stats engine (Phase 9) against an external statistical reference implementation (Phase 11's N.5 fixture stats_engine_differential.json).

Fuzzing: rule parser and config decoder under cargo-fuzz with a 24-hour soak release gate (ties to I5, I7, Phase 11's N.5 fixtures), corpus seeded from every malformed-rule fixture accumulated across Phase 1/3/11.

Chaos: forced delivery-node kill mid-fan-out (ties to FM-3, Phase 5's N.5 thundering_herd_restart.json); forced Postgres failover during a compile (ties to I11, Phase 3's N.9).

Deterministic replay: recorded exposure streams replayed through the stats pipeline must reproduce byte-identical StatsResult output (ties to I12, Phase 9's N.5 fixtures) — a prerequisite for trusting any stats-engine refactor.

Soak: 24-hour sustained load at the §4 throughput targets across evaluation, delivery fan-out, and exposure ingestion simultaneously, watching for memory growth (dedup-structure leak class, FM-5-adjacent) and latency-percentile drift.

Fault injection: delivery-service network partition (ties to P1, P7, Phase 5's N.9); store failover for both Postgres (control plane) and ClickHouse (stats) (ties to FM-2, Phase 3's N.9).

Published conformance suite: third-party SDKs must pass the Phase 11 published conformance/ artifact before being considered parity-compatible (ties to I2, I8, §27's rolling-upgrade guarantee).

Perf-regression gating: every §30 M-numbered target is a CI-enforced benchmark gate (ADR-25, Phase 11's N.4).

29. Build & Release Engineering

Reproducible builds: pinned Cargo.lock (ADR-03) and rust-toolchain.toml; release builds are built in a hermetic container image matching the CI runner exactly, verified by comparing build-artifact hashes across two independent build runs.

Artifact signing: release binaries and the conformance-suite artifact are signed (cosign-style keyless signing against a transparency log), verified by delivery-service and SDK-consumer supply-chain checks before deployment (T10 mitigation).

SBOM: generated per release (cargo-cyclonedx or equivalent), listing every dependency and its audited version, stamped with the conformance-suite version it was validated against (23.10).

Release channels: stable (default, canaried per §26), beta (opt-in, one release ahead), nightly (unpinned, CI-only, never customer-facing).

CI/CD topology: GitHub Actions matrix (ADR-25) — lint/test on every PR, fuzz-smoke on every PR, full 24-hour fuzz soak and perf-regression gate on release-candidate branches only.

Version stamping: every binary embeds its git commit hash, build timestamp, and conformance-suite version via build-script-injected constants, queryable via a --version flag and exposed as a metric label.

Provenance/attestation: SLSA-style build provenance attached to each release artifact, recording the exact CI job, commit, and dependency lockfile hash that produced it.

Dependency auditing: cargo audit runs on every CI build and nightly against the released Cargo.lock, failing the build (or paging, for the nightly scheduled run) on a newly-disclosed advisory.

31. Scalability Analysis

Constant regardless of scale: per-evaluation latency (P1's pure-function guarantee holds regardless of fleet size); bucketing function cost (pure function of two inputs, §8.3).

Grows, and how: config payload size — O(flags × avg rules per flag) (§34); delivery-service memory — O(concurrent connections) per node, horizontally scaled; exposure ingestion volume — O(evaluations × experiment-bound fraction), the dominant growth driver, not evaluation itself; stats-worker compute — O(exposure + goal events per experiment per window).

Named bottlenecks in order: (1) streaming fan-out connections — the concurrency boundary most likely to need horizontal scaling first, since connection count grows with host-application instance count, not with flag count; (2) exposure- event ingest — the next bottleneck, since it grows with request volume across every experiment-bound evaluation; (3) config compile time — grows with flag/rule count but is infrequent (publish-triggered, not per-request) so it dominates last; (4) evaluation itself is not a bottleneck at any realistic scale, per M1/M2's sub-microsecond targets — this ordering deliberately inverts the naive assumption that "the evaluator" is where scaling effort belongs.

Horizontal scaling: delivery service and stats workers scale by adding nodes with no shared state (delivery) or by experiment-sharding (stats); control plane scales reads via replicas, writes remain single-primary (ADR-10, deferred multi-region per §1.10).

Vertical scaling: the config compiler benefits from more cores (parallel rule validation across flags within one compile) but is bounded by the single-transaction requirement (P3) for atomicity.

Sharding: exposure ingestion queue is sharded by environment_id to bound per-partition volume; stats workers claim shards by experiment id, allowing independent horizontal scaling as experiment count grows.

Coordination overhead: layer/domain traffic-budget validation (Phase 10) requires a single-writer lock per domain at authoring time, but this is a low-QPS control-plane operation, never a per-evaluation cost.

Practical ceiling and levers beyond it: the practical ceiling is exposure-ingestion throughput at a single durable-queue cluster's write capacity (§34 derives a concrete number); the lever beyond it is horizontal queue partitioning by environment_id combined with regional ingestion endpoints — deferred per §1.10's multi-region note, since it reintroduces the cross-region consistency questions this blueprint deliberately scoped out of v1.

32. Mental Models & First Principles

MM1 — A feature flag is a distributed configuration cache whose correctness property is agreement, not freshness. Predicts: an SDK serving a slightly-stale config during a partition is correct behavior, not a bug. Bug class avoided: chasing "always freshest" designs that sacrifice offline safety. Resolved in §6 (P1), §3.

MM2 — An experiment is a hypothesis test whose validity is destroyed by the act of looking early, unless the test was built to be looked at. Predicts: any dashboard showing a live p-value without a sequential-testing foundation will eventually produce a false winner. Bug class avoided: shipping features on peeked, uncorrected p-values. Resolved in §8.7, Phase 9.

MM3 — Bucketing is cryptography-adjacent, not cryptography. Predicts: a fast non-cryptographic hash is fine for fairness/uniformity but not for adversarial resistance. Bug class avoided: assuming MurmurHash3 protects against a motivated attacker choosing their own unit id. Resolved in §24 (T3), ADR-06.

MM4 — Config delivery and config authorship are different trust domains. Predicts: the delivery service must never be able to mutate state, only relay it. Bug class avoided: a compromised edge node escalating into a control-plane write. Resolved in §3, §24 (T1, T6).

MM5 — Exposure logging is part of the experiment's measurement instrument, not a side effect of evaluation. Predicts: any exposure-emission bug is a data-integrity bug, not a logging nuisance. Bug class avoided: treating FM-5-class over-emission as low-priority. Resolved in §6 (P5), Phase 6.

MM6 — A rollout percentage and an experiment allocation are the same primitive (a weighted bucket split) used for two different purposes. Predicts: the same bucketing function must serve both "ship to 10% of users" and "A/B test with 50/50 split" without divergent code paths. Bug class avoided: maintaining two hash functions that silently drift apart. Resolved in §8.3, §11.

MM7 — Overlapping experiments are a traffic-allocation problem before they are a statistics problem. Predicts: solving interaction via layering must happen at the bucketing layer, not after the fact in analysis. Bug class avoided: trying to "statistically adjust for" experiment interaction post hoc instead of preventing it via disjoint traffic partitions. Resolved in §8.6, Phase 10.

MM8 — Forward compatibility is a property you must design for, not one you retrofit after the first breaking rule-language change ships. Predicts: any Operator enum growth without a P10-style non-match fallback breaks old SDKs the day it ships. Bug class avoided: FM-9. Resolved in §6 (P10), §27.

MM9 — The audit log's threat model is insider risk, not just external attack. Predicts: the most likely audit-log-defeating actor is a legitimate but compromised or careless internal credential, not a network attacker. Bug class avoided: designing audit-log integrity controls only against external threats while leaving the application's own DB role over-privileged. Resolved in §6 (P11), §24 (T6).

34. Back-of-Envelope Capacity Model

1. Config payload bytes, uncompressed. 500 flags × 5 rules/flag avg × ~80 bytes/ rule (clause list + variant ref + priority, protobuf-encoded) = 500 × 5 × 80 = 200,000 bytes ≈ 200 KB, consistent with §4's 250 KB ceiling including segment definitions.

2. Config payload bytes, gzip-compressed. Rule structures are highly repetitive (shared operator vocabulary, shared attribute names); assuming a conservative 4:1 gzip ratio typical of repetitive protobuf structures: 200,000 / 4 = 50,000 bytes ≈ 50 KB, under the §4 60 KB target.

3. SDK memory for the config. 500 flags × ~400 bytes in-memory node (deserialized Flag struct with Vec<Rule> heap allocations, Vec<Variant>) + 50 segments × ~300 bytes = 500×400 + 50×300 = 200,000 + 15,000 = 215,000 bytes ≈ 210 KB — well under the 32 MB ceiling (§4), leaving headroom for a 20,000-flag hard-cap environment at ~8.6 MB.

4. Delivery fan-out memory per node. 100,000 connections × 8 KB/connection (socket buffers + per-connection subscriber-channel state, midpoint of the 4–10 KB range from §7.3/17.7) = 100,000 × 8,000 = 800,000,000 bytes ≈ 800 MB per node, plus file descriptors: 100,000 FDs, requiring ulimit -n tuning well above the default 1,024/4,096 OS defaults.

5. Exposure-event ingest bandwidth. 1,000,000 events/s × ~150 bytes/event (protobuf-encoded ExposureEvent, §8.5) = 1,000,000 × 150 = 150,000,000 bytes/s ≈ 150 MB/s cluster-wide ingest bandwidth.

6. Exposure storage per day. 150 MB/s × 86,400 s/day = 12,960,000 MB/day ≈ 12.96 TB/day uncompressed; ClickHouse's columnar compression on repetitive event structures typically achieves 5–10x, giving ~1.3–2.6 TB/day compressed storage growth (§4's storage-growth line).

7. Minimum detectable effect / days-to-significance. Two-proportion MDE formula: n = (z_{α/2} + z_β)² × [p₁(1-p₁) + p₂(1-p₂)] / (p₁-p₂)². Baseline conversion p₁ = 5%, target lift to p₂ = 5.5% (a 10% relative lift), α = 0.05 two-sided (z_{α/2} = 1.96), power 80% (z_β = 0.84): numerator (1.96+0.84)² × [0.05×0.95 + 0.055×0.945] = 7.84 × [0.0475 + 0.051975] = 7.84 × 0.099475 ≈ 0.7799; denominator (0.005)² = 0.000025; n ≈ 0.7799 / 0.000025 ≈ 31,196 users per variant. At 10,000 daily unique users per variant (a mid-size product's traffic), this requires ~3.1 days to accumulate the needed sample — the days-to-significance figure Phase 9's acceptance criteria (21.4) checks a Monte Carlo simulation against.

8. Bucket-uniformity chi-square tolerance. For k = 100,000 buckets and N = 1,000,000 sampled unit ids, expected count per bucket E = N/k = 10; a chi-square goodness-of-fit statistic Σ(O-E)²/E over 100,000 bins with 99,999 degrees of freedom has an expected value equal to its degrees of freedom under the null (uniform hash); the test in Phase 2/§28 accepts the null at p > 0.01, i.e. the observed statistic must fall within the chi-square distribution's 0.01–0.99 acceptance region for 99,999 df (approximately df ± 3√(2·df) ≈ 99,999 ± 1,342) — a concrete, computable tolerance band rather than an asserted-only "close to uniform."

35. Hard Questions (Self-Examination)

  1. If the config compiler (§15, Phase 3) and the delivery service (§17, Phase 5) both claim "the config is consistent," what specifically prevents a torn read from the blob store from violating that claim under FM-2's exact failure scenario?
  2. Why does bucketing (§8.3, Phase 2) need to be a permanent compatibility commitment (P8, I8) when almost every other component in §27 allows versioned evolution — what is structurally different about this one function?
  3. Phase 9's sequential boundary (§8.7) and Phase 10's layer independence (§22) both claim statistical validity — under what combined scenario could a layer-independent experiment still produce an invalid sequential-boundary read?
  4. §24's T3 (unit-id enumeration) and ADR-06's choice of MurmurHash3 over SHA-256 are in tension — walk through the exact deployment conditions (§1.4 users/operators) under which that tradeoff is acceptable versus unacceptable.
  5. §4 sets a sub-microsecond evaluation budget and §30's M2 sets p99 at 900 ns — given §8.2's grammar allows unbounded clause lists per rule, what caps actually keep M2 true, and where are those caps enforced (§4's "segments per flag" and "rules per flag" limits, or somewhere else)?
  6. §25's FM-1 (stale variant resurrection on rollback) and §27's rolling-upgrade guarantee both touch config versioning — why is "roll back the config version" explicitly discouraged while "roll back the binary" is the canary/rollback policy in §26; what makes these asymmetric?
  7. §21 (Phase 9) computes CUPED-adjusted variance and a raw sequential boundary simultaneously — does CUPED's covariate adjustment interact with the always-valid confidence sequence's validity guarantee, or are they orthogonal? Justify from §8.7's equations.
  8. §22's mutual-exclusion layering (Phase 10) and §20's per-experiment salt independence (Phase 8) both aim to prevent correlated assignment — under what authoring mistake could both protections simultaneously fail?
  9. §24's T9 (results tampering) is mitigated by "results are re-derivable from raw events" — what does that actually require of the exposure/goal event retention policy in §26, and what happens if retention expires before a tampering investigation completes?
  10. §17's thundering-herd throttling and §7 (original architecture) both address mass reconnection — given §31's claim that streaming fan-out is the first bottleneck to scale, what specifically differentiates a routine deploy-triggered reconnect storm from an attacker-triggered one (§24 T7), and does the mitigation differ?
  11. §18's dedup window (Phase 6) trades storage for accuracy — using §34's ingest bandwidth derivation, what dedup-window size would make exposure storage exceed the daily ceiling assumed in §34.6, and is that window size plausible in practice?
  12. §8.6's experiment lifecycle allows emergency_stop from any state — does this conflict with §12's Phase-0-established invariant that mutations always produce audit entries, and if a kill-switch bypasses approval (§19), how is the emergency entry distinguished from an unauthorized one (T1) after the fact?
  13. §33 shows Flipt evaluating server-side while this blueprint evaluates locally — given §24's T8 (SDK key exfiltration) applies specifically to the local-evaluation model, what would change in the threat model if this blueprint adopted Flipt's approach instead, and would T8 simply be replaced by a different threat?
  14. §30's M7 (100,000 connections/node) and §34.4's derived 800 MB/node memory footprint — at what connection count does a node's memory footprint collide with typical container memory limits (e.g. 1–2 GB), and what does §31 say the lever beyond that ceiling is?
  15. §28's differential testing checks the stats engine against an external reference — but §8.7's sequential boundary (Howard et al. 2021) is a less commonly implemented method than a basic t-test; what does the blueprint actually propose as the "external reference" for that specific equation, and is that answer satisfying?
  16. §9's ADR-14 (bounded dedup, not server-side global dedup) assumes SDKs can be trusted to dedupe correctly — §24's threat model includes T4 (exposure forgery); do these two decisions actually compose safely, or does trusting the SDK's dedup quietly widen the T4 attack surface?
  17. §37's deferred bandit-optimizer and §36's alternative-architectures section both discuss automated decision-making — precisely why does §6's P6 (guardrail-gated reads) make a bandit approach structurally awkward to bolt on later without revisiting the experiment lifecycle in §8.6?
  18. Given §31 names exposure ingestion as the second bottleneck, and §18 batches events every 100 ms or 1,000 events — at what per-instance evaluation rate does the 1,000-event batch threshold trigger before the 100 ms timer does, and does that crossover point match the M8 target's assumptions?

36. Alternative Architectures (Roads Not Taken)

A. Remote/server-side evaluation on every request.

Show the original text diagram
 SDK (thin client) ──gRPC──▶ Evaluation Server ──▶ Rule Store
        ▲                         │
        └────── variant only ─────┘

Winning regime: rule confidentiality matters more than latency, or client platforms cannot safely hold a full ruleset (e.g. thin embedded devices). Embodying system: Flipt (§33). Rejected here because §4's sub-microsecond evaluation budget and P1's offline-safety guarantee are load-bearing requirements this blueprint's users (§1.5) explicitly need — a network hop per evaluation reintroduces exactly the partition-fragility P1 exists to eliminate.

B. Git-repo-as-source-of-truth config with CI-driven delivery, no control plane.

Show the original text diagram
 flags.yaml (git) ──CI pipeline──▶ compiled config ──▶ static artifact ──▶ SDK
        ▲
   PR + review = the "control plane"

Winning regime: teams that already trust git-based review workflows over a bespoke UI, and where flag-change latency of "one CI run" (minutes) is acceptable. Embodying system: GitOps-style config management as practiced by several open-source Unleash deployments using its config-as-code import path. Rejected here because Phase 7's audit log, approval workflow, and sub-2-second kill-switch propagation (§4) are harder to guarantee when "deploy a new config" means "wait for a CI pipeline" — directly conflicting with the kill-switch SLO in §26.

C. Bayesian decision-theoretic stats engine replacing frequentist sequential testing.

Show the original text diagram
 Exposure/Goal events ──▶ Posterior update (per variant) ──▶ P(B>A), credible interval
                                     │
                          (no sequential-boundary concept; posterior is always "valid")

Winning regime: stakeholders who want direct probability statements ("70% chance B is better") and are comfortable specifying/defending a prior. Embodying system: GrowthBook's Bayesian engine (§33). Rejected as the default here (though offered as ADR-15's rejected-alternative-that-sometimes-wins) because always-valid frequentist confidence sequences (Johari et al. 2017, Howard et al. 2021) give a stopping rule with a crisper Type-I-error guarantee that this blueprint's guardrail-gated read model (P6) is built around; a Bayesian engine would require re-deriving §8.6's lifecycle guards around credible-interval thresholds instead.

D. CDN-static-file delivery model with no streaming connections.

Show the original text diagram
 Config Compiler ──▶ Static file (CDN) ◀──polling only── SDK
                          (no SSE, no persistent connections at all)

Winning regime: extremely high SDK fan-out (millions of client-side instances) where maintaining persistent connections at that scale is operationally infeasible, and propagation latency of tens of seconds to minutes is acceptable. Embodying system: this mirrors how several client-side flag SDKs (e.g. mobile-web feature-flag libraries) fetch a CDN-cached JSON blob on a polling interval with no push channel at all. Rejected as the primary transport here because §4's kill-switch propagation target (p99 ≤ 2 s) is unreachable on a CDN-cache-TTL-bound polling-only model; retained as Phase 5's documented fallback rather than the primary path.

38. Glossary

  • Attribute: a named piece of evaluation-context data (country, plan) used by a clause.
  • Allocation salt: the per-experiment Salt value determining its bucket independence from other experiments (§20).
  • Assignment: the resolved (unit id, variant) pairing produced by bucketing.
  • Audit entry: an append-only, hash-chained record of a control-plane mutation.
  • Always-valid p-value: a p-value computed via a confidence sequence that remains valid under continuous monitoring (Johari et al. 2017).
  • Basis point: 1/100th of a percent; rollout weights use basis-points×10 units.
  • Bucket: the numeric position hash(salt, unit_id) mod 100000 used to assign a variant.
  • Bucketing: the deterministic process of mapping a unit id to a bucket.
  • Bucketing version: the named, frozen identity of a specific hash-function-and- input-order contract (P8).
  • Clause: a single (attribute, operator, values) condition inside a rule.
  • Config compiler: the component turning authored state into a ConfigDocument.
  • ConfigDocument: the immutable, versioned, compiled config served to SDKs.
  • ConfigVersion: the monotonic per-environment version number of a ConfigDocument.
  • Confidence sequence: a time-uniform interval valid at every look, not just a pre-specified sample size (Howard et al. 2021).
  • Control plane: the authoring/storage/audit tier; the only mutation trust boundary.
  • CUPED: Controlled-experiment Using Pre-Experiment Data; a variance-reduction covariate adjustment (Deng et al. 2013).
  • Delivery service: the stateless edge tier terminating SDK streaming/polling connections.
  • Dedup window: the bounded time window within which repeat exposures for the same unit id/flag are suppressed.
  • Domain: a top-level traffic-partitioning scope containing one or more layers.
  • EvaluationContext: the caller-supplied attribute bundle plus unit id for one evaluation.
  • EvaluationReason: the tagged reason an evaluation resolved the way it did (FlagOff, TargetMatch, Rollout, Default, Error).
  • Exposure event: a record that a unit id was shown a specific variant of an experiment-bound flag.
  • False discovery rate (FDR): the expected proportion of false positives among all declared significant results; controlled via Benjamini-Hochberg (1995).
  • Fixed horizon: a stopping rule that collects a pre-specified sample size before any decision.
  • Flag: the top-level authored object with variants, targeting, and a rollout.
  • FlagKey: the stable, environment-scoped identifier of a flag.
  • Goal event: a user-action record (conversion, click) used as an experiment outcome metric.
  • Guardrail metric: a declared metric that must not regress for an experiment to be considered launch-safe (P6).
  • Kill switch: a flag designated for emergency disable with an expedited propagation path.
  • Layer: a named mutually-exclusive traffic partition within a domain (Tang et al. 2010).
  • Mutual exclusion: the guarantee that experiments in the same layer never share a unit id.
  • Offline safety: the SDK's guarantee of continued correct evaluation without network access (P1).
  • Operator: a typed comparison/matching function used inside a clause (§8.2).
  • Overlapping layer: the general term for the domain/layer model allowing concurrent, non-interacting experiments.
  • Peeking: checking an experiment's result before its pre-specified stopping condition, which inflates false-positive rate under naive testing.
  • Priority: the integer field determining rule evaluation order (first match wins, I6).
  • Rollout: a weighted variant split applied when no targeting rule matches explicitly, or attached to a rule.
  • Rule: an ordered, clause-guarded targeting condition mapping to a variant or rollout.
  • RuleSet: the SDK-side in-memory representation of the applied ConfigDocument.
  • Salt: the seed string combined with a unit id inside the bucketing hash; changing it reshuffles assignments (§8.3).
  • Sample ratio mismatch (SRM): a statistically significant divergence between planned and realized variant-assignment proportions.
  • Segment: a named, reusable group of units defined by clauses and explicit include/exclude lists.
  • SequentialBoundary: the computed always-valid confidence-sequence bounds gating decision_ready (I12).
  • Sequential testing: statistical methods valid under continuous monitoring (mSPRT, confidence sequences).
  • Sticky bucketing: preserving a unit id's existing variant assignment across a rollout-weight change (§8.3 worked example).
  • Streaming delivery: the SSE-based push transport for config updates.
  • Trust boundary: an architectural line across which data crosses from one authorization/authentication domain to another (§3).
  • UnitId: the randomization unit (usually a stable user id) bucketing is computed against.
  • Variant: one possible typed value a flag can resolve to.
  • VariantId: the stable identifier of a variant, not re-used across edits.
  • VariantWeight: a rollout entry's basis-points×10 share of the bucket space.
  • Version drift: the gap between an SDK's applied ConfigVersion and the latest published version.
