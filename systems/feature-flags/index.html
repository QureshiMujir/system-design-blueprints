In one paragraph

A feature-flag service lets a team switch behaviour on or off for chosen users without redeploying, and an A/B testing service measures whether the change helped. This design is a Rust workspace with six parts: an evaluation engine that runs inside every application process, a control plane for authoring flags and experiments, a compiler that turns authored state into one versioned config document, a delivery service that pushes that document to the applications, an exposure-event ingestion path, and a statistics pipeline (§1). Its defining idea is that trustworthiness belongs to the whole pipeline (bucketing, exposure logging, and inference that stays valid when people peek), not to any single component (§1). Platform operators run it (§1.5).

The problem, concretely

Take the blueprint's own example flag, checkout-v2 (§8.8). The naive version asks a server "which variant does this user get?" on every request. That puts a network call on the hot path, so a partition becomes an outage (P1, §36 A). The blueprint demands evaluation with no I/O and a budget of 150 ns at the median (§4).

The next naive step is to pick a variant at random each time, so one user sees both variants and the experiment means nothing. Assignment must be a pure function of a salt and the user id, giving the same variant on every host and in every language (P2, I2).

The third trap is the statistics. An analyst who checks a naive daily test while the experiment is running reaches a false-positive rate of about 30% (P6, citing Johari et al. 2017; §2 calls peeking "the default failure mode of naive A/B testing"). The design therefore refuses to show a result as decision-ready until a sample-ratio check and a sequential boundary both pass (P6, I12). Finally, if the flag is a kill switch, the whole control path must be fast and trustworthy, not just a UI feature (§2, T7).

How it works, end to end

Follow one change from author to analyst through the boxes of §3. The diagram is adapted from §3.

  1. Control plane (ff-control-plane, §10). The only box allowed to change flag, segment or experiment state. Every change is authenticated, authorized and appended to the audit log before it can reach the compiler (§3). The authored state lives in Postgres, keyed by (environment_id, key) (§3, ADR-11).
  2. Config compiler (ff-config, §10). A pure transformation from authored state to an immutable ConfigDocument at a monotonically increasing ConfigVersion; it never partially applies (§3, I3, I11).
  3. Delivery service (ff-delivery, §10). Stateless; it holds the current document per environment in memory and sits between one publish and N SDK connections (§3). It offers server-sent events (SSE, a one-way push stream over HTTP) and a polling endpoint as the fallback (ADR-08, §3).
  4. SDK local evaluator (ff-sdk, §10). Lives inside the host application, holds the last-known document, and evaluates with zero network calls per evaluation (§1.4, P1). It is also the trust boundary between untrusted request attributes and the flag decision (§3).
  5. Bucketing function (ff-bucketing, §10). A pure function of (salt, unit id) and the one component whose output must never change silently (§3, P8).
  6. Exposure collector and ingestion queue (ff-ingest, §10). The SDK batches ExposureEvent records and ships them across the persistence boundary into a durable, at-least-once queue (§3).
  7. Stats pipeline (ff-stats, §10). Reads exposure and goal events and computes a StatsResult per experiment under a SequentialBoundary, with sample-ratio mismatch (SRM) and guardrail checks (§3). Results land in ClickHouse (§3, ADR-12).

Statistics run asynchronously, never on the evaluation path (P13, §4).

The core ideas

Evaluation: a total order of rules, and a default for everything else (§8.2, §8.8)

A flag has an on/off switch, an ordered list of targeting rules, an optional top-level percentage split, and a default (§8.1). The engine's steps are: a disabled flag returns its off_variant; else walk the rules from highest priority down and return the first full match; else use the top-level rollout if present; else return default_variant (§13.2). Clauses inside a rule are AND-combined and short-circuit on the first false; clauses inside a segment are OR-combined (§8.2). A missing attribute makes a clause false unless NEGATE is set; an unknown operator is a non-match, never an error (§8.2, P10, I7). Equal priorities are broken by declaration order (§13.8).

The blueprint's own trace: context {unit_id: "u-9", country: "US", plan: "pro"}, flag checkout-v2 enabled (§8.8).

Step What happens Source
1 Flag is enabled, so walk rules by descending priority §8.8
2 R1 {country EQ "US" AND plan EQ "pro"}, priority 10: both match, return treatment §8.8
3 R2 (priority 5, 50/50 rollout) is never evaluated: first match wins §8.8, I6

Any evaluation error returns the caller's default; the public API never panics (P4, I5).

Bucketing: hash to a number, then slice the number line (§8.3)

The hash turns a salt and a unit id into one of 100,000 positions; variants own contiguous slices of that line (§8.3).

h(s, u)  =  MurmurHash3_32( s || "." || u )
bucket(s, u)  =  h(s, u) mod 100000

Take weights w_1..w_k summing to 100000, accumulate A_i = Σ_{j≤i} w_j, and assign variant i where A_{i-1} ≤ bucket < A_i (§8.3). The blueprint's worked example, with salt exp-42 and user-777 (§8.3):

Case Weights Bucket Result
Start [50000, 50000] 61,204 variant 2
Rebalance [40000, 60000] 61,204 variant 2, unchanged: the bucket never crossed a moved boundary
A boundary user [50000, 50000] to [40000, 60000] 45,000 moves from variant 1 to variant 2 (the accepted "boundary users move" cost)
New salt exp-42-v2 [50000, 50000] 8,431 variant 1: an uncorrelated reshuffle

Changing the salt is the only supported way to re-randomize a population (§8.3). The hash, the input order and the modulus are frozen: a change is a new named bucketing version, never an in-place edit (P8, I8). One primitive serves both "ship to 10% of users" and "50/50 test", so there is only one hash to keep correct (MM6). A quick uniformity test: 1,000,000 sampled ids over 100,000 buckets, expected count 10 per bucket, accepted at p > 0.01 (§34 item 8).

The config document: one atomic snapshot, pushed with a safety net (§8.4, P3, P7)

The compiler emits a ConfigDocument { version, environment_id, flags, segments, compiled_at }, Protocol-Buffers-encoded and gzip-compressed on the wire (§8.4, ADR-09). The version is a per-environment counter assigned inside a database-serialized transaction (§8.4, I11). The SDK swaps the whole document with one atomic pointer store (ArcSwap), so it never sees flags from two versions mixed (P3, I3).

Delivery follows the shape in §17.2: SSE streams a full document on connect (or deltas if the client is close behind), with a keepalive every 30 seconds. Polling uses If-None-Match: <ConfigVersion> and gets 304 Not Modified when nothing changed. After a drop the SDK reconnects with backoff from 1 s up to 60 s; after 5 minutes of failures it polls every 60 s and retries SSE every 5 minutes (§17.2, P7). Corruption is handled by discarding: in §8.10 the delivery service publishes ConfigVersion(118), the write times out mid-frame, the SDK drops the partial delta and asks for a full resend at its last-known-good version (§8.10, I3). A slow subscriber's channel drops events rather than blocking everyone, and the next full resend resynchronizes it (§17.2, ADR-28).

Exposure events: the experiment's measuring instrument (§8.5, P5)

An exposure is a record that a unit saw a variant of an experiment-bound flag (§38). Its fields are timestamp, unit id, flag key, optional experiment id, variant id, config version and a dedup key (§8.5). The SDK emits one only when evaluate() resolves through an experiment-bound rule, not on every evaluation (§18.2, ADR-14, FM-5). A bounded window, default one hour, suppresses repeats with the same (unit_id, flag_key, window) key (§18.2, §8.5). Events are batched every 100 ms or 1,000 events, whichever comes first, and the queue is at-least-once, so a downstream dedup keyed the same way guards against redelivery (§18.2, ADR-13). The blueprint's acceptance example: 1,000,000 evaluations against 100 unique unit ids inside one window produce exactly 100 exposure events (§18.4, M9). MM5 states why this matters: an emission bug is a data-integrity bug, because SRM detection depends on the counts (P5, I4).

Honest statistics: sequential testing, SRM and the experiment lifecycle (§8.6, §8.7)

A time-uniform confidence sequence stays valid at every look. With running estimate θ̂_t, mixing parameter ψ and error rate α (§8.7):

CS_t = [ θ̂_t ± ( σ̂_t / √n_t ) · √( 2 (n_t ψ + 1) / n_t² · ln( (n_t ψ + 1) / α² ) ) ]

An experiment may conclude the instant 0 ∉ CS_t, at any t, with Type-I error still bounded by α (§8.7, ADR-15). A second guard checks that the realized split matches the planned one: a chi-square test with p < 0.001 moves the experiment from Running to Peeking-Blocked (§8.6, FM-4). A third, CUPED, uses a pre-experiment covariate Y to subtract predictable variance: X_cuped = X - θ(Y - Ȳ) with θ = Cov(X, Y) / Var(Y), giving Var(X)(1 - ρ²) (§8.7).

The lifecycle (§8.6) is a small state machine:

From Event To Guard
Draft start Running at least one guardrail metric declared (else NoGuardrailDeclared)
Running srm_detected Peeking-Blocked chi-square p < 0.001
Running conclude Concluded boundary crossed or fixed horizon reached (else PrematureConclusion)
any emergency_stop Concluded (invalid) kill switch on the bound flag; always audited

Sizing example (the two-proportion MDE formula of §34 item 7): baseline 5%, target 5.5%, α = 0.05, power 80% needs about 31,196 users per variant, about 3.1 days at 10,000 daily users per variant (§34 item 7).

Layers: sharing traffic without experiments contaminating each other (§22.2, P12)

Traffic is a scarce resource (§2). A domain holds layers; each experiment sits in one layer. A unit id is first hashed with a layer-specific salt to choose a layer, and only then bucketed for an experiment (§22.2, ADR-17). Experiments in the same layer are mutually exclusive; experiments in different layers of the same domain run concurrently and are independent by construction (§22.2, MM7). A layer's traffic allocations may not exceed 100% (§22.2). Phase 10's checks: 10,000 synthetic ids in a two-experiment layer show zero units in both, and separate layers pass a chi-square independence test at p > 0.01 (§22.4).

The trade-offs — where engineers disagree

Evaluation location: inside the application (ADR-04)

Chosen: local, in-SDK evaluation, for the sub-microsecond budget (§4) and offline safety (P1). Rejected: remote per-request evaluation. When the rejected choice is right: for a low-QPS admin console that needs zero SDK deployment (ADR-04, §36 A).

Rule language: a typed grammar, not a script (ADR-05)

Chosen: a custom typed EBNF grammar (§8.2), for static analyzability and cycle and DoS safety at save time. Rejected: embedded scripting (Lua/Rhai) and raw JSON logic trees. When the rejected choice is right: when authors need arbitrary computed attributes and trust is fully internal.

Bucketing hash: fast, not cryptographic (ADR-06)

Chosen: MurmurHash3 (32-bit), for uniformity and avalanche properties at the required throughput. Rejected: xxHash and truncated SHA-256. When the rejected choice is right: SHA-256 wins when the threat model includes an adversary choosing unit ids to force a bucket (T3), trading throughput for pre-image resistance. MM3 puts it as "cryptography-adjacent, not cryptography".

Transport: SSE with a polling fallback (ADR-08)

Chosen: SSE plus polling, because the need is one-directional, proxy- and CDN-friendly, with simple reconnect semantics. Rejected: WebSocket, long-poll only, gRPC bidirectional stream. When the rejected choice is right: a gRPC stream wins inside a fully gRPC-native mesh where SSE's HTTP/1.1 heritage adds no value.

Exposure dedup: a bounded window in the SDK (ADR-14)

Chosen: a bounded per-session dedup window, trading storage cost against SRM-detection accuracy. Rejected: no dedup, or server-side global dedup. When the rejected choice is right: server-side global dedup wins when SDKs cannot be trusted to dedupe, such as untrusted third-party SDKs. §35 item 16 asks whether trusting the SDK widens the T4 forgery surface.

Stats engine: frequentist sequential (ADR-15)

Chosen: always-valid confidence sequences, so analysts may peek at any time (Johari et al. 2017). Rejected: pure Bayesian, and fixed-horizon frequentist only. When the rejected choice is right: Bayesian wins when stakeholders want direct "P(B>A)" statements and accept prior-sensitivity (ADR-15, §33, §36 C).

Overlapping experiments: explicit layers (ADR-17)

Chosen: domains and layers (Tang et al. 2010), which prevent uncoordinated interaction on shared traffic (P12). Rejected: fully independent random assignment per experiment. When the rejected choice is right: a low-experiment-count organization where layer administration overhead is not justified.

Consistency: strong where it counts, eventual elsewhere (ADR-10)

Chosen: read-your-writes on the control plane, eventual on delivery fan-out, with no cross-node consensus tax. Rejected: strong global consistency across all SDKs. When the rejected choice is right: for a kill-switch-only fast lane, which the table says justifies "ADR-10a"; no such row exists in §9 (T7 cites it too).

Roads not taken

Remote evaluation on every request (§36 A): wins when rule confidentiality matters more than latency or a client cannot hold a full ruleset; Flipt works this way (§36 A, §33). Rejected because a network hop per evaluation brings back the partition fragility P1 exists to remove (§36 A).

Git repository as the control plane (§36 B): wins for teams that trust git review over a bespoke UI and accept "one CI run" of latency. Rejected because audit, approvals and sub-2-second kill-switch propagation are harder to guarantee behind a pipeline (§36 B, §26).

Bayesian engine as the default (§36 C): wins for stakeholders who want probability statements and can defend a prior; GrowthBook offers one (§36 C, §33). Rejected as default because the guardrail-gated read model (P6) is built around always-valid frequentist boundaries (§36 C).

CDN static file, polling only (§36 D): wins at millions of client-side instances where persistent connections are infeasible and minutes of delay are fine. Rejected as the primary path because the kill-switch propagation target of p99 ≤ 2 s is unreachable on a cache-TTL model; kept as the fallback (§36 D, §26).

Deferred (§37): automatic mTLS rotation, bandit auto-optimization, multi-region active-active control plane, SIMD clause evaluation.

What must never be false

  • I1: evaluation is side-effect-free and never blocks on I/O. Noticed by code review, #[forbid] lints and the eval latency histogram (§7).
  • I2: the same (flag, unit id, config version) gives the same variant on every SDK. Noticed by differential tests and the bucket-parity-mismatch counter (§7).
  • I3: a served config is never a partial update. Noticed by a version monotonicity check and the config-apply-version gauge (§7).
  • I4: every served variant emits exactly one exposure per evaluation context. Noticed by the SRM chi-square test and exposure-count-per-bucket (§7).
  • I5: a flag's default is returned on any evaluation error, never a panic. Noticed by fuzzing (§7).
  • I6: rule evaluation order is total and documented. Noticed by evaluation-trace replay (§7).
  • I7: unknown operators evaluate to non-match. Noticed by a forward-compat fixture and a counter (§7).
  • I8: the bucketing hash and input order are fixed per bucketing version. Noticed by cross-language parity vectors and the bucketing-version gauge (§7).
  • I9: segment references form a DAG, never a cycle. Noticed by the save-time validator, an eval-time depth cap and the segment-cycle-rejected counter (§7).
  • I10: audit entries are immutable. Noticed by a hash-chain verification job (§7).
  • I11: a ConfigVersion only increases per environment. Noticed by a version-regression check on publish and an alert (§7).
  • I12: a StatsResult is not decision-ready until SRM and the sequential boundary both pass. Noticed by the two checks and the result-not-ready counter (§7).
  • I13: rollout weights sum to exactly 100,000. Noticed by save-time validation (§7, §8.9).
  • I14: an SDK never mutates flag, segment or experiment state. Noticed by the control-plane auth boundary and an unauthorized-write alert (§7).

What breaks in production

  • FM-1: a rollback resurrects a stale variant assignment. Symptom: users flip variants after a revert. Cause: reverting to an older ConfigVersion after a salt or weight edit went out and back. Detection: version drift plus bucket-assignment-history comparison. Recovery: none automatic; re-publish forward with a corrected version instead of reverting past a bucketing change (§25).
  • FM-2: SDKs get a 404 on a published ConfigVersion. Cause: blob-store write lag after the commit. Detection: the delivery service's missing-blob counter. Recovery: retry through the compiler's re-publish path, or re-trigger compile-and-publish by hand (§25).
  • FM-3: a delivery node serves a frozen version while looking healthy. Cause: a stuck subscription to the internal change bus. Detection: a "time since last publish observed" gauge. Recovery: the node restarts its subscription past a staleness threshold, or is drained (§25, P7).
  • FM-4: sample ratio mismatch. Cause: a bucketing bug, bot traffic, or a mid-experiment SDK upgrade with a different bucketing version. Detection: the continuous SRM chi-square check. Recovery: automatic Running to Peeking-Blocked, then root-cause investigation (§25, §8.6).
  • FM-5: exposures emitted on paths the user never saw. Cause: emitting on evaluation rather than on experiment-bound resolution. Detection: an exposure-volume-versus-traffic sanity check. Recovery: none automatic, since this is a design-time invariant; fix the code and backfill-correct the data window (§25, P5).
  • FM-6: SDK CPU spikes on one flag. Cause: a catastrophic-backtracking regex clause. Detection: a per-evaluation CPU budget alert. Recovery: reject or rewrite the clause at save time; a shipped clause needs a hotfix compile (§25). The design closes the class with an RE2-class engine (§13.2).
  • FM-9: old SDKs crash on a new ruleset. Cause: a new operator shipped without forward-compatible deserialization. Detection: crash reports aggregated by SDK version. Recovery: recompile the config to avoid the new operator until the fleet upgrades (§25, MM8).
  • FM-10: peeking inflates false positives. Cause: analysts reading naive fixed-horizon p-values under continuous monitoring. Detection: none automatic; it is a process failure. Recovery: the UI refuses to show a non-sequential p-value as primary (§25, P6).

Threats worth knowing (§24): T1, an unauthorized flag flip with a stolen admin credential, answered by role-based access, approvals and an audited break-glass kill switch; T2, a man-in-the-middle serving a malicious variant, answered by TLS 1.3 and an integrity hash the SDK checks; T3, unit-id enumeration, a documented residual risk with an optional SHA-256-truncated mode; T4, forged exposure events, answered by signed payloads and plausibility bounds; T7, flooding delivery to delay the kill switch, answered by a dedicated low-fanout fast lane.

How it compares

  • LaunchDarkly chose a mature streaming tier and a proprietary stats engine (§33). Fine for large enterprises that accept cost and partial vendor lock-in (§33).
  • Unleash chose flags only, no native stats, polling with optional streaming via Unleash Edge (§33). Fine for teams that already have an analytics stack and just need reliable toggling (§33).
  • GrowthBook chose sticky bucketing and a Bayesian-first stats engine, with SSE and polling (§33). Fine for teams wanting an open-source, statistically sophisticated platform without building one (§33).
  • Flipt chose server-side gRPC evaluation with no push (§33). Fine where a network hop per evaluation is acceptable and rule confidentiality matters more than latency (§33, §36 A).
  • Google's overlapping-experiment infrastructure (Tang et al. 2010) chose domains and layers, which Phase 10 adopts wholesale (§33). Fine at thousands of concurrent experiments on one traffic pool, since it solves interaction in infrastructure, not in analysis (§33).

Questions to test yourself

  1. Why does bucketing (§8.3, Phase 2) need to be a permanent compatibility commitment (P8, I8) when almost every other component in §27 allows versioned evolution — what is structurally different about this one function? — Hint: P8 and the "Bucketing-function stability" paragraph of §27.
  2. §24's T3 (unit-id enumeration) and ADR-06's choice of MurmurHash3 over SHA-256 are in tension — walk through the exact deployment conditions (§1.4 users/operators) under which that tradeoff is acceptable versus unacceptable. — Hint: the "When the Rejected Choice Wins" cell of ADR-06 and MM3.
  3. §25's FM-1 (stale variant resurrection on rollback) and §27's rolling-upgrade guarantee both touch config versioning — why is "roll back the config version" explicitly discouraged while "roll back the binary" is the canary/rollback policy in §26; what makes these asymmetric? — Hint: FM-1's recovery column and the canary paragraph of §26.
  4. §9's ADR-14 (bounded dedup, not server-side global dedup) assumes SDKs can be trusted to dedupe correctly — §24's threat model includes T4 (exposure forgery); do these two decisions actually compose safely, or does trusting the SDK's dedup quietly widen the T4 attack surface? — Hint: the downstream dedup in §18.2 and the T4 mitigation column.
  5. §8.6's experiment lifecycle allows emergency_stop from any state — does this conflict with §12's Phase-0-established invariant that mutations always produce audit entries, and if a kill-switch bypasses approval (§19), how is the emergency entry distinguished from an unauthorized one (T1) after the fact? — Hint: the last row of the §8.6 table and T1's mitigation column.

If you only remember three things

A feature flag is a locally evaluated, offline-safe cache of a compiled config, so a partition serves the last-good document and never an error (MM1, P1, P3). Assignment is a pure, frozen hash of salt and unit id, which is why the same user gets the same variant everywhere and why the hash can never silently change (P2, P8, I8). An experiment result is only trustworthy if exposures are logged exactly once, the split is checked for mismatch, and the statistics stay valid under peeking (MM2, MM5, I12).

Words used here

  • Flag: the top-level authored object with variants, targeting rules and a rollout (§38).
  • Salt: the seed string combined with the unit id in the hash; changing it reshuffles (§38).
  • Bucket: the position hash(salt, unit_id) mod 100000 used to assign a variant (§38).
  • ConfigDocument: the immutable, versioned, compiled config served to SDKs (§38).
  • Exposure event: a record that a unit id was shown a variant of an experiment-bound flag (§38).
  • Sample ratio mismatch (SRM): a significant gap between planned and realized variant shares (§38).
  • Peeking: checking a result before its stopping condition, inflating false positives (§38).
  • Layer: a named mutually exclusive traffic partition inside a domain (§38).
