Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If the config compiler (§15, Phase 3) and the delivery service (§17, Phase 5) both claim "the config is consistent," what specifically prevents a torn read from the blob store from violating that claim under FM-2's exact failure scenario?
  2. Why does bucketing (§8.3, Phase 2) need to be a permanent compatibility commitment (P8, I8) when almost every other component in §27 allows versioned evolution — what is structurally different about this one function?
  3. Phase 9's sequential boundary (§8.7) and Phase 10's layer independence (§22) both claim statistical validity — under what combined scenario could a layer-independent experiment still produce an invalid sequential-boundary read?
  4. §24's T3 (unit-id enumeration) and ADR-06's choice of MurmurHash3 over SHA-256 are in tension — walk through the exact deployment conditions (§1.4 users/operators) under which that tradeoff is acceptable versus unacceptable.
  5. §4 sets a sub-microsecond evaluation budget and §30's M2 sets p99 at 900 ns — given §8.2's grammar allows unbounded clause lists per rule, what caps actually keep M2 true, and where are those caps enforced (§4's "segments per flag" and "rules per flag" limits, or somewhere else)?
  6. §25's FM-1 (stale variant resurrection on rollback) and §27's rolling-upgrade guarantee both touch config versioning — why is "roll back the config version" explicitly discouraged while "roll back the binary" is the canary/rollback policy in §26; what makes these asymmetric?
  7. §21 (Phase 9) computes CUPED-adjusted variance and a raw sequential boundary simultaneously — does CUPED's covariate adjustment interact with the always-valid confidence sequence's validity guarantee, or are they orthogonal? Justify from §8.7's equations.
  8. §22's mutual-exclusion layering (Phase 10) and §20's per-experiment salt independence (Phase 8) both aim to prevent correlated assignment — under what authoring mistake could both protections simultaneously fail?
  9. §24's T9 (results tampering) is mitigated by "results are re-derivable from raw events" — what does that actually require of the exposure/goal event retention policy in §26, and what happens if retention expires before a tampering investigation completes?
  10. §17's thundering-herd throttling and §7 (original architecture) both address mass reconnection — given §31's claim that streaming fan-out is the first bottleneck to scale, what specifically differentiates a routine deploy-triggered reconnect storm from an attacker-triggered one (§24 T7), and does the mitigation differ?
  11. §18's dedup window (Phase 6) trades storage for accuracy — using §34's ingest bandwidth derivation, what dedup-window size would make exposure storage exceed the daily ceiling assumed in §34.6, and is that window size plausible in practice?
  12. §8.6's experiment lifecycle allows emergency_stop from any state — does this conflict with §12's Phase-0-established invariant that mutations always produce audit entries, and if a kill-switch bypasses approval (§19), how is the emergency entry distinguished from an unauthorized one (T1) after the fact?
  13. §33 shows Flipt evaluating server-side while this blueprint evaluates locally — given §24's T8 (SDK key exfiltration) applies specifically to the local-evaluation model, what would change in the threat model if this blueprint adopted Flipt's approach instead, and would T8 simply be replaced by a different threat?
  14. §30's M7 (100,000 connections/node) and §34.4's derived 800 MB/node memory footprint — at what connection count does a node's memory footprint collide with typical container memory limits (e.g. 1–2 GB), and what does §31 say the lever beyond that ceiling is?
  15. §28's differential testing checks the stats engine against an external reference — but §8.7's sequential boundary (Howard et al. 2021) is a less commonly implemented method than a basic t-test; what does the blueprint actually propose as the "external reference" for that specific equation, and is that answer satisfying?
  16. §9's ADR-14 (bounded dedup, not server-side global dedup) assumes SDKs can be trusted to dedupe correctly — §24's threat model includes T4 (exposure forgery); do these two decisions actually compose safely, or does trusting the SDK's dedup quietly widen the T4 attack surface?
  17. §37's deferred bandit-optimizer and §36's alternative-architectures section both discuss automated decision-making — precisely why does §6's P6 (guardrail-gated reads) make a bandit approach structurally awkward to bolt on later without revisiting the experiment lifecycle in §8.6?
  18. Given §31 names exposure ingestion as the second bottleneck, and §18 batches events every 100 ms or 1,000 events — at what per-instance evaluation rate does the 1,000-event batch threshold trigger before the 100 ms timer does, and does that crossover point match the M8 target's assumptions?

32. Mental Models & First Principles

MM1 — A feature flag is a distributed configuration cache whose correctness property is agreement, not freshness. Predicts: an SDK serving a slightly-stale config during a partition is correct behavior, not a bug. Bug class avoided: chasing "always freshest" designs that sacrifice offline safety. Resolved in §6 (P1), §3.

MM2 — An experiment is a hypothesis test whose validity is destroyed by the act of looking early, unless the test was built to be looked at. Predicts: any dashboard showing a live p-value without a sequential-testing foundation will eventually produce a false winner. Bug class avoided: shipping features on peeked, uncorrected p-values. Resolved in §8.7, Phase 9.

MM3 — Bucketing is cryptography-adjacent, not cryptography. Predicts: a fast non-cryptographic hash is fine for fairness/uniformity but not for adversarial resistance. Bug class avoided: assuming MurmurHash3 protects against a motivated attacker choosing their own unit id. Resolved in §24 (T3), ADR-06.

MM4 — Config delivery and config authorship are different trust domains. Predicts: the delivery service must never be able to mutate state, only relay it. Bug class avoided: a compromised edge node escalating into a control-plane write. Resolved in §3, §24 (T1, T6).

MM5 — Exposure logging is part of the experiment's measurement instrument, not a side effect of evaluation. Predicts: any exposure-emission bug is a data-integrity bug, not a logging nuisance. Bug class avoided: treating FM-5-class over-emission as low-priority. Resolved in §6 (P5), Phase 6.

MM6 — A rollout percentage and an experiment allocation are the same primitive (a weighted bucket split) used for two different purposes. Predicts: the same bucketing function must serve both "ship to 10% of users" and "A/B test with 50/50 split" without divergent code paths. Bug class avoided: maintaining two hash functions that silently drift apart. Resolved in §8.3, §11.

MM7 — Overlapping experiments are a traffic-allocation problem before they are a statistics problem. Predicts: solving interaction via layering must happen at the bucketing layer, not after the fact in analysis. Bug class avoided: trying to "statistically adjust for" experiment interaction post hoc instead of preventing it via disjoint traffic partitions. Resolved in §8.6, Phase 10.

MM8 — Forward compatibility is a property you must design for, not one you retrofit after the first breaking rule-language change ships. Predicts: any Operator enum growth without a P10-style non-match fallback breaks old SDKs the day it ships. Bug class avoided: FM-9. Resolved in §6 (P10), §27.

MM9 — The audit log's threat model is insider risk, not just external attack. Predicts: the most likely audit-log-defeating actor is a legitimate but compromised or careless internal credential, not a network attacker. Bug class avoided: designing audit-log integrity controls only against external threats while leaving the application's own DB role over-privileged. Resolved in §6 (P11), §24 (T6).

Required reading (§5)

Books

  • Trustworthy Online Controlled Experiments (Kohavi, Tang, Xu, 2020) — chapters on the OEC (overall evaluation criterion), trigger analysis, and the "twyman's law" discussion of surprising results. Extract: the discipline of pre-registering the metric and guardrail set before an experiment starts. Applied in §8, §9, Phase 9.
  • Designing Data-Intensive Applications (Kleppmann) — chapters 5 (replication) and 11 (stream processing). Extract: the delivery-service replica consistency model and the exposure-event ingestion queue's at-least-once semantics. Applied in §3, Phase 5, Phase 6.
  • Database Internals (Petrov) — chapter on WAL and log-structured storage. Extract: why the audit log is append-only and hash-chained rather than mutable-with-history. Applied in §7, Phase 7.
  • Site Reliability Engineering (Beyer et al.) — chapters on SLOs and on-call. Extract: error budgets applied to the kill-switch propagation SLO. Applied in §26.
  • Statistical Inference (Casella & Berger) — chapters on hypothesis testing and sequential analysis foundations. Extract: the Neyman-Pearson lemma as the baseline the sequential test must still respect asymptotically. Applied in §8, Phase 9.
  • The Art of Computer Programming, Vol 3 (Knuth) — sorting/searching chapter on hash functions. Extract: avalanche and uniformity properties required of the bucketing hash. Applied in §8, Phase 2.
  • Release It! (Nygard) — circuit breaker and bulkhead patterns. Extract: the SDK's offline-safe fallback behavior as a bulkhead around the delivery service. Applied in §6 (P1), Phase 4.

Papers

  • Kohavi, Henne, Sommerfield, KDD 2007, "Practical Guide to Controlled Experiments on the Web" — pitfalls (OEC selection, ramp-up). Applied in Phase 8, §9.
  • Kohavi et al., KDD 2013, "Online Controlled Experiments at Large Scale" — the institutional infrastructure needed to run thousands of concurrent experiments. Applied in §3, Phase 10.
  • Tang et al., KDD 2010, "Overlapping Experiment Infrastructure: More, Better, Faster Experimentation" (Google) — the layer/domain model for mutually-exclusive traffic partitioning. Applied in Phase 10, §8.
  • Bakshy, Eckles, Bernstein, CHI 2014, "Designing and Deploying Online Field Experiments" (PlanOut, Facebook) — the declarative randomization-unit language. Applied in §8 (rule grammar), Phase 1.
  • Xu et al., KDD 2015, "From Infrastructure to Culture: A/B Testing Challenges in Large Scale Social Networks" (LinkedIn XLNT) — network-interference and organizational-scaling lessons. Applied in §31, §33.
  • Deng, Xu, Kohavi, Walker, WSDM 2013, "Improving the Sensitivity of Online Controlled Experiments by Utilizing Pre-Experiment Data" (CUPED) — variance reduction via covariate adjustment. Applied in §8 (stats model equations), Phase 9.
  • Johari, Koomen, Pekelis, Walsh, KDD 2017, "Peeking at A/B Tests: Why it matters and what to do about it" — always-valid inference via confidence sequences. Applied in §8, Phase 9, §35.
  • Howard, Ramdas, McAuliffe, Sekhon, 2021, "Time-uniform, nonparametric, nonasymptotic confidence sequences" — the mathematical basis for the SequentialBoundary type. Applied in §8, §11, Phase 9.
  • Benjamini, Hochberg, 1995, "Controlling the False Discovery Rate" — multiple- comparison correction for multi-variant/multi-metric experiments. Applied in Phase 9, ADR-19.
  • Karger et al., STOC 1997, "Consistent Hashing and Random Trees" — the theoretical basis distinguishing consistent hashing from the simpler modulo-bucketing this system uses; clarifies why bucketing does not need ring-based consistent hashing. Applied in §8, ADR-06.

Reference Implementations

  • OpenFeature SDK spec repo — specification/sections/02-evaluation-context.md and 03-flag-evaluation.md. Lesson: a vendor-neutral evaluation-context shape. Pitfall: do not copy its provider-abstraction indirection wholesale — it costs an extra allocation per evaluation this system's latency budget cannot afford. Applied in §11, Phase 1.
  • Unleash (server/src/lib/db and server/src/lib/services/client-metrics) — Lesson: its strategy-constraint model for percentage rollouts. Pitfall: its metrics ingestion couples too tightly to its Postgres schema; keep the queue decoupled. Applied in Phase 2, Phase 6.
  • Flagsmith (api/flag_engine and its cross-language flag-engine core) — Lesson: a shared-core-with-language-bindings design for cross-language parity. Pitfall: its engine historically diverged from the Python reference under edge-case rule ordering; conformance vectors must be the single source of truth, not any one language's implementation. Applied in Phase 2, Phase 11.
  • GrowthBook (packages/sdk-js/src/GrowthBook.ts and packages/back-end/src/util) — Lesson: sticky-bucketing via a separate assignment cache to survive rollout-weight changes without reshuffling existing users. Pitfall: sticky-bucket cache growth is unbounded without a TTL; bound it. Applied in §8 (bucketing equations), Phase 2.
  • Flipt (internal/server/evaluation and its declarative rule engine) — Lesson: a clean separation between the evaluator (pure) and the storage layer (gRPC-fronted). Pitfall: its evaluator historically allowed segment-cycle references; this blueprint requires cycle detection at save time (I9). Applied in Phase 1, Phase 7.
  • LaunchDarkly published SDK evaluation semantics (their public "How LaunchDarkly's SDKs evaluate flags" documentation) — Lesson: the documented evaluation-reason taxonomy (EvaluationReason) this blueprint adopts nearly verbatim. Pitfall: their rule-index-based targeting model is powerful but hard to diff/audit; this blueprint keeps explicit rule IDs instead. Applied in §11, Phase 7.

Glossary (§38) · 52 terms · site-wide glossary

Attribute
: a named piece of evaluation-context data (country, plan) used by a clause.
Allocation salt
: the per-experiment Salt value determining its bucket independence from other experiments (§20).
Assignment
: the resolved (unit id, variant) pairing produced by bucketing.
Audit entry
: an append-only, hash-chained record of a control-plane mutation.
Always-valid p-value
: a p-value computed via a confidence sequence that remains valid under continuous monitoring (Johari et al. 2017).
Basis point
: 1/100th of a percent; rollout weights use basis-points×10 units.
Bucket
: the numeric position hash(salt, unit_id) mod 100000 used to assign a variant.
Bucketing
: the deterministic process of mapping a unit id to a bucket.
Bucketing version
: the named, frozen identity of a specific hash-function-and- input-order contract (P8).
Clause
: a single (attribute, operator, values) condition inside a rule.
Config compiler
: the component turning authored state into a ConfigDocument.
ConfigDocument
: the immutable, versioned, compiled config served to SDKs.
ConfigVersion
: the monotonic per-environment version number of a ConfigDocument.
Confidence sequence
: a time-uniform interval valid at every look, not just a pre-specified sample size (Howard et al. 2021).
Control plane
: the authoring/storage/audit tier; the only mutation trust boundary.
CUPED
: Controlled-experiment Using Pre-Experiment Data; a variance-reduction covariate adjustment (Deng et al. 2013).
Delivery service
: the stateless edge tier terminating SDK streaming/polling connections.
Dedup window
: the bounded time window within which repeat exposures for the same unit id/flag are suppressed.
Domain
: a top-level traffic-partitioning scope containing one or more layers.
EvaluationContext
: the caller-supplied attribute bundle plus unit id for one evaluation.
EvaluationReason
: the tagged reason an evaluation resolved the way it did (FlagOff, TargetMatch, Rollout, Default, Error).
Exposure event
: a record that a unit id was shown a specific variant of an experiment-bound flag.
False discovery rate (FDR)
: the expected proportion of false positives among all declared significant results; controlled via Benjamini-Hochberg (1995).
Fixed horizon
: a stopping rule that collects a pre-specified sample size before any decision.
Flag
: the top-level authored object with variants, targeting, and a rollout.
FlagKey
: the stable, environment-scoped identifier of a flag.
Goal event
: a user-action record (conversion, click) used as an experiment outcome metric.
Guardrail metric
: a declared metric that must not regress for an experiment to be considered launch-safe (P6).
Kill switch
: a flag designated for emergency disable with an expedited propagation path.
Layer
: a named mutually-exclusive traffic partition within a domain (Tang et al. 2010).
Mutual exclusion
: the guarantee that experiments in the same layer never share a unit id.
Offline safety
: the SDK's guarantee of continued correct evaluation without network access (P1).
Operator
: a typed comparison/matching function used inside a clause (§8.2).
Overlapping layer
: the general term for the domain/layer model allowing concurrent, non-interacting experiments.
Peeking
: checking an experiment's result before its pre-specified stopping condition, which inflates false-positive rate under naive testing.
Priority
: the integer field determining rule evaluation order (first match wins, I6).
Rollout
: a weighted variant split applied when no targeting rule matches explicitly, or attached to a rule.
Rule
: an ordered, clause-guarded targeting condition mapping to a variant or rollout.
RuleSet
: the SDK-side in-memory representation of the applied ConfigDocument.
Salt
: the seed string combined with a unit id inside the bucketing hash; changing it reshuffles assignments (§8.3).
Sample ratio mismatch (SRM)
: a statistically significant divergence between planned and realized variant-assignment proportions.
Segment
: a named, reusable group of units defined by clauses and explicit include/exclude lists.
SequentialBoundary
: the computed always-valid confidence-sequence bounds gating decision_ready (I12).
Sequential testing
: statistical methods valid under continuous monitoring (mSPRT, confidence sequences).
Sticky bucketing
: preserving a unit id's existing variant assignment across a rollout-weight change (§8.3 worked example).
Streaming delivery
: the SSE-based push transport for config updates.
Trust boundary
: an architectural line across which data crosses from one authorization/authentication domain to another (§3).
UnitId
: the randomization unit (usually a stable user id) bucketing is computed against.
Variant
: one possible typed value a flag can resolve to.
VariantId
: the stable identifier of a variant, not re-used across edits.
VariantWeight
: a rollout entry's basis-points×10 share of the bucket space.
Version drift
: the gap between an SDK's applied ConfigVersion and the latest published version.
