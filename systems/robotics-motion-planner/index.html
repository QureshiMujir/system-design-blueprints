In one paragraph

A motion planner answers one question for a robot: given where I am, where I want to be, and a map, what route can I follow without hitting anything, and when should each part of it happen? This blueprint specifies a from-scratch Rust library of 13 crates, one of which builds the command-line tool mpctl (§1, §1.6). It returns a collision-free, time-stamped trajectory, byte-identical for the same inputs and seed (§1, §3.3), plus a small real-time loop that steers around moving obstacles and asks for a new plan when the old one is blocked (§1, §3.2). Vehicle, drone and arm teams embed it, and researchers run it offline (§1.4, §1.5).

The problem, concretely

Take a 7-joint arm reaching into a shelf, one of the blueprint's benchmark scenarios (Phase 6). In an empty environment every motion is valid and a straight line is trivial (§8.10); with a shelf in the way, the planner has to search. A grid search is fine for a flat 2-D map, but grid planners scale with the cell count, and sampling-based planners are what reach 6–7 degrees of freedom (§2.1, Scalability Analysis).

Suppose the search succeeds. Two more things go wrong. First, almost all the time goes into asking "is this pose in collision?": the blueprint puts it above 90% of planning time (§2.1, P1). Second, a car cannot turn sharper than its minimum turning radius, so a path with a sharp corner is unexecutable no matter how collision-free it is (I3, §7.3). Even a perfect plan goes stale once the map changes, and replanning from scratch in a dynamic map blows the local loop's real-time budget (P3, MM10).

The blueprint answers these in order: one abstraction (C-space) serves every robot (MM1), a heavily optimised collision checker sits at the centre (MM2), steering is built to obey turning limits by construction (MM9), and a bounded-time loop handles change (P9).

How it works, end to end

Follow one PlanRequest through the boxes of §3.1's diagram:

 PlanRequest (robot, env, q_s, q_g, cfg, seed)
        -> mp-planner      validate start/goal, pick planner, orchestrate
        -> mp-space  <-->  mp-collision (broad: BVH/grid; narrow: GJK/EPA/SAT)  <--> mp-env
        -> GLOBAL PLANNER  { mp-graph | mp-sampling | mp-steer }
        -> mp-opt          shortcutting + CHOMP-style smoothing
        -> mp-time         trapezoidal / S-curve / TOPP-lite  => Trajectory
   ---- OFFLINE | REAL-TIME (concurrency boundary) ----
        -> mp-local        DWA loop, <= 20 ms per tick  --(blocked/stale)--> replan trigger
        -> velocity command (v, omega) to the controller (#289)
  1. mp-planner owns the request and runs the pipeline. First it checks that the start and goal are inside bounds and not in collision, and returns a typed error otherwise (§3.2, I11, §8.11).
  2. mp-space defines the configuration space: sample a pose, interpolate, measure distance, check bounds (§3.2). mp-geom supplies shapes, transforms and forward kinematics (§1.1 row 2).
  3. mp-collision says whether a pose or a motion is in collision: a broad phase culls pairs, a narrow phase resolves the survivors (§3.2, §8.6).
  4. mp-env holds the map as an OccupancyGrid, a Costmap and an Esdf, and answers cost and clearance queries. It treats map files as untrusted input (§3.2, §3.3).
  5. The global planner is one of three crates. mp-graph does grid search (A*, Dijkstra, D* Lite). mp-sampling does PRM, RRT, RRT-Connect, RRT* and Informed RRT*. mp-steer does Dubins, Reeds-Shepp, state lattices and Hybrid A* (§3.2).
  6. mp-opt shortens and smooths the raw path without making it collide, and mp-time attaches timestamps within speed and acceleration limits, giving the Trajectory (§3.2, §8.8).
  7. mp-local is the only real-time component. Each tick it picks the best safe velocity command and raises a replan request if the trajectory is blocked (§3.2, §1.4).
  8. mp-cli (mpctl) exposes plan, smooth, time, local, bench, viz and validate. mp-bench holds scenarios, the determinism check and the anytime-curve recorder (§1.4, §1.6).

Three boundaries organise the boxes (§3.3). A lock-free single-slot channel separates offline planning from the real-time loop. Map files and robot models are untrusted, so parsing is bounds-checked and capped. One seeded generator feeds every random draw.

The core ideas

One space for every robot, one step for every tree (§8.1, §8.9, MM1)

Describe a robot's whole pose as a single point in an abstract space (configuration space, or C-space). A planner that works on points in such a space works for any robot (MM1). The blueprint has four spaces (§8.1):

Space Degrees of freedom State Used for
R² (point) 2 (x, y) holonomic mobile robot, 2-D demos
SE(2) 3 (x, y, θ) mobile robots
SE(3) 6 (x, y, z, quaternion) drones, free-flying bodies
R^n (joint) 6–7 (q₁..qₙ) with limits manipulators

Planners that grow a tree (RRT, RRT-Connect, RRT*) share one extend step (§8.9):

Step What happens Result
1 Nearest q_near = tree.nearest(q_rand) a kd-tree lookup
2 Steer q_new = steer(q_near, q_rand, η) a bounded step, or a feasible primitive
3 Validate checker.motion_valid(q_near, q_new) at resolution ε yes or no
4a Valid insert q_new, parent q_near, cost = cost(q_near) + dist(q_near, q_new) Advanced(q_new)
4b Invalid discard q_new; tree unchanged Trapped

A 3-step trace: sample a random pose, find the closest tree node, step toward the sample. If the short motion is clear the tree gains a node; if not, nothing changes. RRT-Connect grows two such trees and joins them (§8.7). Every planner declares its guarantee (resolution complete for A* and Hybrid A*, probabilistically complete for RRT and PRM, asymptotically optimal for RRT* and Informed RRT*), and stronger promises cost more time (P2). The distance used by the optimising planners must be a true metric, tested on random triples (I9, P7, §8.2).

Collision checking is the cost centre (§8.6, P1, MM2)

A check runs in two stages. The broad phase uses a tree of bounding boxes (a BVH) to throw away pairs that obviously cannot touch. The narrow phase settles the remaining convex pairs with GJK (are they touching, how far apart) and EPA (how deep, which way) (§8.6). To check a motion rather than one pose, the checker splits the edge into steps of size ε (default 0.01 m for a mobile robot, 0.01 rad for a joint) and tests each, optionally by testing the midpoint and recursing so a failing edge is rejected early (§8.6, §4).

Because checks are the bottleneck, edges are validated lazily: only when an edge enters a candidate solution (P1). The blueprint's example is PRM, a reusable map of random poses joined by edges. Built eagerly, the capacity model prices it at 5000 nodes × 15 neighbours × 10 µs = 750 ms of edge checks; the lazy variant defers them to query time (Capacity Model item 6, Phase 5). The 10 µs is the budget per full-robot check at 1e5 checks/s on one core (Capacity Model item 1).

RRT*: a tree that rewires itself toward the best path (Phase 7, I4, MM4)

Plain RRT is only probabilistically complete, so its path may be far from optimal (P2). RRT* improves it as samples accumulate. After adding q_new, it (1) finds the nearby nodes within radius r_n = γ·(log n / n)^(1/d), where n is the node count and d the C-space dimension; (2) picks as parent the near node minimising cost(parent) + dist(parent, q_new) among collision-free connections; (3) rewires each near node through q_new if that lowers its cost (Phase 7).

The blueprint is not consistent about how that near set is chosen. Phase 7 allows the radius rule "or k-nearest, PRM*-style" (Phase 7), and PRM*-style means k grows with log(n) (Phase 5). MM4's heading says asymptotic optimality requires a shrinking radius, and its body says a fixed k-nearest set misses the optimality conditions (MM4). Both are stated here, unresolved. Rewiring accepts only strict improvements, so the best cost never rises: the planner is anytime, and interrupting it returns the best answer so far (I4, §7.4).

Informed RRT* adds one trick: once a first solution of cost c_best exists, sample only inside an ellipsoid (the blueprint's prolate hyperspheroid) whose focal points are start and goal, with long diameter c_best and short diameter √(c_best² − c_min²) (Phase 7). As c_best approaches c_min the short diameter goes to zero; when they are equal the ellipsoid collapses to the straight line, a degenerate case listed as a fixture. It shrinks as the solution improves, so fewer collision checks are wasted (Phase 7).

Steering for a vehicle that cannot turn on the spot: Dubins paths (§8.4, MM9, I3)

A car-like robot has a maximum curvature κ_max. Dubins paths give the shortest forward-only route between two poses: a sequence of left arc, straight and right arc, arc radius R = 1/κ_max, in six patterns (LSL, RSR, LSR, RSL, RLR, LRL). The steering function moves the goal into the start's frame, computes each pattern's length in closed form, and returns the shortest feasible one (§8.4). Reeds-Shepp extends this to vehicles that can reverse, with 48 patterns in the blueprint's count (§8.4).

The blueprint's worked example starts at (0, 0, 0) facing +x, with the goal at (4, 0, π) facing -x, R = 1. It evaluates all six patterns and returns the shortest, of length arc₁·R + straight + arc₂·R, about (π/2)·1 + 2 + (π/2)·1 ≈ 5.14 m, marked illustrative; the conformance fixtures pin exact lengths to 1e-6 (§8.4, Phase 8). Building steering this way (MM9) means every emitted primitive satisfies κ ≤ κ_max by construction. Hybrid A* searches continuous poses and tries a Dubins/Reeds-Shepp shot to the goal; at one try per 10 expansions and ~1 µs each, 1000 tries cost ~1 ms against ~10,000 expansions in a 500 ms budget (Capacity Model item 8).

Distance fields and smoothing (§8.5, Phase 3, Phase 9, MM5)

To clean up a raw path, the blueprint builds an ESDF, a grid storing for every cell the signed distance to the nearest obstacle (positive outside, negative inside), from the occupancy grid in two exact passes (the Felzenszwalb-Huttenlocher distance transform), with the gradient from central differences (§8.5, Phase 3). The sign matters: an unsigned field has zero gradient inside an obstacle, so a gradient step cannot push the path back out (MM5).

Shortcutting picks two waypoints, tries a direct connection, and replaces the stretch between them if the motion is valid. CHOMP-style smoothing treats the path as a list of waypoints ξ and repeats ξ ← ξ − (1/η)·A⁻¹·∇U. The objective U is smoothness (squared accelerations, through a finite-difference matrix A) plus an ESDF-based obstacle cost whose gradient pushes away from obstacles. The endpoints stay fixed, and any step that introduces a collision is rejected (Phase 9, P6, I1). Cost: for a 1000×1000 map in 2-D, the capacity model puts the ESDF build at 2 axes × 1e6 cells × ~5 ns = 10 ms, well under Phase 3's 100 ms target. In 3-D the same arithmetic gives 3 axes × 1e9 × 5 ns = 15 s, which is why the 3-D field is tiled (Capacity Model items 4 and 7, ADR-10).

The real-time loop and incremental replanning (Phase 11, MM7, MM10, I7, I12)

mp-local runs the Dynamic Window Approach every tick (Phase 11). In four steps:

  1. Compute the dynamic window, the velocities (v, ω) reachable from the current ones given the acceleration limits.
  2. Keep only admissible candidates, those from which the robot can still stop before the nearest obstacle (MM7).
  3. Roll each candidate forward a short horizon and score it on heading to goal, clearance from the ESDF or costmap, and speed.
  4. Emit the best-scoring admissible command.

The tick has a hard deadline of 20 ms, bounded sample counts and no heap allocation in steady state. If it would overrun, it returns the last safe command, and it raises a replan request if the trajectory is blocked or stale (I7, I12, P9). The capacity model's example: 100 candidates × 5 simulation steps × 1 ESDF query = 500 queries per tick, at 200 ns each = 100 µs of scoring, leaving about 19.9 ms of the budget (Capacity Model item 5).

Replanning must not stall this loop, so it runs on a worker thread (Phase 11). D* Lite keeps two values per grid vertex, g and rhs, plus a key modifier k_m for a moving start; on an edge-cost change it repairs only the affected vertices, so its work scales with the change, not the map (Phase 4, MM10, Scalability Analysis). Replans are rate-limited with a cooldown (Threat Model).

The trade-offs — where engineers disagree

Language: Rust (ADR-1)

Chosen: Rust 2021, MSRV 1.78, for determinism, no GC pauses on the 20 ms loop, and memory safety on untrusted geometry (§1.10, §9). Rejected: C++ (undefined behaviour on untrusted geometry), Python (too slow for ≥ 1e5 checks/s), Julia (immature embedding, GC) (§1.10). When the rejected choice is right: Python or Julia, for offline research scripts where determinism and single-core throughput are secondary and fast prototyping matters more than deployment latency (§9).

Random numbers: a seeded ChaCha8 per request (ADR-6)

Chosen: rand_chacha, seeded per request, so results are reproducible across versions and platforms (§9, I5). Rejected: thread_rng, StdRng. When the rejected choice is right: thread_rng for security-sensitive key generation, and StdRng when determinism within a single run, not cross-platform replay, is all you need (§9).

Collision library: write our own (ADR-7)

Chosen: own mp-collision (FCL-style GJK/EPA/BVH): no_std-friendly, auditable, no C++ FFI on the hot path (§9). Rejected: binding FCL or libccd. When the rejected choice is right: when the project already carries C++ FFI for other reasons and the geometry (mesh versus mesh, compound shapes) exceeds what a hand-rolled GJK covers in one phase (§9).

Distance field: an exact transform (ADR-10)

Chosen: exact Felzenszwalb-Huttenlocher distance transform, which is O(n) per dimension, exact and deterministic (§9). Rejected: brute force, fast marching. When the rejected choice is right: fast marching when you need wavefront propagation order and approximate distance is acceptable; brute force on tiny grids in unit tests (§9), as in Phase 3.

Concurrency: threads and channels, no async runtime (ADR-11)

Chosen: std threads plus crossbeam channels, because planning is CPU-bound and the real-time loop should avoid executors (§9). Rejected: tokio. When the rejected choice is right: when the planner must serve many simultaneous networked requests (HTTP or gRPC) and I/O latency dominates CPU planning cost (§9).

Roads not taken (Alternative Architectures, Deferred Features Register)

Optimisation-first planning (Alt-A, as in Drake): solve for the whole trajectory at once with direct collocation or CHOMP as the primary planner. It wins in low dimension (6 DOF or fewer) when a feasible first guess is always available and certified, smooth, dynamically optimal output matters, or when contact or torque limits belong in the objective. It is rejected because it needs a feasible start, can stall near it in narrow passages, and an SQP pass costs O(N³) in waypoints; CHOMP stays only as a post-processor (Phase 9).

Lattice-first search (Alt-B, as in SBPL): precompute motion primitives and run weighted anytime search over them. It wins when the robot's action set is finite and enumerable and hard suboptimality bounds are needed on interruption. It is rejected because an arm or a free-flying drone has no finite primitive set. Hybrid A* keeps the lattice idea with continuous states (Phase 8).

Purely reactive potential fields or DWA only (Alt-C): no global planner at all. It wins in open, convex spaces where a single tick must bound the replan latency and path quality does not matter. It is rejected because potential fields trap the robot in U-shaped obstacles and corridors, and the narrow_passage_2d and maze_2d scenarios require a global plan (§4, §3.1).

Deferred features (§1.8, Deferred Features Register): torque-level dynamics, GPU collision checking, learned samplers, multi-robot coordination, advanced optimisers and belief-space planning. Each has an "un-defer when" trigger; GPU checking returns if CPU throughput falls below the §4 target of 1e5 checks/s on a required scenario.

What must never be false

  • I1: every edge of a returned path, discretized at ε, is collision-free. Noticed by re-validation and a property test on every solution; counter path_validation_failures must stay 0 (§7.1).
  • I2: the path starts at the start and ends at the goal, within goal_tol. Noticed by an assertion in the PlanResult constructor; gauge goal_distance_residual (§7.2).
  • I3: curvature, speed and acceleration limits hold on every edge. Noticed by a post-hoc constraint check and property tests on Dubins/RS output; counter constraint_violations{type} (§7.3).
  • I4: the best solution cost never increases across iterations. Noticed by a per-iteration assertion and the anytime-curve fixture; series best_cost (§7.4).
  • I5: identical inputs and seed give identical result bytes. Noticed by the determinism harness that runs each scenario twice; counter determinism_mismatch must be 0 (§7.5).
  • I6: an A* heuristic never overestimates, unless weighted A* with a declared bound. Noticed by a property test against Dijkstra ground truth; gauge heuristic_inflation (§7.6).
  • I7: every local-loop tick finishes within its budget (≤ 20 ms). Noticed by a per-tick histogram local_tick_us and counter local_deadline_overruns (§7.7).
  • I8: no invalid edge ends up in a returned path, including lazily validated ones. Noticed by an invariant sweep in tests; counter lazy_edge_invalidations (§7.8).
  • I9: the distance used by RRT* and PRM obeys the triangle inequality. Noticed by a property test on random triples; counter metric_triangle_violations must be 0 (§7.9).
  • I10: exceeding any resource cap returns PlanError::ResourceExhausted, never an out-of-memory abort. Noticed by fuzzing parsers and planners; counter resource_exhausted_total{what} and gauges tree_nodes, esdf_bytes (§7.10).
  • I11: start and goal are bounds-checked and collision-checked before any search starts. Noticed by integration tests with bad endpoints; counter boundary_validation_rejections{kind} (§7.11).
  • I12: after warm-up, a local-loop tick allocates nothing on the heap. Noticed by an allocator counter in tests; counter local_loop_allocations must be 0 (§7.12).

What breaks in production

The Failure Modes & Recovery table names its rows but does not number them. The offline planner fails closed (NoPath or an error, never an invalid path); the real-time loop fails safe (stop or brake, never an unsafe command) (Failure Modes & Recovery, I1, I7).

  • Narrow-passage failure. Symptom: repeated NoPath on a map known to be feasible. Cause: uniform sampling rarely lands inside a thin gap. Detection: per-scenario success rate. Recovery: fall back to Gaussian or bridge sampling, tune the sampler, raise n (Failure Modes & Recovery, §8.3).
  • Local-minimum trap in DWA. Symptom: the robot sits stuck with no progress. Cause: greedy local scoring walks into a U-shaped obstacle. Detection: a progress-over-window monitor. Recovery: trigger a global replan; an operator retunes weights or adds an intermediate goal (Failure Modes & Recovery, Phase 11).
  • Replan thrash. Symptom: oscillation and jitter between two plans. Cause: no hysteresis in a noisy environment. Detection: a replan-rate spike. Recovery: a cooldown and hysteresis kick in (Failure Modes & Recovery, Phase 11).
  • Numerical degeneracy. Symptom: GJK that never terminates, or NaN costs. Cause: degenerate geometry or bad floats. Detection: iteration-cap hits and NaN guards. Recovery: abort the query and treat it as a collision (Failure Modes & Recovery, P13).
  • Loop deadline overrun. Symptom: the controller starves and the robot lurches. Cause: an allocation or over-budget scoring in the tick. Detection: the tick histogram and overrun counter. Recovery: emit a safe braking command; an operator cuts candidates and profiles the tick (Failure Modes & Recovery, I7).
  • Determinism break. Symptom: replays diverge. Cause: thread-local RNG, map iteration order or a float-mode change. Detection: the determinism harness. Recovery: none at runtime, since it blocks CI; the source is found by bisecting the RNG-draw log (Failure Modes & Recovery, I5, MM8).

Threats worth knowing. Maps, robot models and plan requests are untrusted; Rust removes memory corruption, leaving resource exhaustion, logic denial of service and supply chain (Threat Model):

  • Resource exhaustion from a huge C-space. High DOF plus huge bounds can blow up the tree or ESDF; hard caps on nodes, expansions and ESDF memory return ResourceExhausted (I10, P10).
  • Replanning denial of service. Rapid environment changes can force constant replans; a rate-limit with cooldown keeps the last plan (Threat Model, Phase 11).
  • NaN or infinity poisoning of distance fields. A crafted ESDF cache file can make CHOMP and DWA score NaN and pick random commands; every cell is validated on load and the field is rebuilt from the occupancy grid on failure (Threat Model, P13).
  • Oversized collision mesh. A model with millions of triangles can OOM the BVH build; a triangle cap at parse time returns ResourceExhausted before the build (Threat Model, ADR-7).

How it compares

  • OMPL chose a deep planner abstraction with no built-in robot or environment model, the standard substrate for algorithm research. That fits swapping ten planner variants in a paper benchmark; this design instead fixes a seeded, byte-reproducible pipeline (Comparative Architecture Table, ADR-6).
  • MoveIt 2 chose tight integration with the ROS 2 robot-description ecosystem (URDF, SRDF, FCL plugins). That fits production 6–7 DOF arms already described in URDF (Comparative Architecture Table).
  • Nav2 chose layered costmaps and a behaviour-tree action architecture, with a controller at about 20 Hz and no hard real-time budget. That fits 2-D mobile robots whose sensors already publish ROS 2 topics (Comparative Architecture Table).
  • Drake chose optimisation-first trajectory synthesis (direct collocation, hydroelastic contact). That fits applications needing certified constraints, full rigid-body dynamics or manipulation with contact (Comparative Architecture Table). This design defers torque-level dynamics (§1.8).
  • SBPL chose lattice-first anytime search (ARA*, AD*) over precomputed motion primitives. That fits a robot with a finite, enumerable action set and hard suboptimality bounds (Comparative Architecture Table).

Questions to test yourself

  1. A DWA tick runs at 22 ms on one test scenario. List the five most likely causes in order of probability, the telemetry signals that distinguish them, and the fix for each. — Hint: I7 in §7.7 and Phase 11's failure analysis list the signals; Capacity Model item 5 shows where the budget goes.
  2. You must serve a 7-DOF manipulator and a non-holonomic car with a single Planner implementation. What trait boundaries must be respected, and what breaks if you pass a Dubins SteeringFn to a joint-space StateSpace? — Hint: P5 and §3.2 (mp-space), then §8.4 for what a steering function assumes about the space.
  3. RRT* is used in a 6 m × 6 m room with a single narrow doorway (0.3 m wide). After 1e4 samples the cost gap to optimal is 30%, not 5%. Cite the two most likely causes and the exact §4 acceptance criterion that is failing. — Hint: §4's RRT row, MM3 and MM4, and §8.3's narrow-passage samplers.*
  4. An adversarial map file causes the planner to allocate 800 MB and OOM-kill the process. Enumerate every resource-cap path that should have triggered a ResourceExhausted before the OOM, citing the relevant threat-model row and the ADR that enforces the cap. — Hint: I10 in §7.10, P10, and the Threat Model rows on malformed maps and resource exhaustion; the caps themselves come from P10.
  5. A PRM built in a static environment is reused after a wall has been added. The query returns a path that passes through the new wall. Enumerate the three defense layers that should have caught this and identify which invariant each enforces. — Hint: I1 and I8 in §7.1 and §7.8, plus the stale-map row in Failure Modes & Recovery.

If you only remember three things

Planning is a search through configuration space in which collision checking is the dominant cost, so nearly every design choice is about making checks fewer, lazier or cheaper (MM1, MM2, P1). Each planner states what it guarantees; every returned path is re-validated or replaced by NoPath or an error, and the same seed reproduces it byte for byte (P2, P6, I1, I5). Slow planning stays offline, while a small bounded loop that fails safe handles change in real time (I7, P9, MM7).

Words used here

  • Configuration space (C-space): the space of all robot poses; planning is a search through it (§8.1).
  • Probabilistically complete: the chance of finding a solution tends to 1 as samples grow (Glossary, P2).
  • Asymptotically optimal: the solution cost tends to the best possible as samples grow (Glossary, P2).
  • Anytime planner: one that can return a valid, improving solution whenever it is interrupted (Glossary, P3).
  • Broad phase / narrow phase: cheap culling of pairs that cannot touch, then exact tests on the rest (§8.6).
  • GJK / EPA: algorithms that give distance (GJK) and penetration depth (EPA) between convex shapes (§8.6).
  • ESDF: a grid of signed distances to the nearest obstacle, with gradient (§8.5).
  • Dubins path: the shortest forward-only route for a vehicle with a minimum turning radius (§8.4).
