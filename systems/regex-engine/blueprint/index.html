61 — Regex Engine

Project Number: 61

Project Name: Regex Engine

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

1.1 Engineering Definition

  • Build a from-scratch regular-expression engine in the RE2 / Rust regex-crate tradition: pattern string → recursive-descent parser → AST → desugared, Unicode-resolved HIR → Thompson-construction NFA bytecode → one of three interchangeable execution engines (PikeVM, lazy DFA, budget-bounded backtracking VM) → match range / capture groups.
  • The headline guarantee: every pattern that does not require backreferences or unsupported lookaround runs in O(n·m) time (n = input bytes, m = compiled bytecode size) on every input, including adversarial ones — the property that defeats ReDoS (P1, I1; Cox 2007).
  • Two match-semantics modes — leftmost-first (PCRE-like, default) and leftmost-longest (POSIX, opt-in, P6) — and two alphabets — Unicode &str and raw &[u8] (P5) — share one HIR and one bytecode format; the engine choice is resolved once, at Regex::new compile time, never re-decided mid-match (P3, §19).

1.2 System Boundaries

  • In scope: parser + AST (§13); HIR + Unicode character classes (§14); Thompson NFA construction (§15); PikeVM simulation with capture groups and both leftmost semantics (§16–§17); lazy DFA with a bounded cache plus literal prefilter (§18); engine selection, one-pass DFA, and RegexSet (§19); the four lookaround forms (§20); a budget-bounded backtracking VM for backreferences and variable-width lookbehind (§21); streaming match and build-time pattern compilation (§22); observability and runbooks (§23); fuzzing and the ReDoS regression suite (§24).
  • Out of scope / non-goals: a general context-free or PEG parser generator — regular languages only, no recursion, no arbitrary grammars (§2.7); a Unicode collation/locale library (RL2+ deferred, §38); a network service or daemon — the engine is an embeddable library, never a server; a JIT compiler to native code (deferred, §38); multi-dialect regex-syntax federation (PCRE vs POSIX vs ECMAScript) beyond the documented rust-regex-compatible surface (ADR-24).
  • Explicit non-provision: the engine never silently downgrades a linear-time guarantee to backtracking (P9); it never lets a caller guess which engine ran a match by inspecting anything but Regex::engine() (P3).

1.3 Deployment Model

  • An embeddable Rust library shipped as a small crate family (regex, regex-syntax, regex-automata, regex-macro, regex-cli); #![forbid(unsafe_code)] at the workspace root with documented, individually-audited exceptions (ADR-20). No daemon, no network listener; the CLI examples (grep, lex, waf, streaming) demonstrate embedding patterns — they are not the product.

1.4 Target Users

  • Engineers embedding pattern matching on an adversarial-input hot path: log ingestion, HTTP request routing, WAF rule evaluation, schema/field validators, lexer generators, search-result highlighting. Operators who must reason about the worst-case latency of a pattern they did not write, against an input they do not control.

1.5 Phase 0 Deliverable — Crates/Modules

  1. regex — the public façade: Regex, RegexSet, RegexBuilder, Captures, Match, Error types.
  2. regex-syntax — the parser (ast), the HIR (hir), and the generated Unicode tables.
  3. regex-automata — the Thompson NFA, the three execution engines (pike, dfa, backtrack), the prefilter, the meta engine selector, and the input cursor layer.
  4. regex-macro — the regex! build-time procedural macro.
  5. regex-cli — the mini-regex debug CLI (debug-ast / debug-hir / debug-nfa dumpers).

1.6 What Later Phases Unlock

  • §12 skeleton + "Hello, regex" → §13 parser/AST → §14 HIR/Unicode → §15 Thompson NFA → §16 PikeVM → §17 captures + leftmost semantics → §18 lazy DFA + prefilter → §19 engine selection/one-pass/RegexSet → §20 lookaround → §21 backtracking VM → §22 streaming + regex! macro → §23 observability → §24 fuzzing + ReDoS regression (the Sealed gate).

1.7 Deferred Features (Typed Gate)

  • PhaseDeferred("Deferred Features Register"): tagged-DFA capture extraction (§38); SIMD-accelerated Boyer-Moore (§38); Hyperscan-quality FDR multi-pattern prefilter (§38); reverse-NFA variable-width lookbehind (§38); full UTS#18 RL2 conformance (§38); a regex_set! build-time macro (§38); JIT compilation of hot patterns (§38); a WebAssembly target (§38); a #![no_std] core (§38); OSS-Fuzz onboarding (§38); a bytecode pre-validator for untrusted precompiled programs (§38); differential testing vs PCRE2/rust-regex as a third oracle (§38). 1.8 Estimated Timeline

  • Phase 0: 1–2 weeks (repository skeleton, governance, the literal-only "Hello, regex" smoke test).
  • Full §12–§24 (13 phases): ~10 weeks part-time (~2.5 months) to the Sealed gate (§24). Long poles: §17 (capture-slot / leftmost-semantics correctness), §18 (lazy-DFA cache correctness), §21 (backtracking-VM budget discipline), §24 (the 30-day fuzz canary).

1.9 Recommended Language & Rationale

  • Rust. The linear-time guarantee benefits directly from the borrow checker: no aliasing bugs in the DFA cache, no use-after-free in the PikeVM thread list, no data races across Send + Sync concurrent Regex use. rust-regex is the direct engineering reference to study against. proc_macro2 gives the regex! build-time compiler span-precise diagnostics for free.
  • Rejected: C++ — RE2's own language; nothing it buys is not also available in Rust, and Rust removes an entire bug class (aliased NFA/DFA state) RE2's own postmortems document. Go — regexp's language; weaker generics and manual escape-analysis tuning make the byte-class / cache hot path harder to control. OCaml/Haskell — smaller embedding surface for host applications that need a C-ABI-adjacent library.

1.10 Prerequisites

  • Automata theory: NFA/DFA, epsilon closure, subset construction (Aho, Sethi, Ullman — the Dragon Book, ch. 3). Unicode fundamentals: UTF-8 encoding, UTS#18 property levels. Recursive-descent parsing. Big-O reasoning under an adversarial-input threat model, not just an average-case one.

1.11 Definition of "Phase-0 Done"

  • The done bar is §12–§17: parser, HIR, Thompson NFA, PikeVM with captures, leftmost-first semantics, Unicode classes at UTS#18 RL1.1/RL1.2, matching hello in "world hello world" and a capturing-group fixture, all green under make conformance. §18 onward (lazy DFA, engine selection, lookaround, backtracking VM, streaming, observability, fuzzing) is Phase-1+ work, each gated behind a typed PhaseDeferred(...) where stubbed. This blueprint is the specification; no code is written in this phase.

2. Why Build This

2.1 Unique Knowledge Taught

  • Thompson construction as the bridge from grammar to automaton — every regex operator (concatenation, alternation, Kleene star, repetition) lowers to a fixed epsilon-NFA fragment shape (Thompson 1968; §15).
  • NFA simulation as frontier-tracking, not backtracking — the PikeVM's "set of live states, deduplicated" trick is the idea that turns exponential search into linear scanning (Cox 2007; §16).
  • Lazy subset construction — the DFA is the same automaton eager subset construction would build, computed one state at a time, on demand, under a memory cap (Cox 2010; §18).
  • Capture-group bookkeeping without abandoning linear time — thread-local slot vectors with copy-on-write semantics (§17), and the Laurikari tagged-transition alternative deferred to §38.
  • ReDoS as an algorithmic property, not a bug class — why a step budget is the only sound defense once backtracking is unavoidable (§21, §25).

2.2 Why It Matters

  • On 2 July 2019, Cloudflare's edge network went down globally for 27 minutes because a single WAF regular expression exhibited catastrophic backtracking against a crafted request body, saturating every CPU core simultaneously (Cloudflare, public incident report, "Details of the Cloudflare outage on July 2, 2019"). The teams already on a linear-time engine — Google's RE2, Rust's regex, Go's regexp — were structurally immune to that class of incident; the teams still on backtracking engines were not. This project builds the kind of engine that makes that incident structurally impossible on the linear-time path (§25).

2.3 Engineering Muscles

  • Automaton construction and bytecode design; virtual-machine design (thread scheduling, epsilon closure, dedup); cache design under a hard memory bound (the lazy DFA); string-search algorithm selection (Boyer-Moore vs Aho-Corasick); Unicode-to-byte compilation; differential and fuzz testing against a reference implementation.

2.4 Production Concepts Exercised

  • Guaranteed worst-case latency under adversarial input; engine selection as a compile-time contract; explicit, observable fallback (never silent); budget-bounded computation as a security primitive; streaming/incremental matching; build-time compilation for zero-cost hot paths.

2.5 Cross-Links

  • Lexer-Tokenizer — a lexer generator commonly compiles its token rules through exactly this NFA/DFA pipeline; this project is the general-purpose version of that narrower one.
  • DSL-Language — regex syntax is itself a small domain-specific pattern language; the parser/AST/HIR split here is the same shape a DSL front end uses.
  • Bytecode Verifier — both projects compile to a small, closed bytecode format with a safety contract (here: #![forbid(unsafe_code)] plus a step budget) executed by a VM.
  • Graph-Database — contrast: a DFA's states-as-subsets-of-NFA-states is a compile-time graph-construction problem, not persisted graph storage; no data is owned or indexed here.

2.6 Calibration Value

  • A reader leaves able to open RE2, PCRE2, or the Rust regex crate's source and explain, line by line, why the lazy DFA clears its cache instead of evicting a single state, why regex_syntax::hir exists as a separate IR from the AST, and why a backreference forces a different code path than everything else in the file.

2.7 The Defining Non-Goal — A Regex Engine Is Not a General Parser

  • The most common conflation: "pattern matching" sounds like "parsing," but a regular-expression engine recognizes exactly the regular languages — no recursion, no balanced constructs ((a(b)c) nesting to arbitrary depth is not expressible), no context-free grammar.
  • C1: the Thompson NFA has no stack; a PEG/CFG parser's recursive-descent or pushdown-automaton core is fundamentally more expressive and fundamentally not linear-time-guaranteed against adversarial grammars the way a DFA is.
  • C2: backreferences (\1) already push this engine outside the regular languages (they make the language class context-sensitive in the worst case) — exactly why they are gated to a separate, budget-bounded VM (ADR-03) rather than "just another feature" of the linear-time core.
  • C3: contrast with DSL-Language — a DSL's grammar is typically context-free and needs a real parser generator; this project is the automaton substrate a DSL's lexer might be built on, never the DSL's grammar layer itself.
  • This is the sharpest boundary in the document: everything in §12–§21 exists to match regular languages (plus the explicitly-gated backreference/lookbehind extensions) as fast and as safely as possible — never to grow into a general parser.

2.8 What Mastery Looks Like

  • Derive the Thompson-construction fragment for every regex operator (concatenation, alternation, */+/?, counted repetition, capture) and explain why Split ordering alone encodes greediness — built in Phase 3 (§15).
  • Explain, from the bytecode up, why PikeVM simulation is O(n·m) and never exponential — the epsilon-closure deduplication trick — built in Phase 4 (§16).
  • Trace a capture-group extraction through a thread's copy-on-write slot vector across a Split, and state exactly when the copy fires — built in Phase 5 (§17).
  • Construct a lazy DFA state on demand, explain the cache-clear-on-full policy versus per-state LRU, and justify RE2's choice — built in Phase 6 (§18).
  • Select the correct execution engine for a given pattern from its HIR alone (one-pass, lazy-DFA-eligible, PikeVM-only, or backtracking-VM-only) — built in Phase 7 (§19).
  • State the exact structural reason backreferences cannot run on the NFA path, and bound the backtracking VM's worst case with a step-budget argument — built in Phase 9 (§21).
  • Reconstruct the Cloudflare 2019 ReDoS incident mechanically from the pattern class it belongs to, and name the two independent defenses this engine ships against it — built in Phase 9 (§21) and the Threat Model (§25).

3.2 Box Narratives

  • regex-syntax parser → AST. Hand-written recursive-descent parser (P2, ADR-06) over the pattern grammar (§8.1); every node carries a byte-range Span for diagnostics; on any construct it cannot express it fails fast with a typed ParseErrorKind, never a partial parse (P15).
  • HIR desugar + Unicode resolve → Thompson NFA. The AST is validated, desugared (\d/\w expand, (?i) case-folds), Unicode properties resolve against the generated tables (UTS#18 RL1.2), classes normalize, and the whole tree lowers to a flat Instruction bytecode via Thompson's construction (P2, §14–§15).
  • Input layer. Cursor owns every codepoint-boundary decision (P12); Stream wraps a BufRead for incremental matching (§22); no engine below this box ever indexes a UTF-8 boundary itself.
  • Analysis passes. Four independent HIR walks decide, once, at compile time: is the pattern anchored, is it one-pass, does it need a backreference, does it need lookaround the NFA cannot express (§19–§20) — every downstream decision reads these flags, never re-derives them.
  • Literal extraction. A HIR pass identifies required prefix/suffix/inner literals and builds a LiteralStrategy (Boyer-Moore for one literal, Aho-Corasick for several) that skips positions the NFA/DFA cannot possibly match (P10, §18.5).
  • Meta selector. The single place engine choice is made, once, at Regex::new time (P3); it never re-decides mid-match except the one documented, observable lazy-DFA-cache-exhaustion fallback (P9).
  • PikeVM. The correctness ground truth (§16): NFA simulation with epsilon-closure deduplication, thread-local capture slots, leftmost-first/longest bookkeeping (§17).
  • LazyDfa. The throughput engine (§18): states are subsets of NFA states, built on demand, cached under dfa_size_limit, falling back to the PikeVM when the cache clears too often.
  • BacktrackVM. The engine of last resort (§21): a textbook backtracker with one addition — every step decrements an explicit budget; exhaustion returns Err(Budget), never a silent hang.
  • Public API. Regex/RegexSet/RegexBuilder/Captures/Match — the only surface a host ever touches; the user never names which engine ran (P3).

3.3 Boundaries

  • Trust: the pattern is untrusted when compiled from user input (bounded by size_limit); the haystack is always untrusted (the entire linear-time guarantee exists for this boundary); a build-time regex! pattern is trusted (checked at compile time, never attacker-controlled).
  • Concurrency: a compiled Regex is Send + Sync; concurrent is_match/find/captures calls from multiple threads are valid and allocate no shared mutable state (per-match scratch is arena-local, P13).
  • Persistence: none at the engine's own layer — Unicode tables are checked-in static data (ADR-14); a compiled Regex holds no per-match heap between calls.
  • Protocol: the only "wire format" is the NFA bytecode snapshot format used for conformance fixtures (§15.6) and the regex! macro's compile-time-emitted const/static program.

3.4 Data-Flow Walk — One Match, End to End

  1. Regex::new(r"(?i)foo\d+") → the parser produces the AST (§13) → HIR desugar case-folds foo and resolves \d to a Unicode digit class (§14).
  2. Thompson construction emits bytecode: Byte/Class instructions for the literal+digit run, a Split for the + repetition, a Match terminus (§15).
  3. Analysis passes mark the pattern anchored=false, one-pass=false (the + creates ambiguity at the boundary), backref=false, lookaround=false.
  4. Literal extraction finds the required prefix "foo" (case-insensitive) → a Boyer-Moore LiteralStrategy (§18.5).
  5. The meta selector picks PikeVm + LazyDfa(opportunistic) (§19.1) — the default disposition.
  6. find("xxx FOO123 yyy"): the BM prefilter skips to the case-insensitive "FOO" match at byte 4; the lazy DFA (or PikeVM) confirms and extends the match to 123; the match range 4..10 returns.
  7. If the DFA's cache had filled mid-match, a regex.dfa.fallback trace event fires and the PikeVM finishes the match with an identical answer (P9, cross-engine determinism, §7).

3.5 The Matching Algorithm — Expanded (the Heart)

  • PikeVM::search: seed clist = epsilon_closure({start}); for each input byte, build nlist by advancing every thread in clist whose next instruction accepts the byte, epsilon-closing each successor and deduplicating by NFA StateId — two threads reaching the same state collapse into one (this single rule keeps the simulation O(n·m) instead of exponential; Cox 2007, §16.2, I2).
  • A thread reaching Match records its capture-slot vector; under leftmost-first the first such thread wins and the rest of clist is discarded; under leftmost-longest the simulation continues, keeping the longest match seen (§17.3–§17.4, I5).
  • LazyDfa::search is the same automaton computed lazily: a DFA state is a canonicalized NFA state-set; a transition on a byte is "advance every NFA state in the set, epsilon-close, canonicalize, cache-or-allocate" (§18.1, I6).
  • This mutual grounding — the DFA is provably the same automaton as the PikeVM's frontier, just precomputed and cached — is the cross-engine determinism invariant (I2) and the reason the conformance suite treats the PikeVM as ground truth (§24.4).

3.6 Concurrency & Determinism Sequence (Two Threads, One Compiled Regex)

Thread A: regex.find("input A")   Thread B: regex.find("input B")   (same Arc<Regex>)
  |                                  |
  Scratch::new() (own arena)         Scratch::new() (own arena)
  |                                  |
  PikeVm::search(&input_a, &mut A)   PikeVm::search(&input_b, &mut B)   (run concurrently)
  |                                  |
  Scratch dropped/reset at call end  Scratch dropped/reset at call end

Neither thread touches the other's Scratch; the compiled Regex's own fields (Nfa, ByteClasses, LiteralStrategy) are read-only after construction (P13, P14). This is why the determinism invariant (I10) can be verified with a 1,024-run loop on a single thread and still be trusted under real concurrency — there is no shared mutable state for concurrency to perturb.

4.1 Worked ReDoS Budget (Why the Step Cap, With Numbers)

  • Pattern (a+)+$ against haystack "aaaa…a!" (n characters, no trailing match) on a naive backtracker: each of the 2^n ways to partition the a-run across the outer/inner + is tried before failing — at n = 30, 2^30 ≈ 10^9 backtrack frames.
  • The budgeted VM (§21) counts one step per frame; at the default 1,000,000-step budget, the match aborts with Err(Budget) at roughly n ≈ 20 for this pattern shape — well before the frame count would stall a CPU core for seconds (the Cloudflare 2019 incident's actual mechanism, §2.2, §25).
  • Conclusion: the budget is not a performance tuning knob; it is the structural proof that this engine's worst case is O(budget), a constant, never O(2^n) (P8, I5).

4.2 Worked Lazy-DFA Cache Budget

  • A DFA state is a canonicalized NFA state-set; worst case there are 2^k reachable subsets for k live NFA states. At dfa_size_limit = 8 MB and roughly 64 bytes per cached state+transition row, the cache holds 8×10^6 / 64 ≈ 125,000 states before a clear fires.
  • A pattern whose live-state count k is small (most real patterns: k < 50) never approaches 2^k reachable subsets in practice — the ones that do are exactly the pathological wide-class-inside-counted-repetition patterns the size_limit bytecode cap (§15.3) already rejects at parse time.
  • Conclusion: the two caps (size_limit bounding NFA size, dfa_size_limit bounding DFA cache) are independent defenses against two different blow-up shapes — bytecode unrolling and subset explosion (§4, §18.2).

4.3 Worked Throughput Budget (BM Prefilter)

  • At the 1 GB/s target (§4) and a typical HTTP log line of ~200 bytes, the Boyer-Moore prefilter scans one line in 200 / 10^9 s ≈ 200 ns — three orders of magnitude below the ≤100 µs p99 latency target, confirming the prefilter is never the bottleneck on realistic inputs; the NFA/DFA confirmation step, run only at candidate positions the prefilter finds, dominates the remaining budget (§35 C4).

4.4 Worked Concurrency Budget (Why "Max Concurrency: Unbounded" Is a Real Claim, Not an Aspiration)

  • Because Regex is Send + Sync with zero shared mutable state (P13), the only per-thread cost of concurrent matching is one Scratch arena per in-flight match (§35 C5, ≈ 8 KB for a moderately complex pattern).
  • At C concurrent matches, total transient memory is C × 8 KB (§35 C12) with no lock, no atomic increment, and no contention anywhere on the match path — the "unbounded readers" claim in §4's table is not an approximation, it is a direct consequence of P13's arena-per-match design plus the absence of any shared cache write on the PikeVM/one-pass-DFA paths.
  • The one path that does share mutable state is the lazy DFA's cache (§18.1); it is designed to be either (a) private per compiled Regex instance (no cross-thread sharing, safest) or (b) shared behind a lock-free concurrent map when multiple threads run the same Regex concurrently — the locked-vs-lock-free tradeoff here is documented in docs/architecture/lazy-dfa.md and is the one place "unbounded concurrency" needs a specific data-structure justification rather than following automatically from P13.
  • Conclusion: the concurrency ceiling in practice is host memory (C × 8 KB per C5) and, only on the lazy-DFA path, contention on the shared cache structure — never a correctness limit, and never a limit this blueprint's own design imposes.

6. Design Principles

  1. Linear-time on every pattern that does not use backreferences (P1). The NFA path runs in O(n·m); the lazy DFA runs in O(n) plus bounded compile overhead. Violating this by letting a "convenience" pattern class quietly reach the backtracking VM reopens the exact ReDoS surface §25 exists to close.
  2. Two parsers do not exist (P2). Every engine consumes the same HIR from one parse. Violating this lets syntax bugs diverge silently across engines, breaking the cross-engine determinism invariant (I2).
  3. The engine you run is not the engine you wrote against (P3). The meta selector picks PikeVM, lazy DFA, or backtracking VM once, at compile time; violating this with a match-time branch makes engine choice unauditable and non-deterministic across builds.
  4. The lazy DFA has a bounded cache and an explicit eviction policy (P4). No global LRU, no silent eviction mid-match; the bound is dfa_size_limit, configurable. Violating this either unbounds memory or corrupts an in-flight match's state set.
  5. Unicode is the default; bytes is opt-in (P5). RegexBuilder::unicode(false) switches to 8-bit byte classes and rejects \p{...} at parse time. Violating the boundary (mixing modes at runtime) produces classes that mean different things on the same bytes.
  6. Leftmost-first is the default; leftmost-longest is opt-in (P6). Same engine, different bookkeeping rule (§17.3–§17.4), never a different algorithm. Violating this by forking the engine doubles the maintenance and correctness-testing surface.
  7. Backreferences are gated, never silently accepted onto the linear-time path (P7). A pattern using \1–\9 compiles successfully but is only matchable through the backtracking VM; requesting PikeVm explicitly on such a pattern is a construction error. Violating this is precisely how a backtracking bug becomes a linear-time-engine's problem.
  8. The backtracking VM is budget-bounded (P8). Every backtrack step consumes one unit of an explicit, finite budget (default 1,000,000; max 100,000,000; §4.1). Violating this removes the only defense the last-resort engine has against exponential blowup.
  9. No silent fallbacks (P9). A DFA-cache-full fallback to PikeVM is explicit and traced (regex.dfa.fallback); an engine mismatch against an explicit RegexBuilder::engine(...) request is a build error, not a silent substitution. Violating this hides a correctness-relevant decision from the operator.
  10. The literal prefilter is optional and observable (P10). Regex::literal_strategy() exposes exactly what the extractor decided. Violating observability turns a prefilter bug (skipping a real match) into an unreproducible, silent wrong answer.
  11. Compile-time patterns are first-class (P11). The regex! procedural macro performs the full parse→HIR→NFA→literal-extraction pipeline at build time with span-precise diagnostics. Violating this by treating build-time compilation as an afterthought loses the zero-parse-cost hot-path guarantee.
  12. Strings are owned by the input layer (P12). Only Cursor understands codepoint boundaries; every engine below it sees (byte_offset, byte_class) pairs. Violating this is the source of the single most common regex-engine memory bug: indexing a UTF-8 boundary from inside an engine.
  13. One arena per match (P13). The PikeVM thread list, the DFA's transient state set, and the capture-slot vector all come from a per-match arena reset at the start of each top-level call; the compiled Regex owns no per-match heap. Violating this reintroduces per-match allocator pressure the throughput targets (§4) assume away.
  14. Determinism is the default (P14). A given (pattern, input, RegexBuilder configuration) triple produces a deterministic result across builds, hosts, and engine selections (I2). Violating this breaks every differential and cross-engine conformance test simultaneously.
  15. No surprises in error reporting (P15). Parse errors carry a byte span, a category, and a one-line explanation naming the offending construct and the rule it violated; construction errors carry the same for semantic problems. Violating this turns a debuggable pattern-authoring mistake into a silent construction failure.

These fifteen principles are not independent suggestions — P1/P2/P3 together are the linear-time guarantee's foundation, P7/P8/P9 together are what makes the one deliberately-unbounded path (backreferences) safe to ship at all, and P12/P13 together are what makes the arena-per-match concurrency story in §4.4 true rather than aspirational. Every ADR in §9 traces back to at least one of these; every invariant in §7 is a runtime-checkable restatement of one.

8. Domain Model — Grammar, Automata & Matching Semantics

8.1 Pattern Grammar (EBNF, abridged from the rust-regex-compatible surface)

pattern     ::= alternation
alternation ::= concat ("|" concat)*
concat      ::= factor*
factor      ::= atom repetition?
repetition  ::= ("*" | "+" | "?" | "{" INT ("," INT?)? "}") "?"?
atom        ::= literal | escape | class | group | anchor | "."
escape      ::= "\" (perl_class | unicode_property | hex | oct | special)
class       ::= "[" "^"? class_item+ "]"
group       ::= "(" group_kind? alternation ")"
group_kind  ::= "?:" | "?P<" NAME ">" | "?<" NAME ">" | "?=" | "?!" | "?<=" | "?<!"
anchor      ::= "^" | "$" | "\b" | "\B" | "\A" | "\z"

Each construct is either accepted or rejected with a typed ParseErrorKind (§8.9); the parser never partially accepts.

8.2 HIR Desugaring Rules

AST Construct HIR Form Rule Applied
\d, \w, \s resolved Unicode/byte class UTS#18 RL1.2 property lookup (§14.1)
(?i)… case-folded literal/class chain UTS#18 RL1.5 simple fold (§14.1)

8.3 Thompson Construction Rules (State-Transition Table)

HIR Node Fragment (Entry → Exit)
Empty ε
Literal(b) Byte(b, exit)
Class(c) Class(c, exit)
Concat(a,b) a.exit = b.entry
Alternation(a,b) Split(a.entry, b.entry); both exits → shared exit

Greediness is purely Split branch order: next_a is preferred. Lazy quantifiers swap the order (§15.1).

8.4 NFA Instruction Set

Instruction Semantics
Byte{byte,next} consume exactly this byte
Class{class_id,next} consume any byte in the interned byte class
Split{next_a,next_b} epsilon transition, next_a preferred
Capture{slot,next} zero-width; write current offset into slot
Look{look,next} zero-width anchor/boundary assertion

8.5 Capture Slot Model

Group i's start/end occupy slots 2i/2i+1; slot 0/1 are the implicit whole-match group. Slot count is fixed at compile time (§15.4). A thread's SlotVec is copy-on-write (I9); the copy fires exactly when a Split produces two threads about to diverge in what they write (§17.1).

8.6 Leftmost-First vs Leftmost-Longest (Rule Table)

Semantics Rule Default?
Leftmost-first (PCRE) first thread to reach Match wins; greedy Split prefers its body yes
Leftmost-longest (POSIX) simulation continues after the first Match; longest wins; ties broken by earliest start opt-in (RegexBuilder::longest_match(true))

8.7 The Matching Algorithm (State-Machine View)

  • PikeVM: Ready → Stepping(clist,nlist) → {Matched(slots) | Exhausted}. Each byte transitions Stepping to itself with clist,nlist swapped; Matched short-circuits under leftmost-first, continues under leftmost-longest until Exhausted.
  • LazyDfa: Ready → Stepping(dfa_state) → {Matched | CacheFull→FallbackToPikeVM | Exhausted}. Every Stepping transition either hits a cached transition or computes-and-caches one.
  • BacktrackVM: Ready → Stepping(frame_stack) → {Matched | BudgetExceeded | Exhausted}. Each Split pushes the loser frame; each step decrements the budget.

8.8 Worked Match Trace

Pattern: (a|ab)(c|bcd)(d*)   Input: "abcd"   Engine: PikeVM, leftmost-first

pos  clist (abbreviated)                  action
0    {S0}                                 epsilon-closure of start
0    {a-branch, ab-branch}                Split at group-1 entry
1    after 'a': {c-branch, bcd-branch@b}  consumed 'a'; two live threads
2    after 'b': {bcd-branch@c}            a-branch died (expects c/bcd); ab-branch alive
3    after 'c': {d*-branch}               bcd matched; group2 = "bcd"
4    after 'd': {d*-branch, Match}        d* may stop or continue; Match recorded
end  Match: group0="abcd" group1="ab" group2="bcd" group3="d"

This is the textbook "ambiguous alternation" case Thompson NFA simulation resolves without backtracking: both a and ab branches run simultaneously as separate threads (§16.1) until one dies naturally.

8.11 ReDoS Failure-Path Trace (the Incident-Class Example)

Pattern: (a+)+$        Input: 30 'a' characters, then a mismatch
A purely-backtracking engine (PCRE-style) tries every partition of the 'a'-run
across the outer/inner '+': step count grows combinatorially with n.
This engine's BacktrackVM: budget=1,000,000 steps; exceeded well under the ~2^30
total partitions -> Err(MatchError::Budget) returned in low milliseconds.
This engine's default disposition: the pattern has no backreference, so it never
reaches BacktrackVM at all -- it runs the linear-time NFA path in O(n) (I4, P7).

The trace exists to show why a purely-backtracking engine (the pre-2019 Cloudflare WAF's engine class) stalls on this pattern, and why this engine's default routing never sends a backreference-free pattern there (§2.2, §25).

8.12 Unicode Class → UTF-8 Byte Class (Worked Example)

\p{L} (all letters) resolves to a disjoint set of codepoint ranges; each range decomposes by UTF-8 leading-byte arity (1/2/3/4-byte sequences) into a fan of byte-range instructions Thompson construction consumes directly (Cox's "compiling Unicode classes to UTF-8 byte classes," §14.3) — e.g. the ASCII sub-range [A-Za-z] becomes one single-byte class; the Latin-1 supplement range becomes a two-byte-sequence fan with a fixed leading byte 0xC2–0xC3.

8.13 State Machines Summary

  • Compile lifecycle: Parsed → Desugared → Analyzed → EngineSelected → Compiled; any stage failure returns a typed error and the pipeline halts (never a partial Regex).
  • Match lifecycle (any engine): Ready → Stepping → {Matched | Exhausted | Err}; the three engines share this shape (§8.7) — only the per-step work differs.

8.14 Cross-Engine Determinism (the Domain Model's Closing Invariant)

For any (pattern, input) pair where more than one engine is eligible, PikeVM, LazyDfa, and BacktrackVM (run with a generous budget) must return the identical Option<Captures> (I2). This is the single fixture bucket (cross_engine, §24.4) every other domain-model guarantee in this section ultimately reduces to.

8.15 Worked RegexSet Composition Example

Patterns: ["foo", "bar", "foo.*baz"]     Haystack: "xx foobaz yy"

Thompson construction (shared NFA):
  pattern 0 "foo"        -> ... -> Match{pattern_id: 0}
  pattern 1 "bar"        -> ... -> Match{pattern_id: 1}
  pattern 2 "foo.*baz"   -> ... -> Match{pattern_id: 2}
  (all three share byte-class table + any common literal prefix analysis)

PikeVM simulation against "xx foobaz yy":
  pos 3: threads for pattern 0 and pattern 2 both become live (shared "foo" prefix)
  pos 6: pattern 0's thread reaches Match{0} -- record pattern_id 0 as matched
  pos 9: pattern 2's thread reaches Match{2} after ".*baz" -- record pattern_id 2
  pattern 1 ("bar") never has a live thread -- not in the result set

SetMatches: { 0, 2 }   (pattern 1 correctly absent, I15)

The shared-prefix threads for patterns 0 and 2 are the same PikeVM mechanism that resolves an ordinary ambiguous alternation (§8.8) — RegexSet is not a special algorithm, it is the existing simulation with per-thread pattern_id bookkeeping added at Match (§19.2).

8.16 Worked Streaming Match Trace

Pattern: "error: \d+"   Stream fed in three chunks (chunk boundary mid-literal)

feed(b"...err")     -> NeedMore   (carry buffer holds "err", no live Match thread yet)
feed(b"or: 42 ")     -> Match found at absolute range 10..19 ("error: 42")
                        (resumption token carried the partial "err" state across the boundary)
feed(b"more text")   -> NoMatch   (no further match in the remaining stream)
finish()             -> None      (no additional pending match at EOF)

The resumption token is exactly the lazy DFA's canonicalized state-set (§18.1) or the PikeVM's serialized thread list, carried across the feed() boundary — the match found in the second chunk is correct only because the engine's internal state survived the boundary, which is the entire point of StreamMatcher over re-slicing and re-scanning each chunk independently (§22.2).

9.1 Dependency Relationships (Portfolio Context)

  • Conceptual sibling of Lexer-Tokenizer — a lexer generator's DFA construction is a narrower instance of §15–§18's automaton pipeline.
  • Conceptual sibling of Bytecode Verifier — both projects compile to a closed bytecode executed by a budget/safety-checked VM.

  • Not consumed by, in this batch — this is a leaf library; a host application supplies patterns and haystacks.

13. Phase 1 — Parser & AST

13.1 Objectives

  • Parse the full pattern grammar (§8.1) into a stable AST whose snapshot is checked into conformance/corpora/parser/.

13.2 Detailed Implementation Steps

  • Applies: P2 (one parser), P15 (typed errors), ADR-24 (syntax compatibility), Friedl ch. 4/6 (§5.1).
  • Hand-write a recursive-descent parser with explicit precedence climbing over the grammar in §8.1; track a byte-range Span per node.
  • On any construct the parser cannot express, bail immediately with the most specific ParseErrorKind available — no partial-parse recovery (P15); production parsers that "recover and continue" create downstream ambiguity a fast-fail parser avoids.
  • Implement a Visit trait so the HIR translator (§14), the syntax printer, and the debug CLI (regex-cli debug-ast) are all visitors over one AST shape, never ad hoc match blocks scattered across the codebase.
  • Reject POSIX bracket classes ([[:alpha:]]) and \Q…\E literal blocks with specific ParseErrorKinds rather than silently absorbing PCRE conveniences this engine does not implement (ADR-24).
  • Accept the three common named-group syntaxes ((?P<name>…), (?<name>…), (?'name'…)) and document the canonical form in docs/syntax/reference.md.

13.3 Deliverable

  • regex_syntax::ast::parse returns a stable AST for every fixture in conformance/corpora/parser/; regex-cli debug-ast pretty-prints it.

13.4 Acceptance Criteria

  • 100% of the parser corpus (≥ 200 fixtures) round-trips to a byte-identical AST snapshot across two consecutive builds; every fixture in parser/error_*.json produces the exact ParseErrorKind and byte Span recorded in the fixture.

13.5 Conformance Fixtures

  • parser/literal_ascii.json, parser/class_ranges.json, parser/repetition_greedy_lazy.json, parser/group_kinds.json, parser/error_unclosed_group.json, parser/error_posix_class_rejected.json.

13.6 Pitfalls

  • Greediness is set by the suffix (? after a quantifier means lazy); fixtures must exercise both forms for every quantifier shape or a greedy-vs-lazy regression ships silently.
  • Named-group syntax diverges across PCRE/Python/.NET; accept the three documented forms and reject everything else with a specific error, not a generic one.
  • \Q…\E is a PCRE convenience frequently requested; reject it cleanly with ParseErrorKind::LiteralBlockUnsupported and document regex::escape as the alternative in the syntax reference.

13.7 Performance Concerns

  • Single-pass, no backtracking in the parser itself; Span tracking is a pair of integers per node, not a heap allocation — parser allocation is dominated by the AST node count, which is O(pattern length).

13.8 Edge Cases

  • An empty class [] (reject); a class containing only a negation [^] (reject); a repetition on an anchor (^*, reject — anchors are zero-width and non-repeatable); deeply nested groups (bounded by size_limit, §15.3).

13.9 Failure Analysis

  • A parser ambiguity bug produces either a rejected-valid-pattern or an accepted-invalid-pattern; both are caught by diffing the parser corpus against the rust-regex reference parser's behavior on the same fixture set (§5.3) before the fixture is committed.

13.10 Operational Notes

  • regex.parse.errors metric (I7) increments on every ParseError; the parser corpus's byte-stability check runs in ci.yml on every push, not just nightly.

14. Phase 2 — HIR & Unicode Classes

14.1 Objectives

  • Translate the AST to the desugared, semantics-explicit HIR (§8.2, §11.5) with every Unicode property resolved, so Thompson construction (§15) has nothing left to interpret.

14.2 Detailed Implementation Steps

  • Applies: P5 (Unicode default), P12 (cursor owns boundaries), ADR-14 (checked-in tables), UTS#18 (§5.4).
  • Run the fixed translation pipeline: validate (reject \p{...} when unicode == false), desugar (\d/\w/(?i) expand per §8.2), resolve Unicode properties against the generated tables under regex-syntax/src/unicode_tables/, case-fold per UTS#18 RL1.5 simple fold, normalize classes (merge overlapping ranges, compute complements eagerly), and compute byte classes.
  • Implement the Unicode-class-to-UTF-8-byte-class construction (§8.12, Cox's technique): decompose each codepoint range by UTF-8 leading-byte arity into a fan of byte-range instructions.
  • Cap the number of ranges per class at a documented threshold (default 4096) to bound the UTF-8 byte-class construction's worst case, which is quadratic for pathological Unicode classes.
  • Distinguish ASCII ((?-u:\b)) from Unicode word boundaries (Look::WordAscii vs Look::WordUnicode, §11.5).
  • Desugar \R (UAX#14) to the disjunction of its line-break byte sequences with \r\n prioritized as a single unit.

14.3 Deliverable

  • regex_syntax::hir::translate accepts every AST in the parser corpus and produces a stable HIR; regex-cli debug-hir prints a fully-resolved HIR with no AST-level constructs remaining.

14.4 Acceptance Criteria

  • The Unicode table snapshot conformance/corpora/unicode/general_category.jsonl is byte-identical across at least two build hosts; the UTF-8 byte-class construction matches a precomputed reference table for every Unicode block in conformance/corpora/unicode/utf8_byte_classes.jsonl.

14.5 Conformance Fixtures

  • hir/desugar_perl_classes.json, unicode/general_category.jsonl, unicode/utf8_byte_classes.jsonl, unicode/case_fold_simple.json, unicode/word_boundary_ascii_vs_unicode.json.

14.6 Pitfalls

  • Case-folding must run before class merging, not after — folding after merge silently produces the wrong equivalence classes.
  • \p{InGreek} is a Block name query, not a Script name query — a frequent user error; accept the syntax, look up the Block table, and document the Script/Block distinction in docs/syntax/reference.md.
  • Grapheme-cluster boundaries depend on the pinned Unicode version; re-pin via ADR on every Unicode point release (ADR-14), never silently drift.

14.7 Performance Concerns

  • The UTF-8 byte-class construction is quadratic in range count for pathological classes; the 4096-range cap (§14.2) bounds compile time to a documented constant, verified in benchmarks/bench_unicode.rs.

14.8 Edge Cases

  • A class spanning the full codepoint range [\u{0}-\u{10FFFF}]; a property alias that resolves to an empty set; mixing unicode(false) with a pattern containing \p{...} (rejected at validate step, not silently downgraded).

14.9 Failure Analysis

  • A Unicode-table generation bug changes what \p{L} means silently; the byte-identical cross-host snapshot check (§14.4) is the only defense, since a single-host build would never notice.

14.10 Operational Notes

  • The regeneration script (crates/regex-syntax/build/regenerate-unicode.sh) runs only behind --features regen on a maintainer's machine, never in CI (ADR-14) — this keeps the build hermetic while still tracking Unicode releases.

15. Phase 3 — Thompson NFA Construction

15.1 Objectives

  • Lower the HIR to Thompson-construction NFA bytecode (§8.3, §11.6): a flat Vec<Instruction> with a deferred-fixup pass for forward references.

15.2 Detailed Implementation Steps

  • Applies: P1 (linear time), P2 (one construction path), Thompson 1968, Cox 2007 (§5.2), I1.
  • Implement the fragment rules from §8.3 as a recursive descent over the HIR, emitting placeholder instructions and recording fixup positions in a side table; patch once each successor's StateId is known (O(state_count) fixup pass).
  • Unroll counted repetitions (a{m,n}): m required copies followed by n-m optional copies, bounded by size_limit / size_per_byte (I1, §4.2); a{m,} unrolls as m copies followed by a*.
  • Number capture groups in source order; slot 2i/2i+1 per group (§8.5); emit the implicit whole-match group (Capture(0,…)/Capture(1,…)) even when no explicit groups are present.
  • Intern every concrete class into a per-NFA ByteClasses table, value-based, so two occurrences of [a-z] share one entry (this table is the lazy DFA's transition input in §18).
  • Encode greediness purely via Split branch order (§8.3): next_a preferred for greedy, swapped for lazy.

15.3 Deliverable

  • The Thompson construction passes every HIR fixture in conformance/corpora/nfa/; the bytecode snapshot is byte-stable across builds; regex-cli debug-nfa renders one instruction per line plus the byte-class table.

15.4 Acceptance Criteria

  • Every fixture in conformance/corpora/nfa/ produces byte-identical bytecode across two builds; a{1000000,1000001} returns ParseErrorKind::SizeLimitExceeded before any NFA is constructed, not after a multi-second unrolling attempt.

15.5 Conformance Fixtures

  • nfa/concat_alternation.json, nfa/repetition_unrolling.json, nfa/capture_group_numbering.json, nfa/byte_class_interning.json, nfa/size_limit_rejection.json.

15.6 Pitfalls

  • Off-by-one errors in Split ordering produce a pattern that matches the right language but with the wrong capture (greediness flipped silently) — fixtures must include leftmost-first capture vectors, not just match yes/no.
  • The implicit whole-match capture is easy to forget; a fixture must assert Capture(0,…)/Capture(1,…) exist even for a pattern with zero explicit groups.
  • Counted repetitions blow up bytecode size for adversarial patterns like a{1000000,1000001}; size_limit is the only gate — it must fire at parse time, not mid-construction.

15.7 Performance Concerns

  • The fixup pass is O(state_count); byte-class interning keeps the transition table compact, which is what makes the lazy DFA's per-transition cost bounded in §18.

15.8 Edge Cases

  • A pattern with zero live states after dead-code elimination (e.g. [^\x00-\x{10FFFF}], an empty class); a capture group inside a {0,0} repetition (zero-width, group never sets its slots); a Split cycle from a zero-width * body (rejected — a repeated construct that can match empty is a construction-time error).

15.9 Failure Analysis

  • A wrong fixup silently points a next field at the wrong StateId; the bytecode snapshot's byte-stability check across builds is the detection mechanism, since a wrong-but-stable bytecode would otherwise pass unit tests that don't check exact instruction shape.

15.10 Operational Notes

  • The bytecode snapshot format is documented in docs/architecture/overview.md; a new Instruction variant is an addition only (§11.6) — re-ordering breaks every snapshot fixture in one commit, a deliberate tripwire.

16. Phase 4 — PikeVM & NFA Simulation

16.1 Objectives

  • Implement the PikeVM (§8.7, §11.7): the conformance ground truth every other engine validates against.

16.2 Detailed Implementation Steps

  • Applies: P1 (linear time), I1, I2, Cox 2007/2009 (§5.2).
  • Implement the simulation loop from §3.5: maintain clist/nlist thread lists; at each byte, advance every thread whose instruction accepts it, epsilon-close each successor, and deduplicate by NFA StateId via a HashSet<StateId> keyed by state only — never by (state, slots) (this is the central trick that keeps simulation O(n·m), not exponential).
  • Implement anchors/zero-width assertions as Look instructions evaluated without consuming a byte; \b checks is_word(prev_byte) ^ is_word(curr_byte) using the ASCII or Unicode definition per the HIR variant (§14.2).
  • Implement anchored vs unanchored search: an unanchored search seeds the thread list at every input position (equivalently, an implicit .*? prefix); the HIR anchored-analysis pass (§3.2) decides which at compile time, not match time.
  • Wire regex-cli match --engine pike to force the PikeVM — this becomes the ground truth for the cross_engine conformance bucket (§24.4).
  • Size clist/nlist to the NFA's total state count once, at PikeVm construction, so no per-step growth check is needed on the hot path — a fixed-capacity Vec indexed by StateId is enough because the dedup set (§16.6) already bounds live-thread count by state count.
  • Preserve match_states registration order when a pattern can reach Match from more than one internal path (e.g. via two different alternation branches that both terminate the pattern) — the first-registered match's slot vector wins under leftmost-first, matching the Split branch-order convention (§8.3).

16.3 Deliverable

  • The PikeVM passes every fixture in conformance/corpora/pike/; a determinism test asserts the same input reproduces byte-identical match bytes across 1,024 runs (I10).

16.4 Acceptance Criteria

  • 100% of conformance/corpora/pike/ fixtures pass; the 1,024-run determinism loop shows zero divergence; simulation time on a 1 MB haystack with a moderate pattern stays within the O(n·m) bound measured in benchmarks/bench_simple.rs (≥ 100 MB/s floor, §4).

16.5 Conformance Fixtures

  • pike/anchored_vs_unanchored.json, pike/word_boundary_ascii.json, pike/word_boundary_unicode.json, pike/determinism_1024_runs.json.

16.6 Pitfalls

  • Forgetting epsilon-closure deduplication turns the PikeVM into a backtracker overnight; the dedup must key on StateId alone, never on (state, slots) — this is the single highest-value code-review question for this phase.
  • Unicode word boundaries depend on the codepoint before/after, not the byte; the cursor must expose prev_codepoint()/next_codepoint() on a haystack known to be valid UTF-8, falling back to byte boundaries in bytes mode.
  • Iterating clist in the wrong order (e.g. a HashSet's unspecified iteration order instead of insertion order) silently changes which thread wins leftmost-first ties — clist must be an order-preserving structure, never a plain hash set.

16.7 Performance Concerns

  • clist/nlist are pre-sized to the NFA's state count and reused across steps from the per-match Scratch arena (P13, I8) — no per-step heap allocation.
  • The dedup check itself (a bitset or dense array indexed by StateId, cleared once per step) must be O(1) per thread, not a HashSet lookup with hashing overhead, or the O(n·m) bound degrades to O(n·m·log m) in practice.

16.8 Edge Cases

  • A pattern that can match the empty string at every position (a*); an unanchored search on an empty haystack; a thread list that empties before consuming any byte (immediate Exhausted); a haystack of length zero against a pattern requiring at least one byte (immediate Exhausted, never a panic).

16.9 Failure Analysis

  • A missing dedup silently reintroduces exponential blowup that only manifests on adversarial inputs — indistinguishable from a healthy engine on the conformance corpus alone, which is why the ReDoS regression suite (§24.4) exists as an independent check on top of correctness fixtures.
  • A wrong clist iteration order produces a plausible match that is nonetheless the wrong one under leftmost-first — caught only by fixtures that assert the exact capture vector, not merely match/no-match (§16.5).

16.10 Operational Notes

  • regex.match.duration_ns (I1) is emitted per PikeVm::search call; a sustained upward trend on a fixed pattern set is the operator-visible signal that a dedup regression shipped.
  • The regex-cli match --engine pike --trace flag dumps the clist/nlist contents at every step for interactive debugging — documented as the first tool to reach for when a capture fixture fails.

17. Phase 5 — Capture Groups & Leftmost Semantics

17.1 Objectives

  • Turn the yes/no PikeVM into a capture-extracting matcher with documented leftmost-first and leftmost-longest semantics (§8.5–§8.6).

17.2 Detailed Implementation Steps

  • Applies: P6 (leftmost semantics), P13 (arena), I9, Laurikari 2000 (§5.2, deferred design constraints).
  • Implement SlotVec as copy-on-write: a thread's slots are shared until a Split produces two threads about to diverge in what they write, at which point the copy fires (I9) — write the fixture that exercises two branches both writing slot 1 at different positions to prove the copy timing is correct.
  • Implement leftmost-first (§8.6): the first thread reaching Match wins; its slot vector is returned; the rest of clist is discarded.
  • Implement leftmost-longest (§8.6): the simulation continues after the first Match, comparing (slot[1] - slot[0]) against the saved best and keeping the longer, terminating when the thread list empties.
  • Expose Captures::get(i) (indexed) and Captures::name(&str) (named, via the compiled name table) per §11.1.
  • Build the name table once at Regex::new time as an Arc<HashMap<String, u32>> shared across every Captures instance produced by that Regex — never reconstructed per match (P13).

17.3 Deliverable

  • Captures pass every fixture in conformance/corpora/captures/; leftmost-first and leftmost-longest each pass their corresponding corpora; CI runs both on every push.

17.4 Acceptance Criteria

  • 100% of conformance/corpora/captures/ fixtures pass under both semantics modes; a determinism test confirms identical capture vectors across 1,024 repeats of the same input (I10); at 100 capture groups the per-thread SlotVec footprint stays at the documented 1.6 KB ceiling (2 × 100 × 8 bytes).

17.5 Conformance Fixtures

  • captures/named_and_numbered.json, captures/cow_slot_divergence.json, leftmost_first/pcre_semantics.json, leftmost_longest/posix_semantics.json.

17.6 Pitfalls

  • The slot-vector copy-on-write is wrong if the copy fires after a slot write instead of before it — the canonical test is a Split whose two branches both write slot 1 at different input positions; a naive implementation aliases the write across both threads.
  • The slot vector grows linearly in group count; at 100 groups the per-thread footprint is 1.6 KB — copy-on-write bounds the per-step cost, but the memory footprint itself is real and must be documented, not assumed away.
  • Named-group lookups that rebuild the name table per Captures construction (instead of sharing the compiled Arc<HashMap<...>>) silently reintroduce per-match heap allocation the arena design (P13) was meant to eliminate.

17.7 Performance Concerns

  • Copy-on-write keeps the common case (no divergence) at zero extra allocation per step; the divergence case is bounded by the number of live Split points, which the byte-class-compacted bytecode keeps small.
  • Leftmost-longest's "keep running after the first Match" rule means its worst-case step count is strictly ≥ leftmost-first's for the same pattern — document this as an expected, bounded overhead, not a regression, when comparing benchmark numbers across the two modes.

17.8 Edge Cases

  • A group inside a * that matches multiple times — only the last match's boundaries are retained (per PCRE/rust-regex convention, documented in docs/syntax/differences-from-rust-regex.md); an unmatched optional group returns None from Captures::get, never a panic.
  • Two named groups sharing the same name in different alternation branches (e.g. (?P<x>a)|(?P<x>b)) — accepted per rust-regex convention since only one branch can ever be live in a given match; document this explicitly rather than rejecting it as a duplicate-name error.

17.9 Failure Analysis

  • A leftmost-longest regression that silently returns leftmost-first results is caught only by running both corpora on every push (§17.3) — a single shared corpus would hide the divergence.
  • A capture-slot aliasing bug (§17.6) typically manifests as a passing match/no-match test with a silently wrong captured substring — the capture fixtures must assert exact byte ranges per group, never just overall match success.

17.10 Operational Notes

  • regex.captures.slot_copies (I9) is emitted per copy-on-write fork; an unexpectedly high rate on a hot-path pattern is the signal to consider the tagged-DFA deferred optimization (§38) rather than a code-level bug.
  • regex-cli debug-nfa --slots annotates each Capture instruction with its group number and name, used to cross-check a suspicious capture result against the compiled bytecode directly.

18. Phase 6 — Lazy DFA & Literal Prefilter

18.1 Objectives

  • Build the lazy DFA (§8.10, §11.8): the throughput engine, correct by construction because every state is provably a subset of the PikeVM's frontier.

18.2 Detailed Implementation Steps

  • Applies: P4 (bounded cache), I3, I6, ADR-06/ADR-07/ADR-08, Cox 2010, Aho & Corasick 1975, Boyer & Moore 1977 (§5.2).
  • Implement lazy construction: a DFA state is a canonicalized NFA state-set; a transition on a byte advances every NFA state in the set, epsilon-closes, canonicalizes (a sorted Vec<StateId> plus a hash — encoded in exactly one place), and either hits the cache or allocates a new DfaCache entry.
  • Implement the clear-not-evict cache policy (§8.10): when dfa_size_limit is exceeded, clear the whole cache and resume from the start state (RE2's own tradeoff, ADR-06) rather than a per-state LRU; fire regex.dfa.cache_cleared on every clear.
  • Implement the PikeVM fallback: if the cache clears three times within n bytes of one match, switch to the PikeVM for the rest of that match and fire regex.dfa.fallback (I6, P9) — the cross-engine bucket (§24.4) asserts the fallback never changes the answer.
  • Implement capture-group fallback: the lazy DFA is a yes/no + longest-prefix matcher; when captures are needed it runs a scan pass for the boundary, then a PikeVM capture pass over only the matched substring (RE2's "DFA + NFA composition").
  • Implement the literal extractor as a HIR pass identifying prefix/suffix/inner literals; build a Boyer-Moore LiteralStrategy for one literal (ADR-08) or an Aho-Corasick automaton for several (ADR-07); expose the decision via Regex::literal_strategy() (P10, I12).

18.3 Deliverable

  • The lazy DFA passes every fixture in conformance/corpora/dfa/; the cross_engine bucket asserts PikeVM/LazyDfa agreement on every fixture; the literal prefilter snapshot in conformance/corpora/prefilter/ is byte-stable; the 1 GB/s target (§4) is met on benchmarks/bench_literal.rs on reference hardware.

18.4 Acceptance Criteria

  • 100% of conformance/corpora/dfa/ and conformance/corpora/cross_engine/ fixtures pass; regex.dfa.cache_cleared fires zero times on a fixed 10,000-fixture conformance run at the default 8 MB cache (§4.2); BM prefilter throughput ≥ 1 GB/s, Aho-Corasick prefilter throughput ≥ 800 MB/s on benchmarks/bench_literal.rs.

18.5 Conformance Fixtures

  • dfa/lazy_construction.json, dfa/cache_clear_and_rebuild.json, cross_engine/pike_vs_dfa.json, prefilter/boyer_moore_snapshot.json, prefilter/aho_corasick_snapshot.json.

18.6 Pitfalls

  • The canonical state-set representation matters: a BTreeSet<StateId> is correct but slow on small sets; a sorted Vec<StateId> plus a hash is the conventional, faster choice — encode canonicalization in exactly one function, never duplicated.
  • The cache-fill-detection heuristic ("three clears within n bytes") is the kind of constant that gets silently "tuned" across many PRs; document it in docs/architecture/lazy-dfa.md and require an ADR to change it.
  • A wide class inside a counted repetition ([\x00-\xFF]{50}) can blow up DFA state count even though size_limit bounds the NFA; the dfa_size_limit clear-on-full policy is the independent gate for this shape (§4.2).
  • Choosing Knuth-Morris-Pratt (Knuth, Morris & Pratt 1977, §5.2) over Boyer-Moore for the single-literal path would trade away the average-case sub-linear skip distance BM provides on typical text for a worst-case-linear guarantee that is already redundant here — the surrounding NFA/DFA path already holds the linear-time guarantee (I1), so BM's better average case (ADR-08) is the correct tradeoff, not a compromise.

18.7 Performance Concerns

  • Byte-class compaction (§15.2) is what keeps the per-transition cost bounded; canonicalization cost is amortized because most states are cache hits after the first pass over a repetitive haystack.

18.8 Edge Cases

  • A pattern whose DFA has exactly one reachable state (a fixed-length literal); a haystack that triggers three consecutive cache clears (fallback fires mid-match, §18.2); a literal extractor that finds zero required literals (LiteralStrategy::None, engine runs unassisted).

18.9 Failure Analysis

  • A literal-extraction bug that produces a wrong-but-plausible prefilter is a correctness bug, not a performance regression (I12) — it manifests as a missed match, caught only by the prefilter conformance bucket comparing against an unassisted NFA/DFA scan, never by a benchmark.

18.10 Operational Notes

  • regex.dfa.cache_cleared and regex.dfa.fallback are the two operator-facing signals for "this pattern needs a bigger dfa_size_limit or a rewrite" — both are documented in docs/runbooks/slow-pattern.md (§23.3).

19. Phase 7 — Engine Selection, One-Pass DFA & RegexSet

19.1 Objectives

  • Land the meta-engine selector (§3.2): the single place engine choice is made, once, at Regex::new time (P3); add the one-pass DFA optimization and RegexSet.

19.2 Detailed Implementation Steps

  • Applies: P3 (compile-time selection), P9 (no silent fallback), I4, I15, ADR-18.
  • Implement the selector's decision order: a pattern needing a backreference or NFA-unsupported lookaround routes to Backtrack (or errors if the caller explicitly requested PikeVm, I4); an explicit Backtrack request on a pattern that does not need it is an error; a one-pass-eligible pattern gets the one-pass DFA; otherwise the default is PikeVm + LazyDfa(opportunistic).
  • Implement one-pass detection (ADR-18): walk the NFA and ask whether any state has more than one outgoing edge accepting the same byte class; if not, compile a small dense DFA once, at construction time, and run it without the lazy machinery (RE2's Prog::IsOnePass). Run this detector after the lookaround analysis pass — non-trivial lookbehind is categorically not one-pass even when the prefix grammar suggests otherwise.
  • Implement RegexSet (§11.8): the Thompson construction emits a Match{pattern_id: i} per pattern; the engine reports the set of matching indices via SetMatches, reusing every existing engine — only the post-processing is new (I15).
  • Record the selector's disposition (PikeVm, LazyDfa, OnePassDfa, or Backtrack) as an immutable field on the compiled Regex, read by Regex::engine() (§11.1) and every regex.engine.selected trace event — never recomputed per call.

19.3 Deliverable

  • The selector passes every fixture in conformance/corpora/cross_engine/; the one-pass detector covers every fixture in conformance/corpora/dfa/onepass/; RegexSet::matches passes every fixture in conformance/corpora/set/.

19.4 Acceptance Criteria

  • 100% of conformance/corpora/set/ fixtures show zero false positives and zero false negatives against running each pattern individually (I15); the one-pass detector correctly classifies every fixture in dfa/onepass/ including the lookbehind-exclusion cases; an explicit RegexBuilder::engine(PikeVm) on a backreference pattern returns Err(EngineUnsupported) in 100% of fixtures.

19.5 Conformance Fixtures

  • dfa/onepass/simple_prefix.json, dfa/onepass/lookbehind_excluded.json, set/multi_pattern_match.json, cross_engine/selector_disposition.json.

19.6 Pitfalls

  • A RegexSet whose patterns share a long common prefix produces an NFA that looks one-pass but blows up the cache against a pathological input — benchmark before declaring the one-pass classification a win.
  • The selector's decision is stored once in the compiled Regex; downgrading it at match time is forbidden by P9 except the one documented lazy-DFA-cache-exhaustion fallback (§18.2) — any other match-time re-decision is a design violation, not an optimization.
  • Running the one-pass detector before the lookaround analysis pass instead of after is a subtle ordering bug: a pattern with non-trivial lookbehind can superficially look one-pass from the prefix grammar alone, and only the lookaround pass reveals it is not.

19.7 Performance Concerns

  • One-pass DFA construction runs once at Regex::new time; its cost is amortized across every subsequent match, which is why it is worth doing even though it duplicates work the lazy DFA could eventually do incrementally.
  • RegexSet construction cost is O(Σ pattern sizes) for the shared Thompson construction, plus a fixed per-pattern Match tagging step; this is the number the deferred regex_set! macro (§38) targets when it later moves this cost to build time.

19.8 Edge Cases

  • A RegexSet with zero patterns (constructs successfully, never matches); a pattern that is simultaneously one-pass-eligible and backreference-free but explicitly requested as Backtrack (honored — an explicit request always wins over the auto-selection default).
  • Two patterns in one RegexSet where one is one-pass-eligible and the other is not — the set as a whole runs on whichever engine the shared NFA construction supports, never a per-pattern engine split within a single set.

19.9 Failure Analysis

  • A one-pass misclassification (accepting a non-one-pass NFA as one-pass) produces silently wrong matches on ambiguous input — caught only by the dfa/onepass/lookbehind_excluded.json class of fixture that specifically targets the false-positive case, not by the happy-path fixtures.
  • A RegexSet pattern-id mistagging during shared construction produces a plausible-looking SetMatches result with the wrong bit set — caught only by comparing against per-pattern Regex results, never by inspecting the bit-vector shape alone.

19.10 Operational Notes

  • regex.engine.selected (I2, I4) is the single trace event an operator needs to answer "which engine is running this pattern" — documented as the first step in docs/runbooks/triage.md.
  • regex-cli debug-nfa --onepass reports the one-pass detector's verdict and, on rejection, the specific state and byte class that disqualified the pattern — the first diagnostic to reach for when an expected one-pass win doesn't materialize.

20. Phase 8 — Lookaround Support

20.1 Objectives

  • Implement the four lookaround forms — positive/negative lookahead, positive/negative lookbehind — split between the NFA path (fixed-width lookbehind, all lookahead) and the backtracking VM (variable-width lookbehind).

20.2 Detailed Implementation Steps

  • Applies: P7 (gating), P15 (typed errors), I4, ADR-24.
  • Implement lookahead on the NFA path (§8.4 Look/Lookaround instructions): spawn a side simulation from the current position, evaluate the inner pattern, discard the side simulation's progress, and continue the parent with the side simulation's yes/no verdict — this works for both polarities without backtracking.
  • Implement fixed-width lookbehind on the NFA path: compute the inner pattern's width as a structural-recursion HIR analysis pass (lookarounds inside it contribute zero width); at the lookbehind position, spawn a side simulation that runs backward by exactly that width and evaluates the inner pattern.
  • Route variable-width lookbehind (e.g. (?<=a+)) to the backtracking VM (§21) and flip the engine selector to Backtrack at compile time (I4) — the user sees the budget gate (§21.3), never a silent linear-time attempt that would be wrong.
  • Maintain a stack of in-flight sub-program simulations; unconditionally unwind it on every exit path, including the failure path, so a negative lookahead nested inside a positive lookahead cannot leak stack state.
  • Cache the fixed-width computation per lookbehind construct at compile time (once, in the HIR analysis pass) rather than recomputing it on every match — the width is a static property of the pattern, never a function of the input.

20.3 Deliverable

  • Fixed-width lookbehind and both lookahead polarities pass every fixture in conformance/corpora/lookaround/fixed_width/ and conformance/corpora/lookaround/lookahead/; variable-width lookbehind is gated to BacktrackVM and documented.

20.4 Acceptance Criteria

  • 100% of lookaround/fixed_width/ and lookaround/lookahead/ fixtures pass on the NFA path with zero backtracking-VM invocations; 100% of lookaround/variable_width/ fixtures pass on BacktrackVM only, confirmed by asserting Regex::engine() returns Engine::Backtrack for every fixture in that corpus.

20.5 Conformance Fixtures

  • lookaround/lookahead_positive.json, lookaround/lookahead_negative.json, lookaround/fixed_width/lookbehind_3byte.json, lookaround/variable_width/lookbehind_plus.json.

20.6 Pitfalls

  • A negative lookahead nested inside a positive lookahead is a notorious tarpit; the sub-program stack must unwind on every exit path, including the failure path — a fixture must specifically exercise this nesting.
  • Computing fixed lookbehind width is harder than it looks: the inner pattern can itself contain zero-width lookarounds; the width analysis must be structural recursion over the HIR with a documented width for every variant, not a byte-count heuristic.
  • (?!^) in multi-line mode means "not at the start of a line" — the negation of a zero-width assertion; anchor evaluation inside lookaround must stay consistent with the surrounding multi-line context, not silently reset it.

20.7 Performance Concerns

  • A side simulation for lookahead/lookbehind is bounded by the inner pattern's own bytecode size; nested lookarounds compose linearly in stack depth, not exponentially, because each level is a bounded sub-program, not a re-entrant backtrack.

20.8 Edge Cases

  • A lookbehind whose inner pattern can match zero width ((?<=)); a lookahead at the very end of the haystack; three lookarounds nested inside each other, each of a different polarity.

20.9 Failure Analysis

  • A width-computation bug for fixed lookbehind produces a match at the wrong offset rather than a rejection — caught only by a fixture that checks the exact match range, not just match/no-match, which is why lookaround/fixed_width/ fixtures always assert a byte range.
  • A sub-program stack leak (unwind skipped on one exit path) manifests as a slow memory creep across many matches rather than an immediate crash — the soak test (§29) is the detection mechanism, not a single-match unit test.

20.10 Operational Notes

  • Regex::engine() returning Engine::Backtrack for a pattern the author believed was on the fast path is the single most common lookaround-related support question; docs/runbooks/slow-pattern.md documents checking this first.
  • regex-cli debug-hir --lookaround-widths prints the computed fixed width (or "variable") for every lookbehind construct in a pattern, the first diagnostic for "why did this route to BacktrackVM."

21. Phase 9 — Backtracking VM With Budget

21.1 Objectives

  • Implement the engine of last resort (§8.7, §11.7): a textbook backtracker whose only non-textbook addition is a hard, explicit step budget that makes ReDoS structurally impossible on this path.

21.2 Detailed Implementation Steps

  • Applies: P7 (gating), P8 (budget), I5, ADR-03, ADR-20 (unsafe policy), PCRE2 reference (§5.3), Davis et al. 2018 (§5.2, §25).
  • Implement the dispatch loop: a frame stack of (pc, input_pos, slots); on Split, push the loser frame and continue with the winner; on Match, return; the budget check runs in the dispatch loop itself, not inside individual instruction handlers, so step counts don't vary with implementation details (§4.1).
  • Implement backreferences (Backref{group, case_insensitive, next}): read slots[2*group..2*group+2] for the captured substring, compare byte-for-byte (or case-folded per-codepoint for case-insensitive) against the input from input_pos; on mismatch, drop the frame and pop the next one.
  • Use a copy-on-write SlotVec shared with a per-match arena, identical in spirit to the PikeVM's (§17.2), to avoid the obvious quadratic memory footprint per Split.
  • Wire the default budget (1,000,000 steps) and max (100,000,000) from RegexBuilder::backtrack_budget (§11.2); on exhaustion return Err(MatchError::Budget) — never a partial answer, never a silent stall (P8, I14).
  • Case-fold backreference comparisons per-codepoint (not per-byte) in Unicode mode, reusing the same UTS#18 RL1.5 simple-fold table the HIR case-folding step already consults (§14.2) — never a second, divergent fold implementation.

21.3 Deliverable

  • The backtracking VM passes every fixture in conformance/corpora/backtrack/; the ReDoS regression bucket (conformance/corpora/redos/) runs against it and asserts every adversarial input either finishes within max_wall_ms or returns Err(Budget) — never a silent stall.

21.4 Acceptance Criteria

  • 100% of conformance/corpora/backtrack/ fixtures pass; 100% of conformance/corpora/redos/ fixtures finish within their fixture-specified max_wall_ms or return Err(Budget); a determinism test confirms identical results across 1,024 repeats (I10); every fixture in the public ReDoS corpus (Davis et al. 2018) exhausts the default budget in under 100 ms wall-clock on reference hardware.

21.5 Conformance Fixtures

  • backtrack/backreference_case_sensitive.json, backtrack/backreference_case_insensitive.json, redos/nested_quantifier_catastrophic.json (pattern (a+)+$, max_wall_ms: 100), redos/alternation_overlap.json.

21.6 Pitfalls

  • The budget check placed inside individual instruction handlers instead of the dispatch loop produces step counts that vary with refactoring — always check the budget once per popped frame, in one place.
  • The slot-vector clone per Split is the obvious quadratic memory footprint; copy-on-write with a shared arena (same design as the PikeVM, §17.2) is mandatory, not optional.
  • A "looks-fine" pattern that is actually catastrophic is the recurring surprise (the Cloudflare 2019 incident class, §2.2); the ReDoS regression bucket must be treated as a living document, updated whenever a new pathological pattern is reported in the literature or a CVE.

21.7 Performance Concerns

  • Budget-exhaustion detection is O(1) per frame pop; the dominant cost under normal (non-adversarial) patterns is the frame stack's push/pop churn, bounded in practice because most backtracking VM invocations are on short patterns with few backreferences.

21.8 Edge Cases

  • A backreference to a group that never matched (per rust-regex/PCRE convention, the backreference fails to match anything, documented in docs/syntax/differences-from-rust-regex.md); a pattern requiring Backtrack explicitly requested with RegexBuilder::engine(PikeVm) (construction error, I4); a budget of exactly 0 (immediate Err(Budget) on the first step).

21.9 Failure Analysis

  • A budget-exhaustion event on a pattern the author believed was safe is either (a) a genuinely pathological pattern (rewrite it) or (b) an adversarial input (rate-limit the caller) — docs/runbooks/budget-exceeded.md documents distinguishing the two from the traced input and pattern alone.
  • A case-fold divergence between the backreference comparison and the HIR's own case-folding step produces a backreference that fails to match text a naive reading of the pattern suggests it should — caught only by a fixture that exercises case-insensitive backreferences against non-ASCII input.

21.10 Operational Notes

  • regex.backtrack.budget_exceeded (I5, I14) carries pattern_id, input_pos, and steps; this is the single metric that proves the linear-time guarantee's escape hatch is bounded, and it is the headline dashboard panel in §27.
  • regex-cli match --engine backtrack --trace dumps the frame stack at every step for interactive debugging of a budget-exhaustion or backreference-mismatch report.

22. Phase 10 — Streaming Match & Build-Time Compilation

22.1 Objectives

  • Lift the slice-based engines onto a BufRead stream (§11.7 Input/Stream) and onto the regex! build-time procedural macro (P11).

22.2 Detailed Implementation Steps

  • Applies: P11 (build-time patterns), P13 (arena), ADR-09, ADR-23.
  • Implement StreamMatcher (§11.7-adjacent): feed(&mut self, chunk: &[u8]) -> StreamResult { NeedMore, Match, NoMatch }; the resumption token is the lazy DFA's state-set representation on that path, or the PikeVM's serialized thread list on that path.
  • Bound the "carry bytes across chunks" buffer by the HIR's max_match_len() analysis pass, with a documented default for patterns with unbounded match length (e.g. a*) — an unbounded buffer is a DoS surface (§25).
  • Reject BacktrackVM from streaming construction with Err(StreamingUnsupported) — its frame stack is unbounded in input position and is not safely resumable in the general case.
  • Implement the regex! procedural macro (crates/regex-macro): parse → HIR → NFA → literal extraction, all at build time, emitting the resulting Nfa/LiteralStrategy as a const/static and wrapping it in a Regex constructor that skips runtime parsing entirely; failures are compile errors with proc_macro2::Span-derived diagnostics.
  • Run the same engine-selection logic (§19.2) at macro-expansion time as at runtime Regex::new time — the two code paths must share the selector implementation, never fork a separate "compile-time" selection heuristic.

22.3 Deliverable

  • StreamMatcher passes every fixture in conformance/corpora/streaming/; the regex! macro passes every fixture in a dedicated macro corpus; examples/streaming/ matches against a 100 MB log file read through BufRead.

22.4 Acceptance Criteria

  • 100% of conformance/corpora/streaming/ fixtures match identically whether fed as one slice or as arbitrarily-chunked feed() calls; regex!("...") on a malformed pattern fails the build with a span-precise diagnostic in 100% of macro-corpus negative fixtures; streaming throughput on a 1 GB log file ≥ 200 MB/s (§4, §31 M12).

22.5 Conformance Fixtures

  • streaming/chunked_vs_slice_equivalence.json, streaming/carry_buffer_bound.json, macro/compile_time_literal.json, macro/compile_time_syntax_error.json.

22.6 Pitfalls

  • The carry-buffer bound must come from max_match_len(), not a fixed constant — a pattern with unbounded match length needs a documented, configurable fallback bound, or the buffer itself becomes the DoS surface it was meant to prevent.
  • The proc-macro runs in the proc-macro build context, not the engine's runtime context; diagnostics use proc_macro2::Span, interconverted at the macro entry point, never the engine's own Span type directly.
  • The proc-macro can emit large const data for big patterns; the size_limit unrolling cap (§15.2) keeps emitted code under the default Rust recursion/stack budget for the compiler, not just the runtime engine.

22.7 Performance Concerns

  • regex! reduces per-call construction cost to one allocation (the compiled program is static); StreamMatcher::feed must not re-scan already-confirmed prefix bytes on each call — the resumption token exists precisely to avoid that.

22.8 Edge Cases

  • A stream that never produces a full match before EOF (finish() returns None); a pattern requiring BacktrackVM passed to StreamMatcher::new (construction error); a regex! pattern that requires the backtracking VM (still compiles — the macro emits the correct engine choice, it does not reject backreferences).

22.9 Failure Analysis

  • An unbounded carry buffer on a pattern the author assumed was bounded is a memory-growth incident, not a crash — docs/failure-analysis/ documents deriving the bound from max_match_len() retroactively as the fix, never a hotfix constant.
  • A regex!-vs-Regex::new selector divergence (§22.2) produces a pattern that behaves differently depending on whether it was build-time or runtime compiled — treated as a P0 correctness bug, caught by a fixture that constructs the same pattern both ways and asserts Regex::engine() agreement.

22.10 Operational Notes

  • regex!-compiled patterns carry a marker so Regex::engine() and tracing spans still report accurately even though no runtime parse occurred — build-time compilation must never make the engine less observable than the runtime path.
  • examples/streaming/ is the reference integration test for the 200 MB/s M12 target (§31); its CI run doubles as the streaming-throughput regression gate.

23.1 Objectives

  • Ship the tracing, metrics, and runbook surface every invariant in §7 already assumes exists (P9, P10).

23.2 Detailed Implementation Steps

  • Applies: P9 (observable fallback), P10 (observable prefilter), ADR-16 (tracing).
  • Emit tracing spans/events at: regex.compile.start/regex.compile.finish; regex.engine.selected{engine}; regex.dfa.cache_cleared{at_input_pos,bytes_in_cache}; regex.dfa.fallback{clears_in_window,at_input_pos}; regex.backtrack.budget_exceeded{pattern_id,input_pos,steps}; regex.match.found{pattern_id,range}.

  • Cross-check every metric name and every tracing event name against the identifiers already used in §7 (System Invariants) and §26 (Failure Modes) — the terminology-lock rule (standard §5.5) is enforced here as a literal diff, not a style preference.

23.3 Deliverable

  • Tracing spans cover the full match lifecycle end to end; the Prometheus metrics implementation is wired into examples/waf/; the three runbook entries are real, tested instructions, not placeholders.

23.4 Acceptance Criteria

  • Every event listed in §23.2 fires at least once in the examples/waf/ integration test; a runbook walkthrough (recorded as a fixture transcript) reproduces the diagnosis for one seeded regex.dfa.fallback event and one seeded regex.backtrack.budget_exceeded event within 10 minutes by a reviewer unfamiliar with the specific incident.

23.5 Conformance Fixtures

  • observability/tracing_span_coverage.json, observability/prometheus_metric_names.json, observability/runbook_dfa_fallback_walkthrough.md.

23.6 Pitfalls

  • A metric name that drifts from the tracing event name (e.g. dfa_cache_clear vs regex.dfa.cache_cleared) breaks the dashboard-to-runbook mapping silently — the terminology-lock rule (standard §5.5) applies to telemetry names exactly as it does to code identifiers.
  • Wiring metrics only into examples/waf/ and not the core library leaves embedding hosts with no observability unless they happen to copy that example — the Metrics trait must be a first-class, documented public API (§11.1-adjacent), not example-only glue.
  • A runbook that references a metric name that was later renamed in code (without updating the doc) is worse than no runbook — the doc-lint script (I11) is extended in this phase to also check runbook metric-name references against the Metrics trait's method names.

23.7 Performance Concerns

  • tracing span creation on the hot match path must be near-zero-cost when no subscriber is registered (the crate's own design guarantee) — verify this holds under benchmarks/bench_simple.rs with and without a subscriber attached.
  • The PrometheusMetrics implementation's Histogram/Counter updates must not lock a shared mutable structure on the match hot path; use lock-free atomics or a per-thread aggregation buffer flushed periodically.

23.8 Edge Cases

  • A host that never implements Metrics (the default no-op implementation must compile and cost nothing); a regex.dfa.fallback event firing multiple times within one match (each fires independently, none suppressed).
  • A host running with a tracing subscriber that filters out regex.* events entirely — the engine must not change behavior based on whether events are actually consumed downstream.

23.9 Failure Analysis

  • Missing telemetry on a production incident is itself a failure mode — the runbooks explicitly list "no regex.backtrack.budget_exceeded events, but latency is up" as a symptom pointing at the PikeVM or lazy-DFA path instead, not the backtracking VM.
  • A runbook that fails its own recorded walkthrough fixture (§23.5) during a doc review is treated exactly like a failing conformance fixture — it blocks merge until corrected, never left as "known stale."

23.10 Operational Notes

  • Dashboards: (1) match-latency histogram by engine; (2) DFA cache-clear/fallback rate; (3) budget-exceeded rate and top offending pattern_ids; (4) engine-selection distribution. Alerting: p99 latency breach, a sustained regex.dfa.fallback rate, any regex.backtrack.budget_exceeded spike correlated with a deploy.
  • The runbook walkthrough fixtures (§23.5) are re-run as part of make conformance, not just at authoring time — this is what keeps them "real, tested instructions" rather than documentation that silently rots (§23.3).

24. Phase 12 — Fuzzing Harness & ReDoS Regression Suite

24.1 Objectives

  • Land the validation phase that catches what unit tests cannot: the fuzz targets and the ReDoS regression suite that prove the engine never regresses to exponential behavior (the Sealed gate).

24.2 Detailed Implementation Steps

  • Applies: P8 (budget), I5, I10, ADR-11, ADR-21, Davis et al. 2018 (§5.2).
  • Implement seven fuzz targets under fuzz/fuzz_targets/: parse.rs (random byte streams as patterns, assert no panic); compile.rs (random valid patterns via proptest-style shrinking, assert bounded bytecode); pike.rs (random pattern/input pairs, assert no panic and determinism); dfa.rs (assert agreement with PikeVM); backtrack.rs (assert agreement with PikeVM subject to budget, and budget honored); cross_engine.rs (assert all three engines agree); unicode.rs (random Unicode in patterns/inputs, assert no panic, no incorrect class membership).
  • Seed the fuzz corpus from the conformance corpus, the public ReDoS corpus (Davis et al. 2018), and rust-regex's public test suite (appropriately licensed).
  • Implement the ReDoS regression suite (conformance/corpora/redos/): each fixture is a (pattern, input, max_wall_ms) triple; run on BacktrackVM; assert every fixture finishes within max_wall_ms or returns Err(Budget) — never a silent stall. Update this corpus whenever a new pathological pattern is reported in the literature or a CVE (§21.6).
  • Wire make fuzz to run each target for a configurable wall-clock budget (default 60 s); a nightly CI workflow (fuzz.yml) runs a 1-hour-per-target budget and uploads the corpus diff.
  • Wire redos.yml to run the ReDoS regression bucket at a 5× default budget on a daily schedule, independent of the push-triggered conformance run — a regression here opens an automatic issue rather than silently waiting for the next PR to notice.

24.3 Deliverable

  • All seven fuzz targets compile and run; the ReDoS regression suite is green; the conformance runner emits the final conformance.report.json with every non-deferred bucket at Pass.

24.4 Acceptance Criteria

  • A 60-second make fuzz run across all seven targets finds zero new crashes; the ReDoS regression suite (conformance/corpora/redos/) passes 100% of its fixtures; the cross_engine bucket (§7 I2) shows zero divergences across the full conformance corpus; a 30-day local fuzz canary (the Sealed gate) runs all seven targets concurrently with zero crashes and zero panics.

24.5 Conformance Fixtures

  • redos/nested_quantifier_catastrophic.json, redos/alternation_overlap.json, cross_engine/full_corpus_agreement.json, fuzz/corpus_seed_manifest.json.

24.6 Pitfalls

  • A fuzz target that allocates unboundedly eats the runner's memory; every target sets allocator limits and uses the arbitrary crate to bound input sizes.
  • The cross_engine fuzz target can find legitimate, documented divergences (e.g. byte-mode vs Unicode-mode engines on a pattern with \p{L}) — classify these explicitly in the target's own logic as expected divergences, never silently suppress the whole target.
  • The 30-day canary requires dedicated hardware and a documented setup (docs/runbooks/, referenced from §23) — running it ad hoc on a laptop produces unreproducible results that cannot gate a release.

24.7 Performance Concerns

  • Fuzz targets are excluded from the throughput benchmarks (§4, §31) by design — their job is coverage and crash-finding, not speed measurement; conflating the two hides both signals.

24.8 Edge Cases

  • A fuzzer-discovered pattern that is valid but pathologically slow on the linear-time path (should be structurally impossible per I1 — treat any such finding as a P0 correctness bug, not a ReDoS-suite addition); a fuzzer input that is valid UTF-8 by construction but exercises a rare grapheme-boundary case.

24.9 Failure Analysis

  • Any fuzz-found crash blocks the release (release.yml gates on a clean fuzz.yml run); a cross_engine divergence found by fuzzing is committed to corpora/cross_engine/divergences/ with a description and an ADR disposition before the fixture is resolved, never silently dropped.
  • A ReDoS-suite fixture that starts silently taking longer wall-clock time (without exceeding max_wall_ms) as the codebase evolves is itself a leading indicator of an approaching regression — redos.yml's daily schedule at 5× budget is designed to surface this drift before it crosses the fixture's actual threshold.

24.10 Operational Notes

  • The Sealed gate (§1.11-adjacent) requires: the 30-day fuzz canary clean, the ReDoS regression suite green, and the performance targets (§31 M1–M12) met on reference hardware — recorded in benchmarks/results/reference.md and audits/ at release time.
  • The fuzz corpus diff uploaded by the nightly fuzz.yml run is reviewed weekly for interesting new seeds worth promoting into the permanent conformance corpus, keeping the two test surfaces (fuzzing for discovery, conformance for regression-locking) in sync.

28. Compatibility & Versioning

  • Wire compatibility: the NFA bytecode snapshot format (§11.6) is internal-only, never sent over a network; the only "wire" artifact is the regex! macro's compile-time const/static emission, which is recompiled with the host, never deserialized from an external source (T11).
  • Storage compatibility: none — the engine holds no persistent state; Unicode tables are versioned, checked-in source data (ADR-14, I13).
  • Schema-evolution: a new Instruction variant is an addition only, never a re-ordering (§11.6); adding a variant is a minor-version-compatible change for internal snapshot fixtures but may be a breaking change for any downstream code matching exhaustively on Instruction — documented as such.
  • API stability: Regex/RegexSet/RegexBuilder/Captures/Match/Error signatures (§11.1–§11.3) are SemVer-governed; a breaking change requires a major version bump.
  • Migration: a RegexBuilder default change (e.g. adjusting dfa_size_limit's default) is documented in CHANGELOG.md as a behavior-affecting minor bump, never silent.
  • Deprecation policy: a deprecated builder method is marked #[deprecated] for at least one minor cycle before removal, with the replacement named in the deprecation message.
  • SemVer policy: the public API in §11.1–§11.3 follows strict SemVer; the internal bytecode format (§11.6) follows its own additions-only rule independent of the crate's public SemVer.
  • Rolling-upgrade guarantees: since the engine is an embedded library with no shared mutable external state, there is no cross-instance rolling-upgrade concern — each host process runs its own pinned engine version.
  • Deferred (gated): a wire-transmittable precompiled bytecode format with a validator (§38, T11) — until built, no version of this engine accepts externally-sourced bytecode.
  • Worked example — an additive change: adding a new RegexBuilder::grapheme_aware(bool) builder method in a future release is additive (a minor bump) because existing callers' code compiles and behaves identically without it; a breaking change would be altering what RegexBuilder::unicode(false) means for an existing byte-mode pattern already in production, which requires a major bump and a CHANGELOG.md migration note.
  • Worked example — a behavior-affecting default change: lowering the default backtrack_budget from 1,000,000 to 100,000 could make a previously-succeeding pattern return Err(Budget) — this is documented as a minor-version behavior change (§28's migration rule) with the exact old/new default called out, never silently rolled into a patch release.
  • Divergence documentation: every place this engine's behavior intentionally differs from rust-regex (e.g. a rejected PCRE convenience, §13.6) is tracked in docs/syntax/differences-from-rust-regex.md, which is itself versioned alongside the crate so a caller can pin both together.
  • Conformance-report schema versioning: ConformanceReport.schema_version (§11.9) is itself SemVer-governed independently of the crate version, so a tooling consumer parsing conformance.report.json across releases has its own explicit compatibility contract, never an implicit one tied to the crate's own version number.

29. Testing & Verification Strategy

  • Unit: the parser (per-construct AST snapshots, §13); the HIR translator (per-desugar-rule, §14); Thompson construction (per-fragment-rule, §15); each engine's dispatch loop in isolation.
  • Integration: end-to-end Regex::new → find/captures across the full grammar, both alphabets (Unicode/bytes), both leftmost semantics.
  • Property tests: proptest-generated patterns + inputs asserting cross-engine agreement (I2); parse∘print round-trips where applicable; capture-slot determinism across repeated runs (I10).
  • Differential: the cross_engine bucket (PikeVM vs LazyDfa vs BacktrackVM, §7 I2) is the spine; a divergence is a P0 correctness bug, never a "known difference" without an ADR.
  • Fuzzing: the seven targets in §24.2, cargo-fuzz/libFuzzer-based, CI-budgeted (60 s/target on push, 1 h/target nightly).
  • Chaos/fault injection: deliberately misconfigured dfa_size_limit/backtrack_budget values injected in integration tests to confirm the documented fallback/error behavior fires exactly as specified, not just on the happy path.
  • Deterministic replay: the 1,024-run determinism loop (I10) for both PikeVM captures and BacktrackVM results, run in CI on every push for a representative fixture subset and nightly for the full corpus.
  • Soak: the examples/waf/ integration test run continuously against a synthetic traffic generator for 24 hours, asserting flat memory (I8) and zero unhandled errors.
  • Conformance: the full bucket list in §24 (parser, HIR, NFA, PikeVM, DFA, backtrack, leftmost-first/longest, lookaround, streaming, prefilter, set, cross-engine, ReDoS, adversarial) gated in conformance.yml on every push.
  • Performance-regression gating: the §31 M-table thresholds checked in CI against per-host baselines (benchmarks/results/<host>/, ADR-17); a regression beyond a documented tolerance blocks merge.
  • Golden-master snapshot testing: the parser (AST), HIR translator, and Thompson construction each check their output against a byte-stable snapshot corpus (§13.4, §14.4, §15.4) — any accidental behavior change shows up as a snapshot diff in code review, before it ever reaches a runtime fixture.
  • Cross-host determinism testing: the Unicode-table and NFA-bytecode snapshot checks (I13) run on at least two distinct CI runner architectures to catch any accidental host-dependent nondeterminism (e.g. HashMap iteration order leaking into a snapshot).
  • Mutation-adjacent testing: the conformance corpus's negative fixtures (malformed patterns, rejected syntax, §8.9) are periodically reviewed for coverage gaps by deliberately mutating a passing pattern fixture (flip a Split branch order, drop a Capture instruction) and confirming the mutated bytecode fails at least one fixture — a lightweight substitute for full mutation testing that catches under-specified corpora.
  • Every invariant in §7 maps to at least one of the above; the cross_engine differential suite (I2, I6, I10) and the ReDoS regression suite (I5) are the two release-blocking gates.

32. Scalability Analysis

  • What stays constant: per-call memory (one arena reset per match, I8, O(1) amortized); the compiled Regex's own memory footprint (fixed after Regex::new).
  • What grows: DFA cache size with distinct-state count up to dfa_size_limit (then clears, §18.2); backtracking-VM step count with pattern ambiguity, bounded by backtrack_budget (§21); Unicode table memory with property-class variety used (bounded, checked-in, §4.2 style analysis in §35 C7).
  • Named bottlenecks in order: (1) the backtracking VM's step count for backreference-heavy patterns (bounded by budget, never unbounded); (2) lazy-DFA cache-clear frequency for patterns with high live-state variety; (3) literal-prefilter miss rate when the extractor finds no usable literal (LiteralStrategy::None, engine runs unassisted).
  • Horizontal scaling: trivial — Regex is Send + Sync, stateless per call; N host threads/processes each hold their own compiled Regex or share one behind an Arc, with zero coordination required.
  • Vertical scaling: more cores → more concurrent matches; no shared mutable state means no synchronization overhead scales with core count (P13).
  • Sharding/partitioning: not applicable — there is no persisted or partitioned state; a RegexSet with many patterns is the only construct that "shards" work, and it does so via the shared-NFA construction (§19.2), not external partitioning.
  • Coordination overhead: zero at match time; the only coordination is at Regex::new compile time, which is single-threaded by construction and not on the hot path.
  • Pattern-set scaling (RegexSet): construction cost scales with the sum of pattern sizes (§35 C9); match cost scales with the shared NFA's live-state count, not linearly with pattern count in the common case — the practical scaling limit is cache-clear frequency (§18.2) on a RegexSet whose combined pattern set produces a high-live-state-variety NFA.
  • Memory scaling summary: total steady-state memory is Σ(compiled Regex sizes) + Σ(concurrent per-match arenas) (§35 C5, C12) — the first term is fixed per distinct pattern, the second scales with concurrency, and neither scales with haystack size beyond the streaming carry buffer (§35 C11).
  • The practical ceiling and the levers beyond it: the ceiling is the backtracking VM's budget-bounded worst case on backreference-heavy patterns (§4.1); the levers are (a) avoiding backreferences where possible, (b) raising dfa_size_limit for cache-thrashing patterns after confirming via §35 C2 that the raise is safe, (c) the deferred tagged-DFA (§38) for capture-heavy hot paths once profiling justifies the investment.

33. Mental Models & First Principles

  • MM1 — A regex is not a search procedure, it is an automaton; the engine's job is to build one and run it, never to search. Predicts: once the pattern is a DFA/NFA, matching is a bounded walk over bytes, never a re-tried search. Without it: you write a backtracker "because that's how the syntax reads" and rediscover exponential blowup independently, forgetting the Thompson/RE2 lineage exists precisely to avoid it. Applied: §15 (construction), §16 (simulation).
  • MM2 — NFA simulation is frontier-tracking: the live-state set, not any single path, is the object being advanced. Predicts: ambiguous alternations (§8.8) never need backtracking because every branch runs simultaneously as a deduplicated set. Without it: you write per-thread stacks that re-explore already-visited states, silently reintroducing exponential behavior. Applied: §16.2, I2.
  • MM3 — A lazy DFA is a memoized subset construction: the automaton being built lazily is provably the same one eager construction would produce. Predicts: correctness of the DFA reduces entirely to correctness of the canonicalization function, never to a separate algorithm needing its own proof. Without it: you treat the DFA as an independent, riskier "optimization" instead of the same automaton computed on demand. Applied: §18.1, I6.
  • MM4 — Capture groups are metadata riding on top of automaton state, not a separate computation. Predicts: the cost of tracking captures is proportional to the number of Split points that actually diverge, not to the pattern's total size. Without it: you clone full capture state on every step, producing quadratic blowup that looks like "just how regex works" instead of a fixable copy-on-write bug. Applied: §17.1–§17.2, I9.
  • MM5 — ReDoS is a property of the matching algorithm, not of any particular "bad" pattern. Predicts: the same pattern is instant on a linear-time engine and catastrophic on a backtracker — the fix is never "avoid bad patterns," it is "bound or eliminate backtracking." Without it: you chase a blocklist of "dangerous regex shapes" that is provably incomplete, instead of the structural fix. Applied: §21 (budget), §25 (T1), §2.2 (the Cloudflare incident).
  • MM6 — Engine selection is a compile-time proof obligation: prove which automaton class a pattern belongs to, then dispatch once. Predicts: every engine-selection bug is really a classification bug in one of four independent HIR analysis passes (§3.2), never a runtime heuristic gone wrong. Without it: you add "just check at match time" branches that make engine choice unauditable and break P3/P9. Applied: §19.2, I4.
  • MM7 — A literal prefilter is a cheaper automaton run in front of the real one — it must never change the answer, only the position you start looking from. Predicts: any prefilter bug is a correctness bug (a skipped match), never merely a performance regression. Without it: you tune the prefilter as if it were purely a speed optimization and miss that a wrong skip silently drops real matches. Applied: §18.5, I12.
  • MM8 — Cross-engine determinism is the oracle: "do the three engines agree" is a stronger and cheaper correctness check than any single engine's own unit tests. Predicts: the highest-value bug-catching activity in this codebase is differential testing between PikeVM/LazyDfa/BacktrackVM, not deeper unit coverage of any one engine alone. Without it: effort concentrates on making one engine "more correct" in isolation while a silent divergence ships. Applied: §8.14, §24.4, I2.
  • MM9 — A parenthesized group is a resource claim, not just a syntax marker: every capture group is a slot pair that must be allocated, tracked, and eventually reported, at a real memory cost. Predicts: the number of capture groups in a pattern is a real, bounded input to the per-thread memory footprint (§35 C5), not a free syntactic convenience. Without it: you treat (...) as costless and are surprised when a 100-group pattern's per-thread footprint shows up in a memory profile. Applied: §17.6, §35 C5.
  • MM10 — Every hard limit in this engine (size_limit, dfa_size_limit, backtrack_budget) is a proof obligation discharged once, at the boundary, never re-litigated deeper in the call stack. Predicts: once a pattern or match has passed its relevant limit check, every downstream component can assume the bound holds and skip re-validating it — this is what keeps the hot path free of redundant checks. Without it: you scatter defensive re-checks throughout the engine, adding overhead without adding safety, because the real guarantee already lives at the boundary. Applied: §15.2 (size_limit), §18.2 (dfa_size_limit), §21.2 (backtrack_budget).

  • RE2 — the one decision it made differently: backreferences are rejected outright, never gated. That wins for a security team unwilling to accept even a budgeted exponential path (ADR-03's rejected-alternative regime) — Google's own production stance for search-facing code.
  • PCRE2 — its differentiator: full lookaround and backreference support with no linear-time guarantee at all. That wins when syntax completeness matters more than worst-case latency and inputs are fully trusted (e.g. a developer's local text editor's "find" feature) — precisely the regime this project's own ADR-03 rejected for the default path.
  • Rust regex crate — the closest sibling; its differentiator is maturity and a battle-tested meta-engine selector refined over years of real-world pattern corpora. That wins whenever a production system should simply depend on the existing crate rather than re-deriving this blueprint's engine — this project exists to teach the internals that crate already ships.
  • Hyperscan — its differentiator: SIMD-parallel multi-pattern matching at the packet-inspection scale (thousands of patterns, line-rate throughput). That wins in deep packet inspection and intrusion detection where pattern count dominates and per-pattern capture semantics are secondary — exactly the regime this project's deferred FDR-style prefilter (§38) targets without yet committing to Hyperscan's full architecture.

Synthesis: the four comparison systems occupy two independent axes — worst-case guarantee (RE2/this engine/Rust regex linear-time vs PCRE2 unbounded) and semantic richness vs pattern-count scale (single-pattern captures/lookaround here vs Hyperscan's multi-pattern existence-only matching). This blueprint deliberately sits at the linear-time, semantically-rich corner because that is the corner none of the other four systems occupy simultaneously — RE2 gives up backreferences entirely, PCRE2 gives up the time bound, and Hyperscan gives up per-pattern capture semantics.

35. Back-of-Envelope Capacity Model

  • C1 — NFA bytecode size from pattern length. A pattern of L bytes produces roughly 2–4 instructions per meta-character (Thompson fragments, §8.3); at L = 1 KB (a large but real pattern) and 4 bytes/instruction average, bytecode size ≈ 1024 × 3 × 4 ≈ 12 KB — formula: bytecode_bytes ≈ L × k_instr × instr_size. Conclusion: well under the 10 MB size_limit (§4) with more than 800× headroom for pathological unrolling before the cap fires.
  • C2 — DFA reachable-state ceiling from live NFA states. Worst case 2^k subsets for k live states; at the dfa_size_limit = 8 MB and ~64 bytes/state (§4.2), the cache holds 8×10^6/64 ≈ 125,000 states — formula: max_cached_states = dfa_size_limit / bytes_per_state. Conclusion: a pattern needs k ≥ 17 live states before 2^k could exceed the cache (2^17 ≈ 131,072) — most real patterns (k < 50 typically, but with far fewer reachable distinct subsets in practice) never approach this, confirming the cap is a safety net, not a routine limiter.
  • C3 — Backtracking-VM worst-case wall time from the step budget. At budget = 1,000,000 steps and an estimated ~5 ns/step (frame push/pop + dispatch), worst case is 10^6 × 5×10^-9 s = 5 ms — formula: t_worst ≈ budget × t_step. Conclusion: consistent with the M7 target (≤ 100 ms or Err(Budget), §31) with 20× headroom, confirming the default budget is conservative relative to the latency target.
  • C4 — Prefilter scan time from the 1 GB/s target. A 200-byte haystack line scans in 200 / 10^9 s = 200 ns (§4.3) — formula: t_scan = size_bytes / throughput. Conclusion: three orders of magnitude below the ≤100 µs p99 target (M6, §31); the NFA/DFA confirmation step at the (rare) candidate positions dominates the real latency budget, not the prefilter.
  • C5 — Per-match arena size from thread count × slot count. At k = 50 live NFA states (a moderately complex pattern) and g = 10 capture groups (2g = 20 slots at 8 bytes each = 160 bytes/thread), peak arena use ≈ k × 160 B = 8 KB — formula: arena_bytes ≈ k × (slots × 8B + overhead). Conclusion: trivially bounded per match (I8); at 10,000 concurrent matches (one arena each, no sharing) total transient memory ≈ 80 MB, well within typical service memory budgets.
  • C6 — p99 latency composition on a compiled-at-startup pattern. At a 4 KB haystack and the PikeVM floor (M4, ≥100 MB/s), scan time ≈ 4096 / (100×10^6) s ≈ 41 µs — formula: t_scan = haystack_bytes / throughput_floor. Conclusion: under the ≤100 µs p99 target (M6, §31) with roughly 2.4× headroom even at the conservative PikeVM-only floor; the lazy-DFA/one-pass paths (§18–§19) only improve on this.
  • C7 — Unicode table memory footprint. The generated tables (general category, script, case folding, word/grapheme/line break, §14) total on the order of a few hundred KB to low single-digit MB as checked-in static data (ADR-14) — formula: table_bytes ≈ Σ(ranges_per_table × bytes_per_range_entry). Conclusion: negligible relative to the size_limit/dfa_size_limit budgets (§4); the cost is paid once at binary-link time, never per match.
  • C8 — Boyer-Moore average-case skip distance. For a literal of length m over an alphabet of size σ (≈ 256 for bytes), the average skip is ≈ m on a random haystack (the bad-character rule's expected behavior) — formula: avg_skip ≈ min(m, σ). Conclusion: for a typical 4–8 byte literal, the effective scan rate approaches throughput / avg_skip⁻¹, which is exactly why the 1 GB/s target (M1) is only realistic when a meaningful required literal exists — confirming ADR-08's rationale.
  • C9 — Aho-Corasick automaton size from literal count. For p literals of average length m̄, the automaton has O(p × m̄) states — at p = 20 alternation literals averaging m̄ = 6 bytes, ≈ 120 states, each a small fixed-size transition row — formula: ac_states ≈ p × m̄. Conclusion: trivially within the dfa_size_limit-scale budgets (§4) even for large RegexSets; construction cost is linear and paid once at Regex::new time (§19.2).
  • C10 — Compile-time bound from pattern size. Parse + HIR + Thompson construction is linear in pattern length; at L = 1 KB and the M5 target (≤1 ms, §31), the implied throughput floor is ≥ 1 MB/s of pattern text compiled — formula: t_compile ≈ L / compile_throughput. Conclusion: consistent with typical patterns (tens to low hundreds of bytes) compiling in well under 100 µs, leaving the full 1 ms budget as headroom for larger, generated patterns (e.g. a large RegexSet).
  • C11 — Streaming carry-buffer bound from max_match_len(). For a pattern with a derivable maximum match length M_max bytes, the carry buffer is bounded by M_max — for a typical bounded pattern (M_max ≈ 256 bytes), the buffer is negligible; for an unbounded pattern (a*), the documented default cap (e.g. 64 KB) applies instead — formula: carry_buffer_bytes = min(M_max, default_cap). Conclusion: the cap is what prevents T12 (streaming carry-buffer exhaustion) from being an unbounded-memory DoS surface.
  • C12 — Concurrent-match memory ceiling from arena size × concurrency. At the C5 per-match arena estimate (~8 KB) and C = 10,000 concurrent matches, total transient memory ≈ 8 KB × 10,000 = 80 MB — formula: total_mem ≈ arena_bytes × C. Conclusion: the practical ceiling (§32) is not memory at realistic concurrency levels; the backtracking-VM step budget (C3) and the DFA cache-clear rate (C2) are the real bottlenecks long before per-match memory becomes one.

37. Alternative Architectures (Roads Not Taken)

37.1 Pure Backtracking Engine (vs the NFA/DFA Hybrid)

  pattern -> parse -> AST -> direct recursive backtracker over the AST
  match(pos): try each alternative in order, recurse; on failure, backtrack
  (NO automaton is ever built; the AST itself is the "program")
  • Regime where it wins: small patterns, pervasive backreferences/lookaround, fully trusted patterns and inputs (e.g. a text editor's local "find" feature) where syntax completeness and implementation simplicity matter more than worst-case latency.
  • Real system: PCRE2 and Python's re module embody this.
  • Why rejected: it has no worst-case time bound at all — the exact property this blueprint exists to guarantee away (P1, I1). Adopting it would mean every pattern, not just backreference patterns, is exposed to the Cloudflare-2019 class of incident (§2.2).

37.2 Eager, Fully-Precomputed DFA (vs Lazy Construction)

  compile time: full subset construction -> complete DFA table, ALL states materialized
  match time:   pure table lookup, zero construction work per match
  • Regime where it wins: a small, fixed alphabet and a fixed, small pattern set compiled once and reused billions of times (e.g. a lexer generator's token rules, or grep's classic fixed-pattern fast path) where the eager compile cost amortizes across enormous match volume and the state count is provably small.
  • Real system: classic lex/flex-generated lexers and older grep implementations embody this.
  • Why rejected: worst-case state count is 2^k in the number of live NFA states (§35 C2); for the general, user-supplied patterns this engine must support, eager construction risks unbounded compile-time and memory blowup before a single match runs — exactly what the lazy, cache-bounded approach (§18) avoids.

37.3 SIMD-Parallel Multi-Pattern Automaton (vs a Single-Pattern-Optimized Core)

  many patterns -> Rose/FDR-style automaton compiled ahead of time
  match: SIMD-parallel byte scanning across ALL patterns simultaneously
  • Regime where it wins: deep packet inspection and intrusion detection where pattern count is in the thousands, throughput must sustain line-rate, and per-pattern capture semantics are secondary to existence/position reporting.
  • Real system: Hyperscan embodies this.
  • Why rejected (partially deferred): it is a fundamentally different optimization target — many patterns, minimal per-pattern semantics — versus this project's single-pattern-rich-semantics focus (captures, both leftmost modes, lookaround, backreferences). The literal-extraction strategy is borrowed (§34); the full SIMD/FDR architecture is a registered deferred feature (§38), not a rejected-forever one.

37.4 Derivative-Based Symbolic Matching (vs an Explicit Automaton)

  pattern -> symbolic regex value
  match(input): repeatedly compute the Brzozowski derivative of the regex
                w.r.t. each input symbol; accept if the final derivative is nullable
  • Regime where it wins: symbolic reasoning over infinite or symbolic alphabets (formal verification, symbolic execution engines), or academic settings where compositional simplicity of the algorithm matters more than raw throughput.
  • Real system: the academic "symbolic automata" line of work (Brzozowski derivatives, D'Antoni & Veanes) and .NET's non-backtracking regex engine (which uses a derivative-based construction internally) embody this.
  • Why rejected: derivative computation per input symbol is elegant but has historically required careful caching/minimization to match hand-tuned Thompson/subset-construction engines on raw byte throughput; the RE2/rust-regex lineage this project follows has a longer track record at the specific throughput targets in §4, and Thompson construction's fixed fragment shapes (§8.3) are simpler to teach and to fuzz.

Synthesis: each rejected architecture optimizes a dimension this blueprint deliberately does not: §37.1 optimizes implementation simplicity at the cost of the worst-case guarantee; §37.2 optimizes match-time cost at the cost of unbounded compile-time risk; §37.3 optimizes pattern-count scale at the cost of per-pattern semantics; §37.4 optimizes compositional elegance at the cost of a shorter production track record. The Thompson-NFA-plus-lazy-DFA hybrid (ADR-02) is the point in this design space that keeps the worst-case guarantee (P1) while still supporting rich per-pattern semantics (captures, both leftmost modes, lookaround) — the specific combination none of the four alternatives deliver simultaneously.

39. Glossary

  • NFA (Nondeterministic Finite Automaton): an automaton where a state may have multiple (or zero-width epsilon) transitions on the same input; Thompson construction produces one per pattern (§15).
  • DFA (Deterministic Finite Automaton): an automaton with exactly one transition per state per input symbol; the lazy DFA (§18) computes one on demand.
  • Thompson construction: the algorithm lowering a regex AST/HIR to an epsilon-NFA via fixed per-operator fragment rules (§8.3, Thompson 1968).
  • Subset construction: the classical algorithm converting an NFA to an equivalent DFA by treating sets of NFA states as single DFA states; the lazy DFA computes this incrementally (§18.1).
  • Epsilon closure: the set of NFA states reachable from a given state via zero-width (epsilon) transitions alone; computed on every PikeVM step (§16.2).
  • PikeVM: the thread-based NFA simulation engine tracking a deduplicated frontier of live states; the correctness ground truth (§16).
  • Thread: in the PikeVM, one live NFA state plus its capture-slot vector, tracked as part of the current frontier (§16.1).
  • Lazy DFA: a DFA whose states are computed and cached on demand rather than precomputed eagerly (§18).
  • DFA cache: the bounded map from canonicalized NFA state-sets to DFA states, capped by dfa_size_limit (§11.8).
  • Cache clear: the lazy DFA's eviction policy — clear the whole cache and rebuild from the start state when the cap is exceeded, rather than per-state LRU (§18.2).
  • Backtracking VM: the engine of last resort supporting backreferences and variable-width lookbehind, bounded by an explicit step budget (§21).
  • Budget: the finite step count a BacktrackVM::execute call may consume before returning Err(Budget) (§21.2).
  • ReDoS (Regular Expression Denial of Service): an attack exploiting a backtracking engine's unbounded worst-case time on an adversarial input (§25, Davis et al. 2018).
  • Catastrophic backtracking: the specific failure mode where a backtracking engine explores combinatorially many partitions of an ambiguous match, as in (a+)+$ (§4.1, §8.11).
  • Leftmost-first semantics: PCRE-style matching where the first successful alternative/greedy path wins (§8.6).
  • Leftmost-longest semantics: POSIX-style matching where the longest possible match at the earliest position wins (§8.6).
  • Capture group: a parenthesized subpattern whose matched span is recorded; numbered by source order, slots 2i/2i+1 (§8.5).
  • Capture slot: one of the two integer offsets (start/end) recorded per capture group in a SlotVec (§8.5).
  • Copy-on-write slot vector: a SlotVec sharing strategy where a Split's two resulting threads share one slot vector until either writes, at which point it copies (§17.1, I9).
  • Backreference: a pattern construct (\1–\9) matching the same text a numbered capture group previously matched; only executable on BacktrackVM (§8.4, P7).
  • Lookahead / lookbehind (lookaround): zero-width assertions checking the pattern before/after the current position without consuming input; four polarities (§20).
  • Fixed-width lookbehind: a lookbehind whose inner pattern matches a statically-known byte length, executable on the NFA path (§20.2).
  • Variable-width lookbehind: a lookbehind whose inner pattern's match length is not statically fixed; gated to BacktrackVM (§20.2).
  • Byte class: an interned, value-deduplicated set of byte ranges a single NFA instruction can accept (§8.4, §15.2).
  • HIR (High-level Intermediate Representation): the desugared, semantics-explicit IR every engine consumes, produced from the AST (§8.2, §11.5).
  • AST (Abstract Syntax Tree): the direct parse-tree representation of a pattern, produced by the recursive-descent parser (§11.4).
  • Literal extraction: the HIR analysis pass identifying required prefix/suffix/inner literal substrings for prefiltering (§18.5).
  • Prefilter / LiteralStrategy: the Boyer-Moore or Aho-Corasick scan run ahead of the NFA/DFA to skip impossible match positions (§18.5, P10).
  • Boyer-Moore: the single-literal string-search algorithm using a bad-character skip table (§5.2, Boyer & Moore 1977).
  • Aho-Corasick: the multi-literal string-search automaton matching several literals in one pass (§5.2, Aho & Corasick 1975).
  • One-pass DFA: a compile-time optimization for patterns whose NFA has at most one live outgoing edge per byte class at every state (§19.2, ADR-18).
  • Tagged-DFA: Laurikari's construction adding capture-tracking "tags" to DFA transitions; deferred in this blueprint (§38, §17.5).
  • Engine selector / meta engine: the compile-time component choosing PikeVM, LazyDfa, or BacktrackVM for a given pattern (§3.2, §19.2).
  • RegexSet: a construct matching several patterns simultaneously against one haystack, reporting the set of matching pattern indices (§11.8, I15).
  • Cross-engine determinism: the invariant that every eligible engine returns an identical result for the same input (§8.14, I2).
  • Cursor: the sole owner of codepoint-boundary logic over a haystack, isolating every engine from raw UTF-8 indexing (§11.7, P12).
  • Scratch / arena: the per-match, reset-per-call memory pool backing thread lists, DFA transient state, and capture slots (§11.7, P13, I8).
  • Streaming match / StreamMatcher: the incremental matcher operating over a BufRead-fed sequence of chunks with a bounded carry buffer (§22.2).
  • regex! macro: the build-time procedural macro compiling a pattern at Rust compile time into a const/static program (§22.2, P11).
  • Conformance bucket: a named group of fixtures in conformance/corpora/ gating a specific correctness surface, reported in conformance.report.json (§11.9, §24).
  • UTS#18 / UAX#29 / UAX#14: the Unicode Technical Standard/Annexes governing regex property classes, grapheme-cluster boundaries, and line-breaking respectively (§5.4).
  • size_limit / dfa_size_limit / backtrack_budget: the three independent hard caps bounding bytecode size, DFA cache memory, and backtracking steps respectively (§11.2, §4).
  • PhaseDeferred: the typed marker anchoring a feature not yet built to a real section and a row in the Deferred Features Register (§38).
  • Anchored search: a search seeded only at the haystack's start position (or another single fixed position), as opposed to an unanchored search which tries every starting position (§16.2).
  • Zero-width assertion: a match condition (an anchor or lookaround) that consumes no input byte — ^, $, \b, and all four lookaround forms are zero-width (§8.4).
  • Greedy vs lazy quantifier: a greedy quantifier (*, +, {m,n}) prefers to match as much as possible; a lazy quantifier (*?, +?, {m,n}?) prefers as little as possible; encoded purely by Split branch order (§8.3).
  • Case folding: normalizing a literal or class to an equivalence class under case-insensitivity, per UTS#18 RL1.5 simple fold (§14.1).
  • Grapheme cluster: a user-perceived character, potentially spanning multiple codepoints, matched by \X per UAX#29 (§14.6).
  • Canonicalization (DFA state): the process of reducing an NFA state-set to a stable, hashable representation (a sorted Vec<StateId>) so equal state-sets map to the same cached DFA state (§18.6).
  • Determinism test / determinism loop: the 1,024-repeat-run check confirming a (pattern, input, config) triple produces a byte-identical result every time (§7 I10).
  • Sealed gate: the release-blocking bar requiring a clean 30-day fuzz canary, a green ReDoS regression suite, and met performance targets (§24.10, §1.11).
  • One-pass pattern: a pattern whose NFA has at most one live outgoing edge per byte class at every state, admitting a small, dense, non-lazy DFA at construction time (§19.2).
  • Shared-NFA construction: the Thompson construction technique underlying RegexSet, where multiple patterns compile into one NFA with per-pattern Match{pattern_id} termini (§8.15, §19.2).
  • Reference hardware: the single pinned host that is authoritative for performance-regression gating, documented per release under benchmarks/results/reference/ (ADR-25, §31.1).
  • Divergence fixture: a cross_engine corpus entry recording a case where two engines disagreed, committed with its ADR disposition rather than silently discarded (§18.4, §24.9).
