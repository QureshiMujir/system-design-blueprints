33. Mental Models & First Principles

  • MM1 — A regex is not a search procedure, it is an automaton; the engine's job is to build one and run it, never to search. Predicts: once the pattern is a DFA/NFA, matching is a bounded walk over bytes, never a re-tried search. Without it: you write a backtracker "because that's how the syntax reads" and rediscover exponential blowup independently, forgetting the Thompson/RE2 lineage exists precisely to avoid it. Applied: §15 (construction), §16 (simulation).
  • MM2 — NFA simulation is frontier-tracking: the live-state set, not any single path, is the object being advanced. Predicts: ambiguous alternations (§8.8) never need backtracking because every branch runs simultaneously as a deduplicated set. Without it: you write per-thread stacks that re-explore already-visited states, silently reintroducing exponential behavior. Applied: §16.2, I2.
  • MM3 — A lazy DFA is a memoized subset construction: the automaton being built lazily is provably the same one eager construction would produce. Predicts: correctness of the DFA reduces entirely to correctness of the canonicalization function, never to a separate algorithm needing its own proof. Without it: you treat the DFA as an independent, riskier "optimization" instead of the same automaton computed on demand. Applied: §18.1, I6.
  • MM4 — Capture groups are metadata riding on top of automaton state, not a separate computation. Predicts: the cost of tracking captures is proportional to the number of Split points that actually diverge, not to the pattern's total size. Without it: you clone full capture state on every step, producing quadratic blowup that looks like "just how regex works" instead of a fixable copy-on-write bug. Applied: §17.1–§17.2, I9.
  • MM5 — ReDoS is a property of the matching algorithm, not of any particular "bad" pattern. Predicts: the same pattern is instant on a linear-time engine and catastrophic on a backtracker — the fix is never "avoid bad patterns," it is "bound or eliminate backtracking." Without it: you chase a blocklist of "dangerous regex shapes" that is provably incomplete, instead of the structural fix. Applied: §21 (budget), §25 (T1), §2.2 (the Cloudflare incident).
  • MM6 — Engine selection is a compile-time proof obligation: prove which automaton class a pattern belongs to, then dispatch once. Predicts: every engine-selection bug is really a classification bug in one of four independent HIR analysis passes (§3.2), never a runtime heuristic gone wrong. Without it: you add "just check at match time" branches that make engine choice unauditable and break P3/P9. Applied: §19.2, I4.
  • MM7 — A literal prefilter is a cheaper automaton run in front of the real one — it must never change the answer, only the position you start looking from. Predicts: any prefilter bug is a correctness bug (a skipped match), never merely a performance regression. Without it: you tune the prefilter as if it were purely a speed optimization and miss that a wrong skip silently drops real matches. Applied: §18.5, I12.
  • MM8 — Cross-engine determinism is the oracle: "do the three engines agree" is a stronger and cheaper correctness check than any single engine's own unit tests. Predicts: the highest-value bug-catching activity in this codebase is differential testing between PikeVM/LazyDfa/BacktrackVM, not deeper unit coverage of any one engine alone. Without it: effort concentrates on making one engine "more correct" in isolation while a silent divergence ships. Applied: §8.14, §24.4, I2.
  • MM9 — A parenthesized group is a resource claim, not just a syntax marker: every capture group is a slot pair that must be allocated, tracked, and eventually reported, at a real memory cost. Predicts: the number of capture groups in a pattern is a real, bounded input to the per-thread memory footprint (§35 C5), not a free syntactic convenience. Without it: you treat (...) as costless and are surprised when a 100-group pattern's per-thread footprint shows up in a memory profile. Applied: §17.6, §35 C5.
  • MM10 — Every hard limit in this engine (size_limit, dfa_size_limit, backtrack_budget) is a proof obligation discharged once, at the boundary, never re-litigated deeper in the call stack. Predicts: once a pattern or match has passed its relevant limit check, every downstream component can assume the bound holds and skip re-validating it — this is what keeps the hot path free of redundant checks. Without it: you scatter defensive re-checks throughout the engine, adding overhead without adding safety, because the real guarantee already lives at the boundary. Applied: §15.2 (size_limit), §18.2 (dfa_size_limit), §21.2 (backtrack_budget).

  • Aho, Lam, Sethi, Ullman — Compilers: Principles, Techniques, and Tools (2nd ed., "Dragon Book"), ch. 3 (lexical analysis: NFA/DFA, subset construction, Thompson construction). The formal foundation for §15 and §18; applied in Phase 3 (§15) and Phase 6 (§18).
  • Jeffrey Friedl — Mastering Regular Expressions (3rd ed.), ch. 4 (mechanics), ch. 6 (crafting an efficient expression), ch. 9 (a case study of an optimized engine). The syntax/semantics reference and the backtracking-engine corner cases that motivate the gated backtracking VM; applied in Phase 1 (§13) and Phase 9 (§21).
  • Robert Sedgewick, Kevin Wayne — Algorithms (4th ed.), ch. 5.4 (substring search: Boyer-Moore, Rabin-Karp). The single-literal fast path; applied in Phase 6 (§18.5).
  • Thomas Cormen et al. — Introduction to Algorithms (3rd ed.), ch. 32 (string matching). Complexity-analysis grounding for the literal-extraction prefilter; applied in Phase 6 (§18).
  • Jim Blandy, Jason Orendorff, Leonora Tindall — Programming Rust (2nd ed.), the ownership/enums/lifetimes chapters. The arena/scratch design and the Cursor's borrowed-slice model; applied in Phase 0 (§12) and Phase 4 (§16).
  • Nicholas Nethercote — The Rust Performance Book (community-maintained reference). Allocation, profiling, and benchmarking methodology; applied in Phase 6 (§18) and Performance Engineering (§31).

Glossary (§39) · 55 terms · site-wide glossary

NFA (Nondeterministic Finite Automaton):
an automaton where a state may have multiple (or zero-width epsilon) transitions on the same input; Thompson construction produces one per pattern (§15).
DFA (Deterministic Finite Automaton):
an automaton with exactly one transition per state per input symbol; the lazy DFA (§18) computes one on demand.
Thompson construction:
the algorithm lowering a regex AST/HIR to an epsilon-NFA via fixed per-operator fragment rules (§8.3, Thompson 1968).
Subset construction:
the classical algorithm converting an NFA to an equivalent DFA by treating sets of NFA states as single DFA states; the lazy DFA computes this incrementally (§18.1).
Epsilon closure:
the set of NFA states reachable from a given state via zero-width (epsilon) transitions alone; computed on every PikeVM step (§16.2).
PikeVM:
the thread-based NFA simulation engine tracking a deduplicated frontier of live states; the correctness ground truth (§16).
Thread:
in the PikeVM, one live NFA state plus its capture-slot vector, tracked as part of the current frontier (§16.1).
Lazy DFA:
a DFA whose states are computed and cached on demand rather than precomputed eagerly (§18).
DFA cache:
the bounded map from canonicalized NFA state-sets to DFA states, capped by dfa_size_limit (§11.8).
Cache clear:
the lazy DFA's eviction policy — clear the whole cache and rebuild from the start state when the cap is exceeded, rather than per-state LRU (§18.2).
Backtracking VM:
the engine of last resort supporting backreferences and variable-width lookbehind, bounded by an explicit step budget (§21).
Budget:
the finite step count a BacktrackVM::execute call may consume before returning Err(Budget) (§21.2).
ReDoS (Regular Expression Denial of Service):
an attack exploiting a backtracking engine's unbounded worst-case time on an adversarial input (§25, Davis et al. 2018).
Catastrophic backtracking:
the specific failure mode where a backtracking engine explores combinatorially many partitions of an ambiguous match, as in (a+)+$ (§4.1, §8.11).
Leftmost-first semantics:
PCRE-style matching where the first successful alternative/greedy path wins (§8.6).
Leftmost-longest semantics:
POSIX-style matching where the longest possible match at the earliest position wins (§8.6).
Capture group:
a parenthesized subpattern whose matched span is recorded; numbered by source order, slots 2i/2i+1 (§8.5).
Capture slot:
one of the two integer offsets (start/end) recorded per capture group in a SlotVec (§8.5).
Copy-on-write slot vector:
a SlotVec sharing strategy where a Split's two resulting threads share one slot vector until either writes, at which point it copies (§17.1, I9).
Backreference:
a pattern construct (\1–\9) matching the same text a numbered capture group previously matched; only executable on BacktrackVM (§8.4, P7).
Lookahead / lookbehind (lookaround):
zero-width assertions checking the pattern before/after the current position without consuming input; four polarities (§20).
Fixed-width lookbehind:
a lookbehind whose inner pattern matches a statically-known byte length, executable on the NFA path (§20.2).
Variable-width lookbehind:
a lookbehind whose inner pattern's match length is not statically fixed; gated to BacktrackVM (§20.2).
Byte class:
an interned, value-deduplicated set of byte ranges a single NFA instruction can accept (§8.4, §15.2).
HIR (High-level Intermediate Representation):
the desugared, semantics-explicit IR every engine consumes, produced from the AST (§8.2, §11.5).
AST (Abstract Syntax Tree):
the direct parse-tree representation of a pattern, produced by the recursive-descent parser (§11.4).
Literal extraction:
the HIR analysis pass identifying required prefix/suffix/inner literal substrings for prefiltering (§18.5).
Prefilter / LiteralStrategy:
the Boyer-Moore or Aho-Corasick scan run ahead of the NFA/DFA to skip impossible match positions (§18.5, P10).
Boyer-Moore:
the single-literal string-search algorithm using a bad-character skip table (§5.2, Boyer & Moore 1977).
Aho-Corasick:
the multi-literal string-search automaton matching several literals in one pass (§5.2, Aho & Corasick 1975).
One-pass DFA:
a compile-time optimization for patterns whose NFA has at most one live outgoing edge per byte class at every state (§19.2, ADR-18).
Tagged-DFA:
Laurikari's construction adding capture-tracking "tags" to DFA transitions; deferred in this blueprint (§38, §17.5).
Engine selector / meta engine:
the compile-time component choosing PikeVM, LazyDfa, or BacktrackVM for a given pattern (§3.2, §19.2).
RegexSet:
a construct matching several patterns simultaneously against one haystack, reporting the set of matching pattern indices (§11.8, I15).
Cross-engine determinism:
the invariant that every eligible engine returns an identical result for the same input (§8.14, I2).
Cursor:
the sole owner of codepoint-boundary logic over a haystack, isolating every engine from raw UTF-8 indexing (§11.7, P12).
Scratch / arena:
the per-match, reset-per-call memory pool backing thread lists, DFA transient state, and capture slots (§11.7, P13, I8).
Streaming match / StreamMatcher:
the incremental matcher operating over a BufRead-fed sequence of chunks with a bounded carry buffer (§22.2).
regex! macro:
the build-time procedural macro compiling a pattern at Rust compile time into a const/static program (§22.2, P11).
Conformance bucket:
a named group of fixtures in conformance/corpora/ gating a specific correctness surface, reported in conformance.report.json (§11.9, §24).
UTS#18 / UAX#29 / UAX#14:
the Unicode Technical Standard/Annexes governing regex property classes, grapheme-cluster boundaries, and line-breaking respectively (§5.4).
size_limit / dfa_size_limit / backtrack_budget:
the three independent hard caps bounding bytecode size, DFA cache memory, and backtracking steps respectively (§11.2, §4).
PhaseDeferred:
the typed marker anchoring a feature not yet built to a real section and a row in the Deferred Features Register (§38).
Anchored search:
a search seeded only at the haystack's start position (or another single fixed position), as opposed to an unanchored search which tries every starting position (§16.2).
Zero-width assertion:
a match condition (an anchor or lookaround) that consumes no input byte — ^, $, \b, and all four lookaround forms are zero-width (§8.4).
Greedy vs lazy quantifier:
a greedy quantifier (*, +, {m,n}) prefers to match as much as possible; a lazy quantifier (*?, +?, {m,n}?) prefers as little as possible; encoded purely by Split branch order (§8.3).
Case folding:
normalizing a literal or class to an equivalence class under case-insensitivity, per UTS#18 RL1.5 simple fold (§14.1).
Grapheme cluster:
a user-perceived character, potentially spanning multiple codepoints, matched by \X per UAX#29 (§14.6).
Canonicalization (DFA state):
the process of reducing an NFA state-set to a stable, hashable representation (a sorted Vec<StateId>) so equal state-sets map to the same cached DFA state (§18.6).
Determinism test / determinism loop:
the 1,024-repeat-run check confirming a (pattern, input, config) triple produces a byte-identical result every time (§7 I10).
Sealed gate:
the release-blocking bar requiring a clean 30-day fuzz canary, a green ReDoS regression suite, and met performance targets (§24.10, §1.11).
One-pass pattern:
a pattern whose NFA has at most one live outgoing edge per byte class at every state, admitting a small, dense, non-lazy DFA at construction time (§19.2).
Shared-NFA construction:
the Thompson construction technique underlying RegexSet, where multiple patterns compile into one NFA with per-pattern Match{pattern_id} termini (§8.15, §19.2).
Reference hardware:
the single pinned host that is authoritative for performance-regression gating, documented per release under benchmarks/results/reference/ (ADR-25, §31.1).
Divergence fixture:
a cross_engine corpus entry recording a case where two engines disagreed, committed with its ADR disposition rather than silently discarded (§18.4, §24.9).
