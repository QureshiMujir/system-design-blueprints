In one paragraph

A regular-expression engine takes a pattern such as (?i)foo\d+ and a piece of text, and reports whether, where and how the pattern matches. This blueprint designs one from scratch as an embeddable Rust library, not a service, in the RE2 and Rust regex tradition (§1.1, §1.3). Its headline promise: any pattern without backreferences or unsupported lookaround runs in O(n·m) time, where n is the input size in bytes and m is the compiled program size, on every input, including hostile ones (§1.1, I1). That promise is what defeats ReDoS, the slowdown an attacker causes with a crafted input. Programs that match patterns against untrusted text, such as log pipelines and web firewalls, embed it (§1.4).

The problem, concretely

On 2 July 2019 Cloudflare's edge network went down globally for 27 minutes because one WAF (web application firewall) rule hit catastrophic backtracking on a crafted request body, saturating every CPU core at once (§2.2). Engines that already ran in linear time (RE2, Rust's regex, Go's regexp) were structurally immune (§2.2).

The pattern class behind it is easy to show. Take (a+)+$ against 30 a characters followed by one mismatching character. A naive backtracker tries every way of splitting the run of as between the inner and outer + before it gives up: 2^30, about 10^9 frames at n = 30 (§4.1, §8.11). The obvious way to write a matcher is a recursive search that tries each alternative and backs up on failure, because "that's how the syntax reads" (MM1). That search has no worst-case time bound at all (§37.1).

The blueprint's answer is MM5: ReDoS is a property of the matching algorithm, not of any particular "bad" pattern. The same pattern is instant on a linear-time engine and catastrophic on a backtracker, so a blocklist of dangerous patterns is the wrong fix; bounding or removing backtracking is the right one (MM5). Two further pressures shape the design. Eagerly building the whole deterministic automaton up front can need 2^k states (§37.2, §35 C2). And backreferences (\1) push the language outside the regular languages, which the stack-free Thompson NFA cannot match, so they are gated to a separate, budget-bounded path (§2.7 C1, C2, ADR-03).

How it works, end to end

Follow one pattern and one search through the boxes of §3.1:

 pattern ─► regex-syntax parser ─► AST ─► HIR desugar + Unicode resolve ─► Thompson NFA bytecode
                                                              │
        analysis passes (anchored? one-pass? backref? lookaround?) + literal extraction
                                                              │
                                  meta selector (once, at Regex::new) ──► PikeVM | LazyDfa | BacktrackVM
 haystack ─► input layer (Cursor / Stream) ───────────────────────────────────────────┘
                                                              ▼
                            public API: Regex / RegexSet / Match / Captures

The walk in §3.4 uses Regex::new(r"(?i)foo\d+") then find("xxx FOO123 yyy"):

  1. Parse. regex-syntax has a hand-written recursive-descent parser that builds an AST (a tree mirroring the pattern's syntax). Every node carries a byte-range Span, and anything the parser cannot express is rejected immediately with a typed ParseErrorKind, never a partial parse (§3.2, P15, §8.1).
  2. Desugar into the HIR. regex-syntax::hir (high-level intermediate representation) expands \d and \w, case-folds (?i), resolves Unicode properties against checked-in tables and merges class ranges (§3.2, §8.2). Every engine consumes this one HIR, so there are no "two parsers" (P2).
  3. Compile to an NFA. regex-automata lowers the HIR with Thompson construction into a flat bytecode of Byte, Class, Split, Capture, Look, Backref and Match instructions (§8.3, §8.4). For (?i)foo\d+ that is Byte/Class instructions, one Split for the +, and a Match (§3.4).
  4. Analyse once. Four independent HIR walks decide whether the pattern is anchored, one-pass, needs a backreference, or needs lookaround the NFA cannot express; every later decision reads those flags (§3.2).
  5. Extract literals. A prefilter pass finds literals the match must contain and builds a LiteralStrategy: Boyer-Moore for one literal, Aho-Corasick for several (§3.2, ADR-07, ADR-08). Here the required prefix is "foo", case-insensitive (§3.4).
  6. Select an engine, once. The meta selector picks PikeVM, lazy DFA, one-pass DFA or backtracking VM at Regex::new time and stores the choice as an immutable field readable through Regex::engine() (P3, §19.2). Here it picks the default, PikeVm + LazyDfa(opportunistic) (§3.4).
  7. Search. The prefilter skips ahead to the FOO at byte 4, the lazy DFA (or PikeVM) confirms and extends the match over 123, and the range 4..10 comes back (§3.4). The Cursor in the input layer is the only code that knows where a UTF-8 codepoint begins and ends (P12, I7). §3.4 adds that if the DFA's cache had filled mid-match, a regex.dfa.fallback trace event fires and the PikeVM finishes with an identical answer (§3.4, I6); §18.2 words the trigger differently (see the lazy DFA below).

A compiled Regex is Send + Sync and read-only after construction. Each call draws its thread lists and capture slots from its own Scratch arena, reset at call entry (§3.3, §3.6, P13, I8). The regex! macro (crate regex-macro) runs the same pipeline at build time for patterns known in advance (P11, §1.5). regex-cli holds the debug-ast, debug-hir and debug-nfa dumpers (§1.5).

The core ideas

Thompson construction: every operator becomes a fixed shape (§8.3, §15)

Each HIR node lowers to a small fragment with one entry and one exit. Literal(b) becomes Byte(b, exit); concatenation joins one fragment's exit to the next entry; alternation is a Split to both entries with both exits meeting; a* is s = Split(a.entry, exit) with a.exit → s; a+ puts the Split after the body; a capture wraps its body in Capture(2i, …) and Capture(2i+1, …) (§8.3). The Split instruction is an epsilon transition (it consumes no byte) and next_a is the preferred branch (§8.4). So greedy versus lazy is nothing but the order of the Split branches: a lazy quantifier swaps them (§8.3). Counted repetition a{m,n} is unrolled into m required copies plus n-m optional ones, which is why size_limit (default 10 MB of bytecode) exists (§8.2, §4).

PikeVM: advance the whole frontier, not one path (§3.5, §8.7, MM2)

The PikeVM (the NFA simulation engine) keeps a list of live NFA states, the frontier. For each input byte it builds the next list: advance every thread whose instruction accepts the byte, follow epsilon edges, and deduplicate by NFA StateId so two threads that reach the same state collapse into one (§3.5, §16.2). That single rule is why the simulation stays O(n·m) instead of exponential (§3.5, I2); the thread lists are sized once to the NFA's state count (§16.2). The dedup key is the state alone, never (state, slots), which §16.6 calls the single highest-value code-review question for this phase (§16.2, §16.6).

The trace in §8.15 shows it with a RegexSet of ["foo", "bar", "foo.*baz"] on "xx foobaz yy". At position 3 the threads for patterns 0 and 2 are both live, sharing the foo prefix. At position 6 pattern 0 reaches Match{0}; at position 9 pattern 2 reaches Match{2}; pattern 1 never has a live thread. The answer is {0, 2} (§8.15, I15). Unanchored search is the same loop with a fresh thread seeded at every position, equivalent to an implicit .*? prefix (§16.2).

Captures and the two "leftmost" rules (§8.5, §8.6, I9)

Group i writes its start and end offsets into slots 2i and 2i+1; slots 0 and 1 are the whole match (§8.5). Each thread carries its own slot vector, and the vector is copy-on-write: two threads from one Split share it, and the copy fires when they are about to diverge in what they write (§8.5); I9 words it as sharing "until either thread writes" (I9). The check is a fixture where two branches write the same slot at different positions and both values must survive (I9).

Under leftmost-first (the default, PCRE-like) the first thread to reach Match wins and the rest of the frontier is discarded (§8.6, §17.2). Under leftmost-longest (POSIX, opt-in through RegexBuilder::longest_match(true)) the simulation keeps running after the first Match and keeps the longest, breaking ties by earliest start (§8.6). It is the same engine with different bookkeeping, never a second algorithm (P6). The worked trace in §8.8 ((a|ab)(c|bcd)(d*) on abcd) is not reliable as an example: it ends with group 1 = ab and group 2 = bcd, which overlap inside the four-byte whole match, and its position-2 row says the a branch died even though a followed by bcd still fits the input (§8.8). Its capture values are not used here.

Lazy DFA: the same automaton, computed on demand under a cap (§8.10, §4.2, MM3)

A DFA has exactly one next state per byte. A DFA state here is a canonicalized set of NFA states, so the lazy DFA is the PikeVM's frontier, memoized (§3.5, §18.2). A transition on a byte is: advance every NFA state in the set, epsilon-close, canonicalize, then hit the cache or allocate a new entry (§18.2). In §8.10's trace, state S0 on f is a miss and allocates S1; S1 on o allocates S2; S2 on the second o is a hit. When the cache reaches dfa_size_limit (default 8 MB) the engine clears the whole cache and resumes from the start state, rather than evicting single entries (§8.10, §4, P4); I3's recovery is the same clear-and-rebuild (I3).

The blueprint words the hand-off to the PikeVM two ways. I6, the §4 recovery row and §3.4 say a cache exhaustion mid-match falls back to the PikeVM within the same match (I6, §4, §3.4), and §8.7 goes straight from CacheFull to FallbackToPikeVM (§8.7). §18.2 instead switches only if the cache clears three times within n bytes of one match, firing regex.dfa.fallback (§18.2, P9); §3.2 says "when the cache clears too often" (§3.2). Either way, the cross-engine bucket checks that the fallback never changes the answer (§18.2, I6). The DFA only reports yes/no plus a match boundary, so when captures are needed it finds the boundary first and then runs a PikeVM pass over only the matched substring (§18.2). The cache is also the one place the blueprint lets threads share mutable state: §4.4 says it is either private per Regex or shared behind a lock-free map, while §4's table and §3.3 say concurrent matches share no mutable state (§4.4, §4, §3.3).

Engine selection and the backreference fence (§19.2, I4, ADR-03)

The selector's decision order is fixed. A pattern that needs a backreference or NFA-unsupported lookaround routes to the backtracking VM, or is a construction error if the caller explicitly asked for PikeVm (I4, §19.2). On an explicit Backtrack request for a pattern that does not need it, the blueprint disagrees with itself: §19.2 and §11.10 make it an error, while §19.8 says the request is honored because "an explicit request always wins" (§19.2, §11.10, §19.8). A one-pass pattern (no NFA state has two outgoing edges accepting the same byte class) gets a small dense DFA built once at construction; otherwise the default is PikeVM plus lazy DFA (§19.2, ADR-18). Per §8.9, \1 with RegexBuilder::engine(PikeVm) returns ParseErrorKind::EngineUnsupported{needed: Backtrack, requested: PikeVm}. Nothing is rerouted silently (P7, P9, I4, I14).

The step budget: bounding the one unbounded path (§4.1, §21.2, P8, I5)

The backtracking VM is a textbook backtracker with one addition: every popped frame costs one step from an explicit budget, 1,000,000 by default and 100,000,000 at most (§4, §21.2). On exhaustion it returns Err(MatchError::Budget), never a partial answer and never a hang (§21.2, I14). The budget check lives in the dispatch loop, once per popped frame, so step counts do not change when handlers are refactored (§21.2, §21.6). For (a+)+$ the blueprint says the budget aborts at roughly n ≈ 20, long before the 2^n partitions would stall a core (§4.1). So the worst case is O(budget), a constant, not O(2^n) (§4.1, P8). By default that pattern never reaches the backtracking VM at all: it has no backreference, so it runs on the linear-time NFA path (§8.11, I4, P7).

The trade-offs — where engineers disagree

Matching model: NFA simulation plus lazy DFA (ADR-02)

Chosen: the RE2 model, an NFA simulation plus lazy DFA hybrid, because it is the only path that holds O(n·m) and so defeats ReDoS structurally (§9). Rejected: pure backtracking. When the rejected choice is right: a throwaway script matching trusted, hand-written patterns against small trusted inputs, where linear-time guarantees are irrelevant (§9).

Backreferences: gated and budgeted (ADR-03)

Chosen: accept backreferences but run them only on the budget-bounded backtracking VM, which keeps rust-regex-compatible syntax coverage (§9). Rejected: reject backreferences outright, RE2's own choice. When the rejected choice is right: a security-critical parser where even a budgeted exponential path is an unacceptable attack surface (§9, §34). The blueprint records this budget-bounded-but-nonzero worst case as accepted residual risk (§25).

Default match semantics: leftmost-first (ADR-04)

Chosen: leftmost-first, matching what most users expect from other languages (§9, P6). Rejected: leftmost-longest as the default. When the rejected choice is right: a POSIX-conformance tool such as grep -E or awk, whose users expect POSIX semantics unconditionally (§9). Leftmost-longest stays available as an opt-in on the same engine (§8.6).

Unicode by default (ADR-05)

Chosen: Unicode-aware matching (UTS#18 levels RL1.1 and RL1.2), because most callers match human text and \p{...} is a common ask (§9, P5). Rejected: bytes-only by default. When the rejected choice is right: a binary-protocol matcher such as packet inspection, where every byte value is meaningful and Unicode semantics are actively wrong (§9). Bytes mode is the opt-in and rejects \p{...} at parse time (P5).

Rollout order: PikeVM first, lazy DFA later (ADR-06)

Chosen: ship the PikeVM as the correctness ground truth first and add the lazy DFA later, to avoid debugging a DFA bug that is really a PikeVM capture bug (§9). Rejected: shipping both at once. When the rejected choice is right: when a second team can independently validate the DFA against an external oracle such as RE2 from day one (§9). On oracles the blueprint says two things: §4's assumptions list rust-regex's test suite plus RE2/PCRE2 as correctness oracles (§4), while §34 and §38 defer external oracles to after §24 (§34, §38).

Unicode tables: checked in, not generated (ADR-14)

Chosen: checked-in generated tables and a hermetic build, so a reviewer can read exactly what \p{L} means and I13 holds across hosts (§9, I13). Rejected: generate the tables at build time. When the rejected choice is right: when tracking Unicode point releases faster than a manual re-pin ADR cadence allows, for example a CI-triggered nightly regeneration (§9).

Roads not taken

Pure backtracking engine (§37.1): the AST itself is the program and failure means backing up. It wins for small patterns with pervasive backreferences and lookaround where patterns and input are fully trusted (PCRE2 and Python's re are the examples); it is rejected because it has no worst-case time bound (§37.1).

Eager, fully precomputed DFA (§37.2): all states built at compile time, pure table lookup at match time. It wins with a small fixed alphabet and a small fixed pattern set reused billions of times, such as lex/flex lexers; it is rejected because the state count can be 2^k, risking unbounded compile time and memory on user-supplied patterns (§37.2, §35 C2).

SIMD-parallel multi-pattern automaton (§37.3): Hyperscan's Rose/FDR design. It wins for deep packet inspection with thousands of patterns at line rate and little per-pattern capture semantics; it is partly deferred rather than rejected, and only the literal-extraction idea is borrowed (§37.3, §38).

Derivative-based symbolic matching (§37.4): compute Brzozowski derivatives of the pattern per input symbol instead of building an automaton. It wins for symbolic or infinite alphabets and academic settings; it is rejected here because the Thompson/RE2 lineage has a longer track record at the §4 throughput targets and is simpler to teach and fuzz (§37.4).

The deferred register (§38) holds the later features, among them tagged-DFA capture extraction, SIMD Boyer-Moore, reverse-NFA lookbehind and a JIT, each with a stated trigger.

What must never be false

  • I1: no-backreference patterns run in O(n·m) (NFA) or O(n) (lazy DFA) on any input; the ReDoS suite times every fixture (§24.4); regex.match.duration_ns.
  • I2: PikeVM, LazyDfa and OnePassDfa return the same matched?, range and captures; the cross_engine bucket checks it; regex.engine.selected.
  • I3: the DFA cache never exceeds dfa_size_limit; DfaCache::insert checks first; regex.dfa.cache_cleared counts clears.
  • I4: backreference and variable-width-lookbehind patterns run only on BacktrackVM; a mismatch is Err(EngineUnsupported) at construction.
  • I5: every BacktrackVM::execute ends within backtrack_budget steps; the dispatch-loop counter; regex.backtrack.budget_exceeded.
  • I6: a mid-match DFA cache exhaustion falls back to PikeVM and both agree; the cross_engine bucket re-validates it; regex.dfa.fallback.
  • I7: no engine splits a UTF-8 codepoint in Unicode mode; Cursor owns boundaries; Miri and fuzz targets assert no panic.
  • I8: per-match scratch comes from a Scratch arena reset at call entry; a heap-profiler snapshot over 1,000 calls must show flat RSS; regex.match.arena_bytes.
  • I9: capture slot vectors are copy-on-write; the divergent-write fixture catches aliasing; regex.captures.slot_copies.
  • I10: the same (pattern, input, RegexBuilder) gives a byte-identical result over 1,024 runs and across hosts; regex.match.determinism_check.
  • I11: every PhaseDeferred(...) call names a real anchor in the deferred register (§38); a doc-lint script catches a dangling one.
  • I12: the literal prefilter never skips a position a correct scan would match; prefilter snapshots are compared with an unassisted scan; regex.prefilter.strategy.
  • I13: a Unicode class resolves to the same byte-range automaton on every build for a pinned Unicode version; a cross-host byte-identical snapshot checks it.
  • I14: Err(Budget) and Err(EngineUnsupported) reach the caller and never become a partial answer; type-level, no Option-swallowing path; regex.match.errors.
  • I15: RegexSet reports exactly the indices individual runs would; the set bucket cross-checks per pattern; regex.set.match_count.

What breaks in production

  • FM-1: one pattern gets slow. The lazy-DFA cache is thrashing under a wide class inside a repetition. regex.dfa.cache_cleared spikes. The PikeVM fallback takes over automatically (I6); the operator raises dfa_size_limit or rewrites the pattern. A pattern like [\x00-\xFF]{50} is the cited shape (§18.6, §26).
  • FM-2: Err(Budget) appears unexpectedly. Either the pattern is genuinely pathological or the input is adversarial. regex.backtrack.budget_exceeded carries pattern_id, input_pos and steps. The call returns an error, never a hang (P8). The operator classifies it: pattern bug means rewrite, attack means rate-limit the caller (§21.9, §26).
  • FM-3: two engines disagree. A bug in one engine's handling of a shared HIR construct, found by the cross_engine bucket or a fuzz target. There is no automatic recovery. The fix goes in the divergent engine, and the failing fixture is committed to divergences/ as permanent coverage (§26).
  • FM-5: a Unicode class changes behaviour after a dependency bump. The tables were regenerated against a newer Unicode version without an ADR. The cross-host snapshot mismatch (I13) shows it; recovery is a deliberate, ADR-governed re-pin (§26, ADR-14).
  • FM-6: a streaming match never completes. The carry-buffer bound is smaller than the pattern's true max_match_len(), so NeedMore comes back indefinitely. Raise the bound or refuse the pattern for streaming; the long-term fix is the max_match_len() analysis (§26, §22.2).
  • FM-9: a capture group returns the wrong substring. A copy-on-write bug aliases two threads' writes, most visible at high group counts. A capture-vector fixture mismatch shows it. There is no auto recovery; the fix lands with the exact divergent-write fixture (§26, I9).

Threats worth knowing (§25): T1 ReDoS through a backreference or unsupported-lookaround pattern against a crafted string, answered by the budgeted BacktrackVM and by the linear-time engines being structurally outside the class (P8, I1); T2 bytecode blow-up through counted repetition such as a{1000000,1000001}, rejected at parse time by size_limit; T3 lazy-DFA cache thrash as a soft CPU-amplification attack, answered by dfa_size_limit, clear-on-full and the PikeVM fallback (P4, P9); T8 an attacker-controlled string reaching the regex! macro, ruled out by documenting the macro as trusted-input-only; T12 streaming carry-buffer memory exhaustion, answered by the max_match_len() bound. Residual risk the design keeps on purpose: the budgeted backreference path (T1) and timing side channels, which are out of scope (T6, §25).

How it compares

The comparison (§34) puts four real systems beside this design.

  • RE2 (C++) rejects backreferences outright instead of gating them, and has the same NFA-plus-lazy-DFA design with clear-on-full that this blueprint adopted directly. That suits search-facing code where a security team accepts no exponential path at all (§34).
  • PCRE2 (C) is pure backtracking with full lookaround and backreferences and no linear-time guarantee. That suits a trusted-input tool such as a local editor's "find", where syntax completeness beats worst-case latency (§34, §37.1).
  • Rust regex crate is the closest sibling, with a near-identical design plus years of tuning of its meta-engine selector against real pattern corpora. A production system should simply depend on it; this blueprint exists to teach the internals the crate already ships (§34).
  • Hyperscan (C, Intel) compiles many patterns into a SIMD-parallel automaton, reports existence only and keeps no capture groups, and has no lazy cache. That suits packet inspection with thousands of patterns at line rate (§34, §37.3).

The blueprint's synthesis: this design sits at the linear-time, semantically-rich corner. RE2 gives up backreferences, PCRE2 gives up the time bound, Hyperscan gives up per-pattern captures (§34).

Building it — the phase plan

Build card: blueprints/build-cards/Regex-Engine.md. Each line: phase, section, what exists, proof.

  • 0 (§12): skeleton, governance, CI, literal-only "Hello, regex". make conformance shows one Pass bucket (hello.smoke), all others Deferred (§12.4).
  • 1 (§13): parser and AST. 100% of ≥ 200 parser fixtures give a byte-identical AST snapshot across two builds (§13.4).
  • 2 (§14): HIR and Unicode classes. Unicode snapshot byte-identical across at least two hosts (§14.4).
  • 3 (§15): Thompson NFA. Bytecode byte-identical across two builds; a{1000000,1000001} fails with SizeLimitExceeded before any NFA exists (§15.4).
  • 4 (§16): PikeVM. All pike/ fixtures pass and the 1,024-run loop shows zero divergence (§16.4).
  • 5 (§17): captures and both leftmost modes. All capture fixtures pass in both modes; 100 groups stay at the 1.6 KB slot ceiling (§17.4).
  • 6 (§18): lazy DFA and prefilter. cross_engine fixtures pass, zero cache clears on a 10,000-fixture run at 8 MB, BM ≥ 1 GB/s (§18.4).
  • 7 (§19): selector, one-pass DFA, RegexSet. Zero false positives or negatives in the set bucket (§19.4).
  • 8 (§20): lookaround. Fixed-width and lookahead fixtures pass with zero backtracking calls; variable-width ones run on BacktrackVM only (§20.4).
  • 9 (§21): budgeted backtracking VM. Every ReDoS fixture ends within max_wall_ms or returns Err(Budget) (§21.4).
  • 10 (§22): streaming and regex!. Chunked feed() matches one-slice results; ≥ 200 MB/s on a 1 GB log (§22.4).
  • 11 (§23): observability and runbooks. Every §23.2 event fires in the examples/waf/ integration test (§23.4).
  • 12 (§24): fuzzing and the ReDoS suite, the "Sealed gate". A 60-second run over seven fuzz targets finds zero new crashes; the 30-day canary runs clean (§24.4).

The blueprint is inconsistent on "Phase-0 done": §1.11 sets the bar at §12–§17 (through captures), while §1.8, §12.4 and Appendix B (§41) define Phase 0 as the skeleton plus "Hello, regex" (§1.11, §1.8, §12.4, §41).

Questions to test yourself

If you only remember three things

ReDoS is a property of the matching algorithm, not of any pattern: this design builds an automaton and advances a deduplicated set of states, which makes every backreference-free pattern run in O(n·m) (MM1, MM2, MM5, I1). The one unbounded feature, backreferences, is fenced onto its own engine with a hard step budget and a loud error instead of silent rerouting (P7, P8, I4). Which engine runs is decided once at construction and the engines must always agree, so the cross-engine determinism check is the main safety net (P3, MM8, I2).

Words used here

  • Regular language: the class of patterns a stack-free automaton can match; no balanced nesting and no backreferences (§2.7).
  • ReDoS: regex denial of service, where a crafted input makes a backtracking matcher run for an exponential number of steps (§2.2, MM5).
  • HIR: the simplified tree after desugaring and Unicode resolution, which every engine consumes (§3.2, P2).
  • Thompson NFA: the bytecode automaton built from fixed per-operator fragments, using epsilon Split instructions (§8.3).
  • PikeVM: the engine that advances the full set of live NFA states per byte and is the ground truth for the others (§3.2, §16).
  • Lazy DFA: a deterministic automaton whose states are built on demand under a memory cap (§3.2, P4).
  • Capture slot: the pair of offsets, at 2i and 2i+1, recording where group i matched (§8.5).
  • Leftmost-first / leftmost-longest: the PCRE-style and POSIX-style rules for choosing among matches (§8.6).
  • Prefilter: a cheap literal scan run ahead of the real engine that may only change where matching starts, never the answer (MM7, I12).
  • One-pass: a pattern where no NFA state has two edges for the same byte class, so a small dense DFA suffices (§19.2).
  • Step budget: the finite count of backtracking frames the last-resort engine may pop before it returns Err(Budget) (§21.2, P8).
