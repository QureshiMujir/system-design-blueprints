Ingress. The RESP2/RESP3 frontend (kee-redis crate) and the HTTP admin API are the only untrusted entry points; every command maps to one Engine call. Engine. Owns the per-shard KeyId → KeyState maps, routes each submit to WAL (if durable) then to heap-top-or-wheel, and runs the active+lazy policy. Wheel/Heap. The timing backbone: O(1)-amortised insert via the hierarchical wheel, sub-tick accuracy via the heap-top; these two structures partition all outstanding deadlines disjointly (I6). Cron Driver. The single thread that owns wall-clock time; nothing else advances the wheel or pops the heap-top (§3 first architectural property, restated as I1/I4). Notification Sinks. One-way fan-out from a fired Deadline to zero or more consumers; no sink can push state back into the wheel. Clock Source. The sole owner of both clock domains; every other component reads through it, never through Instant::now()/SystemTime::now() directly. WAL. The source of truth for outstanding deadlines across a crash; recovery re-derives monotonic offsets from the wall-time-stamped records (§22.4). Replication. Consumes the same WAL stream, stamping each record with an HLC and shipping it to followers, which re-clock absolute deadlines locally rather than replaying a relative offset (P7).

Three properties hold everywhere downstream and are never contradicted by a later section: time flows one direction (clock → wheel/heap → fire → notify); the data path is one-way (ingress → engine → wheel/heap → notify, no back-edge); the WAL alone is the crash-recovery source of truth (the wheel's in-memory state is disposable).

8. Domain Model

8.1 Timing-Wheel Structure

A HierarchicalWheel has NUM_LEVELS = 6 levels of SLOTS_PER_LEVEL = 64 slots each, tick resolution TICK_NS = 1,000,000 (1 ms, ADR-05). Level 0 advances every tick; level k advances every 64^k ticks. A deadline's level is ⌊log₆₄(Δticks)⌋; its slot within that level is (Δticks >> (6·level)) & 0x3F. Horizon: 64^6 ticks × 1 ms = 68,719,476,736 ms ≈ 795 days ≈ 2.18 years — see §35 D1 for the derivation and why this exceeds every realistic TTL by construction.

8.2 Deadline Record Layout (Wheel-Resident)

Node { key: KeyId (u64, 8B), generation: Generation (u32, 4B),
       deadline: MonotonicNs (u64, 8B), next: ArenaIdx (u32, 4B) }   // 24B, arena-pooled

8.3 WAL Record Format

Length-prefixed varint, payload, CRC32C trailer (Castagnoli polynomial, hardware-accelerated via _mm_crc32_u64 on x86-64):

| varint length | tag:u8 | payload (tag-specific) | crc32c:u32 |
tag ∈ { Insert(key,generation,deadline_wall_ns:i128),
        Persist(key,generation),
        Tombstone(key,generation,fired_at_wall_ns:i128),
        Snapshot(lsn:u64, path) }

8.4 HLC Timestamp Format

Hlc { wall_ms: u64, logical: u32, node_id: u32 } — 16 bytes, millisecond wall resolution (sufficient for ordering; sub-ms ordering is the logical counter's job, §23.2).

8.5 Worked Example — Insert → Cascade → Fire

now = MonotonicNs(0). PEXPIRE k 130 (130 ms). Δticks = 130. 130 < 64 is false, so level ≥ 1: ⌊log₆₄(130)⌋ = 1; slot = (130 >> 6) & 0x3F = 2. Node lands in level-1 slot 2. At now = 128 ms level-0's cursor wraps (128 / 1 = 128 ticks = 2 full level-0 rotations of 64), triggering a cascade of level-1's current slot (slot 2, since 128 / 64 = 2) down into level-0: the node is re-inserted with Δticks = 130 − 128 = 2, landing in level-0 slot 2. Two ticks later (now = 130 ms), level-0's cursor reaches slot 2 and the node fires — within the 1 ms tick tolerance (M7).

8.7 Malformed-Input Examples

EXPIREAT key 0 — valid, means "fire immediately"; must not be interpreted as "no deadline" (§21.6 pitfall). PEXPIRE key -5 — negative relative TTL: InsertError::AlreadyPast, engine fires immediately rather than rejecting (matches Redis's EXPIRE semantics: a past deadline deletes/expires the key at once). EXPIRE_MANY COUNT 500000 ... — count exceeds the 100,000 bulk cap (§21.6): parser rejects with a typed ExpireError::BulkCountExceeded before reaching the engine. PEXPIREAT key 99999999999999999999 — exceeds MonotonicNs's representable horizon after wall_to_monotonic conversion: InsertError::PastHorizon (P8, no silent truncation).

8.8 Failure-Path Example

Follower receives an Insert WAL record with HLC (wall_ms= 1000, logical=0, node_id=A) followed, due to network reordering, by a Tombstone record with HLC (wall_ms=999, logical=3, node_id=A) for the same key/generation. Per I9, the follower detects merge() would violate causality (tombstone's HLC precedes the insert's observed HLC for the same node) and rejects the tombstone, re-requesting the correct ordering from the primary (§23.4) rather than applying out-of-order and risking a resurrected-after-fire key.

Design principles (§6)

  • P1 — Monotonic time is the engine's time. All internal scheduling runs against CLOCK_MONOTONIC; CLOCK_REALTIME is read only at the API boundary (an EXPIREAT request) or for an outgoing notification's wall-time stamp. Tradeoff: every absolute deadline needs one extra conversion call. Operational implication: a wall-clock NTP step never perturbs an already-scheduled deadline (I5). Violating it: a wheel that stores wall time directly fires early or late on every NTP correction — the single most expensive bug class in timer systems (§27 Key Pitfall 1).
  • P2 — Three primitives, one responsibility each. The wheel is the active path (O(1)-amortised steady state); the heap-top is the accuracy path (O(log 256) worst case); the WAL is the durability path (O(records) on recovery). Tradeoff: three codepaths to keep synchronized (I6) instead of one. Operational implication: each can be benchmarked, and regress, independently (§31). Violating it: merging wheel and heap logic reintroduces the O(log n) cost the wheel exists to avoid at 100M-key scale.
  • P3 — Eviction is not expiration. A fire is "the deadline arrived"; an eviction is "memory is full, pick a victim" — related (a fire frees memory) but distinct (a no-TTL key is never expired but can be evicted; a live-TTL key can be evicted before its deadline). Tradeoff: this engine cannot alone bound memory under adversarial no-TTL growth. Operational implication: LRU-LFU-Cache (rank 59) owns the eviction half of the contract. Violating it: conflating the two produces a system where neither eviction nor expiration is independently correct or testable.
  • P4 — The fire path does not allocate. Wheel pop, heap pop, and notification enqueue run against pre-allocated arenas (I11). Tradeoff: fixed arena capacity must be sized ahead of peak cardinality. Operational implication: tail latency is a function of cache behaviour, not allocator behaviour. Violating it: an allocator spike inside the fire path is indistinguishable from a GC pause and defeats the entire performance case for Rust (ADR-01).
  • P5 — The active-expire cycle is bounded by wall time, not sample count. Following Redis (ADR-06): ≤ 25% of a 100 ms slice per cycle (I10); a cycle that cannot finish resumes next cycle from its recorded cursor. Tradeoff: a skewed key distribution can leave stale entries momentarily unswept. Operational implication: the foreground stall ceiling is predictable regardless of key distribution. Violating it (bounding by sample count instead): a pathological distribution can hold the shard lock arbitrarily long.
  • P6 — Notifications are best-effort by default, durable on opt-in. KeyspaceEventSink drops on a slow subscriber rather than backpressuring the fire path; DurableSink opts into WAL-backed exactly-once-modulo-ack at the cost of two fsyncs per fire. Tradeoff: default delivery has no retry guarantee. Operational implication: consumers that need guarantees must explicitly choose DurableSink and pay its latency. Violating it (making every sink durable by default): halves throughput for the majority of consumers who never needed the guarantee.
  • P7 — Replicated mode uses absolute deadlines, re-clocked on the follower. A PEXPIREAT ships as its absolute wall time; the follower converts to its own monotonic clock at apply time. Tradeoff: follower fire accuracy is bounded by that follower's own NTP skew, not by the primary's clock. Operational implication: this is the only correct replication strategy for a relative TTL under replication lag (§27 Key Pitfall 6). Violating it (replicating the relative offset): every deadline replays late by exactly the replication lag.
  • P8 — No silent fallbacks. An insert past the wheel's maximum representable horizon returns a typed error; the engine never silently truncates it to the horizon. Tradeoff: callers must handle a rejection path. Operational implication: no deadline ever fires earlier than the caller specified without the caller's knowledge. Violating it: silent truncation produces a surprise-immediate-fire bug that is nearly impossible to trace back to its cause.
  • P9 — The public API matches Redis's surface exactly. Same commands, same NX/XX/ GT/LT flags, same return-value semantics (TTL → -2/-1/seconds). Tradeoff: Redis's semantics are inherited even where this engine might prefer different ones. Operational implication: existing Redis clients drop in against this engine with zero code change (M-resp, §21). Violating it: every consumer needs a bespoke client.
  • P10 — Recovery is bounded. A WAL of N outstanding deadlines recovers in O(N log K) where K is the hot level's slot count, with a small constant; recovery is checkpointable via a snapshot pinning a known LSN. Tradeoff: snapshotting costs a background CPU/IO budget. Operational implication: RTO is bounded by the inter-snapshot record count, not by total dataset size (§4, §35 D6). Violating it: RTO grows unbounded with total keyspace size, which is unacceptable at 100M-key scale.
  • P11 — Sharding bounds blast radius. 256 fixed shards at boot (no dynamic resharding); a hot shard's active-expire cycle stall never blocks another shard's inserts. Tradeoff: shard count is a boot-time constant, not elastic. Operational implication: capacity planning must size shard count ahead of peak concurrency (§4). Violating it (dynamic resharding under load): a rehash-in-flight is a correctness hazard (in-flight deadlines can be observed twice or dropped) this engine refuses to hide behind "eventually consistent."
  • P12 — Every stateful mutation is idempotent under replay. WAL replay (§22), HLC merge (§23), and generation-checked fire (I2, I7) must produce identical state whether applied once or twice. Tradeoff: every mutation needs an explicit idempotency key (the Generation field). Operational implication: crash recovery and replication both replay safely with no special-cased "have I seen this before" bookkeeping beyond the generation check. Violating it: a non-idempotent replay double-counts a fire or resurrects a persisted key on every recovery.
