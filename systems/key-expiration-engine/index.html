In one paragraph

A key-expiration engine accepts (key, deadline) pairs and fires each deadline at, or shortly after, the moment it was set against (§1). It targets at least 5,000,000 inserts per second on one thread with O(1) amortised cost per insert, 100M outstanding keys, and crash recovery from a write-ahead log in 5 s or less (§4). Its core is a multi-level timer structure (hierarchical timing wheel) plus a small sorted queue for deadlines that are about to fire (§3, §8.1). It exposes Redis's EXPIRE-family commands, so existing Redis clients work unchanged (§1, P9). Cache and session-store authors, SREs running the standalone binary, and library authors embedding kee-core run it (§1). Choosing what to evict when memory is full is not its job (P3).

The problem, concretely

Every cache, database, broker and session store eventually grows a time-to-live (TTL). The blueprint names the two naive answers and what each costs: check-on-read leaks memory at scale, because a key nobody reads again is never freed, and scan-and-evict stalls the foreground workload while it scans (§2). This project is described as the smallest system that forces you to solve both (§2).

A third trap hides in the clock. If the scheduler stores wall-clock times, every NTP correction makes already-scheduled deadlines fire early or late. The blueprint calls this the single most expensive bug class in timer systems (P1). It repeats the point for replication: if a follower re-adds a relative TTL when it applies a record, every deadline replays late by exactly the replication lag (P7).

Then add scale. At 100M keys and 5,000,000 inserts per second, a plain sorted heap pays O(log n) per insert and "degrades visibly past ~1M keys" (ADR-02). A crash must not lose every TTL (ADR-08). And a hot shard must not stall the others (P11). The blueprint's structure is the answer to those pressures taken together, and it states that every other decision exists to protect one property: the wheel/heap partition is the only path to O(1)-amortised insert at 100M keys (§4).

How it works, end to end

Follow one PEXPIRE through the boxes of §3's diagram (drawn from the blueprint's §3 diagram, coloured by role, with module names from §1, §3 and §4 where the blueprint gives them):

  1. Ingress. The RESP frontend (kee-redis crate) and the HTTP admin API are the only untrusted entry points. Every command maps to one Engine call (§3).
  2. Engine. It owns the per-shard KeyId → KeyState maps. A submit goes to the WAL first if the insert is durable, then to the heap-top or the wheel (§3, I3). The same box runs the active and lazy expiration policy (§3, §18).
  3. Wheel and heap-top. These two structures partition all outstanding deadlines disjointly (I6, §3). The wheel is the O(1) path, the heap-top is the accuracy path, and the WAL is the durability path, one responsibility each (P2).
  4. Cron driver. A single thread owns the advance of time: nothing else advances the wheel or pops the heap-top (§3). On each 1 ms tick it pops the heap-top, advances the wheel, and notifies each fire (§3). The heap-top is consulted before the wheel (§17.2).
  5. Notification sinks. A fired Deadline fans out one-way to zero or more consumers; no sink can push state back into the wheel (§3). A slow sink is treated as Dropped after 100 ms by default (I13, P6).
  6. WAL (kee-wal). It is the only crash-recovery source of truth; the in-memory wheel is disposable (§3, MM3). Replication consumes the same WAL stream, stamps each record with a hybrid logical clock, and followers re-clock absolute deadlines locally (§3, P7).
  7. Clock source. It is the sole owner of both clock domains. Every other component reads time through it, never through Instant::now() or SystemTime::now() (§3, P1).

The blueprint states three properties that hold everywhere: time flows one direction (clock to wheel/heap to fire to notify), the data path has no back-edge, and the WAL alone decides what survives a crash (§3).

The core ideas

A wheel of wheels: a deadline is a base-64 number (§8.1, §8.5, MM1)

A HierarchicalWheel has NUM_LEVELS = 6 levels of SLOTS_PER_LEVEL = 64 slots, with TICK_NS = 1,000,000 (1 ms, ADR-05). Level 0 advances every tick and level k advances every 64^k ticks (§8.1). A deadline's level is ⌊log₆₄(Δticks)⌋ and its slot in that level is (Δticks >> (6·level)) & 0x3F (§8.1). The blueprint reads this as a base-64 radix sort computed one carry at a time, so insert is O(1) because the "sort" is deferred to the tick that needs it (MM1). The horizon is 64^6 ticks × 1 ms = 68,719,476,736 ms, about 795 days or 2.18 years (§8.1, §35 D1).

The blueprint's own trace (§8.5): at now = 0, PEXPIRE k 130, so Δticks = 130.

Step What happens Source
1. Insert 130 < 64 is false; level = ⌊log₆₄(130)⌋ = 1; slot = (130 >> 6) & 0x3F = 2; node sits in level-1 slot 2 §8.5
2. At 128 ms level 0's cursor wraps; level 1's current slot (slot 2) is cascaded down §8.5
3. Re-insert Δticks = 130 − 128 = 2, so the node lands in level-0 slot 2 §8.5
4. At 130 ms level 0's cursor reaches slot 2 and the node fires, within the 1 ms tick tolerance §8.5, M7

The recompute in step 3 is the whole point of cascading: it must use the current now, not the value at insert time. The blueprint names re-inserting against a stale self.now as a bug class (MM1, §26 "Cascade data loss", §36 question 12).

The heap-top: a small sorted queue in front of the wheel (§17.2, §8.6, MM7, ADR-04)

The wheel fires within a 1 ms tick (M7); the heap-top reaches 200 µs (M6, §4). For deadlines about to fire, the engine keeps a BinaryHeap of at most 256 entries (§3, ADR-04). A deadline whose offset is within top_horizon (default 16 ms, which is 16 ticks) goes to the heap-top instead of the wheel (§17.2). The state table says the same: Scheduled (heap-top) when Δ < top_horizon, Scheduled (wheel) otherwise (§8.6). When the heap-top is full, the farthest-deadline entry is evicted into the wheel as one atomic step, which is what keeps I6 (disjoint partition) true (§17.2, I6).

The blueprint's argument for a fixed capacity is that a hot small structure with spillover into a general slow one beats growing the fast structure (MM7). Its sizing note: at M2's 800,000 inserts per second, a 16 ms window could in theory see 800,000 × 0.016 = 12,800 inserts, but 256 was sized against the empirical short-TTL fraction, and the eviction path covers the gap (§35 D4).

Generation numbers: cancel without searching the wheel (§8.2, §8.6, I7, P12, MM5)

Each wheel node is 24 bytes: key (8 B), generation (4 B), deadline (8 B), next (4 B) (§8.2). The per-key KeyState holds the current generation (§39). PERSIST (remove the TTL) does not hunt through a slot. It increments the generation and frees the KeyState, so the wheel entry becomes Stale (§8.6). When that node later fires, the fire path compares generations; a mismatch is silently discarded (I7, §8.6). Re-EXPIRE works the same way (I7).

The same field makes replay safe. WAL replay, HLC merge and generation-checked fire must give the same state when applied once or twice (P12), so at-least-once delivery converges without a separate "have I seen this?" table (MM5).

Two clocks: monotonic for "when", wall for "what it means" (P1, I4, I5, MM2, §22.2)

All scheduling uses the monotonic clock (CLOCK_MONOTONIC). The wall clock (CLOCK_REALTIME) is read only at the API edge (an EXPIREAT) or to stamp an outgoing notification (P1). The two are distinct newtypes, MonotonicNs and WallNs, so mixing them is a compile error (MM2, §1). The conversion from wall to monotonic happens once, at insert, which is why a wall-clock step never reschedules a stored deadline (I5).

The WAL stores wall time. Insert records hold deadline_wall_ns as an i128 and Tombstone records hold fired_at_wall_ns (§8.3). On recovery the engine computes Δ = deadline_wall_ns − now_wall and re-inserts at now_mono + Δ, re-deriving the monotonic offset from the wall-time record (§22.2). The blueprint's edge case for this design is a wall clock stepped backward by a week between crash and restart, where §22.8 says recovery immediately fires every deadline that is "now in the past". That sentence and §22.2's formula, which subtracts the current wall time, do not obviously agree, and the point is logged in the errata. §36 question 17 asks why the monotonic value is not persisted directly.

Active plus lazy expiration, bounded by wall time (§18.2, P5, ADR-06, ADR-07, MM4, I10)

The wheel fires deadlines on time, but a deadline can be past while its node has not yet been swept. Two mechanisms cover that (§18.1). The lazy probe checks KeyState.deadline on every keyed read; a passed deadline fires immediately and leaves the wheel node stale for the generation check to absorb (§18.2, I7). The active-expire cycle sweeps wheel levels 0 and 1 from the current cursor, bounded by wall time (25% of a 100 ms slice, so 25 ms), and saves a resumable cursor if the budget runs out mid-sweep (§18.2, P5, I10).

Why wall time, not a sample count? A count assumes uniform key occupancy and breaks the moment one shard is hot, whereas a time bound holds under any distribution (MM4, P5). Memory pressure raises the budget in steps: Low→25ms, Medium→50ms, High→100ms, Critical→immediate synchronous force_expire_pass() (§18.2). Pressure escalates expiration aggressiveness only; it never makes an eviction decision (§18.2, P3).

Replication ships absolute deadlines, ordered by a hybrid clock (§8.4, §8.8, §23.2, P7, MM6, I9)

A PEXPIREAT ships as an absolute wall time, and the follower converts it to its own monotonic clock when it applies it (P7, §23.2). Ordering uses a hybrid logical clock (HLC): Hlc { wall_ms: u64, logical: u32, node_id: u32 }, 16 bytes (§8.4). Hlc::now takes wall = max(physical, last.wall); logical resets to 0 on a wall advance and increments otherwise (§23.2). The logical counter orders events inside one millisecond, which is why millisecond resolution is enough (§8.4, MM6). §23.6 and §36 question 9 instead speak of a "64-bit packing" of wall_ms with the 32-bit logical counter, which the 16-byte struct of §8.4 and §11 does not describe; the blueprint states both.

The blueprint's failure-path example (§8.8): a follower sees an Insert stamped (wall_ms=1000, logical=0, node_id=A) and then, after network reordering, a Tombstone stamped (wall_ms=999, logical=3, node_id=A) for the same key and generation. Under I9 the follower detects that applying it would violate causality, rejects the tombstone, and re-requests the correct order from the primary, rather than risk a resurrected-after-fire key (§8.8, §23.9).

The trade-offs — where engineers disagree

Active structure: hierarchical wheel (ADR-02)

Chosen: a hierarchical timing wheel, for O(1)-amortised insert against a heap's O(log n) (ADR-02). Rejected: a flat sorted heap (BinaryHeap). When the rejected choice is right: under about 100K keys, where simplicity and debuggability beat the asymptotics, for example a single-tenant embedded cache (ADR-02, §37 Alt-1).

Heap-top capacity: 256 entries (ADR-04)

Chosen: a fixed 256-entry heap-top, the smallest size that absorbs steady-state "soon" arrivals without thrashing (ADR-04, §35 D4). Rejected: 0 (pure wheel) and unbounded. When the rejected choice is right: 0 wins when sub-ms accuracy is not required (batch or session TTLs in minutes); unbounded wins at fewer than 10K live short TTLs, where memory is cheap (ADR-04).

Active-expire bound: wall time (ADR-06)

Chosen: 25% of a 100 ms slice, so a predictable foreground stall whatever the key distribution (ADR-06, P5). Rejected: a fixed sample count. When the rejected choice is right: only with a provably uniform key distribution and an external hard scheduler that already bounds lock hold time (ADR-06).

Lazy expiration on access: mandatory (ADR-07)

Chosen: check on every read, closing the memory-waste gap the active cycle cannot guarantee under skew (ADR-07). Rejected: active-only. When the rejected choice is right: when reads are rare relative to inserts, for example a write-heavy telemetry TTL store, and the per-read branch is not worth paying (ADR-07).

Durability: WAL by default (ADR-08, ADR-09)

Chosen: a mandatory WAL, opt-out per insert with Durability::BestEffort, because losing all TTLs on restart is unacceptable for a session store or billing rate limiter (ADR-08). Group commit runs every 1 ms or 1024 records, whichever is sooner (ADR-09). Rejected: no durability at all, and per-request fsync. When the rejected choice is right: no-WAL for pure cache-aside deployments where the backing store re-validates independently of TTL state (ADR-08); per-request fsync under regulatory zero-durability-gap mandates such as financial ledger TTLs (ADR-09).

Replication ordering: hybrid logical clock (ADR-13)

Chosen: an HLC, combining wall-time meaning for EXPIREAT with causal ordering and needing no synchronized clocks (ADR-13). Rejected: a pure wall clock and a pure Lamport (logical) clock. When the rejected choice is right: a pure wall clock with hardware PTP-synced nodes (sub-µs skew); a pure logical clock for a purely internal deployment where wall-time meaning stays local (ADR-13).

Roads not taken (§37, §38)

Sorted heap only (§37 Alt-1) wins below about 100K live deadlines, where O(log n) is negligible and one well-understood structure is easier to debug. Go's runtime timer heap is the example. It was rejected because the 100M-key, 5,000,000-inserts-per-second target makes O(log n) per insert "an 80× cost penalty at scale" (§37 Alt-1). Alt-1 cites §15.4's baseline comparison for this, and that comparison is 200 ms for the heap against 50 ms for the single-level wheel on 1,000,000 insert+fire round trips (§15.4, §14.4). The blueprint states both and does not reconcile them.

Calendar queue (§37 Alt-2) wins when the deadline distribution is known and stable, so one bucket width can be tuned once, as in discrete-event simulation. It was rejected because TTL distributions here are operator-defined and shift at runtime, and a fixed width either wastes memory or brings back O(occupancy) scans.

One OS timer per key (§37 Alt-3) wins at thousands of latency-critical timers, where the kernel's high-resolution timers give accuracy for free. It was rejected because 100M timers would exhaust the 65,536 file-descriptor budget in §4 and the kernel's per-timer bookkeeping does not amortise. The deferred io_uring driver is a tick-resolution upgrade, not this (§37 Alt-3, ADR-17).

A separate wheel per shard (§37 Alt-4) wins when looser global fire ordering is acceptable and running 256 cron drivers is affordable. It was rejected because it would multiply the WAL, snapshot and recovery machinery by 256 with no correctness benefit (§37 Alt-4, P10).

Deferred features (§38). The register lists 12 items, each with an un-defer trigger: for example the io_uring sub-ms timer driver (when sub-ms accuracy is a hard requirement, ADR-17) and multi-leader replication (when Distributed-KV-Store ships a stable embeddable Raft crate).

What must never be false

  • I1: a deadline never fires before its target. conformance/wheel.insert_fire; kee_fire_early_violations_total (expect 0); fail-closed: halt the cron driver, page on-call (§7).
  • I2: every accepted deadline fires exactly once or is cancelled. Generation tests plus a kee_fires_total vs kee_inserts_total reconciliation job (§7).
  • I3: WAL durability precedes the ack for Durability::DurableLog inserts. kill -9 injection; kee_ack_before_fsync_violations_total (expect 0); fail the request, never ack early (§7).
  • I4: monotonic time never decreases within a process. A 10M-sample property test; kee_monotonic_regression_total; a regression is a process-fatal panic (§7).
  • I5: a wall-clock step never reschedules an inserted deadline. SimulatedClock NTP-step test; structural, so no telemetry (§7).
  • I6: wheel and heap-top hold disjoint deadlines. A property test checks the intersection is empty after every op; kee_dual_residency_violations_total (§7).
  • I7: a fire whose generation mismatches is discarded. kee_stale_fire_discarded_total; a count above 0 is normal, not a failure (§7).
  • I8: recovery replays every deadline outstanding at the crash, and no more. Noticed by the kill -9 recovery test and kee_recovery_deadlines_recovered_total; on a violation startup is blocked pending an operator forensic scan (§7).
  • I9: HLC timestamps strictly increase per node and respect causality on merge. conformance/repl.hlc_ordering; kee_hlc_causality_violations_total; the offending record is rejected and re-requested (§7).
  • I10: the active-expire cycle never holds a shard lock past 25 ms by default. Clock-stall injection test; kee_active_cycle_duration_seconds, alert if p99 exceeds the budget (§7).
  • I11: the fire path performs zero heap allocations in steady state. An instrumented-allocator benchmark; kee_fire_path_allocations_total (expect 0); the CI perf gate fails the build (§7).
  • I12: a follower never fires a replicated deadline earlier than primary_fire_time − 2×NTP_skew_ms. Two-node conformance/repl.absolute; kee_follower_early_fire_total (§7).
  • I13: every Sink::deliver call returns within MAX_SINK_DELIVER_DURATION (100 ms default) or counts as Dropped. kee_notification_dropped_total{sink} (§7).

What breaks in production

The §26 table has no FM-numbers, so each mode is cited by its class name.

  • Cron-driver stall. kee_cron_tick_last_completed_seconds goes stale and inserts pile up. Root causes: a lock-ordering inversion, or an unbounded sink call that bypasses I13. A liveness watchdog alerts after 3 × TICK_NS of staleness. It is process-fatal by design: restart and recover from the WAL, with a thread dump captured on the trip (§26).
  • Cascade data loss. Deadlines silently vanish under load because a cascade re-inserts against a stale self.now (§16.6). Detected by the conformance/wheel.cascade regression or an I2/I8 telemetry gap; no auto recovery: hotfix plus regression fixture, with the 24 h soak trace replay isolating the exact rotation (§26, §16.9).
  • WAL corruption. A torn write or disk failure shows up as a CRC mismatch at the recovery scan (I8). §26 lists "Startup blocked" as the symptom yet truncate-to-last-good-record as the auto recovery; §22.2 calls a tail mismatch "not treated as fatal" and T3 says "Truncate + restart", while §22.9 and I8 block startup for an operator scan with tools/wal-inspect. The blueprint does not say which cases truncate and which block; loss past the truncation point is bounded and never silent (§22.9, T3).
  • Replication divergence. A follower diverges beyond the skew tolerance after an unresolved HLC causality violation, or persistent skew beyond NTP_skew_ms. Detected by kee_hlc_causality_violations_total and kee_follower_early_fire_total. The follower re-requests the record; otherwise a full snapshot resync per docs/runbooks/follower-skew.md (§26, §23.9).
  • Memory-pressure runaway. The OOM-killer fires despite active-expire escalation, typically from adversarial no-TTL key growth, which this engine cannot bound alone (P3). Detected through cgroup MemoryHigh/OOM events. PressureLevel::Critical forces a synchronous expire pass; the operator raises the limit or engages the LRU-LFU-Cache eviction layer (§26).
  • Split-brain. Two nodes accept writes during a partition because the single-leader assumption was violated. Detected as divergent WAL LSN sequences on reconnect. No auto recovery; it is out of scope for single-leader mode, so reconcile manually or resync from the designated primary (§26, §23.8).

Threats worth knowing (§25): T5 an unauthenticated replication stream (mTLS deferred, a trusted network segment assumed); T7 a buggy or malicious Sink, contained by I13's bounded queue and timeout; T10 an unauthenticated FORCE_EXPIRE_PASS, answered by an internal-only admin binding; T11 a TTL timing probe that reveals whether a key exists, documented as a risk needing RESP-boundary authentication.

How it compares

  • Redis chose no timing wheel: a bounded active-cycle sample plus mandatory lazy-on-access, betting that TTL'd keys stay few relative to the keyspace. That wins in a single-node, memory-resident keyspace where operational simplicity matters more than the asymptotics, which is the regime P2 rejects at 100M TTL'd keys (§34).
  • Kafka (TimingWheel.scala) chose an unbounded DelayQueue for overflow instead of a fixed heap-top. That is fine because its timer cardinality is bounded by broker request timeouts; this engine's arbitrary-TTL workload cannot make that bet, so §17.2 fixes the capacity (§34).
  • Netty (HashedWheelTimer) chose a single-level wheel with a "rounds" counter in place of hierarchical cascading. That wins for thousands of per-channel I/O timeouts, where one level is simpler; at 100M keys the simplicity is unaffordable (§34, §14.7).
  • Linux kernel (timer.c, hrtimer.c) chose two entirely separate structures by accuracy class: a cascading wheel and a per-CPU rbtree. That wins because the two timer classes have disjoint call sites; this engine unifies both behind one submit() because Redis clients never distinguish accuracy classes (§34).

Questions to test yourself

  1. Why is the heap-top's capacity fixed at 256 rather than sized to the theoretical worst-case arrival rate, and what mechanism absorbs the gap? — Hint: §35 D4 gives the two figures; §17.2 describes the overflow path; MM7 gives the principle.
  2. Why does the engine's RTO stay bounded at ≤ 5 s regardless of total keyspace size, and what specific ADR makes that true? — Hint: §35 D6 is the derivation; ADR-10 is the cadence; P10 states the goal.
  3. Explain why the active-expire cycle is bounded by wall time rather than sample count, and construct a concrete key distribution that would violate a sample-count bound but not a wall-time bound. — Hint: MM4 and P5 explain the failure; ADR-06 and I10 give the bound.

If you only remember three things

Deadlines live in a wheel of wheels where insert is O(1) and a small fixed-size sorted queue handles the soon-to-fire ones, and the two structures never hold the same deadline (§8.1, ADR-02, I6). Scheduling runs on the monotonic clock, durability lives in the log not the wheel, and replication ships absolute deadlines ordered by a hybrid logical clock (P1, MM3, P7, ADR-13). Everything that could stall the fire path is bounded by wall time or dropped, never waited for (P5, I10, I13).

Words used here

  • Deadline: a (key, generation, MonotonicNs) tuple representing one scheduled fire (§39).
  • Hierarchical timing wheel: a multi-level ring of slots; each level advances 64 times slower than the one below, giving O(1)-amortised insert (§39, §8.1).
  • Cascade: draining a level's current slot and re-inserting its entries one level lower when the cursor wraps (§39, §8.5).
  • Heap-top: the fixed-capacity (256) sorted heap holding near-term deadlines for sub-tick accuracy (§39, ADR-04).
  • Generation: a per-key counter that lets stale wheel entries be discarded instead of removed (§39, I7).
  • Clock domain: monotonic time for scheduling versus wall time for meaning to other processes, kept apart by newtypes (§39, P1).
  • Group commit: batching several WAL appends into one fsync, bounded by time or record count (§39, ADR-09).
  • Snapshot: a point-in-time copy of shard and wheel state that pins WAL replay to a known position (§39, ADR-10).
  • HLC (hybrid logical clock): a (wall_ms, logical, node_id) timestamp that combines wall-time meaning with causal ordering (§39, §8.4).
  • Sink: the pluggable trait that delivers fire notifications to a consumer (§39, §20).
