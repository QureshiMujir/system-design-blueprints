62 — Key-Expiration Engine

Project Number: 62

Project Name: Key-Expiration Engine

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

A standalone, time-driven expiration and notification engine for keyed records: accepts (key, deadline) pairs at sustained high arrival rates, fires each deadline at or shortly after the wall-clock instant it was set against, sustains 100M-key cardinality at bounded O(1)-amortised per-insert cost, survives process crash by replaying a write-ahead log, stays correct under independent wall-clock and monotonic-clock skew, replicates absolute deadlines across followers via hybrid logical clocks without re-deriving them from a relative offset, and exposes a Redis-compatible EXPIRE / PEXPIRE / EXPIREAT / PEXPIREAT / TTL / PTTL / PERSIST command surface plus a documented bulk variant. Eviction (LRU, LFU, ARC, 2Q) is explicitly not this engine's concern — that is the LRU-LFU-Cache project (rank 59); this engine fires expirations and hands the event to whatever consumes it (a cache, an application, a notification sink).

Phase-0 deliverable — numbered modules:

  1. kee-core::clock — MonotonicNs / WallNs newtypes, ClockSource trait (§13).
  2. kee-core::wheel — single-level hashed wheel, correctness kernel (§14).
  3. kee-core::heap (baseline) — sorted-heap reference queue for conformance (§15).
  4. Repository skeleton, CI, governance docs, Makefile targets (§12).
  5. The "tick smoke test" — one-slot wheel, one insert, one fire, asserted (§12.5).

System boundaries.

  • Provides: deadline scheduling primitives (wheel + heap-top), active + lazy expiration policy, WAL-backed crash recovery, a pluggable notification-sink trait, a Redis-compatible TTL command surface, replicated absolute-deadline ordering via HLC.
  • Delegates: eviction policy (LRU-LFU-Cache, rank 59), the value storage engine (LSM-Tree-DB), the network protocol fronting a full cache (Distributed-Cache, rank 61), cross-replica write ordering / consensus (Raft, Distributed-KV-Store, rank 38).
  • Does NOT provide: value storage, cache eviction, multi-key transactions, a consensus protocol, encryption at rest (delegated to the operator's disk layer).

Non-goals: general-purpose job scheduling (cron-like recurring jobs beyond the opt-in RecurrencePolicy stretch goal, §38); a full pub/sub bus (the keyspace-event sink is narrowly scoped to expiration events); a general key-value store (no GET/SET).

Deployment model: a single binary (kee-redis crate) per node, optionally clustered in primary/follower replication mode (§23); embeddable as a library (kee-core alone) inside a host process that owns its own keyspace and only wants deadline scheduling.

Target users/operators: cache and session-store authors who need TTL semantics without adopting all of Redis; SREs operating the standalone binary who need Redis-shaped observability; library authors embedding kee-core inside a larger service.

What later phases unlock: Phase 16 (hierarchical wheel) unlocks 100M-key cardinality; Phase 17 (heap-top hybrid) unlocks sub-tick accuracy; Phase 22 (WAL) unlocks crash safety; Phase 23 (HLC replication) unlocks multi-node deployments; Phase 24 unlocks a publishable, comparative performance story against redis-server.

Recommended language: Rust 2021 edition. The fire path runs without GC pauses; the type system enforces the monotonic-vs-wall-clock distinction at compile time (MonotonicNs / WallNs are non-interconvertible newtypes, §13.1); Tokio's time::wheel is the closest engineering reference and keeps us in the same ecosystem. Rejected: C++ (larger timer-wheel ecosystem, but no compile-time clock-domain guard — ADR-01 records the regime where C++ still wins: embedding inside an existing C++ codebase); Go (GC pauses directly threaten the fire-path tail-latency budget, M4/M5, though its runtime timer heap, §5 Reference Implementations, is a valid distinct-architecture case study, §37); Java/JVM (same GC objection, plus JNI cost for clock_gettime access patterns).

Prerequisites: timer-wheel theory (Varghese & Lauck 1987), logical/physical clock theory (Lamport 1978; Kulkarni et al. 2014), write-ahead logging and recovery (Mohan et al. 1992; ARIES), the Redis and Tokio source trees as engineering references, NTP skew semantics (RFC 5905; Mills 2003).

Estimated timeline: Phase 0 (repository skeleton + correctness kernel) — 1 week. Full Phase-0 drop (hierarchical wheel, heap-top, active+lazy policy, WAL, Redis-compatible surface, benchmark harness against redis-server) — 4–6 weeks (§12–§21). Full system (replication, bulk APIs, third-party-style conformance audit, comparative whitepaper) — 3–5 months (§22–§24, back-matter operational maturity).

Deferred features (flagged here, registered in full at §38):

  • PhaseDeferred("§17.6") — io_uring sub-millisecond timer driver (ADR-17).
  • PhaseDeferred("§23.6") — multi-leader replication via the Distributed-KV-Store Raft layer (rank 38); Phase 23 ships a single-leader gRPC log shipper until that project lands.
  • PhaseDeferred("§21.6") — per-client AUTH at the RESP boundary.
  • PhaseDeferred("§25") — mTLS on the HTTP admin boundary and the replication gRPC channel.
  • PhaseDeferred("§38") — GPU-accelerated bulk fire, TTL recurrence, range deadline queries, multi-tenant memory accounting (full list, §38).

2. Why Build This

  • Every cache, database, message broker, session store, and rate limiter grows a TTL; the naive version (check-on-read) leaks memory at scale, and the naive version (scan-evict) stalls the foreground workload — this project is the smallest system that forces you to solve both correctly.
  • Teaches the full arc from Varghese & Lauck's 1987 timing-wheel paper to a production hybrid (wheel + heap-top) that Tokio, Kafka, Netty, and the Linux kernel each converged on independently — convergent design is a strong signal the tradeoff is fundamental, not incidental.
  • Builds the engineering muscle of reasoning about two clocks at once (monotonic for scheduling, wall for cross-process/cross-replica meaning) — the same muscle that underlies distributed transaction timestamps, certificate expiry, and log-based recovery.
  • Cross-links: LRU-LFU-Cache (rank 59) consumes this engine's fire events for eviction; Distributed-Cache (rank 61) takes a hard dependency on the replicated absolute-deadline mode (§23); Write-Ahead-Log (rank 69) is the durability primitive this engine's kee-wal crate becomes a thin adapter over once it ships (§22.6); Distributed-KV-Store (rank 38) supplies the Raft layer this engine's replication mode defers to (§23.6).
  • Calibration value: a correct hierarchical timer wheel at 100M-key scale, with WAL crash recovery and HLC-ordered replication, is a self-contained proof that the builder can reason about amortised complexity, allocation discipline, clock domains, and durability simultaneously — the same skill bundle a Kafka or Redis core-team hire is expected to demonstrate.

What Mastery Looks Like

  • Hierarchical timing wheels, cold. After Phase 16 you can derive the level/slot count for any horizon and tick resolution, and explain why cascading is O(1) amortised, not O(levels) worst-case.
  • Clock-domain discipline. After Phase 13 you can name, for any codebase, every place a wall-clock read leaks into a scheduling decision — the single most common timer bug class.
  • Bounded background work. After Phase 18 you can design any "sweep in the background" subsystem (GC, compaction, active-expire) with an explicit wall-time budget rather than an unbounded work-count budget.
  • Crash-safe log design. After Phase 22 you can derive a WAL record format, a group-commit policy, and a recovery algorithm from ARIES first principles, and state the RTO it guarantees.
  • Distributed time without synchronized clocks. After Phase 23 you can implement HLC merge/now correctly from the Kulkarni et al. 2014 paper and explain why it, not pure Lamport clocks or pure wall time, is the right primitive for absolute-deadline ordering.
  • Tail-latency engineering. After Phase 24 you can build a benchmark harness that isolates insert cost, fire cost, and recovery cost independently, and defend a p99 number against a skeptical reviewer.
  • API-compatibility engineering. After Phase 21 you can build a byte-compatible subset of an existing wire protocol (RESP) and explain exactly where and why your extension surface (mini_*) diverges.

Ingress. The RESP2/RESP3 frontend (kee-redis crate) and the HTTP admin API are the only untrusted entry points; every command maps to one Engine call. Engine. Owns the per-shard KeyId → KeyState maps, routes each submit to WAL (if durable) then to heap-top-or-wheel, and runs the active+lazy policy. Wheel/Heap. The timing backbone: O(1)-amortised insert via the hierarchical wheel, sub-tick accuracy via the heap-top; these two structures partition all outstanding deadlines disjointly (I6). Cron Driver. The single thread that owns wall-clock time; nothing else advances the wheel or pops the heap-top (§3 first architectural property, restated as I1/I4). Notification Sinks. One-way fan-out from a fired Deadline to zero or more consumers; no sink can push state back into the wheel. Clock Source. The sole owner of both clock domains; every other component reads through it, never through Instant::now()/SystemTime::now() directly. WAL. The source of truth for outstanding deadlines across a crash; recovery re-derives monotonic offsets from the wall-time-stamped records (§22.4). Replication. Consumes the same WAL stream, stamping each record with an HLC and shipping it to followers, which re-clock absolute deadlines locally rather than replaying a relative offset (P7).

Three properties hold everywhere downstream and are never contradicted by a later section: time flows one direction (clock → wheel/heap → fire → notify); the data path is one-way (ingress → engine → wheel/heap → notify, no back-edge); the WAL alone is the crash-recovery source of truth (the wheel's in-memory state is disposable).

6. Design Principles

  1. P1 — Monotonic time is the engine's time. All internal scheduling runs against CLOCK_MONOTONIC; CLOCK_REALTIME is read only at the API boundary (an EXPIREAT request) or for an outgoing notification's wall-time stamp. Tradeoff: every absolute deadline needs one extra conversion call. Operational implication: a wall-clock NTP step never perturbs an already-scheduled deadline (I5). Violating it: a wheel that stores wall time directly fires early or late on every NTP correction — the single most expensive bug class in timer systems (§27 Key Pitfall 1).
  2. P2 — Three primitives, one responsibility each. The wheel is the active path (O(1)-amortised steady state); the heap-top is the accuracy path (O(log 256) worst case); the WAL is the durability path (O(records) on recovery). Tradeoff: three codepaths to keep synchronized (I6) instead of one. Operational implication: each can be benchmarked, and regress, independently (§31). Violating it: merging wheel and heap logic reintroduces the O(log n) cost the wheel exists to avoid at 100M-key scale.
  3. P3 — Eviction is not expiration. A fire is "the deadline arrived"; an eviction is "memory is full, pick a victim" — related (a fire frees memory) but distinct (a no-TTL key is never expired but can be evicted; a live-TTL key can be evicted before its deadline). Tradeoff: this engine cannot alone bound memory under adversarial no-TTL growth. Operational implication: LRU-LFU-Cache (rank 59) owns the eviction half of the contract. Violating it: conflating the two produces a system where neither eviction nor expiration is independently correct or testable.
  4. P4 — The fire path does not allocate. Wheel pop, heap pop, and notification enqueue run against pre-allocated arenas (I11). Tradeoff: fixed arena capacity must be sized ahead of peak cardinality. Operational implication: tail latency is a function of cache behaviour, not allocator behaviour. Violating it: an allocator spike inside the fire path is indistinguishable from a GC pause and defeats the entire performance case for Rust (ADR-01).
  5. P5 — The active-expire cycle is bounded by wall time, not sample count. Following Redis (ADR-06): ≤ 25% of a 100 ms slice per cycle (I10); a cycle that cannot finish resumes next cycle from its recorded cursor. Tradeoff: a skewed key distribution can leave stale entries momentarily unswept. Operational implication: the foreground stall ceiling is predictable regardless of key distribution. Violating it (bounding by sample count instead): a pathological distribution can hold the shard lock arbitrarily long.
  6. P6 — Notifications are best-effort by default, durable on opt-in. KeyspaceEventSink drops on a slow subscriber rather than backpressuring the fire path; DurableSink opts into WAL-backed exactly-once-modulo-ack at the cost of two fsyncs per fire. Tradeoff: default delivery has no retry guarantee. Operational implication: consumers that need guarantees must explicitly choose DurableSink and pay its latency. Violating it (making every sink durable by default): halves throughput for the majority of consumers who never needed the guarantee.
  7. P7 — Replicated mode uses absolute deadlines, re-clocked on the follower. A PEXPIREAT ships as its absolute wall time; the follower converts to its own monotonic clock at apply time. Tradeoff: follower fire accuracy is bounded by that follower's own NTP skew, not by the primary's clock. Operational implication: this is the only correct replication strategy for a relative TTL under replication lag (§27 Key Pitfall 6). Violating it (replicating the relative offset): every deadline replays late by exactly the replication lag.
  8. P8 — No silent fallbacks. An insert past the wheel's maximum representable horizon returns a typed error; the engine never silently truncates it to the horizon. Tradeoff: callers must handle a rejection path. Operational implication: no deadline ever fires earlier than the caller specified without the caller's knowledge. Violating it: silent truncation produces a surprise-immediate-fire bug that is nearly impossible to trace back to its cause.
  9. P9 — The public API matches Redis's surface exactly. Same commands, same NX/XX/ GT/LT flags, same return-value semantics (TTL → -2/-1/seconds). Tradeoff: Redis's semantics are inherited even where this engine might prefer different ones. Operational implication: existing Redis clients drop in against this engine with zero code change (M-resp, §21). Violating it: every consumer needs a bespoke client.
  10. P10 — Recovery is bounded. A WAL of N outstanding deadlines recovers in O(N log K) where K is the hot level's slot count, with a small constant; recovery is checkpointable via a snapshot pinning a known LSN. Tradeoff: snapshotting costs a background CPU/IO budget. Operational implication: RTO is bounded by the inter-snapshot record count, not by total dataset size (§4, §35 D6). Violating it: RTO grows unbounded with total keyspace size, which is unacceptable at 100M-key scale.
  11. P11 — Sharding bounds blast radius. 256 fixed shards at boot (no dynamic resharding); a hot shard's active-expire cycle stall never blocks another shard's inserts. Tradeoff: shard count is a boot-time constant, not elastic. Operational implication: capacity planning must size shard count ahead of peak concurrency (§4). Violating it (dynamic resharding under load): a rehash-in-flight is a correctness hazard (in-flight deadlines can be observed twice or dropped) this engine refuses to hide behind "eventually consistent."
  12. P12 — Every stateful mutation is idempotent under replay. WAL replay (§22), HLC merge (§23), and generation-checked fire (I2, I7) must produce identical state whether applied once or twice. Tradeoff: every mutation needs an explicit idempotency key (the Generation field). Operational implication: crash recovery and replication both replay safely with no special-cased "have I seen this before" bookkeeping beyond the generation check. Violating it: a non-idempotent replay double-counts a fire or resurrects a persisted key on every recovery.

8. Domain Model

8.1 Timing-Wheel Structure

A HierarchicalWheel has NUM_LEVELS = 6 levels of SLOTS_PER_LEVEL = 64 slots each, tick resolution TICK_NS = 1,000,000 (1 ms, ADR-05). Level 0 advances every tick; level k advances every 64^k ticks. A deadline's level is ⌊log₆₄(Δticks)⌋; its slot within that level is (Δticks >> (6·level)) & 0x3F. Horizon: 64^6 ticks × 1 ms = 68,719,476,736 ms ≈ 795 days ≈ 2.18 years — see §35 D1 for the derivation and why this exceeds every realistic TTL by construction.

8.2 Deadline Record Layout (Wheel-Resident)

Node { key: KeyId (u64, 8B), generation: Generation (u32, 4B),
       deadline: MonotonicNs (u64, 8B), next: ArenaIdx (u32, 4B) }   // 24B, arena-pooled

8.3 WAL Record Format

Length-prefixed varint, payload, CRC32C trailer (Castagnoli polynomial, hardware-accelerated via _mm_crc32_u64 on x86-64):

| varint length | tag:u8 | payload (tag-specific) | crc32c:u32 |
tag ∈ { Insert(key,generation,deadline_wall_ns:i128),
        Persist(key,generation),
        Tombstone(key,generation,fired_at_wall_ns:i128),
        Snapshot(lsn:u64, path) }

8.4 HLC Timestamp Format

Hlc { wall_ms: u64, logical: u32, node_id: u32 } — 16 bytes, millisecond wall resolution (sufficient for ordering; sub-ms ordering is the logical counter's job, §23.2).

8.5 Worked Example — Insert → Cascade → Fire

now = MonotonicNs(0). PEXPIRE k 130 (130 ms). Δticks = 130. 130 < 64 is false, so level ≥ 1: ⌊log₆₄(130)⌋ = 1; slot = (130 >> 6) & 0x3F = 2. Node lands in level-1 slot 2. At now = 128 ms level-0's cursor wraps (128 / 1 = 128 ticks = 2 full level-0 rotations of 64), triggering a cascade of level-1's current slot (slot 2, since 128 / 64 = 2) down into level-0: the node is re-inserted with Δticks = 130 − 128 = 2, landing in level-0 slot 2. Two ticks later (now = 130 ms), level-0's cursor reaches slot 2 and the node fires — within the 1 ms tick tolerance (M7).

8.7 Malformed-Input Examples

EXPIREAT key 0 — valid, means "fire immediately"; must not be interpreted as "no deadline" (§21.6 pitfall). PEXPIRE key -5 — negative relative TTL: InsertError::AlreadyPast, engine fires immediately rather than rejecting (matches Redis's EXPIRE semantics: a past deadline deletes/expires the key at once). EXPIRE_MANY COUNT 500000 ... — count exceeds the 100,000 bulk cap (§21.6): parser rejects with a typed ExpireError::BulkCountExceeded before reaching the engine. PEXPIREAT key 99999999999999999999 — exceeds MonotonicNs's representable horizon after wall_to_monotonic conversion: InsertError::PastHorizon (P8, no silent truncation).

8.8 Failure-Path Example

Follower receives an Insert WAL record with HLC (wall_ms= 1000, logical=0, node_id=A) followed, due to network reordering, by a Tombstone record with HLC (wall_ms=999, logical=3, node_id=A) for the same key/generation. Per I9, the follower detects merge() would violate causality (tombstone's HLC precedes the insert's observed HLC for the same node) and rejects the tombstone, re-requesting the correct ordering from the primary (§23.4) rather than applying out-of-order and risking a resurrected-after-fire key.

13. Phase 1 — Clock Source & Time Domain Types

13.1 Objectives

Land MonotonicNs/WallNs/Ns (§11) and the ClockSource trait (P1); this is the foundation Phase 16 (wheel) and Phase 23 (replication) both build on, and the place the type system buys the most correctness for the least runtime cost.

13.2 Detailed Implementation Steps

  • Newtype enforcement: MonotonicNs/WallNs constructed only via ClockSource or a pub(crate)-only _unchecked constructor reserved for the WAL recovery path (§22.4). Arithmetic is named-method-only (MonotonicNs::add(Ns), MonotonicNs::sub(MonotonicNs) -> Ns) — no blanket Add impl that would hide the type distinction (P1).
  • RealClock: clock_gettime(CLOCK_MONOTONIC) / clock_gettime(CLOCK_REALTIME) via libc/nix; wall_to_monotonic samples both clocks twice and accepts the pair with the smaller observed monotonic delta (bounds offset error to that delta, typically < 1 µs).
  • MockClock: two AtomicU64 cells, test-only, lets tests advance time deterministically.
  • SimulatedClock: MockClock plus modeled NTP step events, used by §23.8's clock-step test and I5's verification.
  • Cite Mills 2003 / RFC 5905 (§5) for the skew model this conversion assumes.

13.3 Deliverable

kee-core::clock compiles; RealClock, MockClock, SimulatedClock all implement ClockSource; a property test proves I4 (monotonic non-decreasing) under a mocked backward-stepping wall clock.

13.4 Acceptance Criteria

  • Property test: 10,000,000 sequential MonotonicNs::now() calls are non-decreasing, even while MockClock's wall cell steps backward 100 times during the run.
  • Microbenchmark: MonotonicNs::now() < 30 ns p50 on the reference Linux host (M-clock, §31).
  • cargo test -p kee-core clock:: exits 0 with ≥ 5 test cases.

13.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/wheel/ntp_step_backward.jsonl wall clock steps back 1s mid-run monotonic sequence still non-decreasing
conformance/corpora/wheel/ntp_step_forward.jsonl wall clock steps forward 1h mid-run wall_to_monotonic reflects the new offset within 1 sample pair

13.6 Pitfalls

  • std::time::Instant doesn't expose raw nanoseconds-since-boot and loses precision past ~250 years through Duration — use clock_gettime via libc/nix directly.
  • CLOCK_MONOTONIC_RAW is Linux-only; use plain CLOCK_MONOTONIC (NTP-slewed but never stepped) for macOS portability.
  • On macOS, mach_absolute_time's conversion factor is constant per boot but not across machines — cache it at first call, never hardcode it.

13.7 Performance Concerns

wall_to_monotonic's two-sample-pair technique costs two extra clock_gettime calls per absolute-deadline insert (~20–40 ns each) — amortised into the ≤ 1 µs p99 insert budget (M5) but tracked separately in the benchmark harness (§24.3) so a regression here is attributable.

13.8 Edge Cases

  • Absolute deadline exactly at WallNs::now() (zero-offset EXPIREAT): must convert to MonotonicNs::now() exactly, not underflow into a negative Ns.
  • Host suspend/resume (laptop lid close): CLOCK_MONOTONIC does not advance during suspend on Linux (unlike CLOCK_BOOTTIME) — documented as an explicit non-goal; a suspended host's outstanding deadlines fire "late" by the suspend duration, consistent with P1 (monotonic time is the engine's time, and suspend is invisible to it).

13.9 Failure Analysis

A ClockSource bug (e.g. wall_to_monotonic overflow) manifests as every absolute deadline in a shard misfiring simultaneously — detection via I5's property test and the kee_monotonic_regression_total telemetry (I4); containment is per-shard (P11) since each shard reads the same global clock but the bug's blast radius is process-wide, not shard-scoped — recovery is a process restart plus a clock-source hotfix.

13.10 Operational Notes

Metric: kee_clock_wall_to_monotonic_epsilon_ns (histogram) — the observed conversion error per call, alerted if p99 exceeds 5 µs (indicates host clock jitter beyond the documented tolerance).

14. Phase 2 — Single-Level Hashed Wheel

14.1 Objectives

Build the simplest correct wheel — one level of SLOTS_PER_LEVEL slots — as both the first working scheduler and the literature-accurate "hashed timing wheel" baseline (Varghese & Lauck 1987, §3).

14.2 Detailed Implementation Steps

  • Slot index: (deadline.0 / TICK_NS) % SLOTS_PER_LEVEL (P2: the wheel is the sole active path at this stage; the heap-top and hierarchical cascade arrive in §16/§17).
  • Fire path scans the current slot in O(k) where k is slot occupancy, applying the I7 generation check per node before notifying.
  • Horizon rejection: a deadline whose Δticks ≥ SLOTS_PER_LEVEL returns InsertError::PastHorizon (P8) — this is the exact gap the hierarchical wheel (§16) closes.
  • Arena: slot lists are singly-linked, arena-index-based (ArenaIdx: u32), never Vec-backed (I11 anchored from this phase forward).

14.3 Deliverable

A 64-slot single-level wheel (kee-core::wheel::SingleLevelWheel) that fires every inserted deadline within its 64 ms horizon and rejects everything past it with a typed error.

14.4 Acceptance Criteria

  • Property test (ADR-21, proptest): for any sequence of inserts within-horizon, the fired multiset over one full rotation equals the inserted multiset.
  • Microbenchmark: 1,000,000 insert+fire round trips complete in < 50 ms single-threaded (the wheel's headline number vs the heap baseline's 200 ms, §15.4).
  • Horizon-rejection test: a deadline at Δticks = 64 (one past the max valid 63) returns InsertError::PastHorizon, never a silent truncation.

14.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/wheel/random.jsonl 1,024 random within-horizon inserts fired multiset matches inserted set
conformance/corpora/wheel/past_horizon.jsonl inserts at Δticks ∈ {64, 1000} both rejected with PastHorizon

14.6 Pitfalls

  • Vec::push/Vec::pop for slot lists destroys cache locality under load — arena-backed linked list only (I11).
  • deadline.0 / TICK_NS computed as i64 instead of u64 wraps negative for large deadlines — must be unsigned.

14.7 Performance Concerns

Slot-list scan cost is O(occupancy); a skewed insert pattern (many deadlines in one slot) degrades the fire path locally — this is the exact motivation for the hierarchical cascade (§16) which bounds per-level occupancy statistically, not the single-level scan cost itself.

14.8 Edge Cases

  • Δticks = 0 (fire on the very next tick): must land in the current slot's list, not be silently dropped as "already past."
  • Two deadlines with identical (key, generation) inserted twice (a submit retry): the second insert must be routed through Engine::submit's CAS path (§19.3), not the wheel's raw insert(), which has no dedup of its own.

14.9 Failure Analysis

An off-by-one in slot indexing manifests as every 64th deadline firing one tick early or late — detected by the ADR-21 property test's shrinking (a minimal failing case isolates the exact Δticks boundary); contained to the single-level wheel (no cascade yet to propagate the bug); recovery is a index-arithmetic fix plus a regression fixture added to conformance/corpora/wheel/.

14.10 Operational Notes

No production deployment target for this phase (Phase 5/§17 is the first production construction) — this phase exists purely as the literature-accurate baseline and conformance oracle for every later wheel refinement.

15. Phase 3 — Sorted-Heap Baseline

15.1 Objectives

Land HeapDeadlineQueue, a BinaryHeap-backed reference implementation, in parallel with the wheel work — it exists as the conformance oracle (any wheel construction must match its fire ordering given identical inputs) and as a performance lower bound (P2).

15.2 Detailed Implementation Steps

  • HeapDeadlineQueue implements DeadlineQueue (§11) over BinaryHeap<Reverse<Deadline>> — Reverse because BinaryHeap is a max-heap by default and the earliest deadline must pop first.
  • advance_to(t) pops while peek().deadline <= t, returning the fired Vec<Deadline> in ascending-deadline order (matches the DeadlineQueue contract, §11).
  • No arena, no cascade — this structure intentionally does not implement P4 (fire-path allocation-free); it is the baseline P4 exists to beat.

15.3 Deliverable

HeapDeadlineQueue passing the same DeadlineQueue conformance tests as the wheel constructions in §14/§16/§17, establishing the shared oracle.

15.4 Acceptance Criteria

  • Property test: 1,000,000 random deadlines inserted, advanced one tick at a time, fire order matches a sorted reference vector exactly.
  • Microbenchmark: 1,000,000 insert+fire round trips complete in < 200 ms single-threaded — the number the hierarchical wheel's < 30 s / 100M (300 ns/insert, §16.4) and the single-level wheel's < 50 ms / 1M (§14.4) are measured against.

15.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/wheel/heap_baseline.jsonl 1,024 random inserts, full drain ascending-deadline fire order

15.6 Pitfalls

  • Forgetting the Reverse wrapper fires deadlines in descending order — a subtle bug that only manifests when comparing against another queue's order, not in isolation.
  • BinaryHeap::pop is O(log n); under sustained load this cost is exactly what the hierarchical wheel (§16) exists to amortise away.

15.7 Performance Concerns

This structure is deliberately the slow reference; its cost model (Go's runtime timer heap, §5 Reference Implementations) is cited specifically so a reviewer can attribute the wheel's speedup to a named, real alternative rather than an invented straw man.

15.8 Edge Cases

  • Two deadlines with an identical MonotonicNs value: Ord tie-breaks on (key, generation) deterministically (mirrors HeapEntry's tie-break, §11) so replay is reproducible.
  • Empty heap advance_to call: returns an empty Vec, never panics on peek() of an empty heap.

15.9 Failure Analysis

A tie-break inconsistency between this baseline and the wheel constructions would produce a conformance false-positive-fail (different orderings, both individually "correct") — detection is the property test comparing exact Vec equality, not just set equality; recovery is aligning both structures' tie-break rule to the same (key, generation) order.

15.10 Operational Notes

HeapDeadlineQueue ships in the conformance harness only, never in the production Engine construction (§19) — documented explicitly in conformance/README.md so no future contributor mistakes it for a production fallback path.

16. Phase 4 — Hierarchical Wheel With Cascading

16.1 Objectives

Implement the multi-level wheel from Varghese & Lauck §4 with Tokio's constants (ADR-03): the construction that removes the single-level wheel's 64-tick horizon ceiling (§14.3) and delivers the 100M-key, O(1)-amortised insert this project is named for.

16.2 Detailed Implementation Steps

  • Level assignment: level = ⌊log₆₄(Δticks)⌋; slot = (Δticks >> (6·level)) & 0x3F (§8.1, ADR-03). This is P2's "active path" primitive.
  • Cascade: on level-0 cursor wrap (63→0), level-1's current slot drains and each entry re-insert()s with Δticks recomputed against the current self.now — only one level cascades per level-0 wrap; cascading all six levels unconditionally is the classic bug (§16.6).
  • Generation check (I7) on every fire: a node whose generation disagrees with the shard's current KeyState.generation is dropped silently — this is what makes PERSIST/ re-EXPIRE (§19) O(1) without a wheel-side removal.
  • Recursion guard: cascade(level) returns immediately at level >= NUM_LEVELS.

16.3 Deliverable

HierarchicalWheel (§11) passing the DeadlineQueue conformance oracle (§15.3) against arbitrary insert/advance sequences at 100M-key cardinality.

16.4 Acceptance Criteria

  • Property test: identical fire order/multiset vs HeapDeadlineQueue (§15) over 10,000 randomized insert/advance sequences (ADR-21).
  • Microbenchmark: 100,000,000-key insert completes in < 30 s single-threaded (≤ 300 ns amortised per insert, M4) — the headline number System Constraints (§4) is built on.
  • Microbenchmark: 10,000,000 pre-populated deadlines sustain > 10,000,000 fires/sec (M3).

16.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/wheel/cascade.jsonl every level boundary (63→0 through level 4→5) no deadline lost across any cascade
conformance/corpora/wheel/generations.jsonl stale-generation fires interleaved with live ones stale entries silently dropped, live ones notify

16.6 Pitfalls

  • Cascading all six levels unconditionally on a level-0 wrap instead of exactly one level — cascade only the level whose cursor actually wrapped.
  • Re-insert() during cascade computing Δticks against a stale self.now instead of the just-advanced value — re-overflows into the wrong level.
  • Missing the % SLOTS_PER_LEVEL reduction after adding the cursor offset to a slot index — out-of-bounds indexing under sustained load, not caught until a specific rotation.

16.7 Performance Concerns

Cascade cost is O(slot occupancy) per level per wrap — amortised O(1) per insert across the wheel's lifetime (the standard timing-wheel amortised-cost argument, Varghese & Lauck §3); a pathological distribution concentrating all inserts at one deep-level slot degrades a single cascade event, bounded by I10's wall-time budget in the active-expire overlay (§18), not by this structure alone.

16.8 Edge Cases

  • A deadline inserted exactly at a level boundary (Δticks = 64^k exactly): must resolve to level k, slot 0 — an off-by-one here is the single most common hierarchical-wheel bug (cross-checked against the property test's boundary-focused shrinking, ADR-21).
  • Wheel epoch rolling over u64 nanoseconds (~584 years since epoch): documented non-issue given the realistic deployment lifetime, but the arithmetic uses wrapping_add deliberately (§11) rather than panicking on overflow.

16.9 Failure Analysis

A cascade bug that loses a deadline is the single highest-severity defect this phase can produce (violates I2/I8); detection is the cascade conformance fixture (§16.5) plus the 24-hour soak's continuous I1–I13 assertions; containment is process-wide (the wheel is a process-global structure, not sharded — P11 shards the KeyState map, not the wheel itself); recovery is a hotfix plus a regression fixture capturing the exact failing rotation.

16.10 Operational Notes

Metric: kee_wheel_levels{level} (gauge, per-level slot occupancy) — an operator-visible signal for TTL-distribution skew; a persistently hot single level/slot combination is the trigger for ADR-03's "revisit level geometry" escape hatch.

17. Phase 5 — Hybrid Wheel + Heap-Top

17.1 Objectives

Graft the fixed-capacity heap-top (ADR-04) onto the hierarchical wheel for sub-tick accuracy — the exact construction Tokio ships (§5 Reference Implementations) and the one this project recommends for production deployments needing ± sub-ms accuracy on short deadlines.

17.2 Detailed Implementation Steps

  • Split: a deadline whose offset is within top_horizon (default 16 ms = 16 ticks, ADR-04) routes to the heap-top instead of the wheel (I6: the two structures partition disjointly).
  • Cron-tick order: heap-top is consulted before the wheel's advance_to() — popping every entry whose deadline <= now first, then advancing the wheel against the post-heap-top now (§17.9 pitfall if reversed).
  • Capacity/eviction: heap-top capacity is fixed (256, ADR-04); on overflow the farthest-deadline entry evicts atomically into the wheel under the wheel's lock — I6 requires this eviction and the wheel insert to be a single atomic step.
  • Tie-break: heap-top order is deadline ascending, ties broken by (key, generation) (mirrors §15.8's baseline tie-break for deterministic replay).

17.3 Deliverable

The hybrid Engine-internal scheduler (wheel + heap-top) passing the same DeadlineQueue-shaped conformance oracle at top_horizon = 0 (degenerate: heap-top empty, wheel-only, must match §16.3 exactly) and at top_horizon = 16 ms (representative case).

17.4 Acceptance Criteria

  • Conformance: both degenerate and representative top_horizon configurations pass the wheel-vs-heap-baseline oracle (§15.4) with zero fire-order divergence.
  • Latency benchmark: with top_horizon = 16 ms, p95 fire latency for a deadline 1 ms in the future is < 200 µs on an unloaded reference host (M6).
  • ADR-04's capacity-256 choice is justified by an empirical sweep recorded in benchmarks/results/heap_top_capacity_sweep.json (§35 D4).

17.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/wheel/sub_tick.jsonl deadlines within top_horizon fire within 200 µs p99 of deadline
conformance/corpora/wheel/heap_top_overflow.jsonl > 256 concurrent near-term deadlines oldest evicts to wheel, none lost

17.6 Pitfalls

  • Consulting the wheel before the heap-top: a deadline that should fire at now − 100 µs from the heap-top instead fires at now + 1 ms from the wheel, defeating the entire construction's purpose — heap-top must run first, every tick.
  • Heap-top order must tie-break deterministically ((key, generation)) — an inconsistent tie-break makes replay non-reproducible (§17.10's determinism test would catch this).
  • "Evict oldest into wheel" performed as two non-atomic steps (pop then insert) can lose a deadline if a concurrent reader observes the gap — must be one atomic step under the wheel's lock. PhaseDeferred("§17.6") covers moving this to a lock-free compare-and-swap path if profiling later shows lock contention here.

17.7 Performance Concerns

The heap-top's O(log 256) worst-case pop/push is negligible relative to the wheel's O(1)-amortised path — the capacity-256 choice (§35 D4) is specifically sized so this cost never dominates the cron-tick budget (§19.7).

17.8 Edge Cases

  • top_horizon = 0 exactly: every insert routes to the wheel, heap-top permanently empty — must not special-case this into a code path divergent from the general case (conformance §17.5 exercises this explicitly).
  • A deadline that straddles the heap-top/wheel boundary exactly (Δ == top_horizon): documented as wheel-routed (closed lower bound on the wheel side), consistently applied in both submit() (§19.3) and eviction (§17.2).

17.9 Failure Analysis

A heap-top/wheel ordering bug (consulting wheel first) manifests as a systematic sub-tick-accuracy regression, not a correctness violation — detection is the latency benchmark (§17.4) regressing past 200 µs p99 in CI (§31 M-table gate); containment is process-wide since the cron driver is a single thread; recovery is reverting the tick-order change and adding a regression test asserting heap-top-before-wheel ordering explicitly.

17.10 Operational Notes

Metric: kee_heap_top_size (gauge) — an operator-visible early-warning signal; sustained saturation at capacity 256 is the trigger to reconsider ADR-04's capacity or top_horizon value for the observed workload.

18. Phase 6 — Active + Lazy Expiration Policy & Memory-Pressure Feedback

18.1 Objectives

Bound memory occupied by deadlines that have technically fired but whose wheel-resident node has not yet been swept — the active-expire cycle (Redis-ported, ADR-06) plus mandatory lazy-on-access expiration (ADR-07) plus a memory-pressure escalation path.

18.2 Detailed Implementation Steps

  • Active cycle: samples the wheel's two hottest levels (0, 1) slot-by-slot from the current cursor, bounded by wall time (25% of a 100 ms slice, P5/I10) rather than sample count (ADR-06); fires anything already past now; records a resumable cursor position if the budget expires mid-sweep.
  • Lazy probe: every keyed read checks KeyState.deadline under the shard lock (P11); a passed deadline fires immediately and removes the shard entry, leaving the wheel's node stale for I7's generation check to absorb later.
  • Memory-pressure feedback: subscribes to the host's cgroup MemoryHigh notification (or an operator-configured threshold); escalates the active cycle's budget Low→25ms, Medium→50ms, High→100ms, Critical→immediate synchronous force_expire_pass().
  • Cites Cao/Felten/Li 1994 and Fitzpatrick 2004 (§5) for the eviction-vs-expiration boundary (P3) this policy respects: pressure escalates expiration sweep aggressiveness, never triggers an eviction decision (that remains LRU-LFU-Cache's, rank 59).

18.3 Deliverable

ActiveExpirePolicy + check_lazy() wired into kee-core::policy/lazy.rs, plus a PressureLevel enum and on_memory_pressure() handler, each independently testable.

18.4 Acceptance Criteria

  • End-to-end: 1,000,000 keys with TTLs uniform in [0, 1 hour], 10 simulated minutes with zero foreground reads — every passed deadline fires within ± 25 ms (M8).
  • PressureLevel::Critical injection on a 10,000,000-key wheel completes its forced expire pass in ≤ 1 s (M10).
  • Lazy path: a key with a 100 µs TTL, read at 200 µs, returns LazyResult::Expired and the corresponding Notification is enqueued.

18.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/policy/active_cycle.jsonl skewed TTL distribution, active-only all past-deadlines fire ≤ 25 ms late
conformance/corpora/policy/lazy.jsonl interleaved reads before/after deadline correct Expired/Live results
conformance/corpora/policy/memory_pressure.jsonl injected pressure escalation sequence budget matches the documented ladder

18.6 Pitfalls

  • Bounding the active cycle by sample count instead of wall time (rejected in ADR-06) — a skewed distribution can then hold the shard lock arbitrarily long, violating I10.
  • The lazy path firing a key whose wheel node then becomes stale: do not attempt to remove it from the wheel synchronously (O(slot occupancy)) — let I7's generation check absorb it on its eventual, harmless fire.
  • Delivering memory-pressure events from inside the cron tick itself would let a pressure handler recurse into the tick that invoked it — pressure events must arrive on a separate thread posting to the engine's command queue (§19.2).

18.7 Performance Concerns

The active cycle's per-slot sample cost competes with the shard lock the lazy path also takes — P11's per-shard sharding bounds this contention to one shard at a time, never process-wide; the wall-time budget (I10) is the hard ceiling on this contention's foreground-visible cost.

18.8 Edge Cases

  • A key with no TTL at all (KeyState absent): lazy probe must return LazyResult::NoTtl without touching the wheel or WAL — a no-TTL key is never expired (P3).
  • Active cycle running concurrently with a cascade (§16.2) on the same level: both must observe a consistent slot-list snapshot — enforced by the same per-level lock the cascade already takes.
  • PressureLevel::Critical firing during an in-progress force_expire_pass(): the second invocation must be a no-op (idempotent, P12), not a re-entrant double-sweep.

18.9 Failure Analysis

An active cycle that fails to yield within its budget (a bug bypassing I10's check) manifests as elevated foreground insert latency on the affected shard; detection is the kee_active_cycle_duration_seconds histogram's p99 alert (I10 telemetry); containment is per-shard (P11); recovery is identifying and fixing the budget-check bypass, with a regression fixture added to conformance/corpora/policy/active_cycle.jsonl.

18.10 Operational Notes

Metrics: kee_active_cycle_sampled_total, kee_active_cycle_fired_total (ratio informs the adaptive-rate heuristic Redis's expire.c uses, §5); kee_memory_pressure_level (gauge) surfaced on the operator dashboard (§27) alongside a MemoryPressure structured log event on every escalation.

19. Phase 7 — Engine Integration & Cron-Driver Loop

19.1 Objectives

Wire the wheel, heap-top, active+lazy policy, per-shard maps, and notification sinks into a single Engine (§11) and expose the cron-driver loop that owns wall-clock time process-wide (§3's "nothing else advances the wheel").

19.2 Detailed Implementation Steps

  • Cron-driver loop: each iteration reads monotonic_now() once, runs the heap-top-then- wheel cron_tick() (§17.2), notifies every fired Deadline, runs the active-expire cycle at the policy's current budget (§18.2), then sleeps for tick_period − elapsed (never a flat tick_period, §19.6 pitfall).
  • submit(): computes the target MonotonicNs from DeadlineSpec (§11), acquires the shard entry (P11), checks the if_ flag (NX/XX/GT/LT, P9) against the current state before mutating anything, increments Generation (P12), appends to the WAL if Durability::DurableLog (I3) before returning the Handle, then routes to heap-top or wheel by top_horizon comparison (§17.2).
  • Memory-pressure events (§18.2) arrive via a dedicated command-queue channel, never inline in the tick.
  • Graceful shutdown drains in-flight WAL appends and cron-tick work before returning, target ≤ 2 s (§4).

19.3 Deliverable

Engine::run_forever() driving a live wheel+heap+policy+sinks stack; Engine::submit()/ ttl()/persist()/force_expire_pass() fully wired and independently callable.

19.4 Acceptance Criteria

  • Stress test: 1,000,000 random-TTL submits, cron loop run to drain — every key fires within ± 2 ticks of its deadline.
  • Determinism test: two Engines driven by MockClock in lockstep from identical submit sequences produce bit-identical notification streams (verifies P12/I2 jointly).
  • Graceful-shutdown test: Engine::shutdown() returns with zero outstanding fires queued and zero leaked arena nodes (valgrind --leak-check=full clean).

19.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/wheel/million_key_stress.jsonl 1M submits, full drain all fire within ± 2 ticks
conformance/corpora/wheel/determinism.jsonl identical submits, two engines bit-identical notification order

19.6 Pitfalls

  • Sleeping for a flat tick_period instead of tick_period − elapsed — every cycle runs one elapsed-time longer than the last, and the effective tick rate slows unboundedly over a long-running process.
  • Holding the shard lock across the WAL append inside submit() — a slow disk then stalls every other inserter hitting that shard; the WAL append must sit outside the lock with a pre-check before acquiring it.
  • Logging a WAL record before the if_ flag rejects the submit — a rejected condition must never appear in the durable log (ordering matters, mirrored in §22.6).

19.7 Performance Concerns

The cron tick's total per-iteration budget is TICK_NS (1 ms) minus the active-expire cycle's allotted slice (§18.2) minus the notification-dispatch cost (§20) — every subsystem wired in this phase competes for the same 1 ms window, making this phase's integration test the first place a cross-subsystem tail-latency regression is visible.

19.8 Edge Cases

  • submit() racing a concurrent PERSIST on the same key: the Generation CAS (P12) resolves the race deterministically — whichever mutation observes the current generation first wins, the loser retries against the new generation.
  • Shutdown requested mid-cascade (§16.2): the cascade must complete atomically before the shutdown drain proceeds — partial cascades are never observable externally.
  • Clock read failure (clock_gettime syscall error, exceedingly rare): documented as process-fatal rather than silently substituting a stale value (P8's no-silent-fallback principle extended to the clock boundary itself).

19.9 Failure Analysis

A cron-driver deadlock (e.g. a lock-ordering inversion between the active-expire cycle and submit()'s shard lock) manifests as the entire process stalling — detection is a liveness watchdog metric (kee_cron_tick_last_completed_seconds, alerting if stale beyond 3× TICK_NS); containment is process-wide (the cron driver is a single thread by design, §19.1); recovery is a process restart plus WAL-based recovery (§22), with the specific lock-ordering bug fixed and a regression test added exercising the exact interleaving.

19.10 Operational Notes

Metrics: kee_cron_tick_last_completed_seconds (liveness), kee_outstanding_deadlines_total (gauge, sum across wheel+heap-top). Deployment: the cron driver runs on a dedicated OS thread (not a cooperative async task, §5 Tokio pitfall) to avoid starvation under unrelated async load in an embedding host process.

20. Phase 8 — Notification Sinks

20.1 Objectives

Land KeyspaceEventSink (Redis-compatible), WebhookSink (HMAC-signed), DurableSink (WAL-backed exactly-once-modulo-ack), and the pluggable Sink trait (§11) user code implements for custom downstreams.

20.2 Detailed Implementation Steps

  • KeyspaceEventSink: subscribers register a key-pattern filter; delivery is RESP3 push frames (§8.3-adjacent wire format); best-effort by default (P6) — a full outbound channel drops the event and increments dropped_total, never backpressures the fire path (I13).
  • WebhookSink: HTTP POST with an X-Kee-Signature header, HMAC-SHA-256 over the raw body bytes (never over a re-serialized representation — §20.6 pitfall), exponential backoff with jitter, capped at 5 retries (ADR-18).
  • DurableSink: writes the notification to the WAL before delivery is attempted; the subscriber's ack (RESP +OK or HTTP 2xx) tombstones the WAL entry, keyed by (notification, subscriber_id) so one subscriber's ack never tombstones another's pending delivery (§20.6); un-tombstoned entries re-deliver on restart (ADR-19).
  • All three sinks run behind a bounded async queue with a per-sink timeout enforcing I13 (MAX_SINK_DELIVER_DURATION, default 100 ms) — never inline on the cron-driver thread.

20.3 Deliverable

kee-core::notify exposing Sink, KeyspaceEventSink, WebhookSink, DurableSink, each independently unit-testable and wired into Engine's sinks: Vec<Box<dyn Sink>> (§11).

20.4 Acceptance Criteria

  • A subscriber with a permanently-full channel sees dropped_total increment and the fire path's p99 latency is unaffected (< 1 µs regression, verified against M5).
  • A webhook subscriber returning HTTP 503 is retried exactly 5 times then recorded in failed_total, never retried a 6th time.
  • A DurableSink subscriber that never acks, across an injected engine crash and restart, receives the notification exactly once more (re-delivery, not duplication of an already- acked one).

20.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/notify/keyspace.jsonl slow-subscriber scenario dropped_total increments, fire path unaffected
conformance/corpora/notify/webhook.jsonl 503-then-recover sequence exactly 5 retries, correct HMAC on every attempt

20.6 Pitfalls

  • HMAC computed over a re-serialized JSON representation instead of the exact body bytes sent — a field-order change between signing and sending breaks verification on the receiving end.
  • DurableSink's tombstone key omitting the subscriber id — one subscriber's ack incorrectly tombstones another's still-pending delivery of the same notification.
  • Running any Sink::deliver inline on the cron-driver thread instead of the bounded queue — a single slow sink then stalls every fire in that tick (violates I13 by construction, not just under load).

20.7 Performance Concerns

The bounded async queue's enqueue cost (an atomic push, not a syscall) is the only cost the cron-driver thread pays per notification — actual sink I/O (HTTP POST, WAL append) runs on a separate thread pool, keeping the fire path's allocation-free/syscall-free guarantee (P4, I11) intact even as sinks proliferate.

20.8 Edge Cases

  • Zero registered sinks: Engine::notify() is a no-op, not an error — a fire with no consumer is a valid, common state (nobody subscribed to this key's keyspace events).
  • A sink registered mid-flight while a notification is already enqueued for delivery: documented as "may or may not observe events enqueued before registration" — no retroactive delivery guarantee.
  • DurableSink crash exactly between WAL append and delivery attempt: recovery (§22.4) re-delivers, since the WAL entry has no tombstone yet — correctly idempotent per P12.

20.9 Failure Analysis

A sink that silently blocks past its timeout (a bug in the bounded-queue timeout logic) manifests as elevated kee_notification_dropped_total{sink} with no corresponding increase in successful deliveries; detection is that metric's rate alert; containment is per-sink (each sink's queue is independent); recovery is disabling the offending sink via its name()-keyed config and filing the bug against that sink's implementation.

20.10 Operational Notes

Metrics: kee_notification_dropped_total{sink}, kee_notification_failed_total{sink}. Deployment: WebhookSink's HMAC secret rotates via a documented dual-secret window (old + new both accepted during rotation, docs/api/resp.md cross-references the rotation API, a Phase-1 stretch surface).

21. Phase 9 — Public API & Redis-Compatible Frontend

21.1 Objectives

Land the RESP2/RESP3 frontend (kee-redis crate) and the full EXPIRE/PEXPIRE/ EXPIREAT/PEXPIREAT/TTL/PTTL/PERSIST command surface plus the mini_* bulk/admin extensions (P9).

21.2 Detailed Implementation Steps

  • Command surface: EXPIRE/PEXPIRE/EXPIREAT/PEXPIREAT <key> <ttl> [NX|XX|GT|LT]; TTL/PTTL <key> returning -2 (no key), -1 (no TTL), or remaining time — byte-exact match to Redis's documented return semantics (§5 RFCs/Specifications, P9). PERSIST <key> returns 0/1. Bulk: EXPIRE_MANY COUNT <n> KEYS <k1..> TTLS <t1..>, TTL_MANY COUNT <n> KEYS <k1..> (mini_* extensions, documented at docs/api/resp.md). Admin: SCAN_DEADLINES CURSOR <c> COUNT <n>, FORCE_EXPIRE_PASS.
  • RESP parser: streaming, async I/O; malformed input returns -ERR <message> and keeps the connection open (never terminates on a single bad frame).
  • Flag validation: NX/XX/GT/LT mutual-exclusion checked in the parser, before the engine ever sees the request (§21.6 edge case).
  • Bulk cap: EXPIRE_MANY/TTL_MANY counts > 100,000 rejected at the parser (§21.6), preventing an unbounded-allocation DoS (T2, §25).
  • EXPIRE_MANY submits all deadlines within one cron-driver iteration, amortising lock acquisition and WAL group-commit (§21.4).

21.3 Deliverable

A redis-cli-compatible RESP frontend on a configurable TCP port; keectl (kee-cli crate) issuing admin commands against it.

21.4 Acceptance Criteria

  • redis-cli -p 6380 EXPIRE foo 10 against the running engine returns byte-identical RESP to redis-server's response for the same command.
  • EXPIRE_MANY of 1,000,000 keys completes in < 100 ms single-threaded (< 100 ns/insert amortised, matching M2's WAL-inclusive throughput floor).
  • keectl scan-deadlines --count 100 returns exactly the next 100 outstanding deadlines in cursor order, matching SCAN_DEADLINES's documented cursor semantics.

21.6 Pitfalls

  • EXPIREAT key 0 is a valid "fire immediately" request — the engine must not interpret 0 as "no deadline provided" (this exact confusion is a documented Redis-clone bug class).
  • Unbounded EXPIRE_MANY counts risk an OOM before the parser even validates individual entries — the 100,000 cap is enforced before array allocation, not after.
  • NX/XX/GT/LT combinations that are individually valid but mutually exclusive (e.g. NX GT together) must be rejected by the parser, not passed through to submit()'s if_ flag (which assumes exactly one variant, §11).

21.7 Performance Concerns

The RESP parser's per-frame allocation (for variable-length bulk strings) is the one allocation this phase deliberately accepts outside the fire path (§3's ingress-vs-fire-path boundary) — bounded by the FD budget (§4, ≤ 65,536 concurrent connections) and profiled separately from the allocation-free fire-path guarantee (I11).

21.8 Edge Cases

  • A RESP3 client that never reads its push-frame socket buffer: the keyspace-event sink's bounded queue (§20.2) fills and drops, never blocking the frontend's request/response path for that same connection.
  • TTL issued for a key mid-fire (the deadline passes between the shard lookup and the response formatting): documented as returning either the last-known remaining time or -2, whichever the lazy probe (§18.2) observes first — a benign race, not a correctness violation (no invariant requires linearizable TTL reads).

21.9 Failure Analysis

A parser bug accepting a malformed frame as valid (e.g. missing bulk-length validation) is the highest-severity defect this phase can introduce (T2, §25); detection is the resp_fuzz target (fuzz/, ADR-22) running continuously in fuzz.yml; containment is per-connection (a malformed frame on one connection cannot corrupt another's state); recovery is a parser patch plus a new fuzz-derived regression corpus entry.

21.10 Operational Notes

Metrics: per-command counters (kee_resp_commands_total{command}), per-connection byte counters. Compatibility: every divergence from Redis's documented behaviour is a mini_* extension, itemized in docs/api/resp.md, cross-referenced from Compatibility & Versioning.

22. Phase 10 — Durability: WAL & Crash Recovery

22.1 Objectives

Land the WAL primitives (kee-wal crate) and the recovery path — the feature separating a production-grade engine from an in-memory-only wheel (I3, I8, P10), built against the ARIES discipline (Mohan et al. 1992, §5).

22.2 Detailed Implementation Steps

  • Record encoding: length-prefixed varint, tag byte, tag-specific payload, CRC32C trailer (Castagnoli, hardware _mm_crc32_u64 on x86-64, checked at startup) — §8.3's exact format. Records: Insert(key, generation, deadline_wall_ns), Persist(key, generation), Tombstone(key, generation, fired_at_wall_ns), Snapshot(lsn).
  • Group commit: at most every 1 ms or 1024 records, whichever sooner (ADR-09); fsync runs on a dedicated thread via fdatasync(2) (not fsync(2) — §22.6 pitfall, metadata sync is unneeded for an append-only log and roughly halves throughput on most filesystems). submit() callers wait on the group-commit's completion before acking (I3).
  • Snapshot: serializes shard maps + wheel state to a file every 1M records or 100 MB of WAL (ADR-10); pins the WAL at a known LSN; runs on a background thread against a copy-on-write view of the per-shard maps so it never blocks foreground inserts.
  • Recovery: scans from the last snapshot's LSN to the WAL tail; for each Insert, recomputes Δ = deadline_wall_ns − now_wall, re-inserts at now_mono + Δ (re-derives the monotonic offset from the wall-time-stamped record, per P1/I5); Persist/Tombstone replay their generation-guarded effect (idempotent, P12).
  • Truncation-on-corruption: a CRC mismatch at the tail truncates to the last good record (a torn write from an incomplete fsync, not treated as fatal).

22.3 Deliverable

kee-wal::{log, snapshot, record, recovery} with a recover(wal, snapshot) -> Engine entrypoint (§11) restoring full outstanding-deadline state from disk.

22.4 Acceptance Criteria

  • Crash-recovery test: insert 100,000 deadlines, kill -9 the process mid-steady-state, restart, assert all 100,000 recovered with correctly re-derived relative offsets (I8).
  • 1,000,000-record WAL replay completes in ≤ 5 s (M9).
  • Snapshot test: snapshot 10,000,000 keys, restart, replay, assert bit-identical state to pre-restart (byte-for-byte shard-map + wheel-occupancy comparison).

22.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/recovery/baseline.jsonl clean shutdown + restart all deadlines recovered at correct offset
conformance/corpora/recovery/crash.jsonl kill -9 mid-commit last good record recovered, nothing partially applied
conformance/corpora/recovery/snapshot.jsonl snapshot + replay bit-identical state

22.6 Pitfalls

  • Using fsync(2) instead of fdatasync(2) for an append-only log needlessly syncs file metadata and roughly halves achievable throughput (ADR-09's group-commit floor assumes fdatasync).
  • Logging an Insert record before checking the if_ flag (§19.2) — a rejected condition must never appear in the durable log; the condition check must precede the append, every time, with no code path that logs speculatively.
  • Forgetting the CPU feature check for hardware CRC32C at startup — a software-fallback path exists but silently running it without operator visibility masks a real performance regression.

22.7 Performance Concerns

Group commit's 1 ms/1024-record window trades p99 insert latency (an insert can wait up to the full window before its fsync completes) against fsync IOPS (ADR-09) — the floor is 50,000 commits/sec on an NVMe device with fdatasync, tracked as a dedicated benchmark (§24.3) separate from the pure in-memory insert path (M1).

22.8 Edge Cases

  • Host power loss (not just process crash) mid-fsync: the filesystem's own durability guarantee is assumed (ext4/XFS with fdatasync honoring the write barrier) — documented as an explicit dependency, not re-implemented by this engine.
  • Wall clock stepped backward by a week between crash and restart (host was powered off): recovery correctly fires every deadline that is now in the past, immediately, per I8 — this is the exact scenario P1's design defends against.
  • A Tombstone record for a key never Inserted in the retained WAL window (truncated by an earlier snapshot): recovery treats this as a no-op — the corresponding Insert is already reflected in the snapshot's state, so the tombstone is redundant, not an error.

22.9 Failure Analysis

A WAL corruption beyond the last-good-record truncation boundary (e.g. a torn write spanning multiple records due to a filesystem bug) blocks startup entirely (I8's detection); operator recovery follows docs/runbooks/wal-corruption.md: run tools/wal-inspect to locate the corruption boundary, manually truncate, restart, accept the resulting deadline loss for records past the truncation point (a documented, bounded-blast-radius degradation, never silent).

22.10 Operational Notes

Metrics: kee_wal_append_seconds, kee_wal_fsync_seconds (histograms), kee_wal_bytes_written_total, kee_recovery_seconds (gauge, sampled once per restart). Cites the Write-Ahead-Log project (rank 69, §2): kee-wal becomes a thin adapter over its public surface once that project ships; until then this crate carries the full implementation.

23. Phase 11 — Replicated Mode With Hybrid Logical Clocks

23.1 Objectives

Make the engine replicable: a primary accepts writes, one or more followers apply them, using absolute-deadline replication (P7) with HLC-ordered tombstones (Kulkarni et al. 2014, §5) so no follower needs a synchronized wall clock to apply correctly.

23.2 Detailed Implementation Steps

  • Every WAL record ships with an Hlc stamp (§11); the follower applies records in HLC order, buffering out-of-order arrivals (bounded buffer, rejecting/re-requesting on a causality violation per I9).
  • Insert records carry the absolute deadline_wall_ns; the follower converts to its own monotonic clock at apply time via its own ClockSource::wall_to_monotonic (§13.2) — the conversion is local, never trusts the primary's monotonic clock (P1 extended across the replication boundary).
  • Hlc::now(physical, last, node_id) and Hlc::merge(local, incoming, physical) implement the Kulkarni et al. algorithm exactly: wall = max(physical, last.wall); logical resets to 0 on a wall advance, increments otherwise (I9).
  • Transport: single-leader gRPC log shipper bundled in kee-replication until Distributed-KV-Store (rank 38) ships its Raft layer (PhaseDeferred("§23.6")); mutual TLS deferred to Phase-1 (PhaseDeferred("§25")).

23.3 Deliverable

kee-replication::{hlc, apply, tombstone} driving a two-node primary/follower topology where follower fires converge to within the configured NTP-skew tolerance of the primary's.

23.4 Acceptance Criteria

  • Two-node test: writes against the primary appear as follower fires within 2 × NTP_skew_ms of the deadline (M13, I12).
  • Clock-step test: a simulated 1-second backward step on the follower produces zero duplicate fires (I2/I7 absorb it via the generation check).
  • Partition test: a 30-second network split, healed, follower catches up and converges to identical outstanding-deadline state as the primary.

23.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/cluster/absolute.jsonl primary writes, follower observes follower fires within 2×NTP_skew_ms
conformance/corpora/cluster/hlc.jsonl reordered message delivery tombstones apply in HLC order regardless of arrival order

23.6 Pitfalls

  • Replicating a relative TTL instead of the absolute deadline: the primary observes the deadline at wall time T+10s; a follower applying at T+10.1s (network lag) would insert T+20.1s if it re-added the relative offset — always replicate absolute (P7); this is Key Pitfall 6 (§27).
  • Storing Hlc.wall_ms in anything coarser or finer than milliseconds breaks the 64-bit packing with the 32-bit logical counter (§8.4) — finer ordering is the logical field's job, not wall_ms's.
  • A large forward clock step on the primary advances its HLC monotonically and followers accept it without issue; a backward step holds the primary's HLC steady (the max clamp) until physical time catches up — documented explicitly so an operator does not mistake this pause for a stall.

23.7 Performance Concerns

Follower apply-path throughput is bounded by the HLC buffer's out-of-order tolerance window — a wider buffer absorbs more reordering (tolerating up to the configured network RTT assumption, § 4, ≤ 5 ms intra-DC) at the cost of higher apply latency; this tradeoff is the direct reason replication beyond ≤ 50 ms RTT is documented as unsupported (§4).

23.8 Edge Cases

  • A follower joining after the primary has already truncated WAL history past a snapshot: the follower must bootstrap from the primary's snapshot first, then tail the WAL from that snapshot's LSN — a follower cannot partially replay from an arbitrary mid-stream point.
  • Two primaries both accepting writes during a network partition (split-brain): explicitly out of scope for single-leader mode — PhaseDeferred("§23.6") defers multi-leader conflict resolution to the Raft-backed mode.
  • An Hlc merge where incoming.node_id has never been seen before (a new follower or a primary failover): the merge proceeds per the algorithm unchanged — node_id only breaks ties, never gates acceptance (I9).

23.9 Failure Analysis

A causality violation (I9) that the buffer cannot resolve within its window is the highest-severity replication defect (a resurrected-after-fire key is the worst-case outcome); detection is the kee_hlc_causality_violations_total counter; containment is per-follower (a poisoned follower's stream does not affect the primary or other followers); recovery is the follower re-requesting a fresh snapshot-based resync, documented in docs/runbooks/follower-skew.md.

23.10 Operational Notes

Metric: kee_replication_lag_records (gauge). Deployment: the gRPC log shipper is internal-only by default (§25 trust boundary); a misconfigured follower flooding the primary with resync requests is rate-limited at the gRPC layer per the same runbook.

  • SLOs. 99.9% node availability (§4); recovery RTO ≤ 5 s (M9); replicated fire accuracy ≤ 2×NTP_skew_ms (M13).
  • Incident response. Named runbooks: docs/runbooks/triage.md (first-response checklist), slow-fire.md (I10/I13 violations), wal-corruption.md (T3/§22.9), follower-skew.md (T6/§23.9/I12).
  • Backup/restore. WAL + latest snapshot pair is the full backup unit; restore = copy both, run recover() (§22.4); backup cadence matches the snapshot cadence (ADR-10).
  • Deployment topology. Single binary per node (kee-redis); optional primary/follower replication (§23); library-embeddable kee-core for in-process use.
  • Canary/rolling-upgrade/rollback. New binary versions are wire- and WAL-compatible within a major version (§28); canary a single follower first, monitor kee_replication_lag_records, promote or roll back per the standard canary gate; a rollback is a binary swap plus WAL replay from the last compatible snapshot.
  • Migration strategy. Schema/record-format changes bump the WAL record's tag-byte version (§28); a mixed-version cluster runs the old format until every node is upgraded, then a one-time migration tool rewrites the WAL to the new format.

28. Compatibility & Versioning

  • Wire compatibility (RESP). Byte-identical to Redis's documented EXPIRE/PEXPIRE/ EXPIREAT/PEXPIREAT/TTL/PTTL/PERSIST behaviour (P9); mini_* extensions (EXPIRE_MANY, TTL_MANY, SCAN_DEADLINES, FORCE_EXPIRE_PASS) are additive-only, documented at docs/api/resp.md, never overload an existing Redis command's semantics.
  • WAL/storage compatibility. WalRecord's tag byte is versioned; a new tag is additive (old readers skip unrecognized tags with a logged warning, never a hard failure); a breaking record-layout change bumps the WAL format major version, gated by Cargo.toml's crate version per SemVer (below).
  • API stability. kee-core's public traits (ClockSource, DeadlineQueue, Sink, §11) are stable within a major version; a breaking trait-signature change is a major version bump.
  • SemVer policy. MAJOR.MINOR.PATCH on every crate in the workspace; MAJOR bumps gate on a documented migration path (WAL/wire format changes); MINOR is additive (mini_* extension, new metric); PATCH is bugfix-only, no behavior change to any documented contract.
  • Rolling-upgrade guarantees. A follower running N can apply WAL records from a primary running N+1 within the same major version (forward-compatible tag-skip); a primary running N rejects a follower's HLC records only on an actual major-version WAL-format mismatch, never on a minor-version difference.
  • Deprecation policy. A deprecated command/flag is documented at docs/api/resp.md with a removal-target major version, minimum one major version of advance notice, and a kee_deprecated_command_used_total{command} telemetry counter to measure live usage before removal.

  • Conformance suite. 32. Scalability Analysis

Constant regardless of key cardinality: per-insert amortised cost (O(1), the wheel's defining property, §16.4); per-fire cost (O(1), arena pop); recovery RTO (O(inter-snapshot record count), bounded independent of total dataset size, P10/§35 D6).

Grows with key cardinality: RAM (linear, §35 D2); WAL size between snapshots (linear in insert rate × time, bounded by ADR-10's cadence); shard-map lookup cost (O(1) amortised per DashMap entry, but total memory bandwidth for shard-map traversal during the active cycle grows with occupied-slot count, §18.7).

Named bottlenecks, in order: (1) the cron-driver's single-thread 1ms tick budget — every subsystem (heap-top pop, wheel advance, active cycle, notification dispatch) competes for this window (§19.7); (2) WAL group-commit fsync IOPS ceiling (50,000 commits/sec floor, §22.7) — the hard wall for Durability::DurableLog throughput; (3) per-shard lock contention under a skewed key distribution concentrating traffic on one of the 256 shards (P11); (4) replication apply-path throughput bounded by the HLC out-of-order buffer window (§23.7).

Horizontal scaling. The engine does not itself shard across nodes — that is Distributed-Cache's concern (rank 61, which depends on this engine's replicated mode, §23). A single node's ceiling is the 100M-key/12GiB RAM target (§4); scaling past that means partitioning the keyspace across multiple Key-Expiration-Engine instances at the consuming application's layer, each independently replicated.

Vertical scaling. More cores do not directly help the cron-driver (deliberately single-threaded, §19.1, to avoid cross-thread wheel-lock contention) but do help the RESP frontend's connection-handling concurrency (§21.7) and the WAL's background fsync/snapshot threads (§22.2) — the practical vertical ceiling is therefore ingress-parsing throughput and WAL IOPS, not wheel/heap CPU cost.

Coordination overhead. Replicated mode's HLC merge cost is O(1) per record (§23.2) — no consensus round-trip is required for the ordering itself, only for single-leader write acceptance (deferred to Raft, PhaseDeferred("§23.6"), when multi-leader conflict resolution is needed).

Practical ceiling and the levers beyond it. ~100M keys / node is the documented target; beyond it, the levers are: (a) raise SHARD_COUNT past 256 (P11, requires a version bump per §28 since it's a boot-time constant, not runtime-elastic); (b) widen the WAL group-commit window past 1ms/1024 records (ADR-09) trading latency for IOPS headroom; (c) partition the keyspace across multiple instances (horizontal, above); (d) the io_uring timer driver (PhaseDeferred("§17.6"), ADR-17) removes the cron-thread's 1ms tick-wakeup floor entirely for sub-ms-tick deployments.

33. Mental Models & First Principles

  • MM1 — A timer wheel is a radix sort of deadlines, computed incrementally. The hierarchical level assignment (level = ⌊log₆₄(Δticks)⌋) is a base-64 radix decomposition of the offset; cascading is that decomposition's carry-propagate step, computed one carry at a time instead of all at once. Predicts: insert is O(1) not because deadlines go unsorted, but because the "sort" is deferred until the exact tick that needs the answer. Bug class without it: treating cascade as a one-time bucket move instead of a re-sort against the current now (§16.6's stale-Δticks pitfall). Applied at §16, §8.5.
  • MM2 — Two clocks, one truth: monotonic is "when," wall is "what it means to others." Every production clock bug conflates "duration since a fixed point" with "a value everyone agrees on." Predicts: any function whose signature doesn't statically distinguish the two will eventually be called with the wrong one under skew. Bug class without it: encoding both as bare u64 nanoseconds and trusting code review — exactly what P1's newtypes make a compile error instead. Applied at §13, §6 P1.
  • MM3 — Durability is a property of the log, not of the data structure. The wheel/ heap in memory are disposable; the WAL is what survives a crash, and recovery re-derives the wheel from the log, never the reverse. Predicts: any optimization skipping the WAL append to make the wheel "faster" silently breaks crash safety regardless of the wheel's in-memory correctness. Bug class without it: "the wheel already knows the deadline, why log it again" reasoning. Applied at §22, P10.
  • MM4 — Bounding by wall-time, not work-count, is how a background sweep stays safe inside a real-time budget. Any "sweep in the background" system (GC, compaction, active-expire) bounded by count instead of time inherits an unbounded worst case from its input distribution. Predicts: a skewed workload eventually violates any count-based bound, however conservative. Bug class without it: "sample at most 20 per cycle" reasoning that assumes uniform occupancy, breaking the instant one shard is hot. Applied at §18, P5, I10.
  • MM5 — Idempotent replay turns "exactly once" into "at least once" for free. Once every mutation carries a monotonic idempotency key (Generation), at-least-once redelivery converges to the same state without distributed exactly-once machinery. Predicts: any generation/version-checked apply path tolerates duplicate delivery from crash recovery or replication with no extra dedup table. Bug class without it: bolting on ad-hoc "have I seen this message ID" tables instead of making the state transition naturally idempotent. Applied at §7 I2/I7/I12, P12, §22, §23.
  • MM6 — A hybrid logical clock is a Lamport clock wearing a wall-clock costume. HLC's wall_ms gives callers the wall-time meaning they actually want (EXPIREAT semantics) while its logical component gives strict causal ordering a pure wall clock cannot guarantee for concurrent same-millisecond events. Predicts: any distributed system needing both "roughly real time" and "definitely ordered" converges on this exact construction, independent of domain. Bug class without it: pure wall-clock ordering silently reorders concurrent writes at the same timestamp; pure logical clocks lose the wall-time meaning entirely. Applied at §23, §8.4.
  • MM7 — Fixed-capacity overflow-to-a-bigger-structure beats growing the fast structure. The heap-top's fixed-256-with-eviction-to-wheel design keeps the hot/small path bounded and simple, spilling overflow into the already-general slow path. Predicts: any "hot cache in front of a general store" design benefits from this same fixed-size-with- spillover shape. Bug class without it: an elastic heap-top reintroducing the O(log n)- at-scale cost the wheel exists to avoid. Applied at §17, ADR-04, §35 D4.
  • MM8 — Sharding trades global correctness reasoning for bounded blast radius. A single global lock is easy to reason about but has unbounded blast radius; N shards bound the blast radius to 1/N at the cost of N times as many invariants to hold independently. Predicts: any "hot-key isolation" claim is only as good as its shard-count-to-worst-case-skew ratio. Bug class without it: assuming sharding alone eliminates contention when one sufficiently hot key still saturates its one shard. Applied at §6 P11, §18.7, §32.

This wins in Redis's actual niche: a single-node, memory-resident keyspace where TTL'd keys are a minority and operational simplicity outweighs the asymptotic argument for a wheel — exactly the regime P2 rejects at this project's 100M-key TTL cardinality target.

Kafka. The one decision it made differently: an unbounded DelayQueue overflow bucket instead of a fixed-capacity heap-top. This wins because Kafka's timer cardinality is naturally bounded by its broker-side request/produce-timeout use case (a request-timeout wheel never needs 100M concurrent entries) — a bet this engine's arbitrary-TTL, arbitrary-cardinality workload cannot safely make, which is exactly why §17.2 fixes the heap-top's capacity instead.

Netty. The one decision it made differently: a single-level wheel with a "rounds" counter standing in for hierarchical cascading. This wins for Netty's bounded-cardinality per-channel I/O-timeout workload (thousands, not millions) where one level plus a rounds counter is simpler to implement than a hierarchical structure — this engine's 100M-key target makes that simplicity unaffordable (§14.7's single-level scan-cost argument).

Linux kernel. The one decision it made differently: splitting by accuracy class into two entirely separate structures (cascading wheel for coarse timers, per-CPU rbtree for high-resolution ones) rather than hybridizing one structure the way this engine's wheel-plus-heap-top does. This wins in the kernel's regime because the two timer classes have genuinely disjoint call sites that never interoperate through one API — this engine instead unifies both accuracy classes behind one submit() call because its callers (Redis clients) never distinguish accuracy classes at the API level.

35. Back-of-Envelope Capacity Model

  • D1 — Wheel horizon. 64^6 ticks × TICK_NS (1 ms) = 68,719,476,736 ms ≈ 795 days ≈ 2.18 years (ADR-03, ADR-05). Exceeds every realistic TTL (seconds to weeks) by two to three orders of magnitude, justifying "no realistic deadline is ever rejected as past-horizon" (P8's rejection path is a safety net, not a common case).
  • D2 — RAM ceiling @ 100M keys. Per-key footprint: wheel Node (24 B, §8.2) + KeyState shard entry (12 B raw + ~36 B DashMap bucket/hash overhead ≈ 48 B) = 72 B/ key; × 1.33 allocator/alignment overhead factor ≈ 96 B/key. 100,000,000 × 96 B = 9.6 GB; × 1.25 operational margin (arena fragmentation, in-flight WAL buffer, metrics) ≈ 11.5 GB, rounded to the ≤ 12 GiB ceiling in §4.
  • D3 — Insert-cost budget from throughput. 1 / 5,000,000 inserts/sec = 200 ns average per-insert budget at M1's target — consistent with M4's < 100 ns p50 claim (leaves headroom for the p99 tail, M5).
  • D4 — Heap-top capacity vs. worst-case arrival. At M2's 800,000 inserts/sec floor, a 16 ms top_horizon window could theoretically see 800,000 × 0.016 = 12,800 inserts if every single one carried a sub-16ms TTL. ADR-04's fixed capacity of 256 is sized against the empirical short-TTL fraction (§17.4's sweep), not this theoretical worst case — the gap between 12,800 and 256 is exactly why the eviction-to-wheel overflow path (§17.2) exists as the correctness backstop.
  • D5 — WAL group-commit rate vs. device floor. ADR-09's 1 ms/1024-record window bounds commit rate to min(1000 commits/sec time-bound, arrival_rate/1024 count-bound). At M2's 800,000 inserts/sec, 800,000 × 0.001 s = 800 records accumulate per 1 ms window (under the 1024 cap), so the time bound dominates: ≈ 1,000 fsyncs/sec, 50× under the 50,000 fsyncs/sec NVMe fdatasync floor (§22.7) — comfortable headroom.
  • D6 — Recovery RTO independent of dataset size. M9 requires 1,000,000 records ≤ 5 s ⇒ ≥ 200,000 records/sec replay throughput. Since ADR-10 caps records-since-last- snapshot at ≤ 1,000,000 regardless of total keyspace size, RTO = records_since_snapshot / replay_throughput ≤ 1,000,000 / 200,000 = 5 s for any total dataset size — the formal derivation behind P10's boundedness claim.
  • D7 — Storage amplification. WAL bytes/record ≈ 1–2 B (varint) + 1 B (tag) + 28 B (key 8 + generation 4 + wall_ns i128 16) + 4 B (CRC32C) ≈ 35 B. A full insert+tombstone pair for 100M keys ≈ 100,000,000 × 2 × 35 B = 7 GB, vs. D2's 9.6 GB live-keyspace RAM footprint ⇒ ≈ 0.73× amplification, comfortably under the ≤ 1.2× ceiling in §4 (and bounded absolutely by ADR-10's snapshot cadence regardless of total keyspace size).
  • D8 — Connection-buffer memory budget. 65,536 max FDs (§4) × 32 KB (16 KB read + 16 KB write buffer per connection) ≈ 2.1 GB — a budget tracked separately from D2's keyspace RAM ceiling in total node sizing.
  • D9 — Allocation cost at fire-throughput scale. M3's 10,000,000 fires/sec at 1,000 ticks/sec (1 ms tick) implies ≥ 10,000 fires drained per tick during a synchronized expiry burst (e.g. midnight session expiry). At typical allocator latency (50–100 ns/ alloc), 10,000 allocations would consume 0.5–1 ms of the 1 ms tick budget alone — the exact arithmetic justifying why any allocation in the fire path (P4/I11) is unaffordable at this target throughput.
  • D10 — Replicated fire-accuracy bound. Configured NTP_skew_ms = 100 (§4) ⇒ M13's ≤ 2 × NTP_skew_ms = 200 ms bound derives from worst_case_error ≤ |primary_skew| + |follower_skew| ≤ 2 × max(individual configured skew), assuming both nodes are bounded by the same configured tolerance.

37. Alternative Architectures (Roads Not Taken)

Alt-1 — Sorted heap only, no wheel.

Show the original text diagram
submit() ──► BinaryHeap<Reverse<Deadline>> ──► advance_to(now) pops while peek<=now

Regime where it wins: cardinality under ~100K live deadlines, where O(log n) per op is negligible and the implementation/debugging simplicity of a single well-understood structure outweighs the wheel's asymptotic argument. Real system embodying it: Go's runtime timer heap (runtime/time.go, per-P four-ary heap, §5) — Go accepts O(log n) because its typical timer count per P is small. Rejected here because M1's 100M-key, ≥ 5,000,000 inserts/sec target makes O(log n) per insert an 80× cost penalty at scale relative to the wheel's O(1) (§14, §15.4's 200ms-vs-50ms baseline comparison).

Alt-2 — Calendar queue (flat array indexed by absolute bucket, no hierarchy).

Show the original text diagram
buckets[deadline % N] ──► list of deadlines; requires periodic bucket-width re-tuning

Regime where it wins: a workload with a known, stable deadline distribution where the bucket width can be tuned once and rarely revisited — calendar queues (Varghese & Lauck's own baseline, §5) shine in discrete-event simulation where the event-time distribution is known ahead of time. Rejected here because this engine's TTL distribution is operator/application-defined and can shift at runtime; a fixed bucket width either wastes memory (too fine) or reintroduces O(occupancy) scans (too coarse) — the hierarchical wheel's log-scale level structure adapts to any distribution without re-tuning (§16.2).

Alt-3 — Per-key OS timers (one timerfd/IORING_OP_TIMEOUT per deadline).

Show the original text diagram
each Deadline ──► one timerfd/io_uring timeout registration ──► kernel wakes the process

Regime where it wins: low-cardinality, latency-critical timeout sets (thousands, not millions) where the kernel's own high-resolution timer infrastructure (hrtimer.c, §5) gives sub-microsecond accuracy for free, and per-timer FD/registration overhead is affordable. Rejected here because 100M concurrent timerfds (or io_uring timeout registrations) would exhaust the FD budget (§4's 65,536 ceiling, already allocated to RESP connections) and the kernel's own per-timer bookkeeping cost does not amortise the way a user-space hierarchical wheel does at this cardinality — this is exactly why the io_uring driver is scoped as a Phase-1 tick-resolution improvement (PhaseDeferred ("§17.6"), ADR-17), not a per-key timer replacement.

Alt-4 — Hierarchical wheel with per-shard independent wheels (no single global wheel).

shard[0..255] each owns its own HierarchicalWheel; no cross-shard cron coordination

Regime where it wins: a deployment where per-shard fire-time independence is acceptable and the operational cost of running 256 independent cron drivers (256 threads, 256 sets of active-expire budgets) is affordable — this shape appears in sharded caches that accept looser global fire-ordering guarantees in exchange for eliminating any single-thread bottleneck (§32's named bottleneck #1). Rejected here because P11 already bounds blast-radius via a sharded key map while keeping one global wheel/cron-driver (§19.1) — splitting the wheel itself per-shard would multiply the WAL/snapshot/recovery machinery by 256×, contradicting P10's bounded-RTO goal (§35 D6) without a corresponding correctness benefit, since this engine's global fire-ordering guarantee (I1/I2) does not require per-shard independence to hold.

39. Glossary

  • Active-expire cycle — the wall-time-bounded background sweep that fires already-past deadlines the wheel/heap-top have not yet reached (§18.2, ADR-06).
  • ARIES — Algorithm for Recovery and Isolation Exploiting Semantics; the WAL/recovery discipline this engine's group-commit and replay derive from (Mohan et al. 1992, §5).
  • Arena — a pre-allocated pool of fixed-size node slots the wheel/heap draw from, eliminating per-fire heap allocation (§8.2, I11).
  • Blast radius — the scope of a system affected by a single failure or hot key; bounded to one shard by P11.
  • Cascade — the process of draining a wheel level's current slot and re-inserting its entries into a lower level on cursor wrap (§16.2, §8.5).
  • Clock domain — the distinction between monotonic time (scheduling) and wall time (meaning to other processes); enforced by newtypes (P1, §13).
  • Conformance suite — the automated test harness comparing actual behavior against named fixtures across every phase (§29, per-phase §N.5 tables).
  • Cron driver — the single dedicated thread advancing the wheel/heap-top and running the active-expire cycle once per tick (§19.1).
  • CRC32C — the Castagnoli cyclic redundancy check polynomial used as the WAL record integrity trailer, hardware-accelerated on x86-64 (§22.2).
  • DashMap — the lock-striped concurrent hash map used for the per-shard KeyId → KeyState map (ADR-16).
  • Deadline — a (key, generation, MonotonicNs) tuple representing a scheduled fire event (§8.2, §11).
  • DurableSink — a notification sink that WAL-logs before delivery, giving exactly-once-modulo-ack semantics at the cost of two fsyncs per fire (§20.2, ADR-19).
  • Fire — the moment a deadline's target time is reached and its notification is enqueued (§8.6 state-transition table).
  • Fire jitter — the observed delay between a deadline's target time and its actual fire time (§4, M6/M7).
  • Generation — a per-key monotonic counter that lets stale wheel entries be silently discarded rather than requiring active removal (§8.2, I7, P12).
  • Group commit — batching multiple WAL appends into one fsync, bounded by time or record count, whichever is sooner (ADR-09, §22.2).
  • Handle — an opaque (key, generation) pair returned to callers for later cancel/CAS operations (§11).
  • Heap-top — the fixed-capacity (256) sorted-heap structure holding near-term deadlines for sub-tick fire accuracy (§17, ADR-04).
  • Hierarchical timing wheel — the multi-level cascading wheel structure from Varghese & Lauck 1987 that gives O(1)-amortised insert at unbounded horizon (§16).
  • HLC (Hybrid Logical Clock) — a (wall_ms, logical, node_id) timestamp combining wall- time meaning with strict causal ordering, used for replicated tombstone/insert ordering (§8.4, §23.2, Kulkarni et al. 2014).
  • Horizon — the maximum representable deadline offset a wheel can schedule without rejection (§8.1, §35 D1).
  • Idempotent replay — the property that applying a mutation once or twice yields identical state, enabled by the Generation field (P12, MM5).
  • Invariant — a statement that must hold at all times, enforced and telemetered per §7's table (I1–I13).
  • Keyspace event — a notification emitted on key expiration, compatible with Redis's keyspace-notification pub/sub format (§20.2).
  • KeyState — the per-shard map value holding a key's current generation and deadline (§11).
  • Lazy expiration — checking and firing a deadline on key access rather than waiting for the active cycle to reach it (§18.2, ADR-07).
  • Level (wheel) — one of the six tiers of the hierarchical wheel, each advancing 64× slower than the level below it (§8.1).
  • MAX_SINK_DELIVER_DURATION — the 100ms default timeout bounding any single Sink::deliver call (§11, I13).
  • MonotonicNs — the newtype wrapping CLOCK_MONOTONIC-sourced nanoseconds; the engine's internal scheduling time domain (§11, P1).
  • NTP skew — the divergence between a host's wall clock and true time, bounded by a configured tolerance for replicated fire-accuracy purposes (§4, M13).
  • Ns — a signed nanosecond duration type, the arithmetic result of subtracting two MonotonicNs/WallNs values (§11).
  • PastHorizon — the typed error returned when an insert's deadline exceeds the wheel's maximum representable offset (P8, §8.7).
  • Persist (PERSIST) — the operation that cancels a key's TTL by incrementing its generation and freeing its KeyState (§8.6, §11).
  • RESP (Redis Serialization Protocol) — the wire protocol this engine's frontend implements byte-compatibly (§5, §21).
  • Shard — one of 256 fixed partitions of the KeyId → KeyState map, bounding lock contention blast radius (P11, §6).
  • Sink — the pluggable trait for delivering fire notifications to a consumer (keyspace, webhook, durable, or custom) (§11, §20).
  • Snapshot — a point-in-time serialization of shard-map and wheel state, pinning WAL replay to a known LSN and bounding recovery RTO (§22.2, ADR-10, §35 D6).
  • Split-brain — a failure mode where two nodes both believe themselves the write leader during a partition; explicitly out of scope for single-leader replication (§23.8, §26).
  • Stale entry (wheel) — a wheel node whose generation no longer matches its key's current KeyState, silently dropped on fire (§8.6, I7).
  • Tick — the fixed 1ms (default) unit of wheel/cron-driver advancement (§8.1, ADR-05).
  • Tombstone — a WAL record marking a fired or persisted deadline as resolved, used in recovery and replication ordering (§8.3, §22.2).
  • Top horizon — the offset threshold below which a deadline routes to the heap-top instead of the wheel (default 16ms) (§17.2, ADR-04).
  • WAL (Write-Ahead Log) — the append-only durability log that is the sole source of truth for outstanding deadlines across a crash (§22, I3, I8, P10).
  • WallNs — the newtype wrapping CLOCK_REALTIME-sourced nanoseconds since the Unix epoch; used only at the API boundary and for replicated absolute deadlines (§11, P1).
  • Wheel epoch — the fixed reference MonotonicNs origin against which a wheel's slot indices are computed (§11, §12.6).
