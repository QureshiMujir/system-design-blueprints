In one paragraph

An incremental build graph engine answers one question after you change some files: which build steps must run again, and how do we know every other step is still correct? This design is a family of 14 Rust crates (ibg-core to ibg-bench) that a build tool embeds or runs as a long-lived daemon. It is not a build-file language, a compiler or a package manager (§1.1, §1.4, §1.6). Its defining ideas are content fingerprints instead of timestamps, pull-based evaluation with revision counters, early cutoff, and a content-addressed cache (§3.2, §6.1 to §6.5). Design targets include a graph of 1,000,000 nodes and a null build of at most 50 ms (§4.1, §4.3).

The problem, concretely

You have a C project: src/foo.c and include/foo.h feed a compile step that makes build/foo.o, and a link step turns that into build/bin (§8.13). The naive build tool compares file timestamps and rebuilds whatever looks older than its inputs. That fails in both directions. A touch or a clock skew makes unchanged files look changed, or changed files look unchanged, so real outputs go stale while the tool claims everything is clean (§6.1 violation example, MM2). The blueprint calls a stale output served as current an under-build, and says it is worse than a slow build (§6.1, §7.1).

Now the other direction. You make a formatting-only edit to foo.c, so the compiled output is byte-identical to before (§8.13). A tool that keeps propagating dirtiness past an unchanged output rebuilds the whole downstream subgraph for nothing (§6.4 violation example). The blueprint calls this an over-build, and says it can multiply build times by 10 to 100 in large monorepos (§7.2). Eagerly recomputing everything after every file event also kills interactivity in a large repo (§6.5).

Add a hidden input: the compile step quietly reads a config file it never declared. The cache key does not change when that file changes, so a stale cached result is handed to everything that depends on it (§6.2 violation example). The engine has to solve all three at once: detect changes by content, stop propagating when outputs do not change, and refuse to cache anything whose inputs were not fully declared (§2.4, §6.1, §6.2, §6.4).

How it works, end to end

Follow one build request through the boxes of §3.1:

  1. Graph (ibg-graph) holds the build as a DAG of source, action, glob and group nodes in a slab indexed by NodeId(u32). It checks for cycles on every add_edge, because the front-end is untrusted, and keeps a topological order plus a reverse-dependency index (§3.2, §3.5).
  2. Engine (ibg-engine) is demand-driven: it evaluates only what the requested targets depend on, using per-node last_verified, last_changed, output digest and status (§3.2, §6.5).
  3. Fingerprint (ibg-fingerprint) compares (mtime, size, inode) to cached values first and hashes the file with blake3 only if they differ, then computes the ActionKey (§3.2).
  4. Cache (ibg-cache) looks up the ActionKey. On a hit it writes the outputs from the content-addressed store (CAS) to their declared paths and skips execution (§3.2, §8.14).
  5. Scheduler (ibg-sched) takes the misses and orders them by dependencies and job slots, with a work-stealing deque per worker and critical-path priority (§3.2, §8.8).
  6. Executor and sandbox (ibg-exec, ibg-sandbox) run the action. The executor captures declared outputs, the sandbox detects undeclared reads, and output digests are stored back via ibg-cache, with an optional upload through ibg-remote (§3.1, §3.2).
  7. Persist (ibg-persist) saves graph, node states, revisions and digests at the end of each successful build, so the next invocation starts warm (§3.2).
  8. Watch (ibg-watch) turns file-system events into dirty marks by walking reverse edges. Events are advisory; the engine re-fingerprints before deciding to rebuild (§3.2, §3.5). ibg-telemetry taps evaluation, cache, execution and scheduling (§3.1).

Two things arrive from outside this main flow. Dynamic dependencies: an action writes a list of discovered dependencies (such as #include files) to a declared __deps.json, the engine adds those edges with a cycle check, and a change to any of them dirties the action next build (§8.7). Watch events: after a 50 ms default debounce, a path is resolved to a source node and a breadth-first walk over the reverse-dependency index marks every reachable clean action dirty (§8.9).

The core ideas

Pull evaluation with red/green revision counters (§8.2, §8.3)

A revision is a global u64 counter incremented once per build invocation (§8.3). Each node stores last_verified (the last revision at which it was proven correct) and last_changed (the last revision at which its output changed). A node is green if last_verified == current, and red if it is older (§8.3; this is the Salsa model, §3.2). To check node N at revision R the engine does the following (§8.3):

  1. If N.last_verified == R, return the remembered output digest.
  2. Otherwise check each dependency D of N, recursively.
  3. If every D.last_changed <= N.last_verified, mark N green (last_verified = R) without running anything.
  4. Else recompute the ActionKey, look in the cache, and execute only on a miss.
  5. If the new output digest equals the stored one, keep last_changed and set last_verified = R (early cutoff).
  6. Otherwise store the new digest, set last_changed = R and last_verified = R, and mark dependents red.

A node is Dirty, Running, Clean or Failed (§8.2). Adapted from the transition table of §8.2:

From Event To
Clean an input digest changed, or a watch invalidation reaches it Dirty
Dirty scheduler dequeues it with all deps Clean Running (slot acquired)
Running exec ok, output digest equals stored Clean (last_verified advances, dependents not re-dirtied)
Running exec ok, output digest differs Clean (last_changed = current, dependents dirtied)
Running exec fails Failed (dependents Failed)

The blueprint is not consistent about these rules, and does not say which wins. §8.2 sets last_changed = current_revision when an input digest changes, while §8.3 step 6 sets it only when the output changes. The glossary calls a node green when last_changed < last_verified (Glossary, Red/Green), not §8.3's last_verified == current_revision. And the revision advances once per invocation in §8.3, but only on file events in §6.6.

Early cutoff: stop when the output did not change (§6.4, §7.3, §8.13)

Dirtiness does not spread past a node whose recomputed output digest equals the previous one (§6.4). The blueprint's own worked trace uses A_compile and A_link (§8.13):

Moment A_compile A_link
Build 1, revision 1 (cold) runs, output digest D3; last_changed=1, last_verified=1 runs, output digest D4
Build 2, revision 2, formatting-only edit (D3'==D3) re-runs; last_changed stays 1, last_verified becomes 2 dependency last_changed 1 is <= its own last_verified 1, so it stays green; zero re-execution
Build 2, revision 2, real change (D3'!=D3) last_changed becomes 2, output D3' new ActionKey misses the cache, so it re-runs and produces D4'

The comparison is always the full 32-byte digest (§7.3). The benchmark is a 10-deep chain whose leaf changes but whose output does not, with a target of zero nodes re-executed (Performance Engineering, M4).

Fingerprints and the action key: change detection by content (§3.2, §8.4, §6.1)

A fingerprint is a blake3 digest of a file's bytes, 32 bytes long (§3.2, ADR-04). Hashing every file on every build would defeat a near-free null build (MM8), so the engine first compares (mtime, size, inode) to the cached values and skips the read if they match (stat fast-path, §3.2). The stat result is only a hint: when the timestamp is ambiguous the engine falls back to a full content hash, and the cache key is a digest of inputs, never of timestamps (§6.1, MM2).

The action key is the hash of everything that determines an action's output (§3.2): blake3(command_bytes || sorted(input_digests) || env_bytes || tool_digest). Its mental model: the key is a pure function of inputs, so the cache is just a memo table and an identical key means an identical output (MM1). The blueprint gives three different sort orders for the inputs and does not say which governs: digests "sorted by NodeId" (§8.4), entries sorted by input path (§11.2), and plain sorted digests (§3.2, §7.4).

Content-addressed store and action cache (§8.5, §6.3, §7.9)

Two maps do the work (§8.5). The CAS maps Digest -> bytes, laid out as cas/<aa>/<bb>/<full-64-char-hex>. The action cache maps ActionKey -> CacheEntry { key, outputs: [Digest], metadata }. Blobs are write-once, written to a .tmp file and renamed into place, so a partial file counts as absent (§8.5, §7.9). Garbage collection marks blobs referenced by action-cache entries and sweeps the rest, deleting an entry before the blob it points to (§8.5). Because blobs are named by hash, identical outputs are stored once and corruption is detectable on read (MM7).

Critical-path work-stealing scheduler (§8.8, MM6)

Wall time is bounded by the longest dependency chain, not the number of cores (MM6). A node's priority is its critical-path estimate, the sum of estimated_cost along a chain, where the estimate is the last execution time from ibg-persist and defaults to 1 for unknown nodes (§8.8). The sequence (§8.8): a dirty node whose dependencies are all clean is enqueued with its priority; a worker pops it from its local deque or steals it from a peer; it acquires a job-slot semaphore; the node is marked Running and handed to ibg-exec; on completion the slot is released, each dependent's pending-dependency count is decremented, and a dependent is enqueued when its count reaches zero. The acceptance example is a diamond-shaped graph whose heavier branch must be dispatched first (§19). The blueprint contradicts itself twice in §8.8: the ready queue is a "min-heap by critical-path weight" although the highest-priority node is dequeued first, and priority is the maximum over "ancestor chains" although the invariant speaks of the "longest downstream chain".

Hermetic execution and failing loudly (§6.2, §6.15, §8.11, §7.5)

An action is hermetic when its output depends only on its declared inputs, command, environment and tool (Glossary, Hermetic Action). The sandbox enforces this: on Linux a mount, pid and network namespace plus a seccomp filter; on macOS a sandbox-exec Seatbelt profile (§8.11, ADR-10, ADR-11). Any read outside the declared inputs raises IbgError::UndeclaredInput, the execution is aborted, and no output is stored (§8.11, §7.5). The wider rule: ambiguity (a hash collision, corrupt state, an undeclared input, a cycle) ends in a loud error or a full re-evaluation, never a silent wrong result (§6.15). A corrupt persisted state, for example, is discarded and the engine falls back to a full re-evaluation, which is always correct (§7.8, MM9).

The trade-offs — where engineers disagree

Hash function: blake3 (ADR-04)

Chosen: the blake3 crate (SIMD, tree-parallel): cryptographically sound, fast, and its 32-byte output fits Digest([u8;32]) (ADR-04). Rejected: SHA-256, SHA-1, xxHash, FNV. When the rejected choice is right: SHA-256 when REAPI or remote-cache interoperability mandates it; xxHash or FNV for non-cryptographic, local-only fingerprinting where raw speed beats collision resistance (ADR-04). The blueprint leaves a tension open here: ADR-12 locks REAPI v2 as the remote protocol, yet §8.12 builds its Merkle input trees from blake3 digests, and neither says which digest the remote cache uses (ADR-12, §8.12).

State database: SQLite in WAL mode (ADR-06)

Chosen: SQLite via rusqlite in WAL mode: atomic multi-table commits, crash consistency, portability, judged enough for graphs under 10M nodes (ADR-06). Rejected: RocksDB, LMDB, a custom B-tree, flat files. When the rejected choice is right: RocksDB above 10M nodes with a write-heavy load; LMDB for read-mostly zero-copy mmap access; a custom B-tree if SQLite becomes the bottleneck (ADR-06). The blueprint does not settle this: ADR-06 and §8.10 say SQLite, while §3.2 and Phase 10 (§22) build ibg-persist on redb, with sled as a fallback behind a trait.

Scheduler: custom deque, not Rayon (ADR-08)

Chosen: a custom Chase-Lev deque on crossbeam-deque, because build scheduling needs critical-path priority and dependency gating, which Rayon's work stealing does not know about (ADR-08). Rejected: Rayon, the threadpool crate, unbounded tokio::spawn. When the rejected choice is right: Rayon, when the actions are independent data-parallel tasks with no dependency gating or critical-path priority (ADR-08).

Reproducibility check: re-run and compare (ADR-25)

Chosen: an optional --check-reproducibility flag that re-executes and compares output digests, report only by default (ADR-25). Rejected: trusting the first run. When the rejected choice is right: when every action is known to be deterministic and re-execution is not worth its cost (ADR-25). The blueprint does not agree on what a mismatch does: ADR-25 says report only; §4.6 says the build fails and the cache is not poisoned; §8.4 and §8.11 say the first result is stored; §6.13 says the entry is marked suspect.

Roads not taken (Alternative Architectures, Deferred Features Register)

Timestamp-based incremental builds (Alt-A, Make and Ninja) rebuild a target when a prerequisite's modification time is newer. They win for a local, single-machine build where simplicity beats cross-machine cache correctness. They are rejected because modification times are unsound across machines and clock skew and cannot back a shared content-addressed cache (Alt-A; MM2).

Functional, demand-driven builds (Alt-B, Shake and Nix) discover dependencies while running and win when dependencies are truly data-dependent. They are partly rejected: a static-then-incremental DAG is simpler to schedule, and dynamic discovery is called a deferred extension (Alt-B; MM5), although §8.7 and Phase 8 (§20) specify it in full.

Remote execution fleet (Alt-C, Bazel RBE) runs actions on a worker farm and wins when a build is too large for one machine. It is deferred because remote caching gives most of the benefit at a fraction of the complexity (Alt-C).

Language-integrated incremental computation (Alt-D, Salsa and rustc) memoizes queries inside one process and wins for sub-file incrementality in a compiler or IDE. It is rejected because this engine orchestrates processes at action and file granularity (Alt-D; MM3).

The deferred register lists six items, each with an un-defer trigger: a remote execution fleet, a Starlark front-end, distributed graph partitioning, a query language, a Windows sandbox, and a daemon with a gRPC API (Deferred Features Register).

What must never be false

The invariants are numbered 7.1 to 7.15; each line says how a violation is noticed.

  • No under-build (§7.1): stale output is never served as current. A post-build audit recomputes input digests; stale_output_served must be 0.
  • No over-build (§7.2): a node re-executes only if its key changed and no cache hit exists. Re-executed nodes are counted against the changed-file set (unnecessary_recomputes).
  • Early-cutoff soundness (§7.3): a cut-off node is equivalent to re-running it. A modify-and-compare test and the counter cutoff_false_negative.
  • ActionKey uniqueness (§7.4): distinct inputs give distinct keys. The key is recomputed and compared on a hit; key_collision_detected must be 0.
  • Hermeticity (§7.5): no undeclared read, and such an action is never cached. The sandbox checks every execution (undeclared_input_count).
  • Cycle freedom (§7.6): the graph is always a DAG. add_edge() and the ancestor check fail immediately (cycle_detected_count).
  • Revision monotonicity (§7.7): the revision only increases. A debug assertion and a startup check (revision_skew_detected).
  • Crash-consistent persistence (§7.8): a partial write forces a full re-evaluation. Checksums and WAL replay on open (corrupt_state_detected).
  • CAS immutability (§7.9): a blob never changes after its first write. Paranoia mode re-hashes on read (cas_integrity_failure).
  • Scheduler forward progress (§7.10): work proceeds while any node is ready. A watchdog logs stuck_scheduler after no completion within a configurable default of 60 s.
  • Dynamic dependency consistency (§7.11): a discovered dependency is tracked across revisions. An integration test and dynamic_dep_invalidation_count.
  • Glob node stability (§7.12): a glob digest changes only when its matches change. Tests add files inside and outside the pattern (glob_invalidation_count).
  • Resource bounds (§7.13): slots, queues and in-memory nodes are all bounded. oom_detected, RSS and file-descriptor monitoring.
  • Remote cache safety (§7.14): a remote hit is accepted only if the local key matches. key_mismatch_on_fetch; non-zero triggers invalidation and an alert.
  • Schema version enforcement (§7.15): unknown schema versions are rejected, never read. The version header is checked on open (schema_migration_count).

What breaks in production

The blueprint groups failure modes as F1 to F9 in its Failure Modes & Recovery section.

  • Stale cache hit (F2). An output is out of date although the build said clean, because an undeclared input was not hashed into the key. The sandbox catches the read at execution time, the build fails instead of staying silent, and the developer declares the missing input.
  • Excessive rebuilds (F2). Many nodes rebuild with no real edit because mtimes change without content change (rsync, backup tools). The stat fast-path is masked by an mtime-only compare; --content-hash-always is the diagnostic.
  • Deadlock in the work-stealing queue (F5). A dependency cycle the graph layer missed. A zero-progress watchdog fires after 30 s and aborts the build with a diagnostic. The timeout is 30 s here but 60 s in §7.10 and in Phase 7's DeadlockSuspected check (§19).
  • Corrupt state database (F6). A crash mid-update. A CRC mismatch or invalid epoch tag on open is detected; auto-recovery truncates to the last good epoch and marks all nodes dirty. §7.8 instead discards the entire checkpoint and falls back to full evaluation; §4.1 and §4.6 budget at most 10 s for that fallback.
  • Missed file change, a silent under-build (F7). The inotify queue overflowed; the counter watch.events_dropped_total shows it and the polling fallback re-scans.
  • Remote result with the wrong digest (F8). A remote bug or a man-in-the-middle. Digest verification at fetch triggers a local re-execution and a report to the remote operator.

Threats from the Threat Model's attack-surface table:

  • Undeclared input exfiltration (sandbox bypass): ibg-sandbox intercepts file-system calls and denies undeclared reads; the action fails, its node is marked Failed, and nothing is cached.
  • Remote cache poisoning (MITM): every fetched blob is checked against its digest before materialization; a mismatch drops it, re-executes locally and raises an alert.
  • Cycle injection via dynamic dep: a cycle check runs on every edge insert; the dependency is rejected and the error goes back to the requesting node.
  • Supply-chain — malicious tool in PATH: the tool's digest is part of the ActionKey, so a changed tool triggers a rebuild; the fix is to re-fetch a known-good tool.

How it compares

  • Bazel is the canonical hermetic, content-addressed build system with Skyframe incremental evaluation and native REAPI, and wins for large polyglot monorepos needing remote execution. This design reimplements its core ideas at teachable scale and defers remote execution and Starlark (Comparative Architecture Table).
  • Buck2 is a Rust rewrite with a fully dynamic, async graph and strong remote-execution integration, which pays off where dynamic dependencies and scale matter. This design shares the lineage but keeps a simpler static-then-incremental graph for clarity (Comparative Architecture Table).
  • Ninja is a minimal, fast executor using mtime and depfiles rather than content hashing. That is fine as a low-level backend whose front-end already computed the graph; this design owns fingerprinting and early cutoff for correctness Ninja trades away (Comparative Architecture Table, Alt-A).
  • Nx and Turborepo do task-level input-hash caching with cloud caches for JavaScript and TypeScript monorepos, which suits front-end repos. This design works at file and action granularity with sandboxing and no language assumptions (Comparative Architecture Table).

If you only remember three things

Correctness comes from content, not clocks: the cache key is a pure function of declared inputs, and anything that reads an undeclared input is stopped and never cached (MM1, MM4, §6.2). The speed comes from doing less: pull only what is demanded, and stop propagating dirtiness the moment a node's output digest is unchanged (MM3, §6.4, §6.5). When anything is uncertain, such as corrupt state, a cycle or a missed event, the design fails loudly or falls back to a full rebuild rather than risk a silently wrong incremental result (§6.15, MM9).

Words used here

  • Action: one hermetic unit of work, defined by command, declared inputs, declared outputs, environment and tool digest.
  • ActionKey: a digest of everything that determines an action's output; the cache key.
  • CAS (content-addressed store): a blob store where each blob is named by its own hash.
  • Revision: the global counter that advances with each build; drives red/green accounting.
  • Red / green: dirty or needs-checking, versus verified at the current revision (from Salsa).
  • Early cutoff: stopping dirty propagation when a re-run produces the same output digest.
  • Stat fast-path: skipping the file read when modification time, size and inode are unchanged.
  • Hermetic: depending only on declared inputs, so the same key always gives the same output.
  • Critical path: the longest weighted chain of dependent actions; it bounds wall-clock time.
  • Dynamic dependency: an edge discovered while an action runs, recorded for future builds.
