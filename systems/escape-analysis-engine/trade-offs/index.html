Decisions (§9) · 30 ADRs

ADR-01

Implementation language

Chosen

Rust 1.82+

Rejected

C++, OCaml, Java

When the rejected choice is right

C++ wins when embedding directly into an existing C++-only compiler (e.g., a GCC plugin) where FFI overhead of a Rust component is unacceptable

Why: memory safety without GC pauses in a compiler-pipeline hot path; algebraic enums fit the escape lattice exactly

ADR-02

Analysis abstraction

Chosen

connection graph (Choi et al. 1999)

Rejected

points-to-then-escape (derive escape from a separate whole points-to solve), type-based (Blanchet)

When the rejected choice is right

type-based (Blanchet) wins in a JIT with a hard per-method compile-time budget where near-linear type-based propagation is required over connection-graph precision

Why: connection graph unifies points-to and escape state in one incrementally-updatable structure

ADR-03

Points-to foundation

Chosen

Andersen inclusion-based, field-sensitive

Rejected

Steensgaard unification-based

When the rejected choice is right

Steensgaard wins for a whole-program, compile-time-constrained ahead-of-time compiler (e.g., a mobile AOT backend) where near-linear scaling outweighs precision loss

Why: precision needed for I6's field-alias soundness check on scalar replacement

ADR-04

Analysis scope

Chosen

interprocedural (bottom-up summaries)

Rejected

intraprocedural-only

When the rejected choice is right

intraprocedural-only wins for a debug/non-optimizing build tier where compile speed dominates and missed optimizations are acceptable

Why: cross-method captures (the worked two-method example in §8) are the majority of real NoEscape wins

ADR-05

Interprocedural strategy

Chosen

bottom-up method summaries (Whaley & Rinard 1999)

Rejected

top-down (re-analyze callees per caller), whole-program monolithic solve

When the rejected choice is right

whole-program monolithic solve wins for a small, closed, non-modular program (e.g., a single-file benchmark) where summary infrastructure overhead isn't justified

Why: scales linearly in method count instead of blowing up with call-site fan-in

ADR-06

Context sensitivity

Chosen

context-insensitive baseline, optional 1-CFA extension

Rejected

full k-CFA, object-sensitivity as default

When the rejected choice is right

full k-CFA wins on a small, hot, dispatch-heavy inner-loop method set flagged for extra optimization budget (e.g., a JIT's top-tier compiler)

Why: k-CFA's exponential blowup is unacceptable as a default; 1-CFA is an opt-in precision knob

ADR-07

Field sensitivity

Chosen

field-sensitive (per-field connection-graph nodes)

Rejected

field-insensitive (object-merged fields)

When the rejected choice is right

field-insensitive wins in a fast first-tier JIT compile where compile latency dominates and scalar replacement isn't attempted at that tier

Why: required for I6 scalar-replacement soundness

ADR-08

Flow sensitivity

Chosen

flow-sensitive within a method (SSA-ordered transfer application)

Rejected

flow-insensitive (unordered constraint solve)

When the rejected choice is right

flow-insensitive wins for a purely points-to (not escape) whole-program prepass used only to seed the call graph, where flow order adds no value

Why: SSA already gives a natural flow order at near-zero extra cost

ADR-09

Escape-lattice design

Chosen

3-point lattice (NoEscape/ArgEscape/GlobalEscape)

Rejected

2-point (Escapes/DoesNotEscape), richer N-point (add ThreadEscape as distinct top)

When the rejected choice is right

a 4-point lattice with a distinct ThreadEscape state wins when lock elision needs to be distinguished from full GlobalEscape at the classifier level rather than as a Phase 9 side analysis

Why: 3 points match Choi et al.'s original formulation and the optimizer's three consumer categories exactly

ADR-10

Chosen

Rejected

When the rejected choice is right

CHA-only wins in an early Phase-0 skeleton milestone where RTA infrastructure isn't built yet

Why: RTA refinement removes the majority of CHA's spurious virtual-dispatch targets cheaply

ADR-11

Virtual/dynamic dispatch handling

Chosen

ADR-12

Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

A1. Type-based escape analysis (Blanchet) vs the connection-graph approach

  [Blanchet type-based]              [This project: connection graph]
  types carry escape info    vs      per-object graph nodes + edges
  near-linear propagation            precise but graph-maintenance-heavy
  coarser (type-granularity)         field/object-granularity precision

Winning regime: a JIT with a hard, small per-method compile-time budget where near-linear type-based propagation is required and coarser precision is an acceptable tradeoff. Real embodying system: Blanchet's own OOPSLA 1999/2003 implementation, designed explicitly for that budget. Rejected here because this project's stated payoff target (§4, M11, ≥35% NoEscape) needs field/object-granularity precision that a purely type-based lattice under-delivers on, per Blanchet's own reported precision numbers relative to connection-graph approaches.

A2. Unification-based points-to (Steensgaard) vs inclusion-based (Andersen)

  [Steensgaard: unification]         [This project: Andersen inclusion]
  near-linear, coarser sets   vs      cubic worst-case, precise sets
  merges aliasing eagerly            preserves directional flow precisely

Winning regime: a whole-program, compile-time-constrained ahead-of-time compiler (e.g., embedded/mobile AOT backends) where near-linear scaling outweighs precision loss, exactly as named in ADR-03's sixth column. Real embodying system: Steensgaard's own POPL 1996 implementation and its descendants in several production AOT toolchains. Rejected here because I6's field-alias-free soundness check for scalar replacement (Phase 7) needs Andersen-level directional precision to avoid over-rejecting valid candidates.

A3. Intraprocedural-only analysis vs full interprocedural

  [Intraprocedural-only]             [This project: full interprocedural]
  fast, per-method only       vs      bottom-up summaries (Phase 5)
  misses cross-method capture         captures the §8 store/run example

Winning regime: a debug/non-optimizing build tier where compile speed dominates and missed cross-method optimizations are an acceptable cost, matching ADR-04's sixth column exactly. Real embodying system: many JIT compilers' lowest optimization tier runs escape analysis intraprocedurally-only or skips it entirely for this reason. Rejected as this project's default because the §8 worked two-method example demonstrates the majority of real-world NoEscape wins are specifically cross-method.

A4. Partial escape analysis (GraalVM) as a fundamentally more precise baseline model

  [Whole-object baseline]            [Partial/path-sensitive, as default]
  one state per object         vs    state varies per control-flow path
  simpler, this project's floor      strictly more precise, higher cost

Winning regime: a JIT with aggressive inlining and a compile-time budget that can absorb path-sensitive bookkeeping across a large inlined region — GraalVM's actual production regime. Real embodying system: GraalVM's Graal compiler. Rejected as this project's default baseline (though included additively in Phase 10, gated by I12) because a from-scratch project's first soundness obligation is a provably correct whole-object baseline; path-sensitivity is layered on afterward specifically so a partial-escape bug can never regress below that already-proven baseline (I12's entire reason for existing).
