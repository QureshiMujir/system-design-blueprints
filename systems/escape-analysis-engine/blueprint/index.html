245 — Escape Analysis Engine

Project Number: 245

Project Name: Escape Analysis Engine

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

This project builds, from scratch in Rust, an interprocedural escape analysis engine: a compiler dataflow pass that determines, for every dynamically allocated object in a program's SSA-based IR, whether that object escapes its allocating method or thread — is reachable after the method returns, stored into a field, passed to an unknown/native callee, or shared across threads — or is captured, i.e., provably confined to the allocating stack frame. The pass is built around the connection-graph abstraction of Choi et al. 1999 ("Escape Analysis for Java", OOPSLA), extended interprocedurally via bottom-up method summaries (Whaley & Rinard 1999), and classifies every allocation site into one of three escape states — NoEscape, ArgEscape, GlobalEscape — which downstream optimizer and deoptimization consumers use to perform stack allocation, scalar replacement of aggregates, and lock elision. The engine is a pure analysis: it computes facts about the program and emits them as an OptimizationFacts interface; it never itself rewrites IR, allocates stack frames, elides locks, or rematerializes objects at deopt time. Those transformations belong to the optimizer and to the sibling Deoptimization-Engine (project 246), which consumes scalar-replacement summaries to rematerialize scalarized objects when a speculative optimization is undone.

Phase-0 deliverable — the following crates, each a compilable, independently testable unit:

  1. ir-model — frontend-independent SSA IR node/statement/type model this pass consumes.
  2. cfg-callgraph — intraprocedural CFG construction plus call-graph edges (CHA/RTA seeded).
  3. connection-graph — the Choi connection-graph builder: object nodes, reference nodes, field nodes, points-to and deferred edges.
  4. escape-lattice — the three-point escape lattice (NoEscape ⊑ ArgEscape ⊑ GlobalEscape) and its join/meet.
  5. fixpoint-solver — intraprocedural transfer functions and worklist fixpoint iteration over the connection graph.
  6. classifier — the escape-state classifier that reads a converged connection graph and assigns per-allocation escape states.
  7. callgraph-dispatch — virtual/dynamic dispatch resolution feeding the call graph (CHA, RTA, points-to-refined).
  8. summary-engine — interprocedural method summaries, bottom-up SCC traversal of the call graph, actual-to-formal mapping at call sites.
  9. partial-escape — branch-sensitive partial escape analysis (GraalVM-style materialization points).
  10. optimizer-facts — the OptimizationFacts emitter: scalar-replacement candidates, stack-allocation candidates, lock-elision sites.
  11. soundness-oracle — the dynamic differential oracle that instruments a reference interpreter to verify no NoEscape object actually escapes.
  12. summary-cache — persistent, versioned method-summary cache keyed by IR content hash.
  13. observability-runtime — metrics, tracing, connection-graph dump tooling.
  14. conformance-suite — the labeled escape/capture corpus and differential-validation harness.
  15. cli-driver — the standalone analysis-pass driver for benchmarking and CI.

Boundaries. Provides: connection-graph construction, intraprocedural and interprocedural escape-state computation, method summaries, a soundness-checked OptimizationFacts output (scalar-replacement candidates, stack-allocation candidates, lock-elision sites), a connection-graph dump/trace format for debugging. Delegates: the actual IR rewrite that performs stack allocation, scalar replacement, and lock removal is owned by the optimizing compiler's transformation passes, not this engine; rematerialization of a scalar-replaced object on deoptimization is owned by Deoptimization-Engine (246), which reads this engine's scalar-replacement summaries to reconstruct heap objects when a deopt unwinds past an optimized frame. Does NOT provide: code generation, register allocation, a garbage collector, a full compiler frontend, or a bytecode verifier (that is project 247's job — this pass assumes already-verified, well-typed SSA IR and does not re-derive type or shape safety).

Non-goals, named explicitly against sibling projects: this is not JIT-Compiler — it does not lower IR to machine code or make inlining/scheduling decisions, it only feeds those passes escape facts. It is not Deoptimization-Engine (246) — it does not decide when to deoptimize or how to rebuild a deopt frame; it only supplies the scalar-replacement metadata that 246's rematerialization step consumes. It is not Bytecode-Verifier (247) — it assumes sound, verified input IR and is not a safety-verification pass; an unsound escape classification is a miscompilation bug in this project, not a verification gap in 247's. It is not Garbage-Collector (32) — it reduces GC pressure as a side effect of enabling stack allocation, but it never manages heap memory, scans roots, or moves objects itself. The one property this project is uniquely responsible for is soundness of escape classification: never mark an escaping object as captured.

IR/language model assumed: an SSA-based optimizing-compiler intermediate representation over an object-oriented or otherwise heap-allocating managed language, with explicit new/alloc, load/store (including field and array access), call (direct and virtual), return, and thread-spawn primitives; the pass is IR-shape-agnostic beyond requiring SSA def-use and a resolvable (possibly incomplete) call graph. Deployment model: a reusable, embeddable compiler analysis pass, invoked once per compilation unit or incrementally per method, with no runtime component of its own — it ships as a library plus a standalone CLI driver for offline benchmarking and conformance testing. Users/operators: compiler engineers integrating the pass into an optimizing-compiler pipeline, and PL researchers evaluating precision/soundness tradeoffs against the labeled corpus.

Later phases unlock: scalar replacement of aggregates in the optimizer, stack allocation of NoEscape objects, lock elision on thread-confined monitors, GraalVM-style partial (branch-sensitive) escape analysis, and a differential soundness oracle usable as a CI correctness gate for any future optimization that depends on escape facts.

Language: Rust 1.82+. Rationale: no GC pauses in a latency-sensitive compiler-pipeline component; algebraic enums map directly onto the three-state escape lattice and the connection-graph node/edge taxonomy with exhaustive-match safety; strong ownership discipline prevents the aliasing bugs that a hand-rolled points-to engine is otherwise prone to; mature graph/arena crates and deterministic Cargo.lock builds support reproducible conformance runs. Rejected languages: C++ (rejected — manual memory management invites exactly the aliasing/lifetime bugs this pass analyzes for other programs; slower iteration on lattice-shaped code); OCaml (rejected — excellent fit for the dataflow-equations style but weaker systems-integration story for embedding into a Rust/LLVM-adjacent compiler pipeline and weaker profiling tooling); Java (rejected — reflexive irony of hosting a GC-pressure-reduction tool on a GC'd runtime, and JIT warm-up variance pollutes the pass's own latency benchmarks).

Prerequisites: compiler construction (SSA, CFG, dominance), dataflow analysis and fixpoint theory, pointer/points-to analysis (Andersen, Steensgaard), abstract interpretation (Cousot & Cousot 1977), lattice theory, interprocedural analysis strategies (Sharir & Pnueli 1981 call-strings vs functional). Timeline: Phase 0 skeleton 3 weeks; Phases 1-3 (connection graph, intraprocedural fixpoint, classifier) 8 weeks; Phases 4-6 (call graph, summaries, actual-formal mapping) 8 weeks; Phases 7-9 (scalar replacement, stack alloc, lock elision) 6 weeks; Phase 10 (partial escape analysis) 4 weeks; Phase 11 (soundness/precision benchmark, perf hardening) 4 weeks; total approximately 8 months to a soundness-gated release.

Deferrals: PhaseDeferred("Phase 10 — Partial Escape Analysis") — branch-sensitive materialization is deferred past the baseline whole-object classifier in Phase 3. PhaseDeferred("Phase 6 — Mapping Actuals to Formals at Call Sites") — full context-sensitive (k-CFA) actual/formal binding is deferred behind the context-insensitive bottom-up baseline shipped in Phase 5. PhaseDeferred("Phase 9 — Thread-Escape Analysis and Lock-Elision Sites") — thread-confinement modeling is deferred until the sequential escape lattice is soundness-validated. PhaseDeferred("Phase 11 — Soundness-and-Precision Benchmark, Differential Validation, and Perf Hardening") — whole-program (as opposed to per-compilation-unit) analysis scaling work is deferred to the perf-hardening pass.

2. Why Build This

  • interprocedural dataflow analysis
  • connection-graph / points-to abstraction
  • fixpoint computation over a monotone lattice
  • soundness-vs-precision tradeoffs in static analysis
  • bottom-up summary-based interprocedural analysis
  • call-graph construction under virtual dispatch uncertainty
  • context and field sensitivity cost/precision tuning
  • compiler-optimization payoff measurement (allocation elimination)
  • differential and dynamic-oracle correctness validation
  • the historical link between escape analysis and JIT deoptimization (Kotzmann & Mössenböck 2005)
  • partial escape analysis as a precision advance (GraalVM)
  • abstract interpretation as the theoretical foundation (Cousot & Cousot 1977)

Escape analysis is the textbook case where a purely static, purely mathematical abstraction (reachability in a graph) has direct, measurable production payoff: every allocation proven NoEscape is a heap allocation, and eventually a GC cycle, that never happens. It is also the textbook case where a single soundness bug is not a missed optimization but a miscompilation — a stack-allocated object that actually escapes is a live use-after-return bug, indistinguishable at the machine level from memory corruption. Building this project end to end forces direct engagement with fixpoint termination proofs, lattice monotonicity, the scalability wall of points-to analysis (Hind 2001), and the interprocedural summary technique that makes production compilers tractable.

What Mastery Looks Like

  • Can derive, from first principles, why the connection graph (Choi et al. 1999) needs both points-to edges and deferred edges, and demonstrate the difference with a worked example (Phase 1).
  • Can write a monotone transfer function for every SSA statement class and prove the escape lattice's finite height bounds fixpoint iteration (Phase 2).
  • Can classify an allocation site as NoEscape / ArgEscape / GlobalEscape from a converged connection graph and defend the classification against a soundness adversary (Phase 3).
  • Can explain why bottom-up method summaries scale where naive re-analysis of callees does not, and produce the SCC-ordering algorithm over a call graph with recursion (Phase 5).
  • Can implement actual-to-formal parameter mapping at a call site and show how an imprecise summary forces conservative GlobalEscape propagation (Phase 6).
  • Can distinguish "captured" precisely enough to gate scalar replacement without introducing a field-aliasing unsoundness (Phase 7).
  • Can implement thread-escape detection and justify why lock elision requires strictly more evidence than stack-allocation eligibility (Phase 9).
  • Can explain, with a concrete branch example, why GraalVM's partial escape analysis is strictly more precise than the classic Choi connection graph and reproduce its materialization-point insertion (Phase 10).

IR Reader: parses the frontend-independent SSA IR into the pass's canonical internal model — functions, basic blocks, statements (alloc, load, store, call, return, spawn), and types — validating def-use well-formedness before any analysis runs; malformed input is rejected here, not downstream.

Connection-Graph Builder: constructs the Choi et al. 1999 connection graph per method — object nodes for each allocation site, reference nodes for each SSA value, field nodes for each object's fields, points-to edges from references to objects, field edges, and deferred edges connecting reference nodes not yet resolved to concrete objects (used for parameter/return abstraction).

Intraprocedural Escape-Lattice Solver: runs a worklist fixpoint over the connection graph, applying a transfer function per statement class, until node escape labels stabilize; enforces lattice monotonicity (labels only move up: NoEscape → ArgEscape → GlobalEscape) and bounds iteration by lattice height times node count.

Call-Graph Provider: resolves call edges, including virtual/dynamic dispatch, using CHA/RTA seeding refined by points-to information where available; supplies the interprocedural summary engine with a traversable call graph including SCCs for recursion.

Interprocedural Summary Engine: traverses the call graph bottom-up over SCCs, computing a method summary — a sound abstraction of how each parameter's/return's escape state depends on the arguments passed — and applying summaries at call sites instead of re-analyzing callees.

Escape-State Classifier: reads the fully converged (intra- and interprocedural) connection graph and assigns each allocation site one of NoEscape, ArgEscape, GlobalEscape.

Optimization-Info Emitter: translates classified allocation sites and lock sites into OptimizationFacts — scalar-replacement candidates, stack-allocation candidates, and lock-elision sites — consumed by the optimizer and, for scalar-replacement facts, by the Deoptimization-Engine (246) rematerialization path.

Soundness Verifier: a differential, dynamically-instrumented oracle that runs labeled/benchmark programs, records actual object lifetimes and thread-sharing at runtime, and asserts no NoEscape-classified object actually escaped — the correctness backstop referenced throughout Phase 11 and §28.

6. Design Principles

  • P1. The analysis is sound in one direction only — it may conservatively call a captured object "escaping" (a missed optimization) but must NEVER call an escaping object "captured" (a miscompilation), because a wrongly stack-allocated escaping object is a use-after-return (Choi et al. 1999).
  • P2. Escape analysis is a points-to/reachability problem — an object escapes iff it is reachable from a global root or an unknown callee at method-return time, so the connection graph is the core abstraction, not an afterthought representation.
  • P3. Interprocedural precision comes from method summaries composed bottom-up over the call graph, because re-analyzing callees at every call site does not scale (Whaley & Rinard 1999).
  • P4. The escape lattice is monotone and finite-height by construction — every transfer function only raises a node's state, guaranteeing fixpoint termination in bounded iterations.
  • P5. An unresolved or native callee is always treated as the least precise, most conservative summary (GlobalEscape on every escaping parameter), never as an unknown defaulting to NoEscape.
  • P6. Field sensitivity and context sensitivity are precision knobs, not correctness requirements — the context-insensitive, field-sensitive baseline must already be sound before any precision extension ships.
  • P7. A method summary is itself a sound over-approximation of that method's escape behavior — summaries compose without losing soundness, only precision.
  • P8. Virtual/dynamic dispatch with an unresolved target set is treated as a call to the join of all resolvable targets' summaries, never as a call to the single most likely target.
  • P9. Scalar-replacement candidates are exactly the NoEscape objects with no observed field aliasing that would make per-field replacement unsound.
  • P10. Lock-elision sites require strictly more evidence than stack-allocation eligibility — thread-confinement, not mere method-confinement, because a lock is escapable to a different thread of the same method's continuation even when the lock object itself is NoEscape at the allocation site.
  • P11. Partial escape analysis (GraalVM-style) refines but never contradicts the whole-object connection-graph baseline — path-sensitive materialization is an additive precision layer on top of a sound coarse classification.
  • P12. Every soundness-relevant decision must be replayable from a connection-graph dump — if a classification cannot be reconstructed from the dumped graph and transfer trace, the trace format is incomplete, not the bug elsewhere.
  • P13. Incremental re-analysis invalidates by content hash of a method's IR plus its transitive summary dependencies, never by wall-clock or file-mtime heuristics.
  • P14. The optimizer-facing OptimizationFacts interface is versioned independently of the internal connection-graph representation, so the summary cache format can evolve without breaking optimizer or deopt-engine consumers.

8. Domain Model

The Escape Lattice

        GlobalEscape        (top: reachable from a global root
             |                or an unknown/native callee)
        ArgEscape            (escapes the allocating method via
             |                a parameter/return, but not global)
        NoEscape             (bottom: confined to the allocating
                              stack frame)

Join (⊔) is least-upper-bound toward GlobalEscape: NoEscape ⊔ x = x, ArgEscape ⊔ GlobalEscape = GlobalEscape, x ⊔ x = x. Meet is unused — the analysis only ever raises state (P4), so only join appears in transfer functions. Lattice height = 3, giving the fixpoint iteration bound in I3.

Connection-Graph Model

Element Represents Edge/Node kind
Object node (O_i) an abstract allocation site node
Reference node (R_v) an SSA value that may hold a reference node
Field node (F_o.f) field f of abstract object o node
Points-to edge R_v -> O_i: v may point to object i edge, reference→object
Field edge O_i.f -> O_j: field f of object i may point to object j edge, object.field→object
Deferred edge R_v -> R_w: v's points-to set is deferred to (copies) w's edge, reference→reference

Worked example — method m(p):

a = new Foo()          // O_a created, R_a -> O_a
a.f = p                // field edge O_a.f -> (points-to set of R_p)
b = a                  // deferred edge R_b -> R_a
return b               // R_b (and transitively O_a) escapes via return

Resulting graph: R_a -> O_a, O_a.f -> ?(R_p's points-to set), R_b -> R_a (deferred). Because b is returned, O_a is reachable from the method's return value, so O_a is classified ArgEscape (escapes the method but only to the immediate caller, not globally) — unless the caller's summary further promotes it.

Intraprocedural Transfer Functions

Statement Connection-graph effect Escape-state effect
r = new T create object node O_r, points-to edge R_r -> O_r O_r initialized NoEscape
r.f = v add field edge O_r.f -> points-to(v) join v's pointee states with O_r's current state if O_r already escapes (escape propagates through fields)

spawn t(args) mark each arg's pointees thread-shared join with GlobalEscape-for-thread-sharing (or a distinct thread-escape sub-state feeding lock elision, Phase 9)

Worked propagation to fixpoint (the example above): iteration 0 — O_a = NoEscape. Iteration 1 — the return b transfer joins O_a (reachable via deferred edge R_b -> R_a -> O_a) with ArgEscape. Iteration 2 — no further statements touch O_a; state stable. Fixpoint reached in 2 iterations, within the I3 bound.

Interprocedural Model

Named steps: (1) compute the call graph's SCCs; (2) process SCCs in reverse topological (bottom-up) order so callees are summarized before callers; (3) within an SCC (mutual recursion), iterate to a local fixpoint using each member's best-known partial summary; (4) for each method, build a summary mapping each formal parameter and the return value to an escape-transfer function of the actuals; (5) at each call site in a caller, apply the callee's summary by substituting actual arguments for formals (actual-to-formal mapping, Phase 6).

Worked two-method example:

callee: void store(Box b, Object x) { b.slot = x; }
caller: void run() {
    Box local = new Box();
    Object o = new Object();
    store(local, o);
    // local not returned, not stored globally
}

store's summary: parameter x's escape state is joined into whatever escape state its slot-holder (b) has when store returns — i.e., x escapes to at most b's state. Applying this summary at the call site in run: b -> local, x -> o; local is NoEscape in run (never returned or stored globally), so o is joined to NoEscape via local's state — o is classified NoEscape too, without ever re-analyzing store's body from run's call site.

Partial Escape Analysis (Contrast Model)

Classic connection-graph analysis assigns one escape state per object for the whole method. GraalVM's partial escape analysis instead tracks escape state per control-flow path and defers materialization (converting a virtual/scalarized object back into a real heap object) to only the branch that actually causes it to escape:

if (cond) {
    obj.publish();   // escapes ONLY on this path -> materialize here
} else {
    // obj stays virtual/scalarized on this path
}

The whole-object baseline must conservatively classify obj as escaping (join over both paths), while partial escape analysis keeps it virtual on the non-escaping path and inserts a materialization point exactly where the fast path's virtual object becomes observable — strictly more precise, at the cost of path-sensitive state (I12 governs how this interacts with the sound baseline).

Malformed / Hard Examples

  • Recursive method: summary computed via local SCC fixpoint (interprocedural model step 3); a naive non-SCC-aware traversal would infinite-loop.
  • Virtual call with unknown targets: joined over all resolvable targets (P8); an empty resolvable set (fully unknown) forces GlobalEscape on all arguments (I4-equivalent).
  • Object stored in a static field: field edge from a synthetic "global root" object node — any object reachable from the global root node is GlobalEscape by construction.
  • Thread-shared object: spawn transfer marks pointees thread-shared (Phase 9); interacts with I7 for lock elision.
  • Cycle in the connection graph: handled by the fixpoint solver's worklist naturally — cycles just mean multiple nodes co-stabilize; no special-casing needed given monotonicity (I2).
  • Soundness trap — object returned then apparently stack-allocatable: an object returned by a callee, then never used further by the immediate caller, is NOT NoEscape at the callee's allocation site — it is at least ArgEscape there; only if the caller's own analysis re-confirms non-escape in the caller's frame could stack allocation apply in the caller's frame, never retroactively in the callee's.

Failure-Path Example

An IR module with a call to a method not present in the call graph (a genuinely unresolvable external symbol) triggers I4's native-callee conservative path: all arguments' pointees join to GlobalEscape, a native_callsite_conservative_total telemetry increment fires, and analysis proceeds — this is expected conservative behavior, not an error.

12. Phase 0 — Skeleton, IR Reader, Escape Lattice, and CI

12.1 Objectives

Stand up the workspace skeleton (§10 crate layout), the ir-model SSA IR reader, the three-point escape-lattice (ADR-09), and a CI pipeline capable of running lint, unit tests, and a soundness-oracle smoke job before any real analysis logic exists.

12.2 Detailed Implementation Steps

  • Scaffold the Cargo workspace exactly matching §10's crate list; wire ADR-26 (workspace-of-crates, not monolith).
  • Implement ir-model's Method, Statement, IrNode types per §11, with def-use well-formedness validation on read (P2's reachability model needs a valid graph to start from).
  • Implement the IR reader's rejection path for malformed input (EscapeError::MalformedIr), emitting a deterministic diagnostic per site.
  • Implement escape-lattice's EscapeState enum and join function; prove and unit-test monotonicity (I2) and finite height (I3) directly on the lattice type before any graph exists.
  • Implement Fixpoint's bounded worklist skeleton (empty transfer functions for now) to validate the iteration-cap plumbing (I3) end-to-end.
  • Stand up observability-runtime's tracing subscriber (ADR-20/ADR-21) and register the fixpoint_iterations_total and unsound_classification_total metrics (I3, I1) even though they will read zero until later phases populate them.
  • Wire GitHub Actions (ADR-25): lint (clippy), unit test (cargo-nextest, ADR-23), and a placeholder soundness.yml job that currently only checks the corpus loads.
  • Add the first conformance fixtures: minimal valid and minimal malformed IR programs.
  • Implement deterministic content-hashing for MethodId/AllocId (I8/I9 prerequisite).
  • Add cargo-fuzz scaffold targeting the IR reader (ADR-24), even with a trivial seed corpus.
  • Implement the crate-boundary contract between ir-model and connection-graph as an explicit IrModuleView trait (methods, blocks, statements, types by reference) so Phase 1 never needs a breaking API change once real graph construction starts.
  • Select and vendor a single deterministic content-hash function (BLAKE3, fixed seed, no per-process randomization) for MethodId/AllocId derivation, documented once here so Phase 1/5 don't each re-decide it independently.
  • Pre-declare TransferFn (Phase 2's trait, §11) as an empty marker trait with no implementations yet, so the Phase 0 skeleton's fixpoint-solver crate compiles end-to-end against a real trait signature instead of a TODO stub.
  • Implement the cli-driver's minimal --dump-ir flag against the IR reader's own output, giving every later phase a debugging entrypoint before the connection-graph dump tool (Phase 1) exists.

12.3 Deliverable

A compiling workspace with a working IR reader, a proven-monotone escape lattice, and a green CI pipeline (lint + unit + fuzz-smoke).

12.4 Acceptance Criteria

  • 100% of ir-model def-use validation paths covered by unit tests.
  • Lattice monotonicity property-tested across all 9 (EscapeState, EscapeState) join pairs with zero violations.
  • IR read throughput ≥ 6,000,000 IR nodes/sec on the Phase-0 fixture set (§4 target, measured early to catch regressions).
  • CI green on lint, unit, and fuzz-smoke for 20 consecutive commits before Phase 1 begins.

12.5 Conformance Fixtures

  • conformance/phase0/valid_minimal.ir — a single method, one allocation, no escapes.
  • conformance/phase0/malformed_dangling_ref.ir — a reference to an undefined value; must trigger EscapeError::MalformedIr.
  • conformance/phase0/malformed_duplicate_def.ir — SSA single-def violation.
  • conformance/phase0/malformed_type_mismatch.ir — a store whose value type doesn't match the target field's declared type; must trigger EscapeError::MalformedIr at read time, not silently downstream in the classifier.
  • conformance/phase0/native_declared_no_body.ir — a module containing only native/external method declarations with no bodies, verifying the reader accepts a headers-only module without erroring.

12.6 Pitfalls

  1. Treating MethodId/AllocId as arbitrary counters instead of content-hash-derived — breaks I8/I9 later and forces a painful retrofit.
  2. Skipping the lattice monotonicity proof because "it's just three values" — the join table has 9 entries and a transposition bug is easy to miss without exhaustive testing.
  3. Standing up tracing after analysis logic exists rather than before — retrofitting spans into transfer functions later is error-prone.
  4. Under-scoping the CI soundness job as "future work" and never actually wiring the placeholder that Phase 11 will fill in.
  5. Hashing MethodId from IR syntax alone, omitting the IR schema version — manifestation: two schema versions producing byte-identical method bodies collide on the same MethodId; root cause: the content-hash preimage doesn't include EscapeError::SchemaVersionMismatch's version tag; debug method: replay the hash derivation across both schema versions on a shared fixture; signal: node_identity_conflict_total fires immediately after a schema bump with no source change; recovery: fold the schema version into the hash preimage and force a full re-analysis on any schema bump.
  6. Wiring the CI fuzz-smoke job (ADR-24) against a fixed, never-regenerated seed corpus — manifestation: the fuzzer reports the same zero-findings result release after release; root cause: seed-corpus coverage plateaued at Phase-0-era IR shapes; debug method: diff fuzz-corpus file coverage against the current conformance/ tree; signal: fuzz corpus file count stays static across multiple releases while conformance/ keeps growing; recovery: regenerate the seed corpus from the latest conformance fixtures every release.
  7. Treating the placeholder soundness.yml job's green status as equivalent to a real soundness gate — manifestation: a reviewer approves a Phase-0-era PR citing "soundness CI is green"; root cause: the placeholder only checks that the corpus loads, not that classification is correct; debug method: read the job's actual assertions instead of trusting its pass/fail badge; signal: the job's log shows zero classification-related assertions; recovery: label the placeholder job soundness-smoke, not soundness, until Phase 11 replaces it.
  8. Choosing a content-hash function without checking its collision-resistance characteristics against the expected corpus scale — manifestation: two genuinely distinct methods collide on the same MethodId at the multi-million-method scale targeted by §4's summary-cache ceiling; root cause: a fast but weaker hash was chosen for throughput without checking its birthday-bound at that scale; debug method: run a collision-probability calculation against the §4 M9/summary-cache target of 2,000,000 resident summaries; signal: node_identity_conflict_total shows non-zero collisions under normal (non-adversarial) load at scale; recovery: use a hash width (e.g., BLAKE3's 256-bit output, truncated no lower than 128 bits) whose birthday bound is astronomically beyond the largest realistic corpus.

12.7 Performance Concerns

  • IR reader allocation patterns (one arena vs many small heap allocations) set the baseline for every later phase's throughput number — get arena-backed storage right now, not later.
  • Content-hashing cost must stay off the hot read path except at method boundaries.

12.8 Edge Cases

  • Empty method body (no statements) — must classify as trivially sound with zero allocations.
  • IR with a method that calls itself directly (self-recursion) — the call-graph/SCC machinery isn't built yet, so Phase 0 only needs to not crash, not analyze correctly.
  • Duplicate MethodId collision on hash — must be detected and rejected, not silently overwritten.
  • A module containing two methods with textually identical bodies — content-hash-derived MethodIds must still be distinct, since the hash preimage includes the method's declared signature/position-independent identity, not body text alone.
  • A method whose IR is byte-identical to a previously-analyzed method's IR except for the compilation unit it belongs to — MethodId derivation must include a compilation-unit-scoping component, or two unrelated modules' trivially-identical helper methods will collide.

12.9 Failure Analysis

Failure: a malformed IR file is silently accepted with default-initialized fields. Detection: def-use validator's coverage tests (Acceptance Criteria) plus the malformed-fixture conformance tests. Containment: reject at IR-read time (EscapeError::MalformedIr) before any downstream crate observes the module — this is P2's reachability model's precondition, so a bad graph must never leave the reader.

Failure: the CI fuzz-smoke job (ADR-24) never regenerates its seed corpus and silently stops finding anything meaningful past Phase 0. Detection: a coverage-diff check comparing fuzz/'s seed corpus against the current conformance/ tree, run as part of this phase's own CI job. Containment: regenerate the fuzz seed corpus from conformance/ fixtures on every release, not just at Phase-0 setup time, so Phase 11's expanded fuzzing campaign (§23.2) doesn't inherit a stale seed set.

Failure: a weak or under-sized content-hash truncation causes a genuine (non-adversarial) MethodId collision once the corpus reaches production scale. Detection: a synthetic collision-probability check run against the §4 M9 summary-cache ceiling as a Phase-0 CI assertion, not discovered empirically in production. Containment: widen the hash truncation width and force a one-time full re-analysis if a collision is ever observed outside the synthetic check.

12.10 Operational Notes

Expose ir_read_throughput_nodes_per_sec and ir_read_rejected_total from day one; every later phase's telemetry builds on this baseline. Document the CI soundness-job placeholder explicitly in docs/runbooks/ so Phase 11 knows exactly what to fill in.

Track ir_read_rejected_total broken down by EscapeError variant from day one, not just as an aggregate count — a spike isolated to MalformedIr demands a different on-call response than one isolated to SchemaVersionMismatch, and retrofitting that breakdown after Phase 5's schema-versioning work begins is far more disruptive than adding the label now.

Publish the chosen content-hash function's name and truncation width in docs/adr/ alongside ADR-19 (incremental analysis), since any future change to either is a cache-invalidating, not additive, schema event and must be flagged as such in release notes.

13. Phase 1 — The Connection-Graph Representation

13.1 Objectives

Implement the Choi et al. 1999 connection graph (§8): object nodes, reference nodes, field nodes, points-to edges, field edges, and deferred edges, as a per-method mutable-during-analysis, frozen-after-convergence structure (ADR-02, P2).

13.2 Detailed Implementation Steps

  • Implement ObjectNode, RefNode, FieldNode, PointsToEdge, FieldEdge, DeferredEdge exactly per §11's signatures.
  • Implement graph construction from an alloc statement: create ObjectNode + PointsToEdge (§8 transfer table row 1).
  • Implement field-sensitive storage per ADR-07: each (AllocId, FieldId) pair gets a distinct FieldNode, never a merged per-object blob.
  • Implement deferred-edge resolution: a DeferredEdge between two RefNodes represents "copies the points-to set of," resolved lazily so the fixpoint solver (Phase 2) doesn't need eager propagation at graph-construction time.
  • Choose and implement the points-to foundation per ADR-03: Andersen-style inclusion-based, field-sensitive; unit test against the Steensgaard-style alternative on a shared fixture to document the precision delta named in ADR-03's rationale.
  • Implement the worked graph-construction example from §8 (a = new Foo(); a.f = p; b = a; return b) as an executable, checked-in fixture with an expected graph shape assertion.
  • Implement a connection-graph dump format (feeds §26's key operational artifact) early, even before the fixpoint solver exists, so Phase 2 can be debugged visually from day one.
  • Add graph-size telemetry (connection_graph_nodes_total, connection_graph_edges_total) against the §4 per-method memory ceiling (≤200 bytes/node, ≤120 bytes/edge).
  • Implement graph freezing after convergence (a later Phase-2 dependency, stubbed here as an API with a no-op guard).
  • Implement the synthetic global-root ObjectNode (one per module) that §8's static-field example and Phase 3's classifier both depend on, so its identity is stable from Phase 1 onward rather than retrofitted in Phase 3.
  • Implement FieldEdge construction from a store statement's target expression, resolving the base object's AllocId through any intervening DeferredEdge chain before creating the (AllocId, FieldId) -> AllocId edge (§11's FieldEdge schema).
  • Implement a graph-size hard ceiling check (feeding T9's DoS mitigation) that aborts construction and emits EscapeError::FixpointDivergence-adjacent telemetry for a single method exceeding a configurable node/edge count, rather than allowing unbounded growth to reach the fixpoint solver in Phase 2.

13.3 Deliverable

A standalone connection-graph crate producing a fully-formed, dumpable graph for any valid Phase-0 IR method, with no fixpoint propagation yet (states are all initialized NoEscape at this phase).

13.4 Acceptance Criteria

  • Connection-graph construction throughput ≥ 6,000,000 IR nodes/sec (§4), measured on the conformance/phase1/ corpus.
  • Per-method graph memory within the §4 ceiling (≤200 B/node, ≤120 B/edge) verified on the 64 KB median-method target.
  • The worked §8 example (a = new Foo(); a.f = p; b = a; return b) produces the exact expected graph shape (1 object node, 3 reference-related edges) bit-for-bit reproducibly (ADR-28).
  • Andersen-vs-Steensgaard precision delta documented quantitatively on ≥3 shared fixtures (node-count and edge-count comparison).

13.5 Conformance Fixtures

  • conformance/phase1/worked_example_choi.ir — the §8 worked graph example.
  • conformance/phase1/field_sensitive_alias.ir — two fields of one object pointing to different objects, must not merge (ADR-07).
  • conformance/phase1/deferred_chain.ir — a chain of 5 copy assignments, testing deferred-edge resolution depth.
  • conformance/phase1/andersen_vs_steensgaard.ir — a fixture with a precision-sensitive aliasing pattern for the ADR-03 comparison.
  • conformance/phase1/global_root_static_store.ir — an object stored into a static field, verifying the synthetic global-root ObjectNode gains an edge from the correct field-store site.
  • conformance/phase1/oversized_field_count.ir — a synthetic method with a pathologically large field count, exercising the new graph-size hard ceiling without letting construction run unbounded.

13.6 Pitfalls

  1. Merging fields into one object-level node "for simplicity" — silently regresses to field-insensitivity and breaks I6 two phases later.
  2. Eagerly resolving deferred edges at construction time instead of lazily — reintroduces the re-analysis-per-callsite cost ADR-05 is designed to avoid.
  3. Using pointer identity instead of content-hash-derived AllocId for node identity — breaks I8 under incremental re-analysis.
  4. Not bounding graph growth on pathological IR (e.g., a method with 100,000 fields) — creates a DoS surface later named in T9.
  5. Constructing the synthetic global-root node lazily on first use instead of eagerly per module — manifestation: two different call paths within the same module resolve to two distinct "global root" object identities; root cause: lazy first-touch construction races across parallel per-method analysis workers; debug method: assert a single global-root AllocId per module at graph-freeze time; signal: node_identity_conflict_total fires specifically on the global-root node rather than a user allocation; recovery: construct the global-root node eagerly at module-load time before any per-method worker starts.
  6. Resolving a FieldEdge's base object through a deferred-edge chain incorrectly when the chain itself hasn't stabilized yet — manifestation: a field edge silently attaches to the wrong (stale) object identity; root cause: field-edge construction ran before the deferred chain it depends on had any resolution attempt at all; debug method: dump the deferred-edge chain state at the moment of field-edge construction and compare against the post-fixpoint resolved chain; signal: a field-edge target that changes between two dumps of an otherwise-unchanged method; recovery: defer field-edge attachment itself until Phase 2's fixpoint has at least one resolution pass over the relevant deferred chain.
  7. Constructing the graph-size hard ceiling check as a post-hoc pass over an already-fully-built graph instead of an incremental check during construction — manifestation: a pathologically large method (T9) still consumes the full memory it would have needed before the ceiling check finally rejects it; root cause: "check after building" doesn't actually bound peak memory, only detect the overrun after the fact; debug method: profile peak memory on conformance/phase1/oversized_field_count.ir and compare against the configured ceiling; signal: peak memory during construction exceeds the ceiling by more than one node/edge's worth; recovery: check the ceiling incrementally as each node/edge is added, aborting construction immediately on the first violation.

13.7 Performance Concerns

  • Edge-arena fragmentation on methods with heavy field access patterns.
  • Deferred-edge chains longer than a handful of hops risk O(n^2) resolution cost if resolution isn't memoized.

13.8 Edge Cases

  • An object with zero fields (no field nodes ever created).
  • A self-referential object (a.f = a) — a one-node cycle in the graph, must not infinite-loop the (as-yet-unbuilt) fixpoint solver's graph traversal helpers.
  • A method with no allocations at all (graph has ref/field nodes only, zero object nodes).
  • A method whose only object is the synthetic global root itself reached via a zero-hop static-field store in the method's very first statement — must not be misidentified as "no allocations" by any code path that checks object-node count naively.
  • A method exactly at the incremental graph-size ceiling boundary (the Nth node/edge that would tip it over) — construction must reject deterministically at exactly that boundary on every run, not fluctuate by one node due to insertion-order sensitivity.

13.9 Failure Analysis

Failure: field-sensitivity silently degrades under a refactor that merges field storage for a "quick win" on graph size. Detection: conformance/phase1/field_sensitive_alias.ir regression test fails immediately (node count drops). Containment: field-sensitivity is pinned as ADR-07 and gated by this fixture in CI, not left to code review alone.

Failure: the graph-size hard ceiling (introduced against T9) is set so conservatively that legitimate large-but-not-pathological methods get rejected as "too big," masking a real analysis gap as a resource-limit false positive. Detection: a rejection-rate dashboard tracking EscapeError occurrences attributable to the ceiling, distinct from genuine malformed-IR rejections. Containment: the ceiling is a tunable configuration value, documented in docs/performance/, revisited against real corpus statistics rather than picked once and frozen.

Failure: the incremental (as opposed to post-hoc) ceiling check itself introduces a per-node/edge overhead large enough to threaten the §4 M2 throughput target, since it must run on every single insertion rather than once per method. Detection: a dedicated micro-benchmark isolating the ceiling check's own cost from graph-construction's baseline cost. Containment: implement the check as a cheap running counter compared against a constant, not a recomputation of graph size from scratch on every insertion.

13.10 Operational Notes

The connection-graph dump tool (tools/) becomes the primary debugging artifact for every subsequent phase — document its output format in docs/runbooks/ now, before the volume of graphs makes retrofitting documentation painful.

Publish connection_graph_nodes_total/connection_graph_edges_total as per-method histograms, not just corpus-wide averages, from this phase onward — an average within the §4 ceiling can still hide a long tail of pathological methods that the Phase 11 perf-hardening pass will need this histogram to find.

Document the incremental ceiling check's own overhead budget (a fraction of a percent of total construction time) as a named, tracked sub-metric, so a future ceiling-check optimization has a concrete target rather than an open-ended "make it faster."

14. Phase 2 — Intraprocedural Transfer Functions and the Fixpoint

14.1 Objectives

Implement the per-statement transfer functions from §8's transfer-function table and the worklist fixpoint solver that applies them to convergence within a single method, enforcing monotonicity (I2) and the iteration bound (I3).

14.2 Detailed Implementation Steps

  • Implement TransferFn (§11) for each IrNode variant: Alloc, Store, Load, Call (stubbed to the conservative I4 default until Phase 4/5 exist), Return, Spawn (stubbed until Phase 9).
  • Implement the worklist scheduler: seed with all ObjectNodes touched by a changed edge, process until no node's state changes (P4's finite-height argument bounds this).
  • Implement the monotonicity guard (I2) as a hard assertion inside every transfer application — any downward transition is a panic-and-report, not a silent clamp.
  • Implement the iteration cap (I3: 3 × lattice height × node count) with an alarm and conservative fallback (classify all remaining unconverged allocations GlobalEscape) if exceeded — this is the safe-default path, mirroring I4's philosophy of the paper's soundness argument (Choi et al. 1999).
  • Reproduce the §8 worked propagation-to-fixpoint example (return b promoting O_a to ArgEscape in 2 iterations) as an executable fixture with an iteration-count assertion.
  • Implement determinism (I13): the worklist processing order must be a pure function of the graph's content hash, not of allocation-time pointer order or hash-map iteration order.
  • Add a non-determinism fuzz target (ADR-24): run the same fixture twice, assert bit-identical output graphs and iteration counts.
  • Wire fixpoint_iterations_total and escape_state_regression_total telemetry (I2, I3) into the observability runtime stood up in Phase 0.
  • Implement the Fixpoint.worklist seeding rule precisely: on TransferFn::apply returning Changed, re-enqueue every node reachable via a FieldEdge or DeferredEdge from the changed node, not just the changed node's immediate neighbors, so a two-hop propagation doesn't require two separate outer passes to notice.
  • Implement EscapeLattice::join's single call site inside TransferFn::apply as the only place any transfer function is permitted to combine two EscapeState values, enforced by a lint/review rule tied to Pitfall 1 below.
  • Implement the connection-graph freeze transition (Phase 1's stubbed no-op API) for real here: once the worklist empties and the iteration cap hasn't tripped, mark the graph immutable and reject any further TransferFn::apply call against it with a hard panic, not a silent no-op.

14.3 Deliverable

A working intraprocedural fixpoint solver producing correct, monotone escape states for any single method with no interprocedural calls (calls treated conservatively per I4 as a stub).

14.4 Acceptance Criteria

  • Zero monotonicity violations (escape_state_regression_total == 0) across the full conformance/phase2/ corpus.
  • Fixpoint convergence within the I3 bound on 100% of corpus fixtures; any fixture exceeding it is flagged, not silently truncated.
  • The §8 worked example converges in exactly 2 iterations, matching the hand-derived trace.
  • Deterministic replay: 1,000 repeated runs of the full corpus produce bit-identical graphs and iteration counts (I13).

14.5 Conformance Fixtures

  • conformance/phase2/worked_fixpoint_choi.ir — the §8 worked 2-iteration example.
  • conformance/phase2/self_recursive_field_cycle.ir — a one-node graph cycle (a.f = a), must converge without infinite loop.
  • conformance/phase2/monotonicity_adversary.ir — a hand-crafted fixture designed to tempt a naive implementation into a downward transition.
  • conformance/phase2/iteration_cap_stress.ir — a pathological fixture approaching the I3 bound, verifying the conservative fallback triggers correctly rather than looping forever.
  • conformance/phase2/two_hop_field_propagation.ir — a store-then-store-through-field chain requiring the two-hop worklist re-enqueue rule to converge in the expected iteration count.
  • conformance/phase2/frozen_graph_write_rejected.ir — a regression test asserting that any TransferFn::apply call issued after the graph-freeze transition panics rather than silently no-oping.

14.6 Pitfalls

  1. Implementing join inline at each call site instead of routing through EscapeLattice::join — invites an inconsistent, non-monotone one-off.
  2. Forgetting that Call transfer functions must default conservative (I4) until interprocedural summaries exist — an unstubbed Call that silently no-ops under-approximates escape.
  3. Using a HashMap-ordered worklist without a deterministic tiebreaker — breaks I13's replay guarantee non-deterministically and rarely, making it hard to reproduce.
  4. Not testing the iteration-cap fallback path — it is easy to write code that "should never" hit the cap and never verify what happens when it does.
  5. Conflating "no more changes this pass" with "globally converged" in a graph with cycles — requires re-checking all touched nodes, not just the last one popped.
  6. Re-enqueuing only a changed node's immediate PointsToEdge neighbors and skipping FieldEdge/DeferredEdge neighbors — manifestation: a two-hop escape promotion (object A's field points to object B, B escapes, A should follow) takes an extra outer pass or, worse, never propagates within the I3 bound; root cause: the worklist seeding rule was implemented against only the most common edge kind; debug method: replay conformance/phase2/two_hop_field_propagation.ir with per-iteration graph dumps and check which edge kind the second hop should have traversed; signal: the fixture's iteration count exceeds its hand-derived expectation by exactly one; recovery: fix the seeding rule to re-enqueue across all three edge kinds uniformly.
  7. Allowing TransferFn::apply to be called after the graph has frozen (e.g., a stray interprocedural call-site revisit from Phase 5/6 code that doesn't check freeze state) — manifestation: a "converged" graph's state changes after the fact with no corresponding telemetry; root cause: freeze is treated as advisory rather than an enforced hard invariant; debug method: conformance/phase2/frozen_graph_write_rejected.ir's panic-on-write assertion; signal: escape_state_regression_total incrementing on a method believed already classified; recovery: enforce freeze as a runtime-checked state, not a convention.
  8. Implementing the monotonicity guard (I2) as a debug_assert! that compiles out in release builds — manifestation: a monotonicity violation ships silently in a release build even though it would have panicked in debug/CI; root cause: treating a soundness-critical check as a performance-sensitive debug aid rather than a load-bearing invariant; debug method: grep the codebase for debug_assert! near any EscapeState transition and confirm none of them guard I2 specifically; signal: a production incident traces to a monotonicity violation that no CI run ever caught; recovery: use a real (always-compiled) assertion for I2 specifically, accepting the small fixed per-application cost as a hard requirement per §6/P1, not an optional debug convenience.

14.7 Performance Concerns

  • Worklist re-insertion churn on graphs with many co-dependent cycles; batch re-insertion to avoid quadratic re-scans.
  • Assertion overhead from I2's monotonicity guard on every transfer application — must be cheap enough to run in release builds, not just debug (soundness checks are not optional).

14.8 Edge Cases

  • A method whose every allocation is dead (never loaded, stored, or returned) — trivially converges to NoEscape in 1 iteration.
  • A diamond-shaped CFG where two paths both write different objects into the same field — join must correctly union effects from both paths.
  • An empty worklist on the very first iteration (no allocations) — must terminate immediately, not loop.
  • A node reachable via both a PointsToEdge and a two-hop DeferredEdge+FieldEdge path simultaneously — the worklist must not enqueue it twice per outer pass in a way that double-applies a transfer function and corrupts the iteration count.
  • The monotonicity guard (I2) itself firing on a legitimate join-to-same-value application (x ⊔ x = x, per §8's join table) — the guard must distinguish "no change, still valid" from "downward transition, invalid," never flag the former as a violation.

14.9 Failure Analysis

Failure: a transfer function accidentally computes meet instead of join, causing states to move downward under specific input shapes. Detection: I2's per-application monotonicity assertion catches it at the exact offending transfer call, with the connection-graph dump (Phase 1 deliverable) attached to the panic report. Containment: the offending method's analysis aborts and falls back to the I3 conservative-GlobalEscape path rather than propagating a corrupted graph downstream.

Failure: the worklist's edge-kind coverage regresses silently (Pitfall 6) after a refactor touches only the PointsToEdge re-enqueue path. Detection: conformance/phase2/two_hop_field_propagation.ir's hand-derived iteration-count assertion fails first, before any soundness-level symptom appears. Containment: this fixture is treated as a canary specifically for worklist-seeding regressions and is never removed from the fast CI tier, even after Phase 5/6 add their own richer interprocedural fixtures.

Failure: the I2 monotonicity guard is compiled out in release builds (Pitfall 8), so a real production monotonicity bug ships undetected until the Phase 11 dynamic oracle (or, worse, a production incident) catches it. Detection: a build-configuration audit confirming I2's assertion macro resolves to a real check in every release profile, run as a Phase 2 CI gate distinct from the general test suite. Containment: treat any build profile where I2 compiles to a no-op as a release-blocking configuration defect, per §6's hard-invariant framing of P1/P4.

14.10 Operational Notes

Ship the fixpoint solver's iteration trace as a first-class artifact from day one (not bolted on later) — §28's soundness oracle and §26's runbooks both depend on being able to replay exactly which transfer application caused which state change.

Emit a per-method worklist_reenqueue_by_edge_kind_total{kind=points_to|field|deferred} counter — an edge kind that never appears in this breakdown across the full corpus is a strong signal that the corresponding transfer-function path is under-tested, not just under-used.

Include the I2 guard's release-build-active status as a build-info field (§29's version-stamping artifact) so any consumer or auditor can confirm, without reading source, that a given release binary actually enforces monotonicity rather than merely having enforced it in the CI build that tested it.

15. Phase 3 — The Escape-State Classifier (NoEscape / ArgEscape / GlobalEscape)

15.1 Objectives

Implement the classifier that reads a converged (currently intraprocedural-only) connection graph and assigns each Allocation its final EscapeState, and establish the classifier's soundness contract ahead of the interprocedural phases that will feed it richer input.

15.2 Detailed Implementation Steps

  • Implement classifier's read of a frozen ConnectionGraph (Phase 1's freezing API) into a HashMap<AllocId, EscapeState> keyed classification result.
  • Implement the "reachable from a global root" rule (§8's static-field example): a synthetic global-root object node exists per module; any object with a path to it is GlobalEscape by construction, not by transfer-function coincidence.
  • Implement the ArgEscape rule: an object reachable from a return statement's pointee set, but not from the global root, is ArgEscape (§8's return b example).
  • Implement the NoEscape default: any object node whose state never left its initial value after fixpoint convergence.
  • Wire the classifier's output into soundness-oracle's input contract (SoundnessCheck.claimed) even though the oracle itself isn't built until Phase 11 — the contract must exist now so later phases don't retrofit it.
  • Implement classifier-level regression tests against every fixture from Phases 0-2, confirming the classification matches the hand-derived expectation in each fixture's accompanying comment.
  • Add the classifier's own telemetry: classification_no_escape_total, classification_arg_escape_total, classification_global_escape_total, feeding the §4 payoff metric (fraction NoEscape).
  • Implement the classifier's reachability walk as a single generic graph traversal parameterized by target node (global-root vs. return-pointee set), rather than two independently written traversal functions, so a bug fix to reachability logic can't accidentally apply to only one rule.
  • Implement classification provenance recording: for every AllocId, retain the specific edge path that justified its final EscapeState, feeding both P12's replayability requirement and the soundness-oracle's future SoundnessCheck contract.
  • Implement provenance serialization as self-contained graph-shape data (node kinds and edge sequence, not live node handles), so a provenance record remains replayable after the originating ConnectionGraph has been dropped from memory (directly pre-empting the Failure Analysis scenario named below).

15.3 Deliverable

A classifier crate that turns any converged connection graph into a complete AllocId -> EscapeState map, matching Choi et al. 1999's three-state classification exactly, with interprocedural calls still conservatively over-approximated per I4 until Phase 5.

15.4 Acceptance Criteria

  • 100% of Phase 0-2 conformance fixtures classify exactly as their hand-derived comments specify.
  • Fraction of allocations classified NoEscape on the intraprocedural-only corpus ≥ 15% (a conservative floor, expected to rise to the §4 target of ≥35% once Phase 5's interprocedural summaries remove spurious call-conservatism).
  • Zero cases where an object reachable from the global root is classified anything but GlobalEscape (unit-tested exhaustively against the graph-reachability definition, not sampled).
  • Classification throughput adds no more than 5% overhead over Phase 2's raw fixpoint solve time on the full corpus.

15.5 Conformance Fixtures

  • conformance/phase3/global_static_field.ir — object stored into a static field, must classify GlobalEscape.
  • conformance/phase3/return_only.ir — object returned and nothing else, must classify ArgEscape.
  • conformance/phase3/dead_allocation.ir — object allocated and never used, must classify NoEscape.
  • conformance/phase3/mixed_module.ir — one method exhibiting all three states across different allocations, verifying the classifier doesn't cross-contaminate results between allocations in the same method.
  • conformance/phase3/provenance_replay.ir — a multi-hop classification whose recorded provenance edge path, when replayed independently, reconstructs the exact same EscapeState verdict.
  • conformance/phase3/shared_traversal_regression.ir — a fixture exercising both the global-root and return-pointee reachability rules on the same graph, guarding against the two rules silently diverging after a shared-traversal refactor.

15.6 Pitfalls

  1. Implementing global-root reachability as a special-cased string match on field names ("is this field named 'static'?") instead of a real graph-reachability walk from a synthetic root node — brittle and unsound on renamed or generated fields.
  2. Classifying based on the object's last observed state during fixpoint iteration instead of its converged (post-fixpoint) state — can read a stale intermediate value.
  3. Treating "not GlobalEscape and not ArgEscape" as an implicit default without an explicit NoEscape derivation step — silently masks a classifier bug as a false NoEscape, the worst possible failure direction (I1).
  4. Forgetting that Call transfer functions are still conservative stubs at this phase — the classifier must not be benchmarked against the full §4 payoff target yet, only the intraprocedural-only floor.
  5. Sharing a single traversal implementation between the global-root and return-pointee rules but parameterizing it incorrectly (e.g., accidentally letting the return-pointee walk also terminate at the global root without promoting to GlobalEscape) — manifestation: an object reachable from both a return and the global root classifies ArgEscape instead of GlobalEscape; root cause: the generic traversal's "stop and classify" callback doesn't distinguish which target it hit; debug method: conformance/phase3/shared_traversal_regression.ir's explicit both-reachable case; signal: classification_global_escape_total under-counts relative to the number of known global-root-reachable fixtures; recovery: make the traversal callback return which target it hit, not just that it hit one, and have the classifier apply join semantics on the result.
  6. Recording classification provenance lazily (only on demand, e.g., when a debugger attaches) instead of unconditionally at classification time — manifestation: a soundness-oracle finding has no provenance trail to investigate because provenance was never captured for that run; root cause: provenance recording was treated as a debug-only feature rather than a first-class classifier output; debug method: attempt to reconstruct any archived classification's provenance and observe the gap; signal: docs/runbooks/soundness-violation-response.md's triage steps fail at the "dump provenance" step; recovery: make provenance recording unconditional and part of the classifier's core output contract (P12).

15.7 Performance Concerns

  • Classification is a single linear pass over object nodes post-fixpoint; the main risk is redundant graph traversal if reachability isn't memoized during the Phase 2 solve.

15.8 Edge Cases

  • An object with two return sites reaching it on different paths, one via a plain return and one after being stored to a global — must classify GlobalEscape (join wins), not ArgEscape.
  • A module with no global roots at all (a leaf library with no static state) — global-root reachability check must correctly return empty, not error.
  • An allocation site inside an unreachable (dead) basic block — still must classify soundly (typically NoEscape, since it can never execute, but must not crash the classifier).
  • An object reachable from both the global root and a return statement on different paths within the same method — must classify GlobalEscape (the join-toward-top result), never ArgEscape, regardless of which reachability rule's traversal happens to run first.
  • A classification provenance record for an object whose justifying path includes a node that was later merged or renumbered by an incremental re-analysis — the record's self-contained graph-shape encoding must remain valid even though the live graph's identifiers have since changed.

15.9 Failure Analysis

Failure: the classifier's NoEscape "default" path masks an unhandled graph shape as falsely non-escaping. Detection: the differential/dynamic soundness oracle (Phase 11) is the ultimate backstop, but Phase 3's own exhaustive unit tests against the reachability definition are the first line of defense — any new graph shape added in later phases must get an explicit classifier test, never an assumed default. Containment: I1 makes this a release-blocking class of bug, not a tunable false-positive rate.

Failure: classification provenance is recorded but references connection-graph node IDs that don't survive past the graph's freeze-and-drop lifecycle, making the provenance trail unreplayable exactly when an incident investigation needs it. Detection: the provenance-replay conformance fixture (conformance/phase3/provenance_replay.ir), run specifically against a graph that has already been dropped from memory and reloaded from its dump. Containment: provenance records must be self-contained (embedding enough graph-shape detail to replay without the live graph object), not bare node-ID references into a structure that may no longer exist.

15.10 Operational Notes

Publish the three classification counters (classification_*_total) to the same dashboard used for the §4 payoff metric from this phase onward, so the payoff trend is visible before interprocedural analysis even exists — this makes Phase 5's improvement measurable against a real baseline rather than an assumed one.

Retain classification provenance for at least one full release cycle after the corresponding IR was analyzed, not just until the next incremental re-analysis evicts it from the summary cache — an incident reported days after a release still needs to be replayable against the exact classification that shipped.

16. Phase 4 — The Call Graph and Virtual-Dispatch Handling

16.1 Objectives

Implement cfg-callgraph and callgraph-dispatch: intraprocedural CFG construction plus a whole-module call graph with CHA seeding, RTA refinement, and SCC decomposition, ready for Phase 5's bottom-up interprocedural traversal (ADR-10, ADR-11).

16.2 Detailed Implementation Steps

  • Implement intraprocedural CFG construction (basic blocks, edges, dominance) as a prerequisite the connection-graph builder already implicitly assumed in Phases 1-3; formalize it as its own crate now for clarity of ownership.
  • Implement CHA-based call-graph seeding: every virtual call site's target set is every method overriding the declared receiver type (ADR-10 first stage).
  • Implement RTA refinement: prune CHA's target set to only types actually instantiated somewhere in the analyzed module set (ADR-10 second stage), citing Soot/WALA's framework precedent (§5 reference implementations).
  • Implement SCC decomposition of the call graph (Tarjan's algorithm) — required by ADR-05/P3 for Phase 5's bottom-up ordering.
  • Implement the CallSite.callee_targets population per §11, with len() > 1 signaling virtual dispatch per the schema's own annotation.
  • Implement the join-over-all-resolvable-targets rule (I10, P8, ADR-11): a virtual call site's effect on its arguments is the join of every resolvable target's individual effect, computed once summaries exist in Phase 5 — Phase 4 only needs to correctly enumerate the target set.
  • Implement the fully-unresolved case (native/external symbol, zero resolvable targets) routing to I4's conservative GlobalEscape default.
  • Add call-graph depth handling for the §4 target (≥500 levels) via iterative, not recursive, SCC traversal — a naive recursive DFS blows the stack on deep call chains.
  • Add virtual_dispatch_join_total and native_callsite_conservative_total telemetry (I10, I4).
  • Implement Tarjan's algorithm iteratively (explicit stack, not call-stack recursion) against CallGraph.nodes/edges, populating CallGraph.sccs in a deterministic member order derived from MethodId content hash, not discovery order, to satisfy I13 up front rather than retrofitting determinism later.
  • Implement the CHA/RTA target-set cache keyed by receiver static type, shared across all call sites with the same declared receiver, per the Performance Concerns note below — build the cache structure now so Phase 5/6's higher call-site volume doesn't force a rework.
  • Implement dynamic_dispatch_opaque_total telemetry (T5) for any IR construct the frontend lowers to an "opaque call" node (reflection-like or dynamic-load constructs), distinguishing it from the plain native-external-symbol case already covered by native_callsite_conservative_total.

16.3 Deliverable

A cfg-callgraph + callgraph-dispatch crate pair producing a complete, SCC-decomposed call graph for a module, with CHA/RTA-resolved virtual dispatch targets, ready to drive Phase 5's bottom-up summary traversal.

16.4 Acceptance Criteria

  • Call-graph construction handles ≥500 levels of call depth without stack overflow (§4), verified on a synthetically generated deep-chain fixture.
  • RTA refinement removes ≥60% of CHA's spurious virtual-dispatch targets on the conformance/phase4/ OO-heavy corpus (a measured, named regression floor, not "works").
  • SCC decomposition is deterministic and reproducible bit-for-bit across runs (ADR-28), verified by hash-comparing the SCC partition across 100 repeated runs.
  • Zero call sites left with an empty, unclassified target set — every call site is either resolved (≥1 target), correctly identified as fully external (I4 path), or flagged as a hard analysis error, never silently dropped.

16.5 Conformance Fixtures

  • conformance/phase4/deep_call_chain_500.ir — a synthetic 500-level call chain, stack-safety regression test.
  • conformance/phase4/virtual_dispatch_cha_rta.ir — a class hierarchy where CHA over-approximates and RTA correctly prunes.
  • conformance/phase4/mutual_recursion_scc.ir — two methods calling each other, testing SCC decomposition.
  • conformance/phase4/native_external_call.ir — a call to a symbol with no resolvable body, testing the I4 conservative path.
  • conformance/phase4/opaque_dynamic_dispatch.ir — a reflection-like construct lowered to an opaque-call IR node, verifying it routes through T5's tracked telemetry distinctly from a plain native-external call.
  • conformance/phase4/scc_determinism_stress.ir — a call graph with several same-size SCCs, verifying member ordering is stable and content-hash-derived across 100 repeated runs, not just "usually stable."

16.6 Pitfalls

  1. Implementing SCC decomposition recursively — works on small test fixtures, then stack-overflows in production on a 500-level deep real call graph.
  2. Treating RTA as optional "nice to have" and shipping CHA-only — massively over-approximates escape on any realistically polymorphic codebase, tanking the §4 payoff metric.
  3. Silently dropping unresolvable call sites instead of routing them through I4's explicit conservative path — creates a soundness gap disguised as a missing feature.
  4. Non-deterministic SCC member ordering within an SCC — breaks I13's replay guarantee even though the graph itself is otherwise correct.
  5. Deriving SCC member order from Tarjan's natural discovery order (a function of edge iteration order in whatever container holds them) instead of re-sorting by MethodId content hash after decomposition — manifestation: conformance/phase4/scc_determinism_stress.ir passes on one machine/build but fails on another with a different HashMap iterator implementation; root cause: discovery order is influenced by non-guaranteed container iteration order; debug method: run the same fixture under two different hasher seeds and diff SCC member order; signal: SCC partition hash differs across otherwise-identical runs; recovery: sort each SCC's members by content hash as a final deterministic pass after Tarjan's algorithm produces the raw partition.
  6. Confusing an opaque/dynamic-dispatch call site (T5) with a plain unresolvable-native call site (I4) and routing both through identical telemetry — manifestation: an operator can't distinguish "we correctly modeled an unknown external symbol" from "we may have a whole class of dynamic-dispatch construct our IR lowering doesn't even see"; root cause: both paths default-conservatively to the same EscapeState, so it's tempting to also merge their telemetry; debug method: audit the IR-lowering coverage against known dynamic-dispatch opcodes named in T5; signal: dynamic_dispatch_opaque_total stays at zero even on a corpus known to use reflection-like constructs; recovery: keep the two telemetry counters and IR node kinds distinct even though their conservative escape treatment is identical.
  7. Caching a CHA target-set query result keyed only by the receiver's static type without also keying by module/compilation-unit boundary — manifestation: a stale target set from one compilation unit leaks into another unit's analysis after an incremental rebuild changes only one unit's class hierarchy; root cause: the cache key omits the scope the type hierarchy was queried within; debug method: rebuild only one of two modules sharing a receiver type and diff resolved target sets before/after; signal: a target set doesn't reflect a just-added override in the rebuilt module; recovery: scope the CHA cache key by compilation unit (or invalidate it wholesale on any hierarchy-affecting rebuild) rather than by type alone.

16.7 Performance Concerns

  • CHA target-set computation is a type-hierarchy query per call site; cache hierarchy queries across call sites sharing a receiver type.
  • RTA's "instantiated types" set must be computed once per module, not recomputed per call site.

16.8 Edge Cases

  • A call site whose static receiver type has zero declared subtypes (monomorphic in practice) — CHA and RTA should agree trivially, a good regression check for both paths being correctly wired.
  • A class hierarchy with diamond inheritance — target-set deduplication must not double-count a method reachable via two inheritance paths.
  • A call graph with a self-loop SCC of size 1 (direct self-recursion) — must be handled as the trivial SCC case, not a special edge case requiring separate code.
  • Two same-size SCCs whose members' content hashes happen to sort into an order that looks suspiciously like discovery order — a determinism regression test must not accidentally pass "by coincidence" here; assert against a hash-derived expectation, not merely "did it crash."
  • A CHA target-set cache entry queried before and after an incremental rebuild that changes an unrelated compilation unit's class hierarchy — the cached entry for the untouched unit must remain valid (cache correctness), while the rebuilt unit's entry must invalidate correctly (cache freshness); both properties need their own fixture.

16.9 Failure Analysis

Failure: RTA's instantiated-types set is computed from an incomplete module view (e.g., a library compiled without its call sites), causing under-approximation of the target set. Detection: a call site with a runtime-observed target not in the statically resolved set, caught by the differential soundness oracle (Phase 11) against a closed-world benchmark. Containment: for genuinely open-world/dynamically-loaded scenarios, the target-set resolution must fall back to the I4 conservative path rather than trust a possibly-incomplete RTA result — this is a deployment-model constraint documented in docs/threat-model/.

Failure: the IR frontend fails to lower a reflection-like or dynamic-load construct to an explicit opaque-call node at all, so it simply never appears in the call graph — a silent coverage gap rather than a conservatively-handled known unknown (T5's named residual risk). Detection: an absence-of-coverage audit comparing the frontend's IR-lowering rules against a maintained list of known dynamic-dispatch language constructs, run as a Phase 4 CI check, not deferred to Phase 11. Containment: any newly discovered unlowered construct is treated as a P0 IR-frontend defect (per T5's escalation policy), and the frontend contract (§1/§5) is amended to require explicit lowering for it going forward.

Failure: the CHA target-set cache's compilation-unit scoping (Pitfall 7's fix) is implemented but the invalidation trigger itself is missed on a specific incremental-rebuild code path (e.g., a rename that doesn't touch the hierarchy file directly). Detection: a cache-freshness fixture pairing an incremental rebuild scenario with a direct assertion on resolved target sets before and after. Containment: prefer coarse-grained invalidation (evict the whole cache on any hierarchy-affecting change signal) over fine-grained invalidation whose triggers can be incompletely enumerated.

16.10 Operational Notes

Expose CHA-target-count vs RTA-target-count as a ratio metric per module — a ratio near 1.0 signals RTA isn't finding real opportunities to prune (either a genuinely monomorphic codebase or a bug in RTA's instantiated-type tracking).

Track SCC-partition hash stability across consecutive releases on a fixed reference corpus as its own dashboard signal — an unexpected change in SCC partitioning on unchanged source IR is a red flag for a Tarjan-implementation or content-hash regression well before it manifests as a Phase 5 summary-convergence problem.

Report CHA target-set cache hit/invalidation rates alongside the summary-cache metrics (§17.10) on the same operational dashboard — both are incremental-rebuild-correctness-sensitive caches, and an operator investigating one should be prompted to check the other.

17. Phase 5 — Interprocedural Method Summaries (Bottom-Up)

17.1 Objectives

Implement summary-engine: bottom-up traversal of the Phase-4 call graph's SCCs, computing a sound MethodSummary per method (Whaley & Rinard 1999, ADR-05, P3), replacing Phase 2-3's conservative Call stub with real interprocedural precision.

17.2 Detailed Implementation Steps

  • Implement reverse-topological SCC ordering over the Phase 4 call graph: process callees before callers (P3).
  • Implement within-SCC local fixpoint iteration for mutual recursion: iterate summary computation for all SCC members using each other's best-known partial summary until stable (§8 interprocedural model step 3).
  • Implement MethodSummary's param_effects/return_effect per §11: an EscapeTransfer abstraction mapping "what escape state does this parameter/return reach, as a function of the state of its own transitively-reachable objects at call boundary."
  • Implement summary computation from a method's own converged (Phase 2) connection graph: any object reachable from a formal parameter that is itself later found ArgEscape/GlobalEscape within the method contributes to that parameter's summary effect.
  • Implement summary soundness self-check (I5): after computing a summary, spot-verify it against a direct re-analysis sample to catch summary-computation bugs early (this is a development/CI check, not a production per-run cost).
  • Wire summary application at call sites into the fixpoint solver's Call transfer function, replacing the Phase 2 conservative stub — this is the point where Phase 2's stubbed conservatism starts becoming real precision.
  • Implement summary-cache (ADR-15, I9): content-hash-keyed persistence of computed summaries, so unchanged methods never get re-summarized on incremental runs.
  • Add summary_cache_hit_ratio and summary_soundness_check_total telemetry (§4 target ≥95% hit rate on incremental recompiles).
  • Implement EscapeTransfer (§11's MethodSummary.param_effects element type) as a small closed table keyed by "reaches return," "reaches a GlobalEscape field," "reaches another parameter" — not an open-ended function type — so summary serialization (ADR-15) stays within the §4 M8 512-byte ceiling.
  • Implement the SCC-local fixpoint's own iteration cap (distinct from I3's intraprocedural cap) sized to SCC member count, with the same conservative-fallback philosophy: an SCC that doesn't converge within the cap gets every member's summary conservatively widened to GlobalEscape-on-all-parameters rather than looping.
  • Implement summary-application call-counting (summary_application_total{method}) to directly validate ADR-05's linear-in-method-count claim against the naive re-analysis alternative quantified in §34 item 4.

17.3 Deliverable

A summary-engine + summary-cache crate pair providing real interprocedural escape precision, replacing the Phase 0-3 conservative Call-stub baseline, with persistent cross-run summary caching.

17.4 Acceptance Criteria

  • The §8 worked two-method example (store/run) classifies o as NoEscape, not GlobalEscape — the direct, named regression test for interprocedural precision actually working.
  • Fraction of allocations classified NoEscape rises from Phase 3's ≥15% intraprocedural-only floor to ≥35% on the full conformance/phase5/ corpus (the §4 payoff target, now meaningfully measurable).
  • Summary-cache hit rate ≥95% on a simulated incremental-recompile scenario (one method changed, rest unchanged) — §4's target, first measured here.
  • Zero summary-soundness self-check failures (I5) across the full corpus.
  • Mutual-recursion SCCs converge within a bounded number of local iterations (documented and asserted, not open-ended).

17.5 Conformance Fixtures

  • conformance/phase5/worked_two_method_choi.ir — the §8 store/run worked example.
  • conformance/phase5/mutual_recursion_summary.ir — two mutually recursive methods, testing SCC-local fixpoint summary convergence.
  • conformance/phase5/deep_summary_chain.ir — a 10-method call chain, verifying summaries compose without precision loss across multiple hops.
  • conformance/phase5/incremental_cache_hit.ir plus its one-method-changed variant, testing the ≥95% cache-hit target directly.
  • conformance/phase5/scc_iteration_cap_stress.ir — a large mutually recursive SCC engineered to approach the SCC-local iteration cap, verifying the conservative-widening fallback triggers rather than looping indefinitely.
  • conformance/phase5/summary_size_ceiling.ir — a method with the maximum realistic parameter/field-sensitivity combination, verifying its serialized MethodSummary stays within the M8 512-byte ceiling.

17.6 Pitfalls

  1. Re-analyzing callees from scratch at every call site "to be safe" — silently reintroduces the exact non-scaling behavior ADR-05 rejects, defeating the entire phase's purpose.
  2. Computing a summary once and never invalidating it when the callee's IR changes — a stale-summary correctness bug distinct from but related to I9's cache-key requirement.
  3. Getting mutual-recursion SCC-local fixpoint wrong by processing SCC members in an arbitrary, non-iterated order (treating it like a simple bottom-up case) — produces an under-converged, unsound summary for at least one member.
  4. Skipping the summary soundness self-check (I5) in CI because "it's expensive" — this is precisely the check that catches summary-engine regressions before they reach the release-gating soundness oracle in Phase 11.
  5. Modeling EscapeTransfer as an open-ended closure/function pointer instead of a small closed table — manifestation: MethodSummary serialization blows past the M8 512-byte ceiling on any method with more than a handful of parameters; root cause: an open representation captures more state than the three actually-needed transfer categories require; debug method: inspect a serialized summary's byte size against conformance/phase5/summary_size_ceiling.ir's expectation; signal: summary_cache memory usage grows faster than method count, threatening the §4 2,000,000-summary capacity target; recovery: constrain EscapeTransfer to the closed table and re-derive any summary that was computed under the open representation.
  6. Sizing the SCC-local iteration cap identically to the whole-method I3 cap regardless of SCC member count — manifestation: a large mutually-recursive SCC (10+ methods) never converges within a cap sized for a 2-method SCC; root cause: the cap was copy-pasted from I3 without scaling by SCC size; debug method: conformance/phase5/scc_iteration_cap_stress.ir's explicit large-SCC fixture; signal: SCC-local fixpoint telemetry shows the cap tripping on realistically-sized (not pathological) mutual-recursion clusters; recovery: scale the SCC-local cap by member count, matching I3's own node-count-proportional design philosophy.
  7. Computing summary_application_total only for cache-miss (freshly-computed) summary uses, undercounting cache-hit applications — manifestation: the metric appears to show far fewer summary applications than the actual number of call sites processed; root cause: the counter was wired into the summary-computation code path rather than the summary-application code path; debug method: cross-check summary_application_total against a direct count of CallSite records processed in a full corpus run; signal: the two counts diverge by roughly the cache-hit ratio's complement; recovery: move the counter increment to the single shared call-site-substitution entry point (used by both cache-hit and cache-miss paths), not the cache-miss branch alone.

17.7 Performance Concerns

  • Summary application at a call site with many actual arguments risks O(params × transitively-reachable-objects) cost per call; bound with the field-sensitivity granularity already established in Phase 1.
  • Summary-cache lookup must be cheaper than re-computing a trivial summary, or the cache becomes a net loss on small methods.

17.8 Edge Cases

  • A method with zero parameters and no return value (side-effect-only, e.g., a void logger call) — summary is trivially empty, must not error.
  • An SCC of size >2 (three or more mutually recursive methods) — local fixpoint must handle arbitrary SCC size, not just the pairwise case.
  • A method summary requested for a method not present in the call graph at all (dead code) — must return a documented "unreachable, unanalyzed" result, not crash.
  • An EscapeTransfer table entry that would need to represent "reaches return AND reaches a GlobalEscape field" simultaneously — the closed table must represent conjunctions of its categories, not force a lossy single-category choice.
  • A summary_application_total counter queried mid-analysis (before a compilation unit finishes) — the metric must be safe to read as a running total from another thread/process (observability-runtime's tracing subscriber) without requiring analysis to pause or complete first.

17.9 Failure Analysis

Failure: an SCC-local fixpoint declares convergence one iteration too early, under-approximating one member's summary. Detection: the summary soundness self-check (I5) sampling against direct re-analysis; if that misses it, the Phase 11 differential oracle against the labeled corpus is the backstop. Containment: I5-failing summaries are recomputed from scratch with a widened iteration budget before being cached, never silently accepted.

Failure: summary_application_total reveals that a "cached" summary is actually being recomputed on every call site rather than looked up once and reused, silently reintroducing an ADR-05-violating cost profile without any correctness symptom. Detection: comparing summary_application_total growth rate against summary_cache_hit_ratio — a high application count with a high hit ratio should mean cheap lookups, not repeated recomputation. Containment: profile the summary-cache lookup path directly whenever summary_application_total grows faster than expected relative to method count, per the §34 item 4 linear-cost model this phase exists to realize.

Failure: summary_application_total undercounts cache-hit applications (Pitfall 7), making the metric look artificially healthy (low count, seemingly cheap) while masking the true call-site volume. Detection: the direct cross-check against CallSite record count named in Pitfall 7's debug method, run as a standing CI assertion rather than an ad hoc investigation technique. Containment: treat any divergence between the two counts as a metrics-instrumentation defect requiring a fix before the metric is trusted for any capacity-planning decision.

17.10 Operational Notes

Track summary-cache size against the §4 ceiling (2,000,000 summaries resident) and alert before eviction pressure causes hit-rate degradation below the 95% target.

Report summary_application_total alongside the cache-hit ratio on the same dashboard — the two metrics together are the direct, measurable evidence for or against ADR-05's core scaling claim, not just an internal implementation detail.

Validate summary_application_total's instrumentation point against the Pitfall 7 cross-check as part of every release's metrics-integrity checklist, not just at the metric's initial rollout — a future refactor of the call-site substitution code path is exactly the kind of change that could silently reintroduce the undercounting bug.

18. Phase 6 — Mapping Actuals to Formals at Call Sites

18.1 Objectives

Implement precise actual-argument-to-formal-parameter binding at call sites, so Phase 5's summaries are applied with the correct substitution rather than a coarse worst-case join, and lay the groundwork for the optional 1-CFA context-sensitivity extension (ADR-06).

18.2 Detailed Implementation Steps

  • Implement the actual-to-formal substitution step named in §8's interprocedural model (step 5): for each CallSite.actuals[i], substitute into MethodSummary.param_effects[i]'s EscapeTransfer to compute the concrete effect on that specific actual's points-to set.
  • Implement multi-target (virtual dispatch) substitution: when callee_targets.len() > 1, apply each target's substituted effect and join the results (I10), not just the first target found.
  • Implement return-value substitution: MethodSummary.return_effect substituted against the call site's assignment target, feeding the caller's own fixpoint state.
  • Implement the Context structure (§11) as a currently-unused (context-insensitive baseline, ADR-06) but fully-typed placeholder, so the optional 1-CFA extension in a later maintenance cycle doesn't require a schema change.
  • Add regression coverage for the case where an actual argument aliases another actual at the same call site (f(x, x)) — substitution must not double-count or under-count the shared object's effect.
  • Add regression coverage for a call site passing a field-projection (f(obj.field)) as an actual, exercising the field-sensitive substitution path (ADR-07 interacting with Phase 6).
  • Wire substitution results directly into the Phase 2 fixpoint solver's Call transfer function, completing the replacement of the original conservative stub.
  • Implement an explicit alias-detection pre-pass over CallSite.actuals (reusing Phase 1's connection-graph points-to sets) that partitions actuals into alias-equivalence classes before substitution runs, rather than checking pairwise aliasing inline inside the substitution loop.
  • Implement field-projection substitution (f(obj.field)) by resolving the projected FieldNode through Phase 1's field-sensitive storage first, then substituting the summary's effect against that specific field node rather than the whole obj — preserving ADR-07's granularity exactly at this interprocedural seam.
  • Implement a substitution-level regression harness that re-runs every Phase 4/5 fixture through the new substitution layer and diffs classification output against the pre-Phase-6 (summary-join-only) baseline, quantifying the precision delta named in the Acceptance Criteria.
  • Implement the Context type's threading as literal, tested no-op plumbing: every substitution call site accepts and forwards an empty Context value even though nothing yet branches on it, so the eventual 1-CFA extension only needs to populate the value, never add a new parameter.

18.3 Deliverable

A precise actual-to-formal call-site binding layer completing the interprocedural pipeline: Phase 4's call graph, Phase 5's summaries, and Phase 6's substitution together give the full interprocedural classification precision targeted by §4.

18.4 Acceptance Criteria

  • The aliased-actuals fixture (f(x, x)) classifies identically to two hand-verified separate calls with distinct arguments carrying the same object — a direct soundness-equivalence check.
  • Field-projection actual-argument fixtures classify with the same precision as an equivalent fixture using a temporary local variable instead of an inline field projection (i.e., substitution doesn't lose precision relative to a manually-hoisted equivalent).
  • Fraction of allocations classified NoEscape improves measurably (documented percentage-point delta, not just "better") over the Phase 5 baseline on the conformance/phase6/ corpus, attributable specifically to precise substitution rather than summary coverage growth.
  • Virtual-dispatch call sites with multiple targets produce a join result no less precise than the least precise individual target's substituted effect (a monotonicity sanity bound on I10's join).

18.5 Conformance Fixtures

  • conformance/phase6/aliased_actuals.ir — f(x, x) pattern.
  • conformance/phase6/field_projection_actual.ir — f(obj.field) pattern.
  • conformance/phase6/virtual_multi_target_substitution.ir — a virtual call with 3 resolvable targets, each with a different summary shape.
  • conformance/phase6/return_value_substitution.ir — a call site assigning a callee's return into a variable later itself returned by the caller (transitive ArgEscape chaining).
  • conformance/phase6/alias_equivalence_class_partition.ir — three actuals at one call site, two of which alias each other and one which doesn't, verifying the pre-pass partitions them correctly before substitution runs.
  • conformance/phase6/pre_post_substitution_diff.ir — a fixture specifically designed to show a measurable classification improvement between the pre-Phase-6 join-only baseline and post-Phase-6 substitution.

18.6 Pitfalls

  1. Substituting actuals positionally without checking for aliasing between actual arguments — silently produces an unsound under-approximation when two parameters alias the same object.
  2. Applying only the first resolvable virtual-dispatch target's substituted effect instead of joining all of them — a direct I10 violation introduced at the substitution layer rather than the call-graph layer.
  3. Losing field-sensitivity at the substitution boundary by "flattening" a field-projection actual into its base object — regresses ADR-07's precision exactly at the interprocedural seam where it matters most.
  4. Building the Context type but never actually threading it through substitution even as a no-op — makes the eventual 1-CFA extension a schema-breaking change instead of an additive one.
  5. Running the alias-detection pre-pass against the actuals' syntactic identity (same variable name/SSA value) instead of their connection-graph points-to sets — manifestation: two differently-named actuals that provably alias the same object via a deferred-edge chain get treated as independent, reintroducing Pitfall 1's under-counting risk through a different door; root cause: alias detection was implemented as a cheap syntactic check rather than a graph-based one; debug method: construct a fixture where aliasing is only visible through the connection graph, not variable names, and check partition output; signal: the alias-equivalence-class fixture passes for the syntactic case but a graph-only-aliasing variant fails; recovery: route alias detection exclusively through Phase 1's points-to sets, never through surface syntax.
  6. Substituting a field-projection actual against the summary's whole-parameter effect instead of resolving the specific FieldNode first — manifestation: f(obj.field) classifies identically to f(obj), losing field-sensitivity exactly where ADR-07 requires it; root cause: the substitution code path for field-projection actuals falls through to the generic object-substitution code without a field-resolution step; debug method: compare classification of conformance/phase6/field_projection_actual.ir against an equivalent fixture using a hoisted temporary; signal: the two fixtures classify differently when they should classify identically; recovery: add the explicit FieldNode-resolution step before substitution for any actual that is itself a field projection.

18.7 Performance Concerns

  • Aliasing checks between actuals at high-arity call sites are O(n^2) in argument count naively; bound arity in practice (real call sites rarely exceed single-digit arity) and document the theoretical ceiling.
  • Substitution at virtual-dispatch call sites multiplies cost by target-set size; RTA's pruning from Phase 4 directly bounds this.

18.8 Edge Cases

  • A call site with zero actual arguments (parameterless method) — substitution step trivially no-ops.
  • An actual argument that is itself the result of a not-yet-summarized SCC-mate (mutual recursion interacting with substitution) — must use the SCC-local partial summary from Phase 5, not block.
  • A virtual call site where RTA resolved exactly one target (monomorphic in practice) but the static type still declares multiple overriders — substitution must use the RTA-pruned set, not the CHA superset.
  • An actual argument that aliases another actual only transitively, through a two-hop deferred-edge chain rather than a direct points-to edge — the alias-equivalence-class partition must still group them correctly, not just handle the one-hop case.
  • A call site substitution invoked with a non-empty Context value from a future 1-CFA-enabled build alongside call sites still using the empty context-insensitive default within the same compilation unit — both must produce a well-typed EscapeTransfer application without a branch on "which mode are we in" scattered through the substitution logic.

18.9 Failure Analysis

Failure: aliased-actuals under-counting causes an object to be classified NoEscape when it actually escapes via a second, aliased parameter binding. Detection: conformance/phase6/aliased_actuals.ir's direct equivalence check against the hand-verified two-separate-calls baseline; the Phase 11 dynamic soundness oracle is the final backstop for anything this targeted fixture misses. Containment: this is an I1-class defect (false NoEscape) and blocks release per I11 regardless of how narrow the triggering pattern is.

Failure: field-projection substitution resolves the wrong FieldNode when the projected field itself has been the target of a prior deferred-edge rewrite within the same call site's evaluation order. Detection: conformance/phase6/field_projection_actual.ir extended with a preceding field-rewriting statement, comparing against a manually-traced expected FieldNode identity. Containment: substitution must resolve field-projection actuals against the connection graph's state at the call site's program point, never against a stale or globally-latest field-node snapshot.

18.10 Operational Notes

Document the aliased-actuals and field-projection substitution rules explicitly in docs/adr/ alongside ADR-07, since these are the most common source of subtle precision-vs-soundness regressions reported against real compiler frontends.

Publish the pre/post-substitution classification delta (from the conformance/phase6/pre_post_substitution_diff.ir methodology) as a standing regression-tracked metric, not a one-time Phase-6 launch number — a future refactor that accidentally regresses substitution precision back toward the join-only baseline should be visible on this dashboard immediately.

19. Phase 7 — The Scalar-Replacement Candidate Emitter

19.1 Objectives

Implement the first optimizer-facts consumer-facing output: ScalarReplaceCandidate emission, gated by I6's field-alias-free soundness requirement, directly tying into the Kotzmann & Mössenböck 2007 scalar-replacement technique and its Kotzmann & Mössenböck 2005 deoptimization tie-in.

19.2 Detailed Implementation Steps

  • Implement the ScalarReplaceCandidate emission rule (§8 optimization-consumer mapping): every allocation classified NoEscape by Phase 3-6's pipeline is a candidate, pending the field-alias-free check.
  • Implement the field-alias-free check (I6): using Phase 1's field-sensitive connection graph, verify no two distinct FieldNodes of the candidate object are ever aliased to the same underlying storage in a way that per-field scalar replacement would violate (e.g., via an unsafe reinterpret or an escaping reference to the field itself, not just the object).
  • Implement rejection accounting (scalar_replace_rejected_total, I6) for candidates that fail the field-alias-free check — reject, do not silently downgrade to a weaker guarantee.
  • Implement the direct tie to Deoptimization-Engine (246): emit, alongside each ScalarReplaceCandidate, the field-layout metadata 246's rematerialization step needs to reconstruct a heap object from scalarized fields on deopt (Kotzmann & Mössenböck 2005's central contribution — this project computes the facts, 246 consumes them at deopt time).
  • Add the conformance/phase7/ corpus specifically targeting field-alias adversarial cases: a reference to &obj.field taken and passed elsewhere, which must reject scalar replacement of that field even though obj itself is NoEscape.
  • Wire OptimizationFacts.scalar population and version it per ADR-17's independent-interface-versioning decision.
  • Implement the field-alias-free check as a per-field pass over Phase 1's FieldNodes: for each field of a NoEscape candidate object, verify no &obj.field-style reference-taking operation exists anywhere in the connection graph, using the same field-sensitive storage Phase 1 already tracks rather than a new parallel structure.
  • Implement partial-object candidate emission (§19.8's edge case): ScalarReplaceCandidate.fields may be a strict subset of the object's declared fields, with rejected fields explicitly enumerated in the rejection telemetry rather than silently omitted.
  • Implement the field-layout metadata's self-contained serialization format (offset, type, size per field) independent of any internal FieldNode ID, directly satisfying ADR-17's interface-independence goal and the 246 rematerialization contract in the same pass.
  • Implement recursive field-layout emission for nested aggregates (§19.8's edge case): a field whose own type is itself a NoEscape-classified object emits its own nested field-layout block rather than a single opaque "object" size entry, so 246 can rematerialize arbitrarily deep scalarized structures.

19.3 Deliverable

A working scalar-replacement candidate emitter producing a soundness-checked Vec<ScalarReplaceCandidate> per compilation unit, with field-layout metadata for the Deoptimization-Engine (246) rematerialization contract.

19.4 Acceptance Criteria

  • Zero scalar-replacement candidates emitted for any allocation with an observed field-alias violation (I6), verified exhaustively against the conformance/phase7/ adversarial corpus, not sampled.
  • Fraction of NoEscape-classified allocations that also pass the field-alias-free check and become actual scalar-replacement candidates is documented as a named metric (distinct from the raw NoEscape fraction), establishing the real optimizer payoff number.
  • Field-layout metadata round-trips correctly through a serialization test simulating the 246 consumption contract (i.e., the metadata alone is sufficient to reconstruct the original field layout without consulting the internal connection graph).
  • scalar_replace_rejected_total correctly attributes each rejection to a specific field-alias violation site (traceable, not just counted).

19.5 Conformance Fixtures

  • conformance/phase7/simple_scalar_candidate.ir — a NoEscape object with independent, non-aliased fields, must emit a candidate.
  • conformance/phase7/field_reference_taken.ir — &obj.field passed elsewhere; obj is NoEscape but the specific field must be rejected.
  • conformance/phase7/nested_aggregate.ir — an object containing another object inline, testing recursive field-layout metadata emission.
  • conformance/phase7/deopt_metadata_roundtrip.ir — verifies the field-layout metadata alone reconstructs the original layout, simulating 246's consumption path.
  • conformance/phase7/partial_object_candidate.ir — an object with three fields, one aliased, verifying the emitted candidate covers exactly the two non-aliased fields with the third explicitly enumerated as rejected.
  • conformance/phase7/metadata_id_independence.ir — a regression test asserting field-layout metadata contains no internal FieldNode ID references, only self-contained offset/type/size data.

19.6 Pitfalls

  1. Treating "NoEscape" alone as sufficient for scalar replacement without the separate field-alias-free check (I6) — conflates two distinct soundness conditions that the domain model deliberately separates.
  2. Emitting field-layout metadata that references internal connection-graph node IDs directly instead of a stable, externally-meaningful field-layout description — creates an unnecessary coupling that breaks ADR-17's interface-independence goal.
  3. Silently scalar-replacing a subset of an object's fields while leaving others heap-backed without clearly flagging the object as partially replaced — ambiguous for the optimizer consumer and for 246's rematerialization logic.
  4. Forgetting the deopt-rematerialization consumer entirely and treating this as a self-contained optimization with no downstream dependency — misses the entire point of citing Kotzmann & Mössenböck 2005 as central to this phase.
  5. Emitting a partial-object candidate's rejected-field list only in a debug log rather than as a structured, queryable rejection record — manifestation: an operator sees scalar_replace_rejected_total increment but can't determine which specific field on which object triggered it without re-running with verbose logging; root cause: rejection detail was treated as a debugging convenience rather than a first-class telemetry attribute; debug method: attempt to trace a specific rejection from the dashboard alone, without re-running the analysis; signal: the rejection telemetry's cardinality doesn't match the number of distinct field-alias violation sites; recovery: attach the specific FieldId and violating reference site to every rejection record structurally, per the Acceptance Criteria's traceability requirement.
  6. Letting field-layout metadata leak an internal FieldNode ID as a convenience "for debugging" alongside the self-contained offset/type/size data — manifestation: a future internal refactor of FieldNode's ID scheme silently breaks 246's stored/cached metadata even though the nominal schema version didn't change; root cause: the metadata schema wasn't actually independent of internal representation, just mostly independent; debug method: conformance/phase7/metadata_id_independence.ir's exhaustive field scan for any internal-ID-shaped value; signal: a 246-side deserialization test fails after an internal-only connection-graph refactor with no OptimizationFacts version bump; recovery: strip any internal ID field from the serialized metadata format entirely, enforced by the regression fixture.

19.7 Performance Concerns

  • Field-alias-free checking cost scales with the number of distinct field-referencing operations on a candidate object; bound by the same field-sensitivity granularity Phase 1 already established, so no new asymptotic cost class is introduced.

19.8 Edge Cases

  • An object with a single field that is never aliased — trivial, full-object scalar replacement.
  • An object whose fields are all themselves NoEscape nested objects (nested aggregates) — recursive candidate emission, must not stack-overflow on deep nesting.
  • An object partially aliased (one field aliased, others not) — must emit a candidate covering only the non-aliased fields, not reject the whole object outright, to maximize the payoff metric without sacrificing soundness (I6 governs precision granularity, not an all-or-nothing gate).
  • A nested aggregate whose inner object's single field is aliased while the outer object's fields are not — the partial-candidate logic must apply independently at each nesting level, not propagate the inner rejection up to reject the entire outer object.
  • A nested aggregate three levels deep, all levels NoEscape and alias-free — recursive field-layout emission (§19.2) must terminate cleanly at the innermost level rather than assume a fixed nesting depth.

19.9 Failure Analysis

Failure: field-layout metadata omits a field's offset/type information needed by 246's rematerialization step, causing an incorrect heap-object reconstruction on deopt. Detection: the deopt-metadata-roundtrip conformance fixture, plus an explicit integration-contract test simulating 246's consumption (documented in docs/adr/ as the versioned interface boundary from ADR-17). Containment: field-layout metadata schema changes are versioned and validated against 246's expected schema version before release (§27).

Failure: a partial-object candidate's rejected-field enumeration silently drops a field when the object has more than a handful of fields, due to an off-by-one in the rejection-record accumulation loop. Detection: conformance/phase7/partial_object_candidate.ir's exact-count assertion on both the accepted and rejected field sets, not just the accepted set. Containment: the accepted-plus-rejected field count must always equal the object's total declared field count, enforced as an invariant check at candidate-emission time, not just a test assertion.

19.10 Operational Notes

Publish the scalar-replacement-candidate rate as a distinct dashboard metric from the raw NoEscape rate — operators need to see the gap between "provably non-escaping" and "actually optimizable," since that gap is where I6's soundness cost is paid.

Track the partial-vs-full candidate ratio (objects scalar-replaced entirely vs. only in part) as its own signal — a rising partial-candidate ratio across releases may indicate a codebase idiom worth a dedicated ADR-07 precision investment, distinct from a plain I6 rejection-rate trend.

20. Phase 8 — Stack-Allocation Candidates

20.1 Objectives

Implement StackAllocCandidate emission (§8 optimization-consumer mapping, Gay & Steensgaard 2000), the simpler sibling of Phase 7's scalar replacement — an object stays a single heap-shaped unit but is allocated on the stack frame instead of the heap.

20.2 Detailed Implementation Steps

  • Implement the StackAllocCandidate emission rule: every allocation classified NoEscape (Phase 3-6) is directly eligible — unlike scalar replacement, stack allocation has no field-alias-free precondition (I6 is scalar-replacement-specific; whole-object stack placement is unaffected by internal field aliasing).
  • Implement stack-frame-size estimation metadata alongside each candidate, needed by the optimizer to decide whether a given frame's cumulative stack-allocated size is acceptable (a size-budget policy the optimizer owns, not this pass — this pass only reports size).
  • Implement the interaction rule with Phase 7: an object can be both a StackAllocCandidate and (if it also passes I6) a ScalarReplaceCandidate — the optimizer picks whichever transformation applies; emit both facts independently, never one exclusive-or the other.
  • Implement escape-triggered stack-allocation rejection: if an object's classification is ArgEscape or GlobalEscape, it must never appear as a StackAllocCandidate under any circumstance — this is a direct, simple I1-class check (the "wrongly stack-allocated escaping object is a use-after-return" scenario named throughout §1/§6/§32).
  • Add regression coverage citing Gay & Steensgaard 2000's specific technique of stack-allocating even without full field-sensitivity, to document why this project's field-sensitive baseline (ADR-07) is a strictly more precise superset, not a prerequisite, for this phase.
  • Wire OptimizationFacts.stack population.
  • Implement frame-size estimation by walking the same field-layout metadata Phase 7 already emits (offset/type/size per field), summed to a total object size, rather than re-deriving size information from a separate type-layout query — one source of truth for object shape shared across Phase 7 and Phase 8.
  • Implement the hard rejection guard (an assert!-level check, not a soft heuristic) that a candidate's underlying AllocId must have classifier state exactly EscapeState::NoEscape at emission time, re-checked against the live classifier output rather than a cached snapshot that could have gone stale.
  • Implement the Gay & Steensgaard 2000 regression note as an executable fixture: construct a stack-allocation-eligible object using only whole-object (not field-sensitive) reasoning, and confirm this project's field-sensitive baseline produces the same eligibility verdict, demonstrating strict superset behavior rather than a precision regression.
  • Implement optimizer-facts's size-budget-agnostic contract explicitly: the frame-size number is reported as a plain byte count with no embedded policy threshold, so a future optimizer change to its own stack-budget heuristic never requires a schema or behavior change on this pass's side (ADR-17's independence goal applied specifically to §20's own output field).

20.3 Deliverable

A StackAllocCandidate emitter producing every sound whole-object stack-allocation opportunity per compilation unit, independent of the scalar-replacement decision.

20.4 Acceptance Criteria

  • 100% of StackAllocCandidates correspond to allocations classified NoEscape — checked as a hard invariant test against the classifier's own output, not re-derived independently (avoiding two divergent sources of truth for the same fact).
  • Zero StackAllocCandidates ever emitted for an ArgEscape or GlobalEscape allocation, verified exhaustively against the full conformance/phase8/ corpus including every fixture from Phases 3-6 reused here as a regression net.
  • Stack-allocation candidate count is a strict superset of the scalar-replacement candidate count from Phase 7 on every shared fixture (every scalar-replace candidate is also a stack-alloc candidate, but not vice versa) — a documented, tested cross-phase invariant.
  • Frame-size estimation metadata matches a hand-computed reference value on ≥5 fixtures with known object layouts.

20.5 Conformance Fixtures

  • conformance/phase8/simple_stack_candidate.ir — a plain NoEscape object with internal field aliasing that would fail I6 but is still a valid whole-object stack-allocation candidate (directly demonstrating the Phase 7 vs Phase 8 distinction).
  • conformance/phase8/escaping_rejection_regression.ir — reuses every Phase 3-6 escaping fixture, asserting none produce a StackAllocCandidate.
  • conformance/phase8/superset_check.ir — a fixture producing both a scalar-replace and a stack-alloc candidate for the same object, verifying the superset relationship.
  • conformance/phase8/gay_steensgaard_baseline_parity.ir — a whole-object-reasoning-eligible fixture, verifying this project's field-sensitive analysis doesn't under-deliver relative to the simpler historical technique.
  • conformance/phase8/stale_classification_guard.ir — a fixture where an object's classification changes between an earlier cached read and candidate-emission time, verifying the hard rejection guard catches the staleness rather than trusting the cache.

20.6 Pitfalls

  1. Accidentally requiring the I6 field-alias-free check for stack allocation too, "for consistency" with scalar replacement — this over-restricts a strictly cheaper, more broadly applicable optimization for no soundness benefit.
  2. Deriving StackAllocCandidates from a separate re-classification pass instead of directly from the Phase 3-6 classifier's authoritative output — creates two sources of truth that can silently diverge.
  3. Ignoring frame-size estimation and leaving the optimizer to guess — defeats the purpose of this pass acting as the authoritative fact source for the optimizer's own size-budget policy.
  4. Reading a cached/stale classifier snapshot instead of the live post-fixpoint classification when emitting a StackAllocCandidate — manifestation: an object that was NoEscape during an early analysis pass but later promoted to ArgEscape (e.g., after Phase 6 substitution refines a call site) still gets emitted as a stack-alloc candidate; root cause: candidate emission ran against a snapshot taken before all interprocedural passes finished; debug method: conformance/phase8/stale_classification_guard.ir's explicit before/after classification change; signal: the hard rejection guard's assertion fires in CI on a fixture engineered to exhibit the staleness; recovery: always re-read classifier state at the exact point of candidate emission, after every phase that can change it has run.
  5. Deriving frame-size estimation from a separate, independently-maintained type-layout query instead of Phase 7's field-layout metadata — manifestation: the two size numbers (scalar-replace metadata vs. stack-alloc frame-size estimate) disagree for the same object; root cause: two representations of "how big is this object's layout" evolved independently; debug method: cross-check both numbers on every shared fixture in conformance/phase8/superset_check.ir; signal: a size discrepancy surfaces only on objects with certain field-type combinations; recovery: make Phase 8's frame-size estimation a thin wrapper over Phase 7's field-layout metadata, never a parallel computation.
  6. Embedding a size-budget policy threshold (e.g., "reject candidates over 4KB") directly into this pass's emitted metadata instead of leaving that decision entirely to the optimizer — manifestation: a downstream optimizer change to its own stack-budget heuristic requires an OptimizationFacts schema bump even though the underlying escape facts haven't changed; root cause: a policy decision was smuggled into what should be a pure fact-reporting interface; debug method: audit StackAllocCandidate's fields for anything resembling a threshold or policy constant rather than a measured size; signal: a §27 schema-version bump is required for a change that has nothing to do with escape analysis correctness; recovery: strip any embedded policy threshold from the candidate schema, reporting only the measured size per ADR-17.

20.7 Performance Concerns

  • Frame-size estimation requires walking the object's field-layout metadata (shared machinery with Phase 7); no new asymptotic cost, but must be memoized per allocation site rather than recomputed per candidate emission call.

20.8 Edge Cases

  • An object with zero fields (e.g., a marker/sentinel allocation) — trivial minimal-size stack candidate.
  • A NoEscape object that also happens to be extremely large (e.g., a large fixed-size array) — still a valid candidate; the policy decision of whether stack space is worth it belongs to the optimizer, not this pass, per §1's boundary.
  • An object with a self-referential field failing I6 (from the Phase 7 example) but still a valid stack-alloc candidate — directly exercises the Phase 7/8 divergence this phase is built around.
  • An object whose classification changes from NoEscape to ArgEscape between the time Phase 6's substitution runs and the time Phase 8's emitter is invoked (a pipeline-ordering edge case) — the emitter must observe the final, not an intermediate, classification state.
  • A StackAllocCandidate's reported frame size overflowing a reasonable fixed-width integer field on a pathological fixed-size-array allocation — the size field's type must be wide enough for the §4 corpus's largest realistic object, not silently truncate.

20.9 Failure Analysis

Failure: a future refactor accidentally shares the I6 field-alias-free filter between Phase 7 and Phase 8 emission paths, silently suppressing valid stack-allocation candidates and regressing the §4 payoff metric without any soundness benefit. Detection: the superset-check conformance fixture (conformance/phase8/superset_check.ir) and the broader payoff-metric dashboard (Phase 3's classification counters) would show an unexplained drop in stack-alloc candidates without a corresponding drop in NoEscape classifications — a specific, checkable signature distinguishing this bug class from an actual soundness regression.

Failure: frame-size estimation and scalar-replacement field-layout metadata silently drift apart after an independent Phase 7 or Phase 8 change touches only one of the two consumers of the shared field-layout data. Detection: a cross-check assertion comparing both numbers on every fixture that produces both candidate types, run as a standing CI check rather than a one-time validation. Containment: treat any divergence as a Phase 7/8 shared-dependency regression, root-caused to whichever side stopped using the common field-layout source, not patched independently on each side.

20.10 Operational Notes

Track the scalar-replace-candidate-to-stack-alloc-candidate ratio as an operational signal: a ratio far below expectations on a given codebase suggests a field-aliasing pattern worth investigating (either a real codebase idiom or an I6 check bug).

Alert on any divergence between Phase 7's and Phase 8's size estimates for the same object above a small tolerance — this is a cheap, high-signal check for the shared-field-layout-source regression named in this phase's Failure Analysis, and costs nothing extra to compute since both numbers are already produced per candidate.

21. Phase 9 — Thread-Escape Analysis and Lock-Elision Sites

21.1 Objectives

Implement thread-confinement detection triggered by spawn statements (§8 transfer table) and LockElisionSite emission, requiring strictly more evidence than stack-allocation eligibility per I7/P10.

21.2 Detailed Implementation Steps

  • Implement the Spawn transfer function (§8): any object reachable from a thread-spawn's argument set is marked thread-shared, a distinct tracked property from the base escape state (not necessarily promoting straight to GlobalEscape — an object can be thread-confined-but-not-globally-visible, e.g., shared only with a spawned worker that itself never publishes it further).
  • Implement thread-confinement classification: an object is thread-confined if it is NoEscape or ArgEscape strictly to a statically-known-confined context (e.g., passed only to a spawned thread that itself doesn't further escape it) — the precise definition backing I7.
  • Implement lock-site detection: identify monitor-acquire/release pairs in the IR keyed to a specific object (the lock target).
  • Implement LockElisionSite emission: a lock site is a candidate exactly when its lock-target object is thread-confined per the above definition — never merely NoEscape at the allocation site alone, since a NoEscape allocation can still later be handed to a spawned thread within the same method (P10's core distinction).
  • Implement the rejection path (lock_elision_rejected_total, I7) for lock sites whose target is thread-shared beyond a single confined context — reject to a synchronization-retained default, never a "probably fine" heuristic.
  • Add explicit regression coverage for the P10 scenario: an object that is a valid StackAllocCandidate (Phase 8) but must NOT be a LockElisionSite, directly demonstrating the strictly-stronger-evidence requirement.
  • Wire OptimizationFacts.locks population.
  • Implement the thread-sharing bitflag (Performance Concerns' packing design, §21.7) as a field alongside ObjectNode.state in §11's schema, propagated by its own dedicated transfer-function pass distinct from the base EscapeState join, so a thread-sharing update never accidentally reuses EscapeLattice::join's three-point semantics.
  • Implement per-object lock-site consistency enforcement (the multiple-locks edge case, §21.8): before emitting any LockElisionSite for a given AllocId, collect every lock site referencing that object and require all of them to independently pass the thread-confinement check; a single failing site vetoes elision for every site on that object.
  • Implement transitive thread-sharing propagation across nested spawn calls by treating a spawned thread's own body as if its parameters were passed to an implicit callee, reusing Phase 5/6's summary-substitution machinery rather than a bespoke thread-specific traversal.
  • Implement closure-capture modeling for spawn arguments (Pitfall 6 below pre-empted): every variable captured by a spawned closure, not just its explicit call arguments, is treated as an implicit actual parameter to the spawn's summary so transitive thread-sharing through captured references is never silently dropped.

21.3 Deliverable

A thread-escape analysis and LockElisionSite emitter that never elides a lock on an object visible to more than the confining thread context.

21.4 Acceptance Criteria

  • Zero LockElisionSites emitted for any object also observed thread-shared via a spawn reaching more than one thread context — exhaustively checked, not sampled, given the I1-adjacent severity (an incorrect elision here is a data race, not merely a memory-safety bug).
  • The named P10 regression fixture (a StackAllocCandidate that is not a valid LockElisionSite) passes on every CI run, guarding the strictly-stronger-evidence boundary explicitly.
  • Lock-elision candidate count is measured and reported as a distinct payoff metric alongside (not merged into) the stack-allocation and scalar-replacement counts, since the achievable rate is expected to be substantially lower (thread-confinement is rarer than mere method-confinement).
  • lock_elision_rejected_total attributes every rejection to a specific thread-sharing evidence site (traceable).

21.5 Conformance Fixtures

  • conformance/phase9/simple_confined_lock.ir — a lock on a NoEscape, never-spawned object, valid elision candidate.
  • conformance/phase9/spawned_shared_lock.ir — a lock on an object passed to spawn, must reject elision.
  • conformance/phase9/stack_alloc_but_not_lock_elidable.ir — the named P10 regression: valid StackAllocCandidate, invalid LockElisionSite.
  • conformance/phase9/nested_spawn_chain.ir — an object passed through two levels of spawned threads, testing transitive thread-sharing detection.
  • conformance/phase9/multiple_lock_sites_mixed.ir — one object with two lock sites, one thread-confined and one not, verifying elision is vetoed for both, not granted to the confined one alone.
  • conformance/phase9/spawn_via_summary_substitution.ir — a spawn call whose thread-body parameter binding reuses Phase 5/6 substitution machinery, verifying thread-sharing propagation gets the same precision as ordinary interprocedural calls.

21.6 Pitfalls

  1. Conflating "NoEscape at the allocation site" with "thread-confined" — the single most important pitfall this phase exists to prevent (P10); an object can be a legitimate stack-allocation candidate and still be a lock-elision hazard.
  2. Treating spawn as an automatic promotion straight to GlobalEscape — over-approximates and needlessly tanks the lock-elision payoff metric when a spawned thread never further publishes the object.
  3. Detecting lock sites purely syntactically (matching a specific monitor-acquire opcode) without tracing the lock-target object through the connection graph — misses aliased lock-target references.
  4. Under-testing the nested-spawn transitive case, since single-level spawn tests can pass while multi-level transitive thread-sharing still leaks through undetected.
  5. Evaluating each lock site on a shared object independently and granting elision per-site rather than per-object — manifestation: one lock site on an object elides while a second, less-confined site on the same object also elides based on its own local (incorrect) analysis, together reintroducing a race the per-object consistency rule was designed to prevent; root cause: the emitter iterates lock sites without first grouping by target AllocId; debug method: conformance/phase9/multiple_lock_sites_mixed.ir's explicit two-site fixture; signal: LockElisionSite count for a single AllocId exceeds the confirmed-confined lock-site count for that object; recovery: group lock-site evaluation by AllocId first, and veto all sites on any object with even one non-confined site.
  6. Reusing Phase 5/6's summary-substitution machinery for spawn calls but forgetting that a spawned thread's "return value" has no caller to return to — manifestation: thread-sharing propagation silently drops an object that's captured by the spawned closure but never assigned to anything the substitution logic recognizes as a parameter; root cause: the implicit-callee framing borrowed from ordinary calls doesn't naturally model closure capture; debug method: conformance/phase9/spawn_via_summary_substitution.ir's closure-capture variant; signal: an object known (by the dynamic oracle) to be thread-shared is never marked thread-shared by the static analysis; recovery: model closure-captured variables as additional implicit actual parameters to the spawn's summary, not just the explicit spawn-call arguments.

21.7 Performance Concerns

  • Thread-sharing propagation adds a second "escape-like" property tracked per object alongside the base EscapeState; ensure this doesn't double the per-node memory cost against the §4 connection-graph memory ceiling — pack it as a bitflag alongside EscapeState, not a second full lattice value.

21.8 Edge Cases

  • A lock on an object that is itself a field of a larger GlobalEscape object — the lock-target's own thread-sharing status must be evaluated independently of its container's escape state.
  • A spawn call whose target thread function is itself unanalyzable (native/external) — must route through the same I4-style conservative default (thread-shared, not confined) rather than a distinct ad hoc rule.
  • Multiple locks on the same underlying object at different program points — elision decision must be consistent across all lock sites on that object, not independently (mixed elision on the same object risks reintroducing the exact race the analysis exists to prevent).
  • A closure captured by a spawned thread that references an object only indirectly (through a captured reference to another object that itself holds the target) — transitive thread-sharing must be traced through the captured reference chain, not just the closure's immediately captured variables.
  • A spawned thread whose closure captures a variable that is itself reassigned after the spawn call but before the thread actually starts running — the static analysis must conservatively treat the captured reference, not a fixed runtime value, since it cannot know the actual thread-scheduling order.

21.9 Failure Analysis

Failure: a lock-elision site is approved based on the allocation's base EscapeState alone (Phase 3's classifier) without consulting the separate thread-sharing bitflag, silently reintroducing the exact P10 confusion the phase is designed around. Detection: the P10-named regression fixture catches this directly and immediately; the differential soundness oracle (Phase 11) additionally instruments actual runtime thread-sharing on the labeled corpus as a dynamic backstop. Containment: an approved-then-found-unsound lock-elision site is treated as a data-race-severity release blocker, matching I1's treatment of false NoEscape, not a lower-severity precision bug.

Failure: per-object lock-site consistency enforcement is implemented but only checks lock sites discovered within the same method as the allocation, missing a lock site on the same object taken in a different method after the object escapes to a parameter. Detection: a cross-method variant of conformance/phase9/multiple_lock_sites_mixed.ir where the second lock site lives in a callee reached via Phase 5/6's summary machinery. Containment: lock-site collection for the consistency check must span the full interprocedural reach of an object, not just its allocating method's local view.

21.10 Operational Notes

Given the higher blast radius of an incorrect lock elision (a data race, potentially non-deterministic and hard to reproduce, versus a deterministic use-after-return from a stack-allocation bug), route lock_elision_rejected_total spikes and any soundness-oracle finding touching LockElisionSite through the page-immediately alerting path defined in §26, not the standard precision-regression path.

Report the count of objects with more than one lock site as a distinct dashboard signal from the plain lock-elision candidate count — a codebase with many multi-lock-site objects is exactly where the per-object consistency rule (and its cross-method extension) earns its complexity, and a sudden drop in multi-lock-site coverage after a refactor is worth investigating on its own.

22. Phase 10 — Partial Escape Analysis (Branch-Sensitive, GraalVM-Style)

22.1 Objectives

Implement partial-escape: branch-sensitive materialization tracking that refines the Phase 3-9 whole-object baseline without ever regressing it (I12), directly modeling GraalVM's partial escape analysis advance over the classic Choi connection-graph approach.

22.2 Detailed Implementation Steps

  • Implement PartialEscape's per-branch state tracking (§11): an object can carry a different provisional escape state on different control-flow paths within the same method, rather than one method-wide state.
  • Implement materialization-point insertion: identify the exact program point on a given path where a virtually-tracked (not-yet-materialized) object first becomes observable (escapes on that specific path) and mark it as the materialize_at site (§8's if/else worked example).
  • Implement the I12 cross-check: after computing partial-escape results, verify no path's classification is less conservative than what the whole-object Phase 3-9 baseline classifier would assign to the object overall — partial escape analysis may only refine (keep virtual longer on non-escaping paths), never contradict the sound baseline.
  • Implement the fallback-disable path (I12's recovery clause): if the cross-check fails for a given method, disable partial-escape mode for that method specifically and fall back to the Phase 3-9 baseline classification, rather than failing the whole compilation unit.
  • Implement the loop-back-edge materialization-point placement case flagged as a named pitfall in GraalVM's own design (§5 reference implementations) — a virtual object crossing a loop back-edge without escaping on that iteration must not be prematurely materialized just because the loop body contains an escaping branch elsewhere.
  • Add partial_escape_regression_total telemetry (I12).
  • Implement per-branch PartialEscape state as a map keyed by BranchId (§11), initialized from the Phase 3-9 baseline classification at the branch point and only ever refined (kept virtual) or degraded to materialized, never independently re-derived from scratch per branch.
  • Implement the multi-way (>2) branch case explicitly as an N-ary join over all outgoing edges of a branch point, rather than a pairwise if/else-shaped join generalized ad hoc — this directly targets Pitfall 4 below by construction rather than by later test discovery.
  • Implement the loop-back-edge materialization check as a dedicated case distinguishing "escapes on this specific iteration's path" from "the loop body contains an escaping branch somewhere" — the two are conflated by any implementation that treats a loop as just another control-flow diamond.
  • Implement materialization-point selection as a deterministic function of program point (statement SiteId ordering within the method), so the N-ary join's evaluation order can never influence which specific site is chosen even when two candidate sites are otherwise equally valid (directly closing the gap named in Pitfall 5 below).

22.3 Deliverable

A partial-escape crate providing additive, branch-sensitive precision on top of the sound Phase 3-9 whole-object baseline, with a per-method automatic fallback when the I12 cross-check fails.

22.4 Acceptance Criteria

  • The §8 partial-escape worked example (an object published only inside an if branch) classifies as virtual-until-materialized on the non-escaping else path and materializes exactly at the if branch's publish site — matching the hand-derived expectation exactly.
  • Zero I12 cross-check failures silently pass through to the optimizer — every failure triggers the documented per-method fallback, verified by a fixture specifically engineered to trigger the fallback path.
  • Measured NoEscape-equivalent precision (allocations kept virtual on at least one path) exceeds the Phase 3-9 whole-object baseline's NoEscape fraction by a documented percentage-point delta on the conformance/phase10/ branchy-allocation corpus.
  • The loop-back-edge pitfall fixture materializes correctly (only on the actually-escaping iteration path, not prematurely at loop entry).

22.5 Conformance Fixtures

  • conformance/phase10/worked_partial_escape.ir — the §8 if/else worked example.
  • conformance/phase10/loop_backedge_materialization.ir — the GraalVM-flagged loop pitfall case.
  • conformance/phase10/i12_fallback_trigger.ir — a fixture engineered to fail the I12 cross-check, verifying the per-method fallback activates correctly.
  • conformance/phase10/multi_branch_materialization.ir — three-way branching with materialization required on two of three paths.
  • conformance/phase10/nary_join_five_way.ir — a five-way branch (e.g., a match/switch construct), stress-testing the N-ary join generalization beyond the three-way case.
  • conformance/phase10/loop_body_escaping_branch_no_leak.ir — a loop whose body contains an escaping branch on iteration N only, verifying iterations that don't take that branch are never prematurely materialized.

22.6 Pitfalls

  1. Allowing a partial-escape result to override the baseline classifier's GlobalEscape verdict for an object that genuinely escapes on every path — a direct I12 violation and the single most important thing this phase must never do.
  2. Placing materialization points imprecisely at loop entry instead of at the actual escaping statement inside the loop body — over-conservative and defeats the phase's own precision goal, independent of soundness.
  3. Treating partial-escape mode as a wholesale replacement for the baseline classifier rather than an additive refinement layer that can be selectively disabled per method (I12's fallback design) — makes a partial-escape bug a whole-pipeline soundness risk instead of a contained, disableable one.
  4. Under-testing multi-way (>2) branch fixtures, since if/else pairs are the easy case and three-or-more-way branching is where materialization-point bookkeeping bugs concentrate.
  5. Generalizing the if/else pairwise join to N-ary branches by naive iterated pairwise application instead of a genuine N-ary join — manifestation: a five-way branch's materialization point placement depends on the arbitrary order branches happen to be iterated in; debug method: conformance/phase10/nary_join_five_way.ir run with branch declaration order permuted, checking for identical results; root cause: the "N-ary join" is actually a left-fold of pairwise joins, which is associative for the escape lattice's join operator but can still produce order-dependent materialization-point choices if tie-breaking isn't also order-independent; signal: two semantically-identical fixtures differing only in branch declaration order produce different materialization sites; recovery: make materialization-point selection itself a deterministic function of program point, independent of the join's evaluation order.
  6. Treating "the loop body contains an escaping branch" as sufficient grounds to materialize at loop entry — manifestation: an object never actually escaping on the executed iteration path still gets eagerly materialized, discarding a real precision opportunity though not a soundness violation; root cause: conflating "reachable escaping branch exists in the loop body" with "this iteration's actual control-flow path reaches it"; debug method: conformance/phase10/loop_body_escaping_branch_no_leak.ir's iteration-path-specific assertion; signal: the measured NoEscape-equivalent precision (Acceptance Criteria) is lower than expected specifically on loop-heavy fixtures; recovery: track materialization per actual control-flow path through the loop, not per loop-body-wide reachability summary.

22.7 Performance Concerns

  • Per-branch state tracking multiplies the state space by path count in the worst case; bound in practice by only tracking partial-escape state for objects the baseline classifier already found "interesting" (i.e., not GlobalEscape from the start — a GlobalEscape object gains nothing from path-sensitivity).

22.8 Edge Cases

  • An object escaping on every path (no benefit from partial-escape tracking) — must degrade gracefully to the baseline result, not add pointless per-path bookkeeping overhead.
  • A branch that is statically unreachable (dead code) — must not require a materialization point on a path that can never execute.
  • An object that is virtual on entry to a loop, escapes on iteration N, and the loop has an unbounded iteration count — materialization must still resolve to a single well-defined program point (the escaping statement), not depend on the iteration count.
  • A five-or-more-way branch (e.g., a large match/switch) where only one arm escapes and the rest are dead code at compile time — the N-ary join must correctly treat unreachable arms per the dead-branch edge case above while still joining the remaining live arms correctly.
  • Two candidate materialization sites at the exact same SiteId ordering rank due to a frontend that lowers a single source construct into parallel IR statements — the deterministic-selection rule (§22.2) must have a documented, tested tiebreaker beyond raw SiteId order for this degenerate case.

22.9 Failure Analysis

Failure: the I12 cross-check itself has a bug and fails to catch a genuine partial-escape overreach, letting an unsound "virtual" classification reach the optimizer. Detection: this is exactly the category the Phase 11 dynamic soundness oracle is built to catch as a backstop independent of any single phase's internal self-checks — partial escape analysis results feed the same SoundnessCheck contract as the baseline classifier (§11), with no special exemption. Containment: any oracle-detected violation traced to partial-escape mode disables the feature pipeline-wide pending a fix, per I11's release-gate policy — it does not just disable the one offending method until the root cause (a cross-check bug, not just an instance) is understood.

Failure: the N-ary join's materialization-point selection is order-dependent (Pitfall 5), producing non-deterministic results across semantically-identical builds where branch declaration order differs only due to an upstream frontend change. Detection: conformance/phase10/nary_join_five_way.ir run under branch-order permutation, tied into the same non-determinism fuzz methodology I13 already established in Phase 2. Containment: treat any order-dependent materialization result as an I13-class determinism defect, not a partial-escape-specific issue, and route it through the same fix discipline.

22.10 Operational Notes

Report partial-escape's precision gain and its fallback-trigger rate together — a feature with a high fallback rate is not delivering its intended value even if it never produces an unsound result, and that's a distinct, worth-tracking signal from soundness itself.

Track materialization-point determinism explicitly (via the branch-order-permutation methodology) as part of Phase 10's own release checklist, not merely as a special case folded into Phase 2's general I13 campaign — partial escape analysis is the newest and most control-flow-structure-sensitive component in the pipeline, and deserves its own targeted determinism regression surface.

23. Phase 11 — Soundness-and-Precision Benchmark, Differential Validation, and Perf Hardening

23.1 Objectives

Build soundness-oracle and conformance-suite's full differential/dynamic validation harness, establish the labeled corpus as a release gate (I11), and perform the perf-hardening pass needed to hit every §4/§30 target under real-world-scale input.

23.2 Detailed Implementation Steps

  • Implement the dynamic soundness oracle: instrument a reference interpreter/runtime to record actual object lifetimes (does an object outlive its allocating frame in practice?) and actual thread-sharing, running the full labeled corpus and asserting no object claimed NoEscape actually escaped, and no LockElisionSite target was actually accessed from more than its confining thread (I1, I7, I11).
  • Implement the differential validation harness comparing this engine's classifications against HotSpot's and Go's escape-analysis decisions on a shared corpus subset (§5 reference implementations), reporting both agreement rate and, for disagreements, which side is more conservative (never asserting one is simply "wrong" without dynamic confirmation from the oracle).
  • Implement the precision benchmark with a documented floor: fraction of allocations optimized (stack-alloc ∪ scalar-replace ∪ lock-elision candidates) must not regress below the §4 targets on any release candidate — wired as a CI gate distinct from, and in addition to, the soundness gate.
  • Implement perf-hardening: profile the full pipeline (Phases 0-10) against the §4/§30 latency and throughput targets on a large synthetic and a real-world-scale corpus; address the top-3 profiled hotspots explicitly (expected candidates: connection-graph edge-arena churn, summary-cache lookup cost, virtual-dispatch join fan-out — confirm or refute with real profiling data, don't assume).
  • Implement fuzzing expansion (ADR-24): beyond the IR-reader fuzzing from Phase 0, add a random-valid-program generator that fuzzes the full pipeline end-to-end against the soundness oracle, searching specifically for I1/I7/I12-class violations.
  • Wire the full soundness-oracle and precision-benchmark jobs into CI (ADR-25's previously-placeholder soundness.yml), completing Phase 0's deferred CI work.
  • Implement compile-time overhead measurement against the §4 target (≤8% of total optimizing-compiler wall-clock time), and gate releases on it via §30's performance-regression job.
  • Implement the oracle's instrumentation-coverage self-audit: a maintained checklist of every dynamic-dispatch/reflection-like construct named in T5, cross-checked against what the reference interpreter's instrumentation actually observes, so a coverage gap is a detectable CI finding rather than a purely aspirational documentation claim.
  • Implement the three-way differential comparison path (this engine vs. HotSpot vs. Go) as a genuine three-column report, not a two-way diff run twice, so a fixture where HotSpot and Go themselves disagree (§23.8's edge case) is visible as its own reportable category.
  • Implement perf-hardening's top-3-hotspot identification as a data-driven output of the profiling run itself (not a pre-committed guess) — the phase's own text names connection-graph edge-arena churn, summary-cache lookup cost, and virtual-dispatch join fan-out as expected candidates specifically so the real profiling data can confirm or refute them.

23.3 Deliverable

A complete, CI-gated soundness and precision validation harness (soundness-oracle + conformance-suite), a perf-hardened pipeline meeting every §4/§30 numeric target, and the release-readiness state this blueprint's Status line assumes for any tagged version.

23.4 Acceptance Criteria

  • unsound_classification_total == 0 and zero unsound LockElisionSite findings across the full labeled corpus under the dynamic oracle — the hard release gate (I1, I7, I11).
  • Fraction of allocations provable NoEscape ≥35% (§4 target) and, combined with scalar-replace/stack-alloc/lock-elision candidate rates, meets every §30 M-series target (defined in §30) on the reference corpus.
  • Compile-time overhead ≤8% of total optimizing-compiler wall-clock time (§4), measured on the real-world-scale corpus, not just synthetic benchmarks.
  • Differential agreement rate against HotSpot/Go on the shared corpus subset documented as a specific percentage, with every disagreement classified (this-engine-more-conservative vs other-engine-more-conservative) and zero disagreements where this engine is less conservative and dynamically found unsound.
  • End-to-end fuzzing campaign of ≥72 CPU-hours against the soundness oracle finds zero I1/I7/I12-class violations before release tagging.

23.5 Conformance Fixtures

  • The full accumulated conformance/ corpus from Phases 0-10, now run as one integrated release-gate suite.
  • conformance/phase11/hotspot_differential_subset.ir — the shared corpus subset used for HotSpot/Go differential comparison.
  • conformance/phase11/large_scale_synthetic.ir — a large synthetic program (thousands of methods) for perf-hardening measurement.
  • conformance/phase11/fuzz_regression_corpus/ — a growing directory of fuzz-discovered fixtures, each permanently retained as a regression test once fixed.
  • conformance/phase11/three_way_disagreement.ir — a fixture where this engine, HotSpot, and Go all classify a shared allocation differently, exercising the three-column differential report path directly.
  • conformance/phase11/oracle_coverage_audit_gap.ir — a fixture using a dynamic-dispatch construct deliberately omitted from the maintained T5 checklist, verifying the coverage self-audit actually flags the gap rather than passing silently.

23.6 Pitfalls

  1. Treating the dynamic soundness oracle as a nice-to-have validation extra rather than the actual release gate it is defined to be (I11) — the entire blueprint's soundness claims are only as credible as this oracle's coverage and its enforcement as a hard CI gate.
  2. Interpreting a differential disagreement with HotSpot/Go as automatically "this engine is wrong" without dynamic confirmation — the other systems have their own conservative approximations and are not ground truth by themselves.
  3. Perf-hardening by weakening a soundness check (e.g., disabling an assertion in release builds) instead of addressing the actual algorithmic hotspot — an explicitly forbidden shortcut given I2/I6/I7's assertions are load-bearing, not diagnostic-only.
  4. Declaring the fuzzing campaign "done" after a fixed CPU-hour budget with zero findings, without expanding the random-program generator's grammar coverage over time — a fuzzer that stops finding bugs may have exhausted its own reachable input space, not the actual bug space.
  5. Under-investing in the precision benchmark relative to the soundness oracle — a technically sound but low-payoff release (e.g., 5% NoEscape instead of the 35% target) still fails its purpose even with zero soundness violations.
  6. Building the oracle's coverage self-audit once at Phase 11 launch and never re-running it as T5-relevant IR-lowering rules evolve in later maintenance — manifestation: a newly added language construct's opaque-call lowering (added post-release, per T5's own recovery guidance) is never added to the audited checklist; root cause: the checklist was treated as a Phase-11 deliverable rather than a living artifact tied to the IR frontend's own change process; debug method: diff the checklist's last-updated date against the IR frontend's changelog; signal: conformance/phase11/oracle_coverage_audit_gap.ir-style fixtures stop being written for new constructs; recovery: make checklist maintenance a required step in the IR-frontend contract change process (§1/§5), not a one-time Phase 11 artifact.
  7. Reporting a three-way differential disagreement (this engine vs. HotSpot vs. Go) as a simple pairwise "we agree with HotSpot but not Go" without surfacing that HotSpot and Go also disagree with each other — manifestation: an investigator wastes time trying to root-cause "our bug" when the actual finding is that all three systems reasonably disagree on a genuinely ambiguous case; root cause: the differential report was built as two independent two-way diffs rather than one genuine three-way comparison; debug method: conformance/phase11/three_way_disagreement.ir's explicit three-way-divergent fixture; signal: the differential report's total disagreement count doesn't reconcile against the sum of its two pairwise sub-reports; recovery: implement and test the three-way report as a first-class output, per this phase's Detailed Implementation Steps.
  8. Letting the ≥72 CPU-hour fuzzing-campaign floor (Acceptance Criteria) become a rubber-stamped, unexamined number that never actually changes as the corpus and IR grammar grow — manifestation: the same 72-hour budget from the project's first release is still used years later against a codebase and grammar many times larger; root cause: the floor was set once as a reasonable starting point and never re-derived against corpus growth; debug method: compare fuzz-campaign coverage growth rate against conformance/ corpus growth rate release over release; signal: coverage-per-CPU-hour trends downward while the budget stays flat; recovery: tie the campaign budget to a coverage target (e.g., a minimum new-edge discovery rate), not a fixed wall-clock number, revisited each major release.

23.7 Performance Concerns

  • The dynamic soundness oracle's runtime instrumentation itself adds overhead to the reference interpreter run, not to the analysis pass — keep this cost isolated to the CI validation harness and never let it leak into the analysis pass's own §4 latency budget.
  • Fuzzing campaign wall-clock cost must be bounded and parallelized across CI runners to fit within the release cadence defined in §29.

23.8 Edge Cases

  • A labeled corpus fixture where even HotSpot and Go disagree with each other (not just with this engine) — the differential harness must report a three-way comparison, not silently pick a majority-vote "truth."
  • A fuzzer-discovered fixture that triggers an I3 iteration-cap fallback (not a soundness violation, but a conservatism-under-pressure case) — must be triaged and classified separately from genuine I1/I7/I12 findings, not conflated with them.
  • A perf-hardening fix that improves throughput but measurably reduces the NoEscape fraction (a precision-for-speed tradeoff smuggled in as a "perf fix") — must be caught by the precision-benchmark CI gate before merge, not discovered post-release.
  • A newly added IR-lowering rule for a dynamic-dispatch construct that the oracle's coverage checklist hasn't been updated to include yet — the coverage self-audit must fail loudly on this gap rather than silently reporting full coverage against a stale checklist.
  • A fuzzing campaign that hits its 72-CPU-hour floor but is still actively discovering new coverage at the moment it stops — the campaign-completion criteria (Pitfall 8) must distinguish "budget exhausted, still finding things" from "budget exhausted, coverage has plateaued," since only the latter is a genuinely adequate stopping point.

23.9 Failure Analysis

Failure: the soundness oracle itself has insufficient runtime-instrumentation coverage (e.g., misses a reflection-like dynamic-dispatch path in the reference interpreter) and passes a build that is actually unsound in production. Detection: this is the residual risk the threat model (§24, T5) names explicitly as "a reflection/dynamic-load path invisible to the analysis" — mitigated by keeping the oracle's instrumentation coverage itself under continuous audit and by treating any production-reported use-after-return traced back to this engine as a P0 incident that expands oracle coverage, not just patches the one instance. Containment: per I11, any oracle-coverage gap discovered post-release triggers an immediate re-audit of every release since the gap was introduced, not just a forward fix.

Failure: the coverage self-audit checklist itself silently goes stale because no process ties its maintenance to IR-frontend changes (Pitfall 6). Detection: a checklist-staleness check comparing its last-modified date against the IR frontend's own changelog, run as a lightweight Phase 11 CI job independent of the heavier fuzzing/differential jobs. Containment: block the rc→stable promotion (§29) on checklist staleness exactly as it blocks on unsound_classification_total != 0 — a stale checklist is treated as a soundness-gate-adjacent defect, not a documentation nit.

Failure: the fuzzing campaign's fixed 72-CPU-hour budget stops a run mid-discovery, right as new-edge coverage was accelerating rather than plateauing, giving a false sense of completeness. Detection: a coverage-growth-rate trend check at campaign end, distinguishing a plateaued curve from one still climbing. Containment: extend the campaign automatically (up to a documented hard ceiling) whenever the growth-rate check shows active discovery at the nominal budget's end, rather than stopping unconditionally at the fixed hour count.

23.10 Operational Notes

This phase's CI jobs (soundness oracle, differential validation, precision benchmark, perf-regression gate) are the permanent, ongoing release gate for every future change to this project, not a one-time Phase-11 milestone — document this explicitly in docs/runbooks/ so future contributors don't mistake "Phase 11 shipped" for "soundness validation is now optional."

Publish the three-way differential disagreement breakdown (this-engine-only-conservative vs. HotSpot-only-conservative vs. Go-only-conservative vs. genuine three-way divergence) on the same dashboard as the soundness and precision metrics — a rising "genuine three-way divergence" category over time is a signal worth investigating even when every individual disagreement is dynamically confirmed sound, since it may indicate the reference systems themselves are evolving in ways worth tracking.

Report the fuzzing campaign's coverage-growth-rate curve, not just its final CPU-hour total and finding count, on the release dashboard — the curve's shape is the actual evidence for whether the campaign ran long enough, which a single aggregate number can never show.

26. Operational Readiness

Named metrics: classification_no_escape_fraction (the payoff metric — §4 target ≥35%), analysis_throughput_methods_per_sec and analysis_throughput_nodes_per_sec (§4), fixpoint_iterations_total (distribution, watching for approach to the I3 cap), summary_cache_hit_ratio (§4 target ≥95%), unsound_classification_total (must be 0, page-immediately if nonzero), scalar_replace_candidate_total, stack_alloc_candidate_total, lock_elision_candidate_total (distinct payoff metrics per §19-21).

Tracing: a connection-graph dump is the key debugging artifact (Phase 1 deliverable) — every soundness or convergence incident investigation starts by pulling the dump plus the fixpoint iteration trace (Phase 2) for the affected method. OpenTelemetry-compatible spans (ADR-21) cover per-method analysis timing, summary application, and classification.

Structured logging: tracing-crate structured JSON (ADR-20), correlated by MethodId/AllocId so a single log line is traceable back to a specific connection-graph node.

Dashboards: a payoff dashboard (NoEscape fraction, scalar-replace/stack-alloc/lock-elision candidate rates trended over releases), a soundness dashboard (unsound_classification_total, oracle-finding counts — expected flat zero), a performance dashboard (throughput, latency percentiles, fixpoint iteration distribution vs the I3 cap).

Alerting philosophy: an unsound classification found by the differential/dynamic oracle is a page-immediately correctness event, treated with the same severity as a production memory-corruption bug, because that is precisely what a false NoEscape becomes once the optimizer acts on it. A precision regression (fraction NoEscape dropping) is a build-blocking CI failure, not a page. A perf-target miss is a release-blocking CI failure, not a page.

SLOs: soundness SLO — zero unsound classifications, measured continuously via CI and (where deployed) production canary sampling; precision SLO — NoEscape fraction ≥35% on the reference corpus, measured per release; latency SLO — p99 per-method analysis ≤4ms (§4), measured continuously.

Incident response: any soundness-oracle finding triggers the soundness-violation-response runbook immediately, regardless of triggering phase (baseline classifier, summary engine, or partial-escape refinement). A fixpoint non-convergence alarm triggers fixpoint-nonconvergence-triage. A payoff-metric drop triggers precision-regression. A cache staleness spike triggers summary-cache-invalidation.

Named runbooks under docs/runbooks/: soundness-violation-response.md, fixpoint-nonconvergence-triage.md, precision-regression.md, summary-cache-invalidation.md.

Backup/restore: the summary cache is the only stateful, persisted artifact of consequence; back up via its content-addressed on-disk format (trivially reproducible from source IR if lost — the cache is an optimization, not a source of truth, so "restore" in the worst case is "recompute").

Deployment topology: embedded library within an optimizing-compiler pipeline (primary), or a standalone CLI driver invocation for benchmarking/conformance (secondary) — no long-running daemon topology in the default deployment model.

Canary/rollback/migration: a new release is canaried against the full differential/soundness/precision CI gate before promotion (§29); rollback is a version pin back to the last soundness-gate-passed release; migration between summary-cache schema versions goes through explicit version negotiation (§27), never silent reinterpretation.

27. Compatibility & Versioning

IR-interface versioning: the IR Reader's accepted IR schema is versioned independently of the analysis engine's internal representation; a new IR schema version requires an explicit compatibility-matrix entry before the engine accepts it.

Summary format and cache compatibility: MethodSummary's serialized format is versioned (ADR-15); a cache populated under an old schema version is either migrated via explicit tooling or fully invalidated on version bump — never silently reinterpreted as the new schema.

Optimization-facts interface stability: OptimizationFacts (ADR-17) is the externally consumed contract for the optimizer and for Deoptimization-Engine 246's scalar-replacement rematerialization path; it follows SemVer independently of the internal connection-graph/summary representations, so internal refactors never force a consumer-side change unless the fact schema itself changes.

Context-sensitivity configuration: the optional 1-CFA extension (ADR-06) is a configuration-level opt-in, versioned separately so a compilation unit analyzed context-insensitively and one analyzed with 1-CFA can coexist within the same release without a schema conflict (both produce the same OptimizationFacts shape, differing only in precision).

API stability: public trait boundaries (TransferFn, the OptimizationFacts emitter API) are stable within a major version; breaking changes require a major version bump and a documented migration path.

Migration: summary-cache and IR-schema migrations ship as explicit tooling in tools/, never as implicit best-effort reinterpretation.

Deprecation: a minimum of two minor versions' notice before removing a public API or a schema field, matching the project's SemVer policy (ADR-29's licensing stance and general engineering conservatism extend here).

SemVer: patch versions fix bugs with no interface change; minor versions add optimization-fact fields or precision features additively; major versions may change the OptimizationFacts schema or drop deprecated fields.

28. Testing & Verification Strategy

Unit: per-transfer-function correctness (Phase 2), per-classifier-rule correctness (Phase 3), tied to I2 (monotonicity) and I1 (soundness contract) at the smallest testable granularity.

Integration: full intraprocedural-to-interprocedural pipeline runs against the accumulated Phase 0-11 conformance corpus, tied to I5 (summary soundness) and I10 (virtual-dispatch join correctness).

Property: for every program in the corpus, no object the analysis calls NoEscape is ever reachable after its method returns, checked by the instrumented dynamic oracle (I1) — the central property test of the whole project. The lattice transfer functions are monotone (I2), property-tested exhaustively over the 9-pair join table (Phase 0). The fixpoint terminates within the I3 bound (Phase 2). A more-context-sensitive run (1-CFA, ADR-06) is never less precise than the context-insensitive baseline for the same program (Phase 6).

Soundness oracle as a named CI gate: the dynamic differential oracle (Phase 11) instruments a reference interpreter to record actual object lifetimes and thread-sharing, asserting no NoEscape object actually escaped and no elided lock's target was actually accessed cross-thread — this is soundness.yml's core job (ADR-25), gating every release per I11.

Differential: against HotSpot's and Go's escape-analysis decisions on a shared corpus subset (Phase 11), reporting agreement rate and classifying every disagreement by relative conservatism, tied to I1 and the T3/T5 threat entries.

Fuzzing: the IR parser (Phase 0, ADR-24) and a random-valid-program generator exercising the full pipeline end-to-end against the soundness oracle (Phase 11), searching for I1/I7/I12-class violations specifically.

Chaos: forced worker/analysis-process crashes mid-summary-computation, verifying the summary cache recovers cleanly (RTO target, §4) without serving a partially-written summary.

Deterministic replay: I13's non-determinism fuzz target (Phase 2) — same input, two runs, bit-identical output graphs and iteration counts.

Soak: long-running analysis of a large synthetic corpus (Phase 11's large-scale fixture) checking for memory growth beyond the §4 connection-graph and summary-cache ceilings over sustained operation.

Fault injection: malformed IR injection (Phase 0 fixtures), corrupted summary-cache entries (FM-3), and native-callee-heavy modules (T2) injected deliberately to verify the conservative-default paths (I4) actually trigger rather than silently mis-handling the input.

Precision benchmark with a floor: fraction of allocations optimized must not regress below the §4/§30 targets on any release candidate (Phase 11), a CI gate distinct from the soundness gate, tied to FM-8.

Perf-regression gating: compile-time overhead (§4 target ≤8%) gated per release (Phase 11, §30).

29. Build & Release Engineering

Reproducible builds: pinned Cargo.lock (ADR-28), deterministic fixpoint iteration order (I13) ensures not just build reproducibility but analysis-output reproducibility across identical source+input pairs.

Artifact signing: release artifacts signed via cosign-equivalent tooling before publication (mirroring ADR-30's supply-chain posture); signatures verified by consumers (the optimizer pipeline, 246) before trusting a new engine version.

SBOM: generated per release (ADR-30), covering the full crate dependency graph across all /crates/* workspace members.

Release channels: nightly (unstable, soundness-oracle run but not release-gated), rc (candidate, full gate run required), stable (soundness-gate-passed, tagged, SemVer-versioned per §27).

The soundness-oracle and precision-benchmark jobs (Phase 11) are hard gates on the rc→stable promotion path; no override mechanism exists for a failing soundness gate (I11).

31. Scalability Analysis

What stays constant: per-method connection-graph construction cost (bounded by method size, not corpus size); the escape lattice's 3-point height (never grows regardless of program size).

What grows, with Big-O: points-to analysis is famously expensive — Andersen-style inclusion-based points-to (ADR-03) is roughly cubic in the worst case in program size, while Steensgaard-style unification-based points-to is near-linear but less precise (Hind 2001's central tradeoff, named in ADR-03's rationale); context sensitivity is exponential in the worst case as k in k-CFA grows (ADR-06's reason for defaulting to context-insensitive); interprocedural summaries (ADR-05, Phase 5) keep whole-program cost roughly linear in method count instead of the naive re-analysis blowup that is exponential in call-site fan-out; connection-graph size per method grows with allocation count × field count, independent of whole-program size.

Named bottlenecks: virtual-dispatch target-set fan-out before RTA pruning (Phase 4); summary-cache lookup cost at scale (2,000,000-summary ceiling, §4); edge-arena churn on field-access-heavy methods (Phase 1); SCC-local fixpoint iteration count on large mutual-recursion clusters (Phase 5).

The precision-vs-scalability tradeoff (Hind 2001's central framing of the pointer-analysis field): more precision (field sensitivity, context sensitivity, Andersen-style inclusion) costs more compute; this project's ADR table (§9) resolves the tradeoff per-decision rather than picking one extreme uniformly — field-sensitive by default (cheap enough, required for I6), context-insensitive by default (context sensitivity's cost curve is too steep for a default), Andersen-style points-to by default (precision matters more than raw speed at the intraprocedural scale this project operates at, per ADR-03).

Whole-program vs modular analysis at scale: this project is modular by design (per-method summaries composed bottom-up, ADR-05) rather than a single whole-program points-to solve — the modular design is precisely what keeps Andersen-style precision tractable at all, per Whaley & Rinard 1999's compositional framing.

Practical ceilings and levers beyond them: call-graph depth beyond ~500 levels (M10) risks non-iterative-traversal bugs resurfacing even with iterative SCC decomposition — the lever is increasing the explicit stack/queue depth bound, not algorithmic change. Context depth beyond 1-CFA (k>1) is not supported by default (ADR-06) — the lever, if ever needed, is selectively enabling higher k only on a hand-identified hot method subset, never globally. Summary-cache size beyond 2,000,000 entries (§4) is addressed by LRU-style eviction keyed on recency of incremental-build touch, not by raising the ceiling indefinitely.

32. Mental Models & First Principles

  • MM1. Escape analysis is reachability from a root set — an object escapes iff it is reachable from a global root or an unknown callee when its method returns, so it is a graph-reachability problem dressed as an optimization (Choi et al. 1999).
  • MM2. Soundness is one-directional: the analysis must err toward "escapes," because the cost of a false "captured" is a memory-corruption-class miscompilation while the cost of a false "escapes" is only a missed optimization — this asymmetry, not a balanced accuracy target, is what shapes every design decision in §6 and §9.
  • MM3. Partial escape analysis (GraalVM) is the insight that escape is per-path, not per-object — an object can be captured on the fast path and materialized only on the slow branch that leaks it, which is a strictly more precise model than the classic connection graph's one-state-per-object assumption.
  • MM4. A method summary is a compressed, reusable answer to "what does this method do to its arguments' escape state," and interprocedural analysis at scale is fundamentally about avoiding re-deriving that answer at every call site (Whaley & Rinard 1999).
  • MM5. The escape lattice's monotonicity is not an implementation convenience — it is the mathematical property that makes fixpoint termination provable at all (Cousot & Cousot 1977's abstract-interpretation framework), and every transfer function is a proof obligation, not just a code path.
  • MM6. Points-to precision and analysis scalability are in permanent tension (Hind 2001) — there is no single "correct" point on that curve, only a point appropriate to a given compile-time budget, which is why this project's ADR table treats the tradeoff as a per-decision resolution, not a single global setting.
  • MM7. A connection graph is simultaneously a points-to structure and an escape-tracking structure — treating them as separable concerns (as the rejected points-to-then-escape ADR-02 alternative does) loses the incremental-update efficiency that unifying them provides.
  • MM8. Deoptimization and escape analysis are two ends of the same optimization: escape analysis licenses an optimistic transformation (scalar replacement), and deoptimization is the safety valve that undoes it when a speculative assumption elsewhere breaks (Kotzmann & Mössenböck 2005) — neither makes sense in isolation from the other.

HotSpot's C2 escape analysis is the production reference implementation of the Choi connection-graph design this project's Phase 1-3 directly follows; its escape.cpp demonstrates SCC-based iteration ordering in a real, performance-constrained JIT context, and its known conservatism gaps around unresolved virtual dispatch are exactly what this project's ADR-10/ADR-11 RTA-refinement design is built to reduce.

GraalVM's partial escape analysis is the key contrast this blueprint names repeatedly (§8, Phase 10, MM3): it demonstrates that the classic connection-graph's one-state-per-object assumption is a real precision ceiling, not a fundamental limit of static escape analysis, by tracking escape state per control-flow path and deferring materialization to the exact point of observability.

The Go compiler's escape analysis takes the opposite design point from GraalVM: an ahead-of-time, non-JIT, whole-package analysis with no partial-escape refinement, optimized for compile-speed and predictability over maximum precision — a legitimate, deliberately simpler design point named in §5 and §36 as a real alternative architecture, not a lesser one.

Choi et al.'s original research prototype is the historical origin of the connection-graph abstraction this entire project is built on; its bottom-up interprocedural treatment (refined by the 2003 TOPLAS journal version) is the direct ancestor of this project's Phase 5 summary-engine design, predating and complementing Whaley & Rinard's independently-published compositional approach.

34. Back-of-Envelope Capacity Model

  1. Connection-graph size per method: assume an average method has 8 allocations, 20 SSA references, and 4 fields per allocated object → nodes = 8 (objects) + 20 (refs) + 8×4 (fields) = 60 nodes; edges ≈ 1.5× node count (points-to + field + deferred edges) ≈ 90 edges. Per §4/M6/M7: memory ≈ 60×200B + 90×120B = 12,000B + 10,800B ≈ 22.8 KB per average method, well under the 64 KB median-method target.

  2. Fixpoint cost per method: nodes (60) × lattice height (3) × iteration bound (3, per I3's "3× height" cap) = 540 transfer-function applications worst case; in practice (Phase 2's worked example converges in 2 iterations for a 1-object graph) real convergence is far below the worst-case bound.

  3. Interprocedural cost with summaries: for a 100,000-method program, per-method analysis (Phase 2/3, ~540 transfer applications worst case) plus one summary computation per method (Phase 5, bounded by parameter count × field-sensitivity granularity, say ≤50 "effect units" per summary) → total ≈ 100,000 × (540 + 50) ≈ 59,000,000 units of work, roughly linear in method count.

  4. Interprocedural cost without summaries (the rejected re-analysis-per-call-site alternative, ADR-05): assume an average fan-in of 20 call sites per method → re-analyzing each callee at each call site multiplies cost by fan-in: 100,000 × 540 × 20 ≈ 1,080,000,000 units — roughly 18x the summary-based cost, demonstrating ADR-05's rationale quantitatively.

  5. Points-to precision/cost curve: context-insensitive analysis of the 100,000-method program is the ~59,000,000-unit baseline above; naive k=2-CFA context sensitivity multiplies the effective "virtual method count" by the number of distinct calling contexts per method — assuming an average of 10 distinct 2-deep call-string contexts per method, cost grows to ≈590,000,000 units, illustrating MM6/§31's exponential-in-k warning even at a modest k.

  6. Payoff calculation: assume the 100,000-method program allocates at a rate of 50 allocations/method on average (5,000,000 total allocations), of which the §4 target of ≥35% are classified NoEscape (1,750,000 allocations); assume each avoided heap allocation saves an estimated 40ns of allocator overhead plus an amortized 15ns of GC-pressure cost (100ns total, a representative managed-runtime figure) → total saved ≈ 1,750,000 × 100ns ≈ 175 milliseconds of aggregate allocator/GC time per full-program execution pass — the concrete "payoff" the M11 target exists to protect.

  7. Summary-cache memory: 100,000 methods × ≤512 bytes/summary (M8) = ≤51.2 MB total cache size for the full program, comfortably under the 2,000,000-summary/§4 capacity ceiling (which supports programs up to roughly 20x this size before eviction pressure begins).

  8. Compile-time overhead: assume a baseline optimizing-compiler pass takes 500ms for the 100,000-method program; the M12 target (≤8% overhead) bounds this analysis pass to ≤40ms for the same program — consistent with the M1 throughput target (≥8,000 methods/sec → 100,000 methods in ≈12.5 seconds worst case per-method-latency-bound, but summary caching and sparse propagation bring the steady-state incremental cost, not full recompute, down to the 40ms figure for typical incremental compiles).

36. Alternative Architectures (Roads Not Taken)

A1. Type-based escape analysis (Blanchet) vs the connection-graph approach

  [Blanchet type-based]              [This project: connection graph]
  types carry escape info    vs      per-object graph nodes + edges
  near-linear propagation            precise but graph-maintenance-heavy
  coarser (type-granularity)         field/object-granularity precision

Winning regime: a JIT with a hard, small per-method compile-time budget where near-linear type-based propagation is required and coarser precision is an acceptable tradeoff. Real embodying system: Blanchet's own OOPSLA 1999/2003 implementation, designed explicitly for that budget. Rejected here because this project's stated payoff target (§4, M11, ≥35% NoEscape) needs field/object-granularity precision that a purely type-based lattice under-delivers on, per Blanchet's own reported precision numbers relative to connection-graph approaches.

A2. Unification-based points-to (Steensgaard) vs inclusion-based (Andersen)

  [Steensgaard: unification]         [This project: Andersen inclusion]
  near-linear, coarser sets   vs      cubic worst-case, precise sets
  merges aliasing eagerly            preserves directional flow precisely

Winning regime: a whole-program, compile-time-constrained ahead-of-time compiler (e.g., embedded/mobile AOT backends) where near-linear scaling outweighs precision loss, exactly as named in ADR-03's sixth column. Real embodying system: Steensgaard's own POPL 1996 implementation and its descendants in several production AOT toolchains. Rejected here because I6's field-alias-free soundness check for scalar replacement (Phase 7) needs Andersen-level directional precision to avoid over-rejecting valid candidates.

A3. Intraprocedural-only analysis vs full interprocedural

  [Intraprocedural-only]             [This project: full interprocedural]
  fast, per-method only       vs      bottom-up summaries (Phase 5)
  misses cross-method capture         captures the §8 store/run example

Winning regime: a debug/non-optimizing build tier where compile speed dominates and missed cross-method optimizations are an acceptable cost, matching ADR-04's sixth column exactly. Real embodying system: many JIT compilers' lowest optimization tier runs escape analysis intraprocedurally-only or skips it entirely for this reason. Rejected as this project's default because the §8 worked two-method example demonstrates the majority of real-world NoEscape wins are specifically cross-method.

A4. Partial escape analysis (GraalVM) as a fundamentally more precise baseline model

  [Whole-object baseline]            [Partial/path-sensitive, as default]
  one state per object         vs    state varies per control-flow path
  simpler, this project's floor      strictly more precise, higher cost

Winning regime: a JIT with aggressive inlining and a compile-time budget that can absorb path-sensitive bookkeeping across a large inlined region — GraalVM's actual production regime. Real embodying system: GraalVM's Graal compiler. Rejected as this project's default baseline (though included additively in Phase 10, gated by I12) because a from-scratch project's first soundness obligation is a provably correct whole-object baseline; path-sensitivity is layered on afterward specifically so a partial-escape bug can never regress below that already-proven baseline (I12's entire reason for existing).

38. Glossary

Abstract interpretation — the theoretical framework (Cousot & Cousot 1977) underpinning sound approximation of program behavior, of which escape analysis is an instance.

Actual-to-formal mapping — substituting a call site's actual arguments into a callee summary's formal-parameter effects (Phase 6).

Allocation site — the specific new/alloc IR statement instantiating an object, the unit of escape classification.

Andersen-style points-to — inclusion-based points-to analysis, precise but worst-case cubic (ADR-03).

ArgEscape — the middle escape-lattice state: escapes the allocating method (e.g., via return or an outgoing parameter) but not globally.

Bottom-up interprocedural analysis — computing callee summaries before caller summaries, traversing the call graph's SCCs in reverse topological order (Whaley & Rinard 1999).

Call graph — the directed graph of methods and call edges, including resolved virtual-dispatch targets.

Call-string approach — an interprocedural analysis strategy distinguishing calling contexts by the sequence of call sites (Sharir & Pnueli 1981), contrasted with the functional approach.

Capture / captured — an object confined to its allocating stack frame; the analysis's NoEscape verdict in informal terms.

CHA (Class Hierarchy Analysis) — a coarse virtual-dispatch resolution strategy using only the static type hierarchy.

Classifier — the component assigning final EscapeState values from a converged connection graph (Phase 3).

Connection graph — the Choi et al. 1999 abstraction unifying points-to and escape tracking via object, reference, and field nodes plus points-to/field/deferred edges.

Context sensitivity — distinguishing analysis results by calling context (e.g., 1-CFA), a precision/cost lever (ADR-06).

Deferred edge — a connection-graph edge between two reference nodes representing a not-yet-resolved points-to-set copy relationship.

Escape — an object being reachable after its allocating method returns, stored globally, passed to an unknown callee, or shared across threads.

Escape analysis — the compiler pass computing, per allocation, whether it escapes or is captured.

Escape lattice — the three-point monotone lattice NoEscape ⊑ ArgEscape ⊑ GlobalEscape.

Field edge — a connection-graph edge from an object's field node to another object node.

Field node — a connection-graph node representing a specific field of a specific abstract object (field sensitivity's unit).

Field sensitivity — tracking each field of an object distinctly rather than merging all fields into one node (ADR-07).

Fixpoint — the stable state reached when no further transfer-function application changes any node's escape state.

Flow sensitivity — whether analysis results depend on statement order within a method (ADR-08).

GlobalEscape — the top escape-lattice state: reachable from a global root or an unknown/native callee.

Inclusion-based points-to — see Andersen-style points-to.

Interprocedural analysis — analysis spanning multiple methods via the call graph, as opposed to intraprocedural (single-method) analysis.

Join (⊔) — the lattice least-upper-bound operation, the only lattice operation this analysis' transfer functions use (states only move up).

k-CFA — k-deep call-string context sensitivity; k=1 is this project's optional extension (ADR-06).

Lattice — a partially ordered set with join/meet, here the three-point escape lattice.

Lock elision — removing synchronization on a provably thread-confined object (Phase 9).

Materialization — in partial escape analysis, the point where a virtually-tracked object is converted back into a real heap object because it becomes observable on a specific control-flow path.

Method summary — a compact, reusable abstraction of a method's escape effect on its parameters and return value (Phase 5).

Monotone / monotonicity — the property that escape-lattice transitions only move upward, never downward (I2).

NoEscape — the bottom escape-lattice state: provably confined to the allocating stack frame.

Object node — a connection-graph node representing an abstract allocation site.

Object sensitivity — a context-sensitivity variant keyed by receiver-object abstraction rather than call string.

OptimizationFacts — the versioned external interface (ADR-17) carrying scalar-replacement, stack-allocation, and lock-elision facts to the optimizer and Deoptimization-Engine 246.

Partial escape analysis — GraalVM's branch/path-sensitive refinement of the whole-object escape model (Phase 10).

Points-to analysis — the general static-analysis family computing which memory locations a reference may point to.

Points-to edge — a connection-graph edge from a reference node to an object node.

Precision — how close an analysis's approximation is to the true (dynamic) behavior, as opposed to soundness (never wrong in the unsafe direction).

Reference node — a connection-graph node representing an SSA value that may hold a reference.

RTA (Rapid Type Analysis) — a virtual-dispatch refinement over CHA using only actually-instantiated types.

Scalar replacement — replacing an aggregate object's fields with independent scalar SSA values, eliminating the object entirely (Phase 7).

SCC (strongly connected component) — a maximal set of mutually reachable call-graph nodes, requiring local fixpoint treatment for mutual recursion (Phase 5).

Soundness — the guarantee that the analysis never mis-classifies an escaping object as captured (the one-directional correctness property, I1).

SSA (Static Single Assignment) — the IR form this pass assumes, in which every value has exactly one defining statement.

Stack allocation — allocating a NoEscape object on the stack frame instead of the heap (Phase 8).

Steensgaard-style points-to — unification-based points-to analysis, near-linear but coarser than Andersen-style (ADR-03).

Summary cache — the persistent, content-hash-keyed store of computed method summaries (ADR-15).

Thread confinement — the property that an object is never observable outside a single confining thread context, the precondition for lock elision (I7).

Transfer function — the per-statement function updating the connection graph and escape state during the intraprocedural fixpoint (Phase 2).

Type-based escape analysis — Blanchet's alternative approach encoding escape information in the type system rather than a per-object graph.

Unification-based points-to — see Steensgaard-style points-to.

Virtual dispatch — a call site whose target method depends on a runtime receiver type, requiring call-graph resolution (CHA/RTA/points-to-refined).

Worklist — the fixpoint solver's queue of nodes pending transfer-function reapplication.
