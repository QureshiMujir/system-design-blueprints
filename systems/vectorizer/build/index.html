⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the workspace (§10), CI (ci.yml), governance files, and the two crates every later phase depends on: vec-ir (host-IR adapter) and vec-interp (scalar reference interpreter — the correctness oracle, P12). No vectorization logic yet; this phase proves the harness that every later phase's fixtures run through.

Deliverable

A workspace that builds, a vec-interp that correctly executes the 30-kernel Polybench-analog corpus (§10, examples/) and matches recorded expected outputs, and a green CI badge.

Acceptance

cargo build --workspace exits 0; cargo test --workspace passes 100%; vec-interp matches expected output on all 30 corpus kernels bit-exact for integer kernels and within 1 ULP for floating-point kernels; CI wall-clock ≤ 5 minutes.

Fixtures

fixtures/interp/gemm.vecfix — dense matrix multiply, expected output recorded; fixtures/interp/saxpy.vecfix — vector scale-add; fixtures/interp/reduction_sum.vecfix — accumulator reduction; fixtures/interp/malformed_ir.vecfix — intentionally malformed IR (dangling SSA use), expected: vec-ir returns Err(IrError::DanglingUse), not a panic.

Pitfalls

Treating vec-interp as "good enough if it compiles" — it must be independently authored from the vectorizer's own mental model of semantics, or it stops being an oracle (P12). Letting vec-ir leak #143-internal types into public signatures, which locks every later crate to #143's internal versioning.

⬜ Phase 1 — Loop Selection & Stride Analysis §13

Objectives

Implement innermost-first loop iteration and per-access stride classification (StrideKind, §8.1), the first analysis stage in the pipeline (§3).

Deliverable

A StrideKind classification for every memory access in a loop body, and an innermost- first loop worklist consumable by Phase 2.

Acceptance

100% of the stride/ conformance bucket's 12 named fixtures classify correctly; stride analysis on a 1,000-iteration loop body completes in ≤ 10 ms p50, ≤ 30 ms p99 (§4, M2); a nested-loop fixture visits the inner loop strictly before the outer.

Fixtures

stride/unit_f32.vecfix — a[i], expect Constant(4); stride/unit_f64.vecfix — expect Constant(8); stride/linear_2i.vecfix — a[2*i], expect Linear{step=2*elem}; stride/indirect.vecfix — a[b[i]], expect Unknown; stride/nested_inner_first.vecfix — asserts visitation order.

Pitfalls

A pointer-arithmetic expression i * sizeof(T) folded by an earlier constant-folding pass may present as Constant(sizeof(T)) directly — the analysis must not require seeing the multiply syntactically, only the SCEV AddRec's resolved step. A stride expression that is loop-invariant in an outer loop but varies in the inner loop must be classified relative to the loop currently being analyzed, not the whole nest.

⬜ Phase 2 — Dependence Analysis §14

Objectives

Implement the GCD → Banerjee → Omega ladder (P4, ADR-04) producing a DependenceGraph (§8.2, §11) — the prerequisite fact for legality (§3.1).

Deliverable

A DependenceGraph for any loop body, with every edge's resolving test recorded (DepTest::{Gcd,Banerjee,Omega}) for diagnostics and calibration.

Acceptance

The deps/ bucket's 15 fixtures (including the canonical Banerjee and Omega textbook examples) resolve to the expected DependenceKind/DirectionVector/DistanceVector; analysis on a 1,000-iteration loop with 20 memory ops completes in ≤ 50 ms p50, ≤ 100 ms p99 (§4, M1); Banerjee and Omega agree on every fixture where both are computable.

Fixtures

deps/raw_distance_3.vecfix — a[i] = a[i-3] + 1, expect True, Θ=(<), Δ=(3); deps/backward_blocks.vecfix — a[i] = a[i+1], expect Θ=(>) (I2 must reject downstream); deps/gcd_no_dep.vecfix — a[2*i] = a[2*i+1], GCD resolves "no dependence" without reaching Banerjee; deps/omega_exact.vecfix — a subscript pattern where Banerjee reports "maybe" and Omega resolves exactly; deps/non_affine.vecfix — a[b[i]], expect conservative "assume dependence."

Pitfalls

Treating a Banerjee "maybe" as "no dependence" (must fall through to Omega, never silently optimistic — I2's soundness depends on this). Forgetting that a same-iteration dependence (Δ=0) is always safe regardless of direction. Running Omega on every pair regardless of Banerjee's verdict, blowing the p99 budget (§4) on deep nests.

⬜ Phase 3 — Legality Check §15

Objectives

Implement vec-legality::check_legality (§11), the trust boundary (§3) that produces the single LegalityVerdict every downstream stage trusts without re-verification (P1, I8).

Deliverable

A LegalityVerdict for every candidate loop, with LegalityHints{max_vf, stride_pattern, needs_runtime_alias_check, needs_masking, reductions} populated on the Legal path.

Acceptance

The legality/ bucket's 18 fixtures each produce the exact expected IllegalReason variant or Legal hints; check completes in ≤ 50 ms p50, ≤ 100 ms p99 on a 1,000- iteration loop (§4, M3); zero fixtures produce a bare/unnamed illegal verdict (I14).

Fixtures

legality/negative_distance.vecfix — expects Illegal{NegativeDistanceDep(edge)}; legality/unguarded_div.vecfix — expects Illegal{ExceptionPossible(instr)}; legality/fp_reduction_no_fastmath.vecfix — expects Illegal{UnsupportedReduction} without the flag, Legal with it; legality/unmarked_call.vecfix — expects Illegal{SideEffectInBody}; legality/max_vf_from_distance.vecfix — distance-4 dependence, expects Legal{hints.max_vf = 4}.

Pitfalls

Treating a positive-distance dependence as unconditionally legal at any VF — max_vf must be clamped to the distance (§8.2's worked example contrast, §8.7's malformed-input example). Forgetting that a same-iteration (distance = 0) true dependence is always legal and must not be conflated with a genuine loop-carried hazard. Marking a reduction legal without checking the specific operation is in the supported set (add/mul/min/ max/and/or/xor for integer; add/mul only, fast-math-gated, for float).

⬜ Phase 4 — Cost Model & VF Selection §16

Objectives

Implement the CostModel trait and target impls (vec-cost-x86, vec-cost-aarch64) and select_vf (§11), the profitability half of P1's split.

Deliverable

A chosen VF (or None if no candidate beats the margin) per legal loop, with the full per-candidate cost table retained for diagnostics.

Acceptance

The cost/ bucket's 14 fixtures (one per characteristic pattern per target) select the expected VF; cost computation per candidate plan completes in ≤ 10 ms p50, ≤ 30 ms p99 (§4, M4); on the examples/ corpus, ≥ 70% of legal loops receive a non-None VF (M10).

Fixtures

cost/avx512_max_vf16.vecfix — dense f32 unit-stride, expects VF 16; cost/register_ pressure_clamped.vecfix — 20 live vector temporaries on a 32-register target, expects a narrower VF than the naive maximum (I11); cost/unprofitable_small_trip.vecfix — trip count 3, expects None (VF overhead exceeds benefit); cost/gather_penalty.vecfix — non-affine stride, expects gather cost pushes VF selection down or to None.

Pitfalls

Calibrating cost tables against a single microarchitecture and silently assuming portability across a whole ISA family (AVX2 on a 2013-era part vs. a 2023-era part have materially different real-world throughput) — recalibrate per generation, don't extrapolate. Letting the 5% profitability margin drift to 0% (any-positive-margin "profitable"), which lets measurement noise flip vectorization decisions nondeterministically across otherwise-identical builds.

⬜ Phase 5 — VPlan Construction & Loop Transform §17

Objectives

Implement vec-vplan::build_vplan and vec-loop's strip-mining transform (§8.3, P2, ADR-03) — the first stage that mutates the host IR, and only on a costed, chosen VF.

Deliverable

A transformed function with a vector-body main loop plus a scalar epilog loop, verified to preserve the original loop's exit conditions and side-effect ordering.

Acceptance

The loop/ bucket's 16 fixtures pass differentially against vec-interp (I1); the epilog/ bucket's 8 fixtures (each a distinct trip-count-mod-VF remainder, 0 through VF-1) produce exactly the expected epilog trip count (I4); transform completes in ≤ 200 ms p50, ≤ 500 ms p99 per loop (§4, M5).

Fixtures

loop/saxpy_vf8.vecfix — differential match required; loop/reduction_sum_f32_ fastmath.vecfix — partial-sum reduction, tolerance-bounded differential match; epilog/remainder_0.vecfix — trip count exact multiple of VF, expect empty epilog; epilog/remainder_vf_minus_1.vecfix — worst-case remainder, expect epilog trip count = VF−1 exactly (I4).

Pitfalls

Adjusting the loop bound with an off-by-one (n - (n mod VF) vs. n - (n mod VF) - 1) — the single most common bug class in this phase (§29 Pitfall #8 analog, FM-2). Failing to broadcast a reduction's initial value correctly when the initial value is not the operation's identity element (e.g. acc = 10; acc += a[i] needs a broadcast of 10 only into lane 0, identity 0 into the rest, or an equivalent post-combine correction). Emitting the vector body before verifying every phi's incoming edges are consistently widened.

⬜ Phase 6 — Runtime Alias Checks & Epilog Hardening §18

Objectives

Implement vec-alias-check (P8, ADR-08) — inserting a runtime disjointness guard with scalar fallback exactly when hints.needs_runtime_alias_check is set — and harden vec-epilog's remainder handling against the edge cases surfaced in Phase 5.

Deliverable

A guarded vector loop: if no_overlap(ranges) { vector_loop() } else { scalar_loop() }, plus the standing epilog loop on the disjoint-proven branch, both differentially verified.

Acceptance

The alias-check/ bucket's 10 fixtures (5 provably-disjoint requiring zero checks per I5, 5 requiring a check) match expected check-insertion exactly; inserter completes in ≤ 5 ms p50 per loop; runtime check overhead itself is ≤ 10 cycles measured via vec-bench on the reference target.

Fixtures

alias-check/disjoint_provable.vecfix — restrict-equivalent-annotated pointers, expect zero inserted checks (I5, P8); alias-check/overlap_forced.vecfix — same buffer passed as both input and output, expect scalar-fallback branch taken at runtime and differential match on both branches; alias-check/three_way.vecfix — three ranges pairwise checked, expect all three pairwise comparisons present.

Pitfalls

Inserting a check that compares the wrong range (e.g. [ptr, ptr+elem_size) instead of [ptr, ptr + trip_count*elem_size)) — produces either a false-negative (unsafe vector path taken despite real aliasing, a miscompile) or false-positive (unnecessary scalar fallback, a missed optimization). Both directions are covered by dedicated fixtures (§18.5) precisely because they're easy to get backwards.

⬜ Phase 7 — Masking, If-Conversion & Gather/Scatter §19

Objectives

Implement vec-mask::if_convert and lower_gather_scatter (§11) — predicated execution for control flow inside a vectorized loop, and gather/scatter lowering for non-affine access (§8.1, ADR-14, ADR-16).

Deliverable

A loop body with all data-dependent control flow converted to masked operations, and all non-affine memory access lowered to gather/scatter, both differentially verified.

Acceptance

The mask/ bucket's 12 fixtures produce bit-exact-matching masks against a reference scalar condition evaluation; masking transform completes in ≤ 50 ms p50 per loop (§4); zero fixtures in the bucket show a masked-off lane influencing output (I3).

Fixtures

mask/simple_guard.vecfix — if a[i] > 0 { b[i] = 1/a[i] }, expect masked reciprocal, masked-off lanes untouched in b; mask/nested_guard.vecfix — two nested conditions, expect mask conjunction; mask/gather_indirect.vecfix — c[i] = a[idx[i]], expect VPLoad{gather: true}; mask/scatter_indirect.vecfix — a[idx[i]] = c[i], expect VPStore{scatter: true}; mask/ssse_no_mask_support.vecfix — SSE2 target without native masked-load support, expect the cost model marks masking expensive enough to select a narrower VF or None (ADR-16 interaction with Phase 4).

Pitfalls

A masked store whose mask computation itself has a bug writes outside the intended lanes — silent memory corruption, the highest-severity bug class in this phase (I3, FM-6 analog). Conflating "if-conversion always helps" with the reality that some targets (older SSE) lack efficient masked-load support, making the cost model's role (§16) — not this phase's — the arbiter of whether masking is worthwhile at all.

⬜ Phase 8 — Superword-Level Parallelism (SLP) §20

Objectives

Implement vec-slp (§8.4, P9) — straight-line-code vectorization independent of any loop, run after loop vectorization per the fixed pipeline order (ADR-11).

Deliverable

A basic block with isomorphic scalar statement groups replaced by packed vector operations, differentially verified against the pre-transform scalar block.

Acceptance

The slp/ bucket's 10 fixtures (color-conversion and quaternion-arithmetic patterns) pack correctly; SLP analysis on a 1,000-statement basic block completes in ≤ 50 ms p50, ≤ 100 ms p99 (§4, M6); zero fixtures show a non-isomorphic tree incorrectly accepted.

Fixtures

slp/rgb_to_yuv.vecfix — the canonical 3-statement color-conversion seed pattern, expect a single packed 3-wide (or 4-wide with padding) vector op; slp/quaternion_ mul.vecfix — 4-component quaternion multiply, expect packing across the 4 independent component computations; slp/non_isomorphic_reject.vecfix — a tree with mismatched opcodes at one level, expect rejection (not a partial/incorrect pack); slp/cse_shared_value.vecfix — a common-subexpression-eliminated value used by two seeds, expect tree decomposition rather than a broken pack (§29 Pitfall #9 analog).

Pitfalls

Attempting to pack a tree where a value is used by multiple seeds (a DAG, not a tree) — must decompose or reject rather than silently duplicating computation incorrectly. Failing to reorder commutative operands before the isomorphism check, missing packable patterns that differ only in operand order (e.g. a+b vs b+a at the same tree level). Unbounded tree-search depth on a pathological basic block, blowing the performance budget (§20.7).

⬜ Phase 9 — Differential Verification & Fuzz Canary §21

Objectives

Implement vec-diff, vec-fuzz, and vec-bench (§11) — the semantics-preservation harness (I1, P12, ADR-13) and the sustained-execution fuzz canary (ADR-18) that gate release.

Deliverable

A green differential-llvm/ bucket, four running fuzz targets with recorded corpus growth, and a vec-bench report confirming M1–M12 performance targets.

Acceptance

100% agreement with LLVM LoopVectorize on the differential corpus modulo documented fast-math divergence (M10); fuzz targets sustain ≥ 5,000 exec/sec (M12-adjacent); the 24-hour CI fuzz gate finds 0 new crashes/mismatches before merge; the 30-day soak finds 0 panics before a release tag is cut.

Fixtures

differential-llvm/gemm_corpus.vecfix — full Polybench-analog gemm, cross-checked against opt -passes=loop-vectorize; fuzz/corpus/deps_seed_001 through _050 — seed corpus for the deps fuzz target; fuzz/corpus/differential_seed_001 through _020 — seed corpus biasing the fuzzer toward known-tricky patterns (non-affine subscripts, mixed-type reductions).

Pitfalls

Treating a fast-math-driven divergence from LLVM as a bug — must be classified and documented (both compilers reassociate differently at the bit level; only the presence or absence of reassociation under the flag is checked, not bit-for-bit reduction order). Under-resourcing the fuzz corpus's seed diversity, converging the fuzzer onto one code-pattern family and leaving whole classes (e.g. deeply nested loops) unexplored for months.
