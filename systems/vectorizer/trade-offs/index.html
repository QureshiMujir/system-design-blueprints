Decisions (§9) · 20 ADRs

ADR-01

Implementation language

Chosen

Rust 1.78+ MSRV

Rejected

C++ (LLVM-native); OCaml/Haskell

When the rejected choice is right

an in-tree LLVM patch where C++ is the only integration path

Why: exhaustive enum matching over ~40-variant IR families; no UB while mutating the IR graph

ADR-02

Vectorizer families

Chosen

Loop vectorizer + SLP vectorizer, separate crates

Rejected

Single unified VPlan-only framework

When the rejected choice is right

an embedded compiler with no loops at all, only straight-line kernels

Why: distinct opportunity classes (iteration- vs statement-parallel)

ADR-03

Staged intermediate

Chosen

Explicit VPlan IR, built once per candidate

Rejected

Direct-IR-mutation per candidate VF

When the rejected choice is right

a single-fixed-VF target where only one plan is ever built

Why: costs multiple plans before any mutation, no rollback needed

ADR-04

Dependence testing

Chosen

GCD → Banerjee → Omega ladder

Rejected

Omega-only (always exact)

When the rejected choice is right

an offline non-time-boxed super-optimizer where exactness dominates

Why: bounds p99 compile time; Omega is exponential worst case

ADR-05

Legality/profitability ordering

Chosen

Strict two-phase, no shared mutable state

Rejected

Interleaved single pass

When the rejected choice is right

an extremely tight JIT tier-1 budget where even phase-boundary allocation is measurable

Why: prevents a cost heuristic from also approving legality

ADR-06

Cost model dispatch

Chosen

dyn CostModel trait per target

Rejected

Single generic op-count heuristic

When the rejected choice is right

a portable bytecode target (Wasm SIMD baseline) with one abstract cost table

Why: AVX-512 vs NEON have materially different latency/throughput/pressure profiles

ADR-07

Initial hardware targets

Chosen

x86-64 (SSE2/AVX2/AVX-512) + aarch64 NEON

Rejected

RISC-V V extension (scalable vector length) day one

When the rejected choice is right

an HPC/cloud target where RVV/SVE support is the entire point

Why: RVV's VLA model needs a different VF-selection algorithm; deferred

ADR-08

Runtime alias checks

Chosen

Inserted only when static AA returns Unknown

Rejected

Always insert unconditionally

When the rejected choice is right

a JIT with no static AA budget at all

Why: avoids branch+check cost on provably-disjoint arrays

ADR-09

Tail handling

Chosen

Scalar epilog loop for n mod VF remainder

Rejected

Fold tail into one masked final iteration

When the rejected choice is right

AVX-512/SVE targets where masking is cheap and merging removes a branch

Why: on masking-poor targets (SSE2) scalar epilog beats mask overhead

ADR-10

FP reduction legality

Chosen

Rejected

When the rejected choice is right

an ML training loop where bit-exact reproducibility is already abandoned

Why: silent reassociation is a correctness surprise for numerical users

ADR-11

Pipeline ordering

Chosen

Rejected

SLP-first ordering

When the rejected choice is right

a loop-free kernel body where ordering is moot

ADR-12

Chosen

ADR-13

ADR-14

Non-unit-stride handling

Chosen

Gather/scatter lowering, cost-penalized

ADR-15

Register pressure

Chosen

Rejected

ADR-16

ADR-17

Fuzzing cadence

34. Alternative Architectures (Roads Not Taken)

A1 — Polyhedral whole-nest scheduling (Polly-style).

┌─────────────────────────────────────────────┐
│ Loop nest → affine iteration-domain polytope │
│  → ISL exact dependence + legal schedule set │
│  → chosen schedule (fusion/tiling/vec/interchange) │
└─────────────────────────────────────────────┘

Regime where it wins: regular, affine-bounded numerical kernels (dense linear algebra, stencils) where loop-interchange/fusion/tiling opportunities dominate simple vectorization gains. Real system: Polly (LLVM). Rejected here: exact polyhedral scheduling is exponential in nest depth in the worst case and requires the entire nest to be affine — this design's scope (§1) is deliberately narrower (single innermost loop + SLP) to stay within the compile-time budget (§4) for the general, not-necessarily-affine case.

A2 — Explicit SPMD source-level model (ISPC-style).

┌───────────────────────────────────────────┐
│ Source: foreach(i in 0..n) { ... }         │
│  → programmer states independence directly │
│  → compiler emits SIMD with zero dep. proof │
└───────────────────────────────────────────┘

Regime where it wins: performance-engineering teams already thinking in explicit- parallel terms (graphics, ray tracing) who accept a language-level contract in exchange for zero dependence-analysis compile-time cost and zero risk of an overly-conservative legality rejection. Real system: ISPC. Rejected here: this pass targets existing scalar code with no independence contract — proving legality automatically is the whole point (§1's problem statement).

A3 — Schedule-separated-from-algorithm (Halide-style).

┌────────────────────────────────────────────┐
│ Algorithm (what to compute) — pure, no VF   │
│ Schedule (how: vectorize/tile/unroll) — separate, explicit │
│  → compiler composes the two independently  │
└────────────────────────────────────────────┘

Regime where it wins: image-processing/tensor pipelines where the same algorithm needs many different hand-tuned schedules across targets, and expert-authored schedules consistently beat any automatic cost model. Real system: Halide. Rejected here: this design targets automatic vectorization of pre-existing scalar code with no separate schedule language — introducing one would shift the entire project's scope from a compiler pass to a DSL.

A4 — SIMT/GPU data-parallel model instead of SIMD.

┌─────────────────────────────────────────┐
│ Each loop iteration → one GPU thread     │
│  → massive over-subscription hides latency│
│  → no vector-register-width ceiling at all│
└─────────────────────────────────────────┘

Regime where it wins: workloads with enough independent parallelism to amortize kernel- launch/transfer overhead and hide memory latency via thread over-subscription rather than a fixed VF ceiling. Real system: CUDA/PTX (NVIDIA GPUs). Rejected here: this design targets CPU middle-end code generation with no host-device transfer model, no kernel- launch overhead accounting, and no thousands-of-threads scheduling model — a fundamentally different execution substrate than the SIMD lanes assumed throughout (§4).
