147 — Vectorizer / Auto-SIMD Pass

Project Number: 147

Project Name: Vectorizer / Auto-SIMD Pass

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a standalone auto-vectorization pass — a loop vectorizer plus a straight-line Superword-Level-Parallelism (SLP) vectorizer — that consumes SSA IR annotated with loop info, scalar evolution (SCEV), and alias analysis, and lowers eligible scalar loops and basic blocks to target SIMD instructions while proving semantics preservation on every transform. The pass is a middle-end compiler component in the LLVM LoopVectorize / SLPVectorizer tradition: legality is proven before profitability is costed, and every profitable, legal candidate is lowered to an explicit staged vector IR (VPlan) before any mutation of the original program.

Phase-0 deliverable (numbered modules):

  1. vec-ir — typed adapter over the host IR (loops, SCEV, alias sets).
  2. vec-interp — a scalar reference interpreter (the correctness oracle).
  3. vec-stride — access-pattern / stride classification.
  4. vec-deps — dependence analysis (GCD, Banerjee, Omega).
  5. vec-legality — legality verdict construction.
  6. vec-cost (+ vec-cost-x86, vec-cost-aarch64) — target-dispatched cost model.
  7. vec-vplan — the staged vector-plan IR.
  8. vec-loop — loop transform (strip-mining, reductions, epilog).
  9. vec-alias-check — runtime aliasing-check insertion.
  10. vec-mask — if-conversion / masked predication + gather-scatter lowering.
  11. vec-slp — superword-level parallelism.
  12. vec-diff / vec-fuzz / vec-bench — semantics-preservation and performance harness.

System boundaries. Provides: dependence analysis, legality proof, cost-driven VF (vector factor) selection, loop and SLP vectorization, masking/predication, gather/scatter lowering, runtime alias fallback, epilog handling, differential verification against a scalar oracle. Delegates: SSA construction, SCEV computation, alias analysis, register allocation, and instruction scheduling to the host compiler (Project #143's IR). Does NOT provide: a full code generator, a register allocator, outer-loop (loop-nest) vectorization, polyhedral scheduling, or GPU/SIMT lowering — all explicitly deferred (§35 Deferred Features Register).

Non-goals. Not a general loop-transformation framework (no fusion, no tiling, no interchange outside what dependence analysis requires to prove legality). Not a standalone compiler — it is a pass consumed by a host pipeline. Not an auto-parallelizer for threads/tasks — SIMD lanes only.

Deployment model. A library crate workspace invoked as a compiler pass over one function at a time, single-process, single-threaded per invocation (pass instances may run concurrently across functions in a multi-threaded codegen pipeline, but each invocation owns no shared mutable state — I6, P6).

Target users/operators. Compiler engineers integrating the pass into a host middle-end; performance engineers tuning cost-model calibration per target; release engineers gating CI on the differential and fuzz buckets.

Later phases unlock: SLP-after-loop-vec composite candidates (§18), gather/scatter for non-affine access (§19), a 30-day continuous fuzz canary (§21) gating release.

Recommended language: Rust 1.78+ MSRV. Rationale: no undefined behavior while mutating a mutable IR graph under unsafe-free ownership rules; enum-based ASTs give exhaustive-match safety for the ~40-variant VPInstruction/IllegalReason families; zero-cost abstractions keep the cost model's per-instruction dispatch cheap (ADR-01). Rejected: C++ (LLVM's own language) — rejected because this is a standalone from-scratch pass, not an LLVM in-tree patch, and Rust's exhaustiveness checking catches missing VPInstruction match arms at compile time, which C++'s switch does not; OCaml/Haskell — rejected for lack of a mature SIMD-target-description ecosystem and weaker FFI story into existing IR representations.

Prerequisites: SSA form, dominance, loop-nest recognition, scalar evolution (SCEV), alias analysis fundamentals (Andersen/Steensgaard-style points-to), IEEE-754 floating point semantics, linear-algebra basics (matrix/vector notation for dependence testing), target ISA fundamentals (register files, memory operand encoding).

Estimated timeline: Phase 0 (repo skeleton + scalar-interpreter correctness kernel): 3 weeks. Full system (Phases 0–9, differential + fuzz canary stabilized): 7 months.

Deferred features, each flagged PhaseDeferred("§N.s") at first mention and registered in §35: outer-loop (loop-nest) vectorization PhaseDeferred("§35"), polyhedral scheduling PhaseDeferred("§35"), RISC-V V-extension (scalable vector length) target PhaseDeferred("§35"), GPU/SIMT lowering PhaseDeferred("§35"), profile-guided VF selection PhaseDeferred("§35"), OpenMP-SIMD pragma / vector function calls PhaseDeferred("§35").

2. Why Build This

Auto-vectorization is the compiler pass where the textbook description (strip-mine by a constant factor, run the body N-wide) and the production reality (a quarter-century of LLVM LoopVectorize/GCC tree-vect refinement) diverge the most sharply. Building it teaches: (a) the precise mathematics of loop-carried dependence (direction/distance vectors, the Banerjee inequality, the Omega test's exact integer linear programming) that every restructuring compiler course covers in one lecture and every production compiler spends years hardening; (b) the discipline of separating legality (a yes/no proof) from profitability (a cost race) — the single structural decision that prevents a profitability heuristic from ever causing a miscompile; (c) target-dispatched cost modeling, the same pattern LLVM's TargetTransformInfo and GCC's targetm.vectorize hooks exist for; (d) runtime-checked optimization (alias checks, masked execution) as a general technique for deferring an undecidable static question to a cheap dynamic guard.

It matters architecturally because vectorization is the clearest example in all of compiler engineering where legality and profitability are genuinely orthogonal concerns that historically got conflated (early vectorizing Fortran compilers of the 1980s often did mix them, producing both missed opportunities and, in less careful implementations, correctness bugs) — the same lesson generalizes to instruction scheduling, register allocation, and any optimization with a "can I" and a "should I" question. It builds the same engineering muscle as Project #143's IR passes (dependence graphs, SSA), Project's future instruction scheduler (also legality-then-cost), and database query optimizers (cost-based plan selection over a legal-plan search space) — the cost-model-over-a-legality-filtered-search-space pattern recurs everywhere.

Calibration value: a vectorizer's cost model is falsifiable against real hardware in minutes (run the loop, measure cycles) — a rare property among compiler passes, and a direct training signal for "did I model reality or a fiction."

What Mastery Looks Like

  • Derive, from first principles, why a negative-distance loop-carried dependence blocks vectorization and a positive-distance one at distance ≥ VF does not — Phase 2 (§14) and §8.2.
  • Explain why LLVM introduced VPlan instead of mutating IR per candidate VF — Phase 5 (§17) and §8.5.
  • Trade off the Banerjee test's speed against the Omega test's exactness and state the regime where each wins — Phase 2 (§14), ADR-04.
  • Distinguish loop vectorization from SLP by their opportunity shape (iteration-parallel vs statement-parallel) and know which one a given kernel needs — Phase 8 (§18).
  • Reason about when a runtime alias check earns its keep versus when it is pure overhead — Phase 6 (§18), P8.
  • Explain why floating-point reduction vectorization requires an explicit fast-math contract rather than being silently reassociated — Phase 4 (§16), I7.
  • Read a target's cost table and predict, without running the code, whether a given loop vectorizes profitably — Phase 4 (§16), §8.5.
  • Design the differential-and-fuzz harness that makes "semantics preserved" a continuously checked property rather than a one-time code review — Phase 9 (§21).

Box notes. Host IR is read-only input; the pass never mutates it before a LegalityVerdict::Legal. vec-stride and vec-deps are pure analyses, no IR mutation, queryable independently (their own conformance buckets, §5's Phase N.5). vec-legality is the trust boundary: everything downstream assumes its LegalityHints are sound — violating that assumption is the single highest-severity bug class in this system (T1, FM-1). vec-cost is a concurrency boundary by construction: it is a pure function (VPlan, &dyn CostModel) -> Cost, safely callable from multiple threads across different functions. vec-vplan/vec-loop is where mutation first happens, and only on a proven-legal, proven-profitable candidate. vec-alias-check is a protocol boundary in the sense that it hands a dynamic proof obligation to the generated code itself — the static analysis explicitly punts. vec-mask and vec-slp are the two remaining transform stages; vec-diff/vec-fuzz is the persistence boundary where every transformation's evidence (scalar vs. vector output) is written to a fixture corpus for regression.

3.1 Why Dependence Analysis Comes First

A loop with no loop-carried dependence is unconditionally vectorizable up to any VF the target supports; a loop with a positive-distance dependence is vectorizable only at VF ≤ distance; a loop with any negative-distance dependence is never vectorizable without a transformation this pass does not perform (loop skewing/distribution). The dependence graph is therefore the first prerequisite fact every later stage consumes — legality cannot be decided, and profitability cannot be estimated, before it exists (P1, I2).

3.2 VPlan As the Staged Intermediate

Mutating the original IR once per candidate VF is wasteful and dangerous: a rejected candidate would need a full undo. Instead, a VPlan (§11) is built once per candidate (VF, unroll-factor) pair; the cost model (§16) walks it without touching the original function; only the winning plan is lowered to real IR (§17). This mirrors LLVM's own motivation for introducing VPlan over the pre-VPlan direct-mutation vectorizer (P2, ADR-03).

6. Design Principles

  1. P1 — Legality Before Profitability. No cost estimate is ever consulted before a LegalityVerdict::Legal exists for the candidate. Tradeoff: two full analysis passes instead of one fused pass. Operational implication: the two stages are independently unit-testable and independently bypassable (a debug flag can force "cost only" runs against known-legal fixtures). Violating it: a cost heuristic that also approves legality collapses the miscompile firewall (T1, FM-1).
  2. P2 — Explicit Staged IR (VPlan). Every candidate (VF, UF) pair is materialized as a VPlan before any mutation. Tradeoff: extra allocation per candidate. Operational implication: multiple candidates can be costed and compared without an undo path. Violating it: direct-IR-mutation-per-candidate requires transactional rollback, a much larger correctness surface.
  3. P3 — Target-Dispatched Cost. dyn CostModel per target; the vectorizer core never special-cases a target by name. Tradeoff: a new target requires a new CostModel impl, not a branch. Operational implication: vec-cost-x86/vec-cost-aarch64 are independently calibrated and independently benchmarked. Violating it: cost logic forked by if target == "x86" strings rots silently as targets are added.
  4. P4 — Two-Test Dependence Ladder (GCD → Banerjee → Omega). Cheap tests run first; the exact-but-exponential Omega test runs only when Banerjee returns "maybe." Tradeoff: three code paths instead of one. Operational implication: bounds the p99 analysis latency (§4). Violating it: always running Omega blows the 80 ms p99 budget on deep nests (worst case 2^6).
  5. P5 — Fast-Math Is a Semantics Contract, Not a Performance Switch. FP reduction reassociation is permitted only under an explicit fast-math flag threaded from the host IR. Tradeoff: some FP reductions are left un-vectorized by default. Operational implication: users opt into a documented precision change, never receive it silently. Violating it: silent reassociation is a reproducibility bug users cannot diagnose (T2).
  6. P6 — Deterministic Everything. No HashMap iteration reaches codegen order; every internal collection that affects emitted instruction order is sorted or insertion-ordered. Tradeoff: minor overhead from sorted structures. Operational implication: byte-identical output enables bisection and the differential harness. Violating it: flaky regression tests that "sometimes" reproduce (T5).
  7. P7 — No Global Mutable State In the Pipeline. Every stage is a pure function of its explicit inputs; no thread-local or process-global cache of IR-derived facts. Tradeoff: recomputation across stages where caching might help. Operational implication: multiple function-level pass invocations run concurrently with no coordination. Violating it: cross-invocation data races under a multi-threaded host pipeline.
  8. P8 — Runtime Checks Are a Last Resort, Not a Default. A runtime alias check is inserted only when static alias analysis returns Unknown. Tradeoff: static analysis must be trusted when it says "no alias." Operational implication: keeps the common case (provably disjoint arrays) branch-free. Violating it: unconditional alias-checking taxes every loop with a check that is dead weight 90%+ of the time (ADR-08).
  9. P9 — SLP Runs After Loop Vectorization. The pipeline order is fixed: loop vectorization first, SLP second, because loop vectorization's unrolled remainder can create new SLP opportunities. Tradeoff: SLP cannot influence the loop vectorizer's VF choice. Operational implication: a single fixed pipeline order, no iteration to a fixpoint between the two. Violating it: SLP-first ordering misses candidates created by loop-vec's own unrolling (ADR-11).
  10. P10 — Cost Model Owns Register Pressure. The Cost struct's register_pressure field is not advisory — VF selection is bounded by it (I11). Tradeoff: a conservative VF is chosen over a theoretically-faster wider one when pressure would spill. Operational implication: no separate post-hoc spill-detection pass is needed. Violating it: over-wide VF selection silently negates gains via register spills (ADR-15).
  11. P11 — Diagnostics On Every Illegal Verdict. LegalityVerdict::Illegal always carries the specific IllegalReason and the blocking InstructionId/Span. Tradeoff: every illegal path must construct and thread a diagnostic value. Operational implication: -Rpass-missed-equivalent diagnostics are free, not a separate feature. Violating it: a bare "cannot vectorize" gives operators nothing to act on (I14).
  12. P12 — Differential Oracle Over Self-Consistency. The scalar interpreter (vec-interp) built in Phase 0 is the ground truth every vectorized output is checked against; property tests alone are not trusted. Tradeoff: maintaining a second, independent execution engine. Operational implication: an internally consistent but wrong cost model or legality check cannot silently pass CI. Violating it: property-only testing catches internal contradictions, not external wrongness (ADR-13).
  13. P13 — Conformance Fixtures Before Optimization. Every phase's fixture corpus (N.5) is authored before performance tuning begins on that phase. Tradeoff: slower initial phase velocity. Operational implication: a regression in a later phase's optimization pass is caught immediately by an earlier, stable fixture set. Violating it: tuning against a moving-target fixture set hides regressions.
  14. P14 — Epilogs Are Mandatory, Never Silently Dropped. Any trip count not evenly divisible by VF gets an epilog loop (or masked equivalent, ADR-09); there is no "assume trip count is a multiple of VF" fast path. Tradeoff: extra code size per vectorized loop. Operational implication: correctness holds for every trip count, not just benchmark-convenient ones. Violating it: an epilog-free vectorizer miscompiles every loop whose trip count isn't a multiple of VF (I4, FM-2).

8. Domain Model

8.1 Loop & IR Model

A Loop (from the host IR, #143) is a natural loop with a single header dominating all blocks in the loop, an induction variable recognized by ScalarEvolution as an affine recurrence {base, +, step}, and a trip count either constant or a runtime SCEV expression. Every memory access inside the loop body is a Place (pointer + element type); vec-stride (§13) classifies each Place's per-iteration address delta:

StrideKind Meaning Vectorization path
Constant(0) loop-invariant address broadcast/hoist, not vectorized as an access
Constant(k), k = element size unit stride direct contiguous vector load/store
Linear{base,step}, step ≠ element size affine non-unit stride strided/gather-scatter (§19)
Unknown address depends on another loaded value (a[b[i]]) gather/scatter or reject
Random provably data-dependent, no affine model reject or gather/scatter with cost penalty

8.2 Dependence Analysis: Direction/Distance Vectors and the Three-Test Ladder

For a pair of memory accesses (S1, S2) in a loop nest of depth d, a direction vector Θ = (θ_1 … θ_d) records, per loop level, whether the dependence is < (S1's iteration precedes S2's, "forward"), > (backward — blocks vectorization), = (same iteration), or * (unknown, conservatively assumed both). A distance vector Δ = (δ_1 … δ_d), when computable, gives the exact iteration-count gap. Allen & Kennedy's fundamental theorem of vectorization: a loop is vectorizable at level i iff no dependence has direction > at level i (P1, I2).

The ladder (P4, ADR-04), cheapest test first:

  1. GCD test — O(1) per subscript pair: if gcd of the induction-variable coefficients does not divide the constant offset difference, no dependence exists; otherwise inconclusive, fall through.
  2. Banerjee test — O(d) per pair: bounds a linear inequality system over the iteration-space box; answers "definitely no dependence," "definitely a dependence with this direction," or "maybe."
  3. Omega test (Pugh 1992) — exact integer linear programming, worst case O(2^d) (bounded by §4's depth cap of 6 ⇒ ≤ 64 subproblems); runs only on a Banerjee "maybe."
DependenceGraph
 ├─ edges: Vec<DependenceEdge>
 │   ├─ (S1,S2, True,  Θ=(<),  Δ=(3))   -- RAW, distance 3: vectorizable at VF ≤ 3
 │   ├─ (S3,S4, Anti,  Θ=(=),  Δ=(0))   -- WAR, same iteration: fine
 │   └─ (S5,S6, True,  Θ=(>),  Δ=(-1))  -- RAW, backward: BLOCKS vectorization (I2)
 └─ reduction_edges: Vec<InstructionId>  -- flagged separately, see §8.3

8.3 Loop-Level Vectorization: Strip-Mining, Reductions, If-Conversion

Strip-mining: transform for i in 0..n { body(i) } into a vector loop for i in (0..n).step_by(VF) { vbody(i..i+VF) } plus an epilog for n mod VF (I4, P14). The vector body replaces each scalar operation with its VF-wide VPInstruction (§11); memory ops become VPLoad/VPStore with gather/scatter/mask flags set per §8.1's stride classification.

Reductions (acc = acc OP a[i]): the loop-carried dependence on acc has distance 1 and would otherwise block vectorization; vec-legality recognizes the pattern (I7) and vec-loop emits a VPReduce — a VF-wide partial-accumulator vector plus a horizontal combine after the loop. For floating point, this only proceeds under the fast-math contract (P5) since the partial-sum tree changes rounding.

If-conversion: a conditional in the loop body (if cond(i) { a[i] = f(i) }) is converted to a VPSelect/masked-store pair — compute both arms unconditionally (if safe) or guard with a mask (§8's mask model below), and select/store per-lane based on cond_vector. This trades control flow for data-parallel predication, the same transform LLVM calls "predication."

8.4 Superword-Level Parallelism (SLP)

Loop vectorization exploits parallelism across iterations; SLP (Larsen & Amarasinghe, PLDI 2000) exploits parallelism across statements in straight-line code with no loop. Algorithm: (1) find "seed" pairs — adjacent stores or adjacent uses of adjacent loads; (2) build a tree upward from each seed following operand dependencies; (3) verify the tree is isomorphic (same opcode at each level, matching operand count); (4) cost the packed tree against the sum of scalar costs; (5) if profitable, replace with a single vector operation per tree level. SLP naturally runs on the unrolled remainder that vec-loop's epilog can produce, and on independently loop-free kernels (color-space conversion, quaternion math) — hence P9's ordering (SLP after loop vectorization).

8.5 Cost Model & Profitability

The Cost (§11) for a VPInstruction at a given VF combines target-measured throughput (reciprocal instructions/cycle), latency (cycles to result), and a register_pressure contribution. Total plan cost sums per-instruction costs across the VPlan's blocks; the plan is profitable iff total_cost(VF) < scalar_cost * (1 - margin), where margin accounts for measurement noise (default 5%). VF selection (I11) takes min(legality_hints.max_vf, largest VF whose register_pressure ≤ target register file size).

8.6 Worked Example

Input: for i in 0..1024 { c[i] = a[i] + b[i]; }, all f32, unit stride, no aliasing proven. vec-stride: all three StrideKind::Constant(4) (unit stride). vec-deps: no edges (no aliasing among a,b,c — read-only/write-only, disjoint). vec-legality: Legal{ hints: { max_vf: 16, stride_pattern: Unit, needs_runtime_alias_check: false, needs_masking: false } }. vec-cost: AVX-512 VPArith(Add) throughput cost favors VF=16; total cost 1024/16 × (load+load+add+store cost) ≪ scalar cost. vec-loop: strip- mine to 64 vector iterations of VF 16, trip count 1024 is exactly divisible ⇒ empty epilog. Result: 16-wide vaddps loop, differential-verified equal to scalar (I1).

8.7 Malformed-Input Example

Input: for i in 1..1024 { a[i] = a[i-1] * 2; }. vec-deps finds DependenceEdge{ from: store(a[i-1] read), to: store(a[i]), kind: True, direction: (<), distance: Some(1) } — forward, distance 1. This is legal at VF ≤ 1 only (any VF > 1 would read a not-yet- written future element) — vec-legality returns Legal{ hints: { max_vf: 1, … } }, which the cost model correctly rejects as unprofitable (VF 1 has no vector benefit); the loop remains scalar. This is not an Illegal verdict — it is a correctly-bounded legal verdict that profitability rejects, illustrating P1's clean separation.

8.8 Failure-Path Example

Input: for i in 0..n { c[i] = a[i] / b[i]; } where b is not provably non-zero anywhere (no #[assume(b[i] != 0)] annotation, no dominating check). vec-legality returns Illegal{ reason: ExceptionPossible(div_instr), span: … } (I13) because a vector divide would speculatively execute the divide on all VF lanes, including lanes whose scalar counterpart was never reached under the loop's actual control flow (there is none here, but the value itself might trap on some lane the scalar path would still have executed — the real risk is on a masked/if-converted variant of this loop, where an unmasked division would execute lanes the scalar path skips entirely). The diagnostic names the exact instruction (P11, I14); the loop stays scalar. If masking is available (§19) and the target supports masked divide, vec-mask may instead guard the divide with the branch's own mask rather than reject outright — the two stages cooperate rather than one unconditionally overriding the other.

Set up .github/workflows/ci.yml to run cargo test --workspace and the fixture runner on every push.

A workspace that builds, a vec-interp that correctly executes the 30-kernel Polybench-analog corpus (§10, examples/) and matches recorded expected outputs, and a green CI badge.

Treating vec-interp as "good enough if it compiles" — it must be independently authored from the vectorizer's own mental model of semantics, or it stops being an oracle (P12). Letting vec-ir leak #143-internal types into public signatures, which locks every later crate to #143's internal versioning.

12.7 Performance Concerns

None yet load-bearing — this phase's only performance requirement is CI wall-clock (§12.4); no vectorization runs.

12.8 Edge Cases

Empty function (no loops); a loop with zero trip count; a malformed/dangling-SSA-use fixture (must error, not panic); an IR with an unrecognized SCEV form (must fall back to Unknown, not crash the adapter).

12.9 Failure Analysis

A bug in vec-ir's adapter propagates silently into every later phase's fixtures — this is the highest-leverage phase to get right. Detection: the fixture runner's malformed- input fixture (§12.5) catches adapter panics in CI. Blast radius: unbounded (every later phase) if undetected. Recovery: pin vec-ir's API with its own unit tests independent of any vectorization fixture.

12.10 Operational Notes

CI publishes vec-interp pass/fail counts per corpus kernel as a metric (interp_fixture_pass_total); no deployment topology yet (library crate, not a service).

13. Phase 1 — Loop Selection & Stride Analysis

13.1 Objectives

Implement innermost-first loop iteration and per-access stride classification (StrideKind, §8.1), the first analysis stage in the pipeline (§3).

13.2 Detailed Implementation Steps

vec-stride::analyze_stride (§11) walks each Place's address expression via ScalarEvolution, recognizing three shapes: a SCEV AddRec with a constant step equal to the element size (Constant, unit stride); an AddRec with a non-constant-element step (Linear); anything requiring a load to compute the address (Unknown, per Nuzman-Rosen-Zaks's interleaved-access analysis, §5 Papers — applied here for the Linear case's structure-of-arrays detection). The loop selector (vec-ir) visits loops innermost-first per P1's dependency on having an inner analysis complete before an outer loop is considered (a vectorized inner loop changes the outer loop's cost profile).

13.3 Deliverable

A StrideKind classification for every memory access in a loop body, and an innermost- first loop worklist consumable by Phase 2.

13.4 Acceptance Criteria

100% of the stride/ conformance bucket's 12 named fixtures classify correctly; stride analysis on a 1,000-iteration loop body completes in ≤ 10 ms p50, ≤ 30 ms p99 (§4, M2); a nested-loop fixture visits the inner loop strictly before the outer.

13.5 Conformance Fixtures

stride/unit_f32.vecfix — a[i], expect Constant(4); stride/unit_f64.vecfix — expect Constant(8); stride/linear_2i.vecfix — a[2*i], expect Linear{step=2*elem}; stride/indirect.vecfix — a[b[i]], expect Unknown; stride/nested_inner_first.vecfix — asserts visitation order.

13.6 Pitfalls

A pointer-arithmetic expression i * sizeof(T) folded by an earlier constant-folding pass may present as Constant(sizeof(T)) directly — the analysis must not require seeing the multiply syntactically, only the SCEV AddRec's resolved step. A stride expression that is loop-invariant in an outer loop but varies in the inner loop must be classified relative to the loop currently being analyzed, not the whole nest.

13.7 Performance Concerns

ScalarEvolution queries are memoized by #143's IR layer, not re-derived per access — vec-stride must not trigger redundant SCEV recomputation by querying the same Place twice across sibling analyses.

13.8 Edge Cases

A loop with an induction variable that overflows within the trip count (undefined behavior in the source language) — classify conservatively as Unknown rather than assume wraparound semantics. A multi-dimensional array access flattened to one SCEV expression with a non-trivial step. A loop with zero memory accesses (pure register computation) — trivially Constant classification is vacuous but must not error.

13.9 Failure Analysis

A unit-stride access misclassified as Linear or Unknown is a missed optimization (FM-9), not a miscompile — it degrades to a stricter, safer path. The reverse (a non-unit-stride access misclassified as Constant/unit) is a miscompile risk and is guarded by the stride/ bucket's differential check against vec-interp.

13.10 Operational Notes

Emits stride_classification_total{kind} per analyzed access for operator visibility into how much of a codebase is unit-stride vs. gather-candidate; no migration/rollback concerns (pure analysis, no persisted state).

14. Phase 2 — Dependence Analysis

14.1 Objectives

Implement the GCD → Banerjee → Omega ladder (P4, ADR-04) producing a DependenceGraph (§8.2, §11) — the prerequisite fact for legality (§3.1).

14.2 Detailed Implementation Steps

For every pair of memory accesses in the loop body that may alias (per the host AliasAnalysis, narrowing the O(n²) pair count before any dependence test runs), run the GCD test first (Allen & Kennedy Ch. 2, §5 Books); on "maybe," run Banerjee (Banerjee 1988, §5 Books); on Banerjee's "maybe," run the Omega test (Pugh 1992, §5 Papers) bounded by the depth-6 cap (§4). Each resolved pair becomes a DependenceEdge with DependenceKind (RAW/WAR/WAW/RAR) and, when computable, a DistanceVector. Reduction-shaped self-dependences (acc = acc OP x) are tagged into reduction_edges rather than treated as ordinary blocking edges (I7, consumed by Phase 3's legality check).

14.3 Deliverable

A DependenceGraph for any loop body, with every edge's resolving test recorded (DepTest::{Gcd,Banerjee,Omega}) for diagnostics and calibration.

14.4 Acceptance Criteria

The deps/ bucket's 15 fixtures (including the canonical Banerjee and Omega textbook examples) resolve to the expected DependenceKind/DirectionVector/DistanceVector; analysis on a 1,000-iteration loop with 20 memory ops completes in ≤ 50 ms p50, ≤ 100 ms p99 (§4, M1); Banerjee and Omega agree on every fixture where both are computable.

14.5 Conformance Fixtures

deps/raw_distance_3.vecfix — a[i] = a[i-3] + 1, expect True, Θ=(<), Δ=(3); deps/backward_blocks.vecfix — a[i] = a[i+1], expect Θ=(>) (I2 must reject downstream); deps/gcd_no_dep.vecfix — a[2*i] = a[2*i+1], GCD resolves "no dependence" without reaching Banerjee; deps/omega_exact.vecfix — a subscript pattern where Banerjee reports "maybe" and Omega resolves exactly; deps/non_affine.vecfix — a[b[i]], expect conservative "assume dependence."

14.6 Pitfalls

Treating a Banerjee "maybe" as "no dependence" (must fall through to Omega, never silently optimistic — I2's soundness depends on this). Forgetting that a same-iteration dependence (Δ=0) is always safe regardless of direction. Running Omega on every pair regardless of Banerjee's verdict, blowing the p99 budget (§4) on deep nests.

14.7 Performance Concerns

The alias-analysis pre-filter (§14.2) is the single highest-leverage optimization here — skipping the O(n²) pair test entirely for provably-non-aliasing pairs. Omega's worst-case cost is bounded by the depth-6 cap but should still be measured per-fixture in CI to catch calibration drift (M1).

14.8 Edge Cases

A loop with a self-referential access at distance 0 in a non-reduction shape (e.g. a redundant read-after-write to the same address, same iteration) — must not be flagged as loop-carried. A dependence pair spanning a function call with unknown side effects — conservatively treated as a dependence (I13-adjacent: unknown side effects block legality independently in Phase 3). Integer overflow in a subscript's constant-folded offset — must not silently wrap in a way that changes the GCD test's inputs.

14.9 Failure Analysis

A missed dependence (backward, unflagged) is the single worst possible bug in this system — it directly causes I2/I1 violations (a miscompile). Detection: the deps/ bucket's backward_blocks fixture plus the Phase 9 differential harness catch it before any release; blast radius is every loop that shares the missed pattern. Recovery: revert the offending dependence-test change, re-run the full differential corpus, file FM-1.

14.10 Operational Notes

Emits dep_test_resolved_total{test=gcd|banerjee|omega} so operators can see the actual distribution of ladder-step usage in a real codebase (validates the "cheap tests resolve the vast majority" assumption behind ADR-04); a dep_test_resolved_total{test=omega} rate materially above expectation is itself a calibration signal worth alerting on.

15. Phase 3 — Legality Check

15.1 Objectives

Implement vec-legality::check_legality (§11), the trust boundary (§3) that produces the single LegalityVerdict every downstream stage trusts without re-verification (P1, I8).

15.2 Detailed Implementation Steps

Combine the DependenceGraph (Phase 2), stride classifications (Phase 1), and a side-effect/exception scan of the loop body into a verdict per the rule in §8.3/Allen & Kennedy's fundamental theorem (applied inline, P1): Legal only if (a) no DependenceEdge has direction = Greater at the loop's own level (I2); (b) no instruction has unproven exception potential — division without a proven-nonzero divisor, signed overflow without nsw-equivalent proof (I13); (c) no call to a function not marked vectorizable (conservative default: unmarked = blocks); (d) any reduction_edges entry is recognized as a supported ReductionKind (I7) and, for floating-point kinds, the loop carries the fast-math flag (ADR-10). On any violation, construct IllegalReason naming the exact edge/instruction/span (P11, I14) — never a bare rejection.

15.3 Deliverable

A LegalityVerdict for every candidate loop, with LegalityHints{max_vf, stride_pattern, needs_runtime_alias_check, needs_masking, reductions} populated on the Legal path.

15.4 Acceptance Criteria

The legality/ bucket's 18 fixtures each produce the exact expected IllegalReason variant or Legal hints; check completes in ≤ 50 ms p50, ≤ 100 ms p99 on a 1,000- iteration loop (§4, M3); zero fixtures produce a bare/unnamed illegal verdict (I14).

15.5 Conformance Fixtures

legality/negative_distance.vecfix — expects Illegal{NegativeDistanceDep(edge)}; legality/unguarded_div.vecfix — expects Illegal{ExceptionPossible(instr)}; legality/fp_reduction_no_fastmath.vecfix — expects Illegal{UnsupportedReduction} without the flag, Legal with it; legality/unmarked_call.vecfix — expects Illegal{SideEffectInBody}; legality/max_vf_from_distance.vecfix — distance-4 dependence, expects Legal{hints.max_vf = 4}.

15.6 Pitfalls

Treating a positive-distance dependence as unconditionally legal at any VF — max_vf must be clamped to the distance (§8.2's worked example contrast, §8.7's malformed-input example). Forgetting that a same-iteration (distance = 0) true dependence is always legal and must not be conflated with a genuine loop-carried hazard. Marking a reduction legal without checking the specific operation is in the supported set (add/mul/min/ max/and/or/xor for integer; add/mul only, fast-math-gated, for float).

15.7 Performance Concerns

The side-effect/exception scan should short-circuit on the first disqualifying instruction rather than exhaustively cataloguing every issue in the loop — the verdict only needs one true blocker, and this keeps p99 inside budget on large loop bodies.

15.8 Edge Cases

A loop with both a negative-distance dependence and an unguarded division — verdict must still name exactly one primary IllegalReason deterministically (first-found by a fixed traversal order, I10) rather than nondeterministically picking either. A reduction whose accumulator is also read elsewhere in the loop body (not a pure reduction) — must not be misrecognized as a simple reduction. A loop with a provably-dead code path containing an illegal operation (unreachable) — conservative default still flags it unless dead-code elimination has already removed it upstream.

15.9 Failure Analysis

An Illegal verdict wrongly returned for a legal loop is a missed-optimization bug (FM-9) — costly but not unsafe. A Legal verdict wrongly returned for an illegal loop is a miscompile (FM-1) — the single highest-severity failure this phase can produce. Detection: the legality/ bucket plus Phase 9's differential harness, which will observe scalar/vector output divergence downstream. Recovery: revert the legality-check change; audit every Legal verdict issued since the change via replay.

15.10 Operational Notes

Emits legality_reject_total{reason} and legality_accept_total for operator dashboards tracking vectorization-rate trends (feeds M10); diagnostics surface as -Rpass-missed-equivalent structured log lines naming the blocking InstructionId.

16. Phase 4 — Cost Model & VF Selection

16.1 Objectives

Implement the CostModel trait and target impls (vec-cost-x86, vec-cost-aarch64) and select_vf (§11), the profitability half of P1's split.

16.2 Detailed Implementation Steps

Each target's CostModel::instruction_cost returns a Cost{throughput, latency, register_pressure} per VPInstruction variant, calibrated from vendor optimization manuals (Intel Architecture Manual, ARM NEON Programmer's Guide, §5 Required Reading) and refined against measured microbenchmarks (vec-bench, Phase 9). select_vf (P10, I11, ADR-17) builds candidate VPlans at each of the target's legal_vfs() values capped by hints.max_vf, costs each, and picks min(hints.max_vf, largest VF whose summed register_pressure ≤ target register file size) among plans whose total_cost < scalar_baseline_cost * 0.95 (the 5% margin, §8.5). AVX-512's register-pressure penalty (ADR-15) is modeled as a nonlinear step once live vector temporaries exceed roughly two-thirds of the 32-register file, reflecting spill risk from register allocator behavior observed empirically in vec-bench.

16.3 Deliverable

A chosen VF (or None if no candidate beats the margin) per legal loop, with the full per-candidate cost table retained for diagnostics.

16.4 Acceptance Criteria

The cost/ bucket's 14 fixtures (one per characteristic pattern per target) select the expected VF; cost computation per candidate plan completes in ≤ 10 ms p50, ≤ 30 ms p99 (§4, M4); on the examples/ corpus, ≥ 70% of legal loops receive a non-None VF (M10).

16.5 Conformance Fixtures

cost/avx512_max_vf16.vecfix — dense f32 unit-stride, expects VF 16; cost/register_ pressure_clamped.vecfix — 20 live vector temporaries on a 32-register target, expects a narrower VF than the naive maximum (I11); cost/unprofitable_small_trip.vecfix — trip count 3, expects None (VF overhead exceeds benefit); cost/gather_penalty.vecfix — non-affine stride, expects gather cost pushes VF selection down or to None.

16.6 Pitfalls

Calibrating cost tables against a single microarchitecture and silently assuming portability across a whole ISA family (AVX2 on a 2013-era part vs. a 2023-era part have materially different real-world throughput) — recalibrate per generation, don't extrapolate. Letting the 5% profitability margin drift to 0% (any-positive-margin "profitable"), which lets measurement noise flip vectorization decisions nondeterministically across otherwise-identical builds.

16.7 Performance Concerns

Building and costing a VPlan per candidate VF is the dominant cost of this phase — bound the candidate set to the target's legal_vfs() (typically 3-4 values) rather than every power of two up to the max, to keep p99 inside 30 ms (M4) on wide loop bodies.

16.8 Edge Cases

A loop whose scalar cost is already near zero (trivial body) — must not divide-by- near-zero when computing relative profitability; use an absolute floor cost. A target whose legal_vfs() is empty (no vector unit at all, e.g. a soft-float target) — select_ vf returns None unconditionally without attempting any candidate. Two candidate VFs tying exactly on cost — deterministic tie-break: prefer the wider VF (I10, more throughput per instruction at equal modeled cost).

16.9 Failure Analysis

A miscalibrated cost model causing a widespread unprofitable-vectorization regression (slower than scalar) is detected by vec-bench's regression gate (M8/M9 thresholds, §28) before release, not by users in production. Blast radius: every loop matching the mis-costed instruction pattern. Recovery: recalibrate the specific CostModel impl against fresh microbenchmarks; the differential harness cannot catch this class (it checks correctness, not speed) — vec-bench is the only backstop (T6).

16.10 Operational Notes

Emits vf_selected_total{vf} and vf_selection_none_total histograms per target for tracking vectorization-rate and VF-distribution trends over a codebase's lifetime; per-target calibration data versioned alongside the target crate for reproducibility (ADR-19).

17. Phase 5 — VPlan Construction & Loop Transform

17.1 Objectives

Implement vec-vplan::build_vplan and vec-loop's strip-mining transform (§8.3, P2, ADR-03) — the first stage that mutates the host IR, and only on a costed, chosen VF.

17.2 Detailed Implementation Steps

build_vplan maps each scalar Instruction in the loop body to a VPInstruction (§11): arithmetic to VPArith, memory ops to VPLoad/VPStore (with gather/scatter flags set from hints.stride_pattern), phi nodes to VPPhi with per-incoming-edge values vectorized consistently (I3-adjacent: a phi's incoming values must all be the same width). vec-loop then lowers the winning VPlan (P2): clones the loop body into a "vector body," rewrites the induction variable's step from 1 to VF, adjusts the loop bound (i < n becomes i < n - (n mod VF), Allen & Kennedy TOPLAS 1987's strip-mining algorithm, §5 Papers, applied here), and emits reductions as VPReduce with a broadcast-initialized partial accumulator plus a post-loop horizontal combine (§8.3, I7 for the fast-math gate). An epilog loop (scalar, unmodified body) is always emitted for the n mod VF remainder (P14, I4) — never elided.

17.3 Deliverable

A transformed function with a vector-body main loop plus a scalar epilog loop, verified to preserve the original loop's exit conditions and side-effect ordering.

17.4 Acceptance Criteria

The loop/ bucket's 16 fixtures pass differentially against vec-interp (I1); the epilog/ bucket's 8 fixtures (each a distinct trip-count-mod-VF remainder, 0 through VF-1) produce exactly the expected epilog trip count (I4); transform completes in ≤ 200 ms p50, ≤ 500 ms p99 per loop (§4, M5).

17.5 Conformance Fixtures

loop/saxpy_vf8.vecfix — differential match required; loop/reduction_sum_f32_ fastmath.vecfix — partial-sum reduction, tolerance-bounded differential match; epilog/remainder_0.vecfix — trip count exact multiple of VF, expect empty epilog; epilog/remainder_vf_minus_1.vecfix — worst-case remainder, expect epilog trip count = VF−1 exactly (I4).

17.6 Pitfalls

Adjusting the loop bound with an off-by-one (n - (n mod VF) vs. n - (n mod VF) - 1) — the single most common bug class in this phase (§29 Pitfall #8 analog, FM-2). Failing to broadcast a reduction's initial value correctly when the initial value is not the operation's identity element (e.g. acc = 10; acc += a[i] needs a broadcast of 10 only into lane 0, identity 0 into the rest, or an equivalent post-combine correction). Emitting the vector body before verifying every phi's incoming edges are consistently widened.

17.7 Performance Concerns

Cloning the loop body for the vector variant duplicates code size — for very large loop bodies this is a compile-time and binary-size cost worth tracking (vplan_clone_bytes metric); the epilog loop, being scalar and rarely hot, should not itself be vectorized recursively (I12 idempotency guard prevents this).

17.8 Edge Cases

A trip count known at compile time to be exactly 0 — the vector loop and epilog are both dead; must fold to nothing, not emit an always-empty vector loop. A reduction with mixed integer/float lanes in the same accumulator (not expressible — must be rejected upstream at Phase 3, not discovered here). A loop whose induction variable is used after the loop with a value dependent on the exact original step (loop-carried "last value" use) — the epilog's final value, not the vector loop's, must feed any post-loop use.

17.9 Failure Analysis

An epilog miscount (I4 violation) silently drops or repeats iterations on any trip count not a multiple of VF — this is FM-2, detected by the epilog/ bucket's exhaustive remainder fixtures and the differential harness. Blast radius: every vectorized loop whose trip count isn't VF-aligned at runtime, which in general is unbounded (data- dependent trip counts are the common case). Recovery: revert; the fixture set (§17.5) is exhaustive over all VF remainders so re-running it after a fix gives full confidence.

17.10 Operational Notes

Emits loop_transform_duration_ms histogram (feeds M5) and epilog_trip_count_ mismatch_total (should be 0, alerts if not); no rollback path needed beyond re-running the pass with vectorization disabled for the offending loop (a per-loop opt-out attribute is the operational escape hatch).

18. Phase 6 — Runtime Alias Checks & Epilog Hardening

18.1 Objectives

Implement vec-alias-check (P8, ADR-08) — inserting a runtime disjointness guard with scalar fallback exactly when hints.needs_runtime_alias_check is set — and harden vec-epilog's remainder handling against the edge cases surfaced in Phase 5.

18.2 Detailed Implementation Steps

When static alias analysis cannot prove two accessed ranges disjoint (AliasAnalysis returns MayAlias/Unknown, propagated into hints.needs_runtime_alias_check by Phase 3), vec-alias-check inserts a predicate before the vector loop comparing the two ranges' [ptr, ptr + trip_count * elem_size) bounds (I5); if disjoint, the vector body executes, otherwise control falls to a fully scalar version of the original loop (not just the epilog — the entire iteration space, since aliasing could affect any iteration). The check's own cost (a handful of comparisons and branches) is folded into the cost model's total for the vector path (§16.2) so a loop with many potentially- aliasing ranges can still be correctly deemed unprofitable. vec-epilog is extended to share the alias-check's disjointness proof rather than re-deriving it, avoiding a redundant check on the remainder path.

18.3 Deliverable

A guarded vector loop: if no_overlap(ranges) { vector_loop() } else { scalar_loop() }, plus the standing epilog loop on the disjoint-proven branch, both differentially verified.

18.4 Acceptance Criteria

The alias-check/ bucket's 10 fixtures (5 provably-disjoint requiring zero checks per I5, 5 requiring a check) match expected check-insertion exactly; inserter completes in ≤ 5 ms p50 per loop; runtime check overhead itself is ≤ 10 cycles measured via vec-bench on the reference target.

18.5 Conformance Fixtures

alias-check/disjoint_provable.vecfix — restrict-equivalent-annotated pointers, expect zero inserted checks (I5, P8); alias-check/overlap_forced.vecfix — same buffer passed as both input and output, expect scalar-fallback branch taken at runtime and differential match on both branches; alias-check/three_way.vecfix — three ranges pairwise checked, expect all three pairwise comparisons present.

18.6 Pitfalls

Inserting a check that compares the wrong range (e.g. [ptr, ptr+elem_size) instead of [ptr, ptr + trip_count*elem_size)) — produces either a false-negative (unsafe vector path taken despite real aliasing, a miscompile) or false-positive (unnecessary scalar fallback, a missed optimization). Both directions are covered by dedicated fixtures (§18.5) precisely because they're easy to get backwards.

18.7 Performance Concerns

The check itself must not dominate a short loop's total cost — for very small trip counts, the cost model (Phase 4) may correctly conclude the vector path (check included) is unprofitable and select None, which is the intended interaction, not a bug to "fix" by making the check cheaper than physically possible.

18.8 Edge Cases

Ranges that are adjacent but not overlapping (a ends exactly where b begins) — must be classified disjoint, not conservatively overlapping (an off-by-one here either over- triggers scalar fallback needlessly or, worse, under-triggers on a true one-element overlap). A range whose size depends on a runtime value not known until the check itself executes (variable-length loop) — the check's bound expression must use the same trip- count expression the vector loop uses, not a stale copy.

18.9 Failure Analysis

A false-negative alias check (I5 violated in the unsafe direction) is a miscompile (FM-1) — the vector path executes despite real aliasing, corrupting data through write-after-read hazards the scalar loop never had. Detection: the overlap_forced fixture plus the fuzz corpus's random-aliasing-pattern generator (Phase 9). Recovery: revert; audit every loop whose needs_runtime_alias_check hint was set since the change.

18.10 Operational Notes

Emits alias_check_inserted_total, alias_check_scalar_fallback_taken_total (a runtime counter distinguishing "check inserted but never triggers" from "triggers frequently," useful for flagging loops whose static AA is unexpectedly weak); no schema/migration concerns (pure codegen).

19. Phase 7 — Masking, If-Conversion & Gather/Scatter

19.1 Objectives

Implement vec-mask::if_convert and lower_gather_scatter (§11) — predicated execution for control flow inside a vectorized loop, and gather/scatter lowering for non-affine access (§8.1, ADR-14, ADR-16).

19.2 Detailed Implementation Steps

For a loop body containing a data-dependent conditional (if cond(i) { a[i] = f(i) }), if_convert computes a cond_vector mask (a VPInstruction sequence evaluating the condition VF-wide), then rewrites the guarded store to a VPStore{mask: Some(cond_ vector), ..} and any guarded load similarly (P11-adjacent: this is the primary consumer of hints.needs_masking). Where the condition guards an operation with unproven exception potential (§8.8's failure-path example), the mask is the guard — I13 is satisfied by construction because masked lanes do not fault on the target ISAs in scope (x86/aarch64 masked loads/stores do not trap on masked-off lanes; this is a target property recorded in CostModel::name()-keyed metadata and checked before relying on it). lower_gather_scatter handles StrideKind::Unknown/Random accesses (I9) by emitting VPLoad{gather: true}/VPStore{scatter: true} with a per-lane address vector computed from the original (unvectorized) index expression, replicated VF-wide.

19.3 Deliverable

A loop body with all data-dependent control flow converted to masked operations, and all non-affine memory access lowered to gather/scatter, both differentially verified.

19.4 Acceptance Criteria

The mask/ bucket's 12 fixtures produce bit-exact-matching masks against a reference scalar condition evaluation; masking transform completes in ≤ 50 ms p50 per loop (§4); zero fixtures in the bucket show a masked-off lane influencing output (I3).

19.5 Conformance Fixtures

mask/simple_guard.vecfix — if a[i] > 0 { b[i] = 1/a[i] }, expect masked reciprocal, masked-off lanes untouched in b; mask/nested_guard.vecfix — two nested conditions, expect mask conjunction; mask/gather_indirect.vecfix — c[i] = a[idx[i]], expect VPLoad{gather: true}; mask/scatter_indirect.vecfix — a[idx[i]] = c[i], expect VPStore{scatter: true}; mask/ssse_no_mask_support.vecfix — SSE2 target without native masked-load support, expect the cost model marks masking expensive enough to select a narrower VF or None (ADR-16 interaction with Phase 4).

19.6 Pitfalls

A masked store whose mask computation itself has a bug writes outside the intended lanes — silent memory corruption, the highest-severity bug class in this phase (I3, FM-6 analog). Conflating "if-conversion always helps" with the reality that some targets (older SSE) lack efficient masked-load support, making the cost model's role (§16) — not this phase's — the arbiter of whether masking is worthwhile at all.

19.7 Performance Concerns

Gather/scatter instructions have materially higher latency than contiguous loads/stores on every target in scope (§4's cost tables reflect this) — this phase must not "sell" a gather/scatter transform as unconditionally beneficial; it defers profitability entirely to Phase 4's already-computed cost, applying the transform only after VF selection has already accounted for the gather penalty.

19.8 Edge Cases

A condition that is loop-invariant (does not depend on i) — should have been hoisted by an earlier scalar optimization pass; if it reaches this phase un-hoisted, if- conversion still produces a correct (if suboptimal) uniform mask. A gather where the index array itself is later found to alias the gathered array — handled by Phase 6's alias-check machinery, not duplicated here (P1-style separation of concerns). A mask that is all-false for an entire vector iteration (all lanes guarded off) — the masked operation must still be legal to execute (no fault), consistent with I13's target- property assumption.

19.9 Failure Analysis

A masked store writing outside mask bounds is FM-6 (silent memory corruption) — detected by the mask/ bucket's exhaustive guard-pattern fixtures and the fuzz corpus's random-control-flow generator. Blast radius: any loop with masked stores, potentially corrupting adjacent memory silently rather than crashing, making this a particularly dangerous, hard-to-diagnose class — the fuzz canary (Phase 9, 30-day soak) exists specifically to surface this class at volume.

19.10 Operational Notes

Emits mask_lanes_active_ratio (useful for spotting loops where masking overhead dominates because the condition is rarely true) and gather_scatter_emitted_total; no persisted state.

20. Phase 8 — Superword-Level Parallelism (SLP)

20.1 Objectives

Implement vec-slp (§8.4, P9) — straight-line-code vectorization independent of any loop, run after loop vectorization per the fixed pipeline order (ADR-11).

20.2 Detailed Implementation Steps

find_seeds scans a basic block for adjacent stores to adjacent addresses or adjacent uses of adjacent loads (Larsen & Amarasinghe PLDI 2000, §5 Papers, applied directly). build_tree follows operand dependencies upward from each seed to a bounded depth, producing a SeedTree; a tree is rejected if any level is non-isomorphic (differing opcode or operand count across the level's members) — commutative operators are operand- reordered first to maximize isomorphism-matching opportunities (the PLDI 2000 paper's operand-reordering heuristic, applied here). pack_tree costs the packed candidate against model (reusing Phase 4's CostModel, P3) and, if profitable, emits a VPlan whose lowering replaces the scalar tree with one vector operation per level.

20.3 Deliverable

A basic block with isomorphic scalar statement groups replaced by packed vector operations, differentially verified against the pre-transform scalar block.

20.4 Acceptance Criteria

The slp/ bucket's 10 fixtures (color-conversion and quaternion-arithmetic patterns) pack correctly; SLP analysis on a 1,000-statement basic block completes in ≤ 50 ms p50, ≤ 100 ms p99 (§4, M6); zero fixtures show a non-isomorphic tree incorrectly accepted.

20.5 Conformance Fixtures

slp/rgb_to_yuv.vecfix — the canonical 3-statement color-conversion seed pattern, expect a single packed 3-wide (or 4-wide with padding) vector op; slp/quaternion_ mul.vecfix — 4-component quaternion multiply, expect packing across the 4 independent component computations; slp/non_isomorphic_reject.vecfix — a tree with mismatched opcodes at one level, expect rejection (not a partial/incorrect pack); slp/cse_shared_value.vecfix — a common-subexpression-eliminated value used by two seeds, expect tree decomposition rather than a broken pack (§29 Pitfall #9 analog).

20.6 Pitfalls

Attempting to pack a tree where a value is used by multiple seeds (a DAG, not a tree) — must decompose or reject rather than silently duplicating computation incorrectly. Failing to reorder commutative operands before the isomorphism check, missing packable patterns that differ only in operand order (e.g. a+b vs b+a at the same tree level). Unbounded tree-search depth on a pathological basic block, blowing the performance budget (§20.7).

20.7 Performance Concerns

Tree-building depth must be bounded (a configurable cap, default 6, mirroring the dependence-analysis depth cap for consistency) to prevent worst-case exponential search cost on large basic blocks; find_seeds should be linear in block size, not re-scan from every candidate pairing.

20.8 Edge Cases

A basic block with only two candidate seeds and no viable tree above them (trivial, 2-element case) — correctly rejected as unprofitable rather than forced. A seed pair that are adjacent in address but different element types (type-punned access) — rejected, not coerced. A tree that would pack correctly but whose packed cost exceeds the sum of scalar costs on a register-pressure-constrained target — correctly rejected by the cost model (P3 reuse), not a bug in vec-slp itself.

20.9 Failure Analysis

A bug in tree extraction (incorrect isomorphism check) produces wrong vector operations — a miscompile (FM-1 class) detected by the slp/ bucket's non-isomorphic-reject fixture and the differential harness. Blast radius: any basic block matching the specific isomorphism-check flaw, typically a narrow but hard-to-predict set of straight-line kernels. Recovery: revert; the fixture corpus's negative cases (§20.5) are the primary regression guard.

20.10 Operational Notes

Emits slp_seed_found_total, slp_tree_packed_total, slp_tree_rejected_total{reason} for tracking how much of a codebase's straight-line kernels are SLP-eligible; no persisted state, no migration concerns.

21. Phase 9 — Differential Verification & Fuzz Canary

21.1 Objectives

Implement vec-diff, vec-fuzz, and vec-bench (§11) — the semantics-preservation harness (I1, P12, ADR-13) and the sustained-execution fuzz canary (ADR-18) that gate release.

21.2 Detailed Implementation Steps

run_differential (§11) executes a fixture through both vec-interp (Phase 0 oracle) and the fully vectorized pipeline, comparing outputs with FpTolerance (bit-exact for integer, ULP-bounded for float, reflecting the fast-math contract of P5/I7). A second differential axis runs the same fixture through LLVM's LoopVectorize (via a thin FFI shim invoking opt -passes=loop-vectorize) as an external oracle (ADR-13) on the differential-llvm/ bucket. vec-fuzz defines four libFuzzer-style targets: deps (random loop body → dependence analysis converges without panic), legality (random loop → verdict is internally sound, i.e. Legal never contradicts a re-derived dependence check), loop (random legal loop → vectorized and scalar outputs match), and differential (random loop → this pass and LLVM agree, modulo documented fast-math divergence). CI runs each target 5 minutes per commit (M12's CI gate); a 24-hour extended run gates nightly builds; a 30-day continuous soak (ADR-18) gates release tags.

21.3 Deliverable

A green differential-llvm/ bucket, four running fuzz targets with recorded corpus growth, and a vec-bench report confirming M1–M12 performance targets.

21.4 Acceptance Criteria

100% agreement with LLVM LoopVectorize on the differential corpus modulo documented fast-math divergence (M10); fuzz targets sustain ≥ 5,000 exec/sec (M12-adjacent); the 24-hour CI fuzz gate finds 0 new crashes/mismatches before merge; the 30-day soak finds 0 panics before a release tag is cut.

21.5 Conformance Fixtures

differential-llvm/gemm_corpus.vecfix — full Polybench-analog gemm, cross-checked against opt -passes=loop-vectorize; fuzz/corpus/deps_seed_001 through _050 — seed corpus for the deps fuzz target; fuzz/corpus/differential_seed_001 through _020 — seed corpus biasing the fuzzer toward known-tricky patterns (non-affine subscripts, mixed-type reductions).

21.6 Pitfalls

Treating a fast-math-driven divergence from LLVM as a bug — must be classified and documented (both compilers reassociate differently at the bit level; only the presence or absence of reassociation under the flag is checked, not bit-for-bit reduction order). Under-resourcing the fuzz corpus's seed diversity, converging the fuzzer onto one code-pattern family and leaving whole classes (e.g. deeply nested loops) unexplored for months.

21.7 Performance Concerns

vec-interp's deliberate lack of optimization (§12.2) makes it the throughput floor for the entire differential harness — the corpus run's 10-minute budget (§21.4-adjacent) must account for interpreter execution time dominating, not vectorizer compile time.

21.8 Edge Cases

A fuzz-generated loop that is legal but whose scalar execution itself does not terminate in bounded time (an accidental infinite loop from mutation) — the harness must enforce a per-execution wall-clock timeout and classify as "skipped," not "hung." A fuzz case that triggers a vec-interp bug rather than a vectorizer bug — must be distinguishable (dual- run against LLVM's interpreter-equivalent, lli, as a tertiary check when vec-interp and the vectorizer disagree, to localize which side is wrong).

21.9 Failure Analysis

Any fuzz-found divergence between scalar and vector output is filed as a miscompile (FM-1) regardless of how rare the triggering pattern — this phase's entire purpose is to make "rare" detectable before release. Detection: the differential/fuzz targets themselves. Blast radius assessment: every fixture matching the same code-shape family is re-run against the fix before it is trusted. Recovery: bisect via the deterministic (I10) build to the exact commit; add the minimized fuzz case to the permanent deps/, legality/, or loop/ bucket as a regression fixture.

21.10 Operational Notes

Emits differential_mismatch_total (should be 0, release-blocking if nonzero), fuzz_exec_per_sec, fuzz_corpus_size, fuzz_crash_total; the 30-day soak canary runs as a scheduled CI workflow (fuzz.yml) with results published to docs/performance/; rollback path for a release with a late-discovered divergence is to un-tag the release and re-run the full corpus against the previous known-good commit.

25. Compatibility & Versioning

Wire/storage compatibility: not applicable — no persisted wire format; VPlan is an in-memory, per-invocation structure never serialized except for fixture snapshots (.vecfix files, versioned alongside the fixture corpus, §10). Schema evolution: a .vecfix fixture's schema is versioned by a schema_version field; a fixture-runner version only accepts schema versions it recognizes, erroring explicitly rather than silently misinterpreting an old/new fixture. API stability: vec-ir's public surface (the adapter over host IR types) is the one API contract external crates depend on; SemVer applies — a breaking change to Loop, Place, or LegalityVerdict's public fields is a major version bump. Migration: a major version bump ships a migration note in CHANGELOG.md naming every renamed/removed field and its replacement. Deprecation policy: a deprecated API surface is marked #[deprecated] for one minor version cycle before removal. SemVer policy: vec-* crates version in lockstep (workspace-wide version, ADR-20's crate-topology choice) to avoid combinatorial version- skew across the 17 crates. Rolling-upgrade guarantees: a host compiler may run two vectorizer versions side-by-side during a migration window (e.g. for A/B correctness comparison) since each pass invocation is stateless and carries no cross-invocation version assumptions (P7).

26. Testing & Verification Strategy

Unit: per-crate, exercising each function's contract in isolation (e.g. analyze_stride against synthetic SCEV expressions without a full loop). Integration: the conformance buckets (§10), one per phase, each asserting phase-level input/output contracts. Property: vec-cost's determinism property (I6: same input twice → same Cost) and vec-legality's soundness property (a Legal verdict's max_vf never exceeds the true dependence-distance bound) are checked via proptest-style generated loop shapes. Differential: Phase 9's vec-diff against vec-interp and LLVM LoopVectorize (I1, ADR-13) — the primary correctness backstop tied to every invariant in §7 via the debugging methodology's per-invariant assertions. Fuzzing: Phase 9's four libFuzzer targets (deps, legality, loop, differential), CI-gated at 5 minutes/commit, 24h nightly, 30-day pre-release soak (ADR-18). Chaos: not applicable in the traditional sense (no distributed runtime) — the closest analog is fuzzing with adversarially malformed IR inputs (§12.5's malformed_ir.vecfix pattern, generalized across every phase's bucket). Deterministic replay: every fixture run is deterministic (I10) by construction, making replay trivial — no seed/clock capture needed. Soak: the 30-day fuzz canary (§21.10). Fault injection: malformed-IR and malformed-fixture cases are injected per phase (§12.5, §14.5, §15.5 patterns) to verify graceful Err returns rather than panics. Conformance: the per-phase buckets (§10) are the conformance suite; performance-regression gating: vec-bench's M1–M12 thresholds (§28) gate CI, blocking merge on regression beyond a 10% tolerance band.

Artifact signing: release artifacts (the vec-cli conformance runner binary, when distributed standalone) are signed with a maintainer GPG key; signatures published alongside CHANGELOG.md entries. 29. Scalability Analysis

Constant vs. grows: per-loop analysis cost is O(1) in module size (each loop analyzed independently, P7); whole-module compile time is O(number of loops) — linear, not superlinear, because no cross-loop shared mutable state creates coordination overhead. Named bottlenecks, in order: (1) the Omega test's O(2^depth) worst case on deep nests — bounded by the depth-6 cap (§4); (2) SLP tree search's exponential-in-tree-depth worst case — bounded by the depth-6 cap (§20.7); (3) VPlan construction's per-candidate-VF allocation cost (§28) — bounded by the small legal_vfs() candidate set (typically 3-4 values, §16.7). Horizontal scaling: functions vectorize independently and in parallel across a host compiler's thread pool (P7's statelessness is what makes this free — I6). Vertical scaling: a single loop's analysis does not itself parallelize (the algorithms are inherently sequential per loop); more cores help only via more concurrent function-level invocations. Sharding/partitioning: not applicable (no persisted state to shard) — the natural partition unit is already "one function per invocation." Coordination overhead: zero by design (P7) — no locks, no shared cache, no cross-invocation synchronization. Practical ceiling: bounded by the depth-6 caps on Omega and SLP tree search (§4) — a loop nest or basic block exceeding those bounds degrades to conservative rejection rather than unbounded analysis time, trading optimization opportunity for a hard compile-time ceiling. Levers beyond the ceiling: raising the depth cap trades compile-time budget for deeper-nest coverage (a tunable, not a redesign); a future incremental/cached SCEV-aware re-analysis (deferred, §35) would amortize cost across incremental recompilation.

30. Mental Models & First Principles

  • MM1 — Legality is a monotone predicate over dependence distance; profitability is a cost race against a scalar baseline. Predicts: raising VF can only ever tighten legality (never loosen it), while profitability can flip either direction as VF changes. Bug class without it: engineers conflate "vectorizes at VF 4" with "vectorizes at any VF," missing the per-VF legality re-check. Applied in §8.2, §15 (Phase 3).
  • MM2 — A VPlan is a cost-comparable staging area, not a final IR. Predicts: any candidate can be discarded with zero cleanup cost, because nothing outside vec-vplan has observed it yet. Bug class without it: engineers try to "partially commit" a candidate before costing, reintroducing the rollback problem P2 exists to avoid. Applied in §3.2, §17 (Phase 5).
  • MM3 — Vectorization is instruction-level SPMD: same instruction stream, disjoint data lanes. Predicts: any construct that needs different instructions per lane (genuine control-flow divergence) needs masking (§19), not raw vectorization. Bug class without it: attempting to vectorize a loop with per-iteration function-pointer dispatch directly instead of recognizing it needs if-conversion or rejection. Applied in §8.3, §19 (Phase 7).
  • MM4 — SLP is loop vectorization's dual: parallelism across statements instead of across iterations. Predicts: any kernel with zero loops but repeated isomorphic scalar code (color conversion, quaternion math) is an SLP candidate, never a loop- vectorization one. Bug class without it: engineers try to "find the loop" in inherently loop-free kernels and miss the opportunity entirely. Applied in §8.4, §20 (Phase 8).
  • MM5 — A mask is a runtime legality proof deferred to execution. Predicts: masking is the general escape hatch whenever static analysis can prove disjointness/safety only conditionally, not just for control flow. Bug class without it: engineers reach for loop multiversioning (ADR-16's rejected alternative) even when a mask would be simpler and cheaper. Applied in §8.3, §19.2.
  • MM6 — The epilog is the tax vectorization pays for not dividing evenly. Predicts: the epilog's cost is proportional to how often trip counts are not multiples of VF in the target workload — profile-guided VF selection (deferred, §35) exists precisely to minimize this tax. Bug class without it: engineers try to eliminate the epilog entirely instead of minimizing its expected frequency. Applied in §17.2; anchors the deferred profile-guided-VF feature in §35.
  • MM7 — Fast-math is a semantics contract, not a performance switch. Predicts: any user who flips it without understanding reassociation gets numerically different (not just faster) results — the contract, not the flag name, is what matters. Bug class without it: treating -ffast-math-equivalent flags as free performance, discovering the numerical drift only in production. Applied in §15.2, I7, P5.
  • MM8 — Alias-analysis precision is the vectorizer's fuel. Predicts: every improvement to the host compiler's AliasAnalysis precision directly increases the vectorization rate (M10) without any change to this pass at all. Bug class without it: engineers tune the cost model or legality check to compensate for weak AA, when the actual lever is upstream. Applied in §18.2, T4.

32. Back-of-Envelope Capacity Model

  1. Max live vector temporaries before spill risk = register file size × 0.67 (empirical pressure-penalty threshold, §16.2) = 32 × 0.67 ≈ 21 ZMM registers on AVX-512 before the cost model's nonlinear pressure penalty engages (chained from §4's register-file-size row).
  2. Omega worst-case subproblem count = 2^(max analyzed depth) = 2^6 = 64 inequality systems per dependence pair (chained from §4's depth-cap row) — the hard ceiling behind M1's p99 latency budget.
  3. Compile-time budget per loop = whole-function budget ÷ expected loops per function = 30,000 ms ÷ ~40 loops/function (typical numerical-kernel density) ≈ 750 ms nominal per-loop ceiling, well above the ≤ 100 ms p99 sum of M1–M4, leaving headroom for Phase 5–8's transform cost (chained from §4's M7 row).
  4. Vector body code-size multiplier = 1 (vector body) + 1 (scalar epilog, always emitted, P14) = 2× worst-case code growth per vectorized loop, before accounting for any runtime alias-check branch (chained from §17.2/§18.2).
  5. Alignment padding requirement = cache line size ÷ element size = 64 ÷ 4 (f32) = 16 elements per cache line — the natural alignment boundary the cost model's memory-op cost table assumes for "aligned" access classification (chained from §4's cache-line-size row).
  6. Bandwidth-bound crossover point = memory bandwidth ÷ (VF × element size × clock rate) = 40 GB/s ÷ (16 × 4 bytes × 3 GHz) ≈ 0.208, i.e. below 1 — meaning a VF-16 f32 stream kernel at 3 GHz is memory-bandwidth-bound, not compute-bound, on the reference hardware (chained from §4's bandwidth and vector-width rows); this is the quantitative justification for why M8/M9's speedup targets are capped at 4× rather than the naive 16× VF would suggest.
  7. Expected aggregate corpus speedup = vectorization rate × per-loop speedup = 0.70 × 4× ≈ 2.8× whole-corpus speedup, a lower bound since un-vectorized loops contribute 1× (chained from M10 × M8).
  8. Fuzz canary throughput requirement = target unique-pattern coverage ÷ soak duration = (assume ~10^8 distinct code shapes worth sampling) ÷ (30 days × 86,400 s) ≈ 38.6 execs/sec minimum sustained rate to plausibly sample the space once — comfortably below the ≥ 5,000 execs/sec target (M12-adjacent), leaving ~130× headroom (chained from ADR-18's 30-day soak duration).
  9. SLP tree-search worst case = branching factor^depth = (typical basic block, ~4 operands/level)^6 ≈ 4,096 candidate paths per seed, bounding §20.7's depth-cap rationale (chained from §20.7's depth-6 cap, mirroring MM1's dependence-depth reasoning).
  10. Gather/scatter cost multiplier (approximate, from vendor manuals, §5 Required Reading) ≈ 4–8× a contiguous load/store's cycle cost on AVX-512 — the quantitative floor behind ADR-14's "cost-penalized, not rejected" decision (chained from the cost-model calibration inputs referenced in §16.2).

34. Alternative Architectures (Roads Not Taken)

A1 — Polyhedral whole-nest scheduling (Polly-style).

┌─────────────────────────────────────────────┐
│ Loop nest → affine iteration-domain polytope │
│  → ISL exact dependence + legal schedule set │
│  → chosen schedule (fusion/tiling/vec/interchange) │
└─────────────────────────────────────────────┘

Regime where it wins: regular, affine-bounded numerical kernels (dense linear algebra, stencils) where loop-interchange/fusion/tiling opportunities dominate simple vectorization gains. Real system: Polly (LLVM). Rejected here: exact polyhedral scheduling is exponential in nest depth in the worst case and requires the entire nest to be affine — this design's scope (§1) is deliberately narrower (single innermost loop + SLP) to stay within the compile-time budget (§4) for the general, not-necessarily-affine case.

│  → compiler emits SIMD with zero dep. proof │
└───────────────────────────────────────────┘

Regime where it wins: performance-engineering teams already thinking in explicit- parallel terms (graphics, ray tracing) who accept a language-level contract in exchange for zero dependence-analysis compile-time cost and zero risk of an overly-conservative legality rejection. Real system: ISPC. Rejected here: this pass targets existing scalar code with no independence contract — proving legality automatically is the whole point (§1's problem statement).

A3 — Schedule-separated-from-algorithm (Halide-style).

┌────────────────────────────────────────────┐
│ Algorithm (what to compute) — pure, no VF   │
│ Schedule (how: vectorize/tile/unroll) — separate, explicit │
│  → compiler composes the two independently  │
└────────────────────────────────────────────┘

Regime where it wins: image-processing/tensor pipelines where the same algorithm needs many different hand-tuned schedules across targets, and expert-authored schedules consistently beat any automatic cost model. Real system: Halide. Rejected here: this design targets automatic vectorization of pre-existing scalar code with no separate schedule language — introducing one would shift the entire project's scope from a compiler pass to a DSL.

A4 — SIMT/GPU data-parallel model instead of SIMD.

┌─────────────────────────────────────────┐
│ Each loop iteration → one GPU thread     │
│  → massive over-subscription hides latency│
│  → no vector-register-width ceiling at all│
└─────────────────────────────────────────┘

Regime where it wins: workloads with enough independent parallelism to amortize kernel- launch/transfer overhead and hide memory latency via thread over-subscription rather than a fixed VF ceiling. Real system: CUDA/PTX (NVIDIA GPUs). Rejected here: this design targets CPU middle-end code generation with no host-device transfer model, no kernel- launch overhead accounting, and no thousands-of-threads scheduling model — a fundamentally different execution substrate than the SIMD lanes assumed throughout (§4).

36. Glossary

  • AVX/AVX2/AVX-512: x86-64 vector ISA extensions, 256/256/512-bit widths respectively.
  • Banerjee test: a fast, approximate dependence test bounding a linear inequality system over the iteration-space box (Banerjee 1988).
  • Cost model: a target-dispatched function estimating throughput/latency/register- pressure for a candidate vectorized instruction sequence.
  • Dependence: an ordering constraint between two memory accesses that must be preserved for correct execution.
  • Dependence graph: the set of DependenceEdges for a loop body, labeled by kind, direction, and distance.
  • Direction vector: per-loop-level classification of a dependence's direction (<, >, =, *).
  • Distance vector: per-loop-level exact iteration-count gap of a dependence, when computable.
  • Epilog (remainder loop): the scalar loop handling the n mod VF iterations not covered by the vector loop.
  • Fast-math contract: an explicit flag permitting floating-point reassociation, required before FP reduction vectorization.
  • Gather: a vector load from non-contiguous (indexed) addresses.
  • GCD test: the cheapest dependence prefilter, based on integer divisibility of subscript coefficients.
  • If-conversion: converting a data-dependent branch in a loop body into predicated (masked) straight-line code.
  • Isomorphic (SLP): two operation trees matching in opcode and operand count at every level, a precondition for packing.
  • Legality: the property that vectorizing a given loop/block preserves program semantics.
  • LegalityVerdict: the Legal{hints}/Illegal{reason} output of vec-legality.
  • Loop-carried dependence: a dependence between two accesses in different iterations of the same loop.
  • Mask: a per-lane boolean vector controlling which lanes of a vector operation execute/write.
  • NEON: the aarch64 SIMD ISA extension.
  • Omega test: an exact integer-linear-programming dependence test (Pugh 1992), exponential worst case.
  • Predication: executing an operation unconditionally but committing its effect only on masked-true lanes.
  • Profitability: the cost-model judgment that a legal vectorization is worth performing versus the scalar baseline.
  • Reduction: a loop that accumulates a scalar result across iterations (acc OP= expr).
  • Register pressure: the count of simultaneously live vector temporaries relative to a target's register file size.
  • Scalar evolution (SCEV): an analysis expressing a value's per-iteration evolution as a closed-form (often affine) expression.
  • Scatter: a vector store to non-contiguous (indexed) addresses.
  • Semantics preservation: the property that a transformed program's observable behavior matches the original on every legal input.
  • SIMD (Single Instruction, Multiple Data): one instruction operating on multiple data lanes simultaneously.
  • SLP (Superword-Level Parallelism): vectorization of isomorphic straight-line (loop-free) code (Larsen & Amarasinghe 2000).
  • Stride: the byte distance between consecutive per-iteration accesses of the same place.
  • Strip-mining: transforming a scalar loop into a vector-body loop plus a remainder, stepping the induction variable by VF.
  • Trust boundary (legality): the point past which no downstream stage re-verifies a LegalityVerdict::Legal's soundness.
  • Unit stride: a stride equal to the element size (fully contiguous access).
  • VF (Vector Factor): the number of scalar iterations executed per vector loop iteration.
  • VPlan: the staged, explicit vector-plan IR built per candidate before any original-IR mutation.
  • VPInstruction: one node of a VPlan (e.g. VPLoad, VPArith, VPReduce).
  • Vectorization rate: the fraction of eligible loops in a corpus actually vectorized.
