Hard questions (§33)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does a positive-distance dependence not simply block vectorization the way a negative-distance one does, and what exactly bounds the legal VF in that case? (§8.2, §15.2)
  2. Why is VPlan built once per candidate rather than mutating the original IR per candidate VF, and what would break if that were reversed? (§3.2, §17.2)
  3. Under what conditions does the Banerjee test return "maybe" where the GCD test already returned "no dependence," and why does the ladder still check GCD first? (§8.2, §14.2)
  4. Why must a LegalityVerdict::Illegal always name a specific instruction/edge rather than a generic rejection, and what operational capability would be lost without it? (§6 P11, §15.2)
  5. Why does the fast-math contract gate FP reduction vectorization but not integer reduction vectorization? (§6 P5, §15.2 item d)
  6. Why is the epilog loop mandatory even when a target has cheap masked execution available, and under what regime would folding the tail into a masked main loop actually win? (§6 P14, ADR-09)
  7. Why does register pressure bound VF selection even on a target with a large register file, and what does the pressure-penalty's nonlinearity (§32 item 1) model that a linear penalty would miss?
  8. Why is a runtime alias check inserted only when static AA is inconclusive rather than unconditionally, and what does the "when the rejected choice wins" column of ADR-08 say about when unconditional checking is actually correct?
  9. Why does SLP run after loop vectorization rather than before, given that both are "vectorization"? (§6 P9, §8.4, ADR-11)
  10. What specific property of x86/aarch64 masked loads/stores does I13's "no fault on masked-off lanes" claim depend on, and what would have to change in Phase 7 if that ISA property didn't hold? (§7 I13, §19.2)
  11. Why is the Omega test bounded by loop-nest depth rather than by a wall-clock timeout directly, and how does that choice interact with the compile-time budget in §4? (§8.2, §32 item 2)
  12. Why is LLVM LoopVectorize chosen as an external oracle rather than trusting property tests alone, and what specific bug class would property tests miss? (§6 P12, ADR-13)
  13. What would have to be true of a target's cost model for gather/scatter to never be worth the penalty, and does any target in scope (§4) actually meet that condition? (ADR-14, §32 item 10)
  14. Why does the design treat "vectorization rate" (M10) as a soft SLO while "differential mismatch" (part of M12) is a hard release-blocking gate — what principle in §1/§4 justifies that asymmetry?
  15. How does the depth-6 cap chosen for dependence analysis (§4) also end up bounding SLP's tree-search cost (§20.7), and is that a coincidence or a shared design rationale? (§32 items 2 and 9)
  16. Why is vec-interp deliberately unoptimized, and what would be lost if it were optimized to match the vectorizer's own performance? (§12.2, P12)
  17. Under what real-world workload does the bandwidth-bound crossover (§32 item 6) mean that increasing VF from 8 to 16 yields no additional speedup at all, and how would the cost model need to change to detect that automatically rather than relying on the fixed 4× target? (§4, §32 item 6, §16.2)
  18. Why does Polly's whole-nest polyhedral approach (§31, §34) subsume this design's dependence analysis in principle, and what specific scope limitation (§1) explains why this design does not simply adopt it? (§1, §31, §34)

30. Mental Models & First Principles

  • MM1 — Legality is a monotone predicate over dependence distance; profitability is a cost race against a scalar baseline. Predicts: raising VF can only ever tighten legality (never loosen it), while profitability can flip either direction as VF changes. Bug class without it: engineers conflate "vectorizes at VF 4" with "vectorizes at any VF," missing the per-VF legality re-check. Applied in §8.2, §15 (Phase 3).
  • MM2 — A VPlan is a cost-comparable staging area, not a final IR. Predicts: any candidate can be discarded with zero cleanup cost, because nothing outside vec-vplan has observed it yet. Bug class without it: engineers try to "partially commit" a candidate before costing, reintroducing the rollback problem P2 exists to avoid. Applied in §3.2, §17 (Phase 5).
  • MM3 — Vectorization is instruction-level SPMD: same instruction stream, disjoint data lanes. Predicts: any construct that needs different instructions per lane (genuine control-flow divergence) needs masking (§19), not raw vectorization. Bug class without it: attempting to vectorize a loop with per-iteration function-pointer dispatch directly instead of recognizing it needs if-conversion or rejection. Applied in §8.3, §19 (Phase 7).
  • MM4 — SLP is loop vectorization's dual: parallelism across statements instead of across iterations. Predicts: any kernel with zero loops but repeated isomorphic scalar code (color conversion, quaternion math) is an SLP candidate, never a loop- vectorization one. Bug class without it: engineers try to "find the loop" in inherently loop-free kernels and miss the opportunity entirely. Applied in §8.4, §20 (Phase 8).
  • MM5 — A mask is a runtime legality proof deferred to execution. Predicts: masking is the general escape hatch whenever static analysis can prove disjointness/safety only conditionally, not just for control flow. Bug class without it: engineers reach for loop multiversioning (ADR-16's rejected alternative) even when a mask would be simpler and cheaper. Applied in §8.3, §19.2.
  • MM6 — The epilog is the tax vectorization pays for not dividing evenly. Predicts: the epilog's cost is proportional to how often trip counts are not multiples of VF in the target workload — profile-guided VF selection (deferred, §35) exists precisely to minimize this tax. Bug class without it: engineers try to eliminate the epilog entirely instead of minimizing its expected frequency. Applied in §17.2; anchors the deferred profile-guided-VF feature in §35.
  • MM7 — Fast-math is a semantics contract, not a performance switch. Predicts: any user who flips it without understanding reassociation gets numerically different (not just faster) results — the contract, not the flag name, is what matters. Bug class without it: treating -ffast-math-equivalent flags as free performance, discovering the numerical drift only in production. Applied in §15.2, I7, P5.
  • MM8 — Alias-analysis precision is the vectorizer's fuel. Predicts: every improvement to the host compiler's AliasAnalysis precision directly increases the vectorization rate (M10) without any change to this pass at all. Bug class without it: engineers tune the cost model or legality check to compensate for weak AA, when the actual lever is upstream. Applied in §18.2, T4.

5. Required Reading

Books

  • Allen, R. & Kennedy, K., Optimizing Compilers for Modern Architectures, Morgan Kaufmann, 2002. Ch. 2 (Dependence Analysis), Ch. 5 (Loop Transformations), Ch. 9–11 (vectorization). Extract: the direction-vector formalism and the fundamental vectorization theorem. Applied in §8.2, §14 (Phase 2).
  • Wolfe, M., High Performance Compilers for Parallel Computing, Addison-Wesley, 1995. Ch. 4–7 (dependence testing variants, loop restructuring). Extract: the taxonomy of dependence tests beyond Banerjee (I-test, Delta test) and why a ladder of cheap-then-exact tests dominates a single exact test. Applied in §8.2, ADR-04.
  • Muchnick, S., Advanced Compiler Design and Implementation, Morgan Kaufmann, 1997. Ch. 9 (dependence analysis), Ch. 20 (instruction scheduling — the legality/profitability split recurs). Extract: the general pattern of an analysis producing a conservative-but-sound answer under uncertainty. Applied in §15 (Phase 3), P1.
  • Banerjee, U., Dependence Analysis for Supercomputing, Kluwer, 1988. The full derivation of the Banerjee inequality test. Extract: the linear-inequality bound derivation used directly in vec-deps. Applied in §14 (Phase 2), ADR-04.
  • Banerjee, U., Loop Transformations for Restructuring Compilers: The Foundations, Kluwer, 1993. Extract: loop normalization prerequisites (induction-variable canonicalization) that stride analysis depends on. Applied in §13 (Phase 1).
  • Cooper, K. & Torczon, L., Engineering a Compiler, 2nd ed., Morgan Kaufmann, 2011. Ch. 10 (scheduling), Ch. 8 (SSA, useful for the IR adapter). Extract: a from-scratch, implementation-oriented treatment that grounds the abstract dependence theory in concrete data structures. Applied in §11 (Core Schema), §13.

Papers

  • Larsen, S. & Amarasinghe, S., "Exploiting Superword Level Parallelism with Multimedia Instruction Sets," PLDI 2000. The SLP algorithm this pass's vec-slp directly implements (seed identification, tree packing). Applied in §8.4, §20 (Phase 8).
  • Pugh, W., "The Omega Test: A Fast and Practical Integer Programming Algorithm for Dependence Analysis," Supercomputing 1991 / CACM 1992. The exact fallback test. Applied in §8.2, §14 (Phase 2), ADR-04.
  • Kuck, D., Kuhn, R., Padua, D., Leasure, B., Wolfe, M., "Dependence Graphs and Compiler Optimizations," POPL 1981. The dependence-graph formalism (Kuck et al.) underlying DependenceGraph. Applied in §8.2, §11.
  • Kuck, D., Muraoka, Y., Chen, S., "On the Number of Operations Simultaneously Executable in Fortran-Like Programs and Their Resulting Speedup," IEEE Trans. Computers, 1972. The original parallelism-bound analysis motivating dependence distance vectors. Applied in §8.2.
  • Nuzman, D. & Zaks, A., "Outer-Loop Vectorization: Revisited for Short SIMD Architectures," PACT 2008. Outer-loop vectorization — the deferred feature's design reference. Applied in §35 (Deferred Features Register).
  • Nuzman, D., Rosen, I., Zaks, A., "Auto-Vectorization of Interleaved Data for SIMD," PLDI 2006. Interleaved-access (structure-of-arrays) vectorization technique informing the stride classifier's Linear case. Applied in §8.1, §13 (Phase 1).
  • Padua, D. & Wolfe, M., "Advanced Compiler Optimizations for Supercomputers," CACM 1986. Foundational survey connecting dependence analysis to vectorizing/parallelizing transforms. Applied in §2, §8.2.
  • Allen, R. & Kennedy, K., "Automatic Translation of FORTRAN Programs to Vector Form," ACM TOPLAS, 1987. The original algorithm for the legality→transform pipeline this blueprint's Phase 3→5 sequence mirrors. Applied in §15 (Phase 3), §17 (Phase 5).
  • Maleki, S. et al., "An Evaluation of Vectorizing Compilers," PACT 2011. Empirical study of GCC/ICC/LLVM autovectorization effectiveness — the source of the ≥70% vectorization-rate target in §4. Applied in §4, §16 (Phase 4).

Reference Implementations

  • LLVM lib/Transforms/Vectorize/LoopVectorize.cpp + VPlan.h/VPlan.cpp. Study: the LoopVectorizationLegality/LoopVectorizationCostModel split. Lesson: legality and cost are separate classes with no shared mutable state. Pitfall not to copy: the historical pre-VPlan direct-IR-mutation path (retired) — do not replicate that design. Applied in §15, §16, §17.
  • LLVM lib/Transforms/Vectorize/SLPVectorizer.cpp. Study: seed-selection heuristics and the BoUpSLP tree-building class. Lesson: reordering commutative operands to enable packing. Pitfall: unbounded tree-search cost on pathological inputs — bound depth. Applied in §8.4, §20.
  • GCC gcc/tree-vect-loop.cc, tree-vect-slp.cc, tree-vect-data-refs.cc. Study: the stmt_vec_info side-table design (metadata attached without mutating the IR). Lesson: side-table annotation avoids IR-cloning churn during analysis. Applied in §11 (Core Schema), §13.
  • ISPC (github.com/ispc/ispc, src/opt.cpp). Study: gather/scatter lowering heuristics and the explicit SPMD-on-SIMD execution model. Lesson: an explicit programming model sidesteps legality proof entirely — the alternative-architecture contrast in §34. Pitfall not to copy: ISPC assumes the programmer already proved independence; this pass may not. Applied in §19 (Phase 7), §34.
  • Cranelift (bytecodealliance/wasmtime, cranelift/codegen). Study: the egraph-based rewrite infrastructure and its narrow, conservative autovectorization. Lesson: a JIT-tier compiler trades vectorization completeness for compile-time budget — informs the compile-time constraints in §4. Applied in §4, §33.
  • Polly (llvm/polly). Study: ISL-based polyhedral dependence and scheduling for whole loop nests. Lesson: exact integer-set dependence analysis generalizes the Omega test to nests; the trade is exponential-in-depth cost. Applied in §8.2, §34 (Alternative Architectures).

RFCs / Specifications

  • LLVM Language Reference Manual — Fast-Math Flags. Defines reassoc, nnan, ninf etc.; the exact contract vec-legality checks before permitting FP reduction vectorization. Applied in §15 (Phase 3), I7.
  • LLVM LoopVectorize pass documentation. The canonical description of the legality/cost/transform pipeline this blueprint's architecture (§3) follows. Applied in §3, §17.

Glossary (§36) · 36 terms · site-wide glossary

AVX/AVX2/AVX-512
: x86-64 vector ISA extensions, 256/256/512-bit widths respectively.
Banerjee test
: a fast, approximate dependence test bounding a linear inequality system over the iteration-space box (Banerjee 1988).
Cost model
: a target-dispatched function estimating throughput/latency/register- pressure for a candidate vectorized instruction sequence.
Dependence
: an ordering constraint between two memory accesses that must be preserved for correct execution.
Dependence graph
: the set of DependenceEdges for a loop body, labeled by kind, direction, and distance.
Direction vector
: per-loop-level classification of a dependence's direction (<, >, =, *).
Distance vector
: per-loop-level exact iteration-count gap of a dependence, when computable.
Epilog (remainder loop)
: the scalar loop handling the n mod VF iterations not covered by the vector loop.
Fast-math contract
: an explicit flag permitting floating-point reassociation, required before FP reduction vectorization.
Gather
: a vector load from non-contiguous (indexed) addresses.
GCD test
: the cheapest dependence prefilter, based on integer divisibility of subscript coefficients.
If-conversion
: converting a data-dependent branch in a loop body into predicated (masked) straight-line code.
Isomorphic (SLP)
: two operation trees matching in opcode and operand count at every level, a precondition for packing.
Legality
: the property that vectorizing a given loop/block preserves program semantics.
LegalityVerdict
: the Legal{hints}/Illegal{reason} output of vec-legality.
Loop-carried dependence
: a dependence between two accesses in different iterations of the same loop.
Mask
: a per-lane boolean vector controlling which lanes of a vector operation execute/write.
NEON
: the aarch64 SIMD ISA extension.
Omega test
: an exact integer-linear-programming dependence test (Pugh 1992), exponential worst case.
Predication
: executing an operation unconditionally but committing its effect only on masked-true lanes.
Profitability
: the cost-model judgment that a legal vectorization is worth performing versus the scalar baseline.
Reduction
: a loop that accumulates a scalar result across iterations (acc OP= expr).
Register pressure
: the count of simultaneously live vector temporaries relative to a target's register file size.
Scalar evolution (SCEV)
: an analysis expressing a value's per-iteration evolution as a closed-form (often affine) expression.
Scatter
: a vector store to non-contiguous (indexed) addresses.
Semantics preservation
: the property that a transformed program's observable behavior matches the original on every legal input.
SIMD (Single Instruction, Multiple Data)
: one instruction operating on multiple data lanes simultaneously.
SLP (Superword-Level Parallelism)
: vectorization of isomorphic straight-line (loop-free) code (Larsen & Amarasinghe 2000).
Stride
: the byte distance between consecutive per-iteration accesses of the same place.
Strip-mining
: transforming a scalar loop into a vector-body loop plus a remainder, stepping the induction variable by VF.
Trust boundary (legality)
: the point past which no downstream stage re-verifies a LegalityVerdict::Legal's soundness.
Unit stride
: a stride equal to the element size (fully contiguous access).
VF (Vector Factor)
: the number of scalar iterations executed per vector loop iteration.
VPlan
: the staged, explicit vector-plan IR built per candidate before any original-IR mutation.
VPInstruction
: one node of a VPlan (e.g. VPLoad, VPArith, VPReduce).
Vectorization rate
: the fraction of eligible loops in a corpus actually vectorized.
