Hard questions (§33)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does a cold EPT_VIOLATION cost ~10 ms while a warm one costs ~5 us, and what would change if guest RAM were backed by a tmpfs file instead of anonymous memory? (§8.3, §15.7)
  2. Trace exactly which invariant (I1-I13) would be violated if two vCPU threads shared a single Vcpu struct without a lock, and why adding a lock is still the wrong fix. (§7, P2)
  3. Why does pre-copy migration need an iteration cap (I12) but a theoretically "perfect" convergence algorithm would not - what guest workload characteristic makes the cap necessary in practice? (§20.2, §32 item 3)
  4. What is the concrete mechanism by which the KVM/userspace split (ADR-01) reduces this project's own CVE surface relative to a from-scratch bare-metal hypervisor, and where does that argument break down? (§3, §22, §34)
  5. Why is TPR-gating of interrupt delivery not a bug even though it looks identical to a missed-interrupt bug from the outside? What two pieces of evidence distinguish them? (§16.8, MM5)
  6. Derive, from the System Constraints table alone, why a 128 GiB guest's dirty bitmap does not become the migration bottleneck even at the memory ceiling. (§4, §32 item 1)
  7. Why does this design reject emulated legacy PCI devices (ADR-06) but QEMU does not, and under what guest-compatibility regime does QEMU's choice become mandatory rather than optional? (ADR-06, §31)
  8. What specific sequencing bug does I8 (migration record ordering) prevent, and why would a naive "apply CPU state as soon as it arrives" implementation be unsafe even on a reliable network? (§7, §20.2, §20.9)
  9. Why does the seccomp jail get installed before device threads start rather than after VM boot completes (ADR-14), and what attack window does the alternative ordering leave open? (§21.2, T9)
  10. Using the capacity model's IOPS derivation, what is the single largest lever available to exceed the current >=1M IOPS target, and what does exercising that lever cost elsewhere in the system? (§32 item 5, §29)
  11. Why is desc.addr + desc.len bounds-checking (I6) insufficient on its own without also bounding chain length (I5) - construct the attack that I6 alone would miss. (§7, §17.6)
  12. Compare this design's fail-closed device-thread panic handling (P10) to a hypothetical fail-open design that logs and continues processing after a caught panic - what invariant would the fail-open version violate first? (P10, §17.9, §23)
  13. Why does the Comparative Architecture Table show Firecracker rejecting live migration entirely rather than implementing a simplified version - what does that imply about migration's engineering cost relative to Firecracker's actual target workload? (§31, ADR-08)
  14. What would have to be true of the host CPU for hyperthreading to be safely left enabled under the T4 side-channel threat, and how would an operator verify it before deploying untrusted multi-tenant VMs? (§22 T4, §24)
  15. Trace the full path (spanning at least two phases) by which a malformed guest cmdline string could have produced a boot hang before the length-bound fix in §19.8 - what made this bug hard to distinguish from a boot-protocol offset bug? (§19.6, §19.8)
  16. Why does this project's Alternative Architectures analysis (§34) reject a type-1 bare-metal redesign for Phase 0-9's scope, but concede it as viable for the same architectural spine "in a future phase" (§1)? What would have to change first? (§1, §34)
  17. Using the Back-of-Envelope model's boot-time derivation (§32 item 10), identify which single component's improvement would most reduce the total, and cross-check against the Deferred Features Register for whether that improvement is already planned. (§32, §35)
  18. Why does M7 (nested-guest overhead) appear in the Performance Engineering table at all when nested virtualization is deferred scope - what does its presence there signal about how deferred features are tracked without polluting the Phase 0-9 acceptance criteria? (§28, §35)
  19. Construct the failure sequence FM-9 (correlated multi-vCPU crash) describes, and explain why the correct operator response (escalate, don't relaunch) differs from every other failure class in §23. (§23, §7)

30. Mental Models & First Principles

  • MM1 - A vCPU is a trap-and-emulate state machine, not a thread abstraction. Predicts: every guest instruction either executes natively (non-root mode) or triggers an exit - there is no third state. Bug class without it: engineers who model a vCPU as "just another OS thread" miss why register state must be fully quiesced before migration (§20.6) - a running thread has no equivalent quiescence requirement. Applies at §8.1, §20.2.
  • MM2 - EPT is a second, host-owned page-table walk, invisible to the guest. Predicts: a guest's own page tables never need host awareness; only the GPA->HPA layer does. Bug class without it: attempting to inspect/modify guest virtual memory from the host without first walking the guest's own (opaque) page tables, then EPT. Applies at §8.3, Phase 3 (§15).
  • MM3 - The virtqueue is a lock-free SPSC-per-direction ring with an adversarial peer. Predicts: every field the guest writes must be validated as if from an attacker, not merely as if from a buggy peer. Bug class without it: trusting desc.len without a bounds check is the single most common virtio backend vulnerability class historically. Applies at §8.5, Phase 5 (§17).
  • MM4 - Migration convergence is a race between dirty-page production rate and network transfer rate, not a fixed-duration operation. Predicts: no amount of iteration count alone guarantees convergence under a sufficiently write-heavy guest. Bug class without it: designing migration without an iteration cap (I12) risks an unbounded operation. Applies at §20.2, §20.6.
  • MM5 - Interrupt delivery is gated by two independent conditions: routing (IOAPIC) and priority (LAPIC TPR). Predicts: a correctly routed IRQ can still be legitimately withheld by TPR, which is not a bug. Bug class without it: engineers debug "missed interrupts" by checking routing alone and miss TPR-gating entirely. Applies at §16.2, §16.8.
  • MM6 - The KVM/userspace split delegates the hardest correctness problem (VMX mechanics) to the most-audited code in the stack. Predicts: this project's own bug surface is concentrated in device emulation and memory management, not in "running the guest," which shapes the entire threat model (§22). Bug class without it: reimplementing VMX-adjacent logic in userspace reintroduces exactly the bug class KVM already eliminated. Applies at §3, ADR-01.
  • MM7 - Every guest-visible failure must degrade to a guest-observable status, never a silent host crash. Predicts: device errors surface through the protocol they were requested over (a virtio status byte, a link-down event), preserving P10's bounded blast radius. Bug class without it: propagating a device-level error as an unhandled panic takes down unrelated devices/vCPUs sharing the process. Applies at §17.9, §18.9, §23.
  • MM8 - Dirty-bit tracking is the only source of truth for "what changed"; there is no alternative signal. Predicts: any migration design not built around KVM_MEM_LOG_DIRTY_PAGES (or an equivalent) must either over-copy (send everything, every iteration) or under-copy (silently miss writes). Bug class without it: an engineer who tries to infer dirty pages from a write-instrumentation layer at the application level duplicates hardware-provided functionality incorrectly. Applies at §8.6, §20.2.

Required reading (§5)

Books

  • Computer Organization and Design (Patterson & Hennessy) — ch. on privilege levels and traps; applied in §8 (VM-exit trap discipline).
  • Operating Systems: Three Easy Pieces (Arpaci-Dusseau) — the virtualization chapters on CPU/memory virtualization as the conceptual scaffold; applied in §1, §8.
  • Intel 64 and IA-32 Architectures Software Developer's Manual, Vol. 3C — ch. 24–33 (VMX); applied throughout §8, §14, §16 (VMCS fields, EPT, APIC virtualization).
  • The Design and Implementation of the FreeBSD Operating System (McKusick et al.) — mmap/VM-subsystem chapters; applied in §15 (guest memory backing).
  • Systems Performance (Gregg) — tail-latency and USE-method chapters; applied in §28 (Performance Engineering).
  • Site Reliability Engineering (Beyer et al.) — postmortem and error-budget chapters; applied in §23 (Failure Modes & Recovery), §24 (Operational Readiness).

Papers

  • Popek, G. & Goldberg, R. — "Formal Requirements for Virtualizable Third Generation Architectures", CACM 1974 — the virtualizable-ISA theorem; applied in §2, §8, ADR-02.
  • Adams, K. & Agesen, O. — "A Comparison of Software and Hardware Techniques for x86 Virtualization", ASPLOS 2006 — binary translation vs. VT-x; applied in §2, ADR-02, Alternative Architectures (§34).
  • Barham, P. et al. — "Xen and the Art of Virtualization", SOSP 2003 — paravirtualization and the dom0 split; applied in §34 (Alternative Architectures).
  • Kivity, A. et al. — "kvm: the Linux Virtual Machine Monitor", Linux Symposium 2007 — the KVM/QEMU split this project's architecture mirrors; applied in §3, §9 ADR-01.
  • Russell, R. — "virtio: Towards a De-Facto Standard For Virtual I/O Devices", ACM SIGOPS OSR 2008 — the virtqueue contract; applied in §8, Phase 5 (§17).
  • Waldspurger, C. — "Memory Resource Management in VMware ESX Server", OSDI 2002 — ballooning and memory overcommit; applied in §29 (Performance Engineering) and Deferred Features Register.
  • Chisnall, D. — "The Definitive Guide to the Xen Hypervisor" (technical report chapters on grant tables) — applied in §34 (Alternative Architectures — shared-memory grant model).
  • Agache, A. et al. — "Firecracker: Lightweight Virtualization for Serverless Applications", NSDI 2020 — minimal device surface and the microVM jailer model; applied in §1, §22, Comparative Architecture Table (§31).

Reference Implementations

  • KVM (torvalds/linux, arch/x86/kvm/, virt/kvm/) — the in-kernel VMX dispatch and EPT management this project's ioctls target; study vmx.c's handle_ept_violation; pitfall: do not copy its nested-VMX complexity into Phase 0; applied in §13, §14, §15 (Phases 1–3).
  • Firecracker (firecracker-microvm/firecracker, src/vmm/src/) — the minimal-device-surface VMM this project's scope most resembles; study src/vmm/src/vstate/vcpu/; pitfall: its jailer assumes a single-purpose process — do not port its network-namespace assumptions wholesale; applied in §21 (ADR-14 jail model) and §31 (Comparative Architecture).
  • crosvm (google/crosvm, src/crosvm/, devices/src/virtio/) — Rust virtio device implementations; study devices/src/virtio/block/; pitfall: its sandboxing uses Chrome OS-specific seccomp policies not portable as-is; applied in §17 (Phase 5 virtio-blk) and §31.
  • Cloud Hypervisor (cloud-hypervisor/cloud-hypervisor, vmm/src/vm.rs) — live-migration implementation; study vmm/src/migration/; pitfall: its VFIO passthrough path is out of this project's scope — do not pull it in prematurely; applied in §20 (Phase 8 live migration).
  • QEMU (qemu/qemu, accel/kvm/kvm-all.c) — the reference KVM client against which Phase 9's differential conformance runs; study accel/kvm/kvm-all.c's memory-slot management; pitfall: QEMU's device model breadth (hundreds of devices) is explicitly not a target — do not scope-creep toward it; applied in §21 (Phase 9 differential conformance).
