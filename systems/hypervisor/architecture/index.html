Userspace VMM box — one process per guest (isolation boundary, T1/T4); owns configuration parsing, device model state, and the vCPU-thread pool. vCPU threads — concurrency boundary: one OS thread per vCPU, blocking in KVM_RUN; no shared mutable vCPU state (I1). Device threads — poll virtqueues; the trust boundary against the guest is here (every descriptor field is guest-controlled, §8). hyp-memory — the persistence-adjacent boundary: the single mmap region backing all guest RAM, registered with KVM so EPT walks resolve without a VM-exit on steady-state access. Migration source/dest — the only network-protocol boundary (§20); TLS-optional TCP stream carrying page + CPU-state records. KVM module — delegated boundary; this project treats it as a fixed, trusted kernel interface, never modifies it. CPU — the hardware trust boundary; VMX root mode (host) vs. non-root mode (guest) is the isolation primitive the entire threat model (§22) rests on.

8. Domain Model

8.1 Guest/Host Execution Model

A vCPU alternates between VMX non-root mode (executing guest instructions natively) and VMX root mode (host handling an exit). The transition guest→host is a VM-exit; host→guest is a VM-entry. The VMCS (Virtual Machine Control Structure) is the hardware- resident record of a vCPU's guest state, host state, and exit-control fields; KVM manages the VMCS in-kernel and exposes vCPU register access to userspace via KVM_GET_REGS/KVM_SET_REGS/KVM_GET_SREGS.

vCPU state machine:

Created --(KVM_RUN)--> Running --(vmexit)--> ExitedForReason(reason)
   ^                                                |
   |            (handler processes reason)          |
   +---------------(KVM_RUN, re-enter)---------------
Running --(guest HLT, no pending IRQ)--> Halted
Running --(fatal: triple fault)--> Crashed

8.2 VMCS / vCPU State

Signature-level only (no register bodies inline — see §11 for CpuRegs). Load-bearing VMCS field groups: guest-state (segment registers, RIP/RSP/RFLAGS, control registers CR0/CR3/CR4), host-state (the values VM-exit restores), exit-control (which events cause an exit — e.g. EXCEPTION_BITMAP, IO_BITMAP), entry-control (interrupt/exception injection fields). KVM's kvm_run shared-memory struct mirrors the subset userspace needs per exit (§14).

8.3 EPT / Second-Level Address Translation

EPT is a second page-table walk: guest-virtual → guest-physical (guest's own page tables, opaque to the host) → guest-physical → host-physical (EPT, host-kernel-managed). Userspace registers guest-physical → host-virtual ranges via KVM_SET_USER_MEMORY_REGION; KVM lazily builds EPT entries on first access (demand paging) and tears them down on unmap. KVM_MEM_LOG_DIRTY_PAGES enables a per-page dirty bitmap in the EPT walker for migration (§8.6).

Worked example — cold EPT violation:

  1. Guest accesses GPA 0x3F00_0000, not yet backed → CPU raises EPT_VIOLATION, VM-exit to host.
  2. Host reads VMCS_EXIT_QUALIFICATION (access type) and the faulting GPA from kvm_run.exit_reason == KVM_EXIT_MMIO or an internal EPT-fault path.
  3. hyp-memory resolves GPA → HVA via its registered-region interval tree (I2 guarantees no ambiguity).
  4. If the host page backing that HVA is not resident (e.g. swapped, or never touched), the host's own page-fault handler pages it in — this is an ordinary userspace page fault, invisible to KVM's ioctl surface.
  5. Host re-issues KVM_RUN; hardware retries the guest instruction; EPT entry is now valid — no further exit for that page until it is unmapped again. Cost: ~10 ms cold (disk), ~5 µs warm (page-cache hit + TLB fill), per §4.

8.4 VM-Exit Handling Model

The exit dispatcher (Phase 2, §14) is an exhaustive match over ExitReason (§11). Canonical reasons: Mmio, Io, Hlt, Shutdown, Hypercall, EptViolation, Interrupted (a host-signal requested re-entry stop), Unknown(u32) (I9's catch-all).

Malformed-input example. A guest that writes an MMIO access spanning a device's register boundary (offset + len overflowing the device's mapped range): the dispatcher's range check (I3) rejects it before calling the device's mmio_write; the access is faulted back as #GP — the device implementation itself never sees an out-of-range offset.

Failure-path example. A device thread panics mid-descriptor-processing (e.g. an unwrap on a corrupt internal state): the panic is caught at the thread boundary (catch_unwind), the device is marked Crashed, its virtqueue is drained with all pending descriptors marked used-with-error, and the vCPU threads continue — a single device failure does not take down the VM (bounded blast radius, §23).

8.5 Virtio Device Model

A virtqueue has three guest-writable/host-readable regions: the descriptor table (vring_desc[]: addr, len, flags, next), the available ring (indices the driver has published), and the host-writable used ring (indices the device has completed). Ordering: the driver writes descriptors, then publishes via the available-ring index with a store-release barrier; the device reads with a load-acquire barrier — required correctness on weakly-ordered hosts (aarch64), moot on x86's TSO but coded portably (P4, Russell 2008).

Sequence table — virtio-blk read request:

Step Actor Action
1 Guest driver builds descriptor chain: header, data buffer, status byte
2 Guest driver appends chain head to available ring, idx += 1 (release)
3 Guest driver writes doorbell MMIO (notify)
4 Device thread wakes, reads available ring (acquire), walks chain
5 Device thread validates every desc.addr/desc.len against I6
6 Device thread performs backing-file I/O (io_uring, async)
7 Device thread writes status byte, appends index to used ring
8 Device thread injects completion interrupt (§16)
9 Guest driver reads used ring, completes the I/O request

8.6 Migration-Adjacent Memory Semantics

Dirty-bit tracking (I4) and the pre-copy loop are covered fully in Phase 8 (§20); the domain-model-relevant fact is that EPT's dirty bitmap is the only mechanism by which userspace learns which guest-physical pages changed between two KVM_GET_DIRTY_LOG calls — there is no alternative source of truth.
