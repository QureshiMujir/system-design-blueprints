Decisions (§9) · 23 ADRs

ADR-01

VMM/kernel split

Chosen

Userspace VMM over host KVM module

Rejected

In-house kernel module; type-1 bare-metal hypervisor

When the rejected choice is right

Building a custom bare-metal hypervisor wins when no trusted host OS exists at all (embedded/firmware-level virtualization)

Why: KVM's VMX handling is already hardened and upstream-maintained (Kivity 2007)

ADR-02

Virtualization technique

Chosen

Hardware-assisted (VT-x/VMCS)

Rejected

Binary translation (Adams & Agesen 2006)

When the rejected choice is right

Binary translation wins on pre-2005 hardware or CPUs lacking VT-x/AMD-V entirely

Why: VT-x avoids the ~20% software-translation overhead their paper measured

ADR-03

Language

Chosen

Rust 1.78+ MSRV

Rejected

C; C++; Go

When the rejected choice is right

C wins for a tiny embedded firmware VMM with no allocator and hard real-time ISR budgets

Why: Memory safety on an untrusted-input-parsing hot path (§1)

ADR-04

Concurrency model

Chosen

One OS thread per vCPU

Rejected

Green threads/async vCPU loop; single-threaded event loop

When the rejected choice is right

An async model wins if vCPU count vastly exceeds host core count (heavy oversubscription), which this project's §4 bound (≤32) does not require

Why: KVM_RUN blocks in-kernel; async would require a dedicated executor thread per vCPU anyway

ADR-05

Guest memory backing

Chosen

Single mmap(MAP_SHARED|MAP_ANONYMOUS) region

Rejected

Multiple smaller regions; file-backed (MAP_SHARED over a file) for persistence

When the rejected choice is right

File-backed memory wins when guest RAM must survive a VMM process restart (persistent-memory guests)

Why: Simplicity; matches KVM's memory-slot model 1:1

ADR-06

Device model

Chosen

virtio-only (net/blk/console)

Rejected

Emulated legacy PCI (e1000, IDE)

When the rejected choice is right

Emulated legacy devices win when the guest OS predates virtio drivers (very old/embedded guests)

Why: Firecracker's data: device emulation is the dominant CVE surface (Agache 2020)

ADR-07

Interrupt delivery

Chosen

KVM in-kernel LAPIC/IOAPIC (KVM_CAP_IRQCHIP)

Rejected

Fully userspace-emulated APIC

When the rejected choice is right

Userspace APIC emulation wins when the host wants fine-grained interrupt-injection auditing/interposition for research

Why: In-kernel path avoids a VM-exit round-trip per IPI

ADR-08

Migration strategy

Chosen

Pre-copy

Rejected

Post-copy

When the rejected choice is right

Post-copy wins when network bandwidth is the binding constraint and a brief guest fault-in stall is acceptable (Deferred Features Register)

Why: Industry default; graceful failure (source still has the guest on abort)

ADR-09

Serialization (migration/state)

Chosen

Custom versioned binary framing (append-only)

Rejected

serde + bincode generic derive

When the rejected choice is right

Generic serde/bincode wins for internal-only, single-version state dumps where cross-version compatibility is not required

Why: Explicit control over wire stability across VMM versions (P7)

ADR-10

Async I/O for virtio-blk

Chosen

io_uring

Rejected

Thread-pool blocking I/O; epoll-based AIO

When the rejected choice is right

Thread-pool blocking I/O wins on kernels < 5.1 lacking io_uring, or when io_uring's CVE history (kernel-level) is an unacceptable risk (security-conservative hosts)

Why: Avoids blocking the device thread on disk I/O, meeting §4's throughput target

ADR-11

Network device backend

Chosen

Linux tap interface

Rejected

vhost-net in-kernel offload

When the rejected choice is right

vhost-net wins once throughput targets (§4 M5) cannot be met in pure userspace at scale

Why: Simpler Phase-0 implementation; offload deferred

ADR-12

Testing ground truth

Chosen

Differential vs. upstream QEMU+KVM

Rejected

Formal model (TLA+) of the vCPU state machine only

When the rejected choice is right

A formal model wins for proving abstract protocol properties (e.g. migration convergence) independent of any one implementation

Why: A live reference implementation catches real ioctl/ABI drift a formal model can't

ADR-13

Fuzzing target

Chosen

Exit-reason + virtqueue-descriptor fuzzing (cargo-fuzz)

Rejected

Whole-VM record/replay fuzzing

When the rejected choice is right

Whole-VM fuzzing wins once Phase 0–9 correctness is established and rare cross-subsystem interactions are the remaining risk

Why: Targeted fuzzing finds validation gaps (I6) faster per CPU-hour

ADR-14

Process sandboxing

Chosen

seccomp-bpf + jail from process start

Rejected

Sandboxing after VM boot completes

When the rejected choice is right

Post-boot sandboxing wins only if boot-time syscalls (e.g. dynamic device attach) are incompatible with an early-locked filter — not the case here

Why: A device-model bug during boot is still contained (P12)

ADR-15

Configuration format

Chosen

JSON VmConfig schema

Rejected

When the rejected choice is right

A Rust-native builder API wins for embedding this VMM as a library inside another Rust program, skipping serialization entirely

Why: JSON is orchestrator-friendly (language-agnostic callers)

Logging

When the rejected choice is right

Plaintext logging wins for a single-developer debug build where log-pipeline ingestion doesn't exist yet

ADR-17

Metrics

Chosen

Prometheus text-format /metrics endpoint per VMM process

Rejected

StatsD push model

When the rejected choice is right

StatsD push wins in a topology with thousands of short-lived VMM processes where per-process scrape targets don't scale

Why: Pull-based scraping matches the per-VM-process deployment topology

ADR-18

CI/CD topology

Chosen

GitHub Actions with a nested-KVM runner

Rejected

Self-hosted bare-metal CI only

When the rejected choice is right

Bare-metal-only CI wins when nested-virt is disabled by the CI provider (verify per-provider before committing)

Why: Nested KVM (kvm_intel.nested=1) is broadly available on GH-hosted runners with Intel hosts

ADR-19

Build reproducibility

Chosen

cargo --locked + vendored Cargo.lock pinned in CI

Rejected

Floating dependency versions

When the rejected choice is right

Floating versions win only in a rapid-prototype spike explicitly excluded from the conformance gate

Why: Reproducible builds are required for the conformance-fixture stability across CI runs

ADR-20

Packaging

Chosen

Static-linked (musl) single binary per release

Rejected

Dynamic-linked glibc build

When the rejected choice is right

Dynamic linking wins when the deployment host already manages shared libc security patches centrally and binary size matters less

Why: Simplifies jailer chroot (no shared-lib dependency resolution inside the jail)

ADR-21

Time source

Chosen

CLOCK_MONOTONIC for all internal timers; KVM-PV clock exposed to guest

Rejected

Wall-clock (CLOCK_REALTIME) for internal timers

When the rejected choice is right

Wall-clock matters only for guest-visible time (already handled via KVM-PV clock, not internal timers)

Why: Monotonic clock avoids NTP-step-induced migration/timeout anomalies

ADR-22

Backpressure (virtio queues)

Chosen

Bounded ring depth (256 descriptors, I5) with guest-visible "queue full" signaling

Rejected

Unbounded dynamic descriptor chains

When the rejected choice is right

An unbounded model wins only if guest drivers cannot tolerate ring-full backpressure at all — no such Linux/BSD driver exists in practice

Why: Matches virtio spec's own ring-size negotiation and bounds device-thread work

ADR-23

Licensing

Chosen

Apache-2.0

Rejected

GPL-2.0 (matching KVM's kernel license)

When the rejected choice is right

GPL-2.0 wins if the project intends to eventually upstream code into the Linux kernel tree itself

Why: Apache-2.0 matches crosvm/Firecracker's licensing, easing code-pattern reuse study

34. Alternative Architectures (Roads Not Taken)

Alternative A - Type-1 (bare-metal) hypervisor.

+-------------------------------------------+
|  Guest 1        Guest 2       Guest N      |
+---------------------------------------------+
|  This project's hypervisor (ring 0)          |
|   - owns scheduling, memory, devices          |
+---------------------------------------------+
|  Bare hardware                                |
+-------------------------------------------+

Regime where it wins: no trusted general-purpose host OS should exist beneath the hypervisor at all (embedded/firmware-level virtualization, highest-assurance isolation requirements). Real embodying system: Xen (Barham 2003) in its original ring-0 dom0 design. Rejected here because it requires reimplementing scheduling, memory management, and driver support that a host Linux kernel + KVM already provides at production quality - see ADR-01's rationale and MM6.

Alternative B - Binary-translation-based virtualization (no VT-x).

Guest instructions -> binary translator -> rewritten instructions -> CPU
   (privileged instructions trapped and emulated in software)

Regime where it wins: hardware lacking VT-x/AMD-V entirely (pre-2005 x86, or architectures without a hardware second-level-translation feature). Real embodying system: VMware's original binary-translation-based ESX Server (Adams & Agesen 2006). Rejected here because VT-x is universally available on target deployment hardware and eliminates the ~20% translation overhead the paper measured (ADR-02).

Alternative C - Full-device-emulation VMM (QEMU model).

+-----------------------------------------------+
|  Guest driver (real or virtio, guest's choice)  |
+-----------------------------------------------+
|  QEMU: emulates e1000, IDE, VGA, ..., virtio     |
+-----------------------------------------------+
|  KVM (same VMX/EPT delegation as this design)    |
+-----------------------------------------------+

Regime where it wins: guest compatibility requirements include legacy or arbitrary operating systems without virtio drivers (old Windows, obscure BSDs, firmware-level guests). Real embodying system: QEMU+KVM. Rejected here because the device-emulation surface is the dominant CVE class (Agache 2020's motivating data, §22) and this project's target guests all support virtio (P5).

Alternative D - Paravirtualization with a privileged dom0 device backend (Xen PV model).

+---------------+        +------------------------+
|  DomU (guest)  |<------>| Dom0 (privileged)       |
|  PV frontend   |  event  | device backends         |
|  drivers       | channel | (net/blk)                |
+---------------+        +------------------------+

Regime where it wins: a multi-tenant cloud provider wants device I/O policy/backends centrally managed in one privileged domain rather than per-guest-VMM-process (Xen's original design center). Rejected here because the per-VM-process isolation model (P12, one process per VM) is simpler to reason about and jail (ADR-14) than a shared privileged dom0 that would itself become a single point of compromise across all guest VMs on a host.
