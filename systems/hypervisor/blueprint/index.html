153 — Hypervisor / VMM

Project Number: 153

Project Name: Hypervisor / VMM

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a type-2, KVM-hosted userspace Virtual Machine Monitor (VMM) in Rust — a Firecracker/crosvm-class monitor that drives Linux's in-kernel KVM module over /dev/kvm to run hardware-virtualized guests, in the tradition of KVM (Kivity et al. 2007), Firecracker, crosvm, and Cloud Hypervisor. The VMM owns: vCPU lifecycle (create → run → exit-dispatch → destroy), guest memory backing (mmap-based guest-physical → host-virtual mapping), second-level address translation setup (EPT via KVM ioctls), the VM-exit/VM-entry handling loop, virtio paravirtualized devices (net, block, console), interrupt injection (in-kernel LAPIC/IOAPIC or split-irqchip), a minimal Linux boot protocol loader, and pre-copy live migration. It does not own the KVM kernel module itself (Linux upstream), nor hardware microcode, nor a guest OS.

Phase-0 deliverable — numbered crates:

  1. hyp-core — Vcpu, VmConfig, ExitReason, Device trait, error types.
  2. hyp-kvm-sys — safe wrappers over KVM_CREATE_VM/KVM_CREATE_VCPU/KVM_RUN/ KVM_SET_USER_MEMORY_REGION/KVM_GET_SREGS ioctls.
  3. hyp-memory — guest-physical memory region registration, mmap backing.
  4. hyp-loader — Linux bzImage + boot_params loader (§8).
  5. hyp-cli — the Phase-0 binary: boots a single-vCPU guest to a serial console.

System boundaries.

  • Provides: vCPU create/run/exit dispatch, EPT-backed guest memory, virtio-net/ blk/console, LAPIC/IOAPIC interrupt injection, Linux boot loading, pre-copy live migration, a VM JSON configuration schema, a differential-conformance harness against upstream QEMU+KVM.
  • Delegates: VM-entry/VM-exit mechanics, VMCS field encoding, and EPT walk hardware semantics to the host's KVM kernel module (arch/x86/kvm/); scheduling of vCPU threads to the Linux CFS scheduler; physical NIC/disk I/O to the host kernel's net/block stack.
  • Does NOT provide: AMD SVM or ARM VE backends (Deferred Features Register), nested virtualization, IOMMU/VFIO passthrough, GPU passthrough, post-copy migration, a GUI/VNC front end, or a from-scratch bare-metal (type-1) hypervisor.

Non-goals. Not a general-purpose cloud orchestrator (no scheduler, no fleet management — that is Kubernetes/Nomad's job); not a container runtime; not a replacement for QEMU's device breadth (only virtio + serial); not SEV/SEV-SNP or TDX confidential computing (flagged PhaseDeferred("Deferred Features Register")).

Deployment model. A single-tenant-per-VM host daemon: one VMM process per guest VM (the Firecracker/crosvm jailer model), invoked by an orchestrator (out of scope) that supplies a JSON VmConfig, a kernel image, and a root filesystem block device. The VMM runs unprivileged after VM creation via seccomp + a chroot jail (§9 ADR-14).

Target users/operators. Systems engineers building microVM-based sandboxes (FaaS, CI runners); kernel/virtualization engineers studying VT-x from a from-scratch implementation; SRE teams operating the live-migration pipeline.

What later phases unlock. Phase 5 (virtio-net) unlocks networked guests; Phase 7 (interrupt controller) unlocks multi-vCPU SMP guests; Phase 8 (live migration) unlocks zero-downtime host maintenance; deferred AMD SVM/ARM VE backends would unlock non-Intel hosts.

Language: Rust 1.78+ MSRV. Rationale: memory safety in a process that parses untrusted guest-controlled virtio descriptors and directly mmaps guest memory is not optional — a single OOB write in the device-emulation path is a guest-to-host escape (§22 Threat Model, T3). Rejected: C (crosvm/Firecracker's own rationale for abandoning it — memory-safety CVEs in QEMU's device models are the dominant CVE class per the Qemu security advisories list); Go (GC pauses violate the ≤100µs vCPU-thread scheduling budget, §4); C++ (no borrow-checker equivalent; Google's crosvm and AWS's Firecracker both independently chose Rust for the identical isolation argument).

Prerequisites. x86-64 protected/long-mode paging; the Linux boot protocol; basic PCI/virtio familiarity; POSIX threads and mmap semantics; enough assembly literacy to read a VMCS field dump.

Estimated timeline. Phase 0 (repo skeleton + vCPU-run correctness kernel): 3 weeks. Full ten-phase plan (through live migration, §12–§21): 7 months at one senior engineer full-time.

Deferred features (full table in the Deferred Features Register, back matter): AMD SVM backend PhaseDeferred("§21.2"); ARM VE backend PhaseDeferred("§21.2"); IOMMU/VFIO passthrough PhaseDeferred("§21.2"); nested virtualization PhaseDeferred("§21.2"); post-copy migration PhaseDeferred("§20.2"); SEV/SEV-SNP/TDX confidential VMs PhaseDeferred("§22").

2. Why Build This

Hardware-assisted virtualization is the one place in systems engineering where a paper written in 1974 (Popek & Goldberg) precisely predicts a hardware feature shipped in 2005 (Intel VT-x) — building this VMM is the fastest path to holding that theory and its production consequences in one head. It teaches: the trap-and-emulate discipline formalized by Popek & Goldberg's virtualizable- instruction-set theorem; why x86's non-virtualizable instructions (POPF, SIDT) forced Adams & Agesen's binary-translation era before VT-x existed; the KVM/QEMU split that every modern VMM (Firecracker, crosvm, Cloud Hypervisor) still uses; and the virtio contract that lets a guest driver and a host device model agree on a lock-free ring without either trusting the other.

Why it matters architecturally. Every public cloud (AWS Nitro, GCP, Azure) runs guest workloads inside a VMM built on exactly this spine: vCPU-thread-per- core, EPT-backed memory, virtio I/O. Firecracker's ~50 KLOC proved the device- emulation surface — not the VT-x plumbing — is where most VMM CVEs live, reshaping the industry's threat model around minimal device surface.

Engineering muscles built. Reasoning about a state machine (the vCPU) whose transitions are triggered by hardware traps outside your control; designing a zero-copy, lock-free producer/consumer protocol (the virtqueue) that must tolerate a fully adversarial peer; capacity-planning a memory-copy pipeline (live migration) against a moving convergence target; threat-modeling a system whose entire purpose is enforcing an isolation boundary.

Cross-links to sibling systems. Shares the exit-dispatch-loop shape with an async runtime's poll loop (Project 41 — Async Runtime) but the "task" is a CPU, not a future; shares the ring-buffer producer/consumer discipline with Project 88 — Lock-Free MPMC Queue, but must additionally validate every field because the guest is untrusted; shares live-migration's dirty-page-tracking + convergence loop with Project 112 — Distributed KV Store's leader hand-off.

Calibration value. A working Phase-0 vCPU loop is checkable against a single authoritative source (does the guest reach a login prompt); a broken EPT mapping manifests as a silent guest hang, not a compiler error — this domain calibrates the habit of building an internal verifier (§7) before trusting your own code.

What Mastery Looks Like

  • Trace a single EPT_VIOLATION from VMCS_EXIT_QUALIFICATION through the host page-fault handler to KVM_RUN re-entry, citing the exact ioctl sequence (Phase 2, §14).
  • Explain why POPF/SIDT broke classic trap-and-emulate on x86 and what VT-x's VMCS changed to restore Popek & Goldberg's theorem (Phase 2, §14; ADR-02).
  • Design a virtqueue validation path that rejects every malformed-descriptor class in §8's failure-path table without trusting guest-supplied lengths (Phase 5, §17).
  • Derive the pre-copy migration convergence bound from dirty-rate vs. network bandwidth and know when to fall back to stop-and-copy (Phase 8, §20).
  • Reproduce, from the threat model alone, why Firecracker's device surface is smaller than QEMU's and what that trade costs in guest compatibility (§22; Comparative Architecture Table, §31).
  • Justify the KVM/userspace-VMM split against a type-1 (bare-metal) alternative using the Alternative Architectures analysis (§34).

Userspace VMM box — one process per guest (isolation boundary, T1/T4); owns configuration parsing, device model state, and the vCPU-thread pool. vCPU threads — concurrency boundary: one OS thread per vCPU, blocking in KVM_RUN; no shared mutable vCPU state (I1). Device threads — poll virtqueues; the trust boundary against the guest is here (every descriptor field is guest-controlled, §8). hyp-memory — the persistence-adjacent boundary: the single mmap region backing all guest RAM, registered with KVM so EPT walks resolve without a VM-exit on steady-state access. Migration source/dest — the only network-protocol boundary (§20); TLS-optional TCP stream carrying page + CPU-state records. KVM module — delegated boundary; this project treats it as a fixed, trusted kernel interface, never modifies it. CPU — the hardware trust boundary; VMX root mode (host) vs. non-root mode (guest) is the isolation primitive the entire threat model (§22) rests on.

6. Design Principles

  • P1 — Userspace VMM over kernel KVM module. All VM-entry/exit mechanics live in the host's KVM module; this project only issues ioctls. Tradeoff: couples to KVM's ioctl ABI stability. Operational: a host kernel upgrade can change ioctl struct layouts (§9 ADR-01). Violation cost: reimplementing VMCS management in userspace reintroduces the entire attack surface KVM already hardened.
  • P2 — One OS thread per vCPU, no shared mutable vCPU state. Each vCPU's registers, VMCS handle, and exit state are thread-owned. Tradeoff: N threads for N vCPUs costs context-switch overhead at high vCPU counts. Operational: thread pinning to host cores is a deployment concern, not a code concern. Violation cost: shared vCPU state without locks is a data race that can corrupt guest register state (I2).
  • P3 — Guest memory is a single mmap region; EPT is host-kernel-owned. Userspace registers the region once via KVM_SET_USER_MEMORY_REGION; the kernel builds/tears down EPT. Tradeoff: no userspace control over EPT entry granularity. Violation cost: manual EPT manipulation from userspace is not exposed by KVM's ABI — this is not optional, it is the delegation boundary (§3).
  • P4 — Every guest-controlled field is validated before use. MMIO addresses, virtqueue descriptor lengths/addresses, migration-stream records — none are trusted. Tradeoff: validation costs cycles on the hot I/O path. Violation cost: an unvalidated desc.addr is a guest-to-host arbitrary write (T3, §22).
  • P5 — Virtio before emulated PCI. Ship virtio-net/blk/console; emulated legacy devices are deferred. Tradeoff: guests without virtio drivers (very old kernels) are unsupported. Violation cost: implementing emulated e1000/ATA first would triple Phase 5's scope for no correctness benefit.
  • P6 — Live migration is pre-copy first-class, not a stretch bolt-on. Dirty-page tracking is wired into hyp-memory from Phase 3, not retrofitted. Tradeoff: every memory write path must respect KVM_MEM_LOG_DIRTY_PAGES bookkeeping cost. Violation cost: retrofitting dirty tracking after Phase 3 requires re-touching every memory-region call site.
  • P7 — Determinism in state serialization. CPU/device state serializes to a stable, versioned wire format (§20). Tradeoff: a stable format constrains future field additions to append-only. Violation cost: an unstable format breaks migration compatibility across VMM versions (§25).
  • P8 — The internal verifier asserts every invariant continuously. A debug build runs hyp-verifier assertions on every vCPU exit and every memory region mutation (§7). Tradeoff: debug-build overhead (~15%). Violation cost: without it, an EPT/dirty-bit bug surfaces only as a silent guest data corruption weeks later.
  • P9 — Multi-architecture via per-arch crates, not #[cfg] soup. hyp-arch-vtx isolates Intel-specific VMX/VMCS code; a future hyp-arch-svm mirrors it. Tradeoff: some duplication across arch crates. Violation cost: #[cfg(target_arch)]-laced shared code becomes unreadable past two architectures (learned from QEMU's target/ sprawl).
  • P10 — Fail closed on malformed guest input. A malformed virtqueue descriptor or MMIO access is logged and the operation dropped/faulted, never silently retried with partial data. Tradeoff: a buggy (not malicious) guest driver may see spurious faults. Violation cost: silent partial processing is how double-free/UAF classes enter the device-emulation layer (§22 T3).
  • P11 — Differential testing against KVM+QEMU is the ground truth. Any observable divergence (exit reason, register state after a fixture) is a bug in this VMM until proven otherwise. Tradeoff: requires maintaining a QEMU+KVM reference environment in CI. Violation cost: without a reference, correctness bugs are indistinguishable from guest-kernel quirks.
  • P12 — Seccomp + jail from process start, not bolted on later. The VMM process drops privileges immediately after /dev/kvm open and memory registration (ADR-14). Tradeoff: debugging requires a seccomp-disabled build flag. Violation cost: a VMM compromised via a device-model bug with full host privileges is a total host compromise, not a contained one (T1).

8. Domain Model

8.1 Guest/Host Execution Model

A vCPU alternates between VMX non-root mode (executing guest instructions natively) and VMX root mode (host handling an exit). The transition guest→host is a VM-exit; host→guest is a VM-entry. The VMCS (Virtual Machine Control Structure) is the hardware- resident record of a vCPU's guest state, host state, and exit-control fields; KVM manages the VMCS in-kernel and exposes vCPU register access to userspace via KVM_GET_REGS/KVM_SET_REGS/KVM_GET_SREGS.

vCPU state machine:

Created --(KVM_RUN)--> Running --(vmexit)--> ExitedForReason(reason)
   ^                                                |
   |            (handler processes reason)          |
   +---------------(KVM_RUN, re-enter)---------------
Running --(guest HLT, no pending IRQ)--> Halted
Running --(fatal: triple fault)--> Crashed

8.2 VMCS / vCPU State

Signature-level only (no register bodies inline — see §11 for CpuRegs). Load-bearing VMCS field groups: guest-state (segment registers, RIP/RSP/RFLAGS, control registers CR0/CR3/CR4), host-state (the values VM-exit restores), exit-control (which events cause an exit — e.g. EXCEPTION_BITMAP, IO_BITMAP), entry-control (interrupt/exception injection fields). KVM's kvm_run shared-memory struct mirrors the subset userspace needs per exit (§14).

8.3 EPT / Second-Level Address Translation

EPT is a second page-table walk: guest-virtual → guest-physical (guest's own page tables, opaque to the host) → guest-physical → host-physical (EPT, host-kernel-managed). Userspace registers guest-physical → host-virtual ranges via KVM_SET_USER_MEMORY_REGION; KVM lazily builds EPT entries on first access (demand paging) and tears them down on unmap. KVM_MEM_LOG_DIRTY_PAGES enables a per-page dirty bitmap in the EPT walker for migration (§8.6).

Worked example — cold EPT violation:

  1. Guest accesses GPA 0x3F00_0000, not yet backed → CPU raises EPT_VIOLATION, VM-exit to host.
  2. Host reads VMCS_EXIT_QUALIFICATION (access type) and the faulting GPA from kvm_run.exit_reason == KVM_EXIT_MMIO or an internal EPT-fault path.
  3. hyp-memory resolves GPA → HVA via its registered-region interval tree (I2 guarantees no ambiguity).
  4. If the host page backing that HVA is not resident (e.g. swapped, or never touched), the host's own page-fault handler pages it in — this is an ordinary userspace page fault, invisible to KVM's ioctl surface.
  5. Host re-issues KVM_RUN; hardware retries the guest instruction; EPT entry is now valid — no further exit for that page until it is unmapped again. Cost: ~10 ms cold (disk), ~5 µs warm (page-cache hit + TLB fill), per §4.

8.4 VM-Exit Handling Model

The exit dispatcher (Phase 2, §14) is an exhaustive match over ExitReason (§11). Canonical reasons: Mmio, Io, Hlt, Shutdown, Hypercall, EptViolation, Interrupted (a host-signal requested re-entry stop), Unknown(u32) (I9's catch-all).

Malformed-input example. A guest that writes an MMIO access spanning a device's register boundary (offset + len overflowing the device's mapped range): the dispatcher's range check (I3) rejects it before calling the device's mmio_write; the access is faulted back as #GP — the device implementation itself never sees an out-of-range offset.

Failure-path example. A device thread panics mid-descriptor-processing (e.g. an unwrap on a corrupt internal state): the panic is caught at the thread boundary (catch_unwind), the device is marked Crashed, its virtqueue is drained with all pending descriptors marked used-with-error, and the vCPU threads continue — a single device failure does not take down the VM (bounded blast radius, §23).

8.5 Virtio Device Model

A virtqueue has three guest-writable/host-readable regions: the descriptor table (vring_desc[]: addr, len, flags, next), the available ring (indices the driver has published), and the host-writable used ring (indices the device has completed). Ordering: the driver writes descriptors, then publishes via the available-ring index with a store-release barrier; the device reads with a load-acquire barrier — required correctness on weakly-ordered hosts (aarch64), moot on x86's TSO but coded portably (P4, Russell 2008).

Sequence table — virtio-blk read request:

Step Actor Action
1 Guest driver builds descriptor chain: header, data buffer, status byte
2 Guest driver appends chain head to available ring, idx += 1 (release)
3 Guest driver writes doorbell MMIO (notify)
4 Device thread wakes, reads available ring (acquire), walks chain
5 Device thread validates every desc.addr/desc.len against I6
6 Device thread performs backing-file I/O (io_uring, async)
7 Device thread writes status byte, appends index to used ring
8 Device thread injects completion interrupt (§16)
9 Guest driver reads used ring, completes the I/O request

8.6 Migration-Adjacent Memory Semantics

Dirty-bit tracking (I4) and the pre-copy loop are covered fully in Phase 8 (§20); the domain-model-relevant fact is that EPT's dirty bitmap is the only mechanism by which userspace learns which guest-physical pages changed between two KVM_GET_DIRTY_LOG calls — there is no alternative source of truth.

14. Phase 2 — vCPU Run Loop & VM-Exit Dispatch

14.1 Objectives

Implement the exit-dispatch loop (§8.4): call KVM_RUN, read kvm_run.exit_reason, translate into ExitReason (§11), dispatch exhaustively (I9), re-enter. Cover Hlt, Io, Mmio, Hypercall, Unknown — EptViolation is deferred to Phase 3 (§15) since it needs hyp-memory.

14.2 Detailed Implementation Steps

The vCPU thread (P2: one thread per vCPU, no shared mutable state) loops: issue KVM_RUN; on return, read the shared kvm_run struct's exit_reason field; translate the kernel's raw u32 into ExitReason via an exhaustive match (I9) — any unrecognized value becomes Unknown(u32) and is logged, never silently dropped (P10). Hlt moves the vCPU to VcpuState::Halted pending an external wake (an injected interrupt, §16, later phase). Io/Mmio dispatch to hyp-core::Device registrations by port/address range (I3); an unmatched range faults the guest with #GP, applying P10 directly. Wires the first hyp-verifier assertions: I1 (thread ownership), I3 (exhaustive MMIO dispatch), I9 (exhaustive exit-reason match) — each is a compiled-in assert exercised by the Phase 2 conformance bucket (Adams & Agesen 2006's trap-and-emulate model is the theoretical basis for this exit-dispatch structure).

14.3 Deliverable

hyp-arch-vtx + the vCPU run loop in hyp-cli; a fixture guest (a tiny hand-assembled real-mode stub that issues HLT) runs to completion and the loop observes and logs the Hlt exit.

14.4 Acceptance Criteria

Vmexit-to-dispatch latency p50 ≤ 1 µs, p99 ≤ 5 µs (§4 M1, measured via hyp-bench::vmexit_latency); the conformance/buckets/vcpu/ bucket passes 100% (≥ 20 named fixtures covering each ExitReason variant); zero Unknown exits on the fixture guest.

14.6 Pitfalls

  • The kvm_run struct is shared kernel/userspace memory; reading fields after KVM_RUN returns without a compiler memory-barrier-respecting read pattern can observe torn writes on some architectures — use volatile-equivalent reads via the wrapper, never a raw struct copy.
  • Forgetting to re-arm KVM_RUN after handling Hlt with a pending interrupt causes the vCPU to never resume (manifests as a silent guest hang, diagnosed via hyp-verifier's I1/I9 trace replay).

14.7 Performance Concerns

Each vCPU exit costs a full VM-exit/VM-entry round trip (~1 µs fixed hardware cost, Vmexit anatomy, §28); the dispatcher itself must add negligible overhead — a match over a fixed enum compiles to a jump table, not a linear scan, keeping dispatch sub-100ns.

14.8 Edge Cases

A guest that HLTs with interrupts disabled (RFLAGS.IF=0) and no NMI pending is a legitimate guest shutdown request, not a bug — the dispatcher must distinguish this from a spurious hang via the Shutdown exit reason, not infer it from Hlt alone.

14.9 Failure Analysis

A dispatch-loop panic (e.g. an unwrap on a malformed kvm_run field) is caught at the vCPU-thread boundary; that single vCPU transitions to Crashed, other vCPU threads in the same VM continue, and the VMM signals the orchestrator via hyp-monitor — blast radius is one vCPU, not the process, unless every vCPU independently crashes (correlated failure, escalate to operator per §23).

14.10 Operational Notes

15. Phase 3 — Guest Memory Mapping & EPT Demand Paging

15.1 Objectives

Implement hyp-memory::register_region (mmap-backed guest RAM, KVM_SET_USER_MEMORY_REGION) and the EptViolation exit handler (§8.3's worked example), completing the vCPU exit-reason set from Phase 2.

15.2 Detailed Implementation Steps

hyp-memory::register_region(gpa, size, flags) allocates mmap(MAP_ANONYMOUS | MAP_SHARED) host memory (never PROT_EXEC, I11), inserts it into an interval tree keyed by GPA range (enforcing I2's no-overlap invariant at insertion time), and calls KVM_SET_USER_MEMORY_REGION to hand the mapping to KVM. The EptViolation handler (§8.3) reads VMCS_EXIT_QUALIFICATION, resolves GPA → HVA via the interval tree, and re-enters KVM_RUN — demand-paging is otherwise transparent, as the host kernel's own page-fault handler services the backing mmap. Wires I2 (overlap-reject), I11 (no-exec guest memory) into hyp-verifier. Directly applies P3 (single mmap region, kernel-owned EPT) and ADR-05.

15.3 Deliverable

A guest with a registered 1 GiB memory region can read/write guest RAM and trigger/resolve EptViolation exits without host-side crashes; hyp-memory::register_region is unit-tested for the overlap-reject path.

15.4 Acceptance Criteria

15.6 Pitfalls

  • Memory backing must be page-aligned in both GPA and host virtual address — an unaligned region silently corrupts adjacent EPT entries on some kernel versions rather than erroring; validate alignment in userspace before calling the ioctl (defense in depth).
  • Hot-add of memory regions after vCPU start requires KVM_SET_USER_MEMORY_REGION calls to be serialized against any in-flight KVM_RUN on affected vCPUs — a race here has produced reported EPT corruption in KVM's own issue tracker; this project defers hot-add to the Deferred Features Register.

15.7 Performance Concerns

Cold EPT violations cost a full page-fault + potential disk I/O (~10 ms); pre-touching guest RAM at VM start (a Firecracker-style optimization) trades startup latency for eliminating this cost during steady-state guest execution — noted here, implemented as a Phase 6 loader option (§19).

15.8 Edge Cases

A guest instruction that straddles two guest-physical pages where only one is resident produces two sequential EptViolation exits for the same instruction retry — the dispatcher must handle this as two independent violations, not assume one exit resolves the whole instruction.

15.9 Failure Analysis

A region-registration failure at VM start is fully recoverable (VM creation aborts cleanly, no partial guest state exists); a region registration failure after vCPUs are running (e.g. during a hot-add attempt) risks leaving the interval tree inconsistent with KVM's own memory-slot table — mitigated by treating hot-add as transactional (rollback the interval-tree insert on ioctl failure).

15.10 Operational Notes

Emit memory.region_register_total, memory.region_reject_total (I2's telemetry), and memory.ept_violation_latency_us{warm|cold} histograms — the last is the direct signal for a swapping host (cold violations dominating indicates host memory pressure, an operator escalation per the runbooks, §24).

16. Phase 4 — Interrupt Controller & Injection

16.1 Objectives

Wire interrupt delivery: an in-kernel LAPIC (per-vCPU) and IOAPIC (shared) via KVM_CAP_IRQCHIP, enabling device-completion interrupts (needed before virtio devices in Phase 5 can signal I/O completion) and inter-vCPU IPIs (needed before Phase 9's multi-vCPU conformance).

16.2 Detailed Implementation Steps

hyp-irqchip calls KVM_CREATE_IRQCHIP at VM creation (before any vCPU starts, applying P1's kernel-delegation principle: LAPIC/IOAPIC state lives in KVM, not userspace) and exposes inject_irq(line, vector) via KVM_IRQ_LINE. IOAPIC routes a device's IrqLine (§11's Device trait) to a vector; LAPIC handles the per-vCPU TPR (Task Priority Register) gating — a pending IRQ below the current TPR is held, not delivered, per the Intel SDM's APIC chapter (§5 Required Reading item 3). Adds I3-adjacent validation: an irq_lines() value outside the registered IOAPIC range is rejected at device-registration time, not at injection time.

16.3 Deliverable

A device (the Phase 2 fixture's synthetic device) can raise an IRQ line and the guest's interrupt handler observes it; TPR-gated suppression is demonstrated by a fixture that raises an IRQ below the guest-set TPR and confirms delayed delivery.

16.4 Acceptance Criteria

IRQ injection latency (inject_irq call to guest ISR entry) ≤ 2 µs p50 (§4, §29 M8, in-kernel irqchip path); conformance/buckets/vcpu/ gains ≥ 5 new IRQ-specific fixtures, all green; TPR-gating fixture demonstrates correct suppression (0 spurious deliveries across 10k iterations).

16.5 Conformance Fixtures

Fixture Purpose Expected Output
irq_basic_delivery.bin raise IRQ, guest ISR increments counter counter == expected within 2 µs
tpr_gating.bin raise IRQ below guest TPR delivery deferred until guest lowers TPR
ipi_cross_vcpu.bin vCPU A sends IPI to vCPU B B's ISR observes IPI within M8 bound

16.6 Pitfalls

  • Forgetting KVM_CREATE_IRQCHIP before the first KVM_CREATE_VCPU produces a vCPU that silently cannot receive interrupts — no error is raised at vCPU creation time; validate ordering at VmConfig application time.
  • TPR handling bugs (respecting the wrong priority comparison direction) produce missed IRQs that look identical to a hung device — diagnosed via hyp-verifier replay comparing expected vs. actual delivery order.

16.7 Performance Concerns

The in-kernel irqchip path (ADR-07) avoids a userspace round-trip per IRQ that a fully-emulated APIC would require; this is the single largest latency win available for the IPI path (§29 M8).

16.8 Edge Cases

Two devices sharing the same IOAPIC line (legacy PCI level-triggered sharing): must be explicitly rejected at registration time in this virtio-only device model (P5) — level-triggered sharing semantics are out of scope, and silently allowing registration would produce non-deterministic delivery order.

16.9 Failure Analysis

A misrouted IRQ (wrong vector delivered) manifests as guest-visible data corruption or a hung driver, not a host crash — detection relies entirely on the differential-conformance bucket (§21) comparing guest behavior against upstream QEMU+KVM on the identical fixture.

16.10 Operational Notes

Emit irqchip.injection_total{line} and irqchip.injection_latency_us — a rising injection latency trend across an otherwise-idle host is the first signal of host CPU contention (dashboard, §24).

17. Phase 5 — virtio-blk Device

17.1 Objectives

Implement the virtqueue mechanics (§8.5) generically in hyp-virtio and the first concrete device, virtio-blk, backed by a host file via io_uring (ADR-10).

17.2 Detailed Implementation Steps

hyp-virtio::Vring implements the descriptor-table/available-ring/used- ring layout (§8.5) with the acquire/release barrier discipline (Russell 2008, applied here). Vring::walk_chain enforces I5 (chain length ≤ 256) and I6 (desc.addr + desc.len inside a registered MemoryRegion, via hyp-memory's interval tree from Phase 3) before any descriptor is handed to the device. virtio_blk::Device implements hyp-core::Device (§11); its worker thread submits validated descriptor I/O to io_uring, writes the status byte, and appends to the used ring, then calls hyp-irqchip::inject_irq (Phase 4) to signal completion — directly following the sequence table in §8.5.

17.3 Deliverable

A guest Linux kernel with a virtio_blk driver can read and write a backing file exposed as /dev/vda; dd if=/dev/vda of=/dev/null and a write-then-readback round trip both succeed.

17.4 Acceptance Criteria

virtio-blk IOPS ≥ 1,000,000 (4 KiB random read, NVMe-backed file, §4, §29 M4, measured via hyp-bench::virtio_blk_iops); malformed-descriptor fixtures (I5, I6) are 100% rejected with zero host-side panics across the fuzz corpus (fuzz_targets/virtio_descriptor.rs, ADR-13); chain depth ≥ 257 rejected in ≤ 1 µs.

17.5 Conformance Fixtures

Fixture Purpose Expected Output
blk_read_roundtrip.bin guest reads known-content sectors content matches golden file byte-for-byte
blk_write_roundtrip.bin guest writes then reads back written bytes observed on readback
chain_depth_overflow.rs descriptor chain of 300 entries rejected per I5, virtio.chain_overflow_total incremented
oob_descriptor_addr.rs desc.addr outside any registered region rejected per I6, no host memory touched
malformed_status_byte.rs device writes unexpected status enum value guest driver reports I/O error, no VMM crash

17.6 Pitfalls

  • The vring's descriptor chain can encode a cycle (next pointing backwards); an unbounded walk without a step counter hangs the device thread — enforce I5's 256-step bound as a hard loop counter, not a "detect cycles" heuristic.
  • Async I/O completion (io_uring) arriving out of submission order must still update the used ring in the order the guest expects per-request, not globally — track per-descriptor completion state explicitly.

17.7 Performance Concerns

io_uring avoids blocking the device thread on disk I/O (ADR-10); batching multiple submissions per io_uring_enter syscall amortizes syscall overhead across concurrent requests, which is necessary to hit the ≥1M IOPS target (§29 M4) since a per-request syscall would cap throughput far lower.

17.8 Edge Cases

A guest that posts the same descriptor index twice before the device processes the first (double-submission): the device must track per-descriptor "in-use" state — without it, the backing buffer pool double-frees, a documented historical bug class in virtio backend implementations.

17.9 Failure Analysis

A backing-file I/O error (disk full, EIO) surfaces as a virtio status byte (VIRTIO_BLK_S_IOERR) to the guest, never a VMM crash — the device thread logs the error and continues serving other descriptors; blast radius is one in-flight request, not the device or VM (P10).

17.10 Operational Notes

Emit virtio_blk.iops, virtio_blk.latency_us{p50,p99}, and virtio_blk.chain_overflow_total (I5) — IOPS regression below the §4 M4 floor gates CI release per the Performance Engineering perf-regression policy (§29).

18. Phase 6 — virtio-net & Serial Console

18.1 Objectives

Add virtio-net (tap-backed, ADR-11) and the 16550 UART serial console (hyp-serial) needed for a guest to reach an interactive login prompt — the last device-model prerequisite before Phase 7's boot loader phase is end-to-end testable.

18.2 Detailed Implementation Steps

virtio_net::Device reuses hyp-virtio::Vring (Phase 5) for both TX and RX queues; the host side bridges a Linux tap interface (requiring CAP_NET_ADMIN, documented in the deliverable) to the guest's virtqueue — packets flow tap → host network stack → physical NIC and back. TSO/GSO offload negotiation uses virtio feature bits (VIRTIO_NET_F_HOST_TSO4, etc.) exchanged during device negotiation, applying P5 (virtio-first) and reusing I5/I6 validation from Phase 5's generic Vring unchanged. hyp-serial emulates a 16550 UART at the standard I/O ports: guest writes to the transmit register route to host stdout; host stdin feeds the receive register and asserts the corresponding interrupt-enable bit via hyp-irqchip (Phase 4) when set.

18.3 Deliverable

A guest boots (manually, pre-Phase-7, via a directly-injected register state) far enough to bring up its network stack over the tap device and print output over the emulated serial console.

18.4 Acceptance Criteria

virtio-net throughput ≥ 10 Gbps with TSO enabled (§4, §29 M5, measured via hyp-bench::virtio_net_throughput against an iperf3 guest workload); serial console round-trip latency (keystroke to guest echo) ≤ 5 ms p99; link-state-change event correctly reported to guest when the host tap interface is administratively brought down.

18.5 Conformance Fixtures

Fixture Purpose Expected Output
net_tap_throughput.rs iperf3 guest workload over tap ≥ 10 Gbps sustained, TSO on
net_link_down.rs host brings tap down mid-transfer guest observes VIRTIO_NET_S_LINK_DOWN
serial_echo.rs host writes to stdin, guest echoes round-trip observed ≤ 5 ms
serial_no_tty_stdin.rs host stdin is not a tty (piped) UART still functions, documented degraded-readline mode

18.6 Pitfalls

  • The tap interface requires CAP_NET_ADMIN to create — running the VMM as an unprivileged jailed process (P12, ADR-14) means the tap device must be pre-created and handed to the VMM via a file descriptor, not created by the VMM itself; document this in the deliverable's operator setup steps.
  • The UART's interrupt-enable register bits must be respected exactly — a guest relying on interrupt-driven console I/O hangs if the emulated UART raises interrupts regardless of the enable bits.

18.7 Performance Concerns

TSO/GSO offload moves segmentation work from the guest driver to the host NIC's hardware offload, which is the dominant factor in reaching the 10 Gbps target (§29 M5) — without it, per-packet virtqueue overhead caps throughput an order of magnitude lower.

18.8 Edge Cases

A guest that negotiates TSO but sends a packet exceeding the negotiated MTU: the device must reject/fragment per the virtio-net spec rather than forwarding an oversized frame to the host tap interface, which would be dropped downstream with a confusing host-side error.

18.9 Failure Analysis

A tap-interface failure (host network reconfiguration) degrades to VIRTIO_NET_S_LINK_DOWN visible to the guest, not a VMM crash; a UART write to a closed stdout pipe (host-side console detached) is caught and logged, not propagated as a panic — bounded blast radius per P10.

18.10 Operational Notes

Emit virtio_net.throughput_bps, virtio_net.link_state, and serial.bytes_total{tx,rx} — link-state flapping in the metrics is the first signal an operator checks when a guest reports intermittent connectivity.

19. Phase 7 — Linux Boot Loader

19.1 Objectives

Implement hyp-loader::load_linux, loading a Linux bzImage per the kernel's own boot protocol, so that Phase 5/6's devices are reachable by an actually-booted guest instead of a hand-injected register state.

19.2 Detailed Implementation Steps

hyp-loader places the protected-mode kernel image at guest-physical 0x100000 and the real-mode setup header at 0x10000, per Documentation/x86/boot.rst (§5 RFCs/Specifications). It populates boot_params (command line pointer, initramfs location/size, E820 memory map derived from the registered MemoryRegions of Phase 3) and sets initial vCPU register state (CR0 with paging/protection enabled, segment registers, RIP at the kernel entry point) via KVM_SET_SREGS/KVM_SET_REGS (Phase 1's wrappers). Optionally emits minimal ACPI tables (RSDP, FADT, MADT reflecting the Phase 4 IOAPIC/ LAPIC configuration) for kernels that require them, applying ADR-07's irqchip configuration consistently into the MADT.

19.3 Deliverable

hyp-cli boots an unmodified Linux kernel + minimal initramfs to a shell prompt reachable over the Phase 6 serial console, using Phase 5's virtio-blk as root filesystem.

19.4 Acceptance Criteria

Boot time (kernel entry to systemd/init reaching a target, e.g. a login prompt) ≤ 5 s (§4, §29 M6, measured on the fixture kernel scripts/build_test_kernel.sh produces); zero kernel panics across 100 consecutive boot attempts; E820 map matches the registered MemoryRegion set exactly (no gaps, no overlaps beyond I2's guarantee).

19.5 Conformance Fixtures

Fixture Purpose Expected Output
boot_minimal_linux.bzImage reference test kernel boots to shell in ≤ 5 s
boot_missing_initramfs.rs kernel configured to require initramfs, none supplied loader returns explicit LoaderError, no silent hang
boot_acpi_required_kernel.bzImage a kernel build requiring ACPI tables boots successfully with emitted MADT/FADT/RSDP
e820_map_consistency.rs compares emitted E820 map to registered regions byte-exact match

19.6 Pitfalls

  • Placing the protected-mode kernel and real-mode setup at the wrong offsets (a common transcription error from the boot protocol doc) produces an immediate triple fault indistinguishable at first glance from a VMCS misconfiguration — always verify against a known-good QEMU+KVM boot of the identical kernel first (P11).
  • A kernel requiring the KVM paravirtual clock (kvmclock) that isn't exposed via the correct CPUID leaves hangs at boot; expose the standard KVM PV-clock CPUID bits by default.

19.7 Performance Concerns

Pre-touching (pre-faulting) guest RAM pages that the E820 map marks as kernel-load regions during the loader step trades a small amount of startup latency for eliminating cold EptViolation costs (§15.7) during the earliest, most timing-sensitive boot instructions.

19.8 Edge Cases

A cmdline string exceeding the kernel's documented maximum length (currently 2048 bytes) must be rejected by hyp-loader at configuration time, not truncated silently — silent truncation has historically produced boot-time argument-parsing corruption in guest kernels.

19.9 Failure Analysis

A boot failure (panic before console is live) is diagnosed via the minimal ACPI/E820 fixtures first (fixture bisection: does removing ACPI emission change the failure mode) — blast radius is the single VM being booted; the VMM process exits with a documented LoaderError, never hangs indefinitely (I9's exhaustive-exit-handling extends to the boot path via a boot-timeout watchdog).

19.10 Operational Notes

Emit loader.boot_duration_ms and loader.boot_failure_total{reason} — a boot-duration regression above the §4 M6 5 s ceiling gates CI release per the Performance Engineering policy (§29).

20. Phase 8 — Live Migration (Pre-Copy)

20.1 Objectives

Implement hyp-migrate::source/dest: pre-copy live migration with dirty-page tracking (§8.6), applying I4, I8, I12, and P6/P7 directly.

20.2 Detailed Implementation Steps

hyp-migrate::source::start enables KVM_MEM_LOG_DIRTY_PAGES on every registered MemoryRegion (precondition enforced by I4), then performs an initial full-memory copy over a TCP stream as a sequence of MigrationRecord::MemoryPage records (ADR-09's versioned framing, §11). It iterates: query KVM_GET_DIRTY_LOG, re-send only dirtied pages, repeat while the dirty-page count trend is decreasing and the iteration count is below the cap (I12: 30 iterations, §4). When the convergence criterion (projected next-iteration transfer time below the downtime target) is met, or the cap is reached, the source pauses all vCPU threads, sends final dirty pages plus MigrationRecord::CpuState for every vCPU and DeviceState for every device, then a MigrationRecordKind::EndOfStream record. hyp-migrate::dest applies records strictly in seq order (I8), rejecting any out-of-order record — this ordering gate is the direct implementation of I8.

20.3 Deliverable

A running guest migrates from a source VMM process to a destination process on the same host (loopback network) with the guest's serial console output continuing uninterrupted modulo the pause window.

20.4 Acceptance Criteria

Downtime (pause-to-resume) ≤ 100 ms for a 1 GiB guest over a 10 Gbps link (§4, §20-local target, measured via hyp-bench::migration_downtime); iteration count ≤ 30 (I12) with fallback stop-and-copy exercised by a fixture that pins the guest's dirty rate above convergence; zero out-of-order record acceptances across the fixture corpus (I8).

20.5 Conformance Fixtures

Fixture Purpose Expected Output
migrate_idle_guest.rs migrate a guest with near-zero dirty rate downtime ≤ 100 ms, single iteration converges
migrate_high_dirty_rate.rs guest workload pins CPU dirtying memory continuously falls back to stop-and-copy at iteration 30 (I12)
migrate_out_of_order_record.rs inject a record with seq out of order destination rejects per I8, connection dropped
migrate_network_partition.rs sever the connection mid-transfer source aborts and resumes locally, guest unaffected

20.6 Pitfalls

  • The convergence criterion is delicate: a guest whose dirty rate never drops below the transfer rate never converges under pure iteration — bound iterations at 30 (I12) and fall back to stop-and-copy, accepting a longer pause rather than migrating indefinitely.
  • VMCS-adjacent vCPU state (Phase 1's CpuRegs) must be fully quiesced (all vCPU threads confirmed paused, not merely signaled) before serializing CpuState records — serializing mid-flight register state produces a destination vCPU with an inconsistent, unrunnable state.

20.7 Performance Concerns

Dirty-page-log queries (KVM_GET_DIRTY_LOG) scale with the number of guest-memory pages, not the number dirtied — for very large guests (§4's 128 GiB ceiling), the bitmap itself (1 bit per 4 KiB page, ~4 MiB per 128 GiB) becomes a measurable per-iteration fixed cost, bounding how many iterations are practical within the downtime budget.

20.8 Edge Cases

A migration destination that itself crashes mid-transfer must leave the source in a fully-resumable state (the source never tears down its own vCPUs until it receives an explicit destination-ready acknowledgment) — this is the concrete mechanism behind ADR-08's "graceful failure" claim for pre-copy vs. post-copy.

20.9 Failure Analysis

A network partition mid-migration aborts the migration and resumes the guest on the source unmodified (no data loss, brief internal pause only) — detection is a TCP-level connection failure or a migration-protocol timeout; blast radius is the migration attempt only, never guest correctness, satisfying the ADR-08 rationale directly.

20.10 Operational Notes

Emit migrate.iteration_count, migrate.dirty_pages_per_iteration, and migrate.downtime_ms — the dirty-pages trend across iterations is the exact signal the "migration not converging" runbook (§24) walks an operator through.

21. Phase 9 — Differential Conformance, Hardening & Fuzzing

21.1 Objectives

Close the loop: run the full conformance corpus differentially against upstream QEMU+KVM (P11, ADR-12), install the seccomp jail (P12, ADR-14) as the default runtime posture, and stand up continuous fuzzing (ADR-13) against the exit-reason and virtio-descriptor validation paths.

21.2 Detailed Implementation Steps

conformance/buckets/differential-kvm/ runs each fixture from Phases 2–8 against both this project's VMM and a QEMU+KVM reference on identical guest kernels/workloads, diffing observable outputs (serial console output, exit-reason sequences, final register state) — any divergence is treated as a bug in this VMM until proven otherwise (P11). hyp-cli's startup sequence installs the seccomp-bpf filter (I10) immediately after /dev/kvm open and memory-region registration, before any device thread starts, then chroots into a minimal jail directory (ADR-14). hyp-fuzz's two cargo-fuzz targets — exit_reason.rs (synthesizes malformed/unexpected kvm_run.exit_reason values) and virtio_descriptor.rs (synthesizes malformed vring descriptor chains against I5/I6) — run continuously in CI (scheduled fuzz.yml, ADR-13). This phase also formally registers the deferred scope (AMD SVM, ARM VE, IOMMU passthrough, nested virtualization, post-copy migration, confidential VMs — Deferred Features Register) as explicitly out of the Phase 0–9 plan, closing the phase-by-phase plan at 10 phases (§6 bound: 8–14).

21.3 Deliverable

CI green on conformance/buckets/differential-kvm/; the seccomp jail is the default (non-jailed mode requires an explicit debug flag); the fuzz corpus has run for ≥ 24 continuous hours with zero unresolved crashes.

21.4 Acceptance Criteria

Differential corpus completes in < 30 minutes in CI (§21-local target); zero divergences against QEMU+KVM across ≥ 50 curated fixtures; 24-hour fuzz canary (§29 M10) reports 0 panics; seccomp filter installation verified by a fixture attempting a disallowed syscall post-jail and observing SIGSYS.

21.5 Conformance Fixtures

Fixture Purpose Expected Output

seccomp_disallowed_syscall.rs attempts socket() post-jail process receives SIGSYS, does not silently succeed
fuzz_regression_corpus/ replays all previously-found fuzz crashes 100% now pass (regression-fixed)

21.6 Pitfalls

  • QEMU emulates far more devices than this project's virtio-only model (P5); scope the differential corpus to virtio-only guest workloads — comparing against a QEMU configuration using emulated legacy devices produces meaningless divergences.
  • A seccomp filter written before all Phase 0–8 syscalls are enumerated (e.g. io_uring_enter forgotten) breaks Phase 5's virtio-blk device post-jail — regenerate the filter's allow-list from an strace of a full fixture run, not from memory.

21.7 Performance Concerns

Running the differential corpus doubles guest-boot overhead (two VMMs per fixture); parallelize fixture execution across CI runners to keep the 30-minute budget (§21.4) — this is a CI-topology decision (ADR-18), not a VMM-code concern.

21.8 Edge Cases

A fuzz-discovered crash that only reproduces under a specific vCPU thread interleaving (a race, not a pure input-validation bug) requires hyp-verifier's deterministic replay (§7) rather than the fuzz harness alone to isolate — record the exact trace and replay single-threaded.

21.9 Failure Analysis

A differential divergence is triaged by first checking whether it represents a real correctness bug or a documented, accepted scope gap (e.g. a device QEMU emulates that this project does not) — the Deferred Features Register is the canonical list of accepted gaps; anything not on that register is a Sev-0 bug.

21.10 Operational Notes

Publish the fuzz canary's cumulative execution count and crash count as a public dashboard metric (fuzz.exec_total, fuzz.crash_total) — this is the concrete evidence backing the "0 panics" claim in release notes (Build & Release Engineering, §27).

Tracing. tracing-crate structured spans wrap each vCPU exit, each device I/O operation, and each migration iteration, exportable to an OpenTelemetry collector. Structured logging. JSON logs (ADR-16) with a stable field schema: ts, vm_id, vcpu_id (optional), event, level, plus event-specific fields.

Dashboards. One dashboard per phase-introduced subsystem: vCPU exit-reason distribution (Phase 2), EPT violation latency histogram (Phase 3), IRQ injection latency (Phase 4), virtio-blk IOPS + virtio-net throughput (Phases 5-6), boot duration (Phase 7), migration downtime + iteration trend (Phase 8), fuzz canary cumulative count (Phase 9).

Alerting philosophy. Alert on rate-of-change and threshold breach of the §4/§29 quantified targets, never on raw event occurrence (a single Unknown exit is expected under P10's fail-open logging; a sustained rate increase is not). SLO: 99.9% of VM-creation requests succeed within 2s (RTO, §4).

Incident response. On a Sev-0 (correlated multi-vCPU crash, FM-9; or a security-relevant seccomp violation, FM-5): freeze the affected VMM process (do not auto-relaunch) pending forensic capture (hyp-verifier trace + core dump), per the Forensics column of §23.

Named runbooks (docs/runbooks/): VM hangs after vCPU start (FM-1); Migration not converging (FM-2); Device passthrough fails (N/A - deferred, kept as a stub pointing to the Deferred Features Register); CI nested-KVM flake (FM-10).

Backup/restore. A VM's durable state is its backing block-device file (virtio-blk); the VMM process itself holds no durable state - restart-from- config is the recovery model, not restore-from-backup, except via migration (§20) for live state.

Deployment topology. One VMM process per guest VM (P12); orchestrated externally (out of scope) via hyp-monitor's control socket (create/pause/ resume/query/migrate commands).

Canary/rolling-upgrade/rollback. New VMM binary versions are canaried by migrating a subset of running VMs onto hosts running the new version (§20's migration pipeline doubles as the rolling-upgrade mechanism); rollback is migrating back. A version mismatch between source and destination during migration is rejected at the MigrationRecord framing-version check (Compatibility & Versioning, §25).

25. Compatibility & Versioning

Wire compatibility (migration protocol, §20). MigrationRecord's framing carries an explicit version field (ADR-09); MigrationRecordKind variants are append-only - a new variant is ignored (logged, not fatal) by an older destination rather than causing a parse failure, easing partial rolling upgrades.

Storage compatibility. virtio-blk backing files have no VMM-specific header - they are raw block images, so no migration/versioning concern applies to guest storage itself.

Schema evolution (VmConfig, ADR-15). New optional fields default to their Phase-0 behavior when absent; removing a field is a breaking change requiring a major version bump (SemVer, below).

API stability. hyp-monitor's control-socket protocol is versioned independently of the VMM binary version; a version-negotiation handshake occurs on connect.

SemVer policy. hyp-* crates follow SemVer; a MAJOR bump is required for any Device trait signature change, any ExitReason/MigrationRecordKind variant removal, or any ioctl-wrapper ABI-breaking change.

Rolling-upgrade guarantees. A destination VMM at version N can accept a migration stream from a source at version N-1 (one minor version of backward compatibility, per the append-only MigrationRecordKind rule); cross-major-version migration is unsupported and rejected at handshake.

26. Testing & Verification Strategy

Unit tests cover every hyp-kvm-sys ioctl wrapper (§13.4), every MemoryError/LoaderError/KvmError variant's trigger condition, and Vring::walk_chain's I5/I6 enforcement in isolation.

Integration tests boot the fixture kernel end-to-end through Phases 2-7's combined stack (examples/boot_minimal_linux.rs).

Property tests (via proptest) generate arbitrary VringDescriptor chains and assert I5/I6 hold for all generated inputs, complementing the targeted fuzz corpus.

Differential tests (§21, ADR-12, P11) compare this VMM against QEMU+KVM on the curated fixture corpus - the primary correctness oracle for behavior not fully specified by the Intel SDM alone.

Fuzzing (ADR-13): exit_reason.rs and virtio_descriptor.rs targets, run continuously (§29 M10's 24-hour canary, extended to 30-day soak per the original scope note in §1's timeline).

Chaos/fault injection: network-partition injection during migration (fixture migrate_network_partition.rs, §20.5); device-thread panic injection to verify P10's bounded blast radius (§17.9-style fixtures generalized across all devices).

Deterministic replay (hyp-verifier, §7): every conformance fixture recorded as a trace, replayed with I1-I12 assertions compiled in - this is the primary tool for isolating races (FM-9) that fuzzing alone cannot localize.

Soak testing: a 24-hour (minimum, §29 M10) then 30-day extended fuzz + migration-loop canary exercising create -> boot -> migrate -> destroy repeatedly.

Performance-regression gating: every §29 M-numbered target is measured in CI via hyp-bench (Criterion) on every release candidate; a regression past the target blocks release (§27).

Tie-back to invariants and fixtures: every invariant I1-I13 (§7) has at least one conformance fixture exercising it (cross-referenced in each phase's N.5 table, §12-§21).

Reproducible builds: cargo build --locked against a committed Cargo.lock (ADR-19); release builds are verified bit-identical across two independent CI runners before tagging.

Artifact signing: release binaries are signed with a project GPG key; signatures published alongside CHANGELOG.md entries.

SBOM: a Software Bill of Materials (via cargo-cyclonedx or equivalent) is generated per release, enumerating every dependency and its license (feeding legal/ compliance notes, §10).

Release channels: main (unreleased), beta (release-candidate, soak-tested per §26), stable (tagged, signed).

CI/CD topology (ADR-18): GitHub Actions with a nested-KVM-capable runner image; the fuzz canary runs as a separate scheduled workflow (fuzz.yml) independent of the per-PR ci.yml.

Version stamping: every release binary embeds its git commit hash, build timestamp, and Cargo.lock hash, queryable via hyp-monitor.

Provenance/attestation: CI produces a SLSA-style provenance attestation tying a release artifact to the exact CI job and commit that built it.

Dependency auditing: cargo audit runs on every CI build; a new advisory against a dependency blocks merge until triaged.

28. Performance Engineering

Methodology. Benchmarking via hyp-bench (Criterion) for microbenchmarks (ioctl round-trips, vring validation) and end-to-end workload benchmarks (iperf3 for virtio-net, fio for virtio-blk) run against both a debug and release build to quantify hyp-verifier assertion overhead (P8, ~15% budget). Profiling: perf + flamegraphs for CPU-bound device-thread hot paths; strace -c for syscall-count regressions (relevant to the seccomp allow-list, §21.6). Allocation analysis: heaptrack on the device-emulation crates to catch per-descriptor allocation churn on the virtio hot path. Lock contention: since P2 mandates no shared mutable vCPU state, lock contention analysis focuses on the hyp-memory interval tree (read-heavy, RwLock) and the migration dirty-bitmap query path. Tail-latency analysis: p99/p999 tracked for vmexit dispatch (M1) and EPT-violation resolution (M2), since tail behavior - not median - determines guest- visible jitter.

29. Scalability Analysis

Constant vs. grows. Per-vCPU dispatch cost (M1) stays constant regardless of vCPU count (P2's thread-per-vCPU model has no shared dispatch bottleneck); the dirty-bitmap size (§20.7) grows linearly, O(n), with guest memory size, not with dirty-page count. Named bottlenecks in order: (1) host core count bounds vCPU count 1:1 for full-speed scheduling (§4's 32-vCPU ceiling assumes a 32+ core host); (2) io_uring submission-queue depth bounds virtio-blk IOPS scaling beyond a single queue (ADR-10); (3) TCP single-connection throughput bounds migration transfer rate (§20.7) - a future sharded multi-connection transfer is the lever beyond this ceiling; (4) the interval-tree lookup in hyp-memory is O(log n) in region count, not a practical bottleneck at realistic region counts (single digits per VM).

Horizontal/vertical scaling. Horizontal: more VMM processes across more hosts (P12's one-process-per-VM model scales horizontally trivially, no cross-VM shared state exists - I1/I2 guarantee this). Vertical: more vCPUs per VM up to the host core ceiling (§4).

Sharding/partitioning. Not applicable within a single VM (a VM is not partitioned); across a fleet, orchestration (out of scope) shards VMs across hosts.

Coordination overhead. Zero cross-VMM-process coordination in steady state (each VMM process is fully independent, P12); migration introduces exactly one point-to-point coordination channel (source<->destination TCP, §20), no fleet-wide coordination required.

Practical ceiling and levers beyond it. The practical ceiling for a single host is core-count-bound vCPU density (§4); beyond it, the lever is horizontal scaling across hosts, not deeper per-host optimization - this is why Firecracker/crosvm-class VMMs (Comparative Architecture, §31) optimize for VM density (many small VMs per host) rather than any single VM's raw vCPU count.

30. Mental Models & First Principles

  • MM1 - A vCPU is a trap-and-emulate state machine, not a thread abstraction. Predicts: every guest instruction either executes natively (non-root mode) or triggers an exit - there is no third state. Bug class without it: engineers who model a vCPU as "just another OS thread" miss why register state must be fully quiesced before migration (§20.6) - a running thread has no equivalent quiescence requirement. Applies at §8.1, §20.2.
  • MM2 - EPT is a second, host-owned page-table walk, invisible to the guest. Predicts: a guest's own page tables never need host awareness; only the GPA->HPA layer does. Bug class without it: attempting to inspect/modify guest virtual memory from the host without first walking the guest's own (opaque) page tables, then EPT. Applies at §8.3, Phase 3 (§15).
  • MM3 - The virtqueue is a lock-free SPSC-per-direction ring with an adversarial peer. Predicts: every field the guest writes must be validated as if from an attacker, not merely as if from a buggy peer. Bug class without it: trusting desc.len without a bounds check is the single most common virtio backend vulnerability class historically. Applies at §8.5, Phase 5 (§17).
  • MM4 - Migration convergence is a race between dirty-page production rate and network transfer rate, not a fixed-duration operation. Predicts: no amount of iteration count alone guarantees convergence under a sufficiently write-heavy guest. Bug class without it: designing migration without an iteration cap (I12) risks an unbounded operation. Applies at §20.2, §20.6.
  • MM5 - Interrupt delivery is gated by two independent conditions: routing (IOAPIC) and priority (LAPIC TPR). Predicts: a correctly routed IRQ can still be legitimately withheld by TPR, which is not a bug. Bug class without it: engineers debug "missed interrupts" by checking routing alone and miss TPR-gating entirely. Applies at §16.2, §16.8.
  • MM6 - The KVM/userspace split delegates the hardest correctness problem (VMX mechanics) to the most-audited code in the stack. Predicts: this project's own bug surface is concentrated in device emulation and memory management, not in "running the guest," which shapes the entire threat model (§22). Bug class without it: reimplementing VMX-adjacent logic in userspace reintroduces exactly the bug class KVM already eliminated. Applies at §3, ADR-01.
  • MM7 - Every guest-visible failure must degrade to a guest-observable status, never a silent host crash. Predicts: device errors surface through the protocol they were requested over (a virtio status byte, a link-down event), preserving P10's bounded blast radius. Bug class without it: propagating a device-level error as an unhandled panic takes down unrelated devices/vCPUs sharing the process. Applies at §17.9, §18.9, §23.
  • MM8 - Dirty-bit tracking is the only source of truth for "what changed"; there is no alternative signal. Predicts: any migration design not built around KVM_MEM_LOG_DIRTY_PAGES (or an equivalent) must either over-copy (send everything, every iteration) or under-copy (silently miss writes). Bug class without it: an engineer who tries to infer dirty pages from a write-instrumentation layer at the application level duplicates hardware-provided functionality incorrectly. Applies at §8.6, §20.2.

KVM+QEMU made the opposite device-surface trade from this design: broad device compatibility (any guest OS, any legacy hardware) at the cost of a much larger CVE surface (Agache 2020's own motivating data) - it wins when guest compatibility with arbitrary/legacy operating systems matters more than minimal attack surface.

Firecracker made the identical device-minimalism choice this design makes, but rejected live migration entirely, treating VMs as ephemeral (create, run, destroy) - it wins in exactly the FaaS/serverless regime where migration's engineering cost is not worth paying because VMs are seconds-lived.

crosvm made the same virtio-only, Rust-memory-safety choice, but layered ChromeOS-specific per-device seccomp policies rather than a single process-wide jail - it wins when the deployment environment (ChromeOS) already provides the surrounding sandboxing infrastructure this design builds from scratch.

Xen made the fundamentally different choice of a ring-0 (type-1, bare-metal) hypervisor with a privileged dom0 handling device I/O (Barham 2003) - it wins when no trusted general-purpose host OS should exist at all beneath the hypervisor, the type-1 regime this design explicitly defers (Alternative Architectures, §34).

32. Back-of-Envelope Capacity Model

  1. Guest RAM dirty-bitmap size = memory_size / (4 KiB page x 8 bits) -> for 128 GiB (§4 ceiling): 128x2^30 / (4096x8) = 4 MiB bitmap - confirms §20.7's "trivial fixed cost" claim.
  2. Migration initial-copy time = memory_size / network_bandwidth -> for 1 GiB over 10 Gbps (1.25 GB/s): 1 GiB / 1.25 GB/s ~= 0.8 s - chained into the §20.4 100 ms downtime target (downtime is only the final iteration + pause, not the whole transfer).
  3. Max sustained dirty rate for convergence = network_bandwidth x downtime_target / iteration_time -> at 1.25 GB/s and a 100 ms downtime budget, the final iteration must transfer <= 125 MB, bounding the guest's tolerable dirty rate to roughly 125 MB per iteration window before falling back to stop-and-copy (I12).
  4. vCPU thread memory overhead = thread stack (2 MiB default) + Vcpu struct (§11, ~200 bytes) + kvm_run mmap (typically 8-16 KiB per KVM_GET_VCPU_MMAP_SIZE) -> ~= 2.02 MiB per vCPU, chained into §4's "2 KiB/vCPU" control-plane overhead line being deliberately exclusive of thread-stack cost (stated separately here for clarity).
  5. virtio-blk IOPS ceiling from io_uring batching = queue_depth x (1 / per-op_latency) -> at a queue depth of 128 and ~100 ns submission overhead per batched op, theoretical ceiling ~= 128 / 100ns ~= 1.28M IOPS, consistent with and validating the §4/§29 M4 target of

    =1,000,000.

  6. EPT violation cost, fleet-wide, cold-start VM boot = pages_touched x cold_violation_cost -> a 512 MiB guest touching all pages once at boot (worst case, no pre-fault): 512x2^30/4096 pages x 10 ms ~= far too slow, which is exactly why §19.7's pre-fault-at-load optimization exists - this derivation is the quantified justification for that design choice.
  7. FD budget check = 1 (kvm vm fd) + vcpus (1 each) + devices x2 (net/blk each ~2 fds) + 1 (monitor socket) -> for a 4-vCPU, 3-device VM: 1+4+6+1 = 12 FDs, comfortably inside the ADR-14 jail's <=64 budget (§4).
  8. IRQ injection latency budget vs. M8 = in-kernel irqchip round trip (no userspace hop) ~= VM-exit-equivalent cost (~1 us) + LAPIC delivery logic (~1 us) ~= 2 us, directly deriving the §29 M8 target rather than asserting it.
  9. Fuzz canary throughput needed for 24h coverage = target_exec_count / seconds_available -> to exercise >=10M distinct descriptor-chain shapes in 24h (86,400 s), the fuzzer must sustain >= 116 execs/sec, a concrete floor for hyp-fuzz corpus performance, chained from M10.
  10. Boot-time budget allocation = firmware/setup (~0.5 s) + kernel decompress+init (~2 s) + initramfs+root-mount (~1.5 s) + userspace init to login (~1 s) ~= 5 s total, deriving §4/§29 M6 from its component costs rather than asserting the number.

34. Alternative Architectures (Roads Not Taken)

Alternative A - Type-1 (bare-metal) hypervisor.

+-------------------------------------------+
|  Guest 1        Guest 2       Guest N      |
+---------------------------------------------+
|  This project's hypervisor (ring 0)          |
|   - owns scheduling, memory, devices          |
+---------------------------------------------+
|  Bare hardware                                |
+-------------------------------------------+

Regime where it wins: no trusted general-purpose host OS should exist beneath the hypervisor at all (embedded/firmware-level virtualization, highest-assurance isolation requirements). Real embodying system: Xen (Barham 2003) in its original ring-0 dom0 design. Rejected here because it requires reimplementing scheduling, memory management, and driver support that a host Linux kernel + KVM already provides at production quality - see ADR-01's rationale and MM6.

Alternative B - Binary-translation-based virtualization (no VT-x).

Guest instructions -> binary translator -> rewritten instructions -> CPU
   (privileged instructions trapped and emulated in software)

Regime where it wins: hardware lacking VT-x/AMD-V entirely (pre-2005 x86, or architectures without a hardware second-level-translation feature). Real embodying system: VMware's original binary-translation-based ESX Server (Adams & Agesen 2006). Rejected here because VT-x is universally available on target deployment hardware and eliminates the ~20% translation overhead the paper measured (ADR-02).

Alternative C - Full-device-emulation VMM (QEMU model).

+-----------------------------------------------+
|  Guest driver (real or virtio, guest's choice)  |
+-----------------------------------------------+
|  QEMU: emulates e1000, IDE, VGA, ..., virtio     |
+-----------------------------------------------+
|  KVM (same VMX/EPT delegation as this design)    |
+-----------------------------------------------+

Regime where it wins: guest compatibility requirements include legacy or arbitrary operating systems without virtio drivers (old Windows, obscure BSDs, firmware-level guests). Real embodying system: QEMU+KVM. Rejected here because the device-emulation surface is the dominant CVE class (Agache 2020's motivating data, §22) and this project's target guests all support virtio (P5).

Alternative D - Paravirtualization with a privileged dom0 device backend (Xen PV model).

+---------------+        +------------------------+
|  DomU (guest)  |<------>| Dom0 (privileged)       |
|  PV frontend   |  event  | device backends         |
|  drivers       | channel | (net/blk)                |
+---------------+        +------------------------+

Regime where it wins: a multi-tenant cloud provider wants device I/O policy/backends centrally managed in one privileged domain rather than per-guest-VMM-process (Xen's original design center). Rejected here because the per-VM-process isolation model (P12, one process per VM) is simpler to reason about and jail (ADR-14) than a shared privileged dom0 that would itself become a single point of compromise across all guest VMs on a host.

36. Glossary

  • APIC - Advanced Programmable Interrupt Controller.
  • ACPI - Advanced Configuration and Power Interface; guest firmware tables (MADT/FADT/RSDP).
  • bzImage - compressed Linux kernel image format used by the boot loader (§19).
  • CFS - Completely Fair Scheduler, the Linux host scheduler vCPU threads run under.
  • CR0/CR3/CR4 - x86 control registers governing paging and protection mode.
  • Deferred Features Register - the table (§35) tracking out-of-scope work and its un-defer trigger.
  • Dirty bitmap - per-page bitmap tracking guest writes since the last migration iteration (§8.6).
  • EPT - Extended Page Tables, Intel's second-level address translation.
  • EPT violation - the VM-exit raised when a guest access misses an EPT mapping (§8.3).
  • ExitReason - this project's typed representation of a VM-exit cause (§11).
  • FD - file descriptor.
  • GPA - guest-physical address.
  • HVA - host-virtual address.
  • Hypercall - a paravirtualized "syscall" from guest to hypervisor/VMM.
  • IOAPIC - I/O Advanced Programmable Interrupt Controller, routes device IRQs.
  • IOMMU - I/O Memory Management Unit, hardware DMA isolation (deferred, §35).
  • io_uring - Linux async I/O interface used by virtio-blk's backend (ADR-10).
  • IPI - Inter-Processor Interrupt.
  • kvm_run - the kernel/userspace shared-memory struct carrying per-vCPU exit data.
  • KVM - Kernel-based Virtual Machine, the Linux in-kernel VMX/SVM manager.
  • LAPIC - Local APIC, per-vCPU interrupt controller.
  • MemoryRegion - this project's registered guest-physical->host-virtual mapping (§11).
  • MigrationRecord - the versioned wire-format unit of the migration protocol (§11, §20).
  • MMIO - memory-mapped I/O.
  • NPT - Nested Page Tables, AMD's EPT equivalent (deferred backend, §35).
  • Pre-copy - migration strategy copying memory while the guest still runs (§20).
  • Post-copy - migration strategy resuming the guest before all memory transfers (deferred, §35).
  • seq - the ordering field in MigrationRecord enforcing I8.
  • seccomp-bpf - Linux syscall-filtering sandbox mechanism (ADR-14, P12).
  • SLAT - Second-Level Address Translation, the general term for EPT/NPT.
  • SVM - AMD Secure Virtual Machine, AMD's hardware-virtualization extensions.
  • stop-and-copy - the final pause-and-transfer step of pre-copy migration (§20.2).
  • TAP interface - a Linux virtual network interface used as virtio-net's host backend (§18).
  • TCG - Tiny Code Generator, QEMU's software-emulation fallback (referenced, §31 comparison).
