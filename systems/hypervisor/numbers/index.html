32. Back-of-Envelope Capacity Model

  1. Guest RAM dirty-bitmap size = memory_size / (4 KiB page x 8 bits) -> for 128 GiB (§4 ceiling): 128x2^30 / (4096x8) = 4 MiB bitmap - confirms §20.7's "trivial fixed cost" claim.
  2. Migration initial-copy time = memory_size / network_bandwidth -> for 1 GiB over 10 Gbps (1.25 GB/s): 1 GiB / 1.25 GB/s ~= 0.8 s - chained into the §20.4 100 ms downtime target (downtime is only the final iteration + pause, not the whole transfer).
  3. Max sustained dirty rate for convergence = network_bandwidth x downtime_target / iteration_time -> at 1.25 GB/s and a 100 ms downtime budget, the final iteration must transfer <= 125 MB, bounding the guest's tolerable dirty rate to roughly 125 MB per iteration window before falling back to stop-and-copy (I12).
  4. vCPU thread memory overhead = thread stack (2 MiB default) + Vcpu struct (§11, ~200 bytes) + kvm_run mmap (typically 8-16 KiB per KVM_GET_VCPU_MMAP_SIZE) -> ~= 2.02 MiB per vCPU, chained into §4's "2 KiB/vCPU" control-plane overhead line being deliberately exclusive of thread-stack cost (stated separately here for clarity).
  5. virtio-blk IOPS ceiling from io_uring batching = queue_depth x (1 / per-op_latency) -> at a queue depth of 128 and ~100 ns submission overhead per batched op, theoretical ceiling ~= 128 / 100ns ~= 1.28M IOPS, consistent with and validating the §4/§29 M4 target of

    =1,000,000.

  6. EPT violation cost, fleet-wide, cold-start VM boot = pages_touched x cold_violation_cost -> a 512 MiB guest touching all pages once at boot (worst case, no pre-fault): 512x2^30/4096 pages x 10 ms ~= far too slow, which is exactly why §19.7's pre-fault-at-load optimization exists - this derivation is the quantified justification for that design choice.
  7. FD budget check = 1 (kvm vm fd) + vcpus (1 each) + devices x2 (net/blk each ~2 fds) + 1 (monitor socket) -> for a 4-vCPU, 3-device VM: 1+4+6+1 = 12 FDs, comfortably inside the ADR-14 jail's <=64 budget (§4).
  8. IRQ injection latency budget vs. M8 = in-kernel irqchip round trip (no userspace hop) ~= VM-exit-equivalent cost (~1 us) + LAPIC delivery logic (~1 us) ~= 2 us, directly deriving the §29 M8 target rather than asserting it.
  9. Fuzz canary throughput needed for 24h coverage = target_exec_count / seconds_available -> to exercise >=10M distinct descriptor-chain shapes in 24h (86,400 s), the fuzzer must sustain >= 116 execs/sec, a concrete floor for hyp-fuzz corpus performance, chained from M10.
  10. Boot-time budget allocation = firmware/setup (~0.5 s) + kernel decompress+init (~2 s) + initramfs+root-mount (~1.5 s) + userspace init to login (~1 s) ~= 5 s total, deriving §4/§29 M6 from its component costs rather than asserting the number.
