Project Number: 2

Project Name: Decision Layer

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Decision Layer is a codebase decision-capture and drift-detection system: an IDE-integrated capture surface records architectural decisions bound to concrete code anchors (file path, AST path, symbol identity, content hash, fuzzy context window); an anchor-tracking engine keeps those bindings alive across edits, renames, and refactors by re-resolving anchors on every reparse; a drift detector classifies divergence between recorded decision and current code state (moved, renamed, modified-in-place, deleted, semantically-contradicted); a team backend stores the append-only decision graph, supports replay-based reconstruction, forking of a decision graph for experimental branches, and compliance export (SPDX/CycloneDX-adjacent bundles) for audit. The system treats a decision as a claim about code that must be re-verified, never a static comment or a stored line number.

Phase-0 deliverable (numbered modules, see §10 for file paths):

  1. dlcore — Rust core library: AST index (tree-sitter), anchor model, anchor resolver, drift detector, append-only decision log, replay engine.
  2. lsp-bridge — thin LSP client/server bridge exposing dlcore operations to any LSP-aware editor via custom LSP extension methods (decisionLayer/*).
  3. capture-surface — VS Code extension (TypeScript) hosting the capture UI: anchor picker, decision editor, drift inbox.
  4. sync-client — Rust crate translating local op-log entries into SyncOp batches against the team backend.
  5. team-backend — self-hostable API service (Rust, axum) + Postgres-backed decision graph store + object storage for content blobs.
  6. compliance-exporter — crate producing audit bundles (decision graph snapshot + anchor provenance + SPDX/CycloneDX-shaped manifest) from a replay cursor.
  7. dl-cli — command-line tool wrapping dlcore for CI use (drift scan, replay verify, export) without requiring the editor extension.

System boundaries. Provides: decision capture bound to code, anchor resolution across edits, drift classification, append-only history with replay, team sync, compliance export. Does NOT provide: automatic code generation from decisions, automatic drift resolution (P2), natural-language decision authoring assistance, project-management/ticketing integration, a general-purpose code-review tool. Non-goals: replacing ADR markdown files as the narrative record (Decision Layer stores structured, anchored decisions; long-form rationale documents are linked, not replaced — see Nygard 2011 applied in §5); replacing version control; providing a general semantic-diff product independent of decision tracking.

Deployment model: (a) local — extension + dlcore run entirely inside the developer's editor process, decision log is a local append-only file, no network; (b) self-hosted — a team runs team-backend + Postgres + object storage inside its own network, sync-client pushes/pulls over HTTPS; (c) hosted — a vendor-operated multi-tenant team-backend (deferred, see §37 Deferred Features Register). Phase 0–6 implement (a). Phase 7 implements (b). (c) is PhaseDeferred("37. Deferred Features Register").

Users/operators: individual developers (capture, drift review), tech leads (decision graph review, forking, supersession), compliance/audit staff (export consumption only, read path), platform engineers operating the self-hosted backend (Phase 7+).

What later phases unlock: Phase 3 unlocks interactive capture; Phase 4 unlocks anchors surviving real edits; Phase 5 unlocks drift alerts; Phase 6 unlocks history replay; Phase 7 unlocks team sharing; Phase 8 unlocks graph queries and forking; Phase 9 unlocks non-Rust/TS codebases; Phase 10 unlocks audit export; Phase 11 hardens all of the above to the Performance Engineering targets.

Language: Rust for dlcore, lsp-bridge, sync-client, team-backend, compliance-exporter, dl-cli — rationale: tree-sitter's canonical bindings and the strongest incremental-parsing ecosystem (rust-analyzer's salsa) are Rust-native (applied in §5); anchor resolution runs on every keystroke-batch and must hit the p99 budget in §4, which rules out GC-paused runtimes; a single core library compiled once and reused by CLI, backend, and (via WASM) the extension avoids logic duplication. TypeScript for capture-surface only — rationale: VS Code's extension host is Node/TypeScript; the extension is a thin UI shell that calls into dlcore compiled to WASM, holding no anchor-resolution logic itself. Rejected: Python for the core (GIL serializes concurrent reparse across open files, no mature tree-sitter incremental-edit API at parity with the Rust crate); Go for the core (GC pause tail latency conflicts with the p99 anchor-resolution budget in §4; weaker tree-sitter binding maintenance than Rust's); pure TypeScript/Node for the core (single-threaded event loop cannot bound reparse latency under concurrent multi-file edits, V8 GC pauses violate p99).

Prerequisites: LSP fundamentals (document sync, incremental text sync), tree-sitter grammar and query mechanics, incremental-computation concepts (memoized queries, revision counters), AST-diffing (tree edit distance), append-only log design, CRDT-adjacent merge semantics for concurrent op-logs, content-addressed storage.

Timeline: Phase 0 — 2 weeks. Full system (Phases 0–11) — 11 months at one senior engineer full-time, or 6 months at a two-engineer team. Phases 0–6 (single-user, local) — 5 months; Phases 7–11 (team, multi-language, audit, hardening) — 6 months.

Deferrals: hosted multi-tenant SaaS PhaseDeferred("37. Deferred Features Register"); automatic drift auto-resolution (rejected as a permanent non-goal by P2, tracked regardless) PhaseDeferred("37. 2. Why Build This

  • Anchor resolution across edits — the same class of identity-tracking problem as rust-analyzer's incremental recomputation and LSP position mapping.

  • AST-level identity vs text-level identity — tree edit distance (Falleri et al. ASE 2014), content-addressing, symbol identity vs line-number identity.

  • Append-only, replayable history — the same discipline as event-sourced systems and content-addressed version control.

  • Drift as a first-class detected event, never silently auto-fixed — a hard lesson in designing systems that must never lie about their own state.

  • Team-scale conflict resolution over a decision graph — op-log merge semantics, the same family of problems as CRDT-based collaborative editors.

  • Compliance export under real interchange formats (SPDX/CycloneDX-adjacent) — translating an internal graph into an auditable, third-party-verifiable artifact.

  • Direct lineage to Parnas & Clements 1986 ("fake a rational design process") and Nygard 2011 (ADRs) — this system operationalizes both: the decision record IS the faked rational design process, made falsifiable by anchors instead of aspirational.

  • Sibling systems: shares the incremental-index problem with rust-analyzer; shares the AST-diff problem with GumTree and difftastic; shares the symbol-identity problem with Sourcegraph SCIP; shares the audit-export problem with SBOM tooling (SPDX/CycloneDX).

What Mastery Looks Like

  • Building an anchor resolver whose precedence order (symbol → AST path → content hash → fuzzy window) survives a real rename-then-refactor sequence (Phase 4, Phase 8 worked example in §8).

  • Implementing a tree-sitter-backed incremental index that reparses only changed subtrees under keystroke-batch pressure (Phase 1, Phase 4).

  • Classifying five distinct drift kinds correctly against a labeled fixture corpus with a quantified false-positive rate (Phase 5).

  • Designing an append-only decision log whose replay reproduces the current graph byte-for-byte (Phase 6, I3).

  • Merging concurrent op-logs from two developers without silent data loss (Phase 7).

  • Exporting a compliance bundle that a third party can verify without trusting the exporting team (Phase 10).

  • Extending the AST layer to a second and third language without touching the anchor model (Phase 9) — proof the abstraction boundary in §8 actually holds.

capture-surface: VS Code extension; renders decision editor, drift inbox, anchor picker; holds no resolution logic; talks to lsp-bridge over LSP custom methods (decisionLayer/*).

lsp-bridge: Rust LSP server exposing dlcore over the Language Server Protocol; owns the editor session lifecycle, document sync (incremental, per section 3.4 of the LSP specification), and dispatch of custom requests.

ast-indexer: tree-sitter-backed parser pool; maintains one incremental parse tree per open file; applies edits via tree-sitter's InputEdit-equivalent range patch, not full reparse.

anchor-resolver: given an anchor and a current AST/text state, attempts resolution in precedence order (§8); returns ResolutionResult.

anchor-repair engine: orchestrates the named repair procedure (§8) when a resolver reports non-exact resolution; queues ambiguous cases for capture-surface confirmation.

drift-detector: compares resolved anchor state against the decision's recorded assertion; classifies into the five-way taxonomy (§8); emits DriftEvent.

decision-store: local, append-only, content-addressed op-log (I3, I4); sole writer of decision state; all other components read through it.

replay-engine: reconstructs the decision graph at any point by folding the op-log from genesis; used for verification (H-style self-check) and for team-backend ingestion.

sync-client: converts local op-log tail into SyncOp batches; handles retry, backoff, and conflict surfacing from the backend's merge response.

team-backend (API gateway + decision-graph service + Postgres + object storage): durable, multi-user store; owns tenant isolation, fork/supersede semantics, and the canonical merged op-log across contributors.

compliance-exporter: reads a ReplayCursor-bounded slice of the graph and content blobs; emits an ExportBundle in an SPDX/CycloneDX-adjacent shape plus anchor provenance.

telemetry-emitter: cross-cutting OpenTelemetry instrumentation (spans, counters, histograms) attached to every box above; never transmits source content (I12).

6. Design Principles

  1. P1 — An anchor is a claim, not a fact. Every anchor must be re-verified on read, never trusted from cache alone. Tradeoff: repeated verification costs CPU (§4 latency budget). Operational implication: resolver runs on every drift scan, not just on save. Violating it: a stale anchor silently points at the wrong code, and the system lies to the user (I2).

  2. P2 — Drift is detected, never auto-resolved. The system flags divergence; a human decides whether code or decision is wrong. Tradeoff: more manual triage load. Operational implication: drift inbox is a durable queue, not a transient notification. Violating it: auto-"fixing" a decision to match code silently erases the original intent (I6).

  3. P3 — The decision log is append-only and content-addressed. No decision record is ever mutated in place; state changes are new op-log entries. Tradeoff: storage grows monotonically (bounded by §4 storage-growth ceiling). Operational implication: replay is the only source of current state (I3). Violating it: two replicas can silently diverge with no way to detect it.

  4. P4 — Anchor resolution is precedence-ordered, never best-of-N voting. Symbol identity beats AST path beats content hash beats fuzzy window, strictly in that order. Tradeoff: a lower-precedence match is ignored even if it "looks" more confident. Operational implication: precedence order is a single hard-coded constant, tested exhaustively (§8). Violating it: nondeterministic anchor resolution across runs.

  5. P5 — A decision without an anchor must be explicit, not implicit. Repo-global decisions are tagged scope: repo-global, never left with an empty anchor list by omission. Tradeoff: capture UI must force a scope choice. Operational implication: the drift detector skips repo-global decisions by design (I1). Violating it: an unanchored decision is indistinguishable from a bug.

  6. P6 — Source content never leaves the client without explicit opt-in. Sync transmits anchors, decision text, and hashes; raw source snippets sync only if the user opts in per repo. Tradeoff: backend cannot show inline code context by default. Operational implication: sync-client strips snippet fields unless content_sync_enabled (I12). Violating it: an unaudited data-exfiltration channel (T1).

  7. P7 — A superseded decision is retired, never deleted. Supersession is a graph edge, not an erasure. Tradeoff: the graph grows without bound. Operational implication: query layer must default to "active view" (excluding superseded/retired) with an explicit "show all" toggle. Violating it: history that cannot answer "why did we used to do X" (Cunningham 1992 applied here — deferred/changed decisions are debt, not garbage).

  8. P8 — Reparse is incremental by construction, not by optimization. The AST indexer never falls back to full-file reparse except on first open or corruption. Tradeoff: incremental patch logic is more complex than "just reparse everything". Operational implication: every edit event carries a byte-range patch (§4 keystroke-batch budget). Violating it: p95 reparse latency blows the budget on large files.

  9. P9 — Ambiguous anchor resolution requires human confirmation, never silent pick-first. When two candidates tie in precedence, the resolver returns Ambiguous, not an arbitrary winner. Tradeoff: more UI interruption. Operational implication: capture-surface drift inbox surfaces ambiguous cases distinctly from confirmed drift. Violating it: an anchor can silently rebind to the wrong copy-pasted block (§16 pitfall).

  10. P10 — The decision graph is a directed graph with typed edges, never free-text cross-references. supersedes, depends-on, contradicts are the only edge kinds. Tradeoff: some relationships must be forced into one of three kinds. Operational implication: graph queries are typed traversals, not text search. Violating it: the graph degrades into an unqueryable pile of prose links.

  11. P11 — Compliance export is independently verifiable. An export bundle must be checkable by a party that does not trust the exporting team — via content hashes and a replay-reproducible cursor. Tradeoff: export format is more rigid than free-form reports. Operational implication: compliance-exporter embeds the ReplayCursor and per-node content hashes (§8, §11). Violating it: an export that can be silently doctored defeats its own purpose (T3).

  12. P12 — Team sync merges are deterministic given the same op set. Two replicas that receive the same ops in any order converge to the same graph. Tradeoff: requires a total order (Lamport timestamp + actor id tie-break), not physical wall-clock time. Operational implication: SyncOp carries a logical clock, not just a timestamp (§8 op-log merge semantics). Violating it: split-brain graphs that never reconverge (FM-7).

  13. P13 — Every telemetry event is reviewed for identifier leakage before emission. File paths and symbol names are hashed or redacted in telemetry unless the repo opts into verbose diagnostics. Tradeoff: harder to debug specific repos remotely. Operational implication: telemetry-emitter has a redaction layer as a mandatory pipeline stage (I12, T5). Violating it: identifiers leak into a shared telemetry backend.

Debugging methodology: a deterministic simulator drives the full pipeline (edit sequence → reparse → anchor resolution → drift scan → op-log append → replay) against a corpus of recorded edit traces, asserting each invariant after every simulated step; any invariant violation halts the simulation and dumps the minimal reproducing edit sequence (bisected by edit-count, not just failing at the end).

8. Domain Model

Decision record fields. id (content-addressed, see §11 DecisionId), title, rationale (free text, may link to an external ADR markdown file per Nygard 2011), status (lifecycle state, below), scope (anchored | repo-global), anchors (list, §11 Anchor), edges (list, §11 DecisionEdge), tags, repo_id, created_at, author, assertion (a structured rule the drift detector checks — e.g. "no direct instantiation of type X within this anchor's AST subtree").

Anchor-repair procedure (named steps, decision table).

Steps: (1) detect invalidation trigger from file-watcher/LSP change event; (2) attempt symbol_ref resolution via document-symbol tree; (3) on failure, attempt ast_path match via tree-sitter query, same file then repo-wide if file path changed; (4) on failure, attempt content_hash exact match scoped to the diff hunk (Myers 1986 O(ND) diff bounds the search); (5) on failure, attempt fuzzy_window match under an edit-distance threshold; (6) on total failure, mark Orphaned, emit DriftEvent(kind: Deleted-or-Unresolvable).

Op-log merge semantics. Each op carries (decision_id, op_type, lamport_ts, actor_id). Merge order is total: sort by (lamport_ts, actor_id), ties broken by actor_id lexicographic order (P12). Worked example — decision surviving a rename then a refactor. A decision anchors payments::Ledger::commit via symbol_ref. Step 1: developer renames the function to Ledger::apply. Anchor resolver's symbol_ref lookup fails (name changed); falls to ast_path — the function's AST shape (parameter count, body structure) is unchanged, so ast_path resolves uniquely; anchor-repair engine updates symbol_ref to the new name and appends an op-log entry recording the repair with confidence High. Step 2: developer later extracts part of the function body into Ledger::apply_with_validation, splitting the AST subtree. ast_path no longer matches uniquely (two candidate subtrees share ancestry); resolver returns Ambiguous; capture-surface prompts the developer, who confirms the anchor now binds to apply_with_validation; op-log records the confirmed rebind with actor id.

Malformed-input examples. (a) An anchor referencing a file_path that was never valid UTF-8 — rejected at capture time with AnchorError::InvalidPath. (b) A content_hash computed over a byte range that no longer exists in the file (post-truncation) — resolver returns Orphaned immediately, skipping lower-precedence tiers since the block itself is gone. (c) An assertion rule referencing a symbol kind the current language's tree-sitter grammar does not define — rejected at decision-authoring time with a schema validation error.

Failure-path example. A SyncOp batch arrives at team-backend with a lamport_ts lower than the tenant's last-ingested watermark for that actor (clock regression, e.g. client clock reset). Ingestion rejects the batch (I9), returns a SyncError::ClockRegression, and sync-client requests the actor's last-known watermark before resubmitting with corrected sequencing — never silently reordering into the log.

13. Phase 1 — Tree-sitter AST Index

13.1 Objectives

Implement ast_index.rs: a tree-sitter-backed incremental parser pool that maintains one parse tree per open file and applies edits as byte-range patches (P8), never full reparses except on first open (I11).

13.2 Detailed Implementation Steps

Integrate tree-sitter grammars for the two languages needed by Phase 0–8's own dogfooding corpus: Rust and TypeScript (ADR-02, ADR-14 pins exact grammar commit hashes in a lockfile committed to crates/dlcore/grammars.lock). Implement a parser-pool keyed by file path, each holding the current tree and byte buffer. On an incoming edit (byte offset, length removed, length inserted), apply tree-sitter's edit-tracking API before reparsing so only the affected subtree is re-derived (tree-sitter lesson, §5). Wrap the pool behind a salsa-style memoized query (ast_of(file_path) -> Tree, ADR-08) keyed by a per-file revision counter, so downstream consumers (anchor-resolver, drift-detector) never reparse redundantly within one revision. Implement a corruption detector: if tree-sitter reports a byte-range mismatch after an edit (buffer/tree desync), escalate to full reparse exactly once per I11's three-strikes rule, then flag the file as degraded.

13.3 Deliverable

dl-cli index <repo> builds a full AST index of a repository and reports per-file parse status (clean / error-recovered / degraded). Incremental edits applied via a test harness that replays a recorded keystroke trace show only touched subtrees re-derived (verified via a per-file "nodes re-derived" counter).

13.4 Acceptance Criteria

Cold index build of the 1M-LOC benchmark corpus (§4) completes in ≤ 90 s single-core. Incremental reparse of a single-line edit in a 5,000-LOC file completes in ≤ 8 ms p95 (§4). Zero full-reparse escalations across the conformance/fixtures/replay/keystroke-trace-1 fixture (2,000 simulated keystrokes). Grammar version lockfile matches ADR-14 exactly; CI fails if a grammar version drifts unpinned.

13.5 Conformance Fixtures

conformance/fixtures/parse/malformed-syntax.rs — purpose: unclosed brace, expected output: error-recovered parse tree with a bounded error node, not a crash. conformance/fixtures/ replay/keystroke-trace-1 — purpose: 2,000-edit recorded trace on a 5,000-LOC file, expected output: zero full-reparse escalations, p95 reparse ≤ 8 ms. conformance/fixtures/parse/ grammar-version-mismatch — purpose: a file parsed under a stale pinned grammar, expected output: dl-cli index reports a grammar-version warning, does not silently reparse under a newer grammar.

13.6 Pitfalls

Whitespace-only reformatting invalidates naive line-based tracking but must NOT force a full reparse — verify tree-sitter's edit API correctly narrows the affected range; manifestation: reparse time spikes on a formatter run; root cause: edit offsets computed in characters, not bytes, under multi-byte UTF-8; debug method: replay the formatter diff through the keystroke- trace harness; signal: parse.full_reparse.count (I11) spikes; recovery: fix offset computation to byte-based. External-scanner grammar bugs on generated code (large minified or generated files) causing pathological backtracking — manifestation: single-file parse exceeding the cold-build budget; root cause: generated code triggers grammar ambiguity paths; debug method: isolate the file and time-box the parse; signal: per-file parse duration outlier in telemetry; recovery: apply a size/complexity circuit breaker, mark file degraded rather than blocking the whole index.

13.7 Performance Concerns

Parser-pool memory is bounded by keeping only open/recently-touched files' trees resident, evicting LRU beyond a configurable working-set size (feeds the 900 MB/1M-LOC ceiling, §4). Batch keystroke edits within a debounce window before triggering reparse to avoid redundant work on rapid multi-character input.

13.8 Edge Cases

Binary files misidentified as text — reject via a magic-byte sniff before parsing. Extremely deep nesting (pathological recursion) — bound recursion depth, degrade gracefully. File truncated mid-edit (partial write from another tool) — treat as a corruption trigger (I11). Concurrent edits to the same file from two processes (rare, e.g. external formatter plus editor) — last-applied-edit wins for the in-memory tree, but the on-disk watcher reconciles on next save.

13.9 Failure Analysis

A grammar crash (segfault-class issue in an external scanner) is contained per-file via a subprocess/panic-boundary around the parse call; blast radius is the single file, which is marked degraded and excluded from anchor resolution until manually re-indexed; operator visibility via a parse.degraded_files gauge.

13.10 Operational Notes

Expose parse.full_reparse.count, parse.degraded_files, and parse.duration_ms histogram per file-size bucket. Grammar lockfile changes require a re-index of the full corpus as a migration step (documented in Compatibility & Versioning, §27).

14. Phase 2 — Anchor Model & Resolver

14.1 Objectives

Implement the Anchor type family (§11) and the precedence-ordered anchor-resolver (P4, P1) against the AST index from Phase 1, without yet wiring the capture UI (Phase 3).

14.2 Detailed Implementation Steps

Implement symbol_ref resolution using a document-symbol extraction pass over the tree- sitter AST (a reduced analog of LSP textDocument/documentSymbol). Implement ast_path construction and matching using the GumTree-derived bottom-up/top-down matcher (Falleri et al. ASE 2014, §5), bounded per ADR-19 to avoid quadratic blowup on large subtree moves. Implement content_hash computation over a whitespace-normalized byte range (blake3, ADR-06) and exact-match lookup scoped by the Myers 1986 O(ND) diff of old-vs-new file content to bound the search space. Implement fuzzy_window matching as an edit-distance-thresholded comparison over a configurable ± N line window with whitespace normalization. Wire all four into the single precedence-ordered resolve(anchor, ast_state) -> ResolutionResult entry point (I5 — total, deterministic order, no voting per P4). Implement tie detection: if two tiers report non-identical candidate targets, return Ambiguous (P9) rather than picking the higher-precedence one silently when the higher tier's own match is itself low-confidence.

14.3 Deliverable

A dl-cli resolve <anchor-file> command that, given a serialized anchor and a target repo state, prints the ResolutionResult (Resolved/Ambiguous/Orphaned) with confidence tier and timing.

14.4 Acceptance Criteria

Anchor-resolution latency: p50 ≤ 3 ms, p95 ≤ 20 ms, p99 ≤ 60 ms (§4) measured against the conformance/fixtures/rename-refactor-corpus at 10,000 anchors. Resolution is deterministic: running the same frozen input 100 times yields byte-identical ResolutionResult output (I5, property-tested via proptest, ADR-15). Zero silent mis-resolutions on the labeled ambiguous-cases fixture — every case there returns Ambiguous, never a picked winner.

14.5 Conformance Fixtures

conformance/fixtures/rename-refactor-corpus/rename-only/ — purpose: 200 anchors surviving a pure rename, expected output: 100% resolve via ast_path tier at High confidence. conformance/fixtures/rename-refactor-corpus/move-and-rename/ — purpose: 200 anchors surviving a file move plus symbol rename, expected output: ≥ 95% resolve (some legitimately degrade to Medium/content_hash tier). conformance/fixtures/ambiguous-cases/copy-paste/ — purpose: a block duplicated via copy-paste, expected output: resolver returns Ambiguous, never a silent first-match pick (P9).

14.6 Pitfalls

Anchor false-positive re-binding after copy-paste — manifestation: an anchor silently attaches to the wrong of two now-identical blocks; root cause: content_hash tier alone cannot distinguish duplicates; debug method: replay the copy-paste fixture and inspect which tier resolved; signal: anchor.resolve.ambiguous should have fired but did not; recovery: require ast_path context (parent chain) to break ties before falling to content_hash. Whitespace-only reformat invalidating content_hash unnecessarily — manifestation: reformat- only commits generate mass drift events; root cause: hash computed over raw bytes, not normalized whitespace; debug method: diff hash inputs pre/post format; signal: drift spike correlated with a formatter commit; recovery: normalize whitespace before hashing (§8 anchor model). Generated-code churn causing constant ast_path shifts — manifestation: anchors in generated files orphan on every regeneration; debug method: correlate orphan events with known generated-file globs; recovery: allow repos to mark generated paths as low-priority so resolver escalates confidence thresholds rather than orphaning outright.

14.7 Performance Concerns

ast_path matching is the most expensive tier; short-circuit via symbol_ref first (P4 order already does this) and bound the GumTree-derived search window (ADR-19) so worst-case files don't blow the p99 budget. Cache per-file symbol tables keyed by the same revision counter as Phase 1's AST cache to avoid redundant document-symbol extraction.

14.8 Edge Cases

An anchor whose file_path no longer exists anywhere in the repo (not moved, truly deleted) — resolver must short-circuit to Orphaned without running expensive tiers. A symbol_ref that matches multiple overloaded functions with identical qualified names (language-specific overloading) — treated as ambiguous by construction, never arbitrarily first-matched. An anchor whose recorded ast_path references a node type no longer emitted by an upgraded grammar (ADR-14 version bump) — falls to content_hash/fuzzy_window, flagged for re- anchoring.

14.9 Failure Analysis

A resolver crash on a single anchor must not abort a batch drift scan — wrap resolution in a per-anchor failure boundary, log and count anchor.resolve.error, continue the batch. Systemic resolver slowdown (p99 budget breach across many anchors) triggers an alert; operator can inspect anchor.resolve.latency_ms histograms by tier to find which tier is the bottleneck.

14.10 Operational Notes

Emit anchor.resolve.latency_ms (histogram, tagged by resolved tier), anchor.resolve. ambiguous and anchor.resolve.orphaned counters. dl-cli resolve --explain prints the per-tier attempt trace for debugging a specific anchor without needing to read logs.

16. Phase 4 — Incremental Reparse & Anchor Repair

16.1 Objectives

Wire Phase 1's incremental reparse to Phase 2's resolver under real, continuous editing: implement the full anchor-repair engine (§8 named steps) that runs automatically on every file-watcher/LSP change event, not just on demand (P1, P8).

16.2 Detailed Implementation Steps

Implement repair.rs: a change-event listener subscribing to lsp-bridge's document-sync stream, debounced per a configurable keystroke-batch window (§4). On each batch, re-run ast_index.rs's incremental reparse (Phase 1), then re-run anchor-resolver (Phase 2) for every anchor whose file was touched, scoped via the Myers 1986 diff hunk boundaries to avoid re-resolving unaffected anchors in the same file. Implement the six-step repair procedure from §8 as an explicit state machine (RepairCandidate collection → precedence selection → Resolved/Ambiguous/Orphaned per I2). On Ambiguous, enqueue to a durable local queue consumed by capture-surface's drift inbox (Phase 5 wires the UI; Phase 4 only produces the queue and CLI-visible state). On successful repair, append an op-log entry (OpType::Repair) recording old anchor, new anchor, confidence tier, and triggering edit range — never mutating the prior anchor in place (P3, I4). Implement the three-strikes escalation from I11: after three consecutive incremental-reparse failures on one file, escalate to full reparse once, then mark the file degraded if the fourth also fails.

16.3 Deliverable

dl-cli watch <repo> runs the full incremental loop against a live file-watcher, printing repair events as they occur, with a running count of Resolved/Ambiguous/Orphaned outcomes.

16.4 Acceptance Criteria

Anchor-survival rate on conformance/fixtures/rename-refactor-corpus/rename-and-refactor ≥ 92% resolved at High confidence or better (measures the full repair pipeline, not just the resolver in isolation). Incremental reparse-to-repair round trip ≤ 8 ms + 20 ms (§4's reparse and resolution p95 budgets composed) measured end to end via the keystroke-trace-1 fixture replayed through the live watcher. Zero anchors silently rebound without an op-log entry (I4, verified by replay reproducing the same final state, I3).

16.5 Conformance Fixtures

conformance/fixtures/rename-refactor-corpus/rename-and-refactor/ — purpose: the two-step worked example from §8 (rename then partial extraction), expected output: step 1 resolves at High via ast_path, step 2 returns Ambiguous. conformance/fixtures/replay/repair-log- determinism/ — purpose: same edit trace replayed twice, expected output: byte-identical op-log entries both times (I5 extended to the repair pipeline). conformance/fixtures/ malformed/mid-edit-truncation/ — purpose: a file truncated mid-write (simulated partial disk write), expected output: repair engine treats it as a corruption trigger (I11), does not crash the watch loop.

16.6 Pitfalls

Decision-log merge conflicts arising from two repair events racing on the same anchor within one debounce window — manifestation: two Repair op-log entries for the same anchor with divergent targets; root cause: debounce window boundary allows overlapping batches under heavy concurrent edits; debug method: replay the trace with debounce-window instrumentation; signal: oplog.integrity.check (I4) flags a same-anchor double-write; recovery: serialize repair processing per-file via a per-file lock, never per-repo. Monorepo path collisions where two files in different subprojects share an identical relative path fragment used by a naive fuzzy_window cache key — manifestation: repair engine attaches the wrong file's candidate; root cause: cache keyed on partial path, not full repo-relative path plus repo_id; debug method: reproduce with a synthetic monorepo fixture; recovery: always key by full canonical path. Generated-code churn triggering repeated Orphaned cycles on every build — manifestation: drift-scan noise from build-output directories; debug method: check whether orphaned anchors correlate with .gitignored paths; recovery: exclude build-output globs from the watcher at the ast-indexer boundary, not post-hoc in repair.

16.7 Performance Concerns

Debounce window size trades responsiveness against redundant work; too short causes overlapping batches (the pitfall above), too long delays drift visibility. Per-file locking (pitfall recovery) must not become a global bottleneck — use a sharded lock table keyed by file-path hash. Repair-queue durability (for Ambiguous cases) must not block the reparse hot path — write asynchronously to the local queue store.

16.8 Edge Cases

An edit that both moves a file and modifies its content within one debounce batch — repair must attempt file-move detection (via content_hash match at the new path) before falling to Orphaned. A repair racing against a concurrent dl-cli watch restart — in-flight repairs must be resumable from the last durable op-log entry, never double-applied. A file watched by two separate dlcore instances (e.g. two editor windows on the same repo) — per-file locking must be filesystem-visible (advisory lock file), not merely in-process.

16.9 Failure Analysis

A repair-engine panic on one file's batch must not crash the watch loop for other files — per-file failure boundary (mirrors Phase 1's per-file corruption isolation); blast radius is the single file, flagged degraded; forensics via the op-log entries leading up to the failure (replayable, I3). Systemic repair backlog growth (queue depth climbing) triggers an alert; operator inspects repair.queue_depth gauge to distinguish a genuine edit storm from a stuck worker.

16.10 Operational Notes

Emit repair.outcome counter (tagged Resolved/Ambiguous/Orphaned/Error), repair. queue_depth gauge, repair.debounce_batch_size histogram. dl-cli watch --verbose surfaces the full six-step trace per repair for local debugging, mirroring Phase 2's --explain.

17. Phase 5 — Drift Detector & Taxonomy

17.1 Objectives

Implement drift.rs: classify every repaired-but-changed anchor into the five-way taxonomy (§8) and emit DriftEvents (I13); wire the drift inbox UI (driftInbox.ts stub from Phase 3) to a real feed.

17.2 Detailed Implementation Steps

Implement classification rules mapping repair outcomes (Phase 4) to DriftKind: Moved when content_hash is unchanged but file_path differs; Renamed when symbol_ref name changed but ast_path shape is preserved; ModifiedInPlace when content within anchor bounds changed but structure (ast_path) is preserved; Deleted when repair returns Orphaned with no candidate at any tier; SemanticallyContradicted when the anchor resolves cleanly but the decision's assertion rule (§8, an AST-pattern query over the resolved subtree, difftastic lesson applied — syntax-aware, not line-aware) evaluates false. Implement assertion evaluation as a bounded tree-sitter query executed against the resolved anchor's current subtree (Falleri et al. ASE 2014 and difftastic both inform the query-bounding strategy, ADR-19). Wire DriftEvent emission into the op-log (OpType::DriftDetected) and the Active -> Drifted lifecycle transition (§8 state table). Implement the drift-scan modes: incremental (changed files only, triggered by Phase 4's repair loop) and full (§4 wall-clock budget, triggered on demand or scheduled). Wire driftInbox.ts to render live DriftEvents grouped by DriftKind, with an explicit "mark reviewed" action producing the Drifted -> Active transition (I6 — requires resolved_by).

17.3 Deliverable

dl-cli drift-scan <repo> [--incremental|--full] reports classified drift events; the extension's drift inbox lists them live and lets a developer mark each reviewed.

17.4 Acceptance Criteria

Full drift scan of 50,000 decisions completes in ≤ 120 s wall clock; incremental scan of a single changed file completes in ≤ 2 s (§4). Classification accuracy on the labeled conformance/fixtures/drift-taxonomy corpus (500 labeled cases, 100 per kind) ≥ 97% exact- kind match. False-positive SemanticallyContradicted rate on the assertion-noise fixture (200 unrelated edits) ≤ 2%.

17.5 Conformance Fixtures

conformance/fixtures/drift-taxonomy/moved-100/, .../renamed-100/, .../modified-100/, .../deleted-100/, .../contradicted-100/ — purpose: 100 labeled cases per DriftKind, expected output: exact classification match ≥ 97% aggregate. conformance/fixtures/drift- taxonomy/assertion-noise/ — purpose: 200 edits unrelated to any assertion, expected output: ≤ 2% false-positive SemanticallyContradicted flags. conformance/fixtures/regression/drift- scan-perf/ — purpose: 50,000-decision synthetic repo, expected output: full scan ≤ 120 s, incremental ≤ 2 s.

17.6 Pitfalls

Whitespace-only reformat misclassified as ModifiedInPlace instead of being a non-event — manifestation: mass drift events after a formatter run; root cause: content_hash computed pre-normalization at capture time but assertion evaluated on raw text; debug method: replay a formatter-only commit through drift-scan; recovery: normalize whitespace consistently at both capture and scan time (mirrors Phase 2's pitfall, now surfacing at the taxonomy layer). Decision-log merge conflicts between a DriftDetected event and a concurrent manual resolved_by action — manifestation: a drift event marked reviewed just as a new drift event fires on the same anchor; root cause: race between drift-scan and inbox action both writing to the same decision; debug method: inspect op-log ordering via lamport_ts; recovery: serialize both writers through the same per-decision lock used in Phase 4. Generated-code churn causing repeated Deleted-then-Renamed flapping across build cycles — recovery: same generated-path exclusion as Phase 4 (§16.6), applied consistently at the drift layer.

17.7 Performance Concerns

Full drift scan is dominated by anchor re-resolution cost (Phase 2); parallelize across files using a worker pool bounded by available cores, aggregating results single-threaded into the op-log to preserve I4's append-only ordering guarantee. Assertion evaluation should be skipped entirely for decisions with no assertion rule (the common case) to avoid wasted tree-sitter query execution.

17.8 Edge Cases

A decision whose anchor is Orphaned (Phase 4) but whose assertion would otherwise fire — Deleted takes classification precedence over SemanticallyContradicted since there is no subtree to evaluate the assertion against. A decision with multiple anchors where anchors disagree on drift kind (e.g. one moved, one modified) — classify at the anchor level, roll up to the decision as the most severe kind present (ordering: Deleted > SemanticallyContradicted

Renamed > Moved > ModifiedInPlace). Concurrent full and incremental scans on the same repo — incremental scan results for files also covered by an in-flight full scan are deduplicated by lamport_ts, not double-emitted.

17.9 Failure Analysis

An assertion-evaluation crash on one decision must not abort the batch scan — per-decision failure boundary, logged as drift.assertion.error, decision excluded from this scan pass and retried next cycle. A scan that never completes (stuck worker) is detected via a scan- duration alert threshold tied to the §4 wall-clock ceiling; operator can inspect per-file scan timing to isolate the stuck file.

17.10 Operational Notes

Emit drift.event.count (tagged by DriftKind), drift.scan.duration_ms (tagged incremental/full), drift.assertion.error counter. Drift inbox persists reviewed/unreviewed state locally so a restart of capture-surface does not re-surface already-triaged events.

18. Phase 6 — Append-Only Decision Log & Replay

18.1 Objectives

Implement oplog.rs and replay.rs: the durable, content-addressed, append-only local store that is the sole writer of decision state (P3), and the replay engine that reconstructs the graph byte-for-byte from it (I3).

18.2 Detailed Implementation Steps

Implement the op-log as a sequence of length-prefixed, content-hash-chained protobuf records (each record's hash includes the previous record's hash, forming a hash chain — Database Internals' WAL chapter applied here, §5) stored in a single append-only file per repo. Implement ReplayCursor advancement: fold the op-log from genesis (or from a checkpoint) into an in-memory decision-graph structure, applying each OpType (Create, Repair, DriftDetected, StatusChange, EdgeAdd) per the lifecycle state table (§8) and op-log merge semantics (Lamport-ordered, P12 — though single-writer locally, the same ordering logic is reused unchanged at Phase 7's multi-writer merge). Implement periodic checkpointing: snapshot the folded graph plus its ReplayCursor every N op-log entries to bound replay time on cold start. Implement the I3 self-check: on every dlcore startup, replay from the last checkpoint and compare the resulting graph_hash against a cached live value; mismatch halts writes and alerts (per I3's Recovery column). Implement dl-cli replay --verify as a standalone command usable in CI (conformance.yml) to catch replay regressions before merge.

18.3 Deliverable

dl-cli replay <repo> reconstructs and prints the full decision graph from the op-log alone, independent of any in-memory state; dl-cli replay --verify exits non-zero on any mismatch.

18.4 Acceptance Criteria

Replay of a 50,000-decision op-log completes in ≤ 10 s from the nearest checkpoint. Zero replay.mismatch events across conformance/fixtures/replay/ (all fixtures from Phases 1–5 replayed and hash-compared, I3). Op-log hash-chain verification detects 100% of single-byte corruption injected by the bit-flip-corruption fixture (I4).

18.5 Conformance Fixtures

conformance/fixtures/replay/full-history-50k/ — purpose: 50,000-decision synthetic history, expected output: replay completes ≤ 10 s, hash matches live graph. conformance/fixtures/ malformed/bit-flip-corruption/ — purpose: single-byte flip injected into a mid-log record, expected output: hash-chain verification detects it, replay halts with a clear corruption report rather than silently accepting a wrong graph. conformance/fixtures/regression/ checkpoint-boundary/ — purpose: op-log entries spanning exactly a checkpoint boundary, expected output: replay from checkpoint N and replay from genesis agree byte-for-byte.

18.6 Pitfalls

Decision-log merge conflicts are not applicable at this single-writer local stage but the checkpoint format must already anticipate Phase 7's multi-writer merge — manifestation (deferred but designed against now): a checkpoint schema that cannot represent concurrent lamport_ts gaps; recovery: design the checkpoint format with per-actor watermarks from Phase 6 onward, not retrofitted at Phase 7. Whitespace/content-hash drift between the op-log's stored anchor and a freshly recomputed one during replay (if normalization logic changes between versions) — manifestation: replay hash mismatch after a dlcore upgrade; root cause: hash chain includes normalized content, and normalization rules changed; debug method: bisect which entry's re-normalization diverges; recovery: version-tag normalization rules, replay must use the version active at write time, per Compatibility & Versioning (§27). Checkpoint corruption during an unclean process exit (partial checkpoint write) — manifestation: startup replay fails to find a valid checkpoint; recovery: checkpoints are written to a temp file and atomically renamed, never partially visible.

18.7 Performance Concerns

Checkpoint interval trades cold-start replay time against checkpoint-write overhead; tune so that worst-case replay-from-checkpoint stays within the acceptance ceiling even at maximum decisions-per-repo (§4). Hash-chain verification is O(n) per startup; parallelize the hash recomputation across chunks while preserving sequential chain-link verification.

18.8 Edge Cases

An op-log file that exists but is empty (zero entries, fresh repo) — replay produces an empty graph, not an error. A checkpoint referencing an op-log offset beyond the current file length (truncated log, e.g. disk-full during a prior write) — treated as checkpoint corruption, fall back to the prior checkpoint. Replay interrupted mid-fold (process killed) — safe to restart from the last completed checkpoint; no partial in-memory graph is ever persisted (I4).

18.9 Failure Analysis

An I3 mismatch (replay diverges from live graph) halts all writes immediately and surfaces an operator alert; forensics is the full op-log itself (immutable, I4) plus the last N checkpoints, enabling offline diagnosis without needing to reproduce the live session. Corruption detected via the hash chain isolates the exact byte offset of the first bad record, bounding the blast radius to entries after that point.

18.10 Operational Notes

Emit replay.duration_ms, replay.mismatch (must stay 0), oplog.checkpoint.count, oplog.size_bytes gauges. dl-cli replay --verify is wired into conformance.yml as a required CI stage from this phase onward — every subsequent phase's fixtures are replay- verified automatically.

20. Phase 8 — Decision-Graph Queries & Forking

20.1 Objectives

Implement typed graph traversal queries over graph_service.rs (P10) and a forking model letting a team branch a decision graph for experimental work without disturbing the shared canonical graph.

20.2 Detailed Implementation Steps

Implement typed traversal queries: "decisions superseding X", "decisions X depends on", "decisions contradicting an active decision", each a bounded graph walk over the edges adjacency table (ADR-07), never free-text search (P10). Implement a "blast radius" query: given a code anchor, find all decisions whose depends-on chain would be affected by retiring it, used by the drift inbox to warn before supersession. Implement forking: fork(repo_id, base_cursor) -> fork_id, creating a new logical repo_id whose op-log begins as a copy-on-read view of the base's op-log up to base_cursor (§11 ReplayCursor), with all subsequent writes isolated to the fork until an explicit merge-back. Implement merge-back: replay the fork's op-log tail against the base's current tip using the same deterministic merge logic as Phase 7 (P12), surfacing conflicts (I10) exactly as team sync does. Implement query result caching keyed by the current ReplayCursor (invalidated automatically on any new op-log append, reusing the salsa-style revision-counter pattern from Phase 1/ADR-08).

20.3 Deliverable

dl-cli graph query --supersedes-of <id>, --depends-on <id>, --blast-radius <anchor>; and dl-cli fork create/merge-back commands operating against a live backend.

20.4 Acceptance Criteria

Typed traversal queries return in ≤ 50 ms p95 at 50,000 decisions (backed by an index on the edges table's from/to columns). Fork creation completes in ≤ 500 ms regardless of base graph size (copy-on-read, not copy-on-write). Merge-back on the conformance/fixtures/fork/ divergent-edit fixture produces the same conflict-marker behavior as Phase 7's sync merge (I10), verified byte-for-byte against Phase 7's expected output shape.

20.5 Conformance Fixtures

conformance/fixtures/fork/clean-merge/ — purpose: fork with non-overlapping edits, expected output: merge-back succeeds with zero conflicts. conformance/fixtures/fork/divergent-edit/ — purpose: fork and base both modify the same decision field, expected output: conflict marker recorded, no silent overwrite (I10). conformance/fixtures/regression/graph-query- perf/ — purpose: 50,000-decision graph, 1,000 traversal queries, expected output: p95 ≤ 50 ms.

20.6 Pitfalls

Blast-radius queries under-reporting affected decisions due to a missing transitive closure step — manifestation: retiring a decision silently breaks a two-hop depends-on chain; root cause: query only follows direct edges, not transitive; debug method: construct a three-decision chain fixture and verify all are reported; recovery: blast-radius must do a bounded transitive closure, depth-capped to avoid pathological graphs. Fork copy-on-read leaking base-graph mutations into an already-created fork (isolation violation) — manifestation: a fork sees a decision created in the base after the fork point; root cause: cursor comparison uses wall-clock instead of the frozen base_cursor offset; recovery: fork reads are always bounded strictly by the frozen cursor, never "latest". Decision-log merge conflicts during merge-back mis-ordered relative to concurrent base-graph writes — recovery: merge-back acquires the same per-decision serialization as Phase 7's ingestion path, not a separate ad hoc path.

20.7 Performance Concerns

Adjacency-table traversal must use proper indexes (edges(from), edges(to)) to hit the 50 ms p95 target; unindexed scans at 50,000 decisions would blow the budget by an order of magnitude. Fork-count growth (many experimental forks) must not degrade base-graph query performance — forks are logically separate repo_ids, so base queries never scan fork data.

20.8 Edge Cases

A blast-radius query on a decision with a cyclic depends-on chain (should be prevented at write time, but query must not infinite-loop if one slips through) — bounded-depth traversal with cycle detection as defense in depth. A fork created from a base_cursor that has since been garbage-collected (if checkpoint pruning is ever enabled) — reject fork creation with a clear "cursor too old" error rather than silently forking from a different point. Merge-back attempted twice on the same fork — idempotent by tracking a merge-back watermark per fork.

20.9 Failure Analysis

A stuck transitive-closure query (pathological graph shape) is bounded by the depth cap and a query timeout, surfaced to the caller rather than hanging the graph service. A failed merge- back leaves the fork's own op-log untouched (P3) — safe to retry merge-back after fixing the conflict, no data loss on the fork side.

20.10 Operational Notes

Emit graph.query.latency_ms (tagged by query type), fork.count gauge, fork.merge_back. conflict_count. dl-cli graph explain <query> prints the query plan (which indexes used) for operator debugging of slow traversals.

21. Phase 9 — Multi-Language Parser Support

21.1 Objectives

Extend ast-indexer and anchor-resolver beyond the Rust/TypeScript dogfooding set (Phase 1) to a third and fourth language, proving the anchor model's abstraction boundary holds without touching anchor.rs or drift.rs (§2 mastery goal, §8 model).

21.2 Detailed Implementation Steps

Add tree-sitter grammars for Python and Go (ADR-14 lockfile extended), each behind the same ast_index.rs interface established in Phase 1 — no changes to the Anchor/AstPath/ SymbolRef types in §11, only new per-language symbol_ref extraction rules (document-symbol equivalent) and per-language assertion query grammars. Implement a language-registry abstraction (LanguageId -> GrammarHandle) so dl-cli index auto-detects language by file extension plus a content sniff for ambiguous extensions. Extend the SCIP-inspired symbol scheme (Sourcegraph SCIP, §5) so symbol_ref.qualified_name encoding stays consistent across languages (package/module + descriptor path), enabling cross-language depends-on edges in degenerate polyglot-repo cases. Run the full Phase 2 conformance suite (rename-refactor- corpus, ambiguous-cases) against newly generated Python and Go fixture corpora to prove the resolver's precedence logic is language-agnostic.

21.3 Deliverable

dl-cli index <repo> correctly indexes a four-language polyglot repository (Rust, TS, Python, Go) in one pass; anchor resolution and drift detection work identically across all four without any dlcore core-crate changes beyond the language-registry addition.

21.4 Acceptance Criteria

Anchor-survival rate on new conformance/fixtures/rename-refactor-corpus/python-* and go-* fixtures matches the Rust/TS rates from Phase 4 within 3 percentage points. Zero changes required to anchor.rs, drift.rs, or the §11 core type signatures (verified via a CI diff-check against a pinned pre-Phase-9 snapshot of those files). Cold index build time for a mixed four-language 1M-LOC corpus stays within the §4 90 s ceiling.

21.5 Conformance Fixtures

conformance/fixtures/rename-refactor-corpus/python-rename-only/, .../go-rename-only/ — purpose: language-specific rename fixtures, expected output: parity with Rust/TS resolve rates. conformance/fixtures/parse/language-detection-ambiguous/ — purpose: files with ambiguous extensions (e.g. .h shared by C-family), expected output: correct language detected via content sniff, or explicit "undetectable" flag rather than a silent wrong-grammar parse. conformance/fixtures/regression/core-types-unchanged/ — purpose: CI diff-check fixture, expected output: anchor.rs/drift.rs byte-identical to the pinned pre-Phase-9 snapshot.

21.6 Pitfalls

Whitespace-significant languages (Python) breaking the whitespace-normalization assumption baked into content_hash computation since Phase 2 — manifestation: Python anchors flag spurious drift on pure reformatting when indentation itself is semantically meaningful; root cause: normalization logic treats all whitespace as cosmetic; recovery: per-language normalization policy — Python's content-hash normalization preserves indentation structure while still collapsing trailing whitespace. Generated-code churn in Go (common code- generation idioms, e.g. protobuf-generated .pb.go files) causing mass anchor orphaning — recovery: same generated-path exclusion mechanism as Phases 4/5, extended with Go-specific generated-file header detection (// Code generated ... DO NOT EDIT. convention). Monorepo path collisions across language boundaries (a utils module name existing in both the Python and Go trees) — recovery: symbol_ref.qualified_name always includes the language-scoped module root, never a bare module name (SCIP lesson applied, §5).

21.7 Performance Concerns

Adding grammars increases parser-pool memory footprint; verify the 900 MB/1M-LOC ceiling (§4) still holds for a mixed-language corpus by measuring per-language AST-node byte cost and re-validating the working-set eviction policy from Phase 1.

21.8 Edge Cases

A file matching two languages' extensions under different build configurations (rare polyglot build systems) — language registry requires an explicit per-directory override config rather than guessing. A grammar with no external scanner support for a construct used by the fixture corpus (grammar coverage gap) — degrade that specific construct to a fuzzy_window-tier anchor rather than failing the whole file's index. A repo mixing four languages in one file (e.g. embedded SQL strings) — out of scope for Phase 9, anchors only track the host language's AST.

21.9 Failure Analysis

A grammar-specific crash is contained per-language via the same per-file panic boundary as Phase 1, now also tagged by language_id in telemetry so a systemic issue with one grammar is distinguishable from a general indexer regression.

21.10 Operational Notes

Emit parse.duration_ms and anchor.resolve.latency_ms now tagged by language_id in addition to prior dimensions. docs/adr/ gains a per-language grammar-version changelog entry whenever ADR-14's lockfile is updated.

22. Phase 10 — Compliance Export & Audit

22.1 Objectives

Implement compliance-exporter: produce an independently verifiable ExportBundle (P11, I14) in an SPDX/CycloneDX-adjacent shape from a bounded ReplayCursor slice of the graph.

22.2 Detailed Implementation Steps

Define the export bundle schema (JSON Schema 2020-12, §5) embedding: the bounding ReplayCursor, the full set of Decision records in scope, AnchorProvenance for every anchor (resolved-at timestamp, confidence tier — never raw source unless content_sync_ enabled, per P6 extended to export), and a bundle_hash computed over the canonical serialization of all of the above (blake3, ADR-06, consistent with the rest of the system). Implement dl-cli export --cursor <id> --format spdx|cyclonedx generating the bundle. Implement independent re-verification: given only an ExportBundle and read access to the same op-log, dl-cli export --verify <bundle> re-derives the graph at the embedded cursor and compares bundle_hash (I14) — this must work without trusting the exporting team's tooling, only the shared op-log and the hash function. Implement audit-scoped queries: export bundles can be scoped to a subset of decisions (e.g. only those tagged compliance-relevant) while still embedding a cursor sufficient to prove no cherry-picking occurred (the cursor bounds the full graph state, not just the exported subset — an auditor can request the full-graph replay at the same cursor to cross-check). Wire the SPDX/CycloneDX-adjacent field mapping: decision id/title/status map to SPDX relationship/annotation-equivalent fields; anchor provenance maps to a component-evidence-equivalent structure.

22.3 Deliverable

dl-cli export produces a bundle file; dl-cli export --verify independently confirms it against the op-log without any other tooling.

22.4 Acceptance Criteria

Export of 10,000 decisions completes in ≤ 15 s. Re-verification (--verify) succeeds on 100% of the conformance/fixtures/export/valid-bundles set and fails cleanly (non-zero exit, clear diagnostic) on 100% of conformance/fixtures/export/tampered-bundles (I14). Bundle JSON validates against the published JSON Schema with zero schema-validation errors.

22.5 Conformance Fixtures

conformance/fixtures/export/valid-bundles/full-graph-10k/ — purpose: 10,000-decision export, expected output: verify succeeds, ≤ 15 s generation. conformance/fixtures/export/tampered- bundles/hash-mismatch/ — purpose: bundle with a single field altered post-export, expected output: verify fails with ExportError::CursorMismatch or a bundle-hash mismatch, never a false-positive pass. conformance/fixtures/export/scoped-subset/ — purpose: export scoped to compliance-relevant tag only, expected output: bundle is valid and the embedded cursor still permits a full-graph cross-check replay.

22.6 Pitfalls

Decision-log merge conflicts unresolved at export time silently omitted from the bundle instead of being surfaced — manifestation: an auditor sees a clean graph that hides an unresolved conflict; root cause: export query filters out conflict-marker rows by default; recovery: conflict markers are always included in export unless explicitly excluded with a logged justification. Whitespace/content-hash normalization version mismatch between export time and the original capture time (same class of issue as Phase 6's replay pitfall) — recovery: bundle embeds the normalization-rule version alongside the cursor, verify uses the matching version. Generated-code-churn noise inflating the exported anchor-provenance list with low-value orphan cycles — recovery: export defaults to the current resolved state only, historical churn is available via --include-history as an explicit opt-in, not the default.

22.7 Performance Concerns

Export generation is dominated by replay cost (Phase 6) plus serialization; reuse Phase 6's checkpoint-accelerated replay rather than folding from genesis for every export request.

22.8 Edge Cases

An export requested at a cursor that predates the repo's earliest checkpoint (very old cursor) — falls back to full genesis replay, may exceed the 15 s target for very old cursors, documented as an accepted degraded case rather than a silent failure. A bundle format version mismatch between exporter and verifier (cross-version audit, e.g. auditor uses a newer CLI) — verifier must reject with a clear version-incompatibility error, never attempt a best-effort parse. An empty scoped export (zero decisions match the tag filter) — produces a valid, empty bundle, not an error.

22.9 Failure Analysis

A verification failure's forensics is the op-log itself (immutable) plus the bundle's embedded cursor and normalization-version tag, enabling an independent third party to pinpoint exactly which field diverges without needing help from the exporting team.

22.10 Operational Notes

Emit export.duration_ms, export.verify.result (tagged pass/fail/version-mismatch). docs/runbooks/audit-response.md documents the operator procedure for handling an external audit request end to end using dl-cli export.

23. Phase 11 — Conformance & Performance Hardening

23.1 Objectives

Close the loop: run the full conformance and fuzz suite across every phase's fixtures at scale, validate every §4 constraint under load, and gate all Performance Engineering targets (M1…) in CI. This is the terminal phase — no new user-facing capability, only hardening.

23.2 Detailed Implementation Steps

Assemble benchmarks/ criterion suites covering every latency/throughput target in §4: cold/warm index build, anchor resolution p50/p95/p99, incremental reparse, drift-scan wall clock, sync payload size, backend QPS. Wire .github/workflows/fuzz.yml to run cargo-fuzz (ADR-20) continuously against the anchor parser and AST-path matcher, feeding any crash corpus back into conformance/fixtures/malformed/. Run the full 20M-LOC scale test (§4 ceiling) end to end: cold index, full drift scan, full export, measuring against every row of the Performance Engineering targets table (§30). Implement chaos-style fault injection (Testing & Verification Strategy, §28) against the team-backend: simulated Postgres failover, simulated sync-client network partition, simulated clock skew — verifying I3, I9, I10 hold under each. Run the full Threat Model (§24) as an active red-team pass: attempt each threat's vector against a staging deployment, confirm the listed mitigation and detection fire. Freeze grammar/parser versions (ADR-14) and API/wire schema versions (Compatibility & Versioning, §27) as the v1.0 baseline.

23.3 Deliverable

A tagged v1.0 release: every benchmark in benchmarks/ passing its §4/§30 target, every conformance fixture from Phases 0–10 green, zero open fuzz-discovered crashes, a completed red-team pass report in docs/threat-model/.

23.4 Acceptance Criteria

100% of Performance Engineering targets (§30, M1–M12) met at the 20M-LOC scale test. Zero unresolved fuzz crashes after a 72-hour continuous cargo-fuzz run (ADR-20). 100% of conformance/ fixtures across all prior phases pass in a single CI run. All 10 Threat Model rows (§24) confirmed mitigated in the red-team pass with a signed-off report.

23.5 Conformance Fixtures

conformance/fixtures/regression/full-scale-20m-loc/ — purpose: the terminal scale validation corpus, expected output: every §4 ceiling respected. conformance/fixtures/ regression/chaos-postgres-failover/ — purpose: simulated mid-write Postgres failover, expected output: I3/I9 hold post-recovery, no silent data loss. conformance/fixtures/ regression/fuzz-crash-corpus/ — purpose: accumulated crash-triggering inputs discovered during the 72-hour fuzz run, expected output: all now handled without crashing (added as permanent regression fixtures).

23.6 Pitfalls

Performance targets met in isolation but violated under combined load (e.g. drift-scan running concurrently with sync ingestion) — manifestation: p99 anchor resolution regresses only under combined load; root cause: benchmarks measured subsystems independently; debug method: run the combined-load benchmarks/ profile explicitly; recovery: add a combined-load gate to CI, not just per-subsystem gates. Fuzz-discovered crashes in rarely-exercised malformed-input paths (e.g. a specific Unicode normalization edge case in fuzzy_window matching) — recovery: every fuzz crash becomes a permanent conformance fixture (P8-style discipline — never fixed without a regression test). Grammar-version freeze (ADR-14) breaking a repo still on an older grammar snapshot — recovery: Compatibility & Versioning (§27) documents the exact re-index migration path required.

23.7 Performance Concerns

Combined-load benchmarking must simulate realistic concurrency ratios (e.g. drift-scan frequency vs sync-ingestion rate) rather than worst-case-everything-at-once, which would over-provision beyond what §4 actually requires.

23.8 Edge Cases

A benchmark that passes on CI hardware but would fail on a documented minimum-spec developer machine — benchmarks must be normalized against a documented reference hardware profile, not just "whatever CI happens to run on". A fuzz target that never terminates (infinite loop input) — bounded by a fuzz-harness timeout per input, logged as a distinct crash class (hang) from a panic.

23.9 Failure Analysis

Any Performance Engineering target regression discovered in this phase blocks the v1.0 tag until resolved — no exceptions, since this phase's entire purpose is closing that gate. A red-team-discovered threat-model gap is treated as a release blocker, tracked in docs/ threat-model/ with a remediation entry before v1.0.

23.10 Operational Notes

benchmarks/ results are archived per release in docs/performance/ for historical trend comparison. The v1.0 tag freezes ADR-14's grammar lockfile and the wire schema version referenced throughout Compatibility & Versioning (§27); any further language or schema change is a v1.1+ concern outside this blueprint's scope.

Structured logging fields — fixed set: timestamp, level, span_id, trace_id, repo_id_hash, actor_id_hash, event_type, outcome. Never raw file content or unhashed identifiers (I12) — enforced by the same redaction stage as telemetry.

Dashboards — "Anchor Health" (resolve-latency percentiles, ambiguous rate), "Drift Volume" (event count by DriftKind), "Sync & Backend" (QPS, queue depth, conflict rate), "Replay Integrity" (mismatch counter, checkpoint cadence), "Compliance Export" (reproducibility-check pass rate).

Alerting philosophy — alert on symptom (a §4 ceiling breached or an invariant violated), never on a raw internal metric alone; every alert links to a named runbook (below); page only for must-be-zero counters (I2, I3, I4, I8, I9, I10, I13, I14); ticket, non-paging, for approaching-ceiling conditions.

SLOs — derived from §4: p99 anchor resolution ≤ 60 ms (error budget 0.1% of requests may exceed; alert at 5% of budget burned within 1 h); drift-scan wall clock ≤ 120 s full / ≤ 2 s incremental; backend availability 99.9% monthly (RTO ≤ 30 min, RPO ≤ 5 min, §4).

Incident response — SEV-1 (any must-be-0 counter non-zero, tenant-isolation breach, replay mismatch): page immediately, halt writes per the invariant's Recovery column. SEV-2 (SLO burn-rate breach, e.g. repeated drift-scan ceiling overruns): ticket, next-business-day. SEV-3 (single fixture flake, non-blocking): tracked, no page. Every SEV-1 requires a postmortem filed under docs/failure-analysis/.

Named runbooks (docs/runbooks/): backend-restore.md (§19.10, Postgres WAL restore against RTO/RPO); replay-mismatch.md (FM-2 triage, forced replay-from-checkpoint); oplog-corruption.md (FM-3, I4 hash-chain break isolation); tenant-isolation-incident.md (FM-5/T4 breach containment); grammar-version-rollback.md (FM-6, ADR-14 pin revert plus full re-index); sync-backlog-critical.md (FM-4 outage-drain procedure); fork-merge-conflict-triage.md (FM-8 conflict-marker resolution walkthrough).

Backup/restore — Postgres: continuous WAL archiving (RPO ≤ 5 min), nightly base backup, quarterly restore drill against backend-restore.md. Object storage: versioned bucket, cross-region replication for export bundles. Local op-log: user-owned; dl-cli export --local-backup produces a portable snapshot.

Deployment topology — local (a, §1): single process, no topology. Self-hosted (b, §1): team-backend behind a load balancer, N stateless api_gateway.rs replicas, one primary + read-replica Postgres, S3-compatible object store, entirely inside the team's network.

Canary/rolling-upgrade/rollback/migration — releases canary to 5% of tenants for 30 min, promote on zero SLO-burn increase; rolling upgrade replaces API-gateway replicas one at a time (stateless, zero downtime); rollback redeploys the prior signed image (§29) plus, if a migration ran, its paired down-migration; Postgres schema migrations are additive-first (§27), backward-compatible for one release before a breaking migration ships.

27. Compatibility & Versioning

Decision-log format versioning. Every op-log record carries a schema-version tag (u16); replay.rs dispatches per-version decode logic; a version bump is additive-fields-only until a documented major bump. The Phase 6 checkpoint format anticipates multi-writer per-actor watermarks from day one (§18.6) specifically so Phase 7 never retrofits it.

Anchor-scheme evolution. AnchorKind (§11) is a closed enum; adding a new precedence tier requires an Anchor schema-version bump plus a migration that re-resolves all existing anchors at the new tier boundary — old anchors are never silently reinterpreted under a new scheme.

Tree-sitter grammar version pinning + re-index policy. ADR-14's lockfile pins exact grammar commit hashes. A grammar bump ships as a two-step release: (1) shadow-mode dl-cli reindex --full --language X behind a flag, comparing anchor-survival rate against the old grammar on the full conformance corpus; (2) promote only after regression ≤ 3 percentage points (mirrors the §21.4 acceptance bar).

Extension↔backend protocol versioning. LSP custom methods (decisionLayer/*, ADR-03) and the gRPC SyncOp wire schema (ADR-09/ADR-10) version independently; lsp-bridge negotiates a protocol version at initialize; SyncOp carries protocol_version, and the backend rejects with an explicit upgrade-required error rather than partially decoding and guessing.

API stability. team-backend's gRPC API is additive-only within a major version. A breaking change (removed field, changed semantics) requires a new major version served side-by-side for one deprecation window.

Migration tooling. services/backend/migrations/ (forward-only, paired down-migration for rollback within the deprecation window); dl-cli migrate-anchors for local anchor-scheme bumps; dl-cli migrate-oplog for op-log schema bumps — both idempotent, safe to re-run.

Deprecation policy. A deprecated field/method stays functional ≥ 2 minor releases, removed only at the next major, announced in CHANGELOG.md; backend responses using a deprecated field carry a deprecation-warning header.

SemVer policy. dlcore/dl-cli/team-backend each carry independent SemVer (ADR-01, Semantic Versioning 2.0.0, §5). MAJOR: any Core Schema (§11) breaking change or a removed invariant. MINOR: new AnchorKind/DriftKind/EdgeKind variants or new phase capability. PATCH: bugfixes, no schema change.

Rolling-upgrade guarantees. team-backend supports API version N and N-1 concurrently during any rolling-upgrade window (§26); a sync-client on the older wire version keeps operating unaffected until it upgrades.

28. Testing & Verification Strategy

  • Unit — per-module (ast_index, anchor, drift, oplog, replay, sync-client, graph_service) covering pure boundaries: precedence ordering (P4), DriftKind classification rules. cargo test per crate, gated in ci.yml.

  • Integration — cross-crate flow capture → repair → drift → oplog → replay, exercised against conformance/fixtures/smoke/* (§12.5) and drift-taxonomy fixtures (§17.5); asserts I1, I13.

  • Property (proptest, ADR-15) — anchor round-trip stability: generate random AST-preserving and AST-breaking edit sequences (rename, extract-method, reorder-params) over a seed file, assert the resolver always returns a ResolutionResult consistent with precedence (I5), never a silent wrong-tier match; tied to conformance/fixtures/rename-refactor-corpus/* (§14.5, §21.5).

  • Differential — cross-check drift/anchor classification against two independent oracles on the same edit corpus: git log --follow (line/file provenance ground truth) and a standalone GumTree run (ADR-19, §5). Divergence from either oracle logs a conformance/fixtures/ regression/differential-* case for review, not an automatic fail (the oracles capture different semantics), but every divergence is triaged.

  • Fuzzing (ADR-20, cargo-fuzz) — targets: the anchor parser (malformed Anchor wire records), the AST-path matcher (adversarial ASTs), and op-log record decoding (I4's hash chain must reject malformed records, never panic). Crash corpus feeds conformance/fixtures/ malformed/* permanently (§18.5, §23.5).

  • Chaos — simulated Postgres failover, sync-client network partition, injected clock skew in lamport_ts generation (§23.2); asserts I3, I9, I10 hold post-recovery against the staging docker-compose topology (§26).

  • Deterministic replay — dl-cli replay --verify (§18) runs in CI on every conformance fixture and nightly against the full 50,000-decision corpus (§18.4); the binding proof of I3.

  • Soak — the 72-hour continuous fuzz run (§23.4) plus a multi-day sync-client/backend soak at realistic edit cadence (§4 storage-growth ceiling), catching slow leaks against the dlcore memory ceiling (§4) and queue-depth creep (FM-4).

  • Fault injection — bit-flip corruption (conformance/fixtures/malformed/bit-flip- corruption, §18.5, I4), truncated op-log, partial checkpoint write (§18.8), oversized SyncOp (SyncError::PayloadTooLarge, §19.8).

  • Conformance — the full conformance/fixtures/ tree (§10) is the executable spec; conformance.yml runs it on every push; each phase's N.5 fixtures are permanent regression tests, added to, never deleted.

  • Performance-regression gating — every Performance Engineering target (§30, M1–M14) is a benchmarks/ criterion bench wired into CI, failing on ≥ 10% p95 regression versus the last tagged release; Phase 11 (§23) is the terminal full-scale gate.

31. Scalability Analysis

What stays constant. Anchor-resolution latency per file — O(depth of AST) per resolution: O(log n) symbol lookup via the document-symbol tree index, O(d) ast_path match where d = tree depth — independent of total repo size. Per-file incremental reparse cost, bounded by the edited byte range (ADR-08), not file size.

What grows. Cold index build time — O(LOC), linear, parallelizable across files (M1/M2). Drift-scan full wall clock — O(decisions × anchors-per-decision), the dominant scaling axis at the 50,000-decision ceiling (§4, M8). Op-log size — O(total historical ops), monotonic, bounded practically by the ≤ 5 MB/day/repo storage-growth ceiling (§4). Backend Postgres row count — O(decisions + anchors + edges).

Named bottlenecks, in order. (1) Drift-scan full wall clock at decision-count scale (M8, dominant at 50k decisions) — mitigated primarily by incremental mode (M9). (2) Cold index build at LOC scale (M1/M2) — mitigated by 4-way parallel parse. (3) Postgres connection/query throughput at tenant-count scale (M11) — mitigated by connection pooling (§19.7). (4) Graph traversal latency at edge-count scale (M12) — mitigated by adjacency-table indexing (ADR-07).

Horizontal scaling. team-backend API-gateway replicas scale horizontally (stateless, §26). Postgres scales via read replicas for query-heavy traversal load, single primary for writes — ADR-07 chose Postgres precisely because adjacency-table queries don't need a distributed graph engine at this scale (§9).

Vertical scaling. Single-repo dlcore indexing scales vertically with core count (parallel parse, M2) and RAM (§4, 900 MB/1M-LOC ceiling) — no horizontal story for one repo's local index, since anchor resolution must stay single-process for salsa-style memoization (ADR-08) to hold.

Sharding by repo. team-backend shards naturally by repo_id/tenant_id — already the isolation boundary (T4) — because no cross-repo query is ever required by the domain model (§8), making repo-level sharding trivial versus a system needing cross-shard joins.

Coordination overhead. Op-log merge (P12) is the only cross-actor coordination point, and it requires zero distributed lock or consensus protocol — determinism comes from the Lamport- ordered total order itself (ADR-22), not from serialization at write time.

Practical ceiling and levers beyond it. 20M LOC / 200,000 files / 50,000 decisions / 500 concurrent tenants (§4), validated at Phase 11 (§23.4). Beyond it, drift-scan full-mode wall clock is the first constraint to breach (linear in decisions); the lever is deeper reliance on incremental mode plus decision-count partitioning (e.g. per-module drift-scan scoping) — not yet built, a natural post-v1.0 candidate (§37).

32. Mental Models & First Principles

MM1 — An anchor is a hypothesis about identity, and every edit is an experiment that can falsify it. Predicts: any edit can invalidate an anchor at any precedence tier, so resolution must always re-verify, never trust a cache. Bug class without it: caching a resolved anchor across an edit event and silently serving a stale binding. Resolves in: P1 (§6), I2 (§7).

MM2 — Precedence order is a total order, not a voting system. Predicts: two candidate matches are never blended or scored against each other outside the fixed tier order. Bug class without it: nondeterministic resolution when a lower-tier match happens to look more confident than a higher-tier one. Resolves in: P4 (§6), I5 (§7).

MM3 — Append-only history turns "what happened" into a pure function of the log, never of memory. Predicts: any two processes folding the same log converge to the same state, with no reliance on runtime side-effect ordering. Bug class without it: a decision graph silently diverging between two machines with no way to detect it. Resolves in: P3 (§6), I3 (§7), Phase 6 (§18).

MM4 — Drift is a detector's opinion, not an autopilot's correction. Predicts: the system's job stops at classification; resolution is always a human action with an audit trail. Bug class without it: an auto-"fix" that silently erases the original decision's intent, making history untrustworthy. Resolves in: P2 (§6), I6 (§7).

MM5 — A decision graph's edges are a controlled vocabulary, not free text. Predicts: every relationship between decisions is one of exactly three typed kinds, enabling typed traversal queries instead of text search. Bug class without it: an unqueryable pile of prose cross-references that can't answer "what depends on X" at scale. Resolves in: P10 (§6), Phase 8 (§20).

MM6 — Logical time, not wall-clock time, is what makes merges deterministic. Predicts: two replicas receiving the same ops in different physical arrival order still converge, because ordering is a property of the Lamport clock plus actor-id tie-break, not of arrival time. Bug class without it: split-brain graphs that "usually" converge but occasionally don't, reproducing only under specific race conditions. Resolves in: P12 (§6), I9/I10 (§7), Phase 7 (§19).

MM7 — A compliance export is only as trustworthy as its ability to be independently re-derived. Predicts: an auditor who does not trust the exporting team can still verify the bundle by replaying the same cursor and comparing hashes. Bug class without it: an export format that is internally consistent but unfalsifiable by an outside party, making "compliant" a matter of trust rather than proof. Resolves in: P11 (§6), I14 (§7), Phase 10 (§22).

MM8 — Incremental computation is a memoization discipline, not a performance afterthought. Predicts: the system's entire interactive-latency budget (§4) depends on never recomputing what a revision-stamped input hasn't invalidated, architected in from Phase 1, not bolted on later. Bug class without it: a system fast on first index and unusably slow by the hundredth keystroke because every event triggers full recomputation. Resolves in: P8 (§6), ADR-08 (§9), Phase 1 (§13).

It wins wherever the goal is catching a bug class before merge at massive review volume, not tracking why a choice was made and whether it still holds.

34. Back-of-Envelope Capacity Model

1. Index RAM (LOC × AST nodes/LOC × bytes/node). ~8 AST nodes/LOC (typical tree-sitter coverage of statements + expressions + identifiers) × ~96 bytes/node (node-type tag + byte-range + child-list pointers + salsa memoization wrapper) = 768 bytes/LOC × 1,000,000 LOC = 768 MB, plus ~130 MB symbol-table/anchor overhead at scale ≈ 900 MB — matches the §4 dlcore ceiling exactly, confirming the ceiling is a derived number, not an assertion.

2. Drift-scan wall clock (decisions × anchors/decision × resolve-ms ÷ parallelism). 50,000 decisions × 32 anchors/decision (§4 typical) = 1,600,000 resolutions × 3 ms p50 (§4) = 4,800,000 ms = 4,800 s single-threaded. To hit the §4 120 s full-scan ceiling requires ≥ 40-way effective parallelism (4,800 ÷ 120 = 40) — consistent with a worker pool bounded by available cores (§17.7) at typical 32–64-core scan hosts, plus most anchors hitting the p50 cache-hit path rather than worst-case p99.

3. Incremental reparse budget (edited bytes ÷ tree-sitter throughput). §4 caps incremental reparse at 8 ms p95 for files ≤ 5,000 LOC. tree-sitter's incremental-edit throughput is order ~1,000,000 bytes/sec (§5 reference implementation). A typical keystroke-batch edit spans ≤ 200 bytes: 200 ÷ 1,000,000 = 0.2 ms raw parse time, leaving ~7.8 ms of the 8 ms budget for anchor re-resolution and I/O — the target is dominated by resolution, not reparse.

4. Sync bandwidth (edits/day × bytes/op). §4's ≤ 5 MB/day/repo growth is driven by 20 decisions/week ÷ 7 ≈ 2.9 decisions/day, each producing ~3–5 op-log entries (create + repair + status-change average, §8 OpType) ≈ 12 ops/day, batched (not sent individually) into 1–2 daily SyncOp batches under the ≤ 64 KB median (§4) ≈ 20–40 KB/day/repo wire bandwidth — well under the 5 MB/day ceiling, which also covers at-rest anchor/content overhead, not wire bytes alone.

5. Backend storage (decisions × log records × bytes × retention). 50,000 decisions/tenant × ~5 op-log records/decision lifetime average (create, 1–2 repairs, drift-detected, status-change) × ~300 bytes/record (protobuf SyncOp with anchor + metadata, ADR-09) = 75,000,000 bytes ≈ 75 MB/tenant baseline × 500 concurrent tenants (§4 ceiling) ≈ 37.5 GB aggregate Postgres row storage at full scale — within a single primary + read-replica topology (§26).

6. Cold index build time (parallel efficiency). §4: 90 s single-core / 25 s at 4-way parallel for 1M LOC. 90 ÷ 25 = 3.6× speedup on 4 cores = 90% parallel efficiency, consistent with an embarrassingly-parallel per-file parse workload under Amdahl's law with a small sequential fraction (cross-file symbol-table merge, single-threaded by Phase 1's design).

7. Extension memory composition. §4 caps extension memory at 350 MB. WASM dlcore for a typical open workspace (~50k LOC active) scales to ~45 MB at the 900 MB/1M-LOC ratio (item 1), leaving ~305 MB headroom for the Node/V8 extension-host baseline (~100–150 MB) plus UI state (decisionEditor/driftInbox buffers) — the ceiling is dominated by host baseline, not the WASM core.

8. Anchor storage amplification. 256-anchor hard cap (§4) × ~120 bytes/anchor (Anchor: file_path string + optional SymbolRef + optional AstPath + ContentHash[32 bytes] + optional FuzzyWindow, §11) ≈ 30,720 bytes worst-case per decision — ~8× the typical (32 anchors) footprint, which is the concrete number motivating the typical/cap split in §4 as a capacity-planning signal, not merely a UX limit.

      (no live capture UI; decisions authored via a
       separate manual manifest-edit step)

Winning regime: a heavyweight CI-gate culture wanting zero editor footprint — e.g. a compliance team retrofitting checks onto a legacy codebase where org-wide extension rollout isn't feasible. Real embodying system: the general class of Danger/reviewdog-style CI review bots. Rejected here: capture must happen at decision time, in the editor, next to the code (Sillito et al. 2006, LaToza & Myers 2010, §5) — a CI-only checker only catches drift after the fact, losing the interactive capture UX that makes recording a decision as cheap as a comment (§2, §15).

(c) Comments-as-anchors embedded directly in source.

// @decision: DEC-042 "must not import module X here"
fn some_function() { ... }
        |
   grep/regex scanner extracts @decision comments
   at CI time, checks a simple assertion
        |
   (anchor IS the comment's location; moves with the
    code via git, but only line-level tracking)

Winning regime: tiny codebases or single-file scripts where structured tooling is pure overhead. Real embodying system: the lightweight inline-directive convention generalized (e.g. eslint-disable-next-line-style comments). Rejected here: comments give free co-location but zero structured drift taxonomy, zero graph queries, zero replay/audit trail — and a comment surviving a copy-paste is text-level, not the symbol/AST-level identity (P4) needed to survive a rename-then-refactor sequence (§8) without silently binding to the wrong copy.

(d) LLM semantic-drift judge over diffs instead of AST anchoring.

   git diff (old, new) ---> LLM prompt:
                            "does this diff violate
                             decision DEC-042's intent?"
                                   |
                            LLM judges: yes/no/unsure
                                   |
                     (no deterministic anchor; judgment
                      quality varies by model/prompt version)

Winning regime: judging genuinely semantic/intent-level drift no AST assertion (§8) can express — e.g. "violates our stated preference for composition over inheritance" with no syntactic pattern. Real embodying system: the emerging class of LLM-based code-review assistants; no single citable system does exactly decision-drift judging today. Rejected here: nondeterministic judgments violate I5 and P4's reproducible-classification requirement; an LLM judge cannot be replayed byte-for-byte (I3) months later against a frozen model version, breaking the independently-verifiable compliance-export requirement (P11) this system's audit use case depends on (§22).

38. Glossary

Anchor — the multi-tier binding (symbol ref, AST path, content hash, fuzzy window) tying a decision to concrete code (§8, §11).

Anchor repair — the six-step procedure re-resolving an anchor after an invalidating edit, walking the precedence tiers in order (§8).

Orphaned anchor — an anchor for which no tier resolved a candidate; flagged, never silently dropped (I2).

AST path — a root-relative sequence of node-type + child-index steps identifying a position in a syntax tree independent of byte offset (§11 AstPath).

Symbol identity — binding by qualified name + kind rather than by position; the highest anchor precedence tier (§8).

Content hash — a blake3 digest (ADR-06) of an anchor's enclosing block, whitespace- normalized; third anchor precedence tier.

Drift — detected divergence between a recorded decision and current code state, classified into the five-way DriftKind taxonomy (§8).

Drift taxonomy — Moved, Renamed, ModifiedInPlace, Deleted, SemanticallyContradicted (§11 DriftKind).

Decision graph — the full set of Decision records and their typed DecisionEdges, reconstructed by replay (§8, §11).

Supersedes edge — a typed DecisionEdge marking one decision as replacing another, retiring, never deleting, the prior record (P7).

Replay cursor — (repo_id, op_offset, graph_hash) marking a specific fold position in the op-log; the unit compliance exports are scoped and re-derived by (§11 ReplayCursor).

Incremental reparse — re-parsing only the edited byte range of a file rather than the whole file, bounding reparse latency (P8, ADR-08).

Salsa-style memoization — revision-stamped, dependency-tracked query caching (rust-analyzer salsa, §5) underlying dlcore's incremental computation model (ADR-08).

SCIP — Sourcegraph's symbol/occurrence index format; source of the qualified-name scheme Decision Layer's symbol_ref encoding borrows (§5, §21).

Compliance bundle — the ExportBundle produced by compliance-exporter: decisions, provenance, replay cursor, bundle hash — independently re-derivable (P11, §11).

Fuzzy window — the lowest-precedence anchor tier: a text window matched under an edit-distance threshold, last resort before orphaning (§8).

Precedence tier — one of the four ordered anchor-resolution levels (symbol ref → AST path → content hash → fuzzy window), never voted or blended (P4).

Assertion rule — a structured, AST-pattern-based rule attached to a decision that the drift detector evaluates against the resolved anchor's current subtree (§8, §17).

Decision scope — Anchored or RepoGlobal; every decision must declare one explicitly (P5, I1).

Op-log — the append-only, content-hash-chained, length-prefixed sequence of records that is the sole writer of decision state (P3, §18).

Checkpoint — a periodic snapshot of the folded decision graph plus its ReplayCursor, bounding cold-start replay time (§18).

Lamport timestamp — a logical clock value used, with actor id, to totally order op-log entries across writers independent of wall-clock skew (ADR-22, P12).

Actor id — the identifier of the writer (developer or process) that produced an op-log entry or SyncOp, required on every op (I9).

Logical clock — the Lamport-timestamp-plus-actor-id ordering scheme underlying deterministic multi-writer merge (P12).

SyncOp — the wire unit sync-client sends to team-backend: op type, logical clock, actor id, payload (§11).

Tenant isolation — the guarantee that no query or write crosses tenant_id boundaries in team-backend (T4, I8).

Fork — a logical repo_id whose op-log begins as a copy-on-read view of a base graph up to a frozen ReplayCursor, isolated until an explicit merge-back (§20).

Merge-back — replaying a fork's op-log tail against the base's current tip using the same deterministic merge logic as team sync (§20, P12).

Blast-radius query — a bounded transitive-closure traversal finding all decisions a given anchor's retirement would affect via depends-on chains (§20).

Typed traversal query — a graph query over the three fixed EdgeKinds, never free-text search (P10, §20).

Edge kind — Supersedes, DependsOn, Contradicts; the closed set of decision-graph relationship types (§11 EdgeKind).

DriftKind — the closed five-variant enum classifying a drift event (§11).

AnchorKind — the closed enum tagging which precedence tier an anchor last resolved at (§11).

Content-addressed storage — storing/identifying data by the hash of its content rather than a mutable location, underlying both the op-log and object storage (§9 ADR-05/ADR-11).

Hash chain — each op-log record's hash including the prior record's hash, making tampering structurally detectable (I4, §24 T3).

Tree edit distance — the minimum-cost sequence of node operations transforming one AST into another; the theoretical basis for AST-path matching (Falleri et al. 2014, §5).

GumTree matching — the bottom-up/top-down bounded node-matching heuristic Decision Layer's AST-path resolver adapts (ADR-19, §5).

External scanner — a tree-sitter grammar's hand-written scanner for context-sensitive tokens, a source of cross-grammar-version divergence if unpinned (§5, ADR-14).

Grammar version lockfile — the explicit per-language tree-sitter commit-hash pin preventing silent AST-shape drift (ADR-14).

WASM core — dlcore compiled to WebAssembly for portable execution inside the VS Code extension host (ADR-04).

LSP custom method — a decisionLayer/* extension to the Language Server Protocol exposing dlcore operations to any LSP-aware editor (ADR-03, §5).

Backpressure — the bounded-queue-with-backoff discipline preventing unbounded memory growth during backend outages (ADR-23, FM-4).

Bounded queue — the fixed-capacity local queue sync-client uses to hold undelivered SyncOps during an outage (ADR-23).

Canary release — promoting a new team-backend build to a small tenant fraction before a full rolling upgrade (§26).

Rolling upgrade — replacing stateless API-gateway replicas one at a time with zero downtime (§26).

SBOM — Software Bill of Materials; the per-release dependency manifest feeding both release provenance and the compliance-exporter's own audit shape (§29).

Provenance attestation — a SLSA-style signed record of a release artifact's build platform, source commit, and build steps (§29).

SLO — Service Level Objective; the derived latency/availability targets in §26 tracing directly back to §4's constraints.

RTO / RPO — Recovery Time Objective / Recovery Point Objective; the ≤ 30 min / ≤ 5 min team-backend restore targets (§4, §26).

Conformance fixture — a named, permanent input/expected-output pair under conformance/fixtures/, the executable form of this specification (§10, §28).

Differential testing — cross-checking classification output against an independent oracle (git log --follow, GumTree) rather than a hand-written expected value (§28).

Chaos testing — injected infrastructure faults (Postgres failover, network partition, clock skew) verifying invariants hold under failure, not just the happy path (§28).

Soak testing — sustained multi-day execution catching slow leaks and queue-depth creep invisible in short test runs (§28).

Fault injection — deliberately corrupting or truncating inputs (bit-flip, partial write, oversized payload) to verify the system's designed failure path, not just its success path (§28).
