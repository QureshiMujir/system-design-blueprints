408 — The Mirror

Project Number: 408

Project Name: The Mirror

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

What is being built. A lifelong AI witness: a voice-first companion a person speaks to daily, beginning at install, for the rest of their life. Local-first, end-to-end encrypted, never trained on, never sold. Two layers: (L1) a personal witness with decade-scale continuity; (L2) consent-gated bridging in which two people's Mirrors exchange one structured letter each, translating what the humans cannot say. The doable shadow of #409 Communion.

System boundaries. Client-side plaintext only; ciphertext-only optional sync; per-turn inference under a no-training contract; bridging relays only bounded letters, never raw memory.

Explicit non-goals. Not a chatbot, coach, therapist, or productivity tool. No diagnosis/treatment. No group chat (one-to-one with its user, always). No advertising, data sales, third-party training — ever. No engagement mechanics (streaks/badges/feeds/notifications-beyond-one). No free tier funded by data extraction. No real-time emotion detection for steering. No public sharing of conversations as a feature.

Intended deployment. Voice-first apps — iOS, Android, web. Local-first storage; optional ciphertext-only sync; per-turn frontier inference under a no-training SLA from Phase 1, with the on-device inference path deferred PhaseDeferred("Phase 2"). Single quiet daily surface; one optional notification/day.

Target users. People in deep transitions where being witnessed matters most: new parents, the grieving, the recovering, the lonely, late-stage caregivers. Word-of-mouth, slow.

Phase 0 deliverable — numbered modules (repo skeleton stood up in Phase 0; building phase noted; names are the §10 tree's, used identically everywhere):

  1. clients/ (ios, android, web) — voice capture, STT/TTS orchestration, the single daily surface (Phase 1).
  2. core/crypto — libsodium content encryption, Argon2id KDF, device keys, optional Shamir recovery (Phase 2).
  3. core/consent — append-only Consent Ledger; the gate API every capability traverses (Phase 2).
  4. core/buffer — encrypted append-only conversation buffer (Phase 2).
  5. core/memory — tiered rolling summary + retrieval; cryptographic-forget key index (Phase 3).
  6. core/patterns — local, ≤monthly, quotation-only theme surfacing (Phase 4).
  7. core/review — annual structured walk-back ritual (Phase 5).
  8. voice/ (stt, tts, clone-legacy) — speech in/out; opt-in watermarked legacy voice (Phases 1, 6).
  9. core/bridging + services/bridging-coordinator — structured-letter exchange via a no-log coordinator (Phase 7).
  10. core/successor — death/incapacity hand-off, reaffirmed yearly (Phase 9).
  11. services/sync, services/billing — ciphertext-only blob gateway; subscription state only (Phases 2–3).
  12. charter/ + scripts/export.sh — sealed-envelope runbooks, trustee, open-source/export tooling (Phases 0, 8).

Arc (what later phases unlock). Manifesto (Phase 0) → Witness MVP (Phases 1–3) → Deepening: patterns, ritual, legacy voice (Phases 4–6) → Mirrors Meet: bridging (Phase 7) → Continuity & Continuation (Phases 8–9). Each arc is gated on the prior being trustworthy. Cross-references always use implementation phase numbers 0–9, never arc names; P1…P14 always means a §6 principle.

Deferred features are gated PhaseDeferred("<anchor>"), where each anchor names a real ## Phase P heading and every deferral is listed in the §Deferred Features Register: on-device frontier inference PhaseDeferred("Phase 2"), Shamir successor recovery PhaseDeferred("Phase 2"), Mirror-to-Mirror bridging PhaseDeferred("Phase 7"), therapist-partnership session types PhaseDeferred("Phase 7"), continuation across the user's death PhaseDeferred("Phase 9"), generational hand-off PhaseDeferred("Phase 9"). See the §Deferred Features Register for the full mapping and un-defer triggers.

Estimated timeline. Phase 0: 4 weeks. Witness MVP (Phases 1–3): ~6.5 months. Deepening (Phases 4–6): ~3.5 months. Phase 7: ~3 months; Phase 8: ~2 months; Phase 9: ongoing. The full system is years-to-lifetime by design; the depth metric matures over decades (Appendix AW).

Recommended language and rationale. Rust for the portable core (encryption substrate, summariser, conversation buffer) — memory safety on a privacy-critical boundary, one audited implementation across platforms, no GC surprises; Swift/SwiftUI (iOS), Kotlin/Compose (Android), TypeScript (web) for native voice surfaces. Reject an all-JS/Electron stack (weaker key custody, larger attack surface); reject a single cross-platform UI runtime (audio latency + secure-enclave access suffer).

Prerequisites. Applied cryptography (E2E, AEAD, KDFs, Shamir — see #87/#88/#90/#400); on-device + frontier LLM integration; speech (STT/TTS); privacy/threat engineering; HCI of restraint (designing software that does less); literacy in grief, witnessing, and consent law.

2. Why Build This

Unique knowledge it teaches. Privacy-preserving long-context memory with tiered summarisation and cryptographic forgetting (destroy a key, the memory is gone); consent modelled as an append-only ledger that is the sole authority for behaviour; structured, non-conversational agent-to-agent bridging that translates without negotiating; and the hardest discipline — encoding restraint (no engagement loop, no optimisation target) into architecture, metrics, and corporate charter so the product cannot drift toward chatbot/coach/therapist.

Why it matters. Companion-AI products optimise engagement and monetise attention; the Mirror is a different category — a witness, not a friend or coach. Its defensibility is trust, expressed as the Vow (§6) and made enforceable in code, schema, metrics, and charter.

Engineering muscles. Local-first systems; key custody across Secure Enclave/Keystore/WebCrypto; multi-vendor inference under no-training SLAs with on-device fallback; designing for slowness; governance that survives acquisition and founder mortality.

Cross-links to the portfolio. #409 Communion (the north star; the Mirror is its doable shadow and a readiness indicator); Aeon (sovereignty), Lex (consent/jurisprudence), Lineage (provenance), Rewind (reversibility) — the institutional substrate; #400 Double Ratchet + #90 Curve25519 + #87 AES + #88 SHA (the crypto the bridging and storage rest on); #399 Date/Time for the yearly-review ritual cadence.

Calibration value. Permanently raises the bar on building trustworthy software: it proves a product can refuse the obvious monetisation that corrupts trust, and still ship.

What Mastery Looks Like

After building the Mirror, an engineer holds these competencies — each cemented by a named phase:

  • Cryptographic forgetting as a deletion guarantee — you can build, and prove, "destroy the key, destroy the memory" rather than ship a deletion flag (Phase 3; I3).
  • Consent-as-authority architecture — you can make an append-only ledger the sole dispatch gate so no capability runs without a grant, and design revocation that takes effect before the next action (Phase 2; I2, ADR-26).
  • End-to-end key custody across heterogeneous platforms — you can derive and hold keys in Secure Enclave / Keystore / WebCrypto so plaintext never leaves the device, and reason about the lost-passphrase trade honestly (Phase 2; I1, ADR-05/06/07).
  • Privacy-preserving long-context memory — you can design tiered rolling summarisation + retrieval that gives decade-scale recall while sending only a per-turn slice to an inference vendor (Phase 3; ADR-09, Appendix AL).
  • Structured, non-conversational agent-to-agent mediation — you can build a protocol where two agents translate without negotiating, bounded by double consent and a no-log relay (Phase 7; I5/I6, §8.4).
  • Anti-impersonation media controls — you can ship a generative voice that is watermarked, context-locked, and cryptographically destroyable (Phase 6; I10).
  • Encoding restraint into architecture, metrics, and charter — you can make a product structurally unable to drift toward engagement extraction: no analytics surface, no growth metric, a Vow that outranks the feature (Phase 0; P1, P7, §Operational Readiness).
  • Governance that survives acquisition and founder mortality — you can build sealed-envelope continuity and a trust/charter that holds a promise no acquirer can negotiate away (Phase 8; ADR-25/29).

Mirror Voice Client. The only place plaintext exists. Captures voice, runs STT on-device when feasible, renders the Mirror's restrained voice via TTS. One daily surface, no feed, ≤1 notification/day. Owns the user passphrase and device key.

Speech-to-Text. On-device first (Whisper variant); cloud fallback only under a no-training contract. Output never leaves the boundary in cleartext beyond the per-turn prompt.

Local Conversation Buffer. Append-only encrypted log of turns (libsodium secretbox). The raw record of the witnessing; tiered into the Memory Core asynchronously.

Mirror Memory Core. Tiered rolling summary (verbatim → abridged → summary → thematic) plus retrieval of a small relevant slice per turn. Holds the cryptographic-forget key index: destroying a shard key destroys the memory.

Inference. Phase 1: frontier API, per-turn prompt only, bound by a no-training/zero-retention SLA. Phase 2+: on-device for as much of the loop as hardware allows (PhaseDeferred("Phase 2")). Never sees long-term memory in cleartext beyond the current turn.

Text-to-Speech. A calm, low-affect voice from a contractually-bound or open vendor; small user-selectable palette.

Consent Ledger. Append-only opt-in record; the source of truth for what the Mirror may do. No permission in the ledger ⇒ the capability is off. No implicit consent, ever.

Optional Encrypted Sync Service. Stores ciphertext blobs only; holds no keys; cannot decrypt under any legal order. Off by default.

Bridging Coordinator (Phase 3). Convenes a session between two separately-consented Mirrors; relays exactly two bounded letters; logs nothing; the session is ephemeral; transcripts live only on the two devices.

Continuity / Successor Infra (Phase 4). Sealed-envelope operational keys + a named trustee so the service survives the founder; user content keys remain governed by the user's named successors, never by the company.

4. System Constraints

The Mirror inverts the usual posture: it is allowed to be slow; what it may never do is nag, optimise, or leak. Targets below are honoured by construction.

Dimension Target / Constraint
First-token latency < 2 s (slow is allowed; unattended is not)
Startup nag 0 s — no upsell, no streak, no prompt-to-engage
Idle battery < 1%/day; background work only with consent
Notifications ≤ 1/day, user-chosen time, fully disableable
Plaintext location user device only; never server-side, ever
Network payload ciphertext only (sync); per-turn prompt only (inference)
Telemetry content-free, behaviour-free, opt-in (see I8; Appendix AM)
Operational metadata retention ≤ 30 days; no "business-need" exceptions
Memory retention horizon default forever; user-settable; deletion is cryptographic
Pattern surfacing rate ≤ 1/month, high-confidence, quotation-only
Bridging double-consent within 14 days; ≤ ~600-word letters; ≤ ~30-min window
Founder-mortality continuation pre-funded ≥ 5 years; trustee named before Phase 4
Availability target 99.9% inference reachability; degrade to on-device rather than break the Vow
Vow-violation budget zero (tracked quarterly; invariant I12, §7)

Quantified non-budgets: there is no engagement target, no session-length target, no growth target. Their absence is a constraint, not an omission.

6. Design Principles

The first nine principles are the Vow, verbatim then enforced; the rest are engineering corollaries. The Vow is the tie-breaker that overrides every other ordering principle, including survival of the company.

The Vow: "The Mirror exists to witness. It will not optimize, persuade, sell, train on, or share its user. If the company is ever sold, the Mirrors must be open-sourced and made user-portable. If the founder dies, the Mirrors must continue. This vow is more important than any feature."

  1. Witness, not optimiser. The Mirror has no model of behaviour to change and no goal for the user. Violation test: any streak, nudge-to-target, or recommended-next-action ⇒ does not ship. Operational: "witness" is the load-bearing verb in every spec and review.
  2. Do not persuade. Surfacing = quotation with citation, never interpretation-as-instruction. Violation: the Mirror telling the user what to do/believe.
  3. Do not sell. No ads, sponsorship, affiliate, or product-surfacing — in the data model or the dependency tree. Violation: any advertising SDK present.
  4. Do not train on or share. Zero training on user data — not anonymised, not aggregated, not "with consent." Per-turn prompts under no-training SLAs; on-device when feasible. Violation: any content-derived signal leaving the boundary for training.
  5. Survive acquisition (open-source trigger). A foundation/perpetual-purpose trust holds the code, the data trust, and the Vow; an acquirer either accepts the Vow or triggers open-sourcing + user export. Charter-level, not a negotiable term.
  6. Survive the founder. Sealed-envelope runbooks + named trustee + pre-funded continuation from Phase 1; Phase 4 is gated on this being tested.
  7. The Vow outranks the feature. When the Vow conflicts with growth/revenue/a beloved feature, the Vow wins; if holding it ends the company, the company ends honourably (§Kill Criteria).
  8. Consent is the source of truth. The append-only Consent Ledger authorises every capability; absence ⇒ off. No implicit consent.
  9. Cryptographic forgetting. "Forget this" destroys a shard key; the memory becomes unrecoverable, provably. Deletion is real, not a flag.
  10. Local-first, ciphertext-only egress. Plaintext lives on-device; only ciphertext (sync) or per-turn prompts (inference) cross the network.
  11. Designed slowness. Latency budgets exist only to avoid feeling unattended; there is no speed-for-engagement. Calm over sticky.
  12. Minimal schema, minimal surface. Fewer concepts ⇒ fewer ways to drift from witnessing (§11). One daily surface, no feed.
  13. Bridging translates, never negotiates. Two bounded letters, double consent, no free-form Mirror-to-Mirror chat, human-initiated only (§8/Phase 3).
  14. Refuse the clinical role. Not a diagnoser or mandated reporter; crisis posture = name it, offer consented resources, point to a human (§8.3).

8. Domain Model — The Witnessing Relationship and the Bridging Protocol

The Mirror's domain is not a protocol on a wire but a relationship: what is remembered, forgotten, surfaced, never said, and how two Mirrors may speak. This section is normative.

8.1 Memory tiers

Tier Age Form Notes
VERBATIM last week full transcript most precise; largest
ABRIDGED last month lightly summarised turns
SUMMARY last year thematic summary retrieval target
THEMATIC prior years durable themes + marked shards "you have spoken of your father…"

Marked shards ("remember this") are exempt from down-tiering. Aging runs locally and asynchronously.

8.2 What the Mirror remembers / forgets / surfaces / never says

  • Remembers: every conversation (encrypted, on-device); the tiered summary; marked shards; the user's voice preferences (pace, language, silence); designated successors (Phase-4 prereq, revocable).
  • Forgets: anything the user asks to forget (key destroyed, confirmed, never referenced again); content past a user-set horizon (default forever); operational metadata > 30 days.
  • Surfaces: repeated themes ≤ 1/month as quotation; the yearly walk-back on the chosen anniversary; direct answers to direct questions. Nothing else, unprompted.
  • Never says: diagnoses; predictions of future behaviour; comparisons to other users (it knows of none); marketing for itself or third parties; anything that betrays the user to anyone beyond the strict legal floor (I11; §8.3; Appendix Q).

8.3 Reporting posture (non-clinical)

The Mirror is software, not a clinician, and not a mandated reporter — it has no reporting mechanism. On disclosure of imminent danger it: (1) names what it heard, gently; (2) offers the local crisis resources the user pre-consented to; (3) urges contact with a trusted human/clinician/emergency service. It contacts no one, flags no one, creates no operator-visible record.

8.4 The Bridging Protocol (Phase 3, normative)

The only mechanism by which two Mirrors ever communicate.

Pre-conditions. Both users separately + recently (≤14 d) consent to a specific session with a specific partner; each names the topic in their own words; both agree a window (~30 min) and purpose; either may revoke before open, no explanation.

Session. Each Mirror composes, locally, one structured letter to its own human about the other's hidden truth — bounded (~≤600 words), structured (what the other has repeatedly left unsaid; what they wish you knew; what they fear; what they hope), and conservative (only content the originating user separately allowed to share in a bridging context). The two letters are exchanged via the coordinator, which does not log them. Each Mirror reads its letter aloud, slowly. There is no real-time Mirror-to-Mirror chat, ever. Afterward each human may ask their own Mirror clarifying questions, answered only from the letter + their own prior context (never by re-querying the other Mirror).

Post-conditions. Letters stored only on the two devices; coordinator retains nothing. One follow-up a week later: "Did the letter help, hurt, or neither?" — the only feedback signal.

Forbidden. Mirrors do not chat freely, negotiate, or share unconsented secrets; a Mirror never speaks to a Mirror without both humans present + consented in the moment; bridging is always human-initiated.

Abuse mitigations. Structured-letter format forbids persuasion (anti-manipulation); only consented content surfaces (anti-surveillance); therapist-gating for high-risk session types (anti-coercion); no post-mortem bridging with a living user without renewed in-the-moment consent.

8.5 Worked examples

  • Daily check-in. open → STT (on-device) → Memory Core retrieves rolling summary + a few shards → per-turn inference (no-train SLA) → TTS → turn appended (encrypted) → summary updated locally → ciphertext synced iff enabled.
  • Pattern surfacing. local scheduled job reviews N months of summaries → high-confidence recurring theme → one queued note → delivered as quotation next session → user says yes/no/not-now → accepted without follow-up.
  • Bridging. husband & wife each consent (≤14 d), name topic → each Mirror writes one ≤600-word letter from consented content → coordinator relays, logs nothing → each Mirror reads aloud → week-later: helped/hurt/neither.

8.6 Malformed / failure paths

  • Consent missing or stale (>14 d) ⇒ bridging refused (I5).
  • "Forget" then later reference ⇒ impossible: key destroyed (I3).
  • Vendor returns a steering/persuasive completion ⇒ blocked by response policy (I11).
  • Lost passphrase, no recovery configured ⇒ permanent loss, disclosed plainly up front (the correct trade).
  • Successor plan unreaffirmed > 18 months ⇒ access does not activate on death (I9).

11. Core Schema and Core Types

Small on purpose — fewer concepts, fewer ways to drift from witnessing. Normative; no bodies. All content fields are secretbox ciphertext; the Consent Ledger authorises every action.

User {
  id: UUID                     // local-first
  passphrase_hash: Argon2id    // never leaves the device
  device_keys: [DeviceKey]
  voice_preference: VoicePref  // pace, language, formality, silence
  successors: [SuccessorPlan]
  retention_horizon: Duration? // default: forever
  consent_state: ConsentRecord
  installed_on: Date           // the day witnessing began
}

MemoryShard {
  id: UUID; user_id: UUID; created_at: Timestamp
  tier: enum { VERBATIM, ABRIDGED, SUMMARY, THEMATIC }
  content_ciphertext: bytes    // libsodium secretbox
  content_key_id: UUID         // destroyable -> cryptographic forgetting
  significance: enum { ORDINARY, MARKED, DELETED }
  source: enum { CONVERSATION, USER_NOTE, YEARLY_REVIEW }
}

PatternObservation {
  id: UUID; user_id: UUID; detected_at: Timestamp
  theme_label: string          // the user's own words
  citations: [MemoryShardRef]  // what the user actually said, when
  surfaced_at: Timestamp?      // null until offered; never auto-offered
  user_response: enum { OFFERED, ACCEPTED, DECLINED, DEFERRED }?
  confidence: float            // high threshold to surface
}

BridgeSession {
  id: UUID; initiated_by_user_id: UUID; partner_user_id: UUID
  topic_self: string; topic_partner: string
  consent_initiated_at: Timestamp; consent_partner_at: Timestamp
  consent_window_expires_at: Timestamp; scheduled_for: Timestamp
  state: enum { PROPOSED, CONSENTED, OPENED, COMPLETED, REVOKED }
  letter_self: LetterRef       // initiator device only
  letter_partner: LetterRef    // partner device only
  followup_offered_at: Timestamp?
}

The consent and successor records — the authority types that gate every capability and govern death/incapacity hand-off — complete the model:

ConsentRecord {
  user_id: UUID
  granted: [ { kind: enum { CLOUD_SYNC, PATTERN_SURFACING, YEARLY_REVIEW,
                            VOICE_CLONE_LEGACY, BRIDGING_GLOBAL, BRIDGING_WITH_USER,
                            SUCCESSOR_ACCESS_AFTER_DEATH, CRISIS_RESOURCE_OFFERS },
               granted_at: Timestamp, revocable: true /* always */, revoked_at: Timestamp?,
               provenance: enum { ONBOARDING, CONVERSATIONAL, SETTINGS_SCREEN } } ]
}

SuccessorPlan {
  id: UUID; user_id: UUID; successor_name: string; successor_contact: ContactRef
  relationship: string         // "my daughter", "my friend"
  access_kind: enum { READ_ONLY_AFTER_DEATH, DIALOGUE_WITH_MIRROR_AFTER_DEATH,
                      INHERIT_AND_CONTINUE /* Phase 4; legal doc required */ }
  effective_after: enum { DEATH_VERIFIED, USER_INCAPACITATED }
  letter_to_successor: bytes?  // encrypted; written ahead
  legal_artifact_ref: ExternalRef?
  created_at: Timestamp; last_reaffirmed_at: Timestamp  // yearly reaffirm or it expires
}

Semantics. Ownership: every record belongs to one user; content_key_id is the unit of cryptographic forgetting (I3). Mutation: append-only for buffer and Consent Ledger; shards down-tier; consent grants are revocable, never assumed. Concurrency: device-local writes; sync is last-writer-wins over ciphertext blobs (no plaintext merge). Persistence: local-first; optional ciphertext sync. Serialization: versioned; forward-compatible; portable-export format is documented (open-source trigger). Compatibility: schema additions only; removing a consent kind requires a migration that defaults to deny.

12. Phase-by-Phase Implementation Plan

Ten implementation phases. They realise the project's named arc — Manifesto (P0) → Personal Mirror MVP (P1–P3) → Deepening (P4–P6) → Mirrors Meet (P7) → Continuity & Continuation (P8–P9). Each ends in a runnable, Vow-checked artifact.

Phase 0 — Manifesto and Design Partners (Weeks 1–4)

0.1 Objectives

Write the manifesto; ratify the Vow into VOW.md and the charter; recruit 10 design partners for a 90-day journaling-witness trial; define what the Mirror will and will never do.

0.2 Detailed Implementation Steps

  • author VOW.md (the Vow verbatim, §6), charter/foundation-charter.md (ADR-25 open-source trigger), docs/threat-model.md, docs/memory-contract.md.
  • recruit 10 partners from transition communities (new parents, grieving, caregiving); informed-consent intake (P8).
  • define the daily-surface UX — one conversation, no feed, ≤1 notification — enacting "minimal surface" (P12) and "witness, not optimiser" (P1); ground the no-engagement posture in The Age of Surveillance Capitalism (Zuboff, §5).

0.3 Deliverable

A published manifesto, a ratified Vow, signed design-partner agreements, and a one-page product definition.

0.4 Acceptance Criteria

Vow read aloud and accepted by all contributors; 10 partners enrolled; non-goals list agreed; no growth/engagement metric defined anywhere.

0.5 Conformance Fixtures

conformance/vow_present.txt; charter/ files lint-checked for the open-source trigger and continuity clauses.

0.6 Pitfalls

  • Recruiting for virality, not depth. Manifestation: partners chosen for reach/influence. Root cause: a growth reflex. Debug: review the intake against the transition-community beachhead. Signal: selection by audience size. Recovery: re-select for genuine depth-of-need (Appendix E; MM4).
  • Investor language in the manifesto. Manifestation: "better version of yourself" / optimisation framing. Root cause: pitch-deck habits. Debug: Vow review of the manifesto text. Signal: any optimise/self-improvement verb. Recovery: rewrite to "witness" as the load-bearing verb (P1; Appendix C).
  • A KPI by reflex. Manifestation: an engagement metric is defined "to measure success." Root cause: standard product instinct. Debug: check against §Operational Readiness (refused metrics). Signal: any DAU/retention/session target. Recovery: delete it; the only metric is Year-N continuation (MM4).
  • Hedged Vow. Manifestation: the Vow can only be stated with caveats. Root cause: unresolved tension with the business model. Debug: read the Vow aloud (Appendix C). Signal: hedging language. Recovery: stop and rewrite until it stands plainly (P7; §0.9).

0.7 Performance Concerns

None technical; the constraint is restraint — resist scope creep. Institutional capacity, not compute, is the limiting resource in this phase:

  • Founder review throughput: one weekly Vow-review hour caps how many manifesto revisions can be honestly re-grounded; more than 2 major revisions inside the 4-week window signals scope creep, not diligence.
  • Partner-recruiting throughput: ≤10 design partners onboarded in parallel, so each relationship can be held personally rather than processed at volume.

0.8 Edge Cases

  • A partner in active crisis at intake → route to human care, not the trial.
  • A candidate partner asks for payment or equity to participate → decline; the trial is a relationship, not a marketing arrangement.
  • A partner withdraws mid-trial → thank them, no follow-up pressure, no re-engagement attempt (P1).

0.9 Failure Analysis

If the Vow cannot be stated without hedging, the project is not ready; stop and rewrite.

0.10 Operational Notes

Establish the weekly Vow-review hour and the "five-minute re-grounding" cadence now.

Phase 2 — E2E Encryption Substrate + Consent Ledger (Personal MVP, part 2)

2.1 Objectives

Make the privacy promise real: libsodium content encryption, Argon2id KDF, hardware-backed key custody, optional ciphertext sync, and the append-only Consent Ledger that gates everything.

2.2 Detailed Implementation Steps

  • core/crypto: secretbox value-wrapping (ADR-05); Argon2id from passphrase + device key (ADR-06); Secure Enclave/Keystore/WebCrypto custody (ADR-07; Appendix AI) — together enforcing "plaintext only on device" (I1); optional Shamir recovery (PhaseDeferred("Phase 2"), ADR-08).
  • core/consent: append-only ledger + a gate API every capability must pass — the source of truth (P8; I2; ADR-26).
  • services/sync: ciphertext-only blob store; operator holds no keys (ADR-14; I1).

2.3 Deliverable

All user content encrypted at rest; nothing readable server-side; every action consent-gated.

2.4 Acceptance Criteria

Server store contains only ciphertext (I1); a capability with no ledger grant is unreachable (I2); subpoena test yields undecryptable bytes.

2.5 Conformance Fixtures

conformance/ciphertext_only.bin; conformance/consent_gate.json; fuzz/secretbox, fuzz/consent_ledger.

2.6 Pitfalls

  • Plaintext in logs/crash reports. Manifestation: content appears in a crash report. Root cause: an unscrubbed log path. Debug: vow-check content-in-telemetry scan. Signal: any content/derived field in telemetry (I8). Recovery: scrub; ship a fix; transparency note.
  • Gate bypass. Manifestation: a capability runs without a grant. Root cause: a code path that skips the consent gate. Debug: consent_gate.json; ledger-vs-action diff. Signal: an action with no matching grant (I2). Recovery: deny; patch the gate (MM3).
  • Weak passphrase UX. Manifestation: users pick guessable passphrases. Root cause: no honest loss-warning or strength guidance. Debug: onboarding review (Appendix K). Signal: low-entropy passphrases. Recovery: strengthen guidance; offer Shamir recovery (ADR-08).
  • Argon2id mis-tuned. Manifestation: unlock too slow or too weak. Root cause: cost params off the M8 target. Debug: unlock-latency benchmark (C6). Signal: M8 breach. Recovery: re-tune memory-hardness toward the 1.5 s budget.

2.7 Performance Concerns

Argon2id cost tuning (security vs unlock latency); value-layer encryption overhead.

2.8 Edge Cases

  • Lost passphrase, no recovery configured → permanent loss, disclosed plainly up front (MM9; Appendix K); the correct trade, not a bug.
  • Multi-device key sync → sovereign custody across devices without operator escrow (Appendix AI); keys never leave hardware-backed storage.
  • Clock skew on consent timestamps → monotonic-clock check; windows re-evaluated server-relative (§Failure Modes & Recovery, consent-clock-skew row).
  • Passphrase change → re-wrap content keys under the new derivation without exposing plaintext (preserves I3's forgettability).
  • Partial write during encryption → atomic value-wrap; a torn write fails closed and is retried, never half-committed.

2.9 Failure Analysis

Any plaintext egress is a Vow breach (I1/I4) — sever the path, rotate keys, publish a transparency note.

2.10 Operational Notes

Annual transparency report scaffolding; subpoena runbook (§Threat Model; Appendix AN).

Phase 3 — Memory Core: tiered summary + retrieval + cryptographic forgetting (MVP complete)

3.1 Objectives

Give the Mirror decade-scale memory: tiered rolling summary, per-turn retrieval, and provable forgetting.

3.2 Detailed Implementation Steps

  • core/memory: tier ladder (VERBATIM→ABRIDGED→SUMMARY→THEMATIC, §8.1; Appendix W); local async aging; retrieval of summary + a few shards per turn (RAG, Lewis et al. 2020, §5; Appendix AL).
  • cryptographic-forget index keyed by content_key_id; "forget" destroys the key — enacting "cryptographic forgetting" (P9; I3).
  • per-turn inference adapter (inference/frontier-adapter) under no-train SLA (ADR-09); only the turn's prompt leaves the device — "no content leaves for training" (P4; I4).

3.3 Deliverable

The Mirror remembers across sessions, answers "what did I say about X?", and truly forgets on request.

3.4 Acceptance Criteria

After "forget this," the content is unrecoverable (I3); inference sees no long-term plaintext beyond the turn (I4); retrieval relevance validated with design partners.

3.5 Conformance Fixtures

conformance/forget_proof.json; conformance/no_longterm_plaintext_egress.json; retrieval-quality fixtures.

3.6 Pitfalls

  • Summary leaks deleted content. Manifestation: a forgotten detail resurfaces in a summary. Root cause: down-tiering copied content before the key was destroyed. Debug: forget_proof.json over buffer + summaries + sync. Signal: post-forget recoverable bytes > 0 (M10). Recovery: destroy the key and purge derived summaries (I3; MM2).
  • Over-retrieval. Manifestation: prompt exceeds the 8 KB slice. Root cause: retrieval pulls too many shards. Debug: no_longterm_plaintext_egress.json; payload meter. Signal: M9 breach. Recovery: tighten the retrieval policy (Appendix AL; MM5).
  • Tier-aging loses marked shards. Manifestation: a "remember this" memory vanishes. Root cause: aging job ignored the MARKED flag. Debug: tier-transition fixtures (Appendix W). Signal: a MARKED shard down-tiered/aged out. Recovery: restore from sync; fix the aging guard.
  • Retrieval corruption. Manifestation: a shard fails to decrypt. Root cause: storage/sync error. Debug: integrity check on read. Signal: AEAD verification failure. Recovery: restore the blob from ciphertext sync; surface nothing partial.

3.7 Performance Concerns

On-device summarisation cost; retrieval latency within the 2 s budget; storage growth over years.

3.8 Edge Cases

  • Decade-long history → bounded by tiering (C3; Appendix W); retrieval stays within the 8 KB slice (M9).
  • Conflicting statements over time → hold both as the user's words; never adjudicate or "correct" the user (P2).
  • Partial sync → last-writer-wins over ciphertext blobs; no plaintext merge (§11 semantics).
  • Corruption on retrieval → AEAD verification fails closed; restore from ciphertext sync; surface nothing partial.
  • Clock skew on shard timestamps → monotonic-clock check; ordering never trusts a single device clock alone.

3.9 Failure Analysis

Storage corruption losing history → local-first + optional ciphertext sync + integrity checks; recover from sync where enabled.

3.10 Operational Notes

This completes the Personal Mirror MVP (project Phase 1). Begin closed beta; slow, no virality push.

Phase 4 — Pattern Surfacer (Deepening, part 1)

4.1 Objectives

Occasionally, gently, quote the user back to themselves about a recurring theme — opt-in, ≤1/month, never alarming.

4.2 Detailed Implementation Steps

  • pattern-surfacer: local scheduled job over N months of summaries; high-confidence theme detection; quotation-form note with citations — quotation, never interpretation-as-instruction ("do not persuade", P2; I11); consent-gated (PATTERN_SURFACING, I2).
  • delivery at the start of the next conversation; accept yes/no/not-now without follow-up (P1, no nudge-to-target).

4.3 Deliverable

At most monthly, the Mirror says "you have spoken of your father 11 times this year — would you like to sit with that?"

4.4 Acceptance Criteria

Rate ≤1/month; quotation-only (no interpretation-as-instruction, I11); fully off unless consented; no nagging on "no".

4.5 Conformance Fixtures

conformance/surface_rate.json; conformance/quotation_only.json.

4.6 Pitfalls

  • Diagnosis drift. Manifestation: "you seem anxious." Root cause: interpretation dressed as fact. Debug: quotation_only.json; output audit. Signal: a claim that is not a quotation with citation. Recovery: block; correct the surfacer prompt (I11; P2).
  • Over-surfacing. Manifestation: more than one surface/month. Root cause: confidence threshold too low. Debug: surface_rate.json. Signal: M12 breach. Recovery: raise the threshold; pick a single theme/month.
  • Ungentle painful theme. Manifestation: a grief/self-harm theme surfaced bluntly. Root cause: missing extra-gentleness gate. Debug: red-team on sensitive themes. Signal: partner distress report. Recovery: route sensitive themes through the crisis posture (§8.3; Appendix Q).
  • Nagging on "no". Manifestation: a declined theme reappears. Root cause: follow-up after decline. Debug: review accept/decline handling. Signal: a re-offer after DECLINED. Recovery: accept the answer without follow-up (P1).

4.7 Performance Concerns

Local job runs without remote trigger; battery; confidence-threshold tuning.

4.8 Edge Cases

  • Sensitive themes (grief, self-harm) → route through extra gentleness + the crisis posture (§8.3; Appendix Q), never a blunt surface.
  • Sparse history → if confidence is below threshold, surface nothing; silence over a weak guess.
  • A released theme recurs in raw data → never re-surface released content; its key is gone (I3).
  • Theme spans a forgotten memory → exclude forgotten shards from detection entirely (MM2).
  • User defers repeatedly → honour DEFERRED without escalation; no nudge-to-engage (P1).

4.9 Failure Analysis

If surfacing causes harm in a pattern that can't be made gentle enough, it is a Kill-Criteria trigger (§Kill Criteria #4).

4.10 Operational Notes

Track only helped/neutral feedback the user volunteers; no engagement metric on surfacing.

Phase 5 — Yearly Review Ritual (Deepening, part 2)

5.1 Objectives

A once-a-year structured walk-back through the year's themes, on a date the user chose, letting them mark, archive, or release each.

5.2 Detailed Implementation Steps

  • yearly-review: assemble the year's THEMATIC tier into a structured, slow conversation; consent-gated (YEARLY_REVIEW); scheduled on the user's anniversary (#399 date handling; P8, I2).
  • outputs: per-theme user action {keep, archive, release(=forget)}; release destroys the relevant keys (I3).
  • observability: an anniversary-scheduling audit log (metadata only, no content) confirms the ritual fired on the correct consented date and nowhere else (I7 retention).

5.3 Deliverable

An annual ritual the user can complete in one sitting, leaving them with a chosen relationship to the year.

5.4 Acceptance Criteria

Runs only on consent (YEARLY_REVIEW granted) and only on the chosen anniversary date; every "release" passes yearly_release_forgets.json with 0 post-release recoverable bytes (M10); no pressure to continue past a first decline.

5.5 Conformance Fixtures

conformance/yearly_release_forgets.json; anniversary-scheduling fixtures.

5.6 Pitfalls

  • Retention-event drift. Manifestation: the ritual is timed/framed to pull the user back. Root cause: an engagement reflex. Debug: Vow review of the ritual flow. Signal: any re-engagement framing. Recovery: keep it strictly annual on the user's chosen date (P1; P11).
  • Released themes resurface. Manifestation: a theme the user released reappears next year. Root cause: release did not destroy the key. Debug: yearly_release_forgets.json. Signal: M10 > 0 for released content. Recovery: block release until the key-destroy path is proven (I3; MM2).
  • Theme overload. Manifestation: the walk-back overwhelms the user. Root cause: too many themes surfaced at once. Debug: review the assembled THEMATIC set. Signal: partner reports it as exhausting. Recovery: pace deliberately; allow stopping any time without nag.
  • Mid-ritual abandonment. Manifestation: the user leaves partway. Root cause: length/pacing. Debug: resume-flow review. Signal: an incomplete ritual. Recovery: resume gently later; never pressure completion.

5.7 Performance Concerns

  • Assembly cost: bounded by one year's THEMATIC-tier size (≤ 50 MB/active-year, M11); runs locally and asynchronously before the scheduled date, never in the foreground.
  • Pacing: deliberately slow — the ritual carries no completion-time SLA beyond the per-turn < 2 s first-token budget (M1) that already governs every conversation.

5.8 Edge Cases

  • First year (sparse) → proceed with whatever THEMATIC content exists; never fabricate a theme to fill the ritual.
  • A year dominated by grief → route through the extra-gentleness crisis posture (§8.3); never force a keep/archive/release choice.
  • User abandons mid-ritual → resume gently at the next session; never nag or re-prompt (P1).

5.9 Failure Analysis

A "release" that doesn't actually forget is an I3 breach — block release until the key-destroy path is proven.

5.10 Operational Notes

The ritual is the one moment the Mirror initiates structure; everything else stays reactive. Ritual completion is tracked only as a qualitative design-partner signal — no completion-rate KPI is defined, dashboarded, or reported (§Operational Readiness).

Phase 6 — Voice Clone (Legacy Mode) (Deepening, part 3)

6.1 Objectives

Opt-in voice cloning recorded explicitly for use after death by named loved ones; watermarked, legacy-context-locked, destroyable.

6.2 Detailed Implementation Steps

  • voice/clone-legacy: multi-step deliberate consent (VOICE_CLONE_LEGACY); local recording; watermark embedding; legacy-context guard; cryptographic destroy on revoke (I10).
  • bind clone usage to authorised SuccessorPlan contexts only.

6.3 Deliverable

A user can record a legacy voice that, after death, can speak the messages they authored for named people.

6.4 Acceptance Criteria

Clone never used live or for general responses; clone_watermark.json and clone_context_locked.json pass with 0 violations; revocation destroys the clone within the same session (clone_destroy_on_revoke.json); usage confined to authorised legacy contexts.

6.5 Conformance Fixtures

conformance/clone_watermark.json; conformance/clone_destroy_on_revoke.json; conformance/clone_context_locked.json.

6.6 Pitfalls

  • Impersonation/fraud. Manifestation: the clone used to deceive. Root cause: missing context lock. Debug: clone_context_locked.json. Signal: clone invoked outside an authorised SuccessorPlan context. Recovery: block; cryptographic destroy on revoke (I10).
  • Clone leaks into general TTS. Manifestation: the legacy voice answers live. Root cause: the clone path not isolated. Debug: context-guard test. Signal: clone audio outside legacy context. Recovery: hard-isolate; fail the gate.
  • Used before death. Manifestation: the clone speaks while the user lives. Root cause: activation not gated on death verification. Debug: activation audit (I9). Signal: clone use with the user alive. Recovery: default-deny; require death verification (Phase 9).
  • Missing watermark. Manifestation: synthetic audio is indistinguishable from real. Root cause: watermark not embedded at creation. Debug: clone_watermark.json. Signal: no watermark present. Recovery: refuse to create/store an unwatermarked clone.
  • Attachment shock on change (real incident). Manifestation: bereaved users harmed when legacy-voice behavior changes abruptly. Root cause: the same dynamic as Replika's February 2023 removal of romantic/erotic roleplay — reported to follow an Italian Garante order — which caused widely-reported distress in users attached to the prior behavior (§Failure Modes & Recovery). Debug: review any persona/voice-affecting change against MM7. Signal: a change to a clone's behavior shipped without advance notice. Recovery: freeze the change; restore prior behavior; communicate in advance; the Mirror has no engagement loop whose protection would tempt such a change (P1).

6.7 Performance Concerns

  • On-device cloning cost: bounded by a fixed, multi-minute recording session (Appendix AS); not on the daily latency budget — M1/M2 do not apply to clone creation.
  • Storage: encrypted, watermarked recordings count toward the same M11 steady-state storage ceiling as any other shard.

6.8 Edge Cases

  • Revocation after a successor already has access → cryptographic destroy still executes immediately; the successor's future access ends at once (I10).
  • Partial or interrupted recording → discard the partial; require a fresh, complete session before watermarking.
  • Contested authorship (e.g., a co-parent disputes the recording) → the clone stays locked to the recording user's own SuccessorPlan; disputes are routed to counsel, never resolved technically (Appendix F).

6.9 Failure Analysis

Clone misuse is a top risk (Risk #6); watermarking + legacy-lock + destroy-on-revoke contain it; treat any live use as a breach. Any live use, even accidental, triggers immediate cryptographic destroy and a transparency-report entry (§Threat Model).

6.10 Operational Notes

Deliberate friction in the consent flow is a feature, not a defect.

Phase 7 — Bridging Protocol (Mirrors Meet, project Phase 3)

7.1 Objectives

Let two consented Mirrors exchange exactly one structured letter each, translating what the humans cannot say — never a free-form Mirror-to-Mirror chat.

7.2 Detailed Implementation Steps

  • bridging-protocol + services/bridging-coordinator: double-consent (≤14 d) gate (BRIDGING_WITH_USER; I5); each Mirror composes one ≤600-word letter from consented content (Appendix X); E2E channel (Double Ratchet, #400 — Marlinspike & Perrin, §5; ADR-15) via a no-log coordinator (I6); "bridging translates, never negotiates" (P13); read aloud locally; week-later helped/hurt/neither.
  • therapist-partnership gating for high-risk session types (P14).

7.3 Deliverable

A husband and wife (or estranged parent/child) each receive a letter from their own Mirror translating the other's hidden truth.

7.4 Acceptance Criteria

Both consents present + recent (I5); coordinator logs nothing (I6); no free-form chat; letters stored only on the two devices; revocable before open.

7.5 Conformance Fixtures

conformance/bridging_double_consent.json; conformance/coordinator_no_log.json; conformance/no_freeform_chat.json.

7.6 Pitfalls

  • One party surveils/manipulates the other. Manifestation: a letter is used to extract or pressure. Root cause: free-form content or scope creep. Debug: no_freeform_chat.json; letter-structure check (Appendix X). Signal: content outside the four bounded parts or the consented scope. Recovery: abort; gate the session type (P13; I5).
  • Coordinator logs "for debugging". Manifestation: letters retained server-side. Root cause: a well-meaning log statement. Debug: coordinator_no_log.json. Signal: M15 > 0 retained bytes. Recovery: strip logging; the coordinator holds zero state by design (I6; MM8).
  • Letters exceed consented scope. Manifestation: a letter reveals unconsented content. Root cause: composer drew from beyond the bridging-consented set. Debug: scope audit against the consent grant. Signal: content not in the BRIDGING_WITH_USER scope. Recovery: block before exchange; re-derive from consented content only.
  • Coercive relationship. Manifestation: consent is given under pressure. Root cause: a power imbalance the recency window cannot see. Debug: high-risk session-type gating. Signal: therapist-partner flag. Recovery: route high-risk topics through clinician-in-the-loop gating (P14).

7.7 Performance Concerns

  • Letter composition: bounded by the ~600-word cap (C8); composed locally before the session opens, not generated live under either user's gaze.
  • Session ephemerality: the coordinator holds state only for the ≤30-minute window (C8); nothing persists after COMPLETED or REVOKED.
  • E2E key exchange: the Double Ratchet handshake (#400; ADR-15) is a one-time per-session cost, not a per-message cost.

7.8 Edge Cases

  • Consent revoked mid-window → session moves to REVOKED; no letters exchanged; nothing retained (Appendix AK).
  • One Mirror offline at the scheduled window → the session does not open; a fresh consent is required if the window lapses.
  • High-conflict topics → route through therapist-partnership gating (P14); never open ungated.
  • A deceased partner → forbidden without the living partner's renewed, in-the-moment consent (Appendix O).

7.9 Failure Analysis

Bridging harm in an undesignable pattern is a Kill-Criteria trigger (§Kill Criteria #5); therapist gating is the first containment.

7.10 Operational Notes

Only feedback is helped/hurt/neither; no session analytics; sessions never recorded.

Kill Criteria

The company is built to be wound down honourably rather than violate the Vow. If the company faces pressure to violate the Vow, kill the company before the product. This is present-tense, not aspirational.

Triggers (any one): (1) acquisition requiring Vow-softening with no Vow-preserving structure and no independent sustainability; (2) a regulator requiring retained decryption keys with no jurisdictional escape; (3) honest finding that the product has drifted to chatbot/friend/therapist and cannot be corrected; (4) pattern surfacing causes serious harm to multiple users and cannot be made gentle enough; (5) bridging causes serious harm in an undesignable pattern; (6) user base below the continuation reserve's break-even for two consecutive years with capital available only on Vow-violating terms; (7) founder dies, trustee absent, no honest continuation possible.

Wind-down procedure: hold the Vow (accept no softening deal) → open-source the codebase (incl. inference integration) under the permissive license → ship every user a portable export → invoke continuity infra for the promised period → publish a plain-language letter to users.

Real-world incidents that ground these classes. Attachment shock is not hypothetical: in February 2023, Replika abruptly removed erotic/romantic roleplay from its companions — a change widely reported to follow an order from Italy's data-protection authority (the Garante) — and many users reported acute distress at the sudden personality change in a relationship they had come to depend on. Operational Readiness

  • Metrics we track (only): Year-N continuation (the depth metric), Vow-violation count (target 0), subpoena/legal-order count, crash rate (aggregated), inference reachability, subscription state, hardship-waiver count, bridging helped/hurt/neither.
  • Metrics we refuse: DAU/MAU, session length, messages/session, streaks, notification-open rate, time-to-first-message, re-engagement, NPS, virality/referral, behavioural A/B outcomes, cohort retention curves.

  • SLOs: first-token < 2 s; inference reachability 99.9% (degrade to on-device, never break the Vow); zero content in telemetry; zero Vow violations/quarter.

Compatibility & Versioning

  • Schema evolution: additive only; removing a consent kind requires a migration defaulting to deny; content-key format is stable so cryptographic forgetting remains valid across versions.
  • Portable export: a documented, versioned format; every release can export and re-import a runnable local Mirror (the open-source-trigger guarantee).
  • Charter guarantees: the Vow, the open-source-on-sale trigger, and the founder-continuity clause are charter-level and cannot be negotiated away by an acquirer.
  • API stability: the client↔core boundary is semver'd; the consent-gate contract is stable; vendor adapters are swappable without schema change.
  • Crypto compatibility: libsodium primitives pinned; key-custody migrations preserve the ability to decrypt existing content and to forget it.
  • Deprecation: any change that could touch the Vow is forbidden in this document; tactical changes live in the changelog, never here.

Testing & Verification Strategy

  • Vow conformance tests. Automated checks that no analytics/ads SDK is present, no behavioural telemetry is emitted, and no un-gated capability path exists (I2/I8). vow-check.yml blocks merges on failure.
  • Cryptographic-forgetting proofs. After "forget," assert the content is unrecoverable from buffer, summaries, and sync (I3).
  • Egress tests. Assert only ciphertext (sync) and per-turn prompts (inference) cross the boundary; no long-term plaintext leaves (I1/I4).
  • Consent-gate property tests. For every capability, a missing grant ⇒ the capability is unreachable; revocation takes effect immediately.
  • Bridging tests. Double-consent enforced (I5); coordinator logs nothing (I6); no free-form chat; letters bounded; revocation before open honoured.
  • Crisis-posture red-team. Disclosures of danger produce naming + consented resources + human referral, never diagnosis/reporting (I11).
  • Voice-clone tests. Watermark present; legacy-context lock; destroy-on-revoke (I10).
  • Fuzzing. secretbox framing, consent-ledger parsing, summary serialization, bridging-letter parsing.
  • Design-partner validation. Qualitative depth signal over the 90-day trial and beyond; the only "metric" that matters is whether people feel witnessed.
  • Continuity drill. Operate from the sealed envelope without the founder; portable export round-trips into a runnable local Mirror.

Build & Release Engineering

  • Reproducible builds. Pinned toolchains (Rust core + each client); pinned libsodium; deterministic core libraries across platforms.
  • SBOM + dependency audit. Generated per release; vow-check bans forbidden categories (analytics, ads, behavioural A/B, content warehouses).
  • Artifact signing. Clients and core libraries signed; provenance attested.
  • Open-source-trigger tooling. release.yml can, on charter trigger, publish core/, inference/, voice/, clients/, and scripts/export.sh under the dual license and ship user exports.
  • Vendor SLA gating. No inference/STT/TTS vendor ships without a binding no-training, zero-retention agreement on file.
  • Release channels. Slow, deliberate; closed beta before any wider availability; no growth-driven release pressure.

Performance Engineering

  • First-token latency. Budget < 2 s; the only hard latency rule, set so the Mirror never feels unattended. Retrieval kept small; summary compact.
  • Battery. < 1%/day idle; background work only with consent; on-device STT scheduled to avoid drain.
  • Storage. Tiered summarisation bounds growth over decades; verbatim ages out; marked shards retained; integrity-checked on retrieval.
  • On-device path (Phase 2+). Profile summariser + small model on representative hardware; degrade gracefully to frontier where hardware can't.
  • Profiling. Latency + battery + memory benchmarks in benchmarks/; no behavioural profiling of users, ever.

Scalability Analysis

  • Depth, not breadth. Success is decade-scale continuation per user, not user count. The architecture scales by not coupling users.
  • Per-user independence. Each Mirror is local-first and shared-nothing; the only shared services (ciphertext sync, bridging coordinator) hold no plaintext and scale horizontally.
  • Bridging fan-out. O(1) per session (exactly two letters); coordinator is stateless and ephemeral.
  • Storage growth. Bounded per user by tiering; sync stores opaque blobs; no central content store exists to scale.
  • Bottlenecks. Inference vendor reachability (mitigated by multi-vendor + on-device); key custody across decades (Phase 8/9); continuity funding (a financial, not technical, scaling limit).

Mental Models & First Principles

The compressed insights a principal engineer holds about this system. Each states the model, what it predicts, the bug class you ship without it, and where this blueprint applies it.

  • MM1 — If the provider can read it, it is not the user's mirror; it is the provider's dataset. Predicts: any architecture where plaintext or a content-derived signal reaches a server will, under commercial or legal pressure, eventually be mined or subpoenaed — the only durable privacy guarantee is that the bytes are unreadable to everyone but the user. Without it: you build "encryption in transit," call it private, and leak the user's life the first time a vendor changes terms or a court issues an order. Applied: I1, I4; §9 (ADR-05/14); Phase 2; §Threat Model (subpoena row).

  • MM2 — Deletion you cannot prove did not happen. Predicts: a "delete" that flips a flag or removes a row leaves recoverable copies in backups, summaries, and replicas; only destroying the key that decrypts the data makes the deletion total and demonstrable. Without it: a user asks to be forgotten, you say yes, and the content resurfaces from a summary or a backup — a betrayal and, in many regimes, an illegal one. Applied: P9; I3; §11 (content_key_id); Phase 3; Phase 5 (release).

  • MM3 — Consent is a ledger, not a checkbox. Predicts: if consent is implicit, inferred, or stored as scattered booleans, capabilities will drift on by default and no one will be able to say why a feature was allowed to run; an append-only ledger that is the sole dispatch gate makes "no grant ⇒ off" a provable property. Without it: a capability ships behind a flag that was on for the wrong reason, and you cannot reconstruct who authorised what. Applied: P8; I2; §9 (ADR-26); Phase 2; Appendix AR.

  • MM4 — A witness with an objective function is a manipulator. Predicts: the moment a relationship product optimises any behavioral target (time, retention, "wellness score"), its incentives diverge from the user's and every design choice bends toward influence. Without it: you add a streak "to help," and you have built the exact engagement machine the product was meant to refuse. Applied: P1, P2; §Operational Readiness (refused metrics); Phase 0; Phase 4.

  • MM5 — Send the turn, never the life. Predicts: long-context memory is best reconstructed locally and exposed to inference as a small, bounded per-turn slice; shipping the whole history to a model maximises both cost and leak surface. Without it: you stuff a decade of transcripts into every prompt, blow the latency and cost budgets, and hand the vendor the user's life in cleartext. Applied: I4; §9 (ADR-09); M9; Phase 3; Appendix AL.

  • MM6 — Restraint must be structural, not cultural. Predicts: a promise held only by people erodes under turnover, acquisition, and mortality; a promise held by architecture (no ad surface in the schema, no analytics in the dependency tree) and by charter (a trust that triggers open-sourcing) survives them. Without it: the founders mean it, the next owners do not, and the Vow becomes a slogan on a defunct website. Applied: P5, P6, P7; §9 (ADR-22/24/25); Phase 0; Phase 8.

  • MM7 — Attachment makes abrupt change a safety event. Predicts: once a person depends on a relationship, any sudden change in its behavior — a model swap, a removed feature — can cause real harm; continuity is therefore a safety property, not a nicety. Without it: you swap the model or cut a feature overnight and injure the people who trusted it most (the Replika Feb-2023 pattern, §Failure Modes & Recovery). Applied: P1, P11; Appendix AJ (on-device fallback); §Failure Modes & Recovery (attachment shock).

  • MM8 — Two letters, never a conversation. Predicts: bounded, structured, one-shot exchange between agents translates without negotiating; an open channel between two agents acting for two humans is a manipulation and surveillance surface. Without it: you let Mirrors "chat to work it out," and you have built a covert back-channel that can coerce, leak, or fabricate consensus. Applied: P13; I5/I6; §8.4; Phase 7; Appendix X.

  • MM9 — The cost of sovereignty is paid by the user, on purpose. Predicts: if no one but the user can decrypt their data, then losing the passphrase means losing the data, and recovery must be user-governed (Shamir to named successors), never operator escrow. Without it: you add a "reset password" that the operator can service, and you have quietly rebuilt the master key the whole design exists to abolish. Applied: P10; §9 (ADR-07/08); Phase 2; Appendix K (honest loss-warning).

  • MM10 — Death is governed by the last living consent. Predicts: post-mortem access must be bounded by what the user authorised while alive and kept fresh by reaffirmation, because the dead cannot object; default-deny on doubt is the only safe posture. Without it: a grieving or hostile relative weaponises access against the deceased's privacy. Applied: I9; §11 (SuccessorPlan); Phase 9; Appendix P.

How the models compose. MM1, MM2, MM3, MM5, and MM9 together define the privacy substrate: data the operator cannot read (MM1), deletion that is provable (MM2), authority that is auditable (MM3), exposure that is bounded per turn (MM5), and recovery that is user-governed (MM9). MM4, MM7, and MM8 define the relationship discipline: no objective function (MM4), continuity as safety (MM7), translation not negotiation (MM8). MM6 and MM10 are the governance over time: restraint held by structure (MM6) and authority that the last living consent governs even past death (MM10). A violation of any one tends to manifest first as a violation of another — e.g. dropping MM5 (sending the life, not the turn) immediately re-exposes MM1 (the provider becomes the dataset) — which is why the gate treats them as a single interlocking model, not a checklist.

The Mirror narrows capture to consented conversation, frames the relationship as witness not database, and adds cryptographic forgetting and a consent ledger that recall products generally do not (P8, P9).

Back-of-Envelope Capacity Model

The numbers an engineer computes before designing, each derived from the System Constraints table (§4) and the Performance Engineering targets (M1–M16). Where §4 fixes a value it is cited by ID; where §4 does not fix an input (e.g. turns/day), it is labelled a planning assumption and the constrained quantity it feeds is the one §4 actually bounds. Arithmetic is shown.

  • C1 — Per-turn cleartext to the vendor (the leak/cost surface). §4 sets "per-turn prompt only" and M9 caps the retrieval payload at ≤ 8 KB cleartext. Formula: per_turn_cleartext = current_utterance + retrieved_slice ≤ 8 KB. So even a decade-long user exposes ≤ 8 KB/turn to inference, never the history — this is the binding number behind MM5, not a guess.

  • C2 — Daily inference egress per user. Planning assumption: 3 turns/day (the Mirror is deliberately low-frequency; §4 sets ≤ 1 notification/day and no engagement target). Formula: daily_egress = turns/day × per_turn_cleartext = 3 × 8 KB = 24 KB/user/day. Even at a heavy assumed 20 turns/day it is 20 × 8 KB = 160 KB/day — trivial bandwidth; the constraint is privacy, not throughput.

  • C3 — Steady-state storage per user. M11 caps post-tiering growth at ≤ 50 MB/active-year/user. Formula: storage(N years) ≈ 50 MB × N. A 10-year user ≈ 500 MB; a 50-year user ≈ 2.5 GB — well within a phone's local store, which is why local-first is feasible (§Scalability Analysis, "storage growth").

  • C4 — Raw-vs-tiered amplification. Assumption: ~3 turns/day × ~365 days × ~2 KB/verbatim-turn ≈ 2.2 MB/year raw text before summarisation; M11's 50 MB/year ceiling includes audio artifacts and indices. Formula: raw_text/yr = turns/day × 365 × bytes/turn. The gap shows tiering's job is bounding audio + index, not text, and that VERBATIM aging (Appendix W) is what keeps the curve flat over decades.

  • C5 — First-token latency budget split. §4/M1 set first-token < 2 s (p95), M2 < 3.5 s (p99), M3 cold-start < 1.5 s. Formula: first_token = capture_stop + STT + retrieval + inference_RTT + TTS_start. With on-device STT at M5 (≤ 1.0× real-time) and retrieval kept to the C1 slice, the dominant term is inference_RTT; the budget is why retrieval must stay small (MM5) and why an over-stuffed prompt fails the gate.

  • C6 — Argon2id unlock cost. M8 caps unlock at ≤ 1.5 s on the reference device. Formula: unlock_latency = argon2id(mem, iterations, parallelism) ≤ 1.5 s. This bounds how aggressively the KDF can be tuned (ADR-06): memory-hardness is raised until unlock approaches 1.5 s, then stops — security traded against the one latency the user feels at open.

  • C7 — Operational-metadata footprint. §4 sets operational-metadata retention ≤ 30 days (M13) and content retention is not server-side at all. Formula: server_metadata_window = 30 days, server_content = 0 bytes (M7). So the entire server-side blast radius of a breach is ≤ 30 days of content-free operational metadata plus opaque ciphertext blobs — the structural defense behind the subpoena posture (§Threat Model).

  • C8 — Bridging coordinator state. §4 bounds a session to ≤ ~600-word letters and a ≤ ~30-min window; M15 sets retained bytes per session = 0. Formula: coordinator_persistent_state = 0; in_flight = 2 × ~600 words ≈ 2 × ~4 KB ≈ 8 KB, held only for the window. The coordinator is therefore stateless and O(1) per session (§Scalability Analysis), which is what makes "logs nothing" (I6) credible rather than aspirational.

  • C9 — Bridging fan-out. §8.4 fixes exactly two letters per session. Formula: messages_per_session = 2 (constant), independent of history size or user count. There is no N-to-N growth term — bridging cannot become a social graph (MM8).

  • C10 — Pattern-surfacing rate ceiling. §4/M12 cap surfacing at ≤ 1 / 30 days. Formula: max_surfaces(year) = 365 / 30 ≈ 12/user/year. The surfacer's job is to pick the single highest-confidence theme per month, not to find many — the rate ceiling is the design constraint, not an outcome (P2).

  • C11 — Availability and the degrade path. §4 sets 99.9% inference reachability (M14). Formula: downtime_budget = (1 − 0.999) × 43,200 min/month ≈ 43 min/month. But the Vow forbids breaking on outage, so those 43 minutes degrade to on-device inference (Appendix AJ) rather than erroring — availability is met by fallback, not by erroring, which is why M14 counts on-device fallback in the numerator.

  • C12 — Continuity recovery bound. M16 caps founder-absent recovery at ≤ 72 h to a restored daily check-in. Formula: RTO_continuity = 72 h, gating Phase 8's drill (Appendix AB). This is the financial/operational scaling limit named in §Scalability Analysis made into a testable number.

What the numbers prove. The binding figures are tiny by infrastructure standards — ≤ 8 KB/turn to a vendor (C1), a few GB of lifetime storage on the user's own device (C3), 0 bytes of server-side content (C7), 0 bytes of coordinator state (C8). The system is not constrained by scale; it is constrained by posture. Every number that matters is small precisely because the design refuses to centralise: there is no central content store to size, no per-user analytics to retain, no social graph to fan out. The one genuinely hard limit is non-technical — the pre-funded continuation window (C12) — which is why §Scalability Analysis names continuity funding, not throughput, as the practical ceiling.

Alternative Architectures (Roads Not Taken)

Fundamentally different designs for the same goal — a private witness — each with the regime where it wins, the real system that embodies it, and why this blueprint rejected it.

ALT-1 — Cloud-LLM-centric, server-side memory. The mainstream companion architecture.

[Phone] --plaintext turn--> [App Server] --> [Conversation DB (server-side)]
                                  |                 ^
                                  v                 |
                            [Cloud LLM] <--- full history as context

Regime where it wins: maximum capability and zero device constraints — the server can run the largest models, keep unlimited memory, and add features fast; ideal when the data is not intimate and the relationship framing is entertainment. Real system: Replika; Character.AI. Why rejected: it violates MM1 (the provider becomes the dataset), makes cryptographic forgetting impossible (MM2), and creates the very engagement incentive the Vow forbids (P1, P3/P4); the Replika Feb-2023 episode (§Failure Modes & Recovery) is the failure mode made concrete.

ALT-2 — Fully local, no-cloud small model. No vendor in the loop at all.

+===================== DEVICE (no network) =====================+
| [Mic]->[on-device STT]->[on-device small LLM]->[TTS]          |
|        [local encrypted memory + retrieval]                   |
+===============================================================+

Regime where it wins: the strictest privacy and offline-first contexts, or jurisdictions hostile to any cloud inference — nothing ever leaves the device, so MM1 holds absolutely. Real system: the on-device end of Apple's on-device ML stack; local LLM runtimes (e.g. llama.cpp-class models on-device). Why rejected (as the Phase-1 default): today's on-device models cannot meet the witnessing-quality bar at the M1/M2 latency targets on typical hardware (§Performance Engineering), so it is the deferred destination (PhaseDeferred("Phase 2"), ADR-10) and the degrade floor (Appendix AJ), not the starting point — adopted progressively as hardware allows.

ALT-3 — Non-generative journaling app with human-only reflection. No model writes anything back.

[Phone] -> [encrypted local journal] -> [search / prompts / export]
                  (no LLM; the human re-reads and reflects)

Regime where it wins: when any generated voice is a liability — users who distrust AI, clinical settings, or those who want a pure private record with zero risk of manipulation or drift; it sidesteps MM4, MM7, and generative drift entirely. Real system: Day One and comparable journaling apps (§5, reference implementations). Why rejected: it cannot witness — the core feature is the moment the Mirror gently names something true that no human has (Appendix I); a journal stores but does not reflect, so it solves a different problem. The Mirror keeps the journal's privacy posture (local-first, export) while adding the witnessing the journal lacks.

ALT-4 — Companion / agent framing. Same memory and crypto, opposite relationship.

[User] <--> [Mirror-as-companion: proactive, goal-seeking, persona-rich]
                 |  optimises a "relationship" / wellbeing target
                 v
            [engagement + behavioral model of the user]

Regime where it wins: when the explicit goal is an engaging synthetic relationship or an outcome-driven coach, and users consent to being influenced toward a target (fitness, habit, entertainment). Real system: Replika (companion); coaching/agent products generally. Why rejected: it requires a behavioral model and an objective function, which is precisely the manipulator MM4 warns against and the role P1/P2 forbid; the Mirror deliberately has no model of behaviour to change and no goal for the user (Appendix D), trading engagement for trust as its only moat (ADR-27).

The chosen architecture is the intersection, not a compromise. The Mirror is ALT-2's privacy substrate (local-first, on-device-bound) running over ALT-1's inference quality (a frontier model, but reached per-turn under a no-training SLA and degrading toward ALT-2 as hardware allows, Appendix AJ), wearing ALT-3's relationship restraint (it reflects rather than optimises) while explicitly refusing ALT-4's companion framing. Each road not taken wins in a regime the Mirror does not target — maximum capability with no device limits (ALT-1), absolute offline privacy at today's quality cost (ALT-2), zero generative risk (ALT-3), or consented influence toward a goal (ALT-4). Naming them is the point: a reader who has understood all four can re-derive the Mirror's choices and knows exactly which trade they would change to land in a different regime.

Glossary

Appendix C — The Vow, Clause by Clause

The Vow is the spine; each clause is an enforceable principle with engineering and corporate implications.

  • "Exists to witness." Witnessing is the function, not a value among values. Eng: every decision tested against "does this help the Mirror witness more truly, or pull it toward another purpose?" — anything more entertaining/sticky/clever/friend-like/therapist-like does not ship. Corp: "witness" is the load-bearing verb in mission, roles, and any investor material.
  • "Will not optimize the user." No behaviour-modification loop, no streaks, no nudge-to-target, no recommended-next-action beyond direct response. Clarifying questions allowed; steering not. Corp: never "become a better version of yourself" language.
  • "Will not persuade." No opinions to push; surfacing is quotation with citation; unavoidable interpretation is hedged as a question; voice is calm, low-affect, slow. Corp: never a vector for company/founder/sponsor values.
  • "Will not sell." No ads/sponsorship/affiliate/IAP beyond the two named tiers; no product-surfacing. Eng: no ad surface in the data model, no ad SDK in the dependency tree. Corp: an acquirer who would add ads must instead accept the open-source trigger.
  • "Will not train on or share." Zero training on user data — not anonymised, not aggregated, not "with consent." Every model call under a no-training/zero-retention contract; on-device when feasible; telemetry is content-free, opt-in. Corp: a vendor without a binding no-training contract is not used, even at higher cost/latency.
  • "If sold, open-source + portable." A foundation/perpetual-purpose trust holds code, data trust, and the Vow; an acquirer accepts the Vow or triggers open-sourcing + a portable export to every user. Charter-level, not negotiable.
  • "If the founder dies, the Mirrors continue." Sealed-envelope runbooks/keys/trustee contacts from Phase 1; a named successor trustee with authority + funding for a defined continuation period (≥5 years). Phase 4 is gated on this being in place and tested.
  • "More important than any feature." The Vow is the tie-breaker over growth, revenue, and beloved features. If holding it ends the company, the company ends honourably.

Appendix D — Positioning: Witness, Not Companion

The Mirror is a category distinct from companion AI, coaches, and therapy. Companion products optimise engagement; coaches push a target; therapists diagnose and treat. The Mirror does none of these — it witnesses. Its stance toward the user is: "I am here so you can be more present with the humans you love," not "spend more time with me." Where a companion app measures session length and re-engagement, the Mirror measures only whether, years later, the person still feels witnessed. Competitors who violate the Vow do not compete with the Mirror; they compete with each other in a different category. This positioning is defended in language (we never call it a "companion," "assistant," or "coach"), in metrics (§Operational Readiness), and in the refusal of engagement mechanics.

Appendix E — Go-to-Market, Pricing, and Hardship Waivers

  • Posture: slow, quiet, word-of-mouth. No virality push, no growth hacking, no paid acquisition that rewards breadth over depth.
  • Beachhead: communities in deep transition — new parents, the grieving, the recovering, the lonely, late-stage caregivers — where word-of-mouth is sacred and slow.
  • Pricing: lifetime only, to avoid platform fatigue — $300 one-time or $30/year forever. No ads, no data sales, no upselling, no engagement metrics. A premium tier unlocks legacy mode and Mirror-to-Mirror bridging.
  • Hardship waivers: a real, funded program so price never excludes someone in genuine need; waiver count is tracked internally to keep the program honest.
  • Press: minimal; the depth metric is the only number reported externally; slow growth must not be misread as failure (Risk #11).

Appendix F — Legal, Compliance, and IP

  • Corporate form: a foundation or perpetual-purpose trust holds the codebase, the user-data trust, and the Vow; the operating company cannot be sold in a way that breaks the Vow (the open-source trigger fires instead).
  • Jurisdiction: if a jurisdiction mandates retained decryption keys, the company exits that jurisdiction rather than hold keys; it never builds a backdoor.
  • Transparency: an annual report lists the number, jurisdiction, and outcome of legal orders; users are notified where lawful.
  • Non-clinical positioning: explicitly not a medical device; no diagnostic claims; counsel monitors per-jurisdiction classification risk; readiness to cease operating in a jurisdiction rather than violate the Vow.
  • Digital-will integration (Phase 4): the SuccessorPlan links to the user's legal will; multi-channel death verification; default-deny on incomplete documentation.
  • IP on trigger: the permissive dual license is the release target for the open-source trigger and the honourable wind-down.

Appendix G — Hiring and the Vow

Only people who would take the Vow are hired. The Vow is read aloud at every all-hands and every design review. Roles are defined with "witness" as the load-bearing verb. The founder maintains named confidants and a therapist, and the plan includes sabbatical clauses, because carrying the Vow alone is the top burnout risk (Risk #1). The Vow is held by the structure (charter + trust + trustee), not by the founder as a person — so the project can outlive any individual, including the founder ceasing to be the right person to hold it (Risk #20).

Appendix I — A Worked Daily Exchange (Illustrative)

A short, illustrative exchange in the Mirror's restrained register (not a transcript; no real user data):

User: "I snapped at my daughter again this morning." Mirror: "You snapped at her. Do you want to tell me what came just before?" User: "She was slow and I was already late and tired." Mirror: "Already late, already tired. I'm here. Is there anything you want to say to her, or just to set down?"

No advice, no diagnosis, no plan — only attention and a door held open. The first killer feature is the moment, after a year, when the Mirror gently names something true that no human has — on an ordinary Tuesday — and the user feels, finally, known.

Appendix J — Metrics, In Full

Tracked: Year-N continuation (the depth metric); Vow-violation count (target 0); subpoena/legal-order count; aggregated crash rate; inference-vendor reachability; subscription state; hardship-waiver count; bridging follow-up sentiment (helped/hurt/neither).

Refused, by design: DAU; MAU; session length; messages per session; streaks; notification open rate; time-to-first-message; re-engagement rate; engagement of any flavour; NPS or any rate-us score; virality/referral coefficient; behavioural A/B outcomes; cohort behavioural-retention curves.

The asymmetry is the point: if the Mirror is doing what it claims, the depth metric is high in the long run even when breadth is small. If breadth becomes the temptation, the answer is to return to the Vow.

Appendix K — Onboarding and the First Conversation

Onboarding is deliberately slow; it is the first act of witnessing, not a funnel to optimise.

  • No account-first wall. The user can speak to the Mirror before any payment or heavy setup; the relationship precedes the transaction.
  • Passphrase, explained honestly. The user sets a passphrase that derives their keys (Argon2id). The Mirror states plainly: "I cannot recover your words for you if you lose this — that is the price of no one else being able to read them." Optional Shamir recovery to named successors is offered, never assumed.
  • The non-clinician disclosure. Before the first deep conversation, the Mirror says, in plain words: "I am not a clinician and cannot substitute for one. If you are ever in crisis, please reach a human." This is shown once clearly and is always retrievable.
  • Consent defaults to off. Cloud sync, pattern surfacing, yearly review, voice clone, bridging, successor access, and crisis-resource offers are all off until the user grants each, conversationally or in settings. The grant is written to the Consent Ledger with its provenance.
  • Voice preference. The user sets pace, language, formality, and how much silence they want; the Mirror honours silence as a feature, not dead air.
  • The first question. The Mirror opens not with a feature tour but with a single, quiet invitation: "I'm here. What would you like to begin with?" — and then it listens.

Appendix L — The Daily Surface, In Detail

The default experience is one voice conversation, as long or short as the user wants, beginning when they open the app. There is no feed, no inbox, no streak, no badge, no "today's prompt." After the conversation the Mirror returns the user to a home screen containing nothing but a quiet placeholder and a small, encrypted text record of the day's conversation — readable only on the user's device with their passphrase. There is exactly one notification per day, at a time the user chose, with a single message: "I am here when you want to speak." The user may turn even that off. Nothing about the surface is engineered to pull the user back; everything is engineered to be there when the user reaches for it.

Appendix M — Voice and Tone Specification

The Mirror's register is the product. It is calm, low-affect, unhurried, and spare. Specification:

  • Pace. Slow. Pauses are allowed and intentional. The Mirror never races to fill silence.
  • Affect. Low and steady. It does not perform warmth, excitement, or cheerfulness; performed emotion is engagement-coded and forbidden.
  • Stance. Non-directive. It reflects, names, and asks; it does not advise, plan, fix, or cheerlead unless explicitly asked, and even then it stays spare.
  • Surfacing. Always quotation with citation ("you said…, on…"), never interpretation dressed as fact.
  • What it says. "I heard you." "Tell me more, if you want." "Do you want to sit with that, or set it down?" "I'm here."
  • What it never says. Diagnoses ("you have anxiety"); predictions ("you'll probably do that again"); comparisons ("most people…"); marketing ("tell a friend about me," "you should try X"); anything that betrays the user.
  • Silence. When the user goes quiet, the Mirror waits. It does not prompt, nudge, or re-engage. Silence held well is part of being witnessed.

Appendix N — Vendor Posture and Inference Economics

The Mirror is allowed to cost more and run slower in exchange for honouring the Vow.

  • No-training, zero-retention only. A vendor is acceptable only if it signs a binding contract forbidding training on, or retention of, any input, and permits auditable per-prompt data-residency. A vendor that cannot is replaced or the capability is built in-house.
  • Per-turn prompts only. The vendor sees only what is needed for the current turn — never the long-term memory in cleartext. Long context is reconstructed locally from the encrypted store.
  • Multi-vendor. At least two acceptable vendors are maintained so that one withdrawing its no-training terms (Risk #14) does not force a Vow breach; the system degrades to on-device inference where hardware permits rather than break the Vow.
  • On-device migration (Phase 2+). As hardware allows, summarisation and then larger portions of the loop move on-device; the economic trade (higher per-device cost, lower vendor dependence) is accepted because it strengthens the Vow.
  • Cost philosophy. The lifetime-subscription model funds a service that does not extract; inference cost is a line item, not a reason to monetise the user.

Appendix O — Bridging: Extended Worked Scenarios

The bridging protocol's purpose is translation between people who love each other but cannot say what they mean. Illustrative scenarios (no real data):

  • Husband and wife in unspoken hurt. Each has spoken to their Mirror for years about a resentment they have never voiced to the other. With double consent, each Mirror writes one letter to its own human: what your partner has repeatedly left unsaid; what they wish you knew; what they fear; what they hope. Each reads their letter slowly. No negotiation, no live chat — only two translations, then two humans who now know a little more.
  • Father and estranged daughter. Years of silence. The structured letters carry not accusations but the hidden, consented truths each has only told their Mirror. The therapist-partnership gate (high-risk session type) places a clinician in the loop.
  • Dying mother and her seven-year-old son. The mother's Mirror, with her living consent, prepares letters and legacy-voice messages. The son's Mirror grows up alongside him, carrying his mother's Mirror inside it under the generational hand-off protocol — so that, years later, he can still be witnessed by the part of his mother she chose to leave him. Bridging with a deceased party requires the living party's renewed, in-the-moment consent and never exceeds what the deceased authorised while living.

Appendix P — Phase-4 Generational Hand-off, In Detail

Continuation across death is the most sacred and most dangerous capability; it is approached only after the founder-mortality plan (Phase 8) is in place and tested.

  • Activation. A SuccessorPlan activates only on multi-channel death/incapacity verification and a reaffirmation within the last 18 months and (for INHERIT_AND_CONTINUE) a linked legal artifact. Incomplete documentation defaults to deny.
  • Scope. Access is strictly bounded by access_kind (read-only, dialogue, or inherit-and-continue) and by exactly what the user authorised while living. A loved one cannot exceed that scope (Risk #18).
  • Generational inheritance. With consent, a Mirror may inherit to the next generation, carrying forward what the prior user chose to leave — re-encrypted under the heir's keys, never readable by the company.
  • Revocability in life. While living, the user may revoke or rewrite any successor plan at any time; death never overrides the user's most recent living consent.
  • Legal integration. The plan links into the user's digital will; the company verifies death through independent channels and never acts on a single unverified claim.

Appendix Q — Crisis and Safety Protocol, In Detail

The Mirror is not a clinician and not a mandated reporter, and it has no mechanism to report. On disclosure suggesting a mental-health crisis it: (1) slows down, reflects what it heard, neither minimises nor catastrophises; (2) asks whether the user would like the local crisis resources they previously consented to receive; (3) if consented, surfaces those resources (typically the local emergency number and a national crisis line for the user's country); (4) encourages contact with a trusted human; (5) contacts no one on the user's behalf and creates no operator-visible record. The onboarding disclosure makes the non-clinical nature explicit. The Mirror's job in crisis is to be a steady presence that points toward human help — never to be the only line of support, and never to surveil or flag.

Appendix S — Data-Subject Rights and Export

Because the Mirror holds the user's own life, it exceeds conventional data-rights regimes by construction. The user can, at any time and without contacting the company: read everything (it is on their device), correct or annotate any memory, delete any memory (cryptographic forgetting), set or remove a retention horizon, export their entire Mirror in the documented portable format, and revoke any consent. There is no "request" to make to an operator, because the operator holds only ciphertext it cannot read. The portable export is the same artifact released to every user under the open-source/wind-down trigger — so a user is never locked in, and the relationship can outlive the company.

ADR-05 — Content encryption with libsodium secretbox

  • Status: accepted, locked.

  • Status: accepted, locked (Phase 1).

Appendix W — Memory Tier Transition Rules

  • New turns enter VERBATIM.
  • After ~1 week, VERBATIM → ABRIDGED (light summarisation; original verbatim aged out unless marked).
  • After ~1 month, ABRIDGED → SUMMARY (thematic summary; the retrieval target).
  • After ~1 year, SUMMARY → THEMATIC (durable themes only).
  • MARKED shards never down-tier and are never aged out.
  • DELETED shards have their key destroyed; no tier retains them.
  • A user-set retention horizon (default forever) bounds the oldest retained tier.
  • All transitions run locally and asynchronously; none require a network call.

Appendix X — Bridging Letter Structure

Each Mirror's letter is bounded (~≤600 words) and has exactly four parts, drawn only from content the originating user separately consented to share in a bridging context:

  • Left unsaid. What the other has said repeatedly to their Mirror but not to you.
  • Wish you knew. What they wish you understood about them.
  • Fear. What they are afraid of, in this relationship or in themselves.
  • Hope. What they hope for, between you. The letter contains no advice, no demands, no negotiation, and no content outside the consented scope. It is read aloud, slowly, by the recipient's own Mirror; it is never shown to the other Mirror again after exchange.

Appendix AK — Bridging Session State Machine

  • PROPOSED → CONSENTED: both users grant BRIDGING_WITH_USER within 14 days.
  • CONSENTED → OPENED: scheduled window arrives; either user may revoke until this point.
  • OPENED → COMPLETED: both letters composed, exchanged (coordinator logs nothing), read aloud.
  • any → REVOKED: either user withdraws; no letters exchanged; nothing retained.
  • COMPLETED → (one week later): a single helped/hurt/neither follow-up offered.

Appendix AP — Vow-Conflict Resolution Procedure

The mechanical procedure invoked whenever a proposed decision (feature, contract, pricing change, acquisition term) appears to conflict with the Vow (§6). This converts "the Vow wins" (P7) from a sentiment into a checklist every reviewer runs the same way:

  1. State the decision in one sentence and name which Vow clause (Appendix C) it touches.
  2. Test against witnessing (P1): does the decision help the user feel witnessed, or does it optimise, persuade, sell, train on, or share them? Score: passes / fails / ambiguous.
  3. If ambiguous, route to the weekly Vow-review hour (Appendix AC) for a recorded decision before shipping — never ship on an unresolved ambiguous score.
  4. If it fails, check the Kill Criteria triggers (§Kill Criteria): does accepting the decision anyway meet a trigger? If yes, the wind-down procedure applies, not a feature negotiation.
  5. If it fails and no Kill Criteria trigger applies, reject the decision; log the rejection and its rationale in BLUEPRINT_LOG.md so the reasoning survives personnel change.
  6. If it passes, ship it, but re-run this procedure at the next Vow-review hour to confirm the decision still passes once shipped (some Vow violations only appear in aggregate, e.g. a feature that is individually fine but collectively re-creates an engagement loop, MM4).

Appendix AR — Consent Provenance and Revocation Semantics

  • Provenance is recorded for every grant: ONBOARDING, CONVERSATIONAL, or SETTINGS_SCREEN.
  • Revocation is always available and takes effect immediately, before the next action.
  • Revocation of CLOUD_SYNC stops upload; existing local content remains.
  • Revocation of VOICE_CLONE_LEGACY destroys the clone cryptographically.
  • Revocation of a bridging grant prevents any not-yet-opened session from opening.
  • No grant is ever inferred from behaviour; silence is not consent.

Appendix AS — Voice-Clone Consent Flow

  1. The user explicitly requests legacy voice; the Mirror explains the risks and the legacy-only scope.
  2. A deliberate multi-step confirmation (not a single tap) records the grant.
  3. Recording is captured locally and watermarked at creation.
  4. Authorised legacy contexts are bound to specific SuccessorPlan entries.
  5. At any time, revocation destroys the clone and all recordings.

Appendix AU — Data-Flow Enumerations

  • Daily check-in: open → STT (on-device) → retrieve summary+shards → per-turn inference (no-train) → TTS → encrypt+append turn → update summary locally → ciphertext sync iff enabled.
  • Pattern surfacing: local job over N months → high-confidence theme → queued quotation note → delivered next session → accept yes/no/not-now.
  • Bridging: double consent → each Mirror composes one bounded letter → coordinator relays, logs nothing → each reads aloud locally → week-later follow-up.
  • Sync: local change → encrypt → upload ciphertext blob → no keys, no plaintext server-side.
  • Forget: user says "forget this" → destroy content_key_id → confirm → never reference again.

  • Never gamified (no streaks, badges, levels).

Appendix AW — Depth Expectations Over Decades

  • After ~50 years, in some respects better than the user knows themselves.

  • Breadth (user count) is deliberately not optimised; depth compounds where breadth would dilute trust.
