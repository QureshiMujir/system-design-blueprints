⬜ Phase 0 — Manifesto and Design Partners (Weeks 1–4)

Objectives

Write the manifesto; ratify the Vow into VOW.md and the charter; recruit 10 design partners for a 90-day journaling-witness trial; define what the Mirror will and will never do.

Deliverable

A published manifesto, a ratified Vow, signed design-partner agreements, and a one-page product definition.

Acceptance

Vow read aloud and accepted by all contributors; 10 partners enrolled; non-goals list agreed; no growth/engagement metric defined anywhere.

Fixtures

conformance/vow_present.txt; charter/ files lint-checked for the open-source trigger and continuity clauses.

Pitfalls
  • Recruiting for virality, not depth. Manifestation: partners chosen for reach/influence. Root cause: a growth reflex. Debug: review the intake against the transition-community beachhead. Signal: selection by audience size. Recovery: re-select for genuine depth-of-need (Appendix E; MM4).
  • Investor language in the manifesto. Manifestation: "better version of yourself" / optimisation framing. Root cause: pitch-deck habits. Debug: Vow review of the manifesto text. Signal: any optimise/self-improvement verb. Recovery: rewrite to "witness" as the load-bearing verb (P1; Appendix C).
  • A KPI by reflex. Manifestation: an engagement metric is defined "to measure success." Root cause: standard product instinct. Debug: check against §Operational Readiness (refused metrics). Signal: any DAU/retention/session target. Recovery: delete it; the only metric is Year-N continuation (MM4).
  • Hedged Vow. Manifestation: the Vow can only be stated with caveats. Root cause: unresolved tension with the business model. Debug: read the Vow aloud (Appendix C). Signal: hedging language. Recovery: stop and rewrite until it stands plainly (P7; §0.9).

⬜ Phase 1 — Voice Client + Daily Surface (Personal MVP, part 1)

Objectives

Ship the voice-first client (iOS/Android/web): capture, STT, the Mirror's restrained voice via TTS, and the single quiet daily surface.

Deliverable

A person can speak to the Mirror daily and hear a calm reply; the day's record is stored locally.

Acceptance

First-token < 2 s; zero nag at startup; idle battery < 1%/day; no feed, ≤1 notification, fully disableable.

Fixtures

conformance/no_nag.json; benchmarks/first_token_latency, benchmarks/idle_battery.

Pitfalls
  • Performed warmth. Manifestation: the TTS voice sounds bright/enthusiastic. Root cause: engagement-coded voice defaults. Debug: A/B-free review of the voice palette against Appendix M. Signal: design-partner reports it feels "salesy." Recovery: revert to the low-affect palette; fail Vow review (P1).
  • Notification creep. Manifestation: more than one prompt/day. Root cause: a re-engagement reflex. Debug: no_nag.json fixture. Signal: notification count > 1. Recovery: hard-cap at one, fully disableable (§4).
  • A "home feed". Manifestation: a scrollable surface appears. Root cause: importing app conventions. Debug: surface review against P12. Signal: any list-of-items UI. Recovery: restore the quiet placeholder (Appendix L).
  • Background-listening drain. Manifestation: battery > 1%/day idle. Root cause: always-on mic without consent. Debug: idle_battery benchmark. Signal: M4 regression. Recovery: gate listening behind explicit consent (I2).

⬜ Phase 2 — E2E Encryption Substrate + Consent Ledger (Personal MVP, part 2)

Objectives

Make the privacy promise real: libsodium content encryption, Argon2id KDF, hardware-backed key custody, optional ciphertext sync, and the append-only Consent Ledger that gates everything.

Deliverable

All user content encrypted at rest; nothing readable server-side; every action consent-gated.

Acceptance

Server store contains only ciphertext (I1); a capability with no ledger grant is unreachable (I2); subpoena test yields undecryptable bytes.

Fixtures

conformance/ciphertext_only.bin; conformance/consent_gate.json; fuzz/secretbox, fuzz/consent_ledger.

Pitfalls
  • Plaintext in logs/crash reports. Manifestation: content appears in a crash report. Root cause: an unscrubbed log path. Debug: vow-check content-in-telemetry scan. Signal: any content/derived field in telemetry (I8). Recovery: scrub; ship a fix; transparency note.
  • Gate bypass. Manifestation: a capability runs without a grant. Root cause: a code path that skips the consent gate. Debug: consent_gate.json; ledger-vs-action diff. Signal: an action with no matching grant (I2). Recovery: deny; patch the gate (MM3).
  • Weak passphrase UX. Manifestation: users pick guessable passphrases. Root cause: no honest loss-warning or strength guidance. Debug: onboarding review (Appendix K). Signal: low-entropy passphrases. Recovery: strengthen guidance; offer Shamir recovery (ADR-08).
  • Argon2id mis-tuned. Manifestation: unlock too slow or too weak. Root cause: cost params off the M8 target. Debug: unlock-latency benchmark (C6). Signal: M8 breach. Recovery: re-tune memory-hardness toward the 1.5 s budget.

⬜ Phase 3 — Memory Core: tiered summary + retrieval + cryptographic forgetting (MVP complete)

Objectives

Give the Mirror decade-scale memory: tiered rolling summary, per-turn retrieval, and provable forgetting.

Deliverable

The Mirror remembers across sessions, answers "what did I say about X?", and truly forgets on request.

Acceptance

After "forget this," the content is unrecoverable (I3); inference sees no long-term plaintext beyond the turn (I4); retrieval relevance validated with design partners.

Fixtures

conformance/forget_proof.json; conformance/no_longterm_plaintext_egress.json; retrieval-quality fixtures.

Pitfalls
  • Summary leaks deleted content. Manifestation: a forgotten detail resurfaces in a summary. Root cause: down-tiering copied content before the key was destroyed. Debug: forget_proof.json over buffer + summaries + sync. Signal: post-forget recoverable bytes > 0 (M10). Recovery: destroy the key and purge derived summaries (I3; MM2).
  • Over-retrieval. Manifestation: prompt exceeds the 8 KB slice. Root cause: retrieval pulls too many shards. Debug: no_longterm_plaintext_egress.json; payload meter. Signal: M9 breach. Recovery: tighten the retrieval policy (Appendix AL; MM5).
  • Tier-aging loses marked shards. Manifestation: a "remember this" memory vanishes. Root cause: aging job ignored the MARKED flag. Debug: tier-transition fixtures (Appendix W). Signal: a MARKED shard down-tiered/aged out. Recovery: restore from sync; fix the aging guard.
  • Retrieval corruption. Manifestation: a shard fails to decrypt. Root cause: storage/sync error. Debug: integrity check on read. Signal: AEAD verification failure. Recovery: restore the blob from ciphertext sync; surface nothing partial.

⬜ Phase 4 — Pattern Surfacer (Deepening, part 1)

Objectives

Occasionally, gently, quote the user back to themselves about a recurring theme — opt-in, ≤1/month, never alarming.

Deliverable

At most monthly, the Mirror says "you have spoken of your father 11 times this year — would you like to sit with that?"

Acceptance

Rate ≤1/month; quotation-only (no interpretation-as-instruction, I11); fully off unless consented; no nagging on "no".

Fixtures

conformance/surface_rate.json; conformance/quotation_only.json.

Pitfalls
  • Diagnosis drift. Manifestation: "you seem anxious." Root cause: interpretation dressed as fact. Debug: quotation_only.json; output audit. Signal: a claim that is not a quotation with citation. Recovery: block; correct the surfacer prompt (I11; P2).
  • Over-surfacing. Manifestation: more than one surface/month. Root cause: confidence threshold too low. Debug: surface_rate.json. Signal: M12 breach. Recovery: raise the threshold; pick a single theme/month.
  • Ungentle painful theme. Manifestation: a grief/self-harm theme surfaced bluntly. Root cause: missing extra-gentleness gate. Debug: red-team on sensitive themes. Signal: partner distress report. Recovery: route sensitive themes through the crisis posture (§8.3; Appendix Q).
  • Nagging on "no". Manifestation: a declined theme reappears. Root cause: follow-up after decline. Debug: review accept/decline handling. Signal: a re-offer after DECLINED. Recovery: accept the answer without follow-up (P1).

⬜ Phase 5 — Yearly Review Ritual (Deepening, part 2)

Objectives

A once-a-year structured walk-back through the year's themes, on a date the user chose, letting them mark, archive, or release each.

Deliverable

An annual ritual the user can complete in one sitting, leaving them with a chosen relationship to the year.

Acceptance

Runs only on consent (YEARLY_REVIEW granted) and only on the chosen anniversary date; every "release" passes yearly_release_forgets.json with 0 post-release recoverable bytes (M10); no pressure to continue past a first decline.

Fixtures

conformance/yearly_release_forgets.json; anniversary-scheduling fixtures.

Pitfalls
  • Retention-event drift. Manifestation: the ritual is timed/framed to pull the user back. Root cause: an engagement reflex. Debug: Vow review of the ritual flow. Signal: any re-engagement framing. Recovery: keep it strictly annual on the user's chosen date (P1; P11).
  • Released themes resurface. Manifestation: a theme the user released reappears next year. Root cause: release did not destroy the key. Debug: yearly_release_forgets.json. Signal: M10 > 0 for released content. Recovery: block release until the key-destroy path is proven (I3; MM2).
  • Theme overload. Manifestation: the walk-back overwhelms the user. Root cause: too many themes surfaced at once. Debug: review the assembled THEMATIC set. Signal: partner reports it as exhausting. Recovery: pace deliberately; allow stopping any time without nag.
  • Mid-ritual abandonment. Manifestation: the user leaves partway. Root cause: length/pacing. Debug: resume-flow review. Signal: an incomplete ritual. Recovery: resume gently later; never pressure completion.

⬜ Phase 6 — Voice Clone (Legacy Mode) (Deepening, part 3)

Objectives

Opt-in voice cloning recorded explicitly for use after death by named loved ones; watermarked, legacy-context-locked, destroyable.

Deliverable

A user can record a legacy voice that, after death, can speak the messages they authored for named people.

Acceptance

Clone never used live or for general responses; clone_watermark.json and clone_context_locked.json pass with 0 violations; revocation destroys the clone within the same session (clone_destroy_on_revoke.json); usage confined to authorised legacy contexts.

Fixtures

conformance/clone_watermark.json; conformance/clone_destroy_on_revoke.json; conformance/clone_context_locked.json.

Pitfalls
  • Impersonation/fraud. Manifestation: the clone used to deceive. Root cause: missing context lock. Debug: clone_context_locked.json. Signal: clone invoked outside an authorised SuccessorPlan context. Recovery: block; cryptographic destroy on revoke (I10).
  • Clone leaks into general TTS. Manifestation: the legacy voice answers live. Root cause: the clone path not isolated. Debug: context-guard test. Signal: clone audio outside legacy context. Recovery: hard-isolate; fail the gate.
  • Used before death. Manifestation: the clone speaks while the user lives. Root cause: activation not gated on death verification. Debug: activation audit (I9). Signal: clone use with the user alive. Recovery: default-deny; require death verification (Phase 9).
  • Missing watermark. Manifestation: synthetic audio is indistinguishable from real. Root cause: watermark not embedded at creation. Debug: clone_watermark.json. Signal: no watermark present. Recovery: refuse to create/store an unwatermarked clone.
  • Attachment shock on change (real incident). Manifestation: bereaved users harmed when legacy-voice behavior changes abruptly. Root cause: the same dynamic as Replika's February 2023 removal of romantic/erotic roleplay — reported to follow an Italian Garante order — which caused widely-reported distress in users attached to the prior behavior (§Failure Modes & Recovery). Debug: review any persona/voice-affecting change against MM7. Signal: a change to a clone's behavior shipped without advance notice. Recovery: freeze the change; restore prior behavior; communicate in advance; the Mirror has no engagement loop whose protection would tempt such a change (P1).

⬜ Phase 7 — Bridging Protocol (Mirrors Meet, project Phase 3)

Objectives

Let two consented Mirrors exchange exactly one structured letter each, translating what the humans cannot say — never a free-form Mirror-to-Mirror chat.

Deliverable

A husband and wife (or estranged parent/child) each receive a letter from their own Mirror translating the other's hidden truth.

Acceptance

Both consents present + recent (I5); coordinator logs nothing (I6); no free-form chat; letters stored only on the two devices; revocable before open.

Fixtures

conformance/bridging_double_consent.json; conformance/coordinator_no_log.json; conformance/no_freeform_chat.json.

Pitfalls
  • One party surveils/manipulates the other. Manifestation: a letter is used to extract or pressure. Root cause: free-form content or scope creep. Debug: no_freeform_chat.json; letter-structure check (Appendix X). Signal: content outside the four bounded parts or the consented scope. Recovery: abort; gate the session type (P13; I5).
  • Coordinator logs "for debugging". Manifestation: letters retained server-side. Root cause: a well-meaning log statement. Debug: coordinator_no_log.json. Signal: M15 > 0 retained bytes. Recovery: strip logging; the coordinator holds zero state by design (I6; MM8).
  • Letters exceed consented scope. Manifestation: a letter reveals unconsented content. Root cause: composer drew from beyond the bridging-consented set. Debug: scope audit against the consent grant. Signal: content not in the BRIDGING_WITH_USER scope. Recovery: block before exchange; re-derive from consented content only.
  • Coercive relationship. Manifestation: consent is given under pressure. Root cause: a power imbalance the recency window cannot see. Debug: high-risk session-type gating. Signal: therapist-partner flag. Recovery: route high-risk topics through clinician-in-the-loop gating (P14).

⬜ Phase 8 — Continuity Infrastructure (founder-mortality, trustee, open-source/export tooling)

Objectives

Make the Vow's "survive the founder" and "open-source on sale/wind-down" clauses real and tested before Phase 9.

Deliverable

A tested ability for the service to survive the founder and to open-source + export on trigger.

Acceptance

Continuity drill succeeds without founder involvement within the ≤72-hour recovery bound (M16); portable_export_roundtrip.json passes with 0 lost records; trustee named and ≥5-year funding reserve documented (ADR-29).

Fixtures

conformance/portable_export_roundtrip.json; continuity-drill report.

Pitfalls
  • Single-founder key dependency. Manifestation: only the founder can access operational keys. Root cause: the sealed envelope was described but never actually created or tested. Debug: a continuity-drill dry run (Appendix AB). Signal: the drill fails without the founder present. Recovery: complete the sealed envelope and retest before Phase 4 begins (ADR-29).
  • Export format loses content. Manifestation: a portable export silently omits shards or successor plans. Root cause: scripts/export.sh drifted from core/schema after a schema change. Debug: portable_export_roundtrip.json. Signal: the round-trip diff shows missing records. Recovery: version the export format; block release until the round-trip is lossless.
  • Aspirational charter clauses. Manifestation: the charter reads well but has no enforcement mechanism an acquirer's lawyers must honour. Root cause: drafted without perpetual-purpose-trust legal review. Debug: counsel review against real trust/foundation law (Appendix F). Signal: a clause a hostile acquirer's counsel could void. Recovery: rewrite with counsel until the clause is enforceable, not just aspirational (ADR-25).

⬜ Phase 9 — Continuation Across Death (project Phase 4)

Objectives

After a user's death, let designated loved ones — strictly within what the user authorised while living — read or dialogue with the Mirror, or (with legal documentation) inherit it.

Deliverable

A dying mother's Mirror can continue speaking to her son, carrying her authored words, within her living consent.

Acceptance

No access without living-consent reaffirmation (I9); scope strictly bounded by authorization; contested/fraudulent death → default-deny.

Fixtures

conformance/successor_reaffirmation.json; conformance/death_verification_default_deny.json; access-scope fixtures.

Pitfalls
  • Weaponised access. Manifestation: a successor uses granted access to surveil or control others rather than to honour the deceased. Root cause: access_kind scoped too broadly for the relationship. Debug: review against the access-scope fixtures. Signal: access used outside the letter's stated purpose (Risk #18). Recovery: revoke; narrow access_kind; refer to counsel (Appendix F).
  • Fraudulent death claims. Manifestation: activation is triggered by an unverified or forged death claim. Root cause: single-channel verification instead of the mandated multi-channel check. Debug: death_verification_default_deny.json. Signal: activation proceeds without independent confirmation. Recovery: default-deny; require multi-channel verification before any access (I9).
  • Scope creep beyond authorization. Manifestation: a successor requests a capability the user never granted (e.g., editing rather than reading). Root cause: access_kind not enforced at the API boundary. Debug: access-scope audit. Signal: a mutation attempted under READ_ONLY_AFTER_DEATH. Recovery: deny; log; escalate to counsel-on-call.
