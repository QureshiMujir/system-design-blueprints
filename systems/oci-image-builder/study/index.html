Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Reproducibility boundary conditions: Under what exact conditions does forge guarantee bit-identical output, and what breaks that guarantee even with identical Dockerfile and context? (P4 + §15 forge-tar determinism pitfalls + §4 SOURCE_DATE_EPOCH)
  2. CAS and GC race safety: Describe the window in which a concurrent GC sweep can delete a blob that a new ingest session is about to commit, and exactly which API call order in forge-cas eliminates this window. (§13 Lease/GC-root-set pitfall + I-11 + MM7)
  3. Vertex digest stability across serialization: Why is BTreeMap key ordering necessary in vertex_bytes, and what is the exact failure mode if HashMap is used instead? (§16 forge-llb implementation + P4 + P11 + MM3)
  4. CacheKey compositionality and base image staleness: A Dockerfile has FROM ubuntu:22.04. How does forge detect that the upstream Ubuntu image has been updated, and what must the solver do at solve-start to ensure cache invalidation? (§21 invalidation + tag-to-digest pitfall + I-6 + MM8)
  5. diff_id vs layer digest — when they diverge and why: A consumer rejects an image saying "diff_ids don't match layers". Trace the exact computation of both values and identify two distinct code sites where they could diverge if implemented incorrectly. (§8.1 + §15 LayerBuilder::finish + I-2 + I-3)
  6. Overlayfs fallback triggers and their consequences: List all runtime conditions that force forge-snapshot to fall back from OverlaySnapshotter to CopySnapshotter, and explain how this fallback affects build correctness, performance, and the scalability model. (§18 pitfalls + Scalability Analysis + §4 + C11)
  7. Push order and manifest atomicity: A CI pipeline pushes the same image from two parallel build jobs. Describe the race condition in manifest PUT and whether forge's pre-push checklist (P9) prevents it. (§22 push-order pitfall + I-7 + P9 + MM5)
  8. Multi-stage build cache sharing: In a multi-stage Dockerfile, stage 2 uses COPY --from=stage1 /bin/app /. Under what conditions does forge reuse a cached snapshot from stage 1 across two sequential builds, and when does it not? (§17 COPY --from resolution + §21 CacheKey::for_copy + §8.3 + MM2)
  9. Whiteout completeness and opaque directory semantics: A RUN step deletes /etc/foo/ entirely and creates a new /etc/foo/ with different contents. What exact sequence of tar entries must forge emit, in what order, and why does omitting the opaque whiteout cause incorrect behavior in docker run? (§8.4 + §18 opaque-dir detection + §15 whiteout round-trip + MM4)
  10. Bearer token security model: A bearer token expires mid-build during a 20-layer parallel push. Trace exactly what happens: which component detects expiry, when re-auth is triggered, and whether in-flight PATCH uploads for the chunked upload are affected. (§22 auth.rs token cache + token-expiry edge case + I-12)
  11. Async/sync boundary correctness: Which forge crates perform blocking I/O that must not be called directly from a Tokio async task, and what is the correct mechanism to cross that boundary? Name a specific hot path where a naive implementation would deadlock or starve the executor. (A-02 + §13 forge-cas streaming ingest + Performance Engineering + MM9)
  12. Chunked upload resume correctness: After a network interruption at byte 40 MB of a 100 MB blob, the client must resume the PATCH. Describe the exact HTTP exchange — which requests, which headers, what byte ranges — and why using the client's local write position rather than the server's acknowledged offset causes silent data corruption. (§22 ChunkedUploader resume + RFC 7233 (§5) + MM10)
  13. Fuzz safety guarantees and OOM risk: The fuzz targets assert "no panic", but a forge-tar reader that allocates Vec<TarEntry> proportional to untrusted entry count would OOM the fuzzer. Explain the specific allocation invariant forge-tar must maintain when reading untrusted bytes and how fuzz_tar_reader.rs detects OOM as a failure. (§24 fuzz pitfalls + §15 forge-tar reader + I-8)
  14. Differential test equality conditions: forge's conformance/differential/compare.sh asserts diff_ids == buildah output. Under exactly what normalization conditions can this hold, given two independent implementations? What must both tools agree on for diff_ids to be bit-identical? (§24 differential pitfalls + P4 + §4 SOURCE_DATE_EPOCH/uid normalization)
  15. Solver parallelism and determinism: The solver runs vertices in parallel via tokio::spawn per ready vertex. Is the resulting OCI image deterministic across runs with different concurrency schedules? Justify by tracing data flow from parallel ExecOp completions to the final config.rootfs.diff_ids array. (§20 solver dispatch + diff_ids-ordering pitfall + I-5 + I-9 + §8.7)
  16. CAS mark-sweep root set completeness: Name every source of CAS roots that forge's GC must include in the root set to avoid deleting a live blob. For each, identify the data structure that carries it and the API that adds/removes it. (§13 gc.rs + Lease + I-11 + §21 WAL refcount durability)
  17. Remote cache namespace collision: Two teams share a single cache registry. Team A's build for project X and team B's build for project Y produce the same CacheKey for a SourceOp (same base image, same platform). Does this produce incorrect behavior, and what does forge's namespace isolation prevent or fail to prevent? (§23 remote-cache namespace pitfall + §21 CacheKey computation + MM8)
  18. Incremental multi-platform build: A developer changes one RUN step in a multi-stage, multi-platform Dockerfile. Which vertices are invalidated for which platforms, and how many registry round-trips does forge make in the best case? (§23 multi-platform solve + §21 CacheKey::for_vertex + §17 ARG/ENV scoping)
  19. OCI spec conformance vs Docker compatibility: A consumer using containerd rejects an image that docker pull accepts. What class of incompatibilities causes this, and how does forge-oci's explicit conversion layer prevent producing images that satisfy one but not the other? (§14 convert.rs + §14 pitfalls + P14)
  20. Solver deadlock conditions: Describe a pathological LLB DAG that deadlocks the solver even with a correct Kahn topo-sort, given a bounded concurrency semaphore. What is the minimum semaphore size relative to the maximum fan-in of any vertex that prevents deadlock? (§16 Definition::topo_sort + §20 solver parallel dispatch + Failure Modes and Recovery)

Mental Models & First Principles

The compressed intuitions an expert holds about container-image building. Each: the insight, what it predicts, the bug class you write without it, and where this blueprint applies it.

  • MM1 — A blob's content address is its identity, not its location. A blob's sha256 digest names it; a copy that hashes differently is a different object, so a "wrong copy" is a category error. Predicts: every read of CAS is self-verifiable without out-of-band metadata; corruption is detectable at read time, not silent. Bug without it: trusting a file at blobs/sha256/<x> without verifying its content hashes to <x>, allowing silent bit-rot to flow into a built image. Applied: §13 (forge-cas DigestVerifyingReader at every get(), I-1), §15 (forge-tar dual-stream hashing, I-2/I-3), §8.1.
  • MM2 — A DAG vertex digest is a reproducibility proof, computed not assigned. vertex_digest = sha256(op_bytes + sorted(input_digests)) makes the same operations on the same inputs yield the same digest, so the digest is the cache key by construction. Predicts: any upstream change propagates to every downstream vertex digest automatically — no manual invalidation list. Bug without it: ad-hoc string cache keys that miss transitive dependencies and serve stale layers. Applied: §16 (forge-llb vertex_digest, §8.3), §21 (forge-cache CacheKey::for_vertex), P11.
  • MM3 — Determinism requires a total ordering on every variable, not most of them. Non-determinism hides in any unordered set: filesystem enumeration order, HashMap iteration, mtime sub-second precision, compression-library version. One un-frozen variable is enough to break reproducibility. Predicts: a single un-normalized field produces a digest that diverges on some platform, invisibly until a cross-arch diff. Bug without it: builds that reproduce on the author's machine but drift in CI. Applied: §15 (forge-tar path sort + SOURCE_DATE_EPOCH, P4, I-9), §16 (BTreeMap canonical JSON, A-04).
  • MM4 — Layer stacking is order-sensitive, and whiteouts are the delete protocol. OCI consumers apply layers base→top; a file is "deleted" only when a .wh.<name> entry appears in a later layer, and the .wh..wh..opq sentinel must precede all other entries in its directory. Predicts: wrong layer order or a missing whiteout yields a silently-wrong image that validates but misbehaves at runtime. Bug without it: deleted files resurface after docker run. Applied: §15 (forge-tar whiteout entries, §8.4), §18 (forge-snapshot differ, I-10).
  • MM5 — Registry push order is a strict protocol invariant, not an optimization. A registry validates a manifest PUT by checking that every referenced blob and config Descriptor already exists; a missing blob causes a 400 and leaves a partially-uploaded image in an undefined state. Predicts: manifest-first always breaks; blobs-then-config-then-manifest always works. Bug without it: intermittent "manifest references unknown blobs" errors under concurrent push. Applied: §22 (forge-registry pre-push checklist, P9, I-7).
  • MM6 — User namespaces remap privilege, they do not grant it. CLONE_NEWUSER gives uid 0 inside the namespace mapping to an unprivileged uid outside; in-namespace capabilities are bounded by the outer uid's capabilities. Predicts: pivot_root, overlayfs, and bind-mount inside a user ns carry kernel-version-gated restrictions (EPERM on old kernels). Bug without it: assuming clone(CLONE_NEWUSER) confers host-root powers, then failing mysteriously in restricted CI. Applied: §19 (forge-exec LinuxExecutor, P10, Phase 7 Pitfalls).
  • MM7 — CAS GC safety requires acquiring a lease before the ingest session begins. If GC runs between "decide to ingest" and "create the temp file", a freshly-written but not-yet-referenced blob can be swept; the lease must precede begin_ingest, not follow commit. Predicts: GC racing a lease-less concurrent ingest deletes live blobs under load. Bug without it: intermittent DigestMismatch on builds that trigger GC mid-solve. Applied: §13 (forge-cas Lease, I-11, Phase 1 Pitfalls), §21 (WAL refcount durability).
  • MM8 — A solve cache key must absorb the upstream registry digest, not just the tag. FROM ubuntu:22.04 is a mutable tag whose underlying manifest digest changes when the publisher pushes an update; a SourceOp CacheKey keyed only on the tag string serves the old base after an upstream change. Predicts: stale-base builds that pass CI yet ship un-patched layers. Bug without it: undetected base-image drift across rebuilds. Applied: §21 (forge-cache SourceOp CacheKey with resolved manifest digest, Phase 9 invalidation rules), P11.
  • MM9 — The async/sync boundary must be explicit, never implicit. Tokio's executor must not run synchronous CPU-heavy or blocking I/O in an async task; CAS/tar/digest hot paths cross into spawn_blocking. Predicts: one blocking call in an async task starves the executor thread pool and spikes latency across unrelated futures. Bug without it: forge push hangs intermittently while sha2::update monopolizes an executor thread during a large-layer hash. Applied: §13 (forge-cas streaming ingest spawn_blocking boundary), §20 (solver tokio::spawn per vertex, A-02).
  • MM10 — Chunked-upload resume must use the server's acknowledged offset, not the client's guess. After a mid-PATCH interruption the server has buffered some bytes; the client GETs the upload URL to learn the acknowledged offset and resumes PATCH from there, not from the last locally-sent position. Predicts: resuming from a client-side position yields a 416 Range Not Satisfiable or silent server-side corruption. Bug without it: failed retries that restart the whole upload instead of resuming. Applied: §22 (forge-registry ChunkedUploader resume, RFC 7233, Phase 10 Implementation Steps).

Required reading (§5)

Books

  • Container Security — Liz Rice (O'Reilly 2020) — namespaces, cgroups, rootless, image anatomy. → applied in Phase 7 (forge-exec LinuxExecutor user namespace setup, §19) and Threat Model (sandbox escape mitigation).
  • Systems Performance — Brendan Gregg (2nd ed.) — throughput/latency analysis for hashing pipelines. → applied in Phase 3 (forge-tar TeeWriter pipeline, §4 throughput targets) and Performance Engineering (flamegraph profiling guidance).
  • The Rust Programming Language — Klabnik & Nichols — ownership model for streaming I/O and unsafe boundaries. → applied in Phase 1 (forge-cas IngestSession ownership contract, Lease Drop semantics) and Phase 7 (forge-exec unsafe syscall wrappers via nix crate).
  • Designing Data-Intensive Applications — Kleppmann — CAS, content addressing, GC patterns. → applied in Phase 1 (forge-cas mark-sweep GC design, refcount WAL durability, §13) and Phase 9 (forge-cache sled WAL upgrade).
  • Programming Rust — Blandy, Orendorff, Tindall — async + sync boundary, trait objects, error taxonomy. → applied in Phase 8 (forge-build Solver async dispatch with spawn_blocking, ADR A-02) and §11 Core Schema (ForgeError sum type design).
  • The Linux Programming Interface — Michael Kerrisk (No Starch Press 2010) — ch. 28 (process creation / clone flags), ch. 14 & 18 (filesystems, mount, pivot_root); extract the exact semantics of CLONE_NEWUSER/CLONE_NEWNS/CLONE_NEWPID, uid/gid map writing, and mount-propagation flags. → applied in Phase 7 (forge-exec namespace.rs uid/gid map + mount-ns setup, §19) and Phase 6 (forge-snapshot overlay mount semantics, §18).

Papers

  • Viennot et al. Reproducible Builds (2015) — determinism requirements, timestamp normalization. → applied in Phase 3 (forge-tar SOURCE_DATE_EPOCH normalization, P4, I-9) and Phase 12 (differential conformance test against buildah).
  • Benet IPFS — Content Addressed, Versioned, P2P File System (2014) — CAS design, Merkle DAG. → applied in Phase 1 (forge-cas blob naming by digest, §8.1 Content-Addressing Model) and Phase 4 (forge-llb vertex_digest as Merkle DAG node).
  • Cantrill Observability in Distributed Systems (USENIX 2019) — tracing async solver paths. → applied in Phase 8 (forge-build tracing spans per vertex, A-15) and Operational Readiness (monitoring signals, structured log fields).
  • Turner HTTP Range Requests (RFC 7233) — chunked upload range semantics. → applied in Phase 10 (forge-registry ChunkedUploader Content-Range PATCH/PUT, §22 chunked.rs).
  • Kemerlis et al. kGuard — sandbox escape taxonomy (relevant to forge-exec threat model). → applied in Threat Model (sandbox escape mitigation entry) and Phase 7 (forge-exec network mode isolation, §19 Pitfalls).
  • Bernstein Networking and Cryptography Library — constant-time comparison for digest verification. → applied in Phase 1 (forge-digest DigestVerifyingReader constant-time finalize comparison, §13 Implementation Steps) and §7 Invariants (I-1 CAS correctness).
  • OCI Image Spec authors — OCI Image Layout spec design rationale (GitHub oci/image-spec wiki). → applied in Phase 2 (forge-oci layout.rs write_oci_layout, §14) and Phase 0 (oci-layout marker file, §12 Pitfalls).
  • Agarwal et al. CRAQ — read/write consistency in replicated blob stores (background for remote cache). → applied in Phase 11 (forge-cache RemoteCacheBackend consistency model, §23 remote cache design rationale).

Glossary · 37 terms · site-wide glossary

OCI image layout
On-disk format: blobs/sha256/<hex>, oci-layout, index.json
Image manifest
JSON document listing config + layer Descriptors; media type vnd.oci.image.manifest.v1+json
Image index
JSON document listing per-platform manifest Descriptors; multi-arch entry point
Image config
JSON document with architecture, os, ContainerConfig, rootfs.diff_ids, history
Descriptor
{mediaType, digest, size, [urls, annotations, platform]} — reference to a blob
Media type
MIME-like string identifying blob format (manifest, index, config, layer)
Blob
Arbitrary bytes stored in CAS addressed by sha256 digest
Layer
A gzip or zstd compressed tar archive representing a filesystem changeset
diff_id
sha256(uncompressed layer tar stream) — stored in config.rootfs.diff_ids
Layer digest
sha256(compressed layer blob) — used in manifest.layers[].digest and as blob name in CAS
Content-addressable storage (CAS)
Store where blobs are named by their content digest; write-once, immutable
LLB / build definition
Low-Level Build: content-addressed DAG of Ops representing a build
Vertex
A node in the LLB DAG; {digest, op, inputs[], platform}
Op
An operation in the LLB DAG: SourceOp, ExecOp, FileOp, MergeOp, DiffOp
Solve
Process of executing the LLB DAG: resolve cache, exec ops, produce layers
Snapshotter
Abstraction for managing filesystem snapshots: prepare, commit, diff
Snapshot
A point-in-time filesystem state, either committed (read-only) or writable
Differ
Component that computes the ChangeSet between two snapshots
ChangeSet
Set of `{path, kind: Add
Whiteout
Special tar entry .wh.<name> indicating a file deletion in a layer
Opaque directory
.wh..wh..opq tar entry indicating complete directory replacement in a layer
Deterministic build
Build where same inputs → bit-identical output digests across machines and runs
SOURCE_DATE_EPOCH
Unix timestamp (env var) used to normalize file mtimes for reproducibility
Solve cache
Index mapping CacheKey → (SnapshotId, layer Descriptor); skips exec on hit
Cache key
sha256(op_def, sorted(input_CacheKeys), platform) — uniquely identifies a vertex's inputs
Remote cache
Cache backend backed by a registry; enables cross-machine cache sharing
Cross-repo mount
Registry API: mount a blob from one repository to another without re-uploading
Chunked blob upload
OCI Distribution upload protocol: POST → PATCH(Content-Range) → PUT(?digest=)
Bearer token
Short-lived auth token obtained from registry auth server via WWW-Authenticate flow
Frontend
Component that parses a build definition (Dockerfile, native) into an LLB Definition
Multi-stage build
Dockerfile with multiple FROM instructions; intermediate stages used as inputs
Build arg
User-supplied --build-arg KEY=VALUE overriding ARG defaults in Dockerfile
Exporter
Component that emits build result: OciLayout, DockerArchive, or RegistryPush
Rootless
Build/exec without host root privileges; relies on user namespace uid/gid mapping
Image ID
sha256(image config JSON bytes) — uniquely identifies an image config
Ingest session
Temporary CAS write session; commit atomically renames temp to blob path
Lease
Object holding CAS refcounts for a set of blobs; Drop releases refs; prevents GC
