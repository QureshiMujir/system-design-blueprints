273 — OCI Image Builder

Project Number: 273

Project Name: OCI Image Builder

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

Goal: Build a from-scratch, daemonless, rootless-capable OCI container-image builder in Rust — no Docker daemon, no BuildKit gRPC plane — that parses Dockerfile / native declarative syntax into a content-addressed LLB Op DAG, solves it (resolving base images, sandboxing RUN steps, snapshotting filesystems), produces deterministic/reproducible layer tarballs, assembles OCI image manifests + indexes, stores blobs in a local CAS, and pushes/pulls via the OCI Distribution Spec.

1. Goal

Precise definition: Rust workspace binary (forge) + library ecosystem that builds OCI-compliant container images without a running daemon. Inputs: Dockerfile or native declarative file + build context. Output: OCI image layout on disk, docker-archive tar, or registry push. All layer digests are deterministic (bit-identical on clean rebuild of same inputs).

System boundary:

  • In: build context (files), Dockerfile / native manifest, registry credentials, platform target, cache backend config.
  • Out: OCI image layout (blobs/, index.json), docker-archive tar, registry push receipt (digest).
  • Interfaces: OCI Distribution API (pull base + push result), local CAS, optional remote cache registry.

Non-goals (explicit):

  • Container runtime / exec of the built image → #35 (exec only during RUN solve; no runc/containerd integration beyond that).
  • Registry server / repository hosting → #166 (client only).
  • Orchestration / scheduling of built images → #268.
  • General build system / monorepo tooling → #136, #272 (borrow CAS ideas, don't implement).
  • Image signing UI (cosign/notation) → PhaseDeferred("Deferred Features Register").
  • SBOM generation beyond OCI annotations → PhaseDeferred("Deferred Features Register").
  • Windows containers (build-time stubs only) → PhaseDeferred("Deferred Features Register").

Deployment model: single statically-linked binary; no root required (user namespaces); no background service. Embed all library crates in workspace. Optional rootless mode via newuidmap/newgidmap helpers.

Target users: CI/CD pipeline operators, platform engineers, security-focused build toolchain authors needing reproducible daemonless image builds.

Phase-0 deliverable — 12 workspace crates (locked order):

  1. forge-digest — Digest/Descriptor types, canonical-JSON hashing, verifying I/O wrappers.
  2. forge-cas — local content store: ingest, address, refcount, mark-sweep GC, leases.
  3. forge-oci — OCI Image Spec types + image layout: manifest, index, config, media types, read/write, Docker v2s2↔OCI conversion.
  4. forge-tar — deterministic layer tar: canonical ordering, SOURCE_DATE_EPOCH, gzip/zstd, whiteouts, diff_id vs layer digest.
  5. forge-llb — build IR DAG: Op, Vertex, Definition, topological solve order, content-addressed vertex digests.
  6. forge-frontend — Dockerfile lexer + parser → LLB; native declarative frontend; all instructions; multi-stage; .dockerignore; heredocs; ARG/ENV scoping.
  7. forge-snapshot — Snapshotter trait: prepare/commit/diff, overlay mount, changeset → forge-tar layer, whiteout generation, portable fallback.
  8. forge-exec — sandboxed RUN executor: rootfs assembly, namespaces/chroot, env/cwd/user, capture upper diff; Linux real, others stub.
  9. forge-cache — solve cache: CacheKey, local cache index, COPY/ADD content hashing, invalidation rules, prune.
  10. forge-registry — OCI Distribution client: pull/push manifests+blobs, chunked upload, cross-repo mount, bearer auth, retries.
  11. forge-build — solver/orchestrator: schedules LLB DAG, wires exec+snapshot+cache, assembles config+manifest+index, exporters.
  12. forge-cli — forge binary: build, parse, inspect, push, pull, cache, gc subcommands.

Later phases unlock: remote cache (registry-backed), multi-platform builds + ImageIndex, OCI distribution conformance, differential correctness testing vs buildah/skopeo, fuzzing, benchmarks.

Timeline: Phase 0 skeleton 1 wk; Phases 1–8 core stack 6–10 wks; Phases 9–11 cache + registry + multi-platform 3–5 wks; Phase 12 conformance + fuzz + bench 2 wks. Total: ~14–18 wks.

Language: Rust 2021, MSRV 1.78. Async Tokio for registry/network I/O; sync for CAS/tar/solve hot paths. sha2, flate2, zstd, tar, reqwest/hyper, serde_json, tokio.

Rejected languages: Go (canonical — BuildKit/buildah/kaniko are Go — weaker sum types, no exhaustive Op/MediaType matching); C/C++ (unsafe on untrusted bytes); Python (too slow for layer hashing).

Prerequisites: Linux kernel ≥ 4.18 (user namespaces, overlayfs in user ns); Rust toolchain MSRV 1.78; newuidmap/newgidmap for rootless; cargo-deny, cargo-fuzz, cargo-criterion in CI.

2. Why Build This

Unique systems knowledge:

  • Content-addressed immutable blob store design (CAS) with reference counting and mark-sweep GC across live and transient leases.
  • Deterministic tar production: path-sorted entries, SOURCE_DATE_EPOCH mtime normalization, uid/gid stripping, fixed compression levels → bit-identical layer digests across machines.
  • LLB-style DAG IR: content-addressed vertex digests, topo-sort, dedup by CacheKey (vertex-op + input chain + platform hash), cache-hit fast-path skips exec entirely.
  • OCI Distribution Spec registry protocol: WWW-Authenticate bearer dance, chunked PATCH upload with Content-Range, cross-repo blob mounting, resumable upload after interruption.
  • Rootless sandbox execution: user namespace setup, uid/gid mapping, pivot_root or chroot, network modes, capturing overlay upper dir as changeset.
  • Whiteout semantics: .wh.<name> (delete), .wh..wh..opq (opaque dir replacement) — critical for correct layer stacking in consumers.

Historical/architectural significance: Direct lineage from BuildKit (LLB, content store, solve cache), buildah (rootless layer commit), kaniko (in-container snapshots) — distilled into a safe, auditable Rust codebase without gRPC control plane complexity. Demonstrates container image build infrastructure as a pure library, composable into CI runners, serverless build agents, or WASM host contexts.

Engineering muscles: streaming hash-while-write pipelines (no full-file buffering), async + sync boundary design, layered error taxonomy with ForgeError sum type, cross-layer invariant enforcement at type level.

Cross-links to portfolio projects:

  • #35 Container Runtime — shares rootfs assembly + namespace exec model; minimal subset reused in forge-exec.
  • #166 Container Registry — client of its OCI Distribution API; same bearer auth protocol.
  • #26 Git VCS + #71 Merkle Tree + #88 SHA-256 — content addressing lineage: blob name = digest of bytes, DAG vertex digest = hash of op + inputs.
  • #107 Object Storage + #109 Deduplication — CAS and layer dedup are object-storage patterns.
  • #136 Build System + #272 Artifact/Build Cache Server — CacheKey chaining, remote cache import/export.
  • #268 Kubernetes-like Orchestrator — consumes built images via OCI layout or registry push.
  • #50 Sandbox/Code Execution — RUN isolation: namespaces, chroot, seccomp.

Calibration value: highest-density intersection of systems programming (namespaces, overlayfs), distributed protocol (OCI Distribution), and correctness (reproducibility). Proves safe-systems competence at production container infrastructure level.

What Mastery Looks Like

  • Content-addressing and CAS design (Phase 1 — forge-digest + forge-cas): can design a write-once blob store with streaming ingest, digest verification, refcount leases, and mark-sweep GC; can reason about TOCTOU races at the GC boundary and specify the correct lease-before-ingest API contract.
  • Deterministic artifact production (Phase 3 — forge-tar): can enumerate every source of non-determinism in a tar stream (path ordering, mtime, uid/gid, xattr representation, compression level pinning, gzip header metadata) and implement a LayerBuilder that eliminates all of them; can explain why diff_id and layer digest are computed from different streams.
  • DAG IR and solve scheduling (Phases 4 + 8 — forge-llb + forge-build): can define a content-addressed DAG vertex format, implement Kahn's topological sort with cycle detection, and build a parallel solver that dispatches vertices to exec/snapshot/cache sub-systems in dependency order while maintaining deterministic diff_id ordering in the output.
  • Linux sandbox and namespace mechanics (Phase 7 — forge-exec): can set up a user namespace + mount namespace + PID namespace from scratch using clone() syscalls, write uid/gid maps, perform pivot_root, and explain the capability model inside a user namespace; can diagnose EPERM failures at each step and implement clean mount teardown on error paths.
  • OCI Distribution Spec registry protocol (Phase 10 — forge-registry): can implement the full bearer token WWW-Authenticate dance, chunked blob upload with Content-Range resume, cross-repo blob mounting, and manifest PUT ordering; can write mock-server tests that inject mid-upload failures and verify correct resume behavior.
  • Solve cache correctness and invalidation (Phase 9 — forge-cache): can specify a CacheKey scheme that compositionally captures all inputs including transitive upstream changes (base image digest, ENV/ARG values, COPY file content); can identify subtle invalidation gaps such as mutable tag drift and implement tag-to-digest resolution at solve-start.
  • Reproducibility verification and differential testing (Phase 12 — Conformance + Differential): can set up a differential test harness that compares diff_ids from two independent implementations, diagnose divergences to the specific normalization step that differs, and write fuzz targets that exercise all parser entry points without unbounded allocation.

forge-cli: Entry point; parses subcommands; loads config (credentials, cache backend, platform target); delegates to forge-build or forge-registry. Invariant: never touches raw blobs or CAS paths directly.

forge-frontend: Lexer + parser (Dockerfile DSL → token stream → AST → LLB Definition). Outputs Definition (Vec<Vertex>) with all vertex digests computed. Receives: build context path, ARG defaults, platform. Later phases: heredocs, multi-stage graph pruning.

forge-build (solver): Central scheduler. Topological walk of Definition; checks forge-cache per CacheKey; on miss dispatches to forge-exec (Exec ops) or forge-snapshot (File ops); chains outputs as snapshot inputs. Assembles ImageConfig (rootfs.diff_ids + history) and ImageManifest (layer Descriptors). Runs exporters. Invariant: all layer blobs committed to forge-cas before manifest assembly.

forge-cache: Computes CacheKey per vertex (op bytes + ordered input CacheKey chain + platform). Persists local index (sled). COPY/ADD: hashes copied-file content into key. On hit: returns (snapshot ref, layer Descriptor); solver skips exec.

forge-exec: Assembles rootfs from lower snapshot layers + writable upper dir; enters user namespace (or chroot); sets env/cwd/user; executes command; captures upper dir as changeset via forge-snapshot differ. Platform-gated: Linux full impl; macOS/Windows stub → ForgeError::Unsupported. Invariant: no exec output escapes upper dir.

forge-snapshot: Snapshotter trait + overlay-style commit. prepare(parent) → writable mount; commit(mount) → SnapshotId; diff(parent, child) → ChangeSet; ChangeSet feeds forge-tar. Linux: overlayfs lowerdir/upperdir/workdir. Portable fallback: copy tree + diff. Whiteout files emitted for deletions.

forge-tar: Accepts ChangeSet; emits deterministic tar: entries sorted by path, mtime = SOURCE_DATE_EPOCH, uid=0/gid=0, xattrs preserved as PAX headers, gzip (level 6) or zstd (level 3). Computes diff_id (sha256 uncompressed stream) and layer digest (sha256 compressed blob). Invariant: same ChangeSet → identical bytes.

forge-cas: Write-once blob store under blobs/sha256/<hex>. Ingest: stream-write to temp path, verify digest on close, rename atomically. Refcount table (in-memory + persisted). Mark-sweep GC: collect roots (live leases + index.json refs), sweep unreferenced blobs. Invariant: blob content never mutated after commit.

forge-oci: All OCI Image Spec types. Layout read/write (index.json, oci-layout marker, blobs/). Manifest + config JSON with stable key ordering (BTreeMap for annotations). Docker v2s2 ↔ OCI conversion. Validation: schema version, required fields, descriptor size/digest cross-check.

forge-registry: Async reqwest/hyper client implementing OCI Distribution Spec v1.1. pull_manifest → pull_blob (with digest verify); push_blob (HEAD skip / mono POST-PATCH-PUT / cross-repo mount); put_manifest. Bearer token cache. Retry with exponential backoff + jitter. Chunked upload: POST → PATCH(Content-Range) → PUT(?digest=).

forge-digest: Digest{algo, hex} Display sha256:<hex>; Descriptor{media_type, digest, size, ...}; DigestVerifyingReader (wraps any Read, rejects on mismatch at EOF); canonical_json_digest(T: Serialize) → Digest (BTreeMap-ordered keys, no trailing newline). Invariant: no Digest constructed from unverified hex without explicit Digest::parse → Result.

6. Design Principles

P1 — Content Over Identity: Every artifact (blob, manifest, config, vertex) named by sha256 digest. No mutable names. Violation: mutable CAS paths → cache corruption.

P2 — Streaming First, Buffering Exception: All large I/O (tar ingestion, blob pull/push, layer hashing) must be streaming; full-buffer only when unavoidable (e.g., manifest JSON < 1 MB). Violation: OOM on large layers.

P3 — Result-Only on Untrusted Input: Every path touching registry responses, tar headers, manifest JSON, build context returns Result<_, ForgeError> — no unwrap/panic. Violation: DoS via crafted tar/manifest.

P4 — Determinism as a First-Class Invariant: Same inputs + same platform → byte-identical output digests. Enforced by: SOURCE_DATE_EPOCH normalization, path-sorted tar entries, BTreeMap-ordered JSON, fixed compression levels. Violation: unreproducible cache hits; supply-chain trust breaks.

P5 — DAG Before Execution: All build decisions (stage order, cache lookup, op dedup) made on Definition DAG before any exec or I/O. No discovery during exec. Violation: non-deterministic solve order → flaky cache.

P6 — Layered Error Taxonomy: ForgeError has stable variant set (Parse, DigestMismatch, Unsupported, Registry, Sandbox, Io, CachePoison, Validation). Libraries return typed variants; CLI maps to exit codes + structured log. Violation: opaque errors hide root cause.

P7 — Platform Gating, Not Conditional Compilation Sprawl: forge-exec uses PlatformExecutor trait; Linux impl behind #[cfg(target_os = "linux")]; others return ForgeError::Unsupported. No scattered #[cfg] blocks in solver. Violation: silent wrong behavior on macOS.

P8 — CAS Immutability: Once a blob is committed to CAS (rename from temp), it is never overwritten. GC is the only deletion path. Violation: digest mismatch on reads → DigestMismatch.

P9 — Registry Push Order: Layer blobs + config blob must reach the registry before PUT manifest. Pre-push checklist in forge-registry. Violation: registry rejects manifest referencing unknown blobs → broken image.

P10 — Minimal Privilege: rootless by default (user namespaces); privilege never requested unless --privileged flag; uid/gid maps required for rootless exec. Violation: security boundary collapse in multi-tenant CI.

P11 — Cache Key Compositionality: CacheKey = hash(op_def_bytes, sorted(input_CacheKeys), platform_str). Chaining ensures any input change propagates to all downstream vertices. Violation: stale cache on input change.

P12 — No Daemon, No Socket: All state is on-disk (CAS, cache index) or in-process. No background service, no Unix socket. Violation: state corruption if two concurrent builds share CAS without file locking.

P13 — Separation of Diff and Exec: forge-exec only captures upper dir bytes; forge-snapshot converts to ChangeSet; forge-tar converts to layer bytes. No exec code touches tar or OCI types. Violation: exec leaking filesystem paths into manifest layer descriptions.

P14 — Spec Conformance Over Compatibility Hacks: Implement OCI spec exactly; add Docker v2s2 compatibility via explicit conversion layer (forge-oci), not spread across the codebase. Violation: non-conformant images rejected by strict consumers.

8. Domain Model — OCI Images, Layers, and the Build DAG

8.1 Content-Addressing Model

                               │
              forge-cas: blobs/sha256/<hex>  (write-once, atomic rename)
  • Blob name = sha256(<raw bytes>) — no exceptions.
  • diff_id = sha256(uncompressed tar stream) — stored in config.rootfs.diff_ids.
  • layer digest (manifest.layers[]) = sha256(compressed blob) — what is pushed to registry.
  • image ID = sha256(config JSON bytes).
  • manifest digest = sha256(manifest JSON bytes) — used as image reference by digest.
  • Vertex digest = sha256(proto/canonical-JSON of Op + sorted(input digests)).

8.3 LLB Op DAG

EBNF (Op grammar):

Definition  ::= { Vertex }
Vertex      ::= digest ":" Op "[" { InputRef } "]" Metadata
Op          ::= SourceOp | ExecOp | FileOp | MergeOp | DiffOp
SourceOp    ::= "source" Identifier Attrs
ExecOp      ::= "exec" Cmd Mounts Attrs
FileOp      ::= "file" { FileAction }
FileAction  ::= Copy SrcSelector DstPath Attrs
              | Mkdir DstPath Mode
              | Mkfile DstPath Mode Content
              | Rm DstPath
MergeOp     ::= "merge" { InputRef }
DiffOp      ::= "diff" InputRef InputRef
InputRef    ::= Digest "." OutputIndex
Attrs       ::= { Key "=" Value }

Dockerfile instructions → LLB Op mapping:

Instruction Op emitted Notes
FROM image SourceOp{identifier: docker-image://image} resolves via forge-registry pull
FROM scratch SourceOp{identifier: scratch} → empty vertex no registry pull
RUN cmd ExecOp{meta.args: ["/bin/sh","-c","cmd"]} sandbox via forge-exec
COPY src dst FileOp{Copy{src,dst,chown,chmod}} content-hashed into CacheKey
ADD url dst FileOp{Copy} + HTTP fetch SourceOp URL digest into CacheKey
ENV k=v updates ExecOp.platform.env propagates to downstream ops
ARG k resolves from build-args map; ARG before FROM → global
WORKDIR /x sets ExecOp.meta.cwd creates dir via Mkdir FileOp if not exists
USER u sets ExecOp.meta.user
ENTRYPOINT/CMD/LABEL/EXPOSE/VOLUME/STOPSIGNAL/HEALTHCHECK ImageConfig only; no Op emitted metadata-only → empty_layer history entry

8.4 Tar / Whiteout Layout

layer.tar (uncompressed, entries sorted lexicographically by full path):
  .wh..wh..opq          ← opaque dir: replace entire parent dir
  .wh.deletedfile       ← delete named file
  dir/                  ← directory entry (mode 0755, uid=0, mtime=SOURCE_DATE_EPOCH)
  dir/file              ← regular file (mode 0644, uid=0, mtime=SOURCE_DATE_EPOCH)
  dir/symlink -> target ← symlink entry

Rules: no hardlinks across layers; xattrs preserved as PAX extension headers; no numeric UID/GID in uname/gname fields (empty string).

8.5 State Transitions

CAS blob states:

[nonexistent] --ingest_start--> [ingesting/temp]
[ingesting/temp] --ingest_commit(digest_ok)--> [committed]
[ingesting/temp] --ingest_abort / digest_fail--> [nonexistent]
[committed] --refcount=0 + GC sweep--> [nonexistent]

Build solve states per vertex:

[pending] --cache_hit--> [done/cached]
[pending] --cache_miss--> [running] --exec_ok--> [done/built]
[running] --exec_fail--> [failed]
[done/*] --downstream ready--> unblocks child vertices

8.6 Worked Example — FROM ubuntu:22.04 + RUN apt-get update + COPY . /app

Vertex V0 (SourceOp, digest=sha256:aaa):
  op: source docker-image://ubuntu:22.04
  → registry pull → base layers L0,L1,L2 → CAS
  → CacheKey(V0) = hash("docker-image://ubuntu:22.04", platform)

Vertex V1 (ExecOp, digest=sha256:bbb, inputs=[V0.0]):
  op: exec ["/bin/sh","-c","apt-get update"]
  → cache miss → forge-exec → overlayfs {lower=L0+L1+L2, upper=empty}
  → run → upper dir diff → ChangeSet → forge-tar
  → L3(diff_id=sha256:ddd, layer_descriptor.digest=sha256:eee)
  → CacheKey(V1) = hash(exec_def, CacheKey(V0), "linux/amd64")

Vertex V2 (FileOp/Copy, digest=sha256:ccc, inputs=[V1.0]):
  op: copy {src: context/., dst: /app, uid=0}
  → content-hash copied files → CacheKey(V2) = hash(fileop_def, CacheKey(V1), {file_digests})
  → forge-snapshot diff → ChangeSet → forge-tar
  → L4(diff_id=sha256:fff, layer_descriptor.digest=sha256:ggg)

ImageConfig:
  rootfs.diff_ids: [sha256:d0, sha256:d1, sha256:d2, sha256:ddd, sha256:fff]
  history: [FROM ubuntu(empty_layer=false), RUN apt-get update, COPY . /app]

ImageManifest:
  config: Descriptor{digest=sha256(config_json_bytes)}
  layers: [L0,L1,L2,L3,L4] as Descriptor{digest=sha256(compressed_blob)}

manifest_digest = sha256(manifest_json_bytes)

13. Phase 1 — forge-digest + forge-cas

1.1 Objectives

1.2 Detailed Implementation Steps

  • verifying_io.rs: DigestVerifyingReader<R> — wraps R: Read; accumulates sha2::Sha256::update on each read() call; on EOF (read returns 0), calls finalize() and compares with expected Digest; returns ForgeError::DigestMismatch on mismatch. DigestVerifyingWriter<W> — same for write path. (P1/I-1/Bernstein NaCl — constant-time finalize comparison)
  • canonical_json.rs: serialize T to serde_json::Value; walk value tree converting Object maps to BTreeMap-ordered; re-serialize to compact string; sha256 of bytes. (P4/A-04 — deterministic JSON required for manifest digest and vertex digest)
  • forge-cas/ingest.rs: IngestSession::commit() — flush BufWriter; call hasher.finalize() → Digest; check expected == actual; fs::rename(tmp_path, blob_path); return Digest. (P8/I-1 — atomic rename is the CAS immutability guarantee; Kleppmann DDIA CAS chapter)
  • forge-cas/gc.rs: mark_sweep(roots: HashSet<Digest>) — list all files under blobs/sha256/; parse filenames as Digest; subtract roots from all; remove unreferenced; accumulate GcStats. (I-11/Kleppmann DDIA GC patterns — mark-sweep over reference graph)

  • Refcount: in-memory Mutex<HashMap<Digest, u32>>; persisted to refcounts.json on drop (WAL in Phase 9). (P8 — crash-safe refcount deferred to Phase 9 WAL upgrade)
  • ContentStore::gc() — acquires write lock on refcounts; builds root set from live leases + refcount > 0 entries; calls mark_sweep. (I-11/Benet IPFS — root set = live references graph)

15. Phase 3 — forge-tar

3.1 Objectives

  • Deterministic layer tar: path-sorted entries, SOURCE_DATE_EPOCH normalization, gzip/zstd at fixed levels, dual-stream hashing (diff_id = uncompressed sha256, layer digest = compressed sha256), whiteout generation/detection.

3.2 Detailed Implementation Steps

  • builder.rs: LayerBuilder::new(writer, compression, source_date_epoch) — sets up compression stream + sha2::Sha256 for both digests via TeeWriter pattern (uncompressed tee before compression). (P4/I-9/Viennot Reproducible Builds 2015 — TeeWriter is the canonical dual-hash pattern)
  • LayerBuilder::add_entry(entry) — buffer all TarEntry in Vec; sort on finish() by path (lexicographic byte-order sort). (MM3/P4 — total ordering on every variable; byte-order sort not locale-aware)
  • LayerBuilder::finish() — iterate sorted entries; for each: normalize mtime = source_date_epoch, uid = 0, gid = 0, uname = "", gname = ""; write tar header + content; simultaneously accumulate uncompressed sha256; after all entries: write two 512-byte zero end-of-archive blocks; finalize both hashers → diff_id (uncompressed) and descriptor.digest (compressed); return LayerResult. (OCI Image Spec v1.1 §6.1 layer format; I-2/I-3; A-25 SOURCE_DATE_EPOCH)
  • compression.rs: Gzip(level) wraps flate2::write::GzEncoder; Zstd(level) wraps zstd::Encoder; None passthrough. (A-06/A-07 — fixed level mandatory for determinism; pin Cargo.lock)
  • whiteout.rs: whiteout_name, opaque_name, is_whiteout, is_opaque. (OCI Image Spec v1.1 §6.1 whiteout spec; MM4; I-10)
  • reader.rs: LayerReader — iterates tar entries; validates no absolute paths; detects whiteouts; computes diff_id on the fly for verification. (P3/I-8 — Result-only on untrusted input; no unbounded Vec allocation per I-8 fuzz safety)
  • Tests: 3-entry layer → verify diff_id == sha256(uncompressed bytes); same layer built twice → identical diff_id and descriptor.digest; whiteout round-trip; absolute path rejected.

21. Phase 9 — forge-cache

9.1 Objectives

  • Production solve cache: CacheKey computation (vertex + COPY content hashing); local sled-backed CacheBackend; instruction-level invalidation rules; prune; WAL-based refcount durability.

9.2 Detailed Implementation Steps

  • key.rs: CacheKey::for_vertex(op, input_keys, platform) — sha256 of {op_canonical_bytes, sorted(input_keys), platform_string}; CacheKey::for_copy(op, input_key, file_digests) — sha256 of {fileop_canonical_bytes, input_key, sorted(file_digests)}; file_digests = sha256 of each copied file's content. (MM8 upstream digest in SourceOp CacheKey; P11 compositionality — any input change flows forward; BuildKit cache/manager.go design)
  • local.rs: LocalCacheBackend wraps sled Db; key = CacheKey 32-byte array; value = CacheEntry serialized (snapshot_id + descriptor JSON); lookup(key) → Option<CacheEntry>; store(key, entry); prune(max_age, max_bytes) — iterate all entries; filter by timestamp + evict LRU if over max_bytes. (A-10 sled; C3 capacity model — sled point lookup < 1 ms)
  • content_hash.rs: hash_context_files(paths: &[PathBuf]) → Vec<Digest> — sha256 of each file's content; sorted by path for stability; used in CacheKey::for_copy. (MM3 total ordering on all variables; C9 capacity model — rayon parallel hash < 500 ms for 10K files)
  • invalidation.rs: cache invalidation rules: ENV k=v → invalidates all downstream ExecOps (env change propagates via ExecMeta.env in op bytes); ARG k=v → same; COPY/ADD → content digest change automatically invalidates via for_copy; FROM image:tag → image digest change invalidates (resolve tag → digest at solve start; incorporate manifest digest into SourceOp CacheKey attrs). (MM8 base image staleness; P11; §8.3 SourceOp CacheKey)
  • WAL refcount: replace Phase 1 JSON refcount flush with append-only WAL file: {op: "incr"|"decr", digest: "sha256:..."} per line; replay on startup; compact periodically. (Kleppmann DDIA — append-only WAL for crash-safe refcounts; I-11 GC safety)
  • Tests: test_cache_hit_returns_same_entry; test_cache_invalidation_on_env_change (change ENV → different CacheKey); test_prune_removes_old_entries; test_content_hash_stability (same files, different order → same key).

9.3 Deliverable

9.4 Acceptance Criteria

  • Cache-hit second build of unchanged Dockerfile < 200 ms end-to-end (criterion bench benchmarks/cache_hit.rs).
  • test_cache_invalidation_on_env_change: change ENV value → solver executes all downstream ExecOps (no hit).
  • test_prune_removes_old_entries: store 1000 entries with old timestamps; prune(max_age=1s) → all removed.

22. Phase 10 — forge-registry

10.1 Objectives

  • Production OCI Distribution client: pull (manifest + blob with digest verify), push (HEAD skip / monolithic / chunked / cross-repo mount), PUT manifest, bearer token auth with caching, retry with backoff.

10.2 Detailed Implementation Steps

  • client.rs: HttpRegistryClient implements RegistryClient trait using reqwest::Client with connection pool (max_idle_per_host=8); base URL from Reference.registry; all methods async. (A-03 reqwest; P2 streaming first — pull_blob returns impl AsyncRead immediately; C8 FD budget)
  • auth.rs: AuthState per registry — HashMap<String, BearerToken{token, expires_at}>; authenticate(client, registry, scope) → Result<String, ForgeError>: issue HEAD request to get 401 + WWW-Authenticate: Bearer realm=...,service=...,scope=...; POST to realm with Basic creds; parse {"token":"...","expires_in":300}; cache with Instant::now() + expires_in - 30s buffer. (RFC 7235 WWW-Authenticate; RFC 6750 Bearer Token; I-12 no token persistence; A-23)
  • pull.rs: pull_manifest(r) → (Bytes, MediaType, Digest) — GET /v2/<repo>/manifests/<tag|digest> with Accept headers for OCI + Docker; read response body; verify digest; return. pull_blob(r, digest) → impl AsyncRead — GET /v2/<repo>/blobs/<digest>; return streaming body wrapped in DigestVerifyingReader. (OCI Distribution Spec v1.1 §4 pull protocol; P1 digest verification on every blob read; I-1)
  • push.rs: push_blob(r, descriptor, data) — (1) HEAD /v2/<repo>/blobs/<digest> → 200 means skip; (2) try mount_blob(src, dst, digest) → 201 means mounted; (3) else: POST /v2/<repo>/blobs/uploads/ → 202 with Location; stream data via chunked.rs; PUT with ?digest=; put_manifest(r, manifest_bytes, media_type) — PUT /v2/<repo>/manifests/<tag> with Content-Type + body; return response Docker-Content-Digest header. (OCI Distribution Spec v1.1 §5 push protocol; MM5 push order; I-7 pre-push checklist; P9)
  • chunked.rs: ChunkedUploader — takes upload UUID + Location URL; streams data in 64 MB chunks; PATCH /v2/<repo>/blobs/uploads/<uuid> with Content-Range: <start>-<end>; on 202 advances start; final chunk → PUT with ?digest=; on network error: GET upload status → resume from server-returned offset. (RFC 7233 Range Requests; MM10 server-side offset resume; A-24 64 MB chunk size; C7 capacity model)
  • retry.rs: retry_with_backoff(f, max_attempts=5, base_delay=100ms, max_delay=30s, jitter=true) — retry on 429, 500, 502, 503, 504 and reqwest::Error (network); no retry on 400, 401, 403, 404, 409. (P3 Result-only; OCI Distribution Spec error code taxonomy)
  • Tests: mock HTTP server (using wiremock); test pull_manifest, pull_blob digest mismatch, push_blob HEAD-skip, chunked upload resume, bearer auth refresh.

10.6 Pitfalls

  • WWW-Authenticate header parsing: realm, service, scope may have quoted strings with commas; use a proper header parser not naive split.
  • Cross-repo mount 202 fallback: registry may return 202 (not mounted) even when cross-repo mount is supported; always fall back to upload on 202.
  • Docker-Content-Digest vs computed digest: registry may re-encode manifest; always verify sha256(response_body) == expected; do not trust header alone.
  • PUT manifest before blobs: registry rejects manifest referencing unknown blobs; enforce push order (P9).
  • Chunked upload Content-Range format: bytes <start>-<end>/* for PATCH; bytes */<total> for final PUT; mistake causes 416.
  • Insecure registry (HTTP): support --insecure flag; skip TLS verify; warn loudly.

10.7 Performance Concerns

  • Concurrent blob pushes: semaphore(8) prevents overwhelming registry; tune per registry rate limits.
  • Streaming pull: pull_blob returns impl AsyncRead immediately; no full blob in memory.
  • Connection pool reuse: single reqwest::Client per HttpRegistryClient; do not create new client per request.

10.8 Edge Cases

Mental Models & First Principles

The compressed intuitions an expert holds about container-image building. Each: the insight, what it predicts, the bug class you write without it, and where this blueprint applies it.

  • MM1 — A blob's content address is its identity, not its location. A blob's sha256 digest names it; a copy that hashes differently is a different object, so a "wrong copy" is a category error. Predicts: every read of CAS is self-verifiable without out-of-band metadata; corruption is detectable at read time, not silent. Bug without it: trusting a file at blobs/sha256/<x> without verifying its content hashes to <x>, allowing silent bit-rot to flow into a built image. Applied: §13 (forge-cas DigestVerifyingReader at every get(), I-1), §15 (forge-tar dual-stream hashing, I-2/I-3), §8.1.
  • MM2 — A DAG vertex digest is a reproducibility proof, computed not assigned. vertex_digest = sha256(op_bytes + sorted(input_digests)) makes the same operations on the same inputs yield the same digest, so the digest is the cache key by construction. Predicts: any upstream change propagates to every downstream vertex digest automatically — no manual invalidation list. Bug without it: ad-hoc string cache keys that miss transitive dependencies and serve stale layers. Applied: §16 (forge-llb vertex_digest, §8.3), §21 (forge-cache CacheKey::for_vertex), P11.
  • MM3 — Determinism requires a total ordering on every variable, not most of them. Non-determinism hides in any unordered set: filesystem enumeration order, HashMap iteration, mtime sub-second precision, compression-library version. One un-frozen variable is enough to break reproducibility. Predicts: a single un-normalized field produces a digest that diverges on some platform, invisibly until a cross-arch diff. Bug without it: builds that reproduce on the author's machine but drift in CI. Applied: §15 (forge-tar path sort + SOURCE_DATE_EPOCH, P4, I-9), §16 (BTreeMap canonical JSON, A-04).
  • MM4 — Layer stacking is order-sensitive, and whiteouts are the delete protocol. OCI consumers apply layers base→top; a file is "deleted" only when a .wh.<name> entry appears in a later layer, and the .wh..wh..opq sentinel must precede all other entries in its directory. Predicts: wrong layer order or a missing whiteout yields a silently-wrong image that validates but misbehaves at runtime. Bug without it: deleted files resurface after docker run. Applied: §15 (forge-tar whiteout entries, §8.4), §18 (forge-snapshot differ, I-10).
  • MM5 — Registry push order is a strict protocol invariant, not an optimization. A registry validates a manifest PUT by checking that every referenced blob and config Descriptor already exists; a missing blob causes a 400 and leaves a partially-uploaded image in an undefined state. Predicts: manifest-first always breaks; blobs-then-config-then-manifest always works. Bug without it: intermittent "manifest references unknown blobs" errors under concurrent push. Applied: §22 (forge-registry pre-push checklist, P9, I-7).
  • MM6 — User namespaces remap privilege, they do not grant it. CLONE_NEWUSER gives uid 0 inside the namespace mapping to an unprivileged uid outside; in-namespace capabilities are bounded by the outer uid's capabilities. Predicts: pivot_root, overlayfs, and bind-mount inside a user ns carry kernel-version-gated restrictions (EPERM on old kernels). Bug without it: assuming clone(CLONE_NEWUSER) confers host-root powers, then failing mysteriously in restricted CI. Applied: §19 (forge-exec LinuxExecutor, P10, Phase 7 Pitfalls).
  • MM7 — CAS GC safety requires acquiring a lease before the ingest session begins. If GC runs between "decide to ingest" and "create the temp file", a freshly-written but not-yet-referenced blob can be swept; the lease must precede begin_ingest, not follow commit. Predicts: GC racing a lease-less concurrent ingest deletes live blobs under load. Bug without it: intermittent DigestMismatch on builds that trigger GC mid-solve. Applied: §13 (forge-cas Lease, I-11, Phase 1 Pitfalls), §21 (WAL refcount durability).
  • MM8 — A solve cache key must absorb the upstream registry digest, not just the tag. FROM ubuntu:22.04 is a mutable tag whose underlying manifest digest changes when the publisher pushes an update; a SourceOp CacheKey keyed only on the tag string serves the old base after an upstream change. Predicts: stale-base builds that pass CI yet ship un-patched layers. Bug without it: undetected base-image drift across rebuilds. Applied: §21 (forge-cache SourceOp CacheKey with resolved manifest digest, Phase 9 invalidation rules), P11.
  • MM9 — The async/sync boundary must be explicit, never implicit. Tokio's executor must not run synchronous CPU-heavy or blocking I/O in an async task; CAS/tar/digest hot paths cross into spawn_blocking. Predicts: one blocking call in an async task starves the executor thread pool and spikes latency across unrelated futures. Bug without it: forge push hangs intermittently while sha2::update monopolizes an executor thread during a large-layer hash. Applied: §13 (forge-cas streaming ingest spawn_blocking boundary), §20 (solver tokio::spawn per vertex, A-02).
  • MM10 — Chunked-upload resume must use the server's acknowledged offset, not the client's guess. After a mid-PATCH interruption the server has buffered some bytes; the client GETs the upload URL to learn the acknowledged offset and resumes PATCH from there, not from the last locally-sent position. Predicts: resuming from a client-side position yields a 416 Range Not Satisfiable or silent server-side corruption. Bug without it: failed retries that restart the whole upload instead of resuming. Applied: §22 (forge-registry ChunkedUploader resume, RFC 7233, Phase 10 Implementation Steps).

BuildKit: Made the daemon-as-control-plane decision to allow BuildKit to serve multiple concurrent clients (e.g., Docker daemon + CI runner sharing a single buildkitd instance), enabling cross-client cache reuse. That architecture wins in large-team environments where many clients share one powerful builder host and cache reuse across clients is more valuable than deployment simplicity.

kaniko: Made the "run inside the container being built" decision to eliminate all host-level privilege requirements entirely — no user namespaces, no overlayfs, no pivot_root. That architecture wins in Kubernetes environments where the CI pod has no special capabilities and the security team prohibits any form of privileged container; the tradeoff is that non-reproducibility and no solve cache are acceptable costs.

buildah: Made the direct-libcontainer integration decision, allowing fine-grained OCI runtime spec control (seccomp, capabilities, cgroups v2) at the cost of CGo and platform portability. Wins for security-hardened enterprise environments that need per-build seccomp profiles and tight cgroup budgets; buildah integrates with podman's security model out of the box.

Nixpkgs: Made the purely functional, no-arbitrary-exec decision: every build step is a fixed-output derivation with no network access and a hermetic environment. This wins when cryptographic reproducibility and supply-chain auditability are non-negotiable (e.g., NixOS itself, security-critical infrastructure). The tradeoff is that arbitrary Dockerfiles cannot be expressed without wrapping them in derivations.

Back-of-Envelope Capacity Model

The numbers an expert computes from §4 (System Constraints) before designing. Each is derived step-by-step; the §4 input is named and the formula shown.

  • C1 — Layer hashing throughput budget. Input: §4 "Layer hashing throughput ≥ 800 MB/s / core". A typical Alpine base layer ≈ 5 MB → 5 MB ÷ 800 MB/s = 6.25 ms per layer; a 10-layer base → 10 × 6.25 ms = 62.5 ms on one core. With parallel pulls (§4 "Max concurrent blob uploads 8") → 10 ÷ 8 = 2 batches ≈ 125 ms hash time for the pull phase. Conclusion: hashing is not the bottleneck for typical images; the network is.
  • C2 — sha256 + gzip pipeline bandwidth. Input: §4 "sha256 + gzip pipeline ≥ 200 MB/s". A 500 MB application layer → 500 MB ÷ 200 MB/s = 2.5 s. Reproducibility verification double-builds → 2 × 2.5 s = 5 s for one 500 MB layer. Conclusion: 500 MB layers are feasible; a 5 GB layer → 5000 ÷ 200 = 25 s and should trigger an operator warning.
  • C3 — Cache-hit rebuild working set. Input: §4 "Cache-hit rebuild < 200 ms end-to-end". On hit no layer is hashed; memory touched = sled lookup (key 32 B + value ≈ 200 B per CacheEntry) × vertices. A 20-vertex Dockerfile → 20 × 232 B ≈ 4.6 KB. At sled 4 KB BTree pages, 1–2 page reads/lookup → ~20–40 page reads total, well under 200 ms even cold. Conclusion: cache hit is CPU/IO-latency bound, not memory-bound.
  • C4 — Peak memory during streaming tar. Input: §4 "Peak memory (streaming tar) < 256 MB typical". forge-tar buffers TarEntry metadata (path + stat), content streamed. Worst case 1 M files at avg path 50 B + stat 64 B = 114 B → 1M × 114 B = 114 MB metadata buffer + one 64 KB I/O buffer ≈ 114 MB < 256 MB. Conclusion: the target holds to ~2 M files; beyond that switch to an on-disk merge-sort of entries.
  • C5 — CAS GC time for 1 M blobs. Input: §4 "CAS GC (1 M blobs) < 30 s mark-sweep". mark_sweep walks blobs/sha256/ via read_dir at ~10 µs/entry warm → 10 µs × 1M = 10 s; assume 50% swept at ~5 µs/unlink → 500K × 5 µs = 2.5 s; total ≈ 12.5 s, doubled cold ≈ 25 s < 30 s. Conclusion: streaming read_dir (no Vec) holds the target; two-level sharding sha256/<xx>/<rest> would cut readdir ~100× if scale grows.
  • C6 — Manifest assembly time. Input: §4 "Manifest assembly < 5 ms". A 50-layer config: 50 diff_ids × ~73 B = 3.6 KB + ContainerConfig/history ≈ 2 KB → ~6 KB JSON; serde_json::to_vec < 0.1 ms; sha256 of 6 KB < 0.01 ms. Manifest (50 × ~120 B Descriptors ≈ 6 KB): serialize + sha256 < 0.1 ms. Total < 1 ms — the 5 ms target has 5× headroom; BTreeMap key sort adds < 0.05 ms at 50 entries.
  • C7 — Registry push bandwidth (WAN, 100 MB blob). Input: §4 "p99 blob pull (WAN, 100 MB blob): network-bound; streaming; no 2× copy" + A-24 chunk size. At 100 Mbps WAN → 100 MB ÷ 12.5 MB/s = 8 s; 64 MB chunks → 2 chunks; overhead 2 round-trips × 50 ms RTT = 100 ms; total ≈ 8.1 s (1 Gbps → 0.9 s). Conclusion: A-24's 64 MB chunk is well-tuned; 10 MB chunks would add ~10 × 50 ms = 500 ms of round-trip overhead.
  • C8 — Concurrent blob uploads: file-descriptor budget. Input: §4 "Max concurrent blob uploads 8 (configurable)" + §4 FD assumptions. Per upload ≈ 3 FDs (source file + TCP socket + task) → 8 × 3 = 24; plus CAS files open ≈ 20, sled ≈ 10, Tokio ≈ 4 → ≈ 58 FDs vs ulimit 1024 (~6%). Even at 128 uploads → 128 × 3 + 50 = 434 < 1024. Conclusion: the FD budget is non-binding at the §4 concurrency ceiling.
  • C9 — COPY content-hash time for a large context. Input: §4 "context file hashing (COPY): < 500 ms for 10 K files" + §4 "≥ 800 MB/s / core". 10 K files × 10 KB = 100 MB → serial 100 MB ÷ 800 MB/s = 125 ms; rayon on 8 cores → 125 ÷ 8 ≈ 16 ms. Conclusion: ~30× headroom at 8 cores; the degenerate 10 K × 50 MB = 500 GB case → 500 GB ÷ 800 MB/s = 625 s, so very large monorepos need .dockerignore to bound the context.
  • C10 — Startup time for forge inspect. Input: §4 "Startup time (no-op forge inspect) < 50 ms". Path: clap parse ≈ 1 ms + open layout & read index.json (< 1 MB) ≈ 2 ms + read manifest/config from CAS ≈ 4 ms + JSON print ≈ 0.5 ms = ~7.5 ms (no daemon, no socket, statically linked). Conclusion: 6× headroom; the only risk is an accidental ContentStore::open full-scan — the inspect path must avoid it.
  • C11 — Overlayfs lowerdir chain vs layer depth. Input: §4 "Platforms: Linux … full" + the Scalability Analysis ~128-lowerdir limit. At depth 128, lowerdir string ≈ 128 × (80 B path + sep) ≈ 10 KB vs the kernel mount-options limit (~4 KB pre-5.2, unbounded via fsconfig on 5.2+). Risk: a 100-layer image hits the 4 KB limit on kernels < 5.2. Mitigation: detect kernel version; if < 5.2 and depth > 40, merge intermediates via DiffOp before mounting.
  • C12 — Remote-cache registry round-trip cost. Input: §4 RTT assumptions + §23 remote cache. One HEAD/GET per vertex per build → a 20-vertex cold build 20 × 50 ms RTT = 1 s; with local sled L1 at >80% hit → 20 × 0.2 × 50 ms = 200 ms average. Conclusion: remote L2 adds < 200 ms for typical incremental builds, validating the L1-local / L2-remote design (§23).

  │  builder process (PID 1)                 │
  │  - mounts build context via ConfigMap    │
  │  - executes Dockerfile instructions      │
  │  - reads /proc/self/mountinfo for layers  │
  │  - tars running rootfs diff directly      │
  └─────────────────────────────────────────┘
         (no inner namespaces; no overlayfs)
  • Wins: Kubernetes environments whose policy forbids privileged containers, hostPath, and user-namespace modification — the process mutates its own container rootfs and needs no kernel features beyond basic process isolation.
  • Real system: kaniko (GoogleContainerTools/kaniko) — runs inside the container it is building, mutates the running rootfs, and snapshots via /proc/self/mounts and a custom differ.
  • Rejected because: mutating the running rootfs makes reproducibility impossible (side effects from one instruction leak into the next) and couples the builder to the runtime's snapshot interface. It directly violates P13 (Separation of Diff and Exec), which isolates exec from snapshot — the architectural reason §18 (forge-snapshot) and §19 (forge-exec) are distinct crates.

A3 — Purely functional, no arbitrary exec (Nix model). Every build step is a hermetic, content-addressed derivation with no network access; arbitrary RUN is disallowed.

  Build definition (Nix expression / BUILD file)
           |
  Derivation graph (hermetic; content-addressed)
           |
  Nix daemon / action cache
           |
  +--------+--------+
  |                 |
  Fixed-output      Cached output
  derivation        (hash-verified)
  (sandboxed,       direct from cache
   no network)
  • Wins: security-critical / compliance environments needing cryptographic proof of reproducibility — every step is a pure function, and binary-cache sharing is trivially safe because outputs are content-addressed by all inputs including tool versions.
  • Real system: Nixpkgs / NixOS — every package is a fixed-output derivation; the Nix daemon sandboxes builds with unshare/CLONE_NEWNS; cache.nixos.org serves pre-built derivations.
  • Rejected because: it requires all software to be expressed as Nix derivations, incompatible with arbitrary Dockerfiles — the primary forge deliverable. RUN apt-get install -y curl is a non-deterministic, network-accessing step Nix forbids; forge's users are Dockerfile authors who cannot be required to rewrite their builds (§1 Goal, §17 forge-frontend).

A4 — Registry-as-CAS, no local store (remote-only model). No local blobs/sha256/ directory; every layer is streamed straight to the registry, which is the content store.

  forge CLI
      |
      +--[all blobs served directly from registry]--+
      |                                              |
  forge-registry                            OCI registry (GHCR / ECR)
  (no local blobs/sha256/ dir)
      |
  forge-oci (manifest assembly in memory)
      |
  forge-tar (stream layer directly to registry PATCH)
  • Wins: ephemeral CI runners with no persistent local storage (e.g. hosted runners with < 10 GB disk) — every layer streams to the registry, no local GC is needed, and horizontal scaling is trivial because no local state exists.
  • Real system: ko (google/ko) and crane (google/go-containerregistry) stream build output directly to the registry with minimal local staging; imgpkg (Carvel) uses the same pattern.
  • Rejected because: without a local CAS, a cache hit on an unchanged layer requires re-downloading the blob to verify its diff_id, negating the cache benefit, and concurrent builds cannot share a local blob pool. The sub-200 ms cache-hit target (§4, C3) is unreachable with a registry round-trip per vertex; forge prioritizes offline/air-gapped builds and reproducibility verification (§23), both of which require local blob storage.
