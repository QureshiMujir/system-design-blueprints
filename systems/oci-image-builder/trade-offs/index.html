Decisions (§9) · 28 ADRs

A-01

Language

Chosen

Rust 2021, MSRV 1.78

Rejected

Go, C++, Python

When the rejected choice is right

Go wins when the team is 100% Go and BuildKit integration (gRPC stubs, shared proto types) is the primary requirement; Python wins for a high-level scripting layer atop a stable C library ABI where prototype speed trumps correctness

Why: Memory safety on untrusted bytes; sum types for Op/MediaType; no GC

A-02

Async runtime

Chosen

Tokio (multi-thread)

Rejected

async-std, smol

When the rejected choice is right

async-std wins in projects that require WASM compatibility (Tokio's multi-thread scheduler doesn't compile to WASM); smol wins when embedding a Rust library into a tight embedded system where Tokio's ~300 KB binary footprint is unacceptable

Why: Ecosystem fit (reqwest/hyper); spawn_blocking for sync paths

A-03

HTTP client

Chosen

reqwest (hyper)

Rejected

hyper raw, ureq, isahc

When the rejected choice is right

hyper raw wins when forge-registry is embedded in a host that already owns the Tokio executor and connection pool and needs sub-millisecond control over keep-alive and h2 streams; ureq wins in a synchronous, single-threaded CLI context where the async overhead is pure cost

Why: TLS, connection pooling, async streaming

A-04

Serialization

Chosen

serde + serde_json (BTreeMap annotations)

Rejected

simd-json, json-rust

When the rejected choice is right

simd-json wins when manifest parsing is the hot path in a manifest-indexing proxy (e.g., a registry mirror that parses millions of manifests per second); in that case deterministic key ordering is not required and SIMD throughput dominates

Why: Stable key ordering for deterministic JSON

A-05

SHA-256

Chosen

sha2 crate (RustCrypto)

Rejected

ring, openssl

When the rejected choice is right

ring wins on x86_64 hardware when AVX-512 SHA extensions are available and maximum raw digest throughput (>10 GB/s) is required; openssl wins when FIPS 140-2 certification is a compliance mandate for the build environment

Why: Pure Rust; audited; no C FFI on hot path

A-06

Gzip compression

Chosen

flate2 (miniz_oxide backend)

Rejected

zlib-sys, libdeflate

When the rejected choice is right

libdeflate wins when compressing a large number of small layers in a tight loop where its 3–5× throughput advantage over miniz_oxide pays off and a C dependency is acceptable; zlib-sys wins for maximum compatibility with downstream decompressors that rely on zlib-specific header extensions

Why: Pure Rust; deterministic output at fixed level

A-07

Zstd compression

Chosen

zstd crate (libzstd FFI)

Rejected

zstd-safe, ruzstd

When the rejected choice is right

ruzstd wins in a pure-Rust no-std environment (e.g., a UEFI bootloader or WASM module) where FFI is forbidden; zstd-safe wins when the caller needs fine-grained control over the zstd context lifecycle across multiple threads without the overhead of the zstd crate's mutex-per-context design

Why: Stable, performant; fixed level for determinism

A-08

Tar format

Chosen

tar crate (custom for determinism)

Rejected

libarchive FFI

When the rejected choice is right

libarchive FFI wins when reading a wide variety of archive formats (xz, bzip2, 7z, ISO9660) in a general-purpose unarchiver; the tar crate intentionally omits those formats

Why: Full control over entry order, mtime, uid/gid

A-09

CAS storage

Chosen

local filesystem (blobs/sha256/<hex>)

Rejected

sled, sqlite, RocksDB

When the rejected choice is right

RocksDB wins when the CAS must support transactional multi-blob atomic commits (e.g., committing a manifest + all its layers as one atomic operation with rollback) in a high-throughput server context; sled wins as a middle path when structured queries over blob metadata (size ranges, media type) are needed without the operational cost of RocksDB

Why: Simplest; OS atomic rename; no external DB dependency

A-10

Cache index

Chosen

sled embedded KV

Rejected

sqlite, RocksDB

When the rejected choice is right

sqlite wins when the cache index must be queried with complex SQL (e.g., "find all cache entries older than N days AND referencing a specific base image digest") without a full scan; RocksDB wins at team-scale shared CI where 10M+ entries require bloom filters and compaction tuning beyond sled's capabilities

Why: Embedded, pure Rust; acceptable local cache scale

A-11

Overlay snapshotter

Chosen

Linux overlayfs via nix crate syscalls

Rejected

When the rejected choice is right

fuse-overlayfs wins on kernels < 5.11 without CAP_SYS_ADMIN where in-kernel overlayfs is unavailable in user namespaces; copy-up wins in environments where filesystem correctness must be verified without kernel-level overlay semantics (e.g., macOS, Windows WSL2 with restricted kernel modules)

Why: Kernel-native; lowest overhead; fallback = copy-diff

A-15

Rejected

When the rejected choice is right

log crate wins in library crates that must remain runtime-agnostic and cannot impose a tracing subscriber on the embedding application; slog wins in long-running servers where structured, async-drain logging with backpressure is required and tracing's span overhead is measurable

Why: Structured spans; async-compatible; OpenTelemetry-ready

A-17

Error type

Chosen

thiserror (per-crate) + ForgeError sum at boundary

Rejected

anyhow, failure

When the rejected choice is right

anyhow wins in application-layer code (e.g., integration test harness, scripts) where error context chain readability matters more than variant matching; failure is legacy but wins in codebases locked to Rust 2015 that cannot adopt std::error::Error trait object semantics

Why: Typed variants; exhaustive match in CLI

A-18

Fuzz harness

Chosen

cargo-fuzz (libFuzzer)

Rejected

honggfuzz, afl

When the rejected choice is right

honggfuzz wins when persistent coverage-guided fuzzing on Apple Silicon (M1/M2) is required, as libFuzzer has known limitations on Darwin aarch64; afl++ wins for structured fuzzing with grammar-based mutators (e.g., fuzzing the Dockerfile parser with a grammar-aware mutator produces higher-coverage inputs than pure byte mutation)

Why: Best Rust ecosystem support; CI integration

divan wins for micro-benchmarks in no-std or constrained environments where criterion's dependency on rayon and plotters is too heavy; bench (nightly stdlib) wins when the benchmark suite must be run without any external crate dependencies in a stripped-down CI environment

A-21

Chosen

When the rejected choice is right

native-tls wins when the deployment environment requires FIPS 140-2 TLS (via OpenSSL FIPS module) and rustls's FIPS-certified mode (via aws-lc-rs backend) is not yet approved by the organization's security policy

A-22

Multi-platform manifest

Chosen

ImageIndex (OCI image index)

Rejected

fat manifest (Docker)

When the rejected choice is right

Docker fat manifest wins when the target registry or consumer (e.g., an older Docker Engine < 20.10 or a legacy CI system) does not parse OCI ImageIndex and requires the Docker manifest list format for multi-arch pulls to work correctly

Why: OCI-native; forward-compatible with referrers API

A-23

Registry auth caching

Chosen

in-memory HashMap<registry, BearerToken+expiry>

Rejected

disk cache

When the rejected choice is right

Disk cache wins in a long-running build agent (daemon mode) that handles hundreds of sequential builds and would otherwise perform thousands of re-auth round-trips per day; the token is encrypted at rest using the OS keychain, matching the security level of in-memory storage

Why: Security: no token persistence; re-auth on expiry

A-24

Chunked upload size

Chosen

64 MB default (configurable)

Rejected

10 MB, 128 MB

When the rejected choice is right

10 MB chunks win on high-latency, low-bandwidth links (e.g., a mobile hotspot in a remote CI environment) where 64 MB chunks take minutes to upload and a single packet loss restarts a large chunk; 128 MB chunks win on a 10 Gbps LAN push to a local registry where minimizing per-chunk request overhead (headers, auth check) is measurable

Why: Balances retry granularity vs. request overhead

A-25

SOURCE_DATE_EPOCH

Chosen

env var → u64 seconds; default=0

Rejected

build timestamp

When the rejected choice is right

Build timestamp wins when the OCI image's created field in ImageConfig must reflect the actual build time for auditability (e.g., compliance environments that require a real ISO8601 timestamp for provenance attestation); in that regime, reproducibility is traded for traceability

Why: Reproducibility standard; same as Debian/NixOS

A-27

Lint / format

Chosen

Rejected

custom lints

When the rejected choice is right

Custom lints win in large organizations that enforce domain-specific invariants (e.g., "no Arc<Mutex<>> without a doc comment explaining the lock order") that clippy does not cover; these are implemented via dylint or rustc_plugin

A-28

Cross-compile

Chosen

cross crate + Docker image for aarch64

Rejected

direct qemu

When the rejected choice is right

Direct qemu wins when the Docker daemon is unavailable in the CI environment (e.g., a nested VM with no container runtime) and qemu-user-static is installed as a binfmt handler; native aarch64 hardware wins when cross-compilation produces binaries that must be tested against real hardware-specific kernel behavior (e.g., aarch64 overlayfs lowerdir limits differ from x86_64)

Why: Reproduces Linux aarch64 in CI without native hardware

Alternative Architectures (Roads Not Taken)

Fundamentally different ways to build OCI images for the same goal. Each: an ASCII sketch, the regime where it wins, the real system embodying it, and why this blueprint rejected it.

A1 — Daemon + shared content store (BuildKit model). A long-running daemon owns the content store, snapshotter, and solve cache; clients connect over gRPC.

   client A (forge CLI)     client B (forge CLI)
         |                        |
         +----------+-------------+
                    |
              buildkitd (daemon)
                    |
         +----------+----------+
         |          |          |
      solver     content    snapshot
      (gRPC)     store       manager
         |
     containerd shim → runc/crun
  • Wins: large-team shared build infrastructure where 10+ CI runners share one powerful host — the daemon keeps base layers warm across all clients, cross-client solve-cache reuse pays off, and one daemon owns the overlayfs mounts (no per-client namespace setup).
  • Real system: BuildKit (moby/buildkit) — buildkitd is exactly this: a daemon accepting gRPC from docker build, nerdctl build, and custom clients.
  • Rejected because: a daemon adds a management surface (socket permissions, lifecycle, crash recovery) incompatible with P12 (No Daemon, No Socket); CI/CD and serverless build agents have no persistent host, and a stateless binary is simpler to deploy, audit, and terminate. The gRPC control plane adds generated-code bulk and a protocol-versioning burden the project deliberately avoids (§1, P12).

A2 — Mutating the running container's rootfs (kaniko model). The builder runs inside the image being built and mutates its own rootfs, capturing the diff via the runtime's snapshot mechanism — no inner namespaces, no overlayfs.

  Kubernetes Pod
  ┌─────────────────────────────────────────┐
  │  builder process (PID 1)                 │
  │  - mounts build context via ConfigMap    │
  │  - executes Dockerfile instructions      │
  │  - reads /proc/self/mountinfo for layers  │
  │  - tars running rootfs diff directly      │
  └─────────────────────────────────────────┘
         (no inner namespaces; no overlayfs)
  • Wins: Kubernetes environments whose policy forbids privileged containers, hostPath, and user-namespace modification — the process mutates its own container rootfs and needs no kernel features beyond basic process isolation.
  • Real system: kaniko (GoogleContainerTools/kaniko) — runs inside the container it is building, mutates the running rootfs, and snapshots via /proc/self/mounts and a custom differ.
  • Rejected because: mutating the running rootfs makes reproducibility impossible (side effects from one instruction leak into the next) and couples the builder to the runtime's snapshot interface. It directly violates P13 (Separation of Diff and Exec), which isolates exec from snapshot — the architectural reason §18 (forge-snapshot) and §19 (forge-exec) are distinct crates.

A3 — Purely functional, no arbitrary exec (Nix model). Every build step is a hermetic, content-addressed derivation with no network access; arbitrary RUN is disallowed.

  Build definition (Nix expression / BUILD file)
           |
  Derivation graph (hermetic; content-addressed)
           |
  Nix daemon / action cache
           |
  +--------+--------+
  |                 |
  Fixed-output      Cached output
  derivation        (hash-verified)
  (sandboxed,       direct from cache
   no network)
  • Wins: security-critical / compliance environments needing cryptographic proof of reproducibility — every step is a pure function, and binary-cache sharing is trivially safe because outputs are content-addressed by all inputs including tool versions.
  • Real system: Nixpkgs / NixOS — every package is a fixed-output derivation; the Nix daemon sandboxes builds with unshare/CLONE_NEWNS; cache.nixos.org serves pre-built derivations.
  • Rejected because: it requires all software to be expressed as Nix derivations, incompatible with arbitrary Dockerfiles — the primary forge deliverable. RUN apt-get install -y curl is a non-deterministic, network-accessing step Nix forbids; forge's users are Dockerfile authors who cannot be required to rewrite their builds (§1 Goal, §17 forge-frontend).

A4 — Registry-as-CAS, no local store (remote-only model). No local blobs/sha256/ directory; every layer is streamed straight to the registry, which is the content store.

  forge CLI
      |
      +--[all blobs served directly from registry]--+
      |                                              |
  forge-registry                            OCI registry (GHCR / ECR)
  (no local blobs/sha256/ dir)
      |
  forge-oci (manifest assembly in memory)
      |
  forge-tar (stream layer directly to registry PATCH)
  • Wins: ephemeral CI runners with no persistent local storage (e.g. hosted runners with < 10 GB disk) — every layer streams to the registry, no local GC is needed, and horizontal scaling is trivial because no local state exists.
  • Real system: ko (google/ko) and crane (google/go-containerregistry) stream build output directly to the registry with minimal local staging; imgpkg (Carvel) uses the same pattern.
  • Rejected because: without a local CAS, a cache hit on an unchanged layer requires re-downloading the blob to verify its diff_id, negating the cache benefit, and concurrent builds cannot share a local blob pool. The sub-200 ms cache-hit target (§4, C3) is unreachable with a registry round-trip per vertex; forge prioritizes offline/air-gapped builds and reproducibility verification (§23), both of which require local blob storage.
