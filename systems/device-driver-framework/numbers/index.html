32. Back-of-Envelope Capacity Model

Every number below is derived from §4's constraints table, formula shown, chained to a schema field count from §11 or a target from §28.

  1. Core metadata memory, 256 devices. Device (id 8B + bus Weak 16B + parent Weak 16B + children RwLock<BTreeMap> ~48B empty + ResourceSet ~96B + state 8B + driver RwLock<Option<Arc>> 24B + properties ~128B TLV + refcount 8B) ≈ 352B, rounded to ~400B with alignment. 256 × 400B = 102,400B ≈ 100 KiB — 40× headroom under §4's 4 MiB ceiling.
  2. IRQ vector table memory. 224 vectors (§4) × (fat-pointer handler entry 16B + spurious counter 8B) = 224 × 24B = 5,376B ≈ 5.25 KiB.
  3. DMA mapping table memory. 256 devices × 64 slots/device (§4) × DmaMapping size (dma_addr 8 + len 8 + group 4 + coherent 1, padded to 24B) = 256 × 64 × 24 = 393,216B ≈ 384 KiB.
  4. Hot-plug queue memory. ~16 buses × 128 events/bus (§4) × HotplugEvent size (bus_id 4 + sequence 8 + device 8 + kind 1, padded to 24B) = 16 × 128 × 24 = 49,152B ≈ 48 KiB.
  5. PCI enumeration time. ~50 devices (typical desktop topology) × ~2 ms/device (MMCONFIG access latency) = 100 ms, matching M9's ≤ 100 ms target exactly — the chained-from-§4 check.
  6. USB 4-port-hub enumeration time. 4 devices × 500 ms/device (M10) = 2 s sequential, cross-validating against §37's salvaged historical figure.
  7. Top-half dispatch throughput ceiling. 1 / (1 µs p50, §4) = 1,000,000 dispatches/sec theoretical per-core ceiling before the top-half itself becomes the bottleneck (a sanity ceiling, not an operating target).
  8. Fuzz-canary exploration budget. ~10,000 executions/sec (typical libFuzzer throughput on a small parser) × 86,400 s (24 h, M12) = ≈ 864,000,000 executions per canary run — the number that makes "0 panics over 24 h" meaningful evidence.
  9. Per-mapping DMA-drain budget under refcount pressure. 2,000 ms (§4 refcount-drain p99) / 64 DMA slots/device (§4) = ≈ 31 ms per mapping if drained serially in the worst case — the number that forces parallel (not serial) drain in §17/§19.6.
  10. Bottom-half pool sizing vs. storm rate. At the 1,000-assertion spurious-disable threshold (§16.4) treated as a worst-case rate of ~1,000 storms/sec/vector, an 8-worker pool at ≤ 5 µs wakeup (§4) gives 8 × (1 / 5 µs) = 1,600,000 wakeups/sec theoretical capacity — ≈ 1,600× the single-vector storm rate, showing 8 workers is sufficient before containment (§16) is even needed.
