Boot. Firmware/bootloader hands the kernel a device-tree blob, ACPI tables, or a PCI root-complex; DDF parses only what §8.1 needs to instantiate root Bus objects — it is not a general ACPI/DT interpreter (§1 non-goals).

Bus backends. Each bus type is an isolated crate implementing the Bus trait (§11); each backend enumerates its own children and emits Device records. ddf-mockbus is a first-class backend, not a test-only shim — it implements the same trait surface real buses use, so every conformance fixture runs against the real probe/resource/IRQ code paths (ADR-11).

Probe & match engine. Consumes Device records from any backend; resolves which registered Driver binds, deterministically (P2, I14); this is the sole place drivers are chosen — no backend or driver chooses its own binding.

Resource manager. The only path to claim MMIO, IRQ, or DMA; every claim is typed, tracked, and released via RAII on driver removal (P3, I2, I12).

Driver runtime / bottom-half pool. The capability-gated trait surface a driver implements; top-halves run bounded and non-sleeping (P7, I4); bottom-halves carry deferred work in a separate worker pool that may sleep and may take locks.

Hot-plug event queue. Single per-bus sequenced queue; plug and unplug events for one bus can never reorder relative to each other (I10).

Power management state machine. A total function over (state, event) pairs (I9); every driver's suspend/resume is invoked only through this machine, never directly.

Userspace surface. The only place a device becomes visible to userspace, via VFS cdev/blockdev nodes; unplug while a file descriptor is open returns ENODEV, never a crash (§8.4).

Conformance/fuzz harness. Out-of-band with respect to the runtime path; it drives every box above through ddf-mockbus and asserts each of I1–I14 continuously (§21).

8. Domain Model

8.1 Bus / Device / Driver Binding Model

Cardinality: one Bus owns 0..N Device children; one Device has exactly one parent Bus reference, 0..1 bound Driver, and 0..N child Devices (a USB hub's ports, a PCI bridge's downstream bus). This is the schema behind the §3 diagram's "Bus Backends" and "Probe & Match Engine" boxes.

Role Cardinality vs Device Held By Lifetime Tied To
Bus 1 parent per Device Device.bus: Weak<dyn Bus> Outlives every child Device (I8).
Driver 0..1 bound per Device Device.driver: RwLock<Option<Arc<dyn Driver>>> Bound only while Device is Bound/Suspended (§8.4).
Children 0..N per Device Device.children: RwLock<BTreeMap<DeviceId, Arc<Device>>> Each child pins its parent (I8).
ResourceSet exactly 1 per Device Device.resources Drained to empty before Freed (I7).

8.2 Probe & Match Algorithm

Resolution order when N drivers' match_drivers predicates all match one Device (P2, I14):

Tie-break tier Rule Example
1 Highest Driver::priority() wins. A vendor-specific NIC driver (priority 100) beats a generic virtio-net driver (priority 10) for the same PCI ID.
2 Earlier module load order wins. Two priority-100 drivers: the one registered first in boot order binds.
3 Lexicographic driver name, ascending. Final deterministic tie-break; guarantees I14 even under identical priority and load order.

Algorithm (named steps, not code): (1) bus emits Device in Unbound; (2) resolver iterates the driver registry in BTreeMap order (P12); (3) for each driver, call match_drivers; (4) collect all matches; (5) apply the tie-break tiers above; (6) transition Device to Probing; (7) invoke the winning driver's probe(); (8) on Ok, transition to Bound (I1); (9) on Err, roll back per I7 and return to Unbound, eligible for the next-ranked match (capped at 3 retries — §14 N.8).

8.3 Resource Model — MMIO, IRQ, DMA

Resource Kind Schema Fields Claim Path Release Trigger
MMIO region base: PhysAddr, size: u64 ddf-mmio::claim — range-tree conflict check (I12) Driver remove() or device Freed
I/O port base: u16, size: u16 ddf-mmio::claim_io Same as MMIO
IRQ line number: u32, trigger: Edge|Level ddf-irq::claim — single-owner table Same as MMIO
DMA coherent dma_addr, len, group ddf-dma::map_coherent — IOMMU-mediated (P5) Driver remove(), drained before Suspend (I9)
DMA streaming dma_addr, len, group, direction ddf-dma::map_streaming — sync-before-access (I5) Per-transfer or driver remove()

IRQ trigger types: Edge (one assertion per event; missed edge = lost interrupt, so the top-half must never disable the line without an explicit re-arm) and Level (interrupt stays asserted until the device is serviced; a driver that fails to clear the condition produces an IRQ storm — §22 T2).

DMA coherent vs. streaming: coherent mappings are long-lived, cacheable, and CPU/ device see identical contents without explicit sync (used for descriptor rings that both sides poll); streaming mappings are short-lived and directional, requiring sync_for_device/sync_for_cpu at each boundary crossing (I5) — the classic omission here is the CVE-class bug in §37.

8.5 Worked Example — PCI NIC Bind

Concrete trace binding an Intel-class NIC on a PCI bus:

  1. ddf-bus-pci enumerates (bus 0, device 3, function 0); reads vendor ID 0x8086, device ID 0x100E; emits Device{id: pci:0000:00:03.0, state: Unbound}.
  2. Resolver (§8.2) matches the registered e1000 driver by (vendor_id, device_id); priority 100, tier-1 win; no other driver matches this ID pair.
  3. Device → Probing (I1). e1000::probe() runs.
  4. Driver claims BAR0: Resource::Mmio { base: 0xF000_0000, size: 128 KiB } via ddf-mmio::claim — no conflict (I12) — succeeds.
  5. Driver claims IRQ 11, trigger Edge (post-MSI-X discovery, §20) via ddf-irq::claim — no existing owner — succeeds.
  6. Driver claims a 4 KiB coherent DMA ring via ddf-dma::map_coherent — IOMMU group 3 assigns a translated dma_addr — succeeds.
  7. probe() returns Ok(ProbeOutcome::Bound); Device → Bound (I1); all three resources are now visible in the device's ResourceSet (I2).
  8. ddf-verifier fixture probe_pci_nic_happy_path asserts steps 1–7 against ddf-mockbus's PCI-shaped fixture before any real silicon is touched (P14).

8.6 Malformed-Input Example — Truncated USB Descriptor

Concrete adversarial trace (the CVE-2016-2384 shape, §37):

  1. A USB device at address 5 responds to GetDescriptor(Configuration) with a configuration descriptor whose header field wTotalLength = 255.
  2. The host controller's actual bulk-in transfer completes after only 40 bytes (short transfer — device disconnected mid-response, or a deliberately malformed device).
  3. The parser in ddf-bus-usb walks sub-descriptors using wTotalLength as the trusted bound; without I13's check, it would read 215 bytes past the 40-byte buffer.
  4. Enforcement: the parser cross-checks every sub-descriptor's declared length against the actually received byte count at each step, not just the header's claim; any descriptor whose cumulative offset would exceed the received length is rejected.
  5. On rejection: ProbeError::MalformedDeviceData is returned; Device → Quarantined (§8.4); no bytes past offset 40 are ever dereferenced.
  6. ddf-fuzz's usb_descriptor target (§21) generates exactly this truncation shape as part of its structure-aware corpus.

8.7 Failure-Path Example — Probe Failure Mid-Resource-Claim

Concrete trace of I7's rollback guarantee:

  1. A second NIC (pci:0000:00:04.0) probes; its driver successfully claims BAR0 (MMIO, step as in §8.5).
  2. The same driver then attempts to claim IRQ 11 — already owned by the first NIC from §8.5 (a misconfigured device tree assigning duplicate IRQ routing).
  3. ddf-irq::claim detects the existing owner; returns ResourceError::Conflict.
  4. probe() propagates Err(ProbeError::ResourceConflict(..)).
  5. The probe-path RAII guard (owning the partial ResourceSet) runs its Drop: the BAR0 MMIO claim from step 1 is released via ddf-mmio::release before probe() returns to the resolver.
  6. Device → Unbound (I1); ResourceSet is empty (I7); the resolver may attempt the next-ranked driver match (§8.2) or leave the device unbound if none remains.
  7. ddf-verifier fixture probe_irq_conflict_rollback asserts the ResourceSet is empty immediately after step 6.
