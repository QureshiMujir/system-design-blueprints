Decisions (§9) · 24 ADRs

ADR-01

Language & memory-safety strategy

Chosen

Rust, no_std kernel-context crates + std test crates

Rejected

C, C++, Zig, Ada/SPARK

When the rejected choice is right

C wins when integrating into an existing all-C kernel tree with zero FFI budget for a second toolchain (e.g. a legacy BSP with no Rust target support).

Why: Eliminates the UAF/data-race defect classes dominating driver CVEs (Chou et al., SOSP 2001)

ADR-02

Build system

Chosen

Cargo workspace + xtask

Rejected

Bazel, Make + pkg-config

When the rejected choice is right

Bazel wins at org scale with >100 unrelated crates across many languages needing shared remote caching — not this project's shape.

Why: Native Rust tooling; per-crate incremental builds

ADR-03

Dependency policy

Chosen

Vendored + cargo-vet audited

Rejected

Unpinned floating crates.io deps

When the rejected choice is right

Floating deps win for host-only test crates (ddf-fuzz corpora) with no kernel-context blast radius, where velocity beats audit cost.

Why: Supply-chain integrity for kernel-context code

ADR-04

Device-property storage

Chosen

In-memory typed TLV bag, no persistence

Rejected

On-disk sysfs-style tree

When the rejected choice is right

Persisted properties win when the host kernel needs device state to survive a kexec — delegated to the host (PhaseDeferred("§9"), see §35).

Why: Kernel context has no filesystem dependency (ADR-06)

ADR-05

Property serialization

Chosen

Self-describing TLV

Rejected

Fixed C struct blob

When the rejected choice is right

A fixed struct wins for a frozen, certified embedded target that will never add a field post-certification.

Why: Forward-compatible field addition without an ABI break

ADR-06

Networking scope

Chosen

None in-tree; ddf-bus-virtio drives raw vrings only

Rejected

Framework-level network stack

When the rejected choice is right

A bundled stack wins for a single-purpose appliance shipping exactly one NIC driver with no host network stack at all.

Why: Keeps DDF's scope to device binding, not protocol (§1 non-goals)

ADR-07

Bottom-half execution runtime

Chosen

Dedicated worker-thread pool, host-scheduler-backed

Rejected

Async executor (Tokio-style)

When the rejected choice is right

An async executor wins in the host-side ddf-userspace ioctl-dispatch path, which does use one.

Why: no_std kernel context cannot host a userspace-style async runtime

ADR-08

Async/concurrency in kernel context

Chosen

Explicit worker pool + channels, no async/await

Rejected

async/await on a custom no_std executor

When the rejected choice is right

A custom executor (PhaseDeferred("§9")) wins once the no_std async ecosystem matures past this window — see §35.

Why: Immature stack-size guarantees for no_std async codegen at project start

ADR-09

Logging & tracing

Chosen

Structured tracing-style spans

Rejected

printk-style format strings

When the rejected choice is right

Format strings win for the earliest bring-up on a target with no tracing sink wired yet.

Why: Machine-parseable fields for §24 dashboards

ADR-10

Metrics/telemetry registry

Chosen

Counter/gauge/histogram registry (M#, §28)

Rejected

Ad hoc procfs text

When the rejected choice is right

Ad hoc text wins for a one-off debug build never intended to ship telemetry.

Why: Enables CI-gated regression detection (§28)

ADR-11

Testing harness

Chosen

ddf-mockbus deterministic simulator

Rejected

QEMU-only integration testing

When the rejected choice is right

QEMU wins for the final pre-ship validation pass (§20), run alongside mockbus, not instead of it.

Why: Deterministic replay required for I14 and CI speed (P14)

ADR-12

Fuzzing strategy

Chosen

Coverage-guided structure-aware fuzzing (cargo-fuzz/libFuzzer)

Rejected

Hand-written malformed-input cases only

When the rejected choice is right

Hand-written cases win for regression-locking one already-found bug — they remain as named fixtures (§21 N.5).

Why: Finds bug classes authors didn't anticipate (§21)

ADR-13

CI/CD topology

Chosen

Matrix build + QEMU smoke + fuzz-regression gate

Rejected

Build-only CI

When the rejected choice is right

Build-only CI wins for a doc-only or template-only commit touching no code path.

Why: Catches enumeration/hot-plug regressions pre-merge

ADR-14

Crate packaging boundary

Chosen

Per-bus crate isolation (ddf-bus-*)

Rejected

Monolithic single crate

When the rejected choice is right

A monolithic crate wins for a single-bus embedded target that will never add a second bus backend.

Why: Bus-specific quirks (§20 N.6) can't cross-contaminate

ADR-15

Container use in CI

Chosen

ddf-bench/ddf-fuzz containerized; kernel-context crates are not

Rejected

Everything containerized

When the rejected choice is right

Full containerization wins for the host-side-only crates in isolation — exactly what's done for bench/fuzz.

Why: Kernel-context crates need bare-metal/QEMU, not a container namespace

ADR-16

Security/capability model

Chosen

Capability-gated driver trait surface + IOMMU-mediated DMA

Rejected

Raw pointer access from driver code

When the rejected choice is right

Raw pointer access wins only inside ddf-core's single audited FFI boundary where the capability is minted.

Why: Bounds a driver bug's blast radius (P8)

ADR-17

Release & versioning policy

Chosen

SemVer on crate API; kernel ABI tracks host kernel version out-of-band

Rejected

Lockstep single version number

When the rejected choice is right

Lockstep versioning wins for a vendor shipping one fixed kernel+framework image with no independent crate consumers.

Why: Crate API and kernel ABI evolve at different rates

ADR-18

Reproducibility/determinism

Chosen

BTreeMap/sorted-Vec iteration everywhere (P12)

Rejected

HashMap for speed

When the rejected choice is right

HashMap wins in ddf-bench scratch structures never exposed to enumeration order.

Why: Required for I14 and reproducible conformance runs

ADR-19

Time source

Chosen

Monotonic clock for sequence numbers/timeouts

Rejected

Wall-clock time

When the rejected choice is right

Wall-clock wins for telemetry timestamps shown to a human operator (§24) — display-only, not correctness-bearing.

Why: Wall-clock jumps (NTP step, suspend) would corrupt sequence ordering (I10)

ADR-20

Backpressure policy

Chosen

Bounded hot-plug queue (128/bus), drop-oldest + telemetry

Rejected

Unbounded queue

When the rejected choice is right

Unbounded queue wins inside ddf-verifier's own replay harness, where exhaustive replay must never silently drop an event.

Why: Bounds worst-case memory under an event storm (§22 T2)

ADR-21

Licensing

Chosen

Dual MIT/Apache-2.0

Rejected

GPL-2.0

When the rejected choice is right

GPL wins if DDF is ever upstreamed directly into a GPL-only kernel tree (PhaseDeferred("§9") — out of scope, see §35).

Why: Matches Rust-for-Linux precedent; permits closed-source bus backends

ADR-22

Bus/Driver/Device triangle

Chosen

Hierarchical triangle (P1)

Rejected

Flat device/driver list

When the rejected choice is right

A flat list wins for a fixed single-device embedded target with no bus hierarchy at all.

Why: Hierarchy required for hot-plug/PM/IOMMU-group propagation (§8.1)

ADR-23

Probe/match resolution

Chosen

Priority + load-order + name tie-break (P2, §8.2)

Rejected

First-registered-wins

When the rejected choice is right

First-registered-wins wins for a prototype with exactly one driver per device class — no ambiguity possible.

Why: Determinism (I14) required for reproducible conformance

ADR-24

DMA IOMMU-mediation

Chosen

IOMMU-mediated by default, direct + bounce-buffer fallback

Rejected

Direct DMA only

When the rejected choice is right

Direct DMA wins on a legacy embedded SoC with no IOMMU silicon at all — the fallback path is this regime.

Why: Confused-deputy protection (P5, §22 T3)

Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1 — Fully Isolated Userspace-Driver Model

┌────────────┐  IPC   ┌──────────────┐  IPC   ┌──────────────┐
│ Driver-Host │◄──────►│ Kernel-Resident│◄──────►│ Driver-Host  │
│ Process A   │        │ Resource Arbiter│       │ Process B    │
│ (1 driver)  │        │ (MMIO/IRQ/DMA) │       │ (1 driver)   │
└────────────┘        └──────────────┘        └──────────────┘
     ▲ IPC-delivered interrupt notification, no shared address space ▲

Regime where it wins: an untrusted or frequently-updated driver population, and a security posture tolerating tens-of-microseconds IRQ latency. Real system: seL4 userspace drivers, Fuchsia's DDK (§31). Rejected: §4's ≤ 10 µs p99 top-half budget is incompatible with a per-interrupt IPC round-trip, and §1's target deployment assumes a trusted, audited driver population, not an app-store-style ecosystem.

Alt-2 — Full-VM Driver-Reuse Model

┌───────────┐  paravirt channel  ┌────────────────────────┐
│ Host Kernel│◄──────────────────►│ Driver VM               │
│ (DDF-free) │                    │  unmodified donor kernel│
└───────────┘                    │  + unmodified driver     │
      ▲ hardware passthrough (IOMMU-gated) to the VM ▲       │
                                  └────────────────────────┘

Regime where it wins: reusing a large body of existing unmodified drivers is worth more than a from-scratch safety rewrite (e.g. supporting a large legacy driver catalog unmodified). Real system: LeVasseur et al.'s VM-based driver-reuse design (OSDI 2004, §5 Papers item 3). Rejected: this project's value proposition (§2) is the from-scratch, memory-safe, minimal framework — reusing unmodified C drivers inside a VM sidesteps the exact problem (driver-code memory safety) this blueprint exists to solve, and a full VM-exit per interrupt violates §4's latency budget.

Alt-3 — Flat Device Table, No Bus Hierarchy

┌──────────────────────────────────────────┐
│ Device[256] — fixed global array           │
│  dispatch by hard-coded device-ID switch   │
│  no parent/child, no bus abstraction       │
└──────────────────────────────────────────┘

Regime where it wins: a fixed, small, permanently-known device set (a specific embedded board whose BOM never changes) where hot-plug and IOMMU-group propagation are never needed. Real system: typical embedded-RTOS board-support packages (e.g. FreeRTOS BSPs) that hard-code a device table. Rejected: §1's target explicitly includes hot-pluggable PCI/USB buses with hierarchy requirements (bridge-cascade removal, IOMMU-group propagation, §8.1) that a flat table cannot express without degenerating into a re-implementation of the triangle it was meant to avoid.
