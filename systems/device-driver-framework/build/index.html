⬜ Phase 0 — Repo Skeleton & Correctness Kernel §12

Objectives

Stand up the Cargo workspace and CI matrix; stand up ddf-mockbus + ddf-verifier as the correctness kernel before any bus-specific code exists; prove the DeviceState machine (§8.4) and I1/I7 hold against a synthetic bus (P14).

Deliverable

Workspace builds under cargo build --workspace --all-targets; CI green on both matrix legs; ddf-verifier runs one fixture (probe_smoke) asserting I1 against MockBus.

Acceptance

Cold cargo build --workspace ≤ 100 s (§4); ddf-verifier probe_smoke passes 100/100 runs across distinct random seeds (I14); QEMU smoke boot ≤ 30 s to the verifier entry point.

Fixtures

probe_smoke.json — one MockBus device, one no-op driver, expects Bound. state_machine_exhaustive.json — enumerates every (state, event) pair from §8.4; well-defined pairs must not panic.

Pitfalls
  1. QEMU device-tree/firmware mismatch → silent enumeration failure indistinguishable from "no devices" — mitigated by an explicit device-count assertion in the smoke fixture.
  2. Misconfigured no_std panic handler hangs QEMU silently instead of failing CI — wire a serial-port panic handler before any other code.
  3. A workspace crate accidentally depending on std compiles locally but fails the no_std CI leg — gated by an explicit #![no_std] lint in CI, not convention alone.

⬜ Phase 1 — Core Types & Bus/Device/Driver Registry §13

Objectives

Implement the full ddf-core type surface (§11) as real types; implement DriverRegistry with deterministic BTreeMap storage (P12, ADR-18); make every trait object-safe.

Deliverable

ddf-core compiles as a real crate; unit tests cover every transition-table row from §8.4; DriverRegistry iteration order is asserted stable across 3 independent runs.

Acceptance

100% of the 13 transition-table rows (§8.4) have a passing unit test; illegal transitions (e.g. Unbound → Bound direct) are rejected in both debug (#[should_panic]) and release (Err return); DriverRegistry insert/lookup ≤ 500 ns for a 256-driver registry (§4 ceiling).

Fixtures

illegal_transition_rejected.json — attempts every non-edge in §8.4's table, expects rejection. registry_deterministic_order.json — 10 drivers registered in randomized order across 3 runs, expects identical iteration order.

Pitfalls
  1. Associated types on Driver/Bus break dyn dispatch — every method avoids them, following Rust-for-Linux's driver.rs convention (§5 Ref-impl 3).
  2. AtomicState::compare_exchange looping under contention — bounded by design, since one device is probed by at most one resolver thread at a time (P2).
  3. RefCount overflow from more pins than expected — saturating arithmetic plus a telemetry counter, never silent wraparound.

⬜ Phase 2 — Probe & Match Engine §14

Objectives

Implement ddf-probe's resolver exactly per §8.2's three-tier algorithm; implement the RAII rollback for I7.

Deliverable

ddf-probe::probe_one fully implemented, exercised against ddf-mockbus fixtures with 2+ competing drivers per device.

Acceptance

Resolution ≤ 5 ms per device (§4); bit-identical results across 1,000 replays of one fixture seed (I14); a 4-driver competition fixture resolves to the documented tier-1 winner in 100% of runs.

Fixtures

probe_tier1_priority.json, probe_tier2_loadorder.json, probe_tier3_name.json — one per tie-break tier (§8.2). probe_retry_cap.json — 4 always-failing drivers, expects exactly 3 retries then Unbound.

Pitfalls
  1. An uncapped probe loop on a device with many failing matches starves the resolver thread — capped at 3 (§8.2).
  2. An inverted tie-break comparator (ascending instead of descending priority) silently inverts every resolution — caught by the tier-1 fixture, which is why it is a named fixture and not an assumption.
  3. A driver's probe() panicking instead of returning Err bypasses the RAII guard in no_std (no unwind support) — probe() panic-freedom is a code-review-enforced contract, tracked as an open risk (§23 FM-9).

⬜ Phase 3 — Resource Manager (MMIO Regions & Claims) §15

Objectives

Implement ddf-mmio — the sole path to claim/release MMIO and I/O-port regions; enforce I12 (no overlap) and I2 (no bypass).

Deliverable

ddf-mmio::claim/release fully implemented; exercised against ddf-mockbus fixtures including a deliberate overlap attempt.

Acceptance

Claim/release ≤ 1 ms per allocation (§4); overlap rejected 100% across a randomized 10,000-operation fuzz sequence (I12); zero leaked ranges after 1,000 probe-then-remove cycles (I7/P3, asserted via ddf-verifier).

Fixtures

mmio_overlap_rejected.json — two devices claim overlapping ranges; the second must fail with ResourceError::Overlap. mmio_release_on_remove.json — claim then remove; the range-tree must show zero entries for that device afterward.

Pitfalls
  1. A driver that maps MMIO and panics before remove() leaks kernel virtual address space unless the RAII guard is tied to the Device's own lifetime, not the driver's execution path.
  2. A BAR reported as 64 KiB but only 16 KiB actually decoded (mis-sized BAR, §20 N.6) hangs the bus if trusted blindly — ddf-mmio claims exactly what the bus backend's size-probe sequence reports, never a driver-supplied guess.
  3. Range-tree rebalancing under hot-plug-storm churn — bounded O(log N) by the §4 224-device ceiling.

⬜ Phase 4 — IRQ Subsystem (Top/Bottom Half, Threaded IRQs) §16

Objectives

Implement ddf-irq (top-half dispatch, spurious containment) and ddf-bottom-half (deferred worker pool); enforce I4 and P6/P7.

Deliverable

ddf-irq dispatch + ddf-bottom-half pool fully implemented; a synthetic MockBus IRQ source exercises both a fast (Handled in top-half) and slow (bottom-half-deferred) handler.

Acceptance

Top-half dispatch p50 ≤ 1 µs, p99 ≤ 10 µs (§4, feeds §28 M2); bottom-half wakeup p50 ≤ 5 µs (§4); a spurious-IRQ fixture disables the vector at exactly 1,000 unclaimed assertions, never before 999.

Fixtures

irq_tophalf_latency.json — 10,000 synthetic assertions measured against the §4 p50/p99 targets. irq_spurious_containment.json — asserts the exact 1,000-assertion disable threshold. irq_threaded_deferred.json — asserts a threaded-IRQ handler's bottom-half runs in a sleep-capable context.

Pitfalls
  1. A top-half handler holding a spinlock the bottom half also takes deadlocks the moment the bottom half runs on another core mid-top-half — mitigated by a lint (no-cross-context-lock) flagging any lock shared across the boundary (P7).
  2. A shared legacy INTx vector where one consumer never ACKs causes every sibling handler to be re-invoked needlessly — by design (the dispatch loop always calls every registered handler), so a non-ACKing driver shows as elevated call counts on siblings, not a silent stall.
  3. Threaded-IRQ starvation if too many devices share one worker-pool priority — per-priority pool partitioning (PhaseDeferred("§16") — see §35) is revisited once occupancy telemetry crosses 80% of pool capacity.

⬜ Phase 5 — DMA & IOMMU Integration §17

Objectives

Implement ddf-dma (coherent + streaming mapping) and ddf-iommu (group/translation); enforce I5, I6, P5.

Deliverable

ddf-dma + ddf-iommu implemented; a MockBus IOMMU-group fixture and a non-IOMMU bounce-buffer fixture both green.

Acceptance

Streaming map setup ≤ 5 µs p50 (§4, feeds §28 M4); coherent one-time setup ≤ 50 µs; 100% of cross-group access attempts trapped in the IOMMU-fault fixture (I6); zero stale-cache-read fixture failures across 10,000 sync-boundary crossings (I5).

Fixtures

dma_sync_ordering.json — asserts access without prior sync is rejected at the API boundary. iommu_cross_group_fault.json — a device from group A attempts group B's mapping, expects a fault and quarantine. dma_bounce_buffer_fallback.json — a MockBus fixture with no IOMMU group assigned, expects the bounce-buffer path.

Pitfalls
  1. A streaming map not synced before device access reads stale cache — I5's typestate closes this at compile time in-tree; ADR-16's capability boundary is the last defense at the unsafe FFI edge.
  2. IOMMU groups bundle physically-grouped devices — passthrough-adjacent designs risk pulling in unwanted neighbors (out of scope, §1); the framework exposes group membership rather than hiding it.
  3. Bounce-buffer copy cost mistaken for "free" DMA on legacy hardware — bounce vs. direct path bandwidth is telemetry-tagged separately (§28).

⬜ Phase 6 — Hot-Plug & Refcounted Lifecycle §18

Objectives

Implement ddf-hotplug's sequenced event queue and the device refcounting discipline; enforce I3, I10, I11.

Deliverable

ddf-hotplug fully implemented; a MockBus fixture interleaves plug/unplug/replug against an open FD and asserts no crash and correct ENODEV behavior.

Acceptance

Plug-to-bind ≤ 200 ms p99 (§4, feeds §28 M5); refcount drain on unplug ≤ 2 s p99 (§4) or the device is forced to Quarantined (FM-3 escalation); a 10,000-iteration interleaved plug/unplug/replug fuzz shows zero out-of-order deliveries (I10) and zero use-after-free (I3/I11, sanitizer-checked in the std test harness).

Fixtures

hotplug_sequence_order.json — interleaves plug/unplug across 2 devices on one bus, expects strict per-bus sequence delivery. hotplug_fd_pin_survives_unplug.json — opens a /dev/ FD, unplugs, expects Removing without free until the FD closes, then ENODEV on the next syscall. hotplug_queue_overflow.json — floods 200 events into a 128-capacity queue, expects drop-oldest + telemetry (ADR-20).

Pitfalls
  1. Unplug during an in-flight syscall must not crash — the FD pins refcount before the syscall dispatches, guaranteeing the Device outlives the call (P11).
  2. A leaked refcount (missing decrement on an error path) keeps a device alive past unplug forever — the debug-build tracker (I3's detection column) flags a nonzero refcount N seconds after Removing with no forward progress.
  3. Hot-plug during enumeration (a hub's port-change interrupt firing mid-walk) can produce two parallel enumerations on the same address — serialized per-bus via a mutex held during enumeration (§20 N.6 documents the USB-specific case).

⬜ Phase 7 — Power Management State Machine §19

Objectives

Implement ddf-pm's total (state, event) transition function; enforce I9, P10.

Deliverable

ddf-pm fully implemented; a MockBus fixture drives every power-related (state, event) pair from §8.4 and asserts the exhaustive match compiles with no wildcard arm and behaves per the table.

Acceptance

Suspend ≤ 10 ms (§4, excludes DMA drain, feeds §28 M7); resume ≤ 50 ms (§4, feeds §28 M8); 100% of the (state, event) pairs in §8.4 resolve without reaching a wildcard arm (I9 — compile-time evidence plus a runtime fixture enumerating every pair).

Fixtures

pm_suspend_resume_roundtrip.json — a full D0→D3Hot→D0 cycle, expects suspend/ resume each invoked exactly once. pm_suspend_waits_for_dma.json — an in-flight streaming mapping at SuspendRequest, expects Suspending to hold until drain completes. pm_resume_failure_quarantine.json — driver.resume() returns Err, expects Device → Quarantined per §8.4.

Pitfalls
  1. Suspend during in-flight DMA causes data loss if not drained first — suspend explicitly awaits drain before invoking driver.suspend().
  2. A driver bypassing the PM API to poke hardware into D3 directly desyncs the framework's tracked state from physical reality — the driver API has no direct-register-poke path outside the probe/suspend/resume callbacks (P8 extended to power state).
  3. An IRQ asserting during suspend for a level-triggered device not first disabled floods on resume — suspend disables all IRQ lines for the device before the transition completes.

⬜ Phase 8 — Bus Backends (PCI, USB) & MockBus Hardening §20

Objectives

Implement ddf-bus-pci and ddf-bus-usb against real enumeration protocols; harden ddf-mockbus to model both buses' quirks for pre-hardware conformance (P14).

Deliverable

ddf-bus-pci enumerates a QEMU PCI topology including a bridge; ddf-bus-usb enumerates a QEMU xHCI-attached mass-storage device; both bind a canonical driver.

Acceptance

Full PCI bus enumeration ≤ 100 ms (§4); single USB device enumeration ≤ 500 ms (§4); the BAR size-probe fixture restores the firmware-assigned address correctly in 100% of 1,000 randomized BAR-value fuzz runs; the malformed USB descriptor fixture (§8.6) rejects 100% of over-length sub-descriptors.

Fixtures

pci_bar_size_probe_restore.json — fuzzes BAR values, asserts exact restore. pci_bridge_subordinate_walk.json — a 2-level bridge topology, asserts every downstream device is reachable. usb_malformed_descriptor_reject.json — the §8.6 truncation shape. usb_hub_concurrent_port_change.json — two ports change simultaneously, asserts serialized (not interleaved) enumeration.

Pitfalls
  1. PCIe extended config space (4 KiB) requires MMCONFIG mapping; legacy CF8/CFC ports expose only the first 256 bytes — reading capability data beyond byte 256 via the legacy path silently truncates.
  2. MSI-X vectors live in an MMIO table inside a BAR at a capability-declared offset — conflating this with the capability structure itself is a common implementation bug.
  3. A PCI bridge's secondary/subordinate bus numbers set incorrectly strand every downstream device as unreachable (a historical bug class, §37).
  4. Two USB devices attaching to sibling hub ports simultaneously without per-bus serialization can interleave reset/address-assignment, causing one device's SetAddress to land on the other's pre-address state.

⬜ Phase 9 — Conformance, Fuzzing & Adversarial-Device Hardening §21

Objectives

Close the loop on P14: prove I1–I14 hold under adversarial and malformed device behavior via ddf-verifier's full bucket suite, ddf-fuzz's coverage-guided fuzzers, and a differential test against Linux's drivers/base/ behavior on a curated topology.

Deliverable

Full conformance bucket suite green in CI; both fuzz targets running with zero crashes over a 24 h canary; differential report showing zero undocumented divergences from the curated Linux baseline.

Acceptance

Conformance suite completes in ≤ 15 minutes in CI; 24 h fuzz canary reports 0 panics and 0 sanitizer violations (§28 M12); differential harness shows 100% topology match on the curated boot sequence, with any intentional divergence documented as a named ADR.

Fixtures

differential_linux_boot_topology.json — the curated boot+hotplug script replayed against both systems. fuzz_regression_cve_2016_2384_shape.json — the truncated- descriptor shape locked as a permanent regression fixture (ADR-12). fuzz_regression_ virtio_double_use.json — a descriptor reused twice, expects rejection (I13).

Pitfalls
  1. A fuzz target that only mutates bytes randomly (not structure-aware) spends its budget on inputs rejected at the earliest length check, never reaching deeper parser logic — both targets are structure-aware, mutating field-by-field.
  2. Treating Linux's behavior as unconditionally correct during differential testing — Linux's own historical bugs (§37) are not a spec to match; divergences are triaged, not auto-fixed to match.
  3. A 24 h canary reusing the same seed every night never explores new input space — nightly runs use a fresh seed logged alongside the corpus for reproducibility on failure.
