1. Goal & Scope

Definition. The Device Driver Framework (DDF) is the kernel-side subsystem that binds device drivers to devices through a bus/device/driver abstraction, drives the probe → match → bind → unbind lifecycle, arbitrates ownership of MMIO regions, IRQ lines, and DMA buffers (with IOMMU translation), delivers interrupts through a top-half/bottom-half split with optional threaded IRQs, exposes a uniform capability-gated driver API, drives hot-plug and power-management state transitions, and proves every invariant under malformed and adversarial device behavior — including DMA attacks from a compromised or malicious device — via a deterministic mock-bus conformance harness.

Phase-0 deliverable (numbered list of crates):

  1. ddf-core — Bus/Device/Driver traits, DeviceState machine, registry.
  2. ddf-probe — priority + load-order probe/match resolver.
  3. ddf-mmio — MMIO region claim/release/mapping.
  4. ddf-irq — top-half dispatch, spurious-IRQ containment.
  5. ddf-mockbus — deterministic in-process bus/device simulator.
  6. ddf-verifier — invariant-checking harness driven by ddf-mockbus.

System boundaries.

  • Provides — bus/device/driver binding; resource arbitration (MMIO/IRQ/DMA); IRQ dispatch; DMA/IOMMU mapping; hot-plug sequencing; PM state machine; capability-gated driver trait surface; mock-bus conformance harness.
  • Delegates — physical bus electrical/protocol timing (host firmware/hardware); the thread/task executor backing bottom-half workers (host kernel's scheduler); filesystem plumbing beneath the /dev/ node (host VFS).
  • Does NOT provide — a general-purpose untrusted-userspace driver sandbox (a VFIO-equivalent trust boundary, PhaseDeferred("§1") — see §35); a full ACPI AML interpreter; a GPU/display stack; a network protocol stack above the NIC device boundary.

Non-goals. Not a hypervisor; not an ACPI AML interpreter; not a userspace-driver security sandbox equivalent to VFIO passthrough; not a general-purpose filesystem.

Deployment model. Statically linked into a host kernel (or a kernel-adjacent privileged component) as a set of Rust crates: kernel-context crates run no_std inside the host kernel's address space; ddf-mockbus/ddf-verifier/ddf-bench/ddf-fuzz are host-side (std) test crates that never ship to production.

Target users/operators. Kernel engineers writing bus backends and device drivers; kernel integrators wiring DDF into a host kernel; on-call engineers debugging hot-plug, IRQ, and power incidents via the runbooks in §24 Operational Readiness.

What later phases unlock. Phase 5 (§17, DMA/IOMMU) unlocks safe DMA under a translation boundary; Phase 6 (§18, hot-plug) unlocks live device replacement; Phase 7 (§19, PM) unlocks suspend-to-RAM and runtime power savings; Phase 8 (§20, bus backends) unlocks real PCI/USB hardware; Phase 9 (§21, conformance/fuzzing) unlocks the adversarial-device guarantee load-bearing for production sign-off.

Recommended language + rationale. Rust, stable ≥ 1.78, no_std for every kernel-context crate (std permitted only in the host-side test crates named above). Driver code is the single largest historical source of kernel memory-safety defects — Chou et al. (SOSP 2001) measured Linux driver code at roughly 3–7× the bug rate of core kernel code, concentrated in pointer and refcount errors. Rust's ownership/borrow checker statically eliminates the use-after-free and data-race classes that produced exactly those historical CVEs in the resource-manager and refcounting paths (§18).

Rejected languages. C — no memory-safety guarantee, the defect class this project exists to remove. C++ — exception/RTTI undefined-behavior surface is incompatible with no_std kernel context, and still lacks ownership-checked concurrency. Zig — no stable toolchain/ABI guarantee at project start and a materially smaller no_std driver-adjacent crate ecosystem. Ada/SPARK — strong safety profile but a prohibitively small hiring pool and no existing kernel-adjacent crate ecosystem to build from.

Prerequisites. Interrupt-driven I/O and the top/bottom-half split; virtual memory and IOMMU address translation; PCI/USB enumeration protocols; reference counting and RCU-adjacent reclamation; power-state machines; Rust ownership/lifetime semantics at the unsafe/FFI boundary.

Estimated timeline. Phase 0 (§12): 3 weeks. Full system (§12–§21, Phases 0–9): 7 months.

Deferred features are flagged inline as PhaseDeferred("§N.s") and consolidated in §35 Deferred Features Register.

2. Why Build This

  • Teaches the one abstraction every production kernel driver model converges on independently — Linux's struct bus_type / struct device / struct device_driver, FreeBSD newbus's device_t hierarchy, Windows WDF's WDFDEVICE/WDFDRIVER. Convergent evolution across three unrelated kernel lineages is evidence the bus/device/driver triangle is load-bearing, not incidental (§8.1).
  • Historically, kernels that shipped without this separation paid for it later with unfixable hot-plug/PM retrofits — Linux's 2.6 driver-core rewrite (kobject, struct device) was itself a multi-year migration paid for by not having the triangle from day one; this project builds the triangle first, so nothing downstream needs a rewrite.
  • Builds the muscle of reasoning about lifetime under concurrent hardware events: a device can be unplugged mid-syscall, mid-IRQ, mid-DMA. The refcounting discipline built in §18 is the same discipline behind RCU, Arc, and epoch-based reclamation elsewhere in systems engineering.
  • Cross-links: shares its resource-arbitration problem with hypervisor device-passthrough frameworks (VFIO, Xen PCI passthrough); shares its interrupt-latency problem with real-time schedulers; shares its state-machine discipline with the ACPI device power-state literature (§19).
  • Calibration value: after this project, an engineer reads Linux's drivers/base/dd.c or FreeBSD's subr_bus.c and recognizes every mechanism by name, having built a minimal, correct version first.

What Mastery Looks Like

  • Derive the probe/match resolution order from first principles and predict its outcome for any driver-priority/load-order combination — §12 Phase 0, §13 Phase 1.
  • Trace an IRQ from device assertion to bottom-half completion and name every latency contributor — §16 Phase 4.
  • Explain why DMA without an IOMMU is a confused-deputy vulnerability and design the bounce-buffer fallback — §17 Phase 5.
  • Predict, for any interleaving of unplug and an in-flight syscall/IRQ/DMA, whether the device frees safely, using the refcount discipline alone — §18 Phase 6.
  • Design a total power-state transition function and identify every unhandled (state, event) pair as a defect — §19 Phase 7.
  • Enumerate a PCI or USB bus, including BAR-sizing and MSI-X discovery, and defend every "write all-1s, read-back, restore" step — §20 Phase 8.
  • Construct a fuzzer that finds the same bug class as CVE-2016-2384 without knowing the CVE in advance — §21 Phase 9.

Boot. Firmware/bootloader hands the kernel a device-tree blob, ACPI tables, or a PCI root-complex; DDF parses only what §8.1 needs to instantiate root Bus objects — it is not a general ACPI/DT interpreter (§1 non-goals).

Bus backends. Each bus type is an isolated crate implementing the Bus trait (§11); each backend enumerates its own children and emits Device records. ddf-mockbus is a first-class backend, not a test-only shim — it implements the same trait surface real buses use, so every conformance fixture runs against the real probe/resource/IRQ code paths (ADR-11).

Probe & match engine. Consumes Device records from any backend; resolves which registered Driver binds, deterministically (P2, I14); this is the sole place drivers are chosen — no backend or driver chooses its own binding.

Resource manager. The only path to claim MMIO, IRQ, or DMA; every claim is typed, tracked, and released via RAII on driver removal (P3, I2, I12).

Driver runtime / bottom-half pool. The capability-gated trait surface a driver implements; top-halves run bounded and non-sleeping (P7, I4); bottom-halves carry deferred work in a separate worker pool that may sleep and may take locks.

Hot-plug event queue. Single per-bus sequenced queue; plug and unplug events for one bus can never reorder relative to each other (I10).

Power management state machine. A total function over (state, event) pairs (I9); every driver's suspend/resume is invoked only through this machine, never directly.

Userspace surface. The only place a device becomes visible to userspace, via VFS cdev/blockdev nodes; unplug while a file descriptor is open returns ENODEV, never a crash (§8.4).

Conformance/fuzz harness. Out-of-band with respect to the runtime path; it drives every box above through ddf-mockbus and asserts each of I1–I14 continuously (§21).

6. Design Principles

ID Principle Rule Tradeoff Operational Implication Violation Consequence
P1 Bus/Driver/Device triangle No flat device/driver lists; every device has exactly one parent bus. More object types than a flat table. Hot-plug and IOMMU-group propagation both walk the tree; a flat model cannot express either. A device with no bus context cannot propagate removal to children — orphaned resources.
P2 Deterministic probe/match Resolve by priority, then load order, then driver name — never registration-time races. Requires per-driver priority metadata. Enumeration order is reproducible across boots; conformance diffs are meaningful. "Works on Tuesday, not Wednesday" bug class (§22 T4).
P3 Explicit resource ownership Every MMIO/IRQ/DMA claim is typed, tracked in a ResourceSet, released by RAII. Extra bookkeeping struct per device. Leak detection is mechanical, not manual auditing. Silent resource leak on driver removal (§23 FM-1).
P4 Hot-plug is the default Every driver assumes possible unplug at any point, not just at explicit checkpoints. Every driver method must handle ENODEV. No driver code path may assume device permanence. Use-after-free on a freed Device (§22 T5).
P5 IOMMU-mediated DMA when available Direct DMA is a legacy fallback with bounce buffers, never the default. Bounce buffers cost a copy. DMA from a compromised device cannot reach arbitrary physical memory when an IOMMU is present. Confused-deputy DMA attack (§22 T3).
P6 Top/bottom-half split Top-half is bounded and non-sleeping; bottom-half carries the bulk of the work. Two execution contexts per IRQ source. IRQ latency stays bounded regardless of handler complexity. Long top-half handlers introduce system-wide interrupt jitter.
P7 No blocking in atomic/interrupt context Top-halves never sleep, never take a sleeping mutex, never perform blocking allocation. Enforced by type-level separation (top-half trait cannot name a sleeping primitive). Deadlock analysis is local to the bottom-half pool only. Deadlock or priority inversion in interrupt context (§22 T2/§6 pitfall class).
P8 Capability-gated driver API Drivers reach kernel-internal structures only through the exposed trait surface, never raw pointers. Slightly more indirection per call. A driver bug's blast radius is bounded by the capability surface, not the whole kernel. A driver can corrupt arbitrary kernel memory (defeats the entire safety rationale of §1).
P9 Fail-safe device quarantine Malformed device data triggers containment (device marked faulty, driver unbound), never a panic. Requires bounded parsing everywhere device data is read. A malicious device degrades one driver, not the kernel. Kernel panic from untrusted device input (§22 T1).
P10 Total power state machine Every (state, event) pair has a defined handler; no ad hoc suspend/resume. Requires enumerating every transition up front. Suspend/resume bugs are compile-time-checkable (exhaustive match), not field-discovered. Unhandled transition strands a device in an undefined power state (§23 FM-8).
P11 Refcounted lifetime A Device lives exactly as long as any FD/IRQ/DMA-mapping pin references it. Refcount overhead per pin/unpin. Unplug during any operation is safe by construction. Use-after-free or premature free under concurrent unplug (§22 T5).
P12 Deterministic iteration order Every framework iteration (BTreeMap/sorted Vec), never hash-order. Slightly higher constant factor than a hash map. Test outcomes and probe order reproduce across machines and runs. Flaky conformance fixtures; irreproducible bug reports.
P13 Observability is built-in Every resource claim/release/probe emits structured telemetry, not added later. Telemetry code inline with core logic. Production incidents are diagnosable from existing metrics, not ad hoc instrumentation. Blind debugging during a production incident (§24 Operational Readiness).
P14 Conformance before hardware Every invariant is proven against ddf-mockbus before any real bus backend lands. Mock-bus fixtures must be written before hardware-specific code. Hardware-specific bugs are isolated from framework bugs by construction. Framework and hardware-driver bugs conflated, slower root-cause.

7. System Invariants

# Invariant Why Enforced At Detection Telemetry Recovery
I1 Device state transitions Unbound → Probing → Bound → Removing → Freed monotonically; no transition skips or reverses. A skipped state (e.g. Unbound → Bound direct) bypasses resource-claim bookkeeping. ddf-core::DeviceState transition function (§11). ddf-verifier state-machine assertion per transition. ddf_device_state_transition counter, tagged from/to. Illegal transition rejected; device forced to Removing.
I2 A bound Driver holds only resources declared in its own ResourceSet; no claim bypasses the resource manager. Undeclared claims defeat leak detection and conflict checking. ddf-mmio/ddf-irq/ddf-dma claim APIs (§15–§17). Static: only these APIs can construct a Resource. ddf_resource_claim_total, ddf_resource_conflict_total. Claim rejected with ResourceError::Conflict.
I3 refcount(Device) ≥ 1 while any FD/IRQ/DMA mapping is pinned; drops to 0 only after every pin releases. Load-bearing for safe unplug under concurrency (P11). ddf-hotplug refcount primitive (§18). Debug-build refcount tracker; underflow assertion. ddf_device_refcount_gauge. Underflow panics in debug builds; release builds saturate and log FM-1.
I4 No top-half IrqHandler::handle blocks (sleeps, blocking-allocates, takes a sleeping mutex). Bounds IRQ latency (§4); required by P7. Type-level: IrqHandler trait has no sleeping-primitive-capable methods (§11). Lint (no-sleep-in-tophalf) + runtime watchdog on handler duration. ddf_tophalf_duration_us histogram. Watchdog logs and, above threshold, disables the offending IRQ line.
I5 Every DMA-streaming mapping is synced before device access and after device completion. Unsynced streaming DMA reads/writes stale cache lines. ddf-dma::sync_for_device/sync_for_cpu (§17). ddf-verifier fixture asserting sync-before-access ordering. ddf_dma_sync_total. Access without prior sync rejected at the API boundary (typestate).
I6 IOMMU group membership is static after boot; no cross-group DMA translation. Cross-group translation defeats the IOMMU isolation boundary (P5). ddf-iommu::IommuGroup (§11, §17). IOMMU fault trap on mismatched group access. ddf_iommu_fault_total. Faulting device quarantined (§23 FM-4).
I7 A failed probe() leaves the device Unbound with zero leaked resources. Retryable probe requires a clean rollback (§14). ddf-probe RAII rollback on Err (§14). ddf-verifier fixture: inject probe failure, assert ResourceSet empty. ddf_probe_failure_total. Automatic rollback; device eligible for the next driver match.
I8 A device's parent is not freed while children exist (bottom-up teardown only). Top-down teardown frees a bus while children still reference it. ddf-core::Device::children refcount contributes to parent pin (§11). ddf-verifier teardown-order fixture. ddf_teardown_order_violation_total. Parent free deferred until children count reaches 0.
I9 Power-state transitions form a total function: every (state, event) pair has a defined handler. Load-bearing for P10; an unhandled pair strands a device. ddf-pm::PmState exhaustive match (§19). Compile-time exhaustiveness check + ddf-verifier fixture enumerating all pairs. ddf_pm_unhandled_transition_total (should be permanently 0). Build fails if the match is non-exhaustive.

8. Domain Model

8.1 Bus / Device / Driver Binding Model

Cardinality: one Bus owns 0..N Device children; one Device has exactly one parent Bus reference, 0..1 bound Driver, and 0..N child Devices (a USB hub's ports, a PCI bridge's downstream bus). This is the schema behind the §3 diagram's "Bus Backends" and "Probe & Match Engine" boxes.

Driver 0..1 bound per Device Device.driver: RwLock<Option<Arc<dyn Driver>>> Bound only while Device is Bound/Suspended (§8.4).
Children 0..N per Device Device.children: RwLock<BTreeMap<DeviceId, Arc<Device>>> Each child pins its parent (I8).

8.2 Probe & Match Algorithm

Resolution order when N drivers' match_drivers predicates all match one Device (P2, I14):

Tie-break tier Rule Example
1 Highest Driver::priority() wins. A vendor-specific NIC driver (priority 100) beats a generic virtio-net driver (priority 10) for the same PCI ID.
2 Earlier module load order wins. Two priority-100 drivers: the one registered first in boot order binds.
3 Lexicographic driver name, ascending. Final deterministic tie-break; guarantees I14 even under identical priority and load order.

Algorithm (named steps, not code): (1) bus emits Device in Unbound; (2) resolver iterates the driver registry in BTreeMap order (P12); (3) for each driver, call match_drivers; (4) collect all matches; (5) apply the tie-break tiers above; (6) transition Device to Probing; (7) invoke the winning driver's probe(); (8) on Ok, transition to Bound (I1); (9) on Err, roll back per I7 and return to Unbound, eligible for the next-ranked match (capped at 3 retries — §14 N.8).

8.3 Resource Model — MMIO, IRQ, DMA

Resource Kind Schema Fields Claim Path Release Trigger
MMIO region base: PhysAddr, size: u64 ddf-mmio::claim — range-tree conflict check (I12) Driver remove() or device Freed
I/O port base: u16, size: u16 ddf-mmio::claim_io Same as MMIO
IRQ line number: u32, trigger: Edge|Level ddf-irq::claim — single-owner table Same as MMIO
DMA coherent dma_addr, len, group ddf-dma::map_coherent — IOMMU-mediated (P5) Driver remove(), drained before Suspend (I9)

IRQ trigger types: Edge (one assertion per event; missed edge = lost interrupt, so the top-half must never disable the line without an explicit re-arm) and Level (interrupt stays asserted until the device is serviced; a driver that fails to clear the condition produces an IRQ storm — §22 T2).

DMA coherent vs. streaming: coherent mappings are long-lived, cacheable, and CPU/ device see identical contents without explicit sync (used for descriptor rings that both sides poll); streaming mappings are short-lived and directional, requiring sync_for_device/sync_for_cpu at each boundary crossing (I5) — the classic omission here is the CVE-class bug in §37.

8.5 Worked Example — PCI NIC Bind

Concrete trace binding an Intel-class NIC on a PCI bus:

  1. ddf-bus-pci enumerates (bus 0, device 3, function 0); reads vendor ID 0x8086, device ID 0x100E; emits Device{id: pci:0000:00:03.0, state: Unbound}.
  2. Resolver (§8.2) matches the registered e1000 driver by (vendor_id, device_id); priority 100, tier-1 win; no other driver matches this ID pair.
  3. Device → Probing (I1). e1000::probe() runs.
  4. Driver claims BAR0: Resource::Mmio { base: 0xF000_0000, size: 128 KiB } via ddf-mmio::claim — no conflict (I12) — succeeds.
  5. Driver claims IRQ 11, trigger Edge (post-MSI-X discovery, §20) via ddf-irq::claim — no existing owner — succeeds.
  6. Driver claims a 4 KiB coherent DMA ring via ddf-dma::map_coherent — IOMMU group 3 assigns a translated dma_addr — succeeds.
  7. probe() returns Ok(ProbeOutcome::Bound); Device → Bound (I1); all three resources are now visible in the device's ResourceSet (I2).
  8. ddf-verifier fixture probe_pci_nic_happy_path asserts steps 1–7 against ddf-mockbus's PCI-shaped fixture before any real silicon is touched (P14).

8.6 Malformed-Input Example — Truncated USB Descriptor

Concrete adversarial trace (the CVE-2016-2384 shape, §37):

  1. A USB device at address 5 responds to GetDescriptor(Configuration) with a configuration descriptor whose header field wTotalLength = 255.
  2. The host controller's actual bulk-in transfer completes after only 40 bytes (short transfer — device disconnected mid-response, or a deliberately malformed device).
  3. The parser in ddf-bus-usb walks sub-descriptors using wTotalLength as the trusted bound; without I13's check, it would read 215 bytes past the 40-byte buffer.
  4. Enforcement: the parser cross-checks every sub-descriptor's declared length against the actually received byte count at each step, not just the header's claim; any descriptor whose cumulative offset would exceed the received length is rejected.
  5. On rejection: ProbeError::MalformedDeviceData is returned; Device → Quarantined (§8.4); no bytes past offset 40 are ever dereferenced.
  6. ddf-fuzz's usb_descriptor target (§21) generates exactly this truncation shape as part of its structure-aware corpus.

8.7 Failure-Path Example — Probe Failure Mid-Resource-Claim

Concrete trace of I7's rollback guarantee:

  1. A second NIC (pci:0000:00:04.0) probes; its driver successfully claims BAR0 (MMIO, step as in §8.5).
  2. The same driver then attempts to claim IRQ 11 — already owned by the first NIC from §8.5 (a misconfigured device tree assigning duplicate IRQ routing).
  3. ddf-irq::claim detects the existing owner; returns ResourceError::Conflict.
  4. probe() propagates Err(ProbeError::ResourceConflict(..)).
  5. The probe-path RAII guard (owning the partial ResourceSet) runs its Drop: the BAR0 MMIO claim from step 1 is released via ddf-mmio::release before probe() returns to the resolver.
  6. Device → Unbound (I1); ResourceSet is empty (I7); the resolver may attempt the next-ranked driver match (§8.2) or leave the device unbound if none remains.
  7. ddf-verifier fixture probe_irq_conflict_rollback asserts the ResourceSet is empty immediately after step 6.

11. Core Schema & Types

All load-bearing types as signatures only (No-Code Rule, §4); ownership/mutation/ concurrency/persistence/serialization/compatibility given as leading comments.

// Ownership: framework singleton per bus instance, Arc<dyn Bus>.
// Mutation: interior (RwLock<BTreeMap>) for children — deterministic order (P12).
// Concurrency: Send + Sync; probe() may run from multiple bus-scan threads.
// Persistence: none — rebuilt every boot from firmware enumeration.
pub trait Bus: Send + Sync {
    fn name(&self) -> &str;
    fn probe(&self, child: &Device) -> ProbeResult;
    fn match_drivers(&self, device: &Device, drivers: &[Arc<dyn Driver>]) -> Option<Arc<dyn Driver>>;
    fn iommu_group(&self, device: &Device) -> Option<IommuGroupId>;
}

// Ownership: Arc<Device>, refcounted (I3); freed only at refcount 0.
// Mutation: state via AtomicState (I1); driver binding via RwLock.
// Concurrency: Send + Sync; children iterated in BTreeMap order (P12).
// Persistence: none; DeviceProperties are in-memory TLV only (ADR-04/05).
// Compatibility: DeviceId is stable across probe/unbind/reprobe of the same slot.
pub struct Device {
    pub id: DeviceId,
    pub bus: Weak<dyn Bus>,
    pub parent: Option<Weak<Device>>,
    pub children: RwLock<BTreeMap<DeviceId, Arc<Device>>>,
    pub resources: ResourceSet,
    pub state: AtomicState,
    pub driver: RwLock<Option<Arc<dyn Driver>>>,
    pub properties: DeviceProperties,
    pub refcount: RefCount,
}

// Ownership: registered once at module init; Arc<dyn Driver> shared across devices.
// Mutation: none — Driver is stateless; per-device state lives in Device.
// Concurrency: Send + Sync; probe/remove/suspend/resume serialized per-device (I1).
pub trait Driver: Send + Sync {
    fn name(&self) -> &str;
    fn priority(&self) -> DriverPriority;
    fn probe(&self, device: &Device) -> Result<ProbeOutcome, ProbeError>;
    fn remove(&self, device: &Device) -> RemoveOutcome;
    fn suspend(&self, device: &Device, target: PmState) -> Result<(), PmError>;
    fn resume(&self, device: &Device) -> Result<(), PmError>;
}
// Ownership: exactly one live Resource per (kind, range), enforced by ResourceSet (I2, I12).
// Mutation: immutable once claimed; released only via RAII Drop.
// Concurrency: claims serialized through ddf-mmio/ddf-irq/ddf-dma (single arbiter each).
pub enum Resource {
    Mmio { base: PhysAddr, size: u64 },
    Io { base: u16, size: u16 },
    Irq { number: u32, trigger: IrqTrigger },
    DmaCoherent { mapping: DmaMapping },
    DmaStreaming { mapping: DmaMapping, direction: DmaDirection },
}

// Ownership: one per Device; owns every Resource handle the bound driver holds.
// Mutation: append-only during probe, drained on remove (I7).
pub struct ResourceSet {
    mmio: Vec<Resource>,
    irqs: Vec<Resource>,
    dma: Vec<Resource>,
}

// Ownership: none — pure Copy error enum.
pub enum ResourceError {
    Conflict { existing: ResourceId },
    Overlap { range: (u64, u64) },
    ExhaustedIrqTable,
    ExhaustedDmaSlots,
}

// Concurrency: lock-free read path (top-half dispatch), locked write path (bind/unbind).
pub trait IrqHandler: Send + Sync {
    fn handle(&self) -> IrqResult;
}

pub enum IrqResult { Handled, NotHandled, WakeBottomHalf(BottomHalfRef) }
pub enum IrqTrigger { Edge, Level }
// Ownership: one per active mapping, owned by the requesting ResourceSet.
// Mutation: sync_for_device/sync_for_cpu are the only permitted state changes (I5).
// Concurrency: Send, not Sync — one driver context owns a mapping at a time.
// Persistence: none; torn down on device remove or driver unbind.
pub struct DmaMapping {
    pub dma_addr: DmaAddr,
    pub len: usize,
    pub group: IommuGroupId,
    pub coherent: bool,
}

probe_smoke.json — one MockBus device, one no-op driver, expects Bound. state_machine_exhaustive.json — enumerates every (state, event) pair from §8.4; well-defined pairs must not panic.

12.6 Pitfalls

  1. QEMU device-tree/firmware mismatch → silent enumeration failure indistinguishable from "no devices" — mitigated by an explicit device-count assertion in the smoke fixture.
  2. Misconfigured no_std panic handler hangs QEMU silently instead of failing CI — wire a serial-port panic handler before any other code.
  3. A workspace crate accidentally depending on std compiles locally but fails the no_std CI leg — gated by an explicit #![no_std] lint in CI, not convention alone.

12.7 Performance Concerns

Cold build time is dominated by proc-macro-heavy dependencies; audit cargo tree's deepest chain; keep ddf-core (the critical rebuild path) proc-macro-free.

12.8 Edge Cases

MockBus fixture with zero devices (must not hang the verifier). MockBus fixture where no registered driver matches (must settle in Unbound, not loop). A CI leg that fails only under release-mode optimization (LTO-sensitive UB) — both debug and release run in the same matrix.

12.9 Failure Analysis

Symptom: an entire CI target (e.g. QEMU) silently never runs while CI shows green. Detection: ci.yml's job count is itself asserted against a fixed expected count in a meta-check step. Blast radius: an entire target class ships unverified. Recovery: fail CI if the job-count meta-check regresses.

12.10 Operational Notes

ddf-verifier emits a JSON report (fixture, invariant, pass/fail, seed) consumed by tools/; CI uploads it as a build artifact, giving the next session a machine-readable invariant pass-rate history.

13. Phase 1 — Core Types & Bus/Device/Driver Registry

13.1 Objectives

Implement the full ddf-core type surface (§11) as real types; implement DriverRegistry with deterministic BTreeMap storage (P12, ADR-18); make every trait object-safe.

13.2 Detailed Implementation Steps

Define Bus, Driver, Device, DeviceState, DeviceProperties, ResourceSet per §11 (resource manager lands §15). Implement AtomicState wrapping DeviceState with a compare_exchange-based guard enforcing §8.4's table (I1). Implement RefCount (I3) as a saturating atomic counter with a debug-build underflow assertion — the recoverable- extension discipline of Zhou et al.'s SafeDrive (OSDI 2006, §5 Papers item 7, P9). Implement DriverRegistry::register inserting by (priority, load_order, name) composite key for deterministic iteration (P12, ADR-23).

13.3 Deliverable

ddf-core compiles as a real crate; unit tests cover every transition-table row from §8.4; DriverRegistry iteration order is asserted stable across 3 independent runs.

13.4 Acceptance Criteria

100% of the 13 transition-table rows (§8.4) have a passing unit test; illegal transitions (e.g. Unbound → Bound direct) are rejected in both debug (#[should_panic]) and release (Err return); DriverRegistry insert/lookup ≤ 500 ns for a 256-driver registry (§4 ceiling).

13.5 Conformance Fixtures

illegal_transition_rejected.json — attempts every non-edge in §8.4's table, expects rejection. registry_deterministic_order.json — 10 drivers registered in randomized order across 3 runs, expects identical iteration order.

13.6 Pitfalls

  1. Associated types on Driver/Bus break dyn dispatch — every method avoids them, following Rust-for-Linux's driver.rs convention (§5 Ref-impl 3).
  2. AtomicState::compare_exchange looping under contention — bounded by design, since one device is probed by at most one resolver thread at a time (P2).
  3. RefCount overflow from more pins than expected — saturating arithmetic plus a telemetry counter, never silent wraparound.

13.7 Performance Concerns

DriverRegistry lookup is O(log N) via BTreeMap; for the §4 device ceiling this is dominated by cache-line misses, not comparisons — acceptable against the generous 500 ns target.

13.8 Edge Cases

Two drivers registered with an identical (priority, load_order, name) key — rejected at registration as a configuration error, never silently overwritten. A Device whose parent: Weak has already been dropped — upgrade() returns None; I8 guarantees this cannot happen for a live child.

13.9 Failure Analysis

Symptom: an illegal transition slips through in release mode. Detection: release builds still return Err from the transition function (the caller-visible contract holds in both profiles, not just debug assert!). Blast radius: limited to the one Device. Recovery: caller-visible Err forces explicit handling, no default retry.

13.10 Operational Notes

Every transition emits ddf_device_state_transition{from,to} (I1's telemetry column); dashboards render this as a flow graph to spot devices oscillating between two states — an early PM-bug signature (§19).

14. Phase 2 — Probe & Match Engine

14.1 Objectives

Implement ddf-probe's resolver exactly per §8.2's three-tier algorithm; implement the RAII rollback for I7.

14.2 Detailed Implementation Steps

Implement probe_one(device, registry) -> Result<ProbeOutcome, ProbeError> per §8.2 steps 1–9. Implement the tie-break comparator as a total order over (Reverse(priority), load_order, name) (P2, I14). Implement the probe-path RAII guard (ProbeGuard) wrapping the in-progress ResourceSet; its Drop calls the resource manager's release path (§15) on Err (I7). Cap retries at 3 (§8.2 step 9) with a ddf_probe_retry_total counter, following Ryzhyk et al.'s Dingo (EuroSys 2009, §5 Papers item 4) bounded-retry pattern that prevents an unbounded probe loop.

14.3 Deliverable

ddf-probe::probe_one fully implemented, exercised against ddf-mockbus fixtures with 2+ competing drivers per device.

14.4 Acceptance Criteria

Resolution ≤ 5 ms per device (§4); bit-identical results across 1,000 replays of one fixture seed (I14); a 4-driver competition fixture resolves to the documented tier-1 winner in 100% of runs.

14.5 Conformance Fixtures

probe_tier1_priority.json, probe_tier2_loadorder.json, probe_tier3_name.json — one per tie-break tier (§8.2). probe_retry_cap.json — 4 always-failing drivers, expects exactly 3 retries then Unbound.

14.6 Pitfalls

  1. An uncapped probe loop on a device with many failing matches starves the resolver thread — capped at 3 (§8.2).
  2. An inverted tie-break comparator (ascending instead of descending priority) silently inverts every resolution — caught by the tier-1 fixture, which is why it is a named fixture and not an assumption.
  3. A driver's probe() panicking instead of returning Err bypasses the RAII guard in no_std (no unwind support) — probe() panic-freedom is a code-review-enforced contract, tracked as an open risk (§23 FM-9).

14.7 Performance Concerns

The registry scan for match_drivers is O(N) in driver count per device; well under the 5 ms target for §4's 256-device ceiling. A vendor/device-ID index (PhaseDeferred("§14") — see §35) is not yet load-bearing.

14.8 Edge Cases

Zero registered drivers (resolves to Unbound, no error). A driver's match_drivers mismatching across bus types — guarded by the resolver only invoking a driver against buses it declared support for. Concurrent probe attempts on one device from two bus-scan threads — serialized by I1's compare_exchange denying a second Unbound → Probing.

14.9 Failure Analysis

Symptom: a device never leaves Probing. Detection: ddf_device_state_transition telemetry shows no outbound edge within a watchdog window. Blast radius: one device; siblings unaffected (I8's hierarchy isolates it). Recovery: watchdog forces Probing → Unbound after 2 s and logs FM-9.

14.10 Operational Notes

ddf_probe_duration_ms feeds §28 M1; ddf_probe_retry_total above 10 per boot alerts — usually a misconfigured driver-priority table, not a hardware fault.

15. Phase 3 — Resource Manager (MMIO Regions & Claims)

15.1 Objectives

Implement ddf-mmio — the sole path to claim/release MMIO and I/O-port regions; enforce I12 (no overlap) and I2 (no bypass).

15.2 Detailed Implementation Steps

Implement a range-tree (BTreeMap<PhysAddr, ClaimedRange>, P12) for MMIO claims. claim(base, size) checks interval overlap against every live claim before insertion (I12). release(claim_id) removes the entry. ResourceSet::mmio (§11) is the only caller-visible handle — no driver constructs Resource::Mmio directly (I2, enforced via a module-private constructor — ADR-16's capability discipline applied to MMIO). The RAII Drop for a claimed region calls release automatically on driver remove() or probe rollback (I7, P3).

15.3 Deliverable

ddf-mmio::claim/release fully implemented; exercised against ddf-mockbus fixtures including a deliberate overlap attempt.

15.4 Acceptance Criteria

Claim/release ≤ 1 ms per allocation (§4); overlap rejected 100% across a randomized 10,000-operation fuzz sequence (I12); zero leaked ranges after 1,000 probe-then-remove cycles (I7/P3, asserted via ddf-verifier).

15.5 Conformance Fixtures

mmio_overlap_rejected.json — two devices claim overlapping ranges; the second must fail with ResourceError::Overlap. mmio_release_on_remove.json — claim then remove; the range-tree must show zero entries for that device afterward.

15.6 Pitfalls

  1. A driver that maps MMIO and panics before remove() leaks kernel virtual address space unless the RAII guard is tied to the Device's own lifetime, not the driver's execution path.
  2. A BAR reported as 64 KiB but only 16 KiB actually decoded (mis-sized BAR, §20 N.6) hangs the bus if trusted blindly — ddf-mmio claims exactly what the bus backend's size-probe sequence reports, never a driver-supplied guess.
  3. Range-tree rebalancing under hot-plug-storm churn — bounded O(log N) by the §4 224-device ceiling.

15.7 Performance Concerns

Range-tree lookup dominates claim latency; BTreeMap keeps this O(log N) with good cache locality for ≤256 devices × ≤4 ranges each.

15.8 Edge Cases

Zero-size claim (rejected as a configuration error). A claim spanning a page boundary (handled by the underlying mapping primitive, not ddf-mmio's range tracking). A double-release of one claim ID (rejected — the entry is gone after the first release; the guard is a single-shot consumed Drop token).

15.9 Failure Analysis

Symptom: two devices report garbled register reads. Detection: ddf_mmio_conflict_total should have caught an overlap at claim time; an unsafe direct-MMIO access bypassing ddf-mmio (a P3 violation) is invisible to this telemetry — why P3 is enforced structurally, not by convention. Blast radius: the two overlapping devices (I12). Recovery: code-review audit for any unsafe MMIO access bypassing ddf-mmio.

15.10 Operational Notes

ddf_mmio_claim_total/ddf_mmio_conflict_total feed a per-boot MMIO-map dump (tools/descriptor-dump --mmio-map), used by the "device disappears under load" runbook (§24) when AER-adjacent corruption is suspected.

16. Phase 4 — IRQ Subsystem (Top/Bottom Half, Threaded IRQs)

16.1 Objectives

Implement ddf-irq (top-half dispatch, spurious containment) and ddf-bottom-half (deferred worker pool); enforce I4 and P6/P7.

16.2 Detailed Implementation Steps

Implement the IRQ vector table (§11 IrqHandler) as a lock-free-read fixed array indexed by vector number, written only during bind/unbind (I2). Top-half dispatch: on assertion, call registered handlers in priority order until one returns Handled; if none does, increment a per-vector spurious counter and disable the vector past threshold (containment per P9, following Love's Linux Kernel Development Ch.7 — §5 Books item 2). WakeBottomHalf(BottomHalfRef) enqueues onto the ddf-bottom-half pool (ADR-07); the pool is the only context permitted to sleep or lock (P7, I4) — enforced at the type level, since IrqHandler::handle's signature names no blocking-capable primitive. Threaded-IRQ support: a handler that always returns WakeBottomHalf gets a dedicated worker-thread context, equivalent to Linux's request_threaded_irq.

16.3 Deliverable

ddf-irq dispatch + ddf-bottom-half pool fully implemented; a synthetic MockBus IRQ source exercises both a fast (Handled in top-half) and slow (bottom-half-deferred) handler.

16.4 Acceptance Criteria

Top-half dispatch p50 ≤ 1 µs, p99 ≤ 10 µs (§4, feeds §28 M2); bottom-half wakeup p50 ≤ 5 µs (§4); a spurious-IRQ fixture disables the vector at exactly 1,000 unclaimed assertions, never before 999.

16.5 Conformance Fixtures

irq_tophalf_latency.json — 10,000 synthetic assertions measured against the §4 p50/p99 targets. irq_spurious_containment.json — asserts the exact 1,000-assertion disable threshold. irq_threaded_deferred.json — asserts a threaded-IRQ handler's bottom-half runs in a sleep-capable context.

16.6 Pitfalls

  1. A top-half handler holding a spinlock the bottom half also takes deadlocks the moment the bottom half runs on another core mid-top-half — mitigated by a lint (no-cross-context-lock) flagging any lock shared across the boundary (P7).
  2. A shared legacy INTx vector where one consumer never ACKs causes every sibling handler to be re-invoked needlessly — by design (the dispatch loop always calls every registered handler), so a non-ACKing driver shows as elevated call counts on siblings, not a silent stall.
  3. Threaded-IRQ starvation if too many devices share one worker-pool priority — per-priority pool partitioning (PhaseDeferred("§16") — see §35) is revisited once occupancy telemetry crosses 80% of pool capacity.

16.7 Performance Concerns

Top-half handler lookup is a fixed-index array read (O(1)) — the 224-vector ceiling (§4) makes a flat array cheaper than a tree. Bottom-half wakeup cost is dominated by the host scheduler's context-switch latency, delegated per ADR-07.

16.8 Edge Cases

An IRQ vector shared by 8 devices where the 8th handler always returns NotHandled but the vector still resolves via devices 1–7 — no containment triggers because someone claims it; per-handler (not just per-vector) telemetry surfaces the buggy 8th separately. A bottom-half task that never completes — the pool watchdog logs FM-3 without killing the underlying thread (no safe preemption; a known limitation, §29).

16.9 Failure Analysis

Symptom: CPU pinned near 100% in the bottom-half pool's scheduling class. Detection: ddf_tophalf_duration_us is normal but ddf_bottomhalf_queue_depth is saturated. Blast radius: every device sharing the pool, not just the offender (a known pool-wide tradeoff, §29). Recovery: the "IRQ storm" runbook (§24) reroutes the offending vector to no CPU, buying time for a driver fix.

16.10 Operational Notes

ddf_irq_spurious_total and ddf_tophalf_duration_us are the primary IRQ dashboard metrics; the spurious counter returning to 0 after a driver fix ships is the standard "confirmed resolved" signal.

17. Phase 5 — DMA & IOMMU Integration

17.1 Objectives

Implement ddf-dma (coherent + streaming mapping) and ddf-iommu (group/translation); enforce I5, I6, P5.

17.2 Detailed Implementation Steps

Implement DmaAllocator (§11) with map_coherent/map_streaming; IOMMU-mediated translation via IommuGroup lookup (I6); a bounce-buffer fallback for the non-IOMMU legacy path (P5, ADR-24). Enforce sync_for_device/sync_for_cpu via typestate (I5): a DmaMapping in device-owned state cannot be read by the CPU without transitioning through sync_for_cpu first — following Bovet & Cesati's cache-coherency model (Ch.13, §5 Books item 3).

17.3 Deliverable

ddf-dma + ddf-iommu implemented; a MockBus IOMMU-group fixture and a non-IOMMU bounce-buffer fixture both green.

17.4 Acceptance Criteria

Streaming map setup ≤ 5 µs p50 (§4, feeds §28 M4); coherent one-time setup ≤ 50 µs; 100% of cross-group access attempts trapped in the IOMMU-fault fixture (I6); zero stale-cache-read fixture failures across 10,000 sync-boundary crossings (I5).

17.5 Conformance Fixtures

dma_sync_ordering.json — asserts access without prior sync is rejected at the API boundary. iommu_cross_group_fault.json — a device from group A attempts group B's mapping, expects a fault and quarantine. dma_bounce_buffer_fallback.json — a MockBus fixture with no IOMMU group assigned, expects the bounce-buffer path.

17.6 Pitfalls

  1. A streaming map not synced before device access reads stale cache — I5's typestate closes this at compile time in-tree; ADR-16's capability boundary is the last defense at the unsafe FFI edge.
  2. IOMMU groups bundle physically-grouped devices — passthrough-adjacent designs risk pulling in unwanted neighbors (out of scope, §1); the framework exposes group membership rather than hiding it.
  3. Bounce-buffer copy cost mistaken for "free" DMA on legacy hardware — bounce vs. direct path bandwidth is telemetry-tagged separately (§28).

17.7 Performance Concerns

IOMMU page-table walk dominates map setup (Kadav & Swift, ASPLOS 2012, §5 Papers item 6); reusing pre-mapped coherent buffers instead of remapping per-transfer is the standard optimization, applied to descriptor rings (§8.5).

17.8 Edge Cases

A mapping request exceeding the 64-slot-per-device ceiling (§4) — rejected with DmaError::ExhaustedSlots. A misaligned length request (not IOMMU-page-granularity aligned) — rejected with DmaError::MisalignedLength, never silently rounded. Suspend requested while streaming mappings are in flight — drain is awaited before the D0→D3 transition proceeds (I9, §19).

17.9 Failure Analysis

Symptom: a device reads/writes wrong data intermittently. Detection: ddf_dma_sync_total anomaly (a device access recorded with no preceding sync_for_device). Blast radius: one device's data integrity when the typestate is honored; a kernel-memory-safety issue only if bypassed at the unsafe FFI boundary. Recovery: the "device disappears/misbehaves under load" runbook (§24) checks this trace first.

17.10 Operational Notes

ddf_iommu_fault_total is the primary DMA-attack detection signal (§22 T3); any nonzero value outside a fuzz run is a P1 alert.

18. Phase 6 — Hot-Plug & Refcounted Lifecycle

18.1 Objectives

Implement ddf-hotplug's sequenced event queue and the device refcounting discipline; enforce I3, I10, I11.

18.2 Detailed Implementation Steps

Implement EventQueue (§11) as a bounded per-bus MPSC ring (128 events, ADR-20); push assigns the next monotonic sequence number (I10); the dispatcher pops in strict sequence order. Implement refcount pinning: every open /dev/ FD, every in-flight IRQ handler invocation, every live DmaMapping increments Device.refcount on acquire and decrements on release (I3, P11). Unplug transitions Device → Removing (§8.4) without freeing; Freed happens only at refcount 0 (I3). Post-Removing calls return ENODEV (I11) — dispatch checks state before reaching driver code.

18.3 Deliverable

ddf-hotplug fully implemented; a MockBus fixture interleaves plug/unplug/replug against an open FD and asserts no crash and correct ENODEV behavior.

18.4 Acceptance Criteria

Plug-to-bind ≤ 200 ms p99 (§4, feeds §28 M5); refcount drain on unplug ≤ 2 s p99 (§4) or the device is forced to Quarantined (FM-3 escalation); a 10,000-iteration interleaved plug/unplug/replug fuzz shows zero out-of-order deliveries (I10) and zero use-after-free (I3/I11, sanitizer-checked in the std test harness).

18.5 Conformance Fixtures

hotplug_sequence_order.json — interleaves plug/unplug across 2 devices on one bus, expects strict per-bus sequence delivery. hotplug_fd_pin_survives_unplug.json — opens a /dev/ FD, unplugs, expects Removing without free until the FD closes, then ENODEV on the next syscall. hotplug_queue_overflow.json — floods 200 events into a 128-capacity queue, expects drop-oldest + telemetry (ADR-20).

18.6 Pitfalls

  1. Unplug during an in-flight syscall must not crash — the FD pins refcount before the syscall dispatches, guaranteeing the Device outlives the call (P11).
  2. A leaked refcount (missing decrement on an error path) keeps a device alive past unplug forever — the debug-build tracker (I3's detection column) flags a nonzero refcount N seconds after Removing with no forward progress.
  3. Hot-plug during enumeration (a hub's port-change interrupt firing mid-walk) can produce two parallel enumerations on the same address — serialized per-bus via a mutex held during enumeration (§20 N.6 documents the USB-specific case).

18.7 Performance Concerns

The per-bus sequence counter and MPSC queue are the only serialization points; contention is bounded by bus count (few), not device count (many), keeping the hot path cheap.

18.8 Edge Cases

A device replugged before its refcount drains from the prior unplug (rapid remove/insert) — the new plug queues behind the still-draining Removing state; the resolver treats it as a fresh DeviceId only once Freed completes, never reusing an in-flight one. A bus reporting unplug for a device that never successfully bound (failed probe, still Unbound) — a no-op, since Unbound never held resources.

18.9 Failure Analysis

Symptom: a device shows Bound in telemetry long after physical removal. Detection: ddf_device_refcount_gauge nonzero with no owning FD/IRQ/DMA activity beyond the refcount-drain bound. Blast radius: one device slot unusable until manual intervention. Recovery: the "device disappears under load" runbook's Case 3 path — forced quarantine plus operator-triggered removal.

18.10 Operational Notes

ddf_hotplug_seq_gap_total (should be 0) and ddf_device_refcount_gauge are the two hot-plug dashboard metrics; a udevadm monitor-equivalent event stream is exposed via ddf-userspace for operator visibility (§24).

19. Phase 7 — Power Management State Machine

19.1 Objectives

Implement ddf-pm's total (state, event) transition function; enforce I9, P10.

19.2 Detailed Implementation Steps

Implement PmState/PmEvent (§11) with an exhaustive match rejecting any unhandled pair at build time (I9) — Rust's exhaustiveness checking on the match is the enforcement mechanism, not a runtime check. Wire SuspendRequest to first quiesce bottom-half work for the device, then await DMA drain (§17's in-flight-mapping tracking) before invoking driver.suspend() (P10). Wire ResumeRequest to invoke driver.resume(); on Err, transition to Quarantined per §8.4 rather than leaving the device in an undefined power state. Implement runtime-PM: an idle-timeout daemon auto-issuing SuspendRequest(D3Hot) for devices with no activity for a configurable window.

19.3 Deliverable

ddf-pm fully implemented; a MockBus fixture drives every power-related (state, event) pair from §8.4 and asserts the exhaustive match compiles with no wildcard arm and behaves per the table.

19.4 Acceptance Criteria

Suspend ≤ 10 ms (§4, excludes DMA drain, feeds §28 M7); resume ≤ 50 ms (§4, feeds §28 M8); 100% of the (state, event) pairs in §8.4 resolve without reaching a wildcard arm (I9 — compile-time evidence plus a runtime fixture enumerating every pair).

19.5 Conformance Fixtures

pm_suspend_resume_roundtrip.json — a full D0→D3Hot→D0 cycle, expects suspend/ resume each invoked exactly once. pm_suspend_waits_for_dma.json — an in-flight streaming mapping at SuspendRequest, expects Suspending to hold until drain completes. pm_resume_failure_quarantine.json — driver.resume() returns Err, expects Device → Quarantined per §8.4.

19.6 Pitfalls

  1. Suspend during in-flight DMA causes data loss if not drained first — suspend explicitly awaits drain before invoking driver.suspend().
  2. A driver bypassing the PM API to poke hardware into D3 directly desyncs the framework's tracked state from physical reality — the driver API has no direct-register-poke path outside the probe/suspend/resume callbacks (P8 extended to power state).
  3. An IRQ asserting during suspend for a level-triggered device not first disabled floods on resume — suspend disables all IRQ lines for the device before the transition completes.

19.7 Performance Concerns

DMA-drain wait dominates suspend latency variance; the 10 ms target explicitly excludes this wait (§4) so it is measured and reported separately, avoiding a misleading combined metric.

19.8 Edge Cases

A SuspendRequest arriving while already Suspending (duplicate/racing request) — rejected as a no-op with telemetry, not queued twice. A device with zero in-flight DMA at suspend time (drain is instant, the common case) — must not add artificial latency. Runtime-PM auto-suspend racing a driver-initiated operation — the idle-timeout daemon checks a last-activity timestamp updated by every top-half/bottom-half touch.

19.9 Failure Analysis

Symptom: suspend succeeds but resume fails, device unusable after wake. Detection: ddf_pm_unhandled_transition_total stays 0 (by construction) but driver.resume()'s Err path is visible via PM-tagged failure telemetry. Blast radius: one device — each device's PM state is independent, so system-wide suspend/resume is unaffected structurally. Recovery: the framework forces Quarantined and a forced re-probe applies (the "hot-plug enumeration hangs"-adjacent runbook, §24).

19.10 Operational Notes

ddf_pm_state (gauge, per device) and ddf_pm_unhandled_transition_total (must stay 0) are the PM dashboard signals; a nonzero unhandled-transition count is a build-time-impossible event and is treated as a P0 alert.

20. Phase 8 — Bus Backends (PCI, USB) & MockBus Hardening

20.1 Objectives

Implement ddf-bus-pci and ddf-bus-usb against real enumeration protocols; harden ddf-mockbus to model both buses' quirks for pre-hardware conformance (P14).

20.2 Detailed Implementation Steps

PCI: implement the (bus, device, function) walk, vendor-ID probe, header-type multifunction check, BAR size-probe ("write all-1s, read-back, restore," §8.5), MMCONFIG extended config-space access, MSI/MSI-X capability-list discovery (Corbet et al. Ch.12, §5 Books item 1). USB: implement reset/address-assignment/descriptor-fetch enumeration (§8.6), bounds-checked descriptor parsing (I13), hub port-status handling with per-bus enumeration serialization (§18.6 cross-reference). Extend ddf-mockbus with PCI-shaped and USB-shaped fixtures (malformed descriptors, mis-sized BARs, bridge subordinate-bus-number edge cases) so every §20.6 pitfall has a MockBus-level regression fixture, not only a QEMU-level one (P14).

20.3 Deliverable

ddf-bus-pci enumerates a QEMU PCI topology including a bridge; ddf-bus-usb enumerates a QEMU xHCI-attached mass-storage device; both bind a canonical driver.

20.4 Acceptance Criteria

Full PCI bus enumeration ≤ 100 ms (§4); single USB device enumeration ≤ 500 ms (§4); the BAR size-probe fixture restores the firmware-assigned address correctly in 100% of 1,000 randomized BAR-value fuzz runs; the malformed USB descriptor fixture (§8.6) rejects 100% of over-length sub-descriptors.

20.5 Conformance Fixtures

pci_bar_size_probe_restore.json — fuzzes BAR values, asserts exact restore. pci_bridge_subordinate_walk.json — a 2-level bridge topology, asserts every downstream device is reachable. usb_malformed_descriptor_reject.json — the §8.6 truncation shape. usb_hub_concurrent_port_change.json — two ports change simultaneously, asserts serialized (not interleaved) enumeration.

20.6 Pitfalls

  1. PCIe extended config space (4 KiB) requires MMCONFIG mapping; legacy CF8/CFC ports expose only the first 256 bytes — reading capability data beyond byte 256 via the legacy path silently truncates.
  2. MSI-X vectors live in an MMIO table inside a BAR at a capability-declared offset — conflating this with the capability structure itself is a common implementation bug.
  3. A PCI bridge's secondary/subordinate bus numbers set incorrectly strand every downstream device as unreachable (a historical bug class, §37).
  4. Two USB devices attaching to sibling hub ports simultaneously without per-bus serialization can interleave reset/address-assignment, causing one device's SetAddress to land on the other's pre-address state.

20.7 Performance Concerns

PCI enumeration time is dominated by MMCONFIG access latency, not computation — caching the device list per boot rather than re-walking on every query is the standard optimization. USB enumeration is dominated by the mandatory 10 ms reset window, a protocol floor, not an implementation inefficiency.

20.8 Edge Cases

A PCI function reporting vendor ID 0xFFFF at a non-zero function of a single-function device — treated as "no device," not an error. A USB device that resets mid-enumeration — retried up to 3 times (mirroring §14's retry cap, ADR-23) before giving up. A BAR reporting size 0 (no BAR present) — skipped, never mapped, guarded by an explicit len > 0 assertion before returning to the driver.

20.9 Failure Analysis

Symptom: a device behind a PCI bridge never appears. Detection: compare the bridge's reported subordinate bus number against the highest bus number actually assigned during the recursive walk; a mismatch is logged. Blast radius: every device downstream of the misconfigured bridge (I8's hierarchy makes this containment visible, not silent). Recovery: re-walk with corrected bus-number assignment; a firmware-supplied topology that is itself wrong is documented as an ADR-level divergence from firmware trust (§22 T1).

20.10 Operational Notes

tools/descriptor-dump --pci-tree/--usb-tree render the live enumeration state for the "hot-plug enumeration hangs" runbook (§24); structured logs tag every enumeration step with the (bus, device, function) or (hub, port) tuple.

21. Phase 9 — Conformance, Fuzzing & Adversarial-Device Hardening

21.1 Objectives

Close the loop on P14: prove I1–I14 hold under adversarial and malformed device behavior via ddf-verifier's full bucket suite, ddf-fuzz's coverage-guided fuzzers, and a differential test against Linux's drivers/base/ behavior on a curated topology.

21.2 Detailed Implementation Steps

Wire every conformance/buckets/ fixture (§10) into CI as a required gate (ADR-13). Implement ddf-fuzz targets usb_descriptor.rs and virtio_vring.rs (§10) as structure-aware (not byte-random) fuzzers seeded with the CVE-2016-2384 shape (§8.6, §37) and a virtio vring double-use shape (I13) — complementary to the static verification approach of Ball & Rajamani's SLAM/SDV (§5 Papers item 5), which this dynamic fuzzing does not replace. Implement the differential harness: replay an identical boot-and-hot-plug script against both ddf and a reference Linux VM, diff the resulting device topology and bind outcomes (documented divergences become ADRs, per §5 Ref-impl 1's lesson). Stand up the 24 h fuzz canary (§4, §28 M12) in nightly CI (ADR-13's fuzz-nightly.yml).

21.3 Deliverable

Full conformance bucket suite green in CI; both fuzz targets running with zero crashes over a 24 h canary; differential report showing zero undocumented divergences from the curated Linux baseline.

21.4 Acceptance Criteria

Conformance suite completes in ≤ 15 minutes in CI; 24 h fuzz canary reports 0 panics and 0 sanitizer violations (§28 M12); differential harness shows 100% topology match on the curated boot sequence, with any intentional divergence documented as a named ADR.

21.5 Conformance Fixtures

differential_linux_boot_topology.json — the curated boot+hotplug script replayed against both systems. fuzz_regression_cve_2016_2384_shape.json — the truncated- descriptor shape locked as a permanent regression fixture (ADR-12). fuzz_regression_ virtio_double_use.json — a descriptor reused twice, expects rejection (I13).

21.6 Pitfalls

  1. A fuzz target that only mutates bytes randomly (not structure-aware) spends its budget on inputs rejected at the earliest length check, never reaching deeper parser logic — both targets are structure-aware, mutating field-by-field.
  2. Treating Linux's behavior as unconditionally correct during differential testing — Linux's own historical bugs (§37) are not a spec to match; divergences are triaged, not auto-fixed to match.
  3. A 24 h canary reusing the same seed every night never explores new input space — nightly runs use a fresh seed logged alongside the corpus for reproducibility on failure.

21.7 Performance Concerns

Differential replay cost is dominated by booting the reference Linux VM, not the ddf side — amortized by running the differential suite per-merge-to-main rather than per-commit like the mockbus conformance suite.

21.8 Edge Cases

A fuzz-discovered input violating an invariant only under a specific IOMMU-group configuration — the fuzz corpus captures the full MockBus fixture state, not just the malformed bytes, so it is exactly reproducible. A differential mismatch caused by nondeterminism on the Linux side itself — flagged and excluded from the comparison baseline, not silently ignored.

21.9 Failure Analysis

Symptom: the nightly fuzz canary reports a new crash. Detection: CI fails fuzz-nightly.yml and attaches the minimized crashing input. Blast radius: contained to the specific parser/invariant the crash exercises (I13's structural bounding). Recovery: the crashing input becomes a new named fixture in conformance/buckets/ (closing the loop into per-commit CI), then the root cause is fixed and the fixture must pass.

21.10 Operational Notes

The fuzz corpus (fuzz/corpus/) is versioned in-repo so a corpus regression is bisectable; the differential report is published per-merge as a build artifact, giving operators a standing answer to "how close are we to Linux's behavior" without re-running it manually.

24. Operational Readiness

Metrics. Every counter/gauge/histogram named throughout (§7's Telemetry column, §22, §23) is exported via the ddf_* namespace; §28's M-table is the CI-gated subset.

Tracing. Structured tracing spans (ADR-09) wrap every probe/bind/unbind/suspend/ resume; span fields carry device_id, bus_id, and the invariant ID being enforced where applicable.

Structured logging. Every enumeration step, resource claim, and state transition logs a structured (not free-text) record tagged with (bus, device, function) or (hub, port) as appropriate (§20.10).

Dashboards. Three primary boards: IRQ (spurious rate, top-half latency — §16.10), hot-plug (sequence gaps, refcount gauges — §18.10), power (per-device PM state, unhandled-transition count — §19.10).

Alerting philosophy. Structural invariants (I9's unhandled-transition count, I14's nondeterminism count) alert at any nonzero value — they are build-time-impossible by construction, so a nonzero reading indicates corruption, not degraded performance. Latency/throughput metrics (§28 M-table) alert on sustained threshold breach, not a single sample.

SLOs. Derived directly from §4/§28: 99% of probe attempts succeed without a framework-caused failure (§4's 0.1% budget); p99 hot-plug plug-to-bind ≤ 200 ms (M5); 0 kernel-memory-safety violations from device-supplied data, unconditionally (I13).

Incident response. Named runbooks (below) are the first response artifact; each maps a symptom to a diagnosis sequence and a remediation, mirroring the format established for "device disappears under load," "IRQ storm," and "hot-plug enumeration hangs" (carried forward from the salvaged original document and re-anchored to this blueprint's IDs).

Named runbooks.

  • Device disappears under load — diagnoses PCI AER/CPER errors, bus resets, or driver crashes (FM-4, FM-6); checks ddf_iommu_fault_total and ddf_dma_sync_total (§17.9).
  • IRQ storm — diagnoses a runaway vector (FM-5); checks ddf_irq_spurious_total; remediates via affinity rerouting (§16.9).
  • Hot-plug enumeration hangs — diagnoses a stuck USB/PCI enumeration (FM-9, §20.9); checks tools/descriptor-dump --usb-tree/--pci-tree.

Backup/restore. N/A for kernel-context state (none is persisted, ADR-04); the conformance-report artifacts (§12.10) and fuzz corpus (§21.10) are the durable build-time artifacts and are versioned in-repo.

Deployment topology. Statically linked into the host kernel image (§1); no independent deployment unit — the framework's "deployment" is the host kernel's own build and boot.

Canary / rolling-upgrade / rollback / migration strategy. The 24 h fuzz canary (§21, M12) is the pre-production gate; there is no in-place rolling upgrade of a running kernel-context framework — an upgrade is a new kernel build + reboot. Rollback is booting the previous kernel image. Migration across a framework version is bounded by §25's compatibility guarantees.

25. Compatibility & Versioning

Wire compatibility. Bus wire protocols (PCI config space, USB descriptors, virtio vrings) are external specifications (§5 RFCs); DDF never alters them, only parses them — wire compatibility is inherited, not designed.

Storage compatibility. N/A — no persistent on-disk state (ADR-04).

Schema evolution. DeviceProperties' TLV encoding (ADR-05) permits additive fields without breaking existing readers; a reader unaware of a new tag skips it by length, never by assumed offset.

API stability. Crate-level public APIs (§11) follow SemVer (ADR-17): a breaking change to any pub trait/pub struct signature is a major version bump; adding a new optional method with a default is minor; a bugfix with no signature change is patch.

Migration. A major-version bump to ddf-core requires every ddf-bus-* and downstream driver crate to be recompiled against the new trait signatures — there is no cross-version dynamic linking of driver crates (kernel-context crates are statically linked into one kernel image, §1).

Deprecation policy. A deprecated API is marked #[deprecated] with a migration note for one minor version before removal in the next major version; removal is itself a breaking (major) change.

SemVer policy. Applies to every crate in crates/ independently; ddf-core's version is the one downstream crates pin against most strictly, since it carries the trait definitions of §11.

Rolling-upgrade guarantees. None within a single running kernel instance (§24); a fleet of independently-booted hosts may run different DDF versions simultaneously as long as each host's kernel image is internally version-consistent.

26. Testing & Verification Strategy

Unit tests. Per-crate, exercising individual functions (e.g. the tie-break comparator, §14.2) in isolation.

Integration tests. Cross-crate, exercising a full probe→bind→remove cycle against ddf-mockbus (§12–§21's Deliverables).

Property-based tests. The 10,000-operation randomized MMIO claim/release fuzz (§15.4) and the 1,000-BAR-value randomized fuzz (§20.4) are property tests: "no overlap ever accepted," "restore is always exact," checked across randomized inputs rather than fixed examples.

Differential tests. §21's harness against a reference Linux VM — the strongest external-correctness signal available, since Linux's drivers/base/ (§5 Ref-impl 1) is the most-exercised implementation of this exact problem domain.

Fuzzing. Coverage-guided, structure-aware (§21.2); the primary technique for finding the CVE-2016-2384-class defect this framework exists to prevent (I13).

Chaos / fault injection. The hot-plug interleaving fuzz (§18.4) and the IOMMU cross-group fault fixture (§17.5) are fault-injection tests: deliberately triggering the adversarial condition rather than waiting to observe it.

Deterministic replay. Every ddf-verifier fixture runs with a fixed seed (P12, I14); a failing run is replayable bit-for-bit for debugging, unlike a nondeterministic integration test.

Soak. The 24 h fuzz canary (§21.3, M12) doubles as a soak test — zero panics over a sustained run surfaces slow leaks (FM-1, FM-3) that a short test would miss.

Conformance. conformance/buckets/ (§10) is the authoritative pass/fail gate for every invariant I1–I14; each fixture asserts exactly one invariant (§7's debugging methodology).

Performance-regression gating. §28's M-table is CI-gated: a merge that regresses any M-target beyond its threshold fails CI, per ADR-13's topology.

Tie-back. Every N.5 Conformance Fixtures entry across §12–§21 names the invariant(s) it asserts; §7's table is the master cross-reference from invariant to enforcing phase.

27. Build & Release Engineering

Reproducible builds. Cargo.lock is committed and CI-verified byte-identical across two independent build machines (a standard reproducible-build check); combined with ADR-03's vendored+audited dependency policy.

Artifact signing. Release crate artifacts are signed with a project-held key; signature verification is a precondition for the release-channel promotion in CI.

SBOM. Generated per release from Cargo.lock (cargo-cyclonedx-style tooling), published alongside the release artifacts for downstream supply-chain audits.

Release channels. main (continuous, unstable API per ADR-17), tagged minor/major releases (stable API), and a long-term branch for kernel integrators who need a fixed ddf-core trait surface for an extended window.

CI/CD topology. Per ADR-13: matrix build (native + QEMU, debug + release) on every PR; the differential suite (§21) and fuzz-nightly canary (§21.3) run on merge-to-main and nightly respectively, not on every PR, to bound CI latency.

Version stamping. Every built artifact embeds its crate version + git commit hash, queryable via tools/ at runtime for incident forensics (§23's Forensics columns).

Provenance/attestation. CI-produced artifacts carry a build-provenance attestation (builder identity, source commit, build inputs) verifiable independently of the CI system itself.

Dependency auditing. cargo-vet (ADR-03) gates any new or updated dependency behind a recorded audit entry before it can land in a release build; host-side-only test crates (ddf-fuzz corpora) are exempt per ADR-03's stated regime.

29. Scalability Analysis

Constant regardless of device count. Per-bus sequence counters (§18.2), the IRQ vector table's fixed 224-entry array (§16.7) — both sized by hardware topology, not device count.

Grows with device count, O(log N). DriverRegistry lookup (§13.7), ddf-mmio's range-tree (§15.7) — both BTreeMap-backed, chosen specifically for this scaling shape (ADR-18).

Grows with device count, O(N). ddf-probe's per-device driver-registry scan (§14.7) — the dominant term in probe latency (M1) at scale; acceptable up to §4's 256-device ceiling, the first named bottleneck.

Named bottlenecks in order. (1) Probe/match O(N) driver scan (§14.7) — mitigated today by the ≤256-device/modest-driver-count product staying under 5 ms; a vendor/device-ID index is the lever, deferred (§35) until telemetry shows it's needed. (2) Bottom-half worker-pool occupancy (§16.6) — the second bottleneck, since every IRQ source sharing one pool competes for the same workers; the lever is per-priority-class pool partitioning (not yet built). (3) Hot-plug queue depth (§18, ADR-20) — bounded at 128/bus by design; the lever beyond that bound is backpressure (drop-oldest), not unbounded growth.

Horizontal scaling. Not applicable within one kernel instance — DDF is single-kernel-scoped (§1's deployment model); "horizontal" scaling here means more independently-booted hosts, each running its own DDF instance with no cross-instance coordination.

Vertical scaling. More IRQ vectors, more DMA slots, and a larger device ceiling are all compile-time constants today (§4); raising them is a recompilation, not a runtime reconfiguration — a deliberate simplicity/scale tradeoff (P3's explicit bookkeeping requires a bound).

Sharding/partitioning. Per-bus event queues (§18.2) are already a natural partition; no cross-bus coordination is required for hot-plug ordering (I10 is scoped per-bus, not global) — this is the load-bearing scalability decision that keeps hot-plug storms on one bus from affecting another.

Coordination overhead. The only global coordination point is the driver registry (§13.2), read-mostly and BTreeMap-backed; write contention only occurs at driver module-load time (rare), not at steady-state probe time.

Practical ceiling. §4's 256-device / 224-IRQ-vector / 64-DMA-slot-per-device bounds define the practical ceiling for the Phase-0-through-9 design as specified; beyond that, the probe-scan bottleneck (above) is the first to bite.

Levers beyond the ceiling. A vendor/device-ID-indexed driver registry (removes the O(N) probe scan); per-priority bottom-half pool partitioning (removes pool-wide blast radius, §16.9); a larger compile-time IRQ/DMA-slot budget (trades static memory for headroom) — all deferred (§35) since none is load-bearing at the Phase-0-through-9 scale.

Linux driver core. The closest structural relative to DDF — both converge independently on the bus/device/driver triangle (§2). The one decision made differently: Linux accepts a shared kernel address space for every driver, trading isolation for the lowest possible IRQ/DMA latency; that wins whenever raw performance dominates and the driver population is trusted and audited, the historical regime for in-tree Linux drivers.

FreeBSD newbus. Structurally close to DDF's tier-1 priority resolution (§8.2), but expresses priority as a raw integer return code from probe() rather than declared driver metadata. That wins when a driver needs to compute its priority dynamically from hardware inspection at probe time (e.g. distinguishing chip revisions) — a case DDF defers (PhaseDeferred("§8.2") — see §35) rather than building into the base resolver.

Windows WDF. Its IRP-based asynchronous I/O queue is the mechanism DDF's /dev/ dispatch (§20) borrows the spirit of, without adopting IRP cancellation semantics wholesale. WDF's decision to keep drivers in the kernel address space (KMDF-wrapped, not isolated) wins when driver vendors need direct hardware-timing access that a syscall-mediated boundary would slow down.

Fuchsia Driver Framework (zircon DDK). Isolates each driver (or small group) in its own process, communicating via IPC — the decision made differently from DDF's same-address-space capability gating. That wins when the driver population is untrusted or updated independently of the kernel (Fuchsia's driver-update-without-reboot goal), at the cost of per-call IPC latency that DDF's §4 IRQ-latency budget cannot afford.

seL4 userspace drivers. Takes isolation to its logical extreme: drivers run as ordinary userspace processes with no kernel privilege, receiving interrupts as IPC notifications. That wins decisively when every driver is treated as potentially malicious and tens-of-microseconds IRQ latency is acceptable — seL4's target regime (embedded/security-critical systems), not DDF's regime (§4's ≤10 µs p99 top-half budget).

  7. Top-half dispatch throughput ceiling. 1 / (1 µs p50, §4) = 1,000,000 dispatches/sec theoretical per-core ceiling before the top-half itself becomes the bottleneck (a sanity ceiling, not an operating target).
  8. Fuzz-canary exploration budget. ~10,000 executions/sec (typical libFuzzer throughput on a small parser) × 86,400 s (24 h, M12) = ≈ 864,000,000 executions per canary run — the number that makes "0 panics over 24 h" meaningful evidence.
  9. Per-mapping DMA-drain budget under refcount pressure. 2,000 ms (§4 refcount-drain p99) / 64 DMA slots/device (§4) = ≈ 31 ms per mapping if drained serially in the worst case — the number that forces parallel (not serial) drain in §17/§19.6.
  10. Bottom-half pool sizing vs. storm rate. At the 1,000-assertion spurious-disable threshold (§16.4) treated as a worst-case rate of ~1,000 storms/sec/vector, an 8-worker pool at ≤ 5 µs wakeup (§4) gives 8 × (1 / 5 µs) = 1,600,000 wakeups/sec theoretical capacity — ≈ 1,600× the single-vector storm rate, showing 8 workers is sufficient before containment (§16) is even needed.

34. Alternative Architectures (Roads Not Taken)

Alt-1 — Fully Isolated Userspace-Driver Model

┌────────────┐  IPC   ┌──────────────┐  IPC   ┌──────────────┐
│ Driver-Host │◄──────►│ Kernel-Resident│◄──────►│ Driver-Host  │
│ Process A   │        │ Resource Arbiter│       │ Process B    │
│ (1 driver)  │        │ (MMIO/IRQ/DMA) │       │ (1 driver)   │
└────────────┘        └──────────────┘        └──────────────┘
     ▲ IPC-delivered interrupt notification, no shared address space ▲

Regime where it wins: an untrusted or frequently-updated driver population, and a security posture tolerating tens-of-microseconds IRQ latency. Real system: seL4 userspace drivers, Fuchsia's DDK (§31). Rejected: §4's ≤ 10 µs p99 top-half budget is incompatible with a per-interrupt IPC round-trip, and §1's target deployment assumes a trusted, audited driver population, not an app-store-style ecosystem.

Alt-2 — Full-VM Driver-Reuse Model

┌───────────┐  paravirt channel  ┌────────────────────────┐
│ Host Kernel│◄──────────────────►│ Driver VM               │
│ (DDF-free) │                    │  unmodified donor kernel│
└───────────┘                    │  + unmodified driver     │
      ▲ hardware passthrough (IOMMU-gated) to the VM ▲       │
                                  └────────────────────────┘

Regime where it wins: reusing a large body of existing unmodified drivers is worth more than a from-scratch safety rewrite (e.g. supporting a large legacy driver catalog unmodified). Real system: LeVasseur et al.'s VM-based driver-reuse design (OSDI 2004, §5 Papers item 3). Rejected: this project's value proposition (§2) is the from-scratch, memory-safe, minimal framework — reusing unmodified C drivers inside a VM sidesteps the exact problem (driver-code memory safety) this blueprint exists to solve, and a full VM-exit per interrupt violates §4's latency budget.

Alt-3 — Flat Device Table, No Bus Hierarchy

┌──────────────────────────────────────────┐
│ Device[256] — fixed global array           │
│  dispatch by hard-coded device-ID switch   │
│  no parent/child, no bus abstraction       │
└──────────────────────────────────────────┘

Regime where it wins: a fixed, small, permanently-known device set (a specific embedded board whose BOM never changes) where hot-plug and IOMMU-group propagation are never needed. Real system: typical embedded-RTOS board-support packages (e.g. FreeRTOS BSPs) that hard-code a device table. Rejected: §1's target explicitly includes hot-pluggable PCI/USB buses with hierarchy requirements (bridge-cascade removal, IOMMU-group propagation, §8.1) that a flat table cannot express without degenerating into a re-implementation of the triangle it was meant to avoid.

36. Glossary

  • AER (Advanced Error Reporting) — PCIe capability reporting correctable/uncorrectable link errors.
  • BAR (Base Address Register) — PCI register declaring an MMIO or I/O region and its size.
  • Bottom half — deferred IRQ work, may sleep, runs in ddf-bottom-half's worker pool.
  • Bus — container/enumerator for devices; the Bus trait (§11).
  • cdev — character device, exposed via ddf-userspace.
  • Coherent DMA — cacheable shared mapping; CPU and device see identical contents without explicit sync.
  • Config space — PCI's per-function register space (256 B legacy, 4 KiB extended).
  • CSR (Control/Status Register) — generic device register terminology.
  • D0/D1/D2/D3 (Hot/Cold) — PM power states from active to deepest sleep (§11 PmState).
  • Device — a bound or unbound hardware unit; the Device struct (§11).
  • DeviceState — the framework's per-device lifecycle enum (§8.4, §11).
  • DMA (Direct Memory Access) — device-initiated memory access, bypassing the CPU.
  • DMA bounce buffer — a kernel-owned intermediate buffer used when no IOMMU is present (P5, ADR-24).
  • Driver — software bound to a device via the Driver trait (§11).
  • EHCI / xHCI / OHCI / UHCI — USB 2.0 / USB 3.x / legacy host-controller interfaces.
  • Endpoint — a USB transfer endpoint within an interface.
  • Firmware — pre-OS code (BIOS/UEFI/device firmware) that hands off enumeration data.
  • GIC (Generic Interrupt Controller) — ARM's IRQ controller architecture.
  • Hot-plug — dynamic plug/unplug event handling (§18).
  • HCD (Host Controller Driver) — the driver for the USB host controller itself.
  • Interface (USB) — a device's functional unit within a configuration.
  • INTx — legacy PCI interrupt lines (INTA–INTD).
  • IOAPIC — I/O Advanced Programmable Interrupt Controller.
  • IOMMU (I/O Memory Management Unit) — translates device-visible addresses to physical addresses (§17).
  • IOMMU group — set of devices sharing one IOMMU translation context (I6, §11).
  • IRP (I/O Request Packet) — Windows WDM's asynchronous I/O abstraction (§31).
  • IRQ (Interrupt Request) — a hardware interrupt line/vector.
  • LAPIC (Local APIC) — per-CPU interrupt controller on x86.
  • MCFG — the ACPI table declaring PCIe extended config-space (MMCONFIG) ranges.
  • MMCONFIG — the memory-mapped mechanism for accessing PCIe extended config space.
  • MMIO (Memory-Mapped I/O) — device registers mapped into the physical address space.
  • MSI / MSI-X — Message-Signaled Interrupts / their extended variant.
  • PCIe (PCI Express) — the modern PCI physical/protocol layer.
  • PMC — power-management capability (PCI config-space capability).
  • Probe — the driver-init callback invoked per matched device (§8.2, §14).
  • PTM (Precision Time Measurement) — a PCIe synchronization feature.
  • Quarantined — the DeviceState reached on malformed input or unrecoverable failure (§8.4, P9).
  • Refcount — the pin count keeping a Device alive while any FD/IRQ/DMA holds it (I3).
  • Resource — an MMIO/I/O/IRQ/DMA claim; the Resource enum (§11).
  • ResourceSet — the per-device collection of claimed Resources (§11).
  • Root complex — the top of the PCIe enumeration hierarchy.
  • Runtime PM — dynamic power management applied while the system is otherwise active (§19).
  • Streaming DMA — a short-lived, directional DMA mapping requiring explicit sync (I5).
  • SR-IOV (Single Root I/O Virtualization) — a device exposing multiple virtual functions.
  • Top half — the bounded, non-sleeping IRQ handler context (P7, I4).
  • Transfer (USB) — control / bulk / interrupt / isochronous, the four USB transfer types.
  • VFIO (Virtual Function I/O) — a userspace passthrough driver framework (§1 non-goal, §34).
  • virtio — the paravirtualized device protocol family (§20).
  • vring — virtio's shared-memory descriptor queue (I13, §20).
  • WDF / WDM (Windows Driver Framework / Model) — Windows's kernel driver model (§31).
