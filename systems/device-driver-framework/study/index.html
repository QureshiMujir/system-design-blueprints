Hard questions (§33)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does an unplug during an in-flight syscall never crash, and what three independent mechanisms would all have to fail simultaneously for it to? (§18.2, §11)
  2. If the IOMMU is absent, what exactly stands between a malicious device and arbitrary physical memory, and what regime makes that residual protection acceptable? (§17.6, §22 T3)
  3. Why is probe/match resolution a three-tier function instead of a single priority integer, and what specific bug class does each tier close that the others don't? (§8.2, §22 T4)
  4. Trace the telemetry signals an operator sees, in order, if a level-triggered device stops acking its IRQ — and explain why the top/bottom-half split doesn't make this worse. (§16.6, §16.10)
  5. Why can a failed probe() retry up to 3 times without ever leaking a resource, when remove() is not retried the same way? (§14.2, §8.7)
  6. What does "the power state machine is total" actually buy operationally, and what would the framework look like without that guarantee — name the specific incident class? (§19.2, §23 FM-8)
  7. Why is the hot-plug event queue scoped per-bus rather than global, and what would break if it were global? (§29, §18.2)
  8. A device is quarantined. Walk through the three different root causes in §8.4 that all land in the same state, and explain how an operator distinguishes them using only telemetry. (§8.4, §24)
  9. Why does the ADR table lock DMA to IOMMU-mediation "by default" rather than "always" — under what regime does the rejected direct-DMA path actually win? (§9 ADR-24, §4)
  10. Explain why deterministic (BTreeMap) iteration is load-bearing for correctness, not just for nice test output — what invariant literally cannot be proven without it? (§6 P12, §7 I14)
  11. Two drivers match a device with identical priority and identical load order — what happens, and why was this case not left as "undefined, pick one"? (§8.2, §22 T4)
  12. Why does the capability-gated driver trait surface matter even though the driver runs in the same address space as the framework — what does it prevent versus a fully isolated userspace-driver model? (§6 P8, §31)
  13. What is the single most expensive step in PCI enumeration, and what two design decisions elsewhere keep it off the runtime hot path? (§20.7, §32)
  14. If the framework had chosen a userspace-driver isolation model instead of capability-gated same-address-space, which numbers in §4 would have to change, and in which direction? (§31, §34)
  15. Why does I7's rollback guarantee depend on RAII rather than an explicit cleanup() call the resolver invokes after a failed probe? (§14.2, §8.7)
  16. The Deferred Features Register defers a vendor/device-ID index for the driver registry. What telemetry signal would need to appear before that deferral should be reconsidered? (§29, §35)
  17. Why does the 24-hour fuzz canary validate something the per-commit conformance suite cannot — what does duration buy that iteration count alone would not? (§21.2, §32 item 8)
  18. A device's refcount never reaches zero after unplug. Name two structurally different root causes and the telemetry that distinguishes them. (§18.9, §23)

30. Mental Models & First Principles

ID Insight Predicts Bug Class Without It Applied In
MM1 A Device is a refcounted lease, not a pointer. Any operation on a Device must hold a pin for its full duration. Use-after-free on unplug mid-operation. §18 Phase 6, I3
MM2 The bus tree is the failure-propagation tree. Removing/suspending a node implies the same for every descendant, bottom-up. Orphaned children after parent teardown. §8.1, I8
MM3 The top-half is a trampoline, not a handler. Real work belongs in the bottom half; top-half only decides handled-or-defer. IRQ latency jitter, priority inversion. §16 Phase 4, P6/P7
MM4 An IOMMU group is a trust boundary, not a performance knob. Two devices in different groups can never safely share a DMA mapping. Confused-deputy DMA attacks. §17 Phase 5, I6, §22 T3
MM5 Probe/match is a pure function of (bus state, driver registry) — never of wall-clock timing. Identical inputs always produce identical bindings. "Works on Tuesday" nondeterminism. §8.2, I14, P2
MM6 A power state machine with a missing arm is a stranded device waiting to happen. Exhaustiveness must be checked at compile time, not discovered in the field. Unhandled (state, event) pairs found only in production. §19 Phase 7, I9
MM7 Device-supplied data is attacker-controlled until proven otherwise. Every descriptor field needs an independent bound check, not a single header-trust. The CVE-2016-2384-class kernel OOB read/write. §8.6, I13, §22 T1
MM8 Determinism is a testability property, not a nicety. Any non-deterministic iteration order eventually produces an unreproducible bug report. Flaky conformance fixtures, irreproducible field bugs. P12, §13.2, I14

Reference Implementations

  • Linux drivers/base/ — core.c (device registration), bus.c (bus_type), dd.c (driver-core probe/match). Lesson: the kobject refcounting discipline. Pitfall: do not copy the historical BUS_NOTIFY_* notifier-chain ordering bugs. Applied in §13 Phase 1, §14 Phase 2.
  • FreeBSD sys/kern/subr_bus.c, sys/sys/bus.h — newbus. Lesson: the device_t hierarchy and DEVICE_PROBE/DEVICE_ATTACH return-code contract. Pitfall: newbus's probe return value is a priority, easy to invert accidentally. Applied in §14 Phase 2, §9 ADR-22.
  • Rust-for-Linux (rust/kernel/driver.rs, rust/kernel/device.rs) — the in-tree Rust kernel abstractions project. Lesson: how to express a C-ABI-compatible driver trait in safe Rust. Pitfall: do not leak raw kernel pointers across the trait boundary unwrapped. Applied in §11 Core Schema & Types, §6 P8.
  • Fuchsia Driver Framework (zircon sdk/lib/driver) — DFv2 driver host model. Lesson: driver-host process isolation as a capability boundary. Pitfall: cross-driver-host IPC cost dominates naive designs. Applied in §34 Alternative Architectures Alt-1, §31.
  • seL4 userspace device driver examples (camkes-vm device-driver components). Lesson: userspace drivers trade IRQ latency for fault isolation. Pitfall: IPC-per-interrupt is the dominant cost, not the driver logic. Applied in §34 Alt-1, §5 Papers item 8.
  • Microsoft's published Kernel-Mode Driver Framework (KMDF) design guide — WDF driver model documentation. Lesson: the I/O Request Packet (IRP) queue as a uniform asynchronous-operation abstraction. Pitfall: IRP cancellation races are the framework's hardest bug class. Applied in §8.4, §31 Comparative Architecture Table.

Glossary (§36) · 50 terms · site-wide glossary

AER (Advanced Error Reporting)
PCIe capability reporting correctable/uncorrectable link errors.
BAR (Base Address Register)
PCI register declaring an MMIO or I/O region and its size.
Bottom half
deferred IRQ work, may sleep, runs in ddf-bottom-half's worker pool.
Bus
container/enumerator for devices; the Bus trait (§11).
cdev
character device, exposed via ddf-userspace.
Coherent DMA
cacheable shared mapping; CPU and device see identical contents without explicit sync.
Config space
PCI's per-function register space (256 B legacy, 4 KiB extended).
CSR (Control/Status Register)
generic device register terminology.
D0/D1/D2/D3 (Hot/Cold)
PM power states from active to deepest sleep (§11 PmState).
Device
a bound or unbound hardware unit; the Device struct (§11).
DeviceState
the framework's per-device lifecycle enum (§8.4, §11).
DMA (Direct Memory Access)
device-initiated memory access, bypassing the CPU.
DMA bounce buffer
a kernel-owned intermediate buffer used when no IOMMU is present (P5, ADR-24).
Driver
software bound to a device via the Driver trait (§11).
EHCI / xHCI / OHCI / UHCI
USB 2.0 / USB 3.x / legacy host-controller interfaces.
Endpoint
a USB transfer endpoint within an interface.
Firmware
pre-OS code (BIOS/UEFI/device firmware) that hands off enumeration data.
GIC (Generic Interrupt Controller)
ARM's IRQ controller architecture.
Hot-plug
dynamic plug/unplug event handling (§18).
HCD (Host Controller Driver)
the driver for the USB host controller itself.
Interface (USB)
a device's functional unit within a configuration.
INTx
legacy PCI interrupt lines (INTA–INTD).
IOAPIC
I/O Advanced Programmable Interrupt Controller.
IOMMU (I/O Memory Management Unit)
translates device-visible addresses to physical addresses (§17).
IOMMU group
set of devices sharing one IOMMU translation context (I6, §11).
IRP (I/O Request Packet)
Windows WDM's asynchronous I/O abstraction (§31).
IRQ (Interrupt Request)
a hardware interrupt line/vector.
LAPIC (Local APIC)
per-CPU interrupt controller on x86.
MCFG
the ACPI table declaring PCIe extended config-space (MMCONFIG) ranges.
MMCONFIG
the memory-mapped mechanism for accessing PCIe extended config space.
MMIO (Memory-Mapped I/O)
device registers mapped into the physical address space.
MSI / MSI-X
Message-Signaled Interrupts / their extended variant.
PCIe (PCI Express)
the modern PCI physical/protocol layer.
PMC
power-management capability (PCI config-space capability).
Probe
the driver-init callback invoked per matched device (§8.2, §14).
PTM (Precision Time Measurement)
a PCIe synchronization feature.
Quarantined
the DeviceState reached on malformed input or unrecoverable failure (§8.4, P9).
Refcount
the pin count keeping a Device alive while any FD/IRQ/DMA holds it (I3).
Resource
an MMIO/I/O/IRQ/DMA claim; the Resource enum (§11).
ResourceSet
the per-device collection of claimed Resources (§11).
Root complex
the top of the PCIe enumeration hierarchy.
Runtime PM
dynamic power management applied while the system is otherwise active (§19).
Streaming DMA
a short-lived, directional DMA mapping requiring explicit sync (I5).
SR-IOV (Single Root I/O Virtualization)
a device exposing multiple virtual functions.
Top half
the bounded, non-sleeping IRQ handler context (P7, I4).
Transfer (USB)
control / bulk / interrupt / isochronous, the four USB transfer types.
VFIO (Virtual Function I/O)
a userspace passthrough driver framework (§1 non-goal, §34).
virtio
the paravirtualized device protocol family (§20).
vring
virtio's shared-memory descriptor queue (I13, §20).
WDF / WDM (Windows Driver Framework / Model)
Windows's kernel driver model (§31).
