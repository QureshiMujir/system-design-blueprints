23 — JSON Parser

Project Number: 23

Project Name: JSON Parser

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

This blueprint specifies a from-scratch, production-grade JSON parser and serializer in C++20, targeting spec-exactness against RFC 8259 and ECMA-404, bit-exact IEEE 754-2019 number round-tripping, full RFC 3629 UTF-8 validation, and hardened behavior against adversarial input. The system is explicitly a parser for hostile bytes: every design decision is judged first on whether it preserves a provable accept/reject boundary against the JSONTestSuite corpus (Seriot, "Parsing JSON is a Minefield") and second on throughput. The parser provides a DOM mode (a tagged-union Value tree over an arena), a streaming/SAX mode (constant-memory event emission), and a zero-copy string-view mode with lazy unescaping. A scalar recursive-descent parser is the baseline; an iterative deep-path parser removes the stack-exhaustion risk of unbounded nesting; a SIMD structural scanner (stage 1, simdjson-style) accelerates the common case and must be differentially proven equivalent to the scalar scanner on every byte.

Phase-0 deliverable — numbered target/module list:

  1. include/jsonp/token.hpp — TokenKind, Token, SourceLocation signatures.
  2. include/jsonp/tokenizer.hpp — scalar Tokenizer signature and the state-transition table (Phase 0).
  3. conformance/jsontestsuite/ — vendored corpus + harness invoked from CI (Phase 0).
  4. .github/workflows/ci.yml — build + tokenizer-only conformance gate (Phase 0).
  5. include/jsonp/parser.hpp, include/jsonp/value.hpp, include/jsonp/arena.hpp (Phases 1–2).

Boundaries. Provides: a conformant tokenizer/parser, a DOM with arena allocation, a SAX event interface, a serializer with escaping and pretty-printing, exact number parse/serialize, UTF-8 validation, depth/size limits, and (Phase 11) JSON Pointer (RFC 6901) and JSON Patch (RFC 6902). Delegates: transport (sockets, files) to the caller via an input-adapter abstraction; TLS, compression, and network retry logic are out of scope. Does NOT provide: JSON Schema validation, a query language beyond JSON Pointer, JSON5/JSONC/comment support by default, or a general document database.

Non-goals: no comments or trailing commas in the default grammar (JSON5/JSONC is an explicit, separately-gated extension point per ADR-23, PhaseDeferred("JSON5 extension mode")); no schema validation in Phase 0 through Phase 11 (PhaseDeferred("JSON Schema Draft 2020-12 validator")); not a query engine — JSON Pointer resolves paths, it does not filter or project.

Deployment model: header-only distribution (include/jsonp/*.hpp) plus an optional pre-compiled static library (libjsonp.a) for translation-unit-heavy consumers, and a CLI validator binary (tools/jsonp-validate) that accepts a file or stdin and exits nonzero with a byte-offset error on the first RFC 8259 violation. Users/operators: application developers embedding the library (primary), and operators running the CLI validator in data-ingestion pipelines to reject malformed payloads before they reach a downstream system (mitigating T6 below). Later phases unlock: SAX streaming for multi-gigabyte logs (Phase 8), SIMD throughput competitive with simdjson (Phase 10), and JSON Pointer/Patch for configuration-diffing tools (Phase 11).

Language rationale: C++20 is chosen for constexpr table generation, concepts (constraining the SaxHandler interface without virtual dispatch overhead), and mature SIMD intrinsic support (<immintrin.h>, <arm_neon.h>) plus a mature toolchain of sanitizers (ASan/UBSan/MSan) needed by §28. Rejected: Rust (memory-safety is attractive but the reference corpus of comparison implementations — simdjson, RapidJSON — is C++, and header-only zero-dependency distribution is the deployment target); Go (GC pauses are incompatible with the p99 latency budget in §4 and it lacks portable SIMD intrinsics); pure C (no RAII for arena/exception-safety, no templates for the tagged-union ergonomics in §11).

Prerequisites: IEEE 754-2019 floating-point representation (exponent/mantissa layout, subnormals, round-half-to-even); Unicode fundamentals (code points, UTF-8/UTF-16 encoding, surrogate pairs, the astral plane); SIMD basics (vector width, lane-wise comparison, movemask/bitmask extraction, pdep/pext).

Timeline: 12 phases, Phase 0 through Phase 11 (see §12–§23), each phase 3–10 working days, matching the phase arc in §12's header. Total: approximately 10–12 weeks to the Phase 11 exit criteria (JSONTestSuite 100% pass, SIMD/scalar differential equivalence, zero-crash fuzz gate, JSON Pointer/Patch complete).

Deferrals in this document use PhaseDeferred("<anchor>") where <anchor> names a real heading or corpus that resolves the deferral; see §37 for the closed register.

2. Why Build This

Keyword bullets: RFC-exact grammar enforcement; recursive descent versus iterative deep-path parsing; stack-exhaustion hardening; tagged-union DOM design; arena allocation and allocation counting; zero-copy string views and lazy unescaping; UTF-8 well-formedness (overlong encodings, surrogate ranges); exact binary/decimal float conversion (Grisu, Ryū, Eisel-Lemire, big-integer fallback); SIMD structural scanning and scalar/SIMD differential proof; streaming/SAX event design; error-offset reporting; JSONTestSuite as a conformance oracle; fuzzing under sanitizers; JSON Pointer/Patch semantics; differential testing against simdjson/RapidJSON/nlohmann.

What Mastery Looks Like

  • You can derive, from RFC 8259 alone, the exact set of characters that must be rejected as unescaped in a JSON string, and cite the clause — demonstrated by the string-grammar table in Phase 3 (§15).
  • You can explain why strtod is unsuitable for a production parser and name the algorithm that replaces it and its slow-path fallback — demonstrated by the number-conversion decision table in Phase 5 (§17).
  • You can prove, not assert, that a SIMD scanner and a scalar scanner agree on every byte of a random and adversarial corpus — demonstrated by the differential-testing harness in Phase 10 (§21).
  • You can bound the stack depth of a recursive-descent parser in bytes and derive the safe nesting-depth default from a target thread stack size — demonstrated by the arithmetic in §34.
  • You can distinguish a lone surrogate from a valid surrogate pair in a \u escape sequence and state the exact combining formula — demonstrated by the worked example in Phase 3 (§15).
  • You can enumerate at least five ways an adversarial JSON document can exhaust memory or CPU before it exhausts the parser's correctness, and name the mitigation for each — demonstrated by the threat model (§24) and the hardening phase (§21).
  • You can explain the difference between a DOM parser, a SAX parser, and simdjson's on-demand model, and state which workload favors each — demonstrated by §33 and §36.

Input Adapter: the single point where untrusted bytes enter the system; owns a contiguous buffer or borrows a caller-provided one, and is the only component permitted to perform I/O. SIMD Structural Scanner: stage 1 of the simdjson design — classifies each byte as structural, whitespace, or string-interior using vectorized comparisons and prefix-XOR quote tracking, never interprets values. UTF-8 Validator: independently verifies byte well-formedness (RFC 3629) before any string content is trusted; runs scalar or SIMD depending on ADR-08. Tokenizer: consumes the structural index (or scans byte-by-byte on the scalar path) to emit Tokens with SourceLocation spans into the input buffer — it does not allocate. Parser: recursive-descent by default, switches to the iterative deep-path parser (Phase 9) once nesting exceeds a low static threshold, enforcing the depth limit before recursing (I2). Value Builder: turns a stream of tokens/parser calls into Value nodes, requesting storage from the Arena Allocator. Arena Allocator: bump-allocates fixed blocks for the lifetime of one Document; the sole heap-allocation path for DOM mode. DOM Value Tree: the tagged-union Value graph rooted at Document; owns no bytes directly — string leaves either borrow the input buffer (zero-copy) or point into arena-owned unescape buffers. String Unescaper: converts escape sequences to UTF-8 bytes lazily, only when a view is materialized or when escapes are present. Number Converter: implements the exact decision table of §16 (integer fast path, Eisel-Lemire, big-integer slow path). SAX Event Emitter: alternative to the Value Builder — emits SaxEvents to a caller-provided handler with no DOM construction, enabling constant-memory streaming. Serializer: walks a Value tree or receives SAX-shaped calls and produces bytes, applying the escaping decision table (§20) and optional pretty-printing. Limits Enforcer: cross-cutting component consulted by the tokenizer, parser, and value builder before any allocation or recursion, holding the Limits struct (depth, document size, string length, number length). JSON Pointer/Patch: Phase 11 layer operating purely on the completed Value tree, never on raw bytes. Buffer ownership: the Input Adapter is the sole owner of the byte buffer for the lifetime of a Document; every StringView in the DOM is a borrow with a lifetime obligation documented in §11.

Reference Implementations

  1. simdjson, src/generic/stage1/ — structural-index bitmask pipeline. Lesson: prefix-XOR quote tracking generalizes cleanly to escaped-backslash runs. Pitfall not to copy: simdjson's on-demand API intentionally exposes borrowed-lifetime hazards to the caller for speed — do not adopt that ergonomics tradeoff for the DOM-mode API (ADR-04 chooses safety there).
  2. simdjson, src/generic/stage2/ — tape construction from the structural index. Lesson: a flat tape with type tags avoids pointer-chasing during DOM materialization. Pitfall: the tape's packed 64-bit entries assume a specific pointer width; do not hardcode 64-bit assumptions into this blueprint's ValueUnion layout (§11) without a static_assert guard.
  3. RapidJSON, include/rapidjson/reader.h — SAX-first, template-parameterized parser. Lesson: a handler-interface SAX design (this blueprint's SaxHandler, §11) can be made allocation-free for the reader itself. Pitfall: RapidJSON's in-situ parsing mutates the input buffer to null- terminate strings — incompatible with this blueprint's read-only Input Adapter (ADR-06).
  4. RapidJSON, include/rapidjson/writer.h — escaping and number-formatting dispatch table. Lesson: precomputed per-byte escape-need lookup table for the serializer's fast path (§20). Pitfall: RapidJSON defaults to %g-based number formatting without Ryū; do not inherit that default (ADR-14 locks Ryū).
  5. nlohmann/json, single_include/ — ergonomics-first DOM design with implicit conversions. Lesson: the value-of-any-type ergonomics that make it popular. Pitfall: its recursive value destructor recurses to input depth, causing stack overflow on deeply nested documents even after a bounded parse — this blueprint's Value destruction must be iterative (I2 extends to teardown, not only parse).
  6. yyjson, immutable/mutable dual-DOM design and insitu parsing. Lesson: a read-only immutable DOM variant is measurably faster to build than a mutable one; informs the "mutation support" ADR-19 decision to keep the primary DOM immutable-by-default. Pitfall: yyjson's insitu mode shares RapidJSON's buffer-mutation hazard — rejected for the same reason.
  7. serde_json (Rust) — contrasting design via serde::Deserialize trait dispatch instead of a generic Value. Lesson: compile-time schema binding (ADR-05's "code-generated" alternative, §36) eliminates DOM overhead entirely for known schemas. Pitfall: not directly portable to C++'s weaker reflection; do not attempt a literal port, only the design lesson.

6. Design Principles

P1 — The specification is the authority and the conformance corpus is the judge. Rule: every accept/reject decision traces to a clause of RFC 8259 or a named JSONTestSuite case, never to what seemed reasonable. Tradeoff: slower initial development while every edge case is looked up rather than guessed. Operational implication: code review requires a citation in the diff (N.2 anchors enforce this). Violation consequence: silent grammar drift that a future contributor cannot distinguish from intended behavior.

P2 — Every input is hostile. Rule: depth, length, and allocation are bounded before parsing begins, never discovered mid-parse. Tradeoff: a small fixed check cost on every well-formed document. Operational implication: Limits must be consulted at the top of every recursive call and every allocation request. Violation consequence: unbounded recursive descent on attacker-controlled nesting is a stack-exhaustion crash (T1).

P3 — Number conversion is exact or it is a data-corruption bug. Rule: a double must round-trip bit-identically through parse→serialize→parse; an integer outside the double-exact range must not silently lose precision without a documented, opt-in mode. Tradeoff: the exact path is slower than strtod. Operational implication: every number-conversion change requires a differential run against the 4M-case parse-number-fxx-test-data corpus. Violation consequence: financial or scientific data silently corrupted on ingestion, undetectable until an audit.

P4 — The fast path is SIMD and the correct path is scalar, and they must agree on every byte. Rule: no SIMD code ships without a scalar equivalent proven identical by differential fuzzing. Tradeoff: doubles the surface area to maintain. Operational implication: every SIMD change ships with a corresponding scalar-differential CI job (H-gate in §28). Violation consequence: a CPU-feature-dependent parsing bug that only reproduces on specific hardware.

P5 — Zero-copy is a borrow, and every borrow has a documented lifetime. Rule: a StringView that aliases the input buffer must not outlive that buffer, and the type system or a runtime assertion must make the violation observable, not silent. Tradeoff: API ergonomics are more complex than an always-owning string type. Operational implication: Document documents its buffer-ownership mode (owning vs. borrowing) in its type. Violation consequence: use-after-free when a caller frees the input buffer while a Value tree still borrows from it (T8).

P6 — Errors carry a byte offset or they are not acceptable errors. Rule: every ParseError includes the exact byte offset (and derived line/column) of the first violation. Tradeoff: offset tracking on every token adds bookkeeping cost. Operational implication: error-reporting code cannot short-circuit before computing the location. Violation consequence: an operator debugging a malformed multi-megabyte payload with no offset is reduced to bisection by hand.

P7 — A rejected document is never a partially-populated DOM presented as valid. Rule: parse failure produces ParseResult::Error, never a Value tree with missing branches. Tradeoff: requires transactional construction (build into a scratch arena, commit only on success, or validate structure before commit). Operational implication: the value builder must be able to discard a partially-built tree cheaply (arena reset, not per-node free). Violation consequence: a caller that doesn't check the result variant reads corrupt/incomplete data as if it were complete.

P8 — Depth limits are enforced before recursion, not after. Rule: the parser checks the depth counter and rejects before calling into the next nesting level, never inside the callee after the stack frame is already committed. Tradeoff: one extra branch per structural descent. Operational implication: the check lives in the caller (parse_value), not the callee. Violation consequence: a limit checked one frame too late still allows N+1 frames of stack growth — the exact off-by-one that turns a "safe" limit into an exploitable one.

P9 — Allocation is arena-scoped, not per-node. Rule: DOM construction requests memory from a Document-scoped Arena, never calls the global allocator per Value node. Tradeoff: arena reset discards fine-grained free — acceptable because Document lifetime is the unit of reuse. Operational implication: allocation-count telemetry (§26) tracks arena-block requests, not node count. Violation consequence: a 100M-node document with per-node malloc is dominated by allocator overhead, not parsing (measured against M-series targets in §30).

P10 — The DOM is immutable by default; mutation is an explicit, opt-in builder. Rule: a parsed Value tree cannot be edited in place unless the caller constructs a DocumentBuilder. Tradeoff: editing a large parsed document requires an explicit copy-into-builder step. Operational implication: read-only Document instances can be shared across threads without synchronization (I11). Violation consequence: unguarded in-place mutation of a shared parsed document from two threads is a data race.

P11 — String content is not trusted until it is proven well-formed UTF-8. Rule: the UTF-8 validator runs over every string byte range before that string is exposed to the caller, including zero-copy views. Tradeoff: a validation pass that cannot be skipped even in the zero-copy fast path. Operational implication: the validator's SIMD and scalar variants must both reject the same malformed sequences (I3). Violation consequence: a lone surrogate or overlong sequence propagates into a downstream system that assumes valid UTF-8 (T5).

P12 — A number's textual length is bounded before any digit is examined. Rule: the tokenizer enforces the max-number-literal-length limit (§4) as it scans, not after building a big-integer representation. Tradeoff: an extremely rare legitimate 1025-digit literal is rejected by default (escape hatch: ParseOptions override, documented as a deliberate risk acceptance). Operational implication: the limit check happens character-by-character during tokenization, not post-hoc. Violation consequence: 1e999999999 drives unbounded big-integer exponentiation work, a CPU exhaustion vector (T7).

8. Domain Model

8.1 Grammar (EBNF, per RFC 8259)

value      = ws , ( object | array | string | number | "true" | "false" | "null" ) , ws ;
object     = "{" , ws , [ member , { "," , member } ] , ws , "}" ;
member     = string , ws , ":" , value ;
array      = "[" , ws , [ value , { "," , value } ] , ws , "]" ;
string     = quotation-mark , { char } , quotation-mark ;
char       = unescaped | escape ;
number     = [ "-" ] , int , [ frac ] , [ exp ] ;
int        = "0" | ( digit1-9 , { digit } ) ;
frac       = "." , digit , { digit } ;
exp        = ( "e" | "E" ) , [ "-" | "+" ] , digit , { digit } ;
ws         = { %x20 | %x09 | %x0A | %x0D } ;

Structural characters (six, per RFC 8259 section 2): { } [ ] : ,. Whitespace (three plus space, per RFC 8259 section 2): space (0x20), tab (0x09), line feed (0x0A), carriage return (0x0D) — no others, including no BOM. What the specification permits versus what implementations commonly get wrong: RFC 8259 permits arbitrary nesting depth and arbitrary-precision numbers textually (no grammar-level limit) — implementations commonly get this wrong by either accepting unbounded nesting (T1) or silently truncating number precision without a documented policy (P3). RFC 8259 leaves duplicate object keys as implementation-defined (section 4) — implementations commonly get this wrong by choosing silently and divergently (I10, T6).

Surrogate-pair combining rule: if the decoded \uXXXX value hi is in [0xD800, 0xDBFF], the next token must be \uXXXX with value lo in [0xDC00, 0xDFFF]; the combined code point is 0x10000 + ((hi - 0xD800) << 10) + (lo - 0xDC00). A high surrogate not followed by a matching low surrogate, or a low surrogate not preceded by a high surrogate, is a lone surrogate (ErrorCode::LoneSurrogate).

Worked example — astral-plane character U+1F600 (GRINNING FACE): encoded in the JSON text as 😀. hi = 0xD83D, lo = 0xDE00. Combined: 0x10000 + ((0xD83D - 0xD800) << 10) + (0xDE00 - 0xDC00) = 0x10000 + (0x3D << 10) + 0x200 = 0x10000 + 0xF400 + 0x200 = 0x1F600. The unescaper emits this as the 4-byte UTF-8 sequence F0 9F 98 80.

8.5 Number Grammar and Conversion

Integer-versus-double decision table:

Textual Form No ./e/E Fits in int64 Decision
42 yes yes NumberKind::Integer, exact int64
99999999999999999999 yes no (overflows int64) NumberKind::Double, converted via slow path if needed
3.14 no n/a NumberKind::Double
1e10 no n/a NumberKind::Double
-0 yes yes (special-cased) NumberKind::Double, value negative zero, sign bit preserved (see below)

Exact-conversion procedure (named steps): (1) classify — scan the number span once to determine integer-vs-double per the table above without allocating; (2) fast_int — for integer-classified spans within int64 range, multiply-add with overflow checking, done; (3) eisel_lemire — for double-classified spans, attempt the Eisel-Lemire fast path (Lemire 2021): look up the binary power-of-ten in a precomputed table, perform a 128-bit multiply, round; succeeds for the documented ~99.5% of real-world inputs; (4) slow_path — on Eisel-Lemire's documented failure signal, fall back to a correctly-rounded arbitrary-precision decimal-to-binary conversion (Gay 1990); (5) finalize — apply sign, and for the -0 case, preserve the IEEE 754 negative-zero sign bit rather than normalizing to positive zero.

Worked example (beyond 2^53): 9007199254740993 (2^53 + 1) is not exactly representable as a double; the slow path (or Eisel-Lemire, which agrees with it) rounds to the nearest representable double, 9007199254740992.0, via round-half-to-even.

Worked example (slow path required): 2.2250738585072014e-308 sits at the subnormal boundary where Eisel-Lemire's fast-path table lookup is documented to be insufficiently precise; the big-integer slow path is invoked and produces the correctly-rounded subnormal result.

Worked example (huge exponent): 1e400 exceeds double's finite range (max finite exponent ~308); per ADR-15 this converts to +Infinity only if ParseOptions::allow_infinity_on_overflow is set, otherwise it is rejected with ErrorCode::NumberOutOfRange — the default is reject, because Infinity is not itself a valid JSON literal and silently producing one violates P1.

Worked example (-0): the literal -0 parses to NumberKind::Double with value negative zero; -0 == 0 numerically but the sign bit differs, and serialization (§17) must reproduce -0 exactly, not 0, to satisfy I4.

8.6 SIMD Structural-Scan Bitmask Pipeline

Stage Operation Output
1 Load 64-byte chunk into vector register(s) raw bytes
2 Compare against " byte, produce quote bitmask quote_mask
3 Compare against \ byte, compute odd-length-backslash-run mask via carry-chain, XOR into quote mask escaped_quote_mask
4 Prefix-XOR-scan quote_mask (adjusted for escapes) to produce "inside string" region mask in_string_mask
5 Compare against the six structural bytes, AND with NOT in_string_mask structural_mask
6 Compare against the four whitespace bytes, AND with NOT in_string_mask whitespace_mask
7 pext/iterate-and-clear the structural_mask to emit byte offsets into the structural-index array structural_indices[]

Worked 64-byte example (abbreviated to the load-bearing 16 bytes): input {"a":1,"b":"\"x\""}. Byte 0 { → structural. Bytes 1,4 " → quote boundaries, not inside a backslash run, toggle in_string_mask. Byte 11 is \ immediately followed by " at byte 12 — the escaped quote is excluded from quote_mask by the backslash-run parity check in stage 3, so it does not toggle in_string_mask a third time; the scanner correctly keeps bytes 12–14 (x\" content) inside the string region rather than terminating early.

8.7 DOM Value Bit-Layout Table

Field Bits Meaning
tag 3 ValueTag: Null, Bool, Integer, Double, ShortString, String, Array, Object (8 variants fit in 3 bits)
inline_flag 1 1 = payload stored inline in the union; 0 = payload is an indirect Arena offset
payload 60 inline: bool/short-string bytes/small-int; indirect: 32-bit arena block index + 28-bit intra-block offset

Inline-versus-indirect storage rule: Null, Bool, and strings ≤ 7 bytes (ShortString) store their payload inline in the 60 payload bits, avoiding an arena allocation entirely; Integer and Double store the full 64-bit value inline via a second machine word (the tagged union is 16 bytes total, tag+flag+padding in the first 8, full-width payload in the second, to satisfy 8-byte alignment); String (>7 bytes), Array, and Object store an indirect arena reference. Alignment and padding: the 16-byte Value is 8-byte aligned; the 3 tag bits and 1 inline flag occupy the low 4 bits of word 1, with 60 bits of word 1 unused when word 2 carries the full payload (accepted padding cost, traded for branch-free tag dispatch — ADR-09).

8.8 Arena Allocation Model

Blocks are fixed-size (§4: 64 KiB), bump-allocated within a block, and chained in a singly-linked list owned by Document. An allocation request larger than one block gets its own dedicated oversized block. Reset (on parse failure, P7) discards the entire block chain without per-node destructors, an O(blocks) operation, not O(nodes).

12.2 Detailed Implementation Steps

  1. Scaffold the repository tree per §10; commit LICENSE, README.md, SECURITY.md stubs.

12.4 Acceptance Criteria

12.5 Conformance Fixtures

12.6 Pitfalls

  • Treating \u as always producing exactly one output character — surrogate pairs require two input escapes combined into one; a naive implementation double-counts or drops the combining step. Manifestation: astral-plane characters corrupt on tokenization. Debug: single-step the InUnicodeEscape/PendingSurrogate transition on the astral-plane fixture from §8.3.
  • Off-by-one in whitespace class checks: including 0x0B (vertical tab) or 0x0C (form feed) as whitespace, which RFC 8259 section 2 explicitly excludes. Manifestation: n_* whitespace fixtures wrongly accepted. Debug: diff the whitespace bitmask against the exact four-character set.
  • Number-length limit checked after building the full span instead of during the scan (violates P12). Manifestation: a 10 MB digit string still gets fully scanned before rejection, defeating the CPU-bound protection intent. Debug: instrument the scan loop with a counter assertion.
  • Vendoring JSONTestSuite without pinning a commit — corpus drift silently changes what "100% pass" means between CI runs. Signal: green CI on an unrelated PR suddenly turns red.

12.7 Performance Concerns

Tokenizer-only throughput target is not yet SIMD-accelerated (that's Phase 10); scalar throughput should still hit 300–500 MB/s (§4) to keep the CI harness fast against a 348-file corpus (round-trip under 5 seconds). Avoid std::string allocation per token at this stage — tokens carry StringView spans, not owned strings (P5, informing the eventual zero-copy design).

12.8 Edge Cases

Empty input (zero bytes) — must tokenize to immediate EOF, not an error, but the parser (Phase 1) rejects an empty document as not a valid value. A document consisting of only whitespace. A number immediately followed by EOF with no terminator (must still emit a valid Number token). A string containing \u0000 (escaped null) — must be accepted at the tokenizer level (RFC 8259 permits escaped control characters; only unescaped control characters, 0x00–0x1F literal, are rejected).

12.9 Failure Analysis

Symptom: a fixture the corpus marks n_ is tokenized without error. Root cause: a missing error edge in the state-transition table (§8.2) — cross-check the specific input against every row for the state it should have failed in. Symptom: CI harness times out. Root cause: an infinite loop in InEscape state on a malformed escape that neither errors nor advances — verify every state has a strictly-advancing or error-terminating transition for every byte value, not just the documented ones.

13. Phase 1 — Recursive-Descent Parser and DOM

13.1 Objectives

Build the first working Value-producing parser: recursive descent over the grammar in §8.1, consuming tokens from Phase 0's Tokenizer, enforcing the depth limit (I2, P8) before every recursive descent, and constructing a minimal (not yet arena-backed — that lands in Phase 2) Value tree. This phase makes P7 ("a rejected document is never a partially-populated DOM") operational for the first time.

13.2 Detailed Implementation Steps

  1. Implement one parsing function per grammar non-terminal in §8.1: parse_value, parse_object, parse_array, parse_string, parse_number, parse_literal — directly mirroring the EBNF (Aho/Lam/Sethi/Ullman ch. 4, Grune & Jacobs ch. 8).
  2. Thread a depth counter through parse_value; check depth >= limits.max_depth and reject with ErrorCode::DepthLimitExceeded before incrementing and recursing into parse_object or parse_array (P8, I2, I9).
  3. Implement ParseResult variant discipline (P7, I7): on any error, discard whatever partial structure has been built so far and return only ParseError.
  4. Wire ParseOptions::strict_duplicate_keys as a no-op placeholder for now (real duplicate-key policy lands with the DOM object representation in Phase 2, ADR-16).
  5. Implement error-context formatting: given a ParseError, render "expected X but found Y" with the surrounding byte window, using SourceLocation from Phase 0.
  6. Add a stack-depth-consuming fixture and confirm the depth limit fires before a stack overflow occurs (differential proof against a debug build with an artificially tiny thread stack).
  7. Run the full JSONTestSuite through the DOM parser (not just the tokenizer) and update the harness to check DOM-level accept/reject, not only token-level.

13.3 Deliverable

A recursive-descent Parser producing a Value tree (temporarily heap-allocated per node; arena integration is Phase 2's job) for every well-formed document, and a precise ParseError for every malformed one, passing the full JSONTestSuite at the DOM level.

13.4 Acceptance Criteria

100% pass rate on JSONTestSuite y_*/n_* at DOM level (348/348); every i_* case's verdict matches the Phase 0 documented table; depth-limit fixture (10000_nested_arrays.json, scaled down to the default limit of 512 plus one) rejects with ErrorCode::DepthLimitExceeded and never crashes under ASan with a 512 KiB thread stack; zero instances of a returned Value tree accompanying an Error result (I7) across the entire corpus.

13.5 Conformance Fixtures

conformance/jsontestsuite/y_structure_true_in_array.json — minimal array holding a literal, purpose: baseline non-terminal chaining. n_structure_object_with_trailing_garbage.json — purpose: TrailingData after a valid top-level value must be rejected. depth_513_nested_arrays.json (hand-built) — purpose: exactly one level past the default limit, expected DepthLimitExceeded at the offset of the 513th [.

13.6 Pitfalls

  • Checking the depth limit inside the callee after already recursing one frame (violates P8/I9) — manifestation: the limit is effectively N+1, and under a sufficiently deep adversarial input the "N+1"th frame is still enough to exhaust a small thread stack. Debug: fuzz the exact boundary value and confirm the crash disappears only when the check precedes the call.
  • Returning a partially built Value alongside an error for caller convenience ("might as well give them what we have") — this directly violates P7/I7 and creates a foot-gun where an unchecked caller silently processes truncated data.
  • Recursive Value destruction on a deeply-nested but successfully parsed tree recursing to input depth on teardown (the nlohmann/json pitfall from §5's reference-implementation lesson) — even though the parse succeeded within the depth limit, destructor recursion at the same depth can still be an issue if the limit is set near the stack's actual ceiling; iterative teardown is the fix.
  • Off-by-one in "value then trailing data" detection — accepting 1 2 as two top-level values concatenated instead of rejecting the second 2 as trailing data.

13.7 Performance Concerns

Recursive descent's cost here is dominated by the depth-check branch on every descent (P8) — this is deliberately non-optional overhead, not a target for removal; do not hoist it out "for speed." Per-node heap allocation in this phase is a known temporary regression, resolved in Phase 2 by arena allocation (ADR-11); do not benchmark this phase against the §4 throughput targets — those targets apply post-Phase-2.

13.8 Edge Cases

A document that is a single scalar (42, "hi", true) with no surrounding structure — valid per the value production, must parse successfully as a one-node tree. An empty object {} and empty array []. A deeply nested but well-formed document exactly at the depth limit (512) — must succeed, not be treated as an off-by-one rejection (I9's "before, not after" cuts both ways: the 512th level is allowed, the 513th is not).

13.9 Failure Analysis

Symptom: parser accepts trailing data after a valid top-level value. Root cause: parse_value's caller doesn't check for TokenKind::Eof after the top-level call returns. Detection: add a fixture with valid JSON followed by garbage and assert rejection. Symptom: intermittent stack overflow in CI only on the ASan job. Root cause: ASan's redzones inflate stack frame size, lowering the effective safe depth — this is a signal to lower the default depth limit or increase the assumed frame-byte constant in the §34 arithmetic, not an ASan false positive.

13.10 Operational Notes

The temporary heap-allocation strategy in this phase is explicitly marked with a // TODO(Phase 2): arena comment convention so that Phase 2's arena migration has a greppable checklist. The DOM-level JSONTestSuite harness added here supersedes, but does not replace, the Phase 0 token-level harness — both remain in CI (token-level catches tokenizer regressions faster).

14. Phase 2 — Arena Allocator and Value Representation

14.1 Objectives

Replace Phase 1's per-node heap allocation with the arena model of §8.8, implement the tagged-union ValueUnion bit layout of §8.7, and make Document the owning unit of both the arena and the root Value. This phase makes P9 ("allocation is arena-scoped, not per-node") and ADR-11 operational, and is the first point at which §4's memory-ceiling constraint (5x input size) is measurable.

14.2 Detailed Implementation Steps

  1. Implement ArenaBlock as a fixed 64 KiB (§4) bump-allocated block with a next pointer, forming a singly-linked chain owned by Arena (Stroustrup ch. 34 on resource ownership).
  2. Implement Arena::allocate(size, align) — bump the current block's offset; on exhaustion, allocate a new block (or a dedicated oversized block for allocations larger than 64 KiB) and link it in.
  3. Implement Arena::reset() — walk the block chain and mark all blocks free for reuse (or release them), an O(blocks) operation, satisfying P7/I7's "discard cheaply on failure" requirement.
  4. Implement ValueUnion exactly per the §8.7 bit-layout table: 3-bit tag, 1-bit inline flag, and the inline-versus-indirect payload split; add a static_assert(sizeof(Value) == 16) guard (ADR-09) so any future field addition is caught at compile time.
  5. Implement ShortString inline storage (≤7 bytes) bypassing the arena entirely (ADR-10); implement the indirect-string path allocating from the arena for longer strings.
  6. Migrate Phase 1's Value construction call sites from heap new to Arena::allocate; remove the temporary per-node heap path entirely.
  7. Add allocation-count and high-water-mark telemetry hooks (arena.blocks_allocated, arena.bytes_high_water — I6, §26) around every Arena::allocate call.
  8. Benchmark DOM memory amplification against citm_catalog.json and confirm it lands within the 5x ceiling in §4; if it doesn't, revisit block size or inline-threshold tuning (feeds §34's amplification arithmetic).

14.3 Deliverable

An arena-backed Value/Document implementation where every DOM node's storage traces to exactly one Arena owned by exactly one Document, with Document destruction or reset() freeing all associated memory in O(blocks) time.

14.4 Acceptance Criteria

sizeof(Value) == 16 (static_assert enforced); memory high-water mark on citm_catalog.json is ≤5.0x the input byte count (§4); Arena::reset() on a partially-built tree from an injected mid-parse failure (fault-injection fixture, §28) leaves zero live allocations, verified under ASan leak detection; JSONTestSuite pass rate remains 100% (no regression from Phase 1).

14.5 Conformance Fixtures

benchmarks/corpus/citm_catalog.json — purpose: DOM amplification measurement (small-object-heavy document, the worst case for per-node overhead). fault_injection/alloc_fail_at_node_1000.json — purpose: synthetic allocation-failure injection at a specific arena request count, expected ErrorCode::OutOfMemory and zero leaked blocks. short_string_boundary.json — a string of exactly 7 and exactly 8 bytes, purpose: verify the ShortString inline/indirect boundary in ADR-10.

14.6 Pitfalls

  • Forgetting alignment when computing the inline/indirect split in ValueUnion, causing misaligned reads on architectures that fault on unaligned access (not x86, but ARM in strict mode). Manifestation: crash only on an ARM CI runner. Debug: run the ARM matrix leg of CI (ADR-28) and inspect the faulting instruction's operand alignment.
  • Treating Arena::reset() as safe to call while any StringView from a prior parse still borrows arena memory (violates P5's lifetime obligation extended to arena-owned, not just input-owned, storage). Manifestation: use-after-free detected only under ASan, not in a debug build without sanitizers.
  • Off-by-one in the ShortString length boundary — using < 8 instead of <= 7, silently shifting which strings get inlined and breaking a length-based test fixture.
  • Assuming a single oversized allocation (e.g., a 200 MiB string) can safely coexist with normal 64 KiB blocks in the same free-list bucket — oversized blocks need their own path (step 2) or fragmentation telemetry becomes meaningless.

14.7 Performance Concerns

Arena block size (64 KiB, §4) is tuned for L2 cache locality (ADR-11); halving or doubling it without re-benchmarking against citm_catalog.json risks trading allocation-count reduction for cache-locality loss, or vice versa — any change must re-run the §30 M-series throughput targets. Bump-allocation is O(1) amortized; verify no accidental O(n) scan is introduced when searching for free space within a block (there should be none — it's a pure bump pointer).

14.8 Edge Cases

A document that produces exactly zero Value nodes beyond the root scalar (e.g., top-level 42) — must not allocate an arena block at all if the value fits inline (ADR-10). A document whose total node count divides evenly into 64 average nodes per block (§4's allocation-count formula) — verify the count matches the §34 arithmetic exactly for a synthetic fixture. An arena reset followed immediately by a second parse into the same Arena instance (reuse) — must not leak or double-free.

14.9 Failure Analysis

Symptom: memory high-water mark exceeds the 5x ceiling on citm_catalog.json. Root cause candidates, in order of likelihood: (a) ShortString inline threshold too low, pushing many small strings into indirect arena storage; (b) block size too small relative to average node size, causing per-block waste from the bump pointer never reaching block capacity exactly. Detection: instrument per-block utilization and histogram it; a long tail of near-empty blocks points to (b). Symptom: ASan leak report after a fault-injection test. 14.10 Operational Notes

Allocation telemetry (arena.blocks_allocated, arena.bytes_high_water) feeds the §26 dashboards directly and should be considered a stable metric name from this phase forward — renaming it later is a minor operational-compatibility break even though it's not part of the public API surface.

15. Phase 3 — String Parsing, Escapes, and Surrogate Pairs

15.1 Objectives

Implement the Unescaper (§11) that turns a raw string span (as tokenized in Phase 0) into either a zero-copy StringView (no escapes present) or an arena-materialized unescaped string, correctly combining surrogate pairs per the §8.3 formula. This phase makes P5 ("zero-copy is a borrow, and every borrow has a documented lifetime") and the astral-plane worked example in §8.3 concrete.

15.2 Detailed Implementation Steps

  1. During tokenization (Phase 0's scan), record whether a string span contains any \ — if not, the span is escape-free and can become a zero-copy StringView directly (P5, ADR-08).
  2. For escape-free spans, still run byte-range validation (0x00–0x1F literal control characters already rejected by the tokenizer per §8.2) — no further work needed here; defer full UTF-8 well-formedness to Phase 4 (I3 is satisfied jointly across Phase 3 and Phase 4).
  3. For spans containing escapes, implement Unescaper::unescape per the §8.3 table: single- character escapes map via the constexpr lookup table from Phase 0; \uXXXX requires exactly 4 hex digits (already enforced by the tokenizer) and decodes to a 16-bit code unit.
  4. Implement the surrogate-combining state machine: a decoded code unit in [0xD800, 0xDBFF] enters a "pending high surrogate" state; the next escape must be \uXXXX with a value in [0xDC00, 0xDFFF] or the parse rejects with ErrorCode::LoneSurrogate (§8.3 formula).
  5. Combine surrogate pairs via 0x10000 + ((hi - 0xD800) << 10) + (lo - 0xDC00) and emit the resulting code point as UTF-8 bytes (worked example: U+1F600 → F0 9F 98 80, §8.3).
  6. A lone high surrogate at end-of-string, or a low surrogate with no preceding high surrogate, both reject with ErrorCode::LoneSurrogate — never silently substituted (e.g., with U+FFFD) in the default strict mode.
  7. Materialize the unescaped result into the Arena (Phase 2's allocator), producing an arena-owned StringView with borrowed_from_input = false.
  8. Add the astral-plane worked example and a lone-surrogate fixture to the conformance corpus; run the full JSONTestSuite string-category subset (y_string_*, n_string_*) against this implementation.

15.3 Deliverable

A Unescaper producing correct UTF-8 bytes for every valid escape sequence including surrogate pairs, rejecting every lone-surrogate and invalid-escape case in JSONTestSuite, with zero-copy passthrough for escape-free strings.

15.4 Acceptance Criteria

100% pass rate on JSONTestSuite y_string_*/n_string_* subset; the astral-plane worked example (U+1F600) produces exactly F0 9F 98 80; every lone-surrogate fixture rejects with ErrorCode::LoneSurrogate at the correct byte offset (P6); zero-copy path verified by an instrumented test asserting no arena allocation occurs for an escape-free string fixture.

15.5 Conformance Fixtures

conformance/jsontestsuite/y_string_unicode_escaped_double_quote.json — purpose: \" inside a \u-escaped context doesn't confuse the state machine. n_string_invalid_utf-8_in_escape.json — purpose: malformed escape rejected. astral_plane_grinning_face.json (hand-built) — purpose: the §8.3 worked example, expected output bytes F0 9F 98 80. lone_high_surrogate_eof.json — purpose: \uD800 at end of string with no following low surrogate, expected ErrorCode::LoneSurrogate.

15.6 Pitfalls

  • Decoding \uXXXX as always producing exactly one output code point, forgetting the surrogate- pair combining step entirely — astral-plane characters silently corrupt into two separate BMP replacement characters instead of one combined code point.
  • Accepting a low surrogate not preceded by a high surrogate ("lenient mode leakage") — this must be a hard reject in strict mode (I3), not a permissive default, because it enables T5 (parser-differential attacks via lone surrogates reaching a downstream system that assumes well-formedness).
  • Computing the zero-copy-eligibility flag (step 1) based on the original input span but then accidentally pointing the resulting StringView at a stale or reused buffer after an arena reset — a lifetime-obligation violation (P5) distinct from the UTF-8 correctness issue.
  • Off-by-one in the surrogate combining arithmetic (e.g., using hi - 0xD7FF instead of hi - 0xD800) — produces a code point off by 1024, which will pass casual testing on ASCII-only corpora and only surface on real astral-plane input.

15.7 Performance Concerns

The escape-free zero-copy fast path (step 1) is the common case for typical JSON (most string values contain no escapes) and must remain allocation-free — regressions here disproportionately hurt the §4 DOM-throughput target because string values dominate node count in citm_catalog.json- class documents. The surrogate-combining state machine adds one branch per \u escape; this is negligible relative to escape frequency in real corpora.

15.8 Edge Cases

A string that is entirely one giant \uXXXX run with no literal characters. A string exactly at the Limits::max_string_bytes boundary before and after unescaping (unescaping can only shrink or keep length equal for single-char escapes, but the pre-unescape span length is what's bounded by the tokenizer, per P12's scan-time enforcement extended to strings). An empty string "". A string containing an escaped astral-plane character immediately followed by another escaped astral-plane character with no literal bytes between ("😀😁").

15.9 Failure Analysis

Symptom: astral-plane fixture produces two 3-byte UTF-8 sequences instead of one 4-byte sequence. Root cause: surrogate-pending state not implemented — each \uXXXX treated independently. Debug: step through the PendingSurrogate transition on the exact fixture and confirm the combine formula executes exactly once per pair, not once per \u. Symptom: a valid string with no escapes still allocates from the arena. Root cause: the escape-free detection in step 1 runs too late (after tokenization has already discarded the "contains backslash" flag) — the flag must be computed and threaded through from the tokenizer, not re-derived by re-scanning.

15.10 Operational Notes

The zero-copy-eligibility flag computed in this phase is the first concrete instance of the untrusted-input lifetime obligation named in §11's StringView.borrowed_from_input field — any future refactor of the tokenizer must preserve this flag's correctness or silently regress P5 without a compiler error to catch it (it's a runtime/logical contract, not a type-level one, absent further language support).

16. Phase 4 — UTF-8 Validation

16.1 Objectives

Implement the scalar Utf8Validator per the byte-range table in §8.4, independent of and prior to the SIMD variant (Phase 10), closing I3 ("every accepted string is well-formed UTF-8 with no lone surrogate") for the full input, not just the escape-decoded output of Phase 3. This phase makes P11 operational: string content is not trusted until proven well-formed.

16.2 Detailed Implementation Steps

  1. Implement a DFA-based scalar validator following Hoehrmann's table-driven design (referenced in §5's reference-implementation lessons via the simdjson comparison), validating the exact byte-range constraints of §8.4 per sequence length (1–4 bytes).
  2. Enforce overlong-encoding rejection explicitly: the tightened byte-2 ranges for 3- and 4-byte sequences (e.g., 0xE0 requires byte 2 in 0xA0–0xBF, not the general 0x80–0xBF) per the §8.4 table — this is the single most commonly mis-implemented rule (RFC 3629, Unicode conformance chapter C10).
  3. Enforce surrogate-range rejection: 0xED requires byte 2 in 0x80–0x9F, rejecting the encoding of U+D800–U+DFFF as raw UTF-8 (surrogates are only valid as \u escape halves per §8.3, never as literal UTF-8 bytes in the input stream).
  4. Enforce the U+10FFFF ceiling: 0xF4 requires byte 2 in 0x80–0x8F.
  5. Run the validator over every string span (both zero-copy and unescaped-and-materialized) before any StringView is exposed to a caller — this validation cannot be skipped even on the zero-copy fast path (P11 explicitly forbids skipping it there).
  6. Run the validator over the entire input buffer at the whitespace/structural-character level too — a malformed UTF-8 sequence appearing outside a string (e.g., in what should be whitespace) must also be rejected, since RFC 8259 requires the whole document be valid UTF-8 (section 8.1).
  7. Build the worked accept/reject byte sequences from §8.4 into a dedicated fixture file and wire it into the conformance harness alongside JSONTestSuite's own UTF-8-related n_string_* cases.
  8. Add a differential check comparing this scalar validator's verdict against the Unicode Consortium's public UTF-8 conformance test data where available, beyond JSONTestSuite alone.

16.3 Deliverable

A scalar Utf8Validator (include/jsonp/utf8.hpp) rejecting every overlong encoding, every surrogate-range encoding, and every out-of-range (>U+10FFFF) sequence, returning the byte offset of the first violation.

16.4 Acceptance Criteria

100% pass rate on JSONTestSuite's UTF-8-related fixtures (n_string_overlong_*, n_string_UTF-8_invalid_sequence*, n_string_unicode_CapitalU*); the §8.4 worked-reject byte sequences (E0 80 80, ED A0 80) both reject at offset 0; the §8.4 worked-accept sequence (E2 82 AC) accepts; UTF-8 validation throughput on well-formed ASCII-heavy input ≥1.5 GB/s (scalar target, §4) measured on twitter.json.

16.5 Conformance Fixtures

conformance/utf8_edge/overlong_null.json — bytes C0 80, purpose: 2-byte overlong encoding of U+0000, expected reject at offset of the sequence start. conformance/utf8_edge/surrogate_high.json — bytes ED A0 80, purpose: encodes U+D800, expected reject. conformance/utf8_edge/max_codepoint.json — bytes F4 8F BF BF (U+10FFFF), purpose: exactly at the ceiling, expected accept. conformance/utf8_edge/over_ceiling.json — bytes F4 90 80 80 (U+110000), purpose: one past the ceiling, expected reject.

16.6 Pitfalls

  • Using the general continuation-byte range (0x80–0xBF) for byte 2 of every multi-byte sequence instead of the tightened, length-and-leading-byte-specific ranges in §8.4 — this accepts overlong encodings and surrogate-range encodings that RFC 3629 forbids. Manifestation: n_string_overlong_* fixtures wrongly pass.
  • Validating only string content (post-Phase-3 unescape) and skipping validation of raw bytes outside strings — a malformed sequence in what looks like whitespace between tokens still violates "the whole document must be valid UTF-8" and must be caught.
  • Conflating "this byte sequence decodes to a valid code point" with "this byte sequence is the shortest encoding of that code point" — validity requires both; the overlong check is a distinct rule from the range check, easy to omit if only checking the final decoded value.
  • Off-by-one at the U+10FFFF ceiling — using 0x90 instead of 0x8F as the byte-2 upper bound for leading byte 0xF4, silently accepting one extra invalid code point.

16.7 Performance Concerns

Scalar UTF-8 validation on the SIMD-disabled path (§4: 1.5 GB/s target) must not degrade to a byte-at-a-time branchy implementation for the common ASCII case — a fast ASCII-only pre-check (e.g., a single comparison against the high bit) should short-circuit before falling into the full multi-byte DFA, since real-world JSON is overwhelmingly ASCII outside of a minority of string values.

16.8 Edge Cases

A string containing only ASCII (fast path, no multi-byte sequences at all). A string where the very last byte is a truncated multi-byte sequence (e.g., input ends mid-way through a 3-byte sequence) — must reject with an offset pointing at the start of the truncated sequence, not read past the buffer end (I1). A document where invalid UTF-8 appears in a key rather than a value — both are string productions per the grammar and must be validated identically.

16.9 Failure Analysis

Symptom: fuzzing finds an input that reads one byte past the buffer end during UTF-8 validation. Root cause: the validator assumes a full multi-byte sequence is available without checking remaining-byte count before dereferencing byte 2/3/4. Detection: ASan heap-buffer-overflow report in the fuzz job (§28); this is I1 in direct violation and must gate a release. Symptom: a surrogate-range fixture passes validation. Root cause: byte-2 range for leading byte 0xED not tightened to 0x80–0x9F. Debug: run the exact ED A0 80 fixture through the validator in isolation and inspect which range check failed to fire.

16.10 Operational Notes

The scalar validator built in this phase is the correctness oracle for Phase 10's SIMD validator — I5 (SIMD and scalar must produce identical verdicts) cannot be verified until both exist, so this phase's implementation must be frozen and well-tested before Phase 10 begins differential testing against it.

17. Phase 5 — Exact Number Parsing with Slow-Path Fallback

17.1 Objectives

Implement NumberConverter per the §8.5 decision procedure: fast-path integer conversion, the Eisel-Lemire algorithm (Lemire 2021) for doubles, and a correctly-rounded big-integer slow-path fallback (Gay 1990) for the documented ~0.5% of inputs where Eisel-Lemire's fast path is insufficient. This phase makes P3 ("number conversion is exact or it is a data-corruption bug") operational — the load-bearing correctness concern of the entire blueprint.

17.2 Detailed Implementation Steps

  1. Implement classify (§8.5 step 1): a single scan of the number span determining NumberKind::Integer vs NumberKind::Double without allocating, per the decision table.
  2. Implement the integer fast path: multiply-add accumulation with explicit overflow detection (compare against INT64_MAX/INT64_MIN boundaries before each multiply-add step, not after); on overflow, fall through to the double path rather than wrapping (data-corruption-by-silent- wraparound is exactly what P3 forbids).
  3. Implement the Eisel-Lemire fast path (Lemire 2021): precompute the power-of-ten lookup table at compile time (constexpr); parse mantissa digits into a 64-bit integer, multiply by the looked- up power-of-ten's 128-bit representation, and round using the algorithm's documented rounding rule; detect the failure signal (insufficient precision in the 128-bit product) and route to step 4 rather than returning a possibly-incorrect result.
  4. Implement the big-integer slow path (Gay 1990): arbitrary-precision decimal-to-binary conversion producing a correctly-rounded (round-half-to-even, per Goldberg 1991 and IEEE 754-2019) double for any input that reaches this path, including subnormal-boundary values.
  5. Implement the -0 special case explicitly (§8.5 worked example): preserve the negative-zero sign bit through finalize rather than normalizing to positive zero.
  6. Implement huge-exponent handling (§8.5 worked example, 1e400): default-reject with ErrorCode::NumberOutOfRange; gate the alternative "produce +Infinity" behavior behind ParseOptions::allow_infinity_on_overflow (ADR-15-adjacent), defaulting to off.
  7. Run the full parse-number-fxx-test-data corpus (Nigel Tao, 4M cases, cited via Lemire 2021's companion test data) through the converter and assert bit-exact agreement with the corpus's documented correctly-rounded answers for every case.
  8. Add differential testing against a reference strtod/big-decimal implementation for the subset of cases specifically constructed to stress the Eisel-Lemire failure boundary (near-halfway mantissa values at extreme exponents).

17.3 Deliverable

A NumberConverter producing a bit-exact, correctly-rounded NumberValue for every finite double in the 4M-case parse-number-fxx-test-data corpus, with documented, tested behavior for -0, integer-overflow-to-double fallback, and huge-exponent rejection.

17.4 Acceptance Criteria

100% bit-exact match against parse-number-fxx-test-data (4,000,000 cases, zero mismatches); 9007199254740993 converts to 9007199254740992.0 (round-half-to-even, §8.5 worked example); 2.2250738585072014e-308 converts via the slow path to the correctly-rounded subnormal value; -0 preserves its sign bit through finalize; 1e400 rejects with ErrorCode::NumberOutOfRange by default; slow-path invocation rate on the corpus matches the ~0.5% figure documented by Lemire 2021 (used as a sanity check that the fast path is actually engaging, not silently always falling through).

17.5 Conformance Fixtures

conformance/float_roundtrip/fxx_test_data/ (vendored, 4M cases) — purpose: the primary correctness oracle for this phase. beyond_2_53.json (9007199254740993) — purpose: §8.5 worked example. subnormal_boundary.json (2.2250738585072014e-308) — purpose: slow-path forcing case. huge_exponent.json (1e400) — purpose: overflow-rejection default. negative_zero.json (-0) — purpose: sign-bit preservation.

17.6 Pitfalls

  • Treating Eisel-Lemire's fast path as always correct and never checking its documented failure signal — this silently produces incorrectly-rounded doubles for the ~0.5% of inputs at precision boundaries, a direct P3 violation that will not surface on casual testing (only on the 4M-case corpus or targeted adversarial construction).
  • Implementing integer overflow detection as "multiply first, then check if the result looks wrong" (post-hoc) instead of pre-checking bounds before the multiply — signed integer overflow is undefined behavior in C++ and UBSan will flag it, but only if the exact overflow-triggering input is exercised in a sanitized test run.
  • Normalizing -0 to 0 anywhere in the pipeline (a common "simplification") — breaks I4's round-trip-bit-identical invariant specifically for this one input class, easy to miss because -0 == 0 numerically and most equality-based tests won't catch the sign-bit difference.
  • Using strtod as a fallback "for simplicity" on any code path reachable from untrusted input — reintroduces locale-dependence (a decimal-comma locale silently misparses 3.14) that this entire phase exists to eliminate (ADR-12).

17.7 Performance Concerns

The classify step (step 1) must be O(1) additional work over the tokenizer's already-completed scan, not a second full re-scan of the number span — re-scanning doubles the cost of the dominant common case (small integers) and undermines the §4 throughput target. The slow path's big-integer arithmetic is expected to be orders of magnitude slower than the fast path per the ~0.5% figure — this is acceptable only because it's rare; if fuzzing or production telemetry (§26's numbers.slow_path_conversions metric) shows an unexpectedly high slow-path rate, that is a performance regression signal, not merely a correctness non-issue.

17.8 Edge Cases

0 and -0 (both valid, distinct sign bits). The smallest positive subnormal double, 4.9406564584124654e-324. A mantissa with exactly 17 significant digits (the maximum needed to uniquely round-trip any double, per Steele & White 1990) at various exponents. An integer exactly at INT64_MAX (9223372036854775807) and one past it (9223372036854775808, must fall through to double, not wrap to negative).

17.9 Failure Analysis

Symptom: a specific input from the 4M-case corpus mismatches by exactly one ULP (unit in the last place). Root cause: almost always an off-by-one in the round-half-to-even tie-breaking logic at the Eisel-Lemire/slow-path boundary. Detection: bisect the corpus to find the minimal failing case, then trace it through both the fast and slow paths independently to see where they'd disagree. Symptom: telemetry shows numbers.slow_path_conversions far above 0.5% in production. Root cause: a bug in the fast-path failure-signal check causing it to route valid-for-fast-path inputs to the slow path unnecessarily — a performance bug, not a correctness one, but worth a regression fixture.

17.10 Operational Notes

numbers.slow_path_conversions and numbers.roundtrip_failures (the latter must always read zero, per I4) are the two number-specific metrics that feed §26's dashboards; roundtrip_failures above zero in any environment is a release-blocking signal, not a monitored-and-triaged-later one.

18. Phase 6 — Exact Number Serialization and Round-Trip Proof

18.1 Objectives

Implement double-to-string serialization using Ryū (Adams 2018, locked by ADR-14), producing the shortest string that round-trips back to the exact same double, and prove parse→serialize→parse identity over the same 4M-case corpus used in Phase 5. This phase closes I4 ("every finite double survives parse→serialize→parse bit-identically") end-to-end for the first time.

18.2 Detailed Implementation Steps

  1. Implement Ryū's core algorithm (Adams 2018): compute the shortest decimal representation that, when parsed back, yields the identical double — using the algorithm's fixed-precision integer arithmetic, no fallback path (unlike Grisu, per ADR-14's rationale).
  2. Implement integer serialization (for NumberKind::Integer values) as straightforward decimal digit emission — no floating-point algorithm needed, but must handle INT64_MIN correctly (its magnitude has no positive int64_t representation; must special-case or widen).
  3. Implement -0 serialization: emit the literal text -0, not 0, preserving the sign bit captured in Phase 5's finalize step (I4 applies symmetrically to serialization, not just parsing).
  4. Implement exponent-form decision logic: Ryū's output may be in fixed or scientific notation depending on magnitude — follow Ryū's own shortest-representation choice rather than imposing an arbitrary fixed/scientific threshold that might produce a longer-than-necessary string.
  5. Wire the serializer's number path into the broader Serializer (this phase produces the number sub-component; full serializer integration is Phase 7).
  6. Run the parse→serialize→parse property test over the full 4M-case corpus: parse each case, serialize the resulting NumberValue, re-parse the serialized text, and assert the final double is bit-identical to the first parse's result (I4).
  7. Add a targeted fixture set for values known to stress shortest-round-tripping edge cases: powers of two, powers of ten, and values adjacent to the subnormal boundary.
  8. Benchmark serialization throughput against the §4/§30 target (1.5–3.0 GB/s compact mode) on a numeric-heavy corpus (canada.json, per the simdjson benchmark set).

18.3 Deliverable

A Ryū-based number serializer producing the shortest round-tripping decimal representation for every finite double, with -0 and INT64_MIN handled correctly, verified bit-identical round-trip over the full 4M-case corpus.

18.4 Acceptance Criteria

Zero round-trip failures (I4) over parse-number-fxx-test-data (4,000,000 cases); -0 serializes to the exact text -0; INT64_MIN (-9223372036854775808) serializes correctly without integer overflow in the serialization routine itself; serialization throughput ≥1.5 GB/s compact mode on canada.json (§4).

18.5 Conformance Fixtures

(shared corpus with Phase 5) conformance/float_roundtrip/fxx_test_data/ — purpose: round-trip proof, now exercising both parse and serialize. int64_min.json — purpose: INT64_MIN boundary. shortest_repr_powers_of_two.json — purpose: values like 2.0^52 where naive serialization might emit more digits than necessary. negative_zero_serialize.json — purpose: -0 text-form check.

18.6 Pitfalls

  • Implementing -INT64_MIN anywhere in the integer-serialization path (to get a "positive magnitude to emit digits for") — this is itself undefined behavior in two's-complement arithmetic since INT64_MIN has no positive counterpart; must special-case the digit emission or widen to a 128-bit intermediate.
  • Assuming Ryū's shortest representation is unique across all correct implementations — different correct algorithms can produce different shortest strings if there's a tie in digit count; correctness is "round-trips exactly," not "matches a specific reference string" — differential tests against other libraries (§28) must compare round-trip behavior, not textual output.
  • Emitting 0 instead of -0 "because they're numerically equal" — this is the same P3/I4 violation as Phase 5's parsing-side pitfall, now on the write side; both must be fixed together or a round-trip test will still fail even if each half looks correct in isolation.
  • Choosing a fixed decimal-point threshold for scientific notation that sometimes produces a longer string than Ryū's natural output — defeats the "shortest" property even if round-trip correctness is preserved, regressing the serialize-throughput target via unnecessary bytes.

18.7 Performance Concerns

Ryū's whole selling point (per ADR-14's rationale over Grisu) is having no slow-path fallback rate to worry about — if a slow path is somehow needed here, that's a sign the implementation has a bug, not that a rare-case fallback needs building (contrast directly with Phase 5's number-parsing slow path, which is expected and by design). Serialization throughput is dominated by digit- emission loop efficiency; avoid per-digit division where a batch/table-driven digit extraction is available.

18.8 Edge Cases

The double value 1.0 (must serialize as 1.0 or 1, not 1.00000000000000001 or similar artifacts of a broken shortest-representation implementation). Very large finite doubles near DBL_MAX. Very small subnormal doubles near DBL_MIN's subnormal boundary (paired with Phase 5's 2.2250738585072014e-308 fixture, now serialized). Integer NumberKind::Integer value 0 (distinct code path from double 0.0, must not be confused with -0, which is exclusively a double concept since -0 as an integer literal parses as NumberKind::Double per §8.5's table).

18.9 Failure Analysis

Symptom: round-trip test fails for a specific double, but the parse side (Phase 5) already passed its own bit-exact check independently. Root cause: isolate to the serialize step specifically — compare Ryū's output text against a known-correct reference (e.g., Python's repr(float), which also implements shortest-round-tripping) for the exact failing value. Symptom: INT64_MIN serialization crashes under UBSan. Root cause: unchecked negation of INT64_MIN somewhere in the digit-emission path — grep for any -value on an int64_t in the integer serialization routine.

18.10 Operational Notes

This phase's round-trip property test, run over the full 4M-case corpus, is expensive enough (minutes, not seconds) that it should run as a dedicated CI job distinct from the fast per-push unit-test suite — schedule it on every merge to the main branch and nightly, per the CI topology in §29, rather than on every commit in a feature branch.

19. Phase 7 — Serializer with Escaping and Pretty-Printing

19.1 Objectives

Build the full Serializer combining Phase 6's number serialization with string escaping (§8.10) and structural formatting (compact and pretty modes), producing valid JSON text for any Value tree, with round-trip identity through re-parsing (extending I4's number-specific guarantee to the whole document).

19.2 Detailed Implementation Steps

  1. Implement the compact serializer: walk the Value tree (iteratively — recursive walking of a tree built under a depth limit is bounded and safe, but favor iteration for consistency with the eventual streaming serializer path) emitting minimal JSON text.
  2. Implement the escaping decision table (§8.10) as a constexpr per-byte lookup, precomputed at compile time — informed by the RapidJSON writer.h lesson in §5 (precomputed dispatch table for the fast path).
  3. Implement EscapeMode::Minimal (default: only mandatory escapes, non-ASCII passed through raw) and EscapeMode::AsciiOnly (escape all non-ASCII as \uXXXX, re-encoding astral-plane code points as a surrogate pair on output — the inverse of Phase 3's combining step).
  4. Implement key-ordering per SerializeOptions::sort_keys (ADR-17): default insertion order (pass through the DOM's natural iteration order); optional sorted mode for canonicalization use cases.
  5. Implement pretty-printing: configurable indent width, newline-and-indent between object/array elements, space after : — verify output remains valid JSON (whitespace is cosmetic only per the grammar in §8.1).
  6. Wire Phase 6's number serializer into the value-walking loop for NumberKind::Integer and NumberKind::Double leaves.
  7. Implement the streaming-serializer variant (start_object(), key(), value(), end_object()-shaped incremental API) sharing the escaping and number logic with the DOM-walking serializer, producing output with no intermediate DOM allocation (anticipates Phase 8's SAX integration).
  8. Run the parse→serialize→parse property test over a corpus of real-world documents (twitter.json, citm_catalog.json) asserting value-equality (not necessarily byte-identical text, since whitespace and duplicate-key handling can legitimately normalize) between the original parse and the round-tripped re-parse.

19.3 Deliverable

A Serializer producing valid, escaped, optionally pretty-printed JSON text for any Value tree or equivalent streaming call sequence, verified round-trip-value-equal on twitter.json and citm_catalog.json.

19.4 Acceptance Criteria

Output validated by re-parsing with this library's own parser (self-consistency) and, per §28, cross-validated against at least one external validator; compact-mode throughput ≥1.5 GB/s and pretty-mode ≥0.8 GB/s on twitter.json (§4); zero unescaped " or \ bytes in any output sample across the corpus (mandatory-escape completeness check); EscapeMode::AsciiOnly output contains no byte ≥0x80.

19.5 Conformance Fixtures

benchmarks/corpus/twitter.json — purpose: general round-trip and throughput. escape_all_control_ chars.json — a string containing every byte 0x00–0x1F, purpose: mandatory-escape completeness. sort_keys_canonical.json — an object with keys in non-alphabetical insertion order, purpose: sort_keys option verification. pretty_print_nested.json — a 3-level-deep object/array mix, purpose: indent/newline placement correctness.

19.6 Pitfalls

  • Escaping / by default "to be safe" — RFC 8259 permits but does not require escaping the solidus; unnecessary escaping bloats output size and diverges from the ADR-18 escaping-table decision (§8.10 explicitly locks solidus as unescaped in both compact and pretty modes). Manifestation: output byte count regression against the §30 throughput-adjacent size targets.
  • Implementing AsciiOnly mode's astral-plane re-encoding without the inverse surrogate-pair split — emitting a single \uXXXXX (5 hex digits, invalid) instead of two \uXXXX\uXXXX surrogate halves for code points above U+FFFF.
  • Sorting keys by byte value when the intent was a locale-aware or code-point-aware sort — for canonicalization (ADR-17), the sort order itself must be specified precisely (byte-wise on the UTF-8 encoding is the locked choice) or two implementations claiming "sorted" will disagree, defeating the canonicalization purpose.
  • Recursive tree-walking in the serializer with no depth check — even though the DOM was built under a depth limit (I2), a future change that relaxes the limit or constructs a Value tree via DocumentBuilder without going through the parser could reintroduce unbounded depth on the write side; favor the iterative walk called out in step 1.

19.7 Performance Concerns

The compact-mode throughput target (1.5–3.0 GB/s) is roughly comparable to parse throughput because both are dominated by memory-bandwidth-bound tree traversal (§31) rather than CPU-bound computation, once Ryū (Phase 6) has already eliminated number-formatting as a bottleneck. Pretty- mode's lower target (0.8–1.5 GB/s) reflects the added indentation/newline byte-emission cost, not an algorithmic slowdown.

19.8 Edge Cases

An empty object or array serializing to {}/[] with no interior whitespace even in pretty mode (no elements to put on their own line). A single-element array/object in pretty mode (indent applies, but there's no comma-then-newline between siblings to get wrong). A string containing every mandatory-escape byte adjacent to non-ASCII content, exercising both the escaping table and (in AsciiOnly mode) the \uXXXX re-encoding path in the same string.

19.9 Failure Analysis

Symptom: round-trip test reports value-inequality on a document with duplicate keys. Root cause: expected, not a bug — duplicate-key resolution (I10, ADR-16) is a one-way normalization; the second parse of the serialized (already-deduplicated) output is correctly value-equal to the first parse's already-deduplicated result, but naive byte-for-byte comparison against the original source text would fail; the property test must compare Value trees, not source bytes, matching this section's step 8 design. Symptom: AsciiOnly mode output fails to re-parse. Root cause: an incomplete surrogate pair emitted for an astral-plane code point — verify both halves are written before any other byte is emitted, never interleaved with other escape processing.

19.10 Operational Notes

SerializeOptions::sort_keys is documented as a canonicalization aid, not a general-purpose formatting preference — callers building content-addressed hashes over JSON documents (a common downstream use case) depend on the byte-wise sort order being stable across library versions; a change to sort semantics is a compatibility break (§27) even though it's "just an output option."

20. Phase 8 — Streaming / SAX Interface

20.1 Objectives

Build the constant-memory streaming path: the SaxHandler push interface and the pull-based SaxEvent iterator (§8.9, §11), both sharing the Phase 0 tokenizer core, enabling parsing of documents far larger than available memory with no DOM construction (ADR-19).

20.2 Detailed Implementation Steps

  1. Refactor the tokenizer/parser core so that value-recognition logic (structural transitions of §8.2/§8.1) can drive either DOM construction (Phases 1–2) or direct event emission, without duplicating the state machine (ADR-19's shared-core rationale).
  2. Implement the push-based SaxHandler dispatch: on each recognized structural transition, call the corresponding on_start_object/on_key/on_string/etc. method instead of building a Value node.
  3. Implement the pull-based iterator: wrap the same core in a resumable-state form where next() -> SaxEvent advances the parser exactly one event per call (the state-machine refactor from Phase 9's iterative parser, pulled forward as a shared dependency — coordinate sequencing with §21).
  4. Implement chunked-buffer input: default 64 KiB read chunks (matching the arena block size convention for consistency, §4); when a string or number token spans a chunk boundary, buffer the partial token rather than erroring, and resume tokenization once the next chunk arrives.
  5. Apply the same UTF-8 validation (Phase 4) and number conversion (Phase 5) to streamed values as to DOM values — streaming must not be a "lesser" correctness mode; I3 and I4 apply identically.
  6. Apply the same Limits enforcement (depth, string length, document length) to the streaming path — an attacker sending an unbounded stream must be rejected exactly as a single oversized buffer would be (P2 applies regardless of input-delivery shape).
  7. Add a large-document streaming fixture (a multi-gigabyte synthetic [obj, obj, ...] log-style array) and verify constant memory usage (bounded by Limits and chunk size, not proportional to total document size) via a memory-instrumented test run.
  8. Add fault-injection tests for a chunk boundary landing mid-escape-sequence, mid-surrogate-pair, and mid-number-exponent, verifying correct resumption in each case.

20.3 Deliverable

A SaxHandler-based push parser and a SaxEvent-based pull iterator, both operating in bounded memory independent of total document size, sharing one tokenizer/parser core with the DOM path.

20.4 Acceptance Criteria

Successfully streams a 10 GB synthetic document in bounded memory (peak RSS within a small constant multiple of chunk size plus Limits ceilings, not proportional to the 10 GB total, verified fixture streaming_10gb_synthetic.json); JSONTestSuite pass rate 100% when run through the streaming path (in addition to the existing DOM-path harness); zero incorrect resumption across 500 randomly chosen chunk-boundary split points on a fixed test document (differential check: streamed result equals DOM-parsed result of the same document).

20.5 Conformance Fixtures

streaming_10gb_synthetic.json (generated, not vendored) — purpose: constant-memory claim. chunk_boundary_mid_escape.json — purpose: partial-token buffering correctness, split at a \ byte. chunk_boundary_mid_surrogate.json — split between the two halves of a \uXXXX\uXXXX surrogate pair. chunk_boundary_mid_number.json — split in the middle of an exponent.

20.6 Pitfalls

  • Treating a chunk boundary landing mid-token as an error instead of a buffering opportunity — this defeats the entire purpose of streaming (any real large document will have tokens spanning arbitrary chunk boundaries).
  • Building the pull iterator as a thin wrapper that internally still buffers the whole document before yielding the first event — silently reintroduces the memory-proportional-to-document-size problem streaming exists to solve, undetectable without a memory-instrumented test (unit tests alone won't catch it on small documents).
  • Applying Limits checks only at chunk boundaries rather than continuously — an attacker could craft a single chunk that itself violates a limit (e.g., one 64 KiB chunk containing a 350-million-character number literal if max_number_digits weren't enforced character-by- character as specified in P12/Phase 0).
  • Divergent duplicate-key handling between the SAX path (which has no object to deduplicate into — it just emits Key events) and the DOM path (I10) — document explicitly that SAX callers are responsible for their own duplicate-key policy since there's no DOM object to apply ADR-16 to.

20.7 Performance Concerns

Streaming throughput (§4: 1.0–2.5 GB/s) is necessarily lower than DOM-mode SIMD throughput because the chunked-buffer bookkeeping and per-event dispatch overhead (whether virtual call for SaxHandler or iterator-state-machine step for the pull API) adds per-token cost that DOM-mode's bulk tree construction can sometimes amortize better; do not conflate a streaming throughput regression with a Phase 10 SIMD regression — they are measured and gated separately (§30).

20.8 Edge Cases

A document that is a single top-level scalar streamed in multiple chunks (e.g., "a very long string" split across chunk boundaries) — must resolve to the same on_string call content-wise as if delivered in one chunk. A completely empty final chunk (stream ends exactly at a token boundary). A malformed document detected only after several gigabytes of otherwise-valid prefix — must reject at the correct byte offset without having silently emitted events for structure that turns out to be part of an ultimately-invalid document (see failure-path discipline in P7, extended: SAX callers must be told via on_error/SaxEvent::Error that any previously-emitted events describe a document that did not, in the end, validate as a whole).

20.9 Failure Analysis

Symptom: streamed parse of a large file uses memory proportional to file size despite the "constant memory" claim. Root cause: an unbounded internal buffer (often a debug logging buffer or a "just in case" full-document echo buffer) accidentally retaining every chunk instead of discarding processed ones — audit every std::vector/growable-buffer field reachable from the streaming parser's state for an unbounded-growth pattern. Symptom: a chunk-boundary fixture produces a different result than the DOM-parsed equivalent. Root cause: partial-token buffering logic drops or duplicates bytes at the exact boundary — bisect by shrinking the chunk size in 1-byte steps around the known boundary until the minimal reproducing split is found.

20.10 Operational Notes

The "document turned out invalid after N gigabytes of valid-looking prefix" scenario (§20.8) is an operationally important case for pipeline design: downstream consumers of SAX events must buffer or be prepared to roll back any side effects of processed events until a terminal success signal is received, not just until an error is received — document this clearly in docs/runbooks/ since it is a common source of partial-ingestion bugs in consuming systems, not in this library itself.

21. Phase 9 — Hardening: Depth/Size Limits, Iterative Deep Path, Fuzzing Campaign

21.1 Objectives

Close the stack-exhaustion risk left open by Phases 1–8's recursive-descent baseline by implementing the iterative deep-path parser (Grune & Jacobs ch. 8's explicit-stack technique, ADR-05), enforce every Limits field comprehensively across all entry points (DOM, SAX, streaming), and stand up the continuous fuzzing campaign (ADR-27) that is this section's primary deliverable alongside the code.

21.2 Detailed Implementation Steps

  1. Implement the iterative deep-path parser: an explicit heap-allocated stack of parse contexts (Object/Array, each with its current sub-state per §8.2-adjacent parser states), replacing native call-stack recursion once nesting exceeds a low static threshold (e.g., depth 32) — below the threshold, recursive descent remains simpler and equally safe; above it, switch to the explicit stack (ADR-05's hybrid rationale).
  2. Verify the iterative parser produces byte-for-byte identical ParseResults to the recursive parser across the entire JSONTestSuite and a randomly generated deep-nesting corpus — this is a differential-equivalence requirement, not merely "also works."
  3. Audit every Limits field (max_depth, max_document_bytes, max_string_bytes, max_number_digits, max_allocation_bytes) for enforcement at every entry point established in prior phases (DOM parser, SAX push handler, pull iterator, streaming chunked reader) — close any gap where a limit is checked in one path but not another (this directly targets I9's ordering requirement across all paths, not just the originally-implemented DOM path).
  4. Stand up fuzz/parse_target.cpp (parse-and-validate, no crash expected on any input), fuzz/roundtrip_target.cpp (parse→serialize→parse equality), building on libFuzzer.
  5. Seed the fuzz corpus (fuzz/corpus/) from JSONTestSuite plus the conformance fixtures built in Phases 0–8, giving the fuzzer a head start toward interesting structural coverage.
  6. Run the fuzz campaign under ASan, UBSan, and MSan (ADR-27) continuously via .github/workflows/fuzz.yml, persisting the corpus across runs so coverage accumulates rather than resetting.
  7. Add fault-injection tests: simulate allocation failure at every arena-allocation call site in sequence (I8), and truncation at every byte offset of a set of representative documents, asserting no crash and a well-formed ParseError in every case.
  8. Establish the zero-crash gate: any fuzz-discovered crash or sanitizer finding blocks merge until fixed and a regression fixture is added to the permanent corpus.

21.3 Deliverable

An iterative deep-path parser proven equivalent to recursive descent, comprehensive Limits enforcement across every entry point, and a continuously running, corpus-persisted fuzz campaign under ASan/UBSan/MSan with a zero-crash gate.

21.4 Acceptance Criteria

10,000-deep nesting input (default Limits::max_depth far exceeded) rejects cleanly via the iterative path with ErrorCode::DepthLimitExceeded, consuming heap-proportional-to-depth memory, not stack, and never crashing (verified under a constrained 64 KiB thread stack in CI); iterative and recursive parsers agree byte-for-byte on 100% of JSONTestSuite plus a 10,000-case random-nesting corpus; 72-hour continuous fuzz run (initial baseline, per ADR-27's ongoing-campaign model) produces zero crashes and zero sanitizer findings across all three fuzz targets; every fault- injection allocation-failure and truncation-offset test passes with a well-formed error, never UB.

21.5 Conformance Fixtures

depth_10000_nested_arrays.json — purpose: far-past-limit stack-exhaustion stress, expected clean reject. random_nesting_corpus/ (10,000 generated fixtures, varying depth and structure) — purpose: iterative/recursive differential equivalence. fuzz/corpus/ (persisted, growing) — purpose: continuous crash discovery. truncation_fixtures/ (one fixture per byte offset of a representative document set) — purpose: truncation fault-injection.

21.6 Pitfalls

  • Implementing the iterative parser's explicit stack with its own unbounded growth (no depth check on the explicit stack itself) — this merely moves the stack-exhaustion problem from the native call stack to the heap; the same Limits::max_depth check (I2, P8) must gate the explicit-stack push exactly as it gated native recursion.
  • Fuzzing only the DOM parse path and never the SAX/streaming paths — a crash reachable only through the streaming chunk-boundary logic (Phase 8) will never be found by a fuzz target that only calls the DOM entry point; multiple fuzz targets covering each entry point are necessary, not optional.
  • Treating a 24-hour clean fuzz run as sufficient evidence of hardening — fuzz campaigns are continuous by design (ADR-27) precisely because coverage accumulates over time; a short clean run is a baseline, not a completion criterion.
  • Fault-injecting allocation failure only at the "obvious" large-allocation sites and skipping small/inline-path allocation sites — an allocation-failure bug in a rarely-taken small-string arena path is just as much a crash risk as one in the main tree-construction path.

21.7 Performance Concerns

The iterative deep-path parser is expected to be measurably slower per-frame than native recursion (explicit-stack push/pop versus a CPU call instruction) — this cost is intentionally paid only above the depth-32 threshold (ADR-05), keeping the common shallow-document case on the faster recursive path; verify via benchmark that typical corpus documents (twitter.json, depth ≤10) never engage the iterative path at all.

21.8 Edge Cases

A document at exactly the depth-32 switchover threshold (must produce identical results whether implemented via the recursive or iterative path — the switchover point itself is an internal optimization detail, not observable behavior). A document that fails a limit check exactly at the boundary value (depth 512 succeeds, 513 fails, per Phase 1's fixture, now re-verified through the iterative path specifically). An allocation-failure injection at the very first allocation of a parse (arena's initial block) versus the very last (right before returning the completed Document).

21.9 Failure Analysis

Symptom: the iterative and recursive parsers disagree on a specific fixture. Root cause: a state in the explicit-stack machine not mapped correctly to its recursive-descent equivalent — cross- reference against the §8.2-adjacent parser state list and confirm every recursive-call site has a corresponding explicit-stack push/pop pair. Symptom: fuzzing discovers a crash after weeks of clean runs. Root cause: coverage-guided fuzzing found a structurally novel input class (this is the expected, intended behavior of continuous fuzzing per ADR-27, not evidence of a regression) — follow the docs/runbooks/fuzz_crash_repro.md runbook to minimize and fix, then commit the minimized case as a permanent regression fixture.

21.10 Operational Notes

The zero-crash fuzz gate (§21.4) is a release-blocking CI gate, not an informational dashboard metric — a red fuzz job must block the same way a failing unit test does, per ADR-27's "no fuzzing is unacceptable" stance; corpus persistence (fuzz/corpus/) must survive across CI runner instances (stored as a build artifact or in the repository itself under a size-management policy).

22. Phase 10 — SIMD Structural Scanning with Scalar-Differential Equivalence

22.1 Objectives

Implement SimdScanner per the §8.6 bitmask pipeline (simdjson-style stage 1: Langdale & Lemire 2019), covering AVX2 and NEON with runtime CPU-feature dispatch (ADR-07), and prove — not merely test — that it produces byte-identical structural indexes to the scalar tokenizer's implicit scanning (Phase 0) on every input, closing I5.

22.2 Detailed Implementation Steps

  1. Implement the 64-byte-chunk load-and-compare stage (§8.6 stage 1): vectorized comparison against the quote byte, producing quote_mask, using AVX2 intrinsics with a NEON port following the same logical structure (Muła/Kurz/Lemire SIMD string-processing techniques).
  2. Implement the backslash-run parity check (§8.6 stage 3): a carry-chain computation across chunk boundaries (a backslash run can span a 64-byte boundary) to correctly exclude escaped quotes from quote_mask — this is the single trickiest part of the whole pipeline per simdjson's own documented experience (§5 reference-implementation lesson).
  3. Implement the prefix-XOR scan (§8.6 stage 4) producing in_string_mask, carrying state (parity of the running XOR) across chunk boundaries exactly as the backslash-run check does.
  4. Implement structural- and whitespace-mask extraction (§8.6 stages 5–6) via vectorized comparison against the six structural bytes and four whitespace bytes, masked by NOT in_string_mask.
  5. Implement index extraction (§8.6 stage 7) using pext/iterate-and-clear (BMI2 where available, portable bit-manipulation fallback otherwise) to produce the flat structural_indices[] array consumed by the tokenizer.
  6. Implement runtime CPU-feature detection at library init (ADR-07, §4's <1ms startup budget): probe for AVX2/BMI2 (x86) or NEON (ARM) and select the corresponding SimdScanner implementation, falling back to the Phase 0 scalar path if none is available.
  7. Build the differential-equivalence fuzz target (fuzz/simd_scalar_diff_target.cpp, I5): for every fuzzer-generated input, run both the SIMD and scalar scanners and assert byte-identical structural_indices[] output; this target runs continuously alongside Phase 9's crash-oriented fuzz targets.
  8. Benchmark DOM parse throughput with SIMD engaged against the §4 target (2.0–4.0 GB/s) on twitter.json and citm_catalog.json, and validate the documented scalar-fallback throughput penalty (6–8x) by deliberately disabling SIMD dispatch and re-measuring.

22.3 Deliverable

A SimdScanner (AVX2 primary, NEON port) selected via runtime CPU dispatch, proven byte-identical to the scalar scanner across a continuously running differential fuzz target, hitting the §4 DOM-throughput target on the simdjson benchmark corpus.

22.4 Acceptance Criteria

Zero mismatches between SIMD and scalar structural indexes across the full differential fuzz corpus (I5, simd.diff_mismatches metric permanently at zero — §7); DOM parse throughput ≥2.0 GB/s on twitter.json with SIMD engaged (§4); scalar-fallback throughput lands in the documented 300–500 MB/s band when SIMD is disabled, confirming the 6–8x penalty figure is accurate rather than aspirational; CPU-feature dispatch correctly selects AVX2 on a capable runner and falls back to scalar on a runner with AVX2 masked off (verified via a CI matrix leg, ADR-28).

22.5 Conformance Fixtures

benchmarks/corpus/twitter.json, citm_catalog.json, canada.json — purpose: throughput validation against §4/§30 targets. backslash_run_boundary.json (hand-built, a string with a backslash run straddling a 64-byte offset) — purpose: stage-3 carry-chain correctness. fuzz/corpus/ (shared with the differential target) — purpose: continuous SIMD/scalar equivalence proof.

22.6 Pitfalls

  • Failing to carry the backslash-run parity state across a 64-byte chunk boundary — a backslash run that happens to end exactly at a chunk boundary produces a different (wrong) escaped-quote determination than the same input scanned as one contiguous buffer; this is exactly the class of bug the boundary-straddling fixture in §22.5 exists to catch, and it will not show up on inputs shorter than 64 bytes.
  • Reading past the end of the input buffer when the final chunk is shorter than 64 bytes — the vectorized load must mask off or zero-pad the trailing partial chunk rather than reading adjacent (possibly unmapped) memory, a direct I1 violation reachable only on inputs whose length isn't a multiple of 64.
  • Assuming AVX2 availability implies BMI2 (pext) availability — some real-world CPUs have one without the other; the dispatch table (ADR-07) must probe both independently, not bundle them.
  • Treating a single passing run of the differential fuzzer as sufficient — like Phase 9's crash fuzzing, SIMD/scalar equivalence fuzzing is continuous; a coverage gap in the seed corpus can hide a boundary bug for a long time before a generated input happens to exercise it.

22.7 Performance Concerns

The scalar-fallback penalty (6–8x, §4) is a designed, accepted tradeoff for portability (ADR-07), not a bug to chase — do not over-invest in scalar-path micro-optimization at the expense of SIMD- path correctness work, since production deployments are expected to have AVX2 or NEON available. pext-based index extraction is markedly faster than a branchy bit-scan loop on BMI2-capable hardware; the fallback bit-manipulation path (for non-BMI2 x86) should still avoid a full byte-at-a-time scan of the mask.

22.8 Edge Cases

An input whose length is exactly a multiple of 64 bytes (no partial trailing chunk at all). An input of length 1 (far short of one chunk — the partial-chunk masking logic's most extreme case). A string of pure backslashes with an odd total count spanning multiple chunk boundaries (stresses the carry-chain parity logic repeatedly). A document with zero structural characters at all (a top-level string or number with no {/[/:/, anywhere) — the structural-index array should be empty or near-empty, not a degenerate case that crashes the extraction step.

22.9 Failure Analysis

Symptom: the differential fuzz target reports a mismatch only on inputs longer than roughly 128 bytes. Root cause: strongly suggestive of a chunk-boundary carry-chain bug (backslash-run parity or prefix-XOR state) since single-chunk inputs can't exercise cross-chunk state — bisect the minimized failing input to confirm the mismatch first appears exactly at a 64-byte offset. Symptom: throughput on an AVX2-capable CI runner unexpectedly matches the scalar-fallback band. Root cause: CPU-feature dispatch (ADR-07) failed to detect or select the AVX2 path — verify the dispatch probe logic directly (log which path was selected) rather than assuming the benchmark number alone diagnoses the cause.

22.10 Operational Notes

simd.dispatch_path_taken (recorded per §26) should be logged or exposed at library init so operators can confirm which scanner variant is active in a given deployment — silent scalar fallback on hardware believed to support AVX2 is a performance regression that is otherwise invisible without this telemetry.

23. Phase 11 — JSON Pointer/Patch, Conformance Completion, Performance Hardening

23.1 Objectives

Implement JSON Pointer (RFC 6901) and JSON Patch (RFC 6902) as a layer operating purely on the completed Value tree (§8.11), bring JSONTestSuite conformance and the full §28 verification strategy to their final documented state, and close out remaining §30 performance-engineering targets — this is the terminal phase before the Phase 11 exit criteria referenced throughout this document are considered met.

23.2 Detailed Implementation Steps

  1. Implement JsonPointer::parse per the §8.11 EBNF, including the ~0/~1 escaping rules for literal ~ and / characters within a reference token (RFC 6901 section 3).
  2. Implement JsonPointer::resolve(const Document&) — traverse the Value tree per pointer segment, returning a reference/pointer to the target Value or a not-found signal; array segments use the - token to mean "one past the end" only in the context of add (RFC 6902), not resolution for read.
  3. Implement each PatchOpKind (§8.11 table: add, remove, replace, move, copy, test) via DocumentBuilder (ADR-20), since patch application is DOM mutation and the base Document is immutable by default (P10).
  4. Implement whole-patch atomicity: if any operation in a patch array fails (especially test), no prior operation's effect is visible in the result — apply into a scratch builder and commit only on full success, mirroring P7's "no partial result on failure" principle at the patch level.
  5. Run the JSON Patch specification's own test suite (referenced in RFC 6902's companion test data where available) alongside this blueprint's own fixture set.
  6. Complete the JSONTestSuite i_* expected-verdict table (seeded in Phase 0, §12) to its final, fully-documented state, cross-referenced into §28's testing strategy.
  7. Run the full differential-testing suite (§28) against simdjson, RapidJSON, and nlohmann/json across the shared benchmark corpus, adjudicating any remaining disagreement against RFC 8259 directly and recording the adjudication.
  8. Perform final performance hardening: re-run every §30 M-series target, close any remaining gap, and confirm the §34 back-of-envelope model's predictions are within an order of magnitude of measured reality (a mismatch here signals either a documentation error in §34 or an unexpected implementation inefficiency worth investigating).

23.3 Deliverable

A complete JSON Pointer/Patch implementation operating on the Value tree, a fully closed JSONTestSuite i_* verdict table, a completed differential-testing pass against three reference implementations, and a final performance-hardening pass against all §30 targets.

23.4 Acceptance Criteria

JSON Pointer resolves 100% of RFC 6901's own worked examples (section 5) correctly; JSON Patch passes 100% of this blueprint's fixture set including atomicity fixtures (a failing test op leaves the document completely unchanged); JSONTestSuite 100% pass rate maintained end-to-end (y_/n_/i_, all documented); differential testing against simdjson/RapidJSON/nlohmann shows zero unadjudicated disagreements (every disagreement traces to a specific RFC 8259 clause and a recorded resolution); all twelve-plus §30 M-series targets met or explicitly re-baselined with documented rationale.

23.5 Conformance Fixtures

rfc6901_worked_examples.json — the RFC's own section 5 example document and pointer set, purpose: canonical-example correctness. patch_atomicity_failing_test_op.json — a patch array where the third of five operations is a failing test, purpose: verify operations 1–2's effects are rolled back. differential/shared_corpus/ — the twitter.json/citm_catalog.json/canada.json set, purpose: cross-implementation adjudication.

23.6 Pitfalls

  • Implementing JSON Pointer resolution as if it could read and write with the same code path — the - array-index token is meaningful only for add/write contexts (append), not for read/resolve, and treating it as a valid read index will either crash or silently return the wrong element.
  • Applying patch operations directly to the live Document instead of a scratch builder, then discovering a later test operation fails — without the scratch-builder-then-commit discipline (step 4), the caller is left with a half-applied patch and no way to recover the pre-patch state, violating the patch-level analog of P7.
  • Treating a differential-testing disagreement against a reference implementation as automatically "our bug" or automatically "their bug" — RFC 8259 explicitly leaves some behavior implementation- defined (duplicate keys, for instance); the correct response is adjudication against the spec text, not deference to either implementation's precedent.
  • Declaring the phase complete when JSONTestSuite passes but skipping the re-run of §30's performance targets — a correctness-complete parser that silently regressed throughput somewhere in Phases 8–10's changes would not be caught without this explicit final re-measurement step.

23.7 Performance Concerns

JSON Pointer/Patch operations are not on the hot parsing path and are not subject to the §4 GB/s-class throughput targets — they operate on an already-parsed Value tree at a granularity (single-path resolution, single-operation application) where correctness and atomicity dominate the design tradeoff, not raw throughput; do not over-optimize this layer at the expense of the atomicity guarantee in step 4.

23.8 Edge Cases

The empty JSON Pointer "" (RFC 6901: refers to the whole document). A pointer with a ~0 immediately followed by a literal 0 (~00 decodes to ~0, a literal tilde-zero, not two escape sequences) — the escaping table order (~1 before ~0 is not itself ambiguous, but a naive substitution-based decoder can double-substitute if implemented as sequential string replacement rather than a single left-to-right scan). A move patch operation where from is a prefix of path (RFC 6902 section 4.4 explicitly calls this an error — moving a value into one of its own descendants). A test operation comparing a Double against an Integer of the same numeric value (must this be considered equal? — resolved per RFC 6902's value-equality definition, which this blueprint documents as numeric-value equality, not representation equality, consistent with NumberKind being an internal optimization, not an observable distinction — §27).

23.9 Failure Analysis

Symptom: a move operation into a descendant path succeeds instead of erroring. Root cause: the prefix check (RFC 6902 section 4.4) not implemented — add the explicit path-prefix comparison before applying the operation. Symptom: differential testing shows this implementation and simdjson disagree on a duplicate-key document's final value. Root cause: expected per I10/ADR-16 — not a defect, but must be recorded as an adjudicated, documented disagreement (RFC 8259 section 4 leaves this implementation-defined) rather than left as an unexplained red mark in the differential-testing report.

23.10 Operational Notes

The completed i_* verdict table and the differential-testing adjudication record (§23.2 steps 6–7) together form the authoritative reference for any future contributor asking "why does this implementation do X instead of Y" for a spec-ambiguous case — keep both under version control alongside the fixtures they document, not merely in an ephemeral CI log.

26. Operational Readiness

Named metrics: parse.throughput_bytes_per_sec (by mode: DOM/streaming/serialize), parse. rejection_rate (segmented by ErrorCode), parse.depth_limit_hits, numbers.slow_path_ conversions, numbers.roundtrip_failures (must always read zero — a release-blocking signal if nonzero anywhere), simd.dispatch_path_taken (which scanner variant is active), simd.diff_ mismatches (must always read zero), arena.blocks_allocated, arena.bytes_high_water, fuzz. crash_count (per continuous campaign, §21).

Tracing: each parse call is a single traced span carrying document size, dispatch path taken (SIMD/scalar), and final ErrorCode or success; streaming parses emit one span per chunk plus a parent span for the whole stream.

Structured logging: every rejected document logs its ParseError (code, byte offset, derived line/column per P6) at a level appropriate to the caller's risk posture (info for expected-shape rejections in a validation gateway, warn/error for unexpected internal states); logs never include the full rejected document body by default (avoids leaking potentially sensitive payload content into log aggregation systems — an operational-security default, not a correctness one).

Dashboards: throughput-by-mode over time (regression visibility against §30 M-series targets); rejection-rate-by-error-code (spike in a specific code signals either an upstream data-quality change or an attack pattern, per §24); SIMD dispatch-path distribution across the fleet (T4/I5- adjacent visibility); fuzz-campaign crash count (must trend to and stay at zero).

Alerting philosophy: alert on numbers.roundtrip_failures > 0, simd.diff_mismatches > 0, and any fuzz.crash_count increase as release-blocking-severity pages, not warnings — these three correspond directly to I4, I5, and the zero-crash gate (§21.4) and are never acceptable in any quantity. Alert on rejection-rate anomalies and throughput regressions at a lower, triage-first severity.

SLOs: p99 parse latency ≤300 µs for a 64 KiB document (§4); zero round-trip failures (I4, hard SLO, not a percentage target); zero unresolved sanitizer findings at release time.

Incident response: a round-trip-failure or SIMD/scalar-mismatch incident follows the same "minimize, bisect, patch, add permanent regression fixture" loop used throughout Phases 5, 6, and 10 — the runbooks below formalize this loop per incident class.

Named runbooks under docs/runbooks/: fuzz_crash_repro.md (reproduce and minimize a fuzz- discovered crash), conformance_bisect.md (bisect a JSONTestSuite regression to the offending commit), throughput_triage.md (diagnose a §30 M-series regression via profiling), roundtrip_ failure.md (investigate an I4 violation from the minimal failing double to root cause).

Backup/restore: not applicable in the traditional sense — this is a stateless, in-process library with no persistent store of its own; "backup" is the vendored conformance corpus and fuzz-corpus persistence (§21.10), restored from version control or CI artifact storage.

Deployment topology: embedded directly into consuming application binaries (header-only, ADR-29); the CLI validator (tools/jsonp-validate) may be deployed standalone in an ingestion pipeline as a pre-validation gate ahead of a downstream service (mitigating T6 at a system-architecture level).

Canary/rollback/migration for a library: "canary" means shipping a new minor/patch version to a subset of internal consumers first and watching the metrics above for regressions before a fleet-wide version bump; "rollback" is pinning the previous version in the consumer's dependency manifest; there is no in-place migration step since each parse is independent and stateless.

27. Compatibility & Versioning

The accept/reject behavior of the parser is the primary compatibility contract — tightening strictness (rejecting an input a previous version accepted) is a breaking change requiring a major version bump under SemVer, even though it might be framed internally as "fixing a bug," because a consumer's existing valid-input corpus could newly fail. Loosening strictness (accepting an input a previous version rejected) is additive and minor-version-safe unless it changes the resulting Value for previously-accepted input.

API stability: the public header surface (include/jsonp/*.hpp signatures in §11) follows SemVer; additive fields on ParseOptions/Limits (both documented as additive-only in §11) are minor-version-safe; removing or renumbering an ErrorCode enumerator is a breaking change (§11's error-code-stability annotation).

ABI stability: the header-only distribution mode (ADR-29 primary) has no ABI contract to maintain across consumer recompilation boundaries by construction; the optional pre-compiled static-library variant does carry an ABI contract, and Value's internal bit layout (§8.7) is explicitly documented as an internal detail, not an ABI guarantee — a layout change requires a major version bump for the compiled-library distribution specifically, even if the header-only distribution's source-level API is unchanged.

C++ standard and toolchain support matrix: C++20 minimum (ADR-01); tested toolchains are GCC, Clang, and MSVC across the two most recent stable major releases of each at time of release, matching the CI matrix (ADR-28, §29).

SIMD dispatch compatibility across CPUs: runtime CPU-feature detection (ADR-07) means the same binary runs correctly (via scalar fallback) on hardware lacking AVX2/NEON — this is a portability guarantee, not merely a performance one; a regression here (a crash on non-AVX2 hardware rather than a graceful fallback) is a compatibility break, not just a performance one.

Error-code stability: ErrorCode enumerator values, once released, are never reassigned to a different meaning; new codes are appended, never inserted in the middle of the existing sequence, to avoid consumer code that matches on integer value (discouraged, but not preventable) silently misinterpreting a stable-looking numeric match after a reordering.

DOM layout as an internal detail: consumers must not depend on Value's bit layout, ArenaBlock size, or any other §8.7/§8.8 internal representation detail directly — these are explicitly non-contractual and may change in any release, including a patch release, without a version-bump obligation, precisely because they are documented here as internal.

Deprecation: a deprecated API element remains functional for at least one full minor-version cycle with a compiler-visible deprecation annotation before removal in the next major version.

SemVer: MAJOR.MINOR.PATCH; MAJOR for any breaking accept/reject-behavior or public-signature change; MINOR for additive, backward-compatible functionality (new ErrorCode, new ParseOptions field, new SIMD architecture support); PATCH for bug fixes that do not change any documented accept/reject boundary or public signature.

28. Testing & Verification Strategy

Unit testing covers each module in isolation (tokenizer state transitions, arena allocation bookkeeping, number conversion decision-table branches, escaping-table lookups) against the signatures in §11.

Integration testing covers full parse→DOM and full parse→SAX flows against representative documents, and the serializer against a variety of Value tree shapes.

Property testing (tied to specific invariants): parse→serialize→parse is idempotent and value-equal for any successfully-parsed document (ties to I7, verified in Phase 7, §19); every finite double round-trips bit-identically, checked over millions of random bit patterns in addition to the curated 4M-case corpus (ties to I4, Phases 5–6, §17–§18); the SIMD and scalar scanners agree byte-for-byte on random and adversarial input (ties to I5, Phase 10, §22); any prefix of a valid document either parses successfully or errors cleanly but never crashes (ties to I1/I7, exercised via the truncation fault-injection fixtures of Phase 9, §21.5).

Differential testing: against simdjson, RapidJSON, and nlohmann/json on the shared benchmark corpus (twitter.json, citm_catalog.json, canada.json), with any disagreement adjudicated against RFC 8259 directly (Phase 11, §23) rather than deferred to precedent from any one reference implementation.

The JSONTestSuite corpus is a named CI gate (.github/workflows/ci.yml, established in Phase 0 and never removed) with an explicit expected-verdict table for the i_* (implementation-defined) cases, completed in Phase 11 (§23.6). Every y_* case must be accepted, every n_* case must be rejected, and every i_* case's verdict must match the documented table exactly — a change in an i_* verdict requires an explicit table update and rationale, not a silent drift.

Fuzzing is a first-class phase deliverable (Phase 9, §21), not an afterthought: fuzz/parse_ target.cpp, fuzz/roundtrip_target.cpp, and fuzz/simd_scalar_diff_target.cpp, seeded from the JSONTestSuite plus accumulated conformance fixtures, run continuously under ASan/UBSan/MSan with a zero-crash and zero-sanitizer-finding gate blocking merge (ADR-27).

Chaos and fault injection: allocation failure simulated at every allocation site in sequence (I8); truncation simulated at every byte offset of a representative document set (I1/I7); both established in Phase 9 (§21.2 steps 7–8) and re-run on every release candidate.

Deterministic replay: every fuzz-discovered crash is captured as a minimized, permanently-retained input file added to the corpus, ensuring the exact failure is replayable and cannot silently regress again without CI catching it.

Soak testing: the continuous fuzz campaign (ADR-27) doubles as a soak test by running for extended durations (72-hour baseline established in Phase 9, ongoing indefinitely) rather than a fixed pre-release window.

Perf-regression gating: a dedicated benchmark CI job (.github/workflows/benchmark.yml, §29) compares every merge's throughput against the §30 M-series targets, gated with a documented tolerance band (regression beyond the band blocks merge pending review, per FM-9).

Reproducible builds: pinned toolchain versions in the CI matrix (ADR-28); CMakeLists.txt avoids non-deterministic build steps (no timestamp embedding, no unpinned dependency resolution — ADR-03 already eliminates the runtime-dependency case, but build-time tooling versions are pinned too).

Dependency auditing: even under the zero-runtime-dependency policy (ADR-03), build-time tooling (CMake, the CI runner images, the fuzzing harness libraries) is audited on a recurring schedule for known vulnerabilities, with findings tracked against the SBOM.

30. Performance Engineering

Methodology: cache locality is the primary lever for DOM construction (arena block size tuned to L2, §14.7); branch misprediction is the dominant scalar-path cost in the tokenizer and UTF-8 validator, motivating table-driven/branch-free designs over chained conditionals throughout; SIMD utilization is measured directly via the dispatch-path telemetry (§26) rather than inferred from aggregate throughput alone; allocation count is tracked per parse (I6, §14) since it correlates more reliably with latency tail behavior than raw byte throughput; memory bandwidth is treated as the eventual ceiling once SIMD compute is no longer the bottleneck (§31); tail latency (p95/p99, §4) is measured separately from mean throughput because slow-path number conversions (Phase 5) and rare deep-nesting inputs disproportionately affect the tail without moving the mean.

31. Scalability Analysis

What stays constant: nesting-depth ceiling is bounded by configuration (Limits::max_depth), not by input size — an attacker cannot grow depth beyond the configured limit regardless of document size. Number conversion cost is O(1) per number except on the documented ~0.5% slow path (Phase 5), independent of document size.

What grows, and its Big-O: parsing is linear in input bytes, O(n), for both the scalar and SIMD paths (SIMD reduces the constant factor, not the asymptotic class); DOM memory is linear in input bytes with a stated constant factor (the amplification figure from §4/§34, ≤5.0x for the small-object-heavy worst case); serialization is linear in output bytes, which is itself proportional to input structure size.

Named bottlenecks in order: (1) branch misprediction in the scalar tokenizer/validator, addressed by table-driven dispatch and by the SIMD fast path bypassing per-byte branching entirely; (2) allocation overhead, addressed by arena bump-allocation (P9); (3) once (1) and (2) are addressed, memory bandwidth becomes the wall — a SIMD scanner that is compute-bound relative to available memory bandwidth cannot exceed the bandwidth ceiling regardless of further vectorization, and the §4 throughput targets (2.0–4.0 GB/s) are set with this ceiling in mind rather than an unbounded aspiration.

Parallelism across documents: independent documents parse fully in parallel with no shared mutable state (I8's reentrancy guarantee), scaling linearly with core count for a batch-of-documents workload. Parallelism within a single document: a single document resists parallel parsing because the grammar is inherently sequential — the structural nesting of a single JSON value has no statically-known split points without first scanning the whole document (which is exactly what stage 1's structural scan already does cheaply and sequentially); attempting to parallelize a single document's parse would require redundant scanning work that likely costs more than it saves at the throughput levels already achieved by SIMD stage 1.

Practical document-size ceiling: bounded in DOM mode by the Limits::max_document_bytes default (~2 GiB) and by available memory at the stated ~5x amplification factor (a 2 GiB document requires up to ~10 GiB of DOM memory); the lever beyond this ceiling is streaming (Phase 8, §20), which processes documents of effectively unbounded size in bounded memory by never materializing a full DOM, or a future on-demand/lazy-parsing mode (§36) that parses only the subset of the document actually accessed by the caller.

32. Mental Models & First Principles

MM1 — A parser is a total function from bytes to either a value or a precise error. Insight: "undefined behavior on malformed input" is not a category that exists for this design. Predicts: every input, however malformed, must land in exactly one of {success, documented error}. Bug class without it: crashes and hangs on adversarial input (T1, T2, T4). Resolving §7 (I1, I7) and §24.

MM2 — JSON's grammar is trivial; its difficulty is entirely in numbers, Unicode, and adversarial input. Insight: the six-production EBNF in §8.1 fits on one page, yet this blueprint spends four full phases (5, 6, 4, 9) on exactly those three concerns. Predicts: a naive implementation looks complete after Phase 1 but is nowhere near production-ready. Bug class without it: shipping a "works on the happy path" parser mistaken for a finished one. Resolving §5 (papers on number/UTF-8 correctness) and §12–§23's phase arc.

MM3 — The SIMD fast path is an optimization that must be provably equivalent to the scalar path. Insight: speed is worthless if it's a different function; differential testing is not optional polish, it's the mechanism by which "faster" and "correct" are simultaneously true. Predicts: any SIMD change without a corresponding differential-fuzz run is unreviewable. Bug class without it: a CPU-feature-dependent correctness bug (FM-5). Resolving §22 (Phase 10) and I5.

MM4 — A number is a mathematical value with a textual representation, and the conversion between them is either exact or wrong — there is no acceptable "close enough." Insight: floating-point tolerance-based thinking, appropriate in numerical computing, is actively wrong for a parser whose job is preserving an exact value across a serialization boundary. Predicts: any number bug reports as "occasionally wrong in the 17th digit," not "wildly wrong," because near-misses are the signature of an incomplete rounding implementation. Bug class without it: silent data corruption in financial/scientific data (T7-adjacent, but really P3's core concern). Resolving §16–§17 (§16 in this doc's actual number is §17) and I4.

MM5 — Untrusted input means every resource consumed by parsing — stack, heap, CPU time — must be bounded before the input is trusted enough to drive that consumption. Insight: this reframes "parsing" as "parsing plus resource accounting," a dual concern from the first byte. Predicts: any missing Limits check is a potential denial-of-service vector, not merely an edge-case bug. Bug class without it: every row of §24's threat model. Resolving §7 (I2, I6, I9) and §21 (Phase 9).

MM6 — A borrowed view is a promise about a lifetime that the type system in C++ cannot fully enforce, so the design must make the promise's boundary as narrow and explicit as possible. Insight: zero-copy performance and memory safety are in genuine tension, resolved not by picking one but by making the tension's boundary a single, well-documented field (StringView.borrowed_from_input). Predicts: use-after-free bugs cluster at API boundaries where a caller controls buffer lifetime independently of Document lifetime. Bug class without it: T8. Resolving §11 and P5.

MM7 — Streaming and DOM construction are two different answers to "how much of the document must exist in memory at once," and the right answer depends on what the caller does with the result, not on which is objectively better. Insight: DOM mode trades memory for random-access ergonomics; SAX/streaming mode trades ergonomics for constant memory — neither dominates. Predicts: a caller doing a single sequential pass over a huge log file should never reach for DOM mode. Bug class without it: unnecessary memory pressure from defaulting to DOM mode regardless of access pattern. Resolving §33 and §36.

MM8 — The conformance corpus is not a test suite in the ordinary sense; it is the operational definition of "correct" for every ambiguous case the specification leaves open. Insight: for the i_* category specifically, there is no ground truth outside the project's own documented choice — the corpus is the spec, extended. Predicts: disputes about "is this a bug" for an i_* case resolve by checking the documented verdict table, not by re-arguing from RFC 8259 text that is silent on the point by definition. Bug class without it: endless re-litigation of settled implementation-defined behavior. Resolving §12, §23, §28.

simdjson's decision that wins here: the two-stage structural-scan/tape design decouples "find the structure" from "interpret the structure," which is exactly why this blueprint's SIMD phase (Phase 10, §22) can be developed and differentially tested independently of the number/string correctness work in Phases 3–6 — the two-stage split is a genuine architectural insight, not merely an implementation detail, and it wins whenever throughput at the multi-GB/s level matters more than API simplicity.

RapidJSON's decision and where it wins: in-situ parsing (mutating the input buffer to null- terminate strings in place) avoids a second allocation for unescaped string storage entirely — it wins decisively when the caller already owns a mutable scratch buffer and doesn't need the input preserved, a common pattern in performance-sensitive C++ services parsing a request body they control end-to-end; this blueprint rejects it (ADR-08) because the read-only Input Adapter boundary and the streaming/mmap use case both require the input to remain untouched.

nlohmann/json's decision and where it wins: ergonomics-first design with implicit conversions (value["key"].get<int>()-style access) wins decisively for application code where developer velocity matters more than the last factor of throughput — it is, by a wide margin, the most widely adopted C++ JSON library specifically because of this tradeoff, and it is the correct choice for a huge fraction of real-world C++ JSON consumption that never touches gigabyte-scale documents.

yyjson's decision and where it wins: offering both a mutable and an immutable DOM as genuinely distinct types (not one type with a mutability flag) lets the immutable path skip synchronization and copy-on-write bookkeeping entirely — it wins whenever a workload is read-dominated, which informed this blueprint's own immutable-by-default choice (ADR-20) even though this blueprint does not go as far as offering two distinct root types.

serde_json's decision and where it wins: binding deserialization directly to a target Rust struct via the serde::Deserialize trait, skipping the generic-Value intermediate representation entirely for known-schema workloads, wins decisively on throughput and memory for exactly the workload class where the schema is known at compile time — this is the "code-generated parser" alternative architecture explored and rejected for this blueprint's general-purpose goals in §36, but it is the right choice whenever the caller controls both ends of the schema.

34. Back-of-Envelope Capacity Model

DOM memory amplification (small-object-heavy document). Assume citm_catalog.json-class input with an average of one Value node per ~10 input bytes (typical for deeply-nested small-object JSON) and a 16-byte Value plus ~8 bytes of average indirect-payload overhead (arena block metadata amortized) per node: amplification = (nodes × 24 bytes) ÷ (nodes × 10 input bytes) = 24 ÷ 10 ≈ 2.4x for node storage alone; adding arena-block internal fragmentation (typically 10–15% waste at 64 KiB block granularity against average node sizes) brings the practical figure to roughly 2.7–3.0x measured, well under the 5.0x ceiling in §4/M9, leaving margin for less favorable document shapes.

Parse time from throughput, named sizes. At the M1 target of 2.0–4.0 GB/s SIMD throughput: a 64 KiB document takes 64 KiB ÷ 3 GB/s (midpoint) ≈ 21 µs of pure scan/parse time (consistent with the ≤45 µs p50 latency target M6, which includes fixed per-call overhead beyond pure throughput); a 1 MB document takes 1 MB ÷ 3 GB/s ≈ 333 µs; a 1 GB document takes 1 GB ÷ 3 GB/s ≈ 333 ms.

Stack frames at the depth limit (recursive path). Assume a recursive-descent stack frame of roughly 96 bytes (a handful of local pointers/counters, saved registers, per Stroustrup ch. 8's typical frame-layout discussion): at the default depth limit of 512 (§4), total stack consumption is 512 × 96 bytes ≈ 49 KiB — comfortably within a typical 1 MB thread default stack, but close enough to a constrained 64 KiB embedded/CI thread stack (§13.9's ASan-redzone-inflated scenario) that the depth-32 switchover to the iterative path (ADR-05) provides real margin rather than theoretical margin; this arithmetic is exactly why the depth limit default is 512 and not, say, 100,000 — it is derived from the frame-byte budget, not chosen arbitrarily.

Arena block count and waste. For a document with 1,000,000 nodes at ~24 bytes/node (per the amplification derivation above) = 24 MB of node storage; at 64 KiB per block, that requires 24 MB ÷ 64 KiB ≈ 375 blocks; average per-block waste from the bump pointer not landing exactly at capacity is bounded by (block_size − 1) in the worst single-block case, so total waste across 375 blocks is at most 375 × 64 KiB worst-case but averages roughly half that (≈12 MB) in the typical case — informing the §14.7 tuning note that block size must be re-benchmarked, not merely re-derived analytically, against real corpora.

SIMD speedup ceiling. AVX2 processes 32 bytes per vector; assume a scalar path processes roughly 1 byte per cycle for the branchy comparison-heavy structural scan (a conservative estimate consistent with branch-misprediction being the dominant scalar cost, §30): speedup ceiling ≈ 32 bytes/vector ÷ 1 byte/cycle-scalar-equivalent = 32x in the best case for the scan stage alone; the documented 6–8x scalar-fallback penalty (§4) rather than the full 32x reflects that structural scanning is only one stage of the whole parse (tokenization, value building, and number conversion remain scalar-cost-dominated even when stage 1 is vectorized), diluting the end-to-end speedup from the theoretical per-stage ceiling.

Slow-path number-conversion cost on a numeric-heavy document. Assume canada.json-class input (number-dominated) with 100,000 numeric literals and the documented ~0.5% Eisel-Lemire slow-path rate (Lemire 2021): 500 numbers take the big-integer slow path; if the slow path costs roughly 50x the fast path's per-number cost (a representative order-of-magnitude figure for arbitrary-precision decimal-to-binary conversion versus a 128-bit-multiply fast path), the slow path's total cost is 500 × 50 = 25,000 "fast-path-equivalent" units against a baseline of 100,000 fast-path-cost units for all numbers — a roughly 25% throughput tax from the slow path alone on this adversarially- numeric corpus, which is why numbers.slow_path_conversions (§26) is worth monitoring as a throughput-relevant metric, not merely a correctness curiosity.

Memory bandwidth as the throughput ceiling. Assume a single parse pass touches each input byte roughly 2–3 times (structural scan, tokenization/value-building, and string/number materialization each read overlapping but not identical byte ranges) on a system with, say, 20 GB/s of available single-core memory bandwidth: bandwidth-bound throughput ceiling ≈ 20 GB/s ÷ 2.5 passes = 8 GB/s — comfortably above the M1 target (2.0–4.0 GB/s), confirming that at the currently-targeted throughput level, compute (not bandwidth) is still the binding constraint, and there is headway before bandwidth becomes the wall as SIMD efficiency improves further.

Adversarial worst case (deepest nesting × per-level cost). At the default depth limit of 512 and an iterative-path per-level cost of roughly 64 bytes of explicit-stack-frame allocation (a (kind, sub_state) pair plus alignment, smaller than the native recursive frame per the ADR-05 hybrid design): worst-case adversarial depth-related heap consumption is 512 × 64 bytes = 32 KiB — negligible relative to the §4 memory ceiling, confirming that the depth limit's primary purpose is bounding stack consumption (native recursion path, below the depth-32 threshold) rather than heap consumption, which the iterative path handles cheaply regardless of depth up to the configured limit.

36. Alternative Architectures (Roads Not Taken)

On-demand / lazy parsing (simdjson's model). No DOM is ever built; the caller navigates the input directly, and each accessed field is parsed only when touched, using the structural index from stage 1 as a skip-list to jump over unaccessed substructures.

  input bytes --> structural index (stage 1, eager) --> caller navigates directly
                                                          |
                                              [.] field access triggers
                                              [.] just-in-time parse of
                                              [.] only that value's bytes

Winning regime: selective-field extraction from huge documents where most fields are never touched — e.g., reading one field from a 100 MB log-record array without materializing the other 99% of records. Real embodying system: simdjson's on-demand API. Why rejected here as the default: the borrowed-lifetime constraints it imposes on the caller (every accessed value remains tied to the input buffer and to the specific navigation order) are a usability and safety tradeoff this blueprint's DOM-mode default explicitly avoids (P5, ADR-04) — offered instead as a documented future extension point, not built in Phase 0–11.

Pure streaming SAX-only design, no DOM at all. The library never offers a Value tree; only the push/pull event interfaces of Phase 8 exist, and all structure-holding responsibility is pushed to the caller.

  input bytes --> tokenizer/parser core --> SaxHandler callbacks only
                                             (caller builds any structure
                                              it needs, or none at all)

Winning regime: constant-memory, single-pass consumers (log processors, streaming ETL) that never need random access into the parsed structure. Real embodying system: many streaming XML/JSON parsers in resource-constrained embedded contexts follow this shape exclusively. Why rejected as the sole API here: a large fraction of real-world JSON consumption (configuration files, API response bodies under a few megabytes) genuinely benefits from random-access DOM ergonomics, and this blueprint's shared-tokenizer-core design (ADR-19) means offering both costs little beyond the SAX-only design's own implementation effort.

Code-generated, schema-bound parser (serde/protobuf model). The parser and its target data structure are generated together from a schema at compile time; there is no generic Value type at all, and the parser only accepts documents matching the compiled-in shape.

  schema (compile time) --> generated parse function --> caller's native struct
                                                            (no Value, no DOM,
                                                             no runtime dispatch)

Winning regime: any workload where the schema is known and stable at compile time — this is the fastest possible design because it eliminates the tagged-union dispatch, the arena, and the generic-value overhead entirely, replacing them with direct field assignment. Real embodying system: serde_json paired with #[derive(Deserialize)], and Protocol Buffers generally. Why rejected here: this blueprint's stated goal is a general-purpose JSON parser for arbitrary, not-necessarily-schema-known documents (§1) — a schema-bound generator is a different product with a different scope, not a variant of this one.

Table-driven or parser-combinator implementation. The grammar of §8.1 is expressed as a table of parser-combinator primitives (seq, alt, many) composed declaratively, rather than as hand-written recursive-descent functions.

  value_parser = alt(object_parser, array_parser, string_parser,
                      number_parser, literal_parser)
  object_parser = seq('{', opt(member_list), '}')

Winning regime: contexts where grammar clarity and provable correctness against the EBNF matter more than raw throughput — a combinator-based parser's structure maps almost line-for-line onto the grammar, making it easy to audit for spec fidelity (directly serving P1). Real embodying system: parser-combinator libraries common in Haskell (Parsec-style) and increasingly in Rust (nom). Why rejected here: the combinator abstraction's typical runtime cost (indirect calls, allocation for intermediate combinator results) works against the §4 multi-GB/s throughput target that recursive descent plus a hand-tuned SIMD fast path can hit directly; this blueprint favors provable equivalence via differential testing (P4) over provable-by-construction combinator structure as the path to the same trust outcome.

38. Glossary

Tokenizer — the component converting a raw byte stream into a sequence of Tokens per the state-transition table (§8.2). Lexeme — the substring of input text corresponding to one token. Recursive descent — a parsing technique with one function per grammar non-terminal, directly mirroring the EBNF (§8.1, §13). Structural character — one of the six RFC 8259 characters { } [ ] : , that delimit JSON structure. Structural index — the flat array of byte offsets of every structural character in a document, produced by stage 1 of the SIMD scanner (§8.6). Two-stage parsing — the simdjson-style division of parsing into a structure-finding stage (stage 1) and a value-interpreting stage (stage 2). On-demand parsing — a parsing mode that defers interpreting a value's bytes until the caller actually accesses that value (§36). DOM — Document Object Model; here, the fully-materialized Value tree representing a parsed document. SAX — Simple API for XML, borrowed terminology for JSON's analogous push-based event interface (§8.9, §11). Tagged union — a data structure (ValueUnion, §8.7) that stores one of several possible types alongside a discriminant tag identifying which. Arena allocator — a bump-pointer allocator serving fixed-size blocks for the lifetime of one Document (§8.8). Zero-copy view — a StringView that borrows directly from the input buffer rather than copying (P5). Lazy unescaping — deferring the decoding of escape sequences until a string value is actually materialized or accessed. Surrogate pair — two UTF-16 code units (a high surrogate in [0xD800, 0xDBFF] and a low surrogate in [0xDC00, 0xDFFF]) jointly encoding one astral-plane code point (§8.3). Astral plane — Unicode code points above U+FFFF, requiring a surrogate pair when represented via \u escapes. Lone surrogate — a surrogate code unit with no matching pair partner; invalid per this blueprint's strict UTF-8/escape handling (I3). Overlong encoding — a UTF-8 byte sequence that encodes a code point using more bytes than the shortest valid encoding, forbidden by RFC 3629 (§8.4). Well-formed UTF-8 — a byte sequence conforming to the Unicode Standard's conformance chapter C10, excluding overlong encodings, surrogate-range encodings, and out-of-range code points. Round-trip exactness — the property that parse→serialize→parse of a number produces a bit-identical result to the original parse (I4). Shortest round-tripping representation — the decimal string, among all strings that round-trip to a given double, with the fewest digits (Steele & White 1990). Grisu — Loitsch's 2010 fast float-to-string algorithm with a documented (rare) fallback requirement. Ryū — Adams's 2018 fast float-to-string algorithm with no documented fallback requirement, locked by ADR-14. Eisel-Lemire — Lemire's 2021 fast string-to-float parsing algorithm with a documented ~0.5% fallback rate to a slow path. Slow path — the correctly-rounded but computationally expensive fallback conversion path engaged when a fast-path algorithm's precision guarantee is insufficient. Big-integer fallback — the arbitrary-precision decimal-to-binary conversion (Gay 1990) used as the number-parsing slow path. Subnormal — an IEEE 754 floating-point value smaller in magnitude than the smallest normal value, represented with reduced precision. Negative zero — the IEEE 754 value -0.0, numerically equal to 0.0 but distinct in sign bit and required to round-trip distinctly (§8.5, §17, §18). Depth limit — the configured maximum nesting level (Limits::max_depth) a document may reach before rejection (I2). Stack exhaustion — a crash caused by recursion (or other stack growth) exceeding the available thread stack size; the primary risk mitigated by the depth limit and the iterative deep-path parser (T1). Parser differential — a discrepancy in accept/reject or interpretation behavior between two implementations processing the same input, exploitable when a pipeline includes more than one parser (T6). JSON Pointer — the RFC 6901 syntax for referencing a specific value within a JSON document by path (§8.11). JSON Patch — the RFC 6902 syntax for describing a sequence of mutations to apply to a JSON document (§8.11). JSON Merge Patch — the RFC 7396 alternative patch format expressing a patch as a partial document to be merged, deferred in this blueprint (§37). Sanitizer — a compile-time instrumentation tool (ASan, UBSan, MSan) detecting memory-safety, undefined-behavior, or uninitialized-memory errors at runtime. Fuzz corpus — the persisted set of inputs used to seed and grow coverage-guided fuzzing (§21, §28). Differential testing — comparing this implementation's behavior against independent reference implementations to surface disagreements for adjudication (§28, §33). Property testing — testing that asserts a general invariant (e.g., round-trip identity) holds across a large, often randomly generated, input space rather than checking specific example cases. Arena block — one fixed-size (64 KiB default) chunk of memory within an Arena's block chain (§8.8). Bump allocation — allocating by advancing a single offset pointer within a pre-reserved block, with no per-allocation bookkeeping. Short string optimization — inlining strings below a length threshold (7 bytes, ADR-10) directly into the ValueUnion payload, avoiding arena indirection. Prefix-XOR scan — the SIMD technique used to compute "inside string" regions from a quote bitmask by propagating parity across bit positions (§8.6 stage 4). Backslash-run parity — the computation determining whether a quote character is escaped, based on the parity (odd/even) of the immediately preceding run of backslash bytes (§8.6 stage 3). CPU-feature dispatch — selecting among multiple implementations (e.g., AVX2 versus scalar) at runtime based on detected CPU capabilities (ADR-07). i_ case — a JSONTestSuite fixture whose correct verdict is implementation-defined by RFC 8259, requiring this blueprint to document and test its own chosen behavior (§12, §23, §28). Adversarial input — input specifically crafted to exploit a parser's resource-consumption or correctness weaknesses rather than to represent legitimate data (§24).
