34. Back-of-Envelope Capacity Model

DOM memory amplification (small-object-heavy document). Assume citm_catalog.json-class input with an average of one Value node per ~10 input bytes (typical for deeply-nested small-object JSON) and a 16-byte Value plus ~8 bytes of average indirect-payload overhead (arena block metadata amortized) per node: amplification = (nodes × 24 bytes) ÷ (nodes × 10 input bytes) = 24 ÷ 10 ≈ 2.4x for node storage alone; adding arena-block internal fragmentation (typically 10–15% waste at 64 KiB block granularity against average node sizes) brings the practical figure to roughly 2.7–3.0x measured, well under the 5.0x ceiling in §4/M9, leaving margin for less favorable document shapes.

Parse time from throughput, named sizes. At the M1 target of 2.0–4.0 GB/s SIMD throughput: a 64 KiB document takes 64 KiB ÷ 3 GB/s (midpoint) ≈ 21 µs of pure scan/parse time (consistent with the ≤45 µs p50 latency target M6, which includes fixed per-call overhead beyond pure throughput); a 1 MB document takes 1 MB ÷ 3 GB/s ≈ 333 µs; a 1 GB document takes 1 GB ÷ 3 GB/s ≈ 333 ms.

Stack frames at the depth limit (recursive path). Assume a recursive-descent stack frame of roughly 96 bytes (a handful of local pointers/counters, saved registers, per Stroustrup ch. 8's typical frame-layout discussion): at the default depth limit of 512 (§4), total stack consumption is 512 × 96 bytes ≈ 49 KiB — comfortably within a typical 1 MB thread default stack, but close enough to a constrained 64 KiB embedded/CI thread stack (§13.9's ASan-redzone-inflated scenario) that the depth-32 switchover to the iterative path (ADR-05) provides real margin rather than theoretical margin; this arithmetic is exactly why the depth limit default is 512 and not, say, 100,000 — it is derived from the frame-byte budget, not chosen arbitrarily.

Arena block count and waste. For a document with 1,000,000 nodes at ~24 bytes/node (per the amplification derivation above) = 24 MB of node storage; at 64 KiB per block, that requires 24 MB ÷ 64 KiB ≈ 375 blocks; average per-block waste from the bump pointer not landing exactly at capacity is bounded by (block_size − 1) in the worst single-block case, so total waste across 375 blocks is at most 375 × 64 KiB worst-case but averages roughly half that (≈12 MB) in the typical case — informing the §14.7 tuning note that block size must be re-benchmarked, not merely re-derived analytically, against real corpora.

SIMD speedup ceiling. AVX2 processes 32 bytes per vector; assume a scalar path processes roughly 1 byte per cycle for the branchy comparison-heavy structural scan (a conservative estimate consistent with branch-misprediction being the dominant scalar cost, §30): speedup ceiling ≈ 32 bytes/vector ÷ 1 byte/cycle-scalar-equivalent = 32x in the best case for the scan stage alone; the documented 6–8x scalar-fallback penalty (§4) rather than the full 32x reflects that structural scanning is only one stage of the whole parse (tokenization, value building, and number conversion remain scalar-cost-dominated even when stage 1 is vectorized), diluting the end-to-end speedup from the theoretical per-stage ceiling.

Slow-path number-conversion cost on a numeric-heavy document. Assume canada.json-class input (number-dominated) with 100,000 numeric literals and the documented ~0.5% Eisel-Lemire slow-path rate (Lemire 2021): 500 numbers take the big-integer slow path; if the slow path costs roughly 50x the fast path's per-number cost (a representative order-of-magnitude figure for arbitrary-precision decimal-to-binary conversion versus a 128-bit-multiply fast path), the slow path's total cost is 500 × 50 = 25,000 "fast-path-equivalent" units against a baseline of 100,000 fast-path-cost units for all numbers — a roughly 25% throughput tax from the slow path alone on this adversarially- numeric corpus, which is why numbers.slow_path_conversions (§26) is worth monitoring as a throughput-relevant metric, not merely a correctness curiosity.

Memory bandwidth as the throughput ceiling. Assume a single parse pass touches each input byte roughly 2–3 times (structural scan, tokenization/value-building, and string/number materialization each read overlapping but not identical byte ranges) on a system with, say, 20 GB/s of available single-core memory bandwidth: bandwidth-bound throughput ceiling ≈ 20 GB/s ÷ 2.5 passes = 8 GB/s — comfortably above the M1 target (2.0–4.0 GB/s), confirming that at the currently-targeted throughput level, compute (not bandwidth) is still the binding constraint, and there is headway before bandwidth becomes the wall as SIMD efficiency improves further.

Adversarial worst case (deepest nesting × per-level cost). At the default depth limit of 512 and an iterative-path per-level cost of roughly 64 bytes of explicit-stack-frame allocation (a (kind, sub_state) pair plus alignment, smaller than the native recursive frame per the ADR-05 hybrid design): worst-case adversarial depth-related heap consumption is 512 × 64 bytes = 32 KiB — negligible relative to the §4 memory ceiling, confirming that the depth limit's primary purpose is bounding stack consumption (native recursion path, below the depth-32 threshold) rather than heap consumption, which the iterative path handles cheaply regardless of depth up to the configured limit.
