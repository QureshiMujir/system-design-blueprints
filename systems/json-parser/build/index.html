⬜ Phase 0 — Skeleton, Scalar Tokenizer, CI, JSONTestSuite Harness §12

Objectives

Establish the repository skeleton (§10), vendor the JSONTestSuite corpus (conformance/jsontestsuite/), implement the scalar Tokenizer against the state-transition table of §8.2, and wire CI (.github/workflows/ci.yml) to run the tokenizer against the full corpus at the tokenization level before any parser exists. This phase exists to make P1 ("the specification is the authority and the conformance corpus is the judge") operational from day one rather than aspirational.

Deliverable

A scalar Tokenizer (include/jsonp/tokenizer.hpp) that classifies every JSONTestSuite fixture correctly at the token level, plus a CI job that fails on regression.

Acceptance

Tokenizer-level verdict matches expected verdict for 100% of y_* (accept) and n_* (reject) JSONTestSuite fixtures (348 files in the vendored corpus); every i_* fixture (implementation- defined) has a documented, tested verdict in the harness table; CI job ci.yml is green on a clean checkout; zero crashes when the tokenizer runs over all n_* fixtures under ASan.

Fixtures

conformance/jsontestsuite/y_string_unicode_2.json — validates 4-byte UTF-8 tokenization without erroring, purpose: BMP+astral boundary. n_number_leading_zero.json — must be rejected at the InNumber state per §8.2. n_structure_trailing_comma.json — must be rejected. i_number_huge_exp.json — documented verdict: accept token, defer exact conversion to Phase 5.

Pitfalls
  • Treating \u as always producing exactly one output character — surrogate pairs require two input escapes combined into one; a naive implementation double-counts or drops the combining step. Manifestation: astral-plane characters corrupt on tokenization. Debug: single-step the InUnicodeEscape/PendingSurrogate transition on the astral-plane fixture from §8.3.
  • Off-by-one in whitespace class checks: including 0x0B (vertical tab) or 0x0C (form feed) as whitespace, which RFC 8259 section 2 explicitly excludes. Manifestation: n_* whitespace fixtures wrongly accepted. Debug: diff the whitespace bitmask against the exact four-character set.
  • Number-length limit checked after building the full span instead of during the scan (violates P12). Manifestation: a 10 MB digit string still gets fully scanned before rejection, defeating the CPU-bound protection intent. Debug: instrument the scan loop with a counter assertion.
  • Vendoring JSONTestSuite without pinning a commit — corpus drift silently changes what "100% pass" means between CI runs. Signal: green CI on an unrelated PR suddenly turns red.

⬜ Phase 1 — Recursive-Descent Parser and DOM §13

Objectives

Build the first working Value-producing parser: recursive descent over the grammar in §8.1, consuming tokens from Phase 0's Tokenizer, enforcing the depth limit (I2, P8) before every recursive descent, and constructing a minimal (not yet arena-backed — that lands in Phase 2) Value tree. This phase makes P7 ("a rejected document is never a partially-populated DOM") operational for the first time.

Deliverable

A recursive-descent Parser producing a Value tree (temporarily heap-allocated per node; arena integration is Phase 2's job) for every well-formed document, and a precise ParseError for every malformed one, passing the full JSONTestSuite at the DOM level.

Acceptance

100% pass rate on JSONTestSuite y_*/n_* at DOM level (348/348); every i_* case's verdict matches the Phase 0 documented table; depth-limit fixture (10000_nested_arrays.json, scaled down to the default limit of 512 plus one) rejects with ErrorCode::DepthLimitExceeded and never crashes under ASan with a 512 KiB thread stack; zero instances of a returned Value tree accompanying an Error result (I7) across the entire corpus.

Fixtures

conformance/jsontestsuite/y_structure_true_in_array.json — minimal array holding a literal, purpose: baseline non-terminal chaining. n_structure_object_with_trailing_garbage.json — purpose: TrailingData after a valid top-level value must be rejected. depth_513_nested_arrays.json (hand-built) — purpose: exactly one level past the default limit, expected DepthLimitExceeded at the offset of the 513th [.

Pitfalls
  • Checking the depth limit inside the callee after already recursing one frame (violates P8/I9) — manifestation: the limit is effectively N+1, and under a sufficiently deep adversarial input the "N+1"th frame is still enough to exhaust a small thread stack. Debug: fuzz the exact boundary value and confirm the crash disappears only when the check precedes the call.
  • Returning a partially built Value alongside an error for caller convenience ("might as well give them what we have") — this directly violates P7/I7 and creates a foot-gun where an unchecked caller silently processes truncated data.
  • Recursive Value destruction on a deeply-nested but successfully parsed tree recursing to input depth on teardown (the nlohmann/json pitfall from §5's reference-implementation lesson) — even though the parse succeeded within the depth limit, destructor recursion at the same depth can still be an issue if the limit is set near the stack's actual ceiling; iterative teardown is the fix.
  • Off-by-one in "value then trailing data" detection — accepting 1 2 as two top-level values concatenated instead of rejecting the second 2 as trailing data.

⬜ Phase 2 — Arena Allocator and Value Representation §14

Objectives

Replace Phase 1's per-node heap allocation with the arena model of §8.8, implement the tagged-union ValueUnion bit layout of §8.7, and make Document the owning unit of both the arena and the root Value. This phase makes P9 ("allocation is arena-scoped, not per-node") and ADR-11 operational, and is the first point at which §4's memory-ceiling constraint (5x input size) is measurable.

Deliverable

An arena-backed Value/Document implementation where every DOM node's storage traces to exactly one Arena owned by exactly one Document, with Document destruction or reset() freeing all associated memory in O(blocks) time.

Acceptance

sizeof(Value) == 16 (static_assert enforced); memory high-water mark on citm_catalog.json is ≤5.0x the input byte count (§4); Arena::reset() on a partially-built tree from an injected mid-parse failure (fault-injection fixture, §28) leaves zero live allocations, verified under ASan leak detection; JSONTestSuite pass rate remains 100% (no regression from Phase 1).

Fixtures

benchmarks/corpus/citm_catalog.json — purpose: DOM amplification measurement (small-object-heavy document, the worst case for per-node overhead). fault_injection/alloc_fail_at_node_1000.json — purpose: synthetic allocation-failure injection at a specific arena request count, expected ErrorCode::OutOfMemory and zero leaked blocks. short_string_boundary.json — a string of exactly 7 and exactly 8 bytes, purpose: verify the ShortString inline/indirect boundary in ADR-10.

Pitfalls
  • Forgetting alignment when computing the inline/indirect split in ValueUnion, causing misaligned reads on architectures that fault on unaligned access (not x86, but ARM in strict mode). Manifestation: crash only on an ARM CI runner. Debug: run the ARM matrix leg of CI (ADR-28) and inspect the faulting instruction's operand alignment.
  • Treating Arena::reset() as safe to call while any StringView from a prior parse still borrows arena memory (violates P5's lifetime obligation extended to arena-owned, not just input-owned, storage). Manifestation: use-after-free detected only under ASan, not in a debug build without sanitizers.
  • Off-by-one in the ShortString length boundary — using < 8 instead of <= 7, silently shifting which strings get inlined and breaking a length-based test fixture.
  • Assuming a single oversized allocation (e.g., a 200 MiB string) can safely coexist with normal 64 KiB blocks in the same free-list bucket — oversized blocks need their own path (step 2) or fragmentation telemetry becomes meaningless.

⬜ Phase 3 — String Parsing, Escapes, and Surrogate Pairs §15

Objectives

Implement the Unescaper (§11) that turns a raw string span (as tokenized in Phase 0) into either a zero-copy StringView (no escapes present) or an arena-materialized unescaped string, correctly combining surrogate pairs per the §8.3 formula. This phase makes P5 ("zero-copy is a borrow, and every borrow has a documented lifetime") and the astral-plane worked example in §8.3 concrete.

Deliverable

A Unescaper producing correct UTF-8 bytes for every valid escape sequence including surrogate pairs, rejecting every lone-surrogate and invalid-escape case in JSONTestSuite, with zero-copy passthrough for escape-free strings.

Acceptance

100% pass rate on JSONTestSuite y_string_*/n_string_* subset; the astral-plane worked example (U+1F600) produces exactly F0 9F 98 80; every lone-surrogate fixture rejects with ErrorCode::LoneSurrogate at the correct byte offset (P6); zero-copy path verified by an instrumented test asserting no arena allocation occurs for an escape-free string fixture.

Fixtures

conformance/jsontestsuite/y_string_unicode_escaped_double_quote.json — purpose: \" inside a \u-escaped context doesn't confuse the state machine. n_string_invalid_utf-8_in_escape.json — purpose: malformed escape rejected. astral_plane_grinning_face.json (hand-built) — purpose: the §8.3 worked example, expected output bytes F0 9F 98 80. lone_high_surrogate_eof.json — purpose: \uD800 at end of string with no following low surrogate, expected ErrorCode::LoneSurrogate.

Pitfalls
  • Decoding \uXXXX as always producing exactly one output code point, forgetting the surrogate- pair combining step entirely — astral-plane characters silently corrupt into two separate BMP replacement characters instead of one combined code point.
  • Accepting a low surrogate not preceded by a high surrogate ("lenient mode leakage") — this must be a hard reject in strict mode (I3), not a permissive default, because it enables T5 (parser-differential attacks via lone surrogates reaching a downstream system that assumes well-formedness).
  • Computing the zero-copy-eligibility flag (step 1) based on the original input span but then accidentally pointing the resulting StringView at a stale or reused buffer after an arena reset — a lifetime-obligation violation (P5) distinct from the UTF-8 correctness issue.
  • Off-by-one in the surrogate combining arithmetic (e.g., using hi - 0xD7FF instead of hi - 0xD800) — produces a code point off by 1024, which will pass casual testing on ASCII-only corpora and only surface on real astral-plane input.

⬜ Phase 4 — UTF-8 Validation §16

Objectives

Implement the scalar Utf8Validator per the byte-range table in §8.4, independent of and prior to the SIMD variant (Phase 10), closing I3 ("every accepted string is well-formed UTF-8 with no lone surrogate") for the full input, not just the escape-decoded output of Phase 3. This phase makes P11 operational: string content is not trusted until proven well-formed.

Deliverable

A scalar Utf8Validator (include/jsonp/utf8.hpp) rejecting every overlong encoding, every surrogate-range encoding, and every out-of-range (>U+10FFFF) sequence, returning the byte offset of the first violation.

Acceptance

100% pass rate on JSONTestSuite's UTF-8-related fixtures (n_string_overlong_*, n_string_UTF-8_invalid_sequence*, n_string_unicode_CapitalU*); the §8.4 worked-reject byte sequences (E0 80 80, ED A0 80) both reject at offset 0; the §8.4 worked-accept sequence (E2 82 AC) accepts; UTF-8 validation throughput on well-formed ASCII-heavy input ≥1.5 GB/s (scalar target, §4) measured on twitter.json.

Fixtures

conformance/utf8_edge/overlong_null.json — bytes C0 80, purpose: 2-byte overlong encoding of U+0000, expected reject at offset of the sequence start. conformance/utf8_edge/surrogate_high.json — bytes ED A0 80, purpose: encodes U+D800, expected reject. conformance/utf8_edge/max_codepoint.json — bytes F4 8F BF BF (U+10FFFF), purpose: exactly at the ceiling, expected accept. conformance/utf8_edge/over_ceiling.json — bytes F4 90 80 80 (U+110000), purpose: one past the ceiling, expected reject.

Pitfalls
  • Using the general continuation-byte range (0x80–0xBF) for byte 2 of every multi-byte sequence instead of the tightened, length-and-leading-byte-specific ranges in §8.4 — this accepts overlong encodings and surrogate-range encodings that RFC 3629 forbids. Manifestation: n_string_overlong_* fixtures wrongly pass.
  • Validating only string content (post-Phase-3 unescape) and skipping validation of raw bytes outside strings — a malformed sequence in what looks like whitespace between tokens still violates "the whole document must be valid UTF-8" and must be caught.
  • Conflating "this byte sequence decodes to a valid code point" with "this byte sequence is the shortest encoding of that code point" — validity requires both; the overlong check is a distinct rule from the range check, easy to omit if only checking the final decoded value.
  • Off-by-one at the U+10FFFF ceiling — using 0x90 instead of 0x8F as the byte-2 upper bound for leading byte 0xF4, silently accepting one extra invalid code point.

⬜ Phase 5 — Exact Number Parsing with Slow-Path Fallback §17

Objectives

Implement NumberConverter per the §8.5 decision procedure: fast-path integer conversion, the Eisel-Lemire algorithm (Lemire 2021) for doubles, and a correctly-rounded big-integer slow-path fallback (Gay 1990) for the documented ~0.5% of inputs where Eisel-Lemire's fast path is insufficient. This phase makes P3 ("number conversion is exact or it is a data-corruption bug") operational — the load-bearing correctness concern of the entire blueprint.

Deliverable

A NumberConverter producing a bit-exact, correctly-rounded NumberValue for every finite double in the 4M-case parse-number-fxx-test-data corpus, with documented, tested behavior for -0, integer-overflow-to-double fallback, and huge-exponent rejection.

Acceptance

100% bit-exact match against parse-number-fxx-test-data (4,000,000 cases, zero mismatches); 9007199254740993 converts to 9007199254740992.0 (round-half-to-even, §8.5 worked example); 2.2250738585072014e-308 converts via the slow path to the correctly-rounded subnormal value; -0 preserves its sign bit through finalize; 1e400 rejects with ErrorCode::NumberOutOfRange by default; slow-path invocation rate on the corpus matches the ~0.5% figure documented by Lemire 2021 (used as a sanity check that the fast path is actually engaging, not silently always falling through).

Fixtures

conformance/float_roundtrip/fxx_test_data/ (vendored, 4M cases) — purpose: the primary correctness oracle for this phase. beyond_2_53.json (9007199254740993) — purpose: §8.5 worked example. subnormal_boundary.json (2.2250738585072014e-308) — purpose: slow-path forcing case. huge_exponent.json (1e400) — purpose: overflow-rejection default. negative_zero.json (-0) — purpose: sign-bit preservation.

Pitfalls
  • Treating Eisel-Lemire's fast path as always correct and never checking its documented failure signal — this silently produces incorrectly-rounded doubles for the ~0.5% of inputs at precision boundaries, a direct P3 violation that will not surface on casual testing (only on the 4M-case corpus or targeted adversarial construction).
  • Implementing integer overflow detection as "multiply first, then check if the result looks wrong" (post-hoc) instead of pre-checking bounds before the multiply — signed integer overflow is undefined behavior in C++ and UBSan will flag it, but only if the exact overflow-triggering input is exercised in a sanitized test run.
  • Normalizing -0 to 0 anywhere in the pipeline (a common "simplification") — breaks I4's round-trip-bit-identical invariant specifically for this one input class, easy to miss because -0 == 0 numerically and most equality-based tests won't catch the sign-bit difference.
  • Using strtod as a fallback "for simplicity" on any code path reachable from untrusted input — reintroduces locale-dependence (a decimal-comma locale silently misparses 3.14) that this entire phase exists to eliminate (ADR-12).

⬜ Phase 6 — Exact Number Serialization and Round-Trip Proof §18

Objectives

Implement double-to-string serialization using Ryū (Adams 2018, locked by ADR-14), producing the shortest string that round-trips back to the exact same double, and prove parse→serialize→parse identity over the same 4M-case corpus used in Phase 5. This phase closes I4 ("every finite double survives parse→serialize→parse bit-identically") end-to-end for the first time.

Deliverable

A Ryū-based number serializer producing the shortest round-tripping decimal representation for every finite double, with -0 and INT64_MIN handled correctly, verified bit-identical round-trip over the full 4M-case corpus.

Acceptance

Zero round-trip failures (I4) over parse-number-fxx-test-data (4,000,000 cases); -0 serializes to the exact text -0; INT64_MIN (-9223372036854775808) serializes correctly without integer overflow in the serialization routine itself; serialization throughput ≥1.5 GB/s compact mode on canada.json (§4).

Fixtures

(shared corpus with Phase 5) conformance/float_roundtrip/fxx_test_data/ — purpose: round-trip proof, now exercising both parse and serialize. int64_min.json — purpose: INT64_MIN boundary. shortest_repr_powers_of_two.json — purpose: values like 2.0^52 where naive serialization might emit more digits than necessary. negative_zero_serialize.json — purpose: -0 text-form check.

Pitfalls
  • Implementing -INT64_MIN anywhere in the integer-serialization path (to get a "positive magnitude to emit digits for") — this is itself undefined behavior in two's-complement arithmetic since INT64_MIN has no positive counterpart; must special-case the digit emission or widen to a 128-bit intermediate.
  • Assuming Ryū's shortest representation is unique across all correct implementations — different correct algorithms can produce different shortest strings if there's a tie in digit count; correctness is "round-trips exactly," not "matches a specific reference string" — differential tests against other libraries (§28) must compare round-trip behavior, not textual output.
  • Emitting 0 instead of -0 "because they're numerically equal" — this is the same P3/I4 violation as Phase 5's parsing-side pitfall, now on the write side; both must be fixed together or a round-trip test will still fail even if each half looks correct in isolation.
  • Choosing a fixed decimal-point threshold for scientific notation that sometimes produces a longer string than Ryū's natural output — defeats the "shortest" property even if round-trip correctness is preserved, regressing the serialize-throughput target via unnecessary bytes.

⬜ Phase 7 — Serializer with Escaping and Pretty-Printing §19

Objectives

Build the full Serializer combining Phase 6's number serialization with string escaping (§8.10) and structural formatting (compact and pretty modes), producing valid JSON text for any Value tree, with round-trip identity through re-parsing (extending I4's number-specific guarantee to the whole document).

Deliverable

A Serializer producing valid, escaped, optionally pretty-printed JSON text for any Value tree or equivalent streaming call sequence, verified round-trip-value-equal on twitter.json and citm_catalog.json.

Acceptance

Output validated by re-parsing with this library's own parser (self-consistency) and, per §28, cross-validated against at least one external validator; compact-mode throughput ≥1.5 GB/s and pretty-mode ≥0.8 GB/s on twitter.json (§4); zero unescaped " or \ bytes in any output sample across the corpus (mandatory-escape completeness check); EscapeMode::AsciiOnly output contains no byte ≥0x80.

Fixtures

benchmarks/corpus/twitter.json — purpose: general round-trip and throughput. escape_all_control_ chars.json — a string containing every byte 0x00–0x1F, purpose: mandatory-escape completeness. sort_keys_canonical.json — an object with keys in non-alphabetical insertion order, purpose: sort_keys option verification. pretty_print_nested.json — a 3-level-deep object/array mix, purpose: indent/newline placement correctness.

Pitfalls
  • Escaping / by default "to be safe" — RFC 8259 permits but does not require escaping the solidus; unnecessary escaping bloats output size and diverges from the ADR-18 escaping-table decision (§8.10 explicitly locks solidus as unescaped in both compact and pretty modes). Manifestation: output byte count regression against the §30 throughput-adjacent size targets.
  • Implementing AsciiOnly mode's astral-plane re-encoding without the inverse surrogate-pair split — emitting a single \uXXXXX (5 hex digits, invalid) instead of two \uXXXX\uXXXX surrogate halves for code points above U+FFFF.
  • Sorting keys by byte value when the intent was a locale-aware or code-point-aware sort — for canonicalization (ADR-17), the sort order itself must be specified precisely (byte-wise on the UTF-8 encoding is the locked choice) or two implementations claiming "sorted" will disagree, defeating the canonicalization purpose.
  • Recursive tree-walking in the serializer with no depth check — even though the DOM was built under a depth limit (I2), a future change that relaxes the limit or constructs a Value tree via DocumentBuilder without going through the parser could reintroduce unbounded depth on the write side; favor the iterative walk called out in step 1.

⬜ Phase 8 — Streaming / SAX Interface §20

Objectives

Build the constant-memory streaming path: the SaxHandler push interface and the pull-based SaxEvent iterator (§8.9, §11), both sharing the Phase 0 tokenizer core, enabling parsing of documents far larger than available memory with no DOM construction (ADR-19).

Deliverable

A SaxHandler-based push parser and a SaxEvent-based pull iterator, both operating in bounded memory independent of total document size, sharing one tokenizer/parser core with the DOM path.

Acceptance

Successfully streams a 10 GB synthetic document in bounded memory (peak RSS within a small constant multiple of chunk size plus Limits ceilings, not proportional to the 10 GB total, verified fixture streaming_10gb_synthetic.json); JSONTestSuite pass rate 100% when run through the streaming path (in addition to the existing DOM-path harness); zero incorrect resumption across 500 randomly chosen chunk-boundary split points on a fixed test document (differential check: streamed result equals DOM-parsed result of the same document).

Fixtures

streaming_10gb_synthetic.json (generated, not vendored) — purpose: constant-memory claim. chunk_boundary_mid_escape.json — purpose: partial-token buffering correctness, split at a \ byte. chunk_boundary_mid_surrogate.json — split between the two halves of a \uXXXX\uXXXX surrogate pair. chunk_boundary_mid_number.json — split in the middle of an exponent.

Pitfalls
  • Treating a chunk boundary landing mid-token as an error instead of a buffering opportunity — this defeats the entire purpose of streaming (any real large document will have tokens spanning arbitrary chunk boundaries).
  • Building the pull iterator as a thin wrapper that internally still buffers the whole document before yielding the first event — silently reintroduces the memory-proportional-to-document-size problem streaming exists to solve, undetectable without a memory-instrumented test (unit tests alone won't catch it on small documents).
  • Applying Limits checks only at chunk boundaries rather than continuously — an attacker could craft a single chunk that itself violates a limit (e.g., one 64 KiB chunk containing a 350-million-character number literal if max_number_digits weren't enforced character-by- character as specified in P12/Phase 0).
  • Divergent duplicate-key handling between the SAX path (which has no object to deduplicate into — it just emits Key events) and the DOM path (I10) — document explicitly that SAX callers are responsible for their own duplicate-key policy since there's no DOM object to apply ADR-16 to.

⬜ Phase 9 — Hardening: Depth/Size Limits, Iterative Deep Path, Fuzzing Campaign §21

Objectives

Close the stack-exhaustion risk left open by Phases 1–8's recursive-descent baseline by implementing the iterative deep-path parser (Grune & Jacobs ch. 8's explicit-stack technique, ADR-05), enforce every Limits field comprehensively across all entry points (DOM, SAX, streaming), and stand up the continuous fuzzing campaign (ADR-27) that is this section's primary deliverable alongside the code.

Deliverable

An iterative deep-path parser proven equivalent to recursive descent, comprehensive Limits enforcement across every entry point, and a continuously running, corpus-persisted fuzz campaign under ASan/UBSan/MSan with a zero-crash gate.

Acceptance

10,000-deep nesting input (default Limits::max_depth far exceeded) rejects cleanly via the iterative path with ErrorCode::DepthLimitExceeded, consuming heap-proportional-to-depth memory, not stack, and never crashing (verified under a constrained 64 KiB thread stack in CI); iterative and recursive parsers agree byte-for-byte on 100% of JSONTestSuite plus a 10,000-case random-nesting corpus; 72-hour continuous fuzz run (initial baseline, per ADR-27's ongoing-campaign model) produces zero crashes and zero sanitizer findings across all three fuzz targets; every fault- injection allocation-failure and truncation-offset test passes with a well-formed error, never UB.

Fixtures

depth_10000_nested_arrays.json — purpose: far-past-limit stack-exhaustion stress, expected clean reject. random_nesting_corpus/ (10,000 generated fixtures, varying depth and structure) — purpose: iterative/recursive differential equivalence. fuzz/corpus/ (persisted, growing) — purpose: continuous crash discovery. truncation_fixtures/ (one fixture per byte offset of a representative document set) — purpose: truncation fault-injection.

Pitfalls
  • Implementing the iterative parser's explicit stack with its own unbounded growth (no depth check on the explicit stack itself) — this merely moves the stack-exhaustion problem from the native call stack to the heap; the same Limits::max_depth check (I2, P8) must gate the explicit-stack push exactly as it gated native recursion.
  • Fuzzing only the DOM parse path and never the SAX/streaming paths — a crash reachable only through the streaming chunk-boundary logic (Phase 8) will never be found by a fuzz target that only calls the DOM entry point; multiple fuzz targets covering each entry point are necessary, not optional.
  • Treating a 24-hour clean fuzz run as sufficient evidence of hardening — fuzz campaigns are continuous by design (ADR-27) precisely because coverage accumulates over time; a short clean run is a baseline, not a completion criterion.
  • Fault-injecting allocation failure only at the "obvious" large-allocation sites and skipping small/inline-path allocation sites — an allocation-failure bug in a rarely-taken small-string arena path is just as much a crash risk as one in the main tree-construction path.

⬜ Phase 10 — SIMD Structural Scanning with Scalar-Differential Equivalence §22

Objectives

Implement SimdScanner per the §8.6 bitmask pipeline (simdjson-style stage 1: Langdale & Lemire 2019), covering AVX2 and NEON with runtime CPU-feature dispatch (ADR-07), and prove — not merely test — that it produces byte-identical structural indexes to the scalar tokenizer's implicit scanning (Phase 0) on every input, closing I5.

Deliverable

A SimdScanner (AVX2 primary, NEON port) selected via runtime CPU dispatch, proven byte-identical to the scalar scanner across a continuously running differential fuzz target, hitting the §4 DOM-throughput target on the simdjson benchmark corpus.

Acceptance

Zero mismatches between SIMD and scalar structural indexes across the full differential fuzz corpus (I5, simd.diff_mismatches metric permanently at zero — §7); DOM parse throughput ≥2.0 GB/s on twitter.json with SIMD engaged (§4); scalar-fallback throughput lands in the documented 300–500 MB/s band when SIMD is disabled, confirming the 6–8x penalty figure is accurate rather than aspirational; CPU-feature dispatch correctly selects AVX2 on a capable runner and falls back to scalar on a runner with AVX2 masked off (verified via a CI matrix leg, ADR-28).

Fixtures

benchmarks/corpus/twitter.json, citm_catalog.json, canada.json — purpose: throughput validation against §4/§30 targets. backslash_run_boundary.json (hand-built, a string with a backslash run straddling a 64-byte offset) — purpose: stage-3 carry-chain correctness. fuzz/corpus/ (shared with the differential target) — purpose: continuous SIMD/scalar equivalence proof.

Pitfalls
  • Failing to carry the backslash-run parity state across a 64-byte chunk boundary — a backslash run that happens to end exactly at a chunk boundary produces a different (wrong) escaped-quote determination than the same input scanned as one contiguous buffer; this is exactly the class of bug the boundary-straddling fixture in §22.5 exists to catch, and it will not show up on inputs shorter than 64 bytes.
  • Reading past the end of the input buffer when the final chunk is shorter than 64 bytes — the vectorized load must mask off or zero-pad the trailing partial chunk rather than reading adjacent (possibly unmapped) memory, a direct I1 violation reachable only on inputs whose length isn't a multiple of 64.
  • Assuming AVX2 availability implies BMI2 (pext) availability — some real-world CPUs have one without the other; the dispatch table (ADR-07) must probe both independently, not bundle them.
  • Treating a single passing run of the differential fuzzer as sufficient — like Phase 9's crash fuzzing, SIMD/scalar equivalence fuzzing is continuous; a coverage gap in the seed corpus can hide a boundary bug for a long time before a generated input happens to exercise it.

⬜ Phase 11 — JSON Pointer/Patch, Conformance Completion, Performance Hardening §23

Objectives

Implement JSON Pointer (RFC 6901) and JSON Patch (RFC 6902) as a layer operating purely on the completed Value tree (§8.11), bring JSONTestSuite conformance and the full §28 verification strategy to their final documented state, and close out remaining §30 performance-engineering targets — this is the terminal phase before the Phase 11 exit criteria referenced throughout this document are considered met.

Deliverable

A complete JSON Pointer/Patch implementation operating on the Value tree, a fully closed JSONTestSuite i_* verdict table, a completed differential-testing pass against three reference implementations, and a final performance-hardening pass against all §30 targets.

Acceptance

JSON Pointer resolves 100% of RFC 6901's own worked examples (section 5) correctly; JSON Patch passes 100% of this blueprint's fixture set including atomicity fixtures (a failing test op leaves the document completely unchanged); JSONTestSuite 100% pass rate maintained end-to-end (y_/n_/i_, all documented); differential testing against simdjson/RapidJSON/nlohmann shows zero unadjudicated disagreements (every disagreement traces to a specific RFC 8259 clause and a recorded resolution); all twelve-plus §30 M-series targets met or explicitly re-baselined with documented rationale.

Fixtures

rfc6901_worked_examples.json — the RFC's own section 5 example document and pointer set, purpose: canonical-example correctness. patch_atomicity_failing_test_op.json — a patch array where the third of five operations is a failing test, purpose: verify operations 1–2's effects are rolled back. differential/shared_corpus/ — the twitter.json/citm_catalog.json/canada.json set, purpose: cross-implementation adjudication.

Pitfalls
  • Implementing JSON Pointer resolution as if it could read and write with the same code path — the - array-index token is meaningful only for add/write contexts (append), not for read/resolve, and treating it as a valid read index will either crash or silently return the wrong element.
  • Applying patch operations directly to the live Document instead of a scratch builder, then discovering a later test operation fails — without the scratch-builder-then-commit discipline (step 4), the caller is left with a half-applied patch and no way to recover the pre-patch state, violating the patch-level analog of P7.
  • Treating a differential-testing disagreement against a reference implementation as automatically "our bug" or automatically "their bug" — RFC 8259 explicitly leaves some behavior implementation- defined (duplicate keys, for instance); the correct response is adjudication against the spec text, not deference to either implementation's precedent.
  • Declaring the phase complete when JSONTestSuite passes but skipping the re-run of §30's performance targets — a correctness-complete parser that silently regressed throughput somewhere in Phases 8–10's changes would not be caught without this explicit final re-measurement step.
