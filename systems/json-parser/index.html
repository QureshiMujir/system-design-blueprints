In one paragraph

A JSON parser turns a block of bytes into data a program can use, and refuses the block if it breaks the rules. This design is a from-scratch C++20 library (header-only, with an optional static library and a command-line validator) that treats every input as hostile. Its first test is a provable accept/reject boundary against the JSONTestSuite corpus, and its second is speed (§1). The design targets are 2.0-4.0 GB/s with SIMD and 300-500 MB/s on the plain scalar path (§4). It offers a tree mode, a streaming mode and a zero-copy string mode (§1). Application developers embed it, and operators run the validator to reject malformed payloads in ingestion pipelines (§1).

The problem, concretely

JSON looks trivial: the whole grammar fits on one page (§8.1, MM2). The difficulty is in numbers, Unicode and adversarial input (MM2), and a parser that looks finished after its first phase is "nowhere near production-ready" (MM2). Four concrete ways the naive version fails:

  • Nesting. An attacker sends [[[[[... thousands deep. A recursive-descent parser that does not bound depth crashes with stack exhaustion (T1, P2).
  • Duplicate keys. The standard leaves repeated object keys implementation-defined (§8.1). If a validator and an executor pick different winners for {"admin":false,"admin":true}, the attacker gets through (T6).
  • Numbers. 9007199254740993 is not exactly representable as a double (§8.5). The C library routine strtod is locale-dependent and not always correctly rounded (ADR-12). A literal such as 1e999999999 can force unbounded big-integer work (T7, P12).
  • Text. A \uD800 escape with no partner, or a raw overlong byte sequence, accepted by a lenient parser, flows on into a downstream system that assumes valid UTF-8 (T5, P11).

The design's answer is to treat parsing as "parsing plus resource accounting" (MM5): bound every resource before the input is trusted enough to consume it, make every verdict traceable to the RFC or to a named corpus case (P1), and make the fast path prove it agrees with the slow one (P4).

How it works, end to end

One document passes through these boxes (adapted from §3's diagram, which has more arrows):

 Input Adapter (owns or borrows the bytes; the only box allowed to do I/O)
      |
 SIMD Structural Scan (stage 1) ---> UTF-8 Validator (scalar + SIMD)
      |                                     |
 Tokenizer (scalar; uses the indices) <-----+
      |
 Parser (recursive descent, depth-limited) <--> iterative deep-path parser
      |
 Value Builder ---> Arena Allocator          SAX Event Emitter (instead of the builder)
      |                                      String Unescaper
 DOM Value Tree --> Number Converter
      |
 Serializer (escaper + pretty-printer)
 Limits Enforcer (cross-cuts every box)      JSON Pointer / Patch (Phase 11, on the tree)
  1. Input Adapter is the single entry point for untrusted bytes. It owns a buffer or borrows the caller's, and it is the only component allowed to do I/O (§3).
  2. SIMD Structural Scanner (SimdScanner, Phase 10) marks each byte as structure, whitespace or string interior using vector comparisons. It never interprets values (§3, §8.6).
  3. Utf8Validator checks byte well-formedness before any string content is trusted (§3, P11). It runs scalar or SIMD depending on dispatch (§3 says ADR-08; the dispatch decision is ADR-07, and the validator choice is ADR-06, §9).
  4. Tokenizer consumes the structural index, or scans byte by byte on the scalar path, and emits Tokens with SourceLocation spans into the input. It does not allocate (§3).
  5. Parser is recursive descent by default. Above a low static threshold it switches to the iterative deep-path parser, and it checks the depth limit before recursing (§3, I2).
  6. Value Builder and Arena. The builder turns tokens into Value nodes, requesting storage from the arena, which bump-allocates fixed blocks for the life of one Document (§3, §8.8).
  7. String Unescaper decodes escapes to UTF-8 lazily, only when a view is materialized or when escapes are present (§3).
  8. NumberConverter applies the exact decision table: integer fast path, Eisel-Lemire, then the big-integer slow path (§3, §8.5). §3 points to "§16" for it, but §16 is the UTF-8 phase and number parsing is Phase 5 (§17); MM4 itself notes that its "§16" is really §17.
  9. SAX path. Instead of the builder, the SaxHandler interface receives events with no tree built, which gives constant-memory streaming (§3, §8.9).
  10. Serializer walks a Value tree and writes bytes, applying the escaping table and optional pretty-printing (§3, §8.10).
  11. Limits Enforcer holds the Limits struct (depth, document size, string length, number length) and is consulted before any allocation or recursion (§3, §11).

On failure the result is ParseResult::Error with a byte offset and the partial arena is thrown away; no partly built tree is ever returned (P7, I7).

The core ideas

A strict tokenizer state machine (§8.1, §8.2)

The grammar is RFC 8259's. Six structural characters, four whitespace bytes (space, tab, line feed, carriage return), no BOM, no comments, no trailing commas (§8.1, §1). The Tokenizer is a state machine: Start, InString, InEscape, InUnicodeEscape, PendingSurrogate, InNumber, InLiteral, each row naming its next state and its error edge (§8.2). Every error edge carries a named ErrorCode and a byte offset (§8.2, P6).

The blueprint's failure trace (§8.12) is the template for a toy version. Parsing {"a": tru}:

  1. The tokenizer enters InLiteral expecting true and matches t, r, u.
  2. It meets } where e should be and emits ErrorCode::UnexpectedToken at the offset of }, with line and column derived from a running newline count.
  3. The result is Error, the partial arena is discarded, and no Value reaches the caller.

Strings: escapes, surrogate pairs and UTF-8 (§8.3, §8.4)

Eight short escapes map to single bytes, and \uXXXX gives a 16-bit unit (§8.3). A unit in [0xD800, 0xDBFF] must be followed by a \uXXXX in [0xDC00, 0xDFFF]. The code point is then 0x10000 + ((hi - 0xD800) << 10) + (lo - 0xDC00) (§8.3). Anything else is a lone surrogate (ErrorCode::LoneSurrogate).

Step Value Source
high and low units hi = 0xD83D, lo = 0xDE00 §8.3 worked example
combine 0x10000 + (0x3D << 10) + 0x200 = 0x1F600 §8.3
UTF-8 output F0 9F 98 80 §8.3

Raw bytes are checked separately by a well-formedness table that tightens the second byte for four lead bytes (§8.4): E0 needs A0-BF and F0 needs 90-BF (both reject overlong), ED needs 80-9F (rejects the surrogate range), F4 needs 80-8F (caps at U+10FFFF). Worked cases from §8.4: E2 82 AC is accepted; E0 80 80 is rejected as overlong; ED A0 80 is rejected as a surrogate.

Exact numbers: classify, fast path, slow path (§8.5)

A conversion is exact or it is a data-corruption bug (P3, MM4). The procedure has five named steps: classify (integer or double, one scan, no allocation), fast_int (multiply-add with overflow checks), eisel_lemire (a table lookup plus a 128-bit multiply, succeeding for the "documented ~99.5%" of inputs), slow_path (correctly rounded arbitrary-precision conversion), and finalize (apply sign, keep the sign bit of -0) (§8.5).

Text Decision Source
42 NumberKind::Integer, exact int64 §8.5
99999999999999999999 overflows int64, so Double §8.5
9007199254740993 rounds to 9007199254740992.0, half-to-even §8.5
1e400 rejected with NumberOutOfRange unless allow_infinity_on_overflow is set §8.5, ADR-15
-0 Double, sign bit kept; serialization must print -0 §8.5, I4

The two-stage SIMD scan and its proof of equivalence (§8.6, P4, I5)

Stage 1 never interprets values (§3). It works 64 bytes at a time in seven steps (§8.6): load the chunk; build a bitmask of " bytes; build a mask of backslash runs and use the parity of each run to drop escaped quotes; take a prefix XOR of the quote mask to get the "inside a string" region; mask the structural and whitespace bytes against it; then turn the structural mask into a list of byte offsets (structural_indices[]). The §8.6 worked example shows an escaped quote (\") not toggling the in-string state, so the string does not end early.

The rule that keeps this honest: no SIMD code ships without a scalar twin proven identical by differential fuzzing (P4, MM3). Invariant I5 says the two scanners give identical structural indexes for every input, and the recovery if they ever differ is to disable SIMD dispatch and fall back to scalar (I5, FM-5).

One 16-byte value and an arena (§8.7, §8.8, ADR-09, ADR-11)

Each Value is a 16-byte tagged union: a tag (3 bits), an inline flag (1 bit), then a payload (§8.7). Null, Bool and strings up to 7 bytes (ShortString) live inline; integers and doubles use a second machine word; longer strings, arrays and objects hold an arena reference (§8.7). The arena is a chain of fixed-size blocks, bump-allocated, with one dedicated block for any request larger than a block (§8.8). Reset after a failed parse frees the whole chain, an O(blocks) operation, not O(nodes) (§8.8, P7, P9).

Depth checked before recursion, with an iterative escape hatch (P8, I2, ADR-05)

The caller (parse_value) checks the depth counter and rejects before descending, never inside the callee after the frame is already committed (P8). Checking one frame late allows N+1 frames of stack growth (P8, FM-7). Above a low static threshold (§21.2 gives "e.g., depth 32") the parser swaps native recursion for an explicit heap stack, and the two must give byte-identical results (§21.2, ADR-05). The switchover is "an internal optimization detail, not observable behavior" (§21.8).

The trade-offs — where engineers disagree

Parsing strategy: recursive descent plus a SIMD fast path (ADR-04)

Chosen: recursive descent as the default, with a simdjson-style two-stage SIMD fast path. It is auditable against the EBNF directly and avoids on-demand's borrowed-lifetime hazards (ADR-04). Rejected: pure table-driven, and pure simdjson on-demand. When the rejected choice is right: on-demand wins for selective-field extraction from huge documents when the caller can accept lifetime discipline (ADR-04, §36).

Deep nesting: switch to an explicit stack only when needed (ADR-05)

Chosen: an iterative explicit-stack parser, switched in above a threshold. Recursive descent is simpler for typical shallow documents, and the iterative path removes the stack risk where it matters (ADR-05). Rejected: unconditional iterative, unconditional recursive. When the rejected choice is right: unconditional iterative wins on an embedded target with a tiny fixed stack, where even shallow recursion is risky (ADR-05).

Input buffer: read-only, never modified in place (ADR-08)

Chosen: the input is read-only; string views point into a caller-owned immutable buffer. This is safer and fits streaming and memory-mapped input (ADR-08, §33). Rejected: RapidJSON-style in-situ null-termination. When the rejected choice is right: in-situ wins when the caller owns a mutable scratch copy and wants to avoid a second buffer for unescaping (ADR-08).

Number parsing: Eisel-Lemire with a big-integer fallback (ADR-12)

Chosen: the Eisel-Lemire fast path (Lemire 2021) with a Gay 1990 big-integer slow path: correct by construction, and fast for ~99.5% of inputs (ADR-12, §8.5). Rejected: strtod, and always-big-integer. When the rejected choice is right: always-big-integer wins when literals are known to be adversarially crafted at the subnormal boundary and speed is irrelevant (ADR-12).

Duplicate keys: last value wins, with a strict mode (ADR-16)

Chosen: last-value-wins by default, strict-reject opt-in. It matches most production libraries for interoperability, and strict mode closes T6 for security-sensitive callers (ADR-16, I10). Rejected: first-value-wins, always-reject. When the rejected choice is right: always-reject wins for a hardened ingestion gateway that rejects spec-ambiguous input categorically (ADR-16).

Value layout: a 16-byte tagged union (ADR-09)

Chosen: 16-byte union with a 3-bit tag and an inline/indirect flag, for branch-free tag dispatch and clean alignment (ADR-09, §8.7). Rejected: pointer-tagged NaN-boxing, always-boxed values. When the rejected choice is right: NaN-boxing wins in a memory-constrained embedded target parsing almost entirely numeric arrays (ADR-09).

UTF-8 validation: always on by default (ADR-06)

Chosen: a scalar DFA validator (Hoehrmann-style) plus a SIMD one (Keiser and Lemire), because untrusted input needs provable well-formedness and the library cannot verify that a caller pre-validated (ADR-06, P11). Rejected: trust the caller and skip validation. When the rejected choice is right: only in an internal trusted-pipe mode that is explicitly documented and opt-in, never as the default (ADR-06).

Roads not taken (§36, §37)

On-demand parsing (§36): no tree is built; the caller navigates the input and each field is parsed when touched, using stage 1's index as a skip list. It wins when most fields in a huge document are never read (the blueprint's example is one field from a 100 MB record array). It is rejected as the default for its borrowed-lifetime constraints (P5, ADR-04) and kept as a future extension point.

SAX-only (§36): no Value tree, only events. It wins for constant-memory single-pass consumers such as log processors and streaming ETL. It is rejected as the sole API because much real JSON benefits from random access, and the shared tokenizer core makes offering both cheap (ADR-19).

Code-generated, schema-bound parser (§36): parser and target struct are generated together, so there is no generic Value. It is the fastest design whenever the schema is known and stable at compile time (serde_json with derive, Protocol Buffers). It is rejected because this blueprint targets arbitrary documents (§1); it is "a different product" in scope (§36).

Parser combinators (§36): the grammar is composed from seq, alt and many, which maps almost line for line onto the EBNF and is easy to audit for P1. It wins when clarity matters more than throughput. It is rejected because its indirect calls and intermediate allocation work against the §4 throughput target.

The deferred register (§37) parks eight items, among them JSON5 comments mode, Merge Patch (RFC 7396), JSON Schema validation, AVX-512 and WASM SIMD variants, and intra-document parallel parsing (which needs the SIMD index as a split point; §31 argues it likely costs more than it saves). Each row names the trigger that would un-defer it (§37).

What must never be false

  • I1: parsing never reads outside the input buffer. Noticed by ASan in CI and bounds-checked debug builds; telemetry parse.oob_guard_hits should be zero (§7).
  • I2: nesting depth never exceeds the limit, checked before recursion. Depth-limit fixtures; parse.depth_limit_hits (§7).
  • I3: every accepted string is well-formed UTF-8 with no lone surrogate. UTF-8 edge corpus plus a SIMD/scalar differential test; parse.utf8_reject_count (§7).
  • I4: every finite double survives parse, serialize, parse bit-identically. Property test over the 4M-case corpus; numbers.roundtrip_failures must be zero, and a failure fails CI (§7).
  • I5: SIMD and scalar scanners give identical structural indexes. Differential fuzz target; simd.diff_mismatches must be zero (§7).
  • I6: total allocation stays within a stated multiple of input length. Memory high-water test on the adversarial corpus; arena.blocks_allocated, arena.bytes_high_water (§7).
  • I7: a rejected document yields a precise error with an offset, never a partial DOM. Tests assert Error on every n_* fixture; parse.error_without_offset must be zero (§7).
  • I8: the parser is reentrant and safe on allocation failure. ASan plus thread-sanitizer runs; arena.alloc_failures (§7).
  • I9: depth and size checks run before the allocation or call they guard. Fuzzing at exact boundary values; the telemetry row parse.limit_check_order_violations is described as one that "should not exist post-audit", so detection is by code review and the fuzz corpus (§7).
  • I10: duplicate keys follow one documented policy in both DOM and SAX modes. Fixtures i_object_key_dup*; parse.duplicate_key_hits (§7).
  • I11: a read-only Document is safe to read from many threads. Thread-sanitizer concurrent-read test; no telemetry (§7).
  • I12: a zero-copy StringView is valid only as long as its source buffer. ASan lifetime-stress tests; no runtime telemetry, so the safeguard is documentation and an owning-mode default (§7).

What breaks in production

  • FM-1: a parse hangs on one input. Quadratic escape scanning (T9), a pathological backslash-run pattern, or an unbounded slow-path number loop. Seen as a CPU-time-bound fuzz failure or a p99 latency spike. No automatic recovery; the fix is a caller-side timeout, then adding the input as a timing regression fixture and patching the scan (§25).
  • FM-2: memory grows without bound during a streaming parse. An internal buffer retains every processed chunk, or a Limits gap exists in the streaming path. Seen as an RSS alert or a failing streaming memory test. Restart, patch the retention, add a memory-ceiling test (§25).
  • FM-4: a double comes back different after parse, serialize, parse. A missed Eisel-Lemire failure signal, a Ryu bug, or -0 losing its sign. The 4M-case property test (I4) catches it. It is a release-blocking defect, not a runtime-recoverable condition; bisect to the minimal failing value (§25).
  • FM-5: the SIMD and scalar scanners disagree. Missing carry-chain state at a chunk boundary, or an unmasked partial-chunk read. The differential fuzz target catches it; recovery is to disable SIMD dispatch and fall back to scalar, then fix the SIMD code (§25, I5).
  • FM-7: stack overflow despite a depth limit. The limit was checked after recursion (a P8 violation) or in the wrong order (I9). Found by the constrained-thread-stack CI leg or a fuzz crash signature. No graceful recovery; audit every recursive call site for check-before-call (§25).
  • FM-8: DOM and SAX handle duplicate keys differently. The shared policy function of I10 was reimplemented twice. A differential test comparing DOM construction to the SAX event sequence finds it; refactor to a single shared function (§25).
  • FM-10: a failing test patch operation leaves partial changes. Patch application mutated the live Document instead of a scratch builder. The patch-atomicity fixture finds it; apply into a scratch builder and commit only on success (§25).

Threats a reader should know (§24):

  • T1: stack exhaustion from deep nesting. Mitigated by the depth limit before recursion and the iterative fallback (I2, P8).
  • T6: duplicate-key divergence between a validator and an executor, answered by one policy and an optional strict mode (I10, ADR-16).
  • T7: a huge exponent forcing expensive slow-path work. The digit limit is enforced character by character during the scan, before conversion (P12); numbers.slow_path_conversions is the spike signal.
  • T8: a zero-copy view outliving its buffer. Mitigated by a documented lifetime and an owning-mode default (P5, I12).
  • T11: tampering with the vendored conformance corpus to fake a "100% pass". Mitigated by a pinned corpus commit hash reviewed on every bump (§24).

Points where the blueprint's own text pulls apart (stated, not resolved):

  • §34 computes native stack use at the full depth of 512, but ADR-05 and §21.2 say native recursion gives way to the explicit stack above a low threshold, and §34's own last paragraph says the recursive path is used "below the depth-32 threshold". §21.2 gives 32 only as "e.g.", while §21.7, §21.8 and §34 treat depth 32 as the fixed switchover.
  • §34's amplification paragraph puts arena-block waste at "typically 10–15%", but its arena paragraph puts average waste at roughly half the 375-block worst case (≈12 MB) against 24 MB of node storage.
  • §1 says "approximately 10–12 weeks" to the Phase 11 exit criteria; Appendix B (§40) gives per-phase ranges from 3–5 days up to 6–10 days and states no total.

How it compares

  • simdjson chose a two-stage structural scan with a tape or on-demand access (§33). That split lets the structure-finding stage be built and tested independently, and it wins wherever multi-GB/s throughput matters more than API simplicity (§33).
  • RapidJSON chose in-situ parsing that overwrites the input to null-terminate strings (§33). It wins when the caller owns a mutable scratch buffer; this design rejects it for the read-only, streaming and memory-mapped case (ADR-08).
  • nlohmann/json chose ergonomics first, with an owning string type and implicit conversions (§33). That fits application code where developer speed matters more than the last factor of throughput, and it is "by a wide margin" the most adopted C++ JSON library (§33).
  • yyjson chose distinct mutable and immutable document types, with an arena-like immutable DOM (§33). That lets read-dominated workloads skip synchronization; this design borrowed the immutable-by-default idea but keeps one root type (§33, ADR-20).
  • serde_json chose to bind parsing straight to a known Rust struct (§33). That wins on speed and memory whenever the caller controls both ends of the schema (§33, §36).

Questions to test yourself

  1. If Eisel-Lemire's fast path silently returned an incorrectly-rounded result instead of falling back on failure, how long would it take to notice in production, and what does that imply about the 4M-case corpus's role versus production telemetry? — Hint: §17 and §26; compare I4's detection column with FM-4.
  2. Given that RFC 8259 leaves duplicate-key handling implementation-defined, what specific property does the last-value-wins default (ADR-16) have that a first-value-wins default would lack, with respect to T6's parser-differential-attack scenario? — Hint: §9 ADR-16 and the T6 row in §24.
  3. Why does the SIMD/scalar differential fuzz target (I5) need to run continuously rather than once per release, given that the SIMD implementation is expected to be feature-frozen after Phase 10? — Hint: §21, §22, §28; and the FM-5 root causes in §25.
  4. §34 derives a SIMD speedup ceiling of 32x for the structural-scan stage alone but documents an end-to-end scalar-fallback penalty of only 6–8x — reconcile these two numbers using the phase arc's own division of labor across tokenization, parsing, and number conversion. — Hint: the SIMD ceiling paragraph of §34 and the §4 constraint row.
  5. Streaming/SAX mode (Phase 8) and DOM mode share one tokenizer core (ADR-19) — what specific invariant (from §7) would be at risk if a future optimization forked the two into separate, independently-maintained state machines? — Hint: I10 and FM-8.

If you only remember three things

Treat every byte as hostile: bound depth, size and number length before the input can use the resource, and check the depth before you recurse (MM5, P2, P8). Be exact where it is easy to be approximately right: numbers round-trip bit for bit and text is proven UTF-8 before it is trusted (MM4, P3, P11). Make speed earn its place by proof: the SIMD path ships only with a scalar twin that agrees on every byte, and the JSONTestSuite corpus, not opinion, defines "correct" (MM3, MM8, I5).

Words used here

  • Structural character: one of the six characters { } [ ] : , that shape a JSON document (§38).
  • Tokenizer: the state machine that turns bytes into tokens with positions (§8.2, §38).
  • DOM: the fully built Value tree for a document; streaming (SAX) avoids building it (§38, §8.9).
  • Arena allocator: a bump-pointer allocator whose memory lives and dies with one document (§8.8).
  • Zero-copy view: a string value that points into the input instead of copying it (P5).
  • Surrogate pair: two 16-bit units that together spell one code point above U+FFFF (§8.3, §38).
  • Overlong encoding: a UTF-8 sequence using more bytes than the shortest valid form (§8.4, §38).
  • Eisel-Lemire: a fast string-to-double algorithm that sometimes signals it cannot decide (§8.5).
  • Slow path: the exact but expensive arbitrary-precision fallback conversion (§8.5, §38).
  • Prefix-XOR scan: the bit trick that turns quote positions into "inside a string" regions (§8.6).
  • Parser differential: two parsers disagreeing on the same input, which an attacker can exploit (T6).
  • Stack exhaustion: a crash caused by recursion using up the thread stack (T1, §38).
  • Sanitizer: compile-time instrumentation (ASan, UBSan, MSan) that finds memory and UB bugs (§38).
  • i_ case: a corpus fixture whose correct verdict the RFC leaves open, so the blueprint documents its own (§38, MM8).
