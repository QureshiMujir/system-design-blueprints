ADR-04

Parsing strategy

Chosen

recursive descent (default) + simdjson-style two-stage SIMD fast path

Rejected

pure table-driven, pure simdjson on-demand

When the rejected choice is right

pure on-demand wins when the workload is selective-field extraction from huge documents and lifetime discipline is acceptable to the caller (§36)

Why: recursive descent is auditable against the EBNF directly; two-stage SIMD gives simdjson-class throughput without on-demand's borrowed-lifetime hazards

ADR-05

Deep-nesting fallback

Chosen

iterative explicit-stack parser, switched in above a threshold

Rejected

unconditional iterative, unconditional recursive

When the rejected choice is right

unconditional iterative wins in an embedded target with a tiny fixed stack, where even shallow recursion is risky

Why: recursive descent is simpler to reason about for typical shallow documents; iterative removes stack-exhaustion risk exactly where it matters

ADR-06

UTF-8 validation approach

Chosen

DFA-based scalar (Hoehrmann-style) + SIMD (Keiser & Lemire) dispatch

Rejected

trust-the-caller (skip validation)

When the rejected choice is right

skip-validation wins only in an internal trusted-pipe mode explicitly documented and opt-in, never the default

Why: untrusted input requires provable well-formedness (P11); skipping validation is only acceptable when the caller pre-validates, which cannot be verified at the library boundary

ADR-07

SIMD strategy / dispatch

Chosen

runtime CPU-feature detection selecting AVX2 / NEON / scalar at library init

Rejected

compile-time-only dispatch, always-AVX-512

When the rejected choice is right

compile-time-only wins in a single-target embedded build where the CPU is fixed and known at compile time

Why: portability across deployment fleets with heterogeneous CPUs; compile-time-only forces a lowest-common-denominator binary or per-CPU builds

ADR-08

Input buffer mutation

Chosen

read-only input, no in-situ mutation

Rejected

RapidJSON-style in-situ null-termination

When the rejected choice is right

in-situ wins when the caller explicitly owns a mutable scratch copy and wants to avoid a second buffer for unescaping

Why: zero-copy views into a caller-owned immutable buffer are safer and match the streaming/mmap use case

ADR-09

DOM value representation and tagging

Chosen

16-byte tagged union, 3-bit tag + inline/indirect flag

Rejected

pointer-tagged NaN-boxing, always-boxed values

When the rejected choice is right

NaN-boxing wins in a memory-constrained embedded target parsing almost entirely numeric arrays

Why: branch-free tag dispatch and clean alignment outweigh NaN-boxing's smaller footprint for this workload

ADR-10

Chosen

36. Alternative Architectures (Roads Not Taken)

On-demand / lazy parsing (simdjson's model). No DOM is ever built; the caller navigates the input directly, and each accessed field is parsed only when touched, using the structural index from stage 1 as a skip-list to jump over unaccessed substructures.

  input bytes --> structural index (stage 1, eager) --> caller navigates directly
                                                          |
                                              [.] field access triggers
                                              [.] just-in-time parse of
                                              [.] only that value's bytes

Winning regime: selective-field extraction from huge documents where most fields are never touched — e.g., reading one field from a 100 MB log-record array without materializing the other 99% of records. Real embodying system: simdjson's on-demand API. Why rejected here as the default: the borrowed-lifetime constraints it imposes on the caller (every accessed value remains tied to the input buffer and to the specific navigation order) are a usability and safety tradeoff this blueprint's DOM-mode default explicitly avoids (P5, ADR-04) — offered instead as a documented future extension point, not built in Phase 0–11.

Pure streaming SAX-only design, no DOM at all. The library never offers a Value tree; only the push/pull event interfaces of Phase 8 exist, and all structure-holding responsibility is pushed to the caller.

  input bytes --> tokenizer/parser core --> SaxHandler callbacks only
                                             (caller builds any structure
                                              it needs, or none at all)

Winning regime: constant-memory, single-pass consumers (log processors, streaming ETL) that never need random access into the parsed structure. Real embodying system: many streaming XML/JSON parsers in resource-constrained embedded contexts follow this shape exclusively. Why rejected as the sole API here: a large fraction of real-world JSON consumption (configuration files, API response bodies under a few megabytes) genuinely benefits from random-access DOM ergonomics, and this blueprint's shared-tokenizer-core design (ADR-19) means offering both costs little beyond the SAX-only design's own implementation effort.

Code-generated, schema-bound parser (serde/protobuf model). The parser and its target data structure are generated together from a schema at compile time; there is no generic Value type at all, and the parser only accepts documents matching the compiled-in shape.

  schema (compile time) --> generated parse function --> caller's native struct
                                                            (no Value, no DOM,
                                                             no runtime dispatch)

Winning regime: any workload where the schema is known and stable at compile time — this is the fastest possible design because it eliminates the tagged-union dispatch, the arena, and the generic-value overhead entirely, replacing them with direct field assignment. Real embodying system: serde_json paired with #[derive(Deserialize)], and Protocol Buffers generally. Why rejected here: this blueprint's stated goal is a general-purpose JSON parser for arbitrary, not-necessarily-schema-known documents (§1) — a schema-bound generator is a different product with a different scope, not a variant of this one.

Table-driven or parser-combinator implementation. The grammar of §8.1 is expressed as a table of parser-combinator primitives (seq, alt, many) composed declaratively, rather than as hand-written recursive-descent functions.

  value_parser = alt(object_parser, array_parser, string_parser,
                      number_parser, literal_parser)
  object_parser = seq('{', opt(member_list), '}')

Winning regime: contexts where grammar clarity and provable correctness against the EBNF matter more than raw throughput — a combinator-based parser's structure maps almost line-for-line onto the grammar, making it easy to audit for spec fidelity (directly serving P1). Real embodying system: parser-combinator libraries common in Haskell (Parsec-style) and increasingly in Rust (nom). Why rejected here: the combinator abstraction's typical runtime cost (indirect calls, allocation for intermediate combinator results) works against the §4 multi-GB/s throughput target that recursive descent plus a hand-tuned SIMD fast path can hit directly; this blueprint favors provable equivalence via differential testing (P4) over provable-by-construction combinator structure as the path to the same trust outcome.
