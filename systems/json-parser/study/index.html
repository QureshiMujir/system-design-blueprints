Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If Eisel-Lemire's fast path silently returned an incorrectly-rounded result instead of falling back on failure, how long would it take to notice in production, and what does that imply about the 4M-case corpus's role versus production telemetry? (§17, §26)
  2. Why is a 512-frame recursion limit derived from stack-frame arithmetic (§34) rather than chosen as a round number, and what would change about that derivation if the target deployment were an embedded system with a 16 KiB thread stack? (§4, §13, §34)
  3. Given that RFC 8259 leaves duplicate-key handling implementation-defined, what specific property does the last-value-wins default (ADR-16) have that a first-value-wins default would lack, with respect to T6's parser-differential-attack scenario? (§9, §24)
  4. Why does the SIMD/scalar differential fuzz target (I5) need to run continuously rather than once per release, given that the SIMD implementation is expected to be feature-frozen after Phase 10? (§21, §22, §28)
  5. The zero-copy StringView optimization (P5) and the immutable-by-default DOM (P10) both trade flexibility for safety — what would break if either were relaxed independently of the other, and why must they be considered jointly rather than as two separate tradeoffs? (§6, §11)
  6. §34 derives a SIMD speedup ceiling of 32x for the structural-scan stage alone but documents an end-to-end scalar-fallback penalty of only 6–8x — reconcile these two numbers using the phase arc's own division of labor across tokenization, parsing, and number conversion. (§22, §30, §34)
  7. Why is JSON Pointer/Patch sequenced last (Phase 11) rather than early, given that it seems independent of the number/UTF-8/SIMD correctness work that dominates the middle phases? (§9 ADR-24, §23, §12 arc)
  8. If a consumer depends on SerializeOptions::sort_keys's exact byte-wise ordering for a content-addressed hash, and a future release changes the underlying UTF-8 collation library's behavior transitively, is that a compatibility break under this blueprint's own versioning rules — and where exactly is that boundary drawn? (§19, §27)
  9. The threat model (§24) treats duplicate-key divergence (T6) and lone-surrogate propagation (T5) as parser-differential attacks against downstream systems, not against this parser itself — what does that imply about the limits of what a single conformant parser can guarantee for a multi-hop pipeline? (§24, §33)
  10. Streaming/SAX mode (Phase 8) and DOM mode share one tokenizer core (ADR-19) — what specific invariant (from §7) would be at risk if a future optimization forked the two into separate, independently-maintained state machines? (§7, §20)
  11. §31 argues a single document resists parallel parsing because there's no statically-known split point without a sequential scan — does the SIMD structural scan (Phase 10) actually provide such a split point cheaply, and if so, why doesn't this blueprint exploit it for intra-document parallelism? (§22, §31, §36)
  12. The arena-reset-on-failure design (P7, P9) assumes O(blocks) teardown is always acceptable — under what document shape would this assumption's constant factor start to matter operationally, and how would §26's telemetry surface that? (§7, §14, §26)
  13. §17 and §18 both depend on Eisel-Lemire/Ryū's documented failure/success rates as empirical facts from the cited papers — what would have to be re-verified about this blueprint's own number-handling phases if a future revision of either paper's algorithm changed those rates? (§5, §17, §18)
  14. Given that the CLI validator (tools/jsonp-validate) is explicitly out of scope for shell- injection concerns (T12), what specific operational guidance in §26 closes that gap for an operator deploying it in an ingestion pipeline? (§24 T12, §26)
  15. §36 will present at least one alternative architecture (simdjson's on-demand model) that this blueprint explicitly rejected for the DOM-mode default — what evidence from §33's comparative table would change that rejection if a specific consumer's workload shifted toward selective- field extraction from huge documents? (§33, §36, §9 ADR-04)
  16. The 5.0x DOM memory amplification ceiling (§4, M9) and the §34 derivation arriving at 2.7–3.0x for a specific corpus shape — what document shape would push the measured figure toward the ceiling rather than the derived typical case, and is the ceiling itself derived or merely asserted with margin? (§4, §34)
  17. Phase 9's fuzzing campaign and Phase 10's differential SIMD/scalar fuzz target both use libFuzzer — what specific coverage gap would exist if only one of the two campaigns ran, given that both exercise overlapping code paths? (§21, §22, §28)
  18. §27 declares tightening strictness a breaking change — walk through a concrete scenario where a security fix (rejecting a previously-accepted malformed input that turned out to enable T5) is simultaneously a correctness improvement and a SemVer-major-triggering breaking change, and how the release process should communicate that tension. (§24 T5, §27, §29)
  19. §11 documents Value's bit layout as an internal detail with no ABI guarantee, yet §29 generates an SBOM and provenance attestation for release artifacts — what exactly is being attested if the internal layout can change between patch releases of the compiled-library variant? (§11, §27, §29)
  20. Given MM8's claim that the conformance corpus is "the spec, extended" for i_* cases, what governance process should apply if a future JSONTestSuite update changes an i_* case's own categorization — does this blueprint's pinned-corpus-commit policy (T11) protect against that, or merely delay encountering it? (§24 T11, §28, §32 MM8)

32. Mental Models & First Principles

MM1 — A parser is a total function from bytes to either a value or a precise error. Insight: "undefined behavior on malformed input" is not a category that exists for this design. Predicts: every input, however malformed, must land in exactly one of {success, documented error}. Bug class without it: crashes and hangs on adversarial input (T1, T2, T4). Resolving §7 (I1, I7) and §24.

MM2 — JSON's grammar is trivial; its difficulty is entirely in numbers, Unicode, and adversarial input. Insight: the six-production EBNF in §8.1 fits on one page, yet this blueprint spends four full phases (5, 6, 4, 9) on exactly those three concerns. Predicts: a naive implementation looks complete after Phase 1 but is nowhere near production-ready. Bug class without it: shipping a "works on the happy path" parser mistaken for a finished one. Resolving §5 (papers on number/UTF-8 correctness) and §12–§23's phase arc.

MM3 — The SIMD fast path is an optimization that must be provably equivalent to the scalar path. Insight: speed is worthless if it's a different function; differential testing is not optional polish, it's the mechanism by which "faster" and "correct" are simultaneously true. Predicts: any SIMD change without a corresponding differential-fuzz run is unreviewable. Bug class without it: a CPU-feature-dependent correctness bug (FM-5). Resolving §22 (Phase 10) and I5.

MM4 — A number is a mathematical value with a textual representation, and the conversion between them is either exact or wrong — there is no acceptable "close enough." Insight: floating-point tolerance-based thinking, appropriate in numerical computing, is actively wrong for a parser whose job is preserving an exact value across a serialization boundary. Predicts: any number bug reports as "occasionally wrong in the 17th digit," not "wildly wrong," because near-misses are the signature of an incomplete rounding implementation. Bug class without it: silent data corruption in financial/scientific data (T7-adjacent, but really P3's core concern). Resolving §16–§17 (§16 in this doc's actual number is §17) and I4.

MM5 — Untrusted input means every resource consumed by parsing — stack, heap, CPU time — must be bounded before the input is trusted enough to drive that consumption. Insight: this reframes "parsing" as "parsing plus resource accounting," a dual concern from the first byte. Predicts: any missing Limits check is a potential denial-of-service vector, not merely an edge-case bug. Bug class without it: every row of §24's threat model. Resolving §7 (I2, I6, I9) and §21 (Phase 9).

MM6 — A borrowed view is a promise about a lifetime that the type system in C++ cannot fully enforce, so the design must make the promise's boundary as narrow and explicit as possible. Insight: zero-copy performance and memory safety are in genuine tension, resolved not by picking one but by making the tension's boundary a single, well-documented field (StringView.borrowed_from_input). Predicts: use-after-free bugs cluster at API boundaries where a caller controls buffer lifetime independently of Document lifetime. Bug class without it: T8. Resolving §11 and P5.

MM7 — Streaming and DOM construction are two different answers to "how much of the document must exist in memory at once," and the right answer depends on what the caller does with the result, not on which is objectively better. Insight: DOM mode trades memory for random-access ergonomics; SAX/streaming mode trades ergonomics for constant memory — neither dominates. Predicts: a caller doing a single sequential pass over a huge log file should never reach for DOM mode. Bug class without it: unnecessary memory pressure from defaulting to DOM mode regardless of access pattern. Resolving §33 and §36.

MM8 — The conformance corpus is not a test suite in the ordinary sense; it is the operational definition of "correct" for every ambiguous case the specification leaves open. Insight: for the i_* category specifically, there is no ground truth outside the project's own documented choice — the corpus is the spec, extended. Predicts: disputes about "is this a bug" for an i_* case resolve by checking the documented verdict table, not by re-arguing from RFC 8259 text that is silent on the point by definition. Bug class without it: endless re-litigation of settled implementation-defined behavior. Resolving §12, §23, §28.

Required reading (§5)

Books

  • Aho, Lam, Sethi & Ullman, Compilers: Principles, Techniques, and Tools (2nd ed.) — ch. 3 (Lexical Analysis: DFA construction for the tokenizer) and ch. 4 (Syntax Analysis: recursive descent and table-driven parsing). Extract: the DFA-minimization technique behind the tokenizer state-transition table in §14. Applied in Phase 0 (§12).
  • Grune & Jacobs, Parsing Techniques (2nd ed.) — ch. 2 (grammars) and ch. 8 (recursive descent and its stack-depth failure mode). Extract: the formal justification for the iterative deep-path fallback. Applied in Phase 1 (§13) and Phase 9 (§21).
  • Stroustrup, The C++ Programming Language (4th ed.) — ch. 8 (unions and variant design) and ch. 34 (memory and resources). Extract: tagged-union layout discipline for Value. Applied in §11 and Phase 2 (§14).
  • Meyers, Effective Modern C++ — items 7 (braced init pitfalls with unions), 21 (smart-pointer ownership), and 42 (emplacement) for arena-adjacent construction. Applied in Phase 2 (§14).
  • Williams, C++ Concurrency in Action — ch. 5 (memory model) for the reentrancy and allocation-failure-safety invariant (I12). Applied in §7 and §27 (thread-safety guarantees).
  • Knuth, The Art of Computer Programming, Vol. 2: Seminumerical Algorithms — ch. 4 (arithmetic, specifically multi-precision arithmetic) for the big-integer slow-path conversion. Applied in Phase 5 (§17).

Papers

  • Goldberg, 1991, ACM Computing Surveys, "What Every Computer Scientist Should Know About Floating-Point Arithmetic" — foundational IEEE 754 rounding rules. Applied in Phase 5 (§17).
  • Steele & White, 1990, PLDI, "How to Print Floating-Point Numbers Accurately" — the shortest-round-tripping-representation problem statement. Applied in Phase 6 (§18).
  • Gay, 1990, Bell Labs numerical analysis manuscript, "Correctly Rounded Binary-Decimal and Decimal-Binary Conversions" — the reference correctly-rounded conversion algorithm used as the slow-path oracle. Applied in Phase 5 (§17) and Phase 6 (§18).
  • Loitsch, 2010, PLDI, "Printing Floating-Point Numbers Quickly and Accurately with Integers" (Grisu) — fast serialization with a documented failure rate requiring a fallback. Applied in Phase 6 (§18).
  • Adams, 2018, PLDI, "Ryū: fast float-to-string conversion" — the chosen serialization algorithm, always-fast with no fallback. Applied in Phase 6 (§18), locked by ADR-14.
  • Lemire, 2021, Software: Practice and Experience, "Number Parsing at a Gigabyte per Second" (Eisel-Lemire) — the chosen parse-fast-path algorithm and its ~0.5% fallback rate. Applied in Phase 5 (§17), locked by ADR-13.
  • Langdale & Lemire, 2019, The VLDB Journal, "Parsing Gigabytes of JSON per Second" (simdjson) — the two-stage structural-index/tape design this blueprint's SIMD phase follows. Applied in Phase 10 (§22).
  • Keiser & Lemire, 2021, Software: Practice and Experience, "Validating UTF-8 In Less Than One Instruction Per Byte" — the SIMD UTF-8 validation algorithm. Applied in Phase 4 (§16).
  • Muła, Kurz & Lemire, "Faster Population Counts Using SIMD Instructions" / SIMD string-processing techniques — bitmask extraction (pdep/pext) used in stage 1 structural scanning. Applied in Phase 10 (§22).
  • Seriot, "Parsing JSON is a Minefield" (published article, JSONTestSuite companion) — catalogue of implementation-divergence cases that seeds the conformance corpus. Applied in Phase 0 (§12) and §28.

Reference Implementations

  • simdjson, src/generic/stage1/ — structural-index bitmask pipeline. Lesson: prefix-XOR quote tracking generalizes cleanly to escaped-backslash runs. Pitfall not to copy: simdjson's on-demand API intentionally exposes borrowed-lifetime hazards to the caller for speed — do not adopt that ergonomics tradeoff for the DOM-mode API (ADR-04 chooses safety there).
  • simdjson, src/generic/stage2/ — tape construction from the structural index. Lesson: a flat tape with type tags avoids pointer-chasing during DOM materialization. Pitfall: the tape's packed 64-bit entries assume a specific pointer width; do not hardcode 64-bit assumptions into this blueprint's ValueUnion layout (§11) without a static_assert guard.
  • RapidJSON, include/rapidjson/reader.h — SAX-first, template-parameterized parser. Lesson: a handler-interface SAX design (this blueprint's SaxHandler, §11) can be made allocation-free for the reader itself. Pitfall: RapidJSON's in-situ parsing mutates the input buffer to null- terminate strings — incompatible with this blueprint's read-only Input Adapter (ADR-06).
  • RapidJSON, include/rapidjson/writer.h — escaping and number-formatting dispatch table. Lesson: precomputed per-byte escape-need lookup table for the serializer's fast path (§20). Pitfall: RapidJSON defaults to %g-based number formatting without Ryū; do not inherit that default (ADR-14 locks Ryū).
  • nlohmann/json, single_include/ — ergonomics-first DOM design with implicit conversions. Lesson: the value-of-any-type ergonomics that make it popular. Pitfall: its recursive value destructor recurses to input depth, causing stack overflow on deeply nested documents even after a bounded parse — this blueprint's Value destruction must be iterative (I2 extends to teardown, not only parse).
  • yyjson, immutable/mutable dual-DOM design and insitu parsing. Lesson: a read-only immutable DOM variant is measurably faster to build than a mutable one; informs the "mutation support" ADR-19 decision to keep the primary DOM immutable-by-default. Pitfall: yyjson's insitu mode shares RapidJSON's buffer-mutation hazard — rejected for the same reason.
  • serde_json (Rust) — contrasting design via serde::Deserialize trait dispatch instead of a generic Value. Lesson: compile-time schema binding (ADR-05's "code-generated" alternative, §36) eliminates DOM overhead entirely for known schemas. Pitfall: not directly portable to C++'s weaker reflection; do not attempt a literal port, only the design lesson.

RFCs / Specifications

  • RFC 8259 (Bray, 2017) — the primary JSON specification. Applied in Phase 0 (§12) and §8.
  • RFC 7159 (Bray, 2014) — predecessor to 8259; documents the object-duplicate-key and number-precision ambiguities this blueprint must resolve explicitly. Applied in §8 and ADR-16.
  • RFC 4627 (Crockford, 2006) — original JSON RFC; historical baseline for MIME type and the original (looser) grammar. Applied in §27 (compatibility history).
  • ECMA-404 — the ECMA JSON grammar, cross-checked against RFC 8259 for grammar equivalence. Applied in §8.
  • RFC 3629 (Yergeau, 2003) — UTF-8 encoding rules. Applied in Phase 4 (§16).
  • RFC 6901 (Bryan & Zyp, 2013) — JSON Pointer syntax. Applied in Phase 11 (§23).
  • RFC 6902 (Bryan, Zyp & Luthra, 2013) — JSON Patch operations. Applied in Phase 11 (§23).
  • RFC 7396 (Hoffman & Snell, 2014) — JSON Merge Patch, deferred extension. Applied in §37 (PhaseDeferred("RFC 7396 merge-patch support")).
  • IEEE 754-2019 — binary floating-point arithmetic standard. Applied in Phase 5 (§17) and Phase 6 (§18).
  • The Unicode Standard, conformance chapter (well-formed UTF-8 sequences, C10 conformance clause) — Applied in Phase 4 (§16).

Glossary (§38) · 45 terms · site-wide glossary

Tokenizer
the component converting a raw byte stream into a sequence of Tokens per the state-transition table (§8.2).
Lexeme
the substring of input text corresponding to one token.
Recursive descent
a parsing technique with one function per grammar non-terminal, directly mirroring the EBNF (§8.1, §13).
Structural character
one of the six RFC 8259 characters { } [ ] : , that delimit JSON structure.
Structural index
the flat array of byte offsets of every structural character in a document, produced by stage 1 of the SIMD scanner (§8.6).
Two-stage parsing
the simdjson-style division of parsing into a structure-finding stage (stage 1) and a value-interpreting stage (stage 2).
On-demand parsing
a parsing mode that defers interpreting a value's bytes until the caller actually accesses that value (§36).
DOM
Document Object Model; here, the fully-materialized Value tree representing a parsed document.
SAX
Simple API for XML, borrowed terminology for JSON's analogous push-based event interface (§8.9, §11).
Tagged union
a data structure (ValueUnion, §8.7) that stores one of several possible types alongside a discriminant tag identifying which.
Arena allocator
a bump-pointer allocator serving fixed-size blocks for the lifetime of one Document (§8.8).
Zero-copy view
a StringView that borrows directly from the input buffer rather than copying (P5).
Lazy unescaping
deferring the decoding of escape sequences until a string value is actually materialized or accessed.
Surrogate pair
two UTF-16 code units (a high surrogate in [0xD800, 0xDBFF] and a low surrogate in [0xDC00, 0xDFFF]) jointly encoding one astral-plane code point (§8.3).
Astral plane
Unicode code points above U+FFFF, requiring a surrogate pair when represented via \u escapes.
Lone surrogate
a surrogate code unit with no matching pair partner; invalid per this blueprint's strict UTF-8/escape handling (I3).
Overlong encoding
a UTF-8 byte sequence that encodes a code point using more bytes than the shortest valid encoding, forbidden by RFC 3629 (§8.4).
Well-formed UTF-8
a byte sequence conforming to the Unicode Standard's conformance chapter C10, excluding overlong encodings, surrogate-range encodings, and out-of-range code points.
Round-trip exactness
the property that parse→serialize→parse of a number produces a bit-identical result to the original parse (I4).
Shortest round-tripping representation
the decimal string, among all strings that round-trip to a given double, with the fewest digits (Steele & White 1990).
Grisu
Loitsch's 2010 fast float-to-string algorithm with a documented (rare) fallback requirement.
Ryū
Adams's 2018 fast float-to-string algorithm with no documented fallback requirement, locked by ADR-14.
Eisel-Lemire
Lemire's 2021 fast string-to-float parsing algorithm with a documented ~0.5% fallback rate to a slow path.
Slow path
the correctly-rounded but computationally expensive fallback conversion path engaged when a fast-path algorithm's precision guarantee is insufficient.
Big-integer fallback
the arbitrary-precision decimal-to-binary conversion (Gay 1990) used as the number-parsing slow path.
Subnormal
an IEEE 754 floating-point value smaller in magnitude than the smallest normal value, represented with reduced precision.
Negative zero
the IEEE 754 value -0.0, numerically equal to 0.0 but distinct in sign bit and required to round-trip distinctly (§8.5, §17, §18).
Depth limit
the configured maximum nesting level (Limits::max_depth) a document may reach before rejection (I2).
Stack exhaustion
a crash caused by recursion (or other stack growth) exceeding the available thread stack size; the primary risk mitigated by the depth limit and the iterative deep-path parser (T1).
Parser differential
a discrepancy in accept/reject or interpretation behavior between two implementations processing the same input, exploitable when a pipeline includes more than one parser (T6).
JSON Pointer
the RFC 6901 syntax for referencing a specific value within a JSON document by path (§8.11).
JSON Patch
the RFC 6902 syntax for describing a sequence of mutations to apply to a JSON document (§8.11).
JSON Merge Patch
the RFC 7396 alternative patch format expressing a patch as a partial document to be merged, deferred in this blueprint (§37).
Sanitizer
a compile-time instrumentation tool (ASan, UBSan, MSan) detecting memory-safety, undefined-behavior, or uninitialized-memory errors at runtime.
Fuzz corpus
the persisted set of inputs used to seed and grow coverage-guided fuzzing (§21, §28).
Differential testing
comparing this implementation's behavior against independent reference implementations to surface disagreements for adjudication (§28, §33).
Property testing
testing that asserts a general invariant (e.g., round-trip identity) holds across a large, often randomly generated, input space rather than checking specific example cases.
Arena block
one fixed-size (64 KiB default) chunk of memory within an Arena's block chain (§8.8).
Bump allocation
allocating by advancing a single offset pointer within a pre-reserved block, with no per-allocation bookkeeping.
Short string optimization
inlining strings below a length threshold (7 bytes, ADR-10) directly into the ValueUnion payload, avoiding arena indirection.
Prefix-XOR scan
the SIMD technique used to compute "inside string" regions from a quote bitmask by propagating parity across bit positions (§8.6 stage 4).
Backslash-run parity
the computation determining whether a quote character is escaped, based on the parity (odd/even) of the immediately preceding run of backslash bytes (§8.6 stage 3).
CPU-feature dispatch
selecting among multiple implementations (e.g., AVX2 versus scalar) at runtime based on detected CPU capabilities (ADR-07).
i_ case
a JSONTestSuite fixture whose correct verdict is implementation-defined by RFC 8259, requiring this blueprint to document and test its own chosen behavior (§12, §23, §28).
Adversarial input
input specifically crafted to exploit a parser's resource-consumption or correctness weaknesses rather than to represent legitimate data (§24).
