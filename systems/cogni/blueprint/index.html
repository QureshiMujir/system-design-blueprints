1. Goal & Scope

Cogni is a permissionless network in which independent, stake-bonded node operators execute AI-model inference and return zero-knowledge proofs of correct execution against a publicly committed model, so any verifier — a smart contract, a wallet, an auditor — accepts the output without trusting the operator, the model author, or any single jurisdiction. The system replaces "trust the API provider" with "verify the math": a Proof accompanying an (input, output) pair is checked by an on-chain Verifier in bounded time and gas, independent of model size.

Phase-0 deliverable — numbered modules/crates:

  1. cogni-prover — Rust library: loads a quantised model, executes it, drives a zk-SNARK circuit, emits a Proof.
  2. cogni-circuits — the Groth16 circuit for a fixed 4-layer MNIST MLP (Phase 0's only supported architecture).
  3. cogni-types — wire types (InferenceJob, Proof, Receipt, ModelCommitment, NodeIdentity).
  4. cogni-wire — canonical CBOR codec for the above.
  5. contracts/Verifier.sol — the on-chain Groth16 verifier for the MNIST circuit, deployed to a public testnet.
  6. cogni-bench — benchmark harness producing PCR, proof size, and verifier-gas numbers.

System boundaries — provides:

  • Cryptographic proof of correct inference against a committed model.
  • On-chain settlement of fees and rewards.
  • A marketplace for job/operator matching (from Phase 4).
  • Slashing of provably-dishonest operators.

System boundaries — delegates:

  • Model training — out of scope forever, §2.
  • Custody of user funds — non-custodial, wallet-signed only.
  • Fiat on/off-ramp and KYC — delegated to CEX partners, §27 Compatibility & Versioning.

System boundaries — does NOT provide:

  • A general-purpose smart-contract platform. Cogni Chain's programmability is scoped to Verifier, Ledger, Registry, Marketplace, Slasher — never a generic VM.
  • Reputation- or replication-based verification — rejected, P1 §6.
  • Closed-weight model hosting on the public marketplace — rejected, P2 §6.

Non-goals. Verifiable training (a distinct circuit-shape problem, not attempted); a DePIN GPU-rental marketplace with no verification (a strict subset lacking Cogni's differentiator); a general L1.

Deployment model.

  • Phase 0: single-operator devnet on a laptop, proofs submitted to a public testnet contract.
  • Phase 1: multi-operator public testnet on a forked OP Stack L2.
  • Phase 2+: mainnet L2, with an evaluated own-rollup/Arbitrum-Orbit migration (ADR-06, §9).
  • Node operators self-host; there is no Cogni-operated inference backend.

Target users/operators. Node operators (GPU owners staking the protocol token); clients (crypto-native builders, later regulated enterprises and sovereign buyers); model authors (register ModelCommitments, earn a fee split).

Later phases unlock:

  • Plonk transformer circuits — Phase 5, §17.
  • A live marketplace with SLA tiers — Phase 4, §16.
  • Mainnet token — Phase 8, §20.
  • Encrypted inference — Phase 9, §21.
  • 70B-scale folded proofs — Phase 10, §22.
  • Sovereign subnets — Phase 11, §23.

Recommended language + rationale.

  • Rust for prover/node — arkworks/halo2/plonky3 ecosystem gravity; no GC pause during multi-hour proving jobs (ADR-01, §9).
  • Rejected: C++ — no memory safety; the SNARK-library ecosystem has migrated to Rust.
  • Rejected: Go — GC pauses acceptable only for the off-chain matcher, never the prover hot path (ADR-01's "When the Rejected Choice Wins").
  • Solidity for on-chain contracts — largest EVM auditor pool (ADR-05, §9).
  • Rejected: Move — evaluated only for the Phase 11 sovereign-subnet variant.

Prerequisites. Finite-field/elliptic-curve arithmetic; SNARK/STARK arithmetization, PIOPs, polynomial commitments; EVM gas/state model; Byzantine-fault-tolerant gossip networking; token-economic mechanism design; fixed-point numerical computing.

Estimated timeline. Phase 0: 8 weeks. Full system through Phase 11 (sovereign subnets live): ~66 months (Appendix B, §40, sums the per-phase durations).

Why this scope boundary and not a wider or narrower one:

  • Wider (e.g., adding verifiable training in Phase 0) would double the arithmetization surface before the correctness kernel (§12) is even proven — rejected per P13's conformance-before-merge discipline extended to project scope itself.
  • Narrower (e.g., stopping at Phase 2 mainnet with no frontier-scale story) would leave Cogni permanently priced out of the workloads (70B+ models) where verifiable inference matters most competitively (§2's calibration value) — the Phase 10/11 horizon is what makes the bet in §1's opening paragraph coherent, not optional flourish.
  • The boundary is therefore drawn at "one coherent proof-of-cognition protocol, evolving its cryptography in place (ADR-03/04/P10) rather than forking into parallel products" — every phase after Phase 0 extends the same ProofSystem/NodeOperator boundary, never replaces it.

Deferred features (registered in §37, every anchor resolves):

  • PhaseDeferred("§21") — ZK-encrypted-input proving.
  • PhaseDeferred("§23") — Move-language contract port.
  • PhaseDeferred("§20") — custom/own settlement rollup.
  • PhaseDeferred("§22") — quantum-resistant proof-system swap.
  • PhaseDeferred("§19") — mobile Wallet SDK bindings.
  • PhaseDeferred("§22") — sharded verifier instances.
  • PhaseDeferred("§36") — TEE-as-primary trust model.

2. Why Build This

Unique systems knowledge it teaches:

  • Arithmetization of a real neural network into a circuit (matmul, softmax, GELU as constraint systems).
  • EVM gas/precompile economics for pairing-based verification (EIP-196/197).
  • Byzantine-safe stake-slashing mechanism design.
  • Folding-scheme recursion (Nova family) for amortising proof cost.

Why it matters architecturally/historically. Bitcoin made global consensus on ownership possible without a trusted third party by spending useless work (SHA-256). Ethereum extended consensus to arbitrary state transitions, but every node still re-executes every transaction — redundancy, not succinctness. Cogni is the next step in that lineage: consensus on the correctness of computation whose result the verifier cannot cheaply reproduce (a 7B-parameter forward pass), using succinct proofs instead of redundant execution or reputation.

Engineering muscles it builds:

  • Constraint-system design under a hard proof-size/gas budget.
  • Deterministic numerical computing — the same discipline replay-based databases need.
  • Adversarial mechanism design under real economic stake.
  • Multi-language protocol boundary work — Rust prover ↔ Solidity verifier ↔ TS/Python clients.

Cross-links to sibling systems:

  • Shares its settlement-layer problem with any rollup (Optimism, Arbitrum, §33).
  • Shares its stake-slashing problem with any PoS validator set (Ethereum consensus, EigenLayer AVSs, §33).
  • Shares its off-chain-compute-to-on-chain-settlement shape with oracle networks (Chainlink, §9 ADR-23).

Calibration value. If you can explain why Cogni chooses zk-ML over Bittensor's reputational consensus (§33) and can derive the gas/PCR tradeoff at each phase (§34), you hold the same design vocabulary a Risc0, Succinct, or EigenLayer AVS engineer needs.

Why "verifiable inference" and not a different wedge. Three adjacent problems were considered and set aside as the primary wedge, each for a reason worth stating explicitly:

  • Verifiable training — a strictly harder circuit-arithmetization problem (gradient computation graphs are larger and less standardized than forward-pass graphs); attempting it first would have delayed Phase 0's correctness kernel by an unbounded amount with no compounding benefit until inference verification itself was solid.
  • Generic verifiable computation (a zkVM for arbitrary programs) — strictly more general than Cogni needs, and general-purpose zkVMs (risc0, §5 Ref-impl #3) already exist; Cogni's edge is model-specific custom gates (P11), which a generic zkVM by design forgoes for generality.
  • A pure DePIN GPU marketplace with no verification — the easiest to build, but explicitly the anti-goal (§1): it teaches none of the cryptographic engineering muscle this project exists to build, and is already served by Akash/io.net/Gensyn without needing Cogni to exist at all.

What Mastery Looks Like (competencies, each tied to a named phase):

  1. Hand-arithmetize a matmul+activation layer into a constraint count and predict prover wall-clock before writing the circuit (Phase 0, §12).
  2. Explain, with numbers, why a trusted setup is acceptable in Phase 0 but a liability by Phase 10 (Phase 0 §12, Phase 10 §22).
  3. Design a slashing condition that is falsifiable purely on-chain, with no human vote (Phase 6, §18).
  4. Budget verifier gas against an L2's block gas limit and know which knob (custom gates, recursion, lookup arguments) to pull next (Phase 5 §17, Phase 7 §19).
  5. Distinguish "prover-bound" from "operator-count-bound" from "gas-bound" scaling regimes from the Capacity Model alone (§34).
  6. Design a P2P job marketplace that degrades to a permissionless fallback under matcher censorship (Phase 4, §16).
  7. Reason about restaking-based bootstrap security (EigenLayer pattern) versus native-token-only security and state exactly when each wins (Phase 6 §18, §33).
  8. Specify a cross-chain checkpoint anchor without inventing a new bridge trust model (Phase 11, §23, §9 ADR-23).

Boxes, one paragraph each:

  • Client. Signs jobs, never trusts the network's word — re-verifies locally via the Wallet SDK's WASM verifier core.
  • Marketplace. Off-chain sealed-bid matcher; censorship-resistant fallback is the on-chain order log, so no single matcher is a liveness dependency.
  • Cogni Node. The untrusted-host boundary — runs on hardware the protocol does not control, defended by the proof plus slashable stake, never by reputation.
  • Cogni Prover. Produces the proof; the chain never trusts the binary, only the proof it emits (I1–I4, §7).
  • Cogni Chain. The actual root of trust — if Verifier accepts, the protocol treats the inference as correct, full stop.
  • Explorer/Wallet SDK. Trusted only by the end user, never by the chain; ships the same verification logic as the on-chain verifier so a user never takes the Explorer's word for anything.

6. Design Principles

  1. P1 — Cryptographic verification is the only verification.
    • Rule: no reputation systems, no replication-based consensus.
    • Tradeoff: forfeits the fast-to-market flexibility of reputational networks (§33 Bittensor).
    • Operational implication: every new model architecture blocks on a circuit, not a policy.
    • Violation breaks: Cogni becomes indistinguishable from a DePIN network with a token bolted on.
  2. P2 — Open weights only on the public marketplace.
    • Rule: ModelCommitment is a public merkle root; closed weights may run privately but never register publicly.
    • Tradeoff: excludes closed-weight frontier labs from the public marketplace.
    • Operational implication: Registry.register() rejects unlicensed submissions (I14, license check).
    • Violation breaks: no one can audit the commitment, destroying the differentiator vs. centralized APIs.
  3. P3 — No trusted intermediaries in the proof path.
    • Rule: the on-chain Verifier is the final arbiter — no watchtower fraud-proof window, no censoring sequencer.
    • Tradeoff: forecloses the optimistic-rollup path (§36 Alt 1).
    • Operational implication: every censorship-risk surface needs a permissionless fallback (§16 order log).
    • Violation breaks: settlement latency becomes hostage to a challenge window.
  4. P4 — Operator software is open source, reproducibly built.
    • Rule: Nix-pinned toolchain (ADR-22), no closed-source prover binaries.
    • Tradeoff: slower iteration than closed binaries.
    • Operational implication: SBOM published per release (§29).
    • Violation breaks: a class of operator becomes un-auditable, un-slashable for bugs it cannot see.
  5. P5 — Stake-weighted, not GPU-weighted, rewards.
    • Rule: block rewards scale with verified work under bonded stake.
    • Tradeoff: a well-capitalized operator cannot buy dominance by GPU count alone.
    • Operational implication: reward computation reads NodeIdentity.stake, never raw hardware count.
    • Violation breaks: small operators are drowned out, centralizing the network.
  6. P6 — The token is a means, not an end.
    • Rule: mechanical emission (§20 N.2); no discretionary issuance.
    • Tradeoff: slower fundraising optionality.
    • Operational implication: every mint call is checked against EmissionSchedule (§8.3).
    • Violation breaks: the protocol becomes a pump-and-dump vehicle indistinguishable from any other L1 token.
  7. P7 — Sovereign-neutral by design.
    • Rule: no protocol-level dependency on any one jurisdiction's infrastructure.
    • Tradeoff: higher coordination cost bootstrapping global operators.
    • Operational implication: validators/operators geographically distributed from mainnet day one.
    • Violation breaks: R (regulatory) risk concentrates in one jurisdiction that can then unilaterally kill the network.
  8. P8 — Soundness > liveness > throughput, strictly ordered.
    • Rule: when the three conflict, choose in that order.
    • Tradeoff: the network will pause rather than risk an unsound proof passing (§26).
    • Operational implication: the Soundness Bug Response Playbook (§26) takes precedence over any uptime SLO.
    • Violation breaks: a fast, always-live network that occasionally accepts a wrong proof is worse than a slow, correct one.
  9. P9 — Determinism is mandatory in the proven path.
    • Rule: fixed-point only (I8/I9); native floating point forbidden in circuits.
    • Tradeoff: quantisation accuracy loss vs. FP32.
    • Operational implication: the determinism harness (§13) gates every circuit release.
    • Violation breaks: two honest operators diverge and one gets wrongly slashed (T4, §24).
  10. P10 — The proof system is swappable behind a ProofSystem trait boundary.
    • Rule: no hard dependency on one primitive across phases (§9 ADR-03/04).
    • Tradeoff: an abstraction layer the fastest possible Phase-0 hack would skip.
    • Operational implication: CircuitId binds a model to exactly one proof system at registration (§22.8).
    • Violation breaks: every proof-system upgrade becomes a hard fork of the node software.
  11. P11 — Verifier gas is independent of model size (succinctness is non-negotiable).
    • Rule: a 7B model's verify call costs the same order of magnitude as a 1B model's.
    • Tradeoff: forces custom gates/lookup arguments earlier than a naive circuit would need.
    • Operational implication: I4's gas-ceiling CI gate blocks any regression.
    • Violation breaks: the chain cannot afford to verify frontier-scale inference at all.
  12. P12 — Every protocol-parameter change is an ADR.
    • Rule: no silent drift of slashingMultiplier, slashWindow, emission curve.
    • Tradeoff: bureaucratic overhead on a solo-founder team.
    • Operational implication: docs/adr/ is the single source of truth for every locked parameter.
    • Violation breaks: post-mortems cannot reconstruct why a parameter is what it is.
  13. P13 — Conformance before merge.
    • Rule: no circuit/verifier pair ships without the negative-test suite (§28) passing.
    • Tradeoff: slower phase velocity.
    • Operational implication: CI blocks merge on any conformance regression.
    • Violation breaks: a soundness bug ships to mainnet undetected.
  14. P14 — Receipts are additive-only once locked.
    • Rule: a Receipt field, once shipped, is never removed or repurposed (§27).
    • Tradeoff: schema bloat over years.
    • Operational implication: new fields are always Option<T> until proven universal.
    • Violation breaks: old receipts become unparseable, breaking auditability — the entire point of the network.

Debugging methodology.

  • Every invariant must hold or fail loudly — the simulator never allows a silent violation to pass unlogged.

8. Domain Model

8.1 Protocol State Machine (Job Lifecycle FSM)

Posted --bid(sealed)--> Bidding --award(lowest SLA-meeting bid)--> Awarded
Awarded --execute()--> Executing --submit(Receipt)--> ReceiptSubmitted
ReceiptSubmitted --Verifier.verify()==true--> Verified --Ledger.settle()--> Settled
ReceiptSubmitted --Verifier.verify()==false--> Rejected --Slasher.slash()--> Slashed
Awarded --deadline exceeded, no Receipt--> Expired --escrow refunded--> Refunded

Transition table:

  • Posted → Bidding — any staked operator with the model loaded may bid (I6).
  • Bidding → Awarded — Marketplace picks the lowest SLA-meeting bid.
  • Awarded → Executing — operator loads ModelCommitment, runs NodeOperator::execute.
  • Executing → ReceiptSubmitted — signed Receipt broadcast (I13).
  • ReceiptSubmitted → {Verified, Rejected} — deterministic (I3).
  • Verified → Settled — exactly once (I11).
  • Rejected → Slashed — mechanical, no vote (I10).

8.4 Quantisation and Determinism Rules

  • All operators MUST use the fixed-point representation declared in ModelCommitment.quantisation (I8); native FP is forbidden in proven paths (P9).
  • Reduction order (e.g., matmul summation) MUST follow the canonical order baked into the circuit (I9); parallel reductions MUST use a deterministic tree.
  • Non-arithmetic ops (softmax, GELU, layernorm) use lookup tables registered at circuit-compile time; an operator using a different table cannot produce a valid proof.

8.5 Worked Example (Phase 0 trace, concrete numbers)

  • Client posts InferenceJob{input: 784-byte MNIST image, model_commitment: 0x7a3f..., max_fee: 50 units, sla_tier: BestEffort, deadline: now+120s}.
  • One operator (self, Phase 0 devnet) bids Quote{price: 40}. Awarded.
  • Operator loads the committed 4-layer INT8 MLP, runs inference (raw wall-clock 1 ms), drives the Groth16 prover (measured 1.1 s ⇒ PCR ≈ 1100x, inside the Phase 0 kill-criterion band of §4).
  • Broadcasts Receipt{output: one-hot digit "2", proof: 192-byte Groth16 proof, ...}.
  • Verifier.verify() returns true in 4 ms wall-clock, ≈ 230,000 gas.
  • Ledger.settle() pays 40 units, releases escrow (I11).

8.6 Malformed-Input Example

  • Client posts input of 50,000 bytes against a SchemaId declaring 784 bytes.
  • Marketplace rejects at intake (limits().maxInputBytes check, §11) before any operator bids — no wasted GPU-hours.
  • Telemetry: oversize_job_rejected_total.

8.7 Failure-Path Example

  • A malicious operator flips one output bit (output' ≠ output) hoping the verifier is lax.
  • Verifier.verify(commitment, input, output', proof) returns false because proof.public_inputs_hash was computed over the original output (I1) — the corrupted output re-hashes to a different value than the proof attests.
  • ReceiptSubmitted → Rejected → Slashed (I10); stake burned per SlashingPolicy.
  • Telemetry: slash_executed_total increments.
  • Forensic artifact: the mismatched (output', proof) pair is retained for the postmortem (§25 FM-5).

8.8 Node Operator Behavioral Contract

Every NodeOperator implementation (§11) carries obligations layered on top of the trait signature, gated by the conformance suite (§8.9) and release-blocking per P13:

  • Determinism: two operators running the same model on the same input MUST produce byte-identical outputs, within the fixed-point quantisation rules of §8.4 (I9).
  • No side-channel exfiltration: the operator SHOULD NOT log inputs in plaintext when the client requested encryption; Phase 9 (§21) introduces TEE-attested operators to make this a hard guarantee rather than a SHOULD.
  • Stake bond: the operator MUST maintain stake ≥ job.maxFee × slashingMultiplier to bid on a job (I6); the chain enforces this at quote time, not after the fact.
  • Honest unstaking: an operator leaving the network MUST broadcast an unbond_request; stake unlocks only after slashWindow (I7, 14-day default) so recent proofs remain challengeable.
  • Truthful advertisement: supported_models() MUST list only models the operator has genuinely loaded — bidding on an unloaded model is a slashable false advertisement (T11-adjacent, closed by I10's on-chain-proof requirement).
  • Health honesty: health() MUST reflect true GPU/queue state; a non-responsive operator (>100 ms, §4) is dropped from the marketplace's active set, not silently retried forever.

8.9 Verifier Conformance Suite

Every verifier instance (one per registered CircuitId, §11) ships with a fixed conformance suite that must pass before the instance is eligible for mainnet traffic (P13):

  • 1,000 valid (input, output, proof) triples accepted (baseline established in conformance/mnist_valid.json, §12.5, and re-derived per circuit in later phases).
  • 1,000 adversarial (input, output', proof) triples — output corrupted — rejected (I1, §8.7).
  • 1,000 model-substitution attacks — commitment of model A, prover ran model B — rejected (I1, I14, T3).
  • Verification gas measured below the documented ceiling for that phase (§4, §30 M-table).
  • Cross-implementation interoperability: a proof from prover implementation X verifies under verifier implementation Y for at least two independent implementations (T6 mitigation).

Conformance failure is release-blocking (P13) — no circuit/verifier pair reaches the stable release channel (§29) without a clean run recorded in docs/performance/.

8.10 Marketplace Sealed-Bid Worked Example (Phase 4 trace)

  • Client posts a Standard-tier InferenceJob with max_fee: 200, deadline: now+60s.
  • Three operators submit sealed commit-hashes of their bids within the commit window (§16.2); none can see the others' prices yet, closing the VEV vector T12 describes.
  • At the reveal deadline, bids of 150, 180, and 220 units are revealed; the 220-unit bid exceeds max_fee and is discarded, the 150-unit bid wins (lowest SLA-meeting bid, §8.1's Bidding → Awarded transition).
  • The losing 180-unit bidder's reveal is simply unused — no penalty, since revealing honestly (even when losing) is never punished, only failing to reveal after committing is (§16.6).
  • Awarded transitions to Executing; the rest of the trace matches §8.5's single-operator case from that point on.

12. Phase 0 — Repo Skeleton & Correctness Kernel

12.1 Objectives

  • Stand up the monorepo skeleton (§10).
  • Prove the correctness kernel end-to-end: one fixed circuit (4-layer INT8 MNIST MLP, Groth16/BN254), one operator, one testnet verifier contract.
  • No networking, no marketplace, no token — those are later phases.
  • Constraint introduced: circuit must fit comfortably under the Phase 0 gas kill-criterion (§4).

12.2 Detailed Implementation Steps

  • Implement cogni-types (InferenceJob, Proof, ModelCommitment, Receipt per §11) and cogni-wire CBOR codec (RFC 8949, §5 RFCs).
  • Train and export the MNIST MLP; quantise to INT8 (I8, P9) — no native floats in the proven path (P9).
  • Hand-write the Groth16 circuit (arkworks; ADR-01, ADR-03) following Thaler's arithmetization cost model (§5 Books #1) and the Groth (2016) construction (§5 Papers #1).
  • Generate the Solidity Verifier.sol (ADR-05) implementing ICogniVerifier (§11); deploy to a public testnet.
  • Build cogni-sim's first assertions for I1–I4, I8, I9.
  • Build cogni-bench to measure PCR, proof size, verifier gas.

12.3 Deliverable

  • One repository, one Dockerfile, make demo producing an end-to-end proof + on-chain verification on a public testnet in < 10 minutes on a single laptop.
  • A published benchmark report (PCR, proof size, verifier gas, per-hardware-class numbers).

12.4 Acceptance Criteria

  • Verifier gas per proof < 500,000 (hard ceiling, §4).
  • PCR measured and ≤ 1000x (else the Phase-0 kill criterion fires).
  • 1,000/1,000 valid triples accepted in conformance/mnist_valid.json.
  • 1,000/1,000 corrupted-output triples rejected in conformance/mnist_corrupt.json.
  • Bit-exact determinism across ≥ 2 host machines (I9).

12.5 Conformance Fixtures

  • conformance/mnist_valid.json — 1,000 (input,output,proof) triples, expect verify()==true.
  • conformance/mnist_corrupt.json — same inputs, flipped output bit, expect verify()==false (I1).
  • conformance/mnist_substitution.json — proof from a different trained model against the original commitment, expect verify()==false (I1, T3).
  • conformance/mnist_replay.json — resubmission of an already-settled Receipt, expect revert (I5).

12.6 Pitfalls

  • Native-float creep in the reference PyTorch export causing quantisation drift undetected until Week 3 — debug via the 1,000-image determinism harness (I9); signal: nonzero determinism_divergence_total.
  • Under-provisioned MSM windowing making the prover 10x slower than expected — root cause: naive scalar multiplication instead of Pippenger (§5 Ref-impl #2).
  • Trusted-setup toxic-waste mishandling — mitigated by discarding ceremony randomness immediately and documenting the procedure (T2, §24).
  • Circuit constraint miscounts discovered only at compile time — mitigate by budgeting constraint count on paper first (Thaler cost model, §5 Books #1) before writing gates.
  • Silent CBOR schema mismatch between cogni-wire's encoder and a hand-rolled decoder in cogni-bench — mitigated by generating both from the same cogni-types definitions rather than hand-maintaining a second copy.

12.7 Performance Concerns

  • Prover is CPU-bound at this scale; matmul constraint count dominates wall-clock.
  • Batching (batch=1 only in Phase 0) is not yet relevant; GPU acceleration deferred to Phase 7.
  • Witness-generation allocation churn — reuse arena allocators to avoid allocation-bound stalls even without a GC.

12.8 Edge Cases

  • Malformed CBOR input (truncated bytes) — codec must reject, not panic.
  • Zero-length image input — schema validation rejects before circuit invocation.
  • Clock skew between operator and testnet block timestamp — deadlines use block timestamp (ADR-19), not local wall-clock.
  • Duplicate ModelCommitment registration attempt for an already-registered hash — Registry must reject idempotently, not error ambiguously.
  • A witness that satisfies the circuit's constraints but was generated from a different input than the one hashed into public_inputs_hash — must be caught by I1's binding check, not assumed impossible because "the prover wouldn't do that."

12.9 Failure Analysis

  • Trusted-setup ceremony compromise (T2) — blast radius: any proof for the MNIST circuit could be forged; containment: single-circuit blast radius (Phase 0 has one circuit); recovery: re-run ceremony, re-deploy verifier, invalidate old commitment.
  • Prover crash mid-proof (FM-3) — detection: cogni-bench timeout; recovery: retry with fresh witness, no partial-proof state to corrupt (proofs are atomic).

12.10 Operational Notes

  • Structured logging via tracing (ADR-16) from day one, even solo — establishes the log-shape every later phase reuses.
  • Metrics: prover_wall_clock_seconds, verifier_gas_used, proof_size_bytes.
  • No rollback needed — no persistent state yet beyond the testnet contract, which is redeployable.

13.1 Objectives

  • Harden Phase 0's single circuit into a reusable circuit-library pattern.
  • Close the determinism gap (I9, P9) with an automated harness before any second circuit is attempted.
  • Constraint: no new proof system yet (still Groth16) — this phase is about correctness discipline, not scale.

13.2 Detailed Implementation Steps

  • Build the 1,000-random-image determinism harness comparing proven output against reference PyTorch bit-exact (I9; Kleppmann's consistency vocabulary, §5 Books #5, applied here).
  • Ratify the canonical deterministic reduction order for matmul summation (I9) and lock it into cogni-circuits' lookup-table generation.
  • Build the negative-test harness (corrupted output, model-substitution) as permanent CI gates (P13), not one-off scripts.
  • Extract cogni-circuits into a per-architecture module boundary (mnist-mlp/ today, transformer-1b/ etc. later) so Phase 5 doesn't require restructuring.

13.3 Deliverable

  • A CI-gated determinism + negative-test suite that blocks merge on any divergence.
  • A documented canonical reduction-order spec, feeding §8.4's quantisation rules.

13.4 Acceptance Criteria

  • Zero divergences across 1,000 images on ≥ 3 distinct host architectures (x86, ARM/M-series, one cloud VM).
  • Negative-test suite catches 100% of injected corruption/substitution mutants in conformance/mnist_mutants.json (≥ 200 mutants).
  • CI gate blocks merge on any single divergence (I9).

13.5 Conformance Fixtures

  • conformance/mnist_mutants.json — 200 systematically generated output/proof mutants, expect 100% rejection.
  • conformance/determinism_hosts.json — same 1,000 images run on 3 host classes, expect identical hashes.

13.6 Pitfalls

  • Parallel-reduction non-determinism: naive multi-threaded summation reorders fixed-point rounding — root cause traced via bisection on thread count; fix is the canonical deterministic tree (I9).
  • GPU vs. CPU divergence surfacing only under specific batch shapes — signal: determinism_divergence_total spikes only on the GPU CI runner, not CPU.
  • Assuming determinism "just works" from fixed-point alone without also fixing reduction order — the two are separate requirements (I8 vs. I9).
  • Compiler/optimizer reordering floating-intermediate operations differently across Rust toolchain versions even before quantisation — mitigated by pinning the toolchain (ADR-22) and re-running the full determinism suite on every toolchain bump, not just every circuit change.

13.7 Performance Concerns

  • The determinism harness itself is now the CI bottleneck (1,000 images × N host classes).
  • Mitigate by sampling 100 images per PR and running the full 1,000 nightly, trading latency for coverage cadence.

13.8 Edge Cases

  • Denormalized fixed-point values at the INT8 boundary (-128 edge) — must round consistently, not saturate inconsistently across implementations.
  • A ModelCommitment with param_count of zero (malformed) — Registry must reject at I14, not merely at circuit-load time.
  • A determinism-suite host that silently uses a different BLAS/linear-algebra backend than the other two — must be pinned and asserted at harness startup, not discovered mid-run as an unexplained divergence.

13.9 Failure Analysis

  • A determinism divergence in production would silently mis-slash an honest operator — this phase exists specifically to make that impossible pre-mainnet.
  • Detection: determinism_divergence_total alert.
  • Recovery: quarantine the divergent operator binary version, do not slash until root-caused (P8 soundness priority).

13.10 Operational Notes

  • Publish the reduction-order spec in docs/threat-model/ cross-referenced from I9; every future circuit module must cite it.
  • Dashboard: divergence rate per host class, per circuit.

15.1 Objectives

  • Turn the CLI-driven prover into a long-running daemon (cogni-node) with p2p discovery, replacing manual job submission with a live network.
  • Constraint: must tolerate adversarial churn per libp2p gossipsub defaults tuned in §4.

15.2 Detailed Implementation Steps

  • Implement cogni-node wrapping NodeOperator (§11) with libp2p (ADR-07; Rust-for-Rustaceans async patterns, §5 Books #6) gossipsub for job announcement and Kademlia for peer discovery (§5 Ref-impl #5).
  • Implement persistent stake state that survives daemon restart.
  • Implement the health() probe (§4: <100ms).
  • Implement bounded per-peer queues (ADR-20, backpressure).
  • Onboard 3 external operators (paid testers) as the first non-self-hosted validation of P4 (open-source, reproducible builds).

15.3 Deliverable

  • A cogni-node binary, Nix-built reproducibly (ADR-22), running continuously with structured telemetry.
  • 3 external operators sustained for 7 consecutive days.

15.4 Acceptance Criteria

  • health() responds within 100 ms p99 (§4, M7 in §30).
  • Gossip mesh maintains D=6–12 peers under simulated 20%-node churn over 1 hour (conformance/gossip_churn.json).
  • Zero FD-exhaustion incidents across 3 operators over 7 days (FD budget 4,096, §4).

15.5 Conformance Fixtures

  • conformance/gossip_churn.json — 20% random peer disconnect/reconnect over 1 hour simulated, expect mesh recovers to D≥6 within 30 s.
  • conformance/health_probe_timeout.json — probe under synthetic GPU-saturation load, expect response within 100 ms or explicit unhealthy status (never a hang).

15.6 Pitfalls

  • Default gossipsub mesh degree too low under adversarial churn (§5 Ref-impl #5's named pitfall) — signal: job-announcement propagation p95 degrading past §4's budget; fix: raise D_lo/D_hi explicitly, don't trust defaults.
  • Persistent stake state corruption on ungraceful shutdown — mitigated by a write-ahead state file with fsync before daemon-exit acknowledgment.
  • Assuming libp2p's defaults are production-ready without load-testing under adversarial conditions specific to this workload.
  • Kademlia routing-table poisoning by a burst of short-lived Sybil peer IDs — mitigated by the same stake-floor identity binding (I6) that closes T10 at the marketplace layer, reused here at the network layer.

15.7 Performance Concerns

  • Gossip propagation latency at low operator count is dominated by per-message signature verification, not bandwidth — profile CPU before assuming network RTT is the bottleneck.

15.8 Edge Cases

  • Split-brain: two daemon instances sharing the same NodeIdentity key (operator error) — must be detected via duplicate-identity gossip announcement and refused, not silently double-bid (I6 violation risk otherwise).
  • Clock skew between operators affecting health() timestamps — use monotonic clock locally (ADR-19), only compare durations, never absolute wall time across hosts.
  • Peer connection starvation when every discovered peer is behind a restrictive NAT — must fall back to a bootstrap relay rather than reporting a false "healthy, zero peers" state.

15.9 Failure Analysis

  • P2P network partition (FM-7, §25) — detection: gossip peer-count drop; containment: partitioned operators simply stop receiving jobs (no incorrect state, just reduced throughput); recovery: automatic reconnection via Kademlia bootstrap once partition heals.

15.10 Operational Notes

  • Metrics: gossip_peer_count, gossip_mesh_degree, health_probe_latency_ms.
  • Runbook docs/runbooks/node-restart.md covers graceful vs. crash restart semantics.
  • Rolling upgrade: nodes advertise a protocol-version in gossip handshake; mixed-version meshes tolerated for one minor version (§27).

16.3 Deliverable

  • A live testnet marketplace where any Phase-3 operator can bid, get awarded, execute, and settle a job without intervention.
  • The on-chain order log usable directly by a client if the off-chain matcher is unavailable.

16.4 Acceptance Criteria

  • Marketplace fill p95 < 30 s for Standard tier (§4) measured over 500 testnet jobs.
  • Commit-reveal auction resists a scripted front-running bot in conformance/vev_frontrun.json (bot gains zero informational edge).

  • conformance/vev_frontrun.json — scripted bot attempts to front-run a sealed bid, expect commit-reveal prevents information leakage pre-reveal.
  • conformance/matcher_down.json — off-chain matcher process killed, client posts directly to on-chain order log, expect job still fills (P3).

16.6 Pitfalls

  • Sealed-bid reveal-phase griefing — an operator commits then never reveals, stalling the auction — mitigated by a reveal-deadline forfeit (bidder's minimal bond is burned, not the full stake).
  • SLA-tier misclassification — a client claims Premium but the marketplace can't find a sub-5s-capable operator — must degrade gracefully to Standard with an explicit warning, never silently downgrade.
  • Off-chain matcher and on-chain order log disagreeing about which bid won (a matcher bug, not malice) — mitigated by the on-chain award transaction being the sole source of truth; the matcher's role is proposal, never final say.

16.7 Performance Concerns

  • Off-chain matcher throughput at Postgres-backed order matching — index on (sla_tier, deadline) to keep matching O(log n), not O(n) linear scan, as job volume grows toward Phase 8's 500-operator target.

16.8 Edge Cases

  • Two operators submit identically-priced sealed bids — tie-break must be deterministic and unpredictable pre-reveal (randomised via commit-hash ordering, never operator-ID ordering, to prevent gaming).
  • Deadline expires mid-auction before any reveal — job transitions to Expired/Refunded (§8.1), escrow returned to client.
  • A client cancels a job after Awarded but before Executing — the operator's escrowed opportunity cost must be compensated by a documented cancellation fee, never left as an unrecoverable operator loss.

16.9 Failure Analysis

  • Marketplace matcher censorship (E8/T-class) — detection: client observes their job never gets matched despite eligible bidders; recovery: client posts directly to the on-chain order log (P3 structural defense, not a patch).

16.10 Operational Notes

  • Metrics: marketplace_fill_latency_seconds (histogram, per SLA tier), matcher_uptime_ratio.
  • Multiple matcher implementations may run concurrently (ADR-08); no single matcher is an SPOF by design.

18.1 Objectives

  • Implement the optional restaking hook (ADR-24) allowing Ethereum-denominated stake to back NodeIdentity.stake during bootstrap.

18.3 Deliverable

  • A slashing pipeline drilled on testnet with real (testnet) token burn.
  • A restaking integration allowing an operator to bond via EigenLayer-style delegation as an alternative to native-token-only stake.

18.4 Acceptance Criteria

  • 100/100 deliberately-injected invalid-proof attempts result in a slash within 1 epoch (~10 min, §30 M10) of submission.
  • Unbonding stake remains slashable through the full 14-day slashWindow in conformance/slash_during_unbond.json.
  • Restaking hook passes an integration test against a local EigenLayer-style mock delegation contract.

18.5 Conformance Fixtures

  • conformance/slash_invalid_proof.json — 100 deliberately corrupted receipts, expect 100% slash within 1 epoch.
  • conformance/slash_during_unbond.json — misbehaviour proof submitted during the unbond window, expect slash still executes (I7).

18.6 Pitfalls

  • A slashing-rule bug that fires on a false positive (e.g., a legitimate GPU-driver nondeterminism misclassified as cheating) — root cause traced back to Phase 1's determinism harness gaps; mitigated by requiring the Phase-1 conformance suite to have zero known divergences before Phase 6 ships, a hard dependency.
  • Restaking slashing-condition double-counting — a single misbehaviour must not trigger both native-stake slash and restaked-collateral slash without an explicit, documented policy.
  • A slashing drill that only tests the "obvious" invalid-proof path and never a double-sign-same-JobId path — both are I10 triggers and both need independent drill coverage before the phase's Definition of Done is declared.

18.7 Performance Concerns

  • Slash-detection-to-execution latency (M10, §30) is bound by L2 block time, not computation — the check itself is O(1) given Verifier.verify() already ran; the bottleneck is settlement finality, not the slashing logic.

18.8 Edge Cases

  • An operator's stake drops below the I6 floor during an in-flight job due to an unrelated slash on a different job — the in-flight Receipt's settlement (I11) must still complete; only future bids are blocked by the new insufficient-stake state.
  • Simultaneous slash triggers from two different jobs on the same operator in the same block — must not double-process the same underlying stake reduction.
  • A restaked operator's underlying restaking protocol itself pauses or gets slashed for an unrelated AVS fault — Cogni's Slasher must treat this as a stake-availability event, not silently assume the collateral is always liquid (§9 ADR-24).

18.9 Failure Analysis

  • A slashing-logic bug (FM-5, §25) that over-slashes — detection: operator complaint + on-chain event audit; recovery: governance-free technical remediation only (P1 — no majority-vote reversal of a mechanical slash is permitted; the fix is a patched contract plus a treasury-funded make-whole for provably-erroneous slashes, documented in the postmortem).

18.10 Operational Notes

  • Metrics: slash_executed_total{reason}, restake_delegation_active_gauge.
  • Runbook docs/runbooks/slash-dispute-review.md for postmortem-driven make-whole decisions (never live-vote reversal, P1).

19.3 Deliverable

  • A GPU-accelerated cogni-prover backend measured against the CPU baseline.
  • A 7B-parameter ModelCommitment verified end-to-end on testnet within the single-consumer-GPU hardware floor.

19.4 Acceptance Criteria

  • conformance/recursive_batch_4.json — 4 jobs folded into one verifier call, expect gas < 4x single-proof gas.

  • Continuation-boundary overhead assumed free (the named §5 Ref-impl #3 pitfall from risc0/risc0) — recursion has real per-fold cost; budget it explicitly rather than assuming linear scaling.

  • Assuming CUDA and Metal backends produce bit-identical witness values without re-running the full I9 determinism suite on both — a GPU vendor's fused-multiply-add rounding behavior can differ subtly between backends.

19.7 Performance Concerns

  • GPU utilization target ≥ 70% during proving (M11, §30) — under-utilization signals a CPU-bound witness-generation bottleneck upstream of the GPU kernel, not a GPU capacity problem; profile before purchasing more GPU capacity.

19.8 Edge Cases

  • A 7B model just over the 24 GB VRAM floor (e.g., a slightly larger checkpoint) — must fail gracefully with an explicit ExecError so quote() correctly reports non-support rather than silently accepting and later failing.
  • Mixed-precision drift between CUDA and Metal backends — must pass the same I9 determinism suite across both.
  • A recursive batch where one of the 4 constituent jobs has a malformed proof — the whole batch's verifier call must fail atomically and identify which sub-proof failed, not silently accept the other 3.

19.9 Failure Analysis

  • GPU OOM mid-proof (FM-3, §25) — detection: prover process exit code; containment: job returns to Awarded state for re-bid by another operator, no partial-proof corruption (proofs are atomic, §12.9); recovery: operator's quote() logic adjusted to pre-check VRAM headroom before bidding.

19.10 Operational Notes

  • Metrics: gpu_utilization_pct, gpu_oom_total, recursive_batch_size_gauge.
  • Deployment note: operators advertise hardware_class (§11) so the marketplace can route 7B jobs only to VRAM-sufficient bidders.

  • Implement TEE-attested operator variants that decrypt inside the enclave, run inference, and produce a remote-attestation quote alongside the standard Proof — dual-attestation: cryptographic proof of correctness plus hardware attestation of confidentiality.
  • Extend the Wallet SDK (§10) to verify both the proof and the attestation quote.

21.3 Deliverable

  • An operator hardware class (TeeAttested) live on mainnet capable of accepting encrypted InferenceJobs.
  • Wallet SDK support for dual-verification (proof + attestation).

21.4 Acceptance Criteria

  • 100/100 encrypted jobs in conformance/tee_encrypted_valid.json produce a valid Proof and a valid, non-revoked attestation quote.
  • Attestation-quote revocation (simulated compromised enclave) is detected and the operator's TeeAttested class is suspended within 1 hour (§4 RTO-adjacent budget).
  • Zero plaintext-input leakage detected in conformance/tee_no_plaintext_log.json.

21.5 Conformance Fixtures

  • conformance/tee_encrypted_valid.json — 100 encrypted jobs through a TEE-attested operator, expect proof + attestation both valid.
  • conformance/tee_no_plaintext_log.json — audit of operator logs for plaintext leakage, expect zero occurrences (P4's "SHOULD NOT log inputs in plaintext" obligation, tightened here).

21.6 Pitfalls

  • Single-vendor hardware trust root (Intel) — a documented, un-mitigated limitation (see §36 Alternative Architecture 3's rejection reasoning) — operators and clients must be explicitly informed TeeAttested is an auxiliary, not primary, trust mechanism.
  • Attestation-quote replay — mitigated by binding the quote to the specific JobId and a fresh nonce per job.
  • Conflating "encrypted" with "verified" — a TeeAttested operator's attestation proves confidentiality, not correctness; the zk Proof (I1–I4) is still mandatory and must never be treated as optional just because the job was encrypted.

21.7 Performance Concerns

  • Enclave context-switch overhead adds latency versus a non-TEE operator — must be budgeted separately in the Premium SLA tier's latency accounting, not silently absorbed into the same p95 target as non-TEE jobs.

21.8 Edge Cases

  • Enclave attestation service outage (Intel's attestation service itself unavailable) — operator must fail closed (refuse the job, not silently downgrade to unencrypted execution).
  • Client encryption key rotation mid-job — job must use the key pinned at InferenceJob signing time, never a rotated key.
  • A TeeAttested operator that is also a Datacenter-class GPU host reporting only one of the two hardware attributes — the marketplace's routing logic must treat hardware_class as potentially multi-valued, not a single enum choice, or Premium/TEE-required jobs may be mis-routed.

21.9 Failure Analysis

  • A disclosed side-channel vulnerability against the underlying CPU family (an industry-wide SGX/TDX vulnerability class) — detection: vendor security bulletin; recovery: suspend the TeeAttested hardware class network-wide pending patched microcode, falling back to standard zk-ML-only operators for affected clients (graceful degradation, not a full network halt — P8 liveness preserved for the non-TEE majority).

21.10 Operational Notes

  • Metrics: tee_attestation_valid_total, tee_attestation_revoked_total.
  • Runbook docs/runbooks/tee-vendor-advisory-response.md for coordinated response to a disclosed hardware vulnerability.

22. Phase 10 — Folding Schemes & Frontier-Scale (70B) Inference

22.1 Objectives

  • Migrate to STARKs + folding (Nova family, ADR-04) and lookup arguments (Lasso/Jolt).
  • Reach 70B-parameter verified inference within the §4 cost targets, retiring the trusted-setup dependency entirely (T2 structural mitigation).

22.2 Detailed Implementation Steps

  • Adopt Nova → SuperNova → HyperNova folding (Kothapalli/Setty/Tzialla, §5 Papers #4) to amortise prover cost across many small recursive steps, applying the Capacity Model's derivation (§34 item 2) to size the fold count.
  • Adopt Lasso/Jolt lookup arguments (§5 Papers #5/#6) to collapse non-arithmetic ops (softmax, GELU, layernorm) to near-constant cost, closing the O(n²) attention gap flagged in Phase 5 (§17.7).
  • Migrate all active circuits off Plonk's trusted setup onto the transparent STARK shell; Halo2 remains supported for legacy receipts only (§27).

22.3 Deliverable

  • A 70B-parameter ModelCommitment verified end-to-end on mainnet using the folded STARK pipeline.
  • The trusted-setup dependency fully retired for all newly-registered circuits.

22.4 Acceptance Criteria

  • 70B-model PCR ≤ 10x (§4 phase gate).
  • Proof size < 50 KB (§4).
  • Verifier latency p95 < 200 ms unchanged despite the 70x parameter-count increase over Phase 7, evidencing P11 succinctness held under folding.
  • Zero active circuits depending on a trusted setup at phase close, verified via conformance/no_trusted_setup_audit.json.

22.5 Conformance Fixtures

  • conformance/70b_folded_valid.json — 100 valid 70B-model proofs via the folded pipeline.
  • conformance/no_trusted_setup_audit.json — automated scan of all registered CircuitIds' proof systems, expect zero Groth16/legacy-Plonk entries among newly-registered commitments.

22.6 Pitfalls

  • Lookup-table size explosion with unconstrained ranges (the named §5 Ref-impl #4 pitfall from a16z/jolt) — mitigated by explicit range constraints on every non-arithmetic op's input domain, derived from the model's known quantisation bounds (I8).
  • Fold-count miscalibration causing prover memory blowup — mitigated by the §34 item 2 capacity derivation gating the fold schedule, not an arbitrary constant.
  • Treating the STARK migration as retiring all trusted-setup risk network-wide when legacy Halo2 circuits (for old receipts, §27) remain live — T2 still applies to any circuit still accepting new registrations under the old system, so the audit in conformance/no_trusted_setup_audit.json must scope to newly-registered commitments specifically.

22.7 Performance Concerns

  • Folding trades prover memory for prover time in a tunable way — profile the memory/time Pareto frontier explicitly per model size rather than hard-coding one fold schedule for all of 1B/7B/70B.

22.8 Edge Cases

  • A model registered under the legacy Plonk pipeline attempting a folded-STARK proof — must be rejected at the ProofSystem trait boundary (P10) since CircuitId binds a model to one proof system at registration time, never silently reinterpreted.
  • Fold-step verification failure at step k of n — must localize the failure to the specific step for debugging, not just report "proof invalid" for the whole chain.
  • A 70B job whose fold schedule was sized for a slower GPU generation, now running on newer hardware — must not silently under-utilize the newer GPU; cogni-bench (§10) should flag a fold-schedule/hardware mismatch as a tuning opportunity, not ignore it.

22.9 Failure Analysis

  • A folding-scheme implementation bug causing a proof-of-a-wrong-computation to fold successfully (a soundness risk specific to recursive composition, distinct from T1's flat-circuit soundness risk) — mitigated by requiring each fold step to independently satisfy the same negative-test conformance pattern established in Phase 0/1, applied recursively.

22.10 Operational Notes

  • Metrics: fold_step_count_gauge, fold_memory_peak_bytes.
  • This phase is also the anchor for the sharded/parallel-verifier-instance deferred feature (§37) once VIPD sustains > 1,000,000/day for 30 days.

23. Phase 11 — Sovereign Subnets & ProofChain Composition

23.1 Objectives

  • Ship Cogni Sovereign — an on-prem/sovereign-cloud deployment anchoring to the public chain via periodic checkpoints (ADR-23).
  • Ship ProofChain composition (multiple inferences composed under one proof), completing the "universal cognition layer" ambition within this blueprint's scope.

23.2 Detailed Implementation Steps

  • Implement the Chainlink-CCIP-pattern checkpoint relay (ADR-23) posting the sovereign subnet's state root to L1 on a fixed cadence, enforcing I12 (monotonic, non-forking checkpoint chain).
  • Implement ProofChain composing multiple Proofs (e.g., retrieval → embedding → inference → re-ranking) under one aggregate proof, using the same folding infrastructure built in Phase 10 (ADR-04 dependency).
  • Package the sovereign deployment artefact (Docker + Nix, ADR-18/22) for a first sovereign-nation customer.

23.3 Deliverable

  • A deployable Cogni Sovereign artefact anchoring to mainnet via a live checkpoint relay.
  • A ProofChain demo composing at least 3 chained inferences under one proof, verified in a single on-chain call.

23.4 Acceptance Criteria

  • Checkpoint relay maintains I12 (zero forks) across 90 consecutive days in conformance/checkpoint_monotonic_90d.json.
  • ProofChain of 3 composed inferences verifies in < 2x the gas of a single inference, evidencing composition amortises rather than multiplies verification cost.
  • One sovereign-subnet customer live (Phase 11 Definition-of-Done threshold).

23.5 Conformance Fixtures

  • conformance/checkpoint_monotonic_90d.json — 90 days of simulated checkpoint submissions under injected network delay, expect zero forks (I12).
  • conformance/proofchain_3_step.json — retrieval→embedding→inference composed proof, expect single verifier call succeeds.

23.6 Pitfalls

  • Checkpoint-relay oracle manipulation (T15, §24) — a compromised or colluding relay reporting a false state root — mitigated by requiring the relay's report to itself be attested against the sovereign subnet's own consensus, not trusted blindly.
  • ProofChain step-ordering ambiguity — must be explicit and part of the public inputs, extending I1's binding property across the whole chain, not just one step.
  • Assuming a sovereign customer's local consensus is as adversarially hardened as mainnet's — a smaller, permissioned sovereign subnet has a different, usually weaker, Sybil-resistance profile, and the checkpoint relay's trust assumptions must say so explicitly rather than borrowing mainnet's threat model by default.

23.7 Performance Concerns

  • Checkpoint cadence is a latency/cost tradeoff: too frequent and L1 gas cost dominates, mitigated by EIP-4844 blob transactions (§5 RFCs) for cheap periodic data; too infrequent and the chain-of-custody promise (§8) weakens between checkpoints.

23.8 Edge Cases

  • Sovereign subnet's L1 anchor transaction reorged on L1 itself — the relay must re-submit the same checkpoint content, not silently skip a round (I12 monotonicity must survive an L1 reorg, not just a sovereign-subnet-side fork).
  • ProofChain where an intermediate step's model is later deprecated (Registry no longer serves it) — historical composed proofs must remain independently verifiable against the commitment that was live at execution time, never retroactively invalidated.

23.9 Failure Analysis

  • Bridge exploit on the sovereign checkpoint relay (T16, §24) — the single most catastrophic failure mode in this phase, given bridges are the most-exploited category in crypto (ADR-23's own rationale); containment: the relay carries no funds itself, only a state-root hash — the actual settlement/fee logic never leaves the audited mainnet contracts, sharply limiting blast radius versus a funds-custodying bridge.

23.10 Operational Notes

  • Metrics: checkpoint_relay_lag_seconds, proofchain_composed_depth_gauge.
  • This phase's Definition of Done is intentionally open-ended in ambition but closed in acceptance criteria (§23.4) — sovereign adoption beyond the first customer is explicitly out of this blueprint's locked scope.

27. Compatibility & Versioning

  • Wire compatibility: CBOR-encoded types (§11) are additive-only once locked (P14) — new optional fields append, no field is removed or repurposed.
  • Storage compatibility: on-chain contract storage layouts are versioned via explicit ADRs (P12); a storage-layout change requires a migration contract, never an in-place reinterpretation.
  • Schema evolution: SchemaId (§11) versions the InferenceJob.input encoding independent of the wire envelope, so model-specific input formats evolve without touching cogni-wire.
  • API stability: ICogniVerifier (§11) is locked at v1 for the lifetime of a deployed verifier instance; a new proof system (ADR-03/04 transition) ships as a new verifier instance with its own address, never a breaking change to an existing one — why Phase 5 and Phase 10 run dual verifiers during migration windows (§17.10).
  • Deprecation policy: a deprecated proof system (e.g., Groth16 post-Phase-5) remains verifiable for existing receipts indefinitely (auditability, P14) but is closed to new registrations.
  • SemVer: cogni-node/cogni-prover follow SemVer; a major version bump is required for any change to NodeOperator trait signatures (§11).
  • Rolling-upgrade guarantees: mixed-version node meshes tolerated for one minor version (§15.10); a major-version node refuses to gossip with an incompatible peer rather than silently misbehaving.

28. Testing & Verification Strategy

  • Unit: per-crate (cogni-types, cogni-wire, cogni-prover) standard cargo test.
  • Integration: cogni-sim (§7 methodology) drives the full FSM (§8.1) with one assertion per invariant I1–I14.
  • Property-based: proptest (ADR-17) over cogni-types serialization round-trips and TokenLedger state-transition invariants (I6, I7, I11).
  • Differential: every proof-system migration (Phase 5, Phase 10) runs the old and new verifier against the same fixture set until 100% agreement (§17.4, §17.10).
  • Fuzzing: cargo-fuzz (libFuzzer) on circuit-boundary parsers; Echidna/Certora (ADR-13) on Solidity contract invariants.
  • Chaos: gossip-churn injection (§15.5), sequencer-restart injection (§14.8), simulated L1 reorg during checkpoint submission (§23.8).
  • Deterministic replay: cogni-sim replays recorded mainnet traces under fault injection (§7 methodology).
  • Soak: 3-external-operator 7-day sustained run (§15.3); 90-day checkpoint-monotonicity soak (§23.4).
  • Fault injection: GPU-saturation load during health() probing (§15.5); reorg injection (§23.8).
  • Conformance: every phase's N.5 fixtures (§12.5 through §23.5), release-blocking per P13.
  • Performance-regression gating: every M-table target (§30) is a CI gate, not a dashboard-only number — a regression blocks release.

29. Build & Release Engineering

  • Reproducible builds: Nix-pinned toolchain including GPU driver ABI (ADR-22); cogni-node/cogni-prover binaries are bit-for-bit reproducible from source, a soundness requirement (T1 mitigation).
  • Artifact signing: release binaries signed with a Foundation-controlled key; signature verified by the Nix build process itself.
  • SBOM: generated per release via Nix's dependency graph, published alongside binaries.
  • Release channels: stable (audited, mainnet-recommended), testnet (ahead of stable, matches the live testnet contract set), nightly (unaudited, devnet only).
  • CI/CD topology: GitHub Actions (ADR-12) running build → fuzz → conformance → gas-gate → (on tag) Nix reproducible-build verification → sign → publish.
  • Version stamping: every binary embeds its git commit hash and Nix derivation hash, queryable via a --version flag exposed through health()'s extended diagnostics.
  • Provenance/attestation: release artifacts carry SLSA-style provenance metadata tying the binary to the exact CI run and Nix derivation.
  • Dependency auditing: cargo audit and npm audit (SDK) gated in CI; any new dependency touching the proven path (circuits, prover) requires an ADR (P12).
  • Release cadence: stable releases are cut only after a full conformance + gas-gate + soak pass (§28); testnet releases may cut weekly; nightly builds continuously from main with no gating beyond compilation.

31. Scalability Analysis

  • Constant vs. grows: verifier gas is O(1) in model size by design (I4, P11) — this is the entire point. Registry storage grows O(models), never O(jobs) (receipts are events, §4). Marketplace matching is O(log n) in job volume given the (sla_tier, deadline) index (§16.7).
  • Named bottlenecks, in order (from §34's derivations):
    1. Prover wall-clock/GPU parallelism dominates at low ANO.
    2. Operator count/stake liquidity (ANO growth) binds next.
    3. L2 verifier gas throughput only binds at extreme VIPD (§34 item 1 shows large headroom).
    4. Off-chain matcher throughput.
    5. Gossip propagation at very high ANO (M8).
  • Horizontal scaling: more operators directly increases prover-parallelism capacity — the network's primary scaling lever through Phase 8.
  • Vertical scaling: GPU generation upgrades (Phase 7) shift the PCR curve down without a protocol change.
  • Sharding/partitioning: deferred to Phase 10 (sharded verifier instances, §37) once bottleneck 3 actually binds.
  • Coordination overhead: grows with ANO in the gossip layer (mesh maintenance) — mitigated by libp2p's bounded mesh degree (§4), not full-mesh gossip.
  • Practical ceiling and levers beyond it: the current design's ceiling is set by bottleneck 3 at extreme VIPD (§34 item 1's ~5M proofs/day theoretical L2 ceiling); the lever beyond it is sharded/parallel verifier instances (deferred, §37) or migration to a higher-throughput settlement layer (ADR-06's re-evaluation, Phase 8).
  • Coordination cost at the marketplace layer: as ANO grows past the Phase 8 target of 500, the off-chain matcher's (sla_tier, deadline) index (§16.7) remains O(log n), but the number of eligible bidders per job (I6-qualified, model-loaded operators) grows linearly with ANO — this is a benefit, not a cost, since it improves fill-rate (M6) rather than degrading it.

32. Mental Models & First Principles

  1. MM1 — A proof is a certificate, not a re-computation.
    • Predicts: verification cost should never scale with the computation it certifies (P11).
    • Bug class without it: engineers keep "optimizing" the verifier by speeding up re-execution instead of shrinking the certificate.
    • Applied in §11, §19.2.
  2. MM2 — Determinism is a property you design into the numerical pipeline, not a property that emerges from testing.
    • Predicts: fixed-point + canonical reduction order must be fixed at circuit-design time (I9).
    • Bug class without it: intermittent, hard-to-reproduce "slashing" of honest operators.
    • Applied in §13, §7.
  3. MM3 — Stake is a bond against a specific class of provable misbehaviour, not a general trust score.
    • Predicts: slashing conditions must be mechanically checkable on-chain (I10), never a vote.
    • Bug class without it: governance capture disguised as "community moderation."
    • Applied in §18, P1.
  4. MM4 — A trust boundary is where you stop verifying and start assuming.
    • Predicts: every box in §3's diagram that crosses a trust boundary needs either a proof or an economic bond, never a policy document.
    • Bug class without it: a "trusted matcher" quietly becomes a single point of censorship (T10/E8).
    • Applied in §3, §16.
  5. MM5 — Succinctness is a circuit-design decision, not a proof-system marketing claim.
    • Predicts: a proof system's asymptotic succinctness only holds if the circuit itself avoids re-encoding the full computation into the constraint count (P11, custom gates).
    • Bug class without it: "we use a succinct proof system" while gas still scales with model size.
    • Applied in §17, §22.
  6. MM6 — Recursion amortises cost; it does not eliminate it.
    • Predicts: folding schemes (Phase 10) still pay a real per-step cost (§5 Ref-impl #3's pitfall) — budget it, don't assume it's free.
    • Applied in §22.6, §22.7.
  7. MM7 — A bridge's blast radius is bounded by what it custodies, not by what it verifies.
    • Predicts: a checkpoint relay that carries no funds (only a state-root hash, ADR-23) is structurally safer than a funds-custodying bridge even with the same code quality.
    • Applied in §23.9.
  8. MM8 — Economic security and cryptographic security are complementary, not substitutes.
    • Predicts: restaking (ADR-24) can bootstrap Phase 6's stake liquidity, but it never substitutes for the soundness of the proof system itself (I2 stands regardless of how much stake is bonded).
    • Applied in §18.2, §33.
  9. MM9 — A single number (the north-star metric) forces every downstream tradeoff into the open.
    • Predicts: once VIPD is the one number everyone watches, a feature that doesn't move VIPD (token price, follower count) reveals itself as a distraction rather than progress.
    • Bug class without it: teams optimise vanity metrics that correlate with, but don't cause, network health.
    • Applied in §16.2 (Marketplace Fill Rate as a supporting metric), §30.
  10. MM10 — Every trust boundary you remove, you must replace with either a proof or a bond — never with a promise.
    • Predicts: as Cogni removes trust in the operator (via proofs) and trust in the matcher (via the order-log fallback), each removal must land on I1–I14 or a stake mechanism, never on "the team says so."
    • Bug class without it: a roadmap slide claims "trustless" while a component still runs on an unenforced promise.
    • Applied in §7, §24.

Reading the table as a design space, not a leaderboard. No row of this table is strictly dominant — each system optimises a different point in the soundness/latency/cost/decentralization tradeoff space (MM4, §32). Cogni's specific bet is that, for the inference workload specifically (as opposed to general smart-contract execution or open-ended scoring), the zk-ML point in that space becomes strictly better than the alternatives once PCR crosses the sub-10x threshold targeted in Phase 10 (§22.4) — before that threshold, Cogni concedes it is not yet uniformly better than a well-run reputational or optimistic system, only differently positioned.

34. Back-of-Envelope Capacity Model

  1. Verifier throughput ceiling per L2 block = block_gas_limit (30,000,000) ÷ gas_per_verify (250,000, §4 M2) = 120 proofs/block. At 2 s block time (OP Stack, §4) → 60 proofs/s → 5.18M proofs/day theoretical ceiling — far above Phase 1's 10,000 VIPD target, so L2 throughput is not the Phase 1 bottleneck (§31).
  2. Prover wall-clock parallelism ceiling = PCR (1000x, Phase 0) × raw_inference (1 ms) = 1 s/proof/GPU. 100 GPUs in parallel → 100 proofs/s → 8.64M proofs/day — again not the binding constraint; operator count (ANO) is.
  3. Registry storage growth = DMC × commitment_record_size (≈174 bytes: 32 hash + 8 arch_id + 8 param_count + 1 quant + 20 address + 32 license + 8 ts + 65 sig). At 10,000 committed models (generous Phase 10 estimate) → 1.74 MB on-chain state — trivial; never the bottleneck (§31).
  4. Node fan-out FD load = ANO (500, Phase 8 target) × gossipsub mesh degree (D=8, §4) × 2 (in+out) = 8,000 sockets network-wide; per-node share (D×2=16 + RPC + marketplace conns, ≈ <200) sits comfortably under the 4,096 FD budget (§4).
  5. Marketplace escrow storage = ANO (500) × concurrent_jobs_per_operator (8, from item 7) × lockedFees_entry (32 bytes) = ≈128 KB — negligible against L2 state limits.
  6. Aggregate gossip bandwidth = VIPD (100,000/day, Phase 8 target) ÷ 86,400 s × avg_receipt_size (≈100 KB, dominated by the Phase-5 proof-size ceiling, §4) ≈ 1.16 proofs/s × 100 KB ≈ 116 KB/s aggregate — trivial for any operator uplink.
  7. 7B-model VRAM floor = param_count (7×10⁹) × 1 byte (INT8, I8) = 7 GB weights + activation buffer (≈3x for batch=1 transformer forward) ≈ 21–24 GB — validates the §4 single-RTX-4090 (24 GB) hardware floor exactly at its edge, explaining why Phase 7 mandates INT8 (FP16 weights alone would leave no headroom).
  8. Slashing-window economic-security floor = slashWindow (14 days, I7) × avg_daily_job_value (VIPD × avg_fee) must exceed the value an operator could extract by defecting once (Threat Model T13); as VIPD grows toward Phase 10's 1,000,000/day target, either slashWindow or the per-job stake multiplier (I6) must scale — a live tension revisited every phase (§18, §35 Q19).
  9. 70B-model VRAM floor = param_count (7×10¹⁰) × 1 byte (INT8) = 70 GB weights alone — exceeds any single consumer GPU, which is exactly why Phase 10 requires recursive folding across multiple GPUs/steps rather than a single-device proof (§22.2), unlike the Phase 7 7B case (item 7).
  10. Checkpoint relay L1 gas budget (sovereign subnets) = 365 checkpoints/year × gas_per_checkpoint (≈100,000 gas via EIP-4844 blob posting) ≈ 36.5M gas/year — small enough that a sovereign customer's annual L1 gas spend for checkpointing is a rounding error next to its own compute costs, supporting ADR-23's cost rationale.
  11. Recursive-batch verifier gas amortisation (Phase 7) = single_verify_gas (800,000, §4) × batch_size (4) ÷ measured_folded_gas (target < 4× = 3.2M, §19.4) — if the folded call lands materially below 3.2M gas, each additional batched job costs less than the marginal single-job gas, quantifying exactly how much I4's succinctness "compounds" under recursion rather than merely holding flat.
  12. Sybil-attack cost floor (T10) = stake_floor_per_identity (I6's minimum, tied to slashingMultiplier× typicalmaxFee) × desired_fake_identity_count — at even 100 fake identities, the attacker must lock 100× the per-identity floor in illiquid, slashable stake, which the Capacity Model shows scales the attack cost linearly with intended Sybil weight, making it economically self-limiting exactly as T10's mitigation claims.

36. Alternative Architectures (Roads Not Taken)

Alt 1 — Optimistic (fraud-proof) verifiable inference.

Operator --posts (output, bond)--> Chain --dispute window (7d)--> Challenger
                                       |                              |
                                       +--- no challenge: finalize ---+
                                       +--- challenge: interactive
                                            fraud-proof bisection ----+

Regime where it wins: Turing-complete or circuit-infeasible operations, where a zk circuit cannot yet be written at acceptable cost. Real embodying system: Arbitrum's interactive fraud-proof design (Kalodner et al., §5 Papers #10), and the Truebit proposal for general verifiable computation. Why rejected: a 7-day dispute latency is incompatible with pay-per-inference UX (§35 Q12), and it requires an honest-watcher liveness assumption that P1's "cryptographic verification is the only verification" explicitly forecloses.

Alt 2 — Reputational/replication consensus (Bittensor-style).

Query --> [Miner A, Miner B, Miner C] --> Validator scores each response
                                              |
                                    weighted consensus (Yuma-style)

Regime where it wins: subjective, open-ended tasks with no ground truth and where speed-to-market matters more than mathematical guarantees. Real embodying system: Bittensor. Why rejected: fails P1 outright; colluding miner-validator pairs can extract rewards for wrong answers with no cryptographic recourse (§33).

Alt 3 — TEE-only attestation (no zk at all).

Client --encrypted input--> [SGX/TDX Enclave] --remote attestation quote--> Chain
                                  |
                            decrypt, infer, sign

Regime where it wins: workloads needing input privacy before zk-ML circuits can afford it, or where the model's owner wants confidentiality of the weights themselves. Real embodying system: confidential-compute networks built on Intel SGX/AMD SEV (the pattern used by, e.g., Oasis Sapphire's confidential EVM). Why rejected as primary: single-vendor hardware trust root (Intel/AMD supply chain) violates P7's sovereign-neutrality principle as a sole mechanism — used only as an auxiliary hardware class (Phase 9, §21) alongside, never instead of, zk-ML.

Alt 4 — Centralized-registry + periodic third-party audit.

Operator --logs every inference--> Centralized Log --quarterly audit--> Auditor Report

Regime where it wins: small enterprise deployments where an audit cadence of weeks is acceptable and blockchain overhead is unjustified. Real embodying system: the traditional cloud-provider compliance model (SOC 2 / ISO 27001 attestation regimes used by AWS/Azure/GCP). Why rejected: no continuous/real-time verifiability, a single point of trust in the auditor and the log itself, and it does not scale to a permissionless global operator base — exactly the properties Cogni's beachhead customers (§2) find unacceptable.

Why these four and not others. Each alternative was the strongest real-world embodiment of a fundamentally different trust mechanism (liveness-based dispute, reputation, hardware root, institutional audit) rather than a parameter variant of Cogni's own design (e.g., "Cogni but with Groth16 forever" is not a distinct architecture, it is ADR-03 explored differently, already covered in §9). A design is listed here only if adopting it would change which of P1–P14 the system could still honor — Alt 1 breaks P3, Alt 2 breaks P1, Alt 3 tensions P7, Alt 4 breaks P3 and P1 both.

38. Glossary

  • ADR: Architectural Decision Record — numbered, dated, capturing context/choice/consequences (P12).
  • ANO: Active Node Operators, last-7-day count.
  • ArchitectureId: stable identifier binding a ModelCommitment to its matching CircuitId (I1, T3).
  • CBOR: Concise Binary Object Representation, RFC 8949 — wire format for Receipt/InferenceJob.
  • CCIP: Cross-Chain Interoperability Protocol pattern (Chainlink-style oracle relay, ADR-23).
  • CircuitId: stable identifier for a zk-ML circuit corresponding to one model architecture.
  • Cogni Chain: the settlement layer (EVM L2, Phase 2+).
  • Cogni Node: the long-running operator daemon (Phase 3).
  • Cogni Prover: the Rust + GPU library producing a Proof.
  • Cogni Sovereign: the on-prem/sovereign-cloud deployment artefact (Phase 11).
  • DePIN: Decentralized Physical Infrastructure Network.
  • DMC: Distinct Models Committed.
  • EncryptionSpec: client-declared encryption scheme + pubkey for an encrypted InferenceJob.
  • ExecError: enumerated operator-execution failure (ModelNotLoaded, Timeout, ProverPanic, QuantisationDrift).
  • Folding scheme: recursive proof composition (Nova/SuperNova/HyperNova).
  • Groth16: trusted-setup zk-SNARK; Phase 0 only (ADR-03).
  • Halo2: Plonk-style proof system, Phase 1–9 (ADR-03).
  • HardwareClass: operator-advertised hardware tier (Consumer | Datacenter | TeeAttested).
  • Howey test: US Supreme Court test for what constitutes a security.
  • InferenceJob: client-signed request to run a model on an input.
  • JobId: 32-byte single-use job identifier (I5).
  • KZG: polynomial-commitment scheme used in Plonk variants.
  • Lookup argument: cryptographic primitive (Lasso, Jolt) collapsing non-arithmetic ops to near-constant cost.
  • MiCA: Markets in Crypto-Assets regulation (EU).
  • ModelCommitment: author-signed merkle root of model weights plus metadata (I14).
  • NodeIdentity: operator's on-chain identity bound to a staking key.
  • PCR: Proof Cost Ratio — prover wall-clock ÷ raw inference wall-clock.
  • PIOP: Polynomial Interactive Oracle Proof — the arithmetization abstraction behind Plonk/STARKs (Thaler, §5).
  • Plonk: universal-setup SNARK (Gabizon/Williamson/Ciobotaru).
  • Proof: cryptographic attestation of correct inference execution.
  • ProofChain: composition of multiple Proofs under one aggregate proof (Phase 11).
  • ProofSystem: the trait boundary making the proof primitive swappable (P10).
  • Quote: an operator's bid price + ETA for a job.
  • Receipt: on-chain record of a completed InferenceJob (I5, I11, I13).
  • Restaking: delegating already-staked collateral (e.g., ETH) to secure a second protocol (EigenLayer pattern, ADR-24).
  • SchemaId: version identifier for a model-specific input encoding.
  • SDD: Sovereign-Domain Deployments.
  • SE10K: Slashing Events per 10,000 proofs.
  • Slashing: burn of operator stake on proven misbehaviour (I10).
  • SlaTier: BestEffort | Standard | Premium job service-level class.
  • STARK: transparent, scalable proof system (no trusted setup).
  • TEE: Trusted Execution Environment (Intel SGX/TDX, AMD SEV).
  • TGE: Token Generation Event.
  • VEV: Validator-Extractable Value — the MEV analogue for inference job ordering.
  • VIPD: Verified Inferences per Day — the network's north-star throughput metric.
  • VRAM floor: the minimum GPU memory needed to prove a given model size (§34 item 7).
  • Wassenaar: multilateral export-control arrangement covering dual-use items.
  • zk-ML: zero-knowledge machine learning — cryptographic proofs of correct inference.
  • BN254: the pairing-friendly elliptic curve used by Cogni's Groth16/Plonk circuits (Phase 0–9).
  • EmissionSchedule: the on-chain-encoded, mechanical token-issuance curve (P6, §8.3).
  • FeeSplit: the on-chain record dividing settled fees between operator, treasury, and burn (§8.3, ADR-25).
  • FSM: Finite State Machine — the job-lifecycle model of §8.1.
  • MSM: Multi-Scalar Multiplication — the elliptic-curve operation whose windowing efficiency dominates Groth16 prover cost (§5 Ref-impl #2).
  • PoS: Proof of Stake — the validator-security model Ethereum and EigenLayer use, contrasted with Cogni's proof-based verification in §33.
  • slashingMultiplier: the on-chain constant scaling required stake to a job's maxFee (I6).
  • VRAM: Video RAM — the GPU memory budget that gates model size per operator (§34 items 7 and 9).
