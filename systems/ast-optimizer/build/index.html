⬜ Phase 0 — Repo Skeleton & Correctness Kernel §12

Objectives

Stand up the full governance/build scaffold (§10) and the minimal correctness kernel: the Value/RuntimeError/Env types and a stub interpreter capable of evaluating Lit and Var nodes — the smallest slice of opt-verify::interp (§22) that later phases extend. No optimizer pass lands in Phase 0 (P4 does not yet apply to anything).

Deliverable

A freshly-cloned repository where make bootstrap && make build && make test all return 0, CI is green on a template PR, and cargo test -p opt-verify exercises the Lit/Var interpreter stub against 10 literal fixtures.

Acceptance

make bootstrap exit code 0; make build exit code 0 with 0 clippy warnings; make test exit code 0; make conformance runs and emits a report with 0 bucket rows (none registered yet) validating clean against report.schema.json; the interpreter stub passes exactly 10 named literal fixtures under conformance/fixtures/positive/infra/kernel/*.lock.

Fixtures
Fixture Purpose Expected
infra/kernel/lit-int.lock evaluate an integer literal Value::Int matches source
infra/kernel/lit-bool.lock evaluate a boolean literal Value::Bool matches source
infra/kernel/var-bound.lock evaluate a bound variable resolves via Env
infra/kernel/var-unbound.lock (negative) evaluate an unbound variable RuntimeError::UnboundVar
Pitfalls
  • Writing optimizer code in Phase 0 — the next session collides with it; Phase 0 is scaffold-only (§7).
  • Skipping ADR-01 — future sessions re-litigate the language choice without it.
  • Omitting deny.toml — license/advisory audits are part of the production bar (ADR-16), not an afterthought.
  • Letting the CI templates diverge from .github/workflows/ names in §10 — Appendix A (§39) must match exactly.

⬜ Phase 1 — AST, Types & Annotation Framework §13

Objectives

Land opt-syntax (the locked AST/Type model, §8.1/§11) and opt-annot (the Purity/Freshness/Cost side tables, §11) together — the resolver's annotation population is the first real consumer of the AST, so the two ship as one phase to keep the Phase-Contract's N.4 acceptance criteria meaningfully testable end to end.

Deliverable

opt-syntax and opt-annot compile and are consumed by a CLI-less test harness that parses an examples/*.lock fixture, annotates it, and prints the resulting AnnotTables in a stable, snapshotted textual form.

Acceptance

cargo test -p opt-syntax -p opt-annot exit code 0; round-trip pretty(parse(s)) == s holds on all 5 examples/*.lock fixtures; a NodeId-stability snapshot test confirms identical ids across two pretty-then-parse cycles of the same source; a property test confirms Pure/Fresh annotations agree with a reference interpreter on 1,000 random expressions (I3).

Fixtures
Fixture Purpose Expected
infra/syntax/roundtrip-fib.lock pretty/parse round trip byte-identical source
infra/annot/purity-pure-record.lock record of pure fields Purity::Pure
infra/annot/purity-unknown-call.lock call to unannotated function Purity::Unknown (I3 top)
infra/annot/nodeid-collision.lock (negative) duplicate NodeId injected ValidationError::DuplicateNodeId
Pitfalls
  • Letting the AST grow without a NodeId on a new variant — every future annotation silently breaks (P5).
  • Forgetting ty: Type on an Expr variant — every type-directed pass downstream breaks (I9, P2).
  • Treating Unknown purity as Pure by default — the lattice's top must be the safe default, never the bottom (I3).
  • Forgetting float ops can raise (signaling NaN) — mark float arithmetic Exception-tier unless the FP environment is declared quiet (§17.6 cross-reference).

⬜ Phase 2 — Visitor, Rewrite Engine & Pass Manager Skeleton §14

Objectives

Land opt-visitor (Visitor/Rewriter traits, worklist, §11) and a minimal opt-manager skeleton (PassRegistry, PassDescriptor, Fuel, but not yet the full scheduler — that is Phase 9, §21). This phase proves the traversal and fuel primitives before any real pass is built on them.

Deliverable

A no-op Rewriter that round-trips any Module unchanged, plus a toy fold rewriter (1 + 1 → 2, a throwaway proof-of-concept deleted before Phase 3 ships its real folder) demonstrating the worklist-driven rewrite-to-fixpoint helper terminates.

Acceptance

cargo test -p opt-visitor -p opt-manager exit code 0; the no-op rewriter is a fixpoint after exactly 1 iteration on every examples/*.lock fixture; the toy fold rewriter reaches a fixpoint deterministically (P13) on 1,000 random expressions generated by a depth-bounded strategy; Fuel::tick() returns false exactly once fuel is exhausted, verified by a unit test with Fuel { remaining: 0 }.

Fixtures
Fixture Purpose Expected
infra/visitor/noop-fixpoint.lock no-op rewriter 1-iteration fixpoint
infra/visitor/toy-fold-1000.lock toy fold determinism stable result across 3 reruns
infra/manager/fuel-zero.lock fuel exhaustion tick()==false, no mutation applied
Pitfalls
  • Cloning the entire Module on every rewrite step — acceptable in Phase 0/1 scaffolding, but flagged PhaseDeferred("§14") for a Phase-1+ Cow-style structural-sharing follow-up (P11's stated cost).
  • Worklist starvation — every fact change must enqueue every dependent node, or propagation (§15) silently stops early.
  • Registering a PassDescriptor whose reads/writes do not match the pass body — I11's static check does not exist until Phase 9's CI wiring, so this phase's own registrations must be hand-audited first.

⬜ Phase 3 — Constant Folding & Constant Propagation §15

Objectives

Land the real fold.rs and propagate.rs under opt-passes: type-directed constant folding (ADR-09, P2) and the AST-shaped SCCP-lite propagator (§8.3's Const lattice, Wegman & Zadeck 1991). The two ship together because propagation's output feeds directly back through the folder (§8.4's worked trace).

Deliverable

opt-passes::{Folder, Propagator} composed manually (pre-Phase-9 manager) into a two-pass loop that optimizes every examples/*.lock fixture to its expected reduced form, demonstrated by the §8.4 worked trace.

Acceptance

60 fixtures under tests/fold/positive rewrite to the expected ground term; the folder is idempotent, fold(fold(m)) == fold(m) (P7); a property test confirms interp(fold(m)) == interp(m) (I1) on 5,000 random closed expressions; let x = 1 in x + 2 propagates and folds to 3; a loop variable known-constant on entry but mutated in the body stays at Top (§8.3's join rule).

Fixtures
Fixture Purpose Expected
passes/fold/add-int.lock 1 + 2 folds to 3
passes/fold/div-zero.lock (negative) 1 / 0 preserved unfolded — P2 guard
passes/fold/project-record.lock {x=1,y=2}.x folds to 1
passes/propagate/loop-mutated.lock loop-carried variable stays Top
passes/propagate/sccp-1000.lock 1,000-case differential all agree with interp
Pitfalls
  • Folding 1 / 0 to a value — don't; preserve the expression so runtime semantics still apply (P2's namesake malformed-input concern, §8.5).
  • Folding past a side effect — the Purity guard (I3) exists precisely to block this.
  • Floating-point identity violations — 0.0 + x = x is wrong because 0.0 + (-0.0) = 0.0; guard with an FP-environment annotation (cross-referenced again in §17.6).
  • Confusing Top and Bottom — Top means "could be anything" (join of disagreement); Bottom means "unreachable / not yet computed" (§8.3).

⬜ Phase 4 — Dead-Code Elimination & Common Subexpression Elimination §16

Objectives

Land dce.rs (purity-gated deletion of unused pure bindings) and cse.rs (hash-consing pure subexpressions into a shared let), the two classical redundancy-elimination passes that complete the Phase-3 pair per Cooper & Torczon 2011 ch. 8–10's value-numbering lineage.

Deliverable

opt-passes::{Dce, Cse} composed after the Phase-3 pair, demonstrated on f(a + b) + g(a + b) → let cse_0 = a + b in f(cse_0) + g(cse_0).

Acceptance

let _ = pure_call() in 1 rewrites to 1; let _ = side_effect() in 1 is preserved unchanged (I3 guard); a property test confirms interp(dce(m)) == interp(m) on 5,000 random closed expressions; the CSE example above matches exactly; a saturation cross-check (§20) confirms CSE and the saturator agree on 1,000 expressions.

Fixtures
Fixture Purpose Expected
passes/dce/pure-unused.lock unused pure binding deleted
passes/dce/impure-unused.lock (negative) unused impure binding preserved
passes/dce/letrec-self.lock recursive binding unused in body preserved (own use counts)
passes/cse/shared-subexpr.lock duplicate pure subterm lifted to one let
passes/cse/impure-duplicate.lock (negative) duplicate impure subterm not lifted
Pitfalls
  • DCE on let rec — the recursive binding's value is its own use; never delete solely because the body doesn't reference it (a distinct rule from ordinary let).
  • Useless-match-arm detection is explicitly out of Phase-4 scope — a separate pattern-analysis pass, PhaseDeferred("§16").
  • Lifting an impure expression in CSE — guard strictly with Purity (P3).
  • Hashing modulo alpha — variables must be renamed first (P12), or structurally-identical-up-to-naming terms look different and CSE silently misses them.
  • Lifting past a binder — the lifted let must sit outside the smallest enclosing binder that captures the expression's free variables, or the lift itself introduces capture (I10).

⬜ Phase 5 — Function Inlining & Peephole Rewrites §17

Objectives

Land inline.rs (heuristic-bounded inlining, ADR-08) and peephole.rs (the curated small-rewrite library), the two passes most prone to code-size blowup and therefore the two most fuel-disciplined (P4) after the saturator itself.

Deliverable

opt-passes::{Inliner, Peephole} composed after Phase 4; a synthetic 10,000-call fixture demonstrates the fuel bound holding under max_size=1000, fuel=100.

Acceptance

A call to a 5-line pure function is inlined; a recursive function is never inlined (call-graph check, 0 false negatives on a 50-fixture recursion corpus); the fuel bound is respected — the 10,000-call synthetic fixture with fuel=100 produces at most 100 inlines; 60 peephole fixtures rewrite to the expected term; a differential test runs on 5,000 random expressions for each pass.

Fixtures
Rule LHS → RHS Soundness Guard
pe-add-zero-r x + 0 → x x pure, non-NaN float or int
pe-mul-zero-l/r 0 * x → 0 x pure
pe-and-or-true-false x && true → x, x || false → x x pure
pe-not-not not (not x) → x x : Bool
pe-if-same if c then a else a → a c pure
pe-let-id let x = e in x → e always
pe-record-update-overwrite {{r with l=a} with l=b} → {r with l=b} always
pe-project-update-same/other {r with l=a}.l → a; .k → r.k (k≠l) a/r pure
pe-app-curry (fn x y -> e) a b → (fn y -> e[a/x]) b always (I10 alpha-safe)

Named fixtures: passes/inline/pure-small.lock, passes/inline/recursive-blocked.lock (negative), passes/inline/fuel-100-of-10000.lock; passes/peephole/{rule-name}.lock for each of the 15 rules above, plus passes/peephole/fp-signed-zero.lock (negative).

Pitfalls
  • Inlining a recursive function — diverges; the call graph check (17.2) is mandatory, not advisory.
  • Variable capture during inlining or curry-splitting — alpha-rename first (P12, I10).
  • Floating-point identities are mostly wrong (x + 0.0 fails on x = -0.0) — guard with the FP-environment annotation or omit the rule entirely (a real recurring bug class in production peephole libraries).
  • Distributive rewrites can grow the program — hand them to the saturator (§20), which tracks cost explicitly, rather than looping them here.
  • Rewrites that break sharing (let x=e in x+x → e+e) undo CSE's work; gate on Freshness before applying.

⬜ Phase 6 — Partial Evaluation & Beta/Eta Reduction §18

Objectives

Land partial_eval.rs (online, fuel-bounded specialization, ADR-10) and beta.rs/eta.rs (capture-safe beta and eta reduction) — grouped because partial evaluation is, mechanically, repeated fuel-bounded beta-reduction against known-constant arguments (Reynolds 1972; Plotkin 1975 on the underlying calculus).

Deliverable

opt-passes::{PartialEvaluator, Beta, Eta}; the canonical demonstration is power(x, 3) (power n x = if n==0 then 1 else x * power(n-1,x)) specializing to x * x * x after fuel-bounded unrolling.

Acceptance

The power(x,3) example specializes exactly as stated; recursive specialization of a non-terminating function bottoms out at the fuel bound and emits a PassReport::FuelExhausted diagnostic rather than hanging; (fn x -> x + 1) 2 reduces to 3 after beta + fold (§15); (fn x -> f x) reduces to f exactly when f is pure; a differential test runs on 5,000 random closed expressions per pass; a code-blowup guard refuses any PE rewrite where new_size > 4 × old_size.

Fixtures
Fixture Purpose Expected
passes/pe/power-3.lock canonical specialization x * x * x
passes/pe/nonterminating.lock (negative) recursive non-terminating callee fuel-bounded, deferred diagnostic
passes/beta/simple-app.lock (fn x -> x+1) 2 3 after fold
passes/beta/aliased-arg.lock aliased argument lifted via let, not substituted
passes/eta/pure-wrapper.lock (fn x -> f x), f pure reduces to f
passes/eta/impure-wrapper.lock (negative) f impure not reduced
Pitfalls
  • Specializing a recursive function without fuel — diverges (the namesake concern of ADR-10's online-PE choice).
  • Specializing across an effect — guard with Purity exactly as folding/propagation do (P3).
  • Code blowup from unchecked specialization — track the size delta and refuse past the 4× threshold (18.4).
  • Variable capture during beta substitution — alpha-rename first (P12, I10); this is the single most common bug class this project's audits have seen in hand-written beta reducers.
  • Eta-reducing an impure f — changes side-effect timing; never do it (a distinct pitfall from the capture concern above).

⬜ Phase 7 — Loop-Invariant Code Motion & Tail-Call Detection §19

Objectives

Land licm.rs (hoist loop-invariant pure expressions to a preheader, Knoop, Rüthing & Steffen 1992) and tail_call.rs (annotate calls in tail position for the downstream IR-lowering boundary, Steele 1978) — grouped as the two passes whose output is consumed primarily outside this pass pipeline (LICM feeds the saturator's cost model in §20; tail-call annotations feed the downstream IR lowering, ADR-15).

Deliverable

opt-passes::{Licm, TailCall}; the canonical LICM demonstration is loop { x = a + b; ... } (with a, b defined outside) hoisting a + b to a preheader let; the canonical tail-call demonstration is a self-recursive loop-style function having its recursive call annotated TailPosition::Yes.

Acceptance

The LICM example hoists exactly as stated on 1,000 differentially-tested loop fixtures (I1); a non-tail f x + 1 is annotated TailPosition::No; let rec loop n = if n == 0 then () else loop (n - 1) annotates its recursive call TailPosition::Yes, verified by a snapshot of the annotation table (stable across reruns, I12).

Fixtures
Fixture Purpose Expected
passes/licm/hoist-pure.lock pure loop-invariant expr hoisted to preheader
passes/licm/impure-not-hoisted.lock (negative) impure loop-invariant-looking expr not hoisted
passes/tailcall/self-recursive.lock tail-recursive loop TailPosition::Yes
passes/tailcall/non-tail-add.lock (negative) f x + 1 TailPosition::No
Pitfalls
  • Lifting an impure expression in LICM — guard with Purity exactly as DCE/CSE do (P3); the "loop-invariant" property is purely syntactic and says nothing about effect safety.
  • Lifting past a conditional that guards a fault (e.g. a division only safe inside the guard) — move only into the dominator chain the loop already unconditionally executes, never past a guard.
  • A try/catch-wrapped call is never in tail position, because its result must still be inspected by the handler — Phase-0's surface language has no exception handling, so this is a forward-looking note for Stretch.4-style effect extensions (§37).

⬜ Phase 8 — Equality Saturation Engine §20

Objectives

Land opt-saturate: an e-graph built on egg 0.9 (ADR-06), a curated rewrite library (P10, I8) including every peephole rule from §17.5 plus associativity/commutativity/distributivity rules, a swappable CostModel (P6, ADR-07), and greedy/LP extractors (ADR-20) — the second optimization paradigm this project deliberately runs alongside, not instead of, the pass pipeline (Click & Cooper 1995's argument, realized concretely).

Deliverable

opt-saturate::{Saturator, AstCostModel} implementing SaturationEngine/CostModel (§11); demonstrated on (a + b) + c under add-assoc, which saturates and extracts a cost-equivalent form without re-associating during the extraction step (size-1 cost makes both forms tie, exercising the extractor's tie-break rule).

Acceptance

The (a+b)+c example saturates and extracts as stated; a 200-line fixture saturates in ≤ 100 ms with the curated rule set (§4/§30); a differential test confirms the extracted program matches the interpreter on 5,000 random fixtures (I1); the node-limit failure path of §8.6 is exercised by a dedicated adversarial fixture and reports stopped_reason=NodeLimit rather than crashing.

Fixtures
Fixture Purpose Expected
saturate/rules/assoc-comm.lock (a+b)+c under add-assoc cost-equivalent extraction
saturate/rules/peephole-parity.lock every §17.5 rule mirrored saturator and peephole pass agree
saturate/extraction/200-line.lock perf fixture ≤100ms saturation
saturate/extraction/node-limit-adversarial.lock (negative) 40 nested comm/assoc applications stopped_reason=NodeLimit, sound partial extraction
Pitfalls
  • Saturation explosion — add-comm + add-assoc together grow the e-graph quadratically; fuel (I7) is the mandatory safety net, not an optional tuning knob.
  • Extracting an unsoundly-equivalent term — the rewrite library must be reviewable; docs/saturator-rules.md's "rule → soundness justification" table is the audit trail (I8).
  • Cost-model bugs masquerading as extractor bugs — a rewrite that "should" be cheaper but isn't reveals a CostModel bug, not an extractor bug; the extractor is trusted to pick the argmin of whatever cost function it is given (MM6, §32).
  • Letting the e-graph extractor pick the largest term because of a cost-model sign error — always snapshot-test the cost surface directly, not just the final extraction.

⬜ Phase 9 — Full Pass Manager: Scheduling, Fixpoint, Fuel §21

Objectives

Land the complete opt-manager: the dependency-graph scheduler (ADR-04), the fuel-bounded fixpoint driver (I6, P4), and the per-pass dump writer — upgrading Phase 2's skeleton (§14) into the real orchestrator every later phase's passes compose under.

Deliverable

opt-manager::{Manager, PassRegistry} orchestrating the full 11-pass pipeline (fold → propagate → dce → cse → inline → peephole → partial_eval → beta → eta → licm → tail_call) to a fixpoint on every examples/*.lock fixture.

Acceptance

A four-pass run (fold → propagate → dce → cse) terminates in fewer than 8 iterations on every Phase-0 fixture; the full 11-pass run terminates within the max_iter=32 cap on 100% of the conformance corpus (§28); dump output is byte-stable across reruns of the same input (I12); a regression test confirms the scheduler never violates a declared reads/writes ordering constraint (I11).

Fixtures
Fixture Purpose Expected
manager/scheduling/four-pass-fib.lock fold→prop→dce→cse <8 iterations
manager/scheduling/oscillation-synthetic.lock (negative) crafted fold/dce/cse cycle caught at max_iter, ManagerReport::Unstable
manager/scheduling/dump-determinism.lock 3 consecutive runs byte-identical dumps
Pitfalls
  • Two passes oscillating ("fold makes a let, dce removes it, cse adds it back") — the fixpoint loop catches this via max_iter, but oscillation itself is a smell; triage by adding a tie-breaker rule to one of the passes, not by raising the cap.
  • Forgetting to invalidate an annotation in PassDescriptor.invalidates — a later pass reads a stale Cost/Freshness value and produces a wrong (though not necessarily unsound) rewrite decision, degrading optimization quality silently.
  • Treating the dump writer as optional under disk pressure — losing it removes the only operator-facing view into "why did the optimizer produce this," making regression triage (§16.10 onward) impossible.

⬜ Phase 10 — Differential Verification Harness §22

Objectives

Land opt-verify's full harness: the tree-walk reference interpreter (extending Phase 0's Lit/Var-only stub to the complete Expr grammar), the proptest generation strategy, and the regression corpus — the mechanical realization of I1 and the gate every prior phase's acceptance criteria have referenced.

Deliverable

opt-verify::{interp, Verifier, arb_expr} wired as the mandatory gate behind every pass's differential-test acceptance criterion cited in §15–§21.

Acceptance

A 5,000-case proptest run is green; the regression corpus under tests/regression/ holds at least 50 minimized counter-examples accumulated from Phase-0 development; a coverage report shows > 85% of opt-passes lines exercised by the harness; float comparison uses bit-pattern equality (f64::to_bits), never ==, per the interpreter's NaN-safety requirement.

Fixtures
Fixture Purpose Expected
verify/diff/5000-random.lock aggregate differential run 100% agreement
verify/diff/float-bitpattern.lock NaN/signed-zero comparison bit-pattern equality, not ==
verify/regression/<50 minimized cases>.lock permanent regression corpus all green, forever
verify/diff/nonterminating-guard.lock (negative) crafted non-terminating program step-count ceiling trips, no hang
Pitfalls
  • A non-terminating program slipping into the corpus — bound the interpreter's step count explicitly (mirrors P4 at the oracle level, not just in the optimizer).
  • A floating-point divergence bug hidden by == comparison — always compare via f64::to_bits for Value::Float.
  • Treating "harness is green" as sufficient without checking coverage — the >85% line-coverage acceptance criterion (22.4) exists because a green harness with low coverage is a false sense of security (P8's full intent).

⬜ Phase 11 — Driver, CLI & Conformance Suite §23

Objectives

Land opt-driver (the CLI: optimize/dump-passes/bench/saturate) and opt-conformance (the fixture runner producing the machine-checked JSON report) — the two operator-facing surfaces that make every prior phase's work consumable outside a cargo test invocation.

Deliverable

opt optimize examples/fib.lock --profile=O2 producing a valid, interp-agreeing module; opt dump-passes producing a deterministic dump directory; make conformance producing a schema-valid JSON report with every Phase-0 bucket Pass.

Acceptance

CLI cold-start ≤ 50 ms (§4); opt optimize examples/fib.lock --profile=O2 agrees with interp (I1); opt dump-passes examples/fib.lock --out-dir /tmp/dumps produces byte-identical output across 3 runs; every Phase-0 conformance bucket (§28's table) reports Pass; every Phase-1-target bucket reports Deferred with a blueprint_ref naming the phase it awaits (§37).

Fixtures
Fixture Purpose Expected
driver/cli/optimize-o2-fib.lock end-to-end O2 run interp-agreeing output
driver/cli/dump-passes-determinism.lock 3-run dump comparison byte-identical
driver/cli/profile-manifest-snapshot.lock profile pass-list snapshot matches locked manifest
conformance/report-schema-valid.lock JSON report shape validates against report.schema.json
Pitfalls
  • Profile drift — a profile that silently changes its pass set breaks every downstream regression baseline; snapshot the profile manifest (23.4) explicitly.
  • CLI options that overlap or conflict (e.g. --profile=O0 --exact-cost) — validate combinations before running, fail fast with a named error, not a silently-ignored flag.
  • Treating conformance Deferred buckets as Pass in a summary rollup — the two must remain visibly distinct in the report (§28).
