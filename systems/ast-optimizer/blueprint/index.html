43 — AST Optimizer

Project Number: 43

Project Name: AST Optimizer

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Implement a pre-IR optimizer over a typed abstract syntax tree (AST), in Rust, that consumes a typed AST emitted by an external type-checker/parser front end and produces a smaller, faster, semantically-equivalent typed AST, verified against a reference interpreter before it is trusted. The system is a library plus a batch CLI driver — not a JIT, not a runtime, and not itself a parser or type-checker.

In-scope Phase-0 deliverable (numbered modules/crates):

  1. opt-syntax — AST/Type node model, NodeId, Span, structural pretty-printer.
  2. opt-annot — Purity / Freshness / Cost annotation side tables.
  3. opt-visitor — Visitor / Rewriter traits, worklist-driven rewrite-to-fixpoint helper.
  4. opt-passes — the classical pass library: fold, propagate, dce, cse, inline, peephole, partial_eval, beta, eta, licm, tail_call.
  5. opt-saturate — egg-based equality-saturation engine, curated rewrite library, cost model, extractor.
  6. opt-manager — pass registry, dependency graph, fuel-bounded fixpoint scheduler, per-pass dump.
  7. opt-verify — tree-walk reference interpreter, differential-test harness, proptest strategy.
  8. opt-driver — CLI (optimize / dump-passes / bench / saturate).
  9. opt-conformance — fixture runner producing a machine-checked JSON report.

System boundaries — provides: the pass library, the pass manager, the equality-saturation engine, differential verification, a conformance harness. Delegates: parsing and type-checking (external, upstream); machine-code generation and SSA-form IR lowering (external, downstream, out of scope by design — ADR-15, contrasted in Alternative Architectures §36/A2). Does NOT provide: a runtime, a JIT tier, profile collection, a garbage collector.

Non-goals: machine-code generation; parsing or type-checking the input language; profile-guided optimization (the cost model is static in Phase-0, PhaseDeferred("§21")); whole-program or cross-module fusion (PhaseDeferred("§31")).

Deployment model: a Rust library (crates/) plus one statically-linked CLI binary (opt-driver); no daemon, no network service, no persistent state between invocations beyond on-disk fixture and dump artifacts.

Target users/operators: compiler engineers building or maintaining a DSL/language toolchain who need textbook AST-level optimizations before IR lowering; conformance/CI operators who gate merges on the differential harness (§22, §28) and the performance targets (§30).

What later phases unlock: Phase 8 (§20, saturation) unlocks non-directional, order-independent rewriting; Phase 9 (§21, full manager) unlocks safe multi-pass composition with declared invalidation; Phase 10 (§22, differential harness) unlocks a CI merge gate on semantic equivalence; Phase 11 (§23) unlocks the operator-facing CLI and the conformance report consumed by downstream CI.

Recommended language: Rust 1.83, stable channel (ADR-01). Rationale: algebraic data types via enum give an exhaustive-match AST representation; egg (Willsey et al. 2021) is the only mature, actively-maintained equality-saturation library in a mainstream systems language, and it is Rust-native; arena allocation (id-arena, slotmap) gives cache-friendly traversal without a tracing GC; proptest/insta/criterion give property, snapshot, and benchmark testing with no additional infrastructure. Rejected languages: OCaml — no equivalent of egg; adopting OCaml forces a hand-rolled e-graph, a multi-month sub-project this blueprint declines to absorb (ADR-06). Haskell — comparable ADT ergonomics but no saturation library, and a lazy-evaluation cost model that fights the explicit Fuel-based termination discipline (P4). C++ — ADTs via tagged unions/std::variant are markedly more verbose and error-prone for a match-heavy rewrite codebase, and carry no memory-safety floor under adversarial input (§24, T1).

Prerequisites (systems knowledge required): dataflow analysis and monotone lattices (Kildall 1973); SSA and why this project deliberately stops short of it (Cytron et al. 1991, contrasted in §36/A2); e-graphs and equality saturation (Tate et al. 2009; Willsey et al. 2021); classical pass-based optimization (Cooper & Torczon 2011; Muchnick 1997).

Estimated timeline: Phase 0 (§12) — 1–2 weeks (repo skeleton, correctness kernel). Full Phase 0 through Phase 11 (§12–§23) — 10–14 weeks of full-time engineering. Every deferred feature is flagged PhaseDeferred("§N.s") and registered in the Deferred Features Register (§37).

2. Why Build This

  • Bridges the typed-AST output of an external type-checker/parser front end and any downstream SSA/IR-level optimizer: without this layer, textbook rewrites (folding, DCE, inlining) either never run, or run redundantly inside the IR optimizer at a cost the AST could have paid down first.
  • Teaches tree-rewriting discipline: reading a paper-shaped rewrite rule, encoding it as a structural transform, proving it terminates (P4), and composing it with N other rewrites without oscillation (I6) — a different skill from linear-IR dataflow.
  • Teaches equality saturation (§20) as a second, orthogonal optimization paradigm: representing a program as a set of equivalent trees (an e-graph) instead of one tree, and choosing the cheapest member — directly transferable to superoptimizers and modern research compilers (Herbie, and Herbie's descendants).
  • Teaches that a cost model is a first-class, swappable artifact (P6, ADR-07): a wrong cost model silently inlines a hot loop into bloat, or lets the saturator extract a "smaller" but slower program — a lesson every optimizer author eventually learns the hard way.
  • Teaches differential/property-based verification as the actual specification of "sound rewrite" (P8) — cheaper and more honest than a hand proof, and the discipline this project treats as load-bearing, not optional test coverage.
  • Cross-links: sits upstream of any IR-level SSA optimizer (dataflow-on-a-linear-IR, Cytron et al. 1991 style — contrasted directly in §36/A2); sits downstream of a type-checker (the purity/type annotations of §13 assume a typed, well-scoped AST); shares its differential-testing discipline with any interpreter/compiler-conformance project (§28 names the same methodology family used by reference-interpreter test oracles generally).
  • Calibration value: this is the smallest project in the compiler family that forces the "rewrite, then verify" loop end to end (fold → propagate → DCE → CSE → verify) before the harder SSA/dataflow/register-allocation work; getting the loop right here de-risks every later compiler-shaped project.

What Mastery Looks Like (after building this system, the reader can):

  • Encode any textbook AST rewrite as a Rewriter with an explicit soundness guard (purity/type), and state precisely which guard each rewrite needs — Phase 3 (§15).
  • Explain why a dataflow analysis needs a monotone lattice and a fixpoint, and name the lattice's Top/Bottom/join for constant propagation — Phase 3 (§15).
  • Diagnose an oscillating pass pair (a fixpoint that never stabilizes) from a manager report alone — Phase 9 (§21).
  • Explain why equality saturation subsumes phase-ordering problems a fixed pipeline cannot, and reproduce the argument for one concrete two-rule interaction — Phase 8 (§20).
  • Design a cost model, predict which extraction it produces for a known e-graph, and change it deliberately to shift that extraction — Phase 8 (§20).
  • Build a differential-testing harness against a reference interpreter and use it to falsify an "obviously correct" rewrite — Phase 10 (§22).
  • Reason quantitatively about fuel bounds, and derive the worst-case wall-clock ceiling for a fixpoint loop from first principles — Back-of-Envelope Capacity Model (§34) / Phase 9 (§21).
  • Redesign this system as a pure-saturation optimizer or a post-lowering bytecode peephole optimizer, and state exactly what each alternative trades away — Alternative Architectures (§36).

Typed AST (input): the sole external, untrusted entry point (T1, §24) — the resolver never trusts NodeId uniqueness or well-scopedness from upstream and re-validates both (I2). Resolver & Annotator: single-threaded per module, pure function of the input AST; its output (side tables keyed on NodeId, P5) is the only state every later pass reads. Pass Manager: owns the concurrency boundary — one manager instance per module, run on an independent worker thread by the driver (§23), never shares mutable e-graph or annotation state across threads. The ten classical passes: pure Rewriter/Visitor implementations, each declaring its reads/writes/invalidates set (ADR-04, I11) so the manager can schedule safely. Equality Saturation Engine: the one component with genuinely different data-flow shape (a DAG of equivalence classes, not a tree) — bounded by fuel (I7) so it cannot dominate wall-clock time. Verifier: the trust boundary's closing gate — no optimized output is emitted to the CLI or conformance report until the interpreter agrees with the pre-optimization program (I1). Output: two persistence artifacts — the optimized AST/CLI output, and the JSON conformance report (external interface #2) consumed by CI. IR-lowering boundary: intentionally a hard stop; this project publishes a LowerToIR-shaped contract (§11) but never implements it.

6. Design Principles

P1 — Semantics Preservation Is Non-Negotiable. Rule: every rewrite applied by any pass or the saturator must satisfy interp(before) == interp(after) (I1). Tradeoff: forgoes any rewrite whose soundness cannot be checked or argued, even a profitable-looking one. Operational implication: every new pass ships with a differential-test fixture before merge (§22). Violating it: a single unsound rewrite silently compiles wrong programs — the worst failure class in this system (FM-1, §25).

P2 — Type-Directedness. Rule: every arithmetic or comparison rewrite consults the node's Type before folding (ADR-09). Tradeoff: slower folding (a Type lookup per candidate) versus a untyped-syntactic folder that is faster but silently wrong on overflow/wrap semantics. Operational implication: the folder (§15) cannot run before annotation (§13). Violating it: silent overflow/wrap bugs (§8.5's malformed-input example).

P3 — Purity Gates Rewriting. Rule: only Pure/Reads-purity subtrees may be duplicated, hoisted, or deleted (I3). Tradeoff: some genuinely-dead-looking code is conservatively kept because purity is Unknown. Operational implication: every DCE/CSE/LICM/inline decision reads AnnotTables.purity first. Violating it: reordering or deleting a side effect changes observable behavior — the same failure class as P1.

P4 — Fuel-Bounded Termination. Rule: every non-obviously-terminating pass (inliner, PE, saturator, manager fixpoint) carries an explicit Fuel counter (I4, I6, I7). Tradeoff: bounded fuel means occasionally under-optimizing rather than looping forever. Operational implication: fuel exhaustion is a reportable, testable outcome (PassReport::FuelExhausted), not a crash. Violating it: unbounded compile time is a denial-of-service vector against a crafted input (T2, §24).

P5 — Side Tables Over Inline Fields. Rule: annotations (Purity, Freshness, Cost) live in NodeId-keyed side tables, never as AST node fields (ADR-05). Tradeoff: a hash lookup per annotation read versus zero-cost field access. Operational implication: annotations evolve (new kinds, new lattices) without AST-shape churn across every crate. Violating it: adding an annotation forces a breaking change to every pattern match on Expr.

P6 — One Cost Model, Swappable. Rule: CostModel is a trait with exactly one default implementation shipped (ADR-07); nothing hardcodes cost. Tradeoff: an indirection (dynamic dispatch) on every cost query. Operational implication: the LP-based extractor and any future profile-guided cost model plug in without touching opt-saturate's core. Violating it: a hardcoded cost model blocks --exact-cost (§20) and any Phase-2 profile-guided work (§37).

P7 — Idempotency Where Cheap. Rule: a pass that can be idempotent (fold, peephole) must satisfy pass(pass(m)) == pass(m). Tradeoff: occasionally re-checking a condition already known false. Operational implication: idempotency is itself a conformance fixture (§15.5, §17.5). Violating it: hides oscillation bugs the manager's fixpoint (I6) would otherwise surface quickly.

P8 — Differential Testing Is The Oracle. Rule: every pass has a proptest differential counterpart against the reference interpreter (I1); visual inspection of a rewrite is never sufficient sign-off. Tradeoff: slower CI (running thousands of randomized cases) versus fast-but-blind unit tests. Operational implication: a pass cannot merge without its §N.5 fixtures passing. Violating it: an "obviously correct" rewrite hides a bug — see the pe-add-zero-r NaN pitfall (§17.6).

P9 — Declared Reads/Writes/Invalidates Only. Rule: no pass reads or writes an annotation it has not declared in its PassDescriptor (I11, ADR-04). Tradeoff: upfront bookkeeping per pass. Operational implication: the manager's scheduler and a CI static-analysis check (I11) both depend on this declaration being accurate. Violating it: produces stale-annotation bugs — a pass reads a Cost value another pass invalidated three rewrites ago.

P10 — Small, Curated Saturator Rules. Rule: every egg rewrite rule carries a soundness comment and a fixture (I8); the library grows by review, not by "add everything symmetric." Tradeoff: fewer rules mean occasionally missing an optimization opportunity. Operational implication: docs/saturator-rules.md is the audit trail for every rule (§20). Violating it: an uncurated symmetric rule set (e.g. blind commutativity + associativity) causes e-graph blow-up (§20.6) and unverifiable extraction.

P11 — NodeId Is Stable Within, Not Across, Parses. Rule: NodeId uniquely identifies a node within one Module value and is stable across every pass that mutates that value in place conceptually, but is never assumed stable across two independent parses of the same source (I2). Tradeoff: re-parsing forces a full annotation re-population. Operational implication: snapshot tests key on NodeId stability within a single pipeline run only (§13.4). Violating it: annotation side tables silently point at the wrong node after a re-parse.

P12 — Alpha-Rename Before Substitution. Rule: beta-reduction, inlining, and CSE-lift all alpha-rename bound names before substituting (I10). Tradeoff: extra fresh-symbol allocation per substitution. Operational implication: opt-passes::rename is a shared dependency of §17 (inline), §18 (beta), and §16 (CSE-lift). Violating it: variable capture — a silent, semantics-changing bug (§17.6, §18.6 pitfalls).

P13 — Deterministic Scheduling. Rule: the same PassRegistry plus the same input Module always produces the same pass schedule and the same fixpoint trace (ADR-04). Tradeoff: no adaptive/randomized scheduling, even where it might help. Operational implication: bug reports are reproducible from a (registry, module) pair alone. Violating it: an irreproducible optimizer bug is nearly undebuggable — the single worst property for an on-call engineer to inherit.

P14 — No Implicit Profile Data. Rule: the optimizer never reads runtime profile data absent an explicit ADR admitting a new input channel (ADR-08 locks the Phase-0 inliner to static heuristics only). Tradeoff: static heuristics under-perform profile-guided decisions in some workloads. Operational implication: builds stay reproducible and profile-independent — two builds of the same commit produce byte-identical optimizer output. Violating it silently breaks the reproducible-build guarantee (§29).

8. Domain Model

8.1 Locked Input AST Grammar

The EBNF below is the locked Phase-0 surface. Phase-1+ extensions require an ADR.

Module    ::= Decl*
Decl      ::= "let" Ident "=" Expr
            | "let" "rec" Ident Param+ "=" Expr
            | "type" Ident TypeParam* "=" AdtBody
Expr      ::= Lit
            | Ident
            | "fn" Param+ "->" Expr
            | Expr Expr                            (* application *)
            | "let" Ident "=" Expr "in" Expr
            | "if" Expr "then" Expr "else" Expr
            | "match" Expr "with" Arm+
            | "{" Field* "}"                        (* record *)
            | Expr "." Ident                        (* projection *)
            | "{" Expr "with" Ident "=" Expr "}"     (* row update *)
            | "(" Expr ":" Type ")"                  (* ascription *)
            | "loop" Block                           (* explicit loop, for LICM *)
            | "while" Expr Block                     (* sugar over loop *)
Param     ::= Ident (":" Type)?
Field     ::= Ident "=" Expr
Arm       ::= "|" Pat "->" Expr
Pat       ::= "_" | Ident | Lit | Ident Pat* | "{" PatField* "}"
Lit       ::= Int | Float | Bool | String | Unit

Every node carries a Span and a NodeId (I2). Annotations hang off NodeId in side tables (P5), never on the node.

Show the original text diagram

Join (⊔): Bottom ⊔ x = x; Const(v) ⊔ Const(v) = Const(v); Const(v1) ⊔ Const(v2) = Top (v1 ≠ v2); Top ⊔ x = Top. Monotonicity across worklist iterations is what makes the propagator (§15) terminate in at most |nodes| steps before reaching a fixpoint (Kildall 1973).

8.4 Worked Example (fold → propagate → DCE → CSE trace)

Source: let x = 1 in let y = x + 2 in let _ = pure_call() in y + y

Step Fact / Rewrite Applied Resulting Fragment
0 (Annotated) pure_call marked Purity::Unknown (no callee body visible) unchanged
1 (Propagate, §15) x ↦ Const(1) reaches its one use let y = 1 + 2 in let _ = pure_call() in y + y
2 (Fold, §15) 1 + 2 → 3 (type-directed, P2) let y = 3 in let _ = pure_call() in y + y
3 (Propagate, §15) y ↦ Const(3) reaches both uses let _ = pure_call() in 3 + 3
4 (Fold, §15) 3 + 3 → 6 let _ = pure_call() in 6
5 (DCE, §16) binding for _ is kept — pure_call's purity is Unknown, I3 forbids deletion unchanged (I3 guard fires)
6 (CSE, §16) no duplicate pure subterms remain unchanged — fixpoint reached in 4 manager iterations

Final verified output: let _ = pure_call() in 6, and interp on both the original and the final form agree for every generated environment (I1).

8.5 Malformed-Input Example

Input: an Expr::Var { name, .. } whose Symbol has no reaching Decl/Param/Arm binder — a well-scopedness violation that should never reach the optimizer given the upstream contract (§1), but which the resolver (§13) defensively rejects rather than assumes away. Detected by I5 (WellFormedCheck) immediately after annotation, before any pass runs; the manager refuses to schedule and returns ManagerReport::RejectedInput { reason: DanglingVar(node_id) } rather than silently treating the variable as Unknown-typed garbage — the alternative (silent acceptance) is precisely the P2 violation class illustrated by folding 1 / 0-shaped inputs without a type check.

8.6 Failure-Path Example

During Phase 8 saturation (§20) on an adversarial fixture containing 40 nested applications of add-comm/add-assoc, the e-graph reaches the 50,000-e-node ceiling (I7) before reaching the iteration limit. Runner::stop_reason reports NodeLimit; the engine extracts from the graph as it stands (still sound, per I7's recovery clause) rather than continuing unboundedly. SaturationReport.iterations and .stopped_reason are logged (saturate.stopped_reason{node_limit} telemetry, §26), and the conformance report (§28) marks the case Pass (partial-saturation) rather than Fail, because I1 — not saturation completeness — is the correctness contract.

15. Phase 3 — Constant Folding & Constant Propagation

15.1 Objectives

15.2 Detailed Implementation Steps

15.3 Deliverable

16. Phase 4 — Dead-Code Elimination & Common Subexpression Elimination

16.1 Objectives

Land dce.rs (purity-gated deletion of unused pure bindings) and cse.rs (hash-consing pure subexpressions into a shared let), the two classical redundancy-elimination passes that complete the Phase-3 pair per Cooper & Torczon 2011 ch. 8–10's value-numbering lineage.

16.2 Detailed Implementation Steps

DCE: a Let-bound value is dead iff (1) Purity::Pure (I3, P3), (2) unused in the use-def graph, and (3) deleting it does not change any sibling's evaluation order. CSE: hash-cons every pure expression by structural equality (post alpha-renaming, P12 — unrenamed variables make (fn x -> x+1) and (fn y -> y+1) hash differently); on a duplicate, replace the second occurrence with a Var reference to a let-lifted binding inserted at the lowest enclosing block that dominates both occurrences (Cooper & Torczon 2011's value-numbering placement rule, adapted to a tree walk since no explicit dominator tree exists at the AST level).

16.3 Deliverable

opt-passes::{Dce, Cse} composed after the Phase-3 pair, demonstrated on f(a + b) + g(a + b) → let cse_0 = a + b in f(cse_0) + g(cse_0).

16.4 Acceptance Criteria

  • DCE on let rec — the recursive binding's value is its own use; never delete solely because the body doesn't reference it (a distinct rule from ordinary let).
  • Useless-match-arm detection is explicitly out of Phase-4 scope — a separate pattern-analysis pass, PhaseDeferred("§16").
  • Lifting an impure expression in CSE — guard strictly with Purity (P3).

16.9 Failure Analysis

An over-aggressive DCE that deletes a Writes-purity binding is a P1/I1 violation caught by the differential harness; blast radius is silent effect loss (e.g. a dropped logging call) — one of the harder bugs to notice by inspection, which is exactly why P8 makes the harness mandatory rather than advisory.

18. Phase 6 — Partial Evaluation & Beta/Eta Reduction

18.1 Objectives

Land partial_eval.rs (online, fuel-bounded specialization, ADR-10) and beta.rs/eta.rs (capture-safe beta and eta reduction) — grouped because partial evaluation is, mechanically, repeated fuel-bounded beta-reduction against known-constant arguments (Reynolds 1972; Plotkin 1975 on the underlying calculus).

18.2 Detailed Implementation Steps

Partial evaluator: walks the AST, reduces calls whose arguments are Lit-constant or Freshness::Fresh, specializing fn x y -> x + y applied to 1 into fn y -> 1 + y (then folded, §15, to fn y -> y + 1); bounded by a per-top-level-call fuel counter (default 4,096, ADR-10, P4) so recursive specialization cannot diverge (Jones et al. 1993's online-PE termination concern). Beta: (fn x -> e) v → e[v/x] when v is pure or fresh (P3); when v is Aliased, lifts via let x = v in e instead of substituting, to avoid duplicating a side effect. Eta: (fn x -> f x) → f when f is pure and x is not free in f (an impure f must not be eta-reduced — reduction would change the timing of f's side effect relative to the call site).

18.3 Deliverable

opt-passes::{PartialEvaluator, Beta, Eta}; the canonical demonstration is power(x, 3) (power n x = if n==0 then 1 else x * power(n-1,x)) specializing to x * x * x after fuel-bounded unrolling.

19. Phase 7 — Loop-Invariant Code Motion & Tail-Call Detection

19.1 Objectives

Land licm.rs (hoist loop-invariant pure expressions to a preheader, Knoop, Rüthing & Steffen 1992) and tail_call.rs (annotate calls in tail position for the downstream IR-lowering boundary, Steele 1978) — grouped as the two passes whose output is consumed primarily outside this pass pipeline (LICM feeds the saturator's cost model in §20; tail-call annotations feed the downstream IR lowering, ADR-15).

19.2 Detailed Implementation Steps

LICM: computes the use-def graph for a Loop body; an expression is invariant iff every free variable it uses is either defined outside the loop or is itself invariant (a fixpoint over the body, same worklist machinery as §14/§15); invariant Purity::Pure expressions are hoisted to a preheader let wrapping the loop (P3 guard: an impure expression is never hoisted, even if syntactically loop-invariant, since hoisting changes when it executes). Tail-call detection: an App in tail position iff the enclosing function's body reduces to it directly, or transitively through the tail positions of if/let/match branches (the structural definition in §8.2's table, adapted from Steele 1978); the result is a TailPosition annotation added to the NodeId side table (P5), consumed by the LowerToIR contract (§11) — never acted on within this project (ADR-15).

19.3 Deliverable

opt-passes::{Licm, TailCall}; the canonical LICM demonstration is loop { x = a + b; ... } (with a, b defined outside) hoisting a + b to a preheader let; the canonical tail-call demonstration is a self-recursive loop-style function having its recursive call annotated TailPosition::Yes.

19.4 Acceptance Criteria

The LICM example hoists exactly as stated on 1,000 differentially-tested loop fixtures (I1); a non-tail f x + 1 is annotated TailPosition::No; let rec loop n = if n == 0 then () else loop (n - 1) annotates its recursive call TailPosition::Yes, verified by a snapshot of the annotation table (stable across reruns, I12).

passes/licm/impure-not-hoisted.lock (negative) impure loop-invariant-looking expr not hoisted

  • Lifting an impure expression in LICM — guard with Purity exactly as DCE/CSE do (P3); the "loop-invariant" property is purely syntactic and says nothing about effect safety.
  • Lifting past a conditional that guards a fault (e.g. a division only safe inside the guard) — move only into the dominator chain the loop already unconditionally executes, never past a guard.
  • A try/catch-wrapped call is never in tail position, because its result must still be inspected by the handler — Phase-0's surface language has no exception handling, so this is a forward-looking note for Stretch.4-style effect extensions (§37).

19.7 Performance Concerns

19.8 Edge Cases

A loop with zero invariant subexpressions (LICM is a no-op, not an error); a match where every arm's body is in tail position except one (the whole match is not uniformly tail — annotate per-arm, not per-match); nested loops (LICM hoists to the nearest enclosing preheader, not the outermost, unless the inner hoist target is itself invariant relative to the outer loop too — a second fixpoint iteration catches this via the manager's overall fixpoint, §21).

19.9 Failure Analysis

An unguarded LICM hoist past an effect is a P1/I1 violation caught by the differential harness; blast radius is any loop containing the hoisted effect — potentially every iteration's worth of a side effect collapsed to one, a highly visible bug once triggered, mitigated by requiring the 1,000-fixture differential gate (19.4) before merge.

19.10 Operational Notes

LICM dump reports hoisted_count/preheaders_created; tail-call dump reports tail_annotations{yes,no} — both consumed by docs/runbooks/regression-triage.md, and the tail-call annotation is additionally exported verbatim in the OptimizeResult payload (§11) for the downstream IR-lowering consumer to read (ADR-15).

20. Phase 8 — Equality Saturation Engine

20.1 Objectives

Land opt-saturate: an e-graph built on egg 0.9 (ADR-06), a curated rewrite library (P10, I8) including every peephole rule from §17.5 plus associativity/commutativity/distributivity rules, a swappable CostModel (P6, ADR-07), and greedy/LP extractors (ADR-20) — the second optimization paradigm this project deliberately runs alongside, not instead of, the pass pipeline (Click & Cooper 1995's argument, realized concretely).

20.2 Detailed Implementation Steps

Represent a Module as an e-graph: each equivalence class (e-class) holds a set of equivalent e-nodes; a rewrite LHS ⟺ RHS adds RHS to LHS's e-class without removing LHS (Tate et al. 2009's core idea). Saturation runs the curated rule set to a fixpoint or fuel exhaustion (I7: ≤1,024 iterations OR ≤50,000 e-nodes) via egg::Runner. The rule library (§20's table below) mirrors every §17.5 peephole rule bidirectionally, plus add-comm/add-assoc/mul-comm/mul-assoc/distrib/factor and the fold rules from §15 — every rule carries a soundness comment in docs/saturator-rules.md (I8, P10). CostModel::cost defaults to node count plus a memoization penalty for shared subterms (ADR-07); the default extractor is egg's greedy Extractor, with an LP-based exact extractor behind --exact-cost (ADR-20).

20.3 Deliverable

opt-saturate::{Saturator, AstCostModel} implementing SaturationEngine/CostModel (§11); demonstrated on (a + b) + c under add-assoc, which saturates and extracts a cost-equivalent form without re-associating during the extraction step (size-1 cost makes both forms tie, exercising the extractor's tie-break rule).

20.4 Acceptance Criteria

The (a+b)+c example saturates and extracts as stated; a 200-line fixture saturates in ≤ 100 ms with the curated rule set (§4/§30); a differential test confirms the extracted program matches the interpreter on 5,000 random fixtures (I1); the node-limit failure path of §8.6 is exercised by a dedicated adversarial fixture and reports stopped_reason=NodeLimit rather than crashing.

20.5 Conformance Fixtures

Fixture Purpose Expected
saturate/rules/assoc-comm.lock (a+b)+c under add-assoc cost-equivalent extraction
saturate/rules/peephole-parity.lock every §17.5 rule mirrored saturator and peephole pass agree
saturate/extraction/200-line.lock perf fixture ≤100ms saturation
saturate/extraction/node-limit-adversarial.lock (negative) 40 nested comm/assoc applications stopped_reason=NodeLimit, sound partial extraction

20.6 Pitfalls

  • Saturation explosion — add-comm + add-assoc together grow the e-graph quadratically; fuel (I7) is the mandatory safety net, not an optional tuning knob.
  • Extracting an unsoundly-equivalent term — the rewrite library must be reviewable; docs/saturator-rules.md's "rule → soundness justification" table is the audit trail (I8).
  • Cost-model bugs masquerading as extractor bugs — a rewrite that "should" be cheaper but isn't reveals a CostModel bug, not an extractor bug; the extractor is trusted to pick the argmin of whatever cost function it is given (MM6, §32).
  • Letting the e-graph extractor pick the largest term because of a cost-model sign error — always snapshot-test the cost surface directly, not just the final extraction.

20.7 Performance Concerns

The 50,000-e-node ceiling (I7, §4) bounds worst-case memory to ≈6 MB of e-graph structure (§34/#2); the greedy extractor is O(e-classes) while the LP extractor is exponentially worse in the general case — --exact-cost is opt-in precisely because of this tradeoff (ADR-20).

20.8 Edge Cases

A rule whose LHS and RHS are syntactically identical (a no-op rule — harmless but should be lint-flagged as dead weight); an e-class containing a cycle of purely-equal-cost members (extractor must apply a deterministic tie-break, P13, never pick nondeterministically); a module too small to trigger any rule (saturation terminates in 0 meaningful iterations, not an error).

20.9 Failure Analysis

An unsound rule shipping to production is the single worst failure this phase can produce (P1/I1 violation) — mitigated by requiring every rule to pass its own differential fixture (20.5) before merge, in addition to the aggregate 5,000-case test; a node-limit hit mid-saturation is not a failure (I7's defined recovery is sound partial extraction, §8.6) and must not be conflated with one in the conformance report.

20.10 Operational Notes

saturate.stopped_reason{iteration_limit,node_limit,saturated} and saturate.egraph_size are the two telemetry series operators watch; a sustained shift toward node_limit across commits indicates rule-set growth outpacing the fuel budget and should trigger a docs/runbooks/regression-triage.md review before the ceiling itself is raised. Making the LP-cost extractor the default (rather than opt-in via --exact-cost, ADR-20) remains deferred pending benchmark data showing its solve time is negligible on the standard corpus — PhaseDeferred("§20").

21. Phase 9 — Full Pass Manager: Scheduling, Fixpoint, Fuel

21.1 Objectives

Land the complete opt-manager: the dependency-graph scheduler (ADR-04), the fuel-bounded fixpoint driver (I6, P4), and the per-pass dump writer — upgrading Phase 2's skeleton (§14) into the real orchestrator every later phase's passes compose under.

21.2 Detailed Implementation Steps

PassDescriptor.{reads,writes,invalidates} (§11) feeds a topological sort producing a deterministic pass order (P13); a pass that both reads and writes the same annotation (a cycle in the naive dependency graph) is resolved by the fixpoint loop rather than by ordering trickery (ADR-03's explicit design choice, contra LLVM's legacy PM cited in §5's reference implementations). run_to_fixpoint runs the ordered pass list once per iteration, compares the resulting Module against the prior iteration by structural equality, and halts either on stability or at iter > max_iter=32 (I6). Every pass invocation writes a before/after snapshot to target/opt-dumps/<run-id>/<n>-<pass>.{before,after}.txt, snapshot-tested via insta (ADR-12) for determinism (P13).

21.3 Deliverable

opt-manager::{Manager, PassRegistry} orchestrating the full 11-pass pipeline (fold → propagate → dce → cse → inline → peephole → partial_eval → beta → eta → licm → tail_call) to a fixpoint on every examples/*.lock fixture.

21.4 Acceptance Criteria

A four-pass run (fold → propagate → dce → cse) terminates in fewer than 8 iterations on every Phase-0 fixture; the full 11-pass run terminates within the max_iter=32 cap on 100% of the conformance corpus (§28); dump output is byte-stable across reruns of the same input (I12); a regression test confirms the scheduler never violates a declared reads/writes ordering constraint (I11).

21.5 Conformance Fixtures

Fixture Purpose Expected
manager/scheduling/four-pass-fib.lock fold→prop→dce→cse <8 iterations
manager/scheduling/oscillation-synthetic.lock (negative) crafted fold/dce/cse cycle caught at max_iter, ManagerReport::Unstable
manager/scheduling/dump-determinism.lock 3 consecutive runs byte-identical dumps

21.6 Pitfalls

  • Two passes oscillating ("fold makes a let, dce removes it, cse adds it back") — the fixpoint loop catches this via max_iter, but oscillation itself is a smell; triage by adding a tie-breaker rule to one of the passes, not by raising the cap.
  • Forgetting to invalidate an annotation in PassDescriptor.invalidates — a later pass reads a stale Cost/Freshness value and produces a wrong (though not necessarily unsound) rewrite decision, degrading optimization quality silently.
  • Treating the dump writer as optional under disk pressure — losing it removes the only operator-facing view into "why did the optimizer produce this," making regression triage (§16.10 onward) impossible.

21.7 Performance Concerns

Structural-equality comparison between iterations is the fixpoint loop's main per-iteration cost — bound it to O(n) via a cached structural hash rather than a full deep-equality walk on every iteration (the same hash-consing machinery CSE already builds, §16.2, reused here).

21.8 Edge Cases

A PassRegistry with zero passes registered (the fixpoint loop must terminate in 1 iteration, trivially stable); a pass that mutates Module but reports PassReport as a no-op (a descriptor-honesty bug caught by I11's static check, not by the fixpoint loop itself); disk-full during dump writing (the manager must degrade to in-memory-only dumps with a logged warning, never crash the optimization run over an observability failure).

21.9 Failure Analysis

Hitting max_iter without stabilizing (ManagerReport::Unstable) is reported, not silently swallowed — blast radius is a possibly-under-optimized (but still I1-sound, since every constituent pass individually holds I1) output; recovery is triaging the oscillation per 21.6 and adding a permanent regression fixture once root-caused.

21.10 Operational Notes

manager.max_iter_hit and manager.iterations_to_fixpoint (a histogram) are the two headline telemetry series; a rightward shift in the iterations histogram across a release is treated as a performance regression under §30's gate even absent an Unstable report.

22. Phase 10 — Differential Verification Harness

22.1 Objectives

Land opt-verify's full harness: the tree-walk reference interpreter (extending Phase 0's Lit/Var-only stub to the complete Expr grammar), the proptest generation strategy, and the regression corpus — the mechanical realization of I1 and the gate every prior phase's acceptance criteria have referenced.

22.2 Detailed Implementation Steps

Extend interp (§8's oracle) to cover every Expr variant, correctness over speed (§1 non-goal ordering); implement arb_expr(depth) as a proptest::Strategy, calibrated so 80% of generated expressions terminate within 1 ms of interpretation and the remaining 20% trip an explicit step-count ceiling in the interpreter (never an unbounded loop, mirroring P4's fuel discipline at the oracle level too). Wire Verifier::diff to run the before/after Module pair through interp on a shared input set and report a DiffReport (mismatch details, not just pass/fail) on disagreement. Populate tests/regression/ with every minimized counter-example any prior phase's development produced.

22.3 Deliverable

opt-verify::{interp, Verifier, arb_expr} wired as the mandatory gate behind every pass's differential-test acceptance criterion cited in §15–§21.

22.4 Acceptance Criteria

A 5,000-case proptest run is green; the regression corpus under tests/regression/ holds at least 50 minimized counter-examples accumulated from Phase-0 development; a coverage report shows > 85% of opt-passes lines exercised by the harness; float comparison uses bit-pattern equality (f64::to_bits), never ==, per the interpreter's NaN-safety requirement.

22.5 Conformance Fixtures

Fixture Purpose Expected

verify/diff/float-bitpattern.lock NaN/signed-zero comparison bit-pattern equality, not ==
verify/regression/<50 minimized cases>.lock permanent regression corpus all green, forever
verify/diff/nonterminating-guard.lock (negative) crafted non-terminating program step-count ceiling trips, no hang

22.6 Pitfalls

  • A non-terminating program slipping into the corpus — bound the interpreter's step count explicitly (mirrors P4 at the oracle level, not just in the optimizer).
  • A floating-point divergence bug hidden by == comparison — always compare via f64::to_bits for Value::Float.
  • Treating "harness is green" as sufficient without checking coverage — the >85% line-coverage acceptance criterion (22.4) exists because a green harness with low coverage is a false sense of security (P8's full intent).

22.7 Performance Concerns

The ≤2 s Phase-1 target for 1,000 differential cases (§4/§30/M8) implies each case's generate+interpret×2+compare budget is ≤2 ms; the interpreter must sustain ≥500 evals/sec at arb_expr's default depth bound of 6 (≤127 nodes/expr, §34/#6).

22.8 Edge Cases

An expression whose evaluation order is unspecified upstream but happens to be deterministic in this interpreter (documented as an interpreter implementation choice, not a language-semantics guarantee, to avoid passes silently relying on it); a generated expression that triggers integer overflow in the interpreter itself (must wrap identically to the folder's semantics, §15.8, or the oracle and the optimizer disagree about ground truth).

22.9 Failure Analysis

A harness false-negative (reporting agreement when the two programs actually differ) is the single most dangerous bug this project can contain, since it silently defeats every other phase's correctness gate; mitigated by mutation-testing the harness itself (deliberately injecting an unsound rewrite into a test double and confirming the harness catches it) as part of opt-verify's own test suite.

22.10 Operational Notes

verify.mismatch (should be 0 in CI), verify.coverage_pct, and verify.regression_corpus_size (monotonically non-decreasing) are the three telemetry series gating every merge; a PR that would decrease regression_corpus_size is rejected by CI outright.

23. Phase 11 — Driver, CLI & Conformance Suite

23.1 Objectives

Land opt-driver (the CLI: optimize/dump-passes/bench/saturate) and opt-conformance (the fixture runner producing the machine-checked JSON report) — the two operator-facing surfaces that make every prior phase's work consumable outside a cargo test invocation.

23.2 Detailed Implementation Steps

opt-driver exposes four subcommands mapping to four optimization profiles: O0 (no-op), O1 (fold, propagate, dce, cse, peephole), O2 (O1 + inline + partial_eval + beta + eta + licm), saturate (O2 + the saturator, §20). Each profile is a fixed, snapshot-tested pass list (P13: no silent profile drift). opt-conformance reads conformance/fixtures/{positive,negative}/<pass>/<case>.lock plus its .expected.json, runs each through the driver at the fixture's declared profile, and emits a report matching report.schema.json, exiting non-zero on any Fail bucket (§28's bucket-outcome table).

23.3 Deliverable

opt optimize examples/fib.lock --profile=O2 producing a valid, interp-agreeing module; opt dump-passes producing a deterministic dump directory; make conformance producing a schema-valid JSON report with every Phase-0 bucket Pass.

23.4 Acceptance Criteria

CLI cold-start ≤ 50 ms (§4); opt optimize examples/fib.lock --profile=O2 agrees with interp (I1); opt dump-passes examples/fib.lock --out-dir /tmp/dumps produces byte-identical output across 3 runs; every Phase-0 conformance bucket (§28's table) reports Pass; every Phase-1-target bucket reports Deferred with a blueprint_ref naming the phase it awaits (§37).

23.5 Conformance Fixtures

Fixture Purpose Expected

23.6 Pitfalls

  • Profile drift — a profile that silently changes its pass set breaks every downstream regression baseline; snapshot the profile manifest (23.4) explicitly.
  • CLI options that overlap or conflict (e.g. --profile=O0 --exact-cost) — validate combinations before running, fail fast with a named error, not a silently-ignored flag.
  • Treating conformance Deferred buckets as Pass in a summary rollup — the two must remain visibly distinct in the report (§28).

23.7 Performance Concerns

CLI argument parsing and cold-start must not regress the ≤50 ms budget (§4) as subcommands accumulate; the conformance runner should parallelize independent fixture buckets (rayon, same pool as the module-level concurrency in §4) rather than running the corpus serially.

23.8 Edge Cases

A fixture file that fails to parse at all (reported as a harness-level error, distinct from an optimization-outcome Fail); a conformance run against a partially-populated conformance/fixtures/ directory (missing buckets are reported Missing, never silently skipped); --out-dir pointing at a non-writable path (fail with a clear I/O error, not a panic).

23.9 Failure Analysis

A non-zero-exit conformance run blocks CI merge by design (§28); a false-Pass bucket (a fixture that should fail but the runner mis-scores) is the worst failure here, since it defeats the entire gate — mitigated by I12 (bucket-outcome stability across two runs) and by a small set of deliberately-broken canary fixtures expected to always fail, checked every CI run.

23.10 Operational Notes

The conformance JSON report is archived as a CI artifact per run (docs/runbooks/conformance.md); opt dump-passes output under target/opt-dumps/ is cleaned per the retention policy in §29, never committed to version control.

26. Operational Readiness

Metrics: every counter/histogram named in §24/§25/phase N.10 sections is exported as a tracing-derived metric (metrics crate facade) to a local Prometheus-textfile exporter consumed by CI dashboards — there is no long-running service to scrape live. Tracing: tracing spans wrap each pass invocation and each manager iteration, correlated by a per-run UUID that also names the target/opt-dumps/<run-id>/ directory (§21.2). Structured logging: JSON-formatted tracing-subscriber output at info for manager/driver lifecycle events, debug for per-pass decisions, trace for per-node annotation reads. Dashboards: a single CI-artifact dashboard (docs/runbooks/regression-triage.md-linked) plots manager.iterations_to_fixpoint, saturate.egraph_size, and verify.mismatch per commit. Alerting philosophy: alert on trend, not single-sample noise — a single manager.max_iter_hit is logged; three in a rolling 20-commit window pages the on-call compiler engineer. SLOs: 0 verify.mismatch per release (I1); ≤15 min median bisection time (FM-1); 100% Phase-0 conformance-bucket pass rate (§28). Incident response: FM-1 (miscompilation) is Sev-1 — halts the release channel (§29) until bisected and reverted. Named runbooks: docs/runbooks/{conformance,release,regression-triage}.md. Backup/restore: the durable state is git history plus the regression corpus (§22.4) and conformance fixtures — both live in version control, so "backup" is the repository's own remote mirror policy, not a separate data store. Deployment topology: no persistent deployment — the CLI binary ships via GitHub Releases and (Phase-1+) crates.io; a "deployment" is a tagged release artifact. Canary strategy: a small set of deliberately-broken canary fixtures (§23.9) must always fail, checked every CI run, verifying the harness itself has not silently stopped detecting failures. Rolling-upgrade/rollback/migration: not applicable to a batch CLI with no persistent server state; "rollback" means reverting to the prior release tag, and "migration" means an AST-grammar extension governed by §27's compatibility policy.

27. Compatibility & Versioning

Wire/on-disk format: the .lock fixture format and the conformance/schema/{fixture,report}.schema.json pair are versioned independently via a schema_version field; a breaking schema change bumps schema_version and ships a migration note in CHANGELOG.md. AST grammar (§8.1): append-only within Phase-0 — a new Expr/Decl/Pat variant is additive and requires an ADR (extending §9); removing or changing an existing variant's fields is a breaking change requiring a major version bump of opt-syntax. API stability: every crate in §10 follows SemVer; opt-syntax, opt-annot, and opt-visitor are the "core" crates whose public trait signatures (§11) are the most conservatively versioned, since every other crate depends on them. Migration: an AST-grammar extension ships with a docs/adr/adr-NN-*.md plus a migration note in docs/runbooks/; existing .lock fixtures are re-validated, never silently reinterpreted under the new grammar. Deprecation policy: a deprecated Pass/trait method is marked #[deprecated] for one minor version before removal, consistent with the reproducible-build guarantee (P14) — deprecation never silently changes optimizer output mid-cycle. SemVer policy: patch = bugfix/perf only (no behavior change to any PassDescriptor or profile manifest, §23.6); minor = additive (new pass, new ADR-backed rule); major = any change to the locked AST grammar (§8.1), the LowerToIR contract (§11), or a profile's pass list. Rolling-upgrade guarantees: not applicable (§26) — every release is a fresh, independently-versioned CLI binary with no in-place upgrade path to reason about.

30. Performance Engineering

Benchmarking methodology: criterion (ADR-18) micro-benchmarks per pass under benchmarks/kernels/*.lock, run in CI with a >5% regression gate against benches/baseline.json. Profiling: perf/flamegraph for allocation and cache-locality analysis on the arith.lock/loop-sum.lock kernels; allocation profiling specifically targets the fold/propagate hot path (§15.7) and CSE's hash-consing (§16.7). Lock contention: not applicable within a single manager instance (single-threaded by design, §4); the driver's rayon worker pool is analyzed for scheduling overhead only, not lock contention (each worker owns an independent Module). Cache analysis: id-arena (ADR-14) keeps AST nodes contiguous per-arena, the basis for the §4 throughput floor. Syscall overhead: the dump writer batches writes per pass rather than per node (§21.2), avoiding a syscall-per-node antipattern. Tail-latency analysis: p99 saturation time on the adversarial node-limit fixture (§20.5) is tracked separately from the p50/p95 curated-rule-set path, since I7's fuel bound caps the tail explicitly.

31. Scalability Analysis

What stays constant: per-node annotation footprint (~64 B/node, §34/#1) and per-pass algorithmic complexity (O(n) for fold/propagate/DCE/CSE/peephole, §16.7) regardless of module count, because each module is optimized independently (no cross-module state, §1 non-goal). What grows: total wall-clock and memory scale linearly with module count under the batch driver (§23), and the e-graph's worst-case size scales with the curated rule set's density (P10) more than with input size directly. Named bottlenecks, in order: (1) the saturator's e-graph growth under commutativity/associativity rules (§20.6) — the largest single per-module cost; (2) the manager's fixpoint iteration count when passes interact poorly (§21.6); (3) inliner-driven code growth feeding back into every subsequent pass's per-node cost (§17.7). Horizontal scaling: the batch driver parallelizes across modules (rayon, ≤64 workers, §4) — embarrassingly parallel since modules share no mutable state; this is the primary lever for whole-codebase throughput. Vertical scaling: per-module optimization is single-threaded by design (ADR-03's simplicity argument) — a faster core helps linearly, more cores per module do not (no intra-module parallelism in Phase-0, PhaseDeferred("§20") for a Phase-2 work-stealing parallel saturator). Sharding/partitioning: modules are the natural shard boundary; no partitioning is needed within a module because the AST fits in memory at the §4 ceiling (500,000 nodes). Coordination overhead: zero cross-worker coordination in Phase-0 (independent modules); the only shared resource is the FD budget for dump writing (§4/§34/#7), which is why the worker cap exists. Practical ceiling: ~64 concurrent modules bounded by the FD/worker cap (§4), and ~500,000 nodes/module bounded by the §4 memory ceiling at 200 MB/10K-LOC scaling. Levers beyond the ceiling: raise the FD/worker cap with a larger open-file ulimit (linear cost, no architecture change); introduce cross-module fusion (PhaseDeferred("§31"), this section) to amortize saturator setup cost across modules — a genuinely different architecture, not a parameter tweak, and therefore deferred rather than tuned.

32. Mental Models & First Principles

MM1 — An e-class is a set of equivalent programs, not a program. Predicts: saturation subsumes phase-ordering because it never commits to one rewrite direction. Bug class without it: assuming the e-graph has "the current program" and trying to read one out mid-saturation. Applies in §20.

MM2 — A pass is a monotone step toward a fixpoint, not a one-shot transform. Predicts termination behavior and why re-running a pass twice is meaningful (P7). Bug class without it: writing a pass that "does its one job" and being surprised the manager reruns it (§21). Applies in §21, I6.

MM3 — Purity is a lattice, not a boolean. Predicts float-NaN and partial-purity edge cases (an op that reads but never writes). Bug class without it: treating any "probably safe" op as reorderable. Applies in §13, §8.3.

MM4 — Fuel converts undecidable termination into decidable termination. Predicts fuel-exhaustion diagnostics are a normal, expected outcome, not a bug. Bug class without it: assuming the optimizer "always finishes" and treating FuelExhausted as an error to suppress rather than report. Applies in §17, §18, §20, P4.

MM5 — A rewrite is only as sound as its purity/type guard, never as sound as its algebra. Predicts why some algebraically-true identities (x + 0 = x) are unsound in code (signed zero, NaN). Bug class without it: porting a textbook identity verbatim into a peephole rule. Applies in §15, §17.

MM6 — Cost models are policy, not law. Predicts why the extractor's output changes when only the cost model changes, with the same rule set (P6). Bug class without it: blaming the extractor for a bad extraction that is actually a cost-model bug. Applies in §20, ADR-07.

MM7 — The differential harness is the specification, not a test suite bolted onto one. Predicts why a rewrite without a passing differential fixture is not "probably fine" — it is simply unspecified (P8). Bug class without it: merging a rewrite on code-review confidence alone. Applies in §22.

MM8 — NodeId is identity; structural equality is not. Predicts subtle bugs in hash-consing/CSE where two structurally-identical-but-differently-NodeId'd subtrees must still be treated as distinct annotation-table keys until explicitly unified. Bug class without it: an annotation lookup silently keyed on the wrong node after a clone. Applies in §11, §16.

34. Back-of-Envelope Capacity Model

  1. Peak memory, 10K-LOC module: 10,000 LOC × 8 nodes/LOC (empirical AST density) = 80,000 nodes. Per-node footprint ≈ 96 B (Expr variant + Span + Type pointer) + ≈64 B annotation-side-table overhead (3 HashMaps, amortized) = 160 B/node. 80,000 × 160 B ≈ 12.8 MB baseline; saturation's e-class duplication (~4× during Phase 8, §20) before extraction ⇒ ≈ 51 MB peak — within the ≤200 MB/10K-LOC ceiling (§4).
  2. Saturator e-graph structural ceiling: fuel = 50,000 e-nodes (§4) × ≈120 B/e-node (ENode<AstLanguage> + e-class metadata) ≈ 6 MB e-graph ceiling.
  3. Per-pass throughput derivation: O1 @ 10K LOC in ≤100 ms (§4/M1, Phase-1) ⇒ 80,000 nodes / 0.1 s = 800,000 nodes/sec sustained across 5 passes (fold, propagate, dce, cse, peephole) ⇒ per-pass budget ≈ 4,000,000 nodes/sec/pass single-threaded (matches §4's throughput floor exactly).
  4. Manager worst-case wall time: max_iter=32 (§4/ADR-03) × 5 passes/iteration × (80,000/4,000,000) s per pass ≈ 32 × 5 × 0.02 s = 3.2 s worst-case ceiling. Compared against the ≤400 ms O2 target (M2): confirms typical convergence is ~8× faster than worst case, consistent with the empirical "fewer than 8 iterations" acceptance criterion (§21.4).
  5. Inliner growth bound: fuel = 1,024 inlines/run (§4/ADR-08) × Cost.size ≤ 30 nodes/inline (worst case) = ≤ 30,720 injected nodes/run; against the 80,000-node baseline that bounds inliner-driven growth to ≤ 38% (M12).
  6. Differential-harness throughput: 1,000 cases in ≤2 s (Phase-1, M8) = 500 cases/sec ⇒ ≤2 ms/case budget (generate + interpret×2 + compare); at arb_expr's default depth bound of 6 (≤127 nodes/expr, §22.7), the interpreter must sustain ≥500 evals/sec on generated expressions of that size.
  7. FD/concurrency budget: N worker threads (rayon) × 2 FDs/worker (1 read + 1 write for dumps) = 2N; at the §4 cap of 64 workers/batch, FD ceiling = 128 — well under a typical 1024 soft ulimit.
  8. Storage amplification (pass dumps): each pass writes before+after text dumps (~1.2× source size each) × up to 11 passes (O2 profile) ⇒ ≈ 11 × 2 × 1.2 = 26.4× the original source size in transient dumps per run — a 1 MB source file produces ≈26 MB of transient dump data, cleaned per the §29 retention policy.

36. Alternative Architectures (Roads Not Taken)

A1 — Pure Equality-Saturation Optimizer (no pass pipeline at all).

Show the original text diagram
Typed AST -> single e-graph (whole module) -> saturate to fixpoint -> extract -> Verifier

Regime where it wins: small, arithmetic-heavy DSLs where the entire program fits comfortably in one e-graph and control flow is minimal or absent (Herbie-scale expression rewriting). Real system: Herbie (uwplse/herbie), built entirely on egg with no separate pass pipeline. Why this blueprint rejected it: this project's surface language has let, if, match, loop, and effects — encoding purity/fuel/inlining heuristics purely as e-graph rewrites is markedly harder to review and fuel-bound than a named pass with an explicit guard (P10), and Click & Cooper 1995's own argument (§5) is for combining the two paradigms, not replacing one with the other (§20.1).

A2 — SSA-Based IR Optimizer Instead of an AST-Level One.

Show the original text diagram
Typed AST -> lower to SSA IR (phi nodes, basic blocks) -> classical dataflow passes -> lower to machine code

Regime where it wins: a language with rich control flow (loops with multiple exits, exceptions, goto) where phi-node-based dataflow analysis is dramatically simpler to express than tree-shaped propagation (Cytron et al. 1991). Real system: LLVM's opt pipeline, essentially every production optimizing compiler backend. Why this blueprint rejected it: this project deliberately stays pre-IR (ADR-15) to teach AST-level rewriting and equality saturation as a self-contained skill before the harder SSA-construction problem; a downstream, separately-owned IR optimizer is the correct home for SSA-class work, not a duplicated concern here.

A3 — Post-Lowering Bytecode/Stack-Machine Peephole Optimizer.

Show the original text diagram
Typed AST -> lower to bytecode -> peephole optimize the bytecode stream -> Verifier

Regime where it wins: a bytecode-interpreted language where the interpreter's dispatch overhead dominates and optimization opportunities are naturally expressed as local instruction-sequence rewrites (e.g. LOAD x; LOAD x → LOAD x; DUP). Real system: CPython's historical bytecode peephole optimizer (Python/peephole.c in pre-3.10 CPython). Why this blueprint rejected it: optimizing after lowering discards the high-level type and purity information this project's rewrites depend on (P2, P3) — folding, inlining, and partial evaluation are all markedly easier and more precise with Type/Purity still attached to the node, which a bytecode form has already erased.

A4 — Profile-Guided / JIT-Tiered Optimizer.

Show the original text diagram
Typed AST -> baseline interpreter (collect profile) -> hot-path detector -> tiered recompilation with profile-guided passes

Regime where it wins: a long-running process with stable hot loops where runtime profile data reliably predicts which function to inline and which branch to specialize (V8's TurboFan, HotSpot's C2). Real system: V8 (Ignition + TurboFan), HotSpot JVM. Why this blueprint rejected it: Phase-0 is an ahead-of-time batch tool with no runtime component and no profile source (P14, ADR-08 locks the inliner to static heuristics only); adopting profile-guidance here would break the reproducible-build guarantee (§29) this project treats as load-bearing.

38. Glossary

AnnotTables — the three NodeId-keyed side tables (purity, freshness, cost) holding every annotation the optimizer computes (§11, P5).

ADR (Architecture Decision Record) — a locked, numbered design decision with rejected alternatives and a regime where each alternative wins (§9).

Alpha-renaming — replacing bound variable names with fresh ones to avoid capture before a substitution (P12).

Arena allocation — allocating AST nodes contiguously in one backing store (id-arena) for cache locality (ADR-14).

Beta reduction — (fn x -> e) v → e[v/x], the core computational step of the lambda calculus (§18, Plotkin 1975).

Cost model — a swappable function from an Expr to a Cost { size, time, allocs }, driving inlining and extraction decisions (P6, ADR-07).

Common subexpression elimination (CSE) — sharing the result of two structurally-identical pure subexpressions via one lifted binding (§16).

Conformance bucket — a named group of fixtures whose aggregate outcome (Pass/Fail/Deferred) gates CI (§28).

Conformance fixture — a named .lock input plus its .expected.json, the unit of the conformance harness (§23.2).

Constant folding — rewriting a statically-known operation to its literal result, type-directed (§15, ADR-09).

Constant propagation — flowing a known-literal value from its binding to its uses via a monotone lattice fixpoint (§15, Wegman & Zadeck 1991).

Dead-code elimination (DCE) — deleting a purity-gated, provably-unused binding (§16).

Deferred Features Register — the table (§37) mapping every deferred feature to a resolving anchor, building phase, and un-defer trigger.

Differential testing — comparing an optimized program's behavior against an unoptimized reference interpreter on the same inputs (§22, P8).

Dominator — in a CFG, a node through which all paths to another node pass; approximated at the AST level by "the smallest enclosing binder" (§16.2).

E-class — an equivalence class of programs inside an e-graph, all considered equal by the rewrite rules applied so far (§20, MM1).

E-graph — a data structure representing a set of equivalent programs as a union-find over e-classes (Tate et al. 2009).

E-node — one representative term inside an e-class, referencing child e-classes rather than child terms directly (§20).

Eta reduction — (fn x -> f x) → f when x is not free in f, valid only when f is pure (§18).

Extraction — choosing one concrete program from a saturated e-graph according to a cost model (§20).

Fixpoint — the state at which a monotone iterative process stops changing; the manager's pass loop and the propagator's lattice both converge to one (I6, §8.3).

Freshness — the annotation distinguishing a newly-allocated (Fresh), memoized (Cached), or shared (Aliased) value (§11).

Fuel — an explicit, decrementing budget converting an otherwise-undecidable termination question into a decidable one (P4, MM4).

Hash-consing — canonicalizing structurally-equal terms to a shared representation, the mechanism behind CSE's duplicate detection (§16.2).

Inlining — replacing a call with the callee's body, substituted and alpha-renamed (§17, ADR-08).

Invariant — a property (I1…I14) that must hold at every point the system claims correctness (§7).

Lattice — a partially-ordered set with a join operation, the mathematical structure underlying Purity and constant propagation (§8.3, Nielson et al. 1999).

LICM (loop-invariant code motion) — hoisting a loop-invariant, purity-gated expression to a preheader outside the loop (§19, Knoop, Rüthing & Steffen 1992).

LowerToIR — the published, never-implemented-here trait contract handing an optimized Module to a downstream SSA/IR optimizer (§11, ADR-15).

Manager — the component scheduling passes and driving the fuel-bounded fixpoint loop (§21, ADR-03/04).

Monotonicity — the property that a lattice value only moves toward Top (or only toward Bottom), never oscillates, within one analysis pass (I3).

NodeId — the stable-within-a-module integer identity of an AST node, the key for every annotation side table (§11, P5, P11).

Partial evaluation (PE) — specializing a function against a subset of known-constant arguments, fuel-bounded (§18, ADR-10, Jones et al. 1993).

Peephole optimization — a small, locally-bounded, purity-gated structural rewrite rule (§17.5).

Purity — the 5-level lattice (Pure ⊑ Reads ⊑ Writes ⊑ Exception ⊑ Unknown) gating which subtrees may be duplicated, hoisted, or deleted (§8.3, ADR-21).

Reference interpreter — the tree-walk evaluator (opt-verify::interp) serving as the ground truth for I1 (§22, ADR-22).

Regression corpus — the permanently-retained set of minimized counter-examples from prior bugs, re-run on every CI cycle (§22.4).

Rewriter — the trait for a pass that consumes and returns a new Expr/Decl/Module (§11).

Saturation — running an e-graph's rewrite rules to a fixpoint or fuel exhaustion (§20, I7).

SCCP (sparse conditional constant propagation) — Wegman & Zadeck's algorithm unifying constant propagation with unreachable-code detection (§15.1).

Soundness (of a rewrite) — the property that applying the rewrite preserves interp's observable result (P1, I1).

SSA (static single assignment) — the IR form in which every variable is assigned exactly once, deliberately not built by this project (ADR-15, Cytron et al. 1991, §36/A2).

Symbol — an interned identifier (string_interner::DefaultSymbol) used for variable/field/type names (§11).

Tail position — the syntactic position whose evaluation is the final result of an enclosing function, annotated for the downstream IR-lowering boundary (§19, Steele 1978).

Type-directedness — the principle that arithmetic/comparison rewrites consult the node's Type before folding (P2, ADR-09).

Use-def graph — the graph connecting every variable use to its reaching definition(s), the basis for DCE and CSE (§16.2).

Worklist — a dedup'd FIFO queue of NodeIds driving a fact-propagation fixpoint (§14, §15).
