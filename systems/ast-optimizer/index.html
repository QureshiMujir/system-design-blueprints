In one paragraph

An AST optimizer takes a program that has already been parsed and type-checked, held as a tree, and rewrites it into a smaller, faster tree that behaves identically. This design is a Rust library plus one batch command-line tool, not a JIT, a runtime or a parser (§1). It combines a library of classical rewrite passes with a second technique, equality saturation, and it refuses to trust any rewrite until a reference interpreter agrees that the program's behavior did not change (§1, I1). Its one defining property is zero escaped semantics-preservation violations per release (§4). Compiler engineers building a language toolchain run it, and CI operators gate merges on it (§1).

The problem, concretely

Textbook optimizations are easy to state and easy to get subtly wrong. The blueprint's own examples show four ways a naive optimizer breaks a program. First, an identity that is true in algebra can be false in code: x + 0.0 is not x when x is -0.0, so a peephole rule copied from a textbook changes the answer (§17.6, MM5). Second, deleting "unused" code can delete a side effect: in the trace of §8.4, let _ = pure_call() in 6 must keep the call, because the optimizer cannot see the callee's body and so cannot prove it harmless (§8.4 steps 0 and 5, I3). Third, substituting an expression into another can capture a variable of the same name, which silently changes meaning (P12, §18.6). Fourth, passes that each make sense alone can undo each other: "fold makes a let, dce removes it, cse adds it back", forever (§21.6). Add a rewrite engine that can grow its working set without limit and a crafted input becomes a way to burn CPU and memory (P4, T1, T2). The blueprint's structure is the answer to those four pressures: guard every rewrite by purity and type (P2, P3), bound every loop with a budget (P4), and check every result against an interpreter (P8). Without this layer, the textbook rewrites either never run, or run redundantly inside the IR optimizer at a cost the AST could have paid down first (§2).

How it works, end to end

Follow one module through the boxes of §3's diagram (condensed here, coloured by role):

  1. Input. The typed AST is the one external, untrusted entry point. The resolver does not trust NodeId uniqueness or well-scopedness from upstream and re-checks both (§3, T1, I2). The AST and Type model live in opt-syntax, and the grammar is locked for Phase 0 (§1, §8.1).
  2. Resolver and annotator (opt-annot) renames bound variables to fresh names, builds a use-def graph and fills three side tables keyed by NodeId: Purity, Freshness and Cost (§3, P5). A variable with no reaching binder is rejected right after annotation, before any pass runs: the manager returns ManagerReport::RejectedInput rather than treating it as garbage (§8.5, I5).
  3. Pass manager (opt-manager) reads each pass's declared reads/writes/invalidates sets, orders the passes deterministically, and runs them in a loop until the module stops changing or an iteration cap is hit (§3, §21.2, ADR-03, ADR-04, P13). It writes a before/after dump per pass under target/opt-dumps/ (§21.2, ADR-17). opt-visitor supplies the Visitor and Rewriter traits and a worklist helper the passes build on (§1).
  4. Classical passes (opt-passes) are the eleven named in §1: constant folding, constant propagation, dead-code elimination, common-subexpression elimination, inlining, peephole, partial evaluation, beta reduction, eta reduction, loop-invariant code motion and tail-call detection. Each is a pure Rewriter/Visitor that declares its reads/writes/invalidates set (§3, I11), and every DCE, CSE, LICM and inline decision reads the purity table first (P3). §3's prose says "ten classical passes" while its diagram, §1 and §21.3 name eleven.
  5. Equality saturation (opt-saturate) turns the module into an e-graph, applies a curated set of rules until a fuel limit or a fixpoint, then extracts the cheapest equivalent program (§3, §20.2). The blueprint orders it after the classical pipeline (§8.2, §35 question 4).
  6. Verifier (opt-verify) runs the program before and after on generated inputs through a reference interpreter. No output reaches the CLI or the report until they agree (§3, I1).
  7. Output is the optimized AST, a per-pass diff report and a JSON conformance report that CI consumes (§3). The CLI (opt-driver) has four commands: optimize, dump-passes, bench and saturate, and opt-conformance runs the fixtures that produce the report (§1).
  8. Concurrency. The driver runs one manager per module on its own worker thread, up to 64 per batch. Mutable e-graph and annotation state is never shared between threads (§3, §4, T11).

The core ideas

Purity is a ladder, not a yes/no flag (§8.3, I3, ADR-21, MM3)

Before any pass may delete, duplicate or hoist a piece of code, it needs to know what the code can do. The blueprint scores every subtree on a five-step ladder (a lattice): Pure, then Reads, then Writes, then Exception, then Unknown at the top, which means "assume the worst" and blocks every rewrite guard (§8.3). Only Pure and Reads subtrees may be duplicated, hoisted or deleted (P3). A call's purity is the join (the higher of the two) of the function's and the argument's purity, and a call to a function with no visible body starts at Unknown (§13.2, §13.5, §8.4 step 0). Purity can only move up the ladder within one fixpoint iteration (I3), and the blueprint gives that monotonicity as what the fixpoint argument needs.

Dead-code elimination uses it with two further checks. A let binding is dead only if (1) it is Pure, (2) it is unused in the use-def graph, and (3) removing it does not change any sibling's evaluation order (§16.2). A tiny pair of cases from the Phase 4 acceptance criteria (§16.4):

Input Result in §16.4
let _ = pure_call() in 1 rewrites to 1
let _ = side_effect() in 1 preserved unchanged (I3 guard)

The blueprint is inconsistent about the first case: §16.4 deletes let _ = pure_call(), but §8.4 marks pure_call as Purity::Unknown and keeps the same binding (§8.4 steps 0 and 5). The stated reason for five levels rather than two is precision: a boolean cannot say "reads but never writes" (ADR-21, MM3).

Constant propagation: a value that is either known, unknown, or not yet seen (§8.3, §15)

Constant folding replaces an operation on literals with its result, using the node's Type (integer arithmetic wraps as the type says, floats follow IEEE-754) so it cannot silently get overflow wrong (§15.2, ADR-09, P2). Constant propagation pushes a known value from its binding to every use. It tracks each variable on a three-part lattice: Bottom (not yet computed), a Const(v) per distinct literal, and Top (could be anything) (§8.3). The join rules are:

Join Result
Bottom ⊔ x x
Const(v) ⊔ Const(v) Const(v)
Const(v1) ⊔ Const(v2), v1 ≠ v2 Top
Top ⊔ x Top

Because values only climb, the propagator reaches a fixpoint in at most |nodes| steps (§8.3). A loop variable that is constant on entry but changed in the body ends at Top (§15.4). The two passes feed each other, which is why they ship together (§15.1). The blueprint's worked trace (§8.4), with source let x = 1 in let y = x + 2 in let _ = pure_call() in y + y:

Step Fact / rewrite applied Resulting fragment
0 (Annotated) pure_call marked Purity::Unknown (no callee body visible) unchanged
1 (Propagate) x ↦ Const(1) reaches its one use let y = 1 + 2 in let _ = pure_call() in y + y
2 (Fold) 1 + 2 → 3 (type-directed, P2) let y = 3 in let _ = pure_call() in y + y
3 (Propagate) y ↦ Const(3) reaches both uses let _ = pure_call() in 3 + 3
4 (Fold) 3 + 3 → 6 let _ = pure_call() in 6
5 (DCE) binding for _ is kept: purity is Unknown, I3 forbids deletion unchanged (I3 guard fires)
6 (CSE) no duplicate pure subterms remain unchanged; "fixpoint reached in 4 manager iterations"

§8.4 says the final output agrees with the original under the interpreter (I1). The trace has gaps the blueprint does not explain: it lists six steps but says 4 manager iterations, and each iteration runs the whole pass list (§21.2); the let x and let y bindings vanish in the propagate steps 1 and 3, though no step removes them and the only DCE step comes later; and a callee named pure_call is marked Unknown.

The manager: run to a fixpoint, with a hard cap (§21.2, ADR-03, ADR-04, I6, MM2)

A pass is one step toward a stable program, not a one-shot transform, which is why rerunning it is meaningful (MM2). run_to_fixpoint runs the ordered pass list once per iteration, compares the new module with the previous one by structural equality, and stops when nothing changed or when the iteration count passes max_iter = 32 (§21.2, I6). If it hits the cap it emits ManagerReport::Unstable and keeps the last iteration's output, which is still sound (I6, FM-2). The order comes from a topological sort over what each pass declares it reads, writes and invalidates, so the same registry and module always give the same schedule (§21.2, P13, P9). A pass that both reads and writes one annotation creates a cycle in that graph, and the design resolves it with the fixpoint loop, not with ordering tricks (§21.2).

Two budgets do different jobs. A per-pass Fuel counter (inliner, partial evaluator) is checked with tick() before mutating, and exhaustion is a reported PassReport::FuelExhausted, not a crash (I4, P4, MM4). The manager's max_iter bounds the whole loop across passes (I6). Worked bound from §34 item 4: 32 iterations × 5 passes × (80,000 nodes ÷ 4,000,000 nodes/s = 0.02 s) = 3.2 s worst case, against an O2 target of at most 400 ms (M2). §21.4 requires a four-pass run to finish in fewer than 8 iterations, while §4 calls typical convergence "≤ 8".

Equality saturation: keep every equivalent form, choose at the end (§20.2, MM1, I7, ADR-20)

A classical pass commits to one rewrite direction. Equality saturation instead stores a whole set of equivalent programs in one structure, an e-graph: a group of programs all considered equal is an e-class, and each member is an e-node that points at child e-classes (§20.2, MM1). A rewrite LHS ⟺ RHS adds RHS to LHS's e-class without removing LHS (§20.2). Because it never commits to one rewrite direction, the blueprint says it subsumes phase-ordering problems (MM1, §2).

Tiny example from §20.3: under add-assoc, (a + b) + c saturates and extracts a cost-equivalent form; both associations tie on size cost, which exercises the extractor's deterministic tie-break (§20.8, P13). The extractor picks the cheapest program by a cost model (the default is node count plus a memoization penalty, ADR-07), and it is trusted to pick the argmin of whatever cost function it is given (§20.6). Greedy extraction is the default, and an exact LP-based extractor runs under --exact-cost (§20.2, ADR-20). A different cost model gives a different extraction from the same rules, so a bad extraction is usually a cost-model bug, not an extractor bug (MM6, §20.6).

Saturation can explode, so it is bounded: at most 1,024 iterations or 50,000 e-nodes (I7, §4). In §8.6's failure path, a fixture with 40 nested add-comm/add-assoc applications hits the 50,000-node limit first; Runner::stop_reason reports NodeLimit, the engine extracts from the graph as it stands (still sound), and the case is marked Pass (partial-saturation), not Fail (§8.6).

Differential verification: the interpreter is the specification (§22, I1, ADR-11, MM7, P8)

The correctness contract is interp(before) == interp(after) for every pass and the saturator (I1, P1). opt-verify implements a tree-walk reference interpreter and a proptest generator, arb_expr(depth), calibrated so 80% of generated expressions finish within 1 ms and the rest hit an explicit step ceiling instead of looping (§22.2). The comparison runs the before and after modules on shared inputs and returns a DiffReport with mismatch details, not just pass or fail (§22.2). Floats are compared by bit pattern with f64::to_bits, never ==, so NaN cannot hide a mismatch (§22.4). Every minimized counter-example found during development goes into a regression corpus that must hold at least 50 cases (§22.2, §22.4).

The blueprint's stance is that this harness is the specification itself: a rewrite without a passing differential fixture is not "probably fine", it is unspecified (MM7), and a pass cannot merge without its fixtures (P8). On a mismatch the pass's output is reverted and a regression fixture is filed (I1).

The trade-offs — where engineers disagree

Optimizer style: passes plus a saturator (ADR-02)

Chosen: visitor passes plus an e-graph saturator, to combine readable per-pass rewrites with the global view of saturation (§9). Rejected: a pure pass pipeline, or pure saturation. When the rejected choice is right: pure saturation, for a small arithmetic-only DSL where the whole program fits one e-graph cheaply, for example Herbie-scale expressions (§9, §36/A1).

Pass execution: a fuel-bounded fixpoint (ADR-03)

Chosen: loop the passes to a fixpoint with max_iter = 32, so termination holds even when passes interact (§9, I6). Rejected: a single pass with no fixpoint, or an unbounded fixpoint. When the rejected choice is right: a single pass, in a latency-critical JIT baseline tier where one linear pass must finish in microseconds (§9).

Pass ordering: declared dependencies (ADR-04)

Chosen: a static graph built from each pass's declared reads/writes/invalidates, so the manager picks a safe order itself (§9, P9, I11). Rejected: a hand-tuned fixed order. When the rejected choice is right: a three-pass teaching compiler small enough for a human to check by eye (§9).

Annotation storage: side tables (ADR-05)

Chosen: annotations in NodeId-keyed tables, so adding a new kind of annotation does not change the AST shape (§9, P5). Rejected: inline fields on each node. When the rejected choice is right: when annotations are few, permanent and read by every node, such as an always-present source span (§9). The cost accepted is a hash lookup per read (P5).

Verification: differential testing (ADR-11)

Chosen: differential tests against a tree-walk interpreter, because they are cheap to run and sound by construction (§9, P8). Rejected: mechanized proof-carrying rewrites. When the rejected choice is right: a safety-critical compiler where one miscompile is unacceptable, the CompCert class (§9). The proof route stays deferred for a future fork (§9, §37).

The oracle: a from-scratch interpreter (ADR-22)

Chosen: write the reference interpreter (opt-verify::interp), because no mature reference VM exists for this project's language (§9). Rejected: reuse an existing production VM as the oracle. When the rejected choice is right: when such a VM already exists and is more trusted than a new interpreter, for example checking a new JavaScript optimizer against V8 (§9).

The IR boundary: stop at the AST (ADR-15)

Chosen: no SSA lowering here, only a published LowerToIR contract, which keeps scope to the AST (§9, §11). Rejected: owning SSA lowering inside this project. When the rejected choice is right: a single-project pipeline with no separate downstream IR consumer (§9).

Roads not taken (§36, §37)

A pure equality-saturation optimizer (§36/A1) puts the whole module in one e-graph with no pass pipeline. It wins for small, arithmetic-heavy DSLs with little control flow, as in Herbie. It was rejected because this language has let, if, match, loop and effects, and encoding purity, fuel and inlining heuristics as e-graph rewrites is harder to review than a named pass with a guard (§36/A1, P10).

An SSA-based IR optimizer (§36/A2) lowers to SSA with phi nodes and basic blocks, then runs dataflow passes. It wins for languages with rich control flow such as multi-exit loops, exceptions or goto, where phi-based analysis is simpler than tree-shaped propagation (§36/A2). It was rejected to keep this project a self-contained AST-level lesson, leaving SSA-class work to a downstream owner (§36/A2, ADR-15).

A post-lowering bytecode peephole optimizer (§36/A3) rewrites a bytecode stream. It wins for a bytecode-interpreted language where dispatch overhead dominates and the wins are local instruction sequences, as in CPython's historical peephole pass (§36/A3). It was rejected because lowering erases the type and purity information that folding, inlining and partial evaluation rely on (§36/A3, P2, P3).

A profile-guided, JIT-tiered optimizer (§36/A4) recompiles hot code using runtime profiles. It wins for a long-running process with stable hot loops, as in V8 or HotSpot (§36/A4). It was rejected because this tool is an ahead-of-time batch tool with no profile source, and profile input would break the reproducible-build guarantee (§36/A4, P14, §29); §37 defers it until an ADR admits it.

What must never be false

  • I1: before and after a pass or saturation, the reference interpreter gives the same result. Noticed by the differential harness (§22); counter verify.mismatch; recovery reverts the pass output (§7).
  • I2: every NodeId is unique within a Module. Checked by Module::validate and a debug_assert!; no telemetry; a violating module is rejected (§7).
  • I3: purity only moves up the ladder within one fixpoint iteration. A unit test on AnnotTables::merge; counter annot.purity_downgrade_illegal, target 0 (§7).
  • I4: every fuel-bounded pass checks Fuel::tick() before mutating. Caught by the fuzz_passes fuzz target; counter fuel.exhausted (§7).
  • I5: no pass output has a dangling variable. Post-pass check WellFormedCheck in debug builds; counter verify.dangling_var; the pass is rolled back (§7).
  • I6: the manager's fixpoint loop always halts within 32 iterations. Seen when iter reaches the cap; counter manager.max_iter_hit (§7).
  • I7: the e-graph stays within 1,024 iterations or 50,000 e-nodes. Read from Runner::stop_reason; counter saturate.stopped_reason (§7).
  • I8: every peephole and saturator rule carries a soundness comment. A CI lint, xtask rule-docs-check; no runtime telemetry (§7).
  • I9: every expression's type stays consistent after a pass. A differential-harness step; counter verify.type_mismatch (§7).
  • I10: alpha-renaming precedes every substitution that could capture a variable. Shadowing-heavy property tests; counter rename.capture_detected, target 0 (§7).
  • I11: each pass's declared reads/writes/invalidates matches its body. A CI static check that greps the pass body against its declaration; no telemetry (§7).
  • I12: conformance outcomes are identical across two consecutive CI runs of the same commit. A double-run report diff; counter conformance.flaky_case (§7).
  • I13: Cost.size saturates at 2³¹ instead of overflowing. A property test on adversarially large trees; counter cost.saturated (§7).
  • I14: extraction returns only programs the e-graph actually contains. A debug_assert! plus a differential test right after saturation; counter extract.invalid_id, target 0; falls back to the pre-saturation module (§7).

What breaks in production

  • FM-1: miscompilation. Symptom: a differential mismatch or a downstream bug report. Cause: a rewrite missing its purity or type guard. Detected by verify.mismatch and a red CI. There is no automatic recovery, and CI blocks the merge. An operator bisects with scripts/bisect-miscompile.sh and reverts the commit; DiffReport keeps the input, before and after (§25, P1).
  • FM-2: fixpoint oscillation. Symptom: manager.max_iter_hit keeps recurring. Cause: two passes disagree on a canonical form. Detected as ManagerReport::Unstable. The last iteration's output is returned, which is still sound under I1. An operator adds a tie-break rule or opens an ADR, using the per-iteration dumps to see the cycle (§25, §21.6).
  • FM-3: saturator blowup. Symptom: saturate.stopped_reason=node_limit spikes. Cause: a new rule pair grows the e-graph quadratically. Detected from a telemetry trend. The engine extracts a sound partial result (I7); an operator curates or removes the rule pair, using the egraph_size series per commit (§25, §20.6).
  • FM-4: inliner size blowup. Symptom: code growth past the 38% ceiling. Cause: a Cost.size threshold set too generously. Detected by the performance-regression gate. There is no automatic recovery; an operator tightens the thresholds of ADR-08 (§25, §34 item 5).
  • FM-5: variable capture. Symptom: a mismatch on shadowing-heavy fixtures. Cause: a missing alpha-rename (a P12 violation). Detected by I10's shadowing property test. An operator patches the pass's rename call, adds a regression fixture and works from the minimized shrink output (§25).
  • FM-6: stale annotation read. Symptom: a pass decision that disagrees with the module's real state. Cause: a missing entry in invalidates. I11's static check should catch it, so a miss points at a tooling gap. An operator corrects the descriptor and re-runs the manager (§25, P9).
  • FM-7: flaky conformance. Symptom: a bucket flips between pass and fail on identical reruns. Cause: nondeterministic iteration order, usually an unsorted HashMap. Detected by I12's double-run diff. An operator quarantines the fixture and fixes the nondeterminism (§25).

Threats a reader should know (§24): T1 an adversarially deep or wide AST, or one that blows up the e-graph, answered by fuel bounds and the node ceiling (I4, I7, §4). T2 a crafted input that makes the fixpoint oscillate, answered by the max_iter cap (I6, ADR-03). T3 an unsound rewrite rule contributed by a person (the blueprint's example is x/x→1), answered by the soundness-comment lint and a mandatory per-rule differential fixture (I8). T7 a PR that loosens an expected.json to hide a regression, answered by a second-reviewer rule on those diffs. T9 an invalid extraction from a stale e-class, answered by I14's membership assert and a fallback (§8.6).

How it compares

  • LLVM opt chose a linear SSA IR and a declarative new Pass Manager, working after the source is lowered. That fits workloads dominated by cross-procedure inlining and interprocedural analysis, while this design stays pre-IR and never needs phi nodes (§33, ADR-15).
  • GCC (GIMPLE) chose a three-address IR with heavily hand-tuned pass ordering. That is fine in a decades-old, very wide codebase where every ordering quirk is load-bearing knowledge, whereas this design rejects it to stay onboardable (§33, ADR-04).
  • SWC chose single-traversal AST transforms with no fixpoint and snapshot-test verification. That fits source-to-source work such as TypeScript to JavaScript, where transforms are nearly independent and speed matters most. This design needs the fixpoint because fold, propagate and dce genuinely interact (§33).
  • Closure Compiler chose whole-program analysis over a typeless AST with hand-tuned pass order. That wins when the whole program is available and cross-file dead-code elimination is the main gain, a scope this design defers (§33, §1 non-goals).

Questions to test yourself

  1. Why does constant propagation need a lattice with both Top and Bottom, and what would break if the propagator only had Bottom and Const(v)? — Hint: compare the join rules in §8.3 with the loop-variable case in §15.4.
  2. Why is Purity a 5-level lattice instead of a boolean, and which pass would first misbehave if it were collapsed to a boolean? — Hint: ADR-21, MM3, and the DCE conditions in §16.2.
  3. Derive, from §4's constraints alone, the worst-case wall-clock time for a full manager fixpoint, and explain why the empirical acceptance criterion in §21.4 is far below that worst case. — Hint: §34 item 4 shows the pattern, and §21.4 gives the empirical bound.
  4. Compare the failure mode of a fixpoint that oscillates (FM-2) against one that hits the node-limit (FM-3): which one is a correctness risk and which is purely a quality-of-optimization risk, and why? — Hint: read the recovery columns of FM-2 and FM-3 in §25 beside I6 and I7.
  5. Why is the differential harness described as "the specification" rather than "a test suite," and what governance consequence follows from that framing for a new contributor's PR? — Hint: MM7 in §32, P8 in §6, and T3 in §24.

If you only remember three things

A rewrite is only as sound as its purity and type guard, not as sound as its algebra, so every rewrite is gated on annotations before it fires (MM5, P2, P3). Every loop in the system carries an explicit budget, and running out is a normal reported outcome that still returns a sound program (MM4, P4, I6, I7). The reference interpreter is the specification: nothing is trusted until the differential harness agrees (MM7, I1).

Words used here

  • AST: abstract syntax tree, the program held as a tree of typed nodes.
  • Fixpoint: the point where another round of passes no longer changes the program (I6).
  • Fuel: a decrementing budget that turns "might never stop" into "stops by a known bound" (MM4).
  • Lattice: a partial ordering of values with a join operation, used for purity and constants (§8.3).
  • Purity: how much a subtree can affect the world, from Pure up to Unknown (ADR-21).
  • NodeId: a node's identity within one module; it is not stable across separate parses (P11).
  • Alpha-renaming: giving bound variables fresh names so a substitution cannot capture one (P12).
  • E-graph / e-class: a structure holding many equivalent programs; an e-class is one group (MM1).
  • Extraction: choosing one concrete program from the e-graph by a cost model (ADR-20).
  • Reference interpreter: the slow, simple evaluator that defines correct behavior (ADR-22).
