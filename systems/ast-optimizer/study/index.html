Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does constant propagation need a lattice with both Top and Bottom, and what would break if the propagator only had Bottom and Const(v)? (§8.3, §15.4)
  2. Why is Purity a 5-level lattice instead of a boolean, and which pass would first misbehave if it were collapsed to a boolean? (ADR-21, §13.6, I3)
  3. Why does the manager run passes to a fuel-bounded fixpoint instead of a fixed pipeline order, and what specific two-pass interaction in this project would break under a fixed order? (§21.2, §16.6)
  4. Why is equality saturation run after the classical pass pipeline rather than instead of it, and what does §33's LLVM/SWC comparison say about that choice's cost? (§20.1, §33)
  5. What is the concrete difference between a Fuel-bounded pass and a max_iter-bounded manager, and why does this system need both? (P4, I4, I6)
  6. Why must alpha-renaming precede substitution in three different passes (beta, inline, CSE-lift) rather than being centralized in one shared preprocessing step? (P12, §16.2, §17.2, §18.2)
  7. Derive, from §4's constraints alone, the worst-case wall-clock time for a full manager fixpoint, and explain why the empirical acceptance criterion in §21.4 is far below that worst case. (§34/#4, §21.4)
  8. Why does the cost model live behind a trait (CostModel) instead of being a fixed function, and what two consumers in this blueprint depend on that indirection? (P6, ADR-07, §20.2)
  9. Why is NodeId uniqueness required only within a module and not across parses, and what invariant would break if a later pass assumed cross-parse stability? (P11, I2, §13.9)
  10. What is the actual difference between the saturator's e-graph and the manager's dependency graph, and why can't the manager's scheduling problem be solved by putting every pass into one e-graph instead? (§20.1, §21.2, §36/A1)
  11. Why does DCE require both purity and a use-def check, and give a concrete fixture where purity alone would be unsound to delete on. (§16.2, §16.4)
  12. Trace how a single let _ = pure_call() in 1 decision changes across §8.4's worked example if pure_call's purity were Pure instead of Unknown — which invariant governs the difference? (§8.4, I3)
  13. Why does this blueprint reject building its own SSA form, and under what regime (named in §36) would that rejection be wrong? (ADR-15, §36/A2)
  14. What two telemetry counters would first indicate a saturator rule was added without adequate curation, and what is the operator's remediation path? (§20.10, FM-3)
  15. Why is the differential harness described as "the specification" rather than "a test suite," and what governance consequence follows from that framing for a new contributor's PR? (MM7, P8, T3)
  16. Derive the FD budget for a 64-worker batch run from first principles, and explain why doubling the worker cap does not simply double memory pressure in the same way. (§34/#7, §31)
  17. Why does the inliner's fuel bound (1,024/run) interact with the cost-growth ceiling (M12) multiplicatively rather than additively, and what would change if Cost.size were unbounded? (§34/#5, ADR-08)
  18. Compare the failure mode of a fixpoint that oscillates (FM-2) against one that hits the node-limit (FM-3): which one is a correctness risk and which is purely a quality-of-optimization risk, and why? (§25, I6, I7)
  19. Why does the peephole library (§17.5) require every rule to also exist as a saturator rule (§20.2), and what would go wrong if the two rule sets were allowed to drift apart? (§17.5, §20.2, I8)
  20. Derive why the manager's max_iter=32 cap and the saturator's 50,000-e-node cap are set independently rather than sharing one global fuel budget, and what coupling them would break. (§4, I6, I7, §34/#4)

32. Mental Models & First Principles

MM1 — An e-class is a set of equivalent programs, not a program. Predicts: saturation subsumes phase-ordering because it never commits to one rewrite direction. Bug class without it: assuming the e-graph has "the current program" and trying to read one out mid-saturation. Applies in §20.

MM2 — A pass is a monotone step toward a fixpoint, not a one-shot transform. Predicts termination behavior and why re-running a pass twice is meaningful (P7). Bug class without it: writing a pass that "does its one job" and being surprised the manager reruns it (§21). Applies in §21, I6.

MM3 — Purity is a lattice, not a boolean. Predicts float-NaN and partial-purity edge cases (an op that reads but never writes). Bug class without it: treating any "probably safe" op as reorderable. Applies in §13, §8.3.

MM4 — Fuel converts undecidable termination into decidable termination. Predicts fuel-exhaustion diagnostics are a normal, expected outcome, not a bug. Bug class without it: assuming the optimizer "always finishes" and treating FuelExhausted as an error to suppress rather than report. Applies in §17, §18, §20, P4.

MM5 — A rewrite is only as sound as its purity/type guard, never as sound as its algebra. Predicts why some algebraically-true identities (x + 0 = x) are unsound in code (signed zero, NaN). Bug class without it: porting a textbook identity verbatim into a peephole rule. Applies in §15, §17.

MM6 — Cost models are policy, not law. Predicts why the extractor's output changes when only the cost model changes, with the same rule set (P6). Bug class without it: blaming the extractor for a bad extraction that is actually a cost-model bug. Applies in §20, ADR-07.

MM7 — The differential harness is the specification, not a test suite bolted onto one. Predicts why a rewrite without a passing differential fixture is not "probably fine" — it is simply unspecified (P8). Bug class without it: merging a rewrite on code-review confidence alone. Applies in §22.

MM8 — NodeId is identity; structural equality is not. Predicts subtle bugs in hash-consing/CSE where two structurally-identical-but-differently-NodeId'd subtrees must still be treated as distinct annotation-table keys until explicitly unified. Bug class without it: an annotation lookup silently keyed on the wrong node after a clone. Applies in §11, §16.

Required reading (§5)

Books

  • Cooper, K. D., Torczon, L. (2011). Engineering a Compiler, 2nd ed. Morgan Kaufmann. Chapters 8–10 (value numbering, redundancy elimination, code motion). Extract: local/global value numbering as CSE's theoretical basis; lazy code motion for LICM. Applied in §16 (CSE), §19 (LICM).
  • Appel, A. W. (1998). Modern Compiler Implementation in ML. Cambridge University Press. Chapters 17–18 (optimization). Extract: tree-shaped IR optimization patterns close to this project's AST-level approach. Applied in §15 (fold/propagate), §8 (domain model).
  • Muchnick, S. S. (1997). Advanced Compiler Design and Implementation. Morgan Kaufmann. Chapters 12–13 (global dataflow analysis), 18–19 (procedure optimization). Extract: the general dataflow-framework formalism (lattice, transfer function, meet) this project's constant-propagation lattice specializes. Applied in §8, §15.
  • Aho, A. V., Lam, M. S., Sethi, R., Ullman, J. D. (2006). Compilers: Principles, Techniques, and Tools, 2nd ed. Addison-Wesley. Chapters 8 (code-generation intro), 9 (machine-independent optimizations). Extract: the canonical presentation of constant folding, DCE, CSE. Applied in §15, §16.
  • Nielson, F., Nielson, H. R., Hankin, C. (1999). Principles of Program Analysis. Springer. Chapters 2 (dataflow analysis), 4 (abstract interpretation). Extract: the formal monotone-framework treatment underlying the purity lattice (§8) and the fixpoint-existence argument behind I6. Applied in §7 (I3, I6), §15.
  • Jones, N. D., Gomard, C. K., Sestoft, P. (1993). Partial Evaluation and Automatic Program Generation. Prentice Hall. Chapters 4–5 (online vs. offline PE). Extract: the online/offline tradeoff this project locks to online (ADR-10); binding-time analysis as the road not taken. Applied in §18 (PE), §9 (ADR-10).

Papers

  • Kildall, G. (1973). A Unified Approach to Global Program Optimization. POPL. Contribution: the general dataflow-lattice/fixpoint algorithm. Applied in §8, §15.
  • Wegman, M. N., Zadeck, F. K. (1991). Constant Propagation with Conditional Branches. ACM TOPLAS. Contribution: sparse conditional constant propagation (SCCP). Applied in §15.
  • Cytron, R., Ferrante, J., Rosen, B. K., Wegman, M. N., Zadeck, F. K. (1991). Efficiently Computing Static Single Assignment Form and the Control Dependence Graph. ACM TOPLAS. Contribution: SSA construction — the system this project deliberately does not build. Applied in §36.
  • Tate, R., Stepp, M., Tatlock, Z., Lerner, S. (2009). Equality Saturation: A New Approach to Optimization. POPL. Contribution: e-graph-based optimization representing all equivalent programs simultaneously. Applied in §20.
  • Willsey, M., Nandi, C., Wang, Y. R., Flatt, O., Tatlock, Z., Panchekha, P. (2021). egg: Fast and Extensible Equality Saturation. POPL. Contribution: the extensible e-graph engine this project locks to (ADR-06). Applied in §20.
  • Click, C., Cooper, K. (1995). Combining Analyses, Combining Optimizations. ACM TOPLAS. Contribution: argues analyses/optimizations should be combined rather than sequenced, foreshadowing equality saturation. Applied in §20, §36.
  • Knoop, J., Rüthing, O., Steffen, B. (1992). Lazy Code Motion. PLDI. Contribution: optimal code placement balancing redundancy elimination against register pressure. Applied in §19.
  • Lattner, C., Adve, V. (2004). LLVM: A Compilation Framework for Lifelong Program Analysis & Transformation. CGO. Contribution: a pass-manager architecture with declared analysis dependencies and invalidation. Applied in §14, §21.
  • Stepp, M., Tate, R., Lerner, S. (2011). Equality-Based Translation Validator for LLVM. CAV. Contribution: uses equality saturation to validate optimizer output against its input. Applied in §22.
  • Steele, G. L. (1978). Rabbit: A Compiler for Scheme. MIT AI-TR-474. Contribution: rigorous early treatment of tail-call detection. Applied in §19.

Reference Implementations

  • LLVM — llvm/lib/Transforms/InstCombine/, llvm/lib/Passes/PassBuilder.cpp. Lesson: declarative pass-manager scheduling with explicit analysis invalidation (mirrors ADR-04/§21). Pitfall not to copy: the legacy Pass Manager's implicit global ordering rules; this project's manager stays declarative-only.
  • GCC — gcc/tree-ssa-ccp.cc, gcc/tree-ssa-dce.cc. Lesson: production SCCP and DCE over GIMPLE, useful for cross-checking lattice edge cases (§8.3). Pitfall not to copy: pass ordering is largely hand-tuned global state; this project keeps ordering declarative and testable (I11).
  • SWC (Rust) — crates/swc_ecma_transforms_optimization/src/. Lesson: idiomatic Rust visitor/fold-trait design directly informing §11's Visitor/Rewriter traits. Pitfall not to copy: several SWC passes assume one traversal suffices; this project runs every pass to an explicit fixpoint (ADR-03/I6).
  • Closure Compiler (Google, Java) — src/com/google/javascript/jscomp/{InlineFunctions,RemoveUnusedCode}.java. Lesson: production inliner/DCE cost heuristics and their interaction (§17). Pitfall not to copy: relies on whole-program closure-world assumptions this project's module-local Phase-0 scope does not have (§1 non-goals).
  • egg (egraphs-good/egg) + Herbie (uwplse/herbie) — egg's tests/, Herbie's src/core/egraph. Lesson: rewrite-rule curation with a per-rule soundness argument, and cost-function design for extraction (§20). Pitfall not to copy: Herbie's cost model targets floating-point error, not code size; this project's default CostModel (ADR-07) targets node count — adapt the pattern, not the numbers.

Glossary (§38) · 47 terms · site-wide glossary

AnnotTables
the three NodeId-keyed side tables (purity, freshness, cost) holding every annotation the optimizer computes (§11, P5).
ADR (Architecture Decision Record)
a locked, numbered design decision with rejected alternatives and a regime where each alternative wins (§9).
Alpha-renaming
replacing bound variable names with fresh ones to avoid capture before a substitution (P12).
Arena allocation
allocating AST nodes contiguously in one backing store (id-arena) for cache locality (ADR-14).
Beta reduction
(fn x -> e) v → e[v/x], the core computational step of the lambda calculus (§18, Plotkin 1975).
Cost model
a swappable function from an Expr to a Cost { size, time, allocs }, driving inlining and extraction decisions (P6, ADR-07).
Common subexpression elimination (CSE)
sharing the result of two structurally-identical pure subexpressions via one lifted binding (§16).
Conformance bucket
a named group of fixtures whose aggregate outcome (Pass/Fail/Deferred) gates CI (§28).
Conformance fixture
a named .lock input plus its .expected.json, the unit of the conformance harness (§23.2).
Constant folding
rewriting a statically-known operation to its literal result, type-directed (§15, ADR-09).
Constant propagation
flowing a known-literal value from its binding to its uses via a monotone lattice fixpoint (§15, Wegman & Zadeck 1991).
Dead-code elimination (DCE)
deleting a purity-gated, provably-unused binding (§16).
Deferred Features Register
the table (§37) mapping every deferred feature to a resolving anchor, building phase, and un-defer trigger.
Differential testing
comparing an optimized program's behavior against an unoptimized reference interpreter on the same inputs (§22, P8).
Dominator
in a CFG, a node through which all paths to another node pass; approximated at the AST level by "the smallest enclosing binder" (§16.2).
E-class
an equivalence class of programs inside an e-graph, all considered equal by the rewrite rules applied so far (§20, MM1).
E-graph
a data structure representing a set of equivalent programs as a union-find over e-classes (Tate et al. 2009).
E-node
one representative term inside an e-class, referencing child e-classes rather than child terms directly (§20).
Eta reduction
(fn x -> f x) → f when x is not free in f, valid only when f is pure (§18).
Extraction
choosing one concrete program from a saturated e-graph according to a cost model (§20).
Fixpoint
the state at which a monotone iterative process stops changing; the manager's pass loop and the propagator's lattice both converge to one (I6, §8.3).
Freshness
the annotation distinguishing a newly-allocated (Fresh), memoized (Cached), or shared (Aliased) value (§11).
Fuel
an explicit, decrementing budget converting an otherwise-undecidable termination question into a decidable one (P4, MM4).
Hash-consing
canonicalizing structurally-equal terms to a shared representation, the mechanism behind CSE's duplicate detection (§16.2).
Inlining
replacing a call with the callee's body, substituted and alpha-renamed (§17, ADR-08).
Invariant
a property (I1…I14) that must hold at every point the system claims correctness (§7).
Lattice
a partially-ordered set with a join operation, the mathematical structure underlying Purity and constant propagation (§8.3, Nielson et al. 1999).
LICM (loop-invariant code motion)
hoisting a loop-invariant, purity-gated expression to a preheader outside the loop (§19, Knoop, Rüthing & Steffen 1992).
LowerToIR
the published, never-implemented-here trait contract handing an optimized Module to a downstream SSA/IR optimizer (§11, ADR-15).
Manager
the component scheduling passes and driving the fuel-bounded fixpoint loop (§21, ADR-03/04).
Monotonicity
the property that a lattice value only moves toward Top (or only toward Bottom), never oscillates, within one analysis pass (I3).
NodeId
the stable-within-a-module integer identity of an AST node, the key for every annotation side table (§11, P5, P11).
Partial evaluation (PE)
specializing a function against a subset of known-constant arguments, fuel-bounded (§18, ADR-10, Jones et al. 1993).
Peephole optimization
a small, locally-bounded, purity-gated structural rewrite rule (§17.5).
Purity
the 5-level lattice (Pure ⊑ Reads ⊑ Writes ⊑ Exception ⊑ Unknown) gating which subtrees may be duplicated, hoisted, or deleted (§8.3, ADR-21).
Reference interpreter
the tree-walk evaluator (opt-verify::interp) serving as the ground truth for I1 (§22, ADR-22).
Regression corpus
the permanently-retained set of minimized counter-examples from prior bugs, re-run on every CI cycle (§22.4).
Rewriter
the trait for a pass that consumes and returns a new Expr/Decl/Module (§11).
Saturation
running an e-graph's rewrite rules to a fixpoint or fuel exhaustion (§20, I7).
SCCP (sparse conditional constant propagation)
Wegman & Zadeck's algorithm unifying constant propagation with unreachable-code detection (§15.1).
Soundness (of a rewrite)
the property that applying the rewrite preserves interp's observable result (P1, I1).
SSA (static single assignment)
the IR form in which every variable is assigned exactly once, deliberately not built by this project (ADR-15, Cytron et al. 1991, §36/A2).
Symbol
an interned identifier (string_interner::DefaultSymbol) used for variable/field/type names (§11).
Tail position
the syntactic position whose evaluation is the final result of an enclosing function, annotated for the downstream IR-lowering boundary (§19, Steele 1978).
Type-directedness
the principle that arithmetic/comparison rewrites consult the node's Type before folding (P2, ADR-09).
Use-def graph
the graph connecting every variable use to its reaching definition(s), the basis for DCE and CSE (§16.2).
Worklist
a dedup'd FIFO queue of NodeIds driving a fact-propagation fixpoint (§14, §15). ---
