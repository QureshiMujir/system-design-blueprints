Project Number: 314

Project Name: Formal Verification Engine

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build a deductive program verifier from scratch: annotate an imperative source language with specifications (preconditions, postconditions, loop invariants, frame conditions), compile the annotated program to a verification intermediate representation (guarded commands), generate verification conditions (VCs) by a weakest-precondition calculus, discharge them with an SMT backend, and reconstruct counterexamples in source terms when a VC fails. Plus two auxiliary engines over the same IR: bounded model checking (BMC, finite unrolling) and k-induction (base + inductive step), and an abstract-interpretation front end for automatic loop-invariant inference.

The design point is Dafny / Why3 / Viper — a modular, contract-based verifier where each procedure is verified against its contract using callee contracts (not bodies) at call sites. The "engine" is the pipeline plus the seams between them: a clean source → IR lowering, a VCGen that is deterministic and terminating, a pluggable SMT interface over SMT-LIB2, and a counterexample reconstruction path that maps SMT models back to source.

In scope (Phase 0 deliverable):

  1. syntax — source AST, spec annotations, sorts/types, hash-consing, span tracking.
  2. parse — lexer + recursive-descent parser for the annotated source language and a spec sublanguage.
  3. typeck — sort/type checking, well-formedness of specs, ghost/physical separation, modifies-clause scoping.
  4. vir — verification IR: guarded commands (assume/assert/havoc/assign/;/□), basic blocks, CFG, loop cutpoints.
  5. lower — desugar source (procedures, loops, calls, arrays, ADTs) into VIR; insert contract obligations and frame axioms.
  6. passify — passification to dynamic-single-assignment (DSA), SSA-numbering, cut-loop elimination.
  7. vcgen — weakest-precondition (and strongest-postcondition alternative) over passive guarded commands; VC compaction.
  8. encode — VC → SMT-LIB2: theories LIA/LRA, arrays (select/store), EUF, bitvectors (machine ints), ADTs; quantifiers with triggers.
  9. smt — solver process driver (Z3/CVC5 over SMT-LIB2) + optional embedded DPLL(T) core; incremental push/pop; model/unsat-core extraction.
  10. cex — counterexample reconstruction: SMT model → source valuations, failing assertion, failing path/trace.
  11. bmc — transition-system encoding, bounded unrolling, property check to bound k.
  12. kind — k-induction (base case + inductive step) over the transition system.
  13. absint — abstract-interpretation framework (lattices, transfer functions, widening/narrowing) + invariant inference (intervals, Houdini).
  14. cli — verify, bmc, kinduct, infer, --dump-vir, --dump-smt, --proof, stats.

System boundaries. Verifies single-procedure and modular multi-procedure programs in the annotated language; emits Verified / Refuted(counterexample) / Unknown(reason) per procedure. Handles partial + total correctness (termination via decreases). Does NOT include: concurrency/heap-separation logic beyond a simple frame model (separation logic deferred), higher-order functions, a full proof assistant / tactic language, source languages beyond the project's own (no C/Rust/Java front end Phase 0), automatic specification synthesis beyond invariant inference, a verified-compiler-grade trusted kernel (the SMT solver remains trusted unless proof-checking mode is enabled).

Non-goals (Phase 0): separation logic / heap framing beyond modifies-sets, concurrency (rely-guarantee, linearizability), refinement types / dependent types as the spec language (cross-link #239), interactive proof / tactics, IC3/PDR invariant inference (deferred), interpolation-based invariant inference (deferred), a certified TCB (proof-producing mode is optional, not the default), floating-point reals (machine floats deferred), nonlinear arithmetic completeness.

Deployment model. A library (libverify) + a single CLI binary (verify). Used as: a backend/teaching vehicle for #282 static program verifier, #281 symbolic model verifier, #284 type-soundness proofs; an SMT client of #277/#278/#303; a sibling of #279 model checker (which is finite-state/temporal — see §2 differentiation) and #230 symbolic execution. Linux/macOS, x86-64/aarch64, single process; the SMT backend may be a child process or the embedded core.

Target users. Engineers learning deductive verification; authors of analysis/verification tools needing an embeddable VCGen + SMT-encoding library; researchers studying WP calculi, modular framing, and invariant inference.

What later phases unlock. Separation logic + heap framing; concurrency reasoning; refinement/dependent specs; interpolation + IC3/PDR invariant inference; proof-producing verification with an independent certificate checker; multiple real source-language front ends; an IDE/LSP integration with on-the-fly verification; counterexample-guided abstraction refinement (CEGAR) tying BMC/k-induction to predicate abstraction.

Estimated timeline. Phase 0 (parse → typeck → VIR → passify → WP VCGen → SMT encoding → counterexamples → BMC/k-induction → abstract-interpretation invariant inference): 12–14 weeks at full depth. Hardened multi-theory encoding + invariant inference + proof mode: 6–10 months.

Recommended language: Rust. Rationale: VCGen builds and rewrites large term DAGs (passified guarded commands, VC formulas) where structural sharing (hash-consing) and arena/index references dominate memory behavior — Rust gives precise control without a GC pausing a long verification run; enum models the source AST, VIR guarded commands, SMT terms, and the three-valued verification outcome cleanly and exhaustively (the compiler forces every term/command case to be handled — directly relevant to a determinism invariant); the SMT child-process driver wants robust, predictable I/O and timeout handling; and the borrow checker rules out the aliasing bugs that silently corrupt a term-rewriting pass (a corrupted VC is a soundness failure, the prime invariant). Rejected: OCaml (the traditional choice — Why3, Frama-C, and most of the verification literature are OCaml; superb pattern matching + GC for term graphs; rejected only for portfolio consistency and to keep one systems language across #277/#278/#303/#314, and because GC pauses complicate the determinism/latency story); Lean / Coq / Isabelle (proof-assistant hosts — ideal if the goal were a certified kernel, but this project is an automated verifier driving an external SMT solver, not an interactive prover; their learning surface is orthogonal); Haskell (fine for the symbolic core, laziness complicates reasoning about VCGen cost + determinism); Python (term-graph manipulation at scale is too slow; no static exhaustiveness on the AST). See ADR-01.

Prerequisites. Hoare logic + the weakest-precondition calculus; predicate logic + first-order theories (LIA/LRA, arrays, EUF, bitvectors, ADTs); the SMT-LIB2 standard + the SMT solver interface (assert/check-sat/push/pop/get-model/get-unsat-core); operational semantics + CFGs + SSA/DSA; lattice theory + abstract interpretation (Galois connections, widening/narrowing); bounded model checking + induction; basic proof theory (what makes an SMT answer trustworthy; the trusted computing base).

2. Why Build This

  • The weakest-precondition calculus is the bridge from logic to tools. Hoare triples are taught everywhere; almost no engineer implements wp over guarded commands, the VC-compaction that stops it exploding exponentially, and the loop rule that turns an annotated while into three discharge obligations. Implementing it demystifies every deductive verifier.
  • Modular verification is the architecture behind scalable correctness. Verifying a call site against the callee's contract (not its body), with a sound frame (modifies-clause) axiom, is the single idea that lets verification scale to large programs. Building it — purifying a call into assert pre; havoc modifies; assume post — is the project's intellectual core.
  • SMT encoding is a translation discipline. Mapping mathematical integers vs machine bitvectors, arrays to select/store, recursion to EUF + quantified axioms, and managing triggers / E-matching to instantiate quantifiers without matching loops teaches exactly where automated verification is incomplete and why — and how to engineer around it.
  • Counterexample reconstruction is what makes a verifier usable. A bare unsat/sat is useless to a developer; mapping an SMT model back to "at line 14, with x = 3, a = [0,0,7], the loop invariant is not preserved" is the difference between a research toy and a tool. It exercises the full provenance chain from source span → VIR → passified term → SMT variable → model.
  • Soundness vs completeness is a first-class engineering decision here, not a footnote. The prime invariant — never report a false program as verified — constrains every pass; accepting incompleteness (timeouts, quantifier instantiation gaps) is the deliberate price. Defining the trusted computing base (VCGen + encoding + solver) and an optional proof-checked mode is a rare, formative exercise in calibrated trust.
  • BMC, k-induction, and abstract interpretation are three complementary attacks on the same IR. BMC finds bugs fast (bounded, complete-for-bugs); k-induction proves safety inductively; abstract interpretation infers the invariants the deductive engine needs. Building all three over one transition-system view shows how the verification toolbox actually fits together.
  • Cross-links. SMT client ↔ #277 SAT solver, #278 SMT solver, #303 SAT/SMT hybrid (this project is a consumer of that decision procedure). Differentiate from #279 model checker (finite-state / temporal-logic / explicit-or-symbolic state exploration) — #314 is deductive, VC-based, infinite-state via logic. Spec/type seam ↔ #42 type checker, #238 Hindley-Milner, #239 dependent type checker, #247 bytecode verifier, #145 borrow checker (all are "verify a property of a program statically"). Symbolic seam ↔ #230 symbolic execution, #231 taint analysis (path-based vs VC-based). Logic seam ↔ #280 theorem prover basics, #281 symbolic model verifier, #282 static program verifier, #283 temporal logic evaluator, #284 type-soundness proof. Trust seam ↔ #92 ZK proof (both certify a claim to a skeptic; ZK hides the witness, a verifier produces one as a counterexample or a proof certificate).
  • Calibration. After this project, "verified" stops being a marketing word. You can read Dafny's or Why3's source and recognize every pass; you can explain precisely what a verifier trusts, why it sometimes says "unknown," and how a single dropped frame axiom turns a sound verifier into a confident liar. It permanently upgrades your ability to reason about program correctness as an engineering pipeline, not an abstraction.

Per-box.

  • parse — the only component touching untrusted source text. A hand-written lexer + recursive-descent parser for the annotated imperative language and the spec sublanguage (requires, ensures, invariant, decreases, modifies, reads, ghost, forall/exists with {trigger} annotations). Produces a hash-consed AST with source spans on every node (spans are the spine of counterexample reconstruction, §10/Phase 8). Everything downstream consumes validated, typed structures — never raw text.
  • typeck — assigns sorts/types (Int, Real, Bool, BitVec n, Array S T, ADTs, uninterpreted), enforces well-formedness of specs (a postcondition references only in-scope + old(...) variables; decreases is a well-founded expression; a trigger is a legal term covering the bound variables), separates ghost from physical state (ghost may not influence physical execution), and validates the modifies clause scope (a procedure may only assign variables/heap locations it declares it modifies — the frame discipline). Rejects ill-typed/ill-specified programs with located errors before any VC exists.
  • lower — desugars typed source into VIR guarded commands. The two load-bearing rules: (1) while g invariant I decreases V { B } becomes the standard cut: assert I (entry); havoc the loop-modified variables; assume I ∧ g; verify B re-establishes I and strictly decreases V; then assume I ∧ ¬g on exit — so the loop is verified once against its invariant, not unrolled. (2) call p(args) becomes assert pre[args]; havoc modifies(p); assume post[args, old] — modular: the callee's body is never inlined; correctness rests on the contract + frame. Also lowers if/;/assign/assert/assume/havoc, array read/write to select/store, ADT constructors/match, and ghost code.
  • VIR CFG — basic blocks whose statements are guarded commands (assume P, assert P, havoc x, x := e, sequencing ;, nondeterministic choice □). Loops appear as back-edges with explicit cutpoints carrying the invariant. This is the single normalized form every later pass and every engine (VCGen, BMC, k-induction) consumes.
  • passify — transforms the CFG into a form with no assignments and no cycles. Loops are cut at their cutpoints (the invariant assumption breaks the back-edge), yielding an acyclic CFG; assignments x := e become assume(x_i = e) under dynamic-single-assignment (each variable version numbered, SSA/DSA), so the resulting guarded commands are passive — pure assume/assert over immutable versioned variables. Passivity is what makes WP linear-size with sharing rather than exponential.
  • VCGen (wp/sp) — computes a verification condition per block via the weakest-precondition calculus over passive guarded commands: wp(assume P, Q) = P ⇒ Q, wp(assert P, Q) = P ∧ Q, wp(c1;c2, Q) = wp(c1, wp(c2, Q)), wp(c1 □ c2, Q) = wp(c1,Q) ∧ wp(c2,Q). A strongest-postcondition variant exists for comparison. The product is a first-order formula whose validity means "this block's assertions always hold." Naive WP duplicates Q across choices → exponential; VC compaction (the passive/block-equation form, à la Boogie/Barnett-Leino) introduces a fresh proposition per block and conjoins block equations, keeping the VC linear in program size.
  • VC compaction — converts the per-block WP into a conjunction of block verification equations using one fresh Block_b predicate per block, so shared continuations are referenced, not copied. Carries labels mapping each assert (and its conjuncts) back to a source span + obligation kind (precondition / postcondition / invariant-entry / invariant-preservation / decreases / assertion / array-bounds), feeding counterexample reconstruction.
  • encode — translates a VC (FOL over the verifier's sorts) into SMT-LIB2, choosing theories: linear integer/real arithmetic (LIA/LRA) for math integers/reals, the theory of arrays (McCarthy select/store) for arrays + the heap model, EUF for uninterpreted/recursive functions, bitvectors for machine-int semantics (overflow wraps), and algebraic datatypes for ADTs. Quantifiers are emitted with explicit triggers / patterns; the encoder enforces matching-loop avoidance (no trigger whose instantiation regenerates a matching term ad infinitum). To check validity of VC, it asserts ¬VC and checks for unsat.
  • smt — drives the decision procedure: by default an external Z3 or CVC5 child process over the SMT-LIB2 text stream (LOCK, ADR-14), with an optional embedded DPLL(T) core (cross-link #277/#278/#303) for self-containment. Uses incremental push/pop to reuse context across a procedure's many VCs, enforces a per-VC time budget (timeout → Unknown, never a false Verified — I15/P8), and extracts a model (for counterexamples) on sat and an unsat-core (for proof minimization + diagnostics) on unsat.
  • Verified / next — unsat of ¬VC means the VC is valid; advance to the next VC, then the next procedure. A procedure is Verified only when every VC is unsat within budget.
  • cex — on sat of ¬VC, the SMT model is a witness that the assertion can fail. Reconstruction maps model values back through the version numbering (DSA) and source spans to a human-readable counterexample: input/ghost valuations, the specific failing assertion (with its obligation kind), and the failing path/trace through the CFG (which branch choices and which loop iteration). This is the developer-facing output.
  • bmc — encodes the VIR as a transition system (Init, Trans, Prop) and unrolls Trans to a bound k, asserting Init ∧ Trans^0 ∧ … ∧ Trans^{k-1} ∧ ¬Prop; sat is a concrete bug trace of length ≤ k, unsat proves the property holds up to k. Complete for bug-finding within the bound; not a proof beyond it.
  • kind — k-induction: the base case (BMC to k: no violation in the first k steps) plus the inductive step (assuming the property held for k consecutive states, it holds at the (k+1)-th). If both discharge, the property holds for all reachable states — an inductive proof without a manually supplied invariant (strength permitting).
  • absint — an abstract-interpretation framework: a lattice (intervals Phase 0, with the structure to add octagons/polyhedra), monotone transfer functions per guarded command, a fixpoint iterator with widening (to force termination on loops) and narrowing (to recover precision). Its output is inferred loop invariants that feed lower so the deductive engine can discharge loops the user under-annotated; also drives Houdini (greatest-fixpoint pruning of candidate invariants).

Boundaries. Trust: only parse consumes untrusted input; the trusted computing base is VCGen + encode + the SMT solver (plus the optional proof checker shrinks it — see Deferred Features Register). Concurrency: single-threaded VCGen; VCs of distinct procedures are embarrassingly parallel (deferred parallel discharge). Persistence: none — verification is in-memory; SMT scripts + proofs stream to files. Protocol: the source language + spec sublanguage is the input contract; SMT-LIB2 is the solver contract; the CLI/library result triplet (Verified/Refuted/Unknown) is the external contract.

Correctness (soundness) is the only non-negotiable: a wrong Verified is a total failure regardless of speed or coverage (§6 P1). Incompleteness (Unknown/timeout on a true program) is accepted — it is the deliberate price of decidability + automation.

6. Design Principles

  1. P1 — Soundness over everything — never report a false program as Verified. Every pass (lower, passify, VCGen, encode) must preserve "VC valid ⟹ program correct." A timeout, a malformed encoding, or an unsupported feature returns Unknown, never Verified. Tradeoff: we accept incompleteness (true programs may not verify) to never accept an unsound one. Violation: a dropped frame axiom or an over-eager simplification that proves a false VC valid is catastrophic and silent — the verifier becomes a confident liar (I1).
  2. P2 — VCGen is deterministic and terminating. The same source yields a bit-identical VC; VCGen over the acyclic passive CFG is structurally recursive and always halts (no fixpoint in VCGen — fixpoints live only in absint, where widening guarantees termination). Tradeoff: term construction must use ordered, hash-cons-stable iteration (no HashMap iteration order into a VC). Violation: nondeterministic VCs make failures unreproducible and conformance flaky; a non-terminating VCGen hangs the tool (I7).
  3. P3 — Modularity: verify against contracts, never bodies, at call sites. A call p is assert pre; havoc modifies(p); assume post — p's body is irrelevant to the caller's proof. Tradeoff: a too-weak callee contract makes a correct caller fail to verify (incompleteness, not unsoundness). Violation: inlining bodies destroys scalability and couples every caller to every callee's implementation (P-frame, §8).
  4. P4 — Frame soundness: the call's havoc set must over-approximate the callee's true effects. If p actually modifies x but its modifies clause omits x, the caller wrongly assumes x unchanged across the call — unsound. The verifier therefore checks that each procedure respects its own modifies clause. Tradeoff: an over-broad modifies is sound but loses precision. Violation: under-declared frames are the classic modular-verification soundness hole (I14).
  5. P5 — The trusted computing base is explicit and minimal. What we trust to conclude Verified: the VCGen, the SMT encoding, and the SMT solver. We document it, keep VCGen + encode small + reviewable, and offer an optional proof-checked mode (Deferred Features Register) that shrinks the TCB to an independent certificate checker. Tradeoff: proof production costs time + complexity. Violation: an unstated TCB lets a solver bug silently certify a false program (P-trust).
  6. P6 — VCs must be compact (linear), never exponential. Naive WP duplicates the postcondition across every branch → exponential blowup. The block-equation/passive encoding (Leino) introduces one fresh predicate per block and conjoins block equations, sharing continuations. Tradeoff: the compacted VC is less directly readable. Violation: exponential VCs make any non-trivial program time out — incompleteness masquerading as a solver problem (I6).
  7. P7 — Encoding is faithful to the source semantics — machine ints wrap, math ints don't. A bv32 add overflows by wrapping (encoded over the bitvector theory); a mathematical int is unbounded (LIA). Mixing them is a deliberate, typed choice in lower/encode, never an accident. Tradeoff: bitvector reasoning is more expensive than LIA. Violation: encoding a machine int as a math int hides overflow bugs (a false Verified); the reverse over-constrains (I9).
  8. P8 — Quantifier instantiation is bounded and matching-loop-free. Quantified axioms (array/heap/recursive-function axioms) are emitted with explicit triggers; no trigger may match a term whose instantiation regenerates that trigger forever. Tradeoff: triggers that are too restrictive lose completeness (the solver can't instantiate a needed fact → spurious Unknown); too permissive → matching loops → timeout. Violation: a matching loop turns every VC mentioning the axiom into a non-terminating instantiation storm (I10, P8).
  9. P9 — Every Refuted ships a concrete, source-level counterexample. A bare sat is unacceptable; the model is reconstructed into variable valuations, the failing obligation (with kind + span), and a path/trace. Tradeoff: reconstruction couples encode/passify to source provenance (labels must survive every pass). Violation: a counterexample-less refutation is undebuggable; a spurious counterexample (model not actually a program execution) erodes trust (I11).
  10. P10 — Incrementality is core, not bolted on. Within a procedure, VCs share an SMT context via push/pop; across edits, only procedures whose VCs changed are re-verified (dependency-tracked). Tradeoff: provenance/dependency bookkeeping. Violation: re-verifying the whole program per edit makes interactive use unusable (P-incremental, Phase 11).
  11. P11 — Abstract transfer functions are monotone; widening guarantees termination. The absint fixpoint is sound only if each transfer function is monotone over the lattice, and only terminates on loops because widening forces a finite ascending chain. Tradeoff: widening loses precision (recovered partly by narrowing). Violation: a non-monotone transfer can compute an under-approximation → an unsound inferred invariant → a false Verified downstream (I12/I13).
  12. P12 — Separate the engine seams cleanly. parse → typeck → lower → passify → VCGen → encode → smt → cex is a pipeline of total functions over well-defined IRs; BMC/k-induction/absint are alternative consumers of VIR. The SMT backend never sees source; the parser never sees SMT. Tradeoff: more IRs to maintain. Violation: leaking SMT details into VCGen, or source into encode, ossifies the pipeline and makes a new theory or a new front end a rewrite (P-seam).
  13. P13 — Determinism + reproducibility end to end. Fixed encoding order, pinned solver version + seed, no wall-clock in decisions. A verification outcome reproduces exactly across runs and machines. Tradeoff: must order every iteration explicitly. Violation: a flaky Verified/Unknown is unactionable; a bug that won't reproduce can't be fixed (I7, P2).
  14. P14 — Bounded resources, graceful Unknown. Per-VC time + global memory budgets are first-class; on exhaustion the verifier returns Unknown(reason) and frees the SMT process — never crashes, never lies. Tradeoff: an under-resourced run under-reports. Violation: an OOM-killed verifier loses the run; returning Verified on timeout is the worst soundness bug (I15, P8).
  15. P15 — Specifications are checked for well-formedness before use. A decreases that isn't well-founded, a postcondition referencing out-of-scope state, a trigger not covering its bound variables — all rejected at typeck, with a located error, before a VC is built. Tradeoff: stricter specs are more work to write. Violation: an ill-formed spec produces a meaningless VC — a "verified" that proves nothing (I2/I8).

8.1 Source + spec language (EBNF)

program     ::= { decl } ;
decl        ::= proc_decl | func_decl | type_decl | ghost_decl ;
type_decl   ::= "type" Ident [ "=" adt_def ] ;            (* uninterpreted or ADT *)
adt_def     ::= ctor { "|" ctor } ;
ctor        ::= Ident [ "(" field { "," field } ")" ] ;
field       ::= Ident ":" sort ;
func_decl   ::= "function" Ident "(" [ params ] ")" ":" sort
                { "decreases" expr } [ "=" expr ] ;        (* pure; recursive ⇒ decreases *)
proc_decl   ::= "method" Ident "(" [ params ] ")" [ "returns" "(" params ")" ]
                { contract } block ;
contract    ::= "requires" expr                            (* precondition *)
              | "ensures"  expr                            (* postcondition (may use old(.)) *)
              | "modifies" lvalue { "," lvalue }           (* frame *)
              | "reads"    lvalue { "," lvalue }           (* read frame for functions *)
              | "decreases" expr { "," expr } ;            (* termination metric *)
params      ::= param { "," param } ;
param       ::= [ "ghost" ] Ident ":" sort ;
sort        ::= "int" | "real" | "bool" | "bv" Nat
              | "array" "<" sort "," sort ">" | Ident ;     (* Ident = ADT/uninterpreted *)
block       ::= "{" { stmt } "}" ;
stmt        ::= var_decl | assign | if_stmt | while_stmt
              | "assert" expr ";" | "assume" expr ";"
              | "havoc" lvalue { "," lvalue } ";"
              | call ";" | "return" ";" | block ;
var_decl    ::= [ "ghost" ] "var" Ident ":" sort [ ":=" expr ] ";" ;
assign      ::= lvalue ":=" expr ";" ;
lvalue      ::= Ident | Ident "[" expr "]" ;               (* var or array element *)
if_stmt     ::= "if" "(" expr ")" block [ "else" block ] ;
while_stmt  ::= "while" "(" expr ")"
                { "invariant" expr } [ "decreases" expr { "," expr } ] block ;
call        ::= [ lvalue { "," lvalue } ":=" ] Ident "(" [ args ] ")" ;
expr        ::= literal | lvalue | "old" "(" expr ")"
              | expr binop expr | unop expr
              | Ident "(" [ args ] ")"                      (* function application *)
              | "(" expr ")"
              | quant Ident ":" sort [ "{" trigger { "," trigger } "}" ] "::" expr
              | expr "[" expr "]" | expr "[" expr ":=" expr "]" (* select / store *)
              | "match" expr "{" { matcharm } "}" ;

Worked source (the canonical example — binary search "find max"):

method MaxIndex(a: array<int,int>, n: int) returns (m: int)
  requires n > 0
  ensures  0 <= m < n
  ensures  forall j: int { a[j] } :: 0 <= j < n ==> a[j] <= a[m]
{
  m := 0;
  var i: int := 1;
  while (i < n)
    invariant 1 <= i <= n
    invariant 0 <= m < i
    invariant forall j: int { a[j] } :: 0 <= j < i ==> a[j] <= a[m]
    decreases n - i
  {
    if (a[i] > a[m]) { m := i; }
    i := i + 1;
  }
}

8.2 Verification IR (guarded commands)

vir_proc  ::= "proc" Ident "(" vars ")" "{" cfg "}" ;
cfg       ::= block { block } ;
block     ::= label ":" { gcmd } terminator ;
terminator::= "goto" label { label }        (* nondeterministic choice over successors *)
            | "return" ;
gcmd      ::= "assume" expr                  (* path/loop/contract assumptions *)
            | "assert" expr label_kind span  (* the obligations; carry provenance *)
            | "havoc" var { var }            (* nondeterministic re-assignment *)
            | var ":=" expr ;                (* assignment (removed by passify) *)
label_kind::= "pre" | "post" | "inv_entry" | "inv_pres" | "decreases"
            | "assert" | "bounds" | "frame" | "div_nonzero" ;

VIR semantics (predicate-transformer view — Dijkstra/Boogie):

Command Meaning wp(c, Q)
assume P proceed only on paths where P holds P ⇒ Q
assert P obligation: P must hold here; else fail P ∧ Q
havoc x x takes an arbitrary value ∀x. Q
x := e (pre-passify) assign Q[e/x]
c1 ; c2 sequence wp(c1, wp(c2, Q))
c1 □ c2 nondeterministic choice (≈ goto) wp(c1,Q) ∧ wp(c2,Q)

8.3 Loop translation (the cut) and call translation (modular frame)

while (g) invariant I decreases V { B }      ⟿     # mods = vars assigned in B
   assert I ;                                       # I holds on entry  (inv_entry)
   havoc mods ;                                      # forget loop-modified vars
   assume I ;                                         # arbitrary iteration: assume I
   ( assume g ;                                        #   enter body
     assert 0 <= V ;                                  #   variant bounded below (decreases)
     let v0 = V in B ; assert I ; assert V < v0 ;     #   body re-establishes I, V decreased
     assume false                                     #   this path is for verification only
     □                                                #   ─ or ─
     assume !g )                                       #   exit: fall through with I ∧ ¬g
x := p(args)   (callee: requires Pre, ensures Post, modifies M)   ⟿
   assert Pre[args/params] ;          # caller must establish callee precondition  (pre)
   havoc M, x ;                        # forget everything the callee may change
   assume Post[args/params, old↦pre] ;# assume the callee's postcondition (post)

8.4 VC structure + the SMT validity query

A procedure's VC is a conjunction of block verification equations (compacted):

VC(proc) ≡  ⋀_b  ( Block_b  ⟺  wp_local(b, ⋀_{s∈succ(b)} Block_s) )   ∧   Block_entry

where Block_b is a fresh proposition per block and wp_local is WP over the block's guarded commands only (continuations referenced via Block_s, not inlined — this is the linear-size encoding, P6/I6). Validity check: emit (assert (not VC)) (check-sat); unsat ⟹ Verified; sat ⟹ a model ⟹ counterexample.

8.5 Worked verification — MaxIndex obligations (sketch)

For §8.1 MaxIndex, the VCs are: (1) inv_entry — after m:=0; i:=1, the three invariants hold (1≤1≤n, 0≤0<1, vacuous ∀j. 0≤j<1 ⇒ …); (2) inv_pres — assuming the invariants + i<n, the body (if a[i]>a[m] {m:=i}; i:=i+1) re-establishes them (the interesting one: the forall extends from <i to <i+1, requiring case analysis on whether m updated); (3) decreases — 0 ≤ n−i and n−(i+1) < n−i; (4) post — on exit (i≥n ∧ invariants), 0≤m<n and the global forall j. 0≤j<n ⇒ a[j]≤a[m] (follows since the invariant forall …<i plus i≥n plus i≤n gives i=n). Each is encoded with the array axioms + a quantified VC; the {a[j]} trigger instantiates the quantifier on exactly the array reads that appear.

8.6 Counterexample example (a missing invariant)

Drop invariant 0 <= m < i. Now inv_pres of the forall can't be proved (the verifier doesn't know m is in range when reading a[m]), and post 0≤m<n fails. SMT returns sat with e.g. n=2, i=1, m=5, a=[…]. cex reconstructs: "postcondition 0 <= m < n may fail; model: on entry the loop established no bound on m; at the loop exit m=5, n=2; failing obligation kind = post at line ensures 0 <= m < n." The fix (re-add the invariant) is implied by the trace. Note this is a spec incompleteness, not a soundness bug — the verifier correctly refuses to verify.

8.7 Malformed / edge / failure-path examples

  • Ill-formed decreases (decreases a[i] where a[i] is unbounded below) → typeck rejects: a decreases term must be a known well-founded sort (Int with a proven lower bound, or a lexicographic tuple) — located error (I2).
  • old(x) for a non-modified x → sound but flagged: old(x)=x for anything outside modifies; a redundant old is a warning, not an error.
  • Frame violation — a method assigns g (a global) but omits it from modifies → the per-procedure modifies-conformance VC fails; Refuted with kind frame (I14). This is the verifier catching an unsound spec, the most important diagnostic.
  • Division by zero — a / b emits an assert b != 0 obligation (kind div_nonzero); if unprovable, Refuted. (Not UB — a checked obligation.)
  • Integer overflow on bv32 — x + 1 where x = 2^31−1 wraps to −2^31 (BV semantics); if a postcondition assumed x+1 > x, it's correctly Refuted (overflow is modeled, I9). The same code on math int verifies (x+1 > x always) — the type choice changes the verdict, as it should.
  • Matching loop — a user axiom forall x {f(x)} :: f(x) == f(g(x)) whose trigger f(x) matches f(g(x)), regenerating f(g(g(x))), … → encode flags matching_loop_risk, suggests a safer trigger or Unknown with reason (I10). Never a hang.
  • Non-terminating recursive function without decreases → typeck requires decreases on recursive functions; absent ⇒ rejected (else the EUF axiom for the function could be inconsistent).
  • Quantifier with no trigger covering the bound variable → typeck rejects (the solver couldn't instantiate it deterministically); user must supply {...} (I2).

12. Phase 0 — Repo Skeleton, Syntax, Parser

12.1 Objectives

Lay the workspace, the hash-consed syntax substrate (Sort/Expr/Span/TermId), and the parser for the annotated source + spec sublanguage. No checking or verification yet — produce a typed-but-unchecked AST with spans on every node.

12.2 Detailed Implementation Steps

  • Cargo workspace; Makefile (build test lint fuzz bench conformance soundness-corpus); CI skeleton; Apache license; governance files (Dijkstra 1976; ADR-04).
  • syntax/intern.rs: hash-cons table interning every Expr to a TermId (structural sharing — essential for VCGen DAG size + determinism I7). syntax/span.rs: byte-range spans threaded from the lexer (ADR-05; I7).
  • syntax/sort.rs, syntax/ast.rs: the Sort and Expr/Stmt/Decl/Contract node types (§11).
  • parse/lexer.rs: tokens — keywords (method/function/requires/ensures/invariant/decreases/modifies/reads/ghost/forall/exists/old/assert/assume/havoc), identifiers, numerals, real literals, bitvector literals (0x.., #b.. width-tagged), operators incl. ==>/<==>.
  • parse/parser.rs: recursive descent over §8.1 EBNF; precedence-climbing for expr; explicit trigger syntax { t1, t2 } on quantifiers; located errors via parse/error.rs (Leino LPAR 2010; P2).
  • Depth guard on recursive descent (cap nesting) to prevent stack overflow on adversarial input (P14; T1).
  • --dump-ast echo for round-trip testing.

12.3 Deliverable

cli accepts a .vfy file, parses it, and --dump-ast echoes a normalized form; structurally identical subterms share a TermId; malformed input yields a precise located error.

12.4 Acceptance Criteria

  • Round-trip on examples/*.vfy (parse → dump → re-parse → identical AST).
  • Hash-consing: structurally equal terms share a TermId (identity test).
  • All §8.1 constructs parse, including triggers, old(.), quantifiers, match, store/select syntax.
  • Parser fuzz (cargo-fuzz) survives 5 min with no panic/UB; deep-nesting inputs hit the depth cap, not a stack overflow.

12.5 Conformance Fixtures

parse/method-contract, parse/while-invariant, parse/quantifier-trigger, parse/adt-match, parse/bv-literal, parse/missing-brace (error), parse/unterminated-quant (error), parse/hashcons-sharing.

12.6 Pitfalls

  • Not hash-consing from the start → VCGen term blowup + nondeterministic equality. Intern every node immediately.
  • Losing spans through desugaring later → counterexamples can't point at source (I8). Capture spans at the leaf in the lexer; never synthesize a node without one.
  • Ambiguous ==> vs >= / <==> lexing → silent misparse. Longest-match lexing, explicit tests.
  • Trigger parsed as a set literal → wrong AST. Triggers are pattern terms inside {} immediately after the quantifier binder; test the boundary.
  • Stack overflow on deep terms → crash. Depth cap or explicit stack; fuzz deep inputs.

12.7 Performance Concerns

Parsing is not the hot path, but the intern table is consulted per node — use a fast, deterministically-salted hasher (salt fixed for I7, not random). Stream large files; reuse a token buffer. Span storage is two u32s per node — cheap.

12.8 Edge Cases

Empty program (vacuously verifies later); a method with no body ({} → trivially Verified if no postcondition); old outside a postcondition (parse OK, rejected at typeck); nested quantifiers with shadowed binders; a forall with multiple trigger sets; bitvector literal width mismatch (lexer tags width, typeck checks); Unicode in identifiers (decide + document — ASCII-only Phase 0).

12.9 Failure Analysis

A parser bug mis-encodes the program → every verdict is for a different program (silent, total blast radius). Detection: round-trip + differential parse against a reference grammar on the corpus; --dump-ast alongside any verdict. Containment: the parser is the only untrusted-input component — fuzz it hardest. Recovery: minimize the offending source with tools/ddmin, add to regression.

12.10 Operational Notes

Stats from day one: parse_decls, parse_terms, hashcons_hits, max_term_depth. --dump-ast, --echo-tokens for debugging. Deterministic interning order (I7). The parser + AST are the teaching artifact for "what a spec language is" — heavily commented.

13. Phase 1 — Type/Sort Checking and Spec Well-Formedness

13.1 Objectives

Reject ill-typed and ill-specified programs before any VC exists: sort checking, ghost/physical separation, modifies-scope, decreases/trigger well-formedness. This phase makes "verified" meaningful (P15).

13.2 Detailed Implementation Steps

  • typeck/sorts.rs: bidirectional sort checking over Expr; arithmetic on int/real/bv n (no implicit coercion — int↔bv is an explicit op); array select/store sort agreement; function-application arity + sorts; match exhaustiveness over ADT constructors (Kroening & Strichman 2008; P7).
  • typeck/specs.rs: requires/ensures are bool; ensures may reference parameters, results, and old(e) (and only those); a decreases term is a well-founded metric (an int with a provable lower bound, or a lexicographic tuple) — else error (I2).
  • typeck/ghost.rs: a ghost variable/parameter may not flow into a physical assignment or a physical branch condition (a taint-style check) — ghost erasure soundness (I3) (P3; I3).
  • typeck/frame.rs: every lvalue assigned in a method body must be covered by its modifies clause (scope check); functions get a reads frame. Pure functions may not assign physical state.
  • Trigger well-formedness: each {trigger} must be a term set whose free variables cover all bound variables, and each trigger is a legal (non-ground, non-trivial) pattern (feeds I10 in Phase 6) (Detlefs-Nelson-Saxe JACM 2005; I10).
  • old(.) only in postconditions / 2-state contexts; old of a ghost is fine; old of a non-modified var is a warning (ADR-04; I18).

13.3 Deliverable

cli check file.vfy reports OK or a list of located type/spec errors; well-formed programs pass to lowering.

13.4 Acceptance Criteria

  • Every malformed-spec fixture is rejected with the correct error + span.
  • Ghost-leak fixtures are rejected (I3).
  • Modifies-scope violations are caught at check time (I14, the static half — the dynamic conformance VC is Phase 2/3).
  • Trigger WF rejects uncovered-binder triggers (I2).
  • Differential: well-typedness agrees with a Dafny-like reference on shared fixtures.

13.5 Conformance Fixtures

typeck/sort-mismatch (error), typeck/decreases-not-wf (error), typeck/ghost-leak (error), typeck/modifies-scope (error), typeck/trigger-uncovered (error), typeck/old-outside-post (error), typeck/match-nonexhaustive (error), typeck/valid-maxindex (OK).

13.6 Pitfalls

  • Implicit int/bv coercion → hides the math-vs-machine distinction (P7) → wrong verdicts downstream. Require explicit conversion ops.
  • Ghost flow only checked syntactically → indirect leaks (via a physical var assigned from a ghost). Use a flow/taint analysis, not a syntactic scan (I3).
  • Accepting an un-well-founded decreases → termination "proved" but isn't. The metric's well-foundedness is a checked property (I2).
  • Trigger covering binders but trivially matching everything (e.g. a variable as a trigger) → matching loops later. Reject degenerate triggers here.
  • Forgetting functions need a reads frame → unsound function axioms when the heap is involved.

13.7 Performance Concerns

Sort checking is near-linear in AST size; the ghost flow analysis is a small fixpoint over the (tiny per-procedure) variable set. Cache resolved sorts on TermId. None of this is hot relative to solving.

13.8 Edge Cases

Polymorphic-looking but monomorphic functions (no generics Phase 0); recursive ADTs (well-formedness of the datatype); a decreases lexicographic tuple of mixed sorts; old(old(e)) (flatten/error); a quantifier whose body is trivially true/false; mutually recursive functions (decreases must account for the cycle).

13.9 Failure Analysis

A type/spec checker that is too lenient lets a meaningless VC through → a Verified that proves nothing (the subtle failure). Too strict rejects valid programs (annoying, not unsound). Detection: the malformed-spec corpus must all be rejected; the valid corpus must all pass. Recovery: the offending spec is minimized; the checker rule is the fix.

13.10 Operational Notes

Stats: typeck_errors, ghost_checks, decreases_checked, triggers_validated. --explain-error prints the rule violated. This phase's strictness is a key usability/soundness knob — documented in docs/semantics.md.

14. Phase 2 — Verification IR and Lowering (the Heart of Modularity)

14.1 Objectives

Desugar typed source into VIR guarded commands: the loop cut, the modular call translation (assert pre / havoc modifies / assume post), arrays→select/store, ADTs, old capture, ghost lowering. Insert every proof obligation with its kind + span label (I8). This is where modular verification is built.

14.2 Detailed Implementation Steps

  • vir/gcmd.rs, vir/cfg.rs, vir/label.rs: the guarded-command + CFG + label types (§11).
  • lower/stmts.rs: structural lowering — if→two goto successors guarded by assume g/assume ¬g; ;→sequencing; assign/assert/assume/havoc pass through (assert gets a label); var := e introduces the variable.
  • lower/loops.rs: the cut (§8.3) — assert I (kind inv_entry); havoc the body-modified vars; assume I; the two-way choice (enter: assume g; assert 0≤V (decreases); body; assert I (inv_pres); assert V<v0; assume false □ exit: assume ¬g). Compute the body-modified set precisely (under-havoc is unsound, I14) (Dijkstra 1976; Barnett et al. FMCO 2005).
  • lower/calls.rs: the modular call (§8.3) — assert Pre[args] (kind pre); havoc modifies(callee) ∪ {results}; assume Post[args, old↦entry] (kind post for the callee, but here it's an assume for the caller). Emit a separate per-procedure modifies-conformance obligation: the body's actual assignments ⊆ declared modifies (kind frame, I14) (P3; P4; I14).
  • lower/data.rs: array a[i]→select(a,i), a[i]:=v→a := store(a,i,v); emit assert 0≤i<len bounds obligations (kind bounds) where the array is bounded; ADT ctor/match→theory terms; division emits assert d≠0 (kind div_nonzero); old(e)→capture e into a fresh entry-state version (I18) (ADR-11; I9).
  • lower/ghost.rs: ghost code lowered into VIR but marked erasable; an audit confirms physical VIR is unchanged if ghost commands are removed (I3 at the IR level) (I3; ADR-04).
  • --dump-vir to print the guarded-command CFG with labels.

14.3 Deliverable

cli --dump-vir file.vfy shows each procedure as a labeled guarded-command CFG; loops are cut (not unrolled); calls are modular (callee bodies absent); obligations carry kind + span.

14.4 Acceptance Criteria

  • Loop cut is correct: a verified loop's VIR contains no back-edge into the body verification path (acyclicity established here, completed in passify).
  • Call translation never references the callee body (modular — audit).
  • Every assert has a non-None label (I8 audit).
  • old capture audit: each old(e) resolves to an entry-state version (I18).
  • Modifies-conformance obligation present for every method with a modifies clause (I14).
  • Differential: the set of obligations (kinds + spans) matches a hand-derived oracle on small programs.

14.5 Conformance Fixtures

lower/loop-cut, lower/modular-call, lower/frame-obligation, lower/array-bounds, lower/old-capture, lower/div-obligation, lower/ghost-erasable, lower/adt-match.

14.6 Pitfalls

  • Under-computing the loop-modified set → havoc forgets too little → the loop "remembers" stale values → unsound (I14). Compute the modified set as a fixpoint over the body, including via calls (transitive modifies).
  • Inlining the callee body at a call → defeats modularity, couples the proof to the implementation (P3). Use the contract only.
  • old captured at the wrong point (e.g. after a havoc) → wrong 2-state semantics (I18). Capture at procedure entry.
  • Missing bounds/div obligations → an out-of-range access "verifies" (silent unsoundness). Emit the obligation at the lowering site, unconditionally.
  • Ghost code that changes physical VIR → ghost influences execution (I3). Audit erasure.
  • Forgetting the decreases obligations in the loop cut → termination unchecked while claiming total correctness. Emit 0≤V and V<v0.

14.7 Performance Concerns

Lowering is linear in program size; the transitive-modifies fixpoint is small (per call graph). Hash-cons all generated VIR terms (sharing across the many assume/assert that reference the same expressions). The havoc of a large modifies set introduces many fresh versions later — keep modifies tight (precision) but sound.

14.8 Edge Cases

A loop that modifies nothing (havoc empty — fine); a call to a method with an empty modifies (pure-effect method — havoc only results); nested loops (each cut independently, inner invariant in scope of outer); a while with no decreases (partial correctness only — no termination obligation, document); recursion (a recursive method's call site uses its own contract — the contract must be strong enough, else incompleteness); old of an array element vs the whole array.

14.9 Failure Analysis

A frame/modifies bug here is the classic modular-verification soundness hole — it produces a false Verified only on programs with calls/loops touching shared state (silent). Detection: the I14 modifies-conformance obligation (a method that lies about its frame is itself Refuted); the soundness corpus includes under-framed programs. Containment: every effect (assign, call, store) emits its obligation at lowering. Recovery: minimize; the offending desugaring rule is the fix; add to conformance/soundness/.

14.10 Operational Notes

Stats: vir_blocks, vir_obligations (by kind), loop_cuts, modular_calls, frame_obligations. --dump-vir, --dump-vir-dot (graphviz). This IR + lowering is documented normatively in docs/semantics.md; it is the contract every downstream pass relies on.

15. Phase 3 — Passification (DSA / SSA, Loop Cutpoint Elimination)

15.1 Objectives

Turn the VIR CFG into a passive, acyclic form: cut loops at cutpoints (the invariant assumption breaks the back-edge), number variables into dynamic-single-assignment, and rewrite x := e into assume(x_i = e). Passivity is what makes WP linear-size and terminating (P6/P2, I4/I5).

15.2 Detailed Implementation Steps

  • passify/cut.rs: using the cutpoints from lowering, remove back-edges so the CFG is a DAG; the loop's assume I after havoc is the only thing entering the iteration path, so no cycle remains (I5). Verify acyclicity (cycle check) (Barnett et al. FMCO 2005; I5).
  • passify/dsa.rs: assign each variable a version per definition (DSA). At join points (merge of if branches / loop exit), introduce φ-style versioning via assume(x_merge = x_then) / assume(x_merge = x_else) on the respective incoming edges, or hoist to a single merged version with edge assumptions (Boogie-style). Each Versioned is defined exactly once (I4 audit) (Leino IPL 2005; I4).
  • passify/assume_form.rs: rewrite every Assign(x, e) into Assume(x_new == e[old-versions]); after this pass, VIR contains only assume/assert/havoc (havoc introduces a fresh unconstrained version) — fully passive (Barnett et al. FMCO 2005; ADR-08).
  • Maintain a version map Versioned → (base VarId, source span) so the model can be reversed to source variables in cex (Phase 8) (I11; P9).
  • --dump-passive to print the passive guarded commands + version map.

15.3 Deliverable

cli --dump-passive file.vfy shows assignment-free, acyclic guarded commands with versioned variables and a version→source map; ready for WP.

15.4 Acceptance Criteria

  • Passive CFG is acyclic (I5 cycle check passes).
  • Every versioned variable has exactly one static definition (I4 audit).
  • No Assign remains (only assume/assert/havoc).
  • Semantics preserved: a program's verdict is identical whether WP runs on the un-passified or passified form on small examples (differential against a reference WP that handles assignment directly).
  • Version map round-trips: every model variable maps back to a (base var, span).

15.5 Conformance Fixtures

passify/dsa-straightline, passify/if-merge, passify/loop-cut-acyclic, passify/havoc-fresh-version, passify/version-map, passify/assign-to-assume.

15.6 Pitfalls

  • Wrong φ/merge handling → a variable's value at a join is wrong → unsound VC. The merge must constrain the merged version to each incoming version on the correct edge.
  • A residual cycle (missed cutpoint) → WP non-termination (P2 breach). Assert acyclicity after the pass (I5).
  • Two definitions of one version → DSA broken → the assume(x_i=e) constraints conflict/under-constrain. Audit single-definition (I4).
  • Havoc not introducing a fresh version → the havoc'd value is conflated with its pre-havoc version → loop cut unsound. Each havoc mints a new version.
  • Version map drift → counterexamples point at the wrong source variable. Keep the map authoritative + tested.

15.7 Performance Concerns

Passification is linear with the dominator/merge structure; the version map is a vector. The number of versions bounds the SMT variable count — keep havoc sets tight (from Phase 2). Hash-consing means the many assume(x_i = e) share e's subterms.

15.8 Edge Cases

A variable never assigned (single version = its initial); a variable assigned on one branch only (merge with the unchanged version on the other edge); a loop that assigns a variable used in its own invariant (versioning across the cut); nested branches/loops (versioning composes); a havoc'd variable later read (reads the fresh version).

15.9 Failure Analysis

A passification bug (bad merge, residual cycle, version collision) yields either a wrong VC (silent unsoundness, on programs with the relevant control flow) or a hang (residual cycle → WP loops). Detection: the I4/I5 audits + differential against a direct-assignment WP. Containment: assert acyclicity + single-definition every run in debug builds. Recovery: minimize; the merge/cut rule is the fix.

15.10 Operational Notes

Stats: dsa_versions, passive_blocks, merges, cutpoints_cut. --dump-passive, --dump-version-map. This pass is invisible to users but its correctness underpins both soundness (right VC) and liveness (terminating WP) — paranoid audits stay on in CI.

16. Phase 4 — VC Generation (Weakest Precondition + Compaction)

16.1 Objectives

Generate the verification condition from passive guarded commands via the weakest-precondition calculus, in the block-equation compacted form so the VC is linear, not exponential (P6/I6). Carry obligation provenance into the VC for counterexamples (I8). Implement an sp variant for differential testing only.

16.2 Detailed Implementation Steps

  • vcgen/wp.rs: the WP transformer over guarded commands (§8.2 table): wp(assume P,Q)=P⇒Q, wp(assert P,Q)=P∧Q, wp(havoc x,Q)=∀x.Q, wp(c1;c2,Q)=wp(c1,wp(c2,Q)), wp(c1□c2,Q)=wp(c1,Q)∧wp(c2,Q), wp(skip,Q)=Q. (Assignment is gone — passified.) (Dijkstra 1976; Flanagan & Saxe POPL 2001)
  • vcgen/compact.rs: the block-equation encoding (Leino) — for each block b a fresh boolean Block_b; emit Block_b ⟺ wp_local(b, ⋀_{s∈succ(b)} Block_s) where wp_local is WP over b's own commands with successors referenced by their Block_s (not inlined). The VC is (⋀_b block-equation_b) ∧ Block_entry (§8.4). This shares continuations → linear size (I6) (Leino IPL 2005; ADR-07; I6).
  • vcgen/obligation.rs: tag each assert's contribution with its (ObligationKind, Span) so that when the VC is invalid, the failing conjunct identifies the source obligation (I8/I11). Use distinct boolean "obligation markers" or labeled assertions in the SMT encoding (Phase 5) for unsat-core/model attribution (I8; P9).
  • vcgen/sp.rs: the strongest-postcondition variant (sp(assume P, R)=R∧P, sp(assert P,R)=R∧P with the obligation R⇒P, …) — used only to differentially cross-check WP (a VC valid under WP must be valid under SP for the same program). ADR-06.
  • A VC-size guard: assert vc_nodes = O(program nodes) (I6); fail loudly if the compaction regressed to exponential (I6; M2).

16.3 Deliverable

cli --dump-vc file.vfy prints the per-procedure VC (compacted) as a FOL formula with obligation labels; the VC is linear in program size.

16.4 Acceptance Criteria

  • VC node count is linear in program size across the corpus (I6 ratio guard; a deliberately branch-heavy fixture stays linear, not exponential).
  • WP and SP agree on validity for every fixture (differential, ADR-06).
  • The VC for MaxIndex (§8.5) has exactly the expected obligation set (inv_entry, inv_pres, decreases, post, bounds) with correct spans.
  • VC is bit-identical across runs (I7).
  • Every conjunct of the VC traces to an obligation kind + span (I8).

16.5 Conformance Fixtures

vcgen/straightline, vcgen/branch-linear (exponential-naive, linear-compacted), vcgen/loop-obligations, vcgen/wp-vs-sp, vcgen/obligation-labels, vcgen/vc-deterministic, vcgen/maxindex-vc.

16.6 Pitfalls

  • Naive WP without compaction → exponential VC on nested branches → solver times out (incompleteness blamed on the solver). The block-equation form is mandatory (I6).
  • wp(havoc x, Q) without the universal → unsound (forgets that x is arbitrary). It must be ∀x.Q (the havoc'd version is universally quantified, or equivalently fresh-and-unconstrained in the passive encoding).
  • Losing obligation labels in compaction → counterexamples can't name the failing obligation (I8/I11). Thread (kind, span) through every assert→conjunct.
  • WP/SP divergence → a bug in one calculus. The differential (ADR-06) catches it; investigate any disagreement as a soundness bug.
  • Quantifier capture in WP (havoc introduces ∀x that captures a free x in Q) → wrong VC. With DSA versioning this is avoided (the havoc'd version is fresh), but assert it.

16.7 Performance Concerns

VCGen is the verifier's own hot path (before the solver). The compacted form keeps the VC DAG linear; hash-consing shares subterms aggressively. Build the VC bottom-up over the DAG with memoization (each block's equation computed once). Avoid materializing the exponential naive WP even transiently. The VC size directly drives solver time — minimizing it is the highest-leverage performance work pre-solver.

16.8 Edge Cases

A procedure with no obligations (trivially valid VC — Block_entry reachable, no assert); a single unreachable assert (still emit, the VC handles reachability via the block equations); deeply nested choices (compaction keeps it linear); a havoc of many variables (many universals — but in passive form, fresh versions); an empty CFG (vacuous).

16.9 Failure Analysis

A WP-rule bug (wrong assume/assert/havoc transformer) is a soundness bug — it can make a false VC valid (false Verified) or a true VC invalid (spurious Refuted/Unknown). Detection: the WP-vs-SP differential + the soundness corpus (known-buggy programs must be Refuted) + hand-checked VCs on small programs. Blast radius: every verdict using the buggy rule. Containment: the VC-size guard catches the exponential regression; the differential catches the unsound rule. Recovery: minimize; the transformer rule is the fix; the program enters conformance/soundness/.

16.10 Operational Notes

Stats: vc_nodes, vc_nodes_per_program_node (the I6 ratio), obligations_per_vc (by kind), wp_vs_sp_agreements. --dump-vc, --dump-vc-naive (the uncompacted form, for teaching the blowup). The VC + its labels are the contract between VCGen and both encode (Phase 5) and cex (Phase 8).

17. Phase 5 — SMT Encoding (Theories, Quantifiers, Triggers)

17.1 Objectives

Translate the VC into SMT-LIB2, mapping each sort to a theory (LIA/LRA, arrays, EUF, bitvectors, ADTs), emitting quantifiers with explicit triggers, and enforcing matching-loop avoidance (I10). Machine ints encode over bitvectors (wrap), math ints over LIA (unbounded) (I9). Deterministic emission order (I7).

17.2 Detailed Implementation Steps

  • encode/theory.rs: the sort→theory map — int→Int (LIA/LRA via Reals_Ints), real→Real, bool→Core, bv n→(_ BitVec n), array<S,T>→(Array S T), ADTs→declare-datatypes, uninterpreted sorts→declare-sort. Uninterpreted/recursive functions→declare-fun + quantified defining axioms (recursive ones guarded by the decreases-justified well-founded recursion so the axiom set is consistent) (Kroening & Strichman 2008; ADR-09; I9).
  • encode/bvint.rs: machine-int operations → bitvector ops (bvadd/bvmul/bvsub/bvudiv/bvurem/bvshl/bvlshr/bvashr, bvult/bvslt, sign/zero extend, concat/extract); overflow wraps (the modeled semantics, I9). Explicit int↔bv conversion ops emit int2bv/bv2int (or (_ to_bv n)-style) per SMT-LIB.
  • encode/quant.rs: emit (forall ((x S)) (! body :pattern (trigger))) with the user/typeck-validated triggers; run a matching-loop check — a trigger t is unsafe if instantiating its axiom can produce a new term matching t (e.g. f(x) triggering f(g(x))); flag matching_loop_risk and either pick a safer trigger, split the axiom, or return Unknown(reason) rather than risk a hang (I10) (Detlefs-Nelson-Saxe JACM 2005; de Moura & Bjørner CADE 2007; I10).
  • encode/emit.rs: the SMT-LIB2 text emitter — deterministic declaration + assertion order (sorted by a stable key, I7); names derived deterministically from TermId/version; emit the array/heap framing axioms (select-over-store) the array theory needs only if not native; finally (assert (not VC)) (check-sat) (ADR-24; I7).
  • Per-obligation attribution: emit labeled assertions ((! cond :named ob_k)) so the unsat-core (valid case) and the model (invalid case) attribute to the right obligation (feeds Phase 8) (I8; I11; P9).
  • --dump-smt to print the emitted SMT-LIB2.

17.3 Deliverable

cli --dump-smt file.vfy emits valid, deterministic SMT-LIB2 for each procedure's VC; a standalone Z3/CVC5 reproduces the verifier's verdict on the dumped script (a key trust check).

17.4 Acceptance Criteria

  • Emitted SMT-LIB2 parses + checks under both Z3 and CVC5 (interop).
  • The verdict from the dumped script (run externally) matches the verifier's verdict (no hidden state, faithful encoding).
  • Machine-int fixtures encode over BV (overflow wraps → the overflow bug is sat/refutable); the same code on int encodes over LIA (no overflow) — I9 demonstrated.
  • No emitted axiom forms a matching loop on the trigger corpus (I10 check passes); a deliberately-loopy trigger is flagged, not run to a hang.
  • SMT text is bit-identical across runs (I7).

17.5 Conformance Fixtures

encode/lia-arith, encode/array-select-store, encode/euf-function, encode/bv-overflow, encode/adt-datatype, encode/quant-trigger, encode/matching-loop-flagged, encode/smt-deterministic, encode/z3-cvc5-interop.

17.6 Pitfalls

  • Encoding a machine int as a math int (or vice-versa) → hides overflow (false Verified) or over-constrains (spurious Refuted) — the canonical encoding soundness bug (I9). The type→theory map is authoritative; test both.
  • Over-permissive triggers → matching loops → the solver instantiates forever → timeout on every VC mentioning the axiom (I10). The matching-loop check + conservative triggers are mandatory; prefer Unknown to a hang.
  • Over-restrictive triggers → the solver can't instantiate a needed fact → spurious Unknown (incompleteness). Balance; expose the trigger to the user.
  • Non-deterministic emission order (HashMap iteration) → non-reproducible SMT, flaky verdicts (I7). Sort by a stable key.
  • Inconsistent recursive-function axioms (no decreases guard) → the solver "proves" anything (unsat of everything) → catastrophic false Verified. Recursive defining axioms must be well-founded (tie to typeck I2).
  • Forgetting (assert (not VC)) → checking the VC's satisfiability instead of validity → inverted verdict. Validity = unsat of the negation.

17.7 Performance Concerns

The emitted formula size drives solver time; bitvector reasoning (esp. multiply) is far costlier than LIA — prefer int where the source semantics allow (a typing/modeling decision). Quantifiers + triggers are the dominant solver-time risk; fewer, tighter axioms solve faster. Stream the SMT text to the process (don't buffer huge scripts). Reuse declarations across a procedure's VCs (incremental, Phase 6).

17.8 Edge Cases

A VC with no quantifiers (pure QF — fast, decidable); a VC mixing BV + arrays + EUF (combined theory — the solver's Nelson-Oppen handles it, but the encoding must be sort-consistent); division by a possibly-zero divisor (the div_nonzero obligation already guards it; the encoding uses the theory's total div with the side obligation); a ground quantifier (no binders — just assert); ADT with no recursion vs recursive ADT (datatype decl handles both); a bitvector of width 1 (boolean-ish).

17.9 Failure Analysis

An encoding bug is a soundness bug at the boundary of the TCB — a faithful-looking but wrong encoding produces a false verdict silently. Detection: the dumped-script-vs-verifier check (the encoding has no hidden state, so an external solver must agree); the soundness corpus; the I9/I10 audits; differential against Dafny/Why3 (which encode the same VCs). Containment: --dump-smt makes the encoding inspectable; an external solver is the oracle. Recovery: minimize; the encoding rule is the fix. Full proof-producing mode (independent certificate checker shrinking the TCB) is PhaseDeferred("Deferred Features Register").

17.10 Operational Notes

Stats: smt_terms, quantifiers_emitted, triggers_emitted, matching_loop_flags, bv_ops, lia_ops. --dump-smt, --solver z3|cvc5, --trigger-mode strict|auto. The emitted SMT-LIB2 is a stable, inspectable artifact — the single best debugging surface for "why did the verifier conclude that?"

18. Phase 6 — SMT Backend Driver (External + Embedded), Incremental

18.1 Objectives

Drive the decision procedure: an external Z3/CVC5 child process over SMT-LIB2 (the LOCK, ADR-14/15) and an optional embedded DPLL(T) core; incremental push/pop to reuse context across a procedure's VCs; per-VC time + memory budgets mapping to Unknown (I15); model + unsat-core extraction.

18.2 Detailed Implementation Steps

  • smt/backend.rs: the SmtBackend trait (§11) — declare/assert/push/pop/check_sat(budget)/get_model/get_unsat_core.
  • smt/process.rs: spawn z3 -in / cvc5 --incremental as a child; a line-oriented request/response protocol over stdin/stdout; a hard timeout (the budget) implemented by a watchdog that kills the process on overrun → Unknown(Timeout) (never blocks, never lies, I15); detect solver crash/unknown → Unknown(reason); restart a crashed solver process (ADR-14; ADR-15; I15).
  • Incremental discharge: for a procedure, declare the symbols once, then per VC push; assert (not VC_i); check-sat; pop — reusing the declarations + the solver's learned lemmas (P10). Order VCs to maximize context reuse (P10; ADR-14).
  • smt/model.rs: parse get-model (S-expressions → Model) and get-unsat-core (named assertions → the responsible obligations). Robust to solver-specific formatting (Z3 vs CVC5) (I11; ADR-17).
  • smt/embedded/: the optional self-contained DPLL(T) core (cross-link #277/#278/#303) — a smaller, slower, dependency-free fallback so libverify does not require an external solver; selectable via --solver embedded. (Its internals are the subject of #303; here it is a backend behind the same trait.)
  • Memory budget: cap the solver process RSS (cgroup/rlimit); on breach → kill → Unknown(MemLimit) + free (I15) (P14; I15).

18.3 Deliverable

cli verify file.vfy discharges each procedure's VCs against the chosen backend, returning Verified/Unknown per procedure (counterexamples added in Phase 8); incremental reuse is measurable; budgets enforce a deterministic Unknown.

18.4 Acceptance Criteria

  • MaxIndex (and the valid corpus) verifies under both Z3 and CVC5.
  • A deliberately-hard VC times out to Unknown(Timeout) within budget + ε — never hangs, never returns Verified (I15).
  • Incremental discharge is measurably faster than fresh-context-per-VC on a multi-VC procedure (P10).
  • The embedded core agrees with Z3 on the QF subset of fixtures (where it is complete).
  • A killed/crashed solver process → Unknown, and the verifier recovers (next procedure proceeds).

18.5 Conformance Fixtures

smt/verify-valid, smt/timeout-unknown, smt/incremental-reuse, smt/embedded-vs-z3-qf, smt/solver-crash-recovery, smt/mem-limit-unknown, smt/z3-cvc5-agree.

18.6 Pitfalls

  • Timeout returning the last answer / blocking → a hang or a wrong verdict (I15). The watchdog must kill and force Unknown; never read a partial/stale response as authoritative.
  • Parsing only Z3's model format → CVC5 models mis-parsed → wrong counterexamples. Handle both; test interop.
  • Pop not restoring solver state → cross-VC contamination → wrong verdict on a later VC. Match push/pop exactly; or use a fresh push scope per VC.
  • Solver process leak (not reaped on timeout) → fd/process exhaustion over a large program. Always kill + reap; bound concurrent processes.
  • Trusting unknown as unsat → false Verified. Solver unknown ⟹ verifier Unknown (I15) — never Verified.
  • Embedded core silently incomplete on quantifiers → returns unknown where Z3 succeeds → more Unknown. Document the embedded core's incompleteness; default to external.

18.7 Performance Concerns

The solver dominates end-to-end time. Incremental reuse (declarations + learned clauses across VCs) is the biggest win — verification asks many related queries. Process-transport overhead (text serialization) is real for huge VCs — keep VCs small (Phase 4). Parallelizing distinct procedures' solvers is the natural next axis (deferred). The watchdog adds negligible overhead.

18.8 Edge Cases

A VC that's trivially valid (no solver round-trip needed — short-circuit); a solver that returns sat with a partial model (request full model / mark vars unconstrained); a procedure with thousands of VCs (incremental + budget per VC, global budget overall); the embedded core on a BV-heavy VC (slow but correct); a solver version mismatch (record the version in output, I7/reproducibility); zero budget (immediate Unknown).

18.9 Failure Analysis

The solver is trusted (in the TCB) — a solver soundness bug would cause a false Verified the verifier can't detect without proof mode. Detection (mitigation): run two solvers (Z3 + CVC5) on the soundness corpus and disagreements are red flags; proof-producing mode (independent certificate check) shrinks this trust (PhaseDeferred("Deferred Features Register")). A driver bug (timeout/parse) is detectable: the timeout-fixture must yield Unknown; model-parse fixtures check both formats. Separation-logic/concurrency backends are deferred: PhaseDeferred("Deferred Features Register"). Recovery: restart solver; cross-check the other solver; minimize.

18.10 Operational Notes

Stats: vcs_checked, verified, unknown (by reason: timeout/memlimit/solver-unknown/crash), solver_seconds (p50/p95/p99 per VC), incremental_reuse_ratio, solver_restarts. --solver z3|cvc5|embedded, --timeout MS, --mem-limit MB. The per-VC solver-time distribution is the primary performance + flakiness signal; record solver name + version in every report (reproducibility).

19. Phase 7 — End-to-End Verifier + Modifies Conformance

19.1 Objectives

Compose the pipeline into the verify_program driver: per-procedure verification (all VCs unsat ⟹ Verified), the per-procedure modifies-conformance check (a method must respect its own frame, I14), and the program-level report. This is the first fully-working deductive verifier (modulo counterexample rendering, Phase 8).

19.2 Detailed Implementation Steps

  • cli/main.rs + the Verifier trait (§11): for each procedure, run parse→typeck→lower→passify→vcgen→encode→smt; aggregate per-VC results; Verified iff every VC is unsat within budget, else Refuted (Phase 8) or Unknown (P1; I1).
  • Modifies conformance: discharge the per-procedure obligation from Phase 2 — the method's actual assignments (incl. transitive via calls) ⊆ declared modifies. A method that under-declares its frame is itself Refuted (kind frame) — this is the verifier enforcing the soundness of the modular call rule (I14). Implemented as an extra VC per method (P4; I14; ADR-04).
  • Dependency tracking: record which procedures each procedure's VC depends on (its callees' contracts) so re-verification can be incremental (Phase 11) (P10; Phase 11).
  • Program report: a per-procedure verdict table + aggregate counts; machine-readable conformance.report.json.
  • The soundness tripwire: a CI job runs conformance/soundness/ (known-buggy programs) and fails the build if any is Verified (I1) — the single most important test (I1; M12).

19.3 Deliverable

cli verify program.vfy prints a per-procedure verdict; the valid corpus is Verified, the refuted corpus is Refuted, the soundness corpus is 100% Refuted; a JSON report is emitted.

19.4 Acceptance Criteria

  • The valid corpus: 100% Verified. The soundness corpus: 100% Refuted (I1, the prime gate).
  • A method that lies about its modifies is Refuted with kind frame (I14).
  • Differential vs Dafny/Why3 on shared programs: verdicts agree (allowing for Unknown differences from solver/encoding strength).
  • The report is deterministic (same input + solver version ⟹ same report, I7).

19.5 Conformance Fixtures

verify/valid-corpus, verify/refuted-corpus, soundness/under-framed-call (must Refute), soundness/missing-bounds-check (must Refute), soundness/false-postcondition (must Refute), verify/modifies-conformance, verify/report-deterministic, verify/vs-dafny.

19.6 Pitfalls

  • Verified declared before all VCs discharged (e.g. short-circuiting on the first unsat) → unsound. Verified requires every VC unsat (I1).
  • Skipping the modifies-conformance VC → the frame rule is assumed but never checked → under-framed methods silently produce false Verified at their call sites (I14). The conformance VC is mandatory.
  • Treating Unknown as Verified or Refuted → either unsound or a spurious refutation. Unknown is its own verdict (I15).
  • Soundness corpus not run in CI → a soundness regression ships. The tripwire is a release gate.
  • Cross-procedure contamination (a stale contract used) → wrong verdict. Contracts are fixed inputs; dependency-tracked.

19.7 Performance Concerns

End-to-end time = Σ per-procedure (VCGen + solver). Procedures are independent → the parallelization axis (deferred). Incremental re-verification (Phase 11) is the practical win for iterative use. The modifies-conformance VC is cheap relative to the functional VCs.

19.8 Edge Cases

A program with a single trivially-correct method; mutually recursive methods (each uses the other's contract — contracts must be strong enough, else Unknown); a method with no contract (vacuous pre/post — verifies trivially unless it has internal asserts); a method that calls an unverified method (uses its contract regardless — modular); an empty program (vacuously verified).

19.9 Failure Analysis

A composition bug (short-circuit, skipped conformance VC, Unknown-as-Verified) is a soundness bug at the top level. Detection: the soundness tripwire (I1) + the modifies-conformance fixtures (I14) + differential vs Dafny. Blast radius: any program; this is the verifier's headline guarantee. Containment: the tripwire fails the build. Recovery: the composition logic is the fix; the program enters the soundness corpus permanently.

19.10 Operational Notes

Stats: procedures, verified, refuted, unknown, frame_violations, total_vcs, wall_seconds. --report json, --fail-on unknown (CI strictness knob). The soundness tripwire's result is the headline CI signal; false_verified_total must be 0 on every build.

20. Phase 8 — Counterexample Reconstruction

20.1 Objectives

Turn a sat (VC fails) into a developer-usable counterexample: SMT model → DSA-reverse → source variable valuations, the failing obligation (kind + span), and the failing path/trace through the CFG. Re-check the model for spuriousness (I11).

20.2 Detailed Implementation Steps

  • cex/reconstruct.rs: from the Model (Phase 6), use the version map (Phase 3) to recover source-level variable values at each program point — present the input values (entry versions) and the values at the failing assertion. Map SMT symbols back to source names + spans (I11) (I11; ADR-17).
  • cex/trace.rs: determine the failing path — which goto choices and which loop iteration the model corresponds to (the block-equation truth assignment + the version values identify the path); render it as an ordered list of source statements with the branch taken (I8; P9).
  • Failing-obligation attribution: the labeled assertion / model marker (Phase 5) identifies which obligation failed (kind + span) — e.g. "postcondition at line N", "loop invariant not preserved at line M", "array index out of bounds at line K" (I8; ADR-07).
  • cex/render.rs: a human-readable message (source excerpt + valuations + the failing obligation + the path) and a machine witness (SV-COMP-style) for tooling.
  • Spuriousness re-check (I11): re-evaluate the reconstructed model against the original program along the identified path; if it does not actually violate the obligation, the counterexample is spurious (a reconstruction/encoding bug) → downgrade to Unknown + flag spurious_cex_total (never present a fake counterexample) (T7; P9).

20.3 Deliverable

cli verify on a refuted program prints a concrete counterexample: the failing obligation (kind + span), the input + failing-point valuations, and the failing path; a machine witness is emitted with --witness.

20.4 Acceptance Criteria

  • Every Refuted ships a counterexample whose model satisfies ¬VC and which the spuriousness re-check confirms (I11; spurious_cex_total = 0).
  • The MaxIndex-minus-invariant example (§8.6) produces the expected "postcondition 0≤m<n may fail" message with the right span.
  • Counterexamples for each obligation kind (pre/post/inv/bounds/div/frame) render correctly with the right kind label.
  • The failing path matches a hand-traced execution on small examples.

20.5 Conformance Fixtures

cex/post-fails, cex/inv-not-preserved, cex/array-oob, cex/div-by-zero, cex/precondition-fails, cex/frame-violation, cex/spurious-detected (a crafted case the re-check must catch), cex/witness-format.

20.6 Pitfalls

  • Presenting a spurious counterexample (model isn't a real execution) → erodes all trust in the tool (I11). The spuriousness re-check is mandatory; downgrade to Unknown rather than lie.
  • Wrong variable mapping (version map drift, Phase 3) → values attributed to the wrong source variable. Keep the version map authoritative + tested.
  • Reporting a model, not the failing point's values → confusing (e.g. mid-loop vs entry values conflated). Distinguish input vs failing-point valuations via the versions.
  • Losing the obligation label (Phase 4/5 attribution dropped) → "something failed" with no kind/span (useless). The label must survive to here (I8).
  • Path ambiguity (model consistent with multiple paths) → pick a canonical one deterministically; document.

20.7 Performance Concerns

Reconstruction runs only on Refuted (the minority of VCs in a converged spec), so it can afford to be thorough (the spuriousness re-check re-evaluates one path — cheap). Model parsing is O(model size). Rendering is trivial. No hot-path concern.

20.8 Edge Cases

A model with unconstrained variables (present as "any value" / a chosen default); a quantified-fact failure (the model may not directly exhibit a witness for a forall postcondition — present the instantiation the solver used if available, else the relevant valuations); a counterexample on a loop (which iteration — derive from the variant/version values); a refutation with a huge model (truncate to relevant variables via the unsat-core-style relevance); nested-call refutation (the failing obligation is in a callee's assumed postcondition vs the caller's assert pre).

20.9 Failure Analysis

A counterexample bug is not a soundness bug (the verdict Refuted is correct — the verifier correctly refused to verify) but a trust/usability bug: a wrong or spurious counterexample makes developers distrust correct refutations. Detection: the spuriousness re-check (I11) + hand-checked counterexamples on the fixture corpus + the spurious_cex_total counter (must be 0). Recovery: fix the reconstruction/mapping; the spuriousness re-check is the safety net (downgrades to Unknown meanwhile).

20.10 Operational Notes

Stats: refutations, cex_rendered, spurious_cex_total (must be 0), cex_model_vars_avg, cex_path_len_avg. --witness FILE, --cex-verbose (full model). Counterexamples are the developer-facing payload — their quality determines whether the tool is used; the spuriousness re-check guarantees we never present a fake one.

21. Phase 9 — Bounded Model Checking (BMC)

21.1 Objectives

A complementary engine over the same VIR: encode the program as a transition system (Init, Trans, Prop), unroll Trans to a bound k, and check Init ∧ ⋀_{i<k} Trans_i ∧ ¬Prop — sat is a concrete bug trace ≤ k, unsat proves the property up to k (I16). Complete for bug-finding within the bound; reuses encode/smt/cex.

21.2 Detailed Implementation Steps

  • bmc/transys.rs: lower VIR (the un-cut, original CFG — BMC unrolls, it does not use invariants) into a transition system: state variables (the program variables + a program counter), Init (entry state + preconditions), Trans(s, s') (one step of any enabled guarded command), Prop (the assertion / safety property) (Biere et al. 2003; ADR-19).
  • bmc/unroll.rs: instantiate Trans for steps 0..k with versioned state per step (reusing the DSA machinery); conjoin Init, the unrolled transitions, and ¬Prop at (any) step ≤ k; emit to encode/smt (I16; Sheeran-Singh-Stålmarck FMCAD 2000).
  • On sat: reconstruct a concrete execution trace of length ≤ k via cex (the same model→source path machinery, but a literal step-by-step trace) — BMC's counterexamples are exact program executions (its strength) (I11; P9).
  • On unsat: report "property holds for all executions of length ≤ k" — not a full proof (I16); the bound is reported.
  • Iterative deepening: optionally increase k until a bug is found or a resource bound; report the smallest bug depth (P14; I16).

21.3 Deliverable

cli bmc --bound k file.vfy finds bugs reachable within k steps with concrete traces, or reports "safe up to k".

21.4 Acceptance Criteria

  • A program with a bug at depth d is Refuted by BMC at any k ≥ d with a concrete d-step trace; k < d reports "safe up to k" (I16 — honest, not a false proof).
  • The concrete trace is a real execution (re-checkable, like I11).
  • BMC unsat is never reported as an unconditional proof (I16 audit).
  • Differential: BMC bug-finding agrees with CBMC-style reference on shared bounded fixtures.

21.5 Conformance Fixtures

bmc/bug-at-depth-3, bmc/safe-up-to-k, bmc/concrete-trace, bmc/iterative-deepening, bmc/no-overclaim (unsat tagged with bound), bmc/vs-cbmc.

21.6 Pitfalls

  • Reporting BMC unsat as a full proof → false sense of total correctness (I16). Always tag with the bound.
  • Unrolling the cut loop instead of the real loop → BMC must use the original transition relation (it explores executions), not the invariant-cut form. Use the pre-passify CFG's transition relation.
  • State explosion at large k → solver blows up. Bound k; iterative deepening with a budget; report the depth reached.
  • Off-by-one in the unrolling (k steps vs k+1 states) → missed/extra-depth bugs. Define + test the step/state correspondence precisely.
  • Trace not a real execution → same spuriousness risk as I11; re-check.

21.7 Performance Concerns

BMC formula size grows linearly with k (and with state size); the solver dominates. Incremental SMT across deepening (push one more Trans) reuses learned clauses (P10). Bit-vector state is costly — same trade as Phase 5 (§17.7 Performance Concerns). Iterative deepening trades latency-to-first-bug for completeness-within-bound.

21.8 Edge Cases

A loop-free program (BMC is complete — bounded = full); an unbounded loop with a shallow bug (found at small k); a bug only at large depth (may exceed budget → "safe up to k" with k = budget); a property that's vacuously true (no reachable violating state at any k); nondeterministic input (havoc) at each step (BMC explores all via the solver).

21.9 Failure Analysis

BMC's failure mode is over-claiming (reporting bounded-safe as proven-safe) — a soundness-of-the-claim bug, mitigated by always reporting the bound (I16). A bug-trace that isn't a real execution is a usability bug (re-check, like I11). Detection: the no-overclaim audit + trace re-check + differential vs CBMC. BMC is complementary to deductive verification: fast bug-finding, no infinite-state proof — positioned explicitly against #279's finite-state model checking.

21.10 Operational Notes

Stats: bmc_bound, bmc_bugs_found, bmc_depth_to_bug, bmc_solver_seconds. --bound k, --deepen (iterative), --bmc-budget. BMC + the deductive engine + k-induction are three CLI subcommands over one IR; documenting when to use which (BMC: find bugs fast; deductive: prove with annotations; k-induction: prove without annotations when inductive) is a key user-facing operational note.

22. Phase 10 — k-Induction

22.1 Objectives

Prove safety without a manually supplied invariant (strength permitting) via k-induction: the base case (no violation in the first k steps — a BMC query) plus the inductive step (if the property held for k consecutive states, it holds at the next). Both unsat ⟹ proof for all reachable states (I17).

22.2 Detailed Implementation Steps

  • kind/kinduct.rs: reuse bmc/transys.rs for (Init, Trans, Prop) (Sheeran-Singh-Stålmarck FMCAD 2000; ADR-20).
  • Base case: Init ∧ ⋀_{i<k} Trans_i ∧ (⋁_{i≤k} ¬Prop_i) — unsat means no violation in the first k steps (a BMC query of depth k) (I17; ADR-19).
  • Inductive step: (⋀_{i<k} Prop_i) ∧ (⋀_{i<k} Trans_i) ∧ ¬Prop_k over arbitrary (not-necessarily-initial) states — unsat means: whenever the property held for k consecutive steps, it holds at the (k+1)-th (I17; ADR-20).
  • Both unsat ⟹ Verified (I17 — both required; the step alone is unsound, the base alone is just BMC).
  • Strengthening: add unique-states constraints (the k states in the step are distinct) to make more properties k-inductive (the standard k-induction strengthening); increase k if the step fails (a larger window may be inductive) (Sheeran-Singh-Stålmarck FMCAD 2000; P2).
  • On step failure at all tried k: report Unknown (the property may be true but not k-inductive for the tried k — needs an auxiliary invariant from absint, Phase 11) or a base-case Refuted (a real bug).

22.3 Deliverable

cli kinduct --k k file.vfy proves k-inductive safety properties without invariant annotations, or reports a real bug (base case) or Unknown (not k-inductive for tried k).

22.4 Acceptance Criteria

  • A k-inductive property is Verified (both base + step unsat, I17).
  • A property true-but-not-k-inductive (for small k) is Unknown, not falsely Verified (the step-only trap is avoided, I17).
  • A real bug is Refuted via the base case with a concrete trace.
  • Unique-states strengthening makes a known-not-1-inductive-but-2-inductive property verify at k=2.
  • Differential vs a k-induction reference on shared fixtures.

22.5 Conformance Fixtures

kind/1-inductive, kind/2-inductive-unique-states, kind/not-inductive-unknown, kind/base-case-bug, kind/step-only-unsound (must NOT verify on step alone), kind/vs-reference.

22.6 Pitfalls

  • Reporting Verified on the inductive step alone → unsound (the step says "stays safe if safe", not "is reachable-safe"); the base case is mandatory (I17). The two-obligation gate enforces this.
  • Forgetting unique-states strengthening → many true properties report Unknown at small k (incompleteness). Add the distinctness constraints.
  • Increasing k unboundedly → the step never converges on a non-k-inductive property → hang. Bound k; report Unknown.
  • Using the invariant-cut CFG → k-induction needs the raw transition relation (it reasons over arbitrary states), not the deductive cut. Use transys.
  • Confusing k-induction with the deductive loop rule → they are different proof methods over the same IR; k-induction needs no user invariant but is weaker (only k-inductive properties).

22.7 Performance Concerns

Two solver queries (base + step) per k; the step over arbitrary states is often the harder one. Incremental across increasing k. Unique-states constraints add O(k²) distinctness literals — bounded by small k. The trade vs deductive verification: k-induction needs no annotation effort but proves fewer properties.

22.8 Edge Cases

A 0-inductive (always-true) property (trivial); a property inductive only with an auxiliary invariant (k-induction Unknown → feed an absint invariant, Phase 11, then retry — the CEGAR-like loop); a property with a deep base-case bug (base Refuted at the bug depth); a transition system with input nondeterminism (the step quantifies over it); mutually-dependent safety properties (conjoin into one Prop).

22.9 Failure Analysis

k-induction's signature failure is the step-only-unsound trap — concluding from the inductive step without the base case, which "proves" properties of unreachable states. Detection: the step-only-unsound fixture must NOT verify; the two-obligation gate (I17). A non-convergent step (unbounded k) is a liveness bug — bound k. k-induction complements the deductive engine (no annotations, weaker) and BMC (proves, not just bounded) — the three-engine story.

22.10 Operational Notes

Stats: kind_k, kind_base_unsat, kind_step_unsat, kind_unique_states, kind_unknown. --k k, --max-k, --unique-states. When k-induction returns Unknown, the operational guidance is: supply an annotation (deductive engine) or an inferred invariant (absint) — documented in the runbook tying the three engines together.

23. Phase 11 — Abstract Interpretation, Invariant Inference, Incrementality, CLI

23.1 Objectives

Infer loop invariants automatically (so under-annotated loops verify), via an abstract-interpretation framework (lattice + monotone transfer + widening/narrowing, I12/I13) and Houdini (greatest-fixpoint candidate pruning); make verification incremental (re-verify only changed procedures, P10); finish the cli surface. Inferred invariants feed lower (Phase 2) to strengthen the deductive engine.

23.2 Detailed Implementation Steps

  • absint/lattice.rs: the Lattice trait (§11) + the Interval domain ([lo, hi] with ±∞); join/meet/widen/narrow. Structured to add octagons/polyhedra later (Cousot & Cousot POPL 1977; ADR-21).
  • absint/transfer.rs: monotone transfer functions per guarded command (assume/assert filter; assign evaluates the expression in the abstract domain; havoc → top). Monotonicity is property-tested (I12 — a non-monotone transfer can under-approximate → unsound inferred invariant) (I12; Cousot & Cousot POPL 1977).
  • absint/fixpoint.rs: a worklist iterator over the CFG computing the least fixpoint, applying widening at loop heads to force termination (finite ascending chains, I13), then narrowing to recover precision. Bound iterations as a backstop (I13; Nielson-Nielson-Hankin).
  • absint/houdini.rs: Houdini — start with a large set of candidate invariants (e.g. from templates / the user), iteratively remove any candidate not preserved by the loop (greatest fixpoint), until the surviving set is inductive; the survivors are sound invariants (Flanagan & Leino FME 2001; ADR-22).
  • Feed-back: inferred invariants are injected into the loop cut (Phase 2) as additional assume/assert invariants, then the deductive engine retries — turning an Unknown (under-annotated loop) into a Verified. Soundness preserved: an inferred invariant is checked by the deductive engine like any user invariant (the AI result is a hint, the deductive engine is the judge).
  • Incrementality (cli): dependency-track per-procedure VC inputs (its body + its callees' contracts); on an edit, re-verify only procedures whose inputs changed (a hash of the VC inputs). Cache verdicts keyed by the VC hash.
  • cli/main.rs: finalize verify/bmc/kinduct/infer subcommands, --dump-* flags, --report json, stats.

23.3 Deliverable

cli infer file.vfy prints inferred loop invariants; cli verify uses them to verify under-annotated loops; an edit re-verifies only affected procedures (incremental).

23.4 Acceptance Criteria

  • The interval analysis infers correct ranges (e.g. 0 ≤ i ≤ n for a counting loop) — sound over-approximations (validated by the deductive engine accepting them).
  • Widening terminates on every loop (I13 iteration-count bound never exceeded); narrowing improves precision measurably.
  • All transfer functions pass the monotonicity property test (I12).
  • Houdini converges to an inductive subset.
  • An under-annotated loop that was Unknown becomes Verified after inference (and the inferred invariant is itself checked, not trusted).
  • Incremental: editing one procedure re-verifies O(affected), not O(program) (timing test).

23.5 Conformance Fixtures

absint/interval-counting-loop, absint/widening-terminates, absint/narrowing-precision, absint/transfer-monotone, absint/houdini-converges, absint/inferred-then-verified, incr/edit-one-procedure, incr/verdict-cache.

23.6 Pitfalls

  • Non-monotone transfer function → the fixpoint under-approximates → an unsound "invariant" → a false Verified if trusted (I12). Mitigation 1: property-test monotonicity. Mitigation 2 (defense in depth): the deductive engine re-checks every inferred invariant, so even a buggy AI can't cause unsoundness — it can only cause Unknown.
  • Widening never applied → infinite ascending chain → fixpoint non-termination (I13). Apply widening at every loop head; bound iterations.
  • Over-aggressive widening → invariant too weak to verify the loop (Unknown). Use a widening-with-thresholds + narrowing to recover.
  • Incremental staleness (a callee's contract changed but the caller not re-verified) → wrong cached verdict. The VC-input hash must include callee contracts (dependency completeness).
  • Trusting the AI result directly → couples soundness to the AI's correctness. Always re-check inferred invariants via the deductive engine (the AI is a hint generator, not an oracle).

23.7 Performance Concerns

AI is fast (per-procedure fixpoint over a small lattice) relative to solving; widening keeps it bounded. The big win is incrementality — interactive verification re-checks one procedure, not thousands of VCs. The verdict cache (keyed by VC-input hash) makes re-runs near-instant for unchanged code. Houdini's cost is O(candidates × loop-iterations) — bound the candidate set.

23.8 Edge Cases

A loop with no inferable interval invariant (AI returns top → no help → deductive Unknown, prompting a user annotation); nested loops (AI infers per-loop, composed); a loop whose invariant needs a relational domain (intervals insufficient → Unknown, octagons deferred); an edit that changes only a comment (VC-input hash unchanged → cached verdict reused); a contract change rippling to many callers (re-verify all affected).

23.9 Failure Analysis

An AI soundness bug (non-monotone transfer, widening that under-approximates) would be catastrophic if the inferred invariant were trusted — but the architecture's defense in depth (the deductive engine re-checks every inferred invariant) means a buggy AI degrades to Unknown, never to a false Verified (I12 + the re-check). An incremental-staleness bug gives a wrong cached verdict — detected by periodically full-verifying in CI and comparing to incremental. Deferred: IC3/PDR + interpolation invariant inference (PhaseDeferred("Deferred Features Register")), dependent/refinement specs (PhaseDeferred("Deferred Features Register")), real source front ends (PhaseDeferred("Deferred Features Register")). Recovery: invalidate the cache; the monotonicity test + re-check are the safety nets.

23.10 Operational Notes

Stats: invariants_inferred, ai_iterations, widenings, narrowings, houdini_rounds, incr_procedures_reverified, verdict_cache_hits. cli infer, --domain interval, --no-infer, --incremental. The AI-as-hint / deductive-engine-as-judge split is the key operational principle — documented prominently so users understand inferred invariants are checked, not trusted.

Operational Readiness

A verifier's "operations" are observability of the pipeline, resource governance, reproducibility, and — uniquely — soundness assurance (it is a developer tool / library, not a service).

  • Metrics/stats. Per-pass counters: parse/typeck/lower/passify/vcgen/encode timings; VCs checked / verified / refuted / unknown (by reason); per-VC solver time (p50/p95/p99); inferred invariants; incremental cache hits. JSON dump (--report json). The headline metric is false_verified_total (must be 0).
  • Tracing. tracing spans per pass + per VC + per solver call; level-gated. A --trace-vc N dumps the full pipeline (AST→VIR→passive→VC→SMT→result) for one obligation.
  • Logging. Structured, leveled; the solver request/response is logged at debug; verdicts + reasons at info. Always log solver name + version (reproducibility).
  • "Dashboards". A per-procedure verdict table; for large programs, a progress line (procedures done, VCs/s, current Unknown count). The conformance + soundness pass rates are the project's health board.
  • Resource governance. --timeout (per VC), --mem-limit (global + per solver process), --max-k, AI iteration bound → all map to deterministic Unknown (I15), never crash or false verdict (P14).
  • Reproducibility. Pinned solver version (recorded in output), fixed encoding order (I7), --seed. A bug report = source + spec + flags + solver version reproduces exactly.
  • Soundness assurance (the unique operational concern). The conformance/soundness/ corpus runs on every build (the tripwire); dual-solver cross-check on that corpus; --dump-smt lets any verdict be independently re-checked by a standalone solver. This is the "is the verifier itself correct?" operational loop.
  • Incident response. Runbooks: false-verified.md (tripwire fired → bisect pass → dumped VC/SMT → dual-solver → regress), hang-matching-loop.md (trigger analysis, budget), oom.md (VC/BV size, budgets), spurious-cex.md (re-check, reconstruction), frame-hole.md (modifies conformance).
  • Debugging toolkit. --dump-ast/-vir/-passive/-vc/-smt (every IR inspectable), tools/ddmin (minimize a program+spec to a minimal repro), tools/smt-replay (re-run a dumped script), --trace-vc.
  • Backup/restore. N/A (stateless); the artifact to keep is the minimized repro added to conformance/.
  • Deployment/upgrade. Library SemVer; the source/spec language + the SMT-LIB encoding + the verdict triplet are the stable contracts; new theories/engines/domains are additive.

Compatibility & Versioning

  • Input language: the source + spec language (§8.1 EBNF) is versioned; new constructs are additive; a removed/changed construct is a major-version break with a migration note. Unsupported constructs → a clear error, never a silent wrong verdict.
  • Verdict contract: the Verified / Refuted(counterexample) / Unknown(reason) triplet is stable; the meaning of Verified (the soundness guarantee + the TCB) is documented + frozen.
  • SMT encoding: the VC→SMT-LIB2 encoding is deterministic + inspectable (--dump-smt); the encoding may evolve (more efficient, more complete) but never in a way that turns a prior Refuted into a Verified without a soundness review. SMT-LIB 2.6 is the solver contract.
  • Counterexample/witness format: the machine witness (SV-COMP-style) is versioned; the human format may change freely.
  • API (libverify): SemVer; the Verifier/SmtBackend/Lattice/Transfer traits are the stable contract; additive trait methods via defaults; new abstract domains + theories plug in without core changes (P12).
  • Solver compatibility: Z3 + CVC5 over SMT-LIB2 are supported backends; the embedded core is an additive alternative; a solver version is recorded per run (a verdict is only reproducible against the same solver version, documented).
  • Determinism: for a fixed language version + solver version + seed, verdicts + counterexamples + reports are byte-reproducible across runs + platforms.
  • Deprecation: language constructs / flags deprecated with one-minor warning before removal.

Testing & Verification Strategy

  • Unit: hash-consing identity, sort checking, the loop/call lowering rules, DSA single-definition, WP transformer per command, SMT emission, model parsing (Z3 + CVC5), interval transfer functions, widening.
  • Soundness corpus (the highest-value tests): conformance/soundness/ — a growing set of known-buggy programs (off-by-one, missing bound, false postcondition, under-framed call, overflow assumed away) that must all be Refuted; the CI tripwire fails the build on any false Verified (I1). Every soundness bug ever found becomes a permanent member.
  • Differential: the backbone — verdicts vs Dafny / Why3 on shared programs (allowing Unknown differences from solver strength); WP vs SP VC validity (ADR-06); dual-solver (Z3 vs CVC5) agreement on the dumped SMT; BMC vs CBMC on bounded fixtures; k-induction vs a reference.
  • Property: Verified ⟹ no counterexample exists (sampled by attempting refutation); inferred invariants are sound over-approximations (the deductive engine accepts them); transfer functions are monotone (I12); widening terminates (I13); passive form is acyclic + single-def (I4/I5); the VC is deterministic (I7).
  • Counterexample property: every Refuted's model satisfies ¬VC and survives the spuriousness re-check (I11); every obligation kind renders correctly.
  • Fuzzing: cargo-fuzz on the parser (no panic/UB); structured-program fuzzing — generate random annotated programs, verify, and check the verdict against a reference / against re-running the dumped SMT externally (soundness fuzzing — the most valuable kind for a verifier).
  • Conformance: SV-COMP-style categories (reach-safety, no-overflow, termination) + a curated corpus → conformance.report.json.
  • Regression: every minimized bug becomes a fixture (soundness bugs into soundness/, others into the relevant directory).
  • Soak: verify a large multi-procedure program under budgets; assert no crash, no false Verified, bounded memory, terminating.
  • Performance regression: criterion microbenchmarks (VCGen throughput, encode time) + per-procedure solver-time tracking in CI; >10% regression fails.
  • Determinism test: same input + solver version + seed twice → identical verdict, counterexample, and SMT text (I7).

Performance Engineering

  • Benchmarking: VCGen throughput (VC nodes/s), encode time (SMT terms/s), per-VC + per-procedure solver time (the dominant cost), end-to-end on the conformance corpus (criterion + suite timing).
  • Profiling: perf/flamegraph on VCGen (term-DAG construction) + encode + the solver round-trip; identify whether time is in the verifier (rare) or the solver (usual).
  • Allocator analysis: hash-consed term arena; avoid per-term heap allocation; measure peak RSS vs program size + VC size; the SMT process RSS is bounded + monitored.
  • VC-size analysis (the highest-leverage lever): the compacted VC is linear (I6) — track vc_nodes_per_program_node; a regression to super-linear is a perf cliff caught by the guard. Smaller VCs ⟹ faster solving.
  • Quantifier/trigger analysis: quantified VCs dominate solver time; track instantiation counts (if the solver reports them); tighter triggers ⟹ fewer instantiations ⟹ faster (and matching-loop-free, I10).
  • Theory-cost analysis: bitvector reasoning ≫ LIA; prefer int over bv where source semantics allow (a modeling decision with a perf consequence, P7).
  • Incremental analysis: the per-procedure verdict cache + dependency-tracked re-verification is the dominant real-world perf win (interactive use re-checks one procedure).
  • Branch/cache: the term-DAG traversal in VCGen/encode should be cache-friendly (contiguous arena, index references); not the bottleneck (the solver is).
  • Targets: §4 — linear VC size, deterministic per-VC budget, faithful (exact) arithmetic.

Scalability Analysis

  • Bottleneck #1 the SMT solver: dominates end-to-end time; scales with VC size + quantifier count + theory (BV worst). Mitigations: linear compacted VCs (I6), tight triggers (I10), prefer LIA over BV (P7), incremental discharge (P10), per-procedure parallelism (deferred).
  • Bottleneck #2 quantifier instantiation: the practical scaling wall — many quantified axioms (arrays, recursive functions, user forall) explode instantiation. Mitigation: minimal, tightly-triggered axioms; matching-loop avoidance; Unknown over hang.
  • Bottleneck #3 bitvector reasoning: machine-int-heavy code (esp. multiply/non-linear) blows up the solver. Mitigation: model as int where semantically valid; bound BV width; word-level reasoning (deferred).
  • Bottleneck #4 VC size: non-linear VC (a compaction regression) makes any non-trivial program time out. Mitigation: the block-equation form + the size guard (I6).
  • Bottleneck #5 large programs (many procedures): total time = Σ procedures. Mitigation: per-procedure independence ⟹ parallelize (deferred); incremental re-verification keeps interactive cost O(edit).
  • Memory scaling: dominated by the term-DAG (hash-consed, shared) + the SMT process; both bounded by budgets. Large quantified VCs are the memory risk.
  • Incremental scaling (the practical axis): real use edits one procedure and re-verifies; the verdict cache + dependency tracking make interactive verification O(affected), the difference between a usable IDE-integrated verifier and an unusable batch tool.
  • Engine choice as a scaling lever: BMC scales to find shallow bugs fast (bounded); k-induction proves without annotation effort (when k-inductive); the deductive engine proves arbitrary properties (with annotation effort). Choosing the cheapest engine that answers the question is itself a scaling strategy.

Mental Models & First Principles

  1. MM1 — Passivity is the prerequisite for linear-size WP. Predicts: whether your WP implementation is O(n) or O(2^n) in program size. Without it: naive WP applied to assignments duplicates the postcondition across every branch → exponential term blowup → the solver times out on any non-trivial program, and you blame the solver instead of VCGen. Applied: §8.2 (WP table over passive commands), Phase 3 (passification), Phase 4 (block-equation compaction, ADR-07, I6).

  2. MM2 — A loop cut replaces infinite iteration with one universally-quantified iteration. Predicts: which programs require a user invariant and which can be handled by k-induction or bounded unrolling. Without it: you unroll the loop (BMC style) and can only verify up to the unroll bound — the deductive engine's infinite-state strength disappears. Applied: §8.3 (loop cut), Phase 2 (lower/loops.rs), Phase 9 (BMC deliberately does NOT use the cut), Phase 10 (k-induction also uses the raw transition relation).

  3. MM3 — Modular verification: the call rule is an assume/assert sandwich. Predicts: whether a verifier scales to large programs. Without it: you inline callee bodies at every call site — coupling caller proofs to callee implementations, destroying scalability, and turning any edit into a full re-proof. The sandwich (assert Pre; havoc Modifies; assume Post) is the single idea that makes deductive verification compositional. Applied: §8.3 (call translation), Phase 2 (lower/calls.rs), Phase 7 (modifies conformance, I14, P3/P4).

  4. MM4 — Frame soundness: under-havocking is a silent soundness bug. Predicts: whether a modifies bug produces a false Verified (under-havoc) or spurious Unknown/Refuted (over-havoc). Without it: a callee that modifies x but declares it doesn't allows the caller to wrongly assume x unchanged — a false Verified that is invisible until a real execution contradicts the proof. Applied: Phase 2 (lower/calls.rs, I14), Phase 7 (modifies-conformance VC), §6 P4, Consolidated Pitfall #2.

  5. MM5 — DSA versioning: each variable occurrence becomes a unique SMT constant. Predicts: whether the SMT encoding is correct and whether counterexample reconstruction succeeds. Without it: two occurrences of x in a passified formula collapse to one SMT constant — the solver conflates pre-state and post-state values, producing either a wrong VC or an uninterpretable model. Applied: Phase 3 (passify/dsa.rs, I4), Phase 8 (counterexample reconstruction via version map, I11).

  6. MM6 — Soundness = never false Verified; incompleteness = sometimes Unknown. Predicts: how to triage every verdict. Without it: engineers treat Unknown as a bug and add axioms or weaken triggers until the tool says Verified — destroying soundness to eliminate incompleteness. Applied: §4 (Soundness constraint, P1), §6 P1, Phase 6 (timeout → Unknown, I15), Phase 7 (soundness tripwire, M12).

  7. MM7 — E-matching triggers determine both completeness and termination of quantifier instantiation. Predicts: whether a quantified VC will hang (matching loop), time out (over-restrictive trigger misses a needed instance), or solve (tight, loop-free trigger). Without it: every quantified axiom (array axioms, recursive-function unfolding, user forall postconditions) becomes a probability bet. Applied: Phase 5 (encode/quant.rs, ADR-13, I10), §8.1 (trigger syntax), §8.7 (matching loop example), T3.

  8. MM8 — The trusted computing base is explicit, minimal, and documented. Predicts: what class of bugs can produce a false Verified without any detectable signal in the verifier itself. Without it: a solver soundness bug certifies incorrect programs and there is no fallback — the developer trusts a liar. Applied: §4 (TCB size constraint), §6 P5, Phase 6 (dual-solver cross-check, T4; Failure Analysis, proof-producing mode), Phase 5 (proof-mode deferred, ADR-18, Failure Analysis), Deferred Features Register (proof-producing certificates).

  9. MM9 — k-induction proves safety properties that are k-inductive; it needs the base case to exclude unreachable states. Predicts: when k-induction will return Verified vs Unknown, and why step-only is unsound. Without it: you accept an inductive-step unsat as a proof — but the step holds vacuously for unreachable states; the base case is what connects the induction to the actual initial state. Applied: Phase 10 (kinduct.rs, I17, ADR-20), Consolidated Pitfall #10.

  10. MM10 — Abstract interpretation infers sound over-approximations; the deductive engine re-checks every inferred invariant. Predicts: whether a non-monotone transfer function can cause a false Verified. Without it: you trust the inferred invariant directly — a buggy transfer function under-approximates, producing an invariant that doesn't actually hold, and the verifier certifies a false program. The defense-in-depth split (AI as hint, deductive engine as judge) means a buggy AI degrades to Unknown, not to false Verified. Applied: Phase 11 (absint/transfer.rs, I12/I13, ADR-21/22), §6 P11, Consolidated Pitfall #8.

Back-of-Envelope Capacity Model

From §4: Per-VC solver budget = 10 s wall; VC size = linear in program size; Memory ceiling = 4 GB; Startup ≤ 50 ms; Encoding faithfulness = machine ints wrap (BV), math ints unbounded (LIA); Incremental re-verification = O(changed) procedures.

  1. Maximum procedures before global budget is binding. Assumption: average procedure = 50 VC nodes; average VC = 5 VCs per procedure; each VC uses the full 10 s budget (worst case). Then 1 procedure = 5 × 10 s = 50 s. In a 1 h wall-clock run: 3600 s / 50 s = 72 procedures can be fully verified end-to-end. Design consequence: above ~50 procedures, parallelism per procedure (deferred) or incremental re-verification (Phase 11) is mandatory; purely sequential verification does not scale past a few hundred-procedure programs (§4 per-VC budget, Scalability Analysis).

  2. VC node count for a loop-body program. Source: 1 while with invariant I, body B (10 assignments + 1 conditional = 12 statements), calls one procedure. Lower rule (§8.3): 1 assert I + 1 havoc + 1 assume I + 2 assume/assert per branch + 1 modular-call expansion (3 guarded commands) + 1 assert post = ~20 guarded commands. Passification: each assignment → 1 assume, no change in count. WP block-equation: O(1) block predicate per block + O(guarded commands) = ~25 VC nodes. Design consequence: the compaction (ADR-07, I6) keeps this linear; naive WP on a binary-branch tree with depth d would yield 2^d duplications of the postcondition — for d=10 that is 1,024 copies of a 25-node formula = 25,600 nodes vs 25. The ratio guard enforces this (§4 VC size constraint).

  3. SMT variable count after DSA passification. Each havoc of k variables at a loop cut mints k fresh versions; a loop with a 10-variable modifies set at depth 3 (outer/inner/innermost) mints 3 × 10 = 30 fresh versions above the base. A 5-procedure program with average 10 versioned variables each → 50 SMT declare-const statements. Design consequence: DSA variable count is O(program size × loop nesting depth); at nesting depth > 5 with large modifies sets, the declare-const overhead is non-negligible but dwarfed by the formula size (§4 memory ceiling, ADR-08).

  4. Memory consumed by the term DAG (hash-consed). Assumption: a TermId is 4 bytes; an average term node (enum + 2 children) = 24 bytes. A 50-VC-node formula with 10× sharing (hash-consing typical) uses 50 unique nodes × 24 B = 1.2 KB per procedure. A 1,000-procedure program = 1.2 MB of VC term data. The 4 GB ceiling (§4 memory ceiling) ÷ 24 B/node ≈ 1.8 × 10^8 (180 M) unique nodes — orders of magnitude above any single-process program. Design consequence: the memory budget is dominated by the SMT child process RSS, not the term DAG (Scalability Analysis, Bottleneck #1; ADR-05).

  5. Quantifier instantiation budget per VC. From §4 (quantifier instantiation = bounded, matching-loop-free). Assumption: each triggered axiom fires at most k_inst = 100 instantiations before the solver's E-matching budget is exhausted. A VC with 5 quantified axioms (array select/store + 2 recursive functions + 1 user forall) can fire 5 × 100 = 500 instantiations, each adding ~10 SMT terms = 5,000 incremental terms. Each additional instantiation round at 10 μs = 5 ms per VC. Design consequence: matching-loop avoidance (I10, ADR-13) is not just a correctness property — an uncontrolled loop multiplies this 500-count by the number of ground terms, turning a 5 ms solve into a 10 s timeout. The matching-loop check and conservative triggers are the capacity gate (§17.6 pitfall #2, T3).

  6. Solver startup amortization. From §4 (startup ≤ 50 ms to first VC). Z3/CVC5 child process spawn = ~20–50 ms (platform-dependent). Amortized over N VCs of a procedure: 50 ms / N. For N = 10 (a typical procedure): 5 ms startup overhead per VC — under 1% of the 10 s budget. Design consequence: the startup constraint is met by amortizing the spawn across a procedure's VCs (Phase 6, ADR-15); spawning a fresh process per VC (naive) would add 50 ms × 5 VCs × 72 procedures ≈ 18 s overhead to a 72-procedure run — measurable but acceptable for small programs, unacceptable at scale.

  7. Bitvector solving cost vs LIA. Source: §4 encoding faithfulness (BV for machine ints). Empirically, BV multiply is ~10–100× more expensive than LIA for the same problem size. A 10-VC procedure where 3 VCs involve bv32 multiply at 10× overhead consumes 3 × 10 × (base time) + 7 × (base time). If base LIA solve = 0.1 s, total = 0.3 × 10 + 0.7 = 3.7 s — still within the 10 s budget per VC. Design consequence: a BV-heavy procedure (e.g., a cryptographic function with many bv32 multiplies) can exhaust the per-VC budget; the mitigation is to model with math int where overflow semantics are not load-bearing (P7, ADR-09, Scalability Analysis, Bottleneck #3).

  8. Incremental re-verification speedup. From §4 incremental re-verification = O(changed) procedures. A 100-procedure program where 1 procedure is edited: 1/100 × full-program time. For full-program time = 5,000 s (72 procedures × 70 s each): incremental cost = 50 s (1 procedure). Design consequence: the verdict cache keyed by VC-input hash (Phase 11, ADR-24) turns an interactive edit cycle from minutes to under a minute — the difference between a usable IDE-integrated verifier and an unusable batch tool (Scalability Analysis, Bottleneck #5, P10).

  9. Houdini candidate pruning iterations. Assumption: 50 candidate invariants, loop with 20 iterations before convergence. Each Houdini round: run the deductive engine on the candidate set, prune those not preserved. Phase 11 note: Houdini's cost = O(candidates × rounds) ≈ O(50 × 20) = 1,000 solver calls at 0.1 s each = 100 s for a single loop. Design consequence: the candidate set must be bounded (ADR-22); a quadratic explosion in candidates (e.g., all pairwise predicates over 20 variables = 190 candidates) multiplies this to 19,000 calls = 1,900 s — infeasible. Houdini is practical with ~20–50 focused candidates; wider inference falls back to IC3/PDR (deferred, see Deferred Features Register).

  10. Counterexample reconstruction latency. From M7 (Performance Engineering; ≤ 50 ms per refutation), grounded by §4 (counterexample fidelity — every Refuted ships a concrete model). DSA-reverse: O(|model variables|) = O(DSA versions per procedure) ≈ O(50) for a 10-variable procedure with 5 versions each. At 1 μs per lookup: ~50 μs. Spuriousness re-check: re-evaluate one path = O(path length × guarded-command semantics) ≈ O(20 commands × 1 μs) = 20 μs. Total: ~70 μs << 50 ms bound. Design consequence: counterexample reconstruction is not a hot path (I11, Phase 8); the bound is easily met, and the spuriousness re-check (whose correctness is the key invariant) can be thorough.

Hard Questions (Self-Examination)

  1. The loop-cut rule (§8.3) asserts I on entry, havocs the modified variables, and then assumes I. If the havoc set under-approximates the actual modified set, which invariant is violated first — I4, I14, or I1 — and what is the exact execution that witnesses the false Verified? (§8.3, Phase 2, I14, I1, P4)

  2. The block-equation compacted VC (§8.4) introduces one fresh predicate per block. If two blocks share a successor and that successor's block predicate is referenced from both block equations, trace exactly how structural sharing prevents the exponential blowup — and explain why naive WP applied to a binary-branch tree of depth 10 produces 2^10 copies of the postcondition instead. (Phase 4, ADR-07, I6, MM1)

  3. ADR-14 locks in the external-solver-over-SMT-LIB2 design. Under what program/theorem class does this choice incur a measurable performance penalty compared to a native FFI binding, and does that penalty threaten any §4 constraint? (ADR-14, ADR-15, §4 per-VC solver budget, Phase 6, Scalability Analysis, Bottleneck #1)

  4. The WP of wp(havoc x, Q) is ∀x. Q — a universal quantifier. After passification, havoc x becomes a fresh unconstrained version. Explain precisely why these two formulations produce the same VC validity, and under what degenerate condition they could diverge. (§8.2, Phase 3, Phase 4, I4, ADR-08)

  5. A user supplies the trigger {f(x)} on the axiom forall x :: f(x) == g(x). The matching-loop check in Phase 5 should flag this — but the check as described in §8.7 looks at self-regeneration. Construct a two-axiom system with triggers {f(x)} and {g(x)} that produces a cross-axiom matching loop the single-axiom check misses. (Phase 5, ADR-13, I10, T3, MM7)

  6. k-induction (Phase 10) requires both the base case and the inductive step. Construct a concrete transition system where the inductive step is unsat (1-inductive) but the property is false — i.e., there exists a reachable initial state that violates the property — and identify exactly which of I16/I17 this tests. (Phase 10, I16, I17, ADR-20, MM9)

  7. The spuriousness re-check (Phase 8) re-evaluates the reconstructed model against the original program path. Identify a class of program/encoding (hint: quantified postconditions with an ∃ witness that the SMT model represents only partially) where the re-check may incorrectly classify a genuine counterexample as spurious, and explain the recovery path. (Phase 8, I11, Phase 5, ADR-13)

  8. Inferred invariants from the interval domain (Phase 11) are re-checked by the deductive engine. Now suppose the transfer function for assume(x == y + 1) is non-monotone — it sometimes returns a value below the true abstract semantics. Trace the worst-case consequence through I12, the re-check, and the final verdict. Does the architecture prevent false Verified? (Phase 11, I12, P11, MM10, ADR-21)

  9. §4 states VCGen determinism is bit-identical VC for identical input. The hash-cons table uses a hasher with a fixed salt (I7). Suppose two procedures' term DAGs have the same structural shape but different variable names — their TermIds differ but their VCs have the same structure. Explain why this is not a determinism violation, and then construct a hash-collision scenario that would be. (Phase 0, Phase 4, ADR-24, I7, ADR-05)

  10. The SMT encoding emits (assert (not VC)) (check-sat). If the VC contains a division expression a / b and the div_nonzero obligation was correctly emitted in Phase 2 but the encoding of division in Phase 5 uses the SMT div function (total, defined at zero) without conditioning, is the result sound? Construct a counterexample or prove soundness. (Phase 2, Phase 5, ADR-09, I1, §8.7 division-by-zero example)

  11. ADR-22 defers IC3/PDR; the current invariant inference chain is intervals → Houdini. Identify a class of programs (beyond the §4 constraint "nonlinear arithmetic incompleteness") where Houdini converges to an empty candidate set and the deductive engine returns Unknown, and explain what IC3/PDR would do differently at that class boundary. (Phase 11, ADR-22, Deferred Features Register, MM10, P1)

  12. The modifies-conformance VC (Phase 7) checks that a method's actual assignments ⊆ declared modifies. This is a VC, not a static check. Explain what program pattern would make this VC require quantification over heap locations, and why the current simple modifies-set model (ADR-11) is sufficient for the non-heap case but insufficient for the deferred separation-logic case. (Phase 7, ADR-11, I14, P4, Deferred Features Register)

  13. Phase 8's counterexample reconstruction maps SMT model values through the DSA version map to source spans. Consider a loop whose body contains an assignment m := i conditionally (as in MaxIndex §8.1). After 3 iterations, the model has m_7 = 2, i_7 = 3. Trace the DSA-reverse to identify what source statement each version corresponds to, and explain what old(m) would mean in this context. (Phase 3, Phase 8, §8.1, §8.6, I18, ADR-17)

  14. The three engines (deductive, BMC, k-induction) share the same VIR but use it differently: the deductive engine uses the invariant-cut CFG, BMC uses the original transition relation, and k-induction also uses the raw transition. Explain why k-induction using the invariant-cut CFG would be unsound (not merely incomplete), and then explain why BMC using the cut CFG would be both unsound and produce wrong counterexamples. (Phase 9, Phase 10, Phase 11, ADR-19, ADR-20, I17, MM2)

  15. The soundness tripwire (I1, Phase 7) runs conformance/soundness/ known-buggy programs and fails the build if any is Verified. Suppose a build introduces a regression in Phase 3 (a bad DSA merge that conflates pre- and post-loop versions) that makes the passified CFG semantically wrong for programs with at least 2 loop iterations. (Phase 3, Phase 7, I1, I4, I5, ADR-08, MM5)

  16. The per-VC time budget (§4: default 10 s) maps to Unknown on expiry. Consider a procedure with 100 VCs where 80 are instantaneously unsat (trivial) and 20 each require 9 s. With incremental push/pop reuse, the solver retains learned lemmas across the 80 trivial VCs before hitting the 20 hard ones. Estimate how much incremental context reduces the 9 s solve time for the hard VCs, and identify which §4 constraint and which ADR governs this trade-off. (Phase 6, §4 per-VC solver budget, ADR-14, ADR-15, P10, Scalability Analysis, Bottleneck #1)

  17. The old(e) capture (Phase 2, I18) captures e at procedure entry. Consider a recursive procedure where the recursive call is the last statement. The old(e) in the postcondition should refer to the entry-state of the top-level invocation, not the recursive call's entry. Explain how the modular call rule (assert pre; havoc M; assume post) interacts with old semantics across recursive call sites, and identify whether this is handled correctly or deferred. (Phase 2, §8.3, I18, ADR-04, Phase 7)

  18. Widening (▽) applied at loop heads forces termination but can lose precision. The narrowing (△) phase is supposed to recover it. Construct a two-variable loop (e.g., x := x + 1; y := x * 2) where widening over the interval domain loses the relational invariant y == 2*x, and explain why narrowing cannot recover it (a fundamental limit of the interval domain).   19. The --dump-smt flag (Phase 5) lets a standalone Z3/CVC5 re-check any verdict. Suppose the re-check with Z3 agrees with the verifier (unsat) but the re-check with CVC5 returns unknown (not sat).   20. The Verified verdict is defined as "every VC is unsat within budget." A procedure with 5 VCs where 4 are unsat and 1 is Unknown(Timeout) returns Unknown, not Verified. Explain why this is the correct and sound behavior with reference to P1 and I15, and identify the one scenario where a legitimate user might argue this is too conservative (and how the response documents that position). (§6 P1, I15, Phase 7, §4 per-VC solver budget, MM6)

  21. The block-equation VC for a procedure with a deeply nested conditional (depth 5, 2^5 = 32 paths) has how many block predicates and how many block equations? (Phase 4, §4 memory ceiling, ADR-07, I6, MM1, M2)

Alternative Architectures (Roads Not Taken)

Alt-A: Interactive Proof Assistant (Full Expressiveness, Manual Proofs)

Show the original text diagram
   Source (any language) ──► Proof Assistant kernel
         ▲                        │
         │  tactic scripts        │ type-checked proof terms
         │  (human / automation)  ▼
   User  ──────────────────► Verified certificates
                                  │
                             (small trusted kernel)

Wins when: the program or the mathematical property cannot be expressed in first-order logic; the trusted computing base must be a single, independently verified kernel (a few kLOC); proof certificates must be re-checkable decades later; or completeness is more valuable than automation (hardware / OS / compiler correctness, seL4 Klein et al. SOSP 2009, CompCert Leroy 2009).

Embodied by: Coq, Isabelle/HOL — the seL4 microkernel and CompCert C compiler both use Isabelle/Coq respectively to produce machine-checked proofs.

Why rejected here: the target is an automated, push-button verifier driven by first-order contracts and an SMT backend. Interactive proof assistant workflows require proof engineers writing tactic scripts — incompatible with the design goal of automatic discharge. The SMT solver does remain in the TCB (a deliberate, documented tradeoff; proof-producing mode is deferred to a future certificate checker that would narrow this gap).

Alt-B: Bounded Model Checking Only (Bug-Finding, No Invariants)

Show the original text diagram
   Source ──► CFG (no loop cut) ──► Unroll k times ──► SAT/SMT query
                                         │
                                    k-bounded trace
                                    (concrete bug or "safe ≤ k")

Wins when: the goal is fast bug-finding (test amplification), not proof; the program lacks annotations; shallow bugs at depth ≤ k are the primary target; and the absence of loop invariants eliminates annotation overhead entirely. At hardware/embedded scale, tools like CBMC operate in exactly this regime.

Embodied by: CBMC (diffblue/cbmc) — a production BMC engine for C/C++ that makes no claim beyond the bound.

Why rejected here: BMC cannot prove properties for all executions of a program with unbounded loops — it reports "safe up to k" which is not a verification result. The design point of this project is modular, contract-based, infinite-state deductive proof; BMC is included as a complementary engine (Phase 9) precisely because it fills the fast-bug-finding niche, but it cannot be the primary engine.

Alt-C: Abstract-Interpretation-Only Sound Static Analysis (No Specs)

Show the original text diagram
   Source ──► CFG ──► Abstract fixpoint (lattice domain)
                              │
                    Sound over-approximation of
                    all reachable states ──► alarm / no-alarm
                    (no user specs required)

Wins when: the analysis must be fully automatic (no user annotations), the alarm rate must be soundly bounded, and the property is a fixed safety class (no null dereference, no array out-of-bounds, no integer overflow) — i.e., the spec is built-in, not user-supplied. Astree (Cousot et al.) soundly analyzed Airbus fly-by-wire control software (A340/A380) with zero false alarms in this regime (sound, so no missed errors either).

Embodied by: Astree (Cousot, Cousot, et al.) — the production abstract-interpretation tool for safety-critical embedded C, deployed at Airbus.

Why rejected here: the design goal requires user-specified functional correctness properties (requires/ensures) that go beyond fixed safety classes — e.g., "this sort is correct," "this cryptographic function satisfies this equation." Abstract interpretation without specs can only prove generic safety properties; it cannot prove application-specific postconditions. The absint engine (Phase 11) is included as an invariant-inference layer feeding the deductive engine, not as a standalone verifier.

Alt-D: Deductive VC-Gen Without Passification (Direct-Assignment WP)

Show the original text diagram
   Source ──► VIR (with assignments) ──► Direct WP over assigned CFG
                                               │
                                    VC with substitution chains
                                    (potentially exponential)

Wins when: programs are small (few branches), the exponential blowup never manifests in practice, and the simpler implementation (no SSA/DSA pass, no cutpoint logic) reduces engineering complexity. Research prototypes exploring new theories or encoding strategies sometimes start here.

Embodied by: early Dijkstra-style WP implementations (the original A Discipline of Programming formulation) and the differential sp variant kept in this project (ADR-06) for cross-checking.

Why rejected here: the block-equation compaction (Leino IPL 2005) is not an optimization — it is the correctness boundary for practical verification. Any non-trivial program with nested branches will produce an exponential VC (I6), causing solver timeouts that are misdiagnosed as incompleteness rather than an engineering failure. The compacted form is the design; the naive form is kept only for differential testing (ADR-06).

Domain Deep Dive — From a while Loop to unsat

The path from an annotated loop to a discharged VC is the soul of the verifier. Walk one all the way through.

D.1 The program and its obligations

method Sum(n: int) returns (s: int)
  requires n >= 0
  ensures  s == n * (n + 1) / 2
{
  s := 0;
  var i: int := 0;
  while (i < n)
    invariant 0 <= i <= n
    invariant s == i * (i + 1) / 2
    decreases n - i
  { i := i + 1; s := s + i; }
}

Four obligations arise (§8.5): inv_entry (after s:=0; i:=0: 0≤0≤n from n≥0, and 0 == 0*1/2); inv_pres (assuming the invariants ∧ i<n, after i:=i+1; s:=s+i: 0≤i+1≤n and s+i+1 == (i+1)(i+2)/2); decreases (0 ≤ n−i and n−(i+1) < n−i); post (on exit i≥n ∧ invariants ⟹ i=n ∧ s == n(n+1)/2).

D.2 Lowering — the cut (Phase 2)

Sum's loop lowers to (mods = {i, s}):

assume n >= 0 ;                       # precondition
s := 0 ; i := 0 ;
assert 0 <= i <= n ;                  # inv_entry
assert s == i*(i+1)/2 ;               # inv_entry
havoc i, s ;                          # forget loop-modified vars
assume 0 <= i <= n ;                  # arbitrary iteration: assume invariants
assume s == i*(i+1)/2 ;
( assume i < n ;                       #   enter body
  assert 0 <= n - i ;                  #   decreases bounded
  i := i + 1 ; s := s + i ;            #   body
  assert 0 <= i <= n ;                 #   inv_pres
  assert s == i*(i+1)/2 ;              #   inv_pres
  assert (n - i) < (n - i_old) ;       #   decreases strict (i_old captured)
  assume false                         #   verification-only path
  □
  assume i >= n ) ;                    #   exit
assert s == n*(n+1)/2 ;               # post

The loop body is verified once against the invariant — never unrolled. That single havoc + assume invariant is what makes verification infinite-state (it covers all iterations) where BMC would unroll.

D.3 Passification (Phase 3)

DSA-number the versions and turn assignments into assumptions:

assume n >= 0 ;
assume s_1 == 0 ; assume i_1 == 0 ;
assert 0 <= i_1 <= n ; assert s_1 == i_1*(i_1+1)/2 ;     # inv_entry on versions 1
 # havoc i,s ⟿ fresh i_2, s_2 (unconstrained)
assume 0 <= i_2 <= n ; assume s_2 == i_2*(i_2+1)/2 ;     # inv assumed on versions 2
( assume i_2 < n ;
  assert 0 <= n - i_2 ;
  assume i_3 == i_2 + 1 ; assume s_3 == s_2 + i_3 ;        # body, versions 3
  assert 0 <= i_3 <= n ; assert s_3 == i_3*(i_3+1)/2 ;     # inv_pres
  assert (n - i_3) < (n - i_2) ;
  ... )

Now there are no assignments and no cycle (the back-edge is gone — the havoc+assume replaced it). Every version is defined once (I4); the CFG is a DAG (I5).

D.4 WP and the VC (Phase 4)

WP propagates the post backward through the passive commands. The inv_pres obligation, in isolation, becomes the implication:

(0 <= i_2 <= n)  ∧  (s_2 == i_2*(i_2+1)/2)  ∧  (i_2 < n)
   ∧  (i_3 == i_2 + 1)  ∧  (s_3 == s_2 + i_3)
   ⟹  (0 <= i_3 <= n)  ∧  (s_3 == i_3*(i_3+1)/2)

The arithmetic heart: s_3 = s_2 + i_3 = i_2(i_2+1)/2 + (i_2+1) = (i_2+1)(i_2+2)/2 = i_3(i_3+1)/2. ✓ The block-equation compaction (I6) shares this across the CFG so the full VC stays linear even with many branches.

D.5 Encoding + discharge (Phases 5–6)

int → LIA (math integers, unbounded — no overflow). The VC is closed (the forall invariant in MaxIndex-style examples would carry its {a[j]} trigger; Sum is quantifier-free over LIA, so it's decidable and fast). Emit (assert (not VC)) (check-sat); Z3 returns unsat ⟹ the obligation is valid ⟹ this VC is Verified. All four obligations unsat ⟹ Sum is Verified.

D.6 What a bug looks like

Change the body to s := s + i before i := i + 1 (a classic off-by-one). Now s_3 == s_2 + i_2 (old i), and inv_pres s_3 == i_3(i_3+1)/2 becomes i_2(i_2+1)/2 + i_2 == (i_2+1)(i_2+2)/2, i.e. i_2 == i_2 + 1 — false. Z3 returns sat, e.g. n=2, i_2=1, s_2=1 → after s:=s+i; i:=i+1: s_3=2, i_3=2, but 2 == 2*3/2 = 3 is false. cex reports: "loop invariant s == i*(i+1)/2 not preserved (kind inv_pres) at line N; model n=2, entering iteration with i=1, s=1; after the body i=2, s=2, but the invariant requires s=3." The off-by-one is pinpointed. This is the verifier doing its job: refusing the buggy program with an actionable trace.

D.7 Where every silent-wrong bug hides

Every false-Verified bug in this project lives in one of four places: (1) a WP transformer rule (Phase 4) that proves a false VC valid; (2) an encoding (Phase 5) that mismodels semantics (machine-vs-math int, I9; a wrong array axiom); (3) a frame/modifies hole (Phase 2/7, I14) letting a call assume too much; (4) a trusted solver bug (T4, mitigated by dual-solver + proof mode, Deferred Features Register). The soundness corpus (I1) + the modifies-conformance VC (I14) + dual-solver + --dump-smt external re-check target exactly these four. Master this deep dive and you can debug — and trust — any deductive verifier.

D.8 The three engines on one program

For Sum: the deductive engine proves the functional postcondition s == n(n+1)/2 given the invariant (infinite-state, needs annotation). BMC at k=10 would find any bug in the first 10 iterations with a concrete trace (bounded, no annotation, no proof beyond k). k-induction could prove a safety property like s ≥ 0 without the closed-form invariant (if it's k-inductive), but would return Unknown on the exact s == n(n+1)/2 (not inductive without the invariant — needs the deductive engine or an inferred relational invariant). One program, three complementary attacks — the toolbox the project teaches.

Consolidated Pitfalls (Top 10, cross-phase)

  1. False Verified (the only fatal bug) — a buggy program passes. Example: a dropped frame axiom, a wrong WP rule, a machine-int-as-math-int encoding. Guard: the soundness corpus + tripwire (I1), dual-solver, --dump-smt external re-check.
  2. Frame/modifies hole — a call assumes too much because the callee under-declared its effects. Example: a method modifies a global it omits from modifies. Guard: the per-procedure modifies-conformance VC (I14).
  3. Machine-vs-math int confusion — overflow hidden (false Verified) or over-constrained (spurious Refuted). Example: x+1 > x on bv32 is false (wraps), true on int. Guard: the type→theory map + both encodings tested (I9).
  4. Matching loop — a quantifier trigger regenerates its own match → infinite instantiation → hang. Example: trigger f(x) on axiom f(x)=f(g(x)). Guard: the matching-loop check; prefer Unknown over hang (I10).
  5. Exponential VC — naive WP duplicates the post across branches. Example: nested ifs. Guard: the block-equation compaction + the size guard (I6).
  6. Residual cycle / bad DSA merge — passification leaves a loop or a wrong join value → WP hangs or is unsound. Guard: acyclicity + single-definition audits (I4/I5).
  7. Spurious counterexample — a Refuted ships a model that isn't a real execution → erodes trust. Guard: the spuriousness re-check; downgrade to Unknown (I11).
  8. Non-monotone abstract transfer — AI under-approximates → an unsound inferred invariant. Guard: monotonicity property test (I12) and the deductive engine re-checks every inferred invariant (defense in depth).
  9. Trusting unknown as unsat — solver unknown/timeout read as Verified. Example: a hard VC times out. Guard: any non-unsat ⟹ verifier Unknown (I15).
  10. Over-claim from BMC/k-induction — bounded-safe reported as proven, or k-induction's step taken without the base case. Guard: bound tagging (I16) + the two-obligation gate (I17).

Glossary

  • Deductive verification — proving a program meets its specification by generating + discharging logical verification conditions (this project; vs model checking).
  • Hoare triple — {P} c {Q}: if P holds before c, Q holds after.
  • Weakest precondition (WP) — the predicate transformer wp(c, Q): the weakest P such that {P} c {Q}.
  • Strongest postcondition (SP) — the dual transformer; used here for differential testing.
  • Predicate transformer — a function mapping a postcondition to a precondition (or vice-versa); WP/SP.
  • Verification condition (VC) — the FOL formula whose validity implies a program obligation holds.
  • Guarded command — assume/assert/havoc/assign/;/□; the VIR's command set (Dijkstra).
  • Verification IR (VIR) — the Boogie/WhyML-style guarded-command intermediate representation.
  • Passification — rewriting a program into assignment-free, acyclic (passive) form for WP.
  • DSA / SSA — dynamic/static single assignment: each variable version defined once.
  • Loop cutpoint — the program point where a loop's back-edge is cut by the invariant assumption.
  • Loop invariant — a predicate true on every loop iteration; the crux of loop verification.
  • Decreases / variant — a well-founded metric proving loop/recursion termination.
  • Frame / modifies clause — the set of locations a procedure may change; the basis of modular framing.
  • Modular verification — verifying a call site against the callee's contract, not its body.
  • Contract — a procedure's requires/ensures/modifies.
  • Precondition / postcondition — what a caller must establish / what the callee guarantees.
  • old(e) — the pre-state value of e in a postcondition (2-state assertion).
  • Ghost state — specification-only state that may not influence physical execution.
  • Block-equation encoding — the linear VC form using one fresh predicate per block (Leino).
  • Trusted computing base (TCB) — the components trusted to conclude Verified (VCGen + encode + solver).
  • Soundness — never report a false program as verified (the prime invariant).
  • Completeness — never fail to verify a true program; this verifier is sound but incomplete.
  • SMT — satisfiability modulo theories; the decision procedure backend.
  • SMT-LIB2 — the standard SMT solver command + term language.
  • LIA / LRA — linear integer / real arithmetic theories.
  • Theory of arrays — McCarthy select/store axioms.
  • EUF — equality + uninterpreted functions.
  • Bitvector theory — fixed-width machine-integer semantics (wrapping arithmetic).
  • Algebraic datatypes (ADT) — constructor/selector/tester theory.
  • Trigger / pattern — a term guiding quantifier instantiation (E-matching).
  • E-matching — instantiating quantifiers by matching triggers against ground terms.
  • Matching loop — a trigger whose instantiation regenerates a matching term forever (a hang risk).
  • Counterexample — a concrete model witnessing that an obligation can fail, mapped to source.
  • Spurious counterexample — a model that is not a real program execution (a reconstruction bug).
  • Unsat core — a minimal unsatisfiable subset; here, the obligations responsible for validity/diagnostics.
  • Bounded model checking (BMC) — unrolling the transition relation to a bound k to find bugs ≤ k.
  • Transition system — (Init, Trans, Prop); the BMC/k-induction view of a program.
  • k-induction — proving safety by a base case (BMC to k) + an inductive step over k consecutive states.
  • Unique-states strengthening — requiring the k induction states distinct, to prove more properties.
  • Abstract interpretation — sound over-approximating analysis over a lattice of abstract values.
  • Lattice — a partial order with joins/meets; the abstract-domain structure.
  • Interval domain — abstracting a variable by [lo, hi]; the Phase-0 abstract domain.
  • Transfer function — the abstract semantics of a command; must be monotone for soundness.
  • Widening (▽) — an operator forcing fixpoint termination on infinite-height lattices.
  • Narrowing (△) — an operator recovering precision lost by widening.
  • Fixpoint — the stable solution of the abstract iteration; the inferred invariant.
  • Houdini — greatest-fixpoint pruning of candidate invariants to an inductive subset.
  • Invariant inference — automatically computing loop invariants (so the deductive engine succeeds).
  • CEGAR — counterexample-guided abstraction refinement (a deferred BMC/k-induction tie-in).
  • Hash-consing — interning structurally equal terms to one id (sharing + fast equality + determinism).
  • Verdict triplet — Verified / Refuted(counterexample) / Unknown(reason); the external contract.
  • Obligation kind — the classification of an assert (pre/post/inv/decreases/bounds/frame/…) for diagnostics.
  • Vacuous specification — a spec so weak that Verified proves nothing (rejected by WF checks).
  • Relative completeness — completeness modulo an oracle for the underlying logic (the theoretical limit of an SMT-backed verifier).
