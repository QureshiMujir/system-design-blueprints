Decisions (§9) · 32 ADRs

01

Implementation language

Chosen

Rust (stable)

Rejected

OCaml, Lean/Coq, Haskell, Python

When the rejected choice is right

OCaml wins when GC-pause tolerance is high and the team is embedded in the verification-tools research community (Why3/Frama-C ecosystem).

Why: safe term-DAG mutation, exhaustive enums on AST/VIR/SMT, GC-free long runs, portfolio consistency (§1)

02

Build system

Chosen

Cargo workspace + Makefile

Rejected

CMake, Bazel

When the rejected choice is right

Bazel wins when the monorepo spans multiple languages and hermetic cross-language builds outweigh the single-toolchain simplicity of Cargo.

Why: native, reproducible, one toolchain

03

Dependency policy

Chosen

stdlib + minimal (num/rug for bignum, serde for fixtures)

Rejected

heavy crates

When the rejected choice is right

Heavier crates (nom for parsing, im for persistent collections) win when development speed on non-TCB code matters more than minimizing the trusted base.

Why: small trusted base near the TCB

04

Verification IR

Chosen

Boogie/WhyML-style guarded commands

Rejected

direct source→SMT

When the rejected choice is right

Direct source→SMT lowering wins for a tiny, single-backend throwaway prototype where the IVL abstraction overhead exceeds its benefit.

Why: passification + WP need a normalized IR (P12)

05

Term representation

Chosen

hash-consed DAG, arena, TermId indices

Rejected

boxed trees

When the rejected choice is right

Boxed trees win on a small in-memory prototype where structural sharing is not needed and allocation profile is irrelevant.

Why: sharing + fast structural equality + determinism (I7)

06

VC generation

Chosen

weakest-precondition (sp variant for compare)

Rejected

symbolic execution only

When the rejected choice is right

Symbolic-execution-only discharge wins when path coverage is the goal and modular contract-based proof is not required (e.g. test generation).

Why: WP is modular + standard; sp kept for differential testing

07

VC encoding

Chosen

block-equation passive form (Leino)

Rejected

naive WP

When the rejected choice is right

Naive WP wins when the program is tiny (few branches), the exponential blowup doesn't manifest, and the readable per-path formula aids debugging.

Why: linear VC size, no exponential blowup (P6/I6)

08

Passification

Chosen

DSA/SSA, loop cutpoints

Rejected

none (cyclic WP)

When the rejected choice is right

A non-passified cyclic WP wins only for a direct-assignment WP implementation used for differential testing against the passified form.

Why: makes WP terminating + linear (I4/I5)

09

Arithmetic

Chosen

math int → LIA/LRA; machine int → BV

Rejected

float for reals

When the rejected choice is right

Floating-point encoding wins when the source language includes IEEE 754 operations and faithful float semantics are required (machine floats deferred).

Why: exactness + faithful overflow (P7/I9)

10

Numbers (constants)

Chosen

arbitrary-precision rationals (rug/GMP)

Rejected

i64/f64

When the rejected choice is right

Native i64/f64 constants win when programs are small, constant values always fit in 64 bits, and GMP overhead is the measured bottleneck.

Why: no overflow/rounding in the encoder (soundness)

11

Arrays / heap

Chosen

theory of arrays (select/store); simple heap-as-array

Rejected

separation logic now

When the rejected choice is right

Separation logic wins the moment aliased mutable heap appears; the heap-as-array model is unsound for programs with pointer aliasing.

Why: decidable, classic; SL deferred (Deferred Features Register)

12

Uninterpreted/recursive fns

Chosen

EUF + quantified defining axioms (with decreases)

Rejected

inline unfolding

When the rejected choice is right

Inline unfolding wins for single-call, well-bounded recursion where the EUF axiom's quantifier overhead exceeds the inlining cost.

Why: modular; bounded by triggers (P8)

13

Quantifiers

Chosen

explicit triggers + E-matching; matching-loop check

Rejected

full MBQI now

When the rejected choice is right

Full MBQI (model-based quantifier instantiation) wins when triggers are impossible to supply and completeness matters more than predictable termination.

Why: predictable instantiation; completeness boundaries documented (I10)

14

SMT backend

Chosen

pluggable external Z3/CVC5 over SMT-LIB2 + optional embedded DPLL(T) core

Rejected

built-in solver only; single hard-wired solver

When the rejected choice is right

A single hard-wired solver wins when the deployment target has only one solver available and portability is not a concern.

Why: LOCK: leverage mature solvers; embedded core = self-contained fallback + teaching (cross-link #277/#278/#303). Justification: re-implementing a competitive SMT solver is a separate multi-month project (#303); reuse it, but keep an embeddable core so the verifier is not a hard Z3 dependency

15

Solver transport

Chosen

child process, SMT-LIB2 text, line protocol

Rejected

C API/FFI binding

When the rejected choice is right

An FFI/C API binding wins when the solver process round-trip latency (text serialization) dominates and the ABI is stable across solver versions.

Why: robust, version-portable, sandboxable; FFI couples ABI

Datatypes

Rejected

When the rejected choice is right

Manual EUF axioms win when the solver's native ADT support is absent or buggy and hand-crafted axioms give better instantiation control.

Chosen

base (BMC) + inductive step

Rejected

When the rejected choice is right

Requiring an auxiliary invariant wins when the property is not k-inductive for any practical k, forcing the user to annotate or use the absint engine.

Rejected

Template-only (no general lattice) wins when the invariant shape is known a priori and the generality of a full lattice framework adds unneeded complexity.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-A: Interactive Proof Assistant (Full Expressiveness, Manual Proofs)

   Source (any language) ──► Proof Assistant kernel
         ▲                        │
         │  tactic scripts        │ type-checked proof terms
         │  (human / automation)  ▼
   User  ──────────────────► Verified certificates
                                  │
                             (small trusted kernel)

Wins when: the program or the mathematical property cannot be expressed in first-order logic; the trusted computing base must be a single, independently verified kernel (a few kLOC); proof certificates must be re-checkable decades later; or completeness is more valuable than automation (hardware / OS / compiler correctness, seL4 Klein et al. SOSP 2009, CompCert Leroy 2009).

Embodied by: Coq, Isabelle/HOL — the seL4 microkernel and CompCert C compiler both use Isabelle/Coq respectively to produce machine-checked proofs.

Why rejected here: the target is an automated, push-button verifier driven by first-order contracts and an SMT backend. Interactive proof assistant workflows require proof engineers writing tactic scripts — incompatible with the design goal of automatic discharge. The SMT solver does remain in the TCB (a deliberate, documented tradeoff; proof-producing mode is deferred to a future certificate checker that would narrow this gap).

Alt-B: Bounded Model Checking Only (Bug-Finding, No Invariants)

   Source ──► CFG (no loop cut) ──► Unroll k times ──► SAT/SMT query
                                         │
                                    k-bounded trace
                                    (concrete bug or "safe ≤ k")

Wins when: the goal is fast bug-finding (test amplification), not proof; the program lacks annotations; shallow bugs at depth ≤ k are the primary target; and the absence of loop invariants eliminates annotation overhead entirely. At hardware/embedded scale, tools like CBMC operate in exactly this regime.

Embodied by: CBMC (diffblue/cbmc) — a production BMC engine for C/C++ that makes no claim beyond the bound.

Why rejected here: BMC cannot prove properties for all executions of a program with unbounded loops — it reports "safe up to k" which is not a verification result. The design point of this project is modular, contract-based, infinite-state deductive proof; BMC is included as a complementary engine (Phase 9) precisely because it fills the fast-bug-finding niche, but it cannot be the primary engine.

Alt-C: Abstract-Interpretation-Only Sound Static Analysis (No Specs)

   Source ──► CFG ──► Abstract fixpoint (lattice domain)
                              │
                    Sound over-approximation of
                    all reachable states ──► alarm / no-alarm
                    (no user specs required)

Wins when: the analysis must be fully automatic (no user annotations), the alarm rate must be soundly bounded, and the property is a fixed safety class (no null dereference, no array out-of-bounds, no integer overflow) — i.e., the spec is built-in, not user-supplied. Astree (Cousot et al.) soundly analyzed Airbus fly-by-wire control software (A340/A380) with zero false alarms in this regime (sound, so no missed errors either).

Embodied by: Astree (Cousot, Cousot, et al.) — the production abstract-interpretation tool for safety-critical embedded C, deployed at Airbus.

Why rejected here: the design goal requires user-specified functional correctness properties (requires/ensures) that go beyond fixed safety classes — e.g., "this sort is correct," "this cryptographic function satisfies this equation." Abstract interpretation without specs can only prove generic safety properties; it cannot prove application-specific postconditions. The absint engine (Phase 11) is included as an invariant-inference layer feeding the deductive engine, not as a standalone verifier.

Alt-D: Deductive VC-Gen Without Passification (Direct-Assignment WP)

   Source ──► VIR (with assignments) ──► Direct WP over assigned CFG
                                               │
                                    VC with substitution chains
                                    (potentially exponential)

Wins when: programs are small (few branches), the exponential blowup never manifests in practice, and the simpler implementation (no SSA/DSA pass, no cutpoint logic) reduces engineering complexity. Research prototypes exploring new theories or encoding strategies sometimes start here.

Embodied by: early Dijkstra-style WP implementations (the original A Discipline of Programming formulation) and the differential sp variant kept in this project (ADR-06) for cross-checking.

Why rejected here: the block-equation compaction (Leino IPL 2005) is not an optimization — it is the correctness boundary for practical verification. Any non-trivial program with nested branches will produce an exponential VC (I6), causing solver timeouts that are misdiagnosed as incompleteness rather than an engineering failure. The compacted form is the design; the naive form is kept only for differential testing (ADR-06).
