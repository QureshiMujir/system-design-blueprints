⬜ Phase 0 — Repo Skeleton, Syntax, Parser §12

Objectives

Lay the workspace, the hash-consed syntax substrate (Sort/Expr/Span/TermId), and the parser for the annotated source + spec sublanguage. No checking or verification yet — produce a typed-but-unchecked AST with spans on every node.

Deliverable

cli accepts a .vfy file, parses it, and --dump-ast echoes a normalized form; structurally identical subterms share a TermId; malformed input yields a precise located error.

Acceptance
  • Round-trip on examples/*.vfy (parse → dump → re-parse → identical AST).
  • Hash-consing: structurally equal terms share a TermId (identity test).
  • All §8.1 constructs parse, including triggers, old(.), quantifiers, match, store/select syntax.
  • Parser fuzz (cargo-fuzz) survives 5 min with no panic/UB; deep-nesting inputs hit the depth cap, not a stack overflow.
Fixtures

parse/method-contract, parse/while-invariant, parse/quantifier-trigger, parse/adt-match, parse/bv-literal, parse/missing-brace (error), parse/unterminated-quant (error), parse/hashcons-sharing.

Pitfalls
  • Not hash-consing from the start → VCGen term blowup + nondeterministic equality. Intern every node immediately.
  • Losing spans through desugaring later → counterexamples can't point at source (I8). Capture spans at the leaf in the lexer; never synthesize a node without one.
  • Ambiguous ==> vs >= / <==> lexing → silent misparse. Longest-match lexing, explicit tests.
  • Trigger parsed as a set literal → wrong AST. Triggers are pattern terms inside {} immediately after the quantifier binder; test the boundary.
  • Stack overflow on deep terms → crash. Depth cap or explicit stack; fuzz deep inputs.

⬜ Phase 1 — Type/Sort Checking and Spec Well-Formedness §13

Objectives

Reject ill-typed and ill-specified programs before any VC exists: sort checking, ghost/physical separation, modifies-scope, decreases/trigger well-formedness. This phase makes "verified" meaningful (P15).

Deliverable

cli check file.vfy reports OK or a list of located type/spec errors; well-formed programs pass to lowering.

Acceptance
  • Every malformed-spec fixture is rejected with the correct error + span.
  • Ghost-leak fixtures are rejected (I3).
  • Modifies-scope violations are caught at check time (I14, the static half — the dynamic conformance VC is Phase 2/3).
  • Trigger WF rejects uncovered-binder triggers (I2).
  • Differential: well-typedness agrees with a Dafny-like reference on shared fixtures.
Fixtures

typeck/sort-mismatch (error), typeck/decreases-not-wf (error), typeck/ghost-leak (error), typeck/modifies-scope (error), typeck/trigger-uncovered (error), typeck/old-outside-post (error), typeck/match-nonexhaustive (error), typeck/valid-maxindex (OK).

Pitfalls
  • Implicit int/bv coercion → hides the math-vs-machine distinction (P7) → wrong verdicts downstream. Require explicit conversion ops.
  • Ghost flow only checked syntactically → indirect leaks (via a physical var assigned from a ghost). Use a flow/taint analysis, not a syntactic scan (I3).
  • Accepting an un-well-founded decreases → termination "proved" but isn't. The metric's well-foundedness is a checked property (I2).
  • Trigger covering binders but trivially matching everything (e.g. a variable as a trigger) → matching loops later. Reject degenerate triggers here.
  • Forgetting functions need a reads frame → unsound function axioms when the heap is involved.

⬜ Phase 2 — Verification IR and Lowering (the Heart of Modularity) §14

Objectives

Desugar typed source into VIR guarded commands: the loop cut, the modular call translation (assert pre / havoc modifies / assume post), arrays→select/store, ADTs, old capture, ghost lowering. Insert every proof obligation with its kind + span label (I8). This is where modular verification is built.

Deliverable

cli --dump-vir file.vfy shows each procedure as a labeled guarded-command CFG; loops are cut (not unrolled); calls are modular (callee bodies absent); obligations carry kind + span.

Acceptance
  • Loop cut is correct: a verified loop's VIR contains no back-edge into the body verification path (acyclicity established here, completed in passify).
  • Call translation never references the callee body (modular — audit).
  • Every assert has a non-None label (I8 audit).
  • old capture audit: each old(e) resolves to an entry-state version (I18).
  • Modifies-conformance obligation present for every method with a modifies clause (I14).
  • Differential: the set of obligations (kinds + spans) matches a hand-derived oracle on small programs.
Fixtures

lower/loop-cut, lower/modular-call, lower/frame-obligation, lower/array-bounds, lower/old-capture, lower/div-obligation, lower/ghost-erasable, lower/adt-match.

Pitfalls
  • Under-computing the loop-modified set → havoc forgets too little → the loop "remembers" stale values → unsound (I14). Compute the modified set as a fixpoint over the body, including via calls (transitive modifies).
  • Inlining the callee body at a call → defeats modularity, couples the proof to the implementation (P3). Use the contract only.
  • old captured at the wrong point (e.g. after a havoc) → wrong 2-state semantics (I18). Capture at procedure entry.
  • Missing bounds/div obligations → an out-of-range access "verifies" (silent unsoundness). Emit the obligation at the lowering site, unconditionally.
  • Ghost code that changes physical VIR → ghost influences execution (I3). Audit erasure.
  • Forgetting the decreases obligations in the loop cut → termination unchecked while claiming total correctness. Emit 0≤V and V<v0.

⬜ Phase 3 — Passification (DSA / SSA, Loop Cutpoint Elimination) §15

Objectives

Turn the VIR CFG into a passive, acyclic form: cut loops at cutpoints (the invariant assumption breaks the back-edge), number variables into dynamic-single-assignment, and rewrite x := e into assume(x_i = e). Passivity is what makes WP linear-size and terminating (P6/P2, I4/I5).

Deliverable

cli --dump-passive file.vfy shows assignment-free, acyclic guarded commands with versioned variables and a version→source map; ready for WP.

Acceptance
  • Passive CFG is acyclic (I5 cycle check passes).
  • Every versioned variable has exactly one static definition (I4 audit).
  • No Assign remains (only assume/assert/havoc).
  • Semantics preserved: a program's verdict is identical whether WP runs on the un-passified or passified form on small examples (differential against a reference WP that handles assignment directly).
  • Version map round-trips: every model variable maps back to a (base var, span).
Fixtures

passify/dsa-straightline, passify/if-merge, passify/loop-cut-acyclic, passify/havoc-fresh-version, passify/version-map, passify/assign-to-assume.

Pitfalls
  • Wrong φ/merge handling → a variable's value at a join is wrong → unsound VC. The merge must constrain the merged version to each incoming version on the correct edge.
  • A residual cycle (missed cutpoint) → WP non-termination (P2 breach). Assert acyclicity after the pass (I5).
  • Two definitions of one version → DSA broken → the assume(x_i=e) constraints conflict/under-constrain. Audit single-definition (I4).
  • Havoc not introducing a fresh version → the havoc'd value is conflated with its pre-havoc version → loop cut unsound. Each havoc mints a new version.
  • Version map drift → counterexamples point at the wrong source variable. Keep the map authoritative + tested.

⬜ Phase 4 — VC Generation (Weakest Precondition + Compaction) §16

Objectives

Generate the verification condition from passive guarded commands via the weakest-precondition calculus, in the block-equation compacted form so the VC is linear, not exponential (P6/I6). Carry obligation provenance into the VC for counterexamples (I8). Implement an sp variant for differential testing only.

Deliverable

cli --dump-vc file.vfy prints the per-procedure VC (compacted) as a FOL formula with obligation labels; the VC is linear in program size.

Acceptance
  • VC node count is linear in program size across the corpus (I6 ratio guard; a deliberately branch-heavy fixture stays linear, not exponential).
  • WP and SP agree on validity for every fixture (differential, ADR-06).
  • The VC for MaxIndex (§8.5) has exactly the expected obligation set (inv_entry, inv_pres, decreases, post, bounds) with correct spans.
  • VC is bit-identical across runs (I7).
  • Every conjunct of the VC traces to an obligation kind + span (I8).
Fixtures

vcgen/straightline, vcgen/branch-linear (exponential-naive, linear-compacted), vcgen/loop-obligations, vcgen/wp-vs-sp, vcgen/obligation-labels, vcgen/vc-deterministic, vcgen/maxindex-vc.

Pitfalls
  • Naive WP without compaction → exponential VC on nested branches → solver times out (incompleteness blamed on the solver). The block-equation form is mandatory (I6).
  • wp(havoc x, Q) without the universal → unsound (forgets that x is arbitrary). It must be ∀x.Q (the havoc'd version is universally quantified, or equivalently fresh-and-unconstrained in the passive encoding).
  • Losing obligation labels in compaction → counterexamples can't name the failing obligation (I8/I11). Thread (kind, span) through every assert→conjunct.
  • WP/SP divergence → a bug in one calculus. The differential (ADR-06) catches it; investigate any disagreement as a soundness bug.
  • Quantifier capture in WP (havoc introduces ∀x that captures a free x in Q) → wrong VC. With DSA versioning this is avoided (the havoc'd version is fresh), but assert it.

⬜ Phase 5 — SMT Encoding (Theories, Quantifiers, Triggers) §17

Objectives

Translate the VC into SMT-LIB2, mapping each sort to a theory (LIA/LRA, arrays, EUF, bitvectors, ADTs), emitting quantifiers with explicit triggers, and enforcing matching-loop avoidance (I10). Machine ints encode over bitvectors (wrap), math ints over LIA (unbounded) (I9). Deterministic emission order (I7).

Deliverable

cli --dump-smt file.vfy emits valid, deterministic SMT-LIB2 for each procedure's VC; a standalone Z3/CVC5 reproduces the verifier's verdict on the dumped script (a key trust check).

Acceptance
  • Emitted SMT-LIB2 parses + checks under both Z3 and CVC5 (interop).
  • The verdict from the dumped script (run externally) matches the verifier's verdict (no hidden state, faithful encoding).
  • Machine-int fixtures encode over BV (overflow wraps → the overflow bug is sat/refutable); the same code on int encodes over LIA (no overflow) — I9 demonstrated.
  • No emitted axiom forms a matching loop on the trigger corpus (I10 check passes); a deliberately-loopy trigger is flagged, not run to a hang.
  • SMT text is bit-identical across runs (I7).
Fixtures

encode/lia-arith, encode/array-select-store, encode/euf-function, encode/bv-overflow, encode/adt-datatype, encode/quant-trigger, encode/matching-loop-flagged, encode/smt-deterministic, encode/z3-cvc5-interop.

Pitfalls
  • Encoding a machine int as a math int (or vice-versa) → hides overflow (false Verified) or over-constrains (spurious Refuted) — the canonical encoding soundness bug (I9). The type→theory map is authoritative; test both.
  • Over-permissive triggers → matching loops → the solver instantiates forever → timeout on every VC mentioning the axiom (I10). The matching-loop check + conservative triggers are mandatory; prefer Unknown to a hang.
  • Over-restrictive triggers → the solver can't instantiate a needed fact → spurious Unknown (incompleteness). Balance; expose the trigger to the user.
  • Non-deterministic emission order (HashMap iteration) → non-reproducible SMT, flaky verdicts (I7). Sort by a stable key.
  • Inconsistent recursive-function axioms (no decreases guard) → the solver "proves" anything (unsat of everything) → catastrophic false Verified. Recursive defining axioms must be well-founded (tie to typeck I2).
  • Forgetting (assert (not VC)) → checking the VC's satisfiability instead of validity → inverted verdict. Validity = unsat of the negation.

⬜ Phase 6 — SMT Backend Driver (External + Embedded), Incremental §18

Objectives

Drive the decision procedure: an external Z3/CVC5 child process over SMT-LIB2 (the LOCK, ADR-14/15) and an optional embedded DPLL(T) core; incremental push/pop to reuse context across a procedure's VCs; per-VC time + memory budgets mapping to Unknown (I15); model + unsat-core extraction.

Deliverable

cli verify file.vfy discharges each procedure's VCs against the chosen backend, returning Verified/Unknown per procedure (counterexamples added in Phase 8); incremental reuse is measurable; budgets enforce a deterministic Unknown.

Acceptance
  • MaxIndex (and the valid corpus) verifies under both Z3 and CVC5.
  • A deliberately-hard VC times out to Unknown(Timeout) within budget + ε — never hangs, never returns Verified (I15).
  • Incremental discharge is measurably faster than fresh-context-per-VC on a multi-VC procedure (P10).
  • The embedded core agrees with Z3 on the QF subset of fixtures (where it is complete).
  • A killed/crashed solver process → Unknown, and the verifier recovers (next procedure proceeds).
Fixtures

smt/verify-valid, smt/timeout-unknown, smt/incremental-reuse, smt/embedded-vs-z3-qf, smt/solver-crash-recovery, smt/mem-limit-unknown, smt/z3-cvc5-agree.

Pitfalls
  • Timeout returning the last answer / blocking → a hang or a wrong verdict (I15). The watchdog must kill and force Unknown; never read a partial/stale response as authoritative.
  • Parsing only Z3's model format → CVC5 models mis-parsed → wrong counterexamples. Handle both; test interop.
  • Pop not restoring solver state → cross-VC contamination → wrong verdict on a later VC. Match push/pop exactly; or use a fresh push scope per VC.
  • Solver process leak (not reaped on timeout) → fd/process exhaustion over a large program. Always kill + reap; bound concurrent processes.
  • Trusting unknown as unsat → false Verified. Solver unknown ⟹ verifier Unknown (I15) — never Verified.
  • Embedded core silently incomplete on quantifiers → returns unknown where Z3 succeeds → more Unknown. Document the embedded core's incompleteness; default to external.

⬜ Phase 7 — End-to-End Verifier + Modifies Conformance §19

Objectives

Compose the pipeline into the verify_program driver: per-procedure verification (all VCs unsat ⟹ Verified), the per-procedure modifies-conformance check (a method must respect its own frame, I14), and the program-level report. This is the first fully-working deductive verifier (modulo counterexample rendering, Phase 8).

Deliverable

cli verify program.vfy prints a per-procedure verdict; the valid corpus is Verified, the refuted corpus is Refuted, the soundness corpus is 100% Refuted; a JSON report is emitted.

Acceptance
  • The valid corpus: 100% Verified. The soundness corpus: 100% Refuted (I1, the prime gate).
  • A method that lies about its modifies is Refuted with kind frame (I14).
  • Differential vs Dafny/Why3 on shared programs: verdicts agree (allowing for Unknown differences from solver/encoding strength).
  • The report is deterministic (same input + solver version ⟹ same report, I7).
Fixtures

verify/valid-corpus, verify/refuted-corpus, soundness/under-framed-call (must Refute), soundness/missing-bounds-check (must Refute), soundness/false-postcondition (must Refute), verify/modifies-conformance, verify/report-deterministic, verify/vs-dafny.

Pitfalls
  • Verified declared before all VCs discharged (e.g. short-circuiting on the first unsat) → unsound. Verified requires every VC unsat (I1).
  • Skipping the modifies-conformance VC → the frame rule is assumed but never checked → under-framed methods silently produce false Verified at their call sites (I14). The conformance VC is mandatory.
  • Treating Unknown as Verified or Refuted → either unsound or a spurious refutation. Unknown is its own verdict (I15).
  • Soundness corpus not run in CI → a soundness regression ships. The tripwire is a release gate.
  • Cross-procedure contamination (a stale contract used) → wrong verdict. Contracts are fixed inputs; dependency-tracked.

⬜ Phase 8 — Counterexample Reconstruction §20

Objectives

Turn a sat (VC fails) into a developer-usable counterexample: SMT model → DSA-reverse → source variable valuations, the failing obligation (kind + span), and the failing path/trace through the CFG. Re-check the model for spuriousness (I11).

Deliverable

cli verify on a refuted program prints a concrete counterexample: the failing obligation (kind + span), the input + failing-point valuations, and the failing path; a machine witness is emitted with --witness.

Acceptance
  • Every Refuted ships a counterexample whose model satisfies ¬VC and which the spuriousness re-check confirms (I11; spurious_cex_total = 0).
  • The MaxIndex-minus-invariant example (§8.6) produces the expected "postcondition 0≤m<n may fail" message with the right span.
  • Counterexamples for each obligation kind (pre/post/inv/bounds/div/frame) render correctly with the right kind label.
  • The failing path matches a hand-traced execution on small examples.
Fixtures

cex/post-fails, cex/inv-not-preserved, cex/array-oob, cex/div-by-zero, cex/precondition-fails, cex/frame-violation, cex/spurious-detected (a crafted case the re-check must catch), cex/witness-format.

Pitfalls
  • Presenting a spurious counterexample (model isn't a real execution) → erodes all trust in the tool (I11). The spuriousness re-check is mandatory; downgrade to Unknown rather than lie.
  • Wrong variable mapping (version map drift, Phase 3) → values attributed to the wrong source variable. Keep the version map authoritative + tested.
  • Reporting a model, not the failing point's values → confusing (e.g. mid-loop vs entry values conflated). Distinguish input vs failing-point valuations via the versions.
  • Losing the obligation label (Phase 4/5 attribution dropped) → "something failed" with no kind/span (useless). The label must survive to here (I8).
  • Path ambiguity (model consistent with multiple paths) → pick a canonical one deterministically; document.

⬜ Phase 9 — Bounded Model Checking (BMC) §21

Objectives

A complementary engine over the same VIR: encode the program as a transition system (Init, Trans, Prop), unroll Trans to a bound k, and check Init ∧ ⋀_{i<k} Trans_i ∧ ¬Prop — sat is a concrete bug trace ≤ k, unsat proves the property up to k (I16). Complete for bug-finding within the bound; reuses encode/smt/cex.

Deliverable

cli bmc --bound k file.vfy finds bugs reachable within k steps with concrete traces, or reports "safe up to k".

Acceptance
  • A program with a bug at depth d is Refuted by BMC at any k ≥ d with a concrete d-step trace; k < d reports "safe up to k" (I16 — honest, not a false proof).
  • The concrete trace is a real execution (re-checkable, like I11).
  • BMC unsat is never reported as an unconditional proof (I16 audit).
  • Differential: BMC bug-finding agrees with CBMC-style reference on shared bounded fixtures.
Fixtures

bmc/bug-at-depth-3, bmc/safe-up-to-k, bmc/concrete-trace, bmc/iterative-deepening, bmc/no-overclaim (unsat tagged with bound), bmc/vs-cbmc.

Pitfalls
  • Reporting BMC unsat as a full proof → false sense of total correctness (I16). Always tag with the bound.
  • Unrolling the cut loop instead of the real loop → BMC must use the original transition relation (it explores executions), not the invariant-cut form. Use the pre-passify CFG's transition relation.
  • State explosion at large k → solver blows up. Bound k; iterative deepening with a budget; report the depth reached.
  • Off-by-one in the unrolling (k steps vs k+1 states) → missed/extra-depth bugs. Define + test the step/state correspondence precisely.
  • Trace not a real execution → same spuriousness risk as I11; re-check.

⬜ Phase 10 — k-Induction §22

Objectives

Prove safety without a manually supplied invariant (strength permitting) via k-induction: the base case (no violation in the first k steps — a BMC query) plus the inductive step (if the property held for k consecutive states, it holds at the next). Both unsat ⟹ proof for all reachable states (I17).

Deliverable

cli kinduct --k k file.vfy proves k-inductive safety properties without invariant annotations, or reports a real bug (base case) or Unknown (not k-inductive for tried k).

Acceptance
  • A k-inductive property is Verified (both base + step unsat, I17).
  • A property true-but-not-k-inductive (for small k) is Unknown, not falsely Verified (the step-only trap is avoided, I17).
  • A real bug is Refuted via the base case with a concrete trace.
  • Unique-states strengthening makes a known-not-1-inductive-but-2-inductive property verify at k=2.
  • Differential vs a k-induction reference on shared fixtures.
Fixtures

kind/1-inductive, kind/2-inductive-unique-states, kind/not-inductive-unknown, kind/base-case-bug, kind/step-only-unsound (must NOT verify on step alone), kind/vs-reference.

Pitfalls
  • Reporting Verified on the inductive step alone → unsound (the step says "stays safe if safe", not "is reachable-safe"); the base case is mandatory (I17). The two-obligation gate enforces this.
  • Forgetting unique-states strengthening → many true properties report Unknown at small k (incompleteness). Add the distinctness constraints.
  • Increasing k unboundedly → the step never converges on a non-k-inductive property → hang. Bound k; report Unknown.
  • Using the invariant-cut CFG → k-induction needs the raw transition relation (it reasons over arbitrary states), not the deductive cut. Use transys.
  • Confusing k-induction with the deductive loop rule → they are different proof methods over the same IR; k-induction needs no user invariant but is weaker (only k-inductive properties).

⬜ Phase 11 — Abstract Interpretation, Invariant Inference, Incrementality, CLI §23

Objectives

Infer loop invariants automatically (so under-annotated loops verify), via an abstract-interpretation framework (lattice + monotone transfer + widening/narrowing, I12/I13) and Houdini (greatest-fixpoint candidate pruning); make verification incremental (re-verify only changed procedures, P10); finish the cli surface. Inferred invariants feed lower (Phase 2) to strengthen the deductive engine.

Deliverable

cli infer file.vfy prints inferred loop invariants; cli verify uses them to verify under-annotated loops; an edit re-verifies only affected procedures (incremental).

Acceptance
  • The interval analysis infers correct ranges (e.g. 0 ≤ i ≤ n for a counting loop) — sound over-approximations (validated by the deductive engine accepting them).
  • Widening terminates on every loop (I13 iteration-count bound never exceeded); narrowing improves precision measurably.
  • All transfer functions pass the monotonicity property test (I12).
  • Houdini converges to an inductive subset.
  • An under-annotated loop that was Unknown becomes Verified after inference (and the inferred invariant is itself checked, not trusted).
  • Incremental: editing one procedure re-verifies O(affected), not O(program) (timing test).
Fixtures

absint/interval-counting-loop, absint/widening-terminates, absint/narrowing-precision, absint/transfer-monotone, absint/houdini-converges, absint/inferred-then-verified, incr/edit-one-procedure, incr/verdict-cache.

Pitfalls
  • Non-monotone transfer function → the fixpoint under-approximates → an unsound "invariant" → a false Verified if trusted (I12). Mitigation 1: property-test monotonicity. Mitigation 2 (defense in depth): the deductive engine re-checks every inferred invariant, so even a buggy AI can't cause unsoundness — it can only cause Unknown.
  • Widening never applied → infinite ascending chain → fixpoint non-termination (I13). Apply widening at every loop head; bound iterations.
  • Over-aggressive widening → invariant too weak to verify the loop (Unknown). Use a widening-with-thresholds + narrowing to recover.
  • Incremental staleness (a callee's contract changed but the caller not re-verified) → wrong cached verdict. The VC-input hash must include callee contracts (dependency completeness).
  • Trusting the AI result directly → couples soundness to the AI's correctness. Always re-check inferred invariants via the deductive engine (the AI is a hint generator, not an oracle).
