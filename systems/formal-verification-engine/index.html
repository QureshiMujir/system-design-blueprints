In one paragraph

A deductive program verifier checks a program against the promises written beside it. You annotate code with preconditions, postconditions and loop invariants, and the engine turns each promise into a logical formula and hands the formulas to an external logic solver (§1). Every procedure comes back as Verified, Refuted with a counterexample, or Unknown (§1). It is a Rust library plus one command-line binary, in the style of Dafny, Why3 and Viper (§1). Its users are engineers learning verification and tool authors who want an embeddable verifier (§1). Its one non-negotiable rule is never to call a false program verified (P1, §4).

The problem, concretely

Take the blueprint's own example, MaxIndex: given an array a of length n > 0, return the index m of a largest element (§8.1). §8.1 calls it the canonical "binary search 'find max'" example; the code §8.1 shows steps i from 1 up to n, one element at a time (§8.1).

method MaxIndex(a: array<int,int>, n: int) returns (m: int)
  requires n > 0
  ensures  0 <= m < n
  ensures  forall j: int { a[j] } :: 0 <= j < n ==> a[j] <= a[m]
{
  m := 0;
  var i: int := 1;
  while (i < n)
    invariant 1 <= i <= n
    invariant 0 <= m < i
    invariant forall j: int { a[j] } :: 0 <= j < i ==> a[j] <= a[m]
    decreases n - i
  {
    if (a[i] > a[m]) { m := i; }
    i := i + 1;
  }
}

The verifier must discharge four obligations for it: invariant entry, invariant preservation, decreases, and the postcondition (§8.5). Each obvious shortcut fails, as the mental models explain:

  • Unroll the loop. That verifies only up to the unroll bound; the infinite-state strength disappears (MM2, I16).
  • Inline every callee's body. Each caller's proof is coupled to each callee's code, scalability is destroyed, and any edit becomes a full re-proof (MM3, P3).
  • Apply the weakest-precondition rule naively. It copies the postcondition into every branch, the formula grows exponentially, the solver times out, and you blame the solver instead of your own formula generator (MM1, P6).
  • Forget what a call can change. If a callee modifies x but does not declare it, the caller wrongly assumes x is unchanged and a false program is accepted, silently (MM4, P4).
  • Read a solver timeout as success. A hard formula that times out must come back as Unknown, never Verified (I15, Consolidated Pitfalls item 9).

The blueprint's worked failure: delete the invariant 0 <= m < i. The solver returns sat with, for example, n=2, i=1, m=5, and cex reports that the postcondition 0 <= m < n may fail, kind post, at the ensures line (§8.6). The blueprint calls this a spec incompleteness, not a soundness bug: the verifier correctly refuses (§8.6).

How it works, end to end

Follow MaxIndex through the boxes of §3's diagram, condensed here (module names are the blueprint's, §1):

  1. parse. The only box that touches untrusted text: a hand-written recursive-descent parser builds a hash-consed syntax tree with a source span on every node, the spine of counterexample reconstruction (§3, ADR-23).
  2. typeck. Assigns sorts, separates ghost (specification-only) from physical state, checks spec well-formedness (in-scope names, a well-founded decreases, triggers covering their bound variables) and modifies scoping; bad programs get a located error before any formula exists (§3, P15, I2).
  3. lower. Rewrites the typed source into guarded commands (assume, assert, havoc, assignment, sequence, choice) arranged as a control-flow graph (vir). It cuts loops and turns calls into contract-based stubs (§3, §8.2, §8.3).
  4. passify. Removes assignments and cycles: loops are cut at their cutpoints and each variable gets numbered versions (dynamic single assignment), leaving pure assume/assert over versioned variables (§3, I4, I5).
  5. vcgen. Computes the procedure's verification conditions (VCs) with the weakest-precondition calculus, in a compacted form that stays linear in program size (§3, §8.4, I6).
  6. encode. Translates the VC to SMT-LIB2 using integer arithmetic, arrays, uninterpreted functions, bitvectors and datatypes, with explicit quantifier triggers (§3, I9, I10).
  7. smt. Runs Z3 or CVC5 as a child process, or an optional embedded core, with push/pop for reuse, a per-VC time budget, and model and unsat-core extraction (§3, ADR-14, ADR-15).
  8. Verdict. The query asserts the negation of the VC. unsat means the VC is valid, and a procedure is Verified only when every one of its VCs is unsat within budget. sat goes to cex (§3, §8.4).
  9. cex. Maps the solver's model back through the version numbers and spans into source-level values, the failing obligation and the path taken (§3, I11).
  10. bmc, kind, absint. Three side engines over the same IR (§3). cli exposes verify, bmc, kinduct, infer and the --dump-* flags (§1).

The core ideas

Guarded commands and the weakest-precondition rule (§8.2, P2)

A guarded command language has four primitives. assume P continues only on paths where P holds. assert P is an obligation that must hold here. havoc x gives x an arbitrary value, and x := e assigns (§8.2). The weakest precondition wp(c, Q) is what must be true before c so that Q is true after. The blueprint's table (§8.2):

Command wp(c, Q)
assume P P ⇒ Q
assert P P ∧ Q
havoc x ∀x. Q
x := e (before passification) Q[e/x]
c1 ; c2 wp(c1, wp(c2, Q))
c1 □ c2 (choice, like goto) wp(c1,Q) ∧ wp(c2,Q)

Read the rows as a recipe: a sequence works backwards, and a choice requires both branches to work (§8.2). Because the formula is built by structural recursion over an acyclic, assignment-free graph, it always halts (P2, §4). A strongest-postcondition variant is kept only to cross-check the weakest-precondition one (ADR-06).

The loop cut and the call rule (§8.3, MM2, MM3)

An annotated loop is not unrolled; §8.3 rewrites it like this (§8.3):

while (g) invariant I decreases V { B }      ⟿     # mods = vars assigned in B
   assert I ;                                       # I holds on entry  (inv_entry)
   havoc mods ;                                      # forget loop-modified vars
   assume I ;                                         # arbitrary iteration: assume I
   ( assume g ;                                        #   enter body
     assert 0 <= V ;                                  #   variant bounded below (decreases)
     let v0 = V in B ; assert I ; assert V < v0 ;     #   body re-establishes I, V decreased
     assume false                                     #   this path is for verification only
     □                                                #   ─ or ─
     assume !g )                                       #   exit: fall through with I ∧ ¬g

The loop is checked once, as one universally quantified iteration, instead of infinitely many (MM2). A call x := p(args) to a callee with requires Pre, ensures Post, modifies M becomes assert Pre[args/params] ; havoc M, x ; assume Post[args/params, old↦pre] (§8.3). The callee's body is never read: the blueprint calls this sandwich the single idea that makes deductive verification compositional (MM3, P3). It is safe only if M covers everything the callee really changes (P4), so each procedure also gets a modifies-conformance VC (I14). A method that assigns a global but omits it from modifies comes back Refuted with kind frame (§8.7).

Passification and the compact VC (§8.4, MM1, MM5, P6)

After the cut, assignments are replaced by numbered versions: x := e becomes assume(x_i = e) with a fresh version x_i, and each version is defined exactly once (§3, I4). Without this, weakest preconditions copy the postcondition across branches, which is exponential (MM1). The compacted form gives each block b a fresh proposition Block_b and conjoins one equation per block (§8.4):

VC(proc) ≡  ⋀_b  ( Block_b  ⟺  wp_local(b, ⋀_{s∈succ(b)} Block_s) )   ∧   Block_entry

A shared continuation is referenced by name instead of copied, so the formula is linear in program size (§8.4, ADR-07, I6). The blueprint's own comparison: for a 25-node formula under a binary-branch tree of depth 10, naive copying gives 1,024 copies, which is 25,600 nodes, against 25 compacted (Capacity Model item 2). The version numbering is also what lets a model be translated back to source variable names later (MM5).

Encoding and quantifier triggers (§8.4, §8.7, MM7, I9, I10)

To test validity, encode emits (assert (not VC)) (check-sat): unsat means Verified, sat gives a model and so a counterexample (§8.4). Math integers map to linear integer arithmetic, machine integers to bitvectors that wrap on overflow, arrays to select/store, recursive functions to uninterpreted functions plus defining axioms (§3, I9, ADR-12). The choice changes the verdict: x + 1 > x fails on bv32 at x = 2^31−1 and holds on int (§8.7).

A forall is emitted with a trigger: a pattern, such as {a[j]} in MaxIndex, that tells the solver when to instantiate it (§8.1, §8.5). A badly chosen trigger such as {f(x)} on f(x) == f(g(x)) regenerates its own matches forever (a matching loop) (§8.7). The encoder checks for this and prefers Unknown over a hang (I10, §8.7).

Counterexamples (§8.6, P9, I11, I8)

On sat, the model assigns values to versioned solver constants. cex reverses the version map to get source variable values, takes the failing obligation's kind and span from the labeled assertion, and works out the failing path through the graph (§3, §20.2). Every assert carries a kind (pre, post, inv_entry, inv_pres, decreases, assert, bounds, frame, div_nonzero) and a span (I8, §8.2). Before reporting, the engine re-checks that the model satisfies not VC along that path, and downgrades to Unknown if not (I11).

Three engines on one IR (§3, MM9, MM10, I16, I17)

  • Bounded model checking (bmc) views the program as (Init, Trans, Prop) and asks whether Init ∧ Trans^0 ∧ … ∧ Trans^{k-1} ∧ ¬Prop is satisfiable. sat is a real bug trace of at most k steps, and unsat proves only "holds up to k" (§3, I16).
  • k-induction (kind) adds the inductive step: if the property held on k consecutive states it holds on the next. It counts as proved only when the base case and the step both discharge, because a step alone can hold vacuously for unreachable states (§3, I17, MM9).
  • Abstract interpretation (absint) walks a lattice (intervals first) with monotone transfer functions, forcing termination by widening and recovering precision by narrowing. Its output is a candidate loop invariant, and the deductive engine re-checks every one before use, so a buggy analysis degrades to Unknown rather than a false Verified (§3, I12, I13, MM10).

The trade-offs — where engineers disagree

Use an existing solver as a separate process (ADR-14, ADR-15)

Chosen: a pluggable external Z3 or CVC5 over SMT-LIB2 text on a child process, plus an optional embedded solver core, because writing a competitive solver is a separate multi-month project (§9 ADR-14). The child-process line protocol is robust, portable across solver versions and sandboxable (§9 ADR-15). Rejected: a built-in solver only, or one hard-wired solver; and a C API/FFI binding (§9). When the rejected choice is right: a single hard-wired solver wins when only one solver exists on the deployment target and portability does not matter (ADR-14). An FFI binding wins when the text round trip dominates and the ABI is stable across solver versions (ADR-15).

A guarded-command intermediate language instead of source-to-solver (ADR-04)

Chosen: a Boogie/WhyML-style guarded-command IR, because passification and weakest preconditions need one normalized form (§9). Every engine consumes it (§3). Rejected: translating source straight to SMT (§9). When the rejected choice is right: a tiny, single-backend throwaway prototype where the cost of the extra IR layer exceeds its benefit (§9).

Block equations instead of naive weakest precondition (ADR-07)

Chosen: the block-equation passive form (Leino), giving a linear-size VC (§9, I6). Rejected: naive weakest precondition (§9). When the rejected choice is right: when the program is tiny with few branches, the blowup does not show up, and a readable per-path formula helps debugging (§9). The blueprint also keeps naive direct weakest precondition only as a differential-testing check (Alt-D, ADR-06).

A simple heap-as-array model now, separation logic later (ADR-11)

Chosen: the theory of arrays with a simple heap-as-array model, which is decidable and classic (§9). Rejected: separation logic now (§9). When the rejected choice is right: "the moment aliased mutable heap appears", because the heap-as-array model is unsound for programs with pointer aliasing (§9 ADR-11); it is deferred (Deferred Features Register).

Triggers and E-matching instead of model-based instantiation (ADR-13)

Chosen: explicit triggers with E-matching and a matching-loop check, for predictable instantiation with documented completeness limits (§9, I10). Rejected: full model-based quantifier instantiation (MBQI) now (§9). When the rejected choice is right: when triggers are impossible to supply and completeness matters more than predictable termination (§9).

Intervals plus Houdini for invariants, not IC3/PDR (ADR-22)

Chosen: interval analysis plus Houdini (start with many candidate invariants and drop those that fail, until the rest hold together), which is tractable and classic (§9, Glossary). Rejected: IC3/PDR now (§9). When the rejected choice is right: when invariants are deep, non-linear or out of reach of Houdini, or when no candidates exist and a property-directed search is needed (§9). The blueprint's cost model shows why candidate sets must stay small (Capacity Model item 9).

Roads not taken (Alternative Architectures, Deferred Features Register)

An interactive proof assistant (Alt-A) wins when the property cannot be stated in first-order logic, or when the trusted base must be one small independently verified kernel, as in seL4 and CompCert (Alt-A). It is rejected because tactic scripts written by proof engineers are incompatible with automatic discharge; the documented price is that the SMT solver stays in the trusted base (Alt-A, P5).

Bounded model checking only (Alt-B) wins for fast bug-finding with no annotations, the regime of CBMC, but cannot prove a property for all executions of an unbounded loop, so it stays a side engine (Alt-B, ADR-19). Abstract interpretation only (Alt-C) wins when the analysis must be fully automatic and the property is a fixed safety class, as with Astree on Airbus software, but application-specific postconditions need user specs, so absint only feeds the deductive engine (Alt-C, ADR-21). Weakest precondition without passification (Alt-D) wins for small programs and research prototypes where the blowup never appears, and is kept only for differential testing (Alt-D, ADR-06).

Deferred features each wait for a stated trigger (Deferred Features Register): separation logic for aliased heap, concurrency reasoning for shared-memory programs, IC3/PDR when intervals plus Houdini prove insufficient, interpolation when widening is too imprecise, proof certificates when the solver must leave the trusted base, dependent specs when first-order contracts are not enough, and C or Rust front ends when programs outside the project's own language must be verified.

What must never be false

Each line gives the invariant, then how the system notices a violation (§7 detection and telemetry).

  • I1: a valid VC (solver unsat) means the source obligation holds. Noticed by injecting known-bad programs that must come back Refuted; false_verified_total must stay 0 (§7).
  • I2: every spec is well formed before any formula is built. Noticed by the spec well-formedness checker; spec_wf_errors (§7).
  • I3: ghost state never influences real control or data flow. Noticed by a ghost-flow audit; ghost_leak_total.
  • I4 and I5: each versioned variable has exactly one definition, and the passified graph has no cycles. Noticed by a definition-count audit and a cycle check; dsa_multi_def, passive_cycle_detected (§7).
  • I6: VC size grows with program size, not exponentially. Noticed by comparing VC node count with program size; vc_nodes and a ratio guard (§7).
  • I7: identical source gives a bit-identical VC and SMT text. Noticed by replay and hashing the VC; nondeterminism_detected (§7).
  • I8: every assert carries a source span and obligation kind. Noticed by a label-presence audit; unlabeled_assert (§7).
  • I9: machine integers use bitvectors, math integers use unbounded arithmetic. Noticed by a type-to-theory mapping audit; int_theory_mismatch (§7).
  • I10: no quantifier trigger forms a matching loop. Noticed by trigger self-match analysis; matching_loop_risk.
  • I11: every Refuted has a model that satisfies not VC and maps to source. Noticed by re-checking the model and a spuriousness test; spurious_cex_total (§7).
  • I12 and I13: every abstract transfer function is monotone, and every loop fixpoint terminates through widening. Noticed by a monotonicity property test and an iteration-count bound; nonmonotone_transfer, ai_iterations (§7).
  • I14: a call's havoc set covers what the callee really modifies. Noticed by the per-procedure modifies-conformance VC; frame_violation_total (§7).
  • I15: on any budget exhaustion the result is Unknown, never Verified or Refuted. Noticed by budget-hit accounting; budget_unknown_total (§7).
  • I16 and I17: bounded model checking reports only "holds up to bound k", and k-induction says Verified only if base and step are both unsat. Noticed by a result-tagging audit and a two-obligation gate; bmc_overclaim, kind_step_only (§7).
  • I18: old(e) in a postcondition means the value captured at procedure entry. Noticed by an old-capture audit; old_capture_error (§7).

What breaks in production

The failure table names classes, not numbers, so they are cited by name (Failure Modes & Recovery).

False Verified. A known-buggy program passes. Root cause: a wrong weakest-precondition rule, a dropped frame, a bad encoding, or a solver bug. Detection: the soundness corpus and a dual-solver check. Recovery: none automatic; bisect the pass, add a regression fixture (Failure Modes: False Verified, I1). It is a release blocker (Failure Modes recovery philosophy).

Spurious Refuted. A correct program is refuted with a counterexample that is not a real run. Root cause: an over-constrained encoding or a reconstruction bug. Detection: the spuriousness re-check and differential tests. Recovery: downgrade to Unknown automatically, then fix the encoding or reconstruction (Failure Modes: Spurious Refuted, I11).

Hang. No progress. Root causes: a matching loop, a residual cycle in the graph, an unbounded k or fixpoint. Detection: the time budget, the acyclicity check and the widening flag. Recovery: budget expiry returns Unknown; a person inspects triggers or the graph (Failure Modes: Hang, I5, I13, I15).

Frame hole. A call site assumes too much because a callee under-declared modifies. Detection: the conformance VC. Recovery: the lying method is Refuted, and the author tightens the frame (Failure Modes: Frame hole, I14).

Over-claim from BMC or k-induction. A bounded result is read as a proof, or the step is taken without the base case. Detection: the bound-tag and two-obligation audits. Recovery: tag the bound or add the base case (Failure Modes: Over-claim, I16, I17).

Threats worth knowing (Threat Model): T2 a false Verified from a dropped frame, a bad rule or a wrong encoding is the cardinal threat, met by the soundness corpus, a dual-solver check, an external re-check of dumped SMT and differential tests against Dafny. T4 a bug in the solver itself, a member of the trusted base, is met by cross-checking two solvers and, later, proof mode. T3 an adversarial trigger causing a matching loop is met by the I10 check and a time budget. T5 a lying modifies clause is met by the conformance VC (I14). The blueprint's stance: it is trusted to refuse and advisory when it accepts incompleteness, so every mitigation favors a false Unknown over a false Verified (Threat Model).

The blueprint disagrees with itself in places, and both sides are given:

  • Per-procedure cost. Item 1 prices one procedure at 5 x 10 s = 50 s, so 72 fit in an hour; item 8 prices a 100-procedure program at "5,000 s (72 procedures × 70 s each)" and one edited procedure at 50 s (Capacity Model items 1 and 8).
  • Meaning of "Phase 0". §1 calls the whole pipeline the "Phase 0 deliverable", while §12 titles Phase 0 as the repo skeleton, syntax and parser, the first of 12 phases (§1, §12).

How it compares

  • Dafny goes through Boogie to Z3 with its own language, ghost code, sequences and sets. That is right when the source language is Dafny and the team wants a batteries-included experience (Comparative Architecture Table).
  • Why3 discharges goals through many provers, including Coq and Isabelle. That is right when heterogeneous provers or a machine-checked proof are the deliverable (Comparative Architecture Table).
  • Frama-C/WP targets C with the ACSL specification language and a precise memory model. That is right when the subject is existing C code (Comparative Architecture Table).
  • Viper uses fractional permissions to reason about aliased heap. That is right when aliased mutable heap is unavoidable, the regime this design defers (Comparative Architecture Table, ADR-11).
  • SPARK/GNATprove relies on Ada's ownership model to remove aliasing in the language itself. That is right when the target is Ada and its no-aliasing semantics are acceptable (Comparative Architecture Table).

Questions to test yourself

  1. The loop-cut rule (§8.3) asserts I on entry, havocs the modified variables, and then assumes I. If the havoc set under-approximates the actual modified set, which invariant is violated first — I4, I14, or I1 — and what is the exact execution that witnesses the false Verified? (§8.3, Phase 2, I14, I1, P4) — Hint: §8.3 for the cut, §8.7 for the frame violation, then I14 and MM4.
  2. The block-equation compacted VC (§8.4) introduces one fresh predicate per block. If two blocks share a successor and that successor's block predicate is referenced from both block equations, trace exactly how structural sharing prevents the exponential blowup — and explain why naive WP applied to a binary-branch tree of depth 10 produces 2^10 copies of the postcondition instead. (Phase 4, ADR-07, I6, MM1) — Hint: §8.4 and Capacity Model item 2.
  3. The SMT encoding emits (assert (not VC)) (check-sat). If the VC contains a division expression a / b and the div_nonzero obligation was correctly emitted in Phase 2 but the encoding of division in Phase 5 uses the SMT div function (total, defined at zero) without conditioning, is the result sound? Construct a counterexample or prove soundness. (Phase 2, Phase 5, ADR-09, I1, §8.7 division-by-zero example) — Hint: §8.7's division bullet and §17's edge cases.
  4. The three engines (deductive, BMC, k-induction) share the same VIR but use it differently: the deductive engine uses the invariant-cut CFG, BMC uses the original transition relation, and k-induction also uses the raw transition. Explain why k-induction using the invariant-cut CFG would be unsound (not merely incomplete), and then explain why BMC using the cut CFG would be both unsound and produce wrong counterexamples. (Phase 9, Phase 10, Phase 11, ADR-19, ADR-20, I17, MM2) — Hint: MM2 and MM9, then §21 and §22.
  5. The Verified verdict is defined as "every VC is unsat within budget." A procedure with 5 VCs where 4 are unsat and 1 is Unknown(Timeout) returns Unknown, not Verified. Explain why this is the correct and sound behavior with reference to P1 and I15, and identify the one scenario where a legitimate user might argue this is too conservative (and how the response documents that position). (§6 P1, I15, Phase 7, §4 per-VC solver budget, MM6) — Hint: P1, I15 and the per-VC budget row of §4.

If you only remember three things

Never say Verified unless every obligation was proved within budget, because a timeout, a malformed encoding or an unsupported feature must come back as Unknown (P1, I15). Cut each loop and replace each call with its contract, so the formula stays small and each procedure is proved against contracts, not bodies (MM2, MM3, I6). Keep the verifier honest about its own trust, through the soundness corpus, the frame check and the re-check of every counterexample and inferred invariant (P5, I1, I14, I11, MM10).

Words used here

  • Verification condition (VC): a logical formula whose validity means a program obligation holds (Glossary).
  • Weakest precondition: what must hold before a command so that a given condition holds after (Glossary, §8.2).
  • Guarded command: assume, assert, havoc, assignment, sequence or choice, the IR's command set (Glossary).
  • Passification: rewriting into assignment-free, acyclic form so weakest preconditions are linear (Glossary, MM1).
  • Dynamic single assignment: each variable version is defined once (Glossary, I4).
  • Loop invariant: a statement true on every pass through a loop (Glossary).
  • Frame / modifies: the locations a procedure may change; the basis of modular calls (Glossary, P4).
  • Trusted computing base: what you must trust to believe Verified: VCGen, encode and solver (Glossary, P5).
  • Soundness: never calling a false program verified; incompleteness is allowed (Glossary, MM6).
  • Trigger / E-matching: a pattern telling the solver when to instantiate a quantifier (Glossary, MM7).
  • Matching loop: a trigger that regenerates its own matches and never stops (Glossary, §8.7).
  • Counterexample: a concrete model showing an obligation can fail, mapped to source (Glossary).
  • Houdini: pruning a set of candidate invariants down to those that hold together (Glossary, ADR-22).
