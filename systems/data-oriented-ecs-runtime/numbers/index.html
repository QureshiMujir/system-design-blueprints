4.4 Scaling Assumptions

  • Vertical scaling only: more cores → higher parallel system throughput.
  • Archetype fragmentation degrades iteration; guidance: ≤ 1000 archetypes for sustained throughput targets.
  • Entity count scales linearly with memory; no sharding or streaming in scope.
  • Component type count bounded by Access bitset width; 65 536 components = 1 KB bitset per system.

Back-of-Envelope Capacity Model

Numbers an expert computes before designing, each derived from §4.

  • C1 — Entity metadata memory. 10 M entities × 24 B/EntityMeta (§4.1) = ~240 MB for the entities table — the floor before any component data.
  • C2 — Column iteration time. ≥ 2 GB/s/core (§4.1): iterating one 4-byte component over 1 M entities streams 4 MB ⇒ ~2 ms, matching the ≤ 2 ms p50 query target (§4.1) and confirming memory bandwidth, not compute, is the limit.
  • C3 — Component memory overhead. ≤ 2× raw size (§4.1): a 16-byte component over 1 M entities = 16 MB raw ⇒ ≤ 32 MB including the column BlobVec + tick vectors (added/changed ticks).
  • C4 — Access bitset size. 2 × (65 536 / 64) words = 2 × 1024 × 8 B = 16 KB... actually 2 × 1024 u64 words = 16 KB per fully-sized access set; §4.1's "1 KB at 64K components" counts a single read-or-write bitset (65 536/64 = 1024 words = 8 KB) — the per-system access footprint is small enough to compare cheaply at schedule build.
  • C5 — Spawn/migrate cost. ≤ 500 ns/entity amortized (§4.1): inserting a component is an O(1) archetype-edge lookup (MM4) plus a column move; at 5 M entity ops/s (§4.1) the free-list allocator never syscalls.
  • C6 — Command drain rate. ≤ 100 ns/command (§4.1) via type-erased fn-pointer dispatch: a frame deferring 10 k structural changes drains in ~1 ms at the next sync point (MM5).
  • C7 — Parallel speedup ceiling. ≥ 3.5× on 8 cores for 4 disjoint systems (§4.1): bounded by the critical path of conflicting systems, not core count — non-disjoint systems serialize (MM6).
  • C8 — Tick wrap period. u32 ticks at 60 Hz = 2³² / 60 / 86400 / 365 ≈ 2.3 years (§4.1) before wrap; wrap-aware comparison means even then there's no failure (MM8, §4.3).
  • C9 — Change-detection overhead. ≤ 10% vs unfiltered (§4.1): one tick compare per row in the hot loop is a predictable branch, so a filtered query over 1 M entities stays near the ~2 ms baseline (C2).
  • C10 — Archetype fragmentation budget. ≤ 1000 archetypes for sustained throughput (§4.4): beyond this, iteration spreads across many small columns and per-archetype fixed costs dominate (MM10).
  • C11 — World shutdown cost. ≤ 10 ms at 1 M entities (§4.1): drop_in_place via each BlobVec's stored drop fn frees all columns; type erasure (MM9) means drop is data-driven, not per-type code.
  • C12 — Schedule build cost. ≤ 1 ms for 100 systems (§4.1): pairwise access-bitset conflict checks are O(systems² × bitset-words) = 100² × 1024 ≈ 10 M word-ops — a one-time startup cost, not per-frame (MM6).
