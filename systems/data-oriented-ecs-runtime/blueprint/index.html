1. Goal

1.1 What Is Built

A data-oriented Entity-Component-System (ECS) runtime implemented in Rust from first principles. Entities are 64-bit generational handles; components are stored column-wise in archetype tables (struct-of-arrays) for cache-friendly iteration; queries fetch matching archetype columns at compile-resolved types; systems are scheduled onto a thread pool with automatic conflict-based parallelism and deferred structural mutation via command buffers.

Multithreaded executor (work-stealing pool) Physics, renderer, audio subsystems

Runnable examples (n-body, boids, particles) Persistence, snapshotting, replay

Single process, in-memory only. No FFI surface committed beyond Rust-stable ABI. No persistence layer, no network stack, no asset pipeline.

1.3 Non-Goals (Explicit)

  • No scripting VM or dynamic component registration from non-Rust code.
  • No scene serialisation; no reflection-driven asset pipeline.
  • No rendering backend; examples use terminal or numeric output only.
  • No SIMD acceleration of inner loops (documented deferral to Phase 14+ extensions).
  • No distributed/multi-process world sharding.
  • No game engine shell; only the ECS runtime kernel.

1.4 Intended Deployment Model

  • Library crate embedded in a game engine, simulation runtime, or benchmark harness.
  • Caller owns the main thread; World and Schedule live on the stack or heap in a single process.
  • Thread pool spawned once at startup; size = physical core count by default, configurable.
  • No daemon, no service, no IPC — purely in-process.

1.9 Language Rationale — Rust

Data-oriented design requires explicit memory layout control (SoA columns, contiguous chunks, alignment guarantees). Rust provides:

  • std::alloc::Layout and std::ptr primitives → BlobVec can store any T without boxing.
  • Borrow model maps directly onto query access-conflict analysis: &T / &mut T exclusivity rules are isomorphic to read/write conflict detection in Access<ComponentId>.
  • unsafe is lexically bounded → type-erased storage (BlobVec) hides unsafety behind a safe typed API; miri validates it.
  • Thread pool story (rayon-style work-stealing, or crossbeam channels) without a GC stall; no stop-the-world pauses that would corrupt frame-time budgets.
  • Zero-cost abstractions: query iteration compiles to tight column-pointer loops with no per-entity virtual dispatch.

Model systems: Bevy ECS, flecs (Sander Mertens), EnTT (Vittorio Romeo).

2.2 Historical and Architectural Significance

  • ECS displaced OOP inheritance hierarchies in game development (Unity DOTS, Unreal Mass); the data-oriented argument won on hardware grounds (cache misses dominate at scale).
  • Archetype-based ECS (vs pure sparse-set, vs bitfield) is the dominant production model: Bevy, flecs, Specs (Legion hybrid) all converged here.
  • The access-conflict → automatic parallelism pipeline is the industry answer to the 'dependency hell' of explicit threading in game loops.
  • Generational indices are a template for safe arena allocation appearing in databases (row versioning), compilers (IR node arenas), and language runtimes (GC object handles).

2.3 Engineering Muscles Developed

  • Unsafe Rust mastery — BlobVec, swap_remove, raw pointer arithmetic, drop discipline.
  • Type system gymnastics — WorldQuery/Fetch GAT-style trait chains, blanket SystemParam impls, phantom lifetime threading.
  • Performance engineering — cache-line analysis, profiling with perf/DHAT, benchmark-driven iteration.
  • Concurrency correctness — access-bitset conflict detection, atomic Tick increments, determinism testing.
  • Compiler cooperation — designing for monomorphisation; avoiding dyn where hot; profile-guided layout decisions.
  • Formal specification — invariant tables (I1–I10), ADR discipline, phase-locked design contracts.

2.6 Capability Calibration

Building this runtime to production quality demonstrates: unsafe correctness under miri; benchmark-driven cache analysis; safe concurrency via access analysis (not ad-hoc locking); type-system-driven API ergonomics; and formal scheduling theory applied to a real executor. It is one of the highest-leverage single-codebase exercises in systems Rust, yielding knowledge directly applicable to database kernels, language runtimes, and OS schedulers.

2.7 What Mastery Looks Like

After building this the engineer holds these exact competencies, each tied to a phase:

  • Data-oriented (SoA) design (Phase 1–3): can explain why struct-of-arrays archetype columns beat array-of-structs for component iteration, and measure the cache-locality difference.
  • Type-erased storage (Phase 2): can implement a BlobVec (type-erased Vec<u8> + Layout + drop) safely and validate it under Miri.
  • Archetype graph (Phase 3–4): can model entity composition as a graph with memoized add/remove edges and reason about O(1) structural transitions.
  • Generational entity handles (Phase 1): can implement Entity{index, generation} and explain how the generation defeats the ABA / stale-handle problem (P5).
  • Zero-cost queries (Phase 7): can derive component access at compile time via traits and explain why this avoids per-entity dynamic dispatch.
  • Static access-conflict scheduling (Phase 9–10, 12): can compute read/write access bitsets and build a parallel schedule that proves disjointness before running, with no runtime locks.
  • Deferred structural mutation (Phase 11): can implement a command buffer + apply_deferred to avoid mid-iteration mutation hazards (I6).
  • Change detection (Phase 8): can implement tick-based per-component change tracking with wrap-aware comparison and bounded overhead.

3.2 Subsystem Descriptions

World — top-level owner of all live state. Holds Entities, Components registry, Storages (Archetypes + Tables + SparseSets), Resources, and the global change_tick: AtomicU32. Entry point for all structural mutations and query execution. Single-owner; no interior mutability outside Tick increments. Trust boundary: all safe-API callers; unsafe operations are encapsulated inside storage primitives.

Entities / EntityMeta — free-list allocator over (index: u32, generation: NonZeroU32) pairs. EntityMeta maps each live index to EntityLocation { archetype_id, table_id, table_row, archetype_row }. Bump-on-free defeats ABA (I1). Data in: spawn/despawn calls. Data out: EntityLocation used by every component access path. Concurrency boundary: mutable only via exclusive &mut World or deferred Commands; not accessed concurrently during system execution.

Components Registry — assigns monotonically increasing ComponentId(usize) at register_component<T> time. Stores ComponentInfo { id, name, layout: Layout, drop: Option<unsafe fn(*mut u8)>, storage: StorageType }. Read-only after world construction in steady state. Data out: ComponentId used as the key into all column maps.

Storages / Archetypes / Tables — the core SoA store. Each Archetype is a unique sorted set of ComponentId values; it references one Table. A Table holds one Column (a BlobVec + tick vectors) per component, plus a Vec<Entity>. All columns in a table maintain equal length (I4). Archetype graph Edges memoize structural transitions (add/remove one component → next ArchetypeId). Data in: migration calls from spawn/insert/remove. Data out: raw column pointers consumed by Fetch implementations. Concurrency boundary: tables are partitioned by archetype; disjoint archetypes can be iterated in parallel without synchronization.

SparseSets — per-component SparseSet<Entity, Row> for StorageType::SparseSet components. Used for high-churn components (tags, transient state) that would cause excessive archetype fragmentation if table-stored. Data in: insert/remove on sparse components. Data out: component value pointer for Fetch. Concurrency boundary: same access-conflict rules as tables; sparse components appear in Access bitsets.

Resources — ComponentId-like ResourceId-keyed BlobVec-of-one store. Holds Res<T> / ResMut<T> singletons. Not tied to any entity. Data in: World::insert_resource<T>. Data out: SystemParam fetch for Res<T> / ResMut<T>. Concurrency boundary: resource access appears in SystemMeta.resource_access; conflict analysis gates concurrent system execution.

Query<D, F> / QueryState — cached list of matched ArchetypeIds computed at first use (or on new archetype insertion). Fetch implementations extract typed column pointers per matched archetype; iteration is a two-level loop (archetype × row). QueryFilter prunes archetypes at match time and rows at iteration time. Data in: &World (read-only columns) or &mut World (exclusive columns). Data out: typed component references per entity. No allocations in the hot iteration path.

Commands / CommandQueue — type-erased deferred command store. EntityCommands enqueue spawn/insert/remove/despawn; CommandQueue::apply drains in strict enqueue order (I8) at sync points inserted by the Schedule. Prevents structural mutation mid-iteration (I6, P2). Data in: system execution via Commands SystemParam. Data out: World mutations applied after all systems in a sync-set finish.

Schedule / MultiThreadedExecutor — builds a DAG from explicit before/after ordering edges and inferred conflict edges (overlapping write sets). Topological sort determines execution order. Executor tracks in-flight Access sets; launches a system when its access is disjoint from all running systems (I5). !Send systems pinned to main thread. apply_deferred barriers inserted at explicit sync points. Data in: system registrations, ordering constraints. Data out: dispatch signals to thread pool.

4.4 Scaling Assumptions

  • Vertical scaling only: more cores → higher parallel system throughput.
  • Archetype fragmentation degrades iteration; guidance: ≤ 1000 archetypes for sustained throughput targets.
  • Entity count scales linearly with memory; no sharding or streaming in scope.
  • Component type count bounded by Access bitset width; 65 536 components = 1 KB bitset per system.

6. Design Principles

P1. Data-Oriented Layout

Statement. Components live in contiguous SoA columns (Column = BlobVec + tick vectors); iteration is a linear scan of typed memory.

Explanation. For a given component type T, all values for entities in one archetype occupy a single allocation, element i at offset i * size_of::<T>(). A query iterating that archetype accesses memory sequentially; the hardware prefetcher saturates bandwidth with zero pointer chasing.

Tradeoffs.

  • Add/remove triggers a full row migration (Phase 5); justified because structural changes are rare vs. iteration frequency.
  • Archetype fragmentation (many small archetypes with few entities) reduces column utilisation; mitigated by P3's identity rule and Phase 4 graph pruning.
  • Large components (T: !Copy, large size_of) still benefit from sequential access vs. pointer-chased heap objects.

Operational implications.

  • Bench column width vs. cache line (64 B); prefer T with size_of <= 64.
  • Phase 3 Column capacity growth must preserve alignment (BlobVec uses Layout).
  • doecs-bench fragmentation bench validates throughput degrades gracefully, not catastrophically.

Violation consequence. Storing components in Box<dyn Any> per-entity (AoS) causes one cache miss per entity per component access; observed 5–30× throughput regression in EnTT AoS vs. SoA benchmarks.

P2. Structural Change Is Deferred and Explicit

Statement. spawn, despawn, insert, remove never execute mid-query; they queue into CommandQueue and flush at explicit apply_deferred sync points.

Explanation. A live Query iterates over archetype table rows by raw pointer. A concurrent structural mutation (insert<C> on entity E) would move E's row to a different table, invalidating the pointer and corrupting row-alignment invariant I4.

Tradeoffs.

  • Deferred commands mean state is not immediately visible to systems running after the issuing system in the same schedule tick (until apply_deferred).
  • Sync points serialise the executor; Phase 12 inserts them only where deferred writes are actually needed.
  • World::spawn / World::insert are still available for exclusive systems (&mut World) where no concurrent iteration exists (Phase 14).

Operational implications.

  • CommandQueue::apply_deferred drains in strict FIFO order (I8); test ordering with deterministic command sequences.
  • Excessive sync points collapse parallel stages; profile Schedule DAG for sync-point density.

Violation consequence. Calling world.insert_component on an entity mid-iteration invalidates column raw pointers, triggering undefined behaviour in BlobVec; miri detects this as a stacked-borrows violation.

P3. Archetype Identity Is the Component Set

Statement. An entity's archetype is uniquely determined by the sorted set of ComponentIds it currently possesses; no other property (creation order, entity index) influences storage location.

Explanation. The archetype lookup key is &[ComponentId] (sorted). get_or_insert_archetype hashes the set; matching entities share table rows. Edges (Edges) memoize single-component add/remove transitions, reducing transition cost to one pointer dereference.

Tradeoffs.

  • Two entities with the same component set are always co-located, enabling SIMD and vectorised loops.
  • Entities with volatile component membership (frequent add/remove of tag components) generate many archetype migrations; mitigate with StorageType::SparseSet for those components (Phase 6).

Operational implications.

  • Tag components (zero-sized) still shift archetype; consider SparseSet storage for boolean-flag components.
  • Phase 4 archetype-component index maps ComponentId → Vec<ArchetypeId>; must be updated on every get_or_insert_archetype.

Violation consequence. Allowing two archetypes with the same component set creates duplicate rows for the same entity, breaking I2 and I7; queries would double-iterate entities.

P4. Access-Conflict Analysis Is the Parallelism Engine

Statement. Two systems run concurrently if and only if their Access<ComponentId> and Access<ResourceId> sets do not conflict (write/write or read/write overlap).

Explanation. SystemMeta accumulates component_access: Access<ComponentId> and resource_access: Access<ResourceId> as FixedBitSet pairs during SystemParam::init_access. MultiThreadedExecutor checks bitset intersection before dispatching; disjoint sets run in parallel, conflicting sets are serialised.

Tradeoffs.

  • Static access declaration (compile-time via SystemParam) means the executor requires no runtime lock per component; zero overhead during iteration.
  • reads_all / writes_all flags (e.g. &mut World) force full serialisation; use only in exclusive systems.
  • False positives (over-declared access) reduce parallelism; QueryState narrows access to matched archetypes where possible.

Operational implications.

  • Phase 10 validates no within-system aliasing (e.g. Query<&mut T> + Query<&T> for same T in one system → compile-time panic).
  • Phase 12 conflict graph edge = pair of systems with intersecting access; edge implies ordering or sync point.

Violation consequence. Two systems with aliased mutable component access running concurrently produce data races; undefined behaviour in safe Rust only if BlobVec borrows are not guarded; miri + loom detect races in Phase 13 tests.

P5. Generational Handles

Statement. Entity { index: u32, generation: NonZeroU32 } — a recycled index increments generation so old handles silently fail, never silently succeed on a new occupant.

Explanation. On despawn, EntityMeta.generation is bumped. All subsequent accesses validate handle.generation == meta.generation; stale handles return Err/None. NonZeroU32 generation enables Option<Entity> niche optimisation (8 bytes total vs. 12).

Tradeoffs.

  • 32-bit generation wraps at 2³²; after exactly 2³² despawn-respawn cycles of the same index, ABA recurs. Practical threshold exceeds any game session.
  • NonZeroU32 requires generation to start at 1; initial EntityMeta uses generation=1, free-list bumps to ≥2 after first recycle.

Operational implications.

  • Free-list in Entities stores index only; generation stored in EntityMeta; compact free-list layout.
  • world.get_entity(handle) returns Option<EntityRef> — use ? idiom; never unwrap without documentation.

Violation consequence. Without generation guard: after entity A is despawned and a new entity B occupies A's index, a system holding A's old Entity value silently reads B's components — silent logical corruption, undetectable without generational check.

P6. Zero-Cost Queries

Statement. Query iteration compiles to a tight loop over typed raw slices with no per-entity virtual dispatch, dynamic type checks, or heap allocation.

Explanation. QueryState holds a Vec<ArchetypeId> matched at schedule build time (updated lazily on new archetypes). Per matched archetype, Fetch resolves column pointers once per table then iterates by pointer increment. No dyn Trait in the hot path; generics are monomorphised.

Tradeoffs.

  • Lazy archetype matching (check archetypes.len() vs. last_matched) adds a branch per iter() call; negligible vs. iteration body.
  • Complex multi-component queries increase monomorphised code size (LLVM code bloat); mitigated by LTO.
  • Option<&T> fetch checks per entity whether component is present; acceptable for optional components but avoid in the absolute hot path.

Operational implications.

  • Benchmark with doecs-bench iteration bench after each storage change; regression threshold 5% throughput.
  • Verify LLVM output (cargo asm) for tight queries: expect sequential load, no calls, vectorisable loop body.

Violation consequence. Inserting a dyn Trait dispatch or a HashMap lookup per entity in the query path collapses throughput to pointer-chased AoS levels; profiling shows cache miss rate > 50%.

P7. One Canonical Location per Entity

Statement. An entity occupies exactly one archetype row and one table row at any instant; storage never duplicates it.

Explanation. EntityMeta.location: EntityLocation is the single source of truth. On migration (Phase 5), the source row is swap-removed, destination row is pushed, EntityMeta updated atomically (under &mut World). I9 requires the swapped entity's EntityMeta to be updated in the same operation.

Tradeoffs.

  • Row migration is O(components) per structural change; write amplification for entities with many components.
  • No duplicate storage means consistency is trivially maintained; no need for invalidation protocols.

Operational implications.

  • swap_remove from source table must update moved entity's EntityLocation (I9); test with entities at non-last positions.
  • EntityLocation must be updated before any Query can observe the entity in the new archetype.

Violation consequence. Failing to update the moved entity's EntityLocation after swap-remove leaves a dangling EntityLocation pointing to the wrong row; query accesses return garbage data from the wrong column index.

P8. Determinism of the Single-Threaded Schedule

Statement. The MultiThreadedExecutor must produce results identical to executing all systems in their scheduled topological order single-threaded.

Explanation. Parallelism is an optimisation on top of a defined serial order. Systems that are unordered but non-conflicting may execute concurrently; their outputs must be individually correct (no shared mutable state), so any interleaving produces the same result as serial. Conflicting systems are forced into topological order by the DAG.

Tradeoffs.

  • Ambiguous system pairs (unordered + conflicting) are detected at schedule build time; the engine panics or warns, forcing the user to add explicit ordering. No silent non-determinism.
  • Deterministic fallback (single-threaded executor) in tests ensures Phase 13 bugs are isolatable.

Operational implications.

  • Phase 12 ambiguity detection emits a list of conflicting unordered pairs; user adds before/after constraints.
  • Conformance test: run 1000-tick simulation on both executors; compare world state snapshot.

Violation consequence. Non-deterministic parallel execution produces flaky tests and irreproducible bugs; any race on component data that passes by accident in one run fails in another with different thread scheduling.

P9. Unsafe Is Encapsulated

Statement. All type-erased storage (BlobVec, Column, Table) hides unsafety behind checked typed APIs; public-facing crate surfaces are safe.

Explanation. BlobVec::push<T>, BlobVec::get<T>, BlobVec::swap_remove<T> — the typed wrappers — validate that T matches the stored Layout (size + align) in debug mode. The unsafe block surface area is confined to doecs-storage; all callers in doecs-archetype, doecs-query use the typed wrappers.

Tradeoffs.

  • Debug-mode layout checks add a branch per access; acceptable overhead for correctness assurance.
  • Miri integration test must cover every unsafe fn in doecs-storage to achieve P9 guarantees.
  • unsafe impl Send/Sync on BlobVec requires external caller to ensure no concurrent mutable access (guarded by P4 access sets).

Operational implications.

  • Every unsafe block carries a // SAFETY: comment stating the invariant that makes it sound.
  • CI runs cargo miri test -p doecs-storage on every PR.

Violation consequence. Unchecked type erasure (calling get::<U> where T was stored) produces misaligned reads and type-pun UB; miri detects immediately; release build may silently corrupt data for hours.

P10. Explicit Change Semantics

Statement. Change detection is tick-based and fully observable; mutations are never inferred heuristically.

Explanation. Every Column stores added_ticks: Vec<Tick> and changed_ticks: Vec<Tick> parallel to the data array. World.change_tick increments each schedule run. Mut<T>::deref_mut records the current tick into changed_ticks[row]. Added<T> / Changed<T> query filters compare stored tick with last_run_tick using wrap-aware is_newer_than.

Tradeoffs.

  • Two additional Vec<Tick> per column add memory overhead proportional to entity count × tracked-component count; acceptable given Tick is 4 bytes.
  • Tick wrap (32-bit) at ~4 billion ticks is handled by is_newer_than signed-difference comparison; correctness requires no query to go more than 2³¹ ticks without running.

Operational implications.

  • I7 (changed >= added) asserted in debug; enforce in Column::push by recording same tick for both on insertion.
  • SystemMeta.last_run_tick updated at system start; fetch in Fetch::init.
  • Components in StorageType::SparseSet must also carry change ticks (Phase 6 integration).

Violation consequence. Using pointer comparison or hash-based dirty flags instead of ticks produces false positives after memory reuse (old pointer value matches new allocation) and missed detections after silent overwrites, breaking reactive systems and event-based optimisations.

P11. Storage Policy Is a Per-Component Choice, Not a Global One

Statement. Each component type declares its own StorageType (Table or SparseSet, ADR-06/ADR-07); the engine never forces one storage discipline on the whole world.

Explanation. Component::STORAGE_TYPE defaults to Table (archetype SoA columns); a type can opt into SparseSet (ComponentSparseSet, Phase 6/17) when it churns too fast for archetype moves to be worth paying. Both paths expose the same Storages::get_component read path (Phase 6), so query code is storage-agnostic.

Tradeoffs.

  • Table wins on iteration throughput (SoA, P1) but pays a migration cost on every add/remove (P2); SparseSet wins on churn cost but pays a second cache miss per access (parallel entities array, Phase 6 §17.7).
  • Mixing both policies in one world means the archetype graph (P3) only ever reflects Table components — SparseSet components are invisible to it by design, which simplifies archetype identity but means two lookup paths must both be checked in general-purpose tooling (Storages::get_component).

Operational implications.

  • The churn-policy guidance table (Phase 6 §17.7) is the operator-facing decision aid: >50% population + sequential access → Table; <20% population + high churn → SparseSet.
  • Changing a component's STORAGE_TYPE is a breaking schema change (Compatibility & Versioning) — it changes which crate owns the data and invalidates any serialized archetype snapshot.

Violation consequence. Forcing every component through the archetype graph (no SparseSet escape hatch) turns high-churn marker components (e.g., "just spawned this frame") into constant archetype fragmentation (MM10); forcing every component into sparse sets loses the SoA iteration throughput that P1 depends on.

P12. Resources Are World-Scoped Singletons, Access-Tracked Like Components

Statement. A Resource is exactly one value per World (not per-entity), but it participates in the same Access/conflict-analysis machinery as component reads and writes (P4).

Explanation. Resources (Phase 9/20) stores one BlobVec-of-one per registered type, keyed by ResourceId; Res<T>/ResMut<T> add ResourceId(T) to a system's Access::reads/writes exactly as a component fetch would, so the scheduler (Phase 12/23) treats a resource conflict identically to a component conflict when building the conflict graph.

Tradeoffs.

  • Treating resources uniformly with components means one Access type and one conflict-detection code path (simplicity), at the cost of resources being unable to express per-entity granularity — two systems that touch unrelated entities but the same resource still conflict.
  • A resource read is O(1) (direct ResourceId index), cheaper than any query, which makes resources attractive for cross-cutting state (frame counters, input state) at the cost of encouraging global-state coupling if overused.

Operational implications.

  • Local<T> (Phase 9/20) is the escape hatch for per-system state that should not go through Access — it is invisible to the conflict scan by design (P4 §21.9 Failure Analysis if that invariant breaks).
  • Resource identity (ResourceId) is registration-order-dependent and must not be persisted across binary builds (see Compatibility & Versioning).

Violation consequence. Bypassing Access for a resource (e.g., raw unsafe access to Resources from inside a parallel system) reintroduces exactly the data race I5 exists to prevent, silently, because the scheduler's conflict graph never sees the access.

Transition rules:

  • despawn bumps generation again (odd→even→odd next alloc); clears EntityMeta.

8.2 Component Registry Taxonomy

ComponentId(usize)  ──registered_at──►  ComponentInfo
                                           ├─ id: ComponentId
                                           ├─ name: &'static str
                                           ├─ layout: Layout  (size, align)
                                           ├─ drop: Option<unsafe fn(*mut u8)>
                                           └─ storage: StorageType { Table | SparseSet }

Registration grammar (pseudo-EBNF):

component_registration ::= register<T>
                          | register_with_descriptor(ComponentDescriptor)
ComponentDescriptor    ::= { name, layout, drop_fn, storage_type }

Constraints:

  • ComponentId is dense; assigned monotonically from 0; never reused within a World instance.
  • layout.size == 0 → ZST component; no BlobVec allocation; Column still tracks ticks.
  • drop == None → Copy-like type; BlobVec skip-drop path used.

8.3 Archetype Identity and Graph

Archetype = canonical label for a unique sorted ComponentId set.

ArchetypeId ──identifies──► Archetype
                               ├─ id: ArchetypeId
                               ├─ table_id: TableId
                               ├─ components: Box<[ComponentId]>  (sorted ascending)
                               └─ edges: Edges
                                           ├─ add: HashMap<ComponentId, ArchetypeId>
                                           └─ remove: HashMap<ComponentId, ArchetypeId>

Archetype graph invariants:

  • EMPTY archetype (id=0) is always present; no components; all freshly-spawned entities start here.
  • edges.add[C] = archetype obtained by inserting C into this component set.
  • edges.remove[C] = archetype obtained by removing C; must be present in the set.
  • Two archetypes are equal iff their sorted ComponentId slices are byte-equal.
  • get_or_insert_archetype is the only path to create a new archetype; it also creates the corresponding Table.

Archetype-component index: components_in_archetype: SparseArray<ComponentId, Vec<ArchetypeId>> — inverse map for query matching.

8.4 Table Storage Layout (SoA)

Table (TableId)
  ├─ entities: Vec<Entity>                     // row→entity map
  └─ columns: SparseArray<ComponentId, Column>
       └─ Column
            ├─ data: BlobVec          // raw bytes, stride=layout.size, align=layout.align
            ├─ added_ticks: Vec<Tick>
            └─ changed_ticks: Vec<Tick>

BlobVec layout invariant (I10):

BlobVec.ptr[i * layout.size .. (i+1) * layout.size]  ← component value at row i
// alignment: ptr base aligned to layout.align
// drop: called exactly once; either on swap_remove or on BlobVec::drop

Row alignment invariant (I4):

∀ Column c in Table t: c.data.len() == t.entities.len()
∀ Column c in Table t: c.added_ticks.len() == t.entities.len()
∀ Column c in Table t: c.changed_ticks.len() == t.entities.len()

swap_remove(row r):

  1. Copy last row's bytes to position r in every column.
  2. Truncate all columns by one.
  3. Update EntityMeta.location.table_row for the entity that was moved (I9).

8.5 SparseSet Storage Layout

Used for high-churn components (StorageType::SparseSet); no archetype move on add/remove.

SparseSet<Entity, Row>
  ├─ dense: Vec<(Entity, T)>         // packed values
  └─ sparse: Vec<Option<u32>>        // Entity.index → dense index

Access: O(1) read/write via sparse[entity.index] → dense slot. Removal: swap_remove from dense; update sparse for the moved entity. Archetype: sparse-set components still appear in an entity's archetype (P3), but the value lives in Storages::sparse_sets, not a Table column.

8.6 Query Semantics and Fetch Grammar

Query type: Query<D: QueryData, F: QueryFilter>

QueryState caches:

  • matched_archetypes: Vec<ArchetypeId> — archetypes that pass filter.
  • fetch_state: D::State — pre-fetched column pointers per archetype.
  • Updated lazily when archetypes.len() increases.

QueryData fetch grammar (EBNF):

QueryData  ::= &T | &mut T | Entity | Option<QueryData>
             | (QueryData, QueryData, ...)   -- tuple composition
QueryFilter ::= With<T> | Without<T> | Changed<T> | Added<T>
              | Or<(F, F, ...)> | ()

Fetch sequence per archetype (Phase 7):

  1. archetype_contains_all(required_ids) — filter test.
  2. F::filter_fetch(archetype, last_run, this_run) — change-filter gate.
  3. For each column id in D: table.get_column(id).data.ptr_at(row) → raw pointer.
  4. Iterate rows 0..table.entities.len(); yield typed reference from raw pointer.

Access derivation:

  • &T → reads.insert(ComponentId<T>)
  • &mut T → writes.insert(ComponentId<T>)
  • Option<&T> → reads.insert(ComponentId<T>) (optional; no archetype filter)
  • With<T> / Without<T> → no read/write bit; archetype filter only.

Conflict rule: reads_a ∩ writes_b ≠ ∅ OR writes_a ∩ writes_b ≠ ∅ → systems A and B conflict (I5).

8.7 Change Detection Model

Tick type: Tick(u32) — wraps at u32::MAX; wrap-aware comparison:

is_newer_than(a: Tick, b: Tick, last_run: Tick) →
    a.relative_to(last_run) > b.relative_to(last_run)
// relative_to: wrapping subtraction mod 2^32

Tick sources:

  • World.change_tick: AtomicU32 — incremented each Schedule::run.
  • last_run_tick stored per system in SystemMeta.
  • ComponentTicks.added set at insert-time tick.
  • ComponentTicks.changed set on DerefMut of Mut<T> / ResMut<T>.

Invariant I7: changed_tick >= added_tick (wrap-aware).

Change filter evaluation:

Filter Passes when
Added<T> component_ticks.added.is_newer_than(last_run, this_run)
Changed<T> component_ticks.changed.is_newer_than(last_run, this_run)
With<T> component in archetype (tick-independent)
Without<T> component absent from archetype

8.8 Command Buffer Execution Model

Deferred mutation pipeline (P2):

Show the original text diagram
System runs      ──enqueue──►  CommandQueue (type-erased fn ptrs + byte payloads)
                                    │
                           apply_deferred (sync point)
                                    │
                              drain in FIFO order (I8)
                                    │
                         ┌──────────┴──────────┐
                     spawn / insert          remove / despawn
                     → archetype migration   → archetype migration
                     → EntityMeta update     → generation bump

CommandQueue storage format:

CommandQueue ::= Vec<u8>  // byte blob
Entry         ::= [fn_ptr: usize][payload: N bytes aligned to T]

Type-erased command dispatch:

  • Each command written as (apply_fn, size, align, bytes).
  • apply_deferred casts fn_ptr, passes &mut World + payload pointer.
  • After drain, Vec is cleared; capacity retained for reuse.

Ordering guarantee: commands from a single system run in enqueue order; commands across concurrent systems are merged in system-completion order (deterministic under scheduler serialization).

8.10 Scheduler DAG Semantics

Schedule internal representation:

Schedule
  ├─ systems: Vec<Box<dyn System>>
  ├─ sets: Vec<SystemSet>
  ├─ ordering_edges: Vec<(NodeId, NodeId)>   // before/after constraints
  └─ compiled: CompiledSchedule
       ├─ topological_order: Vec<SystemId>
       ├─ sync_points: BTreeSet<usize>        // indices where apply_deferred fires
       └─ conflict_graph: DiGraph<SystemId>

DAG build steps:

  1. Collect ordering edges from before/after annotations and SystemSet membership.
  2. Add conflict edges (Phase 12) between systems with overlapping access.
  3. Topological sort (Kahn's algorithm); error on cycle.
  4. Insert apply_deferred nodes where commands must flush before dependent reads.
  5. Mark ambiguities (two systems with no ordering edge and no conflict): configurable warn/error.

Executor dispatch table:

Condition Action
System is !Send pin to main thread; skip thread pool
System accesses &mut World (exclusive) run alone; drain all in-flight
Access disjoint from all in-flight dispatch to thread pool immediately
Access conflicts with in-flight system enqueue; retry when in-flight completes
sync_point reached barrier: wait all in-flight, run apply_deferred

8.11 Events Double-Buffer Model

Events<T>
  ├─ events_a: Vec<EventInstance<T>>   // older buffer
  ├─ events_b: Vec<EventInstance<T>>   // current buffer
  ├─ a_start_event_count: usize
  └─ event_count: usize                // monotone counter

Buffer swap occurs each Schedule::run:

  • events_a is replaced by old events_b; events_b cleared.
  • EventReader::cursor stores last_event_count; reads events from both buffers newer than cursor.
  • Events older than 2 frames are dropped (TTL = 1 swap cycle).

EventReader iteration:

readable = [events_a, events_b].filter(|e| e.event_id.id >= reader.last_event_count)

8.12 Worked Example — Spawn, Migrate, Query, Despawn

Normal path (well-formed):

1. world.spawn((Position{x:0.0}, Velocity{dx:1.0}))
   → Entity{index:0, generation:1}
   → archetype A = {Position, Velocity}; table row 0
   → EntityMeta[0] = {gen:1, loc:{archetype:A, table:0, row:0}}

2. world.entity_mut(e).insert(Health{hp:100})
   → archetype graph: A.edges.add[Health] = B = {Health, Position, Velocity}
   → migrate row: copy Position+Velocity cols to table B, push Health col
   → EntityMeta[0].location updated to B row 0

3. Query<(&Position, &mut Velocity)> iteration
   → QueryState.matched_archetypes = [A, B]   (both have Position+Velocity)
   → for table B: fetch col ptr Position[0], col ptr Velocity[0]
   → yield (&Position{x:0.0}, Mut<Velocity{dx:1.0}>)
   → Mut deref_mut sets changed_tick = world.change_tick

4. world.despawn(e)
   → swap_remove row 0 in table B (no other entity → just truncate)
   → EntityMeta[0].generation bumped to 2 (now even/free)
   → entity added to free list

Failure path (stale handle):

1. let e = world.spawn(()).id();   // Entity{index:0, generation:1}
2. world.despawn(e);               // generation bumped to 2
3. world.entity(e)                 // I1: EntityMeta[0].generation=2 ≠ e.generation=1
   → Err(NoSuchEntity) or panic depending on API variant

12.6 Pitfalls

  • Generation = 0 re-entry: wrapping NonZeroU32 past u32::MAX produces None from NonZeroU32::new(0); must skip 0 or saturate. Root cause: naive generation.get().wrapping_add(1). Debug: add #[cfg(debug_assertions)] assert on wrap.
  • pending list corruption: double-free pushes index twice; next alloc produces duplicate entities. Root cause: missing alive-check in free. Detection: debug_assert!(!pending.contains(&index)) (O(n) debug only).
  • reserve vs alloc race: reserve pre-extends meta but does not bump len; later alloc may overlap. Root cause: len updated before location is set. Fix: track pending-but-unplaced separately.
  • EntityLocation::INVALID mistaken for real location: code path forgets to check sentinel before reading archetype/table ids. Detection: add EntityLocation::is_valid() guard in all consumers.
  • Index overflow at u32::MAX entities: meta.len() == u32::MAX as usize; next push panics on 32-bit or silently truncates index cast. Detection: explicit capacity check + error before push.

12.7 Performance Concerns

  • alloc fast path: pop pending (Vec::pop O(1)); amortised O(1).
  • Avoid contains via pending.contains in hot paths (O(n) scan); use generation-compare only.
  • meta Vec realloc: reserve capacity at World construction for expected entity count to avoid repeated doubling.
  • change_tick AtomicU32: Relaxed ordering sufficient for tick increment (no cross-thread data dependency on the tick value itself); stronger ordering only at query/system boundaries.
  • Entity is Copy + 8 bytes; pass by value, not reference, in all hot iteration paths.

12.8 Edge Cases

  • Zero entities world: alloc on empty meta; must push first slot correctly.
  • Single entity alloc + free + alloc: generation increments exactly once.
  • free called with Entity::PLACEHOLDER: must reject gracefully (generation mismatch or out-of-bounds).
  • Batch reserve(0): no-op, no allocation.
  • set_location called with entity that was freed between reservation and placement: generation mismatch detected.

Field Type Role

  • reserve(additional): if len + additional > capacity, grow by max(capacity, additional) doubling; realloc in-place where possible.
  • push(value: *mut u8): memcpy into slot at len; increment len; does NOT run drop (ownership moves in).
  • swap_remove(index) -> bool (was_last): drop slot index if drop.is_some(); if index != len-1, memcpy last slot into index (no drop on last); decrement len; return value tells caller to update EntityLocation for the moved entity (I9).
  • get_ptr(index) -> *mut u8: data.as_ptr().add(index * item_layout.size()), bounds-checked in debug. initialize_unchecked(index, value): write without drop (migration, old slot already moved-from). clear(): drop all, len = 0. Drop for BlobVec: drop 0..len then dealloc.
  • ZST (item_layout.size() == 0): no heap allocation, data = NonNull::dangling(), len tracks count, pointer arithmetic is a no-op.

Component trait — doecs-component/src/lib.rs: trait Component: Send + Sync + 'static { fn storage_type() -> StorageType { StorageType::Table } }; no blanket impl — users derive or impl explicitly.

Test harness (doecs-component/tests/, doecs-storage/tests/): register same type twice → same ComponentId; BlobVec push 1000 u64, verify via get_ptr; swap_remove middle element, verify last moved into gap and len decremented; drop-counting fixture (type incrementing static counter on Drop, clear → counter equals push count); ZST fixture push 100 units, len == 100, get_ptr stable dangling.

13.6 Pitfalls

  • Alignment miscalculation: alloc requires layout.align() ≥ 1 and must be power-of-two; manual size rounding-up to align before multiply. Root cause: using size * capacity without padding to alignment. Debug: ptr as usize % layout.align() != 0 assertion.
  • Double-drop on swap_remove: calling drop on the element being moved (the last element) after copying it to index. Root cause: running drop on last slot after memcpy instead of before copy. Detection: drop counter asserts ≤ N.
  • Move-semantics confusion: push transfers ownership (value pointer is moved-from after call); caller must not use the source after push. Root cause: no Rust borrow checker enforcement on raw pointers. Mitigation: API doc + // SAFETY: precondition.
  • Realloc invalidates stored pointers: any pointer derived from get_ptr before reserve is dangling after growth. Root cause: external pointer caching. Invariant: pointers valid only within a single method call scope.
  • ZST pointer arithmetic UB: data.as_ptr().add(index * 0) is always valid but offset_from between two ZST pointers is UB if they're different provenance. Root cause: mixing offset_from with ZST. Fix: special-case ZST path returning data.as_ptr() directly.

13.7 Performance Concerns

  • BlobVec::push inner loop: single memcpy + len++; no branching per call.

  • Avoid HashMap lookups in hot iteration paths; ComponentId is the dense integer used after registration.

14.6 Pitfalls

  • Column/tick desync on partial push failure: if BlobVec::push succeeds but tick Vec::push fails (OOM), column data and tick vectors have different lengths, violating I4. Mitigation: reserve tick vecs at same time as BlobVec::reserve; OOM is fatal anyway.

  • Row index stale after swap: caller caches table_row before swap_remove; row is now invalid after swap. Root cause: aliased index. Detection: generation-tag table rows (debug build only).
  • SparseArray grows unboundedly: ComponentIds are dense but first registration may be high-numbered; SparseArray pre-allocates up to max_id + 1 with None. Mitigate: register components before table construction; ComponentId starts at 0.

14.7 Performance Concerns

  • SoA layout: iterating over a single Column is a linear scan of BlobVec; cache-hostile access patterns (e.g., reading Position + Velocity) require two separate column pointer offsets per row — still faster than AoS due to no padding bytes from unrelated fields.
  • entities: Vec<Entity> acts as a parallel array; its access pattern mirrors the column iteration.
  • SparseArray::get is an array index (O(1)) with no hashing; hot path in query fetch.
  • allocate_row with N columns performs N BlobVec::push calls; amortised O(1) per column if capacity pre-reserved.
  • swap_remove_row cost scales with column count; prefer fewer columns per archetype (users should not over-component).
  • Vec::swap_remove on tick vecs is O(1); no branching for non-last row case.

15. Phase 4 — Archetype Model + Graph

15.1 Objectives

  • Define Archetype as a sorted Box<[ComponentId]> plus TableId, ArchetypeId, and Edges.
  • Build Archetypes registry: O(1) lookup by component-set hash, sequential ArchetypeId assignment.
  • Maintain archetype-component index: given ComponentId, enumerate all ArchetypeIds containing it (used by QueryState matching in Phase 7).
  • Memoize add/remove structural transitions in Edges so repeated insert/remove paths pay one map lookup, not a new archetype search.
  • Define ArchetypeId(0) as the empty archetype (zero components); every entity starts there at spawn before any component is written.
  • No entity data stored in this phase; delivers pure structural metadata.
  • Enforce P3: archetype identity is the component set; two entities with identical component sets share one Archetype.

15.2 Detailed Implementation Steps

Module layout: doecs-archetype/src/lib.rs (Archetypes, Archetype, ArchetypeId, public API); src/edges.rs (Edges, add/remove maps — ADR-09 memoized graph); src/archetype_index.rs (component_index inverse lookup).

16. Phase 5 — Spawn / Insert / Remove / Despawn + Migration

16.1 Objectives

  • Implement the four structural mutation operations on World: spawn, insert, remove, despawn.
  • insert/remove walk Archetype::edges and physically MOVE the entity row between source and destination Table via migrate_row.
  • After each row move: update EntityMeta.location for the migrated entity; update EntityMeta.location.table_row for the entity displaced by swap_remove (I9).
  • despawn: drop all component values, clear the table row, bump EntityMeta.generation by 1 (P5, I1).
  • Enforce I2 (entity in exactly one archetype at all times) and I4 (column alignment) throughout.
  • Invariant I6 satisfied by deferring all structural mutation to Commands in Phase 11; Phase 5 mutations are synchronous and safe only outside active iteration.

16.6 Pitfalls

  • Displaced entity location not updated after swap_remove — root cause: entities.swap_remove(row) returns the moved entity but caller skips EntityMeta update. Manifestation: query reads wrong row for the displaced entity; silent data corruption. Detection: after every migration, assert table.entities[row].location.table_row == row for all rows. Instrumentation: emit WARN if displaced entity location update is skipped.
  • Double-drop during migration — migrate_row copies bytes from src to dst using swap_remove_no_drop; if caller uses swap_remove (which calls drop) and then also runs column drop on dst, each value is dropped twice. Root cause: using drop-bearing swap_remove on source. Fix: use swap_remove_no_drop for migration, swap_remove_and_drop only for despawn or remove-without-return.
  • Insert of already-present Table component triggers unnecessary migration — naive implementation always walks edges and migrates. Root cause: no contains check before migration. Fix: if src_archetype.component_set.contains(cid) { overwrite_in_place } else { migrate }.
  • Generation wraps on u32 exhaustion — NonZeroU32 max = 4 294 967 295; if an entity is despawned and reallocated that many times, generation aliases. Manifestation: stale handle with generation 1 matches fresh allocation with generation 1. Recovery: if generation would overflow, mark slot permanently invalid (set generation to a sentinel, remove from free list permanently). Metric: generation_overflow_count.
  • added_ticks not set on new component — new columns pushed in allocate are uninitialized; if caller forgets to set added_ticks, Added<T> filter in Phase 8 behaves randomly. Fix: always set added_ticks = current_tick immediately after push in allocate. Assert added_ticks[row] != 0 after spawn.
  • Partial migration on multi-component bundle failure — if writing component N of M panics after components 1..N-1 already written to dst, entity is left in an inconsistent state. Fix: stage all writes; only commit (update EntityMeta) after all writes succeed. Use scopeguard or catch-unwind to roll back on panic.

16.7 Performance Concerns

  • migrate_row copies component bytes via ptr::copy_nonoverlapping per component — linear in component count; no allocation. For structs > 64 bytes, multiple cache lines touched per entity.
  • Batch spawn: resolve archetype once, call Table::reserve(n) to pre-allocate capacity, then tight loop with allocate + write. Avoids repeated realloc amortization overhead.
  • insert hot path (component already present): check component_set.contains before any archetype lookup — single bitset operation, avoids HashMap probe entirely.
  • Despawn in bulk: sort entities by table_row descending; process from highest row first so swap_remove indices remain valid.
  • OwningPtr passing of bundle components avoids intermediate Vec<u8> — zero heap allocation per component write.
  • swap_remove is O(1); never use remove (O(n)) on column vecs.

16.8 Edge Cases

  • insert with all-SparseSet bundle: no archetype migration; only SparseSets::insert calls.

  • ZST components (size == 0): BlobVec::swap_remove_no_drop is a no-op for bytes; tick vectors still have slots. allocate must still push a tick entry even for ZSTs.
  • Entity with no components (empty archetype): despawn has no columns to clear; only entities.free and generation bump.
  • Multi-component remove (not in Phase 5 scope; done via Commands): if implemented, must compute final component set in one step to avoid intermediate archetype allocations.

Method Complexity Behavior
insert(key, value) O(1) amortized absent: push dense+indices, set sparse; present: overwrite dense[sparse[key]]
remove(key) -> Option<V> O(1) absent → None; else swap_remove dense+indices, sparse[indices[last]] = pos, sparse[key] = MAX
get/get_mut(key) O(1) check sparse[key] != MAX; return &(mut )dense[sparse[key]]
contains(key) O(1) key.sparse_set_index() < sparse.len() && sparse[k] != MAX

len() O(1) dense.len()

Grow-on-demand: insert does if key.sparse_set_index() >= sparse.len() { sparse.resize(key.sparse_set_index()+1, u32::MAX) }.

ComponentSparseSet: dense_data: BlobVec (contiguous component bytes, item = ComponentInfo.layout); entities: Vec<Entity> parallel to dense_data; sparse: Vec<u32> (sparse[entity.index()] = dense slot, MAX = absent); added_ticks/changed_ticks: Vec<Tick> parallel to dense_data; component_info: ComponentInfo.

  • remove(entity) -> bool: swap_remove dense_data/entities/added_ticks/changed_ticks; update sparse[entities[slot]] = slot for the moved entity; sparse[entity.index()] = MAX.
  • get(entity) -> Option<Ptr>: bounds+sentinel check, pointer into dense_data. get_ticks(entity): same index path.

SparseSets registry: struct SparseSets { sets: SparseArray<ComponentId, ComponentSparseSet> } — dense Vec<Option<ComponentSparseSet>> indexed by ComponentId.0, grows on demand; get_or_insert(info), get(cid), get_mut(cid).

Storages::get_component(entity, cid, location) -> Option<Ptr> (Phase 7 preview): match ComponentInfo(cid).storage — Table → tables.get(location.table_id)?.get_column(cid)?.get(location.table_row); SparseSet → sparse_sets.get(cid)?.get(entity).

19.2 Detailed Implementation Steps

Tick arithmetic (doecs-change/src/tick.rs):

  • Tick(u32) wraps at u32::MAX.
  • is_newer_than(self, reference: Tick, now: Tick) -> bool: returns (self.0.wrapping_sub(reference.0)) < (now.0.wrapping_sub(reference.0)).
  • MAX_CHANGE_AGE = u32::MAX / 2: ticks older than half the range are treated as never-newer (avoids wrap ambiguity).
  • World::increment_change_tick(&mut self) -> Tick: fetch-add change_tick; called at start of each schedule execution.

Column tick vectors (doecs-storage/src/table.rs):

  • Column { data: BlobVec, added_ticks: Vec<Tick>, changed_ticks: Vec<Tick> }.

19.6 Pitfalls

  • Mut<T> eager tick write: if changed_tick is set on fetch rather than deref_mut, every iterated entity appears changed even without mutation. Root cause: wrong placement of tick-write. Detection: fixtures/change/no_mutation.ron fails.
  • last_run not updated between system runs: system re-runs and sees all previous mutations as new. Cause: QueryState.last_run not refreshed from SystemMeta.last_run. Fix: store last_run in SystemMeta; pass into init_fetch.
  • Tick overflow / MAX_CHANGE_AGE violation: old tick from before a very long pause compares incorrectly. Mitigation: clamp old ticks to this_run - MAX_CHANGE_AGE at start of each schedule run.
  • swap_remove tick desync: when a row is removed and last-row moved in, only data BlobVec swap-removed but tick vectors not. Invariant I4 violated. Fix: Column::swap_remove must swap all three vectors atomically.
  • Or archetype match vs. filter_fetch mismatch: an archetype matching Or doesn't mean each entity satisfies the filter (e.g., Or<(Added<A>, Added<B>)> — entity may have neither recently added). filter_fetch must still gate per entity.
  • Without<T> missing from access: Without<T> adds a read-dependency on ComponentId(T) for conflict analysis (any writer of T may change which archetypes match). Omitting this from Access allows incorrect parallel scheduling.

19.7 Performance Concerns

  • Tick vector cache pressure: each Column has two additional Vec<Tick> (added + changed). For non-change-detection queries, these are never read; no cost. For Changed<T> iteration, tick vectors are accessed per entity — must be contiguous.
  • Mut<T> cache line: deref_mut writes changed_tick at &column.changed_ticks[row]; if row is sequentially iterated, writes are sequential — cache-friendly.
  • Or filter double-evaluation: for each entity, both F1 and F2 filter_fetch may be called. Short-circuit evaluation must be respected.
  • Large Or nesting: Or<(F1,F2,F3,F4)> is a recursive type; monomorphisation depth can be large. Limit nesting to 4; document.
  • Tick increment contention: World::increment_change_tick uses atomic::fetch_add(Relaxed) on AtomicU32; single atomic op per schedule run, negligible.

19.8 Edge Cases

  • Component never mutated: changed_tick == added_tick; invariant I7 holds.
  • Component added and mutated in same tick: changed_tick == added_tick == this_run; both Added and Changed return true.
  • Query with Added<T> on entity spawned before system ever ran (last_run = 0): always returns true until last_run advances. Intended behavior; document.
  • Without<T> on component in sparse-set storage: archetype membership test is the same (archetype does not include T if stored as sparse); filter works correctly.
  • Or<()> (empty tuple): degenerate case; matches nothing. matches_archetype = false; document as invalid, add compile-time assertion.
  • Tick at exactly u32::MAX: wrapping_add(1) = 0; is_newer_than handles this; fuzz test covers.

20.6 Pitfalls

20.7 Performance Concerns

  • HashMap for resource lookup: TypeId → ResourceId hash map; single lookup per system init, not per run. Per-run access is by ResourceId index into a Vec; O(1).

  • Local<T> downcasting: Any::downcast_ref uses TypeId comparison; inlined and branch-predicted as true; effectively free.
  • CommandQueue drain cost: apply_deferred iterates type-erased function pointers in queue; one virtual dispatch per command. Batch large command sets; do not call apply_deferred in inner loops.
  • Resource change tick check: Res::is_changed() is a Tick::is_newer_than call; one subtraction + comparison; no allocation.

22.7 Performance Concerns

  • Byte buffer layout: commands packed contiguously; one allocation per queue per tick maximum; amortised O(1) push.

23. Phase 12 — Schedule + Dependency/Conflict Graph

23.1 Objectives

  • Schedule owns a list of boxed System trait objects and SystemSet groupings with user-declared ordering edges (before/after).
  • Build a directed acyclic graph (DAG); detect cycles; produce a topological order.
  • Conflict detection: two systems conflict iff Access::conflicts(a.component_access, b.component_access) or Access::conflicts(a.resource_access, b.resource_access).
  • Insert apply_deferred sync nodes at mandatory points (after systems using Commands; at user-explicit apply_deferred markers).
  • Report ambiguities (systems with no ordering edge and a potential conflict) as diagnostics, not silent bugs.
  • Constrained to doecs-schedule; consumes doecs-system System trait.

23.2 Detailed Implementation Steps

Type Fields

Build pipeline (Schedule::build(world), named steps not code): initialize all systems (system.initialize(world)) → expand SystemSet edges to concrete system-to-system edges → build adjacency list, run Kahn's topological sort (cycle → BuildError::Cycle{participants}) → conflict scan over every unordered pair in topo order (conflicts(i,j) adds to conflict_pairs; conflict with no ordering edge emits AmbiguityWarning) → insert sync points after every system with uses_commands()==true and every user-placed apply_deferred marker, then coalesce adjacent sync points → call system.new_archetype(a) for each archetype × system.

24. Phase 13 — Multithreaded Executor

24.1 Objectives

  • Replace single-threaded schedule loop with a work-stealing thread pool; systems with disjoint access sets run concurrently.
  • Implement an access-conflict gate: before a system dispatches, verify its Access<ComponentId/ResourceId> does not intersect any in-flight system's write set (or reads, for writes).
  • Pin !Send systems to the main thread; all others may run on worker threads.
  • Preserve deterministic output: multithreaded results must be bit-identical to single-threaded scheduled order on conflict-free schedules.
  • Insert apply_deferred barriers where the DAG has a sync-point edge; drain CommandQueue before systems downstream of a structural command.

Threat Model

Trust Boundaries

  • Boundary T1 — Component type registration: user code calls register_component<T>; the registry trusts the supplied Layout, drop fn pointer, and StorageType enum.
  • Boundary T2 — System fn pointers: IntoSystem wraps user-supplied Rust closures; the scheduler trusts SystemMeta computed by the system.
  • Boundary T3 — World-exclusive access in exclusive systems / apply_deferred: caller holds &mut World; no other thread can observe.
  • Boundary T4 — Thread pool task submission: MultiThreadedExecutor dispatches closures across worker threads; per-task access must be statically disjoint before dispatch.
  • Boundary T5 — CommandQueue byte stream: CommandQueue stores type-erased commands; apply_deferred executes fn pointers over untyped bytes.

Reference the architecture diagram: the World box is the central trust anchor; Commands/CommandQueue is a deferred mutation vector; Query<D,F> is the primary data-access surface; Schedule/MultiThreadedExecutor is the concurrency enforcement point.

Tracing Strategy

  • Span per system execution: span!(Level::TRACE, "system", name = %meta.name).
  • Span per schedule frame: span!(Level::DEBUG, "schedule_frame", tick = %world.read_change_tick()).
  • Span per apply_deferred: logs commands drained + duration.
  • Event on archetype creation: event!(Level::DEBUG, archetype_id, component_ids = ?set).
  • Event on entity migration: event!(Level::TRACE, entity, from_arch, to_arch) — gated behind TRACE to avoid flood.
  • Instrument via tracing crate; no println! in core crates.
  • doecs-cli examples configure tracing-subscriber with JSON formatter for structured output.

Structured Logging

  • All log events include: tick, system_name (where applicable), archetype_id (where applicable).
  • Log levels: ERROR = invariant violation; WARN = archetype explosion threshold crossed, OOM near; INFO = schedule build, executor mode change; DEBUG = frame timing, apply_deferred sync; TRACE = per-entity migration, per-query iteration entry.
  • No log crate calls in doecs-core/doecs-storage hot paths — instrument only at boundaries.

Alerting Philosophy

  • Alert on symptoms (frame latency spike, OOM approach) not causes.
  • No alert storms: group by schedule; deduplicate within 5-minute windows.
  • Page-worthy: frame p99 > 10 × baseline; archetype count > 65 536; entity_free_count == 0.
  • Warning: archetype count > 1 024; command queue depth > 10 000; table bytes > 1 GB.

Incident Response

  1. Detection: alert fires or user report.
  2. Triage: inspect schedule_frame_duration_us histogram; if frame spike → check system_exec_duration_us top offenders.
  3. Isolate: reproduce with doecs-cli example binary; attach tracing JSON log.
  4. Mitigate: switch to single-threaded executor (--executor=single) to rule out concurrency; reduce entity count.
  5. Root cause: run Criterion bench to bisect regression; enable debug_assert build to catch invariant violations.
  6. Postmortem: document archetype count, system access sets, command queue depth at time of incident.

Backup / State Management

  • doecs-core is an in-process runtime; no persistent storage.
  • Snapshot export (optional integration): world state serializable via user-supplied Serialize impl per component; World::snapshot() returns a byte blob per table column.
  • Restore: World::restore(snapshot) deserializes columns, reconstructs archetypes, resets change ticks.
  • Snapshot versioning: include schema_version: u32 in snapshot header; deserializer rejects mismatched versions.
  • No built-in replication or WAL; external persistence is application responsibility.

Deployment Topology

  • doecs-core and related crates compile to a static library linked into the application binary.
  • doecs-bench: separate binary, CI-only; run against --release build.
  • doecs-cli: example binary; ships as a separate target; not part of production library.
  • No daemon, no network listener, no external process.

Canary / Rolling Upgrade

  • Canary: new library version linked into a single game/sim process instance; compare frame-duration metrics against baseline instance for 30 minutes before fleet rollout.
  • Rolling upgrade: library is statically linked; "rolling upgrade" means process restart with new binary; no live migration of in-process world state between library versions.
  • Rollback: revert to previous binary version; no persistent world state to migrate (or restore from snapshot if snapshot was taken before upgrade).
  • Migration strategy for breaking API changes: see Compatibility & Versioning section.

Wire / Trace Compatibility

  • doecs-core has no wire protocol; no inter-process communication.
  • Structured log/trace format: JSON schema versioned with schema_version field; consumers must tolerate unknown fields (forward compat); missing fields in older producers handled with defaults (backward compat).
  • Metrics names follow doecs_{subsystem}_{name}_{unit} convention; names stable within a major version; new metrics may be added in minor versions.

Storage / Snapshot Format Compatibility

  • Snapshot format (optional): [header: 16 bytes][table_count: u32][per-table: archetype_id, component_ids[], row_count, column_bytes[]].
  • Header includes magic: [u8; 8] = b"DOECS\0\0\0", format_version: u16, schema_version: u16.
  • Forward compatibility: loader skips unknown table sections identified by unknown ArchetypeId if format_version >= 2.
  • Backward compatibility: producer writes all columns even if consumer ignores some.
  • Breaking snapshot change → increment format_version; provide migration utility.

Deprecation Policy

  • Deprecate via #[deprecated(since = "X.Y.0", note = "use ... instead")].
  • Deprecated API remains available for two minor versions after deprecation notice.
  • Removal triggers a major version bump.
  • Deprecation notices documented in CHANGELOG.md with replacement example.

Rolling-Upgrade Guarantees

  • No live rolling upgrade of in-process world state between library versions.
  • Upgrade path: take snapshot (if persistence implemented) → stop process → replace binary → start process → restore snapshot (if format compatible) or rebuild world.
  • Cross-version snapshot compatibility governed by format_version and schema_version fields; see Storage section above.
  • Executor mode (MultiThreadedExecutor vs single-thread fallback) is a runtime config flag; switching does not affect stored state or API compatibility.

  • Instrument: system dispatch latency, executor idle time, apply_deferred drain latency per sync point.
  • Tracy session: capture 10-second n-body run; measure scheduler overhead as % of total frame time (target: <5%).

Syscall Analysis

  • ECS runtime must be syscall-free during hot iteration path; verify via strace -c on Linux bench run.
  • Allowed syscalls: mmap/munmap during BlobVec grow; futex in thread-pool; none during Query::iter.
  • Gate: strace annotation in CI nightly; flag any new syscall in hot path.

Lock Analysis

  • Thread pool uses std::sync::Mutex only at task-queue boundaries; no locks inside Query::iter.
  • parking_lot::Mutex preferred over std::Mutex (no kernel roundtrip on uncontended path).
  • Lock contention profiled via perf lock on Linux; target: <1% lock-wait fraction during parallel bench.

Tail-Latency Analysis

  • Criterion captures per-iteration timing; extract p99/p999 from raw sample CSV.
  • Target: p99 iteration time ≤3× median for iter_100k_two_components.
  • High p999 spikes indicate allocator jitter or OS scheduler preemption; investigate with perf sched.

Memory Profiling

  • heaptrack (Linux) and Instruments Allocations (macOS) for full allocation timelines.
  • Metrics: peak RSS, live bytes, fragmentation ratio.
  • Regression gate: peak RSS for n-body 100k-entity soak must not grow >5% vs. previous release.

  • Partitioned worlds: pattern — multiple World instances per process (e.g., per game region); no cross-world queries; supported by design (no global state).

Mental Models & First Principles

The compressed insights an expert in data-oriented ECS design holds. Each predicts a bug class. Every cited § resolves to a real heading.

MM1. An ECS is a column database for game state, not an object graph. Components are columns; entities are rows; systems are queries. Predicts: why iteration is fast (sequential column scans) and why you design around access patterns. Bug without it: modelling entities as objects-with-methods reintroduces pointer-chasing and cache misses the ECS exists to avoid. Applied: §8 (storage model), Phase 1–3, P1, ADR-06.

MM2. Struct-of-arrays exists to feed the cache, not for elegance. Storing each component type in its own contiguous column means iterating one component streams cache lines with zero waste. Predicts: the ≥ 2 GB/s/core iteration throughput. Bug without it: AoS layout drags unused components through cache on every iteration, collapsing throughput. Applied: §8 (SoA table), §4.1 (column throughput), §4.2 (cache), MM1.

MM3. An entity handle is an index plus a generation; the generation is what makes it safe. Reusing a slot bumps its generation, so a stale handle fails the generation check instead of aliasing a new entity. Predicts: safe O(1) entity validity checks. Bug without it: a recycled index lets a dangling handle read a different entity's data (the ABA problem). Applied: §8 (Entity), Phase 1, P5, ADR-04.

MM4. An archetype is the set of component types an entity has; changing composition moves the entity. Adding/removing a component migrates the row to a different archetype table. Predicts: why structural changes are expensive and batched. Bug without it: mutating composition mid-iteration invalidates the table you're scanning. Applied: §8 (archetype), Phase 3–4, MM5, ADR-08.

MM5. Structural mutation during iteration is forbidden; defer it. Spawns, despawns, and component add/remove are recorded in a command buffer and applied at sync points. Predicts: iteration safety (I6). Bug without it: despawning an entity mid-query shifts the column under the iterator → skipped or double-processed rows. Applied: Phase 11 (CommandQueue/apply_deferred), §4.3, ADR-14, I6.

MM6. Parallelism is a static disjointness proof, not runtime locking. Each system declares its read/write access; the scheduler runs two systems concurrently only if their access bitsets don't conflict. Predicts: lock-free parallel execution and the ≥ 3.5× speedup. Bug without it: runtime locks add overhead and risk deadlock; bypassing the check is UB. Applied: Phase 9–10 (Access accumulation/analysis), Phase 12 (scheduler), §4.3 (access conflict), P4, ADR-15.

MM7. Queries are monomorphized at compile time, so there is no per-entity dispatch. WorldQuery derives the exact component access and generates a tight typed loop. Predicts: zero-cost iteration vs reflection. Bug without it: runtime type lookup per entity adds a branch/indirection to the hottest loop in the engine. Applied: §8 (WorldQuery), Phase 7, P6, ADR-10.

MM8. Change detection is a monotonic clock compared per component, not a dirty flag. A Tick advances each frame; a component's changed tick vs the system's last-run tick decides "changed since I last looked." Predicts: per-component precision with wrap-aware comparison. Bug without it: a single global dirty bit over-runs systems on unrelated changes. Applied: Phase 8 (Tick/ComponentTicks), §4.1 (change-detection overhead), ADR-11, P10.

MM9. Type erasure is the price of a generic store, and Miri is how you pay it safely. BlobVec holds bytes + a Layout + a drop fn; every raw-pointer operation is unsafe and must be UB-checked. Predicts: where memory-safety bugs hide. Bug without it: an unchecked BlobVec mis-drops or mis-aligns a column → UB that only Miri catches. Applied: §8 (BlobVec/Column), §4.1 (Miri scope), ADR-05/ADR-23, P9.

MM10. Archetype fragmentation is the silent throughput killer. Too many rarely-shared component combinations create many tiny archetypes, so iteration touches many small columns instead of a few big ones. Predicts: the ≤ 1000-archetype guidance for sustained throughput. Bug without it: per-entity unique component sets fragment storage and destroy SoA locality (MM2). Applied: §4.4 (fragmentation), §8 (archetype), Scalability Analysis.

Bevy ECS is the closest sibling — a Rust archetype+sparse-set ECS with compile-time queries and tick-based change detection; it wins as a full, production game-engine ECS. EnTT is the dominant C++ ECS, sparse-set-first with optional grouping and template-based views; it wins in C++ engines wanting header-only integration and immediate structural changes. We choose an archetype-primary model (MM4) for iteration locality and Rust's safety over EnTT's manual-memory speed.

flecs is a C ECS with a rich runtime query DSL, relationships, and observers; it wins when runtime-defined queries, entity relationships, and language-agnostic C ABI matter. We use compile-time monomorphized queries (MM7) for zero dispatch cost, trading flecs's runtime flexibility for raw iteration speed.

Unity DOTS pairs an archetype-chunk ECS with the Burst compiler and a job system with a safety layer; it wins for shipping high-performance C# games with vectorized jobs. We mirror its static-safety scheduling (MM6) in Rust's type system rather than a runtime safety layer, and defer SIMD/Burst-equivalent vectorization.

Back-of-Envelope Capacity Model

Numbers an expert computes before designing, each derived from §4.

  • C1 — Entity metadata memory. 10 M entities × 24 B/EntityMeta (§4.1) = ~240 MB for the entities table — the floor before any component data.
  • C2 — Column iteration time. ≥ 2 GB/s/core (§4.1): iterating one 4-byte component over 1 M entities streams 4 MB ⇒ ~2 ms, matching the ≤ 2 ms p50 query target (§4.1) and confirming memory bandwidth, not compute, is the limit.
  • C3 — Component memory overhead. ≤ 2× raw size (§4.1): a 16-byte component over 1 M entities = 16 MB raw ⇒ ≤ 32 MB including the column BlobVec + tick vectors (added/changed ticks).
  • C4 — Access bitset size. 2 × (65 536 / 64) words = 2 × 1024 × 8 B = 16 KB... actually 2 × 1024 u64 words = 16 KB per fully-sized access set; §4.1's "1 KB at 64K components" counts a single read-or-write bitset (65 536/64 = 1024 words = 8 KB) — the per-system access footprint is small enough to compare cheaply at schedule build.
  • C5 — Spawn/migrate cost. ≤ 500 ns/entity amortized (§4.1): inserting a component is an O(1) archetype-edge lookup (MM4) plus a column move; at 5 M entity ops/s (§4.1) the free-list allocator never syscalls.
  • C6 — Command drain rate. ≤ 100 ns/command (§4.1) via type-erased fn-pointer dispatch: a frame deferring 10 k structural changes drains in ~1 ms at the next sync point (MM5).
  • C7 — Parallel speedup ceiling. ≥ 3.5× on 8 cores for 4 disjoint systems (§4.1): bounded by the critical path of conflicting systems, not core count — non-disjoint systems serialize (MM6).
  • C8 — Tick wrap period. u32 ticks at 60 Hz = 2³² / 60 / 86400 / 365 ≈ 2.3 years (§4.1) before wrap; wrap-aware comparison means even then there's no failure (MM8, §4.3).
  • C9 — Change-detection overhead. ≤ 10% vs unfiltered (§4.1): one tick compare per row in the hot loop is a predictable branch, so a filtered query over 1 M entities stays near the ~2 ms baseline (C2).
  • C10 — Archetype fragmentation budget. ≤ 1000 archetypes for sustained throughput (§4.4): beyond this, iteration spreads across many small columns and per-archetype fixed costs dominate (MM10).
  • C11 — World shutdown cost. ≤ 10 ms at 1 M entities (§4.1): drop_in_place via each BlobVec's stored drop fn frees all columns; type erasure (MM9) means drop is data-driven, not per-type code.
  • C12 — Schedule build cost. ≤ 1 ms for 100 systems (§4.1): pairwise access-bitset conflict checks are O(systems² × bitset-words) = 100² × 1024 ≈ 10 M word-ops — a one-time startup cost, not per-frame (MM6).

Alternative Architectures (Roads Not Taken)

Alt-A — Sparse-set-primary ECS (EnTT model).

each component = sparse array (entity->dense index) + dense value array; entities are intersections of sparse sets

Wins when: component add/remove churn is very high and you want O(1) structural changes without archetype migration. Embodied by: EnTT, Shipyard. Rejected (as primary) because: archetype tables give better multi-component iteration locality (MM2); we keep sparse sets as the secondary store (ADR-07) for high-churn components, getting both.

Alt-B — Object-oriented entity hierarchy (scene-graph / GameObject).

Entity = object with a Vec<Box<dyn Component>>; systems call virtual methods per entity

Wins when: the game is logic-heavy with few entities and developer familiarity matters more than throughput (classic OOP engines). Embodied by: Unity GameObject/MonoBehaviour, Unreal AActor. Rejected because: per-entity boxing and virtual dispatch reintroduce the pointer-chasing and cache misses the ECS exists to eliminate (MM1, MM7).

Alt-C — Relational/database-backed entity store.

entities + components in an in-memory relational DB; systems are SQL-like queries with a planner

Wins when: complex ad-hoc queries, joins, and persistence dominate over per-frame iteration speed (simulation/strategy with rich queries). Embodied by: some MMO server backends, flecs's query engine leans this way. Rejected because: a query planner adds per-query overhead unacceptable in a 60 Hz hot loop; compile-time monomorphized queries (MM7) are faster for the fixed query set.

Alt-D — Immediate-mode parallel jobs over chunks (Unity DOTS model).

archetype chunks dispatched to a job system; Burst-compiled jobs vectorize over chunk arrays with a runtime safety layer

Wins when: you have a mature vectorizing compiler (Burst) and a runtime safety system, shipping AAA-scale C# games. Embodied by: Unity DOTS. Rejected (partly deferred) because: we encode disjointness in Rust's type system at schedule build (MM6) rather than a runtime safety layer, and SIMD/Burst-equivalent chunk vectorization is in the Deferred Features Register.

Glossary

Alphabetical. Each term is implementation-relevant and cross-referenced to the spine's types and phases.

Term Definition
ABA problem Bug where a recycled slot appears valid because the index matches a prior occupant; defeated by Entity.generation (P5, I1).
Access set Access<T> { reads: FixedBitSet, writes: FixedBitSet } representing all component/resource access declared by a system; the scheduler uses this to detect conflicts (Phase 10, Phase 12).
Added tick ComponentTicks.added: the Tick value at which a component was first inserted onto an entity; never decremented (I7).
apply_deferred Schedule sync point that drains CommandQueue in strict enqueue order (I8), flushing all pending structural mutations (P2).
Archetype The canonical storage unit for entities sharing an identical component set; uniquely identified by ArchetypeId and backed by one Table (P3, I2).
ArchetypeId u32 index into the Archetypes registry; stable for the World's lifetime.
Archetype graph DAG of Edges on each Archetype; each edge is a ComponentId -> ArchetypeId transition memoizing the result of adding or removing one component (Phase 4).
BlobVec Type-erased contiguous store holding items of a single Layout; carries a drop pointer; the primitive behind Column and resource storage (Phase 2, I10, P9).
Change detection Tick-based mechanism comparing ComponentTicks.changed to a system's last_run tick; observable and deterministic, never heuristic (P10, Phase 8).
Changed tick ComponentTicks.changed: set to World.change_tick on every DerefMut through Mut<T> (I7).
Column BlobVec of component values plus parallel Vec<Tick> for added and changed ticks; one per ComponentId per Table (Phase 3, I4).
CommandQueue Type-erased queue of deferred mutations; holds closures/records that each carry their own vtable; drained by apply_deferred (Phase 11, I8).
ComponentId Dense usize index assigned at registration time; stable for the World's lifetime; keys into Components registry.
ComponentInfo Descriptor tuple: { id, name, layout: Layout, drop: Option<unsafe fn(*mut u8)>, storage: StorageType }; registered once per type (Phase 2).
ComponentTicks Pair { added: Tick, changed: Tick } stored in Column's parallel tick vectors, one per row (I7).
Conflict Two systems conflict iff their Access sets intersect on a write, or one writes what the other reads; conflict forbids concurrent execution (I5, Phase 12).
Edges Per-archetype hash maps ComponentId -> ArchetypeId for add and remove transitions; lookup is O(1) amortized; memoized on first structural move (Phase 4).
Entity { index: u32, generation: NonZeroU32 } — 64-bit generational handle; index identifies the slot, generation detects stale reuse (I1, P5).
EntityLocation { archetype_id, table_id, table_row, archetype_row } — precise four-coordinate address of an entity's data; stored in EntityMeta and updated on every migration (I2, I9).
EntityMeta Per-slot record { generation, location: EntityLocation } in the dense entity array; authoritative source for liveness and location (Phase 1).
Exclusive system System taking &mut World; cannot run concurrently with any other system; used for operations requiring unrestricted World access (Phase 14).
Fetch Trait parameterised on a lifetime; fetch() extracts the typed value for one entity from pre-fetched column pointers (Phase 7, P6).
Fragmentation Pathological state where many archetypes each hold few entities, degrading iteration cache efficiency; mitigated by component set design and sparse-set policy for volatile components (Phase 6, doecs-bench).
FunctionSystem Blanket wrapper converting a Rust fn(P0..Pn) -> () into a System by calling SystemParam::init/fetch for each param (Phase 10).
Generational index Index-plus-generation pattern used in Entity and free-list allocators to distinguish reused slots without pointer identity (P5, Phase 1).
IntoSystem Conversion trait; implemented for FunctionSystem and exclusive-system wrappers; entry point for registering any callable as a system.
Observer / hook Callback triggered on component add/remove; registered per ComponentId; runs synchronously within World; introduced in Phase 14.
QueryFilter Trait sub-family of WorldQuery returning a boolean per archetype/entity without producing data (With<T>, Without<T>, Or, Added<T>, Changed<T>).
QueryState Cached per-World state for a Query: list of matched ArchetypeIds, fetch init state; updated lazily when new archetypes are created (Phase 7).
Resource Singleton value stored outside archetypes; keyed by ResourceId (analogous to ComponentId); accessed via Res<T> / ResMut<T> system params (Phase 9).
Row The horizontal cross-section of a Table at a given index; conceptually one entity's component values across all columns; never a concrete struct.
Schedule Ordered collection of systems and SystemSets with explicit ordering edges; compiled into a dependency DAG; executed by MultiThreadedExecutor (Phase 12).
SoA (struct-of-arrays) Layout where each component type occupies its own contiguous array; enables SIMD-friendly iteration with unit-stride memory access (P1, Phase 3).
SparseSet dense: Vec<V> + sparse: Vec<u32> index; O(1) insert/remove/lookup; used for components with high churn to avoid archetype migrations (Phase 6).
StorageType Enum { Table, SparseSet } per ComponentInfo; controls whether a component lives in a Table column or a SparseSet (Phase 6).
Sync point Schedule position where apply_deferred runs, draining all pending CommandQueues before subsequent systems execute (I6, P2, Phase 12).
SystemMeta Metadata accumulated during system construction: component_access, resource_access, is_send, last_run tick; input to conflict analysis (Phase 10).
SystemParam Trait with init_state and get_param methods; implemented by Query, Res<T>, ResMut<T>, Local<T>, Commands, EventReader<T>, EventWriter<T> (Phase 9).
SystemSet Logical grouping of systems with shared ordering constraints; a node in the schedule DAG at the set level (Phase 12).
Table ComponentId -> Column sparse array plus entities: Vec<Entity>; the primary SoA storage for one archetype (Phase 3, I4).
TableId u32 index into Storages.tables; one table shared by exactly one archetype.
Tick u32 logical clock incremented each schedule run; wrap-aware comparison via is_newer_than; used by ComponentTicks and system last_run (Phase 8, I7).
Topological order Linear ordering of schedule nodes consistent with all before/after edges; cycle detection must fail at schedule build time (Phase 12).
WorldQuery Root trait family unifying QueryData and QueryFilter; specifies ReadOnly marker, Fetch associated type, archetype-match predicate, and iteration safety rules (Phase 7).
