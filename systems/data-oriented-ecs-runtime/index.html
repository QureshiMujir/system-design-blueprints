In one paragraph

An ECS runtime (Entity-Component-System) is the engine core that keeps a simulation's objects as rows of plain data and runs functions over them every frame. This blueprint builds one in Rust as an in-process library, with no network, persistence or scripting (§1.1, §1.2). Entities are 64-bit handles, components live in contiguous per-type columns, and two systems run in parallel only when the data they touch does not overlap (§1.1, P4). The aim is cache-friendly iteration: at least 2 GB/s per core, and a 1-million-entity query in 2 ms at the median, both design targets (§4.1). Engine developers embed it, and learners read it as a design reference (§1.4, §1.5).

The problem, concretely

Picture a simulation with a million moving things, each with a position and a velocity (the sizes of §4.1, the example components of §8.12). The object-oriented answer is one object per thing, holding a list of boxed components, with a virtual call per object per frame (Alt-B in the Alternative Architectures section). Each component then sits in its own heap allocation, so each access can miss the cache. P1 quotes a 5–30× throughput loss for this layout in EnTT's array-of-structs versus struct-of-arrays benchmarks (P1, MM2).

Fix the layout and three more problems appear. First, handles: without a generation check, a system that still holds a recycled index silently reads the new occupant's components (P5, TH-01). Second, mutation: adding a component moves the entity's row to a different table, so doing it while a query walks raw column pointers is undefined behaviour (P2, I6). Third, threads: explicit threading in a game loop is the "dependency hell" the access-analysis pipeline replaces (§2.2). The blueprint's answer is to prove, before running, that two systems touch disjoint data (P4, MM6). Every part of the design below answers one of these four pressures.

How it works, end to end

Follow one frame through the boxes of §3.1 (condensed from the diagram there):

  1. Startup. doecs-component assigns each component type a dense ComponentId and records its Layout, drop function and StorageType (§3.2, §8.2). The thread pool is spawned once, one worker per physical core by default (§1.4).
  2. Spawn. doecs-core Entities pops the free list or extends the array and returns an Entity {index, generation} (§8.1, §12). doecs-archetype finds or creates the archetype for the component set, which owns a Table in doecs-storage (§8.3, §3.2). EntityMeta records where the row went (§3.2).
  3. Schedule build. Each SystemParam in doecs-system adds to the system's read/write Access bitsets. doecs-schedule collects ordering edges, adds a conflict edge for every overlapping pair, runs a topological sort, and places apply_deferred nodes (§8.9, §8.10).
  4. Dispatch. MultiThreadedExecutor launches a system when its access is disjoint from everything already running, pins !Send systems to the main thread, and runs exclusive (&mut World) systems alone (§8.10, §3.2).
  5. Iterate. doecs-query QueryState holds the matched archetype list; per archetype, Fetch resolves raw column pointers once, then loops over rows (§8.6, P6). doecs-change Mut<T> stamps the changed tick on write (§8.7).
  6. Defer. Spawns, inserts, removes and despawns issued by systems go to doecs-command CommandQueue instead of touching the tables (§8.8, P2).
  7. Sync point. The executor waits for all running systems, then apply_deferred drains the queue in enqueue order (§8.10, I8). doecs-event Events<T> swap their two buffers each Schedule::run (§8.11).

doecs-bench holds the Criterion benches and doecs-cli the n-body, boids and particle examples (§1.6).

The core ideas

Generational handles: an index plus a "version" (§8.1, P5, I1)

A handle is Entity {index: u32, generation: NonZeroU32}, 8 bytes (ADR-04). The per-slot record EntityMeta stores the slot's current generation, and every access compares the two; a mismatch returns None or Err instead of reading the new occupant (P5, I1). The blueprint's own failure trace (§8.12):

Step Action State
1 spawn(()) Entity{index:0, generation:1}
2 despawn(e) EntityMeta[0].generation bumped to 2
3 entity(e) 2 ≠ 1, so I1 trips: Err(NoSuchEntity) or panic, depending on the API variant

Two places disagree. §8.1 says a free slot has an even generation and a live one an odd generation: alloc sets generation = prev+1 and despawn bumps it again ("odd→even→odd next alloc"). §12 bumps only on despawn, and its fixture expects "generation 2 on recycled slot"; P5 says the free list bumps it "to ≥2 after first recycle" (§8.1, §12, P5). Also, §12 says a generation that overflows to u32::MAX marks the slot permanently dead, while P5 says the generation wraps at 2³² and ABA recurs (§12, P5). Neither pair is resolved here.

Columns of raw bytes: BlobVec, Column, Table (§8.4, §8.2, I4, I9, I10)

A BlobVec is a type-erased Vec<u8> plus a Layout and a drop function, so one container can hold any component type without boxing (ADR-05, §8.2). A Column is a BlobVec plus two tick vectors (added, changed); a Table is one Column per component plus a Vec<Entity> mapping row to entity (§8.4). All of them must have the same length (I4). Removing row r uses swap_remove: copy the last row's bytes into r in every column, truncate every column by one, then update the moved entity's EntityMeta.location.table_row (§8.4, I9). Skipping that last step leaves a dangling location that reads another row's data (P7, FM-03). Zero-sized components allocate no bytes but still keep ticks; a component with no drop function takes a skip-drop path (§8.2). All unsafe code stays inside doecs-storage behind typed wrappers (P9), and Miri runs on it (ADR-23, I10).

Archetypes, the edge graph, queries and the sparse-set escape hatch (§8.3, §8.5, §8.6, P3)

An archetype is the sorted set of ComponentIds an entity has, and it owns one table (P3, §8.3). Adding or removing one component moves the entity to a neighbouring archetype; the result of each such step is cached in per-archetype Edges {add, remove} maps, so only the first transition pays a lookup (ADR-09, §8.3). The blueprint's trace (§8.12):

Step Call Effect
1 spawn((Position, Velocity)) Entity{0, gen 1}, archetype A = {Position, Velocity}, row 0
2 insert(Health) edge A.add[Health] = B; row copied to table B; EntityMeta updated
3 Query<(&Position, &mut Velocity)> matched archetypes [A, B]; yields row 0 of B; Mut stamps the changed tick
4 despawn(e) row swap-removed, generation bumped to 2, index pushed on the free list

A query caches its matched archetype list and refreshes it only when the archetype count grows (§8.6). Because those lists are matched ahead of time, the hot loop has no dynamic dispatch, no hash lookup per entity and no allocation (P6).

For components that are added and removed constantly, a sparse set (a dense value array plus an entity-index-to-slot array) skips the archetype move entirely, with O(1) add, remove and lookup (§8.5, ADR-07). Each component picks Table or SparseSet itself (P11). Disagreement: §8.5 says sparse-set components "still appear in an entity's archetype", while P11 says the archetype graph reflects only Table components and Phase 6 requires the archetype to stay unchanged on insert (§8.5, P11, §17).

Change detection with a wrapping clock (§8.7, P10, I7)

A Tick(u32) counter rises once per Schedule::run. Each row has an added tick and a changed tick; Mut<T>::deref_mut stamps the changed tick with the current one, and a system remembers its own last_run tick (§8.7). Added<T> and Changed<T> compare the stored tick with last_run using wrapping subtraction: is_newer_than(a, b, last_run) = a.relative_to(last_run) > b.relative_to(last_run) (§8.7). Because the subtraction wraps modulo 2³², the comparison stays correct across the wrap as long as no query goes more than 2³¹ ticks without running (P10, §8.13). The Phase 8 test deliberately puts last_run = u32::MAX−1 and this_run = 1 on either side of the wrap (§19). Column::push stamps the same tick into both vectors, which keeps I7 (changed ≥ added) true from the start (P10).

Command buffers: record now, apply at a barrier (§8.8, P2, I6, I8)

A CommandQueue is one byte blob of entries shaped [fn_ptr][payload aligned to T]; apply_deferred casts each function pointer and calls it with &mut World and the payload (§8.8). It drains in strict enqueue order (I8), then clears the blob but keeps its capacity (§8.8). Schedule building places the sync points where commands must be visible to later readers (§8.10, P2). Exclusive systems may still call World::spawn directly because no query can be running beside them (P2, §8.13). One place is ambiguous: §8.8 says commands from concurrent systems are merged "in system-completion order", which it calls deterministic under scheduler serialization, while P8 demands results identical to the single-threaded order (§8.8, P8).

Static disjointness: access sets, conflicts and the executor (§8.6, §8.9, §8.10, P4, I5)

Each parameter contributes bits: &T sets a read bit, &mut T a write bit, With<T> and Without<T> none, and Res/ResMut act the same on a ResourceId (§8.6, §8.9). Two systems conflict when reads_a ∩ writes_b ≠ ∅ or writes_a ∩ writes_b ≠ ∅ (§8.6, I5). The dispatch table (§8.10):

Situation Executor action
system is !Send run on the main thread
system takes &mut World run alone after in-flight systems drain
access disjoint from all running systems dispatch to the pool now
access conflicts with a running system queue it and retry when one finishes
sync point reached barrier, then apply_deferred

§8.10 marks as ambiguities two systems with no ordering edge and no conflict, configurable as warn or error; P8 and Phase 12's acceptance table instead call an unordered conflicting pair ambiguous (§8.10, P8, §23). The target is that any parallel run equals the single-threaded run in topological order (P8). Inside one system, overlapping parameters (a Query<&mut T> plus a Query<&T>) are rejected at initialisation (I11, §8.13).

The trade-offs — where engineers disagree

Storage layout: SoA archetype tables (ADR-06)

Chosen: struct-of-arrays columns per archetype, for cache-line locality when iterating one component type (§9, P1). Rejected: array-of-structs, a hash map per entity, ECS slots. When the rejected choice is right: array-of-structs when most accesses touch all of one entity's components together (rare in ECS); a hash map per entity for very sparse, heterogeneous entities (§9).

Second storage: per-component SparseSet (ADR-07)

Chosen: a sparse set for high-churn components, so add and remove skip archetype movement (§9). Guidance: more than 50% population with sequential access means Table; under 20% population with high churn means SparseSet (P11). Rejected: one storage type for everything. When the rejected choice is right: a single archetype storage when churn is low and the dual-storage complexity is not justified (§9).

Structural changes: deferred commands (ADR-14)

Chosen: a CommandQueue byte buffer drained at apply_deferred, which removes mid-iteration structural change (§9, I6). Rejected: immediate mutation with read/write locks, or transactional copy-on-write. When the rejected choice is right: immediate mutation with locks, for a single-threaded simple world where deferred-apply complexity is not worth it (§9). The price of the chosen side is that state is not visible to later systems until the sync point (P2).

Parallelism: static access analysis (ADR-15)

Chosen: Access<T> bitsets checked at schedule build time, with no runtime lock on the hot path (§9, P4). Rejected: runtime lock acquisition, optimistic concurrency. When the rejected choice is right: runtime locking when the system set is dynamic or unknown at schedule-build time, such as plugin-loaded systems (§9). Over-declared access costs parallelism, and reads_all/writes_all (for example &mut World) forces full serialisation (P4).

Entity handle: index plus NonZeroU32 generation (ADR-04)

Chosen: an 8-byte handle whose non-zero generation gives Option<Entity> a niche and defeats ABA (§9, P5). Rejected: a 32-bit packed handle, a 64-bit opaque u64. When the rejected choice is right: the 64-bit opaque handle when you need more than 4 billion live entities or want to pack extra metadata; the 32-bit packed handle on memory-constrained targets (§9).

Change detection: per-row ticks (ADR-11)

Chosen: a Tick(u32) clock with ComponentTicks {added, changed} per row, for per-component precision with wrap-aware comparison (§9, P10). The cost is two extra tick vectors per column, proportional to entities times tracked components (P10). Rejected: dirty bits, a version per archetype, pointer equality. When the rejected choice is right: a per-archetype version or dirty bits when per-component precision is not needed and lower memory is preferred (§9).

Query model: compile-time access (ADR-10)

Chosen: WorldQuery/QueryData/QueryFilter traits that derive access at compile time and are monomorphised, so there is no dispatch per entity (§9, P6). Cost: code bloat for complex queries, mitigated by LTO (P6). Rejected: runtime type strings, reflection. When the rejected choice is right: reflection for a scripting or modding layer where queries are authored at runtime (§9).

Roads not taken

Sparse-set-primary ECS (Alt-A): one sparse array plus one dense array per component. It wins when add/remove churn is very high and O(1) structural change matters most (EnTT, Shipyard). It is rejected as the primary store because archetype tables iterate multi-component queries with better locality; sparse sets are kept as the secondary store (ADR-07, MM2).

Object-oriented entities (Alt-B): an object with a Vec<Box<dyn Component>> and virtual calls. It wins for logic-heavy games with few entities where developer familiarity beats throughput (Unity GameObject, Unreal actors). It is rejected because boxing and dispatch bring back the cache misses an ECS exists to remove (MM1, MM7).

A relational in-memory store with a query planner (Alt-C). It wins when ad-hoc queries, joins and persistence matter more than per-frame speed. It is rejected because a planner adds per-query overhead that a 60 Hz loop cannot afford (MM7).

Chunk jobs with a vectorising compiler (Alt-D, the Unity DOTS model). It wins where a mature vectorising compiler and a runtime safety layer already exist. It is rejected, partly deferred, because disjointness is proved in Rust's type system at schedule build (MM6).

Deferred features (Deferred Features Register): SIMD column iteration (trigger: throughput targets need explicit SIMD), reflection-driven serialization (trigger: an editor or save game needs runtime type introspection), GPU dispatch (trigger: systems must offload data-parallel work), and a cross-crate plugin registry (trigger: third-party crates must register at runtime). Each is out of scope until its trigger (Deferred Features Register, §1.7).

What must never be false

  • I1: a handle's generation equals the slot's generation. assert_eq! in debug, None/Err in release; counter entity_stale_access_count (§7).
  • I2: an entity occupies exactly one archetype row and one table row. Assert after each insert/remove; per-entity structural-change counter (§7).
  • I3: a component is in archetype.components exactly when it is on the entity. debug_assert! before each column fetch; a query-mismatch log (§7).
  • I4: every column in a table is as long as entities. debug_assert_eq! after every mutation; the assert is the only signal (§7).
  • I5: no two running systems hold conflicting access. Bitset intersection before dispatch; a conflict-pair log at build time and a dispatch count at run time (§7).
  • I6: structural changes happen only at sync points. Miri flags a reallocated BlobVec under a live slice; a debug-only world.is_iterating flag; no release telemetry (§7).
  • I7: changed ≥ added for every stored component. debug_assert! on every tick write (§7).
  • I8: apply_deferred drains in enqueue order. Property test with sequence numbers; command count per flush (§7).
  • I9: swap_remove updates the moved entity's location. Assert after each swap-remove (§7).
  • I10: BlobVec respects each Layout and drops each value exactly once. Miri, a debug layout assert, allocation-size and drop-call counters in tests (§7).
  • I11: no overlapping write or read-plus-write access inside one system. A post-init scan panics with the parameter type names; counter system_init_aliasing_rejections (§7).
  • I12: Schedule::build gives the same topological order whatever the registration order. A 1000-seed property test; metric schedule_build_nondeterminism_detected should stay 0 (§7).

The blueprint also says "I1–I10" in three places (§2.3, §2.4, the §25 soak criterion) although §7 lists twelve.

What breaks in production

  • FM-02, column misalignment (I4). Queries return another entity's component, silently. Cause: a swap_remove that skips a column. Detected by debug_assert_eq! in every Table mutation, so production canaries need debug assertions on. Recovery: a panic in debug mode, then abort and fix; test every structural path (FM-02).
  • FM-03, stale EntityLocation (I9). A live entity yields None or the wrong row. Cause: a migration that forgets the moved entity. Detected by a debug_assert in World::entity(); fixed in the Phase 5 migration code, with a random-operation property test as the guard (FM-03).
  • FM-05, schedule cycle or executor hang. Schedule::build returns Err(CycleError), or the executor stalls. Cause: before/after edges that loop. Detected by cycle detection and an executor watchdog; recovery is removing an ordering constraint, using the schedule_dot_export graph (FM-05). §4.3 instead says a cycle panics at schedule build time (§4.3).
  • FM-06, parallel access conflict (I5). Data race in worker threads. Cause: a dispatch bug that bypasses the access check. Detected by an Access::is_compatible assertion and ThreadSanitizer in CI; recovery is a panic in debug mode, then a fix to the executor gate (FM-06).
  • FM-07, apply_deferred out of order (I8). Component state is inconsistent after commands run. Cause: a drain loop that skips or reorders entries. Detected by comparing queue length before and after and by an order test; fix the loop (FM-07).
  • FM-09, tick wrap gives false or missed changes. Changed<T> fires spuriously or misses a write. Cause: is_newer_than without wrapping subtraction. Detected by a test that advances the tick to 2³²−1; the fix is algorithmic (FM-09).
  • FM-10, panic in a system. The executor crashes and later systems are skipped. Detected by catch_unwind around each dispatch; automatic recovery marks the system failed and skips its dependents (FM-10). Disagreement: §4.3 says a worker panic propagates to the main thread via resume_unwind (§4.3, FM-10).
  • FM-12, out of memory growing a column. BlobVec::push panics. Cause: large payloads, many entities, no pre-allocation. Mitigations: reserve_exact before bulk inserts, a doecs_table_bytes_allocated metric, pre-sized tables (FM-12). §4.3 calls the same event an abort via handle_alloc_error, FM-12 a panic (§4.3, FM-12).

Threats worth knowing: TH-01 a cached Entity reused after despawn, answered by I1 (TH-01); TH-02 a wrong Layout registered for a type, answered by deriving it from Layout::new::<T>() rather than trusting the caller (TH-02); TH-04 two aliased &mut queries in one system, answered by accumulated write bits checked before dispatch and assert_no_conflict in debug (TH-04); TH-05 a misaligned command write, answered by a (size, align, fn_execute, fn_drop, bytes) header and an alignment assert (TH-05); TH-06 archetype explosion by unbounded component combinations, answered by a doecs_archetype_count metric and a warning at 65,536 (TH-06). TH-02 conflicts with §8.2, where register_with_descriptor takes a caller-supplied layout, and with the trust boundary T1, which says the registry trusts the supplied Layout (TH-02, §8.2).

  • Entity alloc: ≥ 5 M ops/s in §4.1, ≥ 50 M ops/s in Phase 1's acceptance table (§12).
  • 10 k command drain: ≈ 1 ms by C6, ≤ 200 µs by M7, < 2 ms in Phase 11's acceptance (§22).
  • Parallel speedup: ≥ 3.5× on 8 cores in §4.1; ≥ 3.2× on 4 hardware threads in M5 and §25, and on 4 cores in §24.

How it compares

  • Bevy ECS is the closest sibling: Rust, archetype tables plus sparse sets, compile-time queries and per-component ticks. It wins as a full production engine ECS; this design reimplements its core ideas at teachable scale, so the type-erased storage and scheduler are the lessons (Comparative Architecture Table).
  • EnTT is C++ and sparse-set-first with optional groups, template views and immediate structural changes. It wins in C++ engines wanting header-only integration; this design is archetype-primary for iteration locality and gives up EnTT's manual-memory speed for Rust safety (Comparative Architecture Table, MM4).
  • flecs is C, with a runtime query DSL, relationships and observers. It wins when runtime-defined queries and a C ABI matter; this design uses compile-time queries to avoid dispatch cost, trading away runtime flexibility (Comparative Architecture Table, MM7).
  • Unity DOTS pairs archetype chunks with the Burst compiler and a job system with a safety layer. It wins for shipping high-performance C# games with vectorised jobs; this design does the safety proof in Rust's type system and defers SIMD (Comparative Architecture Table, MM6).

Questions to test yourself

  1. How does the entity generation defeat the stale-handle (ABA) problem? — Hint: P5 and §8.1, then compare the generation numbers in §8.12 with §12's fixtures.
  2. Why is structural mutation during iteration forbidden, and how is it made safe? — Hint: P2, I6 and §8.8.
  3. Trace how two systems are proven safe to run in parallel without locks. — Hint: §8.6 for the conflict rule, §8.9 for access accumulation, §8.10 for the dispatch table.
  4. What bounds the parallel speedup at 3.5× rather than 8× on 8 cores? — Hint: Capacity C7 and MM6.
  5. How does the SparseSet secondary storage complement archetype tables, and when is it preferred? — Hint: ADR-07, P11, and §8.5.

If you only remember three things

Store each component type in its own contiguous column and iterate it linearly, because the cache, not the arithmetic, sets the speed (MM1, MM2, P1). Never change an entity's shape while something is reading the tables: record the change and apply it at a sync point (MM5, P2, I6). Parallelism is a proof made before running, from the read and write sets each system declares, not a lock taken while running (MM6, P4, ADR-15).

Words used here

  • Entity: a handle made of a slot index and a generation, standing for one simulated thing (P5).
  • Component: a plain data value of one type attached to an entity, registered once per type (§8.2).
  • System: a Rust function whose parameters declare what data it reads and writes (§8.9).
  • Archetype: the group of entities that have exactly the same set of component types (P3).
  • Table / column: the SoA store for one archetype, one contiguous column per component (§8.4).
  • BlobVec: a type-erased growable array holding values of one Layout, with a drop function (§8.2).
  • Sparse set: an alternative store, a dense array plus an index array, for fast-changing components (§8.5).
  • Query: a typed request for all entities having certain components, run as a loop over matched archetypes (§8.6).
  • Tick: a wrapping 32-bit counter, advanced per schedule run, used to ask "changed since I last ran" (§8.7).
  • Command buffer: a queue of recorded structural changes applied later, in order (§8.8, I8).
  • Sync point: the schedule position where apply_deferred runs and the queue drains (I6, P2).
  • Access set: the read and write bitsets that decide which systems may run together (P4, I5).
  • Conflict: two systems where one writes what the other reads or writes, so they cannot overlap (§8.6).
  • Archetype fragmentation: many archetypes with few entities each, which hurts iteration (MM10).
