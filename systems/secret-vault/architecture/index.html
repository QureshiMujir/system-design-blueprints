API Listener — terminates TLS 1.3, parses HTTP, is the sole protocol boundary; rejects malformed requests before they reach auth. Auth Methods — pluggable identity verification (token, AppRole, mTLS) producing an Identity and, on success, a Token. Token Store — persists tokens by hashed id and by accessor; the trust boundary where "bearer of this string" becomes "this Identity." Policy Engine — evaluates the request path and required capability against the token's attached policies; deny-by-default; runs before any secret material is touched (I3). Router/Mount Table — maps a path prefix to a mounted engine instance; concurrency boundary for hot-swapping mounts via ArcSwap. KV Engine — static secrets, versioned, with metadata and soft-delete/rollback. Dynamic Credential Engines — generate secrets on demand against an upstream system and register a lease. Transit Engine — encrypts and signs on behalf of callers without exposing key material; the EaaS path. Lease/Expiration Manager — tracks every issued lease, sweeps expiries, drives revocation; a queue boundary between issuance and cleanup. Rotation/Rewrap Worker — leader-only background job moving ciphertext across key epochs (§20); reads a persisted RewrapCursor so it resumes after a crash. Cryptographic Barrier — the sole encrypt/decrypt path to storage; owns the key hierarchy; every read/write from any engine passes through it (I2). Storage Backend — durable, opaque to plaintext; also hosts the leader-election lock. Audit Log — a queue-fed, append-only, hash-chained sink; a write that cannot be audited is refused (P5). Seal/Unseal Subsystem + Shamir Share Collector — the only path that ever reconstructs the master key in memory, and only transiently. Telemetry — cross-cutting metrics/tracing that must never carry secret fields (I1, ADR-24).

8. Domain Model

8.1 Key Hierarchy

Key Rooted By Wrapped By Rotated When Rotation Cost
MasterKey (MK) Shamir shares (k of n) never wrapped; exists only transiently in memory Rare — disaster or confirmed compromise Full re-init and re-share ceremony
KeyEncryptionKey (KEK) MK MK Scheduled (e.g. quarterly) or on suspected compromise Rewrap the (small) DEK table only (§20)
DataEncryptionKey (DEK) KEK active KEK at mint time Scheduled (e.g. daily/weekly) or on demand Rewrap affected storage records (§20)

Display equations (AEAD-Enc/Dec = ChaCha20-Poly1305, RFC 8439):

KEK_active            = AEAD-Enc(MK, nonce_k, KEK_material,  AAD = "kek" || kek_epoch_id)
DEK(e)                = AEAD-Enc(KEK_active_at_mint(e), nonce_d, DEK_material(e), AAD = "dek" || e)
Ciphertext(path, v)   = AEAD-Enc(DEK(e), nonce_r, plaintext, AAD = mount_id || path)

Unwrap is the corresponding AEAD-Dec; a failed tag check yields VaultError::TamperedRecord, never a "best effort" plaintext (P6).

8.2 Barrier Record Byte Layout

Offset Field Size Description
0 version 1 B record format version, currently 1
1 key_epoch_id 4 B (u32 BE) KeyEpoch whose DEK encrypted this record
5 nonce 12 B AEAD nonce, unique per encryption under this DEK (I13)
17 tag 16 B AEAD authentication tag
33 ciphertext variable AEAD ciphertext of the stored value

AAD is not stored inline: it is mount_id (16 B UUID) || storage_path (UTF-8), recomputed from the lookup key at read time. This binds ciphertext to its location — copying a valid record to a different path fails tag verification.

8.3 Shamir Share Format And Reconstruction

Each 256-bit master key is split byte-plane-wise: for byte i of 32, a degree-(k-1) polynomial f_i(x) = s_i + a_1·x + a_2·x^2 + … + a_{k-1}·x^{k-1} is built over GF(2^8) (Rijndael's reduction polynomial x^8+x^4+x^3+x+1), with s_i the secret byte as the constant term and a_1..a_{k-1} random. Share j (for n operators) is (x_j, [f_1(x_j), …, f_32(x_j)]) — one x-coordinate, 32 y-values.

Reconstruction (Lagrange interpolation at x = 0, arithmetic in GF(2^8)):

s_i = Σ_{j=1}^{k}  y_i,j · Π_{m=1..k, m≠j}  (0 − x_m) / (x_j − x_m)      (all ops in GF(2^8))

Worked example (k=3, n=5, one byte plane, illustrative values): shares at x = {1,2,3,4,5} carry y-values {y1,y2,y3,y4,y5} derived from f(x) = s + a1·x + a2·x². Given any 3 of the 5 (say x=1,3,4), the Lagrange sum above reconstructs s exactly; any 2 shares (k−1) leave s information-theoretically undetermined — every possible byte value remains equally likely (I11).

8.4 Policy Grammar (EBNF)

policy          ::= { path_block } ;
path_block      ::= "path" path_string "{" capability_stmt { capability_stmt } "}" ;
capability_stmt ::= "capabilities" "=" "[" capability { "," capability } "]" ;
capability      ::= "create" | "read" | "update" | "delete" | "list" | "sudo" | "deny" ;
path_string     ::= '"' segment { "/" segment } '"' ;
segment         ::= "*" | "+" | literal ;
literal         ::= ident_char { ident_char } ;
ident_char      ::= letter | digit | "-" | "_" | "." ;

Path-matching precedence (highest wins, independent of Deny which always overrides):

Match Type Specificity Rank Example Notes
Exact literal path 1 (highest) secret/data/prod/db matches only that exact path
Prefix + trailing * 2 secret/data/prod/* deepest matching prefix wins among globs
Single-segment + 3 secret/data/+/db + consumes exactly one path segment
Root/broad * 4 (lowest) secret/* matches everything under the prefix
any rule with deny overrides all — explicit deny always wins regardless of rank

Capability set: create, read, update, delete, list, sudo (bypass certain operator-only checks), deny (explicit negative, always wins).

Worked authorization trace. Token policies = [db-readonly, default]. db-readonly: path secret/data/prod/db/* → [read, list]. default: path secret/data/* → [read]. Request: PUT secret/data/prod/db/creds (new path ⇒ required capability = create). Trace: (1) compute required capability = create; (2) match db-readonly rule, rank 2, grants {read, list} — no create; (3) match default rule, rank 2, grants {read} — no create; (4) no deny rules present; (5) no rule anywhere grants create; (6) deny by default (P4) — 403.

8.7 Dynamic-Credential Generation And Revocation Sequence

Step Actor Action
1 Client request GET dynamic-engine/creds/{role}
2 API authenticate token, load attached policies
3 Policy Engine authorize read on the resolved path (I3)
4 Engine render creation template with role parameters
5 Engine call upstream system (e.g. CREATE ROLE …)
6 Lease Manager register lease {ttl, max_ttl, renewable}
7 Barrier persist the lease record (encrypted)
8 Audit append entry (secret fields HMAC'd)
9 API return credential + lease_id + ttl
10 Sweeper or explicit call trigger revoke(lease_id)
11 Lease Manager look up lease; call engine.revoke()
12 Engine call upstream revoke (e.g. DROP ROLE …)
13 Lease Manager remove from index; mark Revoked
14 Audit append revoke-outcome entry

8.8 Seal/Unseal State Machine

State Trigger Next State Failure Edge
Uninitialized operator init completes Sealed init aborted mid-way → remain Uninitialized
Sealed (progress < k−1) submit valid share Sealed (progress+1) wrong/duplicate share → progress unchanged, error surfaced
Sealed (progress = k−1) submit final share Unsealed reconstructed key fails verification blob decrypt → Sealed, progress reset to 0, alarm raised

State Trigger Next State Failure Edge
Issued lease registered (§8.7 step 6) Active registration fails → issuance rolled back, no credential returned

RenewalPending engine renew hook ok Active (extended) upstream renew fails → Active (unchanged TTL), error surfaced
Active ttl elapses, sweeper picks up RevocationPending —
RevocationPending upstream revoke ok Revoked upstream revoke fails → RevocationFailed
RevocationFailed retry with backoff RevocationPending retry budget exhausted → ManualIntervention (FM-class, §25)

8.10 Audit Merkle Chain And Inclusion Proof

Leaves: leaf_i = HMAC-SHA256(day_key, canonical(entry_i)). Each entry also stores prev_hash = leaf_{i-1} (hash chain). Every checkpoint window (N entries or a time bound) a Merkle tree is built over the window's leaves; the root is HMAC'd and recorded as a checkpoint.

Inclusion-proof verification procedure:

  1. Locate the leaf index for the entry under question.
  2. Fetch the sibling-hash path from leaf to root (provided by the audit index).
  3. Recompute parents bottom-up: parent = H(left || right).
  4. Compare the recomputed root to the published checkpoint root for that window.
  5. Accept if equal; otherwise flag the entry and the whole window as tampered (I8).

8.11 Worked End-To-End Example

operator init (k=3,n=5) → 5 shares distributed, root token returned → 3 operators run operator unseal <share> → Unsealed → operator mounts secret/ (KV engine) → operator writes policy db-readonly → operator issues a scoped token with that policy attached → service authenticates with AppRole, receives a token → service calls GET secret/data/prod/db → policy check passes (read granted by db-readonly) → KV engine fetches, barrier decrypts → response returned, audit entry appended.

8.12 Malformed-Input Examples

  • A barrier record with a truncated ciphertext field: tag verification fails deterministically → VaultError::TamperedRecord, never partial plaintext (P6).
  • A policy rule capabilities = ["read", "sudo", "bogus"]: parser rejects unknown capability token at parse time, policy write is refused wholesale (no partial-policy install).
  • A Shamir share submitted with an x-coordinate colliding with an already-submitted share: reconstruction is refused before attempting interpolation (duplicate x-coordinate is mathematically degenerate).

8.13 Failure-Path Example

Rewrap crashes after 40% of a batch has moved from KeyEpoch(4) to KeyEpoch(5). On restart, the persisted RewrapCursor resumes from the last checkpointed offset; records already rewrapped decrypt correctly under epoch 5, the remainder still decrypt under epoch 4 (retained in the keyring until min_decryption_epoch advances) — no record is ever left undecryptable, satisfying I6/P14.
