Decisions (§9) · 35 ADRs

ADR-01

Language

Chosen

Rust

Rejected

Go, C/C++, Java

When the rejected choice is right

Team has zero Rust experience and must ship a stopgap in under a month

Why: Memory safety for key-material-holding process; constant-time crypto crates; no GC pause on secret memory

ADR-02

Build system

Chosen

Cargo workspace

Rejected

Bazel, plain Makefile-only

When the rejected choice is right

Monorepo already standardized on Bazel across polyglot services

Why: Native Rust tooling; workspace crate boundaries mirror module boundaries

ADR-03

Dependency policy

Chosen

Vetted minimal deps (cargo vet/cargo audit gated)

Rejected

Unrestricted crates.io, vendor-everything

When the rejected choice is right

A throwaway prototype spike that never reaches production

Why: Crypto crates need provenance; prefer audited RustCrypto crates

ADR-04

AEAD cipher

Chosen

ChaCha20-Poly1305 (RFC 8439)

Rejected

AES-256-GCM, XChaCha20-Poly1305

When the rejected choice is right

Deployment guarantees AES-NI and FIPS 140-3-validated module is mandatory

Why: Constant-time without AES-NI dependence; avoids GCM's catastrophic nonce-reuse failure mode

ADR-05

KDF

Chosen

Argon2id (RFC 9106) for passwords; HKDF (RFC 5869) for key expansion

Rejected

scrypt (Percival 2009), PBKDF2

When the rejected choice is right

Platform lacks a maintained Argon2 implementation and scrypt is already audited there

Why: Argon2id won the Password Hashing Competition; HKDF is cheap high-entropy expansion

ADR-06

Key hierarchy depth

Chosen

3 tiers: MK → KEK → DEK

Rejected

2 tiers (MK wraps data directly), 4+ tiers

When the rejected choice is right

Dataset small enough that a full rewrap is always sub-second

Why: Isolates rotation cost per tier without excess indirection

ADR-07

Seal mechanism

Chosen

Shamir threshold (default), cloud-KMS auto-unseal (optional)

Rejected

HSM-only seal, password-only seal

When the rejected choice is right

FIPS 140-3 Level 3 hardware custody is a compliance mandate

Why: Operational sovereignty by default; convenience path opt-in

ADR-08

Share distribution

Chosen

Out-of-band manual distribution to named operators

Rejected

Automated email/Slack distribution

When the rejected choice is right

A fully cloud-KMS auto-unseal design where no human share exists at all (§36)

Why: Automated distribution recreates the single-point-of-compromise Shamir exists to prevent

ADR-09

Storage backend

Chosen

Pluggable trait; Postgres default production backend

Rejected

Embedded sled/RocksDB only, S3-only

When the rejected choice is right

Single-node edge deployment with no external DB available

Why: Postgres gives transactional writes plus advisory locks for leader election in one dependency

ADR-10

Storage encryption granularity

Chosen

Per-record envelope (one AEAD op per record)

Rejected

Whole-file/table encryption, per-mount single key

When the rejected choice is right

Backend already provides transparent full-disk encryption and only backend theft is modeled

Why: Isolates a corrupted/tampered record; enables per-record rewrap

ADR-11

HA / leader election

Chosen

Storage-backend lock (advisory lock / row-TTL)

Rejected

Self-hosted Raft, external etcd coordination

When the rejected choice is right

Storage backend cannot provide atomic compare-and-swap locking (e.g. plain S3)

Why: Reuses the already-required storage backend; avoids a second consensus system

ADR-12

Consistency model

Chosen

Linearizable on leader; standby reads disabled by default

Rejected

Eventual consistency everywhere, quorum reads

When the rejected choice is right

A proven-tolerant workload needs performance-standby read scaling (§31)

Why: A secret read must reflect the latest revocation, never a stale one

ADR-13

Auth method set (Phase 4)

Chosen

Token, AppRole, mTLS-cert (RFC 8705)

Rejected

SMS/email OTP, username+password only

When the rejected choice is right

An internal admin UI needs human login with layered MFA

Why: Machine-to-machine methods with no human-readable long-lived secret

ADR-14

Token format

Chosen

Opaque random token + separate accessor

Rejected

Self-contained JWT (RFC 7519)

When the rejected choice is right

Federated multi-service deployment needs stateless verification with no round trip

Why: Opaque tokens are revocable by deleting server state; JWTs remain valid until expiry

ADR-15

Policy model

Chosen

Path-based capability rules

Rejected

Full RBAC role hierarchy, arbitrary-attribute ABAC

When the rejected choice is right

Authorization must depend on runtime attributes (source IP, time-of-day) at scale

Why: Matches storage hierarchy directly; deny-by-default is simple to reason about (Saltzer & Schroeder 1975)

ADR-16

Lease tracking structure

Chosen

In-memory min-heap by expiry + persisted index

Rejected

Pure DB-scan sweep, external cron scheduler

When the rejected choice is right

Tracked-lease count stays under ~10,000 and simplicity outweighs sweep latency

Why: O(log n) next-expiry lookup; avoids full-table scans per tick

ADR-17

Dynamic-engine plugin boundary

Chosen

In-process trait object, compiled in

Rejected

Out-of-process plugin over gRPC

When the rejected choice is right

Third-party/untrusted engine code needs blast-radius isolation

Why: Simpler for this scope; removes a network hop from issuance

ADR-18

Rotation strategy

Chosen

Read-old/write-new key epochs, no forced downtime

Rejected

Stop-the-world re-encrypt, dual-write windows

When the rejected choice is right

Dataset small enough (§34) that a pause is imperceptible

Why: Matches P8/I6; keeps the system available during rotation

ADR-19

Rewrap batching

Chosen

Cursor-based incremental batches, checkpointed

Rejected

Single-transaction full rewrap

When the rejected choice is right

Total secret count small enough for one transaction inside the backend's timeout

Why: Bounds memory; resumable after crash (I6)

ADR-20

Audit-log integrity

Chosen

HMAC-chained entries + periodic Merkle checkpoint

Rejected

Plain append-only file, per-entry digital signatures

When the rejected choice is right

Individual entries must be independently third-party-verifiable with no checkpoint access

Why: Detects any single deletion/reorder cheaply (Crosby & Wallach 2009; RFC 6962)

Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Cloud-KMS Auto-Unseal, No Shamir Ceremony

   Client → API → Barrier ⇄ Cloud KMS.Decrypt(wrapped_KEK)
                       │
                 Storage Backend

Winning regime: cloud-only fleets prioritizing zero-touch restarts over operator-held trust. Embodying system: AWS-KMS auto-unseal, already an optional mode in HashiCorp Vault itself. Rejected here as the default because it moves the root of trust entirely to the cloud provider (ADR-07), contradicting P1's operator-sovereignty stance; retained as an opt-in path (§37).

HSM-Rooted, Master Key Never Leaves Hardware

   Client → API → Barrier ⇄ PKCS#11 HSM (MK resident, unwrap-only interface)
                       │
                 Storage Backend

Winning regime: FIPS 140-3 Level 3 compliance mandates where software-resident key material is disallowed regardless of Shamir's mathematical guarantees. Embodying system: HSM-backed enterprise Vault/CloudHSM-fronted KMS deployments. Rejected as the default because it adds a hardware dependency and cost this blueprint's phases don't require to demonstrate the key -hierarchy and unseal concepts (deferred, §37).

Stateless, Git-Committed Encrypted-File Model

   developer → age/PGP-encrypt → ciphertext file committed to git
   CI/deploy → age/PGP-decrypt (recipient key) → plaintext at deploy time
   (no running service; no lease; no revocation)

Winning regime: small teams, GitOps pipelines, low secret-change velocity. Embodying system: Mozilla SOPS, age. Rejected here because it provides no lease/revocation model, no dynamic secrets, and no runtime authorization — this blueprint's domain (§1) requires all three.

Short-Lived-Identity-Only, No Stored Secrets

   Workload → SPIRE Agent → SVID (short-lived X.509/JWT)
   Peer verifies the SVID via a SPIFFE trust bundle
   (identity replaces "secret" entirely for service-to-service auth)

Winning regime: pure service-to-service authentication where mutual identity proof suffices and no application-level secret is actually needed. Embodying system: SPIFFE/SPIRE. Rejected as a replacement (noted as complementary in §33) because it does not address static application secrets, third-party API keys, or dynamic database credentials — the core domain targeted here.
