Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If the storage backend silently reorders a keyring update ahead of a barrier-record write that depended on it, what does the read path observe, and which invariant and ADR determine whether that is even possible? (§7, §9 ADR-11/ADR-12)
  2. Why does KEK rotation not require rewrapping application data, and what breaks if the hierarchy were two tiers instead of three? (§8, §20)
  3. During a leader failover mid-rewrap, which component guarantees the rewrap doesn't resume from the wrong offset, and how does that interact with the leader lock's fencing token? (§20, §22)
  4. What specifically prevents a token accepted at t=ttl−1s under one node's clock from also being accepted at t=ttl+1s under a skewed standby's clock during a rolling failover? (§16, §27)
  5. If an operator's Shamir share is compromised but the vault is never resealed, what is actually protected, and by which invariant? (§14, §7 I11)
  6. Why is audit-or-refuse not simply a best-effort logging guarantee, and what does the bounded queue trade away to get that guarantee? (§6, §21)
  7. How does the policy engine's deny-by-default interact with a broadly-granted sudo capability — does sudo bypass deny, and where is that decided? (§8, §17)
  8. What happens to leases issued under a dynamic-engine role deleted mid-lease, and how does that interact with the rewrap worker touching the same storage prefix? (§19, §20)
  9. Given the §34 audit-bytes/day ceiling, what operational lever reduces retention cost without weakening I8's tamper-evidence guarantee? (§34, §21)
  10. Why does the transit engine maintain a DEK versioning scheme separate from the barrier's own storage DEKs, and what breaks if they shared one keyring? (§22, §8)
  11. What is the actual difference between a sealed node and a standby node holding no lock, and could an attacker exploit confusion between the two states? (§8, §22)
  12. If the storage backend's advisory-lock table becomes unavailable while the rest of the backend is healthy, why is refusing all writes correct rather than electing a leader from cached state? (§22, §7 I2)
  13. How does the memory-hygiene verification pass actually prove I10, given that a compiler could in principle still elide a zeroize call the test doesn't happen to exercise? (§23, §7 I10)
  14. Why is the rewrap batch size a tunable rather than a fixed constant, and which two competing §4 targets does it trade off against each other? (§20, §4)
  15. What would have to change in the policy grammar to support the deferred OIDC/JWT federation without breaking existing deny-by-default guarantees? (§8, §37)
  16. Why does the Shamir share format never store a ceremony identifier inside the cryptographic share itself, and how does that constrain the mitigation for cross-ceremony share confusion? (§8, §14)
  17. If two independent dynamic-engine roles template against the same upstream user-naming scheme and collide, which invariant catches it, and at what phase boundary? (§19, §7 I5)
  18. What is the actual cost, in the §34 model, of choosing a smaller Merkle checkpoint window to shrink the forensic gap in T6, and is it worth paying at the computed audit-bytes/day scale? (§34, §24)
  19. Why does this blueprint reject a stateless JWT token format even though it would remove a database round trip on every request, and under which alternative architecture would that tradeoff flip? (§9 ADR-14, §36)
  20. How does the scalability analysis's claim that lease-tracking and audit dominate before crypto get falsified or confirmed by the §34 numbers, concretely? (§31, §34)

32. Mental Models & First Principles

MM1 — "A vault does not keep secrets — it keeps one secret and rents out the rest under a clock." Predicts every dynamic credential should be modeled as a lease, not a stored value. Bug class without it: credentials that live forever because nobody built a revocation path. Resolved in §18 / §19.

MM2 — "Envelope encryption converts the key-rotation problem from rewriting all data into rewriting one wrapper." Predicts KEK rotation is near-instant regardless of dataset size. Bug class without it: rotation that requires touching every record, making rotation too expensive to ever actually perform. Resolved in §20.

MM3 — "Sealed is safety; unsealed is a liability you accept on purpose." Predicts that any code path making unsealing more convenient without quorum authorization is a regression, not a feature. Bug class without it: auto-unseal creeping into places that erode P1. Resolved in §12 / §14.

MM4 — "A capability you didn't grant explicitly is a capability the attacker gets for free if you get the glob precedence wrong." Predicts glob-precedence bugs are privilege-escalation bugs, not cosmetic ones. Resolved in §17.

MM5 — "An audit log you can edit isn't an audit log — it's a suggestion." Predicts any design where one actor can both write and later silently delete an entry has failed the audit requirement, regardless of file format. Resolved in §21.

MM6 — "Time is a security parameter, not a formatting choice." Predicts TTL/lease math on the wrong clock source silently changes security guarantees. Resolved in §16 (I7) and §18 (P11).

MM7 — "A rewrap interrupted is a fact about your keyring, not a fact about your data." Predicts a correctly designed rewrap can be crashed at any point without ever losing readability of a single record. Resolved in §20 (I6).

MM8 — "The storage backend is a place to put ciphertext, not a place to put trust." Predicts any design requiring the storage backend to enforce a security property (rather than durability/ availability alone) has misplaced the trust boundary. Resolved in §13 (P10) and §24 (T2, T11).

Required reading (§5)

Books

  • Ferguson, Schneier & Kohno — Cryptography Engineering — chapters on block-cipher modes and AEAD, key management, and generating randomness — extract the AEAD composition and nonce discipline rules — applied in §13 (Phase 1).
  • Anderson — Security Engineering, 3rd ed. — chapters "Access Control" and "Cryptography" — extract protection-matrix and capability-vs-ACL tradeoffs — applied in §17 (Phase 5).
  • Schneier — Applied Cryptography, 2nd ed. — chapters on key management and secret sharing — extract practical Shamir construction concerns — applied in §14 (Phase 2).
  • Menezes, van Oorschot & Vanstone — Handbook of Applied Cryptography — chapter 12, key establishment — extract key-hierarchy and key-wrapping patterns — applied in §13 (Phase 1).
  • Katz & Lindell — Introduction to Modern Cryptography — chapter on MACs and authenticated encryption — extract the formal AE security definitions — applied in Phase 1 (§13) and Phase 8 (§20).
  • Boneh & Shoup — A Graduate Course in Applied Cryptography — chapters on secret sharing and key derivation — extract HKDF's extract-then-expand rationale — applied in §13 (Phase 1).

Papers

  • Shamir, 1979, How to Share a Secret, CACM — the k-of-n threshold construction — applied in §14 (Phase 2).
  • Krawczyk, 2010, Cryptographic Extraction and Key Derivation: The HKDF Scheme, CRYPTO — extract-then-expand KDF — applied in §13 (Phase 1).
  • Bellare & Namprempre, 2000, generic composition of authenticated encryption — why encrypt-then-MAC is the safe composition — applied in §13 (Phase 1).
  • Rogaway, 2002, authenticated-encryption definitions — AEAD's AAD binding — applied in §13 (Phase 1) and §8 (barrier record layout).
  • Percival, 2009, scrypt — memory-hard KDF design tradeoffs, contrasted with Argon2id — applied in Phase 2 (§14).
  • Biryukov, Dinu & Khovratovich, 2016, Argon2, EuroS&P — the Argon2id parameterization used for any password-derived material — applied in Phase 2 (§14).
  • Saltzer & Schroeder, 1975, The Protection of Information in Computer Systems, Proc. IEEE — fail-safe defaults, least privilege — applied in §17 (Phase 5).
  • Lampson, 1974, the protection matrix — the capability/path model's ancestor — applied in §17 (Phase 5).
  • Samuel et al., 2010, CCS, TUF (The Update Framework) — threshold trust and role separation for distributed signing — applied in §21 (Phase 9).
  • Torres-Arias et al., 2019, USENIX Security, in-toto — supply-chain attestation chaining — applied in §29 (Build & Release Engineering).
  • Crosby & Wallach, 2009, USENIX Security, tamper-evident history trees — the Merkle-chain structure underlying the audit log — applied in §21 (Phase 9).

Reference Implementations

  • HashiCorp Vault — vault/ (core), vault/barrier_aes_gcm.go, physical/ (storage backends), sdk/framework/ — lesson: the barrier-as-single-encrypt-point pattern; pitfall: its per-mount seal_wrap special-casing grew ad hoc, keep the barrier interface uniform instead — applied in §13 (Phase 1).
  • OpenBao — a community fork maintaining Vault's on-disk and wire format under Apache-2.0 — lesson: wire/format compatibility can outlive a single maintaining org; pitfall: divergent forks silently drift on mount-table schema, version it explicitly — applied in §27.
  • SPIFFE/SPIRE — spire/pkg/server/ca — lesson: short-lived workload identity as a complement to, not a replacement for, stored-secret management; pitfall: assuming SPIFFE identities remove the need for a vault — applied in §36.
  • Square Keywhiz — keywhiz-server — lesson: delivering secrets to a filesystem via FUSE avoids a client SDK; pitfall: any host compromise now has filesystem-level secret exposure — applied in §24 (T1).
  • Mozilla SOPS — getsops/sops — lesson: a stateless, git-committed encrypted-file model needs no running service; pitfall: no lease or revocation model exists once a file is decrypted somewhere — applied in §36.
  • age (FiloSottile/age) — lesson: minimal, modern encrypted-file format design discipline; pitfall: single-recipient model has no capability-based authorization layer — applied in §36.
  • AWS KMS published cryptographic-details whitepaper — lesson: envelope encryption at cloud scale with an HSM-backed root of trust; pitfall: the root of trust is opaque to the operator, this blueprint keeps the master key operator-held by default — applied in §9 (ADR-07).

Glossary (§38) · 59 terms · site-wide glossary

Seal
: the vault's locked-at-rest state with no key material in process memory.
Unseal
: the deliberate, quorum-authorized reconstruction of the master key in memory.
Barrier
: the encryption layer between vault logic and the storage backend; the sole encrypt/decrypt path.
Master key (MK)
: the root of the key hierarchy; never persisted in usable form.
Key-encryption key (KEK)
: wraps data-encryption keys; itself wrapped by the master key.
Data-encryption key (DEK)
: encrypts storage records/secret payloads directly.
Envelope encryption
: encrypting data under a key that is itself encrypted by another key.
Key epoch
: a generation identifier for a KEK or DEK, enabling read-old/write-new rotation.
Rewrap
: re-encrypting a record under a newer key epoch without changing its plaintext.
Shamir share
: one fragment of a secret split via Shamir's threshold scheme.
Threshold (k-of-n)
: the minimum number of shares required to reconstruct a secret.
AEAD
: authenticated encryption with associated data.
AAD
: associated data authenticated alongside a ciphertext but not encrypted.
Nonce
: a value used once per encryption under a given key, never reused.
Zeroization
: overwriting secret memory so it cannot be recovered after use.
mlock
: an OS call preventing a memory page from being swapped to disk.
Token accessor
: a safe-to-log identifier for a token, distinct from the bearer token itself.
Orphan token
: a token not revoked when its parent token is revoked.
TTL
: time-to-live; the remaining validity window of a token or lease.
Renewal
: extending a token's or lease's TTL without issuing a new one.
Lease
: a record tracking an issued secret's lifecycle and revocation path.
Revocation
: the act of invalidating a token, lease, or dynamic credential.
Dynamic secret
: a credential generated on demand and tied to a lease.
Policy path glob
: a wildcard pattern (* or +) used in a policy's path match.
Capability
: one of create/read/update/delete/list/sudo/deny attached to a policy rule.
Deny-by-default
: the rule that absence of an explicit allow is treated as a deny.
Sudo capability
: a capability permitting operator-only privileged operations on a path.
Transit engine
: the mount providing encryption-as-a-service without exposing key material.
Tamper-evident log
: a log structured so any alteration is cryptographically detectable.
Inclusion proof
: a proof that a specific entry is included in a Merkle-tree checkpoint.
Performance standby
: a standby node serving reads locally under relaxed consistency.
Mount
: an instance of an engine or auth method bound to a specific path prefix.
Storage backend
: the durable, ciphertext-only persistence layer behind the barrier.
Keyring
: the ordered set of retained KEK/DEK epochs supporting old-ciphertext reads.
RewrapCursor
: a persisted progress marker for an in-flight rewrap.
Merkle tree
: a binary hash tree enabling compact inclusion proofs.
Hash chain
: a sequence of entries each referencing the hash of its predecessor.
HMAC
: a keyed hash used to authenticate audit entries and derive per-day audit keys.
HKDF
: an HMAC-based key-derivation function (RFC 5869).
Argon2id
: a memory-hard password-hashing/KDF algorithm (RFC 9106).
ChaCha20-Poly1305
: the AEAD cipher locked in as this system's default (RFC 8439).
GF(2^8)
: the finite field used for byte-wise Shamir polynomial arithmetic.
Lagrange interpolation
: the polynomial-reconstruction technique used to recover a secret from shares.
Leader election
: the process by which one HA node becomes the sole active node.
Advisory lock
: a storage-backend primitive used to implement leader election.
Split-brain
: a failure state where more than one node believes it is the leader.
Standby
: a non-leader HA node forwarding writes and, by default, refusing reads.
AppRole
: an auth method pairing a stable role-id with a short-lived secret-id.
mTLS
: mutual TLS, used here as a certificate-based auth method (RFC 8705).
Identity
: the verified principal produced by a successful auth-method call.
Periodic token
: a token that renews indefinitely while used, within its period.
Soft-delete
: marking a secret version deleted while retaining its underlying data.
Hard-destroy
: irreversibly removing a secret version's underlying ciphertext.
Rollback
: creating a new secret version whose data matches a prior version's.
Secret version
: one immutable, append-only revision of a KV secret.
Conformance fixture
: a named input/expected-output pair used to validate behavior exactly.
Fault injection
: deliberately introducing a failure (crash, partition) to test recovery.
RPO
: recovery point objective — the maximum acceptable data loss window.
RTO
: recovery time objective — the maximum acceptable time to restore service.
