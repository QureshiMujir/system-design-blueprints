Project Number: 168

Project Name: Secret Manager / Vault

1. Goal & Scope

Build, from scratch, in Rust, an encrypted secret-management service structured around an envelope-encryption key hierarchy rooted in a sealed master key: a MasterKey reconstructed only via Shamir-threshold unseal (Shamir 1979) wraps a rotating set of KeyEncryptionKeys, each of which wraps the DataEncryptionKeys that actually encrypt storage records and secret payloads under an AEAD scheme (RFC 8439, RFC 5116). On top of the barrier sit pluggable authentication methods issuing short-lived tokens, a path-based policy engine performing deny-by-default authorization, a static key-value secret engine with versioning and rollback, a dynamic credential engine framework issuing leased, auto-revoked secrets, a rotation/rewrap worker that moves ciphertext between key epochs without downtime, a tamper-evident hash-chained audit log with Merkle inclusion proofs (Crosby & Wallach 2009; RFC 6962), and a transit encryption-as-a-service path that lets client applications use vault-held keys without the key material ever leaving the process. The system is HA-capable via a storage-backend leader lock.

Phase-0 deliverable — a Cargo workspace skeleton with CI green on:

  1. vault-crypto — AEAD, HKDF, Argon2id, Shamir primitives; no I/O.
  2. vault-barrier — envelope-encryption layer over the storage trait; owns the key hierarchy.
  3. vault-storage — StorageBackend trait plus a local-filesystem and a Postgres backend.
  4. vault-core — seal/unseal state machine, mount table, router skeleton.
  5. vault-policy — policy grammar, parser, capability evaluator (stubbed until Phase 5).
  6. vault-api — HTTP listener skeleton (routes return 501 until engines land).
  7. vault-cli — operator CLI: init, seal, unseal, status.
  8. xtask — build, fixture-generation, and conformance-harness driver.
  9. conformance/ — the fixture corpus consumed from Phase 0 onward (§23).

Boundaries. Provides: sealed storage, key hierarchy, unseal ceremony, auth methods, token store, policy authorization, static and dynamic secret engines, lease tracking and revocation, key rotation/rewrap, tamper-evident audit, transit EaaS, single-process HA leader election. Delegates: hardware key custody to a PKCS#11 HSM when configured (PhaseDeferred, see below); TLS termination to rustls (ADR-21); upstream credential-system mechanics (e.g. the target Postgres cluster's own CREATE ROLE privilege model) to that system. Does not provide: an X.509 certificate authority / CT log, a human-facing password manager, a web UI, a SIEM, or cross-region replication in the phases specified here.

Non-goals. A general PKI/CA issuance engine (related, distinct system — a natural future mount, not built here). A bespoke audit query language — audit sinks export to an external SIEM. Multi-region replicas. A GUI.

Deployment model. Single node (dev, vault-storage local-file backend). HA cluster (prod, Postgres or etcd/Consul-class backend with an advisory lock for leader election, standbys forwarding writes). Every node is, independently, either sealed (no key material in process memory, only unseal/status operations accepted) or unsealed (barrier operational). Sealed is the default and the safe state; unsealed is a deliberate, quorum-authorized transition (P1).

Users/operators. Operators run operator init, hold Shamir shares, perform the unseal ceremony, author policies, and run rotation. Service identities authenticate via non-interactive auth methods (AppRole, mTLS) to fetch static or dynamic secrets. Auditors consume the exported, verifiable audit stream read-only.

What later phases unlock. After Phase 11 (§23), the transit engine and dynamic-credential framework are stable mount points other blueprinted services (workflow engines, API gateways, container registries) can depend on for credential issuance and encryption-as-a-service, without this document taking on their scope.

Rust + rationale. Memory safety for a process that holds raw key material in its address space is non-negotiable; the zeroize crate ecosystem gives auditable wipe-on-drop; RustCrypto crates give constant-time primitives without an OpenSSL FFI boundary. Rejected: Go (GC pauses interact badly with zeroization guarantees, and Vault itself already occupies that niche — building in Go adds no differentiated learning); C/C++ (memory unsafety is unacceptable for a process whose entire job is protecting key material); Java/JVM (heap dumps and GC copying undermine zeroization; no first-class constant-time primitive story).

Prerequisites. Working knowledge of AEAD composition (Bellare & Namprempre 2000; Rogaway 2002), finite-field arithmetic (for Shamir), async Rust, and basic PKI/TLS concepts.

Timeline. Twelve phases (§12–§23), each independently shippable and independently tested against the conformance corpus (§23, §28).

Deferrals (full register at §37): PhaseDeferred("§19 Phase 7 — Dynamic Credential Engines") for a PKI/CA issuance engine; PhaseDeferred("§22 Phase 10 — Transit Encryption-as-a-Service + HA/Leader Election") for cross-region replication and performance-standby read scaling; PhaseDeferred("§14 Phase 2 — Shamir Unseal + Share Ceremony") for PKCS#11 HSM master-key custody; PhaseDeferred("§16 Phase 4 — Auth Methods + Token Store") for OIDC/JWT external IdP federation and response-wrapping.

2. Why Build This

Envelope encryption and key-hierarchy design. Shamir threshold secret sharing over a finite field, implemented, not just cited. AEAD composition pitfalls (nonce reuse, tag-then-decrypt ordering). HKDF-based key derivation and domain separation. Lease-based revocation as a first-class design object, not an afterthought TTL column. Deny-by-default path-capability authorization and glob-precedence surprises. Tamper-evident hash chains and Merkle inclusion proofs, verified by hand once. Key rotation and rewrap without downtime — the read-old/write-new discipline. Zeroization under an optimizing compiler. Building a system whose failure mode is "refuse the operation," not "silently do the insecure thing."

What Mastery Looks Like

  • Reconstructing a 256-bit key from k-of-n Shamir shares by hand over GF(2^8), and explaining why GF(2^8) is used instead of integers mod a prime (Phase 2, §14).
  • Explaining, with the equations, why envelope encryption turns "rewrite all data" into "rewrite one wrapper," and demonstrating it with a timed rewrap (Phase 8, §20).
  • Writing a policy evaluator that is deny-by-default and correctly ranks * against + against literal path segments (Phase 5, §17).
  • Building a lease expiry sweeper that holds the max-tracked-lease ceiling from §4 without falling behind the sweep interval (Phase 6, §18).
  • Constructing and verifying a Merkle inclusion proof for one audit entry by hand against a published checkpoint root (Phase 9, §21).
  • Taking a memory snapshot of an unsealed process, sealing it, and demonstrating the master key and DEKs are unrecoverable from a second snapshot (Phase 1, §13; Phase 0, §12).
  • Running the Phase 11 conformance suite (§23) to green, including a fault-injected crash mid-rewrap that must resume from the persisted RewrapCursor with no mixed-epoch record left unreadable.

API Listener — terminates TLS 1.3, parses HTTP, is the sole protocol boundary; rejects malformed requests before they reach auth. Auth Methods — pluggable identity verification (token, AppRole, mTLS) producing an Identity and, on success, a Token. Token Store — persists tokens by hashed id and by accessor; the trust boundary where "bearer of this string" becomes "this Identity." Policy Engine — evaluates the request path and required capability against the token's attached policies; deny-by-default; runs before any secret material is touched (I3). Router/Mount Table — maps a path prefix to a mounted engine instance; concurrency boundary for hot-swapping mounts via ArcSwap. KV Engine — static secrets, versioned, with metadata and soft-delete/rollback. Dynamic Credential Engines — generate secrets on demand against an upstream system and register a lease. Transit Engine — encrypts and signs on behalf of callers without exposing key material; the EaaS path. Lease/Expiration Manager — tracks every issued lease, sweeps expiries, drives revocation; a queue boundary between issuance and cleanup. Rotation/Rewrap Worker — leader-only background job moving ciphertext across key epochs (§20); reads a persisted RewrapCursor so it resumes after a crash. Cryptographic Barrier — the sole encrypt/decrypt path to storage; owns the key hierarchy; every read/write from any engine passes through it (I2). Storage Backend — durable, opaque to plaintext; also hosts the leader-election lock. Audit Log — a queue-fed, append-only, hash-chained sink; a write that cannot be audited is refused (P5). Seal/Unseal Subsystem + Shamir Share Collector — the only path that ever reconstructs the master key in memory, and only transiently. Telemetry — cross-cutting metrics/tracing that must never carry secret fields (I1, ADR-24).

6. Design Principles

P1 — Sealed is the default state. The master key never exists in persistent storage in usable form. Unsealed is a deliberate, quorum-authorized transition, not the resting state. Tradeoff: every restart requires an unseal ceremony unless auto-unseal is configured, trading convenience for the guarantee that storage theft alone yields nothing. Violating it (e.g. persisting the reconstructed key) turns the whole barrier into a no-op.

P2 — Envelope encryption everywhere. No data is ever encrypted directly by the master key; the hierarchy is MK → KEK → DEK. Tradeoff: an extra unwrap per operation versus the ability to rotate a tier without touching all data. Violating it collapses rotation cost to "rewrite everything" (see MM2, §32).

P3 — Every secret has a lease and a revocation path. A leaked dynamic credential is bounded in time by construction. Tradeoff: bookkeeping cost (a lease record per issued secret) against an unbounded exposure window. Violating it means "leaked" and "leaked forever" become synonyms.

P4 — Deny by default. Authorization requires an explicit matching allow; absence of a rule is a deny, and an explicit deny always wins. Tradeoff: verbose policy authoring versus never accidentally over-granting. Violating it is a silent privilege escalation.

P5 — Audit-or-refuse. A write that cannot be audited is refused rather than performed. Tradeoff: availability during audit-sink outage versus a guarantee that every mutating operation is forensically recoverable. Violating it makes the audit log optional in exactly the situations where it matters most (an active incident).

P6 — AEAD only, never bare encryption. Every ciphertext is authenticated; a tampered ciphertext fails to decrypt rather than returning garbage plaintext. Tradeoff: a fixed per-op tag overhead (16 bytes) versus silent corruption. Violating it turns storage corruption into silent data poisoning.

P7 — Path is the unit of authorization granularity. Every mounted resource is addressed and authorized by a hierarchical path, matching the storage layout. Tradeoff: coarser control than attribute-based rules, in exchange for policies that are readable at a glance.

P8 — Rotate without downtime. Key rotation follows read-old/write-new: new writes use the new epoch, old ciphertext remains readable under retained old epochs until rewrapped. Tradeoff: old key material must be retained until rewrap completes, expanding the keyring, against zero-downtime rotation.

P9 — Zeroize on drop. Secret material is wiped from memory as soon as its scope ends, using a mechanism the optimizer cannot elide. Tradeoff: a small constant cost per secret-holding type versus the possibility of key material surviving in a core dump or swapped page.

P10 — Backends are boundaries, not trust. Storage-backend compromise yields ciphertext, mount metadata, and traffic shape — never plaintext secrets on its own. Tradeoff: the backend must still be treated as semi-trusted for availability and metadata confidentiality.

P11 — Time is a security parameter. TTLs, sweep intervals, and clock skew tolerances are load-bearing, not formatting details; lease and token expiry math uses a monotonic clock (ADR-33). Violating it lets a wall-clock step expire tokens early or extend them past their intended life.

P12 — Idempotent, defined recovery. Every cataloged failure mode (§25) has both a detection signal and a defined recovery procedure, manual or automatic — never detection alone.

P13 — Explicit capability sets. Capabilities (create/read/update/delete/list/sudo/deny) are attached explicitly by policy, never inferred from the HTTP verb alone, so a POST that mutates nothing does not implicitly require create.

P14 — Atomic-per-secret rewrap. A secret's rewrap is a single atomic operation; it is never left readable under a retired key only, and never left in a state where neither key decrypts it.

8. Domain Model

8.1 Key Hierarchy

Key Rooted By Wrapped By Rotated When Rotation Cost
MasterKey (MK) Shamir shares (k of n) never wrapped; exists only transiently in memory Rare — disaster or confirmed compromise Full re-init and re-share ceremony
KeyEncryptionKey (KEK) MK MK Scheduled (e.g. quarterly) or on suspected compromise Rewrap the (small) DEK table only (§20)
DataEncryptionKey (DEK) KEK active KEK at mint time Scheduled (e.g. daily/weekly) or on demand Rewrap affected storage records (§20)

Display equations (AEAD-Enc/Dec = ChaCha20-Poly1305, RFC 8439):

KEK_active            = AEAD-Enc(MK, nonce_k, KEK_material,  AAD = "kek" || kek_epoch_id)
DEK(e)                = AEAD-Enc(KEK_active_at_mint(e), nonce_d, DEK_material(e), AAD = "dek" || e)
Ciphertext(path, v)   = AEAD-Enc(DEK(e), nonce_r, plaintext, AAD = mount_id || path)

Unwrap is the corresponding AEAD-Dec; a failed tag check yields VaultError::TamperedRecord, never a "best effort" plaintext (P6).

AAD is not stored inline: it is mount_id (16 B UUID) || storage_path (UTF-8), recomputed from the lookup key at read time. This binds ciphertext to its location — copying a valid record to a different path fails tag verification.

8.3 Shamir Share Format And Reconstruction

Each 256-bit master key is split byte-plane-wise: for byte i of 32, a degree-(k-1) polynomial f_i(x) = s_i + a_1·x + a_2·x^2 + … + a_{k-1}·x^{k-1} is built over GF(2^8) (Rijndael's reduction polynomial x^8+x^4+x^3+x+1), with s_i the secret byte as the constant term and a_1..a_{k-1} random. Share j (for n operators) is (x_j, [f_1(x_j), …, f_32(x_j)]) — one x-coordinate, 32 y-values.

Reconstruction (Lagrange interpolation at x = 0, arithmetic in GF(2^8)):

s_i = Σ_{j=1}^{k}  y_i,j · Π_{m=1..k, m≠j}  (0 − x_m) / (x_j − x_m)      (all ops in GF(2^8))

Worked example (k=3, n=5, one byte plane, illustrative values): shares at x = {1,2,3,4,5} carry y-values {y1,y2,y3,y4,y5} derived from f(x) = s + a1·x + a2·x². Given any 3 of the 5 (say x=1,3,4), the Lagrange sum above reconstructs s exactly; any 2 shares (k−1) leave s information-theoretically undetermined — every possible byte value remains equally likely (I11).

8.4 Policy Grammar (EBNF)

policy          ::= { path_block } ;
path_block      ::= "path" path_string "{" capability_stmt { capability_stmt } "}" ;
capability_stmt ::= "capabilities" "=" "[" capability { "," capability } "]" ;
capability      ::= "create" | "read" | "update" | "delete" | "list" | "sudo" | "deny" ;
path_string     ::= '"' segment { "/" segment } '"' ;
segment         ::= "*" | "+" | literal ;
literal         ::= ident_char { ident_char } ;
ident_char      ::= letter | digit | "-" | "_" | "." ;

Path-matching precedence (highest wins, independent of Deny which always overrides):

Match Type Specificity Rank Example Notes
Exact literal path 1 (highest) secret/data/prod/db matches only that exact path
Prefix + trailing * 2 secret/data/prod/* deepest matching prefix wins among globs
Single-segment + 3 secret/data/+/db + consumes exactly one path segment
Root/broad * 4 (lowest) secret/* matches everything under the prefix
any rule with deny overrides all — explicit deny always wins regardless of rank

Capability set: create, read, update, delete, list, sudo (bypass certain operator-only checks), deny (explicit negative, always wins).

Worked authorization trace. Token policies = [db-readonly, default]. db-readonly: path secret/data/prod/db/* → [read, list]. default: path secret/data/* → [read]. Request: PUT secret/data/prod/db/creds (new path ⇒ required capability = create). Trace: (1) compute required capability = create; (2) match db-readonly rule, rank 2, grants {read, list} — no create; (3) match default rule, rank 2, grants {read} — no create; (4) no deny rules present; (5) no rule anywhere grants create; (6) deny by default (P4) — 403.

8.10 Audit Merkle Chain And Inclusion Proof

Leaves: leaf_i = HMAC-SHA256(day_key, canonical(entry_i)). Each entry also stores prev_hash = leaf_{i-1} (hash chain). Every checkpoint window (N entries or a time bound) a Merkle tree is built over the window's leaves; the root is HMAC'd and recorded as a checkpoint.

Inclusion-proof verification procedure:

  1. Locate the leaf index for the entry under question.
  2. Fetch the sibling-hash path from leaf to root (provided by the audit index).
  3. Recompute parents bottom-up: parent = H(left || right).
  4. Compare the recomputed root to the published checkpoint root for that window.
  5. Accept if equal; otherwise flag the entry and the whole window as tampered (I8).

8.11 Worked End-To-End Example

operator init (k=3,n=5) → 5 shares distributed, root token returned → 3 operators run operator unseal <share> → Unsealed → operator mounts secret/ (KV engine) → operator writes policy db-readonly → operator issues a scoped token with that policy attached → service authenticates with AppRole, receives a token → service calls GET secret/data/prod/db → policy check passes (read granted by db-readonly) → KV engine fetches, barrier decrypts → response returned, audit entry appended.

8.12 Malformed-Input Examples

  • A barrier record with a truncated ciphertext field: tag verification fails deterministically → VaultError::TamperedRecord, never partial plaintext (P6).
  • A policy rule capabilities = ["read", "sudo", "bogus"]: parser rejects unknown capability token at parse time, policy write is refused wholesale (no partial-policy install).
  • A Shamir share submitted with an x-coordinate colliding with an already-submitted share: reconstruction is refused before attempting interpolation (duplicate x-coordinate is mathematically degenerate).

8.13 Failure-Path Example

Rewrap crashes after 40% of a batch has moved from KeyEpoch(4) to KeyEpoch(5). On restart, the persisted RewrapCursor resumes from the last checkpointed offset; records already rewrapped decrypt correctly under epoch 5, the remainder still decrypt under epoch 4 (retained in the keyring until min_decryption_epoch advances) — no record is ever left undecryptable, satisfying I6/P14.

11. Core Schema & Types

// MasterKey — root of trust; exists only between unseal and reseal.
// Owner: Seal subsystem. Mutation: none after reconstruction (immutable material).
// Concurrency: guarded by a single ArcSwapOption, read by the barrier only.
// Persistence: NEVER persisted in usable form (I1, P1).
// Serialization: no Serialize impl exists — compile-time prevention of accidental encoding.
// Compatibility: format version tracked via KeyEpoch, not this type.
// Zeroization: `zeroize` on Drop (ADR-22); mlock'd page (ADR-22).
struct MasterKey([u8; 32]);

// KeyEpoch — identifies which DEK generation encrypted a given record.
// Owner: vault-barrier. Mutation: monotonic increment only, no reuse.
// Persistence: stored in BarrierRecord header (§8.2). Serialization: u32 BE.
// Compatibility: old epochs retained until min_decryption_epoch advances (§27).
struct KeyEpoch(u32);

// KeyEncryptionKey — wraps DataEncryptionKeys; itself wrapped by MasterKey.
// Owner: vault-barrier keyring. Mutation: rotated on schedule/compromise (ADR-07).
// Concurrency: ArcSwap<Keyring> hot-swap. Persistence: wrapped form in sys/keyring.
// Zeroization: `zeroize` on Drop; never logged (ADR-24).
struct KeyEncryptionKey { epoch: KeyEpoch, material: SecretBytes32 }

// DataEncryptionKey — encrypts storage records/secret payloads directly.
// Owner: vault-barrier. Mutation: minted per rotation cycle (§20).
// Persistence: wrapped by active KEK, stored in sys/keyring. Zeroization: on Drop.
struct DataEncryptionKey { epoch: KeyEpoch, wrapped_by_kek: KeyEpoch, material: SecretBytes32 }

// SealState — the seal/unseal state machine (§8.8).
// Owner: vault-core. Mutation: only via the unseal/seal transitions. Concurrency: AtomicU8.
enum SealState { Uninitialized, Sealed { progress: u8 }, Unsealed }

// UnsealProgress — tracks submitted shares toward threshold.
// Owner: Seal subsystem. Mutation: append-only until threshold or reset on failure.
// Persistence: in-memory only; reset on process restart (shares are not stored, I11).
struct UnsealProgress { threshold: u8, submitted: Vec<RecoveryShare> }

// RecoveryShare — one Shamir share (§8.3).
// Owner: submitting operator (external). Serialization: base64 CLI transport only.
// Zeroization: wiped immediately after reconstruction attempt.
struct RecoveryShare { x: u8, y: [u8; 32] }
// BarrierRecord — on-storage envelope (§8.2).
// Owner: vault-barrier. Mutation: write-once per version; new version = new record.
// Persistence: the sole on-disk representation of any encrypted value.
struct BarrierRecord { version: u8, key_epoch: KeyEpoch, nonce: [u8; 12], tag: [u8; 16], ciphertext: Vec<u8> }

// StoragePath — canonical, normalized path used for both storage keys and AAD.
// Owner: router/barrier. Mutation: immutable once constructed; normalization is mandatory
// before any policy check (prevents CVE-2022-40718-class path-traversal bypass).
struct StoragePath(String);

// SecretVersion — one version of a KV secret (§14).
// Owner: KV engine. Mutation: append-only; prior versions retained per policy.
// Persistence: logical/<mount>/data/<path>/<version>. Compatibility: version counter never reused.
struct SecretVersion { version: u32, created_time: MonotonicTime, deletion_time: Option<MonotonicTime>, data: SecretBytes }

// SecretMetadata — version index + retention policy for a KV path.
// Owner: KV engine. Mutation: updated on every write/delete/rollback.
struct SecretMetadata { current_version: u32, oldest_version: u32, max_versions: u32, versions: BTreeMap<u32, SecretVersion> }

// Policy — a named set of path rules (§8.4).
// Owner: vault-policy. Mutation: whole-document replace, never partial patch (atomicity).
// Persistence: sys/policies/<name>. Serialization: parsed grammar AST, not raw text, at eval time.
struct Policy { name: String, rules: Vec<PathRule>, created_at: WallClockTime }

// PathRule — one path/capability binding within a Policy.
struct PathRule { path_pattern: String, capabilities: Vec<Capability>, specificity_rank: u8 }

// Capability — the fixed capability set (§8.4). Mutation: none, fixed enum.
enum Capability { Create, Read, Update, Delete, List, Sudo, Deny }

// Token — the primary bearer credential (§8.5).
// Owner: vault-auth token store. Mutation: ttl/renew_count updated on renewal only.
// Persistence: stored hashed, never in plaintext (I1). Zeroization: id wiped after hashing.
struct Token { id_hash: [u8; 32], accessor: TokenAccessor, parent: Option<TokenAccessor>,
    policies: Vec<String>, ttl: Duration, max_ttl: Duration, renewable: bool,
    orphan: bool, period: Option<Duration>, num_uses: Option<u32>, entity_id: Option<Uuid> }

// TokenAccessor — safe-to-log token identifier, distinct from the bearer id.
struct TokenAccessor(Uuid);
// AuthMethod — pluggable identity-verification trait boundary (ADR-13).

    fn authenticate(&self, req: &AuthRequest) -> Result<Identity, VaultError>;
}

struct RotationJob { target: RotationTarget, started_at: MonotonicTime, status: RotationStatus }

// AuditEntry — one tamper-evident audit record (§8.10).
// Zeroization: raw secret fields never populated; only HMAC digests of sensitive fields.
struct AuditEntry { seq: u64, prev_hash: [u8; 32], timestamp: WallClockTime,
    token_accessor: Option<TokenAccessor>, path: StoragePath, action: Capability,
    outcome: AuditOutcome, sensitive_fields_hmac: [u8; 32] }

struct MerkleProof { leaf_index: u64, siblings: Vec<[u8; 32]>, checkpoint_root: [u8; 32] }

// TransitKeyRing — versioned key set for one named transit key (§22).

    min_encryption_version: u32, latest_version: u32, versions: BTreeMap<u32, DataEncryptionKey> }

// VaultError — the unified error surface; every variant is audit-loggable without leaking secrets.
enum VaultError { Sealed, PermissionDenied, TamperedRecord, UnknownKeyEpoch, NoMatchingMount,
    LeaseNotFound, RevocationFailed(u32), PolicyParseError(String), StorageUnavailable }

14. Phase 2 — Shamir Unseal + Share Ceremony

14.1 Objectives

Implement real Shamir splitting/reconstruction over GF(2^8) (Shamir 1979), the operator init/operator unseal CLI flow, UnsealProgress tracking, and verification-blob checking.

14.2 Detailed Implementation Steps

  1. Implement GF(2^8) arithmetic (add = XOR, multiply via log/antilog tables, Rijndael's reduction polynomial) in vault-crypto::shamir (Shamir 1979).
  2. Implement byte-plane polynomial split: for each of 32 master-key bytes, generate a degree-(k-1) polynomial, evaluate at n distinct nonzero x-coordinates (§8.3).
  3. Implement Lagrange interpolation reconstruction at x=0 (§8.3); reject duplicate x-coordinates before interpolating (§8.12).
  4. Implement operator init: generate MK, generate initial KEK, wrap KEK under MK, Shamir-split MK, return shares + root token; the first sys/keyring write happens under the freshly derived KEK — MK itself is never persisted in any form (P1).
  5. Implement operator unseal: collect shares into UnsealProgress, reconstruct MK at k shares, unwrap KEK, decrypt a fixed verification blob, transition SealState per §8.8.
  6. Structure the seal as a pluggable trait now (ADR-07) so the deferred KMS auto-unseal path (PhaseDeferred, §37) can be added later without redesigning the state machine.
  7. Property-test: any k of n shares reconstruct MK; any k-1 shares leave every byte value equally likely (I11), over ≥10,000 trials.

14.3 Deliverable

vault operator init returns n shares (default 5) and a root token; vault operator unseal accepts shares one at a time and transitions to Unsealed at threshold k (default 3); a wrong share is rejected without corrupting progress.

14.4 Acceptance Criteria

  • 10,000-trial property test: k-of-n reconstruction succeeds 100%; k-1-of-n reveals no bias (chi-square test on the recovered byte distribution within tolerance).
  • Verification-blob decrypt succeeds for 100% of correct k-share submissions, fails for 100% of synthetically corrupted share sets.
  • UnsealProgress resets to 0 after a failed verification-blob decrypt.

14.5 Conformance Fixtures

  • conformance/vectors/shamir_5_3_known_answer.json — a fixed MK, 5 known shares, and the expected reconstructed value for all 10 distinct 3-of-5 combinations.
  • conformance/malformed/shamir_duplicate_x.json — two shares sharing an x-coordinate; expected: reconstruction refused before interpolation.
  • conformance/malformed/shamir_wrong_share_set.json — 3 valid-looking shares from two different split ceremonies; expected: verification-blob failure, SealState remains Sealed.

14.6 Pitfalls

  • Implementing Shamir over integers mod a prime instead of GF(2^8): subtle reconstruction bias near field boundaries. Debug: the N.4 chi-square test catches it. Recovery: switch to GF(2^8).
  • Reusing x-coordinates across independent split ceremonies (e.g. always operator #1 = x=1): a re-shared ceremony after rotation can let an old share combine with a new one. Fix: tag shares with a ceremony id; refuse cross-ceremony combination.
  • Off-by-one in threshold arithmetic (k vs k-1): caught only by boundary tests submitting exactly k-1 and exactly k shares.

14.7 Performance Concerns

Shamir reconstruction (32 byte-planes × k Lagrange terms) is a one-time per-unseal cost, not a hot path; the §4 ≤2s unseal-completion target is dominated by operator CLI round-trip time, not arithmetic.

14.8 Edge Cases

Threshold k=1 (degenerate — no real sharing, must still function, documented as discouraged). n approaching 255 (GF(2^8) x-coordinate exhaustion; x=0 is reserved and must never be issued as a share).

14.9 Failure Analysis

An operator submits a share for the wrong vault cluster (shares are not self-describing which cluster they belong to) — indistinguishable from a corrupted share via verification-blob failure alone. Mitigation: a non-secret cluster-id tag carried alongside (not inside) the share for operator disambiguation, without weakening I11.

14.10 Operational Notes

Author docs/runbooks/unseal-ceremony.md against this phase's exact CLI flow; operators rehearse it before go-live (§26).

15. Phase 3 — Static KV Engine + Versioning/Rollback

15.1 Objectives

Implement the KV secret engine mounted at a path, with SecretVersion/SecretMetadata (§11), version retention, and rollback.

15.2 Detailed Implementation Steps

  1. Implement MountTable and the router's longest-prefix match (§3); mount KV at secret/ by default.
  2. Implement the SecretEngine trait; KV stores at logical/<mount>/data/<path>/<version> with metadata at logical/<mount>/metadata/<path>.
  3. Every PUT creates a new SecretVersion (append-only); SecretMetadata.current_version advances; oldest_version advances only once max_versions is exceeded (retention).
  4. Implement GET with an optional version parameter, defaulting to current_version.
  5. Implement soft-delete (deletion_time set, data retained) and hard-destroy (data and the underlying BarrierRecord removed) as distinct, non-equivalent operations.
  6. Implement rollback as creating a new version whose data equals a prior version's — never mutate history in place (preserves the append-only guarantee, aids §21 audit consistency).
  7. All reads/writes flow through the Phase-1 Barrier (I2); no engine-local caching of decrypted values beyond one request's scope (P9-adjacent).

15.3 Deliverable

vault kv put secret/foo bar=baz, vault kv get secret/foo, vault kv get -version=2 secret/foo, and vault kv rollback -version=2 secret/foo all function against an unsealed vault with the root token.

15.4 Acceptance Criteria

  • The version counter never repeats or decreases across 1,000 sequential writes to one path.
  • Soft-deleted versions are unreadable via GET but recoverable via undelete; destroyed versions are unrecoverable and the underlying BarrierRecord is absent from storage on direct inspection.
  • Rollback to version N creates version N+1 with identical data; it never rewrites version N.
  • max_versions=10: an 11th write prunes exactly the single oldest retained version.

15.5 Conformance Fixtures

  • conformance/vectors/kv_version_sequence.json — 15 sequential writes with expected version numbers and retained/pruned state at max_versions=10.
  • conformance/malformed/kv_get_nonexistent_version.json — GET for a version number that never existed; expected: a not-found VaultError, not a decrypt attempt.
  • conformance/replay/kv_rollback_after_destroy.json — rollback targeting a hard-destroyed version; expected: explicit VersionDestroyed error, never a silent no-op.

15.6 Pitfalls

  • Confusing soft-delete with destroy in the API surface — document as distinct, independently policy-checkable capabilities.
  • Mutating a SecretVersion in place for "rollback" instead of creating a new version — breaks the append-only trail and desynchronizes the audit-log timeline from storage state.
  • Off-by-one in oldest_version pruning at the max_versions boundary.

15.7 Performance Concerns

SecretMetadata is read on every GET to resolve current_version; cache per-mount with write-through invalidation to stay within the §4 read p99 of 15 ms at 20,000 req/s.

15.8 Edge Cases

Writing an identical value to the same path still creates a new version (no deduplication). Reading a path never written must be distinguishable from a path whose only version is deleted.

15.9 Failure Analysis

A write succeeds at the barrier layer but the metadata update fails (crash between the two storage writes), leaving an orphaned SecretVersion unindexed by SecretMetadata. Recovery: a metadata-reconciliation sweep at startup comparing stored data versions against the metadata index and repairing gaps.

15.10 Operational Notes

Document that the versioned layout is used from the start — no later v1-to-v2 migration is needed. Cross-reference ADR-10: per-record encryption granularity makes per-version records the natural unit.

16.3 Deliverable

A client authenticates via AppRole or mTLS and receives a Token with an attached policy name. (Policy enforcement lands in §17 — Phase 4 issues tokens; it does not yet gate access beyond a root-token bypass.)

16.4 Acceptance Criteria

  • Under a controlled clock, a token is accepted at t = ttl − 1s and rejected at t = ttl + 1s on every validation call (I7).
  • An AppRole secret-id configured single-use is rejected on its second presentation.
  • mTLS auth rejects a certificate not chaining to the configured trust bundle and rejects an expired client certificate.

16.5 Conformance Fixtures

  • conformance/vectors/token_ttl_boundary.json — controlled-clock tokens crossing ttl exactly.

16.6 Pitfalls

  • Caching token validity per request-handler for performance and accidentally caching past expiry (the CVE-2021-32923 class) — always recompute (I7).
  • AppRole secret-id delivered over an unauthenticated channel defeats its own purpose — document the secure-delivery prerequisite explicitly.
  • Clock skew between the vault host and an operator's machine expiring tokens early or late — mitigate with NTP-disciplined hosts and a documented skew tolerance (P11, ADR-33).
  • Treating a root token as a normal service credential (long TTL, wide use) — make root tokens visually and operationally distinct, and easy to revoke immediately after bootstrap.

16.7 Performance Concerns

16.8 Edge Cases

A num_uses=1 token used concurrently by two racing requests — the use-counter decrement must be atomic; exactly one request succeeds. A periodic token (period set) never renewed before its current window elapses must still expire, despite nominally never expiring while renewed.

16.9 Failure Analysis

The token-store write succeeds but the accessor-index write fails (partial creation), leaving a token unusable by accessor-based revocation. Recovery: a startup reconciliation sweep across token records and the accessor index, matching the §15 metadata-reconciliation pattern.

16.10 Operational Notes

Document AppRole and mTLS as the production-recommended machine auth methods; token auth remains for root/bootstrap and CLI convenience only.

17. Phase 5 — Policy Engine + Authorization

17.1 Objectives

Implement the policy grammar/parser/evaluator (§8.4), mandatory path normalization, and wire real authorization into the request pipeline (I3, I9).

17.2 Detailed Implementation Steps

  1. Implement the §8.4 EBNF grammar parser in vault-policy; reject unknown capability tokens at parse time (§8.12).
  2. Implement path normalization (resolve ./../duplicate slashes) before any policy match, and apply the identical canonical path at storage-lookup time — this is the exact fix for the CVE-2022-40718 class bug (normalize-before-match, not after).
  3. Implement the specificity-ranked matcher (§8.4): exact > prefix-* > + > root-*, with deny overriding regardless of rank.
  4. Implement multi-policy combination: allow is OR'd across attached policies; a single deny anywhere short-circuits to denied (I9 determinism verified by property test).
  5. Wire the evaluator ahead of engine dispatch in the router (I3): no engine's handle() is reachable without a prior authorized decision.
  6. Implement policy CRUD (sys/policies/<name>) as whole-document replace only (§11 Policy atomicity note) — never a partial patch.
  7. Encode the §8.4 worked trace as an executable regression fixture.

17.3 Deliverable

A token scoped to "read on secret/myapp/*" cannot write or read outside that prefix; the §8.4 worked trace passes as an automated test.

17.4 Acceptance Criteria

  • Property test over 100,000 randomized (policies, path, capability) triples: identical inputs always yield an identical decision (I9).
  • A token with zero attached policies is denied on every path (deny-by-default).
  • secret/foo/../bar normalizes identically before both the policy check and the storage lookup; a token scoped to secret/bar/* cannot use it to reach secret/foo.
  • The §8.4 worked trace fixture reproduces the documented 403 exactly.

17.5 Conformance Fixtures

  • conformance/vectors/policy_precedence_matrix.json — every pairwise match-type-rank combination with the expected winning rule.
  • conformance/malformed/policy_unknown_capability.json — a policy with an invalid capability string; expected: parse rejected, no partial install.
  • conformance/replay/policy_path_traversal.json — requests using ./../duplicate-slash paths; expected: identical normalization pre- and post-policy-check.

17.6 Pitfalls

  • Normalizing the path after the policy check instead of before — the historical CVE-2022-40718 class bug exactly; normalize first, unconditionally, on every code path touching a request path.
  • Assuming * and + compose like a shell glob — document the precedence table explicitly and test every combination; operator intuition here is a leading source of over-grant incidents.
  • Conflating "no matching policy" with "explicit deny" in telemetry — they carry different operational meanings and must be distinguishable in audit output.

17.7 Performance Concerns

Policy evaluation runs on every request; target ≤30µs for a token with a small attached-policy set by precomputing a matcher structure per policy at load time rather than re-parsing per request.

17.8 Edge Cases

A policy pattern that is just * (matches everything, including sys/ — must still respect explicit sudo gating on privileged paths). Two policies on one token where one grants read at rank 2 and the other denies at rank 4 — deny wins regardless of rank (P4, §8.4).

17.9 Failure Analysis

A policy write partially applies due to a crash mid-write (parse succeeded, storage write interrupted) — structurally prevented by whole-document CAS replace; no partial-document state is representable in storage.

17.10 Operational Notes

18. Phase 6 — Lease Manager + Revocation

18.1 Objectives

Implement the Lease type fully (§8.6, §11), the lease lifecycle state machine (§8.9), the min-heap expiry index (ADR-16), the sweeper, renewal, and revocation (prefix and cascading).

18.2 Detailed Implementation Steps

  1. Persist Lease/LeaseId at sys/leases/<lease_id> through the barrier (I2).
  2. Implement the in-memory min-heap expiry index (ADR-16); rebuild from the persisted index at startup — a leader-only responsibility, foreshadowing §22.
  3. Implement the expiry sweeper on the §4 500ms tick, popping expiring leases and enqueuing RevocationOrders.
  4. Implement renewal: min(ttl + increment, max_ttl − elapsed) per §8.9; call the owning engine's renew hook.
  5. Implement revocation: call the owning engine's revoke hook, remove from both indexes, mark Revoked.
  6. Implement prefix revocation (revoke-prefix) and cascading token-triggered revocation via issued_to_token_accessor.
  7. Implement retry-with-backoff for revocation failure (I14): RevocationFailed → retry → ManualIntervention past a bounded budget, surfaced on an admin-visible endpoint.

18.3 Deliverable

10,000 synthetic leases with staggered short TTLs are all revoked within one sweep interval of expiry; revoke-prefix against a mount clears all its leases; a simulated upstream outage mid -revocation drives affected leases to RevocationFailed and eventually ManualIntervention without crashing the sweeper.

18.4 Acceptance Criteria

  • The sweeper drains 100% of expired leases within 2× the 500ms tick at the §4 2,000,000 tracked-lease ceiling (measured by benchmark).
  • Renewal never extends a lease past max_ttl (property test).
  • revoke-prefix against N leases confirms all N Revoked within the mass-revoke budget implied by §4.
  • A lease whose revoke hook fails 3 consecutive times enters RevocationFailed and appears on the stuck-lease admin endpoint (I14).

18.5 Conformance Fixtures

  • conformance/vectors/lease_renewal_cap.json — renewals that would exceed max_ttl; expected: capped, not rejected outright.
  • conformance/malformed/lease_revoke_unknown_id.json — revoke for a nonexistent lease_id; expected: LeaseNotFound, not a silent success.
  • conformance/replay/lease_sweep_10k_staggered.json — 10,000 staggered-expiry leases; expected sweep-completion trace.

18.6 Pitfalls

  • Lease-tracking growth outrunning the expiry sweep: manifestation is a growing gap between issued and revoked counts; root cause: sweep tick too coarse or heap operations not truly O(log n). Debug: heap-size and sweep-lag metrics (§26). Recovery: tune tick interval, verify heap implementation, rate-limit per-token lease issuance.
  • Revocation retried without backoff, hammering a downed upstream — exponential backoff with a bounded budget (I14).
  • The sweeper running on more than one node simultaneously (before §22's leader election lands) — document this as a known single-process-assumption gap until §22 closes it.
  • A renewal race: two concurrent renewals for the same lease both reading a stale ttl before either writes — must be compare-and-swap, not read-modify-write.

18.7 Performance Concerns

Heap push/pop must stay O(log n) at the 2,000,000-lease ceiling (§4); benchmark heap operations in isolation before integrating with the sweeper loop.

18.8 Edge Cases

A renewable=false lease receiving a renewal request must reject cleanly, not silently ignore. A lease whose owning mount was unmounted while still active (orphaned) must remain revocable or be explicitly flagged un-revocable with an operator-visible reason.

18.9 Failure Analysis

The upstream system for a dynamic credential is unreachable at scheduled revocation time — the TTL has passed but the revoke cannot execute. Retry-with-backoff (I14) bounds the retry storm; past the budget, escalate to ManualIntervention with full credential detail surfaced for cleanup — never silently dropped from tracking.

18.10 Operational Notes

Author docs/runbooks/mass-revocation.md against the revoke-prefix flow built here; wire a stuck-lease dashboard panel (§26) before considering this phase complete.

19. Phase 7 — Dynamic Credential Engines

19.1 Objectives

Implement the dynamic-credential engine framework with one canonical concrete engine (a database credential engine) exercising the full generation/revocation sequence (§8.7).

19.2 Detailed Implementation Steps

  1. Define the dynamic-engine plugin boundary as an in-process trait (ADR-17) extending SecretEngine with revoke/renew hooks tied to the §18 lease lifecycle.
  2. Implement the database credential engine: a configured upstream connection plus a role definition carrying creation-SQL and revocation-SQL templates.
  3. On request: render the creation template with role parameters, execute against upstream, register a Lease via the Phase-6 Lease Manager (§8.7 steps 4–9).
  4. On expiry/explicit revoke: execute the revocation template against upstream (§8.7 steps 10–14).
  5. Document the least-privilege operational constraint: the engine's own upstream connection must not itself be a superuser, bounding blast radius if the engine config is compromised.
  6. Implement retry-with-backoff for revocation failure, reusing the §18 I14 mechanism.
  7. Keep the trait boundary generic enough that another dynamic engine (e.g. cloud-IAM credentials, or the deferred PKI engine, §37) can be added later without touching the Lease Manager.

19.3 Deliverable

vault read database/creds/my-role returns a freshly created upstream credential and a lease_id; after the lease's TTL elapses, the sweeper revokes it and the credential no longer authenticates upstream.

19.4 Acceptance Criteria

  • A generated credential authenticates successfully immediately after issuance and fails to authenticate within one sweep interval after TTL elapses.
  • 100 concurrent requests against one role each receive a distinct, independently revocable credential — no collision, no shared lease.
  • Revocation-template execution failure drives the lease to RevocationFailed per I14, never a silently abandoned upstream credential.

19.5 Conformance Fixtures

  • conformance/vectors/database_engine_role_render.json — role templates with parameter substitution and expected rendered SQL.
  • conformance/malformed/database_engine_bad_template.json — a role template referencing an undefined parameter; expected: rejected at role-config time, not at issuance time.
  • conformance/replay/database_engine_revoke_after_upstream_down.json — a simulated upstream outage during scheduled revocation; expected RevocationFailed → retry → recovery trace.

19.6 Pitfalls

  • Granting the engine's upstream connection superuser privileges "to make it work" — collapses the blast-radius containment the engine boundary exists to provide.
  • Template injection via naive string concatenation for creation/revocation SQL — validate and constrain role parameters strictly at config time.
  • Treating credential generation as always synchronous-and-fast: a slow upstream (e.g. a rate-limited IAM API) can blow the §4 dynamic-secret latency budget — document a per-engine timeout and a clear error, not an indefinite hang.
  • Returning the credential to the client before lease registration is confirmed: a crash in between leaves an untracked, unrevocable credential (an I5 violation) — order registration before response, and treat an unconfirmed registration as an issuance failure requiring upstream cleanup.

19.7 Performance Concerns

Dynamic-credential issuance latency is bounded by the upstream system, not the vault; surface a per-engine timeout distinctly from vault-side latency in telemetry (§26).

19.8 Edge Cases

A role deleted while leases issued under it remain active — those leases must stay revocable using the role definition snapshotted at issuance time, not a live lookup. A revocation template that succeeds partially (e.g. drops the role but fails to revoke a grant) requires the same retry/escalation path as full failure.

19.9 Failure Analysis

The upstream creation call succeeds but the acknowledgment is lost to a network partition before the vault receives it — the vault cannot tell if the credential exists. Mitigation: creation templates should be idempotent-safe, or the engine must reconcile via a listing call before retrying issuance.

19.10 Operational Notes

Treat role-definition changes as security-sensitive as policy changes — route them through the same PR-diff review discipline established in §17.

20. Phase 8 — Key Rotation + Rewrap

20.1 Objectives

Implement KEK/DEK rotation (RotationJob) and the rewrap worker with RewrapCursor, batching, and the atomic-per-secret guarantee (I6, P14), following read-old/write-new (P8, ADR-18).

20.2 Detailed Implementation Steps

  1. Implement RotationJob triggering a new KEK or DEK epoch mint (NIST SP 800-57 rotation guidance).
  2. KEK rotation: mint a new KEK, wrap under MK, add as the new active keyring epoch; rewrap only the small DEK table under the new KEK — the cheap tier (MM2, §32).
  3. DEK rotation: mint a new DEK wrapped under the active KEK; new writes use it immediately (P8); existing records remain under old DEK epochs until rewrapped.
  4. Implement the rewrap worker: cursor-based incremental batches (ADR-19), persisting RewrapCursor{from_epoch, to_epoch, last_completed_path} after each verified batch.
  5. Per-record rewrap: decrypt under the old DEK, re-encrypt under the new DEK, verify the new ciphertext decrypts before advancing the cursor past that record (I6/P14).
  6. On crash/restart: resume from the persisted RewrapCursor; already-advanced records remain valid under the new epoch, the remainder under the retained old epoch.
  7. Implement min_decryption_epoch advancement: once a full pass completes for an old epoch, purge it from the keyring, bounding keyring growth from P8's retention requirement.

20.3 Deliverable

An operator-triggered KEK rotation followed by a full DEK rewrap over a test dataset completes with zero data loss and the old epoch purged; a fault-injected crash mid-rewrap resumes correctly.

20.4 Acceptance Criteria

  • Rewrap throughput ≥8,000 secrets/s per worker thread (§4), measured by benchmark.
  • 100% of records readable both immediately after rotation (old epoch) and after rewrap (new epoch); zero records unreadable at any point (I6).
  • A crash injected at 40% rewrap progress resumes from the persisted cursor and reaches the same end state as an uninterrupted run.
  • KEK rotation's DEK-table-only rewrap completes at least 100× faster than a full-dataset rewrap would (demonstrating MM2, §32).

20.5 Conformance Fixtures

  • conformance/vectors/rewrap_cursor_resume.json — a rewrap interrupted at a known offset and the expected resumed end state.
  • conformance/malformed/rewrap_epoch_mismatch.json — a record whose header claims an epoch absent from the keyring mid-rewrap; expected: flagged, not silently skipped.
  • conformance/replay/kek_rotation_dek_table_rewrap.json — a full KEK rotation cycle with the expected small set of rewrapped DEK records.

20.6 Pitfalls

  • A rewrap interrupted mid-batch leaving mixed epochs with no persisted cursor — the exact I6 failure mode; fixed by the checkpointed RewrapCursor, not by hoping rewraps finish in one shot.
  • Purging an old epoch before every record under it is actually rewrapped (a race between the "rewrap done" signal and the purge trigger) — verify a completion count against the known total first.
  • Nonce reuse across a key epoch during rewrap: re-encrypting under a nonce derived from the old record instead of fresh nonce material for the new epoch — violates I13.
  • Rewrap throughput assumptions ignoring lock contention with concurrent live writes — benchmark under concurrent load, not in isolation.

20.7 Performance Concerns

Rewrap is deliberately throttled (batched, cursor-checkpointed) to avoid starving live traffic of barrier throughput; tune batch size against both the §4 8,000/s-per-worker target and the live latency budgets simultaneously.

20.8 Edge Cases

A soft-deleted secret with no operator-visible current version must still have its underlying ciphertext migrated for internal consistency. A rewrap running concurrently with a live rollback (§15) on the same path must not clobber a version created after the cursor's snapshot point.

20.9 Failure Analysis

The rewrap worker crashes mid-batch-transaction against the storage backend — recovery relies on the backend's own transactional guarantees for the batch plus the RewrapCursor for resumption; this dependency is explicit (ADR-09).

20.10 Operational Notes

Author docs/runbooks/key-compromise-rotation.md against this exact rotation flow — a suspected KEK compromise triggers an emergency rotation via the same mechanism as scheduled rotation, just manually triggered and audited as an incident (§24 T1, T2).

21. Phase 9 — Tamper-Evident Audit Log + Inclusion Proofs

21.1 Objectives

Implement the audit pipeline (§8.10): HMAC-chained entries, periodic Merkle checkpoints, inclusion-proof verification, and the audit-or-refuse gate (P5).

21.2 Detailed Implementation Steps

  1. Implement AuditEntry (§11) with prev_hash chaining and HMAC over sensitive fields using a per-day key derived from the KEK via HKDF (Krawczyk 2010).
  2. Implement the audit-sink trait with file, syslog, and socket backends; every mutating request passes through at least one configured sink before the response returns (P5).
  3. Implement the bounded async audit queue (ADR-34): refuse new operations when full rather than drop entries.
  4. Implement periodic Merkle checkpointing over a window of entries (Crosby & Wallach 2009; RFC 6962-style proofs); persist the checkpoint root.
  5. Implement MerkleProof construction and inclusion-proof verification exactly per §8.10's five named steps.
  6. Implement chain-walk verification as an operator-invokable job: replay entries, recompute prev_hash links, flag the first break (I8).
  7. Refuse vault startup if no audit sink is configured or reachable (P5 applied at boot).

21.3 Deliverable

Every API call produces a visible audit entry in the configured sink(s); tampering with one entry is detected by the chain-walk job; a constructed MerkleProof for a known entry verifies against its checkpoint root.

21.4 Acceptance Criteria

  • Audit append latency p99 ≤2ms to the durable buffer (§4) under 20,000 req/s KV read load.
  • 100% of mutating operations have a corresponding audit entry; a sink outage causes 100% of new mutating operations to be refused (P5), never silently accepted.
  • The chain-walk job detects 100% of single-byte tampering injected into the fixture corpus.
  • A constructed inclusion proof verifies correctly for any entry in a checkpointed window; a proof against a tampered leaf fails.

21.5 Conformance Fixtures

  • conformance/vectors/audit_chain_known_answer.json — a fixed entry sequence with expected prev_hash values and a known checkpoint root.
  • conformance/malformed/audit_entry_tampered_byte.bin — one entry with a single altered byte; expected: chain-walk flags this entry and every subsequent one in the window.
  • conformance/replay/audit_sink_outage_refusal.json — a request sequence with the sink taken offline mid-stream; expected: refusal of new mutating operations from that point.

21.6 Pitfalls

  • Auditing synchronously on the hot path without backpressure design, tanking p99 read latency — use the bounded async queue (ADR-34) with refuse-on-full.
  • Rotating the daily HMAC key without retaining old-day keys long enough to verify historical entries — retain per-day keys across the audit-retention window.
  • Logging full secret values "temporarily for debugging" in a sink — structurally prevented by ADR-24's typed non-Debug wrappers, but must be re-verified whenever a new sink type is added.
  • Setting the Merkle checkpoint interval too large purely as a storage optimization — a larger window means a longer forensic gap before a tamper is provably bounded; tune against §26's incident-response time budget.

21.7 Performance Concerns

Batch audit-entry writes (e.g. 100 entries per file-sink syscall) to sustain the §4 append-latency target under the 100,000+ QPS transit-driven workloads of §22; parallelize across configured sinks.

21.8 Edge Cases

An audit entry for a request that itself failed authentication (no valid Identity) is still logged, with token_accessor explicitly absent rather than omitted silently. A checkpoint window boundary falling mid-lease-sweep-burst must still produce a correct inclusion proof for a window with zero or one entries.

21.9 Failure Analysis

The audit queue fills during a sink outage exactly at the bounded-refusal threshold — legitimate operations begin failing. This is the intended P5 behavior, not a bug; the operator-facing signal is audit_queue_full_total and the runbook response is to restore sink connectivity, never to disable the audit gate.

21.10 Operational Notes

Ship every audit entry off-host as close to real time as the bounded queue allows; the vault holds entries only as a buffer (P5) — the durable system of record is the external sink/SIEM.

22. Phase 10 — Transit Encryption-as-a-Service + HA/Leader Election

22.1 Objectives

Implement the transit engine (TransitKeyRing, §11) providing encrypt/decrypt/rotate/rewrap/ sign-verify as a service, and implement HA leader election (ADR-11) so the rotation/rewrap worker and lease sweeper run leader-only across a cluster.

22.2 Detailed Implementation Steps

  1. Implement transit key creation and the TransitKeyRing version table; encrypt uses latest_version (or the min_encryption_version floor); decrypt uses the ciphertext's embedded version.
  2. Implement the self-describing ciphertext envelope (vault:v<version>:<base64(nonce|| ciphertext||tag)>), reusing the barrier's AEAD primitive (P6) but keyed by the transit engine's own DEK versions — distinct from the barrier's storage DEKs (mount isolation).
  3. Implement transit rotate (mint a new key version) and rewrap (server-side decrypt-old/ encrypt-new, plaintext never exposed to the caller), reusing §20's rotation mechanics at per-key-material granularity.
  4. Implement sign/verify for asymmetric transit key types, hashing input before signing per key-type convention.
  5. Implement the storage-backend advisory lock (ADR-11) as the leader-election primitive: acquire with a bounded TTL, renew on a heartbeat shorter than the TTL, step down on renewal failure.
  6. Gate the rotation/rewrap worker (§20) and lease sweeper (§18) behind "this node is leader," closing the known single-process gaps left open in those phases.
  7. Implement standby behavior: forward writes to the leader, refuse reads by default (ADR-12) unless explicitly configured as a performance standby (deferred scaling path, §37).

22.3 Deliverable

An application encrypts data via transit/encrypt/my-key, decrypts it back, rotates the key, and confirms old ciphertext still decrypts under the retained version; killing the leader process causes a standby to acquire the lock and resume rotation/sweeping within the §4 30s RTO.

22.4 Acceptance Criteria

  • Transit encrypt/decrypt round-trips correctly across a key rotation with zero caller-side re-encryption required.
  • Transit AEAD throughput meets the §4 900 MB/s-per-core ChaCha20-Poly1305 floor under benchmark.
  • Leader failover completes within the §4 30s RTO; exactly one node holds the lock at any instant (no split-brain), verified via a chaos test killing the leader repeatedly.
  • The rotation/rewrap worker and sweeper run on exactly one node cluster-wide at any instant.

22.5 Conformance Fixtures

  • conformance/vectors/transit_encrypt_rotate_decrypt.json — plaintext encrypted, key rotated, ciphertext decrypted, expected identical plaintext.
  • conformance/malformed/transit_ciphertext_bad_version.json — ciphertext referencing a purged key version; expected: explicit "version unavailable" error, not a decrypt attempt.
  • conformance/replay/ha_leader_failover_chaos.json — a leader-kill sequence with expected failover timing and lock-holder-uniqueness assertions.

22.6 Pitfalls

  • Split-brain: two nodes both believe they hold the leader lock. Root cause: lock TTL shorter than network jitter or heartbeat renewal not accounting for scheduling pauses. Debug: continuous chaos-kill test asserting single-holder. Recovery: widen TTL-to-heartbeat ratio; add a fencing token so a demoted leader's stale writes are rejected by storage.
  • Transit per-key rate limits becoming a surprise bottleneck under a millions-of-encryptions/sec workload — document per-key throughput and design for key partitioning rather than silently degrading latency.
  • Standbys serving stale reads because "read replica" mode was enabled without understanding the ADR-12 consistency tradeoff — gate performance-standby reads behind an explicit per-mount opt-in.
  • Convergent-encryption misuse on a small-plaintext-space field enabling a dictionary attack — require explicit operator acknowledgment to enable it.

22.7 Performance Concerns

Transit is typically the highest-QPS engine in a real deployment; the audit-append cost (§21), not the AEAD operation itself, is usually the actual bottleneck at high transit QPS.

22.8 Edge Cases

A transit key marked deletion_allowed=false receiving a delete request must reject, not soft-succeed. A rewrap requested on a single-version key is a no-op but must still return success. A leader stepping down voluntarily (planned maintenance) vs. crashing must both result in exactly the same standby-promotion path.

22.9 Failure Analysis

The storage backend's lock primitive becomes unavailable during a partial outage (e.g. reachable for reads but not for the advisory-lock table) — the cluster cannot safely determine a leader. Documented behavior: all nodes step down to standby and refuse writes rather than guessing, prioritizing correctness over availability.

22.10 Operational Notes

Document the HA topology (leader + N standbys) and promotion procedure in §26's deployment topology notes; dashboard the current leader identity and lock-renewal latency as a first-class operational signal.

23. Phase 11 — Conformance Suite + Perf Hardening

23.1 Objectives

Consolidate every fixture from §12–22 into the conformance/ corpus under a single harness runner, close remaining perf gaps against §4, and run the fault-injection suite (crash mid-rewrap, storage partition, leader loss during unseal) end to end.

23.2 Detailed Implementation Steps

  1. Wire xtask conformance to run every conformance/vectors, conformance/malformed, and conformance/replay fixture from every phase against one running vault instance, asserting exact expected outputs (§28).
  2. Implement the memory-hygiene verification pass (§28): snapshot process memory pre- and post-seal, scan for master-key/DEK byte patterns, assert absence post-seal (I10).
  3. Run the fault-injection suite: crash mid-rewrap (§20), storage partition mid-write, leader loss during an in-progress unseal ceremony (§14/§22 interaction) — assert recovery per each documented failure edge.

23.3 Deliverable

23.4 Acceptance Criteria

  • 100% of fixtures across all prior phases pass under a single harness invocation.
  • Memory-hygiene scan finds zero occurrences of known master-key/DEK byte patterns in a post-seal snapshot, across 50 repeated seal/unseal cycles.
  • All three fault-injection scenarios recover to a correct, documented end state with no data loss (RPO=0 per §4).
  • No measured perf metric regresses more than 10% versus the last tagged release baseline without an explicit, reviewed waiver.

23.5 Conformance Fixtures

  • The full conformance/ corpus aggregated from §12–22 (~40+ fixture files by this phase).
  • conformance/replay/fault_injection_crash_mid_rewrap.json — the full §20 crash/resume scenario as an end-to-end harness case.
  • conformance/replay/fault_injection_storage_partition.json — a mid-write partition scenario with expected refuse-not-corrupt behavior.
  • conformance/replay/fault_injection_leader_loss_during_unseal.json — a leader crash during an in-progress unseal ceremony; expected: UnsealProgress is node-local and restarts cleanly on the new leader, never silently resuming a stale progress count.

23.6 Pitfalls

  • Treating "fixtures pass in isolation" as sufficient — the aggregated single-harness run surfaces cross-phase interaction bugs (e.g. a rewrap concurrent with a lease sweep) that per-phase testing misses.
  • Perf-regression gates too strict for legitimate benchmark noise, or too loose to catch real regressions — tune tolerance against measured variance from repeated baseline runs.
  • Fuzz corpora that never exercise the "just barely valid" boundary — seed with the §8.12 malformed-input examples rather than purely random bytes.
  • Declaring the memory-hygiene pass complete after one clean run — zeroization bugs can be timing-dependent; require the 50-cycle repeat in N.4.

23.7 Performance Concerns

This phase validates the full-stack §4 targets together, not per-component; expect the audit pipeline and lease sweeper to be the first bottlenecks to surface under combined load, per §31's ordering.

23.8 Edge Cases

Running the full fault-injection suite against both the smallest supported deployment (single node, file backend) and the full HA cluster configuration — some fault classes (leader loss) are meaningless single-node and must be explicitly skipped-with-reason there, never silently passed.

23.9 Failure Analysis

A conformance fixture that passed against an earlier phase's narrower harness now fails once integrated — a regression introduced by a later phase touching shared state (e.g. §20's rewrap touching a path §15's rollback also touches). Triage by bisecting which phase's merge introduced the behavior change, using the aggregated corpus as the regression detector going forward.

23.10 Operational Notes

This phase's harness becomes the permanent CI gate for all future changes; any new feature must add fixtures here before merging, per the testing strategy in §28.

27. Compatibility & Versioning

  • Barrier record format versioning: the version byte (§8.2) allows a future format change; readers support the current and immediately prior version during a rolling upgrade.
  • Key-epoch compatibility: read-old/write-new (P8); old epochs retain until rewrap advances min_decryption_epoch (§20).
  • Crypto-agility: the AEAD cipher is itself epoch-scoped — migrating to a different AEAD is a new KeyEpoch cipher tag, not a flag day.
  • Policy grammar evolution: new capability tokens are additive; a policy referencing a capability unknown to an older node fails closed (request rejected), never silently ignored.
  • Token format versioning: the opaque token format carries a version prefix distinguishing token-store schema generations.
  • API stability: SemVer (ADR-31); breaking changes only on a major version, documented in CHANGELOG.md.
  • Storage schema migration: mount-table and lease-index schema changes are additive-first, with an explicit migration step the leader runs before a mixed-version window closes.
  • Deprecation: a deprecated feature remains functional for at least one minor version series before removal.
  • Rolling-upgrade guarantee: standbys running version N and N+1 must both forward writes correctly to a leader running either version during the upgrade window; the leader upgrades last.

28. Testing & Verification Strategy

Unit: crypto primitives, grammar parser, byte-layout codecs. Integration: the full pipeline auth → policy → engine → barrier → audit. Property (proptest): AEAD round-trip; Shamir k-of-n reconstructs while k-1 reveals nothing (I11); policy evaluation is deterministic and deny-by-default (I9); every issued lease is eventually revoked (I5). Differential: rewrap output compared against an independent reference decrypt/encrypt implementation for the same vectors. Fuzzing (cargo-fuzz, ADR-28): barrier-record decoder, policy parser, and API request decoder as primary targets. Chaos: leader-kill, storage-partition, network-jitter injection (§22, §23). Deterministic replay: conformance/replay/ fixtures re-executed byte-identically. Soak: 72-hour sustained load at §4 targets watching for lease-tracking or audit-queue drift. Fault injection: crash mid-rewrap (I6), storage partition (FM-1), leader loss during unseal (§23). Known-answer conformance vectors: AEAD (RFC 8439 §2.8), Shamir (§14.5 fixtures), Argon2/HKDF vectors per their respective RFCs. Memory-hygiene verification: the §23 50-cycle scan (I10). Perf-regression gating: the §23.4 10%-tolerance gate tied to §4/§30 targets.

Tying back to invariants and phase fixtures: I5 → lease property test + conformance/replay/ lease_sweep_10k_staggered.json (§18.5); I6 → rewrap fault injection + rewrap_cursor_resume.json (§20.5); I9 → policy property test + policy_precedence_matrix.json (§17.5); I11 → Shamir property test + shamir_5_3_known_answer.json (§14.5); I13 → nonce-reuse fuzz target seeded from barrier_record_roundtrip.json (§13.5).

29. Build & Release Engineering

Reproducible builds (ADR-32): pinned toolchain, locked dependencies, deterministic build flags; verified by rebuilding a tagged release twice and diffing binaries byte-for-byte. Artifact signing: release artifacts carry a detached signature from an offline-held key. SBOM: generated per release and published alongside the artifact. Release channels: stable (tagged SemVer, signed) and nightly (unsigned, informational only, ADR-31). CI/CD topology: PR → build/test/clippy/audit (ci.yml) → merge → nightly channel; tag → release.yml → signed artifact + SBOM + provenance attestation. Version stamping: the build embeds the git SHA and SemVer into a /sys/version endpoint. Provenance/attestation: an in-toto-style attestation (Torres-Arias et al. 2019) links the source commit to the signed artifact through every build step. Dependency auditing: cargo audit gates CI (ADR-03); a documented audited-dependency policy restricts cryptographic crates to RustCrypto or equivalently reviewed implementations — no ad hoc crypto for AEAD/KDF/Shamir primitives.

31. Scalability Analysis

Constant: per-record barrier overhead (O(1) per operation); policy evaluation with a precomputed matcher (O(policies × rules), effectively flat for typical per-token policy counts). Grows: lease-tracking memory (O(active leases)); audit-log bytes (O(writes/s × time)); keyring size until old epochs purge (O(retained epochs)).

Bottleneck order (named, in order of onset): lease-tracking state and the audit-log append path dominate before crypto throughput does — crypto is microsecond-scale per operation, while the sweeper and audit pipeline are the first to saturate under combined load (§23.7).

Horizontal scaling: additional standbys increase failover redundancy, not write throughput (single leader, ADR-12); performance-standby read scaling is the lever for read-heavy workloads (deferred, §37). Vertical scaling: more cores directly raise AEAD and policy-eval throughput; audit-sink I/O is often the actual ceiling before CPU saturates. Sharding limits: a single barrier/keyring is the unit of consistency; sharding is possible at the mount-table level (separate clusters per business unit) but not within one barrier. Coordination overhead: leader-election lock renewal is a fixed small cost, not scale-sensitive up to the storage backend's own connection limits. Practical ceiling: bounded by the audit pipeline and lease-tracking heap before AEAD throughput; the lever beyond it is horizontal cluster sharding by mount, not vertical scaling of one cluster.

32. Mental Models & First Principles

MM1 — "A vault does not keep secrets — it keeps one secret and rents out the rest under a clock." Predicts every dynamic credential should be modeled as a lease, not a stored value. Bug class without it: credentials that live forever because nobody built a revocation path. Resolved in §18 / §19.

MM2 — "Envelope encryption converts the key-rotation problem from rewriting all data into rewriting one wrapper." Predicts KEK rotation is near-instant regardless of dataset size. Bug class without it: rotation that requires touching every record, making rotation too expensive to ever actually perform. Resolved in §20.

MM3 — "Sealed is safety; unsealed is a liability you accept on purpose." Predicts that any code path making unsealing more convenient without quorum authorization is a regression, not a feature. Bug class without it: auto-unseal creeping into places that erode P1. Resolved in §12 / §14.

MM4 — "A capability you didn't grant explicitly is a capability the attacker gets for free if you get the glob precedence wrong." Predicts glob-precedence bugs are privilege-escalation bugs, not cosmetic ones. Resolved in §17.

MM5 — "An audit log you can edit isn't an audit log — it's a suggestion." Predicts any design where one actor can both write and later silently delete an entry has failed the audit requirement, regardless of file format. Resolved in §21.

MM6 — "Time is a security parameter, not a formatting choice." Predicts TTL/lease math on the wrong clock source silently changes security guarantees. Resolved in §16 (I7) and §18 (P11).

MM7 — "A rewrap interrupted is a fact about your keyring, not a fact about your data." Predicts a correctly designed rewrap can be crashed at any point without ever losing readability of a single record. Resolved in §20 (I6).

MM8 — "The storage backend is a place to put ciphertext, not a place to put trust." Predicts any design requiring the storage backend to enforce a security property (rather than durability/ availability alone) has misplaced the trust boundary. Resolved in §13 (P10) and §24 (T2, T11).

34. Back-of-Envelope Capacity Model

1. Full-rewrap wall clock. secrets × (decrypt_µs + encrypt_µs) ÷ parallelism: 10,000,000 × (60µs + 60µs) = 1,200,000,000 µs = 1,200 s single-threaded; ÷ 8 workers ≈ 150 s, consistent with the §4 ≈156s figure within measurement overhead.

2. Barrier storage overhead per record. header_bytes ÷ average_plaintext_bytes: (1 + 4 + 12 + 16) = 33 B header ÷ 256 B average plaintext ≈ 12.9% amplification ratio.

3. Lease-tracking memory. active_leases × lease_record_bytes: 2,000,000 × ~500 B ≈ 1,000,000,000 B ≈ 954 MiB resident. Expiry-sweep cost per interval is O(log 2,000,000) ≈ 21 comparisons per heap operation — negligible; the real bound is the count of leases expiring in one 500ms tick, not heap depth.

4. Audit-log bytes/day. writes/s × entry_bytes × 86,400: at ≈22,000 audited ops/s (the §4 20,000 req/s KV load plus writes) × 512 B/entry × 86,400 s ≈ 973,220,000,000 B/day ≈ 906 GiB/day at sustained peak — the worst-case ceiling that feeds retention-storage planning; real average load is typically far below this.

5. Merkle-proof size. log2(entries_per_window) × digest_bytes: for a 1,000-entry checkpoint window, log2(1000) ≈ 10 → 10 × 32 B (SHA-256) = 320 B per inclusion proof.

6. AEAD throughput ceiling vs. read target. 900 MB/s/core ÷ 256 B average KV value ≈ 3,515,625 decrypt ops/s/core — vastly exceeds the 20,000 req/s §4 read target, confirming AEAD is never the read-path bottleneck (§31).

7. Shamir share-loss tolerance. For k=3, n=5, the scheme tolerates losing up to n−k=2 shares while remaining reconstructible; the operational risk is losing more than 2 of 5 (e.g. through simultaneous operator turnover) — an availability question the org's own operator-continuity planning must estimate, distinct from I11's confidentiality guarantee below threshold.

36. Alternative Architectures (Roads Not Taken)

36.1 Cloud-KMS Auto-Unseal, No Shamir Ceremony

   Client → API → Barrier ⇄ Cloud KMS.Decrypt(wrapped_KEK)
                       │
                 Storage Backend

Winning regime: cloud-only fleets prioritizing zero-touch restarts over operator-held trust. Embodying system: AWS-KMS auto-unseal, already an optional mode in HashiCorp Vault itself. Rejected here as the default because it moves the root of trust entirely to the cloud provider (ADR-07), contradicting P1's operator-sovereignty stance; retained as an opt-in path (§37).

36.2 HSM-Rooted, Master Key Never Leaves Hardware

   Client → API → Barrier ⇄ PKCS#11 HSM (MK resident, unwrap-only interface)
                       │
                 Storage Backend

Winning regime: FIPS 140-3 Level 3 compliance mandates where software-resident key material is disallowed regardless of Shamir's mathematical guarantees. Embodying system: HSM-backed enterprise Vault/CloudHSM-fronted KMS deployments. Rejected as the default because it adds a hardware dependency and cost this blueprint's phases don't require to demonstrate the key -hierarchy and unseal concepts (deferred, §37).

36.3 Stateless, Git-Committed Encrypted-File Model

   developer → age/PGP-encrypt → ciphertext file committed to git
   CI/deploy → age/PGP-decrypt (recipient key) → plaintext at deploy time
   (no running service; no lease; no revocation)

Winning regime: small teams, GitOps pipelines, low secret-change velocity. Embodying system: Mozilla SOPS, age. Rejected here because it provides no lease/revocation model, no dynamic secrets, and no runtime authorization — this blueprint's domain (§1) requires all three.

36.4 Short-Lived-Identity-Only, No Stored Secrets

   Workload → SPIRE Agent → SVID (short-lived X.509/JWT)
   Peer verifies the SVID via a SPIFFE trust bundle
   (identity replaces "secret" entirely for service-to-service auth)

Winning regime: pure service-to-service authentication where mutual identity proof suffices and no application-level secret is actually needed. Embodying system: SPIFFE/SPIRE. Rejected as a replacement (noted as complementary in §33) because it does not address static application secrets, third-party API keys, or dynamic database credentials — the core domain targeted here.

38. Glossary

  • Seal: the vault's locked-at-rest state with no key material in process memory.
  • Unseal: the deliberate, quorum-authorized reconstruction of the master key in memory.
  • Barrier: the encryption layer between vault logic and the storage backend; the sole encrypt/decrypt path.
  • Master key (MK): the root of the key hierarchy; never persisted in usable form.
  • Key-encryption key (KEK): wraps data-encryption keys; itself wrapped by the master key.
  • Data-encryption key (DEK): encrypts storage records/secret payloads directly.
  • Envelope encryption: encrypting data under a key that is itself encrypted by another key.
  • Key epoch: a generation identifier for a KEK or DEK, enabling read-old/write-new rotation.
  • Rewrap: re-encrypting a record under a newer key epoch without changing its plaintext.
  • Shamir share: one fragment of a secret split via Shamir's threshold scheme.
  • Threshold (k-of-n): the minimum number of shares required to reconstruct a secret.
  • AEAD: authenticated encryption with associated data.
  • AAD: associated data authenticated alongside a ciphertext but not encrypted.
  • Nonce: a value used once per encryption under a given key, never reused.
  • Zeroization: overwriting secret memory so it cannot be recovered after use.
  • mlock: an OS call preventing a memory page from being swapped to disk.
  • Token accessor: a safe-to-log identifier for a token, distinct from the bearer token itself.
  • Orphan token: a token not revoked when its parent token is revoked.
  • TTL: time-to-live; the remaining validity window of a token or lease.
  • Renewal: extending a token's or lease's TTL without issuing a new one.
  • Lease: a record tracking an issued secret's lifecycle and revocation path.
  • Revocation: the act of invalidating a token, lease, or dynamic credential.
  • Dynamic secret: a credential generated on demand and tied to a lease.
  • Policy path glob: a wildcard pattern (* or +) used in a policy's path match.
  • Capability: one of create/read/update/delete/list/sudo/deny attached to a policy rule.
  • Deny-by-default: the rule that absence of an explicit allow is treated as a deny.
  • Sudo capability: a capability permitting operator-only privileged operations on a path.
  • Transit engine: the mount providing encryption-as-a-service without exposing key material.
  • Tamper-evident log: a log structured so any alteration is cryptographically detectable.
  • Inclusion proof: a proof that a specific entry is included in a Merkle-tree checkpoint.
  • Performance standby: a standby node serving reads locally under relaxed consistency.
  • Mount: an instance of an engine or auth method bound to a specific path prefix.
  • Storage backend: the durable, ciphertext-only persistence layer behind the barrier.
  • Keyring: the ordered set of retained KEK/DEK epochs supporting old-ciphertext reads.
  • RewrapCursor: a persisted progress marker for an in-flight rewrap.
  • Merkle tree: a binary hash tree enabling compact inclusion proofs.
  • Hash chain: a sequence of entries each referencing the hash of its predecessor.
  • HMAC: a keyed hash used to authenticate audit entries and derive per-day audit keys.
  • HKDF: an HMAC-based key-derivation function (RFC 5869).
  • Argon2id: a memory-hard password-hashing/KDF algorithm (RFC 9106).
  • ChaCha20-Poly1305: the AEAD cipher locked in as this system's default (RFC 8439).
  • GF(2^8): the finite field used for byte-wise Shamir polynomial arithmetic.
  • Lagrange interpolation: the polynomial-reconstruction technique used to recover a secret from shares.
  • Leader election: the process by which one HA node becomes the sole active node.
  • Advisory lock: a storage-backend primitive used to implement leader election.
  • Split-brain: a failure state where more than one node believes it is the leader.
  • Standby: a non-leader HA node forwarding writes and, by default, refusing reads.
  • AppRole: an auth method pairing a stable role-id with a short-lived secret-id.
  • mTLS: mutual TLS, used here as a certificate-based auth method (RFC 8705).
  • Identity: the verified principal produced by a successful auth-method call.
  • Periodic token: a token that renews indefinitely while used, within its period.
  • Soft-delete: marking a secret version deleted while retaining its underlying data.
  • Hard-destroy: irreversibly removing a secret version's underlying ciphertext.
  • Rollback: creating a new secret version whose data matches a prior version's.
  • Secret version: one immutable, append-only revision of a KV secret.
  • Conformance fixture: a named input/expected-output pair used to validate behavior exactly.
  • Fault injection: deliberately introducing a failure (crash, partition) to test recovery.
  • RPO: recovery point objective — the maximum acceptable data loss window.
  • RTO: recovery time objective — the maximum acceptable time to restore service.
