Project Number: 102

Project Name: Replication Protocol

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade replication protocol library covering both physical replication (byte-for-byte WAL/log shipping — the Postgres streaming-replication / MySQL physical-clone / RDS block-replication model) and logical replication (row-level/statement-level change events decoded from that same WAL — the Postgres logical-decoding / MySQL row-binlog / Debezium CDC model), in safe Rust, with async, synchronous, and quorum acknowledgement modes; replication slots; cascading replicas; controlled and uncontrolled failover; timeline-fork divergence detection; four-point lag monitoring; and schema-aware DDL replay. The system does not invent a WAL format (consumes Blueprint #69's), a storage engine (Blueprint #43's MVCC visibility), a consensus/leader-election layer (Blueprints #93 Paxos / #37 Raft), or multi-primary conflict resolution (Blueprint #99) — it is the replication transport, slot, and failover-primitive layer that those systems compose with.

Phase-0 deliverable (numbered modules):

  1. repl-core — on-wire types: Lsn, TimelineId, ReplicationSlot, ReplicationMode, WireMessage, framing codec.
  2. repl-physical — walsender / walreceiver / apply / restart-from-LSN / sync-quorum ack.
  3. repl-logical — decoder, reorder buffer, schema tracker, output-plugin trait.
  4. repl-slot — slot persistence, advance, timeout policy.
  5. repl-failover — controlled handover, uncontrolled promotion, fencing hooks.
  6. repl-divergence — timeline-fork detector, history file, operator-acknowledged rebase.
  7. repl-net — Tokio transport, rustls TLS, zstd compression.
  8. repl-cli (replctl) — operator surface: slot/failover/divergence/status commands.

System boundaries. Provides: WAL streaming (physical), row/statement change-event streaming (logical), slot durability, sync/async/quorum ack, controlled/uncontrolled failover primitives, divergence detection, lag telemetry. Delegates: WAL record format and durability discipline (Blueprint #69, ARIES), MVCC visibility (Blueprint #43), automatic leader election (Blueprints #93/#37), conflict resolution for multi-primary writes (Blueprint #99). Does NOT provide: a query planner, a storage engine, automatic failover policy (the library exposes handover()/promote(); the orchestrator decides when to call them — ADR-14).

Non-goals (see Deferred Features Register, §36, for the anchor/trigger of each): Aurora-style shared-log-is-the-database replication PhaseDeferred("§32"); Raft/Paxos consensus replication PhaseDeferred("§35.2"); multi-primary conflict-resolved replication PhaseDeferred("§35.1"); statement-based logical replication as the default PhaseDeferred("§35.3"); per-key parallel logical apply PhaseDeferred("§22.7"); online (non-blocking) DDL with dual-schema routing PhaseDeferred("§17.6"); geo-distributed quorum across regions PhaseDeferred("§30"); paused-slot time-travel replica queries PhaseDeferred("§15.1"); PITR bootstrap via archived-WAL replay PhaseDeferred("§13.3"); at-rest encryption of archived WAL segments PhaseDeferred("§23").

Deployment model. A library (not a managed service): linked into a primary process and into standby/consumer processes; operators run replctl for slot/failover/divergence operations; topology (which hosts are standbys, which are sync candidates) is config, not auto-discovered.

Target users/operators. Database-engine implementers who need a replication layer; platform/SRE teams operating a home-grown or embedded datastore; CDC-pipeline builders who need a logical-decoding source without a full RDBMS.

What later phases unlock. Phase 1 (physical streaming) unlocks HA read replicas and warm standbys. Phase 2 (sync/quorum) unlocks zero-RPO configurations. Phase 4–5 (logical + schema) unlock CDC pipelines into Kafka/search/warehouses. Phase 6–7 (failover + divergence) unlock safe operator-driven DR. Phase 8–9 (cascading + lag) unlock read scaling with observable staleness. Phase 10 unlocks multi-core throughput.

Recommended language: Rust 1.78+ (edition 2021). Rationale: the borrow checker statically eliminates the buffer-aliasing/use-after-free class of bugs that has produced real CVEs in C replication code (e.g., historical libpq/walreceiver buffer-handling fixes); async/await with Tokio gives cooperative concurrency without a GC pause budget under WAL-streaming load; no_std-tolerant core types keep the LSN/framing arithmetic portable. Rejected: C — memory safety is the dominant risk in a network-facing byte-shuffling protocol, rejected outright. C++ — same class of risk, mitigated but not eliminated by modern idioms; the ecosystem's async story is fragmented. Go — GC pauses interact badly with p99 sync-ack latency budgets (§4); acceptable for the CLI/CDC consumer side, rejected for the core protocol. Java/JVM — GC and JIT warm-up hurt tail latency and startup-time constraints (§4); acceptable for a Debezium-style consumer, rejected for the transport core. Zig — promising memory-safety-adjacent story but the async ecosystem and library maturity (TLS, zstd bindings) are not production-ready as of this writing.

Prerequisites. Write-ahead logging and ARIES recovery (Mohan et al. 1992); Postgres streaming replication and logical decoding; MySQL binlog (row/statement/mixed); Debezium's snapshot-then-stream connector model; leader epochs (Kafka KIP-101); quorum systems (read-quorum/write-quorum trade-offs); Helland & Campbell's divergence-after-partition model; the general failure taxonomy (split-brain, asymmetric partition, slow replica).

Estimated timeline. Phase 0: 1 week. Full system (Phases 0–10): 11–12 weeks of focused implementation, or 6–9 months at a sustainable part-time pace including the Jepsen/soak gates.

2. Why Build This

Replication is the load-bearing pillar of every production database deployment. A read replica scaling a service to 10K QPS is a physical-replication consumer. A cross-region DR topology is a replication topology. A CDC pipeline feeding a warehouse, search index, or cache is a logical-replication consumer. Aurora, Spanner, CockroachDB, MongoDB replica sets, Cassandra, Kafka, Debezium — each is fundamentally a replication system with a different point chosen on the same trade-off axis: what unit replicates (bytes vs rows), when the primary acks (before vs after replica confirmation), and who decides the new primary (operator vs consensus).

The physical/logical distinction is the field's central lesson learned over four decades. Physical replication ships bytes: fast (no re-parsing, no re-planning), exact (byte-for-byte identical modulo in-flight buffers), and brittle across major-version and cross-engine boundaries. Logical replication ships row/statement events: flexible (heterogeneous sinks, filtering, transformation) at roughly 10x lower throughput and with a long tail of correctness pitfalls (DDL, sequences, large objects, cross-table ordering). Every major database ships both because every deployment eventually needs both properties in different places of the same topology.

This project is the smallest stack that still teaches the full surface: the WAL on-wire framing, the walsender/walreceiver streaming protocol, the replication-slot lifecycle, the logical-decoder reorder-buffer pipeline, the failover state machine (controlled and uncontrolled), the timeline-fork machinery, cascading replicas, and the four-number lag surface every on-call engineer reads at 3 a.m. It cross-links to sibling systems by name: Blueprint #69 (WAL/storage engine, the log this protocol ships), #43 (MVCC, the visibility this protocol must not corrupt on apply), #93/#37 (Paxos/Raft, the consensus layer that can sit above this protocol's promote/fence primitives), #99 (multi-primary conflict resolution, the layer that needs a bidirectional variant of this transport), and #71 (PITR, which shares the WAL and the slot's restart_lsn as its bootstrap point).

The calibration value is concrete: after this blueprint, a production incident — a standby 40 minutes behind, a logical consumer silently skipping rows, a promoted replica whose old primary's clients are still writing, an unnoticed timeline fork — is diagnosable by name, not by guesswork.

Six properties, referenced throughout: (1) the primary's WAL is the single source of truth for all three consumer kinds (physical, logical, PITR) — they share the flush-LSN watermark and the segment format (I1, I2). (2) walsender/walreceiver are protocol- symmetric; a cascading replica cannot tell it is not talking to the primary. (3) replication slots (§15) are the durability contract preventing WAL truncation ahead of a slow consumer (I5, I6). (4) TimelineId is monotonic 4-byte state; every uncontrolled promotion bumps it (I4); a replica applying from a stale timeline is the divergence bug (§19). (5) the failover plane is operator-driven by default (ADR-14); the building blocks are automated, the policy (when to call promote()) is not. (6) trust boundaries: primary↔network (mTLS, ADR-12), network↔wire (CRC32C, I7), operator↔failover plane (explicit acknowledgement, I15) — detailed in the Threat Model (§23).

6. Design Principles

  1. P1 — Physical and logical are different protocols; pick by use case. Physical serves HA/PITR; logical serves CDC/cross-version/heterogeneous sinks. Tradeoff: maintaining two pipelines costs code, but pretending one subsumes the other (Gray et al. 1996) costs correctness. Violate it and you get a "universal" replicator that is slow at HA and unsafe at CDC.
  2. P2 — Sync trades latency for durability; async trades durability for latency; quorum trades both for availability. Default is async (ADR-04); sync/quorum are explicit opt-ins. Operational implication: a slot's mode is visible in replctl status; violating the default silently (advertising sync, acting async) is the #1 pitfall (§14.6).
  3. P3 — The primary's local durability is unconditional (I2). WAL fsync precedes the primary's own commit ack; replication ack layers on top, never replaces it. Violating this reorders cause-before-effect and breaks every invariant downstream.
  4. P4 — LSN is monotonic and never decreases anywhere (I1). A standby's flushed_lsn cannot exceed the primary's flush_lsn; a cascading replica's received_lsn cannot exceed its upstream's flush_lsn. Violation ⇒ divergence event (§19).
  5. P5 — Timelines are 4-byte monotonic IDs; every uncontrolled promotion bumps one (I4). Generalizes Kafka KIP-101's leader-epoch fix for the high-watermark-truncation bug. Skip the bump and forked timelines are indistinguishable from normal catch-up.
  6. P6 — Logical replication must treat DDL as a first-class event or it is wrong. A schema change the consumer never learns about is silent corruption (misread column types, phantom drops). Default policy is deny-by-default (ADR-09).
  7. P7 — The output plugin is the sole contract for logical serialization. One WAL, many output formats (Avro default, JSON optional, protobuf stretch) behind one trait (§11.8). Violating this couples the decoder to a wire format and blocks future sinks.
  8. P8 — Replication slots are the only thing preventing WAL truncation ahead of a slow consumer (I5, I6). Trade-off: an abandoned slot wedges disk; the mitigation is an explicit, alerted slot-timeout (ADR-18), never silent auto-drop.
  9. P9 — Cascading replicas offload the primary but inherit lag additively. A third-level standby's lag is the sum of every hop's lag (§20.3); the monitoring surface must expose the whole chain, not just the immediate hop.
  10. P10 — Failover is operator-driven by default; the library ships the primitives, not the policy (ADR-14). handover() (controlled) and promote() (uncontrolled) are library calls; when to call them is left to the orchestrator. Automating this without a consensus layer is split-brain bait (Gray et al. 1996; §23 T1).
  11. P11 — Divergence after uncontrolled failover is detected, never silently prevented. Writes accepted by the old primary after the fault that triggered promotion are gone or must be manually merged; the detector (§19) refuses rejoin without explicit operator acknowledgement of the loss.
  12. P12 — Lag is reported at all four points — send, receive, flush, replay — never fewer. A dashboard graphing only one lies about the system; the classic "40-minute unnoticed lag" bug is a monitoring bug, not a replication bug (§21.5).
  13. P13 — Quorum-ack threshold defaults to floor(n/2)+1; sync-ack defaults to 1. Both survive exactly one host failure without data loss (DeCandia et al. 2007); both are explicit config, never silently widened or narrowed.
  14. P14 — On-wire framing is explicit length-prefixed binary with a CRC32C trailer. Relying on the transport for framing fails in production (partial reads, TCP coalescing); the codec is the contract, not the socket.
  15. P15 — TLS is non-optional for any cross-DC link. Same-host/rack replication may run plaintext for latency; anything crossing a public or shared network segment uses rustls with mTLS (ADR-12) — violating this is an unauthenticated-primary attack surface (§23 T3).

8. Domain Model / Protocol / Data Model

8.1 WAL record layout (physical)

XLogRecord (variable length):
  ┌─────────┬─────────┬──────┬──────┬──────────┬──────────┬───────────┬─────────┐
  │ lsn:u64 │ xid:u64 │rmid:u8│info:u8│ tl:u32  │prev_lsn:u64│ data:var │crc32c:u32│
  └─────────┴─────────┴──────┴──────┴──────────┴──────────┴───────────┴─────────┘
    8 bytes   8 bytes   1B     1B      4 bytes    8 bytes     N bytes    4 bytes

rmid (resource manager ID) selects the decoder: RMID_HEAP/RMID_HEAP2 (row-level data), RMID_XACT (begin/commit/abort), RMID_RELATION (DDL/relation metadata), RMID_LOGICAL_MSG (application-level pg_logical_emit_message-style payload). prev_lsn chains records within one timeline for crash-consistency verification (I1, I3).

8.2 On-wire frame layout (transport)

Frame:  [ kind:u8 ][ length:u32 BE ][ payload: length bytes ][ crc32c:u32 BE ]
        MAX_PAYLOAD = 16 MiB (fragmented above at the application layer, §11.10)

kind discriminates the WireMessage variant (§11.5): XLogData, KeepAlive, StandbyStatusUpdate, HotStandbyFeedback, LogicalEvent. CRC is computed over kind || length || payload (I7); a mismatch disconnects the stream (§13.7).

8.3 Streaming-replication command grammar (EBNF)

command       = create_slot | drop_slot | start_replication | advance_slot ;
create_slot   = "CREATE_REPLICATION_SLOT" , slot_name , kind ;
kind          = "PHYSICAL" | "LOGICAL" , plugin_name ;
drop_slot     = "DROP_REPLICATION_SLOT" , slot_name ;
start_replication
              = "START_REPLICATION" , "SLOT" , slot_name , kind , start_lsn ;
advance_slot  = "ADVANCE_REPLICATION_SLOT" , slot_name , target_lsn ;
slot_name     = identifier ;
plugin_name   = identifier ;
start_lsn     = lsn_literal ;
target_lsn    = lsn_literal ;
lsn_literal   = hex_u32 , "/" , hex_u32 ;      (* e.g. "0/1A2B3C4D" *)

Mirrors the PostgreSQL Streaming Replication Protocol grammar (§5 RFCs). replctl (§11 repo layout) is the CLI front-end that emits these commands over repl-net.

8.6 Malformed-input example

A frame with length = 0xFFFFFFFF (exceeds MAX_PAYLOAD, §11.10) is rejected by the codec before allocation — the decoder validates length ≤ MAX_PAYLOAD prior to buffering, never allocates on unchecked attacker/corruption-controlled length (mitigates §23 T3/T7). A frame whose trailing CRC32C does not match its kind||length||payload is rejected per I7 and the connection is torn down; received_lsn is not advanced.

8.7 Failure-path example

Walreceiver crashes mid-apply, after received_lsn advanced but before flushed_lsn reached the same record (violating the ordering P3/I2 would demand on the primary side, but is expected transient state on a standby). On restart, WalApplier (§13.4) resumes from the standby's own last-fsynced flushed_lsn, re-reads and re-applies any records between flushed_lsn and the local WAL's tail (idempotent apply, §13.4 pitfalls), recomputes replay_lsn, and reconnects with START_REPLICATION SLOT <name> PHYSICAL <flushed_lsn> — no double-counted bytes are requested from the primary (§13.5).

8.9 Consistency semantics

  • Physical: byte-identical replay ⇒ read-after-write on the standby is exact once replay_lsn ≥ the commit's LSN ("lag-bound consistency", ADR-16). Strict linearizable reads require routing to the primary.
  • Logical: row-level equivalence, not byte-identical; ordering guarantee is per-table commit order (I3), cross-table ordering is by commit LSN, not by table-scan order.
  • Replication modes (§11.4): Async (no wait), SyncReceive (wait for received_lsn ≥ commit_lsn), SyncReplay (wait for replay_lsn ≥ commit_lsn, strictly stronger), Quorum(n) (wait for n acks, threshold floor(n/2)+1 default, P13).

11.1 Lsn (crates/repl-core/src/lsn.rs)

pub struct Lsn(pub u64);                       // repr(transparent), Copy, Eq, Hash
impl Lsn {
    const ZERO: Lsn; const INVALID: Lsn;       // u64::MAX sentinel
    fn to_be_bytes(self) -> [u8; 8];           // Postgres-compatible wire order
    fn from_be_bytes(b: [u8; 8]) -> Self;
    fn distance_from(self, other: Lsn) -> u64; // saturating; 0 if other > self
}
// impl Ord, PartialOrd (total order, I1); impl Debug ("TL/OFFSET" hex, e.g. "0/1A2B3C4D")
// impl Add<u64>, AddAssign<u64>, Sub<Lsn> -> u64

Ownership: Copy type, no allocation. Mutation: immutable value type; "advance" means replacing, not mutating, a stored Lsn. Concurrency: Send + Sync by construction. Persistence: serialized as 8 bytes big-endian everywhere (slot files, wire frames). Compatibility: stable representation across all protocol versions (ADR-10 sibling).

pub struct ReplicationSlot {

pub enum ReplicationMode {
    Async,

Ownership: per-slot config, set at slot creation. Mutation: runtime-changeable via operator command (does not require restart). Compatibility: new variants are additive; an old consumer that does not understand a new variant rejects the handshake explicitly (never silently downgrades).

  • A WAL record spanning a segment boundary must never be split across segment files — follow the Postgres convention (never split) or the reader loses bytes at every boundary (§5 Ref-impl #1).

13.7 Performance Concerns

Batching (deferred fully to Phase 10, §22, but present from Phase 1 as a design constraint): one record per frame is correctness-simple but syscall-expensive at 500 MB/s sustained; the codec must be designed from Phase 1 to accept multi-record frames even if the walsender does not yet batch aggressively. Segment-boundary reads amplify I/O if the reader re-opens the segment file per record instead of holding an open handle.

13.8 Edge Cases

Clock skew between primary and standby: KeepAlive. server_time_us is informational only — no correctness path depends on wall-clock agreement (only on LSN ordering, I1).

13.9 Failure Analysis

Symptom: standby WAL diverges byte-for-byte from primary. Detection: physical.bitparity conformance bucket (§13.5) fails; page-checksum reconciliation (replctl reconcile pages --sample 1%) catches drift in production. Root causes ranked: (1) fsync-before-advance order violated (§13.6), (2) segment-boundary split bug, (3) non-idempotent apply on restart. Containment: standby is marked Suspect and removed from the sync-candidate set (P13) until reseeded from a fresh pg_basebackup-style snapshot. Blast radius: reads against that one standby only; the primary and other standbys are unaffected.

Deployment: standby process requires network egress to the primary's replication port only; no inbound port required from the primary's perspective beyond the listener. Rollback: a standby can always be demoted to a plain read-only snapshot by stopping the walreceiver — no data migration required.

14. Phase 2 — Synchronous Replication and Quorum Acknowledgement

14.1 Objectives

Implement SyncReceive, SyncReplay, and Quorum(n) modes (§11.4) on top of Phase 1's streaming path — the primary's commit path blocks per P2/ADR-04/ADR-05/ADR-06.

  • Implement SyncCoordinator (repo layout sync.rs): tracks per-standby received_lsn/flushed_lsn/replay_lsn from StandbyStatusUpdate frames (§8.5 worked example); wakes commit-waiters in commit_lsn order (not arrival order) via a BTreeMap-keyed waiter set — I2 requires the primary's own fsync to have already happened before this wait even begins.

  • Conformance bucket quorum.tolerate_minority: 3-standby quorum, one down, primary continues acking commits.

14.6 Pitfalls

  • Waking commit-waiters in arrival order instead of commit_lsn order is harmless functionally but produces a confusing out-of-order ack log — use a BTreeMap keyed by commit_lsn.
  • The single worst foot-gun in this stack: a coordinator that returns success from wait_for_commit based on the primary's own flushed_lsn rather than any standby's — test the full wire path with a real, pausable standby, never a mock coordinator.
  • An eligible-sync-candidate set that is not persisted loses "who was a sync candidate" information across a primary crash — a slot that was sync-eligible before the crash must remain so after, or the durability guarantee silently narrows.

14.7 Performance Concerns

Sync-ack latency budget (derived in §33 #6) is local_fsync + RTT + standby_fsync; any extra hop (a proxy, a load balancer) between primary and standby adds directly to p99. Waiter-wake fan-out on a busy primary with hundreds of concurrent commits must not become an O(waiters) scan per ack — the BTreeMap range-query approach keeps it O(log n + k) for k newly-satisfied waiters.

14.8 Edge Cases

A standby that acks received_lsn but crashes before flushed_lsn catches up: under SyncReceive the primary already acked (correct per that mode's contract); under SyncReplay the primary is still waiting (correct — stronger guarantee). Quorum recomputation when a sync candidate is added/removed at runtime: the coordinator must recompute floor(n/2)+1 against the new n before evaluating any in-flight commit's satisfaction.

14.9 Failure Analysis

Symptom: commit latency spikes without an obvious cause. Detection: per-standby ack latency histogram (repl_sync_ack_latency_seconds) isolates the slow standby. Root causes: network RTT regression, standby fsync contention, GC-equivalent pause on a non-Rust consumer in the chain. Recovery: remove the slow standby from the sync-candidate set (an operator action, not automatic — automating this is itself a failover-policy decision per ADR-14) while investigation proceeds.

14.10 Operational Notes

Metrics: repl_sync_ack_latency_seconds{standby}, repl_sync_degraded_total, repl_quorum_eligible_count. replctl status surfaces current mode, eligible set, and per-standby ack state. Runbook: docs/runbooks/slow-replica.md covers the quorum-degradation triage path.

16. Phase 4 — Logical Decoding: Reorder Buffer, Output Plugins

16.1 Objectives

Implement the logical-decode pipeline (§8.8): WAL → decoder → reorder buffer → output plugin → consumer, emitting Begin/Insert/Update/Delete/Commit per transaction in commit order (I3).

16.2 Detailed Implementation Steps

  • Implement LogicalDecoderImpl::feed (§11.8): dispatch on XLogRecord.rmid (RMID_HEAP/RMID_HEAP2 → row ops buffered by xid; RMID_XACT → commit/abort drains the buffer in commit order, I3; RMID_RELATION → schema tracker input, Phase 5's §17).
  • Implement ReorderBuffer (repo layout reorder_buffer.rs): groups LogicalChangeEvents by xid; on abort, drops the buffered set entirely (I8 — emitting aborted-transaction data to a consumer is a correctness violation, not a perf concern); spills to disk past a configurable memory cap (default 256 MiB/slot, §4) — a long-running uncommitted transaction is an OOM vector without this.
  • Implement the OutputPlugin trait (§11.8) with AvroPlugin (default, ADR-08), JsonPlugin, and a stretch ProtobufPlugin; Avro is chosen because it carries schema and survives additive schema evolution gracefully (compatible-add-field).
  • Implement snapshot_table(): a new logical slot's initial consistent snapshot at the slot's confirmed_flush_lsn, so the consumer applies snapshot-then-stream (Debezium pattern, §5 Ref-impl #5) without a gap or an overlap.

16.3 Deliverable

16.4 Acceptance Criteria

  • Conformance bucket logical.rowequiv: after a 1-billion-row replay, every row and column on the consumer matches the primary exactly (fixture below).
  • Conformance bucket logical.throughput: ≥ 50K rows/sec single-core decoder + Avro output (M2, §29).
  • Aborted-transaction events never reach the output plugin — asserted by a negative-case fixture, zero tolerance (I8).

Fixture Purpose Expected Output
conformance/corpora/logical_rowequiv/1b_row_replay.workload 1B-row primary workload consumer row state byte-for-byte column-equal to primary
conformance/corpora/logical_rowequiv/aborted_txn_leak.scenario transaction with 10K ops then abort zero events emitted for that xid (I8)

16.6 Pitfalls

  • A reorder buffer that leaks aborted-transaction events is the single worst correctness bug in the logical pipeline — it looks like a performance optimization ("why buffer at all") but is silently shipping pre-commit data downstream (I8).
  • The relation/type-change (RMID_RELATION) records must be consumed strictly before any RMID_HEAP/RMID_HEAP2 record that references the new tuple shape, or the schema tracker (Phase 5, §17) is stale by exactly one record.
  • Skipping the disk-spill path "because deployments are small" is how a single forgotten BEGIN without COMMIT OOMs a primary — the spill is not an optional feature, it is the OOM mitigation (§4 reorder-buffer memory cap).

16.7 Performance Concerns

Decode throughput (M2) is dominated by per-record allocation in the row-op parse path; the reference implementation reuses buffers across records within one transaction rather than allocating per-event. The spill-to-disk path trades throughput for memory safety — spilling should be rare in steady state and its rate is itself a signal (repl_reorder_spill_total) worth alerting on.

16.8 Edge Cases

A transaction that spans a primary restart mid-decode: the reorder buffer's spilled state must be recoverable, or the decoder must restart the transaction's decode from its first WAL record after crash recovery. A commit record with zero buffered ops (an empty transaction, e.g., BEGIN; COMMIT;): emits Begin/Commit with no row events between — valid, not an error.

16.9 Failure Analysis

Symptom: consumer's row state silently diverges from the primary's. Detection: periodic logical.rowequiv-style reconciliation in production (sampled row comparison). Root causes ranked: (1) aborted-txn leak (I8), (2) type-change record consumed out of order, (3) output-plugin serialization bug losing numeric precision (mitigated by Avro's schema-carrying format, ADR-08). Recovery: re-snapshot the affected table via snapshot_table() and restart the stream from the snapshot's LSN.

16.10 Operational Notes

Metrics: repl_logical_events_total{table}, repl_reorder_spill_total, repl_reorder_memory_bytes. Deployment: the reorder buffer's spill directory must be on the same host as the decoder (no cross-host spill in this design). Compatibility: a new LogicalChangeEvent variant is additive only — an old output plugin that does not recognize it must error explicitly, never silently drop it.

  • Rate-limiting DDL-triggered event floods without rate-limiting normal row events requires the two to be classified separately in the publication's flow-control path — conflating them throttles legitimate traffic during a schema migration.

17.7 Performance Concerns

SchemaTracker.apply_ddl() is on the decode hot path for every RMID_RELATION record; history is append-only per table and indexed by (table_oid, version) for O(1) lookup by a lagging consumer, not a linear scan of history.

17.8 Edge Cases

A DDL that both adds and drops a column in one migration transaction: policy evaluation must consider the whole transaction's DDL set, not approve/deny column-by-column with a mid-transaction partial-apply. A table not yet known to the tracker (first DDL seen before any DML): apply_ddl() on an unknown OID returns SchemaError::UnknownTable deterministically, not a panic.

17.9 Failure Analysis

Symptom: consumer errors decoding a payload against the wrong column layout. Detection: repl_schema_version_mismatch_total (I14 telemetry). Root cause: consumer did not maintain its own schema-version history, or the publication's DDL policy silently allowed a change the consumer could not handle. Recovery: consumer re-reads the primary's schema history for the (table_oid, version) pair via the publication's history endpoint.

17.10 Operational Notes

Metrics: repl_slot_ddl_abort_total, repl_schema_version_mismatch_total. Compatibility: schema-history format is versioned and additive (new SchemaChange variants require a protocol-version bump, mirroring §26). Runbook: DDL-triage section of docs/runbooks/slot-disk-full.md.

18. Phase 6 — Failover: Controlled Handover and Uncontrolled Promotion

18.1 Objectives

Implement the two failover paths (§3 failover plane): controlled handover (zero data loss, planned) and uncontrolled promotion (bounded loss, unplanned) — both operator-driven per P10/ADR-14, both requiring fencing before write-acceptance (I15).

18.2 Detailed Implementation Steps

  • Implement controlled_handover() (repo layout handover.rs): stop the old primary accepting writes → flush all pending WAL to final_lsn → every standby (new primary included) confirms flushed_lsn == final_lsn → bump TimelineId on all hosts simultaneously (P5, I4) → write the (non-forking) history entry → repoint clients. No divergence is possible because every host converges on the same LSN before the bump.
  • Implement promote() (repo layout promote.rs): require a Fence first (STONITH / quorum / operator confirmation — I15, structurally required by the function's own signature, not just by convention) → the promoted replica's received_lsn becomes the fork point → bump TimelineId → write and fsync the history entry (I10) → then accept writes → return a PromotionRecord flagging old_primary_potentially_diverged.
  • Implement the Fence trait (repo layout fence.rs) as an operator-supplied implementation (STONITH hardware call, quorum check via Blueprint #93/#37, or explicit human confirmation) — the library ships the hook, never a default automatic fence (ADR-14).

18.3 Deliverable

A controlled handover from primary A to standby B preserves every committed write; B's flush_lsn at handover time equals A's; clients repoint without a gap. An uncontrolled promotion of standby B after A's simulated host loss completes and opens writes within the RTO budget, with the fork LSN durably recorded before any write is accepted (I10).

18.4 Acceptance Criteria

  • Conformance bucket failover.controlled: zero committed writes lost, verified by comparing A's pre-handover commit log against B's post-handover state.
  • Conformance bucket failover.uncontrolled: RTO ≤ 30 s (M8, §29); history file written and fsynced strictly before the promoted replica's first accepted write (I10, timestamp- ordered assertion in the fixture).
  • Jepsen scenario split_brain_prevention: 1000 runs, 0 observed split-brain writes (M14, §29; I15).

18.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/failover/controlled_handover_a_to_b.scenario planned handover under load zero writes lost; clean timeline bump; client repoint succeeds
conformance/corpora/failover/uncontrolled_host_loss.scenario kill primary, promote standby RTO ≤ 30 s; history entry fsynced before first accepted write
jepsen-harness/scenarios/split_brain_prevention.clj network partition + promote + heal old primary never accepts a write after fencing completes

18.6 Pitfalls

  • Promotion without fencing is the textbook split-brain: A is partitioned, B is promoted, the partition heals, A's clients are still writing to A — both diverge, reconciliation becomes a manual merge. Fencing is structurally required (I15), never skippable.
  • A controlled handover that bumps the timeline before every sync standby (not just the new primary) has confirmed final_lsn produces a divergence on the lagging standby — wait for all of them, not just the promoted one.
  • Opening writes before the history file is fsynced (violating I10) loses the fork LSN on a crash immediately after promotion — the write-acceptance step must be strictly sequenced after the fsync, never reordered "for latency."

18.7 Performance Concerns

Controlled handover's RTO (M7, ≤ 5 s) is dominated by "wait for every standby to reach final_lsn" — a single slow standby in the sync set directly extends handover time; the handover path should time out and report which standby is blocking, not hang silently.

18.8 Edge Cases

A standby that is mid-catch-up (not yet a sync candidate) at the moment of a controlled handover: it is excluded from the "wait for all" set and simply reconnects post-handover as a lagging standby on the new timeline. A promotion where the fence itself fails (e.g., STONITH call times out): promote() must return FailoverError::NotFenced and refuse to proceed — never "promote anyway."

18.9 Failure Analysis

Symptom: two hosts both accepting writes ("split-brain"). Detection: Jepsen scenario (§18.5) in CI; in production, the divergence detector (Phase 7, §19) on any reconnect. Root cause: promotion without a completed fence (violates I15). Containment: once detected, both hosts are treated as untrusted for writes until an operator reconciles (§19.4). Blast radius: every write accepted by the fenced-but-not-actually-fenced host after the partition — bounded by the detection latency, not unbounded.

18.10 Operational Notes

Metrics: repl_failover_rto_seconds{kind}, repl_promote_without_fence_total (must stay 0). Runbooks: docs/runbooks/controlled-failover.md, docs/runbooks/ uncontrolled-failover.md (non-negotiable "fence first, promote second" ordering), and docs/runbooks/failover-drill.md (quarterly game-day cadence — an untested failover path is a broken one, §24 MM analogue).

19. Phase 7 — Timeline Forks: Detection and Reconciliation

19.1 Objectives

Detect and safely reconcile the divergence an uncontrolled promotion (§18) can create (P11, P5, I4, I10, I11) — this phase is what makes Phase 6's promotion safe, not just fast.

19.2 Detailed Implementation Steps

  • Implement detect_divergence() (repo layout detector.rs, §11.2 types): compare a rejoining host's HistoryFile against the cluster's; walk the set of timelines seen (not just the head) to catch a host that was briefly primary on an intermediate timeline before being demoted and is now rejoining on a later one still (§19.6 pitfall).
  • Run the detector on every reconnect, including cascading hops (I11) — a second-level standby whose upstream lost an uncontrolled promotion inherits the fork and must be caught too.
  • Implement rebase (repo layout rebase.rs): rename the divergent host's lost-range WAL segments to <segment>.lost.timeline.N (forensic preservation, never delete), stream the surviving cluster's WAL from fork_lsn forward.
  • Require explicit operator acknowledgement (replctl divergence reconcile --acknowledge-loss <bytes>) matching the detector's reported lost-range size before any rebase proceeds — deliberate friction (P11) forcing the operator to read the report first.

19.3 Deliverable

A rejoining old primary whose timeline diverged from the cluster's is flagged by the detector before it can rejoin as a standby; an operator-acknowledged rebase completes and the rejoined host streams cleanly from the fork point forward.

19.4 Acceptance Criteria

  • Conformance bucket divergence.detect: 100% detection rate across synthetic fork scenarios including the "demoted-then-rejoining-later" multi-timeline case (§19.6).
  • Conformance bucket divergence.reconcile: rebase preserves the lost range as a .lost.timeline.N file (verified present on disk, not merely "no error"); rebase refuses to proceed without a matching --acknowledge-loss byte count.
  • Zero auto-rebases across the entire conformance suite — every rebase in every fixture requires the explicit operator step.

19.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/divergence/simple_fork.scenario one uncontrolled promotion, old primary rejoins detector flags fork at correct fork_lsn
conformance/corpora/divergence/multi_timeline_rejoin.scenario host demoted on timeline 2, rejoins on timeline 3 cluster detector walks full timeline set, still flags divergence
conformance/corpora/divergence/reconcile_wrong_ack.scenario operator supplies a mismatched --acknowledge-loss byte count rebase refused; no data destroyed

19.6 Pitfalls

  • A detector comparing only the latest timeline ID misses the "briefly-primary-then- demoted-then-rejoining" case entirely — walk the full set of timelines in the history file, not just its head (I4, I11).
  • Deleting lost-range WAL before an operator has read the divergence report destroys forensic evidence and hides the data-loss magnitude — always rename, never delete (P11).
  • The .history file format must remain backward-readable across library versions — an old primary rejoining a cluster on a newer library version must still parse the current format; version the format explicitly and default-fill any newly-added field.

19.7 Performance Concerns

detect_divergence() runs on every reconnect (I11), including every cascading hop — for a depth-4 cascade this is 4 comparisons per full-chain reconnect, each O(history-file length), which is negligible (history files are small, growing only on failover events, not on every commit).

19.8 Edge Cases

A history file with a single entry (never forked): detector short-circuits to Divergence::None without walking anything. A candidate whose history file is ahead of the cluster's (it saw a timeline the cluster has not recorded — a corrupted or tampered history file): treated as an unrecoverable state — the library refuses to rebase and surfaces FailoverError::HistoryWriteFailed-adjacent error for manual forensic review, never a best-effort merge.

19.9 Failure Analysis

Symptom: a cascading replica's data quietly does not match the primary's. Detection: divergence.detect conformance bucket catches this class in CI; in production, the detector runs at every hop's reconnect (I11) and alerts immediately on a positive result. Root cause: an intermediate hop was the loser of an uncontrolled promotion and the fork propagated downstream before detection ran. Recovery: rebase the affected hop and every hop downstream of it, in order, from the fork point.

19.10 Operational Notes

Metrics: repl_divergence_detected_total, repl_history_write_before_accept_ms (I10 timing telemetry). Runbook: docs/runbooks/divergence-detected.md. Compatibility: history file version bump requires a documented migration note in docs/compliance/.

20. Phase 8 — Cascading Replicas and Read Scaling

20.1 Objectives

Implement multi-hop replication (primary → standby → standby) for read scaling with additive-lag accounting (P9, ADR-19), within the depth-4 default cap.

20.2 Detailed Implementation Steps

  • Implement cascade::repoint() (repo layout): a cascading replica whose upstream is lost repoints to a surviving upstream (the new primary or another standby) — operator-initiated (auto-repoint deferred, consistent with ADR-14's failover-policy boundary).
  • A first-level standby simply is a walsender to its own downstream connections — the protocol is symmetric (§3 architectural property #2); no cascading-specific wire format is needed, only a cascading-aware divergence check (I11, reusing §19's detector at every hop).
  • Track and expose the per-hop lag chain (feeds Phase 9's lag surface, §21): a third-level standby's total lag is the sum of every hop's lag (P9).
  • Enforce the depth-4 default cap (ADR-19) at slot-creation time for a cascading slot — reject creation beyond the configured depth with a named error, not a silent accept.

20.3 Deliverable

A depth-3 cascading topology (primary → A → B → C) streams a 1 GiB workload with cumulative replay lag under the target bound; replctl cascade repoint <new_upstream> repoints a cascading replica without data loss when its upstream is lost.

20.4 Acceptance Criteria

  • Conformance bucket physical.cascade_depth3: tail standby's replay_lsn matches the head primary's flush_lsn within 5 s cumulative lag (M10, §29).
  • repoint() completes with zero duplicate-applied records and zero gap in the repointed replica's WAL (I3-consistent).
  • A cascading-slot creation request beyond the configured depth cap is rejected with SlotError-adjacent named error, not silently truncated to the cap.

20.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/physical_bitparity/cascade_depth3_1gib.workload 3-hop cascade, 1 GiB primary workload tail lag ≤ 5 s cumulative
conformance/corpora/physical_bitparity/cascade_repoint.scenario mid-stream upstream loss, repoint to new upstream zero duplicate apply, zero gap
conformance/corpora/physical_bitparity/cascade_depth_exceeded.scenario attempt depth-5 slot creation creation rejected with named error

20.6 Pitfalls

  • A cascading replica catching from a forked timeline (its immediate upstream lost an uncontrolled promotion) inherits the divergence silently unless the detector runs at every hop, not just at direct-primary connections (I11, §19.9).
  • A cascading replica's confirmed_flush_lsn advances relative to its immediate upstream, not the primary — an operator reading only the primary's slot list under-counts the true chain depth's lag; traversing the full chain is required for an accurate picture.
  • Read-after-write against a cascading replica is lag-bound consistent (ADR-16) against the cumulative chain lag, not just the last hop's — document this explicitly or application authors will underestimate staleness by 2–3x on a depth-3 chain.

20.7 Performance Concerns

Cascading offloads the primary's egress: a 4-way fan-out at each of 2 levels (1 → 4 → 16) achieves 16x read-replica count at roughly 4x the primary's direct walsender load, not 16x (§33 #9 derivation). The trade is lag: each hop adds its own replay-lag term additively.

20.8 Edge Cases

A cascading replica whose upstream is itself mid-repoint (chained repoint events): serialize repoints per-hop, never allow two repoint operations targeting overlapping hops to race. A depth-1 topology (no cascading) is the degenerate, always-valid case — the cap check must not misfire against it.

20.9 Failure Analysis

Symptom: read replicas at the tail of a cascade show unexpectedly high staleness. Detection: per-hop lag telemetry (feeds Phase 9, §21) makes the chain visible; a dashboard graphing only the primary's direct standbys misses this class entirely (P9, P12). Root cause: an intermediate hop is itself lagging, compounding downstream. Recovery: the runbook's slow-replica triage applied to the specific lagging hop, or a repoint() to a faster upstream if one exists.

20.10 Operational Notes

Metrics: repl_cascade_depth, repl_cascade_hop_lag_seconds{hop}. replctl cascade repoint is the operator surface. Deployment: cascading topology is config (which host's upstream is which), never auto-discovered — this is a deliberate simplicity trade consistent with ADR-14's operator-driven philosophy.

21. Phase 9 — Lag Monitoring and Alerting Hooks

21.1 Objectives

Implement the four-point lag surface (send/receive/flush/replay, P12) with pluggable alerting, closing the "40-minute unnoticed lag" failure class.

21.2 Detailed Implementation Steps

  • Implement LagReport (repo layout lag.rs, §11 types): all four lag numbers, in both bytes and duration, per standby, measured against the primary's current flush_lsn (P12 — reporting fewer than all four is itself the bug this phase exists to prevent).
  • Implement LagAlertSink trait: on_lag_exceeded(report, threshold); default implementation logs via tracing::warn!; production sinks (PagerDuty, Slack, etc.) are operator-supplied implementations, not built-in integrations (consistent with the library-not-service posture, §1).
  • Compute send_lag = primary.flush_lsn - walsender.last_sent_lsn; receive_lag = primary.flush_lsn - standby.received_lsn; flush_lag = primary.flush_lsn - standby.flushed_lsn; replay_lag = primary.flush_lsn - standby.replay_lsn — each computed independently, never derived from another (avoids compounding an upstream measurement error).
  • Wire lag computation to rely on KeepAlive's current_lsn for the primary's baseline (§11.5) — a standby that has not received a keepalive recently must flag its own lag reading as stale, not report an artificially low number.

21.3 Deliverable

replctl status prints all four lag numbers (bytes and duration) for every standby; LagAlertSink::on_lag_exceeded fires within 1 s of a configured threshold breach.

21.4 Acceptance Criteria

  • Conformance bucket lag.accuracy: reported lag within 5% of a synthetic 100 MB/s–1 GB/s workload's ground truth (M13-adjacent, §29).
  • Conformance bucket lag.alert_on_replay: alert fires within 1 s of a replay_lag threshold breach — timestamp-ordered assertion in the fixture, not "eventually." Alert fires on flush_lag breach for RPO-relevant SLAs distinctly from replay_lag for staleness SLAs — the two must be independently configurable thresholds.

21.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/lag/synthetic_100mb_1gb.workload ramped write-rate workload reported lag within 5% of ground truth at every rate step
conformance/corpora/lag/replay_threshold_breach.scenario injected apply-side stall alert fires within 1 s of crossing configured threshold
conformance/corpora/lag/stale_keepalive.scenario keepalive gap > 30 s lag reading flagged stale, not silently understated

21.6 Pitfalls

  • Reporting only receive_lag (near-zero because TCP kept up) while replay_lag grows unbounded is exactly the bug that let a 40-minute lag go unnoticed in the field — report all four, always (P12).
  • On a low-write-rate workload, lag duration looks artificially good (no WAL to replay); alerting must combine bytes and duration in one rule, or a standby stalled for 10 s on a 1 KB/s workload reads as "fine."
  • A standby computing lag against a stale primary.flush_lsn baseline (missed keepalives) silently under-reports its own staleness — treat a keepalive gap as a first-class alert condition, not a quiet fallback to the last-known value.

21.7 Performance Concerns

LagReport computation is O(1) per standby per report interval; the reporting interval itself (typically 1 s) must not become a hot-path bottleneck at 20 sync-candidate standbys — batched into one status-tick per interval, not one timer per standby.

21.8 Edge Cases

A brand-new standby with received_lsn == Lsn::ZERO before its first frame: lag is reported as "initializing," not as a false-positive multi-terabyte lag against Lsn::ZERO. A standby that briefly exceeds the primary's last-known flush_lsn due to a stale baseline read (should be impossible per I1, but defensively checked): clamp to zero and emit repl_lsn_regression_total rather than reporting negative lag.

21.9 Failure Analysis

Symptom: an operator discovers stale reads long after the fact. Detection: this is precisely the failure this phase prevents — post-incident, the fix is always "the wrong lag number was graphed" or "the threshold was on the wrong number for the SLA in question" (P12). Recovery: correct the dashboard/alert configuration; no data-plane recovery is needed (lag alone is not data loss).

21.10 Operational Notes

Metrics: repl_send_lag_bytes, repl_receive_lag_bytes, repl_flush_lag_bytes, repl_replay_lag_seconds (all four, per standby, always). replctl status is the at-a-glance operator view. Dashboards must graph all four distinctly — a combined "lag" single-number dashboard is itself flagged as an anti-pattern in docs/runbooks/slow-replica.md.

22. Phase 10 — Performance Hardening

22.1 Objectives

Reach the throughput targets (M1, M2, §29) via parallel apply, batching, compression, and network tuning — the only phase whose objective is a number, not a new capability.

22.2 Detailed Implementation Steps

  • Implement ParallelApplier (repo layout parallel_apply.rs): a conflict tracker identifies non-conflicting records (different pages) for cross-transaction parallel apply; parallel-within-a-transaction is unsafe (I3 — commit ordering) and never attempted — only cross-transaction parallelism, conflict-graph-gated, matching the Postgres 9.6 "parallel apply" precedent (§5 Ref-impl #1 caveat: study, do not copy the C).
  • Implement batching in the walsender: pack up to 1 MiB of records per XLogData frame (amortizing per-frame codec overhead) with a batch timer that triggers on commit boundaries, not purely on byte thresholds — delaying a transaction's last record blocks its sync ack (§14).
  • Enable streaming zstd level 3 compression (ADR-13) per-frame (not per-record) so receivers decompress in parallel across frames; skip compression for payloads that fail a cheap entropy estimate on the first 4 KiB (already-compressed TOAST/binary values inflate rather than shrink).
  • Set TCP_NODELAY off by default for cross-DC links (let the kernel coalesce), on for sync-mode links (latency dominates) — a per-slot flag, not a global one.

22.3 Deliverable

Physical throughput ≥ 500 MB/s on a 10 GbE link (single-core walsender+walreceiver); logical throughput ≥ 50K rows/sec (single-core decoder + Avro); sync-ack p99 ≤ 5 ms same-DC — all measured on the conformance/benchmark harness, not projected.

22.4 Acceptance Criteria

  • Conformance bucket perf.physical_throughput: ≥ 500 MB/s sustained over a 10-minute run (M1, §29).
  • Conformance bucket perf.logical_throughput: ≥ 50K rows/sec sustained (M2, §29).
  • Parallel apply preserves I3 (apply order = commit order) under a 1000-transaction concurrent-conflict stress fixture — zero ordering violations, not "rare."

22.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/perf/physical_throughput_10gbe.bench sustained 10 GbE workload, 10 min ≥ 500 MB/s throughput, p99 sync-ack ≤ 5 ms
conformance/corpora/perf/logical_throughput_avro.bench single-core decode + Avro emit ≥ 50K rows/sec
conformance/corpora/perf/parallel_apply_conflict_stress.scenario 1000 concurrent conflicting/non-conflicting txns zero I3 ordering violations

22.6 Pitfalls

  • Parallel apply that does not respect commit ordering produces a non-existent intermediate state visible to a concurrent reader on the replica — group by commit, parallelize within a commit's non-conflicting records, preserve order across commits, never the reverse.
  • Compressing already-compressed payloads (TOAST'd values, binary blobs) inflates rather than shrinks — the entropy-estimation skip is not an optimization, it is a correctness- adjacent efficiency fix (uncompressed-but-marked-compressed frames would corrupt the decoder if the skip logic and the frame header disagree).
  • A batch timer that delays a transaction's last record to fill a byte threshold directly extends that transaction's sync-ack latency — the timer must always flush on a commit-record boundary regardless of accumulated byte count.

22.7 Performance Concerns

PhaseDeferred("§22.7"): per-key parallel logical apply (sharding consumer-side workers by primary key) is a natural extension of this phase's conflict-tracker concept applied to the logical pipeline, not built here — it is safe within one table, complicated across foreign-key relations, and left as a stretch (Debezium's per-table variant is the closest real precedent, §5 Ref-impl #5). Within this phase: allocation-per-record in the hot decode/apply path is the dominant cost at 50K rows/sec; the reference implementation reuses buffers within a transaction's lifetime.

22.8 Edge Cases

A workload with mostly single-page "hot" transactions (a counter table under heavy contention): the conflict tracker degenerates to serial apply for that table — correct, not a bug, and observable via a low parallel-apply utilization metric rather than a silent throughput cliff. A batch that would exceed MAX_PAYLOAD (16 MiB, §11.10) mid- transaction: flush the batch before the limit, never truncate a record across frames.

22.9 Failure Analysis

Symptom: replica page state briefly visible in an order the primary never produced. Detection: perf.parallel_apply_conflict_stress conformance bucket (zero-tolerance); production detection is a page-checksum reconciliation sweep (replctl reconcile pages). Root cause: conflict tracker missed a true conflict (e.g., two records touching the same page via different index structures). Recovery: disable parallel apply for the affected table (config fallback to serial) while the conflict-detection gap is fixed; reseed the replica from a fresh snapshot.

22.10 Operational Notes

Metrics: repl_parallel_apply_workers_active, repl_batch_frame_bytes, repl_compression_ratio, repl_compression_skip_total. Deployment: TCP_NODELAY and batch-size are per-slot config, tunable without a restart. Benchmarks tracked in benchmarks/results/ per commit SHA, gated in CI against M1/M2 regressions (§27, §29).

25. Operational Readiness

Metrics. All repl_* counters/gauges/histograms named throughout §12–§22 and §23–§24 are exported via a Prometheus-compatible exposition format; every metric name is stable across minor versions (§26).

Tracing. Every WAL-record apply, every slot advance, every failover state transition emits a tracing span tagged with lsn, timeline_id, slot_name where applicable — sufficient to reconstruct a full causal trace of any incident from span data alone.

Structured logging. JSON-formatted; every log line carries component (walsender/ walreceiver/decoder/failover/divergence), slot_name, and lsn fields for machine-parseable incident correlation.

Dashboards. Four mandatory panels per deployment: (1) four-point lag surface per standby (§21, P12 — never fewer than four), (2) slot count + retained-WAL bytes (§15), (3) failover/divergence event timeline (§18–19), (4) throughput vs M1/M2 targets (§29).

Alerting philosophy. Alert on replay_lag for staleness SLAs, on flush_lag for RPO-relevant SLAs — independently configurable thresholds (§21.4); alert on SlotStale and SyncDegraded unconditionally (both indicate a durability-contract question, never routine).

SLOs. Physical replay lag ≤ 1 s at steady state (M9); controlled-failover RTO ≤ 5 s (M7); uncontrolled-failover RTO ≤ 30 s (M8); zero split-brain writes (I15, Jepsen-gated).

Incident response. Named runbooks (§10 docs/runbooks/): triage.md (first 5 minutes), slow-replica.md, slot-disk-full.md, controlled-failover.md, uncontrolled-failover.md, divergence-detected.md, failover-drill.md (quarterly game-day, §18.10).

Backup/restore. A physical standby is itself a hot backup; PITR bootstrap (PhaseDeferred("§13.3")) shares the slot's restart_lsn as its anchor point when built.

Deployment topology. Primary + N sync/async standbys + optional cascading tier + optional logical CDC consumers, all config-driven (§20.10) — no auto-discovery.

Canary/rolling-upgrade/rollback. A new library version is deployed to one standby first (canary); the wire-protocol version handshake (§26) refuses to stream to an incompatible peer rather than silently misbehaving; rollback is "redeploy the prior binary," since no schema migration is required for a minor version.

26. Compatibility & Versioning

Wire compatibility. WireMessage variants are additive-only across minor versions; a new variant requires a protocol-version handshake bump (checked at START_REPLICATION time, §8.3) — an old peer that does not recognize a new variant refuses the connection explicitly, never silently drops unknown frames.

Storage compatibility. Slot file format (§11.9) and .history file format (§11.2) are independently versioned; both are backward-readable — a newer library reads an older slot/history file and default-fills any newly-added field (§19.6).

Schema-evolution compatibility. LogicalChangeEvent::Schema events are the sole channel for schema change; schema_version (I14) is monotonic per table; a consumer must be able to answer "what did column X mean at version V" from schema history, not just "what does it mean now."

API stability. repl-core public types (§11) follow SemVer: a breaking field change is a major version bump; all Repl*Error enums are #[non_exhaustive] so adding a variant is a minor-version-compatible change for downstream match arms with a wildcard.

Migration. ADR-03's dependency on Blueprint #69's WAL format means a #69 format change requires a coordinated migration ADR here, not an independent one.

Deprecation policy. A deprecated field/variant is marked for one full major version before removal; CHANGELOG.md names the removal version explicitly at the time of deprecation, not retroactively.

Rolling-upgrade guarantees. A cluster may run mixed library versions during a rolling upgrade as long as every host is within one minor version of every peer it directly streams to or from — cross-major-version streaming is refused (ADR-21 notwithstanding, which covers cross-engine Postgres XLog compatibility, a separate axis).

27. Testing & Verification Strategy

Unit. Per-crate, gating I1–I15 invariants at the type level where possible (e.g., Lsn::cmp totality, HistoryFile append-only construction).

Integration. Cross-crate scenarios: primary+standby streaming, slot lifecycle across process restart, failover state-machine transitions — one test binary per phase's deliverable (§12–§22 N.3).

Property-based. Lsn/TimelineId arithmetic fuzzed against algebraic properties (monotonicity, no-decrease); reorder-buffer commit-order preservation fuzzed against randomized transaction interleavings (I3, I8).

Differential. physical.bitparity conformance bucket is inherently differential — primary WAL bytes vs standby WAL bytes, byte-for-byte (§13.5).

Fuzzing. repl-fuzz harnesses (§10, cargo-fuzz, nightly CI): frame_roundtrip.rs (codec, I7), xlog_parse.rs (malformed WAL records), reorder_buffer.rs (adversarial xid interleaving), schema_evolution.rs (malformed DDL sequences), slot_lifecycle.rs (adversarial create/advance/drop ordering).

Chaos / fault injection. Jepsen harness (jepsen-harness/, ADR-20): network partition, cascading partition, clock skew scenarios — gates split_brain_prevention (I15) as a hard CI requirement.

Deterministic replay. The Phase-0-established simulator (§7 debugging methodology) is seeded; a CI failure reproduces bit-for-bit via the seed, no flaky-test triage guesswork.

Soak. 30-day continuous run (soak.yml, §10): zero panics, zero unbounded memory growth — gates the Sealed release status (ADR-24).

Conformance. The full bucket list of §12–§22's N.5 fixtures, aggregated by the conformance/runner into conformance.report.json (§8's report schema analogue); gates Done/Sealed transitions per ADR-24.

Performance-regression gating. Every M1–M14 target (§29) is checked in CI per commit; a regression beyond a configured tolerance band fails the build, not just the dashboard.

30. Scalability Analysis

What stays constant. Per-connection memory (one Framed codec state per walsender/ walreceiver pair) — O(1) per standby regardless of WAL volume. LSN/TimelineId arithmetic — O(1) always.

What grows, and the Big-O. Slot count: min_restart_lsn() is O(slots) per checkpoint (cached, §15.7, effectively O(1) amortized). Reorder-buffer memory: O(concurrent open transactions × avg transaction size), capped and spilled (§16.2). Cascading chain lag: O(depth) additive (P9, ADR-19 caps depth at 4). Sync-candidate fan-out: wake-path is O(log n + k) per ack (§14.7) where n = waiters, k = newly satisfied.

Named bottlenecks, in order. (1) Primary WAL-write throughput (§4, 500 MB/s steady) — the hard ceiling every downstream consumer is bounded by. (2) Single-core decode throughput for logical (50K rows/sec) — the reason PhaseDeferred("§22.7") per-key parallel logical apply exists as the next lever. (3) Cross-region RTT for sync/quorum modes (§4, 150 ms) — a physical latency floor no software change removes. (4) FD/socket budget for sync-candidate fan-out (§4, 20 candidates within a 65536 FD budget) — the reason cascading (§20) exists as the read-scaling lever instead of flat fan-out.

Horizontal scaling. Read scaling via cascading replicas (§20) trades lag for reduced primary egress; horizontal write scaling is explicitly out of scope (single-writer model, ADR-14) — that is Blueprint #99's (multi-primary) or #93/#37's (consensus-replicated multi-node write) territory.

Sharding/partitioning. Not applicable at this layer — sharding is a property of the storage engine (Blueprint #43) or an orchestration layer above this replication transport, which this library's slot/publication model already supports per-table.

Coordination overhead. Quorum-mode ack coordination is O(eligible standbys) per commit (bounded by the FD budget above); controlled handover's "wait for all sync standbys" step is the single largest coordination cost in the whole system, bounded by the slowest sync standby (§18.7).

Practical ceiling and the levers beyond it. The practical ceiling for this design is roughly one primary's WAL-write throughput (500 MB/s–1.2 GB/s, §4) fanned out to O(10–20) direct standbys via sync/async modes plus O(4) cascading levels for read scaling. Beyond that ceiling, the levers are architectural, not parametric: shared-log storage (Aurora model, §32, §35.4) removes the per-standby apply bottleneck entirely; consensus-replicated multi-writer (Raft/Paxos, §35.2) removes the single-primary write ceiling at the cost of write-path coordination latency.

31. Mental Models & First Principles

  • MM1 — A replica is a fold over an event log, not a copy of a database. The compressed insight: state = fold(apply, initial_state, wal_records); everything about replication is a statement about which prefix of that fold a given consumer has computed. Predicts: any two consumers holding the same prefix hold the same state, regardless of transport. Bug class without it: treating a standby as "a separate database that happens to be kept in sync" leads to ad-hoc reconciliation logic instead of trusting the fold. Applied in §8.9, §13 (Phase 1).
  • MM2 — LSN is a clock, not just an offset. The compressed insight: Lsn totally orders every event the way a Lamport clock orders causally-related events — comparing two LSNs answers "which happened first," full stop. Predicts: any invariant statable as "X must never decrease" (I1, I4) is a clock-monotonicity statement. Bug class without it: comparing LSNs across different timelines as if they were on one clock (exactly the timeline-fork bug, §19). Applied in §7 I1/I4, §19.
  • MM3 — Durability is a race between "acknowledged" and "on disk," and replication adds a second racer. The compressed insight: local fsync (I2) and replication ack (§14) are two independent races to "safe," and a system's actual RPO is whichever racer is slower to cross the threshold the caller asked for. Predicts: any RPO number is meaningless without naming which mode (§11.4) was in effect. Bug class without it: quoting "zero RPO" for a system running in Async mode. Applied in §4, §14.
  • MM4 — A replication slot is a durability promise, not a cursor. The compressed insight: a cursor just remembers a position; a slot additionally obligates the primary to keep serving from that position (I6). Predicts: every "why did WAL grow unboundedly" incident traces to a promise nobody is redeeming. Bug class without it: treating slot cleanup as a garbage-collection nicety rather than an active safety trade-off (P8). Applied in §7 I5/I6, §15.
  • MM5 — A timeline is a version number for "history," not for "data." The compressed insight: the rows don't change meaning across a timeline bump; what changes is which sequence of WAL records is now canonical. Predicts: comparing timelines answers "are we even talking about the same history," a strictly prior question to comparing LSNs. Bug class without it: assuming any two hosts at LSN 100 agree on what happened, without checking they're on the same timeline (§19.6). Applied in §7 I4, §19.
  • MM6 — Logical decoding is a lossy compiler from bytes to intent, and DDL is a change to the target language. The compressed insight: the decoder "compiles" WAL bytes into LogicalChangeEvents using a schema as its type system; a DDL change is a language change mid-compilation. Predicts: any decoder that doesn't version its "language" (schema_version, I14) will eventually misparse. Bug class without it: silent DDL skip (P6). Applied in §17, §7 I9/I14.
  • MM7 — Fencing is mutual exclusion for an entire host, not a lock on a resource. The compressed insight: promotion without fencing is exactly the classic "two processes believe they hold the same lock" bug, just at cluster scale. Predicts: any "auto-failover" design that skips fencing will eventually produce two writers. Bug class without it: assuming a network partition heals cleanly without an explicit exclusion mechanism (P10, I15). Applied in §18, §23 T1.
  • MM8 — Lag is staleness measured against a moving target. The compressed insight: because the primary keeps writing, "how far behind" is a rate comparison (write-rate vs apply-rate), not a static distance — a replica can be "100 MB behind" and either catching up or falling further behind depending on the two rates. Predicts: reporting only bytes (not the rate trend) under-informs an operator. Bug class without it: the "40-minute unnoticed lag" incident, where bytes looked stable-ish while the trend was diverging. Applied in §21, §33 #1/#3.

PostgreSQL made physical streaming and logical decoding both first-class from the same WAL, at the cost of maintaining two decode paths against one format — this design copies that decision (P1) because the alternative (logical-only, or physical-only) fails either the HA or the CDC use case. MySQL made row-based binlog also serve as the logical-replication channel, unifying the two formats at the cost of a less clean separation between "what happened" (statement) and "what changed" (row) — it wins when a single wire format for both HA and CDC is operationally simpler than maintaining two. Raft-replicated log (etcd/raft) eliminates fork/divergence by construction — no promotion ever produces two histories because commitment itself requires a quorum before it's "real" — it wins whenever automatic leader election and split-brain-by-construction are worth the write-latency cost of a quorum round-trip on every entry (this design defers exactly this trade to Blueprints #93/#37, §35.2). Chain replication achieves strong consistency with cheap reads at the tail and a simple reconfiguration model, at the cost of write latency scaling with chain length — it wins in a small, low-churn cluster where read throughput at strong consistency matters more than write latency. Amazon Aurora removes the entire "apply WAL to a page cache" step from every replica by making replicas read a shared log-structured store directly — it wins whenever storage-compute disaggregation is available and per-replica apply CPU is the bottleneck this design's Phase 10 (§22) spends real engineering effort fighting. Kafka (ISR) generalizes this design's TimelineId/history-file fork detection into leader epochs (the direct ancestor of I4, per KIP-101) and treats "replication" as an ordered, partitioned log from the start — it wins when the unit of replication is naturally an append-only event stream rather than a mutable-row database.

33. Back-of-Envelope Capacity Model

All derived from §4 System Constraints; formula shown for each.

  1. Steady-state replay lag = WAL production rate ÷ apply rate. At §4's 500 MB/s primary write rate against a single-core physical apply rate of ≥ 500 MB/s (M1), lag trends to ≈ 0 in steady state; logical apply is rate-limited by decode throughput (50K rows/s × ~200 B/row ≈ 10 MB/s, M2), so a primary sustaining > 10 MB/s of logically-relevant row churn will show growing logical lag unless parallelized (PhaseDeferred("§22.7")).
  2. Aggregate primary egress bandwidth = write_rate (MB/s) × direct_standby_count. At 500 MB/s and 3 direct sync/async standbys: 1.5 GB/s aggregate egress — this is why cascading (§20, ADR-19) exists: fan-out beyond ~3–4 direct standbys should go through a cascading tier instead of scaling egress linearly.
  3. Catch-up time after downtime = backlog_bytes ÷ (apply_rate − concurrent_write_rate). A standby down for 1 hour at the 500 MB/s write rate accumulates 500 MB/s × 3600 s ≈ 1.8 TB backlog; resuming at a 500 MB/s apply rate against a reduced 100 MB/s live write rate: 1.8 TB ÷ (500 − 100) MB/s ≈ 4500 s ≈ 75 minutes to fully catch up.
  4. Backlog buffer / disk headroom = slot_timeout × write_rate. At the ADR-18 default 24 h and 500 MB/s: 24h × 3600 × 500 MB/s ≈ 43.2 TB worst-case retained WAL — this is precisely why ADR-18 wins for a low-write-rate primary but a high-write-rate primary must tune the timeout down (§4, §15.6).
  5. Reorder-buffer memory footprint = concurrent_open_txns × avg_txn_size. At an observed 1000 concurrent long-running transactions averaging 256 KB of buffered changes each: 1000 × 256 KB = 256 MB — matching the §4 default 256 MiB/slot spill threshold almost exactly, i.e., the default cap is calibrated to "one large transaction's worth," not an arbitrary round number.
  6. Sync-ack latency budget = local_fsync + RTT + standby_fsync. Same-DC: 0.5 ms + 0.5 ms + 0.5 ms = 1.5 ms, matching M3's p50 target exactly. Cross-region: 0.5 ms + 150 ms + 0.5 ms ≈ 151 ms, within M5's 200 ms p99 bound with headroom for jitter.
  7. Quorum majority = floor(n/2) + 1. For n = 3, 5, 7 sync candidates: majority = 2, 3, 4 respectively — each tolerates exactly ⌈n/2⌉ − 1 simultaneous standby failures without blocking writes (ADR-06, DeCandia et al. 2007).
  8. FD budget for sync-candidate fan-out = sync_candidates × FDs_per_standby. At the §4 cap of 20 sync candidates and ~2 FDs each (one socket, one status-timer-adjacent handle): 20 × 2 = 40 FDs — trivial against a 65536 FD ulimit, confirming the fan-out cap in §4 is set by lag/operational-complexity concerns (P9), not FD exhaustion.
  9. Cascading fan-out efficiency = total_replicas ÷ primary_direct_connections. A two-level 1 → 4 → 16 topology serves 16 leaf replicas from only 4 primary-direct connections: 16 ÷ 4 = 4x read-scaling multiplier per unit of primary egress, at the cost of each leaf's lag being the sum of two hops (P9).
  10. Cascading cumulative lag (depth 3) = hops × per_hop_lag. At an observed ~1.5 s per-hop replay lag: 3 × 1.5 s = 4.5 s, under the M10 5 s target with headroom — consistent with ADR-19's depth-4 cap being chosen for lag-budget reasons.
  11. WAL retention floor = slowest_slot_lag_seconds × write_rate. A slot lagging 10 minutes behind at 500 MB/s requires 600 s × 500 MB/s = 300 GB of WAL retained purely for that one slot (I6) — this number, not disk capacity in the abstract, is what the slot-timeout policy (ADR-18) is really bounding.
  12. Wire bandwidth after compression = write_rate ÷ compression_ratio. At 500 MB/s and zstd level 3's observed 3–5x ratio on WAL streams (ADR-13): effective wire demand of 500 ÷ 4 ≈ 125 MB/s at the midpoint ratio — the difference between needing a dedicated 10 GbE cross-region link and fitting comfortably on a 1 Gbps one.

35. Alternative Architectures (Roads Not Taken)

35.1 Multi-primary (active-active) replication instead of single-leader streaming

   Client A ──▶ Primary A ◀──sync/async──▶ Primary B ◀── Client B
                   │  conflict resolution (LWW / vector clock / CRDT)   │
                   └────────────────────────────────────────────────────┘

Regime where it wins: multi-region write locality where cross-region write latency to a single leader is unacceptable and the application can tolerate (or resolve) write conflicts. Real system: MySQL Group Replication / Galera Cluster (certification- based conflict detection). Why rejected here: this design's whole invariant set (I1–I15) assumes a single writer per timeline; adding true multi-writer requires a conflict- resolution layer with its own correctness model — explicitly Blueprint #99's territory (§1 non-goals), not a parameter on this design.

35.2 Consensus/Raft-replicated log instead of single-leader streaming + operator failover

   Client ──▶ [ Raft leader ] ──replicate(entry)──▶ [ Follower ] [ Follower ]
                    │  commit only after quorum ack; leader election built in
                    ▼
              Applied to state machine (this design's "apply path", §13.4, generalized)

Regime where it wins: environments requiring automatic leader election and split-brain- by-construction, where the write-latency cost of a quorum round-trip per entry is acceptable. Real system: etcd/raft, embedded in CockroachDB and etcd itself. Why rejected here: this design's ADR-14 deliberately keeps failover operator-driven because a consensus layer is a separate, substantial system (Blueprints #93 Paxos / #37 Raft) that this replication transport is designed to compose underneath, not reimplement — building it in here would duplicate #93/#37's entire scope.

35.3 Statement-based logical replication instead of row-based/physical-WAL-decoded

   Primary: executes "UPDATE t SET x = x + 1 WHERE id = 5"
       │  ships the STATEMENT, not the resulting row change
       ▼
   Replica: re-executes the statement locally (must be deterministic!)

Regime where it wins: workloads where statements are naturally small relative to the rows they affect (a bulk UPDATE touching a million rows ships as one statement, not a million row-events) — historically MySQL's original binlog default. Real system: MySQL's statement-based binlog format (the default before row-based became standard practice). Why rejected here: statement replication requires the statement to be deterministic on replay (no NOW(), no non-deterministic UDFs, no auto-increment divergence) — a correctness burden this design's row-based LogicalChangeEvent model (§11.6) avoids entirely by shipping the already-resolved result of execution, matching the row-based-binlog and Postgres logical-decoding precedent (§5 Ref-impl #1, #2).

35.4 Shared-log, log-is-the-database architecture instead of per-host replicated storage

   Primary ──▶ [ Shared durable log service (multi-AZ) ] ◀── Replica reads directly
                        no per-replica "apply to local page cache" step at all

Regime where it wins: cloud environments with disaggregated storage available, where per-replica apply CPU (this design's Phase 10, §22, fights hard to optimize) is the dominant bottleneck and can instead be eliminated by having every replica read from one shared, already-durable log. Real system: Amazon Aurora (§5 Papers #7, §32). Why rejected here: this design targets a portable, storage-agnostic replication library (§1) that must work against any storage backend (including Blueprint #69's own WAL) — committing to a shared multi-AZ log service is an infrastructure dependency this project does not control, and is explicitly deferred (ADR-25, PhaseDeferred("§32")) rather than built as this design's default.

37. Glossary

  • LSN (Lsn) — 64-bit monotonic byte offset into a timeline's WAL; the system's global ordering primitive (I1).
  • TimelineId — 4-byte monotonic identifier bumped on every promotion; the fork-detectability primitive (I4, P5).
  • WAL (Write-Ahead Log) — the append-only durability log every replication consumer reads from, format owned by Blueprint #69 (ADR-03).
  • walsender — the primary-side (or cascading-standby-side) process/task streaming WAL to a consumer.
  • walreceiver — the standby-side task receiving and persisting streamed WAL.
  • Replication slot — the durability contract preventing WAL truncation ahead of a registered consumer (P8, I5, I6).
  • restart_lsn — the LSN before which a primary will not truncate WAL for a given slot.
  • confirmed_flush_lsn — the LSN a slot's consumer has durably confirmed receipt of.
  • catalog_xmin — for logical slots, the oldest catalog snapshot the decoder still needs.
  • XLogRecord — one physical WAL record (§8.1 layout).
  • XLogData — the wire message carrying one or more XLogRecords.
  • KeepAlive — a walsender heartbeat frame, optionally requesting a status reply.
  • StandbyStatusUpdate — the four-LSN status frame a walreceiver sends upstream.
  • HotStandbyFeedback — a walreceiver frame informing the primary of the standby's oldest still-needed transaction horizon.
  • Reorder buffer — the logical-decode component grouping row operations by transaction ID, emitting in commit order (I3, I8).
  • Output plugin — the pluggable serializer converting LogicalChangeEvents to a wire format (Avro/JSON/protobuf, ADR-08).
  • Logical decoding — converting physical WAL records into row/statement-level change events.
  • Physical replication — byte-for-byte WAL shipping and replay.
  • Synchronous replication — a mode where the primary waits for at least one standby's acknowledgement before completing a commit (P2).
  • Asynchronous replication — the default mode; the primary never waits for replication acknowledgement (ADR-04).
  • Quorum replication — waiting for N of M standbys to acknowledge, threshold floor(n/2)+1 by default (P13, ADR-06).
  • Semi-synchronous replication — the general industry term for what this design splits into SyncReceive/SyncReplay (§11.4).
  • Cascading replica — a standby whose WAL source is another standby, not the primary (§20).
  • Controlled handover — a planned, zero-data-loss failover with all hosts converging on one LSN before the timeline bump (§18.2).
  • Uncontrolled promotion — an unplanned failover with a bounded-loss fork risk, requiring fencing first (§18.2, I15).
  • Fencing — the act of preventing an old primary from accepting writes after a promotion (STONITH/quorum/operator, §18.4).
  • STONITH — "Shoot The Other Node In The Head"; a hardware-level fencing mechanism.
  • Divergence — the state where two hosts' histories have forked and cannot be reconciled without data loss (§19).
  • Timeline fork — the point at which two timelines share a prefix but diverge (§19.1).
  • History file — the per-host append-only record of timeline boundaries and fork LSNs (§11.2).
  • Fork LSN — the LSN at which a timeline fork occurred.
  • Rebase / rewind — reconciling a divergent host onto the current timeline after operator acknowledgement (§19.3–19.4).
  • RPO (Recovery Point Objective) — the maximum acceptable committed-data loss, measured here in bytes bounded by flush_lag (async) or zero (quorum, §4).
  • RTO (Recovery Time Objective) — the maximum acceptable time to restore write availability after a fault (§4, M7/M8).
  • Replay lag — primary.flush_lsn − standby.replay_lsn; the read-staleness number (§21.1).
  • Flush lag — primary.flush_lsn − standby.flushed_lsn; the RPO-exposure number.
  • Receive lag — primary.flush_lsn − standby.received_lsn; the network-transit number.
  • Send lag — primary.flush_lsn − walsender.last_sent_lsn; the primary-side send-queue number.
  • Publication — the named configuration governing which tables and DDL-policy a logical slot exposes (§17.2).
  • DDL policy — Deny/AllowAdditive/AllowAll; governs how schema changes flow to logical consumers (ADR-09, I9).
  • Schema version — the monotonic per-table version every LogicalChangeEvent carries (I14).
  • GTID (Global Transaction Identifier) — MySQL's transaction-identity scheme, contrasted with this design's LSN scheme (§5 Ref-impl #2).
  • Binlog — MySQL's WAL-equivalent, in statement/row/mixed formats (§35.3).
  • CDC (Change Data Capture) — the general term for logical-replication-driven downstream consumption (Kreps 2014, §5).
  • Avro — the default logical output-plugin wire format, schema-carrying (ADR-08).
  • Snapshot (logical) — a new logical slot's consistent initial table state, streamed before change events (§16.2).
  • PITR (Point-in-Time Recovery) — replaying archived WAL to a specific LSN/time, sharing this design's slot restart_lsn as anchor (PhaseDeferred("§13.3")).
  • Checkpoint — the periodic point at which the primary consults min_restart_lsn() for WAL-truncation eligibility (§15.2).
  • ARIES — the WAL/recovery discipline (Mohan et al. 1992) this design's durability ordering (I2, I3) is built on top of.
  • Backpressure — the flow-control response to a slow consumer (rate-limiting DDL floods, §17.6; sync-ack timeout, §14.2).
  • mTLS — mutual TLS; the mandatory cross-DC transport-security mode (ADR-12).
  • CRC32C — the per-frame integrity check gating watermark advancement (I7).
  • Framing — the length-prefixed, CRC-trailed on-wire message boundary discipline (ADR-11, §8.2).
  • Batching — packing multiple WAL records into one XLogData frame to amortize codec/syscall overhead (§22.2).
  • TCP_NODELAY — the per-slot socket flag trading coalescing efficiency against latency (§22.2).
  • Split-brain — two hosts simultaneously believing themselves primary and accepting writes (T1, FM2).
  • Leader epoch — Kafka's KIP-101 term for this design's TimelineId (§5 Papers #10).
  • High watermark — the pre-KIP-101 Kafka truncation-safety mechanism that leader epochs replaced; this design's I4/history-file model is the direct descendant.
  • ISR (In-Sync Replica set) — Kafka's quorum-membership concept, analogous to this design's "eligible sync-candidate set" (§14.2, §32).
  • Log-is-the-database — the Aurora architectural pattern where replicas read a shared log directly instead of applying WAL locally (§32, §35.4).
