⬜ Phase 0 — Skeleton, Governance, "Hello, Replica" §12

Objectives

Stand up the repository (§10) and the correctness kernel — the Lsn/TimelineId arithmetic (§11.1–11.2) — and prove one end-to-end frame flows sender→receiver in-process. No real network, no real WAL yet.

Deliverable

make bootstrap && make build && make test all exit 0 on a clean checkout; the "Hello, Replica" integration test passes.

Acceptance
  • tests/hello_replica.rs: after ten XLogRecords with LSNs Lsn(1024)…Lsn(10240) are sent, the receiver's received_lsn() == Lsn(10240) — exact equality, not "close enough".
  • cargo miri test -p repl-core passes with zero UB reports (the no_std-tolerant LSN/ framing arithmetic is Miri-clean).
  • Workspace builds with zero warnings under cargo clippy --all-targets -- -D warnings.
Fixtures
Fixture Purpose Expected Output
conformance/corpora/physical_bitparity/smoke_10_records.bin ten synthetic XLogRecords, LSNs 1024..10240 step 1024 receiver reconstructs identical byte sequence
conformance/corpora/physical_bitparity/malformed_crc.bin one record with a flipped CRC bit codec rejects; received_lsn does not advance (I7)
conformance/corpora/physical_bitparity/replay_smoke.bin same ten records replayed twice (idempotency probe) second replay is a no-op; no duplicate apply
Pitfalls
  • tokio::io::duplex buffer smaller than one max-frame deadlocks the smoke test on a single large frame — size it to 8 KiB minimum for the placeholder; production uses OS socket buffers (§11.10 MAX_PAYLOAD).
  • Placeholder receiver must advance received_lsn after CRC validation, never before (I7) — getting this order wrong here seeds the same bug into every later phase.
  • cargo miri cannot execute the Tokio reactor; gate Miri to the sync, non-async repl-core crate only, or the CI job silently no-ops.

⬜ Phase 1 — Physical Replication: WAL Streaming, Restart-from-LSN §13

Objectives

Implement real physical replication: walsender/walreceiver over TCP, WAL persisted on the standby, and clean restart from a recorded LSN (P4, I1).

Deliverable

A primary and a standby on localhost, two cargo run invocations, stream 1 GiB of fabricated WAL end-to-end with zero byte loss; a killed-and-restarted standby resumes without re-fetching already-persisted WAL. PhaseDeferred("§13.3"): PITR bootstrap via archived-WAL replay reuses this slot's restart_lsn as its anchor but is not built here (Blueprint #71 territory).

Acceptance
  • Conformance bucket physical.bitparity: every byte of every WAL segment on the standby matches the primary after a 1 GiB streamed workload (fixture below).
  • Conformance bucket physical.restart: standby restart resumes from confirmed_flush_lsn with zero duplicate-applied records (I3).
  • Sustained throughput ≥ 500 MB/s single-core walsender+walreceiver on a 10 GbE link (M1, §29) — measured, not estimated.
Fixtures
Fixture Purpose Expected Output
conformance/corpora/physical_bitparity/1gib_workload.bin 1 GiB synthetic WAL stream standby WAL byte-identical to primary
conformance/corpora/physical_bitparity/restart_midstream.scenario kill standby at 512 MiB, restart resumes at last confirmed_flush_lsn; no re-fetch, no gap
conformance/corpora/physical_bitparity/segment_boundary_split.bin one record spanning two 16 MiB segments reader concatenates without byte loss
Pitfalls
  • A WAL record spanning a segment boundary must never be split across segment files — follow the Postgres convention (never split) or the reader loses bytes at every boundary (§5 Ref-impl #1).
  • Receiver must fsync local WAL before advancing flushed_lsn (I2/P3 analogue on the standby) — reversing this order means a crashed-then-restarted standby reports flushed bytes that are not on disk, and the primary may have already truncated them (I6).
  • CRC32C computed over the wrong byte range (kind||length||payload, §8.2) produces a confusing "bad checksum" error with no indication of which field misaligned — the byte range is normative in repl-core/src/frame.rs and must not be reinvented per call site.

⬜ Phase 2 — Synchronous Replication and Quorum Acknowledgement §14

Objectives

Implement SyncReceive, SyncReplay, and Quorum(n) modes (§11.4) on top of Phase 1's streaming path — the primary's commit path blocks per P2/ADR-04/ADR-05/ADR-06.

Deliverable

A SyncReceive-mode primary with one standby blocks each commit until that standby acks received_lsn ≥ commit_lsn; a Quorum(2)-mode primary with three standbys acks once any two catch up, with the third's lag reported but non-blocking.

Acceptance
  • Conformance bucket sync.latency_p99: same-DC, 1 KiB commits, p99 ≤ 5 ms (M4, §29).
  • Conformance bucket quorum.tolerate_minority: 3-standby quorum, one down, primary continues acking commits.
  • Conformance bucket quorum.block_on_majority_loss: 3-standby quorum, two down, primary blocks (never silently degrades) — asserted by a 10 s no-progress check.
Fixtures
Fixture Purpose Expected Output
conformance/corpora/sync_latency/1kib_commits_same_dc.workload 10K commits, 1 KiB payload, same-DC RTT p50 ≤ 1.5 ms, p99 ≤ 5 ms
conformance/corpora/quorum_failure/one_of_three_down.scenario kill one of three sync candidates primary continues acking within 1 commit-latency of baseline
conformance/corpora/quorum_failure/two_of_three_down.scenario kill two of three primary blocks; SyncDegraded never fires unless opted in
Pitfalls
  • Waking commit-waiters in arrival order instead of commit_lsn order is harmless functionally but produces a confusing out-of-order ack log — use a BTreeMap keyed by commit_lsn.
  • The single worst foot-gun in this stack: a coordinator that returns success from wait_for_commit based on the primary's own flushed_lsn rather than any standby's — test the full wire path with a real, pausable standby, never a mock coordinator.
  • An eligible-sync-candidate set that is not persisted loses "who was a sync candidate" information across a primary crash — a slot that was sync-eligible before the crash must remain so after, or the durability guarantee silently narrows.

⬜ Phase 3 — Replication Slots: Persistence, Advance, Timeout §15

Objectives

Implement the slot lifecycle (§8's create/advance/drop/timeout) as the durability contract gating WAL truncation (P8, I5, I6). PhaseDeferred("§15.1"): a paused-slot time-travel query surface is a natural extension of this lifecycle but is not built in this phase.

Deliverable

CREATE_REPLICATION_SLOT, DROP_REPLICATION_SLOT, ADVANCE_REPLICATION_SLOT work end-to-end; WAL truncation correctly respects min_restart_lsn; a slot survives a primary process restart with confirmed_flush_lsn intact.

Acceptance
  • Conformance bucket slot.lifecycle: create→advance→drop→timeout transitions all pass; persistence survives a simulated primary restart.
  • Conformance bucket slot.wal_truncation_gating: segments below min_restart_lsn are truncated; segments at or above are retained — verified by direct segment-file inspection, not just by absence of errors.
  • A slot abandoned for the configured timeout emits exactly one SlotStale event (not a flood) within 60 s of the threshold crossing.
Fixtures
Fixture Purpose Expected Output
conformance/corpora/slot.lifecycle/create_advance_drop.scenario full lifecycle exercised all transitions succeed; final list() is empty
conformance/corpora/slot.lifecycle/crash_during_rename.scenario kill process mid atomic-rename on restart, slot file is either fully old or fully new — never torn
conformance/corpora/slot.wal_truncation_gating/one_slow_one_fast.scenario two slots, one lagging only segments below the lagging slot's restart_lsn retained
Pitfalls
  • Atomic rename requires fsyncing the parent directory, not just the renamed file, on Linux — skipping it risks losing the rename across a crash between the rename syscall and the directory-metadata write reaching disk.
  • A slot recording restart_lsn > confirmed_flush_lsn is corrupt by construction (I5) — validate on every write, not just on read, or the corruption compounds silently.
  • The default 24 h timeout (ADR-18) is a policy default, not a universal constant — busy primaries routinely set 1 h; backup-only slots routinely set 7 d. Ship the default as visibly overridable, not hardcoded.

⬜ Phase 4 — Logical Decoding: Reorder Buffer, Output Plugins §16

Objectives

Implement the logical-decode pipeline (§8.8): WAL → decoder → reorder buffer → output plugin → consumer, emitting Begin/Insert/Update/Delete/Commit per transaction in commit order (I3).

Deliverable

A logical slot streams Begin/Insert/Update/Delete/Commit events for primary transactions; a new slot's snapshot plus subsequent change-event stream reconstructs the primary's row state on the consumer exactly.

Acceptance
  • Conformance bucket logical.rowequiv: after a 1-billion-row replay, every row and column on the consumer matches the primary exactly (fixture below).
  • Conformance bucket logical.throughput: ≥ 50K rows/sec single-core decoder + Avro output (M2, §29).
  • Aborted-transaction events never reach the output plugin — asserted by a negative-case fixture, zero tolerance (I8).
Fixtures
Fixture Purpose Expected Output
conformance/corpora/logical_rowequiv/1b_row_replay.workload 1B-row primary workload consumer row state byte-for-byte column-equal to primary
conformance/corpora/logical_rowequiv/aborted_txn_leak.scenario transaction with 10K ops then abort zero events emitted for that xid (I8)
conformance/corpora/logical_rowequiv/snapshot_then_stream.scenario new slot creation mid-workload snapshot + stream reconstructs state with no gap/overlap
Pitfalls
  • A reorder buffer that leaks aborted-transaction events is the single worst correctness bug in the logical pipeline — it looks like a performance optimization ("why buffer at all") but is silently shipping pre-commit data downstream (I8).
  • The relation/type-change (RMID_RELATION) records must be consumed strictly before any RMID_HEAP/RMID_HEAP2 record that references the new tuple shape, or the schema tracker (Phase 5, §17) is stale by exactly one record.
  • Skipping the disk-spill path "because deployments are small" is how a single forgotten BEGIN without COMMIT OOMs a primary — the spill is not an optional feature, it is the OOM mitigation (§4 reorder-buffer memory cap).

⬜ Phase 5 — Schema Awareness and DDL Handling §17

Objectives

Make logical replication schema-safe: track schema versions per table, enforce deny-by-default DDL policy (P6, ADR-09, I9, I14).

Deliverable

SchemaChange::AddColumn under AllowAdditive flows to the consumer as a Schema event with the new column visible in subsequent row events; SchemaChange::DropColumn under the same policy aborts the slot with an actionable error naming the offending DDL.

Acceptance
  • Conformance bucket schema.evolution: AddColumn flows through; new events carry the incremented schema_version; a consumer holding the prior version can still decode in-flight events tagged with it.
  • Conformance bucket schema.deny_destructive: DropColumn under AllowAdditive aborts the slot within one WAL record of the DDL, with a named error (SchemaError:: DeniedChange { table, change }), not a generic failure.
  • Zero silent schema-drift events across 10K synthetic DDL operations in the conformance suite (I9, hard zero-tolerance count).
Fixtures
Fixture Purpose Expected Output
conformance/corpora/schema/add_column_additive.scenario AddColumn under AllowAdditive new column visible; version incremented; no slot error
conformance/corpora/schema/drop_column_additive.scenario DropColumn under AllowAdditive slot aborts with SchemaError::DeniedChange
conformance/corpora/schema/lagging_consumer_old_version.scenario consumer reads events tagged with N-1 version after a DDL correct decode via schema history, not the current schema
Pitfalls
  • A primary ALTER TABLE that policy denies wedges the slot — this is by design (I9), but the operator runbook (docs/runbooks/uncontrolled-failover.md sibling, slot-disk-full.md's DDL-triage section) must make the unwedge path (change policy, or drop/recreate the slot) obvious, or "safe by default" reads as "broken." PhaseDeferred("§17.6") online DDL is the longer-term fix for this friction.
  • A schema change requiring a backfill (ADD COLUMN ... DEFAULT <value> on an engine that rewrites) floods the slot with UPDATE events — the consumer must tolerate a sustained burst, and the rate-limit knob on the publication is the mitigation, not a workaround.
  • Rate-limiting DDL-triggered event floods without rate-limiting normal row events requires the two to be classified separately in the publication's flow-control path — conflating them throttles legitimate traffic during a schema migration.

⬜ Phase 6 — Failover: Controlled Handover and Uncontrolled Promotion §18

Objectives

Implement the two failover paths (§3 failover plane): controlled handover (zero data loss, planned) and uncontrolled promotion (bounded loss, unplanned) — both operator-driven per P10/ADR-14, both requiring fencing before write-acceptance (I15).

Deliverable

A controlled handover from primary A to standby B preserves every committed write; B's flush_lsn at handover time equals A's; clients repoint without a gap. An uncontrolled promotion of standby B after A's simulated host loss completes and opens writes within the RTO budget, with the fork LSN durably recorded before any write is accepted (I10).

Acceptance
  • Conformance bucket failover.controlled: zero committed writes lost, verified by comparing A's pre-handover commit log against B's post-handover state.
  • Conformance bucket failover.uncontrolled: RTO ≤ 30 s (M8, §29); history file written and fsynced strictly before the promoted replica's first accepted write (I10, timestamp- ordered assertion in the fixture).
  • Jepsen scenario split_brain_prevention: 1000 runs, 0 observed split-brain writes (M14, §29; I15).
Fixtures
Fixture Purpose Expected Output
conformance/corpora/failover/controlled_handover_a_to_b.scenario planned handover under load zero writes lost; clean timeline bump; client repoint succeeds
conformance/corpora/failover/uncontrolled_host_loss.scenario kill primary, promote standby RTO ≤ 30 s; history entry fsynced before first accepted write
jepsen-harness/scenarios/split_brain_prevention.clj network partition + promote + heal old primary never accepts a write after fencing completes
Pitfalls
  • Promotion without fencing is the textbook split-brain: A is partitioned, B is promoted, the partition heals, A's clients are still writing to A — both diverge, reconciliation becomes a manual merge. Fencing is structurally required (I15), never skippable.
  • A controlled handover that bumps the timeline before every sync standby (not just the new primary) has confirmed final_lsn produces a divergence on the lagging standby — wait for all of them, not just the promoted one.
  • Opening writes before the history file is fsynced (violating I10) loses the fork LSN on a crash immediately after promotion — the write-acceptance step must be strictly sequenced after the fsync, never reordered "for latency."

⬜ Phase 7 — Timeline Forks: Detection and Reconciliation §19

Objectives

Detect and safely reconcile the divergence an uncontrolled promotion (§18) can create (P11, P5, I4, I10, I11) — this phase is what makes Phase 6's promotion safe, not just fast.

Deliverable

A rejoining old primary whose timeline diverged from the cluster's is flagged by the detector before it can rejoin as a standby; an operator-acknowledged rebase completes and the rejoined host streams cleanly from the fork point forward.

Acceptance
  • Conformance bucket divergence.detect: 100% detection rate across synthetic fork scenarios including the "demoted-then-rejoining-later" multi-timeline case (§19.6).
  • Conformance bucket divergence.reconcile: rebase preserves the lost range as a .lost.timeline.N file (verified present on disk, not merely "no error"); rebase refuses to proceed without a matching --acknowledge-loss byte count.
  • Zero auto-rebases across the entire conformance suite — every rebase in every fixture requires the explicit operator step.
Fixtures
Fixture Purpose Expected Output
conformance/corpora/divergence/simple_fork.scenario one uncontrolled promotion, old primary rejoins detector flags fork at correct fork_lsn
conformance/corpora/divergence/multi_timeline_rejoin.scenario host demoted on timeline 2, rejoins on timeline 3 cluster detector walks full timeline set, still flags divergence
conformance/corpora/divergence/reconcile_wrong_ack.scenario operator supplies a mismatched --acknowledge-loss byte count rebase refused; no data destroyed
Pitfalls
  • A detector comparing only the latest timeline ID misses the "briefly-primary-then- demoted-then-rejoining" case entirely — walk the full set of timelines in the history file, not just its head (I4, I11).
  • Deleting lost-range WAL before an operator has read the divergence report destroys forensic evidence and hides the data-loss magnitude — always rename, never delete (P11).
  • The .history file format must remain backward-readable across library versions — an old primary rejoining a cluster on a newer library version must still parse the current format; version the format explicitly and default-fill any newly-added field.

⬜ Phase 8 — Cascading Replicas and Read Scaling §20

Objectives

Implement multi-hop replication (primary → standby → standby) for read scaling with additive-lag accounting (P9, ADR-19), within the depth-4 default cap.

Deliverable

A depth-3 cascading topology (primary → A → B → C) streams a 1 GiB workload with cumulative replay lag under the target bound; replctl cascade repoint <new_upstream> repoints a cascading replica without data loss when its upstream is lost.

Acceptance
  • Conformance bucket physical.cascade_depth3: tail standby's replay_lsn matches the head primary's flush_lsn within 5 s cumulative lag (M10, §29).
  • repoint() completes with zero duplicate-applied records and zero gap in the repointed replica's WAL (I3-consistent).
  • A cascading-slot creation request beyond the configured depth cap is rejected with SlotError-adjacent named error, not silently truncated to the cap.
Fixtures
Fixture Purpose Expected Output
conformance/corpora/physical_bitparity/cascade_depth3_1gib.workload 3-hop cascade, 1 GiB primary workload tail lag ≤ 5 s cumulative
conformance/corpora/physical_bitparity/cascade_repoint.scenario mid-stream upstream loss, repoint to new upstream zero duplicate apply, zero gap
conformance/corpora/physical_bitparity/cascade_depth_exceeded.scenario attempt depth-5 slot creation creation rejected with named error
Pitfalls
  • A cascading replica catching from a forked timeline (its immediate upstream lost an uncontrolled promotion) inherits the divergence silently unless the detector runs at every hop, not just at direct-primary connections (I11, §19.9).
  • A cascading replica's confirmed_flush_lsn advances relative to its immediate upstream, not the primary — an operator reading only the primary's slot list under-counts the true chain depth's lag; traversing the full chain is required for an accurate picture.
  • Read-after-write against a cascading replica is lag-bound consistent (ADR-16) against the cumulative chain lag, not just the last hop's — document this explicitly or application authors will underestimate staleness by 2–3x on a depth-3 chain.

⬜ Phase 9 — Lag Monitoring and Alerting Hooks §21

Objectives

Implement the four-point lag surface (send/receive/flush/replay, P12) with pluggable alerting, closing the "40-minute unnoticed lag" failure class.

Deliverable

replctl status prints all four lag numbers (bytes and duration) for every standby; LagAlertSink::on_lag_exceeded fires within 1 s of a configured threshold breach.

Acceptance
  • Conformance bucket lag.accuracy: reported lag within 5% of a synthetic 100 MB/s–1 GB/s workload's ground truth (M13-adjacent, §29).
  • Conformance bucket lag.alert_on_replay: alert fires within 1 s of a replay_lag threshold breach — timestamp-ordered assertion in the fixture, not "eventually." Alert fires on flush_lag breach for RPO-relevant SLAs distinctly from replay_lag for staleness SLAs — the two must be independently configurable thresholds.
Fixtures
Fixture Purpose Expected Output
conformance/corpora/lag/synthetic_100mb_1gb.workload ramped write-rate workload reported lag within 5% of ground truth at every rate step
conformance/corpora/lag/replay_threshold_breach.scenario injected apply-side stall alert fires within 1 s of crossing configured threshold
conformance/corpora/lag/stale_keepalive.scenario keepalive gap > 30 s lag reading flagged stale, not silently understated
Pitfalls
  • Reporting only receive_lag (near-zero because TCP kept up) while replay_lag grows unbounded is exactly the bug that let a 40-minute lag go unnoticed in the field — report all four, always (P12).
  • On a low-write-rate workload, lag duration looks artificially good (no WAL to replay); alerting must combine bytes and duration in one rule, or a standby stalled for 10 s on a 1 KB/s workload reads as "fine."
  • A standby computing lag against a stale primary.flush_lsn baseline (missed keepalives) silently under-reports its own staleness — treat a keepalive gap as a first-class alert condition, not a quiet fallback to the last-known value.

⬜ Phase 10 — Performance Hardening §22

Objectives

Reach the throughput targets (M1, M2, §29) via parallel apply, batching, compression, and network tuning — the only phase whose objective is a number, not a new capability.

Deliverable

Physical throughput ≥ 500 MB/s on a 10 GbE link (single-core walsender+walreceiver); logical throughput ≥ 50K rows/sec (single-core decoder + Avro); sync-ack p99 ≤ 5 ms same-DC — all measured on the conformance/benchmark harness, not projected.

Acceptance
  • Conformance bucket perf.physical_throughput: ≥ 500 MB/s sustained over a 10-minute run (M1, §29).
  • Conformance bucket perf.logical_throughput: ≥ 50K rows/sec sustained (M2, §29).
  • Parallel apply preserves I3 (apply order = commit order) under a 1000-transaction concurrent-conflict stress fixture — zero ordering violations, not "rare."
Fixtures
Fixture Purpose Expected Output
conformance/corpora/perf/physical_throughput_10gbe.bench sustained 10 GbE workload, 10 min ≥ 500 MB/s throughput, p99 sync-ack ≤ 5 ms
conformance/corpora/perf/logical_throughput_avro.bench single-core decode + Avro emit ≥ 50K rows/sec
conformance/corpora/perf/parallel_apply_conflict_stress.scenario 1000 concurrent conflicting/non-conflicting txns zero I3 ordering violations
Pitfalls
  • Parallel apply that does not respect commit ordering produces a non-existent intermediate state visible to a concurrent reader on the replica — group by commit, parallelize within a commit's non-conflicting records, preserve order across commits, never the reverse.
  • Compressing already-compressed payloads (TOAST'd values, binary blobs) inflates rather than shrinks — the entropy-estimation skip is not an optimization, it is a correctness- adjacent efficiency fix (uncompressed-but-marked-compressed frames would corrupt the decoder if the skip logic and the frame header disagree).
  • A batch timer that delays a transaction's last record to fill a byte threshold directly extends that transaction's sync-ack latency — the timer must always flush on a commit-record boundary regardless of accumulated byte count.
