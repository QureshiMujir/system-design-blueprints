In one paragraph

A replication protocol keeps copies of a database's write history on other machines, so that reads can be spread out, a copy can take over when the main machine dies, and changes can be fed to other systems. This design is a Rust library, not a managed service. It ships the write-ahead log (WAL) as raw bytes (physical replication) or as decoded row changes (logical replication), with asynchronous, synchronous and quorum acknowledgement, replication slots, cascading replicas, failover primitives, fork detection and four-point lag monitoring (§1). Database-engine builders, SRE teams and change-data-capture (CDC) pipeline builders run it, using the replctl operator CLI (§1). It is the transport, slot and failover-primitive layer, not a consensus layer (§1, ADR-14).

The problem, concretely

A read replica scaling a service to 10K QPS, a cross-region DR topology and a CDC pipeline feeding a warehouse are all replication consumers (§2). The blueprint's opening premise is that every real system picks a point on three axes: what unit replicates (bytes or rows), when the primary acknowledges (before or after a replica confirms), and who picks the new primary (an operator or a consensus protocol) (§2).

Each axis has a trap. Bytes are fast and exact but brittle across major-version and cross-engine boundaries, and heterogeneous sinks need logical replication (§2, P1). Rows are roughly 10x slower, with a long tail of correctness pitfalls such as DDL and cross-table ordering (§2). In async mode the primary does not wait, so a fault can lose up to flush_lag bytes (§4, MM3). Promote a replica without making sure the old primary stopped, and both accept writes: split-brain (P10, T1). The 3 a.m. incidents the blueprint wants you to diagnose by name are a standby 40 minutes behind, a logical consumer silently skipping rows, a promoted replica whose old primary's clients are still writing, and an unnoticed timeline fork (§2).

How it works, end to end

Follow one committed write through §3's boxes. The blueprint does not invent its own WAL or storage engine: the transaction manager is Blueprint #43 and the WAL writer is Blueprint #69 (§3, ADR-03).

 Txn mgr (#43) -> WAL writer (#69) -> WAL segment files (16 MiB)      flush_lsn advances
        +-> walsender A (physical, sync candidate) --\
        +-> walsender B (physical, cascading) -------+--> repl-net: TLS, zstd, framing
        +-> logical decoder + output plugin ---------/
 Failover plane: controller / handover / promote / fence / reconcile
 Standby A (sync): walreceiver -> apply -> StandbyStatusUpdate     Standby B (async) -> Standby C
 CDC consumer (Kafka / search / warehouse): acks its confirmed LSN
  1. Commit on the primary. The WAL record is fsynced locally first, and only then can any replication acknowledgement matter (I2, P3, §8.5).
  2. walsender. It moves IDLE to STARTED when a client connects and the slot exists, then to STREAMING on START_REPLICATION SLOT <name> <kind> <lsn>, sending XLogData when WAL is available and KeepAlive when the keepalive interval passes with no data (§8.4). Its code lives in repl-physical (§1).
  3. Wire. repl-net (Tokio, rustls, zstd) carries length-prefixed frames with a CRC32C trailer (§1, §8.2, P14). The receiver checks the CRC before moving received_lsn (I7).
  4. walreceiver and apply. The standby persists WAL, advances received_lsn, then flushed_lsn after its own fsync, and a separate WalApplier advances replay_lsn (§13.2, I3). It sends all three upstream in StandbyStatusUpdate (§11.5). The restart point is stated two ways. §8.7 says a crashed walreceiver resumes from its own last-fsynced flushed_lsn and reconnects with START_REPLICATION SLOT <name> PHYSICAL <flushed_lsn>, and §13.2 says to read the slot's confirmed_flush_lsn "or the local WAL tail if higher". §13.4 and §13.5 say the restart resumes from confirmed_flush_lsn (§8.7, §13.2, §13.4, §13.5).
  5. Slot. Each status update triggers a slot advance() (§8.4). repl-slot persists slots so the primary does not truncate WAL ahead of a slow consumer (§1, I6).
  6. Logical branch. repl-logical runs decoder, reorder buffer, then output plugin, then the consumer (§8.8, §1). The consumer acks a confirmed LSN (§3).
  7. Failover plane. repl-failover offers controlled_handover() and promote(), and repl-divergence detects forks on rejoin (§1, §18.2, §19.2). repl-cli (replctl) drives slot, failover, divergence and status commands (§1).

A cascading standby is a walsender to its own downstream, using the same protocol, so a cascading replica cannot tell it is not talking to the primary (§3 property 2, §20.2). Module count: §1 lists eight numbered Phase-0 modules, while §12.2 and Appendix A say the workspace has "eleven crates". The §10 tree and Appendix A's table name ten: the eight plus repl-fuzz and repl-bench (§1, §10, §12.2, §38).

The core ideas

A replica is a fold over a log, and the LSN is its clock (MM1, MM2, §8.1)

A log sequence number (LSN) is a 64-bit byte offset into a timeline's WAL, and it orders every event (§37, I1). MM1 says a replica is state = fold(apply, initial_state, wal_records): any two consumers holding the same prefix hold the same state. Progress is measured at four points: what the walsender sent, and what the standby received, flushed to disk and replayed (§11.5, §21.2).

The tiny example is the Phase-0 smoke test. Ten records have LSNs 1024, 2048, up to 10240; after they are sent, the receiver's received_lsn must equal 10240 exactly (§12.4). The corrupt-record fixture shows the rule: a record with a flipped CRC bit is rejected and received_lsn does not advance (I7, §12). A frame claiming a length above the 16 MiB maximum is rejected before any allocation (§8.6, T7). The laws on top: an LSN never decreases (I1), a cascading replica's received_lsn never exceeds its upstream's flush_lsn (I13), and apply order equals commit order (I3).

Acknowledgement modes: which racer must finish first (§11.4, §14, MM3)

ReplicationMode has four values (§11.4):

Mode Primary waits until Strength
Async nothing default (ADR-04)
SyncReceive standby received_lsn >= commit_lsn weaker
SyncReplay standby replay_lsn >= commit_lsn strictly stronger (§8.9)
Quorum(n) n acks, default floor(n/2)+1 (P13) survives minority loss

The three-step trace for a sync commit, from §8.5: (1) the primary fsyncs the commit record, so flush_lsn = L; (2) SyncCoordinator parks the commit and the walsender ships XLogData up to L; (3) the standby applies and fsyncs, replies with StandbyStatusUpdate carrying flushed_lsn = L, and the coordinator wakes the waiter and acks the client (§8.5, §14.2).

MM3 frames durability as two races, local fsync and replication ack, and an RPO number means nothing unless you say which mode was running (MM3). The majority formula: for n = 3, 5, 7 candidates the threshold is 2, 3, 4 (§33 item 7). There n counts sync candidates, not all nodes; ADR-06 rejects a majority "of all nodes incl. non-voters". How many failures that survives is stated two ways: P13 says the quorum and sync defaults "both survive exactly one host failure", while §33 item 7 says each n tolerates exactly ⌈n/2⌉ − 1 standby failures, which is 2 for n = 5 and 3 for n = 7 (P13, §33 item 7). If the wait times out (default 30 s), the system emits SyncDegraded and does not fall back to async unless degrade_on_timeout=true was set explicitly (§14.2, I12).

Slots: a promise, not a cursor (MM4, §11.3, §15)

A replication slot records restart_lsn (the primary will not truncate WAL before it) and confirmed_flush_lsn (the consumer's durable position) (§11.3). MM4's point: a cursor remembers a position, a slot obliges the primary to keep serving from it, so every "why did WAL grow forever" incident is a promise nobody redeems (MM4).

Toy rules (§15.2): on each truncation decision compute min_restart_lsn(), the minimum restart_lsn over active slots; a segment whose end LSN is below it may go, nothing else (I6). Every advance() checks restart_lsn <= confirmed_flush_lsn and a violation marks the slot Corrupt (I5). A slot file is written by atomic rename plus fsync of file and parent directory (ADR-07, §15.2). The library never auto-drops a slot; after the timeout (default 24 h since last advance) it emits SlotStale and waits for an operator (ADR-18, P8, §15.2). The cost of one lagging slot is on the numbers page: 300 GB for 10 minutes at 500 MB/s (§33 item 11).

Logical decoding: group by transaction, emit in commit order (§8.8, §16, P6)

Logical replication turns WAL bytes into row events (logical decoding). The pipeline is decoder, reorder buffer, output plugin, consumer (§8.8). Records are dispatched by rmid: heap records become row operations buffered per xid, a commit record drains that transaction's buffer in commit order, and an abort drops it entirely, because emitting aborted data is a correctness violation, not a performance issue (§16.2, I8). Past 256 MiB per slot the buffer spills to disk, since a long uncommitted transaction is otherwise an out-of-memory vector (§4, §16.2, T6). A new logical slot takes a snapshot at its confirmed_flush_lsn then streams changes, so the consumer sees neither gap nor overlap (§16.2).

DDL is a first-class event (P6). Every event carries the schema_version it was produced under (I14). With the default AllowAdditive policy an AddColumn flows through as a Schema event and later row events show the column; a DropColumn aborts the slot with a named error (ADR-09, §17.3, §17.4, I9). MM6 calls the decoder a lossy compiler from bytes to intent, with DDL changing the language mid-compilation (MM6).

Failover: fence first, bump the timeline, record the fork (§18, §19, MM5, MM7)

A timeline is a version number for history: it tells you whether two hosts even share the same sequence of WAL records, a question that comes before comparing LSNs (MM5). The 4-byte TimelineId never decreases, and every uncontrolled promotion bumps it (I4, ADR-10).

Two paths (§18.2). Controlled handover: stop the old primary accepting writes, flush to final_lsn, have every standby confirm flushed_lsn == final_lsn, bump the timeline on all hosts, repoint clients. Everyone converges on one LSN first, so no divergence is possible. Uncontrolled promote(): (1) require a Fence, enforced by the function signature (I15); (2) the promoted replica's received_lsn becomes the fork point and the timeline bumps; (3) write and fsync the history entry before accepting any write (I10).

Fencing is mutual exclusion for a whole host, and promotion without it is the "two holders of one lock" bug at cluster scale (MM7). On rejoin, detect_divergence() runs on every reconnect, cascading hops included (I11), and walks the full set of timelines in the host's history file, not only the latest, to catch a host that was briefly primary and then demoted (§19.2, §19.6). A rebase renames the lost WAL to <segment>.lost.timeline.N and needs --acknowledge-loss <bytes> matching the reported size (§19.2, T12).

Lag is four numbers, measured against a moving target (P12, §21, MM8)

Each is computed against the primary's flush_lsn: send_lag = flush_lsn - last_sent_lsn, receive_lag = flush_lsn - received_lsn, flush_lag = flush_lsn - flushed_lsn, and replay_lag = flush_lsn - replay_lsn (§21.2, §37). Each is computed independently, never derived from another (§21.2). Flush lag is the RPO-exposure number and replay lag the read-staleness number (§37). MM8 adds that lag is a rate comparison: a replica "100 MB behind" may be catching up or falling behind (MM8). Cascading lag is the sum of every hop (P9).

The trade-offs — where engineers disagree

Default replication mode: async (ADR-04)

Chosen: async by default, with sync and quorum as explicit opt-ins (ADR-04, P2). Rejected: sync, semi-sync or quorum as the default. When the rejected choice is right: sync-by-default wins for a financial ledger where every read-replica query must reflect the last commit. Cost of the choice: async RPO is bounded only by flush_lag bytes at fault time (§4).

Who decides to fail over: the operator (ADR-14)

Chosen: operator-driven; the library ships handover() and promote() as primitives, not the policy (ADR-14, P10). Rejected: fully automatic failover with built-in leader election. When the rejected choice is right: automatic wins once a real consensus layer (Blueprint #93 or #37) sits above this library. The reason for the choice is that auto-failover without consensus is split-brain bait (ADR-14).

Divergence after promotion: detect and flag (ADR-15)

Chosen: detect and flag, then reconcile manually (ADR-15, P11). Rejected: auto-rebase or silently discard. When the rejected choice is right: auto-rebase wins in a disposable-replica fleet, such as a stateless read cache, where lost writes are irrelevant by design. The chosen path refuses rejoin until the operator acknowledges the loss (P11, §19.2).

DDL policy: deny by default (ADR-09)

Chosen: AllowAdditive as default; unhandled DDL aborts the slot (ADR-09, I9). Rejected: silent skip, or AllowAll as the default. When the rejected choice is right: AllowAll wins when every downstream consumer is known to handle arbitrary schema drift (rare; internal tooling only). The blueprint calls silent DDL skip the number-one logical-replication corruption bug (ADR-09).

Slot timeout: 24 hours, never silent drop (ADR-18)

Chosen: configurable, default 24 h since last advance (ADR-18). Rejected: no timeout, or a fixed 1 h. When the rejected choice is right: the fixed 1 h wins on a high-write-rate primary where 24 h of backlog would exhaust disk (§33 item 4). The tension is explicit: 24 h balances catching a stuck consumer against wedging a brief maintenance window (ADR-18).

Standby reads: lag-bound, not linearizable (ADR-16)

Chosen: lag-bound consistency, replay_lag <= L_max (ADR-16, §8.9). Rejected: strict serializable reads on replicas. When the rejected choice is right: strict wins when the application cannot tolerate any staleness, and the blueprint's answer is to route those reads to the primary instead (ADR-16). Strict reads would need a consensus read-index, out of scope here (ADR-16).

Roads not taken

Multi-primary (active-active) (§35.1): two primaries replicate to each other with conflict resolution (last-write-wins, vector clocks or CRDTs). It wins for multi-region write locality where single-leader write latency is unacceptable and the application can tolerate or resolve conflicts (MySQL Group Replication, Galera). It is rejected because I1 through I15 assume a single writer per timeline, and conflict resolution belongs to Blueprint #99 (§35.1, §36).

Raft/Paxos replicated log (§35.2): commit only after a quorum ack, with leader election built in. It wins where automatic election and split-brain-by-construction are worth a quorum round trip per entry (etcd/raft, CockroachDB). It is rejected here because it is a separate, substantial system (Blueprints #93, #37) that this transport is meant to compose underneath (§35.2, ADR-14).

Statement-based logical replication (§35.3): ship the SQL statement, not the resulting rows. It wins when statements are small relative to the rows they touch, such as a bulk UPDATE of a million rows (historical MySQL default). It is rejected because replay must be deterministic (no NOW(), no auto-increment divergence), whereas row events ship the already-resolved result (§35.3).

Shared log, log-is-the-database (§35.4): replicas read one shared durable log and never apply to a local page cache. It wins in disaggregated-storage clouds where per-replica apply CPU is the bottleneck (Amazon Aurora). It is rejected as a default because this is a portable, storage-agnostic library and a shared log service is an infrastructure dependency; it is deferred (ADR-25, §36).

What must never be false

  • I1: an LSN never decreases for any consumer of a timeline. Noticed by an assert on every advance(); repl_lsn_regression_total.
  • I2: the primary's WAL fsync precedes its own commit ack. A commit-path unit test asserts the order; repl_commit_fsync_order_violation should be 0.
  • I3: apply order equals commit order. Conformance logical.rowequiv and physical.bitparity; repl_apply_out_of_order_total.
  • I4: TimelineId never decreases and every uncontrolled promotion bumps it. The divergence detector on every reconnect; repl_timeline_bump_total, repl_divergence_detected_total.
  • I5: restart_lsn <= confirmed_flush_lsn for every slot. Validated on every advance; repl_slot_invariant_violation_total.
  • I6: no WAL truncation below the minimum restart_lsn of active slots. Conformance slot.wal_truncation_gating; repl_wal_truncate_blocked_total.
  • I7: frame CRC32C is validated before any watermark advances. Per-frame check; repl_frame_crc_failure_total.
  • I8: the reorder buffer never emits events for an aborted transaction. Negative-case fixture; repl_aborted_txn_leak_total should be 0.
  • I9: DDL on a published table with no matching handler aborts the slot. The slot enters Errored; repl_slot_ddl_abort_total.
  • I10: the history file's fork LSN is fsynced before a promoted replica accepts writes. Conformance failover.uncontrolled; repl_history_write_before_accept_ms.
  • I11: divergence detection runs on every reconnect, cascading hops included. Conformance divergence.detect; repl_divergence_check_total.
  • I12: sync or quorum ack never silently degrades to async. A SyncDegraded event fires; repl_sync_degraded_total.
  • I13: a cascading replica's received_lsn never exceeds its upstream's flush_lsn. Same check as I1, applied per hop; repl_lsn_regression_total tagged by hop.
  • I14: every LogicalChangeEvent carries the schema_version it was produced under. Conformance schema.evolution; repl_schema_version_mismatch_total.
  • I15: fencing completes before a promoted replica accepts writes. The Jepsen split_brain_prevention scenario; repl_promote_without_fence_total should be 0.

Two are enforced by construction: I15 by the signature of promote(), and I7 by the codec for every caller (§23 structural defenses, I15, I7).

What breaks in production

The blueprint's failure-mode table lists 12; these are the most instructive (§24). Its header has seven column names, and so does the FM1 row, but FM2 to FM12 carry eight cells, so their labels shift by one; each entry below follows the row's own content.

  • FM-1: advertised sync, actually async. Symptom: commits ack with no standby having the data. Root cause: the commit path acks based on the primary's own flushed_lsn. Detection: a wire-path conformance test against a real, pausable standby (§14.5, §14.6). Recovery: fix, redeploy, then audit every commit acked in the defect window against standby ack timestamps.
  • FM-2: split-brain writes. Root cause: promotion without completed fencing, via partition plus operator error or a missing fence integration. Detection: the Jepsen scenario, and the divergence detector on rejoin. Recovery: none automatic, by design (P11); an operator-acknowledged rebase, with lost data kept in .lost.timeline.N files that are renamed, never deleted.
  • FM-3: silent timeline fork. Root cause: a code defect that skips the timeline bump (I4). Detection: conformance divergence.detect. Recovery: fix the code, then rebase affected hosts one by one. Forensics: history-file gap analysis.
  • FM-4: slot-driven disk exhaustion. Root cause: an abandoned consumer never advances its slot. Detection: the SlotStale event plus a disk-usage alert. Recovery: none automatic (P8); triage via docs/runbooks/slot-disk-full.md. Forensics: the slot's last_advance_at timestamp.
  • FM-5: unbounded replica lag. Root cause: apply slower than the primary's sustained write rate, such as undersized hardware or the single-threaded apply bottleneck before Phase 10. Detection: a replay_lag alert. Recovery: the slow-replica runbook (parallel apply, hardware, or lower write rate).
  • FM-9: WAL truncated ahead of an active slot. Root cause: min_restart_lsn() bypassed or miscomputed (an I6 violation). Detection: conformance slot.wal_truncation_gating. Recovery: mark the slot Corrupt and re-bootstrap the consumer from a snapshot.
  • FM-10: cascading lag blind spot. Root cause: the operator watches only direct standbys, a dashboard gap and not a code defect. Detection: review of per-hop lag telemetry. Recovery: fix dashboards and alert rules; no data-plane action. Forensics: repl_cascade_hop_lag_seconds history.

Threats worth knowing (§23): T1 split-brain from a partitioned old primary, answered by fence-before-write (I15); T2 disk exhaustion via an abandoned slot, answered by the slot timeout with no silent drop (ADR-18, P8); T3 tampering with frames on an untrusted network, where mTLS catches active tampering and the CRC catches corruption (ADR-12, I7); T8 a forked timeline spreading silently through a cascade, answered by the detector at every hop (I11); T12 an operator-triggered data-destroying rebase, answered by requiring a matching byte count (§19.2).

How it compares

  • PostgreSQL made physical streaming and logical decoding both first-class from one WAL, at the cost of two decode paths against one format (§32). This design copies that, because logical-only or physical-only fails either the HA or the CDC use case (P1, §32).
  • MySQL let the row-based binlog double as the logical channel, trading a cleaner separation of "what happened" from "what changed" for one wire format. That is simpler when one format for HA and CDC is easier to operate than two (§32).
  • Raft-replicated log (etcd/raft) removes forks by construction, since commitment requires a quorum, and has leader election built in (§32). It fits when automatic election and split-brain-by-construction are worth a quorum round trip per entry; this design defers that to Blueprints #93 and #37 (§32, §35.2).
  • Chain replication gets strong consistency with cheap tail reads and simple reconfiguration, but write latency grows with chain length (§32). It fits a small, low-churn cluster where strong reads matter more than write latency.
  • Amazon Aurora has replicas read a shared log-structured store, so there is no per-replica apply step (§32). It fits where storage-compute disaggregation is available and apply CPU is the bottleneck that this design's Phase 10 fights (§32, §22).
  • Kafka (ISR) generalises fork detection into leader epochs, the direct ancestor of I4 per KIP-101, and treats replication as an ordered partitioned log from the start (§32). It fits when the replicated unit is naturally an append-only event stream, not a mutable-row database.

Questions to test yourself

  1. Why is "synchronous replication" in this design not the same as linearizable reads on a standby, and what would have to change to make it so? — Hint: §8.9 and ADR-16.
  2. Why must the divergence detector walk the full set of timelines recorded in a history file rather than compare only the latest? Name the exact rejoin scenario it would otherwise miss. — Hint: §19.2 and the pitfalls in §19.6.
  3. Why does a controlled handover never produce a timeline fork, while an uncontrolled promotion always risks one? Name the exact structural difference between the two paths. — Hint: the two step lists in §18.2.
  4. Why does this design report four distinct lag numbers instead of one aggregate figure, and which specific number governs an RPO SLA versus a read-staleness SLA? — Hint: P12 and §21.1.
  5. Why does LSN monotonicity (I1) not, by itself, prevent a timeline fork — what additional mechanism is structurally required, and why? — Hint: I1 versus I4, and §19.1.

If you only remember three things

The primary's local fsync always comes first and replication acknowledgement is layered on top, so "what RPO do you have" has no answer until you name the mode (I2, MM3). A slot is a promise and a timeline is a version number for history, so the two things that wedge or corrupt a cluster, an unredeemed slot and an unnoticed fork, are made visible, never silently auto-fixed (MM4, MM5, P8, P11). Failover is a primitive, not a policy: fence, bump the timeline, fsync the fork LSN, accept writes, in that order, with a human acknowledging any lost range (I10, I15, ADR-14).

Words used here

  • WAL (write-ahead log): the append-only log every replication consumer reads; its format is owned by Blueprint #69 (ADR-03).
  • LSN: a 64-bit byte offset into a timeline's WAL, the system's ordering primitive (I1).
  • Timeline: a 4-byte monotonic ID bumped at every promotion, used to detect forks (I4).
  • Physical replication: byte-for-byte WAL shipping and replay (§2).
  • Logical replication: shipping decoded row or statement change events (§1).
  • Walsender / walreceiver: the sending task on the primary or a cascading standby, and the receiving task on a standby (§37).
  • Replication slot: a durability contract that stops WAL truncation ahead of a registered consumer (P8, I6).
  • restart_lsn / confirmed_flush_lsn: the oldest LSN a slot keeps WAL for, and the LSN the consumer has durably confirmed (§11.3).
  • Quorum: waiting for floor(n/2)+1 acks by default (P13, ADR-06).
  • Reorder buffer: groups row operations by transaction and emits them in commit order (I3, I8).
  • Output plugin: the pluggable serialiser from change events to Avro, JSON or protobuf (P7, ADR-08).
  • Fencing: stopping an old primary from accepting writes before a promotion completes (I15).
  • Divergence: two hosts' histories have forked and cannot be reconciled without data loss (§37).
  • RPO / RTO: the maximum tolerable data loss, and the time to restore write availability (§37, §4).
  • Cascading replica: a standby whose WAL source is another standby (§20).
