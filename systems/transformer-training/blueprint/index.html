114 — Transformer Training Loop

Project Number: 114

Project Name: Transformer Training Loop

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a from-scratch, production-grade training loop for decoder-only Transformer language models in the nanoGPT → GPT-NeoX → Megatron-LM lineage: a system that consumes pre-tokenized token shards, trains an 8M–1.3B-parameter causal Transformer to a quantified loss target on a single 8×A100 80 GB node, and exposes checkpoint, resume, evaluation, and fault-recovery as first-class, inspectable operations. The loop owns four pillars — data pipeline, model, optimizer, control plane — and every later phase extends exactly one of them.

Phase-0 in-scope modules (packages under src/tt/, normative — see §10, §11):

  1. tt.config — TrainConfig / ModelConfig YAML loader + validator.
  2. tt.data — shard catalog, deterministic (seed, epoch) shuffle, mmap streaming reader, sequence packing, Batch collation.
  3. tt.model — token embedding, positional encoding (learned/RoPE), causal multi-head attention, MLP (GELU/SwiGLU), norm (LayerNorm/RMSNorm), causal-LM loss.
  4. tt.optim — hand-rolled AdamW, warmup-cosine schedule, decay/no-decay param groups.
  5. tt.train — the loop: forward, backward, accumulation, clip, precision, RNG.
  6. tt.ckpt — atomic sharded checkpoint writer/reader, retention policy.
  7. tt.eval — held-out perplexity + fixed benchmark suite.
  8. tt.log — JSONL (durable) + W&B (best-effort) dual sink.
  9. tt.fault — OOM shrink, NaN/Inf gate, SIGTERM preempt handler.
  10. tt.cli — tt train|eval|sweep|ckpt|diag operator commands.

System boundaries. Provides: model forward/backward, optimizer + schedule, mixed precision, gradient accumulation + activation checkpointing, single-node DDP and FSDP/ZeRO-2 data parallelism, atomic checkpoint + bit-exact resume, held-out eval, loss-spike detection, throughput/MFU measurement. Delegates: tokenization (upstream project — this loop only reads its .npy shards and never tokenizes at train time); the autograd engine (PyTorch — this blueprint does not reimplement backprop). Does NOT provide: a general deep-learning framework; a hosted training platform; Megatron-style 3D (tensor+pipeline+data) parallelism at multi-node scale — Phase 8 ships the single-node FSDP/ZeRO-2 hook and a documented multi-node extension point, full 3D parallelism is PhaseDeferred("§35"); RLHF/SFT loops; inference/serving.

Non-goals. Not a tokenizer; not a distributed-systems research platform; not a hyperparameter-search product (a grid/random sweep launcher ships, Bayesian search is deferred, §35).

Deployment model. One process per GPU, torchrun-launched, 8 processes on one node for the baseline config; Phase 8 generalizes the launch to multiple nodes under the same entrypoint.

Target users/operators. ML-infra engineers reproducing GPT-2-class runs from raw shards; on-call engineers diagnosing loss spikes, OOM, hangs, and checkpoint corruption during a multi-day run.

What later phases unlock. Phase 1 unlocks real-corpus training (vs. one fixed batch). Phase 4 unlocks 2–3× larger batch sizes via bf16. Phase 5 unlocks models too large for unchecked activation memory. Phase 8 unlocks models too large for one GPU's parameter/optimizer memory. Phase 9 unlocks defensible throughput numbers (MFU) for capacity planning.

Language: Python 3.11 + PyTorch 2.3+. Rationale: PyTorch supplies the CUDA autograd substrate, the distributed primitives this blueprint builds on (DDP, FSDP), and is the language every reference implementation studied here (nanoGPT, Megatron-LM, GPT-NeoX, DeepSpeed) is written in — matching the ecosystem avoids translation-loss between blueprint and literature. Rejected — JAX: cleaner functional/pmap semantics and first-class TPU support, but its checkpoint, logging, and community-op ecosystem is thinner in 2026, and XLA compilation errors are a materially worse debugging experience for a from-scratch team; JAX wins when targeting TPU pods or when functional-transform composability (vmap-of-grad-of-vmap) is the primary engineering problem, which it is not here. Rejected — Rust (candle/burn): memory safety and single-binary deployment, but no mature FSDP/ZeRO-equivalent distributed story in 2026; wins for inference-serving edge deployment, not for a research/production training loop. Rejected — C++/LibTorch: used inside PyTorch already; the host-language iteration speed is not the throughput bottleneck (the CUDA kernels are), so Python's development velocity dominates.

Prerequisites. Matrix calculus for backpropagation; IEEE 754 floating-point semantics; the CUDA execution model (kernels, streams, memory hierarchy, NCCL rings); familiarity with the upstream BPE-tokenizer project's shard format; PyTorch autograd internals (Function, backward(), the tape).

Estimated timeline. Phase 0: 2 weeks. Full system (Phase 0–9): 5–6 months at one senior ML-infra engineer full time, assuming access to an 8×A100 node from Phase 4 onward.

Deferred features, each flagged PhaseDeferred("§35") and rows of the Deferred Features Register (§35): Megatron-style tensor+pipeline 3D parallelism; custom fused Triton/CUDA kernels (fused RoPE, fused RMSNorm, flash-attention drop-in); Bayesian hyperparameter search; RLHF/PPO training hooks; multi-node elastic (torchrun --rdzv) fault tolerance beyond single-node preemption.

2. Why Build This

Every downstream ML project in this portfolio calls into a training loop; when that loop is an opaque framework (transformers.Trainer, PyTorch Lightning, accelerate), a debugging session ends at a stack trace inside someone else's abstraction. When the loop is one you wrote, the same session ends at a specific line: the gradient-norm trace, the deterministic-replay batch, the RNG snapshot.

The literature is unusually concrete and well-anchored. Vaswani et al. (2017) fixed the architecture; GPT-2 (Radford et al. 2019) and GPT-3 (Brown et al. 2020) are the open anchors for what a working run looks like at 124M and 175B parameters; LLaMA (Touvron et al. 2023) is the contemporary open reference for the modern feature set (RMSNorm, RoPE, SwiGLU, AdamW β2=0.95). Karpathy's nanoGPT is the existence proof that a correct GPT-2 reproduction fits in under 1,000 lines; Megatron-LM (Shoeybi et al. 2019) and DeepSpeed/ZeRO (Rajbhandari et al. 2020) are the production-scale references for going past one GPU's memory.

This project sits at the intersection: a nanoGPT-sized Phase-0 surface, with every later phase opening a documented, ADR-gated alternative (RMSNorm vs. LayerNorm, RoPE vs. learned positions, SwiGLU vs. GELU, FSDP vs. plain DDP). By completion, the reader holds the same toolbox OpenAI, Meta, and EleutherAI held when they shipped GPT-2/LLaMA/Pythia — and can name exactly which invariant a line of code protects.

What Mastery Looks Like — after this blueprint, an engineer can:

  • Derive the causal-attention and cross-entropy backward pass by hand and predict which activation must be recomputed under checkpointing (§14, §17).
  • Explain why gradient accumulation without 1/N loss-scaling silently diverges, and prove bit-exact equivalence between micro-batched and full-batch updates (§13, I3).
  • Choose bf16 over fp16 for a given GPU generation and state exactly why one needs GradScaler and the other does not (§16, I6).
  • Diagnose a loss spike from a JSONL trace alone — offending micro-batch, pre-clip gradient norm, largest activation — without re-running the job (§19).
  • Reconstruct, from a crashed run's last checkpoint, a continuation that is bit-exact to a non-crashed run within fp64 tolerance (§18, I1).
  • Compute Model FLOPs Utilization (MFU) from a measured tokens/s number and explain the gap to the theoretical peak (§21, §32).
  • Choose between DDP, FSDP/ZeRO-2, and full 3D parallelism for a given model size and GPU budget, and state the regime where each is the right call (§20, §31, §34).

Data pipeline box. Reads .npy int32 shards produced offline by the upstream tokenizer; the loop never tokenizes at train time (I2). Deterministic (seed, epoch) shuffle, sequence packing, Batch collation. Trust boundary: a shard's SHA-256 is checked once at catalog load (§9 ADR-15).

Model-build box. Constructs the module graph from ModelConfig, applies GPT-2-style or Xavier init, ties token-embedding and output-projection weights (ADR-14), moves to the target device/dtype.

Forward/loss/backward boxes. Pure function of (params, Batch); autocast to bf16/fp16 wraps forward only (I4); loss is causal cross-entropy on shifted targets (§14).

Gradient-accumulation/checkpoint box. Concurrency boundary: micro-batches execute sequentially on one device; accumulation is a correctness primitive (I3), not a throughput one; activation checkpointing trades one extra forward pass per checkpointed block for O(√L) instead of O(L) activation memory (§17).

Optimizer/schedule boxes. AdamW with fp32 master state regardless of model dtype (I4); global-norm clip before the step; cosine-with-warmup LR (§15).

Control-plane boxes (right-hand fan-out). Persistence boundary: the checkpointer is the only writer to durable storage; protocol boundary: the eval harness and logger are read-only with respect to training state; the fault loop is the external-interface boundary (OS signals, CUDA OOM exceptions). All three fire on the same step counter and are individually toggleable via TrainConfig.

6. Design Principles

  1. P1 — Overfit one batch first. The loop must drive one fixed batch to near- zero loss before anything else is trusted (Phase 0, §12). Tradeoff: delays "real" training by a day; operational implication: it is the fastest bisect target for a new bug; violating it means every subsequent bug is indistinguishable from a scale problem.
  2. P2 — Bit-exact resume is the contract. A crash-and-resume at step N must match an uninterrupted run at step N+1000 to fp64 tolerance (I1, §18). Tradeoff: forces deterministic shuffling and full RNG capture, which cost engineering time up front; violating it silently corrupts every long run's reproducibility.
  3. P3 — Deterministic shuffle. The shuffle is a pure function of (seed, epoch) (I2, §8.1). Tradeoff: precludes torch DataLoader's built-in worker-random shuffling; violating it makes P2 unreachable.
  4. P4 — No silent OOM. An OOM must trigger checkpoint-and-shrink, never a bare process crash (§19 FM-3). Tradeoff: requires an exception handler around every optimizer step; violating it loses up to a full checkpoint interval of work.
  5. P5 — Gradient-accumulation correctness. Accumulation must be bit-exact (fp64) with an equivalent full batch (I3, §8.9). Tradeoff: requires 1/N loss scaling, not naive summation; violating it silently changes the effective LR.
  6. P6 — Eval is observational. Held-out eval never steers training hyperparameters (no early stopping on eval loss, §19). Tradeoff: forgoes a cheap regularization signal; violating it couples two subsystems that must stay independently debuggable.
  7. P7 — Checkpoint frequency is a budget decision. Default: every 1,000 steps, atomic write, retain last 3 + best-eval + every-10k milestone (§18). Tradeoff: storage cost vs. lost-compute cost; violating it either wastes storage or risks losing hours of GPU time.
  8. P8 — Every loss spike is explained. A step >3× the rolling-median loss emits a diagnostic bundle (offending micro-batch, per-sample loss, pre-clip grad norm, max activation) — never a silent skip (I9, §19). Tradeoff: extra bookkeeping on every step; violating it makes spikes undiagnosable after the fact.
  9. P9 — No leaky globals. No component reads os.environ or process-wide state outside TrainConfig (I8, §11). Tradeoff: some ergonomics lost (no ambient device selection); violating it breaks P2's determinism.
  10. P10 — Mixed precision defaults to bf16. bf16's fp32-equivalent dynamic range removes the need for GradScaler; fp16 is an ADR-gated fallback for pre-Ampere hardware (ADR-09, §16). Tradeoff: bf16 has fewer mantissa bits (less precision) than fp16; violating the default on Ampere+ hardware adds unneeded loss-scaling complexity.
  11. P11 — Operations are the product. The diagnostics CLI, checkpoint inspector, and run-comparison tool are first-class deliverables, not afterthoughts (§21, §24). Tradeoff: roughly a third of engineering time goes to tooling that never touches the forward pass; violating it means every incident becomes an ad hoc script.
  12. P12 — PyTorch is the substrate, not the framework. torch.nn/autograd/ cuda are used directly; torch.optim, DataLoader, and GradScaler are not, so every arithmetic step stays inspectable (ADR-07, §11). Tradeoff: more code to own and test; violating it re-introduces the opaque-framework problem this project exists to avoid (§2).

8. Domain Model

8.1 Tokenization & Batching Contract

The upstream tokenizer (a separate blueprint) is the sole producer of .npy int32 token-id shards; this project is the sole consumer. Contract: a ShardCatalog (§11.2) lists every shard, its token count, and its SHA-256, checked once at startup (ADR-15, I2). The training loop never invokes a tokenizer. Sequences are packed (ADR-17): multiple documents are concatenated into one (B, T) row separated by eos_token_id, with an attn_mask (§11.3) preventing cross-document attention — this trades a small mask-construction cost for eliminating padding waste entirely.

8.2 Embedding & Positional Encoding

Token embedding: a lookup table E ∈ R^(vocab × d_model), tied to the output projection (ADR-14, I10) so the same matrix produces logits: logits = h · Eᵀ. Two positional schemes (ADR-05): learned absolute positions, added to the token embedding before layer 0; rotary (RoPE), which instead rotates each query/key vector's dimension-pairs by an angle proportional to position, preserving relative-position information in the dot product without adding to the residual stream (Su et al. 2021). RoPE angle for pair i at position p: θ_i(p) = p / base^(2i/d_head), base = 10000 (default, ADR-05).

8.3 Multi-Head Causal Attention

For H heads of dimension d_head = d_model / H: Q, K, V = x·W_Q, x·W_K, x·W_V (or, under GQA, K, V project to n_kv_head < H groups shared across query heads). Attention weights: A = softmax((Q·Kᵀ)/√d_head + M) where M is the causal mask (M[i,j] = -∞ for j > i, 0 otherwise) combined with the packing attn_mask from §8.1. Output: A·V, reshaped back to (B, T, d_model) and projected by W_O. Causal masking is what makes the model autoregressive: position i's output depends only on positions ≤ i (Vaswani et al. 2017 §3).

8.4 MLP & Residual/Pre-Norm Stack

Pre-norm residual block (ADR-03): x' = x + Attn(Norm(x)), then x'' = x' + MLP(Norm(x')). Norm is RMSNorm (default, ADR-04) — RMSNorm(x) = x / rms(x) · γ, rms(x) = √(mean(x²) + ε) — or LayerNorm (mean-subtracting variant), selectable per ModelConfig.norm. MLP is SwiGLU (default, ADR-06) — MLP(x) = (SiLU(x·W1) ⊙ (x·W2))·W3, with d_ff scaled to 2/3 of the GELU-equivalent width to hold parameter count constant — or a plain GELU MLP (GELU(x·W1)·W2).

8.5 Forward Pass & Cross-Entropy Loss

The full forward is L stacked blocks (§8.4) over the embedded, positioned input, a final norm, then the tied output projection to (B, T, vocab) logits. Loss is causal-LM cross-entropy against targets shifted by one position: loss = mean_t[ -log softmax(logits_t)[target_t] ] for t where target_t is not a padding/cross-document sentinel. Under autocast (§8.8), this forward runs in bf16/fp16; the loss reduction itself runs in fp32 to avoid catastrophic cancellation in the log-sum-exp.

8.6 Backward Pass & Gradient Flow

PyTorch's reverse-mode autograd (loss.backward()) walks the tape built during §8.5's forward. Gradient checkpointing (§8.9, Chen et al. 2016) discards intermediate activations per block and recomputes them during this backward pass — trading one extra forward per checkpointed block for O(√L) resident activation memory instead of O(L). The pre-clip global gradient norm is recorded (I9) before any clipping is applied.

8.7 AdamW Optimizer & LR Schedule

Per-parameter update (Loshchilov & Hutter 2019, decoupling weight decay from the adaptive step):

m_t = β1·m_{t-1} + (1-β1)·g_t
v_t = β2·v_{t-1} + (1-β2)·g_t²
m̂_t = m_t / (1-β1^t);  v̂_t = v_t / (1-β2^t)
θ_t = θ_{t-1} - lr_t · ( m̂_t/(√v̂_t + ε) + wd·θ_{t-1} )

β = (0.9, 0.95), ε = 1e-8 (Brown et al. 2020, ADR-07). lr_t follows a linear warmup over warmup_steps then a cosine decay to min_lr_ratio · peak_lr over the remaining max_steps (ADR-08). Parameters are split into decay/no-decay groups (§11.1 groups.py): weight decay applies to matmul weights only, never to biases, norm gains, or embeddings.

8.8 Mixed-Precision Numerics

Forward/backward run under autocast to bf16 (default, ADR-09) or fp16 (fallback for pre-Ampere GPUs). bf16 shares fp32's 8-bit exponent (dynamic range) but has only 7 mantissa bits, so no loss-scaling is required (Micikevicius et al. 2018); fp16 has a 10-bit mantissa but a 5-bit exponent, so small gradients underflow to zero without a GradScaler-equivalent dynamic loss-scale. The optimizer's moments and the master copy of every parameter are always fp32 (I4) — mixed precision is a forward/backward property only, never an optimizer property (P10).

8.9 Gradient Accumulation & Activation Checkpointing

Accumulation splits an effective batch of micro_batch × accum into accum sequential micro-batches whose losses are each scaled by 1/accum before backward(), so the summed gradient equals the true full-batch gradient (I3, P5) — never accumulate un-scaled gradients in a buffer, which double-counts under mixed precision. Activation checkpointing (Chen et al. 2016) is orthogonal: it wraps a subset of blocks so their activations are freed after forward and recomputed during backward, at the cost of one extra forward pass per checkpointed block (§8.6).

8.10 Data / Tensor / Pipeline Parallelism & ZeRO Sharding

Data parallelism (DDP): every rank holds a full model replica; gradients all-reduce after each accumulation cycle. ZeRO (Rajbhandari et al. 2020) shards, progressively, optimizer state (stage 1), gradients (stage 2), and parameters (stage 3, ≈ PyTorch FSDP) across data-parallel ranks, trading all-gather/ reduce-scatter communication for per-GPU memory. Tensor parallelism (Shoeybi et al. 2019) splits individual matmuls (e.g. attention head groups, MLP columns) across GPUs within a layer; pipeline parallelism splits layers across GPUs and pipelines micro-batches through them. This blueprint ships DDP and FSDP/ZeRO-2 (Phase 8); tensor/pipeline (3D) parallelism is PhaseDeferred("§35").

8.11 Worked Example — One Training Step, End to End

micro_batch=8, seq_len=1024, accum=4, 8×A100 DDP ⇒ effective batch = 8 × 4 × 8 = 256 sequences = 262,144 tokens/step. Step: (1) 4 micro-batches run forward+backward with loss scaled by 1/4; (2) gradients accumulate locally then all-reduce once across the 8 ranks; (3) global-norm clip at 1.0; (4) AdamW step with lr_t from the warmup-cosine schedule at the current step; (5) LossPoint logged with tokens_seen += 262,144. At step 0, lr_0 = peak_lr · 0/warmup_steps = 0; at step = warmup_steps, lr = peak_lr.

8.12 Malformed-Input & Failure-Path Examples

Malformed input: a shard whose recorded n_tokens in ShardCatalog disagrees with the actual .npy length — caught by the startup integrity check (§8.1, ADR-15); the loop refuses to start rather than silently truncating. Failure path: a CUDA OOM raised mid-backward() — caught by tt.fault.oom (P4), which discards the current step's gradients, halves micro_batch_size while doubling accum to preserve the effective batch size (I11), checkpoints, and restarts the step; if OOM recurs at the halved size twice consecutively, the run halts and pages an operator (§19 FM-3, §24).

12. Phase 0 — Repository Skeleton & Correctness Kernel

12.1 Objectives

Stand up the full repository shape (§10) and prove the smallest possible correctness kernel: one fixed batch, one GPU, one model, one config, overfit to near-zero loss (P1, I5). No data pipeline, no checkpoint, no eval — those are later phases. This phase is the bisect target for every future regression.

12.2 Detailed Implementation Steps

Land pyproject.toml, uv.lock, the src/tt/ package tree with stub __init__.py files (§10), and Makefile targets bootstrap|build|test|lint| smoke|clean (each uv run-backed, one-line output, non-zero exit on failure). Implement tt.config.loader.load_train_config (§11.1) as a signature-only YAML→TrainConfig parser with a separate tt.config.validate module enforcing I11 (effective-batch invariance) and I8 (no ambient state — P9). Implement tt.model.transformer.build_model(cfg: ModelConfig) per §8.2– §8.5 (Vaswani et al. 2017; ADR-02, ADR-03). Implement the bare training orchestration in tt.train.loop as a state-transition table (state: INIT → FORWARD → LOSS → BACKWARD → CLIP → STEP → SCHEDULE → CHECK_LOSS, no persistence, no accumulation) enforcing I5. Land the CI workflows (§10 .github/workflows/) with numerics.yml/gpu-smoke.yml stubbed pending GPU runners.

12.3 Deliverable

tt train --config configs/presets/smoke_8m.yaml runs on one GPU and drives one fixed, randomly-generated (4, 64) batch from an initial loss of ≈ ln(vocab_size) to below the smoke threshold, exercising the full config→model→loss→backward→optimizer→schedule chain end to end.

12.4 Acceptance Criteria

smoke_8m.yaml (n_layer=4, d_model=256, n_head=4, 8M params) reaches training loss < 0.1 within 200 optimizer steps (I5); initial loss is > 8.0 (≈ ln(50257)); make test exits 0 on the unit suite; make lint/make typecheck exit 0.

12.5 Conformance Fixtures

conformance/corpora/configs/smoke_8m.yaml | fixed-config correctness | final loss < 0.1. conformance/corpora/expected/smoke_8m_losstrace.json | reference 200-step loss curve | new run's curve within 1e-4 of reference at fp32.

12.6 Pitfalls

Unshifted targets: loss plateaus near ln(vocab_size) instead of decreasing — caught by the I5 initial-loss assertion. Bad init (std=1.0 on a 50K-vocab embedding) overflows fp32 in the first softmax — default to init_std=0.02 (GPT-2, ADR-14-adjacent). Scope creep: resist adding checkpointing/eval here; they are Phase 6/7.

12.7 Performance Concerns

Irrelevant at this scale (8M params, one batch) — no batching, no IO. The one real cost is torch.manual_seed + CUDA context init dominating wall time (~5–10 s), which sets the §4 cold-start budget's floor.

12.8 Edge Cases

max_steps=0 (validator rejects, I11); vocab_size mismatched between ModelConfig and the fabricated batch's randint upper bound (validator rejects at config-load time, not at first forward).

12.9 Failure Analysis

A regression here blocks every other phase — treat as a release-blocking P0. Detection: CI gate on test_phase0_overfit_one_batch. Blast radius: none (single process, no shared state). Recovery: git bisect against the loss trace fixture (§12.5).

13. Phase 1 — Tokenized Data Pipeline & Sequence Packing

13.1 Objectives

Replace Phase 0's single in-memory batch with the real input side: a shard catalog, a deterministic (seed, epoch) shuffle (P3, I2), an mmap streaming reader, and sequence packing (ADR-17). End state: for batch in data_pipeline drives the Phase-0 loop and the smoke test still passes.

13.2 Detailed Implementation Steps

Implement tt.data.catalog.ShardCatalog.load/integrity_check (§11.2, ADR-15) — SHA-256 over every shard at startup, hard-fail on mismatch (§8.12). Implement the two-layer deterministic shuffle in tt.data.shuffle: a shard-level permutation seeded by hash((seed, epoch, "shards")) and a within-shard sequence-offset permutation seeded by hash((seed, epoch, shard.path)) (I2, P3). Implement tt.data.stream.ShardStream as a stateful mmap-backed iterator whose state_dict() returns exactly (epoch, shard_index, offset_index) (I12-adjacent — the data-pipeline RNG stream). Implement tt.data.pack (ADR-17): concatenate documents with eos_token_id separators into fixed-length (T,) rows, building the attn_mask that blocks cross-document attention (§8.1, §8.3).

13.3 Deliverable

DataPipeline (§11.3) yields real Batch objects from on-disk shards; the Phase-0 smoke test passes unchanged when its fixed batch is replaced by the first batch this pipeline yields for seed=42, epoch=0.

13.4 Acceptance Criteria

Two ShardStream instances constructed with identical (seed, epoch) yield bit-identical batch sequences for 10,000 consecutive batches (I2); integrity_check() on a corrupted fixture shard raises within < 200 ms; packing wastes 0% of sequence length to padding on the conformance corpus (vs. a fixture measuring padding waste on the same corpus).

13.5 Conformance Fixtures

tests/unit/test_shuffle_determinism.py | same-seed replay | identical permutations. conformance/corpora/shards/corrupt_shard.npy | truncated file | integrity_check() raises ShardIntegrityError. conformance/corpora/ shards/multi_doc.npy | packing correctness | attn_mask blocks doc i from attending into doc i+1.

13.6 Pitfalls

Using numpy.random.default_rng()'s global state instead of a per-call Generator(seed=...) breaks I2 the moment two pipelines run in the same process (e.g. train + eval shards). Forgetting to re-derive the shuffle at epoch rollover repeats the same permutation forever. mmap pages evicted under memory pressure silently reappear as zeros on some filesystems without madvise hints — verify with the shard_read_speed benchmark (§28).

13.7 Performance Concerns

mmap reads are zero-copy but page-fault on first touch; sequential access per shard (the offset permutation is within-shard, not global) keeps page cache locality good. Shard-catalog integrity check is O(total_tokens) SHA-256 — run it once at startup, never per-epoch.

13.8 Edge Cases

A shard shorter than one sequence length T (skip, log a warning, do not crash — validator should have caught degenerate corpora earlier); epoch rollover mid-batch; two ranks racing to open the same shard file (read-only mmap, no lock needed).

13.9 Failure Analysis

A shuffle-determinism regression breaks I1 (bit-exact resume) transitively — detect via test_shuffle_determinism in CI; blast radius is every downstream phase's resume guarantee; recovery is reverting the shuffle-seed derivation change and re-running the fixture.

13.10 Operational Notes

tt diag gains no new commands yet (Phase 12 diag simulate already covers shuffle-determinism assertions). Metric shuffle_hash (I2) and shard_integrity_failures are added to the JSONL schema stub ahead of Phase 6.

14. Phase 2 — Transformer Model: Attention, MLP, Norm, Embeddings

14.1 Objectives

Replace Phase 0's minimal model stub with the full configurable architecture: causal multi-head attention (with optional GQA), RMSNorm/LayerNorm, SwiGLU/ GELU MLP, learned/RoPE positions, tied embeddings — every alternative ADR-gated (ADR-03–ADR-06, ADR-14).

14.2 Detailed Implementation Steps

Implement tt.model.attention per §8.3 (Vaswani et al. 2017, "Model Architecture" section): causal mask M[i,j] = -∞, j>i combined with the packing attn_mask (§13.2, ADR-17). Implement tt.model.positions (§8.2): learned absolute embedding addition, or RoPE rotation of query/key dimension-pairs by θ_i(p) = p / base^(2i/d_head) (Su et al. 2021, ADR-05). Implement tt.model.norm (§8.4): RMSNorm x/rms(x)·γ default (Zhang & Sennrich 2019, ADR-04) or LayerNorm. Implement tt.model.mlp (§8.4): SwiGLU (SiLU(xW1)⊙(xW2))W3 with d_ff scaled to 2/3 of the GELU-equivalent width (Shazeer 2020, ADR-06), or plain GELU. Implement tt.model.embedding tying token-embedding and output-projection (ADR-14, I10) with a shared init-scale assertion. Implement tt.model.block composing pre-norm residual (ADR-03): x' = x + Attn(Norm(x)), x'' = x' + MLP(Norm(x')). Implement tt.model.loss.cross_entropy_causal (§8.5) with fp32 loss reduction under autocast.

14.3 Deliverable

build_model(ModelConfig) constructs a full GPT-2-124M-shaped or LLaMA-120M-shaped model (per presets/gpt2_124m.yaml / presets/ llama_120m.yaml) whose forward pass produces (B, T, vocab) logits and whose parameter count matches the analytically-derived count within 0.1%.

14.4 Acceptance Criteria

Gradient-check: numerical vs. analytic gradient on a 2-layer, 32-dim toy model agree to < 1e-5 relative error (finite-difference, torch.autograd. gradcheck-style fixture). Parameter count for gpt2_124m.yaml equals 124,439,808 ± 0.1% (GPT-2-small reference). RoPE relative-position property: rotating both q and k by the same absolute offset leaves q·k unchanged (< 1e-6 abs error) — the invariance RoPE is built to provide (Su et al. 2021).

14.5 Conformance Fixtures

tests/unit/test_attention.py | causal-mask correctness | position i's output gradient w.r.t. position j>i's input is exactly 0. tests/unit/ test_rope.py | relative-position invariance fixture. tests/unit/ test_rmsnorm.py, test_swiglu.py | numeric equivalence to reference formulas on fixed inputs.

14.6 Pitfalls

Tied-embedding init mismatch (I10): initializing the embedding and output projection independently, then tying, silently rescales one of them — assert the shared std at build time. GQA head-group indexing off-by-one silently degrades to full MHA without erroring — a fixture that asserts n_kv_head < n_head when GQA is enabled catches it. RoPE base/dtype: rotating in fp16 loses precision at long context lengths — always rotate in fp32 regardless of the surrounding autocast dtype (P10-adjacent).

14.7 Performance Concerns

Attention is O(T²·d_model) in compute and memory for the un-fused path; torch.nn.functional.scaled_dot_product_attention (SDPA) is used to get a fused-kernel path without hand-writing CUDA (ADR-19 defers custom kernels). RMSNorm avoids the mean-reduction pass LayerNorm needs — a measurable win at depth (Zhang & Sennrich 2019).

14.8 Edge Cases

seq_len exceeding RoPE's trained range (extrapolation degrades gracefully, does not crash); n_head not dividing d_model (validator rejects at config load, §13.2-adjacent); GQA with n_kv_head=1 (multi-query attention, a valid degenerate case).

14.9 Failure Analysis

A silent causal-mask bug (attending to future tokens) does not crash — it produces a model that looks like it trains but never generalizes; detection is the N.4 gradient-check fixture plus an eval-time held-out perplexity that is implausibly low relative to model size (cross-checked in Phase 7).

14.10 Operational Notes

tt diag ckpt-inspect (stub introduced in Phase 6) will report parameter counts per module for exactly this reason — a silent architecture change between runs is visible as a parameter-count diff.

15. Phase 3 — AdamW Optimizer & Cosine-Warmup Schedule

15.1 Objectives

Implement the hand-rolled AdamW optimizer (ADR-07, P12) and the warmup-cosine LR schedule (ADR-08), replacing any placeholder optimizer from Phase 0.

15.2 Detailed Implementation Steps

Implement tt.optim.adamw.AdamW per §8.7 (Loshchilov & Hutter 2019): decoupled weight-decay update using torch._foreach_* fused multi-tensor ops for throughput, OptimizerState (§11.4) always fp32 (I4, ADR-09). Implement tt.optim.groups.split_decay_groups: weight decay applies to matmul weights only, never biases/norm-gains/embeddings (§8.7). Implement tt.optim.schedule.WarmupCosine (ADR-08): linear ramp over warmup_steps then cosine decay to min_lr_ratio · peak_lr over the remainder (Brown et al. 2020 hyperparameters: β=(0.9,0.95), grad_clip=1.0, ADR-12).

15.3 Deliverable

build_optimizer(cfg, model) and build_scheduler(cfg, opt) produce an AdamW instance and schedule whose per-step LR and per-parameter update match a reference PyTorch torch.optim.AdamW run to numerical tolerance on a fixed toy problem.

15.4 Acceptance Criteria

On a convex quadratic toy loss, this AdamW's trajectory matches torch.optim.AdamW's to < 1e-6 max absolute parameter deviation over 1,000 steps at fp64. WarmupCosine at step=0 yields lr=0; at step=warmup_steps yields lr=peak_lr (± 1e-9); at step=max_steps yields lr=min_lr_ratio·peak_lr (± 1e-9).

15.5 Conformance Fixtures

tests/unit/test_adamw.py | reference-optimizer equivalence fixture. tests/unit/test_schedule.py | named checkpoints at step ∈ {0, warmup_steps, max_steps} with expected LR values. tests/unit/ test_clip.py | global-norm clip returns the pre-clip norm (I9 telemetry).

15.6 Pitfalls

Applying weight decay to LayerNorm/RMSNorm gains or biases (a common copy-paste bug from vanilla Adam implementations) measurably degrades convergence — caught by test_adamw.py's decay-group assertion. Bias-correction (m̂, v̂) omitted at low step counts inflates early-training updates. Cosine schedule computed from step instead of step - warmup_steps shifts the whole curve.

15.7 Performance Concerns

torch._foreach_* fuses the per-parameter-tensor update into one kernel launch instead of one per tensor — materially reduces Python-loop/launch overhead at 124M+ parameter counts (hundreds of tensors).

15.8 Edge Cases

warmup_steps > max_steps (validator rejects, I11-adjacent); betas outside (0,1) (validator rejects); resuming mid-warmup (schedule is a pure function of step, so resume is automatic given I1).

15.9 Failure Analysis

An optimizer-state dtype regression (fp32 master silently downcast to bf16) violates I4 — detection is the OptimizerState dtype assert at every checkpoint save (Phase 6); blast radius is training-quality degradation that looks like a plateau, not a crash, and is the single most-common "why did training stall" postmortem case in the literature (Brown et al. 2020 appendix).

15.10 Operational Notes

grad_norm and grad_norm_clipped (both pre/post clip, §11.5 LossPoint) are logged every step from Phase 6 onward — this phase defines where those numbers come from (§8.6, §8.7).

16. Phase 4 — Mixed Precision & Numerical Stability

16.1 Objectives

Add bf16 (default) / fp16 (fallback) autocast to the forward/backward pass while keeping the optimizer state in fp32 (I4, ADR-09, P10) — the single most consequential numerical-stability decision in the system.

16.2 Detailed Implementation Steps

Implement tt.train.precision.autocast_context(cfg) wrapping the forward pass only (§8.8, Micikevicius et al. 2018): torch.autocast(device_type='cuda', dtype=torch.bfloat16) by default; torch.float16 with an fp16-specific dynamic loss-scale for pre-Ampere hardware (ADR-09's rejected-alternative regime). Assert at optimizer-build time that OptimizerState.exp_avg, exp_avg_sq, and master_params are fp32 regardless of cfg.precision (I4). Implement tt.fault.nan.nan_gate (I6): a pre-optimizer-step scan of the (already-clipped) gradient tensors for NaN/Inf; on detection, skip the step, halve the LR for the next N steps, and emit an FM-6 diagnostic record (§19, P8, I9).

16.3 Deliverable

The same smoke_8m.yaml run from Phase 0 reproduces its loss curve under bf16 autocast within a quantified numerical-drift tolerance of the fp32 baseline.

16.4 Acceptance Criteria

bf16-autocast run's loss trajectory over 200 steps stays within ≤ 5% relative deviation of the fp32 baseline's trajectory at every logged step (a test_bf16_vs_fp32_drift fixture). A synthetic NaN injected into one gradient tensor is caught and the step skipped 100% of the time across 1,000 injected trials (I6). VRAM at micro_batch=8, seq_len=1024 fits the §4 ≤ 60 GB ceiling.

16.5 Conformance Fixtures

tests/integration/test_bf16_vs_fp32_drift.py | drift-bound fixture. tests/unit/test_nan_gate.py (extends test_clip.py) | synthetic-NaN injection | step skipped, nan_gate_triggers incremented.

16.6 Pitfalls

Casting the loss reduction itself to bf16 (instead of only the forward matmuls) reintroduces log-sum-exp cancellation error — always reduce the loss in fp32 (§8.5). Rotating RoPE angles in fp16 loses precision at long context (§14.6) — rotate in fp32 even under fp16 autocast. Forgetting that fp16 (unlike bf16) needs a loss-scale: gradients silently underflow to zero without one, and training appears to "not learn" rather than erroring.

16.7 Performance Concerns

bf16 halves activation memory versus fp32 and roughly doubles achievable batch size at fixed VRAM — the single largest throughput lever available before Phase 8's sharding (§21 M1).

16.8 Edge Cases

Mixed dtype across a checkpoint boundary (model saved in bf16, optimizer always fp32 — §11.4 CheckpointMeta records both); a GPU generation lacking native bf16 tensor cores (validator warns and suggests precision: fp16).

16.9 Failure Analysis

Undetected NaN propagation corrupts every subsequent optimizer step irreversibly — this is why I6's gate runs before the optimizer step, not after; forensic artifact is the FM-6 diagnostic bundle (offending micro-batch, per-sample loss, pre-clip grad norm) written to JSONL (P8).

16.10 Operational Notes

Metrics nan_gate_triggers, gpu_mem_mb (§11.5) ship from this phase. Runbook docs/runbooks/nan-loss.md (§10) is authored alongside this phase's merge.

17. Phase 5 — Gradient Accumulation & Activation Checkpointing

17.1 Objectives

Decouple the effective batch size from single-GPU memory via gradient accumulation (P5, I3) and activation checkpointing (Chen et al. 2016), enabling batch sizes and model depths that do not fit in one forward's resident activation memory.

17.2 Detailed Implementation Steps

Implement tt.train.accumulate (§8.9, ADR-13): scale each micro-batch's loss by 1/grad_accum_steps before backward(), so gradients summed across accum calls equal the true full-batch gradient (I3, P5) — never accumulate un-scaled gradients into a buffer. Wire tt.model.block's pre-norm blocks through torch.utils.checkpoint.checkpoint (non-reentrant variant, per the DeepSpeed/FSDP reference-impl pitfall, §5) for a configurable subset of layers, trading one extra forward per checkpointed block for O(√L) resident activations (Chen et al. 2016). Wire tt.fault.oom.oom_shrink (P4): on CUDA OOM, halve micro_batch_size while doubling grad_accum_steps to hold the effective batch size constant (I11), checkpoint, and retry the step.

17.3 Deliverable

The same 124M-parameter model that OOMs at micro_batch=32, accum=1 on one A100 trains stably at micro_batch=8, accum=4 with an identical effective batch size and a bit-exact (fp64) gradient to the un-chunked reference.

17.4 Acceptance Criteria

test_accum_equivalence: (batch=32, accum=1) vs. (batch=8, accum=4) parameter updates after one step agree to < 1e-12 max absolute deviation at fp64 (I3). Activation-checkpointed forward+backward for n_layer=24 resident activation memory is ≤ O(√24) ≈ 5× the per-block activation size, not O(24)×. OOM-shrink recovers and completes the interrupted step within ≤ 2× the normal step time.

17.5 Conformance Fixtures

tests/integration/test_accum_equivalence.py | bit-exact-equivalence fixture (I3). tests/integration/test_oom_shrink.py | forced-OOM fixture (via an artificially inflated micro_batch_size on a small GPU) | shrink-and-continue, effective batch size unchanged (I11).

17.6 Pitfalls

Accumulating raw (un-scaled) gradients across micro-batches under bf16 autocast silently produces an update accum× too large — the textbook divergence-by-step-100 bug (§3, P5). Reentrant torch.utils.checkpoint (rather than the non-reentrant variant) double-counts gradients when combined with FSDP in Phase 8 — this reference-impl pitfall (pytorch/pytorch FSDP docs, §5) is why the non-reentrant path is chosen now, before Phase 8 needs it.

17.7 Performance Concerns

Checkpointing trades one extra forward pass (≈ 30% wall-time overhead at typical checkpoint ratios) for memory headroom — quantify per-run via benchmarks/step_time_breakdown.py (§28) and only checkpoint as many blocks as the VRAM ceiling (§4) actually requires.

17.8 Edge Cases

grad_accum_steps=1 (accumulation degenerates to the Phase-0 path, must still pass I3 trivially); OOM recurring at the halved micro-batch size twice consecutively (halt and page an operator, §8.12, FM-3); checkpointing the final block (whose output feeds the loss directly) is unnecessary — the implementation must not checkpoint blocks with no recompute benefit.

17.9 Failure Analysis

An accumulation-scaling bug is silent (no crash, no NaN) and manifests only as divergence by step ~100 — the single reason I3's bit-exact fixture is a release gate, not a soft warning; forensic signal is a smoothed loss curve that inflects upward instead of down within the first few hundred steps.

17.10 Operational Notes

docs/runbooks/oom.md documents the shrink-and-continue behavior for on-call engineers; effective_batch_tokens (I11) is logged every step from this phase forward so a mid-run config change is visible in the JSONL trace.

18. Phase 6 — Checkpointing, Resume & Determinism

18.1 Objectives

Implement atomic sharded checkpointing (ADR-10) and bit-exact resume (P2, I1), the property this blueprint treats as its central contract: a crashed run resumed from its last checkpoint must match an uninterrupted run within fp64 tolerance.

18.2 Detailed Implementation Steps

Implement tt.ckpt.writer.save (§11.4, ADR-10): write model/optimizer tensor shards (one per dp_rank) and a CheckpointMeta header to a temp path, then atomically rename() into place, then fsync the containing directory (I7). Implement tt.train.rng.capture_rng/restore_rng (§11.5, I12): snapshot all five RNG streams — torch-CPU, torch-CUDA (per visible device), numpy, Python random, and the DataPipeline.state_dict() cursor (§13.2). Implement tt.ckpt.retention (P7): retain the last 3 checkpoints, the best-eval-loss checkpoint, and every 10,000-step milestone permanently. Implement tt.ckpt.reader.load and Trainer.resume wiring the restored CheckpointMeta.rng_state back through restore_rng before the first post-resume step.

18.3 Deliverable

tt train --resume <ckpt> reconstructs model, optimizer, scheduler, data- pipeline cursor, and RNG state such that continuing training reproduces an uninterrupted run's trajectory.

18.4 Acceptance Criteria

test_ckpt_resume_bitexact: a run killed at step 11,000 and resumed matches an uninterrupted reference run's parameters at step 12,000 to < 1e-12 max absolute deviation at fp64 (I1). Checkpoint write completes in ≤ 45 s for the 124M-param config (§4 M7). A crash injected mid-write leaves zero partial checkpoints visible to Checkpointer.list() (I7).

18.5 Conformance Fixtures

conformance/corpora/crashed-runs/kill_at_11000.json | truncated-run replay fixture. tests/integration/test_ckpt_resume_bitexact.py | the I1 fixture itself. tests/unit/test_rng_capture.py | round-trip capture/restore identity on all 5 streams (I12).

18.6 Pitfalls

Renaming a checkpoint directory without first fsync-ing its contents leaves a window where a crash produces a directory that looks complete but has unflushed pages — always fsync file descriptors before the rename, and fsync the parent directory after (Kleppmann 2017 Ch. 5's durability discussion, §5). Forgetting to snapshot the data-pipeline cursor (not just model/optimizer state) silently replays already-seen batches after resume, violating I1 in a way no gradient check catches — only a shuffle-hash comparison does. Forgetting per-device CUDA RNG state (only capturing device 0) breaks I1 on multi-GPU resume.

18.7 Performance Concerns

Sharded writes (one file per dp_rank) parallelize the write bandwidth across ranks — write time is bounded by the slowest shard, not the sum; benchmarks/ckpt_write_speed.py (§28) tracks this against the §4 M7 budget.

18.8 Edge Cases

Resume from a checkpoint written by a different dp_world_size (Phase 8 concern, documented but not required to succeed in Phase 6 — reject with a clear error); disk full mid-write (temp file is discarded, retention policy frees the oldest milestone-ineligible checkpoint first); resuming twice from the same checkpoint (idempotent — must not double-advance tokens_seen).

18.9 Failure Analysis

A torn/partial checkpoint read is the single scariest failure mode in this system — detection is the sha256_model/sha256_opt integrity fields in CheckpointMeta (§11.4), checked at load time; recovery falls back to the next-oldest retained checkpoint per the retention policy (P7); forensic artifact is the corrupted file preserved (not deleted) under docs/runbooks/ckpt-corruption.md's procedure.

18.10 Operational Notes

tt ckpt inspect <path> (CLI stub from §10 diag/ckpt_inspect.py) prints CheckpointMeta fields for operator triage. Metrics ckpt_write_ms, resume_param_delta (I1 telemetry) ship from this phase.

19. Phase 7 — Evaluation Harness, Loss-Spike Detection & Recovery

19.1 Objectives

Add held-out perplexity evaluation (P6, observational only) and loss-spike detection with a mandatory diagnostic bundle (P8, I9) — the two control-plane features that make a multi-day run debuggable without re-running it.

19.2 Detailed Implementation Steps

Implement tt.eval.harness.evaluate (§11.6): run the model over a fixed number of held-out batches (eval_max_batches) every eval_every_steps, producing an EvalPoint (§11.5) with eval_loss, eval_ppl = exp(eval_loss), and a small fixed benchmark suite score (P6 — eval never mutates TrainConfig or the optimizer state). Implement the spike detector in tt.log.schema (§11.5, I9, P8): flag LossPoint.spike = True when loss > 3 × rolling_median(window=W), and on a flagged step, capture and persist the offending micro-batch's token ids, the per-sample loss distribution, the pre-clip gradient norm (§15.10), and the largest forward activation magnitude.

19.3 Deliverable

tt eval --checkpoint <path> reports held-out perplexity independent of a live training run; a live run's JSONL log contains a full diagnostic bundle for every spike, retrievable by tt diag loss-replay --step <N>.

19.4 Acceptance Criteria

test_eval_during_train: eval runs at exactly the configured cadence and never alters learning_rate, weight_decay, or any TrainConfig field (P6, asserted by config-hash equality before/after eval). A synthetically injected loss spike (10× the rolling median on one fabricated micro-batch) is flagged and its diagnostic bundle contains all four required fields (I9) in 100% of 500 injected trials.

19.5 Conformance Fixtures

tests/integration/test_eval_during_train.py | non-interference fixture. conformance/corpora/expected/spike_bundle_schema.json | required-fields schema for the diagnostic bundle.

19.6 Pitfalls

Coupling eval loss to any training hyperparameter (even implicitly, e.g. an LR-reduction-on-eval-plateau callback) violates P6 and re-introduces the early-stopping coupling this blueprint explicitly rejects. A rolling-median window too short (e.g. W=5) flags normal step-to-step noise as spikes, producing alert fatigue; too long (W=1000) misses genuine early-training instability — W=20–50 in step-units is the empirically stable range cited in the GPT-3 training-instability retrospectives (Brown et al. 2020 appendix).

19.7 Performance Concerns

Eval must not stall the training pipeline — run it on a bounded number of batches (eval_max_batches), not the full held-out set, and log its own wall-time separately from step time so eval cost is visible, not conflated with a slow training step.

19.8 Edge Cases

A spike on the very first step (no rolling window yet — treat as non-flaggable, log a distinct warmup_spike_suppressed counter instead); back-to-back spikes (each gets its own independent diagnostic bundle, not a deduplicated one); eval shard exhaustion (wrap and reuse, log a eval_shard_wrap counter, never crash).

19.9 Failure Analysis

An unflagged loss spike that later causes divergence is the costliest failure class this system defends against — detection is I9's spike flag; containment is P8's mandatory bundle; recovery is the operator runbook (§24) walking the bundle to identify whether the offender was a data anomaly (bad shard) or a numerical one (missed by I6's NaN gate because the value was large-but-finite).

19.10 Operational Notes

docs/runbooks/loss-spike.md documents the triage procedure: check spike_count trend, pull the bundle via tt diag loss-replay, inspect the offending micro-batch's source shard.

20. Phase 8 — Distributed Training: DDP, FSDP, ZeRO, Tensor/Pipeline Parallelism

20.1 Objectives

Scale beyond single-GPU parameter/optimizer memory: single-node DDP (ADR-21) generalized to FSDP/ZeRO-2 sharding (ADR-24, Rajbhandari et al. 2020), with tensor/pipeline (3D) parallelism documented as the deferred extension point (§8.10, PhaseDeferred("§35")).

20.2 Detailed Implementation Steps

Wrap the model in torch.nn.parallel.DistributedDataParallel for the baseline path (ADR-21) and in torch.distributed.fsdp. FullyShardedDataParallel for the ZeRO-2-equivalent path (ADR-24), sharding optimizer state and gradients (not parameters — that is ZeRO-3/full FSDP, deferred) across the data-parallel group. Compose FSDP with Phase 5's activation checkpointing using the non-reentrant wrapper (§17.6's pre-flagged pitfall, per the pytorch/pytorch FSDP reference-impl lesson, §5). Extend tt.ckpt (§18.2) to shard by dp_rank under FSDP consistent with ADR-10's per-rank-shard format already in place. Document, but do not implement, the tensor-parallel column/row-split (Shoeybi et al. 2019) and pipeline-parallel layer-split extension points as named seams in tt.model.transformer and tt.train.loop respectively.

20.3 Deliverable

The same gpt2_124m.yaml config trains under sharding: ddp and sharding: fsdp_zero2 with matching (within numerical tolerance) loss trajectories, and a documented 350M-parameter config that fits under FSDP/ZeRO-2 but not under plain DDP on the §4 baseline hardware.

20.4 Acceptance Criteria

DDP vs. FSDP/ZeRO-2 loss trajectories over 500 steps agree to ≤ 2% relative deviation (allreduce-vs-reduce-scatter numerical differences are expected but bounded). Peak per-GPU VRAM under FSDP/ZeRO-2 for a 350M model is ≥ 30% lower than under plain DDP at the same micro-batch size. Checkpoint round-trip (save under FSDP, load under FSDP) passes I1's bit-exact-resume fixture.

20.5 Conformance Fixtures

tests/integration/test_ddp_fsdp_parity.py | trajectory-agreement fixture. benchmarks/ VRAM-comparison harness (extends throughput_tokens_per_sec.py, §28) | peak-memory-reduction fixture.

20.6 Pitfalls

Reentrant activation checkpointing under FSDP double-counts gradients on the all-reduce/reduce-scatter boundary — the exact pitfall flagged in §17.6 and documented in the pytorch/pytorch FSDP design notes (§5); using the non-reentrant wrapper from the start avoids re-deriving this. NCCL topology assumptions baked into naive rank-to-GPU mapping silently degrade communication bandwidth on non-NVLink topologies — the Megatron-LM reference-impl pitfall (§5) applies here too, even at data-parallel-only scale.

20.7 Performance Concerns

FSDP/ZeRO-2's reduce-scatter + all-gather communication pattern trades bandwidth for memory — profile with benchmarks/step_time_breakdown.py (§28) to confirm the communication/compute overlap is actually achieved, not merely configured.

20.8 Edge Cases

dp_world_size not evenly dividing the effective batch (validator rejects, I11); resuming an FSDP checkpoint at a different dp_world_size (documented as unsupported in Phase 8, a named row in the Deferred Features Register, §35); mixed GPU generations within one job (unsupported, validator warns).

20.9 Failure Analysis

A rank hang during an all-reduce/all-gather (NCCL timeout) blocks the entire job — detection is a configured NCCL watchdog timeout; containment is per-rank health-check telemetry; recovery is torchrun's process-group restart from the last good checkpoint (§18).

20.10 Operational Notes

docs/runbooks/ gains an implicit NCCL-hang triage path (documented under the existing oom.md pattern); metrics add dp_world_size, fsdp_shard_bytes to the JSONL schema.

21. Phase 9 — Throughput, MFU & Production Hardening

21.1 Objectives

Turn a functionally-correct loop into one with defensible throughput numbers: measure and report Model FLOPs Utilization (MFU), enable torch.compile (ADR-20), and close the remaining operational gaps (sweep launcher, diagnostics CLI, run-comparison tool — P11).

21.2 Detailed Implementation Steps

Implement benchmarks/throughput_tokens_per_sec.py and the MFU calculation (§32): MFU = achieved_FLOPs_per_s / peak_FLOPs_per_s, where achieved_FLOPs_per_s ≈ 6 × params × tokens_per_s (the standard forward+ backward FLOPs-per-token approximation, Kaplan et al. 2020) and peak_FLOPs_per_s is the GPU's advertised bf16 tensor-core peak (312 TFLOP/s for A100). Enable torch.compile(mode='reduce-overhead') by default from this phase (ADR-20), with a config escape hatch (torch_compile: false) for debugging. Implement tt.sweep.grid/tt.sweep.random launchers and tt.diag.ckpt_inspect/tt.diag.loss_replay/tt.diag.grad_trace operator commands (P11, §10 cli/, diag/).

21.3 Deliverable

tt train reports a live MFU percentage in its console/JSONL output; the 124M baseline config sustains the §4-specified throughput and MFU targets on the reference 8×A100 node; tt sweep --grid configs/sweeps/warmup_vs_lr.yaml launches and aggregates a parameter sweep.

21.4 Acceptance Criteria

M1 aggregate throughput ≥ 145,000 tokens/s at seq_len=1024, bf16, 8×A100 (§4). M2 MFU ≥ 38% of A100 bf16 peak (§4). M3 torch. compile warmup ≤ 60 s wall time before steady-state throughput is reached. M4 p50 step time ≤ 220 ms; M5 p99 ≤ 3× p50 (§4). Sweep launcher completes a 12-point grid sweep and produces one EvalPoint-keyed comparison table per point.

21.5 Conformance Fixtures

benchmarks/results/mfu_baseline.json | reference throughput/MFU numbers for the 124M config on 8×A100 | regression gate at ≥ 90% of the recorded baseline in CI's numerics.yml/gpu-smoke.yml (§10). conformance/corpora/ configs/sweep_warmup_vs_lr.yaml | 12-point grid fixture.

21.6 Pitfalls

Measuring throughput before torch.compile's warmup completes reports a misleadingly low number — always exclude the first ~100 compiled steps from the throughput average (§21.2). MFU computed against the advertised peak rather than the achievable peak (accounting for non-matmul overhead) overstates the gap-to-close; report both numbers, never conflate them.

21.7 Performance Concerns

torch.compile's reduce-overhead mode uses CUDA graphs, which are sensitive to dynamic shapes (variable-length eval batches invalidate the graph) — this blueprint pads eval batches to a fixed shape specifically to avoid recompilation stalls, a direct consequence of ADR-17's packing already producing fixed-length (B,T) tensors.

21.8 Edge Cases

A sweep point that OOMs (caught by Phase 5's oom_shrink, logged as a degraded-not-failed sweep result); torch.compile graph-break on an unsupported op (falls back to eager for that region, logged, does not crash the run — torch_compile_mode='default' is the documented debugging fallback per ADR-20).

21.9 Failure Analysis

A throughput regression below the CI gate (§21.5) blocks merge — detection is automatic via gpu-smoke.yml; root-cause triage starts with step_time_breakdown.py (§28) to isolate data-loading, compute, or communication as the regressed stage.

21.10 Operational Notes

The MFU number becomes the headline capacity-planning metric (§29, §32); docs/performance/mfu-methodology.md (§10) documents the exact formula and measurement window so future engineers do not re-derive it inconsistently.

25. Compatibility & Versioning

Checkpoint format: CheckpointMeta.version (§11.4) is an integer, bumped on any incompatible on-disk layout change; tools/ckpt_convert.py (§10) migrates old-version checkpoints forward. Rolling-upgrade guarantees: a checkpoint written by version N.x is loadable by every N.y (y≥x) via ckpt_convert.py if needed; cross-MAJOR loading is unsupported and rejected with a clear error (extends FM-11's hash-mismatch check, §23). 28. Performance Engineering

Methodology follows the USE method (Utilization, Saturation, Errors — Gregg 2020 Ch. 4, §5): for each stage of the pipeline (data-fetch, forward, backward, all-reduce, checkpoint-write) measure utilization of the relevant resource (GPU SM occupancy, NVLink bandwidth, disk IOPS), saturation (queue depth), and error rate, via benchmarks/step_time_breakdown.py (§10). Allocation profiling: torch.cuda.memory._record_memory_history snapshots around the Phase-5 (§17) checkpointed-vs-non-checkpointed forward/backward to quantify the O(√L) vs. O(L) activation-memory claim empirically, not just analytically. Lock/contention analysis: the only cross-rank synchronization points are the gradient all-reduce/reduce-scatter (Phase 8, §20) and the sharded-checkpoint barrier (§18) — both profiled for straggler skew via per-rank timing. Tail-latency analysis: p99 step time (§4, M5) is tracked separately from p50 specifically because eval/checkpoint steps are intentionally slower and must not be conflated with a genuine regression.

29. Scalability Analysis

Constant vs. growing: the per-step control-plane cost (logging, spike-detection bookkeeping) is O(1) in model size; the per-step compute cost is O(params) via the 6×params×tokens FLOPs approximation (§21.2, Kaplan et al. 2020); per-step activation memory is O(L·B·T·d_model) without checkpointing, O(√L·B·T·d_model) with it (§8.9, §17). Named bottlenecks in order: (1) single-GPU compute (until Phase 8's sharding is needed, ≈13B+ params per ADR-24's regime), (2) inter-GPU communication bandwidth (NVLink/ NCCL, once FSDP/ZeRO-2's reduce-scatter volume grows with parameter count), (3) checkpoint-write I/O bandwidth (grows linearly with parameter count, §18), (4) shard-read I/O bandwidth (grows with tokens/s target, §13). Horizontal scaling: data-parallel world size (DDP/FSDP) scales near-linearly in throughput up to the point where all-reduce/reduce-scatter communication time exceeds compute time per step (the M11 bandwidth- utilization target exists to detect this crossover). Vertical scaling: larger d_model/n_layer within one GPU's memory is bounded by §4's VRAM ceiling, extendable via Phase-5 checkpointing (trading compute for memory) and Phase-8 sharding (trading communication for memory). Sharding/ partitioning: ZeRO-2 (Phase 8) shards optimizer state + gradients; ZeRO-3/ full FSDP and Megatron-style tensor/pipeline parallelism (§8.10, §34) shard parameters and activations respectively — both PhaseDeferred("§35") beyond the FSDP/ZeRO-2 baseline this blueprint ships. Coordination overhead: grows with dp_world_size (all-reduce cost) and with pipeline depth if 3D parallelism is later added (pipeline-bubble overhead, Shoeybi et al. 2019). Practical ceiling: ≈13B parameters on the §4 baseline 8×A100 node under FSDP/ZeRO-2 alone (ADR-24's stated regime); beyond that, tensor+pipeline parallelism (§34 Alternative Architectures) is required. Levers beyond the ceiling: multi-node FSDP, tensor parallelism (Megatron-LM, §5), pipeline parallelism, and (deferred, §35) custom fused kernels to shrink the per-token compute cost itself.

30. Mental Models & First Principles

  1. MM1 — The loss is a compass, not a target. A decreasing training loss only confirms the gradient direction is being followed; it says nothing about generalization. Predicts: train/eval loss divergence signals overfitting long before eval perplexity plateaus. Bug class without it: chasing train loss into an overfit model that eval-fails silently. Applies at §19 (P6, eval-is-observational) and §29.
  2. MM2 — Gradient accumulation is arithmetic, not scheduling. Accumulation must reproduce the exact math of a larger batch, not merely "spread work over more steps." Predicts: any un-scaled accumulation diverges by a predictable factor (the accumulation count). Bug class without it: silent LR-scale bugs that look like instability. Applies at §17, I3.
  3. MM3 — The optimizer's memory is a second copy of the model. AdamW's fp32 master weights + two fp32 moments roughly triple the memory footprint of the parameters alone, independent of activation memory. Predicts VRAM budgets that surprise engineers who only counted parameter bytes. Bug class without it: OOM diagnosed as "the model is too big" when it's the optimizer state that doesn't fit. Applies at §4, §11.4, §32.
  4. MM4 — Determinism is a chain, not a single flag. Bit-exact resume requires simultaneously correct shuffle-seeding, RNG capture (5 streams), config hashing, and code-version pinning — any single weak link breaks the whole chain. Predicts partial-determinism efforts (e.g. seeding torch but not numpy) fail silently, only visible on resume. Bug class without it: "works on my resume" flukes that do not reproduce. Applies at §18, I1, I12.
  5. MM5 — Precision and dynamic range are different axes. bf16 trades mantissa bits for fp32-equivalent exponent range; fp16 trades exponent range for mantissa bits. Predicts which failure mode each dtype exhibits under stress (bf16: precision loss in small updates; fp16: gradient underflow to zero). Bug class without it: misdiagnosing an fp16 underflow as a bf16-style precision issue and reaching for the wrong fix. Applies at §16, ADR-09.
  6. MM6 — Checkpointing trades time for space, asymmetrically across depth. Recomputing activations during backward has a fixed per-block cost; the O(√L) checkpoint-count optimum balances this against O(L) activation storage. Predicts diminishing returns from checkpointing more blocks than the optimum. Bug class without it: checkpointing every block and eating ~2× compute for no additional memory benefit past the sweet spot. Applies at §17, Chen et al. 2016.
  7. MM7 — Communication is the tax on parallelism. Every scheme — DDP's all-reduce, ZeRO's reduce-scatter/all-gather, tensor parallelism's per-layer collectives, pipeline parallelism's bubble — is a different way of paying a communication cost for a memory or compute benefit. Predicts the point where adding GPUs stops helping (communication-bound regime). Bug class without it: naively scaling GPU count expecting linear speedup indefinitely. Applies at §20, §29, §34.
  8. MM8 — A loss spike is a symptom, not a diagnosis. The same observable symptom (loss > 3× rolling median) can stem from a corrupted data batch or from genuine numerical instability — the flag alone cannot distinguish them. Predicts that acting on the flag alone (blind restart) fixes nothing if the root cause is a bad shard. Bug class without it: repeated restarts that never address the actual cause. Applies at §19, P8, I9.

32. Back-of-Envelope Capacity Model

All numbers chained from §4's System Constraints table.

  1. Baseline parameter count: 124,439,808 (§4, GPT-2-small).
  2. FLOPs per token (fwd+bwd): 6 × params ≈ 6 × 124.4M ≈ 746.4M FLOPs/token (Kaplan et al. 2020's standard approximation).
  3. Chinchilla-optimal tokens: 20 × params ≈ 20 × 124.4M ≈ 2.49B tokens (Hoffmann et al. 2022, §4's tokens-per-parameter row).
  4. Total training FLOPs: FLOPs/token × tokens ≈ 746.4M × 2.49B ≈ 1.86 × 10^18 FLOPs (1.86 ExaFLOPs).
  5. Effective batch tokens/step: micro_batch(8) × accum(4) × dp_world_size(8) × seq_len(1024) = 262,144 tokens/step (§8.11's worked example, consistent with §4's baseline hardware row).
  6. Steps to reach Chinchilla-optimal tokens: 2.49B / 262,144 ≈ 9,499 steps.
  7. Wall-clock time at the §4/M1 throughput floor: 2.49 × 10^9 tokens / 145,000 tokens/s ≈ 17,172 s ≈ 4.8 hours compute-bound; the §1 "24-hour" timeline budgets a ≈5× margin for startup, eval, checkpoint, and any OOM-shrink/resume overhead (§12, §17, §18).
  8. Optimizer + parameter memory per replica: fp32 master (4B) + two fp32 moments (4B+4B) + bf16 compute copy (2B) = 14 bytes/param × 124.4M ≈ 1.74 GB — small relative to the §4 60 GB/GPU ceiling; the ceiling is dominated by activations, not optimizer state, at this scale (MM3).
  9. Non-checkpointed activation memory estimate: L(12) × B(8) × T(1024) × d_model(768) × const(≈34, transformer-block intermediate multiplier) × 2 bytes(bf16) ≈ 4.8 GB — well under the §4 ceiling at 124M scale, which is why Phase 5's checkpointing is a Phase-8-scale-readiness feature more than a 124M-scale necessity (cross-checked against §17's O(√L) claim).
  10. Gradient all-reduce traffic per GPU per step (DDP): params × 4 bytes(fp32 grad) × 2 (ring all-reduce factor) ≈ 124.4M × 4 × 2 ≈ 995 MB per GPU per step — trivial against NVLink's aggregate bandwidth at this model size, confirming §29's claim that communication is not the bottleneck until the ADR-24 ~13B-parameter regime.
  11. Checkpoint storage footprint: ≈1.74 GB/replica-equivalent shard-set × (3 retained + 1 best + ~1 in-progress milestone) ≈ 8.7 GB typical steady-state disk usage (§18, P7's retention policy).
  12. Sequences per checkpoint interval: ckpt_every_steps(1,000) × 262,144 tokens/step / seq_len(1,024) ≈ 256,000 sequences, i.e. the upper bound on tokens re-computed if a crash occurs just before a checkpoint (P7's ≤10-minute loss budget, §4).

34. Alternative Architectures (Roads Not Taken)

Alt 1 — Full 3D Parallelism from Day 1 (Megatron-style).

[GPU0: TP-shard L1-4] -> [GPU2: TP-shard L5-8] -> [GPU4: TP-shard L9-12]
[GPU1: TP-shard L1-4] -> [GPU3: TP-shard L5-8] -> [GPU5: TP-shard L9-12]
        (tensor-parallel pairs)      (pipeline stages, micro-batched)

Regime where it wins: model sizes at or above Megatron-LM's own operating range (10B–500B+ parameters) where no single node's aggregate GPU memory holds even a ZeRO-2-sharded replica. Real embodying system: Megatron-LM (Shoeybi et al. 2019). Rejected here because at the 8M–1.3B target scale (§4), tensor/pipeline parallelism's engineering cost (pipeline-bubble scheduling, tensor-parallel collective placement) buys nothing FSDP/ZeRO-2 doesn't already provide, per ADR-24's stated regime.

Alt 2 — Functional/JAX Training Loop.

params, opt_state -> pmap(grad_fn) -> pmap(update_fn) -> new params, opt_state
        (pure functions; no in-place mutation; XLA-compiled)

Regime where it wins: TPU-pod-scale training or research requiring nested functional transforms (vmap(grad(vmap(...)))) as a first-class capability. Real embodying system: Google's MaxText/T5X on TPU pods. Rejected here per ADR-01: the PyTorch ecosystem's checkpoint/logging/community-op maturity outweighs JAX's functional cleanliness for a from-scratch, GPU-targeted, 2026-era team.

Alt 3 — CPU/NVMe-Offloaded ZeRO-Infinity.

GPU (compute) <--PCIe--> CPU RAM (opt state) <--NVMe--> Disk (params, cold)

Regime where it wins: extremely large models (100B+) trained on a small GPU count where GPU memory, not throughput, is the binding constraint and some throughput loss is an acceptable trade for training at all. Real embodying system: DeepSpeed ZeRO-Infinity. Rejected here because at 124M– 1.3B scale (§4), GPU memory is not the constraint (§32's 1.74 GB optimizer- memory estimate is a small fraction of the 60 GB ceiling) — offloading would only add PCIe/NVMe latency for no benefit.

Alt 4 — Single-File Monolithic Script (pure nanoGPT).

train.py: [load data][build model][for step: fwd->bwd->step][print loss]

Regime where it wins: single-experiment research iteration where one engineer needs the fastest possible path from idea to loss curve and never needs to resume, distribute, or hand the run to an on-call rotation. Real embodying system: karpathy/nanoGPT itself (§5). Rejected here per P11 (" Operations are the product"): this blueprint's entire control-plane half (checkpointing, fault tolerance, eval, sweeps, diagnostics) exists precisely because production training runs are multi-day, multi-operator efforts that a single script cannot support.

36. Glossary

  • AdamW — Adam with decoupled weight decay (Loshchilov & Hutter 2019); this project's default optimizer (§8.7, ADR-07).
  • Activation checkpointing — discarding intermediate activations and recomputing them during backward to trade compute for memory (§8.9, §17).
  • Autocast — PyTorch's context manager that runs ops in a reduced- precision dtype while keeping reductions in fp32 where needed (§8.8).
  • bf16 (bfloat16) — 16-bit float with fp32's 8-bit exponent and a 7-bit mantissa; this project's default compute dtype (§8.8, ADR-09).
  • Bit-exact resume — the guarantee that a crashed-and-resumed run matches an uninterrupted run to fp64 tolerance (§18, I1, P2).
  • Causal mask — the attention mask preventing position i from attending to positions > i (§8.3).
  • Checkpoint retention policy — the rule keeping the last N checkpoints, the best-eval checkpoint, and periodic milestones (§18, P7).
  • Chinchilla-optimal — the 20-tokens-per-parameter training-data ratio from Hoffmann et al. 2022 (§4, §32).
  • Config hash — a SHA-256 over a TrainConfig's YAML source, embedded in every checkpoint for provenance (§11.1, I8).
  • Cosine-with-warmup schedule — LR ramps linearly during warmup then decays along a cosine curve (§8.7, ADR-08).
  • DDP (DistributedDataParallel) — PyTorch's data-parallel wrapper; every rank holds a full model replica (§8.10, ADR-21).
  • Decoupled weight decay — applying weight decay directly to parameters rather than through the adaptive gradient scale (§8.7).
  • Deterministic shuffle — a shuffle that is a pure function of (seed, epoch) (§8.1, I2, P3).
  • Effective batch size — micro_batch × grad_accum_steps × dp_world_size (§4, §32, I11).
  • Eval harness — the held-out perplexity + benchmark evaluation subsystem, observational only (§19, P6).
  • FSDP (FullyShardedDataParallel) — PyTorch's native parameter/gradient/ optimizer-state sharding wrapper (§8.10, §20, ADR-24).
  • Gradient accumulation — summing loss-scaled gradients over several micro-batches to simulate a larger batch (§8.9, I3, P5).
  • Gradient checkpointing — see Activation checkpointing.
  • Gradient clipping (global-norm) — rescaling the full gradient vector so its L2 norm does not exceed a threshold (§8.6, ADR-12).
  • GQA (Grouped-Query Attention) — sharing key/value projections across groups of query heads (§8.3, §11.1 n_kv_head).
  • IEEE 754 — the floating-point arithmetic standard defining fp32/fp16/ bf16 bit layouts (§5, §16).
  • LayerNorm — mean-and-variance normalization layer; an alternative to RMSNorm (§8.4, ADR-04).
  • Loss spike — a training step whose loss exceeds 3× the rolling median (§19, I9, P8).
  • MFU (Model FLOPs Utilization) — achieved FLOPs/s divided by the GPU's theoretical peak FLOPs/s (§21, §28, §32).
  • Micro-batch — one forward/backward pass's worth of data within an accumulation cycle (§8.9, §11.3).
  • Mixed precision — running forward/backward in a reduced-precision dtype while keeping optimizer state in fp32 (§8.8, I4).
  • NaN gate — the pre-optimizer-step scan that halts on NaN/Inf gradients (§16, I6).
  • NCCL — NVIDIA's Collective Communications Library, the transport for DDP/FSDP collectives (§5, §20, §28).
  • Non-reentrant checkpointing — the torch.utils.checkpoint variant compatible with FSDP without gradient double-counting (§17, §20).
  • Packing (sequence packing) — concatenating multiple documents into one fixed-length training sequence separated by EOS tokens (§8.1, ADR-17).
  • Perplexity — exp(eval_loss), the standard LM evaluation metric (§11.5, §19).
  • Pipeline parallelism — splitting model layers across GPUs and pipelining micro-batches through them (§8.10, §34).
  • Pre-norm — applying normalization before, not after, each sublayer (§8.4, ADR-03).
  • RMSNorm — mean-subtraction-free normalization (Zhang & Sennrich 2019), this project's default norm (§8.4, ADR-04).
  • RNG snapshot — the captured state of all five randomness sources needed for bit-exact resume (§11.5, I12).
  • RoPE (Rotary Position Embedding) — relative-position-preserving rotation of query/key vectors (Su et al. 2021, §8.2, ADR-05).
  • Rolling median — the median loss over a fixed recent window, the baseline for spike detection (§19, I9).
  • Shard catalog — the manifest of .npy token shards with integrity hashes (§8.1, §11.2, ADR-15).
  • SwiGLU — a gated-linear-unit MLP variant (Shazeer 2020), this project's default MLP activation (§8.4, ADR-06).
  • Tensor parallelism — splitting individual matmuls across GPUs within one layer (§8.10, §34, Shoeybi et al. 2019).
  • Tied embeddings — sharing one weight matrix between the token embedding and the output projection (§8.2, ADR-14, I10).
  • torch.compile — PyTorch's graph-compilation API for reduced per-step overhead (§21, ADR-20).
  • Warmup steps — the initial steps during which LR ramps linearly from 0 to its peak value (§8.7, ADR-08).
  • ZeRO (Zero Redundancy Optimizer) — progressive sharding of optimizer state / gradients / parameters across data-parallel ranks (Rajbhandari et al. 2020, §8.10, §20).
