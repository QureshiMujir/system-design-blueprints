Decisions (§9) · 23 ADRs

ADR-01

Frontend source language

Chosen

TypeScript 5.x + ts-morph AST

Rejected

Rust proc-macro frontend; Python (ast module)

When the rejected choice is right

A team standardizing on Python-only ML pipelines, where a Python frontend removes a language boundary entirely (Phase 9 revisits this, §21)

Why: Largest pool of edge/FaaS developers already write TS; ts-morph gives production AST tooling without hand-rolling a parser

ADR-02

Scheduler implementation language

Chosen

Go 1.22

Rejected

Rust; Java + GraalVM native-image

When the rejected choice is right

A team needing zero-GC hard real-time guarantees below 100 µs, where Rust's ownership model removes GC entirely

Why: Single static binary, no GC-pause surprises at the µs decision budget (§4), goroutine model maps directly to per-invocation concurrent feed reads

ADR-03

LIR host representation (Phase 0–1)

Chosen

TypeScript type definitions

Rejected

Rust-defined IR with TS bindings; Protobuf-first schema

When the rejected choice is right

A team needing cross-language schema generation from day one, where Protobuf-first avoids a later migration entirely

Why: Avoids a second toolchain before the IR schema has stabilized empirically; migrate once shape is proven (Phase 2, §14)

ADR-04

Build system (monorepo)

Chosen

Turborepo (TS) + native Go modules

Rejected

Bazel; Nx

When the rejected choice is right

A team already past 50 packages with cross-language build graphs, where Bazel's hermeticity pays for its complexity

Why: Turborepo's caching is sufficient at Phase 0–1 scale and has near-zero config overhead

ADR-05

Dependency policy

Chosen

Pinned exact versions, npm audit/cargo-audit/govulncheck blocking CI gate

Rejected

Floating semver ranges; Renovate auto-merge

When the rejected choice is right

A small internal tool with no reproducibility requirement, where floating ranges reduce maintenance overhead

Why: Byte-deterministic builds (I6) require pinned transitive deps; floating ranges break reproducibility

ADR-06

Provenance storage

Chosen

ClickHouse (append-only, columnar)

Rejected

Postgres with a partitioned table; TimescaleDB

When the rejected choice is right

A tenant with < 10k invocations/month, where Postgres's simpler operational model wins outright

Why: Analytical queries over millions of Invocation rows (cost dashboards, residency audits) need columnar scan performance

ADR-07

Serialization format (LIR on disk / wire)

Chosen

JSON with a versioned schema (Phase 0–1); MessagePack evaluated for Phase 2

Rejected

Protobuf; FlatBuffers

When the rejected choice is right

A high-throughput binary wire protocol between adapters and scheduler at > 100k invocations/sec, where FlatBuffers' zero-copy read wins

Why: JSON keeps the round-trip (I1) human-diffable in CI and code review during rapid schema iteration

ADR-08

Adapter transport protocol

Chosen

HTTPS + provider-native SDK per adapter

Rejected

gRPC uniform transport for all adapters

When the rejected choice is right

Beyond ~15 adapters, where a uniform gRPC contract reduces per-adapter maintenance cost

Why: Providers already expose HTTPS APIs (Wrangler API, AWS SDK v3); a uniform gRPC layer adds a translation tax for no benefit at this adapter count

ADR-09

Scheduler concurrency model

Chosen

One goroutine per in-flight invocation, channel-based feed cache

Rejected

Thread pool with explicit work queue; async/await via a Go 1.22 iterator-based scheduler

When the rejected choice is right

A workload exceeding 10,000 concurrent invocations per process, where a bounded worker pool avoids goroutine-scheduling overhead

Why: Goroutines are cheap enough at the FD/memory budget (§4) that per-invocation isolation costs nothing meaningful

ADR-10

Structured logging

Chosen

zap (Go) / pino (TS), JSON lines

Rejected

logrus; unstructured console.log

When the rejected choice is right

A CLI tool meant only for local human reading, where plain-text logs are more ergonomic

Why: JSON-lines logging is directly queryable by the same tooling that reads provenance rows

ADR-11

Distributed tracing

Chosen

OpenTelemetry (OTLP export)

Rejected

Vendor-specific APM SDK (Datadog, New Relic) direct integration

When the rejected choice is right

A team already fully committed to one APM vendor's proprietary trace format, where direct SDK integration removes a translation layer

Why: Vendor neutrality matches the OSS-core commercial-platform split (compiler/scheduler stay portable)

ADR-12

Metrics

Chosen

Prometheus exposition format

Rejected

StatsD; vendor-proprietary metrics API

When the rejected choice is right

A push-based, very-high-cardinality metrics need, where StatsD's push model reduces scrape-interval staleness

Why: Standard scrape-based metrics integrate with any customer's existing Prometheus/Grafana stack

ADR-13

Testing strategy

Chosen

Property-based tests (fast-check for TS, gopter for Go) + golden-fixture conformance suite

Rejected

Example-based unit tests only

When the rejected choice is right

A UI-heavy component with few pure-function invariants, where example-based tests are cheaper to write and just as effective

Why: LIR round-trip (I1) and decision-function purity (I4) are exactly the class of property a fuzz/property test catches that examples miss

ADR-14

Fuzzing

Chosen

go-fuzz/native Go 1.18+ fuzzing on the LIR deserializer and scheduler decision function

Rejected

AFL++ external harness

When the rejected choice is right

A C/C++ adapter binary in scope, where AFL++'s broader instrumentation support is worth the extra harness

Why: Native Go fuzzing integrates directly into go test, lowering the maintenance bar for a solo-to-small team

ADR-15

CI/CD topology

Chosen

GitHub Actions, per-package matrix build

Rejected

Self-hosted Jenkins; CircleCI

When the rejected choice is right

A team with strict on-prem CI requirements (e.g., export-controlled build artifacts), where self-hosted runners are mandatory

Why: Zero infra to maintain at this team size; matrix builds parallelize the 3-language (TS/Go/adapter) test matrix cleanly

ADR-16

Packaging (frontend/CLI)

Chosen

npm package + standalone binary via pkg/bun build --compile

Rejected

Docker-only distribution

When the rejected choice is right

A pure-container deployment shop with no local CLI usage, where Docker-only distribution is simpler to maintain

Why: Developers expect npm install -g @liquid/cli; a binary-only distribution raises the adoption bar

ADR-17

Packaging (scheduler)

Chosen

Single static Go binary + official Docker image

Rejected

Kubernetes Operator as the only distribution

When the rejected choice is right

A Kubernetes-only enterprise deployment target, where an Operator simplifies lifecycle management enough to justify the extra packaging

Why: The scheduler runs as a sidecar in arbitrary environments (edge worker, VM, mobile-embedded); a binary is the lowest common denominator

ADR-18

Artifact signing

Chosen

sigstore (keyless, OIDC-based)

Rejected

Traditional GPG key management

When the rejected choice is right

An air-gapped environment with no OIDC identity provider reachable, where GPG's offline model is the only option

Why: Keyless signing removes the operational burden of key custody for a small team while remaining independently verifiable

ADR-19

Release versioning

Chosen

SemVer per component (compiler, LIR, scheduler, each adapter independently)

Rejected

Lockstep monorepo versioning (one version for everything)

When the rejected choice is right

A tightly coupled system where components are never deployed independently, where lockstep versioning avoids compatibility-matrix complexity

Why: Backend/adapter churn (P7) must not force a compiler or scheduler version bump

ADR-20

Reproducible builds

Chosen

Deterministic esbuild config (sorted inputs, fixed timestamps) + SLSA-3 provenance

Rejected

Best-effort reproducibility with no attestation

When the rejected choice is right

An internal-only tool with no external supply-chain threat model, where best-effort reproducibility is sufficient

Why: Supply-chain verification (T4, §22) requires a signed, checkable claim, not "should be reproducible"

ADR-21

Time source for feed staleness (I11)

Chosen

Monotonic clock for TTL arithmetic, wall clock only for display/logging

Rejected

Wall clock for both

When the rejected choice is right

A system with no sub-minute timing invariants, where wall-clock-only is simpler and the risk is negligible

Why: Wall-clock adjustments (NTP step, DST) must never corrupt a 60 s TTL comparison

ADR-22

Backpressure (scheduler under adapter feed unavailability)

Chosen

Degrade to last-known-good Plan (I5), never block

Rejected

Block/queue the invocation until the feed responds

When the rejected choice is right

A workload where staleness is unacceptable and blocking briefly is cheaper than a wrong decision, e.g., a hard real-time trading system

Why: A control-plane or adapter hiccup must never become a customer-facing latency spike

ADR-23

Licensing

Chosen

MIT for compiler/LIR/scheduler-library/reference adapters

Rejected

Apache 2.0 across the board; AGPL for the scheduler

When the rejected choice is right

A project whose primary contribution risk is patent trolling from day one, where Apache 2.0's explicit patent grant is worth the extra friction

Why: MIT maximizes adoption for the OSS core; a patent grant is deferred until a commercial layer exists to protect

34. Alternative Architectures (Roads Not Taken)

Alt-1 — Compile-time-pinned backend selection (profile-guided, Terraform-style).

   source --> compiler --(profile @ build time)--> ONE chosen artifact --> deploy

Regime where it wins: a workload whose cost/latency/residency profile is genuinely static for the life of the deployment (e.g., a fixed-region internal batch job). Real system: Terraform/ Pulumi's deploy-time resource selection. Rejected because: provider pricing and latency drift within weeks (§2's core bet), and a compile-time pin cannot react to that drift without a redeploy — defeating the entire re-routing value proposition (§19).

Alt-2 — Fully dynamic JIT backend selection, re-decided per call via speculative profiling.

   source --> interpreter/JIT --(profile each call)--> speculative target --> execute

Regime where it wins: workloads with unknown, highly variable performance characteristics where the cost of a wrong first guess is negligible (GraalVM Truffle's polyglot scripting niche, §31). Rejected because: speculative re-profiling on every call is fundamentally at odds with P4's determinism/replayability requirement — an audit trail built on speculative JIT-driven choices cannot answer "why did this route here" reproducibly (MM3, §30).

Alt-3 — Centralized global scheduler (control-plane-authoritative placement, Kubernetes- style).

   many liquidd sidecars --> central scheduler (etcd-backed) --> placement directive --> sidecar executes

Regime where it wins: a single-cluster, single-operator environment where global bin-packing across many workloads matters more than per-invocation reactivity (Kubernetes' own niche, §31). Rejected because: a central control-plane on the invocation hot path reintroduces exactly the outage/latency risk I5 is designed to eliminate — Liquid's customers span multiple provider accounts with no shared cluster to bin-pack against.

Alt-4 — Interpreter-only runtime (no ahead-of-time compilation to backend-native artifacts).

   source --> LIR --> liquidd interprets LIR directly at every backend, no native codegen

Regime where it wins: an environment where deploy-time compilation cost is prohibitive and interpretation overhead is acceptable relative to the invocation's own cost (rare, low-QPS internal tooling). Rejected because: it would fail the CSP9 gate (M2, §28) catastrophically — every invocation would pay interpretation overhead on top of the provider's own cold start, directly violating P6 (cold start is a first-class, gated metric).
