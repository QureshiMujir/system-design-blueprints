30. Mental Models & First Principles

MM1 — A constraint decorator is a refinement type, not a comment. Predicts: a decorator that cannot be statically checked is worthless the moment it drifts from reality. Bug class without it: treating @latency as documentation, letting it silently rot while the actual deployed behavior diverges. Applied in §8 (Domain Model's effect/constraint type system) and P1 (§6).

MM2 — The IR is the compiler's ABI; stability protects everything downstream. Predicts: every frontend and backend added later inherits LIR's stability guarantee for free, or pays for its absence forever. Bug class without it: an opcode-set free-for-all that makes every new backend a frontend-coupled special case. Applied in §11, §14 (Phase 2), P11 (§6).

MM3 — The decision function is the language's memory-model equivalent: same inputs, same answer, forever. Predicts: any non-determinism in pick_target poisons the entire provenance audit trail, the same way a non-deterministic memory model poisons debugging a concurrent program. Bug class without it: "it worked when I reran it" becomes an acceptable engineering answer. Applied in §7 (I4), §17 (Phase 5).

MM4 — Effects are a static approximation of a dynamic future; soundness requires conservative over-approximation. Predicts: any effect-inference shortcut that under-reports will eventually let a @privacy(no_egress) function leak. Bug class without it: effect inference treated as a best-effort hint rather than a soundness-bearing pass. Applied in §8.3, §13 (Phase 1), P13 (§6).

MM5 — A refusal is a type error deferred to runtime. Predicts: treating refusal as "failure" rather than as the type system doing its job late leads engineers to paper over it with retries or fallbacks that violate P9. Bug class without it: silent degradation dressed up as resilience. Applied in §8.4 (scheduler state table), P9 (§6).

MM6 — The adapter is a foreign-function interface into an untrusted execution environment. Predicts: any code that treats an adapter response as trusted without the two-verb/three-feed contract's discipline reopens the exact trust boundary the contract exists to close. Bug class without it: ad hoc provider-specific calls scattered outside the adapter layer. Applied in §11, P12 (§6), Threat Model T1 (§22).

MM7 — Compute-adaptivity is scheduling wearing a type system's clothes. Predicts: the same rigor that makes a type system sound (progress + preservation) is exactly what makes a scheduling decision trustworthy (purity + replayability); the two are the same discipline applied to different runtime questions. Bug class without it: treating the scheduler as "just" an operational concern separate from the language's semantics. Applied in §8, §17, MM3 above.

MM8 — Provenance is the language's stack trace for economic and legal accountability. Predicts: every "why did this cost $X" or "prove this ran in the EU" question must be answerable from a single logged row, the same way a stack trace answers "why did this crash." Bug class without it: an audit trail that requires cross-referencing multiple systems to reconstruct a single decision. Applied in §8.5 (Invocation schema), §24 (Operational Readiness).

MM9 — Backend churn should be invisible to the frontend, and frontend churn invisible to the backend. Predicts: the moment either side needs to know about the other's internals to add a feature, the IR boundary has failed at its one job. Bug class without it: a "just this once" special case that couples a specific frontend construct to a specific backend's codegen. Applied in P7 (§6), §20 (Phase 8), §21 (Phase 9).

Required reading (§5)

Books

  • Benjamin C. Pierce, Types and Programming Languages (MIT Press, 2002) — ch. 15 (Subtyping) and ch. 5 (The Simply Typed Lambda-Calculus): the type-soundness vocabulary (progress + preservation) applied to LIR's type system. Applied in §8 (Domain Model), §14 (Phase 2 — LIR Type System).
  • Aho, Lam, Sethi, Ullman, Compilers: Principles, Techniques, and Tools, 2nd ed. (Pearson, 2006) — ch. 6 (Intermediate-Code Generation) and ch. 8 (Code Generation): canonical three-address-code IR design, directly informing LIR's flat opcode sequence. Applied in §8, §11, §13 (Phase 1 frontend lowering).
  • Andrew W. Appel, Modern Compiler Implementation in ML (Cambridge University Press, 1998) — ch. 7 (Assembly Language) and ch. 19 (Functional Programming Languages, closures): informs LIR's CALL/AWAIT opcode pair and closure-free calling convention. Applied in §14 (Phase 2), §15 (Phase 3 — CFW backend).
  • Robert Harper, Practical Foundations for Programming Languages, 2nd ed. (Cambridge University Press, 2016) — ch. 28 (Control Stacks and Closures) and ch. 30 (Concurrent Algol, effects): grounds the effect-set formalism (network, gpu, crypto, tenant_data) used by LIR's effect inference. Applied in §8, §14.
  • Martin Kleppmann, Designing Data-Intensive Applications (O'Reilly, 2017) — ch. 8 (The Trouble with Distributed Systems) and ch. 9 (Consistency and Consensus): the determinism/replayability argument for pick_target and the append-only provenance design. Applied in §17 (Phase 5 — Scheduler Core), §7 (I4, I9).
  • Robert Nystrom, Crafting Interpreters (Genever Benning, 2021) — ch. 6–9 (parsing expressions/statements) and ch. 17 (Compiling Expressions): practical AST-to-bytecode lowering technique reused for the TS-AST-to-LIR lowering pass. Applied in §13 (Phase 1).

Papers

  • Jeremy G. Siek & Walid Taha, "Gradual Typing for Functional Languages," Scheme and Functional Programming Workshop, 2006 — the gradual-typing discipline behind allowing a Liquid function to declare a subset of constraints while remaining fully checkable. Applied in §8 (Domain Model — Type System), §14 (Phase 2), P13/P14 (§6).
  • Adrian Sampson, Werner Dietl, Emily Fortuna, Danushen Gnanapragasam, Luis Ceze, Dan Grossman, "EnerJ: Approximate Data Types for Safe and General Low-Power Computation," PLDI 2011 — the approximate/adaptive-computing type-annotation model (@approx-style qualifiers) that inspired treating @hardware/@cost as type-level qualifiers rather than runtime flags. Applied in §8, §6 (P1).
  • Martin Rinard, "Probabilistic Accuracy Bounds for Fault-Tolerant Computations that Discard Tasks," ICS 2006 — foundational adaptive/approximate-computing argument that a system may trade strict correctness for a bounded, quantified degradation; informs the soft severity constraint class (§8.2, §11). Applied in §8, §14 (Phase 2 — soft-constraint semantics).
  • Chris Lattner & Vikram Adve, "LLVM: A Compilation Framework for Lifelong Program Analysis & Transformation," CGO 2004 — the case for a small, stable, versioned IR sitting between many frontends and many backends; the direct architectural precedent for LIR. Applied in §11, §14, ADR-05 (§9).
  • Chris Lattner, Mehdi Amini, et al., "MLIR: A Compiler Infrastructure for the End of Moore's Law," CGO 2021 — multi-dialect IR design for heterogeneous hardware targets; informs how LIR's opcode set stays backend-agnostic across CPU/GPU/WASM. Applied in §20 (Phase 8 — GPU & On-Device Backends).
  • Andreas Haas et al., "Bringing the Web up to Speed with WebAssembly," PLDI 2017 — the WASM design constraints (determinism, sandboxing, small validated instruction set) that the browser-WASM backend must respect. Applied in §16 (Phase 4... browser target folded into §20), §20.
  • Abhishek Verma, Luis Pedrosa, Madhukar Korupolu, David Oppenheimer, Eric Tune, John Wilkes, "Large-Scale Cluster Management at Google with Borg," EuroSys 2015 — constraint- based placement at scale; the comparison point for why Liquid's scheduler is per-invocation, not per-deploy, placement. Applied in §31 (Comparative Architecture), §17 (Phase 5).
  • Diego Ongaro & John Ousterhout, "In Search of an Understandable Consensus Algorithm (Raft)," USENIX ATC 2014 — the determinism/replay-from-log argument reused for making pick_target reproducible from its logged inputs. Applied in §17 (Phase 5), I4 (§7).

Reference Implementations

  • rustc (rust-lang/rust, compiler/rustc_middle/src/mir/) — MIR's flat, typed, basic-block IR design; the lesson: keep the IR smaller than the surface language so backends never see sugar. Pitfall not to copy: MIR's borrow-checker coupling — LIR must stay effect-typed, not ownership-typed. Applied in §11, §14.
  • Swift compiler (swiftlang/swift, lib/SIL/) — SIL's ownership/effect annotations on IR instructions; the lesson: attach effect metadata directly to IR ops, not to a side table. Pitfall: SIL's dual "raw" and "canonical" stages add real complexity — LIR stays single-stage through Phase 2. Applied in §8, §14.
  • Go compiler (golang/go, src/cmd/compile/internal/ssa/) — SSA-form IR with a small, fixed opcode table per architecture; the lesson: one opcode table per backend keeps codegen passes independent. Applied in §15, §16 (backend codegen passes).
  • MLIR (llvm/llvm-project, mlir/include/mlir/Dialect/) — the dialect-registration pattern for adding a new backend's operations without touching the core IR; directly reused for adding the GPU/WASM/mobile backends in Phase 8 without a LIR major bump. Applied in §20.
  • GraalVM Truffle (oracle/graal, truffle/src/com.oracle.truffle.api/) — partial evaluation and polyglot dispatch across language runtimes on one VM; the lesson: a single dispatch point for "which implementation runs this node" is exactly pick_target's role. Pitfall not to copy: Truffle's JIT-compiles the dispatch itself, which Liquid deliberately avoids (P4 — determinism over speculative optimization). Applied in §17, §31.
  • Apache TVM (apache/tvm, src/relay/backend/) — multi-backend auto-tuned codegen for one tensor program across CPU/GPU/accelerators; the lesson: a cost model per (op, target) pair driving backend selection is structurally identical to Liquid's cost-feed-driven pick_target. Applied in §20, §31.

CALL

Composition (constraint)
the conjunctive combination of multiple decorators on one function (§8.1).

Deployment Handle
opaque, adapter-defined reference to a live deployment (§11).
Effect
a typed side-effect category (network, gpu, crypto, tenant_data) (§8.3).

the compiler pass computing a function's effect set, sound by conservative over-approximation (I8, P13).

the smart-contract backend emitting EVM-compatible bytecode (§21).

Gradual Typing
a type discipline permitting partial static annotation (Siek & Taha 2006, §5); the basis for P14's incremental-adoption principle.
Hard Constraint
a LirConstraint whose violation triggers refusal, not degradation (§8.2, P9).
Invocation
one call via liquid(fn, args); also the append-only provenance row recording it (§8.5, §11).
LatencyFeed
live per-adapter latency observation, p50/p95/p99 (§11).
LIR
Liquid Intermediate Representation; the typed, serializable IR between frontends and backends (§8, §11).
liquidc
the Liquid compiler CLI (§10).
liquidd

LirConstraint

LirOp
a single opcode in a LirFunction.body sequence (§11).
LOAD / STORE
LIR opcodes for variable read/write (§11).

Smart-Contract Target

Soft Constraint

Substrate

Target

Tenant

Tenant Quota

TTL Cache
the scheduler's feed-freshness cache, bounding staleness at 60 s (I11).
Verifier
the standalone LIR type-soundness checker (liquidc verify) (§14).
WASM (WebAssembly)
the portable, validated instruction-set target for the browser backend (§20, Haas et al. 2017).
