1. Goal & Scope

Liquid is a compute-adaptive programming language: a source language, a typed intermediate representation (LIR), a multi-target ahead-of-time compiler, and a runtime scheduler that routes every function invocation to the execution substrate — edge worker, cloud FaaS, browser WASM, GPU node, or on-device runtime — that currently best satisfies the function's declared constraints. A function is written once in TypeScript (Phase 1 frontend), annotated with constraint decorators (@latency, @cost, @privacy, @throughput, @hardware), and compiled to LIR. LIR lowers to N backend artifacts. At call time the Runtime Scheduler (liquidd, Go) — not the compiler — decides which artifact to invoke, using live cost and latency feeds, a residency policy, and a per-tenant spend quota. The novelty is not the backends (each substrate already has native tooling) — it is that the substrate choice is a runtime decision made by a typed, deterministic decision function, not a deploy-time or write-time choice.

Phase-0 deliverable — numbered modules:

  1. compiler/lir/ — the LIR type definitions, opcode set, and serializer (round-trip identity).
  2. compiler/frontend-ts/ — TypeScript AST analyzer, decorator extraction, effect inference.
  3. compiler/backends/cloudflare-workers/ and compiler/backends/aws-lambda/ — LIR lowering to two concrete targets.
  4. scheduler/ — the Go pick_target decision function and its unit-test harness (no live feeds yet; fixture-driven).
  5. adapters/cloudflare-workers/ and adapters/aws-lambda/ — the two reference Provider Adapters.
  6. conformance/ — the fixture corpus (valid, malformed, and refusal-path LIR + decisions).
  7. bench/ — the Phase-0 three-workload benchmark harness (§12, Phase 0).

System boundaries.

  • Provides: a typed source language + constraint vocabulary; a stable IR; a scheduler decision function; a provider adapter contract; per-invocation provenance.
  • Delegates: actual code execution (to the provider — Cloudflare, AWS, the browser, a GPU cloud, a mobile OS); actual billing (to the provider); actual network transport (to the adapter's HTTP/RPC client).
  • Does NOT provide: hosting of customer code, a competing FaaS runtime, a general infrastructure-as-code replacement, a workflow orchestrator spanning multiple functions.

Non-goals: Liquid does not become a cloud. Liquid does not persist customer payloads. Liquid is not a build tool for entire applications — it compiles one constraint-annotated function at a time into a LiquidFunction unit (§8.3, §11).

Deployment model: the compiler (liquidc) and adapters run in the developer's CI/build environment; the scheduler (liquidd) runs as a sidecar or embedded library inside the customer's own execution environment (never a Liquid-hosted control plane on the invocation hot path — see I5, §7). Target users: backend/platform engineers who currently hand-split a TypeScript service across an edge runtime and a cloud FaaS runtime and maintain the split by hand. Operators: whoever runs the customer's CI and holds the customer's provider credentials.

Language + rationale: TypeScript for the source language and compiler frontend (largest pool of edge/FaaS-adjacent developers already write TypeScript against Workers and Lambda; ts-morph gives a production-grade TS AST without hand-rolling a parser) and Go for the runtime scheduler (single static binary, no GC pause profile surprises at the microsecond decision budget of §4, trivial cross-compilation to the sidecar's target OS). Rejected: Rust for the scheduler (memory-safety benefit is real but iteration speed in Phase 0–1 with a single engineer matters more, and Go's goroutine model maps directly onto per-invocation concurrent feed reads); a Rust-defined LIR from day one (deferred to Phase 2, PhaseDeferred §21.2, once the TypeScript-authored IR schema has stabilized empirically); Python for the frontend (weaker static AST tooling than ts-morph, and the beachhead audience writes TypeScript, not Python).

Prerequisites (systems knowledge required): compiler front-to-back pipeline design (lexer/parser/AST/typed IR/codegen), gradual and effect type systems, distributed scheduling and admission control, WebAssembly and native code generation, cryptographic signing/receipts, and provider-specific execution models (V8 isolates, Lambda's Firecracker microVMs).

Timeline: Phase 0 (repo skeleton + correctness kernel) — 4 weeks. Full system through Phase 9 (multi-language frontends + smart-contract targets) — approximately 26 months across 10 phases (§12–§21).

Deferred features (this phase 0–1 scope defers, full registry at §35): PhaseDeferred("§21") multi-language frontends (Python, Go) and smart-contract targets; PhaseDeferred("§20") GPU node and on-device backends and cross-substrate battery/network-aware sharding; PhaseDeferred("§19") cryptographically signed residency receipts and live cost-feed re-routing (Phase 0–1 use static, adapter-reported feeds only, §12 Phase 0 anti-goals).

2. Why Build This

Liquid teaches the systems knowledge that sits at the intersection of three fields usually kept separate: compiler construction (frontend, typed IR, multi-backend codegen), distributed scheduling (admission control, live cost/latency-aware placement), and language design for non-functional properties (encoding latency, cost, privacy, and hardware affinity as first-class, checkable constraints rather than deployment YAML). Historically, non-functional requirements have been bolted on outside the type system — Kubernetes resource requests, cloud IaC tags, CDN cache-control headers — leaving the compiler blind to them. Liquid's bet is that treating these requirements as effect-typed constraints (MM1, §30) checked at compile time and enforced at runtime by a pure decision function is a better position on the design-space frontier than either pure static placement (Terraform-style) or pure dynamic JIT placement (GraalVM-Truffle-style) — see Alternative Architectures, §34.

Sibling systems: Apache TVM (auto-tuned multi-backend codegen for one program, §31), Kubernetes' scheduler (constraint-based placement, but no type system), Erlang/BEAM (runtime location transparency, no cost awareness), WebAssembly + WASI (portable execution, no constraint vocabulary at all). Liquid sits in the gap: type-checked constraints, at the level of a single function, re-evaluated on every call.

Calibration value: building Liquid forces precision about what a "decision" even is in a language runtime — is it a memory-model guarantee (MM3), a refinement type discharged late (MM5), or an FFI boundary crossing into an adversarial environment (MM6)? Answering that well is the same discipline that underlies designing a borrow checker, a consensus protocol, or a JIT tier-up heuristic.

What Mastery Looks Like (after completing every phase, the reader/builder can):

  • Design and justify a small, stable opcode set for a typed IR that must survive a decade of backend churn without a major version bump — demonstrated in Phase 0 (§12) and Phase 2 (§14).
  • Explain why a scheduling decision function must be pure and replay-reproducible from logged inputs, and implement one that is — demonstrated in Phase 5 (§17).
  • Reason about gradual/effect type soundness well enough to prove a conservative over-approximation never silently under-reports a side effect — demonstrated in Phase 2 (§14).
  • Design a provider trust boundary (the adapter contract) that survives a compromised or lying third party without compromising the invoking tenant — demonstrated in Phase 6 (§18) and the Threat Model (§22).
  • Build a cryptographic provenance chain (signed residency receipts) sufficient to answer a regulator's "prove this ran in the EU" — demonstrated in Phase 7 (§19).
  • Extend a single-source-language compiler into a multi-frontend, multi-backend system without breaking IR stability guarantees — demonstrated in Phase 9 (§21).
  • Derive, not assert, every capacity number governing a system from first principles — demonstrated by the Back-of-Envelope Capacity Model (§32).

Per-box notes. Compiler Frontend — pure TS source -> LIR; no network, no side effects, byte-deterministic (I6). LIR — the single throat to choke for every backend and every tooling consumer; versioned per §25. Backends — pure LIR -> artifact; each an independently versioned package so backend churn never forces a frontend recompile (P7). Provider Adapters — the only code that crosses the trust boundary into a third-party, potentially adversarial execution environment (MM6); exactly two verbs (deploy, invoke) plus three feeds (§11). Runtime Scheduler — the brain; a pure function of five inputs producing route or refuse (I4); runs inside the customer's environment, never a Liquid-hosted hot path (I5, avoids the control-plane-outage failure mode of FM-9, §23). Observability Plane — append-only; every routing decision becomes one Invocation row (§8.5), the audit substrate for every "why did this go to Lambda" and every regulator residency query.

4. System Constraints

Dimension Constraint Rationale
Scheduler decision latency (p50) ≤ 1 ms Decision must not itself become the tail-latency budget's dominant term (see M1, §28).
Scheduler decision latency (p99) ≤ 8 ms Bounds worst-case overhead when cost/latency feeds require a cache miss + revalidation.
Cost/latency feed staleness ≤ 60 s TTL (I11) Matches provider billing-meter granularity; tighter TTLs buy nothing, provider prices do not move sub-minute.
Max concurrent in-flight invocations per liquidd process 10,000 Bounds goroutine + FD footprint on a single sidecar instance (FD budget below).
FD budget per liquidd process 4,096 (ulimit default) 2 FDs/adapter connection × 3 default adapters × pooled connections + feed-poll sockets, headroom to 4,096.
Scheduler process memory ceiling 256 MiB RSS Sidecar must not compete meaningfully with the customer's own workload for memory.
LIR module size (typical) ≤ 64 KiB serialized One function + effects + constraints; keeps liquidc output diffable and fast to round-trip in CI.
Cold-start p99 (CSP9) vs. hand-tuned single-backend baseline ≤ 1.5× (Phase 1) → ≤ 1.1× (Phase 3) Liquid must not tax the invocation it is meant to optimize (M2, §28).
Adapter poll interval (cost/latency feed refresh) 10 s per adapter Matches the reference adapters' rolling-probe interval (§12 Phase 0).
Residency-violation count (RVC) 0, always Hard invariant (I2); a violation is a Sev-1 regardless of scale.
Provenance write success rate ≥ 99.99% Below this, the audit substrate cannot answer a regulator query with confidence (§26).
Compiler build time (single function, cold) ≤ 2 s Keeps liquidc check usable in a pre-commit hook.
LIR round-trip (serialize→deserialize) byte-identical, 100% of fixtures I1; any drift is an automatic compiler regression.
Network RTT assumption (adapter ↔ provider) 5 ms (same-region) – 150 ms (cross-region probe) Bounds the latency-feed's own measurement noise floor.
Availability budget (scheduler decision path) 99.9% (43m/month error budget) Scheduler degrades to last-known-good Plan rather than halting (I5, FM-9).
RTO for a poisoned/quarantined adapter ≤ 5 min (canary-probe cadence) Bounds blast radius of T1/T3 (§22).

The one defining property: the scheduler's routing decision is a pure, replayable function of logged inputs (I4) — every other constraint above exists to keep that property cheap enough to hold on every single invocation.

6. Design Principles

P1 — Constraints are effect-typed, not comments. A decorator (@latency, @cost, …) is a type-level qualifier checked by the compiler's effect inference pass (§8), not documentation. Tradeoff: authors cannot use arbitrary runtime logic to compute a constraint value — it must be statically expressible. Operational implication: liquidc check catches a malformed constraint before deploy, not at first invocation. Violating it breaks: an unchecked decorator silently degrades to a no-op, and the scheduler has no basis for a decision (EnerJ, Sampson et al. 2011, §5).

P2 — Compile-time is provisional; runtime is authoritative. The compiler may emit artifacts for every registered backend; no build embeds a default target. Tradeoff: every deploy produces N artifacts even if only one is ever invoked, costing build time and registry storage. Operational implication: a deploy is idempotent per backend; a routing change never requires a redeploy. Violating it breaks: baking in a default backend re-creates the exact lock-in Liquid exists to remove (§2).

P3 — In-region means in-region. @privacy(in_region(...)) is a hard refusal contract (I2). Tradeoff: a tenant with no eligible in-region target gets an error, never a degraded-but-working invocation. Operational implication: residency-violation count (RVC) is paged at first nonzero, not sampled. Violating it breaks: the entire regulated-industry beachhead (§2) collapses the moment one payload crosses a border undetected.

P4 — The decision function is pure and deterministic (I4). pick_target produces the same output given the same five inputs, every time, on every machine. Tradeoff: no randomized load-balancing jitter, no ML-model-driven placement (yet) — every choice must be hand-auditable. Operational implication: any routing decision is reproducible from its logged inputs (Raft's replay argument, Ongaro & Ousterhout 2014, §5) — no "it worked when I reran it." Violating it breaks: a non-reproducible decision makes the provenance record (§8.5) useless for audit or debugging.

P5 — No silent runaway spend. @cost(max_per_tenant_per_minute) is enforced in the scheduler, never trusted to the cost feed alone (T3, §22). Tradeoff: a tenant near its ceiling sees refusals under legitimate burst load. Operational implication: the ceiling check runs before the feed lookup, not after. Violating it breaks: a compromised or lagging feed becomes an unbounded billing exposure.

P6 — Cold start is a first-class, gated metric (CSP9). Liquid may be slower than the fastest hand-tuned single-backend build; it may never be slower than the typical one. Tradeoff: backend codegen (§15, §16) budgets engineering time on bundle-size and warm-path optimization before feature breadth. Operational implication: CSP9 gates every release (M2, §28). Violating it breaks: a language whose runtime tax exceeds the value of its routing decision has no reason to exist.

P7 — Backend independence. Each backend is LIR -> artifact, an independently versioned package; backend churn never forces a frontend or LIR recompile. Tradeoff: backend authors must track LIR's opcode set even when they only care about one target. Operational implication: adding backend #7 (Phase 8, §20) touches zero frontend code (MLIR's dialect pattern, Lattner et al. 2021, §5). Violating it breaks: a monolithic compiler where every new target requires a frontend release recreates the coupling LLVM was built to remove.

P8 — No provider identity in source. A Liquid function's source never names a provider. Tradeoff: provider-specific optimizations (e.g., Cloudflare Durable Objects) are expressed as capability hints (@hardware), not direct API calls. Operational implication: the same source recompiles to a newly added backend with zero source changes. Violating it breaks: naming a provider in source is the lock-in Liquid is built to remove (§2).

P9 — Refusal over degradation. Every hard-constraint violation is a typed refusal (RefusalCode), never a silent fallback. Tradeoff: a caller must handle the refusal path explicitly; there is no "best effort" mode for hard constraints. Operational implication: refusal correctness rate is tracked at 100% — every refusal must be reproducible from logged inputs (§16.3). Violating it breaks: silent degradation is indistinguishable from a bug until a regulator or a bill surfaces it.

P10 — Byte-deterministic compilation. compile(source) -> artifact is reproducible bit-for- bit given the same compiler version and LIR (I6). Tradeoff: nondeterministic codegen optimizations (e.g., hash-map iteration order in a bundler) must be explicitly seeded or sorted. Operational implication: a customer can independently rebuild and hash-compare any artifact (SLSA provenance, §27). Violating it breaks: supply-chain verification (T4, §22) has nothing to check against.

P11 — Small, stable opcode set. LIR's opcode table changes only on a major version bump (I13). Tradeoff: some backend-specific operations must be expressed as composed sequences of existing opcodes rather than a dedicated opcode. Operational implication: new opcodes go through an RFC process (R15 risk register precedent) before landing. Violating it breaks: an opcode set that grows unchecked becomes as unstable as the surface language it was meant to abstract (LLVM's stability lesson, Lattner & Adve 2004, §5).

P12 — The adapter is the sole trust boundary into third-party infrastructure. Every crossing into a provider's execution environment goes through the two-verb, three-feed adapter contract (§11), never an ad hoc call from the compiler or scheduler core. Tradeoff: every new provider capability requires an adapter change, not a scheduler change. Operational implication: the scheduler's trusted computing base excludes all provider code (MM6, §30). Violating it breaks: a scheduler that calls providers directly cannot be reasoned about under T1 (malicious provider, §22).

P13 — Effect inference is sound by conservative over-approximation. The compiler's inferred effect set for a function is always a superset of its true runtime effects, never a subset (I8). Tradeoff: some functions are over-tagged (e.g., marked network when the call is provably dead code) and lose eligibility for a stricter target. Operational implication: a missing effect tag is a compiler bug, not a runtime surprise (Siek & Taha 2006 gradual-typing soundness argument, §5). Violating it breaks: an under-approximated effect set lets a @privacy(no_egress) function silently perform network I/O.

P14 — Gradual, incremental adoption. A function may declare a strict subset of the five constraint decorators; absent decorators are unconstrained, never defaulted to a hidden value. Tradeoff: two functions with different declared subsets are not directly comparable by the scheduler without normalizing the absent dimensions to "unconstrained." Operational implication: adoption does not require an all-or-nothing rewrite (the gradual-typing adoption argument, Siek & Taha 2006, §5). Violating it breaks: forcing all five decorators on day one raises the adoption bar high enough to kill the beachhead (§2).

Debugging methodology. 8. Domain Model

Liquid's domain model spans four layers: the surface grammar (constraint decorators over TypeScript), the AST, LIR's type system and effect algebra, and the scheduler's state transitions. RFC 2119 keywords are normative throughout.

8.1 Surface Grammar (EBNF, constraint decorators only — the host grammar is TypeScript's)

constraint_decorator = "@latency" "(" latency_args ")"
                      | "@cost"    "(" cost_args ")"
                      | "@privacy" "(" privacy_args ")"
                      | "@throughput" "(" throughput_args ")"
                      | "@hardware" "(" hardware_args ")" ;

latency_args    = "budget" ":" duration [ "," "percentile" ":" percentile ] ;
percentile      = "P50" | "P95" | "P99" ;
cost_args       = [ "max_per_call" ":" usd ]
                  [ "," "max_per_tenant_per_minute" ":" usd ] ;
privacy_args    = [ "in_region" ":" region_tag ]
                  [ "," "no_egress" ":" boolean ]
                  [ "," "classification" ":" classification ] ;
classification  = "\"public\"" | "\"internal\"" | "\"pii\"" | "\"phi\"" ;
throughput_args = [ "rps" ":" number ] [ "," "burst" ":" number ] ;
hardware_args   = [ "prefers" ":" hw_kind ] [ "," "min_memory_mb" ":" number ] ;
hw_kind         = "\"cpu\"" | "\"gpu\"" | "\"tpu\"" | "\"wasm\"" ;
duration        = number, ( "ms" | "s" ) ;
usd             = number ;
region_tag      = "\"" iso_region "\"" ;

Composition is conjunctive (P14): a liquid_function carries zero or more constraint decorators; absent decorators are unconstrained, never defaulted.

8.2 AST → LIR Lowering (state table)

AST Node LIR Construct Notes
Decorated FunctionDeclaration one LirFunction in the enclosing Module Function identity is a content hash of its normalized AST (function_id, §11)
@latency/@cost/@privacy/@throughput/@hardware decorator one LirConstraint each, appended to LirFunction.constraints Order-independent; conjunctive composition (§8.1)
await expr AWAIT opcode Preserves suspension points for backend async lowering
fetch(...), any network call EFFECT_NETWORK opcode + effect tag Effect inference is conservative-superset (I8, P13)
crypto.subtle.* call EFFECT_CRYPTO opcode + effect tag —
conditional (if/? :) BRANCH opcode Flat control-flow representation, no nested block structure in LIR
return expr RETURN opcode Terminates the enclosing LirFunction.body sequence
variable read/write LOAD/STORE opcode Scoped to the function; LIR has no global mutable state
function call to another Liquid function CALL opcode Cross-function calls compile to a scheduler-mediated liquid() invocation, not an inlined call

8.3 Effect & Constraint Type System

LIR's type system is gradual (Siek & Taha 2006, §5): a LirConstraint is a refinement on a function's admissible execution targets, not a value type. The judgment Γ ⊢ f : τ ! ε reads "under context Γ, function f has value type τ and effect set ε." Soundness requirement (I8, P13): the compiler-inferred ε is always a superset of f's true runtime effect set. A hard LirConstraint narrows the admissible-target set at schedule time to exactly those adapters whose advertised capabilities satisfy it; a soft one narrows preference only, and its violation is recorded (not refused).

8.4 Scheduler Decision State Table

State Trigger Transition Emits

Filtered candidate set non-empty Rank by soft-constraint preference + cost/latency feed → Ranked —

Ranked top candidate fails cost ceiling → Refusing RefusalCode = LiquidCostCeilingExceeded

8.5 Worked Example

Source: a function computeRecommendation tagged @latency(budget: 50ms, percentile: P95), @privacy(in_region: "eu"). Candidates: cloudflare-workers (eu-west, p95 = 30 ms, advertises in_region("eu")), aws-lambda (us-east only). Filtering by @privacy eliminates aws-lambda immediately (P3/I2) — it never reaches the latency comparison. cloudflare- workers passes the latency filter (30 ms ≤ 50 ms). Decision: route → cloudflare-workers, eu-west. Provenance row records both feed snapshots and the residency policy id used, so the decision is replayable (I4).

8.6 Malformed-Input Example

Source declares @latency(budget: -10ms). liquidc check rejects at compile time: LiquidCompileError: latency budget must be a positive duration (got -10ms), citing the grammar production duration = number, ("ms"|"s") (§8.1) where number is constrained non-negative by the decorator's declared parameter type. The function never reaches LIR emission (P1 — checked at compile time, not deploy time).

8.7 Failure-Path Example

Source declares @latency(budget: 1ms) and @privacy(in_region: "eu"); the only eu-region adapter's advertised p95 is 40 ms. Filtered state yields a non-empty candidate set (region matches) but Ranked finds no candidate meeting the 1 ms budget. Per §8.1's @latency grammar (soft-severity default, cross-referenced at §8.3), the scheduler MUST attempt the lowest-latency eligible target and emit latency_budget_missed as a soft provenance flag — this is the one case where a hard region filter combines with a soft latency miss rather than a hard refusal, because @latency without an explicit severity: hard on the constraint record (§8.2, Constraint schema in §11) defaults to advisory. Contrast with §8.6/§8.7's sibling: an unsatisfiable hard constraint (e.g., @privacy with zero eligible regions) instead transitions to Refusing per §8.4.

11. Core Schema & Types

All load-bearing types as signatures only (no-code rule, §4 of the standard). Ownership, mutation, concurrency, persistence, serialization, and compatibility annotations are terse and inline.

// LirModule — owned by the compiler; immutable after emission; serialized to JSON (ADR-07)
type LirModule = {
  module_id: string;          // content hash of normalized source; immutable
  lir_version: SemVer;        // compatibility gate, I13
  functions: LirFunction[];   // 1..n; append-only within a module
  dependencies: LirDep[];     // normalized imports
  effects: LirEffect[];       // module-level union of function effects
};

// LirFunction — one per decorated function; immutable; round-trips per I1
type LirFunction = {
  function_id: string;        // content hash of function's normalized AST
  signature: LirType;         // typed params + return
  body: LirOp[];               // flat opcode sequence, no nesting
  constraints: LirConstraint[]; // extracted decorators, §8.2
  effects: LirEffect[];        // conservative superset, I8/P13
};

// LirOp — closed enum; new members require LIR major version bump (P11, I13)
type LirOp =
  | { op: "LOAD"; slot: SlotRef }
  | { op: "STORE"; slot: SlotRef }
  | { op: "CALL"; target: FunctionRef; args: SlotRef[] }
  | { op: "BRANCH"; cond: SlotRef; then: Label; else: Label }
  | { op: "RETURN"; value: SlotRef | null }
  | { op: "AWAIT"; value: SlotRef }
  | { op: "EFFECT_NETWORK" | "EFFECT_GPU" | "EFFECT_CRYPTO"; detail: EffectDetail }
  | ArithmeticOp;             // arithmetic sub-family, not enumerated here
// LirConstraint — one per decorator instance; serialized inline on LirFunction
type LirConstraint = {
  kind: "latency" | "cost" | "privacy" | "throughput" | "hardware";
  spec: LatencySpec | CostSpec | PrivacySpec | ThroughputSpec | HardwareSpec;
  severity: "hard" | "soft";   // hard => refusal on violation; soft => flagged, best-effort
};

// LiquidAdapter — the sole trust-boundary interface (P12); implemented per provider
interface LiquidAdapter {
  readonly id: string;                       // e.g. "cloudflare-workers"
  readonly version: SemVer;
  readonly capabilities: Capability[];        // e.g. ["http","cron","wasm","no_gpu"]

  costFeed(): Promise<CostSnapshot>;          // TTL <= 60s (I11); adapter-authoritative
  latencyFeed(): Promise<LatencySnapshot>;    // p50/p95/p99, rolling window
  regionsAdvertised(): RegionTag[];           // MUST be accurate (adapter contract, §8)

  deploy(artifact: Artifact, cfg: DeployConfig): Promise<DeploymentHandle>;
  invoke(handle: DeploymentHandle, args: unknown[]): Promise<InvokeResult>;
  teardown(handle: DeploymentHandle): Promise<void>;
}

  | "LiquidCostCeilingExceeded"
  | "LiquidConstraintUnsatisfiable"
  | "LiquidResidencyIneligible";

12. Phase 0 — Repo Skeleton & Correctness Kernel

12.1 Objectives

Stand up the monorepo (§10) and prove the one premise the whole project depends on: a typed IR that round-trips exactly (I1) and a toy scheduler that picks correctly between two backends. No live feeds, no commercial surface — a hand-built reference compiler and a hard-coded-price toy scheduler, benchmarked against hand-tuned single-backend baselines. Constraint introduced: the LIR opcode set is frozen at three opcodes (CALL, RETURN, EFFECT_NETWORK) to keep the correctness kernel small enough to fully test by hand.

12.2 Detailed Implementation Steps

Scaffold compiler/lir/, compiler/frontend-ts/, compiler/backends/{cloudflare-workers, aws-lambda}/, scheduler/, adapters/{cloudflare-workers,aws-lambda}/, bench/ per §10. Define LIR v0.1 as a TypeScript type (the LirModule/LirFunction/LirOp shapes of §11, restricted to three opcodes). Implement the serializer and assert serialize(deserialize(x)) === x (I1) via a property-based test (ADR-13, fast-check). Implement the TS AST analyzer using ts-morph (ref-impl lesson from Crafting Interpreters' recursive-descent pattern, §5) to extract one decorated function and its @latency/@cost decorators (§8.1 grammar, restricted subset). Lower the parsed AST to LIR (§8.2 state table, restricted to the three frozen opcodes). Implement the two backends as pure LIR -> artifact functions (P7): CFW via esbuild, Lambda via a zip packer. Implement the two adapters against the LiquidAdapter interface (§11) with hardcoded costFeed()/latencyFeed() values and a 10 s rolling-probe latencyFeed(). Implement a toy pick_target (§11 signature, restricted decision rule: @latency present → CFW; @cost present → Lambda; both → refuse with LiquidConstraintUnsatisfiable, applying P9). Build the bench/ harness running three workload profiles (tight-CPU, network-bound, residency-tagged) three ways each (hand-tuned CFW, hand-tuned Lambda, Liquid-managed).

12.3 Deliverable

A CLI (liquidc) that compiles one decorated TypeScript function to LIR, emits both backend artifacts, deploys both to a personal Cloudflare and AWS account, and a toy liquidd that routes an invocation to the correct one — operator-inspectable via docs/runbooks/phase0.md and a benchmark report at bench/reports/phase0.md.

12.4 Acceptance Criteria

LIR round-trip passes on 100% of a 25-fixture corpus (I1). End-to-end test (source → LIR → CFW artifact → deployed → invoked → result verified) passes in CI on 3 platforms (ADR-15). Benchmark: Liquid-managed beats or matches (within 1.3×) hand-tuned single-backend on at least one of the three workload profiles (Phase 0 go/no-go threshold, K1). 13. Phase 1 — TypeScript Frontend & Constraint Extraction

13.1 Objectives

Harden the compiler frontend into something an external developer can point at a real TypeScript codebase: cover a usable language subset (async/await, fetch, JSON, modules, interfaces), implement full decorator extraction for all five constraint kinds (§8.1), and implement the conservative-superset effect inference (I8, P13) that later phases depend on. Constraint introduced: the frontend remains a pure function (P2) — no network calls, no file writes beyond the emitted LIR module.

13.2 Detailed Implementation Steps

Extend the ts-morph-based AST analyzer to the full constrained subset. Implement the AST → LIR lowering table of §8.2 for all node kinds the subset admits, applying P11 (opcode set stays closed — new surface constructs compose from existing opcodes, never introduce a new one without an RFC). Implement decorator extraction for @privacy, @throughput, @hardware per the §8.1 EBNF, with liquidc check performing the malformed-input rejection of §8.6 for each. Implement effect inference as a dataflow pass over the lowered LirOp sequence: any fetch/network API call taints the enclosing function with EFFECT_NETWORK; any crypto.subtle call taints with EFFECT_CRYPTO; propagate taint through CALL edges conservatively (P13 — a callee's effects are always inherited by the caller, per Harper's effect-typing formalism, §5). Implement liquidc check as a standalone subcommand emitting source-mapped diagnostics. Add composition-rule conflict diagnostics (§8.1's "Composition Rules"): detect statically-provable conflicts (e.g., @latency(1ms) + @privacy(in_region: "eu"→ only 40ms-p95 adapters registered)) and surface as compile-time warnings, deferring the authoritative refusal to runtime per P9 (compile-time is provisional, runtime is authoritative, matching P2).

13.3 Deliverable

liquidc check and liquidc build subcommands usable against an arbitrary TypeScript file in the supported subset; effect-inference output inspectable via liquidc build --emit-effects.

13.4 Acceptance Criteria

Effect-inference soundness (I8) verified on a 100-fixture differential corpus: static effect set is a superset of the dynamically traced effect set on 100% of fixtures (ADR-13 property test). liquidc check cold-build time ≤ 2 s per function (§4 constraint). All five decorator kinds parse and reject malformed arguments per §8.6 on a dedicated 15-fixture malformed-input corpus.

13.5 Conformance Fixtures

conformance/effect-inference/{network,crypto,gpu,tenant_data}-{01..10}.ts — 40 fixtures with known ground-truth effect sets. conformance/malformed-inputs/{privacy,throughput,hardware}- bad-arg.ts — one malformed fixture per remaining decorator kind. conformance/scheduler- decisions/replay-fixture-{01..05}.json — regression corpus carried forward from Phase 0.

13.6 Pitfalls

Effect inference under-tainting through a dynamically-dispatched call (obj[methodName]()) — mitigate by conservatively tainting with the union of all effects reachable from any method on the object's inferred type (over-approximation per P13, at the cost of some false positives). Decorator argument parsing accepting a value that TypeScript's own type checker would reject (e.g., a non-literal region tag) — mitigate by requiring all constraint arguments to be compile-time-constant expressions, rejected otherwise. Treating a compile-time conflict warning as if it were a hard refusal — mitigate by keeping the two code paths (compile-time warning vs. runtime refusal) physically separate modules so a future contributor cannot conflate them.

13.7 Performance Concerns

Dataflow effect inference over a large function body is worst-case quadratic in call-graph depth; bounded in practice by the constrained subset's ban on unbounded recursion at this phase. AST lowering allocates one LirOp per source statement; acceptable at the single- function granularity Liquid compiles at.

13.8 Edge Cases

A function calling itself recursively — the constrained subset defers general recursion support to Phase 2; liquidc check rejects with a specific diagnostic rather than looping. A decorator argument referencing an environment variable at compile time — rejected, since constraint arguments must be literal (P1's "type-level qualifier" requirement). A function with zero decorators — compiles successfully with an empty constraints array; fully unconstrained per P14.

13.9 Failure Analysis

An effect-inference unsoundness bug (I8 violated) is the highest-severity Phase-1 defect: it lets a @privacy(no_egress) function slip past the scheduler's filter. Detection: the differential fixture corpus (13.5) run on every CI build; any regression blocks merge. Recovery: revert the inference-pass change; the fixture corpus pins the last-known-sound behavior.

13.10 Operational Notes

liquidc check diagnostics are structured JSON when run with --json (consumed by IDE tooling); human-readable text otherwise. No production telemetry yet — frontend remains a local CLI tool until Phase 5 wires provenance end-to-end.

14. Phase 2 — LIR Type System & Effect Verifier

14.1 Objectives

Promote LIR from a Phase-0/1 convenience shape to a normatively-typed IR: implement the full opcode set (LOAD, STORE, CALL, BRANCH, RETURN, AWAIT, EFFECT_NETWORK, EFFECT_GPU, EFFECT_CRYPTO, arithmetic), a standalone verifier that proves progress + preservation (Pierce's TAPL soundness pair, §5) on every accepted module, and version LIR to v1.0 with a locked semver policy (I13). Constraint introduced: a LirFunction that fails the verifier MUST be rejected before it reaches any backend (I10).

14.2 Detailed Implementation Steps

Define the full LirOp closed enum (§11) and the arithmetic sub-family. Implement the LIR verifier as a standalone pass: type-check every LOAD/STORE against its declared LirType (progress: a well-typed op never gets stuck; preservation: evaluating an op preserves well-typedness of the remaining sequence — Pierce TAPL ch. 5, applied per P11/I10). Implement the effect-algebra join operation (union of effect sets across BRANCH arms, per Harper's effect-typing treatment, §5) so a conditional's inferred effect set is the union of both arms, never the intersection (I8's superset requirement). Implement the gradual-typing "unknown" constraint marker for a function declaring no constraint of a given kind (Siek & Taha's dynamic type ?, applied to constraint kinds rather than value types, §5, P14). Migrate the LIR schema definition source-of-truth toward the Rust-defined-IR groundwork flagged in ADR-03 (prototype only — the TS-defined schema remains authoritative through Phase 2; full migration is PhaseDeferred("§35")). Extend the round-trip conformance suite (I1) to 500 fixtures covering every opcode combination the verifier admits. Implement liquidc verify as a standalone subcommand runnable independently of a full build, for third-party tooling to validate a LIR module without invoking liquidc's own compiler.

14.3 Deliverable

liquidc verify <module.lir.json> — a standalone, independently distributable verifier binary that any tool producing LIR (including future non-TypeScript frontends, §21) can run to prove its output is well-typed and effect-sound before submitting to a backend.

14.4 Acceptance Criteria

Verifier proves progress + preservation on 100% of the 500-fixture corpus (14.2); rejects 100% of a dedicated 50-fixture "intentionally ill-typed" corpus with a specific, actionable diagnostic (not a generic parse failure). LIR v1.0 tagged and the semver-diff CI check (I13, §25) passes on the first minor-version bump exercise (add a no-op arithmetic variant, confirm no major bump required).

14.5 Conformance Fixtures

conformance/lir-verifier/well-typed-{001..500}.json. conformance/lir-verifier/ill-typed- {01..50}.json — each paired with its expected diagnostic string. conformance/lir-roundtrip/ opcode-coverage.json — one fixture exercising every opcode at least once.

14.6 Pitfalls

A verifier that accepts a module the runtime backend later chokes on — mitigate by running every backend's own smoke-test suite against the full well-typed corpus, closing the gap between "verifier says valid" and "backend can actually lower it." Effect-join implemented as intersection instead of union by an off-by-one design error — mitigate with a dedicated property test asserting effects(branch) ⊇ effects(then) ∪ effects(else) on every fixture. Treating the Rust-IR prototype (ADR-03) as production — mitigate by gating it behind a feature flag never enabled in the default liquidc build path until Phase 2 formally completes the migration decision.

14.7 Performance Concerns

The verifier is O(opcodes) per function — linear, acceptable at LIR's ≤64 KiB module size budget (§4). The 500-fixture round-trip corpus adds ~4 s to CI; mitigated by parallelizing fixture execution across the CI matrix (ADR-15).

14.8 Edge Cases

A BRANCH whose two arms have incompatible return types — verifier must reject (progress violation) rather than let it reach codegen. An AWAIT on a value not produced by a prior CALL — verifier rejects as a dataflow violation. A module claiming lir_version: "2.0.0" against a v1.x verifier — rejected outright per I10/I13, never partially processed.

14.9 Failure Analysis

A verifier unsoundness bug (accepts an ill-typed module) is the single highest-severity Phase-2 defect — it defeats the entire purpose of a typed IR. Detection: the ill-typed fixture corpus (50 cases) run on every CI build, zero tolerance for a false accept. Recovery: revert the verifier change; no release ships with a known false-accept.

14.10 Operational Notes

liquidc verify emits a machine-readable pass/fail plus diagnostic list, consumed by CI gates in every downstream package's own pipeline (adapters, backends) as a pre-merge check before that package's own tests run against a LIR fixture.

conformance/backends/cfw/bundle-size-budget.ts — a fixture intentionally near the platform limit, expected: warning at 80%, hard failure past 100%. conformance/backends/cfw/kv- passthrough.ts — a stateful function, expected: value round-trips through a KV write/read pair. benchmarks/baselines/cfw.json — the CSP9 comparison baseline, regenerated quarterly.

liquidc build --target aws-lambda producing a deployable zip (or Layer-referencing package), deployed via the Lambda adapter's deploy(), with an independent CSP9 report.

Provisioned concurrency silently billing the tenant continuously regardless of actual traffic — mitigate by surfacing the resulting cost delta explicitly in the deploy-time diagnostic output, tying back to P5 (no silent runaway spend) even though this is a deploy-time, not invoke-time, cost. Lambda's per-account concurrency limit being hit silently under burst load — mitigate with an adapter-level pre-flight check against the account's known concurrency ceiling before deploy() requests provisioned concurrency. VPC cold-start tax (ENI attachment) being misattributed to the compiler rather than the VPC config choice — mitigate by tagging the CSP9 report with whether VPC config was active on the sampled invocations.

17. Phase 5 — Runtime Scheduler Core

17.1 Objectives

Replace Phase 0's toy static-rule scheduler with the real pick_target (§11): a pure function of all five declared inputs, running as the Go daemon liquidd, with pluggable cost/latency feeds and provenance emission wired end-to-end. Constraint introduced: the decision function must be provably deterministic (I4) before any live feed is connected in Phase 6 — determinism is validated against static fixture feeds first.

17.2 Detailed Implementation Steps

Implement pick_target per the §11 signature and the §8.4 state table (Evaluating → Filtered → Ranked → Routing/Refusing → Recording/Done), applying P4 (purity) and I4 (determinism) as the load-bearing constraints on every code path. Implement the hard-constraint filter (§8.3's refinement semantics) as a pipeline stage independent of the soft-constraint ranking stage, so a future contributor cannot accidentally let a soft preference override a hard refusal (P9). Implement the pluggable feed interface: a CostFeedSource/ LatencyFeedSource abstraction whose default implementation reads directly from each registered LiquidAdapter.costFeed()/latencyFeed(), with the TTL cache from I11 sitting in front of both. Implement provenance emission: every Done state transition writes exactly one Invocation row (§11) to a pluggable sink (local file for Phase 5, ClickHouse from Phase 6 onward per ADR-06). Implement the deterministic-replay simulator (§7's debugging methodology) as conformance/simulator/, replaying logged (constraints, candidates, cost_feed, latency_feed, residency_policy, tenant_quota) tuples and asserting I4 byte-for-byte. Apply Kleppmann's reproducibility argument (ch. 9, §5) directly: the simulator is the mechanism that makes "replay this decision" an actual, runnable command, not a manual log-reading exercise.

17.3 Deliverable

liquidd — a single static Go binary that accepts a LiquidFunction + Plan, receives liquid(fn, args) calls over a local RPC socket, and routes each to the correct LiquidAdapter.invoke(), with every decision replayable via tools/decision-replay-cli.

17.4 Acceptance Criteria

pick_target decision latency p50 ≤ 1 ms, p99 ≤ 8 ms (§4, M1 in §28) measured on a 10,000-call synthetic load test. 100% replay-determinism (I4) on a 200-case logged-decision corpus. Zero goroutine leaks after a 1-hour soak test at 1,000 concurrent in-flight invocations (bounded by the §4 10,000-concurrency ceiling).

17.5 Conformance Fixtures

conformance/scheduler-decisions/replay-{001..200}.json — logged decision tuples with expected output, used for both regression testing and the I4 replay-determinism proof. conformance/scheduler-decisions/soft-vs-hard-priority.json — a fixture proving a soft preference never overrides a hard refusal. conformance/scheduler-decisions/empty-candidates. json — zero eligible adapters, expected: refuse / LiquidConstraintUnsatisfiable.

17.6 Pitfalls

A subtle non-determinism introduced by Go map iteration order when ranking candidates by soft-constraint score — mitigate by sorting candidates by a stable tiebreaker (adapter id lexical order) before ranking, and asserting stability in the replay simulator. Provenance writes silently failing under backpressure and going unnoticed — mitigate with the write- success-ratio telemetry from I9, alerting below 99.99%. Conflating "no candidates passed the hard filter" with "an adapter feed fetch failed" — mitigate by keeping these as distinct RefusalCode/error paths so an operator can tell an unsatisfiable constraint apart from infrastructure trouble.

17.7 Performance Concerns

The TTL feed cache (I11) avoids a network round-trip on every invocation, which is the dominant cost driver at the §4 1 ms p50 budget — a cache miss forces a synchronous fetch, explaining the p99 ceiling being 8× the p50. Goroutine-per-invocation (ADR-09) keeps allocation localized per call, avoiding shared-state contention on the hot decision path.

17.8 Edge Cases

Two invocations for the same function racing to read a Plan mid-rebalance (Phase 7 concern, but the read path must already be race-safe here since Plan is immutable and superseded, never mutated, §11). A cost feed returning a negative price (adapter bug) — the scheduler MUST reject the reading as invalid rather than route on it, treating it identically to a stale-feed condition (I11's degrade-to-last-known-good path). A tenant quota lookup returning "unknown tenant" — treated as a hard refusal (LiquidConstraintUnsatisfiable), never a default-allow.

17.9 Failure Analysis

A determinism violation (I4) discovered in production is a Sev-1: it means the provenance audit trail cannot be trusted. Detection: the replay simulator run continuously against a sample of production decisions (not just CI fixtures). Blast radius: every tenant's provenance record becomes suspect until the specific non-deterministic code path is identified and reverted. Recovery: halt new deploys of the affected scheduler version; bisect via the fixture corpus.

17.10 Operational Notes

liquidd exposes Prometheus metrics (ADR-12): decision_latency_seconds (histogram), decision_outcome_total{outcome="route|refuse"}, scheduler_degraded_mode_total (I5). OTLP traces (ADR-11) span the full Evaluating → Done lifecycle per invocation. Rollback is a binary swap (single static binary, ADR-17) with no schema migration required at this phase.

18. Phase 6 — Provider Adapter Contract & Feeds

18.1 Objectives

Formalize the LiquidAdapter contract (§11) as a stable, independently-versioned interface third parties can implement, and expand the reference adapter set to include real (not hardcoded) cost and latency feeds. Constraint introduced: every adapter's costFeed()/ latencyFeed() must be cross-validated against a second independent source before the scheduler treats it as authoritative in Phase 7 (T3 mitigation groundwork, §22).

18.2 Detailed Implementation Steps

Publish the LiquidAdapter interface (§11) as a standalone, versioned npm package (@liquid/adapter-contract) so third-party adapter authors depend on a stable contract independent of the scheduler's own release cadence (P7, P12). Implement real costFeed() for the CFW and Lambda adapters against each provider's pricing API (replacing Phase 0's hardcoded values), with the TTL-cache discipline of I11 enforced adapter-side as well as scheduler-side. Implement real latencyFeed() via a continuous 10 s rolling-probe (carried forward from Phase 0, now measuring real deployed functions rather than a toy). Implement regionsAdvertised() against each provider's actual region list, with a canary probe (referenced in T2's mitigation, §22) verifying the advertised region matches the region an actual probe invocation executes in. Add two new adapters — Fly Machines and Google Cloud Run — against the same published contract, proving P7's backend-independence claim empirically (a third-party-shaped adapter, built without touching scheduler or frontend code). Implement adapter-package signing via sigstore (ADR-18) and hash-pinning at adapter load time (T1 mitigation groundwork).

18.3 Deliverable

@liquid/adapter-contract@1.0.0 published; four adapters (CFW, Lambda, Fly Machines, Google Cloud Run) implementing it, each independently versioned and each passing the shared adapter conformance suite.

18.4 Acceptance Criteria

100% of the shared adapter conformance suite (18.5) passes for all four adapters. Region- advertisement canary probes confirm regionsAdvertised() accuracy on 100% of a 20-region sample, re-run every 5 minutes (RTO target for a misreporting adapter, §4). Cost-feed cross- validation flags a synthetic ≥20% divergence injected into a test double within one poll cycle (10 s).

18.5 Conformance Fixtures

conformance/adapters/shared-suite/{deploy,invoke,teardown,cost-feed,latency-feed,regions}- {01..05}.json — one shared fixture set run against every adapter implementation. conformance/adapters/region-canary/mismatch-injection.json — a deliberately misreporting adapter double, expected: quarantine within the RTO. conformance/adapters/cost-feed/ divergence-injection.json — two feed sources disagreeing by 25%, expected: flagged, not silently averaged.

18.6 Pitfalls

A third-party adapter author interpreting costFeed()'s TTL loosely and caching for hours — mitigate by the shared conformance suite asserting a maximum cache age directly (18.4's 10 s poll-cycle check). Region-canary probes themselves adding a measurable cost — mitigate by capping canary frequency at the RTO-derived 5-minute cadence rather than probing every request. An adapter author accidentally logging payload contents in a debug trace — mitigate with a conformance-suite check scanning adapter log output for payload-shaped data on a synthetic tagged input (the "adapter authors MUST NOT log payloads" contract clause, §11).

18.7 Performance Concerns

Real cost-feed API calls (vs. Phase 0's hardcoded constant) introduce genuine network latency into the feed-refresh path; bounded by the 10 s poll interval so it never sits on the invocation-time hot path (I11's cache is what makes this safe). Canary probes add real invocation volume; capped to stay a small fraction of genuine traffic.

18.8 Edge Cases

A provider's pricing API returning a documented-but-unparseable response format change — adapter must fail closed (treat the feed as stale, defer to I11's degrade path) rather than crash the whole liquidd process. Two independent cost sources agreeing exactly by coincidence on a value that is actually wrong — accepted as a known residual risk, mitigated long-term by the quarterly cost-feed-vs-invoice audit (§24). A canary probe itself failing due to transient network trouble unrelated to the adapter's honesty — must not trigger a false quarantine; require two consecutive failed canaries before quarantining (avoids flapping).

18.9 Failure Analysis

A quarantined adapter (T1/T3 detection firing) removes that adapter from the scheduler's candidate set entirely until manually or automatically cleared — blast radius is bounded to tenants whose Plan includes that adapter as a target; other targets in the same Plan continue serving traffic (no single-adapter failure takes down a whole tenant). Detection: region-canary and cost-divergence monitors (18.4). Recovery: adapter hash re-verification and a clean canary pass clears the quarantine automatically.

18.10 Operational Notes

Adapter health (quarantine status, last canary result, feed staleness) exposed via a liquidd adapters status CLI command and a Prometheus gauge adapter_quarantine_status{adapter_id}. New adapter versions roll out independently (ADR-19); a customer pins an adapter version explicitly in their deploy config, with in-flight invocations unaffected by a version bump (I5's version-pin corollary).

19. Phase 7 — Cost-Aware Re-Routing & Residency Enforcement

19.1 Objectives

Turn Liquid from "deploy to many backends, pick once" into "rebalance live as conditions change": subscribe the scheduler to cost-feed deltas, and make @privacy(in_region(...)) cryptographically enforced via signed residency receipts rather than a trust-the-adapter check alone. Constraint introduced: I2 (zero residency violations) now has a cryptographic, not just logical, enforcement mechanism (I12).

19.2 Detailed Implementation Steps

Implement live re-routing: the scheduler subscribes to cost-feed deltas (polling the TTL cache of I11 at its refresh boundary) and re-evaluates pick_target for future invocations when a delta would change the routing outcome for an active Plan's constraint set — without creating a new Plan unless the deploy surface itself changes (§11's Plan-immutability discipline, applying P2/P4 — the decision changes, the deployed artifacts do not). Implement signed residency receipts: every adapter handling a @privacy-tagged invocation MUST produce a receipt signed with the adapter's registered key, attesting the actual execution region; implement scheduler-side receipt verification (I12) against the adapter's known public key, storing the verified receipt in the Invocation row. Implement the quarterly receipt- resampling audit: a scheduled job re-verifying a statistical sample of historical receipts against the adapter's current signing key, catching a key-rotation or forgery issue after the fact. Implement the Cost Model Service (cost-model-service/, Go, per §10) as the out-of-band aggregator feeding a second independent cost source per provider, closing the loop on 18.6's cross-validation groundwork (T3 mitigation, §22, now load-bearing rather than a future note).

19.3 Deliverable

A scheduler that measurably re-routes future invocations when a cost delta crosses a decision threshold (observable via RREP-MI-equivalent internal counter, §28 M-table), with every @privacy-tagged invocation carrying a cryptographically verified residency receipt in its provenance row.

19.4 Acceptance Criteria

A synthetic cost-delta injection (one adapter's price drops 30%) triggers a measurable shift in routing distribution within one feed-refresh cycle (≤ 60 s, I11) on a dedicated load test. 100% of @privacy-tagged invocations in the conformance suite carry a verified receipt; 0% pass with an unverified or missing receipt (I12, zero tolerance). Cost Model Service cross-validation flags every injected ≥20% divergence in the 19.5 fixture set within one poll cycle.

19.5 Conformance Fixtures

conformance/rerouting/cost-delta-injection.json — expected: routing shift within 60 s. conformance/residency/receipt-forgery.json — a receipt signed with the wrong key, expected: LiquidResidencyIneligible-class rejection (I12 firing), never silently accepted. conformance/residency/receipt-missing.json — an adapter that omits the receipt entirely, expected: hard refusal, not a degraded pass-through.

19.6 Pitfalls

Re-routing thrashing — a cost feed oscillating near a decision boundary causing rapid back- and-forth routing changes — mitigate with a hysteresis band (a delta must persist across two consecutive feed-refresh cycles before triggering a re-route). A receipt-verification bug that fails open (treats an unverifiable receipt as valid) rather than fails closed — mitigate with a dedicated fixture (19.5's forgery case) that must fail every CI run if the fail-open bug regresses. Key-rotation on the adapter side without a corresponding scheduler-side key update — mitigate via the quarterly resampling audit (19.2) catching drift before it becomes a systemic false-reject wave.

19.7 Performance Concerns

Re-evaluating pick_target on every feed-refresh cycle for every active Plan scales linearly with active-Plan count; bounded in practice by the §4 concurrency ceiling and mitigated by only re-evaluating Plans whose constraint set includes a cost dimension. Receipt verification adds a signature-check to the decision path; budgeted within the existing p99 8 ms ceiling (§4) since signature verification (ed25519-class) is sub-millisecond.

19.8 Edge Cases

A cost-delta crossing the re-route threshold during an in-flight invocation — the in-flight call completes on its already-chosen target (I5's version-pin corollary extended to Plan targets); only subsequent invocations see the new routing. A residency receipt whose signature verifies but whose attested region does not match any region in the residency policy's allow-list — treated as a violation (I2), not merely "unexpected," since untrusted metadata must never expand eligibility. A Cost Model Service outage — the scheduler degrades to adapter-reported feeds alone (graceful degradation of the second source, not a full I5 degraded-mode trigger, since the primary feed still functions).

19.9 Failure Analysis

A false-negative residency check (I12 fails to catch a forged receipt) is a Sev-1: a residency violation reaches production undetected. Detection: the receipt-forgery conformance fixture, plus the quarterly resampling audit as a production-facing backstop. Blast radius: bounded to tenants with @privacy-tagged functions on the affected adapter; containment is immediate quarantine of that adapter's signing key pending investigation (mirrors 18.9's quarantine mechanism). Recovery: revoke and rotate the adapter's key; re-verify the historical sample.

19.10 Operational Notes

Re-routing events tracked via rerouting_events_total{tenant} (feeds the RREP-MI-equivalent dashboard metric, §28). Residency-receipt verification failures page immediately (I2's zero- tolerance policy) via residency_violation_count, distinct from a routine cost-driven re-route which is expected, healthy behavior.

20. Phase 8 — GPU & On-Device Backends

20.1 Objectives

Extend the backend set to the substrate pair with the largest per-invocation cost delta: GPU- cloud vs. on-device inference. Add a GPU node adapter, a browser-WASM backend with a WebGPU path, and mobile targets (Capacitor, React Native), plus cross-substrate sharding driven by battery/network context. Constraint introduced: adding three new backend classes MUST NOT require an LIR major version bump (P7, P11) — proving MLIR's dialect-registration pattern (Lattner et al. 2021, §5) applies to LIR's opcode set.

20.2 Detailed Implementation Steps

Implement the GPU node adapter treating each GPU cloud as a target advertising hardware: "gpu" (§8.1's @hardware decorator, §11's Capability list); cost feed includes per-token and per-second pricing, latency feed includes cold-start-to-warm transition time. Implement the browser-WASM backend: LirOp → .wasm module via binaryen/emscripten, respecting the WebAssembly Core Specification's validated-instruction-set and determinism requirements (Haas et al. 2017, §5); generate WebGPU shaders for supported arithmetic ops, CPU fallback for the rest (following MLIR's dialect-per-target pattern, §5, to keep the GPU/WASM lowering passes independent of the CPU lowering pass added in Phase 3–4). Implement mobile targets: a Capacitor bundle (iOS + Android via web view) and a React Native native bridge, with CoreML (iOS) / NNAPI (Android) hardware feature flags advertised through the adapter's capabilities list. Implement cross-substrate sharding: extend the scheduler's context inputs (beyond the five in §11's signature — battery level and network class are additive tenant_quota-adjacent context, not a change to pick_target's core five-argument contract) so a function declaring both @hardware(prefers: "gpu") and @latency(50ms) can route to GPU-cloud on Wi-Fi and on-device when battery > 30% and on cellular. Implement per-invocation ML-specific provenance fields (model hash, hardware generation, quantization profile) as an Invocation-row extension, additive and backward-compatible per I13's schema-evolution discipline (§25).

20.3 Deliverable

Three new backends (GPU node, browser-WASM/WebGPU, mobile) passing the shared adapter conformance suite (18.5), plus a working cross-substrate-sharding example (examples/04-gpu-vs-on-device/) demonstrating a single function auto-sharding between a GPU cloud and on-device inference based on live battery/network context.

20.4 Acceptance Criteria

Zero LIR major-version bumps required to add all three backends (I13 — verified by running the Phase-2 verifier against the pre-Phase-8 fixture corpus with no changes). Cross-substrate sharding example correctly routes to GPU-cloud in 100% of a 20-sample Wi-Fi-context test and to on-device in 100% of a 20-sample low-battery-cellular-context test. CSP9 on the WASM backend ≤ 1.5× a hand-tuned WebGPU baseline (mirroring the CFW/Lambda gate pattern of §15–16).

20.5 Conformance Fixtures

conformance/backends/gpu/cold-warm-transition.json — GPU cloud cold-start timing fixture. conformance/backends/wasm/webgpu-shader-fallback.ts — an op unsupported by WebGPU, expected: correct CPU-fallback codegen. conformance/sharding/battery-network-context-{01..20}.json — 20 Wi-Fi and 20 low-battery-cellular fixtures, expected routing outcome per fixture.

20.6 Pitfalls

WebGPU shader generation silently producing numerically divergent results from the CPU fallback path (floating-point non-associativity across backends) — mitigate with a differential-testing fixture comparing WebGPU and CPU-fallback outputs on the same input within a documented epsilon. Mobile hardware feature flags (CoreML/NNAPI availability) varying by device generation in ways the adapter cannot statically know — mitigate by querying capability at invoke time via a lightweight on-device probe rather than assuming a static capability list per OS version. Cross-substrate sharding context (battery, network) becoming stale between context-read and dispatch — mitigate with the same TTL-cache discipline as I11, applied to context reads.

20.7 Performance Concerns

GPU cold-start-to-warm transition dominates GPU-cloud latency variance far more than CFW/Lambda cold starts do; the latency feed must report this transition explicitly, not just steady-state throughput. On-device WASM/WebGPU execution competes for the host device's own CPU/GPU scheduling with the surrounding application — the adapter's latencyFeed() must reflect observed, not theoretical, on-device performance.

20.8 Edge Cases

A device advertising WebGPU support that silently falls back to a software rasterizer (some older Android GPUs) — the CPU-fallback path must produce a correct, if slow, result rather than crash. A GPU-cloud adapter's warm-pool exhausting under burst load — deploy-time pre-flight check (mirroring 16.6's Lambda-concurrency check) rather than a runtime surprise. Battery level context unavailable (a non-mobile on-device target) — treated as an absent/unconstrained context dimension, not a hard refusal, since @hardware degrades gracefully per P14.

20.9 Failure Analysis

A WebGPU/CPU-fallback numerical divergence beyond tolerance reaching production is a data- correctness incident, not a routing incident — detection is the differential-testing fixture (20.6) run continuously against a sample of production sharded invocations. Blast radius: bounded to functions using GPU/WASM hardware hints; contained by disabling the WebGPU path for the affected op class pending a fix, falling back to CPU universally.

20.10 Operational Notes

Cross-substrate sharding decisions are tagged in provenance with the battery/network context that drove them, distinct from the cost/latency/residency inputs already logged (§11) — this additive tagging follows the same backward-compatible schema-evolution rule applied to the ML- specific fields (20.2).

21. Phase 9 — Multi-Language Frontends & Smart-Contract Targets

21.1 Objectives

Prove LIR's frontend-independence claim (P7 mirrored on the input side) by adding Python and Go frontends emitting the same LIR, and prove backend generality by adding EVM and one non-EVM smart-contract target where @cost reinterprets as gas budget and @latency as finality budget. Constraint introduced: neither new frontend may require an LIR opcode addition beyond what Phase 2's closed set already provides (P11) — if either does, that is itself a finding requiring an RFC before landing.

21.2 Detailed Implementation Steps

Implement the Python frontend using Python's built-in ast module, targeting the same subset LIR v1 already supports (P7's independence proven on the input side — no LIR change needed to add a frontend, only a new AST-to-LIR lowering table analogous to §8.2's TS-specific one). Implement the Go frontend building on go/ast, using build-tag-based constraint annotation (//liquid:latency budget=50ms) since Go lacks a native decorator syntax, lowering to the same LirConstraint shape (§11) regardless of source syntax. Implement the EVM smart-contract target: LirOp → Solidity-compilable intermediate form (or direct EVM bytecode), reinterpreting @cost(max_per_call) as a gas-budget ceiling and @latency(budget) as a block-finality-time budget — the same LirConstraint schema, a different spec interpretation per target class (no core schema change, §11). Implement one non-EVM target (Solana, Rust+BPF) proving the reinterpretation generalizes beyond one VM family. Document the "default deployment abstraction" positioning: coexistence patterns with existing IaC tools (Terraform/Pulumi remain the infra layer; Liquid remains the code-bearing-function layer), formalized as a docs/ guide rather than a scheduler or compiler change.

21.3 Deliverable

Three source languages (TypeScript, Python, Go) compiling to the same LIR v1.x, and two smart-contract targets (EVM, Solana) accepting the same constraint vocabulary reinterpreted per target-class semantics, all passing the Phase-2 verifier unchanged.

21.4 Acceptance Criteria

Zero LIR opcode additions across both new frontends (P11, verified against the closed enum, §11) — any violation blocks the phase from completing until resolved via RFC. A single example function compiled from all three frontends produces LIR modules that the Phase-2 verifier accepts identically (round-trip + verifier pass on all three, I1/I10). Gas-budget reinterpretation of @cost correctly rejects a call exceeding the declared ceiling on 100% of a 15-fixture EVM gas-budget corpus.

21.5 Conformance Fixtures

conformance/frontends/cross-language-equivalence/{ts,py,go}-same-function.json — the same logical function compiled from all three, expected: LIR modules pass the verifier identically. conformance/chain-targets/evm-gas-budget-{01..15}.json. conformance/chain-targets/solana- finality-budget-{01..05}.json.

21.6 Pitfalls

A frontend author reaching for a Python- or Go-idiomatic construct with no clean LIR lowering (e.g., Python generators) — mitigate by defining each frontend's supported subset explicitly up front (mirroring Phase 1's TypeScript subset discipline, §13) rather than attempting full- language coverage. Gas-budget reinterpretation silently under-counting actual EVM gas cost (opcode gas costs vary by hard fork) — mitigate with a fixture pinned to a specific EVM hard- fork's gas schedule, re-validated on every fork the target adapter claims to support. Treating "same LIR schema" as "same semantics" across VM families — mitigate by documenting the target-class reinterpretation table explicitly (21.2) rather than leaving it implicit in code.

21.7 Performance Concerns

Cross-language AST-to-LIR lowering adds one lowering-table implementation per frontend but does not change LIR's own size/complexity budget (§4's 64 KiB module-size ceiling still applies uniformly). EVM/Solana bytecode emission is bound by each chain's own compilation toolchain performance, outside Liquid's control surface beyond the LIR-to-target lowering pass itself.

21.8 Edge Cases

A Python frontend fixture using a construct outside the declared subset — liquidc check (now multi-frontend-aware) rejects with a frontend-specific diagnostic, not a generic error. A gas-budget constraint declared below the minimum gas cost of the function's cheapest possible execution path — deploy-time rejection (mirroring 13.6's compile-time conflict diagnostics), never a guaranteed-to-fail on-chain transaction. A Solana finality-budget constraint tighter than the chain's minimum block time — same deploy-time rejection treatment.

21.9 Failure Analysis

A cross-language equivalence failure (two frontends producing verifier-divergent LIR for the "same" function) indicates a lowering-table bug in one of the frontends, not a LIR defect — detection is the 21.5 equivalence fixture, run on every frontend PR. Blast radius: contained to the specific frontend; the other frontends and all backends remain unaffected (P7's independence holding on both the input and output sides).

21.10 Operational Notes

Each frontend is released and versioned independently (ADR-19 extended to frontends symmetrically with backends). The target-class reinterpretation table (21.2) lives in docs/adr/ as a living reference, cross-linked from the Core Schema & Types section (§11) so LirConstraint.spec's per-target meaning is never implicit.

Canary/rolling-upgrade/rollback: each component (compiler, LIR, scheduler, each adapter, each backend) upgrades independently (ADR-19); a scheduler upgrade rolls out canary-first (5% of sidecars) with automatic rollback on an I4/I2 violation signal.

25. Compatibility & Versioning

Wire/storage compatibility: LIR is semver'd (I13); a minor bump adds opcodes or fields additively, never changes existing opcode semantics; a major bump is required for any breaking change, and old-major-version modules are rejected outright (I10), never partially interpreted.

Schema evolution: Invocation row extensions (e.g., 20.2's ML-specific fields) are additive-only — new nullable fields, never a repurposed or removed field, so historical rows remain valid under the current schema reader.

API stability: the LiquidAdapter interface (§11) is published independently (@liquid/adapter-contract, §18) and follows its own semver track, decoupled from the scheduler's own version.

Migration: a LIR major-version bump ships with a migration guide and, where mechanically possible, a liquidc migrate codemod; adapters declare the minimum LIR major version they support, and the scheduler refuses to route to an adapter whose minimum exceeds the deployed module's version.

Deprecation policy: a deprecated opcode or adapter-contract method is marked in one minor release, warned on for one full major-version window, and removed only on the next major bump.

SemVer policy: every independently-versioned component (compiler, LIR, scheduler, each adapter, each backend, each frontend) follows strict SemVer; ADR-19 is the canonical reference.

Rolling-upgrade guarantees: an in-flight invocation is never affected by a mid-flight version bump of any component (I5's version-pin corollary, applied uniformly across adapters, backends, and the scheduler itself).

26. Testing & Verification Strategy

Unit tests: per-package, standard Go/TS test runners; every pure function in §11 (pick_ target, the LIR serializer, the effect-inference pass) has a dedicated unit-test file.

Integration tests: end-to-end source → LIR → backend artifact → deploy → invoke → verify, run against real (personal-account) provider deployments in CI for the CFW and Lambda adapters (carried forward from Phase 0, §12.4).

Property-based tests (ADR-13, fast-check/gopter): I1 (round-trip identity), I4 (decision-function purity/determinism given identical inputs), I8 (effect-set superset property) are all expressed as properties, not fixed examples — this is the class of invariant example-based tests systematically under-test.

Differential tests: static-vs-dynamic effect trace comparison (I8, §13.4); WebGPU-vs-CPU- fallback numerical comparison within an epsilon (20.6).

Fuzzing (ADR-14, native Go fuzzing): the LIR deserializer (T7) and the scheduler's constraint-set intake path (T8) are both fuzz-harnessed; any crash becomes a permanent conformance fixture (§18.5-style shared-suite growth).

Chaos / fault injection: cost-feed divergence injection (18.5), region-canary mismatch injection (18.5), adapter-quarantine-then-clear cycling, control-plane-outage simulation (exercising I5's degrade-to-last-known-good path) — all run in a dedicated chaos-testing CI lane, not just unit tests.

Deterministic replay: the conformance/simulator/ (§7, §17.2) is the backbone of I4 verification — every logged production decision is replayable byte-for-byte against the scheduler binary that produced it.

Soak testing: 1-hour, 1,000-concurrent-invocation soak run per scheduler release (17.4), checking for goroutine leaks and gradual memory growth against the §4 256 MiB RSS ceiling.

Conformance: the shared adapter conformance suite (18.5) is run against every adapter, official or third-party, before that adapter is accepted into the registry.

Performance-regression gating: CSP9 (M2, §28) and decision-latency p50/p99 (M1) are both release-blocking CI gates, not advisory dashboards — a regression fails the build.

Tie-back to invariants: every invariant in §7's table names its own enforcement point and detection mechanism; this section is the aggregate strategy that keeps all thirteen exercised continuously, not just at release time.

27. Build & Release Engineering

Reproducible builds: esbuild with sorted inputs and fixed timestamps (ADR-20); every release artifact's hash is independently reproducible from source given the same compiler version (I6, P10).

Artifact signing: sigstore keyless signing (ADR-18) for every published npm package, Go binary, and Docker image.

SBOM: generated per release via syft-equivalent tooling, covering every transitive dependency across the TS and Go toolchains, published alongside the release artifacts.

Release channels: latest (stable), next (pre-release, opt-in), and a pinned per- major-version channel for LIR consumers who cannot yet adopt a new major (I13's compatibility guarantee made operationally concrete).

CI/CD topology: GitHub Actions (ADR-15), matrixed across TS/Go/per-adapter conformance; every merge to main runs the full conformance suite (§26) before any tag is cut.

Version stamping: every binary and package embeds its exact commit hash, build timestamp, and LIR version it was built against, queryable via a --version flag on every CLI.

Provenance/attestation: SLSA Level 3 build provenance (T4 mitigation, §22) attached to every official release, verifiable independently by a customer rebuilding from source.

Dependency auditing: npm audit and govulncheck/cargo-audit-equivalent blocking gates in CI (ADR-05); a new critical CVE in any pinned dependency blocks merge until patched or explicitly waived with a documented rationale.

28. Performance Engineering

Benchmarking/profiling methodology: every backend maintains an independent baseline (benchmarks/baselines/{cfw,lambda,wasm}.json, §15–16, §20) regenerated quarterly and on any provider-side platform change; the scheduler's decision path is profiled with Go's native pprof under the 17.4 soak-test load.

Allocation analysis: the decision path (pick_target) is designed to avoid heap allocation on the hot path where possible (candidate filtering operates over pre-allocated slices); verified via go test -bench allocation counts.

Lock contention: the goroutine-per-invocation model (ADR-09) deliberately avoids a shared lock on the hot decision path; the only shared state is the TTL feed cache, guarded by a read-mostly sync.RWMutex.

Cache/syscall analysis: the 10 s adapter poll interval and 60 s feed TTL (I11) are tuned to minimize syscalls (network round-trips) on the invocation-time critical path — a cache hit is the overwhelmingly common case by design.

Tail-latency analysis: p99 decision latency (§4, M1 below) is dominated by cache-miss synchronous fetches; the 8 ms p99 ceiling is derived from the network-RTT assumption in §4 (up to 150 ms cross-region probes are amortized by the 10 s poll cadence, not paid per-invocation).

29. Scalability Analysis

What stays constant: per-invocation decision latency (M1) is designed to be O(1) in the number of historical invocations — the decision reads only the current Plan, current feed snapshot, and current tenant quota, never a historical scan.

What grows, and its Big-O: candidate-filtering cost is O(adapters registered for the function) — bounded in practice by PAC (provider-adapter coverage) staying in the single-to- low-double digits per function; provenance storage grows O(invocations) unboundedly without a retention policy, mitigated by per-tenant retention tiers (§25).

Named bottlenecks, in order: (1) provenance write throughput into ClickHouse at very high invocation volume — mitigated by batched, buffered writes; (2) adapter feed-poll fan-out as PAC grows — mitigated by the 10 s poll interval being independent per adapter, parallelized; (3) scheduler process FD/memory ceiling (§4) at very high per-process concurrency — mitigated by horizontal sidecar replication, not single-process tuning.

Horizontal scaling: liquidd is stateless between invocations beyond its feed cache (rebuildable from adapters on restart); running N sidecar replicas behind the customer's own load balancer scales decision throughput linearly, since I4's determinism guarantees any replica computes the same decision given the same inputs.

Vertical scaling: raising the per-process concurrency ceiling (§4's 10,000) trades FD/ memory headroom for fewer replicas; the practical ceiling is the host's own FD ulimit, not a Liquid-imposed architectural limit.

Sharding/partitioning: provenance storage partitions naturally by tenant_id and time (ClickHouse's native partitioning), matching the per-tenant retention-policy boundary (§25).

Coordination overhead: zero — by design, no two liquidd replicas coordinate with each other; each computes its own decision independently from the same feed and policy inputs (P4's purity is what makes coordination unnecessary, unlike a consensus-based scheduler, contrast Alternative Architectures §34).

Practical ceiling and levers beyond it: the practical ceiling is provenance-write throughput at extreme invocation volume (hundreds of millions/month); the lever beyond it is sharding the ClickHouse cluster by tenant cohort, deferred until PFM-AOW-equivalent volume (§4's assumptions) demonstrates the need empirically rather than pre-optimizing.

30. Mental Models & First Principles

MM1 — A constraint decorator is a refinement type, not a comment. Predicts: a decorator that cannot be statically checked is worthless the moment it drifts from reality. Bug class without it: treating @latency as documentation, letting it silently rot while the actual deployed behavior diverges. Applied in §8 (Domain Model's effect/constraint type system) and P1 (§6).

MM2 — The IR is the compiler's ABI; stability protects everything downstream. Predicts: every frontend and backend added later inherits LIR's stability guarantee for free, or pays for its absence forever. Bug class without it: an opcode-set free-for-all that makes every new backend a frontend-coupled special case. Applied in §11, §14 (Phase 2), P11 (§6).

MM3 — The decision function is the language's memory-model equivalent: same inputs, same answer, forever. Predicts: any non-determinism in pick_target poisons the entire provenance audit trail, the same way a non-deterministic memory model poisons debugging a concurrent program. Bug class without it: "it worked when I reran it" becomes an acceptable engineering answer. Applied in §7 (I4), §17 (Phase 5).

MM4 — Effects are a static approximation of a dynamic future; soundness requires conservative over-approximation. Predicts: any effect-inference shortcut that under-reports will eventually let a @privacy(no_egress) function leak. Bug class without it: effect inference treated as a best-effort hint rather than a soundness-bearing pass. Applied in §8.3, §13 (Phase 1), P13 (§6).

MM5 — A refusal is a type error deferred to runtime. Predicts: treating refusal as "failure" rather than as the type system doing its job late leads engineers to paper over it with retries or fallbacks that violate P9. Bug class without it: silent degradation dressed up as resilience. Applied in §8.4 (scheduler state table), P9 (§6).

MM6 — The adapter is a foreign-function interface into an untrusted execution environment. Predicts: any code that treats an adapter response as trusted without the two-verb/three-feed contract's discipline reopens the exact trust boundary the contract exists to close. Bug class without it: ad hoc provider-specific calls scattered outside the adapter layer. Applied in §11, P12 (§6), Threat Model T1 (§22).

MM7 — Compute-adaptivity is scheduling wearing a type system's clothes. Predicts: the same rigor that makes a type system sound (progress + preservation) is exactly what makes a scheduling decision trustworthy (purity + replayability); the two are the same discipline applied to different runtime questions. Bug class without it: treating the scheduler as "just" an operational concern separate from the language's semantics. Applied in §8, §17, MM3 above.

MM8 — Provenance is the language's stack trace for economic and legal accountability. Predicts: every "why did this cost $X" or "prove this ran in the EU" question must be answerable from a single logged row, the same way a stack trace answers "why did this crash." Bug class without it: an audit trail that requires cross-referencing multiple systems to reconstruct a single decision. Applied in §8.5 (Invocation schema), §24 (Operational Readiness).

MM9 — Backend churn should be invisible to the frontend, and frontend churn invisible to the backend. Predicts: the moment either side needs to know about the other's internals to add a feature, the IR boundary has failed at its one job. Bug class without it: a "just this once" special case that couples a specific frontend construct to a specific backend's codegen. Applied in P7 (§6), §20 (Phase 8), §21 (Phase 9).

Apache TVM made the decision to optimize placement ahead of time via an auto-tuning search over a static cost model rather than live-feed-driven runtime routing — this wins when the hardware target set is fixed and known at compile time and re-tuning cost matters more than adapting to live price/latency drift (a training cluster with fixed GPUs, not a multi-cloud FaaS market).

GraalVM Truffle made the decision to let the JIT's own runtime profile drive dispatch speculatively rather than a declared, checkable constraint — this wins when the workload's performance characteristics are unknown ahead of time and the cost of a wrong initial guess is low (a general-purpose polyglot scripting runtime, not a cost/compliance-bound production function).

Kubernetes' scheduler made the decision to place at deploy/reschedule granularity, not per invocation — this wins when the unit of work is long-running (a service, not a discrete function call) and the resource model (CPU/memory requests) is the only non-functional dimension that matters, with no per-call cost-feed-driven routing need.

Erlang/BEAM made the decision to provide location-transparent process scheduling with zero cost-awareness — this wins when the workload's non-functional requirement is fault-tolerant concurrency and hot-code-swap, not cost or residency optimization, and all nodes are economically interchangeable.

32. Back-of-Envelope Capacity Model

Derived from §4's System Constraints table; every number below shows its formula.

  1. Scheduler decision throughput per core. p50 decision latency 1 ms (§4) → 1,000 decisions/sec/core (single-threaded worst case); with Go's goroutine concurrency and the feed-cache hit path dominating, effective throughput ≈ 1,000 × (cache-hit ratio, assumed 0.95 given the 60 s TTL / 10 s poll cadence) ≈ 950 decisions/sec/core sustained.
  2. FD budget per adapter connection. 4,096 FD ceiling (§4) ÷ 2 FDs/adapter connection ÷ 3 default adapters ≈ 682 pooled connections per adapter before headroom exhaustion — informs the connection-pool sizing default in scheduler/internal/feeds/.
  3. Provenance ingestion rate at 10,000 concurrent invocations. 10,000 concurrent (§4) × assumed 50 ms average invocation duration → 200,000 Invocation rows/sec peak write rate into ClickHouse — sizes the ClickHouse ingestion-buffer capacity (ADR-06).
  4. LIR module storage footprint per 1,000 functions. 64 KiB/module ceiling (§4) × 1,000 → 64 MiB total LIR storage for 1,000 registered functions — trivially cacheable in the scheduler's in-memory Plan index.
  5. Adapter poll fan-out at PAC = 10. 10 adapters (Phase 3 target, §16.3) × 1 poll/10 s (§4) → 1 feed-poll request/sec aggregate — negligible network load even before the TTL cache.
  6. Cross-region probe cost bound. 150 ms worst-case RTT (§4) amortized over the 10 s poll interval → probe overhead is 1.5% of the poll cycle's wall-clock budget, never on the invocation-time critical path (I11's cache is what makes this arithmetic hold).
  7. Residency-receipt signature-verification overhead. Ed25519 verification ≈ 50–100 µs (well-documented cryptographic benchmark figure) → at 950 decisions/sec/core (item 1), adds ≈ 5–10% to decision latency in the worst case — still within the 8 ms p99 ceiling (§4) with over 100× headroom.
  8. Memory footprint at max concurrency. 256 MiB RSS ceiling (§4) ÷ 10,000 concurrent invocations (§4) ≈ 25.6 KiB per in-flight invocation's scheduler-side state — a tight but achievable budget given Go's per-goroutine stack starts at 2 KiB and grows on demand.
  9. Cost Model Service scrape volume. 10 adapters (item 5) × 2 independent sources per provider (T3 mitigation, §22) × 1 scrape/60 s (billing-meter granularity, §4) ≈ 0.33 scrapes/sec aggregate — a trivially small background load justifying a single-process Cost Model Service through at least Phase 7.
  10. Canary-probe overhead at PAC = 10. 1 probe per adapter per 5 min RTO cadence (§4) × 10 adapters ÷ 300 s ≈ 0.033 probe-invocations/sec aggregate — under 0.01% of any tenant's real traffic at even modest production volume (hundreds of invocations/sec).

34. Alternative Architectures (Roads Not Taken)

Alt-1 — Compile-time-pinned backend selection (profile-guided, Terraform-style).

   source --> compiler --(profile @ build time)--> ONE chosen artifact --> deploy

Regime where it wins: a workload whose cost/latency/residency profile is genuinely static for the life of the deployment (e.g., a fixed-region internal batch job). Real system: Terraform/ Pulumi's deploy-time resource selection. Rejected because: provider pricing and latency drift within weeks (§2's core bet), and a compile-time pin cannot react to that drift without a redeploy — defeating the entire re-routing value proposition (§19).

Alt-2 — Fully dynamic JIT backend selection, re-decided per call via speculative profiling.

   source --> interpreter/JIT --(profile each call)--> speculative target --> execute

Regime where it wins: workloads with unknown, highly variable performance characteristics where the cost of a wrong first guess is negligible (GraalVM Truffle's polyglot scripting niche, §31). Rejected because: speculative re-profiling on every call is fundamentally at odds with P4's determinism/replayability requirement — an audit trail built on speculative JIT-driven choices cannot answer "why did this route here" reproducibly (MM3, §30).

Alt-3 — Centralized global scheduler (control-plane-authoritative placement, Kubernetes- style).

   many liquidd sidecars --> central scheduler (etcd-backed) --> placement directive --> sidecar executes

Regime where it wins: a single-cluster, single-operator environment where global bin-packing across many workloads matters more than per-invocation reactivity (Kubernetes' own niche, §31). Rejected because: a central control-plane on the invocation hot path reintroduces exactly the outage/latency risk I5 is designed to eliminate — Liquid's customers span multiple provider accounts with no shared cluster to bin-pack against.

Alt-4 — Interpreter-only runtime (no ahead-of-time compilation to backend-native artifacts).

   source --> LIR --> liquidd interprets LIR directly at every backend, no native codegen

Regime where it wins: an environment where deploy-time compilation cost is prohibitive and interpretation overhead is acceptable relative to the invocation's own cost (rare, low-QPS internal tooling). Rejected because: it would fail the CSP9 gate (M2, §28) catastrophically — every invocation would pay interpretation overhead on top of the provider's own cold start, directly violating P6 (cold start is a first-class, gated metric).
