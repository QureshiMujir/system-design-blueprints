303 — SAT/SMT Hybrid Solver

Project Number: 303

Project Name: SAT/SMT Hybrid Solver

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Build a decision procedure that answers satisfiability for two layered logics, from scratch:

  • a CDCL SAT core (Conflict-Driven Clause Learning) for propositional logic in CNF, and
  • a DPLL(T) SMT layer that drives the SAT core over first-order theories — equality + uninterpreted functions (EUF), linear real/integer arithmetic (LRA/LIA), fixed-width bit-vectors (BV), and arrays — with Nelson-Oppen theory combination.

The "hybrid" is the integration: one Boolean engine, several theory solvers, a clean DPLL(T) interface between them, lazy clause learning from theory conflicts, and theory propagation feeding the Boolean search.

In scope (Phase 0 deliverable):

  1. core — Var/Lit/Clause/CNF/Trail types, clause arena allocator.
  2. parse — DIMACS CNF reader + SMT-LIB 2 reader/command loop.
  3. cdcl — two-watched-literal BCP, 1-UIP conflict analysis, non-chronological backjump.
  4. cdcl heuristics (heap.rs, restart.rs, reduce.rs) — VSIDS/EVSIDS branching, phase saving, Luby + glucose restarts, LBD clause deletion.
  5. preprocess — Tseitin CNF, unit/pure, subsumption, bounded variable elimination, blocked-clause elimination.
  6. proof — DRAT trace emission, unsat-core extraction, model construction.
  7. theory — DPLL(T) theory interface (assert/check/propagate/explain/push/pop).
  8. theories — EUF (congruence closure), LRA/LIA (Simplex + branch-and-bound), BV (bit-blasting), arrays.
  9. combine — Nelson-Oppen combination + purification.
  10. smt — assertion stack, incremental push/pop, assumptions, get-model/get-value/get-unsat-core.
  11. cli — solve (DIMACS/SMT-LIB), stats, proof output.

System boundaries. Decides QF (quantifier-free) fragments: QF_UF, QF_LRA, QF_LIA, QF_BV, QF_ABV, and their combinations. Emits SAT+model or UNSAT+proof/core. Does NOT include: full first-order quantifiers (only e-matching stub, deferred), nonlinear arithmetic (NRA/NIA), strings/sequences, floating-point (FP), datatypes, a proof checker (emits DRAT, checking delegated to an external checker), parallel cube-and-conquer (single-thread Phase 0).

Non-goals (Phase 0): quantifier instantiation engine, NRA/NIA, FP/string theories, proof certificate for SMT theories beyond cores (full LFSC/Alethe proofs deferred), incremental theory-aware portfolio, GPU/SIMD bit-blasting, a constraint-modeling DSL.

Deployment model. A library (libhybrid) + a single CLI binary. Used as: a backend for verifiers (#279 model checker, #282 static verifier), package dependency resolution (#135), symbolic execution (#230), type checkers (#42/#238). Linux/macOS, x86-64/aarch64, single process.

Target users. Engineers learning constraint solving; authors of verification/analysis tools needing an embeddable solver; researchers studying CDCL/DPLL(T) internals.

What later phases unlock. Quantifier instantiation (e-matching, MBQI); nonlinear arithmetic (CAD/ICP); FP via bit-blasting; strings; full proof production (Alethe); parallel portfolio + cube-and-conquer; proof-producing theory solvers; optimization (MaxSAT/OMT).

Deferred features behind PhaseDeferred("Stretch Goals"):

  • Quantifier e-matching engine — PhaseDeferred("Stretch Goals").
  • Nonlinear arithmetic (NRA) — PhaseDeferred("Stretch Goals").
  • Floating-point theory — PhaseDeferred("Stretch Goals").
  • Full SMT proof certificates (Alethe/LFSC) — PhaseDeferred("Stretch Goals").
  • Parallel portfolio / cube-and-conquer — PhaseDeferred("Stretch Goals").

Estimated timeline. Phase 0 (SAT core through SMT-LIB loop): 12–14 weeks. Full theory suite + combination hardened: 6–10 months.

Recommended language: Rust. Rationale: the BCP inner loop is the hottest code in any solver and demands tight control over memory layout (clause arena, packed literals, cache-friendly watch lists) without a GC stalling the search; Rust gives that control with memory safety, eliminating the use-after-free/aliasing bugs that plague C++ solver arenas; enums model lbool and the term AST cleanly; the borrow checker is a mild cost in the arena (worked around with index-based references, exactly as production solvers use integer clause refs anyway). Rejected: C++ (the performance peer — MiniSat/CaDiCaL/Z3 are C++ — but unsafe arena bugs are a known time sink and the portfolio already favors Rust for systems work); OCaml/Haskell (excellent for the AST/theory logic, GC and boxing hurt the BCP loop); Python (orders of magnitude too slow for the core).

Prerequisites. Propositional + first-order logic; CNF + resolution; the DPLL algorithm; union-find; linear algebra + the Simplex method; modular/two's-complement arithmetic (BV); basic proof theory (resolution proofs, DRAT); cache-aware data structures.

2. Why Build This

  • CDCL is the most important algorithm most engineers never implement. It turns an exponential search into something that solves industrial instances with millions of clauses. Implementing two-watched literals, 1-UIP learning, and VSIDS teaches why — the interplay of propagation, conflict analysis, and activity-guided search.
  • DPLL(T) is the architecture behind every modern verifier. Z3, CVC5, Yices — all are a SAT core orchestrating theory solvers. Building the interface (theory propagation, conflict explanation, backtracking) demystifies the entire formal-methods stack.
  • Theory solvers are a tour of algorithms: congruence closure (union-find + e-graphs), the Simplex method specialized for satisfiability (Dutertre–de Moura), bit-blasting (compiling arithmetic to SAT), array axiom instantiation. Each is a self-contained masterpiece.
  • Nelson-Oppen combination teaches how independent decision procedures cooperate by exchanging only equalities over shared variables — a deep, beautiful, and practical result.
  • Proofs and cores teach trust: how a solver convinces a skeptic (DRAT), and how UNSAT cores power minimization, abstraction refinement, and debugging.
  • Cross-links. SAT core ↔ #135 package manager (dependency SAT), #277/#278 standalone SAT/SMT; theories ↔ #42/#238 type checkers (EUF), #230 symbolic execution (BV+arrays), #279/#281/#282 model checking/verification; Simplex ↔ #371 LP solver; e-graph ↔ #43 AST optimizer (equality saturation).
  • Calibration. This project is where "search," "deduction," and "decision procedure" stop being abstract. After it, you read a verifier's source and recognize every moving part. It permanently upgrades your ability to reason about NP-hard search and cooperating algorithms.

What Mastery Looks Like

  • Implement two-watched-literal BCP from memory, including the argument for why watches survive backjumping untouched (I2) — built in Phase 2.
  • Derive a 1-UIP learnt clause by hand from any implication graph and justify the backjump level — drilled in Phase 2 and Domain Deep Dive D.1–D.2.
  • State the full DPLL(T) contract (assert/check/propagate/explain/push/pop) and name the invariant each method carries (I5–I7) — built in Phase 6.
  • Implement congruence closure with proof-producing explanations (the Nieuwenhuis–Oliveras forest) — built in Phase 7.
  • Run the Dutertre–de Moura simplex by hand on a 3-variable system, including a Bland's-rule pivot on a degenerate basis — drilled in Phase 8 and Domain Deep Dive D.6.
  • Size a bit-blasted multiplier before writing it (≈7×10⁴ clauses at 64 bits, Capacity C7) and choose blasting vs word-level accordingly (ADR-14) — built in Phase 9.
  • Explain why Nelson-Oppen may exchange only entailed equalities (I13) and what non-convexity forces (case splits) — built in Phase 10.
  • Debug a wrong-answer report end-to-end: paranoid audits → ddmin → differential → regression fixture (Operational Readiness runbooks) — exercised from Phase 2 onward.

Per-box.

  • parse — DIMACS for pure SAT; an SMT-LIB 2 reader that builds typed terms (sorts, function symbols) and runs the command loop (set-logic, declare-fun, assert, check-sat, push, pop, get-*). It is the only component that touches untrusted text; everything downstream sees validated structures.
  • preprocess/inprocess — simplifies CNF before and during search: Tseitin encoding of non-clausal formulas, unit propagation at top level, pure-literal elimination, subsumption + self-subsuming resolution, bounded variable elimination (BVE), blocked-clause elimination (BCE). Reduces the search space the core must explore.
  • smt frontend — maps each theory atom (e.g. x + y ≤ 3) to a fresh Boolean variable, hands the Boolean skeleton to the SAT core, and routes the truth assignments of those atoms to the right theory via the combination router.
  • CDCL SAT core — the engine. decide picks the next literal by activity (VSIDS); BCP propagates unit clauses via two-watched literals; on conflict, analyze computes a 1-UIP learnt clause and the backjump level; the clause DB stores learnt clauses with LBD scores and periodically deletes low-value ones.
  • trail — the assignment stack with decision levels and per-literal reasons; the single source of truth for the current partial model; backjumping pops it.
  • DPLL(T) theory layer — each theory implements a uniform trait. The core asserts theory literals as it assigns their Boolean proxies; theories detect inconsistency (check), deduce implied literals (propagate), and explain conflicts/propagations as clauses the core can learn.
  • EUF — congruence closure over an e-graph: union-find of terms with a signature table so that a=b ⟹ f(a)=f(b). Produces equality explanations.
  • LRA/LIA — a Simplex tailored for satisfiability (general simplex with bound constraints) for reals; branch-and-bound + Gomory cuts on top for integers.
  • Bit-Vectors — bit-blasting: compile each BV operation to a propositional circuit and hand it to the SAT core; the cheapest correct route to QF_BV.
  • Arrays — lazy instantiation of read-over-write and extensionality axioms.
  • combine (N-O) — exchanges entailed equalities over shared variables between theories; purifies mixed terms so each theory sees only its own symbols.
  • results — SAT yields a full model (Boolean + theory values); UNSAT yields a DRAT proof (SAT) and/or an unsat core (subset of assumptions/assertions).

Boundaries. Trust: only parse consumes untrusted input. Concurrency: single-threaded Phase 0 (portfolio parallelism deferred — Stretch Goals). Persistence: none — solving is in-memory; proof trace streams to a file. Protocol: SMT-LIB 2 textual command/response is the external contract.

6. Design Principles

  1. Correctness over speed, always. A faster wrong answer is worthless. Every optimization must preserve the answer; SAT models are self-checked, UNSAT proofs externally checkable. Violation: a watcher bug that drops a unit clause → wrong SAT → silent, catastrophic.
  2. The trail is the single source of truth. The current partial assignment, decision levels, and reasons live only on the trail; backjumping is a trail truncation. Tradeoff: every data structure must be reconstructible from / consistent with the trail. Violation: a theory caching state that desyncs from the trail produces phantom conflicts.
  3. Two-watched literals: lazy, not eager. Track only two unassigned watches per clause; never scan a clause unless a watch is falsified. Tradeoff: subtle invariants on backtrack. Violation: eager BCP is O(clauses) per assignment — solver crawls.
  4. Learn from every conflict (1-UIP). Each conflict yields exactly one asserting clause at the first unique implication point; this is what makes CDCL escape exponential blowup. Violation: weaker learning (e.g. decision-cut) loses propagation power; no learning = DPLL = exponential.
  5. Theory lemmas are just clauses. A T-conflict or T-propagation is explained as a clause over existing atoms and handed to the SAT core, which learns it like any other. Tradeoff: explanations must be valid + minimal. Violation: an unsound explanation teaches the core a false fact → wrong UNSAT.
  6. Backtrackable theory state. Every theory supports push/pop matching the SAT core's decision levels in O(Δ). Violation: full rebuild on backtrack makes incremental + DPLL(T) intolerably slow.
  7. Determinism by construction. No wall-clock, no address-order, no hash-iteration-order influences a decision; a seed fixes any randomness. Tradeoff: must order tie-breaks explicitly. Violation: non-determinism makes bugs unreproducible and conformance flaky.
  8. Bounded resources, graceful "unknown". Time, conflict, and memory budgets are first-class; on exhaustion return unknown, never crash or lie. Violation: OOM-killed mid-solve loses the run; returning sat on timeout is a soundness bug.
  9. Explanations are minimal. Conflict clauses and theory explanations are reduced (self-subsumption, minimization) so learnt clauses are short and reusable. Tradeoff: minimization CPU. Violation: bloated learnt clauses fill memory and slow BCP.
  10. Incrementality is core, not bolted-on. push/pop, assumptions, and assertion levels are designed in from Phase 0 (the SMT loop and many clients are inherently incremental). Violation: a solve-once architecture forces full restarts per query — useless for verification loops.
  11. Lazy theory checking. Call full theory check at fixpoint of Boolean propagation, not on every literal; use cheap propagate continuously. Tradeoff: later conflict detection. Violation: eager full checks dominate runtime.
  12. Separate Boolean abstraction from theory semantics. The SAT core never knows what an atom means; the theory layer never sees Boolean search. This clean seam is what makes new theories pluggable. Violation: leaking theory knowledge into the core makes both unmaintainable.
  13. Arena allocation, index references. Clauses live in a contiguous arena; references are 32-bit offsets, not pointers — cache-friendly and relocatable for compaction. Violation: pointer-chasing clause objects thrash cache and fragment memory.
  14. Reproducible proofs. The DRAT trace exactly reflects the learnt clauses in order; it must check against DRAT-trim. Violation: a proof that doesn't check means the UNSAT claim is unsubstantiated.

8. Domain Model / Source Language / Protocol

8.1 Propositional layer (SAT)

Var     = u32 (1..N)
Lit     = packed u32: (var << 1) | sign        # sign 0 = positive, 1 = negative
lbool   = True | False | Undef
Clause  = [Lit]   (len ≥ 1; unit, binary special-cased)
CNF     = conjunction of Clauses
Assign  : Var -> lbool   (derived from trail)

DIMACS:

p cnf <numVars> <numClauses>
1 -2 3 0          # clause (x1 ∨ ¬x2 ∨ x3), 0 terminates
-1 2 0

8.2 First-order layer (SMT) — terms + sorts

Sort ::= Bool | Int | Real | (BitVec n) | (Array Sort Sort) | <uninterpreted>
Term ::= const | var
       | (f t1..tn)            # uninterpreted or theory function
       | (= t u) | (distinct ..)
       | (and ..)|(or ..)|(not t)|(=> ..)|(ite c t u)
       | (+ ..)|(- ..)|(* ..)|(<= ..)|(< ..)   # arithmetic
       | (bvadd ..)|(bvand ..)|(bvshl ..)|(concat ..)|(extract i j t) # BV
       | (select a i) | (store a i v)          # arrays

(get-model)          ; → ((x 2.0) (y 1.0))
(exit)

8.3 Boolean abstraction

Each theory atom A (e.g. (<= (+ x y) 3)) is assigned a fresh Boolean variable bA. The SAT core searches over {bA}; when it assigns bA=true, the smt frontend asserts A into the arithmetic theory; bA=false asserts ¬A. The theory's job: decide if the conjunction of asserted atoms is T-satisfiable.

8.5 Worked example — EUF conflict

Assert: a=b, b=c, f(a)≠f(c).

  • CC merges {a,b}, then {a,b,c}; signature of f(a) and f(c) collide ⇒ f(a)=f(c) derived.
  • f(a)≠f(c) now contradicts ⇒ T-conflict.
  • explain: (a=b ∧ b=c) ⟹ f(a)=f(c), so learnt clause ¬(a=b) ∨ ¬(b=c) ∨ (f(a)=f(c)) (in atom proxies). Combined with asserted f(a)≠f(c) ⇒ UNSAT.

8.6 Malformed / failure-path examples

  • DIMACS clause without terminating 0 → parse error (line, expected 0).
  • SMT-LIB (check-sat) before (set-logic) → error per spec.
  • BV op on mismatched widths (bvadd #b01 #b001) → sort error.
  • (get-model) after unsat → error (no model).
  • Division by zero in LIA/LRA term → guarded ((/ x 0) is uninterpreted per SMT-LIB, not an error).
  • Integer overflow in coefficient → use arbitrary-precision rationals in arithmetic (no machine overflow).

Phase 1 — DPLL Baseline (Decide / Propagate / Backtrack)

1.1 Objectives

A correct but naive propositional solver: chronological backtracking DPLL with full-scan unit propagation. The oracle the CDCL core (Phase 2) is differentially tested against.

1.2 Detailed Implementation Steps

The DPLL procedure of Davis–Logemann–Loveland (1962); correctness must hold for any decision order (P7), validated against MiniSat as the oracle (ADR-24); models self-checked per I8.

  • decide: pick any unassigned var (fixed order Phase 1), assign a phase.
  • propagate: scan all clauses; if a clause is unit under the current assignment, assign its literal; repeat to fixpoint; detect conflict (all-false clause).
  • backtrack: chronological — flip the last decision, undo assignments above it.
  • Wrap as SatSolver returning Sat(model)/Unsat (I8 self-check on SAT).

1.3 Deliverable

cli solve --engine dpll file.cnf returns correct SAT/UNSAT on small instances (≤ a few hundred vars).

1.4 Acceptance Criteria

  • Matches a reference (MiniSat) on every small SATLIB instance (differential).
  • SAT models verified by re-evaluation (I8); UNSAT confirmed by the reference.
  • Terminates on pigeonhole PHP(n) for small n (slowly — that's expected).

1.5 Conformance Fixtures

dpll/sat-tiny, dpll/unsat-tiny, dpll/php-3-2-unsat, dpll/model-verify.

1.6 Pitfalls

  • Not propagating to fixpoint → miss forced assignments, wrong/slow. Loop until no change.
  • Undo bugs on backtrack → stale assignments leak. Track exactly what each level assigned.
  • Treating decide order as correctness → it's only performance; correctness must hold for any order.

1.7 Performance Concerns

Full-scan propagation is O(clauses) per assignment — intentionally slow; this phase is for correctness, not speed. It exists to validate Phase 2.

1.8 Edge Cases

Empty formula (SAT, empty model); single empty clause (UNSAT); all-unit formula; formula already conflicting after unit prop at level 0.

1.9 Failure Analysis

If the baseline is wrong, the differential oracle is poisoned. Keep it dead-simple and cross-check against MiniSat independently before trusting it as an oracle.

1.10 Operational Notes

Stats: decisions, propagations, conflicts, max_depth. This is also the teaching artifact — heavily commented to show DPLL before CDCL complicates it.

Phase 2 — CDCL Core: Two-Watched Literals, 1-UIP, Backjump

2.1 Objectives

The real engine: watched-literal BCP, conflict-driven clause learning at the 1-UIP, and non-chronological backjumping. The single most important phase.

2.2 Detailed Implementation Steps

  • Two-watched literals: each clause watches two literals; per-literal watch lists with a blocker (cached other-watch literal to skip lookups). On a watched literal becoming false: find a new non-false literal to watch; if none and the other watch is unassigned → unit (propagate); if other is false → conflict (I2).
  • analyze (1-UIP): starting from the conflict clause, resolve against reasons of literals at the current decision level until exactly one literal of the current level remains (the UIP) — that literal becomes the asserting literal (I3). Compute the backjump level = second-highest level in the learnt clause.
  • clause minimization: self-subsuming resolution removes literals whose reasons are already implied (local + recursive minimization).
  • backjump: truncate trail to the backjump level (I4); add the learnt clause; the asserting literal is now unit → propagate.
  • Special-case binary + unit clauses for speed.

2.3 Deliverable

cli solve (default CDCL engine) solves instances orders of magnitude larger than DPLL; matches the DPLL oracle on all small instances.

2.4 Acceptance Criteria

  • Identical SAT/UNSAT to Phase 1 on the full small corpus (differential).
  • Solves medium SATLIB instances (10⁴–10⁵ vars) that DPLL cannot.
  • Learnt clauses are asserting (I3 assertion in debug builds).
  • Watcher invariant audit (I2) passes in paranoid mode after every conflict.

2.5 Conformance Fixtures

cdcl/vs-dpll-differential, cdcl/medium-sat, cdcl/medium-unsat, cdcl/learnt-asserting, cdcl/watcher-audit, cdcl/php-7-6-unsat.

2.6 Pitfalls

  • Watcher not restored on backtrack → corrupt watch lists → dropped propagations → wrong SAT. The classic killer bug. Watches are not trail-scoped (they persist), but their invariant must hold; audit it.
  • Wrong UIP (last-UIP vs 1-UIP) → weaker learning, much slower. Stop at the first UIP.
  • Backjump to wrong level → re-explore or miss propagations. Backjump = second-highest level in learnt clause.
  • Minimization that drops needed literals → unsound learnt clause → wrong UNSAT. Minimize only via valid self-subsumption.
  • Binary-clause watch bugs → silent. Test binary-heavy instances specifically.

2.7 Performance Concerns

BCP is ~80% of runtime; the watcher inner loop must be branch-predictable and cache-friendly (blocker literal avoids dereferencing the clause in the common satisfied case). Keep clauses contiguous; prefetch. Conflict analysis touches reasons — keep the trail dense.

2.8 Edge Cases

Conflict at decision level 0 → UNSAT (top-level). Learnt unit clause → backjump to level 0. Self-loop in reasons (must not happen — assertion). Very long learnt clauses (minimize aggressively). Conflict on the assumption literal (incremental, Phase 11).

2.9 Failure Analysis

A watcher/learning bug produces a wrong answer, not a crash — the worst failure (silent). Detection: differential vs oracle + model self-check (I8) + UNSAT proof check (I9). Containment: paranoid invariant audits localize to a conflict. Recovery: ddmin minimizes the instance; add to regression corpus. This phase's correctness is the project's correctness.

2.10 Operational Notes

Stats: conflicts, learnts, learnt_avg_len, props_per_conflict, bcp_seconds. --paranoid enables I2/I3 audits. Every learnt clause optionally streamed to the DRAT trace (Phase 5).

Phase 3 — Branching, Restarts, Clause-DB Management

3.1 Objectives

Make the core competitive: VSIDS/EVSIDS activity branching with phase saving, Luby + glucose (LBD) restarts, and LBD-driven clause deletion.

3.2 Detailed Implementation Steps

VSIDS is from Chaff (Moskewicz et al. 2001, ADR-06); LBD-driven deletion + glucose restarts from Glucose (Audemard & Simon 2009, ADR-09/10); never delete a locked reason clause (P2: the trail is truth). Tie-breaks ordered for determinism (I14, P7).

  • VSIDS: per-variable activity; bump on appearing in conflict analysis; decay all (implemented as increasing var_inc); decide pops the max-activity unassigned var from a binary heap; rescale activities when they overflow.
  • EVSIDS variant (exponential) for efficiency; pick one, document.
  • Phase saving: remember each variable's last assigned phase; decide reuses it (locality — re-find the same partial solution after restart).
  • Restarts: Luby sequence (guaranteed-complete schedule) and glucose-style (restart when recent LBD average exceeds long-term average); selectable.
  • LBD (glue): number of distinct decision levels in a learnt clause; low LBD = high quality. Compute on learn.
  • reduce: periodically delete ~half of high-LBD, low-activity learnt clauses; never delete clauses currently used as a reason (locked) or binary/unit.

3.3 Deliverable

A solver that solves hard SATLIB/competition instances in reasonable time; stats show healthy restart + deletion behavior.

3.4 Acceptance Criteria

  • Solves instances Phase 2 times out on (e.g. larger crafted unsat).
  • Restart + deletion preserve correctness (still matches oracle on small; UNSAT proofs still check).
  • Memory stays bounded under clause deletion (no unbounded learnt growth).
  • Determinism preserved under a fixed seed (I14).

3.5 Conformance Fixtures

heur/vsids-progress, heur/phase-saving, restart/luby, restart/glucose-lbd, reduce/db-bounded, heur/determinism-seed.

3.6 Pitfalls

  • Deleting a locked clause (current reason) → dangling reason → crash/wrong. Lock reasons; never delete them.
  • Activity overflow → NaN/garbage order. Rescale on threshold.
  • Restarting too aggressively → never finishes a promising subtree; too rarely → stuck. Tune via LBD signal.
  • Non-deterministic heap tie-break → flaky. Break ties by var index (I14).

3.7 Performance Concerns

Heap operations on decide/bump are frequent — keep the heap compact. LBD computation walks the learnt clause once. Deletion compacts the arena (relocate refs) — amortize. Phase saving improves cache reuse of the assignment.

3.8 Edge Cases

All activities equal at start (index order); restart at level 0 (no-op); deletion when almost all clauses are locked (skip); seed=0 vs random.

3.9 Failure Analysis

Bad heuristics don't cause wrong answers, only slowness — but a deletion bug (removing a reason) does cause wrong answers/crashes. Detection: correctness suite must stay green across these changes; if a proof stops checking after enabling deletion, the deletion is unsound. Recovery: bisect the heuristic change.

3.10 Operational Notes

Stats: restarts, lbd_avg, db_reductions, learnts_deleted, vsids_rescales. --restart luby|glucose, --seed N. These knobs are the primary performance-tuning surface.

Phase 4 — Preprocessing and Inprocessing

4.1 Objectives

Shrink the formula before and during search: Tseitin CNF conversion, top-level unit + pure-literal elimination, subsumption + self-subsuming resolution, bounded variable elimination (BVE), blocked-clause elimination (BCE).

4.2 Detailed Implementation Steps

BVE + self-subsuming resolution follow Eén & Biere (SatELite, SAT 2005, ADR-07 occurrence lists); preprocessing must stay equisatisfiable and its steps emitted to the proof so it still checks (I9), and the elimination stack preserves the SAT-model self-check on the original formula (I8).

  • Tseitin: convert arbitrary Boolean structure (from SMT abstraction or non-CNF input) to CNF with fresh aux vars, preserving satisfiability; Plaisted-Greenbaum polarity optimization to halve clauses.
  • Unit propagation at level 0: assign + remove satisfied clauses / shrink others.
  • Pure literal: a variable appearing in only one polarity can be fixed.
  • Subsumption: clause C subsumes D if C ⊆ D (D removed); use occurrence lists + signatures.
  • Self-subsuming resolution: if resolving C and D on a literal yields a clause subsuming D, strengthen D.
  • BVE: eliminate a variable by resolving all its positive × negative clauses, if the result doesn't grow the formula (bounded); the SatELite technique.
  • BCE: remove clauses blocked on a literal (no resolvent is non-tautological).
  • Inprocessing: run cheap simplifications periodically during search (between restarts), reconstructing models for eliminated vars on SAT.
  • Model reconstruction: maintain an elimination stack so a SAT model over the simplified formula extends to the original (critical — eliminated vars must be re-derived).

4.3 Deliverable

Preprocessing measurably reduces var/clause counts and end-to-end solve time; model reconstruction yields a valid original-formula model.

4.4 Acceptance Criteria

  • Simplified formula is equisatisfiable (differential: same SAT/UNSAT as unsimplified).
  • SAT model reconstructs to satisfy the original formula (I8 on original).
  • BVE bounded (never blows up clause count beyond the cap).
  • UNSAT proofs account for preprocessing steps (DRAT includes elimination — checks).

4.5 Conformance Fixtures

pre/tseitin-equisat, pre/unit-pure, pre/subsume, pre/bve-bounded, pre/bce, pre/model-reconstruct, pre/proof-with-elim.

4.6 Pitfalls

  • Forgetting model reconstruction → SAT model invalid for original (eliminated vars unset). Maintain + replay the elimination stack.
  • Unbounded BVE → quadratic blowup, OOM. Enforce the growth bound.
  • Preprocessing breaking the proof → DRAT no longer checks. Emit elimination steps to the proof.
  • Subsumption with stale occurrence lists → miss/incorrect removals. Update lists on every change.

4.7 Performance Concerns

Subsumption is O(clauses²) naively — use signatures (bitset of literal hashes) to prune comparisons. BVE touches occurrence lists heavily — bound work per call. Inprocessing must not dominate search time — budget it.

4.8 Edge Cases

A variable eliminated then needed for explanation (it's gone — reconstruct); preprocessing that makes the formula trivially SAT/UNSAT (short-circuit); empty formula after simplification; interaction with assumptions (don't eliminate assumption vars).

4.9 Failure Analysis

A preprocessing soundness bug changes the answer. Detection: differential against the unsimplified solver on the whole corpus; proof must still check (I9). Containment: each technique behind a flag — bisect by disabling. Recovery: minimize + regression.

4.10 Operational Notes

Stats: pre_vars_removed, pre_clauses_removed, bve_eliminated, subsumed, inprocess_calls. --no-preprocess, --bve-bound N. Reconstruction stack size is a memory signal.

Phase 5 — Proofs, Cores, Model Verification

5.1 Objectives

Make answers trustworthy: emit a DRAT trace for UNSAT (externally checkable), extract unsat cores over assumptions, and self-verify SAT models.

5.2 Detailed Implementation Steps

DRAT is the clausal proof system of Heule, Hunt & Wetzler (ADR-18, P14: reproducible proofs); the trace must check against DRAT-trim (I9) and SAT models are self-verified before reporting (I8, P1).

  • DRAT emission: on each learnt clause, append it to the trace; on each deletion, append a d line. The trace is the resolution/RAT proof of UNSAT.
  • DRAT-trim integration: CI runs the external checker on every UNSAT conformance instance (I9).
  • Unsat core: solve under assumptions; on UNSAT, the final conflict analysis at level 0 yields the subset of assumptions responsible (the "failed assumptions"); for SMT, map back to named assertions.
  • Model verification: on SAT, re-evaluate every original clause (and theory atom, later) under the model (I8); refuse to report SAT if it fails.
  • Core minimization: optionally minimize the core (iteratively drop assumptions, re-solve).

5.3 Deliverable

Every UNSAT result ships a DRAT proof that DRAT-trim accepts; every SAT result is self-verified; cores returned for assumption-based queries.

5.4 Acceptance Criteria

  • 100% of UNSAT conformance instances produce DRAT proofs that check (I9).
  • SAT models pass internal verification (I8) on 100% of SAT instances.
  • Cores are unsatisfiable subsets (removing any one makes it SAT — for minimal cores).

5.5 Conformance Fixtures

proof/drat-checks, proof/sat-self-verify, core/failed-assumptions, core/minimal, proof/with-preprocessing.

5.6 Pitfalls

  • Proof missing deletion lines → DRAT-trim slow or rejects. Emit d lines matching deletions.
  • Proof order mismatch → checker fails. Emit in learn order exactly.
  • Core includes irrelevant assumptions → less useful. Minimize.
  • Trusting SAT without verification → ships wrong answers. Always self-verify (I8).

5.7 Performance Concerns

DRAT I/O can rival solve time on hard instances — stream to a buffered file, don't hold in memory. Self-verification is O(formula) — cheap relative to solving. Core minimization re-solves — bound iterations.

5.8 Edge Cases

Empty proof (formula UNSAT at level 0 by unit prop); SAT with no assumptions (no core); proof for a preprocessed formula (must include elimination); huge proofs (multi-GB — stream + optionally compress).

5.9 Failure Analysis

If a proof doesn't check, the UNSAT claim is unsubstantiated — treat as a potential soundness bug, not just a proof bug. Detection: DRAT-trim in CI gates releases. Recovery: the failing instance is gold for debugging the core engine.

5.10 Operational Notes

Stats: proof_bytes, proof_clauses, core_size, model_verify_ms. --proof out.drat, --check-proof (run checker inline). This phase operationalizes principles 1, 9, 14.

Phase 6 — DPLL(T) Framework: The Theory Interface

6.1 Objectives

Wire the SAT core to pluggable theories: Boolean abstraction, theory propagation, T-conflict explanation as learnt clauses, and backtrackable theory state. No concrete theory yet beyond a trivial one for testing.

6.2 Detailed Implementation Steps

  • Abstraction: smt frontend maps each theory atom to a Boolean var (I7); the CNF over these proxies goes to the SAT core.
  • Notification: when the core assigns a proxy var, call theory.assert_lit(atom-literal).
  • Lazy check: at Boolean propagation fixpoint, call theory.check(full=true); on Conflict(expl), learn the explanation clause (over proxies) and backjump (P5/P11).
  • Theory propagation: between decisions, call theory.propagate() for cheap implied literals; enqueue them with a lazy reason (call explain only if that literal participates in a later conflict).
  • Backtracking: on backjump to level L, call theory.pop() so theory state matches the trail (I6); on new decision level, theory.push().
  • Model: on SAT, assemble Boolean + each theory's model() (I8).
  • Test theory: a "difference" or trivial equality theory to validate the protocol before EUF.

6.3 Deliverable

The DPLL(T) loop runs end-to-end with a stub theory; theory conflicts are learnt and drive backjumping; push/pop tracks the trail.

6.4 Acceptance Criteria

  • Theory conflict → learnt clause → correct backjump → eventual SAT/UNSAT.
  • push/pop restores exact theory state (I6 checkpoint-hash test).
  • Theory propagation reduces decisions (measurable) without changing the answer.
  • Atom↔var bijection holds throughout (I7).

6.5 Conformance Fixtures

dpllt/stub-theory-sat, dpllt/stub-theory-conflict, dpllt/pushpop-restore, dpllt/propagation-reduces-decisions, dpllt/atom-bijection.

6.6 Pitfalls

  • Theory state desync from trail → phantom conflicts / missed conflicts. push/pop must mirror every level (I6, P2).
  • Eager full checks → runtime dominated by theory. Check only at Boolean fixpoint (P11).
  • Lazy explanation that's stale → unsound reason. Capture enough to reconstruct a valid explanation at conflict time (I5).
  • Forgetting to assert ¬atom when proxy=false → theory sees half the constraints. Assert both polarities.

6.7 Performance Concerns

assert_lit is called per assignment — keep it cheap (queue work, defer to check). Theory propagation must be cheaper than the decisions it saves. Explanation generation is rare (only on conflict) so can be more expensive.

6.8 Edge Cases

Theory atom that's also Boolean-forced (consistent handling); a literal both theory-propagated and Boolean-propagated (dedupe); backjump past a theory push with no matching state (assertion); empty theory (pure SAT — bypass).

6.9 Failure Analysis

A desync between trail and theory state is the signature DPLL(T) bug — it manifests as wrong answers under specific backjump sequences. Detection: I6 checkpoint hashing in paranoid mode; differential vs Z3 on theory instances. Recovery: log the trail + theory-op sequence; replay.

6.10 Operational Notes

Stats: theory_checks, theory_conflicts, theory_propagations, theory_push_pop. --theory-paranoid validates I6. This framework is reused unchanged by every theory in Phase 7–9.

Phase 7 — Theory of EUF (Congruence Closure)

7.1 Objectives

Decide equality with uninterpreted functions: a=b ∧ f(a)≠f(b) is UNSAT. Union-find + signature table + proof-producing explanations.

7.2 Detailed Implementation Steps

  • Union-find over term ids, union-by-rank + path compression.
  • Signature table: for each function application f(t1..tn), key by (f, find(t1)..find(tn)); if two apps share a signature, their results are congruent → merge.
  • assert_lit: a=b → merge(a,b) → propagate congruences (re-canonicalize affected apps, merge new collisions to fixpoint); a≠b → record disequality, conflict if find(a)==find(b).
  • check: verify no asserted disequality has equal representatives.
  • explain: proof forest (Nieuwenhuis–Oliveras) records why each union happened; explain_eq(a,b) walks the forest to the set of input equalities + congruence steps → the conflict clause (I11, I5).
  • propagate: if a≠b asserted and a merge would make them equal, propagate the negation; equality propagation to combination layer (Phase 10).

7.3 Deliverable

QF_UF solving: cli solve euf.smt2 returns correct sat/unsat with models (an equivalence-class assignment) and cores.

7.4 Acceptance Criteria

  • Matches Z3 on QF_UF conformance subset (differential).
  • Congruence complete: every implied equality derived (I11 audit).
  • Explanations sound + minimal (replay check, I5).
  • push/pop on the union-find restores exactly (I6).

7.5 Conformance Fixtures

euf/congruence-basic, euf/diseq-conflict, euf/nested-functions, euf/explain-minimal, euf/vs-z3-qfuf, euf/pushpop.

7.6 Pitfalls

  • Not re-canonicalizing apps after merge → missed congruences (I11 breach) → wrong SAT. Maintain use-lists; re-examine on every merge.
  • Path compression breaking the proof forest → can't explain. Keep explanation edges separate from the find-parent pointers.
  • Disequality checked only at assert, not after later merges → missed conflict. Re-check on merge.
  • Union-find backtrack → must undo merges in reverse (I6). Record a merge log.

7.7 Performance Concerns

find is near-O(1) amortized; use-lists make congruence propagation proportional to affected apps. Signature table is hot — fast hash. Explanation is O(path) — acceptable (rare).

7.8 Edge Cases

Reflexive a=a (no-op); function of arity 0 (constant); deeply nested f(f(f(x))); disequality between congruent terms (conflict); predicate symbols (treat as functions to a Bool sort).

7.9 Failure Analysis

Missed congruence → wrong SAT (silent). Detection: I11 audit (recompute all signatures, compare); differential vs Z3. Containment: paranoid signature audit after each check. Recovery: minimize, regress.

7.10 Operational Notes

Stats: cc_merges, cc_congruences, cc_diseqs, explain_len_avg. EUF is the simplest theory and the template for the interface; its explanation machinery is reused conceptually by others.

Phase 8 — Theory of Linear Arithmetic (Simplex + Branch-and-Cut)

8.1 Objectives

Decide linear arithmetic over reals (QF_LRA) via the Dutertre–de Moura simplex, and over integers (QF_LIA) via branch-and-bound + Gomory cuts, all in exact rationals (ADR-11) for soundness.

8.2 Detailed Implementation Steps

Implements the Dutertre–de Moura simplex (CAV 2006, ADR-12) in exact rationals (ADR-11, P1) with Bland's anti-cycling rule for termination (I10); conflict explanations must be entailed and minimal (P5/P9, I5).

  • Representation: each arithmetic atom is a bound on a (possibly fresh slack) variable: t ≤ c, t ≥ c, t = c where t = Σ aᵢxᵢ is introduced as a basic variable.
  • General simplex (LRA): tableau of basic = linear combo of nonbasic; maintain an assignment satisfying all equalities; assert_bound tightens a bound; check pivots (select a basic var violating its bound, pivot in a suitable nonbasic) until all bounds satisfied or infeasibility detected; Bland's rule on degeneracy guarantees termination (I10).
  • Conflict explanation: an infeasible row gives the subset of bounds (atoms) that are mutually inconsistent → the T-conflict clause.
  • Theory propagation: bounds implied by the current tableau (a derived bound tighter than asserted) → propagate the corresponding atom.
  • LIA: solve the LRA relaxation; if the model is integral, done; else branch on a fractional variable (x ≤ ⌊v⌋ ∨ x ≥ ⌈v⌉) — implemented as a lemma the SAT core splits on — and/or add Gomory cuts; bound the branch depth.
  • Exact rationals via bignum (rug/GMP) — no float, no overflow.

8.3 Deliverable

QF_LRA and QF_LIA solving with models (rational/integer values) and cores; matches Z3 on the conformance subset.

8.4 Acceptance Criteria

  • LRA: correct sat/unsat; model satisfies all asserted bounds exactly (I8).
  • LIA: integral models; branch-and-cut terminates within budget; correct on conformance.
  • Simplex never cycles (I10 — pivot count bounded, Bland's engaged on degeneracy).
  • Differential vs Z3 on QF_LRA/QF_LIA.

8.5 Conformance Fixtures

lra/sat-model, lra/unsat-explain, lia/branch-and-bound, lia/gomory-cut, arith/exact-no-overflow, arith/bland-no-cycle, arith/vs-z3.

8.6 Pitfalls

  • Floating point → rounding → wrong sat/unsat (soundness). Exact rationals only.
  • Simplex cycling on degeneracy → nontermination. Bland's rule (I10).
  • Branch-and-bound divergence (unbounded integer search) → loops forever. Bound + detect; return unknown on budget (I15).
  • Wrong conflict explanation (non-minimal infeasible set) → bloated lemmas. Extract the tight infeasible row.
  • Strict vs non-strict bounds (< vs ≤) → use the δ-rationals trick (value + δ·infinitesimal).

8.7 Performance Concerns

Pivoting is the cost; keep the tableau sparse where possible (though general simplex is dense-ish). Bignum arithmetic is expensive — normalize fractions, avoid blowup of numerator/denominator size. Theory propagation of bounds can be frequent — budget it.

8.8 Edge Cases

Empty bound set (trivially sat); equality bound (lo=hi); contradictory bounds on one var (immediate conflict); unbounded direction (LRA sat with a ray); large coefficients (bignum handles); mixed strict/non-strict yielding empty open interval.

8.9 Failure Analysis

A float creeping in, or a cycling pivot, are the two classic LRA disasters — one silent-wrong, one hang. Detection: exact-arithmetic assertions (no float type in the module); pivot-count cap with cycle detection; differential vs Z3. Recovery: minimize; the offending instance often has degenerate geometry — keep it.

8.10 Operational Notes

Stats: simplex_pivots, simplex_checks, lia_branches, gomory_cuts, rational_max_bits. --lia-branch-limit N. Rational bit-width growth is a memory/perf signal.

Phase 9 — Theory of Bit-Vectors (Bit-Blasting) and Arrays

9.1 Objectives

Decide fixed-width bit-vectors (QF_BV) by bit-blasting to the SAT core, and arrays (QF_ABV) via lazy read-over-write + extensionality axioms.

9.2 Detailed Implementation Steps

Bit-blasting to the CDCL core (ADR-14) must be semantics-preserving — the blasted circuit is SAT iff the BV formula is (I12), guarded by the exhaustive ≤8-bit differential; arrays reuse the EUF machinery (Phase 7) with lazy axioms (ADR-15) to honor P11 (lazy theory checking).

  • Bit-blasting: each n-bit BV term → n Boolean vars; compile each operation to a propositional circuit: bvand/bvor/bvnot bitwise; bvadd ripple-carry (or carry-lookahead); bvmul shift-add (O(n²) clauses); bvult/bvule comparison circuits; concat/extract/bvshl/bvlshr wiring + muxes; equality = bitwise XNOR conjunction. Feed all generated clauses to the CDCL core.
  • Arrays (lazy): treat select/store as uninterpreted (EUF) plus on-demand axioms: read-over-write select(store(a,i,v),j) = (i=j ? v : select(a,j)) instantiated when a conflicting pattern appears; extensionality a=b ∨ select(a,k)≠select(b,k) for some witness k when array equalities are compared. Add lemmas incrementally (lazy) to avoid axiom blowup.
  • Combination hooks: BV and arrays export equalities to the N-O layer (Phase 10) when mixed with EUF/arith.

9.3 Deliverable

QF_BV and QF_ABV solving with models (bit-vector values, array as a function table); matches Z3 on the conformance subset.

9.4 Acceptance Criteria

  • BV: blasted circuit is semantics-preserving (I12 — differential vs brute-force on small widths, e.g. ≤ 8 bits exhaustive).
  • Arrays: rd-over-wr + extensionality correct on conformance; lazy instantiation terminates.
  • Models: BV assignment + array tables satisfy the formula (I8).
  • Differential vs Z3 on QF_BV/QF_ABV.

9.5 Conformance Fixtures

bv/arith-circuits, bv/shift-extract-concat, bv/mul-overflow, bv/blast-vs-brute-8bit, arr/read-over-write, arr/extensionality, abv/combined, bv/vs-z3.

9.6 Pitfalls

  • Off-by-one in bit ordering / sign → wrong arithmetic (silent). Exhaustive small-width differential (I12) catches it.
  • Multiplier clause explosion → OOM on wide multiplies. Track clause growth; warn/limit.
  • Eager array axioms → exponential blowup. Instantiate lazily, only on demand.
  • Extensionality witness mismanagement → wrong array (dis)equality. Introduce a fresh index witness correctly.

9.7 Performance Concerns

Bit-blasting can dwarf the original formula (esp. multiply, O(n²)); the SAT core then dominates — preprocessing on the blasted CNF helps. Lazy array axioms keep the formula small but add solve rounds. Cache blasted subterms (hash-consing pays off).

9.8 Edge Cases

1-bit vectors (Boolean); zero-width (reject); shift by ≥ width (defined per SMT-LIB — zero/wrap); signed vs unsigned compare; nested stores; array of arrays; bvudiv/bvurem by zero (SMT-LIB defines result). Full SMT proof certificates for theory steps: PhaseDeferred("Stretch Goals").

9.9 Failure Analysis

A blasting bug is silent-wrong; the exhaustive small-width differential (I12) is the primary guard — run it for every operation. Array axiom bugs manifest on specific store/select patterns; keep a rich array corpus. Recovery: minimize widths, differential vs Z3.

9.10 Operational Notes

Stats: bv_blasted_vars, bv_blasted_clauses, array_axioms_instantiated, array_lemmas. --bv-blast-limit. Blasted clause count is the key BV scaling signal.

Phase 10 — Theory Combination (Nelson-Oppen)

10.1 Objectives

Solve formulas mixing theories (e.g. f(x) = y ∧ x + 1 ≤ y ∧ y ≤ x over EUF+LIA) by Nelson-Oppen combination: purify mixed terms, share variables, exchange entailed equalities.

10.2 Detailed Implementation Steps

  • Purification: rewrite a mixed term so each atom is pure in one theory, introducing fresh shared variables for the boundary subterms (e.g. f(x+1) → introduce w = x+1 (arith), f(w) (EUF)).
  • Shared variables: variables appearing in ≥2 theories are the exchange surface.
  • Equality exchange: each theory, after check, reports entailed equalities over shared variables; these are propagated to the other theories as new asserted equalities; iterate to fixpoint (I13 — only entailed equalities, soundness).
  • Convexity / case-splitting: LIA is non-convex (may entail a disjunction of equalities); handle by case-splitting (delegate the disjunction to the SAT core as a lemma) — the Nelson-Oppen requirement for non-convex theories.
  • Model: combine per-theory models consistently on shared variables.
  • Determinism: fixed theory order + ordered equality propagation (I14).

10.3 Deliverable

Combined-theory solving (QF_UFLIA, QF_UFLRA, QF_AUFBV subsets) correct vs Z3; equality exchange visible in stats.

10.4 Acceptance Criteria

  • Correct sat/unsat on combined conformance (differential vs Z3).
  • Only entailed shared equalities propagated (I13 — soundness audit).
  • Non-convex case-splitting terminates and is correct.
  • Models agree on shared variables across theories (I8).

10.5 Conformance Fixtures

combine/uf-lia-unsat, combine/uf-lra-sat, combine/purification, combine/nonconvex-split, combine/shared-eq-exchange, combine/vs-z3.

10.6 Pitfalls

  • Propagating a non-entailed equality → wrong UNSAT (I13 breach). Each theory must only export equalities it can prove.
  • Missing the non-convex split → incompleteness (wrong SAT). LIA needs case-splitting; don't skip it.
  • Purification name capture → wrong sharing. Fresh, unique shared vars.
  • Combination loop non-termination → equalities ping-pong. Propagate to fixpoint with a worklist; equalities only ever merge (monotone).

10.7 Performance Concerns

Equality exchange iterates — keep per-round work bounded; share only over the (usually small) shared-variable set. Non-convex splitting multiplies SAT search — minimize the introduced disjunctions. Model-based theory combination (cheaper in practice) is a Phase-2 optimization.

10.8 Edge Cases

No shared variables (theories independent — no exchange); a single shared variable equal across all; theory entailing x=y and y=z (transitive); empty theory in the mix; combining three+ theories.

10.9 Failure Analysis

Combination bugs are subtle and silent — wrong answers only on mixed instances. Detection: extensive combined differential vs Z3; I13 entailment audit (re-prove each exported equality independently). Recovery: minimize across theories (hard — keep both theory traces).

10.10 Operational Notes

Stats: combine_shared_vars, combine_eq_exchanged, combine_splits, combine_rounds. --combine-order. This phase is where multi-theory correctness lives — the most-tested integration point.

Phase 11 — SMT-LIB 2 Command Loop and Incremental Solving

11.1 Objectives

Expose the full external contract: the SMT-LIB 2 command loop with incremental push/pop, named assertions, assumptions, get-model/get-value/get-unsat-core — the interface verification tools actually call (P10).

11.2 Detailed Implementation Steps

  • Command interpreter: set-logic, set-option, declare-sort, declare-fun, define-fun, assert, check-sat, check-sat-assuming, push, pop, get-model, get-value, get-unsat-core, get-info, reset, exit.
  • Assertion stack: push saves a scope; pop discards assertions (and learnt clauses derived solely under them) and restores SAT + theory state in O(Δ) (P10, I6).
  • Incremental SAT: keep learnt clauses across check-sat calls when sound (clauses not dependent on popped assertions); use assumptions for cheap per-query constraints.
  • Named assertions (:named) → unsat core maps failed assumptions back to names.
  • Models/values: get-model from the combined theory models; get-value evaluates terms under the model.
  • Output exactly per SMT-LIB (sat/unsat/unknown, S-expression responses).

11.3 Deliverable

A spec-conformant solve that runs SMT-LIB 2 scripts incrementally; passes the SMT-LIB response-format checks.

11.4 Acceptance Criteria

  • Incremental script (push/assert/check/pop/check) yields correct results at each check (vs Z3).
  • push/pop is O(Δ), not full rebuild (timing test on a deep stack).
  • Unsat cores reference the correct named assertions.
  • Output is byte-conformant SMT-LIB where specified.

11.5 Conformance Fixtures

11.6 Pitfalls

  • Keeping learnt clauses that depend on popped assertions → unsound after pop. Track clause provenance vs assertion level; drop dependent learnts.
  • Full rebuild on pop → defeats incrementality. Scope theory + SAT state by level (I6).
  • Model after unsat / core after sat → spec violation. State-machine guards.
  • Assumption literals leaking into the permanent formula → wrong later queries. Assumptions are per-check, not asserted.

Incremental reuse (learnt clauses, theory state) is the whole point — verification loops do thousands of checks. Provenance tracking must be cheap. get-value evaluation is O(terms).

11.8 Edge Cases

11.9 Failure Analysis

Phase 12 — Optimization, Tuning, and Optional Portfolio

12.1 Objectives

Close the performance gap: modern branching (LRB/CHB as alternatives to VSIDS), aggressive inprocessing scheduling, and an optional multi-thread portfolio (diverse configs racing). Portfolio parallelism fulfils PhaseDeferred("Stretch Goals").

12.2 Detailed Implementation Steps

  • LRB (Learning Rate Branching) / CHB as selectable branchers; compare against VSIDS on the corpus.
  • Inprocessing schedule: interleave BVE/subsumption/vivification with search on a budget; vivification (clause strengthening via propagation) for learnt clauses.
  • Target-phase / rephasing strategies; chronological backtracking option (Nadel-Ryvchin) for specific instance classes.
  • Portfolio (optional, deferred): N threads with different seeds/restart/branch configs; first to finish wins; share short learnt clauses (LBD ≤ k) via a lock-free queue; deterministic mode disables sharing for reproducibility (I14 vs speed tradeoff — documented).

12.3 Deliverable

Measurable speedup on the hard corpus; portfolio (if enabled) beats single-thread on a diverse benchmark set.

12.4 Acceptance Criteria

  • New branchers preserve correctness (full suite green) and improve median solve time on the benchmark set.
  • Portfolio is correct (every thread is a sound solver) and faster wall-clock on hard instances.
  • Deterministic single-thread mode unchanged (I14).

12.5 Conformance Fixtures

opt/lrb-vs-vsids, opt/vivification, opt/chrono-backtrack, portfolio/correct, portfolio/speedup, portfolio/deterministic-off.

12.6 Pitfalls

  • Clause sharing corrupting a thread's arena → crash/wrong. Copy shared clauses into the receiver's arena; never share refs.
  • Non-determinism from portfolio breaking conformance. Gate sharing behind a non-deterministic flag; CI uses single-thread deterministic mode.
  • Vivification removing needed literals → unsound. Strengthen only via valid propagation.

12.7 Performance Concerns

Branching choice has large variance across instance families — no universal winner; expose the knob. Inprocessing budget vs search budget is a balance. Portfolio scales sub-linearly (shared structure); memory ×N.

12.8 Edge Cases

Single-core machine (portfolio = 1 thread); extremely easy instances (overhead dominates — short-circuit); sharing queue full (drop, don't block).

12.9 Failure Analysis

Portfolio + sharing is the most concurrency-bug-prone code; keep each solver fully independent except for the explicit, copied clause-sharing channel. Detection: run portfolio under tsan; correctness suite per-thread. Recovery: disable sharing (still correct, just slower).

12.10 Operational Notes

Stats: branch_policy, vivifications, portfolio_threads, shared_clauses_in/out. --threads N, --branch vsids|lrb|chb, --deterministic. Document that --threads >1 trades reproducibility for speed.

Domain Deep Dive — Anatomy of a Conflict (CDCL → DPLL(T))

The conflict-analysis loop is the soul of the solver. Walk one all the way through, first propositional then theory-aware.

D.1 Propositional 1-UIP, step by step

Clauses: c1=(¬1∨2), c2=(¬1∨3), c3=(¬2∨¬3∨4), c4=(¬4∨5), c5=(¬4∨6), c6=(¬5∨¬6). Decide 1@1 (variable 1 true at level 1):

BCP: 1 → c1 ⇒ 2@1 (reason c1); c2 ⇒ 3@1 (c2); c3 ⇒ 4@1 (c3); c4 ⇒ 5@1 (c4); c5 ⇒ 6@1 (c5)
c6 = (¬5 ∨ ¬6): both 5,6 true ⇒ CONFLICT
analyze: start from c6 {¬5,¬6}. Both at level 1. Resolve on the last-assigned (6) against its reason c5={¬4,6}:
   {¬5,¬6} ⊗6 {¬4,6} = {¬5,¬4}. Resolve on 5 against c4={¬4,5}: {¬4,¬4}={¬4}.
   Now exactly one literal at level 1 (¬4) → 4 is the 1-UIP.
learnt = (¬4); backjump level = 0 (no other level). Assert ¬4 at level 0.

The learnt clause (¬4) captures the real reason: 4 forces the contradiction regardless of how we reached it. Next time 4 is never assigned true without justification — exponential pruning from one conflict.

D.2 Why 1-UIP and not "the decision"

We could learn (¬1) (the decision-cut). But (¬4) is stronger: it prunes every future branch where 4 becomes true, not just this exact decision. The 1-UIP is the unique literal that, alone at the conflict level, dominates the conflict — the tightest single-literal explanation. Learning it is the difference between CDCL and exponential DPLL.

D.3 The same loop, theory-aware

Now atoms are arithmetic: suppose proxies b1=(x≥2), b2=(y≥2), b3=(x+y≤3). The SAT core decides b1@1, b2@2, b3@3 all true. At Boolean fixpoint, theory.check(full) runs Simplex on {x≥2, y≥2, x+y≤3} → infeasible. explain() returns the minimal infeasible bound set {b1,b2,b3} → T-conflict clause (¬b1 ∨ ¬b2 ∨ ¬b3). The core learns it exactly like a propositional clause and backjumps. From the core's view, nothing special happened — a clause appeared and a conflict resolved. That uniformity (P5: theory lemmas are just clauses) is the entire elegance of DPLL(T).

D.4 Theory propagation closes the loop tighter

Better: after b1=(x≥2) and b3=(x+y≤3) are assigned, Simplex can propagate y ≤ 1, i.e. force proxy b2=(y≥2) to false before the core decides it — with lazy reason {b1,b3}. This prunes the search like Boolean unit propagation, but driven by arithmetic. The art of a fast SMT solver is propagating cheaply and often (P11) so the expensive full check rarely finds a conflict the propagation didn't already prevent.

D.5 Where bugs hide

Every silent-wrong bug in this project lives in one of three places: (1) the watcher invariant after backjump (I2) — propositional; (2) the soundness of an explain() (I5/I11/I13) — theory; (3) theory state not matching the trail after pop (I6) — integration. The paranoid-mode audits and differential testing target exactly these three. Master this deep dive and you can debug any DPLL(T) solver.

D.6 Simplex for satisfiability — a worked pivot

The Dutertre–de Moura simplex does not optimize; it seeks feasibility against variable bounds. Tableau form: basic variables are linear combinations of nonbasic ones; every variable has an assignment and optional lo/hi bounds.

Constraints: s1 = x + y, s2 = x − y, with bounds s1 ≥ 2, s1 ≤ 4, s2 ≤ 1, x ≥ 0, y ≥ 0. Start: all nonbasic at 0 → x=y=0, s1=0, s2=0.

check: s1=0 violates s1≥2 (lower bound). s1 is basic and too low.
  → need to increase s1. s1 = x + y; increasing a nonbasic with positive coeff raises s1.
  pick nonbasic x (coeff +1), able to increase (x has no upper bound) → pivot x into basis for s1.
  raise s1 to its bound 2 ⇒ x = 2 (y still 0). Now s1=2 ✓.
recheck: s2 = x − y = 2 − 0 = 2, violates s2 ≤ 1 (upper). s2 too high.
  → decrease s2. s2 = x − y; decrease by lowering x (coeff +1) or raising y (coeff −1).
  x is basic now (tied to s1's bound); raise y instead. Raising y lowers s2 and raises s1.
  but s1 is at its lower bound 2 and may rise to ≤4 (slack of 2). Raise y by 1 ⇒ s2=1 ✓, s1=3 ✓ (≤4).
result: x=2, y=1, s1=3, s2=1 — all bounds satisfied ⇒ SAT, model (x=2, y=1).

If instead we had added s1 ≥ 5, no pivot could satisfy s1≤4 ∧ s1≥5; the violated row whose every increasing/decreasing direction is blocked by an opposite bound yields the infeasible explanation — the exact set of bounds {s1≤4, s1≥5} → the T-conflict clause. Bland's rule (choose the lowest-index eligible entering/leaving variable) guarantees we never cycle through the same degenerate bases (I10). Everything is exact rationals — x=2, y=1 here, but x=7/3 is represented precisely, never 2.333….

D.7 Bit-blasting a 2-bit multiplier — why BV is "just" SAT

(bvmul a b) with a=a1a0, b=b1b0 (2-bit). Product is 4-bit p3p2p1p0. Partial products (AND gates): pp00=a0∧b0, pp01=a1∧b0, pp10=a0∧b1, pp11=a1∧b1. Sum them with adders:

p0 = pp00
p1 = pp01 XOR pp10                 carry c1 = pp01 AND pp10
p2 = pp11 XOR c1                   carry c2 = pp11 AND c1
p3 = c2

Each XOR/AND becomes Tseitin clauses over fresh Booleans (e.g. t=u∧v ≡ (¬t∨u)∧(¬t∨v)∧(t∨¬u∨¬v)). A 2-bit multiply is a handful of clauses; an n-bit multiply is O(n²) partial products → the clause blowup Phase 9 warns about. The CDCL core then solves the resulting CNF with no idea it is "multiplication." This is the entire trick of QF_BV: compile arithmetic to a circuit, let the SAT engine reason about the circuit. Correctness is verified by the exhaustive ≤8-bit differential (I12): enumerate all a,b, check the blasted result equals the true product.

D.8 An incremental session — what the client actually drives

Verification tools rarely ask one question; they ask thousands, each a small delta on the last (path conditions in symbolic execution, frame conditions in a model checker). The incremental contract (Phase 11) is what makes that tractable. Trace the engine state through a session mixing EUF + LIA:

(set-logic QF_UFLIA)
(declare-fun f (Int) Int) (declare-fun x () Int) (declare-fun y () Int)
(assert (! (= (f x) (f y)) :named a1))     ; EUF atom A1, proxy b1; assert permanently
(check-sat)                                  ; trail: b1; EUF: merge classes via congruence
   → sat   (no constraint forces x≠y; model x=y=0, f(·)=0)            [base learnt clauses kept]
(push 1)                                     ; assertion level 1 opens; theory.push()
  (assert (! (= x 2) :named a2))             ; LIA bound x=2  (proxy b2)
  (assert (! (= y 3) :named a3))             ; LIA bound y=3  (proxy b3)
  (assert (! (distinct (f x) (f y)) :named a4)) ; EUF diseq f(x)≠f(y) (proxy b4)
  (check-sat)
     ; N-O: LIA has x=2,y=3 ⇒ x≠y entailed; shared eq exchange tells EUF nothing forces f(x)=f(y),
     ;      but a1 asserted f(x)=f(y) while a4 asserts f(x)≠f(y) ⇒ direct EUF conflict.
     → unsat
  (get-unsat-core) → (a1 a4)                 ; minimal: a2,a3 irrelevant to the contradiction
(pop 1)                                      ; level-1 assertions a2..a4 discarded; theory.pop();
                                             ; learnt clauses derived *using* b2/b3/b4 are dropped (I6/provenance)
(check-sat)                                  ; back to just a1
   → sat                                     ; base learnts from the first check are *reused* (P10)
(exit)

Three things to notice. (1) The core after pop is back to exactly the level-0 state — but the reusable learnt clauses (those depending only on permanent assertions) survive, so the final check-sat is near-instant. (2) The unsat core (a1 a4) correctly omits the arithmetic facts a2,a3 — minimization (Phase 5) earns its keep here. (3) The contradiction was found by EUF alone, but N-O still ran the equality exchange; on a harder instance that exchange is what couples the theories. This single session exercises Phases 5, 6, 7, 8, 10, and 11 at once — it is the canonical integration test.

Consolidated Pitfalls (Top 10, cross-phase)

  1. Watcher invariant violated after backjump — dropped propagation → wrong SAT. Example: a clause whose watched literal was falsified at a now-undone level isn't re-watched. Guard: I2 paranoid audit.
  2. Last-UIP instead of 1-UIP — weaker learning, 10–100× slowdown. Example: stopping conflict analysis too late. Guard: stop at the first single-level literal (I3).
  3. Deleting a locked (reason) clause — dangling reason → crash or wrong answer. Example: reduce() removes a clause currently justifying a trail literal. Guard: lock reasons.
  4. Float in arithmetic — rounding → wrong sat/unsat. Example: 0.1+0.2 ≠ 0.3 decides feasibility. Guard: exact rationals only (ADR-11); no float type compiles in arith.
  5. Simplex cycling — nontermination on degenerate bases. Example: repeated pivots among zero-slack rows. Guard: Bland's rule (I10) + pivot cap.
  6. Missed congruence — a=b but f(a)=f(b) not derived → wrong SAT. Example: not re-canonicalizing applications after a merge. Guard: use-lists + I11 audit.
  7. Bit-blast off-by-one / sign error — silent wrong arithmetic. Example: ripple-carry MSB miswired. Guard: exhaustive ≤8-bit differential (I12).
  8. Eager array axioms — exponential blowup / OOM. Example: instantiating rd-over-wr for every select×store pair upfront. Guard: lazy, on-demand instantiation.
  9. Non-entailed equality in N-O exchange — wrong UNSAT. Example: a theory exports x=y it only guessed. Guard: export only proven equalities (I13) + entailment audit.
  10. Stale learnt clause after pop — wrong answer in incremental mode only. Example: keeping a learnt clause derived under a popped assertion. Guard: clause provenance vs assertion level (I6, Phase 11).

Final Notes

This blueprint deliberately layers two solvers: a self-contained CDCL SAT engine (phases 0–5) that is valuable on its own (dependency resolution #135, model checking #279), and a DPLL(T) SMT layer (phases 6–11) built strictly on top of it through one narrow interface (the Theory trait). The seam between them — Boolean abstraction in, theory lemmas out — is the single most important architectural decision; honor it (P12) and new theories are additive, violate it and the engine ossifies.

Three commitments are non-negotiable and recur in every phase: soundness (a wrong sat/unsat is total failure — guarded by model self-check I8, DRAT proofs I9, and differential testing), exactness (bignum rationals, never floats — I10/ADR-11), and determinism (seeded, ordered — I14 — so every bug reproduces). A solver that is fast but occasionally wrong is worthless; build the correctness scaffolding (paranoid audits, the ddmin minimizer, the differential harness) before chasing speed.

The Phase-0 Done bar is concrete: QF_UF, QF_LRA, QF_LIA, QF_BV, QF_ABV and their N-O combinations, conformance-green against an SMT-LIB subset, with checkable DRAT proofs for the SAT layer and self-verified models. Quantifiers, nonlinear arithmetic, floating-point, full SMT proof certificates, and parallelism are explicitly deferred behind typed PhaseDeferred references and tracked in BUILD_PLAN.md §6. Build the core the owner is here to understand; defer only what genuinely needs more weeks, never the algorithm itself.

Operational Readiness

A solver's "operations" are observability of the search, resource governance, and reproducibility (it is a library/CLI, not a service).

  • Metrics/stats. Counters: conflicts, decisions, propagations, restarts, learnts, deletions, theory checks/conflicts/propagations per theory, simplex pivots, BV blasted clauses, combination rounds. JSON dump (--stats json).
  • Tracing. tracing spans for parse / preprocess / each check-sat / theory checks; level-gated (off in hot loops by default).
  • Logging. Structured, leveled; never log inside BCP at default level (perf). DIMACS/SMT-LIB echo for repro.
  • "Dashboards". A stats summary table per solve; for long solves, periodic progress lines (conflicts/s, current LBD avg, DB size).
  • Resource governance. --timeout, --conflict-limit, --memory-limit → deterministic unknown (I15, P8). Budgets checked at safe points (between conflicts), not async-killed.
  • Reproducibility. --seed; deterministic single-thread mode; pinned build. A bug report = input + flags + seed reproduces exactly.
  • Incident response. Runbooks: wrong-answer.md (self-check failed → ddmin → differential → regress), hang.md (budgets, pivot cap, degeneracy), oom.md (limits, blast/learnt growth), proof-fails-check.md.
  • Debugging toolkit. --paranoid (invariant audits I2/I3/I6/I11), tools/ddmin (delta-debug an instance to a minimal repro), --echo-parsed, --check-proof.
  • Backup/restore. N/A (stateless); the "artifact to keep" is the minimized repro instance added to conformance/.
  • Deployment/upgrade. Library SemVer; SMT-LIB output stable; new theories additive.

Scalability Analysis

  • Bottleneck #1 BCP: dominates runtime; scales with clause count + activity. Mitigations: watched literals, blocker literals, cache-friendly arena, clause deletion to keep the DB small.
  • Bottleneck #2 learnt-clause growth: unbounded learning → OOM + slow BCP. Mitigation: LBD-based deletion keeps only "glue" clauses.
  • Bottleneck #3 bit-blasting: wide multiplies → O(n²) clause blowup → SAT core swamped. Mitigation: clause-growth limits, word-level reasoning (later), preprocessing on blasted CNF.
  • Bottleneck #4 simplex bignum: numerator/denominator growth on pathological instances. Mitigation: normalization, bounded coefficient growth, switch strategies.
  • Bottleneck #5 combination splitting: non-convex theories multiply SAT search. Mitigation: minimize introduced disjunctions; model-based combination (later).
  • Parallel scaling: portfolio is sub-linear (diminishing returns past a few threads; shared structure helps unsat). Cube-and-conquer (deferred — Stretch Goals) scales SAT better but adds a splitting heuristic.
  • Memory scaling: dominated by clause arena + watch lists + (for BV) blasted CNF; bounded by deletion + budgets.
  • Incremental scaling: verification clients do 10³–10⁶ checks; incremental reuse (learnt clauses + theory state) is what makes that tractable — the practical scaling axis for real users.

Mental Models & First Principles

The compressed insights an expert solver engineer carries. Each model: the one-sentence intuition, what it predicts, the bug class you write without it, and where this blueprint applies it.

Read these as a lens, not a glossary: MM1/MM4 are the propositional invariants (trail + watches), MM2 is the soundness asymmetry that ranks all audit effort, MM3 is the performance reality, MM5/MM6/MM9 are the DPLL(T) seam and theory cooperation, MM7/MM8 are the two theory-specific traps (exactness, blow-up), and MM10 is the discipline that makes every other bug debuggable. A reader who holds all ten can predict where a given solver design will break before reading its code.

MM1 — The trail is the program counter; everything else is a cache of it. The current partial assignment is the solver's state; watch lists, theory tableaux, activity scores, and learnt clauses are all derived views that must agree with the trail at every decision level.

  • Predicts: any structure that can desync from the trail is a latent wrong-answer bug, and the fix is always "reconstruct from / re-sync to the trail," never "patch the cache."
  • Bug class without it: you treat theory state, watches, or occurrence lists as independent state mutated ad hoc, and a backjump leaves them stale → phantom or missed conflicts.
  • Applied: P2, I1/I4 (trail), I6 (theory push/pop mirrors levels), Phase 2 (watcher invariant), Phase 6 (theory state tracks the trail), Domain Deep Dive D.5 (where bugs hide).

MM2 — A learnt clause is a proof step you are allowed to forget. Every clause CDCL learns is a resolvent entailed by the input; learning it is sound, deleting it is sound, the only thing that is not sound is learning a clause that is not entailed.

  • Predicts: clause deletion can never cause a wrong answer (only slowdown), but a single unsound learnt clause — propositional minimization gone wrong, or a bad theory explain() — causes wrong UNSAT; so audit what you learn far harder than what you delete.
  • Bug class without it: you fear deletion and hoard clauses (OOM) while under-checking explanation soundness (the actual danger).
  • Applied: P4/P5 (1-UIP + theory lemmas are clauses), P9 (minimization), I3/I5, Phase 3 (deletion is free), Phase 7/8/10 (explanation soundness is the risk).

MM3 — BCP is a memory-bandwidth problem, not a CPU problem. On industrial CNF the solver spends ~80% of its time in propagation, and that time is dominated by cache misses chasing watch lists and clause bodies, not by arithmetic.

  • Predicts: the layout of literals and watchers (packed u32, blocking literal, contiguous arena) moves the wall-clock far more than algorithmic cleverness in the inner loop; profiling will show LLC misses, not instruction count, as the ceiling.
  • Bug class without it: you micro-optimize branches in the propagate loop while pointer-chasing boxed clauses thrashes cache — a 5–10× loss invisible to instruction-level reasoning.
  • Applied: P3/P13, ADR-04/05/07, Phase 2 N.7, Performance Engineering (cache analysis), C1/C2/C5 (capacity model), MM10 below.

MM4 — Two-watched literals are an invariant, not an algorithm. You do not "run" watching; you maintain the property "each clause watches two literals that are unassigned, or the clause is already satisfied/unit/conflicting" across assign and backjump.

  • Predicts: the correctness question is never "did I propagate?" but "does the invariant still hold after this backjump?" — and because watches survive backjumping untouched (only the trail truncates), the audit is a pure structural check.
  • Bug class without it: you try to "undo" watch moves on backtrack (the classic killer bug), corrupting watch lists and silently dropping propagations → wrong SAT.
  • Applied: P3, I2, Phase 2 (the most important phase), Domain Deep Dive D.5, Consolidated Pitfall 1.

MM5 — DPLL(T) is the SAT core wearing a blindfold. The Boolean engine never learns what an atom means; a theory conflict reaches it as nothing but a new clause over proxy variables, indistinguishable from a learnt propositional clause.

  • Predicts: adding a theory cannot require touching the core — if it does, the abstraction has leaked; and every theory technique reduces to "produce a sound clause the blind core can resolve."
  • Bug class without it: you special-case theory knowledge inside the search (e.g. arithmetic hints in decide), and the engine ossifies — new theories become impossible.
  • Applied: P5/P12, I7, Phase 6 (Theory trait), Domain Deep Dive D.3, the "Final Notes" seam.

MM6 — Theory propagation is unit propagation in another language. Just as BCP forces a literal when a clause becomes unit, a theory can force a proxy literal when its constraints entail it (e.g. x≥2 ∧ x+y≤3 forces ¬(y≥2)), feeding the same trail.

  • Predicts: a fast SMT solver propagates cheaply and often so the expensive full check rarely discovers a conflict propagation didn't already prevent; the lever for SMT speed is propagation rate, not check speed.
  • Bug class without it: you rely on full check to catch every theory conflict, exploring exponentially more Boolean assignments than necessary.
  • Applied: P11, Phase 6 (propagate + lazy reason), Phase 8 (bound propagation), Domain Deep Dive D.4.

MM7 — Exactness is a soundness property, not a numerics preference. In a decision procedure the answer is a single bit; one rounding error in a simplex pivot does not "lose precision," it flips SAT↔UNSAT.

  • Predicts: floating point cannot appear anywhere a feasibility decision is made, no matter how much faster; bignum rational growth is the price of correctness and must be managed (normalize, bound — C8), never avoided by switching to floats.
  • Bug class without it: you reach for f64 in the tableau "for speed," and 0.1+0.2 ≠ 0.3 decides a benchmark wrong — silently.
  • Applied: P1, ADR-11, I10, Phase 8 N.6, Consolidated Pitfall 4, Comparative note on Yices/exact LRA (Comparative Architecture).

MM8 — Bit-blasting trades a hard theory for a huge propositional formula. Every QF_BV operation compiles to a circuit; the SAT core then reasons about gates with no idea it is doing arithmetic — correct, simple, and exponentially wasteful on wide multipliers.

  • Predicts: BV scaling is governed by generated clause count, and the multiplier (O(n²) partial products) is the cliff; you size the blast before you write it (C7) and switch to word-level reasoning when n is large.
  • Bug class without it: you bit-blast a 256-bit multiply, generate ~10⁵–10⁶ clauses, and swamp the core.
  • Applied: ADR-14, I12, Phase 9, C7 (multiplier capacity), Domain Deep Dive D.7, ALT-1 (eager bit-blasting, Alternative Architectures).

MM9 — Nelson-Oppen cooperation is the exchange of facts, never guesses. Combined theories agree on satisfiability by propagating only equalities over shared variables that each can prove entailed; a single guessed (non-entailed) equality is a wrong UNSAT.

  • Predicts: combination soundness lives entirely in the entailment check, and non-convex theories (LIA) cannot propagate a disjunction of equalities directly — they must hand the case split to the SAT core.
  • Bug class without it: you let a theory export an equality that merely holds in its current model (the model-based shortcut) without the entailment guarantee N-O requires → unsound combination.
  • Applied: P5, I13, ADR-16, Phase 10, Domain Deep Dive D.8, Comparative note on Z3 model-based combination (Comparative Architecture).

MM10 — Determinism is a debugging tool you build before you need it. A solver whose decisions depend on hash-iteration or address order produces bugs that vanish on the next run; making every tie-break a function of (formula, seed) means every bug reproduces exactly.

  • Predicts: the cost (explicit tie-break ordering) is paid once and repays itself the first time a soundness bug must be minimized with ddmin; conformance flakiness is always a determinism leak, not "a hard instance."
  • Bug class without it: a wrong-answer report cannot be reproduced, ddmin cannot shrink it, and the bug is effectively undebuggable.
  • Applied: P7, I14, ADR-21, Phase 3 (tie-breaks), Operational Readiness (reproducibility), Failure Mode "Non-determinism".

MiniSat. Its one defining decision was radical minimalism: a few thousand lines exposing the CDCL core with no preprocessing and activity-only clause deletion. That wins as the canonical teaching and embedding reference — the architecture everyone clones first (this blueprint mirrors its SatSolver shape, §11) — precisely because it omits the modern machinery that obscures the core loop; you add LBD/restarts from Glucose afterward (Phase 3).

CaDiCaL / Kissat (Biere). Their defining decision was to make inprocessing a first-class, scheduled citizen — interleaving bounded variable elimination, subsumption, and vivification with search rather than only preprocessing once up front. That wins in the competition / hardest-industrial-instance regime, where simplifying the formula mid-search is worth more than any single heuristic; this blueprint borrows the idea in Phase 4 (inprocessing schedule) and Phase 12 (vivification) but keeps it bounded so it never dominates search.

Z3 (de Moura, Bjørner). Its defining decision was model-based theory combination plus a vast breadth of theories, quantifiers, and tactics. That wins in the general-purpose production SMT regime — when a tool must accept almost any SMT-LIB input and combine many theories on large mixed instances, model-guided equality sharing is markedly faster than exhaustive entailed-equality exchange. This blueprint deliberately chooses deterministic Nelson-Oppen first (ADR-16) because it is debuggable and teaches the entailment guarantee (MM9), and lists model-based combination as the documented Phase-2 optimization.

Boolector / Bitwuzla (Niemetz, Preiner). Their defining decision was word-level reasoning before bit-blasting: algebraic simplification and lazy, on-demand blasting of bit-vector and array constraints rather than eagerly flattening everything to gates. That wins in the wide-datapath QF_BV/QF_ABV regime — large multipliers, equalities over 256/512-bit vectors, lemmas-on-demand for arrays — exactly where this blueprint's eager bit-blasting (ADR-14, C7) hits its O(n²) cliff. The blueprint chooses bit-blasting for Phase 0 because it is the simplest correct route (MM8) and defers word-level BV to Stretch Goals.

CVC5 (Barrett, Tinelli, et al.). Its defining decision was a proof-producing, theory-rich architecture with first-class, fine-grained proof objects and a clean theory-combination interface designed for downstream reconstruction. That wins in the certified verification regime — when a proof assistant (e.g. Isabelle/HOL) must replay the SMT proof rather than trust the result, CVC5's proof machinery is the deliverable. This blueprint ships unsat cores for SMT in Phase 0 (ADR-19) and defers full Alethe/LFSC certificates (Stretch Goals); §5 Required Reading explicitly warns against copying CVC5's proof subsystem wholesale before the core is sound.

Yices2 (Dutertre). Its defining decision was a lean, high-performance implementation built directly around the author's own DPLL(T) simplex (the CAV 2006 paper this blueprint implements in Phase 8) with a tight C core and exact arithmetic, favoring raw QF_LRA/QF_LIA speed over the broadest theory menu. That wins in the arithmetic-heavy, latency-sensitive regime — embedded in tools that issue huge numbers of linear-arithmetic queries. This blueprint follows Yices's arithmetic lineage (ADR-12, the same simplex) but chooses Rust over C for the memory-safety reasons in §1/ADR-01 and prioritizes a teachable, multi-theory seam over single-theory peak throughput.

Where this design sits. The comparison is not a ranking but a map of the design space, and this blueprint occupies a deliberate point in it: MiniSat's minimal, clonable core (the shape, §11) plus Glucose's clause-quality management (Phase 3), wrapped in the lazy DPLL(T) seam the production solvers (Z3, CVC5) use, but with the debuggable, deterministic choices a learner needs first — Nelson-Oppen over model-based combination (ADR-16/MM9), eager bit-blasting over word-level (ADR-14/MM8), single-thread over portfolio (ALT-3). Every such choice is the teachable member of its pair, with the production alternative named as a Phase-2/Stretch-Goal upgrade. The thesis (Final Notes): get the seam and the soundness scaffolding right first; the production-grade heuristics are additive on top of a correct core, never a substitute for one.

Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived from the §4 System Constraints (and the stated standard assumptions), with the arithmetic shown. These set the memory, throughput, and blow-up budgets every later decision must respect.

Standing assumptions (named, not asserted as constraints): industrial CNF averages L ≈ 5 literals/clause (3-SAT is 3; industrial is a few to tens — 5 is the standard planning figure); a literal is a packed u32 = 4 bytes (ADR-05); a clause header is ~16 bytes (len:u32, lbd:u32, activity:f32, flags per §11 ClauseHeader).

The twelve numbers fall into three budget families: memory (C1–C4, C8–C9, C11 — what the DB, watches, learnts, tableau, signatures, and proof cost in RAM), throughput (C5–C6, C12 — propagation bandwidth, parse rate, restart cadence), and blow-up / payoff (C7, C10 — the BV multiplier cliff and the incremental-reuse win). Each derives from §4 plus the standing assumptions above; none is asserted.

C1 — Raw clause-DB literal bytes (10M clauses). From §4 "≥10M clauses" and L≈5, 4 B/lit: 10×10⁶ clauses × 5 lit/clause × 4 B/lit = 2.0×10⁸ B ≈ 200 MB of bare literals.

C2 — Clause-DB RAM with headers + arena overhead. Add the ~16 B header per clause and the §4 "≤1.3× raw literal bytes" arena ceiling (ADR-04): headers = 10×10⁶ × 16 B = 160 MB; literals incl. overhead = 200 MB × 1.3 = 260 MB; total ≈ 420 MB. Comfortably inside the §4 default 4 GB cap — so the learnt DB, not the input, is the memory risk (→ C4).

C3 — Watch-list RAM. Two watches per clause, each a Watcher{ClauseRef:u32, blocker:Lit:u32} = 8 B (§11): 10×10⁶ clauses × 2 watches × 8 B = 1.6×10⁸ B ≈ 160 MB. Watch lists are ~⅓ of the input clause-DB footprint — non-trivial, and why the blocker is packed (MM3).

C4 — Learnt-clause growth between reductions. §4 targets ≥100k conflicts/s and each conflict learns ~1 clause averaging (say) 10 literals: 100×10³ conflicts/s × 10 lit × 4 B = 4.0×10⁶ B/s ≈ 4 MB/s of learnt literals. Unbounded over a 1000 s solve that is 4 GB — i.e. the learnt DB alone hits the §4 cap in ~17 min without deletion. This is the quantitative reason LBD reduce (Phase 3, ADR-10) is mandatory, not optional.

C5 — BCP work per second vs the throughput target. §4 wants ≥10M propagations/s. If each propagation visits, on average, a watch list of ~8 entries and touches ~16 B per visit: 10×10⁶ prop/s × 8 visits × 16 B = 1.28×10⁹ B/s ≈ 1.3 GB/s of memory traffic — within a single core's cache/RAM bandwidth only if the data is cache-resident, which is the entire justification for packed literals + contiguous arena (MM3, P13). At 50M prop/s (the tuned target) it is ~6.4 GB/s, pushing the L2/L3 ceiling — the practical BCP wall.

C6 — Parse budget for a 10M-clause DIMACS. §4/M4 allow ≤5 s. With 5 lit/clause that is 10×10⁶ × 5 = 5×10⁷ integers to scan: 5×10⁷ ints ÷ 5 s = 1.0×10⁷ ints/s minimum — trivial for a streaming parser, but it confirms parsing must stream, not buffer-then-split (Phase 0 N.7): buffering 5×10⁷ integers as boxed values would blow the budget and the RAM.

C7 — Bit-blasted multiplier clause count (the BV cliff). An n-bit shift-add multiplier has n partial-product rows (n² AND gates) summed by ~(n−1) ripple-carry adders of n full-adders each; a full adder Tseitin-encodes to ~5 clauses, an AND to ~3: partial products ≈ n² AND × 3 clauses = 3n²; adders ≈ (n−1)·n full-adders × 5 clauses ≈ 5n²; total ≈ 8n² clauses. For n=64: 8 × 64² = 8 × 4096 ≈ 3.3×10⁴; counting the auxiliary equality/output wiring and carry definitions roughly doubles it to ≈7×10⁴ clauses for one 64-bit multiply (the figure cited in §2 "What Mastery Looks Like" and Phase 9). Ten such multiplies ≈ 7×10⁵ clauses — already 3.5× the entire C1 input budget, from arithmetic alone. This is MM8/ADR-14 made quantitative and the trigger for word-level BV (Stretch Goals).

C8 — Simplex tableau memory (LRA). For a system with v variables and r rows of bignum rationals, with a rational averaging ~b bits (numerator+denominator) ≈ 16 B early: tableau ≈ v × r × 16 B. For a modest v=r=1000: 1000 × 1000 × 16 B = 1.6×10⁷ B ≈ 16 MB — small, until bignum growth (Phase 8 N.7) inflates b. If rationals grow to 1000 bits (~128 B) on a pathological instance the same tableau is ~128 MB; coefficient-size growth, not dimension, is the LRA memory cliff (Scalability bottleneck #4).

C9 — EUF signature-table sizing. With t hash-consed terms (§11 TermId) and a signature entry ~24 B (key + representative): t × 24 B. For t=10⁶ terms: 10⁶ × 24 B = 2.4×10⁷ B ≈ 24 MB. EUF memory is linear in distinct terms — which is why hash-consing from Phase 0 (one TermId per structural term) is load-bearing, not a convenience (MM is supported by §11).

C10 — Incremental reuse payoff. §4/M10 require O(Δ) pop, and verification clients (Scalability: 10³–10⁶ checks) issue many near-identical queries. If a full re-solve costs T and an incremental delta costs ~0.01T (typical when learnt clauses are reused): 10⁶ checks × T (cold) vs 10⁶ × 0.01T (warm) = 10⁴ T — a ~100× wall-clock difference over a campaign. This is the quantitative case for P10 (incrementality is core, not bolted-on): the speedup is in the integral over thousands of queries, not any single check.

C11 — DRAT proof-trace size and the ≤2× overhead budget. §4 caps proof overhead at ≤2× solve time with streamed I/O. The trace records every learnt clause plus a d deletion line; at the C4 learn rate of ~4 MB/s of learnt literals, a 1000 s solve emits on the order of: 4 MB/s × 1000 s ≈ 4 GB of proof (deletions roughly double the line count but each d line is short). That is why §4 mandates streaming to a buffered file, never holding the proof in RAM (Phase 5 N.7): a multi-GB trace cannot coexist with a 4 GB solve in the §4 memory cap. It also bounds the DRAT-trim check cost in CI (I9) — proof checking is itself roughly linear in proof size.

C12 — Restart cadence and conflicts-between-restarts (Luby). The Luby sequence (ADR-09) with unit u gives restart intervals u·(1,1,2,1,1,2,4,…); with a typical u=100 conflicts the early restarts fire after ~100, ~100, ~200, … conflicts. Over the C4 budget of 100k conflicts/s, that is: 100×10³ conflicts/s ÷ ~150 conflicts/restart ≈ 670 restarts/s early on, decaying as Luby terms grow. This sets the frequency at which phase-saving (Phase 3) must restore a good assignment cheaply — restarts are common enough that re-deciding from scratch each time would dominate, which is exactly why saved phases (not fresh decisions) are reused after a restart.

What the numbers jointly imply. Three forces fall out of these twelve figures and shape every later design choice. (1) Memory is dominated by what you learn, not what you load (C2 vs C4): the input DB is ~420 MB but learning hits the 4 GB cap in minutes — so deletion (ADR-10) is structural, not optional. (2) Throughput is a bandwidth budget, not a clock-speed budget (C5): 1.3–6.4 GB/s of propagation traffic only fits if the data is cache-resident — making layout (ADR-04/05) the highest-leverage performance decision, above any inner-loop cleverness. (3) Blow-up is theory-local and predictable (C7/C8/C9): the BV multiplier (≈7×10⁴ clauses/op) and bignum growth are the two cliffs an expert sizes before writing the theory, and each has a named escape (word-level BV, rational normalization). Together they explain why the priority order is correctness → observability → maintainability → performance: the capacity envelope is set by data layout and deletion policy, both of which are cheap to get right early and ruinous to retrofit.

Alternative Architectures (Roads Not Taken)

Fundamentally different shapes for "decide satisfiability," each embodied by a real system, with the regime where it wins and why this blueprint rejected it for Phase 0. These are not parameter tweaks of the chosen design — each varies a different load-bearing axis:

  • ALT-1 varies the theory boundary — eager (flatten everything to SAT) vs lazy DPLL(T).
  • ALT-2 varies the search paradigm — stochastic local search vs systematic, complete CDCL.
  • ALT-3 varies the parallelism model — racing diverse configurations vs a single deterministic engine.
  • ALT-4 varies the decomposition strategy — look-ahead splitting into cubes vs monolithic CDCL.

Knowing each — its winning regime, its real embodiment, and its cost here — is what lets a principal engineer redesign this system for a different workload rather than only operate the one chosen.

ALT-1 — Eager SMT: bit-blast (and Ackermann-encode) everything to a single SAT call

formula ──▶ encode ALL theory atoms ──▶ one giant CNF ──▶ single CDCL solve ──▶ SAT/UNSAT
            (BV→gates, EUF→Ackermann,
             arrays→eager axioms)
  • Regime where it wins: pure, finite-domain QF_BV dominated by bitwise/structural operations with no wide multipliers — the eager flattening is simple, and a single well-tuned SAT solve beats the round-trip overhead of a lazy theory loop.
  • Real system: early Boolector and the eager mode of bit-vector solvers; STP for QF_BV/arrays.
  • Why rejected here: eager encoding explodes on EUF (Ackermann is O(pairs²)) and on wide multipliers (C7), and it discards the clean DPLL(T) seam (MM5/P12) that lets EUF/LRA/LIA/arrays plug in uniformly — the very architecture this project exists to teach.
  • What it would cost here: it collapses Phases 6–10 into one encoder + one SAT call, deleting the Theory trait — a smaller engine that cannot grow new theories. Bit-blasting is therefore kept within the lazy framework (ADR-14), not promoted to the whole engine.

ALT-2 — Stochastic local search (SLS): WalkSAT / probSAT instead of systematic CDCL

random assignment ──▶ pick an unsatisfied clause ──▶ flip a var (greedy + noise) ──▶ repeat
                       (no trail, no learning, no proof; incomplete)
  • Regime where it wins: large, satisfiable, random or loosely-structured instances (random 3-SAT near the phase transition, some hard combinatorial SAT) where local search finds a model far faster than systematic search — and where you do not need an UNSAT proof.
  • Real system: WalkSAT, probSAT, and the SLS components hybridized into modern solvers (SLS phases inside some CDCL solvers).
  • Why rejected here: SLS is incomplete — it can never prove UNSAT, produces no DRAT proof (violating P1/P14, I9), has no trail to anchor theory state (MM1), and cannot host DPLL(T).
  • What it would cost here: it would forfeit the project's core deliverable — checkable UNSAT (Phase 5) and the entire theory layer. It is at best a SAT-only accelerator bolted beside the CDCL core for satisfiable instances, not a foundation.

ALT-3 — Parallel portfolio: race diverse CDCL configurations, share short clauses

   ┌─ solver A (seed1, restart=luby) ─┐
in ─┼─ solver B (seed2, restart=glucose)┼─▶ first to finish wins
   └─ solver C (seed3, branch=LRB) ───┘   (share learnt clauses LBD≤k)
  • Regime where it wins: a multicore machine with a wall-clock deadline on a diverse benchmark set — different configurations win different instance families, so racing them with limited clause sharing beats any single configuration.
  • Real system: ManySAT, Plingeling / Treengeling (Biere), and most parallel SAT-competition entrants.
  • Why rejected for Phase 0: portfolio trades the determinism this blueprint treats as a debugging prerequisite (P7/I14/MM10) for speed, multiplies memory ×N (Capacity note: per-worker clause DBs), and is the most concurrency-bug-prone code (shared arenas — Phase 12 N.9).
  • What it would cost here: reproducibility — every soundness bug would become a heisenbug ddmin cannot shrink. It is therefore deferred (Stretch Goals; Phase 12 implements it behind a non-deterministic flag), not foundational; correctness and reproducibility come first.

ALT-4 — Cube-and-conquer / look-ahead: split into millions of subproblems

look-ahead splitter ──▶ cube₁ ─┐
(march-style)         cube₂ ─┼─▶ each cube solved by a CDCL "conquer" solver
                      ...   │     (in parallel; recombine for global answer)
                      cubeₘ ─┘
  • Regime where it wins: the hardest combinatorial UNSAT instances — pigeonhole-like and Ramsey/Schur problems — where a look-ahead heuristic (expensive per node, but globally informed) splits the space into cubes that CDCL then closes; this is how problems like the Boolean Pythagorean Triples were settled.
  • Real system: march (look-ahead) feeding a CDCL conqueror; the cube-and-conquer methodology (Heule, Kullmann, Biere).
  • Why rejected for Phase 0: it requires a second, fundamentally different search engine (look-ahead) plus a splitting heuristic and a parallel harness — enormous surface for a project whose Phase-0 bar is a correct single-thread CDCL + DPLL(T).
  • What it would cost here: a whole second solver and splitter before the first one is sound. It is deferred (Stretch Goals: parallel cube-and-conquer) and scales hard UNSAT better than the portfolio (Scalability "parallel scaling") when revisited.

The common rejection pattern. Three of the four (ALT-1, ALT-3, ALT-4) are not rejected on merit but on sequencing: each is a legitimate, sometimes superior architecture that this blueprint defers because it presupposes a correct, sound, deterministic single-thread CDCL+DPLL(T) core to build on or race. Only ALT-2 (SLS) is rejected on kind — it cannot produce the checkable UNSAT that is the project's reason to exist. The lesson the design space teaches: pick the architecture that makes the correctness scaffolding cheapest first (this design), then graduate to the production-grade alternative once the core is trustworthy — never the reverse.

Glossary

  • SAT — propositional satisfiability; find a truth assignment or prove none exists.
  • SMT — satisfiability modulo theories; SAT over first-order theory atoms.
  • CNF — conjunctive normal form (AND of OR-clauses).
  • DIMACS — the standard CNF text format.
  • SMT-LIB — the standard SMT command + term language.
  • CDCL — conflict-driven clause learning; modern SAT search.
  • DPLL — the backtracking-search ancestor of CDCL.
  • DPLL(T) — DPLL/CDCL driving theory solvers; the lazy SMT architecture.
  • Literal — a variable or its negation.
  • Clause — a disjunction of literals.
  • Trail — the assignment stack with levels + reasons.
  • Decision level — depth of decisions; backjump target unit.
  • BCP — Boolean constraint (unit) propagation.
  • Two-watched literals — lazy clause-watching scheme for fast BCP.
  • Blocker — cached watch literal to skip clause dereference.
  • Conflict clause — the all-false clause that triggers analysis.
  • 1-UIP — first unique implication point; the literal a learnt clause asserts.
  • Backjump — non-chronological backtrack to the asserting level.
  • Learnt clause — clause derived from a conflict (added to DB).
  • VSIDS / EVSIDS — activity-based branching heuristic.
  • Phase saving — reuse a variable's last assigned polarity.
  • Restart — discard the decision stack (keep learnts) to escape bad subtrees.
  • Luby sequence — a restart schedule guaranteeing completeness.
  • LBD (glue) — distinct decision levels in a clause; clause-quality metric.
  • BVE — bounded variable elimination (preprocessing).
  • BCE — blocked-clause elimination.
  • Tseitin encoding — CNF conversion of arbitrary Boolean formulas.
  • DRAT / RAT — DRAT is the externally-checkable clausal proof format for UNSAT; RAT (resolution asymmetric tautology) is the redundancy property it certifies beyond plain resolution.
  • Unsat core — minimal unsatisfiable subset of assumptions/assertions.
  • Theory — a decision procedure for a fragment (EUF, LRA, BV, arrays).
  • EUF — equality + uninterpreted functions.
  • Congruence closure — deducing equalities of function applications.
  • Union-find — disjoint-set structure for equivalence classes.
  • Simplex — the LP/feasibility pivoting method (here, for satisfiability).
  • Bland's rule — anti-cycling pivot rule guaranteeing termination.
  • LIA / LRA — linear integer / real arithmetic.
  • Branch-and-bound / Gomory cut — integer-feasibility techniques.
  • Bit-blasting — compiling bit-vector ops to propositional circuits.
  • Read-over-write — the array axiom relating select and store.
  • Extensionality — arrays equal iff equal at every index.
  • Nelson-Oppen — combining theories via shared-variable equality exchange.
  • Purification — splitting mixed terms so each atom is single-theory.
  • Convex theory — entails an equality whenever it entails a disjunction of one; non-convex needs case-splitting.
  • Theory propagation — theory-implied literals fed to the SAT core.
  • Incremental solving — push/pop/assumptions reusing state across queries.
  • Assumption — a temporary unit constraint for one check-sat, not permanently asserted.
  • Assertion level — push/pop scope; bounds the lifetime of assertions + dependent learnt clauses.
  • Clause provenance — the assertion level a learnt clause depends on (governs incremental soundness).
  • Vivification — strengthening a clause by propagating its negated literals.
  • δ-rationals — value + infinitesimal δ encoding to handle strict < bounds in simplex.
  • Slack variable — a fresh variable equal to a linear term, carrying its bound.
  • Degeneracy — a simplex basis with zero-slack rows; the cycling risk Bland's rule removes.
  • Cube-and-conquer / portfolio — parallel strategies: split a formula into cubes solved in parallel, or race diverse solver configs on the same instance (deferred).
  • Hash-consing — interning structurally equal terms to one id (sharing + fast equality).
  • e-graph — equality graph; congruence-closed term DAG (here, union-find + signatures).
  • Tautological clause — a clause containing both x and ¬x; always true, droppable.
  • Equisatisfiable — same satisfiability (not same models); preprocessing's guarantee.
  • Soundness vs completeness — never wrong vs never says "unknown"; this solver prioritizes soundness, bounds completeness with budgets.
  • Resolution — the inference (A∨l) ∧ (B∨¬l) ⊢ (A∨B); the proof step underlying learning + DRAT.
  • Lemma — a learned clause (propositional or theory) added to prune future search.
