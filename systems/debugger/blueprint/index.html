74 — Debugger from Scratch

Project Number: 74

Project Name: Debugger from Scratch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a native, source-level debugger for compiled languages on Linux x86-64 (AArch64 as a documented parallel path, not a separate product): it controls an inferior process via ptrace(2), sets software breakpoints (0xCC/brk #0) and hardware breakpoints/watchpoints (debug registers), parses ELF and DWARF (v4/v5) to map addresses to source lines, variables, and types, walks the call stack via DWARF Call Frame Information (CFI) with a frame-pointer fallback, evaluates a C-like expression subset over DWARF location expressions, steps at source-line granularity including inline-frame fidelity, follows fork/exec across processes, debugs multiple threads under one supervisor, and speaks two front-end wire protocols — the GDB Remote Serial Protocol (GDB-RSP) so a stock gdb client attaches unmodified, and the Debug Adapter Protocol (DAP) so VS Code and any DAP-aware IDE attaches unmodified.

Phase-0 deliverable — numbered modules (crates):

  1. dbg-inferior — the ptrace control plane: attach/launch/step/continue, register and memory access, software/hardware breakpoint install.
  2. dbg-elf — ELF reader, module/symbol discovery, dynamic-linker rendezvous, demanglers.
  3. dbg-dwarf — DWARF v4/v5 parsing: line tables, type DIEs, location expressions, CFI.
  4. dbg-unwind — stack unwinder (CFI walker + frame-pointer fallback + inline expansion).
  5. dbg-core — Session, breakpoint/watchpoint tables, expression evaluator, step state machine, follow-fork/exec policy.
  6. dbg-rsp — GDB Remote Serial Protocol server.
  7. dbg-dap — Debug Adapter Protocol server.
  8. dbg — the interactive CLI front-end.
  9. dbg-trace — self-instrumentation (tracing spans, Prometheus metrics).
  10. dbg-test-utils — shared conformance/property-test fixtures.

System boundaries. Provides: process control, breakpoints/watchpoints, symbolication, unwinding, variable display, stepping, two wire protocols. Delegates: disassembly rendering to capstone-class libraries (not built here); build-system/compiler behavior (we consume debug info, we do not produce it). Does not provide: a GUI (the IDE is the GUI, via DAP); remote kernel/JTAG debugging (probe-rs's job); record-and-replay (Deferred Features Register); a C++ template-instantiation-aware expression parser (we parse a strict C subset).

Non-goals. 32-bit and big-endian targets; Windows/macOS as first-class backends (documented stretch, not scheduled); a bespoke GUI; JIT-code debugging in Phase 0-12 scope.

Deployment model. A single self-contained binary (dbg) run on the same host as the inferior (local ptrace requires same-host, same-PID-namespace, CAP_SYS_PTRACE or matching UID). The GDB-RSP/DAP servers listen on loopback by default (ADR-21); remote transport is a documented, explicitly-opted-into configuration.

Target users/operators. Systems engineers debugging native Linux binaries (C, C++, Rust) without an existing GDB/LLDB installation matching the target's toolchain; IDE integrators wiring a DAP-compliant debug adapter; the portfolio's own tracer/profiler and kernel-module projects, which need a debugger they can extend in an afternoon.

What later phases unlock. Phase 5-6 (breakpoints) unlock interactive triage. Phase 7-8 (variables, stepping) unlock source-level workflows. Phase 9 (multi-thread/process) unlocks production-shaped workloads. Phase 10-11 (protocols) unlock every existing GDB/DAP client. Phase 12 unlocks operability (metrics, runbooks, the 30-day fuzz Sealed gate).

Recommended language: Rust 1.75+. Locked in ADR-01. Candidates considered: C++17 (GDB's and LLDB's choice — rejected: no ownership discipline over inferior-memory views, and this project's timeline does not afford re-deriving gimli/object-grade parsers in C++), OCaml (ocamldebug's choice — rejected: weaker systems-programming ecosystem for raw ptrace/ELF/ DWARF work, smaller reference-implementation base to learn from).

Prerequisites. Process control on Unix (fork, execve, waitpid, WIFSTOPPED, WSTOPSIG); the System V AMD64 ABI calling convention; the ELF specification at the level of locating .debug_info in a hex dump; DWARF v5 (sections, abbreviations, line programs, call frame information, location expressions); the Itanium C++ ABI mangling grammar and the Rust v0/legacy manglings; x86-64 trap/single-step/PC-write instruction semantics; socket programming for the GDB-RSP transport.

Estimated timeline. Phase 0: 1 week (repo skeleton + the ptrace smoke test). Full Phase 0-12 system: 4-6 months at one engineer full-time, matching the per-phase durations in Appendix B — Milestone Summary.

Deferred features, each flagged against a real anchor: reverse debugging PhaseDeferred("Deferred Features Register"); JIT-code debugging PhaseDeferred("Deferred Features Register"); macOS/Windows backends PhaseDeferred("Deferred Features Register"); symbol-server/debuginfod integration PhaseDeferred("Deferred Features Register"); function-call evaluation inside expressions PhaseDeferred("Deferred Features Register"); Python pretty-printer adapter PhaseDeferred("Deferred Features Register"); core-file (post-mortem) debugging PhaseDeferred("Deferred Features Register"); kernel-mode debugging (kgdb/kdb) PhaseDeferred("Deferred Features Register"); tracepoints PhaseDeferred("Deferred Features Register").

2. Why Build This

A debugger decides whether a hard bug costs an hour or a week, yet for most engineers it is the most opaque tool in the toolchain: the compiler, linker, build system, and profiler each have at least one well-known book walking their implementation; the debugger's canonical references are GDB's C source (decades of accreted state) and LLDB's comparable C++ mass. Anyone who must extend a debugger ends up re-deriving the architecture from those sources. This project is the artifact that teaches that architecture directly: small enough to read in a sitting, correct enough to drive real workloads (a Rust release binary built with -C debuginfo=2), and decoupled enough that the front end is two real wire protocols instead of a bespoke UI.

It matters historically because every major systems-language ecosystem re-derives the same four layers (process control, symbol/debug-info reader, unwinder, protocol front end) — understanding why they are four separate layers, not one, is the architectural lesson that transfers to profilers, tracers, and sandboxes alike (Principle P6). It matters practically because the muscles built here — reading raw kernel-reported CPU state, treating a DWARF file as an address-keyed database rather than a tree to scan, reasoning about a hardware register file as a scarce physical resource — recur across the portfolio's tracer, sandbox, and hypervisor-adjacent projects.

This is not a GDB clone: no remote JTAG/SWD, no bespoke GUI, no record-and-replay in Phase 0-12 (Deferred Features Register). That tight focus is why the timeline is months, not years.

What Mastery Looks Like

  • Explain, from the register file alone, why a debugger's notion of "current PC" can never be cached — tied to Phase 1 (ptrace control plane) and Invariant I3.
  • Perform the single-step-over-breakpoint dance by hand and explain every invariant it protects — tied to Phase 5 (software breakpoints).
  • Read a .eh_frame CIE/FDE pair and hand-compute a Canonical Frame Address — tied to Phase 4 (stack unwinding).
  • Explain why hardware watchpoints cannot be emulated by software breakpoints — tied to Phase 6 (hardware breakpoints/watchpoints).
  • Trace a GDB-RSP packet from wire bytes to a Session mutation and back — tied to Phase 10 (GDB Remote Serial Protocol Server).
  • Diagnose a follow-fork race from a captured event log — tied to Phase 9 (multi-thread and multi-process debugging).
  • Explain, using the Comparative Architecture Table, why rr's design center is incompatible with this project's live-attach requirement without a from-scratch rebuild.

Three properties hold throughout and are referenced repeatedly. First, data flow is one-way downward for control (front end → Session → Inferior Control) and upward for queries (Inferior Control → Symbol/Debug-Info → Unwinder/Evaluator → Session → front end); debug info enters from the side via mmap of the on-disk ELF. Second, front ends are interchangeable: Session never knows whether a request came from GDB-RSP, DAP, or the CLI (Principle P7). Third, correctness ground truth lives in the Symbol/Debug-Info layer and the Unwinder; every front-end query reduces to a small set of primitives over those layers, each with a conformance fixture (Testing & Verification Strategy).

The one defining property: every query is a read-through of live kernel state (Invariant I3) layered under a lazily-parsed, address-indexed debug-info cache (Invariant I6) — nothing here is a database with its own durability story; correctness comes from never caching what the kernel can tell you fresher.

6. Design Principles

  1. Inferior memory is untrusted (P1). Every read from /proc/PID/mem or PTRACE_PEEKDATA returns Result<Bytes, IoError>; zero unwrap()s on inferior reads, zero panics on bad DWARF. Tradeoff: more Result-threading boilerplate. Operationally: a malformed binary degrades to a typed error, never a crash. Violate it and a single corrupted inferior takes the debugger down with it.
  2. The register file is ground truth (P2). Every "where am I" query resolves through PTRACE_GETREGSET(NT_PRSTATUS), never a cache. Tradeoff: one extra syscall per query. Operationally: no stale-PC display class of bug exists. Violate it and the UI can show a PC the inferior left an instruction ago.
  3. One inferior, one supervisor task (P3). Per-inferior ptrace state is owned by exactly one task; cross-task access goes through a typed mailbox. Tradeoff: a serialization point per inferior. Operationally: the entire family of kernel per-thread tracer-tracee binding bugs is structurally avoided. Violate it and ptrace calls fail with ESRCH/EPERM under concurrent access from the wrong thread.
  4. Software breakpoints are reversible by construction (P4). The installer saves the original byte before writing the trap; every step-over path runs uninstall → single-step → reinstall → continue with no shortcut. Tradeoff: two extra ptrace calls per step-over. Operationally: no crash-after-clear bug class. Violate it and Failure Mode FM1 (lost breakpoint byte) reproduces.
  5. DWARF is parsed lazily (P5). No compilation unit loads until a query reaches it; .debug_aranges indexes address → CU without a scan; parsed CUs are LRU-cached (Invariant I6). Tradeoff: first-query-per-CU latency spike. Operationally: attach time stays sub-second even on 500 MB binaries (SC1-SC2). Violate it and attach time becomes O(binary size).
  6. Symbolication is separate from unwinding (P6). The unwinder emits (pc, cfa, sp) triples and stops; symbol names/lines are resolved lazily only when the front end asks. Tradeoff: two passes over frame data when both are needed. Operationally: bt stays fast even with missing debug info (Performance Engineering M5). Violate it and a stripped frame silently drops instead of showing an address (Mental Model MM4).
  7. The two protocols share one session (P7). A DAP setBreakpoints request and a GDB-RSP Z0 packet both call Session::set_breakpoint. Tradeoff: a translation layer per protocol. Operationally: GDB and DAP clients attached to the same session never disagree about state. Violate it and Failure Mode-class divergence appears (Mental Model MM7).
  8. Correctness before speed in Phase 0 (P8). Phase 0 ships a working next, print, backtrace, and the GDB-RSP minimum set; speed (lazy DWARF, hardware breakpoints, indexing) and coverage (pretty-printers, inline stepping) land in later phases. Tradeoff: early phases are slower than final targets. Operationally: every phase has something runnable to gate on. Violate it and premature optimization stalls Phase 0.
  9. Determinism is the default (P9). Two runs of the same script against the same binary produce bit-identical front-end output modulo PIDs/timestamps, which are documented as redacted. Tradeoff: conformance fixtures must explicitly redact nondeterministic fields. Operationally: regressions are byte-diffable. Violate it and flaky conformance fixtures erode trust in the whole suite.
  10. No silent fallbacks (P10). If a hardware breakpoint cannot be set (slots exhausted), the caller gets a typed error, never a silent downgrade to software. Tradeoff: the caller must handle the error explicitly. Operationally: a user profiling cache misses on a hot loop never has their experiment silently altered. Violate it and Invariant I5 breaks.
  11. The breakpoint table is indexed, never scanned (P11). BTreeMap<BreakpointId,_> and an address-sorted index, not a Vec. Tradeoff: slightly more complex insert/delete. Operationally: continue with 1,000 breakpoints stays under Performance target M7. Violate it and headcrab's documented mistake (Reference Implementations) reproduces.
  12. Hardware resources are explicitly rationed (P12). DR0-DR3/BRP-WRP slots are tracked by a bijective allocator (Invariant I5); the count is read from the CPU at attach time, never assumed. Tradeoff: a fixed, small ceiling regardless of software ambition. Operationally: SlotsExhausted is a typed, expected error, not a crash. Violate it and Failure Mode FM7 (slot leak) reproduces.
  13. Every supervisor task owns its ptrace state exclusively (P13). Only the task that issued PTRACE_SEIZE may issue further requests for that Tid (kernel-enforced tracer binding). Tradeoff: cross-thread requests must be proxied through the mailbox (P3). Operationally: no EPERM surprises from a second thread trying to trace the same Tid. Violate it and Failure Mode FM6 (double-trace) reproduces.
  14. Observability is not an afterthought (P14). Every command, supervisor event, and breakpoint operation emits a tracing span from Phase 0 onward, not bolted on in Phase
    1. Tradeoff: span overhead on the hot path (mitigated — Performance Engineering). Operationally: docs/runbooks/triage.md's first 15 minutes rely on this data existing. Violate it and every production incident starts with "let me add logging and reproduce."

8. Domain Model / Protocol / Data Model

8.1 The Breakpoint State Machine

        ┌────────────┐  install_swbp Ok
        │  Pending   │ ─────────────────────► ┌────────────┐
        └────────────┘                        │ Installed  │
              ▲                                └─────┬──────┘
              │ disable                 hit; step-over dance (P4) │
              │                                       │ re-arm
        ┌────────────┐                                │
        │  Disabled  │ ◄──────────────────────────────┘
        └─────┬──────┘
              │ delete
              ▼
        ┌────────────┐
        │  Deleted   │ (terminal — BreakpointId never reused)
        └────────────┘

A breakpoint against a not-yet-loaded symbol starts Pending; the rendezvous mechanism (Phase 2) flips it to Installed (Invariant I9). Disabled restores the original byte if the breakpoint was Installed. Deleted is the only terminal transition. The step-over dance (Phase 5) is a self-loop on Installed — never visible to the front end as Disabled.

8.2 ASLR Slide and the Dynamic-Linker Rendezvous

At module load, aslr_slide = load_address - file_base_address (the file's lowest PT_LOAD segment vaddr), read from /proc/PID/maps. The dynamic linker exposes _r_debug with an r_brk field naming a function invoked on every dlopen/dlclose; a software breakpoint at r_brk re-walks _r_debug.r_map on every hit to refresh the ModuleSet (mirrors gdb/solib-svr4.c, Reference Implementations).

8.3 Expression Grammar (EBNF)

expr        = or_expr ;
or_expr     = and_expr , { "||" , and_expr } ;
and_expr    = equality , { "&&" , equality } ;
equality    = relational , { ("==" | "!="), relational } ;
relational  = additive , { ("<"|">"|"<="|">="), additive } ;
additive    = unary , { ("+"|"-"), unary } ;
unary       = ["*"|"&"|"-"] , postfix ;
postfix     = primary , { "." ident | "->" ident | "[" expr "]" } ;
primary     = ident | number | string | "(" expr ")" | "(" type ")" unary ;

A strict C-expression subset: no function calls (deferred — Deferred Features Register), no C++ template instantiation syntax. Field/Index/Deref resolve through the current Frame's type DIEs (Phase 7).

8.4 GDB-RSP Packet Grammar

packet     = "$" , payload , "#" , checksum ;
payload    = { escaped_byte } ;
escaped_byte = normal_byte | "}" , (byte XOR 0x20) ;
checksum   = 2 * hex_digit ;               (* sum(payload) mod 256, unsigned *)
ack        = "+" | "-" ;                   (* "-" triggers resend of last packet *)

Special bytes #, $, }, * are escape-encoded. A receiver ACKs + (checksum OK) or - (bad, resend). Phase 10 §10.1 covers the full command set.

8.6 Malformed-Input Examples

  • Truncated DWARF: .debug_abbrev ends mid-attribute-list. gimli returns Err(UnexpectedEof); dbg-dwarf maps it to DwarfError::Truncated{cu_offset}, module marked "no debug info," never a panic (Invariant I13).
  • Bad GDB-RSP checksum: server recomputes; on mismatch it does not process the packet and sends -; the last-sent reply is cached for resend (Phase 10 §10.6).
  • Malformed DAP JSON: Content-Length header present but body fails to deserialize into the expected request shape; server replies with a DAP response carrying success: false and a message, never crashes the adapter process.

8.7 Failure-Path Example: Inferior Killed Mid-Continue

Sequence: front end sends continue → supervisor issues PTRACE_CONT → before the next waitpid, the OOM killer sends SIGKILL to the inferior → the next ptrace call against that Tid returns ESRCH. The wrapper (Phase 1 §1.7 pitfall) translates ESRCH into InferiorEvent::Exited{pid, status: SIGKILL} rather than propagating a raw OS error; Session tears down its breakpoint/watchpoint tables for that inferior and the front end receives an exited/terminated event exactly once (Invariant I2 still holds — nothing is left in T-state because the kernel already reaped the state via the fatal signal).

0.6 Pitfalls

  1. Forgetting PTRACE_O_EXITKILL — leaves the inferior wedged in T state on debugger death (Invariant I2, Failure Mode FM2); set it immediately after PTRACE_SEIZE.
  2. Using PTRACE_ATTACH instead of PTRACE_SEIZE — ATTACH injects a SIGSTOP the supervisor must then absorb; SEIZE does not. Phase 0 uses SEIZE exclusively.
  3. Not handling ESRCH on every ptrace call from the start — a signal between wait and the next request returns ESRCH (Garfinkel 2003; Threat T10); every wrapper must translate it to a typed InferiorGone, never propagate a raw OS error.
  4. Committing the governance-file skeleton as an afterthought — later phases assume docs/adr/, docs/runbooks/, and fuzz/ already exist; retrofitting them mid-Phase-3 costs more than doing it here.

0.7 Performance Concerns

The smoke test's attach latency is dominated by PTRACE_SEIZE's syscall cost, not by any project code — establishing the SC9 baseline (< 50 ms) before any DWARF/ELF work exists gives later phases a clean number to regress against.

0.8 Edge Cases

Target binary does not exist (launch returns a typed SpawnError, not a panic); target is not executable (EACCES surfaces as a typed error); PTRACE_SEIZE on a process already being traced by another tracer returns EPERM, surfaced as AlreadyTraced.

0.9 Failure Analysis

If the smoke test hangs, the blast radius is total (nothing later can be built); detection is immediate via CI timeout; containment is a hard per-test timeout in ci.yml; recovery is manual inspection of strace -f on the CI runner; postmortem guidance lives in docs/runbooks/attach-fail.md from day one even though it is nearly empty at Phase 0.

0.10 Operational Notes

tracing spans are wired from the first commit (Principle P14), even though Phase 0 emits almost nothing worth tracing yet — this is deliberate so Phase 12 is additive, not a rewrite. No deployment/rollback concerns exist yet; BUILD_PLAN.md's Status: field is complete for Phase 0 once §0.4 passes.

Phase 1 — Ptrace Control Plane & the Supervisor Event Loop

1.1 Objectives

Build the kernel-facing layer every later feature calls through — dbg-core never issues a raw ptrace request directly. Constraint: exactly one task per inferior may hold ptrace state (Principle P3, Invariant I4).

1.2 Detailed Implementation Steps

Implement the supervisor's per-inferior actor: a waitpid(WNOHANG | __WALL) inner loop woken by a signalfd-driven outer loop on SIGCHLD. Every kernel-reported event (stop, exit, fork, exec, syscall-enter/exit) becomes a typed InferiorEvent (Core Schema §11.4) pushed to the mailbox. Implement classify_stop, distinguishing the seven stop kinds: software-breakpoint trap (SIGTRAP, PC already advanced past 0xCC on x86-64 — decrement before reporting, per Kerrisk Ch. 20-22 signal semantics), hardware single-step trap, hardware breakpoint/watchpoint trap (read DR6), ptrace-event stop (PTRACE_EVENT_FORK/CLONE/EXEC/EXIT), syscall stop (PTRACE_O_TRACESYSGOOD required — see §1.6), forwarded signal, group stop. Implement the /proc/PID/mem bulk read/write path (ADR-05-adjacent: not the unwinder, but the same "prefer the fast path" instinct) alongside the PTRACE_PEEKDATA word-at-a-time fallback. Theory anchor: Principle P2 (register file is ground truth) and Invariant I3 are what make get_regs a read-through with no cache layer at all.

1.3 Deliverable

dbg-inferior builds and passes on x86-64 and AArch64; the supervisor loop runs four scripted scenarios: single-step, software-breakpoint hit (a trivial hand-patched 0xCC), fork, exec.

1.4 Acceptance Criteria

Conformance buckets inferior.attach, inferior.singlestep, inferior.event_fork, inferior.event_exec all Pass; single-step throughput ≥ 20,000 steps/s (SC3, Performance target M2); bulk /proc/PID/mem read ≥ 2 GB/s sequential (SC11, M3).

1.5 Conformance Fixtures

corpora/inferior/singlestep/tight-loop.scenario | purpose: throughput measurement | expected: 100k steps < 5 s (M2). corpora/inferior/event_fork/basic.scenario | purpose: fork ordering either direction | expected: both Forked{parent,child} orders accepted. corpora/inferior/killed-mid-continue.scenario | purpose: malformed/adversarial timing (Domain Model §8.7) | expected: Exited event, no panic.

1.6 Pitfalls

  1. Not detaching on supervisor crash — Inferior's Drop must call PTRACE_DETACH and close FDs (Invariant I2); Rust's drop guarantee is load-bearing here.
  2. Mixing PTRACE_CONT and PTRACE_SYSCALL resume modes across resumes without remembering the prior mode per-thread — causes misclassified stops.
  3. Treating PTRACE_PEEKDATA's errno=0-on-success-even-if-value-is--1quirk carelessly — always zeroerrno` before the call and check after.
  4. Reading memory one word at a time via ptrace for anything > 32 bytes — /proc/PID/mem is an order of magnitude faster (SC11); use it (Andriesse Ch. 5).
  5. Not setting PTRACE_O_TRACESYSGOOD — without it, a syscall stop is indistinguishable from a breakpoint SIGTRAP, and step-over intermittently single-steps a syscall instead.
  6. Not translating ESRCH to a typed event on every call (Garfinkel 2003, Threat T10) — a signal race between wait and the next request kills the inferior out from under a ptrace request; every wrapper must catch it.

1.7 Performance Concerns

The /proc/PID/mem path amortizes the syscall-boundary cost across large reads; PEEKDATA does not and is documented as the deliberately slow fallback (M4, < 60 s for 1 GB — a contrast number, not a target to hit). signalfd-driven wakeup avoids a busy-poll waitpid loop, keeping idle CPU near zero between events.

1.8 Edge Cases

A thread group leader exits while non-leader threads are still running (leader exit is the process's exit — Mental Model MM6); a signal arrives between PTRACE_CONT and the next waitpid targeting a different Tid than expected; vfork shares the parent's address space until PTRACE_EVENT_VFORK_DONE (handled fully in Phase 9, flagged here as a known edge).

1.9 Failure Analysis

A missed ESRCH translation crashes the whole supervisor task, taking every inferior it owns down with it (blast radius: one supervisor task, bounded by Principle P3's one-task-per- inferior design — other inferiors' tasks are unaffected). Detection: cargo test integration suite kills an inferior mid-request and asserts no panic. Recovery: none needed if I13-style Result discipline holds; if it does not, this is the single highest-priority regression to fix, tracked in docs/failure-analysis/failure-modes.md.

1.10 Operational Notes

Every InferiorEvent emission is a tracing span event (Principle P14); dbg_inferior_events_ total{kind} increments on every event. No migration/compatibility concerns yet — this phase has no wire format.

Phase 2 — ELF Reading, Module Discovery & the Dynamic-Linker Rendezvous

2.1 Objectives

Parse ELF via the object crate (ADR-04); discover loaded modules from /proc/PID/maps; maintain the module set incrementally via the dynamic-linker rendezvous (Domain Model §8.2). Constraint: every address the rest of the system handles must be resolvable to a Module and an aslr_slide before any DWARF query is meaningful.

2.2 Detailed Implementation Steps

Wrap object::File in an mmap-backed ElfImage sharing one Arc<Mmap> across queries (Levine Ch. 1-3 — object-file anatomy). Parse /proc/PID/maps once at attach, then incrementally on every rendezvous hit. Compute aslr_slide from the lowest PT_LOAD segment vaddr, never the entry point (§2.6 pitfall). Implement find_separate_debug_info: check .gnu_debuglink first, then .note.gnu.build-id, then the standard /usr/lib/debug/ paths. Theory anchor: Principle P1 (untrusted binary — bounded reads on every section-header field, Threat T2) and ADR-04 (the object crate's multi-format support, unblocking Deferred Features Register's macOS/Windows backends without a rewrite here).

2.3 Deliverable

Module/ModuleSet (Core Schema §11.3) fully implemented; the rendezvous breakpoint installs at r_brk and fires correctly on dlopen of libc, libm, and a custom .so.

2.4 Acceptance Criteria

Conformance bucket module.discovery Pass for a binary that dlopens three libraries; attach + symbolicate a 100 MB binary completes < 1 s p50 / < 2 s p99 (SC2, Performance target M1); zero panics on the elf_fuzz.rs corpus (Threat T2).

2.5 Conformance Fixtures

corpora/elf/pie-binary.json | purpose: ASLR-slide correctness | expected: slide computed from lowest PT_LOAD, not entry point. corpora/elf/dlopen-three.scenario | purpose: rendezvous | expected: ModuleSet grows by exactly 3 after three dlopen calls. corpora/elf/truncated-header.bin | purpose: malformed input (Domain Model §8.6) | expected: typed error, no panic, no OOB read.

2.6 Pitfalls

  1. Treating the /proc/PID/maps [vdso] line as a normal on-disk module — it is in-memory only; the mmap path differs.
  2. Computing the ASLR slide off the entry point or section table instead of the lowest PT_LOAD segment — off by a few hundred bytes on PIE binaries (Levine Ch. 6).
  3. Caching debug-info paths across invocations keyed by path instead of build-id — distributions update packages; build-id is the only stable key (Core Schema §11.6 annotation table).

2.7 Performance Concerns

mmap-sharing one Arc<Mmap> across every query avoids re-reading the file per section lookup; the rendezvous re-walk of _r_debug.r_map is O(loaded modules), acceptable because dlopen events are rare relative to breakpoint hits.

2.8 Edge Cases

A statically-linked binary has no _r_debug at all — module discovery degrades to the single main-executable module, documented, not an error. A binary with a .gnu_debuglink pointing at a file that does not exist on this host — dwarf: None, function names still resolve from .symtab/.dynsym.

2.9 Failure Analysis

A malformed ELF section-header count that would cause unbounded allocation is caught by a length-vs-file-size sanity check before allocation (Threat T2); detection is the elf_fuzz.rs nightly run; recovery is rejecting the file with a typed error, module marked "no ELF."

2.10 Operational Notes

dbg_dwarf_cu_cache_hits_total/_misses_total (introduced fully in Phase 3) begin accumulating here as modules load; no migration concerns — ELF parsing has no persistent state across runs beyond the (append-only) conformance corpus.

Phase 3 — DWARF Parsing: Line Tables, Types & Location Expressions

3.1 Objectives

Parse .debug_info/.debug_abbrev/.debug_line/.debug_loc(lists)/.debug_aranges/ .debug_str via gimli (ADR-03), lazily (Principle P5, Invariant I6). Constraint: no CU parses until a query reaches it; .debug_aranges is the mandatory address index (Mental Model MM3).

3.2 Detailed Implementation Steps

Implement the lazy CU iterator over gimli::DwarfSections::iter_units(), LRU-cached at 256 CUs by default (Invariant I6, sized against Back-of-Envelope Capacity Model BEC1). Parse .debug_aranges once per module at load into a BTreeMap<Range<u64>, CuOffset> for O(log CUs) address→CU resolution. Implement the .debug_line state-machine reader, materializing (file, line, column, is_stmt, prologue_end, epilogue_begin) rows per CU on first query. Implement the type-DIE walker over DW_TAG_base_type/pointer_type/array_type/ structure_type/enumeration_type/typedef/subroutine_type. Implement the location- expression evaluator (.debug_loc for DWARF v4, .debug_loclists for v5 — different offset bases, different match arms, per Andriesse Ch. 2). Wire the Itanium (cpp_demangle, ADR-11) and Rust v0/legacy (rustc_demangle, ADR-12) demanglers. Theory anchor: Mental Model MM3 ("DWARF is an address-keyed database, not a tree to scan") is the organizing idea behind every choice in this phase; Linton 1990's dbx-architecture split (symbol reader vs. process control) is the paper this phase most directly embodies.

3.3 Deliverable

Address-to-source resolution at addr2line parity across the conformance corpus; type-DIE parsing sufficient to display C/C++/Rust structs, enums, primitives, pointers, arrays.

3.4 Acceptance Criteria

Conformance buckets dwarf.line, dwarf.subprogram, dwarf.type, dwarf.location, demangle.itanium, demangle.rust_v0 all Pass; DWARF parse of 100 MB .debug_info with a hot address index completes < 100 ms (Performance target M8); demangling matches reference output on 10,000 symbols per demangler (exact match, zero divergence).

3.5 Conformance Fixtures

corpora/dwarf/line/optimized-inline.json | purpose: line-table fidelity on -O2 builds | expected: matches addr2line line-for-line. corpora/dwarf/location/loclists-v5.json | purpose: DWARF5 offset-base handling | expected: same resolved address as the v4 equivalent fixture. corpora/demangle/rust_v0/10k.tsv | purpose: RFC 2603 conformance | expected: exact string match, 10,000/10,000.

3.6 Pitfalls

  1. Trusting DW_AT_decl_file over the line table for source-file mapping — the line table is authoritative at a given PC; DW_AT_decl_file is only where the compiler thought the function was declared (sometimes a header).
  2. Ignoring DW_AT_ranges — modern compilers split functions into discontiguous ranges.
  3. Confusing DWARF v4's .debug_loc (absolute addresses) with v5's .debug_loclists (offset-based) — same evaluator, different match arms.
  4. Not honoring prologue_end when resolving "the start of the function" — a breakpoint at a function's first line must land past the prologue.
  5. Caching parsed DIEs keyed by path instead of inode+mtime — a rebuilt binary invalidates the cache silently otherwise.
  6. Not bounding DW_OP_call* recursion depth in location-expression evaluation — a crafted expression can otherwise recurse unboundedly (Invariant I13, Threat T3).

3.7 Performance Concerns

.debug_aranges turns address→CU resolution from O(n) in .debug_info size into O(log CUs); on a 100 MB binary this is the difference between a sub-second and a multi-second attach (Mental Model MM3, Performance target M8). The LRU cache bound (256 CUs, Invariant I6) trades memory (Back-of-Envelope BEC1, ~38 MB worst case) for avoiding re-parse thrash.

3.8 Edge Cases

A CU with zero .debug_aranges coverage (some compilers omit it for tiny CUs) falls back to a linear scan for that CU only, not the whole binary. A location expression referencing a register number the current architecture does not define — typed error, not a panic. Unicode identifiers in Rust v0 mangled names (Punycode-encoded per RFC 2603) — demangler must decode Punycode, not merely strip the u prefix.

3.9 Failure Analysis

A malformed location expression that would otherwise infinite-loop is bounded by an iteration-count ceiling (Invariant I13); detection is dwarf_fuzz.rs; blast radius is a single query returning a typed error, never the supervisor process; forensic artifact is the crashing input added to the fuzz corpus as a permanent regression fixture (Zeller 1999 minimization methodology, Testing & Verification Strategy).

3.10 Operational Notes

dbg_dwarf_cu_cache_hits_total/_misses_total are the primary Phase-3 operational signal; a sustained low hit ratio under a many-module workload is Failure Mode FM10, resolved by raising --dwarf-cache-cus. No wire-format compatibility concerns — DWARF is read-only input.

Phase 4 — Stack Unwinding via CFI and Frame-Pointer Fallback

4.1 Objectives

Build the unwinder: .eh_frame CIE/FDE-driven CFI walking as the correctness path, a frame-pointer fallback for modules without debug info, and inline-frame expansion. Constraint: unwinding never blocks on missing debug info (Principle P6).

4.2 Detailed Implementation Steps

Evaluate CFI via gimli::UnwindContext::unwind_info_for_address, which yields, per PC, where the CFA lives (e.g. RBP + 16) and where each saved register lives. Walk frame-by-frame: resolve the current frame's module (Invariant I7), compute CFA, restore the caller's registers, repeat until pc == 0 or no module is found. On CFI-miss (stripped module, or a JIT/hand-written-asm region), fall back to the System V AMD64 frame-pointer convention (*RBP = caller's saved RBP, *(RBP+8) = return address — Bryant & O'Hallaron Ch. 3), marking the resulting frame source: None so the front end shows an address, not silence (Mental Model MM4). After real frames are produced, expand inline frames by walking each real frame's subprogram DIE for DW_TAG_inlined_subroutine children whose range covers the PC. Theory anchor: Invariant I7 (every frame's PC lies within a known module) and I8 (strictly descending CFA) are enforced exactly here, in walker.rs; ADR-05 is why this is hand-rolled Rust over gimli, not an FFI call into libunwind.

4.3 Deliverable

bt matches gdb -batch -ex 'bt' line-for-line on the conformance corpus binaries, including one built with frame pointers omitted (-fomit-frame-pointer, forcing the CFI path) and one built specifically to exercise the FP fallback.

4.4 Acceptance Criteria

Conformance buckets unwind.cfi, unwind.inline, unwind.fp_fallback all Pass; 1,000-frame CFI unwind completes < 1 ms (Performance target M5); 1,000-frame FP-fallback unwind completes < 200 µs (M6, cheaper because it skips CFI evaluation entirely).

4.5 Conformance Fixtures

corpora/unwind/cfi/1k-frames.bin | purpose: throughput + correctness at depth | expected: 1,000/1,000 frames match reference, < 1 ms. corpora/unwind/inline/nested-3-deep.bin | purpose: inline-chain fidelity | expected: 3 synthesized inline frames between two real frames. corpora/unwind/fp/stripped.bin | purpose: fallback path | expected: frame count matches reference even with source: None.

4.6 Pitfalls

  1. Reading RBP as "the saved frame pointer" before the prologue's push %rbp executes — the CFI rule for "RBP holds the saved register" only activates post-prologue.
  2. Walking .debug_frame instead of .eh_frame — modern compilers emit and require .eh_frame at runtime; .debug_frame is frequently stripped.
  3. Not respecting DW_CFA_GNU_args_size for variadic functions, which adjust SP post-call.
  4. Treating a tail call as a normal frame — a tail call has no stack entry at all; the "PC is at a call instruction" heuristic is unreliable for detecting this.
  5. Trusting frame pointers in -O2 code where they are routinely omitted — CFI must be the primary path, FP only the documented fallback (this phase's entire premise).

4.7 Performance Concerns

CFI evaluation costs one gimli lookup per frame; the FP fallback skips it entirely, which is why M6's target (200 µs) is 5x tighter than M5's (1 ms) for the same frame count — the contrast is deliberate, not an inconsistency, and is worth stating explicitly to the reader (Hard Questions HQ-adjacent synthesis point).

4.8 Edge Cases

A signal frame interposed on the stack (the kernel's rt_sigreturn trampoline) requires special-cased CFI (the CIE marks it); a corrupted stack (smashed return address) must not crash the unwinder — Invariant I7 catches it by rejecting a PC outside any known module and truncating (I8's descending-CFA check as the second line of defense).

4.9 Failure Analysis

An unwind that would otherwise loop forever on a corrupted or cyclic frame chain is caught by Invariant I8 (strictly descending CFA); detection is the property test; recovery is truncating the backtrace and reporting it as partial, never hanging bt; forensic value is in the truncation point itself, which usually locates stack corruption.

4.10 Operational Notes

dbg_unwind_frames (a histogram) is the primary signal; a sudden shift in its distribution toward very short backtraces across a fleet often indicates a corrupted-stack pattern worth a runbook entry. No wire/version compatibility concerns beyond .eh_frame's own stability (kernel/compiler ABI, out of this project's control).

Phase 5 — Software Breakpoints & the Single-Step-Over-Breakpoint Dance

5.1 Objectives

Implement software breakpoint install/uninstall and the exact step-over sequence that makes Invariant I1 hold. Constraint: the six-step dance runs to completion inside the supervisor task without yielding to the front end (Principle P3/I4).

5.2 Detailed Implementation Steps

install(addr): read the byte at addr (via the bulk-read path from Phase 1), write 0xCC (x86-64) / brk #0 (AArch64, ADR-06), return the saved byte for Breakpoint.installed_byte (Principle P4). uninstall(addr, saved): write the saved byte back. The step-over dance on a breakpoint hit: (i) decrement PC back to addr (x86-64 only — AArch64's trap PC is already correct, Phase 6 architecture notes), (ii) uninstall, (iii) PTRACE_SINGLESTEP, (iv) wait for the resulting trap, (v) reinstall, (vi) resume with PTRACE_CONT. Theory anchor: this six-step sequence is the direct implementation of Invariant I1 and Principle P4; TartanLlama's minidbg (Reference Implementations) teaches this exact sequence and is the fixture this phase's conformance corpus is checked against for shape (not byte-for-byte, since encodings differ per architecture).

5.3 Deliverable

A CLI session that sets a breakpoint at main, continues, hits it, single-steps past it, and continues to exit — verified against gdb -batch -ex 'b main' -ex 'run' -ex 'next' -ex 'continue' on the same binary.

5.4 Acceptance Criteria

Conformance bucket inferior.swbreak Pass; 1,000 breakpoints installed in < 20 ms (Performance target M7, Invariant/Principle P11's indexed table is what makes this possible); zero lost-byte incidents (Invariant I1) across a 24-hour soak (Performance target M11).

5.5 Conformance Fixtures

corpora/breakpoint/sw/install-hit-restore.scenario | purpose: the core dance | expected: byte restored bit-identical after 1,000 hit/step cycles. corpora/breakpoint/sw/pending-dlopen. scenario | purpose: Invariant I9 | expected: breakpoint installs exactly once after the target library loads.

5.6 Pitfalls

  1. Forgetting to restore the original byte — the single most common debugger bug (Failure Mode FM1); the inferior crashes mysteriously, possibly on a different thread, possibly much later.
  2. Confusing the two architectures' trap-PC semantics: x86-64's SIGTRAP reports PC one past the 0xCC; AArch64's brk #0 reports PC at the trap itself. Getting this backwards shifts every subsequent line-table query by one instruction.
  3. Storing the breakpoint table as a Vec — O(n) lookup at scale (Principle P11, Reference Implementations' headcrab pitfall).
  4. Not clearing a breakpoint before follow-exec tears down the module set — installed_addr is meaningless in the new address space (handled fully in Phase 9, flagged here).

5.7 Performance Concerns

The indexed BTreeMap<BreakpointId,_> plus an address-sorted secondary index keeps both install and per-continue lookup at O(log n even at the SC6 ceiling (10,000 breakpoints), directly enabling Performance target M7.

5.8 Edge Cases

Setting a breakpoint at an address that already has one installed (idempotent, returns the existing BreakpointId); setting a breakpoint mid-instruction (rejected — must align to an instruction boundary, validated via the line table); a breakpoint at the very last byte of a mapped region (bounds-checked write).

5.9 Failure Analysis

If the byte-restore step is skipped (a bug, not a designed path), blast radius is the entire inferior process, often manifesting far from the breakpoint site; detection is the soak test's zero-lost-byte assertion; recovery is inspecting the crash address against the historical breakpoint-install log (dbg_breakpoints_total plus the tracing span for the specific BreakpointId).

5.10 Operational Notes

dbg_breakpoints_total{state} is the primary gauge; docs/runbooks/lost-breakpoint.md covers exactly this failure class end to end, written before Phase 5 ships (Principle P14).

Phase 6 — Hardware Breakpoints and Watchpoints via Debug Registers

6.1 Objectives

Implement hardware breakpoints and watchpoints using x86-64's DR0-DR7 and AArch64's BRP/WRP register files — the only mechanism that observes memory access without modifying inferior code (ADR-07: pulled into Phase-0 scope, not deferred).

6.2 Detailed Implementation Steps

Read the hardware slot count at attach time (x86-64: architecturally fixed at 4; AArch64: read from ID_AA64DFR0_EL1.BRPs/WRPs via PTRACE_GETREGSET(NT_ARM_HW_BREAK)), never assumed (Principle P12). Implement the slot allocator as a bijective map slot↔BreakpointId/ WatchpointId (Invariant I5). On x86-64, program DR0-DR3 with the address and DR7's RW/LEN fields with the access kind/width via PTRACE_POKEUSER; read DR6 on trap to identify which slot fired. On AArch64, program BVR<n>_EL1/BCR<n>_EL1 (breakpoints) or WVR<n>_EL1/WCR<n>_EL1 (watchpoints) independently. On exhaustion, return typed SlotsExhausted — never fall back to software (Principle P10). Theory anchor: Intel SDM Vol. 3B Chapters 17-18 and the Arm ARM Chapter D2.4 are the two specs this section directly implements; Invariant I5's bijection property is what a property test in dbg-core/tests/properties.rs checks on every insert/delete.

6.3 Deliverable

A watchpoint set on a heap allocation fires exactly once per write, across both a software- breakpoint-heavy workload (proving the two mechanisms coexist) and a tight loop where a software breakpoint would have distorted timing (proving the watchpoint's non-invasive property).

6.4 Acceptance Criteria

Conformance bucket inferior.hwbreak/inferior.hwwatch Pass; hardware breakpoint/watchpoint install latency < 1 ms per slot (Performance target M14); SlotsExhausted returned, not a crash or silent downgrade, on the 5th concurrent request (SC7).

6.5 Conformance Fixtures

corpora/breakpoint/hw/watch-write-4byte.scenario | purpose: access-kind/width correctness | expected: fires exactly on 4-byte writes, not reads. corpora/breakpoint/hw/exhaustion. scenario | purpose: Invariant I5/Principle P10 | expected: 5th request returns SlotsExhausted, first 4 remain intact.

6.6 Pitfalls

  1. Assuming 4 slots on AArch64 without reading ID_AA64DFR0_EL1 — implementations vary (6 is typical but not universal).
  2. Forgetting that x86-64's DR7 RW/LEN fields are shared between breakpoint and watchpoint use of the same 4 slots — a hardware breakpoint and a hardware watchpoint compete for the same 4-slot budget, not independent budgets.
  3. Not clearing the slot allocator's bit on delete — a leaked slot manifests as premature SlotsExhausted (Failure Mode FM7).
  4. Reading DR6 without clearing it after use — stale bits misattribute the next trap to the wrong slot.

6.7 Performance Concerns

PTRACE_POKEUSER is a single syscall per register write; programming a watchpoint is O(1) and easily meets M14's < 1 ms target — the cost here is entirely the fixed ptrace syscall overhead, not any algorithmic concern.

6.8 Edge Cases

A watchpoint address that straddles two cache lines (still valid per the ISA, size ∈ {1,2,4,8} and naturally aligned is the safe subset — unaligned watchpoints are architecturally permitted on some CPUs but not guaranteed portable, documented as a caveat); a watchpoint on a stack address that goes out of scope mid-session (fires on the next unrelated write to that now-reused address — documented as an inherent hardware-watchpoint limitation, not a bug).

6.9 Failure Analysis

A slot-allocator bug that double-assigns a slot corrupts both the old and new breakpoint/watchpoint's behavior simultaneously; detection is the property test (I5's bijection); blast radius is bounded to hardware-mechanism users only (software breakpoints are unaffected, Principle P3-style isolation by mechanism).

6.10 Operational Notes

dbg_hw_slots_used is the primary gauge, alarmed at the SC7/SC8 ceiling; no wire/version compatibility concerns — purely local kernel-facing state.

Phase 7 — Variable Display, Type-Aware Rendering & Pretty-Printers

7.1 Objectives

Implement print: parse an expression (Domain Model §8.3), evaluate it against the current frame, render it through a type/language-aware pretty-printer. Constraint: the expression language is a strict C subset — no function calls (Deferred Features Register).

7.2 Detailed Implementation Steps

Parse via the EBNF grammar (Domain Model §8.3) into Expression (Core Schema §11.4). Evaluate in an EvaluationContext{session, thread, frame}, resolving Variable names through the current frame's locals (Phase 3's type-DIE walker) and DWARF location expressions (Phase 3's location evaluator). Render through PrettyPrinter (Core Schema §11.5): C primitives/structs, C++ classes (field-by-field; vtable detail deferred — Deferred Features Register), Rust primitives/structs/enums (tagged, including niche optimization for Option<&T>), slices, &str/String, Vec<T>, HashMap<K,V>. Bound pointer-following recursion at depth 16 and string reads at 4 KiB (Threat T8-adjacent OOM concern). Theory anchor: Principle P6 (symbolication separate from unwinding) is why locals_for_pc is a lazy, on-demand call, not something the unwinder populates eagerly; ADR-19 (native Rust trait, Python adapter deferred) governs the PrettyPrinter trait's shape.

7.3 Deliverable

print renders correctly on ~50 fixtures spanning C, C++, and Rust, including nested structs, tagged enums, and a niche-optimized Option<&T>.

7.4 Acceptance Criteria

Conformance bucket print.basic Pass on all ~50 fixtures; print.vtable reports Deferred with a resolving anchor (Deferred Features Register); pointer-cycle fixtures terminate within the depth-16 bound, never hang.

7.5 Conformance Fixtures

corpora/print/rust-option-niche.json | purpose: niche-optimization correctness | expected: Some(&x)/None render distinctly with no extra discriminant byte assumed. corpora/print/ cyclic-pointer.json | purpose: recursion-depth bound | expected: renders "...(depth limit)" at depth 16, no hang. corpora/print/cpp_vtable.json | purpose: Deferred-bucket contract | expected: report shows outcome: "Deferred".

7.6 Pitfalls

  1. Following pointers without a depth bound — a cyclic structure recurses forever; bound at 16 (§7.2).
  2. Reading a string via read_string(addr) with no length cap — a race with a concurrent free can read megabytes of garbage; cap at 4 KiB, emit a truncation marker.
  3. Trusting DW_AT_byte_size over DW_AT_data_member_location for field offsets — byte_size is a source-level size, not necessarily the in-memory layout's authority.

7.7 Performance Concerns

Pretty-printing is on the interactive-latency path (a human is waiting on print); the depth and length bounds above exist as much for latency predictability as for safety — an unbounded print of a large Vec<T> would otherwise dominate a session's perceived responsiveness.

7.8 Edge Cases

A type whose DIE is absent (declaration-only, e.g. an opaque forward-declared struct) — render as an untyped hex dump with a note, never fail the whole print. A union type — render the active-looking member heuristically with an explicit "union — first member shown" caveat.

7.9 Failure Analysis

A pretty-printer panic (should be structurally impossible per Principle P1, but printers are the most likely place for a missed Result) is caught at the printer-invocation boundary and converted to a typed rendering error, so one broken printer never takes down print for every other type.

7.10 Operational Notes

No dedicated metric beyond dbg_command_latency_seconds{command="print"}; no wire-compat concerns — printer output is a rendering, not a persisted format.

Phase 8 — Step Semantics: step-in, step-over, step-out, until, inline frames

8.1 Objectives

Implement the step state machine over the primitives Phases 1, 3-5 provide. Constraint: the temporary breakpoint the machine sets for step-over/step-out is cleared on every stop, not only the expected one (Invariant I11).

8.2 Detailed Implementation Steps

step-in: single-step until the line-table row changes; if the containing function changes, stop. step-over: if the current instruction is a call, set a temporary breakpoint at the return address, continue, clear on hit; otherwise behave as step-in. step-out/finish: read the return address from the current frame's CFI (Phase 4), set a temporary breakpoint there. until <line>: continue until the line table reports <line> or the frame returns. Detect DW_AT_noreturn (Phase 3's type/subprogram DIE walk) and downgrade a step-over of a noreturn call to step-in, avoiding an infinite wait on a temp breakpoint that will never fire. When the current frame is an inline frame (Phase 4's inline expansion), step-out leaves the inline frame first, consulting the inline-frame chain at the current PC. Theory anchor: Invariant I11 is enforced exactly in this phase's stop-dispatch path; Principle P8 (correctness before speed) is why Phase 0's next ships before any of Phase 6's hardware optimizations exist.

8.3 Deliverable

The four step operations work correctly across single-threaded and (in coordination with Phase 9) multi-threaded programs, both optimized and unoptimized builds, including inline frames.

8.4 Acceptance Criteria

Conformance buckets step.in, step.over, step.out, step.until, step.inline all Pass; a step-over of a noreturn call downgrades to step-in within one instruction (verified by fixture, not timeout-dependent); zero stuck temporary breakpoints across a 24-hour soak (Invariant I11, Performance target M11).

8.5 Conformance Fixtures

corpora/stepping/inline-3-deep.scenario | purpose: inline-frame step-out ordering | expected: leaves 3 inline frames before the real frame changes. corpora/stepping/noreturn-call. scenario | purpose: the abort/exit/longjmp class | expected: downgrades to step-in, no hang. corpora/stepping/signal-during-step-over.scenario | purpose: Invariant I11 | expected: temp breakpoint cleared even though the expected return-address breakpoint never fired.

8.6 Pitfalls

  1. Not clearing the temp breakpoint on an intervening signal — if the inferior takes a signal between continue and the expected temp-breakpoint hit, the temp breakpoint lingers in the table and the next step-out misbehaves (Invariant I11 is the direct fix).
  2. Stepping over a call to a function that never returns — the temp breakpoint at the return address never fires; detect DW_AT_noreturn and downgrade rather than hang.
  3. Stepping over an instruction that is itself a software breakpoint — the step-over-breakpoint dance (Phase 5) must run first, or step-over loops.

8.7 Performance Concerns

step-over's temporary breakpoint avoids single-stepping through an entire called function (which could be arbitrarily long) — the whole point of the mechanism is turning an O(callee instruction count) operation into O(1) ptrace calls plus one continue.

8.8 Edge Cases

A step-over where the call target is itself already breakpointed at its entry (the temp breakpoint and the user's breakpoint coexist at different addresses, both fire correctly, first-hit-wins semantics for which stops the front end sees). A step-until <line> where that line never executes again in the current frame before it returns (stops at frame return instead, documented behavior, not a hang).

8.9 Failure Analysis

A stuck temporary breakpoint (Invariant I11 violated) manifests as a spurious extra stop on a later, unrelated continue; detection is the soak test's zero-stuck-breakpoint assertion; recovery is fixing the stop-dispatch path to clear on every stop unconditionally.

8.10 Operational Notes

Step-command latency is tracked via dbg_command_latency_seconds{command="step"}; no wire compatibility concerns beyond Phase 10/11's translation of these operations into GDB-RSP s/ DAP next/stepIn/stepOut.

Phase 9 — Multi-Thread and Multi-Process Debugging

9.1 Objectives

Track threads within one inferior and follow fork/exec across process boundaries. Constraint: no two supervisor tasks ever trace the same Tid simultaneously (Invariant I12, Principle P13).

9.2 Detailed Implementation Steps

Track threads via PTRACE_EVENT_CLONE (add) and per-thread PTRACE_EVENT_EXIT (remove); leader-thread exit is process exit (Mental Model MM6, Kerrisk Ch. 20-22 signal semantics underpin the exit-signal delivery this depends on). Implement follow_fork_mode (Parent: detach child immediately; Child: detach parent, attach child; Both: two independent supervisor tasks, two Inferiors, Principle P3 applied recursively). Implement follow_exec_mode (Reuse: keep the Inferior handle, rebuild ModuleSet, reinstall Pending and named-symbol breakpoints post-exec since old addresses are meaningless; Detach: drop tracing post-exec). Implement scheduler_locking (Off: all threads run during a step, only the stepping thread is monitored; Step: only the stepping thread runs — the default for step-in/next, required for determinism; On: only the stepping thread runs even for continue). Theory anchor: Invariant I12 and Principle P13 are enforced exactly in follow.rs's mode-transition logic; Stevens & Rago Ch. 8/10 is the direct reference for the fork/exec/signal semantics this phase automates.

9.3 Deliverable

A 32-thread pthread program is debugged correctly (info threads lists all 32, thread N switches, bt works per-thread); a fork-then-exec shell-style program follows the child correctly under follow-fork child.

9.4 Acceptance Criteria

Conformance buckets thread.list, thread.switch, follow.fork, follow.exec all Pass; 32-thread info threads + per-thread bt completes < 50 ms total (Performance target M13); zero double-traced Tids across 1,000 fork events (Invariant I12).

9.5 Conformance Fixtures

corpora/follow_fork/parent-first.scenario and corpora/follow_fork/child-first.scenario | purpose: unspecified kernel event ordering | expected: both orders handled identically. corpora/follow_fork/vfork-window.scenario | purpose: shared-address-space hazard | expected: breakpoint-set requests between VFORK and VFORK_DONE are rejected with a typed error, not silently applied to both processes. corpora/multithread/pthread32.scenario | purpose: scale target | expected: all 32 threads enumerated, switch round-trips correctly.

9.6 Pitfalls

  1. Assuming PTRACE_EVENT_FORK always arrives on the parent before the child — the order is unspecified; handle either (fixture parent-first/child-first).
  2. Not realizing vfork shares the parent's address space until VFORK_DONE — setting a breakpoint in that window affects both processes; refuse breakpoint-set requests during it.
  3. Persisting a breakpoint's installed_addr across exec — the address space is entirely new; the pending/named-symbol set must be re-resolved and reinstalled after re-walking the fresh module set (Phase 2's rendezvous re-run).
  4. Assuming any thread's exit means the process exited — only the leader's exit does (Mental Model MM6); a non-leader thread exit only removes that Tid from the thread map.

9.7 Performance Concerns

Per-thread state (a Registers-sized structure per Tid) scales linearly with thread count up to SC4's 4,096 ceiling; the Back-of-Envelope Capacity Model's BEC11 quantifies the worst-case resident cost (~885 KB) as comfortably within budget.

9.8 Edge Cases

A thread created and destroyed between two supervisor polls (both CLONE and EXIT events queued back-to-back, must not race the thread map into an inconsistent state — Invariant I4's single-writer mailbox is what prevents this). A process that fork()s from a non-leader thread (POSIX semantics: only the calling thread is duplicated into the child — handled identically to a leader fork from this project's perspective, since ptrace events name the Tid, not assume it is the leader).

9.9 Failure Analysis

A double-trace (Invariant I12 violated, Failure Mode FM6) manifests as EPERM on subsequent ptrace calls against the contested Tid from the losing task; detection is the fixture's single-owner assertion; recovery is the losing task detaching automatically on EPERM during its next request, then the operator restarting that half of the session.

9.10 Operational Notes

dbg_inferior_events_total{kind="forked"|"execed"|"thread_started"|"thread_exited"} is the primary signal set; follow-fork/follow-exec mode is logged at session start since it changes debugging semantics materially enough to matter in a postmortem.

Phase 10 — GDB Remote Serial Protocol Server

10.1 Objectives

Implement the GDB-RSP wire protocol (Domain Model §8.4) so a stock gdb client attaches unmodified (ADR-08). Constraint: bind to loopback by default (ADR-21, Threat T4).

10.2 Detailed Implementation Steps

Implement packet encode/decode with the escape rules (#, $, }, * → } + byte XOR 0x20) and the mod-256 checksum (Domain Model §8.4). Implement the minimum command set: ? (stop reason), g/G (read/write all registers), p/P (single register), m/M (memory read/write), c/s (continue/step), Z0/z0 (software breakpoint set/clear), Z1-Z4 (hardware — Phase 6 now makes these real, not Deferred), qSupported/qXfer:features:read (target-description XML, per-architecture, generated by tools/gen-target-xml.rs from kernel headers), qC/H (thread operations), T<sig> (stop-reply), vCont/vCont? (multi-thread resume — advertise vContSupported+, since modern gdb prefers it over bare c/s), D (detach), k (kill). Route every command through Session::* (Principle P7) — never maintain protocol-local state. Theory anchor: ADR-08 and ADR-21 govern this phase's two defining choices (protocol selection, default bind); Stallman/Pesch/Shebs's Appendix E is the wire grammar this section implements exactly.

10.3 Deliverable

gdb -ex "target remote :4444" connects and successfully drives info registers, x/16i $pc, b main, c, s, bt, print x, continue, detach against this project's server.

10.4 Acceptance Criteria

Conformance bucket rsp.minimum Pass against a recorded gdb session corpus (byte-for-byte replay after PID/timestamp redaction, Principle P9); GDB-RSP round trip for a g packet < 1 ms median (Performance target M9, SC12).

10.5 Conformance Fixtures

corpora/rsp/gdb-session-basic.recording | purpose: end-to-end replay | expected: bit- identical transcript after redaction. corpora/rsp/checksum-mismatch.scenario | purpose: malformed input (Domain Model §8.6) | expected: server sends -, resends last reply on request, never desyncs.

10.6 Pitfalls

  1. Not handling +/- half-duplex resend correctly — the server must retain the last-sent packet and resend verbatim on -.
  2. Sending an unescaped #, $, or } byte — the most common implementer bug; the client silently truncates or misparses (Failure Mode FM8).
  3. Returning a wrong-length register file on g — must match the target-description XML byte-for-byte, or gdb displays garbage (Failure Mode FM4).
  4. Not advertising vContSupported+ in the qSupported reply — modern gdb falls back to c/s, breaking the multi-thread story.

10.7 Performance Concerns

The checksum computation and escape-scan are O(payload length) per packet — negligible next to the round-trip's dominant cost, which is the underlying ptrace call Session performs to satisfy the request; M9's < 1 ms target is really a ptrace-latency budget, not a protocol- parsing budget.

10.8 Edge Cases

A client sends a packet larger than any single read() returns (must reassemble across reads using the #<checksum> terminator, not a fixed length). A client that never ACKs (protocol allows this in NoAckMode, negotiated via QStartNoAckMode — a Phase-0 minimum-set gap, documented, not silently mishandled: unsupported requests get an empty reply per protocol convention).

10.9 Failure Analysis

A checksum-escaping bug (Failure Mode FM8) manifests as the client resending forever; detection is rsp_fuzz.rs plus the checksum-mismatch fixture; recovery is a packet.rs patch and redeploy, verified against a captured packet trace before closing the incident.

10.10 Operational Notes

dbg_rsp_connections_total and dbg_command_latency_seconds{command} (labeled per RSP command letter) are the primary signals; the loopback-default bind (ADR-21) is logged loudly at startup if overridden to a public interface, per Threat T4.

Phase 11 — Debug Adapter Protocol Server and Interactive CLI

11.1 Objectives

Implement the DAP wire protocol (ADR-09) and the GDB-alias interactive CLI. Constraint: both are translation layers over Session, never parallel state (Principle P7, Invariant I10).

11.2 Detailed Implementation Steps

Implement DAP's Content-Length-framed JSON-RPC over stdio. Implement the minimum surface: initialize, launch, attach, setBreakpoints, setExceptionBreakpoints, configurationDone, threads, stackTrace, scopes, variables, continue, next, stepIn, stepOut, pause, evaluate, disconnect — each a thin adapter calling the same Session::* method Phase 10's GDB-RSP commands call. Rebase DAP's JSON-numeric thread IDs against Tid via a per-session monotonic mapping (DAP reserves 0). Emit a stopped DAP event for every StopReason variant, not only breakpoint hits (Failure Mode FM9 is exactly the bug of missing this). Cap variables response size, exposing start/count pagination for large aggregates. Implement the CLI (dbg) as a readline-style REPL with GDB-aliased commands (b, c, s, n, fin, bt, p, info threads, thread <n>, up, down, list, quit) so muscle memory transfers from gdb. Theory anchor: Invariant I10 (identical underlying Session call regardless of protocol) is verified by fixtures asserting matching state after equivalent GDB-RSP and DAP requests; ADR-09's rationale (IDE-agnostic) is why DAP was chosen over a VS Code-only extension API.

11.3 Deliverable

A VS Code launch configuration ("type": "dbg-native") debugs examples/c-hello: hits a breakpoint, prints a local, single-steps a line, continues to exit. The CLI runs the identical scenario.

11.4 Acceptance Criteria

Conformance buckets dap.minimum and cli.minimum both Pass; DAP stackTrace for a 256-frame stack < 5 ms (Performance target M10, SC13); zero missing stopped events across every StopReason variant in the fixture matrix (Failure Mode FM9 regression guard).

11.5 Conformance Fixtures

corpora/dap/vscode-session-basic.recording | purpose: end-to-end replay (redacted) | expected: bit-identical transcript. corpora/dap/watchpoint-stop-event.scenario | purpose: Failure Mode FM9 regression | expected: stopped event emitted for a watchpoint hit, not only breakpoint hits. corpora/cli/gdb-alias-parity.scenario | purpose: muscle-memory contract | expected: every listed CLI alias resolves to the documented Session call.

11.6 Pitfalls

  1. Reusing GDB-RSP Tid semantics directly in DAP — DAP's 0 is reserved; rebase via a per-session monotonic mapping.
  2. Not sending stopped events for non-breakpoint stops — the IDE ignores any stop it never received an event for (signals, watchpoint hits, step completions all need one).
  3. Returning unbounded variables responses — some IDEs paginate poorly under load; cap and expose start/count.

11.7 Performance Concerns

DAP's JSON serialization cost is the dominant per-request overhead versus GDB-RSP's leaner framing; M10's 5 ms budget for a 256-frame stackTrace is sized against serde_json throughput plus the underlying Session::stack_trace call's cost (dominated by Phase 4's unwinder, already bounded by M5).

11.8 Edge Cases

An IDE that sends setBreakpoints for a source file not yet loaded (module not dlopen'd yet) — breakpoints go Pending exactly as in the CLI/GDB-RSP path (Invariant I9), no special DAP-only code path. A DAP client that disconnects mid-continue — session detaches cleanly per Invariant I2, inferior is not left running untraced with stale breakpoints installed unless the user explicitly requested "run to completion on disconnect."

11.9 Failure Analysis

A missing stopped event (Failure Mode FM9) manifests as an IDE that appears hung after a watchpoint fires; detection is the fixture matrix covering every StopReason variant; recovery is a one-line translate.rs fix once the missing variant is identified from the fixture's diff against the recorded transcript.

11.10 Operational Notes

dbg_command_latency_seconds{command} is shared with Phase 10 (Principle P7's single Session means one metric namespace, not two); the CLI has no separate telemetry surface beyond what Session already emits.

Scalability Analysis

Constant regardless of inferior size: breakpoint lookup (O(log n) in breakpoint count, never binary size, Principle P11); register read/write (O(1)). Grows with binary size: the initial /proc/PID/maps parse (O(modules)); total DWARF volume, but the effective per-query cost stays O(log CUs) thanks to .debug_aranges (Principle P5, Mental Model MM3) — the O(binary size) cost is paid once per queried CU, amortized and cached (Invariant I6). Grows with stack depth: unwind cost is O(frames) (Performance targets M5/M6); inline expansion adds a bounded per-frame constant (typically < 10 DW_TAG_inlined_subroutine children). Grows with thread count: supervisor dispatch is O(1) amortized per event via signalfd, but total throughput is bounded by System Constraints SC4 (4,096 threads) times per-event dispatch cost.

Named bottlenecks, in order: (1) cold-cache DWARF CU parse (Phase 3, mitigated by .debug_aranges + the LRU cache); (2) the ptrace syscall round trip itself (an unavoidable kernel boundary, mitigated for bulk reads by the /proc/PID/mem path, Performance target M3 vs. M4's contrast); (3) breakpoint reinstall after follow-exec, which must re-walk the entire pending set (Phase 9); (4) the GDB-RSP Phase-0 single-client TCP transport (multi-client is a documented Phase-1+ extension, not a Phase-0 gap that blocks anything in scope).

Horizontal scaling: not the traditional sense — a debugging session is inherently bound to one OS process tree. "Horizontal" here means multiple independent Session instances (one per inferior tree) sharing a host, bounded by System Constraints SC5 (64 concurrent inferiors) and the FD budget (Back-of-Envelope Capacity Model BEC6). Vertical scaling: a larger DWARF CU cache (tunable via --dwarf-cache-cus, default 256); more hardware slots is not tunable — SC7/SC8 are a CPU-vendor-set ceiling, not a software parameter. Coordination overhead: near-zero, since each Session/Inferior pair is independent; the only cross-session coordination is the kernel's own tracer-tracee binding (Principle P13). Practical ceiling: the DR0-DR3/BRP-WRP register-file size (4-6 slots) is a hard architectural ceiling per CPU that no software lever raises. Levers beyond that ceiling: software breakpoints (10,000+, SC6) rather than hardware for scale; a build-time precomputed address-sorted DIE index is a candidate Phase-1+ optimization for query throughput, not a Phase-0 deliverable.

Mental Models & First Principles

  1. MM1 — A breakpoint is a temporary lie the debugger tells the CPU. Insight: 0xCC/brk #0 patches code in place; the step-over dance restores the truth around it. Predicts: any code path reading inferior code without going through the breakpoint table sees the lie. Bug class without it: "phantom instruction" bugs in disassembly views showing a trap byte that was never in the source binary. Applies in Phase 5.
  2. MM2 — The register file, not any cache, is the only present tense. Insight: Invariant I3. Predicts: any UI element showing PC without a fresh GETREGSET is potentially stale. Bug class without it: stale-PC display after an out-of-band resume. Applies in Phase 1, Phase 4.
  3. MM3 — DWARF is an address-keyed database, not a tree to scan. Insight: .debug_aranges and .debug_line are indexes, not incidental byproducts. Predicts: any linear CU scan is wrong at scale. Bug class without it: quadratic attach-time slowdowns on large binaries. Applies in Phase 3.
  4. MM4 — The unwinder tells you where you are; the symbolicator tells you what that means. Insight: Principle P6's separation. Predicts: unwinding must never block on missing debug info. Bug class without it: an unsymbolicated frame silently dropped instead of shown with a bare address. Applies in Phase 4.
  5. MM5 — Every ptrace request is a question the kernel might refuse to answer. Insight: the wait/ptrace race (Garfinkel 2003). Predicts: any missing Result-wrapping in the ptrace wrapper is a crash waiting for a timing coincidence. Bug class without it: rare, timing-dependent supervisor panics. Applies in Phase 1.
  6. MM6 — A thread is not a process; a process's exit is its leader's exit, nothing else's. Insight: kernel thread-group semantics. Predicts: code assuming any thread's exit means process exit is wrong for non-leader threads. Bug class without it: premature Inferior teardown on a non-leader Tid exit. Applies in Phase 9.
  7. MM7 — The front-end protocol is a view; Session is the model. Insight: Principle P7. Predicts: state duplicated in dbg-rsp/dbg-dap instead of read from Session diverges under concurrent access. Bug class without it: GDB and DAP clients attached to the same session disagreeing about the breakpoint set. Applies in Phase 10, Phase 11.
  8. MM8 — Hardware breakpoint slots are a hard, small, physical resource, not a cache. Insight: DR0-DR3/BRPs are 4-6 registers, not a growable table. Predicts: code that tries to "add one more" past the count is wrong. Bug class without it: silent hardware-breakpoint starvation misreported as "the breakpoint didn't fire." Applies in Phase 6.

GDB chose a single monolithic C process accreted since 1986; it wins where maximum target/architecture breadth is needed (dozens of embedded targets) at the cost of an implicit-global-state core that is hard to reason about. WinDbg chose a proprietary protocol and PDB symbol format tightly integrated with Windows's own kernel debug objects; it wins on native Windows kernel-mode debugging (no Linux kgdb/kdb equivalent on Windows), at the cost of being unusable outside the Windows ecosystem.

Back-of-Envelope Capacity Model

  • BEC1 — Max resident DWARF working set. CU cache capacity (256, Invariant I6) × avg parsed CU size (≈150 KB, measured on typical -g binaries) = 256 × 150 KB ≈ 37.5 MB.
  • BEC2 — Breakpoint table memory. 10,000 (SC6) × sizeof(Breakpoint) (≈128 B incl. Option/enum overhead) = 1.28 MB.
  • BEC3 — Bulk-read time for a 1 GB region at SC11 (≥ 2 GB/s). 1 GB ÷ 2 GB/s = 0.5 s (matches Performance target M3 exactly).
  • BEC4 — Single-step time for a 100k-iteration loop at SC3 (≥ 20k steps/s). 100,000 ÷ 20,000 = 5.0 s (matches M2 exactly).
  • BEC5 — Hardware breakpoint fan-out. 4 x86-64 DR slots (SC7) × 64 max concurrent inferiors (SC5) = 256 total hardware breakpoints addressable system-wide, though any single inferior is still capped at 4 (Invariant I5).
  • BEC6 — FD budget check. 3 FDs/inferior (SC14) × 64 concurrent inferiors (SC5) = 192 FDs — 5.3x headroom inside the 1,024 default ulimit.
  • BEC7 — GDB-RSP packet-rate ceiling. 1 ÷ SC12 (1 ms median round trip) = 1,000 packets/s per connection — the rate an interactive info registers polling loop can sustain.
  • BEC8 — DAP concurrent-IDE ceiling. SC13 (5 ms/256-frame trace) × N IDEs must stay under a 100 ms human-perceptible UI-latency budget ⇒ N ≤ 20 concurrent stackTrace requests per 100 ms window before requests queue.
  • BEC9 — 30-day fuzz executions for the M12 gate. ≈10,000 exec/s per fuzz core (typical libFuzzer throughput on small DWARF inputs) × 86,400 s/day × 30 days ≈ 2.59×10^10 executions — the statistical weight behind M12's "zero crashes" claim.
  • BEC10 — Soak-test RSS ceiling (M11, ±5% over 24h). Starting RSS ≈ 50 MB (post-attach + symbolicate, SC2) × 1.05 = 52.5 MB before the soak test is considered failed.
  • BEC11 — Multi-thread register-cache worst case. SC4's 4,096-thread ceiling × per-thread Registers size (≈216 B, GPRs + FPU selector, NT_PRSTATUS+NT_PRFPREG) ≈ 885 KB resident at the pathological maximum.

Alternative Architectures (Roads Not Taken)

ALT1 — JIT-based dynamic binary instrumentation (Pin/Valgrind-style).

[inferior code] --rewrite--> [code cache] --instrumented basic blocks--> [analysis hooks]

Regime where it wins: heavyweight whole-program analysis (memory checking, taint tracking) where per-instruction overhead is acceptable and no live gdb-style interactive session is needed. Real system: Valgrind (Nethercote & Seward 2007), Pin (Luk et al. 2005). Rejected because: a 5-100x slowdown is unacceptable for an interactive stepping debugger (violates SC9 startup and SC3 step-throughput targets), and instrumentation-based tools have no clean mapping onto hardware breakpoints/watchpoints since their mechanism is software-only.

ALT2 — Full syscall-interception record/replay first (rr-style).

[recorder: ptrace+seccomp-bpf] --trace file--> [replayer: deterministic re-execution]

Regime where it wins: bugs that must be reproduced exactly and stepped backward (races, heisenbugs). Real system: Mozilla rr. Rejected as the Phase-0 architecture because live attach-to-a-running-process — the single most common debugging entry point — is not rr's design center, and rr requires single-logical-CPU replay plus specific CPU performance- counter support not universally available (tracked as a Phase-1+ stretch, Deferred Features Register, not a Phase-0 substitute).

ALT3 — In-process debugging via self-installed signal handlers (no supervisor process).

[target binary + linked runtime] --installs own SIGTRAP/SIGSEGV handlers--> [socket to inspector]

Regime where it wins: production post-mortem/crash-reporting agents where the target must debug itself with zero external privilege (embedded crash handlers). Real system: Google Breakpad/Crashpad. Rejected because: it cannot set breakpoints before a crash happens, cannot control CPU registers/execution from outside the process, and a compromised inferior can lie to its own handler — violating Principle P1 (inferior state is untrusted) at the architectural level, not just an implementation detail.

ALT4 — Kernel-mode/hypervisor-level debugging (VM introspection) instead of ptrace.

[hypervisor/VMI] --intercepts guest traps, bypasses ptrace entirely--> [debug port outside guest]

Regime where it wins: kernel-mode debugging (kgdb/kdb), or debugging a guest OS that must not be trusted to cooperate at all. Real system: Linux's own kgdb/kdb; VMI frameworks such as LibVMI. Rejected because: this project's Phase 0-12 scope is user-space process debugging on a single Linux host — kernel/hypervisor debugging is a different trust boundary and privilege model entirely, explicitly out of scope (Deferred Features Register: kernel-mode debugging).

Glossary

  • ptrace — the Linux syscall (ptrace(2)) giving one process control over another's execution and memory.
  • PTRACE_SEIZE — attaches without injecting a SIGSTOP, this project's exclusive attach mode.
  • PTRACE_ATTACH — legacy attach mode that injects SIGSTOP; not used here.
  • PTRACE_PEEKDATA / POKEDATA — word-at-a-time inferior memory read/write via ptrace.
  • PTRACE_GETREGSET — reads a named register set (NT_PRSTATUS, NT_PRFPREG, …).
  • PTRACE_CONT / PTRACE_SINGLESTEP — resume the inferior, optionally one instruction.
  • waitpid — the syscall a supervisor blocks on to learn of an inferior's state changes.
  • WIFSTOPPED / WSTOPSIG — macros classifying a waitpid status as a stop and its signal.
  • SIGTRAP — the signal delivered on a breakpoint or single-step trap.
  • 0xCC / INT3 — the x86-64 software-breakpoint trap opcode.
  • brk #0 — the AArch64 software-breakpoint trap instruction.
  • ASLR — Address Space Layout Randomization; source of the aslr_slide computation.
  • CFA (Canonical Frame Address) — the reference address a CFI rule table is keyed against per frame.
  • CFI (Call Frame Information) — the .eh_frame/.debug_frame encoding of how to compute the CFA and recover saved registers.
  • CIE / FDE — Common Information Entry / Frame Description Entry, the two record types composing CFI.
  • DWARF — the debugging information format this project parses (v4/v5).
  • DIE (Debugging Information Entry) — one node in a DWARF compilation unit's tree.
  • Compilation Unit (CU) — one source file's worth of DWARF DIEs.
  • .debug_info / .debug_abbrev — the DIE tree and its abbreviation codes.
  • .debug_line — the line-number program (address ↔ source line/column).
  • .debug_loc / .debug_loclists — DWARF v4/v5 location-expression lists.
  • .debug_aranges — the address-range-to-CU index (Mental Model MM3).
  • .eh_frame — the runtime-loaded CFI section (vs. the often-stripped .debug_frame).
  • DR0-DR7 — x86-64 debug registers controlling hardware breakpoints/watchpoints.
  • BRP / WRP — AArch64 breakpoint/watchpoint register pairs.
  • Watchpoint — a hardware trap on a memory access (read/write/both), not a code patch.
  • Software breakpoint — a code patch (0xCC/brk #0) trapping execution at an address.
  • Hardware breakpoint — a debug-register-driven trap, not a code patch.
  • Inline frame — a synthesized stack frame for an inlined call, not present on the real stack.
  • Tail call — a call whose frame is replaced by the callee's, invisible to naive unwinding.
  • Frame pointer — the register (RBP/X29) conventionally chaining stack frames.
  • Stack unwinding — reconstructing the call chain from register/memory state.
  • Symbolication — mapping an address to a function/file/line/type name.
  • Demangling — reversing a compiler's name-mangling scheme to a readable symbol.
  • Itanium mangling — the C++ ABI's symbol-name encoding.
  • Rust v0 mangling — RFC 2603's symbol-name encoding, successor to Rust's legacy scheme.
  • GDB-RSP — the GDB Remote Serial Protocol.
  • DAP — the Debug Adapter Protocol.
  • Rendezvous (_r_debug) — the dynamic linker's structure notifying a debugger of load/unload events.
  • build-id — a .note.gnu.build-id hash uniquely identifying a binary across paths.
  • debuglink — a .gnu_debuglink section pointing at separated debug info.
  • follow-fork — the policy for which process(es) remain traced after fork.
  • follow-exec — the policy for whether tracing continues after exec.
  • Scheduler-locking — the policy for which threads run during a step.
  • PhaseDeferred — this document's marker for a feature intentionally out of Phase 0-12 scope, registered in the Deferred Features Register.
  • Conformance fixture — a named input/expected-output pair gating a phase's Acceptance Criteria.
  • TOCTOU — Time-Of-Check-To-Time-Of-Use; the ptrace race class documented in Garfinkel 2003 (Threat T10).
  • Core file — a post-mortem memory snapshot of a crashed process (deferred feature).
  • Tracepoint — a breakpoint that captures state without stopping execution (deferred feature).
