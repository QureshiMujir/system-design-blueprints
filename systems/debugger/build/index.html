⬜ Phase 0 — Repository Skeleton, Governance & the Ptrace Smoke Test

Objectives

Stand up the full repository shape (Repository Layout) before any debugging logic exists; prove the single load-bearing fact the entire project rests on — that this process can PTRACE_SEIZE a child, single-step it, and read its registers back — via one integration test. Constraint introduced: every later phase assumes the governance files, CI workflow, and crate skeleton already exist; nothing is retrofitted.

Deliverable

A repository tree matching Repository Layout line-for-line; make test returns 0 running exactly the ptrace smoke test; make lint returns 0; make conformance prints a JSON report with every bucket Deferred and a non-zero engine_version.

Acceptance

cargo test -p dbg-inferior passes 1/1; smoke test completes attach→singlestep→read-regs→ detach in < 50 ms (System Constraints SC9); cargo clippy --all-targets -- -D warnings exits 0; conformance.report.json validates against report_schema.json.

Fixtures

examples/c-hello/hello.c (trivial C binary, no debug info required yet) | purpose: smoke target | expected: process launches, PC is non-zero after one single-step. conformance/corpora/inferior/attach/basic.scenario | purpose: attach+detach round trip | expected: Pass within 100 ms.

Pitfalls
  1. Forgetting PTRACE_O_EXITKILL — leaves the inferior wedged in T state on debugger death (Invariant I2, Failure Mode FM2); set it immediately after PTRACE_SEIZE.
  2. Using PTRACE_ATTACH instead of PTRACE_SEIZE — ATTACH injects a SIGSTOP the supervisor must then absorb; SEIZE does not. Phase 0 uses SEIZE exclusively.
  3. Not handling ESRCH on every ptrace call from the start — a signal between wait and the next request returns ESRCH (Garfinkel 2003; Threat T10); every wrapper must translate it to a typed InferiorGone, never propagate a raw OS error.
  4. Committing the governance-file skeleton as an afterthought — later phases assume docs/adr/, docs/runbooks/, and fuzz/ already exist; retrofitting them mid-Phase-3 costs more than doing it here.

⬜ Phase 1 — Ptrace Control Plane & the Supervisor Event Loop

Objectives

Build the kernel-facing layer every later feature calls through — dbg-core never issues a raw ptrace request directly. Constraint: exactly one task per inferior may hold ptrace state (Principle P3, Invariant I4).

Deliverable

dbg-inferior builds and passes on x86-64 and AArch64; the supervisor loop runs four scripted scenarios: single-step, software-breakpoint hit (a trivial hand-patched 0xCC), fork, exec.

Acceptance

Conformance buckets inferior.attach, inferior.singlestep, inferior.event_fork, inferior.event_exec all Pass; single-step throughput ≥ 20,000 steps/s (SC3, Performance target M2); bulk /proc/PID/mem read ≥ 2 GB/s sequential (SC11, M3).

Fixtures

corpora/inferior/singlestep/tight-loop.scenario | purpose: throughput measurement | expected: 100k steps < 5 s (M2). corpora/inferior/event_fork/basic.scenario | purpose: fork ordering either direction | expected: both Forked{parent,child} orders accepted. corpora/inferior/killed-mid-continue.scenario | purpose: malformed/adversarial timing (Domain Model §8.7) | expected: Exited event, no panic.

Pitfalls
  1. Not detaching on supervisor crash — Inferior's Drop must call PTRACE_DETACH and close FDs (Invariant I2); Rust's drop guarantee is load-bearing here.
  2. Mixing PTRACE_CONT and PTRACE_SYSCALL resume modes across resumes without remembering the prior mode per-thread — causes misclassified stops.
  3. Treating PTRACE_PEEKDATA's errno=0-on-success-even-if-value-is--1quirk carelessly — always zeroerrno` before the call and check after.
  4. Reading memory one word at a time via ptrace for anything > 32 bytes — /proc/PID/mem is an order of magnitude faster (SC11); use it (Andriesse Ch. 5).
  5. Not setting PTRACE_O_TRACESYSGOOD — without it, a syscall stop is indistinguishable from a breakpoint SIGTRAP, and step-over intermittently single-steps a syscall instead.
  6. Not translating ESRCH to a typed event on every call (Garfinkel 2003, Threat T10) — a signal race between wait and the next request kills the inferior out from under a ptrace request; every wrapper must catch it.

⬜ Phase 2 — ELF Reading, Module Discovery & the Dynamic-Linker Rendezvous

Objectives

Parse ELF via the object crate (ADR-04); discover loaded modules from /proc/PID/maps; maintain the module set incrementally via the dynamic-linker rendezvous (Domain Model §8.2). Constraint: every address the rest of the system handles must be resolvable to a Module and an aslr_slide before any DWARF query is meaningful.

Deliverable

Module/ModuleSet (Core Schema §11.3) fully implemented; the rendezvous breakpoint installs at r_brk and fires correctly on dlopen of libc, libm, and a custom .so.

Acceptance

Conformance bucket module.discovery Pass for a binary that dlopens three libraries; attach + symbolicate a 100 MB binary completes < 1 s p50 / < 2 s p99 (SC2, Performance target M1); zero panics on the elf_fuzz.rs corpus (Threat T2).

Fixtures

corpora/elf/pie-binary.json | purpose: ASLR-slide correctness | expected: slide computed from lowest PT_LOAD, not entry point. corpora/elf/dlopen-three.scenario | purpose: rendezvous | expected: ModuleSet grows by exactly 3 after three dlopen calls. corpora/elf/truncated-header.bin | purpose: malformed input (Domain Model §8.6) | expected: typed error, no panic, no OOB read.

Pitfalls
  1. Treating the /proc/PID/maps [vdso] line as a normal on-disk module — it is in-memory only; the mmap path differs.
  2. Computing the ASLR slide off the entry point or section table instead of the lowest PT_LOAD segment — off by a few hundred bytes on PIE binaries (Levine Ch. 6).
  3. Caching debug-info paths across invocations keyed by path instead of build-id — distributions update packages; build-id is the only stable key (Core Schema §11.6 annotation table).

⬜ Phase 3 — DWARF Parsing: Line Tables, Types & Location Expressions

Objectives

Parse .debug_info/.debug_abbrev/.debug_line/.debug_loc(lists)/.debug_aranges/ .debug_str via gimli (ADR-03), lazily (Principle P5, Invariant I6). Constraint: no CU parses until a query reaches it; .debug_aranges is the mandatory address index (Mental Model MM3).

Deliverable

Address-to-source resolution at addr2line parity across the conformance corpus; type-DIE parsing sufficient to display C/C++/Rust structs, enums, primitives, pointers, arrays.

Acceptance

Conformance buckets dwarf.line, dwarf.subprogram, dwarf.type, dwarf.location, demangle.itanium, demangle.rust_v0 all Pass; DWARF parse of 100 MB .debug_info with a hot address index completes < 100 ms (Performance target M8); demangling matches reference output on 10,000 symbols per demangler (exact match, zero divergence).

Fixtures

corpora/dwarf/line/optimized-inline.json | purpose: line-table fidelity on -O2 builds | expected: matches addr2line line-for-line. corpora/dwarf/location/loclists-v5.json | purpose: DWARF5 offset-base handling | expected: same resolved address as the v4 equivalent fixture. corpora/demangle/rust_v0/10k.tsv | purpose: RFC 2603 conformance | expected: exact string match, 10,000/10,000.

Pitfalls
  1. Trusting DW_AT_decl_file over the line table for source-file mapping — the line table is authoritative at a given PC; DW_AT_decl_file is only where the compiler thought the function was declared (sometimes a header).
  2. Ignoring DW_AT_ranges — modern compilers split functions into discontiguous ranges.
  3. Confusing DWARF v4's .debug_loc (absolute addresses) with v5's .debug_loclists (offset-based) — same evaluator, different match arms.
  4. Not honoring prologue_end when resolving "the start of the function" — a breakpoint at a function's first line must land past the prologue.
  5. Caching parsed DIEs keyed by path instead of inode+mtime — a rebuilt binary invalidates the cache silently otherwise.
  6. Not bounding DW_OP_call* recursion depth in location-expression evaluation — a crafted expression can otherwise recurse unboundedly (Invariant I13, Threat T3).

⬜ Phase 4 — Stack Unwinding via CFI and Frame-Pointer Fallback

Objectives

Build the unwinder: .eh_frame CIE/FDE-driven CFI walking as the correctness path, a frame-pointer fallback for modules without debug info, and inline-frame expansion. Constraint: unwinding never blocks on missing debug info (Principle P6).

Deliverable

bt matches gdb -batch -ex 'bt' line-for-line on the conformance corpus binaries, including one built with frame pointers omitted (-fomit-frame-pointer, forcing the CFI path) and one built specifically to exercise the FP fallback.

Acceptance

Conformance buckets unwind.cfi, unwind.inline, unwind.fp_fallback all Pass; 1,000-frame CFI unwind completes < 1 ms (Performance target M5); 1,000-frame FP-fallback unwind completes < 200 µs (M6, cheaper because it skips CFI evaluation entirely).

Fixtures

corpora/unwind/cfi/1k-frames.bin | purpose: throughput + correctness at depth | expected: 1,000/1,000 frames match reference, < 1 ms. corpora/unwind/inline/nested-3-deep.bin | purpose: inline-chain fidelity | expected: 3 synthesized inline frames between two real frames. corpora/unwind/fp/stripped.bin | purpose: fallback path | expected: frame count matches reference even with source: None.

Pitfalls
  1. Reading RBP as "the saved frame pointer" before the prologue's push %rbp executes — the CFI rule for "RBP holds the saved register" only activates post-prologue.
  2. Walking .debug_frame instead of .eh_frame — modern compilers emit and require .eh_frame at runtime; .debug_frame is frequently stripped.
  3. Not respecting DW_CFA_GNU_args_size for variadic functions, which adjust SP post-call.
  4. Treating a tail call as a normal frame — a tail call has no stack entry at all; the "PC is at a call instruction" heuristic is unreliable for detecting this.
  5. Trusting frame pointers in -O2 code where they are routinely omitted — CFI must be the primary path, FP only the documented fallback (this phase's entire premise).

⬜ Phase 5 — Software Breakpoints & the Single-Step-Over-Breakpoint Dance

Objectives

Implement software breakpoint install/uninstall and the exact step-over sequence that makes Invariant I1 hold. Constraint: the six-step dance runs to completion inside the supervisor task without yielding to the front end (Principle P3/I4).

Deliverable

A CLI session that sets a breakpoint at main, continues, hits it, single-steps past it, and continues to exit — verified against gdb -batch -ex 'b main' -ex 'run' -ex 'next' -ex 'continue' on the same binary.

Acceptance

Conformance bucket inferior.swbreak Pass; 1,000 breakpoints installed in < 20 ms (Performance target M7, Invariant/Principle P11's indexed table is what makes this possible); zero lost-byte incidents (Invariant I1) across a 24-hour soak (Performance target M11).

Fixtures

corpora/breakpoint/sw/install-hit-restore.scenario | purpose: the core dance | expected: byte restored bit-identical after 1,000 hit/step cycles. corpora/breakpoint/sw/pending-dlopen. scenario | purpose: Invariant I9 | expected: breakpoint installs exactly once after the target library loads.

Pitfalls
  1. Forgetting to restore the original byte — the single most common debugger bug (Failure Mode FM1); the inferior crashes mysteriously, possibly on a different thread, possibly much later.
  2. Confusing the two architectures' trap-PC semantics: x86-64's SIGTRAP reports PC one past the 0xCC; AArch64's brk #0 reports PC at the trap itself. Getting this backwards shifts every subsequent line-table query by one instruction.
  3. Storing the breakpoint table as a Vec — O(n) lookup at scale (Principle P11, Reference Implementations' headcrab pitfall).
  4. Not clearing a breakpoint before follow-exec tears down the module set — installed_addr is meaningless in the new address space (handled fully in Phase 9, flagged here).

⬜ Phase 6 — Hardware Breakpoints and Watchpoints via Debug Registers

Objectives

Implement hardware breakpoints and watchpoints using x86-64's DR0-DR7 and AArch64's BRP/WRP register files — the only mechanism that observes memory access without modifying inferior code (ADR-07: pulled into Phase-0 scope, not deferred).

Deliverable

A watchpoint set on a heap allocation fires exactly once per write, across both a software- breakpoint-heavy workload (proving the two mechanisms coexist) and a tight loop where a software breakpoint would have distorted timing (proving the watchpoint's non-invasive property).

Acceptance

Conformance bucket inferior.hwbreak/inferior.hwwatch Pass; hardware breakpoint/watchpoint install latency < 1 ms per slot (Performance target M14); SlotsExhausted returned, not a crash or silent downgrade, on the 5th concurrent request (SC7).

Fixtures

corpora/breakpoint/hw/watch-write-4byte.scenario | purpose: access-kind/width correctness | expected: fires exactly on 4-byte writes, not reads. corpora/breakpoint/hw/exhaustion. scenario | purpose: Invariant I5/Principle P10 | expected: 5th request returns SlotsExhausted, first 4 remain intact.

Pitfalls
  1. Assuming 4 slots on AArch64 without reading ID_AA64DFR0_EL1 — implementations vary (6 is typical but not universal).
  2. Forgetting that x86-64's DR7 RW/LEN fields are shared between breakpoint and watchpoint use of the same 4 slots — a hardware breakpoint and a hardware watchpoint compete for the same 4-slot budget, not independent budgets.
  3. Not clearing the slot allocator's bit on delete — a leaked slot manifests as premature SlotsExhausted (Failure Mode FM7).
  4. Reading DR6 without clearing it after use — stale bits misattribute the next trap to the wrong slot.

⬜ Phase 7 — Variable Display, Type-Aware Rendering & Pretty-Printers

Objectives

Implement print: parse an expression (Domain Model §8.3), evaluate it against the current frame, render it through a type/language-aware pretty-printer. Constraint: the expression language is a strict C subset — no function calls (Deferred Features Register).

Deliverable

print renders correctly on ~50 fixtures spanning C, C++, and Rust, including nested structs, tagged enums, and a niche-optimized Option<&T>.

Acceptance

Conformance bucket print.basic Pass on all ~50 fixtures; print.vtable reports Deferred with a resolving anchor (Deferred Features Register); pointer-cycle fixtures terminate within the depth-16 bound, never hang.

Fixtures

corpora/print/rust-option-niche.json | purpose: niche-optimization correctness | expected: Some(&x)/None render distinctly with no extra discriminant byte assumed. corpora/print/ cyclic-pointer.json | purpose: recursion-depth bound | expected: renders "...(depth limit)" at depth 16, no hang. corpora/print/cpp_vtable.json | purpose: Deferred-bucket contract | expected: report shows outcome: "Deferred".

Pitfalls
  1. Following pointers without a depth bound — a cyclic structure recurses forever; bound at 16 (§7.2).
  2. Reading a string via read_string(addr) with no length cap — a race with a concurrent free can read megabytes of garbage; cap at 4 KiB, emit a truncation marker.
  3. Trusting DW_AT_byte_size over DW_AT_data_member_location for field offsets — byte_size is a source-level size, not necessarily the in-memory layout's authority.

⬜ Phase 8 — Step Semantics: step-in, step-over, step-out, until, inline frames

Objectives

Implement the step state machine over the primitives Phases 1, 3-5 provide. Constraint: the temporary breakpoint the machine sets for step-over/step-out is cleared on every stop, not only the expected one (Invariant I11).

Deliverable

The four step operations work correctly across single-threaded and (in coordination with Phase 9) multi-threaded programs, both optimized and unoptimized builds, including inline frames.

Acceptance

Conformance buckets step.in, step.over, step.out, step.until, step.inline all Pass; a step-over of a noreturn call downgrades to step-in within one instruction (verified by fixture, not timeout-dependent); zero stuck temporary breakpoints across a 24-hour soak (Invariant I11, Performance target M11).

Fixtures

corpora/stepping/inline-3-deep.scenario | purpose: inline-frame step-out ordering | expected: leaves 3 inline frames before the real frame changes. corpora/stepping/noreturn-call. scenario | purpose: the abort/exit/longjmp class | expected: downgrades to step-in, no hang. corpora/stepping/signal-during-step-over.scenario | purpose: Invariant I11 | expected: temp breakpoint cleared even though the expected return-address breakpoint never fired.

Pitfalls
  1. Not clearing the temp breakpoint on an intervening signal — if the inferior takes a signal between continue and the expected temp-breakpoint hit, the temp breakpoint lingers in the table and the next step-out misbehaves (Invariant I11 is the direct fix).
  2. Stepping over a call to a function that never returns — the temp breakpoint at the return address never fires; detect DW_AT_noreturn and downgrade rather than hang.
  3. Stepping over an instruction that is itself a software breakpoint — the step-over-breakpoint dance (Phase 5) must run first, or step-over loops.

⬜ Phase 9 — Multi-Thread and Multi-Process Debugging

Objectives

Track threads within one inferior and follow fork/exec across process boundaries. Constraint: no two supervisor tasks ever trace the same Tid simultaneously (Invariant I12, Principle P13).

Deliverable

A 32-thread pthread program is debugged correctly (info threads lists all 32, thread N switches, bt works per-thread); a fork-then-exec shell-style program follows the child correctly under follow-fork child.

Acceptance

Conformance buckets thread.list, thread.switch, follow.fork, follow.exec all Pass; 32-thread info threads + per-thread bt completes < 50 ms total (Performance target M13); zero double-traced Tids across 1,000 fork events (Invariant I12).

Fixtures

corpora/follow_fork/parent-first.scenario and corpora/follow_fork/child-first.scenario | purpose: unspecified kernel event ordering | expected: both orders handled identically. corpora/follow_fork/vfork-window.scenario | purpose: shared-address-space hazard | expected: breakpoint-set requests between VFORK and VFORK_DONE are rejected with a typed error, not silently applied to both processes. corpora/multithread/pthread32.scenario | purpose: scale target | expected: all 32 threads enumerated, switch round-trips correctly.

Pitfalls
  1. Assuming PTRACE_EVENT_FORK always arrives on the parent before the child — the order is unspecified; handle either (fixture parent-first/child-first).
  2. Not realizing vfork shares the parent's address space until VFORK_DONE — setting a breakpoint in that window affects both processes; refuse breakpoint-set requests during it.
  3. Persisting a breakpoint's installed_addr across exec — the address space is entirely new; the pending/named-symbol set must be re-resolved and reinstalled after re-walking the fresh module set (Phase 2's rendezvous re-run).
  4. Assuming any thread's exit means the process exited — only the leader's exit does (Mental Model MM6); a non-leader thread exit only removes that Tid from the thread map.

⬜ Phase 10 — GDB Remote Serial Protocol Server

Objectives

Implement the GDB-RSP wire protocol (Domain Model §8.4) so a stock gdb client attaches unmodified (ADR-08). Constraint: bind to loopback by default (ADR-21, Threat T4).

Deliverable

gdb -ex "target remote :4444" connects and successfully drives info registers, x/16i $pc, b main, c, s, bt, print x, continue, detach against this project's server.

Acceptance

Conformance bucket rsp.minimum Pass against a recorded gdb session corpus (byte-for-byte replay after PID/timestamp redaction, Principle P9); GDB-RSP round trip for a g packet < 1 ms median (Performance target M9, SC12).

Fixtures

corpora/rsp/gdb-session-basic.recording | purpose: end-to-end replay | expected: bit- identical transcript after redaction. corpora/rsp/checksum-mismatch.scenario | purpose: malformed input (Domain Model §8.6) | expected: server sends -, resends last reply on request, never desyncs.

Pitfalls
  1. Not handling +/- half-duplex resend correctly — the server must retain the last-sent packet and resend verbatim on -.
  2. Sending an unescaped #, $, or } byte — the most common implementer bug; the client silently truncates or misparses (Failure Mode FM8).
  3. Returning a wrong-length register file on g — must match the target-description XML byte-for-byte, or gdb displays garbage (Failure Mode FM4).
  4. Not advertising vContSupported+ in the qSupported reply — modern gdb falls back to c/s, breaking the multi-thread story.

⬜ Phase 11 — Debug Adapter Protocol Server and Interactive CLI

Objectives

Implement the DAP wire protocol (ADR-09) and the GDB-alias interactive CLI. Constraint: both are translation layers over Session, never parallel state (Principle P7, Invariant I10).

Deliverable

A VS Code launch configuration ("type": "dbg-native") debugs examples/c-hello: hits a breakpoint, prints a local, single-steps a line, continues to exit. The CLI runs the identical scenario.

Acceptance

Conformance buckets dap.minimum and cli.minimum both Pass; DAP stackTrace for a 256-frame stack < 5 ms (Performance target M10, SC13); zero missing stopped events across every StopReason variant in the fixture matrix (Failure Mode FM9 regression guard).

Fixtures

corpora/dap/vscode-session-basic.recording | purpose: end-to-end replay (redacted) | expected: bit-identical transcript. corpora/dap/watchpoint-stop-event.scenario | purpose: Failure Mode FM9 regression | expected: stopped event emitted for a watchpoint hit, not only breakpoint hits. corpora/cli/gdb-alias-parity.scenario | purpose: muscle-memory contract | expected: every listed CLI alias resolves to the documented Session call.

Pitfalls
  1. Reusing GDB-RSP Tid semantics directly in DAP — DAP's 0 is reserved; rebase via a per-session monotonic mapping.
  2. Not sending stopped events for non-breakpoint stops — the IDE ignores any stop it never received an event for (signals, watchpoint hits, step completions all need one).
  3. Returning unbounded variables responses — some IDEs paginate poorly under load; cap and expose start/count.

⬜ Phase 12 — Observability, Operations & Release Readiness

Objectives

Wire production-shaped observability, the operational runbooks, and the release gates (fuzzing, soak testing, sanitizers) that must pass before this project is considered Sealed. Constraint: every span/metric introduced here should already have been emitted since Phase 0 (Principle P14) — this phase adds dashboards and gates, not instrumentation.

Deliverable

make trace runs the conformance suite with tracing on, producing a JSONL trace covering every supervisor event; make metrics brings up Prometheus + Grafana with a working dashboard; the fuzz/soak/sanitizer CI matrix runs on every push and nightly respectively.

Acceptance

24-hour soak: zero unhandled exceptions, RSS stable ±5% (Performance target M11); 30-day fuzz corpus replay: zero crashes across all four targets (M12, the Sealed gate); cargo miri test --workspace passes for dbg-core's type-level invariants; all three runbooks reviewed and linked from README.md.

Fixtures

tests/soak/24h-mixed-workload.rs | purpose: M11 gate | expected: RSS delta ≤ 5% over 24h, zero panics. docs/architecture/trace-example.json | purpose: tracing completeness | expected: every InferiorEvent variant appears at least once in a full-scenario trace. fuzz/corpus-regressions/*.bin | purpose: permanent regression fixtures from prior crashes (Zeller 1999 minimization) | expected: each replays clean, zero crashes.

Pitfalls
  1. Spanning every individual memory read instead of the user-level command — a print of a 1 MB array does thousands of reads; span the command, treat reads as span events.
  2. Logging the inferior's environment (/proc/PID/environ) — contains secrets; redact at INFO, permit only at DEBUG with an explicit opt-in flag (Threat T7).
  3. Exposing --metrics-port without authentication — metrics expose Tids and addresses; documented as requiring a reverse proxy or loopback-only bind, mirroring ADR-21's GDB-RSP default.
