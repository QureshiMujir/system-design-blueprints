Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does Invariant I3 (register file is ground truth) make Principle P5 (lazy DWARF parsing) safe rather than risky?
  2. Trace the exact ptrace-call sequence the single-step-over-breakpoint dance (Phase 5) performs, and explain which part of Invariant I1 each step protects.
  3. Why does hardware-breakpoint exhaustion (Invariant I5) never silently degrade to a software breakpoint, and which principle (P10) forbids it?
  4. Compare the ASLR-slide computation (Domain Model §8.2) with the unwinder's CFA computation (Phase 4) — why must both be applied before, not after, a symbol lookup?
  5. Why is .debug_aranges (Phase 3) necessary given that .debug_info already contains every DIE? Connect the answer to the System Constraints numbers that make an O(n) scan unacceptable.
  6. Using the Comparative Architecture Table, explain why rr's chaos-mode replay cannot be bolted onto this design's live-debugging Session without violating Invariant I4.
  7. Why does follow-fork "both" mode (Phase 9) require two independent supervisor tasks rather than one task tracking two Pids, per Invariant I4 and Principle P3?
  8. Using Threat T10 and Failure Mode FM2, explain why PTRACE_SEIZE (not PTRACE_ATTACH) plus PTRACE_O_EXITKILL is the only combination that satisfies Invariant I2.
  9. Why must the step state machine (Phase 8) clear its temporary breakpoint on every stop, not only the expected one, per Invariant I11? Give the specific race this prevents.
  10. Explain why the GDB-RSP and DAP servers (Phase 10, Phase 11) are translation layers over one Session rather than parallel implementations, and what Mental Model MM7 predicts breaks if that boundary is violated.
  11. Using the Back-of-Envelope Capacity Model (BEC1, BEC10), justify the 256-CU LRU cache size (Invariant I6) against the 24-hour soak-test RSS budget (Performance target M11).
  12. Why is symbol-server/debuginfod integration deferred (Deferred Features Register) rather than built in Phase 2, given that .gnu_debuglink resolution already exists there?
  13. Contrast this design's CFI+FP-fallback unwinder (Phase 4) against Pin's/Valgrind's JIT-based instrumentation (Comparative Architecture Table; Papers: Luk 2005, Nethercote 2007) — why would a JIT-based approach make fp_fallback.rs unnecessary, and what would it cost instead?
  14. Using Invariant I9 and Phase 2's rendezvous mechanism, explain what happens to a Pending breakpoint if its target library is dlopen'd and immediately dlclose'd before the rendezvous breakpoint fires.
  15. Why does Alternative Architectures' "userspace emulator" road-not-taken avoid the entire ptrace threat surface in the Threat Model (T1, T4, T10), and why was it rejected anyway?
  16. Using Performance Engineering's M2/M5 targets and the Scalability Analysis bottleneck ranking, identify which subsystem must be optimized first if a customer reports a binary 10x larger than System Constraints SC1 assumes.
  17. Why does the Rust v0 demangler (ADR-12, RFC 2603) matter more for this project than it historically did for GDB, which demangled only at display time?
  18. Explain how Testing & Verification Strategy's delta-debugging fixture-minimization approach (Zeller 1999) would be used to shrink a fuzzer-discovered DWARF crash (Threat T3, Failure Mode FM5) into a Phase 3 conformance fixture.

Mental Models & First Principles

  1. MM1 — A breakpoint is a temporary lie the debugger tells the CPU. Insight: 0xCC/brk #0 patches code in place; the step-over dance restores the truth around it. Predicts: any code path reading inferior code without going through the breakpoint table sees the lie. Bug class without it: "phantom instruction" bugs in disassembly views showing a trap byte that was never in the source binary. Applies in Phase 5.
  2. MM2 — The register file, not any cache, is the only present tense. Insight: Invariant I3. Predicts: any UI element showing PC without a fresh GETREGSET is potentially stale. Bug class without it: stale-PC display after an out-of-band resume. Applies in Phase 1, Phase 4.
  3. MM3 — DWARF is an address-keyed database, not a tree to scan. Insight: .debug_aranges and .debug_line are indexes, not incidental byproducts. Predicts: any linear CU scan is wrong at scale. Bug class without it: quadratic attach-time slowdowns on large binaries. Applies in Phase 3.
  4. MM4 — The unwinder tells you where you are; the symbolicator tells you what that means. Insight: Principle P6's separation. Predicts: unwinding must never block on missing debug info. Bug class without it: an unsymbolicated frame silently dropped instead of shown with a bare address. Applies in Phase 4.
  5. MM5 — Every ptrace request is a question the kernel might refuse to answer. Insight: the wait/ptrace race (Garfinkel 2003). Predicts: any missing Result-wrapping in the ptrace wrapper is a crash waiting for a timing coincidence. Bug class without it: rare, timing-dependent supervisor panics. Applies in Phase 1.
  6. MM6 — A thread is not a process; a process's exit is its leader's exit, nothing else's. Insight: kernel thread-group semantics. Predicts: code assuming any thread's exit means process exit is wrong for non-leader threads. Bug class without it: premature Inferior teardown on a non-leader Tid exit. Applies in Phase 9.
  7. MM7 — The front-end protocol is a view; Session is the model. Insight: Principle P7. Predicts: state duplicated in dbg-rsp/dbg-dap instead of read from Session diverges under concurrent access. Bug class without it: GDB and DAP clients attached to the same session disagreeing about the breakpoint set. Applies in Phase 10, Phase 11.
  8. MM8 — Hardware breakpoint slots are a hard, small, physical resource, not a cache. Insight: DR0-DR3/BRPs are 4-6 registers, not a growable table. Predicts: code that tries to "add one more" past the count is wrong. Bug class without it: silent hardware-breakpoint starvation misreported as "the breakpoint didn't fire." Applies in Phase 6.

5. Required Reading

Books

  • Levine, J.R. — Linkers and Loaders (Morgan Kaufmann, 1999). Ch. 1-3 (object-file anatomy, symbol resolution), Ch. 6 (dynamic linking/relocation). Extract: why ASLR-slide computation and the dynamic-linker rendezvous exist at all. Applied in Phase 2 and Domain Model.
  • Bryant, R.E. & O'Hallaron, D.R. — Computer Systems: A Programmer's Perspective, 3rd ed. (Pearson, 2015). Ch. 3 (Machine-Level Representation of Programs), Ch. 7 (Linking). Extract: the register/stack mental model the unwinder and evaluator both depend on. Applied in Phase 4 and Phase 7.
  • Stevens, W.R. & Rago, S.A. — Advanced Programming in the UNIX Environment, 3rd ed. (Addison-Wesley, 2013). Ch. 8 (Process Control), Ch. 10 (Signals). Extract: the exact fork/exec/wait state machine the supervisor event loop is built on. Applied in Phase 1 and Phase 9.
  • Andriesse, D. — Practical Binary Analysis (No Starch Press, 2018). Ch. 2 (The ELF Format), Ch. 5 (Basic Binary Analysis in Linux), Ch. 9 (Binary Instrumentation). Extract: the ELF section-table walk and the ptrace-based code-patching technique the breakpoint installer reuses. Applied in Phase 2 and Phase 5.
  • Love, R. — Linux Kernel Development, 3rd ed. (Addison-Wesley, 2010). Ch. 3 (Process Management), Ch. 7 (Interrupts and Interrupt Handlers). Extract: how the kernel delivers a trap to a tracer before the tracee ever sees it. Applied in Phase 1.
  • Kerrisk, M. — The Linux Programming Interface (No Starch Press, 2010). Ch. 20-22 (Signals: Fundamental Concepts; Signal Handlers; Advanced Features). Extract: signal-delivery semantics (SA_RESTART, masks, real-time signals) classify_stop depends on. Applied in Phase 1 and Phase 9.
  • Stallman, R., Pesch, R., Shebs, S., et al. — Debugging with GDB (Free Software Foundation, current edition). The "Set Breaks", "Continuing and Stepping" chapters, Appendix E (GDB Remote Serial Protocol). Extract: the breakpoint/watchpoint command semantics this project's CLI mirrors, and the exact RSP packet grammar. Applied in Phase 5, Phase 6, Phase 10.

Papers

  • O'Callahan, R. et al. — "Engineering Record and Replay for Deployability" (USENIX ATC, 2017). Contribution: ptrace + seccomp-bpf syscall interception for deterministic record/replay. Applied in: Deferred Features Register (reverse debugging), Alternative Architectures.
  • O'Callahan, R. et al. — "Lightweight User-Space Record and Replay" (arXiv:1610.02144, 2016). Contribution: the earlier rr design — chaos-mode scheduling, ptrace-based syscall recording. Applied in: Deferred Features Register.
  • Garfinkel, T. — "Traps and Pitfalls: Practical Problems in System Call Interposition Based Security Tools" (NDSS, 2003). Contribution: documents the TOCTOU races inherent to ptrace/syscall-interposition tools. Applied in: Phase 1 (N.6 Pitfalls), Threat Model.
  • Provos, N. — "Improving Host Security with System Call Policies" (USENIX Security, 2003). Contribution: systrace, a ptrace-based syscall-policy enforcement architecture. Applied in: Threat Model, Alternative Architectures.
  • Luk, C.-K. et al. — "Pin: Building Customized Program Analysis Tools with Dynamic Instrumentation" (PLDI, 2005). Contribution: JIT-based dynamic binary instrumentation as an alternative to trap-based breakpoints. Applied in: Alternative Architectures, Comparative Architecture Table.
  • Nethercote, N. & Seward, J. — "Valgrind: A Framework for Heavyweight Dynamic Binary Instrumentation" (PLDI, 2007). Contribution: shadow-value/synthetic-CPU instrumentation architecture. Applied in: Alternative Architectures, Comparative Architecture Table.
  • Zeller, A. — "Yesterday, my program worked. Today, it does not. Why?" (ESEC/FSE, 1999). Contribution: delta debugging / systematic input minimization for isolating a regression's root cause. Applied in: Testing & Verification Strategy.
  • Linton, M.A. — "The Evolution of Dbx" (USENIX Summer Conference Proceedings, 1990). Contribution: the original architecture separating a source-level debugger's symbol-table reader from its process-control layer — the split this project's Architectural Overview mirrors. Applied in: Architectural Overview, Phase 3.
  • Bruening, D. — "Efficient, Transparent, and Comprehensive Runtime Code Manipulation" (PhD dissertation, MIT, 2004). Contribution: DynamoRIO's code-cache-based binary instrumentation, contrasted with ptrace's syscall-boundary granularity. Applied in: Alternative Architectures.

Reference Implementations

  • GDB source tree — gdb/breakpoint.c, gdb/dwarf2/, gdb/frame.c, gdb/infrun.c, gdb/remote.c. Lesson: the canonical breakpoint/frame/stepping state machines. Pitfall not to copy: infrun.c's implicit global-state coupling — keep Session's state explicit. Applied in Phase 5, Phase 8, Phase 10.
  • LLDB source tree — lldb/source/Plugins/Process/Linux/, lldb/source/Symbol/, lldb/source/Plugins/SymbolFile/DWARF/. Lesson: a cleaner plugin separation of process-control vs. symbol layer than GDB's. Pitfall: its SB-API surface is far larger than a Phase-0 target needs — do not mirror its breadth early. Applied in Phase 1, Phase 3.
  • Mozilla rr source tree — src/RecordSession.cc, src/ReplaySession.cc. Lesson: ptrace + seccomp-bpf syscall interception for deterministic replay. Pitfall: its scheduler assumes a single logical CPU during replay; this does not generalize to live debugging. Applied in Deferred Features Register, Alternative Architectures.
  • gimli-rs project — gimli, addr2line, object crate sources. Lesson: streaming, zero-copy DWARF parsing over an mmap'd ELF. Pitfall: fighting gimli's EndianSlice lifetime discipline instead of modeling DwarfCursor around it. Applied in Phase 3, Phase 4.
  • nix-rust project — nix::sys::ptrace, nix::sys::wait. Lesson: the safe-Rust wrapper shape for raw ptrace requests. Pitfall: some pinned versions lag PTRACE_GETREGSET/ NT_ARM_HW_BREAK ergonomics — verify or fall back to raw libc::syscall. Applied in Phase 1, Phase 6.
  • headcrab project (GitHub) — a from-scratch Rust ptrace debugger prototype. Lesson: the minimal attach/read-registers/read-memory surface. Pitfall: its breakpoint table was an unindexed Vec — do not copy that. Applied in Phase 5, Performance Engineering.
  • TartanLlama (Simon Brand) — minidbg, companion code to the "Writing a Linux Debugger" blog series. Lesson: the single-step-over-breakpoint dance taught end to end in under 2,000 lines. Pitfall: no multi-threaded or follow-fork support — exactly Phase 9's gap. Applied in Phase 5, Phase 9.

Glossary · 49 terms · site-wide glossary

ptrace
the Linux syscall (ptrace(2)) giving one process control over another's execution and memory.
PTRACE_SEIZE
attaches without injecting a SIGSTOP, this project's exclusive attach mode.
PTRACE_ATTACH
legacy attach mode that injects SIGSTOP; not used here.
PTRACE_PEEKDATA / POKEDATA
word-at-a-time inferior memory read/write via ptrace.
PTRACE_GETREGSET
reads a named register set (NT_PRSTATUS, NT_PRFPREG, …).
PTRACE_CONT / PTRACE_SINGLESTEP
resume the inferior, optionally one instruction.
waitpid
the syscall a supervisor blocks on to learn of an inferior's state changes.
WIFSTOPPED / WSTOPSIG
macros classifying a waitpid status as a stop and its signal.
SIGTRAP
the signal delivered on a breakpoint or single-step trap.
0xCC / INT3
the x86-64 software-breakpoint trap opcode.
brk #0
the AArch64 software-breakpoint trap instruction.
ASLR
Address Space Layout Randomization; source of the aslr_slide computation.
CFA (Canonical Frame Address)
the reference address a CFI rule table is keyed against per frame.
CFI (Call Frame Information)
the .eh_frame/.debug_frame encoding of how to compute the CFA and recover saved registers.
CIE / FDE
Common Information Entry / Frame Description Entry, the two record types composing CFI.
DWARF
the debugging information format this project parses (v4/v5).
DIE (Debugging Information Entry)
one node in a DWARF compilation unit's tree.
Compilation Unit (CU)
one source file's worth of DWARF DIEs.
.debug_info / .debug_abbrev
the DIE tree and its abbreviation codes.
.debug_line
the line-number program (address ↔ source line/column).
.debug_loc / .debug_loclists
DWARF v4/v5 location-expression lists.
.debug_aranges
the address-range-to-CU index (Mental Model MM3).
.eh_frame
the runtime-loaded CFI section (vs. the often-stripped .debug_frame).
DR0-DR7
x86-64 debug registers controlling hardware breakpoints/watchpoints.
BRP / WRP
AArch64 breakpoint/watchpoint register pairs.
Watchpoint
a hardware trap on a memory access (read/write/both), not a code patch.
Software breakpoint
a code patch (0xCC/brk #0) trapping execution at an address.
Hardware breakpoint
a debug-register-driven trap, not a code patch.
Inline frame
a synthesized stack frame for an inlined call, not present on the real stack.
Tail call
a call whose frame is replaced by the callee's, invisible to naive unwinding.
Frame pointer
the register (RBP/X29) conventionally chaining stack frames.
Stack unwinding
reconstructing the call chain from register/memory state.
Symbolication
mapping an address to a function/file/line/type name.
Demangling
reversing a compiler's name-mangling scheme to a readable symbol.
Itanium mangling
the C++ ABI's symbol-name encoding.
Rust v0 mangling
RFC 2603's symbol-name encoding, successor to Rust's legacy scheme.
GDB-RSP
the GDB Remote Serial Protocol.
DAP
the Debug Adapter Protocol.
Rendezvous (_r_debug)
the dynamic linker's structure notifying a debugger of load/unload events.
build-id
a .note.gnu.build-id hash uniquely identifying a binary across paths.
debuglink
a .gnu_debuglink section pointing at separated debug info.
follow-fork
the policy for which process(es) remain traced after fork.
follow-exec
the policy for whether tracing continues after exec.
Scheduler-locking
the policy for which threads run during a step.
PhaseDeferred
this document's marker for a feature intentionally out of Phase 0-12 scope, registered in the Deferred Features Register.
Conformance fixture
a named input/expected-output pair gating a phase's Acceptance Criteria.
TOCTOU
Time-Of-Check-To-Time-Of-Use; the ptrace race class documented in Garfinkel 2003 (Threat T10).
Core file
a post-mortem memory snapshot of a crashed process (deferred feature).
Tracepoint
a breakpoint that captures state without stopping execution (deferred feature).
