Decisions (§9) · 22 ADRs

ADR-01

Implementation language

Chosen

Rust 1.78+, workspace-wide

Rejected

C++, Java/JVM, Go

When the rejected choice is right

Java wins when team Rust expertise is near-zero and a 10-year JVM shuffle codebase already exists (sunk cost dominates)

Why: borrow checker removes UAF at the buffer-lifetime boundary speculative cancellation stresses (§1)

ADR-02

std-bound, no no_std

Chosen

std everywhere

Rejected

no_std + custom allocator

When the rejected choice is right

no_std wins only if this ran on a microcontroller-class shuffle appliance — it doesn't

Why: network/disk-heavy; no embedded target

ADR-03

Async runtime

Chosen

tokio multi-thread

Rejected

async-std, smol, raw threads

When the rejected choice is right

raw threads win for a single-digit-fan-out embedded tool with no need for async I/O

Why: proven at 10⁴+ fan-out (§1)

ADR-04

Default shuffle backend

Chosen

sort-based local (mrs-shuffle-local)

Rejected

push-first, S3-first

When the rejected choice is right

push/S3-first wins when Phase 0 is skipped and the target is directly a 100+-node cloud cluster

Why: single-host dev + small-cluster correctness baseline (P2)

ADR-05

Medium-scale shuffle backend

Chosen

push-based Magnet-style (mrs-shuffle-push)

Rejected

stay pull-only

When the rejected choice is right

pull-only wins at < ~50 nodes where M×R² fetch cost is still cheap and a 3rd service tier is not worth operating

Why: Shen VLDB 2020: 100× fewer fetch RPCs (M6)

ADR-06

Cloud-native shuffle backend

Chosen

disaggregated S3 (mrs-shuffle-s3)

Rejected

local-disk-only

When the rejected choice is right

local-disk wins on a fixed, non-preemptible, on-prem cluster where object-store RTT (§4) is pure overhead

Why: spot/ephemeral compute breaks local disk (P9)

ADR-07

Larger-than-RAM sort

Chosen

in-memory + external merge, tiered fan-in

Rejected

single giant in-memory sort

When the rejected choice is right

single in-memory sort wins when every partition provably fits in the per-task memory budget

Why: Graefe 2006 reference design; caps reduce-side FD use (§15.3)

ADR-08

Sort-key encoding

Chosen

length-prefixed big-endian bytes

Rejected

native typed comparators per type

When the rejected choice is right

typed comparators win when the workload is 100% one fixed numeric type and byte-compare's constant-factor overhead is measured to matter

Why: Hadoop WritableComparable model; byte-comparable is comparator-agnostic (§8.2)

ADR-09

Default partitioner

Chosen

HashPartitioner{num_partitions}

Rejected

RangePartitioner only, no default

When the rejected choice is right

range partitioning wins for order-sensitive downstream consumers (e.g. TeraSort, §23) — used there explicitly

Why: 99% case; range available (ADR-09b) via trait (§11.4)

ADR-10

Combiner contract

Chosen

must be associative + commutative (I8)

Rejected

allow arbitrary reduce-like combiners

When the rejected choice is right

arbitrary combiners are acceptable only for approximate, order-tolerant aggregates where exact reproducibility is not required — not this system's target regime

Why: non-associative combine gives fan-in-dependent results (P6)

ADR-11

Speculative scheduler

Chosen

LATE (Zaharia OSDI 2008)

Rejected

no speculation, naive re-launch-on-timeout

When the rejected choice is right

naive re-launch wins on a homogeneous, dedicated cluster with near-zero straggler probability

Why: the only widely-deployed, measured design (§18)

ADR-12

Max task attempts

Chosen

4 (1 + 3 retries)

Rejected

1 (no retry), unlimited

When the rejected choice is right

unlimited retry is defensible only in an offline batch tool with a human supervising every failure — not an unattended production regime

Why: Hadoop-empirical: transient failures resolve by attempt 4

ADR-13

Locality preference source

Chosen

LocalityHint from input-split metadata

Rejected

ignore locality entirely

When the rejected choice is right

ignoring locality wins when all inputs are on uniformly-fast shared network storage (S3, no locality signal exists — §16.3)

Why: delay scheduling matches near-best locality (Zaharia EuroSys 2010)

ADR-14

Resource model

Chosen

(cpu_milli, memory_mb) 2D bin-pack

Rejected

richer model (+GPU, NUMA, IOPS)

When the rejected choice is right

richer model wins once GPU kernels (deferred, §38) or IOPS-sensitive S3 backends dominate cost

Why: 2D is tractable; richer model is a stretch (§38)

ADR-15

Fetch backpressure

Chosen

credit-based flow control

Rejected

unbounded send, TCP backpressure only

When the rejected choice is right

TCP-only backpressure wins for a low-fan-in, single-consumer pipe where app-level credit accounting is pure overhead

Why: closes OOM-by-fast-sender (P10, I11)

ADR-16

Default shuffle compression

Chosen

LZ4

Rejected

Zstd, none

When the rejected choice is right

Zstd wins on storage-constrained backends trading ~3× CPU for ~30% size (used on S3 backend, §22.2)

Why: highest decompression throughput/cycle (M15)

ADR-17

Driver process topology

Chosen

single process (HA deferred)

Rejected

Raft-replicated driver from day one

When the rejected choice is right

Raft-replicated driver wins the moment job re-submission cost exceeds the coordination overhead — flagged in §38

Why: HA is Blueprint 110+ scope; re-submit cost is bounded (§4 RTO)

ADR-18

Control-plane protocol

Chosen

gRPC (HTTP/2, RFC 7540)

Rejected

REST/JSON, raw TCP framing

When the rejected choice is right

raw TCP framing wins on the shuffle fetch hot path itself — which is why fetch uses a custom protocol, not gRPC

Why: fits driver-executor request/response; not on the shuffle hot path

ADR-19

Shuffle-service auth

Chosen

mTLS + per-job HMAC token

Rejected

no auth (trust the network)

When the rejected choice is right

no-auth wins only inside a single-tenant, physically-isolated cluster with no compliance requirement

Why: multi-tenant by default (P11)

ADR-20

Vectorised-kernel integration

Chosen

Blueprint #104 RecordBatch for secondary-sort example

Rejected

reimplement columnar sort locally

When the rejected choice is right

reimplementing locally wins if Blueprint #104 is unavailable/unbuilt in the target deployment

Why: avoids duplicating a columnar sort kernel; cross-blueprint consistency (§2)

ADR-21

Conformance gate set

Chosen

6 independent gates (TeraSort, WordCount, equivalence, fault-injection, speculation, chaos)

Rejected

single "integration test" gate

When the rejected choice is right

a single aggregate gate wins only for a throwaway prototype with no production path

Why: a regression in one dimension must not hide behind an aggregate pass (P12)

ADR-22

Secret handling

Chosen

Zeroize/Zeroizing<T> for shuffle auth tokens

Rejected

plain String/Vec<u8>

When the rejected choice is right

plain types are acceptable only in a process guaranteed not to persist heap dumps or run under a production profiler — an assumption this system does not make

Why: heap dump must not leak tokens (P11)

Roads not taken (§37)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

AA1 — Fully in-memory shuffle (no spill), original Spark 2010 model

┌────────┐  cache in RAM   ┌──────────┐   RAM-to-RAM    ┌────────┐
│ Mapper │───────────────▶│ RAM cache │────fetch───────▶│ Reducer│
└────────┘  (no disk path) └──────────┘                  └────────┘

Regime where it wins: interactive/iterative workloads (repeated passes over the same working set, e.g. ML training loops) where the working set provably fits cluster RAM and recomputation-on-eviction (RDD lineage) is cheap relative to disk I/O. Real system: early Spark (HotCloud 2010) before ExternalSorter matured. Why this blueprint rejected it: the target workload (TeraSort-scale batch) routinely exceeds cluster RAM by design (§1, §4); an all-in-memory shuffle would OOM or silently degrade to disk anyway, so building the external-merge path (§15) from the start is the only workload-honest choice (P1).

AA2 — Pipelined (non-blocking) shuffle, Flink-batch model

Mapper ──stream──▶ [network buffer, bounded] ──stream──▶ Reducer
        (reducer starts consuming before mapper finishes — no stage barrier)

Regime where it wins: workloads needing low end-to-end latency across many small stages, or a single runtime shared with true streaming (Flink's actual reason for this choice, Carbone 2015). Real system: Apache Flink (batch mode via pipelined ResultPartition). Why this blueprint rejected it: pipelining forfeits the clean stage-boundary fault-tolerance story this blueprint depends on (§17) — a failure mid-pipeline has a much larger, harder-to-bound recovery scope than "re-run the map task, the blocking boundary already isolated its output" (I6). The blocking boundary is a deliberate simplicity-for- recoverability trade (§1 non-goals exclude streaming precisely to keep this trade clean).

AA3 — Serverless (Lambda-style) executors, Locus/Pywren model

Driver (Step-Functions-style state machine)
   │  invoke                                invoke
   ▼                                          ▼
Lambda map task ──write──▶ S3 ◀──read────  Lambda reduce task
(no persistent executor process; shuffle IS the only durable state)

Regime where it wins: infrequently-run or bursty jobs where executor-pool warm-up cost dominates total job cost, and per-invocation billing beats holding a warm cluster. Real system: the Pywren/Locus line of research (Pu, Venkataraman, Stoica NSDI 2019, applied per §5). Why this blueprint rejected it: Lambda-class function limits (memory, execution duration, no local disk for spill) are structurally incompatible with the external-merge- sort design this blueprint's Phase 3 requires at TeraSort scale (§15); the S3 backend (§20) already captures the disaggregation benefit Locus is after without inheriting Lambda's per-invocation resource ceiling — PhaseDeferred("§38") covers a future serverless executor pool as an addition, not a replacement.
