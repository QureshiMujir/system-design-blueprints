3. Architectural Overview

┌───────────────────────────────────────────────────────────────────────┐
│ Client / mrs-cli  (submit job DAG; poll status)                       │
└───────────────────────────────┬───────────────────────────────────────┘
                                 │ gRPC (mrs-net control channel, ADR-18)
┌────────────────────────────────▼──────────────────────────────────────┐
│ mrs-driver  (single process; control plane ONLY — I1)                 │
│  Dag materialiser │ Scheduler (locality+resource+LATE) │ Lineage      │
│  tracker │ Straggler monitor │ Shuffle-metadata table (M×R index)     │
└──────────┬──────────────────────────────────────────────┬─────────────┘
           │ task assignment                              │ block metadata
┌──────────▼───────────────────┐             ┌─────────────▼────────────┐
│ mrs-executor (map, 1..N)      │             │ Shuffler (trait, §11.5)  │
│  read split → user map()      │  write via  │  mrs-shuffle-local       │
│  → Partitioner → local sort   │─────────────▶  mrs-shuffle-push        │
│  → optional Combiner → spill  │             │  mrs-shuffle-s3          │
└────────────────────────────────┘             └─────────────┬────────────┘
                                                              │ read via Shuffler
┌─────────────────────────────────────────────────────────────▼──────────┐
│ mrs-executor (reduce, 1..M)                                            │
│  fetch all map outputs for partition p → k-way external merge (§14.6)  │
│  → optional secondary sort → user reduce() → write next-stage/sink     │
└──────────────────────────────────────────────────────────────────────┘

One tight paragraph per box:

Client / mrs-cli — submits a Job (§11.6), polls JobStatus; stateless; no shuffle bytes ever pass through it.

mrs-driver — control plane only (I1): task assignment, shuffle-block metadata, lineage, completion acks; never touches a map/reduce byte. Single process (ADR-17); HA is PhaseDeferred("§38").

mrs-executor (map) — hosts both the map-runner and reduce-runner code paths (Phase 0 unifies them in one binary, §12); a map task's output always passes through the Partitioner (§11.4) then an optional Combiner (§11.4) before the Shuffler write.

Shuffler backends — mrs-shuffle-local (Phase 2, §14), mrs-shuffle-push (Phase 7, §19), mrs-shuffle-s3 (Phase 8, §20) all implement the one Shuffler trait (§11.5); switching is a config change (P2).

mrs-executor (reduce) — fetches via Shuffler::read_partition, k-way merges (§14.6), runs the user reduce function, writes to the next stage's shuffle or the final sink.

Five load-bearing properties, referenced throughout: (1) control plane carries no data (I1) — this is why the driver scales to 10⁴ tasks; (2) the backend is plug-replaceable (P2, ADR-04/05/06) via one trait; (3) speculation is a passive monitor emitting launch requests, not a task-level property (P3, Phase 6); (4) the combiner is opportunistic, negotiated at submit time, invisible to the shuffle backend (P6); (5) fault tolerance is by re-execution against the lineage tracker, never by checkpoint (P4, Phase 5).

8. Domain Model / Protocol / Data Model

8.1 Job/Stage/Task state machine

Job:     Submitted → Running → { Completed | Failed }
Stage:   Pending → Activated → Running → Complete
Task:    Materialized → Assigned → Running → { Completed | Failed → retry≤4 (I14) }
Attempt: Launched → { Won (canonical, I2) | Cancelled (speculative loser) | Failed }

A stage transitions Pending → Activated only when every upstream stage is Complete (I6). A task transitions Failed → retry up to max_task_attempts (ADR-12); beyond that the enclosing stage (and job) is Failed (I14).

8.2 Wire records

Spill-block layout (on-disk, §14.2/14.3, one block per partition within a spill file):

[u64 partition_id][u64 record_count][u64 byte_len][LZ4-compressed (key,value)* payload]

(key, value) pair encoding within a decompressed payload: [u32 key_len][key bytes] [u32 val_len][val bytes], key bytes are length-prefixed big-endian-comparable (ADR-08).

Push-protocol messages (§19.2, mrs-shuffle-push::push_protocol):

PushRequest  { job, stage, map_attempt, partition, block: bytes, checksum: blake3 }
PushAck      { map_attempt, partition, merged_offset: u64 }

S3 object key layout (§20.2):

s3://{bucket}/{job_id}/{stage_id}/{partition}/{map_attempt}.block
s3://{bucket}/{job_id}/{stage_id}/manifest.json

8.3 Sequence — normal reduce fetch (local backend)

Reducer                Shuffler(local)              Mapper(s)
   │  ShuffleReadRequest(p, [m1..mk])                    │
   ├──────────────────▶│                                 │
   │                    │ mmap data file per mi          │
   │                    │◀───────────────────────────────┤ (already written, §14)
   │◀── stream of blocks (one per mi, checksum-verified) ┤
   │  k-way merge (§15.2), reduce fn, write next stage    │

8.4 Malformed-input examples (conformance fuzz.*, §29)

  • Truncated spill block (byte_len exceeds remaining file bytes) → ShuffleError::Corrupt, source map re-run (I7 recovery path).
  • PushRequest with checksum mismatch → service rejects with ShuffleError::ChecksumFail, mapper retries with backoff (§19.7 pitfall).
  • S3 manifest referencing a key with no corresponding object (crashed multipart upload, §20.8) → reducer treats as not-yet-available, waits, driver retries manifest write.

8.5 Failure-path example

Executor holding 3 live map outputs crashes mid-stage. Driver's heartbeat monitor fires after heartbeat_timeout (I3) → OutputLineage::on_executor_lost (§17.3) returns the 3 TaskIds → driver re-materializes those 3 map tasks (fresh attempt) → any reducer with an in-flight fetch against the lost host reports ShuffleFetchFailed{source_map} → driver re-runs exactly that upstream map (not the whole stage) → reducer resumes from its fetch-progress journal (§17.4) once the new attempt's output is ready.

Design principles (§6)

  • P1 — Shuffle dominates. Rule: every performance number in this blueprint is dominated by shuffle bytes/second; map/reduce user code is out of optimization scope. Tradeoff: we under-invest in compute-kernel speed (no SIMD map-function JIT). Operational implication: profiling always starts at the Shuffler boundary (§31). Violating it: teams that "optimize the reducer" without measuring shuffle first waste the sprint (Zaharia 2012).
  • P2 — Pluggable shuffle backends are mandatory. Rule: the Shuffler trait (§11.5) is the sole contract between executor and storage. Tradeoff: the trait must be the lowest common denominator across local/push/S3, forfeiting backend-specific fast paths inside the executor. Operational implication: backend choice is a deploy-time config, not a recompile. Violating it: hard-coding the local backend (Spark pre-2020) forces a rewrite to add push/S3 later.
  • P3 — Speculative execution answers stragglers, not hardware tuning. Rule: launch a speculative copy of any task exceeding median × 1.5 (ADR-11). Tradeoff: wasted compute on the losing attempt. Operational implication: max_speculative_per_stage caps blast radius. Violating it: "standardize the hardware" (pre-LATE) never converges — Zaharia OSDI 2008 measured this directly.
  • P4 — Task re-execution beats checkpointing for batch. Rule: never write task-progress checkpoints; recompute from the prior stage's shuffle output. Tradeoff: a lost task re-does its whole unit of work. Operational implication: no checkpoint storage tier to operate. Violating it: checkpoint overhead exceeds re-execution cost at every measured input size (RDD paper, NSDI 2012).
  • P5 — Data locality is a soft preference. Rule: delay-schedule up to locality_delay_ms (3,000 ms default, ADR-13) before falling back rack-local → any. Tradeoff: a task can wait 3 s doing nothing. Operational implication: cluster utilization stays high under skewed data placement. Violating it: strict-locality scheduling underutilizes the cluster (Quincy, SOSP 2009).
  • P6 — The combiner is opportunistic, not mandatory. Rule: run only if user-supplied and the per-task memory budget allows; must be associative + commutative (I8). Tradeoff: an unused combiner opportunity leaves shuffle bytes on the table. Operational implication: shuffle-volume regressions are triaged first at "did the combiner run." Violating it: a non-associative combiner (naive average) silently corrupts output depending on combine fan-in (§21.5 pitfall).
  • P7 — Secondary sort is the optimization most miss. Rule: (primary_key, secondary_key) sort at shuffle time lets the reducer stream values in order without buffering. Tradeoff: extra sort-key bytes per record. Operational implication: a general (non-combinable) reducer over an unbounded value list needs this to avoid an OOM. Violating it: reducers buffer all values for a key in memory and OOM on skewed keys.
  • P8 — Resource-aware scheduling is half the win. Rule: match ResourceRequest to free ResourceUnits (cpu_milli, memory_mb) before assignment. Tradeoff: two-dimensional bin-packing is NP-hard in general; we accept a greedy heuristic. Operational implication: OOM-kills drop sharply versus locality-only scheduling. Violating it: scheduling by locality alone OOMs hosts under heavy tasks (Mesos, NSDI 2011).
  • P9 — Disaggregated shuffle on object storage is the cloud-native answer. Rule: mrs-shuffle-s3 is a first-class backend, not a bolt-on. Tradeoff: object-store RTT caps per-fetch latency (§4). Operational implication: spot/ephemeral executor pools become viable. Violating it: local-disk-only shuffle loses data on every preemption (the Cosco/Zeus/Celeborn convergent finding).
  • P10 — Backpressure must be explicit. Rule: credit-based flow control on the fetch protocol (§11.5, mrs-net::credit_flow); sender never exceeds the advertised window. Tradeoff: a slow receiver throttles a fast sender's effective throughput. Operational implication: OOM-by-fast-sender becomes structurally impossible. Violating it: an unthrottled push-shuffle service OOMs under a burst (Flink batch backpressure model, Carbone 2015).
  • P11 — The shuffle service IS a data plane — harden it as one. Rule: auth (mTLS + per-job token, ADR-19), checksums (BLAKE3, I7), quota (soft/hard bytes), observability (per-partition fetch-latency metrics) are line-zero, not stretch goals. Tradeoff: extra latency per request for auth verification. Operational implication: a rogue tenant cannot read another tenant's shuffle or starve the store. Violating it: an unauthenticated shuffle service is a lateral-movement vector (T7).
  • P12 — Conformance is the contract. Rule: the conformance suite (§29) gates every phase's exit; a regression in TeraSort, WordCount, backend-equivalence, fault-injection, speculation, or the chaos soak is a merge block. Tradeoff: CI wall-clock grows with every added fixture. Operational implication: no "it works on my machine" promotions. Violating it: an ungated regression reaches the 30-day soak and burns a month (§24.3).
  • P13 — Determinism is a documented user contract, not an enforced one. Rule: Task::run (§11.3) requires deterministic output for a given input+config; the library cannot statically verify user closures. Tradeoff: a non-deterministic map function silently breaks re-execution and speculative-attempt equivalence. Operational implication: the conformance suite includes a documented non-determinism canary (§17.5) rather than a runtime check. Violating it: duplicate/lost output under retry or speculation (I2, T-nondeterminism).
  • P14 — The manifest (or index) is the source of truth, never a storage listing. Rule: every backend has an authoritative record of which blocks exist — the local backend's per-mapper index (§14.2), the push service's partition offset table (§19.3), the S3 backend's manifest (§20.5) — and readers never infer existence by listing storage. Tradeoff: the manifest itself must be durable and consistent. Operational implication: eliminates the "list-and-infer" bug class (§20.8). Violating it: half of real shuffle-on-object-store incidents trace to exactly this anti-pattern.
