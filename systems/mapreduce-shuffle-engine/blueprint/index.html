106 — MapReduce Shuffle Engine

Project Number: 106

Project Name: MapReduce Shuffle Engine

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Goal. mrs (MapReduce Shuffle Engine) is a from-scratch Rust batch execution engine implementing the four canonical MapReduce stages (map, sort, shuffle, reduce) over a DAG-of-stages job model, with three interchangeable shuffle backends — sort-based local disk, Magnet-style push service, Cosco-style disaggregated object storage — behind one Shuffler trait (§11.5), LATE speculative execution (§18), re-execution fault tolerance via an in-memory lineage tracker (§17), and a locality- and resource-aware single-job scheduler (§16). It is the shuffle data plane plus the minimum control plane needed to drive it — not a user-facing SQL/dataframe compute layer.

Phase-0 deliverable (numbered modules, §10 names these crates):

  1. mrs-core — job/stage/task/partitioner/combiner/shuffler/lineage types, no I/O.
  2. mrs-driver — coordinator binary: DAG materialiser, scheduler, lineage tracker, RPC.
  3. mrs-executor — map/reduce runtime binary: map runner, reduce runner, external sort.
  4. mrs-shuffle-local — sort-based on-disk shuffle backend (in-memory stub → Phase 2 disk).
  5. mrs-cli — job submission and inspection CLI.
  6. conformance/runner — WordCount smoke fixture and harness.

System boundaries.

  • Provides: DAG job execution, three shuffle backends, speculative execution, task fault tolerance, resource+locality scheduling, combiner/secondary-sort/custom-partitioner.
  • Delegates: input/output storage (local FS, HDFS-compatible, S3) via thin adapters, not owned; a fixed per-job executor pool — no multi-tenant cluster resource manager.
  • Does NOT provide: a SQL/dataframe planner (Blueprint #102), a streaming/micro-batch runtime (no watermarks, no checkpoint barriers — Blueprint 110+), a multi-job fair scheduler (no DRF, no Mesos two-level scheduling), driver HA (single process; deferred).

Non-goals. Raw Mapper/Reducer as the primary user API (present only for the WordCount/TeraSort smoke surface); a relational optimizer; GPU kernels; cross-DC replication.

Deployment model. One mrs-driver process; N mrs-executor processes (bare metal, VM, or container); the shuffle backend deployed as co-located library code (local), a standalone service tier (push), or an object-store client (S3).

Target users/operators. Data-platform engineers building or debugging a batch shuffle layer; on-call SREs triaging a stuck stage at 3 a.m.

What later phases unlock. Magnet-style push shuffle removes the M×R fetch storm (§19); disaggregated S3 shuffle removes the local-disk durability dependency (§20); TeraSort 1 TB conformance is the performance gate (§23); the 30-day chaos soak is the operational-readiness gate (§24).

Recommended language: Rust 1.78+ (edition 2021), std-bound. Rationale: the workspace is network- and disk-heavy (no no_std benefit); the borrow checker statically removes the use-after-free class of bug that has hit production C++ shuffle services at exactly the buffer-lifetime boundary speculative-attempt cancellation stresses; tokio's multi-thread runtime is proven at 10⁴+ concurrent shuffle fetches. Rejected — C++: manual memory management risk collides with buffer lifetimes under cancellation. Rejected — Java/JVM: GC pause collides with the heartbeat-timeout invariant (I3) and is a documented real failure class (FM3). Rejected — Go: shorter GC pauses than Java but still non-deterministic; weaker zero-copy story for sendfile/splice (P10, §22.3).

Prerequisites. Dean-Ghemawat 2004 (OSDI); Zaharia's RDD lineage model (NSDI 2012); hash- vs range-partitioned shuffle; the external merge-sort cost model; one production shuffle implementation read end to end (Spark ExternalSorter/ShuffleBlockResolver, Tez OrderedPartitionedKVOutput, or the Celeborn worker).

Estimated timeline. Phase 0: 1 week. Full 13-phase system: 6–9 months (per-phase weeks stated at each phase heading, §12–§24).

Deferred features (each PhaseDeferred("§38"), resolved in the Deferred Features Register, §38): HA driver via Raft; AQE-style skew-split and partition coalescing; GPU map/reduce kernels; serverless (Lambda-style) executors; Arrow-columnar shuffle records; Iceberg/Delta source/sink; streaming micro-batch mode; cross-DC geo-replicated shuffle; RDMA-attached-NVMe shuffle backend; predicate pushdown into the shuffle fetch path; a TLA+ model of the speculative-execution protocol; an ML-driven (Decima-style) scheduler.

2. Why Build This

  • Unique systems knowledge. The shuffle layer — not the map/reduce user API — is the architectural core every modern batch/analytics engine shares: Spark's ExternalSorter
    • block-fetch protocol, Tez's OrderedPartitionedKVOutput, Flink batch's blocking result partitions, and every MPP's exchange operator (Trino, Snowflake, BigQuery, Redshift) are the same lineage — Dean-Ghemawat 2004 → Zaharia 2010/2012 → Shen 2020 → Facebook Cosco 2019 — with one variable: where shuffle bytes sit between writer and reader (local disk, remote service, object store).
  • Why it matters architecturally/historically. Dean and Ghemawat's own CACM 2010 retrospective concedes the user API (single map, single reduce) was too narrow for real pipelines; every successor (Tez 2014, Spark 2010, Flink batch 2015) replaced it with a DAG of stages connected by shuffles. The DAG is an interpreter for a relational-algebra tree; the shuffle underneath is the part that did not get replaced.
  • The engineering muscles it builds. External merge sort at scale (Graefe 2006); credit-based backpressure (P10); re-execution-based fault tolerance vs. checkpointing (P4); locality-vs-utilization tradeoffs under delay scheduling (Zaharia 2010 EuroSys); tail-latency control via speculative execution (Zaharia 2008 OSDI); multi-tenant data-plane hardening (auth, quota, checksums) on a service that is not "just storage."
  • Concrete cross-links to sibling systems. Blueprint #104 (vectorised OLAP engine) supplies the columnar kernels this blueprint's secondary-sort example calls (ADR-20); Blueprint #102 (SQL planner, deferred here) would compile down to this engine's DAG the way Spark SQL's Catalyst compiles to RDD/shuffle stages; a future streaming blueprint (110+) would replace this engine's blocking-shuffle boundary with a pipelined one (§37).
  • Calibration value. Matei Zaharia has repeated in every Spark performance talk since 2012: "shuffle is the bottleneck in nearly every benchmark." A senior data-platform engineer who has built one shuffle engine can read any production shuffle incident (a stuck reducer, a metadata storm, a service OOM) and localize the fault in minutes instead of days.

What Mastery Looks Like (5–8 competencies, each tied to a named phase):

  • Can explain, from the type signatures alone, why Shuffler (§11.5) is the entire contract between compute and storage, and swap backends without touching the executor (Phase 2 / Phase 7 / Phase 8, §14/§19/§20).
  • Can derive the M×R metadata-fetch cost and explain why push-based merge-on-write cuts it to O(R) (Phase 7, §19; Capacity Model §35 row on fetch count).
  • Can distinguish "task" from "task attempt" and explain why conflating them is the root cause of double-counted speculative output (Phase 6, §18; Invariant I2).
  • Can explain why re-execution beats checkpointing for this workload class, with the cost argument from the RDD paper, not from memory (Phase 5, §17; P4).
  • Can size a shuffle deployment from first principles — throughput, RAM, FD budget — using only the System Constraints numbers (§4) and the Back-of-Envelope Capacity Model (§35).
  • Can name the real system that would win under each Alternative Architecture (§37) and say precisely why this blueprint did not choose it.
  • Can debug a production "one reducer stuck at 99%" incident by walking the decision tree: partitioner skew (P7) → shuffle-service latency (Phase 7 N.7) → speculative scheduler behavior (Phase 6) → non-associative combiner (P6) — in that order, per Hard Questions §36.

One tight paragraph per box:

Client / mrs-cli — submits a Job (§11.6), polls JobStatus; stateless; no shuffle bytes ever pass through it.

mrs-driver — control plane only (I1): task assignment, shuffle-block metadata, lineage, completion acks; never touches a map/reduce byte. Single process (ADR-17); HA is PhaseDeferred("§38").

mrs-executor (map) — hosts both the map-runner and reduce-runner code paths (Phase 0 unifies them in one binary, §12); a map task's output always passes through the Partitioner (§11.4) then an optional Combiner (§11.4) before the Shuffler write.

Shuffler backends — mrs-shuffle-local (Phase 2, §14), mrs-shuffle-push (Phase 7, §19), mrs-shuffle-s3 (Phase 8, §20) all implement the one Shuffler trait (§11.5); switching is a config change (P2).

mrs-executor (reduce) — fetches via Shuffler::read_partition, k-way merges (§14.6), runs the user reduce function, writes to the next stage's shuffle or the final sink.

Five load-bearing properties, referenced throughout: (1) control plane carries no data (I1) — this is why the driver scales to 10⁴ tasks; (2) the backend is plug-replaceable (P2, ADR-04/05/06) via one trait; (3) speculation is a passive monitor emitting launch requests, not a task-level property (P3, Phase 6); (4) the combiner is opportunistic, negotiated at submit time, invisible to the shuffle backend (P6); (5) fault tolerance is by re-execution against the lineage tracker, never by checkpoint (P4, Phase 5).

6. Design Principles

  1. P1 — Shuffle dominates. Rule: every performance number in this blueprint is dominated by shuffle bytes/second; map/reduce user code is out of optimization scope. Tradeoff: we under-invest in compute-kernel speed (no SIMD map-function JIT). Operational implication: profiling always starts at the Shuffler boundary (§31). Violating it: teams that "optimize the reducer" without measuring shuffle first waste the sprint (Zaharia 2012).
  2. P2 — Pluggable shuffle backends are mandatory. Rule: the Shuffler trait (§11.5) is the sole contract between executor and storage. Tradeoff: the trait must be the lowest common denominator across local/push/S3, forfeiting backend-specific fast paths inside the executor. Operational implication: backend choice is a deploy-time config, not a recompile. Violating it: hard-coding the local backend (Spark pre-2020) forces a rewrite to add push/S3 later.
  3. P3 — Speculative execution answers stragglers, not hardware tuning. Rule: launch a speculative copy of any task exceeding median × 1.5 (ADR-11). Tradeoff: wasted compute on the losing attempt. Operational implication: max_speculative_per_stage caps blast radius. Violating it: "standardize the hardware" (pre-LATE) never converges — Zaharia OSDI 2008 measured this directly.
  4. P4 — Task re-execution beats checkpointing for batch. Rule: never write task-progress checkpoints; recompute from the prior stage's shuffle output. Tradeoff: a lost task re-does its whole unit of work. Operational implication: no checkpoint storage tier to operate. Violating it: checkpoint overhead exceeds re-execution cost at every measured input size (RDD paper, NSDI 2012).
  5. P5 — Data locality is a soft preference. Rule: delay-schedule up to locality_delay_ms (3,000 ms default, ADR-13) before falling back rack-local → any. Tradeoff: a task can wait 3 s doing nothing. Operational implication: cluster utilization stays high under skewed data placement. Violating it: strict-locality scheduling underutilizes the cluster (Quincy, SOSP 2009).
  6. P6 — The combiner is opportunistic, not mandatory. Rule: run only if user-supplied and the per-task memory budget allows; must be associative + commutative (I8). Tradeoff: an unused combiner opportunity leaves shuffle bytes on the table. Operational implication: shuffle-volume regressions are triaged first at "did the combiner run." Violating it: a non-associative combiner (naive average) silently corrupts output depending on combine fan-in (§21.5 pitfall).
  7. P7 — Secondary sort is the optimization most miss. Rule: (primary_key, secondary_key) sort at shuffle time lets the reducer stream values in order without buffering. Tradeoff: extra sort-key bytes per record. Operational implication: a general (non-combinable) reducer over an unbounded value list needs this to avoid an OOM. Violating it: reducers buffer all values for a key in memory and OOM on skewed keys.
  8. P8 — Resource-aware scheduling is half the win. Rule: match ResourceRequest to free ResourceUnits (cpu_milli, memory_mb) before assignment. Tradeoff: two-dimensional bin-packing is NP-hard in general; we accept a greedy heuristic. Operational implication: OOM-kills drop sharply versus locality-only scheduling. Violating it: scheduling by locality alone OOMs hosts under heavy tasks (Mesos, NSDI 2011).
  9. P9 — Disaggregated shuffle on object storage is the cloud-native answer. Rule: mrs-shuffle-s3 is a first-class backend, not a bolt-on. Tradeoff: object-store RTT caps per-fetch latency (§4). Operational implication: spot/ephemeral executor pools become viable. Violating it: local-disk-only shuffle loses data on every preemption (the Cosco/Zeus/Celeborn convergent finding).
  10. P10 — Backpressure must be explicit. Rule: credit-based flow control on the fetch protocol (§11.5, mrs-net::credit_flow); sender never exceeds the advertised window. Tradeoff: a slow receiver throttles a fast sender's effective throughput. Operational implication: OOM-by-fast-sender becomes structurally impossible. Violating it: an unthrottled push-shuffle service OOMs under a burst (Flink batch backpressure model, Carbone 2015).
  11. P11 — The shuffle service IS a data plane — harden it as one. Rule: auth (mTLS + per-job token, ADR-19), checksums (BLAKE3, I7), quota (soft/hard bytes), observability (per-partition fetch-latency metrics) are line-zero, not stretch goals. Tradeoff: extra latency per request for auth verification. Operational implication: a rogue tenant cannot read another tenant's shuffle or starve the store. Violating it: an unauthenticated shuffle service is a lateral-movement vector (T7).
  12. P12 — Conformance is the contract. Rule: the conformance suite (§29) gates every phase's exit; a regression in TeraSort, WordCount, backend-equivalence, fault-injection, speculation, or the chaos soak is a merge block. Tradeoff: CI wall-clock grows with every added fixture. Operational implication: no "it works on my machine" promotions. Violating it: an ungated regression reaches the 30-day soak and burns a month (§24.3).
  13. P13 — Determinism is a documented user contract, not an enforced one. Rule: Task::run (§11.3) requires deterministic output for a given input+config; the library cannot statically verify user closures. Tradeoff: a non-deterministic map function silently breaks re-execution and speculative-attempt equivalence. Operational implication: the conformance suite includes a documented non-determinism canary (§17.5) rather than a runtime check. Violating it: duplicate/lost output under retry or speculation (I2, T-nondeterminism).
  14. P14 — The manifest (or index) is the source of truth, never a storage listing. Rule: every backend has an authoritative record of which blocks exist — the local backend's per-mapper index (§14.2), the push service's partition offset table (§19.3), the S3 backend's manifest (§20.5) — and readers never infer existence by listing storage. Tradeoff: the manifest itself must be durable and consistent. Operational implication: eliminates the "list-and-infer" bug class (§20.8). Violating it: half of real shuffle-on-object-store incidents trace to exactly this anti-pattern.

8. Domain Model / Protocol / Data Model

8.1 Job/Stage/Task state machine

Job:     Submitted → Running → { Completed | Failed }
Stage:   Pending → Activated → Running → Complete
Task:    Materialized → Assigned → Running → { Completed | Failed → retry≤4 (I14) }
Attempt: Launched → { Won (canonical, I2) | Cancelled (speculative loser) | Failed }

A stage transitions Pending → Activated only when every upstream stage is Complete (I6). A task transitions Failed → retry up to max_task_attempts (ADR-12); beyond that the enclosing stage (and job) is Failed (I14).

8.2 Wire records

Spill-block layout (on-disk, §14.2/14.3, one block per partition within a spill file):

[u64 partition_id][u64 record_count][u64 byte_len][LZ4-compressed (key,value)* payload]

(key, value) pair encoding within a decompressed payload: [u32 key_len][key bytes] [u32 val_len][val bytes], key bytes are length-prefixed big-endian-comparable (ADR-08).

Push-protocol messages (§19.2, mrs-shuffle-push::push_protocol):

PushRequest  { job, stage, map_attempt, partition, block: bytes, checksum: blake3 }
PushAck      { map_attempt, partition, merged_offset: u64 }

S3 object key layout (§20.2):

s3://{bucket}/{job_id}/{stage_id}/{partition}/{map_attempt}.block
s3://{bucket}/{job_id}/{stage_id}/manifest.json

8.3 Sequence — normal reduce fetch (local backend)

Reducer                Shuffler(local)              Mapper(s)
   │  ShuffleReadRequest(p, [m1..mk])                    │
   ├──────────────────▶│                                 │
   │                    │ mmap data file per mi          │
   │                    │◀───────────────────────────────┤ (already written, §14)
   │◀── stream of blocks (one per mi, checksum-verified) ┤
   │  k-way merge (§15.2), reduce fn, write next stage    │

8.4 Malformed-input examples (conformance fuzz.*, §29)

  • Truncated spill block (byte_len exceeds remaining file bytes) → ShuffleError::Corrupt, source map re-run (I7 recovery path).
  • PushRequest with checksum mismatch → service rejects with ShuffleError::ChecksumFail, mapper retries with backoff (§19.7 pitfall).
  • S3 manifest referencing a key with no corresponding object (crashed multipart upload, §20.8) → reducer treats as not-yet-available, waits, driver retries manifest write.

8.5 Failure-path example

Executor holding 3 live map outputs crashes mid-stage. Driver's heartbeat monitor fires after heartbeat_timeout (I3) → OutputLineage::on_executor_lost (§17.3) returns the 3 TaskIds → driver re-materializes those 3 map tasks (fresh attempt) → any reducer with an in-flight fetch against the lost host reports ShuffleFetchFailed{source_map} → driver re-runs exactly that upstream map (not the whole stage) → reducer resumes from its fetch-progress journal (§17.4) once the new attempt's output is ready.

11. Core Schema & Types

Signatures only (No-Code Rule, standard §4); every type below is referenced by ID from phases §12–§24. Ownership/mutation/concurrency/persistence/serialization noted inline.

11.1 Identifiers (mrs-core::ids)

struct JobId(u64)                                  Copy, Hash — job-scoped, driver-assigned
struct StageId { job: JobId, idx: u32 }             Copy, Hash — stable per Dag build
struct TaskId  { stage: StageId, partition: u32, attempt: u32 }   Copy, Hash — universal task-attempt address
struct HostId(u32); struct RackId(u32)              Copy, Hash — scheduler-local

(stage, partition, attempt) is the universal addressing triple (§8.1). attempt increments on retry (I14) and speculative launch (I2); "task" (academic sense) ≠ "task attempt" (operational sense) — conflating them is a top pitfall (I9).

11.2 Map output & shuffle addressing (mrs-core::shuffler)

struct MapOutput { task: TaskId, partition_sizes: Vec<u64>, partition_record_counts: Vec<u64>,
                    locations: Vec<HostId>, checksum: [u8;32] }     owned by driver post-ACK; immutable
struct ShuffleReadRequest { stage: StageId, partition: u32, map_attempts: Vec<TaskId> }
                                                                     constructed per-reduce-task; immutable

map_attempts enforces I2: the driver records exactly the winning TaskId per map task; the reducer fetches only those, never a speculative loser.

11.3 Task (mrs-core::task)

enum TaskKind { Map { input_split: InputSplit, num_output_partitions: u32 },
                Reduce { source_stage: StageId, partition: u32 } }
trait Task: Send + 'static {
  fn id(&self) -> TaskId
  fn kind(&self) -> &TaskKind
  fn locality_hint(&self) -> &LocalityHint
  fn resource_request(&self) -> &ResourceRequest
  fn run(self: Box<Self>, ctx: TaskContext) -> Result<TaskResult, TaskError>   // MUST be
}                                                                              // deterministic (P13)
struct TaskResult { task: TaskId, map_output: Option<MapOutput>, records_written: u64,
                     bytes_written: u64, wall_time: Duration }

Task::run determinism is documented, not statically enforced (P13); re-execution (§17) and speculation (§18) both depend on it holding.

11.4 Partitioner & Combiner (mrs-core::partitioner, ::combiner)

trait Partitioner: Send + Sync + 'static { fn num_partitions(&self) -> u32
                                            fn partition_for(&self, key: &[u8]) -> u32 }
struct HashPartitioner  { num_partitions: u32 }                       xxh3_64(key) % num_partitions
struct RangePartitioner  { num_partitions: u32, boundaries: Vec<Vec<u8>> }  ADR-09
struct PartitionAndSecondarySort<P: Partitioner> { partitioner: P,
    secondary_comparator: Arc<dyn Fn(&[u8],&[u8]) -> Ordering + Send + Sync> }   §21.2

trait Combiner: Send + Sync + 'static {
  fn combine(&self, key: &[u8], values: &mut Vec<Vec<u8>>)     // MUST be assoc.+commut. (I8)
}

Partitioner/Combiner instances are Arc-shared read-only across all task attempts of a stage; no interior mutability.

11.5 Shuffler (mrs-core::shuffler) — the backend contract (P2)

trait Shuffler: Send + Sync + 'static {
  fn write_map_output<'a>(&'a self, map: TaskId, data: BoxStream<'a,(u32,Vec<u8>)>)
      -> BoxFuture<'a, Result<MapOutput, ShuffleError>>
  fn read_partition<'a>(&'a self, request: ShuffleReadRequest)
      -> BoxStream<'a, Result<Vec<u8>, ShuffleError>>
  fn cleanup_stage<'a>(&'a self, stage: StageId) -> BoxFuture<'a, Result<(), ShuffleError>>
}

Three impls (§14/§19/§20) share this signature exactly; executor code is backend-agnostic. Persistence/durability semantics differ per impl but the ACK-after-fsync contract (§26 pitfall) is invariant across all three.

11.6 Job & Stage (mrs-core::job)

struct Dag<N> { nodes: Vec<N>, edges: Vec<Vec<usize>>, reverse_edges: Vec<Vec<usize>> }  // topo-ordered, I10
struct Stage { id: StageId, kind: StageKind, num_partitions: u32,
               partitioner: Arc<dyn Partitioner>, combiner: Option<Arc<dyn Combiner>>,
               dependencies: Vec<StageId> }
enum StageKind { Map { input_splits: Vec<InputSplit> }, Reduce { source_stage: StageId } }
struct Job { id: JobId, stages: Dag<Stage>, final_outputs: Vec<StageId> }

Dag<Stage> cycles rejected at submit time (I10, Error::CyclicJob). Mutation: built once at submit, read-only thereafter (matches Tez/Dryad DAG-of-vertices model, §2).

11.7 Scheduler surface (mrs-driver::scheduler)

trait Scheduler: Send + Sync {
  fn next_task(&mut self, free_host: HostId, free_resources: ResourceUnits,
               candidates: &[TaskId]) -> Option<TaskId>
  fn notify(&mut self, event: SchedulerEvent)
}

                       TaskFailed { task: TaskId, reason: FailureReason },
                       SpeculativeLaunch { task: TaskId, new_attempt: u32 } }
struct ResourceUnits { cpu_milli: u32, memory_mb: u32 }
struct ResourceRequest { cpu_milli: u32, memory_mb: u32 }
struct LocalityHint { hosts: Vec<HostId>, racks: Vec<RackId> }

One Scheduler instance per job, owned by mrs-driver::coordinator; LateScheduler (§18.2) runs beside it as a passive monitor emitting SpeculativeLaunch (P3).

struct OutputLineage { alive_map_outputs: HashMap<StageId, HashSet<TaskId>>,
                        host_to_outputs: HashMap<HostId, HashSet<TaskId>> }

  • mrs-core::job::Dag<N> (§11.6): nodes: Vec<N> in topological order, edges/ reverse_edges adjacency; cycle detection at construction rejects with Error::CyclicJob (I10).
  • mrs-driver::stage_orchestrator: stage_state: HashMap<StageId, StageState> where StageState ∈ {Pending, Running{remaining_tasks}, Complete}; a stage transitions Pending → Running only when every entry in dependencies (§11.6) is Complete (I6).
  • materialise_tasks(&Stage) -> Vec<TaskId>: a map stage with N input splits and P output partitions produces N map tasks (TaskId.partition = input-split index, I9); a reduce stage with P partitions produces P reduce tasks (TaskId.partition = output partition).
  • Wire mrs-driver::coordinator to call materialise_tasks on every stage activation and push results to mrs-driver::task_assigner (stubbed until Phase 4, §16).

13.3 Deliverable

A three-stage join Job (two map stages feeding one reduce stage) materializes the expected task graph and executes correctly against the Phase-0 in-memory shuffler.

13.4 Acceptance Criteria

Property test (proptest): for any acyclic stage graph up to 50 stages × 100 partitions/stage, materialization order matches the DAG's topological order exactly (I10); negative test: a hand-built cyclic graph is rejected with Error::CyclicJob in <1 ms.

13.5 Conformance Fixtures

Fixture Purpose Expected Output
dag_join_topology.rs 2-map + 1-reduce join materialization task count = sum(input_splits) + num_partitions
dag_cyclic_rejected.rs I10 negative case Error::CyclicJob, no tasks materialized
dag_random_50stage.rs (proptest) topological-order correctness at scale materialization order == topo_order()

13.6 Pitfalls

  • Stage activation via "all upstream complete" is correct but coarse — partial stage activation (consuming a subset of upstream partitions early, as some Spark configs do) is PhaseDeferred("§38"), not built here.
  • Conflating TaskId.partition (input-split index for a map task) with the output partition index in MapOutput::partition_sizes (I9) — the type system does not catch this; it is the single most-repeated bug at this layer across real implementations.

13.7 Performance Concerns

Dag construction is O(stages + edges); materialization is O(tasks) per stage activation. At 50 stages × 100 partitions the whole graph materializes in single-digit milliseconds — not a bottleneck relative to shuffle (P1); no further optimization budget spent here.

13.8 Edge Cases

A stage with zero input splits (empty map stage — produces zero tasks, immediately Complete); a diamond-shaped DAG (two independent paths reconverging) — activation must wait for both paths' completion, not just one.

13.9 Failure Analysis

A malformed Job (dangling StageId in dependencies pointing to a stage not in nodes) is rejected at Dag construction with Error::DanglingDependency, symmetric to Error::CyclicJob (I10); no partial materialization occurs on either rejection path.

13.10 Operational Notes

mrs-cli gains a dag-print subcommand rendering the topological order and per-stage dependency count — the first operator-facing debugging tool, used again in every later phase's runbook (docs/runbooks/stuck-stage.md, FM1).

14. Phase 2 — Map Executor & Sort-Based Local Shuffle Write (Weeks 2–3)

14.1 Objectives

Replace the Phase-0 in-memory shuffler with the real mrs-shuffle-local backend (ADR-04): map-side sort, spill, optional combine, and a durable per-mapper consolidated file + index.

14.2 Detailed Implementation Steps

  • mrs-executor::map_runner: read input split → user map fn → Partitioner::partition_for (§11.4, P2) → append to SortBuffer (in-memory, keyed (partition, key)).
  • Spill trigger: SortBuffer.size_bytes() ≥ spill_threshold_bytes (default 256 MiB, §4) → sort by (partition, key) (I4) → optional Combiner::combine (P6, I8) → write spill file (block layout, §8.2).
  • End-of-input: merge all spills into one file via SpillFile::merge_to_single (external k-way merge, Graefe 2006, applied per §5) → shuffler.write_map_output (§11.5).
  • mrs-shuffle-local::writer: final file at ${shuffle_dir}/${stage_id}/${task_id}.data + index ${task_id}.index ((partition, offset, length) triples, I5 — one consolidated file per mapper, never per-(mapper,partition)).
  • mrs-shuffle-local::reader: mmap the data file; for a ShuffleReadRequest, stream the relevant byte ranges per requested map_attempts entry (I2 — only winning attempts).
  • mrs-shuffle-local::compress: LZ4 per block (ADR-16), independently decompressible.
  • ACK-after-fsync contract (§26 FM pitfall): write_map_output only returns Ok after both .data and .index are fsync-ed.

14.3 Deliverable

WordCount on mrs-shuffle-local produces a per-mapper .data+.index pair; manual inspection of the index confirms partition-offset layout matches the writer contract.

14.4 Acceptance Criteria

A Combiner summing per-key counts reduces bytes written by ≥ 60% on the WordCount corpus (measured, not asserted); property test: for any random input split, the merged file's per-partition records equal the sorted union of map-emitted records modulo the combiner (I4, I8); fsync-before-ACK verified by fault-injecting a crash between write and ACK (see §14.9).

14.5 Conformance Fixtures

Fixture Purpose Expected Output
local_shuffle_index_layout.rs index triple correctness offsets sum to file length per partition
combiner_volume_reduction.rs P6/I8 volume check bytes_written_with_combiner ≤ 0.4 × without
spill_sort_property.rs (proptest) I4 every spill internally sorted by (partition,key)

14.6 Pitfalls

  • Spilling without sorting first (§8.1) — the writer assumes "I'll sort at merge time" and the merger discovers unsorted 256 MiB spills it cannot k-way merge (I4 exists exactly to prevent this).
  • Merge-to-single-file transiently doubles disk footprint — spill directory needs ≥2× the spilled volume free (§4 disk amplification row).
  • spill_threshold_bytes too small → metadata storm of tiny spill files; too large → map task OOMs. 256 MiB default is a starting point, not a universal constant.

14.7 Performance Concerns

Batch map-output writes (≥64 KiB buffered per partition before a shuffler call, §22.1); pipeline the spill-sort thread alongside the map function's input read so sort does not serialize behind I/O (§22.1); LZ4 keeps decompression off the critical path at merge time (M15).

14.8 Edge Cases

A map task whose entire output fits below spill_threshold_bytes (zero spills, one direct-to-merge path); a partition that receives zero records from a given mapper (index entry with length=0, reader must handle gracefully); a key that recurs across multiple spill files pre-combine (merge must still combine across spill boundaries, not just within one).

14.9 Failure Analysis

Crash between spill-file write and its fsync → spill file is either fully absent (task re-run from scratch, no partial-file risk) or fully present-and-durable — no torn-write window given append-then-fsync ordering. Crash between write_map_output internal fsync and the driver ACK is the FM3-adjacent case (§26): the driver treats the task as failed (no ACK received) and re-runs it (P4); a stale spill file left on disk is reclaimed at cleanup_stage.

14.10 Operational Notes

tools/shuffle-inspect gains a dump-index <task_id> subcommand that prints the (partition,offset,length) table for manual triage; metrics shuffle_local_bytes_written_total, shuffle_local_spill_count exported per task (feeds docs/runbooks/stuck-stage.md).

15. Phase 3 — Reduce Executor & External Merge Sort (Weeks 3–4)

15.1 Objectives

Implement the reduce-side k-way external merge across all winning map-attempt streams for a partition, with tiered fan-in above the FD budget (§4), and drive TeraSort-scale correctness on a single host.

15.2 Detailed Implementation Steps

  • mrs-executor::reduce_runner: issue ShuffleReadRequest(partition, map_attempts) (§11.2, I2) to the Shuffler (§11.5) → receive one sorted byte-stream per mapper.
  • mrs-executor::external_sort::KWayMerge: a min-heap keyed (key, stream_index) — the stream-index tie-break makes the merge stable (needed for secondary sort, §21.2, applied per P7).
  • Tiered merge (Graefe 2006, ch. "Implementing Sorting," sec. 3.2, applied per §5): if input-mapper count exceeds the per-task FD budget (default 256, §4), merge in groups of 256 into intermediate sorted files, then merge those — bounds heap memory and FD use simultaneously.
  • Streaming vs. buffered reduce: if the reducer is itself a Combiner (associative, I8), stream the combined result per key transition; else buffer the full value list for the current key (spill-to-disk if it exceeds the in-memory budget — the case secondary sort, §21.2, is designed to make unnecessary).
  • Raise RLIMIT_NOFILE at executor startup (§4 FD budget row) so the tiered policy's concurrency cap, not the OS default, governs merge fan-in.

15.3 Deliverable

WordCount (Phase-2 mapper + Phase-3 reducer) produces correct per-word counts at 100 MiB, 1 GiB, and 10 GiB input scales; a 100 GiB TeraSort-shaped run (100 maps × 50 reduces) completes correctly on one host with sufficient disk.

15.4 Acceptance Criteria

Property test: for any randomly partitioned input, concatenated reduce-partition output (in partition order) equals the global sort of the input; 100 GiB single-host TeraSort- shaped run completes with zero valsort-equivalent ordering violations; tiered-merge FD usage stays ≤ 256 concurrent open files regardless of mapper fan-in (measured via lsof-equivalent instrumentation).

15.5 Conformance Fixtures

Fixture Purpose Expected Output
kway_merge_stability.rs stable tie-break correctness duplicate keys preserve stream-index order
tiered_merge_fd_cap.rs FD budget enforcement open-FD high-water-mark ≤ 256
reduce_100gib_single_host.rs scale correctness output totally ordered, record count matches input

15.6 Pitfalls

  • A non-stable k-way merge heap breaks secondary sort (§21.2) even though it is correct for plain keyed reduction — always key the heap (key, stream_index).
  • Tiered-merge tier boundaries (every 256 streams) transiently double on-disk footprint per tier — use tempfile dirs with guaranteed cleanup on task exit (incl. panic).
  • M × T open FDs (M mappers × T concurrent reduce tasks per host) exhausts descriptors fast without the RLIMIT_NOFILE raise + tiered cap acting together.

15.7 Performance Concerns

Pipeline fetch and merge (feed the heap from a bounded channel so the next block's fetch overlaps the current merge step, §22.1); size the merge heap as k × record_overhead (~64 B/record) per merge step, not total — undersizing thrashes the allocator (§26 FM-adjacent pitfall).

15.8 Edge Cases

A partition with zero contributing mappers (empty reduce input — task completes immediately with zero output); a key present in only one of k streams (heap must not stall waiting for phantom entries from empty streams); value-list-too-large-for-memory under the buffered (non-combinable) reduce path (spill-to-disk fallback, re-read).

15.9 Failure Analysis

A ShuffleFetchFailed{source_map} mid-merge does not fail the whole reduce task immediately (§17.4 detail); the merge's progress is checkpointed at "map outputs consumed so far" via a small fetch-progress journal, letting the reducer resume once the driver re-runs exactly the failed upstream map.

15.10 Operational Notes

Reduce-side metrics: reduce_merge_heap_size, reduce_tiered_merge_tiers, reduce_fd_open_count — exported per task, graphed in docs/performance/shuffle- throughput.md; a merge stuck at a flat reduce_merge_heap_size for >30 s is the first signal in docs/runbooks/stuck-stage.md.

16. Phase 4 — Driver & Locality/Resource-Aware Scheduler (Weeks 4–5)

16.1 Objectives

Promote the driver-executor split from in-process (Phase 0) to a real network boundary (gRPC, ADR-18); implement delay-scheduled locality preference (P5) and resource-aware bin-packing (P8).

16.2 Detailed Implementation Steps

  • mrs-driver::rpc: gRPC surface for task assignment, heartbeats, completion/failure reporting — control-plane-only payloads (I1); schema fuzzed by mrs-fuzz (H14-safe, signatures only in this document).
  • DefaultScheduler::next_task (§11.7): three-tier lookup — (1) node-local + fits resources, (2) rack-local with locality_delay expired, (3) any with delay expired (delay scheduling, Zaharia EuroSys 2010, applied per P5, ADR-13).
  • ResourceUnits/ResourceRequest (§11.7) bin-packing: fits() = request ≤ free componentwise (Mesos two-dimensional model, applied per P8, ADR-14); a task whose request exceeds every host's total capacity is rejected at submit time, not runtime.
  • LocalityHint derivation (§11.7): HDFS-block input → replica DataNodes; S3 object range → empty (no node affinity); local file → single host. Reduce-task locality hint = hosts holding the most upstream shuffle bytes for that partition (reduce-side locality).
  • Executor heartbeat loop (mrs-executor::heartbeat) at 1 Hz reporting liveness + free ResourceUnits; driver-side heartbeat_timeout = 30 s (I3, §4).

16.3 Deliverable

A 1 GiB WordCount on a 3-host cluster (driver + 3 executors, one mapper's input local per host) achieves measured node-locality on the map stage.

16.4 Acceptance Criteria

Node-locality rate ≥ 90% (M8) on the 3-host WordCount fixture; property test: for randomized task placement + locality preferences, scheduler locality-rate is within 5% of a brute-force-computed optimum; negative test: an over-resourced task submission is rejected with Error::ResourceUnsatisfiable at submit, never surfacing as a runtime OOM.

16.5 Conformance Fixtures

Fixture Purpose Expected Output
locality.node_local_rate measures node-locality on 3-host WordCount ≥ 90% over 100 runs
locality.delay_scheduling delay-scheduling vs. brute-force optimum within 5%
resource_unsatisfiable_rejected.rs submit-time resource check Error::ResourceUnsatisfiable, zero tasks launched

16.6 Pitfalls

  • locality_delay = 0 collapses immediately to any-host, destroying locality rates; too large stalls the scheduler — 3,000 ms (Spark's inherited default) is the starting point.
  • Empty LocalityHint (S3 input, or a reduce task whose upstream wrote nowhere specific) must be treated as "no preference, proceed now," never "delay forever."
  • Executors that over-report free capacity (a runtime "free" per the scheduler's view but actually paging) — documented known limitation (docs/runbooks/stuck-stage.md, FM- adjacent), not solved at this phase.

16.7 Performance Concerns

Driver scheduling-decision p99 ≤ 10 ms (M9) — the three-tier lookup must stay O(candidates) per free-host event, not O(candidates × hosts); candidate lists are pruned by resource- infeasibility before the locality tiers run.

16.8 Edge Cases

All hosts simultaneously busy (scheduler holds tasks pending, no assignment attempted); a task whose LocalityHint names a host that has since left the cluster (falls through to rack/any tier immediately, no wasted delay); heartbeat arriving out of order under network jitter (driver keys by monotonic sequence number per host, discards stale heartbeats).

16.9 Failure Analysis

A missed heartbeat past heartbeat_timeout (I3) marks the host ExecutorLost and hands off to Phase 5's lineage-invalidation path (§17.3); a scheduling-decision that races a concurrent ExecutorLost event must not assign a task to the now-lost host (driver locks per-host state during the decision window).

16.10 Operational Notes

Metrics: scheduler_locality_tier{node,rack,any} counters, scheduler_decision_latency_ms histogram (gates M9 in CI), resource_bin_pack_rejections_total; mrs-cli cluster-status subcommand added for operator visibility into free ResourceUnits per host.

17. Phase 5 — Fault Tolerance via Re-Execution & Lineage (Weeks 5–6)

17.1 Objectives

Implement the four failure-mode taxonomy (§8.5) and lineage-driven re-execution (P4); no checkpointing is introduced — recomputation from the prior stage's shuffle output is the sole recovery mechanism.

17.2 Detailed Implementation Steps

  • mrs-core::lineage::OutputLineage (§11.8): alive_map_outputs, host_to_outputs; updated on every TaskCompleted (insert) and ExecutorLost (remove via on_executor_lost, §11.8 signature).
  • Four failure modes and their driver-side response: (1) executor crash → heartbeat timeout (I3) → on_executor_lost returns invalidated TaskIds → re-materialize; (2) task-level user error/panic → retry up to max_task_attempts (ADR-12, I14); (3) shuffle fetch failure → re-run exactly the named source_map + the failed reducer; (4) disk-full/quota-exceeded → ResourceExhausted, retry on a different host.
  • Reducer-side resilience (§8.5): a ShuffleFetchFailed does not abort the whole reduce task; a durable fetch-progress journal (flushed on each failure event) lets the reducer resume mid-merge once the re-run upstream map's output is ready — unless the reducer has already begun emitting output (post-merge-start), in which case it restarts fully (documented limitation, PhaseDeferred("§38") for partial-reducer-resume).
  • Attempt counting: every retry increments TaskId.attempt; the attempt field, not a side channel, is the sole record of retry count (I14).

17.3 Deliverable

A kill -9 of one of three executors mid-WordCount-job results in job completion with at most one stage re-execution and total wall time within the RTO bound (§4).

17.4 Acceptance Criteria

Executor-kill RTO ≤ 2× no-failure wall time (§4 RTO row, fault.executor_kill bucket); fault-injection property test: 100 runs, each randomly killing 1–3 executors, every run terminates correctly (zero data loss, correct final output); negative test: a documented non-deterministic user map function is asserted to fail the re-execution-equivalence property, with the failure mode and constraint recorded, not silently tolerated (P13).

17.5 Conformance Fixtures

Fixture Purpose Expected Output
fault.executor_kill kill 1 of 3 executors mid-run job completes, wall time ≤ 2× baseline
fault.random_1to3_kill (100 runs) property test over kill counts every run terminates correctly
fault.nondeterministic_canary P13 documented failure equivalence property fails as documented, not silently

17.6 Pitfalls

  • host_to_outputs is the load-bearing structure (§11.8) — an off-by-one in the executor-lost path either duplicates a map task (new attempt runs beside an already- completed one) or misses one (lineage thinks output is still alive on a dead host).
  • Resuming a reducer mid-fetch needs a durable journal; an executor crash during the journal write loses resumption state and the reducer restarts from zero — acceptable, documented, not silently swallowed.
  • A reducer that has started emitting output cannot resume mid-fetch — restart fully; the "partial-reducer-resume" optimization is explicitly deferred (§38), not attempted here.

17.7 Performance Concerns

Re-execution cost is bounded by "one stage's worth of recompute" in the worst case (ADR-17 rationale) — the RTO figures in §4 assume this; a design that re-ran the whole job on any single-task failure would violate P4's entire premise and is explicitly rejected.

17.8 Edge Cases

Two executors lost within the same heartbeat window (both invalidation sets computed before either re-materialization runs — no double-counting of shared map outputs); a retried task itself fails on the same class of error as its predecessor (still bounded by max_task_attempts=4, not treated specially); a ShuffleFetchFailed racing a concurrent speculative re-run of the same upstream map (driver de-duplicates re-run requests per source map).

17.9 Failure Analysis

Blast radius of an executor loss = every map output it held (§11.8), never the whole stage; containment is automatic via lineage invalidation; operator visibility is a ExecutorLost{host, invalidated_tasks} structured log line plus a lineage_invalidations_total counter — postmortem guidance in docs/runbooks/driver- restart.md covers the ADR-17 boundary (driver crash ≠ executor crash; driver crash is out of this phase's recovery scope, T-driver-spof).

17.10 Operational Notes

fault_injection_kills_total{mode} metric per failure class (1–4); mrs-cli replay- lineage <job_id> dumps the OutputLineage state for postmortem use; this phase's recovery paths are exercised continuously from Phase 12 onward (§24 chaos soak).

18. Phase 6 — Speculative Execution: the LATE Scheduler (Weeks 6–7)

18.1 Objectives

Implement Zaharia's LATE (Longest Approximate Time to End) scheduler (OSDI 2008, applied per P3, ADR-11) as a passive straggler monitor beside the assignment scheduler.

18.2 Detailed Implementation Steps

  • mrs-speculation::late::LateScheduler (§14.2-style signature list): fields slow_task_threshold_stddevs (default 1.0), minimum_task_age (30 s), max_speculative_per_stage (⌈0.1 × stage size⌉), slow_task_progress_threshold (0.25).
  • ProgressScore { progress, progress_rate, estimated_time_to_end } — estimated_time_to_end = (1 - progress) / progress_rate (the LATE paper's core contribution, applied verbatim per §5).
  • LateScheduler::tick: filter tasks younger than minimum_task_age → rank remaining by estimated_time_to_end descending → candidates are those also below slow_task_progress_threshold → cap by max_speculative_per_stage → return TaskIds; driver launches a fresh attempt per returned id (I2 governs which one wins later).
  • Progress reporting (mrs-executor::progress_reporter, 1 Hz, folded into the heartbeat, §16.2): map task progress = bytes_read / total_bytes; reduce task progress = 0.3×fetch_fraction + 0.3×merge_fraction + 0.4×reduce_fraction (weights per the LATE paper, sec. 3.2, applied per §5).
  • Winning-attempt selection (I2): first completion → driver sends TaskCancelled to all other attempts → stamps the completing attempt's TaskId as canonical in MapOutput → schedules cleanup of the loser's partial state.

18.3 Deliverable

A controlled-straggler test (one map task delayed 5× the median) completes within the RTO bound (§4, M7); the speculative-execution conformance bucket passes across 100 synthetic- straggler runs.

18.4 Acceptance Criteria

Wall time ≤ 1.5 × median + minimum_task_age on the 5×-straggler fixture (M7); ≥ 30% wall- time improvement across 100 synthetic-straggler runs (speculation.straggler bucket); property test: the scheduler never exceeds max_speculative_per_stage launches per stage; speculation.no_storm fixture: a stagger-free job launches zero speculative attempts.

18.5 Conformance Fixtures

Fixture Purpose Expected Output
speculation.straggler 5× delayed map task wall time ≤ 1.5× median + 30 s
speculation.no_storm no stragglers present zero speculative attempts launched
speculation.cap_respected (proptest) I-adjacent cap check launches ≤ max_speculative_per_stage always

18.6 Pitfalls

  • Speculative execution without idempotent tasks duplicates side effects — documented at Task::run (P13); the library cannot enforce it.
  • "Predict which attempt finishes first" smarter-than-first-wins policies (rejected per Ananthanarayanan NSDI 2013, applied per §5) can kill the eventually-faster attempt — first-completion-wins only, never a predictive kill.
  • slow_task_progress_threshold mistuned high speculates merely-slow-starting tasks; mistuned low never speculates — 0.25 is the LATE paper's recommendation, not a universal constant.
  • Progress reporting faster than 1 Hz floods the heartbeat channel, creating control-plane backpressure (I1-adjacent concern) — don't.

18.7 Performance Concerns

LateScheduler::tick is O(running_tasks × log(running_tasks)) for the rank step — negligible next to shuffle cost (P1) at any realistic stage size; the max_speculative_ per_stage cap bounds worst-case wasted compute to 10% extra task-seconds per stage.

18.8 Edge Cases

A task at exactly the age/progress threshold boundary (inclusive/exclusive semantics documented and tested); two stragglers in the same stage simultaneously eligible (both speculated, subject to the cap); a speculative attempt that itself becomes a straggler (eligible for a second speculative launch, still bounded by max_task_attempts, I14).

18.9 Failure Analysis

A speculative attempt that fails does not retry the original attempt's count against max_task_attempts — attempts are counted per launched TaskId.attempt, so a failed speculative copy consumes one of the four attempt slots (I14); operator-visible via speculative_attempts_total vs. speculative_attempts_failed_total.

18.10 Operational Notes

docs/runbooks/speculative-storm.md covers the failure mode where mistuned thresholds speculate excessively; metrics late_scheduler_candidates_total, late_scheduler_launches_total, winning_attempt_selected_total feed the dashboard that distinguishes "healthy speculation" from "storm."

19. Phase 7 — Push-Based Shuffle Service (Magnet-Style) (Weeks 7–9)

19.1 Objectives

Implement mrs-shuffle-push (ADR-05): mappers push per-partition blocks to a service tier that merges on write, cutting per-reducer fetch RPCs from O(M) to O(1) (Shen VLDB 2020, applied per §5, M6).

19.2 Detailed Implementation Steps

  • Wire protocol (§8.2): PushRequest{job,stage,map_attempt,partition,block,checksum} → PushAck{map_attempt,partition,merged_offset}.
  • Mapper flow: generate per-partition output as in §14 → issue one PushRequest per partition to the service node responsible for that partition (consistent hash of (job_id, partition), not partition alone — avoids the hot-node pitfall, §19.7) → record MapOutput{locations:[service_node]} on ACK.
  • mrs-shuffle-push::merge_on_write::PartitionAggregator: verify checksum (I7) → append to an in-memory sort-merge buffer → drain via k-way merge into the persistent per-partition file once the buffer crosses a high-water mark — the on-disk file is always key-sorted (eliminates reducer-side sort for this backend).
  • Replication: each block replicated to 2 service nodes (primary + secondary via consistent hashing); writer waits only for the primary ACK (Magnet's "best-effort replication," applied per §5); reducer falls back to secondary on primary failure.
  • Auth/quota (P11): mTLS + per-job HMAC token (ADR-19) on every PushRequest/ ShuffleReadRequest; per-job (soft_limit_bytes, hard_limit_bytes) quota (I12).
  • Reduce-stage activation gate (I6, applied here concretely): the driver does not activate the reduce stage until every upstream map task's push has been service-ACKed.

19.3 Deliverable

WordCount-on-push-shuffle produces byte-identical output to WordCount-on-local-shuffle on the same input; a 100 GB push-shuffle TeraSort-shaped run completes within the bound below.

19.4 Acceptance Criteria

Byte-identical output vs. local backend (equivalence.local_vs_push); wall time ≤ 1.5× the local-shuffle equivalent on a 3-node cluster; per-reducer fetch RPC count ≤ 2 (M6, primary

  • fallback) vs. M for the local backend; a service-node kill mid-run completes correctly via the secondary replica.

19.5 Conformance Fixtures

Fixture Purpose Expected Output
equivalence.local_vs_push cross-backend byte-equality identical output, WordCount + TeraSort-shaped
push.fetch_rpc_count M6 measurement ≤ 2 RPCs/reducer at 10K-mapper scale
push.service_kill_failover secondary-replica correctness job completes, output correct

19.6 Pitfalls

  • A reducer fetching before every map has pushed AND been merged returns a partial result the merge step cannot detect — the reduce-stage-activation gate (I6, §19.2) is the only correct fix; do not weaken it for latency.
  • Cascading retries: a push failing on service-node OOM triggers a map retry, which re-pushes to the same overloaded node, repeating — mitigate with exponential backoff on PushRequest plus a service-side circuit breaker.
  • Consistent-hashing on partition alone (not (job_id, partition)) produces hot service nodes under a skewed partitioner — hash the pair (§19.2), not the partition alone.

19.7 Performance Concerns

Merge-on-write is CPU-bound (sort-merge per incoming block), not disk-bound — size service nodes for CPU, a non-obvious but load-bearing sizing decision (docs/architecture/push- shuffle.md); target throughput ≥ 150 MB/s/node (M4).

19.8 Edge Cases

A PushRequest arriving after the reduce stage has already activated due to a race in the ACK-count check (must be structurally impossible given I6's gate — tested via a fault-injected reordering harness); a partition whose primary and secondary service nodes are both briefly unreachable (reducer retries with backoff, does not fail the task immediately).

19.9 Failure Analysis

A service-node crash invalidates only the primaries it held; the driver's shuffle-metadata table (mrs-driver::shuffle_metadata) already knows the secondary location (replicated at write time) and redirects reducer fetches there — no re-run of upstream maps required unless both replicas are lost (rare; falls back to the Phase-5 re-execution path).

19.10 Operational Notes

docs/runbooks/shuffle-service-full.md covers the quota-exhaustion incident path; metrics push_service_merge_cpu_seconds, push_fetch_rpc_count, push_replica_failover_total exported per service node.

20. Phase 8 — Disaggregated Shuffle on Object Storage (Cosco-Style) (Weeks 9–11)

20.1 Objectives

Implement mrs-shuffle-s3 (ADR-06): shuffle data lands on durable, autoscaling, multi-tenant object storage, making executors stateless against pod restarts, autoscaling downscale, and spot preemption (P9).

20.2 Detailed Implementation Steps

  • Object layout (§8.2): s3://{bucket}/{job_id}/{stage_id}/{partition}/{map_attempt}.block plus a per-stage manifest.json.
  • mrs-shuffle-s3::writer::S3ShuffleWriter::write_partition: one multipart upload per (map, partition); returns size on CompleteMultipartUpload — the ACK-after-fsync contract's S3 equivalent (§26 pitfall).
  • mrs-shuffle-s3::manifest: driver-written (not map-task-written) (map_attempt, partition) → object_key table, updated only after the map task's write is ACKed — never inferred by listing the bucket (P14, I13).
  • mrs-shuffle-s3::reader::read_partition: read manifest → resolve keys per requested map_attempts → parallel range-GETs with credit-based flow control (P10) bounding in-flight bytes.
  • Cleanup (mrs-shuffle-s3::cleanup): post-job bulk DeleteObjects against the per-job prefix by the driver; a separate periodic sweeper (cron, not the driver) garbage-collects orphans from crashed jobs whose drivers never finished cleanup.
  • Bucket-prefix sharding ({hash_prefix}/{job_id}/...) to spread S3's per-prefix PUT rate limit (§20.8 pitfall) across enough prefixes at 10⁴-mapper scale.

20.3 Deliverable

WordCount-on-S3-shuffle byte-matches both the local- and push-backend runs on the same input; a kill -9 mid-job re-reads inputs from S3 and completes within the RTO bound.

20.4 Acceptance Criteria

Byte-identical output vs. local and push backends (equivalence.local_vs_s3, equivalence.push_vs_s3); 100 GB TeraSort-shaped run ≤ 2.5× local-shuffle wall time (object-store RTT is the documented, accepted cost, §4); executor-kill RTO ≤ 1.5× no- failure wall time — better than local backend's 1.8× under the same fault (P9's concrete payoff); cleanup_stage verified empty via a post-cleanup bucket listing.

Fixture Purpose Expected Output

equivalence.push_vs_s3 cross-backend byte-equality identical output

20.6 Pitfalls

  • PUT amplification: 10⁴ maps × 10⁴ partitions = 10⁸ PUTs at full scale, hitting S3's default per-prefix rate limit (3,500 req/s) — mitigate via prefix sharding (§20.2).
  • Manifest race: a map's PUT succeeds but the manifest update fails — reducer treats a manifest-absent key as not-yet-available and waits (never falls back to LIST, I13); the driver retries the manifest write.
  • Multipart-upload abort leak: a crashed map task's incomplete multipart upload costs money indefinitely — a bucket lifecycle policy aborting incomplete uploads after 24h is mandatory, not optional.
  • List-versus-manifest divergence: never implement read_partition as "list the bucket prefix" — the manifest is the sole existence authority (P14, I13).

20.7 Performance Concerns

Target throughput ≥ 80 MB/s/node (M5) — object-store RTT, not CPU or local disk, is the ceiling; parallel range-GET concurrency (bounded by fetch_concurrency + credit flow, P10) is the only lever that matters here; compression trades toward Zstd (ADR-16 exception) for this backend given the RTT-bound regime.

20.8 Edge Cases

A manifest listing a key whose object was never fully uploaded (crashed multipart, §20.6) — reader must distinguish "not yet in manifest" from "in manifest but GET 404s" and treat the latter as a hard error (source map re-run), not an infinite wait; eventual-consistency edge cases on non-S3-compatible object stores (design documented as manifest-mediated, works on GCS/Azure/legacy-HDFS-on-S3 per §20.2 rationale even though S3 itself has been strongly consistent since 2020).

20.9 Failure Analysis

An object-store outage affecting a subset of keys degrades to per-key retry-with-backoff, not a whole-job failure; a full-region outage exceeds this backend's design envelope and is out of scope (documented, not solved) — falls to job-level operator intervention.

20.10 Operational Notes

docs/runbooks/shuffle-service-full.md §S3 covers PUT-rate-limit incidents; metrics s3_shuffle_put_latency_ms, s3_manifest_lookup_miss_total, s3_orphan_sweep_bytes_total (from the periodic sweeper) are dashboarded; lifecycle-policy configuration is part of Phase-8's Terraform/IaC deliverable (out of blueprint scope, referenced only).

21. Phase 9 — Combiner, Secondary Sort, Custom Partitioner (Weeks 11–12)

21.1 Objectives

Complete the user-facing tuning surface: the Combiner contract (P6), secondary sort (P7), and the open Partitioner trait (§11.4) for custom bucketing strategies.

21.2 Detailed Implementation Steps

  • Combiner::combine(key, &mut Vec<Vec<u8>>) (§11.4, I8) runs at map-spill time and again at map-merge time (§14.2); a differential conformance test asserts identical output across {no combiner, spill-only, spill+merge, spill+merge+reduce-side} for a known-associative combiner (sum).
  • Secondary sort: PartitionAndSecondarySort<P> (§11.4) sorts map output by (partition, primary_key, secondary_key); the reducer groups on primary_key alone and receives values already in secondary_key order — makes the Phase-3 buffered-reduce fallback (§15.2) unnecessary for this case (Dean-Ghemawat 2004, sec. 4.2, applied per §5).
  • Custom partitioner examples: geo-bucket (hash of (lat_bucket, lon_bucket)), tenant-bucket (hash of tenant id), time-bucket (hash of a time window) — all implement Partitioner (§11.4) directly, no library changes required (P2-style open extension).
  • Consistency check tooling: a lint (part of make lint) that flags a PartitionAndSecondarySort whose secondary_comparator disagrees with the partitioner's implied ordering (§21.6 pitfall) — best-effort static check, not a proof.

21.3 Deliverable

A Combiner for WordCount reduces shuffle volume by ≥ 60% (re-verified end-to-end, extends §14.4's map-side-only measurement); a secondary-sort example sorts (user_id, timestamp) logs and verifies chronological order per user_id without reducer-side buffering; a geo-bucket custom partitioner achieves balanced partition sizes.

21.4 Acceptance Criteria

Combiner: ≥ 60% shuffle-byte reduction on the WordCount conformance corpus (M-referenced, extends M-comb from §14); secondary sort: 100% of user_id groups verified in strict timestamp order across the synthetic corpus with zero reducer-side buffering measured; custom partitioner: max partition size ≤ 2× the mean on the geo conformance corpus.

21.5 Conformance Fixtures

Fixture Purpose Expected Output

correctness.secondary_sort chronological order per user zero out-of-order pairs, zero buffering
custom_partitioner.geo_balance partition-size balance max ≤ 2× mean

21.6 Pitfalls

  • Non-associative combiner: average = sum/count combined naively is not associative; correct form is (sum,count) pairs combined associatively, divided only at the reducer (I8) — the library cannot detect this at runtime, only document it.
  • Secondary-sort comparator/partitioner mismatch: the secondary_comparator must agree with the partitioner's implied bucket ordering, or the reducer's assumed order is silently wrong — the §21.2 lint catches the common cases, not all.
  • Skewed custom partitioner (e.g. one tenant = 90% of data): produces straggler reducers the speculative scheduler (§18) cannot help with (the straggler has 10× the data, not merely bad luck) — mitigate via range partitioning with sampling or the deferred AQE skew-split (PhaseDeferred("§38")).

21.7 Performance Concerns

Secondary-sort adds sort-key bytes per record (extra comparator bytes in the sort key, §8.2 encoding) — the tradeoff is explicit in P7: extra bytes/record vs. eliminated reducer-side buffering; measure the crossover point on the conformance corpus.

21.8 Edge Cases

A combiner that reduces a key's value list to zero entries (must be handled as "key disappears from output," not an empty-value bug); a secondary-sort key that ties on both primary and secondary key (stable order falls back to k-way-merge's stream-index tie-break, §15.2); a custom partitioner returning a partition index ≥ num_partitions (rejected at partition-assignment time with Error::PartitionOutOfRange).

21.9 Failure Analysis

A partitioner panic (user code) surfaces as TaskFailed{reason: UserError} (§17.2 failure mode 2), retried per I14 — no special-casing versus any other user-code panic; a misconfigured secondary comparator is a silent-correctness bug, not a crash, and is therefore caught only by the §21.6 lint and conformance fixtures, never at runtime.

21.10 Operational Notes

mrs-cli partition-balance-report <job_id> prints per-partition record/byte counts post-hoc for skew triage; the geo/tenant/time-bucket examples ship as docs/architecture/ companion notes for teams writing their own partitioner.

22. Phase 10 — Performance Hardening (Weeks 12–14)

22.1 Objectives

Close the gap between "correct" (Phases 0–9) and "fast" (§4 targets): batching/pipelining, compression tuning, zero-copy network paths, NUMA-aware sort, SIMD sort.

22.2 Detailed Implementation Steps

  • Batch map-output writes: buffer ≥ 64 KiB sorted output per partition before a Shuffler call (applied at §14.2); pipeline reduce fetch + merge via a bounded mpsc channel feeding the k-way heap (applied at §15.2); pipeline spill-sort alongside map-input read.
  • Compression: LZ4 default (ADR-16) at ≥ 1.5 GB/s/core decompression (M15); Zstd level 3 available for the S3 backend (§20.7) trading ~3× CPU for ~30% size; per-block (not per-stream) compression lets the reducer decompress block-by-block.
  • Zero-copy network: sendfile(2) for local-backend fetch (mapped file → socket, no userspace copy, ~2× throughput vs. read+write, applied at §14.2); splice(2) for the push-service's incoming-push-to-merge-buffer path (applied at §19.2); writev/readv iovec batching on the fetch protocol (mrs-net::fetch_protocol).
  • NUMA-aware sort: SortBuffer allocation pinned to the executor's CPU-affinity NUMA node via numactl --membind at startup (Hennessy & Patterson Ch. 2, applied per §5) — a wrong-NUMA-node buffer halves sort throughput on a 2-socket host.
  • SIMD sort: SIMD radix sort for fixed-size keys (8/16/32-byte); falls back to pdqsort for variable-length keys; ~3–5× faster on small fixed keys, within 10% of pdqsort once the buffer exceeds L3 cache (don't over-tune past that point).

22.3 Deliverable

TeraSort 1 TB on a 16-node cluster completes in ≤ 30 min (M2) on the local backend; a criterion benchmark suite captures per-phase cost (map-sort, spill, shuffle-write, shuffle-fetch, reduce-merge, reduce-fn).

22.4 Acceptance Criteria

TeraSort 1 TB wall time ≤ 30 min (M2); TeraSort 100 GB shuffle throughput ≥ 200 MB/s/node at the NIC (M3); WordCount on the Project Gutenberg corpus ≥ 80% of peak measured network throughput between executors and shuffle service; criterion suite committed and gated in CI for regression (P12, §31).

22.5 Conformance Fixtures

Fixture Purpose Expected Output
perf.terasort_1tb_16node M2 gate ≤ 30 min
perf.shuffle_throughput_100gb M3 gate ≥ 200 MB/s/node at NIC
perf.criterion_regression per-phase cost regression gate no phase regresses > 10% vs. baseline

22.6 Pitfalls

  • LZ4 on already-compressed input (e.g. Parquet-encoded records) wastes CPU for no size win — document the input-encoding assumption at the Combiner/Partitioner trait boundary.
  • sendfile naming/semantics differ subtly Linux vs. BSD/macOS despite similar man pages — feature-gate via nix::sys::sendfile per platform.
  • NUMA-pinning a single-socket host is a no-op, not an error — do not fail executor startup if numactl reports one node.
  • SIMD radix sort past the L3-cache-fit boundary is memory-bandwidth-bound and gains nothing over pdqsort — don't over-tune based on microbenchmarks alone.

22.7 Performance Concerns

This phase's entire subject is performance (§31 carries the full targets table, M1–M15); the phase-local concern is regression discipline: every optimization here is gated by the criterion suite (§22.5) so a "faster" change that silently regresses another phase's number is caught in CI, not in the 30-day soak (§24).

22.8 Edge Cases

A host with heterogeneous NUMA topology (4-socket, uneven memory-per-socket) — pin to the CPU's local node, accept imperfect balance rather than skip pinning; a record whose key does not fit any fixed-size SIMD bucket (falls to pdqsort transparently, no separate code path for the caller).

22.9 Failure Analysis

A numactl invocation failing on an unsupported kernel degrades to unpinned allocation with a warning log, never a hard startup failure — performance-hardening features must be fail-open with respect to correctness (P1's ordering: correctness is never traded for speed).

22.10 Operational Notes

docs/performance/numa-sort.md and docs/performance/shuffle-throughput.md carry the long-form benchmark methodology; benchmarks/results/ + benchmarks/plots/ track per-release trend lines feeding the perf-regression dashboard (§31).

23. Phase 11 — TeraSort Benchmark Gate (Weeks 14–15)

23.1 Objectives

Wire the public Sort Benchmark (sortbenchmark.org) as the canonical large-data correctness + performance gate, using gensort/valsort (applied per §5 RFCs/Specs).

23.2 Detailed Implementation Steps

  • examples/terasort.rs: identity map (Kv → vec![Kv]), RangePartitioner (ADR-09) constructed from a uniformly-sampled set of split points (standard TeraSort technique — sampling must be uniform across the input, not front-biased, §23.6 pitfall), identity reduce, file output.

23.3 Deliverable

TeraSort 100 GB completes correctly on a 3-node cluster ≤ 5 min (M1); TeraSort 1 TB completes correctly on a 16-node cluster ≤ 30 min (M2, re-verified from §22 at full gate strictness including valsort).

23.4 Acceptance Criteria

valsort reports zero errors on both the 100 GB and 1 TB runs; M1 (≤5 min/100GB/3-node) and M2 (≤30 min/1TB/16-node) both met; the nightly CI job posts wall time to the dashboard with no manual step.

24. Phase 12 — 30-Day Chaos Soak (Continuous, Operational-Readiness Gate)

24.1 Objectives

24.2 Detailed Implementation Steps

  • Canary topology: 3 driver-eligible nodes (ADR-17 — single active driver, no HA; the other 2 are cold standbys operators can manually promote), 12 executor nodes, 4 push-shuffle service nodes, one S3 bucket.
  • Continuous workload: a WordCount job every 5 min against a rotating corpus; a TeraSort 100 GB job every hour; backend rotation (half local, quarter push, quarter S3) with cross-backend output-equivalence asserted on shared inputs (§19/§20 equivalence buckets, re-run continuously here).

24.4 Acceptance Criteria

25. Threat Model

25.1 Trust boundaries

  1. Caller boundary — the job submitter supplies map/reduce functions, partitioner, combiner, I/O sinks; the library trusts these to be deterministic (P13) but not to be benign (untrusted code still runs sandboxed at the OS-process level, T3).
  2. Executor boundary — executors run user code; cannot read another job's shuffle data (auth at the shuffle service, ADR-19; OS-level user separation on the host).
  3. Shuffle-service boundary — the push service (§19) is multi-tenant by construction; mTLS + per-job HMAC (ADR-19) isolate tenants.
  4. Object-storage boundary — the S3 backend (§20) relies on bucket-level IAM; per-job-prefix-scoped roles; an IAM misconfiguration is out of this library's scope but named here (T9).

27. Operational Readiness

Metrics. Every phase names its own (§12.10–§24.10); aggregated under a Prometheus- compatible /metrics endpoint per binary (mrs-driver, mrs-executor, mrs-shuffle-push). Tracing. Alerting philosophy. Alert on rate-of-change for the invariant-violation counters (I1–I14, all "must be 0" counters) before alerting on absolute thresholds — a nonzero invariant-violation counter is always page-worthy. 28. Compatibility & Versioning

Wire compatibility. The gRPC control-plane schema (ADR-18) and the shuffle fetch-protocol framing (mrs-net::fetch_protocol) are versioned independently; a driver and executor within one minor version are guaranteed wire-compatible; cross-minor-version compatibility is maintained for one release back (N-1) to support rolling upgrades. Storage compatibility. The spill-block layout (§8.2) and S3 object/manifest layout (§20.2) are versioned via a layout-version byte in the file/object header; a reader supporting version V must accept V and V-1. Schema evolution. MapOutput and ShuffleReadRequest (§11.2) are Protobuf-encoded on the wire; new fields are additive and optional, never renumbered (standard Protobuf discipline). API stability. The Shuffler, Task, Partitioner, Combiner traits (§11) are the public extension surface; a breaking change to any requires a major version bump per SemVer. Migration. A layout-version bump ships with a mrs-cli migrate-shuffle-data tool that rewrites existing spill files to the new layout offline. Deprecation policy. A deprecated trait method is marked #[deprecated] for one minor version with a runbook note before removal. SemVer policy. MAJOR.MINOR.PATCH; MAJOR = wire/storage/trait-breaking; MINOR = additive; PATCH = bugfix only. Rolling-upgrade guarantees. Executors on version N and N-1 may coexist against one driver during a rolling upgrade window (bounded by the wire- compatibility guarantee above); the push-shuffle service similarly supports N/N-1 mixed fleets for the duration of a rolling deploy.

32. Scalability Analysis

Constant vs. grows. Driver control-plane load is O(tasks), not O(bytes) (I1) — stays roughly constant per task regardless of shuffle volume, the property that lets it scale to 10⁴ tasks/stage. Shuffle bytes and fetch-RPC count grow with M×R on the local backend (O(M×R²) worst-case pull fetches) but only O(R) on the push backend (M6) — the entire motivation for ADR-05. Named bottlenecks in order. (1) shuffle network/disk bandwidth (P1, always first); (2) reduce-side merge fan-in once mapper count exceeds the FD budget (§15, tiered merge is the mitigation, not a fix — Big-O stays O(M log(256)) after tiering vs. O(M log M) untiered); (3) driver scheduling-decision latency at extreme task counts (M9, mitigated by candidate-list pruning, §16.7); (4) push-service CPU (merge-on-write is CPU-bound, §19.7) at extreme fan-in per partition. Horizontal scaling. Executors scale linearly with cluster size for map-stage throughput; shuffle-service nodes scale linearly for push-backend merge capacity (bounded by consistent-hash rebalancing cost on node add/remove, out of Phase-0–12 scope). Vertical scaling. NUMA-aware sort (§22.2) and FD budget (§4) are the two per-host levers before adding nodes helps. Sharding/ partitioning. The partitioner (§11.4) is the user-facing sharding lever; the S3 backend's bucket-prefix sharding (§20.2) is the infrastructure-facing one. Coordination overhead. Single-driver control plane has zero cross-driver coordination cost (no consensus) at the cost of the ADR-17 HA tradeoff (T4). Practical ceiling. ~10⁴ tasks/stage on the local backend before the M×R² pull-fetch cost dominates (Capacity Model §35 derives this); the push backend raises the practical ceiling by roughly two orders of magnitude on fetch count alone (M6) before push-service CPU becomes the new bottleneck (§19.7). Levers beyond the ceiling. Push/S3 backend adoption (already built in, §19/§20); AQE-style partition coalescing to reduce effective R (PhaseDeferred("§38")); a multi-tenant/multi- job scheduler (DRF, out of scope per §1) to share a ceiling-bound cluster across jobs.

33. Mental Models & First Principles

  1. MM1 — Control plane ≠ data plane; conflating them is the scaling wall. Insight: a coordinator that never touches a byte of payload scales with task count, not payload volume. Predicts: any design routing shuffle bytes through the driver hits a wall around single-node NIC bandwidth regardless of cluster size. Bug without it: a "helpful" debug feature that has the driver relay a sample of shuffle bytes for inspection quietly becomes the throughput ceiling. Applies at §3 (I1).
  2. MM2 — A "task" and a "task attempt" are different objects; the address must say which. Insight: TaskId{stage,partition,attempt} names an attempt, not a task; speculative execution and retries are only safe because every attempt has its own identity. Predicts: any scheme that identifies work by (stage,partition) alone will double-count or lose output the first time two attempts of the same task are ever simultaneously alive. Bug without it: exactly the double-counted-speculative-output class (I2). Applies at §11.1, §18.4.
  3. MM3 — Re-execution is checkpointing where the checkpoint is free. Insight: the prior stage's shuffle output already is a checkpoint of that stage's compute; writing a second, dedicated checkpoint duplicates durability spend for no correctness gain, as long as the upstream stage's output survives long enough to be re-read. Predicts: a system that adds explicit task-progress checkpointing on top of this design is paying twice for the same guarantee. Bug without it: over-engineered checkpoint machinery that the RDD paper's cost argument shows is unnecessary. Applies at §17 (P4).
  4. MM4 — The shuffle backend is a storage-tier decision, not a compute decision. Insight: Shuffler (§11.5) is the entire interface; everything backend-specific (sort location, replication, durability window) lives behind it, and the executor's compute logic is backend-agnostic by construction. Predicts: adding a fourth backend (e.g. RDMA-NVMe, §37) requires zero executor-logic changes, only a new Shuffler impl. Bug without it: backend-specific branches leaking into map_runner/reduce_runner, the exact mistake pre-2020 Spark made hard-coding local disk. Applies at §3, §11.5.
  5. MM5 — M×R is a hidden quadratic; push-based merge trades it for M+R. Insight: pull- based shuffle's fetch count is bounded by mappers × reducers² in the worst pathological case and M×R in the common case; a push service that merges per-partition collapses the reducer's fetch count to O(1) per partition regardless of M. Predicts: pull-based shuffle's fetch-metadata cost, not bandwidth, becomes the bottleneck first at high (M,R) — exactly what Magnet measured. Bug without it: teams "add more executors" to fix a metadata-storm-caused slowdown and it doesn't help. Applies at §19.1, Capacity Model (§35).
  6. MM6 — A manifest is a lock-free existence proof; a directory listing is a race. Insight: object storage offers no transactional multi-object write, so "does this data exist" must be answered by a single authoritative record (the manifest), never by enumerating storage. Predicts: any shuffle-on-object-store design that lists the bucket to discover blocks will exhibit intermittent, hard-to-reproduce partial-read bugs under concurrent writers. Bug without it: the list-and-infer anti-pattern (P14, I13, documented as the root cause of half of real shuffle-on-S3 incidents). Applies at §20.5.
  7. MM7 — Speculation is a monitor, not a scheduler feature. Insight: LATE observes progress and emits launch requests; it never decides where to run them — that's still the assignment scheduler's job. Predicts: a design that couples speculation logic into the assignment scheduler will need a rewrite the first time it wants a different straggler policy (e.g. Ananthanarayanan's Attack of the Clones aggressive-but-cheap speculation). Bug without it: a monolithic scheduler where changing the speculative policy risks the (unrelated) locality/resource logic. Applies at §11.7, §18.
  8. MM8 — Associativity is a proof obligation the type system cannot discharge. Insight: Combiner (§11.4) can only state the associative+commutative requirement (I8); Rust's type system has no way to verify a closure is associative. Predicts: every combiner-related production bug traces to a violated, undetected assumption, not a library defect. Bug without it: naive average = sum/count combiners silently producing fan-in-dependent results (§21.6). Applies at §6 (P6), §21.

One paragraph per system:

Hadoop MapReduce made the one decision this blueprint's Phase 2/3 (§14/§15) directly descends from: per-mapper consolidated sorted spill files with an offset index (I5), fetched by pull. It wins today in environments needing a battle-tested, JVM-ecosystem- integrated batch engine with no appetite to operate a third shuffle-service tier — the simplicity of "shuffle lives on local disk, full stop" is a feature when the cluster is fixed-size and non-preemptible.

Apache Spark generalized the user API into a DAG of RDD transformations (Zaharia 2010) and made lineage-based recomputation (not checkpointing) the default fault-tolerance story (NSDI 2012) — the single decision this blueprint's §17 borrows most directly. Spark wins wherever an interactive, iterative, or SQL-compiled workload needs the RDD/DataFrame abstraction layered above the shuffle primitive this blueprint specifies underneath.

Apache Tez replaced MapReduce's two-stage rigidity with an arbitrary DAG-of-vertices model years before Spark's SQL layer matured on top of it, and its OrderedPartitionedKVOutput is close kin to this blueprint's mrs-shuffle-local::writer. Tez wins inside the Hadoop/YARN ecosystem where Hive-on-Tez needs DAG execution without adopting Spark's full runtime and memory model.

Apache Flink (batch) unifies streaming and batch under one runtime by making the shuffle boundary a runtime choice (pipelined vs. blocking) rather than a fixed property of the engine (Carbone 2015) — the option this blueprint deliberately forecloses (§1 non-goals; explored as an Alternative Architecture, §37). Flink wins when the same platform must serve genuinely low-latency streaming and batch workloads from one engine.

35. Back-of-Envelope Capacity Model

Each number is derived from §4 System Constraints with the formula shown; none is asserted without a derivation.

  1. Shuffle bandwidth, local backend, 3-node cluster. throughput/node (§4) × nodes = 200 MB/s × 3 = 600 MB/s aggregate shuffle bandwidth ceiling — the number M1's 100 GB/ 5 min target (≈341 MB/s aggregate) must stay comfortably under.
  2. TeraSort 1 TB wall time, 16 nodes, local backend. total_bytes / (throughput/node × nodes) = 10¹² B / (200 MB/s × 16) = 10¹² / 3.2×10⁹ B/s ≈ 312 s ≈ 5.2 min pure-transfer floor; M2's 30 min target leaves ~5.7× headroom for sort/merge/fetch overhead atop raw transfer — consistent with TeraSort being shuffle-dominated but not transfer-bound alone.
  3. RAM for the reduce-side merge heap. k_streams × record_overhead (§15.7) = 256 × 64 B ≈ 16 KiB per merge step at the FD-budget cap (§4); negligible against per-executor RAM, confirming the tiered-merge design trades FDs, not memory, as the binding constraint.
  4. FDs for an untiered 10K-mapper reduce task. mappers × streams_per_mapper (1) = 10,000 open FDs — exceeds the 256 FD-budget cap (§4) by ~39×, which is exactly the derivation behind mandating tiered merge (§15.2) once mapper count exceeds 256.
  5. Push-backend fetch RPCs, 10K mappers. Pull backend: M × R² worst case or practically ~M fetches/reducer (§4 network-amplification row) ⇒ 10,000 RPCs/reducer; push backend: ≤ 2 (primary + fallback, M6) ⇒ a 5,000× reduction in per-reducer fetch count, matching the "100×" order-of-magnitude Magnet reports at their production scale (the exact ratio scales with M).
  6. Disk headroom needed for merge-to-single-file. spill_volume × amplification (§4) = spill_volume × 2 — a map task spilling 2 GiB needs 4 GiB free during the transient merge-to-single-file step (§14.6).
  7. Spill-file count before merge, WordCount 10 GB input. input_bytes / spill_threshold_bytes = 10×10⁹ / (256×2²⁰) ≈ 38 spills per mapper before the final merge-to-single-file step — well within a sane per-mapper file-descriptor budget during the write phase itself.
  8. Driver control-plane load at 10K tasks/stage. tasks × RPC_size_estimate ÷ scheduling_decision_budget (M9, §4) = 10,000 × (metadata-only, I1) / 10 ms p99 — since payload is metadata-only (kilobytes, not the gigabytes of actual shuffle data), the driver's aggregate control bandwidth stays orders of magnitude below any shuffle backend's data bandwidth, confirming I1's scaling claim numerically.
  9. S3 PUT rate at full 10K×10K scale. mappers × partitions = 10,000 × 10,000 = 10⁸ PUTs total; against S3's default 3,500 req/s/prefix (§20.6), a single prefix would take 10⁸ / 3,500 ≈ 28,571 s ≈ 7.9 h — the derivation directly motivating the bucket-prefix sharding requirement (§20.2): sharding across just 8 prefixes brings this under 1 hour.
  10. Compression throughput vs. shuffle bandwidth. LZ4 decompression (M15) at ≥ 1.5 GB/s/ core comfortably exceeds the local backend's 200 MB/s/node target (M3) even on a single core, confirming compression is never the bottleneck on the local backend — the basis for choosing throughput-optimized LZ4 over ratio-optimized Zstd there (ADR-16).
  11. Chaos-soak executor-kill exposure. kills/interval × soak_duration = (1 per 10 min) × (30 days × 144 ten-minute-intervals/day) = 4,320 executor-kill events over the 30-day soak — each one exercising the Phase-5 re-execution path (§17), giving the statistical confidence behind M12's ≥99%-completion target.
  12. Object-storage fetch concurrency for M5's 80 MB/s/node target. Assuming a single-object-range-GET throughput of ~10 MB/s (typical S3 per-connection figure), target / per_connection = 80 / 10 = 8 concurrent range-GETs per node are the minimum fetch_concurrency (§20.2) needed to hit M5 — the number that sizes the credit-flow window (P10) for this backend.

37. Alternative Architectures (Roads Not Taken)

AA1 — Fully in-memory shuffle (no spill), original Spark 2010 model

┌────────┐  cache in RAM   ┌──────────┐   RAM-to-RAM    ┌────────┐
│ Mapper │───────────────▶│ RAM cache │────fetch───────▶│ Reducer│
└────────┘  (no disk path) └──────────┘                  └────────┘

Regime where it wins: interactive/iterative workloads (repeated passes over the same working set, e.g. ML training loops) where the working set provably fits cluster RAM and recomputation-on-eviction (RDD lineage) is cheap relative to disk I/O. Real system: early Spark (HotCloud 2010) before ExternalSorter matured. Why this blueprint rejected it: the target workload (TeraSort-scale batch) routinely exceeds cluster RAM by design (§1, §4); an all-in-memory shuffle would OOM or silently degrade to disk anyway, so building the external-merge path (§15) from the start is the only workload-honest choice (P1).

AA2 — Pipelined (non-blocking) shuffle, Flink-batch model

Mapper ──stream──▶ [network buffer, bounded] ──stream──▶ Reducer
        (reducer starts consuming before mapper finishes — no stage barrier)

Regime where it wins: workloads needing low end-to-end latency across many small stages, or a single runtime shared with true streaming (Flink's actual reason for this choice, Carbone 2015). Real system: Apache Flink (batch mode via pipelined ResultPartition). Why this blueprint rejected it: pipelining forfeits the clean stage-boundary fault-tolerance story this blueprint depends on (§17) — a failure mid-pipeline has a much larger, harder-to-bound recovery scope than "re-run the map task, the blocking boundary already isolated its output" (I6). The blocking boundary is a deliberate simplicity-for- recoverability trade (§1 non-goals exclude streaming precisely to keep this trade clean).

AA3 — Serverless (Lambda-style) executors, Locus/Pywren model

Driver (Step-Functions-style state machine)
   │  invoke                                invoke
   ▼                                          ▼
Lambda map task ──write──▶ S3 ◀──read────  Lambda reduce task
(no persistent executor process; shuffle IS the only durable state)

Regime where it wins: infrequently-run or bursty jobs where executor-pool warm-up cost dominates total job cost, and per-invocation billing beats holding a warm cluster. Real system: the Pywren/Locus line of research (Pu, Venkataraman, Stoica NSDI 2019, applied per §5). Why this blueprint rejected it: Lambda-class function limits (memory, execution duration, no local disk for spill) are structurally incompatible with the external-merge- sort design this blueprint's Phase 3 requires at TeraSort scale (§15); the S3 backend (§20) already captures the disaggregation benefit Locus is after without inheriting Lambda's per-invocation resource ceiling — PhaseDeferred("§38") covers a future serverless executor pool as an addition, not a replacement.

BLAKE3 — the cryptographic hash function used for shuffle-block checksums (I7).

Bucket prefix sharding — splitting an object-store key space across multiple prefixes to spread PUT-rate-limit load (§20.2, §35).

Chaos daemon — the injected-fault process driving the 30-day soak (§24.2).

Checksum — a per-block integrity value verified on read to detect silent corruption (I7, T1).

Combiner — a user-supplied, associative-and-commutative function that reduces map output volume before shuffle (§11.4, P6, I8).

Consistent hashing — the technique routing a (job_id, partition) pair to a specific push-shuffle service node while minimizing rebalancing on node add/remove (§19.2).

Control plane — the driver's task-assignment, metadata, and lineage traffic; carries no shuffle bytes (I1).

Credit window — the sender-visible limit on in-flight unacknowledged bytes under credit-based flow control (P10).

Dag — the acyclic, topologically-ordered graph of Stages composing a Job (§11.6, I10).

Data plane — the path shuffle bytes actually travel: mapper → Shuffler → reducer (§3).

Delay scheduling — waiting up to locality_delay for a locality-preferred host before falling back (P5, ADR-13).

Determinism contract — the documented (not enforced) requirement that Task::run produce the same output for the same input+config (P13).

External merge sort — a sort algorithm operating on data larger than available memory via sorted runs (spills) merged in passes (§15, Graefe 2006).

Fetch-progress journal — a durable record of which map outputs a reducer has already consumed, enabling mid-merge resumption after a fetch failure (§17.4).

FD budget — the per-task cap on concurrently open file descriptors, driving the tiered-merge design (§4, §15.2).

Heartbeat — the periodic liveness+progress signal an executor sends the driver (§16.2, I3).

HMAC token — the per-job authentication credential used on push-shuffle and S3-backend requests (ADR-19).

Invariant — a system property enforced structurally and checked continuously (§7, I1–I14).

k-way merge — merging k sorted streams into one sorted stream via a min-heap keyed (key, stream_index) (§15.2).

LATE (Longest Approximate Time to End) — the speculative-execution scheduling policy ranking tasks by estimated time-to-completion (§18, Zaharia OSDI 2008).

Lineage — the in-memory record of which map outputs are alive and where, driving re-execution (§11.8, §17).

Locality hint — a task's preferred hosts/racks, derived from input-split metadata (§11.7).

Manifest — the authoritative existence record for shuffle blocks on the push and S3 backends; never inferred by storage listing (P14, I13).

Map output — the per-partition sorted, checksummed, sized record a map task produces (§11.2).

Merge-on-write — the push-shuffle service's technique of sort-merging incoming blocks at ingestion time, keeping the persisted file always sorted (§19.2).

Metadata storm — the M×R (or worse) fetch/file-count explosion pull-based shuffle produces at high mapper×reducer counts (§4, MM5).

Partitioner — the function mapping an encoded key to an output partition index (§11.4).

Progress score — the (progress, progress_rate, estimated_time_to_end) tuple driving LATE's ranking (§18.2).

Push-based shuffle — a shuffle model where mappers push output to a merging service rather than reducers pulling from mappers (§19, ADR-05).

Range partitioner — a partitioner assigning keys to partitions by sorted-boundary comparison, used by TeraSort (§11.4, §23).

Re-execution — recomputing a failed task's output from its inputs, this system's sole fault-tolerance mechanism (P4, §17).

Reduce-stage activation gate — the rule that a reduce stage begins only once every upstream map task has ACKed (I6).

RTO (Recovery Time Objective) — the bounded time a system takes to recover from a named failure class (§4).

Secondary sort — sorting shuffle output by (primary_key, secondary_key) so a reducer can stream ordered values without buffering (§21.2, P7).

Shuffle — the all-to-all (or all-to-subset) data exchange between map and reduce stages, partitioned and sorted (§3).

Shuffler — the trait abstracting shuffle-backend write/read/cleanup (§11.5, P2).

Skew — an uneven distribution of keys/bytes across partitions, producing straggler reducers (§21.6).

Spill — a sorted, optionally combined, on-disk write of a map task's in-memory buffer once it crosses spill_threshold_bytes (§14.2).

Stage — a set of tasks sharing a partitioner/combiner and upstream dependencies within a Job's Dag (§11.6).

Straggler — a task running much slower than its peers due to transient host/network conditions (§18.1).

Task — one unit of work (map or reduce) within a stage; addressed via its winning attempt (§11.3, MM2).

Tiered merge — a k-way merge performed in bounded-fan-in groups when input-stream count exceeds the FD budget (§15.2).

Winning attempt — the first-completing attempt of a task, whose output becomes canonical; all others are cancelled (I2, §18.4).

Zeroize — the Rust crate/trait ensuring secret bytes (auth tokens) are wiped from memory on drop (ADR-22).
