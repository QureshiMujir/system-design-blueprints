33. Mental Models & First Principles

  1. MM1 — Control plane ≠ data plane; conflating them is the scaling wall. Insight: a coordinator that never touches a byte of payload scales with task count, not payload volume. Predicts: any design routing shuffle bytes through the driver hits a wall around single-node NIC bandwidth regardless of cluster size. Bug without it: a "helpful" debug feature that has the driver relay a sample of shuffle bytes for inspection quietly becomes the throughput ceiling. Applies at §3 (I1).
  2. MM2 — A "task" and a "task attempt" are different objects; the address must say which. Insight: TaskId{stage,partition,attempt} names an attempt, not a task; speculative execution and retries are only safe because every attempt has its own identity. Predicts: any scheme that identifies work by (stage,partition) alone will double-count or lose output the first time two attempts of the same task are ever simultaneously alive. Bug without it: exactly the double-counted-speculative-output class (I2). Applies at §11.1, §18.4.
  3. MM3 — Re-execution is checkpointing where the checkpoint is free. Insight: the prior stage's shuffle output already is a checkpoint of that stage's compute; writing a second, dedicated checkpoint duplicates durability spend for no correctness gain, as long as the upstream stage's output survives long enough to be re-read. Predicts: a system that adds explicit task-progress checkpointing on top of this design is paying twice for the same guarantee. Bug without it: over-engineered checkpoint machinery that the RDD paper's cost argument shows is unnecessary. Applies at §17 (P4).
  4. MM4 — The shuffle backend is a storage-tier decision, not a compute decision. Insight: Shuffler (§11.5) is the entire interface; everything backend-specific (sort location, replication, durability window) lives behind it, and the executor's compute logic is backend-agnostic by construction. Predicts: adding a fourth backend (e.g. RDMA-NVMe, §37) requires zero executor-logic changes, only a new Shuffler impl. Bug without it: backend-specific branches leaking into map_runner/reduce_runner, the exact mistake pre-2020 Spark made hard-coding local disk. Applies at §3, §11.5.
  5. MM5 — M×R is a hidden quadratic; push-based merge trades it for M+R. Insight: pull- based shuffle's fetch count is bounded by mappers × reducers² in the worst pathological case and M×R in the common case; a push service that merges per-partition collapses the reducer's fetch count to O(1) per partition regardless of M. Predicts: pull-based shuffle's fetch-metadata cost, not bandwidth, becomes the bottleneck first at high (M,R) — exactly what Magnet measured. Bug without it: teams "add more executors" to fix a metadata-storm-caused slowdown and it doesn't help. Applies at §19.1, Capacity Model (§35).
  6. MM6 — A manifest is a lock-free existence proof; a directory listing is a race. Insight: object storage offers no transactional multi-object write, so "does this data exist" must be answered by a single authoritative record (the manifest), never by enumerating storage. Predicts: any shuffle-on-object-store design that lists the bucket to discover blocks will exhibit intermittent, hard-to-reproduce partial-read bugs under concurrent writers. Bug without it: the list-and-infer anti-pattern (P14, I13, documented as the root cause of half of real shuffle-on-S3 incidents). Applies at §20.5.
  7. MM7 — Speculation is a monitor, not a scheduler feature. Insight: LATE observes progress and emits launch requests; it never decides where to run them — that's still the assignment scheduler's job. Predicts: a design that couples speculation logic into the assignment scheduler will need a rewrite the first time it wants a different straggler policy (e.g. Ananthanarayanan's Attack of the Clones aggressive-but-cheap speculation). Bug without it: a monolithic scheduler where changing the speculative policy risks the (unrelated) locality/resource logic. Applies at §11.7, §18.
  8. MM8 — Associativity is a proof obligation the type system cannot discharge. Insight: Combiner (§11.4) can only state the associative+commutative requirement (I8); Rust's type system has no way to verify a closure is associative. Predicts: every combiner-related production bug traces to a violated, undetected assumption, not a library defect. Bug without it: naive average = sum/count combiners silently producing fan-in-dependent results (§21.6). Applies at §6 (P6), §21.

Glossary (§39) · 46 terms · site-wide glossary

Attempt
one launched execution of a task, identified by TaskId.attempt; distinct from the logical "task" it belongs to (I2, MM2).
Backpressure
a receiver-driven signal limiting a sender's send rate; implemented here via credit-based flow control (P10, I11).
BLAKE3
the cryptographic hash function used for shuffle-block checksums (I7).
Bucket prefix sharding
splitting an object-store key space across multiple prefixes to spread PUT-rate-limit load (§20.2, §35).
Chaos daemon
the injected-fault process driving the 30-day soak (§24.2).
Checksum
a per-block integrity value verified on read to detect silent corruption (I7, T1).
Combiner
a user-supplied, associative-and-commutative function that reduces map output volume before shuffle (§11.4, P6, I8).
Consistent hashing
the technique routing a (job_id, partition) pair to a specific push-shuffle service node while minimizing rebalancing on node add/remove (§19.2).
Control plane
the driver's task-assignment, metadata, and lineage traffic; carries no shuffle bytes (I1).
Credit window
the sender-visible limit on in-flight unacknowledged bytes under credit-based flow control (P10).
Dag
the acyclic, topologically-ordered graph of Stages composing a Job (§11.6, I10).
Data plane
the path shuffle bytes actually travel: mapper → Shuffler → reducer (§3).
Delay scheduling
waiting up to locality_delay for a locality-preferred host before falling back (P5, ADR-13).
Determinism contract
the documented (not enforced) requirement that Task::run produce the same output for the same input+config (P13).
External merge sort
a sort algorithm operating on data larger than available memory via sorted runs (spills) merged in passes (§15, Graefe 2006).
Fetch-progress journal
a durable record of which map outputs a reducer has already consumed, enabling mid-merge resumption after a fetch failure (§17.4).
FD budget
the per-task cap on concurrently open file descriptors, driving the tiered-merge design (§4, §15.2).
Heartbeat
the periodic liveness+progress signal an executor sends the driver (§16.2, I3).
HMAC token
the per-job authentication credential used on push-shuffle and S3-backend requests (ADR-19).
Invariant
a system property enforced structurally and checked continuously (§7, I1–I14).
k-way merge
merging k sorted streams into one sorted stream via a min-heap keyed (key, stream_index) (§15.2).
LATE (Longest Approximate Time to End)
the speculative-execution scheduling policy ranking tasks by estimated time-to-completion (§18, Zaharia OSDI 2008).
Lineage
the in-memory record of which map outputs are alive and where, driving re-execution (§11.8, §17).
Locality hint
a task's preferred hosts/racks, derived from input-split metadata (§11.7).
Manifest
the authoritative existence record for shuffle blocks on the push and S3 backends; never inferred by storage listing (P14, I13).
Map output
the per-partition sorted, checksummed, sized record a map task produces (§11.2).
Merge-on-write
the push-shuffle service's technique of sort-merging incoming blocks at ingestion time, keeping the persisted file always sorted (§19.2).
Metadata storm
the M×R (or worse) fetch/file-count explosion pull-based shuffle produces at high mapper×reducer counts (§4, MM5).
Partitioner
the function mapping an encoded key to an output partition index (§11.4).
Progress score
the (progress, progress_rate, estimated_time_to_end) tuple driving LATE's ranking (§18.2).
Push-based shuffle
a shuffle model where mappers push output to a merging service rather than reducers pulling from mappers (§19, ADR-05).
Range partitioner
a partitioner assigning keys to partitions by sorted-boundary comparison, used by TeraSort (§11.4, §23).
Re-execution
recomputing a failed task's output from its inputs, this system's sole fault-tolerance mechanism (P4, §17).
Reduce-stage activation gate
the rule that a reduce stage begins only once every upstream map task has ACKed (I6).
RTO (Recovery Time Objective)
the bounded time a system takes to recover from a named failure class (§4).
Secondary sort
sorting shuffle output by (primary_key, secondary_key) so a reducer can stream ordered values without buffering (§21.2, P7).
Shuffle
the all-to-all (or all-to-subset) data exchange between map and reduce stages, partitioned and sorted (§3).
Shuffler
the trait abstracting shuffle-backend write/read/cleanup (§11.5, P2).
Skew
an uneven distribution of keys/bytes across partitions, producing straggler reducers (§21.6).
Spill
a sorted, optionally combined, on-disk write of a map task's in-memory buffer once it crosses spill_threshold_bytes (§14.2).
Stage
a set of tasks sharing a partitioner/combiner and upstream dependencies within a Job's Dag (§11.6).
Straggler
a task running much slower than its peers due to transient host/network conditions (§18.1).
Task
one unit of work (map or reduce) within a stage; addressed via its winning attempt (§11.3, MM2).
Tiered merge
a k-way merge performed in bounded-fan-in groups when input-stream count exceeds the FD budget (§15.2).
Winning attempt
the first-completing attempt of a task, whose output becomes canonical; all others are cancelled (I2, §18.4).
Zeroize
the Rust crate/trait ensuring secret bytes (auth tokens) are wiped from memory on drop (ADR-22). ---
