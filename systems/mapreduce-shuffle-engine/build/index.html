⬜ Phase 0 — Repository Skeleton & Correctness Kernel (Week 1) §12

Objectives

Stand up the full repo (§10), governance docs, CI, and a single-process WordCount smoke test using an in-memory shuffle stub. Nothing here touches real shuffle I/O (P1 scope starts Phase 2); the goal is that the next twelve phases land on a clean, tested skeleton.

Deliverable

make bootstrap && make build && make test all exit 0; tests/wordcount_smoke.rs runs the example end-to-end and asserts byte-equality against a checked-in fixture.

Acceptance

make test passes with ≥1 green integration test (wordcount_smoke); ADR-01, ADR-02, ADR-03, ADR-04, ADR-22 committed under docs/adr/; repo tree diff against §10 is empty for all Phase-0-owned paths.

Fixtures
Fixture Purpose Expected Output
wordcount_smoke.rs end-to-end 4-map/2-reduce byte-equality matches examples/data/wordcount/expected.txt exactly
cyclic_job_rejected.rs negative test, I10 Error::CyclicJob returned at submit
Pitfalls
  • Letting the in-memory Shuffler stub accrete sort/spill/compression features — Phase 2 replaces it wholesale; scope creep here wastes the phase boundary's test value.
  • Unicode-normalization brittleness in a HashMap<String,u64> reference counter — use ASCII-only fixture text.
  • Treating the Phase-0 driver/executor split as a network boundary too early — it is in-process until Phase 4 (§16); over-engineering the RPC layer now is wasted work.

⬜ Phase 1 — DAG Job/Stage/Task Model (Weeks 1–2) §13

Objectives

Implement Dag<Stage> (§11.6), stage activation, and task materialization; prove the model on a join-shaped (two map stages → one reduce stage) topology.

Deliverable

A three-stage join Job (two map stages feeding one reduce stage) materializes the expected task graph and executes correctly against the Phase-0 in-memory shuffler.

Acceptance

Property test (proptest): for any acyclic stage graph up to 50 stages × 100 partitions/stage, materialization order matches the DAG's topological order exactly (I10); negative test: a hand-built cyclic graph is rejected with Error::CyclicJob in <1 ms.

Fixtures
Fixture Purpose Expected Output
dag_join_topology.rs 2-map + 1-reduce join materialization task count = sum(input_splits) + num_partitions
dag_cyclic_rejected.rs I10 negative case Error::CyclicJob, no tasks materialized
dag_random_50stage.rs (proptest) topological-order correctness at scale materialization order == topo_order()
Pitfalls
  • Stage activation via "all upstream complete" is correct but coarse — partial stage activation (consuming a subset of upstream partitions early, as some Spark configs do) is PhaseDeferred("§38"), not built here.
  • Conflating TaskId.partition (input-split index for a map task) with the output partition index in MapOutput::partition_sizes (I9) — the type system does not catch this; it is the single most-repeated bug at this layer across real implementations.

⬜ Phase 2 — Map Executor & Sort-Based Local Shuffle Write (Weeks 2–3) §14

Objectives

Replace the Phase-0 in-memory shuffler with the real mrs-shuffle-local backend (ADR-04): map-side sort, spill, optional combine, and a durable per-mapper consolidated file + index.

Deliverable

WordCount on mrs-shuffle-local produces a per-mapper .data+.index pair; manual inspection of the index confirms partition-offset layout matches the writer contract.

Acceptance

A Combiner summing per-key counts reduces bytes written by ≥ 60% on the WordCount corpus (measured, not asserted); property test: for any random input split, the merged file's per-partition records equal the sorted union of map-emitted records modulo the combiner (I4, I8); fsync-before-ACK verified by fault-injecting a crash between write and ACK (see §14.9).

Fixtures
Fixture Purpose Expected Output
local_shuffle_index_layout.rs index triple correctness offsets sum to file length per partition
combiner_volume_reduction.rs P6/I8 volume check bytes_written_with_combiner ≤ 0.4 × without
spill_sort_property.rs (proptest) I4 every spill internally sorted by (partition,key)
Pitfalls
  • Spilling without sorting first (§8.1) — the writer assumes "I'll sort at merge time" and the merger discovers unsorted 256 MiB spills it cannot k-way merge (I4 exists exactly to prevent this).
  • Merge-to-single-file transiently doubles disk footprint — spill directory needs ≥2× the spilled volume free (§4 disk amplification row).
  • spill_threshold_bytes too small → metadata storm of tiny spill files; too large → map task OOMs. 256 MiB default is a starting point, not a universal constant.

⬜ Phase 3 — Reduce Executor & External Merge Sort (Weeks 3–4) §15

Objectives

Implement the reduce-side k-way external merge across all winning map-attempt streams for a partition, with tiered fan-in above the FD budget (§4), and drive TeraSort-scale correctness on a single host.

Deliverable

WordCount (Phase-2 mapper + Phase-3 reducer) produces correct per-word counts at 100 MiB, 1 GiB, and 10 GiB input scales; a 100 GiB TeraSort-shaped run (100 maps × 50 reduces) completes correctly on one host with sufficient disk.

Acceptance

Property test: for any randomly partitioned input, concatenated reduce-partition output (in partition order) equals the global sort of the input; 100 GiB single-host TeraSort- shaped run completes with zero valsort-equivalent ordering violations; tiered-merge FD usage stays ≤ 256 concurrent open files regardless of mapper fan-in (measured via lsof-equivalent instrumentation).

Fixtures
Fixture Purpose Expected Output
kway_merge_stability.rs stable tie-break correctness duplicate keys preserve stream-index order
tiered_merge_fd_cap.rs FD budget enforcement open-FD high-water-mark ≤ 256
reduce_100gib_single_host.rs scale correctness output totally ordered, record count matches input
Pitfalls
  • A non-stable k-way merge heap breaks secondary sort (§21.2) even though it is correct for plain keyed reduction — always key the heap (key, stream_index).
  • Tiered-merge tier boundaries (every 256 streams) transiently double on-disk footprint per tier — use tempfile dirs with guaranteed cleanup on task exit (incl. panic).
  • M × T open FDs (M mappers × T concurrent reduce tasks per host) exhausts descriptors fast without the RLIMIT_NOFILE raise + tiered cap acting together.

⬜ Phase 4 — Driver & Locality/Resource-Aware Scheduler (Weeks 4–5) §16

Objectives

Promote the driver-executor split from in-process (Phase 0) to a real network boundary (gRPC, ADR-18); implement delay-scheduled locality preference (P5) and resource-aware bin-packing (P8).

Deliverable

A 1 GiB WordCount on a 3-host cluster (driver + 3 executors, one mapper's input local per host) achieves measured node-locality on the map stage.

Acceptance

Node-locality rate ≥ 90% (M8) on the 3-host WordCount fixture; property test: for randomized task placement + locality preferences, scheduler locality-rate is within 5% of a brute-force-computed optimum; negative test: an over-resourced task submission is rejected with Error::ResourceUnsatisfiable at submit, never surfacing as a runtime OOM.

Fixtures
Fixture Purpose Expected Output
locality.node_local_rate measures node-locality on 3-host WordCount ≥ 90% over 100 runs
locality.delay_scheduling delay-scheduling vs. brute-force optimum within 5%
resource_unsatisfiable_rejected.rs submit-time resource check Error::ResourceUnsatisfiable, zero tasks launched
Pitfalls
  • locality_delay = 0 collapses immediately to any-host, destroying locality rates; too large stalls the scheduler — 3,000 ms (Spark's inherited default) is the starting point.
  • Empty LocalityHint (S3 input, or a reduce task whose upstream wrote nowhere specific) must be treated as "no preference, proceed now," never "delay forever."
  • Executors that over-report free capacity (a runtime "free" per the scheduler's view but actually paging) — documented known limitation (docs/runbooks/stuck-stage.md, FM- adjacent), not solved at this phase.

⬜ Phase 5 — Fault Tolerance via Re-Execution & Lineage (Weeks 5–6) §17

Objectives

Implement the four failure-mode taxonomy (§8.5) and lineage-driven re-execution (P4); no checkpointing is introduced — recomputation from the prior stage's shuffle output is the sole recovery mechanism.

Deliverable

A kill -9 of one of three executors mid-WordCount-job results in job completion with at most one stage re-execution and total wall time within the RTO bound (§4).

Acceptance

Executor-kill RTO ≤ 2× no-failure wall time (§4 RTO row, fault.executor_kill bucket); fault-injection property test: 100 runs, each randomly killing 1–3 executors, every run terminates correctly (zero data loss, correct final output); negative test: a documented non-deterministic user map function is asserted to fail the re-execution-equivalence property, with the failure mode and constraint recorded, not silently tolerated (P13).

Fixtures
Fixture Purpose Expected Output
fault.executor_kill kill 1 of 3 executors mid-run job completes, wall time ≤ 2× baseline
fault.random_1to3_kill (100 runs) property test over kill counts every run terminates correctly
fault.nondeterministic_canary P13 documented failure equivalence property fails as documented, not silently
Pitfalls
  • host_to_outputs is the load-bearing structure (§11.8) — an off-by-one in the executor-lost path either duplicates a map task (new attempt runs beside an already- completed one) or misses one (lineage thinks output is still alive on a dead host).
  • Resuming a reducer mid-fetch needs a durable journal; an executor crash during the journal write loses resumption state and the reducer restarts from zero — acceptable, documented, not silently swallowed.
  • A reducer that has started emitting output cannot resume mid-fetch — restart fully; the "partial-reducer-resume" optimization is explicitly deferred (§38), not attempted here.

⬜ Phase 6 — Speculative Execution: the LATE Scheduler (Weeks 6–7) §18

Objectives

Implement Zaharia's LATE (Longest Approximate Time to End) scheduler (OSDI 2008, applied per P3, ADR-11) as a passive straggler monitor beside the assignment scheduler.

Deliverable

A controlled-straggler test (one map task delayed 5× the median) completes within the RTO bound (§4, M7); the speculative-execution conformance bucket passes across 100 synthetic- straggler runs.

Acceptance

Wall time ≤ 1.5 × median + minimum_task_age on the 5×-straggler fixture (M7); ≥ 30% wall- time improvement across 100 synthetic-straggler runs (speculation.straggler bucket); property test: the scheduler never exceeds max_speculative_per_stage launches per stage; speculation.no_storm fixture: a stagger-free job launches zero speculative attempts.

Fixtures
Fixture Purpose Expected Output
speculation.straggler 5× delayed map task wall time ≤ 1.5× median + 30 s
speculation.no_storm no stragglers present zero speculative attempts launched
speculation.cap_respected (proptest) I-adjacent cap check launches ≤ max_speculative_per_stage always
Pitfalls
  • Speculative execution without idempotent tasks duplicates side effects — documented at Task::run (P13); the library cannot enforce it.
  • "Predict which attempt finishes first" smarter-than-first-wins policies (rejected per Ananthanarayanan NSDI 2013, applied per §5) can kill the eventually-faster attempt — first-completion-wins only, never a predictive kill.
  • slow_task_progress_threshold mistuned high speculates merely-slow-starting tasks; mistuned low never speculates — 0.25 is the LATE paper's recommendation, not a universal constant.
  • Progress reporting faster than 1 Hz floods the heartbeat channel, creating control-plane backpressure (I1-adjacent concern) — don't.

⬜ Phase 7 — Push-Based Shuffle Service (Magnet-Style) (Weeks 7–9) §19

Objectives

Implement mrs-shuffle-push (ADR-05): mappers push per-partition blocks to a service tier that merges on write, cutting per-reducer fetch RPCs from O(M) to O(1) (Shen VLDB 2020, applied per §5, M6).

Deliverable

WordCount-on-push-shuffle produces byte-identical output to WordCount-on-local-shuffle on the same input; a 100 GB push-shuffle TeraSort-shaped run completes within the bound below.

Acceptance

Byte-identical output vs. local backend (equivalence.local_vs_push); wall time ≤ 1.5× the local-shuffle equivalent on a 3-node cluster; per-reducer fetch RPC count ≤ 2 (M6, primary

  • fallback) vs. M for the local backend; a service-node kill mid-run completes correctly via the secondary replica.
Fixtures
Fixture Purpose Expected Output
equivalence.local_vs_push cross-backend byte-equality identical output, WordCount + TeraSort-shaped
push.fetch_rpc_count M6 measurement ≤ 2 RPCs/reducer at 10K-mapper scale
push.service_kill_failover secondary-replica correctness job completes, output correct
Pitfalls
  • A reducer fetching before every map has pushed AND been merged returns a partial result the merge step cannot detect — the reduce-stage-activation gate (I6, §19.2) is the only correct fix; do not weaken it for latency.
  • Cascading retries: a push failing on service-node OOM triggers a map retry, which re-pushes to the same overloaded node, repeating — mitigate with exponential backoff on PushRequest plus a service-side circuit breaker.
  • Consistent-hashing on partition alone (not (job_id, partition)) produces hot service nodes under a skewed partitioner — hash the pair (§19.2), not the partition alone.

⬜ Phase 8 — Disaggregated Shuffle on Object Storage (Cosco-Style) (Weeks 9–11) §20

Objectives

Implement mrs-shuffle-s3 (ADR-06): shuffle data lands on durable, autoscaling, multi-tenant object storage, making executors stateless against pod restarts, autoscaling downscale, and spot preemption (P9).

Deliverable

WordCount-on-S3-shuffle byte-matches both the local- and push-backend runs on the same input; a kill -9 mid-job re-reads inputs from S3 and completes within the RTO bound.

Acceptance

Byte-identical output vs. local and push backends (equivalence.local_vs_s3, equivalence.push_vs_s3); 100 GB TeraSort-shaped run ≤ 2.5× local-shuffle wall time (object-store RTT is the documented, accepted cost, §4); executor-kill RTO ≤ 1.5× no- failure wall time — better than local backend's 1.8× under the same fault (P9's concrete payoff); cleanup_stage verified empty via a post-cleanup bucket listing.

Fixtures
Fixture Purpose Expected Output
equivalence.local_vs_s3 cross-backend byte-equality identical output
equivalence.push_vs_s3 cross-backend byte-equality identical output
s3.executor_kill_rto disaggregation failure-RTO payoff ≤ 1.5× baseline, beats local's 1.8×
s3.cleanup_verified post-job bucket state zero objects under job prefix
Pitfalls
  • PUT amplification: 10⁴ maps × 10⁴ partitions = 10⁸ PUTs at full scale, hitting S3's default per-prefix rate limit (3,500 req/s) — mitigate via prefix sharding (§20.2).
  • Manifest race: a map's PUT succeeds but the manifest update fails — reducer treats a manifest-absent key as not-yet-available and waits (never falls back to LIST, I13); the driver retries the manifest write.
  • Multipart-upload abort leak: a crashed map task's incomplete multipart upload costs money indefinitely — a bucket lifecycle policy aborting incomplete uploads after 24h is mandatory, not optional.
  • List-versus-manifest divergence: never implement read_partition as "list the bucket prefix" — the manifest is the sole existence authority (P14, I13).

⬜ Phase 9 — Combiner, Secondary Sort, Custom Partitioner (Weeks 11–12) §21

Objectives

Complete the user-facing tuning surface: the Combiner contract (P6), secondary sort (P7), and the open Partitioner trait (§11.4) for custom bucketing strategies.

Deliverable

A Combiner for WordCount reduces shuffle volume by ≥ 60% (re-verified end-to-end, extends §14.4's map-side-only measurement); a secondary-sort example sorts (user_id, timestamp) logs and verifies chronological order per user_id without reducer-side buffering; a geo-bucket custom partitioner achieves balanced partition sizes.

Acceptance

Combiner: ≥ 60% shuffle-byte reduction on the WordCount conformance corpus (M-referenced, extends M-comb from §14); secondary sort: 100% of user_id groups verified in strict timestamp order across the synthetic corpus with zero reducer-side buffering measured; custom partitioner: max partition size ≤ 2× the mean on the geo conformance corpus.

Fixtures
Fixture Purpose Expected Output
correctness.combiner differential fan-in test (I8) 4 configs produce identical output
correctness.secondary_sort chronological order per user zero out-of-order pairs, zero buffering
custom_partitioner.geo_balance partition-size balance max ≤ 2× mean
Pitfalls
  • Non-associative combiner: average = sum/count combined naively is not associative; correct form is (sum,count) pairs combined associatively, divided only at the reducer (I8) — the library cannot detect this at runtime, only document it.
  • Secondary-sort comparator/partitioner mismatch: the secondary_comparator must agree with the partitioner's implied bucket ordering, or the reducer's assumed order is silently wrong — the §21.2 lint catches the common cases, not all.
  • Skewed custom partitioner (e.g. one tenant = 90% of data): produces straggler reducers the speculative scheduler (§18) cannot help with (the straggler has 10× the data, not merely bad luck) — mitigate via range partitioning with sampling or the deferred AQE skew-split (PhaseDeferred("§38")).

⬜ Phase 10 — Performance Hardening (Weeks 12–14) §22

Objectives

Close the gap between "correct" (Phases 0–9) and "fast" (§4 targets): batching/pipelining, compression tuning, zero-copy network paths, NUMA-aware sort, SIMD sort.

Deliverable

TeraSort 1 TB on a 16-node cluster completes in ≤ 30 min (M2) on the local backend; a criterion benchmark suite captures per-phase cost (map-sort, spill, shuffle-write, shuffle-fetch, reduce-merge, reduce-fn).

Acceptance

TeraSort 1 TB wall time ≤ 30 min (M2); TeraSort 100 GB shuffle throughput ≥ 200 MB/s/node at the NIC (M3); WordCount on the Project Gutenberg corpus ≥ 80% of peak measured network throughput between executors and shuffle service; criterion suite committed and gated in CI for regression (P12, §31).

Fixtures
Fixture Purpose Expected Output
perf.terasort_1tb_16node M2 gate ≤ 30 min
perf.shuffle_throughput_100gb M3 gate ≥ 200 MB/s/node at NIC
perf.criterion_regression per-phase cost regression gate no phase regresses > 10% vs. baseline
Pitfalls
  • LZ4 on already-compressed input (e.g. Parquet-encoded records) wastes CPU for no size win — document the input-encoding assumption at the Combiner/Partitioner trait boundary.
  • sendfile naming/semantics differ subtly Linux vs. BSD/macOS despite similar man pages — feature-gate via nix::sys::sendfile per platform.
  • NUMA-pinning a single-socket host is a no-op, not an error — do not fail executor startup if numactl reports one node.
  • SIMD radix sort past the L3-cache-fit boundary is memory-bandwidth-bound and gains nothing over pdqsort — don't over-tune based on microbenchmarks alone.

⬜ Phase 11 — TeraSort Benchmark Gate (Weeks 14–15) §23

Objectives

Wire the public Sort Benchmark (sortbenchmark.org) as the canonical large-data correctness + performance gate, using gensort/valsort (applied per §5 RFCs/Specs).

Deliverable

TeraSort 100 GB completes correctly on a 3-node cluster ≤ 5 min (M1); TeraSort 1 TB completes correctly on a 16-node cluster ≤ 30 min (M2, re-verified from §22 at full gate strictness including valsort).

Acceptance

valsort reports zero errors on both the 100 GB and 1 TB runs; M1 (≤5 min/100GB/3-node) and M2 (≤30 min/1TB/16-node) both met; the nightly CI job posts wall time to the dashboard with no manual step.

Fixtures
Fixture Purpose Expected Output
correctness.terasort_100gb valsort gate, 3-node zero valsort errors, ≤ 5 min
correctness.terasort_1tb valsort gate, 16-node zero valsort errors, ≤ 30 min
terasort.sample_uniformity range-partitioner sampling check split points within 5% of true quantiles
Pitfalls
  • A split-point sample drawn from only the start of the input file gives a biased range partition — read uniformly across the whole input for the sample.
  • valsort expects the canonical gensort fixed-width binary record format — deviating (e.g. newline-delimited text) breaks the gate silently until valsort itself errors.
  • TeraSort is a "no compute" benchmark (100% shuffle) — it is the right gate for shuffle performance and the wrong one for map/reduce compute throughput; WordCount (§14/§21) complements it.

⬜ Phase 12 — 30-Day Chaos Soak (Continuous, Operational-Readiness Gate) §24

Objectives

Run the full system continuously under injected chaos for 30 days as the terminal operational-readiness gate (P12, ADR-21) before any deployment is considered production- ready.

Deliverable

audits/chaos/canary-30d-<sha>.md — a signed report covering completion rate, panic count, p99 wall-time variance, and every chaos-daemon action taken across the 30 days.

Acceptance

Zero correctness regressions (every job that should complete does, with correct output); zero panics in mrs-driver/mrs-executor/mrs-shuffle-push (M11 extended to 30 days as M12); job completion rate ≥ 99% (M12); p99 job wall-time variance ≤ 2× the chaos-free baseline (M12).

Fixtures
Fixture Purpose Expected Output
chaos.30d_soak full 30-day continuous run zero panics, ≥ 99% completion
chaos.backend_rotation_equivalence cross-backend output equality under chaos byte-identical per rotated triple
chaos.cleanup_no_leak 30-day state-accumulation check disk/object-store usage bounded, sweeper keeps pace
Pitfalls
  • The chaos daemon over-killing driver-eligible nodes stalls the cluster entirely — the ≤1-kill-per-hour cap on driver-eligible nodes (§24.2) is load-bearing, not a suggestion.
  • A leak invisible in 24 hours (log growth, orphaned S3 objects, .tmp spill remnants) shows up only at 30-day scale — the sweeper (§20.2) must be continuously verified, not assumed to keep working.
  • Performance-regression detection across 30 days is confounded by kernel updates, cloud hardware refreshes, or chaos-policy tuning — the baseline must be explicitly regenerated whenever any of those change (docs/runbooks/triage.md).
