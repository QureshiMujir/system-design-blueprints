143 — SSA-Based Optimizer

Project Number: 143

Project Name: SSA-Based Optimizer

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a mid-level, SSA-based optimizer library in Rust: a program takes an already-lowered control-flow-graph IR, converts it to pruned SSA form, runs a fixed sequence of SSA-based optimization passes under a pass manager with analysis caching, and lowers back out of SSA into a virtual-register form consumable by a register allocator/backend — with every stage bounded by an explicit correctness contract (a verifier) and every optimization proven semantics-preserving by differential testing against a reference interpreter, plus a translation-validation smoke check on locked fixtures.

In-scope Phase-0 deliverable (crates):

  1. ssa-ir — CFG, BasicBlock, Instruction, Value, typed operand model.
  2. ssa-verifier — linear-time structural + dominance + type invariant checker.
  3. ssa-domtree — dominator tree + dominance frontier construction.
  4. ssa-construct — phi placement (pruned) + variable renaming.
  5. ssa-interp — reference interpreter (differential-testing oracle).
  6. ssa-fixtures — the conformance-fixture corpus and loader.

System boundaries:

  • Provides: SSA construction, a fixed catalogue of SSA-based scalar optimizations (§8), an analysis-manager/pass-pipeline framework, out-of-SSA translation, a differential-testing harness, a translation-validation smoke check.
  • Delegates: front-end lowering (parsing, type-checking) to the caller; register allocation, instruction selection, and machine-code emission to a downstream backend (out of scope, consumes this project's out-of-SSA output).
  • Does NOT provide: a source-language front-end, a JIT execution engine, a full formal-verification pipeline (translation validation here is a bounded smoke check, not a proof), auto-vectorization, interprocedural optimization (no call-graph SCC inliner in Phase 0–9; see Deferred Features Register).

Non-goals: whole-program interprocedural optimization; a garbage collector or runtime; a hardware backend; supporting an SSA dialect other than the one-IR model defined in §8 (no sea-of-nodes, no block-parameter form — see Alternative Architectures for why those were rejected).

Deployment model: an embeddable Rust library (cdylib/rlib), invoked in-process by a host compiler; no network service, no persistent daemon; single-process, single-invocation-per- compilation-unit.

Target users/operators: compiler engineers embedding this optimizer in a front-end; the "operator" at runtime is the CI pipeline that runs the conformance and fuzz buckets on every commit.

What later phases unlock: Phase 3 (SSA construction) unlocks every optimization pass in Phases 5–8; Phase 4 (analysis manager) unlocks safe pass composition and future interprocedural work; Phase 9 (out-of-SSA + verification) unlocks integration with a real register allocator and closes the correctness loop end-to-end.

Recommended language: Rust (stable, MSRV 1.78). Rationale: arena/slot-map-friendly ownership model matches IR-graph mutation patterns without a GC; enum + exhaustive match gives compile-time-checked opcode coverage (a pass that forgets an opcode fails to compile); cargo fuzz/proptest are first-class for the differential/fuzz harness (§26); no runtime GC pause risk in a component meant to run inside a JIT's hot compile path. Rejected: C++ (LLVM's own language) — richer inheritance-based IR extensibility, but manual memory management around graph mutation is the single largest historical miscompile/UAF source in LLVM's own bug tracker; OCaml — excellent for correctness-carrying transforms, but poor ecosystem fit for a library meant to slot into a Rust/C toolchain and weaker SIMD-adjacent performance tooling; Zig — no mature cargo fuzz-equivalent differential/property-testing ecosystem yet.

Prerequisites: control-flow graphs and reducibility; lattice theory basics (meet-semilattices, fixpoints) for dataflow analysis; dominance and dominance frontiers; graph algorithms (DFS numbering, Tarjan SCC); basic type systems for a typed IR.

Estimated timeline: Phase 0 (repo skeleton + correctness kernel) — 3 weeks. Full system (Phases 0–9, all optimizations + out-of-SSA + verification harness) — 7 months at one senior compiler engineer full-time.

Deferred features (flagged PhaseDeferred("§N.s"), registered in the Deferred Features Register): interprocedural constant propagation PhaseDeferred("§35"); a CGSCC-ordered inliner PhaseDeferred("§35"); auto-vectorization prep PhaseDeferred("§35"); profile-guided pass ordering PhaseDeferred("§35"); incremental dominator-tree update PhaseDeferred("§35").

2. Why Build This

Unique systems knowledge it teaches: how a textbook "dominance frontier" becomes a linear-time algorithm under Cooper-Harvey-Kennedy iteration; how a "prove semantics preservation" claim is actually operationalized (differential testing plus a translation-validation smoke check, not a hand-wave); how analysis caching/invalidation prevents the single most common correctness bug class in production optimizers (stale-analysis miscompiles); how out-of-SSA translation is genuinely hard (the swap problem, the lost-copy problem) and why naive phi-to-copy lowering silently miscompiles.

Why it matters architecturally/historically: SSA form (Cytron et al. 1991) is the single most consequential IR design of the last four decades of compiler construction — it turned dataflow analysis from a general fixpoint problem into a sparse, def-use-graph-local one, and every mainstream optimizing compiler built after roughly 1995 (GCC's tree-ssa rewrite, LLVM from inception, V8's TurboFan, Cranelift) is either literally SSA or SSA-isomorphic (sea-of-nodes, block-parameters).

Engineering muscles it builds: reading and implementing a dense algorithms paper (Cytron et al.) correctly; building a verifier as the load-bearing correctness mechanism rather than an afterthought; treating "this pass preserves analysis X" as a machine-checked contract, not a comment; building differential-testing infrastructure that catches miscompiles a unit-test suite structurally cannot.

Concrete cross-links to sibling systems: the analysis-manager/pass-pipeline design mirrors LLVM's PassManager/AnalysisManager split; the phi-placement algorithm is the direct ancestor of GCC's tree-ssa phi insertion; the out-of-SSA phase is the direct counterpart of Cranelift's register-allocator-facing lowering and of sea-of-nodes compilers' phi elimination.

Calibration value: an engineer who ships this system correctly (verifier-clean, differential-tested, translation-validated) has calibrated proof that they can be trusted with a real compiler backend's optimizer team — the failure modes here (stale analysis, swap/lost-copy, dominance violations) are exactly the failure modes that cause production miscompiles at that scale.

What Mastery Looks Like:

  • Derive dominance frontiers from first principles and explain why the Cooper-Harvey-Kennedy iterative algorithm is preferred over textbook Lengauer-Tarjan for JIT-latency-sensitive code — §14 (Phase 2).
  • Implement pruned SSA construction (phi placement bounded to the iterated dominance frontier of actual definition sites) and explain the prune-vs-maximal tradeoff — §15 (Phase 3).
  • Explain why an AnalysisManager with explicit PreservedAnalyses declarations exists and name the exact bug class it prevents — §16 (Phase 4).
  • Trace a value through SCCP's three-valued lattice across a loop back-edge and explain why the sparse worklist beats the classical dense iterative dataflow algorithm — §17 (Phase 5).
  • Explain why naive SSA destruction miscompiles a value swap and name the two specific bugs (lost-copy, swap) that Sreedhar-Ju-Gillies and Boissinot et al. exist to fix — §21 (Phase 9).
  • Design a translation-validation smoke check and explain precisely what it does and does not prove relative to a full formal proof — §21 (Phase 9), §26.

Caller/Front-End: the only external interface; supplies a well-typed but not-yet-verified Module via the IrBuilder cursor API (§11) — this project owns nothing upstream of this box. Module/Function/CFG: the single in-memory representation every pass reads and writes (P8, one-IR); no hidden secondary IR ever exists downstream. Verifier (pre-SSA): the entry gate — a Module that fails I1–I14 here never reaches a pass (P1). Dominator Tree + DF: rebuilt fresh whenever CFG shape changes (ADR-09); the only structure SSA construction and later loop analyses depend on. SSA Construction: the phase boundary between "arbitrary CFG with non-SSA temporaries" and "pruned SSA" — every pass after this box assumes I1–I5 hold. Analysis Manager: mediates every analysis request from every pass; owns the invalidation graph (I9, P3). Pass Pipeline: a fixed, versioned sequence (P7) — not a runtime DSL — of the five scalar optimizations this project ships. Verifier (post-pass): runs after every single pass in debug builds, once at exit in release (P1). Out-of-SSA / Phi Destruct: the last representation change before backend handoff; the phase where I12 (congruence-class integrity) is the binding correctness contract. Backend handoff: out of scope — a register allocator downstream consumes the virtual-register-form output. The side harness boxes are not on the control-flow path; they consume IR snapshots captured at every pipeline stage and are the truth source for semantic (not merely structural) correctness (P10).

Trust boundary: none beyond process boundary — single untrusted input is the incoming Module from the front-end, validated at the pre-SSA verifier gate. Concurrency boundary: single- threaded per-Function pass execution; Module-level parallelism is across independent Functions only (rayon, ADR-12, §4). Persistence boundary: none — in-memory only in Phase 0–9 (ADR-05); no serialization boundary exists yet. Protocol boundary: none — in-process API only, no RPC surface (ADR-06 networking row, §9).

6. Design Principles

  1. P1 — Verifier-first. Rule: no IR mutation point ships without a corresponding named invariant (I1–I14) it must preserve. Tradeoff: every new opcode or pass requires a verifier update before merge — slows initial pass authoring. Operational implication: CI blocks any PR touching ssa-ir without a corresponding verifier-fixture diff. Violation consequence: silent miscompiles surface only as downstream test flakiness, often attributed to the wrong pass.
  2. P2 — Explicit phi nodes, not block parameters. Rule: control-flow merges are Phi instructions local to the destination block, never block-declared parameters. Tradeoff: destination-local ergonomics for pass writers vs. Cranelift's source-local block-parameter form. Operational implication: every pass mutating predecessors must keep phi incoming-lists in lockstep (I3). Violation consequence: a phi/predecessor mismatch is silent until I3's check fires, or worse, a wrong value is read at runtime.
  3. P3 — Analysis preservation is a machine-checked contract. Rule: every pass returns a PreservedAnalyses value; the AnalysisManager invalidates everything not named. Tradeoff: pass authors must reason about what they preserve on every change. Operational implication: a spot-check AnalysisVerifier recomputes a sample of cached analyses after each pass and asserts equality (§16). Violation consequence: the single most common production-optimizer bug class — a stale LoopInfo or DominatorTree silently corrupts the next pass's decisions.
  4. P4 — Determinism is non-negotiable. Rule: two runs of the same input on the same host produce byte-identical output IR; no iteration order depends on hash-map insertion order. Tradeoff: sorted-key iteration costs O(N log N) over O(N) HashMap iteration. Operational implication: every internal collection iterated for output uses a stable order. Violation consequence: flaky differential tests, and two engineers diffing output get spurious diffs.
  5. P5 — No silent miscompiles; every optimization gated on sound analysis. Rule: a pass may only fire a rewrite licensed by an analysis result whose soundness is itself invariant-checked (e.g. GVN congruence gated on alias-freedom, §18). Tradeoff: conservative bail-out in ambiguous alias cases loses some redundancy elimination. Operational implication: every rewrite site names the analysis and invariant licensing it (H19). Violation consequence: a "correct on the common case" optimization miscompiles the uncommon one — the volatile/alias bug class in §22.
  6. P6 — Pruned SSA, not maximal. Rule: phi nodes are inserted only at the iterated dominance frontier of a variable's actual definition sites (I5), never at every merge point regardless of liveness. Tradeoff: pruning requires a live-variable check interleaved with placement — more upfront work than maximal placement. Operational implication: bounds Phase-0 memory (§4) and downstream pass cost. Violation consequence: unpruned pipelines measure 30–40% extra phi nodes on real corpora, inflating every subsequent pass's working set.
  7. P7 — The pipeline is a fixed, versioned sequence, not a runtime DSL. Rule: pass order (§16) is locked per optimization level and committed as a table, not parsed from a string at runtime. Tradeoff: less flexibility than LLVM's PassBuilder DSL. Operational implication: reproducing a build's exact pipeline requires only the optimization-level enum. Violation consequence: LLVM's own DSL has been a source of "which passes actually ran" debugging sessions; this project trades that flexibility for auditability.
  8. P8 — One-IR; no hidden secondary representation. Rule: every pass, including out-of-SSA, transforms the same Module/Function type. Tradeoff: the out-of-SSA output must still satisfy a relaxed verifier-invariant subset rather than escaping to an untyped form. Operational implication: the verifier runs once more after out-of-SSA (§21) on the relaxed set. Violation consequence: a second IR doubles the surface area for representation-mismatch bugs (a classic GCC RTL/GIMPLE-boundary bug class).
  9. P9 — No global mutable state. Rule: every pass and analysis receives its inputs by explicit reference; no thread-local caches, no process-global singletons. Tradeoff: more verbose call signatures throughout. Operational implication: rayon-based function-level parallelism (§4) is sound by construction. Violation consequence: global state is the single largest source of "works alone, fails under parallel test execution" bugs.
  10. P10 — Differential testing against a reference interpreter is the correctness truth source. Rule: every optimization pass, once it compiles, must additionally pass a differential-testing gate (§26) before merge. Tradeoff: the interpreter (ssa-interp) is itself a maintained artifact requiring its own correctness bar. Operational implication: CI runs the fuzz/differential bucket on every PR touching a pass crate (§27). Violation consequence: unit tests check the cases the author thought of; differential testing checks the cases the author didn't.
  11. P11 — Named invariants, not comments. Rule: every correctness property has an ID (I1…, §7) referenced by name in code, tests, and this document — never restated informally. Tradeoff: upfront cost of naming and tabulating every invariant before writing the passes that rely on it. Operational implication: a verifier failure message names the violated I#. Violation consequence: undocumented invariants get silently violated by a future pass author who never knew they existed.
  12. P12 — Fixtures are named and regression-locked. Rule: every conformance fixture (N.5, every phase) has a stable filename and a committed expected-output artifact. Tradeoff: golden-file churn on intentional behavior changes requires an explicit regeneration step with review. Operational implication: cargo test --workspace fails with fixture name + diff, never a generic assertion failure. Violation consequence: without named fixtures, a regression is indistinguishable from an intentional improvement until a human reasons about the diff.
  13. P13 — Compile-time budget is a first-class constraint. Rule: every pass carries a measured time-per-instruction budget (§4, §28) enforced by a CI perf-regression gate. Tradeoff: some analyses (full Andersen-style points-to) are excluded from the fixed pipeline specifically because they blow the budget (ADR-14, §31). Operational implication: a pass regressing its M-target (§28) fails CI, not just human review. Violation consequence: without a gate, compile-time regressions accumulate invisibly pass-by-pass until the optimizer is unusable in a JIT's hot path.
  14. P14 — Out-of-SSA correctness is proved, not assumed. Rule: SSA destruction (§21) is validated against the two named historical bug classes — the lost-copy problem and the swap problem — with a dedicated fixture for each. Tradeoff: implementing Sreedhar-Ju- Gillies/Boissinot-et-al. congruence classes is materially more code than naive phi-to-copy lowering. Operational implication: the out-of-SSA fixture bucket (§21 N.5) names both problems explicitly by fixture filename. Violation consequence: naive lowering of a phi(a,b)/phi(b,a) pair (the swap case) silently overwrites a live value — a textbook miscompile recurring independently across multiple production compilers.

8. Domain Model

CFG Model

A Function is a SlotMap<BlockId, BasicBlock> plus an entry: BlockId. Each BasicBlock holds an ordered Vec<InstructionId>, a terminator: InstructionId (last slot, I6), and preds: SmallVec<[BlockId;4]> (successors are derived from the terminator's target fields, never stored redundantly — a second copy that can drift would violate P4/I3). Edges are directed, control-flow only; an edge is identified by the (source_block, target_block) pair.

Block reachability classification (used by I7):

State Predicate Transition In Transition Out
Entry block_id == function.entry — (initial) → Live once visited
Live reachable from Entry via DFS from Entry/Live via an edge stays Live
Dead not DFS-reachable, unmarked never (absence of a transition IS the state) verifier rejects (I7)
MarkedDead not DFS-reachable, explicitly tagged by GCM from Live after a fold proves unreachable excluded from dominator-tree input

Dominator Tree & Dominance Frontiers

Built over the Live block set only (MarkedDead/Dead excluded, I7 precondition). idom: HashMap<BlockId,BlockId> gives immediate dominators (entry has none); dominance_frontier: HashMap<BlockId,BTreeSet<BlockId>> gives, for each block n, the frontier {b | n dominates a predecessor of b, n does not strictly dominate b} (Cytron et al. 1991 definition, §5). The tree is rebuilt, not incrementally patched, after any CFG-shape-changing pass in Phase 0–9 — incremental dominance update is deferred (PhaseDeferred("§35"), ADR-09).

SSA Construction — Phi Placement & Renaming

Two steps per Cytron et al.: (1) Placement — for each source-level variable v with definition-block set Defs(v), insert a Phi at every block in the iterated dominance frontier DF+(Defs(v)) (fixpoint of DF(DF(...)), converges in ≤3 iterations on the reference corpus, §4). Pruned (P6): a live-variable check restricts insertion to blocks where v is live-in, avoiding dead phis (I5). (2) Renaming — a single DFS pre-order walk of the dominator tree; each block pushes its own definitions onto a per-variable reaching-definition stack, rewrites its uses to the stack top, and pops on DFS exit. Phi incoming values are resolved from the predecessor's reaching definition at the point of the predecessor's exit, not the current block's — the detail most from-scratch implementations get wrong first (§5 Appel Ch. 19; ADR-06 documents the rejected Braun et al. on-the-fly alternative).

Renaming-stack discipline per variable:

Event Stack Action Applies To
Enter block, encounter a phi for v push the phi's result value destination block only
Enter block, encounter a non-phi def of v push new value defining block
Encounter a use of v read (do not pop) stack top any block
Exit block (DFS pop) pop every value this block pushed the block being exited
Visit a successor's phi read this block's current stack top for v; write into the phi's incoming list keyed by this BlockId predecessor, at exit time

Value / Use-Def Graph

Every ValueDef (§11) owns a uses: SmallVec<[Use;4]> — the reverse edge set enabling O(1)-amortized "who reads this value" queries (I13). The forward edges are the operands: SmallVec<[ValueId;3]> on each Instruction. Together they form a bipartite def-use graph over (ValueId, InstructionId) that every optimization pass (§16–§20) queries directly rather than re-deriving liveness/reachability from scratch — the single biggest performance lever over a naive re-scanning optimizer (§28).

Pass Pipeline State Model

Each pass transitions the (Module, AnalysisManager) pair atomically: on entry, it may get_or_compute any analysis; on exit, it returns PreservedAnalyses, and the manager invalidates the complement (I9).

State Meaning Entered By Exited By
Uncomputed never requested this pipeline run initial get_or_compute → Cached
Cached valid, safe to reuse successful compute, or preserved not-preserved declaration → Invalidated
Invalidated stale, must recompute before next use a pass omits it from PreservedAnalyses next get_or_compute → Cached (recomputed)

Worked Example — Diamond CFG Constant Propagation

Source shape: entry → {left, right} → merge, left: x = 1, right: x = 2, merge: y = x + 0. Post-SSA: merge gets x2 = phi [x0: left] [x1: right]; y0 = add x2, 0. SCCP (§17) lattice-walks x2: predecessors resolve x0=1(const), x1=2(const) but they disagree, so x2 → ⊥ (not-a-constant) — y0 cannot fold to a constant, only the +0 identity fires (an algebraic-identity rewrite in GVN's table, §18), yielding y0 = x2. This is the textbook case distinguishing SCCP's soundness (no false constant) from a naive per-predecessor guess.

Malformed-Input Example

A Phi at merge with incoming list [(left, x0)] only — missing the right edge entirely (a front-end bug, or a pass that added a predecessor without updating the phi, violating I3). The verifier's I3 check computes merge.preds = {left, right} from the CFG, compares to the phi's incoming-edge key set {left}, finds a set mismatch, and rejects with VerifierError::PhiPredecessorMismatch { block: merge, phi: <id>, missing: [right] } — pinpointing the exact missing edge rather than a generic "malformed IR" message (P11).

Failure-Path Example

A hypothetical buggy draft of GCM (§19) hoists a Load out of a loop whose guard can skip the loop body entirely, without checking that the hoist point is executed on every path (LICM safety condition, §20, I2-adjacent). The verifier cannot catch this — dominance and types remain well-formed — so the failure surfaces one layer up: the differential harness (§26) runs the pre- and post-pass IR through ssa-interp on a fixture where the loop guard is false on iteration 0, and the two interpretations diverge (post-pass reads memory pre-pass never touched). This is the concrete reason P10 exists: the verifier bounds structural well-formedness, never semantic equivalence.

Stand up the Cargo workspace (ADR-02), pin the toolchain (ADR-01), and land the minimal correctness kernel: ssa-ir's core types (§11), a first-cut ssa-verifier covering I1, I4, I6, and the governance files at the Repository Layout bar (§10). No optimization pass exists yet; this phase's sole job is a Module that can be built, verified, and rejected correctly.

12.2 Detailed Implementation Steps

Populate Cargo.toml workspace members per §10's crates/ tree. Implement Module, Function, BasicBlock, Instruction, ValueDef exactly per §11's signatures using slotmap::SlotMap (ADR-04) for all three ID-keyed collections and smallvec::SmallVec for operand/use lists (P6-adjacent memory discipline, quantified in §4). Implement ssa-verifier::verify checking I1 (duplicate-definition scan via a HashMap<ValueId, InstructionId> insert), I4 (per-operand type-table lookup against TypeTable), and I6 (last-slot terminator-opcode check) — the three invariants expressible without a dominator tree (deferred to Phase 2, §14). Wire .github/workflows/ci.yml to run cargo build --all-targets, cargo clippy --all-targets -- -D warnings, cargo fmt --check on the Linux/macOS/Windows × stable/nightly matrix (ADR-21).

12.3 Deliverable

A workspace that builds clean on every CI matrix entry; ssa-verifier::verify rejects a duplicate-definition fixture and a missing-terminator fixture with the correct VerifierError variant; governance files present per §10.

12.4 Acceptance Criteria

cargo build --all-targets and cargo clippy -- -D warnings return exit code 0 on all 6 matrix entries (3 OS × 2 toolchain channels). A 12-fixture corpus in conformance/buckets/verifier/ (6 positive, 6 negative covering I1/I4/I6) passes with the exact expected VerifierError variant per negative fixture. Cold workspace build completes in < 120 s on the 16-core reference host (§4).

12.5 Conformance Fixtures

verifier/dup_def_simple.ir — two instructions writing the same ValueId; expects DuplicateDefinition. verifier/missing_terminator.ir — a block with no terminator; expects TerminatorMissing. verifier/type_mismatch_add.ir — an Add operand typed as a pointer; expects TypeMismatch. verifier/clean_module_baseline.ir — a well-formed 3-block function; expects Ok(()).

12.6 Pitfalls

Pinning mismatched slotmap versions across crates silently duplicates the arena's memory layout assumptions — pin a single version at the workspace root. A SmallVec inline capacity chosen without profiling (e.g. too small for common 4-operand Call instructions) causes silent heap spills that defeat the whole point of using SmallVec — measure against the fixture corpus before locking the inline size. Forgetting #[non_exhaustive] on Opcode from day one (§11) forces a breaking change the first time a new opcode is added post-1.0.

12.7 Performance Concerns

SlotMap insertion/removal is O(1) amortized but a naive per-verify-run full re-scan of every Instruction's operand list is what dominates verifier cost (§4 M1 budget) — batch all I1/I4/ I6 checks into a single linear pass, never three separate walks.

12.8 Edge Cases

An empty Function (zero blocks) — the verifier must reject via TerminatorMissing on the absent entry block rather than panicking on SlotMap lookup. A self-referential Phi (an instruction that uses its own result) is legal in SSA loops and must not be flagged as I1 duplicate-definition (the definition is still unique; the use is merely of itself via the loop-carried value). Integer overflow in ValueId/InstructionId generation beyond u32::MAX must be a documented hard limit (§4), not a silent wraparound.

12.9 Failure Analysis

A verifier that produces false positives (rejecting well-formed IR) stops the entire pipeline downstream — the 12.5 fixture corpus explicitly includes the clean-baseline case specifically to catch this regression class before it reaches Phase 2+. Blast radius of a Phase-0 verifier bug is total: every later phase assumes I1/I4/I6 hold pre-SSA.

12.10 Operational Notes

cargo metadata --format-version 1 lists every crate for CI matrix generation. No telemetry beyond CI pass/fail exists at this phase (metrics land in Phase 4, §16). No migration/rollback concern yet — this is the initial commit.

13. Phase 1 — CFG Construction & IR Builder

13.1 Objectives

Deliver the ssa-builder cursor API so a front-end can construct a well-formed (pre-verifier) CFG: blocks, predecessors, terminators, and non-SSA (redefinable) local variables as a stepping stone to Phase 3's SSA construction.

13.2 Detailed Implementation Steps

Implement IrBuilder holding a (current_function, current_block, insertion_point) cursor; expose build_<opcode>(...) -> ValueId methods for every Opcode variant (§11) that transactionally: (a) allocate the Instruction in the Function's SlotMap, (b) append its id to the current block's insts, (c) update the new value's uses bookkeeping — maintaining I13 from the moment of construction, never as a post-hoc pass (P11: named invariant, enforced here). builder.set_insert_point(block, index) lets callers steer non-append insertion (needed later by GVN/GCM rewrites, §18–§19). Maintain preds incrementally on every build_br/build_cond_br call rather than deriving it lazily, so I3's precondition (an accurate predecessor set) holds immediately for the Phase-2 dominator-tree build (§14).

13.3 Deliverable

ssa-builder compiles with #![forbid(unsafe_code)] (ADR-24); a smoke-test front-end in examples/ builds a 3-block diamond CFG (§8 worked example's shape) and passes ssa-verifier::verify unmodified.

13.4 Acceptance Criteria

100% of Opcode variants have a corresponding build_* method (a clippy-enforced exhaustive-match lint fails CI otherwise, ADR-01's exhaustive-match rationale made concrete). Building a 1,000-instruction function completes in < 1 ms (§4-derived budget). The diamond-CFG smoke fixture (construct/diamond_baseline.ir) round-trips through verify with zero errors.

13.5 Conformance Fixtures

construct/diamond_baseline.ir — the §8 worked-example shape, expects clean verify. construct/unset_terminator.ir — a block built without a terminator call; expects the builder's own debug-assertion to fire before the verifier is even reached. construct/ predecessor_drift.ir — a hand-constructed case bypassing the builder's incremental preds update; expects ssa-verifier to catch the resulting I3-adjacent inconsistency downstream in Phase 2.

13.6 Pitfalls

A builder that does not maintain use-lists on construction makes every later set_operand call an O(n) linear search to find and remove the stale use entry — maintain the use-list transactionally from instruction creation, never lazily (I13, P11). Forgetting to update the terminator pointer when a new branch instruction is inserted mid-block breaks I6 silently until the next verifier run — the cursor API must make "insert a terminator" and "this block now has that terminator" atomic. A Vec<ValueId> operand list instead of SmallVec doubles per-instruction memory on the common ≤3-operand case (§4's 220-bytes/instruction budget, §32).

13.7 Performance Concerns

Cursor-style insertion is O(1) amortized per instruction for append-only construction; the set_insert_point steering path is O(1) via direct Vec index, not a linear scan — the implementation must not degrade to O(n) per insert when passes later use steering heavily (§18's GVN rewrite sites, §19's GCM hoisting).

13.8 Edge Cases

Building a function with a single block that is simultaneously entry and must terminate with Return — the builder must not require a separate "close the function" call that could be forgotten. A CondBr whose true and false targets are the same block (a degenerate but legal CFG shape) must still produce a correct preds multiset (the block is its own predecessor twice, not once) — I3's phi-predecessor correspondence check in Phase 3 depends on this being exact, including multiplicity.

13.9 Failure Analysis

A builder bug that under-counts predecessor multiplicity (the degenerate CondBr case above) surfaces downstream as a hard-to-diagnose I3 verifier failure in Phase 3, not at construction time — this is why 13.5 fixture predecessor_drift.ir exists as an explicit early-warning regression lock rather than relying on Phase-3 fixtures to catch it incidentally.

13.10 Operational Notes

The builder crate carries no telemetry of its own (it is a construction-time API, not a pipeline stage); its correctness is entirely covered by 13.5's fixtures plus the differential harness once Phase 9 (§21) exists to interpret builder output end-to-end.

14. Phase 2 — Dominator Tree & Dominance Frontiers

14.1 Objectives

Implement ssa-domtree: the Cooper-Harvey-Kennedy iterative dominance algorithm as the primary implementation (ADR-32) plus Lengauer-Tarjan as a property-test cross-check, and dominance-frontier computation — the load-bearing prerequisite for Phase 3's SSA construction.

14.2 Detailed Implementation Steps

Compute a reverse-postorder (RPO) numbering via DFS from entry first (Cooper, Harvey, Kennedy §5 requires RPO as a precondition); preprocess to exclude Dead/unmarked-unreachable blocks per I7's state table (§8) — Lengauer-Tarjan and CHK both produce wrong answers over unreachable blocks if not excluded first (§5 Cooper-Torczon Ch. 5.4). Implement CHK's fixed-point intersect(finger1, finger2) walk over RPO numbers to compute idom (P13: budgeted at §4 M2). Implement Lengauer-Tarjan (§5 paper) independently in the same crate as build_lengauer_tarjan, used only in test/property-check builds, never in the production pipeline (ADR-32's tradeoff). Compute dominance_frontier per Cytron et al.'s O(E) formula: for each block b with ≥2 predecessors, walk each predecessor p up the dominator tree from p until reaching idom(b), adding b to each visited node's frontier set.

14.3 Deliverable

ssa-domtree crate exposing DominatorTree::{idom, dominates, dominance_frontier, build_cooper_harvey_kennedy, build_lengauer_tarjan} (§11); a proptest-driven property test generating random reducible and irreducible CFGs and asserting both algorithms agree on every idom entry.

14.4 Acceptance Criteria

10,000 randomly generated CFGs (domtree/random_10k.ir batch) — both dominance algorithms agree on 100% of idom entries. A 10,000-block single CFG completes build_cooper_harvey_ kennedy in < 10 ms p50, < 20 ms p99 on the reference host (§4 M2, §28). dominates(a,b) is O(1) via DFS pre/post numbering, verified by a benchmark asserting < 50 ns per call.

14.5 Conformance Fixtures

domtree/diamond_baseline.ir — expects idom(merge) == entry. domtree/irreducible_loop.ir — a CFG with two entries into one SCC (a goto-into-loop shape); expects CHK and Lengauer-Tarjan to still agree (irreducibility affects natural-loop discovery in Phase 20's ssa-loopinfo, not dominance itself). domtree/unreachable_block.ir — a block with no predecessor path from entry; expects preprocessing to exclude it before CHK runs, never a CHK-internal panic.

14.6 Pitfalls

Running CHK before removing unreachable blocks (I7) produces wrong idom answers silently — no crash, just an incorrect tree that corrupts every downstream dominance query; preprocessing order is not optional. Computing RPO via a naive recursive DFS overflows the stack on a 10,000+-block function generated by a pathological front-end — use an explicit-stack iterative DFS. A dominance-frontier computation that walks from idom(b) inclusive instead of exclusive off-by-one's the frontier set, silently under- or over-placing phi nodes in Phase 3.

14.7 Performance Concerns

CHK's iterate-to-fixpoint loop is the dominant cost; RPO-ordered processing (not arbitrary block-id order) is what gives CHK its fast-in-practice near-linear behavior (§5 Cooper-Harvey- Kennedy paper) — processing in BlockId insertion order instead of RPO order has been measured to cause 3–5× more iterations to converge on deep CFGs.

14.8 Edge Cases

A single-block function (no branches at all) — idom is empty (entry has no dominator), and dominance_frontier is the empty map for every block; the algorithm must terminate in one step, not loop indefinitely on a degenerate fixpoint. A CFG where every block is its own predecessor's sole successor (a straight-line chain) exercises CHK's fast path — used as a performance regression canary. Deeply nested irreducible regions (multiple re-entrant loops) must not cause the RPO-DFS to revisit a block, which would corrupt dfs_pre/dfs_post numbering used by dominates's O(1) check.

14.9 Failure Analysis

A stale dominator tree — computed once, then consulted after a CFG-mutating pass without rebuilding (violating ADR-09's rebuild-not-patch discipline) — breaks every downstream pass that queries it; detection is I2's dominance-violation check in the post-pass verifier (§7), which is why ADR-09 mandates full rebuild rather than trusting a pass author to patch correctly. Blast radius: silent, until a verifier run or a differential-test divergence surfaces it.

14.10 Operational Notes

ssa-domtree emits a domtree.build_duration_ns metric per build (feeds §28's M2 gate); no persistence or migration concerns (rebuilt fresh every time, ADR-09). The property-test cross-check (Lengauer-Tarjan vs CHK) runs in CI's conformance.yml, never in the production build path — a debug assertion, not a release-mode cost.

15. Phase 3 — SSA Construction (Phi Placement & Renaming)

15.1 Objectives

Implement ssa-construct: pruned phi placement at the iterated dominance frontier (I5) and dominator-tree-DFS renaming, converting a non-SSA Function (arbitrary redefinable locals) into pruned SSA form satisfying I1–I3.

15.2 Detailed Implementation Steps

For each non-SSA local variable v, compute Defs(v) (the set of blocks containing an assignment to v) via a single pass over the function. Compute the iterated dominance frontier DF+(Defs(v)) as the fixpoint of repeatedly unioning DF(b) for each newly added block b, converging in ≤3 iterations on the reference corpus (§4; Cytron et al. 1991, §5). Prune (P6, I5): before inserting a phi at a candidate block, check v's liveness-in at that block via a backward liveness scan; skip insertion if dead. Rename via a single DFS pre-order walk of the dominator tree (§14's DominatorTree), maintaining a HashMap<Variable, Vec<ValueId>> reaching-definition stack per §8's state table — push on def/phi-entry, read on use, pop on DFS exit, and critically: resolve each successor's phi incoming value from this block's stack top at the point of this block's DFS exit, keyed by this BlockId (§8; the detail ADR-06 notes as the most commonly mis-implemented step, contrasted with Braun et al.'s on-the-fly alternative which sidesteps a separate placement pass entirely).

15.3 Deliverable

ssa-construct::construct(f: &mut Function, dom: &DominatorTree) transforms a non-SSA Function in place; output passes ssa-verifier::verify including I1, I2, I3, I5.

15.4 Acceptance Criteria

100% of the construct/ fixture bucket (40 fixtures spanning diamonds, loops, nested branches, and the §8 worked example) produce verifier-clean SSA output. Dead-phi count (I5 telemetry, construct.dead_phi_count) is 0 across the entire corpus post-construction, pre-DCE. A 1,000-function module completes construction in < 300 ms p50 (§28 M3-adjacent budget, derived from §4's 3-iteration bound).

15.5 Conformance Fixtures

construct/diamond_rename.ir — the §8 worked example; expects x2 = phi [x0:left][x1:right] exactly. construct/loop_carried_value.ir — a single-block-body loop redefining v each iteration; expects a phi at the loop header reading itself from the back edge (a self-referential phi, per 12.8's edge case). construct/dead_variable_pruning.ir — a variable assigned but never read on any path; expects zero phis inserted for it (I5, pruning). construct/ irreducible_df_iteration.ir — exercises the §14 irreducible-CFG case through phi placement, confirming DF+ converges even when natural-loop discovery (Phase 20) would treat the region specially.

15.6 Pitfalls

Resolving a phi's incoming value from the destination block's current reaching-definition state instead of the predecessor's state at its exit silently miscompiles any diamond-merge pattern — this is the single most common from-scratch SSA-construction bug (§5 Appel Ch. 19) and is exactly why 15.5's diamond_rename.ir fixture is the first one authored, not an afterthought. Iterating Defs(v) in HashMap order rather than sorted order threatens P4 determinism the moment two variables' phi-insertion order becomes observable in tie-breaking logic. Failing to prune (I5) before, not after, construction inflates every downstream pass's working set unnecessarily — pruning post-hoc via DCE works but wastes the whole pipeline's first iteration on dead phis.

15.7 Performance Concerns

The iterated-dominance-frontier fixpoint is the dominant construction cost; because it converges in ≤3 iterations on realistic corpora (§4), a construction implementation that instead does one iteration per Defs(v) block (rather than a shared worklist across all frontier blocks) can regress to O(n²) on deeply nested control flow — the worklist must be shared and deduplicated across the whole DF+ computation.

15.8 Edge Cases

A variable defined in every block on every path (never subject to any merge ambiguity) must receive zero phi insertions — the pruning liveness check must not conservatively over-insert. A function whose entry block itself is in some other block's dominance frontier is impossible by construction (entry dominates everything) — the implementation must assert this never occurs rather than silently accepting it, catching an upstream dominator-tree bug early. A phi that would be inserted at a block already containing a non-phi definition of v in the same block (redefinition after merge) must correctly interleave the phi (implicitly at block-entry) before the local redefinition in the renaming walk.

15.9 Failure Analysis

A phi-placement bug (missing a required frontier block) surfaces downstream not as a construction-time error but as an I2 dominance violation the first time a use born after the missed merge point is verified — cross-referencing the failure back to Phase 3 requires the verifier's diagnostic (12.5-style, naming the exact use+def sites) plus knowledge that Phase 3 is the only phase that inserts phis. A renaming-walk bug (wrong predecessor-exit-state resolution, 15.6) is almost always caught by the §8 worked-example fixture first, given it is the canonical smallest reproducing case.

15.10 Operational Notes

ssa-construct emits construct.df_iterations (should be ≤3, §4) and construct.dead_phi_count (should be 0, I5) as structured tracing fields (ADR-13) feeding the pipeline's PipelineReport (§11, §16). No migration concern — construction runs exactly once per function per compilation, never incrementally re-run.

16. Phase 4 — Analysis Manager & Pass Pipeline

16.1 Objectives

Implement ssa-analyses (the AnalysisManager, generation-counter invalidation, I9) and ssa-passmgr (the fixed, versioned pass sequence, P7/ADR-10) that every optimization pass in Phases 5–8 plugs into.

16.2 Detailed Implementation Steps

Implement AnalysisManager::get_or_compute<A> (§11): on cache miss, run A::run(f), store (Box<dyn Any + Send>, generation); on hit, compare stored generation to current — a mismatch recomputes (I9's generation-counter mechanism, not a type-level "dirty" flag, chosen for O(1) staleness checks). Implement invalidate_all_except(preserved: &PreservedAnalyses): bump the global generation counter, sparing entries whose TypeId is in preserved's set. Implement Pipeline::locked_for(OptLevel) (ADR-10) returning the exact Vec<Box<dyn FunctionPass>> for O0/O1/O2 as a compiled Rust table, never parsed from a string. Implement the debug-build-only AnalysisVerifier (P3): after every pass, recompute a fixed spot-check set (DominatorTree, UseDefGraph) from scratch and assert equality against whatever the manager currently has cached for analyses the pass claimed to preserve — this is the mechanism that catches a pass lying about PreservedAnalyses::all() (§6 P3's named bug class).

16.3 Deliverable

ssa-analyses + ssa-passmgr crates; Pipeline::run(&mut Module) -> PipelineReport executes the full O2 sequence (SCCP → GVN/CopyProp → DCE → GCM → LICM, plus verifier before/after) end to end over a fixture module with correct cache hit/miss counts.

16.4 Acceptance Criteria

Cache-hit latency ≤ 150 ns p50 (§4, §28 M4-adjacent), measured via criterion benchmark. analyses.stale_hits telemetry counter is 0 across the entire 200-fixture regression corpus. A synthetic "lying pass" (a test-only FunctionPass that mutates but claims PreservedAnalyses::all()) is caught by the AnalysisVerifier in a dedicated unit test (analyses/lying_pass_detected.rs) — the test asserts a spot-check mismatch is reported, not just that the mutation occurred.

16.5 Conformance Fixtures

analyses/cache_hit_after_preserve.ir — a pass declaring full preservation; expects the next pass's get_or_compute to be a cache hit, verified via injected counter. analyses/ invalidate_on_mutation.ir — a pass declaring PreservedAnalyses::none(); expects the next get_or_compute to recompute (cache miss). analyses/lying_pass_detected.rs — see 16.4. passmgr/o2_full_sequence.ir — runs the complete locked O2 pipeline on a 50-instruction fixture; expects a specific, committed golden output IR (P12).

16.6 Pitfalls

A nested pass manager (a hypothetical future Module-pass invoking Function-passes) must not share one AnalysisManager generation counter across unrelated Functions — cross-function generation bleed would falsely invalidate an unrelated function's valid cache; scope one AnalysisManager per Function (§11, ADR-08's per-function independence). A PreservedAnalyses::all() default that is too easy to reach for (versus explicitly listing what's preserved) invites exactly the lying-pass bug class the AnalysisVerifier exists to catch — all() remains available for genuinely pure analysis passes only, and its use is reviewed per P3.

16.7 Performance Concerns

The AnalysisVerifier spot-check recomputation is debug-build-only (§4, §7's I9 methodology) — it must be feature-gated out of release builds entirely via cfg(debug_assertions), not merely made cheap, since even a "cheap" spot-check recompute of DominatorTree on every pass would violate the §4 M9 8ms compile-time budget at O2.

16.8 Edge Cases

A pass that preserves an analysis it never actually consumed (over-cautious preservation) is legal but wastes no correctness — only a missed opportunity for the manager to free memory earlier; not a bug, but flagged by a lint suggesting tighter preservation sets. A pipeline run on a Module with zero functions must complete and return an empty PipelineReport, not panic on an empty iteration. Concurrent (rayon-parallel, ADR-08) execution of two Function's pipelines must never share an AnalysisManager instance — a Send-but-not- Sync design (§11) makes this a compile-time-enforced property, not a runtime discipline.

16.9 Failure Analysis

A stale-analysis bug that slips past the AnalysisVerifier (spot-check covers only a fixed sample, not every analysis type) surfaces as a wrong downstream pass decision — for example LICM (§20) hoisting based on a stale LoopInfo. Detection at that point falls back to the differential-testing harness (§26, P10); this two-layer defense (spot-check catches most cases cheaply, differential testing catches the rest at higher cost) is a deliberate depth-of-defense design, not redundancy.

16.10 Operational Notes

PipelineReport.per_pass_timing/per_pass_memory_delta (§11) are emitted as structured tracing spans (ADR-13) and serialized to the JSON perf report (ADR-28) consumed by §28's CI perf-regression gate. No rollback/migration concern — the pipeline is deterministic and stateless across invocations (P4, P9).

17. Phase 5 — Sparse Conditional Constant Propagation

17.1 Objectives

Implement ssa-sccp: Wegman-Zadeck sparse conditional constant propagation over the pruned SSA form from Phase 3, the first optimization pass in the fixed pipeline (ADR-10 position 1).

17.2 Detailed Implementation Steps

Initialize every SSA value's lattice state to Top (⊤, "not yet known"); maintain two worklists — an SSA-edge worklist (value redefinitions to re-propagate) and a CFG-edge worklist (newly-provably-executable edges) — per Wegman-Zadeck's original sparse formulation (§5 paper; Nielson-Nielson-Hankin §5 book's monotone-framework formalism is the lattice-theoretic grounding, ⊤ ⊑ Constant(k) ⊑ ⊥). Mark only entry's outgoing CFG edges executable initially; propagate a value's lattice meet only along CFG edges marked executable — this coupling (unlike naive dense constant propagation) is what lets SCCP prove a branch's condition constant and mark the untaken side's block permanently unreachable rather than merely unreached-so-far (§8 worked example: the diamond-CFG case where x2's two predecessors disagree, correctly yielding ⊥ not a guessed constant). When a comparison instruction resolves to a constant, mark only the corresponding CondBr target edge executable, leaving the other edge's destination block's phi inputs from that edge un-propagated. Iterate both worklists to joint fixpoint (I9-compliant: SCCP declares it does not preserve DominatorTree or LoopInfo since it may mark blocks unreachable, deferring their physical removal to §19's GCM).

17.3 Deliverable

ssa-sccp::run as a FunctionPass (§11) rewriting provably-constant values in place and tagging provably-unreachable CFG edges for later removal; passes ssa-verifier unmodified (constant folding never violates I1–I14 — it only replaces uses, per I13's mutation API).

17.4 Acceptance Criteria

100% of the sccp/ fixture bucket (25 canonical Wegman-Zadeck cases, including the §8 disagreeing-predecessors diamond) produce the exact expected constant-folded output (golden file, P12). SCCP on a 1,000-function module completes in ≤ 1 s p50, ≤ 2 s p99 (§28 M6). Zero false-positive constant folds across the 10,000,000-program fuzz/differential soak (§4, §26).

17.5 Conformance Fixtures

sccp/diamond_disagreement.ir — the §8 worked example; expects x2 to remain unresolved (⊥), not folded. sccp/branch_condition_constant.ir — a CondBr on a provably-constant condition; expects the untaken edge marked unreachable, not physically removed (that is GCM's job, §19). sccp/nan_comparison_no_fold.ir — a floating-point comparison against NaN; expects no constant fold under strict (non-fast-math) semantics. sccp/loop_carried_top.ir — a loop-carried phi whose initial value is constant but the back-edge value is not; expects the phi to correctly settle at ⊥ after the SSA-edge worklist processes the back edge, not to incorrectly freeze at the initial constant.

17.6 Pitfalls

Treating "not yet visited" the same as "proven non-constant" collapses SCCP into classical dense constant propagation, losing exactly the reachability-aware precision that is SCCP's entire point (§5 Wegman-Zadeck paper's core contribution) — the three-state lattice discipline must be enforced, not approximated with a boolean. Folding a floating-point comparison involving NaN under the assumption "these constants are equal" without checking FastMathFlags silently changes IEEE-754 semantics (I11-adjacent wrap-flag discipline extends to float semantics flags). Physically deleting an unreachable block during SCCP itself (instead of only tagging it) couples two passes' responsibilities and has caused, in this project's own design review, a dominator-tree staleness bug — SCCP tags, GCM removes (§19).

17.7 Performance Concerns

The sparse dual-worklist design is what gives SCCP its near-linear-in-practice cost over a dense iterative dataflow reformulation (§5 Aho-Lam-Sethi-Ullman Ch. 9's classical iteration would revisit every block on every iteration regardless of reachability) — a worklist implementation that fails to deduplicate repeated entries degrades toward the dense algorithm's cost profile.

17.8 Edge Cases

A function with no branches (straight-line code) must still terminate correctly with an empty CFG-edge worklist after one initial-edge seed. A self-loop CFG-edge (a block branching to itself) must not cause the CFG-edge worklist to grow unboundedly — marking an edge executable is idempotent (a set, not a queue with duplicates). A phi with all-constant but distinct incoming values from unreachable predecessors must ignore those predecessors' contributions entirely (only executable-edge-sourced values participate in the meet), per the CFG-edge/SSA-edge coupling.

17.9 Failure Analysis

A miscompile from an unsound fold (e.g. ignoring NaN semantics, 17.6) is caught by the differential harness (§26) comparing pre-/post-SCCP interpretation — this is the concrete instance of §8's failure-path-example pattern applied to SCCP specifically. Detection is immediate (single-fixture divergence), and blast radius is contained to SCCP's own output since no later pass in the fixed pipeline re-derives constants from scratch (they consume SCCP's result via the def-use graph, §8).

17.10 Operational Notes

SCCP emits sccp.values_folded and sccp.edges_marked_unreachable counters (ADR-28) feeding the perf/quality report; no rollback concern (a pure rewrite of the in-memory Function, P4). PreservedAnalyses declared: preserves nothing structural (dominator tree becomes advisory once edges are marked unreachable) — the manager's I9 invalidation ensures GCM (§19) rebuilds before consuming reachability information.

18. Phase 6 — Global Value Numbering & Copy Propagation

18.1 Objectives

Implement ssa-gvn: Click's hash-based global value numbering (redundant-computation elimination via congruence detection) plus copy propagation (eliminating Copy/trivial-phi indirections), the pipeline's second stage (ADR-10, ADR-15).

18.2 Detailed Implementation Steps

Build a structural hash per instruction from (opcode, operand value-numbers) — not operand ValueIds directly, since two syntactically different ValueIds may already be congruent (recursive value numbering, Click §5 paper). Instructions with equal hash and a subsequent structural equality check are congruent; pick a canonical representative (lowest ValueId for determinism, P4) and rewrite all other class members' uses to it via replace_all_uses_with (I13's mutation API — the only way GVN may touch the use-def graph). Gate every congruence merge candidate through ssa-aa's alias-analysis query for Load/Call instructions (P5, I8): two loads are congruent only if no intervening Store may alias either address, per the TBAA-lite stack (ADR-14). Copy propagation: a phi with all incoming values congruent to a single value (a "trivial phi," the base case Braun et al.'s on-the-fly SSA construction relies on for cleanup, §5) is replaced by that value directly, recursively re-triggering GVN on its former users.

18.3 Deliverable

ssa-gvn::run as a FunctionPass; eliminates redundant computations and trivial phis in place; declares PreservedAnalyses including DominatorTree (GVN never changes CFG shape) but not UseDefGraph snapshot caches (I13-sensitive).

18.4 Acceptance Criteria

100% of the gvn/ fixture bucket (30 congruence + copy-prop cases) match golden output (P12). GVN on a 1,000-function module completes in ≤ 1 s p50, ≤ 2 s p99 (§28 M5). Zero volatile-load merges across the entire fixture corpus and fuzz soak (I8, enforced by a dedicated assertion at the merge call site, not merely by test coverage).

18.5 Conformance Fixtures

gvn/redundant_add_diamond.ir — the same add computed on both sides of a diamond with provably-equal operands post-merge; expects a single canonical instruction post-GVN. gvn/ volatile_load_no_merge.ir — two structurally identical Loads, one marked volatile; expects no congruence merge (I8). gvn/trivial_phi_elimination.ir — a phi whose every incoming value is congruent to one value; expects the phi eliminated and uses rewritten directly. gvn/ aliasing_load_conservative.ir — two loads separated by a Store through an unrelated-looking but potentially-aliasing pointer; expects no merge (P5 conservative gate via ssa-aa).

18.6 Pitfalls

Value-numbering by raw ValueId instead of recursively-resolved congruence class misses the majority of real-world redundancy (Click's whole contribution is exactly this recursive formulation, §5 paper) — a naive "same Instruction shape" hash without operand-congruence resolution under-deduplicates. Merging two Call instructions to functions without a readnone/readonly-equivalent attribute silently assumes no side effects — the attribute model gating congruence for calls must default conservative (no merge) absent positive proof of purity. A canonical-representative choice that is not deterministic (e.g. "first one found" under HashMap iteration) breaks P4/I10 — always break ties by the lowest ValueId.

18.7 Performance Concerns

The structural hash table is the dominant cost driver; a poor hash function (e.g. hashing only the opcode, ignoring operands) degrades every bucket to a linear congruence-class scan, turning an expected-O(n) pass into O(n²) on large basic blocks — the hash must mix opcode and every operand's resolved value-number.

18.8 Edge Cases

Two instructions that are structurally identical but reside in mutually-unreachable-from-each- other blocks (no path connects them, yet both dominate a common use) — still valid congruence candidates provided the dominance condition (I2) for the chosen representative's use sites holds; the representative choice must itself remain a valid definition for every use it inherits. Self-referential value numbering (an instruction using its own not-yet-finalized value number during a recursive resolution, a loop-carried case) must terminate — resolve via a fixed-point iteration bounded by SSA's acyclic def-dominance property (I2), never unbounded recursion.

18.9 Failure Analysis

An unsound merge (missing the I8 volatile gate, or a stale/incomplete alias query) is exactly §8's failure-path-example pattern: structurally the IR remains verifier-clean (types and dominance are untouched), so detection depends entirely on the differential harness (§26) surfacing a semantic divergence. This is the concrete reason P5 requires every rewrite site name its licensing analysis and invariant (H19) — an audit of ssa-gvn's merge call sites is the first triage step when a divergence is reported against this pass specifically.

18.10 Operational Notes

Emits gvn.congruence_classes_found, gvn.merges_applied, gvn.trivial_phis_eliminated (ADR-28). PreservedAnalyses explicitly excludes any cached UseDefGraph snapshot (I13 requires it stay live-updated, not cached across a use-rewriting pass) — this is deliberately conservative per P3's "when in doubt, invalidate" operational stance.

19. Phase 7 — Dead Code Elimination & Global Code Motion

19.1 Objectives

Implement ssa-dce (worklist DCE + ADCE, ADR-16) and ssa-gcm (global code motion: physical removal of SCCP-marked-unreachable blocks plus Click-style instruction scheduling), the pipeline's third stage.

19.2 Detailed Implementation Steps

DCE: seed a worklist with every instruction that has zero entries in its uses list (I13 makes this an O(1) check per instruction) and no side effects (a Call without a pure/ readnone-equivalent attribute, or any Store, is never seed-eligible regardless of use count — P5). Pop the worklist, remove the instruction, and for each of its operands, decrement their conceptual use count (via replace_all_uses_with semantics in reverse, removing the Use entry, I13); if an operand's use-list becomes empty and it is itself side-effect-free, push it. ADCE (aggressive variant): start from the complement — mark every provably-essential instruction (terminators, side effects, volatile ops per I8) live via backward reachability over the use-def graph, then delete everything unmarked in one pass — used when DCE's worklist convergence is measured slower than a single backward sweep (§28-driven choice per function size). GCM: physically remove blocks SCCP (§17) tagged unreachable, rebuilding preds/dominator-tree-triggering CFG shape change (I7, I3 must both be re-verified after); then perform Click-style code scheduling — for each floating (non-pinned) instruction, place it at the earliest position that dominates all its uses and honors loop-invariant placement where beneficial (folding in the LICM handoff to §20).

19.3 Deliverable

ssa-dce::run and ssa-gcm::run as FunctionPasses; the combined stage removes all dead instructions, physically deletes SCCP-marked-unreachable blocks, and re-establishes a verifier-clean, dominator-tree-consistent Function.

19.4 Acceptance Criteria

100% of dce/ (20 fixtures) and gcm/ (15 fixtures) buckets match golden output. ADCE on a 1,000-function module completes in ≤ 500 ms p50, ≤ 1 s p99 (§28 M7). Post-GCM, ssa-verifier reports zero I7 violations (no unmarked-unreachable blocks survive) across the entire fixture corpus.

19.5 Conformance Fixtures

dce/pure_call_dead.ir — a call to a readnone-equivalent pure function with no uses; expects removal. dce/side_effecting_call_retained.ir — a call with unknown side effects and no uses; expects retention despite zero uses (P5's conservative gate). gcm/unreachable_block_ removal.ir — consumes an SCCP-tagged-unreachable block; expects physical deletion and a rebuilt, verifier-clean dominator tree. gcm/instruction_hoist_to_dominating_point.ir — a floating instruction whose uses are all in a dominated successor; expects relocation to the earliest legal point.

19.6 Pitfalls

Treating "zero uses" as sufficient for deletion without the side-effect gate (P5) is the single most common DCE bug — a Store or a volatile Load with zero uses must never be deleted; the side-effect classification must be checked before the use-count check, not after. Running GCM's physical block removal before SCCP has fully converged (17.2's iteration) risks removing a block that a not-yet-processed SSA-edge worklist entry still depends on — GCM must be sequenced strictly after SCCP's fixpoint, never interleaved (ADR-10's fixed ordering exists partly for this reason). Rebuilding preds incorrectly after block removal reintroduces exactly the predecessor-drift bug 13.6 warns about, now via a different code path.

19.7 Performance Concerns

ADCE's single backward sweep beats worklist-DCE's iterate-to-fixpoint cost specifically when the live set is large relative to the dead set (typical post-SCCP/GVN state, where most code survived); the pipeline selects ADCE at O2 and worklist-DCE at O1 as a measured tradeoff (§28 data), not an arbitrary choice — profile before changing the default per level.

19.8 Edge Cases

An instruction with side effects that is provably unreachable (inside an SCCP-tagged-dead block) must be removed as part of block deletion, not retained by DCE's side-effect gate — the gate applies to reachable dead code, not to code inside a block already proven unreachable; these are handled by different mechanisms (GCM's block deletion vs. DCE's use-count deletion) and must not be conflated. A function whose entire body becomes dead after constant folding (e.g. an always-false guard removes everything) must still retain a minimal valid terminator (a bare Return) — DCE/GCM must never produce a function with zero blocks, which would violate I6's precondition.

19.9 Failure Analysis

A DCE bug that removes a side-effecting instruction is a miscompile with maximal blast radius (the program's observable behavior changes, not just its performance) — this is why 19.6's side-effect gate is checked first in 19.2's ordering, and why dce/side_effecting_call_ retained.ir (19.5) is a P0-severity fixture, differential-tested on every PR touching ssa-dce (P10, ADR-19).

19.10 Operational Notes

Emits dce.instructions_removed, gcm.blocks_removed, gcm.instructions_rescheduled (ADR-28). PreservedAnalyses: DCE alone preserves DominatorTree (no CFG shape change); GCM's block-removal step does not (I7-triggering), forcing a Phase-2 rebuild before LICM (§20) consumes loop information downstream.

20. Phase 8 — Loop-Invariant Code Motion

20.1 Objectives

Implement ssa-loopinfo (Tarjan natural loops via dominator back-edges, I14) and ssa-licm (loop-invariant code motion), the pipeline's fourth stage — the first pass to consume loop structure rather than pure CFG/dominance.

20.2 Detailed Implementation Steps

ssa-loopinfo: identify back edges as any CFG edge (s, t) where t dominates s (I14's defining condition, checked against Phase-2's rebuilt DominatorTree, ADR-17); for each back edge, the natural loop is the set of blocks that can reach s without passing through t (backward DFS from s, stopping at t). Nest loops by dominator-tree containment of headers. Flag any SCC not captured as a natural loop (multiple entries) as irreducible (loopinfo.irreducible_regions_found, §7 I14 telemetry) and exclude it from LICM eligibility entirely (conservative fallback, never miscompiled — I14's recovery path). ssa-licm: for each loop (innermost-first), for each instruction in the loop body, hoist to the newly-materialized preheader block if and only if (a) all operands are loop-invariant (defined outside the loop, or themselves already hoisted this iteration — a fixed-point per-loop pass), (b) the instruction is either side-effect-free and speculatively safe (P5, I8's volatile gate applies here too) or it dominates every loop exit (proving it always executes), and (c) hoisting is profitability-gated (never hoist into a preheader that itself sits inside an outer loop unless the instruction is invariant with respect to that outer loop too, avoiding a net pessimization on nested loops, Knoop-Rüthing-Steffen §5 paper's lazy-code- motion profitability argument generalized here).

20.3 Deliverable

ssa-loopinfo::build producing a loop-nest tree; ssa-licm::run as a FunctionPass hoisting eligible instructions to materialized preheaders; both verifier-clean on output (I14, plus I2 since a hoisted instruction's new position must still dominate all its uses).

20.4 Acceptance Criteria

100% of licm/ (18 fixtures) match golden output. LICM on a 1,000-function module completes in ≤ 1 s p50, ≤ 2 s p99 (§28 M8). Zero instances across the fuzz/differential soak (§26) of a hoisted load executing on an iteration where the original loop would not have executed it (the trapping-load safety condition, §8's failure-path example made concrete for this specific pass).

20.5 Conformance Fixtures

licm/simple_invariant_hoist.ir — an invariant add inside a loop with operands defined outside; expects relocation to a materialized preheader. licm/trapping_load_not_hoisted.ir — a Load inside a conditionally-executed loop body (guard may skip it); expects no hoist (safety condition (b) fails). licm/irreducible_region_excluded.ir — an irreducible SCC; expects zero LICM activity, confirmed via loopinfo.irreducible_regions_found > 0 telemetry. licm/nested_loop_profitability.ir — an instruction invariant to the inner loop but not the outer; expects hoist only to the inner preheader, not further.

20.6 Pitfalls

Hoisting a Load that may not execute on every loop iteration, without proving it dominates every loop exit, is the textbook LICM miscompile (§8's failure-path example; a null-pointer guard skipped by hoisting segfaults on iteration 0) — safety condition (b) must be checked before profitability, never the reverse. Failing to detect an irreducible region before running natural-loop-based analysis produces an incomplete or wrong loop nest silently — the irreducible_regions_found telemetry (I14) must be checked by the calling pipeline stage, not merely logged and ignored. Materializing a preheader without correctly updating the phi nodes at the loop header (the preheader becomes a new sole non-back-edge predecessor) reintroduces an I3 phi-predecessor-mismatch bug via a new code path.

20.7 Performance Concerns

Natural-loop discovery is O(E) per back edge found; a pathological CFG with many small nested loops can make repeated per-loop invariant-fixpoint hoisting in 20.2 costlier than a single whole-function fixpoint — the innermost-first ordering bounds this by ensuring each instruction is considered invariant-or-not against the smallest enclosing loop first, avoiding redundant outer-loop re-evaluation of already-hoisted instructions.

20.8 Edge Cases

A loop with zero iterations possible at runtime (a guard that is always false, but not provably so at compile time by SCCP) must still be handled soundly — LICM's safety condition (b) does not require proving the loop executes at least once, only that if it executes, the hoisted instruction executes too; this distinction is what makes hoisting sound even for possibly-zero-trip loops. A loop whose header is also the function entry (a loop enclosing the entire function body) requires the preheader to become the new entry block, requiring an update to Function::entry itself — a case distinct from all other preheader insertions.

20.9 Failure Analysis

A LICM safety-condition violation surfaces as a memory-safety or trapping-instruction bug at runtime, not a verifier failure (structural invariants remain intact) — exactly the §8 failure-path-example pattern, now instantiated for real; detection is the differential harness running the specific "guard sometimes skips the load" fixture shape (20.5). Blast radius: a single mis-hoisted trapping instruction can crash every invocation of the containing function, not just pathological inputs — this is why 20.6's ordering (safety before profitability) is treated as inviolable, never a "usually fine" heuristic.

20.10 Operational Notes

Emits licm.instructions_hoisted, loopinfo.irreducible_regions_found, loopinfo.loop_nest_depth_max (ADR-28). PreservedAnalyses: LICM preserves DominatorTree identity for existing blocks but invalidates it for recomputation given the new preheader blocks (I7-adjacent CFG-shape change, smaller in scope than GCM's but still requiring a rebuild per ADR-09).

21. Phase 9 — Out-of-SSA / Phi Destruction & Semantics-Preservation Verification

21.1 Objectives

Implement ssa-outofssa (Boissinot et al. interference-graph-on-webs destruction, ADR-18, I12) and close the correctness loop: wire the full differential-testing harness (§26) and a translation-validation smoke check against every fixture in the corpus, the final pipeline stage before backend handoff.

21.2 Detailed Implementation Steps

Compute congruence classes: group SSA values that a phi's incoming-value set (and the phi's own result) could, in principle, share a single physical location, per Boissinot et al.'s webs-based formulation (§5 paper) — a strict improvement in implementation simplicity over Sreedhar-Ju-Gillies' original congruence-class algorithm (ADR-18) while preserving its correctness guarantee (I12). Build an interference graph over congruence-class members: two values interfere if simultaneously live at some program point; split a congruence class at an interference by inserting a copy, never by silently sharing a location anyway (the lost-copy problem, §5 Sreedhar-Ju-Gillies paper: naively assuming non-interference within a class silently overwrites a live value). For critical edges (a predecessor with multiple successors feeding a block with multiple predecessors), split the edge with a new empty block before inserting any copy (P8: still a first-class Function/BasicBlock, never a special "lowering-only" construct) — this is the concrete fix for the swap problem (phi(a,b) in one block and phi(b,a) in a parallel merge, naive simultaneous-assignment-as-sequential-copies overwrites one of the two values; critical-edge splitting plus congruence-class-aware copy insertion resolves the ordering ambiguity correctly). Lower each surviving phi to its congruence class's representative location; emit the resulting DestructionResult (§11) reporting inserted_copies for the §4 ≤1.15× budget check. Finally, wire the translation- validation smoke check (§26): for every fixture, symbolically compare the pre-destruction and post-destruction IR's def-use structure over a small set of representative execution paths, confirming no value's runtime binding changed — a bounded smoke check, explicitly not a full formal equivalence proof (§2's What-Mastery-Looks-Like bullet on this exact distinction).

21.3 Deliverable

ssa-outofssa::destroy_ssa producing a phi-free Function in virtual-register form; the full differential-testing harness (ssa-interp-based) and translation-validation smoke check wired into conformance.yml, running over the entire fixture corpus end to end.

21.4 Acceptance Criteria

100% of outofssa/ (22 fixtures, explicitly including a named swap-problem case and a named lost-copy-problem case) produce zero I12 interference violations. inserted_copies stays within 1.15× the fixture's hand-computed theoretical minimum (§4) across the corpus. The differential harness reports 0 divergences between pre-SSA-construction and post-out-of-SSA interpretation across all 200+ fixtures plus the 10,000,000-program 24h fuzz soak (§4, §26). The translation-validation smoke check passes on 100% of the locked fixture corpus (a FAIL here blocks release, ADR-25).

21.5 Conformance Fixtures

outofssa/swap_problem_named.ir — the canonical phi(a,b)/phi(b,a) parallel-merge shape; expects correct value exchange, verified by differential interpretation, not just structural inspection. outofssa/lost_copy_problem_named.ir — a congruence class with an internal interference that naive lowering would silently drop; expects a copy inserted, not a dropped value. outofssa/critical_edge_split.ir — a predecessor/successor pair requiring edge splitting before copy insertion; expects a new empty block materialized. outofssa/ minimal_copy_count.ir — a case with a known theoretical-minimum copy count; expects the implementation's inserted_copies at or near that minimum (§4 bound).

21.6 Pitfalls

Naive phi-to-copy lowering (insert a copy on each predecessor edge independently, ignoring whether classes interfere) is precisely the bug class this phase exists to prevent — both the swap problem and the lost-copy problem are textbook instances of this naivety and recur independently across production compilers whenever a team reaches for the "obvious" lowering instead of Sreedhar-Ju-Gillies/Boissinot-et-al. (P14, §6). Forgetting to split a critical edge before inserting a copy places the copy on an edge shared by unrelated control-flow paths, corrupting values for paths that should not have received it. Treating the translation- validation smoke check's PASS as a full correctness proof (rather than a bounded sanity check over representative paths) is a documentation/expectation-setting pitfall, not an implementation one — §2 explicitly calls out the distinction as a mastery checkpoint.

21.7 Performance Concerns

Interference-graph construction over congruence classes is the dominant cost; computing full pairwise liveness intersection naively is O(n²) in live-range count — Boissinot et al.'s specific contribution (over Sreedhar-Ju-Gillies) is an implementation that avoids this blowup via a sparser representation keyed on dominance-tree structure (§5 paper), which is the concrete performance rationale behind ADR-18's choice, not merely "simpler code."

21.8 Edge Cases

A phi whose every incoming value is already the same ValueId (post-GVN copy propagation, §18, should have eliminated this already, but defense-in-depth here) must destruct to a no-op, inserting zero copies. A congruence class spanning a loop back-edge (the loop-carried-value case from 12.8/15.8) requires the interference check to correctly account for the value being simultaneously "old" (from the previous iteration) and "new" (freshly defined this iteration) at the loop header — exactly the scenario the swap problem generalizes to inside loops. A function with zero phis remaining (fully resolved by GVN's trivial-phi elimination, §18) must skip destruction entirely as a fast path, producing zero inserted copies.

21.9 Failure Analysis

An I12 violation (two co-live values sharing one location post-destruction) is a maximal-severity miscompile — the program silently computes a wrong result using stale or overwritten data, with no crash or verifier signal, since destruction's relaxed post-condition (P8) does not re-check full SSA invariants. Detection is entirely the differential harness (§26) plus the translation-validation smoke check's representative-path comparison; this dual detection is why 21.4 makes both a hard release gate (ADR-25) rather than either alone.

21.10 Operational Notes

Emits outofssa.inserted_copies, outofssa.split_critical_edges, outofssa.interference_violations (must be 0, ADR-28). This phase's output is the handoff boundary to a downstream register allocator (out of scope, §1) — compatibility of the virtual-register-form output is covered by §25's versioning policy; no rollback path exists downstream of this phase within this project's scope.

Metrics: every pass emits PipelineReport timing + memory-delta entries (§11) plus the per-invariant telemetry counters named throughout §7/§22/§23 (verifier.i*_violations, analyses.stale_hits, outofssa.interference_violations, etc.), serialized as JSON (ADR-28). Tracing: tracing-crate structured spans (ADR-13), one per pass invocation, nested under one span per Pipeline::run call, carrying function_name, opt_level, and instruction count. Structured logging: every VerifierError and PipelineReport entry is serializable (serde-derived), never a free-text-only log line, so CI and any embedding host can programmatically triage a failure. Dashboards: a benchmarks/ Criterion HTML report per CI run, tracking each §28 M-target's trend over the last 90 days. Alerting philosophy: CI is the only "operator" (§1) — a failing determinism, conformance, or perf-regression gate blocks merge; there is no production on-call rotation because this is an embedded library, not a service (contrast with §22 T9's front-end-boundary threat, which is the closest analogue to a "production" concern). Incident response: a fuzz-found divergence (T11) or a reported downstream miscompile opens a P0 ticket referencing the specific I#/ADR/pass suspected; resolution requires a new regression fixture before closing. Runbooks (docs/runbooks/): bisect-a-miscompile.md (walks the per-pass IR-snapshot bisection procedure referenced in FM-2, FM-9), regenerate-golden-fixtures.md (the P12-mandated reviewed regeneration procedure), triage-a-fuzz-crash.md (FM-12's crash-to-fixture pipeline). Backup/restore: not applicable — no persistent state exists in this library (ADR-05). Deployment topology: none — a crates.io-published rlib, statically linked into the embedding host's binary. Canary/ rolling-upgrade/rollback/migration strategy: governed entirely by §25's SemVer policy; a consuming project pins an exact version and upgrades explicitly, there is no live-upgrade concept for an embedded library.

25. Compatibility & Versioning

Wire compatibility: not applicable in Phase 0–9 (ADR-05, no serialized IR format yet); once a textual IR format is added (Deferred Features Register), it will carry its own version tag independent of the crate's SemVer. Storage compatibility: not applicable (no persistence). API stability: Opcode and every public trait (FunctionPass, Analysis) are #[non_exhaustive] (§11, 12.6) so adding a variant is a non-breaking minor-version change for downstream matchers using a wildcard arm, but any crate depending on exhaustive matching over Opcode must be advised via the CHANGELOG that this is an intentional, permanent extensibility point. Migration: a downstream consumer upgrading across a minor version that adds an Opcode variant must audit any exhaustive match they wrote against it (mitigated by the #[non_exhaustive] compiler warning). Deprecation policy: a removed Opcode variant or public function requires one full minor-version deprecation cycle (marked #[deprecated]) before removal in the next major version. SemVer policy (ADR-25): patch = fixture/bugfix/perf-only changes with no API surface change; minor = additive API (new Opcode variant, new FunctionPass, new pass added to a non-default OptLevel); major = any change to a locked OptLevel's pass sequence (P7) or to the meaning of an existing Opcode, since either can change a downstream consumer's compiled output. Rolling-upgrade guarantees: none needed — no in-process upgrade path exists; a host recompiles against a new pinned version.

26. Testing & Verification Strategy

Unit tests: per-crate, covering individual functions (DominatorTree::dominates, AnalysisManager::get_or_compute cache semantics) in isolation. Integration tests: the conformance-fixture buckets (§10 conformance/buckets/), one per pass/analysis, each entry named per P12 with a committed golden-output file. Property testing: proptest-generated random CFGs cross-checking the two dominance algorithms (§14.4's 10,000-CFG corpus) and SCCP-lattice monotonicity assertions. Differential testing (P10, the correctness truth source): every optimization pass's pre- and post-transformation IR is interpreted by ssa-interp (§11) on every fixture and on the fuzz corpus; a divergence is an automatic P0. Fuzzing (ADR-20): cargo-fuzz/libFuzzer targets — verifier_fuzz.rs (feeds arbitrary byte sequences through the IrBuilder, asserting the verifier never panics, only ever returns Result), construct_fuzz.rs (random non-SSA CFGs through SSA construction, checking I1–I5 hold on output), differential_fuzz.rs (random programs through the full pipeline, comparing pre-/post-pipeline interpretation) — run continuously for the §4-mandated 24h/10,000,000- program soak (T11). Chaos/fault injection: not applicable in the traditional distributed- systems sense (no network, no partial failure domain) — the closest analogue is fuzzing's adversarial-input injection, covered above. Deterministic replay: every fixture's expected output is a byte-identical golden file (P12); replay is simply re-running the pipeline against the same input, and I10 requires the result to match exactly, every time. Soak testing: the 24h fuzz soak (§4) is this project's soak-test equivalent. Conformance: the entire conformance/buckets/ tree, run in conformance.yml on every PR. Performance-regression gating: §28's M-table, each row's CI-enforced threshold (P13). This strategy ties back directly to the System Invariants (§7): every I1–I14 has at least one dedicated positive and negative fixture, and every phase's N.5 fixtures are drawn from this same corpus, never a separate ad hoc test suite.

27. Build & Release Engineering

Reproducible builds: MSRV-pinned toolchain (ADR-01), committed Cargo.lock (ADR-26), and a CI-only Dockerfile (ADR-23) pinning every build-time tool identically across contributors and CI — two independent CI runs of the same commit must produce byte-identical rlib artifacts (verified as part of I10's determinism check extended to the build artifact itself, not just pipeline output). Artifact signing: released crates.io artifacts are signed via cargo's sigstore-based provenance attestation where available; git release tags are GPG-signed (ADR-25). SBOM: generated per release via cargo-cyclonedx, published alongside the release artifact, covering the minimal vetted dependency set (ADR-03). Release channels: a single stable channel on crates.io; no beta/nightly channel is published (a consumer wanting bleeding-edge functionality pins a git commit directly, an explicitly unsupported but not forbidden path). CI/CD topology: GitHub Actions matrix (ADR-21) — ci.yml (build+test+clippy+ fmt), conformance.yml (fixture buckets), fuzz.yml (nightly cargo-fuzz corpus run), release.yml (tag-triggered cargo publish). Version stamping: the crate's Cargo.toml version is the single source of truth, embedded into PipelineReport's metadata for any consumer wanting to correlate a compile artifact with the exact optimizer version that produced it. Provenance/attestation: release.yml records the exact commit SHA, CI run ID, and dependency-lock hash into the SBOM, giving any consumer a verifiable chain from source to published artifact. Dependency auditing: cargo-deny (ADR-03) runs on every PR, checking license compatibility (ADR-30), known-vulnerability advisories, and duplicate-version bloat; a failing cargo-deny check blocks merge exactly like a failing test.

28. Performance Engineering

Benchmarking methodology: criterion-based microbenchmarks per pass/analysis (§10 benchmarks/), run on the pinned 16-core x86_64 reference host (§4) with the corpus fixed across runs so trend lines are comparable. Profiling: perf + flamegraph for CPU hotspot identification, heaptrack for the §4 220-bytes/instruction memory budget verification. Allocation analysis: SmallVec/SlotMap inline-capacity tuning is re-validated against the fixture corpus whenever a new Opcode variant changes the common operand-count distribution (13.6's pitfall). Lock/contention analysis: rayon's work-stealing scheduler (ADR-08, ADR-12) is profiled for load imbalance when function-size distribution is highly skewed (many tiny functions plus a few huge ones) — mitigated by rayon's default chunking, re-tuned only if profiling shows otherwise. Cache-locality: SlotMap's dense generational-index storage keeps Instruction/ValueDef access patterns largely sequential during a linear verifier scan, deliberately chosen over a pointer-chasing Rc<RefCell<_>> graph (ADR-04) for exactly this reason. Syscall overhead: not a driver of this library's performance profile — no I/O occurs mid-pipeline (ADR-06, ADR-07). Tail-latency analysis: every §28 M-row below reports both p50 and p99 specifically because a JIT-embedding host cares about worst-case pipeline stalls, not just average throughput (§4's "must not visibly stall interpreter fallback" framing).

29. Scalability Analysis

What stays constant vs. grows: per-instruction verifier and construction cost is O(1) amortized (SlotMap access, §4); what grows is the number of instructions/functions in a module, and the dominant super-linear factor is dominance-frontier iteration count (bounded to ≤3 amortized by §4, but pathologically deep/wide CFGs can push toward CHK's O(N²) worst case, §14.7). Named bottlenecks in order: (1) dominator-tree construction on very large single functions (CHK's worst case), (2) GVN's structural-hash congruence-class resolution on functions with many syntactically-similar expressions, (3) out-of-SSA interference-graph construction on functions with deeply nested loop-carried congruence classes (§21.7). Horizontal scaling: function-level rayon parallelism (ADR-08, ADR-12) scales near-linearly with physical core count up to the number of functions in a module — a module with fewer functions than cores under-utilizes parallelism, the accepted tradeoff given no cross-function analysis exists in Phase 0–9. Vertical scaling: single-function throughput is bounded by the per-pass algorithmic complexity noted above; there is no vertical-scaling lever beyond falling back to Lengauer-Tarjan (ADR-32) on the rare pathological CFG where CHK's worst case manifests. Sharding/partitioning: not applicable — a Module is processed as one unit; splitting a single function's dominance computation across threads is explicitly deferred (Deferred Features Register) as the added synchronization cost was measured to outweigh benefit below the ≤2^20-instruction function-size ceiling (§4). Coordination overhead: zero at the function level (P9's no-shared-mutable-state design makes this a compile-time guarantee, not a runtime cost); at the module level, rayon's work-stealing overhead is the only coordination cost, and it is amortized across the whole pipeline run, not per-pass. Practical ceiling: a single function above roughly 2^18–2^20 instructions (§4's hard limit) exhausts the SlotMap key-space budget before it exhausts realistic compile- time budgets — the practical ceiling is therefore an explicit, documented limit, not an emergent performance cliff. Levers beyond the ceiling: incremental dominator-tree maintenance (ADR-09's rejected-alternative-wins regime) and a wider ValueId (u64) are both deferred levers (Deferred Features Register), traded off against Phase 0–9's simplicity-first philosophy (P1, P9).

30. Mental Models & First Principles

  • MM1 — "A phi node is a proof obligation, not a value selector." Insight: a phi's correctness depends entirely on the renaming walk resolving each incoming value from its predecessor's exit state (§15.2), not from treating it as a simple runtime "pick one of N" operation. Predicts: any implementation that tries to evaluate a phi "in place" during construction, rather than deferring resolution to the predecessor's DFS-exit moment, will miscompile diamond merges. Bug class without it: the renaming-walk miscompile named in §15.6/T6. Applied in §15, §8.
  • MM2 — "Dominance is a promise about every path, not the common path." Insight: I2's dominance invariant must hold for every control-flow path from entry to a use, not merely the paths an author tested. Predicts: any optimization that reasons "this is probably always true" instead of proving dominance via the DominatorTree will eventually miscompile an untested path. Bug class without it: the LICM trapping-load hoist (§20, FM-5). Applied in §14, §20, §7 (I2).
  • MM3 — "An analysis result is a loan, not a gift." Insight: a cached analysis is borrowed under the condition that the pass consuming it has not been told the loan is void (PreservedAnalyses); using it past that point is a use-after-invalidation bug structurally identical to a dangling reference. Predicts: any pass architecture without an explicit invalidation contract will eventually consume stale data. Bug class without it: T1/FM-3, the single most common production-optimizer bug class (P3). Applied in §16, §7 (I9).
  • MM4 — "SSA trades write-locality for read-locality." Insight: a non-SSA variable is cheap to write (redefine in place) but expensive to reason about (which definition reaches this use?); SSA inverts this — each value has exactly one, statically-known definition, making every optimization's soundness argument local to the def-use edge rather than global to the whole function. Predicts: any pass that tries to "help" by mutating a value in place post-construction (rather than defining a new ValueId) breaks I1 and every analysis built on it. Bug class without it: I1 violations, the foundational invariant every other one is built atop. Applied in §8, §15, §7 (I1).
  • MM5 — "The verifier bounds structure; the interpreter bounds meaning." Insight: no structural checker, however exhaustive, can prove semantic equivalence — I1–I14 are necessary but not sufficient for correctness (§8's failure-path example makes this concrete). Predicts: any correctness argument resting solely on "the verifier passed" is incomplete; a differential oracle is structurally required, not optional polish. Bug class without it: every semantic-only miscompile in §22 (T2, T4, T6, T7, T8). Applied in §8, §26, P10.
  • MM6 — "Congruence is an equivalence relation until interference proves otherwise." Insight: out-of-SSA destruction starts by assuming every phi-connected value could share one location, then subtracts the pairs that are simultaneously live — the interference check is a refinement, not the primary construction. Predicts: an implementation that tries to build interference-freedom "up front" per value rather than per congruence-class-then- split will over- or under-count copies relative to the §4 1.15× bound. Bug class without it: the swap and lost-copy problems (§21, T7/T8). Applied in §21.
  • MM7 — "A fixed pipeline is a promise you can audit; a DSL is a promise you must trust." Insight: P7's locked-sequence design trades runtime flexibility for the specific property that "what ran" is fully determined by one enum value, never a parsed string that could silently differ between two invocations. Predicts: any system exposing a stringly-typed pipeline configuration will eventually need a separate "what actually ran" audit mechanism bolted on after the fact (LLVM's own experience, §5). Applied in §16, §9 (ADR-10).
  • MM8 — "Compile-time budget is a correctness-adjacent constraint, not a nice-to-have." Insight: in a JIT-embedding context, a compile-time regression is observably indistinguishable from a correctness bug to the end user (the interpreter fallback stalls visibly) — treating §4's budgets as advisory rather than gated is a category error about what "correct" means for this system. Predicts: any pass added without a companion M-target (§28) will eventually regress compile time silently until a user-visible stall is reported as a "bug." Applied in §4, §28, P13.

32. Back-of-Envelope Capacity Model

  • IR memory footprint for a 1,000-function, 10,000-instruction-per-function module: 10,000,000 total instructions × 220 bytes/instruction (§4) = 2.2 GB peak resident memory — chained directly from §4's per-instruction budget row.
  • Verifier wall-clock on the same module: 10,000,000 instructions ÷ 10,000,000 instructions/s (§4 verifier-throughput floor) = 1.0 s per full-module verify pass; at 8 verifier invocations across the O2 pipeline (§4 pass-count row: before + after each of the ~7 stages) = ≤ 8.0 s total verifier overhead, budgeted within the pipeline's own M9 target's surrounding wall-clock.
  • Dominance-frontier iteration cost: 1,000 functions × ≤3 DF+ iterations/function (§4) × (10,000 instructions/function ÷ average branching factor ≈ 500 blocks/function) = ≤ 1,500,000 block-visits for the whole module's SSA construction, directly bounding §28 M3's 300 ms target (1,500,000 visits ÷ 300 ms ≈ 5,000,000 block-visits/s required throughput, consistent with M1's instruction-throughput floor scaled by the ~20 instructions/block average).
  • GVN hash-table size: 10,000,000 instructions × ~1 congruence-class-bucket-entry each × ~40 bytes/entry (hash + ValueId + class pointer) = 400 MB additional peak memory during the GVN pass specifically — a transient cost on top of the 2.2 GB IR footprint, motivating §4's "peak resident memory" wording as a steady-state (not GVN-transient-peak) budget.
  • Out-of-SSA copy count: assume 5% of instructions are phis (a typical post-construction ratio) = 500,000 phis; at a measured ~1.3 average congruence-class size, theoretical minimum copies ≈ 500,000 × 0.3 (fraction requiring a copy due to interference) = 150,000; at the §4 ≤1.15× bound = ≤ 172,500 inserted copies for the whole module, the concrete number M10's ratio target resolves to at this module size.
  • Full-module O2 compile-time: 1,000 functions × 8 ms/10,000-instruction function (§4 M9, scaled linearly per function) = 8.0 s module-level wall-clock at full serial execution; with rayon function-level parallelism (ADR-08) across 16 physical cores at near-linear speedup (§29) = ≈ 0.5 s realistic wall-clock, the number that actually matters for the "must not visibly stall interpreter fallback" framing (§4).
  • Fuzz-soak throughput requirement: 10,000,000 programs/24h (§4) ÷ 86,400 s/day ≈ 116 programs/s sustained differential-test throughput required from the fuzz harness infrastructure — a capacity number the CI fuzz runner (ADR-20, ADR-21) must be provisioned against directly.
  • Fan-out of rayon work-stealing: 1,000 functions ÷ 16 physical cores (§4 max-concurrency row) ≈ 63 functions per core if perfectly load-balanced — the number that justifies §29's observation that a module with fewer functions than cores under-utilizes parallelism (below ~16 functions total, some cores go idle).

34. Alternative Architectures (Roads Not Taken)

Alternative 1 — Sea-of-Nodes (no explicit basic blocks or phi nodes).

   [Start]──┐
            ▼
     [Region]◄────┐          data edges (solid) and control
      │  ▲         │          edges (dashed) coexist on one
      ▼  │         │          graph; a separate Scheduler pass
  [Phi]  [Merge]───┘          assigns nodes to blocks post-hoc.
      │
      ▼
   [Return]

Regime where it wins: extremely hot, small, frequently-recompiled functions in a tiering JIT (V8 TurboFan's actual workload) where instruction-scheduling freedom directly translates to codegen quality and the mandatory scheduling-pass cost is amortized across enormous recompile volume. Real system: V8 TurboFan (§5, §31). Why this blueprint rejected it: this project's compile-time budget (§4) is dominated by batch, not tiered-recompile, workloads, and every pass in §16–§20 is written assuming a directly-inspectable, already-scheduled CFG (P8's one-IR principle) — adopting sea-of-nodes would require rewriting every pass's traversal logic around an unscheduled graph plus adding a mandatory scheduler this design has no other use for.

Alternative 2 — Block Parameters instead of Phi Nodes.

block0:
  br block2(v1, v2)
block1:
  br block2(v3, v4)
block2(a, b):          ◄── block declares its own parameters;
  v5 = add a, b            no separate Phi instruction exists
  ret v5

Regime where it wins: a from-scratch, correctness-focused backend where minimizing the number of distinct instruction-shape special cases (no separate "Phi" opcode with its own predecessor-matching invariant, I3) simplifies the verifier and every pass's traversal code. Real system: Cranelift (§5, §31). Why this blueprint rejected it: P2 — the bulk of the optimization literature this project's fixtures are validated against (Cytron et al., Click, Wegman-Zadeck, Sreedhar-Ju-Gillies) is written in phi-node terms; adapting each algorithm to a block-parameter representation requires a systematic reverse-mapping this project chose to avoid in favor of pass writers reading the papers directly.

Alternative 3 — Maximal (Unpruned) SSA Placement.

   every merge point gets a phi for every
   live-or-not variable, regardless of
   whether the variable is read past it —
   pruning deferred entirely to DCE (§19)

Regime where it wins: a from-scratch prototype prioritizing implementation simplicity over runtime cost — maximal placement needs no liveness computation at construction time at all, only the dominance-frontier computation. Real system: early SSA implementations predating Cytron et al.'s pruning refinement, and several teaching-compiler implementations (§5 Appel's simplified variant). Why this blueprint rejected it: P6/I5 — measured 30–40% extra phi-node overhead on real corpora inflates every downstream pass's working set for the entire pipeline lifetime, not just construction; this project's §4 memory and compile-time budgets are tight enough that the extra liveness-check cost at construction time is the better amortized tradeoff.

Alternative 4 — Interprocedural-First Design (whole-program SSA across a call graph).

   ┌─────────┐     ┌─────────┐     ┌─────────┐
   │ func A  │────►│ func B  │────►│ func C  │   one SSA-like
   │ (SSA)   │◄────│ (SSA)   │◄────│ (SSA)   │   value space
   └─────────┘     └─────────┘     └─────────┘   spans all three
        interprocedural constant propagation,
        cross-function GVN, and a CGSCC-ordered inliner
        operate over this shared space directly.

Regime where it wins: a whole-program batch compiler with a closed call graph (no dynamic dispatch, no separately-compiled shared libraries) where cross-function redundancy is common enough to justify the analysis cost — a regime some GCC LTO configurations and specialized embedded-systems compilers target. Real system: GCC's LTO/WHOPR pipeline is the closest production analogue (§5). Why this blueprint rejected it: explicitly out of scope (§1 non-goals) — interprocedural analysis multiplies the verifier/analysis-manager surface area by the size of the call graph, a scope this project's 7-month full-system timeline (§1) does not budget for; every interprocedural feature (IPCP, a CGSCC inliner) is instead named in the Deferred Features Register as a natural Phase 10+ extension once the intraprocedural foundation here is proven solid.

36. Glossary

  • ADCE: Aggressive Dead Code Elimination — backward-liveness-marking DCE variant (§19).
  • ADR: Architecture Decision Record — a locked, rejected-alternatives-documented choice (§9).
  • Alias analysis: the query interface determining whether two memory operations may reference the same address (§9 ADR-14).
  • AnalysisManager: the cache + invalidation-graph system mediating every pass's analysis requests (§16).
  • Back edge: a CFG edge whose target dominates its source; the defining condition of a natural loop (I14).
  • Congruence class: a set of SSA values that may share one physical location post-SSA- destruction (§21).
  • CFG: Control-Flow Graph — the block-and-edge structure a Function is built from (§8).
  • Copy propagation: eliminating a trivial phi or copy instruction by rewriting its uses directly to its source value (§18).
  • Critical edge: a CFG edge from a multi-successor block to a multi-predecessor block, requiring splitting before certain transformations (§21).
  • CHK: Cooper-Harvey-Kennedy — the iterative dominance algorithm used as this project's primary implementation (§14, ADR-32).
  • DCE: Dead Code Elimination — worklist-based removal of unused, side-effect-free instructions (§19).
  • Dominance: block a dominates block b if every path from entry to b passes through a (I2).
  • Dominance frontier: the set of blocks where a block's strict dominance "ends" — the precise set where phi placement is required (§8, §15).
  • DominatorTree: the analysis structure recording each block's immediate dominator (§11).
  • GCM: Global Code Motion — Click's scheduling discipline plus physical dead-block removal (§19).
  • GVN: Global Value Numbering — hash-based congruence detection eliminating redundant computations (§18).
  • Iterated dominance frontier (DF+): the fixpoint closure of the dominance-frontier operator, the exact set where phi placement is required for pruned SSA (§8, §15).
  • I1…I14: this document's numbered System Invariants, the correctness contract every pass must uphold (§7).
  • IrBuilder: the cursor-style API used to construct a Module (§11, §13).
