⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the Cargo workspace (ADR-02), pin the toolchain (ADR-01), and land the minimal correctness kernel: ssa-ir's core types (§11), a first-cut ssa-verifier covering I1, I4, I6, and the governance files at the Repository Layout bar (§10). No optimization pass exists yet; this phase's sole job is a Module that can be built, verified, and rejected correctly.

Deliverable

A workspace that builds clean on every CI matrix entry; ssa-verifier::verify rejects a duplicate-definition fixture and a missing-terminator fixture with the correct VerifierError variant; governance files present per §10.

Acceptance

cargo build --all-targets and cargo clippy -- -D warnings return exit code 0 on all 6 matrix entries (3 OS × 2 toolchain channels). A 12-fixture corpus in conformance/buckets/verifier/ (6 positive, 6 negative covering I1/I4/I6) passes with the exact expected VerifierError variant per negative fixture. Cold workspace build completes in < 120 s on the 16-core reference host (§4).

Fixtures

verifier/dup_def_simple.ir — two instructions writing the same ValueId; expects DuplicateDefinition. verifier/missing_terminator.ir — a block with no terminator; expects TerminatorMissing. verifier/type_mismatch_add.ir — an Add operand typed as a pointer; expects TypeMismatch. verifier/clean_module_baseline.ir — a well-formed 3-block function; expects Ok(()).

Pitfalls

Pinning mismatched slotmap versions across crates silently duplicates the arena's memory layout assumptions — pin a single version at the workspace root. A SmallVec inline capacity chosen without profiling (e.g. too small for common 4-operand Call instructions) causes silent heap spills that defeat the whole point of using SmallVec — measure against the fixture corpus before locking the inline size. Forgetting #[non_exhaustive] on Opcode from day one (§11) forces a breaking change the first time a new opcode is added post-1.0.

⬜ Phase 1 — CFG Construction & IR Builder §13

Objectives

Deliver the ssa-builder cursor API so a front-end can construct a well-formed (pre-verifier) CFG: blocks, predecessors, terminators, and non-SSA (redefinable) local variables as a stepping stone to Phase 3's SSA construction.

Deliverable

ssa-builder compiles with #![forbid(unsafe_code)] (ADR-24); a smoke-test front-end in examples/ builds a 3-block diamond CFG (§8 worked example's shape) and passes ssa-verifier::verify unmodified.

Acceptance

100% of Opcode variants have a corresponding build_* method (a clippy-enforced exhaustive-match lint fails CI otherwise, ADR-01's exhaustive-match rationale made concrete). Building a 1,000-instruction function completes in < 1 ms (§4-derived budget). The diamond-CFG smoke fixture (construct/diamond_baseline.ir) round-trips through verify with zero errors.

Fixtures

construct/diamond_baseline.ir — the §8 worked-example shape, expects clean verify. construct/unset_terminator.ir — a block built without a terminator call; expects the builder's own debug-assertion to fire before the verifier is even reached. construct/ predecessor_drift.ir — a hand-constructed case bypassing the builder's incremental preds update; expects ssa-verifier to catch the resulting I3-adjacent inconsistency downstream in Phase 2.

Pitfalls

A builder that does not maintain use-lists on construction makes every later set_operand call an O(n) linear search to find and remove the stale use entry — maintain the use-list transactionally from instruction creation, never lazily (I13, P11). Forgetting to update the terminator pointer when a new branch instruction is inserted mid-block breaks I6 silently until the next verifier run — the cursor API must make "insert a terminator" and "this block now has that terminator" atomic. A Vec<ValueId> operand list instead of SmallVec doubles per-instruction memory on the common ≤3-operand case (§4's 220-bytes/instruction budget, §32).

⬜ Phase 2 — Dominator Tree & Dominance Frontiers §14

Objectives

Implement ssa-domtree: the Cooper-Harvey-Kennedy iterative dominance algorithm as the primary implementation (ADR-32) plus Lengauer-Tarjan as a property-test cross-check, and dominance-frontier computation — the load-bearing prerequisite for Phase 3's SSA construction.

Deliverable

ssa-domtree crate exposing DominatorTree::{idom, dominates, dominance_frontier, build_cooper_harvey_kennedy, build_lengauer_tarjan} (§11); a proptest-driven property test generating random reducible and irreducible CFGs and asserting both algorithms agree on every idom entry.

Acceptance

10,000 randomly generated CFGs (domtree/random_10k.ir batch) — both dominance algorithms agree on 100% of idom entries. A 10,000-block single CFG completes build_cooper_harvey_ kennedy in < 10 ms p50, < 20 ms p99 on the reference host (§4 M2, §28). dominates(a,b) is O(1) via DFS pre/post numbering, verified by a benchmark asserting < 50 ns per call.

Fixtures

domtree/diamond_baseline.ir — expects idom(merge) == entry. domtree/irreducible_loop.ir — a CFG with two entries into one SCC (a goto-into-loop shape); expects CHK and Lengauer-Tarjan to still agree (irreducibility affects natural-loop discovery in Phase 20's ssa-loopinfo, not dominance itself). domtree/unreachable_block.ir — a block with no predecessor path from entry; expects preprocessing to exclude it before CHK runs, never a CHK-internal panic.

Pitfalls

Running CHK before removing unreachable blocks (I7) produces wrong idom answers silently — no crash, just an incorrect tree that corrupts every downstream dominance query; preprocessing order is not optional. Computing RPO via a naive recursive DFS overflows the stack on a 10,000+-block function generated by a pathological front-end — use an explicit-stack iterative DFS. A dominance-frontier computation that walks from idom(b) inclusive instead of exclusive off-by-one's the frontier set, silently under- or over-placing phi nodes in Phase 3.

⬜ Phase 3 — SSA Construction (Phi Placement & Renaming) §15

Objectives

Implement ssa-construct: pruned phi placement at the iterated dominance frontier (I5) and dominator-tree-DFS renaming, converting a non-SSA Function (arbitrary redefinable locals) into pruned SSA form satisfying I1–I3.

Deliverable

ssa-construct::construct(f: &mut Function, dom: &DominatorTree) transforms a non-SSA Function in place; output passes ssa-verifier::verify including I1, I2, I3, I5.

Acceptance

100% of the construct/ fixture bucket (40 fixtures spanning diamonds, loops, nested branches, and the §8 worked example) produce verifier-clean SSA output. Dead-phi count (I5 telemetry, construct.dead_phi_count) is 0 across the entire corpus post-construction, pre-DCE. A 1,000-function module completes construction in < 300 ms p50 (§28 M3-adjacent budget, derived from §4's 3-iteration bound).

Fixtures

construct/diamond_rename.ir — the §8 worked example; expects x2 = phi [x0:left][x1:right] exactly. construct/loop_carried_value.ir — a single-block-body loop redefining v each iteration; expects a phi at the loop header reading itself from the back edge (a self-referential phi, per 12.8's edge case). construct/dead_variable_pruning.ir — a variable assigned but never read on any path; expects zero phis inserted for it (I5, pruning). construct/ irreducible_df_iteration.ir — exercises the §14 irreducible-CFG case through phi placement, confirming DF+ converges even when natural-loop discovery (Phase 20) would treat the region specially.

Pitfalls

Resolving a phi's incoming value from the destination block's current reaching-definition state instead of the predecessor's state at its exit silently miscompiles any diamond-merge pattern — this is the single most common from-scratch SSA-construction bug (§5 Appel Ch. 19) and is exactly why 15.5's diamond_rename.ir fixture is the first one authored, not an afterthought. Iterating Defs(v) in HashMap order rather than sorted order threatens P4 determinism the moment two variables' phi-insertion order becomes observable in tie-breaking logic. Failing to prune (I5) before, not after, construction inflates every downstream pass's working set unnecessarily — pruning post-hoc via DCE works but wastes the whole pipeline's first iteration on dead phis.

⬜ Phase 4 — Analysis Manager & Pass Pipeline §16

Objectives

Implement ssa-analyses (the AnalysisManager, generation-counter invalidation, I9) and ssa-passmgr (the fixed, versioned pass sequence, P7/ADR-10) that every optimization pass in Phases 5–8 plugs into.

Deliverable

ssa-analyses + ssa-passmgr crates; Pipeline::run(&mut Module) -> PipelineReport executes the full O2 sequence (SCCP → GVN/CopyProp → DCE → GCM → LICM, plus verifier before/after) end to end over a fixture module with correct cache hit/miss counts.

Acceptance

Cache-hit latency ≤ 150 ns p50 (§4, §28 M4-adjacent), measured via criterion benchmark. analyses.stale_hits telemetry counter is 0 across the entire 200-fixture regression corpus. A synthetic "lying pass" (a test-only FunctionPass that mutates but claims PreservedAnalyses::all()) is caught by the AnalysisVerifier in a dedicated unit test (analyses/lying_pass_detected.rs) — the test asserts a spot-check mismatch is reported, not just that the mutation occurred.

Fixtures

analyses/cache_hit_after_preserve.ir — a pass declaring full preservation; expects the next pass's get_or_compute to be a cache hit, verified via injected counter. analyses/ invalidate_on_mutation.ir — a pass declaring PreservedAnalyses::none(); expects the next get_or_compute to recompute (cache miss). analyses/lying_pass_detected.rs — see 16.4. passmgr/o2_full_sequence.ir — runs the complete locked O2 pipeline on a 50-instruction fixture; expects a specific, committed golden output IR (P12).

Pitfalls

A nested pass manager (a hypothetical future Module-pass invoking Function-passes) must not share one AnalysisManager generation counter across unrelated Functions — cross-function generation bleed would falsely invalidate an unrelated function's valid cache; scope one AnalysisManager per Function (§11, ADR-08's per-function independence). A PreservedAnalyses::all() default that is too easy to reach for (versus explicitly listing what's preserved) invites exactly the lying-pass bug class the AnalysisVerifier exists to catch — all() remains available for genuinely pure analysis passes only, and its use is reviewed per P3.

⬜ Phase 5 — Sparse Conditional Constant Propagation §17

Objectives

Implement ssa-sccp: Wegman-Zadeck sparse conditional constant propagation over the pruned SSA form from Phase 3, the first optimization pass in the fixed pipeline (ADR-10 position 1).

Deliverable

ssa-sccp::run as a FunctionPass (§11) rewriting provably-constant values in place and tagging provably-unreachable CFG edges for later removal; passes ssa-verifier unmodified (constant folding never violates I1–I14 — it only replaces uses, per I13's mutation API).

Acceptance

100% of the sccp/ fixture bucket (25 canonical Wegman-Zadeck cases, including the §8 disagreeing-predecessors diamond) produce the exact expected constant-folded output (golden file, P12). SCCP on a 1,000-function module completes in ≤ 1 s p50, ≤ 2 s p99 (§28 M6). Zero false-positive constant folds across the 10,000,000-program fuzz/differential soak (§4, §26).

Fixtures

sccp/diamond_disagreement.ir — the §8 worked example; expects x2 to remain unresolved (⊥), not folded. sccp/branch_condition_constant.ir — a CondBr on a provably-constant condition; expects the untaken edge marked unreachable, not physically removed (that is GCM's job, §19). sccp/nan_comparison_no_fold.ir — a floating-point comparison against NaN; expects no constant fold under strict (non-fast-math) semantics. sccp/loop_carried_top.ir — a loop-carried phi whose initial value is constant but the back-edge value is not; expects the phi to correctly settle at ⊥ after the SSA-edge worklist processes the back edge, not to incorrectly freeze at the initial constant.

Pitfalls

Treating "not yet visited" the same as "proven non-constant" collapses SCCP into classical dense constant propagation, losing exactly the reachability-aware precision that is SCCP's entire point (§5 Wegman-Zadeck paper's core contribution) — the three-state lattice discipline must be enforced, not approximated with a boolean. Folding a floating-point comparison involving NaN under the assumption "these constants are equal" without checking FastMathFlags silently changes IEEE-754 semantics (I11-adjacent wrap-flag discipline extends to float semantics flags). Physically deleting an unreachable block during SCCP itself (instead of only tagging it) couples two passes' responsibilities and has caused, in this project's own design review, a dominator-tree staleness bug — SCCP tags, GCM removes (§19).

⬜ Phase 6 — Global Value Numbering & Copy Propagation §18

Objectives

Implement ssa-gvn: Click's hash-based global value numbering (redundant-computation elimination via congruence detection) plus copy propagation (eliminating Copy/trivial-phi indirections), the pipeline's second stage (ADR-10, ADR-15).

Deliverable

ssa-gvn::run as a FunctionPass; eliminates redundant computations and trivial phis in place; declares PreservedAnalyses including DominatorTree (GVN never changes CFG shape) but not UseDefGraph snapshot caches (I13-sensitive).

Acceptance

100% of the gvn/ fixture bucket (30 congruence + copy-prop cases) match golden output (P12). GVN on a 1,000-function module completes in ≤ 1 s p50, ≤ 2 s p99 (§28 M5). Zero volatile-load merges across the entire fixture corpus and fuzz soak (I8, enforced by a dedicated assertion at the merge call site, not merely by test coverage).

Fixtures

gvn/redundant_add_diamond.ir — the same add computed on both sides of a diamond with provably-equal operands post-merge; expects a single canonical instruction post-GVN. gvn/ volatile_load_no_merge.ir — two structurally identical Loads, one marked volatile; expects no congruence merge (I8). gvn/trivial_phi_elimination.ir — a phi whose every incoming value is congruent to one value; expects the phi eliminated and uses rewritten directly. gvn/ aliasing_load_conservative.ir — two loads separated by a Store through an unrelated-looking but potentially-aliasing pointer; expects no merge (P5 conservative gate via ssa-aa).

Pitfalls

Value-numbering by raw ValueId instead of recursively-resolved congruence class misses the majority of real-world redundancy (Click's whole contribution is exactly this recursive formulation, §5 paper) — a naive "same Instruction shape" hash without operand-congruence resolution under-deduplicates. Merging two Call instructions to functions without a readnone/readonly-equivalent attribute silently assumes no side effects — the attribute model gating congruence for calls must default conservative (no merge) absent positive proof of purity. A canonical-representative choice that is not deterministic (e.g. "first one found" under HashMap iteration) breaks P4/I10 — always break ties by the lowest ValueId.

⬜ Phase 7 — Dead Code Elimination & Global Code Motion §19

Objectives

Implement ssa-dce (worklist DCE + ADCE, ADR-16) and ssa-gcm (global code motion: physical removal of SCCP-marked-unreachable blocks plus Click-style instruction scheduling), the pipeline's third stage.

Deliverable

ssa-dce::run and ssa-gcm::run as FunctionPasses; the combined stage removes all dead instructions, physically deletes SCCP-marked-unreachable blocks, and re-establishes a verifier-clean, dominator-tree-consistent Function.

Acceptance

100% of dce/ (20 fixtures) and gcm/ (15 fixtures) buckets match golden output. ADCE on a 1,000-function module completes in ≤ 500 ms p50, ≤ 1 s p99 (§28 M7). Post-GCM, ssa-verifier reports zero I7 violations (no unmarked-unreachable blocks survive) across the entire fixture corpus.

Fixtures

dce/pure_call_dead.ir — a call to a readnone-equivalent pure function with no uses; expects removal. dce/side_effecting_call_retained.ir — a call with unknown side effects and no uses; expects retention despite zero uses (P5's conservative gate). gcm/unreachable_block_ removal.ir — consumes an SCCP-tagged-unreachable block; expects physical deletion and a rebuilt, verifier-clean dominator tree. gcm/instruction_hoist_to_dominating_point.ir — a floating instruction whose uses are all in a dominated successor; expects relocation to the earliest legal point.

Pitfalls

Treating "zero uses" as sufficient for deletion without the side-effect gate (P5) is the single most common DCE bug — a Store or a volatile Load with zero uses must never be deleted; the side-effect classification must be checked before the use-count check, not after. Running GCM's physical block removal before SCCP has fully converged (17.2's iteration) risks removing a block that a not-yet-processed SSA-edge worklist entry still depends on — GCM must be sequenced strictly after SCCP's fixpoint, never interleaved (ADR-10's fixed ordering exists partly for this reason). Rebuilding preds incorrectly after block removal reintroduces exactly the predecessor-drift bug 13.6 warns about, now via a different code path.

⬜ Phase 8 — Loop-Invariant Code Motion §20

Objectives

Implement ssa-loopinfo (Tarjan natural loops via dominator back-edges, I14) and ssa-licm (loop-invariant code motion), the pipeline's fourth stage — the first pass to consume loop structure rather than pure CFG/dominance.

Deliverable

ssa-loopinfo::build producing a loop-nest tree; ssa-licm::run as a FunctionPass hoisting eligible instructions to materialized preheaders; both verifier-clean on output (I14, plus I2 since a hoisted instruction's new position must still dominate all its uses).

Acceptance

100% of licm/ (18 fixtures) match golden output. LICM on a 1,000-function module completes in ≤ 1 s p50, ≤ 2 s p99 (§28 M8). Zero instances across the fuzz/differential soak (§26) of a hoisted load executing on an iteration where the original loop would not have executed it (the trapping-load safety condition, §8's failure-path example made concrete for this specific pass).

Fixtures

licm/simple_invariant_hoist.ir — an invariant add inside a loop with operands defined outside; expects relocation to a materialized preheader. licm/trapping_load_not_hoisted.ir — a Load inside a conditionally-executed loop body (guard may skip it); expects no hoist (safety condition (b) fails). licm/irreducible_region_excluded.ir — an irreducible SCC; expects zero LICM activity, confirmed via loopinfo.irreducible_regions_found > 0 telemetry. licm/nested_loop_profitability.ir — an instruction invariant to the inner loop but not the outer; expects hoist only to the inner preheader, not further.

Pitfalls

Hoisting a Load that may not execute on every loop iteration, without proving it dominates every loop exit, is the textbook LICM miscompile (§8's failure-path example; a null-pointer guard skipped by hoisting segfaults on iteration 0) — safety condition (b) must be checked before profitability, never the reverse. Failing to detect an irreducible region before running natural-loop-based analysis produces an incomplete or wrong loop nest silently — the irreducible_regions_found telemetry (I14) must be checked by the calling pipeline stage, not merely logged and ignored. Materializing a preheader without correctly updating the phi nodes at the loop header (the preheader becomes a new sole non-back-edge predecessor) reintroduces an I3 phi-predecessor-mismatch bug via a new code path.

⬜ Phase 9 — Out-of-SSA / Phi Destruction & Semantics-Preservation Verification §21

Objectives

Implement ssa-outofssa (Boissinot et al. interference-graph-on-webs destruction, ADR-18, I12) and close the correctness loop: wire the full differential-testing harness (§26) and a translation-validation smoke check against every fixture in the corpus, the final pipeline stage before backend handoff.

Deliverable

ssa-outofssa::destroy_ssa producing a phi-free Function in virtual-register form; the full differential-testing harness (ssa-interp-based) and translation-validation smoke check wired into conformance.yml, running over the entire fixture corpus end to end.

Acceptance

100% of outofssa/ (22 fixtures, explicitly including a named swap-problem case and a named lost-copy-problem case) produce zero I12 interference violations. inserted_copies stays within 1.15× the fixture's hand-computed theoretical minimum (§4) across the corpus. The differential harness reports 0 divergences between pre-SSA-construction and post-out-of-SSA interpretation across all 200+ fixtures plus the 10,000,000-program 24h fuzz soak (§4, §26). The translation-validation smoke check passes on 100% of the locked fixture corpus (a FAIL here blocks release, ADR-25).

Fixtures

outofssa/swap_problem_named.ir — the canonical phi(a,b)/phi(b,a) parallel-merge shape; expects correct value exchange, verified by differential interpretation, not just structural inspection. outofssa/lost_copy_problem_named.ir — a congruence class with an internal interference that naive lowering would silently drop; expects a copy inserted, not a dropped value. outofssa/critical_edge_split.ir — a predecessor/successor pair requiring edge splitting before copy insertion; expects a new empty block materialized. outofssa/ minimal_copy_count.ir — a case with a known theoretical-minimum copy count; expects the implementation's inserted_copies at or near that minimum (§4 bound).

Pitfalls

Naive phi-to-copy lowering (insert a copy on each predecessor edge independently, ignoring whether classes interfere) is precisely the bug class this phase exists to prevent — both the swap problem and the lost-copy problem are textbook instances of this naivety and recur independently across production compilers whenever a team reaches for the "obvious" lowering instead of Sreedhar-Ju-Gillies/Boissinot-et-al. (P14, §6). Forgetting to split a critical edge before inserting a copy places the copy on an edge shared by unrelated control-flow paths, corrupting values for paths that should not have received it. Treating the translation- validation smoke check's PASS as a full correctness proof (rather than a bounded sanity check over representative paths) is a documentation/expectation-setting pitfall, not an implementation one — §2 explicitly calls out the distinction as a mastery checkpoint.
