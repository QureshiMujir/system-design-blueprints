Decisions (§9) · 26 ADRs

ADR-01

Language

Chosen

Rust

Rejected

C++, C, Zig

When the rejected choice is right

C++ wins when linking into an existing AAA C++ engine core requiring zero-FFI-overhead and the team's expertise is entirely C++

Why: memory safety in the hot pixel-write loop + trait-based shader stage + rayon

ADR-02

Arithmetic for edge functions

Chosen

Fixed-point 24.8

Rejected

pure f32, f64

When the rejected choice is right

pure f32 wins when prototyping without needing bit-exact reproducibility, or targeting a platform with weak integer ALUs relative to float

Why: exact, deterministic sign comparisons on shared edges (P1, I1)

ADR-03

Subpixel precision

Chosen

8 fractional bits (1/256 px)

Rejected

4 bits, 16 bits

When the rejected choice is right

4 bits wins when targeting extremely large virtual canvases (giant print-resolution renders) where range matters more than accuracy

Why: balances guard-band range against practical AA positional accuracy

ADR-04

Rasterization strategy

Chosen

half-space/edge-function, tiled/binned

Rejected

scanline/active-edge-table, per-triangle immediate

When the rejected choice is right

scanline/AET wins for wireframe/line-only debug views or extremely thin slivers where the bbox overhead of edge functions is wasted

Why: binning-amenable form (P11); trivially parallel per-pixel (Pineda 1988)

ADR-05

Tile size

Chosen

64×64 px

Rejected

16×16, 32×32, 128×128

When the rejected choice is right

16×16 wins for scenes dominated by very small triangles (dense foliage, particle sprites) where fine tiles cut overdraw waste

Why: fits tile-local color+depth+MSAA in L2 while keeping binning overhead low (section 34)

ADR-06

Clipping strategy

Chosen

guard-band + full clip only at near/far or overflow

Rejected

full Sutherland-Hodgman always, clip-on-demand only

When the rejected choice is right

full-clip-always wins when geometry is guaranteed pre-clipped offline and simplicity outweighs per-triangle cost

Why: most triangles never cross the near plane; always-clipping wastes the common case

ADR-07

Culling order

Chosen

after divide+viewport (screen-space winding)

Rejected

in clip space before divide

When the rejected choice is right

clip-space cull wins when heavy off-screen geometry dominates and culling before divide saves that per-vertex work

Why: cheap sign check reusing the already-computed setup sign

ADR-08

Fill-rule convention & depth range

Chosen

OpenGL top-left rule, z_ndc ∈ [−1,1]

Rejected

D3D-style convention, z ∈ [0,1]

When the rejected choice is right

D3D convention wins when differentially testing against a D3D-lineage software rasterizer (e.g. WARP) instead of Mesa/SwiftShader

Why: conformance target is the OpenGL 4.6 specification (P12)

ADR-09

Depth format & range

Chosen

f32 linear NDC depth

Rejected

24-bit fixed, reverse-Z f32

When the rejected choice is right

reverse-Z f32 wins when near/far ratio exceeds ~10,000:1 (open-world/space-sim scenes)

Why: adequate precision at the target near/far ratio (section 34)

ADR-10

Early-Z vs. late-Z ordering

Chosen

early-Z by default, late-Z when shader declares discard/depth-write

Rejected

always late-Z

When the rejected choice is right

always-late-Z wins when every shader in the pipeline discards or writes depth, making early-Z bookkeeping pure overhead

Why: avoids wasted shading on occluded fragments (P7)

ADR-11

Shader stage representation

Chosen

Rust trait objects (dyn VertexShader/FragmentShader)

Rejected

generics/monomorphization, bytecode interpreter

When the rejected choice is right

generics win when the shader set is fixed at compile time and raw throughput matters more than runtime swapability

Why: swappable shaders at runtime, acceptable vtable overhead vs. shading cost

ADR-12

Attribute interpolation implementation

Chosen

per-pixel 1/w + a/w linear interpolation, shared reciprocal

Rejected

screen-space linear with post-hoc "correction," precomputed scanline deltas only

When the rejected choice is right

screen-linear wins for flat, camera-facing UI quads where perspective distortion is provably zero

Why: exact per P3; avoids the tinyrenderer-style shortcut (section 5)

ADR-13

Texture layout

Chosen

linear (row-major) per mip level

Rejected

swizzled/Morton-tiled

When the rejected choice is right

swizzled wins when texture footprint dominates triangle footprint and 2D-locality-per-fetch matters more than generation simplicity

Why: simpler generation/debugging given the tile-local texture cache footprint (section 34)

ADR-14

Filtering & mipmapping policy

Chosen

bilinear + trilinear (isotropic)

Rejected

When the rejected choice is right

nearest-only wins for pixel-art or debug visualization wanting crisp texel boundaries

Why: matches the fixed-function baseline; anisotropic deferred (section 37)

ADR-15

36. Alternative Architectures (Roads Not Taken)

Scanline / active-edge-table rasterizer — the classic pre-GPU approach: maintain a sorted active-edge table per scanline, walking horizontal spans rather than testing a bounding box against edge functions.

 Sorted Edge Table (by ymin)
        │
        ▼
 For each scanline y:
   [Update Active Edge List]  (add edges starting, remove edges ending)
        │
        ▼
   [Sort AEL by current x]
        │
        ▼
   [Fill spans between AEL pairs]  -- one span per (in,out) edge crossing
        │
        ▼
   [Next scanline]  (increment each edge's x by its slope)

Winning regime: single-threaded, immediate-mode rendering of large polygons with few triangles (classic 1990s software rendering, wireframe/vector-art fills). Embodied by early Mesa swrast and pre-GPU-era renderers generally. Rejected here because active-edge-table state is inherently sequential per scanline (each scanline's AEL depends on the previous one), hostile to the tile-parallel decomposition (P11, ADR-04) this blueprint is built around — Pineda's edge-function formulation was chosen specifically because it has no such sequential dependency (section 5, section 8).

Ray-traced visibility (the sibling rank-170 architecture) — solve visibility by tracing rays per pixel against an acceleration structure instead of projecting geometry.

 Camera rays (one+ per pixel)
        │
        ▼
 [Acceleration Structure Traversal]  (BVH/kd-tree)
        │
        ▼
 [Ray-Primitive Intersection]
        │
        ▼
 [Shading + recursive/stochastic sampling]  (light transport)
        │
        ▼
 [Framebuffer accumulate]

Winning regime: scenes where visibility cost should scale logarithmically with scene complexity rather than linearly with fill rate — complex, deeply occluded scenes, or physically based global illumination where secondary rays are unavoidable. Embodied by the Ray Tracer, rank 170. Rejected here because this project's defining bet is the opposite one: visibility is solved by projection and a depth buffer (section 1's stated scope), trading logarithmic scene-scaling for a fill-rate-bound cost model that maps directly onto exactly the tiled, cache-friendly hardware this blueprint targets (P11, section 31).

Deferred / visibility-buffer architecture — decouple rasterization (write a per-pixel primitive/barycentric ID) from shading (a full-screen pass reading that buffer).

 [Rasterize: write VisibilityBuffer]  (triangle_id, barycentrics per pixel)
        │
        ▼
 [Full-screen Shading Pass]  (reads VisibilityBuffer, reconstructs attributes, shades once)
        │
        ▼
 [Framebuffer]

Winning regime: scenes with extreme shader complexity and material variety where avoiding redundant shading work on overdrawn fragments matters more than pipeline simplicity — this is the modern deferred/visibility-buffer approach used in several real-time engines under heavy overdraw. Rejected here because it adds a second full-screen pass and a reconstruction step that would obscure the direct, one-pass pipeline this blueprint is built to teach (section 1's legibility goal) — the forward, single-pass tiled pipeline (section 3) keeps the shading contract (P7, P10) directly attached to the rasterization stage that produced it.

Sort-last parallel architecture — as the alternative to this blueprint's sort-middle binning: each thread rasterizes an entire disjoint subset of triangles into a full-screen private framebuffer, then a final compositing pass merges all threads' framebuffers by depth.

 Triangle list, partitioned by thread (not by screen tile)
        │
   ┌────┴────┬─────────┐
   ▼         ▼         ▼
[Thread 0] [Thread 1] [Thread N]   each: full pipeline, full-screen private framebuffer
        │         │         │
        └────┬────┴─────────┘
             ▼
     [Depth-Composite Merge]   -- O(threads) per pixel, every pixel

Winning regime: scenes with a very small, fixed triangle count relative to screen resolution, where per-thread full-screen framebuffer memory is affordable and triangle-partitioning is trivially balanced. Embodied conceptually by some early parallel-rendering research systems. Rejected here because per-thread full-screen framebuffers multiply memory cost by thread count (violating the section 4 framebuffer-memory budget at any nontrivial thread count) and the final merge pass is itself an O(threads × pixels) serialization point that P11's disjoint-tile design avoids entirely by construction (ADR-04, ADR-18, ADR-19).
