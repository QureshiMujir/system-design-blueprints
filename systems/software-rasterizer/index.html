In one paragraph

A software rasterizer turns triangles into pixels using only the CPU. This design builds the whole real-time graphics pipeline from scratch in Rust: transform vertices, clip, project, decide which pixels each triangle covers, test depth, shade, sample textures, blend and write an image (§1). It ships as a library plus a command-line renderer, not as a game engine or a GPU backend (§1). Its users are graphics engineers learning the pipeline, CI systems that need reproducible reference renders, and a downstream engine blueprint that links the core crate (§1, §2). Its defining concerns are an exact rule for who owns each pixel, perspective-correct interpolation and the tile-local memory-access pattern, and it promises a multithreaded path that is bit-identical to the single-threaded one (§1, P1, P3, P11, I7).

The problem, concretely

A GPU hides every step of drawing a triangle behind a driver. The blueprint wants each matrix multiply, clip, divide and blend to be readable Rust instead, and it wants renders that a CI machine can reproduce exactly without a GPU (§2). That goal exposes the places where the obvious approach quietly fails.

  • Shared edges. Two triangles in a mesh meet along an edge. If a pixel sits exactly on that edge, a careless renderer lets both triangles draw it (a double-blended seam) or neither (a crack). The design requires every such pixel to be covered exactly once (P1, I1, FM-1, FM-2).
  • Dividing too early. Projection ends with a divide by the homogeneous coordinate w. A vertex behind the eye has w at or below zero, and dividing by it gives a mirrored or garbage triangle, so clipping has to come first (P2, I2, MM3, FM-5).
  • Interpolating in the wrong space. Blending texture coordinates linearly across the screen looks right on a flat, camera-facing quad and wrong on a receding floor, where the texture swims (P3, MM4, FM-3). The blueprint notes that the early lessons of the tinyrenderer teaching project skip this step and says this design does not repeat that shortcut (§5, ADR-12).

How it works, end to end

Follow one triangle through the boxes of §3's diagram. The blueprint lays out the crates in §10: raster-math, raster-core, raster-shade, raster-io, raster-cli, raster-conformance, and a deferred raster-window (§1, §10). §1 calls all seven the Phase-0 deliverable, while §12.1 has Phase 0 set up only raster-math, raster-core, raster-io and raster-cli, and the §10 workspace-manifest comment names five crates (§1, §12.1, §10).

 Vertex Buffer + Index Buffer
   -> [Vertex Fetch] -> [Vertex Shader] -> [Primitive Assembly]
   -> [Homogeneous Clipping] -> [Perspective Divide + Viewport] -> [Backface Cull]
   -> [Triangle Setup] -> [Tile Binner]
 ==== per-tile parallel boundary (rayon fork) ====
   per tile: [Early-Z] -> [Fragment Shader + Texture Unit] -> [Blending] -> tile-local buffer
 ==== join (barrier) ====
   -> [Framebuffer Resolve] -> [Output Writer] (PPM/PNG, sRGB encode)
  1. Vertex fetch. raster-core/src/vertex_fetch.rs reads the vertex and index buffers in a fixed order and does no reordering. That fixed order is what later makes bit-identical frames possible (§3, §10, P9).
  2. Vertex shader. A user-supplied implementation of the VertexShader trait (raster-shade/src/vertex_shader.rs) runs once per vertex and outputs a clip-space position plus interpolable attributes called ShaderVaryings (§3, §8, §10, ADR-11).
  3. Primitive assembly. Index triples become triangles. It does no math, and exists as its own stage only because clipping works on whole polygons (§3).
  4. Clipping. clip.rs runs Sutherland-Hodgman against six frustum planes, before any divide (§3, §10, P2). A guard-band test lets triangles that are safely inside an extended screen margin skip the full pass (§3, P13, ADR-06).
  5. Divide and viewport. viewport.rs divides by w to reach normalized device coordinates, then maps to pixel coordinates (§3, §8, §10).
  6. Cull and setup. cull.rs drops triangles whose signed screen-space area has the wrong sign (ADR-07). setup.rs then computes the three edge functions, the per-vertex 1/w and a bounding box in 24.8 fixed-point coordinates (§3, §10, P1, P8).
  7. Binning. binning.rs appends the triangle to every tile its bounding box touches. This is the last single-threaded stage (§3, §10, ADR-04).
  8. Per-tile work. Each tile, owned by exactly one thread, runs the early depth test (depth.rs), the fragment shader with the texture unit (texture.rs) and blending (blend.rs) against its own private color and depth slice (§3, §10, I5, P7).
  9. Resolve and output. After the join, resolve.rs copies, or under MSAA averages, each tile's buffers into the global Framebuffer. raster-io (ppm.rs, png.rs) writes the file, and the linear-to-sRGB conversion happens only at this last step (§3, §10, ADR-19).

The core ideas

Edge functions and the fill rule (§8, P1, I1)

An edge function is a formula of a pixel's position that is zero on one edge of a triangle and has one sign on each side. A pixel is inside a triangle if all three edge functions are positive. A pixel exactly on an edge (value zero) counts as inside only if that edge is a "top" or "left" edge, which is the top-left rule (§8, §38). Because both triangles apply the same rule to the shared edge, a pixel on it is covered by exactly one of the two (P1). For this to work, both triangles must compute the shared edge from the same vertex data with the same arithmetic. That is why coordinates are rounded to 24.8 fixed-point numbers (24 sign-and-integer bits, 8 fractional bits, 1/256 pixel) before any edge function is evaluated (§8, P8, ADR-02, ADR-03).

The blueprint's worked example places a triangle at pixel positions P0=(256,256), P1=(341.33,256) and P2=(256,170.67) and tests the pixel centre (280.5, 240.5) (§8):

Quantity Value the blueprint gives
E0, E1, E2 (all positive, so inside) 1322.6, 3868.0, 2090.6
Twice the signed area, 2A = E0+E1+E2 7281.2 (matches the analytic area)
Barycentric weights λ0, λ1, λ2 0.5312, 0.2871, 0.1817 (sum 1.0000)
Interpolated UV, for uv0=(0,0), uv1=(1,0), uv2=(0,1) u=0.2871, v=0.1817

The weights are the edge-function values divided by 2A, with λ0 from E1, λ1 from E2 and λ2 from E0 (§8). The blueprint states its rule as dy < 0, or dy == 0 and dx > 0 (§8). Applied to the worked example's vertex order, that test marks the horizontal edge P0→P1 as top-left and the vertical edge P2→P0 as not, although screen y grows downward (sy = (1 − y_ndc)·…), so P0→P1 is the triangle's bottom edge and P2→P0 its left edge; the glossary defines the rule by top and left edges (§8, §38). The blueprint does not comment on this.

Clip before you divide (§8, P2, I2, I13)

Homogeneous clip space keeps a fourth number, w, that the divide will later consume. A point is inside the view volume when -w ≤ x ≤ w, -w ≤ y ≤ w, -w ≤ z ≤ w and w > ε (§8). Where a polygon edge from A to B crosses a plane, the new vertex is the linear blend of A and B at t = d_A / (d_A − d_B), where d is the signed distance to the plane, computed before the divide (§8). Each of the six planes adds at most one vertex, so a triangle becomes at most nine vertices, which fan-triangulates into at most seven triangles (§4, §34, I13). The test is w > ε, not a bare w > 0, to avoid a divide by zero at the boundary (§8, FM-5). The blueprint's degenerate cases: a triangle entirely behind the eye is rejected at clipping, and one with zero area is discarded at setup (§8).

Perspective-correct interpolation (§8, P3, P4, I4)

Screen position is not linear in a triangle's attributes once projection is involved, but attribute/w and 1/w are. So the pipeline interpolates both with the barycentric weights and divides at each pixel: a = (a/w)_screen / (1/w)_screen (§8, P3, MM4). Setup caches 1/w per vertex so the pixel loop does not recompute it (P3, §16.2). Depth is the exception: z/w is already linear on screen, so depth skips the 1/w machinery (§8, P4). The blueprint's worked example cannot show the difference, because all three vertices have w = 3 and so both methods agree. It points to the receding-checkerboard fixture for the visible failure (§8, §16.4). Depth precision depends on where the projection puts the near plane, not only on bit width (MM6, P4).

Texture detail from derivatives (§8, P6, I6)

A mipmap is a pyramid of progressively downsampled copies of a texture (§38). To pick a level, the renderer shades fragments in 2×2 groups (quads) so it can subtract neighbouring texture coordinates and get how fast they change per screen pixel (§8, P6, ADR-15). Three steps:

  1. Take the four differences ∂u/∂x, ∂v/∂x, ∂u/∂y, ∂v/∂y from the quad (§8).
  2. Compute ρ as the larger of the two vector lengths times the texture width, then LOD = log2(ρ) (§8).
  3. Use level floor(LOD) and, for trilinear filtering, blend with the next level by frac(LOD) (§8). Each level is sampled by bilinear filtering, a weighted average of the four nearest texels (§8, §38).

Camera distance is rejected as the input because a grazing surface at the same distance needs a different level (MM7). If a triangle edge cuts a quad, lanes outside the triangle borrow the nearest valid lane's derivative to avoid NaN values (§8, FM-6).

MSAA: shade once, cover many (§8, P10, I11)

Multisample antialiasing (MSAA) samples coverage at several positions per pixel but runs the fragment shader only once per pixel (P10). The steps (§21.2):

  1. Evaluate each sample position against the three edge functions to build a coverage mask. This design uses a fixed 4-sample rotated grid (ADR-17, §21.2).
  2. Run the shader once, and write its colour to every sample that is covered and passes its own depth test.
  3. At resolve, average the covered, shaded samples. Uncovered samples keep an explicit clear colour so they never contribute garbage (§8, I11).

If shading ran per sample instead, the design would be paying for supersampling (MM9, P10). Blending is fixed pipeline state applied after shading, not code inside the shader (P14, ADR-16).

Tiles: cache locality, ownership and determinism (§3, P5, P9, P11, I5, I7)

The framebuffer is cut into 64×64 tiles (ADR-05). The binner records which triangles touch which tile, and a rayon fork runs each tile on one thread against its own slice (§3, ADR-18). The blueprint says tiling exists for cache locality, not merely for parallelism (P11). Because tile slices are disjoint borrows, Rust's borrow checker rather than a test enforces that no two threads write the same pixel (§3, I5, §22.2). The blueprint also says a tile boundary acts as "a second, coarser fill rule", so tile-edge bugs are the same bug as shared-edge cracks (MM5).

For the 1920×1080 example, the blueprint gives 30 × 17 = 510 tiles, and, assuming an average of 40 binned primitives at roughly 64 bytes each, 2,560 bytes of bins per tile (§34). The blueprint contradicts itself on scheduling: P9 says the fixed processing order "forecloses greedy work-stealing schedules", while §3 makes rayon's work-stealing scheduler the tile scheduler and §22.6, §31 and FM-12 rely on it to balance uneven tiles (P9, §3, §22.6, §31, FM-12). It does not reconcile the two.

The trade-offs — where engineers disagree

Fixed-point edge functions (ADR-02, ADR-03)

Chosen: 24.8 fixed-point arithmetic, which gives exact, deterministic sign tests on shared edges; the 8 fractional bits balance guard-band range against positional accuracy (§9, P1, I1). Rejected: pure f32 or f64 arithmetic; 4 or 16 fractional bits (§9). When the rejected choice is right: pure float wins when prototyping without bit-exact reproducibility, or on a platform whose integer units are weak relative to float. 4 fractional bits wins on very large virtual canvases where range matters more than accuracy (§9).

Tiled edge functions instead of scanlines (ADR-04)

Chosen: half-space (edge-function) rasterization with tiles and binning, which trivially parallelizes per pixel (§9, Pineda 1988 as cited in §9). Rejected: scanline with an active edge table, and per-triangle immediate mode (§9). When the rejected choice is right: scanline wins for wireframe or line-only debug views and for very thin slivers, where a bounding box wastes work (§9). §36 adds that the active edge table is sequential per scanline, which fights tiling (§36).

Guard band instead of always clipping (ADR-06)

Chosen: a guard-band fast path, with full clipping only at the near and far planes or on overflow, because most triangles never cross the near plane (§9, P13). Rejected: running full Sutherland-Hodgman on every triangle, or clipping only on demand (§9). When the rejected choice is right: always-clip wins when geometry is guaranteed pre-clipped offline and simplicity outweighs per-triangle cost (§9).

Early-Z unless the shader says otherwise (ADR-10)

Chosen: test depth before shading, and fall back to late-Z when a shader declares it discards or writes depth. The shader trait declares this statically (§9, P7, I10). Rejected: always testing depth after shading (§9). When the rejected choice is right: when every shader in the pipeline discards or writes depth, so early-Z bookkeeping is pure overhead (§9).

Trait objects for shaders (ADR-11)

Chosen: dyn VertexShader and dyn FragmentShader, giving shaders that can be swapped at runtime at an acceptable vtable cost compared with shading work (§9). Rejected: generics through monomorphization, and a bytecode interpreter (§9). When the rejected choice is right: generics win when the shader set is fixed at compile time and raw throughput outweighs runtime swapping (§9). The shader code is compiled Rust, so the trust boundary is at compile time (T8).

Pinned reproducibility (ADR-24)

Chosen: a pinned thread count or deterministic reduction order, pinned FMA contraction (fused multiply-add) and a pinned SIMD path per build, which the bit-identical guarantees need (§9, I7, I8). Rejected: best-effort reproducibility with no pinning (§9). When the rejected choice is right: interactive real-time use, where frame-to-frame bit identity does not matter (§9).

Roads not taken (§36, §37)

Scanline / active edge table (§36) wins for single-threaded, immediate-mode drawing of large polygons with few triangles, as in 1990s software rendering and vector-art fills. It loses here because each scanline's edge list depends on the previous one, which is hostile to tile parallelism (§36).

Ray-traced visibility (§36) wins when visibility cost should scale logarithmically with scene complexity, or when secondary rays are unavoidable, as in physically based global illumination. It loses here because this project bets on projection plus a depth buffer and a fill-rate-bound cost model that maps onto tiled, cache-friendly hardware (§36, §1).

Deferred / visibility buffer (§36) wins in scenes with extreme shader complexity and heavy overdraw, where shading each pixel once matters more than simplicity. It loses here because the extra full-screen pass and reconstruction step would obscure the one-pass pipeline the blueprint is built to teach (§36).

Sort-last parallelism (§36) wins when the triangle count is very small and fixed relative to the screen, so per-thread full-screen buffers are affordable. It loses here because those buffers multiply memory by thread count and the final depth merge is a serial point that disjoint tiles avoid (§36).

Deferred features (§37) each wait for a trigger. The live window (raster-window) waits until the offline path is regression-locked. Anisotropic filtering waits until a scene needs grazing-angle quality beyond isotropic trilinear. A logarithmic depth buffer waits until a scene's near-to-far ratio exceeds about 10,000 to 1 (§37, ADR-09).

What must never be false

  • I1: every pixel of a watertight mesh is covered exactly once. Noticed by a coverage-count fixture and a coverage-mismatch counter; there is no runtime recovery, only a build-time fix (§7).
  • I2: clipping never lets a vertex with non-positive w reach the divide. Noticed by a fixture with a triangle straddling the eye plane and a clip-degenerate counter; the runtime response is to discard the primitive and log it (§7).
  • I3 and I4: depth comparisons match the declared compare function, and interpolation is perspective-correct. Noticed by a monotonicity property test with depth-test counters (I3) and an analytic checkerboard fixture with no telemetry (I4) (§7).
  • I5: only a tile's owning thread writes that tile's fragments. Noticed by ThreadSanitizer in CI; the disjoint-slice design does not compile otherwise (§7).
  • I6: mip level derives from screen-space derivatives, never a constant heuristic. Noticed by a derivative-versus-analytic-LOD fixture and a LOD histogram in FrameStats (§7).
  • I7: the single-threaded and tiled paths produce bit-identical framebuffers. Noticed by a byte-diff fixture on every Phase 11 CI run and a reproducibility-diff counter that must be zero (§7).
  • I8: the same input at the same thread count renders byte-identical twice. Noticed by a double-render diff in CI and a frame-hash mismatch counter (§7).
  • I9: subpixel coordinates never overflow the fixed-point range without triggering the guard-band path. Noticed by a guard-band-overflow fixture and counter; recovery is a full re-clip (§7, FM-7).
  • I10 and I11: early-Z applies only to shaders declaring no discard and no depth write, and the MSAA resolve equals the coverage-weighted average of shaded samples. Noticed by a unit test with an early-Z-bypass counter (I10) and the black-hole-at-edges fixture (I11) (§7).
  • I12: texture sampling never reads outside the wrap mode's range. Noticed by a fuzz test over out-of-range UVs and an out-of-range-sample counter; recovery is to clamp per wrap mode (§7).
  • I13: clip output never exceeds seven triangles per input triangle. Noticed by a degenerate-geometry fixture, a debug assertion and a clip-amplification-max counter (§7).

The blueprint says I1, I2, I4, I6 and I13 are caught "exclusively" by fixtures and property tests before merge, "never at runtime in a release build" (§7). Yet the I2 row gives a runtime recovery (discard the primitive and log it), the I1, I2, I6 and I13 rows list counters, and FM-5 and T6 describe discarding triangles at run time (§7, §25, §24). It does not say which reading governs.

What breaks in production

This is a library and CLI, so there is no live production traffic. A conformance or differential regression blocks the merge instead of paging anyone, and the "alerts" are CI failures (§26).

FM-1 and FM-2: cracks, then double-blended seams. Pixels go missing, or are drawn twice and show up as seams under blending, between adjacent triangles. The root cause is a fill-rule inconsistency or shared-edge arithmetic that differs between the two triangles (P1). Detection is fx_2_watertight_coverage and fx_10_tile_boundary_coverage. There is no automatic recovery. The fix is to use one canonical arithmetic order per shared edge, guided by the crack-seam-triage runbook (§25).

FM-3: texture swimming. Textures warp on receding surfaces. The cause is that perspective-correct interpolation is disabled or missing (P3). Detection is fx_4_checkerboard_receding. Manual recovery applies the §8 formula and checks it with the --disable-perspective-correction toggle (§25).

FM-4: z-fighting. Coplanar surfaces shimmer because depth precision is too coarse or the near plane is too far out (P4). Detection is fx_3_zfighting_threshold. Recovery is moving the near plane closer or adopting reverse-Z, with a z-fighting-diagnosis runbook (§25, ADR-09).

FM-5: garbage or flipped triangles near the camera. The cause is clipping after the divide, or testing w > 0 instead of w > ε (P2, I2). Detection is fx_5_near_plane_straddle and fx_5_fully_behind_eye. Auto-recovery discards a triangle found with w ≤ ε after the fact; manual recovery fixes the clip-stage plane-test order (§25).

FM-9: non-reproducible frames. Output differs across runs, threads or SIMD paths because FMA contraction or lane order was not pinned (ADR-24, I7, I8). Detection is fx_10_thread_reproducibility and fx_11_simd_equivalence. There is no auto-recovery; the fix is pinning, using the reference-image regression bisect runbook (§25).

FM-12: poor parallel speedup. Triangles bunch in a few tiles, or adjacent tile buffers share cache lines (false sharing). Detection is fx_10_uneven_load_distribution and the per-tile time histogram. Rayon's work-stealing mitigates it partially; manual recovery pads tile buffers to cache-line boundaries (§25, §30).

Threats worth knowing (§24):

  • T1, a crafted glTF mesh file that exploits the parser, is met by strict schema validation and bounded allocation before parsing, plus a fuzz target. A bad file is rejected with no partial state (§24).
  • T2, a crafted index that points past the vertex buffer, is met by bounds-checking every index before vertex fetch. The triangle is discarded and counted as dropped (§24).
  • T5, a texture that claims enormous decoded dimensions (a decompression bomb), is met by a pre-decode check against the 4096×4096 limit; the load falls back to a default texture (§24, §4).
  • T8, an untrusted third-party shader, is met by making shaders compiled Rust, so the trust boundary is at build time. The blueprint says to document it in SECURITY.md (§24, ADR-11).
  • T9, a mesh built so every triangle straddles all six clip planes, is bounded by I13's analytic limit, so total cost stays linear in triangle count (§24, I13).

The blueprint disagrees with itself in a few places on these figures. Both sides are given here, unresolved.

  • Thread scaling. §4 gives 5M tri/s and 100M px/s for one thread and 45M tri/s and 800M px/s for eight, while M8 asks for a speedup of at least 5.5x and §22.4 calls "sub-8×" speedup expected because of setup and binning overhead; §3 makes binning the last single-threaded stage (§4, M8, §22.4, §3).
  • MSAA samples. §4 lists 4 samples with "8 optional", while ADR-17 locks a fixed 4-sample rotated grid and §21.10 fixes the sample pattern at build time (§4, ADR-17, §21.10).
  • Thread count and identical frames. I7 and §22.4 require byte-identical output between 1 and 8 threads. §27 says thread count is part of the reproducibility contract and changing it across builds is "not guaranteed" to give identical frames, and I8 is stated for identical thread count (I7, §22.4, §27, I8).

How it compares

  • Mesa llvmpipe also bins into tiles, but JIT-compiles each shader to native code at draw time, trading compile latency for near-native throughput. That fits a production driver fallback that must run arbitrary, changing shaders; this design uses compiled trait objects instead (§33, ADR-11).
  • SwiftShader targets exact D3D/Vulkan/OpenGL precision rules and recompiles shaders dynamically. That suits headless Chrome and CI screenshots, where agreement with a real GPU is the whole point, and it supports anisotropic filtering that this design defers (§33, §37).
  • Larrabee (as published) made the rasterizer itself software on many general x86 cores, with software binning at scale. That wins when programmability of every stage is worth more than fixed-function efficiency, though the product never shipped as a GPU (§33).
  • tinyrenderer draws per triangle with no tiling and no conformance target. That is the shortest path to a first triangle on screen, at the cost of shortcuts such as skipping perspective-correct interpolation that this design avoids (§33, §5).
  • A hardware GPU pipeline fixes rasterization, blend and depth in silicon and makes only shading programmable. That wins whenever throughput per watt matters more than being able to modify the rasterizer, which is the axis this project makes legible instead of competing on (§33).

Questions to test yourself

  1. Why must clipping happen strictly before perspective divide, and what exact numeric symptom appears if you get the order backward? — Hint: §8's frustum conditions and the degenerate-input examples, then I2.
  2. What is the precise relationship between the top-left fill rule and I1's "exactly once" coverage guarantee — why does the rule need to be a shared convention rather than each triangle picking independently? — Hint: P1 and the edge-function block in §8.
  3. What is the concrete mechanism by which tiling improves performance, and why does section 30 insist on measuring cache-miss rate directly rather than trusting wall-clock speedup alone as proof? — Hint: P11, MM2 and the profiling paragraph of §30.
  4. Why is frame reproducibility (I7, I8) described as a property that must be actively pinned rather than one that "just happens" from deterministic code — name three specific sources of nondeterminism this project must suppress. — Hint: MM8 and ADR-24, then §27.
  5. Why is the guard-band approach (ADR-06) preferred over always-clipping, and under what scene characteristic does that preference reverse? — Hint: P13 and the ADR-06 row in §9.

If you only remember three things

Decide who owns each pixel with one exact, shared rule, computed in fixed-point so both triangles agree (P1, ADR-02, I1). Clip before you divide, and interpolate attribute/w rather than the attribute itself (P2, P3). Tiles exist for cache locality as much as for threads, and identical output across threads only holds because order and floating-point behaviour are pinned (P11, I7, ADR-24).

Words used here

  • Rasterization: finding which pixels a triangle covers, treated as a point-in-triangle test on a grid (MM1, §1).
  • Homogeneous coordinate (w): a fourth number that lets projection be a matrix multiply; the divide by it must come after clipping (§38, MM3).
  • Edge function: a formula zero on a triangle edge, with one sign on each side; the inside test (§38).
  • Fill rule (top-left rule): the convention that gives a pixel on a shared edge to exactly one triangle (§38, P1).
  • Fixed-point (24.8): numbers with an implicit scale, here 24 whole bits and 8 fractional bits (§38, §8).
  • Perspective-correct interpolation: interpolating attribute/w and 1/w, then dividing (§38, §8).
  • Guard band: an extended screen region where triangles skip full clipping (§38, P13).
  • Mipmap and LOD: a pyramid of smaller texture copies, and the level chosen from derivatives (§38, §8).
  • MSAA: sampling coverage at several positions per pixel while shading once per pixel (§38, P10).
