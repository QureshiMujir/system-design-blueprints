169 — Software Rasterizer / 3D Renderer

Project Number: 169

Project Name: Software Rasterizer / 3D Renderer

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch in Rust, a CPU-only software rasterizer implementing the full fixed-function-plus-programmable real-time graphics pipeline: vertex fetch and transformation through the model/view/projection chain, homogeneous clipping against all six frustum planes, perspective division and viewport mapping, backface culling, triangle setup via the edge-function formulation, scanline/tiled rasterization enforcing an exact top-left fill rule, perspective-correct attribute interpolation, a depth buffer with early-Z rejection, programmable vertex and fragment shader stages exposed as Rust traits, texture sampling with bilinear filtering and mipmapping whose LOD derives from screen-space derivatives, alpha blending, multisample antialiasing, and a tiled multithreaded binning architecture that parallelizes rasterization across CPU cores. The system consumes typed vertex/index buffers plus shader implementations and produces a deterministic color+depth framebuffer, resolvable to PNG/PPM. It is a rendering library and CLI renderer, not a game engine, an asset pipeline, or a windowing framework.

Phase-0 deliverable — crates:

  1. raster-math — Vec2/Vec3/Vec4/Mat4 types, fixed-point subpixel arithmetic.
  2. raster-core — pipeline stages: vertex fetch through framebuffer resolve.
  3. raster-shade — VertexShader/FragmentShader traits, sampler, texture, blend state.
  4. raster-io — PPM/PNG writer, glTF 2.0 mesh/texture ingestion.
  5. raster-cli — command-line driver: load scene description, render N frames, write image.
  6. raster-window (Phase 11+, PhaseDeferred("§23")) — interactive winit-backed live viewer.
  7. raster-conformance — fixture harness, reference-image diffing, coverage counters.

Boundaries — provides: the full CPU rasterization pipeline described above, a minimal glTF 2.0 mesh/material loader, PPM/PNG output, a deterministic single-threaded reference path and a tiled multithreaded path guaranteed bit-identical to it (I7). Delegates: windowing/input to winit (Phase 11, optional), image decode of source textures to a vetted png/image crate, scene authoring to external DCC tools that export glTF. Does NOT provide: a GPU backend of any kind, a shading language or compiler, a scene graph, animation/skinning, physically based light transport, denoising, or an asset editor.

Non-goals: no GPU backend — this is a CPU-bound reference and learning artifact, not a competitor to hardware rasterizers on speed; this is not the Ray Tracer (rank 170) — that sibling project solves visibility by tracing rays through the scene and solves light transport stochastically (path tracing, importance sampling, Monte Carlo integration), while this project solves visibility by projecting geometry through the MVP chain and scan-converting it against a depth buffer, with its defining engineering concerns being the rasterization fill rules (I1, P1), perspective-correct interpolation (P3, section 8), and the tile-local memory-access pattern (P11, section 30) — none of that path-tracing material is re-specified here; no full scene/asset system (materials are flat structs, not a node graph, section 11); no soft shadows, global illumination, or a post-process stack.

Deployment model: (a) a Rust library (raster-core + raster-shade) linked into host programs; (b) a CLI renderer (raster-cli) that reads a scene manifest and shader selection and writes a framebuffer to disk, suited to batch/CI regression rendering; (c) an interactive window mode (Phase 11, optional) for live camera manipulation during development. Users/operators: graphics engineers learning the pipeline, CI systems running conformance regression (section 28), and downstream blueprint consumers (Game-Engine-Core, rank 172) that link raster-core as their renderer.

What later phases unlock: Phase 3 (depth buffer) unlocks correct hidden-surface removal for arbitrary draw order; Phase 5 (clipping) unlocks cameras with geometry crossing the near plane; Phase 6 (programmable shading) unlocks material variety without touching pipeline internals; Phase 8 (mipmapping) unlocks minification without aliasing; Phase 10 (tiling) unlocks multi-core throughput; Phase 11 unlocks CI-gated correctness across every prior phase simultaneously.

Language: Rust — memory safety without a GC pause in the hot per-pixel loop, #[repr(C)] control over buffer layout for SIMD and cache-line alignment, rayon for the tile-parallel fork-join without a hand-rolled thread pool, and a trait-object-vs-generics choice for the shader stage (ADR-11). Rejected: C++ (memory-safety footguns in exactly the code — raw pixel-buffer writes — where this project spends most of its time; no built-in data-parallel work-stealing without a third-party library); C (no traits, manual vtables for the shader stage, no borrow checker to machine-check the tile-ownership invariant I5); Zig (immature ecosystem for the image/png/glTF crates this project depends on for I/O, forcing a costly reimplementation). Prerequisites: linear algebra (matrix composition, homogeneous coordinates), projective geometry (why clipping precedes perspective divide), sampling theory (Nyquist/aliasing, for mipmap LOD and MSAA). Timeline: 12 phases (Phase 0–11), each independently deliverable and gated by conformance fixtures. Deferrals: interactive window mode is PhaseDeferred("§23") (built in Phase 11 alongside the conformance harness, only after the offline path is regression-locked); anisotropic filtering is PhaseDeferred("§20") (Phase 8 ships isotropic trilinear only; see section 37 un-defer trigger); a logarithmic depth buffer is PhaseDeferred("§15") (Phase 3 ships the standard OpenGL depth mapping; log-depth remains a documented extension point).

2. Why Build This

  • Legibility: every matrix multiply, clip, divide, and blend is inspectable Rust, not a driver black box.
  • Pipeline literacy: real-time graphics papers since Catmull assume fluency with triangle setup, fill rules, and Z-buffering as background knowledge.
  • Numerical precision as a first-class concern: fixed-point subpixel coordinates, IEEE 754 rounding, and depth-precision tradeoffs are load-bearing, not incidental.
  • Memory-access-pattern intuition: tiling exists because cache misses dominate a flat framebuffer; building the tiled path makes the Drepper 2007 argument concrete.
  • A reusable, dependency-light renderer for offline/embedded/no-GPU contexts (CI screenshot generation, headless test rendering, CAD-style bit-exact reproducibility).
  • A direct contrast case against the Ray Tracer (rank 170): building both makes the visibility-algorithm design space (rasterize-and-Z-test vs. trace-and-intersect) concrete rather than a textbook abstraction.

What Mastery Looks Like

  • Deriving the top-left fill rule from first principles and explaining why its absence produces cracks or double-blended seams (Phase 2).
  • Explaining why clipping must precede perspective divide, with a concrete w≤0 counterexample (Phase 5).
  • Deriving perspective-correct interpolation from the 1/w-linearity property and reproducing the "swimming texture" bug on demand by disabling it (Phase 4).
  • Reading a screen-space derivative and predicting the chosen mip LOD without running the renderer (Phase 8).
  • Explaining, with a memory-bandwidth calculation, why tile-local framebuffers beat a flat buffer (Phase 10, section 34).
  • Producing a bit-identical framebuffer from the single-threaded and tiled-parallel code paths on the same input (Phase 10, Phase 11).
  • Diagnosing a z-fighting artifact from the depth-precision equation rather than by trial-and-error bias tuning (Phase 3, section 8).

Vertex Fetch reads VertexBuffer/IndexBuffer in a fixed, reproducible order (P9), streaming raw Vertex records to the next stage with no reordering — the deterministic-order guarantee this stage provides is what makes I7/I8's bit-identical-frame promise possible downstream, since every later stage's parallelism is layered on top of an otherwise-deterministic sequence.

Vertex Shader is a user-supplied VertexShader trait implementation (ADR-11), invoked once per vertex, transforming object-space attributes through the MVP chain into clip space plus an arbitrary bag of interpolable ShaderVaryings. It is the first extension point in the pipeline and the only stage before clipping that can be swapped without touching pipeline internals (Phase 6).

Primitive Assembly groups three already-shaded vertices, addressed by an index triple from the IndexBuffer, into a Triangle. It performs no math of its own; it exists as a distinct stage because clipping (next) operates on whole polygons, not individual vertices.

Homogeneous Clipping runs Sutherland-Hodgman against all six frustum planes in clip space, strictly before perspective divide (P2, I2), producing a fan of zero to seven triangles from the worst-case nine-vertex clipped polygon (I13). The guard-band fast path (P13, ADR-06) skips this stage's full cost for triangles safely within an extended screen margin.

Perspective Divide + Viewport Transform converts clip space to NDC via the per-component divide by w, then to screen-pixel coordinates via the viewport equations (P3, section 8) — this is the single stage where the "perspective" in perspective-correct interpolation is actually applied to position; attributes are deferred to the fragment stage precisely so they can be divided per-pixel instead (P3's tradeoff).

Backface Cull discards triangles whose signed screen-space area has the wrong sign for the configured winding (ADR-07), reusing the same area computation triangle setup needs next, so the two stages share one arithmetic pass in the actual implementation even though they are drawn as separate boxes here.

Triangle Setup computes the three edge-function coefficients, the per-vertex reciprocal-w values, and the screen-space bounding box in fixed-point subpixel coordinates (Pineda 1988, P1, P8) — everything the tile rasterizer needs is fully precomputed here so the per-tile parallel stage below never re-derives per-triangle state.

Tile Binner assigns each TriangleSetup to every tile its bounding box overlaps (sort-middle, ADR-04), producing the BinnedPrimitive records that seed each tile's TileBin. This is the last single-threaded stage; everything after it runs inside the per-tile parallel boundary.

The per-tile parallel boundary is exactly the rayon fork shown in the diagram: from this point forward, each tile's Early-Z test, Fragment Shader invocation, and Blending run independently and write only to that tile's private color/depth (and MSAA sample) slice — no shared mutable state crosses a tile boundary at any point (I5, P5, P11), and the Rust borrow checker, not a runtime check, is what makes this true (section 11, ADR-18).

Texture Unit backs the Fragment Shader's texture-sampling calls with bilinear/trilinear filtering and derivative-based mip LOD selection (P6, Williams 1983); it is drawn adjacent to, not inside, the Fragment Shader box because it is invoked by shader code rather than being a fixed pipeline stage itself.

Framebuffer Resolve runs after the join barrier, copying (or, under MSAA, averaging per I11) each tile's local buffers into the single global Framebuffer — this step is itself disjoint and trivially parallel-safe since tiles never overlap, even though it executes after the fork-join barrier closes.

Output Writer encodes the resolved Framebuffer to PNG or PPM (section 5 RFCs), performing the linear-to-sRGB conversion at this final step, never earlier, so no intermediate stage operates on gamma-encoded values.

Tile Scheduler is rayon's work-stealing scheduler (ADR-18) operating over the list of non-empty tiles; it is what keeps Phase 10's parallel speedup close to linear despite uneven per-tile triangle density (FM-12), by letting idle threads steal unprocessed tiles from busier ones rather than following a static, pre-partitioned assignment.

6. Design Principles

P1 — Exact, shared fill rule. Every edge shared by two triangles is classified identically by both, using the top-left rule, so a pixel on the edge is covered by exactly one of the two triangles. Tradeoff: requires consistent winding order and bit-identical fixed-point arithmetic on both triangles sharing the edge. Operational implication: shared-edge coefficients must be derived from the same vertex data with the same arithmetic order on both sides. Violating this breaks the system: double-coverage shows as seams under blending; no-coverage shows as cracks (I1).

P2 — Clip before divide. Clipping always precedes perspective division; clip-space vertices with w≤0 never reach the divide. Tradeoff: adds a full Sutherland-Hodgman pass even for triangles that are already entirely inside. Operational implication: a fast bounding test (all w>0 and inside all six planes) skips clipping in the common case (ADR-06). Violating this breaks the system: dividing by a non-positive w produces a mirrored or garbage triangle (I2).

P3 — Perspective-correct by construction. Attribute/w and 1/w are interpolated linearly in screen space; the true attribute is recovered by a per-pixel divide. Tradeoff: roughly 2× the interpolation work plus a divide versus a naive screen-space lerp. Operational implication: 1/w is cached once per vertex at triangle setup, not recomputed per pixel. Violating this breaks the system: textures swim and warp on receding geometry — interpolating in screen space is the classic wrong answer that looks right on flat geometry.

P4 — Depth is screen-space linear; world z is not. z/w (NDC depth) is interpolated linearly in screen space; eye-space z is never interpolated directly. Tradeoff: depth precision is nonuniform, concentrated near the near plane. Operational implication: near-plane placement, not depth-buffer bit depth alone, is the primary lever against z-fighting. Violating this breaks the system: either garbage depth values from interpolating an incompatible representation, or catastrophic near-plane precision loss.

P5 — Tile ownership is exclusive. A tile's fragments are written by exactly one thread for the tile's lifetime. Tradeoff: primitives overlapping many tiles are cost-duplicated into every bin they touch. Operational implication: bin memory scales with average tile-overlap, not unique triangle count (section 34). Violating this breaks the system: framebuffer races and nondeterministic corrupted pixels (I5).

P6 — LOD derives from derivatives, never a heuristic. Mip level is computed per fragment from the screen-space partial derivatives of the texture coordinate (quad finite differences), never a fixed distance heuristic. Tradeoff: requires evaluating fragments in 2×2 quads even at triangle boundaries, wasting some off-triangle lane work. Operational implication: single-pixel or quad-edge triangles need a special-cased derivative fallback. Violating this breaks the system: textures alias at grazing angles, or blur when they should not, or LOD pops at quad seams (I6).

P7 — Early-Z before shading, gated by the declared shader contract. Depth test runs before the fragment shader unless the shader declares it discards or writes depth. Tradeoff: discarding/depth-writing shaders forfeit the early-Z skip. Operational implication: the FragmentShader trait declares this contract statically so the pipeline can choose early- vs. late-Z (ADR-10). Violating this breaks the system: wasted shading on occluded fragments, or incorrect results if a discarding shader is early-Z'd unconditionally.

P8 — Subpixel precision is fixed-point, not float. Screen coordinates are quantized to a fixed number of subpixel bits (24.8, I9) before edge-function evaluation. Tradeoff: a hard ceiling on screen coordinate range and subpixel accuracy. Operational implication: guard-band clipping (ADR-06) bounds how far off-screen a vertex may sit before subpixel overflow. Violating this breaks the system: cracks between triangles from inconsistent floating-point rounding on shared edges.

P9 — Deterministic processing order. Within a frame, vertex fetch and per-tile binned-primitive processing follow a fixed, reproducible order. Tradeoff: forecloses greedy work-stealing schedules that would otherwise balance load better. Operational implication: bit-identical frames (I8) require a stable primitive order per tile, not merely per frame. Violating this breaks the system: a blend-order-sensitive scene renders differently run to run.

P10 — One shader invocation per covered pixel under MSAA. The fragment shader runs once per pixel; its result is written to every covered, depth-passing sample. Tradeoff: shading detail itself is not supersampled, only edges are antialiased. Operational implication: the coverage mask is computed per-sample at rasterization time, independent of shading. Violating this breaks the system: N× shading cost for N samples, defeating the entire reason MSAA is cheaper than supersampling.

P11 — Tiling exists for cache locality, not merely parallelism. Tile dimensions are chosen so a tile's color+depth (×MSAA) fits the target cache level. Tradeoff: small tiles raise binning overhead per triangle; large tiles blow the cache budget. Operational implication: tile size is a validated, tunable decision (ADR-05), not a fixed constant. Violating this breaks the system: cache-thrashing framebuffer writes dominate fill rate — exactly the pre-tiling failure mode this architecture exists to avoid.

P12 — Conformance beats taste. Fill convention, interpolation semantics, and clip behavior are specified against the OpenGL rasterization rules (section 5). Tradeoff: some "more correct-looking" fill choices are rejected because they diverge from the reference spec. Operational implication: conformance fixtures (N.5) assert against the spec's stated behavior, not against "looks right." Violating this breaks the system: silent incompatibility with reference images from real GPU drivers, invalidating differential testing (section 28).

P13 — Guard-band over full re-clip when safe. Triangles within the guard band skip full Sutherland-Hodgman clipping; only near/far-plane crossings or guard-band overflow force a full clip. Tradeoff: the guard band consumes part of the fixed-point coordinate range (interacts with P8). Operational implication: guard-band size is derived from the fixed-point range, not chosen arbitrarily (ADR-06). Violating this breaks the system: silently wrong rasterization for extreme off-screen triangles whose subpixel coordinates overflow.

P14 — Blending is declared pipeline state, not per-fragment improvisation. Blend factors and the depth-compare function are fixed state (BlendState, DepthState) set before a draw, not decided inside the fragment shader. Tradeoff: order-independent transparency techniques are out of reach without extra passes. Operational implication: the blend equation is evaluated once, uniformly, by the tile rasterizer after shading — never inside shader code. Violating this breaks the system: nondeterministic blend order interacting with P9, and untestable per-fragment blend logic.

8. Domain Model

Model/view/projection composition:

M_mvp = M_proj · M_view · M_model

Perspective-projection matrix (right-handed, OpenGL depth convention, f = 1/tan(fov_y/2)):

        ⎡ f/aspect   0        0                        0                 ⎤
M_proj = ⎢ 0          f        0                        0                 ⎥
        ⎢ 0          0   (far+near)/(near−far)   (2·far·near)/(near−far) ⎥
        ⎣ 0          0        −1                       0                 ⎦

Homogeneous clip-space frustum conditions (all six planes, locked to the OpenGL convention, ADR-08):

−w ≤ x ≤ w      −w ≤ y ≤ w      −w ≤ z ≤ w      w > ε

Sutherland–Hodgman clip interpolation parameter, for polygon edge A→B against a plane with signed distances d_A, d_B:

t = d_A / (d_A − d_B)          clipped_vertex = lerp(A, B, t)   (in clip space, pre-divide)

Perspective divide and viewport transform:

NDC:    (x_ndc, y_ndc, z_ndc) = (x/w, y/w, z/w)
Screen: sx = (x_ndc + 1)·0.5·viewport.width  + viewport.x
        sy = (1 − y_ndc)·0.5·viewport.height + viewport.y
        depth = (z_ndc + 1)·0.5

Edge function (Pineda 1988), sign convention and top-left fill rule stated exactly:

E_i(x, y) = (x − x_a)(y_b − y_a) − (y − y_a)(x_b − x_a)

is_top_left(edge) := (edge.dy < 0)  OR  (edge.dy == 0 AND edge.dx > 0)
inside_i          := (E_i > 0)  OR  (E_i == 0 AND is_top_left(edge_i))
pixel is inside triangle iff inside_0 AND inside_1 AND inside_2

Barycentric coordinates from edge functions:

2A = E0 + E1 + E2      (signed double area, evaluated once per triangle)
λ0 = E1(x,y) / 2A      λ1 = E2(x,y) / 2A      λ2 = E0(x,y) / 2A      λ0+λ1+λ2 = 1

Perspective-correct interpolation (1/w interpolation, division per attribute):

(a/w)_screen = λ0·(a0/w0) + λ1·(a1/w1) + λ2·(a2/w2)
(1/w)_screen = λ0·(1/w0)  + λ1·(1/w1)  + λ2·(1/w2)
a            = (a/w)_screen / (1/w)_screen

Depth interpolation — z/w is screen-space linear by construction of M_proj; world-space z is not:

z_screen = λ0·z0_ndc + λ1·z1_ndc + λ2·z2_ndc            (valid: z_ndc affine in 1/w_eye)
z_world  = 1 / (1/w)_screen  restated via w_eye recovery, NOT a direct lerp of world z

Mipmap LOD equation from screen-space derivatives:

ρ   = max( √((∂u/∂x)²+(∂v/∂x)²), √((∂u/∂y)²+(∂v/∂y)²) ) · texture.width_texels
LOD = log2(ρ)
mip = clamp(floor(LOD), 0, mip_count−1);  trilinear blends mip, mip+1 by frac(LOD)

Bilinear filter weights (fu, fv fractional texel offsets):

texel(u,v) = (1−fu)(1−fv)·T[i,j] + fu(1−fv)·T[i+1,j] + (1−fu)fv·T[i,j+1] + fu·fv·T[i+1,j+1]

Alpha-blending equation (standard "over" compositing):

C_out = C_src · F_src + C_dst · F_dst        F_src = SRC_ALPHA, F_dst = ONE_MINUS_SRC_ALPHA

MSAA coverage-and-resolve arithmetic:

coverage_mask = { k ∈ [1..N] : E_i(sample_k) satisfies inside_i for all i }
C_resolved    = (1/N) · Σ_{k=1..N} C_sample_k     (uncovered samples retain clear color, I11)

Worked numeric example — one triangle, object space to three shaded pixels. Object-space triangle v0=(0,0,0), v1=(1,0,0), v2=(0,1,0); uv0=(0,0), uv1=(1,0), uv2=(0,1). Model = identity. Camera at the origin looking down −Z; the triangle sits at eye-space z=−3 (so v0_eye=(0,0,−3), v1_eye=(1,0,−3), v2_eye=(0,1,−3)). fov_y=90°, aspect=1, near=1, far=100, so f=1/tan(45°)=1. With M_proj row [0,0,−1,0], w=−z_eye=3 for all three vertices. x_clip=x_eye, y_clip=y_eye (since f/aspect=f=1): v0_clip=(0,0,z_c,3), v1_clip=(1,0,z_c,3), v2_clip=(0,1,z_c,3). z_clip=(far+near)/(near−far)·z_eye+2·far·near/(near−far) = (101/−99)·(−3)+(200/−99) = (303−200)/99 = 1.0404; z_ndc=1.0404/3=0.3468 for all three (fronto-parallel triangle — note perspective correction here numerically matches screen-linear since all three w equal 3; the receding-plane fixture in Phase 4, N.5, is where the divergence is visible). NDC: v0=(0,0,0.3468), v1=(0.3333,0,0.3468), v2=(0,0.3333,0.3468). Viewport 512×512 at origin: sx=(x_ndc+1)·256, sy=(1−y_ndc)·256 → P0=(256,256), P1=(341.33,256), P2=(256,170.67); depth=(z_ndc+1)/2=0.6734 for all three.

Sample pixel center (280.5, 240.5): edge0 (P0→P1, Δ=(85.33,0)): E0 = −85.33·(y−256) = −85.33·(−15.5) = 1322.6. edge1 (P1→P2, Δ=(−85.33,−85.33)): E1 = −85.33·[(x−341.33)−(y−256)] = −85.33·(−45.33) = 3868.0. edge2 (P2→P0, Δ=(0,85.33)): E2 = 85.33·(x−256) = 85.33·24.5 = 2090.6. All positive → inside. 2A = 1322.6+3868.0+2090.6 = 7281.2, matching the analytic 2·(0.5·85.33·85.33) = 7281.2 (arithmetic self-check). λ0=E1/2A=0.5312, λ1=E2/2A=0.2871, λ2=E0/2A=0.1817, sum=1.0000. Since all w=3, perspective-correct UV equals screen-linear UV here: u=λ0·0+λ1·1+λ2·0=0.2871, v=λ0·0+λ1·0+λ2·1=0.1817. Depth: z_screen=0.6734 (flat, as expected). Neighboring quad pixels (281.5,240.5) and (280.5,241.5) repeat the same edge-function arithmetic with Δx=1 or Δy=1 shifts, producing ∂u/∂x, ∂u/∂y, ∂v/∂x, ∂v/∂y via finite differences — feeding the Phase 8 LOD equation directly.

Degenerate-input examples: zero-area triangle (2A=0) is discarded at triangle setup before binning (I13-adjacent, "SetUp→Discarded" edge above); a triangle entirely behind the eye has all three w≤0 after the attempted transform and is rejected at the clip stage before divide (I2, "ClipTested→Rejected"); a vertex exactly on a clip plane (d=0) is classified "inside" by the ≥0 convention, consistent with the top-left-style boundary-inclusion approach in P1; w exactly 0 is treated via the w>ε test (Blinn 1996) rather than a literal w>0 test, avoiding a divide-by-zero at the boundary; coincident vertices produce 2A=0, handled identically to the zero-area case; a triangle spanning the entire screen interacts with the guard band (P13) and subpixel range (I9) — if its fixed-point coordinates would overflow 24.8, the guard-band-overflow path (FM-7) forces a full re-clip against the screen-space guard rectangle.

Failure-path example: a triangle with one vertex exactly on a tile's quad boundary produces a 2×2 derivative-computation quad where one or more lanes lie outside the triangle; those lanes' varyings are undefined reads unless the pipeline substitutes a triangle-interior derivative estimate (nearest valid lane) for the missing lane, avoiding NaN propagation into the LOD equation — detailed as a named pitfall in Phase 8, N.6.

14.3 Deliverable

14.4 Acceptance Criteria

  • Watertight-mesh coverage fixture (fx_2_watertight_coverage, a fan of triangles tiling a quad exactly): every pixel inside the quad's boundary is covered exactly once, counted programmatically — zero cracks, zero double-coverage.
  • Shared-edge fixture (fx_2_shared_edge): two triangles sharing a diagonal edge across a 256×256 region produce zero double-blended pixels when both are rendered with 50% alpha (blend introduced only as a test probe here, formally implemented in Phase 9).

14.5 Conformance Fixtures

  • fx_2_watertight_coverage.json — fan-triangulated quad, expected per-pixel coverage count == 1 everywhere inside.
  • fx_2_shared_edge.json — two triangles sharing a diagonal edge, expected zero double-coverage/zero gap pixels.
  • fx_2_degenerate_zero_area.json — three collinear points, expects the triangle discarded (2A==0), not rasterized.
  • fx_2_subpixel_crack_regression.json — a regression case from a previously-fixed crack bug, numeric tolerance zero (exact fixed-point match required).

14.6 Pitfalls

  • Rasterizing without fixed-point subpixel precision produces seams between adjacent triangles from floating-point rounding differences (P8) — manifestation: hairline gaps at 45°-ish edges; root cause: two triangles computing the same shared-edge coefficients with different rounding; debug method: dump raw edge-function values for the shared edge from both triangles and diff them; signal: nonzero diff at pixel centers exactly on the edge; recovery: force the shared-edge fixed-point conversion to happen once, from canonical vertex order, not independently per triangle.
  • Off-by-one bounding-box walk (inclusive vs. exclusive box edges) either over-tests pixels (slow) or misses edge pixels (cracks) — debug via the watertight-coverage fixture's exact-count assertion.
  • Applying the top-left rule inconsistently (e.g., only on some edges) reintroduces double-coverage on shared edges — root cause traced by isolating which of the three is_top_left calls diverges from the section 8 definition.
  • Sign-convention mismatch between CW/CCW winding and the "positive inside" assumption silently inverts which triangles rasterize at all — signal: nothing renders; debug by printing two_area sign for a known-CCW triangle.

14.7 Performance Concerns

  • The per-pixel bbox walk dominates runtime at this phase (section 13's profiling breakdown target: ~60% rasterization); incremental edge-function stepping (E(x+1,y) = E(x,y) + A) is the first optimization, deferred formally to Phase 11 hardening but the data layout must not preclude it here.
  • Hierarchical (tile-corner) early rejection is deferred to Phase 10; do not prematurely optimize this phase's flat bbox walk into a tiled one.

14.8 Edge Cases

  • Triangle entirely outside the framebuffer bounds — bbox clamps to [0,width)×[0,height); an empty intersection skips rasterization with zero pixel writes, not an error.
  • A triangle one subpixel wide (near-degenerate but nonzero area) — two_area near zero but nonzero; must not divide-by-zero when computing barycentrics (guarded by a minimum-area threshold, consistent with P8's numerical-robustness discussion).
  • A pixel center exactly on two edges simultaneously (a triangle corner) — the fill rule must resolve consistently via the same is_top_left test applied per edge independently.

14.9 Failure Analysis

  • Symptom: thin dark or light seams between adjacent opaque triangles in a tiled mesh render. Root cause: fill-rule or fixed-point inconsistency (P1, P8). Debug method: render the watertight-coverage fixture and diff per-pixel coverage counts against the expected all-ones map; the exact pixel coordinates of the mismatch localize which edge's arithmetic diverges. Detection: fx_2_watertight_coverage fails in CI (section 28). Recovery: fix arithmetic order to be canonical per shared edge; not a runtime-recoverable condition.

14.10 Operational Notes

  • The watertight-coverage and shared-edge fixtures introduced here are re-run, unmodified, in every subsequent phase's CI job (section 28) — they are the cheapest, fastest-failing regression signal for the entire rasterization core and must never be skipped or weakened.

16.1 Objectives

  • Implement the 1/w interpolation scheme (P3, section 8 equations) for UV and color attributes.

Build the receding-plane checkerboard fixture: a UV-textured quad rotated to a steep angle relative to the camera, verified against an analytically computed UV at several sample pixels (extending the section 8 worked-example arithmetic to a non-fronto-parallel case where w differs per vertex).

16.3 Deliverable

A textured quad tilted 80° from fronto-parallel renders with a straight, non-warping checkerboard pattern under raster-cli --debug-raster-3d --texture checkerboard.png; the --disable-perspective-correction toggle visibly reproduces the swimming artifact for comparison.

16.4 Acceptance Criteria

  • Perspective-correctness fixture (fx_4_checkerboard_receding): per-pixel interpolated UV matches the analytically computed UV (via the section 8 formula, independently recomputed) within 1e-5 at 200 sampled pixels across the tilted quad.
  • The --disable-perspective-correction toggle produces a measurably different (>0.05 average UV deviation) result on the same fixture, confirming the fixture actually discriminates correct from incorrect behavior.
  • Zero regression on the Phase 2/3 watertight-coverage and draw-order-independence fixtures (perspective correction must not alter coverage or depth behavior).

16.5 Conformance Fixtures

  • fx_4_checkerboard_receding.png + fx_4_checkerboard_receding_uv.json — tilted textured quad, analytic UV comparison at 200 sample points, 1e-5 tolerance.
  • fx_4_fronto_parallel_regression.json — the section 8 worked-example triangle (equal w per vertex), asserting perspective-correct and screen-linear interpolation agree exactly here (a regression guard on the worked-example arithmetic itself).
  • fx_4_extreme_w_ratio.json — a triangle with one vertex very close to the camera and two far away (large w ratio), stress-testing numerical precision of the 1/w divide (section 8's floating-point caveat).

16.6 Pitfalls

  • Applying perspective correction to UVs but forgetting world-space normals/positions — manifestation: lighting (wired later in Phase 6) looks correct on nearby geometry and subtly wrong far away, because normal interpolation silently reverted to screen-linear; debug method: apply the same receding-plane fixture methodology to normals, not just UVs.
  • Precision loss from computing 1/w on a very small w (near-eye geometry) — mitigated per section 8's floating-point caveat; detected by fx_4_extreme_w_ratio.
  • Forgetting to cache inv_w per vertex and instead recomputing 1/w per pixel — not incorrect, but defeats the P3 operational implication and regresses fill-rate performance measurably (caught by benchmarking, not correctness fixtures).
  • Screen-space-linear-then-"corrected" shortcuts (sampling a smaller mip to hide the artifact, per section 8's explicit warning) must not be adopted even as a stopgap — this is flagged as the wrong fix, not a lesser version of the right one.

16.7 Performance Concerns

  • Two interpolations (attr/w, 1/w) plus a divide per pixel roughly doubles interpolation cost versus naive screen-space lerp (P3's stated tradeoff); the divide is shared across all attributes per pixel by computing (1/w)_screen once and reusing its reciprocal.

16.8 Edge Cases

  • A triangle with all three vertices at equal w (fronto-parallel, section 8 worked example) — perspective-correct and screen-linear interpolation must agree exactly (fx_4_fronto_parallel_regression), serving as a built-in self-check that the general formula degenerates correctly.
  • w values that differ by several orders of magnitude across a triangle's three vertices — must not overflow or lose all precision in the shared reciprocal (fx_4_extreme_w_ratio).

16.9 Failure Analysis

  • Symptom: textures visibly "swim" or warp as a textured surface recedes from the camera. Root cause: screen-space-linear interpolation instead of the 1/w formula (P3). Detection: fx_4_checkerboard_receding fails; the --disable-perspective-correction toggle reproduces the symptom on demand for diagnosis. Recovery: not a runtime-recoverable condition — a code-level fix gated by the fixture, consistent with section 7's build-time invariant handling for I4.

16.10 Operational Notes

  • The --disable-perspective-correction debug toggle introduced here is retained permanently as a documented CLI flag; it is the fastest way for a future contributor to demonstrate the bug this phase exists to prevent, and is referenced directly by the crack/seam and z-fighting runbooks when the symptom is ambiguous between a fill-rule and an interpolation bug.

17. Phase 5 — Homogeneous Clipping and Guard-Band Handling

17.1 Objectives

  • Implement Sutherland-Hodgman clipping against all six frustum planes in homogeneous (clip) space, before perspective divide (P2, I2).
  • Implement the guard-band fast path (P13, ADR-06) that skips full clipping for triangles safely within an extended screen-space margin.
  • Handle the w≤0 case correctly, closing the "triangle behind the eye" failure mode.

17.2 Detailed Implementation Steps

  1. Implement ClipPlane for the six frustum planes per the section 8 homogeneous conditions (-w ≤ x ≤ w, etc., plus w > ε), following Sutherland & Hodgman 1974's reentrant polygon-clipping algorithm.
  2. Implement the per-plane clip: walk the polygon's vertices (starting as a triangle, growing up to 9 vertices per the section 4/section 8 worst-case bound, I13), computing the interpolation parameter t = d_A/(d_A - d_B) (section 8) and lerping clip-space attributes (Blinn's 1996 homogeneous-clipping Corner column cited for the correctness argument).
  3. Fan-triangulate the resulting convex polygon (up to 7 triangles from up to 9 vertices).
  4. Implement the guard-band fast path: a bounding test against an extended screen-space rectangle (derived from the 24.8 fixed-point range, ADR-06/P13) that, when satisfied, skips the full Sutherland-Hodgman pass entirely.
  5. Implement the w > ε boundary test (not literal w > 0) to avoid a divide-by-zero exactly at the eye plane, consistent with Blinn 1996's treatment and I2/degenerate-case handling in section 8.
  6. Add fixtures for: a triangle straddling the near plane, a triangle fully behind the eye, a vertex exactly on a clip plane, and a guard-band-overflow case.

17.3 Deliverable

raster-cli --debug-raster-3d correctly renders a camera flown through solid geometry (near-plane-straddling triangles) with no visible garbage/flipped triangles, and a synthetic extreme off-screen triangle exercising the guard-band overflow path without producing corrupted pixels.

17.4 Acceptance Criteria

  • Near-plane-straddling fixture: the visible portion of a triangle crossing the near plane renders with pixel-correct silhouette against a hand-computed reference edge, within 1-pixel tolerance at the clip boundary.
  • Zero garbage/flipped triangles across a fixture sweeping camera position through a dense mesh at 1,000 sampled frames (fx_5_flythrough_regression), detected via a NaN/Inf scan of the output framebuffer.
  • Clip-stage output triangle count never exceeds 7 per input triangle across the entire fixture corpus (I13), assertion-checked, not just documented.

17.5 Conformance Fixtures

  • fx_5_near_plane_straddle.png — a triangle crossing the near plane, expected silhouette within 1px.
  • fx_5_fully_behind_eye.json — all three vertices behind the eye, expects zero output triangles, not garbage.
  • fx_5_vertex_on_plane.json — one vertex exactly on a clip plane (d=0), expects the "inside" boundary classification (consistent with section 8's degenerate-input example).
  • fx_5_guard_band_overflow.json — an extreme off-screen triangle whose subpixel coordinates would overflow 24.8, expects the guard-band-overflow path to trigger a full re-clip (I9), not silent corruption.
  • fx_5_w_epsilon_boundary.json — a vertex with w very close to zero (but not exactly zero), expects the w > ε test to classify correctly without dividing by near-zero.

17.6 Pitfalls

  • Clipping after perspective divide instead of before — manifestation: triangles behind the camera appear mirrored/flipped rather than absent; root cause: dividing by negative w before clipping (P2 violation); debug method: log raw clip-space w before divide for any triangle producing a visibly wrong silhouette; recovery: clip strictly before divide, per I2.
  • Testing w > 0 literally instead of w > ε — manifestation: intermittent NaN/Inf pixels exactly at the eye plane boundary; recovery: adopt the epsilon test (Blinn 1996).
  • Guard-band size chosen arbitrarily rather than derived from the fixed-point range (P13's explicit warning) — manifestation: silently wrong rasterization for large off-screen triangles that should have triggered a full re-clip but didn't; detection: fx_5_guard_band_overflow regresses.
  • Fan-triangulating a clipped polygon in the wrong vertex order — manifestation: some triangles in the fan wind backward and get backface-culled incorrectly; debug via a fixture asserting fan-triangle count and consistent winding.
  • Forgetting to lerp attributes (not just position) at clip time — manifestation: correct silhouette but wrong color/UV right at the clipped edge; debug by comparing interpolated UV at a clip-boundary pixel against the analytic clip-parameter t.

17.7 Performance Concerns

  • Full Sutherland-Hodgman clipping on every triangle (bypassing the guard-band fast path) would be correct but wastes the common case where most triangles are safely inside (P13's stated tradeoff); the guard-band test must be cheap (a handful of comparisons) relative to the full clip it's meant to avoid.

17.8 Edge Cases

  • A triangle with exactly one vertex outside one plane — produces a quad (4 vertices), fan-triangulated into 2 triangles.
  • A triangle straddling two planes simultaneously (e.g., both near and left) — must correctly chain the per-plane clip without losing vertices between passes.
  • The degenerate "point" and "line" results of clipping (a triangle clipped down to zero or near-zero area) — treated identically to the Phase 2 zero-area discard path.

17.9 Failure Analysis

  • Symptom: geometry crossing the near plane produces flickering, inverted, or garbage triangles instead of a clean silhouette. Root cause: either divide-before-clip (P2 violation, I2) or an incorrect epsilon boundary. Detection: fx_5_near_plane_straddle and fx_5_fully_behind_eye regress together. Recovery: not runtime-recoverable — the clip stage's plane-test order must be corrected in code; the debug-transform CLI mode from Phase 1 is the fastest tool to inspect raw w values at the failure point.

17.10 Operational Notes

  • The flythrough regression fixture (fx_5_flythrough_regression) is computationally the most expensive fixture introduced so far (1,000 sampled frames); it runs in the nightly conformance job (section 26), not on every commit, to keep PR-gating CI fast (section 12's operational-notes precedent).

18. Phase 6 — Programmable Vertex and Fragment Shader Stages

18.1 Objectives

  • Implement the VertexShader/FragmentShader traits as the pipeline's extension point (ADR-11), replacing the hardcoded Phase 1/2 transform-and-flat-color path.
  • Implement UniformBlock, ShaderVaryings plumbing end-to-end from vertex shader output through fragment shader input.
  • Implement the DISCARDS/WRITES_DEPTH static contract gating early- vs. late-Z (P7, ADR-10, I10).

18.2 Detailed Implementation Steps

  1. Finalize the VertexShader trait (section 11) and rewire Phase 1's hardcoded transform into a concrete TransformShader implementation.
  2. Finalize the FragmentShader trait with its DISCARDS/WRITES_DEPTH associated consts (I10); implement two reference shaders: a flat-color shader (DISCARDS=false) and an alpha-test shader (DISCARDS=true) for testing the early-Z bypass path.

  4. Implement ShaderVaryings interpolation using the Phase 4 perspective-correct machinery generically, for arbitrary vertex-shader-defined varyings, not just the hardcoded UV/color/position/normal set (Gregory ch. 10's pipeline-layering argument applied here).

18.3 Deliverable

  • Early-Z bypass unit test (I10) passes: the alpha-test (DISCARDS=true) shader measurably runs its full fragment evaluation before the depth write, verified via a FrameStats.fragments_early_z_killed counter that stays at zero for that shader while nonzero for the flat-color shader on an identical occluded-geometry fixture.

  • Zero regression on all Phase 0-5 fixtures (the programmable stage must be a drop-in replacement for the earlier hardcoded path, not a parallel code path).

18.5 Conformance Fixtures

  • fx_6_shader_swap_flat.png — flat-color shader reference image.
  • fx_6_shader_swap_alpha_test.png — alpha-test shader reference image, including its characteristic hard-edged discard boundary.
  • fx_6_early_z_bypass.json — asserts fragments_early_z_killed behavior differs correctly between the two shaders' static contracts (I10).
  • fx_6_varying_passthrough.json — a custom test varying (not UV/color/normal/position) round-trips from vertex shader to fragment shader unmodified at a sampled pixel.

18.6 Pitfalls

  • Hardcoding early-Z on regardless of the shader's DISCARDS flag — manifestation: an alpha-test shader's discarded fragments still write depth incorrectly, corrupting later opaque-object occlusion; detection: fx_6_early_z_bypass regresses.
  • Treating ShaderVaryings as a fixed struct rather than a generically interpolated bag of attributes — manifestation: works for the two reference shaders but breaks the moment a third shader needs a different varying set; caught by fx_6_varying_passthrough if the varying set is deliberately varied.
  • Vtable dispatch overhead (ADR-11's accepted tradeoff) mistaken for a bug — this is expected; do not "fix" it by prematurely switching to generics without revisiting ADR-11's decision record.

18.7 Performance Concerns

  • Trait-object dispatch (ADR-11) costs one indirect call per vertex/fragment; acceptable per the ADR's rationale, but must be measured (not assumed) against the section 4 throughput targets to confirm it doesn't already dominate at this phase, before Phase 10's tiling adds parallelism on top.

18.8 Edge Cases

  • A fragment shader returning None (discard) for every fragment of a triangle — the triangle contributes zero visible pixels but must not corrupt FrameStats counters or the depth buffer (I10).
  • A vertex shader producing NaN varyings for a subset of vertices (malformed uniform input) — must not propagate into a framebuffer write; caught by a NaN-scan fixture, consistent with Phase 5's flythrough-regression NaN scan.

18.9 Failure Analysis

  • Symptom: an alpha-tested (discarding) shader's occluded geometry still appears to affect depth-buffer state incorrectly. Root cause: early-Z applied despite DISCARDS=true (I10 violation, P7). Detection: fx_6_early_z_bypass. Recovery: pipeline-setup stage must read the static contract before choosing early- vs. late-Z; not a runtime-recoverable condition.

18.10 Operational Notes

  • The two reference shaders (flat-color, alpha-test) introduced here remain the canonical minimal test shaders for every subsequent phase's fixtures (texturing in Phase 7, blending in Phase 9) — new phases extend them rather than replacing them, keeping the fixture corpus's shader surface small and well-understood.

19. Phase 7 — Texture Sampling With Bilinear Filtering

19.1 Objectives

  • Implement Texture2D, SamplerState, FilterMode, WrapMode (section 11).
  • Implement nearest-neighbor and bilinear sampling per the section 8 bilinear-weight equation.
  • Wire a texture-sampling fragment shader using the Phase 6 programmable stage and Phase 4 perspective-correct UV.

19.2 Detailed Implementation Steps

  1. Implement Texture2D::load from a decoded RGBA8 buffer (via the raster-io glTF/image ingestion path).
  2. Implement SamplerState addressing: WrapMode::{Repeat, Clamp, MirroredRepeat} applied to UV before texel lookup, bounds-checked per I12.
  3. Implement FilterMode::Nearest: direct texel lookup at floor(u*width), floor(v*height).
  4. Implement FilterMode::Bilinear: four-texel weighted sum per the section 8 bilinear equation (Heckbert 1986's survey cited for the filtering taxonomy this implements one point of).
  5. Implement a TexturedShader: FragmentShader sampling Texture2D at the perspective-correct UV from Phase 4, feeding the Blinn & Newell 1976 texture-mapping lineage forward into a concrete shader.
  6. Add the bilinear-vs-nearest visual comparison fixture and the out-of-range UV fuzz target (I12, T2-adjacent).

19.3 Deliverable

raster-cli --shader textured --texture checkerboard.png renders the Phase 4 tilted quad with bilinear-filtered sampling, visibly smoother at minification/magnification boundaries than the nearest-neighbor mode selectable via the same flag.

19.4 Acceptance Criteria

  • Bilinear sample value at a fractional UV matches the section 8 bilinear-weight formula's hand-computed value within 1/255 (one 8-bit quantization step) at 50 sampled fractional UV coordinates (fx_7_bilinear_analytic).
  • Nearest-neighbor sampling exactly matches direct-index texel lookup (bit-exact, zero tolerance) at 50 sampled UV coordinates (fx_7_nearest_exact).
  • Zero out-of-bounds texel reads across a fuzz corpus of 10,000 random (including negative and >1.0) UV values under each WrapMode (I12), verified by ASan/bounds-checked build.

19.5 Conformance Fixtures

  • fx_7_bilinear_analytic.json — 50 fractional UV samples, hand-computed bilinear reference, 1/255 tolerance.
  • fx_7_nearest_exact.json — 50 UV samples, exact texel-index match.
  • fx_7_wrap_mode_boundary.json — UV values at and beyond [0,1] under each WrapMode, expected addressed texel per mode's defined behavior.
  • fx_7_out_of_range_fuzz (fuzz target, not a fixed fixture) — 10,000 random UVs, zero out-of-bounds reads (I12).

19.6 Pitfalls

  • Sampling texture data as if linear when it is sRGB-encoded on disk — manifestation: lit/blended results (wired in later phases) look subtly too bright; not fully in scope for this phase's flat-texture-display deliverable but flagged here because the texture-loading path introduced in this phase is where the sRGB-to-linear conversion decision must be made once, correctly, rather than retrofitted.
  • Off-by-one texel indexing at the bilinear boundary (sampling T[width][j] when width is out of bounds) — manifestation: crash or wraparound artifact at the texture's right/bottom edge; caught by fx_7_wrap_mode_boundary.
  • UV seam wrapping: a triangle straddling a UV seam (u=0.95 to u=0.05) interpolates through u=0.5 under naive linear interpolation, sampling the wrong texture region — flagged here as a known mesh-authoring concern (duplicate seam vertices), not a sampler bug; out of this phase's fix scope but documented so it isn't misdiagnosed as a filtering bug later.
  • Treating WrapMode::Clamp and WrapMode::Repeat addressing math identically — manifestation: edge texels bleed or repeat incorrectly; caught by fx_7_wrap_mode_boundary's per-mode assertions.

19.7 Performance Concerns

  • Bilinear sampling costs 4 texel fetches + 3 lerps versus nearest's 1 fetch; acceptable per ADR-14's default, but the texture-cache footprint (section 4: 8MB per-thread working set) must be validated against this phase's access pattern before Phase 10 multiplies it across threads.

19.8 Edge Cases

  • A 1×1 texture (solid color) — bilinear filtering must degenerate to that single texel's value regardless of UV.
  • UV exactly at a texel center (fractional part exactly 0) — bilinear weights degenerate to a single-texel lookup, must match nearest-neighbor exactly at that exact coordinate (a useful self-consistency check).

19.9 Failure Analysis

  • Symptom: texture edges show garbage colors or crashes near UV=0 or UV=1. Root cause: wrap-mode addressing math not bounds-checked before the texel fetch (I12 violation, T2-adjacent). Detection: fx_7_wrap_mode_boundary and the out-of-range fuzz target. Recovery: clamp/wrap per the declared WrapMode before indexing, never after; add the bounds check at the addressing function's single call site, not scattered across call sites.

19.10 Operational Notes

  • The bilinear-analytic and nearest-exact fixtures are parameterized by texture size so Phase 8's mip-chain work can reuse the identical assertion methodology against each mip level, avoiding fixture duplication.

20. Phase 8 — Mipmapping With Derivative-Based LOD Selection

20.1 Objectives

  • Implement MipChain generation (box-filtered downsample pyramid, Williams 1983).
  • Implement Derivatives/FragmentQuad (2×2 quad finite differences, P6, ADR-15).
  • Implement the LOD equation (section 8) and trilinear blending between adjacent mip levels.

20.2 Detailed Implementation Steps

  1. Implement MipChain::generate from a base Texture2D: each level box-filters four texels of the previous level into one, halving both dimensions (Williams 1983's pyramidal-parametrics construction).
  2. Implement FragmentQuad: group fragment evaluation into 2×2 screen-space lanes so ∂u/∂x, ∂u/∂y etc. are available as finite differences between lanes (P6's operational implication), with the section 8 failure-path fallback for lanes outside the triangle (nearest valid lane substitution, avoiding NaN).
  3. Implement the LOD equation exactly as specified in section 8 (ρ, LOD = log2(ρ), clamped mip selection), citing Heckbert 1989's derivation of texture-space derivatives from screen-space ones.
  4. Implement trilinear filtering: bilinear-sample both floor(LOD) and floor(LOD)+1, lerp by frac(LOD).
  5. Add the mip-selection-at-known-distance fixture: a receding textured plane at a camera distance where the analytic LOD is known in closed form, verifying I6 (LOD derives from derivatives, not a heuristic).
  6. Add the quad-boundary derivative fixture, exercising the section 8 failure-path example directly (a triangle edge bisecting a 2×2 quad).

20.3 Deliverable

raster-cli --shader textured --texture checkerboard.png --mipmap renders a textured floor plane receding to the horizon, crisp near the camera and smoothly (not aliased, not overly blurred) minified toward the horizon.

20.4 Acceptance Criteria

  • LOD-at-known-distance fixture (fx_8_lod_analytic): computed mip level matches the closed-form analytic LOD (derived independently from the camera/plane geometry, not from the renderer's own derivative code) within ±0.5 mip levels at 20 sampled camera distances.
  • Zero LOD "popping" across a continuous camera dolly fixture (fx_8_lod_continuity): LOD changes monotonically and smoothly frame-to-frame, no discontinuous jumps exceeding 1.0 mip level between adjacent sampled frames at a fixed dolly speed.
  • Quad-boundary derivative fixture (fx_8_quad_boundary_fallback): a triangle edge bisecting a 2×2 quad produces zero NaN/Inf fragment output, all four lanes assigned a valid derivative estimate.

20.5 Conformance Fixtures

  • fx_8_lod_analytic.json — 20 camera distances, closed-form LOD reference, ±0.5 mip-level tolerance.
  • fx_8_lod_continuity.png sequence — dolly-camera frame sequence, LOD-jump assertion between adjacent frames.
  • fx_8_quad_boundary_fallback.json — a deliberately constructed triangle edge inside a 2×2 quad, NaN/Inf scan.
  • fx_8_mip_chain_dimensions.json — asserts each mip level is exactly half the previous (rounded down), down to a 1×1 terminal level.

20.6 Pitfalls

  • Deriving LOD from world-space camera distance (a heuristic) instead of screen-space derivatives — manifestation: LOD is wrong for surfaces at a grazing angle even at a fixed distance (I6 violation); detection: fx_8_lod_analytic fixture includes a grazing-angle case specifically to catch this.
  • Computing derivatives from only one lane pair (∂u/∂x alone, ignoring ∂u/∂y) — manifestation: LOD is correct for horizontal minification but wrong for vertical, an easy oversight since many test scenes are horizontally dominant; caught by a fixture with a strongly anisotropic minification direction.
  • LOD popping at quad boundaries from inconsistent off-triangle lane handling (the section 8 failure-path example) — manifestation: visible mip-level flicker exactly at triangle silhouette edges; detection: fx_8_quad_boundary_fallback and fx_8_lod_continuity.
  • Off-by-one in mip-level clamping (floor(LOD)+1 exceeding mip_count-1) — manifestation: out-of-bounds mip-level read at the coarsest levels; caught by fx_8_mip_chain_dimensions combined with an extreme-distance LOD fixture.

20.7 Performance Concerns

  • Mip-chain memory overhead is 4/3× the base texture size (section 34's derivation); this must be validated against the section 4 texture-cache budget (8MB per-thread) before Phase 10 introduces per-thread contention on texture reads.
  • Trilinear filtering costs 2× bilinear's texel-fetch count; acceptable per ADR-14, measured against the fill-rate target (M2, section 30).

20.8 Edge Cases

  • A texture whose dimensions are not a power of two — mip generation must still halve-and-round consistently down to a 1×1 terminal level without an off-by-one truncation error.
  • A camera so close that LOD computes as negative (magnification, not minification) — clamped to mip level 0, not extrapolated to a nonexistent "level -1".
  • A camera so far that LOD exceeds mip_count-1 — clamped to the coarsest level, not sampling past the mip chain's end.

20.9 Failure Analysis

  • Symptom: mip level visibly "pops" (discrete jump) as the camera moves smoothly, rather than transitioning gradually. Root cause: derivative computed inconsistently at quad/triangle boundaries (P6 violation), or trilinear blending disabled/miswired. Detection: fx_8_lod_continuity regresses with a jump exceeding the 1.0-mip-level threshold between adjacent dolly frames. Recovery: verify the quad-boundary fallback (section 8 failure-path example) is applied uniformly, and that frac(LOD) is actually used to blend rather than the mip level being rounded before sampling.

20.10 Operational Notes

  • Anisotropic filtering remains PhaseDeferred("§20") per section 1 and section 37 — this phase ships isotropic trilinear only; the Greene & Heckbert 1986 EWA citation (section 5) documents the un-defer path without implementing it here.

21. Phase 9 — Alpha Blending and MSAA

21.1 Objectives

  • Implement BlendState/BlendFactor and the alpha-blending equation (section 8, P14).
  • Implement MSAA: per-sample coverage, per-sample depth, shade-once-per-pixel-write-to-covered-samples (P10), and the resolve average (I11).
  • Formalize the coverage mask computation as part of triangle rasterization (extending the Phase 2 edge-function inside-test to per-sample offsets).

21.2 Detailed Implementation Steps

  1. Implement BlendState application as a fixed post-shading step (P14, ADR-16): C_out = C_src·F_src + C_dst·F_dst per the section 8 equation, using the standard SRC_ALPHA/ONE_MINUS_SRC_ALPHA factors by default.
  2. Extend ColorBuffer/DepthBuffer to carry msaa_samples per pixel (section 4: 4 samples default, ADR-17), using a fixed rotated-grid sample-position pattern (Akeley 1993's RealityEngine multisampling architecture cited as the hardware precedent).
  3. Extend the rasterization inside-test to evaluate each sample's offset position against the triangle's edge functions, producing a coverage bitmask per pixel (section 8's MSAA arithmetic).
  4. Implement the shade-once rule (P10): the fragment shader runs exactly once per covered pixel; its result writes to every sample that is both covered and passes that sample's depth test — never to uncovered samples (I11).
  5. Implement the resolve step: average covered+shaded samples per pixel into the final Framebuffer.color (section 8's resolve equation); uncovered samples retain the explicit clear color, never garbage (I11's enforcement point).
  6. Add the "black hole at edges" regression fixture directly testing I11: a triangle edge at a known sub-pixel coverage fraction, verifying the resolved edge color matches the analytic coverage-weighted average.

21.3 Deliverable

raster-cli --msaa 4 renders a scene with visibly antialiased triangle silhouette edges compared to --msaa 1 (off) on the same geometry, plus a working alpha-blended transparent overlay demonstrated via a semi-transparent quad over an opaque background.

21.4 Acceptance Criteria

  • MSAA edge-antialiasing fixture (fx_9_msaa_edge_quality): average per-pixel color deviation from a supersampled (16×) ground-truth reference is reduced by at least 60% when comparing --msaa 4 against --msaa 1 on the same silhouette edge.
  • I11 black-hole fixture (fx_9_black_hole_edges): resolved edge-pixel colors match the analytic coverage-weighted average within 1/255 at 20 sampled sub-pixel-coverage fractions.
  • Alpha-blend equation fixture (fx_9_blend_equation): blended output matches the hand-computed C_src·F_src + C_dst·F_dst result exactly (bit-exact, since this is pure arithmetic with no filtering) at 10 sampled src/dst/alpha combinations.
  • Shader invocation count fixture: FrameStats confirms exactly one fragment-shader invocation per covered pixel regardless of MSAA sample count (P10), not N invocations for N samples.

21.5 Conformance Fixtures

  • fx_9_msaa_edge_quality.png + supersampled reference — silhouette-edge antialiasing quality comparison.
  • fx_9_black_hole_edges.json — 20 sub-pixel coverage fractions, analytic coverage-weighted color reference.
  • fx_9_blend_equation.json — 10 src/dst/alpha combinations, bit-exact arithmetic reference.
  • fx_9_shader_invocation_count.json — asserts fragment-shader call count == covered-pixel count, independent of MSAA sample count.

21.6 Pitfalls

  • Shading once per sample instead of once per pixel (P10 violation) — manifestation: MSAA becomes as expensive as supersampling, silently defeating its entire cost advantage; detection: fx_9_shader_invocation_count regresses immediately and obviously.
  • Writing shaded color to uncovered samples during resolve (I11 violation) — manifestation: dark or bright "halos" at triangle edges from blending in stale/garbage sample data; detection: fx_9_black_hole_edges.
  • Resolve step reading uninitialized sample memory for pixels with zero coverage this frame — manifestation: nondeterministic edge colors that vary run-to-run; recovery: explicit clear-color initialization every frame, not a "clear on first write" optimization that skips uncovered samples.
  • Blend factor confusion (swapping F_src/F_dst or using premultiplied-alpha assumptions inconsistently) — manifestation: transparent overlays look either too dark or with a visible edge halo; detection: fx_9_blend_equation's bit-exact check catches any factor-order error immediately.

21.7 Performance Concerns

  • MSAA memory cost scales linearly with sample count (section 4: ×4 for color+depth at 4 samples); this must be validated against the section 4 framebuffer-memory budget (63.3MB total) before Phase 10 replicates this per tile.
  • The coverage-mask computation adds N edge-function evaluations per pixel (one per sample) versus 1 for non-MSAA rasterization; amortized via the same incremental-stepping optimization noted in Phase 2, formalized in Phase 11.

21.8 Edge Cases

  • A pixel with partial coverage where all covered samples fail the depth test (occluded) — the fragment shader must not run at all for that pixel (early-Z still applies per-pixel, gating on "any sample both covered and depth-passing").
  • Fully transparent (alpha=0) blended geometry — must produce zero visible change to the destination color, not a rounding-error-induced faint tint (caught by fx_9_blend_equation's zero-alpha case).
  • A triangle whose edge passes exactly through a sample position — resolved via the identical top-left fill-rule tie-break as Phase 2's pixel-center test, applied per sample rather than per pixel center.

21.9 Failure Analysis

  • Symptom: pixels along antialiased edges appear darker or lighter than either the foreground or background color, rather than a smooth blend between them. Root cause: resolve averaging in unshaded/garbage samples (I11 violation) — the "black hole" pattern. Detection: fx_9_black_hole_edges. Recovery: not runtime-recoverable — verify the resolve step's coverage-mask gating excludes uncovered samples from the average, per the section 8 resolve equation exactly as specified.

21.10 Operational Notes

  • The MSAA sample-position pattern (rotated grid, ADR-17) is fixed at build time, not runtime-configurable, to preserve the I7/I8 bit-identical-frame guarantees across the single-threaded and (Phase 10) tiled-parallel paths — a runtime-configurable sample pattern would need its own reproducibility fixture, deliberately out of scope.

22. Phase 10 — Tiled Binning and Multithreaded Rasterization

22.1 Objectives

  • Implement Tile/TileBin/BinnedPrimitive (section 11) and the sort-middle binning stage (ADR-04, McCormack & McNamara 2000).
  • Implement the per-tile parallel boundary (section 3 diagram) via rayon, with disjoint tile-local color/depth/MSAA buffers (P5, P11, I5, ADR-18/ADR-19).
  • Prove the tiled-parallel path is bit-identical to the single-threaded path (I7) across the entire fixture corpus built in Phases 0-9.

22.2 Detailed Implementation Steps

  1. Implement TileBin population: for each TriangleSetup, compute its overlapping tile set from the screen-space bbox, appending a BinnedPrimitive to every overlapping tile's bin (sort-middle, Seiler et al. 2008's Larrabee binning architecture cited as the scale reference).
  2. Size tiles at 64×64 pixels (ADR-05) and validate the resulting per-tile color+depth(+MSAA) footprint against the section 4/section 34 cache-fit budget.
  3. Allocate tile-local ColorBuffer/DepthBuffer slices as disjoint mutable borrows (Rust's borrow checker machine-checks I5 at compile time, not merely at test time) — this is the concrete mechanism, not just the intent, behind P5/P11.
  4. Wire rayon::par_iter over the tile list as the fork; each tile independently runs Early-Z, Fragment Shader (with Texture Unit), and Blending (Phases 3, 6, 7, 8, 9's logic, unmodified) against its private slice.
  5. Implement the join-then-resolve barrier: after all tiles complete, a single-threaded (or trivially data-parallel, since tiles are disjoint) resolve copies/averages tile-local buffers into the global Framebuffer (I11 unchanged).
  6. Pin the thread count and reduction order per ADR-24; disable FMA contraction inconsistency across the single- and multi-threaded paths; add the byte-diff fixture comparing both paths across the full Phase 0-9 fixture corpus (I7's primary enforcement point).

22.3 Deliverable

raster-cli --threads 8 renders the full Phase 0-9 fixture corpus and produces byte-identical output to --threads 1 on every fixture, with measured wall-clock speedup approaching (not necessarily reaching) 8× on the reference benchmark machine.

22.4 Acceptance Criteria

  • Bit-identical-paths fixture (fx_10_thread_reproducibility): every fixture from Phases 0-9, rendered at --threads 1 and --threads 8, produces byte-identical framebuffers — zero-byte diff across the entire corpus (I7).
  • Parallel speedup fixture: wall-clock time at 8 threads is at least 5.5× faster than 1 thread on the tiled_stress_scene benchmark (M8, section 30) — sub-8× expected and acceptable per the setup/binning overhead documented in section 31.
  • Zero data races: a ThreadSanitizer-instrumented build of the full fixture corpus produces zero race reports (I5).

22.5 Conformance Fixtures

  • fx_10_thread_reproducibility (meta-fixture, re-runs the entire Phase 0-9 corpus at two thread counts) — zero-byte diff required.
  • fx_10_tile_boundary_coverage.json — a triangle straddling exactly 4 tiles, watertight-coverage assertion extended across the tile grid (I1 generalized to the tiled path).
  • fx_10_uneven_load_distribution.json — a scene with 90% of triangles in one screen region, asserting no tile starves (every tile's bin is processed) and total wall-clock stays within the section 30 tile-imbalance budget.
  • fx_10_tsan_race_scan (CI job, not a fixed-output fixture) — ThreadSanitizer run over the full corpus, zero reports required.

22.6 Pitfalls

  • A triangle straddling a tile boundary rasterized inconsistently by the two owning tiles (different rounding at the shared boundary) — manifestation: a crack or double-blend exactly at tile edges, distinct from but analogous to Phase 2's shared-triangle-edge crack (I1 extended to tile boundaries); detection: fx_10_tile_boundary_coverage.
  • False sharing between threads writing to adjacent tiles whose underlying memory allocation places them on the same cache line — manifestation: measured speedup far below the M8 target despite zero logical bugs; debug method: profile cache-line contention directly (section 30's methodology), not just wall-clock time; recovery: pad tile-local buffer allocations to cache-line boundaries.
  • FMA contraction differing between the single- and multi-threaded compiled code paths (e.g., due to different inlining decisions under rayon) — manifestation: fx_10_thread_reproducibility fails with tiny (1-ULP) pixel differences, not gross corruption; detection is exactly this fixture; recovery: pin FMA contraction globally (ADR-24), verified by a targeted single-operation reproducibility test isolating the contraction behavior.
  • Load imbalance from naive equal-sized tile chunking rather than work-stealing — manifestation: fx_10_uneven_load_distribution shows most threads idle while one thread processes a dense region; recovery: rely on rayon's work-stealing scheduler operating over individual tiles (fine-grained units), not pre-partitioned thread-sized chunks.

22.7 Performance Concerns

  • This phase's entire purpose is the section 30 performance-engineering payoff; profile cache locality of tile-local framebuffer access (P11), SIMD readiness across pixel quads (feeding Phase 11's SIMD hardening), and the per-tile time histogram (tail latency, section 30) as the primary instrumented metrics, not just aggregate wall-clock.
  • Bin memory (section 34) must be re-validated at this phase against actual measured average tile-overlap on realistic scenes, not just the analytic worst case from section 4.

22.8 Edge Cases

  • A triangle whose bbox covers zero tiles due to floating-point/fixed-point rounding at the screen edge — must not silently vanish; the binning bbox computation must be inclusive-safe against the same rounding the rasterizer itself uses (shared arithmetic, per P1's operational implication extended to binning).
  • An empty tile (zero triangles ever bin to it) — its lifecycle (section 8 tile state-transition table) goes Idle → Resolved directly, contributing zero work, not an error.
  • A degenerate single-tile scene (entire screen is one small triangle) — the "parallelism" is trivial (1 active tile out of many), and speedup should gracefully degrade toward 1× without an error or a special-cased code path.

22.9 Failure Analysis

  • Symptom: the tiled-multithreaded path produces output that visually matches but is not byte-identical to the single-threaded path. Root cause: almost always a floating-point non-associativity or FMA-contraction difference between compiled code paths (ADR-24), rarely a logic bug. Detection: fx_10_thread_reproducibility's zero-byte-diff requirement. Recovery: documented in docs/runbooks/reference-image-regression-bisect.md — bisect by disabling FMA contraction, then by forcing a fixed reduction order, to isolate which pinning is missing.

22.10 Operational Notes

  • fx_10_thread_reproducibility is the single most valuable fixture in the entire corpus (it re-validates every prior phase's correctness under parallelism) and is run on every CI job from this phase onward, not merely nightly, despite its cost — the tile-imbalance and false-sharing pitfalls above are cheap to reintroduce silently in later refactors.

23.6 Pitfalls

  • SIMD vectorization subtly changing floating-point reduction order and silently breaking I7/I8 bit-identity — manifestation: fx_11_simd_equivalence regresses with 1-ULP differences; recovery: pin the SIMD reduction order explicitly (extending ADR-24's reproducibility pinning to the SIMD dimension), don't assume the wide crate's default lane order matches the scalar loop's iteration order.

  • raster-window's interactive mode accidentally diverging from raster-core's validated pipeline (e.g., a separate fast-path added "just for the live viewer") — recovery: raster-window must call the identical raster-core entry points as raster-cli, verified by running a subset of the conformance corpus through the windowed path headlessly.
  • Perf-regression gating flagging noise (benchmark machine variance) as a regression — recovery: the 10% margin and multiple-run averaging in perf-regression.yml must be tuned against measured CI benchmark-machine variance before being trusted as a hard gate.

23.7 Performance Concerns

  • This phase is where section 30's full profiling methodology (cache locality, SIMD, allocation, false sharing, tail latency) is applied end-to-end for the first time across the complete pipeline, not per-phase in isolation; the M1-M12 targets (section 30) are validated here as a whole-system measurement, distinct from any single phase's local benchmark.

23.8 Edge Cases

  • A fixture that passes on the reference benchmark machine but fails on a different CPU microarchitecture in CI (ADR-25's cross-arch matrix) — surfaces exactly the class of bug ADR-24's pinning exists to prevent; treated as a blocking failure, not a known-flaky skip.
  • The differential-testing reference (llvmpipe) itself has a documented bug or convention difference on a specific scene — the shared scene set must exclude or annotate any such known-divergent case rather than silently lowering the global tolerance to compensate.

23.9 Failure Analysis

  • Symptom: the full conformance suite passes locally but fails intermittently in CI. Root cause: almost always either uninitialized memory (a missed I11/I3 initialization edge case from an earlier phase) or a benchmark-machine-variance false positive in the perf-regression gate, rarely a new logic bug at this late phase. Detection: fx_11_full_corpus_gate's per-fixture breakdown isolates which specific fixture is flaky, and its phase-of-origin (sections 12-22) directs the investigation to that phase's specific pitfalls (N.6) first.

23.10 Operational Notes

27. Compatibility & Versioning

The primary compatibility surface is the rasterization-rule conformance contract itself (P12): any change that alters fill-rule behavior, interpolation semantics, or clip-plane handling in a way that shifts a single pixel's coverage classification is a breaking change, gated by the entire section 28 fixture corpus, not just documented in a changelog. Shader interface stability: the VertexShader/FragmentShader trait signatures (section 11) are a SemVer-major surface — adding a required method or changing ShaderVaryings's layout breaks every downstream shader implementation and requires a major version bump. Texture and asset format versioning: glTF 2.0 ingestion tracks the upstream spec version explicitly; a texture format change (e.g., adding compressed-texture support) is additive (new Texture2D variant) rather than breaking the existing linear-layout contract (ADR-13).

Frame reproducibility guarantees (I7, I8) hold only within a pinned build: thread count, FMA contraction setting, and SIMD path selection (ADR-24) are all part of the reproducibility contract, and changing any of them across two builds is explicitly not guaranteed to produce identical frames — this is documented as a hard boundary, not a bug, in CHANGELOG.md for any release that changes the default thread count or SIMD baseline. API stability follows SemVer against the raster-core/raster-shade public trait and struct surface (section 11); patch releases fix bugs without changing any signature; minor releases add capability (new FilterMode variant, new blend factor) without breaking existing callers; major releases may break the shader trait contract or the fixed-point format (ADR-02/03). Migration guidance accompanies every major release in CHANGELOG.md, keyed to the specific ADR that changed. Deprecation: a feature slated for removal is marked #[deprecated] for at least one minor release cycle before removal. Rolling-upgrade guarantees: since this is a library/CLI, not a service, there is no rolling-upgrade concern in the traditional sense — the relevant guarantee is that a downstream consumer can pin an exact patch version and rebuild deterministically (ADR-24, reproducible builds, section 29).

28. Testing & Verification Strategy

Unit tests cover individual functions (matrix composition, edge-function coefficient computation, bilinear weight arithmetic) in isolation. Integration tests exercise a full frame through the pipeline sequence table (section 8) against a known scene. Property tests (section 28's core addition beyond unit/integration): a watertight mesh covers each pixel exactly once, counted programmatically (I1, tied to fx_2_watertight_coverage and fx_10_tile_boundary_coverage); a shared edge is never double-covered (I1, fx_2_shared_edge); perspective-correct interpolation matches the analytic value at sampled points (I4, fx_4_checkerboard_receding); the depth test is monotonic across random z-sequences (I3, fx_3_depth_monotonicity); the single-threaded and tiled-multithreaded paths produce bit-identical framebuffers (I7, fx_10_thread_reproducibility).

Differential testing renders a shared scene set through both raster-cli and Mesa llvmpipe (or SwiftShader), comparing per-pixel within a documented tolerance (section 5 reference implementations, fx_11_differential_llvmpipe) — this is the primary defense against conformance drift from the OpenGL rasterization rules (P12). Fuzzing targets the mesh/glTF parser (T1, fuzz/fuzz_targets/gltf_parser.rs), index buffers (T2, fuzz/fuzz_targets/index_buffer.rs), and texture decoders (T5, fuzz/fuzz_targets/texture_decoder.rs), run continuously in CI with a corpus-minimization step. Chaos/fault injection: deliberately corrupt a single tile's binning input mid-run in a test harness to confirm the failure is contained to that tile's output (I5) rather than propagating.

Deterministic frame replay with bit-exact comparison is the mechanism behind I7/I8: the same scene, rendered twice (same thread count, same build), must hash-match exactly (fx_10_thread_reproducibility, fx_11_simd_equivalence). Soak testing: the tiled_stress_scene benchmark run continuously for an extended duration (hours) under a memory-sanitized build, watching for leaks or gradual corruption in the tile-local buffer reuse path. Conformance against the OpenGL rasterization rules is named-test-case-driven: each of the section 5 RFC citations maps to at least one fixture asserting the specific rule it documents (top-left fill rule → fx_2_shared_edge; perspective-correct interpolation qualifiers → fx_4_checkerboard_receding). Perf-regression gating (section 30's M1-M12) runs on every commit via perf-regression.yml, failing on a >10% regression against the pinned baseline. Every test class above is tied back to a specific invariant (I1-I13) and the phase N.5 fixture that exercises it, per the cross-references embedded in this section.

29. Build & Release Engineering

Reproducible builds: Cargo.lock is checked in and never auto-updated by CI (ADR-24); the rust-toolchain.toml pins an exact compiler version and target triples, and the release pipeline builds inside the Dockerfile-defined container (section 10) to eliminate host-environment drift. Artifact signing: release binaries and crate publications are signed (cargo publish with a scoped token, plus a detached signature on the CLI binary artifact) before being attached to a GitHub release. SBOM: cargo-cyclonedx (or equivalent) generates a software bill of materials per release, published alongside the binary artifacts. Release channels: a stable channel tracks tagged SemVer releases; a nightly channel tracks main-branch builds for early differential-testing feedback, not recommended for downstream production pinning.

CI/CD topology (ADR-25): .github/workflows/ci.yml (build+unit test matrix, x86_64/aarch64), conformance.yml (the full fixture corpus, section 28), differential.yml (the llvmpipe/SwiftShader comparison job), perf-regression.yml (M1-M12 gating), and release.yml (signed artifact + SBOM publish), each a distinct workflow so a conformance failure doesn't block a documentation-only PR's fast unit-test feedback. Version stamping: every built artifact embeds its exact git commit SHA and Cargo.lock hash in a --version output, enabling exact reproduction of any released binary. Provenance/attestation: release artifacts carry SLSA-style build provenance (build environment, source commit, workflow run ID) attached to the GitHub release. Dependency auditing: cargo audit runs in CI (T10 mitigation) against every PR touching Cargo.lock, and additionally on a scheduled weekly job to catch newly disclosed vulnerabilities in already-merged dependencies.

The compiler/SIMD pinning that preserves frame reproducibility (I7, I8, ADR-24) is itself a release-engineering artifact: the exact Rust compiler version, the exact wide-crate-selected SIMD backend, and FMA-contraction flags are recorded per release in CHANGELOG.md and enforced by the rust-toolchain.toml pin — a toolchain upgrade is treated as a candidate breaking change for reproducibility (section 27) until proven otherwise by re-running the full fx_10_thread_reproducibility/fx_11_simd_equivalence corpus against the new toolchain.

30. Performance Engineering

Profiling/benchmark methodology: cache locality of tile-local framebuffer access is measured directly via hardware performance counters (L1/L2 miss rate) comparing the flat pre-tiling framebuffer access pattern (hypothetically, or via the --threads 1 --tile-size <huge> degenerate configuration) against the tuned 64×64 tile size (ADR-05) — this is the concrete measurement behind P11's "tiling exists for cache locality" claim, not an assumption. SIMD utilization across pixel quads is measured via vectorization reports from the wide-crate-backed inner loop, cross-checked against the section 23 SIMD-equivalence fixture. Allocation is profiled per-frame (target: zero heap allocations in the steady-state per-tile rasterize loop, section 4's per-thread scratch-memory budget). False sharing between threads writing adjacent tiles is measured via cache-line-contention counters (perf c2c or equivalent), the direct diagnostic for the Phase 10 false-sharing pitfall. Branch behavior in the inner rasterization loop (the edge-function inside-test and the fill-rule branch) is profiled for misprediction rate, since the top-left tie-break (P1) is a data-dependent branch on every pixel. Tail latency is reported as a per-tile time histogram (p50/p95/p99), not a mean, since a single slow tile (load-imbalance, FM-12) can dominate frame time even when the mean looks fine.

31. Scalability Analysis

What stays constant vs. grows, in Big-O terms: the vertex stage is linear in vertex count, independent of screen resolution or triangle overlap (O(V)). Rasterization cost is linear in covered fragments, not in triangle count — a single huge triangle costs more than many small ones covering the same area (O(F), F = total covered fragments, not O(T)). Binning cost is linear in triangle-tile overlaps, which itself scales with both triangle count and triangle size relative to tile size (O(Σ overlaps), section 34's per-tile bin-memory derivation). Clip-stage cost is linear in triangle count with a bounded per-triangle constant factor (I13's ≤7× amplification bound, never superlinear).

Named bottlenecks in order of typical dominance: fill rate versus setup rate is the primary crossover — for scenes with many small triangles (sub-pixel or near-sub-pixel), setup cost dominates (each triangle costs a fixed setup overhead regardless of how few pixels it covers); for scenes with few large triangles, fill rate dominates (per-pixel/per-fragment cost, including texture sampling and shading, scales with covered area). The crossover point is roughly where average triangle screen-area approaches the per-triangle setup cost divided by per-pixel shading cost — measured empirically per scene, not a fixed constant (section 30's profiling methodology is how this crossover is located for a given workload).

Parallel scaling across tiles is limited by two named factors: load imbalance from uneven triangle distribution across tiles (mitigated by rayon's work-stealing over fine-grained per-tile units, but not eliminated — a single screen region with disproportionate triangle density still bottlenecks that region's owning thread, FM-12), and memory bandwidth (all threads ultimately share the same memory bus; texture-cache and tile-buffer traffic contends even though logical tile ownership is disjoint, section 30's false-sharing profiling). Resolution and triangle-count ceilings: the section 4 framebuffer-memory budget (64 MB at 1920×1080 MSAA4x) scales linearly with resolution² and MSAA sample count, becoming the binding constraint before compute does at sufficiently high resolution or sample count; the levers beyond that ceiling are reducing MSAA sample count, tiling more aggressively (smaller tiles reduce peak per-tile memory but raise binning overhead, ADR-05's tradeoff), or accepting a lower resolution — there is no architectural lever beyond those three within this design.

32. Mental Models & First Principles

MM1 — Rasterization is a point-in-triangle test evaluated on a lattice. Every quality rule — fill conventions, interpolation, antialiasing — is a statement about how that lattice is sampled. It predicts that any visual artifact traces back to either where the lattice samples are placed (MSAA, P10) or how "inside" is decided at a sample (the fill rule, P1). Without it, a developer treats cracks and seams as separate bug classes instead of the same underlying sampling-consistency question. Resolved in section 8 and Phase 2.

MM2 — The whole pipeline is a memory-access-pattern problem wearing geometry clothes. Tiling exists because cache misses, not FLOPs, dominate a flat framebuffer's cost (Drepper 2007). It predicts that the biggest single-phase speedup (Phase 10) comes from a data-layout change, not a math optimization. Without it, a developer chases SIMD and algebraic optimizations first and is surprised when tiling alone dwarfs them. Resolved in Phase 10 and section 30.

MM3 — Homogeneous coordinates make projection a matrix, at the cost of a divide you must not skip or reorder. w carries the information that perspective divide will later consume; treating a clip-space vector as if it were already Euclidean (dividing early, or clipping late) is the single most common structural bug class in this domain. It predicts every w≤0/w=0 failure mode in Phase 5. Resolved in section 8 (P2) and Phase 5.

MM4 — Perspective-correctness is a statement about what's linear in which space. Screen-space position is not linear in barycentric-space attributes once projection is involved; 1/w is the quantity that restores linearity. It predicts the exact shape of the "swimming texture" bug and why it's invisible on fronto-parallel geometry. Resolved in section 8 (P3) and Phase 4.

MM5 — A tile boundary is a second, coarser fill rule. Everything I1 says about shared triangle edges applies again, one level up, to shared tile edges — the same discipline (canonical shared arithmetic) that prevents Phase 2 cracks is what prevents Phase 10 tile-boundary cracks. It predicts that Phase 10's hardest bugs are Phase 2's bugs recurring at a different granularity, not new bugs. Resolved in Phase 10 (fx_10_tile_boundary_coverage).

MM6 — Depth precision is a resource allocated by the projection matrix, not a property of the depth buffer's bit width. Where that precision concentrates (near the near plane, under the standard OpenGL mapping) is a design choice, not a law of nature — reverse-Z reallocates it. It predicts that widening the depth buffer's bit width without changing near/far or the mapping barely helps z-fighting. Resolved in section 8 and Phase 3 (P4).

MM7 — LOD selection is a local, differential quantity, not a global, distance-based one. Screen-space derivatives measure how fast texture coordinates change per screen pixel, which is what aliasing actually depends on — camera distance is a confound, not the cause. It predicts that a grazing-angle surface at a fixed distance needs a different mip level than a fronto-parallel surface at the same distance. Resolved in section 8 (P6) and Phase 8.

MM8 — Determinism is a design decision, enforced continuously, not a property you get for free from "the same code." Floating-point non-associativity, FMA contraction, and thread/SIMD scheduling all silently break bit-identical output unless explicitly pinned. It predicts that I7/I8 regressions are almost always toolchain/scheduling changes, not logic bugs. Resolved in section 27 (ADR-24) and Phase 10/11.

MM9 — MSAA buys antialiasing cheaply only because shading and coverage are decoupled. The moment shading happens per-sample instead of per-pixel, the "cheap" is gone and you've reinvented supersampling with extra bookkeeping. It predicts the exact failure signature of P10 violations (shader-invocation-count fixture). Resolved in section 8 and Phase 9.

Mesa llvmpipe made the decision to JIT-compile each shader to native machine code at draw time, trading compilation latency for near-native per-fragment throughput — this wins whenever a driver-fallback path must sustain arbitrary, frequently-changing shader programs at production quality without a GPU present. SwiftShader made the decision to target exact conformance with a real hardware API's (D3D/Vulkan) precision and behavior rules rather than an idealized abstract pipeline — this wins specifically for headless browser rendering, where pixel-perfect agreement with what a real GPU would have produced is the entire point. Larrabee made the decision to make the rasterizer itself a piece of software running on general-purpose x86 cores rather than fixed-function silicon — this wins (as a research/architecture direction, though the product never shipped as a GPU) whenever programmability of every pipeline stage, not just shading, is worth more than the efficiency fixed-function hardware buys. tinyrenderer made the decision to skip tiling, perspective-correct interpolation shortcuts, and conformance entirely in favor of the shortest path to "a triangle appears on screen" — this wins purely for first-exposure pedagogy, at the explicit cost of teaching a couple of shortcuts (flagged in section 5) that this blueprint deliberately does not repeat. A hardware GPU pipeline made the decision to fix the rasterizer, blend, and depth-test stages in silicon while making only shading programmable — this wins at any scale where raw throughput per watt matters more than the ability to modify the rasterizer itself, which is exactly the axis this software project exists to make legible rather than to compete on.

34. Back-of-Envelope Capacity Model

Framebuffer memory (chained from section 4): width × height × (color bytes + depth bytes) × MSAA samples = 1920 × 1080 × (4 + 4) × 1 = 16,588,800 bytes ≈ 15.8 MB at 1×; × 4 samples (ADR-17) = 63.3 MB, matching the section 4 constraint.

Tile count and per-tile bin memory: tile count = ⌈1920/64⌉ × ⌈1080/64⌉ = 30 × 17 = 510 tiles. Assuming an average of 40 binned primitives per tile on a moderately dense scene, and a BinnedPrimitive bin-entry size of roughly 64 bytes (triangle_id + edge coefficients + clipped bbox, section 11), per-tile bin memory ≈ 40 × 64 = 2,560 bytes, well under the ADR-05/section 4 64 KB-per-tile ceiling — the ceiling is sized for a worst-case dense-overlap scene, not the average case.

Fill-rate requirement: pixels × average overdraw × frames per second = (1920×1080) × 3 (assumed average overdraw for a moderately complex scene) × 60 fps ≈ 373.2M fragments/second required, comfortably under the M5 target (≥800M px/s at 8 threads, section 30) with headroom for shading cost. The resulting per-pixel time budget at 60fps, single fragment: 1/373.2M ≈ 2.68 ns per fragment amortized across all shaded fragments in the frame.

Vertex-stage cost: vertices × per-vertex transform cost. At 500K visible triangles (≈250K unique vertices with shared-vertex indexing) and a per-vertex cost of one 4×4 matrix multiply (~16 multiply-adds, well under 10ns on a modern core), total vertex-stage cost ≈ 250,000 × 10ns = 2.5 ms — a small fraction of the 16.6ms frame budget (M3), confirming the section 13.7 claim that vertex transform is not the bottleneck.

Clip amplification worst case: one triangle against six planes produces up to 9 vertices (3 + 6, one added vertex per plane in the worst case) → up to 7 triangles via fan triangulation (I13, section 4 M6). Memory implication: the clip-stage scratch buffer must hold at least 9 ClipVertex records (each carrying Vec4 + ShaderVaryings, roughly 64-96 bytes depending on varying count) ≈ 9 × 96 ≈ 864 bytes of worst-case per-triangle clip scratch — negligible compared to the 256KB per-thread scratch budget (section 4).

Texture memory with a full mipmap chain: base texture at 4096×4096×4 bytes (RGBA8, section 4 max) = 67,108,864 bytes ≈ 64 MB; full mip chain adds levels at 1/4, 1/16, 1/64... of the base, summing geometrically to base × (1 + 1/4 + 1/16 + ...) = base × 4/3 ≈ 85.3 MB total for one fully-mipped max-size texture — the 4/3 multiplier is the standard mipmap-chain memory overhead cited in Williams 1983's construction.

Depth precision at the chosen near/far ratio: near=0.1, far=1000 (ratio 10,000:1). Using the section 8 z_ndc equation, the world-space z-fighting threshold near the near plane (where one f32 depth ULP maps to the smallest resolvable world-space z difference) is approximately 2.4×10⁻⁴ world units; at the far plane, the same one-ULP depth step corresponds to approximately 24 world units — a 10^5-scale precision disparity between near and far, the concrete numeric justification for placing the near plane as close as the scene tolerates (P4, Phase 3 N.6).

SIMD speedup ceiling from quad-based fragment processing: processing 4 pixels per SIMD lane-group (128-bit SIMD, wide crate, ADR-20) yields a theoretical 4× ceiling on the inner rasterization/shading loop, reduced in practice by the fraction of quads that are only partially covered (wasted lane work at triangle silhouette edges, section 8's failure-path example) — for typical scenes with triangle edge density seen in the section 4 workload (500K triangles at 1920×1080), the practically achievable SIMD speedup is estimated at 2.5-3× rather than the full 4× ceiling, consistent with the Phase 11 M-series targets already assuming sub-linear SIMD scaling.

36. Alternative Architectures (Roads Not Taken)

Scanline / active-edge-table rasterizer — the classic pre-GPU approach: maintain a sorted active-edge table per scanline, walking horizontal spans rather than testing a bounding box against edge functions.

 Sorted Edge Table (by ymin)
        │
        ▼
 For each scanline y:
   [Update Active Edge List]  (add edges starting, remove edges ending)
        │
        ▼
   [Sort AEL by current x]
        │
        ▼
   [Fill spans between AEL pairs]  -- one span per (in,out) edge crossing
        │
        ▼
   [Next scanline]  (increment each edge's x by its slope)

Winning regime: single-threaded, immediate-mode rendering of large polygons with few triangles (classic 1990s software rendering, wireframe/vector-art fills). Embodied by early Mesa swrast and pre-GPU-era renderers generally. Rejected here because active-edge-table state is inherently sequential per scanline (each scanline's AEL depends on the previous one), hostile to the tile-parallel decomposition (P11, ADR-04) this blueprint is built around — Pineda's edge-function formulation was chosen specifically because it has no such sequential dependency (section 5, section 8).

Ray-traced visibility (the sibling rank-170 architecture) — solve visibility by tracing rays per pixel against an acceleration structure instead of projecting geometry.

 Camera rays (one+ per pixel)
        │
        ▼
 [Acceleration Structure Traversal]  (BVH/kd-tree)
        │
        ▼
 [Ray-Primitive Intersection]
        │
        ▼
 [Shading + recursive/stochastic sampling]  (light transport)
        │
        ▼
 [Framebuffer accumulate]

Winning regime: scenes where visibility cost should scale logarithmically with scene complexity rather than linearly with fill rate — complex, deeply occluded scenes, or physically based global illumination where secondary rays are unavoidable. Embodied by the Ray Tracer, rank 170. Rejected here because this project's defining bet is the opposite one: visibility is solved by projection and a depth buffer (section 1's stated scope), trading logarithmic scene-scaling for a fill-rate-bound cost model that maps directly onto exactly the tiled, cache-friendly hardware this blueprint targets (P11, section 31).

Deferred / visibility-buffer architecture — decouple rasterization (write a per-pixel primitive/barycentric ID) from shading (a full-screen pass reading that buffer).

 [Rasterize: write VisibilityBuffer]  (triangle_id, barycentrics per pixel)
        │
        ▼
 [Full-screen Shading Pass]  (reads VisibilityBuffer, reconstructs attributes, shades once)
        │
        ▼
 [Framebuffer]

Winning regime: scenes with extreme shader complexity and material variety where avoiding redundant shading work on overdrawn fragments matters more than pipeline simplicity — this is the modern deferred/visibility-buffer approach used in several real-time engines under heavy overdraw. Rejected here because it adds a second full-screen pass and a reconstruction step that would obscure the direct, one-pass pipeline this blueprint is built to teach (section 1's legibility goal) — the forward, single-pass tiled pipeline (section 3) keeps the shading contract (P7, P10) directly attached to the rasterization stage that produced it.

Sort-last parallel architecture — as the alternative to this blueprint's sort-middle binning: each thread rasterizes an entire disjoint subset of triangles into a full-screen private framebuffer, then a final compositing pass merges all threads' framebuffers by depth.

 Triangle list, partitioned by thread (not by screen tile)
        │
   ┌────┴────┬─────────┐
   ▼         ▼         ▼
[Thread 0] [Thread 1] [Thread N]   each: full pipeline, full-screen private framebuffer
        │         │         │
        └────┬────┴─────────┘
             ▼
     [Depth-Composite Merge]   -- O(threads) per pixel, every pixel

Winning regime: scenes with a very small, fixed triangle count relative to screen resolution, where per-thread full-screen framebuffer memory is affordable and triangle-partitioning is trivially balanced. Embodied conceptually by some early parallel-rendering research systems. Rejected here because per-thread full-screen framebuffers multiply memory cost by thread count (violating the section 4 framebuffer-memory budget at any nontrivial thread count) and the final merge pass is itself an O(threads × pixels) serialization point that P11's disjoint-tile design avoids entirely by construction (ADR-04, ADR-18, ADR-19).

38. Glossary

  • Anisotropic filtering: sampling a texture with more samples along the elongated axis of its screen-space footprint; deferred (section 37).
  • Backface culling: discarding a triangle whose screen-space winding indicates it faces away from the camera (ADR-07).
  • Barycentric coordinate: a triangle-relative weight (λ0, λ1, λ2), summing to 1, expressing a point as a combination of the triangle's three vertices.
  • Bilinear filtering: sampling a texture as a weighted average of the four nearest texels.
  • Binning: assigning primitives to the tiles their bounding box overlaps, prior to per-tile rasterization.
  • Clip space: the coordinate space immediately after the projection matrix is applied, before perspective divide.
  • Coverage mask: a per-pixel bitmask indicating which MSAA sample positions are inside a given triangle.
  • Depth buffer: a per-pixel buffer storing the closest interpolated depth value seen so far, used for hidden-surface removal.
  • Depth precision: the granularity with which distinct world-space depths can be distinguished by the depth buffer's representation.
  • Derivative (screen-space): the rate of change of an interpolated attribute (e.g. UV) with respect to screen x or y, used for LOD selection.
  • Early-Z: performing the depth test before the fragment shader runs, skipping shading for occluded fragments.
  • Edge function: a linear function of pixel position, zero on a triangle edge and of consistent sign on either side, used for the inside-triangle test (Pineda 1988).
  • Fill rate: the number of fragments a rasterizer can shade and write per second.
  • Fill rule: the convention deciding which triangle owns a pixel that lies exactly on a shared edge.
  • Fixed-point: a numeric representation with an implicit fractional scale (here, 24.8 subpixel coordinates), as opposed to floating point.
  • Fragment: a single candidate pixel-sample produced by rasterizing a triangle, prior to the depth test and shading.
  • Framebuffer: the combined color and depth (and MSAA sample) storage for one rendered frame.
  • Frustum: the truncated-pyramid view volume bounded by six clip planes.
  • Guard band: an extended screen-space region within which triangles skip full clipping (P13).
  • Half-space test: an equivalent name for the edge-function inside-triangle test, evaluating which side of each edge's line a point falls on.
  • Homogeneous coordinate: a 4-component representation (x,y,z,w) of a 3D point or vector enabling projection to be expressed as a matrix multiply.
  • LOD (level of detail): the selected mip level for texture sampling, derived from screen-space derivatives (section 8).
  • Mipmap: a precomputed pyramid of progressively downsampled texture images (Williams 1983).
  • MSAA (multisample antialiasing): sampling triangle coverage at multiple positions per pixel while shading only once per pixel (P10).
  • NDC (normalized device coordinates): the coordinate space after perspective divide, in [-1,1]³ (or [0,1] for depth, per convention).
  • Overdraw: the number of times a given pixel is shaded across all triangles submitted in a frame, before depth testing eliminates the occluded ones.
  • Perspective-correct interpolation: interpolating an attribute via the 1/w formula (section 8) so the result respects projective foreshortening.
  • Perspective divide: dividing a clip-space coordinate's x, y, z components by w to obtain NDC.
  • Premultiplied alpha: a color representation where RGB channels are pre-scaled by alpha, simplifying certain blend equations.
  • Primitive assembly: grouping shaded vertices, via index triples, into triangles.
  • Quad (fragment quad): a 2×2 group of fragments processed together to enable finite-difference derivative computation (P6).
  • Resolve: averaging MSAA samples (or copying tile-local buffers) into the final single-sample framebuffer.
  • Screen-space derivative: see derivative (screen-space).
  • Setup rate: the number of triangles per second a rasterizer can compute edge functions and bounding boxes for, independent of fill cost.
  • Sort-middle: a parallel rasterization architecture partitioning work by screen-space tile after geometry processing but before final compositing (ADR-04).
  • Sort-last: a parallel rasterization architecture partitioning work by primitive/thread, compositing full private framebuffers at the end (section 36).
  • Subpixel precision: the fractional-bit resolution at which screen coordinates are quantized for rasterization (24.8, ADR-02/03).
  • Tile: a fixed-size rectangular region of the framebuffer processed independently during rasterization (P11).
  • Tile scheduler: the work-distribution mechanism (rayon's work-stealing scheduler, ADR-18) that assigns tiles to worker threads.
  • Top-left rule: the specific fill-rule convention classifying a pixel on a shared edge as covered by the triangle for which that edge is a top or left edge (section 8).
  • Varying: an interpolable per-vertex attribute passed from vertex shader to fragment shader (ShaderVaryings).
  • Viewport transform: mapping NDC coordinates to screen-space pixel coordinates.
  • Watertight mesh: a mesh whose triangles share edges exactly, with no gaps or overlaps, used as the basis for the I1 coverage invariant.
  • Winding order: the vertex traversal order (clockwise or counter-clockwise) of a triangle, determining its facing direction.
  • w (homogeneous coordinate): the fourth component of a homogeneous vector, equal to −z_eye under this project's projection-matrix convention (section 8).
  • Z-buffer: see depth buffer.
  • Z-fighting: visible flicker between two near-coplanar surfaces whose depth values are indistinguishable at the buffer's precision (P4).
