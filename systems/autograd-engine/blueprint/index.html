112 — Autograd Engine / Mini-PyTorch

Project Number: 112

Project Name: Autograd Engine / Mini-PyTorch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a reverse-mode automatic-differentiation engine with a dynamic, define-by-run computation graph, in the lineage of PyTorch's torch.autograd, JAX, Karpathy's micrograd, and Tinygrad: a strided N-dimensional Tensor, a tape of Nodes each holding a Function's saved context and a backward closure, numpy-style broadcasting with its gradient-reduction inverse, a small principled op library (elementwise, reductions, matmul, conv2d, layer-norm, softmax, attention), a Module/Parameter/ Optimizer layer, and a dataloader + training loop sufficient to drive a 3-layer MLP on MNIST to <2% test error. Later phases add higher-order gradients, mixed-precision autocast, JIT graph capture + fusion, and CUDA/Metal backends behind one Device abstraction.

Phase-0 deliverable (numbered):

  1. ag-core — DType, Device, Shape, Strides, error types.
  2. examples/micrograd-port — scalar Value autograd (the correctness kernel).
  3. Repository skeleton — workspace Cargo.toml, CI, Makefile, docs scaffold (§10).
  4. Conformance runner stub — conformance/runner, emits conformance.report.json.
  5. ADRs 001, 002, 004, 007, 008, 010, 018, 023 (§9) drafted and accepted.

System boundaries.

  • Provides: tensor algebra, reverse-mode autodiff, a tape-based dynamic graph, a differentiable op library, an nn.Module layer, optimizers, a dataloader, and (from Phase 9 onward) higher-order grads, autocast, JIT fusion, and GPU backends.
  • Delegates: BLAS-grade linear algebra is hand-written, not vendored (ADR-15); distributed training beyond a ring-allreduce hook (§24) is out of scope; a Python frontend is a deferred surface (Deferred Features Register).
  • Does NOT provide: a general tensor-compiler (no XLA-equivalent HLO IR), a model zoo, a serving runtime, or ONNX import/export.

Non-goals: matching PyTorch's full op surface (~2,000 ops); supporting arbitrary Python-level dynamism (control flow is Rust control flow, not a traced language); multi-node training beyond the Phase-12 ring-allreduce hook.

Deployment model: a linked Rust library (ag-* crates) plus a CLI (agctl) for benchmarking, training, and tape inspection; no server component, no network service surface except the Phase-12 distributed hook.

Target users/operators: ML systems engineers building or debugging training infrastructure; the CLI operator who runs agctl train / agctl bench / agctl inspect-tape locally or in CI.

What later phases unlock: Phase 9 (higher-order grads) unlocks meta-learning and Hessian-vector products; Phase 10 (autocast) unlocks 1.5-2x training throughput on bf16-capable CPUs; Phase 11 (JIT) unlocks kernel fusion and a torch.compile-shaped speedup; Phase 12 (GPU backends + distributed) unlocks off-CPU training and multi-process data parallelism.

Recommended language + rationale: Rust, edition 2021, toolchain pinned 1.75 (ADR-01). Rejected: Python + C++ split (the PyTorch shape) — doubles the surface area, adds a Pybind11/ABI maintenance tax, and the point of the project is to own the kernel layer, not wrap one; C++ alone — no memory-safety guarantee for the Weak/Arc tape discipline (§8.4) that this design leans on; Zig — smaller ecosystem, no mature SIMD

  • rayon-equivalent story at project start.

Prerequisites: reverse-mode AD as a graph-traversal algorithm (§5 primer if new to it); strided tensor layouts (what expand does to strides, why transpose is free); Rust ownership well enough to reason about Arc/Weak cycles; linear algebra at the level of deriving d/dW softmax(Wx+b) by hand.

Estimated timeline: Phase 0 — 1 week. Full system (Phase 0 through Phase 12) — 8-12 months of part-time systems work, or 10-14 weeks full-time.

Deferred features, flagged where they are introduced and collected in the Deferred Features Register: a Python frontend via PyO3 PhaseDeferred("§38"); ONNX import/export PhaseDeferred("§38"); gradient checkpointing as a runtime opt-in (recomputation is a Phase-11 JIT-time transform only) PhaseDeferred("§38"); a full BLAS-vendor fast path behind a blas feature PhaseDeferred("§38"); sparse tensors PhaseDeferred("§38").

2. Why Build This

Every deep-learning project rests on an autodiff engine its author did not write. torch.autograd, JAX's grad, TensorFlow's GradientTape are each opaque the moment a training loop misbehaves — a NaN loss at step 4,217, a custom Function whose gradient is silently wrong by a sign, a non-contiguous view that corrupts a backward pass through an in-place op. "I assume the framework is correct" is right 99% of the time; the 1% is what separates an ML engineer who ships from one who debugs, and that 1% is only reachable by having built the tape yourself.

The literature is unusually deep and unusually settled (§5 is the reading list in full; this is the map). Griewank & Walther (2008) is the textbook: forward-mode, reverse-mode, the chain rule on a DAG, checkpointing. Baydin et al. (2018, JMLR) is the contemporary survey and the source of this blueprint's vocabulary — tape, primal, adjoint, VJP, JVP. Wengert (1964) is the origin of the tape itself. Maclaurin et al. (2015) is the spiritual ancestor of every modern tape-based engine — 1,000 lines of Python that fit in your head. Karpathy's micrograd is the same idea at 100 lines and is Phase 0 of this blueprint almost verbatim. Tinygrad takes the same idea and makes it a real, if minimal, production framework with kernel fusion. PyTorch (Paszke et al. 2019) and JAX (Bradbury et al. 2018) are the two systems the field actually trains against, and this design sits at their intersection: PyTorch's eager, imperative tape by default (Phases 0-10), with a JAX/Tinygrad-shaped traced-and-fused path opt-in at Phase 11.

Building this engine builds muscles that transfer directly: reasoning about reference-counted cyclic-looking graphs without leaking (the Arc/Weak discipline, §8.4, shared with any incremental-computation system — Salsa, Adapton); reasoning about strided memory and cache-aware kernels (shared with any numerical-computing system — BLAS, NumPy, TVM); reasoning about correctness under floating-point (gradcheck, shared with any numerical-simulation codebase); reasoning about a compiler pipeline for a traced IR (Phase 11, shared with XLA, TVM, Halide). It also builds the calibration to read a stack trace out of PyTorch's engine.cpp and know, from first principles, what went wrong.

What Mastery Looks Like — after building this system, you can:

  • Derive the VJP of any elementwise, reduction, or contraction op on paper and predict its shape before running it (built in Phase 3, §15).
  • Explain why a Tensor's grad_fn must be a Weak reference and what leaks if it is not (Phase 2, §14; §8.4).
  • Diagnose a wrong gradient by bisecting the tape with gradcheck and reading a single op's forward/backward pair in isolation (Phase 2, §14.6; Phase 3, §15.5).
  • Explain the memory/recompute trade in gradient checkpointing and where the JIT would insert it (Phase 11, §23).
  • Predict, from the System Constraints table alone (§4), whether a given model and batch size will OOM before running it (Back-of-Envelope Capacity Model, §35).
  • Redesign the engine as a static-graph (TensorFlow 1.x-shape) or a fully-traced-functional (JAX-shape) system and state exactly which properties are traded (Alternative Architectures, §37).
  • Read PyTorch's or JAX's autograd source and map every construct in it back to a named concept in this blueprint (§5 traceability).

Trust boundary: none (single-process library). Concurrency boundary: the Tape is thread-local (§8.4) — cross-thread autograd is out of scope (§1). Persistence boundary: state_dict serialization only (§9 ADR-13). External interface: the agctl CLI (§10) and the ag-py FFI stub (Deferred, §38).

User code / nn.Module / functional API. Two equivalent entry points into the engine: a stateful Module tree that owns Parameters (§19, Phase 7), or bare functions (F.relu, F.cross_entropy) that take tensors and return tensors. Both bottom out in the same Tensor + Function machinery — there is no separate "graph mode."

Tensor. A (Storage, StridedView, autograd metadata) triple (§11.3). Carries an optional grad_fn pointing at the Node that produced it. Does not own the graph.

Function. The unit of differentiation (§11.5). Every op — built-in or user-defined — implements forward (computes the primal, dispatches to a Backend) and backward (computes the vector-Jacobian product from a saved Ctx).

Tape. The recording surface (§11.6, §8.4). Holds the only strong (Arc) references to Nodes; every Tensor.grad_fn is a Weak reference. backward() topologically sorts from the output, seeds its gradient, and walks in reverse, calling each Node's Function::backward and accumulating the result into parent gradients (§8.3).

Backend. The kernel layer (§11.4). A Device tag on every Tensor selects CpuBackend (the only backend through Phase 8), or CudaBackend/MetalBackend (Phase 12, §24). The autograd machinery above this line never changes across backends — only the kernel implementation does.

Six invariant properties of this diagram, referenced throughout: the graph is dynamic (built at call time, no separate compile step — I1, §7); the tape, not the tensor, is the unit of differentiation (I2); tensors are zero-copy strided views over reference-counted storage (I3, §8.1); broadcasting is numpy semantics exactly (I4, §8.2); autograd is reverse-mode by default with a first-class Function/VJP interface for custom ops (I5); the backend is pluggable, the autograd is not (I6).

6. Design Principles

  1. P1 — Reverse-mode by default, forward-mode behind a flag. Reverse-mode wins when outputs are scalar (losses) and inputs are vectors (parameters) — the universal deep-learning case. Forward-mode (jvp) ships in Phase 9 (§21) as a separate transform, never the default path. Violating this (running both modes unconditionally) doubles compute for no benefit on the common case.

  2. P2 — Dynamic graph, eager execution. Every op runs and records at call time; no compile() step on the default path (§3, ADR-02). Trade-off: no whole-graph compiler optimization until Phase 11's opt-in JIT. Violating this by requiring a trace up front breaks the imperative debugging story that is this project's reason to exist (§2).

  3. P3 — The tape is the source of truth for the graph; the tensor is not. A Tensor.grad_fn is a Weak pointer into the current Tape; the Tape owns Nodes via Arc (§8.4, ADR-04). Violating this — tensors holding strong refs to their producing node — creates an uncollectable reference cycle the first time a tensor is reused across steps.

  4. P4 — Storage is reference-counted; views are zero-copy. Reshape, transpose, slice, permute, expand all share the source Storage (§8.1, ADR-03). Only .contiguous() copies. Violating this by copying on every view makes the engine quadratic in graph depth for view-heavy models (attention, in particular).

  5. P5 — Broadcasting is numpy semantics, exactly. Two shapes broadcast iff each right-aligned dimension pair is equal, one is 1, or one is absent (§8.2). The backward of every broadcasting op reduces via unbroadcast (§8.3). Violating this — inventing a bespoke broadcast rule — breaks every ported numpy/PyTorch reference fixture (§5, Required Reading — numpy spec).

  6. P6 — In-place ops are dangerous and version-tracked. A per-Storage atomic version counter is bumped on every mutating write; backward() checks the saved version before differentiating through a saved tensor and errors if it has moved (§8.4, ADR-07, I9 §7). Violating this — allowing silent in-place corruption of a value needed for backward — produces gradients that are wrong without any error signal, the single worst failure class in an AD engine (FM-2, §26).

  7. P7 — Gradients accumulate; .grad is never auto-zeroed. A parameter used twice in one forward pass receives the sum of both branches' VJP contributions (§8.3). The caller zeros gradients explicitly (Optimizer::zero_grad, §18). Violating this by auto-zeroing breaks legitimate gradient-accumulation training loops (large effective batch size via multiple micro-batches).

  8. P8 — Mixed precision is opt-in and per-op, never per-network. bf16 autocast (Phase 10, §22) whitelists ops where reduced range is safe (matmul, conv) and blacklists ops where it is not (softmax, layer-norm, loss reduction). Violating this by running an entire network in bf16 loses training stability on exactly the ops (softmax, norm) whose dynamic range matters most.

  9. P9 — Backends are pluggable behind a Device tag; autograd is not. The same Function trait executes regardless of Device::Cpu | Cuda | Metal (§3, §11.4). Violating this — special-casing autograd logic per backend — means every new backend re-derives correctness from scratch instead of inheriting it.

  10. P10 — The kernel set is small and principled. Elementwise, reductions, matmul, conv2d, layer-norm, softmax, attention — the set that expresses an MLP, a CNN, and a small transformer (§11.1, §15-17). Violating this by chasing PyTorch's ~2,000-op surface trades reviewability for coverage this project does not need (§1 Non-Goals).

  11. P11 — No Python on the critical path. The engine, CLI, and conformance harness are Rust; PyO3 bindings are a deferred surface (PhaseDeferred("§38")), not a dependency of any phase. Violating this reintroduces the Python/C++ ABI maintenance tax ADR-01 rejected.

  12. P12 — The MNIST integration test is non-negotiable. Every phase must keep the Phase-8 MNIST run (§20) green: <2% test error, <10 min CPU wall-clock (§4 M7). Violating this — merging a phase that regresses either bound without an accompanying ADR — is treated as a build break, not a follow-up item.

  13. P13 — Fixtures before ops. No op ships without a gradcheck conformance fixture (§8.3, §5 grad_check.rs) at both f32 and f64. Violating this means an op's backward is unverified the moment it lands, and unverified backwards are exactly where AD engines silently rot.

  14. P14 — One numbering, one vocabulary, everywhere. Type names, file paths, invariant IDs (I#), ADR IDs (ADR-##), principle IDs (P#) are chosen once (this document) and reused identically in the Repository Layout (§10), Core Schema (§11), and every phase. Violating this — renaming a type between the schema and a phase — is the single most common defect this standard exists to catch.

8. Domain Model

8.1 Tensor and storage model

A Tensor is (Arc<Storage>, StridedView, autograd metadata). Storage is a flat Arc<[T]>-equivalent allocation tagged with dtype and device; a StridedView is (shape: [u32; ≤6], strides: [i64; ≤6], offset: u64). Element i at logical index (i0..in) reads storage[offset + Σ ik * strides[k]]. A tensor is contiguous iff strides == shape.contiguous_strides(). Reshape/transpose/permute/slice/expand return a new StridedView over the same Arc<Storage> — zero bytes copied (I3, P4). .contiguous() is the only operation that allocates a fresh Storage when the source view is non-contiguous.

View op Storage shared? Strides change Backward (Phase 2, §14)
reshape/view yes (requires contiguous source) recomputed for new shape inverse reshape
transpose(d0,d1) yes swap strides[d0], strides[d1] transpose(d0,d1) again
permute(dims) yes reorder per dims inverse permutation
expand(shape) yes 0 on broadcast axes sum over the 0-stride axes
slice(ranges) yes unchanged; offset shifts zero-pad-scatter into source shape
contiguous() no — copies recomputed contiguous identity (already contiguous)

8.2 Broadcasting

Two shapes A, B broadcast to C by right-aligning and, per aligned pair (a, b): if a == b, c = a; if a == 1 or absent, c = b; if b == 1 or absent, c = a; otherwise incompatible (BroadcastError, I4). Example: (4, 1, 3) and (2, 3) right-align to (4, 1, 3) / (_, 2, 3) → c = (4, 2, 3). Broadcasting is implemented as a stride trick — a broadcast axis gets stride = 0, so repeated reads hit the same memory (§8.1) — never a materializing copy.

Backward of broadcasting (unbroadcast). A gradient computed at the broadcast output shape C must be reduced to each input's original shape before attribution: first sum over any leading axes C has beyond the input's rank, then sum(..., keepdim=true) over any axis where the input had size 1 and C does not. This single helper (§14.3) is called by every broadcasting op's backward (add, mul, div, pow, comparisons).

8.3 Reverse-mode autodiff and the backward walk — worked example

Forward: y = x*x + 3*x + 2 at x = 4.0 (tensor of one element). Trace recorded on the tape, in call order:

Step Op Inputs Output Node parents
1 mul x, x t1 = 16 x (twice — same TensorId)
2 mul const(3), x t2 = 12 x
3 add t1, t2 t3 = 28 t1, t2
4 add t3, const(2) y = 30 t3

Backward: seed grad(y) = 1. Topological order reversed: y → t3 → t2, t1 → x. At each node, Function::backward(ctx, grad_output) returns the VJP for each input, and the caller accumulates (I6) into that input's running gradient:

  • add(t3, 2): grad(t3) += 1, (the constant 2 is not a leaf, discarded).
  • add(t1, t2): grad(t1) += 1, grad(t2) += 1.
  • mul(3, x) (t2): grad(x) += 3 * grad(t2) = 3.
  • mul(x, x) (t1): grad(x) += x * grad(t1) + x * grad(t1) = 4 + 4 = 8.
  • Final: grad(x) = 3 + 8 = 11, matching the analytic dy/dx = 2x + 3 = 11 at x=4.

This is the exact fixture in Phase 0 (§12.5) and Phase 2 (§14.7); it exercises the topological sort (I8), the accumulation invariant (I6), and the base case of every later gradcheck fixture (§8.3, P13).

8.4 The tape, Node, and the Weak-pointer discipline

Node {
  fn_obj:    Arc<dyn Function>     // §11.5
  ctx:       Ctx                    // saved tensors/scalars/shapes for backward
  inputs:    [NodeRef]              // NodeRef = Weak<Node>, the upstream parents
  output_id: TensorId
}

Tape {
  nodes:     Vec<Arc<Node>>         // the ONLY strong references to Node
  by_output: HashMap<TensorId, Weak<Node>>
}

A Tensor's grad_fn: Option<NodeRef> is a Weak<Node>; a Node's inputs are also Weak<Node>. Only the Tape holds Arc<Node> (P3, I2). This breaks the cycle "tensor A's grad_fn references the node that produced it, which references tensor B's node as a parent, which references A" — a cycle that would otherwise leak on every training step. When Tape::fresh() runs at the start of the next step, every Node's sole strong reference (the Vec<Arc<Node>>) is dropped; all Weak pointers held by surviving leaf tensors (the parameters) simply resolve to None, which is correct — leaves have no grad_fn in the first place.

Malformed-input example. Calling y.backward() where y.grad_fn.is_none() (e.g. y is a leaf, or was produced entirely under a NoGradGuard) is a malformed call: the tape has no node to start the reverse walk from. §11.3's backward() returns Err(NoGradFn) from Phase 9 onward (a panic in the Phase 0-8 didactic build, per §12); the message names the tensor's TensorId and whether it was ever requires_grad.

Failure-path example. An in-place op (x.add_(1.0)) bumps x.storage.version() (I5). If a Function::backward later reads x from a saved Ctx whose saved_version no longer matches, verify_versions (§14.4) fails the backward call with InPlaceHazard { tensor_id, saved_version, current_version } before any wrong gradient is computed or accumulated — the version check runs at node-visit time, ahead of the VJP call (I5, I9).

8.5 State machine: tape lifecycle

State Entered by Exit transition Invariant held
Empty process start / Tape::fresh() first op with requires_grad input I2 (no nodes)
Recording any op call while grad_enabled() == true backward() call, or Tape::fresh() I1, I8
Draining (mid-backward()) backward() entry reverse walk completes or errors (I5/I7/I9) I6, I8, I9
Stale (post-backward, pre-reset) successful backward() return next Tape::fresh() at step boundary I2 (nodes still live; leaves still valid)

NoGradGuard (§14.5) does not change tape state — it flips grad_enabled so ops skip the Recording transition entirely, which is how inference and parameter copies avoid growing the tape at all.

Ownership: one Arc<dyn Backend> singleton per Device (§3, P9). Concurrency: Send + Sync; CPU backend parallelizes internally via rayon (ADR-10). Persistence: stateless; no backend state crosses a state_dict boundary.

11.5 Function and Ctx

pub trait Function: Send + Sync + Debug {
    fn name(&self) -> &'static str;
    fn n_inputs(&self) -> usize;
    fn forward(&self, ctx: &mut Ctx, inputs: &[&Tensor]) -> Tensor;
    fn backward(&self, ctx: &Ctx, grad_output: &Tensor) -> SmallVec<[Tensor; 4]>;
}

pub struct Ctx {
    saved_tensors: SmallVec<[Tensor; 4]>,
    saved_scalars: SmallVec<[f64; 4]>,
    saved_shapes:  SmallVec<[Shape; 4]>,
}
impl Ctx {
    pub fn save_for_backward(&mut self, t: &Tensor);
    pub fn save_shape(&mut self, s: &Shape);
    pub fn saved_tensors(&self) -> &[Tensor];
    pub fn saved_shapes(&self) -> &[Shape];
}

Ownership: a Function is stateless and shared (Arc<dyn Function>) across every call site; a Ctx is per-call and owned by the Node that records it (§8.4). Mutation: Ctx is write-once during forward, read-only during backward. Persistence: never persisted; scoped to one tape lifetime (§8.5).

11.6 Node, NodeRef, Tape

pub struct Node {
    pub fn_obj:    Arc<dyn Function>,
    pub ctx:       Ctx,
    pub inputs:    SmallVec<[NodeRef; 4]>,   // Weak parents, I2
    pub output_id: TensorId,
}
pub struct NodeRef(pub Weak<Node>);

pub struct Tape {
    nodes:        Vec<Arc<Node>>,             // sole strong owner, I2
    by_output:    HashMap<TensorId, Weak<Node>>,
    grad_enabled: Cell<bool>,
}
impl Tape {
    pub fn current() -> RefMut<'static, Tape>;   // thread-local, I10
    pub fn record(&mut self, f: Arc<dyn Function>, ctx: Ctx,

    pub fn grad_enabled(&self) -> bool;
}
pub struct NoGradGuard { prev: bool }
impl NoGradGuard { pub fn new() -> Self; }       // RAII, restores on Drop

Ownership: exactly one Tape per thread (thread_local!, I10); Vec<Arc<Node>> is the only strong-reference holder in the whole system (P3). Mutation: append-only during Recording (§8.5); cleared wholesale by fresh(). Concurrency: !Send, !Sync by construction — cross-thread autograd is a compile error (I10).

11.7 Module, Parameter, Optimizer

pub struct Parameter { pub tensor: Tensor, pub name: String }

}

Ownership: a Module tree owns its Parameters; Optimizer borrows them mutably per step (§18-19). Persistence: state_dict() is the full serialization surface (ADR-13, §27); no other path writes model state to disk.

16. Phase 4 — The Matmul Kernel

16.1 Objectives

Ship a hand-written, cache-blocked, SIMD, multi-threaded f32 matmul kernel on CPU — the single op every later phase (conv2d via im2col, attention, linear layers) is built on top of (ADR-14, ADR-15).

  • Implement Goto's blocked algorithm (Golub & Van Loan Ch.1, §5 Books) with block sizes KC=256, MC=256, NC=4096 tuned to L2/L3 cache residency (Hennessy & Patterson Ch.2-3, §5).

  • Parallelize over the M dimension via rayon::par_chunks_mut (ADR-10, P9 — the backend, not the autograd, changes across thread counts).
  • Implement MatmulFn::backward as the standard VJP pair: grad_a = grad_out @ b.transpose(-1,-2), grad_b = a.transpose(-1,-2) @ grad_out (P4 — transpose is free; the backward pays only the matmul cost, not a copy).

  • gradcheck on a (32,64)@(64,16) random matmul passes at 1e-3 (f32, M6).
  • Backward wall-clock ≤ 2.2x forward wall-clock on the same shape (M3, §4).

16.6 Pitfalls

  • The microkernel is where a stray cache miss costs 30% of peak throughput — pack_a/ pack_b must lay data out in exactly the order the microkernel reads it (SIMD-aligned, contiguous); a misaligned pack compiles, runs, and silently loses register cycles to L1 conflicts (M1 regression, caught only by the throughput fixture, §16.5).
  • Dimensions not a multiple of the microkernel's MR/NR (6/16) require an edge-case scalar fallback for the remainder tile — omitting it either panics or silently truncates output (§16.5 misaligned_pack fixture).

16.7 Performance Concerns

This phase's entire purpose is performance (§4 M1-M3): cache blocking (Hennessy & Patterson Ch.2-3), SIMD register blocking, and rayon thread partitioning are all tuned here. Tail latency: the last rayon chunk (uneven M division) must not straggle — chunk sizes are computed to balance within one microkernel tile.

16.8 Edge Cases

  • K=1 (outer product) — degenerates the blocking scheme; must not divide by zero in block-count computation.
  • Extremely tall-skinny (M=100000, K=4, N=4) — poor arithmetic intensity; falls back to the scalar path rather than paying blocking overhead for no cache benefit.
  • NaN/Inf in either operand — propagates per IEEE 754 (§5 RFCs) through the kernel; the op does not guard this (matmul has no restricted domain, unlike pow/log in §15.6) but the surrounding network-level NaN-scan (§26) still catches it.

16.9 Failure Analysis

A silently wrong matmul (e.g. a packing bug that corrupts only non-multiple-of-16 tiles) is the highest-severity bug this phase can introduce — it is invisible on square power-of-two benchmark shapes and only surfaces on real model shapes. Detection: matmul/misaligned_pack.rs (§16.5) specifically exercises non-aligned dimensions; containment: every new kernel change re-runs the full matmul/ conformance bucket, not just the benchmark.

benchmarks/matmul_throughput.rs results are tracked in benchmarks/results/ and gated in bench.yml (§10) — a regression below M1/M2 fails CI, per P12's "a phase that lifts wall-clock is investigated before merge."

  • Implement conv2d via im2col + the Phase-4 matmul kernel (ADR-14, §16): rearrange input to (N*H_out*W_out, C_in*K_h*K_w), weight to (C_in*K_h*K_w, C_out), matmul, reshape. Backward is im2col's transpose (col2im) applied to matmul's standard VJP pair (§16.2).
  • Implement pooling (max_pool2d/avg_pool2d) with backward scattering the gradient to the argmax location (max) or evenly across the window (avg).
  • Implement layer_norm per Goodfellow (§5 Books, adjacent citation) with the numerically stable two-pass (mean, then variance) formulation; backward derives from the standard layer-norm VJP (three terms: scale, shift, variance-correction).
  • Implement softmax with the max-subtraction numerical-stability trick (I9 domain safety — prevents exp overflow); backward is the Jacobian-vector product s * (grad_out - (grad_out . s)) per row.
  • Implement scaled_dot_product_attention composed from existing differentiable primitives (matmul, softmax, div by sqrt(d_k)) — no new Function needed; this validates P10 (a small principled kernel set composes into higher-level ops without bespoke backward code).

17.3 Deliverable

A tiny transformer block (attention + layer_norm + a 2-layer MLP) runs forward and backward end-to-end against the examples/tiny-transformer fixture.

17.4 Acceptance Criteria

  • conv2d gradcheck passes at 1e-3 (f32) for a 3x3 kernel, stride 1, padding 1, on a (2,3,8,8) input (M6, §4).
  • softmax backward matches the analytic Jacobian-vector product within 1e-4 on a (4,10) logits fixture.
  • scaled_dot_product_attention end-to-end gradcheck passes at 1e-3 on a (2,4,8,16) (batch, heads, seq, d_k) fixture.
  • CIFAR-10 CNN example (examples/cnn-cifar10) trains one epoch without diverging (loss strictly decreasing after epoch 1, tracked but not gated at this phase — gating is Phase 8's job, §20).

17.6 Pitfalls

  • softmax without the max-subtraction trick overflows exp on large logits — a silent inf/NaN that I9's domain guard must catch at forward time, not let reach backward.
  • col2im (conv2d's backward scatter) is the most error-prone routine in this phase — overlapping receptive fields (stride < kernel size) must accumulate, not overwrite, into overlapping input positions (mirrors I6's accumulation invariant at the kernel-window level, not just the graph level).
  • Composing attention from primitives (§17.2) is correct but naive: it re-materializes the full (seq, seq) attention-score tensor rather than fusing softmax+matmul — the memory cost is flagged here and addressed by kernel fusion in Phase 11 (§23, PhaseDeferred("§38") for flash-attention-style fusion specifically).

17.7 Performance Concerns

im2col materializes a (N*H_out*W_out, C_in*K_h*K_w) buffer — for large spatial inputs this can dominate memory bandwidth over the matmul itself; the buffer is reused across the batch dimension where possible to amortize allocation.

17.8 Edge Cases

  • conv2d with padding larger than the kernel — must not produce out-of-bounds im2col indices; padding is applied as a logical zero-read, not a materialized padded copy.
  • softmax over an axis of size 1 — degenerates to the identity (output = 1.0 everywhere); backward must return exactly 0 (the Jacobian of a size-1 softmax is zero), not a numerically-near-zero value that fails a tight gradcheck.
  • max_pool2d with an all-equal window (tie) — convention (first index) must match the reference PyTorch fixture used by pytorch_compat.rs (§10).

17.9 Failure Analysis

A col2im accumulation bug (overwrite instead of add on overlapping windows) produces a conv2d gradient that is wrong only when stride < kernel size — invisible on stride-equals-kernel fixtures. Detection: conv2d_gradcheck_3x3 specifically uses stride 1 with a 3x3 kernel (heavy overlap) to force the bug to surface; containment: every conv2d shape variant in the CIFAR-10 example is gradchecked, not just the unit fixture.

17.10 Operational Notes

The examples/tiny-transformer and examples/cnn-cifar10 binaries both emit per-layer OTLP spans (ADR-16) tagged with the op name, feeding the same agctl inspect-tape tooling introduced in Phase 2 (§14.10) — no new observability surface, deliberate reuse per P14.

18. Phase 6 — Optimizers: SGD, Adam, AdamW, Schedulers

18.1 Objectives

Ship the Optimizer trait (§11.7) and three implementations (SGD-with-momentum, Adam, AdamW) plus LR schedulers (cosine, step, warmup) and gradient clipping — the layer that consumes .grad and mutates parameters (Goodfellow Ch.8, §5, applied here).

18.2 Detailed Implementation Steps

  • Implement Optimizer::step/zero_grad (§11.7) with SGD holding a per-parameter momentum buffer, Adam/AdamW holding first/second moment buffers plus a step counter (bias-correction term).
  • Implement AdamW's decoupled weight decay distinctly from Adam's L2-via-gradient approach — a correctness-relevant distinction (ADR pending references the original Loshchilov & Hutter decoupling; not re-derived here, applied per Goodfellow Ch.8 framing, §5).
  • Implement state_dict/load_state_dict (§11.7) serializing every optimizer buffer alongside parameter tensors (I11 — must round-trip through a crash-and-resume fixture, §27).
  • Implement grad_clip_norm/grad_clip_value operating over a &mut [&mut Parameter] slice before step() — guards against the exploding-gradient failure class (FM-4, §26).
  • Implement schedulers (cosine, step, warmup) as pure functions of (base_lr, epoch/step) — no hidden state beyond what state_dict already captures.

18.3 Deliverable

A parameter tensor trained by each of SGD/Adam/AdamW on a synthetic convex quadratic converges to the known minimum within a fixed step budget.

18.4 Acceptance Criteria

  • SGD-momentum on f(x) = (x-3)^2 converges to |x-3| < 1e-3 within 200 steps at lr=0.1, momentum=0.9.
  • Adam on the same problem converges within 100 steps at default betas (0.9, 0.999).
  • state_dict round-trip (save then load) on a 3-step Adam run reproduces bit-identical subsequent updates (I11 crash-resume fixture, §27).
  • grad_clip_norm(max_norm=1.0) on a synthetic exploding-gradient fixture (grad norm 1000x over threshold) bounds the post-clip norm to exactly 1.0 ± 1e-6.

18.6 Pitfalls

  • Confusing Adam's L2-regularization-via-gradient with AdamW's decoupled weight decay is the most common optimizer bug in the field — the two must be separate Function-free arithmetic paths in adam.rs/adamw.rs, not a shared code path with a boolean flag (P14 — one name, one meaning).
  • Forgetting bias-correction on Adam's first few steps produces an artificially small effective learning rate early in training — adam_bias_correction (§18.5) is the trip-wire.
  • zero_grad() that reassigns .grad = None versus one that zeroes in place have different performance and correctness implications under gradient accumulation (P7) — this design uses None-reassignment (matches PyTorch's modern default) and documents the divergence from the older in-place-zero convention.

18.7 Performance Concerns

Optimizer state (momentum/moment buffers) doubles or triples per-parameter memory (Adam: 2x, AdamW: 2x plus decay term) — this is folded into the §4 M5 peak-RSS budget and must be accounted for explicitly in the Back-of-Envelope Capacity Model (§35).

18.8 Edge Cases

  • A parameter with requires_grad=True but grad=None at step() time (never touched by backward) — must be skipped, not treated as a zero-gradient update.
  • grad_clip_norm when the total norm is already under max_norm — must be a no-op (scale factor 1.0), not an accidental renormalization.
  • Loading a state_dict saved by a different optimizer type (Adam state loaded into SGD) — must error (Err(OptimizerMismatch)), never silently reinterpret buffers.

18.9 Failure Analysis

An undetected exploding gradient (no clipping configured) propagates into Adam's second-moment buffer and can permanently distort the effective learning rate for the rest of training — a slow-motion failure that only "recovers" after enough steps dilute the corrupted moment estimate. Detection: a moment-magnitude telemetry gauge (ag_optim_second_moment_max); recovery: restart from the last good checkpoint with clipping enabled (I11, §27).

18.10 Operational Notes

Optimizer step latency and moment-buffer norms are exported as Prometheus metrics (ADR-16) — ag_optim_step_duration_seconds, ag_optim_grad_norm, ag_optim_second_moment_max — feeding the exploding-grad.md runbook (§27).

21. Phase 9 — Higher-Order Gradients and Forward-Mode (JVP)

21.1 Objectives

Extend the engine to support gradients-of-gradients (double backward) and a forward-mode jvp transform, unlocking Hessian-vector products and meta-learning use cases (§1, §2 "What Mastery Looks Like").

21.2 Detailed Implementation Steps

  • Make backward() itself differentiable: run it with Tape::grad_enabled() == true so the VJP computation's own ops (the Function::backward bodies) are traced onto a new tape layer, per P1/P2 — a second backward() call over the gradient tensor then yields the Hessian-vector product.
  • Implement torch.autograd.grad-equivalent: a functional grad(outputs, inputs, create_graph: bool) that does not mutate .grad (contrast with I6's accumulation-into-.grad path, which remains the default for Tensor::backward).
  • Implement a jvp transform (Baydin et al. 2018 §3-4, applied here per P1) as a forward-mode dual-number-style evaluation, kept as a strictly separate code path from the reverse-mode tape (P1 — never run both by default).
  • Add create_graph: bool to backward()'s signature — false (default) frees the tape immediately after the walk (ADR-23); true retains it for a subsequent backward-of-backward call.

21.3 Deliverable

A Hessian-vector product on f(x) = x^T A x matches the analytic 2*A*v for a random symmetric A and vector v, computed via double backward.

21.4 Acceptance Criteria

  • Hessian-vector product gradcheck passes at 1e-3 (f32) against the closed-form 2*A*v on a (16,16) symmetric A (M6-equivalent tolerance, §4).
  • grad(outputs, inputs, create_graph=False) does not mutate inputs[i].grad — a fixture asserts .grad is None before and after the call.
  • Memory: create_graph=False (the default) shows ag_tape_live_nodes == 0 after the call (I2 preserved); create_graph=True retains the tape until an explicit second backward or Tape::fresh().

21.5 Conformance Fixtures

Fixture Purpose Expected Output
autograd/hessian_vector_product.rs double-backward correctness matches 2*A*v, <1e-3
autograd/functional_grad_no_mutation.rs .grad untouched by functional API .grad is None pre/post
autograd/create_graph_retention.rs tape lifetime under create_graph=True tape freed only after 2nd backward
autograd/jvp_matches_vjp_dot.rs forward/reverse-mode cross-check jvp(f,x,v) . w == vjp(f,x,w) . v

21.6 Pitfalls

  • Running backward() with grad-tracking disabled by default (a natural optimization) silently breaks double backward the first time a user calls create_graph=True — the default must be an explicit, tested flag, not an accidental side effect of an unrelated performance change.
  • The jvp/vjp duality check (autograd/jvp_matches_vjp_dot, §21.5) is the standard correctness cross-check from the AD literature (Baydin et al. §3, §5) — skipping it means forward-mode and reverse-mode can silently diverge without either individually failing its own gradcheck.
  • A create_graph=True retained tape that is never explicitly freed is a real memory leak vector distinct from the I2 Weak-pointer discipline — this is a correct strong reference the caller must release, and the pitfall is forgetting to document that obligation (§21.10).

21.7 Performance Concerns

Double backward roughly doubles both compute and tape-node allocation (§4 M4) per level of nesting — this phase's acceptance criteria (§21.4) do not gate a new throughput number, but the Back-of-Envelope Capacity Model (§35) accounts for create_graph=True's memory cost explicitly.

21.8 Edge Cases

  • Nested double-backward (Hessian-vector-product-of-a-Hessian-vector-product, third order) — must not infinite-loop or panic; correctness at 3rd order is documented as untested-but-not-forbidden (the fixture suite only asserts 2nd order, §21.5).
  • jvp on an op with no defined forward-mode rule yet (e.g. a brand-new custom Function) — must error Err(NoJvpRule), never silently fall back to a numerically approximated JVP.
  • grad() called with an inputs list containing a tensor not reachable from outputs in the graph — returns None for that input's gradient, not an error (this matches PyTorch's allow_unused semantics and must be documented explicitly).

21.9 Failure Analysis

A double-backward correctness bug is uniquely hard to detect because the first backward (the one used everywhere else in the engine) is unaffected — only a second-order consumer (a meta-learning loop, a Hessian-vector product) trips it. Detection: the dedicated hessian_vector_product and jvp_matches_vjp_dot fixtures (§21.5) are the only trip-wires; recovery is a targeted re-derivation of the specific Function::backward whose own internal ops were not properly traced.

21.10 Operational Notes

create_graph=True retention is logged at WARN via the OTLP span (ADR-16) when a tape survives past the caller's expected scope (heuristic: more than one training step), surfacing the "forgot to free the retained graph" pitfall (§21.6) as an observable signal rather than a silent leak.

22. Phase 10 — Mixed Precision: bf16 Autocast

22.1 Objectives

Ship an opt-in autocast() region (P8, ADR-09) that runs a per-op whitelist in bf16 while keeping numerically sensitive ops (softmax, layer_norm, loss reduction) in f32, targeting a 1.5-2x throughput improvement on bf16-capable CPUs.

22.2 Detailed Implementation Steps

  • Implement autocast() as a scoped guard (mirrors NoGradGuard's RAII pattern, §14.2) that consults a static whitelist/blacklist table per op name when dispatching through current_backend (§11.4).
  • Whitelist: matmul, conv2d, elementwise add/mul on activations. Blacklist: softmax, layer_norm, cross_entropy/loss reductions, and any reduction over a large axis (dynamic-range-sensitive, P8).
  • Implement automatic dtype promotion at whitelist/blacklist boundaries: a bf16 tensor entering a blacklisted op is upcast to f32 before the op and the output stays f32 (matches PyTorch's autocast boundary behavior, cited per Paszke et al. 2019 §5).
  • Backward under autocast: the backward pass replays the same whitelist/blacklist decision recorded in each Node's Ctx (§11.5) at forward time — the dtype decision is not re-derived at backward time, avoiding a forward/backward dtype mismatch.

22.3 Deliverable

The Phase-8 MNIST MLP trains inside an autocast() region and reaches the same <2% test error (M7) at measurably reduced wall-clock on a bf16-capable CI runner.

22.4 Acceptance Criteria

  • MNIST run under autocast() reaches <2% test error (same M7 bound, §4) — autocast must not regress accuracy on this reference workload (P12).
  • Measured wall-clock improvement ≥ 1.3x versus the f32 baseline on a bf16-capable runner (a documented, not over-claimed, lower bound — full 1.5-2x is aspirational and tracked but not gated).
  • A gradcheck fixture on a whitelisted matmul inside autocast() passes at a relaxed tolerance 1e-2 (bf16 precision, distinct from the f32 M6 1e-3) — the relaxed bound is itself a quantified, named threshold, not "roughly right."
  • Blacklisted ops (softmax, layer_norm) inside an autocast() region measurably execute in f32 — verified by a dtype-assertion fixture reading the actual tensor dtype at each op boundary.

22.5 Conformance Fixtures

Fixture Purpose Expected Output
autocast/mnist_accuracy_preserved.rs P12 gate under bf16 <2% test error (M7)
autocast/whitelist_dtype_boundary.rs matmul runs bf16, output promotes correctly dtype matches whitelist table
autocast/blacklist_forced_f32.rs softmax/layernorm stay f32 dtype assertion passes
autocast/backward_dtype_consistency.rs forward/backward dtype decision matches no dtype mismatch panic

22.6 Pitfalls

  • Autocasting an entire network (violating P8) rather than per-op loses training stability specifically on softmax/layer_norm, whose dynamic range bf16 cannot represent — this is the exact mistake P8 exists to prevent, and the blacklist_forced_f32 fixture (§22.5) is the regression guard.
  • Re-deriving the whitelist/blacklist decision at backward time (instead of reading it from the saved Ctx) risks a forward/backward dtype mismatch if the global autocast state changed between forward and backward (e.g. nested autocast regions) — backward_dtype_consistency (§22.5) is the trip-wire.
  • bf16's reduced mantissa (7 bits) makes naive summation over long axes lose precision fast — reductions accumulate in f32 internally even when the input/output tensors are tagged bf16 (a kernel-level, not autograd-level, detail, but load-bearing for accuracy).

22.7 Performance Concerns

The whole point of this phase is throughput (§22.4) — but the dtype-boundary promotion/demotion casts themselves cost bandwidth; the implementation must fuse the cast into the adjacent op's memory pass (mirrors the §15.7 elementwise fusion concern) rather than materializing a separate cast buffer at every whitelist/ blacklist boundary.

22.8 Edge Cases

  • Nested autocast() regions (entering one inside another) — the inner region's whitelist/blacklist decision must not silently override an outer region's explicit per-op override (documented precedence: innermost wins).
  • A user-defined custom Function with no declared autocast policy — defaults to blacklist (f32), the safe default, never an assumed whitelist.
  • autocast() combined with create_graph=True (Phase 9) — the dtype decision saved in Ctx must survive into the second-order backward unchanged.

22.9 Failure Analysis

A silent accuracy regression under autocast (blacklist rule not actually enforced) is this phase's worst failure — it does not crash, it just trains to a worse final accuracy, which is easy to attribute incorrectly to hyperparameters instead of the precision bug. Detection: autocast/mnist_accuracy_preserved is the mandatory regression gate (P12) tied directly to this failure mode; recovery is disabling autocast and re-running to isolate whether the regression is precision-related.

22.10 Operational Notes

agctl train --autocast logs the resolved whitelist/blacklist decision per op at DEBUG (ADR-16), letting an operator confirm which ops actually ran in bf16 for a given run without instrumenting the model code.

23. Phase 11 — JIT: Graph Capture and Kernel Fusion

23.1 Objectives

Add an opt-in graph-capture-and-fusion path (mirrors JAX's jit/Tinygrad's Linearizer, §5) on top of the default eager engine (P2) — capture a traced graph from a callable, fuse adjacent elementwise ops, and re-run the fused graph faster, without changing the default execution model.

23.2 Detailed Implementation Steps

  • Implement graph capture: run the target callable once under a recording Tape (§8.4 machinery, reused unmodified per P14), then freeze the resulting Node sequence into an immutable CapturedGraph keyed by an xxh3 fingerprint of the input shapes/dtypes (ADR-12).
  • Implement a fusion pass over CapturedGraph: adjacent elementwise Functions (e.g. add → relu → mul) collapse into a single fused kernel call, following TVM's scheduling/tiling approach (Chen et al. 2018, §5, applied here) at a small scale — no full polyhedral compiler, just adjacent-elementwise fusion.
  • Implement re-dispatch: a CapturedGraph whose fingerprint matches the current call's input shapes/dtypes skips re-tracing and runs the fused kernel sequence directly; a fingerprint miss falls back to eager re-trace (never a hard error — P2's eager path is always the correctness fallback).
  • Implement gradient checkpointing (ADR-22) as a JIT-time transform: mark a captured subgraph for recompute-on-backward instead of saving its Ctx tensors, trading memory for recompute FLOPs (Griewank & Walther Ch.12, §5, applied directly here). This is the JIT-time flavor ADR-22 locked; the rejected runtime-opt-in flavor remains deferred (Deferred Features Register, §38).

23.3 Deliverable

The Phase-8 MNIST MLP, run under agctl train --jit, produces bit-identical loss curves to the eager path and measurably reduced per-step wall-clock from elementwise fusion.

23.4 Acceptance Criteria

  • JIT'd MNIST run reaches the same <2% test error (M7) with loss values matching the eager path within 1e-5 per step (fusion must not change numerics beyond floating-point reassociation error).
  • Per-step wall-clock improvement ≥ 10% versus eager on the MNIST MLP from elementwise fusion alone (a conservative, named bound distinct from the full matmul-bound M7 budget).
  • A fingerprint cache hit rate ≥ 95% after the first training step (subsequent steps reuse the same captured graph shape) — verified by ag_jit_cache_hit_ratio.
  • Gradient-checkpointed subgraph reduces peak RSS by a measurable, named amount (≥ 20%) on a synthetic deep-MLP fixture, at a documented recompute FLOP cost.

23.6 Pitfalls

  • Dynamic graphs were historically considered hard to batch/compile efficiently (Looks et al. 2017, §5) — this phase's fingerprint-keyed cache sidesteps that by only fusing graphs with identical captured shape/dtype, falling back to eager otherwise, rather than attempting a general dynamic-batching compiler.
  • A fusion bug that reorders floating-point summation can produce results that differ from eager by more than expected floating-point reassociation error — the mnist_bitwise_parity fixture's 1e-5 bound is deliberately tight enough to catch a real fusion bug but loose enough to tolerate legitimate reassociation.
  • Gradient checkpointing (§23.2) recomputes a subgraph's forward during backward — forgetting to re-establish the NoGradGuard state correctly during that recompute can spuriously grow the tape a second time.

23.7 Performance Concerns

Fusion's entire purpose is performance, but the fingerprinting overhead itself (xxh3 over shape+dtype, ADR-12) must stay negligible (≤ 1 microsecond) relative to the op dispatch it gates — a slow fingerprint check would erase the fusion win it is meant to enable.

23.8 Edge Cases

  • A captured graph containing a custom Function with no fusion rule — must pass through unfused (correct but not accelerated), never silently dropped from the graph.
  • A shape that changes between calls in a way that does not affect fusability (e.g. batch dimension only) — an advanced cache could still hit, but this phase's simpler fingerprint (exact shape match) intentionally treats it as a cache miss, documented as a known limitation, not a bug.
  • Checkpointed recompute during a crash mid-backward — must not leave the tape in the Draining state (§8.5) indefinitely; the crash-resume fixture (§20.5, I11) is extended to cover this JIT path.

23.9 Failure Analysis

A fusion correctness bug is the highest-severity failure this phase can introduce — by construction it can silently diverge from the eager baseline's already-verified correctness (Phases 0-9). Detection: mnist_bitwise_parity is the mandatory regression gate; containment: agctl train always supports --no-jit as an eager-path escape hatch (P2's fallback guarantee), letting an operator immediately rule out fusion as the cause of a training anomaly.

23.10 Operational Notes

agctl inspect-tape --jit visualizes the captured, fused graph distinctly from the eager per-step trace, and ag_jit_cache_hit_ratio/ag_jit_fusion_savings_seconds (ADR-16) feed the Performance Engineering targets table (§31, M9).

24. Phase 12 — GPU Backends (CUDA/Metal) and Distributed Data-Parallel

24.1 Objectives

Add CudaBackend/MetalBackend implementations of the Backend trait (§11.4, P9) behind cuda/metal cargo features, plus a ring-all-reduce distributed-data-parallel hook (ADR-21) — the final phase, closing out the full system scope from §1.

24.2 Detailed Implementation Steps

  • Implement CudaBackend via raw cuda-sys-style FFI (ADR-19) — hand-written CUDA kernels per op family (elementwise, matmul, conv2d), called through FFI, never a vendored cudarc/candle dependency (mirrors ADR-15's rationale for owning the kernel layer).
  • Implement MetalBackend via metal-rs FFI (ADR-20) with hand-written Metal Shading Language kernels for the same op families.
  • Implement Tensor::to(device) as the sole inter-device transfer op — any op call with mismatched-device operands errors Err(DeviceMismatch) rather than silently moving data (P9 — explicit device moves only).
  • Implement the ring-all-reduce hook (ADR-21) over tokio::net::TcpStream for the default path, with an nccl feature shelling out to NCCL for the GPU ring-all-reduce case: each process holds a full model replica, computes local gradients (unmodified Phase 2-9 autograd), and all-reduces before each optimizer step (§18).
  • Wire agctl train --device cuda:0 / --devices 0,1,2,3 (multi-process launch) into the CLI, reusing the Phase-8 training loop (§20.2) unmodified apart from the device tag and the all-reduce call inserted between backward() and step().

24.3 Deliverable

The Phase-8 MNIST MLP trains on a single GPU (CUDA or Metal, whichever is available in CI) reaching the same <2% test error (M7), and a 2-process CPU ring-all-reduce run reaches the same accuracy as the single-process baseline.

24.4 Acceptance Criteria

  • GPU MNIST run reaches <2% test error (M7) with wall-clock strictly less than the CPU baseline (a directional, not absolute, GPU-specific bound — absolute GPU throughput targets are hardware-dependent and out of this blueprint's quantified scope, §4).
  • Tensor::to(Device::Cuda(0)) followed by an op against a Device::Cpu tensor returns Err(DeviceMismatch), never a silent host-to-device copy.
  • 2-process ring-all-reduce MNIST run (each process holding half the batch) reaches test error within 0.2 percentage points of the single-process M7 baseline.
  • All-reduce round-trip latency for a (256,784)-sized gradient tensor over localhost TcpStream is ≤ 5 ms per step (a named, quantified bound for the default non-NCCL path).

24.6 Pitfalls

  • Hand-writing CUDA/Metal kernels (ADR-19/20) re-derives correctness per backend — the autograd layer above Backend (§11.4, P9) must not need any backend-specific branch; any such branch is a design regression and a review-blocking defect.
  • A ring-all-reduce implemented without a documented failure mode for a dropped peer mid-reduce will hang the entire distributed run — the Failure Modes register (§26, FM-9) names this explicitly and requires a timeout-and-abort path.
  • GPU memory is a separate budget from the §4 M5 CPU RSS bound — a naive port of the CPU allocator's assumptions (e.g. assuming Storage::alloc never fails) breaks the first time a GPU OOMs, which must surface as Err(DeviceOom), not a driver-level abort.

24.7 Performance Concerns

Host-to-device transfer (Tensor::to) bandwidth is a first-class cost this phase introduces that no earlier phase had — every to(device) call in a hot loop (e.g. per-step data movement) must be flagged in code review; the dataloader (§20.2) is extended to prefetch directly to device memory where the backend supports it.

24.8 Edge Cases

  • A multi-GPU machine where only one GPU is requested (cuda:0 of 4 available) — must not implicitly touch the other GPUs' memory or context.
  • A ring-all-reduce with an odd number of processes — the ring topology must handle non-power-of-two process counts without a partial/hanging reduce.
  • Mixed CPU/GPU distributed run (one process on CPU, one on GPU) — explicitly out of scope (documented, not silently broken): the ring-all-reduce assumes homogeneous devices across processes.

24.9 Failure Analysis

A hung ring-all-reduce (a peer crashes or is unreachable mid-reduce, §24.6 FM-9) is this phase's highest-severity failure — with no timeout, the entire distributed job stalls indefinitely with no forward progress and no error surfaced. Detection: a per-round timeout (default 30s, configurable) triggers Err(PeerUnreachable{rank}); recovery is a documented manual restart of the whole job from the last synchronized checkpoint (I11) — this phase does not implement elastic/fault-tolerant re-partitioning (PhaseDeferred("§38")).

24.10 Operational Notes

agctl train --devices ... logs per-process rank, device, and all-reduce round latency as OTLP spans (ADR-16); ag_dist_allreduce_latency_seconds and ag_dist_peer_timeouts_total are the two metrics that gate the distributed-run runbook introduced in Operational Readiness (§27).

27. Operational Readiness

Metrics (Prometheus, ADR-16): ag_tape_live_nodes, ag_tape_nodes_recorded_total, ag_inplace_hazard_detected_total, ag_nan_grad_detected_total, ag_gradcheck_coverage_ratio, ag_optim_grad_norm, ag_optim_second_moment_max, ag_jit_cache_hit_ratio, ag_dist_allreduce_latency_seconds, ag_dist_peer_timeouts_total — the full list is the union of every phase's N.10 Operational Notes (§12-§24).

Tracing (OpenTelemetry/OTLP, ADR-16): one span per op (forward/backward), one span per optimizer step, one span per dataloader fetch, one span per distributed all-reduce round. agctl inspect-tape is the primary trace-reading tool, extended per-phase (§14.10, §19.10, §23.10).

Structured logging: JSON-formatted, one line per training step (loss/test-error/wall-clock/RSS), one line per checkpoint write/load, one line per detected hazard (I5/I9 violations) — never free-text.

Dashboards: a training-run dashboard (loss curve, gradient norm, RSS, throughput) and a distributed-run dashboard (per-rank all-reduce latency, timeout counts) built from the metrics above.

Alerting philosophy: alert on rate-of-change anomalies (grad norm spiking 10x step-over-step) rather than absolute thresholds alone, since "normal" gradient magnitude varies by model; page only on FM-classes with no auto-recovery (FM-2, FM-8, FM-9) — the auto-recovering classes (FM-3's CI gate, FM-6's designed error) are logged, not paged.

Incident response: the runbooks under docs/runbooks/ (§10) — nan-loss.md (FM-1), exploding-grad.md (FM-4), memory-leak.md (FM-5), in-place-failure.md (FM-6/I5) — each following the template in templates/runbook.md: symptom → first three diagnostic commands → likely root causes ranked → recovery steps → postmortem trigger.

Backup/restore: every state_dict write (I11) is atomic (temp file + rename); restore is agctl train --resume-from <checkpoint>, verified by the crash_resume_mid_epoch fixture (§20.5).

Deployment topology: a linked library, no server; the only "deployment" concept is the CLI binary and its checkpoint/config files, plus the Phase-12 multi-process distributed launch (§24).

Canary/rollback: a new engine version is canaried by running the full end-to-end/ conformance bucket (§10) against the previous version's recorded fixtures before any release tag (§30); rollback is reverting to the previous crate version pin in Cargo.lock.

28. Compatibility & Versioning

Wire/storage compatibility: the state_dict format (§11.7, ADR-13) carries a version header; a minor-version-compatible loader upgrades old headers in place (e.g. adding a new optional field defaults it); a major-version bump requires an explicit migration path documented in CHANGELOG.md.

Schema evolution: new DType variants (§11.1) are additive-only within a major version; removing a variant is a major-version, breaking change.

API stability: Tensor, Module, Optimizer, Function (§11) are the stable public surface; Backend internals (§11.4) may change within a minor version as long as the trait contract holds.

SemVer policy: breaking changes to any type in §11 or any ADR marked load-bearing (ADR-02, 04, 07, 23, §9) require a major-version bump; new ops (§15-17) are additive, minor-version changes; bug fixes (e.g. a corrected gradient) are patch versions but must be flagged prominently in CHANGELOG.md since they silently change training numerics for existing users.

Rolling-upgrade guarantees: a distributed run (§24) requires all processes on the same minor version — the ring-all-reduce wire format (raw tensor bytes plus a shape header) is not guaranteed stable across even minor versions without an explicit compatibility ADR.

Deprecation policy: a deprecated API (e.g. an old Optimizer config field) emits a WARN-level log for one full minor-version cycle before removal in the next major version.

29. Testing & Verification Strategy

Unit tests: per-crate tests/, one module per file under src/ (§10); cover type-level invariants (I1-I12, §7) in isolation.

Property tests: proptest-based generation of random tensor shapes/strides for the view family (§13) and broadcast-shape resolution (§8.2, I4) — asserting the numpy-matching broadcast rule holds for thousands of generated shape pairs, not just the hand-picked fixtures.

Differential testing: conformance/runner/src/pytorch_compat.rs (§10) replays a recorded corpus of PyTorch forward/backward outputs and diffs against this engine's output at the §4 M6 tolerance — the primary defense against FM-2 (silent wrong gradient).

Fuzzing: fuzz/ targets the MNIST IDX parser (§20.6, T2) and the state_dict deserializer (T1) with cargo-fuzz, gated in security.yml (§10) on a rolling corpus.

Chaos / fault injection: the crash_resume_mid_epoch (§20.5) and ring_allreduce_2proc (§24.5) fixtures inject a simulated process kill / peer unreachability mid-run, asserting I11 and the FM-9 timeout recovery path.

Deterministic replay: agctl inspect-tape --replay <trace> reruns a captured OTLP trace's op sequence bit-for-bit — used to reproduce a reported FM-1/FM-2 bug without needing the original training data.

Soak testing: a 24-hour continuous MNIST-retrain loop (restart on completion) tracked in bench.yml's nightly job, asserting no RSS growth trend (FM-5) across restarts.

Conformance: every phase's N.5 fixtures (§12-§24) roll up into conformance.report.json, gated in CI (conformance.yml, §10) — a merge is blocked if the report shows any regression versus the previous commit's report.

Performance-regression gating: bench.yml (§10) enforces every M-target in §31 on every merge to the default branch (P12); a regression blocks merge, not just warns.

Tie-back to invariants: every row of §7's Invariants table names its enforcing fixture bucket; the debugging methodology described there (a deterministic simulator, one assertion per invariant) is exactly this section's conformance runner.

32. Scalability Analysis

What stays constant: per-op dispatch overhead (§11.4, O(1) trait-object call); view operation cost (§8.1, O(1) metadata update, I3).

What grows, and its Big-O: matmul is O(M*N*K) compute-bound (§16); memory for optimizer state is O(params) linear, with a 2-3x constant factor for Adam/AdamW (§18.7); dataloader prefetch memory is O(prefetch_depth * batch_size) (§4); tape memory is O(ops_per_step) and bounded by the per-step reset (ADR-23, §8.5).

Named bottlenecks in order: (1) matmul throughput (M1/M2, §16) dominates wall-clock for any model beyond a tiny MLP; (2) dataloader decode throughput (§20.2) becomes the bottleneck once matmul is fast enough that compute no longer hides I/O; (3) ring-all-reduce bandwidth (§24, M10) becomes the bottleneck beyond a handful of distributed processes on a single network link; (4) tape-node allocation overhead (M4, §14.7) becomes visible only on models with very many small ops (a a regime the JIT fusion pass, §23, exists to address).

Horizontal scaling: the Phase-12 ring-all-reduce (§24, ADR-21) is the only horizontal-scaling lever in this design; it scales bandwidth-optimally at moderate node counts but degrades relative to a hierarchical/tree reduce at very large (1,000+) node counts (documented in ADR-21's rejected-alternative column, §9).

Vertical scaling: more CPU cores scale matmul (M2, §16) near-linearly up to memory-bandwidth saturation; a single GPU (§24) removes the CPU compute ceiling entirely for matmul/conv-bound workloads.

Sharding/partitioning: the ring-all-reduce's data-parallel model shards the batch, not the model — model parallelism (sharding parameters across devices) is out of scope (§1 Non-Goals) and is the natural next lever beyond this design's practical ceiling.

Coordination overhead: the ring-all-reduce's per-round overhead (M10, §24) is O(rounds) in the ring topology (2*(P-1) rounds for P processes) — the practical ceiling before coordination overhead dominates useful compute is roughly the point where a single training step's compute time approaches the round latency times the round count (formalized in §35's capacity model).

Practical ceiling and levers beyond it: the practical ceiling of this design is a single-node, multi-GPU (or a small handful of ring-connected nodes) training run; the lever beyond it is a fundamentally different architecture (model-parallel sharding, a parameter server, or a compiler-driven partitioner) — the subject of §37's Alternative Architectures.

33. Mental Models & First Principles

  1. MM1 — "A Tensor is a view; the Storage is the truth." Predicts: any two tensors sharing a Storage see each other's in-place writes. Bug class without it: assuming y = x.transpose(...) gives an independent copy, then being surprised when mutating x changes y too. Applied at §8.1, §11.2-11.3.

  2. MM2 — "Reverse-mode AD is backwards-CPS." The chain-rule walk (§8.3) is structurally a continuation-passing reformulation of the forward computation run backwards (Wang et al. 2018, §5). Predicts: every forward op must have a corresponding "what do I do with the gradient once it arrives" backward continuation — there is no way to differentiate an op whose effect cannot be inverted into a VJP. Bug class without it: writing a Function::backward that tries to recompute the forward instead of directly computing the VJP. Applied at §8.3, §14.2.

  3. MM3 — "The tape is a stack frame that outlives the call." Every op's Node is exactly the reified stack frame of "what was called, with what, producing what" — persisted past the forward call's return so backward can walk it later. Predicts: anything not saved into Ctx at forward time is unavailable at backward time; there is no "going back" to recompute from scratch (absent Phase 11's explicit checkpointing). Bug class without it: writing a backward that assumes access to an intermediate value never saved via save_for_backward. Applied at §8.4, §11.5.

  4. MM4 — "Eager is a debugger; traced is a compiler." JAX's purely functional tracing (§5 ref-impls) versus this design's eager, mutating tape are two different answers to the same question: eager cannot see the whole graph before running it (great for debugging, bad for whole-program optimization); traced can (bad for debugging, great for optimization). Predicts: any optimization requiring whole-graph knowledge (operator fusion, memory planning) needs Phase 11's opt-in capture step — it cannot be bolted onto the eager path directly. Bug class without it: expecting eager execution to somehow "know" about future ops for an optimization. Applied at §3, §23.

  5. MM5 — "Gradients are sums over paths." Reverse-mode accumulation (I6, §8.3) is exactly the statement that a variable's total gradient is the sum of its contribution along every path through the DAG to the output — the same principle underlying Feynman path-sum intuitions in physics. Predicts: any variable reachable via multiple paths must be summed, never overwritten, at backward time. Bug class without it: the +=-vs-= bug (§12.6, §14.6) — the single most common new-author AD mistake. Applied at §7 (I6), §8.3.

  6. MM6 — "Broadcasting is implicit summation's inverse." If the forward broadcasts (implicitly repeats) a value across an axis, the backward must sum across that same axis (§8.2's unbroadcast) — broadcast and reduce are dual operations under differentiation. Predicts: any new broadcasting op's backward is incomplete until it calls unbroadcast on every input whose shape was broadcast. Bug class without it: a gradient that is correct in magnitude but wrong in shape, causing a downstream shape-mismatch panic rather than an obviously wrong number. Applied at §8.2, §15.2.

  7. MM7 — "A kernel-fusion compiler is a scheduling problem, not a rewriting problem." TVM's insight (Chen et al. 2018, §5): the hard part of fusing ops is not deciding which ops can combine (that's a local pattern match) but how to schedule the fused loop nest for the target's cache hierarchy. Predicts: Phase 11's fusion pass (§23) will hit diminishing returns quickly without also addressing loop-level scheduling, which is exactly why this design scopes it to adjacent-elementwise fusion only, not general loop fusion. Applied at §23.2, §23.7.

  8. MM8 — "A version counter turns aliasing bugs into detected errors, not undefined behavior." The per-Storage atomic version (I5, §8.4) does not prevent aliasing — Rust's own borrow checker cannot statically prevent the UnsafeCell-based sharing this design requires (§11.2) — it instead converts a would-be silent-corruption bug into a loud, attributable error at the moment backward tries to use a stale value. Predicts: any future op or backend that bypasses bump_version on a mutating write reintroduces exactly the failure class (FM-2) this design otherwise eliminates. Applied at §7 (I5), §11.2, §26 (FM-2).

PyTorch made the opposite bet from JAX on mutation and imperative style, and it is the closest sibling to this design — the difference that matters most is scale: PyTorch's engine.cpp runs a multi-threaded ready-queue backward across a CPU/GPU-heterogeneous graph; this design deliberately stays single-threaded per tape (I10) for simplicity, at the cost of a scaling ceiling this blueprint documents explicitly (§32) rather than hides.

JAX wins wherever a program can be made purely functional and re-traced per-shape: its jit+XLA path gets whole-program compiler optimization this design only approximates with adjacent-elementwise fusion (§23, MM7). The niche it wins is research code that re-runs the same shape thousands of times (RL environments, scientific computing) where re-tracing cost amortizes to near-zero.

TensorFlow 1.x wins wherever the graph shape truly never changes and the deployment target has zero tolerance for per-step interpretation overhead (embedded inference, TPU pods with a fixed compiled program) — the static-graph bet this design explicitly rejected (ADR-02) for the sake of debuggability (§2).

Tinygrad wins as a minimal, hackable reference where the entire system must fit in one engineer's head across the full stack (tensor to codegen) — its lazy-by-default scheduling is a more aggressive bet on fusion than this design makes by default (ADR-05 locks eager-by-default here), trading debuggability for baseline throughput.

35. Back-of-Envelope Capacity Model

Every number below is derived from §4's System Constraints table, formula shown.

  1. MNIST batch memory: batch=256 * 28*28 px * 4 bytes (f32) = 256*784*4 = 802,816 bytes ≈ 784 KiB per input batch (feeds M5's 512 MiB budget, §4).
  2. 3-layer MLP parameter count: 784*256 + 256*256 + 256*10 ≈ 200,704 + 65,536 + 2,560 = 268,800 params; at f32, 268,800 * 4 ≈ 1.05 MiB of weights.
  3. Adam optimizer memory overhead: 2 extra buffers (first/second moment) per parameter (§18.7) → 268,800 * 4 bytes * 2 = 2.1 MiB — roughly 2x the raw parameter memory, well inside M5's 512 MiB.
  4. Matmul FLOPs for one MNIST forward step: 2 * batch * in * out per layer (multiply-add counted as 2 FLOPs) → layer 1: 2*256*784*256 ≈ 102.8M FLOPs; total forward ≈ 2*(102.8M + 33.6M + 1.3M) ≈ 275M FLOPs; backward ≈ 2x forward (M3, §4) → total per step ≈ 825M FLOPs.
  5. Steps-per-epoch and epoch wall-clock: MNIST train set 60,000 images / batch 256 ≈ 234 steps/epoch; at M1's 8 GFLOP/s floor, 825M FLOPs / 8e9 FLOP/s ≈ 103 microseconds compute-bound per step — far under the M7 10-minute/234-step budget, confirming the bottleneck is dataloader/overhead, not raw matmul FLOPs at this tiny scale (validates §32's bottleneck ordering).
  6. Dataloader prefetch memory: prefetch_depth (2-4) * batch bytes (784 KiB) ≈ 1.5-3.1 MiB (§4), negligible against M5's 512 MiB ceiling.
  7. Tape memory for one MNIST step: roughly one Node per op call; a 3-layer MLP forward is ≈10 ops (3 matmul + 3 add + 2 relu + loss + softmax); at M4's 200 ns/op allocation budget and a rough 200-byte Node footprint, tape memory per step ≈ 10 * 200 bytes = 2 KiB — confirms the tape itself is never the RSS bottleneck at this scale (ADR-23's per-step reset matters far more at deeper/wider models).
  8. Ring-all-reduce bandwidth for the gradient tensor: (256,784)-shaped gradient at f32 (the largest single-layer gradient in the MNIST MLP) = 256*784*4 ≈ 802,816 bytes ≈ 784 KiB; at M10's 5 ms round-latency budget, minimum required bandwidth ≈ 784 KiB / 5 ms ≈ 157 MiB/s — comfortably inside localhost loopback bandwidth (typically several GiB/s), confirming the M10 target is dominated by round-trip latency, not payload bandwidth, at this tensor size.
  9. GPU host-to-device transfer cost (Phase 12): one MNIST batch (784 KiB, item 1) over a PCIe Gen4 link (~16 GB/s practical) ≈ 784 KiB / 16 GB/s ≈ 49 microseconds per batch — negligible next to the 103-microsecond compute estimate (item 5), confirming host-to-device transfer is not the GPU-path bottleneck at MNIST scale.
  10. Peak RSS budget reconciliation: parameters (1.05 MiB) + Adam state (2.1 MiB) + prefetch buffers (≤3.1 MiB) + tape (≤1 MiB even generously) + runtime/allocator overhead ≈ 10-20 MiB realistic floor for the MNIST reference run — the M5 512 MiB ceiling therefore has roughly 25-50x headroom at this model size, headroom consumed by larger models (the CIFAR CNN, the tiny transformer, §17) as the system scales beyond the Phase-8 reference workload.

  19. Why does this design fuse only adjacent elementwise ops in its JIT (§23.2) rather than attempting the general loop-fusion TVM performs, and what mental model explains why that scope limitation is deliberate, not a shortcut? (§33 MM7, §23.6)
  20. If this engine's tape discipline (§8.4) were ported to a language with a tracing garbage collector (e.g. the language HIPS Autograd is written in), which parts of the Weak/Arc design would become unnecessary, and which invariants would still need explicit enforcement? (§5 ref-impls, §33 MM8)

37. Alternative Architectures (Roads Not Taken)

Alt-1 — Static graph, build-then-run (the TensorFlow 1.x shape).

   define graph (no execution)         session.run(graph, feed_dict)
   +-----------------------+            +------------------------+
   | placeholder -> op ->  |  compile   | partitioned, optimized |
   | op -> op -> output    | ---------> | executable graph runs  |
   +-----------------------+            +------------------------+

Regime where it wins: a fixed, unchanging graph shape deployed to a target with zero tolerance for per-step interpretation overhead (embedded inference, TPU pods running the same compiled program billions of times). Real system: TensorFlow 1.x (Abadi et al. 2016, §5). Rejected here (ADR-02) because it breaks the imperative debugging story (§2) that motivates this entire project — a stack trace through a graph executor is not the stack trace the user wrote.

Alt-2 — Fully functional, traced-and-compiled (the JAX shape).

   pure fn(params, x) -> loss     jax.grad traces once per shape
   +------------------------+      +--------------------------+
   | no mutation; every op  | ---> | XLA-compiled executable,  |
   | is a pure transform    |      | re-run for matching shapes|
   +------------------------+      +--------------------------+

Regime where it wins: research code that re-executes the same shape thousands of times (RL loops, scientific computing sweeps) where whole-program compilation amortizes and purity simplifies reasoning about parallelism. Real system: JAX (Bradbury et al. 2018, §5). Rejected here (ADR-08) because .grad-mutation and in-place ops (P6, P7) are load-bearing for this design's PyTorch-shaped training-loop ergonomics, and giving them up trades away exactly the imperative debuggability §2 targets.

Alt-3 — Lazy-by-default with aggressive fusion (the Tinygrad shape).

   op call -> LazyBuffer (no compute yet) -> .realize() triggers
   +------------------------+                +---------------------+
   | graph of unexecuted    |  scheduling +   | fused kernel(s)     |
   | lazy ops accumulates   |  codegen        | actually dispatched |
   +------------------------+                +---------------------+

Regime where it wins: a small, hackable framework where kernel fusion is the primary performance lever and the whole stack (tensor to codegen) must fit in one person's head. Real system: Tinygrad (Hotz et al., §5). Rejected as the default here (ADR-05) because lazy-by-default conflates scheduling with autograd (§5 ref-impl pitfall), complicating the Phase 0-2 correctness kernel this design prioritizes first (P13); Phase 11's opt-in JIT (§23) recovers most of the fusion benefit without that coupling.

Alt-4 — Source-to-source compiler-transformation AD (the Enzyme/Zygote shape).

   source fn                    compiler pass rewrites the fn's
   (Rust/LLVM IR/Julia AST)     IR/AST into an adjoint-computing fn
   +----------------------+     +-------------------------------+
   | ordinary program,     | -> | no runtime tape at all; the    |
   | no tape at runtime     |    | derivative IS compiled code   |
   +----------------------+     +-------------------------------+

Regime where it wins: differentiating existing, unmodified numerical code (legacy Fortran/C++/LLVM IR) without any operator-overloading API — Enzyme operates directly on LLVM IR; Zygote operates on Julia's IR via source-to-source transformation. Real systems: Enzyme (LLVM-level AD) and Zygote (Julia). Rejected here because it requires a compiler-pass-level integration far beyond a library's scope (§1 — this is a linked Rust library, not a compiler plugin), and it sacrifices the tape's runtime inspectability (agctl inspect-tape, §14.10) that this design's debugging story (§2) depends on.

39. Glossary

  • Tensor — an N-dimensional strided view over a shared Storage; the engine's primary value type (§11.3).
  • Storage — the flat, reference-counted, version-tracked byte allocation backing one or more Tensor views (§11.2).
  • StridedView — the (shape, strides, offset) triple interpreting a flat Storage as an N-dimensional array (§8.1).
  • Stride — the number of elements to skip in Storage to advance one index along a given axis (§11.1).
  • Contiguous — a tensor whose strides match shape.contiguous_strides(); the only layout view() accepts without a copy (§8.1).
  • DType — the element type tag (F32, I64, Bool, …) of a Storage (§11.1).
  • Device — the backend tag (Cpu, Cuda(idx), Metal(idx)) selecting kernel dispatch (§11.1, §11.4).
  • Tape — the thread-local, push-only record of Nodes forming the current computation graph (§8.4, §11.6).
  • Node — one recorded op invocation on the Tape: its Function, saved Ctx, and parent references (§11.6).
  • Function — the trait implemented by every differentiable op, defining forward and backward (§11.5).
  • Ctx — the per-call context a Function uses to save state at forward time for use at backward time (§11.5).
  • VJP (vector-Jacobian product) — the reverse-mode gradient computation: a gradient vector times the op's Jacobian (§5 Baydin et al.).
  • JVP (Jacobian-vector product) — the forward-mode dual of a VJP, used in Phase 9 (§21).
  • Define-by-run — building the computation graph by executing it, as opposed to a separate build phase (§3, ADR-02).
  • Eager execution — running each op immediately at call time rather than compiling first (P2).
  • Backward pass — the reverse topological walk over the Tape computing gradients (§8.3).
  • Forward pass — the ordinary execution of a computation, producing both the output and (if tracing) a Tape record.
  • Broadcasting — numpy's rule for making mismatched-but-compatible shapes operate elementwise without copying (§8.2, I4).
  • Unbroadcast — the backward-pass operation reducing a broadcast-shaped gradient back to an input's original shape (§8.2).
  • Version counter — the per-Storage atomic counter bumped on every in-place write, used to detect stale-tensor use in backward (§11.2, I5).
  • In-place op — an operation that mutates a tensor's existing Storage rather than allocating a new one (§6 P6).
  • Leaf tensor — a tensor with no grad_fn; either user-created or the origin of the graph (§8.4).
  • requires_grad — the flag marking a tensor as needing gradient tracking (§11.3).
  • grad_fn — a leaf-less tensor's Weak pointer to the Node that produced it (§11.3, I2).
  • Gradient accumulation — summing (not overwriting) gradient contributions from multiple paths into one tensor's .grad (I6, P7).
  • Topological sort — the ordering of Nodes such that every parent is visited before it is needed, used to drive the reverse walk (I8).
  • Weak pointer — a non-owning reference (Weak<Node>) that does not keep its target alive, used to break the tape/tensor reference cycle (§8.4, ADR-04).
  • Gradcheck — the numerical-vs-analytical gradient verification technique using central finite differences (§8.3, P13, M6).
  • Central difference — the (f(x+eps) - f(x-eps)) / (2*eps) numerical derivative approximation used by gradcheck (§4).
  • Adjoint — the reverse-mode AD term (Baydin et al., §5) for a variable's accumulated backward-flowing gradient.
  • Primal — the forward-computed value, as distinct from its adjoint.
  • Jacobian — the matrix of all first partial derivatives of a vector-valued function.
  • Hessian-vector product — a second-order derivative quantity computed via double backward (§21).
  • Gradient checkpointing — trading memory for recomputed FLOPs by not saving an intermediate value for backward, recomputing it instead (§23.2, Griewank & Walther).
  • Autocast — the opt-in, per-op mixed-precision (bf16) execution region (§22).
  • Mixed precision — using a lower-precision dtype for part of a computation to gain throughput while preserving numerical stability where it matters (P8).
  • JIT (just-in-time compilation) — this design's opt-in graph-capture-and-fusion path (§23).
  • Kernel fusion — combining multiple ops into one kernel dispatch to save memory bandwidth (§23.2).
  • im2col — the technique of rearranging convolution input patches into matmul- compatible matrix rows (§17.2, ADR-14).
  • Microkernel — the innermost, register-blocked, SIMD-vectorized loop of the matmul kernel (§16.2).
  • Ring all-reduce — a bandwidth-efficient distributed gradient-aggregation topology where each process only communicates with its ring neighbors (§24.2, ADR-21).
  • Data parallelism — replicating the full model per process and sharding the training batch across processes (§24).
  • Model parallelism — sharding the model's parameters themselves across devices (out of scope, §1, §32).
  • state_dict — the serialized snapshot of a model's and optimizer's persistent state (§11.7, ADR-13).
  • Optimizer — the trait/implementation consuming gradients to update parameters (§11.7, §18).
  • Momentum — an optimizer term accumulating an exponential moving average of past gradients to smooth updates (SGD-momentum, §18).
  • Conformance fixture — a named, checked-in test case with an expected output, gating correctness in CI (§10, P13).
  • ADR (Architecture Decision Record) — a locked design decision with rejected alternatives and rationale (§9).
  • Invariant — a system property enforced and checked throughout the codebase, identified by an I# token (§7).
