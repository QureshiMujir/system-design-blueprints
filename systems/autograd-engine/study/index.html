Hard questions (§36)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why must Tensor.grad_fn be a Weak reference rather than an Arc, and what specifically leaks if it is not? (§8.4, §7 I2)
  2. Trace the exact sequence of Node visits and gradient accumulations for y = x*x + 3*x + 2 at x=4 — where does the += versus = distinction actually matter, and what would the wrong answer be if it were =? (§8.3, §7 I6)
  3. Why does unbroadcast need to handle both "extra leading rank" and "size-1 axis" cases separately, and what numpy shape pair would only exercise one of the two? (§8.2, §15.2)
  4. What does the per-Storage version counter actually prevent, and why can Rust's own type system not prevent it statically given the UnsafeCell sharing this design requires? (§11.2, §7 I5, §33 MM8)
  5. Why is the default tape thread-local rather than global, and what would break under multi-threaded training if it were global? (§7 I10, §8.5)
  6. Derive, from the §4 System Constraints table alone, whether a 10-layer MLP with 4096-wide hidden layers would fit inside the M5 peak-RSS budget — show the arithmetic. (§4, §35)
  7. Why does this design choose eager execution by default (ADR-02) when JAX's traced-functional approach unlocks strictly more compiler optimization? What is the actual cost JAX pays for that? (§33 MM4, §34)
  8. What is the precise failure mode if a custom Function's backward forgets to route through unbroadcast, and why does it manifest as a shape-mismatch panic downstream rather than an obviously wrong gradient at the source? (§8.2, §15.6)
  9. Why does gradient checkpointing (ADR-22) belong at the JIT layer (Phase 11) rather than as a Phase-2 runtime flag, given that the memory savings are identical either way? (§9 ADR-22, §23.2)
  10. Trace how a NaN loss at step 4,217 would be diagnosed using only the tools introduced by Phase 8 — name the specific commands and telemetry consulted, in order. (§20.9, §26 FM-1, §27)
  11. Why were dynamic computation graphs once considered hard to batch/compile efficiently, and how does this design's fingerprint-keyed JIT cache sidestep that problem rather than solving it in general? (§5 Looks et al., §23.6)
  12. Compare the memory/recompute trade of gradient checkpointing (§23.2) against the Adam optimizer's memory overhead (§35 item 3) — under what model size does checkpointing become the dominant lever for fitting inside the M5 budget?
  13. Why does the ring-all-reduce hook (ADR-21) scale worse than a hierarchical reduce at very large node counts, and at what rough node count does that crossover happen given the M10 latency target? (§9 ADR-21, §32)
  14. What is the exact distinction between Adam's and AdamW's weight-decay handling, and why does conflating them under one code path with a boolean flag violate this design's terminology-lock principle? (§18.2, §18.6, §6 P14)
  15. Why is softmax's max-subtraction trick necessary for correctness (not just numerical elegance), and what specific downstream failure (§26) does omitting it cause? (§17.6, §26 FM-1)
  16. Under what circumstances does this design's Err(DeviceMismatch) discipline (P9) trade convenience for safety compared to PyTorch's implicit cross-device-copy behavior, and which real incidents (if any) motivate the stricter choice? (§9 ADR-19/20, §6 P9)
  17. Why does autocast operate per-op rather than per-network (P8), and what specifically would go wrong numerically if softmax ran in bf16 during MNIST training? (§22.2, §22.6)
  18. Derive the steps-per-epoch and expected step count for one MNIST epoch from the dataset size and batch size in §4/§35 — then explain why the M7 10-minute wall-clock bound is dominated by dataloader overhead rather than matmul FLOPs at this scale. (§35 items 4-5, §32)
  19. Why does this design fuse only adjacent elementwise ops in its JIT (§23.2) rather than attempting the general loop-fusion TVM performs, and what mental model explains why that scope limitation is deliberate, not a shortcut? (§33 MM7, §23.6)
  20. If this engine's tape discipline (§8.4) were ported to a language with a tracing garbage collector (e.g. the language HIPS Autograd is written in), which parts of the Weak/Arc design would become unnecessary, and which invariants would still need explicit enforcement? (§5 ref-impls, §33 MM8)

33. Mental Models & First Principles

  1. MM1 — "A Tensor is a view; the Storage is the truth." Predicts: any two tensors sharing a Storage see each other's in-place writes. Bug class without it: assuming y = x.transpose(...) gives an independent copy, then being surprised when mutating x changes y too. Applied at §8.1, §11.2-11.3.

  2. MM2 — "Reverse-mode AD is backwards-CPS." The chain-rule walk (§8.3) is structurally a continuation-passing reformulation of the forward computation run backwards (Wang et al. 2018, §5). Predicts: every forward op must have a corresponding "what do I do with the gradient once it arrives" backward continuation — there is no way to differentiate an op whose effect cannot be inverted into a VJP. Bug class without it: writing a Function::backward that tries to recompute the forward instead of directly computing the VJP. Applied at §8.3, §14.2.

  3. MM3 — "The tape is a stack frame that outlives the call." Every op's Node is exactly the reified stack frame of "what was called, with what, producing what" — persisted past the forward call's return so backward can walk it later. Predicts: anything not saved into Ctx at forward time is unavailable at backward time; there is no "going back" to recompute from scratch (absent Phase 11's explicit checkpointing). Bug class without it: writing a backward that assumes access to an intermediate value never saved via save_for_backward. Applied at §8.4, §11.5.

  4. MM4 — "Eager is a debugger; traced is a compiler." JAX's purely functional tracing (§5 ref-impls) versus this design's eager, mutating tape are two different answers to the same question: eager cannot see the whole graph before running it (great for debugging, bad for whole-program optimization); traced can (bad for debugging, great for optimization). Predicts: any optimization requiring whole-graph knowledge (operator fusion, memory planning) needs Phase 11's opt-in capture step — it cannot be bolted onto the eager path directly. Bug class without it: expecting eager execution to somehow "know" about future ops for an optimization. Applied at §3, §23.

  5. MM5 — "Gradients are sums over paths." Reverse-mode accumulation (I6, §8.3) is exactly the statement that a variable's total gradient is the sum of its contribution along every path through the DAG to the output — the same principle underlying Feynman path-sum intuitions in physics. Predicts: any variable reachable via multiple paths must be summed, never overwritten, at backward time. Bug class without it: the +=-vs-= bug (§12.6, §14.6) — the single most common new-author AD mistake. Applied at §7 (I6), §8.3.

  6. MM6 — "Broadcasting is implicit summation's inverse." If the forward broadcasts (implicitly repeats) a value across an axis, the backward must sum across that same axis (§8.2's unbroadcast) — broadcast and reduce are dual operations under differentiation. Predicts: any new broadcasting op's backward is incomplete until it calls unbroadcast on every input whose shape was broadcast. Bug class without it: a gradient that is correct in magnitude but wrong in shape, causing a downstream shape-mismatch panic rather than an obviously wrong number. Applied at §8.2, §15.2.

  7. MM7 — "A kernel-fusion compiler is a scheduling problem, not a rewriting problem." TVM's insight (Chen et al. 2018, §5): the hard part of fusing ops is not deciding which ops can combine (that's a local pattern match) but how to schedule the fused loop nest for the target's cache hierarchy. Predicts: Phase 11's fusion pass (§23) will hit diminishing returns quickly without also addressing loop-level scheduling, which is exactly why this design scopes it to adjacent-elementwise fusion only, not general loop fusion. Applied at §23.2, §23.7.

  8. MM8 — "A version counter turns aliasing bugs into detected errors, not undefined behavior." The per-Storage atomic version (I5, §8.4) does not prevent aliasing — Rust's own borrow checker cannot statically prevent the UnsafeCell-based sharing this design requires (§11.2) — it instead converts a would-be silent-corruption bug into a loud, attributable error at the moment backward tries to use a stale value. Predicts: any future op or backend that bypasses bump_version on a mutating write reintroduces exactly the failure class (FM-2) this design otherwise eliminates. Applied at §7 (I5), §11.2, §26 (FM-2).

5. Required Reading

Read in this order; do not skip the foundational works. Every entry names where its idea is applied in this blueprint.

Books

  • Griewank, A. & Walther, A., 2008. Evaluating Derivatives: Principles and Techniques of Algorithmic Differentiation, 2nd ed., SIAM. Ch. 3-4: the formal chain rule on a DAG — applied in §8 (Domain Model) and Phase 2 (§14). Ch. 12: checkpointing, the memory/recompute trade — applied in Phase 11 (§23) and Alternative Architectures (§37).
  • Goodfellow, I., Bengio, Y., Courville, A., 2016. Deep Learning, MIT Press. Ch. 6.5: back-propagation as a special case of reverse-mode AD — applied in §8.3 (worked backward example). Ch. 8: optimization algorithms — applied in Phase 6 (§18, SGD/Adam/AdamW).
  • Golub, G. & Van Loan, C., 2013. Matrix Computations, 4th ed., Johns Hopkins University Press. Ch. 1 (blocked matrix multiplication) — applied in Phase 4 (§16, the matmul kernel's blocking scheme).
  • Hennessy, J. & Patterson, D., 2019. Computer Architecture: A Quantitative Approach, 6th ed., Morgan Kaufmann. Ch. 2-3 (memory hierarchy, cache blocking) — applied in Phase 4 (§16.7 Performance Concerns) and Performance Engineering (§31).
  • Kleppmann, M., 2017. Designing Data-Intensive Applications, O'Reilly. Ch. 11 (stream processing, backpressure) — applied in Phase 8's dataloader design (§20.2, the bounded-channel prefetch).
  • McKinney, W., 2022. Python for Data Analysis, 3rd ed., O'Reilly. Ch. 4 (numpy broadcasting and strides) — applied in §8.2 (Broadcasting) and Phase 1 (§13).

Papers

  • Wengert, R.E., 1964. "A Simple Automatic Derivative Evaluation Program." Communications of the ACM 7(8). The origin of the tape — applied in §8.4 (Tape and Node) and Phase 2 (§14).
  • Baydin, A.G., Pearlmutter, B.A., Radul, A.A., Siskind, J.M., 2018. "Automatic Differentiation in Machine Learning: A Survey." JMLR 18. §3-4: forward/reverse mode mechanics and the implementation taxonomy — applied throughout §8 and named in the vocabulary (tape, primal, adjoint, VJP, JVP) used everywhere in this document.
  • Maclaurin, D., Duvenaud, D., Adams, R.P., 2015. "Autograd: Effortless Gradients in Numpy." ICML AutoML Workshop. The tape-based operator-overloading pattern — applied directly in Phase 2 (§14, the Function/Tape design) and cited as the HIPS Autograd reference implementation below.
  • Paszke, A., Gross, S., Massa, F. et al., 2019. "PyTorch: An Imperative Style, High-Performance Deep Learning Library." NeurIPS. §3 (design principles), §4 (implementation) — applied in ADR-02 (dynamic graph), ADR-07 (version counter), and the whole Phase 0-8 eager execution model.
  • Bradbury, J., Frostig, R., Hawkins, P. et al., 2018. "JAX: Composable Transformations of Python+NumPy Programs." The functional, traced, JIT-compiled alternative — applied in Phase 11 (§23, JIT capture + fusion) and Alternative Architectures (§37, Alt-2).
  • Abadi, M., Barham, P., Chen, J. et al., 2016. "TensorFlow: A System for Large-Scale Machine Learning." OSDI. §3 (execution model), §4 (common subexpression elimination, partitioning) — applied in Alternative Architectures (§37, Alt-1, the static-graph road not taken).
  • Chen, T., Moreau, T., Jiang, Z. et al., 2018. "TVM: An Automated End-to-End Optimizing Compiler for Deep Learning." OSDI. Scheduling, tiling, loop transformations — applied in Phase 11 (§23.2, the fusion path) and Mental Model MM7 (§33).
  • Looks, M., Herreshoff, M., Hutchins, D., Norvig, P., 2017. "Deep Learning with Dynamic Computation Graphs." ICLR. Why dynamic graphs were once hard to batch efficiently — applied in Phase 11 Pitfalls (§23.6) and Hard Question HQ-11 (§36).
  • Wang, F., Zheng, D., Decker, J. et al., 2018. "Demystifying Differentiable Programming: Shift/Reset the Penultimate Backpropagator." ICFP. Reverse-mode AD as backwards-CPS — applied as the theoretical cross-check for the backward() walk in §8.3 and cited in Mental Model MM2 (§33).

Reference Implementations

  • Karpathy, A. micrograd. github.com/karpathy/micrograd. The entire ~150-line source. Study engine.py's Value class. Lesson: the tape/topo-sort/chain-rule pattern fits in one file — applied verbatim in Phase 0 (§12). Pitfall not to copy: micrograd's scalar-only design does not generalize to broadcasting; do not try to bolt broadcasting onto Value — lift to Tensor cleanly in Phase 1 (§13) instead.
  • Hotz, G. et al. Tinygrad. github.com/tinygrad/tinygrad. Study tinygrad/tensor.py, tinygrad/engine/lazy.py, tinygrad/codegen/kernel.py. Lesson: lazy execution + a fusion pass over a small IR is tractable in ~5,000 lines — applied in Phase 11 (§23). Pitfall not to copy: Tinygrad's LazyBuffer conflates scheduling and autograd; this design keeps them separate (ADR-05).
  • The PyTorch source. github.com/pytorch/pytorch, specifically torch/csrc/autograd/engine.cpp, torch/csrc/autograd/function.h, torch/_C/_TensorBase.pyi. Lesson: the production reverse-mode engine's node/tape structure — applied directly in §11.5-§11.6 (Function/Tape signatures) and ADR-04. Pitfall not to copy: engine.cpp's ready-queue multi-threaded backward is a Phase-11+ extension, not a Phase-2 requirement — building it too early stalls the correctness kernel.
  • The JAX source. github.com/jax-ml/jax, specifically jax/_src/core.py and jax/_src/interpreters/ad.py. Lesson: a purely functional AD engine with no mutable tape — applied as the contrast case in Alternative Architectures (§37, Alt-2) and Mental Model MM4 (§33). Pitfall not to copy: JAX's tracing requires pure functions; this design's Tensor.backward() mutates .grad by design (ADR-08) and that divergence must stay a documented, deliberate choice, not an accident.
  • HIPS Autograd. github.com/HIPS/autograd. Study autograd/tracer.py and autograd/core.py. Lesson: the minimal operator-overloading tape in pure Python, the direct ancestor of Maclaurin et al. (2015) — applied as the conceptual reference for §8.4's Weak-pointer discipline (the Python GC handles cycles automatically; Rust does not, which is exactly why ADR-04 locks Weak parent refs).

RFCs / Specifications

  • The numpy broadcasting specification (numpy.org/doc/stable/user/basics.broadcasting.html). The normative reference for broadcast semantics — applied verbatim in §8.2 and Design Principle P5 (§6).
  • IEEE 754-2019, floating-point arithmetic. Governs NaN propagation, denormals, and rounding — applied in Failure Mode FM-1 (§26, NaN/Inf gradients) and the gradcheck tolerances in §4.

Glossary (§39) · 49 terms · site-wide glossary

Tensor
an N-dimensional strided view over a shared Storage; the engine's primary value type (§11.3).
Storage
the flat, reference-counted, version-tracked byte allocation backing one or more Tensor views (§11.2).
StridedView
the (shape, strides, offset) triple interpreting a flat Storage as an N-dimensional array (§8.1).
Stride
the number of elements to skip in Storage to advance one index along a given axis (§11.1).
Contiguous
a tensor whose strides match shape.contiguous_strides(); the only layout view() accepts without a copy (§8.1).
DType
the element type tag (F32, I64, Bool, …) of a Storage (§11.1).
Device
the backend tag (Cpu, Cuda(idx), Metal(idx)) selecting kernel dispatch (§11.1, §11.4).
Tape
the thread-local, push-only record of Nodes forming the current computation graph (§8.4, §11.6).
Node
one recorded op invocation on the Tape: its Function, saved Ctx, and parent references (§11.6).
Function
the trait implemented by every differentiable op, defining forward and backward (§11.5).
Ctx
the per-call context a Function uses to save state at forward time for use at backward time (§11.5).
VJP (vector-Jacobian product)
the reverse-mode gradient computation: a gradient vector times the op's Jacobian (§5 Baydin et al.).
JVP (Jacobian-vector product)
the forward-mode dual of a VJP, used in Phase 9 (§21).
Define-by-run
building the computation graph by executing it, as opposed to a separate build phase (§3, ADR-02).
Eager execution
running each op immediately at call time rather than compiling first (P2).
Backward pass
the reverse topological walk over the Tape computing gradients (§8.3).
Forward pass
the ordinary execution of a computation, producing both the output and (if tracing) a Tape record.
Broadcasting
numpy's rule for making mismatched-but-compatible shapes operate elementwise without copying (§8.2, I4).
Unbroadcast
the backward-pass operation reducing a broadcast-shaped gradient back to an input's original shape (§8.2).
Version counter
the per-Storage atomic counter bumped on every in-place write, used to detect stale-tensor use in backward (§11.2, I5).
In-place op
an operation that mutates a tensor's existing Storage rather than allocating a new one (§6 P6).
Leaf tensor
a tensor with no grad_fn; either user-created or the origin of the graph (§8.4).
requires_grad
the flag marking a tensor as needing gradient tracking (§11.3).
grad_fn
a leaf-less tensor's Weak pointer to the Node that produced it (§11.3, I2).
Gradient accumulation
summing (not overwriting) gradient contributions from multiple paths into one tensor's .grad (I6, P7).
Topological sort
the ordering of Nodes such that every parent is visited before it is needed, used to drive the reverse walk (I8).
Weak pointer
a non-owning reference (Weak<Node>) that does not keep its target alive, used to break the tape/tensor reference cycle (§8.4, ADR-04).
Gradcheck
the numerical-vs-analytical gradient verification technique using central finite differences (§8.3, P13, M6).
Central difference
the (f(x+eps) - f(x-eps)) / (2*eps) numerical derivative approximation used by gradcheck (§4).
Adjoint
the reverse-mode AD term (Baydin et al., §5) for a variable's accumulated backward-flowing gradient.
Primal
the forward-computed value, as distinct from its adjoint.
Jacobian
the matrix of all first partial derivatives of a vector-valued function.
Hessian-vector product
a second-order derivative quantity computed via double backward (§21).
Gradient checkpointing
trading memory for recomputed FLOPs by not saving an intermediate value for backward, recomputing it instead (§23.2, Griewank & Walther).
Autocast
the opt-in, per-op mixed-precision (bf16) execution region (§22).
Mixed precision
using a lower-precision dtype for part of a computation to gain throughput while preserving numerical stability where it matters (P8).
JIT (just-in-time compilation)
this design's opt-in graph-capture-and-fusion path (§23).
Kernel fusion
combining multiple ops into one kernel dispatch to save memory bandwidth (§23.2).
im2col
the technique of rearranging convolution input patches into matmul- compatible matrix rows (§17.2, ADR-14).
Microkernel
the innermost, register-blocked, SIMD-vectorized loop of the matmul kernel (§16.2).
Ring all-reduce
a bandwidth-efficient distributed gradient-aggregation topology where each process only communicates with its ring neighbors (§24.2, ADR-21).
Data parallelism
replicating the full model per process and sharding the training batch across processes (§24).
Model parallelism
sharding the model's parameters themselves across devices (out of scope, §1, §32).
state_dict
the serialized snapshot of a model's and optimizer's persistent state (§11.7, ADR-13).
Optimizer
the trait/implementation consuming gradients to update parameters (§11.7, §18).
Momentum
an optimizer term accumulating an exponential moving average of past gradients to smooth updates (SGD-momentum, §18).
Conformance fixture
a named, checked-in test case with an expected output, gating correctness in CI (§10, P13).
ADR (Architecture Decision Record)
a locked design decision with rejected alternatives and rationale (§9).
Invariant
a system property enforced and checked throughout the codebase, identified by an I# token (§7).
