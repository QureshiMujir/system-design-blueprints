Each card is one row of the blueprint's decision table: what was locked in, what was rejected, and — the column that matters most — the situation in which the rejected choice is the right one.

Decisions (§9) · 31 ADRs

ADR-01

Implementation language

Chosen

Rust, edition 2021, MSRV 1.78

Rejected

Go (Terraform's own lang); Python; Haskell

When the rejected choice is right

Go: building a provider ecosystem that maximizes contributor volume and accepts nil-pointer discipline (Terraform's own codebase). Python: single-developer automation scripts where iteration speed > correctness guarantees. Haskell: purely functional correctness proofs where type-system expressiveness > ops ecosystem depth.

Why: Wrong plan = prod incident on irreversible infra mutations. Sum types + exhaustive match model config AST, Value lattice (incl. Unknown), Action precisely. Ownership enforces "state = single source of truth, written atomically". Fearless concurrency for the parallel Walker. Go: no sum types, nil-pointer risk on plan hot path, weaker value-lattice typing. Python: zero static guarantees. Haskell: provider FFI/process friction, thin ops ecosystem.

ADR-02

Code organization

Chosen

Cargo workspace, seven members: iac-hcl, iac-eval, iac-graph, iac-state, iac-provider, iac-core, iac-cli

Rejected

One monolithic crate; per-function microcrates

When the rejected choice is right

Monolithic crate: a small prototype or learning project where cross-crate boundary setup overhead dominates; eliminates resolver complexity and isolation friction. Microcrates: when crates are truly independently versioned and distributed (e.g., a public SDK library suite with independent consumers).

Why: Mirrors layered architecture; enforces dep DAG (iac-core depends on 1–5, iac-cli on iac-core only); fuzz/bench targets isolate to one crate; incremental compile. Microcrates → version-churn, no cohesion gain.

ADR-03

Front-end: lexer + parser

Chosen

Hand-written lexer + recursive-descent parser in iac-hcl

Rejected

Parser generators (LALRPOP, pest, nom) — cross-link 63 Parser-Combinator / Generator

When the rejected choice is right

Parser generators (pest/nom): when grammar is medium-sized and error-quality requirements are secondary (e.g., a config DSL where only the happy path matters); generators save weeks of boilerplate and are well-tested against adversarial input if the framework itself is fuzz-hardened.

Why: Need byte-precise Span on every token + node and rich Diagnostic recovery (never panic on bad input, Phase 1). Generators bury span control and emit terse "unexpected token" errors. Hand-roll cost amortized by error-quality requirement.

ADR-04

Configuration surface syntax

Chosen

HCL-like native syntax (blocks, attributes, templates, here-docs, comments)

Rejected

JSON-only config; YAML config

When the rejected choice is right

JSON-only: machine-generated config (CI pipelines, SDK output) where humans never author it — zero parser complexity, universal tooling. YAML: configs where minimal punctuation and anchors/aliases reduce duplication (e.g., Kubernetes manifests where hierarchy depth ≫ expression power).

Why: Native syntax carries ${...} interpolation, for-expressions, dynamic blocks, conditionals ergonomically; matches Terraform/OpenTofu reference. JSON: no comments, poor human ergonomics. YAML: indentation ambiguity, no native expression grammar. (A JSON variant may be added later via the same AST; not in scope now.)

ADR-05

Value/type system

Chosen

cty-like dynamic Value lattice + Type (iac-eval)

Rejected

Static compile-time-typed config; untyped strings (shell-style)

When the rejected choice is right

Static compile-time typing: if the schema is fixed at compile time (e.g., a closed system with no external plugins) — faster diffs, better IDE support. Untyped strings: shell-style configs where every value is a key-value string (simpler model, trivially serializable, suitable for simple infra tools like Ansible inventory).

Why: Config types depend on provider schemas resolved at runtime; dynamic lattice + convert/unify matches reality. Static typing impossible pre-schema-fetch. Untyped strings lose collection/object structure needed for the three-way diff.

ADR-06

Representing not-yet-known values

Chosen

Value::Unknown(Type) — a first-class lattice member

Rejected

Separate boolean computed flag alongside a concrete value

When the rejected choice is right

A side boolean computed flag: when the value system is a simple struct (not a sum type) and propagation tracking is done at a higher layer — e.g., a domain-specific DSL compiler with a separate type-annotation pass where the flag can ride the AST without fighting the type system.

Why: Unknown must propagate through arbitrary expressions (any expr referencing Unknown yields Unknown) and render "(known after apply)". A side flag cannot ride through evaluate/convert. Invariant: Unknown NEVER compares equal to a concrete value.

ADR-07

Numeric representation

Chosen

Decimal (arbitrary-precision, base-10) for Expression::Number / Value::Number

Rejected

IEEE-754 f64; i64/u64 only

When the rejected choice is right

IEEE-754 f64: when numeric values are purely for display/estimation (not plan determinism) and performance dominates — e.g., metric dashboards or simulation engines where exact round-trip isn't a correctness requirement.

Why: Infra values (ports, CIDRs, capacities, costs) demand exact round-trip; f64 corrupts large ints / decimal fractions and breaks plan determinism (byte-identical requirement). Integer-only loses fractional config (e.g. 0.5 cpu).

ADR-08

Sensitivity marking

Chosen

Value::Sensitive(Box<Value>) — a propagating lattice mark

Rejected

An out-of-band set of "sensitive paths"; encryption-at-eval

When the rejected choice is right

Out-of-band path set: when the sensitive concept is coarse-grained and values are immutable strings (env-var systems, simple secret stores). At-eval encryption: when the security model requires that even in-process memory is ciphertext (high-assurance HSM-backed systems where a memory dump must reveal nothing).

Why: Mark must flow through every expression and provider attr (Attribute.sensitive) and redact in plan/log output automatically. Path-set desyncs as values are transformed. Encryption is out of scope (cross-link 270 Secrets Rotation).

ADR-09

Dependency graph representation

Chosen

Graph<N>: Vec<N> nodes + NodeId(u32) + adjacency edges (dependency → dependent)

Rejected

Pointer/Rc<RefCell> node graph; petgraph dependency

When the rejected choice is right

Pointer/Rc<RefCell>: in single-threaded graph algorithms where arena allocation is complex and the graph mutates frequently during construction — e.g., a dynamic DAG scheduler with frequent rewrites during planning. petgraph: when algorithmic breadth matters over auditing — petgraph ships Dijkstra, Floyd-Warshall, Kruskal etc. that a bespoke NodeId graph must reimplement.

Why: NodeId indices are Copy, serializable, cycle-safe, no borrow-checker fight. Generic over payload N (reuse for resource/module/output nodes). Avoid external graph dep to keep the algorithm (Tarjan, reduction) auditable.

ADR-10

Cycle detection

Chosen

Tarjan strongly-connected-components → detect_cycles() -> Result<(), Vec<Vec<NodeId>>>

Rejected

DFS back-edge detection; Kahn-failure heuristic

When the rejected choice is right

DFS back-edge: when only the existence of a cycle matters (not the full membership) and the graph is small — e.g., a dependency resolver that just needs to reject cyclic packages without rendering cycle members to the user.

Why: Tarjan reports all SCCs in one O(V+E) pass; the returned cycle sets feed precise multi-resource cycle Diagnostics. Back-edge DFS finds one cycle only; less actionable.

ADR-11

Edge minimization

Chosen

Transitive reduction (transitive_reduction()) before walk

Rejected

Walk the raw reference graph

When the rejected choice is right

Raw reference graph: when rendering the full explicit reference set is more important than minimizing edges — e.g., audit/compliance tools that need to show every declared dependency, including redundant ones, for human review.

Why: Removes redundant edges so the Walker sees true precedence only → maximizes safe parallelism, clearer graph output. Raw graph over-serializes independent nodes.

ADR-12

Graph walk concurrency

Chosen

Bounded-parallel reverse-topological walk(parallelism, visit), capped at -parallelism (default 10)

Rejected

Unbounded spawn (one task per node); strictly sequential walk

When the rejected choice is right

Unbounded spawn: when each node is ultra-lightweight (in-process, sub-microsecond), making semaphore overhead dominate — e.g., a pure-in-memory graph computation kernel with no I/O. Sequential: when debugging or deterministic replay is the primary concern (e.g., integration-test harnesses that need node execution order to be exactly reproducible).

Why: Unbounded → provider-side rate-limit/exhaustion + nondeterministic load. Sequential → unusably slow at scale. Bounded reverse-topo (deps before dependents on apply, reverse on destroy) + deferred-error aggregation (a node error defers dependents, never panics).

ADR-13

State document format

Chosen

Versioned JSON (State.version: u32, serde)

Rejected

SQLite store; custom binary; Protobuf

When the rejected choice is right

SQLite: when the state needs ad-hoc query capability, supports concurrent read access, or must store very large blobs efficiently — e.g., a build-cache store where tens-of-thousands of keys are queried with filters. Protobuf: when state is machine-consumed only, size matters (wire size, parse speed), and schema evolution is managed via proto field numbers rather than manual migration code.

Why: Human-diffable, mergeable in review, state pull/push trivial, forward-migratable via version + schema upgrade (Phase 5). SQLite/binary opaque to operators and to differential testing vs Terraform.

ADR-14

State durability write

Chosen

Atomic: write temp → fsync → rename, with .backup of prior serial

Rejected

In-place overwrite; append-only log

When the rejected choice is right

Append-only log: when write throughput is the primary constraint and compaction is acceptable — e.g., a high-write event store or WAL where the working set is a stream, not a single document that needs to be atomically replaced.

Why: Crash mid-write must leave old-or-valid state, never a torn file (STATE SAFETY invariant). rename is atomic on POSIX; backup enables manual recovery. In-place risks corruption; log adds compaction complexity.

ADR-15

Concurrency control on state

Chosen

Optimistic: monotonically increasing serial + lineage: Uuid; write requires StateLock

Rejected

Pessimistic global mutex; CAS-only; no locking

When the rejected choice is right

Pessimistic global mutex: when contention is very high (many concurrent writers), the critical section is short, and distributed coordination is not needed — a local in-process cache where a Mutex is cheaper than serialized OCC validation. CAS-only: when there is no centralized lock server and the system is truly distributed (etcd, DynamoDB conditional writes) — CAS without a local lock gives linearizability without a single lock bottleneck.

Why: serial detects stale writes; lineage detects "wrong state file" entirely. Lock (Phase 11: acquire/heartbeat/force-unlock) prevents concurrent apply. State is single-writer per the concurrency boundary.

ADR-16

Backend abstraction

Chosen

StateBackend trait; local backend now, remote a stub

Rejected

Hard-coded local file I/O; ship remote (S3/HTTP) now

When the rejected choice is right

Ship remote now: when the target deployment is always cloud-native from day one (CI/CD service, shared team state) and the cost of retrofitting a remote backend later is higher than the initial complexity — e.g., a SaaS IaC product where the local backend is used in production.

Why: Trait isolates lock/read/write/atomic semantics so remote backends slot in later without touching iac-core. Remote deferred — not in scope; stub proves the seam.

ADR-17

Provider execution model

Chosen

Out-of-process plugin: provider runs as a child process, engine talks via RPC

Rejected

In-process dynamic linking (dlopen/cdylib); in-tree static providers

When the rejected choice is right

In-process dynamic linking (dlopen): when RPC latency dominates and providers are trusted/same-vendor — e.g., an internal IaC engine where all providers are first-party, audited, and crash isolation is not a requirement. Provider crashes simply restart the whole process.

Why: Providers are untrusted, crash-prone, independently versioned/licensed; process isolation contains panics/segfaults and a bad provider can't corrupt engine memory or state. Matches go-plugin model. dlopen → ABI fragility + shared address space.

ADR-18

Provider RPC framing

Chosen

Length-prefixed, protobuf-ish framed messages over child stdio, with a handshake

Rejected

JSON-RPC; raw text; gRPC/HTTP server

When the rejected choice is right

gRPC/HTTP: when the provider ecosystem needs a polyglot, standards-based interface that third parties can implement without understanding a custom framing protocol — e.g., a provider SDK that targets Python, Java, and Go developers who already know gRPC toolchains.

Why: Length-prefix = unambiguous framing for binary Values + large schemas; handshake negotiates protocol version + schema (Phase 6). JSON-RPC bloats/loses binary fidelity. Full gRPC/HTTP server = heavy dep + port management for a local child.

ADR-19

Replace/computed semantics

Chosen

Schema-driven: Attribute.force_new → requires-replace; Attribute.computed → provider-filled Unknown

Rejected

Hard-coded per-resource replace rules; config-author-declared replace

When the rejected choice is right

Author-declared requires-replace: when the provider schema is a static compile-time artifact (single-vendor, no plugin model) and the author has full knowledge of immutable attributes — reduces an RPC round-trip at plan time for small closed ecosystems.

Why: Provider schema is the authority on which attrs force replacement / are computed; engine stays provider-agnostic. Hard-coding leaks provider knowledge into core; author-declared is unsound (author can't know provider internals).

ADR-20

Plan computation

Chosen

Three-way diff: prior state × refreshed reality (read_resource) × desired config → ResourceChange/Action

Rejected

Two-way (config vs state, no refresh); provider-internal diff only

When the rejected choice is right

Two-way (config vs state, no refresh): when provider APIs are expensive to call (high latency, cost-per-call) and drift detection is not a requirement — e.g., an internal service mesh where resources are never mutated out-of-band and refresh adds only cost.

Why: Refresh catches drift; only the three-way comparison yields correct NoOp/Update/Replace/Create/Delete. Two-way misses out-of-band changes. Provider-only diff can't see cross-resource references/Unknowns.

ADR-21

Replace ordering default

Chosen

create_before_destroy: false by default (opt-in per resource)

Rejected

Default create-before-destroy on

When the rejected choice is right

Default create-before-destroy: when resources are stateless (ephemeral compute, auto-scaled instances) and zero-downtime replacement is the universal requirement — the cost of double-billing is acceptable compared to a downtime event.

Why: Default delete-then-create avoids duplicate-name/quota collisions and surprise double-billing; CBD is opt-in where zero-downtime is needed (and changes graph edge direction).

ADR-22

Error model

Chosen

Diagnostic/Diagnostics (severity + summary + detail + Span) returned, not panics

Rejected

panic!/unwind; bare Result<_, String>

When the rejected choice is right

panic!/unwrap: in small single-binary internal scripts where recovery is meaningless (crash = restart), fast iteration outweighs error quality, and the entire input space is trusted. Bare Result<_, String>: in very small internal libraries (< 500 lines) where structured error types add more indirection than value.

Why: Untrusted config + provider responses must never crash the engine (Phase 1: never panics). Spanned diagnostics give source-located, multi-error output; Result<E> (EvalError, BackendError) used at API edges, surfaced as Diagnostic.

ADR-23

Serialization

Chosen

serde (+ serde_json) for State, RPC payloads, config-JSON variant

Rejected

Hand-rolled (de)serializers; bincode-only

When the rejected choice is right

Hand-rolled serializers: when the format is fixed (no evolution), extremely performance-sensitive, and the schema is a closed internal implementation detail with no cross-language consumers. bincode: when state is never human-read, maximum compactness matters, and schema evolution is managed in code rather than by format.

Why: Derive-driven, audited, schema-migration-friendly; one mechanism for State JSON + RPC. Hand-rolled = bug surface on the durability path.

ADR-24

CLI argument parsing

Chosen

clap (derive) for the iac binary subcommands

Rejected

Hand-rolled arg parser; structopt/argh

When the rejected choice is right

Hand-rolled arg parser: for a one-subcommand, few-flag binary where the overhead of clap's derive macro and binary size increase (adds ~150 KB) outweighs the convenience — e.g., a focused single-purpose tool.

Why: Subcommand-rich CLI (init/validate/fmt/plan/apply/destroy/refresh/import/output/graph/state …) needs help/version/validation for free; clap is the ecosystem standard. Hand-roll = reinventing flag parsing.

ADR-25

Observability

Chosen

tracing crate (structured spans/events), sensitive-redacting layer

Rejected

log crate; ad-hoc eprintln!

When the rejected choice is right

log crate: when the project is a library (not a binary) that must remain agnostic to the logging backend — crates.io libraries should not force a subscriber on their consumers; log is the right dependency-free façade. eprintln: for throwaway scripts where structured correlation is not needed.

Why: Spans trace per-resource RPC latency through the parallel Walker; structured fields feed timing/bench. Custom layer enforces Sensitive redaction in logs (ADR-08). log lacks spans; eprintln! unstructured.

ADR-26

Fuzzing

Chosen

cargo-fuzz (libFuzzer); HCL parser fuzz target (Phase 12)

Rejected

AFL standalone; proptest-only for parser

When the rejected choice is right

AFL: when the target platform is Linux-only and AFL's persistent mode / network fuzzing is preferred, or when the organization's security team mandates AFL for compliance. proptest-only: when the input space is highly structured (not raw bytes) and structured-random property tests already find the interesting bugs — e.g., a pure algebraic evaluator where grammar coverage is more valuable than bit-flipping.

Why: Parser must never panic on arbitrary bytes; coverage-guided libFuzzer maximizes path discovery. proptest used for property tests (idempotency, plan-determinism), not raw-byte robustness.

ADR-27

Differential oracle

Chosen

Terraform/OpenTofu as the differential reference for a config/plan corpus (Phase 12)

Rejected

Self-consistency only; CloudFormation change sets

When the rejected choice is right

Self-consistency only: when Terraform's behavior is not the target spec (building a deliberately incompatible IaC tool), or when Terraform cannot be installed in the CI environment (air-gapped, license constraints). CloudFormation change sets: when the deployment target is AWS-only and CloudFormation semantics are the normative reference.

Why: Terraform is the de-facto behavior spec; diffing our plans against it on a shared corpus catches semantic drift. Self-consistency can't catch shared misconceptions. CFN change sets = different model (contrast only).

ADR-28

Benchmarking

Chosen

criterion (statistical, regression-tracking) vs section-4 targets

Rejected

#[bench] (nightly); wall-clock timers

When the rejected choice is right

nightly #[bench]: in very small projects where the nightly overhead is acceptable and the benchmark suite is < 5 tests that need no statistical rigor. ad-hoc timers: in micro-optimization loops during development where rapid iteration matters more than CI-stable regression gating.

Why: Stable-toolchain, statistically rigorous, CI-trackable regressions for parse/eval/graph-build/plan/apply hot paths. #[bench] needs nightly; ad-hoc timers are noisy.

ADR-29

MSRV policy

Chosen

Pin MSRV 1.78; CI matrix builds {MSRV, stable}; bump only with a changelog entry

Rejected

Track latest stable; no MSRV gate

When the rejected choice is right

Track latest stable: for internal developer tools with a homogeneous toolchain where the latest features improve productivity and no one is running an old compiler. No MSRV gate: for application-only repos (not published libraries) deployed via Docker/Nix where the build toolchain is fully controlled.

Why: Operators embed iac in CI on older toolchains; a stable MSRV is a compatibility contract. Verified by a dedicated CI job (Phase 0).

ADR-30

Dependency policy

Chosen

Minimal, vetted deps gated by cargo-deny (licenses + advisories + bans + sources)

Rejected

Liberal dependency use; vendor-everything

When the rejected choice is right

Liberal dependency use: in rapid-prototype or hackathon contexts where productivity dominates and auditability is deferred. Vendor-everything: in air-gapped / regulated environments (military, healthcare, high-security finance) where no outbound network access is permitted during build.

Why: Engine drives irreversible mutations → small audited supply chain. cargo-deny blocks disallowed licenses, RUSTSEC advisories, duplicate/banned crates in CI.

ADR-31

License

Chosen

MPL-2.0

Rejected

MIT/Apache-2.0 dual; GPL-3.0; proprietary

When the rejected choice is right

MIT/Apache dual: when maximizing contributor adoption is the primary goal (permissive license attracts more community forks and integration) — e.g., a foundational SDK library that third parties embed in closed-source products. GPL-3.0: when the goal is to ensure all improvements to the engine itself remain open-source, even at the cost of discouraging proprietary provider ecosystems. Proprietary: when the engine is a competitive moat and open-sourcing would directly enable competing products.

Why: Mirrors Terraform's historical license; file-level copyleft keeps engine improvements open while permitting proprietary providers/config alongside (per-file boundary fits the plugin model). GPL too viral for provider ecosystem; MIT/Apache permits closed forks of the engine itself — rejected to keep the core open.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1 — Continuous reconcile loop (Kubernetes controller model)

    Config in etcd/API server
          │
    Controller watches for changes
          │
     Read current state (list/watch infra API)
          │
     Compute delta (desired minus observed)
          │
     Apply delta (partial, best-effort)
          │
     Write status back to API server
          └── loop forever (level-triggered)

Winning regime: continuously evolving desired state; infra that self-heals and must converge without operator intervention; systems where "an apply that missed 3 resources" is fine because the loop will correct it on the next tick. Kubernetes itself, AWS Controllers for Kubernetes (ACK), and CrossPlane all use this model.

Real system: CrossPlane — applies Kubernetes controller machinery to cloud resources; each provider is a Kubernetes controller, each resource is a CRD.

Why rejected: this engine targets one-shot provisioning where an operator reviews a plan and approves it. A continuous loop cannot provide a "show me exactly what will change before I approve" guarantee. There is no plan artifact that a human or CI gate can inspect. More critically, for irreversible mutations (database deletion, VPC destruction) a level-triggered controller that immediately acts on a desired-state diff is dangerous without the plan/approve barrier. The plan/apply split is the architectural answer to "irreversible + expensive mutations" — the continuous loop trades that safety for convergence speed.

Alt-2 — General-purpose language SDK (Pulumi model)

    TypeScript/Python/Go program
          │ calls SDK resource constructors
          │ (resource("aws:s3:Bucket", name, args))
          v
    Resource graph constructed at runtime (program execution)
          │
    Engine serializes resource registrations → snapshot
          │
    Diff snapshot vs prior → changes
          │
    Apply changes via providers

Winning regime: config that is genuinely Turing-complete — loops over dynamically-fetched data, conditional resource creation based on external API responses, library/module reuse via the host language's package manager. Teams where infrastructure authors are software engineers comfortable with TypeScript/Python, and the overhead of learning HCL-like syntax is higher than the overhead of learning the SDK.

Real system: Pulumi (TypeScript/Python/Go/Java/C#/.NET SDKs).

Why rejected: this engine deliberately takes the declarative position. A config program can read files, make HTTP calls, call arbitrary functions — making it impossible to statically analyze the resource graph before execution. There is no plan without running the program. The declarative constraint (*.iac config has no side effects beyond file reads in templatefile()) enables: (1) a parse-only validate pass, (2) a plan that is byte-deterministic without executing any infra, (3) a diff that is a static analysis of text changes. These properties are the anchor of the audit + review workflow.

Alt-3 — Server-side managed state (CloudFormation model)

    Operator submits template to CloudFormation API
          │
    CloudFormation service stores and manages state server-side
          │
    CloudFormation computes change set (optional preview)
          │
    CloudFormation executes (concurrently, with rollback)
          │
    Operator queries stack events for status

Winning regime: all-AWS deployments where native IAM integration, CloudTrail audit logging of every stack event, automatic rollback on failure, and no operator-managed state files are more valuable than provider-agnosticism or custom state manipulation. Organizations that cannot allow engineers to directly access or modify state files (compliance/SOC2 requirement).

Real system: AWS CloudFormation; Azure Resource Manager (same model for Azure).

Why rejected: (1) provider-agnosticism — this engine orchestrates any provider via the plugin RPC; CloudFormation is AWS-only. (2) state access — CloudFormation hides the state from the operator, making state mv, state rm, and import scenarios require workarounds. (3) rollback model — CloudFormation attempts a full rollback on failure; this engine's partial-state model (taint + re-plan) is more transparent. (4) cross-resource unknowns — CloudFormation's !Ref/!GetAtt function does not propagate an Unknown type through the template; it simply defers the value, with less expressibility than Value::Unknown(Type).

Alt-4 — Embedded scripting engine (Jsonnet/Starlark model)

    *.jsonnet / *.star config files
          │
    Embedded interpreter (pure, deterministic, sandboxed)
    evaluates to a JSON/dict structure
          │
    JSON structure describes resources
          │
    Engine diffs JSON tree vs prior state
          │
    Engine calls providers

Winning regime: configs that need programmability (loops, functions, imports) but must remain deterministic and auditable; templating at scale where HCL-like syntax is too limiting but a full host language SDK (Alt-2) is too opaque. Jsonnet is used by large Kubernetes configuration pipelines (Tanka, qbec); Starlark is used by Bazel build rules.

Real system: Tanka (uses Jsonnet to produce Kubernetes manifests); Dhall (typed functional config language, similar idea).

Why rejected: an embedded scripting language adds a full language runtime as a dependency (interpreter complexity, security surface, evaluation semantics to specify). More importantly, Jsonnet/Starlark evaluate to a static JSON tree — they do not support Unknown(Type) semantics. You cannot express "this value is known after apply" in a Jsonnet evaluation; the Unknown propagation that drives the "(known after apply)" in the plan is a first-class concept in this engine's value lattice, not a post-evaluation annotation. That makes Jsonnet/Starlark unsuitable as a drop-in config front end without losing the Unknown-aware planning model.
