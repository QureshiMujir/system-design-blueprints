4. System Constraints

4.1 Operating Envelope (Phase-0 scope)

  • In-process engine + local files. Single host, single iac process; provider plugins are child processes on the same host.
  • No NUMA / cluster / multi-host assumptions. No shared-memory provider model.
  • Durable artifact = exactly one iac-state State file per workspace + its .backup. No DB, no network state in Phase 0.
  • Remote/HA StateBackend (S3/etcd/consul-style) = deferred; iac-state ships a StateBackend trait + local backend + remote-stub only.
  • Untrusted inputs: *.iac config (operator-authored, may be malformed/hostile) + provider RPC responses (separate process, may misbehave/hang/crash). Trust boundary enforced at iac-hcl parse and iac-provider RPC decode.
  • Concurrency boundary: iac-graph Walker runs provider RPCs in parallel up to -parallelism; State is single-writer (engine), serialized through StateBackend::write.

4.3 Provider RPC Constraints

  • Timeout: default 30 s/call, per-call configurable. Exceed → Diagnostics error, node marked failed, dependents deferred (not panicked).
  • Retry: only on transient RPC classes (connection reset, handshake-not-ready, timeout); bounded (default 3, exponential backoff). Never retry apply_resource that may have partially mutated unless provider declares idempotency — default = no retry on apply, surface and taint.
  • Crash/hang of plugin → isolated to its child process; engine never inherits a torn State from a dead plugin. Kill on Drop / shutdown.

4.4 Determinism Constraints (planning)

  • Zero wall-clock, zero RNG in PLAN. No SystemTime, no rand, no HashMap iteration order in plan output.
  • Map/Object iteration sorted (BTreeMap/BTreeSet in Value) → byte-identical plan given identical {config, variables, prior State, provider responses}.
  • Unknown(Type) never == a concrete Value; comparison is conservative (Unknown ⇒ "(known after apply)").
  • Differential + property gates (Phase 12 ## 24): plan-determinism (re-run = byte-identical) and apply-then-plan idempotency (fresh plan post-apply = all-NoOp).

4.5 Durability & Recovery

  • State safety invariant: a malformed config or misbehaving provider can never corrupt State nor leave a torn file. Write = temp file → fsync → atomic rename, prior serial preserved as .backup.
  • serial monotonic ↑; lineage UUID detects "wrong state file"; every write requires the held StateLock.
  • Crash-consistency: a crash mid-apply leaves either the old State or a partially-advanced-but-valid State (incremental writes commit per-resource), never a partial/torn document.
  • RTO: a crashed apply re-plans cleanly from the last written State; already-applied resources diff to NoOp, in-flight ones re-diff to their pending Action. No manual state surgery on the happy crash path.
  • Sensitive: Sensitive-marked values redacted in plan render + logs; mark propagates through iac-eval expressions; never written to .backup in cleartext beyond the existing State representation.

4.7 Explicit Non-Targets (this phase)

  • No remote/HA backend, no state-locking-as-a-service (deferred; trait shape only).
  • No distributed graph walk across hosts; -parallelism is intra-process thread bound only.
  • No sub-second plan SLA for provider-RPC-bound work — only the engine overhead budget (< 100 ms/resource) is guaranteed; provider latency is out of the engine's control.
  • No incremental/streaming parse; whole-config parse fits memory budget.
  • Secrets management beyond Sensitive marking is out of scope (cross-link 270 Secrets Rotation).

Back-of-Envelope Capacity Model

Six numbers derived step-by-step from the System Constraints (§4). All reference-provider (no network) unless stated; real-provider numbers are RPC-latency dominated.

C1 — Config parse throughput (§4.2 target: 5k resources < 2 s)

Assume: 50 tokens/resource × 5 bytes/token = 250 bytes/resource
5k resources → 5k × 250 B = 1.25 MB config

Lexer target: 50 MB/s (Compatibility Guarantees bench gate)
→ 1.25 MB / 50 MB·s⁻¹ = 25 ms lex time

Parser is O(tokens); parser target ≥ 10 MB/s
→ 1.25 MB / 10 MB·s⁻¹ = 125 ms parse time

Total parse: 25 + 125 ≈ 150 ms  ✓ (well within 2 s target)

C2 — Evaluation memory per resource (§4.2 target: < 512 MB at 10k resources)

Per resource (evaluated config):
  ~20 Attributes × (8 B key + 32 B Value avg) = ~800 B config values
  + ~5 graph edges × 16 B per NodeId pair = 80 B

Per ResourceInstance in state:
  ~20 Attributes × 40 B each (serde overhead) = 800 B
  + dependencies Vec: ~5 × 24 B = 120 B
  + overhead (status, index_key, schema_version) = 32 B
  → ≈ 1 KB per instance (matches §4.2 "< 4 KB" target)

10k instances: 10k × 1 KB = 10 MB state values
+ Graph (NodeId u32 × 10k nodes + 40k edges × 8 B) = 40 + 320 KB ≈ 360 KB
+ Plan (before+after per change, ~2 × 10k × 1 KB) = 20 MB worst-case (all-Create)

Total: ≈ 30 MB resident for a 10k-resource all-Create plan
→ 512 MB target leaves 480 MB headroom for serde/AST allocations ✓

C3 — State file size at 10k resources (§4.2 target: state write < 50 ms)

Per ResourceInstance JSON (serde_json, sorted keys):
  ~20 attrs × (10 B key + 20 B value + 4 B punctuation) ≈ 680 B
  + wrapping JSON overhead = ~320 B
  → ≈ 1 KB/instance

10k instances: 10 KB × 1 KB = 10 MB state file (matches §4.2 "10 MB State" row)

Disk write: modern SSD sequential write ≈ 500 MB/s
10 MB / 500 MB·s⁻¹ = 20 ms write
+ fsync latency (SSD barrier): ~5–15 ms
+ rename + dir-fsync: ~1 ms
→ Total atomic write: 20 + 10 + 1 ≈ 31 ms  ✓ (< 50 ms target)

C4 — Apply wall-clock at -parallelism=10 with real cloud provider (§4.2 provider RPC = 30 s timeout)

Assume: 1000 resources, fully independent (wide graph, depth=1), RPC latency = 1 s avg

Rounds = ceil(1000 / 10) = 100 rounds
Each round: 10 resources × 1 s (apply_resource) ≈ 10 s/round
Total apply: 100 rounds × 10 s = 1000 s ≈ 17 min

With depth D = 10 (chain of 10 dependencies):
  Chain cost: 10 × 1 s = 10 s (serialized, parallelism can't help)
  Wide cost: ceil((1000 - 10) / 10) × 1 s = 99 s
  Total: 109 s ≈ 2 min

Lesson: depth dominates; flattening the graph (removing unnecessary force_new or reference
chains) from D=100 to D=10 cuts apply time from ~120 min to ~12 min with the same providers.

C5 — Semaphore / Walker scheduling overhead (§4.2 target: < 100 ms engine overhead/resource)

Per-resource engine cost (non-RPC): diff + state-write dispatch + semaphore acquire
  Diff: O(attrs) = 20 attrs × ~1 µs each = 20 µs
  Semaphore acquire (uncontended): ~50 ns
  State write dispatch (chan send): ~200 ns
  Total non-RPC per resource: ~21 µs

1000 resources × 21 µs = 21 ms total engine overhead
→ Engine overhead fraction of 1000-resource apply: 21 ms / (1000 s RPC) = 0.002%
→ Well within ≤ 200 µs/resource target and "≤5% engine fraction" goal ✓

C6 — FD budget at maximum -parallelism=256 (§4.6 target: bounded resources)

Per provider child process:
  1 unix socket (2 FDs: one per side) + 3 stdio (stdin/stdout/stderr) = 5 FDs

One provider binary reused for all resources of that type.
Assume 10 distinct providers × 5 FDs = 50 FDs for provider connections

Walker semaphore: does NOT create an FD per node — it controls scheduling, not processes
State lock: 1 FD (lock file) + 1 FD (state file) + 1 FD (tmp file during write) = 3 FDs

Total FD budget: 50 (providers) + 3 (state) + 10 (misc: log, config files) = 63 FDs
Default OS limit: 1024 FDs (ulimit -n)
Headroom: 1024 - 63 = 961 FDs → no FD exhaustion even at full parallelism ✓

Risk: if each provider spawns a NEW child per RPC (not reused), 256 × 5 = 1280 FDs > limit.
This is why ADR-17 / §18 mandates ONE persistent provider process per provider type.
