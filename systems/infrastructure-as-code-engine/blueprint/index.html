267 — Infrastructure-as-Code Engine (Terraform-like)

Goal: Build, from scratch in Rust, a Terraform-like declarative infrastructure-as-code engine: an HCL-like configuration parser (iac-hcl), a cty-like value/type evaluator with first-class Unknown and Sensitive values (iac-eval), a dependency-graph engine with bounded-parallel walking (iac-graph), a versioned, atomically-written, lockable state store (iac-state), an out-of-process provider plugin protocol (iac-provider), and the plan/apply orchestration core (iac-core) — driven by the iac CLI. It computes a three-way-diff PLAN of Create/Read/Update/Delete/Replace actions and APPLIES it idempotently. It orchestrates providers; it is not itself a cloud provider, a policy engine, or a config-management tool.

1. Goal

Goal: Build iac — a from-scratch, Terraform/OpenTofu-class declarative provisioning engine in Rust that parses HCL-like config, evaluates it over a cty-like value lattice (incl. Unknown/Sensitive), builds a resource dependency DAG, computes a minimal three-way-diff PLAN, and APPLIES it idempotently against out-of-process providers, with versioned, lockable, atomically-written state as the single source of truth.

1.1 What is built (the pipeline)

End-to-end transform: *.iac config → AST → evaluated config → DAG → Plan → Apply → State. Seven stages, one per crate boundary:

Stage Crate Input → Output Key types
Parse iac-hcl *.iac text → config AST + Diagnostics Body, Block, Attribute, Expression
Evaluate iac-eval AST + scopes → Values (some Unknown) Value, Type, EvalContext, Function
Graph iac-graph refs → DAG, cycle-checked, reduced Graph<N>, NodeId, Edge, Walker
State iac-state prior reality persisted/loaded State, ResourceInstance, StateBackend
Provide iac-provider schema + CRUD over child process Provider, ProviderSchema, PlannedChange
Orchestrate iac-core expand → plan → apply Plan, ResourceChange, Action
Drive iac-cli operator/CI subcommands `iac init

Engine contract: consumes config + state + provider responses, answers "what must change, and apply it safely". It orchestrates providers; it does not implement any cloud.

1.2 The four correctness pillars (headline invariants)

  • Three-way diff — compare (a) prior state, (b) refreshed reality (read_resource), (c) desired config. NoOp if all agree; Update if non-force_new attrs differ; Replace if any force_new attr changed (ordered by create_before_destroy); Create if no prior; Delete if in state, absent from config.
  • Unknown propagation — computed attrs are Value::Unknown(ty) at plan time; any expression touching one yields Unknown ("known after apply"); Unknown NEVER compares equal to a concrete value; apply resolves top-down in graph order.
  • Idempotency — apply(plan) then a fresh plan against the new state yields an all-NoOp plan when reality is unchanged. The single most important property.
  • State safety — atomic write (temp + fsync + rename) + .backup of prior serial; serial monotonic; lineage detects wrong-file; write requires lock; crash leaves old-or-valid-partial state, never torn.

Plus determinism (identical inputs → byte-identical plan; sorted map/object iteration; no wall-clock/RNG in planning) and sensitive propagation (Sensitive mark flows through expressions; redacted in plan output + logs).

1.3 System boundaries

TRUST BOUNDARY      : *.iac config + provider responses are UNTRUSTED — never panic, never trust.
CONCURRENCY BOUNDARY: Walker runs provider RPCs in parallel up to -parallelism; State is single-writer.
PERSISTENCE BOUNDARY: iac-state is the only durable artifact — written atomically, lock-guarded.
PROCESS BOUNDARY    : providers run as separate child processes, spoken to over the plugin RPC protocol.

In scope: config language, value/type system, dependency graph, plan, apply, refresh, destroy, import, targeting, modules, count/for_each, local + remote-stub state backend, a built-in reference provider ("null"/"local").

1.5 Deployment model

  • A single statically-linked iac binary, run by an operator at a terminal or inside a CI pipeline. No daemon, no server.
  • Provider plugins are separate child processes the binary spawns and speaks the plugin RPC protocol to (handshake → framed messages → CRUD); they may be third-party.
  • State is local-file by default (StateBackend local impl); a remote backend is a stub (StateBackend trait + lock contract present, network impl deferred).
  • Inputs: *.iac config + CLI flags + variables. Output: an updated State file + a human-readable plan/apply log.

1.6 Target users

Platform / SRE / infrastructure engineers managing real, expensive, irreversible infra; CI/CD pipelines running unattended plan/apply with -parallelism and locking; provider authors writing plugins against the Provider trait + ProviderSchema.

1.7 Phase-0 deliverable — the seven iac-* crates

Phase-0 acceptance: CI (fmt/clippy/build/test) green + smoke test — parse a trivial config + build an empty Plan against an empty State.

1.11 Language: Rust (edition 2021, MSRV 1.78)

A wrong plan drives irreversible, expensive production mutations from untrusted config — correctness is the dominant constraint, so the language must make the critical invariants type-enforced:

  • Sum types + exhaustive match model the config AST (Expression), the value lattice incl. Unknown/Sensitive, and the Action enum precisely — a forgotten Unknown/Replace case is a compile error, not a runtime mis-plan.
  • Ownership makes "State is the single source of truth, written atomically" an enforceable invariant (single writer, move semantics on the State document).
  • Fearless concurrency lets the Walker parallelize provider RPCs up to -parallelism without data races on shared state.
  • Out-of-process provider model maps cleanly to a typed RPC over a spawned child process; Result/? makes provider/diagnostic error paths explicit.

Rejected: Go (Terraform's own — no sum types, nil-pointer risk on the plan hot path, weaker value-lattice type safety); Python (no static guarantees on irreversible mutations); Haskell (provider FFI / process plumbing friction, smaller ops ecosystem).

1.12 Prerequisites

Reader/implementer should know: HCL2 + cty value semantics (the dynamic value lattice, Unknown, conversion); recursive-descent parsing (Pratt/precedence-climbing for expressions); DAG / topological sort + SCC (Tarjan) + transitive reduction; optimistic concurrency control + atomic file writes (temp+fsync+rename, lockfiles); RPC / child-process plumbing (handshake, framed messages); and the three-way diff idea (desired vs. prior vs. refreshed reality). References: HashiCorp Terraform & OpenTofu (internal/{configs,lang,plans,states}, the go-plugin/gRPC provider protocol); HCL2 + cty; Pulumi's resource/state model (contrast); AWS CloudFormation change sets (contrast).

2. Why Build This

2.1 The systems knowledge it teaches

An infrastructure-as-code engine is a forcing function for a cluster of distributed-systems disciplines that rarely co-occur in one codebase. Each maps to a locked component:

Discipline Where it lives Why it is hard / non-obvious
Declarative reconciliation iac-core Plan + Apply Desired state is a fixpoint goal, not a script; engine derives the imperative steps. Convergent, restartable, order-free at the boundary.
Three-way diff iac-core Plan engine (Phase 7 / ## 19) Diff over prior state × refreshed reality × desired config, not a 2-way before/after. Drift detection requires the third leg.
Unknown-value propagation iac-eval Value::Unknown(Type) Partial knowledge during planning; computed attrs are unknown until apply. Lattice algebra: Unknown ⊓ x = Unknown; never == a concrete value.
Dependency-graph scheduling iac-graph Graph<N>::walk DAG from references; bounded-parallel reverse-topo walk; deferred-error aggregation, not fail-fast panic.
Atomic state + optimistic locking iac-state StateBackend + StateLock temp+fsync+rename, .backup, monotonic serial, lineage UUID, lock-before-write. Crash-consistency under SIGKILL.
Out-of-process typed RPC plugin protocol iac-provider Provider over child process Handshake, framed messages, schema negotiation, version skew, untrusted-plugin trust boundary.
Idempotency as a first-class property Phase 12 (## 24) property test apply(plan) then fresh plan ⇒ all-NoOp. The headline correctness invariant, machine-checked.

These are the same primitives behind Kubernetes controllers, database query planners (the diff = a logical→physical plan), and consensus-backed config stores — concentrated into ~7 crates with a single binary iac.

2.2 Why IaC matters — historically and architecturally

  • Pre-IaC (≤2010): infrastructure mutated by hand / imperative shell. Non-reproducible, no review surface, snowflake servers, drift invisible until outage.
  • CloudFormation (2011): declarative templates + change sets — first mainstream "show me the diff before I touch prod".
  • Terraform (2014) / OpenTofu (2023): provider-agnostic, the canonical plan → apply split, state file as source of truth, the HCL2 + cty value model this engine reimplements.
  • Pulumi (2018, contrast): general-purpose languages emit a resource graph; same reconciler core, different front end. We deliberately reject this CDK-style model (NON-GOAL) to keep the declarative-config contract clean.

The architectural lesson that outlives any tool: separate "compute the change" from "commit the change." The plan/apply split is the infra analog of EXPLAIN vs COMMIT, dry-run vs execute, a compiler's typed IR vs codegen. A reviewable, deterministic, byte-stable plan is the artifact that makes irreversible mutation auditable. That is why §2.1 lists determinism and idempotency as headline properties rather than nice-to-haves: a non-deterministic plan is unreviewable, and a non-idempotent apply is a production incident generator.

2.3 Engineering muscles this builds

  • Designing a value lattice. Value/Type with Unknown and Sensitive marks is a real lattice: meet/join, monotone propagation, top (Dynamic) / partial-knowledge elements. Teaches convert/unify (subtype coercion + least-upper-bound) — the same skill as type inference and abstract interpretation.
  • Reasoning about partial knowledge. Planning runs with values literally not-yet-computed. You must propagate Unknown through arithmetic, templates, conditionals, for-expressions, and graph dependencies without ever fabricating a concrete value — and render it honestly as "(known after apply)".
  • Crash-consistent persistence. iac-state is the only durable artifact: atomic write (temp+fsync+rename), .backup of prior serial, monotonic serial, lineage to detect a wrong/forked state file, lock-gated writes. Forces precise reasoning about failure windows — "a crash mid-apply leaves the old OR a valid partially-advanced state, never a torn file."
  • Bounded-parallel scheduling. Walk independent nodes concurrently up to -parallelism; single-writer state; defer a failed node's dependents and aggregate diagnostics. Teaches the concurrency/persistence boundary split.
  • Typed RPC across a trust boundary. Untrusted *.iac config and untrusted provider responses; CRUD over a child-process protocol with handshake + schema negotiation. Teaches API versioning, framing, and timeout/retry under partial failure.
  • Exhaustive modeling with sum types. The Action enum, Expression, Value, InstanceStatus (Ready/Tainted/Deposed) — Rust's exhaustive match turns "did we handle Replace-with-create_before_destroy?" into a compile error, not a 3am page.

2.5 Calibration value

Owning a plan/apply engine end-to-end permanently raises infra-engineering judgement: you stop treating Terraform/OpenTofu as a black box and start reasoning about why a plan shows "(known after apply)", why a force_new attr triggers Replace, why a state lock blocks a concurrent apply, and why a non-deterministic plan is a bug. The mental model — three-way diff, unknown propagation, atomic locked state, graph-ordered idempotent apply — transfers to every reconciler-shaped system (orchestrators, schedulers, sync engines, migration tools). This is a once-built-never-unlearned competency; it is the calibration anchor for the entire infra cluster (268–274) of this portfolio.

2.6 What Mastery Looks Like

  • Three-way diff without a framework (Phase 7 / §19): given only config + state + provider responses, derive exact Create/Update/Replace/Delete/NoOp decisions for any resource, including drift and Unknown propagation — without looking anything up.
  • Crash-consistent state design (Phase 5 / §17): specify the exact write protocol (temp → fsync(file) → copy-to-backup → rename → fsync(dir)) and explain why each step is necessary, what a crash at each step leaves, and how recovery works.
  • Unknown-value calculus (Phase 2/3 / §14–15): trace an Unknown value through a template, for-expression, and a conditional, deriving the result type at each step; identify when applyable=false must be set.
  • Provider trust boundary (Phase 6 / §18): specify the minimal validation the engine must perform on a provider response before accepting it into state, and identify three distinct attack vectors a malicious provider could exploit.
  • Idempotency proof (Phase 12 / §24): construct the argument that apply(plan) then a fresh plan yields all-NoOp — naming the three properties (deterministic diff, complete incremental state write, normalization round-trip) each responsible for one leg of the proof.
  • Graph scheduling (Phase 4 / §16): given a diamond DAG with one failing node, trace the exact set of nodes that execute, are deferred, and are skipped, under -parallelism=2, naming the WalkResult fields that record each outcome.
  • State migration safety (Phase 5 / §17): write the acceptance criteria for a state schema upgrade from version N to N+1, specifying the rollback invariant, the backup requirement, and the forward-only constraint.

Data flows top-down through a strict pipeline; each crate owns one transformation and a single invariant. iac-core is the only orchestrator — it is the sole crate that fans out to iac-graph, iac-state, and iac-provider, and it holds the single write capability for State.

3.1 iac-cli — the iac binary

Thin presentation/orchestration shell. In: argv (subcommand + flags), env, *.iac files on disk, stdin (for state push). Out: exit code, human-rendered diagnostics/plan/apply progress to stderr, machine output (-json) to stdout, output values. Subcommands init validate fmt plan apply destroy refresh import output graph state{list,show,mv,rm,pull,push} each translate to one iac-core entry point; no business logic lives here. Invariant: a non-zero exit ⇔ at least one error Diagnostic; plan exits 0/2 (0=empty, 2=non-empty diff, -detailed-exitcode). Owns flag parsing, -var/-var-file collection, TTY detection for color/progress, and SIGINT capture forwarded to the Apply executor's cancel token. Built Phase 0 (shell) then wired per subcommand across Phases 7–10.

3.2 iac-hcl — configuration language front end

Turns bytes into a typed but unevaluated config AST. In: UTF-8 source + filename. Out: Body (root), or Vec<Diagnostic> with byte-accurate Spans. Pipeline: Lexer (tokens, here-doc <<EOT / <<-EOT, #/////* */ comments, template ${/%{ interpolation lexing) → recursive-descent Parser (blocks with labels, attributes, the full Expression grammar incl. precedence-climbed BinaryOp/UnaryOp, Conditional, ForExpr, Splat, Index, FunctionCall{expand_final}, Template). Invariant: never panics on adversarial input — every malformed byte sequence yields a recoverable Diagnostic, and parsing is total. No evaluation, no I/O beyond the provided source, no provider knowledge. Built Phase 1; fmt reuses its lossless token/span info.

3.3 iac-eval — value/type lattice + evaluator

Evaluates an AST Expression against an EvalContext to a Value. In: AST + scopes (variables, locals, each/count, function registry, current module path). Out: Value or EvalError. Implements the cty-like lattice: concrete kinds (Null/Bool/Number(Decimal)/String/List/Set/Map/Object/Tuple) plus the two lattice marks Unknown(Type) (computed, not-yet-known) and Sensitive(Box<Value>). convert(v,to) and unify(types) give type coercion/common-supertype; the Function trait registry supplies builtins. Invariants: Unknown never compares equal to a concrete value and is contagious (any op touching Unknown → Unknown); Sensitive propagates through every operation and is never silently dropped; evaluation order is deterministic (sorted map/object iteration, no wall-clock/RNG). Built Phases 2 (lattice + core evaluator) and 3 (Functions, for/cond/splat/dynamic, var/local/output scopes).

3.4 iac-core — the orchestration engine

Owns the end-to-end lifecycle; depends on all of 1–5. Sub-components:

  • Module expander / config loader — discovers *.iac, loads module calls recursively, resolves source addresses, builds the module tree, evaluates variables/locals/outputs per module instance. Invariant: a module instance is a closed scope; cross-module refs flow only through declared variable/output. Built Phase 9.
  • NodeExpander — expands count (→ integer IndexKey) and for_each (→ string IndexKey) into per-instance ResourceAddresses. Invariant: expansion under an Unknown count/for_each is deferred ("known after apply" instance set), never guessed. Built Phase 9.
  • Graph builder — extracts references from evaluated config, emits nodes (resources, data sources, modules, var/local/output) and dependency edges into an iac-graph Graph<N> where N: GraphNode. Invariant: every references() edge present before walk. Built Phase 4.
  • Plan engine — the three-way diff: refresh prior State via Provider::read_resource, compare (a) prior, (b) refreshed reality, (c) desired config, call Provider::plan_resource for computed/requires_replace, and emit ResourceChange{action,before,after,requires_replace}. Action rule: NoOp if all agree; Update if non-force_new attrs differ; Replace if any force_new attr differs (ordered by create_before_destroy); Create if no prior; Delete if in State but absent from config. Propagates Unknown top-down; renders human-readable plan with Sensitive redaction. Invariant: plan is byte-identical given identical config+vars+prior+provider responses. Built Phase 7.
  • Apply executor — walks the graph at -parallelism, calls Provider::apply_resource, resolves Unknowns in dependency order, and writes State incrementally after each instance. Invariant: partial failure leaves a valid, partially-advanced State (failed/interrupted instances marked Tainted/Deposed, dependents deferred), and apply is idempotent — a fresh plan against the new State is all-NoOp when reality is unchanged. Built Phase 8; CBD/cancel hardening Phase 11.

refresh, destroy, import, and -target are thin operations over these components (Phase 10).

3.5 iac-graph — dependency graph engine

Generic Graph<N> over node payload; edges directed dependency → dependent. In: nodes + add_edge. Out: a WalkResult{diagnostics, visited}. detect_cycles() runs Tarjan SCC (returns the offending node lists), transitive_reduction() drops redundant edges for a minimal walk, walk(parallelism, visit) performs the reverse-topological traversal (dependencies before dependents on apply; reversed on destroy). Invariants: cycles are a hard error before any walk; a node's error defers its dependents and is aggregated, never panicked — independent subgraphs continue. Pure graph algorithms, no domain knowledge of resources/providers. Built Phase 4.

3.6 iac-state + StateBackend — durable reality

Holds desired-vs-actual reality across runs and is the only durable artifact. State{version, serial, lineage, resources: Vec<ResourceStateBucket>, outputs}; each ResourceInstance carries attributes: Value, schema_version, dependencies, and status (Ready/Tainted/Deposed). StateBackend trait: lock/unlock (advisory StateLock with LockInfo), read, write. In: a State to persist or a lock request. Out: State or BackendError. Invariants: single-writer (a write requires the held lock); atomic write = temp file + fsync + rename, with .backup of the prior serial; serial increments monotonically; lineage (a Uuid) detects a wrong/forked state file; a crash mid-write leaves the old or new file, never torn. Local backend ships now; remote is a stub. State schema upgrade/migration bridges version. Built Phase 5; lock heartbeat/force-unlock Phase 11.

3.7 iac-provider + plugin RPC — the provider boundary

Defines the Provider trait and the out-of-process plugin protocol; the engine orchestrates providers, it is not a cloud (NON-GOAL). ProviderSchema{provider, resources, data_sources} describes each resource's Attributes (required/optional/computed/sensitive/force_new) and NestedBlocks. CRUD surface: configure, validate_resource, read_resource (refresh), plan_resource (→ PlannedChange{planned, requires_replace}, Unknown for computed), apply_resource, import_resource. Transport: launch provider as a child process, perform a version handshake, then exchange framed protobuf-ish messages for schema negotiation + CRUD; an installer/registry resolves/pins provider binaries. Invariant: provider responses are untrusted (across the TRUST boundary) — every response is type-checked against the negotiated schema and force_new/computed claims are validated, never blindly persisted. A built-in reference provider ("null"/"local") backs tests without external infra. Built Phase 6; timeouts/retries Phase 11.

3.8 The provider process — real infrastructure

A separate executable (child of iac) that actually performs read/plan/apply/import against real APIs (AWS/GCP/etc.). Lives entirely outside the trust boundary and outside this codebase (NON-GOAL: we do not implement any cloud). It crashes, times out, returns malformed or eventually-consistent data — all of which iac-provider must contain. The Walker's -parallelism bounds how many such processes run CRUD concurrently; each is single-purpose per RPC and stateless between calls (all durable truth lives in iac-state). Exercised end-to-end via the reference provider from Phase 6 onward and in the Phase 12 conformance/idempotency gate.

4. System Constraints

4.1 Operating Envelope (Phase-0 scope)

  • In-process engine + local files. Single host, single iac process; provider plugins are child processes on the same host.
  • No NUMA / cluster / multi-host assumptions. No shared-memory provider model.
  • Durable artifact = exactly one iac-state State file per workspace + its .backup. No DB, no network state in Phase 0.
  • Remote/HA StateBackend (S3/etcd/consul-style) = deferred; iac-state ships a StateBackend trait + local backend + remote-stub only.
  • Untrusted inputs: *.iac config (operator-authored, may be malformed/hostile) + provider RPC responses (separate process, may misbehave/hang/crash). Trust boundary enforced at iac-hcl parse and iac-provider RPC decode.
  • Concurrency boundary: iac-graph Walker runs provider RPCs in parallel up to -parallelism; State is single-writer (engine), serialized through StateBackend::write.

4.3 Provider RPC Constraints

  • Timeout: default 30 s/call, per-call configurable. Exceed → Diagnostics error, node marked failed, dependents deferred (not panicked).
  • Retry: only on transient RPC classes (connection reset, handshake-not-ready, timeout); bounded (default 3, exponential backoff). Never retry apply_resource that may have partially mutated unless provider declares idempotency — default = no retry on apply, surface and taint.
  • Crash/hang of plugin → isolated to its child process; engine never inherits a torn State from a dead plugin. Kill on Drop / shutdown.

4.4 Determinism Constraints (planning)

  • Zero wall-clock, zero RNG in PLAN. No SystemTime, no rand, no HashMap iteration order in plan output.
  • Map/Object iteration sorted (BTreeMap/BTreeSet in Value) → byte-identical plan given identical {config, variables, prior State, provider responses}.
  • Unknown(Type) never == a concrete Value; comparison is conservative (Unknown ⇒ "(known after apply)").
  • Differential + property gates (Phase 12 ## 24): plan-determinism (re-run = byte-identical) and apply-then-plan idempotency (fresh plan post-apply = all-NoOp).

4.5 Durability & Recovery

  • State safety invariant: a malformed config or misbehaving provider can never corrupt State nor leave a torn file. Write = temp file → fsync → atomic rename, prior serial preserved as .backup.
  • serial monotonic ↑; lineage UUID detects "wrong state file"; every write requires the held StateLock.
  • Crash-consistency: a crash mid-apply leaves either the old State or a partially-advanced-but-valid State (incremental writes commit per-resource), never a partial/torn document.
  • RTO: a crashed apply re-plans cleanly from the last written State; already-applied resources diff to NoOp, in-flight ones re-diff to their pending Action. No manual state surgery on the happy crash path.
  • Sensitive: Sensitive-marked values redacted in plan render + logs; mark propagates through iac-eval expressions; never written to .backup in cleartext beyond the existing State representation.

4.7 Explicit Non-Targets (this phase)

  • No remote/HA backend, no state-locking-as-a-service (deferred; trait shape only).
  • No distributed graph walk across hosts; -parallelism is intra-process thread bound only.
  • No sub-second plan SLA for provider-RPC-bound work — only the engine overhead budget (< 100 ms/resource) is guaranteed; provider latency is out of the engine's control.
  • No incremental/streaming parse; whole-config parse fits memory budget.
  • Secrets management beyond Sensitive marking is out of scope (cross-link 270 Secrets Rotation).

6. Design Principles

Twelve to fifteen non-negotiable principles. Each: definition, tradeoff, operational implication, and the concrete failure mode when violated. These are referenced by name across Phases 0–12 (## 12–## 24).

6.1 Plan before apply, always

  • No managed-resource mutation without a reviewable Plan (Vec<ResourceChange> + OutputChanges) first computed and surfaced. apply consumes a saved/recomputed Plan; never re-derives actions silently mid-walk.
  • Tradeoff: two passes (refresh+diff, then mutate) cost a second provider round-trip vs. blind convergence; accepted — irreversible mutation demands a diff a human/CI can gate.
  • Operational: Plan.applyable flag gates apply; CI pattern = iac plan -out=p then iac apply p; a stale plan (prior-state serial drift) is rejected, not silently applied.
  • Violation: apply without a frozen plan → provider mutates resources the operator never saw in the diff (e.g. a force_new rename deletes a prod DB the reviewer believed was an in-place Update).

6.2 Idempotency is the headline property

  • apply(plan) then a fresh plan against the resulting State (reality unchanged) MUST yield an all-NoOp plan (applyable=false with zero changes). The one correctness invariant every other behavior serves.
  • Tradeoff: forces every read_resource→plan_resource path to normalize provider output identically to config (ordering, defaults, type coercion); more conversion logic vs. tolerating spurious diffs.
  • Operational: the Phase 12 (## 24) apply-then-plan property test is the release gate; a non-empty second plan is a P0 bug, not a warning.
  • Violation: non-normalized read_resource returns ["b","a"] for a config ["a","b"] set → perpetual Update, infinite churn, apply never settles, drift alarms cry wolf.

6.3 State is the single source of truth, written atomically

  • iac-state is the only durable artifact. Written via temp file + fsync + rename (atomic), with a .backup of the prior serial. serial increments monotonically; lineage (Uuid) identifies the file's identity. Every write requires a held StateLock.
  • Tradeoff: atomic rename + lock + backup add per-write latency and a lock-contention point vs. in-place mutation; accepted — State is the ground truth that decides Create-vs-Update.
  • Operational: StateBackend::write does temp+rename internally; serial mismatch on read → "state changed since plan, re-plan"; lineage mismatch → "wrong state file, refusing".
  • Violation: non-atomic write + crash → torn JSON; next read fails or, worse, parses a half-written resource list → engine plans Create for resources that already exist → duplicate live infrastructure.

6.4 Determinism in planning

  • Identical config + variables + prior State + provider responses → byte-identical Plan. No wall-clock, no RNG, no hashmap-iteration-order in the planning path. Map/Object/Set use BTreeMap/BTreeSet (sorted); convert/unify are pure.
  • Tradeoff: sorted collections cost O(log n) inserts vs. hash O(1); accepted — reproducible diffs are reviewable diffs.
  • Operational: Phase 12 plan-determinism property = N runs, assert byte-equal; any timestamp()/uuid() function is evaluated at apply, never folded into plan output.
  • Violation: a HashMap leaks iteration order into rendered plan → two CI runs on the same commit show different diffs → reviewers lose trust, plan-as-artifact comparison (CloudFormation change-set parity) breaks.

6.5 Unknown is a first-class value

  • A computed attribute not yet known is Value::Unknown(Type), not a guess or placeholder. Unknown propagates: any evaluate/convert/Function::call touching an Unknown yields Unknown; resources depending on it render "(known after apply)". Unknown NEVER compares equal to a concrete value.
  • Tradeoff: the evaluator + every function must handle the Unknown arm explicitly (more match arms) vs. the lie of substituting a fake value; accepted — a guessed value is a wrong plan.
  • Operational: plan_resource returns PlannedChange.planned with Unknown for computed fields; apply resolves Unknowns top-down in graph order; a fully-Unknown count defers expansion (Phase 9, ## 21).
  • Violation: treating an unresolved computed id as "" → downstream resource plans against "", applies, then the real id appears → next plan shows an Update that should never have existed (broken idempotency, 6.2).

6.6 The provider owns the resource semantics

  • iac-core is provider-agnostic. force_new (requires-replace), computed, required/optional, sensitive, default-filling, and the actual diff live in ProviderSchema/Attribute and Provider::plan_resource/apply_resource. The engine orchestrates; it does not know what an "S3 bucket" is.
  • Tradeoff: an RPC round-trip per resource for plan_resource vs. engine-side hardcoded diffing; accepted — provider-specific replace/compute rules can't live in the engine without coupling.
  • Operational: the engine reads Attribute.force_new only to know an Action is Replace; PlannedChange.requires_replace: Vec<Path> is authored by the provider, consumed by the engine.
  • Violation: engine guesses force_new for an attribute → either a no-downtime Update becomes a destructive Replace, or a name change that needs Replace is applied as Update and the provider API rejects it mid-apply (partial-failure, 6.8).

6.7 Dependencies are explicit and graph-ordered

  • Edges in iac-graph::Graph come solely from references: every ScopeTraversal/Splat in evaluated config that names another resource produces an add_edge(dependency, dependent). No hidden, time-based, or declaration-order ordering. Apply walks reverse-topological (leaves→roots); destroy reverses it.
  • Tradeoff: authors must express ordering via references (or explicit depends_on edges) vs. implicit file order; accepted — implicit order is non-reproducible and racy under -parallelism.
  • Operational: the reference extractor (Phase 4, ## 16) runs detect_cycles (Tarjan SCC) before any walk; transitive_reduction removes redundant edges for clearer graphs.
  • Violation: a true dependency expressed only by file proximity, not a reference → Walker schedules dependent before dependency in parallel → provider applies against a not-yet-created upstream → "resource not found" race, nondeterministic by core count.

6.8 Fail the dependents, not the process

  • A node error in Graph::walk is captured into WalkResult.diagnostics, marks the node failed, and DEFERS (skips, does not crash) its transitive dependents; independent subgraphs keep running. The process never panics on a provider/resource error. Errors aggregate; WalkResult reports all.
  • Tradeoff: more bookkeeping (failed-set, deferred-set) and a partially-applied result vs. fail-fast simplicity; accepted — aborting the whole walk on one failure wastes successful work and corrupts mental model of state.
  • Operational: failed apply writes State incrementally for succeeded nodes (6.3), marks the failed instance Tainted, returns nonzero; a re-plan shows the remaining work.
  • Violation: a panic! on one provider 500 → the walker thread unwinds with N in-flight RPCs → State never records the resources that DID apply → next plan tries to Create them again → duplicates.

6.9 Sensitive values never leak

  • Value::Sensitive(Box<Value>) is a propagating privacy mark: any expression/function consuming a Sensitive value yields Sensitive; values flowing from a sensitive provider Attribute or a sensitive variable acquire the mark. Plan render and all logs redact Sensitive to (sensitive value).
  • Tradeoff: the mark must survive evaluate/convert/collection ops (extra wrapping logic) vs. cheap plaintext; accepted — a leaked secret in a CI plan log is a breach. (Full secrets lifecycle → cross-link 270 Secrets Rotation.)
  • Operational: redaction happens at the render/log boundary, not at storage — State stores the value (it's the source of truth) but marked; diff still shows "sensitive value changed".
  • Violation: a function strips the Sensitive mark when concatenating → a DB password appears in plaintext in a shared CI plan artifact → credential disclosure.

6.10 Parsing and evaluation never panic on untrusted config

  • *.iac config is an untrusted input (trust boundary). iac-hcl Lexer/Parser and iac-eval evaluate return Diagnostics (severity + summary + detail + Span), never unwrap/panic/unbounded recursion. Malformed, adversarial, or deeply-nested input yields a clean error with source location.
  • Tradeoff: every fallible step threads Result/diagnostics vs. terse unwrap; accepted — a panic is a crash, a non-recoverable DoS, and an unactionable error.
  • Operational: recursion-depth cap on nested expressions/templates; Phase 12 (## 24) fuzz target asserts "no panic, always a Diagnostic"; spans drive caret-underlined error output.
  • Violation: unbounded recursive-descent on ((((... → stack overflow → iac plan in CI aborts with SIGSEGV, no diagnostic, the offending line unknown.

6.11 Bounded concurrency and bounded resources

  • The Walker runs independent nodes up to -parallelism (default 10) — never unbounded. Every provider RPC has a timeout; config/state parsing has size and nesting caps; template/string operations have length limits. No operation can consume unbounded memory, file descriptors, or child processes.
  • Tradeoff: caps can reject a pathological-but-legitimate huge config vs. OOM/fd-exhaustion; accepted — bounded failure beats unbounded.
  • Operational: Graph::walk(parallelism, …) enforces the semaphore; provider child processes are pooled/limited; RPC timeout → node error (6.8), not a hang.
  • Violation: unbounded parallelism on a 5000-resource graph → 5000 simultaneous child-process provider RPCs → fd exhaustion + provider API rate-limit storm → apply wedges, cloud account throttled.

6.12 Backwards-compatible, migratable state

  • State.version: u32 and per-instance schema_version: u64 are explicit. A newer engine reading an older State runs ordered, idempotent upgrade/migration (Phase 5, ## 17) before use; a refusal is explicit ("state version N > supported M"), never a silent misparse.
  • Tradeoff: migration code accrues over versions (carry cost) vs. orphaning users on old state; accepted — state is long-lived and irreplaceable.
  • Operational: migration writes a .backup first (6.3) and bumps serial; downgrade (newer state, older engine) is rejected, not attempted.
  • Violation: a field rename without a version bump → old engine reads new state as missing-attribute defaults → plans destructive Update/Replace against correct live infra → mass unintended mutation.

6.13 Observable, explainable plan and apply

  • Every Action is traceable to its cause: a ResourceChange carries before/after/requires_replace, the render explains WHY (which attr forced Replace, what is "known after apply"). Apply emits structured, ordered events (node start/finish/error) keyed by ResourceAddress.
  • Tradeoff: richer change records + event stream cost memory/IO vs. terse output; accepted — an unexplained destructive action won't pass review.
  • Operational: structured logs/events correlate plan→apply by address; -target and graph (iac graph) subcommands expose the reasoning; sensitive fields redacted (6.9).
  • Violation: a plan shows Replace with no attribute attribution → reviewer can't tell a safe metadata change from a data-destroying one → either rubber-stamps a deletion or blocks a safe change.

6.14 No mutation outside the provider boundary

  • iac-core/iac-graph/iac-state perform ZERO direct infrastructure I/O. The only path that touches real infrastructure is Provider::apply_resource (and read_resource for refresh), invoked over the plugin RPC. The engine's own side effects are limited to reading config and reading/writing State.
  • Tradeoff: indirection through the RPC boundary vs. inlined cloud calls; accepted — it keeps the trust/concurrency/persistence boundaries (architecture diagram) clean and the engine testable with the reference provider.
  • Operational: the built-in "null"/"local" reference provider lets the entire plan/apply pipeline run hermetically in tests with no network; a real provider is a child process behind the same trait.
  • Violation: iac-core calls a cloud SDK directly to "fix up" a resource → that mutation is invisible to plan/State/idempotency → drift the engine itself created, untracked, unreviewable.

6.15 Refresh reflects reality; config declares intent; the diff reconciles

  • The three-way diff is sacred: (a) prior State, (b) refreshed reality via read_resource, (c) desired config. NoOp iff all agree; Update iff config differs on non-force_new attrs; Replace iff a changed attr is force_new; Create iff no prior; Delete iff in state but absent from config. Refresh updates the engine's view of reality before diffing — it never mutates infrastructure.
  • Tradeoff: a refresh round-trip per resource (latency, API cost) vs. planning against possibly-stale State; accepted — drift detection requires seeing real reality.
  • Operational: refresh-only plan (Phase 10, ## 22) surfaces drift without proposing config-driven changes; read_resource returning "not found" → resource was deleted out-of-band → plan shows Create.
  • Violation: skipping refresh and diffing config-vs-State only → out-of-band deletion invisible → plan says NoOp → apply does nothing → the missing resource silently stays missing, State lies.

7. System Invariants

The engine drives irreversible, expensive infrastructure mutations from untrusted config. A violated invariant is a production incident (lost resources, double-create, torn state, leaked secret), not a test failure. Each invariant below is assertable — encoded as a runtime check, a property test, or a type-level guarantee — and is wired to a trace event. Severity tiers: P0 = data loss / safety (abort + refuse to write state); P1 = correctness (abort the operation, state untouched); P2 = quality (warn, continue). Convention: P0/P1 violations panic only behind debug_assertions; in release they return Diagnostics and unwind the Walker cleanly without writing State.

Trace fields are emitted on the iac.invariant span family (tracing crate); every violation logs inv_id, severity, address?, serial?, lineage?, and a stable code (e.g. INV-CYCLE) greppable in CI and incident review.

7.2 INV-ACYCLIC — graph is acyclic

  • Why — a cycle means no valid apply order; a naive walker would deadlock or infinite-loop while holding the lock and mid-mutation. Cycles arise from mutual references (a → b → a), self-reference, or create_before_destroy interaction with a replace edge.
  • Enforced — Graph::detect_cycles() -> Result<(), Vec<Vec<NodeId>>> (Tarjan SCC) runs before any node executes and before the lock is acquired for apply. Any SCC of size > 1, or a self-loop, fails the build.
  • Detection — every returned SCC is rendered as a Diagnostic cycle path a.b → b.c → a.b with source spans of the offending references().
  • Telemetry — span iac.graph.detect_cycles{nodes, edges, scc_count}; on failure code=INV-CYCLE, cycle_paths=[...].
  • Recovery — abort pre-walk; nothing mutated; operator breaks the cycle (often via indirection or depends_on removal). No lock taken ⇒ no force-unlock needed.
  • Debugging — iac graph emits the DOT of the full DAG; highlight the SCC subgraph; cross-check each edge against the reference extractor (Phase 4) to find the spurious dependency.

7.3 INV-WALK-ORDER — reverse-topological apply, reverse on destroy

  • Why — a dependent created before its dependency reads Unknown/missing upstream ids ⇒ provider error or orphaned resource. Destroy in forward order deletes a parent while children still reference it.
  • Enforced — Graph::walk only dispatches a node once all dependency edges are visited (in-degree on the dependency→dependent adjacency reaches its satisfied count). Destroy walks the edge-reversed graph; same gate.
  • Detection — debug-build assertion: at node.execute, every address in references() is already present in WalkCtx with a non-Unknown resolved value (or is intentionally deferred under Unknown count, §7.9 cross-ref). A reference resolving to absent ⇒ INV-ORDER.
  • Telemetry — per-node span iac.walk.node{address, op, deps_satisfied, parallelism_in_flight}; ordering breach emits code=INV-ORDER, address, unsatisfied_dep.
  • Recovery — P1 abort of the walk; deferred-error aggregation prevents launching the offending node's dependents; State holds only nodes that completed in-order.
  • Debugging — diff the topo order from walk against the DOT; confirm transitive_reduction did not drop a real edge; replay with -parallelism=1 to linearize and isolate.

7.4 INV-STATE-ATOMIC — atomic state write

  • Why — a crash mid-write must never leave a half-serialized State; that loses the record of real infrastructure and is unrecoverable without backups.
  • Enforced — StateBackend::write: serialize to state.tmp.<pid> → fsync(file) → fsync(dir) → copy prior to terraform.tfstate.backup-style .backup → atomic rename(tmp, state). Rename is the single commit point (POSIX atomic within a filesystem).
  • Detection — on read, verify trailing checksum + valid JSON/CBOR frame; a torn artifact fails parse ⇒ fall back to .backup (one serial behind) with a loud Diagnostic.
  • Telemetry — iac.state.write{serial, bytes, fsync_ms, backup_written}; corruption on read ⇒ code=INV-STATE-ATOMIC, recovered_from=backup.
  • Recovery — never overwrite .backup until the new primary is durably renamed; operator can iac state pull from backup; serial gap is detectable.
  • Debugging — stat the temp/primary/backup mtimes and serials; a tmp file surviving ⇒ crash before rename ⇒ primary is intact, drop the tmp.

7.5 INV-SERIAL-MONO — strictly monotonic serial

  • Why — serial orders state versions and detects stale writes / lost updates from a concurrent operator who bypassed the lock.
  • Enforced — write path asserts new.serial == old.serial + 1; remote backends additionally CAS on the prior serial (write rejected if backend serial advanced).
  • Detection — new.serial <= old.serial ⇒ INV-SERIAL; a backend CAS mismatch ⇒ INV-SERIAL, observed=<backend>, expected=<local>.
  • Telemetry — iac.state.write{serial, prev_serial}; violation code=INV-SERIAL.
  • Recovery — P0 abort before write; operator re-pulls latest state and re-plans; never decrement or reuse a serial.
  • Debugging — compare local prior serial, on-disk serial, backend serial; a jump > 1 means an out-of-band write — inspect .backup chain.

7.6 INV-LOCK-HELD — lock spans the mutation window

  • Why — two concurrent applies = double-create, conflicting writes, lost state. The lock is the only guard for the State single-writer boundary.
  • Enforced — Apply acquires StateBackend::lock(&LockInfo) -> LockId before refresh/plan-consume and holds it until the final write + unlock; RAII LockId guard releases on every exit path including panic/SIGINT.
  • Detection — every write requires a live LockId; a write attempted without one is a type-level/debug_assert impossibility (INV-LOCK). Lock heartbeat (Phase 11) detects a lost lock mid-apply.
  • Telemetry — iac.state.lock{lock_id, who, op, held_ms}; heartbeat-miss ⇒ code=INV-LOCK, lost_after_ms.
  • Recovery — if heartbeat detects loss, abort before next write (State still valid at last serial). Stale lock ⇒ explicit iac force-unlock with operator confirmation; never auto-steal.
  • Debugging — LockInfo records who/host/PID/created/operation; cross-reference with CI run ids to find the concurrent actor.

7.7 INV-LINEAGE — refuse foreign state

  • Why — pointing a config at the wrong backend (copied/forked state) and applying would create duplicate or destroy unrelated infrastructure.
  • Enforced — read records lineage: Uuid; write asserts new.lineage == prior.lineage; a fresh init generates a new lineage exactly once.
  • Detection — lineage mismatch on read-then-write ⇒ INV-LINEAGE, refuse to proceed.
  • Telemetry — iac.state.read{lineage, serial}; mismatch code=INV-LINEAGE, expected, observed.
  • Recovery — P0 hard refuse; operator must intentionally state push with override or re-init; no silent adoption.
  • Debugging — print both lineages; check backend path vs configured backend; common cause: terraform.tfstate copied between environments.

7.8 INV-IDEMPOTENT — apply then plan is empty

  • Why — the headline correctness property; a non-empty re-plan means apply under-/over-applied or the diff is unstable, eroding all operator trust.
  • Enforced — emergent from a correct three-way diff + complete incremental state write; not a single assertion but a property test (Phase 12): generate config → apply against mock provider → re-plan → assert plan.changes all Action::NoOp and applyable == false (nothing to do).
  • Detection — the idempotency property test; in production, a plan immediately post-apply showing changes emits code=INV-IDEMPOTENT, drifting_addresses=[...].
  • Telemetry — iac.plan.summary{create, update, delete, replace, noop}; post-apply non-NoOp ⇒ violation event.
  • Recovery — P1: surface to operator; usually a provider bug (apply_resource returns a value that won't round-trip through read_resource/plan_resource) or a normalization gap (e.g. set ordering, default injection).
  • Debugging — capture before/after Values of the offending ResourceChange; diff field-by-field; classify as provider normalization vs. engine diff bug; the differential corpus vs Terraform pinpoints which.

7.9 INV-UNKNOWN-NEQ — Unknown is never equal, never silently known

  • Why — if Unknown == concrete ever returned true, the diff would mark "no change" for a value computed at apply, silently dropping a required Update/Create.
  • Enforced — Value's PartialEq: any Unknown(_) operand ⇒ comparison is not equal (and == against another Unknown is also not equal). convert may widen an Unknown(t) to Unknown(u) but never to a concrete value. Only apply_resource resolves an Unknown, top-down in walk order.
  • Detection — debug assertion in the diff: comparing two Values where either side is Unknown must route through the Unknown branch, not concrete equality. A planned Value that should be Unknown but is concrete (computed attr leaked) ⇒ INV-UNKNOWN.
  • Telemetry — iac.plan.unknown{address, path, ty} counts "(known after apply)" fields; code=INV-UNKNOWN on illegal concretization.
  • Recovery — P1 abort plan; the bug is in provider plan_resource (must return Unknown for computed) or in propagation.
  • Debugging — dump the Value tree of the resource pre-apply; locate the path that is concrete but schema-computed; trace back through evaluate to the offending expression.

7.10 INV-FORCENEW — force_new always yields Replace

  • Why — applying an in-place Update to an immutable attribute (e.g. an instance's availability zone) either errors at the provider or silently no-ops, drifting reality from state.
  • Enforced — iac-core diff: for each changed attribute whose Attribute.force_new == true (or each Path in PlannedChange.requires_replace), the resulting Action is forced to Replace { create_before_destroy }, never Update. The provider's requires_replace is the authority and is unioned with schema force_new.
  • Detection — assertion: if any changed path ∈ requires_replace and action == Update ⇒ INV-FORCENEW.
  • Telemetry — iac.plan.change{address, action, requires_replace_paths}; violation code=INV-FORCENEW.
  • Recovery — P1 abort; engine bug in Action computation (the force_new/requires_replace union was not consulted).
  • Debugging — compare the schema force_new flags + provider requires_replace against the computed Action for that ResourceChange; confirm create_before_destroy ordering downstream (§7.3).

7.11 INV-SENSITIVE — sensitive marks propagate and redact

  • Why — a leaked secret in plan output, logs, or state diff is a security incident; the mark must survive every expression that touches the value.
  • Enforced — Value::Sensitive(Box<Value>): evaluate propagates the mark through arithmetic, templates, traversal, function calls, for/splat (any sensitive operand ⇒ sensitive result). A sensitive provider Attribute or sensitive variable seeds the mark. Plan render and tracing log formatters redact to (sensitive value).
  • Detection — render/log layer asserts no raw bytes of a Sensitive value reach output; a fuzz/property test marks an input sensitive and greps all output streams for the cleartext ⇒ INV-SENSITIVE if found.
  • Telemetry — iac.plan.change{has_sensitive}; leak detection code=INV-SENSITIVE, sink=<render|log|state>.
  • Recovery — P1 (treated as P0 in security contexts): block the output; never log the cleartext even in the violation event (log the path, not the value).
  • Debugging — track the mark through the Value tree; the loss point is the first expression node whose output dropped the mark — typically a function that rebuilt a collection without re-wrapping.

7.12 INV-DETERMINISM — byte-identical plans

  • Why — non-deterministic plans break diff review, idempotency checks, and the differential corpus; operators cannot approve a plan they cannot reproduce.
  • Enforced — planning forbids wall-clock, RNG, and HashMap iteration order: all maps/objects are BTreeMap/BTreeSet (sorted), Set(BTreeSet<Value>), change list sorted by ResourceAddress. No SystemTime/Instant reads in the Plan path.
  • Detection — Phase 12 plan-determinism property: plan twice over identical inputs, assert byte-identical serialized Plan. CI greps the iac-core Plan path for banned symbols (Instant::now, rand, HashMap).
  • Telemetry — iac.plan.hash{plan_sha256}; two differing hashes for identical inputs ⇒ code=INV-DETERMINISM.
  • Recovery — P1; fix the nondeterministic source (usually an unsorted collection or a timestamp injected into an attribute default).
  • Debugging — diff the two serialized plans; the first differing byte localizes the unsorted/volatile field; bisect by zeroing subsystems.

7.13 INV-PARTIAL-VALID — partial apply records exactly what succeeded

  • Why — apply mutates real infra incrementally; if node 7 of 12 fails, State must record nodes 1–7 (and only those that truly succeeded) so a re-plan converges. A phantom instance (in state, not real) ⇒ later spurious Delete or Update against nothing; a missing instance (real, not in state) ⇒ orphaned resource billed forever.
  • Enforced — the Apply Walker writes State incrementally after each successful apply_resource (or batches with bounded loss window), under the held lock; a node that errors does not write a success record and defers its dependents. On apply_resource returning a Value, that exact Value is recorded (no optimistic pre-write).
  • Detection — post-apply reconciliation: every ResourceInstance in State must correspond to a node whose execute returned Ok; any error-path node must be absent or marked Tainted. Crash-recovery test injects a panic between RPC-success and state-write to assert the window is bounded and recoverable.
  • Telemetry — iac.apply.node{address, result, state_written}; on partial failure iac.apply.summary{succeeded, failed, deferred}; mismatch ⇒ code=INV-PARTIAL.
  • Recovery — P0: never write a success record for a failed/uncertain RPC; on RPC ambiguity (timeout after send) mark the instance Tainted so the next plan forces Replace rather than assuming success.
  • Debugging — replay with -parallelism=1; compare the per-node result trace against the final State buckets; a Tainted instance is the recovery breadcrumb.

7.14 INV-PROVIDER-BOUND — every state instance has a provider + schema version

  • Why — an instance without a resolvable provider cannot be refreshed, planned, or destroyed (it becomes unmanageable); a wrong schema_version mis-decodes attributes.
  • Enforced — iac-core requires every ResourceStateBucket to carry a ProviderAddress resolved at plan time; the write path asserts provider is non-empty and ResourceInstance.schema_version matches the configured provider's current schema (or a known-upgradeable prior version, see iac-state migration).
  • Detection — pre-write scan: any instance with an unresolved provider or a schema_version newer than the loaded provider ⇒ INV-PROVIDER.
  • Telemetry — iac.state.write{instances, providers, max_schema_version}; violation code=INV-PROVIDER, address, provider, schema_version.
  • Recovery — P1 abort; missing provider ⇒ operator runs iac init to install it; a too-new schema_version ⇒ the state was written by a newer engine, refuse and warn.
  • Debugging — list (address → provider, schema_version); diff against the installed provider registry; the upgrade path runs the provider's state-upgrade for an older schema_version before use.

7.16 Cross-cutting enforcement notes

  • Single choke point — all P0 state invariants (ATOMIC, SERIAL-MONO, LOCK-HELD, LINEAGE, PARTIAL-VALID, PROVIDER-BOUND) funnel through StateBackend::write; it is the one function permitted to mutate the durable artifact, so its preconditions are the union of those checks. No other code path writes State.
  • Fail-closed — every P0/P1 violation returns Diagnostics and unwinds without writing State; the default is "do nothing and refuse," never "guess and proceed."
  • Invariant ⇒ test — each INV-* code maps 1:1 to at least one Phase 12 fixture; CI fails if any INV-* lacks a covering test (the catalog is the test manifest).
  • Trace correlation — all violations carry the active serial, lineage, and operation id, so an incident reviewer can grep code=INV-* across the run log and reconstruct the exact pre-mutation state.

8.1 Lexical model — tokens

iac-hcl Lexer emits a token stream with byte-offset Span (start, len, line, col) on every token; never panics, emits Diagnostic{severity:Error} on illegal bytes and resyncs.

8.2 Configuration grammar (EBNF)

config-file  = body ;
body         = { attribute | block } ;
block        = IDENT { label } "{" body "}" ;
label        = IDENT | STRING ;
attribute    = IDENT "=" expr NEWLINE ;

expr         = conditional ;
conditional  = logic_or [ "?" expr ":" expr ] ;
logic_or     = logic_and { "||" logic_and } ;
logic_and    = equality  { "&&" equality } ;
equality     = compare   { ( "==" | "!=" ) compare } ;
compare      = additive  { ( "<" | "<=" | ">" | ">=" ) additive } ;
additive     = multiply  { ( "+" | "-" ) multiply } ;
multiply     = unary     { ( "*" | "/" | "%" ) unary } ;
unary        = [ "!" | "-" ] postfix ;
postfix      = primary { index | getattr | splat } ;
index        = "[" expr "]" ;
getattr      = "." IDENT | "." NUMBER ;          (* NUMBER -> LegacyIndex *)
splat        = "." "*" { getattr | index } ;     (* attr.*.id *)

primary      = literal | tuple | object | template | scope_traversal
             | func_call | for_expr | "(" expr ")" ;
literal      = "null" | "true" | "false" | NUMBER | STRING ;
tuple        = "[" [ expr { "," expr } [ "," ] ] "]" ;
object       = "{" [ objelem { ( "," | NEWLINE ) objelem } ] "}" ;
objelem      = ( IDENT | "(" expr ")" | STRING ) ( "=" | ":" ) expr ;
template     = QUOTED_WITH_INTERP | HEREDOC ;     (* -> Expression::Template *)
scope_traversal = IDENT { getattr | index } ;     (* -> Variable | ScopeTraversal *)
func_call    = IDENT "(" [ expr { "," expr } [ "," ] ] [ "..." ] ")" ;  (* "..." -> expand_final *)
for_expr     = "[" "for" IDENT [ "," IDENT ] "in" expr ":" expr [ "if" expr ] "]"   (* tuple/list *)
             | "{" "for" IDENT [ "," IDENT ] "in" expr ":" expr "=>" expr [ "..." ] [ "if" expr ] "}" ; (* object *)

Parser is recursive-descent with the precedence ladder above (Pratt-style for binary ops). A bare IDENT with no following getattr/index → Expression::Variable; with a traversal tail → Expression::ScopeTraversal(Vec<Traversal>). Dynamic blocks are surface sugar: dynamic "ingress" { for_each = … content { … } } parses as an ordinary Block ty=dynamic, expanded in Phase 3.

8.4 Value lattice + Type system

Value (iac-eval) is the cty-like dynamic value. Each Value has a Type; Unknown(Type) carries its type even when the concrete value is not yet known; Sensitive(Box<Value>) is a privacy mark that propagates through every operation.

         (leaf)

8.5 The three-way diff + Action computation

A plan diffs three inputs per resource instance: P = prior State value, R = refreshed reality (Provider::read_resource(prior)), C = desired config (evaluated Value, possibly Unknown). Drift = P ≠ R. The provider's plan_resource(prior=R, proposed=C) returns PlannedChange{ planned, requires_replace }; iac-core computes the Action.

In prior? In config? R vs C force_new attr changed? → Action
no yes — — Create
yes no — — Delete
yes (data) yes — — Read (data sources always re-read)
yes yes R == C — NoOp
yes yes R ≠ C no Update
yes yes R ≠ C yes Replace{ create_before_destroy }
yes yes drift P≠R, C==R — NoOp (state reconciled to R; recorded)
yes yes drift P≠R, C≠R per-attr Update/Replace as above, diff vs R

Rules: comparison is against refreshed reality R, not stale prior P, so drift is healed. Replace ordering: create_before_destroy=true → new instance created, dependents re-pointed, old Deposed(DeposedKey) then destroyed; false → destroy-then-create (default). Any operand Unknown ⇒ changed attrs that are Unknown render (known after apply) and the instance is applyable but not fully diffable until apply resolves them top-down. lifecycle.prevent_destroy=true + Delete/Replace ⇒ Diagnostic Error, plan rejected. ignore_changes masks listed attrs from the diff.

/// Number is `Decimal` (arbitrary precision, base-10) — no f64, to keep plans byte-deterministic.

    Null, Bool(bool), Number(Decimal), Str(String),

    Template(Vec<TemplatePart>),                       // "pre-${x}-post" / here-docs
    Variable(String),                                  // bare leaf name
    ScopeTraversal(Vec<Traversal>),                    // a.b[0].c

    BinaryOp(BinOp, Box<Expression>, Box<Expression>),
    UnaryOp(UnOp, Box<Expression>),
    Conditional { cond: Box<Expression>, t: Box<Expression>, f: Box<Expression> },
    ForExpr(Box<ForExpr>),                             // [for k,v in coll : expr if cond]
    Index { coll: Box<Expression>, key: Box<Expression> },
    Splat { source: Box<Expression>, each: Box<Expression> }, // attr.*.id
}

/// One step of a reference path. LegacyIndex = `a.0` form; Index = `a[expr]` (expr eval'd late).
pub enum Traversal { Attr(String), Index(Expression), LegacyIndex(u64) }

/// One static segment or one `${...}` interpolation hole.
pub enum TemplatePart { Literal(String), Interp(Expression) }

/// Source location: byte range into a named file; drives Diagnostic underlining.

pub struct Diagnostic { pub severity: Severity, pub summary: String, pub detail: String, pub span: Span }
pub enum Severity { Error, Warning, Note }

  • Object keys are Expression (keys may interpolate); ordering preserved from source for first-eval, but evaluated map is BTreeMap (canonical sort) — see 11.2.

11.2 iac-eval — Value / Type lattice

/// The cty-like dynamic value lattice. Total Ord/Eq over canonical encoding (Unknown excepted).
pub enum Value {
    Null, Bool(bool), Number(Decimal), Str(String),
    List(Vec<Value>),                    // ordered, homogeneous-by-unify
    Set(BTreeSet<Value>),                // dedup + sorted → canonical
    Map(BTreeMap<String, Value>),        // string-keyed, sorted
    Object(BTreeMap<String, Value>),     // fixed attr set, sorted keys
    Tuple(Vec<Value>),                   // ordered, heterogeneous
    Unknown(Type),                       // value computed by a provider; carries its known Type
    Sensitive(Box<Value>),              // privacy mark; wraps any of the above; propagates
}

Unknown + Sensitive semantics (LOCKED):

Concern Rule
Unknown(ty) equality NEVER == any value, incl. another Unknown. Diff renders it (known after apply).
Unknown propagation Any op/fn with an Unknown operand returns Unknown(result_ty); result_ty from return_type. Short-circuits known-false && etc. only when the other operand is fully known.
Unknown placement Sorts as a single class in BTreeSet/Map; canonical encoding tags it so encodings stay stable.
Sensitive propagation Marks flow outward through every combining op; Sensitive(Unknown(ty)) legal. Unwrapped only at the provider boundary; redacted ((sensitive value)) in plan render + logs.
Idempotency tie-in convert/unify/iteration are deterministic → planning is byte-stable (§4 determinism).

/// Generic DAG over node payload N. Edges = adjacency, dependency -> dependent.
pub struct Graph<N> { /* nodes: Vec<N>, edges: adjacency lists both directions */ }

impl<N> Graph<N> {
    pub fn add_node(&mut self, n: N) -> NodeId;
    pub fn add_edge(&mut self, from: NodeId, to: NodeId);

    pub fn transitive_reduction(&mut self);                         // drop redundant edges; preserves reachability
    /// Reverse-topological (leaves→roots) walk; ≤ parallelism nodes concurrent; errors defer dependents.

}

/// The minimal mutation for one resource instance. Replace = delete+create, order per create_before_destroy.

    NoOp,
    Read,                                              // data source / refresh-only
    Create, Update, Delete,
    Replace { create_before_destroy: bool },
}

/// One line of the plan. before = prior+refreshed; after = desired (Unknown for computed).

    pub action: Action,
    pub before: Value,
    pub after: Value,                                  // may contain Unknown
    pub requires_replace: Vec<Path>,
    pub deposed: Option<DeposedKey>,
}

/// The full, saved, byte-deterministic plan. Applyable = no errors + no required re-plan.
pub struct Plan {
    pub changes: Vec<ResourceChange>,
    pub output_changes: Vec<OutputChange>,
    pub prior_state: State,                            // pinned snapshot the plan was built against
    pub variables: BTreeMap<String, Value>,           // pinned inputs → reproducibility
    pub applyable: bool,
}

/// Implemented by every graph node (resource / data / module-call / local / output / provider).
pub trait GraphNode {
    fn address(&self) -> &Addr;
    fn references(&self) -> Vec<Addr>;                 // → edges (dependency extraction, §16)
    fn execute(&self, op: &Op, ctx: &mut WalkCtx) -> Result<(), Diagnostics>;  // op = Refresh|Plan|Apply|Destroy
}

Three-way diff → Action (LOCKED, normative for §19):

prior refreshed reality desired config changed attrs ⇒ Action
absent — present — Create
present present absent — Delete
present present present none NoOp
present present present only non-force_new Update
present present present any force_new Replace { create_before_destroy }
present drifted present reality≠prior re-diff vs refreshed, may yield Update/Replace
any — data source — Read
  • Plan is immutable after build + serde + Send + Sync; the Apply Walker shares it by &. prior_state + variables are pinned so apply reproduces planning exactly; applyable=false blocks iac apply (forces fresh plan).
  • Action is Copy; exhaustive match everywhere (no catch-all arm) so a new action variant fails the build, not at runtime.
  • Idempotency contract (headline §4): apply(plan) then a fresh plan against new state ⇒ all-NoOp when reality unchanged. Determinism: changes sorted by ResourceAddress; Unknown never compares equal ⇒ no spurious diffs.

20. Phase 8 — Apply engine: execute the plan, incremental state, partial failure

8.1 Objectives

  • Load saved Plan -> walk graph reverse-topological with -parallelism -> for each non-NoOp ResourceChange call Provider::apply_resource(ty, prior, planned) -> resolve Unknown -> write ResourceInstance into State incrementally + atomically.

23. Phase 11 — Concurrency, locking, and consistency hardening

11.1 Objectives

  • Precise -parallelism semantics: one global semaphore across the iac-graph Walker (default 10); per-provider concurrency caps layered beneath it.
  • State-lock lifecycle: acquire before any state mutation; heartbeat to detect dead holder; stale-lock detection; force-unlock gated on operator confirmation.
  • Provider-call timeouts + bounded retries (exponential backoff) on transient/retryable Diagnostics only — never on deterministic errors.
  • SIGINT/SIGTERM graceful shutdown: stop scheduling new nodes, drain in-flight apply_resource, flush State, exit non-zero.
  • Crash-consistent partial applies: every written ResourceInstance durable; next plan reconciles. Consistency self-checks: serial monotonicity, lineage match, no orphaned instances.

11.2 Detailed Implementation Steps

  • iac-graph::walk: replace ad-hoc spawn with a Semaphore(parallelism) (tokio or std Condvar-backed); permit acquired before visit, released on completion/error. Independent nodes contend on it; dependents still gated by reverse-topo edges. (P3, P11, I5=INV-LOCK-HELD, ADR-14, ADR-15, B4 ch.9, P9/OSDI-2014)
  • iac-provider: add ProviderHandle { sem: Semaphore(cap) }; cap from schema-declared max_concurrency (default = global). RPC wrapped in with_timeout(d, retry_policy); RetryPolicy { max_attempts: 5, base: 200ms, factor: 2.0, cap: 30s, jitter }. Retry only if Diagnostics::is_retryable() (transport reset, RPC Unavailable, explicit Retryable severity).
  • iac-state: extend StateBackend with heartbeat(LockId) -> Result<(), BackendError> + LockInfo { id, who, version, created, operation, hb_at }; local backend writes .iac.lock (advisory + content). Background heartbeat thread refreshes hb_at every 10s. Lock stale if now - hb_at > 3×interval.
  • iac-core Apply executor: wrap walk in a Cancel token (Arc<AtomicBool>); SIGINT handler sets it; scheduler checks before each acquire. On set: await in-flight, single final atomic State::write, return Cancelled.
  • Add State::self_check() -> Result<(), Vec<Diagnostic>>: serial strictly increased vs prior, lineage matches backend, every ResourceInstance reachable from a ResourceStateBucket (no orphans/dangling Deposed).

  • Backoff cap 30s bounds tail latency; total retry budget per node ≤ ~60s before hard fail.
  • Cancel check is a relaxed atomic load (< 5ns); no measurable scheduler overhead.

T2 — Malicious / compromised provider plugin

Provider is the highest-privilege component: a child process holding the operator's cloud creds, invoked over the plugin RPC protocol (Phase 6).

  • Out-of-process boundary: provider is a separate child process — a panic/segfault there fails one RPC, never crashes iac; the engine treats every response as untrusted (T4).
  • Identity/integrity: provider lockfile (.iac.lock.hcl) pins {source, version (SemVer), sha256[]} per platform. iac init downloads, verifies SHA-256 against lock; mismatch → hard fail. First acquisition records hash; later drift → error (TOFU + pin).
  • SemVer pinning: config required_providers { version = "~> 1.4" }; resolver picks highest matching, writes exact version + hash to lock; CI commits the lock.
  • Signature verification: registry-served binaries carry a detached signature over the SHA-256; verify signing key before trusting the hash chain.
  • Least-privilege guidance (doc-level, engine cannot enforce host policy): run iac under a scoped role (short-lived STS creds), per-env credential isolation, no long-lived root keys; on CI, OIDC-federated ephemeral creds.
  • Sandboxing guidance: providers need network + creds, so full sandbox is impractical; recommend running in a constrained container / seccomp profile / network egress allowlist. The engine documents that a provider can exfiltrate any cred it is configured with — trust in a provider == trust with the creds you hand it.
  • Detection: log provider {name, version, sha256, pid} at handshake; emit iac.provider.spawn event.
  • Recovery: lockfile lets an operator roll back to a known-good pinned version; iac init -upgrade is the only path that changes pins (explicit, reviewable diff).

T4 — Malicious provider RPC responses

Provider responses are untrusted even from a "trusted" provider (could be compromised mid-run or buggy):

  • Response size cap (16 MiB / message, framed); over-cap → kill RPC, Diagnostic.
  • Returned Value is schema-validated against the resource Schema (type-checked via convert) before entering state → a provider cannot inject a type the engine can't represent.
  • Unknown in an apply-time result (must be concrete after apply) → error; provider must resolve all computed values on apply.
  • RPC timeout (default 30 min/call, configurable) → cancel, taint instance (T8), no hang.
  • Recovery: a poisoned attribute is contained to that ResourceInstance; incremental state write means only the last good instance persists.

T5 — Secret leakage (plan output / logs / state)

  • Sensitive propagation: Value::Sensitive(Box<Value>) mark flows through every evaluate/convert/function path (any op touching a sensitive operand → sensitive result); enforced by construction in iac-eval, covered by a property test.
  • Provider attrs with sensitive: true → values wrapped Sensitive on read_resource/apply_resource; variables marked sensitive = true → wrapped at entry.
  • Redaction: plan render and all logs print (sensitive value); never the plaintext. Sensitive masking is applied at the render boundary, not relied on at call sites.
  • Privacy analysis — state contains secrets: even redacted in output, the state file stores the actual values (a DB password lives in ResourceInstance.attributes). Therefore: state at rest is as sensitive as the secrets within it; doc mandates restricted FS perms (0600), restricted remote backend ACLs, and (deferred) encryption (T3). iac state show redacts Sensitive on display; state pull emits raw → documented as a privileged op.
  • Leak vectors closed: -no-color/CI logs, crash dumps (no Value in panic messages — Diagnostics carry spans not values), error messages (redact before format).

T6 — Path traversal in file() / templatefile()

  • Filesystem functions resolve only within a restricted root = the configuration root directory (module dir). .. escaping the root, absolute paths outside root, and symlinks pointing outside root → Diagnostic, refused.
  • Canonicalize then prefix-check against the root after resolving symlinks (defeats symlink escape).
  • No general FS read primitive exposed to config; only the whitelisted functions.
  • Telemetry: iac.fn.file{path} (path relative-only logged). Recovery: pure eval, no side effects; abort.

T7 — Supply-chain risk (engine deps + provider binaries)

  • Engine: cargo-deny in CI — advisory DB (RUSTSEC) gate, license allowlist, duplicate/yanked-crate ban, source allowlist (crates.io only). Cargo.lock committed; MSRV 1.78 pinned.
  • Providers: SHA-256 + signature verification + lockfile (T2). Vendored mirror option for air-gapped installs.
  • Build: reproducible-build target for iac itself; release artifacts signed.
  • Detection: CI fails on new advisory; iac init fails on hash drift.

T8 — Panics / DoS on adversarial config

  • Diagnostics-only parsing/eval: iac-hcl and iac-eval return Result/Diagnostic for every malformed input; panic == bug, asserted by the fuzz gate (Phase 12).
  • Fuzz targets: HCL parser fuzz (arbitrary bytes → never panic, bounded time/mem); evaluator fuzz on random AST. corpus seeded from the differential suite.
  • Bounded execution: caps from T1 guarantee parse/eval terminate in time linear-ish in capped input.
  • Recovery: a single bad config aborts that invocation cleanly (exit 1, diagnostics), zero infra effect.

T10 — Concurrent apply / state-lock bypass

Two operators (or CI jobs) applying against the same state at once → interleaved refresh/write → lost updates, split-brain state, resources created twice or orphaned.

Vector Guardrail
Simultaneous apply on shared state mandatory backend state lock acquired before refresh, released after atomic write; LockInfo{who,version,operation,created} shown to the loser

Crash holding the lock audited force-unlock <lock-id> after operator verifies no live apply; serial+lineage guard (T3) rejects a torn write on next apply
  • Detection/telemetry: state_lock_wait_seconds, state_lock_contention_total, force_unlock_total (alert if > 0); second applier blocks with the holder's LockInfo.
  • Recovery: .backup + monotonic serial/lineage catch a partially-written state; a bypassed lock that corrupts state is recovered from .backup and re-planned.

Residual risk (accepted / deferred)

  • State at rest unencrypted until the deferred KMS work (T3/T5) → mitigated by FS perms + backend ACLs, documented as operator responsibility.
  • A provider trusted with creds can abuse them (T2) → unavoidable given the model; bounded by least-privilege + lockfile pinning + audit.
  • Host/kernel compromise out of model.

Failure Modes and Recovery

Taxonomy of every way iac can fail, ordered by blast radius. Severity scale: S0 silent wrong infra / state loss · S1 failed mutation, recoverable · S2 aborted run, no infra touched · S3 local-only nuisance. Two classes are S0 and get the most ink: state corruption / torn write and idempotency violation. Every class carries: symptoms · root causes · detection · automatic recovery · manual recovery · operator actions · forensic artifacts · long-term mitigation.

Trace methodology (shared by all classes)

Three forensic instruments, emitted on demand or on failure:

Instrument Source Captures Flag
plan -json iac-core Plan engine every ResourceChange (address, action, before/after, requires_replace, Unknown markers) iac plan -json
state diff iac-state serial/lineage + per-ResourceInstance attribute delta old vs new iac state show + .backup compare
provider RPC trace iac-provider transport framed messages per call (validate/read/plan/apply/import), wall-clock, exit code IAC_PROVIDER_TRACE=1

Rule: a wrong plan is debugged top-down — plan -json localizes the bad ResourceChange, RPC trace localizes the provider call, state diff confirms what landed in State.

F1 — Parse / eval error (bad config)

  • Symptoms: iac validate/plan exits non-zero with Diagnostic list; no Plan, no State mutation.
  • Root causes: malformed HCL (unbalanced braces, bad here-doc terminator), unknown function, type-conversion failure in convert, unbound ScopeTraversal, unify returns None.
  • Detection: iac-hcl Parser / iac-eval evaluate return Diagnostic { severity, summary, detail, span }; Parser never panics (Phase 1 invariant) — recovers to next block, aggregates.
  • Automatic recovery: none needed — fail-closed before the graph builder; State untouched (PERSISTENCE BOUNDARY never crossed).
  • Manual recovery: fix config at reported Span; re-run.
  • Operator actions: iac fmt to normalize; iac validate in CI as a gate.
  • Forensic artifacts: Diagnostic with source span + caret; plan -json empty.
  • Long-term mitigation: parser fuzz target (Phase 12) ensures bad input → Diagnostic, never panic/hang.

F2 — Cyclic dependency graph

  • Symptoms: plan aborts: "Cycle: a.x → b.y → a.x".
  • Root causes: mutual references, self-reference, depends_on loop, module-call cycle.
  • Detection: Graph::detect_cycles (Tarjan SCC) → Err(Vec<Vec<NodeId>>) before any walk.
  • Automatic recovery: none — abort pre-walk; State untouched.
  • Manual recovery: break edge (introduce a local, remove spurious depends_on).
  • Operator actions: iac graph to visualize the SCC.
  • Forensic artifacts: the SCC node list, rendered as ResourceAddress chain.
  • Long-term mitigation: cycle-detection unit corpus; transitive_reduction runs only on acyclic graphs.

F3 — Provider plugin crash / RPC timeout mid-apply

  • Symptoms: apply stalls then errors on one resource: "provider exited" / "RPC timeout after Ns".
  • Root causes: child process segfault, panic, OOM-kill, hang; network call inside provider stuck.
  • Detection: iac-provider transport: child exit code ≠ 0 / EOF on framed stream / per-call timeout (default 30s, Phase 11).
  • Automatic recovery: Walker defers dependents of the failed node (deferred-error aggregation), persists already-applied resources via incremental State::write, retries idempotent reads with backoff (Phase 11 retry policy); does not retry apply_resource (non-idempotent mutation).
  • Manual recovery: re-run apply — completed resources are NoOp; the failed one re-plans from refreshed reality.
  • Operator actions: inspect provider logs; raise timeout via flag; reduce -parallelism if provider rate-limits.
  • Forensic artifacts: RPC trace (last framed message + exit code); partial-apply summary listing succeeded/failed/deferred.
  • Long-term mitigation: provider handshake version pin; per-call timeout + bounded retries; child reaped on iac exit.

F4 — Partial apply (some resources created, then failure)

  • Symptoms: apply reports "N applied, 1 failed, M deferred"; State advanced for the N.
  • Root causes: any per-resource apply_resource error after earlier successes (auth expiry, quota, conflict).
  • Detection: non-empty WalkResult.diagnostics; failed instance marked InstanceStatus::Tainted.
  • Automatic recovery: incremental State write after each successful node (crash-consistent); failed resource → Tainted so next plan schedules Replace.
  • Manual recovery: re-run apply; or iac state rm a half-created resource the provider couldn't read back.
  • Operator actions: read partial-apply summary; confirm tainted set before re-apply.
  • Forensic artifacts: State serial bumped per success; tainted ResourceInstance list; plan -json of the re-plan.
  • Long-term mitigation: create-before-destroy default for replace-sensitive resources; deposed bookkeeping for in-flight replacements.

F5 — State corruption / torn write (S0 — gravest class)

  • Symptoms: iac refuses to load State: "state unparseable" / version mismatch / truncated JSON; or a crash left a .tmp file.
  • Root causes: process/host crash mid-write, full disk, killed during serialize, manual hand-edit, concurrent writer bypassing the lock.
  • Detection: deserialize failure on StateBackend::read; version/checksum check; presence of orphan temp file.
  • Automatic recovery: the atomic write protocol prevents torn files — write to temp, fsync, atomic rename, and a .backup of the prior serial is always kept. A crash leaves either old state or a valid advanced state, never torn. On a detected unparseable primary, iac halts and points to .backup.
  • Manual recovery: iac state pull to inspect; restore the .backup (one serial behind) → iac state push; if reality drifted past backup, reconcile via iac import + targeted apply.
  • Operator actions: never hand-edit; verify serial/lineage after restore; re-acquire lock.
  • Forensic artifacts: primary file + .backup + any .tmp; serial/lineage triple; state diff backup-vs-primary.
  • Long-term mitigation: atomic temp+fsync+rename invariant (Phase 5); single-writer guarantee via lock; serial monotonicity check; crash-consistency property test that kills the process at every write offset and asserts post-load validity.

F6 — Stale / orphaned state lock

  • Symptoms: apply blocks: "state locked by <who>@<host> since <t>, LockId=...".
  • Root causes: prior iac killed (SIGKILL) before StateBackend::unlock; crashed CI runner.
  • Detection: lock returns existing LockInfo with stale heartbeat (Phase 11 heartbeat TTL).
  • Automatic recovery: none (deliberate — auto-stealing a live lock risks two writers = F5).
  • Manual recovery: verify no live run, then iac force-unlock by LockId.
  • Operator actions: confirm holder is dead before forcing; check heartbeat age.
  • Forensic artifacts: LockInfo (who/host/operation/created/heartbeat); LockId.
  • Long-term mitigation: heartbeat-based liveness; lock acquired before any write; advisory TTL surfaced in the error.

F7 — Drift (reality changed out-of-band)

  • Symptoms: a plan shows changes you didn't author; "objects have changed outside of iac".
  • Root causes: console/manual edits, another tool, provider-side defaulting.
  • Detection: refresh — read_resource into prior, three-way diff vs State.
  • Automatic recovery: none auto-applied; drift surfaced as Update/Replace ResourceChange.
  • Manual recovery: iac apply to reconcile config→reality, or iac plan -refresh-only then accept to update State to match reality.
  • Operator actions: decide reconcile-vs-accept per resource; scope with -target.
  • Forensic artifacts: refresh-only plan -json; state diff prior-vs-refreshed.
  • Long-term mitigation: scheduled refresh-only drift detection in CI; ignore_changes for intentionally external attrs.

F8 — Provider produced an unexpected result (planned != applied)

  • Symptoms: apply errors: "Provider produced an unexpected result: attr was X in the plan but Y after apply".
  • Root causes: provider bug — returns a value diverging from PlannedChange.planned for a non-Unknown attribute; missing computed/force_new marking; non-deterministic provider.
  • Detection: iac-core post-apply consistency check: apply_resource result must equal planned except where planned was Value::Unknown(ty).
  • Automatic recovery: none — error raised, the offending ResourceInstance left Tainted; State records the actual returned Value (so it isn't lost), flagged suspect.
  • Manual recovery: file provider bug; mark the attr computed in schema if legitimately server-set; re-plan.
  • Operator actions: capture RPC trace of the plan vs apply calls for the provider author.
  • Forensic artifacts: planned Value vs applied Value side-by-side; RPC trace of both calls.
  • Long-term mitigation: strict consistency enforcement on every apply; reference provider held to the same contract; differential corpus (F11) catches divergent providers.

F9 — Unknown that never resolves

  • Symptoms: apply errors: "value was Unknown after apply" / a ResourceChange.after still contains Value::Unknown post-apply.
  • Root causes: dependency that should have produced a concrete value stayed Unknown (upstream failed/deferred); cyclic-through-Unknown; provider returned Unknown for a non-computed attr.
  • Detection: Apply executor asserts no surviving Unknown in an applied resource's attributes (Unknown resolves top-down in graph order).
  • Automatic recovery: none — abort that node, defer dependents (Unknown never compares equal to concrete).
  • Manual recovery: re-run apply after the upstream resolves; if structural, fix config so the computed value has a real producer.
  • Operator actions: trace the Unknown's provenance via plan -json ("known after apply" chain).
  • Forensic artifacts: the Unknown-bearing Path; the dependency chain from plan -json.
  • Long-term mitigation: unknown-propagation property tests; graph order guarantees producers before consumers.

F10 — Idempotency violation (apply→plan ≠ empty) (S0 — highest severity)

  • Symptoms: immediately after a clean apply with reality unchanged, a fresh plan is not all-NoOp. This is the headline correctness failure.
  • Root causes: diff bug (three-way diff treats equal values as differing — e.g. Set ordering, Number/Decimal normalization, sensitive-mark mismatch); provider returns post-apply Value ≠ what it will read back; schema marks an attr non-computed that the server mutates; map/object iteration not sorted (DETERMINISM breach).
  • Detection: the apply-then-plan idempotency property test (Phase 12) — the "done" gate; also a post-apply self-check in CI.
  • Automatic recovery: none — this is a correctness bug, not a transient fault; surfaced loudly.
  • Manual recovery: none operationally; the fix is to the engine or provider. Workaround: ignore_changes only if the attr is truly external.
  • Operator actions: capture the offending plan -json + state diff + RPC trace and escalate as a defect.
  • Forensic artifacts: the non-empty Plan with each spurious ResourceChange; before/after Value pair pinpointing the mis-diffed Path.
  • Long-term mitigation: idempotency + plan-determinism property tests in the gate; sorted BTreeMap/BTreeSet iteration; canonical Decimal normalization; convert/unify round-trip tests; differential oracle (F11).

F11 — Differential-oracle divergence vs Terraform

  • Symptoms: the differential test reports iac's Plan for a corpus config differs from Terraform's for the same config + state.
  • Root causes: semantic gap (function behavior, for-expression edge case, unknown propagation, force_new semantics) between iac and the oracle.
  • Detection: Phase 12 differential harness over the config/plan corpus.
  • Automatic recovery: none — test-only; classify each divergence as iac bug, oracle quirk, or accepted deviation.
  • Manual recovery: fix iac or annotate the corpus case as a known/intended deviation.
  • Operator actions: none in production; this is a CI/dev signal.
  • Forensic artifacts: both plans normalized to plan -json, diffed; failing corpus case id.
  • Long-term mitigation: grow corpus from every real divergence; pin oracle Terraform/OpenTofu version.

F12 — Wrong state file / lineage mismatch

  • Symptoms: iac refuses: "state lineage <uuid> does not match expected; refusing to operate".
  • Root causes: pointing at the wrong backend/path; restored a backup from a different stack; copied state between environments.
  • Detection: lineage (Uuid) compared on read; serial regression also rejected.
  • Automatic recovery: none — abort on read, before any mutation (fail-closed).
  • Manual recovery: repoint to the correct backend; if intentional re-lineage, explicit iac state push with confirmation.
  • Operator actions: verify backend config and workspace; never paste another stack's state.
  • Forensic artifacts: expected vs actual lineage/serial; backend path.
  • Long-term mitigation: lineage stamped at state creation, immutable; serial-monotonicity guard; push refuses lineage change without override.

Severity summary: F5 (state corruption) and F10 (idempotency violation) are S0 — the former endangers the only durable artifact, the latter means the engine's headline correctness contract is broken. Both are defended structurally (atomic write + .backup; property tests in the Phase 12 gate) rather than recovered after the fact, because for an engine that drives irreversible infrastructure mutations, a wrong plan is a production incident.

Operational Readiness

Framing: iac is a CLI invoked by an operator/CI, not a daemon. Observability targets the run (one plan/apply invocation) and the fleet (many runs aggregated by a platform team). No always-on metrics endpoint — runs emit structured events to stdout/stderr + an optional sink; a CI scraper or platform pipeline aggregates them.

N.2 Tracing (the tracing crate)

  • One root span per invocation: iac.run{op, run_id, config_hash, state_serial}. run_id = ULID generated once, threaded everywhere.
  • Span hierarchy: iac.run → iac.phase{name=parse|eval|graph|refresh|plan|apply} → iac.resource{addr, action} → iac.rpc{provider, method, rpc_id}.
  • One span per resource per operation; addr = ResourceAddress display form (module.x.aws_s3_bucket.b["k"]).
  • Correlation: rpc_id = run_id + monotonic seq, attached to the child-process RPC frame header (Phase 6 protocol) so provider-side logs join engine-side spans. Provider may echo rpc_id in its Diagnostics.
  • Sinks: default human (tracing_subscriber fmt, level via RUST_LOG/-v); -json swaps to a JSON event layer (one object per line, NDJSON). Span enter/exit + the final metrics record share the stream.
  • Sampling: none in plan/apply (every resource matters); RPC-internal byte-level frames at TRACE only.

N.3 Logging philosophy

  • Machine-readable first: -json produces a stable event schema ({"type":"resource_change"|"apply_progress"|"diagnostic"|"metrics", ...}) consumed by CI; the human renderer is a view over the same events, never a separate code path.
  • Secrets always redacted: any Value::Sensitive (or value flowing from a sensitive provider Attribute / variable) renders as (sensitive value) in every sink — plan output, -json, span fields, error detail. Redaction is enforced at the Value Display/serialize boundary, not by ad-hoc string scrubbing → a new sink cannot leak.
  • Log levels: ERROR = a Diagnostic{severity: Error} that fails the run; WARN = drift/deprecation; INFO = phase transitions + per-resource action; DEBUG = RPC summaries; TRACE = frames/bytes.
  • No wall-clock or RNG values appear in -json resource_change records (only in metrics) → keeps plan output diffable.

N.7 Deployment & distribution

  • Engine: single static binary iac (musl target for portable Linux CI; signed release artifacts + SHA256SUMS). No runtime deps; MSRV 1.78 build.
  • Providers: out-of-process plugin binaries, fetched by iac init from a registry into .iac/providers/<host>/<ns>/<name>/<version>/<os>_<arch>/. Verified against the lockfile before exec (Phase 6 installer/registry).
  • Provider lockfile .iac.lock (committed): pins each provider to version + per-platform hash:
provider "registry.local/builtin/null" {
  version     = "1.4.0"
  constraints = "~> 1.4"
  hashes      = ["h1:9b...e2", "h1:7c...aa"]   # one per os_arch
}

init writes/updates it; plan/apply refuse to run if an installed provider's hash is absent or mismatched → supply-chain integrity. The built-in reference provider ("null"/"local") needs no download.

N.8 Backend & state-migration lifecycle

  • State.version = the document schema version (engine-owned); ResourceInstance.schema_version = provider resource schema version.
  • Engine upgrade: on read, if State.version < CURRENT, run the ordered migration chain; back up first → .iac/state.<old_serial>.backup before any rewrite; bump version, preserve serial/lineage; write atomically. Never auto-migrate without a backup.
  • Provider upgrade: if installed provider's resource schema version > ResourceInstance.schema_version, the provider's state-upgrade path runs during refresh; engine stamps the new schema_version.
  • Backend swap (local ↔ remote-stub): iac state pull → snapshot; reconfigure backend; iac state push (refuses on lineage mismatch unless -force). Migration is opt-in, lock-guarded, and always preceded by a backup.
  • Downgrade is unsupported (newer version on older iac ⇒ hard error, no silent truncation).

Compatibility Guarantees

Defines what the engine promises across versions. Six surfaces: config language, state format, provider plugin protocol, CLI + JSON output, crate API, MSRV — plus the differential-parity guarantee vs pinned Terraform. Driving rule: an iac minor upgrade never breaks a passing apply; a major upgrade may, with a migration path and one minor cycle of deprecation warnings.

25.1 Versioning model

Surface Scheme Owner crate "Breaking" means
iac binary (CLI + JSON) SemVer (engine version) iac-cli removed/renamed flag, changed default, JSON schema field removed/retyped
Config language dated spec snapshot lang-YYYY.MM pinned per engine minor iac-hcl+iac-eval syntax/semantics that re-evaluates an existing valid config differently
State format integer State.version iac-state a new on-disk shape the reader must upgrade
Provider plugin protocol integer protocol_version iac-provider wire/handshake/schema-semantics change
Crate APIs (iac-*) SemVer per crate each per Rust SemVer (RFC 1105)
Toolchain MSRV 1.78 workspace raising MSRV

Engine version, lang snapshot, max State.version, and protocol_version range are emitted by iac version -json and recorded in every written State (provenance, for "wrong-tool" diagnostics).

25.2 Configuration-language compatibility

  • Pinned snapshot: each engine minor pins one lang-YYYY.MM. The lexer/parser grammar and iac-eval semantics for that snapshot are frozen; a config valid + accepted under lang-2026.05 parses and evaluates identically under any later engine pinning a >= snapshot.
  • Additive evolution: new Function registry entries, new built-in Expression forms, new Type constructors → additive only. Never repurpose an existing function name or change its return_type/param_types.
  • Deprecation policy: deprecate → Diagnostic{ severity: Warning } for one full minor cycle (e.g. deprecate in 1.4, removable in 1.5 earliest but only at the next major) → remove only at a major. Warning carries span + replacement guidance.
  • Reserved surface: new keywords/block types are introduced only with a snapshot bump; until then they remain ordinary identifiers, so no existing config gains a parse error from an upgrade.
  • Determinism contract is part of the language: sorted map/object iteration, no wall-clock/RNG in evaluation (the determinism contract). A change here is breaking even if syntax is untouched, because plan bytes change.
  • iac fmt stability: formatting is idempotent and pinned to the snapshot; fmt output may change at a snapshot bump but never alters semantics. CI may assert fmt --check only within one lang snapshot.

25.3 State format compatibility

read(disk State.version = V_disk):
  if V_disk  > V_max(engine)        -> ERROR "state written by newer iac; refusing" (never downgrade)
  if V_disk == V_max                -> use as-is
  if V_disk  < V_max                -> run migrations V_disk -> V_disk+1 -> ... -> V_max
  • Forward-upgrade only: the engine reads any older State.version and upgrades it forward via a registered chain of single-step migrations in iac-state (one fn per N -> N+1). Upgrades are pure, deterministic, and run in-memory before any write.
  • Never silently downgrade: a State whose version exceeds the engine's V_max is a hard error, not a truncation. Prevents an old iac from corrupting a newer state.
  • Upgrade is write-gated: a forward upgrade is persisted only on the next normal atomic StateBackend::write (after lock), with a .backup of the pre-upgrade serial retained → a botched upgrade is recoverable.
  • Stable contracts within state: serial (monotonic, +1 per write), lineage (UUID, immutable for a state's life, identifies "is this the same state lineage"), and ResourceAddress/IndexKey string forms are frozen across versions — state mv/pull/push and lineage mismatch detection depend on them.
  • Migration testing: a golden corpus of every historical State.version ships as fixtures; CI asserts upgrade(v_i) for all i < V_max produces a valid V_max document and that re-reading is a NoOp (idempotent upgrade).

25.4 Provider plugin protocol compatibility

  • Negotiated in handshake: child provider process announces supported protocol_version(s); engine selects the highest mutually supported. Engine guarantees support for protocol N and N-1 (one version of skew), so a provider built for the previous engine minor still loads.
  • No common version → fail closed: explicit Diagnostic naming engine range vs provider range; the provider is never run under a guessed protocol.
  • Schema additions are backward compatible: adding resources/data_sources entries, or adding optional/computed Attributes to an existing Schema, is non-breaking. Adding a required attribute, or flipping an attribute to required, is a breaking schema change (existing configs would fail validate_resource).
  • Semantics are contract: force_new (⇒ Action::Replace) and computed (⇒ Value::Unknown at plan time) are part of the wire contract, not provider-internal detail. A provider may not change an attribute from force_new:false→true without a schema-version bump, because it silently turns Updates into Replaces (destroy of real infra).
  • schema_version ladder: each resource carries a schema_version; a provider raising it must supply an upgrade for prior-version ResourceInstance.attributes, invoked during refresh before diff (mirrors Compatibility Guarantees at the resource grain).
  • Framing/handshake bytes frozen per protocol version: length-prefixed message framing and handshake field layout are fixed for a given protocol_version; changes ride a version bump only.

25.5 CLI flag + JSON-output stability

  • Flags are SemVer'd: within a major, no flag removed/renamed and no default changed. New flags are additive with backward-compatible defaults; -target, -parallelism, -var/-var-file semantics are frozen.
  • plan -json is a stable schema: a documented, versioned envelope { format_version, ... }. Consumers key off format_version; fields are only added, never removed/retyped within a major. ResourceChange/Action serialization ("create"|"read"|"update"|"delete"|"replace"|"no-op") and (known after apply) rendering of Unknown, plus redaction of Sensitive, are part of the contract.
  • Same JSON guarantee for show -json, state list, output -json, validate -json, graph output.
  • Exit codes frozen: 0 success/empty plan, 1 error, 2 (plan) "diff present" — stable for CI gating.
  • Human (non--json) output is NOT a stability surface — explicitly free to change; scripts must use -json.

25.8 Differential-parity guarantee vs pinned Terraform

25.6 Chaos suite

  • Kill mid-apply: SIGKILL engine after K of N resources applied ⇒ on restart, State is old-or-partially-advanced-but-valid (never torn), .backup present, serial consistent, lock reclaimable.
  • Kill provider plugin mid-RPC ⇒ engine surfaces Diagnostic, defers dependents, no state corruption.
  • RPC timeout injection ⇒ provider-call timeout fires, retry policy applies, bounded.
  • Provider-inconsistent-result (apply returns ≠ planned non-computed attr) ⇒ hard error, resource not silently accepted (Terraform "produced inconsistent result").
  • Corrupt + restore state (truncate / bad serial / wrong lineage) ⇒ refuse with diagnostic, never auto-overwrite.
  • Concurrent run ⇒ second acquirer blocked by StateLock; force-unlock path tested.

25.7 Deterministic replay

  • Saved binary Plan re-applied later ⇒ identical Action sequence; stale-plan detection (prior-state serial moved) ⇒ refuse to apply.
  • Record/replay of provider RPC transcripts ⇒ planning reproducible offline (CI hermetic, no network).

Provider Plugin Distribution

  • Providers are out-of-process plugins (Phase 6 RPC), distributed independently of the iac binary — mirrors Terraform's registry + go-plugin model.

provider "registry.example/null" {
  version     = "3.2.1"

IO amplification: per-resource vs batched state writes

  • Naïve incremental: N resources → N atomic writes (temp+fsync+rename) of the whole state → O(N × |state|) bytes written; 1k resources × 10 MB = 10 GB write amplification. Unacceptable.
  • Mitigation: in-memory State is authoritative during apply; persist on a coalescing cadence — every K resources or T ms (default K=20, T=2 s), plus a guaranteed flush on completion/cancel/error. Each flush still atomic (temp+fsync+rename, .backup of prior serial).
  • Crash-consistency preserved: a flush is all-or-nothing; between flushes, redoing un-flushed Create/Update is idempotent (idempotency invariant). Tradeoff: bounded re-work on crash vs write amplification — K/T tunable.
  • Single-writer invariant unchanged; coalescing only reduces flush frequency, not concurrency of writers (still one).

Serialization cost of large states

  • Format: JSON (Terraform-compatible) via serde_json; 100 MB / 50k instances → naïve full parse ≥300 ms + 3× peak heap.
  • Mitigations: (1) stream-deserialize buckets, decode attributes: Value lazily (only resources touched by plan); (2) write via buffered+BufWriter over the temp file; (3) optional length-prefixed binary backend behind StateBackend for remote-stub (faster, non-portable).
  • Targets (§4): 10 MB read ≤40 ms / write ≤60 ms; 100 MB stays linear (≤400 ms read).

  • Walker runs independent nodes concurrently up to -parallelism (default 10) — wide graphs finish in ceil(W/P) rounds.
  • Deep chains are the hard floor: a length-D reference chain costs ≥ D·RPC regardless of P. Critical-path latency dominates; widening parallelism gives zero speedup once P ≥ W.
  • Mitigation for depth: break artificial chains (don't reference an attr you don't need → fewer edges → flatter graph → more parallelism). force_new churn deepens effective work (Replace = delete+create on critical path).

Cost vs. state size (central bottleneck)

Op Complexity Frequency
StateBackend::read (deserialize) O(instances · attrs) once/op
StateBackend::write (serialize + temp+fsync+rename + .backup) O(instances · attrs) incremental during apply
In-mem lookup by ResourceAddress O(1) amortized (indexed) per node
  • State is single-writer (PERSISTENCE + CONCURRENCY boundary): every incremental write during apply re-serializes the whole document → O(N) per write, O(N²) over an apply touching N instances if naively flushed each node. Mitigation: batch/coalesce writes, fsync at safe checkpoints, debounce; correctness floor = a valid checkpoint after each successful provider mutation.
  • This is the scaling ceiling for very large monolithic workspaces: a 50k-instance state file (~tens of MB JSON) makes each read/write tens-of-ms to low-seconds and serializes all ops on the one lock.
  • Mitigations (in order): (1) split one giant config into smaller workspaces, each with its own smaller state + independent lock — linear reduction in per-op state cost and lock contention; (2) keep state lean (avoid storing huge computed blobs); (3) deferred: a remote backend with finer-grained / per-resource locking + state sharding (the horizontal-scaling path).

Cost vs. provider RPC fan-out (the real ceiling)

  • N managed resources ⇒ refresh = N read_resource calls; plan = N plan_resource; apply = up-to-N apply_resource. Wall-time is RPC-bound, not CPU-bound.
  • -parallelism caps concurrent in-flight RPCs (protects provider + remote API rate limits). Effective throughput = min(parallelism, provider_concurrency_limit) / RPC_latency.
  • Ceiling: slow or rate-limited providers. A 200 ms-per-call provider at P=10 ⇒ ~50 resources/s ⇒ 10k resources ≈ 200 s of pure RPC even fully parallel.
  • Mitigations: raise -parallelism (until provider/API rate-limits bite, then retries/backoff in Phase 11 cost more than they save); provider-side batching (one RPC mutating many objects — provider's responsibility, engine just issues fewer calls); reduce churn (fewer force_new Replaces → fewer create+delete pairs).

count / for_each expansion blow-up

  • NodeExpander materializes one node per index key: count = n → n nodes; nested for_each over a k-element map inside m instances → m·k. Graph V and memory grow with the product, not the sum.
  • Risk: an accidentally large or computed-then-large collection explodes V → graph build, walk, and per-node state writes all scale up.
  • Guards: cap on expanded instance count (configurable, warn → error); count/for_each over an Unknown collection is deferred (cannot expand at plan time → shown "known after apply", expanded at apply) — prevents unbounded plan-time expansion on computed sizes.

Deferred horizontal-scaling path

Single-process, single-state, single-writer is the v1 design — correctness over throughput. The horizontal path (out of scope now, cross-link the remote backend stub in iac-state): a remote StateBackend with finer-grained locking, per-resource or per-module state sharding, and concurrent applies across disjoint shards. This lifts both the single-writer state ceiling and the one-host memory ceiling, at the cost of cross-shard consistency machinery — deferred until the monolithic engine is proven idempotent and crash-consistent (Phase 11/12 gates).

Six compressed expert models that predict behavior, explain bugs, and anchor every phase.

MM1 The three-way diff is the frame — every Action comes from comparing exactly three inputs: prior State (P), refreshed reality R = read_resource(P), desired config C. When all three agree, it's NoOp; when P≠R, it's drift; when C≠R, it's a planned change. If you conflate any two legs, you mis-categorize Actions. The .backup must be written BEFORE the rename to guarantee a recovery copy always exists. MM4 The walker is a topological processor with a semaphore — graph execution is not "run nodes concurrently"; it is "a reverse-topological BFS where each node's readiness is its in-degree reaching zero, bounded by a semaphore(P)". The ready-queue is populated by decrementing in-degree on each completed node; the semaphore caps concurrent inflight. A deferred (failed) node must also decrement its dependents' in-degree (as "skipped") or the queue deadlocks. Correct -parallelism modeling; partial-failure deadlock analysis Not decrementing deferred-node dependents' in-degree → queue drain stalls → apply hangs with some nodes never visited (observed symptom: apply exits 1 but never reports N of the expected nodes) §16 (Phase 4), §20 (Apply), §7 I2
MM5 Sensitive is a monotone privacy mark, not encryption — Sensitive(v) means "this value must not appear in any output sink". It is monotone: any expression combining a Sensitive operand produces a Sensitive result. It propagates through collection ops, functions, templates. It is NOT at-rest encryption. The state file stores the raw value wrapped in Sensitive; redaction happens only at the output boundary (plan render, log formatter, RPC response). A new output sink that bypasses the redaction boundary leaks all marks at once. Leak-free output design; new sink threat model Adding a diagnostic serializer that formats Value via Display (not the redaction-aware formatter) → a Sensitive password appears in a structured log line. The symptom doesn't appear in any existing test because the new sink is untested. §6.9 (Sensitive invariant), §14 Phase 2, T5 (Threat T5)
MM6 Idempotency is an emergent property, not a single assertion — apply(plan) → fresh plan = all-NoOp holds iff three independent sub-properties all hold simultaneously: (1) the diff is stable (same inputs → same Action, every time — DETERMINISM); (2) every successful mutation is recorded in state before the run ends (PARTIAL-VALID); (3) read_resource then plan_resource round-trips through the engine's convert/normalize losslessly (PROVIDER NORMALIZATION). Any one failure breaks idempotency. Debugging an idempotency violation requires determining which of the three sub-properties failed first. Root-cause isolation for idempotency violations Debugging "phantom Update after apply" by only checking the diff logic (sub-property 1) while the real cause is provider returning a reordered set that the diff sees as changed (sub-property 3 normalization failure) §7 I7, §19 (Plan), §20 (Apply), §24 (Phase 12 gate)

Terraform/OpenTofu made exactly the same core architectural choices as this project — the design is deliberately a Rust reimplementation of the same semantics. The key difference is implementation language: Go's nil-interface footguns on the plan hot path (where a ResourceChange.After that is a non-nil interface holding nil would silently bypass a nil-check) are replaced by Rust's Option<Value> exhaustive match. The differential testing in Phase 12 turns this design equivalence into a concrete correctness gate.

Pulumi chose a radically different front-end: instead of a declarative config language, a general-purpose program constructs the resource graph at runtime. This eliminates the entire iac-hcl/iac-eval stack and replaces it with a language SDK. The downside is that the resource graph is not statically analyzable before execution (no plan without running the program), and the config is not diffable as text. Pulumi wins in teams that need full programming-language expressiveness (loops over SDK-returned data, complex conditionals, library reuse) — this engine deliberately rejects that model to keep the declarative guarantee.

AWS CloudFormation is the reference for the "plan as a saved, reviewable artifact" concept (change sets). It wins in all-AWS deployments where native integration with IAM, CloudTrail audit logs, drift detection, and stack-event history is more valuable than provider-agnosticism. Its fundamental limitation — operator cannot directly access or modify state — removes the entire state mv/rm/pull/push surface, which is a strength (no footguns) and a weakness (no escape hatch for misconfigured state).

Kubernetes controllers embody the continuous-reconcile model: there is no plan artifact, no apply command, no idempotency property that must be proven via testing. Idempotency is guaranteed structurally by the level-triggered loop (the controller always re-reads desired and observed state and derives the minimum delta). The controller wins when the desired state is continuously evolving (autoscaler, operator managing a stateful app) and the cost of a "missed event" must be zero. This engine wins for one-shot provisioning where the operator needs to see and approve the exact change set before mutation.

Back-of-Envelope Capacity Model

Six numbers derived step-by-step from the System Constraints (§4). All reference-provider (no network) unless stated; real-provider numbers are RPC-latency dominated.

C1 — Config parse throughput (§4.2 target: 5k resources < 2 s)

Assume: 50 tokens/resource × 5 bytes/token = 250 bytes/resource
5k resources → 5k × 250 B = 1.25 MB config

Lexer target: 50 MB/s (Compatibility Guarantees bench gate)
→ 1.25 MB / 50 MB·s⁻¹ = 25 ms lex time

Parser is O(tokens); parser target ≥ 10 MB/s
→ 1.25 MB / 10 MB·s⁻¹ = 125 ms parse time

Total parse: 25 + 125 ≈ 150 ms  ✓ (well within 2 s target)

C2 — Evaluation memory per resource (§4.2 target: < 512 MB at 10k resources)

Per resource (evaluated config):
  ~20 Attributes × (8 B key + 32 B Value avg) = ~800 B config values
  + ~5 graph edges × 16 B per NodeId pair = 80 B

Per ResourceInstance in state:
  ~20 Attributes × 40 B each (serde overhead) = 800 B
  + dependencies Vec: ~5 × 24 B = 120 B
  + overhead (status, index_key, schema_version) = 32 B
  → ≈ 1 KB per instance (matches §4.2 "< 4 KB" target)

10k instances: 10k × 1 KB = 10 MB state values
+ Graph (NodeId u32 × 10k nodes + 40k edges × 8 B) = 40 + 320 KB ≈ 360 KB
+ Plan (before+after per change, ~2 × 10k × 1 KB) = 20 MB worst-case (all-Create)

Total: ≈ 30 MB resident for a 10k-resource all-Create plan
→ 512 MB target leaves 480 MB headroom for serde/AST allocations ✓

C3 — State file size at 10k resources (§4.2 target: state write < 50 ms)

Per ResourceInstance JSON (serde_json, sorted keys):
  ~20 attrs × (10 B key + 20 B value + 4 B punctuation) ≈ 680 B
  + wrapping JSON overhead = ~320 B
  → ≈ 1 KB/instance

10k instances: 10 KB × 1 KB = 10 MB state file (matches §4.2 "10 MB State" row)

Disk write: modern SSD sequential write ≈ 500 MB/s
10 MB / 500 MB·s⁻¹ = 20 ms write
+ fsync latency (SSD barrier): ~5–15 ms
+ rename + dir-fsync: ~1 ms
→ Total atomic write: 20 + 10 + 1 ≈ 31 ms  ✓ (< 50 ms target)

C4 — Apply wall-clock at -parallelism=10 with real cloud provider (§4.2 provider RPC = 30 s timeout)

Assume: 1000 resources, fully independent (wide graph, depth=1), RPC latency = 1 s avg

Rounds = ceil(1000 / 10) = 100 rounds
Each round: 10 resources × 1 s (apply_resource) ≈ 10 s/round
Total apply: 100 rounds × 10 s = 1000 s ≈ 17 min

With depth D = 10 (chain of 10 dependencies):
  Chain cost: 10 × 1 s = 10 s (serialized, parallelism can't help)
  Wide cost: ceil((1000 - 10) / 10) × 1 s = 99 s
  Total: 109 s ≈ 2 min

Lesson: depth dominates; flattening the graph (removing unnecessary force_new or reference
chains) from D=100 to D=10 cuts apply time from ~120 min to ~12 min with the same providers.

C5 — Semaphore / Walker scheduling overhead (§4.2 target: < 100 ms engine overhead/resource)

Per-resource engine cost (non-RPC): diff + state-write dispatch + semaphore acquire
  Diff: O(attrs) = 20 attrs × ~1 µs each = 20 µs
  Semaphore acquire (uncontended): ~50 ns
  State write dispatch (chan send): ~200 ns
  Total non-RPC per resource: ~21 µs

1000 resources × 21 µs = 21 ms total engine overhead
→ Engine overhead fraction of 1000-resource apply: 21 ms / (1000 s RPC) = 0.002%
→ Well within ≤ 200 µs/resource target and "≤5% engine fraction" goal ✓

C6 — FD budget at maximum -parallelism=256 (§4.6 target: bounded resources)

Per provider child process:
  1 unix socket (2 FDs: one per side) + 3 stdio (stdin/stdout/stderr) = 5 FDs

One provider binary reused for all resources of that type.
Assume 10 distinct providers × 5 FDs = 50 FDs for provider connections

Walker semaphore: does NOT create an FD per node — it controls scheduling, not processes
State lock: 1 FD (lock file) + 1 FD (state file) + 1 FD (tmp file during write) = 3 FDs

Total FD budget: 50 (providers) + 3 (state) + 10 (misc: log, config files) = 63 FDs
Default OS limit: 1024 FDs (ulimit -n)
Headroom: 1024 - 63 = 961 FDs → no FD exhaustion even at full parallelism ✓

Risk: if each provider spawns a NEW child per RPC (not reused), 256 × 5 = 1280 FDs > limit.
This is why ADR-17 / §18 mandates ONE persistent provider process per provider type.

Alternative Architectures (Roads Not Taken)

Four fundamentally different architectures for the same problem. Not parameter tweaks — different structural choices.

Alt-1 — Continuous reconcile loop (Kubernetes controller model)

    Config in etcd/API server
          │
    Controller watches for changes
          │
     Read current state (list/watch infra API)
          │
     Compute delta (desired minus observed)
          │
     Apply delta (partial, best-effort)
          │
     Write status back to API server
          └── loop forever (level-triggered)

Winning regime: continuously evolving desired state; infra that self-heals and must converge without operator intervention; systems where "an apply that missed 3 resources" is fine because the loop will correct it on the next tick. Kubernetes itself, AWS Controllers for Kubernetes (ACK), and CrossPlane all use this model.

Real system: CrossPlane — applies Kubernetes controller machinery to cloud resources; each provider is a Kubernetes controller, each resource is a CRD.

Why rejected: this engine targets one-shot provisioning where an operator reviews a plan and approves it. A continuous loop cannot provide a "show me exactly what will change before I approve" guarantee. There is no plan artifact that a human or CI gate can inspect. More critically, for irreversible mutations (database deletion, VPC destruction) a level-triggered controller that immediately acts on a desired-state diff is dangerous without the plan/approve barrier. The plan/apply split is the architectural answer to "irreversible + expensive mutations" — the continuous loop trades that safety for convergence speed.

Alt-2 — General-purpose language SDK (Pulumi model)

    TypeScript/Python/Go program
          │ calls SDK resource constructors
          │ (resource("aws:s3:Bucket", name, args))
          v
    Resource graph constructed at runtime (program execution)
          │
    Engine serializes resource registrations → snapshot
          │
    Diff snapshot vs prior → changes
          │
    Apply changes via providers

Winning regime: config that is genuinely Turing-complete — loops over dynamically-fetched data, conditional resource creation based on external API responses, library/module reuse via the host language's package manager. Teams where infrastructure authors are software engineers comfortable with TypeScript/Python, and the overhead of learning HCL-like syntax is higher than the overhead of learning the SDK.

Real system: Pulumi (TypeScript/Python/Go/Java/C#/.NET SDKs).

Why rejected: this engine deliberately takes the declarative position. A config program can read files, make HTTP calls, call arbitrary functions — making it impossible to statically analyze the resource graph before execution. There is no plan without running the program. The declarative constraint (*.iac config has no side effects beyond file reads in templatefile()) enables: (1) a parse-only validate pass, (2) a plan that is byte-deterministic without executing any infra, (3) a diff that is a static analysis of text changes. These properties are the anchor of the audit + review workflow.

Alt-3 — Server-side managed state (CloudFormation model)

    Operator submits template to CloudFormation API
          │
    CloudFormation service stores and manages state server-side
          │
    CloudFormation computes change set (optional preview)
          │
    CloudFormation executes (concurrently, with rollback)
          │
    Operator queries stack events for status

Winning regime: all-AWS deployments where native IAM integration, CloudTrail audit logging of every stack event, automatic rollback on failure, and no operator-managed state files are more valuable than provider-agnosticism or custom state manipulation. Organizations that cannot allow engineers to directly access or modify state files (compliance/SOC2 requirement).

Real system: AWS CloudFormation; Azure Resource Manager (same model for Azure).

Why rejected: (1) provider-agnosticism — this engine orchestrates any provider via the plugin RPC; CloudFormation is AWS-only. (2) state access — CloudFormation hides the state from the operator, making state mv, state rm, and import scenarios require workarounds. (3) rollback model — CloudFormation attempts a full rollback on failure; this engine's partial-state model (taint + re-plan) is more transparent. (4) cross-resource unknowns — CloudFormation's !Ref/!GetAtt function does not propagate an Unknown type through the template; it simply defers the value, with less expressibility than Value::Unknown(Type).

Alt-4 — Embedded scripting engine (Jsonnet/Starlark model)

    *.jsonnet / *.star config files
          │
    Embedded interpreter (pure, deterministic, sandboxed)
    evaluates to a JSON/dict structure
          │
    JSON structure describes resources
          │
    Engine diffs JSON tree vs prior state
          │
    Engine calls providers

Winning regime: configs that need programmability (loops, functions, imports) but must remain deterministic and auditable; templating at scale where HCL-like syntax is too limiting but a full host language SDK (Alt-2) is too opaque. Jsonnet is used by large Kubernetes configuration pipelines (Tanka, qbec); Starlark is used by Bazel build rules.

Real system: Tanka (uses Jsonnet to produce Kubernetes manifests); Dhall (typed functional config language, similar idea).

Why rejected: an embedded scripting language adds a full language runtime as a dependency (interpreter complexity, security surface, evaluation semantics to specify). More importantly, Jsonnet/Starlark evaluate to a static JSON tree — they do not support Unknown(Type) semantics. You cannot express "this value is known after apply" in a Jsonnet evaluation; the Unknown propagation that drives the "(known after apply)" in the plan is a first-class concept in this engine's value lattice, not a post-evaluation annotation. That makes Jsonnet/Starlark unsuitable as a drop-in config front end without losing the Unknown-aware planning model.

Glossary

Term Definition (implementation-relevant)
configuration / config The *.iac source: blocks + attributes parsed by iac-hcl into a Body, then evaluated by iac-eval. The desired leg of the three-way diff. Untrusted input — crosses the trust boundary.
resource A provider-managed real-world object (ResourceMode::Managed) declared by a resource "ty" "name" {} block. Has lifecycle: Create/Read/Update/Delete via the Provider CRUD methods.
data source A read-only external lookup (ResourceMode::Data); never mutates infra. Refreshed via read_resource, contributes values to other resources, produces only Action::Read.
managed resource A resource whose lifecycle the engine owns (vs a data source it merely reads). Eligible for Create/Update/Delete/Replace.
provider An out-of-process plugin implementing the Provider trait; orchestrated, not implemented, by the engine (non-goal: being a cloud). Exposes a ProviderSchema; runs as a child process over the plugin RPC.
provider schema ProviderSchema { provider, resources, data_sources } — declares each type's Schema (attributes + blocks), driving validation, type checking, and the diff. Negotiated at handshake.
attribute A typed field of a resource: Attribute { ty, required, optional, computed, sensitive, force_new }. Also iac-hcl's config Attribute { name, expr, span }.
nested block A NestedBlock schema entry — a repeatable/structural sub-block within a resource (e.g. ingress {}), distinct from a scalar/collection attribute.
computed attribute An Attribute with computed: true — the provider fills the value, so it is Value::Unknown(ty) during planning ("known after apply").
force_new / requires-replace Attribute.force_new: true — changing it cannot be done in place; the diff must Replace (delete+create). PlannedChange.requires_replace: Vec<Path> / ResourceChange.requires_replace carry the offending paths.
plan Plan { changes, output_changes, prior_state, variables, applyable } — the minimal ordered set of actions to reconcile reality to config. Output of the Plan engine (Phase 7); input to Apply (Phase 8).
the diff The per-resource comparison producing an Action; the engine-wide diff is the three-way diff.
three-way diff Compares (a) prior state, (b) refreshed reality (read_resource), (c) desired config. NoOp if all agree; Update if changed attrs are non-force_new; Replace if any changed attr is force_new; Create if no prior; Delete if in state but not config.
ResourceChange { address, action, before, after, requires_replace, deposed } — one resource's planned transition; the unit of the Plan and the unit Apply executes.
Action enum Action { NoOp, Read, Create, Update, Delete, Replace { create_before_destroy: bool } } — exhaustive set of per-resource operations.
create-before-destroy A Replace ordering: provision the new instance before destroying the old to avoid downtime. The old becomes deposed until the new is healthy. Flag on Action::Replace.
deposed InstanceStatus::Deposed(DeposedKey) — an old instance kept alive during a create-before-destroy Replace, destroyed after the replacement succeeds; tracked so a crash can still clean it up.
tainted InstanceStatus::Tainted — an instance whose Apply partially failed or is user-marked bad; the next plan forces its Replace.
refresh Calling read_resource(ty, prior) to update prior state with observed reality before diffing; the (b) leg of the three-way diff. Phase 7 / refresh-only plan (Phase 10).
drift Divergence between state and refreshed reality (out-of-band change). Surfaced by refresh; the diff plans corrective actions.
state State { version, serial, lineage, resources, outputs } — the only durable artifact; the single source of truth, written atomically and behind a lock by iac-state.
serial State.serial: u64 — monotonically increasing write counter; a stale serial signals a lost update; bumped on every successful write.
lineage State.lineage: Uuid — identity stamp created with the state; a mismatch means "wrong state file" and aborts the operation.
state lock StateLock / StateBackend::lock(LockInfo) -> LockId — mutual exclusion guarding a write; held with heartbeat; unlock/force-unlock release it. State is single-writer.
backend StateBackend implementer (local; remote-stub) abstracting state read/write/lock; write is atomic (temp + fsync + rename + .backup).
ResourceAddress { module: ModulePath, mode, ty, name } — canonical identity of a resource (plus IndexKey for instances); printed as module.x.aws_s3_bucket.y["k"]; used by state, targeting, and state mv/rm.
module A reusable config unit (its own Body + variables/outputs) instantiated via a module-call block; expanded by iac-core's loader into the module-call graph.
module instance One expansion of a module call (a count/for_each index); contributes a ModulePath segment to descendant ResourceAddresses.
count Meta-arg producing N indexed instances keyed by integer IndexKey; expanded by the NodeExpander. Under Unknown count → expansion deferred.
for_each Meta-arg producing instances keyed by map/set string IndexKey; NodeExpander materializes one node per key; stable, order-independent addressing.
index key Option<IndexKey> on a ResourceInstance — the count integer or for_each string distinguishing instances of one address.
NodeExpander The iac-core component turning a single configured node into 0..N graph nodes per count/for_each, assigning ResourceAddress index keys (Phase 9).
dependency graph Graph<N> (iac-graph) of resource nodes; edges = dependency→dependent extracted from references; cycle-checked (Tarjan SCC) and transitively reduced.
reverse-topological walk Graph::walk(parallelism, visit) order: dependencies before dependents on apply (from leaves), reversed on destroy. Independent nodes run concurrently; errors defer dependents and aggregate.
-parallelism CLI flag bounding concurrent provider RPCs in the Walker; the concurrency boundary. State remains single-writer regardless.
reference An expression pointing at another object's attribute (e.g. aws_vpc.main.id); the reference extractor mines these to build graph edges.
traversal enum Traversal { Attr(String), Index(Expression), LegacyIndex(u64) } — the steps of a ScopeTraversal expression (a.b[0].c) navigated during evaluation.
Value lattice The Value sum type (Null/Bool/Number/Str/List/Set/Map/Object/Tuple/Unknown/Sensitive) ordered by knowledge: a concrete value refines Unknown; Sensitive wraps and propagates.
Unknown value / known-after-apply Value::Unknown(Type) — a not-yet-computed value during planning; any expression touching it yields Unknown; rendered "(known after apply)"; never compares equal to a concrete value; resolved top-down at apply.
Sensitive value Value::Sensitive(Box<Value>) — a privacy mark (from sensitive attrs/vars) that propagates through expressions and is redacted in plan output and logs.
type conversion / unification convert(v, &Type) coerces a Value to a target Type (cty convert); unify(&[Type]) -> Option<Type> finds a common type (e.g. for tuple→list, conditional arms).
EvalContext EvalContext<'a> — the evaluation scope: variables, locals, each/count scope, the Function registry, and path; passed to evaluate.
Function The Function trait (name, call, param_types, return_type) — a registered callable (string/numeric/collection/encoding/hash/filesystem) invoked by Expression::FunctionCall.
for-expression Expression::ForExpr — [for k,v in coll : expr if cond] (and object form); evaluated deterministically with sorted iteration over maps/objects.
dynamic block A meta-construct generating zero+ nested blocks from a collection at eval time; expanded in Phase 3 before graph build.
provider plugin protocol The typed RPC (iac-provider) over a child process: handshake → schema negotiation → framed protobuf-ish messages carrying validate/plan/apply/read/import.
handshake The startup negotiation establishing protocol version + transport with a freshly launched provider child process before any CRUD RPC.
idempotency The headline property: apply(plan) then a fresh plan against the new state yields an all-NoOp plan when reality is unchanged. Gated in Phase 12.
target (-target) CLI flag pruning the graph to a chosen ResourceAddress (and its dependencies) for a partial plan/apply (Phase 10).
import import_resource(ty, id) -> Vec<ImportedResource> — adopting pre-existing infra into state without recreating it (Phase 10).
output A State.outputs entry / OutputChange in the plan — a named, exported computed value; may be Sensitive.
Diagnostic Diagnostic { severity, summary, detail, span } — the structured error/warning carrier from lexing through apply; aggregated (never panicked) across the pipeline.
