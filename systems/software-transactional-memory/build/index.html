⬜ Phase 0 — Repo Skeleton & Correctness Kernel §12

Objectives
  • Stand up the workspace skeleton (§10) and CI scaffolding.
  • Land TVar<T> and Tx as single-thread-correct types with no real concurrency (a placeholder World with one thread).
  • Establish the documentation trio (README, CONTRIBUTING, SECURITY) and license files (ADR-17).
Deliverable

A compiling workspace; cargo test runs the smoke test green; CI (ci.yml) runs build + clippy + fmt on every push; four ADR files exist under docs/adr/.

Acceptance
  • cargo build --workspace succeeds with zero warnings under clippy --deny warnings.
  • Smoke test smoke_counter_increment passes 100/100 runs.
  • cargo deny check passes (license + advisory check, ADR-17).
  • Repository tree matches §10 exactly, verified by scripts/check-layout.sh.
Fixtures
  • single-tx/smoke-counter.json — one TVar<u64>, ten sequential increments, expected final value 10.
  • single-tx/malformed-missing-field.json — a fixture missing the expected key; the runner must reject it with a parse error, not a panic.
Pitfalls
  • Standing up eight empty crates invites premature abstraction; keep every crate's public surface to the minimum §11 signatures until a later phase needs more.
  • cargo-deny's default config is stricter than expected; pin the license allowlist to Apache-2.0/MIT explicitly in deny.toml before it blocks CI on transitive dependencies.
  • Wiring CI before real concurrency exists risks a false sense of completeness; loom.yml/shuttle.yml should be added but marked non-blocking until Phase 2 lands real commit logic.

⬜ Phase 1 — TVar & Transaction-Context Primitives §13

Objectives
  • Give TVar<T> its real layout: AtomicPtr<T> value + packed version-and-lock word (§8.3, ADR-19).
  • Give Tx a real read/write-set discipline (§8.2) with no commit protocol yet (that is Phase 2, §14).
  • Establish TVarId stability (I6) as the heap address of Inner<T>.
Deliverable

tx.read on a fresh TVar returns its constructor value; tx.write followed by tx.read in the same transaction returns the buffered write, not the shared value; a TVar's vlock layout passes a static-size assertion (size_of::<AtomicU64>() == 8).

Acceptance
  • Conformance fixture single-tx/read-after-write.json passes: write 42, read back 42, without touching the shared AtomicPtr (verified by an instrumented counter asserting zero shared-state reads after the write).
  • size_of::<Inner<u64>>() <= 64 bytes (M-adjacent target from §4, one cache line).
  • 10,000 TVar::new/drop cycles under Miri report zero UB.
Fixtures
  • single-tx/read-after-write.json — write then read, expects the buffered value.
  • single-tx/tvarid-stability.json — 1,000 TVars allocated under memory pressure; asserts no TVarId collision or drift.
  • single-tx/malformed-double-write.json — two writes to the same TVar in one tx; expects last-write-wins, not an error.
Pitfalls
  • The TVar id is the address of the Inner<T> box; Inner<T> must never be moved (e.g. via Vec reallocation) — always heap-allocate through Arc (ADR-03), never inline in a growable container.
  • Packing version + lock-bit in one AtomicU64 (ADR-19, §8.3) is easy to get wrong on the shift direction; a fixture (tvarid-stability.json) and a doc comment pin the exact bit layout.
  • Reading value before vlock (wrong order) can observe a value newer than the version recorded — always load vlock first if a strict pairing is required by a future paranoid-mode check (§18.6).

⬜ Phase 2 — TL2 Commit Protocol §14

Objectives
  • Implement the five-step TL2 commit sequence (P2, ADR-02) end to end: lock, allocate version, validate, publish, unlock.
  • Introduce the global version clock (World::clock, I2) and prove I2/I3/I8 hold under loom TC 2–3.
  • Introduce panic-safety via the CommitGuard RAII pattern (§8.7).
Deliverable

A two-thread "transfer between accounts" test (§8.5) runs concurrently under real threads and under loom (TC 2–3) and never observes an inconsistent sum; the commit protocol passes Miri with zero UB.

Acceptance
  • Loom exhaustive search at TC 2 and TC 3 over the transfer fixture: 0 opacity violations, 0 leaked locks (I8), verified via the stm_lock_leak_total counter staying 0 across all enumerated interleavings.
  • 1,000,000-iteration real-thread stress run (16 threads, 100 accounts) preserves the invariant sum(accounts) == initial_sum with zero violations.
  • Commit latency p50 ≤ 400 ns uncontended (M4), measured via stm-bench.
Fixtures
  • two-tx-conflict/transfer-canonical-order.json — the §8.5 worked example, exact expected final balances A=80, B=70.
  • two-tx-conflict/lock-cas-failure.json — forces a CAS failure on the second lock acquisition; expects a clean abort with zero locks held afterward.
  • two-tx-conflict/malformed-negative-version.json — a corrupted fixture asserting a negative observed version; the runner rejects it as malformed input, not a runtime panic.
Pitfalls
  • Lock acquisition must use compare_exchange_strong, not _weak — spurious failures from _weak cause unnecessary aborts under low contention (P1 violation risk).
  • Validation must check both version and lock-bit; a TVar locked by another transaction is in-flight and must abort us even if the version otherwise matches (I3).
  • The sort order on locks must be by TVarId consistently; changing the sort criterion (e.g. to a hash) between two code paths is a deadlock hazard the moment two transactions disagree on relative order.
  • A panic during commit must release acquired locks via CommitGuard's Drop, or I8 is violated the instant any commit-path code can panic (allocator failure, arithmetic overflow in debug builds).

⬜ Phase 3 — Retry & or_else Composition §15

Objectives
  • Implement retry() (§8.1 Retrying→Parked transition) and its wait-set registration (P6, Harris et al. PPoPP 2005, applied here).
  • Implement or_else with lazy evaluation and read-set union semantics (P7).
  • Prove I7 (non-empty read set required) and the wakeup-correctness property under loom.
Deliverable

A "blocking queue" example (producer commits to a TVar<VecDeque<T>>; consumer calls retry() when empty) demonstrates a clean wake on the next producer commit; or_else passes a conformance subset where both branches are non-trivial and read disjoint TVars.

Acceptance
  • Fixture retry/blocking-queue.json: consumer parked on empty queue wakes within one commit cycle of a producer write, verified by a bounded-wait assertion (≤ 10 ms wall-clock in the real-thread test, unbounded-but-deterministic under loom).
  • Fixture or_else/union-readset.json: a wakeup triggered by a change alt1 (not alt2) read still re-runs the whole or_else expression — asserted by the read-set-union invariant (P7).
  • I7 debug-assertion fires (panic) on retry/malformed-empty-readset.json rather than hanging.
Fixtures
  • retry/blocking-queue.json — producer/consumer wakeup correctness.
  • retry/malformed-empty-readset.json — retry() with an empty read set; expects a panic, not a deadlock.
  • or_else/union-readset.json — wakeup sourced from alt1's read set after alt2 also retried.
  • or_else/lazy-evaluation.json — asserts alt2 is never invoked when alt1 succeeds (instrumented call counter).
Pitfalls
  • A retry() whose read set is empty is a permanent deadlock (the transaction will never wake) — the runtime panics on this rather than parking forever (I7).
  • A retry() whose read set is large registers many wakers; the cost is amortized per-TVar but is visible in stm_retry_readset_size telemetry (§26) — documented, not treated as a bug.
  • An or_else whose first branch performs side effects (only possible via unsafe, illegal in STM) leaks the side effects on retry — documented constraint, not runtime-detectable in Phase 0–11.
  • Forgetting to register alt1's read set on a subsequent alt2 retry produces a lost-wakeup bug (FM-4) — the union-read-set fixture (or_else/union-readset.json) exists specifically to catch this regression.

⬜ Phase 4 — Nested Transactions §16

Objectives
  • Implement closed nesting (P8, ADR-07): a nested atomically appends to the outer's read/write sets rather than opening an independent commit point.
  • Prove I9 (nested writes invisible outside the outer chain until outermost commit) under a conformance fixture and loom.
  • Document, but do not build, open nesting (§16.6) as a rejected alternative.
Deliverable

A nested atomically inside another runs to completion and commits as part of the outer transaction, verified by fixture nested/closed-commit.json; a nested retry() correctly propagates to the outermost transaction, verified by nested/propagated-retry.json.

Acceptance
  • Fixture nested/closed-commit.json: an outer transaction containing a nested one, both touching disjoint TVars, commits both sets of writes atomically — verified by an external observer thread that can never see only one side committed (I9).
  • Fixture nested/propagated-retry.json: a nested retry() correctly wakes when a TVar in the outer's read set (not touched by the inner) changes, since the accumulated read set is shared (P8).
  • Nesting depth of 100 (a realistic worst case) does not overflow an 8 MB default thread stack, verified by a stress fixture.
Fixtures
  • nested/closed-commit.json — atomic visibility of combined outer+inner writes.
  • nested/propagated-retry.json — retry propagation through the parent chain.
  • nested/malformed-cycle.json — a fixture attempting a self-referential parent pointer; the runner rejects it at construction (impossible via the safe API, exercised only through the internal test harness).
Pitfalls
  • The nested or_else interacts with the outer's read set (§15); the wait-set registration on a nested retry must include the outer's accumulated reads, not just the inner's.
  • Open nesting is a research topic; shipping it would break the composability property that is this whole project's thesis (§2) — resist the temptation even when a caller asks for independent inner-commit visibility. Design-space note: closed nesting (chosen, ADR-07) means inner writes are not visible to any other transaction until the outer commits; open nesting (rejected) would let the inner commit independently, becoming visible before the outer commits — which breaks composition, since a function written assuming closed-nesting invisibility cannot be drop-in replaced with an open-nesting version (callers depend on I9 to reason about the whole call's atomicity). Open nesting does reduce false-conflict aborts for long-running outer transactions with independent inner sub-transactions, but this project's target workloads (§1) do not have that shape (see §36 for the alternative-architecture sketch).
  • A nested transaction that would (hypothetically, under open nesting) commit internally but whose outer then aborts must roll back the internal commit too — closed nesting sidesteps this entire class of bug by construction, which is the strongest argument for P8.
  • Nesting depth is bounded by stack, not by an explicit counter; a runaway recursive nested-atomically call surfaces as a stack overflow, not a graceful STM-level error (documented in §16.8).

⬜ Phase 5 — Contention Management & Livelock Prevention §17

Objectives
  • Implement the back-off ladder (P9, Felber, Fetzer, Riegel PPoPP 2008 — the TinySTM contention-manager lineage) bounding retry latency after repeated aborts.
  • Implement priority bumping (§17.5) to guarantee I12 (bounded fairness among conflicting writers).
  • Prove livelock-freedom under a 16-thread adversarial stress fixture (M7).
Deliverable

A "two-counter ping-pong" test under 16-thread contention completes in bounded time (every transaction commits within 24 attempts, M7); a livelock-stress fixture confirms no thread starves indefinitely.

Acceptance
  • Abort rate under the 16-thread single-hot-TVar workload ≤ 40%, bounded retries ≤ 24 per transaction (M7, quantified in §4).
  • Priority-fairness fixture priority-fairness.json: no more than one transaction holds priority=true among a mutually-conflicting write set at any sampled instant (I12).
  • The back-off ladder's four tiers are each independently unit-tested against the documented formula (100ns × 2^(N-4), etc.) with a tolerance of ±10%.
Fixtures
  • livelock/two-counter-pingpong.json — 16 threads incrementing two shared counters in alternating order; every thread must commit within the bounded retry ceiling.
  • livelock/priority-fairness.json — asserts I12 under a scripted contention scenario.
  • livelock/malformed-negative-abort-count.json — a corrupted fixture with a negative aborted_count; the runner rejects it as malformed, not a panic in the back-off calculation.
Pitfalls
  • Back-off introduces fairness interaction with cooperative (green-thread/async) scheduling; under the async-aware variant (ADR-12), back-off uses an async sleep primitive rather than blocking the executor thread.
  • Priority bumping can itself create a symmetric livelock if two transactions both reach aborted_count > 16 simultaneously and both try to preempt each other — mitigated by I12's at-most-one-priority-holder-per-conflict-set invariant, but documented as a residual risk requiring the fixture in §17.5 to catch regressions. Protocol detail (Felber et al. 2008's TinySTM contention-manager approach, applied here): (1) on the next commit attempt past aborted_count=16, mark the transaction's header priority=true; (2) when acquiring write-set locks, a priority transaction whose CAS fails inspects the holder's priority flag, and if the holder is not priority, sets the holder's cooperative abort_flag; (3) the non-priority holder, at its next read/write/validation step, observes abort_flag and aborts voluntarily; (4) the priority transaction retries with the contested lock now free — this prevents starvation by giving long-failing transactions the right to preempt short-running ones, at the cost of the one cross-transaction coordination point P9 explicitly permits past the abort threshold.
  • A priority transaction that still fails to commit even after preempting its holder signals a deeper problem (a genuinely hot-spot TVar under sustained multi-writer load) — the runbook (docs/runbooks/livelock.md) documents the diagnostic path, not a further escalation tier.
  • The back-off ladder's constants are workload-calibrated, not universal; document the tuning knob (atomically_with_backoff(custom_ladder)) rather than hard-coding assumptions about the caller's contention profile.

⬜ Phase 6 — Opacity Verification & Model Checking §18

Objectives
  • Implement the opacity oracle (§18.3): a sequential reference STM checked against the real implementation's observed histories.
  • Implement --features paranoid per-read validation (§18.6) as a debug-mode defense against the torn-read hang (§8.6).
  • Prove I1 holds across the full conformance corpus and 10,000 random property-test op sequences.
Deliverable

The opacity oracle differential-checks the full conformance corpus (conformance/corpora/) with zero violations; --features paranoid catches the §8.6 torn-read hazard in a targeted fixture that reproduces Harris & Fraser's Figure 4 scenario.

Acceptance
  • 10,000-iteration proptest run: zero opacity violations (stm_opacity_violation_total stays 0, I1).
  • Fixture opacity/harris-fraser-fig4.json: reproduces the torn-read hazard under a scripted interleaving; --features paranoid build aborts the transaction before the busy-wait can hang; the non-paranoid build is documented as relying on correct fencing (I4) instead.
  • Loom exhaustive search (TC 2–3) over every conformance fixture reports zero opacity violations.
Fixtures
  • opacity/harris-fraser-fig4.json — the torn-read hazard from §8.6, exact reproduction.
  • opacity/random-proptest-seed-*.json — checked-in failing seeds from any historical proptest regression.
  • opacity/malformed-oracle-mismatch.json — a deliberately-corrupted fixture whose expected oracle output does not match any valid interleaving; the runner must flag it as a fixture-authoring error, not a false STM failure.
Pitfalls
  • An invariant-checking transaction (one whose body asserts application invariants) must itself be re-runnable on abort; side-effecting invariant checks are out of scope and will double-report on retry.
  • Opacity is strictly stronger than linearizability (Herlihy & Shavit, Ch. 9 vs. Ch. 18) — document the relationship explicitly in docs/architecture/opacity.md so a future contributor does not assume linearizability testing alone suffices. Runtime-check detail: in --features paranoid, every tx.read re-validates by walking the existing read_set after loading the newly-read TVar — for each (other_id, observed_version), load other_id's current vlock version, and abort immediately if any has advanced past observed_version (an opacity violation caught in-flight, not merely prevented from committing). This is O(|read_set|) per read (vs. O(|read_set|) once per commit in the non-paranoid path).
  • A T whose Drop has observable side effects (e.g. closes a file) conflicts with the transaction re-run semantics (a retried transaction re-constructs and re-drops values) — document as a constraint on what T may safely be.
  • A transaction that re-reads its own buffered write via the write-set shadow (P1, §8.2) is fine and must not be flagged as an opacity violation by the oracle — a common false-positive if the oracle's history recording does not account for write-set shadowing correctly.

⬜ Phase 7 — GC Integration (Epoch Reclamation) §19

Objectives
  • Integrate crossbeam-epoch (P4, ADR-04) as stm-gc: every committed write retires its old heap value, reclaimed once safe.
  • Prove I10 (retire epoch ≤ every possibly-holding transaction's epoch) via ASan and a 1-hour stress soak.
  • Implement wait-set scrubbing (§19.5) to bound stm-wait memory growth.
Deliverable

A 1-hour, 16-thread stress run (mixed read/write/retry workload) shows zero unbounded memory growth (RSS plateaus within 5% after the first 5 minutes, M-adjacent target tied to §4's 100MB/1M-TVar constraint); a "drop a transaction mid-retry" fixture confirms its wait-set entries are cleaned up.

Acceptance
  • 1-hour soak: RSS growth after the initial 5-minute warm-up ≤ 5%, measured via stm_gc_pin_count/process RSS sampling.
  • ASan reports zero use-after-free across the full conformance corpus plus a targeted "retire under concurrent read" fixture.
  • Fixture overflow/wait-set-scrub.json: 10,000 transactions parked-then-dropped without commit; asserts wait-set size returns to baseline within one scrub cycle.
Fixtures
  • overflow/pin-epoch-lag.json — a thread pinned artificially long while other threads commit repeatedly; asserts retired values are held (not freed early) until the pinned thread unpins (I10).
  • overflow/wait-set-scrub.json — dropped-mid-retry cleanup, described above.
  • overflow/malformed-negative-epoch.json — a corrupted fixture with a negative epoch value; the runner rejects it as malformed rather than crashing the reclaimer.
Pitfalls
  • An active transaction that parks (via retry) for an extended period holds its epoch pin the whole time, stalling reclamation for the entire process (P4's stated tradeoff) — docs/runbooks/memory-bloat.md documents the diagnostic (stm_gc_pin_count staying elevated correlates with a long-parked thread).
  • The wait-set scrub frequency is a tunable knob; too infrequent and dead entries accumulate (a slow memory leak of Waker allocations); too frequent and the scrub itself becomes a contention point on hot TVars' wait-sets.
  • A scrub that runs concurrently with a commit touching the same TVar's wait-set is the canonical lock-contention pattern for this subsystem — stm-wait's internal locking (documented in docs/architecture/gc.md) must be reviewed whenever scrub frequency changes.
  • Retiring a value without incrementing the collector's global epoch afterward silently disables reclamation progress — a regression class caught by the 1-hour soak's RSS-plateau assertion, not by a unit test.

⬜ Phase 8 — Verification Harness (Loom, Shuttle, Fuzz) §20

Objectives
  • Wire loom (exhaustive interleaving search, TC 2–3) across every commit-path operation (P12).
  • Wire shuttle (randomized, PCT-biased scheduling, TC 4–16) with checked-in failing seeds for regression.
  • Wire cargo-fuzz targets per operation type and cross-architecture CI (P13).
Deliverable

Every public operation has a green loom test and a green shuttle test in CI; the opacity oracle is the cross-algorithm differential contract; the herd7 Power check runs as a scheduled (not per-PR) job given its extraction/translation overhead.

Acceptance
  • 100% of public operations (§11's signatures) have a corresponding loom test at TC 2–3, verified by a coverage-mapping script (scripts/loom-coverage.sh).
  • Shuttle: 10,000 schedules per algorithm per CI run, zero opacity violations; any historical failing seed remains green permanently (regression-locked).
  • herd7 Power check: zero missing-fence findings across the extracted instruction sequences for the TL2 commit protocol.
Fixtures
  • cross-arch/x86-64-native.json, cross-arch/aarch64-native.json — the full conformance corpus run natively per architecture.
  • cross-arch/power-herd7-extract.json — the extracted instruction sequence for the commit protocol, fed to herd7 offline.
  • retry/malformed-fuzz-corpus-seed.json — a minimized fuzz-discovered regression seed (populated as fuzzing finds real issues; empty at Phase-8 completion, structurally present for future regressions).
Pitfalls
  • Loom's state-space grows combinatorially with thread count and op-sequence length; keep loom fixtures to 2–4 TVars and short op sequences (P12's stated tradeoff) — anything larger belongs in shuttle instead.
  • Shuttle's randomness is non-deterministic run-to-run by design; the checked-in failing-seed mechanism is what makes a shuttle-discovered bug a permanent regression test rather than a one-off flake.
  • cargo-fuzz corpus growth without periodic minimization bloats CI time; scripts/ includes a corpus-minimization helper run monthly.
  • Skipping the herd7 cross-arch check "because it's slow" is exactly the failure mode that let a real-world GOD-tagged blueprint (Communion.md) ship structurally-complete-looking but functionally under-verified content — this project's §16-harness discipline exists to prevent the same class of self-deception here. Cross-architecture detail: the same matrix pattern used by mature concurrency crates is x86-64 native, aarch64 native, Power emulated via herd7 on extracted instruction sequences (P13); a test green on x86 alone is not a correctness signal, since x86's TSO-like model masks missing-fence bugs that aarch64's weaker model (and Power's weaker model still) would expose — any test passing on x86 but failing on aarch64 indicates a missing Release/Acquire fence somewhere in the commit path (§14.2) or the read path (§13.2).

⬜ Phase 9 — Privatization, Publication & C ABI §21

Objectives
  • Implement the stm-abi C ABI surface (P14): cbindgen-generated header, type-erased TVar/Tx handles.
  • Document and defend against the privatization and publication safety problems (I14, T7, T8).
  • Ship a working C example (bank-transfer over the ABI).
Deliverable

A C example (examples/bank-transfer built against the cdylib) runs the two-account transfer (§8.5) correctly from C; the header (include/stm.h) is binary-compatible with itself across a patch-version bump, verified by an ABI-compatibility CI check.

Acceptance
  • The C bank-transfer example produces the exact final balances from §8.5 (A=80, B=70) after 1,000 concurrent transfer pairs, run under ASan/TSan from the C side.
  • ABI version mismatch (a deliberately-corrupted header constant) causes stm_world_new to return a documented error code, not undefined behavior — verified by fixture cross-arch/abi-version-mismatch.json.
  • Publication-safety fixture publication-safety.json (I14, carried over from §7) passes: no C caller can obtain a pointer into Inner<T> through any exported function.
Fixtures
  • single-tx/c-abi-bank-transfer.json — the ABI-level equivalent of §8.5's worked example.
  • cross-arch/abi-version-mismatch.json — deliberate version-constant corruption, expects a clean error return.
  • publication-safety.json — asserts no exported function returns a live internal pointer (I14).
Pitfalls
  • The closure-passing convention across the C ABI ((state*, fn) pair) is easy to get wrong on the embedder side; docs/architecture/overview.md's ABI section documents the exact calling convention with a worked C snippet.
  • Panics inside the Rust closure invoked from C must be caught (catch_unwind, P6) and surfaced as a documented error code (STM_USER_ABORT), never allowed to unwind across the FFI boundary (undefined behavior in Rust's FFI model).
  • Type-erased TVar pointers require the embedder to keep types consistent; the runtime cannot type-check across the erased boundary — documented as a hard API contract, not a runtime-checkable invariant. Design-space note: publication (T7) and privatization (T8) are duals — publication is "a not-yet-committed value escaping to a non-transactional reader," privatization is "a value becoming non-transactionally accessible after a commit that removed its shared reachability, while a stale transactional reference might still exist" (Guerraoui & Kapalka's opacity paper treats both under the same "consistency of what escapes the transactional boundary" umbrella). This project structurally prevents publication (I14, no API returns a live pointer pre-commit) but documents privatization as a caller responsibility backed by stm-gc's epoch delay (§19) rather than a fully automatic runtime guarantee, since detecting "no other transaction still intends to touch this TVar" in general requires whole-program knowledge the library does not have.
  • ABI version skew (embedder linked against a different stm-abi version than deployed) is the single most common embedder-side production incident class for C-ABI libraries generally; the version stamp (§21.2) is the sole defense.

  • cargo-deny, cargo-audit, clippy --deny warnings, rustfmt --check, Miri all report clean.

Pitfalls

Pitfalls
  • Treating the concurrent-counter example (§23.2) as a recommended pattern rather than an anti-pattern demonstration is a common misreading of "STM is easy" — the README explicitly frames it as a boundary case.
  • Publishing to crates.io before the cargo public-api check is wired risks an accidental breaking-change release; §27 (Compatibility & Versioning) documents the semver discipline this must follow going forward.
  • The whitepaper drifting out of sync with this blueprint (§1–§22) as future ADRs are added is a documentation-maintenance risk; docs/BLUEPRINT_LOG.md tracks required whitepaper updates alongside blueprint amendments.
