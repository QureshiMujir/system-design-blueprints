In one paragraph

Software transactional memory (STM) lets several threads share in-memory data without hand-written locks. You wrap a block of code in a transaction; the library runs it optimistically, and either all of its writes appear at once or none do (§1). This blueprint specifies it as a Rust library built on the TL2 algorithm and one global version counter (§1, P2). It adds blocking waits (retry), alternatives (or_else), closed nested transactions, a contention manager that bounds abort rates, and epoch-based memory reclamation (§1). Its correctness contract is opacity: every read inside a live transaction sees a mutually consistent snapshot (I1). It is linked into the embedding application, with no daemon; an SRE reads its runbooks when abort rates spike (§1).

The problem, concretely

Take two bank accounts, A = TVar(100) and B = TVar(50). One thread transfers 30 from A to B while another transfers 10 from B to A (§8.5). Each transfer is correct alone, and the goal is that both stay correct together, with A + B equal to 150 at every instant anyone can observe (§8.5). The blueprint's pitch is composability: two independently correct atomic operations combine into a third correct atomic operation, which mutexes and lock-free data structures structurally cannot offer (§2).

The blueprint names the naive fix as "just add a global lock" and wants the reader able to judge whether that is really cheaper than STM (§2). The constraints table makes that comparison for the hardest case, one hot variable: at least 50 K commits/s with 16 threads on one hot TVar, against about 30 K for a Mutex<T> (§4, M3). The commit protocol itself must lock several TVars, so it sorts its write set by TVarId; two transactions that locked in opposite orders would be a deadlock hazard (§14.2 step 1, §14.6).

Optimism creates a second, subtler problem. A transaction can see another transaction's commit in its read of x but not yet in its reads of y, observe a mixed state, and then loop forever on a guard that can never become true. Commit-time checking never runs because the body never returns (§8.6, T5). This is why the correctness contract is opacity and not just serializability (§7 I1, §32 MM2).

How it works, end to end

The architecture is a stack of boxes in which stm-clock is the only contention point (§3, P1). User code calls atomically(|tx| ...); the Tx handle cannot escape the closure because its lifetime is tied to it (§3, P5).

user code: atomically(|tx| ...), tx.read, tx.write, retry, or_else      (adapted from §3)
   -> stm-core facade (owns no state; forwards to a Tx or a TVar)
   -> Tx: read_set, write_set, start_version, aborted_count, parent
   -> stm-clock: sort+lock write set, fetch_add clock, validate, publish or abort
        -> TVar<T>: value (AtomicPtr) + vlock (AtomicU64)
        -> stm-wait: per-TVar wait-set; commit drains and wakes waiters
        -> stm-gc: retires the old value of every write
   stm-verify: opacity oracle + loom + shuttle (on the CI path, not the runtime path)

Following one transfer through the boxes:

  1. stm-core is only a re-export surface: TVar<T>::new, atomically, try_atomically, retry, or_else (§3, §11). It owns no state.
  2. Tx is stack-allocated per atomically call (ADR-21). Its read and write sets are SmallVec with inline capacity 8 (ADR-22, §8.2). start_version is read from the clock when the transaction becomes Active (§8.1).
  3. The body runs touching nothing shared except each TVar's own fields: reads record the observed version, writes are buffered and a later read of the same TVar returns the buffered value (§8.2, P1).
  4. stm-clock runs the five-step commit when the body returns (§14.2). It is the only place conflicts surface (P1, §3).
  5. TVar<T> holds a pointer to a heap-allocated value plus one packed version-and-lock word (§3, §11, ADR-03).
  6. stm-wait keeps, per TVar, the transactions parked by retry. A commit that touches the TVar drains and wakes them (§3, §15.2).
  7. stm-gc (built on crossbeam-epoch) frees the replaced value only once no thread could still hold a pointer to it (§3, §19.1).
  8. stm-verify is the CI gate every commit-path change must clear (§3, P12).

stm-bench, the criterion suite comparing STM against Mutex/RwLock, is the sixth module numbered in §1. The §10 tree and the Phase 0 steps add two more crates, stm-abi (the C ABI) and stm-cli (a debug-only introspection binary), so §1 lists six modules where §12.2 creates eight crates (§1, §10, §12.2). The library has no network layer (ADR-11), delegates thread scheduling and allocation, and provides no persistence (§1).

The core ideas

Optimistic execution and the five-step commit (§8.2, §8.3, §14.2)

A transaction runs against private read and write sets and touches shared state only at commit (P1). Each TVar carries one 64-bit word that packs a version and a lock bit, so "is it locked" and "what version" are always read together (§8.3, MM3):

VLock (AtomicU64):
  bit 0        : locked (1 = held by a committing writer)
  bits 1..63   : version (monotonic, from the global clock)

encode(version, locked) = (version << 1) | (locked as u64)
decode(word)            = (word >> 1, word & 1)

The commit sequence, numbered as in §14.2. The box in §3 numbers it differently: it folds "sort+lock" into step 1, puts validation at step 3, and splits "publish" and "abort" into steps 4 and 5. Every other cross-reference (I1, I3, §8.4, §8.6, §8.7) uses the §14.2 numbering, with validation as step 4.

  1. Sort the write set by TVarId, the canonical lock order.
  2. Lock each written TVar with a compare-and-swap from (version, 0) to (version, 1). A failed CAS aborts at once (I3).
  3. Take a commit version with world.clock.fetch_add(1, AcqRel). This is the single serialization point (I2, P1).
  4. Validate the read set. Each entry is valid if its version matches and its lock is free or held by this transaction itself (I3, I5).
  5. On success, swap each AtomicPtr to the new value, retire the old one and store (commit_version, 0). On failure, release all held locks and abort (I8).

The blueprint's own trace (§8.5), where thread 1 transfers 30 from A to B and thread 2 transfers 10 from B to A:

Step Thread 1 Thread 2
Read A@v0=100, B@v0=50 B@v0=50, A@v0=100
Buffer A=70, B=80 B=40, A=110
Commit, step 2 locks A, then B CAS on A fails, aborts before locking B
Commit, steps 3-5 takes v1, validates, publishes at v1, unlocks (not reached)
Retry none back-off with aborted_count=1 (no delay yet), restarts with start_version=v1, reads B=80 and A=70, writes B=70 and A=80, commits

The final state is A=80 and B=70, and A + B = 150 held throughout (§8.5). The same fixture is two-tx-conflict/transfer-canonical-order.json (§14.5). A panic mid-commit is handled by the CommitGuard drop guard, which stores the observed versions back and surfaces the panic as AbortReason::UserAbort without retrying (§8.7, I8). A transaction that only writes a TVar never validates it, but two such writers still collide at the lock CAS (§8.8).

Opacity: consistent even when about to abort (§7 I1, §8.6, §18)

Serializability constrains committed histories only. Opacity also constrains the runs that will abort, because user code between reads can loop or crash before the abort is noticed (§32 MM2). The blueprint's hazard example: x and y are both 0 and every committed transaction keeps x == y. A transaction reads x, then busy-waits until y is nonzero. If a reordered load shows it the post-commit x but the pre-commit y, it spins forever, and TL2's commit-time check is powerless because validation never runs (§8.6).

Two defences are named. First, an Acquire fence on every TVar read so the loads cannot be seen out of commit order (§8.6, I4). Second, a --features paranoid build that re-validates the whole read set on every tx.read, which is O(|read_set|) per read against O(|read_set|) once per commit normally (§18.2, §18.6). The checking side is a sequential oracle, a single-threaded reference STM over a HashMap, compared against histories from the real STM under real threads or loom (§18.2). The blueprint is not consistent about where opacity is enforced. I1's table row names "Commit validation (§14.2 step 4)" as the enforcement point (§7), and §1 phrases the property as "either from a consistent snapshot or the transaction never commits". But §8.6 says commit-time validation is powerless against the hang, and the non-paranoid build relies on I4's fencing for that case (§18.4, T5).

Composition: retry, or_else and nesting (§15, §16)

retry() means "I cannot proceed until something I read changes". It is a control-flow marker returned as AbortReason::Retry, never a panic (P6, ADR-05). The transaction walks its read set, registers a waker on every TVar in it, and the thread parks. A later commit touching any of them wakes it and it restarts from Active (§15.2, §8.1). An empty read set at retry time would never wake, so it is a contract violation that panics in debug (I7, §15.6).

or_else(alt1, alt2) is lazy: snapshot the sets, run alt1; only if it retries, restore the snapshot and run alt2 (§15.2, P7). If both retry, the wait-set is the union of both branches' read sets, so a change that only alt1 read still wakes the whole expression (P7, §15.2). Registering only alt2's reads would lose wakeups (FM-4, MM5).

Nesting is closed: a nested atomically appends to the outer's sets, inherits its start_version and commits only once, at the outermost call (P8, §16.2). A nested retry propagates to the outermost transaction (§16.2). Inner writes are therefore invisible until the outer commits (I9).

Contention management: back-off then priority (§8.9, §17)

When a transaction keeps aborting, blind spinning can leave two symmetric writers aborting each other forever (P9, FM-8). The ladder in §17.2 escalates with aborted_count:

Aborts Action (§17.2)
1 to 3 retry immediately
4 to 7 spin back-off, 100ns × 2^(N-4)
8 to 15 yield back-off, 1µs × 2^(N-8)
16 and up sleep back-off, 100µs × 2^(N-16), capped at 100ms

Past the threshold a transaction sets a priority flag. If its lock CAS then fails against a non-priority holder, it sets that holder's cooperative abort_flag; the holder notices at its next read, write or validation step and aborts voluntarily (§17.2). Priority clears after the transaction's next successful commit, and at most one transaction holds it per conflict set (I12, I15, MM6). The blueprint is not consistent about the exact threshold. The state table's BackingOff row exits "→ Priority at abort 16" (§8.9). The Priority row's own trigger is aborted_count > 16 (§8.9), and the steps, pitfalls and threat model say the same (§17.2, §17.6, T13). It is left unresolved here.

Epoch reclamation: free once provably safe (§19, P4, MM4)

Each commit publishes a new heap allocation for a TVar (P3), so the old value cannot be freed at once: a concurrent reader may already hold its pointer, and freeing it eagerly is a use-after-free (P4). Every thread pins an epoch guard for the duration of each atomically call; the replaced value is handed to guard.defer_destroy, and crossbeam-epoch's three-epoch scheme frees it only after every pinned thread has moved past the retiring epoch (§19.2, I10). Retires are batched, 64 per scan by default (§19.2). The cost is that a thread pinned for a long time, for example one parked in retry, stalls reclamation for the whole process (§19.6, P4, FM-7). A periodic scrub also removes wait-set entries of terminated transactions (§19.2, I16).

The trade-offs — where engineers disagree

Algorithm: TL2 (ADR-02)

Chosen: TL2, with commit-time locking and a version clock, for O(1) per-read validation and the smallest single-paper verification surface (ADR-02). The blueprint describes the same validation elsewhere as O(|read_set|) once per commit (§8.4). Rejected: TinySTM encounter-time locking, and NORec value-based validation (ADR-02). When the rejected choice is right: encounter-time locking wins for write-dominated workloads, where early conflict detection avoids wasted read-heavy work before a doomed commit (ADR-02, §36.1).

Value storage: heap pointer per TVar (ADR-03)

Chosen: a heap-allocated value behind an AtomicPtr, which handles T that is not Copy and avoids requiring T: Clone (ADR-03, P3). Rejected: in-place mutation with a deep copy (ADR-03). When the rejected choice is right: for small Copy types such as TVar<u64>, where allocation overhead dominates; the Phase-10 stretch targets exactly this and is deferred (ADR-03, §37).

Memory reclamation: epochs (ADR-04)

Chosen: epoch-based reclamation through crossbeam-epoch, for bounded retire-list memory and a battle-tested crate (ADR-04). Rejected: hazard pointers per TVar (ADR-04). When the rejected choice is right: hazard pointers win when a hard per-object memory bound matters more than throughput, for example on an embedded target (ADR-04).

or_else evaluation: lazy (ADR-06)

Chosen: lazy, so alt2 runs only if alt1 retries, avoiding wasted work when alt1 succeeds (ADR-06, P7). Rejected: eager evaluation, running both and picking the first (ADR-06). When the rejected choice is right: eager wins when both branches are cheap and side-effect-free and tail latency matters more than average-case work (ADR-06).

Nesting: closed only (ADR-07)

Chosen: closed nesting, which preserves the outer transaction's atomicity and composability (ADR-07, §16.6). Rejected: open nesting (ADR-07). When the rejected choice is right: open nesting wins for long outer transactions with independent, non-conflicting inner sub-transactions, a batch-job architecture and not this project's target (ADR-07, §16.6).

Contention management: back-off plus priority bump (ADR-08)

Chosen: exponential back-off with a priority bump (Felber et al. 2008), which bounds worst-case retries without per-transaction priority accounting infrastructure (ADR-08, I12). Rejected: randomized back-off alone, and timestamp-based contention management (ADR-08). When the rejected choice is right: timestamp-based (oldest-transaction-wins) wins when strict FIFO fairness is needed, for example a scheduler simulation (ADR-08).

Lock representation: packed into the version word (ADR-19)

Chosen: a 1-bit lock inside the 64-bit version word, so one atomic operation both checks the lock and reads the version, and a cache line is saved (ADR-19, §8.3). Rejected: a separate AtomicBool lock field (ADR-19). When the rejected choice is right: a separate field wins if the version range must exceed 63 bits (ADR-19, I13).

Side effects: no irrevocable transactions (ADR-24)

Chosen: not supported; side effects run outside atomically, because a retried transaction would re-run them non-idempotently and support needs a process-wide lock that defeats P1 (ADR-24). Rejected: a serial-irrevocable-mode fallback as in GCC libitm (ADR-24). When the rejected choice is right: it wins when embedding legacy code that cannot be restructured, accepting a global serialization point during each irrevocable transaction (ADR-24, T9).

Roads not taken

Encounter-time locking (§36.1) acquires a lock at each write and keeps an undo log. It wins for write-dominated workloads, and is rejected because it needs undo-log discipline that commit-time locking avoids, while the write-set shadow already helps the read-mostly target (§36.1).

NORec value-based validation (§36.2) records values instead of versions and so has zero per-object metadata. It wins when values are small and cheap to compare. It is rejected because validation re-reads and re-compares every value, O(|read_set| × value-size), a poor fit once T exceeds a machine word (§36.2).

HTM/STM hybrid (§36.3) tries a hardware transaction first (Intel TSX) and falls back to software. It wins for latency-critical, x86-only deployments with short transactions. It is deferred rather than rejected outright, because TSX is x86-only and leaks platform detail into a portable library (§36.3, ADR-23, §37).

Static transactions (§36.4), the 1995 origin of the field, declare the whole data footprint at compile time. They win in embedded or safety-critical systems that need a statically bounded footprint. They are rejected because the target workloads need runtime-determined transaction shapes (§36.4).

The deferred register (§37) parks features until a named trigger appears: a lazy or sharded global clock once sustained commits approach the ≈200M/s single-clock ceiling; in-place updates for Copy primitives once allocation profiling shows allocator pressure dominating TVar<u64>-style hot paths; durable TVars on a crash-recoverable durability requirement; and distributed STM if the library becomes the concurrency-control layer of a multi-node service (§37, §34 item 1).

What must never be false

  • I1: every read in a live transaction sees a mutually consistent snapshot. Noticed by the opacity-oracle differential run (§20.3); stm_opacity_violation_total must stay 0 (§7).
  • I2: the version clock totally orders all commits. Noticed by the loom exhaustive check at 2 and 3 threads; stm_clock_value gauge (§7).
  • I3: a TVar's version-and-lock word changes only through a successful CAS. Noticed through the CAS return value; stm_lock_cas_fail_total (§7).
  • I4: no torn reads; tx.read never returns a half-written value. Noticed by Miri and ASan on the read path; stm_read_total (§7).
  • I5: the word packs a 63-bit version and a 1-bit lock atomically. Noticed by a static layout assertion (§7, ADR-19).
  • I6: a transaction's sets are mutated only by its owning thread, since Tx is not Send. Caught at compile time (§7). The same I6 label is also used for TVarId stability in §11 and §13, which §7 does not describe.
  • I7: retry() needs a non-empty read set. Noticed by a debug assertion; stm_retry_empty_readset_total (§7).
  • I8: every acquired write-set lock is released exactly once per commit attempt. Noticed by loom; stm_lock_leak_total must stay 0 (§7).
  • I9: a nested transaction's writes are invisible outside its outer chain until the outermost commit. Noticed by fixture nested/closed-commit.json (§7, §16.5).
  • I10: a value's retire epoch is no later than any transaction that could still hold a pointer to it. Noticed by the ASan use-after-free detector in CI; stm_gc_pin_count (§7).
  • I11: the library is lock-free, not wait-free. This is a documented contract, with no runtime detection (§7, §1).
  • I12: at most one transaction holds priority among mutually conflicting writers. Noticed by fixture priority-fairness.json; stm_priority_holder_count stays at most 1 per set (§7).
  • I13: the global clock never wraps in the supported lifetime. Noticed by a compile-time width assertion plus a runtime warning at 90% headroom; stm_clock_headroom_pct (§7).
  • I14: a publication never exposes a pre-commit value to a non-transactional reader. Noticed by fixture publication-safety.json; stm_publication_race_total (§7).
  • I15: a transaction's priority flag is set at most once per attempt and cleared once after its own next commit. Noticed by a priority-transition log; stm_priority_transition_total (§7).
  • I16: a wait-set entry is removed by exactly one path: wakeup, scrub or the owner's termination. Noticed by an ASan double-free detector over the scrub fixture; stm_waitset_entry_removed_total{path} (§7).

What breaks in production

  • FM-1, opacity violation reaches a committed state. Root cause: a missing validation step or a fencing bug (T5). Detected by the opacity-oracle CI gate and stm_opacity_violation_total above 0. No automatic recovery; the class should be structurally impossible, CI blocks merge, and the fix is a bisect using the checked-in failing seed (§25, P12).
  • FM-2, a lock is never released. A panic during commit that CommitGuard did not catch. Detected by stm_lock_leak_total above 0 and loom at 2 and 3 threads. Later writers to that TVar starve; recovery is a process restart (§25, I8).
  • FM-3, slow commits. Clock contention near the roughly 200M/s ceiling, or a large write set. Detected as a p99 regression in stm_commit_latency_seconds. Recovery is manual, via the slow-commit runbook (§25, §34 item 1).
  • FM-4, a lost wakeup. A parked transaction never wakes despite a relevant commit, because or_else failed to union read sets. Detected by the or_else/union-readset.json regression and a high stm_parked_thread_count. Recovery is restarting the parked transaction by hand and fixing the union bug (§25, P7).
  • FM-5, unbounded memory growth. An epoch-pin stall or a retire-queue backlog (T12). Detected by stm_gc_pin_count staying high or stm_retire_queue_depth growing; recovery is finding the stuck pin or raising the batch threshold (§25). A related class, FM-7, is reclamation stalled for the whole process by a single thread pinned indefinitely, parked in retry or crashed without unpinning; the fix is restarting that thread or process (§25, MM4).
  • FM-8, livelock. Symmetric high-frequency writers abort each other faster than back-off and priority resolve. Detected as stm_aborted_count p99 above the 24-attempt ceiling of M7; priority bumping is the built-in recovery, and the runbook redesigns the hot TVar (§25, P9).
  • FM-9, green on x86, wrong on aarch64 or Power. A missing Release/Acquire fence that x86 hides. Detected by arch-matrix.yml divergence or a herd7 finding; recovery is adding the fence and re-running the matrix (§25, P13).
  • FM-12, a zombie transaction. One that read inconsistent state terminates plausibly before commit validation (T5). The oracle catches only results that would have reached commit, so the defence is discipline: side-effect-free transaction bodies (§25, §18.6).

Threats to know (§24): T1 adversarial contention, answered by back-off plus priority (P9, I12). T5 the torn-read hang before validation, answered by Acquire fencing and the paranoid feature (§8.6). T6 a panic in user closures, answered by CommitGuard and kept distinct from Retry in telemetry (P6). T7 publication safety at the C boundary, answered by copy-out-only reads that never return a live pointer (§21.2, I14). T8 privatization, where epoch delay defers deallocation but safe non-transactional access stays a caller responsibility (§24, §21.2).

Places where the blueprint disagrees with itself (both sides stated, not resolved):

  • Transaction shape. §4 and §22.8 give M1 and M4 for a 2-read, 1-write transaction. The derivation of 400 ns and 2.5 M/s uses an 8-read, 2-write transaction (§34 items 2 and 3, §30.1, §14.7, §22.7).
  • Clock horizon. §4, ADR-20 and T10 state "≈293 × 10^9 yr @ 1B commits/s". §34 item 6 computes about 292 years for the same rate, and says both figures are "retained in §4/I13"; the I13 row itself states no figure (§7).
  • Conflict formula. §4 and §34 item 7 write the abort probability as 1 − (1 − K/N)^(K−1). T11 says the conflict rate "scales as K²/N", and §31 calls it "the K²/N formula" while citing §4.

The blueprint uses §34 item 7 to explain why M3's target sits far below M1's despite identical per-commit cost: in the hot-TVar regime, approximated as K=16 among N=100, most attempts abort and must retry (§34 item 7, §35 item 17).

How it compares

  • GHC Control.Concurrent.STM keeps side effects out of transactions through the type system (a distinct STM monad), which wins in a language with a monadic effect system; Rust has none, so this design relies on documentation and review (§33, §18.6). It is garbage collected, so it has no explicit reclamation (§33).
  • Clojure refs use version stamps in JVM object headers with dynamic typing and only partial composition (ensure, no full retry/orElse). That suits a dynamically typed Lisp but would fit Rust's static TVar<T> badly (§33).
  • ScalaSTM (CCSTM) is TL2-derived and mirrors Haskell's composition, and keeps version metadata in the JVM object header. That is free on the JVM but not available in Rust, where ADR-19 uses an explicit AtomicU64 instead (§33, ADR-19).
  • TinySTM is the source of this design's contention-management ideas but locks at encounter time by default and offers no composition primitives. That wins for write-dominated work at the cost of an undo-log discipline (§33, §36.1).
  • ZIO STM folds transactions into a general effect monad (ZSTM) and delegates contention handling to the fiber scheduler. That fits a stack standardized on one effect system; Rust has no dominant equivalent, which is why ADR-12 is sync-first (§33, ADR-12).

If you only remember three things

Reads and writes touch nothing shared until a five-step commit that takes one global clock tick, so that single counter is both the design's serialization point and its throughput ceiling (P1, I2, §34 item 1). Correctness means opacity, so even doomed transactions must see consistent data, and the commit-time check alone is not enough for a transaction that hangs before reaching it (I1, §8.6). Composition, back-off with a single priority holder, and epochs that free memory only when provably safe all exist to keep that one idea usable without the usual lock hazards (P7, P8, I12, P4).

Words used here

  • Transaction: a block of code that runs as one all-or-nothing step, retried on conflict (§11, §38).
  • TVar: the transactional cell, the unit of shared state (§11).
  • Read set / write set: what a transaction has read, with versions, and what it intends to publish (§8.2).
  • Version clock: the one shared counter that totally orders commits (I2, §8.3).
  • TL2: the commit-time-locking, version-clock algorithm this library implements (§38, P2).
  • Opacity: every read in a live transaction sees a consistent snapshot, stronger than serializability (I1, §38).
  • Torn read: a read that mixes values from before and after another commit (§8.6, §38).
  • Zombie transaction: one that read inconsistent state and ends before validation can catch it (FM-12, §38).
  • retry / or_else: wait until something I read changes; try a second alternative if the first retries (§15).
  • Closed nesting: an inner transaction shares the outer's commit point (P8, §16.1).
  • Contention manager: the back-off plus priority subsystem that prevents livelock (§17, P9).
  • Epoch reclamation: delay freeing until no pinned thread could hold a stale pointer (§19, P4).
  • Publication / privatization safety: keeping uncommitted values from escaping, and keeping unlinked values safe to touch (I14, T7, T8).
