User code issues atomically(|tx| ...) closures; tx never escapes the closure (a lifetime parameter enforces this, ADR-01, P5) — the sole entry point; there is no way to read or write a TVar outside a transaction.

stm-core facade is the crate-root re-export surface (§11); it owns no state — every call forwards into a Tx or a TVar.

Tx accumulates the read set and write set as the closure runs; stack-allocated per atomically call (ADR-21) with inline capacity 8 (ADR-22) sized to the common small-transaction case.

stm-clock is the only contention point in the architecture (P1): reads/writes during the transaction body touch no shared state beyond the TVar's own fields; conflicts surface exclusively at the five-step commit sequence (§14.2).

TVar<T> is the shared transactional cell: a version-and-lock word packed into one AtomicU64 (I5) plus an AtomicPtr<T> to the current heap-allocated value (ADR-03).

stm-wait holds, per TVar, the set of parked transactions waiting on a retry; a successful commit drains and wakes every waiter whose read set included that TVar (§15.3).

stm-gc retires the old heap value of every write into crossbeam-epoch's reclamation list; a value is freed only once every transaction that could hold a pointer to it has advanced past the epoch it was retired in (§19.1).

stm-verify is off the runtime critical path but on the CI critical path: it proves the other six boxes satisfy opacity (I1) under every interleaving it can enumerate or sample (§20).

Four properties referenced throughout: optimistic reads (contention only at commit, P1); the version clock totally orders commits (I2); validation is per-commit not per-read (§8.4); opacity is the correctness contract, not an optimization (I1).

8. Domain Model

8.1 The transaction state machine

State Entry Reads/Writes allowed Exit transitions
Active atomically begins; start_version = clock.load() Yes, into read_set/write_set → Committing (body returns) / → Retrying (retry()) / → Aborting (panic/user abort)
Committing Body returned a value No → Committed (validation passes) / → Aborted (validation fails, loop to Active with fresh start_version)
Retrying retry() called, read set non-empty (I7) No → Parked (wait-set registration complete)
Parked Waker registered on every read-set TVar No → Active (a relevant commit drains the wait-set)
Aborting Validation failed or user abort No → Active (retry from scratch, back-off per §17)
Committed Publish complete, locks released — Terminal

8.2 Read-set / write-set representation

read_set: SmallVec<[(TVarId, ObservedVersion); 8]>; write_set: SmallVec<[(TVarId, NewValue); 8]> (ADR-22). A tx.write to a TVar already in write_set overwrites the buffered entry (last-write-wins within one transaction); a subsequent tx.read of that same TVar returns the buffered write, never re-touching the shared AtomicPtr (P1).

8.3 The versioned-lock schema (TL2)

VLock (AtomicU64):
  bit 0        : locked (1 = held by a committing writer)
  bits 1..63   : version (monotonic, from the global clock)

encode(version, locked) = (version << 1) | (locked as u64)
decode(word)            = (word >> 1, word & 1)

Lock acquire: CAS (v<<1)|0 → (v<<1)|1. Lock release+publish: store (v_new<<1)|0. Validation: decode(word) == (observed_version, 0) OR the TVar is in our own write set (I3, I5).

8.4 Commit-time validation and conflict detection

Conflict is structural: transaction A conflicts with committed B iff A.read_set ∩ B.write_set ≠ ∅ and B's commit version falls inside (A.start_version, A.commit_attempt]. TL2 detects this without a per-object conflict graph — it re-reads each TVar's current VLock at validation time (§14.2 step 4) and compares against the value observed at read time: O(|read_set|) per commit attempt, not O(active transactions) — the key TL2 scaling property (P2, referenced in §34).

8.5 Worked example — two-account transfer under contention

Accounts A = TVar(100), B = TVar(50). Thread 1 runs transfer(A, B, 30): reads A@v0=100, reads B@v0=50, writes A=70, writes B=80. Concurrently thread 2 runs transfer(B, A, 10): reads B@v0=50, reads A@v0=100, writes B=40, writes A=110.

Both write sets overlap ({A, B}) — the canonical-order lock (§14.2 step 1, sorted by TVarId) means both threads attempt to lock A then B in the same order, so no deadlock occurs; one thread's CAS on A fails and it aborts before ever locking B (I3). Say thread 1 wins: locks A, locks B, allocates commit version v1 = clock.fetch_add(1), validates (both TVars still at v0, locks held by self — valid), publishes A=70, B=80 at v1, unlocks. Thread 2's CAS on A failed at step 2; it aborts, backs off (§17.1, aborted_count=1, no delay yet), retries from scratch with start_version=v1: reads B@v1=80, reads A@v1=70, writes B=70, writes A=80. Commits cleanly. Final state A=80, B=70 — the invariant A+B=150 holds throughout (I1: no thread ever observed an inconsistent intermediate sum).

8.6 Malformed-input / hazard example — torn reads without commit-time validation (Harris & Fraser, OOPSLA 2003, Fig. 4)

Setup: x = TVar(0), y = TVar(0); the application invariant x == y is maintained by every committed transaction. A transaction body reads x into a local, then — only when that value is nonzero — busy-waits re-reading y until it too is observed nonzero: a pattern that is legal Rust but pathological under STM, since it never returns to let the runtime validate.

timeline →
T:      read(x)=0 ......... [reordered: T now sees x=1] .. read(y) read(y) ...
Other:            commit: x=1, y=1 (v1)

If T's read of x is reordered (by CPU or missing fence) to observe the post-commit value while its later reads of y still observe the pre-commit value, T busy-waits forever: the guard is true but y never becomes nonzero from T's point of view. This is not a validation failure — validation never runs, because the transaction body never returns. TL2's commit-time check (§14.2 step 4) is powerless against a transaction that hangs before reaching it; the defenses are (a) a correct Acquire fence on every TVar read so x and y can never be observed out of commit order (I4), and (b) --features paranoid per-read validation (§18.6) that aborts as soon as inconsistency is detected. Documented as Threat Model T5 and Pitfall §18.6.

8.7 Failure-path example — panic during commit

Thread holds locks on {A, B} mid-commit (§14.2 step 2 complete, step 4 in progress) when the validation-comparison code panics (e.g., an allocator failure inside the retire path, §19). The commit's RAII guard (CommitGuard, §14.7) runs on unwind: releases every lock acquired so far by storing (observed_version<<1)|0 back into each held TVar's VLock, then propagates the panic to the caller as AbortReason::UserAbort wrapping the original payload. No TVar is left locked (I8); no partial write is published (I1). The caller's atomically does not auto-retry on UserAbort (only on Retry) — the panic surfaces to the application, per P6's distinction between "wants to wait" and "crashed."

8.8 Write-only transactions (conflict-detection edge case)

A transaction that only writes (never reads) a TVar — e.g. an unconditional tx.write(&v, new_value) with no preceding tx.read(&v) — never adds that TVar to its read_set (§8.2), and so never validates it against a concurrent writer's commit (§8.4's validation is defined over the read set, not the write set). This is not a bug: TL2's correctness argument (§14.4) only requires that a transaction's read set be consistent at commit; a pure write has no prior observation to be inconsistent with. Two write-only transactions to the same TVar still conflict at the lock-acquisition step (§14.2 step 2, I3) — one's CAS fails and it aborts — so mutual exclusion on the write itself is preserved even though no read-set validation is involved. The distinction matters operationally: a workload dominated by write-only transactions to a shared TVar shows contention exclusively as stm_lock_cas_fail_total (T11), not as stm_opacity_violation_total, since there is no read-set-consistency question to violate.

8.9 Contention-manager state (detailed in §17)

Normal Default Retry immediately or minimal back-off (aborts 1–3) → BackingOff at abort 4
BackingOff aborted_count 4–15 Exponential spin/yield delay (§17.4) → Priority at abort 16
Priority aborted_count > 16 May abort a non-priority lock holder on CAS failure (§17.5) → Normal after next successful commit
