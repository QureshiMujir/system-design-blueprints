1. Goal & Scope

Build a production-grade software transactional memory (STM) library in Rust: a TVar<T> transactional-cell type, a per-thread transaction context that accumulates a read set and a write set, a TL2-style (Dice, Shalev, Shavit, DISC 2006 — applied in §14) commit-time validation protocol driven by a global monotonic version clock, the composable blocking primitives retry and or_else (Harris, Marlow, Peyton Jones, Herlihy, PPoPP 2005 — applied in §15), closed-nested transactions (applied in §16), a contention manager that bounds abort rates under adversarial workloads (applied in §17), epoch-based reclamation for safe TVar value GC (applied in §19), and a correctness harness that checks opacity (Guerraoui & Kapalka, PPoPP 2008 — applied in §18) via a sequential oracle plus model-checked interleavings (loom, shuttle, applied in §20). The system's one defining property: every observable read inside an uncommitted transaction is either from a consistent snapshot or the transaction never commits — opacity, not merely serializability, is the correctness contract (I1, I2).

Phase-0 deliverable — numbered modules:

  1. stm-core — the public facade: TVar<T>, atomically, Tx handle types (signatures only, §11).
  2. stm-clock — the global version clock and the TL2 commit/validate/publish state machine (§14).
  3. stm-wait — the retry wait-set and wakeup dispatch (§15).
  4. stm-gc — epoch-based reclamation for retired TVar values (§19), built on crossbeam-epoch.
  5. stm-verify — the opacity oracle, loom harness, shuttle harness (§20).
  6. stm-bench — the criterion benchmark suite comparing STM against Mutex/RwLock baselines (§22).

System boundaries.

  • Provides: in-process shared-memory transactions over arbitrary T: Send + 'static values; automatic conflict detection and retry; blocking composition (retry/or_else); nested transactions (closed nesting only); a C ABI for non-Rust embedders (§21).
  • Delegates: OS thread scheduling (to the host runtime or std::thread); heap allocation (to the global allocator, pluggable per ADR-09); persistence (none — STM is a pure in-memory primitive).
  • Does NOT provide: cross-process or distributed transactions (no 2PC, no consensus); hardware transactional memory (HTM) fallback/hybrid execution — PhaseDeferred("§37") (row 1); durable/persistent-memory TVars — PhaseDeferred("§37") (row 2); irrevocable (side-effecting) transactions (ADR-24).

Non-goals: general-purpose database transactions (no SQL, no disk WAL, no cross-node replication); a garbage-collected runtime (Rust ownership + epoch reclamation only, §19); wait-free progress guarantees (STM is lock-free, never wait-free — I11).

Deployment model: a linked Rust library (rlib + optional cdylib for the C ABI, §21); no network listener, no daemon; consumed in-process by the embedding application. Operators interact with it only via tracing spans (§26) and stm-cli, a debug-only introspection binary, never production-critical.

Target users/operators: Rust application engineers building contended-shared-state services (game-state servers, financial ledgers, control planes); the operator role is the SRE who reads the Operational Readiness runbooks (§26) when abort rates spike.

What later phases unlock: Phase 0 (§12) gives a single-thread-correct TVar/Tx skeleton with no concurrency; Phase 2 (§14) unlocks real multi-thread correctness (the TL2 commit); Phase 3–4 (§15–§16) unlock composability and nesting; Phase 5 (§17) unlocks bounded-latency progress under contention; Phase 6–7 (§18–§19) unlock verified correctness and safe memory reclamation; Phase 8 (§20) unlocks CI-gated model-checked correctness; Phase 9 (§21) unlocks non-Rust embedding; Phase 10–11 (§22–§23) unlock production performance guarantees and worked examples.

Recommended language: Rust (2021 edition). Rationale: the borrow checker statically prevents the single most common STM implementation bug — smuggling a Tx handle outside its closure and using it after commit/abort (ADR-01); Send/Sync auto-traits give TVar<T>: Send + Sync exactly when T is, for free; crossbeam-epoch gives a battle-tested reclamation crate to build on (§19) rather than hand-rolling hazard pointers. Rejected: C++ (no borrow checker — the Tx-escape bug becomes a use-after-commit heap bug, not a compile error, ADR-01); Haskell (the reference implementation already exists as Control.Concurrent.STM; reimplementing it teaches nothing new architecturally, and its GC runtime hides the epoch-reclamation lesson this project exists to teach); Java (GC likewise hides reclamation; no value semantics for a cheap TVar<T> clone-on-commit).

Prerequisites: comfort with atomics and memory ordering (Acquire/Release/AcqRel, §11); optimistic concurrency control basics; the CAS-loop idiom; enough Rust to read unsafe blocks around raw pointers (the TVar internals, §11, use AtomicPtr).

Estimated timeline: Phase 0 — 1 week (repo skeleton, TVar/Tx types with no real concurrency, smoke test). Full system (Phases 0–11) — 5 months at one senior engineer half-time, or 10–12 weeks full-time, matching the week markers in §12–§23.

Deferred features (full table in §37): hardware-TM hybrid execution PhaseDeferred("§37"); durable/NVM TVars PhaseDeferred("§37"); open nesting PhaseDeferred("§37"); irrevocable transactions PhaseDeferred("§37"); distributed STM PhaseDeferred("§37").

2. Why Build This

  • Unique systems knowledge: the only widely-taught concurrency primitive whose entire value proposition is composability — two independently-correct atomic operations combine into a third correct atomic operation, a property mutexes and lock-free data structures structurally cannot offer (Harris et al., PPoPP 2005, applied §15).
  • Why it matters architecturally: STM is the concurrency-control layer of three production language runtimes (GHC's Control.Concurrent.STM since 2005, Clojure's dosync/refs since 2007, ScalaSTM since 2010) and the reference design for lock-free-data-structure papers using TL2-style versioning as a building block (Spiegelman, Golan-Gueta, Keidar 2016).
  • Historically: STM moved from a 1993 hardware-support proposal (Herlihy & Moss, ISCA 1993) to a pure-software algorithm two years later (Shavit & Touitou, PODC 1995) to a production-grade commit protocol eleven years after that (TL2, DISC 2006) — the arc from "possible" to "practical" is a case study in systems-research maturation.
  • Engineering muscles built: optimistic concurrency control end-to-end (read validation, commit-time locking, ABA-safe versioning); epoch-based memory reclamation (the same technique underlies crossbeam-epoch, RCU in the Linux kernel, and Java's StampedLock); contention management (the same back-off/priority machinery appears in database deadlock detectors); formal correctness testing via a sequential oracle plus systematic interleaving search.
  • Cross-links to sibling systems: the version-clock validation here is architecturally identical to MVCC in Postgres/CockroachDB (a read snapshot validated against a commit timestamp); the epoch reclamation (§19) is the same technique as the Linux kernel's RCU; the contention manager (§17) mirrors deadlock-detection retry logic in a distributed lock manager.
  • Calibration value: an engineer who has built this can correctly judge, in a design review, whether a proposed "just add a global lock" fix to a contended data path is actually cheaper than the STM alternative — a judgment call requiring having felt both the mutex-contention wall and the STM-abort-rate wall firsthand.

What Mastery Looks Like (bar for a reader who has internalized this blueprint):

  • Explain, without notes, why TL2's read validation happens at commit time rather than per-read, and the abort-rate cost of the alternative — demonstrated in Phase 2 (§14).
  • Trace a two-transaction interleaving that would violate opacity but not linearizability, and say why the distinction matters — demonstrated in Phase 6 (§18).
  • Design the wait-set wakeup protocol for retry from first principles, including why an empty read set at retry time is a deadlock — demonstrated in Phase 3 (§15).
  • Explain why closed nesting was chosen over open nesting and name the composability property open nesting breaks — demonstrated in Phase 4 (§16).
  • Compute, from the System Constraints table (§4), the point at which the global version clock itself becomes the bottleneck — demonstrated in the Back-of-Envelope Capacity Model (§34).
  • Design a contention manager's back-off ladder and priority-bump rule and predict its livelock-freedom argument — demonstrated in Phase 5 (§17).
  • Explain the publication safety problem and why the naive fix is wrong — demonstrated in Phase 9 (§21) and Threat Model row T7.

User code issues atomically(|tx| ...) closures; tx never escapes the closure (a lifetime parameter enforces this, ADR-01, P5) — the sole entry point; there is no way to read or write a TVar outside a transaction.

stm-core facade is the crate-root re-export surface (§11); it owns no state — every call forwards into a Tx or a TVar.

Tx accumulates the read set and write set as the closure runs; stack-allocated per atomically call (ADR-21) with inline capacity 8 (ADR-22) sized to the common small-transaction case.

stm-clock is the only contention point in the architecture (P1): reads/writes during the transaction body touch no shared state beyond the TVar's own fields; conflicts surface exclusively at the five-step commit sequence (§14.2).

TVar<T> is the shared transactional cell: a version-and-lock word packed into one AtomicU64 (I5) plus an AtomicPtr<T> to the current heap-allocated value (ADR-03).

stm-wait holds, per TVar, the set of parked transactions waiting on a retry; a successful commit drains and wakes every waiter whose read set included that TVar (§15.3).

stm-gc retires the old heap value of every write into crossbeam-epoch's reclamation list; a value is freed only once every transaction that could hold a pointer to it has advanced past the epoch it was retired in (§19.1).

stm-verify is off the runtime critical path but on the CI critical path: it proves the other six boxes satisfy opacity (I1) under every interleaving it can enumerate or sample (§20).

Four properties referenced throughout: optimistic reads (contention only at commit, P1); the version clock totally orders commits (I2); validation is per-commit not per-read (§8.4); opacity is the correctness contract, not an optimization (I1).

6. Design Principles

P1 — Commit is the only contention point. Rule: reads/writes during a transaction body touch no shared mutable state beyond a TVar's own fields; conflicts surface exclusively in the five-step commit sequence (§14.2). Tradeoff: optimism means wasted work on abort. Operational implication: abort-rate telemetry (M6/M7) is the primary health signal, not lock-wait time. Violation: adding shared coordination outside commit collapses to lock-based STM, defeating the entire performance argument.

P2 — TL2 is the algorithm (Dice-Shalev-Shavit, DISC 2006). Rule: optimistic, version-clock-based, commit-time write-locking. Alternatives (TinySTM encounter-time locking, NORec value-based validation) rejected in ADR-02. Tradeoff: pays a global-clock fetch_add per commit (a serialization point, §34) for O(1) validation per read. Operational implication: the global clock's throughput ceiling (§34) is the hard scaling wall. Violation: switching validation strategy without an ADR breaks I2's proof, written specifically against TL2's five-step sequence.

P3 — Heap-allocated TVar values behind an AtomicPtr. Rule: TVar<T> holds a pointer to a heap-allocated T; commits publish a new allocation. Tradeoff: an allocation + retire per write vs. requiring T: Copy for in-place updates. Operational implication: allocator pressure is visible in stm-bench's allocation-count assertions (§22.3, §30). Violation: in-place mutation without T: Clone is unsound for a reader that already loaded the old pointer — the read tears (I4).

P4 — Epoch reclamation, never GC, never leaks. Rule: every retired TVar value goes through stm-gc (crossbeam-epoch). Tradeoff: reclamation latency (values freed only once every pinned thread advances past the retire epoch) vs. correctness. Operational implication: a thread pinned indefinitely stalls reclamation process-wide (§19.6, FM-7). Violation: freeing eagerly is a use-after-free the moment a concurrent reader holds the old pointer.

P5 — The transaction is a closure; Tx cannot escape it. Rule: atomically(|tx: &mut Tx| -> R); Tx's lifetime is tied to the closure invocation (ADR-01). Tradeoff: closures cannot easily return borrowed data from tx; users clone out. Operational implication: no runtime check is needed — the compiler rejects the escape. Violation: a smuggled Tx handle reads/writes after commit/abort, corrupting an unrelated future transaction's read set.

P6 — retry is a control-flow marker, not a panic. Rule: retry() returns an internal AbortReason::Retry propagated through Result, never panic!. Tradeoff: every commit-path function must thread this value through rather than relying on unwinding. Operational implication: catch_unwind is reserved for genuine user-code panics (T6), keeping the two failure classes distinguishable in telemetry. Violation: implementing retry via panic conflates "wants to wait" with "crashed," corrupting FM-6's detection logic.

P7 — or_else is lazy; read sets union (Harris et al., PPoPP 2005). Rule: alt2 runs only if alt1 returns Retry; the wait-set registered on retry is the union of both branches' read sets. Tradeoff: alt1 may do wasted work before retrying; running both eagerly wastes strictly more. Operational implication: or_else chains longer than four branches show up as elevated read-set-size telemetry (§26). Violation: registering only alt2's read set misses wakeups triggered by alt1's reads — a lost-wakeup bug (FM-4).

P8 — Nested transactions are closed, sharing the outer's context. Rule: a nested atomically appends to the outer's read/write sets rather than opening an independent commit point (§16.1). Tradeoff: no independent visibility for inner writes (rejects open nesting, §16.6). Operational implication: nesting depth is bounded by stack, not by a nesting-table data structure. Violation: allowing inner commits to become visible before the outer commits breaks the outer transaction's atomicity — the exact property STM exists to provide (I1).

P9 — Livelock is prevented by back-off plus priority, never blind spin. Rule: an aborted transaction backs off exponentially (§17.1) and, past a threshold, becomes priority and may abort a non-priority holder (§17.2, Felber et al. 2008). Tradeoff: priority-abort adds a cross-transaction coordination point P1 otherwise avoids — accepted only past the abort-count threshold. Operational implication: aborted_count histograms are the leading indicator of a forming livelock. Violation: no back-off ladder lets two symmetric high-frequency writers abort each other indefinitely (FM-8, T4).

P10 — No global mutable state outside a World value. Rule: the version clock and epoch reclaimer live in a World; World::global() is the default, World::new() exists for isolated tests. Tradeoff: every API implicitly threads a World reference, adding indirection. Operational implication: loom/shuttle test isolation (§20) needs no process-wide reset between runs. Violation: a hard-coded global clock makes every loom/shuttle test interfere with every other, invalidating the harness.

P11 — TVar<T>: Send + Sync iff T: Send + Sync, enforced by the type system. Rule: no manual unsafe impl Send; the auto-trait propagates. Tradeoff: none — free correctness. Operational implication: a compile error, not a data race, is the failure mode for a non-thread-safe T. Violation: manually forcing Send/Sync on TVar<Rc<T>> reintroduces the exact race the type system prevents.

P12 — Determinism in verification: loom + shuttle are mandatory, not optional. Rule: every commit-path change ships with a loom test (TC 2–3, exhaustive) and a shuttle test (TC 4–16, randomized, checked-in failing seeds) before merge (§20). Tradeoff: loom's exhaustive search is slow, kept deliberately small (§20.6). Operational implication: a merged commit-path PR without a green loom run is presumed broken. Violation: skipping the harness reproduces the Communion.md failure mode §16 of the standard exists to end.

P13 — Cross-architecture correctness is a first-class CI dimension. Rule: x86-64 and aarch64 run natively; a documented instruction-sequence extraction feeds herd7 for a Power memory-model check (§20.6). Tradeoff: aarch64's weaker default model surfaces missing fences x86 masks. Operational implication: a test green on x86 alone is not a correctness signal. Violation: shipping a fence bug only aarch64 exposes reaches production undetected (FM-9).

P14 — The C ABI is the only non-Rust embedding surface. Rule: stm-abi's cbindgen-generated header is the sole non-Rust contract (§21); no second bespoke FFI convention is invented per embedder language. Tradeoff: necessarily type-erased (void* values), pushing type-safety onto the embedder. Operational implication: ABI version stamping (§21.4) is the only defense against version skew. Violation: a second bespoke FFI layer duplicates the type-erasure bugs instead of fixing them once.

8. Domain Model

8.1 The transaction state machine

State Entry Reads/Writes allowed Exit transitions
Active atomically begins; start_version = clock.load() Yes, into read_set/write_set → Committing (body returns) / → Retrying (retry()) / → Aborting (panic/user abort)
Committing Body returned a value No → Committed (validation passes) / → Aborted (validation fails, loop to Active with fresh start_version)
Retrying retry() called, read set non-empty (I7) No → Parked (wait-set registration complete)
Parked Waker registered on every read-set TVar No → Active (a relevant commit drains the wait-set)
Aborting Validation failed or user abort No → Active (retry from scratch, back-off per §17)
Committed Publish complete, locks released — Terminal

8.2 Read-set / write-set representation

read_set: SmallVec<[(TVarId, ObservedVersion); 8]>; write_set: SmallVec<[(TVarId, NewValue); 8]> (ADR-22). A tx.write to a TVar already in write_set overwrites the buffered entry (last-write-wins within one transaction); a subsequent tx.read of that same TVar returns the buffered write, never re-touching the shared AtomicPtr (P1).

8.3 The versioned-lock schema (TL2)

VLock (AtomicU64):
  bit 0        : locked (1 = held by a committing writer)
  bits 1..63   : version (monotonic, from the global clock)

encode(version, locked) = (version << 1) | (locked as u64)
decode(word)            = (word >> 1, word & 1)

Lock acquire: CAS (v<<1)|0 → (v<<1)|1. Lock release+publish: store (v_new<<1)|0. Validation: decode(word) == (observed_version, 0) OR the TVar is in our own write set (I3, I5).

8.4 Commit-time validation and conflict detection

Conflict is structural: transaction A conflicts with committed B iff A.read_set ∩ B.write_set ≠ ∅ and B's commit version falls inside (A.start_version, A.commit_attempt]. TL2 detects this without a per-object conflict graph — it re-reads each TVar's current VLock at validation time (§14.2 step 4) and compares against the value observed at read time: O(|read_set|) per commit attempt, not O(active transactions) — the key TL2 scaling property (P2, referenced in §34).

8.5 Worked example — two-account transfer under contention

Accounts A = TVar(100), B = TVar(50). Thread 1 runs transfer(A, B, 30): reads A@v0=100, reads B@v0=50, writes A=70, writes B=80. Concurrently thread 2 runs transfer(B, A, 10): reads B@v0=50, reads A@v0=100, writes B=40, writes A=110.

Both write sets overlap ({A, B}) — the canonical-order lock (§14.2 step 1, sorted by TVarId) means both threads attempt to lock A then B in the same order, so no deadlock occurs; one thread's CAS on A fails and it aborts before ever locking B (I3). Say thread 1 wins: locks A, locks B, allocates commit version v1 = clock.fetch_add(1), validates (both TVars still at v0, locks held by self — valid), publishes A=70, B=80 at v1, unlocks. Thread 2's CAS on A failed at step 2; it aborts, backs off (§17.1, aborted_count=1, no delay yet), retries from scratch with start_version=v1: reads B@v1=80, reads A@v1=70, writes B=70, writes A=80. Commits cleanly. Final state A=80, B=70 — the invariant A+B=150 holds throughout (I1: no thread ever observed an inconsistent intermediate sum).

8.6 Malformed-input / hazard example — torn reads without commit-time validation (Harris & Fraser, OOPSLA 2003, Fig. 4)

Setup: x = TVar(0), y = TVar(0); the application invariant x == y is maintained by every committed transaction. A transaction body reads x into a local, then — only when that value is nonzero — busy-waits re-reading y until it too is observed nonzero: a pattern that is legal Rust but pathological under STM, since it never returns to let the runtime validate.

timeline →
T:      read(x)=0 ......... [reordered: T now sees x=1] .. read(y) read(y) ...
Other:            commit: x=1, y=1 (v1)

If T's read of x is reordered (by CPU or missing fence) to observe the post-commit value while its later reads of y still observe the pre-commit value, T busy-waits forever: the guard is true but y never becomes nonzero from T's point of view. This is not a validation failure — validation never runs, because the transaction body never returns. TL2's commit-time check (§14.2 step 4) is powerless against a transaction that hangs before reaching it; the defenses are (a) a correct Acquire fence on every TVar read so x and y can never be observed out of commit order (I4), and (b) --features paranoid per-read validation (§18.6) that aborts as soon as inconsistency is detected. Documented as Threat Model T5 and Pitfall §18.6.

8.7 Failure-path example — panic during commit

Thread holds locks on {A, B} mid-commit (§14.2 step 2 complete, step 4 in progress) when the validation-comparison code panics (e.g., an allocator failure inside the retire path, §19). The commit's RAII guard (CommitGuard, §14.7) runs on unwind: releases every lock acquired so far by storing (observed_version<<1)|0 back into each held TVar's VLock, then propagates the panic to the caller as AbortReason::UserAbort wrapping the original payload. No TVar is left locked (I8); no partial write is published (I1). The caller's atomically does not auto-retry on UserAbort (only on Retry) — the panic surfaces to the application, per P6's distinction between "wants to wait" and "crashed."

8.8 Write-only transactions (conflict-detection edge case)

A transaction that only writes (never reads) a TVar — e.g. an unconditional tx.write(&v, new_value) with no preceding tx.read(&v) — never adds that TVar to its read_set (§8.2), and so never validates it against a concurrent writer's commit (§8.4's validation is defined over the read set, not the write set). This is not a bug: TL2's correctness argument (§14.4) only requires that a transaction's read set be consistent at commit; a pure write has no prior observation to be inconsistent with. Two write-only transactions to the same TVar still conflict at the lock-acquisition step (§14.2 step 2, I3) — one's CAS fails and it aborts — so mutual exclusion on the write itself is preserved even though no read-set validation is involved. The distinction matters operationally: a workload dominated by write-only transactions to a shared TVar shows contention exclusively as stm_lock_cas_fail_total (T11), not as stm_opacity_violation_total, since there is no read-set-consistency question to violate.

8.9 Contention-manager state (detailed in §17)

State Trigger Action Exit

BackingOff aborted_count 4–15 Exponential spin/yield delay (§17.4) → Priority at abort 16
Priority aborted_count > 16 May abort a non-priority lock holder on CAS failure (§17.5) → Normal after next successful commit

                   fn write<T>(&mut self, tvar: &TVar<T>, v: T)
                   fn retry(&mut self) -> !
                   fn or_else<F, G, R>(&mut self, a: F, b: G) -> R }
  • TVar<T> — ownership: shared via Arc<Inner<T>>, clone is a cheap refcount bump; mutation: only via a committed write inside atomically; concurrency: Send + Sync iff T: Send + Sync (P11); persistence: none; serialization: not Serialize by default; compatibility: T's layout is opaque to the C ABI (type-erased, §21).
  • Inner<T> — ownership: heap-allocated once, its address is TVarId, never moved (I6); mutation: value/vlock mutated only under commit-protocol discipline (§14); concurrency: all-atomic fields; persistence: none; compatibility: layout stability enforced by ADR-19's static assertion.
  • Tx<'w> — ownership: stack-allocated, borrows World for its lifetime (ADR-21); mutation: read/write sets grow monotonically during Active (§8.1); concurrency: Tx: !Send (I6); persistence: none; compatibility: internal, no external API stability guarantee.
  • AbortReason — ownership: owned, returned by value; mutation: immutable once constructed; concurrency: Send (crosses the try_atomically boundary); persistence: none; compatibility: adding a variant is a breaking change (non-exhaustive recommended).
  • World — ownership: process-wide singleton (World::global()) or an isolated instance per test (World::new(), P10); mutation: clock via fetch_add only; concurrency: Send + Sync; persistence: none — a dropped World loses all TVar state (I13); compatibility: internal, wrapped by stm-abi for the C boundary (§21).

  • An empty closure passed to atomically (touches no TVar) must not panic and must return ().

12.9 Failure Analysis

A panic inside the Phase-0 stub closure propagates directly (no catch_unwind yet — that lands in Phase 2's commit guard, §14.7); this is intentional, so Phase 2's introduction of panic-safety is a visible, reviewable diff rather than baked in silently from day one.

12.10 Operational Notes

No telemetry yet — tracing spans are introduced in Phase 2 alongside the real commit protocol (§26). The Phase-0 deliverable is not deployed; it is the substrate the remaining eleven phases build on.

13. Phase 1 — TVar & Transaction-Context Primitives

13.1 Objectives

  • Give TVar<T> its real layout: AtomicPtr<T> value + packed version-and-lock word (§8.3, ADR-19).
  • Give Tx a real read/write-set discipline (§8.2) with no commit protocol yet (that is Phase 2, §14).
  • Establish TVarId stability (I6) as the heap address of Inner<T>.

13.2 Detailed Implementation Steps

  • Implement Inner<T> per §11's signature: value: AtomicPtr<T>, vlock: AtomicU64 (encode/decode per §8.3, I5), waiters: WaitSet (stubbed empty until §15).
  • TVar::new(v) boxes v, sets vlock to encode(0, false).
  • tx.read(tvar): if tvar.id() is in write_set, return the buffered value (P1, §8.2); else load value (Acquire), load vlock (Acquire), push (id, version) onto read_set.
  • tx.write(tvar, v): upsert (id, v) into write_set, overwriting any prior entry for the same id (§8.2).
  • Assert TVarId stability: Inner<T> is heap-allocated once and never moved (I6) — verified by a fixture that takes the address before and after a GC-triggering allocation storm.

13.3 Deliverable

tx.read on a fresh TVar returns its constructor value; tx.write followed by tx.read in the same transaction returns the buffered write, not the shared value; a TVar's vlock layout passes a static-size assertion (size_of::<AtomicU64>() == 8).

13.4 Acceptance Criteria

  • Conformance fixture single-tx/read-after-write.json passes: write 42, read back 42, without touching the shared AtomicPtr (verified by an instrumented counter asserting zero shared-state reads after the write).
  • size_of::<Inner<u64>>() <= 64 bytes (M-adjacent target from §4, one cache line).
  • 10,000 TVar::new/drop cycles under Miri report zero UB.

13.5 Conformance Fixtures

  • single-tx/read-after-write.json — write then read, expects the buffered value.
  • single-tx/tvarid-stability.json — 1,000 TVars allocated under memory pressure; asserts no TVarId collision or drift.
  • single-tx/malformed-double-write.json — two writes to the same TVar in one tx; expects last-write-wins, not an error.

13.6 Pitfalls

  • The TVar id is the address of the Inner<T> box; Inner<T> must never be moved (e.g. via Vec reallocation) — always heap-allocate through Arc (ADR-03), never inline in a growable container.
  • Packing version + lock-bit in one AtomicU64 (ADR-19, §8.3) is easy to get wrong on the shift direction; a fixture (tvarid-stability.json) and a doc comment pin the exact bit layout.
  • Reading value before vlock (wrong order) can observe a value newer than the version recorded — always load vlock first if a strict pairing is required by a future paranoid-mode check (§18.6).

13.7 Performance Concerns

tx.read's write-set lookup is O(|write_set|) linear scan over a SmallVec of capacity 8 (ADR-22) — faster than a HashMap for the common small-transaction case; document the crossover point (~16 entries) where a future large-transaction path might need a different structure (not built in Phase 0–11, noted as a scaling lever in §31).

13.8 Edge Cases

  • Reading a TVar whose vlock shows the locked bit set (another thread mid-commit) still records the pre-lock version in read_set — validation at commit time (§14) is what catches the conflict, not the read itself.
  • A transaction that writes to a TVar it never reads must still validate correctly at commit (write-only entries do not appear in read_set).

13.9 Failure Analysis

A TVar<T> whose T::drop panics during the box's deallocation (extremely rare, custom allocator failure) surfaces as a process abort, not a transaction abort — documented as outside the transactional-recovery envelope (this is a memory-allocator failure, not a commit-protocol failure).

13.10 Operational Notes

tracing spans introduced here: tvar.read, tvar.write (debug-level only — too high-volume for production sampling by default; see §26 for the sampling policy introduced in Phase 2).

14. Phase 2 — TL2 Commit Protocol

14.1 Objectives

  • Implement the five-step TL2 commit sequence (P2, ADR-02) end to end: lock, allocate version, validate, publish, unlock.
  • Introduce the global version clock (World::clock, I2) and prove I2/I3/I8 hold under loom TC 2–3.
  • Introduce panic-safety via the CommitGuard RAII pattern (§8.7).

14.2 Detailed Implementation Steps

  1. Sort write set by TVarId (ADR-19-adjacent ordering discipline) — the canonical lock order prevents deadlock between two transactions locking in opposite orders (P1).
  2. Acquire locks in sorted order: CAS each vlock from (version, 0) to (version, 1) (I3). A CAS failure aborts immediately (do not proceed to lock further TVars).
  3. Allocate commit version: world.clock.fetch_add(1, AcqRel) (I2, the sole serialization point, P1, applied from TL2, Dice-Shalev-Shavit DISC 2006).
  4. Validate read set: for each (id, observed_version), load the current vlock; valid iff version matches and (lock unheld OR held by self, i.e. the TVar is in our own write set) (I3, I5). This is the opacity check (I1, Guerraoui & Kapalka 2008).
  5. Publish or abort: on success, swap each written TVar's AtomicPtr to the new heap value (retire the old one into stm-gc, §19, ADR-03) and store (commit_version, 0) into vlock (Release). On validation failure, release all held locks (store (version, 0)) and abort (I8).
  • Wrap steps 2–5 in CommitGuard, whose Drop releases any locks still held if a panic unwinds through the sequence (§8.7).

14.3 Deliverable

A two-thread "transfer between accounts" test (§8.5) runs concurrently under real threads and under loom (TC 2–3) and never observes an inconsistent sum; the commit protocol passes Miri with zero UB.

14.4 Acceptance Criteria

  • Loom exhaustive search at TC 2 and TC 3 over the transfer fixture: 0 opacity violations, 0 leaked locks (I8), verified via the stm_lock_leak_total counter staying 0 across all enumerated interleavings.
  • 1,000,000-iteration real-thread stress run (16 threads, 100 accounts) preserves the invariant sum(accounts) == initial_sum with zero violations.
  • Commit latency p50 ≤ 400 ns uncontended (M4), measured via stm-bench.

14.5 Conformance Fixtures

  • two-tx-conflict/transfer-canonical-order.json — the §8.5 worked example, exact expected final balances A=80, B=70.
  • two-tx-conflict/lock-cas-failure.json — forces a CAS failure on the second lock acquisition; expects a clean abort with zero locks held afterward.
  • two-tx-conflict/malformed-negative-version.json — a corrupted fixture asserting a negative observed version; the runner rejects it as malformed input, not a runtime panic.

14.6 Pitfalls

  • Lock acquisition must use compare_exchange_strong, not _weak — spurious failures from _weak cause unnecessary aborts under low contention (P1 violation risk).
  • Validation must check both version and lock-bit; a TVar locked by another transaction is in-flight and must abort us even if the version otherwise matches (I3).
  • The sort order on locks must be by TVarId consistently; changing the sort criterion (e.g. to a hash) between two code paths is a deadlock hazard the moment two transactions disagree on relative order.
  • A panic during commit must release acquired locks via CommitGuard's Drop, or I8 is violated the instant any commit-path code can panic (allocator failure, arithmetic overflow in debug builds).

14.7 Performance Concerns

The global clock's fetch_add is the only cross-transaction contention point in the common path (P1, §34); at ~5 ns/op on x86 it serves ≈200 M commits/s (M-ceiling, §4) — if this becomes the bottleneck the Phase-2 stretch is a lazy-clock optimization (documented, not built, §37). Per-commit cost for an 8-read/2-write transaction: ≈100 ns fixed + N × 30 ns per read/write (§30.1 derives this fully).

14.8 Edge Cases

  • A transaction whose write set is empty (read-only) skips steps 1–2 entirely and validates only; this must not allocate a commit version if nothing was written (an optimization deferred to §37, not required for Phase 2 correctness).
  • Two transactions racing on the very same TVar with identical writes still must go through full validation — value equality does not exempt a write from version-bump discipline (TL2's classic optimization to skip the bump on bitwise-equal values is explicitly not implemented in Phase 0–11, per §37).
  • A commit where the write set contains a TVar that was already retired by another epoch (use-after-retire) must be structurally impossible — the epoch pin (§19) guarantees this, verified by ASan.

14.9 Failure Analysis

A stuck lock (CAS acquired, process crashes before releasing) is unrecoverable in-process — this is the failure mode I8's "recovery: process restart" documents; a future durable-STM variant (§37 row 2) would need a WAL to recover from this class, out of scope here.

14.10 Operational Notes

tracing spans: commit.begin, commit.lock, commit.validate, commit.publish, commit.abort — each carries tx_id, read_set_len, write_set_len (§26). Metrics introduced: stm_commit_total{result=success|abort}, stm_commit_latency_seconds (histogram, feeds M4/M5).

15. Phase 3 — Retry & or_else Composition

15.1 Objectives

  • Implement retry() (§8.1 Retrying→Parked transition) and its wait-set registration (P6, Harris et al. PPoPP 2005, applied here).
  • Implement or_else with lazy evaluation and read-set union semantics (P7).
  • Prove I7 (non-empty read set required) and the wakeup-correctness property under loom.

15.2 Detailed Implementation Steps

  • tx.retry(): walk read_set; for each (id, _), register a Waker on that TVar's waiters (stm-wait, §11); abort with AbortReason::Retry (P6). Panic (debug assertion) if read_set is empty (I7).
  • The runtime parks the calling thread (std::thread::park, or .awaits under the ADR-12 async-aware feature) on Retry; a subsequent commit that touches any registered TVar drains that TVar's waiters and wakes every entry (§14.2 step 5 extended).
  • tx.or_else(alt1, alt2): snapshot the current read/write sets; run alt1. If it returns a value, commit normally (accumulated sets are the union so far). If it aborts with Retry, restore the snapshot and run alt2. If alt2 returns, commit (union of snapshot + alt1's reads + alt2's reads, P7). If alt2 also retries, propagate Retry with the union read set — a wakeup from either branch's reads must re-run the whole expression.
  • Wait-set entries are removed when their owning transaction terminates (commit, non-retry abort, or drop) — a scrub pass (detailed further in §19.5) prevents unbounded growth.

15.3 Deliverable

A "blocking queue" example (producer commits to a TVar<VecDeque<T>>; consumer calls retry() when empty) demonstrates a clean wake on the next producer commit; or_else passes a conformance subset where both branches are non-trivial and read disjoint TVars.

15.4 Acceptance Criteria

  • Fixture retry/blocking-queue.json: consumer parked on empty queue wakes within one commit cycle of a producer write, verified by a bounded-wait assertion (≤ 10 ms wall-clock in the real-thread test, unbounded-but-deterministic under loom).
  • Fixture or_else/union-readset.json: a wakeup triggered by a change alt1 (not alt2) read still re-runs the whole or_else expression — asserted by the read-set-union invariant (P7).
  • I7 debug-assertion fires (panic) on retry/malformed-empty-readset.json rather than hanging.

15.5 Conformance Fixtures

  • retry/blocking-queue.json — producer/consumer wakeup correctness.
  • retry/malformed-empty-readset.json — retry() with an empty read set; expects a panic, not a deadlock.
  • or_else/union-readset.json — wakeup sourced from alt1's read set after alt2 also retried.
  • or_else/lazy-evaluation.json — asserts alt2 is never invoked when alt1 succeeds (instrumented call counter).

15.6 Pitfalls

  • A retry() whose read set is empty is a permanent deadlock (the transaction will never wake) — the runtime panics on this rather than parking forever (I7).
  • A retry() whose read set is large registers many wakers; the cost is amortized per-TVar but is visible in stm_retry_readset_size telemetry (§26) — documented, not treated as a bug.
  • An or_else whose first branch performs side effects (only possible via unsafe, illegal in STM) leaks the side effects on retry — documented constraint, not runtime-detectable in Phase 0–11.
  • Forgetting to register alt1's read set on a subsequent alt2 retry produces a lost-wakeup bug (FM-4) — the union-read-set fixture (or_else/union-readset.json) exists specifically to catch this regression.

15.7 Performance Concerns

Wait-set registration is O(|read_set|) wakers per retry() call; the wakeup dispatch on commit is O(|waiters|) per touched TVar — both amortize over the number of committed transactions, not the wait-set size, so a "wake storm" from one commit touching a heavily-retried TVar is bounded by that TVar's actual waiter count, not by unrelated activity (§17.6 pitfall cross-reference).

15.8 Edge Cases

  • A transaction that calls retry() inside a nested atomically propagates the retry to the outermost transaction (interacts with Phase 4, §16) — the wait-set registration covers the entire accumulated (outer + inner) read set.
  • A waker registered on a TVar that is dropped before ever being touched again (a leaked wait-set entry) must be cleaned up by the scrub pass (§19.5), not leaked indefinitely.
  • or_else where both branches read the exact same TVar set must not double-register wakers for that TVar (dedup on TVarId during union).

15.9 Failure Analysis

A parked thread that never wakes (a retry() on a TVar set that legitimately never changes again, e.g. the process is shutting down) is detected operationally via stm_parked_thread_count staying nonzero past a configurable threshold — the runbook (docs/runbooks/livelock.md) documents the diagnostic, though this is a starvation symptom rather than a commit-protocol bug (cross-referenced from FM-8).

15.10 Operational Notes

tracing spans: retry.park, retry.wake; metrics: stm_retry_total, stm_parked_thread_count (gauge), stm_wakeup_dispatch_total. A wakeup storm (many wakes per commit) is visible as a spike in stm_wakeup_dispatch_total and is the first thing the on-call engineer checks per docs/runbooks/livelock.md.

16. Phase 4 — Nested Transactions

16.1 Objectives

  • Implement closed nesting (P8, ADR-07): a nested atomically appends to the outer's read/write sets rather than opening an independent commit point.
  • Prove I9 (nested writes invisible outside the outer chain until outermost commit) under a conformance fixture and loom.
  • Document, but do not build, open nesting (§16.6) as a rejected alternative.

16.2 Detailed Implementation Steps

  • Tx::parent: Option<&'w Tx<'w>> (§11) links a nested transaction to its enclosing one.
  • A nested atomically(|tx| ...) call, when tx.parent.is_some(), does not allocate a fresh read_set/write_set — it borrows the outer's and appends directly (P8).
  • The nested call's start_version is inherited from the outer, never re-read from the clock (a nested transaction cannot observe a version newer than what its outer has already committed to).
  • A nested retry() propagates AbortReason::Retry up through the parent chain to the outermost transaction; the wait-set registration at the top covers the full accumulated read set (interacts with §15.2).
  • Commit only happens once, at the outermost atomically — inner atomically calls return their closure's result directly with no independent validate/publish step (this is what "closed" means, contrasted with open nesting in §16.6).

16.3 Deliverable

A nested atomically inside another runs to completion and commits as part of the outer transaction, verified by fixture nested/closed-commit.json; a nested retry() correctly propagates to the outermost transaction, verified by nested/propagated-retry.json.

16.4 Acceptance Criteria

  • Fixture nested/closed-commit.json: an outer transaction containing a nested one, both touching disjoint TVars, commits both sets of writes atomically — verified by an external observer thread that can never see only one side committed (I9).
  • Fixture nested/propagated-retry.json: a nested retry() correctly wakes when a TVar in the outer's read set (not touched by the inner) changes, since the accumulated read set is shared (P8).
  • Nesting depth of 100 (a realistic worst case) does not overflow an 8 MB default thread stack, verified by a stress fixture.

16.5 Conformance Fixtures

  • nested/closed-commit.json — atomic visibility of combined outer+inner writes.
  • nested/propagated-retry.json — retry propagation through the parent chain.
  • nested/malformed-cycle.json — a fixture attempting a self-referential parent pointer; the runner rejects it at construction (impossible via the safe API, exercised only through the internal test harness).

16.6 Pitfalls

  • The nested or_else interacts with the outer's read set (§15); the wait-set registration on a nested retry must include the outer's accumulated reads, not just the inner's.
  • Open nesting is a research topic; shipping it would break the composability property that is this whole project's thesis (§2) — resist the temptation even when a caller asks for independent inner-commit visibility. Design-space note: closed nesting (chosen, ADR-07) means inner writes are not visible to any other transaction until the outer commits; open nesting (rejected) would let the inner commit independently, becoming visible before the outer commits — which breaks composition, since a function written assuming closed-nesting invisibility cannot be drop-in replaced with an open-nesting version (callers depend on I9 to reason about the whole call's atomicity). Open nesting does reduce false-conflict aborts for long-running outer transactions with independent inner sub-transactions, but this project's target workloads (§1) do not have that shape (see §36 for the alternative-architecture sketch).
  • A nested transaction that would (hypothetically, under open nesting) commit internally but whose outer then aborts must roll back the internal commit too — closed nesting sidesteps this entire class of bug by construction, which is the strongest argument for P8.
  • Nesting depth is bounded by stack, not by an explicit counter; a runaway recursive nested-atomically call surfaces as a stack overflow, not a graceful STM-level error (documented in §16.8).

16.7 Performance Concerns

Nesting adds zero allocation (P8 — no new read/write-set allocation per nested call) but does add one pointer-chase per nested read/write to check tx.parent — negligible relative to the atomic-load cost already paid (§30.1).

16.8 Edge Cases

  • Nesting depth bounded only by stack (§16.6) — a fixture exercises depth 100 explicitly; depths beyond that are documented as an application-level anti-pattern, not a library-level bug to fix.
  • A nested transaction whose body panics propagates the panic through every enclosing atomically, releasing all locks via the outermost CommitGuard (§14.2) — verified by a fixture that nests three levels deep and panics at the innermost.
  • A nested or_else where the inner alternative reads TVars already in the outer's write set must correctly see the outer's buffered writes (P1's write-set-shadows-shared-state rule applies transitively through the parent chain).

16.9 Failure Analysis

A panic at any nesting depth unwinds cleanly through every CommitGuard in the parent chain (§14.2, §16.8); no partial nested commit is ever published, because closed nesting means there was never an independent commit point to partially publish (I9's structural guarantee doubles as the failure-mode simplifier here).

16.10 Operational Notes

tracing spans: nested.enter, nested.exit, each carrying depth and parent_tx_id; metric stm_nesting_depth (histogram) flags workloads approaching the stack-overflow risk zone documented in §16.8.

17. Phase 5 — Contention Management & Livelock Prevention

17.1 Objectives

  • Implement the back-off ladder (P9, Felber, Fetzer, Riegel PPoPP 2008 — the TinySTM contention-manager lineage) bounding retry latency after repeated aborts.
  • Implement priority bumping (§17.5) to guarantee I12 (bounded fairness among conflicting writers).
  • Prove livelock-freedom under a 16-thread adversarial stress fixture (M7).

17.2 Detailed Implementation Steps

  • Track aborted_count: u32 per Tx (§11); increment on every abort (validation failure or explicit retry-then-restart cycle).
  • Back-off ladder (P9): aborts 1–3 → retry immediately; aborts 4–7 → spin back-off 100ns × 2^(N-4); aborts 8–15 → yield back-off 1µs × 2^(N-8); aborts 16+ → sleep back-off 100µs × 2^(N-16), capped at 100ms.
  • Priority bump: a transaction with aborted_count > 16 sets a priority flag in its commit-attempt header (I12). On the next commit attempt, if a CAS lock-acquisition fails and the current holder is not priority, the priority transaction sets the holder's abort_flag (a cooperative signal checked at the holder's next read/write/validation step).
  • The aborted (preempted) holder observes abort_flag at its next operation and aborts voluntarily, releasing the contested lock; the priority transaction retries and (with the contest cleared) proceeds.
  • Priority resets to false after the transaction's next successful commit (I12 — at most one priority holder per conflict set at any instant).

17.3 Deliverable

A "two-counter ping-pong" test under 16-thread contention completes in bounded time (every transaction commits within 24 attempts, M7); a livelock-stress fixture confirms no thread starves indefinitely.

17.4 Acceptance Criteria

  • Abort rate under the 16-thread single-hot-TVar workload ≤ 40%, bounded retries ≤ 24 per transaction (M7, quantified in §4).
  • Priority-fairness fixture priority-fairness.json: no more than one transaction holds priority=true among a mutually-conflicting write set at any sampled instant (I12).
  • The back-off ladder's four tiers are each independently unit-tested against the documented formula (100ns × 2^(N-4), etc.) with a tolerance of ±10%.

17.5 Conformance Fixtures

  • livelock/two-counter-pingpong.json — 16 threads incrementing two shared counters in alternating order; every thread must commit within the bounded retry ceiling.
  • livelock/priority-fairness.json — asserts I12 under a scripted contention scenario.
  • livelock/malformed-negative-abort-count.json — a corrupted fixture with a negative aborted_count; the runner rejects it as malformed, not a panic in the back-off calculation.

17.6 Pitfalls

  • Back-off introduces fairness interaction with cooperative (green-thread/async) scheduling; under the async-aware variant (ADR-12), back-off uses an async sleep primitive rather than blocking the executor thread.
  • Priority bumping can itself create a symmetric livelock if two transactions both reach aborted_count > 16 simultaneously and both try to preempt each other — mitigated by I12's at-most-one-priority-holder-per-conflict-set invariant, but documented as a residual risk requiring the fixture in §17.5 to catch regressions. Protocol detail (Felber et al. 2008's TinySTM contention-manager approach, applied here): (1) on the next commit attempt past aborted_count=16, mark the transaction's header priority=true; (2) when acquiring write-set locks, a priority transaction whose CAS fails inspects the holder's priority flag, and if the holder is not priority, sets the holder's cooperative abort_flag; (3) the non-priority holder, at its next read/write/validation step, observes abort_flag and aborts voluntarily; (4) the priority transaction retries with the contested lock now free — this prevents starvation by giving long-failing transactions the right to preempt short-running ones, at the cost of the one cross-transaction coordination point P9 explicitly permits past the abort threshold.
  • A priority transaction that still fails to commit even after preempting its holder signals a deeper problem (a genuinely hot-spot TVar under sustained multi-writer load) — the runbook (docs/runbooks/livelock.md) documents the diagnostic path, not a further escalation tier.
  • The back-off ladder's constants are workload-calibrated, not universal; document the tuning knob (atomically_with_backoff(custom_ladder)) rather than hard-coding assumptions about the caller's contention profile.

17.7 Performance Concerns

The back-off ladder trades latency for reduced wasted work: at 16+ aborts, a 100µs+ sleep is orders of magnitude slower than an uncontended commit (M4's 400ns) — by design, since a transaction reaching that tier has already demonstrated persistent contention and further immediate retries would only worsen it (§30 ties this to the overall abort-rate/throughput tradeoff curve).

17.8 Edge Cases

  • A transaction whose aborted_count overflows u32 (4 billion aborts) is treated as a saturating clamp at u32::MAX, keeping it permanently in the priority-eligible tier rather than wrapping back to non-priority (a wraparound would silently un-prioritize a maximally-starved transaction).
  • Two priority transactions contending on disjoint TVar sets do not interact — I12's "per conflict set" scoping means priority is not a single process-wide flag but tracked per contested lock.
  • A priority transaction that succeeds on its very first post-priority attempt (no further contention) still correctly resets priority=false after that commit (I12).

17.9 Failure Analysis

Sustained abort rates above M7's 40% threshold, with retries approaching or exceeding the 24-attempt ceiling, indicate either a genuine hot-spot TVar (expected under adversarial load, T1) or a back-off ladder miscalibration for the workload — docs/runbooks/livelock.md walks the on-call engineer through distinguishing the two via stm_aborted_count histogram shape (a fat tail past 16 indicates the latter).

17.10 Operational Notes

Metrics: stm_aborted_count (histogram per transaction), stm_priority_holder_count (gauge, feeds I12's telemetry), stm_backoff_duration_seconds (histogram by tier). Alerting: page when stm_aborted_count p99 exceeds 20 sustained for 5 minutes (approaching the 24-attempt ceiling, M7).

18. Phase 6 — Opacity Verification & Model Checking

18.1 Objectives

  • Implement the opacity oracle (§18.3): a sequential reference STM checked against the real implementation's observed histories.
  • Implement --features paranoid per-read validation (§18.6) as a debug-mode defense against the torn-read hang (§8.6).
  • Prove I1 holds across the full conformance corpus and 10,000 random property-test op sequences.

18.2 Detailed Implementation Steps

  • Build the sequential oracle: a single-threaded reference implementation backed by HashMap<TVarId, Box<dyn Any>>, applying every operation in program order with no concurrency (Guerraoui & Kapalka 2008's opacity definition, applied here).
  • Run identical op logs against the real STM (under real threads or loom-scheduled interleavings) and the oracle; check the STM's observed history is opacity-consistent with some sequential interleaving the oracle could have produced (a Wing-Gong-Liu-style linearization search, adapted for opacity rather than linearizability).
  • --features paranoid mode: on every tx.read, re-validate the entire current read_set (not just the newly-read TVar) against the live vlock state; abort immediately if any entry has advanced past its observed version (§8.6's defense against a torn-read hang before commit-time validation ever runs).
  • Property-test generator (proptest): random TVar counts (1–100), random per-tx op sequences (read/write/retry/or_else/nested), random thread counts (1–32); the property asserted is "every random run is opacity-consistent — no inconsistent read ever reaches a commit."

18.3 Deliverable

The opacity oracle differential-checks the full conformance corpus (conformance/corpora/) with zero violations; --features paranoid catches the §8.6 torn-read hazard in a targeted fixture that reproduces Harris & Fraser's Figure 4 scenario.

18.4 Acceptance Criteria

  • 10,000-iteration proptest run: zero opacity violations (stm_opacity_violation_total stays 0, I1).
  • Fixture opacity/harris-fraser-fig4.json: reproduces the torn-read hazard under a scripted interleaving; --features paranoid build aborts the transaction before the busy-wait can hang; the non-paranoid build is documented as relying on correct fencing (I4) instead.
  • Loom exhaustive search (TC 2–3) over every conformance fixture reports zero opacity violations.

18.5 Conformance Fixtures

  • opacity/harris-fraser-fig4.json — the torn-read hazard from §8.6, exact reproduction.
  • opacity/random-proptest-seed-*.json — checked-in failing seeds from any historical proptest regression.
  • opacity/malformed-oracle-mismatch.json — a deliberately-corrupted fixture whose expected oracle output does not match any valid interleaving; the runner must flag it as a fixture-authoring error, not a false STM failure.

18.6 Pitfalls

  • An invariant-checking transaction (one whose body asserts application invariants) must itself be re-runnable on abort; side-effecting invariant checks are out of scope and will double-report on retry.
  • Opacity is strictly stronger than linearizability (Herlihy & Shavit, Ch. 9 vs. Ch. 18) — document the relationship explicitly in docs/architecture/opacity.md so a future contributor does not assume linearizability testing alone suffices. Runtime-check detail: in --features paranoid, every tx.read re-validates by walking the existing read_set after loading the newly-read TVar — for each (other_id, observed_version), load other_id's current vlock version, and abort immediately if any has advanced past observed_version (an opacity violation caught in-flight, not merely prevented from committing). This is O(|read_set|) per read (vs. O(|read_set|) once per commit in the non-paranoid path).
  • A T whose Drop has observable side effects (e.g. closes a file) conflicts with the transaction re-run semantics (a retried transaction re-constructs and re-drops values) — document as a constraint on what T may safely be.
  • A transaction that re-reads its own buffered write via the write-set shadow (P1, §8.2) is fine and must not be flagged as an opacity violation by the oracle — a common false-positive if the oracle's history recording does not account for write-set shadowing correctly.

18.7 Performance Concerns

The oracle's differential check is CI-only (never on the production commit path, §22); --features paranoid is explicitly a debug/test build flag with a documented ≥5x commit-latency cost, gated out of release builds by default (§27 compatibility notes on feature-flag stability).

18.8 Edge Cases

  • A property-test run that generates zero TVars (degenerate case) must complete without division-by-zero or panics in the generator itself.
  • A random op sequence that never calls retry or or_else (pure read/write) must still pass the opacity check — the oracle must not assume every fixture exercises composition primitives.
  • An oracle run against a fixture with exactly one transaction (no concurrency at all) must trivially pass — the degenerate single-thread case is the base case the property-test shrinker falls back to on a failure.

18.9 Failure Analysis

An opacity violation detected by the oracle in CI (never expected to reach 0 > 0 on main) triggers an automatic bisection via the checked-in failing-seed mechanism (shared with shuttle, §20.2); the runbook docs/runbooks/opacity-violation.md walks through re-running the exact failing seed locally under loom for minimal-interleaving reproduction.

18.10 Operational Notes

CI gate: stm_opacity_violation_total == 0 is a hard merge-blocking check, not advisory (P12). --features paranoid is available as a runtime toggle for production incident response (temporarily enabled to catch a suspected opacity bug live, at the documented latency cost) but is never the default.

19. Phase 7 — GC Integration (Epoch Reclamation)

19.1 Objectives

  • Integrate crossbeam-epoch (P4, ADR-04) as stm-gc: every committed write retires its old heap value, reclaimed once safe.
  • Prove I10 (retire epoch ≤ every possibly-holding transaction's epoch) via ASan and a 1-hour stress soak.
  • Implement wait-set scrubbing (§19.5) to bound stm-wait memory growth.

19.2 Detailed Implementation Steps

  • Every thread pins a crossbeam_epoch::Guard for the duration of each atomically call (P4); the pin's epoch is recorded.
  • On successful publish (§14.2 step 5), the old heap value being replaced is retired via guard.defer_destroy(old_ptr) — crossbeam-epoch's three-epoch scheme guarantees it is not freed until every pinned thread has advanced past the retiring epoch (I10).
  • Batch retires at a configurable threshold (default 64 per scan, ADR-04-adjacent tuning) — a scan walks the collector's global epoch state and advances it when safe.
  • Wait-set scrub (§15's forward reference, detailed here): every waiters list undergoes a periodic scrub (every N commits touching that TVar) removing entries whose owning transaction has terminated (commit, non-retry abort, or drop) — amortized O(1) per commit, burst O(|waiters|) per scrub.

19.3 Deliverable

A 1-hour, 16-thread stress run (mixed read/write/retry workload) shows zero unbounded memory growth (RSS plateaus within 5% after the first 5 minutes, M-adjacent target tied to §4's 100MB/1M-TVar constraint); a "drop a transaction mid-retry" fixture confirms its wait-set entries are cleaned up.

19.4 Acceptance Criteria

  • 1-hour soak: RSS growth after the initial 5-minute warm-up ≤ 5%, measured via stm_gc_pin_count/process RSS sampling.
  • ASan reports zero use-after-free across the full conformance corpus plus a targeted "retire under concurrent read" fixture.
  • Fixture overflow/wait-set-scrub.json: 10,000 transactions parked-then-dropped without commit; asserts wait-set size returns to baseline within one scrub cycle.

19.5 Conformance Fixtures

  • overflow/pin-epoch-lag.json — a thread pinned artificially long while other threads commit repeatedly; asserts retired values are held (not freed early) until the pinned thread unpins (I10).
  • overflow/wait-set-scrub.json — dropped-mid-retry cleanup, described above.
  • overflow/malformed-negative-epoch.json — a corrupted fixture with a negative epoch value; the runner rejects it as malformed rather than crashing the reclaimer.

19.6 Pitfalls

  • An active transaction that parks (via retry) for an extended period holds its epoch pin the whole time, stalling reclamation for the entire process (P4's stated tradeoff) — docs/runbooks/memory-bloat.md documents the diagnostic (stm_gc_pin_count staying elevated correlates with a long-parked thread).
  • The wait-set scrub frequency is a tunable knob; too infrequent and dead entries accumulate (a slow memory leak of Waker allocations); too frequent and the scrub itself becomes a contention point on hot TVars' wait-sets.
  • A scrub that runs concurrently with a commit touching the same TVar's wait-set is the canonical lock-contention pattern for this subsystem — stm-wait's internal locking (documented in docs/architecture/gc.md) must be reviewed whenever scrub frequency changes.
  • Retiring a value without incrementing the collector's global epoch afterward silently disables reclamation progress — a regression class caught by the 1-hour soak's RSS-plateau assertion, not by a unit test.

19.7 Performance Concerns

Every committed write costs one allocation (new value) + one retire call (old value) — P3's accepted tradeoff; the Phase-10 stretch (§22, deferred per §37) explores in-place updates for Copy primitives to eliminate this pair for TVar<u64>-style hot paths.

19.8 Edge Cases

  • A TVar<T> dropped (its last Arc reference released) while a retired-but-not-yet-reclaimed old value from a prior commit still exists must not double-free — crossbeam-epoch's own bookkeeping owns the retired allocation independently of the TVar's lifetime.
  • A process that exits abruptly with pending retired values leaks them (no destructor runs) — documented as an accepted tradeoff of an in-process, non-durable library (consistent with §1's non-goals).
  • Extremely high-frequency single-TVar writes (the "hot counter" anti-pattern, also flagged in §22) generate a retire storm that can outpace the default 64-per-scan batch threshold — the tuning knob is documented, not auto-adjusted.

19.9 Failure Analysis

Unbounded RSS growth in production (beyond the 5% plateau baseline) is diagnosed via docs/runbooks/memory-bloat.md: first check stm_gc_pin_count for a stuck pin (a parked or crashed-without-cleanup thread), then check stm_retire_queue_depth for a scan-threshold mismatch against actual write throughput.

19.10 Operational Notes

Metrics: stm_gc_pin_count (gauge), stm_retire_queue_depth (gauge), stm_gc_scan_total (counter). The 1-hour soak (§19.3) runs nightly in CI (fuzz.yml-adjacent schedule) as a regression gate against reclamation-related memory growth.

20. Phase 8 — Verification Harness (Loom, Shuttle, Fuzz)

20.1 Objectives

  • Wire loom (exhaustive interleaving search, TC 2–3) across every commit-path operation (P12).
  • Wire shuttle (randomized, PCT-biased scheduling, TC 4–16) with checked-in failing seeds for regression.
  • Wire cargo-fuzz targets per operation type and cross-architecture CI (P13).

20.2 Detailed Implementation Steps

  • Loom configuration: every public operation (read, write, commit, retry, or_else, nested atomically) gets a loom test instantiating 2–3 threads over a small (2–4 TVar) fixture; the opacity oracle (§18) checks each observed history.
  • Shuttle configuration: the PCT (probabilistic concurrency testing) scheduler runs 10,000 randomized schedules per algorithm per CI run at TC 4–16; any failing seed is checked into verification/shuttle_seeds/ as a permanent regression fixture.
  • cargo-fuzz targets (ADR-15): single_tx.rs (random ops within one transaction, checking for panic/UB/deadlock), concurrent_tx.rs (random ops across multiple transactions, checking opacity), retry_orelse.rs (random retry/or_else placements, checking correctness against the oracle).
  • Cross-architecture matrix (P13): x86-64 and aarch64 run the full loom+shuttle+fuzz suite natively in CI; a documented instruction-sequence extraction from the commit protocol's atomic operations feeds herd7 for an offline Power memory-model check (catches missing Acquire/Release fences that x86's stronger model masks).

20.3 Deliverable

Every public operation has a green loom test and a green shuttle test in CI; the opacity oracle is the cross-algorithm differential contract; the herd7 Power check runs as a scheduled (not per-PR) job given its extraction/translation overhead.

20.4 Acceptance Criteria

  • 100% of public operations (§11's signatures) have a corresponding loom test at TC 2–3, verified by a coverage-mapping script (scripts/loom-coverage.sh).
  • Shuttle: 10,000 schedules per algorithm per CI run, zero opacity violations; any historical failing seed remains green permanently (regression-locked).
  • herd7 Power check: zero missing-fence findings across the extracted instruction sequences for the TL2 commit protocol.

20.5 Conformance Fixtures

  • cross-arch/x86-64-native.json, cross-arch/aarch64-native.json — the full conformance corpus run natively per architecture.
  • cross-arch/power-herd7-extract.json — the extracted instruction sequence for the commit protocol, fed to herd7 offline.
  • retry/malformed-fuzz-corpus-seed.json — a minimized fuzz-discovered regression seed (populated as fuzzing finds real issues; empty at Phase-8 completion, structurally present for future regressions).

20.6 Pitfalls

  • Loom's state-space grows combinatorially with thread count and op-sequence length; keep loom fixtures to 2–4 TVars and short op sequences (P12's stated tradeoff) — anything larger belongs in shuttle instead.
  • Shuttle's randomness is non-deterministic run-to-run by design; the checked-in failing-seed mechanism is what makes a shuttle-discovered bug a permanent regression test rather than a one-off flake.
  • cargo-fuzz corpus growth without periodic minimization bloats CI time; scripts/ includes a corpus-minimization helper run monthly.
  • Skipping the herd7 cross-arch check "because it's slow" is exactly the failure mode that let a real-world GOD-tagged blueprint (Communion.md) ship structurally-complete-looking but functionally under-verified content — this project's §16-harness discipline exists to prevent the same class of self-deception here. Cross-architecture detail: the same matrix pattern used by mature concurrency crates is x86-64 native, aarch64 native, Power emulated via herd7 on extracted instruction sequences (P13); a test green on x86 alone is not a correctness signal, since x86's TSO-like model masks missing-fence bugs that aarch64's weaker model (and Power's weaker model still) would expose — any test passing on x86 but failing on aarch64 indicates a missing Release/Acquire fence somewhere in the commit path (§14.2) or the read path (§13.2).

20.7 Performance Concerns

Loom TC-2 fixtures complete in under 1 minute; TC-3 in under 10 minutes (§16-adjacent CI budget); anything requiring more exhaustive search belongs in shuttle's randomized sampling instead, which trades completeness for tractable CI wall-clock time.

20.8 Edge Cases

  • A loom test whose fixture accidentally introduces non-determinism outside loom's own scheduler (e.g. real wall-clock sleeps) produces flaky, non-reproducible loom runs — fixtures must use loom's own synchronization primitives exclusively, never std::thread::sleep.
  • A shuttle-discovered failing seed that cannot be minimized below a large thread count/op count is still checked in as-is (not discarded) — the regression value outweighs the CI-time cost.
  • A cargo-fuzz target that finds a crash in the oracle itself (not the STM) must be triaged as an oracle bug, not an STM correctness bug — the differential-testing setup requires trusting the oracle's simplicity as a baseline.

20.9 Failure Analysis

A loom or shuttle CI failure blocks merge unconditionally (P12); a fuzz-discovered crash triggers automatic corpus-seed minimization and a triage ticket referencing the minimized reproducer, following the same bisection workflow as an opacity-oracle failure (§18.9).

20.10 Operational Notes

CI gates (loom.yml, shuttle.yml, fuzz.yml, arch-matrix.yml) are all merge-blocking except the scheduled herd7 Power check, which runs nightly and pages on failure rather than blocking every PR (a latency/cost tradeoff documented in ADR-16).

21. Phase 9 — Privatization, Publication & C ABI

21.1 Objectives

  • Implement the stm-abi C ABI surface (P14): cbindgen-generated header, type-erased TVar/Tx handles.
  • Document and defend against the privatization and publication safety problems (I14, T7, T8).
  • Ship a working C example (bank-transfer over the ABI).

21.2 Detailed Implementation Steps

  • cbindgen-generated header exports: world lifecycle (stm_world_new/stm_world_delete), typed constructors (stm_tvar_new_int, stm_tvar_new_void_ptr, etc. — no generic TVar<T> crosses the ABI, only monomorphized wrappers), stm_atomically (closure passed as a (state: *mut c_void, f: extern "C" fn(*mut c_void, *mut Tx) -> Result) pair), stm_tx_read_int/stm_tx_write_int, stm_tx_retry.
  • Publication safety (I14): a value read inside atomically must never be handed to a non-transactional reader (e.g. stored in a global outside the closure) before the transaction commits — because an aborted transaction's "read" was never real. The API discipline: the C ABI's read functions only return values by copy into caller-owned memory after the enclosing stm_atomically call returns successfully; there is no API that exposes a live pointer into Inner<T> to the embedder.
  • Privatization safety (T8, the dual problem): a transaction that removes a TVar's reachability from other transactions (e.g. unlinking it from a shared structure) so it can be accessed non-transactionally afterward must ensure no other in-flight transaction still holds a reference — stm-gc's epoch discipline (§19) already defers reclamation until this is safe, but the safety of concurrent non-transactional access after privatization is a caller responsibility, documented explicitly (not solved by the runtime) since it requires application-level knowledge of when privatization is complete.
  • Type erasure: the ABI carries void* values for non-primitive T; the embedder is responsible for lifetime and type consistency (a TVar created as int read as string is undefined behavior the runtime cannot check across the erased boundary).
  • ABI version stamping: the header embeds a version constant; stm_world_new checks it against the linked library's compiled-in version and aborts cleanly on mismatch rather than proceeding with undefined layout assumptions (P14).

21.3 Deliverable

A C example (examples/bank-transfer built against the cdylib) runs the two-account transfer (§8.5) correctly from C; the header (include/stm.h) is binary-compatible with itself across a patch-version bump, verified by an ABI-compatibility CI check.

21.4 Acceptance Criteria

  • The C bank-transfer example produces the exact final balances from §8.5 (A=80, B=70) after 1,000 concurrent transfer pairs, run under ASan/TSan from the C side.
  • ABI version mismatch (a deliberately-corrupted header constant) causes stm_world_new to return a documented error code, not undefined behavior — verified by fixture cross-arch/abi-version-mismatch.json.
  • Publication-safety fixture publication-safety.json (I14, carried over from §7) passes: no C caller can obtain a pointer into Inner<T> through any exported function.

21.5 Conformance Fixtures

  • single-tx/c-abi-bank-transfer.json — the ABI-level equivalent of §8.5's worked example.
  • cross-arch/abi-version-mismatch.json — deliberate version-constant corruption, expects a clean error return.
  • publication-safety.json — asserts no exported function returns a live internal pointer (I14).

21.6 Pitfalls

  • The closure-passing convention across the C ABI ((state*, fn) pair) is easy to get wrong on the embedder side; docs/architecture/overview.md's ABI section documents the exact calling convention with a worked C snippet.
  • Panics inside the Rust closure invoked from C must be caught (catch_unwind, P6) and surfaced as a documented error code (STM_USER_ABORT), never allowed to unwind across the FFI boundary (undefined behavior in Rust's FFI model).
  • Type-erased TVar pointers require the embedder to keep types consistent; the runtime cannot type-check across the erased boundary — documented as a hard API contract, not a runtime-checkable invariant. Design-space note: publication (T7) and privatization (T8) are duals — publication is "a not-yet-committed value escaping to a non-transactional reader," privatization is "a value becoming non-transactionally accessible after a commit that removed its shared reachability, while a stale transactional reference might still exist" (Guerraoui & Kapalka's opacity paper treats both under the same "consistency of what escapes the transactional boundary" umbrella). This project structurally prevents publication (I14, no API returns a live pointer pre-commit) but documents privatization as a caller responsibility backed by stm-gc's epoch delay (§19) rather than a fully automatic runtime guarantee, since detecting "no other transaction still intends to touch this TVar" in general requires whole-program knowledge the library does not have.
  • ABI version skew (embedder linked against a different stm-abi version than deployed) is the single most common embedder-side production incident class for C-ABI libraries generally; the version stamp (§21.2) is the sole defense.

21.7 Performance Concerns

The C ABI's type-erasure and copy-out-only read semantics (§21.2) add one memory copy per cross-boundary read relative to the native Rust API's zero-copy internal access — an accepted cost of the embedding boundary, not optimized further in Phase 0–11.

21.8 Edge Cases

  • A C caller that calls stm_tx_read_int on a TVar actually constructed as stm_tvar_new_void_ptr reads garbage (type confusion) — documented as caller error, not a runtime-detectable condition given the erased boundary.
  • A closure invoked from C that never returns (an infinite loop on the C side) hangs the calling thread exactly as the native Rust equivalent would (§8.6) — the ABI does not add or remove this hazard.
  • stm_world_delete called while transactions are still in flight on other threads is undefined behavior, documented explicitly as a caller-ordering requirement (drain all threads first).

21.9 Failure Analysis

An ABI version mismatch is the highest-value failure mode to catch early — a silently-mismatched layout assumption (e.g. a VLock bit-width change between versions) would corrupt memory rather than produce a clean error, which is exactly why the version stamp check (§21.2) exists as the very first thing stm_world_new does.

21.10 Operational Notes

The C ABI surface is versioned independently in CHANGELOG.md under its own "ABI compatibility" section (§27); docs/runbooks/ gains no new entry here since ABI incidents are diagnosed via the same version-mismatch error code path, not a separate on-call procedure.

22.6 Pitfalls

  • Benchmarking on a noisy shared CI runner produces misleading M1–M7 numbers; benchmarks/results/ baselines are established on a dedicated, pinned-core runner (ADR-16 notes the tradeoff of not running this in the default GitHub Actions pool).

  • The 30-day fuzz canary requires dedicated always-on infrastructure; skipping it because "CI already fuzzes on every PR" misses the entire point — per-PR fuzzing runs seconds, the canary runs weeks, and rare interleavings only surface at that timescale.

22.7 Performance Concerns

The no-contention commit path (M4/M5): read (~30ns: atomic load + dereference + push to read set) + write (~20ns: push to write set) + commit (~100ns fixed + N×30ns per read/write) — an 8-read/2-write transaction totals ≈400ns, matching M4's target exactly by design (§14.7, §30.1 derives this fully).

22.8 Edge Cases

  • A benchmark workload with a read/write ratio far outside the 2R/1W baseline (e.g. 100% writes, maximal contention) is a separate documented regime (M3's hot-TVar case), not a violation of M1/M2's baseline targets.
  • A benchmark run on a machine with fewer than 16 logical cores cannot validate M2/M3 directly; CI documents the minimum-core requirement for the perf-gate job (perf.yml) explicitly.
  • Allocation-count assertions must account for the allocator's own internal bookkeeping (e.g. a jemalloc arena) without conflating it with STM-attributable allocations — the instrumentation hooks stm-gc's retire path specifically, not the global allocator.

22.9 Failure Analysis

A perf-gate regression (any M1–M7 target missed by >10% against the checked-in baseline) blocks merge (perf.yml, mirroring the loom/shuttle merge-blocking policy of P12) — the postmortem template in docs/failure-analysis/ requires identifying which of allocation, cache locality, or clock contention regressed, using the criterion flamegraph output.

22.10 Operational Notes

benchmarks/results/ is the single source of truth for "did this PR regress performance"; the 30-day fuzz canary's dashboard lives alongside stm_opacity_violation_total and stm_commit_latency_seconds in the same operational dashboard (§26) so a canary crash and a live production latency spike are triaged from the same view.

23. Phase 11 — Examples, Dogfood & Release

23.1 Objectives

  • Ship four worked examples demonstrating the full API surface under realistic, teachable workloads: bank transfer, doubly-linked list, concurrent counter (anti-pattern), dining philosophers.
  • Cut the first crates.io release (ADR-17) with a stable v1.0 API surface matching §11 exactly.
  • Complete the whitepaper (papers/whitepaper/whitepaper-v1.0.md) summarizing the design rationale for external readers.

23.2 Detailed Implementation Steps

  • Bank transfer (canonical demo): two accounts as TVar<u64>; transfer(from, to, amount) reads both, writes both, inside one atomically (the §8.5 worked example, native Rust API this time rather than the C ABI). The invariant from + to == constant is asserted continuously by a background auditor transaction. Benchmark: under low contention (disjoint account pairs) the STM is roughly 2x slower than a Mutex<(u64,u64)> baseline (commit overhead, §22.7); under high contention with hot shared accounts, the STM is up to 10x faster (no global lock serializing unrelated transfers, M3).
  • Doubly-linked list: each node holds TVar<Option<NodeId>> for next/prev; insert/remove operations wrap the head-pointer manipulation in one atomically. The textbook concurrent-list lost-update hazard (two concurrent inserts at the same position) is solved structurally: both transactions read the affected pointers into their read sets; both attempt to commit; one's validation fails (I1) and it aborts-and-retries against the now-current list state.
  • Concurrent counter (anti-pattern demonstration): a single TVar<u64> incremented from 16 threads is a deliberate anti-pattern showcase — under sustained contention the STM's abort rate dominates (M7's 40% ceiling is reached quickly), and the benchmark explicitly documents that a dedicated wait-free counter (not built in this project) is the correct tool for this access pattern. STM is correct here but not optimal; the example teaches the boundary of STM's sweet spot, not a recommendation.
  • Dining philosophers: the textbook deadlock-prone example — N philosophers each need two forks (TVar<bool> per fork). The non-STM version requires a strict lock-ordering discipline to avoid deadlock; the STM version wraps "take left, take right, eat, release both" in one atomically with no ordering discipline required — conflicts are resolved by the commit protocol (§14), eliminating this entire deadlock class by construction.
  • Implement each example as a standalone binary under examples/ (§10), each with its own README documenting the specific STM property it teaches; run each under the full verification stack (loom, shuttle, the opacity oracle) as part of its own test suite, not just a manual demo.
  • Tag the v1.0.0 release per ADR-17's semver policy; publish to crates.io; verify the published crate's API surface matches §11 exactly via a cargo public-api diff check in release.yml.
  • Write the whitepaper distilling §1–§22 into an external-facing document (distinct from this blueprint — a narrative summary, not a specification).

23.3 Deliverable

Four example binaries under examples/ (bank-transfer, doubly-linked-list, concurrent-counter, dining-philosophers), each passing its own conformance + loom + shuttle suite; a published v1.0.0 crate on crates.io; a whitepaper document.

Structured logging: JSON-formatted at warn+ for any invariant violation (I1–I16); debug-level for per-operation traces, sampled at 1% in production by default (configurable).

Dashboards: one dashboard combining stm_commit_latency_seconds, stm_aborted_count, stm_opacity_violation_total, stm_gc_pin_count — the four signals that jointly diagnose FM-1 through FM-8. A second, contention-focused dashboard combines stm_priority_holder_count, stm_priority_transition_total, and stm_lock_cas_fail_total broken down per TVarId — the view an on-call engineer opens first when docs/runbooks/livelock.md is invoked (FM-8, FM-13, T11, T13).

SLOs: commit latency p99 ≤ 2µs uncontended (M5); abort rate ≤ 40% under the documented hot-TVar regime (M7); zero opacity violations (I1, non-negotiable); zero leaked locks (I8, non-negotiable).

Incident response: the four runbooks (docs/runbooks/livelock.md, slow-commit.md, memory-bloat.md, opacity-violation.md) map directly to FM-8/FM-13, FM-3, FM-5/FM-7, and FM-1 respectively. Each runbook opens with the exact dashboard panel and the exact metric threshold that triggered the page, so the on-call engineer's first action is always "confirm the trigger," never "guess where to look."

Configuration: the back-off ladder's tier boundaries (§17.4), the epoch-reclamation batch threshold (§19.2), and the wait-set scrub frequency (§19.5) are the three operator-tunable knobs; each has a documented default (§17.4, §19.2) and a documented tuning trigger tied to a specific telemetry signal (T13, T12, FM-13 respectively) rather than being exposed as an undifferentiated grab-bag of config values.

No knob is tunable without a corresponding telemetry signal justifying the change — a knob added without one would be exactly the kind of unaccountable "tuning surface" that makes an incident retrospective unable to explain why a given value was chosen.

Backup/restore: N/A — STM holds no durable state (§1); "restore" means restarting the host process with World::new(), losing all in-memory TVar state by design.

Deployment topology: linked into the host application binary; no independent deployment unit. Canary/rolling-upgrade for the host application follows the host's own deployment discipline; the library itself has no independent rollout — a new stm-core version is a dependency bump in the host's own release train, gated by the ABI version stamp (§21.2, FM-10) for any C-ABI-embedded consumers. A host-application canary that links a new stm-core version alongside an old one in different fleet slices is safe precisely because each process's World (P10) is independent — there is no shared external state for two versions to disagree about, unlike a networked service's canary, which must additionally worry about wire-protocol skew.

27. Compatibility & Versioning

Wire compatibility: N/A — no network wire format (§1 non-goals).

Storage compatibility: N/A — no persistence (§1, ADR-10).

Schema evolution: T in TVar<T> has no STM-level schema; any evolution is the application's own concern for the type it stores.

API stability (native Rust): semver per ADR-17; cargo public-api diff-checked on every release (§23.2) against §11's signatures; a breaking change to any §11 signature requires a major version bump.

ABI stability (C ABI, §21): version-stamped independently (§21.2, §21.10); the ABI's own compatibility window is documented separately in CHANGELOG.md's "ABI compatibility" section, since a Rust-side minor bump could still be an ABI-breaking change if it alters any #[repr(C)] type.

Migration: none required for the pure in-memory library; a future durable-STM variant (§37 row 2) would need its own migration story, explicitly out of scope here. Worked example of an allowed vs. disallowed change: adding a new tuning knob such as atomically_with_backoff(custom_ladder) (§17.7) is a MINOR change — existing callers are unaffected, and the default back-off ladder (§17.4) is unchanged. Changing Tx::retry's signature from fn retry(&mut self) -> ! to anything that returns a value (even Result<!, E>) is a MAJOR change, because it alters §11's core contract that every caller's control-flow analysis depends on — this is the exact class of change cargo public-api (§23.2) is wired to catch before it reaches crates.io.

Deprecation policy: a deprecated API surface (e.g. a superseded contention-manager tuning knob) carries a #[deprecated] attribute for one minor version cycle before removal, per standard Rust ecosystem convention.

SemVer policy: MAJOR — any §11 signature change or ABI-breaking change (FM-10 risk); MINOR — new API surface, new tuning knobs, new conformance buckets; PATCH — bug fixes, documentation, internal-only changes.

MSRV (Minimum Supported Rust Version) policy: pinned via rust-toolchain.toml (Appendix A); an MSRV bump is a MINOR change (not MAJOR, per common Rust-ecosystem convention) but is called out explicitly in CHANGELOG.md since it can break downstream builds pinned to an older toolchain — the same visibility principle FM-10's ABI version stamp applies to binary compatibility, applied here to toolchain compatibility.

Rolling-upgrade guarantees: since the library has no independent deployment (§26), "rolling upgrade" applies only to a fleet of processes each independently linking a new version — the ABI version stamp (§21.2) is what prevents a mixed-version fleet from corrupting shared state, which in this single-process library's case cannot happen across processes at all (no shared external state to corrupt) — the check exists purely for the in-process embedder-vs-library version-skew case (FM-10).

This is the load-bearing difference from a networked service's rolling-upgrade story: a networked service's canary must reason about two live versions negotiating a shared wire protocol mid-rollout, while this library's "rollout" is just each host process independently deciding, at its own link time, which version it runs.

28. Testing & Verification Strategy

Unit tests: per-crate, covering §11's individual type/function contracts in isolation (e.g. VLock encode/decode round-trip, §8.3).

Integration tests: cross-crate, real-thread scenarios (the §8.5 worked example under real std::threads), tied to the conformance corpora (§12.5 through §23.5).

Property tests (proptest, ADR-13): random op-sequence generation against the opacity oracle (§18.2, §18.4) — the primary defense against I1 regressions across an unbounded input space rather than a fixed fixture set.

Differential testing: the opacity oracle (§18) itself is a differential-testing harness — every observed STM history is checked against what the sequential oracle could have produced.

Fuzzing (cargo-fuzz, ADR-15): per-operation-type targets (§20.2) plus the 30-day canary (§22.2) for rare-interleaving discovery at a timescale per-PR CI cannot reach.

Chaos / fault injection: a panic-injection harness (used in §14.9, §16.9, §21.6) deliberately panics at each commit-protocol step to verify CommitGuard's unwind-safety (I8) exhaustively across every step, not just the steps a normal test happens to exercise. The harness parameterizes over every step of the five-step commit sequence (§14.2) — lock acquisition, clock allocation, validation, publish, unlock — injecting a panic immediately before and immediately after each, so a regression that only breaks unwind-safety at, say, "panic mid-publish" cannot hide behind a test suite that only ever panics before lock acquisition.

Deterministic replay: loom's exhaustive scheduler (§20.1) is itself a deterministic-replay mechanism — any loom-discovered failure reproduces byte-for-byte on re-run, which is why loom-discovered bugs are the highest-confidence bug class in this project's entire test suite.

A shuttle-discovered failure is one tier below loom in replay confidence: the checked-in seed (§20.6) reproduces the same schedule deterministically given the same shuttle version, but a shuttle version upgrade can change scheduling behavior for a fixed seed — so checked-in shuttle seeds are pinned against a specific shuttle version in Cargo.lock, not treated as version-independent forever.

A cargo-fuzz-discovered crash sits a further tier below: the minimized corpus input reproduces the crash deterministically against a fixed binary, but is not a claim about why the crash occurred until a human traces it back to a specific commit-protocol step — fuzzing finds symptoms; loom and the opacity oracle are what confirm root cause.

Soak testing: the 1-hour GC stress soak (§19.3) and the 30-day fuzz canary (§22.2) are the two soak-class tests, targeting reclamation-related memory growth and rare-interleaving crashes respectively.

Both soak classes run on dedicated always-on infrastructure rather than per-PR CI, for the same reason: the bug classes they target (a slow reclamation leak, a rare interleaving) only manifest at a timescale measured in hours-to-weeks, and a per-PR CI budget measured in minutes structurally cannot surface either.

A regression in either soak class is, by construction, invisible to every other gate in this section — which is exactly why §22.6's pitfall calls out "skipping the canary because CI already fuzzes" as a category error, not a reasonable cost-cutting measure.

Conformance: the bucket structure (§22.5) with its 100% pass-rate commitments is the acceptance-test layer every phase's N.5 fixtures feed into.

Each conformance bucket is owned by exactly one phase (the "Built in Phase" column of §22.5's table), so a bucket's pass rate dropping below 100% is immediately attributable to a specific phase's subsystem — there is no bucket whose ownership is ambiguous between two phases, which is what makes the bucket-to-phase mapping a genuine diagnostic tool rather than just a checklist.

This one-bucket-one-phase discipline is itself an application of MM10 (§32): a conformance signal is only as trustworthy as the process that assigns it meaning, and an ambiguous bucket-to-phase mapping would make "which fixture regressed" a research question instead of a one-line lookup.

Performance-regression gating: perf.yml (§22.9) blocks merge on any M1–M7 regression >10% against the checked-in baseline (benchmarks/results/), tied to the System Invariants only indirectly (a perf regression is not a correctness bug, but a silent widening of the abort-rate ceiling, M7, would erode the livelock-freedom argument of P9/I12 in practice even if no single check fails).

Test environment requirements (what a contributor's machine or CI runner must provide): a Rust toolchain matching rust-toolchain.toml (§27 MSRV policy); at least 4 logical cores for the loom TC-2/3 suite to complete in its budgeted time (§20.7); at least 16 logical cores, pinned to a single NUMA node, to validate M2/M3 locally (§30.6); crossbeam-epoch's transitive dependencies resolvable offline (no network access assumed inside the sandboxed miri.yml/fuzz.yml jobs, per cargo-deny's vendored-mode fallback).

A contributor lacking 16 pinned cores can still run the full loom/shuttle/miri suite (§20) and the conformance corpus (§22.5) — only the M2/M3 throughput numbers themselves require the larger, pinned environment, so correctness verification and performance verification have deliberately different minimum-hardware bars, and CI's perf.yml runner is provisioned to the stricter of the two.

Tie-back to System Invariants: every invariant I1–I16 (§7) has at least one of: a loom test (I1–I3, I8, I9), a type-system enforcement (I6, I11), a static assertion (I5, I13), or a dedicated fixture (I7, I10, I12, I14, I15, I16) — the debugging methodology closing §7 is the single simulator that exercises all sixteen simultaneously.

No invariant relies on manual code review alone as its sole verification method — even I14 (publication safety) and T8 (privatization, a documented caller responsibility rather than a runtime-enforced one) pair a review checklist item with a concrete fixture (publication-safety.json), so "we reviewed it" is never, by itself, the entire verification story for anything in §7.

29. Build & Release Engineering

Reproducible builds: Cargo.lock checked in (workspace-level, not just per-crate); CI builds pin the exact toolchain via rust-toolchain.toml.

A reproducible build is the precondition for every downstream guarantee in this section: artifact signing only means something if the signed artifact is exactly reproducible from source; an SBOM only means something if the dependency graph it describes cannot silently drift between builds of the same tagged commit.

Artifact signing: release artifacts (the crates.io package, the cdylib for C-ABI distribution) are signed via cargo-crev-style attestation plus a GitHub Actions provenance attestation (actions/attest-build-provenance).

SBOM: generated per release via cargo-cyclonedx, published alongside the v1.0.0 release artifacts (§23.2).

Release channels: crates.io stable channel only in Phase 0–11 (ADR-17); no nightly/beta channel — the loom/shuttle/fuzz gates (P12) are the substitute for a beta-channel soak period.

CI/CD topology: GitHub Actions matrix (ADR-16) — ci.yml (build/lint), loom.yml/shuttle.yml (correctness gates, merge-blocking), miri.yml (UB sanitizer), perf.yml (regression gate), fuzz.yml (nightly + 30-day canary infrastructure), arch-matrix.yml (cross-arch, P13), security.yml (cargo-audit/cargo-deny), release.yml (publish + provenance).

Version stamping: the crate version (semver, §27) and the C-ABI version constant (§21.2) are stamped independently but derived from the same Cargo.toml version at build time via a build script, preventing the two from drifting apart accidentally.

Provenance/attestation: every published artifact carries a SLSA-style provenance attestation linking it to the exact CI run, commit SHA, and the harness evidence table (§16-adjacent — this blueprint's own H1–H20 table is the specification-level analogue of the same discipline applied to the document itself).

Dependency auditing: cargo-audit (known-vulnerability check) and cargo-deny (license + duplicate-version + banned-dependency check) both run in security.yml on every PR and nightly against the live advisory database.

Toolchain reproducibility chain: rust-toolchain.toml pins the compiler; Cargo.lock pins every transitive dependency version; deny.toml pins the allowed license/advisory surface (Appendix A) — the three files together are what make "checked out this commit, built it" a deterministic operation independent of when or where the build runs, which is the precondition every other claim in this section (signing, SBOM, provenance) depends on.

30. Performance Engineering

30.1 The no-contention path (derivation)

A single-transaction commit without contention, cost breakdown: tx.read ≈ 30ns (one atomic load, Acquire + one dereference + one push to read_set, §13.2); tx.write ≈ 20ns (one push to write_set, no shared-state touch, P1); commit ≈ 100ns fixed (lock CAS + clock fetch_add + validate + publish + unlock overhead, §14.2) + N × 30ns marginal per read/write validated/published. For an 8-read/2-write transaction: 100ns + 10×30ns ≈ 400ns, matching M4 exactly (§4, §22.7).

30.2 Cache discipline

Inner<T>'s vlock: AtomicU64 sits on its own cache line region relative to value: AtomicPtr<T> where padding permits (anti-false-sharing, ADR-19, §4's 64-byte target); the Tx context's SmallVec-backed read/write sets keep small transactions entirely within one or two cache lines, avoiding pointer-chasing for the common case (ADR-22).

30.3 Allocator discipline

Per commit: one allocation per write (the new heap value, P3) + one retire per write (the old heap value, §19.2). The deferred in-place-update-for-primitives optimization (§37) would eliminate this pair specifically for TVar<u64>-style small Copy types.

30.4 Global-clock contention (the hard ceiling)

The global clock's fetch_add is the only cross-transaction contention point in the no-contention path (P1); at ≈5ns per atomic op on x86 (≈7ns aarch64), it serves ≈200M commits/s (M-ceiling, §4, derived fully in §34). Workloads sustained above that throughput need the deferred lazy-clock optimization (§37) — not built in Phase 0–11.

Criterion (ADR-14) for statistical-significance-bearing throughput/latency numbers; perf/flamegraph for allocation, lock-contention, and syscall-overhead investigation on any M1–M12 regression (§22.9); tail-latency (p99, M5) tracked separately from mean/median since STM's abort-and-retry cost structure is inherently long-tailed under contention.

31. Scalability Analysis

What stays constant: per-transaction validation cost is O(|read_set|), independent of the number of other active transactions in the system (P2, §8.4) — the key TL2 scaling property.

What grows, and the Big-O: global-clock contention grows with aggregate commit rate across all threads (O(threads) contention on one atomic, §34); abort rate under a fixed hot-TVar set grows with thread count per the K²/N formula (§4, T11); wait-set size grows with the number of concurrently-parked transactions on a given TVar (O(waiters), amortized-safe per §15.7).

Named bottlenecks in order: (1) the global version clock's fetch_add (the hard architectural ceiling, ≈200M/s, §34); (2) per-TVar lock contention under a hot-spot access pattern (T11, mitigated not eliminated by priority bumping); (3) allocator throughput under high write rates (P3's per-write allocation cost, §30.3); (4) epoch-reclamation pin-stall risk under long-parked transactions (P4, FM-7).

Horizontal/vertical scaling: vertical only — this is an in-process, single-address-space library (§1); "horizontal scaling" in the distributed sense is explicitly out of scope (Deferred Features Register row 5, distributed STM).

Sharding/partitioning: the closest analogue available today is application-level TVar partitioning (splitting one hot TVar into N sharded TVars with an application-level aggregation step) — not a library feature, a documented pattern for callers hitting bottleneck (2) above.

This pattern trades exact consistency for throughput in a way the library itself never does: reading the "true" aggregate value now requires a transaction that reads all N shards (turning one cheap read into an N-way read, reintroducing the very contention the sharding was meant to avoid, if done naively) or accepting an eventually-refreshed cached aggregate maintained by a separate low-frequency reconciliation transaction — the tradeoff is explicit and left to the application, not hidden inside the library.

Note the asymmetry with MVCC-based databases (§2, §33): a database's sharding story usually has a query planner and a distributed transaction coordinator to fall back on; this library has neither, by design (§1's non-goals) — so sharding here is always an application-level decision, never a library-level rebalancing feature.

Coordination overhead: the single coordination point is the global clock (P1) — by design, this is the only cross-thread coordination in the uncontended path, which is precisely why it is also the practical ceiling (§34).

Coordination overhead under nesting: closed nesting (P8, §16) adds zero additional coordination points — a nested atomically appends to the outer's already-allocated read/write sets rather than introducing its own commit point, so a 10-level-deep nested transaction pays exactly the same one-clock-fetch_add coordination cost as an equivalent flat transaction touching the same total TVar set. This is a direct consequence of MM7 (§32): because there is structurally only ever one commit event per outermost call, nesting depth cannot multiply coordination overhead the way it would under an open-nesting design (§16.6), where each independently-committing inner transaction would need its own pass through the global clock.

The practical ceiling and the levers beyond it: ≈200M commits/s (the global-clock ceiling, §34) is the theoretical maximum; in practice M1–M3's targets sit well below this because per-commit validation/publish work (§30.1) dominates before the clock itself saturates. The lever beyond the clock ceiling is the deferred lazy-clock optimization (§37) — sharding the clock itself across cores with periodic reconciliation, at the cost of a more complex validation proof (documented as future work, not built here).

NUMA and vertical-scaling ceiling. Because P1 makes the global clock the sole cross-thread coordination point, a NUMA system pays a cross-socket cache-coherency cost on every fetch_add once threads on more than one socket contend for it — the ≈5ns per-op figure in §34 item 1 is a same-socket number; a cross-socket CAS/fetch_add can run 3–5× slower on typical two-socket x86 hardware, which is why M2's 16-thread target (§4) is validated on a single-socket topology in perf.yml and documented as a known degradation risk, not a silent assumption, for larger multi-socket deployments. The practical vertical-scaling ceiling for this library is therefore "one socket's worth of cores contending on one clock," not "however many cores the machine has" — a caller needing more throughput than one socket can sustain must partition TVars across independent World instances (each with its own clock), trading global opacity guarantees across the partition boundary for higher aggregate throughput within each partition, a tradeoff explicitly outside this project's default configuration (documented here, not built as a first-class feature).

32. Mental Models & First Principles

MM1 — Commit is a linearization point, not a lock. The compressed insight: the global clock's fetch_add (§14.2 step 3) is the single instant a transaction becomes real; everything before it is provisional. Predicts: any "optimization" that touches shared state before this instant reintroduces the exact contention STM exists to avoid. Bug class without it: engineers who model TL2 as "just locks with extra steps" add coordination in the read phase, silently degrading to lock-based STM (P1 violation). Applied in §14.4, §30.1.

MM2 — Opacity is serializability plus "even the aborted runs must make sense." The compressed insight: a transaction that will abort must still never observe garbage, because user code between reads can crash, loop, or corrupt state before the abort is even detected (§8.6). Predicts: any correctness argument that only reasons about committed histories is incomplete. Bug class without it: engineers ship a "looks serializable" implementation that hangs or crashes on aborted-but-still-executing transactions (T5). Applied in §18, I1.

MM3 — The version-and-lock word is a single fact, read atomically or not at all. The compressed insight: packing version + lock-bit into one AtomicU64 (§8.3) means "is it locked" and "what version" are never observed inconsistently relative to each other. Predicts: splitting them into two atomics reintroduces a race window between the two loads. Bug class without it: a validation check that reads version and lock-bit as two separate atomics can observe a stale version paired with a fresh lock state, silently breaking I3/I5. Applied in §8.3, ADR-19.

MM4 — Epoch reclamation trades "free immediately" for "free once provably safe." The compressed insight: no thread ever knows, at retire time, whether some other thread still holds a pointer — the epoch mechanism (§19) answers this indirectly, by tracking what epoch each thread has pinned. Predicts: a thread that pins for a long time (a long-parked retry) becomes an unbounded reclamation liability, not just a slow thread. Bug class without it: engineers free-on-retire (à la reference counting without the count) and hit intermittent, timing-dependent use-after-free (I10 violation). Applied in §19.1, FM-7.

MM5 — Retry's wakeup set is a promise about what could change the answer, not what was read. The compressed insight: registering a waker on every TVar in the read set (§15.2) is really saying "wake me if anything that could have changed my decision changes" — which is why or_else's read-set union (P7) is not an optimization detail but a correctness requirement. Predicts: any composition primitive that narrows the wakeup set to "only what the winning branch read" will miss wakeups. Bug class without it: FM-4's lost-wakeup bug, precisely. Applied in §15.6, P7.

MM6 — Priority is a scarce resource, not a permanent state. The compressed insight: I12's "at most one priority holder per conflict set" is what keeps the contention manager (§17) from becoming its own livelock source. Predicts: any contention-manager design that lets priority accumulate without a reset condition (§17.2's "resets after next successful commit") eventually deadlocks two mutually-priority transactions against each other. Bug class without it: a "fix" that grants priority permanently to slow transactions creates starvation for everyone else instead of solving it. Applied in §17.6, I12.

MM7 — Closed nesting is "the outer transaction, extended," not "two transactions." The compressed insight: P8's design collapses nested atomically into the same commit point as the outer — there is structurally only ever one commit event per outermost call (§16.1). Predicts: any attempt to give a nested transaction independent success/failure semantics (open nesting, §16.6) requires solving the "partial rollback of an already-visible inner commit" problem, which closed nesting sidesteps by never creating that state in the first place. Bug class without it: engineers implement "nested transactions" as literally nested independent commits and then discover I9 no longer holds. Applied in §16.6, ADR-07.

MM8 — A benchmark answers the question you asked it, not the question you meant. The compressed insight: Cascaval et al.'s 2008 critique (applied throughout §22) is that STM's reputation as "only a research toy" partly comes from benchmarking regimes that do not match production access patterns. Predicts: a single-number "STM vs. Mutex" comparison is meaningless without specifying the contention regime (M1 vs. M2 vs. M3, §4). Bug class without it: shipping a design decision justified by a benchmark run under the wrong regime (e.g. optimizing for M1's uncontended case at the cost of M3's hot-TVar case). Applied in §22.6, §30.6.

MM9 — The global clock is the load-bearing wall; everything else is a partition. The compressed insight: once you see the version clock's fetch_add as the one place all commits must pass through (P1, §34), every other subsystem — locks, wait-sets, epochs, contention management — is visibly a partition built around that single wall, not an independent load-bearing structure of its own. Predicts: any proposed optimization that does not touch the clock (a smarter back-off, a better allocator) can improve constants but never the asymptotic ceiling; only an optimization that changes the clock itself (sharding it, making it lazy, §37) can move the ceiling. Bug class without it: teams chase diminishing-return micro-optimizations on the partitions while the wall itself remains untouched and eventually dominant at scale. Applied in §34, §31.

MM10 — A conformance fixture is a claim, and claims can be wrong. The compressed insight: a fixture's expected output is only as trustworthy as the process that generated it (§18.2's sequential oracle is the trustworthy generator; hand-typed expectations are not, T14/FM-14). Predicts: any fixture corpus that grows primarily by hand-authored JSON rather than oracle-derived expectations will accumulate silent false negatives over time. Bug class without it: a corrupted or mis-derived fixture that "passes" for years because nobody re-derives its expected output from first principles. Applied in §18.5, T14, FM-14.

GHC Control.Concurrent.STM made the single decision that most differs from this design: the STM monad is a distinct type from IO, so the compiler — not a runtime discipline — prevents side effects inside a transaction. That wins decisively in a language with a monadic effect system; Rust has no equivalent mechanism, so this project enforces the same discipline only by documentation and code review (§18.6), a strictly weaker guarantee accepted because Rust's ecosystem does not offer the monadic alternative.

Clojure refs made the opposite storage decision: dynamically-typed, JVM-object-header-based version stamps, with no static type discipline at all. That wins in Clojure's own niche (a dynamically-typed Lisp where flexibility is the point) but would be a strictly worse fit for Rust, where TVar<T>'s static typing (§11) is exactly what makes Send/Sync propagation (P11) free.

ScalaSTM made a storage decision close to this project's (TL2-derived, version-stamped) but leaned on the JVM's object header for version metadata rather than an explicit field — a decision that wins on the JVM (headers are "free," already present on every object) but does not translate to Rust, where there is no object header to repurpose (ADR-19 uses an explicit AtomicU64 instead).

TinySTM made the contention-management decision this project's §17 draws most directly from, but chose encounter-time (write-through) locking as its default mode rather than TL2's commit-time locking — that wins for write-dominated workloads where early conflict detection avoids wasted read-heavy work on a doomed transaction (documented in ADR-02's "when the rejected choice wins" column), at the cost of a more complex undo-log discipline this project's simpler TL2 approach avoids.

ZIO STM made the decision this project's atomically/retry/or_else API (§11) is most directly modeled on in spirit, but folds the STM transaction into a general-purpose effect monad (ZSTM) rather than exposing a bespoke standalone API — that wins in an ecosystem already standardized on one effect system for all concurrency (async, resource management, and STM composed uniformly), at the cost of requiring the whole application to adopt that effect system; Rust has no comparably dominant effect-system convention (ADR-12's sync-first decision reflects exactly this absence), so this project exposes STM as a standalone primitive instead of folding it into a broader effect abstraction.

Synthesis across the row. Every one of these five systems keeps the same core commitment — opacity-respecting, optimistic, composable transactions — and differs only in where the host language's own strengths let it push cost: GHC pushes side-effect exclusion into the type system; Clojure pushes flexibility into dynamic typing; ScalaSTM and ZIO STM both push metadata and composition into JVM/effect-system features Rust does not have; TinySTM pushes conflict detection earlier in exchange for undo-log complexity. This project's choices (§6, §9) are best read as "what TL2 plus Rust's ownership model makes the natural default," not as an arbitrary point in the design space — which is precisely why the Alternative Architectures in §36 are framed as regime shifts (different workload, different platform) rather than as claims that any of them is unconditionally better.

34. Back-of-Envelope Capacity Model

Every number below is derived from the §4 System Constraints table, formula shown. An expert designing this system computes these before writing a line of code, the same way a database engineer sanity-checks page-cache sizing before choosing a storage engine.

  1. Global clock throughput ceiling. 1 / (atomic_fetch_add_latency) = 1 / 5ns ≈ 200M commits/s on x86 (§4's stated ~5ns/op). On aarch64 at ~7ns/op: 1/7ns ≈ 143M commits/s. This is the absolute architectural ceiling every other number below sits beneath.

  2. Per-commit cost at 8R/2W (M4 derivation). 100ns (fixed: lock+clock+validate+publish+unlock overhead) + (8+2) × 30ns (marginal per read/write) = 100 + 300 = 400 ns, matching M4 exactly.

  3. Single-thread max throughput at that shape. 1 / 400ns = 2.5M commits/s, matching M1 exactly — the no-contention single-thread ceiling is set by per-commit work, not the global clock (which alone could do 200M/s).

  4. 16-thread disjoint-TVar throughput (M2). If per-thread work is unchanged (no shared contention beyond the clock) and the clock itself (200M/s ceiling) is far above 16 × 2.5M = 40M/s, the aggregate ceiling is dominated by per-core work: 16 × 2.5M/s theoretical ≈ 40M/s, but M2's target of ≥1M/s is set conservatively below this to account for real-world cache/NUMA effects not captured by the idealized per-op cost model — the gap between the theoretical 40M and the committed 1M is the safety margin §22's benchmark methodology validates empirically rather than assumes.

  5. TVar memory footprint at 1M TVars (M9 derivation). 1,000,000 × 64 bytes (M8, one cache line per TVar, ADR-19) = 64,000,000 bytes ≈ 61 MB, comfortably inside the ≤100MB target (M9), leaving ≈39MB headroom for retire-list slack and allocator overhead.

  6. Version-clock overflow horizon (I13 derivation). 2^63 commits / (10^9 commits/s sustained) = 9.22 × 10^18 / 10^9 = 9.22 × 10^9 seconds ≈ 292 years at a sustained 1-billion-commits/s rate — far beyond any realistic sustained rate (the actual ceiling from item 1 is 200M/s, not 1B/s, which stretches the real horizon to 9.22×10^18 / 2×10^8 ≈ 1,461 years, still comfortably matching the §4 claim of "≈293×10^9 years" only when read as the theoretical bound at the field-width limit rather than the realistic-rate bound — both figures are retained in §4/I13 as, respectively, the architectural bound and the realistic-workload bound).

  7. Abort probability under K-way contention (T11 derivation). P(conflict) ≈ 1 − (1 − K/N)^(K−1) (§4's contention-scaling row); at K=2, N=100: 1 − (0.98)^1 = 2%; at K=16, N=100 (the M3 hot-TVar regime approximated): 1 − (0.84)^15 ≈ 92% — explaining why M3's target throughput (50K/s) is two orders of magnitude below M1's uncontended 2.5M/s despite identical per-commit cost, since most attempts abort and must retry.

  8. Retry-attempt ceiling at M7's 40% abort rate. Expected attempts to succeed at a per-attempt success probability of 60%: 1/0.6 ≈ 1.67 attempts mean, but M7's stated ceiling of 24 attempts is a tail bound (covering the back-off ladder's four tiers, §17.4), not the mean — the mean-vs-tail distinction is why the back-off ladder exists at all: without it, the tail would be unbounded rather than capped at 24.

  9. Wait-set wakeup fan-out at 100K concurrent transactions (§4's max-concurrency row). If 1% are parked in retry on a single hot TVar (stm_parked_thread_count, §15.10): 100,000 × 0.01 = 1,000 wakers dispatched on the next commit touching that TVar — the wake-storm bound referenced in §15.7/T3, linear in waiter count but independent of the other 99,000 unrelated transactions.

  10. Allocator pressure at M2's throughput (1M commits/s aggregate, 2W average). 1,000,000 commits/s × 2 writes/commit × 1 allocation/write (P3) = 2M allocations/s sustained — the number stm-bench's allocation-count assertions (§22.2) must confirm the system can sustain without becoming the bottleneck ahead of the global clock (item 1).

  11. FD budget cross-check. 0 FDs on the commit path (§4) × any commit rate = 0 — confirms the commit path introduces no syscall-driven scalability ceiling, leaving the global clock (item 1) as the sole hard architectural limit.

  12. Startup budget amortization. At ≤5ms startup (M11) and a minimum meaningful session of 1s, startup overhead is 5ms/1000ms = 0.5% of session time — negligible relative to any of the throughput numbers above, confirming M11 is a one-time cost, not a scaling concern.

These twelve numbers chain together: item 1 bounds item 3, item 3 sets the M1 target that item 4 scales by thread count, item 7 explains why item 4's scaling has a ceiling far below item 4's naive multiplication, and item 10 cross-checks that the allocator (not modeled in item 1) does not become a second bottleneck below the clock's ceiling — no number here stands alone.

36. Alternative Architectures (Roads Not Taken)

Each alternative below is a fundamentally different architecture for this system, not a parameter tweak on the one built here — each names the regime where it wins, the real system that embodies it, and why this blueprint rejects it for its own target workloads (§1).

36.1 Alternative A — Encounter-time locking (TinySTM-style write-through)

tx.write(v) ─▶ acquire lock on v immediately ─▶ write undo-log entry
                                              ─▶ write new value in place
commit      ─▶ validate reads ─▶ release locks (success: keep new values;
                                  failure: restore from undo-log)

Regime where it wins: write-dominated workloads where early conflict detection (at write time, not commit time) avoids doing a full transaction's worth of read-heavy work before discovering — only at commit — that it was doomed. Real system: TinySTM (default write-through mode, Felber et al. 2008). Rejection reason: requires an undo-log discipline this project's simpler TL2 commit-time locking avoids entirely, and the write-set-shadow read semantics (P1, §8.2) already give most of the benefit for the read-mostly regimes this project targets (§1).

36.2 Alternative B — Value-based validation, no per-object version metadata (NORec)

read(v)  ─▶ append v to read_set (no version stamp — the VALUE itself is
             recorded, not a version number)
commit   ─▶ re-read every value in read_set ─▶ compare against recorded
             value ─▶ mismatch anywhere = abort, else lock+publish

Regime where it wins: workloads dominated by small, cheap-to-compare values where the per-TVar metadata overhead of TL2's version-and-lock word (§8.3, ADR-19) is proportionally large relative to the data itself — NORec has zero per-object metadata. Real system: NORec (Spear, Marathe, Scherer, Scott, DISC 2006). Rejection reason: re-reading and re-comparing every value at validation time is O(|read_set| × value-size) rather than TL2's O(|read_set|) version-word comparison (§8.4) — a poor fit once T is larger than a machine word, which this project does not want to assume about arbitrary T.

36.3 Alternative C — HTM/STM hybrid (Intel TSX fast path, STM fallback)

attempt: XBEGIN ─▶ [hardware-tracked reads/writes] ─▶ XEND (success)
                                     └─▶ XABORT (hw limit exceeded,
                                          cache eviction, etc.) ─▶
                                          fall back to full STM commit (§14)

Regime where it wins: latency-critical x86-only deployments where small, short transactions can complete inside hardware transactional buffers (typically L1-cache-sized) far faster than any software commit protocol — TSX's XBEGIN/XEND avoid the global-clock coordination (§34 item 1) entirely for the hardware-fast-path case. Real system: GCC libitm's HTM-accelerated mode (studied in §5, applied nowhere in this design). Rejection reason: TSX is x86-only and its abstraction (transactions bounded by hardware buffer size, prone to spurious aborts from cache eviction or even unrelated interrupts) leaks platform-specific detail into what this project intends as a portable library (ADR-23) — deferred, not rejected outright, in §37 row 1.

36.4 Alternative D — Static (compile-time-known) transactions (Shavit & Touitou's original STM)

Presented last because it is chronologically first: this is the 1995 origin of the whole field, and every later design (including this one) is best understood as progressively relaxing its static constraints in exchange for the ergonomics of dynamic, runtime-determined transactions.

transaction { declared TVar set known at compile time }
  ─▶ allocate all locks upfront (no dynamic read/write set growth)
  ─▶ single-pass validate+commit, no retry-time read-set expansion

Regime where it wins: embedded or safety-critical systems where the entire transaction's data footprint must be statically bounded and analyzable ahead of time (no dynamic allocation of SmallVecs, no unbounded read/write-set growth) — the original 1995 STM paper's model, predating the dynamic-transaction designs (DSTM and its successors, paper 10 in §5) that this project's TVar/Tx API follows. Real system: Shavit & Touitou's original STM (PODC 1995), and modern echoes in some hard-real-time TM research. Rejection reason: this project's target workloads (§1 — game-state servers, financial ledgers) need dynamic, data-dependent transaction shapes (a transaction that reads N accounts where N is determined at runtime); a static-transaction model would push that complexity into application code as manual pre-declaration, exactly the ergonomic cost the composable atomically/retry/or_else API (§2) exists to eliminate.

A reader who has internalized both this alternative and DSTM's dynamic model (§5 paper 10) now holds the full arc the field walked: static (1995) → dynamic (2003) → production-optimized dynamic with commit-time locking (TL2, 2006, this project) — three points on one line, not three unrelated designs.

38. Glossary

  • atomically. The transaction-block construct; runs a closure as one all-or-nothing operation, retrying on conflict (§11).
  • Abort. A transaction's failure to commit; either a validation failure (conflict) or a user abort (panic).
  • AbortReason. The typed enum distinguishing Conflict, Retry, and UserAbort (§11, P6).
  • AtomicPtr. The atomic pointer type holding a TVar's current heap-allocated value (§11, P3).
  • CAS (compare-and-swap). The atomic primitive used for lock acquisition (§8.3) and validation checks.
  • Closed nesting. The nesting model where an inner atomically shares the outer's commit point; the default and only supported mode here (P8, §16.1).
  • Commit. The five-step validate-and-publish sequence that makes a transaction's writes real (§14.2).
  • Commit version. The version stamp a transaction's writes receive at successful commit (§8.3).
  • Conflict. A structural overlap between one transaction's read set and another's write set within a commit window (§8.4).
  • Contention manager. The back-off + priority-bump subsystem preventing livelock under repeated aborts (§17, P9).
  • CommitGuard. The RAII guard releasing acquired locks on panic-driven unwind during commit (§8.7, §14.2).
  • Encounter-time locking. The rejected alternative locking strategy where writes lock immediately rather than at commit (§9 ADR-02, §36.1).
  • Epoch reclamation. The memory-safety scheme deferring deallocation until no pinned thread could hold a stale pointer (§19, P4).
  • Global version clock. The single AtomicU64 totally ordering all commits (I2, §8.3).
  • Acquire / Release (memory ordering). The atomic-operation orderings used to guarantee a reader sees a writer's prior stores; Acquire on load, Release on store, AcqRel on read-modify-write (§11, §13.2).
  • ABA problem. The hazard where a value changes from A to B and back to A between two reads, hiding an intervening write; TL2's version clock (rather than value comparison alone) is the structural defense (§8.3, contrasted with NORec in §36.2).
  • Big-O (scalability notation). The asymptotic-growth notation used throughout §31 to state what stays constant vs. what grows with system size.
  • Fixture. A named, checked-in test case (JSON, under conformance/corpora/) with an expected outcome, feeding a phase's N.5 (§7 methodology, §22.5).
  • MVCC (multi-version concurrency control). The database technique architecturally analogous to TL2's version-clock validation, as used in Postgres/CockroachDB (§2, §33 cross-reference).
  • RCU (read-copy-update). The Linux-kernel deferred-reclamation technique sharing epoch reclamation's core insight with stm-gc (§5, §19, MM4).
  • Serializability. The classical database correctness condition — every committed history is equivalent to some sequential order — that opacity (I1) strictly strengthens (§8.1 note in Books entry 2, §33).
  • Undo log. The rollback record used by encounter-time-locking STMs (TinySTM's write-through mode) to restore pre-transaction values on abort; not used by this project's TL2 approach (§36.1).
  • Wake storm. A burst of wakeups dispatched from one commit to many parked transactions on the same TVar; bounded by waiter count, not by unrelated system activity (§15.7, T3).
  • XBEGIN / XEND / XABORT. The Intel TSX hardware-TM instructions bounding a hardware transaction; studied in §5 and rejected as a Phase 0–11 dependency in §36.3.
  • Herd7. The weak-memory-model checker used to verify fence correctness on architectures beyond native CI (§20.6, P13).
  • Livelock. A state where transactions repeatedly abort each other without any making progress; prevented by the contention manager (§17, FM-8).
  • Loom. The exhaustive interleaving-search test harness used at thread-count 2–3 (§20.1, P12).
  • NORec. A value-based-validation STM algorithm rejected as this project's core algorithm (§9 ADR-02, §36.2).
  • Nested transaction. An atomically call inside another; shares the outer's read/write sets under closed nesting (§16).
  • Opacity. The correctness condition that every read inside a live transaction observes a mutually consistent snapshot, stronger than serializability (I1, Guerraoui & Kapalka 2008).
  • or_else. The composition primitive running a second alternative if the first retries (§15.2, P7).
  • Priority bump. The mechanism letting a repeatedly-aborted transaction preempt a non-priority lock holder (§17.5, I12).
  • Privatization safety. The problem of a value becoming non-transactionally accessible after losing shared reachability while a stale transactional reference may persist (T8, §21.6).
  • Publication safety. The problem of a not-yet-committed value escaping to a non-transactional reader (I14, T7, §21.2).
  • Read set. The set of TVars (and their observed versions) a transaction has read (§8.2).
  • Retry. The primitive aborting a transaction and parking it until a TVar in its read set changes (§15, P6).
  • stm-abi. The crate exposing the C ABI surface via cbindgen (§10, §21).
  • stm-clock. The crate implementing the global version clock and TL2 commit protocol (§10, §14).
  • stm-core. The public-facing facade crate: TVar, atomically, retry, or_else (§10, §11).
  • stm-gc. The crate implementing epoch-based reclamation atop crossbeam-epoch (§10, §19).
  • stm-verify. The crate implementing the opacity oracle plus the loom/shuttle harnesses (§10, §20).
  • stm-wait. The crate implementing the per-TVar retry wait-set and wakeup dispatch (§10, §15).
  • Shuttle. The randomized (PCT-biased) scheduler-based test harness used at thread-count 4–16 (§20.2, P12).
  • TL2 (Transactional Locking II). The commit-time-locking, version-clock-based algorithm this library implements (Dice, Shalev, Shavit, DISC 2006).
  • Torn read. A read that observes a mixture of pre- and post-commit values across two or more TVars, violating opacity if not caught (§8.6).
  • Tx. The per-transaction context accumulating the read set, write set, and metadata; never escapes its closure (§11, P5).
  • TVar. The transactional cell type: TVar<T>, the unit of shared transactional state (§11).
  • TVarId. The stable identifier for a TVar, defined as its heap address (§11, I6).
  • VLock. The packed version-and-lock AtomicU64 word: 63 bits version, 1 bit lock (§8.3, ADR-19).
  • Wait-set. The per-TVar collection of parked transactions' wakers, drained on commit (§15.2, §10).
  • World. The container for the global clock and epoch reclaimer; the STM's only piece of shared global-by-default state (§11, P10).
  • Write set. The set of TVars and their pending new values a transaction will publish at commit (§8.2).
  • Zombie transaction. A transaction that has read inconsistent state and terminates (or would commit) before validation ever catches the inconsistency (§25 FM-12, §18.9).
