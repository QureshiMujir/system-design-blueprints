32. Mental Models & First Principles

MM1 — Commit is a linearization point, not a lock. The compressed insight: the global clock's fetch_add (§14.2 step 3) is the single instant a transaction becomes real; everything before it is provisional. Predicts: any "optimization" that touches shared state before this instant reintroduces the exact contention STM exists to avoid. Bug class without it: engineers who model TL2 as "just locks with extra steps" add coordination in the read phase, silently degrading to lock-based STM (P1 violation). Applied in §14.4, §30.1.

MM2 — Opacity is serializability plus "even the aborted runs must make sense." The compressed insight: a transaction that will abort must still never observe garbage, because user code between reads can crash, loop, or corrupt state before the abort is even detected (§8.6). Predicts: any correctness argument that only reasons about committed histories is incomplete. Bug class without it: engineers ship a "looks serializable" implementation that hangs or crashes on aborted-but-still-executing transactions (T5). Applied in §18, I1.

MM3 — The version-and-lock word is a single fact, read atomically or not at all. The compressed insight: packing version + lock-bit into one AtomicU64 (§8.3) means "is it locked" and "what version" are never observed inconsistently relative to each other. Predicts: splitting them into two atomics reintroduces a race window between the two loads. Bug class without it: a validation check that reads version and lock-bit as two separate atomics can observe a stale version paired with a fresh lock state, silently breaking I3/I5. Applied in §8.3, ADR-19.

MM4 — Epoch reclamation trades "free immediately" for "free once provably safe." The compressed insight: no thread ever knows, at retire time, whether some other thread still holds a pointer — the epoch mechanism (§19) answers this indirectly, by tracking what epoch each thread has pinned. Predicts: a thread that pins for a long time (a long-parked retry) becomes an unbounded reclamation liability, not just a slow thread. Bug class without it: engineers free-on-retire (à la reference counting without the count) and hit intermittent, timing-dependent use-after-free (I10 violation). Applied in §19.1, FM-7.

MM5 — Retry's wakeup set is a promise about what could change the answer, not what was read. The compressed insight: registering a waker on every TVar in the read set (§15.2) is really saying "wake me if anything that could have changed my decision changes" — which is why or_else's read-set union (P7) is not an optimization detail but a correctness requirement. Predicts: any composition primitive that narrows the wakeup set to "only what the winning branch read" will miss wakeups. Bug class without it: FM-4's lost-wakeup bug, precisely. Applied in §15.6, P7.

MM6 — Priority is a scarce resource, not a permanent state. The compressed insight: I12's "at most one priority holder per conflict set" is what keeps the contention manager (§17) from becoming its own livelock source. Predicts: any contention-manager design that lets priority accumulate without a reset condition (§17.2's "resets after next successful commit") eventually deadlocks two mutually-priority transactions against each other. Bug class without it: a "fix" that grants priority permanently to slow transactions creates starvation for everyone else instead of solving it. Applied in §17.6, I12.

MM7 — Closed nesting is "the outer transaction, extended," not "two transactions." The compressed insight: P8's design collapses nested atomically into the same commit point as the outer — there is structurally only ever one commit event per outermost call (§16.1). Predicts: any attempt to give a nested transaction independent success/failure semantics (open nesting, §16.6) requires solving the "partial rollback of an already-visible inner commit" problem, which closed nesting sidesteps by never creating that state in the first place. Bug class without it: engineers implement "nested transactions" as literally nested independent commits and then discover I9 no longer holds. Applied in §16.6, ADR-07.

MM8 — A benchmark answers the question you asked it, not the question you meant. The compressed insight: Cascaval et al.'s 2008 critique (applied throughout §22) is that STM's reputation as "only a research toy" partly comes from benchmarking regimes that do not match production access patterns. Predicts: a single-number "STM vs. Mutex" comparison is meaningless without specifying the contention regime (M1 vs. M2 vs. M3, §4). Bug class without it: shipping a design decision justified by a benchmark run under the wrong regime (e.g. optimizing for M1's uncontended case at the cost of M3's hot-TVar case). Applied in §22.6, §30.6.

MM9 — The global clock is the load-bearing wall; everything else is a partition. The compressed insight: once you see the version clock's fetch_add as the one place all commits must pass through (P1, §34), every other subsystem — locks, wait-sets, epochs, contention management — is visibly a partition built around that single wall, not an independent load-bearing structure of its own. Predicts: any proposed optimization that does not touch the clock (a smarter back-off, a better allocator) can improve constants but never the asymptotic ceiling; only an optimization that changes the clock itself (sharding it, making it lazy, §37) can move the ceiling. Bug class without it: teams chase diminishing-return micro-optimizations on the partitions while the wall itself remains untouched and eventually dominant at scale. Applied in §34, §31.

MM10 — A conformance fixture is a claim, and claims can be wrong. The compressed insight: a fixture's expected output is only as trustworthy as the process that generated it (§18.2's sequential oracle is the trustworthy generator; hand-typed expectations are not, T14/FM-14). Predicts: any fixture corpus that grows primarily by hand-authored JSON rather than oracle-derived expectations will accumulate silent false negatives over time. Bug class without it: a corrupted or mis-derived fixture that "passes" for years because nobody re-derives its expected output from first principles. Applied in §18.5, T14, FM-14.

Required reading (§5)

Books

  • Herlihy & Shavit, The Art of Multiprocessor Programming, 2nd ed. (Morgan Kaufmann, 2020), Ch. 18 (Transactional Memory). Extract: the formal opacity definition and the STM-as-optimistic-concurrency-control framing. Applied in §8, §18.
  • Herlihy & Shavit, The Art of Multiprocessor Programming, Ch. 9 (Linearizability). Extract: the correctness condition opacity strengthens. Applied in §8, §33.
  • Herlihy & Shavit, The Art of Multiprocessor Programming, Ch. 7 (Spin Locks and Contention). Extract: the back-off/contention-manager vocabulary. Applied in §17.
  • **McKenney, Is Parallel Programming Hard, And, If So, What Can You Do About It?, Ch. 9 (Deferred Processing).** Extract: RCU/epoch-reclamation first principles. Applied in §19.
  • Herlihy, Transactional Memory (Synthesis Lectures on Computer Architecture, Morgan & Claypool). Extract: HTM/STM hybrid taxonomy. Applied in §36.
  • Peyton Jones (ed.), Beautiful Code, Ch. 24 ("Beautiful Concurrency"). Extract: the pedagogical case for atomically/retry/orElse as language primitives. Applied in §11.
  • Cesarini & Devin, Erlang and OTP in Action, Ch. 2. Extract: the message-passing alternative STM is contrasted against. Applied in §2, §36.

Papers

  • Herlihy & Moss. "Transactional Memory: Architectural Support for Lock-Free Data Structures." ISCA 1993. Introduces hardware TM and the transaction/abort/commit vocabulary STM inherits. Applied in §1, §2.
  • Shavit & Touitou. "Software Transactional Memory." PODC 1995. The first all-software STM (static, compile-time-known transactions). Applied in §6 (P2), §36.
  • Harris & Fraser. "Language Support for Lightweight Transactions." OOPSLA 2003. The atomic { } block; the torn-read hazard (their Fig. 4). Applied in §8.6, I1.
  • Harris, Marlow, Peyton Jones, Herlihy. "Composable Memory Transactions." PPoPP 2005. retry/orElse composition and the compositionality argument against locks. Applied in §15, P7.
  • Dice, Shalev, Shavit. "Transactional Locking II." DISC 2006. The TL2 algorithm: global version clock, commit-time locking, per-commit validation. Applied in §14, P2, I2.
  • Guerraoui & Kapalka. "On the Correctness of Transactional Memory." PPoPP 2008. The formal opacity definition, distinct from serializability/linearizability. Applied in §18, I1.
  • Felber, Fetzer, Riegel. "Dynamic Performance Tuning of Word-Based Software Transactional Memory." PPoPP 2008. Encounter-time locking and the TinySTM contention-manager taxonomy. Applied in §17, ADR-08.
  • Cascaval, Blundell, Michael, Cain, Wu, Chiras, Chatterjee. "Software Transactional Memory: Why Is It Only a Research Toy?" CACM 2008. Critique of STM's practical viability; responses woven through §4, §17, §22. Applied in §30.
  • Spear, Marathe, Scherer, Scott. "Conflict Detection and Validation Strategies for Software Transactional Memory" (NORec). DISC 2006. Value-based validation without per-object metadata, the alternative rejected in ADR-02. Applied in §9, §36.
  • Herlihy, Luchangco, Moir, Scherer. "Software Transactional Memory for Dynamic-Sized Data Structures" (DSTM). PODC 2003. The dynamic (runtime-determined) transaction shape this project's Tx API follows, contrasted against the static model of paper 2. Applied in §36.4.

Reference Implementations

  • GHC libraries/stm/ (gitlab.haskell.org/ghc/ghc, libraries/stm/Control/Concurrent/STM.hs). Lesson: the STM monad statically prevents IO inside a transaction. Pitfall not to copy: GHC's STM is GC-backed — do not assume free reclamation. Applied in §11, §21.
  • Clojure LockingTransaction (github.com/clojure/clojure, src/jvm/clojure/lang/LockingTransaction.java). Lesson: dynamic transactions and the "barge" priority mechanism. Pitfall: Clojure's ensure (read-without-conflict) is not replicated (non-goal, §1). Applied in §17, P9.
  • ScalaSTM (github.com/nbronson/scala-stm, src/main/scala/scala/concurrent/stm/ccstm/). Lesson: CCSTM's per-Ref version metadata packing, mirroring TL2's version-and-lock word. Pitfall not to copy: JVM-object-header stamps do not translate to Rust; we use an explicit AtomicU64 (ADR-19). Applied in §11, §14.
  • TinySTM (github.com/patrickmarlier/tinystm, src/wt.c). Lesson: pluggable contention-manager interface and encounter-time locking. Pitfall not to copy: TinySTM's striped global lock table trades memory for simplicity; we use per-TVar version-lock words (ADR-19). Applied in §17, ADR-08.
  • GCC libitm (gcc.gnu.org/git, libitm/). Lesson: the ABI-level transaction descriptor and the irrevocable-transaction fallback path. Pitfall not to copy: the serial-irrevocable escape hatch is exactly the feature ADR-24 rejects. Applied in §21, Threat Model T9.
  • crossbeam-epoch (github.com/crossbeam-rs/crossbeam, crossbeam-epoch/src/). Lesson: the three-epoch global/local-pin reclamation scheme stm-gc builds directly on. Pitfall not to copy: pinning a thread for a long transaction stalls reclamation process-wide; §19.6 documents the mitigation. Applied in §19.
  • RSTM (Rochester Software Transactional Memory) (research site: rstm.rochester.edu, the multi-algorithm C++ STM research testbed from Scherer, Scott, Marathe et al.). Lesson: RSTM's side-by-side implementation of multiple algorithms (TL2, NOrec, and others) behind one interface is the direct precedent for this project's ADR-02 documenting rejected alternatives with equal rigor to the chosen one. Pitfall not to copy: RSTM optimizes for algorithm-comparison research flexibility over production performance; this project locks one algorithm (TL2) rather than keeping the interface pluggable. Applied in §9 (ADR-02), §36.

Glossary (§38) · 53 terms · site-wide glossary

atomically
The transaction-block construct; runs a closure as one all-or-nothing operation, retrying on conflict (§11).
Abort
A transaction's failure to commit; either a validation failure (conflict) or a user abort (panic).
AbortReason
The typed enum distinguishing Conflict, Retry, and UserAbort (§11, P6).
AtomicPtr
The atomic pointer type holding a TVar's current heap-allocated value (§11, P3).
CAS (compare-and-swap)
The atomic primitive used for lock acquisition (§8.3) and validation checks.
Closed nesting
The nesting model where an inner atomically shares the outer's commit point; the default and only supported mode here (P8, §16.1).
Commit
The five-step validate-and-publish sequence that makes a transaction's writes real (§14.2).
Commit version
The version stamp a transaction's writes receive at successful commit (§8.3).
Conflict
A structural overlap between one transaction's read set and another's write set within a commit window (§8.4).
Contention manager
The back-off + priority-bump subsystem preventing livelock under repeated aborts (§17, P9).
CommitGuard
The RAII guard releasing acquired locks on panic-driven unwind during commit (§8.7, §14.2).
Encounter-time locking
The rejected alternative locking strategy where writes lock immediately rather than at commit (§9 ADR-02, §36.1).
Epoch reclamation
The memory-safety scheme deferring deallocation until no pinned thread could hold a stale pointer (§19, P4).
Global version clock
The single AtomicU64 totally ordering all commits (I2, §8.3).
Acquire / Release (memory ordering)
The atomic-operation orderings used to guarantee a reader sees a writer's prior stores; Acquire on load, Release on store, AcqRel on read-modify-write (§11, §13.2).
ABA problem
The hazard where a value changes from A to B and back to A between two reads, hiding an intervening write; TL2's version clock (rather than value comparison alone) is the structural defense (§8.3, contrasted with NORec in §36.2).
Big-O (scalability notation)
The asymptotic-growth notation used throughout §31 to state what stays constant vs. what grows with system size.
Fixture
A named, checked-in test case (JSON, under conformance/corpora/) with an expected outcome, feeding a phase's N.5 (§7 methodology, §22.5).
MVCC (multi-version concurrency control)
The database technique architecturally analogous to TL2's version-clock validation, as used in Postgres/CockroachDB (§2, §33 cross-reference).
RCU (read-copy-update)
The Linux-kernel deferred-reclamation technique sharing epoch reclamation's core insight with stm-gc (§5, §19, MM4).
Serializability
The classical database correctness condition — every committed history is equivalent to some sequential order — that opacity (I1) strictly strengthens (§8.1 note in Books entry 2, §33).
Undo log
The rollback record used by encounter-time-locking STMs (TinySTM's write-through mode) to restore pre-transaction values on abort; not used by this project's TL2 approach (§36.1).
Wake storm
A burst of wakeups dispatched from one commit to many parked transactions on the same TVar; bounded by waiter count, not by unrelated system activity (§15.7, T3).
XBEGIN / XEND / XABORT
The Intel TSX hardware-TM instructions bounding a hardware transaction; studied in §5 and rejected as a Phase 0–11 dependency in §36.3.
Herd7
The weak-memory-model checker used to verify fence correctness on architectures beyond native CI (§20.6, P13).
Livelock
A state where transactions repeatedly abort each other without any making progress; prevented by the contention manager (§17, FM-8).
Loom
The exhaustive interleaving-search test harness used at thread-count 2–3 (§20.1, P12).
NORec
A value-based-validation STM algorithm rejected as this project's core algorithm (§9 ADR-02, §36.2).
Nested transaction
An atomically call inside another; shares the outer's read/write sets under closed nesting (§16).
Opacity
The correctness condition that every read inside a live transaction observes a mutually consistent snapshot, stronger than serializability (I1, Guerraoui & Kapalka 2008).
or_else
The composition primitive running a second alternative if the first retries (§15.2, P7).
Priority bump
The mechanism letting a repeatedly-aborted transaction preempt a non-priority lock holder (§17.5, I12).
Privatization safety
The problem of a value becoming non-transactionally accessible after losing shared reachability while a stale transactional reference may persist (T8, §21.6).
Publication safety
The problem of a not-yet-committed value escaping to a non-transactional reader (I14, T7, §21.2).
Read set
The set of TVars (and their observed versions) a transaction has read (§8.2).
Retry
The primitive aborting a transaction and parking it until a TVar in its read set changes (§15, P6).
stm-abi
The crate exposing the C ABI surface via cbindgen (§10, §21).
stm-clock
The crate implementing the global version clock and TL2 commit protocol (§10, §14).
stm-core
The public-facing facade crate: TVar, atomically, retry, or_else (§10, §11).
stm-gc
The crate implementing epoch-based reclamation atop crossbeam-epoch (§10, §19).
stm-verify
The crate implementing the opacity oracle plus the loom/shuttle harnesses (§10, §20).
stm-wait
The crate implementing the per-TVar retry wait-set and wakeup dispatch (§10, §15).
Shuttle
The randomized (PCT-biased) scheduler-based test harness used at thread-count 4–16 (§20.2, P12).
TL2 (Transactional Locking II)
The commit-time-locking, version-clock-based algorithm this library implements (Dice, Shalev, Shavit, DISC 2006).
Torn read
A read that observes a mixture of pre- and post-commit values across two or more TVars, violating opacity if not caught (§8.6).
Tx
The per-transaction context accumulating the read set, write set, and metadata; never escapes its closure (§11, P5).
TVar
The transactional cell type: TVar<T>, the unit of shared transactional state (§11).
TVarId
The stable identifier for a TVar, defined as its heap address (§11, I6).
VLock
The packed version-and-lock AtomicU64 word: 63 bits version, 1 bit lock (§8.3, ADR-19).
Wait-set
The per-TVar collection of parked transactions' wakers, drained on commit (§15.2, §10).
World
The container for the global clock and epoch reclaimer; the STM's only piece of shared global-by-default state (§11, P10).
Write set
The set of TVars and their pending new values a transaction will publish at commit (§8.2).
Zombie transaction
A transaction that has read inconsistent state and terminates (or would commit) before validation ever catches the inconsistency (§25 FM-12, §18.9).
