Project Number: 295

Project Name: Workflow DAG Optimizer

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build, from scratch, a cost-based optimizer and resource-aware scheduler for workflow DAGs — directed acyclic graphs of tasks (units of computation) connected by typed data/control edges. Input: a declarative workflow definition. Output: a semantically-equivalent, optimized execution plan plus a resource-aware schedule, emitted to a pluggable executor interface. The optimizer is to a workflow runtime what a query optimizer is to a database: it ingests a logical graph, applies validity-preserving rewrites, estimates cost, searches the plan space, places tasks on resources, and hands a physical plan to execution.

Precise engineering terms:

  • Frontend — parse workflow definition language (WDL-lite, our DSL) → typed DAG IR. Validate: acyclicity, port type compatibility, resource declaration well-formedness.
  • Canonicalizer — normalize IR to a canonical form (stable node IDs, sorted edges, hashed subgraphs) so equal graphs compare equal and rewrites are confluent where possible.
  • Analyzer — compute derived facts: topological order, critical path, dominators, reachability, artifact liveness.
  • Rewriter — apply validity-preserving rewrite rules (operator fusion, dead-task elimination, common-subgraph elimination, constant/branch folding, predicate pushdown) via a pattern matcher over the IR.
  • Cost Model — estimate per-task and per-plan cost (CPU-seconds, wall-clock, memory-bytes, IO-bytes) from statistics and runtime estimates.
  • Search — explore equivalent plans (greedy + memoized dynamic programming + optional branch-and-bound; equivalence saturation via an e-graph) and select the minimum-cost plan under constraints.
  • Scheduler — resource-aware placement and ordering (list scheduling on critical path, bin-packing onto resource pools, concurrency limits, affinity).
  • Emitter — serialize the chosen physical plan + schedule; expose an executor interface with backpressure.
  • Persistence/Replay — content-addressed task-result cache, deterministic replay log, incremental re-planning on change.

1.1 System boundaries

In scope:

  • DAG IR, the WDL-lite definition language, validation, canonicalization, analysis, rewrite engine, cost model, plan search, scheduling, plan emission, the executor interface (not a full executor), result caching, replay, incremental re-planning, distributed/sharded planning, observability.

Out of scope (the system orchestrates and plans; it does not itself run user code):

  • The task executor runtime (container/process launcher, sandboxing). We define the interface; a reference no-op/simulated executor ships for tests.
  • A general-purpose programming language. WDL-lite is declarative; tasks are opaque handles with declared types and resource profiles.
  • A persistent control-plane database. State is held in an embedded log + content-addressed store; integration with an external store is a deferred interface.
  • UI/visualization beyond textual explain and plan-diff output.

1.2 Explicit non-goals

  • Not a Turing-complete workflow engine; no arbitrary loops (bounded map/fan-out only). Recursion is rejected at validation.
  • Not a stream/dataflow runtime with unbounded streams; edges carry bounded, materializable artifacts.
  • Not a distributed transaction coordinator; the optimizer plans, the executor commits.
  • Not an ML cost model trainer in Phase 0 (statistics-driven estimates only; learned costs deferred — PhaseDeferred("FINAL_BLUEPRINT §5.5 Required Reading")).
  • Not a multi-tenant scheduler with fairness/quotas in Phase 0 (single-tenant; fair-share deferred — PhaseDeferred("FINAL_BLUEPRINT §7.10")).

1.3 Deployment model

  • Primary: a library + CLI (dagopt) embedded in a workflow control plane. Single-process planning.
  • Secondary: a planning service (dagopt-svc) exposing a gRPC plan API for control planes that submit DAGs and receive plans.
  • Scale-out: sharded planner — partition a large DAG across planner shards that plan subgraphs and a coordinator stitches boundary edges (Phase 12).
  • Operators run the service; developers embed the library; workflow authors write WDL-lite.

1.4 Target users / operators / developers

  • Workflow authors — write .wdl definitions; consume explain/plan-diff to understand chosen plans.
  • Platform operators — run dagopt-svc, watch metrics/SLOs, manage the result cache and replay log, perform upgrades.
  • Platform developers — embed dagopt crate, implement the Executor and StatsProvider traits, register custom rewrite rules.

1.9 Recommended language

Rust. Rationale:

  • Immutable shared IR — plan search forks and shares large IR fragments; Arc<Node> + interning gives cheap structural sharing with no GC pauses during search.
  • Strong enums for IR nodes — enum NodeKind { Task, Map, Reduce, Source, Sink, Barrier } and enum RewriteRule { … } make exhaustive matching compiler-checked; an unhandled node kind is a build error, not a runtime panic.
  • Performance for plan search — DP/branch-and-bound over equivalence classes is allocation- and pointer-chase-heavy; zero-cost abstractions, control over layout, and no GC keep p99 planning latency bounded.
  • Fearless concurrency — sharded planning and parallel rule application need data-race-free sharing; the borrow checker enforces it.
  • Ecosystem — petgraph (reference only, we own the IR), salsa/egg (e-graph inspiration), prost/tonic (gRPC), criterion (bench), proptest (property tests), tracing (spans).

Rejected:

  • Go — GC pauses perturb tail planning latency; lack of sum types makes the IR/rule model stringly-typed and error-prone; generics are weaker for the typed-port machinery.
  • C++ — equivalent performance but no borrow checker; the shared-immutable-IR aliasing discipline becomes a manual, bug-prone contract; build/dep hygiene worse.
  • OCaml — excellent for the optimizer core (algebraic types, pattern matching) but weaker for the systems/concurrency layer (scheduler, service, sharding) and a smaller production ecosystem for gRPC/observability.

1.10 Required prerequisites

  • Graph theory — DAGs, topological sorting, dominators, strongly-connected components (for cycle reporting), critical-path method, graph reachability, bipartite matching (for placement).
  • Compilers/optimizers — IR design, SSA-adjacent dataflow, rewrite systems, term rewriting confluence/termination, e-graphs and equivalence saturation, cost-based instruction/plan selection.
  • Query optimization — System-R style cost-based DP, cardinality estimation, predicate pushdown, common-subexpression elimination, plan-space enumeration, memoization (memo table / Cascades groups).
  • Scheduling — list scheduling, critical-path scheduling, bin-packing, makespan minimization, HEFT, resource-constrained project scheduling (RCPSP).
  • Distributed systems — partitioning, coordination, content-addressed storage, deterministic replay, idempotency, eventual consistency of caches.
  • Concurrency — work-stealing, lock-free interning, immutable structural sharing, backpressure, bounded queues.

2. Why Build This

2.1 Unique systems knowledge taught

  • How a cost-based optimizer actually works end-to-end: the loop of normalize → enumerate equivalents → estimate → choose, and why each stage is separable.
  • Why equivalence saturation (e-graphs) beats greedy rewriting for phase-ordering problems, and what it costs.
  • How scheduling and optimization interact — that the cheapest plan is not the shortest makespan, and resource-aware scheduling is a second optimization problem layered on the first.
  • Content-addressing and memoization as the bridge between optimization and incremental execution: the same fingerprint that dedupes subgraphs also keys the result cache.
  • Determinism engineering — making planning reproducible so plans can be diffed, replayed, and trusted in production.

2.2 Historical / architectural significance

  • Descends from System R / Selinger cost-based optimization (1979) and Volcano/Cascades (Graefe) — the lineage of every modern SQL optimizer.
  • Mirrors build systems (Bazel, Buck): a DAG of actions, content-addressed caching, incremental rebuilds, remote execution interface.
  • Mirrors dataflow/orchestration runtimes (Airflow, Dagster, Argo, Temporal, Spark/Tez DAG schedulers): the planning and scheduling half, isolated and made rigorous.
  • E-graph saturation connects to modern compiler research (egg, Cranelift's ISLE, TVM/Halide schedule search).

2.3 Engineering muscles developed

  • IR design under a hard "no implementation leakage" boundary.
  • Writing provably validity-preserving transformations and testing them differentially.
  • Building a memo/search layer that does not blow up combinatorially.
  • Layering two optimization problems (plan cost, then schedule makespan) without conflating them.
  • Production discipline: invariants, telemetry, replay, fuzzing of structured (graph) inputs.

2.4 Production engineering concepts exercised

  • Backpressure, bounded queues, deterministic replay, content-addressed storage, incremental computation, structured tracing of a multi-stage pipeline, plan-diffing for change review, SLOs on planning latency.

2.5 Cross-links to related projects

  • Query optimizers — shares the cost-model/DP/memo machinery; this project is the "logical+physical optimizer" without a storage engine.
  • Build systems (Bazel/Buck) — shares action-graph, content addressing, incremental re-planning.
  • Schedulers (Kubernetes, Borg, Slurm) — shares bin-packing/placement; here coupled to a plan optimizer.
  • Dataflow runtimes (Spark/Tez/Flink planners) — shares DAG scheduling, stage fusion.
  • Durable execution (Temporal, Cadence) — shares deterministic replay and run-state machines; this project plans, Temporal executes durably.
  • Compilers — shares IR, rewrite engine, e-graph saturation, cost-based selection.

2.6 Calibration value

Completing this raises capability permanently: after building a correct, observable, replayable cost-based optimizer + scheduler, the engineer can reason about any optimizer (SQL, compiler, build, query) and any DAG scheduler from first principles, distinguish logical from physical optimization, and recognize when a "performance" problem is actually a phase-ordering or cost-model problem.

2.7 What mastery looks like

  • Design a validity-preserving rewrite system and prove it (Phase 4): author a rule, state its proof obligation, and gate it with a differential harness — never ship a "usually-correct" rewrite.
  • Choose the right search strategy per regime (Phase 6): know when greedy suffices, when DP/Cascades pays for itself, and when only e-graph saturation escapes phase-ordering — and what each costs in latency and memory.
  • Separate two optimization problems cleanly (Phases 6–7): optimize plan cost, then schedule makespan, without conflating them — recognize a makespan regression masquerading as a cost-model bug.
  • Make planning deterministic and reproducible (Phase 11): eliminate hidden nondeterminism (hash iteration, wall clock, FP) so plans diff cleanly and replay byte-identically.
  • Wield content addressing as one mechanism for three jobs (Phases 2, 8): CSE, result cache, and replay keys all from one fingerprint — and know the collision/drift failure that ties them together.
  • Bound every search and degrade gracefully (Phases 6, 9, 13): turn a pathological-DAG DOS into a flagged-suboptimal result, not an OOM.
  • Scale a planner out (Phase 12): partition a DAG to parallelize search and reason about the cut-ratio knee where coordination overtakes the win.

3.2 Per-box detail

FRONTEND (dagopt-parse). Owns the lexer and recursive-descent parser for WDL-lite. Produces IR0, a typed but unvalidated DAG carrying source spans on every node/edge for diagnostics. Responsibilities: tokenization, grammar enforcement, building the node/edge/port structures, attaching declared resource profiles. Boundary: untrusted text in, structurally-typed IR out. Failure mode: parse errors with span and recovery (skip-to-next-task). It performs no graph-global checks (that is VALIDATE's job) so a single concern owns each guarantee.

CONTROL/CLI/SVC (dagopt-cli, dagopt-svc). The request surface. CLI parses args, loads .wdl, drives the pipeline, prints explain/diff. SVC is the gRPC server: receives PlanRequest{ dag, constraints, stats_snapshot }, returns PlanResponse{ plan, schedule, explain, cost }. It owns request lifecycle, deadlines, concurrency limiting (a bounded planning worker pool), and backpressure to clients. It is the only component that talks to the network.

VALIDATION/TRUST BOUNDARY. Everything to the right trusts that IR is acyclic, port-typed, and resource-well-formed. The boundary is enforced by dagopt-validate; bypassing it (e.g., constructing IR programmatically) requires calling Dag::validate() which returns ValidatedDag, a newtype the rest of the system requires. This makes the trust boundary type-enforced, not convention.

VALIDATE (dagopt-validate). Global graph checks: cycle detection (DFS/Kahn), port type unification across every edge, resource declarations within pool capacity, no dangling ports, exactly-one producer per artifact (single-assignment of artifacts). Emits IR1 (ValidatedDag). Detects: cycles (with the offending back-edge path), type mismatches (producer/consumer port types), over-subscription. Recovery: rejection with a structured ValidationError enumerating all violations (not just the first).

CANONICALIZE (dagopt-canon). Rewrites IR1 to IR2: assigns stable, content-derived node IDs; sorts edges and node inputs deterministically; computes a Merkle-style structural hash per node (fingerprint = H(kind, sorted(input_fingerprints), params)). Two structurally-identical subgraphs get identical fingerprints — the foundation of common-subgraph elimination and the result cache. Boundary: determinism — same IR1 always yields byte-identical IR2.

ANALYZE (dagopt-analysis) + ANALYSIS CACHE. Computes derived facts memoized by IR2 fingerprint: topological order, per-node earliest/latest start (critical path), dominator tree, reachability bitsets, artifact liveness (when each artifact may be freed). Facts are immutable and attached to IR2. The cache keys on (dag_fingerprint, analysis_kind) so re-planning an unchanged subgraph reuses analysis.

OPTIMIZER CORE — REWRITE ENGINE (dagopt-rewrite). Pattern matcher over IR2; rule registry of validity-preserving rewrites (fusion, dead-task elimination, common-subgraph elimination, constant/branch folding, predicate pushdown). In greedy mode it applies rules to a fix-point. Feeds the e-graph in saturation mode. Each rule declares a precondition (a pattern + a guard) and a rewrite (a new subgraph), and a proof obligation that outputs are semantically equal to inputs.

OPTIMIZER CORE — E-GRAPH (dagopt-search). An equivalence graph (e-graph): e-classes group provably-equivalent subgraphs, e-nodes are operators whose children are e-classes. Rules are applied non-destructively to saturation (or a budget), so phase-ordering is avoided: all rewrite orders are represented simultaneously. Extraction picks the min-cost representative per e-class.

OPTIMIZER CORE — COST MODEL (dagopt-cost). Pluggable StatsProvider supplies per-task estimates (runtime, memory, IO, cardinality of fan-out). Cost is propagated bottom-up over the DAG; the model returns a Cost vector (cpu_secs, wall_secs, mem_bytes, io_bytes) and a scalar objective (weighted). Costs are monotone where possible so DP pruning is sound.

SEARCH/EXTRACT (dagopt-search). Three strategies: greedy fix-point (fast, no optimality), memoized DP over equivalence classes (System-R-style, optimal within the explored space), branch-and-bound (prune by cost lower bound). For e-graphs, extraction is a min-cost DAG selection (greedy or ILP-lite). Output: IR3, the chosen optimized plan.

SCHEDULER (dagopt-sched) + RESOURCE POOLS. Second optimization problem: given IR3 and resource pools (CPU/mem/IO capacities, concurrency limits, affinity constraints), assign each task a start time and a resource, minimizing makespan subject to constraints. Uses list scheduling on critical-path priority + bin-packing. Output: IR4, a scheduled plan with a ScheduleTable.

EMITTER (dagopt-plan). Serializes IR4 to a stable ExecPlan wire format and performs the executor handshake. Issues backpressure tokens (the executor admits work only up to outstanding-token budget). Boundary: execution — beyond here, the executor (not us) runs tasks.

EXECUTOR IFACE (dagopt-plan) + SIMULATED EXEC. The Executor trait: submit(task) -> TaskHandle, poll(handle) -> TaskState, ack(result_digest). A simulated executor in testkit drives deterministic tests and benchmarks; real executors are external and out of scope.

PERSISTENCE — RESULT CACHE (dagopt-cache). Content-addressed store keyed by task fingerprint → result digest. Enables memoization across runs and incremental re-planning: an unchanged subgraph with a cached result need not be re-scheduled.

PERSISTENCE — REPLAY LOG (dagopt-replay). Append-only log of plan inputs (DAG fingerprint, stats snapshot, constraints, RNG seed) and chosen plan. Enables deterministic replay, regression fixtures, and plan-diff over time.

OBSERVABILITY (dagopt-obs). Metrics (planning latency, e-graph size, rules applied, cache hit rate), tracing spans per stage, structured logs, the explain renderer, and plan-diff. The single place operators look to understand why a plan was chosen.

4. System Constraints

Targets are for a single planner process on a modern x86-64 server (16 cores, 64 GiB RAM) unless noted; "graph N" = number of tasks.

IR resident size ≤ 1.5 KiB / node amortized (interned params, Arc sharing)

  • DP memo entries default 5M; LRU-evict equivalence groups beyond, log a memo_pressure event.
  • Branch-and-bound node budget 1M; on exhaustion return best-so-far flagged suboptimal=true.

6. Design Principles

  1. Validity-preservation is absolute. Every rewrite maps a DAG to a semantically-equivalent DAG: same observable outputs for the same inputs. Tradeoff: forbids speculative "usually-correct" rewrites. Operational: a differential test (optimized vs unoptimized execution) gates every rule. Violation: silent wrong results in production — the worst failure class, undetectable without differential testing.

  2. Logical/physical/schedule separation. Three distinct stages with distinct IRs (IR2 logical, IR3 physical/optimized, IR4 scheduled). Tradeoff: more IR conversions. Operational: each stage independently testable and observable via explain. Violation: cost model and scheduler become entangled, makespan regressions masquerade as cost bugs.

  3. Determinism over convenience. Same inputs (DAG, stats, constraints, seed) → byte-identical plan. Tradeoff: forbids unseeded randomness, wall-clock-dependent decisions, hash-map iteration order. Operational: plan-diff and replay only work if deterministic. Violation: plan-diff produces noise, replay diverges, incidents become irreproducible.

  4. Bounded resource usage. Every search has a node/time/memory budget; exceeding it degrades gracefully (fall back to greedy, return best-so-far flagged suboptimal). Tradeoff: may return non-optimal plans. Operational: planning latency SLO is enforceable. Violation: a pathological DAG OOMs or hangs the planner — a DOS vector (see Threat Model).

  5. Content addressing is the spine. Subgraph fingerprints serve three masters: common-subgraph elimination, the result cache, and replay keys. Tradeoff: fingerprints must be stable across versions (or versioned). Operational: a cache hit and a CSE share one mechanism. Violation: cache poisoning or false dedup if fingerprints collide or drift.

  6. Cost monotonicity where claimed. When the cost model claims monotonicity (a subplan's cost ≤ any plan containing it), DP pruning depends on it. Tradeoff: some realistic costs are non-monotone (caching makes a bigger plan cheaper); those are modeled explicitly and disable pruning locally. Operational: pruning is sound only under declared monotonicity. Violation: DP prunes the optimal plan, silently returns a worse one.

  7. Explicit ownership of IR. IR nodes are immutable Arc-shared after canonicalization; rewrites produce new nodes, never mutate. Tradeoff: allocation churn during search. Operational: safe concurrent search, cheap structural sharing, trivial replay. Violation: a mutated shared node corrupts every plan referencing it across threads.

  8. Backpressure everywhere. The emitter issues bounded tokens; the executor pulls within budget; the service bounds its planning pool. Tradeoff: throughput capped by slowest stage. Operational: no unbounded queue growth, predictable memory. Violation: a slow executor causes unbounded plan buffering and OOM.

  9. Observability by default. Every stage emits spans, metrics, and contributes to explain. Tradeoff: tracing overhead (mitigated by sampling). Operational: "why this plan?" is always answerable. Violation: plan choices are black boxes, incidents undebuggable.

  10. Replayability first. Inputs to every plan are logged sufficiently to reproduce it offline. Tradeoff: log volume (mitigated, ≤ 200 B/plan). Operational: regression fixtures generated from production, bugs reproduced exactly. Violation: production-only bugs cannot be reproduced.

  11. Stable wire/IR compatibility. Wire and serialized-IR formats are versioned; new versions read old. Tradeoff: migration code. Operational: rolling upgrades of the service, cache survives upgrades. Violation: an upgrade invalidates the cache or breaks in-flight clients.

  12. Crash-only persistence. Cache and replay log are append-only and crash-consistent; recovery is reopen + truncate-torn-tail, never a repair tool. Tradeoff: no in-place edits. Operational: kill -9 is safe. Violation: a crash mid-write corrupts the cache, poisoning future plans.

  13. Fail closed on ambiguity. Unknown node kinds, missing stats, or unverifiable rewrite preconditions reject (or skip the rewrite) rather than guess. Tradeoff: conservative plans. Operational: no silent miscompilation. Violation: an unhandled construct is silently dropped from the plan.

  14. Separation of trust boundaries. Untrusted text is validated once; past the validation boundary the IR is trusted by type (ValidatedDag). Tradeoff: a newtype barrier to cross. Operational: downstream code need not re-validate. Violation: an unvalidated graph reaches the optimizer, which assumes acyclicity and loops forever.

  15. Small, composable rules. Rewrite rules are small, independently testable, and order-insensitive under saturation. Tradeoff: more rules than monolithic passes. Operational: a buggy rule is isolated and disableable by flag. Violation: a monolithic pass conflates concerns and is untestable in isolation.

8.2 DAG IR — typed node/edge model

NodeKind  ::= Source        // external input, no in-ports
            | Task          // opaque op, in/out ports, resource profile
            | Map           // fan-out: applies child over an array artifact
            | Reduce        // fan-in: folds an array of artifacts
            | Barrier       // sync point, no transform
            | Sink          // terminal output
            | Const         // compile-time-known value (folding target)

Node      = { id: NodeId, kind: NodeKind, op: OpId, params: ParamMap,
              in: [Port], out: [Port], pool: PoolId?, pure: bool,
              span: Span, fingerprint: Fp }

Port      = { name: Sym, ty: Type, node: NodeId, idx: u16 }

Edge      = { from: (NodeId, PortIdx), to: (NodeId, PortIdx), artifact: ArtifactId }

Artifact  = { id: ArtifactId, ty: Type, producer: (NodeId,PortIdx),
              consumers: [(NodeId,PortIdx)], size_est: u64, digest: Digest? }

Type lattice (for unification): ⊥ < {int,float,bool,string,bytes} < array<T> < record{...} < ⊤. Unification fails on incompatible base types; array<T>/record unify structurally.

8.3 Rewrite-rule representation

Rule      = { name: Sym, pattern: Pattern, guard: Guard, rewrite: Rewrite,
              cost_delta: CostHint, proof: ProofTag }
Pattern   = tree of PNode; PNode = Op(OpId,[Pattern]) | Var(VarId) | AnyPure
Guard     = predicate over bindings (e.g., is_pure(?t), types_eq(?a,?b))
Rewrite   = constructor of new subgraph from bindings
ProofTag  = Algebraic | Identity | DeadCode | Dedup | Fold | Pushdown

Example rules (illustrative, not exhaustive):

  • Fusion: Task(f, Task(g, ?x)) where both pure and pool compatible ⇒ Task(f∘g, ?x) — ProofTag=Algebraic, fewer scheduling units.
  • Dead-task elimination: ?t with no live out-edge and pure ⇒ delete — DeadCode.
  • Common-subgraph elimination: two nodes with equal fingerprint and pure ⇒ merge, redirect consumers — Dedup.
  • Constant folding: Task(f, Const(c)) and f pure ⇒ Const(f(c)) — Fold.
  • Branch folding: Map over Const([...]) with known length ⇒ unrolled fixed fan-out — Fold.
  • Predicate pushdown: Filter(p, Task(t, ?x)) where p independent of t ⇒ Task(t, Filter(p, ?x)) — Pushdown, shrinks intermediate artifact.

8.7 Scheduling semantics

  • A task may start only after all in-edge artifacts exist (precedence).
  • Concurrency at any instant ≤ pool concurrency limit; resource use ≤ pool capacity.
  • Priority = critical-path length (longest path to any sink) — list scheduling.
  • Affinity: tasks may pin to a pool (pool=); unpinned tasks bin-pack to minimize makespan.
  • Determinism: ties broken by (critical_path desc, fingerprint asc) — total order, no randomness.

8.8 Determinism semantics

  • Plan is a pure function of (IR1, stats_snapshot, constraints, weights, seed).
  • All ordering uses explicit total orders (fingerprint, NodeId), never hash iteration.
  • Floating-point cost compares with a fixed epsilon and deterministic tie-break to avoid platform FP divergence.
  • The seed parameterizes any randomized search (B&B node order) so randomness is reproducible.

8.9 Worked example

WDL-lite:

workflow etl {
  pool big { cpu=8, mem=16GiB, concurrency=4 }
  task load  { op="read";  out(d: array<record{id:int,v:float}>); pure; }
  task filt  { op="filter"; in(d: array<record{id:int,v:float}>);
               out(d: array<record{id:int,v:float}>); pure; }
  task agg   { op="sum";    in(d: array<record{id:int,v:float}>); out(s: float); }
  task agg2  { op="sum";    in(d: array<record{id:int,v:float}>); out(s: float); }
  edge load.d -> filt.d;  edge filt.d -> agg.d;  edge filt.d -> agg2.d;
}

Pipeline:

  • Validate: acyclic, types unify (array<record{...}> on every edge), single producer per artifact.
  • Canonicalize: agg and agg2 have identical fingerprints (same op, same input fingerprint, pure).
  • Rewrite: CSE merges agg/agg2 → one node, both consumers of its s. Predicate pushdown: filt already adjacent to load; if filt selective, push toward source.
  • Cost: estimate load IO, filt selectivity shrinks artifact, agg cheap.
  • Schedule: critical path load→filt→agg; place on big, concurrency 4 unused (linear), makespan = sum.
  • Emit: ExecPlan with 3 tasks (after CSE), schedule table, backpressure tokens.

8.11 Edge-case / malformed examples

  • Cycle: edge a.x -> b.y; edge b.y2 -> a.z; → ValidationError::Cycle{path:[a,b,a]}.
  • Type mismatch: producer out(d: array<int>) to consumer in(d: array<float>) → TypeMismatch.
  • Dup producer: two out ports feeding one artifact → DuplicateProducer.
  • Dangling port: in(d:int) never connected → UnboundPort (warning if optional, error if required).
  • Unbounded map: map over x where x length unknown and no fanout_cardinality stat → planned with conservative estimate; if x from a non-terminating source → rejected (only bounded artifacts).
  • Self-edge: edge a.x -> a.y → Cycle (trivial).
  • Empty workflow: no sinks → NoSink error (nothing to compute).

11. Core Schema and Core Types

All types in dagopt-ir unless noted. Convention: Id types are u32 newtypes (interned), Sym is an interned string, Fp is a 32-byte BLAKE3 digest.

11.1 Identity and interning

NodeId(u32); ArtifactId(u32); PoolId(u32); OpId(u32); Sym(u32); RuleId(u16)
Fp([u8;32])                       // structural fingerprint / content address
Span { lo: u32, hi: u32, file: FileId }
  • Ownership: IDs are values (Copy). The Interner owns the backing arena (Arc<Interner> shared, append-only). Interner mutation = intern-only (never remove), so IDs are stable for process lifetime.
  • Concurrency: interner is a sharded concurrent map (dashmap) + arena; reads lock-free, inserts shard-locked.
  • Persistence: IDs are not persisted across processes; serialization writes resolved strings/params. Fingerprints (Fp) are the cross-process stable identity.
  • Serialization: Fp is the cache key and replay key; CBOR-encoded as 32 bytes.
  • Compatibility: Fp algorithm is versioned (fp_version); a version bump invalidates cache (handled by namespacing the cache by fp_version).

11.2 DAG and nodes

Dag { nodes: Vec<Node>, edges: Vec<Edge>, artifacts: Vec<Artifact>,
      pools: Vec<Pool>, params: ParamMap, roots: Vec<NodeId>, sinks: Vec<NodeId> }

ValidatedDag(Dag)                  // newtype; only constructible via validate()
CanonicalDag { dag: ValidatedDag, order: Vec<NodeId>, fps: Vec<Fp> }

Node { id, kind: NodeKind, op: OpId, params: ParamMap,
       in_ports: SmallVec<[Port;2]>, out_ports: SmallVec<[Port;2]>,
       pool: Option<PoolId>, pure: bool, span: Span, fp: Fp }

NodeKind = Source | Task | Map { over: ArtifactId } | Reduce { init: Sym }
         | Barrier | Sink | Const { value: ConstVal }
  • Ownership: Dag owns its Vecs; after canonicalization, CanonicalDag is wrapped in Arc and shared immutably across search threads. Rewrites build new Arc<CanonicalDag> fragments.
  • Mutation: pre-validation only. Post-canon: immutable; transformations are functional (copy-on-write of the changed region, shared tails).
  • Concurrency: Arc<CanonicalDag> is Send + Sync; safe for parallel search.
  • Persistence: serialized as a node/edge list with resolved params + fp (for verification on load).
  • Serialization: CBOR, version-tagged. SmallVec flattens to arrays.
  • Compatibility: adding a NodeKind variant is a breaking IR change (major version); readers reject unknown kinds (I16).

11.3 Ports, edges, artifacts, types

Port { name: Sym, ty: Type, idx: u16, required: bool }
Edge { from: PortRef, to: PortRef, artifact: ArtifactId }
PortRef { node: NodeId, port: u16 }
Artifact { id, ty: Type, producer: PortRef, consumers: SmallVec<[PortRef;4]>,
           size_est: u64, digest: Option<Digest>, live: bool }
Type = Int | Float | Bool | Str | Bytes | Array(Box<Type>) | Record(Vec<(Sym,Type)>)
ConstVal = ... (matches Type)
  • Ownership: artifacts owned by Dag; digest populated post-execution (by cache layer) — the only field mutated after canon, guarded behind the cache, not the optimizer.
  • Concurrency: artifact digest/live updates happen post-plan, single-threaded in the cache layer.
  • Serialization: Type is recursively encoded; Record field order canonicalized (sorted by Sym's resolved string) for stable fingerprints (I5).

11.4 Rewrite rule types (dagopt-rewrite)

Rule { id: RuleId, name: Sym, pattern: Pattern, guard: GuardFn,
       build: BuildFn, proof: ProofTag, enabled: bool }
Pattern = Op(OpId, Vec<Pattern>) | Var(VarId) | AnyPure | AnyConst
GuardFn  = fn(&Bindings, &CanonicalDag) -> bool
BuildFn  = fn(&Bindings, &mut DagBuilder) -> NodeId
Bindings = Map<VarId, NodeId>
ProofTag = Algebraic | Identity | DeadCode | Dedup | Fold | Pushdown
RuleRegistry { rules: Vec<Rule>, by_root_op: Map<OpId, Vec<RuleId>> }
  • Ownership: registry owned by the optimizer config; Arc-shared, immutable after load.
  • Concurrency: rules applied in parallel over disjoint match sites; BuildFn writes to a thread-local DagBuilder, merged under lock.
  • Compatibility: rules are versioned by RuleId; replay records the active rule-set hash so a plan replays under the same rules (I15).

11.5 Cost types (dagopt-cost)

Cost { cpu_secs: f64, wall_secs: f64, mem_bytes: u64, io_bytes: u64 }

  fn task_mem(&self, op: OpId, params: &ParamMap, in_sizes: &[u64]) -> u64;

  • Monotonicity: cpu_secs, io_bytes declared monotone; wall_secs non-monotone (caching/fusion can reduce a superplan below a subplan); mem_bytes non-monotone. DP pruning uses only monotone dimensions (I8).
  • Persistence: a stats_snapshot (the StatsProvider's serialized state) is captured per plan for replay.

11.6 Search types (dagopt-search)

Phase 1 — DAG IR, Parser/Loader, Validation

1.1 Objectives

  • Define the canonical DAG IR (Node/Edge/Port/Artifact/Type) and identity/interning machinery.
  • Parse WDL-lite text → IR0 with spans and recoverable diagnostics.
  • Validate IR0 → ValidatedDag (IR1): acyclicity, port-type unification, single-producer, resource well-formedness.
  • Establish the type-enforced validation/trust boundary (only validate() produces ValidatedDag).
  • Constraint introduced: nothing downstream accepts an unvalidated Dag.

1.2 Detailed Implementation Steps

  • dagopt-ir/src/ids.rs: newtype IDs (NodeId, ArtifactId, PoolId, OpId, Sym, RuleId), all Copy, #[repr(transparent)] over u32/u16.
  • dagopt-ir/src/intern.rs: Interner { strings: DashMap<Box<str>,Sym>, ops: ..., arena: bumpalo }. intern_str(&str)->Sym, resolve(Sym)->&str. Sharded by hash to reduce insert contention. Append-only: never removes — guarantees stable IDs.
  • dagopt-ir/src/node.rs, edge.rs, port.rs: the structs from §11 (Core Schema). Node uses SmallVec<[Port;2]> (most tasks ≤2 ports). Type unification in port.rs::unify(&Type,&Type)->Result<Type,TypeErr> over the lattice (§8.2, Domain Model).
  • dagopt-ir/src/fingerprint.rs: fingerprint(node, child_fps) = blake3(kind_tag || op || sorted(child_fps) || canonical(params)). fp_version constant prefixed into the hash input.
  • dagopt-parse/src/lexer.rs: hand-written lexer (no generator) producing (Token, Span); tokens for keywords (workflow, task, edge, pool, param, pure, map, over), idents, literals, punctuation, byte-size suffixes.
  • dagopt-parse/src/parser.rs: recursive-descent per §8.1 (Domain Model) EBNF. Builds Dag incrementally. Error recovery: on unexpected token inside a task block, skip to next } or top-level keyword, emit diagnostic, continue (collect all errors).
  • dagopt-parse/src/diag.rs: Diagnostic { severity, span, msg, note }; renders with source line + caret.
  • dagopt-validate/src/acyclic.rs: Kahn's algorithm (compute in-degrees, peel zero-in-degree). If residual nodes remain → cycle; recover the cycle path via DFS from a residual node following an unsatisfied in-edge (for the error message).
  • dagopt-validate/src/typeck.rs: for each edge, unify(producer_port.ty, consumer_port.ty); record all mismatches.
  • dagopt-validate/src/resource.rs: every pool= reference resolves; declared cost{mem=} ≤ pool mem; concurrency ≥ 1.
  • dagopt-validate/src/lib.rs: validate(dag: Dag) -> Result<ValidatedDag, Vec<ValidationError>> runs all checks, aggregates errors (does not short-circuit on first).
  • Observability hooks: each validation pass emits a tracing span validate.acyclic etc. with node counts; counters validate.errors_total{kind}.
  • Test harness: dagopt-testkit/src/fixtures.rs loads .wdl fixtures and expected outcomes (valid / error-kind list).
  • Theory anchors: Kahn acyclicity → I1 + CLRS ch.22; type unification → I2 + Dragon Book ch.6; single-assignment → I3, P5; the ValidatedDag newtype boundary → P14; interning/IDs → ADR-10; BLAKE3 fingerprint → ADR-09, I5.

1.6 Pitfalls

  • Span drift after error recovery. Manifestation: diagnostics point at wrong lines after a skip. Root cause: skip-to-recovery loses byte offsets. Debug: assert every Diagnostic.span is within file bounds; fuzz parser and check span validity. Signals: parse.span_oob counter. Recovery: clamp spans; add span invariants test.
  • Interner unbounded growth. Manifestation: RSS climbs on a service planning many distinct DAGs. Root cause: append-only interner never frees per-request symbols. Debug: track interner size metric. Signal: intern.size. Recovery: per-request interner scope (reset between requests) — interner is request-scoped, not global, in the service.
  • Fingerprint includes nondeterministic param order. Manifestation: equal graphs get different Fp (I5 violation). Root cause: ParamMap iterated in hash order. Debug: canon test re-hashing. Signal: canon.fp_collision/skew. Recovery: sort params by key before hashing (done in canonical(params)).
  • Cycle path report is just "a cycle exists". Manifestation: operator can't locate the cycle. Root cause: Kahn detects but doesn't reconstruct. Debug: DFS reconstruction test on every cyclic fixture. Recovery: implement back-edge DFS path recovery.
  • Type unification too permissive. Manifestation: array<int> accepted where array<float> expected, wrong results downstream. Root cause: base-type coercion in unify. Debug: property test that unify(a,b)=Ok ⇒ a,b interchangeable. Recovery: forbid implicit numeric coercion; require explicit cast nodes.

1.7 Performance Concerns

  • Parser is single-pass, allocation-light (intern on the fly). Avoid per-token String; slice the source.
  • Validation is two linear passes (Kahn + edge scan); reachability uses bitsets for cache locality.
  • SmallVec keeps ports inline (no heap) for the common case.
  • Interner insert contention only matters in the service; request-scoped interners avoid global lock.

1.8 Edge Cases

  • Empty workflow → NoSink.
  • Single node, no edges → valid iff it is a Sink-reachable Source+Sink (degenerate).
  • Self-edge → Cycle.
  • Duplicate task name → parse error Redefinition.
  • Port referenced that doesn't exist → UnknownPort (parse/validate).
  • Very deep linear chain (N=1M) → Kahn handles in O(N); recursion-free (no stack overflow).
  • Unicode in identifiers → restricted to ASCII identifiers (grammar), reject others with a clear message.

1.9 Failure Analysis

  • What breaks: malformed input crashes the parser (panic) instead of erroring. Detection: fuzz fuzz_targets/parse.rs to zero panics. Blast radius: a service request, not the process (panics caught at request boundary, returned as 500/INVALID_ARGUMENT). Containment: catch_unwind at the request handler; library callers get Result. Recovery: fix grammar/recovery; add fixture. Operator visibility: parse.panic counter, error log with input hash. Postmortem: replay the input from the hash via scripts/replay_prod.sh.

1.10 Operational Notes

  • Metrics: parse.bytes, parse.errors{kind}, validate.errors{kind}, validate.duration, ir.nodes, ir.edges.
  • Tracing: span pipeline.frontend with child spans per pass; attributes node/edge counts.
  • Logging: structured, one line per rejected workflow with the first error and total error count.
  • Deployment: pure CPU, no IO; embeddable. No migration concerns (Phase 1 has no persistence).
  • Compatibility: IR Type/NodeKind additions are major-version; document in CHANGELOG.

Phase 2 — Canonicalization and Normalization

2.1 Objectives

  • Transform ValidatedDag (IR1) → CanonicalDag (IR2): deterministic node ordering, stable content-derived IDs, structural fingerprints per node and subgraph.
  • Guarantee: structurally-equal subgraphs share one Fp (I5); same IR1 → byte-identical IR2 (I4).
  • Provide subgraph fingerprinting as the substrate for CSE (P4) and the result cache (P8/P11).
  • Constraint: canonicalization is a pure, total function with no external state.

2.2 Detailed Implementation Steps

  • dagopt-canon/src/order.rs: deterministic topological order — Kahn with a min-heap keyed by (in_degree=0 set), tie-broken by a pre-fingerprint (hash of local node attributes only, no children) then by source span. This gives a stable order before full fingerprints exist.
  • dagopt-canon/src/subgraph.rs: bottom-up fingerprint in topo order: fp[n] = blake3(fp_version || kind || op || canonical_params(n) || sorted(fp[child] for child in inputs(n))). Because inputs are processed first, every node's children already have fingerprints. Sorting child fps makes commutative ops (e.g., Reduce over a set) canonical.
  • Handle commutativity explicitly: ops flagged commutative sort their input fps; non-commutative ops preserve port order (use (port_idx, fp) pairs).
  • dagopt-canon/src/canon.rs: assign canonical NodeIds = rank in canonical topo order. Rewrite all PortRef/Edge/Artifact references to canonical IDs. Sort edges and artifacts vectors by (from, to). Produce CanonicalDag { dag, order, fps }.
  • Collision audit: maintain Map<Fp, NodeId>; on a fingerprint hit, deep-structural-equality check the two nodes; if unequal → CanonError::FingerprintCollision (astronomically unlikely with BLAKE3, but audited; falls back to treating them as distinct).
  • Determinism guard: canon(canon(x)) == canon(x) (idempotence) and bytes(canon(x)) stable — golden test re-runs canon 100× and byte-compares.
  • Subgraph extraction API: subgraph_fp(node) -> Fp (the node's fp = the fp of the subgraph rooted at it). equal_subgraphs(a,b) = fp[a]==fp[b] (with audit).
  • Observability: span pipeline.canon; metric canon.fp_unique (distinct fps), canon.dedup_candidates (fp collisions = CSE opportunities), canon.duration.
  • Theory anchors: deterministic canon → I4, P3; equal-subgraph fingerprints → I5, P5, ADR-09 (BLAKE3); Merkle-style structural hash → RFC 6962-style hashing (§5.4, Required Reading); collision deep-eq audit → I5; idempotence guard → P3.

2.3 Deliverable

  • dagopt canon <file.wdl> (debug) prints canonical node order with fingerprints.
  • Library: canonicalize(ValidatedDag) -> CanonicalDag.
  • CanonicalDag is the universal input to analysis, rewrite, cost, search.

2.4 Acceptance Criteria

  • Idempotence: canon(canon(d)) == canon(d) byte-identical on all fixtures.
  • Determinism: 1000 re-canonicalizations of each fixture produce identical bytes (I4).
  • Equal-subgraph detection: in diamond.wdl and etl.wdl, structurally-identical subtrees get identical fps; differing ones differ (I5), verified against hand-computed expectations.
  • Performance: canonicalization ≤ 2× the cost of a topo sort; ≥ 500k nodes/s.
  • Memory: fingerprints add ≤ 32 B/node; no quadratic blowup on wide fan-out.

  • conformance/ir/canon_cse.wdl — two identical subtrees → equal fps (CSE candidate).

  • conformance/ir/canon_noncommutative.wdl — reordered non-commutative inputs → different fp.
  • conformance/ir/canon_idempotent.golden — re-canon byte-identical.
  • Compat: conformance/ir/canon_fpv1.golden pinned to fp_version=1 (detects accidental fp algorithm change).

2.6 Pitfalls

  • Tie-break instability. Manifestation: canonical order differs run-to-run for nodes with equal in-degree. Root cause: relying on insertion/hash order to break ties. Debug: determinism golden test. Signal: canon.nondeterminism. Recovery: total tie-break (pre_fp asc, span asc).
  • Commutativity mishandled. Manifestation: a+b and b+a get different fps (missed CSE) or, worse, a-b and b-a get the same fp (wrong dedup). Root cause: blanket sorting of all child fps. Debug: per-op commutativity table test. Recovery: sort only for ops flagged commutative.
  • Fingerprint not covering params. Manifestation: two tasks with same op but different params dedup incorrectly. Root cause: params omitted from hash. Debug: differential test (dedup then execute, compare). Signal: cache.key_result_skew. Recovery: include canonicalized params in the hash.
  • fp_version not namespaced into cache. Manifestation: after an fp algorithm change, stale cache entries served against new fps. Root cause: cache keyed by raw fp. Debug: bump fp_version in a test, assert cache miss. Recovery: cache key = (fp_version, fp).
  • Large param blobs in hash input. Manifestation: canon slow on tasks with big inline params. Root cause: hashing megabyte params each time. Debug: profile canon. Recovery: pre-intern params and hash the interned id when params are large/identical.

2.7 Performance Concerns

  • Bottom-up fp is one linear pass given topo order; reuse the topo order from P1's validation when available (analysis cache).
  • Sorting child fps is O(k log k) per node; k small for most nodes; wide fan-in (Reduce over thousands) is the worst case — use radix on the 32-byte fps if k large.
  • BLAKE3 is SIMD-accelerated; hashing dominates; batch small inputs.
  • Cache the pre_fp to avoid recomputation across the order and fp passes.

2.8 Edge Cases

  • Two sinks with identical subtrees → both fps equal; canonical order still total (tie-break).
  • Diamond (shared subexpression) → the shared node has one fp, referenced by two parents; canonical IDs assigned once.
  • Self-referential params (a task param referencing another task's name) → resolved to fp references, not names.
  • Empty params → canonical empty encoding (not "missing"), so absent vs empty are distinguished consistently.
  • Maximum fan-in/out (single node consuming/producing thousands of artifacts) → fp sort cost bounded by radix.

2.9 Failure Analysis

  • What breaks: a fingerprint collision (true or, more likely, a bug producing equal fps for unequal graphs). Detection: the deep-eq audit on every fp hit; canon.fp_collision metric. Blast radius: incorrect CSE/cache reuse → wrong results — high severity. Containment: audit treats colliding-but-unequal as distinct (correctness preserved at cost of a missed dedup). Recovery: investigate the hash input construction; the audit prevents silent corruption. Forensic: log both nodes' full structural dumps. Postmortem: add the pair as a regression fixture.

2.10 Operational Notes

  • Metrics: canon.fp_unique, canon.dedup_candidates, canon.collisions, canon.duration_ms.
  • Tracing: span attributes — distinct fps, dedup candidates (a leading indicator of optimizer benefit).
  • Logging: warn on any collision-audit hit (should be ~never).
  • Deployment: pure CPU; no persistence. fp_version is a build constant; changing it is a documented, cache-invalidating event.
  • Compatibility: fp_version bump = cache namespace change + replay-log note; document migration in the Compatibility & Versioning section.

Phase 3 — Analysis Passes

3.1 Objectives

  • Compute derived, immutable facts over CanonicalDag (IR2), memoized by dag fingerprint: topological order, critical path (earliest/latest start, slack), dominator tree, reachability bitsets, artifact liveness.
  • These facts feed rewrites (liveness → DCE), cost (critical path → wall estimate), scheduling (critical path → priority).
  • Constraint: analyses are pure; results cached and shared (Arc), invalidated only by fingerprint change.

3.2 Detailed Implementation Steps

  • dagopt-analysis/src/topo.rs: reuse the canonical order (already a valid topo order from P2); expose topo_order() -> &[NodeId] and reverse_topo().
  • dagopt-analysis/src/critpath.rs: forward pass over topo order computes earliest_start[n] = max(earliest_finish[pred]); earliest_finish = earliest_start + duration(n) (duration from cost model stub or unit). Backward pass over reverse topo computes latest_finish/latest_start; slack = latest_start - earliest_start. Critical path = nodes with slack 0. critical_path_len() -> f64 = max earliest_finish.
  • dagopt-analysis/src/dom.rs: dominator tree via Cooper-Harvey-Kennedy iterative algorithm over the topo order (cheap, near-linear in practice). Used to identify single-entry regions for region-scoped rewrites and to bound predicate pushdown.
  • dagopt-analysis/src/reach.rs: reachability via bitset propagation in reverse topo order: reach[n] = {n} ∪ ⋃ reach[succ]. Bitsets sized to node count; for very large graphs, use roaring bitmaps. Answers "does artifact of n feed sink s?".
  • dagopt-analysis/src/liveness.rs: an artifact is live from its producer until its last consumer completes. Compute last_use[artifact] = max position (in schedule order, here topo order as proxy) among consumers. Liveness intervals enable memory-pressure estimation and DCE (artifact with no live consumer → dead).
  • dagopt-analysis/src/cache.rs: AnalysisCache { map: DashMap<(Fp, AnalysisKind), Arc<dyn Any>> }. Key = (dag fp, which analysis). get_or_compute. Eviction LRU under a configurable cap.
  • Each analysis exposes a typed accessor returning Arc<Facts>; facts are immutable.
  • Observability: spans analysis.topo, analysis.critpath, analysis.dom, analysis.reach, analysis.liveness; metrics for duration and cache hit/miss.
  • Theory anchors: critical path → Adam/Chandy/Dickson 1974, feeds Phase 7 priority; dominators → Cooper-Harvey-Kennedy, bounds pushdown (Phase 4); liveness fix-point → Appel ch.17–19; reachability bitsets → CLRS ch.22; analysis cache keyed by fp → P5, I5; facts immutable & Arc-shared → P7.

3.3 Deliverable

  • dagopt explain --analysis <file.wdl> prints critical path, per-node slack, dominators, and live ranges.
  • Library: analyze(&CanonicalDag) -> Analysis { topo, critpath, dom, reach, liveness } (lazily computed, cached).

3.4 Acceptance Criteria

  • Critical path matches hand-computed values on diamond.wdl, fanout.wdl, etl.wdl.
  • Dominator tree validated against a brute-force O(n²) reference on small graphs (differential).
  • Reachability matches transitive-closure reference on small graphs.
  • Liveness intervals: no artifact reported live after its last consumer; verified by property test.
  • Performance: all analyses linear-ish; critical path ≥ 1M nodes/s; dominators ≥ 200k nodes/s; cache hit ≤ 1 µs.
  • Memory: reachability bitsets ≤ N²/8 bytes worst case; roaring for sparse large graphs caps growth.

3.5 Conformance Fixtures

  • conformance/ir/analysis_diamond.golden — critical path, slack, dominators.
  • conformance/ir/analysis_fanout.golden — wide fan-out critical path (max over branches).
  • conformance/ir/analysis_liveness.golden — live ranges for an ETL pipeline.
  • conformance/ir/analysis_dom_chain.golden — linear chain dominators (each dominates the next).
  • Regression: analysis_regress_* for each fixed analysis bug.

3.6 Pitfalls

  • Critical path off-by-duration. Manifestation: wrong scheduling priority, suboptimal makespan. Root cause: confusing start vs finish in the recurrence. Debug: hand-compute on diamond; assert earliest_finish = earliest_start + duration. Signal: differential vs reference. Recovery: unit tests pinning the recurrence.
  • Dominator iteration not converged. Manifestation: incorrect dominators on irreducible-looking graphs (shouldn't occur in DAGs but bugs do). Root cause: insufficient iterations / wrong RPO. Debug: compare to brute force. Recovery: iterate to fix-point; assert convergence.
  • Reachability bitset OOM. Manifestation: 100k-node dense graph allocates 1.25 GB of bitsets. Root cause: dense N² representation. Debug: memory metric per analysis. Signal: analysis.reach.bytes. Recovery: switch to roaring above a node threshold; or compute reachability on demand per query.
  • Stale analysis served. Manifestation: post-rewrite plan uses pre-rewrite critical path. Root cause: cache keyed by a fingerprint not updated after rewrite. Debug: assert analysis fp == current dag fp. Signal: analysis.stale_fp. Recovery: recompute analyses on the rewritten (re-canonicalized) dag; never carry facts across a rewrite without re-canon.
  • Liveness ignores cache reuse. Manifestation: an artifact freed though a cached downstream still needs it. Root cause: liveness computed on logical graph ignoring cache reads. Debug: integration test with cache. Recovery: extend last_use to include cache-consumer edges (P8 integration).

3.7 Performance Concerns

  • Reuse topo order across analyses (compute once).
  • Bitset ops are cache-friendly and vectorizable; align bitsets to 64-bit words.
  • Dominators: use RPO numbering and the "intersect" with doms-array; O(n·d) where d is tree depth — near-linear for shallow DAGs.
  • Analysis cache avoids recompute during iterative search where the dag is unchanged.

3.8 Edge Cases

  • Disconnected components (multiple independent sub-DAGs) → each has its own critical path; overall makespan is the max if resources shared, sum if serialized — analysis reports per-component, scheduler decides.
  • Single node → critical path = its duration; dominates trivially.
  • Wide fan-out then fan-in (map/reduce) → critical path through one representative branch; liveness of the array artifact spans the whole fan-out.
  • Zero-duration nodes (barriers) → critical path unaffected by them except as sync points.
  • Very deep chain → backward pass must not recurse (iterative over reverse topo).

3.9 Failure Analysis

  • What breaks: an incorrect dominator/reachability fact silently misguides a rewrite (e.g., pushdown past a node it shouldn't). Detection: differential rewrite tests (P4) compare optimized vs unoptimized execution. Blast radius: wrong plan → wrong results. Containment: analyses are validated against brute-force references in CI; rewrites that depend on analysis carry their own differential tests. Recovery: disable the dependent rule; fix the analysis. Forensic: dump the analysis facts alongside the failing plan. Postmortem: add brute-force differential coverage for the failing shape.

3.10 Operational Notes

  • Metrics: analysis.{kind}.duration, analysis.cache.hit_ratio, analysis.reach.bytes, analysis.critical_path_len.
  • Tracing: critical-path length and dominator-tree depth as span attributes (operator sees graph shape).
  • Logging: debug-level dump of critical path on explain.
  • Deployment: pure CPU; analysis cache is in-memory, bounded, reset per process.
  • Compatibility: analysis output is internal (not serialized externally); changes are non-breaking. The explain format is versioned (see Compatibility & Versioning).

Phase 4 — Rewrite-Rule Engine and Pattern Matcher

4.1 Objectives

  • Build a pattern matcher over CanonicalDag and a registry of validity-preserving rewrite rules.
  • Implement the core rule families: operator fusion, dead-task elimination (DCE), common-subgraph elimination (CSE), constant/branch folding, predicate pushdown.
  • Greedy fix-point application mode (rules to convergence) as the baseline; e-graph saturation deferred to P6.
  • Constraint (Principle 1): every rule preserves semantics; every rule has a differential test.

4.2 Detailed Implementation Steps

  • dagopt-rewrite/src/pattern.rs: Pattern AST (§11.4, Core Schema). AnyPure/AnyConst wildcards. Patterns compile to a matching automaton keyed by root op for fast candidate lookup (RuleRegistry.by_root_op).
  • dagopt-rewrite/src/matcher.rs: top-down match — for a candidate node, attempt to unify the pattern tree with the subgraph, binding Vars to nodes. Handles shared subgraphs (a Var bound twice must bind the same NodeId). Returns Bindings or none.
  • dagopt-rewrite/src/registry.rs: RuleRegistry holds rules, indexes by root op. register(Rule); rules toggleable via config (enabled) for bisection.
  • dagopt-rewrite/src/apply.rs: greedy driver — worklist of nodes; for each, find applicable rules; apply the first whose guard holds (or, in cost-guided greedy, the one with best cost_delta); rebuild the affected region; re-canonicalize incrementally; loop until no rule applies or a step budget is hit.
  • dagopt-rewrite/src/rules/fusion.rs: Task(f, Task(g, ?x)) with both pure, compatible pools, and f consuming exactly g's output → fused Task(f∘g, ?x). Guard: single-consumer of g's output (else fusion duplicates work). Proof: Algebraic.
  • dagopt-rewrite/src/rules/dce.rs: node with no path to any sink (from reachability) and pure → delete; cascade to now-dead predecessors. Proof: DeadCode.
  • dagopt-rewrite/src/rules/cse.rs: two nodes with equal fp (from canon, I5) and pure → merge: keep one, redirect all consumers of the other, drop the duplicate. Proof: Dedup.
  • dagopt-rewrite/src/rules/fold.rs: Task(f, Const(c)) with f pure and a registered evaluator → Const(f(c)). Branch fold: Map over Const([...]) with known length → fixed fan-out (or single node if length 1). Proof: Fold.
  • dagopt-rewrite/src/rules/pushdown.rs: Filter(p, Task(t, ?x)) where p's columns are produced by ?x (independent of t) and t is row-wise → Task(t, Filter(p, ?x)). Uses dominator/reachability to verify independence. Shrinks the intermediate artifact. Proof: Pushdown.
  • Proof obligations: each rule carries a ProofTag; the differential harness (dagopt-testkit/src/diff_harness.rs) runs the simulated executor on the DAG before and after the rule and asserts equal artifact digests for all sink outputs (I6).
  • Confluence/termination: greedy applies a terminating subset (fusion/DCE/CSE/fold strictly reduce node count or const-ness; pushdown reduces artifact size and is bounded by graph depth). Pushdown guarded against oscillation by a "do not push if already pushed" marker.
  • Observability: rewrite.rule_applied{rule} counter, rewrite.nodes_before/after, span pipeline.rewrite, per-rule timing.
  • Theory anchors: rule registry/extensibility → Volcano (Graefe & McKenna 1993), ADR-11; pattern matcher → BURS/BURG (Fraser/Hanson/Proebsting 1992); confluence/termination of greedy rewrite set → Baader & Nipkow §1–4; validity-preservation proof obligation → P1, I6; CSE via fingerprint → I5, P5; small composable rules + kill switch → P15; fail-closed folding → P13; differential gate → ADR-16.

4.3 Deliverable

  • dagopt plan --mode greedy <file.wdl> produces a rewritten DAG; --explain shows the rule trace (sequence of rules applied with before/after node counts).
  • Library: rewrite_greedy(&CanonicalDag, &RuleRegistry, budget) -> CanonicalDag.

4.4 Acceptance Criteria

  • Each rule, on its targeted fixture, produces the expected transformed DAG (snapshot).
  • Differential harness: 10,000 random DAGs, optimized vs unoptimized execution → identical sink digests (I6). Zero divergences.
  • Greedy reaches a fix-point (no rule applies) on all fixtures within the step budget.
  • CSE on canon_cse.wdl reduces node count by the expected amount.
  • Fusion on a linear pure chain of length k collapses to 1 node.
  • Performance: greedy rewrite ≥ 100k nodes/s on the medium corpus; pattern match candidate lookup O(1) by root op.
  • No rule, when disabled, changes correctness (only cost) — verified by differential test with each rule toggled.

4.5 Conformance Fixtures

  • conformance/rewrites/fusion_chain.{in,out}.wdl — pure chain → single node.
  • conformance/rewrites/dce_unused.{in,out}.wdl — unused branch removed.
  • conformance/rewrites/cse_dup.{in,out}.wdl — duplicate subtree merged.
  • conformance/rewrites/fold_const.{in,out}.wdl — constant subtree folded.
  • conformance/rewrites/pushdown_filter.{in,out}.wdl — filter pushed to source.
  • conformance/rewrites/no_fuse_shared.{in,out}.wdl — fusion correctly NOT applied (shared consumer).
  • conformance/rewrites/malformed_impure_fold.wdl — fold NOT applied on impure op.
  • Differential corpus: conformance/rewrites/diff_corpus/*.wdl for the property harness.

4.6 Pitfalls

  • Fusing a multiply-consumed node. Manifestation: work duplicated, cost increases or results diverge if op non-idempotent. Root cause: fusion guard missing single-consumer check. Debug: differential test on no_fuse_shared. Signal: rewrite.nodes_after > before after fusion. Recovery: guard fusion on out-degree 1.
  • CSE merging impure nodes. Manifestation: two side-effecting tasks collapsed to one, side effects lost. Root cause: dedup ignoring pure. Debug: differential test with side-effect-tracking sim executor. Signal: rewrite.semantic_div{cse}. Recovery: require pure for CSE (I6).
  • Pushdown past a dependent node. Manifestation: filter evaluated before the column it needs exists. Root cause: independence check wrong. Debug: reachability-based independence test; differential. Signal: divergence. Recovery: verify filter columns produced strictly upstream of the pushdown target.
  • Greedy oscillation / non-termination. Manifestation: rewrite loops forever (push down then a fusion pushes back). Root cause: two rules with inverse effects. Debug: step counter + cycle detection on dag fps. Signal: rewrite.budget_exhausted, repeated fps. Recovery: terminating subset for greedy; oscillating pairs only allowed under saturation (P6) with cost-based extraction.
  • Pattern match exponential on shared subgraphs. Manifestation: matcher revisits a shared node many times. Root cause: tree matching over a DAG. Debug: match-attempts metric. Signal: rewrite.match_attempts superlinear. Recovery: memoize match results by (rule, node).
  • Const folding diverging from executor. Manifestation: folded constant differs from what the executor would compute (FP, rounding). Root cause: a folding evaluator not bit-identical to the executor's op. Debug: differential per folded op. Recovery: only fold ops with a certified bit-identical evaluator; otherwise skip (fail closed, Principle 13).

4.7 Performance Concerns

  • Candidate lookup by root op avoids scanning all rules per node.
  • Memoize (rule, node) -> matched? to avoid re-matching unchanged regions across greedy iterations.
  • Incremental re-canonicalization: only re-fingerprint the changed region and its ancestors, not the whole graph.
  • Rule application allocates new nodes; use the arena interner and Arc sharing of unchanged tails.
  • Pushdown can shrink intermediate artifacts dramatically — the biggest single-rule win for cost; prioritize it in greedy.

4.8 Edge Cases

  • Rewrite that empties the graph (everything dead) → must still leave required sinks; DCE never removes a sink or a node feeding a live sink.
  • Self-fusion (a node whose output feeds its own fusion candidate) — impossible in a DAG, but guarded.
  • Const fold producing a huge constant (folding a 1 GB array) → guard fold by result size estimate; skip if it materializes a large artifact (cost regression).
  • Pushdown through a Map (fan-out) → push into each branch; verify the filter is element-wise.
  • Two CSE candidates that are each other's duplicates → merge once (canonical winner = lowest canonical NodeId).
  • Rule applied to a node that a concurrent rule removed → in parallel mode, detect via versioned node generation; skip stale.

4.9 Failure Analysis

  • What breaks: a buggy rule changes results (I6 violation) — the highest-severity failure (silent wrong answers). Detection: differential harness in CI on every commit; production differential sampling (run a fraction of plans both optimized and unoptimized, compare digests). Blast radius: every workflow using that op pattern. Containment: per-rule kill switch (enabled=false via config) disables the rule fleet-wide without redeploy. Recovery: disable rule, alarm, bisect with the replay log (re-run captured plans with the rule off). Forensic: the rule trace in explain plus the minimized failing DAG (delta-debugging). Postmortem: add the minimized DAG to the differential corpus permanently.

4.10 Operational Notes

  • Metrics: rewrite.rule_applied{rule}, rewrite.nodes_before, rewrite.nodes_after, rewrite.reduction_ratio, rewrite.duration, rewrite.semantic_div{rule} (must be 0).
  • Tracing: span per rule batch; the rule trace is attached to the plan for explain/diff.
  • Logging: warn on any semantic_div; info on large reductions.
  • Deployment: rules ship with the binary; the enabled set is config (hot-reloadable in the service) so a bad rule is disabled without redeploy.
  • Rollback: disabling a rule is config-only; a plan-diff before/after disabling shows the cost impact.
  • Compatibility: rule-set is hashed into the replay log; replaying a plan re-applies the same rule-set (I15). Adding a rule is non-breaking (only changes cost), but the rule-set hash changes — replays pin the old hash.

Phase 5 — Cost Model and Statistics

5.1 Objectives

  • Build the cost model: a pluggable StatsProvider, per-node cost estimation, bottom-up cost propagation, and a weighted scalar objective.
  • Provide cardinality/selectivity/size estimation that flows through Map/Reduce/Filter.
  • Declare per-dimension monotonicity so DP pruning (P6) is sound (I8).
  • Constraint: cost is deterministic (Principle 3); estimates are captured per plan for replay.

5.2 Detailed Implementation Steps

  • dagopt-cost/src/stats.rs: the StatsProvider trait (§11.5, Core Schema). Two reference impls: StaticStats (from cost{} hints in WDL-lite and defaults) and HistogramStats (from a captured execution-history table keyed by op fingerprint). The provider is Arc<dyn StatsProvider>.
  • dagopt-cost/src/model.rs: CostModel { stats, weights }. cost_of(dag, node) -> Cost, memoized by node fp in an AnalysisCache-style table (same dag fp ⇒ same costs).
  • dagopt-cost/src/propagate.rs: bottom-up over topo order. Leaf (Source) cost from stats. Task cost = own cost (from stats given input sizes) combined with children. Size estimation: output size_est = f(op, input sizes, selectivity); Filter multiplies by selectivity; Map multiplies by fanout cardinality; Reduce collapses to a scalar/small artifact.
  • Wall-clock combination: along a path, wall = sum of durations on the critical path; across parallel branches, wall = max; CPU-seconds = sum across all nodes regardless of parallelism. This separation lets the objective trade throughput (cpu) vs latency (wall).
  • dagopt-cost/src/objective.rs: objective(Cost) = w_cpu*cpu + w_wall*wall + w_mem*norm(mem) + w_io*norm(io). Weights are config; default wall-dominant for latency-sensitive workflows. Memory/IO normalized to comparable units.
  • Monotonicity declarations: MonotoneDims { cpu: true, io: true, wall: false, mem: false }. The cost model exposes lower_bound(partial_plan) using only monotone dims for B&B/DP pruning.
  • Confidence/uncertainty: each estimate carries a confidence (from stats sample size); low-confidence estimates widen lower bounds (conservative pruning) to avoid pruning the true optimum.
  • stats_snapshot: the provider serializes its relevant state (fp-keyed estimates touched) into a snapshot stored with the plan for replay (I15).
  • Observability: cost.estimate{op} histograms, cost.objective per plan, span pipeline.cost, cost.monotonicity_violation (must be 0).
  • Theory anchors: cost-based estimation → Selinger 1979, Garcia-Molina ch.16; declared monotonicity for sound pruning → P6, I8 (feeds Phase 6 B&B/DP); deterministic FP compare + tie-break → P3; stats snapshot for replay → P10, I15; fail-closed on missing stats → P13; learned cost model deferred → §5.5 Required Reading (Neo/Bao).

5.3 Deliverable

  • dagopt explain --cost <file.wdl> prints per-node Cost vectors, the critical-path wall estimate, and the plan objective.
  • Library: CostModel::cost_of, objective, lower_bound; pluggable StatsProvider.

5.4 Acceptance Criteria

  • Cost propagation matches hand-computed values on etl.wdl, fanout.wdl, diamond.wdl.
  • Monotonicity contract test: for 10,000 random (subplan, superplan) pairs, monotone dims satisfy cost(sub) ≤ cost(super); report any violation (I8).
  • Selectivity/cardinality flow: a Filter(0.1) followed by agg reduces estimated input size by 10×.
  • Determinism: same dag+stats → identical costs and objective, 1000×.
  • Performance: cost of a 100k-node graph ≤ 20 ms (memoized linear pass); lower_bound O(1) per call given memoized node costs.
  • Pruning soundness: on graphs with a known optimum, B&B/DP using lower_bound never prunes the optimum (verified in P6 acceptance).

5.5 Conformance Fixtures

  • conformance/plans/cost_etl.golden — per-node and plan cost.
  • conformance/plans/cost_fanout.golden — fan-out cardinality flow.
  • conformance/plans/cost_selectivity.golden — filter shrinks downstream size.
  • conformance/plans/cost_monotone.golden — monotone-dimension assertions.
  • conformance/plans/cost_lowconfidence.golden — widened bounds under low sample size.
  • Deferred: learned cost model — PhaseDeferred("FINAL_BLUEPRINT §5.5 Required Reading") (Neo/Bao reading in §5.5 Required Reading, distinct from this subsection's own number).

5.6 Pitfalls

  • Non-monotone dim used for pruning. Manifestation: B&B prunes the optimal plan; result is suboptimal but looks correct. Root cause: lower_bound includes wall/mem. Debug: pruning-soundness test on known-optimum graphs. Signal: search.optimum_pruned (test-only). Recovery: bound only on cpu/io (declared monotone).
  • Selectivity compounding error. Manifestation: deep pipelines estimate near-zero size, mis-rank plans. Root cause: multiplying many <1 selectivities without a floor. Debug: compare estimated vs simulated sizes. Recovery: floor estimates, track confidence, widen bounds when compounded.
  • Stats provider non-determinism. Manifestation: same DAG yields different plans across runs. Root cause: provider reads wall clock / live metrics. Debug: determinism test. Signal: cost.nondeterministic. Recovery: snapshot stats at plan start; the provider must be a pure function of the snapshot.
  • FP nondeterminism across platforms. Manifestation: x86 vs ARM choose different plans. Root cause: floating-point objective compared without epsilon. Debug: cross-arch golden. Recovery: compare objectives with a fixed epsilon and a deterministic tie-break (fingerprint).
  • Cost memo not invalidated on stats change. Manifestation: stale costs after a stats refresh. Root cause: memo keyed only by dag fp, not stats fp. Debug: change stats, assert recompute. Recovery: key cost memo by (dag_fp, stats_snapshot_fp).

5.7 Performance Concerns

  • Cost propagation reuses topo order; one linear pass, memoized by fp so unchanged subgraphs are not re-estimated across search iterations.
  • Cost is a small Copy struct (4 fields) — combine ops are branch-free arithmetic.
  • Stats lookups can be the bottleneck if the provider hits a remote store; the snapshot pre-fetches and caches all needed estimates once.
  • Objective is a dot product — vectorizable; computed once per candidate plan in search.

5.8 Edge Cases

  • Missing stats for an op → conservative default with low confidence; logged cost.stat_missing{op}; never crash (fail closed).
  • Zero-size input → downstream sizes floor at a minimum (avoid divide-by-zero in per-byte rates).
  • Huge fan-out (cardinality 10^9) → cost saturates to a cap (avoid overflow); flagged as a cost outlier.
  • Negative/NaN stats from a buggy provider → rejected at the provider boundary (StatsError), plan fails closed.
  • Cyclic stat dependency (cost depends on a downstream estimate) → forbidden; cost is strictly bottom-up.

5.9 Failure Analysis

  • What breaks: a mis-calibrated cost model chooses a worse plan (correct but slow). Detection: production plan-cost vs actual-runtime divergence metric (cost.estimate_error); alerts when estimates systematically mispredict. Blast radius: performance, not correctness — degraded throughput/latency. Containment: weights and provider are config; can revert to StaticStats. Recovery: recalibrate from execution history; the differential of estimated vs actual feeds the (deferred) learned model. Forensic: the stats_snapshot in the replay log reproduces the exact decision. Postmortem: add the mispredicted shape to a calibration corpus.

5.10 Operational Notes

  • Metrics: cost.objective, cost.estimate{op,dim}, cost.estimate_error (vs actual), cost.stat_missing{op}, cost.monotonicity_violation.
  • Tracing: plan objective and dominant cost dimension as span attributes.
  • Logging: warn on missing stats and on large estimate errors post-execution.
  • Deployment: stats provider is pluggable; StaticStats needs no external dependency; HistogramStats reads a snapshot file.
  • Migration: stats snapshot format is versioned; old snapshots replay under their captured version.
  • Compatibility: changing weights changes plans but not the wire/IR; document weight changes as operational (not API) changes.

Phase 6 — Cost-Based Search and Plan Extraction

6.1 Objectives

  • Explore the space of equivalent plans and select the minimum-objective plan under budgets.
  • Implement four strategies: greedy fix-point (P4 reuse), memoized dynamic programming (System-R/Cascades-style), branch-and-bound (cost-lower-bound pruning), and e-graph equivalence saturation + extraction.
  • Bound every search (Principle 4): node/time/memory budgets; on breach, return best-so-far flagged suboptimal.
  • Constraint: search is deterministic given seed (I3); extraction is reproducible.

6.2 Detailed Implementation Steps

  • dagopt-search/src/memo.rs: MemoTable { DashMap<Fp,(Plan,Cost)> } — best known plan per subgraph fingerprint. Keyed by (dag_fp, stats_snapshot_fp). The DP/Cascades "group" abstraction: an equivalence class of plans for a logical subgraph; best member memoized.
  • dagopt-search/src/dp.rs: bottom-up DP over the canonical topo order. For each node, enumerate the rewrite alternatives producing its output (from the rule registry), compute each alternative's cost using already-memoized children costs, keep the min. Optimal within the enumerated alternatives. O(nodes × alternatives × children).
  • dagopt-search/src/bnb.rs: branch-and-bound for the global plan when alternatives interact (e.g., shared-subexpression placement). Maintains best-so-far cost; prunes a partial plan when lower_bound(partial) ≥ best (uses monotone dims only, I8). Node order seeded for determinism. Node budget caps exploration.
  • dagopt-search/src/egraph.rs: the e-graph (§11.6, Core Schema). add(enode) -> EClassId (hash-cons via memo), union(a,b) merges classes (union-find), rebuild() restores the congruence invariant (egg-style deferred rebuild). Rules from P4 are applied non-destructively: a match adds the rewritten subgraph and unions it with the matched class. Saturation = apply all rules until no new unions (or budget).
  • dagopt-search/src/extract.rs: from a saturated e-graph, pick the min-cost representative per class bottom-up: best[class] = argmin over enodes of (own_cost + Σ best[child]). Greedy extraction is optimal for tree-shaped costs; for shared subexpressions, an ILP-lite pass (or the greedy with common-subexpr discount) handles reuse. Output Plan (IR3).
  • dagopt-search/src/lib.rs: search(&CanonicalDag, &RuleRegistry, &CostModel, SearchConfig) -> SearchResult. Dispatches by mode. Enforces budgets via a Budget guard checked in the hot loop; on breach returns best-so-far with suboptimal=true.
  • Equivalence classes ensure phase-ordering independence: unlike greedy (P4), saturation represents all rewrite orders, so the extracted plan is not biased by application order.
  • Determinism: e-class iteration uses sorted class IDs; union-find merges deterministically (lower ID wins); extraction ties broken by fingerprint.
  • Observability: search.enodes, search.eclasses, search.iterations, search.pruned, search.suboptimal, search.objective_chosen, span pipeline.search with mode attribute.
  • Theory anchors: memoized DP groups → Selinger 1979, Cascades (Graefe 1995); e-graph + deferred rebuild → egg (Willsey 2021), ADR-11; saturation equational-theory grounding → Baader & Nipkow §6; saturation beats phase-ordering → Equality Saturation (Tate 2009); sound pruning on monotone dims → I8, P6; bounded search + suboptimal fallback → P4; ILP-lite extraction → ADR-29; deterministic extraction → P3, I3; equivalence preserved → I7.

6.3 Deliverable

  • dagopt plan --mode {greedy|dp|bnb|saturate} <file.wdl> produces the optimized plan; --explain shows alternatives considered and why the winner was chosen (objective comparison).
  • Library: search(...) -> SearchResult { plan, cost, suboptimal, stats }.

6.4 Acceptance Criteria

  • On graphs with a known optimum, DP and saturation return the optimum; greedy returns within a documented factor; B&B returns the optimum within budget.
  • Pruning soundness (with P5): B&B/DP never prune the true optimum (verified on enumerable small graphs by comparing to exhaustive search).
  • Saturation reaches a fix-point on bounded rule sets; on unbounded sets, terminates at budget with suboptimal correctly set.
  • Determinism: 1000× runs with the same seed → identical chosen plan (byte-identical IR3).
  • Performance (N=1k): DP p50 ≤ 120 ms; saturation p50 ≤ 600 ms (budgeted); greedy ≤ 15 ms (per §4 constraints).
  • Memory: e-graph ≤ node_budget e-nodes; abort + greedy fallback beyond 2M e-nodes.
  • Differential: optimized plan executes to identical sink digests as the unoptimized DAG (I7), 10,000 random graphs.

6.5 Conformance Fixtures

  • conformance/plans/search_known_opt.{wdl,golden} — small graph with hand-derived optimum.
  • conformance/plans/search_phase_order.wdl — greedy and saturation diverge (saturation finds better plan); golden documents both.
  • conformance/plans/search_shared_subexpr.wdl — extraction must reuse a shared subexpression.
  • conformance/plans/search_budget_breach.wdl — pathological graph forcing suboptimal=true fallback.
  • conformance/plans/search_determinism.golden — fixed-seed chosen plan.
  • Regression: search_regress_* for each pruning/extraction bug.

6.6 Pitfalls

  • E-graph rebuild missed. Manifestation: extraction picks a non-canonical or stale node; equal subexpressions not merged. Root cause: forgetting rebuild() after unions. Debug: invariant check that the memo is congruent post-rebuild. Signal: search.congruence_violation. Recovery: deferred rebuild after each saturation round (egg pattern).
  • Extraction loops on cyclic e-graph. Manifestation: extraction recurses forever. Root cause: a rewrite created a self-referential e-class (a class containing a node whose child is itself). Debug: cycle check in extraction. Signal: search.extract_cycle. Recovery: detect via visited set; break ties to a non-cyclic representative; cyclic classes indicate an invalid rule (alarm).
  • DP enumerates exponential alternatives. Manifestation: DP time explodes on graphs with many local rewrites. Root cause: cartesian product of per-node alternatives. Debug: search.alternatives metric. Recovery: cap alternatives per node; fall back to greedy beyond a threshold; this is why saturation (shared structure) scales better than naive DP.
  • B&B never prunes (loose bound). Manifestation: B&B degenerates to exhaustive search. Root cause: lower_bound too loose (e.g., 0). Debug: search.pruned ratio near 0. Recovery: tighten the monotone lower bound; use the cheapest-alternative-per-node sum as a bound.
  • Pruning the optimum (tight-but-wrong bound). Manifestation: returns suboptimal silently. Root cause: lower bound exceeds true cost (unsound). Debug: pruning-soundness test. Signal: search.optimum_pruned. Recovery: prove the bound is a true lower bound; use only monotone dims; widen by confidence (P5).
  • Nondeterministic extraction. Manifestation: plan-diff noisy though inputs unchanged. Root cause: e-class iteration in hash order. Debug: determinism golden. Recovery: sort by class ID/fingerprint everywhere.

6.7 Performance Concerns

  • Hash-consing (add via memo) deduplicates e-nodes — the main memory control.
  • Deferred rebuild batches congruence restoration — avoids O(n²) eager maintenance.
  • Memo table is the contention point under parallel saturation; shard it (dashmap) and keep critical sections tiny.
  • Extraction is bottom-up over classes; memoize best[class]; for shared subexprs, a single ILP-lite pass over the extracted DAG handles reuse discounts.
  • Budget checks must be cheap (atomic counter, checked every K iterations, not every node).

6.8 Edge Cases

  • No rewrite applies (already optimal) → search returns the input plan unchanged, suboptimal=false.
  • All plans equal cost → deterministic tie-break by fingerprint; plan-diff stable.
  • Single-node graph → trivial; no enumeration.
  • Extremely wide graph (10^6 parallel branches) → saturation memory dominated by branches; budget triggers greedy fallback.
  • Rewrite explosion (a rule that always applies, e.g., add identity) → saturation budget caps; such rules are flagged non-terminating and excluded from greedy.
  • Conflicting equivalent plans with different observable side effects → impossible (CSE/fusion require pure); a rule producing such is rejected by differential testing (P4).

6.9 Failure Analysis

  • What breaks: extraction returns a plan not equivalent to the input (I7 violation). Detection: differential harness; production differential sampling. Blast radius: wrong results for affected workflows. Containment: switch mode to greedy (no e-graph) via config; the bug is isolated to saturation/extraction. Recovery: replay the captured plan inputs, reproduce, minimize the DAG, fix the rule or extraction. Forensic: dump the e-graph (e-classes + unions) and the extraction trace. Postmortem: add the minimized case to the differential corpus and an extraction unit test.

6.10 Operational Notes

  • Metrics: search.mode, search.enodes, search.eclasses, search.iterations, search.pruned_ratio, search.suboptimal_total, search.objective_chosen, search.duration{mode}, search.budget_breach{kind}.
  • Tracing: span attributes — mode, e-graph size, iterations, whether budget hit. The alternatives-considered set is attached for explain.
  • Logging: warn on suboptimal=true (operator should know a budget was hit); info on large e-graphs.
  • Deployment: default mode is config (greedy for latency-critical, saturate for batch). Budgets tuned per deployment.
  • Rollback: mode and budgets are config; revert to greedy disables the e-graph entirely.
  • Compatibility: search is internal; chosen plan is IR3 → emitted via the versioned wire (P9). The rule-set + cost weights + seed are recorded for replay (I15).

Phase 7 — Resource-Aware Scheduling and Placement

7.1 Objectives

  • Layer the second optimization problem onto the optimized plan (IR3): assign each task a start time and a resource pool, minimizing makespan subject to precedence, capacity, concurrency, and affinity constraints. Output IR4.
  • Implement critical-path list scheduling + bin-packing onto resource pools.
  • Validate the schedule (I9 precedence, I10 capacity).
  • Constraint: scheduling is deterministic (ties broken by critical-path then fingerprint) and bounded.

7.2 Detailed Implementation Steps

  • dagopt-sched/src/pools.rs: Pool (cpu/mem/io/concurrency) and runtime ResourcePool tracking remaining capacity over a timeline (event-driven, not discretized: a min-heap of resource-release events).
  • dagopt-sched/src/listsched.rs: list scheduling — priority queue of ready tasks (all inputs scheduled) keyed by critical-path length (from P3 analysis), tie-broken by fingerprint (determinism). Pop highest priority, assign to the earliest-available compatible pool slot; advance the timeline by processing release events; admit newly-ready tasks. This is the classic Adam/Chandy/Dickson critical-path list schedule; HEFT-style for heterogeneous pools.
  • dagopt-sched/src/binpack.rs: when multiple pools can host a task, choose to minimize makespan: prefer the pool that frees soonest and fits cpu/mem; ties by lowest pool ID. First-fit-decreasing on memory for batchable tasks.
  • dagopt-sched/src/affinity.rs: tasks with pool= pin to that pool (hard affinity); unpinned tasks float. Soft affinity (co-locate tasks sharing a large input artifact to avoid transfer) is a tie-breaker.
  • dagopt-sched/src/validate.rs: post-schedule validation — every task starts ≥ max(end of predecessors) (I9); at every instant, per-pool concurrent tasks ≤ concurrency and Σcpu ≤ cpu, Σmem ≤ mem (I10). Implemented by sweeping the timeline events.
  • Makespan computation: makespan = max(end) across all tasks. Slack-aware: tasks with positive slack can be delayed to reduce peak resource usage without extending makespan.
  • Concurrency limits: pool concurrency caps simultaneous tasks regardless of cpu fit (models executor parallelism limits).
  • Determinism: the ready-queue order and pool-selection tie-breaks are total orders; no wall clock, no randomness.
  • Deferred: speculative/duplicate execution for stragglers — PhaseDeferred("FINAL_BLUEPRINT §7.9"); multi-tenant fair-share — PhaseDeferred("FINAL_BLUEPRINT §7.10").
  • Observability: sched.makespan, sched.pool_utilization{pool}, sched.peak_concurrency{pool}, sched.precedence_violation (0), sched.capacity_violation (0), span pipeline.schedule.
  • Theory anchors: critical-path list scheduling → Adam/Chandy/Dickson 1974; heterogeneous pools → HEFT (Topcuoglu 2002); bin-packing/RCPSP → Pinedo ch.4–6,10; precedence/capacity validation → I9, I10; logical/physical/schedule separation → P2; deterministic tie-breaks → P3; bounded scheduling → P4; straggler/fair-share deferred → §7.9, §7.10.

7.3 Deliverable

  • dagopt plan <file.wdl> now emits a ScheduledDag (IR4) with a ScheduleTable; dagopt explain --schedule prints per-task start/end/pool and a Gantt-style ASCII timeline.
  • Library: schedule(&Plan, &[Pool], SchedConfig) -> Result<ScheduledDag, SchedError>.

7.4 Acceptance Criteria

  • Schedule validates: 0 precedence violations, 0 capacity violations on all fixtures (I9, I10).
  • Makespan within a documented factor of the critical-path lower bound (list scheduling is ≤ 2× optimal for identical machines; tighter for our priority).
  • On fanout.wdl with concurrency=4, exactly ≤4 tasks run simultaneously.
  • Determinism: 1000× → identical schedule.
  • Performance: scheduling ≥ 200k tasks/s; event-driven timeline avoids O(time) discretization.
  • Resource respect: no pool exceeds cpu/mem/concurrency at any instant (timeline sweep proves it).

7.5 Conformance Fixtures

  • conformance/schedules/sched_linear.golden — serial chain, makespan = sum.
  • conformance/schedules/sched_fanout_concurrency.golden — fan-out capped by concurrency.
  • conformance/schedules/sched_affinity.golden — pinned tasks honor pool.
  • conformance/schedules/sched_binpack.golden — multiple pools, makespan-minimizing placement.
  • conformance/schedules/sched_capacity_tight.golden — cpu/mem-constrained packing.
  • conformance/schedules/malformed_infeasible.wdl — task needs more cpu than any pool → Infeasible.
  • Regression: sched_regress_*.

7.6 Pitfalls

  • Priority inversion via wrong critical path. Manifestation: a long-pole task scheduled late, makespan balloons. Root cause: stale/incorrect critical-path length. Debug: compare makespan to critical-path lower bound; alarm if far off. Signal: sched.makespan_ratio. Recovery: recompute critical path on IR3 (post-rewrite), not IR2.
  • Capacity check off-by-one at boundaries. Manifestation: brief oversubscription at task start/end ticks. Root cause: open vs closed intervals at the timeline event. Debug: timeline sweep with strict interval semantics; property test. Signal: sched.capacity_violation. Recovery: half-open intervals [start, end); release before admit at the same instant.
  • Bin-packing thrash. Manifestation: tasks scattered across pools, large artifact transfers. Root cause: ignoring soft affinity. Debug: transfer-bytes metric. Recovery: tie-break placement by co-location with the largest input's producer pool.
  • Concurrency limit ignored under cpu headroom. Manifestation: more tasks run than the executor can handle. Root cause: admitting on cpu fit alone. Debug: peak-concurrency metric vs limit. Signal: sched.peak_concurrency > limit. Recovery: gate admission on both cpu/mem AND concurrency count.
  • Infeasible task not detected early. Manifestation: scheduler loops or stalls when a task fits no pool. Root cause: no feasibility pre-check. Debug: pre-scan tasks vs max pool capacity. Signal: sched.infeasible. Recovery: pre-validate feasibility, return SchedError::Infeasible with the offending task.
  • Slack mis-used, makespan extended. Manifestation: delaying a task to reduce peak memory pushes a successor past the makespan. Root cause: delaying a zero-slack (critical) task. Debug: assert delayed tasks have slack ≥ delay. Recovery: only delay tasks with sufficient slack.

7.7 Performance Concerns

  • Event-driven timeline (heap of release events) is O(n log n), not O(timeline length) — essential for long-running plans.
  • Ready-queue is a binary heap keyed by critical path; pops are O(log n).
  • Pool selection scans compatible pools (small constant); cache per-task compatible-pool lists.
  • Capacity tracking uses incremental counters updated at events, not recomputed per task.
  • Determinism tie-breaks add a fingerprint comparison — cheap (32-byte compare, usually decided in first bytes).

7.8 Edge Cases

  • Single pool, concurrency 1 → fully serial schedule = topo order.
  • Task larger than any pool → Infeasible (pre-checked).
  • All tasks pinned to one pool → bin-packing degenerates to that pool's capacity; makespan may exceed critical path (resource-bound, not dependency-bound).
  • Zero-duration barriers → scheduled at the instant their predecessors finish; no resource use.
  • Massive fan-out exceeding concurrency by 1000× → tasks queue; makespan = (fanout/concurrency) × task duration.
  • Equal-priority ready tasks → fingerprint tie-break, total order, deterministic.
  • Empty schedule (only sources/sinks, no tasks) → makespan 0.

7.9 Failure Analysis

  • What breaks: a schedule violates precedence (I9) — a task is told to start before its inputs exist, causing executor errors or wrong results. Detection: post-schedule validation sweep (mandatory, fails the plan); production executor reports "input missing". Blast radius: the affected workflow run. Containment: validation rejects the plan before emission (fail closed). Recovery: re-schedule; the bug is in the scheduler, isolated from the optimizer. Forensic: the schedule table + the violating (predecessor, successor) pair. Postmortem: add the shape to schedule conformance. Deferred straggler mitigation (§7.9) would add duplicate execution; not in Phase 0.

7.10 Operational Notes

  • Metrics: sched.makespan, sched.makespan_ratio (vs critical path), sched.pool_utilization{pool}, sched.peak_concurrency{pool}, sched.duration, sched.infeasible_total.
  • Tracing: makespan and per-pool utilization as span attributes; the Gantt is attached for explain.
  • Logging: warn on makespan far above critical path (resource-bound) and on infeasible tasks.
  • Deployment: pool definitions come from the request/config (mirroring the executor's real resources); a stale pool config produces a schedule the executor can't honor — keep pool config synced with executor capacity.
  • Rollback: scheduling parameters (affinity weight, packing strategy) are config.
  • Compatibility: ScheduleTable is part of the emitted ExecPlan (versioned, P9). Multi-tenant fair-share (§7.10) is deferred and would add per-tenant quotas.

Phase 8 — Caching, Memoization, and Incremental Re-Planning

8.1 Objectives

  • Content-addressed result cache keyed by task fingerprint: a pure task whose fingerprint matches a stored result reuses the result (CACHED state) instead of being scheduled.
  • Incremental re-planning: when a workflow changes, re-plan only the affected region (change propagation from changed nodes to sinks), reusing cached results and prior analysis for the unchanged region.
  • Constraint (Principle 5, 12): cache is content-addressed, crash-consistent, append-only; same key ⇒ same result (I13).

8.2 Detailed Implementation Steps

  • dagopt-cache/src/digest.rs: result digest = the task fingerprint (Fp from canon) — the same content-address that drives CSE. Cache key = (fp_version, task_fp); value = result_digest (a hash of the produced artifact bytes) + metadata (size, produced-at, cost-actual).
  • dagopt-cache/src/store.rs: a local content-addressed directory store: lookup(key) -> Option<ResultRef>, insert(key, result_ref). Sharded by key prefix into subdirectories. Optional remote backend behind a trait (PhaseDeferred("FINAL_BLUEPRINT Phase 8 §8.9") for cross-DAG global sharing).
  • dagopt-cache/src/incremental.rs: replan(old: ScheduledDag, new: CanonicalDag) -> ScheduledDag. Diff old vs new by fingerprint: nodes with unchanged fp and a cache hit are reusable; the "dirty set" = nodes whose fp changed plus their transitive successors (change propagation via reachability, P3). Only the dirty set is re-optimized and re-scheduled; the clean prefix's plan and analysis are reused.
  • Cache-aware planning: during search/scheduling, a node with a cache hit has near-zero cost (just the read) and is placed in CACHED state, removed from the schedule's compute load. This couples Phase 6 cost model (cache hit → near-zero objective) and Phase 7 scheduling (cached task not scheduled onto compute resources).
  • dagopt-cache/src/gc.rs: mark-and-sweep GC over the content store; reachability roots = recent plans' result refs (from the replay log). Unreferenced results older than a TTL are collected. GC is concurrent with planning (reads tolerate missing entries → cache miss).
  • Crash consistency: cache writes are write-to-temp + atomic rename (POSIX rename atomicity); a torn write leaves a temp file ignored by lookup. No in-place mutation (Principle 12).
  • Liveness integration (P3): an artifact consumed only by a cached downstream is still "live" for the cache read; liveness extended to include cache-consumer edges (the P3 pitfall).
  • Observability: cache.hit_ratio, cache.size_bytes, cache.gc_collected, cache.key_result_skew (must be 0), incremental.dirty_nodes, incremental.reused_nodes, span pipeline.cache.
  • Theory anchors: content-addressed result cache → Bazel action cache, CacheLib (Berg 2020), P5; rebuild/incremental strategy → Build Systems à la Carte (Mokhov 2018), Kineograph (Cheng 2012); dirty-set via reachability → Phase 3, I13; lineage reuse → Spark RDD (Zaharia 2012); crash-only atomic-rename store → P12; key→result soundness → I13; pure-only caching → P1, I6.

8.3 Deliverable

  • dagopt plan --cache <dir> <file.wdl> reuses cached results; dagopt replan --old <plan> <new.wdl> re-plans incrementally and reports reused vs recomputed nodes.
  • Library: ResultCache::lookup/insert, incremental::replan.

8.4 Acceptance Criteria

  • Cache hit reuse: a re-plan of an unchanged workflow with a warm cache schedules 0 compute tasks (all cached); verified.
  • Incremental: changing one leaf task re-plans only that task and its successors (dirty-set size matches expectation); the clean prefix is reused byte-identically.
  • Key→result soundness (I13): a fixture asserts the same fingerprint always maps to the same result; a deliberate skew is detected and rejected.
  • Crash consistency: kill the process mid-insert (fault injection); on restart, lookup returns either the old value or a miss, never a torn value.
  • Performance: cache lookup ≤ 50 µs (local FS, hot dir cache); incremental re-plan cost ∝ dirty-set size, not total graph size.
  • GC: collects unreferenced results; never collects a result referenced by a retained plan (verified).

8.5 Conformance Fixtures

  • conformance/plans/cache_full_reuse.golden — warm cache → 0 compute tasks.
  • conformance/plans/cache_partial.golden — one node changed → partial reuse.
  • conformance/plans/incremental_dirty_set.golden — dirty-set computation for a leaf change.
  • conformance/plans/cache_key_skew.fixture — deliberate key/result mismatch → KeyResultSkew.
  • conformance/plans/cache_torn_write.fixture — simulated torn write → miss, not corruption.
  • Compat: conformance/plans/cache_fpv_bump.golden — fp_version bump → cache miss (namespaced).

8.6 Pitfalls

  • Caching an impure task's result. Manifestation: stale/incorrect result reused for a task with side effects or nondeterministic output. Root cause: caching ignored pure. Debug: only pure tasks are cacheable; differential test. Signal: cache.impure_insert. Recovery: gate insert/lookup on pure (mirrors CSE gate, I6/I13).
  • Fingerprint not capturing an input that affects output. Manifestation: two different computations share a cache key, wrong reuse. Root cause: an input (e.g., an external param) omitted from the fingerprint. Debug: differential (cache vs recompute). Signal: cache.key_result_skew. Recovery: ensure the fingerprint covers all output-determining inputs; treat external params as fingerprint inputs.
  • GC races a planner read. Manifestation: a planner reads a result the GC just collected → spurious miss or error. Root cause: GC and read unsynchronized. Debug: stress test GC during planning. Signal: cache.gc_race. Recovery: reads tolerate missing entries as a miss (recompute); GC only collects entries older than the longest plan duration.
  • Torn write served as valid. Manifestation: a partial result file read as complete → corruption. Root cause: writing in place. Debug: fault injection mid-write. Signal: cache.corrupt. Recovery: temp-file + atomic rename; verify result digest on read.
  • Incremental dirty-set too small. Manifestation: a transitively-affected node not re-planned, stale plan used. Root cause: change propagation missed an edge. Debug: differential incremental vs full re-plan (must produce identical plans). Signal: incremental.divergence. Recovery: dirty set = changed nodes ∪ all reachable successors (P3 reachability); never narrower.
  • Cache namespace not bumped on fp_version. Manifestation: results from an old fingerprint algorithm served against new keys. Root cause: key = raw fp. Debug: bump fp_version in a test, assert cache miss. Recovery: key includes fp_version (I5; see Phase 2 §2.6 fp_version pitfall).

8.7 Performance Concerns

  • Content-addressed dedup keeps amplification ≤ 1.2× (identical results stored once).
  • Lookup hot path is a hash + FS stat; keep the directory shallow-sharded to avoid huge dirs.
  • Incremental re-plan reuses prior analysis (P3 cache) and prior plan for the clean region — cost proportional to change size, the key scalability win for iterative workflows.
  • GC is background, rate-limited; mark phase uses the replay log's recent roots (bounded).
  • Result digest verification on read adds a hash; amortized by the avoided recompute.

8.8 Edge Cases

  • First run (cold cache) → all misses; full plan; results inserted.
  • Concurrent inserts of the same key → idempotent (same content); last writer wins, identical bytes.
  • Cache full / disk pressure → GC triggered; if still full, inserts fail gracefully (treated as "not cached", recompute next time).
  • A changed pool/resource but unchanged task fingerprints → tasks reusable from cache, but the schedule changes; incremental re-plan re-schedules without recompute.
  • Non-deterministic op marked pure by mistake → caught by differential testing (cache vs recompute diverge); reject marking.
  • Very large result (multi-GB artifact) → stored by reference (digest + external blob); cache holds metadata, not bytes, above a size threshold.

8.9 Failure Analysis

  • What breaks: cache returns a wrong result for a key (I13 violation) — silent wrong answers. Detection: production differential sampling (recompute a fraction, compare to cache); cache.key_result_skew. Blast radius: every workflow hitting that key. Containment: a global cache-disable flag (plan as if cold) isolates the cache instantly. Recovery: invalidate the offending key (or the whole namespace), recompute, find the omitted fingerprint input. Forensic: the key, both results, and the producing plans (from replay log). Postmortem: add the input to the fingerprint, add a regression fixture. Cross-DAG global cache sharing (this subsection, Phase 8 §8.9) is deferred — it would widen blast radius and is gated.

8.10 Operational Notes

  • Metrics: cache.hit_ratio, cache.size_bytes, cache.entries, cache.gc_collected, cache.corrupt, incremental.dirty_nodes, incremental.reused_ratio.
  • Tracing: cache hit/miss per task as span events; reuse ratio per re-plan.
  • Logging: warn on corruption, skew, GC pressure; info on large reuse.
  • Deployment: cache directory is operator-managed storage; size/TTL/GC-rate are config. A remote cache backend is a deferred interface.
  • Backup/restore: the cache is regenerable (recompute) — not backed up; the replay log (P11) is backed up. Losing the cache costs recompute, not correctness.
  • Migration: fp_version bumps namespace the cache; old namespace GC'd after a grace period.
  • Compatibility: cache format is versioned; readers handle their own version; cross-version reads miss (safe).

Phase 9 — Execution-Plan Emission, Executor Interface, Backpressure

9.1 Objectives

  • Serialize the scheduled plan (IR4) to a stable ExecPlan wire format and define the Executor interface the optimizer hands off to.
  • Implement backpressure: the emitter admits tasks to the executor only within a bounded token budget (I12).
  • Stand up dagopt-svc: the gRPC planning service exposing Plan/Explain/Diff.
  • Constraint (Principle 8, 11): bounded outstanding work; versioned, round-trippable wire (I11).

9.2 Detailed Implementation Steps

  • dagopt-plan/src/physical.rs: ExecPlan/ExecTask (§11.8, Core Schema). ExecTask carries op, params, input result-digests, output artifact IDs, pool, fingerprint — everything the executor needs, nothing more.
  • dagopt-plan/src/wire.rs: CBOR serialization with a leading version: u32 and a fp over the canonical encoding. Round-trip test: deserialize(serialize(p)) == p byte-for-byte (I11).
  • dagopt-plan/src/emit.rs: emit(&ScheduledDag) -> ExecPlan — lowers IR4 to wire form, resolves interned symbols to strings, attaches the schedule table and the stats_snapshot_ref/rule-set hash for replay.
  • dagopt-plan/src/executor.rs: the Executor trait (submit/poll/ack). A driver loop in the emitter walks the schedule in start-time order, submits ready tasks (inputs satisfied) within token budget, polls for completion, on Done(digest) releases the token and admits successors, inserts the result into the cache, on Failed applies retry policy.
  • dagopt-plan/src/backpressure.rs: TokenPool { budget, outstanding: AtomicU32 }. acquire() -> Option<Token> (None when full → emitter waits); release(Token). Budget = min(pool concurrency sum, configured max-in-flight). The executor pulls; the emitter never pushes beyond budget (I12).
  • dagopt-svc/proto/dagopt.proto: service Planner { rpc Plan(PlanRequest) returns (PlanResponse); rpc Explain(...); rpc Diff(...); }. PlanRequest { wdl_or_ir, constraints, stats_snapshot, weights, seed }. PlanResponse { exec_plan, schedule, explain, cost, suboptimal }.
  • dagopt-svc/src/server.rs: tonic server; bounded planning worker pool (= cores); per-request deadline; concurrency limit → backpressure to clients (gRPC RESOURCE_EXHAUSTED when the pool is saturated).
  • dagopt-svc/src/limits.rs: request size limits (max nodes, max payload), planning time/memory budgets per request (Principle 4) → reject pathological DAGs (DOS mitigation, Threat Model).
  • Streaming: plans > 1 MiB streamed in chunks (gRPC server streaming).
  • Observability: emit.plan_bytes, exec.tokens_outstanding, exec.token_overrun (0), svc.requests{status}, svc.queue_depth, svc.reject{reason}, spans pipeline.emit, svc.plan.
  • Theory anchors: executor handoff/DAG exec boundary → Dryad (Isard 2007); canonical CBOR round-trip → ADR-04, I11; backpressure tokens → P8, I12; versioned wire → P11, ADR-05; gRPC service + deadlines → ADR-06 (tonic), ADR-07 (tokio); bounded planning pool / DOS limits → P4 (Threat Model); online re-optimization deferred → §9.9.

9.3 Deliverable

  • dagopt plan <file.wdl> -o plan.cbor writes a portable ExecPlan; dagopt-svc serves Plan over gRPC; the simulated executor (testkit) runs the plan deterministically.
  • Library: emit, Executor trait, TokenPool.

9.4 Acceptance Criteria

  • Wire round-trip (I11): 10,000 random plans serialize/deserialize byte-identically.
  • Backpressure (I12): under a slow simulated executor, outstanding tasks never exceed budget; memory stays bounded.
  • Service: handles concurrent plan requests up to the worker-pool limit; excess requests get RESOURCE_EXHAUSTED (not OOM, not unbounded latency).
  • Deadlines honored: a request exceeding its deadline returns DEADLINE_EXCEEDED, planning aborted, resources freed.
  • Determinism: the same request returns byte-identical ExecPlan (I3).
  • Performance: emit ≤ 5 ms for N=1k; service p99 planning latency per §4 constraints; startup ≤ 1.5 s.

9.5 Conformance Fixtures

  • conformance/plans/exec_etl.cbor.golden — emitted plan for the ETL example.
  • conformance/plans/roundtrip_corpus/*.cbor — round-trip fixtures (I11).
  • conformance/plans/backpressure_slow_exec.fixture — slow executor, bounded outstanding.
  • conformance/plans/svc_overload.fixture — request flood → RESOURCE_EXHAUSTED.

9.6 Pitfalls

  • Token leak. Manifestation: outstanding count drifts up, throughput collapses to 0 (no tokens). Root cause: a path (failure/timeout) that doesn't release the token. Debug: assert tokens released on every terminal task state; token-ledger metric. Signal: exec.tokens_outstanding stuck high. Recovery: RAII token guard (release on drop); release in all terminal branches.
  • Wire version drift. Manifestation: a new field breaks old readers. Root cause: changing the CBOR layout without a version bump or back-compat. Debug: cross-version round-trip test. Signal: plan.version_unsupported. Recovery: additive fields only within a major version; bump major for layout changes; readers handle version ≤ self.
  • Submitting a task before inputs ready. Manifestation: executor error "input missing". Root cause: emitter driver ignored schedule precedence. Debug: assert all input digests present before submit. Signal: executor failure. Recovery: gate submit on input availability (schedule already orders this; double-check at submit).
  • Service unbounded planning pool. Manifestation: a request flood spawns unbounded planners → OOM. Root cause: no admission limit. Debug: load test. Signal: svc.queue_depth unbounded. Recovery: bounded worker pool; reject excess with backpressure (Principle 8).
  • Non-canonical CBOR breaks fp. Manifestation: the same plan serializes to different bytes (map key order), breaking the plan fp and replay. Root cause: non-deterministic CBOR encoding. Debug: round-trip + fp stability test. Recovery: canonical CBOR (sorted keys, definite lengths).
  • Deadline cancels but leaves resources. Manifestation: a cancelled request leaks the planner's memory/threads. Root cause: cancellation not propagated into the search loop. Debug: cancel-under-load test, watch RSS. Recovery: budget guard checks a cancellation token; cooperative cancellation at loop checkpoints.

9.7 Performance Concerns

  • CBOR encoding is linear; canonical encoding adds a key-sort (small).
  • The emitter driver is event-driven (poll on completion), not busy-waiting; use the executor's completion notification.
  • Token accounting is a single atomic — negligible contention.
  • Service worker pool sized to cores; per-request internal parallelism bounded so total threads ≤ 2×cores (avoid oversubscription).
  • Large plans streamed to avoid a single huge allocation/serialization spike.

9.8 Edge Cases

  • Empty plan (no tasks) → valid ExecPlan with empty task list; executor no-ops.
  • All tasks cached → ExecPlan marks them CACHED; executor only reads, no compute.
  • Single task → trivial submit/poll/ack.
  • Executor never returns (hung task) → per-task wall timeout (from §8.5, Domain Model, state machine) → FAILED → retry/abort; token released on timeout.
  • Plan larger than max payload → streamed; if it exceeds the hard max-nodes limit → rejected pre-emit (limits.rs).
  • Client disconnects mid-stream → server aborts, frees resources, releases tokens.
  • Retry storm (many failures) → bounded retries with backoff; circuit-break after a threshold.

9.9 Failure Analysis

  • What breaks: backpressure fails and outstanding tasks grow unbounded → emitter/service OOM (I12 violation). Detection: exec.tokens_outstanding vs budget; RSS alert. Blast radius: the planning process (one service instance); other instances unaffected (stateless). Containment: the token pool is a hard gate; an OOM aborts one instance, the LB routes elsewhere; cache/log uncorrupted (Principle 12). Recovery: restart the instance (≤ 5 s RTO); the in-flight plan is recomputed. Forensic: the token ledger and the slow executor's poll latencies. Postmortem: tune budget, add a slow-executor alert. Online re-optimization mid-run (§9.9) is deferred — Phase 0 emits a static plan; adaptive re-planning would observe execution and re-plan, increasing complexity.

  • Metrics: emit.plan_bytes, exec.tokens_outstanding, exec.token_overrun, exec.task_state{state}, svc.requests{status}, svc.queue_depth, svc.reject{reason}, svc.plan_latency.
  • Tracing: end-to-end span from PlanRequest to PlanResponse, propagated trace context; per-task submit/poll/ack events.
  • Logging: structured per request (request id, node count, latency, suboptimal flag, status).
  • Deployment: dagopt-svc is stateless behind an LB; cache/log are on attached storage. Rolling upgrades supported (wire is versioned).
  • Rollback: deploy the previous image; the wire version is back-compatible so in-flight clients are unaffected.
  • Migration: wire/plan format versioned (see Compatibility & Versioning); a major bump requires clients to upgrade first (read-new-before-write-new).
  • Compatibility: ExecPlan.version is the contract with executors; semver-governed.

Phase 10 — Observability: Explain, Plan-Diff, Metrics, Tracing

10.1 Objectives

  • Make every plan choice explainable: explain renders the pipeline (validation, rewrites applied, alternatives considered, cost comparison, schedule).
  • diff compares two plans (e.g., before/after a rule or stats change) and shows what changed and why.
  • Wire up metrics, tracing spans, and structured logs across all stages into a coherent operator view.

10.2 Detailed Implementation Steps

  • dagopt-obs/src/explain.rs: explain(&PlanArtifacts) -> Explain where PlanArtifacts bundles the per-stage outputs (validation result, rule trace, search alternatives, cost vectors, schedule). Renders as text (human) and structured JSON (machine). Sections: input summary, rewrites applied (rule + before/after), top-K alternatives with objectives, chosen plan, schedule Gantt, cost breakdown.
  • dagopt-obs/src/diff.rs: diff(&Plan, &Plan) -> PlanDiff. Aligns nodes by fingerprint (canon makes this stable). Reports: nodes added/removed, edges changed, rules that differ, cost delta per dimension, makespan delta, which input change (DAG/stats/weights) plausibly caused each difference. Deterministic alignment (Principle 3) → diffs are noise-free when inputs are unchanged.
  • dagopt-obs/src/metrics.rs: registers the metric families used across crates (planning latency histograms per stage, e-graph size, rule-application counts, cache hit ratio, makespan, suboptimal counter). Prometheus exporter.
  • dagopt-obs/src/trace.rs: tracing spans per stage (pipeline.frontend/canon/analysis/rewrite/cost/search/schedule/emit), nested under a root plan span carrying request id and DAG fingerprint; OTLP export.
  • dagopt-obs/src/log.rs: structured JSON logs; one summary line per plan (fingerprints, node counts, rules, objective, makespan, latency, suboptimal); debug logs gated.
  • tools/plan-viz/: renders a plan as ASCII or Graphviz dot for visual inspection (operator tool).
  • Sampling: tracing is head-sampled (configurable rate) to bound overhead; explain is on-demand (not always computed) — computing the full alternatives set is opt-in via a flag to avoid overhead on the hot path.
  • Observability of observability: a metric for explain/diff computation cost; a flag to disable alternatives capture in production.
  • Theory anchors: observability-by-default → P9; deterministic fingerprint-aligned diff → P3, I5; structured spans/metrics → ADR-12 (tracing), ADR-13 (OTLP), ADR-14 (Prometheus); low-cardinality labels → Phase 10 §10.6 (cardinality explosion pitfall); explain off the hot path → P4 (overhead bound).

  • explain output is deterministic for a fixed input (snapshot-tested via insta).

10.6 Pitfalls

  • Non-deterministic explain/diff. Manifestation: diff shows spurious changes between identical plans. Root cause: fingerprint-unstable alignment or hash-ordered output. Debug: identity-diff test. Signal: diff.spurious. Recovery: align by canonical fingerprint; sort all output (Principle 3).
  • Explain captures everything always (overhead). Manifestation: planning latency regresses in production. Root cause: alternatives set computed on the hot path. Debug: latency with/without explain. Signal: explain.compute_ms high. Recovery: capture alternatives only when requested (flag); default off in production.
  • Metric cardinality explosion. Manifestation: Prometheus OOM from per-DAG label values. Root cause: high-cardinality labels (e.g., dag fingerprint as a label). Debug: cardinality audit. Signal: metrics.series_count. Recovery: fingerprints go in traces/logs (exemplars), never as metric labels; labels are low-cardinality (stage, rule, status).
  • Trace context lost across async boundaries. Manifestation: disconnected spans, no end-to-end view. Root cause: not propagating the span into spawned tasks. Debug: trace inspection. Recovery: tracing::Instrument on spawned futures; propagate context.
  • Diff causal attribution wrong. Manifestation: diff blames the wrong input for a change. Root cause: heuristic attribution. Debug: controlled single-variable diffs. Recovery: present attribution as "candidate cause" with the changed inputs listed; don't overclaim.

10.7 Performance Concerns

  • Metrics use atomic counters/histograms; lock-free; negligible on the hot path.
  • Tracing head-sampling bounds span volume; spans carry minimal attributes (counts, durations), not payloads.
  • explain/diff are off the hot path (on-demand); their cost is acceptable since they're operator tools.
  • Plan-diff alignment is O(n) by fingerprint hash join, not O(n²) structural matching.

10.8 Edge Cases

  • Diff of plans with different node counts → added/removed sections; alignment by fingerprint handles partial overlap.

  • Explain of an all-cached plan → shows cache hits, zero compute schedule.
  • Very large plan explain → paginated/truncated text; full data in --json.
  • Diff across wire versions → normalize to a common in-memory form first; flag version difference.

Blast radius: operability (not correctness) — incidents become harder to debug. Containment: observability is non-load-bearing for correctness; its failure degrades debuggability only. Recovery: ensure every plan path emits the summary log and root span even when alternatives capture is off. Forensic: the structured summary log is the minimum always-on record. Postmortem: add the missing signal.

Phase 11 — Persistence, Replay, and Determinism

11.1 Objectives

  • Persist sufficient inputs per plan to reproduce it byte-identically offline: DAG fingerprint, stats snapshot, constraints, weights, rule-set hash, seed, and the chosen plan (I14, I15).
  • Append-only, crash-consistent replay log; deterministic replay harness; regression-fixture generation from production.
  • Constraint (Principle 10, 12): replayability first; crash-only persistence.

11.2 Detailed Implementation Steps

  • dagopt-replay/src/segment.rs: segmented append-only log. Each segment is a sequence of length-prefixed CBOR records with a per-record CRC32C; segments roll at a size threshold. On open, scan the tail and truncate a torn final record (CRC mismatch) — crash-consistent (I14).
  • dagopt-replay/src/log.rs: append(PlanRecord); iter() for replay/audit. PlanRecord { plan_fp, dag_fp, stats_snapshot_fp, constraints, weights, rule_set_hash, seed, exec_plan_ref, ts }. The actual DAG/stats bytes are content-addressed (stored once, referenced by fp) to keep the log small (≤ 200 B/plan compressed, §4).
  • dagopt-replay/src/snapshot.rs: stats snapshot store — the StatsProvider state needed to reproduce a decision, content-addressed by stats_snapshot_fp.
  • dagopt-replay/src/replay.rs: replay(plan_fp) -> Plan — load the record, reconstruct inputs (DAG by fp, stats by fp, rule-set by hash), re-run the pipeline with the recorded seed, assert the result equals the recorded plan (I15). Divergence → ReplayError::Divergence with a per-stage bisection (which stage first differs).
  • Determinism hardening: audit all sources of nondeterminism — hash-map iteration (replace with sorted/BTreeMap or explicit sort), wall clock (snapshot once), thread scheduling (search results order-independent or seeded), float compares (epsilon + tie-break). A determinism test runs each fixture N times across thread counts and asserts identical output.
  • Regression generation: scripts/replay_prod.sh pulls a production PlanRecord, replays it locally; if it diverges (e.g., after a code change), it becomes a regression fixture.
  • Rule-set pinning: replay reconstructs the exact rule-set by hash; if the current binary's rule-set hash differs, replay loads the recorded rule definitions or errors RuleSetMismatch (replays are pinned to a binary version range).
  • Deferred: persistent external metadata store — PhaseDeferred("FINAL_BLUEPRINT §11.10").
  • Observability: replay.records, replay.torn_tail, replay.divergence{stage}, replay.duration, span replay.
  • Theory anchors: replayability-first → P10; crash-only append log + per-record CRC → P12, I14, ADR-27 (CBOR); byte-identical replay → I15, P3; lineage/deterministic re-execution → Temporal replay, Spark RDD lineage; content-addressed inputs → P5, ADR-09; external metadata store deferred → §11.10.

11.3 Deliverable

  • dagopt replay <plan_fp> reproduces a plan and reports match/divergence; the log is queryable for audit.
  • Library: replay log append/iter/replay.

11.4 Acceptance Criteria

  • Replay reproduces 100% of logged plans byte-identically across runs and thread counts (I15).
  • Crash consistency (I14): kill mid-append (fault injection); on reopen, the log truncates the torn tail and all prior records are intact.
  • Determinism: every conformance fixture produces identical output over 1000 runs × {1,2,4,8} threads.
  • Log size ≤ 200 B/plan compressed; content-addressed dedup of DAG/stats verified.
  • Divergence bisection: a deliberately-introduced nondeterminism is localized to the first divergent stage.
  • Performance: append ≤ 20 µs; replay throughput ≥ 1k plans/s (bounded by pipeline cost).

11.5 Conformance Fixtures

  • conformance/plans/replay_etl.record — a recorded plan; replay must match.
  • conformance/plans/replay_torn_tail.segment — truncated segment → tail dropped, prior intact.
  • conformance/plans/replay_divergence.record — record + a divergence-inducing patch → Divergence{stage}.
  • conformance/plans/determinism_threads.golden — identical output across thread counts.
  • Compat: conformance/plans/replay_ruleset_mismatch.record → RuleSetMismatch.

11.6 Pitfalls

  • Hidden nondeterminism via hash iteration. Manifestation: replay diverges; plan-diff noisy. Root cause: iterating a HashMap in a plan-affecting way. Debug: determinism test across runs; the divergence bisection points to the stage. Signal: replay.divergence{stage}. Recovery: replace plan-affecting iteration with sorted order (BTreeMap/explicit sort); ban HashMap iteration in plan-producing code (lint).
  • Snapshot incomplete. Manifestation: replay can't reproduce because some input wasn't captured. Root cause: a decision read state not in the snapshot. Debug: replay fails to find an input. Signal: replay.missing_input. Recovery: the snapshot must capture every input the cost model/search touched; enforce by making the StatsProvider snapshot-only during planning.
  • Torn tail mis-detected as valid. Manifestation: a partial record replayed as complete → corruption. Root cause: missing/weak CRC. Debug: fault injection mid-record. Signal: replay.torn_tail should fire. Recovery: per-record CRC32C; truncate on mismatch; never partially decode.
  • Float divergence across platforms. Manifestation: replay on a different CPU picks a different plan. Root cause: FP objective compared exactly. Debug: cross-arch replay. Recovery: epsilon compares + deterministic tie-break; or fixed-point objective for the decision (FP for display only).
  • Rule-set drift. Manifestation: replay under a newer binary diverges (a rule changed). Root cause: not pinning the rule-set. Debug: RuleSetMismatch. Recovery: record the rule-set hash; replay errors clearly if it differs; keep old rule definitions for replay across versions.
  • Log unbounded growth. Manifestation: disk fills. Root cause: never rotating/GC'ing old records. Debug: log-size metric. Signal: replay.log_bytes. Recovery: retention policy (rotate, archive, GC content-addressed blobs no longer referenced).

11.7 Performance Concerns

  • Append is a sequential write + CRC; batch fsync (group commit) for throughput, with a bounded latency.
  • Content-addressing dedups DAG/stats so the log records only references — keeps it tiny.
  • Replay cost = pipeline cost; parallelize replay across records for bulk regression runs.
  • CRC32C is hardware-accelerated; negligible per record.

11.8 Edge Cases

  • Empty log → replay no-op; reopen creates the first segment.
  • Replay of a plan whose DAG/stats blob was GC'd → ReplayError::MissingInput; retain blobs as long as their records are retained.
  • Concurrent appends → serialized by a single-writer log (the planning service has one log writer); readers (replay) are lock-free.
  • A plan that hit a budget (suboptimal=true) → replays to the same suboptimal plan (seed + budget reproduce the early stop).
  • Clock skew → timestamps are metadata only, never decision inputs; skew doesn't affect replay.
  • Mid-segment crash then restart then crash → each reopen truncates any torn tail idempotently.

11.9 Failure Analysis

  • What breaks: replay diverges (I15 violation) — production plans can't be reproduced, undermining trust and debugging. Detection: a periodic replay-audit job re-runs recent records and alerts on divergence (replay.divergence). Blast radius: debuggability and confidence (not live correctness). Containment: divergence indicates hidden nondeterminism or rule drift; the bisection localizes the stage. Recovery: fix the nondeterminism source; until then, plans are still correct, just not reproducible. Forensic: the diverging stage + the two plan dumps. Postmortem: add a determinism test for the offending construct; the replay-audit job is the long-term guard.

11.10 Operational Notes

  • Metrics: replay.records, replay.log_bytes, replay.torn_tail, replay.divergence{stage}, replay.audit_pass_ratio.
  • Tracing: replay span with match/divergence outcome.
  • Logging: warn on torn tail (expected after a crash, should be rare) and on any divergence (should be never).
  • Deployment: the log lives on durable storage; the planning service is the single writer. Backup the log + content store (the regenerable cache is not backed up — see Phase 8 §8.10).
  • Restore testing: periodically restore the log+blobs to a staging instance and run the replay-audit (proves backups are usable).
  • Migration: log/record formats are versioned; readers handle prior versions; a major bump migrates via a one-time rewrite tool. Persistent external metadata store is deferred (§11.10).
  • Compatibility: PlanRecord is #[non_exhaustive]; additive fields are non-breaking; the rule-set hash pins replay to a binary range.

Phase 12 — Distributed / Sharded Planning and Scale

12.1 Objectives

  • Plan a single very large DAG (N ≫ single-process limits) by partitioning it across planner shards that optimize subgraphs in parallel, with a coordinator stitching boundary edges.
  • Preserve correctness: the stitched plan is equivalent to a single-process plan (or a documented, bounded approximation).
  • Constraint: coordination overhead bounded; determinism preserved across the distributed run.

12.2 Detailed Implementation Steps

  • dagopt-dist/src/partition.rs: partition the canonical DAG into shards minimizing cut edges (a graph-partitioning pass — multilevel / Kernighan-Lin style, or a cheap topo-band partition for chains). Each partition is a connected subgraph; cut edges become boundary artifacts.
  • dagopt-dist/src/shard.rs: a shard worker runs the full single-process pipeline (rewrite/cost/search/schedule) on its subgraph, treating boundary inputs as Sources with cost/size annotations supplied by the coordinator and boundary outputs as Sinks.
  • dagopt-dist/src/coordinator.rs: assigns partitions to shards, exchanges boundary metadata (artifact sizes, costs) iteratively until boundary estimates converge (fixed-point or bounded rounds), collects sub-plans, and globally schedules across shards' resource pools.
  • dagopt-dist/src/stitch.rs: reconnect shard sub-plans at boundary artifacts; verify global precedence and that cross-shard rewrites (CSE across the cut) are either applied via a coordinator-level pass or explicitly forgone (documented approximation). Validate the stitched plan (I9/I10 globally).
  • Cross-shard CSE: a duplicate subgraph split across shards won't be deduped locally. The coordinator runs a global fingerprint reconciliation: boundary subgraphs with equal fps are merged at stitch time. Deep cross-shard CSE is bounded (only at boundaries) — full global CSE is the deferred cross-DAG cache (Phase 8 §8.9).
  • Determinism: partitioning is deterministic (seeded); boundary-exchange rounds are deterministic; shard assignment by partition id; stitching by fingerprint order.
  • Failure handling: a shard crash → the coordinator reassigns its partition (idempotent: re-plan the subgraph). Partial progress is checkpointed at boundary-metadata granularity.
  • Deferred: NUMA-aware shard placement — PhaseDeferred("FINAL_BLUEPRINT §12.10").
  • Observability: dist.shards, dist.cut_edges, dist.boundary_rounds, dist.shard_crash, dist.global_makespan, span dist.plan with per-shard child spans.
  • Theory anchors: min-cut partitioning → Kernighan-Lin / multilevel partitioning, Tanenbaum ch.6; decentralized/sharded scheduling → Sparrow (Ousterhout 2013); deterministic seeded partition → P3; idempotent shard re-plan → P12; global precedence/capacity on stitch → I9, I10; boundary CSE → I5; NUMA placement deferred → §12.10.

12.3 Deliverable

  • dagopt plan --shards N <huge.wdl> partitions, plans in parallel, stitches; dagopt-dist coordinator + shard workers (in-process simulated cluster for tests; real cluster via the service).
  • Library: partition, shard worker, coordinator, stitch.

12.4 Acceptance Criteria

  • Equivalence: the stitched plan executes to identical sink digests as a single-process plan (I7) on graphs that fit both modes (differential).
  • Cost parity: stitched plan objective within a documented factor (e.g., ≤ 1.1×) of single-process (boundary approximation cost).
  • Scaling: planning a 1M-node DAG with K shards reduces wall time ≈ linearly until coordination dominates (measure the knee).
  • Determinism: same DAG + shard count + seed → identical stitched plan.
  • Fault tolerance: a shard crash mid-plan → coordinator reassigns; final plan correct.
  • Performance: coordination overhead (boundary exchange) ≤ 15% of total planning wall time at K=16.

12.5 Conformance Fixtures

  • conformance/plans/dist_equiv.golden — stitched vs single-process plan equivalence.
  • conformance/plans/dist_cross_shard_cse.golden — boundary CSE reconciliation.
  • conformance/plans/dist_shard_crash.fixture — shard crash → reassignment → correct plan.
  • conformance/plans/dist_partition_balance.golden — balanced partitions, minimal cut.
  • conformance/plans/dist_determinism.golden — fixed seed/shard-count plan.

12.6 Pitfalls

  • Boundary estimate oscillation. Manifestation: boundary-exchange rounds never converge. Root cause: shard A's output size depends on B's, circularly. Debug: round-count metric; detect oscillation. Signal: dist.boundary_rounds at cap. Recovery: bound rounds, damp estimates, accept the last as an approximation (documented).
  • Cut edges too many (bad partition). Manifestation: coordination dominates, no speedup. Root cause: partition ignored edge weights. Debug: cut-edge metric vs total edges. Signal: dist.cut_ratio high. Recovery: weight edges by artifact size; partition to minimize weighted cut.
  • Cross-shard CSE missed → cost regression. Manifestation: duplicate work across shards. Root cause: local-only dedup. Debug: compare node count to single-process. Recovery: coordinator fingerprint reconciliation at boundaries; accept interior duplicates as a documented bound.
  • Stitched plan violates global precedence. Manifestation: a cross-shard edge ordered wrong. Root cause: shards scheduled independently, global order not enforced. Debug: global precedence validation (I9) on the stitched plan. Signal: sched.precedence_violation. Recovery: coordinator-level global schedule pass over boundary edges after stitching.
  • Non-deterministic partition. Manifestation: different shardings run-to-run → different plans. Root cause: partition uses randomness/hash order. Debug: determinism test. Recovery: seed the partitioner; deterministic tie-breaks.
  • Shard reassignment double-counts resources. Manifestation: after a crash+reassign, the global schedule oversubscribes (the dead shard's reservations not released). Root cause: stale resource reservations. Debug: capacity validation. Recovery: reservations are per-final-plan, computed after all shards report; a reassigned shard's prior partial reservations are discarded.

12.7 Performance Concerns

  • Partitioning cost must be << planning savings; use a cheap partitioner (topo-band) for chain-like DAGs, multilevel only for dense ones.
  • Boundary metadata is small (sizes/costs per cut edge); exchange is cheap relative to subgraph planning.
  • Shards run the full pipeline in parallel — near-linear speedup until the coordinator's stitch/global-schedule pass (serial) dominates (Amdahl).
  • The coordinator's global schedule over boundary edges is O(cut edges), not O(total nodes) — keeps it cheap.
  • Content-addressed DAG/stats shared across shards via the store (no re-sending the whole graph).

12.8 Edge Cases

  • Single shard → degenerates to single-process planning (no partition, no stitch).
  • Fully connected DAG (every node depends on every other) → cut is large, partitioning yields little; fall back to single-process with a warning.
  • Partition smaller than a shard's min work → merge tiny partitions to avoid coordination overhead exceeding planning.
  • All cross-shard edges to one sink → that sink's shard is a bottleneck; balance by replicating boundary metadata.
  • A shard's subgraph itself exceeds single-process limits → recursive sharding (shard-of-shards), bounded depth.
  • Zero cut edges (already disconnected components) → embarrassingly parallel; no boundary exchange.

12.9 Failure Analysis

  • What breaks: the coordinator (single point) crashes mid-plan. Detection: heartbeat/health; the request times out. Blast radius: one in-flight large-DAG plan. Containment: planning is recomputable (stateless); the coordinator role is recoverable — a new coordinator re-partitions from the content-addressed DAG. Recovery: restart, re-plan (≤ RTO); no persisted plan state lost. Forensic: per-shard spans + boundary-round logs. Postmortem: if the coordinator is a recurring bottleneck, shard the coordinator role (hierarchical). NUMA-aware placement (§12.10) is deferred — Phase 0 assumes uniform shards.

12.10 Operational Notes

  • Metrics: dist.shards, dist.cut_edges, dist.cut_ratio, dist.boundary_rounds, dist.shard_crash, dist.global_makespan, dist.coordination_fraction.
  • Tracing: a dist.plan root span with per-shard child spans; boundary-round events.
  • Logging: per-shard summary; coordinator decisions (partition sizes, cut, rounds).
  • Deployment: shards are stateless dagopt-svc instances; the coordinator is a role (can co-locate or be separate). Scale shards horizontally; the coordinator is the vertical bottleneck (see Scalability Analysis).
  • Rollback: shard count is a request/config parameter; set to 1 to disable sharding.
  • Migration: boundary-metadata protocol is versioned; mixed-version shards rejected (coordinator pins a version).
  • Compatibility: sub-plans use the same ExecPlan wire; the stitched plan is a normal ExecPlan (executors see no difference).

Phase 13 — Hardening: Fuzzing, Chaos, Conformance

13.1 Objectives

  • Make the system survive adversarial and pathological inputs and operational faults: structured DAG fuzzing, chaos/fault injection, a versioned conformance suite, and performance-regression gating.
  • Close the loop: every invariant (I1–I18) has an automated check; every prior phase's pitfalls have regression coverage.
  • Constraint: the system fails closed and bounded under all tested adversity (Principles 4, 13).

13.2 Detailed Implementation Steps

  • fuzz/fuzz_targets/: libFuzzer targets for parse, validate, canon, rewrite, schedule, roundtrip. Structured generators (dagopt-testkit/src/gen.rs) emit valid-by-construction DAGs (random topo-ordered graphs with typed ports) plus mutated/malformed variants. Goal: zero panics, zero hangs, zero OOMs; all errors are typed.
  • Differential fuzzing: generate a random DAG, run optimized vs unoptimized through the simulated executor, assert identical sink digests (I6/I7) — fuzzing the correctness of the whole optimizer.
  • dagopt-testkit/src/diff_harness.rs: the differential harness, now driven by the fuzzer and by replayed production records.
  • Chaos: scripts/ + testkit fault injectors simulate cache corruption, torn log writes, shard crashes, slow executors, OOM (budget breach), clock skew. Each must produce the documented behavior (fail closed, fall back, recover) — verifying Failure Modes & Recovery.
  • conformance/: the versioned suite — IR round-trips, rewrite before/after, schedules, full plans, replay records — run in CI and tagged per release. A new release must pass all prior conformance fixtures (compat) plus its own.
  • benchmarks/ + .github/workflows/bench.yml: criterion benches for each stage; a regression gate fails CI if p50/p99 regress beyond a threshold vs the baseline.
  • Pathological corpora: benchmarks/datasets/pathological/ — graphs designed to stress each subsystem (deep chains, extreme fan-out, dense diamonds, rewrite-explosion patterns, fingerprint-collision attempts). Used for both perf and DOS-resilience testing.
  • Soak: a long-running test plans a stream of DAGs for hours, asserting bounded memory (no leaks in interner/e-graph/cache) and stable latency.
  • Observability: fuzz.crashes (0), fuzz.timeouts (0), chaos.recovered_ratio, conformance.pass_ratio, bench.regression.
  • Theory anchors: structured/coverage-guided fuzzing → ADR-17 (cargo-fuzz); differential correctness fuzz → I6, I7, ADR-16; one assertion per invariant → I1–I18 (deterministic simulator, §7); chaos validating documented recovery → Failure Modes & Recovery (F1–F10); bench-regression gate → ADR-18 (criterion); fail-closed-and-bounded under adversity → P4, P13.

13.3 Deliverable

  • Green CI gates: fuzz-short (per PR), fuzz-long (nightly), conformance (per PR), bench-regression (per PR), chaos (nightly). A release artifact is produced only when all pass.
  • Library/tooling: structured DAG generators, fault injectors, conformance runner.

13.4 Acceptance Criteria

  • Fuzzing: ≥ 72 cpu-hours per target with zero panics/timeouts/OOMs; all reachable errors are typed (no unwrap on input-derived data).
  • Differential fuzzing: ≥ 1M random DAGs, zero optimized-vs-unoptimized divergences (I6/I7).
  • Chaos: every documented failure mode (Failure Modes & Recovery) injected → observed behavior matches the documented containment/recovery.
  • Conformance: 100% pass, including all prior-release fixtures (backward compat).
  • Bench regression: no stage regresses > 5% (p50) or > 10% (p99) vs the locked baseline without an explicit baseline update.
  • Soak: 24-hour run with bounded RSS (no upward trend) and stable p99.

13.5 Conformance Fixtures

  • conformance/ (entire suite, versioned) — the union of all phases' fixtures.
  • fuzz/corpus/ — seed corpus + minimized crash reproducers (each crash becomes a permanent regression seed).
  • benchmarks/datasets/{small,medium,large,pathological}/ — perf and resilience corpora.
  • conformance/chaos/*.scenario — fault-injection scenarios with expected outcomes.
  • conformance/compat/* — cross-version wire/IR/replay fixtures.

13.6 Pitfalls

  • Fuzzer only explores shallow inputs. Manifestation: green fuzzing but production crashes on complex DAGs. Root cause: unstructured byte fuzzing rarely produces valid graphs. Debug: coverage report. Recovery: structured generators produce valid DAGs; mutate at the IR level, not the byte level.
  • Differential harness hides nondeterminism. Manifestation: differential passes but production diverges. Root cause: the simulated executor is deterministic, masking a real-executor nondeterminism the optimizer assumed away. Debug: run differential with a nondeterminism-injecting executor. Recovery: only cache/CSE pure ops; the harness models impurity.
  • Bench baseline drift. Manifestation: gradual perf regression slips through (each PR < threshold, cumulatively large). Root cause: rebasing the baseline each PR. Debug: track absolute perf over time, not just per-PR delta. Recovery: lock the baseline; require explicit, reviewed baseline updates.
  • Chaos test flakiness. Manifestation: chaos tests fail intermittently, get disabled. Root cause: timing-dependent fault injection. Debug: deterministic fault injection (inject at a logical point, not a wall-clock time). Recovery: hook fault points in code, trigger deterministically.
  • Conformance fixtures rot. Manifestation: fixtures updated to match buggy output (test confirms the bug). Root cause: blindly accepting insta snapshot updates. Debug: review every snapshot change. Recovery: snapshot updates require explicit review; golden changes are PR-visible diffs.
  • Pathological corpus triggers real DOS in CI. Manifestation: a pathological graph OOMs the CI runner. Root cause: the budget guard not engaged in the test. Debug: run pathological corpus with budgets on. Recovery: budgets are always on; the test asserts graceful degradation (suboptimal/abort), not success.

13.7 Performance Concerns

  • Fuzzing is coverage-guided; structured generation keeps inputs valid so coverage reaches deep code.
  • Bench harness uses criterion for statistical rigor (variance, outlier detection) — avoids flaky thresholds.
  • Soak watches allocator stats (interner size, e-graph nodes, cache entries) for unbounded growth.
  • Pathological corpus is the DOS-resilience benchmark: it must complete (degraded) within budgets, never hang.

13.8 Edge Cases

  • Fuzzer generates a graph at the max-node limit → must be rejected by limits.rs, not crash.
  • A fingerprint-collision-attempt input (crafted to collide) → the deep-eq audit (I5) catches it; no wrong dedup.
  • A rewrite-explosion graph → saturation budget caps; greedy fallback; no OOM.
  • Chaos: simultaneous cache corruption + shard crash → both containment paths engage independently; recovery composes.
  • Clock skew injected → no effect on plans (timestamps are metadata only).
  • Torn log write + immediate crash → reopen truncates; no data loss beyond the torn record.

13.9 Failure Analysis

  • What breaks: a class of adversarial input not covered by fuzzing causes a panic/hang/OOM in production. Detection: production panic/timeout/OOM metrics; the request boundary catches panics. Blast radius: one request (caught) or one instance (OOM, stateless). Containment: request-level catch_unwind; per-request budgets; the LB routes around a dead instance. Recovery: capture the input (by hash, via replay), reproduce, minimize, add to the fuzz corpus + a regression fixture. Forensic: the minimized input and the stack. Postmortem: extend the structured generator to cover the new shape; the corpus grows monotonically.

13.10 Operational Notes

  • Metrics: fuzz.crashes, fuzz.timeouts, chaos.recovered_ratio, conformance.pass_ratio, bench.regression{stage}, production *.panic/*.timeout/*.oom counters.
  • Tracing: chaos scenarios traced end-to-end to verify the recovery path executed.
  • Logging: every crash reproducer logged with its input hash for replay.
  • Deployment: hardening gates run in CI, not production; production carries the budget guards and request-boundary panic catch that the gates validate.
  • Rollback: a release that fails any gate is not produced; rollback is to the last green release.
  • Compatibility: the conformance suite is the compatibility contract — a release must pass all prior fixtures; intentional breaks require a major version and a documented migration.

Failure Modes & Recovery

Taxonomy by subsystem. Each: symptoms, root causes, detection, automatic recovery, manual recovery, operator actions, forensic artifacts, long-term mitigation.

F1 — Frontend/validation failure

  • Symptoms: workflows rejected; parser panic (bug).
  • Root causes: malformed input; grammar/recovery bug.
  • Detection: typed errors; parse.panic (should be 0); fuzzing.
  • Automatic: typed Result; request-boundary catch_unwind → INVALID_ARGUMENT.
  • Manual: inspect diagnostic; fix the .wdl or the grammar.
  • Operator: check validate.errors{kind}; common kinds indicate a workflow-author issue vs a bug.
  • Forensic: input hash → replay; diagnostic with span.
  • Long-term: fuzz corpus seed for any panic.

F2 — Incorrect optimization (semantic divergence)

  • Symptoms: optimized plan produces different results than unoptimized (the worst failure).
  • Root causes: buggy rewrite rule, bad CSE/cache (omitted fingerprint input), wrong analysis (dominators/reachability), unsound cost pruning.
  • Detection: differential testing (CI + production sampling); rewrite.semantic_div, cache.key_result_skew, search.equiv_violation.
  • Automatic: per-rule kill switch (config); global cache-disable; mode=greedy fallback (no e-graph).
  • Manual: bisect with replay log (re-run captured plans with the rule/cache off); delta-debug the failing DAG.
  • Operator: flip the rule/cache flag; alarm fires on any divergence.
  • Forensic: rule trace, e-graph dump, minimized DAG, the two result digests.
  • Long-term: minimized DAG → permanent differential fixture; tighten the rule's proof obligation.

F3 — Suboptimal plan (correct but slow)

  • Symptoms: plan executes correctly but with poor makespan/cost; SLO miss on execution side.
  • Root causes: budget breach (search stopped early), mis-calibrated cost model, bad partition (sharded), wrong critical path.
  • Detection: search.suboptimal, cost.estimate_error, sched.makespan_ratio, dist.cut_ratio.
  • Automatic: none (correctness preserved); flagged suboptimal=true.
  • Manual: raise budgets, recalibrate stats, re-partition; compare via plan-diff.
  • Operator: watch suboptimal rate and estimate-error; tune budgets/weights (config).
  • Forensic: stats_snapshot, search stats, the chosen-vs-alternatives in explain.
  • Long-term: feed estimate errors to recalibration; the deferred learned model (§5.5 Required Reading).

F4 — Scheduling infeasibility/violation

  • Symptoms: plan rejected (Infeasible) or executor reports input-missing/oversubscription.
  • Root causes: task larger than any pool; scheduler precedence/capacity bug; stale pool config.
  • Detection: post-schedule validation (I9/I10, mandatory); executor errors.
  • Automatic: validation fails the plan before emission (fail closed).
  • Manual: fix pool config (sync with executor); fix the workflow's resource request.
  • Operator: check sched.infeasible, sched.capacity_violation.
  • Forensic: schedule table, the violating pair, pool config.
  • Long-term: feasibility pre-check; pool-config drift alert.

F5 — Backpressure failure / OOM

  • Symptoms: planner/service memory climbs unbounded; OOM kill.
  • Root causes: token leak, unbounded planning pool, e-graph budget not enforced.
  • Detection: exec.tokens_outstanding, svc.queue_depth, RSS alerts, mem.budget_exceeded.
  • Automatic: hard budget abort (Principle 4); token gate (I12); LB routes around a dead instance.
  • Manual: restart the instance; tune budgets/pool size.
  • Operator: scale out; lower max-in-flight.
  • Forensic: token ledger, heap profile, the offending DAG.
  • Long-term: RAII token guards; budget guards in every loop; slow-executor alert.

F6 — Persistence corruption / loss

  • Symptoms: cache returns corrupt/missing; replay log torn; cache/log unreadable.
  • Root causes: crash mid-write, disk failure, bit rot.
  • Detection: CRC/digest verify on read; replay.torn_tail, cache.corrupt.
  • Automatic: truncate torn tail (log); treat corrupt cache entry as miss (recompute); atomic rename prevents torn cache files.
  • Manual: restore log+blobs from backup; rebuild cache by recompute.
  • Operator: run restore-test; check storage health.
  • Forensic: the corrupt segment/entry, CRC mismatch logs.
  • Long-term: scrub job (periodic digest verification); the cache is regenerable so loss costs recompute, not correctness.

F7 — Determinism/replay divergence

  • Symptoms: replay produces a different plan; plan-diff noisy.
  • Root causes: hidden nondeterminism (hash iteration, wall clock, FP), rule-set drift, incomplete snapshot.
  • Detection: replay-audit job; determinism tests; replay.divergence{stage}.
  • Automatic: none (plans still correct); divergence flagged.
  • Manual: bisect to the divergent stage; fix the nondeterminism source.
  • Operator: monitor replay.audit_pass_ratio.
  • Forensic: the diverging stage, both plan dumps, the record.
  • Long-term: ban plan-affecting HashMap iteration (lint); the audit job is the standing guard.

F8 — Distributed coordination failure

  • Symptoms: large-DAG plan times out; shard crash; boundary oscillation.
  • Root causes: coordinator crash, shard crash, partition imbalance, non-converging boundary estimates.
  • Detection: heartbeats, dist.shard_crash, dist.boundary_rounds at cap, dist.coordination_fraction.
  • Automatic: shard reassignment (idempotent re-plan); coordinator restart re-partitions from content-addressed DAG.
  • Manual: reduce shard count; improve partition; cap rounds.
  • Operator: scale shards; watch coordination fraction.
  • Forensic: per-shard spans, boundary-round logs, partition sizes.
  • Long-term: hierarchical coordinator if it bottlenecks; damped boundary estimates.

F9 — Service availability

  • Symptoms: requests fail/time out; instance down.
  • Root causes: OOM, crash, overload, deploy gone wrong.
  • Detection: health checks, error-rate/latency SLO alerts.
  • Automatic: LB removes unhealthy instances; backpressure sheds load; stateless restart.
  • Manual: rollback deploy; scale out.
  • Operator: incident runbook; canary check.
  • Forensic: instance logs, the in-flight request set (by id).
  • Long-term: capacity planning; canary + rolling upgrade discipline.

F10 — Cache / incremental staleness

  • Symptoms: a re-plan reuses an outdated result or schedule though an input changed; results are uncorrupted but stale (distinct from F2's rule bug and F6's corruption).
  • Root causes: a too-narrow dirty set (a transitively-affected node not re-planned), a fingerprint that omits an output-determining input, or a cache entry served after its inputs changed (Phase 8 §8.6).
  • Detection: differential of incremental vs full re-plan (must match), incremental.divergence, cache.key_result_skew (I13); production differential sampling.
  • Automatic: dirty set = changed nodes ∪ all reachable successors (never narrower); pure-only caching; global cache-disable flag.
  • Manual: invalidate the offending key/namespace; widen the fingerprint to cover the missed input; recompute.
  • Operator: watch incremental.reused_ratio vs expected; flip cache-disable on suspicion.
  • Forensic: the dirty set, the key + both results, the producing plans (replay log).
  • Long-term: make incremental-vs-full equivalence a standing property test (Phase 8 §8.4); add the missed input shape to the differential corpus.

Operational Readiness

Metrics strategy

  • Pull-based Prometheus; histograms for all latencies (SLO-aligned buckets), counters for events, gauges for live state.
  • Low-cardinality labels only (stage, rule, status, pool); fingerprints/request-ids go to traces/logs, never labels (avoid cardinality explosion — see Phase 10 §10.6).
  • Key families: pipeline.{stage}.duration, search.*, cost.*, rewrite.rule_applied{rule}, cache.hit_ratio, sched.makespan*, svc.*, replay.*, dist.*, mem.budget_exceeded.

Tracing strategy

  • OpenTelemetry OTLP; root plan span per request carrying request id + DAG fingerprint (as attributes/exemplars); per-stage child spans; cross-async propagation via Instrument.
  • Head sampling (configurable) bounds overhead; errors/suboptimal plans always sampled (tail rule).

Structured logging

  • JSON; one summary line per plan (fingerprints, node counts, rules applied, objective, makespan, latency, suboptimal, status). Debug logs gated/sampled. Every rejected input logged with its hash for replay.

Dashboards

  1. Planning latency (p50/p95/p99 per stage, stacked) — the primary SLO view.
  2. Optimizer effectiveness (rewrite reduction ratio, cache hit ratio, cost objective distribution).
  3. Search health (e-graph size, iterations, suboptimal rate, budget breaches).
  4. Scheduling (makespan distribution, makespan/critical-path ratio, pool utilization).
  5. Service (request rate, error rate, queue depth, reject rate, in-flight).
  6. Correctness sentinels (semantic-divergence count, key/result skew, replay-audit pass ratio — all should be flat at 0/100%).
  7. Resource (RSS, interner size, cache size, fd count).

Alerting philosophy

  • Page on correctness sentinels (any semantic_div, key_result_skew, replay.divergence > 0) — these are never acceptable.
  • Page on SLO burn (planning p99 over target sustained, error rate, availability).
  • Ticket (non-paging) on suboptimal-rate rise, cache-hit-ratio drop, estimate-error rise — degradations, not outages.
  • Alert on leading indicators (queue depth, memory trend) before saturation.

SLOs

  • Planning availability (svc): 99.9% successful plan responses/month.
  • Planning latency: p99 ≤ §4 targets per mode and graph size.
  • Correctness: 0 semantic divergences (hard SLO; any breach is a Sev-1).
  • Replay reproducibility: ≥ 99.99% of audited plans replay identically.

Incident response

  • Runbooks in docs/runbooks/ per failure class (F1–F10). First action for correctness Sev-1: flip the relevant kill switch (rule/cache/mode) — config-only, no redeploy. Then bisect with the replay log.

Backup / restore

  • Backup: replay log + content-addressed input/result store (durable storage, periodic snapshot). The cache of computed results is regenerable and not backed up.
  • Restore testing: periodic restore to staging + run the replay-audit (proves backups are usable, not just present).

Deployment topology

  • dagopt-svc stateless instances behind an LB; shared durable storage for log + content store; a coordinator role for sharded planning. Prometheus + OTLP collector adjacent.

Canary / rolling upgrade / rollback

  • Canary: route a small traffic fraction to the new version; compare plan-diff (new vs old) and SLOs; the wire is versioned so canary and stable interoperate.
  • Rolling upgrade: instances replaced one at a time; back-compatible wire (read-new-before-write-new) keeps in-flight clients working.
  • Rollback: redeploy the prior image; config kill switches give instant mitigation without a deploy.

Migration

  • IR/wire/log/cache formats are versioned (see Compatibility & Versioning). A major bump ships a migration tool and a documented sequence (upgrade readers first). fp_version bumps namespace the cache.

Build & Release Engineering

  • Reproducible builds: pinned toolchain (rust-toolchain.toml), cargo build --locked, SOURCE_DATE_EPOCH, vendored deps; two builds byte-identical (verified in repro_build.sh, ADR-26).
  • Artifact signing: release binaries + container images signed (sigstore/cosign-style); signatures published.
  • SBOM: CycloneDX generated per release (cargo-cyclonedx); attached to the release.
  • Provenance: SLSA-style build attestation (who/what/when/inputs); verifiable against the source commit.
  • Release channels: nightly (per-merge), beta (pre-release soak), stable (gated by full conformance + bench + chaos green).
  • CI/CD topology: GitHub Actions matrix — ci.yml (fmt, clippy, test, coverage), fuzz.yml (nightly long), bench.yml (regression gate), audit.yml (cargo-audit/deny scheduled), release.yml (build → sign → SBOM → provenance → publish).
  • Version stamping: binary embeds git SHA + semver + build date + rule-set hash (replay pins to this).
  • Dependency auditing: cargo-audit (CVEs) + cargo-deny (licenses/bans/duplicates) block release.
  • Supply-chain verification: deps pinned with checksums; lockfile committed; SBOM diffed across releases for review.
  • Release automation: a tag triggers release.yml; no manual artifact handling; rollback = re-publish prior tag's signed artifact.

Performance Engineering

  • Benchmarking: criterion per stage (parse/canon/analysis/rewrite/search/sched/emit) over {small,medium,large,pathological} corpora; statistical, with regression gating vs a locked baseline.
  • Profiling methodology: CPU profile (perf/pprof) the planner on the large corpus; identify hot stages (expected: search/saturation, canon hashing, pattern matching).
  • Flamegraph workflow: cargo flamegraph on representative + pathological inputs; compare across releases; attach to docs/performance/.
  • Tracing methodology: per-stage span durations under load reveal where p99 is spent; correlate with metrics.
  • Allocator analysis: track allocations in search/canon (the churn-heavy stages); arena + Arc sharing to cut allocations; consider a bump allocator for per-plan scratch.
  • Lock analysis: the memo table and interner are the contention points under parallel search; measure with lock-contention profiling; shard (dashmap) and keep critical sections tiny.
  • Cache analysis: e-node and IR-node layout 64-byte aligned; bitsets word-aligned; measure cache misses on the hot match/hash loops.
  • Throughput targets: §4 (≥ 2,000 small plans/sec/core greedy; ≥ 100k nodes/s rewrite; ≥ 200k tasks/s schedule).
  • Tail latency: p99 is dominated by large/dense graphs and saturation; budgets cap the tail (Principle 4); measure p99 separately per mode and size bucket.
  • Memory profiling: heap profiling (dhat/heaptrack) on soak; assert no upward trend in interner/e-graph/cache; enforce budgets.

Scalability Analysis

  • Bottlenecks: (1) plan search (e-graph saturation) — superlinear in rewrite opportunities; (2) the memo/interner under parallel search — lock contention; (3) the sharded coordinator's serial stitch/global-schedule pass (Amdahl); (4) replay-log single writer.
  • Scaling ceilings: single-process planning bounded by memory (e-graph node budget) and the search budget; ~100k–1M nodes per process depending on density (§4).
  • Horizontal scaling: stateless planners behind an LB scale request throughput linearly; sharded planning (Phase 12) scales a single huge DAG until coordination dominates (knee measured at the cut ratio).
  • Vertical scaling: search parallelism scales with cores until memo-table contention; mitigated by sharding the table.
  • Sharding/partitioning of plan search: partition the DAG (Phase 12) to parallelize search; the cut ratio bounds the benefit (high cut → coordination overhead).
  • Coordination overhead: boundary-metadata exchange is O(cut edges); target ≤ 15% of planning wall at K=16; rises with cut ratio.
  • Metadata scaling: the replay log grows ≤ 200 B/plan (content-addressed); the content store grows with distinct DAGs/results, GC-bounded; cache amplification ≤ 1.2×.
  • Network fanout: minimal — shards pull content-addressed inputs from the store, exchange small boundary metadata; not a network-bound system.
  • Scheduler saturation: list scheduling is per-DAG serial; parallelism is across DAGs; a single enormous DAG's schedule is the per-DAG ceiling (sharded scheduling at boundaries helps).
  • Storage growth: log + content store on durable storage; retention/GC policies bound growth; the regenerable result cache is separately sized.

Mental Models & First Principles

The compressed insights an expert holds; each predicts behavior, names the bug class you write without it, and the section/phase where this blueprint applies it.

  • MM1 — The optimizer is two stacked optimization problems, not one. Plan cost (which equivalent graph) is minimized first; schedule makespan (when/where on resources) second. Predicts: the cheapest plan need not have the shortest makespan. Bug class without it: folding cost and schedule into one objective, so a makespan regression looks like a cost-model bug and is "fixed" in the wrong stage. Applied: P2 (logical/physical/schedule separation), Phase 6, Phase 7.
  • MM2 — A fingerprint is one identity serving three masters. The BLAKE3 structural hash is the CSE key, the cache key, and the replay key. Predicts: any drift/collision in canonicalization simultaneously breaks dedup, cache, and replay. Bug class: keying the cache on a hash that omits an output-determining input → silent wrong reuse. Applied: Phase 2, Phase 8, Phase 11; I5, I13.
  • MM3 — Greedy rewriting is hostage to phase ordering; saturation escapes it. An e-graph represents all rewrite orders at once, so extraction is unbiased by application order. Predicts: greedy can get stuck below the optimum that a different rule order would reach. Bug class: chasing a "missing optimization" that is really an ordering artifact. Applied: Phase 4 (greedy), Phase 6 (saturation); Tate 2009.
  • MM4 — Pruning is only as sound as the monotonicity you can prove. DP/B&B may prune a partial plan only on cost dimensions where a subplan's cost ≤ any containing plan's. Predicts: pruning on a non-monotone dim (wall under caching) silently discards the optimum. Bug class: a "fast but occasionally worse" optimizer. Applied: Phase 5, Phase 6; I8, P6.
  • MM5 — Determinism is a property you engineer, not one you get. Hash-map iteration, wall clock, thread order, and raw FP compares each inject nondeterminism that survives until a plan-diff goes noisy or a replay diverges. Predicts: where reproducibility breaks first. Bug class: irreproducible production incidents. Applied: Phase 11; P3, I15.
  • MM6 — Every search must have a budget, and the budget must degrade, not crash. A bounded search turns a pathological DAG into a flagged-suboptimal result rather than an OOM/hang. Predicts: the DOS surface of the planner. Bug class: an unbounded e-graph or memo table that takes down the process. Applied: Phase 6, Phase 9, Phase 13; P4, I18.
  • MM7 — The type system is the trust boundary. ValidatedDag is constructible only via validate(); downstream code assumes acyclicity by type, not by convention. Predicts: an unvalidated graph reaching the optimizer loops forever. Bug class: re-validation scattered everywhere, or its absence. Applied: Phase 1; P14, I1.
  • MM8 — Content addressing turns "recompute" into "reuse" for free. The same hash that dedupes a subgraph keys the result cache, so incremental re-planning is just diffing fingerprints and reusing the clean prefix. Predicts: re-plan cost scales with change size, not graph size. Bug class: re-optimizing the whole graph on a one-node edit. Applied: Phase 2, Phase 8; P5.
  • MM9 — Crash-only beats repair. Append-only logs + atomic-rename cache + truncate-torn-tail recovery mean kill -9 is always safe and there is never a repair tool to get wrong. Predicts: which failure leaves state corrupt (none, if the discipline holds). Bug class: an in-place mutation that a mid-write crash corrupts. Applied: Phase 8, Phase 11; P12, I14.

Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived from the System Constraints table (§4) with the formula shown. Symbols: N = task count, E = edges, B = e-node bytes, C = cores.

  • C1 — IR resident memory. mem ≈ N × 1.5 KiB (§4 IR resident size). N=100k → 100,000 × 1.5 KiB ≈ 150 MiB; the §4 ≤8 GiB ceiling at 100k leaves ~50× headroom for search structures.
  • C2 — E-graph memory at budget. Default budget 2M e-nodes (§4); at B≈64 B aligned (§4 cache line) → 2,000,000 × 64 B = 128 MiB for e-nodes alone; with ~2× overhead for memo/union-find → ~256 MiB, well under the 12 GiB hard abort.
  • C3 — Memo table size. DP memo default 5M entries (§4); each ≈ (32 B fp + 24 B (plan ptr,cost)) ≈ 56 B → 5,000,000 × 56 B ≈ 280 MiB before LRU eviction fires memo_pressure.
  • C4 — Topological-sort cost. Kahn is O(N+E); at the §4 validate target ≥1M nodes/s and E≈3N (typical), a 100k-node DAG sorts in ≈ (100k+300k)/1e6 s ≈ 0.4 ms — negligible vs the planning budget.
  • C5 — Canonicalization cost. Bottom-up BLAKE3 fingerprinting is one O(N) pass; §4 targets ≥500k nodes/s, so 100k nodes ≈ 200 ms worst case — the canon hashing the perf section flags as a hot stage.
  • C6 — Critical-path compute. Two linear passes over topo order; §4 critical-path ≥1M nodes/s → 100k nodes ≈ 0.1 ms forward + 0.1 ms backward ≈ 0.2 ms.
  • C7 — Reachability bitset memory. Dense N²/8 bytes: N=100k → (1e5)²/8 = 1.25 GB — exceeds budget, which is why §4/Phase 3 switch to roaring bitmaps above a threshold (the dense form is the rejected representation).
  • C8 — Max useful parallelism vs worker pool. Schedule parallelism is capped by min(ready-task width, pool concurrency). With pool concurrency=4 (example) and C=16 cores, a wide fan-out of 1,000 tasks runs 4 at a time → makespan ≈ (1000/4) × task_dur, the §4/Phase 7 concurrency bound — cores beyond 4 idle for that pool.
  • C9 — Service throughput. §4 ≥2,000 small plans/sec/core greedy × C=16 → ≈32,000 plans/sec peak; the bounded worker pool (= cores) and per-request budget keep this from becoming unbounded.
  • C10 — Replay-log growth. §4 ≤200 B/plan compressed; at 32k plans/sec sustained → 32,000 × 200 B = 6.4 MB/s → ~553 GB/day if every plan logged — so retention/sampling (Phase 11) is mandatory, not optional.
  • C11 — Cache amplification & footprint. §4 ≤1.2× result bytes; storing 1 TB of distinct results costs ≈ 1.2 TB on disk; dedup (content addressing) is what holds the 1.2× ceiling.
  • C12 — Coordination overhead at scale. §4/Phase 12 target ≤15% of planning wall at K=16 shards; boundary exchange is O(cut edges), so for a 1M-node DAG cut into 16 balanced shards with cut ratio ~1%, boundary edges ≈ 10k vs 1M interior → exchange cost ≈ 1% of interior planning, comfortably under the 15% knee.

Alternative Architectures (Roads Not Taken)

Fundamentally different designs for the same system; each with its winning regime, the real system that embodies it, and why this blueprint rejected it.

ALT-1 — Static ahead-of-time plan (this design's choice, contrasted with dynamic). The whole DAG is known up front; optimize and schedule once, emit a fixed ExecPlan.

  WDL → validate → canon → optimize → schedule → ExecPlan ──► executor
  (one planning pass; plan is immutable during execution)

Winning regime: bounded, materializable DAGs where inputs/sizes are estimable before run (ETL, build graphs). Embodied by: Bazel action graphs, classic SQL plans. Chosen here because it makes plans diffable, cacheable, and replayable. Rejected forms below.

ALT-2 — Dynamic / data-dependent DAG (online re-optimization). The graph's shape depends on runtime values (data-dependent fan-out, content-driven branching); the planner observes execution and re-plans mid-run.

  partial DAG → plan → execute step → observe sizes ─┐
        ▲                                            │
        └──────────── re-plan dirty region ◄─────────┘  (adaptive loop)

Winning regime: workflows whose structure or cardinalities are unknown until data arrives (adaptive query execution, ML pipelines with data-dependent branching). Embodied by: Spark Adaptive Query Execution, Dryad's runtime graph refinement. Rejected for Phase 0 because it forfeits the static plan's diffability/replayability and multiplies the cost-model and determinism burden; captured as the deferred online re-optimization (§9.9).

ALT-3 — Push-driven (eager dataflow) execution, no separate optimizer. Tasks fire as inputs arrive; the runtime, not a planner, decides ordering; optimization is emergent (operator fusion at the dataflow layer).

  source ─►[op]─►[op]─►sink     data pushed downstream as produced;
            ▲     ▲              scheduling = "run when input ready"
          fused at runtime

Winning regime: long-running streaming/timely-dataflow systems with unbounded inputs where a one-shot plan is meaningless. Embodied by: Naiad timely dataflow, Flink. Rejected because dagopt's domain is bounded, materializable artifacts (§1.2, Explicit Non-Goals); a push runtime gives up the cost-based plan search that is the project's entire point.

ALT-4 — Pull / demand-driven (lazy) scheduling. Nothing computes until a sink is demanded; the scheduler walks backward from outputs, computing only what is needed, memoizing by content.

  demand(sink) ─► need(filt) ─► need(load)   (walk backward;
       ◄── value ◄── value ◄── compute        compute on demand, memoize)

Winning regime: large graphs where only a subset of outputs is ever requested, with heavy caching (build systems, incremental compilers). Embodied by: Shake / Build Systems à la Carte's demand-driven rebuilds, Salsa/Adapton incremental frameworks. Rejected as the primary model because dagopt optimizes and schedules the whole requested plan for makespan up front — but its content-addressed cache and dirty-set re-planning (Phase 8) borrow the demand-driven memoization idea for the incremental path.
