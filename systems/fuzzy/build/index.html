⬜ Phase 0 — Repo Skeleton & Correctness Kernel §12

Objectives

Stand up the repo (§10), the pgrx extension scaffold, and the smallest possible correctness kernel: confident<text> round-trips through Postgres losslessly. No operators, no rewriter, no bgworker yet. Establishes the CI matrix (ADR-14) every later phase builds on.

Deliverable

CREATE EXTENSION fuzzy; CREATE TABLE t(val confident<text>); compiles and loads on Postgres 16 and 17; a value inserted and selected back is byte-identical to the input.

Acceptance
  • INSERT INTO t VALUES ('{"v":"hi","c":0.7,"s":"system"}'::confident<text>); SELECT * FROM t; returns the inserted tuple verbatim in conformance/fixtures/roundtrip_text_001.sql.
  • CI green on all 4 pinned Postgres minors (16.0, 16.6, 17.0, 17.2).
  • c = 1.4 insertion raises ERRCODE_FUZZY_INVALID_CONFIDENCE (fixture invalid_confidence_001.sql).
  • cargo pgrx test passes with 0 failures.
Fixtures
Fixture Purpose Expected Output
roundtrip_text_001.sql basic insert/select round-trip byte-identical tuple
invalid_confidence_001.sql c out of [0,1] ERRCODE_FUZZY_INVALID_CONFIDENCE
malformed_literal_001.sql truncated/garbage JSON literal parse error, no crash (T4)
version_skew_001.sql build against PG16 headers, run PG17 clean load or explicit incompatibility error
Pitfalls
  • Allocating with the global Rust allocator instead of PgMemoryContexts inside the type input function corrupts the executor arena (pgrx reference impl pitfall, §5) — debug via cargo pgrx test under valgrind; signal is a SIGSEGV inside palloc.
  • Forgetting #[pg_extern(immutable)] on pure scalar accessors defeats planner constant-folding — signal: unexpectedly slow EXPLAIN plans later (Phase 2, §14).
  • Skipping the length-prefix on variable-length T breaks TOAST compatibility for large text values — signal: corruption only above the TOAST threshold (~2KB), easy to miss in small fixtures.

⬜ Phase 1 — Parametric Types & Source Registry §13

Objectives

Extend confident<T> to all seven base types via generics (P1, §8.1); ship fuzzy_source (§11.2) with auto-registration; ship the pure scalar accessors value()/confidence()/source() (§8.3).

Deliverable

All 7 base types round-trip; SELECT confidence(val), source(val) FROM t runs against any of them; unregistered source handles auto-register with a logged warning.

Acceptance
  • 7/7 base types pass conformance/fixtures/roundtrip_<type>_001.sql (60 fixtures total across types × edge cases).
  • fuzzy_source row count increases by exactly 1 per distinct new handle, verified by source_registry_growth_001.sql.
  • confident<T> → T cast never silently drops without an explicit ::T — verified by cast_matrix_001.sql (I12).
Fixtures
Fixture Purpose Expected Output
roundtrip_<type>_001.sql (×7) per-base-type round-trip byte-identical
source_registry_growth_001.sql auto-registration count +1 row per new handle
cast_matrix_001.sql every confident<T>→U pair only declared casts succeed
unregistered_source_warning_001.sql first-use of unknown handle WARNING logged, write proceeds
Pitfalls
  • jsonb-typed T nested inside a confident<T> literal creates ambiguous parsing (is the outer or inner structure the JSON?) — resolved by requiring the outer literal's keys (v,c,s) to be reserved; debug signal is a parse error citing key collision. Root cause: literal-format grammar ambiguity (§8.1, P11).
  • uuid-typed T collides syntactically with s (also a uuid) in the wire tuple — mitigated by keeping v and s in strictly separate fixed-offset wire slots (§11.1), never overlapping encodings.
  • Auto-registration under concurrent first-writes from two backends races on fuzzy_source.handle uniqueness — mitigated by ON CONFLICT DO NOTHING semantics at the registry insert, detected via a conformance race-fixture run under pgbench -c 8.

⬜ Phase 2 — Comparison Operators & WHERE Rewriter §14

Objectives

Ship =, ==, ~, ordering operators (§8.3); ship the post-parse rewriter that desugars WITH confidence > X (ADR-23, P7); ship the EXPLAIN (FUZZY) skeleton (I5).

Deliverable

SELECT * FROM customers WHERE intent = 'churn' WITH confidence > 0.8 executes correctly on a 1M-row table; EXPLAIN (FUZZY) <query> prints the rewritten predicate.

Acceptance
  • 30 representative queries from the domain corpus (§8.7-style worked examples) parse and execute correctly (conformance/fixtures/rewriter_corpus_030.sql).
  • p50 latency for the query above ≤ 8 ms, p99 ≤ 45 ms at 1M rows (§4 M6/M7).
  • EXPLAIN (FUZZY) output for every corpus query textually contains the desugared predicate (I5 conformance diff, zero mismatches).
Fixtures
Fixture Purpose Expected Output
rewriter_corpus_030.sql 30 representative WITH confidence queries correct rows, matching plain-Postgres semantics on v
explain_fuzzy_diff_001.sql rewrite ↔ EXPLAIN(FUZZY) text match zero diff (I5)
operator_class_index_001.sql B-tree index usable on value index scan chosen by planner, not seq scan
hook_chain_coexist_001.sql Fuzzy hook alongside a second dummy extension's hook both hooks fire, in registration order
Pitfalls
  • Registering the post-parse hook without chaining to a previously-installed hook silently disables any other extension's post-parse behavior — root cause: hook-chain pointer overwritten instead of composed; debugging method: load a second dummy extension in CI and assert both fire (fixture above); signal is the dummy extension's side effect silently vanishing.
  • Rewriting WITH confidence > X inside a subquery whose outer query also has a WITH clause (Postgres CTE syntax) creates a grammar collision — mitigated by scoping the clause-modifier detection to immediately follow a WHERE/ON token, never a bare WITH at statement start.
  • Operator class registration missing the RECHECK flag on a lossy comparison causes incorrect index-only-scan results — signal: correct output only when enable_indexscan is off, wrong results when on.

⬜ Phase 3 — Join Propagation Algebra (MIN + PRODUCT) §15

Objectives

Ship two of the three locked propagation modes (§8.4): MIN (default) and PRODUCT. Planner hook attaches propagation metadata to join nodes over confident<T> columns.

Deliverable

A 3-way join over confident<T> columns produces correct propagated confidence under both MIN and PRODUCT, selectable via WITH PROPAGATION =.

Acceptance
  • conformance/fixtures/join_propagation_min_020.sql and ..._product_020.sql: 20 fixtures each, all pass exactly.
  • Join cost ≤ 1.4× plain join at 10M rows (M4, §4) verified by benchmarks/join_10m.rs.
  • ERRCODE_FUZZY_AMBIGUOUS_PROPAGATION raised on conflicting column defaults with no explicit WITH PROPAGATION = (I4), fixture ambiguous_propagation_001.sql.
Fixtures
Fixture Purpose Expected Output
join_propagation_min_020.sql 3-way joins, MIN mode c_out = min(...) exact
join_propagation_product_020.sql 3-way joins, PRODUCT mode c_out = product(...) exact
ambiguous_propagation_001.sql conflicting column defaults, no override I4 error raised
join_10m_perf.sql 10M-row join benchmark ≤ 1.4× plain-join cost
Pitfalls
  • Treating PRODUCT propagation as valid for correlated (non-independent) sources silently understates true confidence — root cause: PRODUCT assumes independence (Dalvi & Suciu 2004, §5); mitigation is documentation + a linter warning (Phase 9, §21) when two joined columns share the same source handle pattern.
  • Propagation-metadata plan nodes not surviving EXPLAIN's plan-cache reuse path causes a stale mode to apply after a column's DEFAULT PROPAGATION changes — debug signal: changing config has no effect until DISCARD PLANS.
  • Nested joins (3+ tables) compounding MIN incorrectly (taking min of mins is associative, so this is actually safe) versus PRODUCT chains losing precision on many multiplications — mitigated by computing in f64 with a documented precision floor.

⬜ Phase 4 — Bayesian Propagation & Reliability Priors §16

Objectives

Ship the third propagation mode, BAYESIAN (§8.4.3); wire reliability_a/reliability_b priors into fuzzy_source (§11.2) and expose an admin function to set them.

Deliverable

WITH PROPAGATION = BAYESIAN over two columns with configured priors produces output confidence matching the closed-form posterior mean.

Acceptance
  • Synthetic correlated-source workload matches the closed-form Beta-binomial mean to ±0.001 (conformance/fixtures/bayesian_closed_form_015.sql, 15 cases).
  • fuzzy_source_set_reliability rejects α ≤ 0 or β ≤ 0 (fixture reliability_validation_001.sql).
  • BAYESIAN join cost ≤ 2.0× plain join at 10M rows (M5, §4).
Fixtures
Fixture Purpose Expected Output
bayesian_closed_form_015.sql posterior mean vs. hand-computed closed form match to ±0.001
reliability_validation_001.sql invalid α/β rejected error, no write
bayesian_join_10m_perf.sql 10M-row BAYESIAN join ≤ 2.0× plain-join cost (M5)
explain_fuzzy_mode_diff_001.sql EXPLAIN(FUZZY) shows BAYESIAN mode text match, no mismatch
Pitfalls
  • Treating reliability_a/b as directly-writable columns instead of routing all changes through the admin function violates I10 — mitigated by revoking direct UPDATE grants on fuzzy_source at CREATE EXTENSION time (ADR-17); signal is an audit-log gap (fully closed once Phase 8's fuzzy_audit_log lands, §20).
  • Floating-point accumulation error across many BAYESIAN joins in a chain — mitigated by computing in f64 and rounding only at final output, with a documented ±0.001 tolerance band matching the acceptance criterion itself.
  • Confusing "confidence" with "probability of the ground truth" when picking priors — root cause is the calibration gap identified by Niculescu-Mizil & Caruana 2005 (§5); mitigation is a documentation callout, not a code fix (this is a modeling responsibility of the caller, not a Fuzzy defect).

⬜ Phase 5 — Decay Engine (bgworker) §17

Objectives

Ship fuzzy_decay, the throttled, cooperatively-cancellable background worker (ADR-08, P13) that applies configured decay functions (§8.6-adjacent, §11.4) to confident<T> columns on a schedule, keeping the read path O(1) (I8).

Deliverable

A confident<text> column declared DECAY half_life(days => 14) shows confidence reduced by ~50% after the sweep simulates 14 days' elapsed time; a 100M-row sweep completes within budget.

Acceptance
  • half_life(14) column: confidence at simulated t+14d is 0.5 × c_original ±1% (conformance/fixtures/decay_half_life_001.sql).
  • 100M-row sweep completes in < 4 hours at default throttle (M8, §4), verified by benchmarks/decay_sweep_100m.rs.
  • bgworker cancellation on SIGTERM drains within < 2 s (I9, fixture decay_cancel_drain_001.sql).
  • CPU usage stays ≤ 1 core sustained during a sweep (M9, §4).
Fixtures
Fixture Purpose Expected Output
decay_half_life_001.sql half-life primitive correctness c halved ±1% at t+14d
decay_linear_001.sql linear-decay primitive linear ramp to 0 at configured horizon
decay_step_001.sql step-function primitive exact factor multiply at threshold
decay_sweep_100m_perf.sql 100M-row sweep timing < 4 h wall clock
decay_cancel_drain_001.sql SIGTERM mid-sweep drains < 2 s, resumable, no partial row corruption
Pitfalls
  • A sweep that computes decay as a running multiplicative delta (rather than from t and elapsed time each pass) compounds error across repeated sweeps — root cause: confusing "decay is a function of elapsed time" (correct, I7) with "decay is a mutation applied repeatedly" (wrong); debugging signal is confidence drifting below the decay function's true curve after multiple sweep cycles.
  • Missing the cancellation check inside a tight per-row loop stalls checkpoint completion — signal: pg_stat_activity shows a long-running bgworker blocking CHECKPOINT; root cause traced to I9's ≤10,000-row check interval not being honored.
  • Throttle GUC misconfigured to 0 (meant to mean "unlimited") is ambiguous with "disabled" — resolved by a dedicated fuzzy.decay_enabled boolean GUC instead of overloading the rate.

⬜ Phase 6 — Aggregates & IS DECAYED §18

Objectives

Ship confident_avg, confident_max, confident_count, confident_consensus (§8.5); ship the IS DECAYED predicate (§8.3) reading the column threshold from fuzzy_column_config.threshold (§11.3); close the HAVING-clause gap deferred from Phase 2 (§14.8).

Deliverable

SELECT confident_consensus(intent) FROM customers GROUP BY segment returns the modal value per segment with correct consensus confidence; WHERE ... HAVING confident_avg(c) IS DECAYED parses and executes.

Acceptance
  • Consensus confidence formula Σc_i[agree] / Σc_i[all] verified exact on 25 synthetic groups (conformance/fixtures/consensus_025.sql).
  • Parallel aggregate plan chosen by the planner for a 10-worker parallel scan (parallel_agg_001.sql, EXPLAIN shows Parallel Aggregate).
  • HAVING ... IS DECAYED executes without falling back to sequential scan-only plans (having_decayed_001.sql).
  • Conformance suite reaches 200/200 green (cumulative across all prior phases plus this phase's additions).
Fixtures
Fixture Purpose Expected Output
consensus_025.sql modal value + consensus confidence exact formula match
confident_avg_weighted_010.sql value-weighted mean matches hand-computed weighted mean
parallel_agg_001.sql parallel-safe aggregate plan planner selects Parallel Aggregate
having_decayed_001.sql HAVING ... IS DECAYED correct groups filtered
Pitfalls
  • Marking an aggregate parallel-safe when its accumulator secretly depends on row order (e.g., "first observed" tie-breaking in confident_max) produces nondeterministic results under parallel workers — root cause is violating P9; mitigation is an explicit tie-break rule (lowest source_id wins ties) making the accumulator truly commutative.
  • confident_count(a) WITH confidence > k interacting with the Phase 2 rewriter's clause-modifier scoping can double-desugar inside an aggregate argument — mitigated by restricting clause-modifier detection to top-level WHERE/HAVING/ON, never inside an aggregate's argument list.
  • Floating-point summation order differences between sequential and parallel plans causing consensus-confidence values to differ in the last bit — mitigated by documenting a tolerance band (matches the ±0.001 precedent from Phase 4, §16.4).

⬜ Phase 7 — Conflict Log & Resolution Modes §19

Objectives

Ship fuzzy_conflict_log (§11.5, P10) as an append-only store: when track_conflicts = true on a column (§11.3), a second write to the same (row, column) appends rather than overwrites (I6). Ship the MAX_CONFIDENCE, NEWEST, BAYESIAN_FUSE resolution modes computing the canonical read-path value.

Deliverable

Two conflicting writes to the same (row, column) both land in fuzzy_conflict_log; reads return the canonical value per the configured resolution mode; observations(col) lists the full history.

Acceptance
  • Write amplification for a track_conflicts column stays < 2× plain UPDATE (M10, §4) — kill-trigger threshold at ≥5× (FM-6, §23), verified by benchmarks/conflict_write_amp.rs.
  • All three resolution modes verified exact on 50 fixtures (conformance/fixtures/resolution_modes_050.sql).
  • Concurrent-write race fixture under pgbench -c 16 produces zero lost observations (conflict_race_016.sql).
  • Retention compaction (fuzzy_conflict_compact()) preserves the currently-canonical observation under every resolution mode (compaction_preserves_canonical_001.sql).
Fixtures
Fixture Purpose Expected Output
resolution_modes_050.sql 50 cases across 3 modes exact canonical value per mode
conflict_write_amp.sql write-amplification benchmark < 2× plain UPDATE
conflict_race_016.sql 16 concurrent writers, same row all observations logged, none lost
compaction_preserves_canonical_001.sql compact then re-read canonical value unchanged
Pitfalls
  • Implementing the conflict-log append as an AFTER trigger with DEFERRABLE INITIALLY DEFERRED breaks I6 if the outer transaction can commit the base row without the log row committing atomically together under certain isolation levels — mitigated by using a non-deferrable AFTER trigger in the same transaction, verified by conflict_race_016.sql's abort-mid-transaction variant.
  • BAYESIAN_FUSE naively re-deriving priors from raw observation counts (rather than each source's registered (α, β), §11.2) double-counts evidence — root cause: conflating "number of observations" with "source reliability"; fixed by fusing through fuzzy_source.reliability_a/b, not observation counts.
  • Retention compaction run concurrently with an in-flight NEWEST-mode read can transiently disagree on the canonical row — mitigated by compaction taking a ROW EXCLUSIVE lock on the affected log rows for its duration.

⬜ Phase 8 — Feedback API & Reliability Update §20

Objectives

Ship fuzzy_feedback (§11.5) and the SQL admin function that records a human (or higher-trust source) correction and updates the originating source's (α, β) Beta reliability prior (§8.4.3) via the posterior update rule.

Deliverable

fuzzy_apply_feedback(...) records a correction; the originating source's reliability prior updates via the Beta posterior rule; subsequent BAYESIAN/BAYESIAN_FUSE queries reflect the updated prior.

Acceptance
  • Property-based test confirms the Beta posterior update preserves α, β > 0 and α/(α+β) ∈ [0,1] across 1,000 randomized feedback sequences (conformance/fixtures/feedback_posterior_property_1000.sql).
  • A feedback event that disagrees with a source's prior observation measurably lowers that source's α/(α+β) ratio within the same transaction (feedback_disagree_lowers_reliability_001.sql).
  • fuzzy_audit_log (new in this phase) records every feedback event and every reliability_a/b change with 100% coverage (audit_coverage_001.sql).
Fixtures
Fixture Purpose Expected Output
feedback_posterior_property_1000.sql property-based posterior invariants α,β>0, ratio bounded, 1000/1000 pass
feedback_disagree_lowers_reliability_001.sql disagreement lowers reliability α/(α+β) strictly decreases
audit_coverage_001.sql every feedback + reliability change logged 100% coverage, zero gaps
feedback_js_client_001.sql fuzzy-js typed feedback call round-trips through fuzzy_apply_feedback
Pitfalls
  • Applying feedback with weight unbounded lets a single correction dominate a well-established source's prior — root cause: no ceiling on weight; mitigated by a documented recommended range (0.1–5.0) and a WARNING above 10.0, not a hard cap (P5- style "opt-in but obvious" philosophy applied to feedback weight).
  • Feedback events racing with an in-flight BAYESIAN_FUSE read can read a pre-update prior — acceptable under standard MVCC snapshot semantics, documented as expected (not a bug) since the read simply reflects a consistent prior transaction snapshot.
  • Forgetting to route the correction itself through the conflict log (§19) means observations(col) under-reports history post-feedback — fixed by making fuzzy_apply_feedback internally call the same append path as a normal write.

⬜ Phase 9 — Performance Hardening & Client Library §21

Objectives

Verify every §4 budget under automated benchmarks; ship fuzzy-py (thin psycopg3 + SQLAlchemy client); close the Phase 0-deferred fuzzing gap (§12.9) with cargo-fuzz in CI; harden the Postgres-version compatibility matrix ahead of the next major.

Deliverable

All ten §4 budgets pass automated benchmarks in CI; pip install fuzzy-py gives a typed Confident[str] class round-tripping through psycopg3; cargo-fuzz runs on every PR with zero crashing inputs found over a 24-hour corpus run.

Acceptance
  • 10/10 §4 budgets (M1–M10, §28) pass in the automated benchmark suite, gating merge (benchmarks/budget_gate.rs).
  • cargo-fuzz 24-hour run against the type input function: zero crashes, zero sanitizer violations (fuzz/corpus_24h_report.json).
  • A toy CRM app writing/reading a confident<text> column via fuzzy-py round-trips correctly (clients/python/tests/test_roundtrip.py, referenced as a fixture-equivalent integration test).
  • Build matrix green on the current two Postgres majors' latest two minors each (P8, version_matrix_001.yml).
Fixtures
Fixture Purpose Expected Output
budget_gate.rs all 10 M-targets 10/10 pass

test_roundtrip.py fuzzy-py round-trip value preserved end-to-end
version_matrix_001.yml multi-PG-version build green on all pinned minors
Pitfalls
  • Benchmarking on a warm cache only (never a cold-start measurement) overstates steady-state performance and misses first-query latency regressions — mitigated by a dedicated cold-start benchmark variant.
  • cargo-fuzz corpus seeded only with well-formed literals finds nothing — mitigated by seeding with the Phase 0 malformed-input fixtures (§12.5, §12.8) as the initial corpus.
  • fuzzy-py's SQLAlchemy TypeDecorator silently coercing None to a zero-confidence tuple instead of SQL NULL breaks NULL-vs-zero-confidence semantics (§12.8 edge case) — mitigated by explicit NULL passthrough in the adapter.
