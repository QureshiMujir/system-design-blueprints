8 — Fuzzy

Project Number: 8

Project Name: Fuzzy

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Fuzzy is a PostgreSQL 16+ extension that adds a first-class probabilistic column type, confident<T>, and the SQL surface (operators, a query rewriter, a planner hook, and a background decay worker) needed to store, query, join, and age model-derived observations with an explicit confidence, source, and timestamp — inside the transactional row store, not bolted on in application code. It targets AI-native applications (agent memory, AI CRMs/CDPs, OSINT/intelligence aggregation) where most written data is inferred rather than typed by a human, and where confidence, provenance, and staleness are today reimplemented ad hoc, per team, on top of plain columns and JSON sidecars.

Phase-0 deliverable (in-scope), as buildable modules/crates:

  1. fuzzy_types — the confident<T> parametric type: wire format, input/output functions, cast rules.
  2. fuzzy_ext — the pgrx-based extension crate wiring fuzzy_types into Postgres (CREATE EXTENSION fuzzy).
  3. conformance/ — a fixture-driven correctness harness exercised by every later phase.
  4. fuzzy_source (schema only in Phase 0; populated from Phase 1) — the source registry table.

System boundaries:

  • Provides: a typed uncertain-value column, confidence-aware predicates and joins, a locked join-propagation algebra (§8.4), a decay engine (§17), and — from Phase 7/8 — an append-only conflict log and a feedback API that re-weights source reliability.
  • Delegates: transactions, WAL, replication, buffer management, and query execution to PostgreSQL itself. Fuzzy hooks the planner/executor (ADR-23); it does not replace them.
  • Does NOT provide: vector similarity search (delegate to pgvector, ADR-04), model serving, probabilistic-programming inference (MCMC/variational solvers), or a Postgres fork.

Non-goals: schema-on-read/dynamic typing (confident<T> is parametric over one fixed T per column, §8.1); multi-master replication of confidence state (PhaseDeferred("§35")); a bespoke wire protocol (Fuzzy rides libpq, ADR-06).

Deployment model: a single .so + .control extension installed into an existing PostgreSQL 16+ cluster via CREATE EXTENSION fuzzy;, plus one fuzzy_decay background worker per opted-in database. No separate server process through Phase 9 (a hosted control plane is explicitly out of blueprint scope — PhaseDeferred("§35")).

Target users/operators: backend engineers embedding model output into Postgres; database operators running the bgworker and monitoring fuzzy_stat_* views; downstream SQL authors writing WITH confidence > X predicates.

What later phases unlock: Phase 3 (§15) unlocks confidence-aware joins; Phase 5 (§17) unlocks aging/decay; Phase 7 (§19) unlocks multi-writer conflict history; Phase 8 (§20) unlocks a feedback-driven reliability loop. Each phase is a strict superset — none weakens an earlier phase's invariants (I1, I2, §7).

Recommended language: Rust via pgrx (ADR-01). Rationale: pgrx gives memory-safe bindings to Postgres's C ABI (type I/O, planner hooks, bgworkers) without hand-rolling palloc-aware unsafe C for every function; the ecosystem (pgvector, TimescaleDB, citus) has converged on Rust or C for exactly this reason (§5 Reference Implementations). Rejected languages: pure C (loses memory safety on a security-sensitive parsing surface — the type input function parses untrusted client bytes, §8.7); PL/pgSQL-only (cannot hook the planner or run a bgworker); Zig (no mature Postgres FFI ecosystem as of 2026).

Prerequisites: PostgreSQL internals (type system, extended query protocol, planner/executor split, bgworker API); Bayesian probability (Beta-binomial conjugacy, §5 Books); belief-combination theory (Dempster-Shafer, deferred, §8.4.4); Rust ownership/FFI safety.

Estimated timeline: Phase 0 — repo skeleton + confident<text> correctness kernel, 2 weeks. Full system (Phase 0 through Phase 9, §12–§21) — ~11 months at one senior engineer with AI-assisted execution.

Deferred features (flagged, resolved in the Deferred Features Register, §35): DEMPSTER-SHAFER propagation PhaseDeferred("§35"); multi-master replicated confidence PhaseDeferred("§35"); on-prem governance/classification plane PhaseDeferred("§35"); hosted lineage explorer UI PhaseDeferred("§35").

2. Why Build This

Fuzzy teaches the systems knowledge that sits at the intersection of three fields most engineers only ever touch separately: extensible database internals (how a type, operator, and planner hook actually plug into a production RDBMS), probabilistic data management (possible-worlds semantics, belief propagation, calibration), and production Rust-against-C-ABI engineering (safe wrappers over palloc, MemoryContext, and the extended query protocol). Few projects force all three at once.

Why it matters architecturally: every AI-native application today re-derives the same primitive — "this value came from a model, here is how sure it is, and it gets less sure over time" — in application code, badly, once per team. Historically, Postgres itself became dominant by proving that a general-purpose relational engine could absorb what looked like a bespoke need (geometric types, full-text search, JSON) as a first-class, extensible type. Fuzzy is a bet on the same absorption pattern for uncertainty.

Engineering muscles built: designing a wire format that must remain backward-compatible forever (§9 ADR-05); writing a planner/executor hook without breaking cost-based optimization; building a background worker that is throttleable, cancellable, and crash- isolated; reasoning about belief combination (MIN / PRODUCT / BAYESIAN, §8.4) as an algebra with real rejected alternatives, not a single "right answer."

Cross-links to sibling systems (by name): shares extensibility DNA with pgvector (new type + operator class + index support) and TimescaleDB/citus (bgworker + planner-hook patterns); shares domain DNA with academic probabilistic databases Trio and MayBMS (§5 Papers, §31 Comparative Architecture); shares calibration concerns with any ML-serving system that reports a confidence score.

Calibration value: after building Fuzzy, an engineer can look at any system that emits a "confidence" number and immediately ask the right questions — is this calibrated (Niculescu-Mizil & Caruana 2005, §5), is it independent evidence or correlated evidence (§8.4.2 vs §8.4.3), what happens when two of them disagree (§19 Conflict Log)?

What Mastery Looks Like (after completing all phases):

  • Can implement a new Postgres parametric type (I/O functions, cast rules, operator class) from scratch — cemented in Phase 0–1 (§12–§13).
  • Can write a post-parse query rewriter that desugars new syntax without forking the parser, and knows exactly when that stops being sufficient — Phase 2 (§14), ADR-23.
  • Can design and defend a belief-propagation algebra with explicit, named rejected alternatives — Phase 3–4 (§15–§16).
  • Can build a throttled, crash-isolated Postgres background worker with cooperative cancellation — Phase 5 (§17).
  • Can reason about append-only conflict logs and their resolution-mode tradeoffs under concurrent writers — Phase 7 (§19), Gray et al. 1976 (§5).
  • Can close a feedback loop that updates a Bayesian reliability prior from human corrections and verify it against the closed-form posterior — Phase 8 (§20).
  • Can defend every locked decision against ≥4 real competing systems and name the exact regime where each competitor's choice would have won instead — §31 Comparative Architecture, §34 Alternative Architectures.

Boxes, one paragraph each.

Client. Any libpq-speaking client, or fuzzy-py (Phase 9, §21). No trust is placed in the client beyond standard Postgres role auth; the type input function must be robust to adversarial byte streams (§8.7, T4).

fuzzy_planner. Two hooks: a post-parse rewriter (desugars WITH confidence > X into plain boolean predicates, ADR-23) and a planner hook (attaches a propagation mode, §8.4, to each join over confident<T> columns). Both are pure, side-effect-free, and inspectable via EXPLAIN (FUZZY) (P7, I5).

Executor / fuzzy_types. The operator implementations (confident_eq, confident_join, aggregates, §8.5) run in the standard executor, no custom execution nodes. They read/write confident<T> values through the type's I/O functions against the heap.

fuzzy_conflict (Phase 7+). When a column has track_conflicts = true, writes append to fuzzy_conflict_log instead of overwriting; the read path computes the canonical value per the column's resolution mode.

fuzzy_feedback (Phase 8+). SQL admin functions that record a correction and update the originating source's Beta(α, β) reliability prior (§8.4.3, Gelman et al. 2013).

fuzzy_decay bgworker. One process per database that opted in, walking columns with a configured decay function on a throttled schedule, cooperatively cancelled on checkpoint or shutdown (ADR-08, I9). Crashes here never take down a backend (I11).

fuzzy_source registry. Maps a source_id to a handle, kind, and (α, β) reliability prior consumed by BAYESIAN propagation (§8.4.3) and updated by feedback (Phase 8, §20).

All later sections (Domain Model §8, Repository Layout §10, Core Schema §11, and every phase) name exactly these boxes and no others; a module introduced later must be traced back to one of them or is out of scope (§1 non-goals).

6. Design Principles

  1. P1 — Postgres-native, always. Fuzzy is an extension, never a fork or wrapper. Tradeoff: caps what is possible to whatever the extension API exposes. Operational implication: every phase's exit criterion is buildable via pgrx/PGXS. Violating it (forking Postgres) forfeits the entire "I already run Postgres" adoption moat (§2).
  2. P2 — The join-propagation algebra is locked once shipped (§8.4). Tradeoff: new propagation modes ship additively behind WITH PROPAGATION =, never as a silent default change. Violating it breaks every downstream query that depends on today's default (MIN).
  3. P3 — Confidence and source are metadata, never a substitute for access control over the value. Tradeoff: Fuzzy must not become a covert channel for value exfiltration via confidence-derived side channels (T5). Violating it turns a monitoring feature into a security bug.
  4. P4 — Every confident<T> write has a source; anonymous writes are rejected. Tradeoff: adds a mandatory registry lookup on every write path (§28 M-cost). Violating it collapses the entire feedback loop (Phase 8, §20) which depends on attributable reliability priors.
  5. P5 — Decay is opt-in, but once configured, applied consistently and only by the bgworker — never silently at read time. Tradeoff: reads stay O(1); decayed values can lag the sweep schedule by up to one throttle interval. Violating it (computing decay inline at read time) reintroduces read-path variance the whole design avoids (I8).
  6. P6 — OSS core is permanent and unconditional. Tradeoff: monetization must live entirely outside fuzzy_types/fuzzy_ext/fuzzy_decay/fuzzy_conflict/fuzzy_feedback. Violating it breaks the adoption thesis that the moat is the algebra, not a paywall.
  7. P7 — No silent query rewriting. Every transformation fuzzy_planner performs is visible via EXPLAIN (FUZZY) (§8.6). Tradeoff: extra bookkeeping to record rewrite provenance per plan node. Violating it makes the system undebuggable in production — the single highest-cost failure mode for any query rewriter (FM-2).
  8. P8 — Postgres-version compatibility is a first-class deliverable, not an afterthought. Tradeoff: every phase carries CI cost across ≥2 major Postgres versions (§26). Violating it (targeting one pinned minor) creates T2/FM-1 risk that compounds every release.
  9. P9 — Determinism over cleverness. Same inputs + same propagation mode ⇒ same output confidence, always. Tradeoff: rules out randomized/sampling-based propagation shortcuts even where they would be faster. Violating it makes conformance fixtures (N.5 of every phase) meaningless.
  10. P10 — Conflicts are stored, never silently overwritten (Phase 7+). Tradeoff: write amplification (§4, M10) in exchange for auditability. Violating it destroys the provenance chain the feedback loop (§20) depends on.
  11. P11 — The type input function is a hostile-input boundary. Tradeoff: every base T specialization pays a validation cost on write (§8.1). Violating it turns a parsing bug into a backend crash (T4, FM-3).
  12. P12 — Every propagation mode names its rejected alternatives and the regime where each wins (§9 ADR 6th column). Tradeoff: slower ADR authoring. Violating it produces an algebra nobody can reason about outside the original author's head.
  13. P13 — The bgworker is cooperatively cancellable and crash-isolated from backends. Tradeoff: sweep loops must check a cancellation flag at bounded intervals, adding branch overhead (§28 M9). Violating it risks stalling checkpoints or crashing user backends on a decay bug (FM-5).
  14. P14 — Wire format changes are additive only (§9 ADR-05). Tradeoff: old field-slots can never be repurposed, only appended after. Violating it breaks rolling-upgrade compatibility (§25) for every existing confident<T> column on disk.

8. Domain Model

8.1 The confident<T> Type (formal)

For T ∈ { int, bigint, float8, text, boolean, uuid, timestamptz, jsonb }:

confident<T> ≡ (
    v          : T,                    -- the value
    c          : float8 ∈ [0.0, 1.0],  -- confidence (I1)
    s          : source_id (uuid),     -- FK → fuzzy_source (I2)
    t          : timestamptz,          -- observation time, default now()
    decay_ref  : decay_id NULL,        -- FK → fuzzy_decay_def
    conflict_ix: bigint NULL           -- FK → fuzzy_conflict_log (Phase 7+)
)

Wire format: 4-byte length prefix + packed binary tuple (P14, ADR-05). Text I/O literal: '{"v": "churn", "c": 0.83, "s": "model:gpt-4o-2025-09"}'. Fixed overhead: 62 bytes/row (§4), variable part is T's own encoding.

8.2 Cast Rules

  • confident<T> → T: allowed, yields v; confidence explicitly discarded (I12, P3) — never implicit.
  • T → confident<T>: allowed only via :: confident<T> SOURCE 'literal:default' (I2).
  • confident<T> → confident<U>: allowed iff T → U is a known Postgres cast; c, s, t carry through unchanged.
  • Aggregate casts: confident<T> columns aggregate to confident<T> per §8.5.

8.3 Comparison and Filter Operators

Operator Definition Notes
a = b a.v = b.v confidence ignored
a == b a.v = b.v ∧ |a.c − b.c| ≤ ε (default ε = 0.05) confidence-aware eq
a ~ b a.v = b.v, output c = min(a.c, b.c) locked MIN propagation, §8.4.1
a > x WITH confidence > k rewrites to a.v > x ∧ a.c > k desugared by fuzzy_planner (ADR-23)
confidence(a) / source(a) / value(a) scalar accessors pure functions
a IS DECAYED true iff latest sweep put a.c below the column threshold Phase 5, §17

WITH confidence > X is a clause modifier on WHERE/ON, desugared in the post-parse hook (P7, I5) — this is why Fuzzy does not fork the parser in Phase 0–9 (ADR-23).

8.4 Join Propagation Algebra (LOCKED)

Chosen per-join via WITH PROPAGATION = MODE, or per-column DEFAULT PROPAGATION.

8.4.1 MIN (default)

c_out = min(c_left, c_right). Conservative, monotonic; matches naive intuition about weakest-link confidence. Provenance framing: a semiring-style min-combination (Green et al. 2007, §5).

8.4.2 PRODUCT (independent evidence)

c_out = c_left × c_right. Correct when the two confidences are independent probabilities of correctness (Dalvi & Suciu 2004, §5).

8.4.3 BAYESIAN (beta-binomial, locked variant)

c_out = (α_left + α_right) / (α_left + β_left + α_right + β_right), where each input's (α, β) is the effective-sample-size Beta prior stored per source in fuzzy_source (Gelman et al. 2013, §5). Used when sources have known reliability priors.

8.4.4 DEMPSTER-SHAFER — deferred (PhaseDeferred("§35"))

Combining belief masses via Dempster's rule of combination (Dempster 1967, Shafer 1976, §5) requires a conflict-mass normalization step that is computationally heavier and only pays off for governance-tier, multi-source-fusion use cases; not in the Phase 0–9 algebra.

8.4.5 Ambiguity resolution

If two joined columns declare conflicting DEFAULT PROPAGATION, the planner raises ERRCODE_FUZZY_AMBIGUOUS_PROPAGATION (I4) unless the query specifies WITH PROPAGATION = explicitly.

8.5 Aggregate Propagation

  • confident_avg(a) → value-weighted mean; output c = mean(c_i).
  • confident_max(a) → row with max v; output c = that row's c.
  • confident_count(a) WITH confidence > k → counts rows clearing the threshold only.
  • confident_consensus(a) → modal v; output c = Σc_i[agree] / Σc_i[all].

8.6 EXPLAIN (FUZZY)

Reports: the rewritten query (I5), chosen propagation mode per join, confidence-threshold predicate hits, and decay state at plan time. Backed by fuzzy_stat_columns, fuzzy_stat_propagation, fuzzy_stat_decay_runs (§11.6).

8.7 Worked Example — Write, Join, Decay

-- write (two independent sources observe the same customer's intent)
INSERT INTO customers(id, intent) VALUES
  (42, '{"v":"churn","c":0.90,"s":"model:gpt-4o-2025-09"}'),
  (42, '{"v":"churn","c":0.60,"s":"model:claude-haiku"}');   -- Phase 7: 2nd write → conflict log

-- confidence-aware join, explicit propagation
SELECT c.id FROM customers c JOIN risk_flags r ON c.id = r.id
  WITH PROPAGATION = PRODUCT
WHERE r.flag = 'high' WITH confidence > 0.5;
-- c_out = c.intent.c * r.flag.c, only rows clearing 0.5 pass

-- 14 days later, half_life(14) decay sweep halves the first observation's confidence
-- fuzzy_decay: c := c * 0.5^(elapsed_days / half_life_days)  ⇒ 0.90 → 0.45

8.8 Malformed-Input Example

INSERT INTO customers(intent) VALUES ('{"v":"churn","c":1.4,"s":"model:x"}') — c = 1.4 violates I1; the type input function raises ERRCODE_FUZZY_INVALID_CONFIDENCE before any heap write, transaction aborts (T4, FM-3).

8.9 Failure-Path Example

fuzzy_decay crashes mid-sweep on database db1 (e.g. OOM on a pathological jsonb payload). Postmaster detects the bgworker exit, logs a restart event, relaunches within the RTO budget (< 60 s, I11, FM-5); in-flight row updates from the crashed sweep are not partially applied because each row's decay write is a single-row UPDATE committed individually — worst case is a resumed sweep re-visiting a handful of already-decayed rows, which is idempotent (decay is a pure function of t and elapsed time, not a running delta).

14. Phase 2 — Comparison Operators & WHERE Rewriter

14.1 Objectives

Ship =, ==, ~, ordering operators (§8.3); ship the post-parse rewriter that desugars WITH confidence > X (ADR-23, P7); ship the EXPLAIN (FUZZY) skeleton (I5).

14.2 Detailed Implementation Steps

Operator registration + operator class so B-tree indexing works on value with c as payload, not key (avoids indexing on a mutable-by-decay field, foresight for Phase 5, §17). Post-parse hook (C shim → Rust, ADR-01) intercepts the WITH confidence > X clause modifier before the standard parser hands off to the planner — citing Citus's hook-composition lesson (§5 Reference Implementations) to avoid breaking other extensions' post_parse_analyze_hook chains. Desugars to confidence(col) > X predicate (I5 traceability requirement: this exact rewrite must appear verbatim in EXPLAIN (FUZZY) output). EXPLAIN (FUZZY) skeleton hooks ExplainOneQuery to print the rewritten SQL string.

  • 30 representative queries from the domain corpus (§8.7-style worked examples) parse and execute correctly (conformance/fixtures/rewriter_corpus_030.sql).
  • p50 latency for the query above ≤ 8 ms, p99 ≤ 45 ms at 1M rows (§4 M6/M7).
  • EXPLAIN (FUZZY) output for every corpus query textually contains the desugared predicate (I5 conformance diff, zero mismatches).

14.6 Pitfalls

  • Registering the post-parse hook without chaining to a previously-installed hook silently disables any other extension's post-parse behavior — root cause: hook-chain pointer overwritten instead of composed; debugging method: load a second dummy extension in CI and assert both fire (fixture above); signal is the dummy extension's side effect silently vanishing.
  • Rewriting WITH confidence > X inside a subquery whose outer query also has a WITH clause (Postgres CTE syntax) creates a grammar collision — mitigated by scoping the clause-modifier detection to immediately follow a WHERE/ON token, never a bare WITH at statement start.
  • Operator class registration missing the RECHECK flag on a lossy comparison causes incorrect index-only-scan results — signal: correct output only when enable_indexscan is off, wrong results when on.

14.7 Performance Concerns

The rewriter must not force a full replan on every query — cached rewrite decisions keyed by the parsed query's fingerprint keep the P7-mandated inspectability cost near-zero at steady state (M3 budget, §4/§28).

14.8 Edge Cases

WITH confidence > X inside a HAVING clause (not just WHERE/ON) — Phase 2 scope explicitly excludes HAVING, documented as a known gap and closed in Phase 6 alongside aggregates (§18); confidence predicate on a NULL confident<T> column value — three- valued logic preserved, WITH confidence > X on NULL yields NULL, not false; negative X in WITH confidence > X — always true since c ≥ 0 (I1), a documented, intentional non-error.

14.9 Failure Analysis

If the rewriter mis-desugars a predicate, silent wrong-answer queries are the failure mode — the worst class, because no error is raised. Detection relies entirely on the conformance corpus (14.5) since there is no runtime self-check; containment is scoped by keeping the rewriter's grammar surface deliberately small (only one clause modifier form, ADR-23); recovery is a patch release with an expanded fixture covering the missed case.

fuzzy_stat_propagation begins tracking ambiguous-mode hits from this phase's planner groundwork even though propagation modes themselves ship in Phase 3 (§15) — the column exists early to avoid a schema migration later (ADR-05 additive discipline applied to Fuzzy's own internal tables, not just confident<T>).

15. Phase 3 — Join Propagation Algebra (MIN + PRODUCT)

15.1 Objectives

Ship two of the three locked propagation modes (§8.4): MIN (default) and PRODUCT. Planner hook attaches propagation metadata to join nodes over confident<T> columns.

15.2 Detailed Implementation Steps

confident_join operator family implementing a ~ b (§8.3, P2 — the algebra is locked from this phase forward). Planner hook detects join conditions over confident<T> columns and attaches the chosen mode (from WITH PROPAGATION = or the column's DEFAULT PROPAGATION, §11.3) as plan-node metadata; executor reads that metadata and computes c_out per §8.4.1/§8.4.2 — theoretically grounded in Dalvi & Suciu 2004's possible-worlds independence assumption for PRODUCT (§5) and the semiring min-framing of Green et al. 2007 (§5, MM3 §30) for MIN. Cost model: both modes cost-equivalent to a plain join (MIN is a comparison, PRODUCT is one extra multiply) — verified against M4 (§4/§28).

15.3 Deliverable

A 3-way join over confident<T> columns produces correct propagated confidence under both MIN and PRODUCT, selectable via WITH PROPAGATION =.

15.4 Acceptance Criteria

  • conformance/fixtures/join_propagation_min_020.sql and ..._product_020.sql: 20 fixtures each, all pass exactly.
  • Join cost ≤ 1.4× plain join at 10M rows (M4, §4) verified by benchmarks/join_10m.rs.
  • ERRCODE_FUZZY_AMBIGUOUS_PROPAGATION raised on conflicting column defaults with no explicit WITH PROPAGATION = (I4), fixture ambiguous_propagation_001.sql.

Fixture Purpose Expected Output

15.6 Pitfalls

  • Treating PRODUCT propagation as valid for correlated (non-independent) sources silently understates true confidence — root cause: PRODUCT assumes independence (Dalvi & Suciu 2004, §5); mitigation is documentation + a linter warning (Phase 9, §21) when two joined columns share the same source handle pattern.
  • Propagation-metadata plan nodes not surviving EXPLAIN's plan-cache reuse path causes a stale mode to apply after a column's DEFAULT PROPAGATION changes — debug signal: changing config has no effect until DISCARD PLANS.
  • Nested joins (3+ tables) compounding MIN incorrectly (taking min of mins is associative, so this is actually safe) versus PRODUCT chains losing precision on many multiplications — mitigated by computing in f64 with a documented precision floor.

15.7 Performance Concerns

Propagation computation is O(1) per joined row pair — no batching needed. The planner hook's cost-estimation adjustment must not itself become an O(n²) pass over join candidates (guard via memoized per-relation confidence-column metadata).

15.8 Edge Cases

Self-join on a confident<T> column (both sides same column) — MIN/PRODUCT both degenerate correctly (min(c,c)=c, c×c=c², both well-defined); one side NULL confidence (should not occur under I1+NOT NULL column constraint, but outer joins can produce NULL rows) — propagation over a NULL-side row yields NULL confidence, row still returned per standard outer-join semantics; propagation depth limit (ADR-21) rejects plans with unbounded propagation chains (T1).

15.9 Failure Analysis

A propagation-mode bug that silently applies MIN where PRODUCT was requested is a correctness failure with no crash signal — contained by the fixture matrix (15.5) plus a differential test that compares against a reference Python implementation of §8.4.1/2 on the same 20 fixtures nightly in CI.

15.10 Operational Notes

fuzzy_stat_propagation.mode becomes populated per-join from this phase; operators should dashboard the distribution of modes in production to catch unexpected MIN fallback (indicating queries that never specify PRODUCT/BAYESIAN when they should).

16. Phase 4 — Bayesian Propagation & Reliability Priors

16.1 Objectives

Ship the third propagation mode, BAYESIAN (§8.4.3); wire reliability_a/reliability_b priors into fuzzy_source (§11.2) and expose an admin function to set them.

16.2 Detailed Implementation Steps

Implement c_out = (α_l + α_r) / (α_l + β_l + α_r + β_r) (§8.4.3) directly against fuzzy_source.reliability_a/b, grounded in the Beta-Binomial conjugate-prior closed form (Gelman et al. 2013 Ch. 2, §5) — this is P9's determinism requirement made concrete: the same two priors always yield the same posterior mean. Admin function fuzzy_source_set_reliability(handle, alpha, beta) validates α, β > 0 before writing (guards I10 — direct writes elsewhere are blocked by grants, ADR-17). Extend EXPLAIN (FUZZY) to print the chosen mode per join (extends I5's rewrite-visibility guarantee to propagation choice too).

16.3 Deliverable

WITH PROPAGATION = BAYESIAN over two columns with configured priors produces output confidence matching the closed-form posterior mean.

16.4 Acceptance Criteria

  • Synthetic correlated-source workload matches the closed-form Beta-binomial mean to ±0.001 (conformance/fixtures/bayesian_closed_form_015.sql, 15 cases).
  • fuzzy_source_set_reliability rejects α ≤ 0 or β ≤ 0 (fixture reliability_validation_001.sql).
  • BAYESIAN join cost ≤ 2.0× plain join at 10M rows (M5, §4).

  • Treating reliability_a/b as directly-writable columns instead of routing all changes through the admin function violates I10 — mitigated by revoking direct UPDATE grants on fuzzy_source at CREATE EXTENSION time (ADR-17); signal is an audit-log gap (fully closed once Phase 8's fuzzy_audit_log lands, §20).

  • Confusing "confidence" with "probability of the ground truth" when picking priors — root cause is the calibration gap identified by Niculescu-Mizil & Caruana 2005 (§5); mitigation is a documentation callout, not a code fix (this is a modeling responsibility of the caller, not a Fuzzy defect).

16.7 Performance Concerns

BAYESIAN mode's four-way division is more expensive than MIN/PRODUCT's single op — budgeted separately as M5 (2.0× vs. MIN/PRODUCT's 1.4×, §4) precisely because it is not free; batching is not applicable since the computation is row-local and non-amortizable.

16.8 Edge Cases

Both sources have identical (α, β) = degenerates to a simple average; one source with α = β = 1 (uninformative uniform prior) — behaves as an near-neutral pass-through, documented as the safe default for newly-registered sources (matches fuzzy_source's DEFAULT 1.0 for both fields, §11.2); extremely large α + β (a very "experienced" source) dominates the posterior — no overflow risk since inputs are float8 (well within range for any realistic effective sample size).

16.9 Failure Analysis

A wrong (α, β) write (bypassing the admin function via a superuser role) silently biases every future BAYESIAN join touching that source — detection is a periodic conformance-style production check comparing fuzzy_source state against the audit trail (Phase 8+ closes this fully); until then, the mitigation is grant restriction (ADR-17) plus documented operator discipline.

16.10 Operational Notes

Dashboard fuzzy_stat_propagation filtered to mode = 'bayesian' alongside fuzzy_source.reliability_a/b drift over time — a source whose reliability trends toward α ≈ β is becoming uninformative and may need re-calibration (a Phase 8 feedback signal, §20).

17. Phase 5 — Decay Engine (bgworker)

17.1 Objectives

Ship fuzzy_decay, the throttled, cooperatively-cancellable background worker (ADR-08, P13) that applies configured decay functions (§8.6-adjacent, §11.4) to confident<T> columns on a schedule, keeping the read path O(1) (I8).

17.2 Detailed Implementation Steps

pgrx bgworker scaffold, one launcher entry per opted-in database (ADR-08) — following TimescaleDB's per-database worker lifecycle pattern (§5 Reference Implementations). fuzzy_decay_def table (§11.4) backs half_life, linear, step, none primitives (§8.6-adjacent table). ALTER TABLE ... ALTER COLUMN ... SET DECAY ... syntax via the rewriter (extends ADR-23's mechanism to DDL). Throttling via fuzzy.decay_max_rows_per_minute GUC; cooperative cancellation check every ≤10,000 rows (I9) — the exact interval size is itself a conformance-checked constant, not a magic number left to drift. Sweep is idempotent: c := c_base × decay_fn(elapsed(t, now())), never a running delta (supports the resumable-after-crash property proven in §8.9).

  • 100M-row sweep completes in < 4 hours at default throttle (M8, §4), verified by benchmarks/decay_sweep_100m.rs.
  • bgworker cancellation on SIGTERM drains within < 2 s (I9, fixture decay_cancel_drain_001.sql).
  • CPU usage stays ≤ 1 core sustained during a sweep (M9, §4).

17.6 Pitfalls

  • A sweep that computes decay as a running multiplicative delta (rather than from t and elapsed time each pass) compounds error across repeated sweeps — root cause: confusing "decay is a function of elapsed time" (correct, I7) with "decay is a mutation applied repeatedly" (wrong); debugging signal is confidence drifting below the decay function's true curve after multiple sweep cycles.
  • Missing the cancellation check inside a tight per-row loop stalls checkpoint completion — signal: pg_stat_activity shows a long-running bgworker blocking CHECKPOINT; root cause traced to I9's ≤10,000-row check interval not being honored.
  • Throttle GUC misconfigured to 0 (meant to mean "unlimited") is ambiguous with "disabled" — resolved by a dedicated fuzzy.decay_enabled boolean GUC instead of overloading the rate.

17.7 Performance Concerns

Sweep must avoid a full table scan when only a small fraction of rows have a non-none decay configured — indexed via fuzzy_column_config.decay_ref IS NOT NULL to skip undecorated columns entirely; per-row write is a single-row UPDATE, not a batch COPY, trading throughput for crash-safety (§8.9 idempotency argument).

17.8 Edge Cases

Decay sweep encountering a row whose t is in the future (clock skew) — clamps elapsed time to zero, does not apply negative decay; a column's decay function changed mid-sweep — next sweep cycle picks up the new function, current cycle finishes with the function it started with (no mid-sweep function-swap); database with zero decay-configured columns — sweep exits immediately, no wasted cycles.

17.9 Failure Analysis

A bgworker crash mid-sweep (e.g., OOM on a pathological value) is isolated to that OS process (I11) — postmaster restart within RTO < 60 s (FM-5, §23); worst-case blast radius is a resumed sweep re-visiting already-decayed rows, which is a no-op given idempotency (§8.9), not a correctness bug.

17.10 Operational Notes

fuzzy_stat_decay_runs exposes rows_visited, out_of_range_clamped, cancelled_gracefully per run — alert if out_of_range_clamped is ever nonzero (would indicate an I7 violation reaching the write path, which should be structurally impossible given the clamp-before-write design). Rollback: disabling fuzzy.decay_enabled stops future sweeps without reverting already-decayed values (decay is one-directional by design, matching real-world confidence aging).

19. Phase 7 — Conflict Log & Resolution Modes

19.1 Objectives

Ship fuzzy_conflict_log (§11.5, P10) as an append-only store: when track_conflicts = true on a column (§11.3), a second write to the same (row, column) appends rather than overwrites (I6). Ship the MAX_CONFIDENCE, NEWEST, BAYESIAN_FUSE resolution modes computing the canonical read-path value.

19.2 Detailed Implementation Steps

Trigger-based interception on the confident<T> update path: when fuzzy_column_config.track_conflicts is true, the write path appends an observation row to fuzzy_conflict_log inside the same transaction (I6, Gray et al. 1976's degrees-of-consistency analysis, §5, informs why this must not be a deferred/async trigger). Read path: for track_conflicts columns, computes the canonical value from the log per the column's resolution mode — MAX_CONFIDENCE (highest c wins), NEWEST (latest t wins), BAYESIAN_FUSE (Beta-posterior fusion across all observations, reusing §8.4.3's math). Index (rel_id, attnum, row_id, written_at DESC) (§11.5) supports efficient canonical-value computation without a full log scan per read. New SQL surface: observations(col) returns all observations for a row+column; confident_disagreement(col) aggregate returns Shannon entropy of the source distribution (grounded in Sen & Deshpande 2007's correlated-tuple representation, §5). Retention: per-column max-observations / max-age caps; fuzzy_conflict_compact() admin function merges old observations.

19.3 Deliverable

Two conflicting writes to the same (row, column) both land in fuzzy_conflict_log; reads return the canonical value per the configured resolution mode; observations(col) lists the full history.

19.4 Acceptance Criteria

  • Write amplification for a track_conflicts column stays < 2× plain UPDATE (M10, §4) — kill-trigger threshold at ≥5× (FM-6, §23), verified by benchmarks/conflict_write_amp.rs.
  • All three resolution modes verified exact on 50 fixtures (conformance/fixtures/resolution_modes_050.sql).
  • Concurrent-write race fixture under pgbench -c 16 produces zero lost observations (conflict_race_016.sql).
  • Retention compaction (fuzzy_conflict_compact()) preserves the currently-canonical observation under every resolution mode (compaction_preserves_canonical_001.sql).

19.6 Pitfalls

  • Implementing the conflict-log append as an AFTER trigger with DEFERRABLE INITIALLY DEFERRED breaks I6 if the outer transaction can commit the base row without the log row committing atomically together under certain isolation levels — mitigated by using a non-deferrable AFTER trigger in the same transaction, verified by conflict_race_016.sql's abort-mid-transaction variant.
  • BAYESIAN_FUSE naively re-deriving priors from raw observation counts (rather than each source's registered (α, β), §11.2) double-counts evidence — root cause: conflating "number of observations" with "source reliability"; fixed by fusing through fuzzy_source.reliability_a/b, not observation counts.
  • Retention compaction run concurrently with an in-flight NEWEST-mode read can transiently disagree on the canonical row — mitigated by compaction taking a ROW EXCLUSIVE lock on the affected log rows for its duration.

19.7 Performance Concerns

The index on (rel_id, attnum, row_id, written_at DESC) (§11.5) keeps canonical-value computation to an index range scan bounded by observation count for that cell, not a table-wide scan; retention caps bound worst-case observation count per cell, keeping read-path cost predictable even under adversarial repeated-write workloads.

19.8 Edge Cases

A single writer overwriting the same (row, column) many times in one transaction — each UPDATE still appends (I6 applies per-statement, not per-transaction); all observations for a cell superseded (superseded_by chain) — observations(col) still returns full history unless explicitly filtered; a resolution-mode change while observations already exist — takes effect on next read, no historical rewrite needed (canonical value is always computed, never cached long-term).

19.9 Failure Analysis

A trigger bug that fails to append under specific isolation levels (e.g. REPEATABLE READ) silently reverts to Phase 0–6 overwrite behavior — detected by conflict_race_016.sql run under all four Postgres isolation levels in CI; blast radius if missed in production: loss of provenance for disagreement history, not data corruption (the base row's current value remains correct) — recoverable by re-enabling track_conflicts going forward, prior history unrecoverable (documented operator risk).

19.10 Operational Notes

fuzzy_stat_columns.conflict_writes tracks append volume; operators should alert on an unbounded growth rate relative to the retention cap (indicates a badly-tuned cap or an unexpectedly high-disagreement source mix). Migration: fuzzy_enable_conflicts(table, column) backfills the log with the current row state as observation #1, online, in small batches with per-batch commits (avoiding a single giant lock, per Kleppmann 2017's migration-safety guidance, §5).

20. Phase 8 — Feedback API & Reliability Update

20.1 Objectives

Ship fuzzy_feedback (§11.5) and the SQL admin function that records a human (or higher-trust source) correction and updates the originating source's (α, β) Beta reliability prior (§8.4.3) via the posterior update rule.

20.2 Detailed Implementation Steps

fuzzy_apply_feedback(rel, attnum, row_id, corrected_to, correcting_source) writes a fuzzy_feedback row and appends a new observation (c = 1.0 by default, configurable) to fuzzy_conflict_log (reusing Phase 7's append mechanism, §19.2) so the correction participates in future BAYESIAN_FUSE resolution. Reliability update rule: if feedback agrees with a source's original observation, α += weight; if it disagrees, β += weight (weight defaults to 1.0) — this is exactly the Beta-binomial conjugate update (Gelman et al. 2013, §5, same closed form validated in Phase 4, §16.4). The update is the only legal path that mutates fuzzy_source.reliability_a/b (I10, enforced by revoked direct-UPDATE grants, ADR-17) — this phase is what finally closes the detection gap flagged in §16.9.

20.3 Deliverable

fuzzy_apply_feedback(...) records a correction; the originating source's reliability prior updates via the Beta posterior rule; subsequent BAYESIAN/BAYESIAN_FUSE queries reflect the updated prior.

20.4 Acceptance Criteria

  • Property-based test confirms the Beta posterior update preserves α, β > 0 and α/(α+β) ∈ [0,1] across 1,000 randomized feedback sequences (conformance/fixtures/feedback_posterior_property_1000.sql).
  • A feedback event that disagrees with a source's prior observation measurably lowers that source's α/(α+β) ratio within the same transaction (feedback_disagree_lowers_reliability_001.sql).
  • fuzzy_audit_log (new in this phase) records every feedback event and every reliability_a/b change with 100% coverage (audit_coverage_001.sql).

20.6 Pitfalls

  • Applying feedback with weight unbounded lets a single correction dominate a well-established source's prior — root cause: no ceiling on weight; mitigated by a documented recommended range (0.1–5.0) and a WARNING above 10.0, not a hard cap (P5- style "opt-in but obvious" philosophy applied to feedback weight).

20.7 Performance Concerns

The posterior update is O(1) per feedback event — no batching required; audit-log writes add one extra append per feedback call, budgeted at the same write-amplification ceiling as conflict-log writes (M10, §4) since both ride the same in-transaction append mechanism.

20.8 Edge Cases

Feedback on a row/column with no prior conflict-log history (feedback is the first correction ever) — the update rule still applies against the source's registry-default prior; feedback from a source that is itself unregistered — auto-registers per I2/P4 before the update proceeds; simultaneous feedback from two different correcting sources on the same cell — both recorded, both applied to their respective original sources' priors independently (not to each other).

20.9 Failure Analysis

A bug in the update rule's sign (accidentally incrementing α on disagreement) would silently increase reliability for a source that is actually wrong — the highest-value property test in the whole system (feedback_posterior_property_1000.sql) exists specifically to catch this class before release; in production, detection relies on fuzzy_audit_log review during incident postmortems (§23).

20.10 Operational Notes

fuzzy_audit_log (introduced this phase, a governance-plane precursor — PhaseDeferred("§35") for the full policy engine) is append-only and should be streamed to durable external storage per the operator's retention policy; dashboard reliability drift (reliability_a/(reliability_a+reliability_b)) per source over time as the primary feedback-loop health signal.

Fuzzed input containing valid JSON with an out-of-range c nested inside a deeply recursive jsonb value for T=jsonb — bounded by a maximum nesting-depth check in the type input function; a benchmark run on a Postgres minor not yet in the pinned matrix — treated as informational only, does not gate merge until formally added to the matrix.

21.9 Failure Analysis

A budget regression caught by budget_gate.rs blocks the release (§4 hard gate) rather than shipping with a documented exception — the one place in the whole blueprint where "fix before ship" is non-negotiable, because performance budgets compound silently across releases if allowed to slip even once.

Deployment topology. Single extension .so per Postgres instance; bgworker auto-launches per opted-in database at instance start.

25. Compatibility & Versioning

Wire compatibility. confident<T> wire tuple fields are additive-only (ADR-05, P14, I3) — no field is ever repurposed or removed; new fields append after conflict_ix. Verified every release by conformance/version-skew/.

Storage compatibility. fuzzy_* catalog tables follow standard Postgres extension- upgrade scripts (ALTER EXTENSION fuzzy UPDATE); schema changes are additive (new nullable columns only) within a major version.

Schema-evolution policy. A breaking storage change requires a new major version and an explicit migration script in extension/sql/; documented in CHANGELOG.md 60 days ahead of release (matching the major-release cadence, §27).

API stability. SQL function signatures (confidence(), source(), value(), aggregates, fuzzy_apply_feedback, admin functions) are stable within a major version; new optional parameters may be added with defaults, never a required-parameter change.

Deprecation policy. A deprecated function/GUC is retained, documented, and emits a one-time WARNING for at least one full major-version cycle before removal.

SemVer policy (ADR-18). MAJOR: wire/storage breaking change. MINOR: new propagation mode, new decay primitive, new SQL function — additive only. PATCH: bug fix, no behavior change to any locked semantic (P2, P9).

Rolling-upgrade guarantees. A cluster may run mixed extension .so versions across replicas for the duration of a rolling upgrade window, provided both versions are within the same major (guaranteed by the additive-only wire/storage rules above); cross-major mixed operation is unsupported and blocked by ALTER EXTENSION's version check.

26. Testing & Verification Strategy

Unit tests. pgrx test harness against fuzzy_types/fuzzy_planner/fuzzy_decay modules; target >85% line coverage on type-system and operator code (mirrors the original project's coverage bar, retained as a real quantified target).

Integration/conformance. The conformance/ suite (§10) is the primary correctness oracle, growing phase by phase: 4 fixtures (Phase 0) → 60 (Phase 1) → 200 (Phase 6, §18.4) → 250+ by Phase 9 (§21). Every invariant (§7) maps to at least one fixture class.

Property-based testing. The Beta-posterior update (§20.4, feedback_posterior_property_1000.sql) is the canonical example: 1,000 randomized sequences checked against the algebraic invariant α,β>0 ∧ α/(α+β)∈[0,1], not fixed examples.

Differential testing. Propagation modes (§15.9) are checked nightly against a reference Python re-implementation of §8.4.1/§8.4.2/§8.4.3 on the same fixture corpus — catches silent-drift bugs (FM-2) that a single implementation's own tests cannot.

Fuzzing. cargo-fuzz on the type input function (ADR-13, §21) — the sole hostile- input boundary (P11) — seeded from the Phase 0 malformed-input fixtures (§21.6).

Chaos / fault injection. SIGTERM mid-sweep (I9, decay_cancel_drain_001.sql, §17.5); concurrent-writer races under pgbench -c 16 (§19.5); transaction-abort-mid- write for conflict-log atomicity (I6, §19.6).

Deterministic replay. The conformance simulator (§7 debugging methodology) replays a fixed corpus deterministically — same input, same verdict, every CI run (P9).

Soak testing. A 24-hour cargo-fuzz corpus run (§21.4) plus a multi-day decay-sweep soak on a synthetic 100M-row table before every major release.

Performance-regression gating. benchmarks/budget_gate.rs (§21.2) blocks merge on any of the ten M1–M10 targets regressing (§28) — the only hard, non-overridable CI gate in the whole pipeline (§21.9).

Tie-back to invariants and fixtures. Every row of §7's invariant table names its enforcement point and detection mechanism; every phase's N.5 names the fixtures that exercise it — together they form the full verification matrix referenced by this section.

29. Scalability Analysis

Stays constant. Read-path cost per row — O(1) regardless of decay schedule (I8); type I/O cost per value — O(size of T) plus fixed 62-byte overhead (§4), independent of table size.

Grows. Decay-sweep wall time — O(rows with non-none decay configured) (§17.7); conflict-log size per cell — O(observations), bounded by retention caps (§19.2); fuzzy_source registry size — O(distinct sources), typically small relative to row count.

Named bottlenecks, in order. (1) Decay-sweep throughput at very large row counts (M8 budget assumes ≥6,944 rows/s single-core; beyond ~500M decayed rows this becomes the dominant operational cost, §32). (2) Conflict-log write amplification under high-disagreement workloads (M10; retention tuning is the primary lever, FM-6). (3) BAYESIAN join cost at very wide fan-out joins (M5's 2.0× ceiling assumes a bounded join width; propagation-depth cap, ADR-21, bounds worst case).

Horizontal/vertical scaling. Vertical first (§4): a single Postgres instance scales with CPU/memory for the OLTP write path. Horizontal: read replicas absorb read-only confidence-predicate query load (standard Postgres streaming replication, no Fuzzy- specific replication logic); the decay bgworker runs only on the primary (writes must happen there).

Sharding/partitioning. Not built into Fuzzy directly — a sharded deployment (e.g. via Citus, §5 Reference Implementations) would need the propagation algebra (§8.4) to compose correctly across shards for cross-shard joins, an explicitly out-of-scope concern for Phase 0–9 (PhaseDeferred("§35")).

Coordination overhead. None inside a single instance — all Fuzzy operations are single-node; the only coordination point is the bgworker-per-database launcher, which is Postgres's own postmaster, not custom-built coordination.

Practical ceiling and levers beyond it. The practical ceiling for Phase 0–9 is a single large Postgres instance (up to the point where decay-sweep or conflict-log write-amplification dominate, above). The lever beyond it is out of blueprint scope: sharding via Citus-style distribution, deferred pending a cross-shard propagation-algebra design (§35).

30. Mental Models & First Principles

  1. MM1 — A confident<T> value is a possible-worlds compressor, not a single fact. It predicts that any operation over it (comparison, join, aggregate) must define what happens across the implied distribution of worlds, not just the point value. Without it you write operators that silently assume c=1.0 everywhere. Applied in §8.4, §15.
  2. MM2 — Confidence is metadata about the writer's belief, not a property of the world. Predicts that two sources can disagree about the same v and both be "correctly" reporting their own confidence — which is exactly why the conflict log (§19) exists rather than a single overwritten cell. The bug class without it: treating disagreement as an error condition instead of data. Applied in §19, §20.
  3. MM3 — Propagation is a semiring combination, not an ad hoc formula. Predicts that MIN, PRODUCT, and BAYESIAN must each be associative/commutative to compose safely across multi-way joins (Green et al. 2007, §5). The bug class without it: a propagation mode that gives different answers depending on join order. Applied in §8.4, §15.6, §18.6.
  4. MM4 — Decay is a pure function of elapsed time, never a running mutation. Predicts that a crashed, resumed, or repeated sweep is always safe (idempotent). The bug class without it: confidence drifting further from truth with every re-sweep. Applied in §17.2, §17.6, §8.9.
  5. MM5 — An extension's ABI surface is someone else's implementation detail. Predicts that any internal (non-public) Postgres API used will eventually move; the only defense is an explicit inventory (§21.2) and a compatibility shim, never hoping the API stays put. The bug class without it: a working extension that silently stops building on the next Postgres minor. Applied in §9 ADR-01, §22 T2, §23 FM-1.
  6. MM6 — Attribution is what makes correction possible. Predicts that a system without a mandatory source on every write cannot ever build a feedback loop, because there is nothing to re-weight. The bug class without it: "confidence" that never improves no matter how many corrections arrive. Applied in §7 I2, §20.
  7. MM7 — Calibration and confidence are not the same number. Predicts that a model reporting c=0.9 is not necessarily right 90% of the time unless it has been calibrated (Niculescu-Mizil & Caruana 2005, §5) — Fuzzy stores the number faithfully but does not manufacture calibration. The bug class without it: treating confident<T> as a probability guarantee the database itself does not and cannot provide. Applied in §16.6, Glossary §36.
  8. MM8 — A background worker is a second failure domain, not a free lunch. Predicts that anything run in fuzzy_decay needs its own crash isolation, cancellation, and throttling story, independent of the backend's. The bug class without it: a decay bug that takes down user queries instead of just delaying a sweep. Applied in §17, I9, I11.

32. Back-of-Envelope Capacity Model

Every number below is derived from §4's System Constraints table, formula shown.

  1. Decay-sweep throughput floor. rows ÷ time = throughput ⇒ 100,000,000 rows ÷ 14,400 s = 6,944 rows/s (M8, §4).
  2. Per-row memory footprint (text T, ~20B avg). fixed_overhead + |T| ⇒ 62 B + 20 B = 82 B/row (§4 storage amplification row).
  3. Storage overhead at 100M rows. rows × fixed_overhead ⇒ 100,000,000 × 62 B ≈ 6.2 GB of pure Fuzzy tuple overhead, excluding T itself.
  4. Worst-case backend memory for type I/O. max_concurrent_backends × per-backend ceiling ⇒ 1,000 × 64 MB = 64 GB (§4 concurrency target × memory ceiling row).
  5. Conflict-log growth rate. write_rate × observation_size × seconds/day ⇒ at a representative 1,000 writes/s to a track_conflicts column, 150 B average observation size (§11.5 jsonb + row overhead): 1,000 × 150 B × 86,400 s ≈ 12.9 GB/day — the number that makes the M10 write-amplification budget (§28) and retention caps (§19.2) operationally necessary, not cosmetic.
  6. BAYESIAN join cost bound at 10M rows. plain_join_cost × M5_multiplier ⇒ assuming a representative 2,000 ms plain hash join at 10M rows, 2,000 ms × 2.0 = 4,000 ms ceiling (M5, §4).
  7. Read-path bandwidth at scan rate. rows/s × row_size × (1 + M2_overhead) ⇒ 10,000 rows/s × 82 B × 1.15 ≈ 943 KB/s sustained scan bandwidth.
  8. Query latency floor from network + serialization. RTT + serialization_overhead ⇒ 5 ms + 0.2 ms = 5.2 ms, leaving only 8 ms − 5.2 ms = 2.8 ms of the p50 budget (M6, §4) for actual index-scan + predicate evaluation — the number that justifies requiring an index in M6/M7's acceptance criteria (§14.4).
  9. Annual write-count ceiling for a single source's Beta prior. writes/s × s/year ⇒ 1 × 31,536,000 = 31,536,000 maximum realistic α+β accumulation — many orders of magnitude below float8's range, confirming no overflow risk in the posterior update (§20.2, I7-adjacent safety margin).
  10. FD budget at max concurrency. (backends × FD/backend) + databases_with_bgworker ⇒ (1,000 × 10) + 50 = 10,050 file descriptors — the number a production ulimit -n must clear (§4 FD budget row).

34. Alternative Architectures (Roads Not Taken)

A. Parser-Fork Architecture.

Client SQL ──▶ [Forked Postgres Grammar: native `confident<T>` syntax]
                        │
                        ▼
              [Native planner nodes for confidence joins]

Regime where it wins: once desired syntax genuinely cannot be expressed as a clause modifier over existing grammar (the exact ADR-23 escalation trigger). Real system embodying it: Postgres itself historically absorbed geometric and full-text-search syntax this way over many major versions. Rejected because: a forked grammar means tracking every Postgres grammar change forever, an order of magnitude larger maintenance surface than a post-parse rewriter (§9 ADR-23) — acceptable only if the rewriter proves structurally insufficient, which Phase 0–9's fixture corpus (§14.4) shows it is not.

B. External Confidence Service Architecture.

App ──▶ [Fuzzy Service: gRPC/HTTP] ──▶ [Confidence Store] ◀──correlate by row-id── [Postgres]

Regime where it wins: multi-database or polyglot-persistence environments where confidence must span more than one underlying store (no single Postgres instance holds all the data). Real system embodying it: Trio's research architecture kept lineage/ confidence management logically separate from the base data model (Widom 2005, §5, §31). Rejected because: correlating confidence to base rows across a network boundary reintroduces exactly the two-phase-commit-shaped consistency problem Fuzzy exists to avoid — the entire value proposition (§2) is that confidence lives in the same transaction as the value.

C. World-Set Decomposition Storage Architecture.

[Base Relation] ──▶ [World-Set Decomposition: (tuple, condition) pairs]
                              │
                              ▼
                  [Query evaluator enumerates consistent worlds]

Regime where it wins: analytical workloads over a bounded number of tightly correlated alternative worlds, where exact possible-worlds query answers matter more than OLTP write latency (MayBMS, Antova/Koch/Olteanu 2007, §5, §31). Rejected because: query evaluation complexity grows with the number of possible worlds (Dalvi & Suciu 2004, §5), which is incompatible with Fuzzy's OLTP-first performance budgets (§4, M1–M3) — this is the same tradeoff already recorded in ADR-04's rejected-alternative column, elevated here to the level of a whole-system alternative rather than a single storage decision.

36. Glossary

  • confident<T> — the parametric Postgres type: (v, c, s, t, decay_ref, conflict_ix) (§8.1).
  • Confidence (c) — a scalar in [0.0, 1.0] reporting a source's belief in v; not a calibrated probability by construction (MM7, §5 Niculescu-Mizil & Caruana 2005).
  • Source (s) — a source_id identifying the producer of an observation (§8.1, I2).
  • Source registry — fuzzy_source (§11.2); maps handles to kinds and reliability priors.
  • Source kind — enum {model, agent, sensor, human, system} classifying a source.
  • Decay function — a configured rule (half_life, linear, step, none, §11.4) by which confidence ages, applied only by fuzzy_decay (P5).
  • Half-life decay — confidence halves every configured N days from t.
  • Linear decay — confidence ramps linearly to zero over a configured horizon.
  • Step decay — confidence multiplied by a factor after a configured interval.
  • Decay engine (fuzzy_decay) — the bgworker walking columns and applying decay (§17).
  • Cooperative cancellation — a bgworker checking a cancellation flag at bounded intervals (≤10,000 rows, I9) rather than being forcibly killed.
  • Conflict log — fuzzy_conflict_log (§11.5); append-only store of every observation written to a track_conflicts cell (P10).
  • Resolution mode — per-column rule (MAX_CONFIDENCE, NEWEST, BAYESIAN_FUSE) computing the canonical value from the conflict log (§19.2).
  • Propagation mode — per-join rule (MIN, PRODUCT, BAYESIAN, deferred DEMPSTER-SHAFER) combining input confidences at a join (§8.4).
  • Beta-binomial conjugate prior — the closed-form posterior update used by BAYESIAN propagation and the feedback reliability update (Gelman et al. 2013, §5).
  • Reliability prior (α, β) — a source's Beta-distribution parameters in fuzzy_source, updated only via the feedback rule (I10, §20.2).
  • Feedback — a correction recorded via fuzzy_apply_feedback, updating the originating source's reliability prior (§20).
  • Calibration — whether a reported confidence matches empirical correctness frequency; a modeling responsibility of the caller, not a Fuzzy guarantee (MM7).
  • EXPLAIN (FUZZY) — the Fuzzy variant of EXPLAIN; reports rewrites, propagation modes, and decay state (§8.6, I5, P7).
  • Post-parse rewriter — the hook desugaring WITH confidence > X into plain predicates (ADR-23, §14.2).
  • Planner hook — the hook attaching a propagation mode to join plan nodes (§8.4, §15.2).
  • Wire format — the packed binary tuple encoding of confident<T> (§8.1, ADR-05, additive-only per P14/I3).
  • Abstract data type (ADT) extensibility — the Postgres mechanism allowing a new parametric type to become first-class (Stonebraker & Rowe 1986, §5).
  • pgrx — the Rust framework binding Postgres's C ABI safely (§5, ADR-01).
  • palloc / PgMemoryContexts — Postgres's per-context memory allocator; must be used instead of the global Rust allocator inside extension code (§12.6).
  • Operator class — the Postgres mechanism letting a B-tree index understand ordering over a custom type (§14.2).
  • Possible-worlds semantics — the formal model treating an uncertain database as a distribution over possible exact databases (Dalvi & Suciu 2004, §5).
  • World-set decomposition — MayBMS's storage technique representing correlated uncertain tuples as (tuple, condition) pairs (§5, §31, ADR-04).
  • Semiring combination — an algebraic framing (associative/commutative combination) used to reason about propagation-mode composability (Green et al. 2007, §5, MM3).
  • Dempster-Shafer theory — a belief-combination framework heavier than MIN/PRODUCT, deferred to a later phase (§8.4.4, §5 Dempster 1967/Shafer 1976).
  • Consensus confidence — confident_consensus's output: Σc_i[agree] / Σc_i[all] (§8.5).
  • Disagreement entropy — confident_disagreement's output, Shannon entropy of a cell's source distribution (§19.2, Sen & Deshpande 2007).
  • Conformance suite — the fixture-driven correctness harness in conformance/ (§26).
  • Write amplification — extra write cost imposed by a feature (e.g. conflict-log appends) versus a plain UPDATE (M10, §4).
  • Retention cap — a per-column max-observations/max-age limit bounding conflict-log growth (§19.2).
  • fuzzy_audit_log — the append-only audit trail for feedback and reliability changes, introduced Phase 8 (§20.10).
  • panic_disable GUC — an emergency setting disabling rewriter/planner hooks without uninstalling the extension (§24).
  • Propagation-depth cap — a bound on join-propagation chain depth preventing pathological plans (ADR-21, T1).
  • statement_timeout — standard Postgres GUC bounding query execution time, reused as a backpressure mechanism (ADR-21).
  • SemVer — semantic versioning discipline locking MAJOR/MINOR/PATCH meaning to wire/storage compatibility (ADR-18, §25).
  • RTO (Recovery Time Objective) — the maximum acceptable time to recover from a failure (e.g. < 60s after a bgworker crash, §4, I11).
  • Idempotent sweep — a decay sweep computed fresh from t and elapsed time each pass, safe to re-run after a crash (§8.9, MM4).
  • TOAST — Postgres's mechanism for storing oversized variable-length values out-of-line; relevant to confident<T> for large T (§12.6).
  • RUSTSEC — the Rust security-advisory database checked by cargo-deny in CI (ADR-03, §27).
  • SBOM (Software Bill of Materials) — a generated inventory of build dependencies attached to every release (§27).
