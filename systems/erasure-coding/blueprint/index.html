108 — Erasure Coding (Reed-Solomon)

Project Number: 108

Project Name: Erasure Coding (Reed-Solomon)

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a systematic Reed-Solomon erasure-coding library over GF(2^8) — encode k data shards into k + m shards (k data + m parity) such that any k of the k + m shards reconstruct the original bytes exactly (the MDS property, I1) — plus a Local Reconstruction Code (LRC) extension that cuts single-shard repair bandwidth, and the storage-integration surface (CLI, scrubber, repair planner) that a distributed object store consumes for cold-tier durability. The codec is a library, never a service: it is linked in-process by consumers and exposes byte-slice-in / byte-slice-out APIs plus an optional C ABI.

Phase-0 deliverable (numbered, in-scope):

  1. ec-core — shared types: Gf256, Matrix, Shard, EncodingMatrix, CodecParams.
  2. ec-gf256 — GF(2^8) scalar arithmetic kernel (log/exp tables, add/mul/inv/div).
  3. ec-encoder / ec-decoder — the (k=2, m=1) placeholder codec (deleted §14).
  4. ec-conformance — the harness scaffold: three green buckets, nine Deferred.
  5. Repository scaffold of §10, with governance files and CI stubs.

System boundaries.

  • Provides: GF(2^8) encode/decode, Cauchy + Vandermonde matrix construction, systematic form, SIMD acceleration, LRC (Azure-LRC, XORBAS), a repair planner, a streaming API, a frozen C ABI, an operator CLI, a bitrot scrubber.
  • Delegates: durable storage placement, replication topology, and network transport to the consumer (rank-86 DFS chunkserver, rank-107 object store, rank-111 backup engine — sibling systems in this portfolio).
  • Does NOT provide: encryption, deduplication, compression, cross-region placement, or a listening network service in Phase 0 – Phase 9 (the optional ec-proto RPC in §23 is opt-in and off by default).

Non-goals: cryptographic secret-sharing (the systematic layout leaks plaintext data shards by design, P2); support for k + m > 255 (I7; PhaseDeferred("§9 ADR-03") covers a wider-field variant); a general-purpose linear-algebra library.

Deployment model: statically or dynamically linked library (cdylib + rlib), consumed in-process; the CLI (ec-cli/ec-bin) is a standalone operator binary.

Target users/operators: storage-system engineers integrating erasure coding into a chunk/object store; SREs running the scrubber and rebuild tooling via the CLI.

What later phases unlock: Phase 5 (§17) SIMD lifts throughput 6–15×; Phase 9 (§21) LRC cuts repair bandwidth 2×; Phase 10 (§22) Hitchhiker cuts it a further 25–45% (Rashmi 2014); Phase 11 (§23) unlocks non-Rust consumers via the frozen C ABI — PhaseDeferred("§23") covers JNI/Java bindings until a JVM consumer requests them.

Recommended language: Rust, edition 2021, pinned toolchain 1.75. Rationale: stable std::arch::{x86_64,aarch64} SIMD intrinsics (needed by P4/§17), #![forbid(unsafe_code)] enforceable per-crate (P4), zero-cost abstractions matching the scalar-C throughput of Jerasure/ISA-L while keeping memory safety outside the one unsafe-carrying crate. Rejected: Go (klauspost/reedsolomon lineage) — GC pauses are incompatible with p99 encode-latency targets (§4) at the SIMD tier, though it wins for teams already on a Go monorepo (ADR-21); C (Jerasure/ISA-L lineage) — no memory-safety guarantee at the shard-parsing boundary (I13), though it wins for kernel-module targets with no Rust toolchain (ADR-21).

Prerequisites: linear algebra over finite fields; the Reed-Solomon polynomial-code construction (Reed & Solomon 1960); Cauchy vs. Vandermonde matrix theory; CRC32C; x86-64/aarch64 SIMD intrinsics; unsafe-Rust discipline.

Estimated timeline: Phase 0 — 1 week. Full system (Phase 0 – Phase 12) — 6–9 months at one engineer, or 3–4 months at a team of three running phases in parallel where the dependency graph (§41 Appendix B) allows.

2. Why Build This

Every durability system pays in one of two currencies: replication or parity. Three-way replication (GFS/HDFS/early-Ceph) is a flat 3× storage tax; parity (RAID-5/6, Reed-Solomon) trades a tunable (k+m)/k factor for more complex encode, decode, and — as the field took thirty-five years to fully internalize (Reed & Solomon 1960 → Rashmi 2014) — a hard repair-bandwidth problem. At petabyte/exabyte scale the storage delta is hundreds of millions of dollars over a fleet's life; it is the difference between a system that fits one data center and one that cannot afford to. Reed-Solomon coding is the quiet engineering underneath the cheap-cloud-storage industry, load-bearing in every major storage paper since RAID (Patterson, Gibson, Katz 1988).

The literature is unusually deep and unusually accessible: Reed & Solomon (1960) is six pages of algebra that is the entire construction; Plank's tutorials (1997, corrected 2005) translate the algebra into a working library and explain why GF multiplication eats 95% of encode CPU; Intel's ISA-L is the modern industrial reference every cloud object store either uses or has copied; Huang et al.'s Azure-LRC paper (2012) explains why pure RS is the wrong choice at cluster scale; Rashmi et al. (2014, two papers) close the repair-bandwidth gap from two different directions. This project sits at the intersection: Cauchy-systematic RS as the default (ADR-01/ADR-02), a Vandermonde reference for differential testing, LRC as a first-class repair-locality mechanism, and a repair planner that makes bandwidth cost visible to the consumer instead of implicit.

What Mastery Looks Like (5–8 competencies, each tied to the phase that builds it):

  • Deriving why Reed-Solomon achieves the Singleton bound n − k + 1 and what "MDS" buys operationally — Phase 1 (§13).
  • Constructing a Cauchy matrix and proving pairwise-distinct, non-singular submatrices by enumeration, not assertion — Phase 2 (§14).
  • Explaining why GF(2^8) multiplication is the bottleneck and closing it with a split-table SIMD shuffle — Phase 5 (§17).
  • Reasoning about repair bandwidth as a first-class cost, distinguishing decode from repair — Phase 7 (§19).
  • Trading parity-shard count for repair locality via LRC and stating the exact bandwidth/storage tradeoff — Phase 9 (§21).
  • Freezing a C ABI and reasoning about what "v1 forever" costs a maintainer — Phase 11 (§23).
  • Running a fleet-scale bitrot scrubber and budgeting its bandwidth against foreground reads — Phase 8 (§20).

6. Design Principles

  • P1 — GF(2^8) is the field; the byte is the symbol. Every shard is a byte-slice; every op is byte-in/byte-out. Tradeoff: caps k+m at 255/256 (I7). Operational implication: log/exp tables (512 B) fit L1 (§4). Violating it (e.g. mixing GF(2^16) silently) breaks every downstream conformance vector.
  • P2 — The matrix is Cauchy; the encoding is systematic. ADR-01/ADR-02. Tradeoff: Vandermonde is textbook-simpler but inverts slower. Operational implication: reads bypass decode entirely when no shard is lost. Violating systematic form means every read pays a decode, silently, forever.
  • P3 — Byte-slice-in/byte-slice-out, with a zero-copy escape hatch. encode allocates; encode_into writes caller buffers. Tradeoff: two APIs to keep in sync. Operational implication: the C ABI (§23) only exposes the zero-copy form. Violating it (allocating in the FFI path) forces an extra copy per call across the boundary.
  • P4 — unsafe is gated to ec-simd. Every other crate is #![forbid(unsafe_code)]. Tradeoff: the SIMD crate carries the entire safety argument. Operational implication: a documented safety contract (alignment, length, runtime feature check) per intrinsic wrapper. Violating it turns one crate's memory bug into an unbounded-blast-radius bug (I12 is the check that catches it).
  • P5 — Repair is a first-class operation, distinct from decode. A naive consumer decodes to repair (reads k shards); a repair-aware one calls RepairPlanner::plan (§19). Tradeoff: a second API surface to teach. Operational implication: LRC/Hitchhiker savings are invisible unless the consumer opts in. Violating it silently forfeits the entire repair-bandwidth investment of §21–§22.
  • P6 — Streaming is a codec loop, not a codec mode. A 1 TiB input is n complete (k,m) invocations over fixed chunks (§23). Tradeoff: bounded memory, unbounded cumulative header overhead. Operational implication: interrupted encodes resume at chunk boundaries (I14). Violating it (streaming arithmetic across chunk boundaries) breaks resumability.
  • P7 — Bitrot detection is the codec's responsibility. Every shard carries a CRC32C (I6); a CRC mismatch is treated as "missing," not "corrupt-but-present." Tradeoff: duplicates the storage layer's own checksum. Operational implication: the decoder never trusts bytes it did not itself verify. Violating it means a bit-rotted present shard silently corrupts a decode.
  • P8 — The encoder is deterministic and reproducible. Same input + params → same bytes, on every architecture, every SIMD tier (I5, I12). Tradeoff: forecloses any randomized or adaptive optimization inside the hot path. Operational implication: the Jerasure differential vectors are a permanent oracle (§18). Violating it collapses the entire conformance strategy.
  • P9 — k + m ≤ 255 strict, ≤ 256 by convention. Enforced at CodecParams::new (I7). Tradeoff: a hard ceiling on fan-out. Operational implication: a wider-field variant is PhaseDeferred("§9 ADR-03"). Violating it (accepting 256 raw) collides with the zero-element convention.
  • P10 — The C ABI is frozen at v1. ADR-08. Tradeoff: new functions only, never a changed signature. Operational implication: the generated header is committed in-tree so consumers need no Rust toolchain. Violating it breaks every C/Go/Python consumer on the next release.
  • P11 — The codec carries no opinion about the storage layer. No file I/O, no sockets, in ec-core/ec-gf256/ec-matrix/ec-encoder/ec-decoder. Tradeoff: the CLI must do all of that itself. Operational implication: portable to no_std + allocator (ADR-09), to WASM. Violating it couples the arithmetic core to one storage backend forever.
  • P12 — Performance regressions are bugs, equal to correctness regressions. CI fails a PR regressing any M# target (§35) by more than 5% without an ADR. Tradeoff: benchmark flakiness must be actively managed. Operational implication: every target is gated, not aspirational. Violating it lets throughput erode silently over years.
  • P13 — Differential testing is the primary correctness oracle. Cauchy vs. Vandermonde, scalar vs. every SIMD tier, our encoder vs. Jerasure vectors (§18). Tradeoff: every new code path needs a differential partner. Operational implication: a code path with no differential partner is untrusted by construction. Violating it means a shared bug in two "independent" implementations goes undetected.
  • P14 — MDS by construction, not by luck. Every k-subset of a Cauchy/Vandermonde encoding matrix is proven invertible by enumeration up to (k,m)=(16,8) (§13.2). Tradeoff: enumeration is O(C(n,k)) and must be capped. Operational implication: LRC explicitly is not MDS (P5, §21) and must branch on flavour. Violating it (assuming any LRC k-subset is invertible) produces a silent decode failure in production.

8. Domain Model

8.1 GF(2^8) field arithmetic

Elements are bytes 0..255. Addition/subtraction: XOR (I3). Multiplication: table lookup via discrete log/antilog over the multiplicative group generated by primitive element 0x02, modulo the irreducible polynomial 0x11D (x^8+x^4+x^3+x^2+1, ADR-04). Two 256-entry tables (LOG[0..256], EXP[0..510], doubled to avoid modular wraparound in the lookup) — 512 B total, fits L1 (§4).

mul(a, b):
  a==0 or b==0        -> 0                      (special case, no log entry for 0)
  otherwise            -> EXP[ LOG[a] + LOG[b] ]  (index sum, no explicit mod 255 needed
                                                     given the doubled EXP table)
inv(a):  a==0 -> undefined ;  a!=0 -> EXP[255 - LOG[a]]

The above is a lookup relation, not executable control flow — the actual kernel is a table read, described fully as signatures in §11.

8.2 Cauchy generator matrix

An m × k matrix, element (i,j) = 1 / (x_i ⊕ y_j), x_i = i+k for i∈0..m, y_j = j for j∈0..k, GF(2^8) addition (XOR). Plank's choice (ADR-01); requires all x_i ⊕ y_j pairwise distinct and non-zero (I4).

8.3 Vandermonde reference matrix

(i,j) = x_i ^ j (field exponentiation) — the textbook construction, shipped as a differential-testing reference (P13), never the production default.

8.4 Systematic form

[ I_k ]              [ I_k  ]
[     ]  --invert-->  [       ]   where the top k×k block of the raw
[ P_m ]  top-k block  [ P'_m ]   Cauchy/Vandermonde matrix is inverted and

8.5 Encoding as matrix multiplication

parity[m×L] = P'_m[m×k] · data[k×L] (L = shard length in bytes, GF(2^8) arithmetic throughout). Column-parallel: each output byte position is an independent length-k dot-product (P1, this is exactly what §17's SIMD shuffle parallelizes across bytes).

8.6 Decoding as matrix inversion

Given a present-shard bitmap, select any k present indices, form the k×k submatrix of rows {present indices} × cols 0..k, invert it (Gauss-Jordan, I9), multiply by the present-shard byte columns to recover all k data shards (§16.1).

8.7 State-transition table — codec lifecycle

State Trigger Next State Notes
Idle encode() called Encoding matrix already built at construction
Encoding matrix·data complete Encoded shards + headers emitted
Idle/Encoded decode() called VerifyingCrc I6 check per present shard
VerifyingCrc ≥k verified present SelectingSubmatrix else → Failed(Insufficient)
SelectingSubmatrix invertible found Inverting else → Failed(Singular), retry with new subset
Inverting inversion complete Reconstructing
Reconstructing multiply complete Decoded terminal, success
any unrecoverable error Failed(reason) terminal, DecodeError surfaced

8.8 Worked example — RS(2,1)

Data shards d0 = 0x03, d1 = 0x07. Cauchy row for m=1,k=2: coefficients [1,1] (the degenerate 1-parity case reduces to XOR). parity = (1·d0) ⊕ (1·d1) = 0x03 ⊕ 0x07 = 0x04. Losing d0: d0' = parity ⊕ d1 = 0x04 ⊕ 0x07 = 0x03 — recovered exactly (I1).

8.9 Malformed-input example

A shard header with magic != b"EC01" or payload_bytes > SHARD_PAYLOAD_MAX (§4) is rejected at ShardHeader::parse before any payload byte is read (I13) — this is the fuzz-harness (§18) primary target; a header claiming payload_bytes = u32::MAX must never reach an allocation call.

8.10 Failure-path example

Present bitmap has only k−1 verified shards (one failed CRC, I6, one genuinely absent). Decoder::decode returns DecodeError::Insufficient (I8) without attempting any matrix work — the state machine (§8.7) short-circuits at VerifyingCrc.

13. Phase 1 — Full GF(2^8) Arithmetic & Polynomial Machinery

13.1 Objectives

Extend the scalar kernel with polynomial arithmetic over GF(2^8) and formally prove the MDS property (I1, P14) by enumeration, laying the foundation the Phase-2 matrix constructions and the Phase-10 regenerating-code option (ADR-07) both need.

13.3 Deliverable

ec-gf256 exports Poly plus a passing property-test suite; a standalone MDS-proof test report enumerating pass/fail per (k,m).

13.4 Acceptance Criteria

  • Field-axiom proptest: 65,536 default cases pass; CI long-run job: 65,536× more.
  • MDS enumeration completes for (k,m) up to (16,8) in ≤ 90 s on one core, zero failures (I1).
  • Scalar GF(2^8) multiplication benchmark ≥ 200 MOps/s single core (§4 baseline for §17's SIMD comparison).

13.5 Conformance Fixtures

  • gf-arith/poly-eval-degree-0-to-16.bin — Horner vs. explicit-sum agreement.
  • mds-proof/k16-m8-enumeration.json — expected: 735,471 cases, 0 singular.
  • chaos/poly-zero-high-coeff.bin — a polynomial with a zero leading coefficient, expected: canonicalized (trimmed) on construction, not treated as higher-degree.

13.6 Pitfalls

  • Confusing coefficient multiplication (GF(2^8) table lookup) with bit-XOR (GF(2) addition) silently produces a codec that encodes but never decodes correctly.
  • The enumeration is O(C(n,k)) — uncapped, it explodes past (16,8); cap it in CI and document larger configurations as spot-checked, not exhaustively proven.

13.7 Performance Concerns

Enumeration cost grows combinatorially; keep the CI-gated cap distinct from an uncapped nightly job so PR latency stays bounded.

13.8 Edge Cases

A polynomial with all-zero coefficients (Poly::zero()); degree-0 (constant) polynomials; division by the zero polynomial (must return an explicit error, not panic).

13.9 Failure Analysis

A false-positive MDS proof (enumeration bug, not construction bug) would let a genuinely non-invertible submatrix reach production decode — mitigated by also running the Phase-4 decoder's own singularity check (I9) as a second, independent gate.

13.10 Operational Notes

The MDS-proof report is committed as a build artifact (mds-proof-report.json) and diffed in CI against the previous commit's report — a shrinking pass-count is a build failure, not a warning.

  • cauchy-matrix/k16-m8-invertibility.json — every row-subset invertible.
  • cauchy-matrix/differential-cauchy-vandermonde.bin — same recoverability, different parity bytes (both MDS).
  • chaos/singular-submatrix-forced.bin — a hand-constructed degenerate matrix, expected: MatrixError::Singular, not a panic.

14.6 Pitfalls

  • The Cauchy constraint x_i ⊕ y_j pairwise-distinct (I4) holds for the chosen x_i=i+k, y_j=j mapping only within k+m ≤ 255 (P9) — verify at construction, not just at test time.
  • A bug in invert corrupts the systematic derivation in a way that still passes naive roundtrip tests if encoder and decoder share the same matrix instance — the Vandermonde differential (P13) is the canary; never skip it.

14.7 Performance Concerns

Gauss-Jordan is O(n^3); at n ≤ 64 this is ~1 µs, never the throughput bottleneck (P1 remains the bottleneck at the byte-multiplication level, not the matrix level).

14.8 Edge Cases

k=1 (degenerate, matrix is a single column); m = n-1 (maximal parity, minimal data); a requested submatrix subset that repeats an index (must be rejected before inversion is attempted).

14.9 Failure Analysis

An inversion that silently returns a wrong-but-non-singular result (a logic bug, not a math impossibility) is undetectable by the singularity check alone — the differential test against Vandermonde and the Jerasure vectors (§18) are the only catches; document this explicitly in docs/failure-analysis/.

14.10 Operational Notes

ec-matrix emits no telemetry directly (it is a pure library called synchronously); ec-metrics (Phase 8, §20) wraps calls at the encoder/decoder boundary instead.

15. Phase 3 — Production RS(k,m) Encoder

15.1 Objectives

Replace the Phase-0 placeholder with the general Cauchy-systematic encoder (P2, ADR-01/02), the byte-slice and zero-copy APIs (P3), and shard-header framing.

15.2 Detailed Implementation Steps

Implement ReedSolomonEncoder (§11) over EncodingMatrix::cauchy/vandermonde selected by Flavour; the encode operation is the matrix multiplication of §8.5, parallel across byte columns. Fill ShardHeader (§11, I13) at encode time including CRC32C (P7, ADR-20) computed over the payload. Delete the Phase-0 Phase0Codec. Land the general_encode_decode and jerasure_vectors (ADR-16, P13) conformance buckets; benchmark against Rizzo 1997's systematic-encoding rationale (§5).

15.3 Deliverable

ec-encoder ships ReedSolomonEncoder; every (k,m) up to (16,8) encodes and its output validates against vendored Jerasure vectors byte-for-byte.

15.4 Acceptance Criteria

  • RS(6,3) scalar encode ≥ 1.0 GB/s (§4, M1); RS(10,4) ≥ 0.8 GB/s; RS(17,3) ≥ 0.5 GB/s.
  • jerasure_vectors bucket: 100% byte-identical match across all vendored (k,m,data) triples.
  • encode_into zero-copy path produces byte-identical output to encode (P3).

15.5 Conformance Fixtures

  • encode-decode/rs-6-3-4mib.bin — canonical mid-size roundtrip fixture.
  • jerasure-vectors/rs-17-3-1mib.bin — Backblaze-shape vendored oracle match.
  • chaos/mismatched-shard-lengths.bin — expected: EncodeError::ShardLen.

15.6 Pitfalls

  • The inner column-wise GF-multiply-XOR loop is the hot path the autovectorizer cannot help with — this is precisely the gap Phase 5 (§17) closes with the Plank-Greenan-Miller shuffle (§5).
  • encode_into's alignment contract is stricter than encode's allocating path; document it (align_of::<u8>() scalar, 32 B AVX2, 64 B AVX-512) and check on entry.
  • Jerasure 1.2 vs. 2.0 parity-shard ordering differs — vendor exactly 1.2.0 (ADR-16) and record its vector-file SHA-256.

15.7 Performance Concerns

Encode throughput is bounded by scalar GF-multiply until §17; batching across shards (not just bytes) does not help — the bottleneck is per-byte, not per-call (P1).

15.8 Edge Cases

Single-byte shard length; shard length not a multiple of any SIMD width (irrelevant until Phase 5, but the header/CRC framing must already tolerate it); m=0 rejected (I7) before any matrix work.

15.9 Failure Analysis

A wrong CRC written at encode time is invisible until decode treats a valid shard as missing (§16.6) — the Phase-4 "all-parity-present" CRC-consistency check exists specifically to catch this class early.

15.10 Operational Notes

Encode-path spans are emitted via ec-metrics starting Phase 8 (§20); until then, criterion benchmark output (benchmarks/results/encode-*.json) is the only throughput signal, versioned and regression-gated at ±5% (P12).

16. Phase 4 — Decoder, Repair Semantics, Multi-Shard Loss

16.1 Objectives

Land the general decoder: given any k of k+m shards, reconstruct the missing ones via the state machine of §8.7, honoring I8/I9.

16.2 Detailed Implementation Steps

Implement ReedSolomonDecoder::decode (§11) following §8.6's matrix-inversion recipe: verify CRC per shard (I6), select k present indices, build and invert the submatrix (I9), multiply to recover data, re-encode any missing parity shards as a cheap second pass. Implement ec-verifier's post-decode re-encode-and-compare check (opt-in, debug-default-on per P7/I6). Reference Moon 2005's syndrome-decoding contrast in the module doc (§5) to justify choosing matrix-inversion over syndrome decoding for this construction.

16.3 Deliverable

ec-decoder recovers from any 1..m simultaneous shard losses for every tested (k,m); ec-verifier catches an injected encoder/decoder asymmetry in CI.

16.4 Acceptance Criteria

  • general_encode_decode bucket covers every loss pattern up to m shards, 100% pass.
  • RS(6,3) scalar decode ≥ 0.8 GB/s (§4).
  • Decode with < k present shards returns DecodeError::Insufficient in 100% of cases (I8), never a partial/garbage result.

16.5 Conformance Fixtures

  • multi-loss/rs-10-4-lose-4.bin — maximal-loss recovery for RS(10,4).
  • single-loss/rs-6-3-lose-p2.bin — parity-shard loss, re-encode path exercised.
  • chaos/insufficient-shards.bin — k-1 present, expected DecodeError::Insufficient.

16.6 Pitfalls

  • Naively picking the first k present shards assumes MDS (I1, P14) — true for Cauchy/Vandermonde here, false for LRC (Phase 9, §21); the Phase-4 decoder is explicitly MDS-only; the LRC-aware submatrix-selection heuristic is built directly in Phase 9 (§21), not deferred beyond the plan.
  • A wrong parity CRC at encode time is masked by the decoder simply treating that shard as missing and reconstructing it — add an explicit "decode with all parity present, assert CRC matches" test so this class surfaces in CI, not production.

16.7 Performance Concerns

ec-verifier's re-encode check doubles decode cost — default-off in release builds, default-on in the conformance harness only (P12 exempts test-only overhead from the regression gate).

16.8 Edge Cases

All m parity shards lost simultaneously (pure data-shard recovery, no re-encode needed); all data shards lost (full re-encode from decoded data); a present shard whose CRC fails but whose header is otherwise well-formed (I6 treats it as missing, not malformed).

16.9 Failure Analysis

A Matrix::invert bug that returns a wrong-but-non-singular inverse silently corrupts every decode using that submatrix selection — blast radius is every consumer read hitting that specific (k,m,loss-pattern); contained by the Jerasure differential (§18) and the ec-verifier re-encode check together, not by either alone.

16.10 Operational Notes

Decode failures increment insufficient_shards_total / singular_submatrix_total (I8/I9 telemetry, §7); operator-visible via the ec scrub/ec rebuild runbooks (§24.3, §27).

17. Phase 5 — SIMD Acceleration (AVX2/AVX-512/GFNI/NEON)

17.1 Objectives

Close the scalar-throughput gap (§4) with the Plank-Greenan-Miller (2013) split-table shuffle (P4, P13), lifting encode from ~1 GB/s to 6–15 GB/s.

17.2 Detailed Implementation Steps

Implement per-architecture shuffle-table GF-multiply-add kernels (x86_avx2.rs/x86_avx512.rs/x86_gfni.rs/arm_neon.rs, §10.3) as unsafe fn signatures with a documented safety contract (alignment, length, CPU-feature precondition — P4): split each byte into 4-bit high/low halves, shuffle-lookup each half against a 16-entry table, XOR the halves (Plank-Greenan-Miller 2013, §5). Implement select_gf_mul_add as a priority table, not a code branch chain: GFNI

AVX-512 > AVX2 > SSSE3 > NEON > scalar, chosen via is_x86_feature_detected!/ is_aarch64_feature_detected! at first call, cached thereafter. Land the simd_path differential bucket (I12, P13) against every boundary-adjacent buffer size.

17.3 Deliverable

ec-simd ships all five kernels plus the scalar fallback; every kernel is differentially verified byte-identical to scalar (I12) on its target CPU.

17.4 Acceptance Criteria

  • RS(6,3) AVX2 ≥ 6.0 GB/s; AVX-512 ≥ 12.0 GB/s; GFNI ≥ 15.0 GB/s; NEON ≥ 10.0 GB/s (§4, M2).
  • simd_path bucket: 100% byte-equality across coefficients 0..256 × sizes {31,32,33,63,64,65,127,128,129,255,256,257}.
  • Runtime-detection fallback exercised in a CI host lacking AVX-512 (feature-gated matrix job).

17.5 Conformance Fixtures

  • simd/avx2-vs-scalar-boundary-sizes.bin — the size set above, expected: byte-equal.
  • simd/gfni-vs-avx512.bin — cross-tier equality on GFNI-capable hardware.
  • chaos/unaligned-simd-input.bin — deliberately misaligned buffer, expected: correct output via the unaligned-load path, not a fault.

17.6 Pitfalls

  • _mm256_shuffle_epi8 operates per-128-bit-lane, not across the full 256-bit register — a cross-lane assumption silently corrupts half the output.
  • #[target_feature(enable = "avx2")] is a hard requirement; calling the attributed function without a prior runtime check is undefined behavior, not merely slow (P4's safety contract exists exactly to prevent this).
  • Unaligned loads are fast on modern CPUs, ~5–10% slower on older Skylake steppings — accepted cost per ADR-10; an alignment-aware path is PhaseDeferred("§17").

17.7 Performance Concerns

Tail handling (< SIMD-width remainder) falls back to scalar per call — negligible at multi-KB shard sizes, dominant at sub-32-byte test fixtures; the boundary-size fixture set (§17.5) exists specifically to catch tail bugs.

17.8 Edge Cases

A buffer exactly at the SIMD width boundary (no tail); a CPU reporting AVX2 but not SSSE3 (impossible on real hardware but defensively tested); GFNI present without AVX-512 (valid on some server SKUs — priority table must still resolve correctly).

17.9 Failure Analysis

A kernel that silently diverges from scalar on an untested buffer size is the single highest-severity SIMD bug class — caught only by I12's differential test; the boundary-size fixture set is the mitigation, not a proof of absence.

17.10 Operational Notes

The selected SIMD tier is logged once at process start (simd_tier_selected gauge); the CI matrix runs the full conformance suite on at least one host per tier (Skylake, Ice Lake, Apple Silicon, §4 NUMA assumption).

19. Phase 7 — Repair Planner & Minimum-Bandwidth Reconstruction

19.1 Objectives

Make repair bandwidth a first-class, queryable cost (P5) distinct from decode, ahead of LRC (Phase 9) and Hitchhiker (Phase 10) making that cost actually low.

19.2 Detailed Implementation Steps

Implement RsPlanner (§11) per P5: for pure RS, plan() selects the first k present indices and accounts bandwidth = k × payload_bytes, flops = k² (the inversion cost, I9). Stub LrcPlanner/HitchhikerPlanner returning PlannerError until Phases 9–10 land (built out in §21 and §22 respectively, not deferred beyond the plan). Wire ec-cli plan to print {reads, ops, bandwidth, flops} as JSON — reference Rashmi et al. 2014's HotStorage framing of repair cost (§5) in the module doc.

19.3 Deliverable

ec-repair-planner ships RsPlanner; ec cli plan --k=6 --m=3 --present=... emits a valid cost-accounted plan.

19.4 Acceptance Criteria

  • repair_planner bucket: pure-RS plans validated for every (k,m) and every present-bitmap in the tested range (§4).
  • repair_plan_latency benchmark ≤ 5 µs for RS(6,3) (§4, M4).
  • Executing a returned plan recovers all missing shards in 100% of harness runs.

19.5 Conformance Fixtures

  • repair-planner/rs-6-3-plan-lose-d2.json — expected reads = first k present, exact bandwidth figure.
  • chaos/planner-length-mismatch.bin — present-bitmap length ≠ n, expected PlannerError::Length.

19.6 Pitfalls

  • Conflating the planner with the decoder — a consumer bypassing the planner and calling Decoder::decode directly is correct but forfeits every bandwidth optimization from Phase 9 onward (P5).
  • bandwidth must count bytes read from storage, not bytes after any storage-layer compression/dedup — the planner's contract is disk-read bytes, full stop.

19.7 Performance Concerns

Plan computation itself must stay far below the I/O it plans for (≤ 5 µs vs. milliseconds of actual shard reads) or the planner becomes its own bottleneck.

19.8 Edge Cases

A present-bitmap with exactly k shards true (no choice in shard selection); a present-bitmap with all n shards true (planner should still pick a minimal-cost k, not read everything).

19.9 Failure Analysis

A planner returning a plan whose shards are insufficient (a bookkeeping bug, not a math one) is caught by the harness's "execute the plan, assert recovery" fixture (§19.5) — never trust the plan without executing it in tests.

19.10 Operational Notes

ec cli plan output feeds directly into the future ec rebuild (§24) invocation; planner latency is tracked via ec-metrics starting Phase 8 (§20).

20. Phase 8 — Storage Backend & Bitrot Scrubber

20.1 Objectives

Wrap the codec in a concrete on-disk layout and a background scrubber, giving the library its first operational (not purely in-memory) surface.

20.2 Detailed Implementation Steps

Define the per-object directory layout: manifest.json (codec params, shard hashes, encode time) plus one *.shard file per data/parity index (§10.6-adjacent). Implement Scrubber (§11-adjacent) with a configurable concurrency and schedule (P7/I6 applied continuously): read every shard, verify CRC32C, emit ScrubReport{scanned_objects, scanned_shards, crc_failures, io_errors, elapsed}. Wire ec-metrics (OpenTelemetry spans + Prometheus counters, ADR-12) at the encode/decode/scrub call boundaries for the first time in the phase plan.

20.3 Deliverable

A storage layout that survives a process crash mid-encode (atomic rename from .tmp); a scrubber that completes a full-fleet pass on the configured schedule and reports CRC failures.

20.4 Acceptance Criteria

  • Default scrub schedule: full-fleet cycle every 14 days, ≤ 3.3 GB/s bandwidth for a 4 PiB fleet (§4, M3).
  • A deliberately bit-flipped shard is detected within one scrub cycle, 100% of injected-fault runs.
  • Encoder writes via .tmp + atomic rename; an interrupted encode leaves zero partially-visible objects.

20.5 Conformance Fixtures

  • storage-backend/scrub-detects-bitflip.bin — one-byte flip, expected: detected, logged, crc_failures incremented.
  • chaos/interrupted-encode-crash.bin — simulated crash mid-write, expected: no partial object visible after recovery.

20.6 Pitfalls

  • Unthrottled scrubbing competes with foreground reads — the 14-day default is conservative precisely to keep this under the §4 bandwidth budget; document the trade-off in docs/runbooks/scrub.md.
  • A missing fsync before rename reintroduces the exact interrupted-write hazard the atomic-rename design was meant to close.

20.7 Performance Concerns

Scrub I/O must be rate-limited independently of encode/decode I/O — a shared token bucket (documented, not code) prevents scrub from starving foreground traffic (§4).

20.8 Edge Cases

An object directory missing its manifest.json (treat as corrupt, alert, do not guess codec params); a shard file present but zero-length (treat as CRC failure, not a parse crash).

20.9 Failure Analysis

A scrubber that silently stops running is the single worst operational failure mode for I6 — the Phase-8 documentation ships a "your scrubber is not running" Prometheus alert template specifically to close this gap (§27).

20.10 Operational Notes

ScrubReport is exported as scrub_crc_failures_total, scrub_io_errors_total, scrub_scanned_shards_total; runbooks docs/runbooks/scrub.md and docs/runbooks/bitrot.md (§10.6) cover triage.

21. Phase 9 — Local Reconstruction Codes (Azure-LRC, XORBAS)

21.1 Objectives

Cut single-shard repair bandwidth from k reads to r ≪ k reads (P5) using local parity groups (Huang et al. 2012; Sathiamoorthy et al. 2013, §5).

21.2 Detailed Implementation Steps

Implement AzureLrcEncoder (§11, Flavour::Lrc(l,r)) per ADR-06: partition k data shards into l locality groups of k/l shards each, each with its own local parity, plus r_global global parities covering all data shards. Implement XorbasEncoder as the differential-testing partner (P13, ADR-06). Make LrcPlanner real (§19 stub → implementation): single-shard loss reads the r shards in that shard's local group plus its local parity (I10); multi-shard-loss within one group falls back to the global-parity path. Enforce k divisible by l at CodecParams construction.

21.3 Deliverable

ec-lrc ships both constructions; LrcPlanner is real; the Azure default (k=12, l=2, r=2) and XORBAS (k=10, l=2, r=2) both round-trip and report the bandwidth saving.

21.4 Acceptance Criteria

  • lrc bucket green for both constructions at their published parameters (§5).
  • Single-shard repair for (12,2,2) reads exactly 6 shards vs. 12 for pure RS — measured 2× saving (§4, M3; I10).
  • CodecParams::new rejects k not divisible by l with a named error, not a panic.

21.5 Conformance Fixtures

  • lrc/azure-12-2-2-single-loss.bin — expected: 6-shard local repair, not 12.
  • xorbas/xorbas-10-2-2-single-loss.bin — comparable XORBAS repair-locality check.
  • chaos/lrc-non-invertible-k-subset.bin — a k-subset that is not invertible for LRC (unlike MDS RS), expected: planner/decoder fall back to global recovery, not a silent wrong answer.

21.6 Pitfalls

  • LRC is not MDS (P14 caveat) — some k-subsets are non-invertible; the Phase-4 MDS-only decoder must not be reused unmodified (§16.6); the LRC decoder checks invertibility and falls back.
  • Azure-LRC parameters are constrained (k % l == 0) — reject invalid combinations at construction, not at encode time.
  • The bandwidth saving is single-shard-loss-only; two losses in the same group still require global recovery — document this limit in the planner's own output, not just in prose.

21.7 Performance Concerns

lrc_repair_bandwidth benchmark reports the RS-vs-LRC ratio directly (§4, M3) — tracked as its own regression-gated metric, distinct from raw encode/decode throughput.

21.8 Edge Cases

l=1 (degenerates to a single global group, no locality benefit — must still be valid, just pointless); a group boundary that does not align with shard indices (rejected at construction, not silently truncated).

21.9 Failure Analysis

A repair that silently uses the global path when the local path should have sufficed is a performance bug, not a correctness bug — but it defeats the entire purpose of Phase 9; the lrc_repair_bandwidth benchmark (§21.7) is the regression gate that catches this class.

21.10 Operational Notes

ec cli plan reports which planner (Rs/Lrc/Hitchhiker) was used and the resulting bandwidth, so operators can verify LRC is actually engaged in production, not silently falling back.

22. Phase 10 — Hitchhiker & Regenerating Codes

22.1 Objectives

Cut repair bandwidth a further 25–45% (Rashmi et al. 2014, SIGCOMM, §5) by piggybacking repair traffic on already-scheduled degraded reads, and document (without shipping) the regenerating-code alternative (Dimakis et al. 2010).

22.2 Detailed Implementation Steps

Implement the Hitchhiker encoder (§11-adjacent) as RS-plus-piggyback: each parity shard carries standard parity plus small auxiliary bytes computed at encode time (ADR-18). Bump the shard header to v2 for Hitchhiker shards (I11-adjacent version discipline) so v1 readers refuse rather than misinterpret. Make HitchhikerPlanner real: it asks the storage layer for the next scheduled degraded read and attaches the auxiliary bytes to that response. Document MSR/MBR regenerating codes (ADR-07) as a deferred alternative, reserving the ec-regenerating crate name without implementing it (PhaseDeferred("§22"); register entry, §38).

22.3 Deliverable

ec-hitchhiker ships the piggyback encoder/decoder/planner; measured repair-bandwidth saving vs. pure RS and vs. Azure-LRC is reported by benchmark.

22.4 Acceptance Criteria

  • hitchhiker bucket: round-trip and piggyback-correctness both green.
  • Measured repair-bandwidth saving 25–45% vs. pure RS (§4, matching the Facebook warehouse-cluster figures in Rashmi 2014).
  • A v1 reader presented a v2 (Hitchhiker) shard refuses with a named version-mismatch error, never silent misparse (I13-adjacent).

22.5 Conformance Fixtures

  • hitchhiker/piggyback-roundtrip.bin — encode, degraded-read simulate, repair via piggyback bytes only.
  • chaos/v1-reader-v2-shard.bin — expected: explicit version-mismatch rejection.

22.6 Pitfalls

  • Hitchhiker requires storage-layer cooperation — a consumer not implementing the piggyback read path gets zero benefit and must not be silently assumed compatible; a worked example for the DFS chunkserver (rank 86) and object store (rank 107) is mandatory documentation, not optional.
  • The piggyback bytes are an in-band extension of the parity payload — treating them as opaque padding instead of versioned data breaks forward compatibility.

22.7 Performance Concerns

The piggyback computation adds encode-time CPU (auxiliary-byte derivation) in exchange for repair-time network savings — the tradeoff is quantified per-deployment via the lrc_repair_bandwidth/Hitchhiker-equivalent benchmark, not assumed universally beneficial.

22.8 Edge Cases

A degraded read that never actually occurs (piggyback opportunity never materializes, repair must fall back to a direct read); a storage layer that partially implements the piggyback contract (must fail closed, not silently degrade to pure RS bandwidth without telling the operator).

22.9 Failure Analysis

Silent piggyback-opportunity starvation (the repair waits indefinitely for a degraded read that isn't coming) is a liveness bug — mitigated by a bounded wait with fallback to the RsPlanner path, logged as a distinct event from a genuine piggyback success.

22.10 Operational Notes

Hitchhiker's bandwidth saving is only realized with storage-layer support — the runbook documents how to verify piggyback reads are actually occurring (a hitchhiker_piggyback_hits_total vs. hitchhiker_fallback_total counter pair).

23. Phase 11 — Streaming Encoder, C FFI, Cross-Process Repair RPC

23.1 Objectives

Extend the codec beyond in-memory buffers (P6) and beyond Rust (P10), landing the streaming API, the frozen C ABI, and an optional cross-process repair RPC.

23.2 Detailed Implementation Steps

Implement StreamingRsEncoder (§11) over fixed 4 MiB chunks (ADR-22), each a complete codec invocation (P6), emitting EncodedChunk{data,parity,offset} per chunk with a resumable cursor (I14). Implement ec-ffi's flat extern "C" surface (§11-adjacent: ec_codec_new/free/encode/decode/plan) with a cbindgen -generated, committed header (ADR-08, P10); document every precondition (buffer validity, alignment, aliasing) since Rust's safety guarantees end at this boundary (P4 does not extend past FFI). Implement the optional ec-proto gRPC RepairService (ADR-13) as a thin wrapper over ec-decoder/ec-repair-planner, feature-gated off by default.

23.3 Deliverable

A 1 GiB stream encodes and recovers from a shard loss chunk-by-chunk; a C consumer in examples/ffi-c-consumer/ builds against the committed header and round-trips; the gRPC smoke client completes a Plan/Repair call pair.

23.4 Acceptance Criteria

  • streaming bucket: 1 GiB input, chunked, one shard dropped mid-stream, full recovery, hash-verified.
  • ffi bucket: C-consumer round-trip byte-equal to the Rust-direct path.
  • Interrupt-and-resume at any chunk boundary produces output identical to an uninterrupted encode (I14).

23.5 Conformance Fixtures

  • streaming/1gib-interrupted-resume.bin — resume-equivalence check (I14).
  • ffi/c-consumer-roundtrip.bin — cross-language byte-equality.
  • chaos/ffi-null-pointer.bin — a null data pointer across the FFI boundary, expected: EC_ERR_PARAMS, never a crash in the conformance harness's guarded wrapper (documented as a known unguarded case for real C callers, per SECURITY.md).

23.6 Pitfalls

  • The 4 MiB default chunk size trades small per-chunk header overhead against RAM footprint — matches the DFS chunk-write batch (ADR-22); revisit only with measured justification.
  • The FFI unsafe boundary is where Rust's guarantees end — a misbehaving C caller can corrupt memory; this is unavoidable at any FFI boundary and is documented, not "fixed."
  • The gRPC surface is opt-in (--features proto) — Phase 0–10 ship without it; do not accidentally make it a default-on dependency.

23.7 Performance Concerns

Streaming's working memory is bounded by chunk size × n (§4), not input size — this is the entire point of P6; verify no code path buffers the whole stream.

23.8 Edge Cases

An input whose final chunk is shorter than 4 MiB (must still encode correctly, not be padded silently in a way that changes recoverable byte count); an FFI caller passing mismatched shard_len across data/parity arrays (rejected with EC_ERR_SHARD_LEN).

23.9 Failure Analysis

An FFI caller violating the documented alignment/aliasing contract produces undefined behavior outside the library's control — contained by documentation (SECURITY.md) and by recommending a higher-level owning wrapper (Go cgo, Python cffi) rather than raw pointer use.

23.10 Operational Notes

The committed header at crates/ec-ffi/include/ec.h is diffed in CI against the cbindgen-regenerated version — any drift fails the build (I11); the gRPC service's Plan/Repair RPCs are traced via ec-metrics spans identical to the in-process path.

24. Phase 12 — Operator Tooling (CLI)

24.1 Objectives

Ship the operator surface (P11, ADR-17) that makes every library capability reachable without writing Rust: ec encode/decode/scrub/rebuild/plan.

24.2 Detailed Implementation Steps

Implement each CLI verb (§10.4) as a thin wrapper: clap-parsed flags map 1:1 to library parameters (P11); output is JSON (--output=json) or human-readable (default), never a CLI-invented configuration layer. Wire ec rebuild to require --force before overwriting an existing shard (a safety guard, not a suggestion). Write the four operator runbooks (§10.6: triage.md, scrub.md, rebuild.md, bitrot.md) and the three worked examples (minio-shape, backblaze-vault, ffi-c-consumer, §10.6) referencing the shapes from Backblaze's B2 vaults and MinIO's 4+2 layout (§5).

24.3 Deliverable

The ec binary; every verb in §10.4 works end-to-end against a real directory tree; runbooks and worked examples committed.

24.4 Acceptance Criteria

  • ec encode --k 6 --m 3 on a 4 MiB file completes and reports a throughput figure consistent with §4's targets (within the ±5% regression gate, P12).
  • ec rebuild refuses to overwrite an existing shard without --force, 100% of tested invocations.
  • ec scrub reports zero CRC failures on an uncorrupted fixture tree and exactly one on a tree with one injected bit-flip.

24.5 Conformance Fixtures

  • ffi/minio-4-2-shape.bin — worked-example roundtrip.
  • chaos/rebuild-without-force.bin — expected: refusal, non-zero exit, no overwrite.
  • streaming/backblaze-17-3-vault.bin — worked-example roundtrip at Backblaze's published shape.

24.6 Pitfalls

  • Any flag that does not correspond to a library parameter is scope creep — the CLI must stay predictable from the library alone (P11); resist adding CLI-only configuration.
  • ec rebuild is the single command that can destroy data if misused — the --force guard and the rebuild.md runbook exist specifically because this is the highest-blast-radius operator action in the system.

24.7 Performance Concerns

CLI process-startup overhead (codec construction, §4: ≤ 1 ms) must stay negligible relative to the encode/decode/scrub work it wraps — no per-invocation table regeneration (tables are compile-time, ADR-05).

24.8 Edge Cases

A target directory that already contains a partial object from a previous interrupted run (must be detected and reported, not silently overwritten); a plan invocation against a present-bitmap with fewer than k shards (must report the insufficiency, not crash).

24.9 Failure Analysis

A careless ec rebuild invocation without understanding the present-shard state is the primary operator-error failure mode this phase defends against — the runbook's first section is explicitly "read the plan output before you rebuild."

24.10 Operational Notes

Every CLI verb emits a structured log line (JSON) suitable for ingestion by the same observability stack as the library's OTel spans (ADR-12); exit codes are non-zero and distinct per failure class (EC_ERR_* mirrored from the FFI layer, §23).

27. Operational Readiness

Metrics (Prometheus, ADR-12): every counter/gauge named in §7 (invariant telemetry) and §25/§26 tables is exported; dashboards group by codec instance (k,m,flavour). Tracing: OpenTelemetry spans wrap every encode/decode/plan/ scrub call, propagated through ec-proto when enabled (§23). Structured logging: JSON lines from the CLI (§24.10) and the scrubber (§20.10). Dashboards: encode/decode throughput vs. §4 targets; scrub cycle age vs. the 14-day SLO; repair bandwidth by planner tier (Rs/Lrc/Hitchhiker). Alerting philosophy: page only on liveness (scrubber not running, T8) and correctness (CRC-mismatch rate above baseline, ABI diff) — never on a single benchmark blip. SLOs: scrub full-fleet cycle ≤ 14 days; repair RTO ≤ 30 s for a single shard at 10 Gbps (§4). Incident response: the four runbooks (§10.6) are the first response; each links back to the relevant Failure Mode row (§26). Backup/restore: not applicable to the codec itself (stateless library); the consumer's object manifests are the durable state, covered by their own backup story. Deployment topology: linked in-process with every consumer; the CLI/scrubber run as a sidecar or cron-scheduled job per fleet node. Canary/rolling-upgrade/rollback: a new codec version is canaried by running its conformance suite against the previous version's Jerasure-vector-validated output before fleet-wide rollout (I5); rollback is a version pin, no data migration needed because the wire format (§28) is stable within a major version.

28. Compatibility & Versioning

Wire/storage format: the 32-byte ShardHeader (§11) is stable within a major version; a version field bump (v1→v2, as Hitchhiker does, §22) requires explicit reader opt-in — a v1 reader must refuse a v2 shard, never guess (I13-adjacent). Schema evolution: manifest.json (§20) is JSON, additive-only within a major version; unknown fields are ignored by readers, never rejected. API stability: the Rust trait surface (Encoder/Decoder/RepairPlanner/StreamingEncoder, §11) follows SemVer; a breaking trait change is a major-version bump. C ABI: frozen at v1 (ADR-08, P10, I11) — additive functions only, enforced by the cbindgen header-diff CI gate. Migration: moving a fleet from RS-only to LRC requires re-encoding existing objects (no in-place codec-flavour migration is supported — document this explicitly as a non-goal, §1). Rolling-upgrade guarantees: mixed-version fleets are safe as long as every shard's header version field is honored by every reader (I13); mixed SIMD tiers across nodes are always safe by construction (I12 guarantees identical output regardless of which tier produced a shard). Deprecation policy: a deprecated flavour or CLI flag is announced one minor version ahead, removed only at the next major version, per CHANGELOG.md (§10.1).

29. Testing & Verification Strategy

Unit: per-crate, exercising every signature in §11 (Core Schema). Property (proptest): field axioms (§13.2), MDS-by-enumeration (§13.2), Cauchy-vs-Vandermonde recoverability equivalence (§14.2) — all tied to I1, I3, I4, I9. Differential (P13): scalar vs. every SIMD tier (I12, §17.2), our encoder vs. Jerasure vectors (ADR-16, §18.2). Fuzzing (§18.2): four cargo-fuzz targets, 24 h weekly, seed corpus source-controlled. Chaos: the conformance/corpora/chaos/ bucket (§10.5) — malformed shards, oversized inputs, interrupted writes, non-invertible LRC subsets — exercised on every conformance run, not just chaos-specific jobs. Deterministic replay: the state-machine simulator (§7's debugging methodology) replays any (k,m,flavour,loss-pattern) combination and asserts one invariant per transition. Soak: the weekly 24 h fuzz job doubles as a soak test for long-running memory/resource stability. Fault injection: the scrubber bit-flip fixture (§20.5) and the interrupted-encode-crash fixture (§20.5) are fault-injection tests proper, not merely unit tests with a misleading name. Conformance: every bucket in §10.5's corpora/ maps 1:1 to a phase's §N.5 fixtures — a bucket reporting Deferred beyond its owning phase's completion is a build-blocking regression. Performance-regression gating: every M# target (§31) is checked in CI at ±5% (P12); a miss without an accompanying ADR blocks merge.

30. Build & Release Engineering

Reproducible builds: Nix flake (ADR-15) pins the toolchain and every build input; sccache shares compilation artifacts across maintainer machines. Artifact signing: released binaries (ec-bin, the cdylib) are signed; the signature is verified by the release workflow before publish. SBOM: generated per release via cargo-deny's dependency graph, attached to the GitHub release. Release channels: stable (SemVer-tagged), nightly (tip-of-main, unsigned, for internal consumers only). 31. Performance Engineering

Benchmarking methodology: criterion (ADR-11) with a fixed hardware matrix (Skylake/Ice Lake/Apple Silicon, §4 NUMA assumption); every result versioned under benchmarks/results/ and diffed against the committed baseline. Profiling: perf/cachegrind for cache-locality analysis of the GF-multiply inner loop (§15.6); valgrind --tool=massif for the streaming encoder's working-set verification against the §4 memory-ceiling table. Allocation analysis: the encode/encode_into split (P3) exists precisely so the zero-copy path can be measured with zero allocator calls in the hot loop. Lock contention: none in the core codec (immutable, Send + Sync after construction, §11); the scrubber's concurrency pool is the only lock-adjacent surface, profiled separately (§20.7). Cache analysis: the 512-byte log/exp tables (§4) are sized to guarantee L1 residency; a regression that grows the tables past L1 is a correctness-adjacent performance bug. Syscall overhead: the scrubber and CLI are the only syscall-heavy paths (file reads/writes); the core codec issues none. Tail-latency analysis: p99 figures in §4 are derived from the scalar/SIMD throughput floors plus a fixed per-call overhead budget (§35's capacity model shows the derivation).

32. Scalability Analysis

Constant regardless of scale: per-byte GF-multiply cost (P1, O(1) table lookup); matrix-inversion cost per codec instance (O(n³), n ≤ 255, negligible at production (k,m)). Grows with scale: aggregate encode/decode throughput demand (linear in ingest rate); scrubber bandwidth (linear in fleet size, §4's 3.3 GB/s figure scales linearly with fleet bytes); repair traffic under node churn (linear in failure rate × shard count, mitigated by LRC/Hitchhiker, §21–§22). Named bottlenecks, in order: (1) scalar GF-multiply throughput until SIMD is engaged (§17); (2) network fabric bandwidth for repair traffic once SIMD removes the compute bottleneck (§19, §21); (3) FD/concurrency ceiling on the scrubber (§4's 64-FD budget) at extreme fleet sizes. Horizontal scaling: the codec is stateless and per-object — horizontal scale is "more nodes running the same library," with no shared coordination required (P11). Sharding/partitioning: not applicable to the codec itself; the consumer partitions objects across nodes and the codec is invoked per-object. Coordination overhead: zero for encode/decode (embarrassingly parallel across objects); non-zero only for the optional cross-process repair RPC (§23), which is opt-in specifically to avoid imposing coordination cost on consumers that don't need it. Practical ceiling: network fabric bandwidth for repair traffic at high churn rates — the lever beyond it is the repair-bandwidth axis itself (pure RS → LRC → Hitchhiker → regenerating codes, ADR-07, §37), each trading construction complexity for a lower ceiling.

33. Mental Models & First Principles

  • MM1 — A GF(2^8) multiply is a shuffle, not a loop. Predicts SIMD throughput ceilings directly from register width. Bug class without it: writing a per-byte scalar loop and being surprised SIMD "doesn't help" because the shuffle-table restructuring was skipped. Applies at §17.
  • MM2 — Systematic code = identity block + parity block. Predicts that uncorrupted reads never touch the decoder. Bug class without it: routing every read through decode "for safety," destroying the entire throughput argument for P2. Applies at §8.4, §15.
  • MM3 — MDS means any k survive, by construction, not by luck. Predicts that correctness is provable by enumeration, not by hoping the matrix "happens to work." Bug class without it: trusting an unproven matrix construction and discovering a singular submatrix in production. Applies at §13.2, §7 I1.
  • MM4 — Repair is not decode. Predicts that a bandwidth-aware consumer needs a separate API. Bug class without it: always paying the full-k-shard-read cost even when LRC/Hitchhiker could have made it cheap. Applies at §19.
  • MM5 — Locality trades parity shards for bandwidth. Predicts the exact storage/bandwidth tradeoff curve LRC sits on. Bug class without it: treating LRC's extra parity shards as pure waste instead of a deliberate bandwidth purchase. Applies at §21.
  • MM6 — The codec has no opinion about storage. Predicts portability to embedded/WASM/any consumer. Bug class without it: accidentally coupling arithmetic code to a specific storage backend, making the library un-reusable. Applies at §11, P11.
  • MM7 — Determinism is the entire premise of conformance. Predicts that any non-deterministic path (a random tie-break, an uninitialized read) poisons every downstream differential test. Bug class without it: a flaky conformance suite that is trusted anyway. Applies at §18, P8.
  • MM8 — The field is exact; only the construction can be singular. Predicts that GF(2^8) arithmetic never has floating-point-style rounding error — every failure is a construction/logic bug, never numerical drift. Bug class without it: adding defensive epsilon-comparison code that has no meaning in an exact field. Applies at §8.6, §14.

37. Alternative Architectures (Roads Not Taken)

A1 — Pure replication (no coding).

Show the original text diagram
   write --> [copy 1] [copy 2] [copy 3]     read <-- any one copy

Regime where it wins: small clusters where network cost of extra copies is cheap relative to engineering complexity, and read-path simplicity dominates. Real system: early Ceph / GFS default 3-replica placement. Rejected here because the flat 3× storage tax is the exact cost this project exists to eliminate at scale (§2).

A2 — Regenerating codes (MSR/MBR) as the default, not a documented option.

Show the original text diagram
   [d0][d1][d2][d3] --(sub-packetized encode)--> [c0][c1][c2][c3][c4]
        repair reads a FRACTION of each surviving shard, not whole shards

Regime where it wins: a single fabric-constrained data center at extreme scale (>100 PiB) with heavy disk churn, where repair bandwidth dominates every other cost. Real system: Ceph's Clay-code plugin (Dimakis et al. 2010 theory, productionized in Ceph). Rejected as the Phase-0 default (ADR-07) because the construction complexity (Product-Matrix-MSR, Clay sub-packetization) is not justified until measured repair-bandwidth pressure exceeds what LRC/Hitchhiker already buy (§21–§22).

A3 — Dedicated hardware RAID controller (ASIC RS engine).

Show the original text diagram
   host CPU --(no coding work)--> [RAID HBA: fixed RS(k,m) in silicon]

Regime where it wins: fixed, small (k,m) (e.g., RAID-6's implicit m=2) where CPU-free encode matters more than flexibility, and software upgrades to the codec are never needed. Real system: legacy RAID-6 controllers (e.g., Broadcom/LSI MegaRAID). Rejected here because the entire point of this project is a software-flexible (k,m), SIMD-portable, LRC/Hitchhiker-capable codec — a fixed-function ASIC forecloses every phase past Phase 4.

A4 — Fountain/rateless codes (RaptorQ) instead of fixed-rate RS.

Show the original text diagram
   encode: unbounded symbol stream --> decode: ANY (1+ε)·k symbols reconstruct

Regime where it wins: unknown or streaming loss rates where the number of shards needed to reconstruct is not fixed in advance — e.g., multicast file delivery to many receivers with heterogeneous loss. Real system: RaptorQ (RFC 6330), used in 3GPP MBMS broadcast delivery. Rejected here because storage erasure coding has a known, fixed (k,m) per object at rest — the rateless property solves a transport problem this system does not have (§5 RFC 5510 vs. RFC 6330 contrast).

39. Glossary

  • GF(2^8) — Galois Field of 256 elements; addition is XOR, multiplication is polynomial multiplication modulo an irreducible polynomial.
  • MDS code — Maximum Distance Separable code; achieves the Singleton bound d = n−k+1; Reed-Solomon is MDS, LRC is not.
  • Cauchy matrix — matrix with element (i,j) = 1/(x_i⊕y_j) for pairwise-distinct, non-zero sums; the production generator matrix (ADR-01).
  • Vandermonde matrix — matrix with element (i,j) = x_i^j; the textbook construction, the differential-testing reference here.
  • Systematic code — a code whose first k shards are the unmodified original data.
  • Shard — one of the k+m byte-slices an encoder produces.
  • Data shard — an unmodified original-data shard (indices 0..k).
  • Parity shard — a computed redundancy shard (indices k..k+m).
  • LRC (Local Reconstruction Code) — adds local parities so single-shard repair reads r ≪ k shards.
  • Azure-LRC — the Huang et al. (2012) LRC construction, (k,l,r) parameterized.
  • XORBAS — the Sathiamoorthy et al. (2013) alternative LRC construction.
  • Hitchhiker — a code that piggybacks repair traffic on scheduled degraded reads (Rashmi et al. 2014).
  • Regenerating code — a code achieving optimal repair bandwidth via sub-packetization; MSR and MBR are the two extreme points (Dimakis et al. 2010).
  • Repair plan — the minimum-cost sequence of reads/arithmetic to reconstruct a missing shard.
  • Bitrot — silent on-disk byte corruption, detected via per-shard CRC.
  • Scrubber — a background process verifying every shard's CRC on a schedule.
  • Singleton bound — the information-theoretic ceiling d ≤ n−k+1 on a code's minimum distance.
  • GFNI — Galois Field New Instructions; an Intel ISA extension providing native GF(2^8) multiply.
  • Shuffle table — the 16-entry SIMD lookup table implementing GF multiplication-by-constant via 4-bit-half decomposition.
  • Gauss-Jordan elimination — the row-reduction algorithm used to invert the decode submatrix over GF(2^8).
  • Primitive element — a field element (here 0x02) generating the entire multiplicative subgroup.
  • Irreducible polynomial — the modulus polynomial (0x11D) defining GF(2^8) multiplication.
  • Conformance bucket — a named group of related conformance tests in the harness.
  • CRC32C — the Castagnoli CRC-32 variant used for per-shard integrity (naming caveat in §15.6/ADR-20).
  • Zero-copy encode — the encode_into API writing directly into caller-owned buffers.
  • Frozen ABI — a C interface guaranteed never to change signatures within a major version (P10).
  • Locality group — a subset of data shards covered by one local parity in LRC.
  • Global parity — an LRC parity shard covering all data shards, used when local recovery is insufficient.
  • Piggyback bytes — Hitchhiker's small auxiliary repair data riding on a degraded-read response.
  • Chunk (streaming) — a fixed-size (default 4 MiB) unit of a streaming codec invocation.
  • Present-shard bitmap — the boolean vector indicating which of k+m shards are available at decode/repair time.
  • Submatrix selection — choosing k present shard indices to build an invertible decode matrix.
  • Fountain/rateless code — a code producing unbounded symbols where any sufficient subset reconstructs the input (contrast, §37 A4).
  • Storage amplification — the (k+m)/k overhead factor of an erasure-coded layout vs. raw data size.
