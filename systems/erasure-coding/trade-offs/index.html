37. Alternative Architectures (Roads Not Taken)

A1 — Pure replication (no coding).

Show the original text diagram
   write --> [copy 1] [copy 2] [copy 3]     read <-- any one copy

Regime where it wins: small clusters where network cost of extra copies is cheap relative to engineering complexity, and read-path simplicity dominates. Real system: early Ceph / GFS default 3-replica placement. Rejected here because the flat 3× storage tax is the exact cost this project exists to eliminate at scale (§2).

A2 — Regenerating codes (MSR/MBR) as the default, not a documented option.

Show the original text diagram
   [d0][d1][d2][d3] --(sub-packetized encode)--> [c0][c1][c2][c3][c4]
        repair reads a FRACTION of each surviving shard, not whole shards

Regime where it wins: a single fabric-constrained data center at extreme scale (>100 PiB) with heavy disk churn, where repair bandwidth dominates every other cost. Real system: Ceph's Clay-code plugin (Dimakis et al. 2010 theory, productionized in Ceph). Rejected as the Phase-0 default (ADR-07) because the construction complexity (Product-Matrix-MSR, Clay sub-packetization) is not justified until measured repair-bandwidth pressure exceeds what LRC/Hitchhiker already buy (§21–§22).

A3 — Dedicated hardware RAID controller (ASIC RS engine).

Show the original text diagram
   host CPU --(no coding work)--> [RAID HBA: fixed RS(k,m) in silicon]

Regime where it wins: fixed, small (k,m) (e.g., RAID-6's implicit m=2) where CPU-free encode matters more than flexibility, and software upgrades to the codec are never needed. Real system: legacy RAID-6 controllers (e.g., Broadcom/LSI MegaRAID). Rejected here because the entire point of this project is a software-flexible (k,m), SIMD-portable, LRC/Hitchhiker-capable codec — a fixed-function ASIC forecloses every phase past Phase 4.

A4 — Fountain/rateless codes (RaptorQ) instead of fixed-rate RS.

Show the original text diagram
   encode: unbounded symbol stream --> decode: ANY (1+ε)·k symbols reconstruct

Regime where it wins: unknown or streaming loss rates where the number of shards needed to reconstruct is not fixed in advance — e.g., multicast file delivery to many receivers with heterogeneous loss. Real system: RaptorQ (RFC 6330), used in 3GPP MBMS broadcast delivery. Rejected here because storage erasure coding has a known, fixed (k,m) per object at rest — the rateless property solves a transport problem this system does not have (§5 RFC 5510 vs. RFC 6330 contrast).
