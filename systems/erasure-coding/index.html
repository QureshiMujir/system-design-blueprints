In one paragraph

Erasure coding stores a file as k data pieces plus m computed extra pieces, so that any k of the k + m pieces rebuild the original bytes exactly (§1, I1). This design is a Rust library (not a service) for Reed-Solomon over GF(2^8), plus a Local Reconstruction Code extension that cuts single-piece repair traffic, a repair planner, a CLI and a background corruption scrubber (§1). Storage-system engineers link it into a chunk or object store for cold-tier durability, and SREs run the scrubber and rebuild tooling (§1). Its defining constraint: multiplying bytes in the field is the single scalar bottleneck, and every other number in the budget follows from it (§4, P1).

The problem, concretely

Every durability system pays in one of two currencies, replication or parity (§2). Three-way replication is a flat 3x storage tax, and at petabyte to exabyte scale the blueprint puts the difference at hundreds of millions of dollars over a fleet's life (§2). Parity instead costs a tunable factor of (k+m)/k: RS(6,3) is 9/6 = 1.50x (§4, §35 item 1). Tolerating any m concurrent shard losses is the stated failure budget (§4).

Parity trades that storage saving for three new pressures, and the blueprint's structure answers each.

  1. CPU. Reed-Solomon needs field multiplication on every byte, and the blueprint cites Plank's tutorials for GF multiplication eating 95% of encode CPU (§2). So the design makes the multiply a table lookup and then a SIMD shuffle (§4, P1, MM1).
  2. Repair bandwidth. Plain Reed-Solomon repairs one lost shard by reading k shards. For a 4 MiB chunk with k = 6 that is 6 x 4 MiB = 24 MiB read to rebuild one chunk (§35 item 4). The field "took thirty-five years" to internalize this problem (§2). The design answers with a planner that makes the cost visible (P5, MM4) and with LRC and Hitchhiker, which lower it (§21, §22).
  3. Silent corruption. A disk can corrupt bytes silently and the shard can look valid (bitrot, §39, T5). A decoder that trusted such a shard would decode garbage, so every shard carries a CRC and a mismatch is treated as "missing", not "corrupt-but-present" (P7, I6, T5).

The naive alternative, copying data three times, is rejected because that flat 3x tax is "the exact cost this project exists to eliminate at scale" (§37 A1, §2).

How it works, end to end

Follow one object through the boxes of §3's diagram. The consumer (a DFS chunkserver, object store or backup engine, all sibling systems in the portfolio) hands the library byte slices and gets byte slices back; durable placement and network transport stay with the consumer (§1, P11).

Condensed, adapted from the §3 diagram (rows follow its layering, top to bottom):

  1. ec-core holds the shared types: Gf256, Matrix, Shard, EncodingMatrix, CodecParams. It is the "terminology lock": no crate below redefines these (§3, P1, §11). CodecParams::new is where k + m <= 255 is enforced (I7, P9).
  2. ec-gf256 and ec-matrix are the pure arithmetic and linear-algebra substrate: log/exp tables for multiply, and Cauchy / Vandermonde construction plus inversion. Both are no_std-compatible with no I/O (§3, ADR-09, P11). §3 places invert in ec-matrix; §11 declares Matrix::invert in ec-core, and §10.2 also gives ec-decoder a gauss_jordan.rs.
  3. ec-encoder / ec-decoder do systematic encoding and Gauss-Jordan decoding. The trust boundary is "present-shard bitmap in, recovered bytes out" (§3, P2, §8.6).
  4. ec-simd speeds up the inner multiply with AVX2, AVX-512, GFNI or NEON shuffles, tested against the scalar kernel (§3, I12). §3 and P4 make it the sole unsafe crate; §25 names the unsafe surface as ec-simd and ec-ffi, and §23.6 calls FFI an unsafe boundary.
  5. ec-lrc, ec-hitchhiker, ec-repair-planner are the repair-bandwidth axis: pluggable planners behind one trait (§3, P5, §11).
  6. ec-streaming is "a codec loop over chunks, not a new codec" (§3, P6). ec-ffi is the frozen v1 C ABI (§3, P10). ec-cli / ec-bin is a thin operator surface where every flag maps to a library call (§3, P11).

Write path: data shards go out unchanged, m parity shards come from one matrix multiplication, and each shard gets a header with a CRC32C (§8.4, §8.5, §15.2, I2, I6). With nothing lost, reads never touch the decoder (P2, MM2). With shards missing, the decoder verifies CRCs, picks k shards, inverts a small matrix and multiplies (§8.6, §8.7).

The core ideas

Bytes as numbers in a tiny number system (§8.1)

Treat each byte as one of 256 values and define arithmetic so that the answer is always a byte again (GF(2^8), a Galois field; I3). Addition and subtraction are both XOR. Multiplication goes through a discrete log: with the generator 0x02 and the polynomial 0x11D, mul(a, b) is zero if either input is zero, and otherwise EXP[LOG[a] + LOG[b]]; inv(a) is EXP[255 - LOG[a]] (§8.1, ADR-04). The EXP table is doubled so the index sum never needs a modulo (§8.1). The tables are generated at compile time by a const fn (ADR-05). Because the field is exact there is no rounding error: every failure is a construction or logic bug, never numerical drift (MM8).

The 256 elements are also why k + m is capped at 255 (256 by convention); accepting 256 raw "collides with the zero-element convention" (P9, I7, §35 item 10).

Contradiction: §8.1 describes "two 256-entry tables" with EXP[0..510] doubled, then gives "512 B total", which §4, P1 and §31 repeat. The blueprint does not reconcile the two.

The Cauchy matrix and systematic form (§8.2, §8.4)

A generator matrix says how each parity byte is a weighted sum of the data bytes. The design uses a Cauchy matrix, an m x k matrix whose entry (i, j) is 1 / (x_i XOR y_j), with x_i = i + k for i in 0..m and y_j = j for j in 0..k (§8.2, ADR-01). The sums x_i XOR y_j must be pairwise distinct and non-zero, otherwise the matrix cannot be inverted (I4). The point of the construction is the MDS property (MDS, "maximum distance separable"): any k of the k + m shards rebuild the data, by construction rather than by luck (I1, MM3). The design backs this with an enumeration proof for every (k, m) up to (16, 8) (P14, §13). A Vandermonde matrix, entry x_i ^ j, ships only as a differential-testing reference (§8.3, P13).

Systematic means the first k output shards are the original data, unmodified (I2). The design gets there by inverting the top k x k block of the raw matrix and multiplying through (§8.4):

[ I_k ]              [ I_k  ]
[     ]  --invert-->  [       ]   where the top k×k block of the raw
[ P_m ]  top-k block  [ P'_m ]   Cauchy/Vandermonde matrix is inverted and
                                  multiplied through (§14.1).

The payoff is that reads of undamaged data bypass decoding entirely (P2, MM2, ADR-02). The cost is that the data shards are readable in plaintext, which is why secret-sharing is a stated non-goal (§1, ADR-02).

Encoding is one matrix multiplication (§8.5, §8.8)

parity[m x L] = P'[m x k] . data[k x L], where L is the shard length in bytes and all arithmetic is in GF(2^8) (§8.5). Each output byte position is an independent dot-product of length k, which is exactly what SIMD parallelizes across byte positions (§8.5, §17).

The blueprint's smallest worked example is RS(2,1) (§8.8). Take data shards d0 = 0x03 and d1 = 0x07. The single parity row is [1, 1], a degenerate case that reduces to XOR:

Step Computation Result
encode parity = (1 . d0) XOR (1 . d1) = 0x03 XOR 0x07 0x04
lose d0 d0' = parity XOR d1 = 0x04 XOR 0x07 0x03
check recovered equals the original d0 exact (I1)

Contradiction: §8.2 defines every Cauchy entry as 1 / (x_i XOR y_j) with x_i = i + k and y_j = j, while §8.8 (and §12.2) call the Cauchy row for m = 1, k = 2 simply [1, 1]. The blueprint does not show how one yields the other.

Decoding is a matrix inversion (§8.6, §8.7, §8.10)

Given a present-shard bitmap (which of the k + m shards you still have), choose any k present indices, form the k x k submatrix of those rows, invert it with Gauss-Jordan elimination, and multiply it by the surviving byte columns to recover all k data shards (§8.6, I9). The codec lifecycle is a small state machine (§8.7):

State Trigger Next state
VerifyingCrc at least k verified present (CRC check per shard, I6) SelectingSubmatrix
VerifyingCrc fewer than k verified Failed(Insufficient)
SelectingSubmatrix an invertible subset found Inverting
SelectingSubmatrix none invertible Failed(Singular), retry with a new subset
Inverting then Reconstructing inversion, then multiply, complete Decoded (terminal)

The failure-path example (§8.10): only k - 1 verified shards remain, because one failed its CRC and one is genuinely gone. Decoder::decode returns DecodeError::Insufficient without any matrix work (I8, §8.10). The malformed-input example (§8.9): a header with the wrong magic, or a payload_bytes above the 64 MiB ceiling, is rejected at ShardHeader::parse before any payload is read, and a header claiming u32::MAX must never reach an allocation (I13, §4).

Making the multiply fast: the shuffle (§17.2, MM1)

Scalar code multiplies one byte at a time. The SIMD kernels instead split each byte into its high and low 4-bit halves, look each half up in a 16-entry table (a shuffle table) for the constant being multiplied by, and XOR the two results (§17.2, §39). One shuffle instruction does that for a whole register of bytes (MM1). At startup select_gf_mul_add picks the best kernel by a priority table, GFNI, then AVX-512, AVX2, SSSE3, NEON, scalar, and caches the choice (§17.2). §17.2 and §10.3 list four kernel files (no SSSE3 one), while §17.3 says ec-simd ships "all five kernels plus the scalar fallback".

Two named hazards: _mm256_shuffle_epi8 works per 128-bit lane, so a cross-lane assumption silently corrupts half the output, and calling a #[target_feature] function without a prior runtime check is undefined behaviour (§17.6, P4). The safety net is I12: every kernel must byte-equal the scalar kernel, enforced by the simd_path bucket over sizes at and around register boundaries (§17.4); a divergence disables that tier and falls back to scalar (FM-3).

Repair is not decode (§19.2, §21.2, P5, MM4)

A naive consumer repairs a lost shard by decoding, which reads k shards. A repair-aware consumer asks RepairPlanner::plan for a plan whose cost is accounted explicitly: for pure RS, bandwidth = k x payload_bytes and flops = k^2 (§19.2, P5). The blueprint's own number for pure RS with a 4 MiB chunk and k = 6 is 24 MiB per repaired chunk (§35 item 4).

A Local Reconstruction Code (LRC) lowers that by splitting the k data shards into l locality groups of k/l shards, each with its own local parity, plus global parities over all the data (§21.2, MM5). Losing one shard now means reading only its group. For the Azure shape (12, 2, 2) that is exactly 6 shards instead of 12 for pure RS (§21.4, M10). The blueprint uses r two ways: I10 says a repair reads "exactly r shards" and §35 item 6 sets r = 6, while §11 writes the shape as (12,4) Lrc(2,2), §34 gives Azure "local groups (r=2)" and §21.2 counts r_global global parities. Three caveats: LRC is not MDS, so some k-subsets cannot be inverted and the decoder must check and fall back to global recovery (P14, §21.6); the saving holds for a single loss only, two losses in one group need the global path (§21.6); and k must divide evenly by l, checked at construction (§21.2, FM-12). Hitchhiker goes further by piggybacking small auxiliary bytes on parity shards and on already-scheduled degraded reads, for a further 25-45% saving (§22.1, §22.2, M11), but only if the storage layer implements the piggyback read path (§22.6, FM-10).

The trade-offs — where engineers disagree

Generator matrix: Cauchy (ADR-01)

Chosen: Cauchy (Plank and Xu 2006), for faster inversion at scale (§9, P2). Rejected: Vandermonde, which is textbook-simpler but inverts slower (P2). When the rejected choice is right: small teaching corpora (under 10 shards), or audit contexts that need textbook-traceable coefficients (§9). The design still ships Vandermonde, as the differential partner (§8.3, P13).

Encoding form: systematic (ADR-02)

Chosen: systematic, so reads bypass decoding entirely (§9, P2, MM2). Rejected: non-systematic. When the rejected choice is right: when shard confidentiality matters more than read latency, the secret-sharing use cases (§9, §1).

Field size: GF(2^8) (ADR-03)

Chosen: GF(2^8), because the tables fit in L1 cache and the symbol is one byte, with a one-register SIMD width (§9, P1). Rejected: GF(2^16) and GF(2^32). When the rejected choice is right: GF(2^16), when a deployment needs k + m > 255 shards, accepting 64 KiB tables and no native shuffle width (§9). The wider field is parked in the deferred register (§38, I7).

LRC flavour: Azure-LRC by default (ADR-06)

Chosen: Azure-LRC, for a cleaner construction and published parameters (§9). Rejected: XORBAS as the default. When the rejected choice is right: when multi-shard-in-group repair locality matters more than construction simplicity (Sathiamoorthy 2013, §9). XORBAS is still built, as the differential partner (§21.2, P13).

Regenerating codes: documented, not shipped (ADR-07)

Chosen: document MSR/MBR codes and defer them, because the construction complexity (Clay codes) is not justified yet (§9, §22.2). Rejected: ship them as the default. When the rejected choice is right: a single fabric-constrained data centre above 100 PiB with heavy disk churn (§9, §37 A2). The un-defer trigger is a measured repair-bandwidth SLO breach beyond Hitchhiker's 25-45% saving (§38).

Who owns bitrot detection: the codec (ADR-20)

Chosen: a codec-owned CRC32C per shard; the decoder trusts nothing it did not verify (§9, P7, I6). Rejected: delegating to the storage layer, which already has its own checksum. When the rejected choice is right: when every consumer already guarantees end-to-end checksums and CPU is the scarce resource (§9). P7 itself admits the duplication as its tradeoff.

Roads not taken (§37, §38)

Pure replication (§37 A1): a flat 3x storage tax, but no coding at all. It wins in small clusters where the network cost of extra copies is cheap relative to engineering complexity and read-path simplicity dominates; early Ceph and GFS defaulted to 3 replicas (§37 A1).

Regenerating codes as the default (§37 A2): repair reads a fraction of each surviving shard. It wins in a single fabric-constrained data centre above 100 PiB with heavy disk churn; Ceph's Clay plugin is the real system. Rejected as the Phase-0 default for construction complexity (ADR-07).

A hardware RAID controller (§37 A3): fixed RS(k,m) in silicon, no CPU coding work. It wins for a fixed small (k,m) such as RAID-6's implicit m = 2 where software upgrades are never needed. Rejected because it forecloses every phase past Phase 4 (§37 A3).

Rateless fountain codes such as RaptorQ (§37 A4): any (1+e) . k symbols reconstruct. They win for unknown or streaming loss rates, for example multicast delivery to receivers with different loss. Rejected because storage at rest has a known, fixed (k,m) per object, so the rateless property solves a transport problem this system does not have (§37 A4).

Deferred features (§38), each with an un-defer trigger: regenerating codes (an SLO breach), a wider field (a consumer needs k + m > 255), RPC hardening (an off-host consumer), WASM / no_std certification, JNI bindings (a JVM consumer), and an alignment-aware SIMD path (a measured regression).

What must never be false

  • I1: any k of k + m shards reconstruct the data (MDS). Noticed by the enumeration proof at construction (§13); mds_check_total; the construction is rejected with MatrixError (§7).
  • I2: shards 0..k are the unmodified data. The general_encode_decode bucket; systematic_violations_total (§7).
  • I3: every field operation returns a value in 0..255. Enforced by the u8 type and a field-axiom property test; no telemetry needed (§7).
  • I4: Cauchy sums x_i XOR y_j are pairwise distinct and non-zero. An enumeration test; cauchy_construction_failures; MatrixError::Singular (§7).
  • I5: the same input and parameters give byte-identical shards on any architecture. The Jerasure differential (§18); nondeterminism_detected_total; fail the build and block release (§7, P8).
  • I6: a stored CRC32C matches the recomputed one for a non-corrupt shard. Checked at decode by ec-verifier; crc_mismatch_total; a mismatch means the shard is treated as missing (§7).
  • I7: k + m <= 255 (256 by convention). Checked in CodecParams::new; codec_params_rejected_total; CodecError::TooManyShards (§7).
  • I8: decoding needs at least k verified-present shards. A shard-count check at Decoder::decode entry; insufficient_shards_total (§7).
  • I9: every selected decode submatrix is non-singular. Noticed when Gauss-Jordan finds no pivot; singular_submatrix_total; try another k-subset (§7).
  • I10: LRC single-shard repair reads exactly r shards from one group. A bandwidth-accounting assert in LrcPlanner::plan; lrc_repair_bandwidth_bytes; fall back to global recovery (§7).
  • I11: a frozen v1 C ABI function's signature never changes. The cbindgen header diff in CI; abi_diff_detected; the release is blocked (§7).
  • I12: every SIMD kernel byte-equals the scalar kernel for all inputs. The simd_path differential bucket; simd_divergence_total; disable that tier and fall back (§7).
  • I13: the shard header is validated before any payload is read. The fuzz harness (§18); malformed_header_total; the shard is treated as missing (§7).
  • I14: an interrupted-and-resumed stream equals an uninterrupted one. A replay-equivalence test; stream_resume_divergence; replay from the last committed offset (§7, P6).

What breaks in production

  • FM-1: decode returns wrong bytes. A matrix-inversion logic bug, detected by the Jerasure differential (§18); no automatic recovery. Roll back the encoder/decoder version and re-run conformance; the evidence is the failing fixture plus mds-proof-report.json (§26).
  • FM-2: decode fails with Insufficient unexpectedly. Fewer than k shards are actually present. The shard-count check (I8) detects it, and since this is an information-theoretic floor nothing recovers automatically; an operator restores or replaces shards (§26).
  • FM-3: a SIMD kernel diverges from scalar. Cause is a lane-boundary bug in the shuffle path. The simd_path differential (I12) detects it; the system falls back to the scalar tier automatically, and a human patches the kernel (§26).
  • FM-5: a corrupt shard passes the CRC. A CRC32C collision (astronomically rare) or the wrong polynomial. No reliable detection, an inherent limit of any checksum; the manual route is to re-verify with a decode plus an ec-verifier re-encode check (§26).
  • FM-7: repair reads far more than planned. Planner and executor disagree, or LRC fell back to the global path silently. The bandwidth-accounting assert (I10) catches it; there is no automatic recovery. Inspect ec cli plan output against actual bytes read (§26, §21.10).
  • FM-10: Hitchhiker piggyback never engages. The storage layer does not implement the piggyback contract. The hitchhiker_fallback_total counter shows it; the system falls back to RsPlanner automatically, and the consumer must implement the piggyback read path (§26, §22.6).

Threats a reader should know (§25): T1 a crafted header with payload_bytes = u32::MAX, answered by validating before allocation (I13); T5 bitrot masquerading as a valid shard, answered by the per-shard CRC and found by the scrubber cycle (I6, P7); T9 an operator overwriting a live shard with ec rebuild, answered by a --force guard (§24); T10 an unauthenticated ec-proto repair RPC, answered by shipping it off by default and requiring TLS and auth to enable (ADR-13); T12 a degenerate (k, m) that yields a non-MDS matrix, answered by the construction-time enumeration check (I1, I4). (T3, a bad pointer across the C boundary, is outside Rust's reach and is contained to the consumer's process, §25.)

First, M-numbers: §4 sources its encode latencies to "§35 M1" and "§35 M2" and its scrub budget to "§35 M3", yet the M table is in §31, where M3 is GFNI throughput and the scrub budget is M9 (as §35 item 3 says); §19.4 cites M4 for planner latency (§31: M8), and §20.4, §21.4 and §21.7 cite M3 for scrub and the LRC saving (§31: M9, M10). Third, §4, §20.4 and M9 size the scrub budget for a 4 PiB fleet, while §35 item 3 computes it from 4x10^15 B.

How it compares

  • Intel ISA-L chose hand-tuned assembly per instruction set, a stable versioned C API, and no opinion on repair bandwidth or storage integration. That fits raw single-node encode/decode throughput; this design borrows its SIMD strategy and adds the planner and storage layers ISA-L leaves out (§34).
  • Jerasure 1.2 is the academic reference: Cauchy matrices in C, SSE-era SIMD, no planner. It is fine for correctness-reference clarity rather than throughput, and this design's conformance suite validates against its vectors byte for byte (§34, ADR-16).
  • Ceph EC (Clay) chose Reed-Solomon plus Clay-code sub-packetization, delegating SIMD to ISA-L/Jerasure. That wins where shrinking repair bandwidth below what LRC achieves is worth a much harder implementation; it is a real embodiment of the regenerating-code option this design defers (§34, ADR-07).
  • Azure Storage (LRC) chose Reed-Solomon plus Azure-LRC, with local groups, in C++ with proprietary SIMD and no external ABI. That fits hyperscale clusters where the 2x single-shard repair saving cuts cross-rack traffic; this design ships the same construction as an opt-in flavour because not every consumer operates at Azure's scale (§34, §21).

  1. Why does the Singleton bound force d = n − k + 1 for an MDS code, and where in this document is that bound actually exercised rather than merely asserted? — Hint: the enumeration proof in §13, and I1.
  2. Why is Cauchy preferred over Vandermonde here, and under what regime would that choice reverse? — Hint: ADR-01 and the construction detail in §14.
  3. Why is repair explicitly not the same operation as decode, and what would a consumer lose by conflating them? — Hint: P5 and §19.

If you only remember three things

Reed-Solomon over GF(2^8) turns "any k of k+m pieces rebuild the data" into a matrix you can prove invertible by enumeration, and the systematic layout means undamaged reads never decode at all (I1, P2, MM3). The byte multiply is the one scalar bottleneck, so the design turns it into a table lookup and then a SIMD shuffle that must byte-equal the scalar path (P1, MM1, I12). Repair is a different operation from decode and costs k shard reads in plain RS, which is why LRC and Hitchhiker exist and why the planner makes that cost visible (P5, MM4, MM5).

Words used here

  • Erasure code: k data shards plus m computed shards such that any k rebuild the data (§1).
  • Shard: one of the k + m byte slices an encoder produces (§39).
  • GF(2^8): a number system of 256 elements where addition is XOR (§39).
  • MDS code: any k of n shards suffice; Reed-Solomon is MDS, LRC is not (§39, I1).
  • Systematic code: the first k shards are the unmodified data (§39, I2).
  • Bitrot: silent on-disk corruption, caught by a per-shard CRC (§39).
  • Shuffle table: the 16-entry SIMD lookup table used for multiply-by-constant (§39).
  • LRC: a code with local parities so one lost shard is repaired from a small group (§39).
  • Hitchhiker: a code that piggybacks repair data on scheduled degraded reads (§39).
  • Repair plan: the minimum-cost sequence of reads and arithmetic to rebuild a missing shard (§39).
