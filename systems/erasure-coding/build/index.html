⬜ Phase 0 — Repository Skeleton & GF(2^8) Correctness Kernel §12

Objectives

Stand up the repository (§10) and land a correct GF(2^8) scalar kernel plus a throwaway (k=2, m=1) smoke codec, proving the toolchain, CI, and conformance harness work end to end before any general construction exists.

Deliverable

make bootstrap && make build && make test && make conformance all succeed; a (k=2,m=1) codec encodes a 1 MiB buffer, survives a one-shard loss, and decodes back to the original bytes (§8.8 worked example, generalized to 1 MiB).

Acceptance
  • gf_arith bucket: all 65,536 (a,b) pairs pass field-axiom assertions in ≤ 50 ms.
  • phase0_smoke bucket: 1 MiB roundtrip passes for both "lose d0" and "lose parity."
  • Nine remaining buckets report Deferred with a resolving PhaseDeferred anchor, never Fail.
  • ADR-01, ADR-02, ADR-03, ADR-04, ADR-05, ADR-14 filed under docs/adr/.
Fixtures
  • gf-arith/full-pairs.bin — every (a,b) byte pair, expected: field axioms hold.
  • phase0-smoke/1mib-lose-d0.bin — expected: d0 recovered exactly.
  • phase0-smoke/1mib-lose-parity.bin — expected: no-op decode (I2 systematic).
  • chaos/malformed-header-magic.bin — expected: ShardHeader::parse rejects (I13).
Pitfalls
  • Choosing a primitive element that does not generate the full 255-element multiplicative subgroup silently breaks every table (must be 0x02 with 0x11D, ADR-04).
  • mul has an unguarded special case at Gf256(0) (no log entry) — branch before the table lookup.
  • Shipping the general Cauchy encoder here is scope creep; Phase 0 is GF(2^8) + one smoke test, nothing else (P14 applies only from Phase 1 onward).

⬜ Phase 1 — Full GF(2^8) Arithmetic & Polynomial Machinery §13

Objectives

Extend the scalar kernel with polynomial arithmetic over GF(2^8) and formally prove the MDS property (I1, P14) by enumeration, laying the foundation the Phase-2 matrix constructions and the Phase-10 regenerating-code option (ADR-07) both need.

Deliverable

ec-gf256 exports Poly plus a passing property-test suite; a standalone MDS-proof test report enumerating pass/fail per (k,m).

Acceptance
  • Field-axiom proptest: 65,536 default cases pass; CI long-run job: 65,536× more.
  • MDS enumeration completes for (k,m) up to (16,8) in ≤ 90 s on one core, zero failures (I1).
  • Scalar GF(2^8) multiplication benchmark ≥ 200 MOps/s single core (§4 baseline for §17's SIMD comparison).
Fixtures
  • gf-arith/poly-eval-degree-0-to-16.bin — Horner vs. explicit-sum agreement.
  • mds-proof/k16-m8-enumeration.json — expected: 735,471 cases, 0 singular.
  • chaos/poly-zero-high-coeff.bin — a polynomial with a zero leading coefficient, expected: canonicalized (trimmed) on construction, not treated as higher-degree.
Pitfalls
  • Confusing coefficient multiplication (GF(2^8) table lookup) with bit-XOR (GF(2) addition) silently produces a codec that encodes but never decodes correctly.
  • The enumeration is O(C(n,k)) — uncapped, it explodes past (16,8); cap it in CI and document larger configurations as spot-checked, not exhaustively proven.

⬜ Phase 2 — Cauchy & Vandermonde Construction, Systematic Form §14

Objectives

Build the real encoding-matrix constructions (§8.2–8.4), the systematic-form derivation, and the Gauss-Jordan inversion primitive the whole system depends on.

Deliverable

ec-matrix exports cauchy, vandermonde, to_systematic, invert; the cauchy_matrix bucket green for (k,m) up to (16,8).

Acceptance
  • Cauchy-vs-Vandermonde differential roundtrip passes for 100% of (k,m) in the tested range, both flavours (I1).
  • Matrix-inversion benchmark ≥ 10,000 invocations/s at n=16 (§4).
  • Singular-submatrix path returns MatrixError::Singular, never panics (I9).
Fixtures
  • cauchy-matrix/k16-m8-invertibility.json — every row-subset invertible.
  • cauchy-matrix/differential-cauchy-vandermonde.bin — same recoverability, different parity bytes (both MDS).
  • chaos/singular-submatrix-forced.bin — a hand-constructed degenerate matrix, expected: MatrixError::Singular, not a panic.
Pitfalls
  • The Cauchy constraint x_i ⊕ y_j pairwise-distinct (I4) holds for the chosen x_i=i+k, y_j=j mapping only within k+m ≤ 255 (P9) — verify at construction, not just at test time.
  • A bug in invert corrupts the systematic derivation in a way that still passes naive roundtrip tests if encoder and decoder share the same matrix instance — the Vandermonde differential (P13) is the canary; never skip it.

⬜ Phase 3 — Production RS(k,m) Encoder §15

Objectives

Replace the Phase-0 placeholder with the general Cauchy-systematic encoder (P2, ADR-01/02), the byte-slice and zero-copy APIs (P3), and shard-header framing.

Deliverable

ec-encoder ships ReedSolomonEncoder; every (k,m) up to (16,8) encodes and its output validates against vendored Jerasure vectors byte-for-byte.

Acceptance
  • RS(6,3) scalar encode ≥ 1.0 GB/s (§4, M1); RS(10,4) ≥ 0.8 GB/s; RS(17,3) ≥ 0.5 GB/s.
  • jerasure_vectors bucket: 100% byte-identical match across all vendored (k,m,data) triples.
  • encode_into zero-copy path produces byte-identical output to encode (P3).
Fixtures
  • encode-decode/rs-6-3-4mib.bin — canonical mid-size roundtrip fixture.
  • jerasure-vectors/rs-17-3-1mib.bin — Backblaze-shape vendored oracle match.
  • chaos/mismatched-shard-lengths.bin — expected: EncodeError::ShardLen.
Pitfalls
  • The inner column-wise GF-multiply-XOR loop is the hot path the autovectorizer cannot help with — this is precisely the gap Phase 5 (§17) closes with the Plank-Greenan-Miller shuffle (§5).
  • encode_into's alignment contract is stricter than encode's allocating path; document it (align_of::<u8>() scalar, 32 B AVX2, 64 B AVX-512) and check on entry.
  • Jerasure 1.2 vs. 2.0 parity-shard ordering differs — vendor exactly 1.2.0 (ADR-16) and record its vector-file SHA-256.

⬜ Phase 4 — Decoder, Repair Semantics, Multi-Shard Loss §16

Objectives

Land the general decoder: given any k of k+m shards, reconstruct the missing ones via the state machine of §8.7, honoring I8/I9.

Deliverable

ec-decoder recovers from any 1..m simultaneous shard losses for every tested (k,m); ec-verifier catches an injected encoder/decoder asymmetry in CI.

Acceptance
  • general_encode_decode bucket covers every loss pattern up to m shards, 100% pass.
  • RS(6,3) scalar decode ≥ 0.8 GB/s (§4).
  • Decode with < k present shards returns DecodeError::Insufficient in 100% of cases (I8), never a partial/garbage result.
Fixtures
  • multi-loss/rs-10-4-lose-4.bin — maximal-loss recovery for RS(10,4).
  • single-loss/rs-6-3-lose-p2.bin — parity-shard loss, re-encode path exercised.
  • chaos/insufficient-shards.bin — k-1 present, expected DecodeError::Insufficient.
Pitfalls
  • Naively picking the first k present shards assumes MDS (I1, P14) — true for Cauchy/Vandermonde here, false for LRC (Phase 9, §21); the Phase-4 decoder is explicitly MDS-only; the LRC-aware submatrix-selection heuristic is built directly in Phase 9 (§21), not deferred beyond the plan.
  • A wrong parity CRC at encode time is masked by the decoder simply treating that shard as missing and reconstructing it — add an explicit "decode with all parity present, assert CRC matches" test so this class surfaces in CI, not production.

⬜ Phase 5 — SIMD Acceleration (AVX2/AVX-512/GFNI/NEON) §17

Objectives

Close the scalar-throughput gap (§4) with the Plank-Greenan-Miller (2013) split-table shuffle (P4, P13), lifting encode from ~1 GB/s to 6–15 GB/s.

Deliverable

ec-simd ships all five kernels plus the scalar fallback; every kernel is differentially verified byte-identical to scalar (I12) on its target CPU.

Acceptance
  • RS(6,3) AVX2 ≥ 6.0 GB/s; AVX-512 ≥ 12.0 GB/s; GFNI ≥ 15.0 GB/s; NEON ≥ 10.0 GB/s (§4, M2).
  • simd_path bucket: 100% byte-equality across coefficients 0..256 × sizes {31,32,33,63,64,65,127,128,129,255,256,257}.
  • Runtime-detection fallback exercised in a CI host lacking AVX-512 (feature-gated matrix job).
Fixtures
  • simd/avx2-vs-scalar-boundary-sizes.bin — the size set above, expected: byte-equal.
  • simd/gfni-vs-avx512.bin — cross-tier equality on GFNI-capable hardware.
  • chaos/unaligned-simd-input.bin — deliberately misaligned buffer, expected: correct output via the unaligned-load path, not a fault.
Pitfalls
  • _mm256_shuffle_epi8 operates per-128-bit-lane, not across the full 256-bit register — a cross-lane assumption silently corrupts half the output.
  • #[target_feature(enable = "avx2")] is a hard requirement; calling the attributed function without a prior runtime check is undefined behavior, not merely slow (P4's safety contract exists exactly to prevent this).
  • Unaligned loads are fast on modern CPUs, ~5–10% slower on older Skylake steppings — accepted cost per ADR-10; an alignment-aware path is PhaseDeferred("§17").

⬜ Phase 6 — Fuzzing, Property Testing, Jerasure Differential §18

Objectives

Harden the codec beyond property tests with fuzzing (I13, P13) and a byte-exact differential against the Jerasure 1.2 reference (ADR-16).

Deliverable

Four fuzz targets running 24 h weekly in fuzz.yml; jerasure_vectors green; proptest suites at 256 cases/PR, 65,536 cases/week.

Acceptance
  • Zero fuzz crashes surviving 24 h × 4 targets in the weekly job.
  • jerasure_vectors: 100% byte-identical match, all vendored triples.
  • Seed corpus committed under crates/ec-fuzz/corpus/; running corpus never committed.
Fixtures
  • jerasure-vectors/SHA256SUMS — pinned hash manifest for every vendored vector file.
  • chaos/fuzz-seed-malformed-shard-count.bin — a starter fuzz corpus entry.
  • chaos/fuzz-seed-oversized-payload.bin — payload_bytes near u32::MAX.
Pitfalls
  • cargo-fuzz requires nightly Rust — pin a specific nightly in CI and document it in CONTRIBUTING.md (ADR-11).
  • Jerasure vectors are not exhaustive; they validate production parameter regimes, not corner cases — the proptest suites (Phase 1, §13) cover the corners the vectors miss.

⬜ Phase 7 — Repair Planner & Minimum-Bandwidth Reconstruction §19

Objectives

Make repair bandwidth a first-class, queryable cost (P5) distinct from decode, ahead of LRC (Phase 9) and Hitchhiker (Phase 10) making that cost actually low.

Deliverable

ec-repair-planner ships RsPlanner; ec cli plan --k=6 --m=3 --present=... emits a valid cost-accounted plan.

Acceptance
  • repair_planner bucket: pure-RS plans validated for every (k,m) and every present-bitmap in the tested range (§4).
  • repair_plan_latency benchmark ≤ 5 µs for RS(6,3) (§4, M4).
  • Executing a returned plan recovers all missing shards in 100% of harness runs.
Fixtures
  • repair-planner/rs-6-3-plan-lose-d2.json — expected reads = first k present, exact bandwidth figure.
  • chaos/planner-length-mismatch.bin — present-bitmap length ≠ n, expected PlannerError::Length.
Pitfalls
  • Conflating the planner with the decoder — a consumer bypassing the planner and calling Decoder::decode directly is correct but forfeits every bandwidth optimization from Phase 9 onward (P5).
  • bandwidth must count bytes read from storage, not bytes after any storage-layer compression/dedup — the planner's contract is disk-read bytes, full stop.

⬜ Phase 8 — Storage Backend & Bitrot Scrubber §20

Objectives

Wrap the codec in a concrete on-disk layout and a background scrubber, giving the library its first operational (not purely in-memory) surface.

Deliverable

A storage layout that survives a process crash mid-encode (atomic rename from .tmp); a scrubber that completes a full-fleet pass on the configured schedule and reports CRC failures.

Acceptance
  • Default scrub schedule: full-fleet cycle every 14 days, ≤ 3.3 GB/s bandwidth for a 4 PiB fleet (§4, M3).
  • A deliberately bit-flipped shard is detected within one scrub cycle, 100% of injected-fault runs.
  • Encoder writes via .tmp + atomic rename; an interrupted encode leaves zero partially-visible objects.
Fixtures
  • storage-backend/scrub-detects-bitflip.bin — one-byte flip, expected: detected, logged, crc_failures incremented.
  • chaos/interrupted-encode-crash.bin — simulated crash mid-write, expected: no partial object visible after recovery.
Pitfalls
  • Unthrottled scrubbing competes with foreground reads — the 14-day default is conservative precisely to keep this under the §4 bandwidth budget; document the trade-off in docs/runbooks/scrub.md.
  • A missing fsync before rename reintroduces the exact interrupted-write hazard the atomic-rename design was meant to close.

⬜ Phase 9 — Local Reconstruction Codes (Azure-LRC, XORBAS) §21

Objectives

Cut single-shard repair bandwidth from k reads to r ≪ k reads (P5) using local parity groups (Huang et al. 2012; Sathiamoorthy et al. 2013, §5).

Deliverable

ec-lrc ships both constructions; LrcPlanner is real; the Azure default (k=12, l=2, r=2) and XORBAS (k=10, l=2, r=2) both round-trip and report the bandwidth saving.

Acceptance
  • lrc bucket green for both constructions at their published parameters (§5).
  • Single-shard repair for (12,2,2) reads exactly 6 shards vs. 12 for pure RS — measured 2× saving (§4, M3; I10).
  • CodecParams::new rejects k not divisible by l with a named error, not a panic.
Fixtures
  • lrc/azure-12-2-2-single-loss.bin — expected: 6-shard local repair, not 12.
  • xorbas/xorbas-10-2-2-single-loss.bin — comparable XORBAS repair-locality check.
  • chaos/lrc-non-invertible-k-subset.bin — a k-subset that is not invertible for LRC (unlike MDS RS), expected: planner/decoder fall back to global recovery, not a silent wrong answer.
Pitfalls
  • LRC is not MDS (P14 caveat) — some k-subsets are non-invertible; the Phase-4 MDS-only decoder must not be reused unmodified (§16.6); the LRC decoder checks invertibility and falls back.
  • Azure-LRC parameters are constrained (k % l == 0) — reject invalid combinations at construction, not at encode time.
  • The bandwidth saving is single-shard-loss-only; two losses in the same group still require global recovery — document this limit in the planner's own output, not just in prose.

⬜ Phase 10 — Hitchhiker & Regenerating Codes §22

Objectives

Cut repair bandwidth a further 25–45% (Rashmi et al. 2014, SIGCOMM, §5) by piggybacking repair traffic on already-scheduled degraded reads, and document (without shipping) the regenerating-code alternative (Dimakis et al. 2010).

Deliverable

ec-hitchhiker ships the piggyback encoder/decoder/planner; measured repair-bandwidth saving vs. pure RS and vs. Azure-LRC is reported by benchmark.

Acceptance
  • hitchhiker bucket: round-trip and piggyback-correctness both green.
  • Measured repair-bandwidth saving 25–45% vs. pure RS (§4, matching the Facebook warehouse-cluster figures in Rashmi 2014).
  • A v1 reader presented a v2 (Hitchhiker) shard refuses with a named version-mismatch error, never silent misparse (I13-adjacent).
Fixtures
  • hitchhiker/piggyback-roundtrip.bin — encode, degraded-read simulate, repair via piggyback bytes only.
  • chaos/v1-reader-v2-shard.bin — expected: explicit version-mismatch rejection.
Pitfalls
  • Hitchhiker requires storage-layer cooperation — a consumer not implementing the piggyback read path gets zero benefit and must not be silently assumed compatible; a worked example for the DFS chunkserver (rank 86) and object store (rank 107) is mandatory documentation, not optional.
  • The piggyback bytes are an in-band extension of the parity payload — treating them as opaque padding instead of versioned data breaks forward compatibility.

⬜ Phase 11 — Streaming Encoder, C FFI, Cross-Process Repair RPC §23

Objectives

Extend the codec beyond in-memory buffers (P6) and beyond Rust (P10), landing the streaming API, the frozen C ABI, and an optional cross-process repair RPC.

Deliverable

A 1 GiB stream encodes and recovers from a shard loss chunk-by-chunk; a C consumer in examples/ffi-c-consumer/ builds against the committed header and round-trips; the gRPC smoke client completes a Plan/Repair call pair.

Acceptance
  • streaming bucket: 1 GiB input, chunked, one shard dropped mid-stream, full recovery, hash-verified.
  • ffi bucket: C-consumer round-trip byte-equal to the Rust-direct path.
  • Interrupt-and-resume at any chunk boundary produces output identical to an uninterrupted encode (I14).
Fixtures
  • streaming/1gib-interrupted-resume.bin — resume-equivalence check (I14).
  • ffi/c-consumer-roundtrip.bin — cross-language byte-equality.
  • chaos/ffi-null-pointer.bin — a null data pointer across the FFI boundary, expected: EC_ERR_PARAMS, never a crash in the conformance harness's guarded wrapper (documented as a known unguarded case for real C callers, per SECURITY.md).
Pitfalls
  • The 4 MiB default chunk size trades small per-chunk header overhead against RAM footprint — matches the DFS chunk-write batch (ADR-22); revisit only with measured justification.
  • The FFI unsafe boundary is where Rust's guarantees end — a misbehaving C caller can corrupt memory; this is unavoidable at any FFI boundary and is documented, not "fixed."
  • The gRPC surface is opt-in (--features proto) — Phase 0–10 ship without it; do not accidentally make it a default-on dependency.

⬜ Phase 12 — Operator Tooling (CLI) §24

Objectives

Ship the operator surface (P11, ADR-17) that makes every library capability reachable without writing Rust: ec encode/decode/scrub/rebuild/plan.

Deliverable

The ec binary; every verb in §10.4 works end-to-end against a real directory tree; runbooks and worked examples committed.

Acceptance
  • ec encode --k 6 --m 3 on a 4 MiB file completes and reports a throughput figure consistent with §4's targets (within the ±5% regression gate, P12).
  • ec rebuild refuses to overwrite an existing shard without --force, 100% of tested invocations.
  • ec scrub reports zero CRC failures on an uncorrupted fixture tree and exactly one on a tree with one injected bit-flip.
Fixtures
  • ffi/minio-4-2-shape.bin — worked-example roundtrip.
  • chaos/rebuild-without-force.bin — expected: refusal, non-zero exit, no overwrite.
  • streaming/backblaze-17-3-vault.bin — worked-example roundtrip at Backblaze's published shape.
Pitfalls
  • Any flag that does not correspond to a library parameter is scope creep — the CLI must stay predictable from the library alone (P11); resist adding CLI-only configuration.
  • ec rebuild is the single command that can destroy data if misused — the --force guard and the rebuild.md runbook exist specifically because this is the highest-blast-radius operator action in the system.
