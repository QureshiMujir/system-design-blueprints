15 — Synapse

Project Number: 15

Project Name: Synapse

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Synapse is a portable model-capability registry and runtime: a package format, a signed-artifact trust boundary, a registry, and a serving runtime for composable model capabilities — LoRA/PEFT adapters (Hu et al. 2021) and distilled capability artifacts — that attach to a compatible base language model without retraining it. A capability artifact is architecture-scoped rather than checkpoint-scoped: it declares the base architecture family it targets, the target modules it touches, its rank and dtype, and a tokenizer fingerprint, so a single artifact can be resolved against any checkpoint that satisfies its declared contract, gated by a numeric evaluation score rather than assumed compatible. The system separates four concerns that are conflated in ad hoc fine-tune sharing today: (1) a safe, non-executable artifact format, (2) a cryptographically verifiable chain of custody from packager to consumer, (3) a compatibility/resolution engine that proves an artifact may be attached to a given base before any GPU work happens, and (4) a serving runtime that hot-swaps and composes multiple such artifacts per inference request without mutating base weights.

Phase 0 (§12) delivers the following packages/services as the foundational skeleton:

  1. synapse-format — the capability-artifact byte layout, manifest schema, and tensor-index encoder/decoder (no signing yet).
  2. synapse-cli — a thin command-line entry point for artifact inspection (synapse inspect, synapse validate) with no network calls.
  3. synapse-conformance — a first-cut conformance fixture set (§12.5) exercised in CI.
  4. CI pipeline — build, unit test, and conformance-fixture execution on every commit.

Boundaries: Synapse does not train base models or capability artifacts; it packages, verifies, resolves, serves, composes, distills, and federates already-produced weight deltas. Synapse does not implement a general model-hosting control plane (autoscaling of base-model replicas, request routing across regions) — it assumes a base-model serving substrate exists and Synapse's runtime is a layer on top of it. Non-goals: full-parameter fine-tuning workflows, dataset management, prompt-engineering tooling, a hosted SaaS billing layer. Deployment model: a self-hostable set of services (registry control plane + blob store + serving runtime sidecar) deployable on a single node for evaluation or a multi-node cluster for production; no assumption of a single managed cloud vendor. Users/operators: capability authors (data scientists producing adapters), platform operators (running the registry and serving fleet), and inference consumers (applications requesting capability-augmented completions).

Language: Rust for the packager, signer/verifier, tensor-index codec, and conformance CLI — deserialization-safety and byte-layout precision are load-bearing (P1, §6) and Rust's ownership model statically prevents the class of memory-safety bugs that made the 2024 malicious-pickle-on-hub incidents possible in dynamically-typed loaders. Go for the registry control-plane services (index API, resolver service) — mature concurrency primitives and a mature OCI-ecosystem client/server library set (ADR-04, ADR-23). Python (PyTorch) for the serving runtime's model-execution hot path, because base-model and adapter execution must sit on the existing PyTorch/CUDA ecosystem; Rust-accelerated extensions handle verification and hashing inside that process (ADR-06). Rejected: a pure-Python control plane (rejected for GIL-bound throughput under concurrent resolver load); a pure-C++ runtime (rejected because it forgoes the PyTorch model zoo integration needed to attach to arbitrary base architectures); TypeScript/Node for the control plane (rejected — weaker numeric/binary-format tooling for tensor-index work).

Prerequisites: a working understanding of transformer attention/MLP module boundaries, familiarity with content-addressed storage, and access to at least one GPU node for Phase 4 (§16) onward. Timeline: Phase 0 through Phase 3 (§12–§15) are a single formatting/trust/registry/resolution track (~10 weeks combined); Phase 4 through Phase 7 (§16–§19) bring up serving, composition, and evaluation (~14 weeks combined); Phase 8 through Phase 11 (§20–§23) add quantized-base support, distillation, the federated bridge, and hardening (~16 weeks combined).

What later phases unlock: multi-adapter batched serving is PhaseDeferred("§17 Phase 5 — Multi-Adapter Batched Serving") until a working single-adapter path exists (§16). Weight-space composition (merge/stack/route) is PhaseDeferred("§18 Phase 6 — Composition (Merge/Stack/Route)"). Quantized-base (QLoRA) attachment is PhaseDeferred("§20 Phase 8 — Quantized-Base Support (QLoRA)"). Cross-architecture portability is PhaseDeferred("§21 Phase 9 — Cross-Architecture Distillation"). Privacy-preserving multi-party training is PhaseDeferred("§22 Phase 10 — Federated Bridge + Secure Aggregation").

2. Why Build This

Portable capability packaging. Signed supply chain for weight deltas. Compatibility proof instead of compatibility hope. Hot-swappable adapters without base mutation. Batched heterogeneous-rank serving at scale. Weight-space algebra (task arithmetic, TIES, DARE) as a first-class composition primitive. Cross-architecture capability portability via distillation. Privacy-preserving multi-party capability training. Content-addressed dedup economics at registry scale. Eval-gated promotion instead of "latest wins."

What Mastery Looks Like

  • Designing a non-executable, mmap-friendly binary artifact format that closes an entire vulnerability class (Phase 0, §12).
  • Building a supply-chain trust boundary (signing, transparency log, provenance attestation) that survives an adversarial upload path (Phase 1, §13).
  • Implementing a compatibility resolver that turns "will this adapter work on this base" from a guess into a provable decision table (Phase 3, §15).
  • Writing a batched-kernel serving path that keeps heterogeneous-rank adapters from degenerating into padded, wasted compute (Phase 5, §17).
  • Expressing model composition as weight-space algebra with display-equation rigor instead of ad hoc merge scripts (Phase 6, §18).
  • Porting a capability across base architectures via distillation and proving fidelity with a regression-gated eval harness (Phase 9, §21).
  • Running a federated training round with secure aggregation and a formal privacy budget instead of trusting participants (Phase 10, §22).

Capability packager: takes trained delta tensors plus author-declared metadata and emits the unsigned artifact — manifest, tensor index, tensor blob region — in the byte layout fixed by §8; never touches the network.

Signer/verifier: wraps a packaged artifact in a SignatureEnvelope (§11) using Sigstore keyless signing, and on the read path recomputes the blob digest tree and verifies the signature before anything downstream trusts the bytes (I1, §7).

Registry: an index (relational metadata: manifests, eval scores, provenance, versions) fronting a content-addressed blob store; the two halves are managed independently so identical tensor blocks dedupe across artifacts (P8, §6).

Compatibility resolver: given a requested CapabilityId and a target base fingerprint, evaluates the decision table in §8 and returns a CompatibilityVerdict before any tensor is loaded.

Adapter loader: performs the pre-mmap signature/digest check (I1) then maps tensor blobs into the serving process's address space, producing an AdapterHandle (§11) without mutating base weights (P5, I3).

Serving runtime: routes each inference request's declared adapter set through a routing queue, applies the composition engine's merge/stack/route decision, and dispatches batched heterogeneous-rank matmuls through the SGMV kernel path (ADR-07).

Composition engine: implements the display-equation math of §8 — sequential stacking, static merging, TIES trimming, DARE dropout — as three interchangeable composition strategies selected by CompositionPolicy (§11).

Evaluation harness: runs the regression fixture suite against a candidate artifact or composite plan and emits an EvalReport (§11) that gates registry publish (P12, I8).

Distillation pipeline: consumes a teacher capability plus a target base fingerprint and produces a new, architecture-ported CapabilityId with mandatory provenance back to its source (P10, I12).

Federated bridge: coordinates multi-party training rounds, requiring either a secure- aggregation proof or a DP-SGD privacy budget attached to every FederatedRound before it is accepted into aggregation (P11, I11).

Telemetry: an OpenTelemetry bus threading every box above — verification latency, resolver verdicts, pool occupancy, swap latency, eval-gate outcomes, federated round privacy spend — feeding the metrics named throughout §7 and §26.

6. Design Principles

P1 — No artifact is a pickle. Rule: every tensor is serialized as a flat header-plus-raw-bytes region (safetensors-shaped); the manifest is a strict schema (protobuf), never an executable object graph. Tradeoff: loses arbitrary custom-object convenience. Operational implication: the loader has a fixed allowlist of dtypes and shapes, nothing else deserializes. Violating this breaks the system exactly the way the 2024 malicious-pickle-on-hub incidents did — remote code execution at load time.

P2 — Compatibility is proven, never assumed. Rule: a CompatibilityVerdict is ACCEPT only after the resolver checks architecture fingerprint, target-module subset, rank/dtype/tokenizer agreement, and a numeric eval-gate score clears its threshold. Tradeoff: extra compute per load. Operational implication: the registry must persist eval scores per (adapter, base) pair. Violating this produces silent quality degradation that looks like a successful load.

P3 — Composition order is explicit and recorded. Rule: CompositionPolicy is an ordered list, never a set; stacking A then B differs from B then A on overlapping modules. Tradeoff: authors must reason about commutativity. Operational implication: the ResolvedPlan hash includes order. Violating this causes non-deterministic output for what looks like "the same adapter set."

P4 — Verification precedes memory-mapping. Rule: the whole manifest, tensor index, and blob digest tree are verified before any tensor is mapped into the serving process. Tradeoff: verification latency on the cold path (C9). Operational implication: a TTL-bounded warm cache skips re-verification within the TTL only. Violating this opens a TOCTOU window where a blob can be swapped after "verified."

P5 — Base weights are never mutated in place by adapter loading, except for an explicit, logged merge-and-freeze operation. Rule: a LoRA delta is applied via functional composition at forward time. Tradeoff: extra per-forward compute versus a statically merged model. Operational implication: this is what makes hot-swap and multi-tenant base sharing possible. Violating this lets one tenant's merge corrupt another tenant's request on a shared base.

P6 — Rank, alpha, and dtype are declared, never inferred from tensor shape alone. Rule: the manifest states r, α, dtype, and target modules explicitly; the loader cross-checks declared values against actual tensor shapes and rejects mismatch. Tradeoff: more metadata to keep synchronized. Operational implication: the resolver can reject before any GPU work. Violating this lets alpha/rank scaling silently corrupt the effective delta magnitude with no error raised.

P7 — A capability artifact is architecture-scoped, not checkpoint-scoped. Rule: BaseModelFingerprint captures architecture family, hidden size, layer count, and tokenizer hash — not a specific checkpoint hash — unless training provenance pins one. Tradeoff: risk of attaching to a checkpoint whose weights have drifted; this must be caught by the eval gate, not skipped. Operational implication: the registry indexes by architecture fingerprint. Violating this in either direction makes the registry either useless (over-narrow) or unsafe (over-broad, ungated).

P8 — Registry content addressing is per-blob, not per-package. Rule: tensor blobs are hashed and stored independently of the manifest that references them; two artifacts sharing identical tensor blocks dedupe automatically. Tradeoff: an extra indirection layer (index → digest → storage location). Operational implication: garbage collection must reference-count blobs. Violating this makes storage growth (C12) unbounded.

P9 — Serving-time adapter selection is a pure function of declared inputs. Rule: given (artifact digests, composition policy, base fingerprint), the ResolvedPlan is deterministic and cacheable; no hidden global "last loaded wins" state may influence which adapters apply. Tradeoff: request payloads must be fully explicit. Operational implication: this enables safe response caching. Violating this causes cross-request adapter leakage between tenants.

P10 — Distillation targets are first-class, versioned artifacts. Rule: cross- architecture distillation produces a new CapabilityId with a provenance pointer to its source, never a silent fold into the source's version. Tradeoff: artifact proliferation across base architectures. Operational implication: the registry groups artifacts into "capability families" across architectures. Violating this makes it impossible to tell a distilled artifact's fidelity apart from its source's.

P11 — Federated rounds never accept raw client updates without a privacy boundary. Rule: every FederatedRound requires a secure-aggregation proof or a DP-SGD epsilon/delta budget before acceptance. Tradeoff: added cryptographic/noise overhead reduces per-round quality. Operational implication: FederatedRound records cumulative privacy spend. Violating this permits training-data leakage or membership inference from raw gradients.

P12 — Eval gates block promotion; they do not merely warn. Rule: an artifact cannot move from candidate to published registry state unless its EvalReport clears the registered regression threshold. Tradeoff: slower iteration for authors. Operational implication: the Phase 7 (§19) harness is a hard CI gate. Violating this ships quality regressions silently to consumers pulling "latest."

P13 — Quantized-base compatibility is declared, not discovered by trial and error. Rule: BaseModelFingerprint carries an explicit quantization-scheme field; the resolver rejects a fp16-trained adapter loading onto an incompatible quantization scheme without an explicit dtype-promotion path. Tradeoff: more fingerprint dimensions to maintain. Operational implication: this is the Phase 8 (§20) gate. Violating this lets dtype promotion silently change numerics, producing subtly wrong output that passes a superficial smoke test.

Debugging methodology: when an invariant's telemetry counter moves, first bisect which stage of the pipeline (packager → signer → registry → resolver → loader → runtime → composition) produced the offending artifact or plan by replaying the same inputs against each stage's fixture harness (§12.5 onward) in isolation; an invariant violation that reproduces at the packager stage is a format/authoring bug, one that reproduces only at the loader stage is an environment/runtime bug, and one that reproduces only under composition is an interaction bug localized to the composition engine (§18).

8.4 Composition Semantics — Display Equations

Single-adapter merge (Hu et al. 2021):

W' = W + (α / r) · B · A

Sequential stacking (order-sensitive per I7, non-overlapping modules commute, overlapping modules apply in declared order):

h' = h + Σ_i (α_i / r_i) · B_i · A_i · x

Task-arithmetic composition (Ilharco et al. 2023), task vector τ_i = ΔW_i:

τ_combined = Σ_i λ_i · τ_i

TIES-Merging trim + sign-election (Yadav et al. 2023), threshold τ, elected sign function E(·):

W' = W + λ · Σ_i E( trim_τ(ΔW_i) )

DARE drop-and-rescale (Yu et al. 2024), drop mask m_i ~ Bernoulli(1 − p):

ΔW_i^DARE = ( m_i ⊙ ΔW_i ) / (1 − p)

8.7 Worked Example

A request declares CapabilityIds "summarize-v2" (r=16) and "translate-en-fr-v1" (r=8), CompositionPolicy = STACK[summarize-v2, translate-en-fr-v1]. The resolver confirms both target q_proj/v_proj only (subset of base modules, I2), both share tokenizer_hash with the base (I6), both clear their eval thresholds (I8). The ResolvedPlan hash is computed over (digest(summarize-v2), digest(translate-en-fr-v1), STACK, order=[summarize-v2, translate-en-fr-v1]). Since both touch the same modules, order matters (I7): the runtime applies summarize-v2's delta first, then translate-en-fr-v1's, per §8.4's sequential-stacking equation, and caches the plan under its hash for reuse by subsequent identical requests (P9).

8.8 Malformed-Artifact Examples

  • Truncated tensor index: Tensor Index Length field claims more bytes than remain before the declared blob region starts — loader rejects at parse time, never attempts a partial read (I5-adjacent format guard).
  • Oversized manifest-length field: an attacker sets Manifest Length to a value exceeding the artifact's total file size, attempting an allocation-overflow DoS (the safetensors pitfall, §5) — packager and loader both bound-check against a hard ceiling before allocating.
  • Signature envelope missing or zero-length: artifact parses structurally but has no SignatureEnvelope — loader treats this identically to a failed verification (I1), never as "unsigned, trust anyway."
  • Declared rank does not match tensor shape: manifest states r=16 but the B matrix tensor shape implies r=8 — loader rejects via I5's shape-assert before any GEMM is scheduled.

8.9 Failure-Path Example

A blob-store node serving a popular r=64 artifact suffers partial disk corruption. A pulling node's adapter loader recomputes the blob digest tree (P4) and detects a mismatch against the tensor index (I9). The loader does not retry against the same replica; it falls back to a second blob-store replica (registry is configured with ≥2 replicas per blob per C14's RTO), re-verifies, and only then proceeds to mmap. The corrupted replica is flagged via blob_digest_mismatch_total and taken out of rotation pending re-sync from origin.

12. Phase 0 — Skeleton + Artifact Format + CI

12.1 Objectives

Establish the capability-artifact byte layout (§8.1), the ArtifactManifest and TensorIndexEntry schemas (§11), and a CI pipeline that exercises them against a conformance fixture set, with no signing, no registry, and no network calls yet.

12.2 Detailed Implementation Steps

Implement synapse-format as a Rust crate: magic/version header writer/reader, manifest length bound-check (P1, guards against the safetensors header-overflow pitfall, §5), protobuf-encoded ArtifactManifest (de)serialization (ADR-02), and a tensor-index codec enforcing 64-byte-aligned blob offsets. Implement LoraSpec and TargetModuleSet (§11) as manifest sub-messages. Enforce I5 (rank/shape agreement) at parse time by cross-checking each TensorIndexEntry.Shape against the declared LoraSpec.Rank for its module. Build synapse-cli with inspect (dump manifest as JSON for humans) and validate (run the format's own parser plus I5 shape-assert, exit non-zero on any violation) subcommands. Wire a GitHub Actions ci.yml running cargo test plus synapse-conformance run --fixtures conformance/fixtures/. No composition, no serving, no signature — those are explicitly out of scope (P1, P4 ground rules apply from day one even though signing lands in Phase 1, §13).

12.3 Deliverable

synapse-format crate, synapse-cli binary, synapse-conformance fixture runner, green CI on ci.yml for every commit.

12.4 Acceptance Criteria

synapse validate rejects 100% of the malformed fixtures in §12.5 with a non-zero exit code and a SynapseError variant printed; round-trip encode→decode of a valid r=8/16/64 manifest (§4 C1–C3 sizes) preserves every field bit-for-bit; manifest length bound-check rejects any declared length exceeding 64 MiB hard ceiling.

12.5 Conformance Fixtures

valid_r8_llama7b.bin, valid_r16_llama7b.bin, valid_r64_llama7b.bin — expected: parse success, round-trip match. malformed_truncated_index.bin — expected: ErrShapeMismatch-class parse rejection (§8.8). malformed_oversized_manifest_len.bin — expected: bound-check rejection before allocation. malformed_rank_shape_mismatch.bin — expected: ErrShapeMismatch at I5 check. regression_v0_format_replay.bin — a frozen Phase-0 format-version artifact replayed on every CI run to catch accidental breaking changes to the byte layout.

12.6 Pitfalls

Manifest-length field trusted before bounds-checking, reproducing the safetensors header-overflow class (§5) as an allocation-size DoS. Protobuf optional-field defaults silently treated as "compatible" when they actually indicate "field never set by an old packager version" (§27 foreshadowing). Tensor-index offsets computed relative to the wrong base (file start vs. blob-region start) causing off-by-header- length reads. Alignment padding omitted, breaking future mmap (§16) assumptions.

12.7 Performance Concerns

Manifest parse and I5 shape-assert must add negligible latency relative to C9's verification budget, since Phase 1 (§13) will stack signature verification on top of this parse; a slow parser here compounds into the cold-path p99 in C5/C9.

12.8 Edge Cases

Zero-tensor manifest (a manifest declaring TargetModuleSet with no matching TensorIndexEntry rows) — must reject, not silently accept an empty adapter. Manifest declaring a QuantizationScheme not yet implemented (Phase 8, §20 reserved enum value) — must round-trip losslessly even though Phase 0 cannot act on it.

12.9 Failure Analysis

If CI shows the round-trip fixture diverging after a schema change, the cause is almost always an added protobuf field without a default that breaks the frozen regression_v0_format_replay.bin fixture — resolved by treating all new fields as optional/additive per §27 from the first schema draft, not retrofitted later.

12.10 Operational Notes

synapse-cli inspect is the primary human-facing debugging tool for every later phase; keep its output format stable so runbooks (§26) referencing it in later phases remain accurate without edits.

13. Phase 1 — Packager + Signer/Verifier

13.1 Objectives

Add the trust boundary: a packager that emits artifacts conforming to Phase 0's format plus author-declared provenance, and a signer/verifier implementing P1's "deserialization must not execute code" guarantee end-to-end with a real signature (I1, P4).

13.2 Detailed Implementation Steps

Implement synapse-sign (Rust): Sigstore keyless signing (ADR-03) producing a SignatureEnvelope (§11) over (manifest ‖ tensor index ‖ blob digest tree); a digest-tree builder computing per-tensor SHA-256 (feeding TensorIndexEntry.Sha256) plus an aggregate root hash. Implement the verifier as the mirror operation: recompute the digest tree, verify the Ed25519 signature against the Fulcio cert chain, check the Rekor transparency-log entry exists (in-toto/SLSA provenance predicate, ADR-18), and only then return a "verified" result consumed by I1. Extend synapse-cli with a pack subcommand (folds Phase 0's format writer with provenance fields) and a sign subcommand. Apply P4 literally in the verifier's control flow ordering: no tensor byte range is read into a return buffer until the full signature check completes. Building-secure-and-reliable-systems least-privilege guidance (§5 books) drives the signer key-custody model: the signer process never persists a long-lived private key, only ephemeral Fulcio-issued certs.

13.3 Deliverable

synapse-sign crate, synapse-cli pack|sign|verify subcommands, a documented signer key-custody runbook (docs/runbooks/).

13.4 Acceptance Criteria

100% of Phase-0-valid fixtures sign and verify round-trip; a bit-flipped tensor byte in any signed fixture is detected by verify with ErrVerificationFailed before any tensor read; verification latency meets C9 (≤134 ms cold r=64, ≤2 ms warm-cached).

13.5 Conformance Fixtures

signed_valid_r16.bin — expected: verify success. tampered_single_byte_tensor.bin — expected: ErrVerificationFailed, digest-tree mismatch localized to the tampered tensor's index entry. stripped_signature_envelope.bin — expected: treated as verification failure, not "unsigned, allow" (§8.8). replay_old_cert_chain.bin — a fixture using an expired Fulcio cert, expected: rejection with a distinguishable SynapseError from ordinary signature failure.

13.6 Pitfalls

Verifying the signature after partially reading tensor bytes into a working buffer (a TOCTOU regression against P4) rather than before any read. Treating a missing SignatureEnvelope as "legacy unsigned artifact, allow" instead of rejecting — this exact class of leniency is what made the 2024 pickle-hub incidents exploitable via unsigned/mistrusted uploads. Digest-tree computed over the wrong byte range (including trailing signature bytes in the hash input, making every future verify fail).

13.7 Performance Concerns

Cold verification latency (C9) is dominated by SHA-256 over the full blob region; budget hashing throughput realistically (~1 GB/s single-core) rather than assuming a GPU-accelerated hash path is available in the signer/verifier's Rust process.

13.8 Edge Cases

An artifact signed twice by two different authors (co-signing) — verifier must support a SignatureEnvelope list, not assume exactly one. A signer running with a revoked Fulcio cert mid-signing — must fail closed, not emit a signature that later verifies against a since-revoked identity without a Rekor log check.

13.9 Failure Analysis

If verification latency exceeds C9's cold-path budget in production, first check whether the digest-tree computation is single-threaded over the full blob rather than parallelized per-tensor — this is the most common regression source since tensor blobs are independently hashable.

13.10 Operational Notes

Key-custody runbook must specify what happens on a Fulcio/Rekor outage: signing blocks (fail closed) rather than falling back to a self-signed, unlogged path, consistent with P1/P4's "no artifact is trusted without the full chain."

14. Phase 2 — Registry + Content-Addressed Blobs

14.1 Objectives

Stand up the registry's two halves — a PostgreSQL-backed index (ADR-05) and an OCI-distribution-compatible content-addressed blob store (ADR-04, ADR-16) — with per-blob deduplication (P8) and a publish path gated by nothing yet but signature validity (eval-gating arrives in Phase 7, §19).

14.2 Detailed Implementation Steps

Implement registry-index (Go, ADR-23): a schema covering CapabilityId, ArtifactManifest fields, lifecycle state (§8.5), and provenance, following Petrov's B-Tree/storage-engine lessons (§5) for the manifest-lookup index. Implement registry-blobstore-gateway: an OCI Distribution Spec-compatible pull/push API (section 4 and section 6 of the spec) fronting the S3-compatible object store; blobs addressed by TensorIndexEntry.Sha256 (P8), with reference counting for garbage collection. Publish path: signer's verify output (I1) is a precondition for index insertion; a lifecycle-state column starts every new artifact at CANDIDATE (§8.5) and advances to VERIFIED on a successful push. Kleppmann's replication chapter (§5) informs the index's read-replica topology for C13's RTO. Blob GC job (tools/) reference-counts blobs across manifests before deletion (P8 requires this).

14.3 Deliverable

registry-index service, registry-blobstore-gateway service, a blob GC tool, and a docker-compose stack wiring both plus PostgreSQL for local dev.

14.4 Acceptance Criteria

Pushing two artifacts sharing an identical tensor block results in exactly one stored blob (verified via blob-store object count, not just API success); index read-replica failover completes within C13's 5-minute RTO in a chaos drill; blob pull sustains ≥500 MB/s per node (C8) in a local benchmark.

14.5 Conformance Fixtures

push_duplicate_blob_pair.bin (two manifests sharing one tensor block) — expected: single blob stored, two index rows. push_unverified_artifact.bin — expected: publish rejection, artifact never reaches VERIFIED. gc_dangling_blob_reference.bin — expected: GC does not delete a blob still referenced by any manifest. replica_failover_drill — scripted chaos fixture, expected: index reachable within RTO.

14.6 Pitfalls

Reference counting blobs at manifest-delete time instead of at manifest-publish time, causing a race where a blob is GC'd while still mid-push from a second manifest. Treating the blob store as strongly consistent with the index without a transactional or two-phase confirm, risking an index row pointing at a blob that never finished uploading. OCI-spec pull path not handling partial/resumed pulls, forcing full re-pull on any network blip (hurts C8 in flaky-network conditions).

14.7 Performance Concerns

Index lookups on the manifest-by-architecture-fingerprint path (used heavily by the Phase 3 resolver, §15) must be covered by an index on ArchitectureFingerprint plus CapabilityId — an unindexed scan here becomes the dominant resolver latency once the catalog reaches C12's growth rate.

14.8 Edge Cases

A manifest referencing a blob digest that no push ever uploaded (dangling reference, e.g. from a crashed push) — publish must detect and reject, not leave a BROKEN row silently at CANDIDATE forever. Simultaneous pushes of the same CapabilityId at the same version (should be rejected as an immutability violation, per SemVer's immutable-release convention, ADR-17).

14.9 Failure Analysis

Storage-growth (C12) exceeding projection is diagnosed by checking blob GC's reference-count job cadence first — a paused or crashing GC job is the most common cause of unbounded growth, more common than genuinely low dedup rates.

14.10 Operational Notes

Blob GC must run as a low-priority background job with a dry-run mode that reports would-be-deleted bytes before any real deletion, given how costly a false-positive GC delete is against I9 (blob digest integrity).

15. Phase 3 — Compatibility Resolver

15.1 Objectives

Implement the resolver service embodying §8.3's decision table as a queryable API returning a CompatibilityVerdict (§11) before any adapter load is attempted, satisfying P2 and I2/I6.

15.2 Detailed Implementation Steps

Implement resolver (Go): given a CapabilityId and target BaseModelFingerprint, query the registry index for the artifact's manifest, then evaluate §8.3's rows in order — architecture-family match, target-module subset (I2), rank/dtype agreement (I5-adjacent, resolved statically from manifest not tensor shapes), tokenizer-hash agreement (I6), and eval-score threshold (P2, though Phase 7's harness is the actual score producer — Phase 3 consumes whatever EvalScores exist at this point, even if sparse). Cache verdicts keyed by (CapabilityId digest, BaseModelFingerprint) with a TTL, since P9 requires determinism — a cached verdict must be invalidated whenever the underlying manifest or eval score changes (I4). Implement the quantization- scheme-mismatch branch (§8.3 last-but-one row) as a stub returning REJECT always until Phase 8 (§20) implements the promotion path — this is a PhaseDeferred("§20 Phase 8 — Quantized-Base Support (QLoRA)") boundary.

15.3 Deliverable

resolver service with a gRPC/HTTP API returning CompatibilityVerdict, a verdict cache layer, and a CLI wrapper (synapse-cli resolve) for manual debugging.

15.4 Acceptance Criteria

100% of §8.3's decision-table rows have a corresponding fixture (§15.5) producing the documented verdict; verdict cache invalidates within one polling interval (≤10 s) of an eval-score update; resolver P99 latency ≤5 ms against a warm registry index (excludes cold artifact-load latency, which is Phase 4's concern).

15.5 Conformance Fixtures

resolve_exact_match_accept.bin — expected: ACCEPT. resolve_module_superset_reject.bin — expected: REJECT, ErrModuleNotSubset (I2). resolve_tokenizer_warn.bin — expected: WARN_ACCEPT with I6 reason string. resolve_quant_mismatch_stub_reject.bin — expected: REJECT pending Phase 8. resolve_below_threshold_reject.bin — expected: REJECT with ErrEvalGateFailed.

15.6 Pitfalls

Caching a verdict without a TTL or invalidation hook, so a later-published eval score never propagates (violates I4's determinism-given-current-inputs framing — the plan must be deterministic given current digests, not stale ones). Evaluating architecture-family match by string comparison alone without also checking HiddenSize/NumLayers, letting two same-named-but-differently-shaped architectures falsely resolve as compatible.

15.7 Performance Concerns

The resolver sits on the hot path of every cache-miss serving request (§8.6 step 3); an unindexed or synchronous-DB-roundtrip-per-check implementation directly inflates C6's added-latency budget — the verdict cache exists specifically to keep this off the steady-state hot path.

15.8 Edge Cases

A CapabilityId with no eval score recorded at all (Phase 7 not yet run against it) — resolver must return REJECT or a clearly-labeled provisional WARN, never silently treat "no score" as "passing score." A base fingerprint with a CheckpointDigest pinned (P7's checkpoint-pinning case) — resolver must additionally check checkpoint identity, not just architecture family.

15.9 Failure Analysis

A spike in resolver_reject_total{reason=module_mismatch} (I2's telemetry) after a registry migration usually indicates the migration changed how TargetModuleSet strings are normalized (e.g., casing or naming-convention drift) — verified by diffing the resolver's module-subset check inputs before and after migration.

15.10 Operational Notes

synapse-cli resolve must be runnable against production registry state read-only, so on-call operators can reproduce a customer-reported REJECT without needing serving-runtime access.

16. Phase 4 — Single-Adapter Serving Runtime

16.1 Objectives

Bring up the Python/PyTorch serving runtime (ADR-06) that loads one resolved adapter onto a running base model without mutating base weights (P5, I3), applying the single-adapter merge equation of §8.4 at forward time.

16.2 Detailed Implementation Steps

Implement synapse_runtime/loader.py: given a ResolvedPlan with exactly one CapabilityId, pull the artifact (registry client against Phase 2's gateway), re-verify (P4, I1 — verification is never skipped even on a warm registry pull), then mmap tensor blobs into pinned host memory and copy to GPU, producing an AdapterHandle (§11). Apply Burns's sidecar pattern (§5 books) — the loader runs as a logically separate component from the base model's forward pass, communicating via an in-process handle rather than re-implementing model internals. Implement forward- time composition for the single-adapter case as a functional hook: at each target module, compute h' = h + (α/r)·B·A·x (§8.4) without ever writing into the base Linear layer's weight tensor (P5). Wire pool-slot allocation (AdapterHandle.PoolSlot) against the GPU memory ceiling (C10, I10) with an LRU eviction policy (ADR-08) even though only one adapter is resident at a time in this phase — the pool abstraction must not need rework in Phase 5 (§17).

16.3 Deliverable

synapse_runtime package with loader.py and a minimal forward-hook composition path; an end-to-end example (examples/single_adapter_serve.md) describing request flow without executable code.

16.4 Acceptance Criteria

Loading and serving one r=16 adapter adds ≤8% latency vs. base-only inference (C6); adapter swap (load a different CapabilityId, evict the prior one) completes within C5's p50 (1.3 ms) under warm-cache conditions; base model weight checksum (I3 detection) is unchanged after 1,000 consecutive adapter load/evict cycles in a soak-test fixture.

16.5 Conformance Fixtures

serve_single_adapter_r16.bin — expected: output matches a golden reference generation. swap_adapter_100_cycles.bin — expected: base-weight checksum stable across all 100 cycles (I3). load_unverified_pull.bin (simulated tampered registry response) — expected: loader re-verification catches it, ErrVerificationFailed, never reaches mmap. pool_ceiling_exceeded.bin — expected: ErrPoolExhausted before an OOM, LRU eviction triggered first if eligible.

16.6 Pitfalls

Trusting the registry pull as already-verified because Phase 2's publish gate checked it once, and skipping the loader's own re-verification — this reintroduces exactly the TOCTOU gap P4 exists to close, since a compromised blob-store replica could serve different bytes than what was originally verified. Writing the adapter delta directly into the base Linear.weight tensor "for speed," silently violating P5/I3 and corrupting subsequent requests that don't want this adapter. Forgetting alignment padding from Phase 0's byte layout when computing GPU tensor strides, producing numerically wrong (not crashing) matmuls.

16.7 Performance Concerns

The forward-hook composition path must be implemented so its overhead is proportional to adapter rank, not proportional to full hidden-dimension GEMM cost — an implementation that materializes the full BA product before adding it to h defeats the entire point of a low-rank delta and blows the C6 latency budget.

16.8 Edge Cases

A request arrives for a CapabilityId whose artifact has since been DEPRECATED (§8.5) between resolve and load — loader must re-check lifecycle state at load time, not trust a stale resolve. GPU pool ceiling reached exactly at the moment a new adapter's load is requested with no evictable (all-ACTIVE) slots — must backpressure the request rather than exceed C10.

16.9 Failure Analysis

An unexplained latency regression that only appears at scale is diagnosed first against I3's checksum-drift telemetry — a regression here almost always traces to an accidental in-place write path introduced during an "optimization," not to GPU contention.

16.10 Operational Notes

Runbook must document the exact eviction order (strict LRU per ADR-08) so an operator investigating a pool-thrash incident can reason about which adapters were evicted and why without reading source.

17. Phase 5 — Multi-Adapter Batched Serving

17.1 Objectives

Extend the runtime to serve a batch of requests referencing heterogeneous CapabilityId sets and ranks concurrently, using SGMV batched kernels (ADR-07) to avoid the pad-to-max-rank waste identified in the vLLM/Punica reference implementations (§5). Satisfies the C7 throughput targets.

17.2 Detailed Implementation Steps

Implement synapse_runtime/kernels/ with a segmented gather matrix-vector dispatch (Chen et al. 2024, Punica) grouping requests by target module and gathering each request's adapter B/A matrices without padding shorter ranks up to the batch maximum. Extend the pool manager (Phase 4, ADR-08) to the S-LoRA-style unified-paging model (Sheng et al. 2023): adapter memory is allocated in fixed-size pages shared across adapters of similar size class, reducing fragmentation under high adapter churn. Implement request-level routing so each request's ResolvedPlan (I4) independently selects its adapter set within one physical batch — the batched kernel dispatch must not leak one request's adapter delta into another's output (this is I3 extended to the multi-tenant batch case). Add backpressure signaling when C10's pool ceiling is approached under a load spike, per the LoRAX reference implementation's async-prefetch lesson (§5) — never block the scheduler hot path on a synchronous registry pull for a cold adapter.

17.3 Deliverable

Batched SGMV kernel dispatch path, unified-paging pool manager, a load-test harness in benchmarks/ reproducing the C7 throughput curve at N=1/8/32 adapters.

17.4 Acceptance Criteria

Throughput at N=8 concurrent distinct adapters is within 2% of C7's 2,100 tok/s target; at N=32, within 2% of 1,750 tok/s; no cross-request output leakage across 1,000 randomized heterogeneous-batch fixture runs (§17.5); pool fragmentation after a 24-hour churn soak stays below a 10% wasted-page ratio.

17.5 Conformance Fixtures

batch_n8_heterogeneous_rank.bin (mix of r=8/16/64 adapters in one batch) — expected: throughput within C7 tolerance, per-request output matches single-adapter golden references. batch_isolation_leak_check.bin — expected: zero cross-request contamination detected via per-request output hashing. pool_churn_24h_soak.bin — expected: fragmentation ratio below threshold. cold_adapter_under_load_spike.bin — expected: backpressure signal returned, no scheduler stall.

17.6 Pitfalls

Padding all adapters in a batch to the maximum rank present "to simplify the kernel," silently reproducing the exact waste Punica's SGMV design exists to avoid (§5, vLLM pitfall) and missing the C7 throughput target. Heterogeneous-adapter batches serializing kernel dispatch per adapter instead of a true segmented gather, which looks correct in unit tests (small batches) but collapses throughput at scale. Unified-paging eviction interacting with skewed request popularity (the S-LoRA pitfall, §5) causing thrashing when a small number of adapters are extremely hot.

17.7 Performance Concerns

C7's degradation curve (2,400 → 2,100 → 1,750 tok/s) is the acceptance bar; any implementation change to the kernel dispatch path must be re-benchmarked against benchmarks/ before merge, since batched-kernel performance is highly sensitive to grouping-key choice (module identity vs. rank vs. both).

17.8 Edge Cases

A batch where every request shares the exact same adapter set (degenerates toward Phase 4's single-adapter case) — the batched path must not regress single-adapter latency relative to Phase 4's C6 budget. A batch mixing quantized-base requests (Phase 8, not yet implemented — PhaseDeferred("§20 Phase 8 — Quantized-Base Support (QLoRA)")) with fp16-base requests — must be rejected or segregated into separate physical batches, never silently mixed.

17.9 Failure Analysis

A throughput regression that reproduces only under heterogeneous-rank batches (not homogeneous ones) points to the SGMV grouping logic falling back to serial dispatch for some rank combination — verified by adding a per-batch dispatch-path counter and checking whether the "serial fallback" branch fired.

17.10 Operational Notes

Load-test harness results must be archived per release in benchmarks/ history so a throughput regression can be bisected to a specific commit rather than discovered only in production.

18. Phase 6 — Composition (Merge/Stack/Route)

18.1 Objectives

Implement the full CompositionPolicy (§11) space — STACK, MERGE, ROUTE — realizing §8.4's display equations as the composition engine, including TIES trimming and DARE dropout as MERGE-mode variants (ADR-10).

18.2 Detailed Implementation Steps

Implement synapse_runtime/composition/: a STACK executor applying sequential adapters in CompositionPolicy.Order (I7 enforced — the executor must reject any attempt to reorder, even for "equivalent" non-overlapping modules, keeping the enforcement mechanism simple and auditable). Implement a MERGE executor performing static weight-space merging: default path is TIES-Merging (Yadav et al. 2023) — trim threshold τ, sign-election E(·) — with DARE (Yu et al. 2024) as an opt-in MergeParams variant; both build on the task-arithmetic addition primitive (Ilharco et al. 2023) per ADR-11. Enforce I13: the merge step reads α/r scaling directly from each source manifest, never recomputing or defaulting it. Implement a ROUTE executor: given multiple candidate CapabilityIds, select exactly one per request based on a router policy (e.g., a lightweight classifier or declared routing key) — Order is ignored for ROUTE per I7's table note, since routing has no stacking order. Mergekit's lesson (§5) — validate tokenizer/vocab-size agreement across all sources before any merge math executes, since a shape mismatch mid-merge is far harder to debug than a pre-flight check.

18.3 Deliverable

STACK/MERGE/ROUTE executors in synapse_runtime/composition/, a merge-math reference document showing worked numeric examples of each equation from §8.4.

18.4 Acceptance Criteria

STACK output for two non-conflicting adapters matches applying each independently in sequence within floating-point tolerance (1e-5 relative); MERGE (TIES) output on a 2-adapter conflict fixture shows measurably reduced interference vs. naive averaging, scored against a held-out benchmark; ROUTE selects the declared routing key's adapter with 100% accuracy across a 500-case fixture set.

18.5 Conformance Fixtures

stack_two_nonconflicting.bin — expected: matches sequential independent-apply golden reference. merge_ties_vs_naive_interference.bin — expected: TIES score strictly better than naive-average baseline on the fixture's held-out benchmark. merge_dare_dropout_rescale.bin — expected: rescaled deltas match the DARE equation's algebra within tolerance. route_key_selection_500cases.bin — expected: 100% correct routing. merge_vocab_mismatch_preflight_reject.bin — expected: rejection before any merge math runs (mergekit pitfall guard).

18.6 Pitfalls

Recomputing or defaulting α/r during a merge instead of reading each source's declared value (violates I13), silently rescaling the composite delta. Allowing STACK to silently reorder two adapters it judges "non-overlapping" based on a static module-name check that misses a runtime-only overlap (e.g., a shared low-level kernel buffer) — I7 requires the declared order be preserved verbatim regardless of the engine's own overlap analysis. Running TIES/DARE merge math on adapters with different tokenizer hashes without the mergekit-style preflight check, producing a shape-valid but semantically meaningless merged tensor.

18.7 Performance Concerns

MERGE-mode static merging is a one-time cost per composite (amortized across many requests once cached as a ResolvedPlan), whereas STACK's forward-time composition recurs every request — the composition engine must expose which mode a given CompositionPolicy resolves to so the serving runtime can cache MERGE results but must recompute STACK results per request.

18.8 Edge Cases

A MERGE request combining more adapters than C11's concurrency cap (4) — must reject at composition-policy validation time, not partway through the merge loop. A ROUTE policy where no candidate's routing key matches the request — must return a clear SynapseError, never silently fall back to an arbitrary candidate.

18.9 Failure Analysis

An interference regression detected by the eval harness (Phase 7, §19) after a MERGE-path change is diagnosed by comparing the trim threshold τ and sign-election outcome against the last-known-good merge — most regressions trace to a τ value that was tuned for one adapter pair and silently reused as a global default.

18.10 Operational Notes

The merge-math reference document (§18.3) must be kept synchronized with any change to the TIES/DARE parameters' defaults, since it is the primary artifact authors consult when debugging an unexpected composite output.

19. Phase 7 — Eval Harness + Regression Gates

19.1 Objectives

Implement the evaluation harness that produces EvalReport (§11), gating registry publish per P12/I8 and feeding the resolver's eval-score check (§8.3, §15).

19.2 Detailed Implementation Steps

Implement synapse_runtime/eval_harness/: a held-out benchmark suite runner (ADR-19) executing a candidate artifact or a composite ResolvedPlan against task-specific benchmarks, computing bootstrap confidence intervals per benchmark (populating EvalReport.ConfidenceInterval). Wire the harness as a hard CI gate on the registry publish path (Phase 2, §14) — a manifest cannot transition CANDIDATE → PUBLISHED (§8.5) without EvalReport.PassedThreshold = true (I8). Implement a regression-detection mode: given a new EvalReport for an already-PUBLISHED CapabilityId version bump, compare against the prior version's report and flag a statistically significant regression (using the same bootstrap CI machinery) — triggering a transition to QUARANTINED (§8.5) rather than blocking publish outright, since a regression on an already-live artifact needs a different remediation path than a candidate that never shipped. Threshold policy is versioned independently of the harness code itself, so raising a bar does not require a harness redeploy.

19.3 Deliverable

eval_harness package, a threshold-policy config format, CI wiring that blocks publish on gate failure, a regression-quarantine workflow.

19.4 Acceptance Criteria

100% of publish attempts with PassedThreshold = false are blocked (I8, zero exceptions in a 200-case fixture sweep); regression detection flags a synthetically injected 15%-benchmark-score drop with ≥95% statistical confidence within one CI run; bootstrap CI width narrows monotonically with benchmark sample size in a sanity fixture.

19.5 Conformance Fixtures

eval_pass_threshold.bin — expected: PUBLISHED transition allowed. eval_fail_threshold.bin — expected: publish blocked, artifact stays CANDIDATE. eval_regression_injected_15pct.bin — expected: QUARANTINED transition, regression flagged with CI. eval_no_score_recorded.bin — expected: resolver-visible REJECT per §15.8's edge case, not a passing default.

19.6 Pitfalls

Treating a single benchmark run's point estimate as sufficient without the bootstrap CI, letting benchmark noise masquerade as a real pass/fail signal (ADR-19's rationale exists specifically to avoid this). Gating only at initial publish and not re-running the harness on version bumps of an already-PUBLISHED capability, missing regressions entirely (this is precisely what the regression-detection mode in §19.2 closes). Threshold policy hardcoded into harness code, forcing a redeploy every time a benchmark bar changes and coupling unrelated release trains.

19.7 Performance Concerns

Running the full benchmark suite against every composite ResolvedPlan a client might request (rather than only against published, individually-scored capabilities) would make eval an unbounded-cost hot-path operation — the harness must scope composite-plan evaluation to an explicit, separately-scheduled batch job, not the serving request path.

19.8 Edge Cases

A benchmark suite update that changes scoring methodology mid-flight — historical EvalReports must be tagged with the benchmark-suite version they were scored under, so regression comparisons never compare incompatible methodologies. A candidate artifact that passes on one benchmark but fails another within the same suite — threshold policy must specify whether gating is per-benchmark or aggregate, and the harness must apply that policy consistently.

19.9 Failure Analysis

A flood of false-positive regression flags after a harness upgrade is diagnosed by checking whether the bootstrap resampling count was reduced (widening variance, narrowing effective confidence) — the most common cause of a suddenly noisy regression signal.

19.10 Operational Notes

Quarantine transitions (§19.2) must page a human, not auto-resolve — an already- live capability regressing is a production incident, and the runbook (docs/runbooks/) must specify rollback-to-prior-version as the default immediate action pending investigation.

20. Phase 8 — Quantized-Base Support (QLoRA)

20.1 Objectives

Implement the quantization-scheme dimension of BaseModelFingerprint (§11) end to end — resolver promotion path, loader dtype handling, and serving numerics — for 4-bit NF4 quantized bases per QLoRA (Dettmers et al. 2023), closing the PhaseDeferred("§20 Phase 8 — Quantized-Base Support (QLoRA)") marker from §12 and §15/§17.

20.2 Detailed Implementation Steps

Extend LoraSpec.Dtype and BaseModelFingerprint.QuantizationScheme (§11) to carry NF4 with double quantization (ADR-13); adapters themselves remain higher-precision (bf16/fp16) even when the base is 4-bit, per QLoRA's design — only the frozen base weights are quantized. Implement the resolver's promotion-path branch (§8.3, stubbed REJECT in Phase 3, §15.2) as an explicit, declared dtype-promotion table: which (adapter dtype, base quantization scheme) pairs are accepted, keyed off manifest fields, never inferred from runtime tensor introspection (P13). Implement the loader/composition math change: the merge equation W' = W + (α/r)·BA (§8.4) must dequantize the relevant base weight block to the adapter's compute dtype before addition, then requantize only if a merge-and-freeze (P5's explicit exception) is requested — forward-time composition (the default, non-merged path) never requantizes, it computes in the adapter's native precision and casts only the output activation. Add a dtype-promotion numerics fixture suite validating that promotion does not silently change output distribution beyond a documented tolerance (§20.6 pitfall).

20.3 Deliverable

NF4 quantized-base loading path, resolver promotion-table config, dtype-promotion numerics fixture suite, updated merge-math reference doc (§18.3) covering the quantized case.

20.4 Acceptance Criteria

A QLoRA-trained r=16 adapter resolves ACCEPT against its declared NF4 base and REJECT against an undeclared-compatible fp16 base without an explicit promotion entry (P13); output distributional distance (KL divergence vs. an fp16 reference run) for a promoted-dtype path stays under a documented 0.02 threshold; adapter artifact size for a QLoRA adapter matches C1–C3 (adapter tensors are not quantized, only the base is, so sizes are unchanged).

20.5 Conformance Fixtures

qlora_nf4_base_accept.bin — expected: ACCEPT, correct dequant-before-merge path taken. qlora_undeclared_promotion_reject.bin — expected: REJECT per P13. qlora_kl_divergence_check.bin — expected: divergence under 0.02 threshold vs. fp16 reference. qlora_merge_and_freeze_requant.bin — expected: requantized merged output matches a golden NF4 reference within tolerance.

20.6 Pitfalls

Dtype promotion silently changing numerics — casting a 4-bit dequantized block up to bf16 using a different rounding mode than QLoRA's reference implementation used during training, producing outputs that "look plausible" but diverge measurably (exactly the class of bug §20.4's KL-divergence acceptance criterion exists to catch). Requantizing on every forward pass in the default non-merged path "to save memory," which both violates P5's default (base is never mutated/rewritten in place outside an explicit merge) and destroys performance. Treating quantization scheme as inferable from tensor dtype alone rather than the declared manifest field, breaking P13's "declared, not discovered" rule the moment a base is re-quantized with a different scheme but the same on-disk dtype tag.

20.7 Performance Concerns

Dequantize-before-merge adds a per-forward cost proportional to the target module's block size; this must be benchmarked against C6's latency budget separately from the unquantized Phase 4 baseline, since QLoRA's design assumption (cheaper storage, comparable compute) only holds if the dequantization kernel is efficient.

20.8 Edge Cases

An adapter trained against one double-quantization block size attempting to load against a base quantized with a different block size — must be caught by the promotion table as a distinct, non-matching scheme, not conflated with plain NF4-vs-NF4 compatibility. A merge-and-freeze request against a quantized base where the resulting merged weights would need to be requantized to remain within the original memory budget — must be an explicit, logged operation (P5 exception), never implicit.

20.9 Failure Analysis

A KL-divergence fixture failure after an otherwise-passing unit test suite usually traces to a rounding-mode mismatch in the dequantization kernel — verified by comparing intermediate dequantized tensors against the QLoRA reference implementation's output for the same input block.

20.10 Operational Notes

Runbook must document the accepted promotion-table entries as a reviewable, versioned config (not code) so platform operators can audit which (adapter-dtype, base-quantization) pairs are currently trusted without reading the resolver's source.

21. Phase 9 — Cross-Architecture Distillation

21.1 Objectives

Implement the distillation pipeline producing a DistillationJob (§11) that ports a capability from a source architecture to a target BaseModelFingerprint, closing PhaseDeferred("§21 Phase 9 — Cross-Architecture Distillation") and satisfying P10/I12's provenance requirement.

21.2 Detailed Implementation Steps

Implement synapse_runtime/distillation/: response-based knowledge distillation (Hinton et al. 2015) — the teacher is the source capability composed onto its native base, the student is a freshly-initialized adapter (LoraSpec) attached to the target architecture's fingerprint. Follow the DistilBERT recipe (Sanh et al. 2019) for the training-loop shape (temperature-scaled soft targets plus a task-specific loss term) at the level of a described procedure, not an implementation — Synapse's blueprint scope stops at "run this training job," the actual gradient loop belongs to the training substrate, not to Synapse's own code surface. On completion, produce a new CapabilityId (I12 — provenance pointer to SourceCapability), route it through the same packager/signer/resolver/eval-harness path as any authored artifact (no distillation-specific bypass of P1/P2/P12). DistillationJob.Status transitions QUEUED → RUNNING → EVAL_PENDING → COMPLETE | FAILED, with EVAL_PENDING explicitly requiring a Phase 7 (§19) EvalReport before COMPLETE — a distilled artifact is gated exactly like any other candidate.

21.3 Deliverable

distillation package, DistillationJob lifecycle implementation, an end-to-end example distilling a capability from a 7B source architecture to a differently architected target, gated through the standard eval harness.

21.4 Acceptance Criteria

A distilled artifact's EvalReport (§19) clears the same threshold policy applied to authored artifacts — no separate, lower bar; 100% of DistillationJob records reaching COMPLETE carry a non-null ResultCapability with a provenance link verifiable back to SourceCapability (I12); a fidelity regression (student score more than a documented margin below teacher score on the same benchmark) blocks the COMPLETE transition.

21.5 Conformance Fixtures

distill_cross_arch_complete.bin — expected: COMPLETE, provenance link verifiable. distill_missing_provenance_reject.bin — expected: publish blocked per I12. distill_fidelity_regression_block.bin — expected: job stays EVAL_PENDING / transitions FAILED, never COMPLETE. distill_same_arch_noop_reject.bin — expected: a same-architecture "distillation" request rejected as a misuse of the pipeline (the correct tool for same-architecture is composition, Phase 6, §18, not distillation).

21.6 Pitfalls

Folding a distilled artifact's version into its source's CapabilityId instead of minting a new one (violates P10, breaks fidelity traceability the moment the two diverge in quality). Skipping the eval harness for distilled artifacts under the assumption that "distillation is inherently lower stakes," silently shipping a lower-fidelity capability without the regression-gate protection authored artifacts get. Treating architecture porting as purely a tensor-shape-reshaping exercise (ignoring tokenizer/vocabulary differences between source and target architectures), producing a student adapter that trains but never converges to useful fidelity.

21.7 Performance Concerns

Distillation training-job cost scales with teacher-inference calls needed to generate soft targets; this is explicitly out of the serving runtime's latency budgets (C5–C7) — it is a batch job scheduled separately, and its resource consumption must not compete with live-serving GPU pool allocation (I10).

21.8 Edge Cases

A target architecture whose hidden dimension does not evenly divide by any sensible rank choice — the packager (Phase 1, §13) must still validate the resulting artifact's shapes (I5) exactly as it would an authored one; distillation gets no shape-validation exemption. A distillation job whose teacher capability is itself later QUARANTINED (§19) mid-job — must fail the job rather than complete against a since-invalidated teacher.

21.9 Failure Analysis

A student that trains without error but scores far below the teacher on the eval harness is diagnosed first against tokenizer/vocabulary alignment between source and target (§21.6's pitfall) before assuming a training-hyperparameter problem — cross- architecture vocabulary mismatch is the dominant real-world failure mode for this class of porting.

21.10 Operational Notes

DistillationJob records must remain queryable indefinitely (not garbage-collected like ephemeral verdicts, §15) since provenance (I12) must be traceable for the lifetime of the resulting CapabilityId, including after the job record's active phase ends.

22. Phase 10 — Federated Bridge + Secure Aggregation

22.1 Objectives

Implement the federated bridge coordinating multi-party training rounds, requiring either secure aggregation (Bonawitz et al. 2017) or a DP-SGD privacy budget (Abadi et al. 2016) on every FederatedRound (§11), closing PhaseDeferred("§22 Phase 10 — Federated Bridge + Secure Aggregation") and satisfying P11/I11.

22.2 Detailed Implementation Steps

Implement the federated coordinator over mutual-TLS gRPC (ADR-24): participants submit local adapter updates (never raw training data) for a declared round; the coordinator implements FedAvg (McMahan et al. 2017) as the aggregation rule over those updates. Wire secure aggregation (Bonawitz et al. 2017) as the default transport-level protection — participant updates are cryptographically summed such that the coordinator only ever observes the aggregate, never an individual participant's update — with DP-SGD (Abadi et al. 2016) noise injection as an additional, composable layer tracked via FederatedRound.PrivacyBudget (epsilon/delta accounting across rounds, cumulative spend enforced as a hard ceiling per Kairouz et al. 2021's open-problems framing of budget exhaustion). I11 is enforced at the ingestion boundary: a round missing both SecureAggProof and PrivacyBudget is rejected before any aggregation computation begins. The aggregated result becomes a new CapabilityId (FederatedRound.AggregatedDelta) routed through the standard packager/signer/resolver/eval-harness path exactly like a distilled artifact (Phase 9, §21) — no federated-specific bypass.

22.3 Deliverable

Federated coordinator service, secure-aggregation protocol implementation, DP-SGD budget accounting, an end-to-end example with ≥3 simulated participants.

22.4 Acceptance Criteria

100% of rounds missing both a SecureAggProof and a PrivacyBudget are rejected at ingestion (I11, zero exceptions across a 100-case fixture sweep); cumulative epsilon spend across a simulated 50-round sequence never exceeds the configured budget ceiling; the coordinator process never logs or persists an individual participant's raw update, verified by an audit-log content scan fixture.

22.5 Conformance Fixtures

fedround_no_privacy_reject.bin — expected: rejection per I11. fedround_secure_agg_valid.bin — expected: aggregation succeeds, coordinator log contains no per-participant plaintext update. fedround_dpsgd_budget_exhausted.bin — expected: round rejected once cumulative epsilon exceeds ceiling. fedround_malicious_participant_outlier.bin — expected: outlier update's influence bounded per the aggregation rule (ties into T7 in §24).

22.6 Pitfalls

Logging individual participant updates "temporarily for debugging" before secure aggregation completes, which defeats the entire privacy guarantee even if the production aggregation math is correct. Treating DP-SGD's epsilon budget as per-round rather than cumulative, silently allowing unbounded total privacy loss across many rounds (Kairouz et al. 2021's central open problem). Accepting a SecureAggProof without verifying it cryptographically (treating presence of the field as sufficient), which is equivalent to I11 not being enforced at all.

22.7 Performance Concerns

Secure aggregation's cryptographic overhead scales with participant count and update size; round latency must be budgeted separately from serving-path latencies (C5–C7) — federated rounds are an asynchronous batch process, never on the request hot path.

22.8 Edge Cases

A participant that drops out mid-round after submitting a partial secure-aggregation share — the protocol must have a defined dropout-tolerance threshold (a minimum participant count below which the round aborts rather than silently aggregating a weaker set). A round where all participants collude to reconstruct another non-colluding participant's update from the aggregate (a known secure-aggregation threat, tracked in §24 as T7) — mitigated by a minimum-cohort-size policy.

22.9 Failure Analysis

An unexpectedly low aggregated-artifact eval score is diagnosed first against whether DP-SGD noise was miscalibrated (too aggressive for the cohort size) before assuming a data-quality problem among participants — noise-to-signal ratio scales inversely with cohort size and is the most common cause of unexplained quality loss in federated rounds.

22.10 Operational Notes

Privacy-budget ledgers must be exposed to participants themselves (not just operators) so participating organizations can independently verify their epsilon spend has not exceeded what they consented to.

26. Operational Readiness

On-call rotation covers registry (index + blob store), resolver, and serving runtime as three separately pageable services, since their failure modes and RTOs differ (C13–C15). Federated-bridge operational readiness additionally requires a published, participant-visible privacy-budget ledger (§22.10) reviewed before every new cohort's round sequence begins.

27. Compatibility & Versioning

CapabilityId.Version follows SemVer 2.0.0 (ADR-17): a major-version bump signals a breaking change to the declared base-architecture contract (target modules, rank, or required base fingerprint fields); minor bumps signal additive, backward-compatible manifest fields; patch bumps signal no contract change (re-training with identical declared shape). The artifact byte-layout format version (§8.1) is independent of CapabilityId versioning and changes only when the container structure itself changes — the format-version fixture (regression_v0_format_replay.bin, §12.5) exists specifically to catch accidental format-version drift. Manifest schema evolution is additive-only (§12.9): new protobuf fields must have safe defaults so an old decoder reading a new manifest degrades gracefully rather than failing closed on an unrecognized-but-non-load- bearing field. Deprecation of a PUBLISHED capability transitions it to DEPRECATED (§8.5) with a mandatory successor pointer; the resolver returns WARN_ACCEPT with the successor CapabilityId rather than an outright REJECT, giving consumers a migration path. Quantization-scheme and architecture-family fields (§11) are never silently reinterpreted across a minor version — any change to how those fields are interpreted is itself a major-version change to the format spec, not the individual capability.

28. Testing & Verification Strategy

Layered verification, narrowest to broadest: unit tests within each crate/service/package (Rust synapse-format/synapse-sign, Go resolver/ registry-index, Python synapse_runtime); conformance fixtures (§12.5 onward, one set per phase, accumulating in conformance/fixtures/) verified identically across all three language surfaces starting formally in Phase 11 (§23) but authored incrementally from Phase 0; fuzz targets (fuzz/) against every untrusted-input parsing boundary (artifact bytes, signature envelope, manifest protobuf) seeded from the malformed-fixture corpus; load/throughput benchmarks (benchmarks/) validating the C-series constraints (§4) and M-series targets (§30); the eval harness (§19) itself as a testing layer for capability quality, distinct from format/behavior correctness; chaos drills (§26) validating RTOs under induced failure. Every phase's acceptance criteria (N.4) must have a corresponding fixture (N.5) — a phase is not complete if any N.4 claim lacks a fixture proving it.

29. Build & Release Engineering

CI (ci.yml) runs on every commit: build all three language surfaces, run unit tests, run the conformance suite against fixtures accumulated to date. Release (release.yml) triggers on a semver tag: builds signed release artifacts for the Rust binaries and Go services (software-supply-chain signing, distinct from but using the same Sigstore/in-toto tooling as ADR-03/ADR-18 apply to capability artifacts themselves — the tooling is shared, the trust roots are not), publishes container images, and updates CHANGELOG.md. Fuzz (fuzz.yml) runs on a schedule (nightly, plus the full 24-hour sweep required by §23.4 before any major release). Rollback strategy: registry-index and resolver services are deployed with the prior version kept warm for immediate traffic-shift rollback (no cold restart on rollback); the serving runtime's synapse_runtime package pins exact dependency versions so a rollback never silently picks up an incompatible PyTorch/CUDA combination. Release gating requires: green CI, a passing conformance run, and — for any release touching the format/manifest/signature surfaces — an updated ADR (docs/adr/) documenting the change per §27's compatibility rules.

31. Scalability Analysis

Registry index scales horizontally via PostgreSQL read replicas (ADR-05, Kleppmann's replication chapter, §5); the resolver and blob-store gateway are stateless and scale by adding nodes behind a load balancer, bounded only by index read-replica capacity. The blob store scales via the underlying S3-compatible object storage's native horizontal scaling plus CDN edge caching for hot artifacts, directly reducing C8's per-node pull-bandwidth pressure at fleet scale. The serving runtime scales by adding GPU nodes, each independently bounded by C10's per-node pool ceiling — total fleet adapter-residency capacity is nodes × C4, and C12's storage-growth rate combined with C4 determines how many nodes are needed to keep a given hit-rate of "already resident" adapters as the catalog grows. The federated bridge coordinator scales by sharding independent training cohorts across coordinator instances — a single coordinator instance handles one cohort's round sequence at a time (secure aggregation's cryptographic protocol is inherently per-cohort), so horizontal scaling here means running more cohorts concurrently, not making one cohort's rounds faster.

32. Mental Models & First Principles

MM1 — Composition is vector addition in weight space. Insight: a LoRA delta ΔW = (α/r)·B·A is a low-rank direction in weight space; composing two adapters is summing directions, and interference is just non-orthogonality between them. Predicts: near-orthogonal task adapters stack cleanly; adapters touching the same modules with correlated directions degrade each other. Bug without it: treating "more adapters" as strictly additive capability with no interference budget, silently shipping degraded composed output. Resolves: §18, §8.4.

MM2 — The trust boundary is per-byte, not per-file. Insight: the signature covers manifest ‖ tensor index ‖ blob digest tree as one unit (§8.1); there is no "the manifest is signed, trust the blob bytes" shortcut. Predicts: any single tampered byte anywhere in the artifact fails verification globally. Bug without it: verifying only metadata and trusting blob content unconditionally, leaving I9 violations undetected until numerically wrong output appears. Resolves: §13, §24 T5.

MM3 — Compatibility is proof, not trial-and-error. Insight: a CompatibilityVerdict is a decision-table output over declared facts (§8.3), computed before any GPU work, not inferred by attempting a load and seeing if it errors. Predicts: rejection is millisecond-cheap (M9); false negatives (over-strict subset match) are the safe failure mode, not false positives. Bug without it: "try it and see" lets coincidentally-matching shapes mask a real incompatibility, producing silent corruption (P6). Resolves: §15, §8.3.

MM4 — Base weights are read-only; adapters are functions, not patches. Insight: an adapter composes at forward time (P5); it never mutates the resident base tensor, which is what makes multi-tenant sharing of one resident base model possible at all. Predicts: N tenants share one base economically; merge-and-freeze is a rare, explicit, logged exception, never the default path. Bug without it: in-place mutation from one tenant's adapter corrupts every concurrent tenant's request on the same base (I3). Resolves: §16, §7 I3.

MM5 — Dedup is a side effect of addressing, not a feature. Insight: content-addressed, per-blob storage (P8) makes "does this tensor block already exist" a hash lookup; deduplication and garbage collection fall out of the addressing scheme rather than needing a bolted-on tracking system. Predicts: registry storage grows sublinearly in artifact count once shared base-layer blocks recur (C12's ~40% dedup). Bug without it: per-package storage (the ADR-04 rejected alternative) makes reference counting — and therefore GC — impossible without a second system. Resolves: §14, P8.

MM6 — Rank is a capacity budget, not a free parameter. Insight: artifact size and swap latency scale linearly with r (C1→C3 is an 8x jump for an 8x rank increase); capability does not scale linearly with it past a task-appropriate rank. Predicts: naive "default to high rank for safety" blows the resident-adapter budget (C4) and the throughput curve (C7) for marginal quality return. Bug without it: authors over-provision rank, and the fleet silently loses adapter-residency headroom. Resolves: §34, §4 C1–C4.

MM7 — An eval gate is a hypothesis test, not a spot check. Insight: a benchmark score has sampling noise; promotion decisions need a confidence interval (ADR-19), not a point estimate. Predicts: two artifacts with identical point-estimate scores can carry very different promotion risk if their bootstrap CI widths differ (M10). Bug without it: regressions within the noise band get promoted or blocked inconsistently, eroding the meaning of "PUBLISHED" (P12). Resolves: §19, ADR-19.

MM8 — Composition order is a non-commutative operator. Insight: for overlapping target modules, STACK(A,B) ≠ STACK(B,A) (§8.4); order is data, not an incidental request detail. Predicts: identical adapter sets requested in different order are two distinct, both valid, outputs. Bug without it: caching or logging by adapter-set-as-set conflates two genuinely different results (P3, I7). Resolves: §18, §7 I7.

MM9 — Architecture-scoping trades precision for reusability, and the eval gate is what keeps that trade safe. Insight: BaseModelFingerprint captures architecture family, not checkpoint identity (P7); a single artifact resolves against any checkpoint sharing the fingerprint, with quality enforced downstream by score rather than upstream by identity. Predicts: the same artifact reuses across a whole checkpoint lineage; safety depends entirely on the eval gate actually running. Bug without it: over-narrow checkpoint-pinning makes the registry useless at scale; over-broad with no gate makes it unsafe. Resolves: §8.3, §15.

MM10 — A privacy budget is a ledger, not a one-time knob. Insight: cumulative epsilon spend across FederatedRounds must accumulate and be enforced monotonically (I11); "we used DP-SGD" without a running ledger is theater. Predicts: a bridge that resets epsilon per round instead of accumulating silently exceeds any real guarantee after enough rounds. Bug without it: FM-7, the exact privacy-budget-breach failure class the ledger exists to prevent. Resolves: §22, §7 I11, §25 FM-7.

34. Back-of-Envelope Capacity Model

Methodology: every number below re-derives a §4 constraint (or extends one) from first principles, formula shown inline, not just the answer.

1. Adapter artifact size at rank r. Formula: size(r) = 2 × r × d_model × modules_per_layer × layers × bytes_per_param (the 2 is the A+B matrix pair per module). d_model=4096, modules_per_layer=4 (q_proj/k_proj/v_proj/o_proj), layers=32 → modules_total = 4×32 = 128.

  • r=8: 2×8×4096×128×2 bytes → 16×4096=65,536; ×128=8,388,608; ×2=16,777,216 bytes ≈16.0 MiB payload → C1 (16.8 MB with ~40 KB manifest/index overhead).
  • r=16: double r=8 → 33,554,432 bytes ≈32.0 MiB → C2 (33.6 MB w/ overhead).
  • r=64: 4× r=16 → 134,217,728 bytes ≈128.0 MiB → C3 (134.2 MB w/ overhead).

2. Resident adapters per GPU (C4). Formula: resident_count = adapter_pool_bytes ÷ artifact_size. 80 GB HBM under C10's ceiling, minus base (bf16 7B ≈14 GB) plus KV-cache reserve, leaves ≈40 GB adapter pool. 40 GB ÷ 33.6 MB (r=16, C2) = 1,190.5 → rounded down for index/bookkeeping overhead ≈1,200 (C4).

3. Adapter swap latency p50 (C5). Formula: latency = artifact_size ÷ effective_PCIe_bandwidth. Effective PCIe4 x16 bandwidth ≈25.6 GB/s (≈80% of raw 32 GB/s). 33.6 MB ÷ 25.6 GB/s = 0.0336 GB ÷ 25.6 GB/s ≈1.31 ms ≈ C5's 1.3 ms p50.

4. Extra GEMM FLOPs per token under composition. Per-module LoRA forward is two GEMV ops: r_out = A·x (r×d_model by d_model×1 → 2×r×d_model FLOPs), then h_delta = B·r_out (d_model×r by r×1 → 2×d_model×r FLOPs); total per module-instance = 4 × r × d_model. Across modules_total=128 for one active adapter at r=16: 4×16×4096×128 → 64×4096=262,144; ×128=33,554,432 ≈33.55M FLOPs/token/adapter. At C11's cap of 4 composed adapters: 4×33.55M ≈134.2M FLOPs/token. Against a 7B-parameter base's ≈14 GFLOPs/token (≈2×params, standard forward-pass estimate): 134.2M ÷ 14G ≈0.96% raw-compute overhead — far under C6's 8% ceiling, confirming C6's budget is dominated by memory/kernel-launch cost (§17), not raw FLOPs (Hard Question 18, §35).

5. Registry storage growth, daily and annualized (C12). Formula: raw_growth = new_artifacts_per_day × avg_artifact_size; net_growth = raw_growth × (1 − dedup_rate). 1,000 new r=16 artifacts/day × 33.6 MB = 33.6 GB/day raw; ×(1−0.40) = 20.16 GB/day net (C12). Annualized: 20.16 GB/day × 365 ≈7.36 TB/year net registry growth at steady-state publish rate.

6. Verification throughput and cold-start burst. Formula: cold_verify_time = artifact_size ÷ hashing_throughput. At ≈1 GB/s SHA-256 throughput: r=64 (134 MB, C3) → 134 ms (C9 cold); r=16 (33.6 MB) → 33.6 ms. For a cache-miss burst of K=100 freshly-pulled r=16 adapters serialized on one hashing core: 100 × 33.6 ms = 3.36 s; parallelized across 8 hashing threads (typical verifier worker pool): 3.36 s ÷ 8 ≈0.42 s burst cold-start latency.

7. Verification throughput, checks/s per core. Formula: throughput = 1 ÷ per_check_latency. Cold path: 1 ÷ 0.134 s ≈7.46 checks/s/core (C9 cold). Warm path (cached-digest short-circuit, ≤2 ms, C9 warm): 1 ÷ 0.002 s = 500 checks/s/core — a 67x throughput gap that is the entire justification for P4's TTL-bounded warm-cache carve-out.

8. Fleet-wide adapter-residency capacity (§31). Formula: fleet_capacity = nodes × C4. A 10-node serving fleet: 10 × 1,200 = 12,000 resident adapters fleet-wide, before any single node needs a cache-miss cold pull (§31; C4 and C12 jointly determine how fast catalog growth outruns this ceiling).

35. Hard Questions (Self-Examination)

  1. If a resolver's ACCEPT verdict is cached (P9) and later an eval score is retroactively found gamed (post-publish regression), how does the system unwind already-served requests without violating I4's determinism guarantee? (§8.3, §19, §25 FM-6)

  2. Under C10's pool ceiling and C11's max-4-composition cap, what happens to a request specifying 5 STACK-composed adapters — resolver-time REJECT or runtime-time backpressure, and which invariant governs which? (§7 I10, §4 C11, §8.6)

  3. Given P5 (base weights never mutated except explicit merge-and-freeze) and ADR-08's dedicated LRU pool, how does an operator distinguish "the pool evicted my hot adapter" from "someone ran merge-and-freeze on the base" when diagnosing a latency spike? (§25 FM-3, §7 I3, §18)

  4. If TIES-Merging (ADR-10) trims and elects signs across adapters trained on quantized (NF4) and full-precision bases respectively, does I13's "exact alpha/r scaling per source manifest" still hold post-dequantization, or does Phase 8's promotion path need its own merge-scaling rule? (§20, §18, §7 I13)

  5. P7 makes artifacts architecture-scoped rather than checkpoint-scoped — how does the eval gate (I8) distinguish "broadly compatible" from "passed eval against one lucky checkpoint in its architecture family"? (§8.3, §19)

  6. §22's federated bridge produces an AggregatedDelta as a CapabilityId — does it pass through the same P2/I2 resolution and P12 eval gate as an individually-authored adapter, or does federated provenance grant a different promotion path? (§22, §8.5)

  7. C12's dedup assumes 40% storage reduction from shared base-fingerprint blocks — under P8 (per-blob addressing), what dedup rate should be expected between two independently-trained adapters on the same modules/base (near-zero shared bytes) versus a merge-and-freeze derivative of an existing artifact (potentially high shared bytes)? (§4 C12, P8, §18)

  8. I7 requires byte-identical composition-order preservation — how does this interact with ADR-07's SGMV batched kernel, which processes many requests' adapter sets in one batched GEMM call; does batching risk silently reordering per-request composition sequences for throughput? (§7 I7, §17, ADR-07)

  9. FM-2's resolver false-reject cascade is triggered by TargetModuleSet normalization drift — what in §28's testing strategy would have caught this before production, given per-crate unit tests don't exercise cross-service normalization consistency? (§25 FM-2, §28, §8.3)

  10. T7 (federated poisoning) and I11 (privacy-boundary requirement) both gate FederatedRound ingestion — can a well-formed secure-aggregation proof (satisfying I11) still admit a poisoned outlier update (T7), and if so, which control actually catches it? (§24 T7, §7 I11, §22)

  11. M12's distillation fidelity margin is a Phase 9 gate — combined with P10's provenance-pointer requirement and I12, what should happen if a distilled artifact scores above its teacher (an unexpectedly favorable, possibly suspicious result)? (§21, §7 I12, §19)

  12. §20's quantized-base promotion path allows an fp16-trained adapter onto an NF4 base with a "declared promotion path" — how does §8.3's decision table distinguish a legitimate promotion from T-class dtype-mismatch exploitation absent an explicit human sign-off step? (§8.3, §20, §24)

  13. C4's resident-adapter count and C7's throughput curve are functions of N concurrent adapters, but composition (C11, ≤4 per request) means one request may occupy up to 4 pool slots simultaneously — does §17's capacity planning (M4/M5) account for composed-request slot multiplication, or only distinct- adapter count? (§4 C4/C7/C11, §17, §34)

  14. §27 says manifest schema evolution is additive-only, but §8.1's byte-layout format version is independent — when a format-version bump occurs mid- registry-lifetime, do already-PUBLISHED artifacts need re-signing, or must the verifier support N and N−1 format versions simultaneously? (§27, §8.1, §29)

  15. ADR-09 places the resolver server-side, client-cached — under I4 (deterministic plan given inputs), what invalidates a client's cached ResolvedPlan when the server-side eval score changes post-hoc (e.g. a regression detected after initial ACCEPT)? (§7 I4, ADR-09, §25 FM-6)

  16. §21's cross-architecture distillation and §36's rejected full-fine-tune checkpoint registry both eventually produce a new artifact tied to a target architecture — what makes the distillation path categorically different from the rejected full-fine-tune-registry path in the trust/compatibility machinery each must satisfy? (§21, §36, P10)

  17. §26's chaos drills exercise C13 (registry failover) and C14 (blob RTO) quarterly, but T10 describes a Rekor transparency-log outage forcing fail-closed signing — is a Rekor outage itself drilled, and if not, which FM/T-row's recovery procedure has never been chaos-tested? (§24 T10, §26, §25)

  18. §34's extra-GEMM-FLOPs-per-token calculation shows composition overhead is <1% of base compute, yet C6 sets an 8% measured latency budget — what does the gap between the FLOPs-level estimate and the empirical ceiling reveal about where the real cost of composition actually lives? (§34, §4 C6, §17)

36. Alternative Architectures (Roads Not Taken)

(a) Full-Fine-Tune Checkpoint Registry — no adapters at all, every capability is a complete retrained checkpoint.

Author --> full fine-tune --> 14+ GB checkpoint
                                     |
                                     v
                             Checkpoint Registry
                        (one full copy per capability)
                                     |
                +--------------------+--------------------+
                v                                          v
         Serving Node A                             Serving Node B
    (loads whole ckpt #1,                       (loads whole ckpt #2,
     no shared base weights)                     no shared base weights)

Winning regime: few capabilities, no cross-capability GPU sharing need, and full-fine-tune quality ceiling matters more than storage/serving cost. REAL system: a plain per-model Hugging Face Hub repo storing whole fine-tuned checkpoints instead of PEFT adapters — the "one checkpoint per task" pattern many orgs already run internally. Why rejected: storage scales linearly with capability count at 10–100x an r=16 adapter's size (C2 vs. a 14 GB checkpoint); no hot-swap since each capability needs its own resident base copy, destroying C4/C10's shared-base economics; no composition primitive exists at all.

(b) Jointly-Trained Mixture-of-Experts Router — a learned router over experts trained together, not post-hoc composable adapters.

        Training-time only
   +----------------------------+
   |  Base transformer trunk    |
   |  Router (gating network)   |
   |  Expert_1 ... Expert_N     |   <- trained jointly, one run
   +----------------------------+
                 |
                 v
         Single frozen model
   (adding Expert_N+1 requires
    retraining router + experts)

Winning regime: the full capability set is known upfront and can be trained together, and post-hoc capability addition without retraining is not required — maximizes per-token quality via joint optimization. REAL system: Mixtral-style sparse MoE models (Mistral AI) and Switch Transformer (Fedus et al.), experts and router trained jointly from scratch. Why rejected: adding a capability requires retraining the router and potentially every expert, violating §1's "attach without retraining" premise entirely; no post-hoc third-party capability authoring, breaking the multi-author registry model; no independent signing/versioning per capability — P10's provenance-pointer has no analog for one expert inside a jointly trained mixture.

(c) Prompt/Context-Only Capability Packaging — capability as a signed prompt/exemplar bundle, no weight delta.

Capability = { prompt_template, few-shot exemplars, retrieval_cfg }
                        |
                        v
     signed bundle --> injected into context window at inference
                        |
                        v
     Base model (unmodified weights, zero deltas)
     -- capability "strength" bounded by token budget, not rank

Winning regime: base model is closed/API-only with zero weight access — the only composable-capability mechanism available at all in that setting. REAL system: soft-prompt tuning (Lester, Al-Rfou & Constant 2021) and, more practically, prompt-template/library ecosystems (e.g. LangChain prompt hubs) packaging reusable prompts as the unit of "capability." Why rejected: no weight-space precision — P6's declared rank/alpha/dtype has no analog, so capability magnitude and interference are not formally boundable; composing many "capabilities" competes with the user's actual query for the same token budget; cannot express capabilities requiring learned representational shifts (translation, code-domain adaptation) at LoRA's fidelity.

(d) Compile-Time Merge-and-Freeze Pipeline — merge once at build time, deploy one static model, no runtime composition engine.

Author declares capability set (build-time)
                |
                v
    merge pipeline (TIES/DARE/task-arith, run ONCE)
                |
                v
    single static merged checkpoint
                |
                v
    deployed as-is: no runtime composition engine,
    no per-request STACK/MERGE/ROUTE, no hot-swap

Winning regime: exactly one fixed capability set is needed in production long-term (a single-SKU deployment) and per-request composition overhead (however small per §34) isn't worth paying forever. REAL system: mergekit used in its offline-only mode (§33) — teams that merge once and deploy the static result with vanilla vLLM/TGI, no adapter runtime at all. Why rejected as Synapse's primary model: a static merge forecloses hot-swap (P5), forecloses per-tenant/ per-request composition variety (C11 — the merge-side analog of ADR-11's "full retraining wins" regime), and forecloses eval-gated per-artifact revocation (I8 — no way to revoke one ingredient out of an already-frozen merge without re-merging); Synapse keeps this available as an ADR-11-endorsed escape hatch (P5's explicit merge-and-freeze) for the fixed-SKU case, but rejects it as the default architecture.

38. Glossary

Adapter interference — quality degradation from composing non-orthogonal LoRA deltas on overlapping modules (MM1, §18).

Alpha (α) — LoRA scaling factor applied to the low-rank delta (§8.2, §8.4).

Architecture family — the base-model lineage field (e.g. "llama", "mistral") in BaseModelFingerprint (§11, P7).

Base-model fingerprint — BaseModelFingerprint: architecture family, hidden size, layer count, vocab size, quantization scheme, optional checkpoint digest (§11).

Bootstrap confidence interval — resampling-based CI on an eval score, used for regression-gate significance (ADR-19, M10).

Capability artifact — the signed, self-describing package containing a manifest, tensor index, and tensor blobs (§8.1).

CapabilityId — namespaced, versioned, content-addressed identifier for a capability artifact (§11).

Composition policy — CompositionPolicy: STACK/MERGE/ROUTE mode plus ordered capability list (§11, P3).

Conformance fixture — a named input/expected-output pair exercised identically across language surfaces (§12.5, §28).

Content-addressed storage — blob storage keyed by content hash, enabling per-blob dedup (§14, P8).

DARE (Drop And REscale) — merge method dropping and rescaling delta weights by Bernoulli mask (Yu et al. 2024; §8.4, ADR-10).

Digest tree — the hierarchical hash structure covering manifest, tensor index, and blobs, checked at verification (§8.1, I9).

Distillation — producing a new capability for a different base architecture by training against a teacher's outputs (§21).

DistillationJob — lifecycle record for a distillation run: source, target fingerprint, status, result (§11).

Double quantization — QLoRA technique quantizing the quantization constants themselves (Dettmers et al. 2023; §20, ADR-13).

DP-SGD — differentially private SGD bounding per-round privacy loss (Abadi et al. 2016; ADR-15).

Eval gate — the hard promotion check requiring EvalReport to clear a threshold before PUBLISHED (P12, §19).

EvalReport — benchmark scores, confidence intervals, and pass/fail record for a capability (§11).

FedAvg — federated averaging round algorithm (McMahan et al. 2017; ADR-14, §22).

FederatedRound — a bridge round record: participants, privacy budget or secure-agg proof, aggregated delta (§11).

Fidelity margin — the acceptable quality gap between a distilled student and its teacher (M12, §21).

Fulcio — the Sigstore short-lived certificate issuer used in keyless signing (§13, ADR-03).

Hot-swap — replacing a serving node's active adapter set without restarting the base-model process (§16, P5).

In-toto attestation — a signed statement about a build/publish step, providing provenance (ADR-18).

LoRA (Low-Rank Adaptation) — low-rank weight delta ΔW = (α/r)·B·A (Hu et al. 2021; §8.4).

LRU eviction — least-recently-used pool-slot reclamation policy under memory pressure (I10, ADR-08).

Merge-and-freeze — the explicit, logged operation that statically bakes an adapter into base weights, the sole exception to P5.

NF4 (4-bit NormalFloat) — QLoRA's quantized base-weight datatype (§20).

NFE (Number of Forward Evaluations) — count of benchmark forward passes underlying an eval score's bootstrap resampling (§19, ADR-19).

PEFT (Parameter-Efficient Fine-Tuning) — the family of fine-tuning methods adjusting a small parameter subset instead of all weights (Houlsby et al. 2019; §8, §5).

Plan hash — the deterministic hash identifying a ResolvedPlan for caching (§8.6, I4).

Pool slot — a unit of GPU-resident adapter memory tracked by AdapterHandle (§11, I10).

Prefix-tuning — continuous-prompt conditioning as a non-weight-delta capability shape (Li & Liang 2021; §36).

Privacy budget (epsilon/delta) — the DP-SGD spend ledger bounding worst-case membership-inference risk (DPBudget, I11).

Quantization scheme — QuantScheme: the declared base-model quantization dtype family, part of the compatibility fingerprint (§11, P13).

QLoRA — LoRA fine-tuning atop an NF4-quantized frozen base (Dettmers et al. 2023; §20, ADR-13).

Rank (r) — the LoRA low-rank dimension; capacity/size/latency budget knob (§8.2, §34 MM6).

Response-based knowledge distillation — matching student output logits to a teacher's, architecture-agnostic (Hinton et al. 2015; ADR-12).

ResolvedPlan — the deterministic, cacheable output of resolving a ServingRequest's composition against a base (§11, P9).

Secure aggregation — cryptographic protocol combining client updates without revealing individual contributions (Bonawitz et al. 2017; §22, I11).

Signature envelope — SignatureEnvelope: algorithm, signature bytes, cert chain, transparency-log index (§11, §8.1).

Sigstore — keyless signing infrastructure (Fulcio + Rekor) backing artifact signatures (ADR-03).

Soft prompt tuning — learned continuous prompt embeddings as a capability-packaging alternative (Lester, Al-Rfou & Constant 2021; §36).

SGMV (Segmented Gather Matrix-Vector) — batched-kernel strategy for heterogeneous-rank multi-adapter serving (Chen et al. 2024; ADR-07, §17).

SLSA provenance — a build-provenance predicate level standard used in attestations (ADR-18).

Target modules — TargetModuleSet: the named base-model sublayers (e.g. q_proj) an adapter touches (§11, I2).

Task arithmetic — additive composition of task vectors (deltas) across adapters (Ilharco et al. 2023; §8.4, ADR-11).

Tensor index — the ordered array of TensorIndexEntry describing each tensor's offset/shape/digest within an artifact (§8.1, §11).

TIES-Merging — trim + sign-election merge rule reducing interference (Yadav et al. 2023; §8.4, ADR-10).

Tokenizer hash/fingerprint — the digest identifying tokenizer compatibility between adapter and base (§8.2, I6).

Transparency log (Rekor) — the append-only log recording signing events, required by P4/ADR-03's fail-closed policy (§13, T10).

Unified paging — S-LoRA-style single memory pool shared across many adapters, analogous to PagedAttention (ADR-08, §33).
