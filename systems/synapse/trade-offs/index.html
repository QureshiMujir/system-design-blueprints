ADR-01

Artifact serialization format

Chosen

safetensors-style flat header + raw tensor blocks

Rejected

torch.save/pickle, ONNX, HDF5

When the rejected choice is right

pickle wins only in a single-machine, trusted, offline research notebook kept off any distribution path

Why: no code execution on load, direct mmap into GPU tensors (P1)

ADR-02

Manifest encoding

Chosen

Protocol Buffers (proto3)

Rejected

JSON, YAML, MessagePack

When the rejected choice is right

JSON wins for a human-hand-edited, low-volume local CLI config file

Why: schema evolution via field numbers, compact binary, multi-language codegen

ADR-03

Signature scheme

Chosen

Sigstore keyless signing (Ed25519 via Fulcio/Rekor)

Rejected

self-managed PGP keys, private-CA RSA

When the rejected choice is right

self-managed PGP wins in an air-gapped deployment with no network path to a transparency log

Why: transparency log + short-lived certs remove long-lived key custody risk

ADR-04

Content-addressed storage backend

Chosen

S3-compatible object store behind an OCI-distribution-spec API

Rejected

When the rejected choice is right

plain filesystem wins for a single-node home-lab deployment under 10 GB total artifacts

Why: reuses existing container-registry tooling and auth ecosystems

ADR-05

Registry index database

Chosen

PostgreSQL

Rejected

When the rejected choice is right

ADR-06

Serving runtime language/runtime

Chosen

Python (PyTorch) host process, Rust-accelerated hot paths

Rejected

When the rejected choice is right

ADR-07

Batched multi-adapter kernel strategy

Chosen

Segmented Gather Matrix-Vector (SGMV, Punica-style)

Rejected

When the rejected choice is right

pad-to-max-rank wins when the whole fleet shares one identical rank

ADR-08

GPU memory management for adapters

Chosen

Rejected

When the rejected choice is right

ADR-09

Compatibility resolver placement

Chosen

Rejected

When the rejected choice is right

ADR-10

Composition merge default

Chosen

TIES-Merging trim+sign-election, DARE opt-in

Rejected

When the rejected choice is right

naive averaging wins merging 2 highly-correlated adapters from the same checkpoint lineage

ADR-11

36. Alternative Architectures (Roads Not Taken)

(a) Full-Fine-Tune Checkpoint Registry — no adapters at all, every capability is a complete retrained checkpoint.

Author --> full fine-tune --> 14+ GB checkpoint
                                     |
                                     v
                             Checkpoint Registry
                        (one full copy per capability)
                                     |
                +--------------------+--------------------+
                v                                          v
         Serving Node A                             Serving Node B
    (loads whole ckpt #1,                       (loads whole ckpt #2,
     no shared base weights)                     no shared base weights)

Winning regime: few capabilities, no cross-capability GPU sharing need, and full-fine-tune quality ceiling matters more than storage/serving cost. REAL system: a plain per-model Hugging Face Hub repo storing whole fine-tuned checkpoints instead of PEFT adapters — the "one checkpoint per task" pattern many orgs already run internally. Why rejected: storage scales linearly with capability count at 10–100x an r=16 adapter's size (C2 vs. a 14 GB checkpoint); no hot-swap since each capability needs its own resident base copy, destroying C4/C10's shared-base economics; no composition primitive exists at all.

(b) Jointly-Trained Mixture-of-Experts Router — a learned router over experts trained together, not post-hoc composable adapters.

        Training-time only
   +----------------------------+
   |  Base transformer trunk    |
   |  Router (gating network)   |
   |  Expert_1 ... Expert_N     |   <- trained jointly, one run
   +----------------------------+
                 |
                 v
         Single frozen model
   (adding Expert_N+1 requires
    retraining router + experts)

Winning regime: the full capability set is known upfront and can be trained together, and post-hoc capability addition without retraining is not required — maximizes per-token quality via joint optimization. REAL system: Mixtral-style sparse MoE models (Mistral AI) and Switch Transformer (Fedus et al.), experts and router trained jointly from scratch. Why rejected: adding a capability requires retraining the router and potentially every expert, violating §1's "attach without retraining" premise entirely; no post-hoc third-party capability authoring, breaking the multi-author registry model; no independent signing/versioning per capability — P10's provenance-pointer has no analog for one expert inside a jointly trained mixture.

(c) Prompt/Context-Only Capability Packaging — capability as a signed prompt/exemplar bundle, no weight delta.

Capability = { prompt_template, few-shot exemplars, retrieval_cfg }
                        |
                        v
     signed bundle --> injected into context window at inference
                        |
                        v
     Base model (unmodified weights, zero deltas)
     -- capability "strength" bounded by token budget, not rank

Winning regime: base model is closed/API-only with zero weight access — the only composable-capability mechanism available at all in that setting. REAL system: soft-prompt tuning (Lester, Al-Rfou & Constant 2021) and, more practically, prompt-template/library ecosystems (e.g. LangChain prompt hubs) packaging reusable prompts as the unit of "capability." Why rejected: no weight-space precision — P6's declared rank/alpha/dtype has no analog, so capability magnitude and interference are not formally boundable; composing many "capabilities" competes with the user's actual query for the same token budget; cannot express capabilities requiring learned representational shifts (translation, code-domain adaptation) at LoRA's fidelity.

(d) Compile-Time Merge-and-Freeze Pipeline — merge once at build time, deploy one static model, no runtime composition engine.

Author declares capability set (build-time)
                |
                v
    merge pipeline (TIES/DARE/task-arith, run ONCE)
                |
                v
    single static merged checkpoint
                |
                v
    deployed as-is: no runtime composition engine,
    no per-request STACK/MERGE/ROUTE, no hot-swap

Winning regime: exactly one fixed capability set is needed in production long-term (a single-SKU deployment) and per-request composition overhead (however small per §34) isn't worth paying forever. REAL system: mergekit used in its offline-only mode (§33) — teams that merge once and deploy the static result with vanilla vLLM/TGI, no adapter runtime at all. Why rejected as Synapse's primary model: a static merge forecloses hot-swap (P5), forecloses per-tenant/ per-request composition variety (C11 — the merge-side analog of ADR-11's "full retraining wins" regime), and forecloses eval-gated per-artifact revocation (I8 — no way to revoke one ingredient out of an already-frozen merge without re-merging); Synapse keeps this available as an ADR-11-endorsed escape hatch (P5's explicit merge-and-freeze) for the fixed-SKU case, but rejects it as the default architecture.
