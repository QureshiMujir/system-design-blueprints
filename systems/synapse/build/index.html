⬜ Phase 0 — Skeleton + Artifact Format + CI §12

Objectives

Establish the capability-artifact byte layout (§8.1), the ArtifactManifest and TensorIndexEntry schemas (§11), and a CI pipeline that exercises them against a conformance fixture set, with no signing, no registry, and no network calls yet.

Deliverable

synapse-format crate, synapse-cli binary, synapse-conformance fixture runner, green CI on ci.yml for every commit.

Acceptance

synapse validate rejects 100% of the malformed fixtures in §12.5 with a non-zero exit code and a SynapseError variant printed; round-trip encode→decode of a valid r=8/16/64 manifest (§4 C1–C3 sizes) preserves every field bit-for-bit; manifest length bound-check rejects any declared length exceeding 64 MiB hard ceiling.

Fixtures

valid_r8_llama7b.bin, valid_r16_llama7b.bin, valid_r64_llama7b.bin — expected: parse success, round-trip match. malformed_truncated_index.bin — expected: ErrShapeMismatch-class parse rejection (§8.8). malformed_oversized_manifest_len.bin — expected: bound-check rejection before allocation. malformed_rank_shape_mismatch.bin — expected: ErrShapeMismatch at I5 check. regression_v0_format_replay.bin — a frozen Phase-0 format-version artifact replayed on every CI run to catch accidental breaking changes to the byte layout.

Pitfalls

Manifest-length field trusted before bounds-checking, reproducing the safetensors header-overflow class (§5) as an allocation-size DoS. Protobuf optional-field defaults silently treated as "compatible" when they actually indicate "field never set by an old packager version" (§27 foreshadowing). Tensor-index offsets computed relative to the wrong base (file start vs. blob-region start) causing off-by-header- length reads. Alignment padding omitted, breaking future mmap (§16) assumptions.

⬜ Phase 1 — Packager + Signer/Verifier §13

Objectives

Add the trust boundary: a packager that emits artifacts conforming to Phase 0's format plus author-declared provenance, and a signer/verifier implementing P1's "deserialization must not execute code" guarantee end-to-end with a real signature (I1, P4).

Deliverable

synapse-sign crate, synapse-cli pack|sign|verify subcommands, a documented signer key-custody runbook (docs/runbooks/).

Acceptance

100% of Phase-0-valid fixtures sign and verify round-trip; a bit-flipped tensor byte in any signed fixture is detected by verify with ErrVerificationFailed before any tensor read; verification latency meets C9 (≤134 ms cold r=64, ≤2 ms warm-cached).

Fixtures

signed_valid_r16.bin — expected: verify success. tampered_single_byte_tensor.bin — expected: ErrVerificationFailed, digest-tree mismatch localized to the tampered tensor's index entry. stripped_signature_envelope.bin — expected: treated as verification failure, not "unsigned, allow" (§8.8). replay_old_cert_chain.bin — a fixture using an expired Fulcio cert, expected: rejection with a distinguishable SynapseError from ordinary signature failure.

Pitfalls

Verifying the signature after partially reading tensor bytes into a working buffer (a TOCTOU regression against P4) rather than before any read. Treating a missing SignatureEnvelope as "legacy unsigned artifact, allow" instead of rejecting — this exact class of leniency is what made the 2024 pickle-hub incidents exploitable via unsigned/mistrusted uploads. Digest-tree computed over the wrong byte range (including trailing signature bytes in the hash input, making every future verify fail).

⬜ Phase 2 — Registry + Content-Addressed Blobs §14

Objectives

Stand up the registry's two halves — a PostgreSQL-backed index (ADR-05) and an OCI-distribution-compatible content-addressed blob store (ADR-04, ADR-16) — with per-blob deduplication (P8) and a publish path gated by nothing yet but signature validity (eval-gating arrives in Phase 7, §19).

Deliverable

registry-index service, registry-blobstore-gateway service, a blob GC tool, and a docker-compose stack wiring both plus PostgreSQL for local dev.

Acceptance

Pushing two artifacts sharing an identical tensor block results in exactly one stored blob (verified via blob-store object count, not just API success); index read-replica failover completes within C13's 5-minute RTO in a chaos drill; blob pull sustains ≥500 MB/s per node (C8) in a local benchmark.

Fixtures

push_duplicate_blob_pair.bin (two manifests sharing one tensor block) — expected: single blob stored, two index rows. push_unverified_artifact.bin — expected: publish rejection, artifact never reaches VERIFIED. gc_dangling_blob_reference.bin — expected: GC does not delete a blob still referenced by any manifest. replica_failover_drill — scripted chaos fixture, expected: index reachable within RTO.

Pitfalls

Reference counting blobs at manifest-delete time instead of at manifest-publish time, causing a race where a blob is GC'd while still mid-push from a second manifest. Treating the blob store as strongly consistent with the index without a transactional or two-phase confirm, risking an index row pointing at a blob that never finished uploading. OCI-spec pull path not handling partial/resumed pulls, forcing full re-pull on any network blip (hurts C8 in flaky-network conditions).

⬜ Phase 3 — Compatibility Resolver §15

Objectives

Implement the resolver service embodying §8.3's decision table as a queryable API returning a CompatibilityVerdict (§11) before any adapter load is attempted, satisfying P2 and I2/I6.

Deliverable

resolver service with a gRPC/HTTP API returning CompatibilityVerdict, a verdict cache layer, and a CLI wrapper (synapse-cli resolve) for manual debugging.

Acceptance

100% of §8.3's decision-table rows have a corresponding fixture (§15.5) producing the documented verdict; verdict cache invalidates within one polling interval (≤10 s) of an eval-score update; resolver P99 latency ≤5 ms against a warm registry index (excludes cold artifact-load latency, which is Phase 4's concern).

Fixtures

resolve_exact_match_accept.bin — expected: ACCEPT. resolve_module_superset_reject.bin — expected: REJECT, ErrModuleNotSubset (I2). resolve_tokenizer_warn.bin — expected: WARN_ACCEPT with I6 reason string. resolve_quant_mismatch_stub_reject.bin — expected: REJECT pending Phase 8. resolve_below_threshold_reject.bin — expected: REJECT with ErrEvalGateFailed.

Pitfalls

Caching a verdict without a TTL or invalidation hook, so a later-published eval score never propagates (violates I4's determinism-given-current-inputs framing — the plan must be deterministic given current digests, not stale ones). Evaluating architecture-family match by string comparison alone without also checking HiddenSize/NumLayers, letting two same-named-but-differently-shaped architectures falsely resolve as compatible.

⬜ Phase 4 — Single-Adapter Serving Runtime §16

Objectives

Bring up the Python/PyTorch serving runtime (ADR-06) that loads one resolved adapter onto a running base model without mutating base weights (P5, I3), applying the single-adapter merge equation of §8.4 at forward time.

Deliverable

synapse_runtime package with loader.py and a minimal forward-hook composition path; an end-to-end example (examples/single_adapter_serve.md) describing request flow without executable code.

Acceptance

Loading and serving one r=16 adapter adds ≤8% latency vs. base-only inference (C6); adapter swap (load a different CapabilityId, evict the prior one) completes within C5's p50 (1.3 ms) under warm-cache conditions; base model weight checksum (I3 detection) is unchanged after 1,000 consecutive adapter load/evict cycles in a soak-test fixture.

Fixtures

serve_single_adapter_r16.bin — expected: output matches a golden reference generation. swap_adapter_100_cycles.bin — expected: base-weight checksum stable across all 100 cycles (I3). load_unverified_pull.bin (simulated tampered registry response) — expected: loader re-verification catches it, ErrVerificationFailed, never reaches mmap. pool_ceiling_exceeded.bin — expected: ErrPoolExhausted before an OOM, LRU eviction triggered first if eligible.

Pitfalls

Trusting the registry pull as already-verified because Phase 2's publish gate checked it once, and skipping the loader's own re-verification — this reintroduces exactly the TOCTOU gap P4 exists to close, since a compromised blob-store replica could serve different bytes than what was originally verified. Writing the adapter delta directly into the base Linear.weight tensor "for speed," silently violating P5/I3 and corrupting subsequent requests that don't want this adapter. Forgetting alignment padding from Phase 0's byte layout when computing GPU tensor strides, producing numerically wrong (not crashing) matmuls.

⬜ Phase 5 — Multi-Adapter Batched Serving §17

Objectives

Extend the runtime to serve a batch of requests referencing heterogeneous CapabilityId sets and ranks concurrently, using SGMV batched kernels (ADR-07) to avoid the pad-to-max-rank waste identified in the vLLM/Punica reference implementations (§5). Satisfies the C7 throughput targets.

Deliverable

Batched SGMV kernel dispatch path, unified-paging pool manager, a load-test harness in benchmarks/ reproducing the C7 throughput curve at N=1/8/32 adapters.

Acceptance

Throughput at N=8 concurrent distinct adapters is within 2% of C7's 2,100 tok/s target; at N=32, within 2% of 1,750 tok/s; no cross-request output leakage across 1,000 randomized heterogeneous-batch fixture runs (§17.5); pool fragmentation after a 24-hour churn soak stays below a 10% wasted-page ratio.

Fixtures

batch_n8_heterogeneous_rank.bin (mix of r=8/16/64 adapters in one batch) — expected: throughput within C7 tolerance, per-request output matches single-adapter golden references. batch_isolation_leak_check.bin — expected: zero cross-request contamination detected via per-request output hashing. pool_churn_24h_soak.bin — expected: fragmentation ratio below threshold. cold_adapter_under_load_spike.bin — expected: backpressure signal returned, no scheduler stall.

Pitfalls

Padding all adapters in a batch to the maximum rank present "to simplify the kernel," silently reproducing the exact waste Punica's SGMV design exists to avoid (§5, vLLM pitfall) and missing the C7 throughput target. Heterogeneous-adapter batches serializing kernel dispatch per adapter instead of a true segmented gather, which looks correct in unit tests (small batches) but collapses throughput at scale. Unified-paging eviction interacting with skewed request popularity (the S-LoRA pitfall, §5) causing thrashing when a small number of adapters are extremely hot.

⬜ Phase 6 — Composition (Merge/Stack/Route) §18

Objectives

Implement the full CompositionPolicy (§11) space — STACK, MERGE, ROUTE — realizing §8.4's display equations as the composition engine, including TIES trimming and DARE dropout as MERGE-mode variants (ADR-10).

Deliverable

STACK/MERGE/ROUTE executors in synapse_runtime/composition/, a merge-math reference document showing worked numeric examples of each equation from §8.4.

Acceptance

STACK output for two non-conflicting adapters matches applying each independently in sequence within floating-point tolerance (1e-5 relative); MERGE (TIES) output on a 2-adapter conflict fixture shows measurably reduced interference vs. naive averaging, scored against a held-out benchmark; ROUTE selects the declared routing key's adapter with 100% accuracy across a 500-case fixture set.

Fixtures

stack_two_nonconflicting.bin — expected: matches sequential independent-apply golden reference. merge_ties_vs_naive_interference.bin — expected: TIES score strictly better than naive-average baseline on the fixture's held-out benchmark. merge_dare_dropout_rescale.bin — expected: rescaled deltas match the DARE equation's algebra within tolerance. route_key_selection_500cases.bin — expected: 100% correct routing. merge_vocab_mismatch_preflight_reject.bin — expected: rejection before any merge math runs (mergekit pitfall guard).

Pitfalls

Recomputing or defaulting α/r during a merge instead of reading each source's declared value (violates I13), silently rescaling the composite delta. Allowing STACK to silently reorder two adapters it judges "non-overlapping" based on a static module-name check that misses a runtime-only overlap (e.g., a shared low-level kernel buffer) — I7 requires the declared order be preserved verbatim regardless of the engine's own overlap analysis. Running TIES/DARE merge math on adapters with different tokenizer hashes without the mergekit-style preflight check, producing a shape-valid but semantically meaningless merged tensor.

⬜ Phase 7 — Eval Harness + Regression Gates §19

Objectives

Implement the evaluation harness that produces EvalReport (§11), gating registry publish per P12/I8 and feeding the resolver's eval-score check (§8.3, §15).

Deliverable

eval_harness package, a threshold-policy config format, CI wiring that blocks publish on gate failure, a regression-quarantine workflow.

Acceptance

100% of publish attempts with PassedThreshold = false are blocked (I8, zero exceptions in a 200-case fixture sweep); regression detection flags a synthetically injected 15%-benchmark-score drop with ≥95% statistical confidence within one CI run; bootstrap CI width narrows monotonically with benchmark sample size in a sanity fixture.

Fixtures

eval_pass_threshold.bin — expected: PUBLISHED transition allowed. eval_fail_threshold.bin — expected: publish blocked, artifact stays CANDIDATE. eval_regression_injected_15pct.bin — expected: QUARANTINED transition, regression flagged with CI. eval_no_score_recorded.bin — expected: resolver-visible REJECT per §15.8's edge case, not a passing default.

Pitfalls

Treating a single benchmark run's point estimate as sufficient without the bootstrap CI, letting benchmark noise masquerade as a real pass/fail signal (ADR-19's rationale exists specifically to avoid this). Gating only at initial publish and not re-running the harness on version bumps of an already-PUBLISHED capability, missing regressions entirely (this is precisely what the regression-detection mode in §19.2 closes). Threshold policy hardcoded into harness code, forcing a redeploy every time a benchmark bar changes and coupling unrelated release trains.

⬜ Phase 8 — Quantized-Base Support (QLoRA) §20

Objectives

Implement the quantization-scheme dimension of BaseModelFingerprint (§11) end to end — resolver promotion path, loader dtype handling, and serving numerics — for 4-bit NF4 quantized bases per QLoRA (Dettmers et al. 2023), closing the PhaseDeferred("§20 Phase 8 — Quantized-Base Support (QLoRA)") marker from §12 and §15/§17.

Deliverable

NF4 quantized-base loading path, resolver promotion-table config, dtype-promotion numerics fixture suite, updated merge-math reference doc (§18.3) covering the quantized case.

Acceptance

A QLoRA-trained r=16 adapter resolves ACCEPT against its declared NF4 base and REJECT against an undeclared-compatible fp16 base without an explicit promotion entry (P13); output distributional distance (KL divergence vs. an fp16 reference run) for a promoted-dtype path stays under a documented 0.02 threshold; adapter artifact size for a QLoRA adapter matches C1–C3 (adapter tensors are not quantized, only the base is, so sizes are unchanged).

Fixtures

qlora_nf4_base_accept.bin — expected: ACCEPT, correct dequant-before-merge path taken. qlora_undeclared_promotion_reject.bin — expected: REJECT per P13. qlora_kl_divergence_check.bin — expected: divergence under 0.02 threshold vs. fp16 reference. qlora_merge_and_freeze_requant.bin — expected: requantized merged output matches a golden NF4 reference within tolerance.

Pitfalls

Dtype promotion silently changing numerics — casting a 4-bit dequantized block up to bf16 using a different rounding mode than QLoRA's reference implementation used during training, producing outputs that "look plausible" but diverge measurably (exactly the class of bug §20.4's KL-divergence acceptance criterion exists to catch). Requantizing on every forward pass in the default non-merged path "to save memory," which both violates P5's default (base is never mutated/rewritten in place outside an explicit merge) and destroys performance. Treating quantization scheme as inferable from tensor dtype alone rather than the declared manifest field, breaking P13's "declared, not discovered" rule the moment a base is re-quantized with a different scheme but the same on-disk dtype tag.

⬜ Phase 9 — Cross-Architecture Distillation §21

Objectives

Implement the distillation pipeline producing a DistillationJob (§11) that ports a capability from a source architecture to a target BaseModelFingerprint, closing PhaseDeferred("§21 Phase 9 — Cross-Architecture Distillation") and satisfying P10/I12's provenance requirement.

Deliverable

distillation package, DistillationJob lifecycle implementation, an end-to-end example distilling a capability from a 7B source architecture to a differently architected target, gated through the standard eval harness.

Acceptance

A distilled artifact's EvalReport (§19) clears the same threshold policy applied to authored artifacts — no separate, lower bar; 100% of DistillationJob records reaching COMPLETE carry a non-null ResultCapability with a provenance link verifiable back to SourceCapability (I12); a fidelity regression (student score more than a documented margin below teacher score on the same benchmark) blocks the COMPLETE transition.

Fixtures

distill_cross_arch_complete.bin — expected: COMPLETE, provenance link verifiable. distill_missing_provenance_reject.bin — expected: publish blocked per I12. distill_fidelity_regression_block.bin — expected: job stays EVAL_PENDING / transitions FAILED, never COMPLETE. distill_same_arch_noop_reject.bin — expected: a same-architecture "distillation" request rejected as a misuse of the pipeline (the correct tool for same-architecture is composition, Phase 6, §18, not distillation).

Pitfalls

Folding a distilled artifact's version into its source's CapabilityId instead of minting a new one (violates P10, breaks fidelity traceability the moment the two diverge in quality). Skipping the eval harness for distilled artifacts under the assumption that "distillation is inherently lower stakes," silently shipping a lower-fidelity capability without the regression-gate protection authored artifacts get. Treating architecture porting as purely a tensor-shape-reshaping exercise (ignoring tokenizer/vocabulary differences between source and target architectures), producing a student adapter that trains but never converges to useful fidelity.

⬜ Phase 10 — Federated Bridge + Secure Aggregation §22

Objectives

Implement the federated bridge coordinating multi-party training rounds, requiring either secure aggregation (Bonawitz et al. 2017) or a DP-SGD privacy budget (Abadi et al. 2016) on every FederatedRound (§11), closing PhaseDeferred("§22 Phase 10 — Federated Bridge + Secure Aggregation") and satisfying P11/I11.

Deliverable

Federated coordinator service, secure-aggregation protocol implementation, DP-SGD budget accounting, an end-to-end example with ≥3 simulated participants.

Acceptance

100% of rounds missing both a SecureAggProof and a PrivacyBudget are rejected at ingestion (I11, zero exceptions across a 100-case fixture sweep); cumulative epsilon spend across a simulated 50-round sequence never exceeds the configured budget ceiling; the coordinator process never logs or persists an individual participant's raw update, verified by an audit-log content scan fixture.

Fixtures

fedround_no_privacy_reject.bin — expected: rejection per I11. fedround_secure_agg_valid.bin — expected: aggregation succeeds, coordinator log contains no per-participant plaintext update. fedround_dpsgd_budget_exhausted.bin — expected: round rejected once cumulative epsilon exceeds ceiling. fedround_malicious_participant_outlier.bin — expected: outlier update's influence bounded per the aggregation rule (ties into T7 in §24).

Pitfalls

Logging individual participant updates "temporarily for debugging" before secure aggregation completes, which defeats the entire privacy guarantee even if the production aggregation math is correct. Treating DP-SGD's epsilon budget as per-round rather than cumulative, silently allowing unbounded total privacy loss across many rounds (Kairouz et al. 2021's central open problem). Accepting a SecureAggProof without verifying it cryptographically (treating presence of the field as sufficient), which is equivalent to I11 not being enforced at all.

⬜ Phase 11 — Conformance + Performance Hardening §23

Objectives

Close the loop on cross-language conformance (Rust format/signer, Go registry/ resolver, Python runtime all agreeing on wire formats) and drive every §4 constraint and §30 performance target to a verified, harnessed pass (§16 harness, back-matter).

Deliverable

Full cross-language conformance suite, fuzz-target corpus wired into fuzz.yml CI, a completed performance-engineering pass with recorded benchmark history, a closed Deferred Features Register.

Acceptance

Cross-language conformance suite passes identically across Rust/Go/Python decoders for 100% of conformance/fixtures/; fuzz corpus runs 24 CPU-hours with zero new crashes or sanitizer findings; every C1–C15 (§4) measured value is within 10% of its target; every M1-series target (§30) is met or has a documented, approved deviation.

Fixtures

cross_lang_roundtrip_full_corpus.bin — expected: identical decode across all three language surfaces. fuzz_seed_corpus/ (directory, not a single file) — expected: 24-hour run, zero crashes. perf_full_constraint_remeasure.bin — expected: report matching §4 within tolerance, archived to benchmarks/. deferred_register_closure_check — expected: every register row (§37) either still correctly deferred or has its building-phase entry updated.

Pitfalls

Treating conformance as "the Rust tests pass" without actually exercising the Go and Python decoders against the identical byte-for-byte fixtures, missing exactly the drift class this phase exists to catch. Fuzzing only the happy-path parser entry point and never the signature-envelope or manifest-protobuf decoders, leaving the most security-sensitive parsing surfaces unfuzzed. Declaring a performance target "met" from a single benchmark run rather than the bootstrap-style statistical rigor established in Phase 7 (§19) for eval scoring — performance numbers deserve the same statistical discipline as eval scores.
