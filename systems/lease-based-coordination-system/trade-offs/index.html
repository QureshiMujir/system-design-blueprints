Decisions (§9) · 24 ADRs

ADR-01

Implementation language

Chosen

Python 3.12+

Rejected

Rust, Go, Java, C++

When the rejected choice is right

a production coordination service handling >100k grants/sec on a single node, where per-request CPU cost dominates and a compiled language's throughput ceiling is the binding constraint

Why: readability of the safety-critical state machine and guard-interval arithmetic outweighs raw throughput for a specification-grade reference implementation (§1)

ADR-02

Backing store consensus model

Chosen

pluggable ConsensusStore, Raft/Paxos-backed in production

Rejected

single-authority (no replication); Redlock-style quorum-of-independent-nodes

When the rejected choice is right

a single-node development/test deployment, or a lab environment where durability across coordinator crash is explicitly not required (Phase 0 stub)

Why: Raft/Paxos gives a proven single-committed-log guarantee (I6); Redlock's independent-timer model lacks that and is unsafe without fencing (§8.9)

ADR-03

Clock model

Chosen

bounded-skew NTP-disciplined wall clock, δ configurable

Rejected

TrueTime-style hardware-uncertainty interval; pure logical (Lamport) clocks

When the rejected choice is right

a deployment with GPS/atomic clock hardware available (e.g., a Spanner-adjacent environment), where a TrueTime-style interval model tightens δ substantially and is worth the hardware cost

Why: NTP-bounded skew is deployable on commodity hardware without atomic/GPS clocks (contrast Spanner); logical clocks cannot bound real-time expiry, which leases require by definition

ADR-04

Lease-duration / guard-interval policy

Chosen

per-resource configurable L, guard G derived from δ per §8.2 formula

Rejected

a single global fixed L for all resources

When the rejected choice is right

a small, homogeneous deployment where operational simplicity of one L outweighs per-resource tuning (early Phase 0/1 default)

Why: different resources have different failover-time tolerance (a leader-election lease can tolerate a longer failover than a hot lock) — one-size-fits-all wastes either safety margin or renewal budget

ADR-05

Fencing-token design

Chosen

monotonic per-resource counter, persisted high-water mark

Rejected

per-cluster global counter; term number reused from the backing consensus log

When the rejected choice is right

a deployment where the backing consensus log's term number is already exposed cheaply to every resource guard and a second counter is genuinely redundant (tight Raft-Consensus-sibling integration)

Why: per-resource counters avoid unnecessary cross-resource contention on a single shared counter and keep the invariant (I2) locally verifiable at each ResourceGuard

ADR-06

Leader election mechanism

Chosen

lease-based (this project's leader_election module)

Rejected

consensus-native (Raft's own leader with terms, no separate lease)

When the rejected choice is right

a deployment where the application is the consensus group itself and a separate election layer is pure overhead (Raft-Consensus sibling's own internal election)

Why: decouples application-level leadership from the backing consensus group's internal leader, so the two can fail over independently (§1 non-goals)

ADR-07

Lock semantics

Chosen

lease-bounded, bounded FIFO wait queue

Rejected

unbounded wait queue; no queue (fail-fast only)

When the rejected choice is right

an extremely low-contention deployment where queueing overhead is pure waste and fail-fast-only is simpler (embedded/edge use)

Why: bounded FIFO prevents unbounded memory growth under contention while preserving fairness (P11-adjacent operational concern)

ADR-08

Session model

Chosen

meta-lease covering N resource leases, cascading release on expiry (I7)

Rejected

per-resource independent heartbeats only (no session concept)

When the rejected choice is right

a client holding exactly one lease, where the session layer is pure indirection overhead (simple single-lock use case)

Why: amortizes heartbeat traffic for clients holding many leases (§8.6)

ADR-09

Renewal strategy

Chosen

client-initiated periodic renewal at L/3

Rejected

grantor-initiated push-based renewal offers

When the rejected choice is right

a deployment with untrusted or resource-constrained clients where the grantor should not depend on client-side timers at all (rare; not this project's target)

Why: client-initiated keeps the grantor stateless with respect to scheduling client behavior and matches Chubby/etcd/ZooKeeper precedent

ADR-10

Grace period policy

Chosen

disabled by default, operator-opt-in, no fencing-token bump on grace-period renewal

Rejected

always-on grace period; no grace period ever (strict cutoff only)

When the rejected choice is right

a deployment with known bursty renewal delay (e.g., an overloaded shared network) where operators explicitly accept the tradeoff to reduce spurious token churn

Why: strict-by-default aligns with P4 (prefer unavailability to unsafety); opt-in grace period is an audited convenience for operators who accept the tradeoff (§8.7)

ADR-11

Expiry detection

Chosen

grantor-side timer (Timer Wheel), never holder-side self-report

Rejected

holder-side self-expiry with grantor trusting the report

When the rejected choice is right

a single-process embedded deployment where holder and grantor are the same process reading one monotonic clock (the Phase-0 in-process stub, ADR-02, and the sim_harness fake-clock regime) — "self-report" is then the grantor's own reading and carries no cross-node skew term, so §8.2's δ collapses to 0

Why: P5: never trust the holder's self-assessment; a paused holder cannot self-report accurately by construction (§8.3)

ADR-12

Failure model

Chosen

crash-stop plus pause/GC-stall (bounded but unbounded-duration pause)

Rejected

crash-stop only (no pause modeling)

When the rejected choice is right

a deployment on a runtime with hard real-time guarantees and no GC (e.g., a no-GC embedded runtime) where pause duration is itself bounded and provably small relative to L

Why: the pause/GC-stall case is the one that actually breaks naive designs (§8.3, §8.9); ignoring it would reproduce the Redlock flaw

ADR-13

Split-brain prevention

Chosen

delegate primary defense to ConsensusStore's term/leader uniqueness, defend in depth with fencing

Rejected

fencing alone, no reliance on consensus term uniqueness

When the rejected choice is right

a deployment with a single-authority stub (ADR-02's Phase-0 case) where there is no consensus term to lean on and fencing is the only defense — explicitly the Phase-0/test regime

Why: defense in depth (§8.10); relying on fencing alone would require every downstream system to implement TokenChecker perfectly, which cannot be guaranteed

ADR-14

Resource-side token-check contract

Chosen

synchronous integer comparison, TokenChecker.check(token) -> Verdict

Rejected

asynchronous/best-effort token logging without hard rejection

When the rejected choice is right

a purely observational/audit deployment where the resource cannot be modified to reject (legacy integration) and only after-the-fact detection is achievable — explicitly a degraded mode, not the default

Why: the safety guarantee (I3) requires a hard, synchronous reject, not an after-the-fact log line

ADR-15

Timer-wheel design

Chosen

hashed timer wheel, O(1) amortized insert/cancel

Rejected

sorted heap (O(log n) insert/cancel)

When the rejected choice is right

a deployment with far fewer concurrent leases (<10k) where a heap's simplicity and exact-ordering guarantees outweigh the wheel's amortized-cost benefit

Why: at the target scale (§4, 1M concurrent leases) O(1) amortized materially reduces sweep cost per tick

ADR-16

Clock-skew monitoring + fail-safe

Chosen

continuous skew sampling against NTP/PTP reference, hard trip at δ, soft alarm at 0.8δ

Rejected

one-time startup check only

When the rejected choice is right

a short-lived batch job environment where the process lifetime is shorter than any realistic skew-drift window (not this project's deployment model)

Why: clock skew can drift during operation (VM migration, thermal drift, NTP daemon failure), so a startup-only check misses the exact failure class this project cares about

ADR-17

Logging

Chosen

structured JSON, one event per state transition

Rejected

unstructured plaintext logs

When the rejected choice is right

a very early prototype/spike phase where human-readable plaintext is faster to eyeball (pre-Phase-0 exploration only)

Why: every invariant's detection story (§7) depends on machine-parseable, correlatable events

ADR-18

Tracing

Chosen

OpenTelemetry spans across grant/renew/expire/fence-check

Rejected

no distributed tracing

When the rejected choice is right

a single-process, single-node Phase-0 stub where there is no cross-node path yet to trace

Why: reconstructing a cross-node timing bug (this project's entire bug class) without spans is impractical

ADR-19

Metrics

Chosen

Prometheus-style counters/histograms per §7/§26 named series

Rejected

ad hoc custom metrics format

When the rejected choice is right

an air-gapped or deeply embedded deployment with no scrape path to the coordination-service process, where the §7 series ride out as structured-log fields (ADR-17) parsed by the operator's existing in-house pipeline — adding a Prometheus exposition endpoint would cost a network listener the deployment deliberately does not have

Why: every invariant has a named Prometheus series by design (§7); a nonstandard format would break the alerting/dashboard tooling assumed in §26

ADR-20

Testing methodology

Chosen

deterministic simulation (fake clock, fake network) as the primary correctness gate

Rejected

real-network integration tests only

When the rejected choice is right

a final pre-release smoke-test pass where real-network conditions validate the deployment environment itself, complementary to but not replacing simulation

Why: real-network tests cannot reliably reproduce a specific clock-skew or pause schedule; determinism is required to reproduce the exact bugs this project is about (§7 debugging methodology)

ADR-21

Fuzzing

Chosen

structure-aware fuzzing of the wire-protocol decoders (grant/renew/revoke messages)

Rejected

no fuzzing

When the rejected choice is right

a purely in-process library-only deployment with no network-facing decoder at all (rare; not this project's default deployment)

Why: protocol decoders are the untrusted-input boundary; unfuzzed decoders are a known source of crash/DoS bugs

ADR-22

CI/CD

Chosen

GitHub Actions, gated on the Jepsen-style mutual-exclusion job (§28, §29)

Rejected

Jenkins; no fault-injection gate in CI

When the rejected choice is right

a resource-constrained solo-maintainer fork where periodic (nightly) fault-injection is accepted as a cost tradeoff instead of per-merge

Why: the mutual-exclusion-under-faults job is the project's primary correctness gate and must run on every merge, not just periodically

ADR-23

Packaging / release

Chosen

SemVer, signed wheels, SBOM per release

Rejected

date-based versioning, unsigned artifacts

When the rejected choice is right

the nightly/RC snapshot channel (§29), which makes no compatibility promise at all: a date-based tag (2026.08.08-nightly) conveys recency better than a SemVer number, the artifact stays inside the internal build cache, and trust is anchored at the container/registry signature (§29) rather than per wheel

Why: protocol/format compatibility guarantees (§27) require SemVer's explicit breaking-change signal; supply-chain trust requires signing (§24 T10)

ADR-24

Licensing

Chosen

Apache 2.0

Rejected

GPL-family copyleft, proprietary-only

When the rejected choice is right

a deployment where the maintaining organization requires copyleft to prevent proprietary forks (a governance choice orthogonal to this project's technical scope)

Why: permissive licensing matches the project's role as a reusable primitive library intended for embedding in other systems (§1)

36. Alternative Architectures (Roads Not Taken)

Four fundamentally different coordination architectures — not parameter tweaks on this project's design — each real, each rejected for a stated reason.

Alternative A — Failure-detector-based coordination (no wall clock, no lease). Liveness is a probabilistic suspicion level (Chandra & Toueg 1996 formalism), not a deadline.

node A --heartbeat--> node B --heartbeat--> node C
  ^                                            |
  +-----------------heartbeat------------------+
each node keeps a phi-accrual suspicion score per peer
score > threshold  =>  peer suspected down (probabilistic, revisable)
no grant, no expiry deadline, no fencing token issued anywhere

Regime where it wins: gossip-based membership/routing where approximate liveness for replica selection is enough and a hard mutual-exclusion proof is not the goal. Real system: Apache Cassandra's Phi Accrual Failure Detector (Hayashibara, Défago, Yared & Katayama 2004), also used by Akka Cluster. Rejected here because I1's guarantee must be provable, not probabilistic (P4, MM8) — a suspicion score can be revised; a lease expiry cannot un-happen.

Alternative B — Optimistic replication, no mutual exclusion at all. Concurrent writers proceed unfenced; conflicts are versioned and resolved after the fact.

writer1 --write(v1,vclock1)-->  R  <--write(v2,vclock2)-- writer2
                                 |
                          both versions stored as siblings
                                 |
                         reader/app merges vclock1, vclock2

Regime where it wins: highly-available, partition-tolerant key-value stores where write availability during a partition outweighs exclusivity, and merge logic is cheap (counters, sets). Real system: Amazon Dynamo (DeCandia et al. 2007, SOSP), whose vector clocks descend directly from Lamport's 1978 logical-clock lineage. Rejected here because this project's target use cases (leader election, mutual exclusion) have no meaningful "merge" of two simultaneous leaders or two holders of one lock — the domain requires exclusion, not reconciliation.

Alternative C — Quorum of independent timers, no shared log, no fencing.

client ---SET NX PX ttl---> Redis-1
client ---SET NX PX ttl---> Redis-2
client ---SET NX PX ttl---> Redis-3
       majority (>= N/2+1) acquired within validity window => "locked"
       each node's TTL is a local, independent timer; no consensus log; no token

Regime where it wins: environments already running Redis for caching that want a lock with zero new infrastructure and can tolerate best-effort exclusion. Real system: Redis Redlock (redis.io). Rejected here per §8.9: unsafe under process pause or clock jump because there is no fencing token to reject a stale holder's late write (Kleppmann's critique) — exactly the gap ADR-02 and ADR-05 close.

Alternative D — Fencing fused directly into a dedicated per-resource consensus group.

   +----------- Raft group for lock "R" (3-5 CP members) -----------+
   |  members replicate a tiny log whose commit index IS the fence  |
   |  acquire(R) = propose+commit "acquire" entry; fence = log index|
   +------------------------------------------------------------------+
one such group per lock/resource; no separate app-level Lease Manager,
no separate Fencing-Token Issuer — the consensus commit index is the token

Regime where it wins: deployments wanting linearizable locks with fencing baked in in one guarantee, willing to pay a dedicated consensus group per lock/resource rather than layering a lease abstraction over one shared store. Real system: Hazelcast CP Subsystem's FencedLock (Raft-based, getFence() returns a monotonic token). Rejected here per ADR-06 and P9: this project keeps the lease decision layer and the durability layer separable so any correct ConsensusStore can back it (§1, §11), and so leader-election, locks, and sessions can all reuse one fencing/clock-safety argument (§8) instead of re-deriving it inside N independent per-resource consensus groups.
