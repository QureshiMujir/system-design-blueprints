⬜ Phase 0 — Skeleton, Single-Authority Grant/Expire, and CI §12

Objectives

Stand up the repository skeleton (§10), the deterministic test harness (module 13), and a minimal single-authority (non-replicated) Lease grant/expire path sufficient to exercise LeaseState transitions end to end before any clock-safety or fencing machinery exists. This phase deliberately ships an unsafe-for-production lease (no guard interval derivation yet, no fencing) so later phases have a stable, testable base to layer safety onto incrementally.

Deliverable

A runnable, single-process lease service exposing grant() and an expiry sweep, backed by the single-authority ConsensusStore stub, with green CI and a deterministic-clock test suite.

Acceptance
  • 100% of LeaseState transitions in the Phase-0 subset (Free → Granted → Expired → Free) covered by unit tests under the fake clock.
  • Grant latency (single-process, no network) p99 < 1 ms — a numeric placeholder confirming the in-process path has no accidental blocking I/O, ahead of the real p99 target in §4.
  • Zero flaky tests across 100 CI runs (determinism check, ADR-20).
Fixtures
  • conformance/phase0/grant_then_expire.json — single grant, clock-advance past TTL, expect Expired.
  • conformance/phase0/grant_twice_rejected.json — second grant attempt on an already-Granted resource must fail with LeaseConflict (early I1 check, no clock-safety argument needed yet).
  • conformance/phase0/ci_matrix.yaml — the CI job definition fixture.
Pitfalls
  • Reaching for time.time() directly instead of the injected fake clock, silently reintroducing nondeterminism into "deterministic" tests.
  • Treating the single-authority stub's in-memory state as if it were already durable — it is not, and Phase 0 must not claim I6 compliance.
  • Skipping the Renewing state entirely for too long, making Phase 1's diff larger than necessary.

⬜ Phase 1 — The Lease State Machine and Renewal §13

Objectives

Complete the full §8.1 state machine, including Renewing, and implement renewal per P7/I5: identity-preserving, expiry-advancing-only.

Deliverable

A lease runtime where a held lease can be renewed indefinitely by its rightful owner without losing identity, and where renewal by a non-owner or a post-revocation renewal is deterministically rejected (I5, I8, P7).

Acceptance
  • Property test: for any sequence of renewals by the correct owner, lease_id and owner_id never change across the sequence (I5) — numeric gate: 10,000 randomized sequences, 0 violations.
  • Renewal latency p99 < 5 ms under the fake-clock/fake-network harness (early proxy for the real §4 target).
  • revoke_race_detected_total fires exactly once in the dedicated race fixture (below), never in the clean-path fixtures.
Fixtures
  • conformance/phase1/renew_by_owner.json
  • conformance/phase1/renew_by_wrong_owner_rejected.json
  • conformance/phase1/revoke_then_renew_race.json — renewal request queued before, applied after, a revoke commit; must be rejected (I8).
Pitfalls
  • Bumping generation on renewal by mistake, which would break I5 and cascade into fencing-token confusion once Phase 3 lands.
  • Allowing a Renewing-state lease to be granted to a new owner before the renewal outcome is resolved (a race that reintroduces I1 risk).
  • Forgetting to cancel the old Timer Wheel entry before scheduling the renewed one, leaking timer slots (I11-adjacent concern, though I11 is fully scoped in Phase 8).

⬜ Phase 2 — The Clock Model and the Guard-Interval Safety Argument §14

Objectives

Replace Phase 0/1's naive TTL-only expiry with the full clock-safety argument of §8.2: implement ClockMonitor, derive the guard interval from the configured clock-skew bound δ, and make expiry decisions guard-adjusted (I4) rather than raw-TTL-adjusted.

Deliverable

A lease runtime whose expiry timing is provably derived from a stated, documented clock-skew bound (Gray & Cheriton 1989; §8.2), with the guard-interval arithmetic exposed in telemetry for every grant/renew/expiry decision (P12).

Acceptance
  • Numeric: for δ = 200 ms, RTT_p99 = 20 ms, computed G must equal 420 ms before rounding and match the configured 500 ms operational default (§4, §8.2) — exact arithmetic assertion in a unit test.
  • Property test: under injected clock skew up to the configured δ (via fake-clock offset injection), guard_interval_margin_ms never goes negative across 10,000 randomized grant/renew/expiry sequences (I4) — 0 violations required.
  • Failover-time numeric gate: with L=10s default, observed grantor-side expiry occurs at grant + 9.3s ± 10 ms under the fake clock (§8.2 worked example).
Fixtures
  • conformance/phase2/skew_within_bound.json — skew injected up to exactly δ, expect safe operation.
  • conformance/phase2/skew_exceeds_bound.json — skew injected above δ, expect the soft-alarm telemetry to fire (hard trip deferred to Phase 9's fixture set).
  • conformance/phase2/guard_interval_arithmetic.json — the exact §8.2 worked-example numbers.
  • conformance/phase2/clock_jump_forward.json, conformance/phase2/clock_jump_backward.json — early clock-jump detection groundwork (full fail-safe response lands in Phase 9).
Pitfalls
  • Using the monotonic clock for cross-node skew comparison (a category error — monotonic clocks are only valid for local interval measurement, never cross-node comparison, ADR-03).
  • Computing G once at startup and never re-deriving it as δ's live estimate changes.
  • Off-by-one rounding in the guard-interval formula that silently narrows the safety margin below the documented 2δ + RTT_p99 floor.
  • Conflating the guard interval (safety margin) with the grace period (Phase 6/§8.7's convenience feature) — these are deliberately distinct mechanisms with opposite risk postures.

⬜ Phase 3 — Fencing Tokens and the Resource-Side Check §15

Objectives

Implement the Fencing-Token Issuer (I2) and the ResourceGuard/TokenChecker contract (I3), closing the pause/GC-stall safety hole that Phases 0-2 leave open, per the Kleppmann scenario worked in §8.3.

Deliverable

A fencing layer such that a stale leaseholder's write is rejected by any resource that implements TokenChecker, independent of whether the staleness came from a crash, a pause, or a partition (§8.10).

Acceptance
  • Numeric: 0 instances of fencing_token_regression_total across 50,000 randomized grant sequences including coordinator-restart injection (I2).
  • The exact §8.3 Kleppmann scenario reproduced as an automated test: paused holder's stale write (token N) is rejected after a new holder (token N+1) has already written — 100% rejection rate required, 0 tolerance.
  • fenced_write_rejected_total correctly attributes rejections to stale-token cause vs. other causes (no misclassification) in a dedicated classification fixture.
Fixtures
  • conformance/phase3/kleppmann_gc_pause_scenario.json — the full §8.3 worked example as an executable fixture (pause duration parametrized).
  • conformance/phase3/token_monotonic_across_restart.json — coordinator restart mid-sequence, token must not reset or regress.
  • conformance/phase3/unfenced_resource_warning.json — a resource that never calls TokenChecker produces an explicit client-library warning (defense against ADR-14's degraded mode being adopted silently).
Pitfalls
  • Implementing TokenChecker as advisory (log-only) instead of a hard reject, silently reintroducing the Redlock flaw (§8.9) at the resource boundary.
  • Forgetting to bump the token on leadership hand-off specifically (as opposed to only on generic resource grants), leaving Phase 4's leader-election path unfenced.
  • Persisting the high-water mark asynchronously (fire-and-forget) instead of committing it before the token is handed to the client, allowing a coordinator crash to hand out a duplicate token.
  • Treating highest_seen() as resettable — it must never reset, including across resource restarts, which requires resources to persist it too (a documented resource-integration requirement).

⬜ Phase 4 — Lease-Based Leader Election §16

Objectives

Build leader_election.py as a thin, named-election-specific layer over lease_manager.py, implementing the §8.4 sequence table and its uniqueness guarantee (I12).

Deliverable

A leader-election primitive such that, under the stated clock model (§8.2) and with fencing wired (Phase 3), at most one candidate is ever the fenced-effective leader at a time (I12), with observable failover bounded by L + G (§4, §34).

Acceptance
  • Numeric: dual-leader detection fires 0 times across 5,000 randomized campaign/crash/failover sequences under the fake-clock/fake-network harness (I12).
  • Failover-time numeric gate: leadership hand-off completes within L + G (default ≤ 10.5 s) in 99% of injected-crash trials.
  • resign() followed immediately by a competing campaign() never produces two simultaneously ACCEPT-verdict leaders against a shared ResourceGuard-protected downstream (ties to Phase 3).
Fixtures
  • conformance/phase4/single_leader_under_crash.json
  • conformance/phase4/voluntary_resign_handoff.json
  • conformance/phase4/dual_leader_attempt_blocked.json — a deliberately racing pair of campaigns.
  • conformance/phase4/observe_during_handoff.json — a follower's observe() call racing an in-flight hand-off must never return a torn/partial leadership record.
Pitfalls
  • Building leader election as a bespoke state machine parallel to Lease instead of a thin layer over it, duplicating (and risking divergence from) the §8.1 safety argument (violates P9, and contradicts ADR-06's explicit rationale).
  • Allowing observe() to read stale, uncommitted state, letting a follower briefly believe an old leader is still current past a hand-off.
  • Forgetting the fencing-token bump specifically on hand-off (as flagged in Phase 3 Pitfalls) — re-verified here as an integration regression test.

⬜ Phase 5 — Lease-Bounded Distributed Locks §17

Objectives

Generalize the lease/fencing machinery to arbitrary named resources with contention, implementing lock_module.py and the §8.5 sequence table, including the bounded FIFO wait queue (ADR-07).

Deliverable

A distributed lock primitive where a crashed holder's lock is reclaimed within L + G and handed to the next queued waiter with a correctly incremented fencing token, with no unbounded queue growth under sustained contention.

Acceptance
  • Numeric: queue never exceeds the configured bound across a 10,000-request contention-storm fixture; overflow requests receive an explicit rejection, never silent drop.
  • Mutual-exclusion-safety numeric gate: 0 violations of I1 across 10,000 randomized acquire/release/crash sequences with 2-20 concurrent contenders per resource.
  • Wait-time p99 under moderate contention (5 concurrent waiters) bounded by (queue_position) × (L + G) within a documented tolerance.
Fixtures
  • conformance/phase5/fifo_ordering_under_contention.json
  • conformance/phase5/queue_overflow_rejected.json
  • conformance/phase5/crash_holder_reclaimed_by_waiter.json — the full §8.5 sequence as an executable fixture.
  • conformance/phase5/release_races_expiry.json — voluntary release arriving at almost the same instant as the Timer Wheel's expiry sweep; must not double-grant.
Pitfalls
  • Implementing lock semantics as a copy-pasted variant of lease_manager.py instead of composing it, reintroducing exactly the duplication risk flagged in Phase 4's Pitfalls for leader election.
  • Allowing an unbounded wait queue "temporarily" for convenience, violating ADR-07 and P11's backpressure principle.
  • Popping the wait queue before confirming the prior holder's lease has actually committed to Expired (a race that could grant to two parties near-simultaneously).

⬜ Phase 6 — Sessions (Meta-Leases) §18

Objectives

Implement session_tracker.py per §8.6: a session as a lease whose expiry cascades to release every attached resource lease exactly once (I7), plus the opt-in grace-period policy of §8.7 (ADR-10).

Deliverable

A session abstraction letting one heartbeat cover many resource leases, with a proven-exactly-once cascading release on session death and zero orphaned locks left behind (I7).

Acceptance
  • Numeric: 0 instances of orphan_lease_after_session_expiry_total across 10,000 randomized session-expiry trials with 1-100 attached leases per session.
  • Session-expiry detection time numeric gate: ≤ heartbeat interval × missed-heartbeat threshold (§4: ≤ 6 s default) in 99.9% of trials.
  • Grace-period fixture: a renewal arriving inside the configured grace window is reattached without a token bump; one arriving outside it is treated as a full re-acquire with a fresh token — both behaviors verified explicitly and distinctly.
Fixtures
  • conformance/phase6/session_expiry_cascades_all_leases.json
  • conformance/phase6/orphan_scanner_backstop.json — a deliberately injected partial-cascade bug scenario the scanner must still catch.
  • conformance/phase6/grace_period_reattach.json
  • conformance/phase6/grace_period_disabled_by_default.json — confirms ADR-10's default posture.
Pitfalls
  • Implementing cascading release as a loop that can partially complete on crash, violating "exactly once" — must be structured so the orphan scanner can always complete an interrupted cascade idempotently.
  • Enabling the grace period by default "for convenience," silently reintroducing a sliver of the exact staleness ambiguity fencing tokens exist to remove (explicitly flagged against in §8.7 and ADR-10).
  • Treating session heartbeat loss and explicit session close as the same code path when their telemetry and operator-facing semantics should be distinguishable.

⬜ Phase 7 — Backing the Lease Store with Consensus (Durability) §19

Objectives

Replace the Phase 0-6 single-authority ConsensusStore stub with a real Raft/Paxos-backed implementation (ADR-02), closing the I6 durability gap: a coordinator crash or failover must never double-grant or roll back a fencing token.

Deliverable

A lease runtime durable across coordinator crash and failover, satisfying I6, with the exact single-writer-per-resource-key safety argument from Phases 0-6 now proven to survive the backing store's own leader changes (delegated correctness, ADR-02, but integration-tested here).

Acceptance
  • Numeric: 0 instances of post_failover_state_divergence_total across 500 controlled coordinator- failover drills.
  • RTO numeric gate: coordinator failover plus lease-store recovery completes within 2 minutes (§4) in 99% of drills.
  • Idempotent-retry fixture: a client retry after an ack-loss-but-actually-committed grant returns the original token, never a new one (I2 preserved across the retry).
Fixtures
  • conformance/phase7/failover_mid_grant_committed.json
  • conformance/phase7/failover_mid_grant_uncommitted.json — the two branches of §8.11's worked example, both as executable fixtures.
  • conformance/phase7/replay_reconstructs_fencing_highwater.json
  • conformance/phase7/idempotent_retry_after_ack_loss.json
Pitfalls
  • Applying replayed commands non-deterministically (e.g., depending on wall-clock time read at replay time rather than the timestamp embedded in the committed command), violating I6's implicit determinism requirement (echoes the general replay-determinism principle from consensus literature, Chandra/Griesemer/Redstone 2007).
  • Acking a grant to the client before the propose() call's commit actually returns, reintroducing exactly the ack-loss ambiguity the idempotent-retry design exists to handle.
  • Assuming the backing consensus store's own leader is the same entity as this project's application-level "leader" from Phase 4 (ADR-06 explicitly separates these).

⬜ Phase 8 — Pause/GC-Stall and Clock-Jump Fault Handling §20

Objectives

Systematically inject and defend against the two fault classes flagged as the hard cases throughout the document (P10, ADR-12): process pauses exceeding lease duration, and wall-clock jumps, beyond the single worked example already covered informally in Phase 3.

Deliverable

A verified, telemetry-rich confirmation that the project's existing fencing and clock-safety machinery (Phases 2-3) correctly survives arbitrary-duration pauses and instantaneous clock jumps, with no new safety gaps discovered.

Acceptance
  • Numeric: 0 mutual-exclusion-safety violations (I1) across 5,000 randomized trials with pause durations ranging from 0.5L to 10L and clock jumps of ±1s to ±60s.
  • Clock-jump detection latency numeric gate: detected within one skew-sampling interval (§14.2) after the jump occurs, in 99% of trials.
  • Fencing-rejection-to-pause-cause correlation: ≥ 99% of rejections during pause trials are correctly attributed to the injected pause in the audit telemetry (not misclassified).
Fixtures
  • conformance/phase8/gc_pause_0.5L_to_10L_sweep.json — a parametrized sweep, not a single point.
  • conformance/phase8/clock_jump_forward_60s.json, conformance/phase8/clock_jump_backward_60s.json
  • conformance/phase8/pause_during_leader_election.json — combines Phase 4's election path with the pause fault, confirming I12 holds under this fault class too.
  • conformance/phase8/pause_during_lock_hold.json — combines Phase 5's lock path similarly.
Pitfalls
  • Assuming "we already handled this in Phase 3" without actually re-running the full fixture suite against the newer leader-election and lock code paths added in Phases 4-5 — the fencing guarantee is general, but integration bugs are path-specific.
  • Conflating a clock jump with a skew-bound violation in telemetry, making post-incident forensics harder (they have different root causes and different runbooks, §26).
  • Under-sampling pause durations near the L boundary itself (neither clearly short nor clearly long), which is where guard-interval-margin edge cases are most likely to surface.

⬜ Phase 9 — Clock-Skew Monitoring and the Fail-Safe §21

Objectives

Complete the I9 fail-safe: wire the soft alarm (0.8δ) and hard trip (δ) built incrementally in Phases 2/8 into an actual cluster-wide grant/renewal refusal, per P4's "prefer unavailability to unsafety."

Deliverable

A fully wired fail-safe such that a genuine clock-skew-bound violation halts new grants/renewals cluster-wide before any unsafe decision can be made, with a clear, human-in-the-loop recovery path.

Acceptance
  • Numeric: 100% of injected skew-bound-violation trials (skew forced above δ) result in the fail-safe tripping before any subsequent grant/renew is accepted — 0 unsafe grants permitted during a tripped state, across 1,000 trials.
  • Trip-to-alarm latency numeric gate: soft alarm fires within one sampling interval of crossing 0.8δ; hard trip fires within one sampling interval of crossing δ.
  • Manual-clear fixture: a tripped fail-safe never auto-clears within a 24-hour simulated window absent explicit operator action.
Fixtures
  • conformance/phase9/softalarm_at_0.8delta.json
  • conformance/phase9/hardtrip_at_delta_blocks_all_grants.json
  • conformance/phase9/operator_ack_clears_trip.json
  • conformance/phase9/no_autoclear_regression.json
Pitfalls
  • Auto-clearing the trip once skew returns within bound, silently reintroducing risk if the skew source (e.g., a flapping NTP daemon) is intermittent rather than resolved.
  • Failing to distinguish "this node's clock is bad" from "the cluster's skew estimate is bad" in operator-facing diagnostics, making the runbook (§26) hard to follow under real incident pressure.
  • Gating only new grants but forgetting to gate renewals too, leaving a hole where already-held leases can still be extended unsafely during a tripped state.

⬜ Phase 10 — The Redlock Cautionary Comparison and Split-Brain Hardening §22

Objectives

Formally reproduce the Redlock debate (§8.9) as an executable comparison, and harden split-brain prevention (I13-adjacent defense-in-depth per ADR-13) beyond what the backing consensus store alone provides.

Deliverable

An executable, reproducible demonstration that this project's fenced lease design survives exactly the fault classes that make Redlock unsafe, plus verified defense-in-depth behavior under a hypothetical split-brain at the consensus layer itself.

Acceptance
  • Numeric: the Redlock-style harness reproduces ≥ 1 mutual-exclusion violation under the Kleppmann GC-pause schedule in 100% of trials (confirming the comparison harness is faithful to the known flaw, not accidentally safe).
  • Numeric: this project's Phase-3-fenced design reproduces 0 violations under the identical fault schedule in 100% of the same trials.
  • Split-brain-attempt fixture: 0 downstream safety violations across 1,000 forced-dual-coordinator trials, confirming fencing's defense-in-depth holds even when the primary consensus-level defense is hypothetically bypassed.
Fixtures
  • conformance/phase10/redlock_gc_pause_fails.json
  • conformance/phase10/redlock_clock_jump_fails.json
  • conformance/phase10/fenced_design_survives_identical_schedule.json
  • conformance/phase10/forced_dual_coordinator_fenced_safe.json
Pitfalls
  • Building the Redlock-style comparison harness sloppily such that it "accidentally" passes even the GC-pause scenario, undermining the entire pedagogical and validation point of Phase 10 — the harness's fidelity to the real Redlock design must itself be reviewed carefully.
  • Treating the split-brain-attempt fixture as testing the consensus layer's own correctness (it is not — that is delegated and out of scope, §1) rather than testing this project's fencing defense-in-depth specifically.
  • Shipping the Redlock-style comparison code in a way that could be mistaken for a supported alternative backend, contradicting ADR-02's locked choice.

⬜ Phase 11 — Jepsen-Style Verification, Chaos, and Performance Hardening §23

Objectives

Deliver the project's primary correctness gate: a Jepsen/Elle-style test that injects GC pauses, clock jumps, and partitions together (not in isolation, as in Phases 8-10) and asserts mutual exclusion is never violated and no un-fenced stale write ever succeeds, then harden performance to the §30 targets under chaos.

Deliverable

A CI-gating Jepsen-style verification harness that has been run against every fault class in Phases 8-10 in combination, plus a hardened, perf-validated cluster meeting the §30/§4 numeric targets under sustained chaos.

Acceptance
  • Numeric: 0 mutual-exclusion-safety violations (I1) and 0 un-fenced-stale-write successes across 100,000 combined-fault randomized trials (the project's single highest-volume correctness gate).
  • Numeric: perf-regression gate — grant/renew throughput and p50/p95/p99 latency (§4) within 10% of the targets table under a moderate concurrent-chaos background load.
  • Soak numeric gate: 7-day continuous run with 0 invariant violations and 0 unbounded resource growth (memory, queue depth, timer-wheel size).
Fixtures
  • conformance/phase11/combined_fault_jepsen_suite/ — a directory of seed-parametrized combined scenarios (pause + partition + clock-jump together), the project's largest fixture set.
  • conformance/phase11/differential_vs_etcd_lease_semantics.json
  • conformance/phase11/differential_vs_zookeeper_session_semantics.json
  • conformance/phase11/soak_7day_summary.json
  • conformance/phase11/perf_regression_baseline.json
Pitfalls
  • Running combined-fault trials with a fixed, small seed set, understating the true bug-discovery power of the harness relative to a genuinely broad randomized search.
  • Allowing the CI-gating run to be shortened under deadline pressure to the point it no longer meaningfully exercises the combined-fault space, quietly eroding the project's primary safety gate (a direct violation of ADR-22's rationale).
  • Treating a differential-testing mismatch against etcd/ZooKeeper as automatically "their bug" — divergence requires investigation to determine which system's documented semantics are actually correct for the scenario in question.
