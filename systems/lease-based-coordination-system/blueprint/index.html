Project Name: Lease-Based Coordination System

1. Goal & Scope

This project builds, from scratch in Python, the lease as a first-class distributed-systems primitive and the minimal coordination layer built directly on top of it: lease grant, renewal, expiry, and revocation; leader election in which the current leaseholder is by definition the leader; lease-bounded distributed locks that cannot deadlock the system when a holder crashes; monotonically increasing fencing tokens issued with every lease grant so that a stale leaseholder who does not yet know its lease has expired cannot corrupt a protected resource; a session abstraction (a lease that covers many resources under one heartbeat); and a thin adapter interface to a consensus-backed replicated store that durably persists lease state across a coordinator crash. The central engineering claim of the project, following Gray & Cheriton 1989, is that a lease converts the undecidable problem of detecting a remote crash (Fischer, Lynch & Paterson 1985) into the tractable, measurable problem of bounding clock drift: a crashed holder's lease simply elapses, so no perfect failure detector (Chandra & Toueg 1996) is required — only an explicit, published bound on clock skew and a guard interval that absorbs it. The correctness argument for every mechanism in this project — mutual exclusion, leader uniqueness, safe lock hand-off — reduces to that clock-skew bound. Fencing tokens (Burrows 2006; Kleppmann's critique of Redlock) exist because the clock-skew bound alone is insufficient in an asynchronous runtime where a process can pause (stop-the-world garbage collection, virtualization stalls, swap storms) for longer than its lease and then resume believing itself still valid; the token turns that latent unsafety into a cheap, resource-side integer comparison.

Phase-0 deliverable — the minimal end-to-end skeleton, expressed as a numbered module list that also fixes the vocabulary used throughout §3, §10, and §11:

  1. lease_core — the Lease value object and the LeaseState state machine (Free, Granted, Renewing, Expired, Revoked).
  2. clock_monitor — wall-clock and monotonic-clock sampling, skew estimation, the fail-safe trip.
  3. guard_interval — the derived safety margin from the configured clock-skew bound and RTT.
  4. fencing_issuer — the monotonic FencingToken/Term generator, one counter per resource.
  5. timer_wheel — the renewal/expiry scheduling structure (a classic hashed timer wheel).
  6. lease_manager — orchestrates grant/renew/expire/revoke against the ConsensusStore.
  7. leader_election — a thin layer over lease_manager for a single named "leadership" lease.
  8. lock_module — lease-bounded mutual-exclusion locks with a bounded wait queue.
  9. session_tracker — the meta-lease binding many resource leases to one heartbeat.
  10. consensus_store_stub — an in-process, single-authority ConsensusStore implementation used for Phase 0 and unit tests, standing in for the production Raft/Paxos-backed store.
  11. resource_guard — the TokenChecker contract a protected resource implements to reject stale fencing tokens.
  12. cli_admin — an inspection/administration command-line tool (list leases, force-revoke, inspect skew).
  13. deterministic_test_harness — a fake-clock, fake-network simulation harness used from Phase 0 onward for reproducible fault injection (GC pauses, clock jumps, partitions).

Boundaries. This project provides the lease abstraction, lease-bounded locks, and lease-based leader election as a client-usable library plus a small coordination service. It explicitly delegates the durable, replicated persistence of lease state to a pluggable ConsensusStore trait/interface — in production this is backed by a Raft or Paxos log (the sibling Raft-Consensus project, or an off-the-shelf consensus library); this project does not re-implement consensus.

Non-goals. (a) This is not Distributed-Lock-Service-96: that sibling project is a complete, deployable distributed lock service (wire protocol, multi-tenant namespaces, a hardened server); this project is the lease mechanism as a reusable primitive that a lock service, a leader election library, or a session manager can be built on top of — the two are complementary, not duplicates, and Distributed-Lock-Service-96 could in principle consume this project's lease_manager module. (b) This is not a from-scratch Raft or Paxos implementation — the Raft-Consensus sibling project owns log replication and leader election within a consensus group; this project's leader_election module elects an application-level leader via a lease, which is a different, higher-level notion of "leader" that happens to be layered over whatever consensus log backs the ConsensusStore. (c) Not a general key-value store: no arbitrary query surface, no secondary indexing, no blob storage, no OLTP transactions beyond the lease/lock/session state machine itself. (d) Not Byzantine-fault-tolerant: the threat model (§24) assumes crash-stop and pause/stall faults, not malicious consensus participants.

Clock-drift assumption, stated explicitly because it is the load-bearing assumption of the entire project: every node and client is assumed to run an NTP- (or PTP-) disciplined clock with a published, operator-configured maximum pairwise skew bound δ (default 200 ms; see §4, §9 ADR-03). Every safety argument in §8 depends on δ being true. If the true skew ever exceeds δ, mutual exclusion is not guaranteed and the system must fail safe: refuse further renewals, alarm immediately (§26), and prefer unavailability over an unsafe grant. The guard interval (§8.2) is the mechanism that converts this probabilistic clock assumption into a deterministic operational rule.

Deployment model: a small (3- or 5-node) coordination service exposing lease/lock/session RPCs, backed by a ConsensusStore (Raft/Paxos-backed in production), plus a client library that transparently attaches fencing tokens to protected-resource writes. Protected resources (databases, storage backends, external actuators) must implement the TokenChecker contract (§11) to gain the fencing guarantee; the guarantee is opt-in at the resource boundary by design — this project cannot force a downstream system to check a token it was never taught to check.

Users/operators: (a) platform operators run the coordination service cluster, own the clock policy, and respond to skew alarms; (b) application engineers consume the client library to build leader election, mutual exclusion, and session-scoped work claims; (c) resource owners implement TokenChecker on systems that must be protected from stale writers.

What later phases unlock: Phase 1 makes leases renewable and expirable (not just grant-once); Phase 2 turns the informal clock assumption into a proven guard-interval inequality; Phase 3 adds the fencing token, closing the pause/GC-stall safety hole that Phase 1–2 leave open; Phase 4 builds leader election on top of a stable lease; Phase 5 generalizes to general-purpose mutual exclusion (locks); Phase 6 generalizes further to sessions covering many resources; Phase 7 replaces the single-authority store with a real consensus-backed store; Phases 8–9 hunt down and close the fault classes (pauses, clock jumps, skew violations) that naive lease designs miss; Phase 10 confronts the Redlock debate head-on and hardens against split-brain; Phase 11 delivers the Jepsen-style verification harness that is the project's primary correctness gate.

Language: Python (3.12+). Rationale: the project's hard problem is not raw throughput — it is getting a subtle, timing-sensitive safety argument (§8) right and legible; Python's readability keeps the state machine, the guard-interval arithmetic, and the fencing check auditable line by line, which matters more here than in a throughput-bound consensus log; asyncio gives an adequate single-threaded event loop for the timer wheel and RPC surface without hand-rolled threading hazards; the dataclasses/typing/enum stdlib trio expresses the Lease state machine and error taxonomy (§11) precisely; the deterministic test harness (module 13) is far easier to build under a single-threaded cooperative scheduler, which Python's asyncio naturally provides; mature bindings exist for etcd, ZooKeeper, and Consul clients for the differential-testing gate (§28). Rejected alternatives:

Language Rejection Reason
Rust ownership/borrow-checker overhead is disproportionate for a specification-grade reference implementation whose goal is auditability of the safety argument, not zero-cost abstraction; slows iteration on the state-machine and guard-interval logic that changes every phase

Prerequisites: distributed systems fundamentals (replication, quorums, partitions); time and clocks (NTP/PTP, monotonic vs. wall-clock time, clock skew and drift); consensus (Paxos, Raft, the FLP impossibility result and why it matters); failure detectors (Chandra & Toueg 1996, unreliable failure detectors, why leases sidestep them); linearizability (Herlihy & Wing 1990).

Timeline: Phase 0 skeleton, 2 weeks. Phases 1–6 (the lease/lock/election/session core), 10 weeks. Phase 7 (consensus-backed durability), 3 weeks. Phases 8–10 (fault hardening, Redlock analysis, split-brain hardening), 6 weeks. Phase 11 (Jepsen-style verification harness, chaos, perf), 4 weeks. Total: approximately 25 weeks to a hardened v1.

2. Why Build This

Keyword bullets:

  • time-as-a-primitive engineering — trading failure detection for bounded clock measurement.
  • the fencing-token insight — closing the async-pause safety hole that naive leases leave open.
  • leader election without hand-rolling a consensus protocol.
  • lease-bounded mutual exclusion — locks that cannot deadlock forever on a crashed holder.
  • the guard-interval derivation — converting a probabilistic clock model into a hard deadline rule.
  • session design — amortizing many resource leases under one heartbeat.
  • the Redlock debate — a public, well-documented case study in getting distributed locking wrong.
  • Jepsen-style verification methodology for time-sensitive safety properties.
  • production coordination-service literacy: Chubby, ZooKeeper, etcd, Consul, Kubernetes lease-based leader election all rest on this exact primitive.

Historical importance: leases are the load-bearing idea underneath essentially every production coordination system in use today (Chubby, ZooKeeper's ephemeral nodes, etcd's lease package, Consul's sessions, Kubernetes' client-go leaderelection). Gray & Cheriton's 1989 paper predates all of them and derives the core safety argument this project re-derives in §8. Burrows' 2006 Chubby paper adds sequencers/fencing, arguably the single most consequential refinement to the original idea, and the one most often skipped by systems that later turn out to be unsafe (Redlock).

What Mastery Looks Like

  • Can derive the guard-interval inequality from a stated clock-skew bound and RTT, from memory, and explain why it bounds failover time (tied to Phase 2).
  • Can construct, on demand, the exact GC-pause scenario that breaks a fencing-token-less lease design and explain why the token check fixes it (tied to Phase 3).
  • Can implement lease-based leader election that is provably safe under the stated clock model and explain precisely where that safety argument would break if the model's assumptions were violated (tied to Phase 4).
  • Can explain, without notes, why Redlock is unsafe under combined clock-jump and process-pause faults and reproduce Kleppmann's counter-example (tied to Phase 10).
  • Can design and run a Jepsen-style fault-injection suite that would have caught the Redlock flaw, and interpret its output correctly (tied to Phase 11).
  • Can reason about the renewal-traffic-vs-failover-time tradeoff quantitatively for a given lease duration and cluster size (tied to §30, §34).

Client (lease holder). The application process that acquires, renews, and eventually releases a lease; it must attach the fencing token it currently holds to every write against a protected resource. It cannot be trusted to know, in real time, whether its lease has already expired (pause/GC-stall fault, §8.5) — this is precisely why the fencing token exists.

Lease Manager. The single logical owner of the Lease state machine (§8.1); it processes grant, renew, and revoke requests against the ConsensusStore and is the only component authorized to transition a Lease between states.

Fencing-Token Issuer. Hands out a strictly monotonically increasing token with every successful grant or leadership hand-off; never reuses or decrements a token; persists the high-water mark in the ConsensusStore so a coordinator crash cannot roll it back (I3).

Leader Election module. A thin, named-lease-specific layer over the Lease Manager: whoever holds the "leadership" lease for a given election name is the leader; leadership hand-off is exactly a lease grant to a new holder plus a fencing-token bump.

Lock module. Generalizes the same lease machinery to arbitrary named resources with a bounded FIFO wait queue, so a crashed lock holder's lease simply expires and the next waiter is granted the lock plus a fresh fencing token.

Session tracker. A meta-lease: one heartbeat/liveness signal covers a whole set of resource leases, so a client does not need one heartbeat per resource (Chubby's session model; ZooKeeper's ephemeral session).

Clock/Skew Monitor. Samples wall-clock and monotonic-clock offsets against the coordination service's own view of time (and, transitively, against NTP), maintains a live skew estimate, and trips a fail-safe (refuse renewals, page immediately) if the estimate exceeds the configured bound. This is the component that makes the clock-safety boundary in the diagram a checked, not merely assumed, boundary.

Timer Wheel. A hashed timer wheel scheduling renewal reminders and expiry sweeps in O(1) amortized insert/cancel, sized to the configured lease-count ceiling (§4).

Replicated Lease Store (ConsensusStore). The durable, replicated home for lease/session/fencing state; backed by Raft or Paxos in production (delegated, not reimplemented — §1); a coordinator crash and restart, or a coordinator failover, must not double-grant a lease or roll back a fencing token, which is why this state — and only this state — is required to be consensus-durable.

The lease-grant boundary (top half of the diagram) marks the point past which a request has been accepted into the lease/lock/election/session subsystem; the clock-safety boundary (lower half) marks the point past which every decision is provably bound to the configured clock-skew model — crossing it without passing through the Clock/Skew Monitor is a correctness bug by construction.

6. Design Principles

P1. A lease is a lock with a deadline, and the deadline is what makes it fault-tolerant — a crashed holder's lease simply expires, so no failure detector is needed, only bounded clock drift (Gray & Cheriton 1989).

P2. Fencing tokens make a stale leaseholder harmless: hand out a monotonically increasing token with each lease and have the protected resource reject any token below the highest it has seen, so an expired-but-unaware holder's writes are refused (Chubby; Kleppmann).

P3. The safety of leases rests entirely on a clock-skew bound plus a guard interval — a clock that drifts more than assumed breaks mutual exclusion, so the clock model IS the correctness argument, not an implementation detail of it.

P4. Prefer unavailability to unsafety: on skew-bound violation, refuse renewals rather than risk a double grant (I1, §24 T1).

P5. Never trust the holder's self-assessment of validity: the grantor's clock, not the holder's, determines expiry, and the grantor must consider a lease dead strictly before the holder could still believe it alive (I4).

P6. Monotonicity is non-negotiable: fencing tokens and terms only increase, across grants, across coordinator restarts, and across consensus-store recovery (I2).

P7. A renewal must never look, from the resource's point of view, different from the original grant except in expiry time — renewal preserves identity, advances only the deadline (I5).

P8. Sessions are leases of leases: a session's liveness is itself modeled as exactly the same grant/renew/expire state machine as a single resource lease, just fanned out to many dependents on expiry (P1 applied recursively).

P9. Separate the decision to grant/expire (Lease Manager, clock-boundary logic) from the decision to durably persist that fact (ConsensusStore) — the former is time-sensitive and single-writer per resource; the latter is a generic replicated log.

P10. The pause/GC-stall fault, not the crash fault, is the hard case: a crashed process cannot act; a paused-then-resumed process can, and only fencing (P2) — never a longer lease duration alone — closes that hole.

P11. A shorter lease duration buys faster failover and costs more renewal traffic; a longer lease duration buys the reverse — this tradeoff is explicit and tunable per resource, never hidden (§30, §34).

P12. Every clock-adjacent decision (grant, renew-accept, expire, guard-interval check) must emit telemetry sufficient to reconstruct, after the fact, exactly which clock reading drove it (§26).

P13. Consensus is a dependency, not a deliverable: the lease-safety argument must hold given any correct ConsensusStore implementation, single-authority or Raft/Paxos-backed, so the interface boundary (§11) is treated as inviolable.

P14. Redlock's mistake is treated as a first-class design input, not a footnote: any mechanism this project proposes that resembles a quorum-of-independent-timers-without-fencing must be rejected at the ADR stage (§9 ADR-02) unless fencing closes the gap.

8. Domain Model

8.1 The Lease State Machine

States: Free, Granted, Renewing, Expired, Revoked.

        grant(owner, ttl)
 Free ─────────────────────────► Granted ──renew(owner)──► Renewing
   ▲                                │  ▲                       │
   │        release(owner)          │  └───renew_ok────────────┘
   │        or expire-sweep         │
   │        or revoke(admin)        │ renew_fail / ttl_elapsed
   │                                ▼
   └──────────────────────────  Expired ──── revoke(admin) ───► Revoked
                                     │                              │
                                     └──── reacquire(new_owner) ────┘
                                              (only from Free/Expired,
                                               never from Granted/Renewing)

Failure edges: Granted → Expired (ttl elapsed with no successful renewal, detected by the Timer Wheel, I4); Renewing → Expired (a renewal request that arrives after the grantor has already declared expiry per I4's margin — the request is rejected, not applied, I8); Granted → Revoked (administrative or fail-safe-triggered revocation, I9); Expired → Free (after the guard interval elapses with no reacquire, the resource returns to the pool). A Revoked lease can never transition back to Granted directly — it must pass through Free and a fresh grant (I8).

8.2 The Clock-Safety Argument

Let δ be the configured maximum pairwise clock skew bound (§4, default 200 ms), L the lease duration, and G the guard interval. Let grant denote the grantor's wall-clock timestamp at grant time.

The holder, using its own (possibly skewed) clock, believes the lease valid until:

T_holder_valid_until = grant + L

The grantor, to be safe against a holder whose clock reads up to δ behind the grantor's, must declare the lease expired no later than:

T_grantor_expires_at = grant + L − δ − G

For the grantor's expiry decision to never precede a moment the holder could still legitimately believe valid — the entire point of I4 — the guard interval must absorb both the round-trip communication delay and the residual clock uncertainty:

G ≥ 2δ + RTT_p99

Worked example with the project defaults (δ = 200 ms, RTT_p99 = 20 ms, §4):

G ≥ 2(200 ms) + 20 ms = 420 ms   →   round up to G = 500 ms (§4 default)

With L = 10 s (default), the grantor treats the lease as expired at grant + 10s − 0.2s − 0.5s = grant + 9.3s, i.e. 700 ms before the holder's own clock would read grant + 10s. That 700 ms margin is the price of the stated clock-skew bound; failover time (§34) is bounded below by L − 0.7s plus the time to complete a new grant, and bounded above by L + G if the grantor waits the full guard interval before declaring expiry to a new claimant (defensive posture, §9 ADR-11).

8.3 Fencing Tokens — The Kleppmann Scenario, Worked

Named steps, following Kleppmann's canonical example:

  1. Client A acquires the lease on resource R with lease duration L = 10 s and fencing token 33.
  2. Client A begins a long write to R, then experiences a stop-the-world GC pause of 15 s (exceeds L, and exceeds L + G).
  3. While A is paused, the grantor's Timer Wheel expires A's lease at grant + 9.3s (per §8.2) and the resource is returned to Free.
  4. Client B acquires the lease on R, receiving fencing token 34 (I2: strictly greater than 33).
  5. B begins writing to R, tagging each write with token 34.
  6. Client A resumes from its GC pause, still believing (per its own clock, per §8.2's T_holder_valid_until) that its lease is valid, and issues its pending write to R tagged with its stale token 33.
  7. R's ResourceGuard (implementing TokenChecker) has already recorded 34 as the highest token seen (from step 5) and rejects A's write carrying token 33 (I3).
  8. Result: mutual exclusion is preserved despite the pause, because the token check — not the clock, not A's own self-assessment — is the final arbiter at the point of actual resource mutation. This is exactly the gap Redlock leaves open (§8.7, §36) and exactly what Chubby's sequencers close (Burrows 2006).

8.6 Session Model — The Meta-Lease

A session S is itself a Lease (state machine identical to §8.1) whose "resource" is the client's overall liveness rather than a single protected object; S maintains a set of attached resource leases {R1, R2, ..., Rn}. The session's own expiry (missed heartbeats past the threshold, §4) triggers cascading release of every Ri (I7), each following its own Granted → Expired transition independently but atomically with respect to the session's expiry event — no Ri may be observed still Granted after S has transitioned to Expired (extension of I1/I4 to the one-to-many case). This mirrors ZooKeeper's ephemeral-node-tied-to-session model and Chubby's session concept directly (Hunt et al. 2010; Burrows 2006).

8.7 Renewal and the Grace Period

Renewal request renew(owner, current_token) succeeds only if: (a) the lease is in Granted or Renewing state, (b) owner matches the current holder (I5), and (c) the request arrives before T_grantor_expires_at (§8.2). A grace period (distinct from the guard interval) may optionally extend a just-missed renewal — one arriving within a small operator-configured window after T_grantor_expires_at but before the resource has been re-granted — back to the same owner without a fencing-token bump, trading a small safety-adjacent convenience (avoiding unnecessary token churn under transient renewal delay) for slightly relaxed strictness; this is a named, ADR-governed policy choice (§9 ADR-10), off by default, because it reintroduces a sliver of the exact ambiguity fencing tokens exist to eliminate and is therefore treated as a deliberate, audited exception.

8.8 Interaction with the Consensus-Backed Store

Every state transition in §8.1 that is not purely a read (grant, renew-commit, expire-commit, revoke) is proposed as a command to the ConsensusStore and only takes effect once committed (quorum-acknowledged); the Lease Manager applies committed commands deterministically, exactly the same way regardless of which physical coordinator node originated them, so a coordinator failover mid-grant either commits (and the new coordinator observes the committed grant on replay) or never commits (and the client must retry) — there is no partially-applied state (I6).

8.9 The Redlock Cautionary Analysis

Redlock (a quorum of N independent Redis nodes, each an independent timer with no shared consensus log and, critically, no fencing token) is unsafe under two realistic faults it was not designed to survive: (a) a process pause between acquiring the lock and using the protected resource — the resumed, still-token-less process cannot be told apart from a legitimately valid holder by the resource, because there is no token to check (contrast §8.3 step 7, which does have a token to check); (b) a clock jump on any one of the N Redis nodes (NTP step correction, VM migration, manual clock set) can cause that node to believe a lock it already granted has expired far earlier or later than intended, and because Redlock's safety proof depends on every node's clock behaving monotonically and boundedly, a single misbehaving node can violate the majority argument. Kleppmann's critique (cited §5) formalizes both points; Antirez's rebuttal accepts the GC-pause point as valid for any lock without fencing (including this project's, absent §8.3) and argues clock jumps are an operational, not algorithmic, concern — this project resolves the debate operationally by (i) mandating fencing everywhere (§9 ADR-05, non-negotiable) and (ii) treating clock-jump detection as a first-class, alarmed invariant (I9) rather than an assumed-away operational nicety.

8.10 Malformed and Hard Examples

  • GC pause exceeding the lease: covered fully in §8.3; resolved by fencing, not by clock policy alone.
  • Clock jump (NTP step correction moves a node's wall clock backward or forward by seconds): the Clock/Skew Monitor's continuous skew estimate detects the discontinuity (a monotonic-clock vs. wall-clock divergence spike) and trips the I9 fail-safe before any grant decision uses the jumped clock reading.
  • Network partition isolating the leaseholder: the isolated holder cannot renew (no path to the ConsensusStore quorum side); its lease expires on schedule from the majority side; the isolated holder, even if it keeps acting, is fenced out the moment its writes reach a ResourceGuard that is reachable from the majority side (I3) — this is the same mechanism as §8.3, with "partition" substituted for "pause" as the root cause of the holder's stale self-belief.
  • A renewal racing expiry: resolved by I8 plus the strict ordering enforced by the ConsensusStore's single commit log — the renewal command and the expiry-commit command cannot both be accepted for the same lease generation; whichever commits first wins, and the loser is rejected deterministically on replay (no ambiguity survives past the commit point).
  • A token that goes backward: caught at issuance by I2's self-check before it ever reaches a client; if it were ever observed downstream (implying a bug elsewhere, e.g., a ConsensusStore rollback bug), it is caught at the ResourceGuard boundary by I3's core comparison regardless.
  • A split-brain attempt (two coordinators each believing themselves the current lease authority after a partition heals asymmetrically): prevented at the ConsensusStore layer by the backing consensus protocol's own term/leader uniqueness guarantee (delegated, §1), and defended in depth at the fencing layer (I3) even in the hypothetical case that the backing store's guarantee were violated.

8.11 A Failure-Path Example, End to End

Coordinator crashes mid-commit of a grant to client A for resource R (WAL entry proposed to ConsensusStore but not yet quorum-acknowledged to the original coordinator, though it may have already reached a quorum of replicas). On failover, the new coordinator's Lease Manager replays the ConsensusStore log: if the entry is present in the committed prefix, the grant is honored and A is informed (idempotently, on retry) that its grant succeeded with its original fencing token; if the entry never reached a quorum, it is absent from the committed prefix and the grant is treated as never having happened — A's retry produces a fresh grant with a new (higher) token per I2. In neither case does R end up with two simultaneously valid holders (I1), and in neither case does a token get reused or decremented (I2).

14. Phase 2 — The Clock Model and the Guard-Interval Safety Argument

14.1 Objectives

Replace Phase 0/1's naive TTL-only expiry with the full clock-safety argument of §8.2: implement ClockMonitor, derive the guard interval from the configured clock-skew bound δ, and make expiry decisions guard-adjusted (I4) rather than raw-TTL-adjusted.

14.2 Detailed Implementation Steps

  • Implement clock_monitor.py: continuous wall-clock-vs-reference skew sampling (ADR-16), applying the RFC 5905 NTP discipline assumption from §5.
  • Implement guard_interval.py computing G ≥ 2δ + RTT_p99 per the §8.2 formula and ADR-04's per-resource policy.
  • Change TimerWheel expiry scheduling to use grant + L − δ − G (I4) instead of raw grant + L.
  • Add the guard-interval-margin self-check (I4's Detection column) emitting guard_interval_margin_ms.
  • Add the soft alarm at 0.8δ and hard trip at δ (I9, ADR-16) — trip behavior itself (refusing grants cluster-wide) is fully wired in Phase 9; Phase 2 implements the measurement and threshold logic only.
  • Add configuration surface for per-resource L and derived G (ADR-04).

14.3 Deliverable

A lease runtime whose expiry timing is provably derived from a stated, documented clock-skew bound (Gray & Cheriton 1989; §8.2), with the guard-interval arithmetic exposed in telemetry for every grant/renew/expiry decision (P12).

14.4 Acceptance Criteria

  • Numeric: for δ = 200 ms, RTT_p99 = 20 ms, computed G must equal 420 ms before rounding and match the configured 500 ms operational default (§4, §8.2) — exact arithmetic assertion in a unit test.
  • Property test: under injected clock skew up to the configured δ (via fake-clock offset injection), guard_interval_margin_ms never goes negative across 10,000 randomized grant/renew/expiry sequences (I4) — 0 violations required.
  • Failover-time numeric gate: with L=10s default, observed grantor-side expiry occurs at grant + 9.3s ± 10 ms under the fake clock (§8.2 worked example).

14.5 Conformance Fixtures

  • conformance/phase2/skew_within_bound.json — skew injected up to exactly δ, expect safe operation.
  • conformance/phase2/skew_exceeds_bound.json — skew injected above δ, expect the soft-alarm telemetry to fire (hard trip deferred to Phase 9's fixture set).
  • conformance/phase2/guard_interval_arithmetic.json — the exact §8.2 worked-example numbers.
  • conformance/phase2/clock_jump_forward.json, conformance/phase2/clock_jump_backward.json — early clock-jump detection groundwork (full fail-safe response lands in Phase 9).

14.6 Pitfalls

  • Using the monotonic clock for cross-node skew comparison (a category error — monotonic clocks are only valid for local interval measurement, never cross-node comparison, ADR-03).
  • Computing G once at startup and never re-deriving it as δ's live estimate changes.
  • Off-by-one rounding in the guard-interval formula that silently narrows the safety margin below the documented 2δ + RTT_p99 floor.
  • Conflating the guard interval (safety margin) with the grace period (Phase 6/§8.7's convenience feature) — these are deliberately distinct mechanisms with opposite risk postures.

14.7 Performance Concerns

  • Continuous skew sampling must not itself become a bottleneck; sampling frequency is tuned to be much lower-cost than the grant/renew RPC path it protects.

14.8 Edge Cases

  • δ reconfigured (operator raises or lowers the bound) while leases are in flight — in-flight leases must use the G value in effect at their own grant time, never retroactively recomputed.
  • RTT_p99 spikes transiently (network congestion) without a true clock-skew change — must not be conflated with an actual skew violation in telemetry.

14.9 Failure Analysis

A guard-interval-margin violation (negative margin observed) is treated as a Sev-1 correctness bug, not an operational alert — it means the core safety argument's arithmetic itself has a bug, which is categorically different from an operational clock-skew violation (that is I9's concern, Phase 9).

14.10 Operational Notes

Expose clock_skew_estimate_ms and guard_interval_margin_ms as first-class dashboard metrics from this phase forward (they are the two numbers that most directly answer "is the safety argument currently holding").

15. Phase 3 — Fencing Tokens and the Resource-Side Check

15.1 Objectives

Implement the Fencing-Token Issuer (I2) and the ResourceGuard/TokenChecker contract (I3), closing the pause/GC-stall safety hole that Phases 0-2 leave open, per the Kleppmann scenario worked in §8.3.

15.2 Detailed Implementation Steps

  • Implement fencing_issuer.py: per-resource monotonic counter, persisted high-water mark via ConsensusStore.propose() (I2; still single-authority store at this phase, full consensus lands Phase 7).
  • Bump the fencing token on every successful grant and on every leadership/ownership hand-off; never on renewal (P7, mirrors the generation rule from Phase 1).
  • Implement resource_guard.py's TokenChecker.check() per the Verdict enum (§11): synchronous integer comparison against highest_seen() (ADR-14).
  • Add the token-regression self-check at issuance (I2's Detection column) and the ResourceGuard rejection counter (I3's Telemetry column).
  • Wire the client library so every fenced write call attaches the current FencingToken automatically (§1 deployment model, "opt-in at the resource boundary" caveat noted explicitly in client docs).

15.3 Deliverable

A fencing layer such that a stale leaseholder's write is rejected by any resource that implements TokenChecker, independent of whether the staleness came from a crash, a pause, or a partition (§8.10).

15.4 Acceptance Criteria

  • Numeric: 0 instances of fencing_token_regression_total across 50,000 randomized grant sequences including coordinator-restart injection (I2).
  • The exact §8.3 Kleppmann scenario reproduced as an automated test: paused holder's stale write (token N) is rejected after a new holder (token N+1) has already written — 100% rejection rate required, 0 tolerance.
  • fenced_write_rejected_total correctly attributes rejections to stale-token cause vs. other causes (no misclassification) in a dedicated classification fixture.

15.5 Conformance Fixtures

  • conformance/phase3/kleppmann_gc_pause_scenario.json — the full §8.3 worked example as an executable fixture (pause duration parametrized).
  • conformance/phase3/token_monotonic_across_restart.json — coordinator restart mid-sequence, token must not reset or regress.
  • conformance/phase3/unfenced_resource_warning.json — a resource that never calls TokenChecker produces an explicit client-library warning (defense against ADR-14's degraded mode being adopted silently).

15.6 Pitfalls

  • Implementing TokenChecker as advisory (log-only) instead of a hard reject, silently reintroducing the Redlock flaw (§8.9) at the resource boundary.
  • Forgetting to bump the token on leadership hand-off specifically (as opposed to only on generic resource grants), leaving Phase 4's leader-election path unfenced.
  • Persisting the high-water mark asynchronously (fire-and-forget) instead of committing it before the token is handed to the client, allowing a coordinator crash to hand out a duplicate token.
  • Treating highest_seen() as resettable — it must never reset, including across resource restarts, which requires resources to persist it too (a documented resource-integration requirement).

15.7 Performance Concerns

  • TokenChecker.check() must be O(1) — a single integer comparison — since it sits on every protected write's hot path; this is explicitly why ADR-14 chose synchronous comparison over any richer (and slower) verification scheme.

15.8 Edge Cases

  • Two grants racing for the same resource under the single-authority stub (pre-Phase-7 durability) — must still serialize correctly through the stub's single-writer property, deferring only the crash-durability guarantee (I6) to Phase 7.
  • A resource that restarts and loses its highest_seen() state (an integration bug, not a coordination-service bug) — documented explicitly as a resource-owner responsibility.
  • Token overflow at extreme scale (mitigated by using a 64-bit counter; the practical ceiling is documented in §34 and is not reachable within the project's stated lifetime assumptions).

15.9 Failure Analysis

Any observed fencing rejection is, by design, not a failure — it is the safety mechanism working (I3's Recovery column: "none needed — rejection IS the safety mechanism"). Failure analysis at this phase instead targets false negatives: a stale write that was not rejected, which would indicate either a TokenChecker integration bug at the resource or a token-issuance bug (I2) — both Sev-1.

15.10 Operational Notes

Add the docs/runbooks/fencing-rejection-investigation.md runbook (full content in §26): a rise in fenced_write_rejected_total is expected under normal failover and is not itself alarm-worthy; a sustained, high rate is a signal of either aggressive client retry behavior or an unexpectedly high churn rate on a given resource's lease.

  • Implementing lock semantics as a copy-pasted variant of lease_manager.py instead of composing it, reintroducing exactly the duplication risk flagged in Phase 4's Pitfalls for leader election.
  • Allowing an unbounded wait queue "temporarily" for convenience, violating ADR-07 and P11's backpressure principle.
  • Popping the wait queue before confirming the prior holder's lease has actually committed to Expired (a race that could grant to two parties near-simultaneously).

17.7 Performance Concerns

17.8 Edge Cases

  • A queued waiter cancels its own request before being granted — must be removable from the queue in O(1) without disturbing FIFO order for remaining waiters.
  • Every waiter times out (gives up) before contention resolves — queue must not leak stale entries.
  • A single client attempting to enqueue twice for the same resource — must be rejected or deduplicated per an explicit, documented policy (ADR-07 companion note).

17.9 Failure Analysis

A double-grant (two parties simultaneously holding a "granted" verdict for the same lock) is classified identically to an I1 violation (Phase 0-3's core safety property) — locks do not get a separate, weaker safety bar than leases in general, since a lock is a lease (P1).

17.10 Operational Notes

Dashboards: per-resource queue depth distribution, lock hold-time distribution, contention hot-spot identification (resources with sustained non-empty queues) for capacity-planning follow-up (§31).

18.6 Pitfalls

  • Implementing cascading release as a loop that can partially complete on crash, violating "exactly once" — must be structured so the orphan scanner can always complete an interrupted cascade idempotently.
  • Enabling the grace period by default "for convenience," silently reintroducing a sliver of the exact staleness ambiguity fencing tokens exist to remove (explicitly flagged against in §8.7 and ADR-10).
  • Treating session heartbeat loss and explicit session close as the same code path when their telemetry and operator-facing semantics should be distinguishable.

18.7 Performance Concerns

  • Cascading release of a session with a large attached_leases set must not block the Timer Wheel's processing of unrelated resources' expiry sweeps (isolate per-session cascade work).

18.8 Edge Cases

  • A session with zero attached leases expiring (must be a cheap no-op cascade).
  • A lease attached to two different sessions simultaneously (an explicit policy decision: rejected at attach time, documented as a hard constraint, not a silent last-writer-wins).
  • Heartbeat arriving in the same tick as the expiry sweep — resolved by the same commit-ordering argument used for the renew-vs-expiry race in Phase 1 (I8-adjacent).

18.9 Failure Analysis

An orphan-lease detection is treated as a Sev-2 (not Sev-1) bug — the scanner's backstop already resolves the safety-relevant consequence (the lease does get released), but the root cause (why did the atomic cascade not complete) still requires investigation and a fix.

18.10 Operational Notes

Dashboards: session count, average/percentile attached-lease-count per session, grace-period usage rate (if enabled) as an ongoing signal of whether the opt-in tradeoff is being relied upon more than intended.

19. Phase 7 — Backing the Lease Store with Consensus (Durability)

19.1 Objectives

Replace the Phase 0-6 single-authority ConsensusStore stub with a real Raft/Paxos-backed implementation (ADR-02), closing the I6 durability gap: a coordinator crash or failover must never double-grant or roll back a fencing token.

19.2 Detailed Implementation Steps

  • Implement consensus_store/raft_backed.py against the ConsensusStore protocol (§11), delegating actual log replication to the Raft-Consensus sibling project or an equivalent library (§1 non-goals; Ongaro & Ousterhout 2014).
  • Implement commit-before-ack semantics for every propose() call carrying a grant/renew/revoke/ fencing-issue command (I6).
  • Implement post-failover replay: on new-coordinator promotion, replay the committed log prefix and reconstruct in-memory Lease/Session/fencing high-water-mark state before accepting new requests (§8.11's worked failure path).
  • Implement the post-failover state-divergence audit (I6's Detection column): compare pre/post leaseholder sets across a controlled failover drill.
  • Add idempotent client retry semantics for grants that may have committed before an ack was lost (§8.11).

19.3 Deliverable

A lease runtime durable across coordinator crash and failover, satisfying I6, with the exact single-writer-per-resource-key safety argument from Phases 0-6 now proven to survive the backing store's own leader changes (delegated correctness, ADR-02, but integration-tested here).

19.4 Acceptance Criteria

  • Numeric: 0 instances of post_failover_state_divergence_total across 500 controlled coordinator- failover drills.
  • RTO numeric gate: coordinator failover plus lease-store recovery completes within 2 minutes (§4) in 99% of drills.
  • Idempotent-retry fixture: a client retry after an ack-loss-but-actually-committed grant returns the original token, never a new one (I2 preserved across the retry).

19.5 Conformance Fixtures

  • conformance/phase7/failover_mid_grant_committed.json
  • conformance/phase7/failover_mid_grant_uncommitted.json — the two branches of §8.11's worked example, both as executable fixtures.
  • conformance/phase7/replay_reconstructs_fencing_highwater.json
  • conformance/phase7/idempotent_retry_after_ack_loss.json

19.6 Pitfalls

  • Applying replayed commands non-deterministically (e.g., depending on wall-clock time read at replay time rather than the timestamp embedded in the committed command), violating I6's implicit determinism requirement (echoes the general replay-determinism principle from consensus literature, Chandra/Griesemer/Redstone 2007).
  • Acking a grant to the client before the propose() call's commit actually returns, reintroducing exactly the ack-loss ambiguity the idempotent-retry design exists to handle.
  • Assuming the backing consensus store's own leader is the same entity as this project's application-level "leader" from Phase 4 (ADR-06 explicitly separates these).

19.7 Performance Concerns

  • Consensus-round latency on the grant path (§4: p99 < 15 ms for a 3-node cluster) now dominates end-to-end grant latency; renewal traffic volume (§13.7, §31) directly drives write load on the consensus log — this is the tradeoff formalized in §34.

19.8 Edge Cases

  • A failover occurring while a Phase-6 session cascade is mid-flight — the cascade must be safely resumable from the replayed committed prefix, not restarted from scratch in a way that could double-release or miss a lease.
  • Simultaneous failover and clock-skew soft-alarm (Phase 2/9 overlap) — both mechanisms must degrade independently without interacting unsafely.
  • A minority-partitioned former coordinator that believes itself still leader — must be unable to commit anything (delegated to the consensus protocol's own term/leader safety, ADR-13).

19.9 Failure Analysis

A post-failover divergence is a Sev-1 correctness bug in either this project's replay logic or the backing consensus store's own guarantee; the debugging methodology (§7) applies directly: pull the committed log prefix, replay deterministically, compare against the observed divergent state.

19.10 Operational Notes

Add the docs/runbooks/failover.md runbook (full content §26); dashboards add consensus-round latency and commit-index lag as new first-class series alongside the lease-specific ones from earlier phases.

20. Phase 8 — Pause/GC-Stall and Clock-Jump Fault Handling

20.1 Objectives

Systematically inject and defend against the two fault classes flagged as the hard cases throughout the document (P10, ADR-12): process pauses exceeding lease duration, and wall-clock jumps, beyond the single worked example already covered informally in Phase 3.

20.2 Detailed Implementation Steps

  • Extend sim_harness/fake_clock.py with pause injection (freeze a simulated process's perceived time while global time advances) and clock-jump injection (step a node's wall clock forward or backward instantaneously).
  • Harden clock_monitor.py's skew estimator to distinguish a genuine clock jump from ordinary RTT jitter (I9's Detection column, ADR-16).
  • Verify, via the harness, that every pause scenario is already handled correctly purely by fencing (Phase 3) — Phase 8's job is verification and telemetry depth, not new safety machinery, per P10's claim that "only fencing... closes that hole."
  • Add pause-duration telemetry correlated with fencing-rejection telemetry, to make the causal chain (pause → stale token → rejection) auditable end to end (ties §7's debugging methodology to a concrete new fault class).
  • Add clock-jump detection to trigger the I9 soft alarm immediately, ahead of Phase 9's full fail-safe trip wiring.

20.3 Deliverable

A verified, telemetry-rich confirmation that the project's existing fencing and clock-safety machinery (Phases 2-3) correctly survives arbitrary-duration pauses and instantaneous clock jumps, with no new safety gaps discovered.

20.4 Acceptance Criteria

  • Numeric: 0 mutual-exclusion-safety violations (I1) across 5,000 randomized trials with pause durations ranging from 0.5L to 10L and clock jumps of ±1s to ±60s.
  • Clock-jump detection latency numeric gate: detected within one skew-sampling interval (§14.2) after the jump occurs, in 99% of trials.
  • Fencing-rejection-to-pause-cause correlation: ≥ 99% of rejections during pause trials are correctly attributed to the injected pause in the audit telemetry (not misclassified).

20.5 Conformance Fixtures

  • conformance/phase8/gc_pause_0.5L_to_10L_sweep.json — a parametrized sweep, not a single point.
  • conformance/phase8/clock_jump_forward_60s.json, conformance/phase8/clock_jump_backward_60s.json
  • conformance/phase8/pause_during_leader_election.json — combines Phase 4's election path with the pause fault, confirming I12 holds under this fault class too.
  • conformance/phase8/pause_during_lock_hold.json — combines Phase 5's lock path similarly.

20.6 Pitfalls

  • Assuming "we already handled this in Phase 3" without actually re-running the full fixture suite against the newer leader-election and lock code paths added in Phases 4-5 — the fencing guarantee is general, but integration bugs are path-specific.
  • Conflating a clock jump with a skew-bound violation in telemetry, making post-incident forensics harder (they have different root causes and different runbooks, §26).
  • Under-sampling pause durations near the L boundary itself (neither clearly short nor clearly long), which is where guard-interval-margin edge cases are most likely to surface.

20.7 Performance Concerns

  • Fault-injection trial volume (thousands of randomized sequences) must run fast enough under the deterministic simulation harness to be a practical CI gate, not just an offline research exercise — this concern is fully addressed by Phase 11's harness but must not regress starting here.

20.8 Edge Cases

  • A pause exactly equal to L − δ − G (the theoretical boundary from §8.2) — must resolve deterministically in one direction or the other, never flakily.
  • Two independent clock jumps on two different nodes within the same guard-interval window.
  • A pause that outlasts not just the lease but also the session's heartbeat threshold (Phase 6 interaction) — must trigger the correct cascading release, not a partial one.

20.9 Failure Analysis

Any safety violation discovered in this phase is treated as a regression against Phases 2-3's claimed guarantees, not a new, acceptable gap — per P10, the pause/GC-stall class was explicitly supposed to already be closed by fencing, so a violation here means the fencing implementation itself has a bug, not that a new mechanism is needed.

20.10 Operational Notes

Add docs/runbooks/clock-skew-violation-failsafe.md groundwork (finalized §26); dashboards begin tracking pause-duration distribution (inferred from fencing-rejection timing patterns) as an operational health signal distinct from raw skew.

21. Phase 9 — Clock-Skew Monitoring and the Fail-Safe

21.1 Objectives

Complete the I9 fail-safe: wire the soft alarm (0.8δ) and hard trip (δ) built incrementally in Phases 2/8 into an actual cluster-wide grant/renewal refusal, per P4's "prefer unavailability to unsafety."

21.2 Detailed Implementation Steps

  • Implement the cluster-wide fail-safe gate in lease_manager.py's entry point: every grant/renew call first checks ClockMonitor.is_within_bound() before proceeding (I9, ADR-16).
  • Implement operator-acknowledged clearing of a tripped fail-safe (I9's Recovery column) — explicitly not auto-clearing, to force a human to confirm the skew source has been addressed.
  • Implement the soft-alarm-to-hard-trip escalation path with distinct telemetry/paging severities (§26 alert philosophy preview: "a clock-skew exceeding the assumed bound is page-immediately").
  • Add a dedicated docs/runbooks/clock-skew-violation-failsafe.md runbook (finalized here, first drafted Phase 8).
  • Add skew-source diagnostic tooling to cli_admin (module 12): per-node skew breakdown to help operators localize which node's clock is misbehaving.

21.3 Deliverable

A fully wired fail-safe such that a genuine clock-skew-bound violation halts new grants/renewals cluster-wide before any unsafe decision can be made, with a clear, human-in-the-loop recovery path.

21.4 Acceptance Criteria

  • Numeric: 100% of injected skew-bound-violation trials (skew forced above δ) result in the fail-safe tripping before any subsequent grant/renew is accepted — 0 unsafe grants permitted during a tripped state, across 1,000 trials.
  • Trip-to-alarm latency numeric gate: soft alarm fires within one sampling interval of crossing 0.8δ; hard trip fires within one sampling interval of crossing δ.
  • Manual-clear fixture: a tripped fail-safe never auto-clears within a 24-hour simulated window absent explicit operator action.

21.5 Conformance Fixtures

  • conformance/phase9/softalarm_at_0.8delta.json
  • conformance/phase9/hardtrip_at_delta_blocks_all_grants.json
  • conformance/phase9/operator_ack_clears_trip.json
  • conformance/phase9/no_autoclear_regression.json

21.6 Pitfalls

  • Auto-clearing the trip once skew returns within bound, silently reintroducing risk if the skew source (e.g., a flapping NTP daemon) is intermittent rather than resolved.
  • Failing to distinguish "this node's clock is bad" from "the cluster's skew estimate is bad" in operator-facing diagnostics, making the runbook (§26) hard to follow under real incident pressure.
  • Gating only new grants but forgetting to gate renewals too, leaving a hole where already-held leases can still be extended unsafely during a tripped state.

21.7 Performance Concerns

  • The fail-safe gate check must be cheap (a boolean flag read) so it does not add meaningful latency to the hot grant/renew path during normal (untripped) operation.

21.8 Edge Cases

  • Skew crosses δ, then immediately drops back below it within one sampling interval (a transient spike) — must still trip, per P4's conservative posture, rather than debounce away a genuine (if brief) violation.
  • Multiple nodes independently detect skew violations at slightly different times — trip state must be a cluster-wide consensus-durable flag (via ConsensusStore), not a per-node-only flag, or a minority of nodes could keep granting unsafely.
  • Operator acknowledges and clears the trip while the underlying skew condition has not actually been fixed — accepted as an operator-error scenario the system cannot fully prevent, but the runbook explicitly warns against premature clearing.

21.9 Failure Analysis

An "unsafe grant during tripped state" finding (should be structurally impossible per 21.4) is treated as the single highest-severity bug class in the entire project, on par with an I1 violation directly, since it represents the fail-safe itself failing.

21.10 Operational Notes

The clock-skew-violation runbook is the single most safety-critical document in docs/runbooks/; its page-immediately alert tier (§26) is non-negotiable and must never be downgraded regardless of perceived incident fatigue.

  • Treating the split-brain-attempt fixture as testing the consensus layer's own correctness (it is not — that is delegated and out of scope, §1) rather than testing this project's fencing defense-in-depth specifically.

23. Phase 11 — Jepsen-Style Verification, Chaos, and Performance Hardening

23.1 Objectives

Deliver the project's primary correctness gate: a Jepsen/Elle-style test that injects GC pauses, clock jumps, and partitions together (not in isolation, as in Phases 8-10) and asserts mutual exclusion is never violated and no un-fenced stale write ever succeeds, then harden performance to the §30 targets under chaos.

23.2 Detailed Implementation Steps

  • Implement sim_harness/jepsen_style/ combining fake-clock pause/jump injection (Phase 8), fake-network partition injection, and the mutual-exclusion/fencing assertions (I1, I2, I3, I12) into one unified, randomized, seed-reproducible test generator.
  • Implement a linearizability/history-checker component (Herlihy & Wing 1990) that consumes the full operation history from a trial and verifies no two operations violate mutual exclusion.
  • Wire this harness as the primary CI gate (ADR-22): every merge must pass a bounded-time run; a longer nightly run explores a larger random-seed space.
  • Add differential testing against real etcd and ZooKeeper lease/session semantics (§28) to catch any divergence between this project's documented model and established production systems.
  • Run soak tests (multi-day continuous operation under moderate chaos) and perf-regression gating against the §30 targets table.

23.3 Deliverable

A CI-gating Jepsen-style verification harness that has been run against every fault class in Phases 8-10 in combination, plus a hardened, perf-validated cluster meeting the §30/§4 numeric targets under sustained chaos.

23.4 Acceptance Criteria

  • Numeric: 0 mutual-exclusion-safety violations (I1) and 0 un-fenced-stale-write successes across 100,000 combined-fault randomized trials (the project's single highest-volume correctness gate).
  • Numeric: perf-regression gate — grant/renew throughput and p50/p95/p99 latency (§4) within 10% of the targets table under a moderate concurrent-chaos background load.
  • Soak numeric gate: 7-day continuous run with 0 invariant violations and 0 unbounded resource growth (memory, queue depth, timer-wheel size).

23.5 Conformance Fixtures

  • conformance/phase11/combined_fault_jepsen_suite/ — a directory of seed-parametrized combined scenarios (pause + partition + clock-jump together), the project's largest fixture set.
  • conformance/phase11/differential_vs_etcd_lease_semantics.json
  • conformance/phase11/differential_vs_zookeeper_session_semantics.json
  • conformance/phase11/soak_7day_summary.json
  • conformance/phase11/perf_regression_baseline.json

23.6 Pitfalls

  • Running combined-fault trials with a fixed, small seed set, understating the true bug-discovery power of the harness relative to a genuinely broad randomized search.
  • Allowing the CI-gating run to be shortened under deadline pressure to the point it no longer meaningfully exercises the combined-fault space, quietly eroding the project's primary safety gate (a direct violation of ADR-22's rationale).
  • Treating a differential-testing mismatch against etcd/ZooKeeper as automatically "their bug" — divergence requires investigation to determine which system's documented semantics are actually correct for the scenario in question.

23.7 Performance Concerns

  • The harness itself (thousands to hundreds of thousands of simulated trials) must remain fast enough to run in CI within a practical time budget; achieving this without shortcuts is itself a deliverable-grade engineering problem (parallelizing independent trial seeds is the primary lever).

23.8 Edge Cases

  • A combined-fault trial where a pause, a clock jump, and a partition all begin and end within the same guard-interval window — the hardest single class of scenario the harness can generate, and explicitly weighted higher in the random-seed distribution.
  • A soak test that happens to never trigger a coordinator failover across 7 days (a coverage gap) — mitigated by deliberately scheduling at least one forced failover per soak run.

23.9 Failure Analysis

Any violation discovered by the Jepsen-style harness is, by construction, reproducible via its seed (determinism, ADR-20) — the failure-analysis procedure is simply "re-run with the recorded seed," making this phase's failures the fastest in the entire project to root-cause, by design.

23.10 Operational Notes

The combined-fault CI job's pass/fail status is treated as a release-blocking gate (§29); its historical trend (violations found per week during active development, trending to zero and staying there) is tracked as a project health metric distinct from any single release's status.

Backup & Restore

Durable state lives entirely in the ConsensusStore (delegated, ADR-02); backup is the backing Raft/Paxos library's own snapshot mechanism, taken at a cadence tighter than the log's truncation policy so RPO = 0 (§4) always holds. Restore replays the snapshot plus subsequent committed log exactly as §8.11/§19.2's failover replay does, generalized to a disaster-recovery scope (a restore is "a failover with a longer log to replay").

Deployment Topology

3-node (recommended) or 5-node (max, §4) coordination-service cluster per region, plus the client library embedded in application processes; each node runs Lease Manager, Clock/Skew Monitor, Timer Wheel, and Fencing-Token Issuer colocated, with ConsensusStore as the only cross-node dependency. The intra-region RTT_p99 = 20 ms assumption feeding the M6 guard-interval default (§8.2, §30) is a same-region topology constraint — a cross-region coordination-service cluster must re-derive G from its own, higher, measured RTT_p99 before deployment, never reuse the intra-region default (ADR-04).

Canary, Rolling Upgrade, Rollback, and Migration

Canary: roll a version/config change to a minority of coordination-service nodes first, gated on zero new Safety Invariants telemetry before proceeding — safe because a Raft/Paxos-backed cluster tolerates a minority running a different version under the rolling-upgrade guarantee (§27). Rollback: revert the binary; wire/storage backward compatibility (§27) guarantees no data loss on revert. Migration: any storage/wire change follows §27's additive-only rule; a breaking change gates on a major-version bump and the documented multi-step rolling migration (§27).

27. Compatibility & Versioning

Wire Format

Grant/renew/revoke/expiry messages are versioned protobuf/msgpack (§11's Lease "serialization" annotation generalizes to every wire type) carrying an explicit schema_version field; decoders (the T2/ADR-21 fuzz surface) accept unknown optional fields but reject messages missing a required field for their declared schema_version — bounded leniency, not implicit tolerance.

Storage Format

ConsensusStore commands are the same versioned wire messages proposed as log entries (§8.8); the committed log is append-only and immutable, so a storage-format bump cannot rewrite history — it requires the dual-version negotiation window described under Migration.

Schema Evolution

Rule Applies To Breaking?
New field, additive-only Lease, Session, Grant, Renew, Revoke, Expiry (§11) no — minor
Field removal or type change any §11 dataclass yes — major
Enum value addition LeaseState, Verdict (§11) no — minor, but unknown values must fail closed
Enum value removal/reinterpretation LeaseState, Verdict yes — major
Unknown enum value at decode any decoder raises SerializationFailure (never silently coerced, P4/T2)

API Stability

The LeaseManager, LeaderElection, Lock, ClockMonitor, TimerWheel, ConsensusStore, and ResourceGuard Protocols (§11) are the public surface. A signature change to any Protocol method is breaking (major); adding a new Protocol method is minor. Concrete internal modules (lease_core.py, clock_monitor.py, etc., §10) carry no cross-minor-version compatibility promise.

Migration

A breaking wire/storage change ships behind schema_version negotiation: each node advertises its highest supported version at cluster join; the cluster operates at the min-supported version across all members until every member upgrades (rolling upgrade), then a documented cutover step bumps the effective version cluster-wide — mirrors etcd's and ZooKeeper's own version-negotiation precedent (§5 Reference Implementations).

Deprecation Policy

A deprecated field/method is flagged in CHANGELOG.md and docs at version N.0, emits a runtime structured-log deprecation warning (ADR-17) during the deprecation window, and is removed no earlier than N+1.0 (a SemVer major bump).

SemVer Policy (ADR-23)

MAJOR = breaking wire/storage/API change. MINOR = additive field, new Protocol method, new ADR-governed optional policy. PATCH = bugfix, no schema/API change. Invariant IDs (I1–I12) and ADR IDs are never renumbered or redefined across any version — operator runbooks and dashboards (§26) key off these IDs directly, and an ID's meaning is a compatibility contract in its own right.

Client Compatibility

The client library degrades its request schema_version to match the server's advertised maximum at connection time (forward-compatible downgrade, never silent corruption); a client refuses to start against a server whose minimum supported version exceeds the client's own (hard fail, per P4's fail-closed posture, rather than sending a request the server cannot parse).

Rolling Upgrade Guarantees

A cluster must tolerate N-1/N mixed-version operation for the full upgrade window without violating I1, I2, or I6; mixed-version safety is itself a conformance fixture family (§28). Cluster-membership changes during the upgrade delegate to the backing consensus protocol's own membership-change mechanism (Ongaro & Ousterhout 2014, §5).

Named Bottlenecks, Priority Order

  1. ConsensusStore commit throughput — single replicated log, single-writer-per-resource-key serialization (P9); renewal traffic (grows with active-lease-count) is the dominant write load (§19.7); the backing log's p99 < 15 ms commit latency (M10) is a hard ceiling on aggregate grants+renewals/sec regardless of spare Lease Manager CPU.
  2. Timer Wheel tick loop — single-threaded (Python asyncio, §1 language rationale); at 1,000,000 concurrent leases (§4) this is the second bottleneck once consensus throughput is adequately provisioned; timer_wheel_tick_lag_ms (FM-7) is the leading indicator.
  3. Per-resource single-writer serialization (P9) — one extremely hot resource still serializes through one Lease Manager writer for that resource_key; sharding (below) parallelizes across resources but not within one hot resource.
  4. Cascading-release fan-out for large sessions — a session near the 100-lease ceiling (§4) makes expiry an O(100) burst; correlated mass session expiry (e.g., a fleet restart) is a distinct correlated-load spike, not steady state.
  5. Fencing-Token Issuer persistence write amplification — every issuance's high-water-mark persist is itself a ConsensusStore write (I2), doubling relevant commit traffic alongside the triggering grant/renewal commit unless batched.

Coordination Overhead

Every safety-relevant decision crosses the clock-safety boundary (§3) and commits through ConsensusStore (§8.8) — fixed per-operation overhead, not O(n) in cluster size beyond the quorum-size effect above, and irreducible below the consensus-round latency floor (M10). Horizontal scaling (adding shards) scales aggregate throughput linearly in shard count but does not lower any single shard's per-operation latency floor.

Practical Ceiling

One shard's aggregate grant+renewal ceiling is bounded by its 3-node consensus log's commit throughput at p99 < 15 ms/commit (M10). The stated 5,000 grants/sec + 50,000 renewals/sec sustained target (§4, M1/M2) is calibrated to sit under that ceiling with margin for the 10% chaos-load perf-regression tolerance (M13). Beyond roughly this point within one shard, added load either queues (pushing p95/p99 past the §4 targets) or must be sharded out.

Levers Beyond the Ceiling

  • Shard by resource_key across additional independent clusters (above) — the primary horizontal lever, no core-safety redesign required.
  • Lengthen L for resources that tolerate slower failover (P11) — directly cuts the dominant renewal-traffic bottleneck.
  • Batch the fencing-token high-water-mark persist with its triggering grant/renewal commit into one ConsensusStore proposal instead of two — a post-v1 optimization, not in the Phase 0–11 plan.
  • Swap the backing consensus implementation for one with a higher commit-throughput ceiling — the ConsensusStore interface (§11) makes this possible without touching the lease-safety argument (delegated boundary, ADR-02).
  • Increase node count only within the §4 ceiling (max 5) — beyond 5, quorum-latency growth works against throughput, not for it; node count is a fault-tolerance lever, not a scaling lever, and on-call must not reach for it when chasing throughput (§26).

MM3 Fencing turns an availability decision (when is it dead) into a safety decision (reject the stale write) — the two are independent and both must be right loosening δ or lengthening G buys safety margin without touching correctness; making the fencing check optional never can "we made the guard interval huge, so we don't need to fence" — still unsafe under an unbounded pause, since no finite guard interval is infinite §8.2, §8.3, I2, I3
MM4 Monotonic clocks measure local elapsed intervals; wall clocks compare instants across machines — conflating them reintroduces the exact skew problem leases exist to bound any code path feeding a monotonic reading into a cross-node comparison drifts subtly and only under load or after an NTP correction a "can't happen" clock-jump bug that only appears after a leap-second smear or VM live-migration, because local tests never exercised a wall-clock discontinuity §4, §14, §20
MM5 Grant and renewal are the same operation except for one bit — identity preservation — and conflating them breaks the invariant tied to that bit any refactor merging the renew/grant paths for "DRY" reasons reintroduces a token bump on renewal or an identity leak on grant unless the bit is enforced structurally token churn on every renewal, or worse, an identity hijack disguised as a routine renewal §8.1, §13, I5, ADR-05
MM6 Consensus durability (I6) and clock-boundary safety (I1/I4) are orthogonal, solved by different mechanisms; neither substitutes for the other hardening the backing store never fixes a skew-driven safety violation, and tightening the clock model never fixes a coordinator-crash data-loss bug "we upgraded the consensus backend, safety issues should be fixed now" — a category error leaving I4's clock gap untouched §8.8, §19, P9, P13
MM7 Every operational lever here trades failover time against renewal load (P11); there is no free improvement, only a chosen point on one curve fixed by §4's numbers "make failover faster without more renewal traffic" is asking to move off the curve, not along it, and needs a concrete new operating point plus its cost an operator shortens L cluster-wide to chase an SLO, then is surprised when renewal traffic saturates the consensus log P11, §30, §34
MM8 Unreliable failure detectors (Chandra & Toueg 1996) formalize exactly what a lease refuses to be — a probabilistic "is it alive" guess; a lease asks the decidable question "has enough time passed" instead any heuristic liveness signal added as a safety input, not a UX input, reintroduces the undecidability leases exist to avoid a "smarter" adaptive-timeout feature quietly makes expiry probabilistic again, undermining I1's provable guarantee §8.2, §36
MM9 A session is not a new primitive — it is §8.1's state machine applied recursively one fan-out level up (P8) session-specific bugs mirror lease-specific bugs one level up; §7's debugging methodology applies unchanged a bespoke session-expiry path that duplicates, then diverges from, lease-expiry logic — the same duplication risk P9/ADR-06 warn against for leader election §8.6, §18, P8

Kubernetes leaderelection's one differing decision: no separate lease-serving subsystem at all — the Lease API object is a plain versioned resource in the same etcd-backed store as everything else, and client-go is pure client-side polling/renewal logic. Redlock's one differing decision: achieve locking via a majority of independent, non-consensus timer nodes instead of a shared committed log. It wins where Redis is already deployed for caching and best-effort mutual exclusion (no hard safety proof) is acceptable — exactly the regime §8.9 and ADR-02 judge unsafe once fencing is required, which is why it appears here only as contrast.

34. Back-of-Envelope Capacity Model

Every figure below is derived, with the formula and substitution shown, chained from the §4 System Constraints table (or from a number that table itself already fixes, e.g. RTT_p99 used in §8.2).

C1 — Guard interval: G ≥ 2δ + RTT_p99. Substituting δ = 200 ms (§4), RTT_p99 = 20 ms (§8.2): G ≥ 2(200) + 20 = 420 ms, rounded up to the §4 operational default of 500 ms.

C2 — Failover-time ceiling: L + G. With defaults L = 10 s, G = 0.5 s (§4): 10 + 0.5 = 10.5 s, matching the §4/§16.4 ≤ 10.5 s target exactly.

C3 — Session-expiry detection ceiling: heartbeat_interval × missed_heartbeat_threshold. Defaults 2 s × 3 (§4): 2 × 3 = 6 s, matching the §4/§18.4 ≤ 6 s target.

C4 — Renewal traffic at max concurrency, default L: renewal_rate = N ÷ (L / 3). At N = 1,000,000 (§4 max concurrent leases), L = 10 s (§4 default): renewal_interval = 10/3 ≈ 3.33 s; renewal_rate = 1,000,000 ÷ 3.33 ≈ 300,000/s — six times over the §4 sustained-renewal target of 50,000/s. The max-concurrency ceiling and the default lease duration cannot both hold at full load.

C5 — Minimum average L to reconcile C4: solving renewal_rate = 3N / L for L at the target throughput: L_min = 3N ÷ renewal_target = 3(1,000,000) ÷ 50,000 = 60 s. Sustaining 1,000,000 concurrent leases inside the 50,000/s renewal budget needs an average L six times the 10 s default — a fact P11's tradeoff discussion must carry explicitly.

C6 — Fencing-issuance floor, additive check: grant_rate + renewal_hand-off_rate = 5,000/s (§4) + 50,000/s (§4) = 55,000/s, exactly matching the §4 stated ≥ 55,000 tokens/s floor — confirming the four §4 rows are mutually consistent.

C7 — Consensus in-flight concurrency (Little's Law, L = λW): λ ≈ 55,000/s (C6), W = 15 ms (§4 consensus-round p99, 3-node). in_flight ≈ 55,000 × 0.015 = 825. The backing ConsensusStore (§19) must sustain roughly 825 concurrent in-flight proposals at steady state to hold the stated p99.

C8 — Timer-wheel throughput requirement, chained from C4: every renewal reschedules its Timer Wheel entry (§13.2), so the wheel sustains ≈ 300,000 schedule+cancel ops/s at max concurrency under default L. At O(1) amortized per op (ADR-15) that is 300,000 constant-time ops/s; the rejected O(log n) sorted-heap alternative at n = 1,000,000 (log2(1,000,000) ≈ 20) costs ≈ 20× more comparison work per op — an effective 6,000,000 comparison-equivalents/s — quantifying ADR-15's rejection.

C9 — Session fan-out ceiling vs. flat lease ceiling: max_sessions × max_leases_per_session = 200,000 × 100 = 20,000,000 (§4) nominal attach-slots, twenty times the flat max-concurrent-leases ceiling of 1,000,000 (§4). The binding constraint on total addressable resource leases is the flat ceiling, never the session-fan-out product; §18/§31 capacity planning must size against it first.

C10 — RTO-driven minimum replay throughput: RTO < 2 min = 120 s (§4) covers coordinator failover and lease-store recovery together. At the max-concurrency ceiling of 1,000,000 leases (§4), a Phase-7 replay (§19.2) needs a minimum sustained replay-application rate of 1,000,000 ÷ 120 ≈ 8,334 records/s merely to stay inside the RTO budget, before any other recovery cost shares that same window.

35. Hard Questions (Self-Examination)

  1. If an operator raises δ to the §4 hard cap of 1 s without recomputing per-resource G, which invariant fails first — and does the Timer Wheel (§8.2, ADR-15) or the fail-safe (I9, §21) catch it before a client observes it?
  2. Given the renewal ceiling derived in §34 (C4/C5), is the §4 1,000,000-lease concurrency target actually reachable at the 10 s default L, or does ADR-04 silently assume operators lengthen L as they approach it — where in §26 would that assumption surface before it bites?
  3. §19 proves I6 durability assuming any correct ConsensusStore; §22 proves fencing defense-in-depth assuming the backing store's term uniqueness might be violated. Are these two assumptions consistent, or does §22's hypothetical undermine the delegation boundary of §1/ADR-02?
  4. ADR-10's grace period reattaches a renewal without a token bump; I2 requires strict monotonicity across grants. Does a grace-period reattach count as a grant for I2's purposes, and what in §8.7 and §11's Renew type distinguishes it from an ordinary renewal at the type level?
  5. §8.9 argues Redlock is unsafe purely for lacking a fencing token; §36 Alternative D fuses fencing into the consensus group itself. Given I2/I3 already close the pause hole per §8.3, what residual safety argument does §36 Alternative D actually buy over this project's layered design?
  6. §8.2's guard-interval formula assumes RTT_p99 = 20 ms, a number with no row of its own in §4. If true RTT_p99 degrades to 200 ms under congestion, does the system distinguish this from a skew violation (I9), and which §7/§26 telemetry series would actually tell the two apart?
  7. §21.8 requires the fail-safe trip to be a cluster-wide, consensus-durable flag, not per-node, so a minority cannot keep granting. Does the trip itself now depend on the same commit path (§19, I6) it might need to protect against during a skew-during-partition scenario — what stops the minority side from granting if the trip flag cannot commit?
  8. §34's C7 derives ≈ 825 required in-flight consensus proposals; §19.7 flags consensus-round latency as now dominating grant latency. At what combined throughput does the p99 < 60 ms grant target (§4) become mathematically incompatible with the p99 < 15 ms consensus-round target, and which §4 row would an operator relax first?
  9. I7 requires cascading release exactly once; §18.6 resolves partial-cascade-on-crash with an idempotent orphan scanner. If the scanner observes a lease mid-cascade during a §19.8 failover, how does it distinguish "legitimately in progress" from "abandoned by a crashed coordinator" without racing §19.2's own replay logic?
  10. ADR-06 decouples application leadership (§16) from the backing consensus group's own leader election; §36 Alternative D collapses that decoupling deliberately. At what cluster size or resource count does ADR-06's decoupling cost more in operational surface area than it buys in independent failover — when does its "when the rejected choice wins" column actually trigger?
  11. §8.10's split-brain defense relies on fencing (I3) even if consensus term uniqueness (ADR-13) is hypothetically violated. Is a violated consensus guarantee actually inside this project's stated threat model (crash-stop + pause, ADR-12, §1 non-goals), or is ADR-13 defending against a fault class §1 explicitly places out of scope?
  12. §15.6 warns against an advisory TokenChecker; ADR-14 nonetheless names exactly that as an accepted degraded mode. In a deployment mixing ADR-14 degraded-mode resources with mandatory I3 resources, does one degraded resource undermine I1's cluster-wide guarantee, or is the guarantee actually scoped per-resource in a way §7's table never makes explicit?
  13. §20 treats any pause/clock-jump violation as a Phases-2-3 regression, never a new gap; §23 runs the same faults combined. If a violation surfaces only under pause + clock-jump + partition together, does §20's regression framing still apply, or were Phases 2-3's guarantees only ever proven per fault class in isolation?
  14. §33 shows etcd's concurrency.NewMutex permits skipping the revision check silently — the exact pitfall §5 flags for etcd. Given §15.2 already auto-attaches the current token to every fenced write, why does the client library not simply refuse to compile/run a token-omitting write, and what would that require changing in §11's ResourceGuard contract?
  15. §34's C9 shows the session fan-out product is never the binding constraint — the flat lease ceiling is. Does §18's "up to 100 leases per session" figure in §4 do any real work, or is it vestigial, and would a future ceiling increase (§37) need the per-session cap to move with it to keep C9's finding true?
  16. §21.8 requires the trip to fire on a transient skew spike that drops back within one sampling interval; §14.8 separately requires RTT spikes to not be conflated with true skew, on the same underlying sample path. Is that distinction falsifiable from the raw samples §14.2 collects, or only from a derived signal §7's telemetry table does not yet name?
  17. ADR-15's O(1)-vs-O(log n) argument is quantified in §34's C8 for the Timer Wheel; §17.7 requires the lock module's wait-queue pop to also be O(1). Do both share one data structure, or does the lock module maintain a separate FIFO whose O(1) guarantee could degrade under cancellation churn (§17.8) without I11 catching it?
  18. §22's Redlock-style harness is explicitly never shipped to production; §36 discusses Redlock as a rejected architecture. Does §22 test the same claim as §36, or only the narrower one (fencing beats no-fencing under one schedule) versus §36's broader generalization (consensus-log beats independent-timer design) — could a Redlock defender accept §22 while rejecting §36?
  19. §5 lists Herlihy & Wing 1990 as applied in both §7 and §28; §16.2's observe() is built as a linearizable read specifically to avoid a stale-leader window. Does §23.2's Jepsen-style history checker actually verify observe()'s linearizability, or only I1/I2/I3 on the grant/fence path — and if only the latter, is §16.2's claim verified anywhere in this document's test plan?
  20. §1 calls the clock-drift assumption load-bearing and requires fail-safe on violation (§21); the Clock/Skew Monitor can only detect skew relative to its own reference. If the NTP/PTP reference itself (§5, RFC 5905) is uniformly wrong on every node in the same direction, does the relative skew estimate ever detect this, and is "fail safe on skew violation" a complete implementation of §1's assumption or only of its relative half?

36. Alternative Architectures (Roads Not Taken)

Four fundamentally different coordination architectures — not parameter tweaks on this project's design — each real, each rejected for a stated reason.

Alternative A — Failure-detector-based coordination (no wall clock, no lease). Liveness is a probabilistic suspicion level (Chandra & Toueg 1996 formalism), not a deadline.

node A --heartbeat--> node B --heartbeat--> node C
  ^                                            |
  +-----------------heartbeat------------------+
each node keeps a phi-accrual suspicion score per peer
score > threshold  =>  peer suspected down (probabilistic, revisable)
no grant, no expiry deadline, no fencing token issued anywhere

Regime where it wins: gossip-based membership/routing where approximate liveness for replica selection is enough and a hard mutual-exclusion proof is not the goal. Real system: Apache Cassandra's Phi Accrual Failure Detector (Hayashibara, Défago, Yared & Katayama 2004), also used by Akka Cluster. Rejected here because I1's guarantee must be provable, not probabilistic (P4, MM8) — a suspicion score can be revised; a lease expiry cannot un-happen.

Alternative B — Optimistic replication, no mutual exclusion at all. Concurrent writers proceed unfenced; conflicts are versioned and resolved after the fact.

writer1 --write(v1,vclock1)-->  R  <--write(v2,vclock2)-- writer2
                                 |
                          both versions stored as siblings
                                 |
                         reader/app merges vclock1, vclock2

Regime where it wins: highly-available, partition-tolerant key-value stores where write availability during a partition outweighs exclusivity, and merge logic is cheap (counters, sets). Real system: Amazon Dynamo (DeCandia et al. 2007, SOSP), whose vector clocks descend directly from Lamport's 1978 logical-clock lineage. Rejected here because this project's target use cases (leader election, mutual exclusion) have no meaningful "merge" of two simultaneous leaders or two holders of one lock — the domain requires exclusion, not reconciliation.

Alternative C — Quorum of independent timers, no shared log, no fencing.

client ---SET NX PX ttl---> Redis-1
client ---SET NX PX ttl---> Redis-2
client ---SET NX PX ttl---> Redis-3
       majority (>= N/2+1) acquired within validity window => "locked"
       each node's TTL is a local, independent timer; no consensus log; no token

Regime where it wins: environments already running Redis for caching that want a lock with zero new infrastructure and can tolerate best-effort exclusion. Real system: Redis Redlock (redis.io). Rejected here per §8.9: unsafe under process pause or clock jump because there is no fencing token to reject a stale holder's late write (Kleppmann's critique) — exactly the gap ADR-02 and ADR-05 close.

Alternative D — Fencing fused directly into a dedicated per-resource consensus group.

   +----------- Raft group for lock "R" (3-5 CP members) -----------+
   |  members replicate a tiny log whose commit index IS the fence  |
   |  acquire(R) = propose+commit "acquire" entry; fence = log index|
   +------------------------------------------------------------------+
one such group per lock/resource; no separate app-level Lease Manager,
no separate Fencing-Token Issuer — the consensus commit index is the token

Regime where it wins: deployments wanting linearizable locks with fencing baked in in one guarantee, willing to pay a dedicated consensus group per lock/resource rather than layering a lease abstraction over one shared store. Real system: Hazelcast CP Subsystem's FencedLock (Raft-based, getFence() returns a monotonic token). Rejected here per ADR-06 and P9: this project keeps the lease decision layer and the durability layer separable so any correct ConsensusStore can back it (§1, §11), and so leader-election, locks, and sessions can all reuse one fencing/clock-safety argument (§8) instead of re-deriving it inside N independent per-resource consensus groups.

38. Glossary

Lease — a time-bounded grant of exclusive validity over a resource, expiring by clock rather than by explicit failure detection (P1, §8.1).

Lease Duration (L) — the configured validity window of a lease from grant to nominal expiry (§4, ADR-04).

Guard Interval (G) — the safety margin subtracted from nominal expiry to absorb clock skew and RTT before the grantor declares a lease dead (§8.2, I4).

Clock-Skew Bound (δ) — the operator-published maximum pairwise clock difference the entire safety argument assumes holds (§1, §4).

Fencing Token — a strictly monotonically increasing integer issued with every grant/hand-off, used by protected resources to reject stale writers (I2, Burrows 2006).

Generation — the counter bumped on every grant, never on renewal, distinguishing successive holders of the same resource_key (§11, I5).

Term — the alias domain for election/consensus epoch numbers, structurally identical to a fencing token (§11).

ResourceGuard / TokenChecker — the contract a protected resource implements to synchronously reject any operation carrying a stale fencing token (I3, §11).

Verdict — the two-valued outcome (ACCEPT / REJECT_STALE_TOKEN) of a TokenChecker.check() call (§11).

Lease Manager — the single logical owner of the Lease state machine; the only component authorized to transition its state (§3, §11).

Clock/Skew Monitor — the component continuously sampling wall-clock skew and tripping the fail-safe on violation (§3, I9).

Timer Wheel — the hashed, O(1)-amortized structure scheduling renewal reminders and expiry sweeps (ADR-15, I11).

ConsensusStore — the pluggable, delegated durability interface backing lease/session/fencing state (§11, ADR-02).

Single-Authority Store — the non-replicated Phase-0 ConsensusStore stub used before Phase 7's real consensus backing lands (§12, ADR-02).

Commit-Before-Ack — the rule that a client is never told a request succeeded until the backing store has durably committed it (I6, §19).

High-Water Mark — the persisted highest fencing token issued for a resource; must never regress, even across a coordinator crash (I2).

Post-Failover Replay — reconstructing in-memory lease/session/fencing state from the committed consensus log after a new coordinator is promoted (§19.2, §8.11).

Session — a meta-lease whose "resource" is a client's overall liveness, covering a set of attached resource leases under one heartbeat (§8.6, I7).

Cascading Release — the atomic, exactly-once release of every lease attached to a session at the moment the session itself expires (I7, §18).

Orphan-Lease Scanner — the backstop process that force-releases any resource lease left Granted after its owning session has already expired (I7).

Grace Period — an optional, off-by-default window after nominal expiry in which a just-missed renewal reattaches to the same owner without a token bump (§8.7, ADR-10).

Leader Election — the thin layer over the Lease Manager whereby holding the "leadership" lease for a named election defines being the leader (§8.4, ADR-06).

Leadership — the return value of a winning campaign() call: election name, leader id, fencing token, and underlying lease (§11).

Fail-Safe Trip — the cluster-wide, consensus-durable refusal of new grants/renewals triggered when measured skew exceeds δ (I9, §21).

Soft Alarm — the early-warning telemetry event fired at 0.8δ, ahead of the hard trip at δ (§4, ADR-16).

Hard Trip — the grant/renewal-refusing fail-safe activation at δ, requiring operator acknowledgment to clear (I9, §21).

Guard-Interval Margin — the live per-decision self-check value that must never go negative, confirming I4 holds in practice (§7).

Fencing-Token Regression — a detected decrease or reuse of a fencing token value; must never happen, caught at issuance (I2).

Wait Queue — the bounded FIFO structure ordering contenders for a lease-bounded lock while the current holder is valid (ADR-07, §17).

Split-Brain — a state in which two coordinators simultaneously believe themselves the current lease authority for the same resource (§8.10, ADR-13).

Redlock — the Redis-based, quorum-of-independent-timers locking algorithm lacking a fencing token, unsafe under process pause or clock jump (§8.9, §36 Alternative C).

Sequencer — Chubby's term for what this project calls a fencing token (Burrows 2006, §5).

Ephemeral Node — ZooKeeper's session-bound znode, the structural analogue of a lease-bound resource (Hunt et al. 2010, §5, §33).

Linearizability — the correctness condition (Herlihy & Wing 1990) this project's observe() reads and grant path must respect (§7, §16).

FLP Impossibility — the Fischer/Lynch/Paterson 1985 result that no perfectly accurate failure detector can exist in an asynchronous system, motivating leases' clock-based approach (§1, §32).

Unreliable Failure Detector — the Chandra & Toueg 1996 formalism for probabilistic liveness suspicion, deliberately sidestepped rather than implemented by leases (§32, §36).

Monotonic Clock — a clock valid only for measuring local elapsed intervals, never for cross-node comparison (ADR-03, §11).

Wall Clock — an NTP/PTP-disciplined clock used for cross-node skew estimation, the basis of the clock-safety argument (§8.2, ADR-03).

Clock Jump — an instantaneous forward or backward step in a node's wall clock, detected as a discontinuity distinct from ordinary skew drift (§8.10, ADR-16).

RTO (Recovery Time Objective) — the maximum acceptable time to restore service after a coordinator failure; < 2 minutes (§4).

RPO (Recovery Point Objective) — the maximum acceptable committed-state loss on recovery; zero for lease/fencing state (§4).

Deterministic Simulation Harness — the fake-clock, fake-network test infrastructure enabling byte-for-byte reproducible fault-injection scenarios (module 13, ADR-20).

Jepsen-Style Verification — combined, randomized, seed-reproducible fault injection asserting mutual exclusion never breaks (§23, Chandy & Lamport 1985).

Differential Testing — comparing this project's documented lease/session semantics against real etcd and ZooKeeper behavior to catch specification drift (§23, §28).

Soak Test — a multi-day continuous run under moderate chaos verifying no invariant violation and no unbounded resource growth (§23).

SBOM (Software Bill of Materials) — the enumerated dependency list shipped with each signed release, required for supply-chain trust (ADR-23).

Backpressure — deliberate rejection of new requests (e.g. wait-queue overflow) rather than unbounded queuing (ADR-07, P11).

Defense in Depth — layering fencing (I3) on top of consensus-layer term uniqueness (ADR-13) so a hypothetical failure of either layer alone does not by itself cause a safety violation.

Idempotent Retry — client retry semantics guaranteeing a grant that actually committed before an ack was lost returns the original token, never a new one (§19.2, I2).

resource_key — the flat string namespace identifying the object a lease/lock is held against (§11), the trust boundary later extended by Hierarchical Namespace ACLs (§37).
