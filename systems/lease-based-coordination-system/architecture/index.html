3. Architectural Overview

Client (lease holder). The application process that acquires, renews, and eventually releases a lease; it must attach the fencing token it currently holds to every write against a protected resource. It cannot be trusted to know, in real time, whether its lease has already expired (pause/GC-stall fault, §8.5) — this is precisely why the fencing token exists.

Lease Manager. The single logical owner of the Lease state machine (§8.1); it processes grant, renew, and revoke requests against the ConsensusStore and is the only component authorized to transition a Lease between states.

Fencing-Token Issuer. Hands out a strictly monotonically increasing token with every successful grant or leadership hand-off; never reuses or decrements a token; persists the high-water mark in the ConsensusStore so a coordinator crash cannot roll it back (I3).

Leader Election module. A thin, named-lease-specific layer over the Lease Manager: whoever holds the "leadership" lease for a given election name is the leader; leadership hand-off is exactly a lease grant to a new holder plus a fencing-token bump.

Lock module. Generalizes the same lease machinery to arbitrary named resources with a bounded FIFO wait queue, so a crashed lock holder's lease simply expires and the next waiter is granted the lock plus a fresh fencing token.

Session tracker. A meta-lease: one heartbeat/liveness signal covers a whole set of resource leases, so a client does not need one heartbeat per resource (Chubby's session model; ZooKeeper's ephemeral session).

Clock/Skew Monitor. Samples wall-clock and monotonic-clock offsets against the coordination service's own view of time (and, transitively, against NTP), maintains a live skew estimate, and trips a fail-safe (refuse renewals, page immediately) if the estimate exceeds the configured bound. This is the component that makes the clock-safety boundary in the diagram a checked, not merely assumed, boundary.

Timer Wheel. A hashed timer wheel scheduling renewal reminders and expiry sweeps in O(1) amortized insert/cancel, sized to the configured lease-count ceiling (§4).

Replicated Lease Store (ConsensusStore). The durable, replicated home for lease/session/fencing state; backed by Raft or Paxos in production (delegated, not reimplemented — §1); a coordinator crash and restart, or a coordinator failover, must not double-grant a lease or roll back a fencing token, which is why this state — and only this state — is required to be consensus-durable.

The lease-grant boundary (top half of the diagram) marks the point past which a request has been accepted into the lease/lock/election/session subsystem; the clock-safety boundary (lower half) marks the point past which every decision is provably bound to the configured clock-skew model — crossing it without passing through the Clock/Skew Monitor is a correctness bug by construction.

8. Domain Model

8.1 The Lease State Machine

States: Free, Granted, Renewing, Expired, Revoked.

        grant(owner, ttl)
 Free ─────────────────────────► Granted ──renew(owner)──► Renewing
   ▲                                │  ▲                       │
   │        release(owner)          │  └───renew_ok────────────┘
   │        or expire-sweep         │
   │        or revoke(admin)        │ renew_fail / ttl_elapsed
   │                                ▼
   └──────────────────────────  Expired ──── revoke(admin) ───► Revoked
                                     │                              │
                                     └──── reacquire(new_owner) ────┘
                                              (only from Free/Expired,
                                               never from Granted/Renewing)

Failure edges: Granted → Expired (ttl elapsed with no successful renewal, detected by the Timer Wheel, I4); Renewing → Expired (a renewal request that arrives after the grantor has already declared expiry per I4's margin — the request is rejected, not applied, I8); Granted → Revoked (administrative or fail-safe-triggered revocation, I9); Expired → Free (after the guard interval elapses with no reacquire, the resource returns to the pool). A Revoked lease can never transition back to Granted directly — it must pass through Free and a fresh grant (I8).

8.2 The Clock-Safety Argument

Let δ be the configured maximum pairwise clock skew bound (§4, default 200 ms), L the lease duration, and G the guard interval. Let grant denote the grantor's wall-clock timestamp at grant time.

The holder, using its own (possibly skewed) clock, believes the lease valid until:

T_holder_valid_until = grant + L

The grantor, to be safe against a holder whose clock reads up to δ behind the grantor's, must declare the lease expired no later than:

T_grantor_expires_at = grant + L − δ − G

For the grantor's expiry decision to never precede a moment the holder could still legitimately believe valid — the entire point of I4 — the guard interval must absorb both the round-trip communication delay and the residual clock uncertainty:

G ≥ 2δ + RTT_p99

Worked example with the project defaults (δ = 200 ms, RTT_p99 = 20 ms, §4):

G ≥ 2(200 ms) + 20 ms = 420 ms   →   round up to G = 500 ms (§4 default)

With L = 10 s (default), the grantor treats the lease as expired at grant + 10s − 0.2s − 0.5s = grant + 9.3s, i.e. 700 ms before the holder's own clock would read grant + 10s. That 700 ms margin is the price of the stated clock-skew bound; failover time (§34) is bounded below by L − 0.7s plus the time to complete a new grant, and bounded above by L + G if the grantor waits the full guard interval before declaring expiry to a new claimant (defensive posture, §9 ADR-11).

8.3 Fencing Tokens — The Kleppmann Scenario, Worked

Named steps, following Kleppmann's canonical example:

  1. Client A acquires the lease on resource R with lease duration L = 10 s and fencing token 33.
  2. Client A begins a long write to R, then experiences a stop-the-world GC pause of 15 s (exceeds L, and exceeds L + G).
  3. While A is paused, the grantor's Timer Wheel expires A's lease at grant + 9.3s (per §8.2) and the resource is returned to Free.
  4. Client B acquires the lease on R, receiving fencing token 34 (I2: strictly greater than 33).
  5. B begins writing to R, tagging each write with token 34.
  6. Client A resumes from its GC pause, still believing (per its own clock, per §8.2's T_holder_valid_until) that its lease is valid, and issues its pending write to R tagged with its stale token 33.
  7. R's ResourceGuard (implementing TokenChecker) has already recorded 34 as the highest token seen (from step 5) and rejects A's write carrying token 33 (I3).
  8. Result: mutual exclusion is preserved despite the pause, because the token check — not the clock, not A's own self-assessment — is the final arbiter at the point of actual resource mutation. This is exactly the gap Redlock leaves open (§8.7, §36) and exactly what Chubby's sequencers close (Burrows 2006).

8.4 Lease-Based Leader Election — Sequence Table

Step Actor Action
1 Candidate C1 requests grant on election lease "leader:svc-x"
2 Lease Manager resource Free → grants to C1, issues token 100
3 C1 begins acting as leader, attaches token 100 to all leader-only actions
4 C1 renews every L/3 interval; renewal preserves identity and token (I5)
5 C1 crashes (or pauses beyond L + G)
6 Timer Wheel expires C1's lease at grant + L − δ − G
7 Candidate C2 requests grant, resource Free → grants to C2, issues token 101
8 C2 begins acting as leader with token 101
9 Downstream systems reject any lingering C1 action tagged token 100 (I3)
10 C1 (if it resumes) observes its renewal fail (I8: post-revocation renewal rejected), steps down voluntarily as a defense-in-depth measure even though token-fencing already made it harmless

8.5 Lease-Bounded Distributed Locking — Sequence Table

Step Actor Action
1 Client A LockRequest("resource-y", ttl=10s)
2 Lock Module resource free, grants to A, token 7, wait queue empty
3 Client B LockRequest("resource-y", ttl=10s) while A holds
4 Lock Module enqueues B in bounded FIFO wait queue (§9 ADR-07)
5 Client A crashes without releasing
6 Timer Wheel expires A's lease at guard-adjusted deadline
7 Lock Module pops B from wait queue, grants lock, issues token 8
8 Protected resource rejects any late write from A carrying token 7 (I3)
9 Client B releases voluntarily; resource returns to Free, wait queue empty

8.6 Session Model — The Meta-Lease

A session S is itself a Lease (state machine identical to §8.1) whose "resource" is the client's overall liveness rather than a single protected object; S maintains a set of attached resource leases {R1, R2, ..., Rn}. The session's own expiry (missed heartbeats past the threshold, §4) triggers cascading release of every Ri (I7), each following its own Granted → Expired transition independently but atomically with respect to the session's expiry event — no Ri may be observed still Granted after S has transitioned to Expired (extension of I1/I4 to the one-to-many case). This mirrors ZooKeeper's ephemeral-node-tied-to-session model and Chubby's session concept directly (Hunt et al. 2010; Burrows 2006).

8.7 Renewal and the Grace Period

Renewal request renew(owner, current_token) succeeds only if: (a) the lease is in Granted or Renewing state, (b) owner matches the current holder (I5), and (c) the request arrives before T_grantor_expires_at (§8.2). A grace period (distinct from the guard interval) may optionally extend a just-missed renewal — one arriving within a small operator-configured window after T_grantor_expires_at but before the resource has been re-granted — back to the same owner without a fencing-token bump, trading a small safety-adjacent convenience (avoiding unnecessary token churn under transient renewal delay) for slightly relaxed strictness; this is a named, ADR-governed policy choice (§9 ADR-10), off by default, because it reintroduces a sliver of the exact ambiguity fencing tokens exist to eliminate and is therefore treated as a deliberate, audited exception.

8.8 Interaction with the Consensus-Backed Store

Every state transition in §8.1 that is not purely a read (grant, renew-commit, expire-commit, revoke) is proposed as a command to the ConsensusStore and only takes effect once committed (quorum-acknowledged); the Lease Manager applies committed commands deterministically, exactly the same way regardless of which physical coordinator node originated them, so a coordinator failover mid-grant either commits (and the new coordinator observes the committed grant on replay) or never commits (and the client must retry) — there is no partially-applied state (I6).

8.9 The Redlock Cautionary Analysis

Redlock (a quorum of N independent Redis nodes, each an independent timer with no shared consensus log and, critically, no fencing token) is unsafe under two realistic faults it was not designed to survive: (a) a process pause between acquiring the lock and using the protected resource — the resumed, still-token-less process cannot be told apart from a legitimately valid holder by the resource, because there is no token to check (contrast §8.3 step 7, which does have a token to check); (b) a clock jump on any one of the N Redis nodes (NTP step correction, VM migration, manual clock set) can cause that node to believe a lock it already granted has expired far earlier or later than intended, and because Redlock's safety proof depends on every node's clock behaving monotonically and boundedly, a single misbehaving node can violate the majority argument. Kleppmann's critique (cited §5) formalizes both points; Antirez's rebuttal accepts the GC-pause point as valid for any lock without fencing (including this project's, absent §8.3) and argues clock jumps are an operational, not algorithmic, concern — this project resolves the debate operationally by (i) mandating fencing everywhere (§9 ADR-05, non-negotiable) and (ii) treating clock-jump detection as a first-class, alarmed invariant (I9) rather than an assumed-away operational nicety.

8.10 Malformed and Hard Examples

  • GC pause exceeding the lease: covered fully in §8.3; resolved by fencing, not by clock policy alone.
  • Clock jump (NTP step correction moves a node's wall clock backward or forward by seconds): the Clock/Skew Monitor's continuous skew estimate detects the discontinuity (a monotonic-clock vs. wall-clock divergence spike) and trips the I9 fail-safe before any grant decision uses the jumped clock reading.
  • Network partition isolating the leaseholder: the isolated holder cannot renew (no path to the ConsensusStore quorum side); its lease expires on schedule from the majority side; the isolated holder, even if it keeps acting, is fenced out the moment its writes reach a ResourceGuard that is reachable from the majority side (I3) — this is the same mechanism as §8.3, with "partition" substituted for "pause" as the root cause of the holder's stale self-belief.
  • A renewal racing expiry: resolved by I8 plus the strict ordering enforced by the ConsensusStore's single commit log — the renewal command and the expiry-commit command cannot both be accepted for the same lease generation; whichever commits first wins, and the loser is rejected deterministically on replay (no ambiguity survives past the commit point).
  • A token that goes backward: caught at issuance by I2's self-check before it ever reaches a client; if it were ever observed downstream (implying a bug elsewhere, e.g., a ConsensusStore rollback bug), it is caught at the ResourceGuard boundary by I3's core comparison regardless.
  • A split-brain attempt (two coordinators each believing themselves the current lease authority after a partition heals asymmetrically): prevented at the ConsensusStore layer by the backing consensus protocol's own term/leader uniqueness guarantee (delegated, §1), and defended in depth at the fencing layer (I3) even in the hypothetical case that the backing store's guarantee were violated.

8.11 A Failure-Path Example, End to End

Coordinator crashes mid-commit of a grant to client A for resource R (WAL entry proposed to ConsensusStore but not yet quorum-acknowledged to the original coordinator, though it may have already reached a quorum of replicas). On failover, the new coordinator's Lease Manager replays the ConsensusStore log: if the entry is present in the committed prefix, the grant is honored and A is informed (idempotently, on retry) that its grant succeeded with its original fencing token; if the entry never reached a quorum, it is absent from the committed prefix and the grant is treated as never having happened — A's retry produces a fresh grant with a new (higher) token per I2. In neither case does R end up with two simultaneously valid holders (I1), and in neither case does a token get reused or decremented (I2).
