⬜ Phase 0 — Skeleton, governance, and the "Hello, backup" smoke test (Week 1)

Objectives

By the end of Phase 0: clone, make bootstrap/build/test/conformance, bks init, bks backup, modify a file, bks backup again, observe the second backup uploaded only the delta, bks restore, and bit-identically compare source against restore. Encryption OFF (AeadAlgo::None); local backend only.

Deliverable

A working bks binary against a local repository: init, backup, list, restore, verify all runnable and inspectable by an operator via plain JSON logs; repository at the production-scaffold bar with the five workflows present; ADRs 01, 02, 03, 04, 10, 12, 14, 17, 19, 23 written.

Acceptance

make test green with the smoke test; fixture append_100b_10k_reback shows both unchanged files (1 KB, 1 MB) share 100% of chunks between backup 1 (M1) and backup 2 (M2); fixture restore_bytecompare shows every restored file byte-identical to source; bks verify M1 and bks verify M2 both exit 0; conformance buckets core_types, repo_local, backup_e2e Pass; a reviewer cloning at a clean rev reproduces all of the above with zero manual steps.

Fixture Purpose Expected
corpora/backup_e2e/three_file_source/ (1 KB text, 10 KB binary, 1 MB deterministic-random) smoke baseline backup M1 produced
corpora/backup_e2e/append_100b_10k_reback/ dedup proof M2 ≠ M1; unchanged 1 KB + 1 MB files share 100% of chunks
corpora/backup_e2e/restore_bytecompare/ round-trip every file byte-identical
corpora/backup_e2e/verify_m1_m2/ integrity bks verify M1, bks verify M2 both succeed
corpora/backup_e2e/malformed_manifest_body/ (truncated prost body) malformed input bks restore rejects with MANIFEST_INVALID, no partial write
corpora/chaos/crash_before_head_update/ I11 replay next bks backup succeeds, no orphan head
Pitfalls
  • The local head pointer tempts flock/fcntl advisory locks; resist — use rename-into-place (the atomic-rename POSIX guarantee), because the Phase-4 S3 backend cannot flock (ADR-15).
  • Fixed-size 1 MB chunks mean a 100-byte append to a 10 KB file changes that file's only chunk entirely; the Phase-0 dedup assertion therefore targets the unchanged files; Phase 2 swaps in FastCDC and extends the assertion.
  • Resist shipping encryption in Phase 0 — AeadAlgo::None is deliberately rejected by the Phase-3+ validator (I3) so it can never leak into production use.
  • A chunker bug that clamps every boundary to max silently degrades to "one chunk per file" and still passes a round-trip test — assert chunk count, not only byte equality.

⬜ Phase 1 — Walker, metadata preservation, and round-trip integrity (Week 2)

Objectives

Make POSIX metadata first-class: mode, owner, group, mtime, atime, ctime, xattrs, ACLs, special files, hard links — with a bit-identical round-trip including metadata (I10).

Deliverable

bks-walker crate: a lazy, one-entry-per-next() metadata iterator plus the restore-side metadata-application routine, exercised end-to-end by the round-trip conformance suite.

Acceptance

Fixture metadata_corner_100 round-trips content and every metadata field byte-and-field-identical; fixture hardlink_10k_1k preserves all 1,000 hard links within one file system (I9); the pjdfstest-style POSIX-semantics harness passes on the restored tree; fixture walker_1m_files completes in ≤ 60 s on one SSD (§4, M1); conformance walker bucket Pass.

Fixtures
Fixture Purpose Expected
corpora/walker/metadata_corner_100/ (setuid, sticky, xattrs, ACLs, symlinks, hard links, devices) round-trip content + every metadata field identical
corpora/walker/hardlink_10k_1k/ (10 K files, 1 K hard links) hard-link identity (I9) links preserved within one FS

Pitfalls
  • atime is an anti-feature: reading a file updates atime, the next incremental sees every file as modified — open O_NOATIME (needs file ownership or CAP_FOWNER); document the leak where it cannot.
  • Restore-side ordering is strict (I10): chown before mode clears setuid bits; setting times before other ops lets those ops overwrite them.
  • Hard-link detection by (dev,inode) is correct only within one FS (I9).

⬜ Phase 2 — FastCDC chunker (rank 109) and the chunk index (Week 3)

Objectives

Swap the Phase-0 fixed-size chunker for rank 109's FastCDC and wire the chunk index that makes incremental backup fast. Prove a single insert into a large file re-uploads ≤ 10% of that file's chunks.

Deliverable

bks-chunker over rank 109, wired into the Phase-0 backup path in place of the fixed-size stub; a runnable "Hello, dedup" end-to-end test an operator can execute directly.

Acceptance

Fixture insert_100b_random_offset shares ≥ 95% of chunks with the pre-insert backup; fixture append_10mb_100b re-uploads ≤ 10% of that file's chunks (§4, M2); fixture index_restart_reload round-trips to identical membership; a 10 M-entry index stays ≤ 1 GB in-memory / ≤ 200 MB on the disk-backed variant (§4); chunker throughput ≥ 1 GB/s/core (§4, M2); conformance chunker_fastcdc bucket Pass.

Fixtures
Fixture Purpose Expected
corpora/chunker/insert_100b_random_offset/ CDC alignment ≥ 95% chunks shared
corpora/chunker/append_10mb_100b/ incremental upload ≤ 10% of chunks re-uploaded
corpora/chunker/index_restart_reload/ round-trip identical membership
corpora/chunker/index_10m_entries/ memory ≤ 1 GB (in-mem) / ≤ 200 MB (disk)

corpora/chunker/index_tmp_crash_replay/ (kill mid .tmp write) replay/regression next start sweeps the stale .tmp, index unaffected
Pitfalls
  • The index is an availability concern, not a correctness one — do not over-engineer cache coherence (I5).
  • Index upload must be atomic (.tmp+rename); a crashed backup leaves a .tmp the next start sweeps.
  • FastCDC parameters are sensitive: smaller chunks improve dedup at the cost of index size; benchmark, do not tune blindly.

⬜ Phase 3 — Key derivation, AEAD, and the encrypted backup path (Week 4-5)

Objectives

Turn the plaintext Phase-2 backup into an encrypted one: passphrase → Argon2id master key → HKDF purpose keys → per-chunk XChaCha20-Poly1305 → signed manifest. Establish I2 and I12.

Deliverable

bks-crypto: a runnable seal/open/sign/verify surface an operator can exercise via bks backup --encrypt end to end, plus docs/architecture/crypto.md.

Acceptance

All primitive test vectors (RFC 8439/XChaCha20-draft, Argon2, RFC 5869, RFC 8032) pass byte-exact; the encrypted round-trip fixture is byte-identical; the two tamper fixtures (flip_ciphertext_byte, flip_manifest_bit) surface CHUNK_CORRUPT/rejection respectively; the 1 M-sample nonce-derivation fixture shows zero collisions (I2); Argon2id derivation completes in 1–2 s at default params (§4, M8); encrypt path ≥ 1.5 GB/s/core (§4, M4); conformance crypto_kdf + crypto_aead buckets Pass.

Fixtures
Fixture Purpose Expected
corpora/crypto/rfc8439_xchacha_vectors/ primitive correctness byte-exact
corpora/crypto/argon2_hkdf_ed25519_vectors/ (RFC 5869, RFC 8032) KDF + sig correctness byte-exact
corpora/crypto/nonce_1m_samples/ I2 no collisions
corpora/crypto/encrypted_roundtrip/ round-trip byte-identical
corpora/crypto/flip_ciphertext_byte/ I1/I12 tamper CHUNK_CORRUPT with correct chunk_ref
corpora/crypto/flip_manifest_bit/ I3/I4 tamper rejected at load
Pitfalls
  • Nonce derivation is the most dangerous step: deriving the same nonce on the same (chunk_ref, epoch) is fine (deterministic, identical output) but two distinct pairs colliding would be catastrophic — I2 asserts they never do.
  • Storing the ciphertext under a ciphertext-derived key would destroy dedup (every ciphertext is unique).
  • The known-plaintext-existence surface (an attacker hashing P to check membership) is inherent to any content-addressed system; accepted at single-repo scope, mitigated cross-tenant by per-repository salts (ADR-09).
  • Argon2id parameters are an operator knob documented in docs/threat-model.md.

Pitfalls

Objectives

Pitfalls
  • The signature is over the body and the id is BLAKE3(body); a manifest whose stored id ≠ BLAKE3(body) is invalid even with a valid signature (I4).

  • prost drops default-valued fields — a restore expecting an omitted field sees None; the round-trip fixture covers every variant at default and at max.

Pitfalls
  • Mark must walk every retained manifest — a six-month-old monthly's chunks must stay live; walking only head is a data-loss bug.
  • S3 delete is eventually consistent, so chunks_deleted is "marked for deletion", not "verifiably absent"; correctness does not depend on read-after-delete.
  • A backup that re-uploads a just-deleted chunk is fine (now live again) though its storage is briefly double-counted — the index is advisory (I5).

  • Verify is bandwidth-expensive — a 1 PB repo at 1 GB/s takes ~12 days; document sampling.

⬜ Phase 8 — Concurrency, the lock manager, and the journal (Week 10-11)

Objectives

Add the concurrency primitives that make multi-host operations safe: a TTL-fenced repo lock (I6) and a replayable per-backup journal (I11).

Deliverable

Acceptance

Fixture lock_1hr_ttl_renewal holds the lock throughout a 1-hour backup; fixture kill9_coordinator_resume resumes correctly from the journal (I11); fixture 5_concurrent_backups_same_repo serializes to exactly one active writer with zero orphan chunks (I6); fixture expired_lock_takeover lets a new holder acquire while the old holder's writes fail IfMatch; conformance chaos_concurrent_backup + per-backend lock_manager buckets Pass.

Fixtures
Fixture Purpose Expected
corpora/lock/lock_1hr_ttl_renewal/ fencing lock held throughout
corpora/chaos/kill9_coordinator_resume/ journal replay (I11) resume from last event
corpora/chaos/5_concurrent_backups_same_repo/ I6 exactly one at a time; no orphan chunks

Pitfalls
  • The TTL must exceed the longest backup window or it expires mid-backup and two backups race — renew at half the TTL.
  • Journal events must be idempotent on replay.
  • The lock is only as strong as the backend's put_if_match: S3 If-Match is strong, SFTP/local emulate via rename-into-place — the trait documents the required semantics and every backend passes the lock_manager bucket.

⬜ Phase 9 — Snapshot drivers: Btrfs, ZFS, LVM, fsfreeze (Week 11-14)

Objectives

Make the backup operate on a consistent snapshot rather than the live tree (P2): Btrfs, ZFS, LVM, fsfreeze, and a LiveWalk fallback.

Fixtures
Fixture Purpose Expected
corpora/snapshot/btrfs_1tb_subvolume/ Btrfs perf snapshot ≤ 1 s
corpora/snapshot/zfs_1tb_dataset/ ZFS perf snapshot ≤ 1 s
corpora/snapshot/lvm_1tb_thin_lv/ LVM perf snapshot ≤ 5 s

Pitfalls
  • A Btrfs snapshot is read-only; a writable one is a clone and is not what backup needs — verify RDONLY.

  • FIFREEZE blocks writers; a frozen mount past the Linux dirty-flush deadline (~5 min) is a serious hazard — complete within the TTL or surface a clear error.

Fixture rotate_new_version completes in ≤ 5 s (§4, M16); fixture rekey_100gb_backup is bounded by AEAD throughput (§4, M4) and restores byte-identically; fixture old_version_backup_restores shows an un-rekeyed backup still restores under its original key version; fixture kms_sealed_master_unseal restores after a KMS unseal round trip; conformance key_rotation bucket Pass.

Fixtures
Fixture Purpose Expected
corpora/keys/rotate_new_version/ new version add ≤ 5 s
corpora/keys/rekey_100gb_backup/ re-encrypt bounded by AEAD throughput
corpora/keys/rekeyd_backup_restore/ correctness byte-identical

Pitfalls
  • Rotation does not invalidate the old key — an attacker with it still decrypts old backups; rotation protects future, rekey protects past.
  • A rekey'd manifest gets a new id and a rewritten parent chain (100 manifests → 100 new); the old chain is left to retention.
  • The KMS integration is the load-bearing escape hatch; AWS-KMS lacks Ed25519 (ADR-05 open), so signing-key export there needs P256.
