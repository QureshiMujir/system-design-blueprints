111 — Backup / Snapshot System

Project Number: 111

Project Name: Backup / Snapshot System

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

Build a content-addressed, encrypted, incremental backup and snapshot system in the BorgBackup / restic / Kopia / Tarsnap lineage, layered on the copy-on-write snapshot lineage of ZFS, Btrfs, and NetApp WAFL.

1. Goal & Scope

Build a content-addressed, encrypted, incremental backup and snapshot system in the BorgBackup / restic / Kopia / Tarsnap / duplicity / rdiff-backup lineage, layered on the snapshot lineage of ZFS, Btrfs, NetApp WAFL, and Apple Time Machine. The system has two halves.

The snapshot half captures a consistent, point-in-time view of a source tree — a directory, a database directory, an entire file system — via copy-on-write where available (Btrfs, ZFS, LVM thin) and via a freeze-pause-resume protocol (FIFREEZE/FITHAW, application-coordinated for databases) where not.

The backup half walks the snapshot, content-defined-chunks every file (delegating chunking and content-addressing to rank 109's FastCDC + BLAKE3 engine), encrypts each chunk with a per-chunk derived key under XChaCha20-Poly1305, writes the encrypted chunks to a pluggable repository backend (local disk, S3 via rank 107, SFTP, or a small REST blob server), and commits a signed manifest pointing to the chunk identifiers. Restores read the manifest, fetch the chunks, decrypt them, and reconstruct the tree. Retention policies (keep 7 daily / 4 weekly / 12 monthly) operate on the manifest set; a garbage collector reclaims chunks no longer referenced by any retained manifest. A verify pass re-fetches every chunk in a manifest, decrypts, and re-hashes; a prune is a manifest deletion plus a GC pass.

In scope: the backup + snapshot substrate, the repository trait and three backends (local, S3, SFTP), the crypto stack (Argon2id → HKDF → XChaCha20-Poly1305 + Ed25519), retention/GC/verify/restore/prune, key rotation and rekey, multi-site replication, and operator tooling (fsck, doctor, dry-run restore).

Out of scope (see Deferred Features Register and Appendix F — Out of Scope): a backup web UI, a scheduling daemon, a hosted multi-tenant retention service, block-level backup, continuous data protection (CDP).

Phase-0 surface (≈2 weeks): one source tree, one local repository backend, one backup operation, one verify, one restore, no encryption, no S3, no retention — enough to snapshot a directory, take a first backup, modify one file, take a second, prove the second re-stored only the delta, restore, and bit-identically compare against the source.

Recommended language: Rust (edition 2021). The snapshot driver, walker, chunker bridge, AEAD layer, manifest serializer, repository backends, retention/GC engines, verify/restore engines, and CLI are all tokio-async workspace crates. Cryptographic primitives are vendor-pinned to chacha20poly1305, aes-gcm-siv, argon2, hkdf, blake3, ed25519-dalek, and the audited RustCrypto traits; we do not roll our own primitives.

Prerequisites: rank 36 (local File System — source-tree walking, POSIX metadata), rank 107 (Object Storage — S3 backend), rank 108 (Erasure Coding — optional repository parity), rank 109 (Deduplication Engine — FastCDC chunking + content-addressing), rank 110 (Filesystem Journaling — the snapshot half's consistent-view semantics). Read the BorgBackup internals docs, the restic design paper, the Tarsnap whitepaper, and at minimum open the NetApp WAFL paper and the Venti paper.

Estimated time: 9–12 months for the full plan; 6–8 weeks for the Phase-0 drop.

2. Why Build This

Backup is the most misunderstood storage layer in the stack. Every engineer has lost data; every team has discovered a backup that turned out to be unreadable; every operator has at least once watched a restore run for fourteen hours and produce nothing usable. The discipline of correct backup is the line between a postmortem that ends in "we restored from yesterday" and one that ends in "we are now writing the customer-impact email." When the substrate is a managed cloud service or a vendor's proprietary blob format, every restore session ends in support tickets. When the substrate is one you have written, every restore session ends in a chunk-by-chunk audit trail and a confident answer.

The literature on backup and snapshot systems is older, denser, and stranger than the literature on most distributed systems. Quinlan and Dorward's 2002 Venti paper is the modern starting point for content-addressed archival storage; the system was already shipping at Bell Labs when GFS was being written. Hitz, Lau, and Malcolm's 1994 NetApp WAFL paper showed how to take a consistent snapshot of a live file system without quiescing it — a technique Apple Time Machine, ZFS, Btrfs, and every modern snapshot implementation owe a debt to. Bonwick's ZFS snapshots and clones generalised WAFL into a copy-on-write block layer with O(1) snapshots at any time. Percival's Tarsnap whitepaper (2009) showed that authenticated encryption over content-defined chunks produces a deduplicated, encrypted, cloud-resident backup format that survives auditing. BorgBackup's internals docs (2015 onward) are the contemporary reference for an open-source production implementation; restic's design document (2014 onward) is the same for a Go-based equivalent; Kopia (2019 onward) is the latest entry, putting manifests-as-commit-objects at the centre from day one.

This project sits at the intersection of all of these. The snapshot half follows WAFL and ZFS — copy-on-write where the file system supports it; the rsync/restic discipline of walking a live tree where it does not. The backup half follows BorgBackup and restic: content-defined chunking with FastCDC, BLAKE3 fingerprints, per-chunk AEAD under XChaCha20-Poly1305, a Merkle-tree manifest, a repository format durable in object storage. The encryption follows Tarsnap and Kopia: a master key derived from a passphrase via Argon2id, a purpose-key hierarchy via HKDF, Ed25519 signatures over manifests for tamper-evidence.

The promise of the blueprint is that, by Phase 12, you have a backup system you would trust to run unattended against your own laptop, a production database directory, and a 100 TB file server with thirty days of retention. That trust comes from three properties: every byte that goes on the wire is encrypted with a primitive that has a publication and a security proof; every byte that comes off the wire is verified against a cryptographic hash before being handed to the caller; every manifest carries a signature you can verify with a public key you control. None of these are optional in production; each is gated by a conformance bucket and a chaos test.

What Mastery Looks Like

  • You can explain, without notes, why nonce reuse is impossible by construction in this design and trace it to the HKDF derivation — see Phase 3.
  • You can predict the dedup ratio of a single-byte insert into a 10 MB file before running it, from FastCDC's expected chunk size — see Phase 2 and the Back-of-Envelope Capacity Model.
  • You can reason about a GC racing a backup and name the exact ordering hazard and the lock that closes it — see Phase 6 and Phase 8.
  • You can restore a single file from a 100-million-file backup in O(log N) tree fetches, not O(N) — see Phase 5's Merkle-tree manifest.
  • You can rotate a compromised key and explain the difference between rotation (protects future) and rekey (protects past) — see Phase 10.
  • You can stand in front of an auditor and produce, for any retained backup, a verifiable signature chain back to a key you control — see Phase 5 and Phase 7.
  • You can replicate a 100 GB repository to a second site transferring only the delta, and prove the destination restores bit-identically — see Phase 11.

(1) Snapshot driver. Captures a consistent point-in-time view via copy-on-write where available (Btrfs BTRFS_IOC_SNAP_CREATE_V2, zfs snapshot, LVM lvcreate -s) and via FIFREEZE/FITHAW or application-coordinated quiesce where not. The backup never reads the live tree directly; this is what makes it work against running databases.

(2) Walker. Traverses the snapshot mount, emitting POSIX metadata (mode, owner, mtime, xattrs, ACLs, hard-link identity) per entry. Lazy iterator; one entry per next().

(3) Chunker. Delegates to rank 109's FastCDC + BLAKE3 engine. A chunk is named by the BLAKE3 hash of its plaintext — content addressing is the durability story, not redundancy. A chunk read back is required to hash to its name; bit rot is detected at read time, never trusted at scrub time.

(4) AEAD layer. Encryption is per-chunk with a derived key. A per-chunk key is HKDF-derived from the master key and chunk id; the nonce is HKDF-derived from chunk id and a per-backup epoch. Nonce reuse — the single most dangerous failure of GCM/ChaCha20-Poly1305 — is impossible by construction, not by hygiene.

(5) Repository backend. Pluggable with a small surface: put, put_if_match, get, head, list, delete, content-typed keys (chunks/<hash>, manifests/<hash>, keys/<version>), optimistic concurrency via etag. Local disk, S3 (rank 107), SFTP, and a REST blob server all implement the same trait.

(6) Manifest. The only mutable object. A signed Merkle-tree commit object naming the chunks of a backup; its id is the BLAKE3 of its body. Chunks are content-addressed, append-only, never overwritten. Restore, verify, retention, and GC all operate on the manifest set; they never modify chunks.

(7) Retention / GC / verify / restore / prune. Retention is a pure function from [Manifest] to the kept set. GC is mark-sweep over the chunk set against the retained-manifest live closure. Verify is end-to-end (fetch, decrypt, re-hash, check signature). Restore is the inverse of backup. Prune is retention + GC.

6. Design Principles

Twelve principles every API surface and data-path decision is negotiated against. Each names its rule, the tradeoff it accepts, and how violating it breaks the system. Enforced by the conformance suite, code review, and the ADR table.

P1 — A backup is content, not bytes. A chunk is named by the BLAKE3 hash of its plaintext; a chunk read back must hash to its name. Tradeoff: re-hash cost on every read. Violating it: trusting storage bytes without verifying means silent bit rot reaches the restored tree undetected.

P2 — A snapshot is a commit, not a copy. Capture a consistent point-in-time view via CoW or freeze-pause; the backup is taken from the snapshot, never the live tree. Tradeoff: a snapshot driver per file system. Violating it: the backup observes a torn, mid-write tree and a database restore replays into corruption.

P3 — Encryption is per-chunk, with a derived key and a derived nonce. Per-chunk key = HKDF(master, chunk_id); nonce = HKDF(chunk_id, epoch). Tradeoff: a KDF call per chunk. Violating it (a single repo key + random nonces): a nonce-reuse bug reveals plaintext-xor and breaks tag unforgeability.

P4 — The manifest is the only mutable object, and it is append-only. A signed Merkle-tree commit; retention/GC delete manifests, never modify them. Tradeoff: dead manifests linger until GC. Violating it: mutating chunks turns content addressing into a lie and corrupts dedup.

P5 — The repository backend is a small REST-shaped surface. put/put_if_match/get/head/list/delete with etag optimistic concurrency. Tradeoff: no server-side transactions/batch. Violating it (a fat trait): backends like SFTP and a 50-line local store can no longer satisfy the contract.

P6 — Retention is policy on the manifest set, offline. A pure function [Manifest] -> [Manifest]. Tradeoff: retention cannot see live writes. Violating it (retention in the backup path): a backup that fails leaves retention half-applied and risks deleting a still-needed manifest.

P7 — GC is mark-sweep over the chunk set, not refcount. Compute the live closure from retained manifests, list chunks, delete the difference. Tradeoff: a full list+walk per GC. Violating it (refcount): a missed decrement leaks, a missed increment is data loss.

P8 — Verify is end-to-end. Fetch, decrypt, hash plaintext, assert == chunk id; check manifest signature and chain. Tradeoff: bandwidth-expensive. Violating it (trusting etags/sizes): a corrupt-but-right-sized chunk passes verify and fails restore.

P9 — Restore is the exact inverse of backup. Reconstruct content + metadata bit-identically to the source at snapshot time. Tradeoff: strict metadata-application ordering. Violating it: setuid bits, owners, or times come back wrong and the "restore" silently diverges from the source.

P10 — Failures are first-class. Resumable uploads, surfaced corrupt-chunk ids, continue-on-gap restore, re-runnable GC. Tradeoff: journal + lock machinery. Violating it: a mid-upload crash strands orphans and the next backup cannot make progress.

P11 — Operations are the product. retention, GC, verify, prune, list, dry-run restore, fsck, doctor are first-class, not afterthoughts. Tradeoff: the ops chapter is as long as the chunker chapter. Violating it: the system is unoperable at 3 a.m. and the data is effectively lost.

P12 — Reuse the lower ranks; do not re-implement. rank 109 owns chunking + content-addressing; rank 107 owns S3 signing/multipart; rank 108 owns optional parity. Tradeoff: a dependency edge per substrate. Violating it: re-implementing FastCDC or S3 sigv4 is a multi-week mistake that inherits none of their conformance.

Worked example. Source tree /data = a.txt (1 KB), bin/b.dat (10 KB), big.rnd (1 MB). Backup 1: FastCDC produces chunks C1 (a.txt), C2 (b.dat), C3..C6 (big.rnd). Stored delta ≈ one chunk, not the whole tree.

Malformed input. A manifest whose id != BLAKE3(body) (I4), whose signature fails (I3), or whose prost body fails to decode is rejected at load with MANIFEST_INVALID. A chunk whose decrypted plaintext does not hash to its key name (I1) raises CHUNK_HASH_MISMATCH. A truncated chunk (ciphertext shorter than the AEAD tag) raises CHUNK_TRUNCATED. An unknown aead enum value raises AEAD_UNSUPPORTED. A layout_version greater than the binary understands raises LAYOUT_TOO_NEW and refuses to operate.

Failure path. Mid-upload repo disconnect → transient error → journal retained → bks resume replays from last ChunkUploaded; already-present chunks are no-ops (content-addressed). Tag failure on open → CHUNK_CORRUPT(chunk_ref, manifest_id) surfaced, restore continues to surface all gaps rather than aborting on the first.

0.6 Pitfalls

  • The local head pointer tempts flock/fcntl advisory locks; resist — use rename-into-place (the atomic-rename POSIX guarantee), because the Phase-4 S3 backend cannot flock (ADR-15).
  • Fixed-size 1 MB chunks mean a 100-byte append to a 10 KB file changes that file's only chunk entirely; the Phase-0 dedup assertion therefore targets the unchanged files; Phase 2 swaps in FastCDC and extends the assertion.
  • Resist shipping encryption in Phase 0 — AeadAlgo::None is deliberately rejected by the Phase-3+ validator (I3) so it can never leak into production use.
  • A chunker bug that clamps every boundary to max silently degrades to "one chunk per file" and still passes a round-trip test — assert chunk count, not only byte equality.

0.7 Performance Concerns

  • Local repo PUT is dominated by the rename-into-place syscall pair (open+fsync+rename), not disk bandwidth at Phase-0 scale (§4 target ≥5 K ops/s small-chunk PUT, M7).
  • The fixed 1 MB chunker is CPU-cheap (no gear hash) but caps dedup granularity — do not mistake Phase-0 chunker throughput for the Phase-2 FastCDC target (≥1 GB/s/core, §4, M2).
  • Walker metadata reads are ignored at Phase 0 but still cost one stat() per entry; budget for the Phase-1 throughput target (≥1 M files/minute, M1) even though Phase 0 does not gate on it.
  • fsync on every chunk PUT is correct but the dominant cost at small chunk sizes; Phase 4's pack mode is the eventual lever, not something Phase 0 should attempt to optimize prematurely.

0.8 Edge Cases

  • Zero-byte source file (chunker must emit zero chunks, not a spurious empty chunk).
  • Empty source directory (TreeNode::Directory with an empty entries list).
  • A source path containing a .. component (walker must reject, not traverse outside source_root).
  • Two Phase-0 backups issued back-to-back with no lock manager yet built (Phase 8) — Phase 0 accepts the single-writer assumption explicitly and documents it as a known gap closed in Phase 8.

0.9 Failure Analysis

  • Crash before the head CAS write (I11): the manifest and chunks are already durable, only the pointer update is lost — the next bks backup free-runs and produces a fresh, correct manifest chain (no data loss, just a missed pointer advance, later detectable by fsck in Phase 12).
  • Disk-full mid-backup: RepoNoSpace surfaces at the failing PUT; partial chunks already written are inert (unreferenced, later GC-able once Phase 6 lands) and the backup is safely re-run after freeing space.
  • A corrupted local repo directory (wrong permissions, foreign owner) fails fast at the first PUT with a clear io::Error — Phase 0 does not yet wrap this in BksError::RepoUnavailable (Phase 4 formalizes the repo-error taxonomy surface).

0.10 Operational Notes

  • Hard-link detection by (dev,inode) is correct only within one FS (I9).

1.7 Performance Concerns

  • xattr/ACL reads add getxattr/listxattr syscalls per file beyond the base stat(); batch-read where the platform allows (llistxattr once, then one lgetxattr per name) to stay under the ≥1 M files/minute target (§4, M1).
  • Hard-link detection needs an O(1) (dev,inode) → first-path hashmap, not a linear scan, or throughput collapses on link-heavy trees.
  • The walker is a single-threaded lazy iterator by design (bound memory, not maximize throughput) — parallelizing it is a lever held in reserve, not exercised until profiling shows the walker (not the chunker) is the bottleneck.

1.8 Edge Cases

  • Symlink loops (self-referential or mutually cyclic) — detect via a visited-inode set, never recurse unbounded.
  • Sparse files with large holes — do not materialize zero-filled ranges, preserve the hole via SEEK_HOLE/SEEK_DATA at chunk time (Phase 2).
  • Directory nesting deep enough to threaten native recursion stack depth — walk iteratively with an explicit stack.
  • Case-insensitive-but-case-preserving layered file systems (macOS) producing two on-disk names that collide case-insensitively.

1.9 Failure Analysis

  • Partial metadata capture from EACCES on an xattr read: surfaced as a per-file warning, not a fatal error — the file's content still backs up.
  • A walker crash mid-traversal loses no already-written chunks (content-addressed, safely re-uploaded) but leaves no partial manifest since the manifest is built only after the full tree completes (Phase 0.2).
  • A TOCTOU race between stat() and open() (file replaced between calls) surfaces as a short read or ENOENT, logged and skipped rather than corrupting the tree with mismatched size/content.

1.10 Operational Notes

bks_walk_files_total, bks_walk_seconds, a counter for files the walker could not open O_NOATIME; metadata-ordering documented in docs/architecture/; no rollback/migration surface yet (walker output format is internal to the backup run, not persisted independently).

Phase 2 — FastCDC chunker (rank 109) and the chunk index (Week 3)

2.1 Objectives

Swap the Phase-0 fixed-size chunker for rank 109's FastCDC and wire the chunk index that makes incremental backup fast. Prove a single insert into a large file re-uploads ≤ 10% of that file's chunks.

2.2 Detailed Implementation Steps

FastCDC (Xia 2016, §5 ref 16; ADR-02) supplies gear-hash content-defined boundaries; BLAKE3 content addressing (ADR-03; P1) names each chunk; the index is advisory, never authoritative (I5). 2.6 Pitfalls

  • The index is an availability concern, not a correctness one — do not over-engineer cache coherence (I5).
  • Index upload must be atomic (.tmp+rename); a crashed backup leaves a .tmp the next start sweeps.
  • FastCDC parameters are sensitive: smaller chunks improve dedup at the cost of index size; benchmark, do not tune blindly.

2.7 Performance Concerns

  • The gear-hash rolling computation is per-byte and must stay cache-resident (small gear table, sequential scan) to hold ≥ 1 GB/s/core (§4, M2).
  • InMemoryChunkIndex resizing a HashSet at scale causes allocation-spike stalls — pre-size for the expected chunk count from the Back-of-Envelope Capacity Model (#2).
  • Index lookup sits on the backup hot path; the disk-backed variant fronts every lookup with a Bloom filter specifically to avoid a syscall per chunk at repositories beyond ~50 M chunks (Scalability Analysis).

2.8 Edge Cases

  • Zero-byte and all-zero-byte files (the latter produces many identical chunks — an intentional dedup stress case, not a hash-collision bug).
  • FastCDC boundary clamping at file start/end (first/last chunk may be shorter than min).
  • A pathological byte pattern that repeatedly hits the gear hash's mask boundary, producing worst-case max-size (4 MB) chunks.
  • An index snapshot larger than available memory on load (falls back to streaming load into DiskChunkIndex).

2.9 Failure Analysis

  • A corrupt or lost chunk index is always safe to discard and rebuild from an empty index — worst case is a full re-upload pass, not data loss (I5).
  • An index upload interrupted mid-transfer leaves the previous index as the most recent valid one, so a fresh client never sees a torn index.
  • Chunk-count growth past the in-memory index's ~1 GB/10 M-entry budget (§4) degrades from an availability problem (slow dedup) to a correctness-adjacent one only if ignored past the DiskChunkIndex switchover trigger documented in Scalability Analysis.

2.10 Operational Notes

Phase 3 — Key derivation, AEAD, and the encrypted backup path (Week 4-5)

3.1 Objectives

Turn the plaintext Phase-2 backup into an encrypted one: passphrase → Argon2id master key → HKDF purpose keys → per-chunk XChaCha20-Poly1305 → signed manifest. Establish I2 and I12.

3.2 Detailed Implementation Steps

Argon2id (§5 ref 13, ADR-10), HKDF (§5 ref 14, ADR-11), XChaCha20-Poly1305 (§5 refs 11–12, ADR-07), and Ed25519 (§5 ref 15, ADR-05) compose into the key hierarchy that enforces P3. Types (crates/bks-crypto/src, normative derivations in Appendix C): fn derive_master(passphrase, salt: [u8;32], params: Argon2Params) -> Result<MasterKey> with Argon2Params { m_cost, t_cost, p_cost } (default 256 MiB, 4, 1); fn chunk_key/chunk_nonce(master, chunk: ChunkRef, epoch: u64) -> ChunkKey/ChunkNonce; fn manifest_key/sign_key(master, version: KeyVersion) -> ManifestKey/ManifestSignKey; fn seal(key, nonce, plaintext, aad) -> Result<Vec<u8>> (ct‖tag) and fn open(key, nonce, ciphertext, aad) -> Result<Vec<u8>> (Err on auth fail). HKDF info labels: "bks.chunk.key/v1", "bks.chunk.nonce/v1", "bks.manifest.key/v1", "bks.manifest.sign/v1"; chunk aad = chunk_ref ‖ epoch.to_be_bytes() ‖ aead_algo.to_be_bytes() (I12). Implementation: the salt is 32 random bytes at keys/<version>/salt, params at keys/<version>/params; after the Phase-2 chunker emits (chunk_ref, plaintext), derive key + nonce, build aad, seal, PUT the ciphertext (embeds the tag) under chunks/<aa>/<rest> — the chunk_ref is BLAKE3 of the plaintext, never the ciphertext, which is what makes dedup work and why two repos with different master keys store the same chunk_ref under different ciphertexts; restore derives key+nonce, opens, and an open failure is CHUNK_CORRUPT with chunk_ref + manifest_id; the manifest body is prost-encoded, id = BLAKE3(body), signature = Ed25519_sign(sign_key, body), and a bad signature is rejected at load (I3).

3.6 Pitfalls

  • Nonce derivation is the most dangerous step: deriving the same nonce on the same (chunk_ref, epoch) is fine (deterministic, identical output) but two distinct pairs colliding would be catastrophic — I2 asserts they never do.
  • Storing the ciphertext under a ciphertext-derived key would destroy dedup (every ciphertext is unique).
  • The known-plaintext-existence surface (an attacker hashing P to check membership) is inherent to any content-addressed system; accepted at single-repo scope, mitigated cross-tenant by per-repository salts (ADR-09).
  • Argon2id parameters are an operator knob documented in docs/threat-model.md.

3.7 Performance Concerns

  • Argon2id's deliberate 1–2 s cost (§4, M8) must never sit on the per-chunk hot path — derive the master key once per session, not per chunk.
  • HKDF is called twice per chunk (key + nonce); batch the two expands from one extracted PRK rather than re-extracting per call.
  • seal/open should operate on borrowed buffers, not clone plaintext/ciphertext, to hold the ≥1.5 GB/s/core encrypt target (§4, M4) — a streaming AEAD API (no full-buffer copy) is the lever if profiling shows allocation dominating.

3.8 Edge Cases

  • Two distinct (chunk_ref, epoch) pairs producing the same derived nonce (I2; astronomically unlikely under HKDF-SHA256, still asserted by property test, never merely assumed).
  • A passphrase rotated mid-backup (the in-flight backup must finish under the epoch/version it started with, not straddle two).
  • Multiple key epochs used concurrently by overlapping backups of different sources.
  • A truncated ciphertext shorter than the AEAD tag length (CHUNK_TRUNCATED, distinct from a tag-mismatch CHUNK_CORRUPT).

3.9 Failure Analysis

  • A tag-verification failure is classified precisely: CHUNK_CORRUPT (right size, wrong tag — bit rot or tamper) vs ChunkMissing (repository 404) vs AeadUnsupported (unknown algo byte) — conflating them hides the root cause from the operator.
  • Supplying the wrong key version at restore fails every open in the manifest, not just one — surfaced as a bulk CHUNK_CORRUPT burst that should immediately point the operator at "wrong key version" rather than "corrupted repository" (Phase 12's doctor heuristic).
  • An Argon2id parameter downgrade (an attacker forcing weaker params) is rejected because params are recorded per key version and the loader refuses a params record weaker than the repository's configured floor.

3.10 Operational Notes

bks_chunk_encrypt_seconds{aead}, bks_chunk_decrypt_seconds{aead}, bks_manifest_verify_total{outcome}, bks_master_derive_seconds; no rollback needed for this phase (encryption is additive over Phase 0–2's plaintext path, gated by AeadAlgo); key-version compatibility across upgrades is formalized in Compatibility & Versioning.

  • S3 429 (Slow Down) triggers exponential backoff and resume from the journal (Phase 8), not a full restart — bounded by the ≥99.5% success failure budget (§4, M14).

  • Credential expiry mid-backup (short-lived STS tokens) is detected at the first failing signed request and surfaced distinctly from a permissions error so the operator refreshes credentials rather than investigating IAM policy.
  • Abandoned multipart uploads accumulate storage cost silently unless the GC-driven abort sweep (Phase 6) runs on schedule — document the cost-monitoring runbook entry.

5.8 Edge Cases

  • A manifest referencing a TreeNodeId never written (partial upload interrupted before all tree nodes landed) — restore must surface ChunkMissing-equivalent for the tree node, not panic.
  • A BLAKE3 collision producing two distinct bodies with the same TreeNodeId (treated as cryptographically impossible, still guarded by I4's exact-body-hash re-check).
  • A parent chain deep enough that a naive recursive walk risks stack overflow — the chain walker is iterative, not recursive.
  • created_at timestamps out of order across a chain due to clock skew (retention bucketing falls back to creation order per F6, not wall-clock order).

5.9 Failure Analysis

  • A broken parent chain (an intermediate manifest lost or GC'd out of turn) is detected by the chain walker failing to resolve a parent id; blast radius is bounded to restores requesting history before the break, not the latest manifest itself.
  • A signature-verification failure at load poisons only that one manifest — the loader rejects it and the caller falls back to an older manifest or a replica (Phase 11), never propagating a bad manifest into a restore.
  • Clock-skew-induced created_at anomalies are cosmetic (retention bucketing is defined to tolerate them, F6) and never a correctness hazard because ordering for chaining uses the explicit parent pointer, not timestamps.

6.7 Performance Concerns

  • The mark phase is O(live_chunks) tree-node fetches — IO-amplified relative to the chunk count itself since every retained manifest's full tree is walked, not diffed against siblings.
  • The sweep's list("chunks/") is O(total_chunks) and paginated on S3, dominating GC wall-time at high chunk counts (Scalability Analysis).

6.8 Edge Cases

  • Two backups landing in the same retention bucket on the same day (tie-break: keep the most recent created_at, drop the earlier).
  • GC racing a prune that has already computed its own live set (must re-run mark, not reuse a stale set, if any backup landed in between).
  • A manifest with a broken parent chain encountered during mark (walk what resolves, log the break, do not abort the whole mark).
  • An operator retention policy that would retain zero manifests (empty retained set) — GC must refuse to run rather than silently deleting every chunk in the repository.

6.9 Failure Analysis

  • A GC that crashes mid-mark leaves no partial live set committed anywhere — the next GC invocation starts mark from scratch, so a partial mark is never unsafe to abandon.
  • A GC that crashes mid-sweep has already deleted only chunks it had already determined were not live; re-running mark+sweep is idempotent and safe (I8) because deletes are keyed on the (recomputed) live/dead partition, not on a resumable cursor.
  • A misconfigured retention policy that would retain zero manifests is treated as an operator error requiring explicit confirmation (Edge Cases), not executed silently — the blast radius of silently accepting it is total data loss.

6.10 Operational Notes

Phase 7 — Verify, prune, and the integrity story (Week 9-10)

7.1 Objectives

7.6 Pitfalls

  • Verify is bandwidth-expensive — a 1 PB repo at 1 GB/s takes ~12 days; document sampling.
  • Verify does not auto-repair (no second copy outside multi-site, Phase 11); recourse is restore from an older backup not referencing the corrupt chunk (bks chain --excluding <chunk_ref>).

7.7 Performance Concerns

  • Full verify is bandwidth-bound (§4, M11: ≥1 GB/s aggregate target), so parallel chunk fetch fan-out (bounded by the FD budget, §4) is the primary lever to hold the 25-minute/100 GB target.
  • Sampling trades detection probability for a linear cost reduction (Back-of-Envelope Capacity Model #7).
  • Prune's cost is dominated by GC's mark+sweep (Phase 6 Performance Concerns), not by the retention computation itself, which is O(manifest count) and cheap at any realistic scale.

7.8 Edge Cases

  • A network drop mid-verify leaves a partial VerifyReport — the CLI must report "incomplete: N of M chunks checked", never claim a clean bill of integrity from a partial scan.
  • verify --sample unluckily never selecting the one corrupt chunk in a large repo (a known, documented statistical limit, not a bug — the sample rate is chosen against an acceptable miss probability).
  • A prune --dry-run followed by state-changing operations (a concurrent backup) before the real commit, so the dry-run's reported set may go stale — document that --dry-run is advisory, not a lock-held preview.

7.9 Failure Analysis

  • Verify discovering corruption across many chunks (beyond an isolated bit-flip) escalates from a routine finding to an incident — the runbook (Operational Readiness #2) directs the operator to bks chain --excluding and a broader storage-media health check, not a single-chunk fix.
  • Prune deleting a manifest that a concurrent restore is mid-read on is prevented by retention/GC being lock-gated (I6, Phase 8) against backup, but restore itself does not hold the GC lock — a race window exists and is documented: a restore reading a manifest GC has just pruned fails cleanly with ManifestMissing, retried against a still-retained manifest, rather than corrupting the restored tree.

Phase 8 — Concurrency, the lock manager, and the journal (Week 10-11)

8.1 Objectives

Add the concurrency primitives that make multi-host operations safe: a TTL-fenced repo lock (I6) and a replayable per-backup journal (I11).

8.2 Detailed Implementation Steps

8.6 Pitfalls

  • The TTL must exceed the longest backup window or it expires mid-backup and two backups race — renew at half the TTL.
  • Journal events must be idempotent on replay.
  • The lock is only as strong as the backend's put_if_match: S3 If-Match is strong, SFTP/local emulate via rename-into-place — the trait documents the required semantics and every backend passes the lock_manager bucket.

8.7 Performance Concerns

  • Lock renewal at half the TTL trades heartbeat overhead against fencing latency — too-frequent renewal wastes a round trip per interval, too-infrequent risks a false expiry under transient repo slowness.
  • Tune TTL against the §4 backup e2e target (30 min/100 GB) with margin.
  • Journal writes are one event per chunk by default, which is write-amplifying at high chunk counts — batching multiple ChunkUploaded events into one flush is the lever if journal-write overhead measurably slows the backup hot path.

8.8 Edge Cases

  • Lock TTL expiring at the exact moment of a renewal attempt (race between the renewal's put_if_match and another process's fencing overwrite — the loser's renewal fails IfMatch and that process must abort, not assume it still holds the lock).
  • Two processes both observing an expired lock and both attempting takeover (only one put_if_match wins; the other retries against the new holder).
  • A journal replay encountering an event referencing a chunk already GC'd (should be impossible under correct lock discipline — Phase 8 treats this as a lock-invariant violation to alert on, not silently paper over).

8.9 Failure Analysis

  • Split-brain — two hosts both believing they hold the repo lock — is structurally prevented by the backend's conditional-write guarantee (I6); if it is ever observed, it indicates a backend put_if_match semantics violation and is treated as a release-blocking defect, not routine.
  • Journal corruption (a truncated or malformed event record) preventing resume falls back to a fresh full backup rather than a doomed partial-replay attempt — bounded blast radius is one extra full-backup cost, not data loss, since already-uploaded chunks are content-addressed and re-referenced for free.
  • A crashed lock holder's TTL expiry is the sole recovery path — there is no manual "force unlock" that bypasses fencing, by design (P10).

8.10 Operational Notes

bks_lock_acquire_seconds{purpose}, bks_lock_holder_age_seconds, lock-conflict counter, journal-replay counter; the runbook "GC ran concurrently with a backup" (Operational Readiness #3) is this phase's primary on-call reference.

Phase 9 — Snapshot drivers: Btrfs, ZFS, LVM, fsfreeze (Week 11-14)

9.1 Objectives

9.2 Detailed Implementation Steps

Types (crates/bks-snapshot/src, trait in §11.6): BtrfsDriver, ZfsDriver, LvmDriver, FsfreezeDriver, LiveWalkDriver, each implementing SnapshotDriver { async fn snapshot(..) -> Result<SnapshotHandle>; async fn release(..) -> Result<()>; }. 9.6 Pitfalls

  • A Btrfs snapshot is read-only; a writable one is a clone and is not what backup needs — verify RDONLY.
  • ZFS zfs destroy is permanent; hold the snapshot until the backup completes, release in finally.
  • FIFREEZE blocks writers; a frozen mount past the Linux dirty-flush deadline (~5 min) is a serious hazard — complete within the TTL or surface a clear error.

9.7 Performance Concerns

  • Snapshot creation latency must fit comfortably ahead of any freeze window budget — Btrfs/ZFS CoW snapshots are O(1) metadata operations (≤1 s target), while lvcreate -s allocates thin-pool metadata and is measurably slower (≤5 s target).
  • Walking a mounted snapshot vs. the live tree adds no meaningful walker overhead (same code path, Phase 1), but bind-mounting the snapshot for the walker to traverse costs one extra mount/unmount pair per backup.

9.8 Edge Cases

  • A snapshot request racing another in-flight snapshot on the same CoW pool (busy-pool error, retried with backoff, not treated as fatal).
  • The fsfreeze window exceeding the dirty-flush deadline mid-walk (abort cleanly, FITHAW, surface SnapshotDriverError, never leave the mount frozen).
  • A nested "snapshot of a snapshot" request (rejected — drivers operate only on primary sources).
  • A source root that is not on any snapshot-capable file system and has no driver configured (falls through to LiveWalkDriver by explicit auto-detection order, never silently to an incorrect driver).

9.9 Failure Analysis

  • fsfreeze thaw failure (a stuck frozen file system) is a host-availability incident, not a backup-correctness one — the runbook requires an operator-triggered manual FITHAW retry and, if that fails, treats it as equivalent to a hung write path requiring host intervention; document this explicitly since a stuck freeze can outage-impact unrelated processes on the same mount.
  • A ZFS zfs destroy failing because of a lingering clone or hold leaks a snapshot (storage cost, not data risk) until the hold is manually cleared — surfaced by bks_snapshot_release_seconds spiking (F10).
  • A PostgreSQL pg_backup_stop failing after the freeze already succeeded must still release the freeze in a finally-equivalent path — never leave the database in backup mode because the release step errored.

9.10 Operational Notes

Phase 10 — Key rotation and the rekey path (Week 14-15)

10.1 Objectives

Make the cryptographic story long-term: rotate keys (protect future backups) and rekey (re-encrypt past backups), with old key versions archived.

10.6 Pitfalls

  • Rotation does not invalidate the old key — an attacker with it still decrypts old backups; rotation protects future, rekey protects past.
  • A rekey'd manifest gets a new id and a rewritten parent chain (100 manifests → 100 new); the old chain is left to retention.
  • The KMS integration is the load-bearing escape hatch; AWS-KMS lacks Ed25519 (ADR-05 open), so signing-key export there needs P256.

10.7 Performance Concerns

  • Rekey throughput is bounded by a double AEAD pass (decrypt under old key, encrypt under new) per chunk, so it runs at roughly half the single-pass encrypt rate (§4, M4) — document this expectation rather than treat it as a regression.
  • KMS unseal is a network round trip on the restore critical path; cache the unsealed master key for the duration of one restore/rekey session rather than re-unsealing per chunk.
  • Bulk rekey across many manifests multiplies the parent-chain rewrite cost linearly with backup count — batch-schedule large rekeys during low-traffic windows.

10.8 Edge Cases

  • rotate invoked concurrently with an in-flight backup (the backup must finish under the key version it started with — no straddling).
  • rekey interrupted mid-chain (a partial new chain with some manifests rekeyed and some not — the un-rekeyed tail is unaffected and rekey is safely re-run, content-addressed chunks make re-encryption idempotent per manifest).
  • KMS unavailable during unseal (restore blocks with a clear KMS_UNAVAILABLE error, not a silent hang).
  • A compromised key discovered several rotations after the fact (rekey must cover every affected version's manifests, not just the most recent).

10.9 Failure Analysis

  • A compromise detected after multiple rotations requires rekeying across every affected key version's manifest set — rekeying only the latest version leaves older, still-compromised-key manifests exposed (MM8).
  • The runbook (Operational Readiness #4) enumerates the full sequence: rotate → rekey --all → archive old key metadata offline → GC → verify --all.
  • A rekey producing a manifest chain whose chunk set diverges from GC's already-computed live set requires GC's mark phase to re-run before any sweep — treating a stale live set as valid after a rekey risks deleting chunks the new chain still references.

10.10 Operational Notes

bks_key_rotate_total, bks_rekey_chunks_total, bks_rekey_seconds, KMS-unseal latency histogram; docs/runbook/key-rotation.md is the canonical post-compromise procedure referenced by Operational Readiness #4.

  • A RepoId mismatch discovered only after some chunks have already been written (the guard must check and reject before any write, not after a partial, inconsistent transfer has begun).

11.9 Failure Analysis

  • Destination corruption is invisible until a restore or verify is attempted against dst — replication itself does not re-verify already-present chunks it skips, so a scheduled verify --repo <dst> (Phase 7) is the operational safety net, not an implicit guarantee of this phase.
  • Replicating a rekeyed source (Phase 10) after mirrors have diverged produces two valid but different chain histories on src and dst — documented as an unsupported combination requiring a fresh full replication rather than an incremental reconciliation.

Operations Runbook (index)

  1. Backup failed mid-way: inspect failed counter → trace_id → failing span; S3_RATE_LIMITED/S3_TIMEOUT → bks resume; REPO_LOCK_HELD → wait/coordinate.
  2. Restore reports a corrupt chunk: read chunk_ref+manifest from the error; bks verify <manifest>; bks chain <manifest> to list referencing manifests; find alternate source (replica/older backup); else document data loss; bks gc after pruning affected manifests.
  3. GC ran concurrently with a backup: inspect the journal; if last event is BackupComplete, nothing to do; if ChunkUploaded and GC swept it, bks verify; the lock should have prevented it — if not, file a CVE-class issue; restore from a manifest not referencing the deleted chunk.
  4. Key rotation post-compromise: bks key rotate --new-passphrase; bks rekey --all; archive old key metadata offline; bks gc; bks verify --all.
  5. Repository migration (local → S3): stand up the dst bucket; bks replicate --src file://... --dst s3://...; bks verify --all --repo s3://...; repoint the daemon; fresh backup to confirm.

Compatibility & Versioning

The wire/storage formats are versioned independently of the binary:

  • Manifest schema version (manifest.proto field schema_version): incremented on backwards-incompatible changes. A 1.0.0 binary reads every 0.x manifest and writes a 1.0.0 manifest.
  • Repository layout version (config.toml field layout_version, fixed at 1): incremented on layout changes; the daemon negotiates at open and refuses a future layout it does not understand (LAYOUT_TOO_NEW).
  • Chunk encryption scheme version: tied to the manifest aead field; old backups verify under their original AEAD; new backups use the configured one. The aad binding (I12) prevents cross-algo substitution.
  • Cryptographic agility: a future AeadAlgo::Ascon128 can be added without breaking old backups (ADR-25 region; see Deferred Features Register).
  • Release cadence: 0.1.x Phase 0; 0.2.x Phases 1–2; 0.3.x Phase 3; 0.4.x Phase 4; 0.5.x Phases 5–6; 0.6.x Phases 7–8; 0.7.x Phase 9; 0.8.x Phase 10; 0.9.x Phase 11; 1.0.x Phase 12 + stable-API commitment. Each release is a git tag; release.yml builds reproducible binaries.
  • ADR discipline: every §9 decision has a docs/adr/ file; new decisions land Proposed → Accepted/Rejected; an Accepted ADR may be Deprecated with a pointer to its replacement.

Scalability Analysis

  • Chunk count vs. index memory. The in-memory index is O(unique_chunks); at ~32 B/ChunkRef plus HashSet overhead (~48 B/entry effective), 10 M chunks ≈ 480 MB, 100 M ≈ 4.8 GB. Past ~50 M unique chunks the Bloom-fronted disk index (ADR-14-adjacent) is mandatory to stay under the §4 1.5 GB budget.
  • Files vs. tree depth. The Merkle-tree manifest makes single-file restore O(log N) tree fetches; a 100 M-file backup with average fan-out 100 has depth ~4, so single-file restore is ~5 GETs regardless of total size.
  • Backup time vs. delta. Incremental backup time is O(changed_bytes / chunker_throughput + new_chunks × PUT_latency), not O(repo_size). A 1 GB daily delta on a 10 TB repo backs up in minutes.
  • GC time vs. chunk count. Mark is O(live_chunks) tree walks; sweep is O(total_chunks) list + rate-capped deletes. At 100/s delete rate, sweeping 1 M garbage chunks takes ~2.8 h — pack-mode delete (one object per pack) is the lever to raise this.
  • S3 request scaling. Per-chunk objects scale request count with chunk count; pack files collapse 100 chunks to ~1 PUT, shifting the bound from request-rate to bandwidth.
  • Replication vs. delta. SnapVault incremental is O(new_chunks) transfer, independent of repository size — multi-site stays viable as the primary grows.
  • Concurrency ceiling. One backup per repo (lock-gated, I6); horizontal scale is across repos/sources, not within one repo. A multi-host orchestrator (rank 39 Raft, deferred) coordinates many repos.

Mental Models & First Principles

MM1 — The hash is the address. A chunk's name is the hash of its content, so equal content is automatically one object and corruption is detectable at read time. Predicts: dedup and bit-rot detection fall out for free. Bug class without it: trusting storage and shipping silently-corrupt restores. Applied: P1, I1, Phase 2–3.

MM2 — Make misuse impossible, not merely discouraged. Derive the nonce from the chunk id + epoch instead of asking engineers to manage nonces. Predicts: the entire class of nonce-reuse CVEs cannot occur. Bug class without it: catastrophic AEAD nonce reuse. Applied: P3, I2, Phase 3.

MM3 — One mutable pointer, everything else immutable. Only the head pointer changes; chunks, trees, manifests are append-only. Predicts: concurrency reduces to a single CAS; GC is mark-sweep. Bug class without it: lost updates and torn manifests under concurrency. Applied: P4, I6, Phase 5/8.

MM4 — Separate the consistent view from the copy. Snapshot first, then walk the snapshot. Predicts: live databases back up cleanly without quiescing the application for the whole walk. Bug class without it: torn, unrestorable database backups. Applied: P2, Phase 9.

MM5 — Advisory caches, authoritative storage. The chunk index can be wrong; the repository's content addressing is the truth. Predicts: you can lose/rebuild the index with at worst a re-upload. Bug class without it: over-engineered cache-coherence machinery and data-loss from a "missing" decrement. Applied: I5, Phase 2/6.

MM6 — Reclamation is liveness, not refcounting. Compute the live set from retained manifests and delete the complement. Predicts: a crashed GC is always safe to re-run. Bug class without it: refcount leaks and double-frees. Applied: P7, I8, Phase 6.

MM7 — Verify what you will rely on, end to end. A backup is only as good as its last successful verify. Predicts: corruption is found on a schedule, not during a 3 a.m. restore. Bug class without it: discovering an unreadable backup at the worst time. Applied: P8, Phase 7.

MM8 — Rotation and rekey are different verbs. Rotation protects future data; rekey re-encrypts past data. Predicts: the correct response to a key compromise. Bug class without it: believing rotation alone protects old backups. Applied: Phase 10, T3.

MM9 — The bound that matters is the delta, not the size. Incremental backup, GC mark, and replication scale with change, not total bytes. Predicts: the system stays usable at 100 TB with daily small deltas. Bug class without it: O(repo_size) operations that stop completing. Applied: Scalability Analysis, Phase 11.

MM10 — Bind context into the ciphertext. The aad binds chunk_ref ‖ epoch ‖ algo. Predicts: swapping or re-labelling a chunk fails authentication. Bug class without it: chunk-substitution and cross-algo downgrade attacks. Applied: I12, T5, Phase 3.

ZFS snapshots put copy-on-write inside the file system, so snapshots are O(1) and free of any external coordination — it wins on a single host where you control the pool and want instant, cheap, application-transparent snapshots, but it cannot back up to arbitrary object storage or across heterogeneous file systems.

restic chose a single per-repository key with random nonces and SHA-256 addressing for simplicity and a huge backend matrix — it wins for cross-platform, many-backend simplicity, but accepts a more fragile nonce story than our per-chunk derived nonce (P3).

BorgBackup chose a stateful local cache and segment files with an explicit lock manager, optimising single-machine repeated backups — it wins for one host backing up to one repo very fast, but its single-machine cache assumption makes the pure object-storage story harder than our stateless-client design.

Veeam chose changed-block tracking and VSS integration at the hypervisor/OS layer, optimising VM image backup — it wins for enterprise VM estates with agentless image-level backup, but it is a closed proprietary format with no chunk-by-chunk audit trail, which is exactly the auditability we build for (§2).

Back-of-Envelope Capacity Model

Each number is derived from the §4 System Constraints table; formulas shown.

  1. Single-core encrypt ceiling. AEAD encrypt = 1.5 GB/s/core (§4). One 100 GB backup, encrypt-bound: 100 GB / 1.5 GB/s ≈ 67 s of pure crypto.
  2. Chunk count for 100 GB. avg chunk = 1 MB (§4 chunker default). 100 GB / 1 MB = 102,400 chunks — matches the "100 K chunks" e2e target.
  3. Per-chunk S3 PUT time. S3 small-chunk PUT = 500 ops/s (§4). 102,400 / 500 = 205 s of PUT-time if unpacked — already a fifth of the 30-min budget, motivating packs.
  4. Packed PUT time. Pack = 32 MB (Phase 4). 100 GB / 32 MB = 3,200 packs; at 500 MB/s/connection (§4), 100 GB / 0.5 GB/s = 200 s bandwidth-bound — same order, but request count drops 32×.
  5. Index memory at 10 M chunks. ~48 B effective/entry (§4 ≤1.5 GB budget): 10 M × 48 B = 480 MB — under budget; 100 M ≈ 4.8 GB ⇒ disk index required.
  6. Argon2id wall cost. m=256 MiB, t=4 (§4): 1–2 s per derivation ⇒ a brute-forcer doing 10⁶ guesses needs ~10⁶ × 1.5 s ≈ 17 days per core, the deliberate cost of P3/ADR-10.
  7. Verify time for 1 PB. Verify e2e ∝ throughput; at 1 GB/s aggregate: 1 PB / 1 GB/s = 10⁶ s ≈ 11.6 days ⇒ sampled verify is mandatory (Phase 7).
  8. GC sweep at 100/s. 1 M garbage chunks (§4 GC sweep ≤5 min target assumes packs): unpacked 1 M / 100 = 10⁴ s ≈ 2.8 h ⇒ pack-delete or higher rate needed to hit 5 min.
  9. RTO bandwidth. RTO ≤ 4 h for 1 TB (§4): required restore bandwidth 1 TB / 4 h ≈ 72 MB/s — comfortably under the 25-min/100 GB target (≈68 MB/s sustained), consistent.
  10. Daily delta backup time. 1% daily change on 1 TB = 10 GB new; encrypt-bound 10 GB / 1.5 GB/s ≈ 7 s plus 10,240 chunks / 500 PUT/s ≈ 20 s ⇒ ~30 s, validating MM9 (delta-bound, not size-bound).
  11. FD budget headroom. ≤1024 FDs (§4): one source file + bounded repo connections (say 64) leaves ~950 FDs ⇒ no FD pressure at default concurrency.
  12. Failure budget math. ≥99.5% success (§4) over 365 daily runs allows 365 × 0.005 ≈ 1.8 failed runs/year before breaching budget ⇒ resumability (F1) must cover virtually all transient errors.

Alternative Architectures (Roads Not Taken)

A1 — In-filesystem CoW only (ZFS/Btrfs-native).

[ app ] -> [ ZFS pool : snapshot @t1, @t2 ... ] -> zfs send -> [ remote pool ]

Wins when you own a single host/pool, want instant transparent snapshots, and never need arbitrary object storage. Embodied by ZFS snapshots + zfs send. Rejected because it cannot target heterogeneous backends (S3/SFTP), cannot encrypt per-chunk for an untrusted backend, and offers no cross-host content dedup — our §1 scope requires pluggable, encrypted, cloud-resident repositories (P5, P3).

A2 — Full-image, changed-block tracking.

[ VM / block device ] -> [ CBT bitmap ] -> [ full image + incremental block deltas ]

Wins for VM estates where the unit of backup is a disk image and the hypervisor exposes changed blocks. Embodied by Veeam / LVM snapshot images. Rejected because it backs up opaque block ranges, not files — no per-file restore, no file-level dedup across hosts, and no chunk-by-chunk audit trail (§2). We back up file systems (Out of Scope #4).

A3 — Reference-counted chunk store.

[ backup ] -> chunk.refcount++ ; [ prune ] -> chunk.refcount-- ; refcount==0 -> delete

Wins for very high-churn repositories where a full mark-sweep list+walk is too expensive to run often. Embodied by content stores using refcounted GC. Rejected (ADR-17, P7, MM6) because a single missed increment is data loss and a missed decrement is a leak; for archival workloads the robustness of mark-sweep beats the efficiency of refcounting.

A4 — Convergent (cross-tenant) encryption.

key = H(plaintext) ; ct = Enc(key, plaintext) ; addr = H(ct)  -> identical plaintext dedups across tenants

Wins for a single trusted tenant wanting maximal dedup across many repositories of overlapping data. Embodied by convergent-encryption backup systems (Storer 2008 lineage). Rejected (ADR-09, T7) because it lets anyone holding plaintext P prove P exists in any tenant's repository — an unacceptable cross-tenant leak; we use per-repository salts and accept only intra-repository dedup.

Glossary

  • AEAD — Authenticated Encryption with Associated Data; encrypts and authenticates ciphertext plus associated data.
  • aad — Additional Authenticated Data; here chunk_ref ‖ epoch ‖ aead_algo, binding ciphertext to context (I12).
  • Append-only — written once, never modified; all objects except head/lock pointers are append-only.
  • Argon2id — memory-hard passphrase KDF (Biryukov 2016); passphrase → master key.
  • BLAKE3 — fast Merkle-tree-friendly cryptographic hash; the content-addressing primitive.
  • Btrfs — Linux CoW file system; one snapshot driver source.
  • Chunk — a content-defined slice of a file, named by BLAKE3 of its plaintext.
  • ChunkRef — the 32-byte BLAKE3 hash of a chunk's plaintext; its repository address.
  • Chunk index — advisory local set of known chunk_refs; speeds dedup (I5).
  • CDC — Content-Defined Chunking; boundaries chosen by content so inserts shift few chunks.
  • Content addressing — naming an object by the hash of its contents.
  • CoW — Copy-on-write; enables O(1) snapshots.

Appendix C — Cryptographic Derivation Reference

Normative definition of every key and nonce derivation. Every test vector in conformance/corpora/crypto/ references this appendix.

C.1 Master key

salt        = 32 random bytes, stored at keys/<version>/salt
params      = { m_cost: 256*1024, t_cost: 4, p_cost: 1, output_len: 32 }
master_key  = Argon2id(passphrase, salt, params)            // 32 bytes

C.2 Chunk key and nonce

info_key    = "bks.chunk.key/v1"   || chunk_ref || epoch.to_be_bytes()
info_nonce  = "bks.chunk.nonce/v1" || chunk_ref || epoch.to_be_bytes()
chunk_key   = HKDF-SHA256-Expand(master_key, info_key,   length = 32)
chunk_nonce = HKDF-SHA256-Expand(master_key, info_nonce, length = 24)

C.3 Manifest key and signing key

info_mk     = "bks.manifest.key/v1"  || key_version.to_be_bytes()
info_sk     = "bks.manifest.sign/v1" || key_version.to_be_bytes()
manifest_key       = HKDF-SHA256-Expand(master_key, info_mk, length = 32)
sign_seed          = HKDF-SHA256-Expand(master_key, info_sk, length = 32)
(sign_pk, sign_sk) = Ed25519::keypair_from_seed(sign_seed)   // sign_pk -> keys/<version>/sign_pk; sign_sk never persisted

C.4 AEAD seal / open

aad        = chunk_ref || epoch.to_be_bytes() || aead_algo.to_be_bytes()  // aead_algo: 0=None 1=XChaCha20Poly1305 2=Aes256GcmSiv
ct_with_tag = XChaCha20Poly1305::seal(chunk_key, chunk_nonce, chunk_bytes, aad)
plaintext   = XChaCha20Poly1305::open(chunk_key, chunk_nonce, ct_with_tag, aad)   // Err(TagMismatch) on tamper

C.5 Manifest signature

body         = prost::encode(Manifest { id: 0, signature: blank, ...rest })
manifest_id  = BLAKE3(body)
body_with_id = prost::encode(Manifest { id: manifest_id, signature: blank, ...rest })
signature    = Ed25519::sign(sign_sk, body_with_id)
stored_object = body_with_id || signature

The id is part of the signed body (I4); storing it outside would let an attacker repoint it.

C.6 Test vectors. conformance/corpora/crypto/ includes: RFC 8439 ChaCha20/Poly1305 vectors adapted for XChaCha20; Argon2 reference vectors; HKDF-SHA256 (RFC 5869); Ed25519 (RFC 8032); and a 1024-row (chunk_ref, epoch) → (chunk_key, chunk_nonce) table under a fixed master key for byte-equality re-derivation.

Appendix D — Repository Layout Reference

On-storage layout for every backend (local/S3/SFTP), identical modulo syntactic differences. layout_version = 1.

<repo-root>/
|-- config.toml                     # layout_version, default aead, repo_id
|-- keys/
|   |-- 1/ { salt, params, sign_pk, aead, sealed? }   # key version 1
|   |-- 2/ ...                                          # after rotation
|   `-- current                     # pointer: current key version number
|-- chunks/
|   |-- 00/ 00aa...                 # XChaCha20Poly1305(plaintext) || tag
|   |-- ...                         # 256-way first-byte fan-out
|   `-- ff/
|-- manifests/
|   |-- <manifest-id>               # prost body || Ed25519 signature
|   `-- trees/ <tree-node-id>       # prost TreeNode body
|-- heads/ <source-root-hash>       # pointer: current manifest_id (etag CAS)
|-- indexes/ <repo-id>/ <timestamp> # serialized chunk index (advisory, I5)
|-- locks/ { repo.lock, gc.lock }   # exclusive locks (etag CAS, I6)
|-- packs/ { <pack-id>, <pack-id>.idx }  # optional pack storage (Phase 4)
`-- backups/ <backup-id>/ { events/<seq>, complete }  # journal (Phase 8, I11)

The <aa> fan-out is the first hex byte of the chunk_ref, keeping each directory well under the ext4 inode-per-directory soft limit and the S3 list 1000-key page limit. A future layout_version = 2 is negotiated at open; the daemon refuses a layout it does not understand (LAYOUT_TOO_NEW).

Appendix E — Detailed Data Path

This appendix describes execution at each load-bearing path, for the engineer about to write the code. Every other section describes intent; this one describes order. It is the long-form companion to the §8 state table.

E.1 The write path at Phase 3 (encrypted, plaintext-content-addressed)

A single Backup::backup(source, repo, keys) performs, in order:

  1. Snapshot acquisition (bks-snapshot): the driver returns a SnapshotHandle; with no driver configured, LiveWalk returns a handle at the source root and logs LIVE_WALK_NOT_CONSISTENT. The handle's mount is the root the walker traverses.
  2. Walker init (bks-walker): open the snapshot mount, compile exclusion patterns; the iterator is lazy, one WalkEntry per next().
  3. Per-file processing for each WalkEntry::File: open O_NOATIME if possible; stream through FastCDC emitting (plaintext, chunk_ref=BLAKE3(plaintext)); consult the chunk index — if present, increment dedup and continue; else derive chunk_key = HKDF(master,"bks.chunk.key/v1",chunk_ref‖epoch), chunk_nonce = HKDF(master,"bks.chunk.nonce/v1",chunk_ref‖epoch), aad = chunk_ref‖epoch‖aead, ciphertext = seal(...); PUT to chunks/<aa>/<rest> (unconditional — a concurrent identical write is a content-addressed no-op); insert into the index; append a ChunkEntry to the file's node.
  4. Per-directory processing: after all children, build TreeNode::Directory{entries:[child ids]}, prost-encode, hash to tree_node_id, PUT to manifests/trees/<id>.
  5. Manifest construction: the root directory node's id is the manifest root; build and prost-encode the body.
  6. Signing: signature = Ed25519::sign(sign_key, body_with_id); manifest_id = BLAKE3(body) (Appendix C.5).
  7. Manifest upload: PUT to manifests/<manifest_id>.
  8. Head update: read heads/<source-hash> etag; PUT with If-Match/If-None-Match and body manifest_id; on conflict, reload, relink the parent, repeat from step 5.
  9. Index upload: serialize the in-memory index, .tmp+rename to indexes/<repo-id>/<ts>.
  10. Snapshot release: driver.release(handle).

E.2 The read path at Phase 7 (verify + restore)

A single Restore::restore(manifest, repo, keys, target) performs:

  1. Manifest load: GET manifests/<id>; split body / 64-byte signature; Ed25519::verify; reject on failure (I3); check id == BLAKE3(body) (I4).
  2. Tree traversal: GET manifests/trees/<root>; recurse into each child id.
  3. Per-file restore: create target/<rel-path>; for each ChunkEntry, GET ciphertext, derive key+nonce+aad, open (tag failure → CHUNK_CORRUPT(chunk_ref, manifest_id)), assert BLAKE3(plaintext) == chunk_ref (else CHUNK_HASH_MISMATCH), pwrite at offset; then apply metadata in the I10 order (xattrs → ACL → mode → owner → times).
  4. Per-directory restore: apply directory metadata after all children (mtime set last).
  5. Symlink restore: symlink(target, path).

Verify is the same path with no writes — every chunk fetched and verified, every signature checked, every hash compared. A restore continues past a corrupt chunk to surface every gap rather than aborting on the first (P10).

E.3 The GC path at Phase 6

A single Gc::run(repo, retained):

  1. Acquire GC lock: put_if_match("locks/gc.lock", body, Etag::ZERO); on non-zero etag found, another holder owns it — abort (I6).
  2. Mark: for each retained manifest, walk its tree, insert every ChunkEntry.chunk into the live set (every manifest, not just head).
  3. List: list("chunks/").
  4. Sweep: for each chunk key not in the live set, delete, rate-capped (default 100/s) to stay under the backend's rate floor.
  5. Release: delete("locks/gc.lock") (best-effort; TTL expires it).
  6. Report: GcReport{...}.

E.4 The replication path at Phase 11

A single Replicator::replicate(since):

  1. Enumerate: src.list("manifests/"), filter created_at >= since, sort ascending.
  2. Per manifest: GET from src, verify signature locally, PUT to dst.
  3. Trees: for each TreeNodeId, GET src → PUT dst, skipping via dst.head.
  4. Chunks: for each ChunkEntry.chunk, dst.head(...); skip if present, else GET src → PUT dst.
  5. Head: after each manifest, dst.put_if_match("heads/<source-hash>", ...) to the latest replicated manifest.

Bandwidth is dominated by chunk replication; manifest and tree replication is constant per backup.

Appendix F — Out of Scope (detail)

The blueprint's scope is the backup + snapshot substrate. The following are explicitly out of scope; each names why and the boundary it draws.

  1. A backup web UI. The CLI and the metrics dashboard are the user surface; a web UI is a separate product with its own auth and threat model.
  2. A scheduling daemon. cron, systemd timers, or a Kubernetes CronJob are the operator's choice; embedding a scheduler couples release cadence to scheduling bugs.
  3. A hosted multi-tenant retention service. Reserved under ELv2 (ADR-23); this repository ships the runtime only. The convergent-encryption multi-tenancy it would need is rejected (ADR-09).
  4. Block-level backup. We back up file systems, not block devices; block-level backup (Bareos block, Borg block) is a different product with different consistency constraints (A2).
  5. Continuous data protection (CDP). We take point-in-time snapshots; CDP-style continuous journaling is a different RPO regime (§4 RPO = backup interval).
  6. Re-implementing lower-rank substrates. FastCDC/BLAKE3 (rank 109), S3 signing/multipart (rank 107), erasure parity (rank 108), and Raft (rank 39) are dependencies, not deliverables (P12).
