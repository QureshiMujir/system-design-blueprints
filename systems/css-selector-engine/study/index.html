Hard Questions (Self-Examination)

# Question Resolving § (synthesis of ≥2 sections)
HQ1 A user reports that querySelectorAll(".foo a") silently drops 3 nodes that querySelectorAll("a") includes. Sketch the complete diagnosis protocol, naming every component you'd inspect first. §N.2 (F1 trace protocol) + §3.4 (Bloom false-negative) + Phase 10 §22 (filter lifecycle). Check: Bloom FP/FN counters, run bloom=None vs bloom=Some differential, inspect AncestorHashes.packed for the selector vs ancestor filter buckets.
HQ2 Why does :has() require a complexity guard, but :is() does not, even though both recurse into inner selectors? §6.10 (bounded complexity) + Phase 11 §23 (:has forward traversal). :is() recurse into the same candidate (no additional tree walk); :has() walks a forward/backward subtree per candidate — multiplicative O(subtree) per nesting level.
HQ3 A consumer observes that matches(el, ":nth-child(2n+1)") returns stale results after a sibling insert. What is the root cause and the correct fix at each layer? I9 (NthIndexCache coherence) + Phase 4 §16 (An+B engine) + Phase 12 §24 (invalidation/structural mutation). Cache scoped to one traversal; host must clear cache on structural mutation OR rely on Phase 12's RESTYLE_LATER_SIBLINGS hint to re-run the match.
HQ4 You add a new pseudo-class ::nth-match() that needs a complex argument selector. Which crate files do you touch, in which order, and what invariant does each modification threaten? §10.1 (repo layout crate deps) + §11.3 (AST Component), §11.4 (Element trait) + Phase 5 §17 (logical pseudo parse) + Phase 7 §19 (compound match dispatch). Add Component::NthMatch in ast.rs, parse in parser.rs/pseudo.rs, dispatch in checker.rs, add specificity rule in specificity.rs; I1 and I3 threatened.
HQ5 Explain why VisitedHandlingMode::AllLinksUnvisited is enforced at the sel-query boundary, not inside sel-matching. What goes wrong if it is enforced one layer lower? §3.9 (sel-query role) + §6.9 (:visited privacy) + I8 + Phase 8 §20. Enforcing inside sel-matching means matches_selector returns different bool based on visit state, which leaks through any host that bypasses sel-query directly. The boundary must be where the public API lives.
HQ6 A stylesheet has 5000 rules, all with universal * as the rightmost selector. How does this degrade performance, quantify it, and name the fix? §3.5 (SelectorMap) + Phase 10 §22 + C8 (capacity model). All 5000 rules land in SelectorMap.other: Vec<T> — O(5000) linear scan per element. 10k nodes × 5000 × 10 ns = 500 ms per query_selector_all, far over the 5 ms target. Fix: rewrite rules to have concrete rightmost simple selector; warn in bench when other.len() > 64.
HQ7 Prove that the Component matching-order invariant (I1) implies ToCss round-trip stability (I7), and vice versa. I1 (matching order, Phase 2 §14) + I7 (ToCss stability, Phase 6 §18) + §3.2 (sel-parser). I1 → ToCss must re-reverse to emit source order → serializer is the only site that knows the stored order. If I1 is violated (components not reversed), ToCss produces a selector with wrong combinator order → re-parse produces a different AST → I7 fails. I7 failure (non-idempotent serialize) always reveals an I1 or serializer bug.
HQ8 A host implements add_element_unique_hashes but accidentally skips inserting the element's classes. What is the observable failure and which test would catch it? §6.4 (Bloom no-false-negative) + I4 + Phase 10 §22 (bloom reject corpus). Observable: .class selectors silently fail to match even when the class is present → F1 false-negative. Caught by: opt_eq_brute differential (Bloom on vs off → results diverge) and the bloom_no_false_negative property test (200k cases).
HQ9 Why does the sel-parser store Specificity at parse time rather than computing it at match time? Name two concrete failure modes if it were deferred to match time. §6.8 (specificity at parse) + §4.1 (throughput) + ADR-10 + Phase 6 §18. (1) A hot querySelectorAll with 1000 candidates re-walks the entire AST per candidate for specificity → blows the 10M matches/s target. (2) Cascade consumers (project 124) cache specificity alongside match results; deferred computation invalidates that cache contract.
HQ10 What is the formal criterion that determines whether a selector's rightmost simple selector is placed in id_hash, class_hash, local_name_hash, or other in SelectorMap? What happens to :scope > .x specifically? §3.5 (SelectorMap) + Phase 10 §22 + §8.3 (AST mapping). Rightmost simple selector = last non-Combinator Component in matching-order slice (index 0 compound). For :scope > .x: matching-order slice[0] = Class("x") → class_hash. :scope is left of Child combinator → it's an ancestor constraint, not the rightmost.
HQ11 A fuzzer finds a 15-byte selector that causes matches_selector to return true in 200 µs (within budget) but only when nesting_level=31. Explain why this is concerning and how to reproduce it deterministically. §6.10 (bounded complexity) + I10 + Phase 11 §23 (nesting guard). nesting_level=31 is one below the cap: the guard has not fired, but the selector exploits near-exponential combinator backtracking. Deterministic reproduction: feed the bytes to fuzz_match, seed with fixed arbitrary::Unstructured from the saved crash bytes, assert wall-time < 1 ms.
HQ12 Explain the full lifecycle of NthIndexCache across a query_selector_all call on a tree that mutates between two calls. Where is the state allocated, when is it valid, and what triggers its invalidation? I9 (cache coherence) + Phase 4 §16 (An+B) + Phase 12 §24 (invalidation RestyleHint). Allocated as part of MatchingContext (caller-owned), valid for one uninterrupted query_selector_all sweep, discarded afterward. On mutation: Phase 12 emits RESTYLE_LATER_SIBLINGS for structural changes; host must create a fresh MatchingContext (and thus fresh cache) for the next query.
HQ13 Design a test that proves the :visited gate is correctly enforced at the API boundary, not just by convention. What assertions does it make and against which public functions? §6.9 + I8 + Phase 8 §20 + Phase 9 §21. Test: build a NodeRef tree with a visited link. Call sel_query::matches(el, ":visited") and sel_query::query_selector_all(root, ":visited"). Assert: return values identical to the AllLinksUnvisited case. Also assert: any code path reaching sel_matching::matches_selector with RelevantLinkVisited via the public API causes a debug_assert! failure (gate is in sel_query, not bypassable via public API).
HQ14 Given that BloomFilter is 4 KB and fits in L1, but the host tree contains millions of nodes with wide ancestor chains (depth 200), at what ancestor depth does the filter become a performance liability rather than an asset? Derive the crossover analytically. §3.4 + C3 (capacity model) + Phase 10 §22. FP rate at depth D: load_factor = D×2/4096; FP ≈ load_factor² × 4096. FP rate = 1 (useless) when load_factor ≈ 1, i.e. D ≈ 4096/2 = 2048 ancestors. Long before 2048, FP rate rises: at D=200 → 10% FP → 10% of candidates still walk the full tree. Crossover (Bloom overhead > benefit) at FP ≈ 50% → D ≈ 1024. Practical trees (web DOM) rarely exceed D=50; the filter is always beneficial.
HQ15 The Servo selectors crate is updated upstream and now parses :has() non-forgiving (our choice) but emits a different ToCss form for 2n+0. Will the differential test fail, and if so, what is the correct response? Phase 13 §25 (differential oracle) + §6.11 (deterministic serialization) + ADR-19 + Compatibility & Versioning (Parity vs Servo selectors). The differential test compares: parse-accept/reject (same behavior → no fail), match-set (same → no fail), and ToCss string (different → FAIL on corpus lines with 2n+0). Correct response: add to PARITY.md with spec citation if both forms are spec-valid normalizations; OR align serialization in Phase 6 §18 and treat as a bug fix.

Mental Models & First Principles

# Expert Insight What It Predicts Bug Class Without It Resolving §
MM1 Right-to-left = fail-fast on the hardest constraint first. The rightmost simple selector is the tightest discriminator (it targets the candidate directly); failing there costs zero tree traversal. A selector like div span will reject ≥ 95% of candidates at the span test before ever walking up to check div. Implementors match left-to-right: every div in a 10k-node tree spawns a descendant walk → O(N × descendants) instead of O(N × 1) per failing candidate. §6.3, Phase 7 §19
MM2 A Bloom filter is not an index — it is a one-sided certificate of absence. might_contain=false is a proof of no-match; might_contain=true is only a hint. The engine's correctness rests entirely on zero false negatives (never reject a real match). Bloom reject rate on miss-heavy corpora should be ≥ 90%; FP rate < 5%. Any FP merely adds a slow-path match that returns false — never wrong. Engineer treats FP as a correctness issue and lowers the bucket count to "fix" it → increases FP further, no change in correctness, AND reduces fast-reject benefit. §3.4, §6.4, Phase 10 §22
MM3 Matching order storage makes iteration direction equal to semantic direction. Component slice index 0 = rightmost compound means "iterate forward" = "evaluate right-to-left" — a single invariant eliminates all index arithmetic at match time. Any slice-walk bug that advances an index produces RTL evaluation; any off-by-one in matching maps directly to an off-by-one in semantic evaluation. Stored in source order → matcher must reverse or index with len-1-i → one pointer offset error silently matches a different selector. §3.2, §6.5, I1, ADR-05
MM4 Specificity is a saturating packed integer, not a triple comparison. Packing (a,b,c) into one u32 at parse time turns cascade ordering into a single integer compare at use time. Saturation (clamp to 255) is a spec requirement, not an implementation choice. Any :is() / :not() / :has() argument must contribute its whole packed value (max over args), not per-field max → field-wise max produces wrong ordering when argument specificities differ across fields. Per-field max on functional pseudo: :is(#a, .b.c) yields (1,2,0) instead of correct (1,0,0) (max packed = #a's (1,0,0)). §6.8, Phase 6 §18, ADR-10
MM5 Forgiving vs non-forgiving is a typed parse-mode, not a recovery heuristic. :is()/:where() drop invalid args by spec; :not()/:has()/top-level query* propagate errors. Conflating these either silently eats author errors or rejects valid :is() lists. parse_selector_list(Forgiving) on :is(.a, !!!) yields [.a]; parse_selector_list(Strict) on the same input yields ParseError. The parse-mode flag is the single branching point. Applying forgiving mode at top-level querySelector → div > returns Ok([]) instead of SyntaxError → the WHATWG DOM contract is violated, detectable only by explicit API-boundary tests. §6.7, I6, Phase 5 §17, Phase 9 §21
MM6 :visited indistinguishability is an invariant, not a feature. The API surface must collapse visited/unvisited results so that timing and result-set probing cannot distinguish. The engine computes both; the boundary discards the visited branch. querySelector(":visited") must return the same nodes regardless of actual visit history. Any branching on real visit state at the API layer is a privacy regression. Returning real visited nodes from querySelector enables any script to enumerate the user's browsing history by testing link elements against :visited — a well-known browser attack class. §6.9, I8, Phase 8 §20, Phase 9 §21
MM7 Counting Bloom (vs bitset Bloom) is required by the tree-descent use pattern. Ancestor filter must be push-on-descent / pop-on-backtrack. Counting (8-bit) buckets allow O(1) decrement; a bitset Bloom cannot decrement → requires O(ancestor-count) rebuild on every backtrack step. Push/pop symmetry is provable from the counting invariant: net insertions == current ancestor depth. Any underflow → false negative. Using a bitset Bloom and rebuilding on pop → O(depth²) per combinator-backtrack step for Descendant chains → defeats the fast-reject purpose on deep trees. §3.4, §6.4, ADR-12, Phase 10 §22
MM8 The Element trait is a query interface, not an ownership model. The engine holds &E, never E; OpaqueElement is the only identity that crosses the trust boundary. This separates match correctness from host-tree lifecycle. matches_selector is pure over the tree (I5); parallel query_selector_all is correct because there is no write to any host-owned state. Storing a host node reference inside the AST or MatchingContext → host tree mutation during match corrupts engine state → data race or use-after-free if the host drops the node. §3.3, §6.6, ADR-04, I5

Glossary · 9 terms · site-wide glossary

selector list
SelectorList(Box<[Selector]>). Matches if ANY member matches. Top-level is NON-forgiving.
complex selector
Compound selectors joined by combinators. One Selector (Box<[Component]> + Specificity).
compound selector
Simple selectors constraining ONE element (e.g. div.x#y). Rightmost is the subject's anchor.
simple selector
One condition: type, universal, ID, Class, attribute, pseudo. One Component (excluding Combinator).
combinator
Combinator enum: Descendant ( , unbounded/backtracks), Child (>, bounded/no-backtrack), NextSibling (+, bounded), LaterSibling (~, unbounded/backtracks).
subject
The element selected = the rightmost compound. querySelector returns subjects.
rightmost compound
Stored FIRST in matching order; matched first → fastest reject.
matching order
Components rightmost-compound-first; forward slice iteration = RTL selector walk. Load-bearing.
right-to-left matching
matches_selector starts at candidate, matches rightmost compound, walks Combinators leftward with backtracking on unbounded combinators.
