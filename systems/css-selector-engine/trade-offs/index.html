Decisions (§9) · 26 ADRs

ADR-01

Implementation language

Chosen

Rust, edition 2021, MSRV 1.78

Rejected

C/C++; Go; TypeScript

When the rejected choice is right

C if embedding in a kernel or OS-level style engine where Rust's toolchain is unavailable; Go if the selector grammar is a subset and type-safety matters more than perf.

Why: Untrusted input hot path -> memory safety non-negotiable; sum-type enums + exhaustive match model AST zero-cost; Servo selectors reference maps 1:1. C/C++ unsafe on untrusted; Go lacks sum types / zero-cost generics for Element; TS no alloc/cache control.

ADR-02

Workspace topology

Chosen

Cargo workspace, 6 members: sel-tokenizer, sel-parser, sel-matching, sel-dom, sel-query, sel-cli

Rejected

Single monolithic crate; per-pseudo-class micro-crates

When the rejected choice is right

Single crate when shipping a vendored proof-of-concept where binary size matters more than no_std layering.

Why: Crate = compile firewall + dep arrow (tokenizer<-parser<-matching<-query); incremental builds; sel-dom/sel-cli isolate std. Monolith blocks no_std split; micro-crates -> link/version churn.

ADR-03

Core runtime environment

Chosen

no_std + alloc for sel-tokenizer/sel-parser/sel-matching/sel-query; std only in sel-dom, sel-cli

Rejected

std everywhere; no_std no-alloc (arena only)

When the rejected choice is right

std everywhere if the library is only used in a browser-process native plugin that already requires std and binary size is unconstrained.

Why: Engine embeddable in no_std hosts (style systems, WASM). alloc needed for Box<[..]>/Vec. Full std blocks embedding; no-alloc impractical for AST.

ADR-04

Host-tree coupling

Chosen

Generic trait Element: Sized + Clone

Rejected

Concrete DOM struct; dyn Element trait objects; callback closures

When the rejected choice is right

dyn Element when code size dominates (many Element impls in one binary), monomorphization bloat exceeds vtable cost, or you ship a C-FFI ABI where generic instantiation is impossible.

Why: Decouple matcher from any tree; monomorphized = zero-cost; host plugs parent_element/has_class/attr_matches. dyn adds vtable on hot path; concrete DOM defeats reuse; closures lose Clone/inlining.

ADR-05

AST component ordering

Chosen

Selector stores Components in matching order (rightmost compound first)

Rejected

Source order (left-to-right as written)

When the rejected choice is right

Source order if the primary consumer is a pretty-printer or linter (not a matcher) that needs zero-reversal serialization and matching performance is secondary.

Why: Matching is right-to-left; storing in matching order makes iteration == walk direction, no reversal per match. Source order forces reverse-iteration or index math on every matches_selector. ToCss re-reverses for serialization.

ADR-06

Component / list container

Chosen

Box<[Component]>, Box<[Selector]>

Rejected

Vec<Component>; SmallVec; linked list

When the rejected choice is right

SmallVec<[Component; N]> if profile shows most selectors fit N components and avoiding that single heap alloc per selector measurably reduces latency (e.g. embedded style system).

Why: AST immutable post-parse -> slim 16-byte fat pointer, no spare capacity, cache-dense. Vec carries unused cap; SmallVec adds inline-size tuning + dep; list kills locality.

ADR-07

Token/atom string storage

Chosen

CowRcStr<'i> (copy-on-write, refcounted) + interned Atom/LocalName/NamespaceUrl

Rejected

String everywhere; &'i str only; Cow<str>

When the rejected choice is right

Owned String when the selector source is transient (from a network buffer that is freed immediately after parse), forcing owned values for all tokens regardless.

Why: Most tokens borrow input slice (zero-copy); escapes/owned values refcount-share. Interned Atom -> ptr-eq id/class/name compares in matcher. Owned String = alloc per token; pure &str can't hold un-escaped values.

ADR-08

Tokenizer construction

Chosen

Hand-written Tokenizer (code-point classifier + manual consumers)

Rejected

Lexer generator (logos, lalrpop lexer); regex

When the rejected choice is right

logos if generating a prototype quickly matters more than no_std or precise error recovery, or if the token set is reduced to a well-classified subset.

Why: CSS Syntax L3 has escapes, BadString/BadUrl recovery, sign/int_value number split, context-sensitive An+B tokens — generators model these poorly. Hand-roll = full control over error tokens + no_std, no build-script/proc-macro dep.

ADR-09

Parser strategy

Chosen

Hand-rolled recursive-descent (sel-parser)

Rejected

Parser-combinator lib; PEG/LALR generator (cf. portfolio project 63)

When the rejected choice is right

Parser combinators (chumsky, nom) when the grammar grows more complex combinatorially, the team is larger and composability matters more than fine-grained error recovery.

Why: Selectors L4 needs targeted recovery (forgiving lists drop one selector), precise ParseErrorKind, and matching-order emission — easier in straight-line RD. Project 63 is the generic-parser exercise; here we hand-roll for control + no_std + zero proc-macro.

ADR-10

Specificity representation

Chosen

Specificity{id,class,element} packed to one u32, 8 bits/field, saturating

Rejected

Three separate u32; (u8,u8,u8) tuple; u64

When the rejected choice is right

Three separate u32 if a spec extension raises specificity field sizes beyond 8 bits (e.g. a new Selectors L5 with deeper id-counts per rule).

Why: Single u32 -> one-compare ordering, cheap to store on every Selector. 8-bit saturating per Selectors L4 overflow note. Separate fields cost 12B + multi-compare; u64 over-allocates.

ADR-11

Ancestor-reject hashing

Chosen

AncestorHashes{ packed:[u32;3] } — 3x 24-bit hashes + overflow bits

Rejected

4+ hashes; full 32-bit hashes; no ancestor hashing

When the rejected choice is right

4+ hashes if profiling shows that selectors with 4+ distinct left-of-combinator keys are common (e.g. a very class-heavy framework like Tailwind at massive scale).

Why: 3 hashes of id/class/local-name left of descendant/child combinator cover most reject cases; 24-bit fits + overflow bits in 3 u32 (12B). More hashes -> diminishing reject gain, more memory; none -> always walk tree.

ADR-12

Ancestor membership filter

Chosen

Counting BloomFilter, 4096 8-bit buckets, 2 hash slots/insert

Rejected

Bitset Bloom (no counting); 1024 buckets; HashSet of ancestors

When the rejected choice is right

Bitset Bloom (non-counting) if the tree is fully static (no push/pop on subtrees, rebuild entire filter per element) and halving the filter size to 2KB is worth the rebuild cost.

Why: Counting buckets allow removal as the stack pops (push/pop ancestors). 4096x8b = 4KB fits L1; 2 slots balances FP rate. Invariant: zero false negatives. Bitset can't decrement; HashSet too heavy on hot path.

ADR-13

Rule bucketing

Chosen

SelectorMap<T> keyed by rightmost simple selector (id/class/local-name/namespace hash maps + other: Vec<T>)

Rejected

Linear scan of all rules; trie on full selector

When the rejected choice is right

Linear scan when the ruleset is < 20 rules (bucket overhead exceeds linear-scan benefit) or when all rules have universal * rightmost (everything lands in other).

Why: Bucket by rightmost simple selector -> candidate element retrieves only plausibly-matching rules. Linear scan O(rules) per element; full-selector trie complex with combinators/:is().

ADR-14

nth-index memoization

Chosen

NthIndexCache memoizing (parent, of-type?) -> child index

Rejected

Recompute index each match; cache on the node

When the rejected choice is right

Recompute each match when the subtree mutates between every query (cache invalidation cost exceeds memoization gain), or when sibling count is always small (< 20).

Why: :nth-*(An+B) over many siblings is O(n^2) naive; cache makes it O(n) per parent. Caching on node mutates host tree (forbidden).

ADR-15

:has() complexity guard

Chosen

Cap relative-selector traversal: bounded recursion depth + subtree-node budget; abort -> no-match

Rejected

Unbounded relational matching; disallow :has()

When the rejected choice is right

Unbounded if the engine runs in a fully trusted environment (no user-supplied selectors, all selectors are authored and audited) and :has() performance on deep trees is critical.

Why: :has() is O(subtree) per candidate; cap bounds CPU on adversarial selectors/trees. Unbounded = DoS; disallowing fails L4 conformance.

ADR-16

Forgiving-list policy

Chosen

:is()/:where() forgiving; :not() non-forgiving; :has() non-forgiving; top-level query* non-forgiving -> SyntaxError

Rejected

Forgiving everywhere; non-forgiving everywhere

When the rejected choice is right

Forgiving everywhere in a lenient CSS tooling context (linters, formatters) where surfacing every invalid selector as an error would break on real-world stylesheet quirks.

Why: Matches Selectors L4 + WHATWG DOM exactly. Uniform policy either silently eats real errors or breaks valid :is() lists.

ADR-17

Error handling model

Chosen

Result<_, ParseError/ParseErrorKind>; never panic on untrusted input

Rejected

panic!/unwrap; sentinel Option; exception-style

When the rejected choice is right

panic! only in trusted internal tooling (corpus generators, offline linters) where untrusted input is never fed and developer ergonomics outweigh safety.

Why: Untrusted selectors must fail gracefully -> typed errors map to SyntaxError at API boundary. Panic across FFI/embeds = abort; Option loses the 9 ParseErrorKind variants.

ADR-18

Serialization mechanism

Chosen

ToCss trait on AST nodes

Rejected

Display/Debug; ad-hoc to_string; serde

When the rejected choice is right

serde serialization for a binary AST cache format (skip string parsing on repeated loads), where JSON/binary round-trip matters more than CSS text output.

Why: Dedicated trait controls CSS-correct escaping/identifier quoting separate from Debug. Display conflates; serde wrong format + heavy dep.

ADR-19

Round-trip guarantee

Chosen

parse -> ToCss -> parse is stable (idempotent normal form)

Rejected

Best-effort, byte-preserving serialization

When the rejected choice is right

Byte-preserving if the consumer is a CSS diff tool that must reproduce exact whitespace and comment placement from the original author source.

Why: Stability testable + lets host cache canonical form. Byte-preservation impossible (whitespace/escape normalization).

ADR-20

Fuzzing harness

Chosen

cargo-fuzz / libFuzzer: parse, roundtrip, match targets

Rejected

proptest-only; AFL; no fuzzing

When the rejected choice is right

AFL if the execution environment cannot support libFuzzer (e.g. cross-compiled target, no LLVM instrumentation), or when corpus minimization via AFL's deterministic mutations is preferred.

Why: libFuzzer coverage-guided on untrusted-input surface; 3 targets mirror invariants. proptest kept for structured props; AFL heavier toolchain.

ADR-21

Differential oracle

Chosen

Servo selectors crate on shared corpus (Phase 13)

Rejected

WebKit/Blink (C++) oracle; self-checking only

When the rejected choice is right

WebKit/Blink C++ oracle when targeting exact browser behavior (including known bugs), not spec behavior; or when Servo's implementation diverges from spec for a specific feature.

Why: Servo is Rust -> link directly as test-dep, no FFI; reference reading already maps 1:1. C++ engines need FFI bridge; self-check can't catch spec misreads.

ADR-24

Chosen

Rejected

When the rejected choice is right

Track latest stable in a project with no downstream consumers (internal monorepo binary) and when using cutting-edge language features accelerates implementation.

ADR-25

Dependency policy

Chosen

Minimal; no syn/proc-macro / no build scripts in core crates; std-only deps confined to sel-dom/sel-cli

Rejected

Liberal deps; proc-macro codegen in core

When the rejected choice is right

Liberal deps when a higher-level framework (e.g. a WASM runtime) is the downstream and already pulls in heavy syn/proc-macro anyway, removing the incremental cost concern.

Why: Keeps core no_std, audit-light, fast-compiling; proc-macros bloat build + complicate no_std.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-A: Left-to-Right Descendant-Walk Engine

             query_selector_all(root, "div span")
                        |
              LTR: find all "div" first (type-bucket)
                        |
               for each div -> walk ALL descendants
                        |
                find "span" descendants -> emit

Regime where it wins: When the leftmost selector is extremely selective (e.g. #unique-id span) and the right-hand candidates are numerous. LTR avoids building ancestor-hash infrastructure and is simpler to implement. Also wins when the tree is shallow (depth ≤ 3) and descendant fan-out is small.

Real system: Early jQuery (pre-Sizzle, v1.2), which walked descendants left-to-right. Sizzle's RTL rewrite in jQuery 1.3 was motivated by the pathological LTR cost on CSS-class selectors over large DOMs.

Why rejected: On typical CSS (compound selectors, descendant combinators, class-heavy rules) the rightmost simple selector is the most selective discriminator. LTR forces visiting O(tree) descendants per leftmost-compound match before failing, whereas RTL fails at the candidate's own compound test with zero tree traversal. The 10M match/s throughput target (§4.1) is unreachable LTR on real-world selector corpora.

Alt-B: Finite Automaton / Compiled Bytecode Matcher

  Selector string
       |
   Compile (offline)
       |
   Bytecode: [CHECK_LOCAL_NAME, WALK_ANCESTOR, CHECK_CLASS, ...]
       |
   Interpreter / JIT over host tree

Regime where it wins: Long-lived style systems that apply the same rule set millions of times (browser layout engine at 60 fps). Compiling each selector to native bytecode amortizes parse cost, enables constant folding, and can specialize Bloom lookups into register comparisons. Wins for throughput; loses for startup latency and code complexity.

Real system: Blink's SelectorChecker is hand-optimized C++ that approximates this (inlined templates, PGO), and proposals for a CSS-bytecode VM have been explored in WebKit/Blink issues (not shipped). The Stylo team at Mozilla considered AOT-compiled selectors but deferred in favor of Rust's monomorphized generics.

Why rejected: The blueprint targets an embeddable Rust library with no_std + alloc. A bytecode compiler adds a significant implementation surface (compiler pass + interpreter or JIT), non-trivial code size, and is incompatible with the no-proc-macro / no-build-script core crate policy (ADR-25). The matches_selector generic monomorphization already achieves near-zero-overhead dispatch via LLVM inlining without a custom VM.

Alt-C: Pull-Model / Lazy-Match Iterator (streaming without tree materialization)

  querySelector(".card > p") over a streaming HTML parser
        |
  Push tokens to a stateful selector automaton
        |
  Emit matched element references as they arrive
  (no full tree materialized in memory)

Regime where it wins: Streaming HTML parsing (SAX-style) where materializing the DOM is too expensive (large documents, constrained memory). A finite push automaton can match element > child in O(1) per token. Used in CSS streaming extractors for web scraping and search indexing.

Real system: lxml's iterparse in Python; CSS streaming selectors in html5-parser architectures; some XPath streaming evaluators. The cssselect library's streaming mode is a partial example.

Why rejected: Descendant (unbounded) and subsequent-sibling combinators require knowledge of arbitrary ancestor or sibling history — not O(1) per token, requiring a stack bounded by tree depth. More critically, :has(), :nth-child(), and stateful pseudo-classes require backward references into already-parsed subtrees. Full selector conformance is not achievable in a single-pass streaming model; this architecture is valid only for a strict subset. This engine targets full Selectors L4 conformance (§13 Phase 13).
