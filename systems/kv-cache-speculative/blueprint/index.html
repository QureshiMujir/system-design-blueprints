117 — KV-Cache + Speculative Decoding

Project Number: 117

Status: specification — locked

1. Goal & Scope

Build a high-throughput LLM inference engine — in the vLLM / TensorRT-LLM / llama.cpp lineage — that serves an open-weights decoder-only transformer (Llama-3-8B, Qwen-2-7B, Mistral-7B family; GQA attention, RoPE, RMSNorm) under a continuous-batching scheduler with a paged KV-cache, and accelerates decode with speculative execution (independent draft model, Medusa multi-head, or n-gram lookahead) verified against the target model's exact output distribution. The deliverable is one process tree — a driver plus one worker per GPU — that turns a Hugging Face model directory into a quoted tokens/s-at-p50/p99 number on a status page, with every accelerant (paging, prefix sharing, speculation, quantization, tensor parallelism) individually toggleable and individually measured.

Phase-0 deliverable — numbered modules (package paths fixed here, reused identically in §10 Repository Layout, §11 Core Schema & Types, and every phase):

  1. kvspec.types — Sequence, BlockTable, BatchPlan, BatchOutput schemas (§11).
  2. kvspec.cache — static (Phase 0) then paged (§14) KV-cache manager.
  3. kvspec.scheduler — single-sequence stub (Phase 0), continuous-batching engine (§15).
  4. kvspec.model — Llama forward wrapper, BatchPlan → BatchOutput contract (§13).
  5. kvspec.sampling — greedy sampler (Phase 0), full sampler (temperature/top-k/top-p) later.
  6. kvspec.tokenizer — Hugging Face tokenizer wrapper, incremental detokenizer.
  7. kvspec.cli — kvspec serve, kvspec bench, kvspec inspect.
  8. benchmarks/ — single_seq_baseline.py, the Phase-0 tokens/s harness every later phase is contractually required to beat (§28 M1).

System boundaries.

  • Provides: request scheduling, paged KV-cache allocation/sharing/eviction, model forward orchestration, speculative decoding (three interchangeable methods), sampling, an OpenAI-compatible HTTP surface, Prometheus/OpenTelemetry observability.
  • Delegates: the fused attention/RMSNorm/RoPE kernels to Triton/FlashInfer/CUDA (implemented in-tree, §10 src/kernels/, but treated as a replaceable dependency boundary — ADR-11); model weight formats to safetensors; tokenization algorithms to tokenizers/sentencepiece.
  • Does NOT provide: draft-model or Medusa-head training (ADR-24 — consumes pre-trained artifacts only); a vector database or RAG pipeline; a multi-tenant billing/quota control plane (only per-request accounting hooks); a general training/fine-tuning framework; support for encoder-decoder or diffusion architectures (decoder-only transformers only, Phase 0–9).

Non-goals. Not a research framework for novel attention variants; not a model-conversion/quantization-training tool (consumes already-quantized weights where applicable); not a Kubernetes operator (ships a Helm chart, §10, but cluster lifecycle is out of scope); not a general prompt-caching CDN across organizations.

Deployment model. One driver process per replica; one worker process per GPU (ADR-25, no NVIDIA MPS); workers communicate via NCCL collectives for tensor parallelism (§21); the replica is packaged as one container (Dockerfile, §10) and deployed via the provided Helm chart or docker-compose.yml for single-node testing.

Target users/operators. ML-platform engineers self-hosting inference for a product team; the on-call SRE who must diagnose a p99 regression or an acceptance-rate collapse at 3 a.m. using only the runbooks in §10 docs/runbook/.

What later phases unlock. Phase 1 replaces the ad hoc HF forward with the typed BatchPlan → BatchOutput contract every later phase depends on. Phase 2 turns memory into a paged resource. Phase 3 turns the scheduler into a continuous-batching engine. Phase 4 makes prefixes free. Phases 5–7 unlock three interchangeable speculative methods. Phase 8 shrinks the KV-cache footprint 2–4×. Phase 9 unlocks multi-GPU serving and the production API surface.

Language + rationale. Python 3.11 for orchestration (scheduler, cache manager, speculative loop, serving layer) + CUDA C++ / Triton for the fused kernels (paged attention, fused RMSNorm/RoPE, KV-cache write, tree attention) — the same split vLLM, TensorRT-LLM, and every production serving stack in §31 converge on, because the scheduler is not the bottleneck (§4) and Python's per-step overhead (~200 µs) is amortized by kernel time (~5–20 ms) at any useful batch size. Rejected: pure Rust — the CUDA-kernel ecosystem (cudarc, candle) is years behind PyTorch/Triton/FlashInfer in maturity and would force re-deriving fused-attention kernels from scratch (ADR-01); pure C++ — correct but slows iteration on the scheduler/cache-manager logic that changes weekly, for no throughput benefit since kernels dominate wall time; Go — no first-class CUDA interop, no tensor/autograd ecosystem; Julia — immature GPU-serving packaging story, thin production track record versus PyTorch's CUDA graph and torch.compile tooling.

Prerequisites. Multi-head attention forward-pass mechanics (can write one by hand); the autoregressive decode loop and KV-cache read/write pattern; the prefill-vs-decode split; CUDA streams, torch.compile, nsys/nvidia-smi profiling; at least one fused attention kernel read end-to-end (FlashAttention-2 or FlashInfer); safetensors and Hugging Face tokenizer libraries.

Timeline. Phase 0: 2 weeks. Full system (10 phases, §12–§21): 7–8 months at one senior engineer full-time, or 4–5 months at two.

Deferred features (full table: §35 Deferred Features Register): PhaseDeferred("§21.10") FP8 KV-cache (H100-only numerics path, deferred past INT4); PhaseDeferred("§21.10") sequence-parallel attention (Korthavati et al.) for million-token contexts; PhaseDeferred("§15.10") disaggregated prefill/decode serving (DistServe/Splitwise-style); PhaseDeferred("§17.10") EAGLE-2/EAGLE-3 draft heads as a fourth speculative method; PhaseDeferred("§16.10") cross-organization prefix-cache sharing; PhaseDeferred("§21.10") LoRA adapter hot-swap per request; PhaseDeferred("§19.10") multi-modal (vision) token paths.

2. Why Build This

  • Naive serving (model.generate(), one KV-cache per request, no batching) achieves 5–10% of GPU roofline FLOP/s; paged + batched + speculative serving achieves 60–80% and costs roughly ⅛ per million tokens (§32 M-series numbers).
  • The literature is unusually rich and unusually implementable end-to-end: Kwon et al. (PagedAttention, SOSP 2023) and Leviathan et al. / Chen et al. (speculative decoding,
    1. each fit in an afternoon of careful reading and a week of correct implementation.
  • Building this from scratch is the fastest path to principal-engineer command of: memory fragmentation under variable-length allocation, continuous-batching scheduler design, provably-distribution-preserving rejection sampling, and tree-structured speculative verification — skills directly transferable to database buffer-pool design, OS page allocators, and any system serving heterogeneous-length work under a shared resource.
  • Cross-links: the paged block allocator is architecturally the same problem as a database buffer pool (see Type-Soundness-Proof sibling project's memory-region allocator) and an OS virtual-memory page table; the continuous-batching scheduler is architecturally the same problem as a network scheduler doing weighted-fair-queuing over heterogeneous flow sizes.
  • Calibration value: every design decision here (block size, eviction policy, speculative method, quantization level) has a publicly documented "we changed our mind" post-mortem from vLLM, TensorRT-LLM, or SGLang — you can grade your own ADRs against the real engineering teams' public retrospectives.

What Mastery Looks Like (5–8 competencies, each tied to a named phase):

  1. Derive KV-cache memory cost from first principles and explain fragmentation's dollar cost without a paper open — Phase 0 / Phase 2 (§12, §14).
  2. Implement and numerically validate a paged-attention kernel against an eager reference at a stated tolerance — Phase 1 (§13).
  3. Design a continuous-batching scheduler with named admission/preemption states and defend the fairness-policy choice — Phase 3 (§15).
  4. Prove (on paper, then in code) that a speculative-sampling acceptance rule preserves the target model's output distribution exactly — Phase 5 (§17).
  5. Compare three speculative methods (draft model, Medusa, lookahead) on the same acceptance-rate/latency harness and state which regime each wins — Phase 5–7 (§17–§19).
  6. Quantify a quality/memory trade curve for KV-cache quantization and set a perplexity-loss budget — Phase 8 (§20).
  7. Reason about tensor-parallel sharding, NCCL collective placement, and multi-GPU failure containment — Phase 9 (§21).

Request router. Terminates HTTP/gRPC, tokenizes, validates SamplingParams/ SpeculativeParams (§11.4), assigns a SequenceId, hands the Sequence to the scheduler. Trust boundary: the only place untrusted client input is parsed.

Scheduler. Owns four named sequence sets (I3) and the fairness policy (P7); the sole concurrency boundary between request arrival and GPU execution — one schedule_step() call per tick, never re-entrant.

KV-cache manager. Owns the physical block pool, the per-sequence block tables, the hash-keyed prefix cache, and copy-on-write; the sole authority on GPU-memory admission (can_allocate) — the persistence boundary for anything that must survive a preemption (swap to host memory, §15.6).

Model forward. Pure function of BatchPlan → BatchOutput (I5); the protocol boundary between scheduler-owned bookkeeping and kernel-owned tensor math; never mutates scheduler or cache-manager state directly.

Speculative decoder. Wraps the model forward with a propose/verify/accept loop; scheduler-visible (P4) — the scheduler, not the model, decides whether a step is speculative and how many slots to reserve.

Detokenizer + stream. Per-request incremental detokenization and the external streaming interface (SSE); the only component touching a str — everything upstream is token ids.

6. Design Principles

  1. P1 — Block-as-allocation-unit. KV memory is allocated/freed/shared/evicted as fixed-size blocks (B = 16 tokens default). Tradeoff: internal fragmentation ≤ B−1 tokens/sequence vs. the unbounded external fragmentation of contiguous allocation. Violating it (falling back to per-sequence contiguous buffers) reintroduces the 30–60% fragmentation loss the vLLM paper measured — see ADR-02.
  2. P2 — Prefix-sharing by default. Sequences with a common prompt prefix share blocks by reference (§16); no opt-in flag required. Tradeoff: a refcounted block is immutable once shared (forces copy-on-write, P3). Violating it (per-sample copies) costs O(n) memory for n-way parallel sampling instead of O(1) extra.
  3. P3 — Copy-on-write on divergence. The first writer to a shared block forks a new physical block (§16.4). Tradeoff: one extra block-copy per divergence point vs. correctness under concurrent mutation. Violating it silently corrupts a sibling sequence's cache (I6).
  4. P4 — Speculative-as-config. speculative_method ∈ {off, draft, medusa, lookahead} is a per-request or per-deployment toggle; scheduler and cache manager are speculation-agnostic below §17. Tradeoff: extra indirection (SpeculativePlan, §11.6) vs. the ability to disable speculation in production with zero code change when acceptance collapses (FM-6).
  5. P5 — Never-recompute-prefix. A cache hit on a hashed prefix (§16.3) is a lookup, never a re-forward. Tradeoff: hashing cost (~50 ns/block, xxHash3) vs. skipping an entire prefill forward (milliseconds). Violating it defeats the entire purpose of the prefix cache.
  6. P6 — KV-quant orthogonal. The dtype of a KV block (FP16/INT8/INT4) is a per-pool configuration invisible to the scheduler, prefix cache, and speculative loop (§20). Tradeoff: an extra dequant step in the attention kernel vs. keeping every upstream component dtype-agnostic. Violating it (hardcoding FP16 assumptions) blocks quantization from ever shipping without a scheduler rewrite.
  7. P7 — Fairness policy is named and singular. Exactly one SchedulingPolicy (FCFS, priority, or fair-share) is active per deployment, implemented once (§15.3). Tradeoff: less per-request flexibility vs. a debuggable, single code path. Violating it (heuristics scattered across three files) is the #1 documented root cause of scheduler bugs in production serving stacks (TGI issue history, §31).
  8. P8 — Preemption, not panic. A sequence that cannot fit a new block is swapped to host memory or aborted (I8); out-of-memory in the cache manager is a scheduled state transition, never an unhandled exception. Tradeoff: swap bandwidth cost (~PCIe Gen5 ~50 GB/s) vs. never crash-looping the worker under load.
  9. P9 — One model forward per scheduler step. Prefill, decode, and speculative verification for every admitted sequence share one forward(BatchPlan) call (I5). Tradeoff: a more complex ragged-batch kernel vs. avoiding per-step Python/kernel-launch overhead doubling. Violating it (separate prefill/decode passes) costs the ~200 µs per-step launch overhead twice, dominating at small batch sizes.
  10. P10 — Tokenizer/detokenizer in-process. No network round-trip for tokenization; the CPU-side incremental detokenizer runs on the same host as the GPU worker. Tradeoff: CPU core contention with NCCL/driver threads vs. removing a network hop from the token-emission critical path.
  11. P11 — Numerics tested against a reference, always. Every kernel (paged attention, fused RMSNorm/RoPE, sampler) is unit-tested against a PyTorch-eager reference at a stated per-element tolerance (I11). Tradeoff: a slower CI numerics suite (~10 min) vs. catching silent precision drift before it reaches production (the single hardest class of bug to diagnose post-hoc).
  12. P12 — Benchmarks are reproducible artifacts. Every benchmark run pins CUDA toolkit, driver, model-weight hash, prompt corpus, and RNG seed, and is invoked by one make bench target (§27). Tradeoff: benchmark-harness maintenance cost vs. a number nobody can dispute in a regression review.
  13. P13 — Output-distribution equivalence is non-negotiable. Any speculative method must produce token distributions statistically indistinguishable from the target model run without speculation (I9). Tradeoff: rejecting faster-but-approximate accept rules (e.g. always-accept top-1) in favor of the proven rejection-sampling construction (Leviathan et al. 2023, Chen et al. 2023).
  14. P14 — Every accelerant is independently toggleable and independently measured. Paging, prefix caching, speculation, and quantization each have a benchmark and a kill-switch (§28 M-series, §11.4 config flags). Tradeoff: a combinatorial benchmark matrix (§27) vs. being able to attribute a regression to exactly one subsystem.

8. Domain Model

8.1 KV-cache layout

Per-layer, per-head K and V tensors are stored in a single physical pool tensor of shape (2, num_layers, num_blocks, block_size, num_kv_heads, head_dim). A block holds block_size (16) contiguous token positions' K and V for every layer — one block allocation serves the whole model depth, avoiding per-layer fragmentation.

Physical pool tensor (conceptual layout):

  axis 0: {K=0, V=1}
  axis 1: layer   0 .. L-1
  axis 2: block   0 .. num_blocks-1      <- BlockId indexes here
  axis 3: slot    0 .. block_size-1      <- offset_within_block
  axis 4: kv_head 0 .. num_kv_heads-1
  axis 5: dim     0 .. head_dim-1

  addressing: physical_slot(seq, position) =
      block_table[seq].physical[position // block_size]   -> BlockId
      offset = position % block_size                       -> slot index

8.3 Draft/target speculative verification — worked example

K = 3 proposed tokens, draft distribution q, target distribution p, per Leviathan et al. 2023 §2:

step   draft token   q(token)   p(token)   accept prob = min(1, p/q)   outcome
1      "the"         0.60       0.55       0.917                       accept (r=0.40)
2      "cat"         0.45       0.20       0.444                       reject (r=0.70)
       -> resample from  max(0, p - q) normalized over full vocab
       -> resampled token: "dog"                                       (I9 holds: distribution = p)
(step 3 not reached; verification stops at first reject + 1 bonus token)

Accepted prefix = ["the", "dog"] (2 tokens from 1 forward pass of the target model, vs. 2 sequential target forwards without speculation). The accept/reject decision uses a single uniform draw r ~ U(0,1) per proposed token, compared against min(1, p(x)/q(x)) — this is the entire correctness-critical logic of I9.

8.4 Malformed-input examples

  • Prefix-cache hash collision: two distinct token sequences hash to the same content_hash (xxHash3, ADR-19). Detection: §16.5 verify step re-compares the actual token ids on a candidate cache hit before serving it; a mismatch is logged as prefix_cache_hash_collision_total and treated as a cache miss (never served as a false hit).
  • Draft/target vocab mismatch: a draft model with a different tokenizer or vocab size than the target. Detection: a startup-time check (SpeculativeParams validation, Phase 5) compares vocab_size and a fixed set of special-token ids; mismatch is a startup error, never a runtime crash (P4, FM-7).
  • num_speculative_tokens exceeding remaining max_seq_len budget: the admission check (I8) clamps the speculative window to max_seq_len - current_len before allocating speculative blocks; an unclamped request would over-allocate blocks that are immediately freed, wasting a can_allocate cycle.

8.5 Failure-path example

A Running sequence mid-speculation loses its draft-model forward (draft-model worker OOM). Recovery path: the speculative decoder catches the draft failure, falls back to speculative_method = off for that sequence only (P4), logs spec_draft_failure_total, and the scheduler continues the sequence in plain decode mode for the remainder of its lifetime — the sequence is never aborted for a draft failure (I8's abort path is reserved for max_seq_len and explicit operator kill only).

    num_layers: int; hidden_size: int; vocab_size: int
    def forward(self, hidden_state: torch.Tensor) -> torch.Tensor: ...  # [batch, vocab]

@dataclass(slots=True)
class MedusaConfig:
    num_heads: int = 4; head_layers: int = 1

13.3 Deliverable

fixtures/numerics_64tok_fp16.json — 64-token prompt, expected max-abs-err bound 5e-3. fixtures/numerics_64tok_fp32.json — same prompt, bound 1e-6. fixtures/slot_mapping_dtype.json — regression fixture pinning slot_mapping as int64 (§13.6 pitfall).

13.6 Pitfalls

FlashInfer's slot_mapping API expects int64; PyTorch's tensor-construction default is int32 — a silent narrowing produces a CUDA out-of-bounds access that only manifests at large batch sizes, not in the Phase-1 single-sequence test (ref-impl pitfall, §5). cu_seq_lens is an exclusive prefix sum ([0, len_0, len_0+len_1, ...]) — an inclusive variant is the most common bug here, diagnosed by an off-by-one in the last-position gather. Hugging Face's attention path applies a residual reshape the paged kernel does not need; skipping the numerics test here lets this drift silently into a reproducible-only-every-fifth-step bug once speculation (Phase 5) makes timing nondeterministic enough to expose it.

13.7 Performance Concerns

Kernel-launch overhead at batch size 1 is dominated by Python-side dispatch (~150–200 µs); this is invisible until Phase 3's continuous batching amortizes it across 32+ sequences. The mixed-mode prefill/decode wrapper's branch cost is negligible at single-sequence scale but becomes the load-bearing path once mixed batches are common.

13.8 Edge Cases

A sequence whose prompt length is exactly one block boundary (16 tokens) — the last-position gather must not read past cu_seq_lens. A prefill batch containing a zero-length sequence (already-finished, still present in the plan due to a scheduler race) — the forward must skip it without a shape error, anchored by I4 (BlockTable/ Sequence token-count agreement).

13.9 Failure Analysis

A dtype mismatch in slot_mapping (13.6) surfaces as a CUDA illegal-memory-access error at kernel launch — caught by the numerics test before merge (I11 gate, §27); in production, an equivalent bug would corrupt an adjacent sequence's cache (I6-class blast radius) and is why the numerics gate blocks every merge, not just release branches.

13.10 Operational Notes

kvspec_numerics_max_abs_err{kernel} exported per kernel (I11's telemetry column). No wire/storage compatibility concerns yet (no persisted BatchPlan). Rollback: a Phase-1 regression reverts to the Phase-0 model wrapper behind a feature flag during the transition window only (not carried past Phase 2).

14. Phase 2 — Paged KV-Cache and the Block Pool

14.1 Objectives

Replace the Phase-1 static contiguous cache with the paged block pool (§8.1, §11.1– 11.2, P1/ADR-02). Still single-sequence-at-a-time on the GPU (the scheduler stays a Phase-0 stub); this phase's job is purely correct block allocation, addressing, and free/seal transitions (§8.2 state machine).

14.2 Detailed Implementation Steps

Implement BlockPool (src/kvspec/cache/block_pool.py) owning the single contiguous physical tensor (2, L, num_blocks, block_size, Hkv, Dh) (§8.1 layout) and the free-list/refcount/content-hash tracking arrays (§11.1). Implement alloc(n), free_block(b), incref(b), decref(b), seal(b) as the only mutators of PhysicalBlock state (I2, I7). Implement BlockTable.slot_of() (§11.2) as the sole addressing primitive every kernel call routes through — no kernel computes a physical offset itself. Wire KvCacheManager.can_allocate/allocate/free (§11.7) against the pool; can_allocate is the first concrete instance of I8 (even though preemption itself is Phase 3 — Phase 2's admission simply refuses over-allocation with a structured error, ADR-02's fragmentation math made real).

14.3 Deliverable

A single sequence runs entirely on paged blocks: prefill allocates ceil(prompt_len/block_size) blocks, decode appends one block every block_size tokens, free() returns every block to the pool on sequence completion. kvspec inspect block-table <seq_id> (CLI, §10) prints the live logical→physical mapping for debugging.

14.4 Acceptance Criteria

tests/unit/test_block_pool.py: alloc/free round-trip leaves len(free) == num_blocks for 10,000 randomized alloc/free sequences (property test, I2). Fragmentation measurement (benchmarks/results/phase2_fragmentation.json) shows < 5% internal fragmentation at block_size=16 vs. the 30–60% contiguous-buffer baseline the vLLM paper reports (Kwon et al. 2023 §2, ADR-02's cited number). Throughput within 3% of Phase-1 baseline (paging overhead must not regress single-sequence performance).

14.5 Conformance Fixtures

fixtures/block_pool_exhaustion.json — allocate until can_allocate returns false, expect a structured AdmissionDenied error, never an unguarded CUDA OOM. fixtures/block_pool_refcount_leak.json — a scripted alloc/incref/decref/free sequence with an intentionally unpaired incref, expected: the deterministic simulator (§7 methodology) flags an I2 violation before the test exits.

14.6 Pitfalls

An off-by-one in slot_of(position, block_size) (integer division vs. modulo swapped) silently reads the wrong block for every 16th token — caught only by a per-position regression test, not a per-sequence one. Sealing a block (is_full=true, content_hash set, I7) before its last write commits produces a hash of stale data; the seal call must happen strictly after the kernel's write_kv_cache completes, not before it is dispatched (a common async-CUDA-stream ordering bug).

14.7 Performance Concerns

Block-pool alloc/free are O(1) via a free-list (not a linear scan) — a linear-scan implementation would silently regress to O(num_blocks) per allocation at high concurrency (irrelevant at Phase 2's single-sequence scale but load-bearing by Phase 3). The physical pool tensor's block-size axis (16 tokens × head_dim 128 × 2 bytes = 4 KiB/head) is chosen partly for GPU cache-line-friendly coalesced reads (H&P ch. 4, §5 Books).

14.8 Edge Cases

A sequence whose length is an exact multiple of block_size (no partial last block — last_block_offset must correctly read as block_size, not 0, to avoid an off-by-block error on the next append). Pool exhaustion mid-prefill (a single prefill request needing more blocks than currently free) — must fail the admission atomically, never partially allocate then roll back mid-kernel-call.

14.9 Failure Analysis

A refcount leak (I2 violation) manifests as either a permanently "stuck" unfree-able block (undercounted decref) or a premature free while still referenced (overcounted decref, corrupting a live sequence — I6-adjacent blast radius). Detection: the deterministic simulator's per-event assertion (§7); production detection is the block_refcount_mismatch_total counter (I2 telemetry) with the worker crash-and-restart fail-fast policy, since a corrupted pool cannot be trusted to self-heal.

14.10 Operational Notes

kvspec_blocks_free, kvspec_blocks_allocated, kvspec_fragmentation_ratio exported. kvspec inspect block-table is the first operator-facing debugging tool (§10 CLI) — documented in docs/runbooks/ for use during an OOM-storm investigation (FM-2). No wire-format concerns (block pool is worker-local, not persisted or shared).

15. Phase 3 — Continuous-Batching Scheduler

15.1 Objectives

Turn the Phase-0 single-slot scheduler stub into the real continuous-batching engine (P3, ADR-03): admit new prompts and retire finished sequences at every decode tick, run a mixed prefill+decode batch through the Phase-1 forward contract, and implement the full Waiting/Running/Swapped/Aborted state machine (I3) including preemption (P8).

15.2 Detailed Implementation Steps

Implement SchedulerEngine.schedule_step() (§11.8): scan waiting, admit while cache.can_allocate() holds (I8); scan running, build the mixed BatchPlan (ADR-04's one-forward principle, P9) via cu_seq_lens/is_prefill construction. Implement the fairness policy object (policy.py, P7) with FCFS as the sole Phase-3 implementation (ADR-15); the SchedulingPolicy interface is defined now so priority/fair-share (Phase 8) slot in without a scheduler rewrite. Implement preempt.py: on can_allocate failure, select the lowest-priority Running sequence (P7's named policy, never a heuristic scattered across files) and either swap_out (§15.6, ADR-16) to host-pinned memory or abort if it exceeds max_seq_len (I8's two-path admission gate). Fix the O(n^2) detokenizer flagged in Phase 0 (§12.7) with an incremental streaming implementation (P10).

15.3 Deliverable

A worker processing 32 concurrent chat-style requests with continuous admission: kvspec serve --model llama-3-8b --max-batch 32 accepts new HTTP requests mid-stream without waiting for the current batch to drain.

15.4 Acceptance Criteria

tests/e2e/test_continuous_batching.py: 32-way concurrent load sustains ≥ 1,800 tokens/s aggregate (M3, §28), p99 inter-token latency ≤ 90 ms (§4). Preemption correctness: tests/chaos/test_oom_preempts.py drives the pool to exhaustion and asserts every preempted sequence resumes with byte-identical continuation vs. an unpreempted control run (I3, I8).

15.5 Conformance Fixtures

fixtures/mixed_batch_16prefill_16decode.json — 16 sequences in prefill, 16 in decode, same tick; expected: single BatchPlan, single forward call (ADR-04). Malformed: fixtures/malformed_batch_plan_empty_cu_seq_lens.json — a plan with mismatched cu_seq_lens length; expected: a validation error before kernel dispatch, not a CUDA crash. Replay: fixtures/sharegpt_replay_1000req.json — 1,000-request ShareGPT-style trace replayed at fixed arrival timestamps for regression detection.

15.6 Pitfalls

FCFS's arrival_ns comparator (I12) must be strictly monotonic under concurrent request arrival — a wall-clock tie (two requests in the same microsecond) needs a secondary tiebreak (SequenceId order) or the property test flags nondeterministic ordering. Preemption chosen naively "youngest first" instead of by the named policy (P7) silently reintroduces the exact scattered-heuristic bug class documented in TGI's issue history (§5 ref-impls). Swap-out to host memory must pin the destination buffer (torch.cuda.pin_memory) or the PCIe transfer silently falls back to a much slower pageable-memory path — invisible in a functional test, visible only in a p99 latency regression.

15.7 Performance Concerns

The mixed prefill/decode kernel path (§13.2's branch) is the throughput-critical path at scale; a scheduler that only ever produces pure-prefill or pure-decode batches (never mixed) forfeits continuous batching's entire benefit (ADR-03). Swap bandwidth (~50 GB/s PCIe Gen5, §4) bounds how many sequences can be preempted per second without the swap path itself becoming the bottleneck — sized against §4's constraint table.

15.8 Edge Cases

A request that arrives and is aborted (client disconnect) before its first token is scheduled — must be removed from waiting without ever reaching can_allocate. Simultaneous preemption candidates at equal priority (fairness-policy tiebreak, extending I12's monotonicity requirement to preemption order). A swapped sequence whose max_seq_len budget is exhausted while swapped — must abort on swap-in attempt, not resume into an invalid state.

15.9 Failure Analysis

An acceptance-rate-unrelated scheduler livelock (every Waiting sequence repeatedly loses the preemption race to every Running sequence, admitting nothing) is detected by a scheduler_step_admits_zero_total counter alerting after N consecutive zero-admission ticks; recovery is a fairness-policy fallback to strict FCFS (P7's single-implementation guarantee makes this fallback trivial — there is only one other policy to fall back to before Phase 8 adds more).

15.10 Operational Notes

kvspec_scheduler_state_total{state} (I3), kvspec_preemptions_total, kvspec_admission_denied_total (I8) exported. Runbook: docs/runbooks/oom-storm.md walks the on-call engineer from an admission-denial spike to root cause via these three metrics. PhaseDeferred("§15.10") — disaggregated prefill/decode serving (separate hardware pools) is deferred past this phase; see §35 Deferred Features Register and §34 Alternative Architectures Alt-2.

16. Phase 4 — Prefix Cache and Copy-on-Write

16.1 Objectives

Implement the hash-keyed prefix cache (ADR-05, P5) and copy-on-write block forking (P3, ADR-06) so that shared prompt prefixes and n-way parallel sampling cost no extra prefill or extra memory beyond the point of divergence.

16.2 Detailed Implementation Steps

Implement prefix_cache.py: hash each sealed block's tokens with xxHash3 (ADR-19) into a key (model_id, tokenizer_id, block_tokens) (ADR-05); lookup_prefix(hashes) returns the longest matching prefix of already-sealed physical blocks. Implement the verify step (§16.5, ref-impl pitfall from §5's vLLM lesson): on a candidate hit, re-compare actual token ids before serving the shared blocks, never trusting the hash alone (defends I7 against ADR-19's accepted non-cryptographic collision risk). Implement cow_block() (§11.7): on the first write to a ref_count > 1 block, allocate a fresh physical block, copy content, decref the old reference, incref the new one — strictly gated by I6 (no in-place write to a shared block). Wire share_blocks() for beam search / parallel sampling (n > 1, ADR-06, ADR-23-equivalent): forking is "n parallel samples sharing a prefix" with no separate beam_search.py code path.

16.3 Deliverable

Two sequences with an identical 512-token system-prompt prefix: the second sequence's prefill is a cache lookup (P5), not a forward pass — measurable as near-zero TTFT for the second request. kvspec inspect prefix-cache --stats reports hit rate.

16.4 Acceptance Criteria

benchmarks/prefix_cache_hit_rate.py on a ShareGPT-style chat corpus with a shared system prompt: ≥ 40% hit rate (M9, §28). CoW correctness: tests/unit/test_cow.py asserts a divergent write to sequence A never appears in sibling sequence B's decoded output (I6), across 1,000 randomized fork points.

16.5 Conformance Fixtures

fixtures/prefix_hit_512tok_system_prompt.json — expected: TTFT < 20 ms for the second request (cache lookup, not prefill). Malformed: fixtures/prefix_hash_collision_synthetic.json — two distinct token sequences forced to the same xxHash3 value (constructed offline); expected: the verify step (I7) detects the mismatch and falls back to a cache miss, never serving corrupted context.

16.6 Pitfalls

Trusting the hash without the verify step (the exact bug vLLM's early releases shipped, §5 ref-impl pitfall) silently serves a wrong-context completion under a rare collision — undetectable without the re-compare step, because the failure is a plausible wrong answer, not a crash. Sealing a block (I7) before all its tokens are finalized (e.g. a speculative block sealed before verification completes) poisons the prefix cache with speculative-but-rejected content — sealing must happen only after Phase 5's acceptance step commits (forward reference to §17.4).

16.7 Performance Concerns

Hash computation (~50 ns/block, xxHash3, P5) is negligible against a skipped prefill forward (milliseconds) — the design bet only fails if the corpus has near-zero prefix reuse, in which case the hashing overhead is pure waste; §28 M9 gates on hit rate to catch this in benchmarking, not production.

16.8 Edge Cases

A prefix match that is exactly the full prompt (100% cache hit, zero-token prefill) — must still emit a valid BatchPlan with is_prefill=false and a legitimate decode-only first step. Two sequences forking from the same block simultaneously (concurrent CoW race) — Phase 4 remains single-worker/single-thread, so this is a same-tick sequential concern, not a true race; multi-worker consistency is I13's Phase 9 concern.

16.9 Failure Analysis

A CoW bug that fails to fork (writes in place to a shared block) corrupts every sibling sequence sharing that block — the highest blast-radius bug class in the cache subsystem, caught by tests/unit/test_cow.py's randomized fork-point sweep before it reaches production; production detection is indirect (a downstream output-quality regression report), which is why the pre-merge test coverage here is non-negotiable (I6, P11).

16.10 Operational Notes

kvspec_prefix_cache_hit_rate, kvspec_prefix_cache_hash_collision_total (I7), kvspec_cow_forks_total (I6) exported. Runbook: docs/runbooks/prefix-cache-corruption.md walks the collision-detection counter to a root-cause hash-collision report. PhaseDeferred("§16.10") — cross-organization prefix-cache sharing (a shared cache across tenants) is deferred; see §35.

17. Phase 5 — Speculative Decoding with an Independent Draft Model

17.1 Objectives

Implement the first speculative method (ADR-07, P4): a small draft model proposes K tokens, the target model verifies them in one forward pass, and the rejection-sampling acceptance rule (I9, Leviathan et al. 2023 / Chen et al. 2023) accepts a prefix while provably preserving the target model's output distribution.

17.2 Detailed Implementation Steps

Implement draft.py: run the draft model autoregressively for K steps (K=5 default, §4), producing SpeculativePlan.proposed_tokens/proposed_probs (§11.6). Implement accept.py's AcceptanceResult construction per the Leviathan et al. 2023 §2 construction (worked example, §8.3): for each proposed token, draw r ~ U(0,1), accept if r < min(1, p(x)/q(x)); on first rejection, resample from max(0, p - q) normalized (the "modified rejection sampling" framing Chen et al. 2023 independently derives) and stop the prefix there — this exact construction is what makes I9 provable, not an implementation choice. Wire the scheduler (§15.2) to reserve speculative blocks for the K proposed positions and free rejected ones on commit_step (P4's scheduler-visible requirement — the model and cache manager stay speculation-agnostic below this phase). Add the startup-time draft/target vocab- compatibility check (§8.4 malformed-input case).

17.3 Deliverable

speculative_method: draft end-to-end: a TinyLlama draft model paired with Llama-3-8B-Instruct target, measurable acceptance rate and tokens/s-per-forward improvement over Phase 3's non-speculative baseline.

17.4 Acceptance Criteria

tests/e2e/test_speculative.py: acceptance rate 0.55–0.85 on the fixed chat benchmark corpus (§4, Leviathan et al. / Chen et al. ballpark). Differential distribution test (I9): KL-divergence < 1e-4 between 10,000 samples generated with speculation on vs. off at a fixed seed and temperature — any larger divergence blocks release (I9's CI gate). Throughput: ≥ 1.6× tokens/s vs. Phase-3 non-speculative baseline at the same batch size (M-series target, §28 M10).

17.5 Conformance Fixtures

fixtures/spec_accept_deterministic_seed.json — fixed seed, fixed draft/target pair, expected accepted-token sequence pinned for regression. Malformed: fixtures/spec_vocab_mismatch.json — draft model with a different vocab_size; expected: a SpeculativeParams validation StartupError, not a runtime crash (§8.4). Failure-path: fixtures/spec_draft_worker_oom.json — simulated draft-model OOM mid- sequence; expected: fallback to speculative_method=off for that sequence only (§8.5).

17.6 Pitfalls

An acceptance rule that always accepts the draft's top-1 token (skipping the min(1, p/q) draw) is faster but violates I9 — it is a documented anti-pattern, not a valid optimization; the differential KL test exists specifically to catch this class of "looks faster, silently wrong" regression. A draft model whose tokenizer differs from the target's (even subtly, e.g. a different BOS-token convention) produces plausible-looking garbage acceptance rates that pass a shallow smoke test but fail the vocab-compatibility startup check — always run that check first when acceptance rate looks suspiciously low.

17.7 Performance Concerns

Draft-model forward cost must stay well under the target model's per-token cost or speculation nets negative (the K sequential draft forwards are on the critical path before the one target verification forward) — sized against the acceptance-rate formula in Leviathan et al. 2023 §3 (expected speedup as a function of draft cost ratio and acceptance rate). Reserved-but-rejected speculative blocks must free promptly (commit_step) or KV-cache pressure rises under high speculation-window K.

17.8 Edge Cases

K proposed tokens all rejected (worst case, num_accepted=0, I10's lower bound) — the bonus resampled token still advances the sequence by exactly one, never zero (a "stuck" sequence would be an I10 violation). A sequence within K tokens of max_seq_len — the speculative window must clamp (§8.4) to avoid over-allocating doomed-to-be-freed blocks.

17.9 Failure Analysis

An acceptance-rate collapse (rate drops below ~0.2, e.g. after a target-model prompt- template change desyncs draft and target) is detected by kvspec_spec_acceptance_rate crossing an alerting threshold; auto-recovery is the scheduler's per-deployment kill-switch (P4) disabling speculation without a restart; manual recovery is investigating the draft/target prompt-format alignment via the docs/runbooks/acceptance-rate-collapse.md runbook.

17.10 Operational Notes

kvspec_spec_acceptance_rate, kvspec_spec_proposed_total, kvspec_spec_accepted_total, kvspec_spec_draft_failure_total exported. Compatibility: a draft-model swap (different checkpoint) requires re-running the vocab-compatibility check and the differential KL test before production rollout — documented as a release-gate step (§27).

18. Phase 6 — Medusa Multi-Head Speculation

18.1 Objectives

Ship Medusa (Cai et al. 2024) as the second speculative method (ADR-08): multiple lightweight decoding heads attached to the target model's final hidden state replace the separate draft model entirely, verified via tree-structured attention (Miao et al. 2024's generalization).

18.2 Detailed Implementation Steps

Implement MedusaHead/MedusaConfig (§11.9) loading pre-trained heads from medusa_head_path (ADR-24 — training is out of scope). Each head i predicts the (i+1)-th future token from the shared final hidden state; tree_topk (§4) fixes the candidate fan-out per head ((10,10,8,4) default, Cai et al. 2024 §3's reported configuration). Implement tree_attn.cu (ADR-18, CUDA not Triton — the ~20% warp-level scan cost measured in §5's pitfall) to verify the entire candidate tree in one forward pass rather than K sequential forwards; the tree-attention mask encodes each candidate's ancestor path (Medusa §4 / SpecInfer's generalized tree verification). Reuse accept.py's I9-preserving construction, generalized from a linear K-token sequence to a tree — the acceptance rule still reduces to per-edge min(1, p/q) draws along the accepted path.

18.3 Deliverable

speculative_method: medusa end-to-end against Llama-3-8B with published Medusa-1 heads; no draft model process required (ADR-08's core benefit — removes an entire worker class and its vocab-compatibility failure mode, §17.6).

18.4 Acceptance Criteria

Mean accepted length 2.2–3.6 tokens/step (§4, Cai et al. 2024's Vicuna-7B/13B range) on the fixed benchmark corpus. Tree-attention numerics: max_abs_err < 5e-3 vs. an eager-mode tree-verification reference (I11 extended to the tree kernel). Speedup ≥ 1.8× vs. Phase-3 non-speculative baseline (M11, §28).

18.5 Conformance Fixtures

fixtures/medusa_tree_4head_fixed_seed.json — deterministic tree-candidate expansion, expected accepted path pinned. Malformed: fixtures/medusa_head_shape_mismatch.json — a head file whose hidden_size disagrees with the target model; expected: startup validation error, mirroring §17.6's vocab-mismatch check for the draft path.

18.6 Pitfalls

Tree topology depth beyond tree_depth=4 (§4 default) grows the verification batch combinatorially — an unbounded topology silently regresses to worse-than-no-speculation throughput; tree_topk/tree_depth are validated at startup against a documented ceiling. Medusa-1 (frozen backbone) vs. Medusa-2 (fine-tuned backbone) heads are not interchangeable — loading Medusa-2 heads against an unmodified backbone produces low but not obviously-wrong acceptance rates, a subtle failure mode distinct from §17.6's sharper vocab-mismatch error.

18.7 Performance Concerns

The tree-attention CUDA kernel (ADR-18) is the single hottest kernel in this phase; its warp-level scan must stay within the ~20% margin measured against a hypothetical Triton reimplementation (the documented reason CUDA was chosen, ADR-18) or the ADR should be revisited. Candidate-tree memory (extra KV blocks per candidate path) is freed identically to Phase 5's rejected-token blocks (commit_step).

18.8 Edge Cases

A tree where every path beyond the root is rejected (worst case, equivalent to Phase-5's num_accepted=0) — the same I10 lower-bound guarantee applies via the generalized tree acceptance rule. A tree_topk misconfiguration where a later level has more candidates than an earlier level (topologically invalid) — rejected at MedusaConfig construction, not at runtime.

18.9 Failure Analysis

A malformed Medusa-head checkpoint (dimension mismatch, §18.6) is a startup error (P4's config-agnostic scheduler means this never surfaces as a runtime scheduler bug). A tree-attention kernel numerics regression (I11 violation) blocks merge via the same CI numerics gate as every other kernel (§27) — no exception carved out for CUDA-only kernels.

18.10 Operational Notes

kvspec_medusa_mean_accepted_length, kvspec_medusa_tree_candidates_total exported. Compatibility: Medusa heads are versioned against a specific backbone checkpoint hash; docs/architecture/medusa.md documents the compatibility matrix. Deployment note: Medusa removes an entire worker class (the draft model) vs. Phase 5 — a meaningful operational simplification worth calling out to on-call staff choosing between methods.

19. Phase 7 — Lookahead Decoding (Draft-Free N-Gram Speculation)

19.1 Objectives

Ship lookahead decoding (Fu et al. 2024) as the third speculative method (ADR-08): no draft model, no trained heads — n-gram extrapolation from the target model's own recent outputs via a Jacobi-iteration reframing of the decode loop.

19.2 Detailed Implementation Steps

Implement lookahead.py: maintain an n-gram pool (lookahead_n_grams=4 default, §4) of recently-generated token sequences; at each step, propose candidate continuations by matching the current context suffix against the pool (Fu et al. 2024 §2's Jacobi- iteration framing — the decode loop is reinterpreted as fixed-point iteration over a window of future-token guesses, verified in parallel rather than sequentially). Verify proposed n-grams through the same accept.py I9-preserving construction reused from Phase 5/6 — lookahead's proposals are just another SpeculativePlan source (P4's speculative-as-config principle paying off: zero scheduler or cache-manager changes needed for a third method).

19.3 Deliverable

speculative_method: lookahead end-to-end with zero auxiliary model/head artifacts — the smallest-footprint speculative deployment (no draft-model worker, no head checkpoint to version).

19.4 Acceptance Criteria

Speedup ≥ 1.3× vs. Phase-3 non-speculative baseline on the fixed benchmark corpus (lower than draft/Medusa per Fu et al. 2024's own reported range — set as the realistic floor, M12 §28). N-gram pool memory bounded: ≤ 64 MB per sequence (a quantified ceiling, not "small").

19.5 Conformance Fixtures

fixtures/lookahead_repetitive_prompt.json — a prompt with strong internal repetition (lookahead's best case); expected: acceptance rate measurably higher than the low-repetition control fixture fixtures/lookahead_novel_text.json.

19.6 Pitfalls

Lookahead's speedup is workload-dependent in a way draft/Medusa are not — code generation and repetitive text see strong gains, free-form creative text sees little; deploying it as the default without workload-aware measurement (§28 M12) risks a net-negative rollout, unlike draft/Medusa's more workload-stable gains.

19.7 Performance Concerns

The n-gram pool lookup must stay O(1)-ish (hash-indexed by suffix) or it becomes the bottleneck lookahead was meant to remove; a naive linear scan over the pool regresses throughput below the non-speculative baseline at pool sizes beyond a few hundred entries.

19.8 Edge Cases

A cold-start sequence with no accumulated n-gram history (first few decode steps) — falls back to non-speculative decode until the pool has enough history to propose from, never blocks on an empty pool.

19.9 Failure Analysis

A pool that grows unbounded (missing eviction) exceeds the 64 MB/sequence ceiling (§19.4) — detected by kvspec_lookahead_pool_bytes crossing threshold, recovered by an LRU eviction identical in spirit to ADR-14's prefix-cache policy.

19.10 Operational Notes

kvspec_lookahead_pool_bytes, kvspec_lookahead_acceptance_rate exported. PhaseDeferred("§19.10") — multi-modal (vision) token paths are deferred past this phase; lookahead's n-gram matching does not generalize to non-textual tokens without further design (§35).

20. Phase 8 — KV-Cache Quantization

20.1 Objectives

Shrink KV-cache memory 2–4× via INT8 then INT4 quantization (ADR-09) while keeping the scheduler, prefix cache, and speculative subsystems dtype-agnostic (P6) and bounding quality loss to a stated perplexity budget.

20.2 Detailed Implementation Steps

Implement quant.py: per-pool dtype configuration (FP16/INT8/INT4) with per-channel scale factors (Yao et al. 2022 ZeroQuant §3's per-channel-vs-per-token framing; Hooper et al. 2024 KVQuant §4's non-uniform quantization for the INT4 tier). The attention kernel gains a dequantization step at read time (P6: everything upstream — block tables, prefix-cache hashing, speculative acceptance — stays dtype-agnostic, only the kernel and the pool's byte layout change). Extend BlockPool (§14.2) to carry a per-pool dtype tag consulted only at kernel-dispatch time.

20.3 Deliverable

Three deployable configurations (kv_dtype: fp16 | int8 | int4) on the same scheduler/cache-manager code, each independently benchmarked (P14).

20.4 Acceptance Criteria

INT4: 4× KV memory reduction, ≤ 0.5 perplexity-point loss on a held-out WikiText sample vs. FP16 baseline (ADR-09, Hooper et al. 2024's reported bound). INT8: 2× reduction, ≤ 0.1 perplexity-point loss. benchmarks/kv_quant_quality.py gates both numbers in CI (M-series, §28).

20.5 Conformance Fixtures

fixtures/quant_int4_perplexity_wikitext.json — pinned expected perplexity delta. Malformed: fixtures/quant_dtype_mismatch_prefix_hit.json — a prefix-cache lookup where the candidate block's dtype differs from the requesting sequence's configured dtype; expected: treated as a cache miss (dtype is part of the effective cache key, an extension of ADR-05's keying scheme).

20.6 Pitfalls

Sharing a quantized block across sequences configured for different kv_dtype values (a P2/P6 interaction bug) silently serves numerically wrong context unless the prefix-cache key incorporates dtype (§20.5's fixture exists specifically for this). Per-tensor (not per-channel) INT4 scaling loses noticeably more quality than the budget allows — always verify per-channel scaling is wired before trusting the perplexity number.

20.7 Performance Concerns

The dequantization step adds kernel-side FLOPs but the net effect is throughput- positive at high concurrency because memory-bandwidth savings dominate (§4's KV-cache-is-the-bottleneck framing) — measured explicitly, never assumed.

20.8 Edge Cases

A block quantized at INT4 that a speculative rollback (Phase 5's rejected-token free) touches — free/realloc must not attempt to reuse stale scale factors from a previous occupant.

20.9 Failure Analysis

A perplexity regression beyond budget (§20.4) blocks release via the CI quality gate (§27) exactly like a numerics regression (I11) — quality-loss-from-quantization is treated as a correctness class of bug, not a tunable knob to silently accept.

20.10 Operational Notes

kvspec_kv_dtype{pool}, kvspec_quant_perplexity_delta exported. PhaseDeferred("§21.10") — FP8 KV-cache (H100+-only) and sequence-parallel attention for million-token contexts are both deferred past this phase; see §35 and ADR-09.

21. Phase 9 — Multi-GPU Tensor Parallelism and Production Serving API

21.1 Objectives

Shard the model across multiple GPUs via NCCL tensor parallelism (ADR-10, Pope et al. 2022) and ship the production-facing OpenAI-compatible HTTP/SSE surface (ADR-17) plus the gRPC alternative, closing out the ten-phase plan with the operator-facing API.

21.2 Detailed Implementation Steps

Implement worker/shard.py: partition attention heads and MLP columns/rows across tp_size workers (Megatron-style tensor parallelism, Pope et al. 2022's KV-cache- placement discussion) with worker/distributed.py wrapping NCCL all-reduce/broadcast collectives. Extend BlockTable consistency (I13): every TP worker's local block table for a given SequenceId must stay byte-identical, enforced by a per-commit_step NCCL broadcast of block-table deltas from the driver's canonical copy. Implement serving/openai.py (/v1/completions, /v1/chat/completions, ADR-17) with SSE streaming and serving/grpc.py as a parallel low-latency surface. Wire per-request usage accounting (metrics/usage.py) into both surfaces identically (no surface-specific accounting drift).

21.3 Deliverable

A 2-GPU tensor-parallel deployment (examples/two-gpu-tp/) serving /v1/chat/completions with SSE streaming, plus a single-GPU deployment for comparison — both driven by the same scheduler/cache-manager code (P1–P14 hold regardless of TP degree).

21.4 Acceptance Criteria

2-way TP throughput ≥ 1.7× single-GPU throughput (sub-linear due to NCCL all-reduce overhead, quantified against §29's scaling analysis) — a number, not "faster". I13 conformance: tests/chaos NCCL delta-drop injection detects divergence within 1 step and triggers full resync. OpenAI-compat conformance: the fixture suite in tests/e2e/test_openai_compat.py validates response shape against the published OpenAI schema for both streaming and non-streaming requests.

21.5 Conformance Fixtures

fixtures/tp_2gpu_block_table_sync.json — scripted block-table delta broadcast, expected byte-identical tables post-sync. Malformed: fixtures/tp_delta_drop_injected.json — a dropped NCCL broadcast; expected: I13 divergence detection fires and a full resync completes before the next commit_step.

21.6 Pitfalls

NCCL collective placement inside the same CUDA stream as the attention kernel can serialize unexpectedly if stream priorities are misconfigured — a documented production gotcha (Pope et al. 2022's placement discussion, §5). The OpenAI-compat surface's streaming SSE format has subtle differences from the non-streaming response shape (e.g. delta vs. full message objects) that a shallow client-library test misses; the conformance fixture explicitly checks both shapes.

21.7 Performance Concerns

All-reduce overhead grows with TP degree and eventually dominates decode latency (the named ceiling in §29's scalability analysis, bounded at 8-way per §4). gRPC's lower per-call overhead vs. HTTP/SSE matters at very high request rates; both are benchmarked, neither is assumed superior.

21.8 Edge Cases

A worker crash mid-TP-collective (one of N workers dies inside an all-reduce) — the surviving workers must detect the missing peer via NCCL's timeout mechanism and the driver must abort the in-flight step cleanly rather than hang indefinitely (bounded by the availability/RTO targets in §4). A client disconnecting mid-SSE-stream — the server must free the sequence's blocks promptly, not leak them until max_tokens completes.

21.9 Failure Analysis

A worker crash during TP serving has cluster-wide blast radius (the entire replica's in-flight batch is lost, I13's consistency guarantee cannot be maintained with a missing shard) — detection via NCCL timeout, recovery via full replica restart and re-admission of in-flight sequences from the driver's swapped-sequence record (P8), bounded by the 30 s RTO target (§4).

21.10 Operational Notes

kvspec_tp_block_table_divergence_total (I13), kvspec_nccl_allreduce_latency_ms, per-surface (http/grpc) request-rate and latency histograms exported. Deployment topology: one driver + N GPU workers per replica (§3), Helm chart (ops/helm/) parameterizes tp_size. This is the terminal phase of the ten-phase plan; §22 onward covers the cross-cutting operational, testing, and analysis sections.

24. Operational Readiness

Metrics. Every counter/gauge/histogram named in the invariant table (§7), threat table (§22), and failure-mode table (§23) is exported via Prometheus (metrics/prom.py, ADR-20); traces via OpenTelemetry span every scheduler step, model forward, and cache-manager allocation.

Dashboards. One Grafana dashboard per subsystem: scheduler-state (I3 gauge), cache-pool (fragmentation, hit rate), speculative (acceptance rate by method), multi-GPU (NCCL latency, divergence count).

Alerting philosophy. Alert on rate-of-change for admission denials and acceptance rate (leading indicators), not just absolute thresholds — a slow acceptance-rate decay is as actionable as a sharp collapse (FM-3).

SLOs. p99 inter-token latency ≤ 90 ms at 32-way concurrency (§4); availability 99.5% monthly; RTO ≤ 30 s on worker crash (§4, FM-8).

Incident response. Five named runbooks (§10 docs/runbooks/) map directly to FM-2 through FM-8's most operationally common classes; each runbook starts from a named metric and ends at a named recovery action.

Backup/restore. No durable state beyond benchmarks/results/ (append-only, I14) and model weights (immutable, content-hash-verified, T9) — the engine itself is stateless across restarts by design (swapped sequences are best-effort, not durably persisted across a full outage).

Deployment topology. One driver + N GPU workers per replica (§21.10); Helm chart (ops/helm/) parameterizes replica count, tp_size, and kv_dtype.

Canary/rolling-upgrade/rollback. New replicas start with speculation disabled by default (P4's kill-switch), enabled only after the differential KL test (I9) passes against the new build; rollback is a Helm revision revert, safe because no durable state is carried across replicas.

25. Compatibility & Versioning

Wire compatibility. The OpenAI-compat surface (ADR-17) follows the upstream OpenAI schema version pinned in docs/api/openai-compat.md; a schema-breaking upstream change is handled by an additive, backward-compatible extension, never a breaking change to existing fields.

Storage compatibility. No persistent on-disk format beyond model weights (safetensors, externally versioned) and benchmark JSON (§10, schema versioned via a schema_version field checked at read time).

Schema evolution. BatchPlan/BatchOutput (§11.5) are worker-internal and never serialized across a version boundary — no compatibility contract needed there. The SamplingParams/SpeculativeParams (§11.4) wire schema is additive-only: new fields get defaults, no field is ever repurposed.

API stability. The OpenAI-compat surface is stable within a major version; the gRPC surface (§21.2) follows protobuf's standard field-number-never-reused discipline.

Deprecation policy. A deprecated SamplingParams field is logged (deprecated_field_used_total{field}) for two minor versions before removal.

SemVer policy. MAJOR: wire-schema-breaking or ADR-reversal changes (e.g. dropping paged-cache in favor of contiguous). MINOR: new speculative method, new quantization tier. PATCH: kernel numerics fixes within tolerance, bug fixes.

Rolling-upgrade guarantees. Mixed-version replicas within one deployment are supported for the OpenAI-compat surface (additive schema); NOT supported for cross-worker NCCL collectives (I13 requires byte-identical worker builds within one replica — a rolling upgrade replaces whole replicas, never individual workers within one).

26. Testing & Verification Strategy

Unit (tests/unit/): block pool, block table, prefix cache, CoW, scheduler, speculative-accept, sampler, detokenizer — one file per component, exercising I1–I14 directly.

Numerics (tests/numerics/): every fused kernel against a PyTorch-eager reference (I11), gated in CI (numerics.yml) on every merge — the single non-negotiable gate in the whole pipeline.

Property-based: refcount round-trip (I2, 10,000 randomized sequences), FCFS ordering (I12), CoW fork-point sweep (I6, 1,000 randomized points).

Differential: speculative-on vs. speculative-off KL-divergence (I9) — the correctness backbone of the entire speculative subsystem.

Fuzzing (fuzz/): fuzz_block_pool.py (malformed alloc/free sequences), fuzz_batch_plan.py (malformed cu_seq_lens/slot_mapping shapes).

Chaos (tests/chaos/): OOM-preemption (I8), draft-worker kill (FM-6), NCCL delta-drop (I13), long-context p99 latency under sustained load.

Deterministic replay: the scheduler simulator (§7 methodology) replays a scripted event log with one assertion per invariant, deterministic across runs.

Soak: 24-hour sustained-load run at target concurrency (32-way) checking for memory growth (leak detection) and latency drift.

Conformance (conformance/fixtures/): every phase's N.5 fixtures, collected centrally and re-run on every release candidate.

Performance-regression gating: bench.yml compares every M-series target (§28) against the Phase-0 baseline (I14) and the previous release; a regression beyond a stated percentage blocks the release.

Every test class ties back to a named invariant (§7) or a named fixture (each phase's N.5) — no test exists without a stated "what does this catch."

29. Scalability Analysis

Constant vs. grows. Per-token KV memory (I1, §4) is constant given a fixed model config; it does not grow with batch size — what grows is the number of tokens held concurrently (batch × context length), which is the actual bottleneck resource (§3). Scheduler tick cost grows O(batch size) per step (linear scan over waiting/ running, §15.2) — acceptable up to the hundreds-of-sequences range this engine targets; a scheduler serving tens of thousands of concurrent sequences would need a priority-queue-backed admission path instead of a linear scan (a documented ceiling, not built here).

Named bottlenecks, in order. (1) KV-cache memory (§4's defining property) — the first ceiling hit as concurrency grows. (2) NCCL all-reduce overhead — the ceiling for horizontal (multi-GPU) scaling beyond 8-way TP (§4, §21.7). (3) PCIe swap bandwidth — the ceiling for how fast preemption can absorb an admission burst (§15.7). (4) Scheduler tick's linear scan — the ceiling for total concurrent-sequence count, far beyond this engine's target range.

Horizontal/vertical scaling. Vertical: more GPU memory per worker directly raises the concurrent-sequence ceiling (§4's arithmetic). Horizontal: more replicas behind a load balancer (stateless-across-replicas design, §24) scales aggregate throughput linearly with no coordination overhead, since replicas never share KV-cache state.

Sharding/partitioning. Tensor parallelism (§21) shards within a replica across GPUs; there is no cross-replica sharding — each replica independently serves a full model copy (or a full TP-sharded copy).

Coordination overhead. Zero across replicas (stateless); within a replica, I13's per-step NCCL broadcast is the only cross-worker coordination point, and it scales with TP degree, not with request volume.

Practical ceiling and levers beyond it. The practical single-replica ceiling is set by GPU memory (§4's ~58-sequence number at 8K context on one H100) and 8-way TP's NCCL overhead; beyond that, the lever is horizontal replica scaling (linear, no coordination cost) rather than further vertical scaling within one replica.

30. Mental Models & First Principles

  1. MM1 — A block is a page, a block table is a page table. Predicts: any OS virtual-memory bug class (fragmentation, TLB-miss-equivalent lookup cost, sharing via copy-on-write) has a direct analog here. Bug class without it: reinventing contiguous allocation and rediscovering fragmentation the hard way. Applied in §14.
  2. MM2 — The KV-cache is the buffer pool; sealing is checkpointing. Predicts: a sealed (immutable, hashed) block behaves like a committed database page — safe to share, unsafe to mutate. Bug class without it: mutating a shared block in place (I6 violations). Applied in §16.
  3. MM3 — Continuous batching is weighted-fair-queuing over heterogeneous flow sizes. Predicts: the same starvation/fairness failure modes that plague naive network schedulers (short flows starving behind long ones, or vice versa under a bad policy) apply directly to sequence scheduling. Bug class without it: an undocumented heuristic-du-jour preemption policy (P7's entire justification). Applied in §15.
  4. MM4 — Speculative decoding is importance-sampling correction, not a heuristic speedup. Predicts: the acceptance rule must take the exact min(1, p/q) form or the output distribution silently shifts — this is a probability-theory constraint, not an engineering tradeoff. Bug class without it: "just accept the top-1 draft token" (§17.6's documented anti-pattern). Applied in §17.
  5. MM5 — A Medusa tree is a speculative-decode search tree, not a batch. Predicts: tree depth/fan-out trades verification cost against expected accepted length combinatorially, not linearly. Bug class without it: an unbounded tree topology that regresses below non-speculative baseline (§18.6). Applied in §18.
  6. MM6 — Lookahead is Jacobi iteration over the decode recurrence. Predicts: it converges fastest exactly where the sequence has high internal redundancy (code, repetitive text) and slowest on genuinely novel content — the same convergence profile Jacobi methods show on diagonally-dominant vs. ill-conditioned systems. Bug class without it: deploying lookahead as a universal default and being surprised by workload-dependent regressions (§19.6). Applied in §19.
  7. MM7 — Quantization is a signal-processing quality/bandwidth trade, not a free lunch. Predicts: per-channel scaling beats per-tensor scaling because KV values' dynamic range varies by channel, not uniformly — the same reason per-channel quantization wins in classical DSP compression. Bug class without it: a perplexity regression traced to per-tensor scaling instead of the intended per-channel approach (§20.6). Applied in §20.
  8. MM8 — Tensor parallelism is distributed shared memory with an explicit consistency protocol. Predicts: any distributed-consistency bug class (a dropped update, a stale replica) maps directly onto I13's block-table-divergence detection problem. Bug class without it: assuming NCCL broadcasts are exactly-once with no verification step. Applied in §21.

vLLM. The design this blueprint follows most closely — the one decision it makes differently from us at the reference-implementation level is compiling its scheduler loop tightly with the model executor for lower Python overhead; it wins in the niche of maximum single-replica throughput on well-supported model architectures with a large open-source kernel community behind it.

TensorRT-LLM. Compiles the entire model graph ahead-of-time into a TensorRT engine, trading flexibility (a graph rebuild is required for architecture changes) for NVIDIA-hardware-specific kernel fusion depth beyond what a Triton/CUDA-hybrid engine achieves; it wins in the niche of maximum throughput on a fixed, unchanging model on NVIDIA-only hardware fleets, where the AOT-compile cost amortizes over long-running production deployments.

llama.cpp. Chooses a simpler, contiguous-per-sequence KV-cache and a single-process model over paging and continuous batching; it wins in the niche of single-user or small-batch local/edge inference (consumer GPUs, CPU-only, Apple Silicon) where concurrency-driven fragmentation never arises and simplicity beats a scheduler this blueprint would consider mandatory at any meaningful concurrency.

HuggingFace TGI. Implements its router in Rust for lower per-request overhead than a Python scheduler, at the cost of a two-language codebase (Rust router, Python/C++ model execution); it wins in the niche of very high request-rate, small-payload workloads where router-side CPU overhead genuinely dominates, a regime this blueprint's single-language Python scheduler is not optimized for (P1's tradeoff explicitly accepted in ADR-01).

34. Alternative Architectures (Roads Not Taken)

Alt-1 — Contiguous per-sequence KV-cache (no paging).

 [ sequence A: contiguous KV buffer, max_seq_len sized ]
 [ sequence B: contiguous KV buffer, max_seq_len sized ]
 [ ... unused tail space wasted per sequence ...       ]

Regime where it wins: single-user or small-batch local inference with no concurrent- sequence memory pressure (consumer GPU, one chat session at a time). Real embodiment: llama.cpp's default KV-cache (§31). Rejected here because production concurrency (dozens of variable-length sequences, §4) makes fragmentation the dominant memory cost — exactly the problem PagedAttention (Kwon et al. 2023) was built to solve, and this blueprint's entire premise (§3) is serving that concurrency regime.

Alt-2 — Disaggregated prefill/decode serving.

 [ prefill GPU pool ] --KV transfer--> [ decode GPU pool ]
     (compute-bound)                      (memory-bandwidth-bound)

Regime where it wins: workloads with a sharp, predictable prefill/decode compute- profile split at very large fleet scale, where dedicating separate hardware pools to each phase avoids the one-forward-per-step principle's (P9, ADR-04) implicit coupling of prefill and decode resource contention. Real embodiment: DistServe and Splitwise (both published systems disaggregating prefill and decode across hardware pools). Rejected here (PhaseDeferred("§15.10"), §35) because it requires a KV-transfer network protocol and doubles operational complexity (two hardware pool types to capacity-plan) for a benefit that only appears at fleet scales well beyond this blueprint's single-to-few-replica target (§3's single-driver-plus-N-workers model).

Alt-3 — Heterogeneous CPU/GPU offload (FlexGen-style).

 [ GPU: hot layers/weights ] <--offload--> [ CPU/NVMe: cold layers, KV overflow ]

Regime where it wins: throughput-oriented batch inference on a single consumer GPU with insufficient memory for the full model + KV-cache, where latency is not a constraint (offline batch scoring). Real embodiment: FlexGen (Sheng et al. 2023, throughput-oriented single-GPU LLM serving via CPU/disk offload). Rejected here because this blueprint targets interactive-latency serving (§4's p50/p99 targets) where CPU/NVMe round-trips for cold weights or overflowed KV blocks would violate the inter-token latency budget by an order of magnitude.

36. Glossary

Acceptance rate — fraction of speculatively proposed tokens accepted by the target model's verification step (I9). Admission — the scheduler decision to move a sequence from Waiting to Running (I3, I8). Batch manager — TensorRT-LLM's term for its in-flight-batching state machine (§5, §31). BatchOutput — the model forward's return type (§11.5). BatchPlan — the model forward's input type, carrying block tables and slot mappings (§11.5). Block — the fixed-size (16-token default) unit of KV-cache allocation (P1). BlockTable — per-sequence logical-to-physical block mapping (§11.2). Continuous batching — admitting/ retiring sequences at every scheduler tick rather than waiting for a batch to drain (ADR-03). Copy-on-write (CoW) — forking a shared block on first divergent write (P3, I6). Decode — the autoregressive one-token-at-a-time generation phase, as opposed to prefill. Draft model — a small model proposing candidate tokens for speculative verification (§17). FCFS — first-come-first-served scheduling policy (ADR-15). Fragmentation — wasted memory from contiguous-allocation's inability to reuse partially-freed space (ADR-02). GQA — grouped-query attention, fewer KV heads than query heads (§4's Hkv). Head dim — the per-attention-head embedding dimension (Dh, §4). Inter-token latency — time between consecutive emitted tokens during decode (§4 M4-M6). KL-divergence — statistical distance measure used to test speculative-decoding output-distribution equivalence (I9). KV-cache — stored key/value tensors from prior decode steps, avoiding recomputation. Lookahead decoding — draft-free speculation via n-gram extrapolation and Jacobi iteration (§19, Fu et al. 2024). Medusa — multi-head speculative decoding replacing a separate draft model (§18, Cai et al. 2024). NCCL — NVIDIA Collective Communications Library, used for tensor-parallel collectives (§21). Paged attention — the attention kernel variant reading K/V from non-contiguous physical blocks via a block table (Kwon et al. 2023). Perplexity — a language-model quality metric; used here to bound quantization-induced quality loss (§20). Preemption — removing a running sequence (swap or abort) to admit or continue another (P8). Prefill — the initial forward pass over the full prompt before decode begins. Prefix cache — hash-keyed store of sealed blocks enabling cross-request prefix reuse (§16, ADR-05). Ref count — number of live block-table entries pointing at a physical block (I2). Rejection sampling — the probabilistic accept/reject construction underlying speculative decoding's distribution-preservation guarantee (I9, Leviathan et al. 2023). RoPE — rotary position embedding. Sealed block — an immutable, content-hashed, full block eligible for prefix-cache sharing (I7). Slot mapping — the tensor mapping each input token to its physical KV-cache slot (§11.5). Speculative decoding — proposing multiple future tokens and verifying them in one forward pass (§17). Swap — moving a sequence's KV-cache blocks to host memory to free GPU memory without aborting the sequence (P8, ADR-16). Tensor parallelism — sharding a model's weights and computation across multiple GPUs (§21, ADR-10). Tree attention — the attention variant verifying a tree of speculative candidates (rather than a linear sequence) in one pass (Medusa, SpecInfer, §18). TTFT — time to first token, the prefill-dominated latency metric (§4 M7). xxHash3 — the non-cryptographic hash function used for block content-hashing (ADR-19).
