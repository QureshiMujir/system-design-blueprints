ADR-01

Language

Chosen

Rust

Rejected

Go, Scala/JVM, Python

When the rejected choice is right

Go wins for a thin, I/O-bound, trigger-only scheduler with no in-process join hot path and an existing Go platform team

Why: deterministic memory ownership, no GC pause in the join hot path

ADR-02

DAG/orchestration model

Chosen

declarative pipeline spec (nodes/edges are data)

Rejected

imperative Python DAG (Airflow-style)

When the rejected choice is right

imperative wins for a one-off, rarely-repeated exploratory ETL script with no production repetition

Why: declarative DAGs are statically analyzable for cycles and leakage before execution

ADR-03

Scheduler design

Chosen

unified time/event/backfill trigger model

Rejected

cron-only scheduler

When the rejected choice is right

cron-only wins for a pipeline whose sole input is a daily batch drop with no streaming or backfill need

Why: event and backfill triggers are core to feature freshness

ADR-04

Batch engine

Chosen

pluggable batch engine via connector (Spark/DataFusion)

Rejected

in-house distributed batch engine

When the rejected choice is right

in-house wins only at a scale/latency point no existing engine reaches, e.g. sub-millisecond single-node micro-batch with no shuffle

Why: avoids reinventing a mature shuffle/query engine

ADR-05

Streaming engine

Chosen

unified Dataflow-style windowing/triggers delegated to Flink via connector

Rejected

custom streaming engine

When the rejected choice is right

custom wins for an edge/air-gapped single-node deployment that must run with zero external stream-processing dependency

Why: Flink's checkpointing and watermark model is proven at scale (Carbone et al.)

ADR-06

Point-in-time join implementation

Chosen

native as-of operator in pit-join

Rejected

When the rejected choice is right

pushdown wins for a purely offline, warehouse-only backfill with native ASOF JOIN support and no streaming path

Why: native control over leakage-proof semantics and reuse across streaming

ADR-07

Event-time/watermark handling

Chosen

per-source watermark tracked in the scheduler

Rejected

When the rejected choice is right

wall-clock wins for a provably always-in-order, low-volume, single-writer monotonic audit log

Why: wall-clock breaks under out-of-order/late data (Akidau et al.)

ADR-08

Incremental materialization strategy

Chosen

append-only incremental with periodic full-recompute reconciliation

Rejected

full recompute every run

When the rejected choice is right

full recompute wins for small (< 1M row), cheap-to-recompute features where incremental bookkeeping costs more than rerunning

Why: required to hit throughput/freshness SLOs at scale

ADR-09

Backfill mechanism

Chosen

Rejected

When the rejected choice is right

a separate path wins only for a one-time cold-start migration backfill with no prior baseline to diff against

Why: a separate path guarantees skew between backfill and live (P2)

36. Alternative Architectures (Roads Not Taken)

Alt A: Batch-only pipeline
[Lake/Warehouse] -> [Airflow DAG] -> [Spark Batch Job] -> [Offline Table]
                                                        -> (periodic export) -> [Online Cache]

Winning regime: pipelines with no low-latency serving requirement and a daily/hourly cadence, e.g. a monthly risk report. Real embodying system: dbt-plus-Airflow batch ELT pipelines. Why rejected here: online features go stale between batch runs, violating the freshness SLO (§4, I6), and there is no watermark-based streaming freshness path at all.

Alt B: Streaming-only pipeline
[Kafka/Pulsar] -> [Flink Job: windows + watermarks] -> [Online Store]
                                                     -> (replay from cold storage) -> [Offline Table]

Winning regime: pipelines where freshness dominates and deep-history reprocessing is rare, e.g. real-time fraud signals with short retention. Real embodying system: pure Flink-based feature computation (Carbone et al.). Why rejected here: backfilling months or years of history through a purely streaming engine is operationally expensive, and full-history batch training-table generation becomes second-class.

Alt C: Inline compute at serving time
[Request] -> [Serving Service: compute feature on demand] -> [Response]
                        (no materialization, no pre-computation)

Winning regime: rarely-read, cheap-to-compute features where any staleness is unacceptable, e.g. a trivial real-time inventory lookup. Real embodying system: request-time feature computation as used in some low-feature-count online-only recommender stacks. Why rejected here: recompute-per-request cost and latency do not scale to FPOS's throughput targets (§4), and every request pays the full transform cost with no reuse.

Alt D: Lambda architecture (separate batch + speed layers)
[Batch Layer: Spark]  --\
                         >-- [Serving Layer: merge] -> [Online Store]
[Speed Layer: Flink]  --/

Winning regime: legacy systems that already have separate, independently-evolved batch and streaming codebases and cannot yet unify them. Real embodying system: the classic Lambda architecture (batch layer, speed layer, serving layer) popularized before the Dataflow Model. Why rejected here: this is precisely the two-codepath skew risk that FPOS's unified batch/stream transform definition (Phase 6, P2) exists to eliminate — Lambda architectures are the historical embodiment of the training/serving-skew problem this project targets (Kleppmann; Akidau et al.).
