1. Goal & Scope

The Feature Pipeline Orchestration System (FPOS) is a from-scratch Rust orchestration platform for machine-learning feature engineering. It owns the DAG model and dependency resolver for feature transforms, a scheduler that triggers on time, event, and backfill signals, a batch and a streaming execution engine unified under one transform-definition language, a point-in-time-correct join engine that eliminates label leakage by construction, an incremental/full materialization writer that publishes to both an offline (training) and an online (serving) target from the same transform, a lineage and version tracker, and a freshness/data-quality monitor. FPOS computes and schedules features; it never serves them at low latency and never owns the durable feature values at query time — that responsibility belongs to the feature store (Feature-Store-122, already REAL-GOD), which FPOS treats as one of its materialization sinks. FPOS also does not own the raw data lake or warehouse (Data-Lake-Table-Format-214) — it reads from and writes intermediate and materialized data into those systems as a client. The system exists to make the two structurally hard problems of production ML feature engineering — label leakage from incorrect temporal joins, and training/serving skew from divergent offline/online code paths — impossible by construction rather than caught by testing after the fact.

Phase-0 deliverable — initial crate list:

  1. dag-model — pipeline DAG, node, edge, transform types; static acyclicity and schema checks
  2. dep-resolver — dependency resolution, cycle detection, topological schedule generation
  3. scheduler-core — time-triggered, event-triggered, and backfill-triggered scheduling
  4. exec-batch — batch transform execution engine over lake/warehouse sources
  5. exec-stream — streaming transform execution engine with event-time and watermarks
  6. pit-join — point-in-time-correct (as-of) join engine
  7. materialize — offline and online materialization writer with idempotent commit
  8. lineage — feature/version lineage graph capture and query
  9. quality — schema validation, distribution-drift, and freshness-SLO checks
  10. connectors — source and sink adapters (lake, warehouse, Kafka/Pulsar, feature store)
  11. metadata-store — pipeline, feature, version, and run metadata system of record
  12. cli — operator CLI (register, backfill, inspect lineage, replay)
  13. sdk-rust — the pipeline/transform definition SDK (one definition, two codegen targets)
  14. conformance-suite — the leakage/skew/backfill-determinism correctness harness
  15. observability — metrics, tracing, structured logging

Boundaries.

Provides: the DAG model and dependency resolver; the scheduler (time/event/backfill); batch and streaming transform execution; point-in-time-correct join semantics; incremental and full materialization; feature versioning and lineage capture; freshness-SLO and data-quality monitoring; connectors to sources and sinks including the feature store.

Delegates: low-latency point/lookup serving of materialized features to the feature store (Feature-Store-122); durable storage of raw and intermediate data to the data lake/warehouse (Data-Lake-Table-Format-214, object storage); general-purpose workflow orchestration of non-feature workloads to nothing — FPOS is feature-domain-specific, not a general scheduler; model training itself to training frameworks that consume the features FPOS produces.

Does NOT provide: a training loop, a model registry, an online feature cache, a general-purpose DAG UI, a BI/analytics layer, or a distributed compute engine — FPOS schedules work onto batch/stream engines, it does not reimplement Spark or Flink.

Non-goals.

FPOS is not a general workflow engine — Airflow/Dagster/Prefect exist for that; FPOS embeds only the DAG scheduling that feature pipelines need, with point-in-time correctness baked into the scheduling model itself, whereas a generic workflow engine has no notion of event time or label leakage. FPOS is not a serving layer: Feature-Store-122 already provides that, and the explicit contrast is that Feature-Store-122 computes nothing and serves everything at low latency (p99 single-digit-millisecond keyed lookups), while FPOS computes everything and serves nothing — it hands finished, versioned, lineage-tracked feature values to the store's write path. FPOS is not a training framework — it produces training-ready offline feature tables but does not train models.

Batch and streaming scope. FPOS treats batch and streaming as two execution modes of the same transform definition (Phase 6, §18), not two products. A pipeline may declare a batch source (lake/warehouse partitions), a stream source (Kafka/Pulsar topics), or both, and the point-in-time join engine and materialization writer are mode-agnostic: the offline path always runs in batch mode (possibly against a replayed stream), and the online path runs in streaming or micro-batch mode against the same transform code.

Deployment model. An orchestrator control-plane service (scheduler, dependency resolver, metadata store, lineage store) plus a pool of stateless execution workers (batch and streaming) plus connectors to batch sources (lake/warehouse) and streaming sources (Kafka/Pulsar) and sinks (offline store, online store via the feature store's write API). Kubernetes-first; the control plane is a small stateful core, workers are horizontally scalable and disposable.

Users/operators. ML platform engineers who define pipelines and transforms; data engineers who own source connectors and backfills; ML engineers who consume the offline/online feature contract; SREs who operate the scheduler and worker fleet and respond to leakage, skew, and freshness alerts.

What later phases unlock. Phase 1 unlocks dependency-aware scheduling; Phase 3 unlocks the anti-leakage join core that makes offline features trustworthy; Phase 5 unlocks true streaming freshness; Phase 7 unlocks safe historical backfill; Phase 8 unlocks the offline/online consistency guarantee that is the entire point of the system; Phase 11 unlocks the correctness benchmark that proves zero leakage and zero skew under chaos.

Language: Rust. Rationale: the scheduler and join engine are latency- and correctness-critical control-plane code where a GC pause or a null-pointer class of bug is unacceptable; Rust's ownership model lets the DAG and lineage graphs be shared across async tasks without data races; zero-cost abstractions keep the point-in-time join — the system's hot path — allocation-disciplined; the async ecosystem (Tokio) supports both the batch scheduler and the streaming engine's backpressure model natively. Rejected: Python — the natural ML-adjacent choice, but GIL-bound and unsuitable for a correctness-critical low-latency scheduler and join engine, acceptable only for the SDK/user-facing transform-authoring layer, not the runtime; Scala/JVM — Spark/Flink's native language, good ecosystem fit, but GC pauses and JVM startup cost are wrong for a control plane that must fail fast and restart cheaply; Go — simpler concurrency story than Rust, but its GC and weaker type system make the point-in-time join's temporal-correctness invariants harder to enforce at compile time.

Prerequisites: dataflow and stream-processing theory (Kleppmann; Akidau et al.); DAG scheduling and dependency resolution; event-time versus processing-time semantics and watermarks; ML feature-engineering practice (feature stores, training/serving skew); distributed-systems fundamentals (idempotency, exactly-once semantics, backpressure).

Timeline: Phase 0-2 (skeleton, scheduler, batch engine) 10-12 weeks; Phase 3-5 (point-in-time joins, materialization modes, streaming) 12-16 weeks; Phase 6-8 (unified transforms, backfill, offline/online consistency) 12-14 weeks; Phase 9-11 (lineage, quality, correctness benchmark) 8-10 weeks; production hardening 3-5 months beyond Phase 11.

2. Why Build This

Building FPOS is the direct, hands-on route to the two hardest unsolved problems in production ML infrastructure: label leakage and training/serving skew.

Key engineering domains exercised:

  • DAG dependency resolution and topological scheduling
  • Event-time semantics and watermark-based stream processing (Akidau et al.)
  • Point-in-time-correct temporal joins
  • Deterministic, replayable backfill
  • Unified batch/stream transform codegen
  • Feature versioning and lineage-graph maintenance
  • Data-quality and distribution-drift detection
  • Freshness-SLO enforcement
  • Offline/online consistency mechanisms
  • Idempotent materialization and exactly-once writes

Historically, feature platforms emerged because:

  • Ad-hoc offline notebooks computed features one way for training and a hand-ported version for serving, silently diverging (Sculley et al. 2015)
  • Naive joins against "current" tables leaked future information into training labels, producing offline accuracy that collapsed online
  • Backfilling months of history by hand was slow, error-prone, and non-reproducible
  • No system tracked which model was trained on which feature version, making incidents undebuggable
  • Streaming and batch feature logic were maintained as two separate codebases that drifted apart

The project develops engineering muscles in:

  • Temporal reasoning: event time vs. processing time vs. label time
  • Determinism as an architectural property, not a testing goal
  • Designing systems where an entire bug class (leakage) is structurally unrepresentable
  • Backfill-as-time-travel and its determinism requirement
  • Cross-system consistency (offline store vs. online store) without two-phase commit
  • Lineage-graph design for auditability at scale

Related systems: Airflow/Dagster/Prefect (DAG scheduling), Feast/Tecton (feature stores), Spark/Flink (batch/stream engines), Delta/Iceberg-family table formats (Data-Lake-Table-Format-214), TFX (validation and pipelines), dbt (batch transform DAGs).

Calibration value: implementing FPOS permanently improves the ability to reason about event-time correctness, deterministic replay, cross-system consistency without distributed transactions, and the specific silent-failure shape of ML data bugs — a leaking join does not crash, it just makes the model wrong in production months later.

What Mastery Looks Like

  • Explaining, from the DAG model outward, why a cycle in feature dependencies must be caught at compile time rather than at run time (Phase 0, §12)
  • Writing a topological scheduler that never reorders a node ahead of an unmaterialized dependency, including under partial failure (Phase 1, §13)
  • Implementing an as-of join whose worst case is still zero leakage, and proving it rather than merely testing for it (Phase 3, §15)
  • Explaining why a transform is a pure function of (entity, event_time, inputs) and what breaks the moment it isn't (Phase 6, §18; Phase 7, §19)
  • Reproducing a streaming run's exact output via batch backfill, byte for byte, over a historical window (Phase 7, §19)
  • Designing a mechanism that makes offline and online feature values provably equal for the same entity and timestamp without a distributed transaction (Phase 8, §20)
  • Building a lineage graph that can answer "which model, which run, which source version" for any feature value in production (Phase 9, §21)
  • Running a correctness harness that generates labeled data with known temporal structure and asserts zero leakage and zero skew under chaos (Phase 11, §23)

Pipeline DAG registry: the durable, versioned record of every declared pipeline's transforms, inputs, and outputs; it is the compile-time artifact from which everything downstream is derived, and it is where a cyclic or malformed definition is rejected before any compute is spent (I4).

Dependency resolver: converts the registry's node/edge graph into a validated topological order, detecting cycles and unready dependencies; it is a pure, stateless function of the DAG and re-runs identically for the same DAG hash.

Scheduler: fires time-triggered, event-triggered, and backfill-triggered runs against the resolved order, enforcing admission control and bounded queues (P13) so that no single trigger storm can exhaust the worker fleet.

Batch execution engine: runs transforms against lake/warehouse partitions for offline (training) computation and for backfill replay; it is one of two codegen targets for a single transform definition (P2).

Streaming execution engine: runs the same transform definition against Kafka/Pulsar topics with explicit event-time and watermark tracking (Akidau et al.), producing low-latency online updates.

Point-in-time join engine: the anti-leakage core; it enforces that every feature value joined to a label uses only source records whose event time precedes the label's timestamp, independent of whether the underlying execution was batch or streaming.

Materialization writer: commits the joined, transformed output to both the offline store and the online store using the identical transform version, which is the mechanism (not a test) that keeps the two consistent (I2).

Lineage/version tracker: an append-only graph recording which transform version, run, and source versions produced each feature value, queried for audits, incident forensics, and reproducibility.

Freshness/quality monitor: continuously measures materialization lag against declared SLOs and validates schema and distributional properties (Breck et al.), raising before stale or invalid data reaches serving.

Connectors: the pluggable source/sink layer (lake, warehouse, Kafka/Pulsar, Feature-Store-122's write API) that isolates the rest of the system from source-specific protocol details.

Persistence boundaries: metadata store (WAL-backed), lineage store (append-only), checkpoint storage (streaming engine), object storage (batch intermediates), offline store and online store (external systems, ADR-11/ADR-12).

Concurrency boundaries: scheduler admission queues, per-partition streaming state, worker execution pools, materialization commit leases.

Trust boundaries: the public operator API, the internal scheduler-to-worker RPC mesh, the tenant/namespace isolation boundary, the external-source ingress boundary, and the online-store write boundary shared with Feature-Store-122.

6. Design Principles

P1. Point-in-time correctness is the whole game: a feature join must use only data known as of the label's timestamp, because a single future-leaking join silently inflates offline accuracy and collapses in production (Sculley et al.).

P2. The same transformation definition produces both the offline (training) and online (serving) feature, so training/serving skew is structurally impossible, not merely tested for.

P3. A DAG node is a pure, versioned, backfillable function of its inputs — backfill is just re-running the DAG over a historical window, which only works if transforms are deterministic.

P4. Determinism is an architectural property enforced at compile time and by replay-hash comparison, not a hope that a test suite catches non-determinism.

P5. Backfill is time travel; it only works if transforms have no hidden wall-clock, randomness, or network dependence.

P6. Freshness is a contract (an SLO), not a best-effort characteristic — a violation must raise before a stale feature is served.

P7. Lineage must answer "what produced this value" from captured records, not from post-hoc reconstruction of logs.

P8. Watermarks, not wall-clock time, define when a window's data is complete enough to materialize (Akidau et al.).

P9. Incremental materialization must be provably equivalent to full materialization over the same window — idempotent and replayable.

P10. Offline/online consistency is enforced by a shared code path and shared point-in-time semantics, not by comparing values after the fact.

P11. A quality or schema violation halts propagation at the boundary where it is detected, never silently downstream.

P12. Every scheduling decision — trigger, backfill window, retry — must be explainable and reconstructable after the fact.

P13. Bound every queue, window, and state store; unbounded backfills and unbounded streaming state are outages waiting to happen.

P14. Fail closed on ambiguous DAG or version state — an unknown dependency or unrecognized feature version blocks scheduling rather than guesses.

8. Domain Model

DAG Model

A pipeline DAG is a set of nodes (transforms) and edges (data dependencies). Worked example:

Node Transform Depends On
A ingest_raw_txn (source)
B user_agg_7d A
C merchant_agg_7d A
D risk_score B, C

Topological schedule: [A] -> [B, C] (parallel) -> [D]. Equation: a valid schedule order satisfies ∀(u,v) ∈ E, order(u) < order(v) (I4).

Transform Contract

Property Requirement
Inputs declared entity keys + upstream feature versions, no hidden reads
Output exactly one versioned FeatureId per transform
Determinism pure function of (entity, event_time, inputs) — no wall clock, no randomness, no network (P3, P5)
Batch/stream duality one definition compiles to both an exec-batch plan and an exec-stream operator (P2, ADR-13)

Event-Time, Processing-Time, and Watermarks

Concept Definition Example
Event time when the event occurred at the source a transaction's timestamp
Processing time when FPOS observes/handles the event when the streaming engine reads the Kafka record
Watermark W(t) estimated point below which no more events with event_time < t will arrive (Akidau et al.) W = max(event_time seen) - allowed_lateness
Window (Fixed) [start, start+size) non-overlapping hourly aggregation
Window (Sliding) overlapping, period < size 7-day average updated hourly
Window (Session) closes after gap of inactivity per-visit session aggregate

Point-in-Time-Correct Join Semantics

Named steps: (1) for each label row (entity, label_time), (2) select from the feature source only rows with event_time <= label_time, (3) pick the most recent such row per entity (as-of semantics), (4) join. Worked example contrasting correct vs. leaking:

Entity Feature events (time:value) Label time Correct as-of value Naive "latest" value
U1 t1:0.2, t3:0.9 t2 0.2 (only t1 known at t2) 0.9 — uses t3, future data, LEAKS

The naive join lets the model see post-label information correlated with the label itself, producing an inflated offline metric — the "accuracy illusion" — that collapses in production because at serving time t3 has not happened yet (Sculley et al.).

Incremental vs. Full Materialization

Signal Choose Incremental Choose Full
Data volume already materialized large, append-only small or first run
Transform change additive, backward-compatible breaking (new version)
Freshness SLO tight (P6) loose, periodic
Determinism risk low, well-tested transform new/unverified transform (safer to fully recompute and diff)

Backfill Model

Backfill replays the same transform code over a historical window, parallelized by sub-window. Determinism requirement (I3): hash(transform(inputs_over_window)) from the backfill run must equal the hash recorded from the original streaming/batch run for that window.

FeatureVersion(risk_score, v3)
   depends_on -> FeatureVersion(user_agg_7d, v2)
   depends_on -> FeatureVersion(merchant_agg_7d, v1)
   produced_by -> RunId(run-88213)

Lineage edges are append-only (I9); a new transform version produces a new FeatureVersion node rather than mutating the old one (I5).

Offline/Online Materialization-Consistency Mechanism

Because the same transform version and the same point-in-time semantics feed both the offline write and the online write (P2, P10), consistency reduces to: skew = |online_value(entity, t) - offline_value(entity, t)| must equal 0 whenever both are computed from the same FeatureVersion. This is enforced by construction (shared code path, I2) and verified continuously (§28) rather than reconciled after divergence.

Malformed and Hard Examples

  • A leaking join: a transform joins against "current" state instead of as-of state, admitting post-label events (I1 violation)
  • A non-deterministic transform breaking backfill: hidden wall-clock or RNG use makes replay hashes diverge (I3 violation)
  • A late-arriving record past the watermark: arrives after W(t) has advanced past its event time, requiring an explicit late-data policy (Akidau et al.)
  • A schema drift: an upstream source adds/removes a field without a migration plan (I10 violation)
  • A DAG cycle: a transform is declared to (transitively) depend on its own output (I4 violation)
  • An offline/online skew: a bug in one codegen target only, breaking the single-definition guarantee (I2/P2 violation)

Failure-Path Example

An operator ships a transform that calls the system clock inside a feature computation, violating purity (P5). The streaming run succeeds and materializes correctly. Three months later a backfill is triggered to reprocess that historical window; the backfill's replay hash diverges from the original streaming hash because the clock call returns a different value on each run. The conformance harness (I3) raises NonDeterministicBackfill. Recovery quarantines the transform version and requires a deterministic rewrite that derives all time-dependent behavior from event_time rather than wall-clock time.

11. Core Schema & Types

// Ownership: value type, Copy; Mutation: immutable; Persistence: metadata-store row;
// Serialization: protobuf uint64 wrapper; Compatibility: stable wire ID 1
struct PipelineId(u64);

// Ownership: value type; Mutation: immutable per version; Persistence: metadata-store;
// Serialization: protobuf; Compatibility: additive fields only (I5)
struct Dag {
    pipeline_id: PipelineId,
    dag_hash: [u8; 32],       // content hash, determinism check target (I3)
    nodes: Vec<Node>,
    edges: Vec<Edge>,
    version: u32,
}

// Ownership: owned by Dag; Mutation: immutable after compile; Concurrency: shared via Arc<Dag>
struct Node { id: NodeId, transform: Transform, inputs: Vec<NodeId> }

struct NodeId(u32);           // scoped to one Dag, not globally unique
struct Edge { from: NodeId, to: NodeId }  // from produces an input consumed by to

// Ownership: owned by Node; Mutation: immutable, versioned (ADR-13, ADR-14)
struct Transform {
    transform_id: String,
    version: FeatureVersion,
    codegen_target: CodegenTarget,   // P2, ADR-13
    determinism_checked: bool,        // ADR-10 purity-lint result
}
enum CodegenTarget { Batch, Stream, Both }
// Ownership: value type; Persistence: metadata-store; Compatibility: append-only versions (I5)
struct FeatureId(String);
struct FeatureVersion { feature_id: FeatureId, version: u32, content_hash: [u8; 32] }

// Ownership: value type; Serialization: bytes, domain-defined key schema
struct EntityKey(Vec<u8>);

// Ownership: value type, Copy; Concurrency: compared via total order (I1, I7)
struct EventTime(i64);        // micros since epoch, UTC

// Ownership: value type; Mutation: monotonic non-decreasing per partition (I7)
struct Watermark(EventTime);

// Ownership: value type; consumed by the streaming engine and materialization windows
struct Window { start: EventTime, end: EventTime, kind: WindowKind }
enum WindowKind { Fixed, Sliding { period_us: i64 }, Session { gap_us: i64 } }
// Ownership: owned by scheduler-core; Persistence: WAL-backed schedule log
struct Schedule { pipeline_id: PipelineId, trigger: Trigger }
enum Trigger {
    Time { cron: String },
    Event { topic: String },
    Backfill { window: Window, parallelism: u32 },
}

// Ownership: transient, owned by the scheduler during execution; Concurrency: single-owner lease
struct Backfill {
    pipeline_id: PipelineId,
    window: Window,
    determinism_hash_expected: Option<[u8; 32]>,   // I3 check target
    state: RunState,
}
enum MaterializationMode { Incremental, Full }
// Ownership: transient, constructed per execution; Concurrency: read-only during join
struct PointInTimeJoin { as_of: AsOf, left: Source, right: Source }

// Ownership: value type; I1 boundary — right.event_time <= as_of.label_time enforced here
struct AsOf { label_time: EventTime }

trait Source { fn read(&self, window: Window) -> DataFrameHandle; }
trait Sink { fn write(&self, batch: MaterializedBatch) -> Result<CommitToken, MaterializeError>; }

// Ownership: external system handle; FPOS is a client, not the owner (§1 delegation)
struct OfflineStore { connector: Connector }
struct OnlineStore { connector: Connector }   // delegates to Feature-Store-122 (ADR-12)

trait Connector { fn kind(&self) -> ConnectorKind; }
enum ConnectorKind { Lake, Warehouse, KafkaPulsar, FeatureStore }
// Ownership: append-only; Persistence: lineage store; Mutation: never (I9)
struct Lineage {
    feature_version: FeatureVersion,
    produced_by: NodeId,
    run_id: RunId,
    sources: Vec<FeatureVersion>,
}
struct RunId(u64);

struct QualityCheck { schema_check: bool, drift_score: f64, passed: bool }   // Breck et al.
struct FreshnessSlo { feature_id: FeatureId, max_lag_us: i64 }               // I6

enum RunState { Defined, Scheduled, Running, Materialized, Backfilling, Stale, Failed }

// error taxonomy
enum OrchestrationError {
    CyclicDag(PipelineId),
    LeakageDetected { node: NodeId, offending_event_time: EventTime },              // I1
    NonDeterministicBackfill { pipeline_id: PipelineId, expected: [u8; 32], actual: [u8; 32] }, // I3
    SchemaBreak { feature_id: FeatureId },                                          // I10
    FreshnessSloViolation { feature_id: FeatureId, lag_us: i64 },                   // I6
    MaterializeError(MaterializeError),
}
enum MaterializeError { DuplicateCommit, SinkUnavailable, IdempotencyConflict }

  1. An off-by-one on the <= vs. < boundary at event_time == label_time (must be an explicit documented policy, not an accident)
  2. Assuming a source is pre-sorted by event time and skipping the as-of selection's correctness check
  3. Leaking through a dependency's dependency — a leaking join two hops upstream still leaks into the final feature, so the full lineage chain must be validated, not just the immediate join
  4. Letting the naive join fixture bit-rot instead of running it every CI cycle as the negative baseline

  • As-of index construction cost per entity-history size (§31 Big-O)
  • Join cost blow-up for entities with very long histories (the "hot entity" problem)

15.8 Edge Cases

  • An entity with thousands of feature events between two label times

  • Every pit-join invocation emits a trace span with label_time, admitted_event_time_max, and an assertion result
  • The leakage-fuzz corpus runs on every CI build, not just nightly, given its status as the primary correctness gate (§28)

23.6 Pitfalls

  1. Running the correctness harness against synthetic data that doesn't actually exercise realistic leakage-prone patterns — it must include adversarially-constructed temporal structures
  2. Chaos scenarios that are too gentle to actually trigger the failure paths they claim to test
  3. Performance-regression gating with a tolerance loose enough to let a slow creep through release after release
  4. Treating a clean soak-test run as sufficient without also validating resource-usage stability over the full 72 hours, since a slow leak may not manifest in the first hour

23.7 Performance Concerns

  • Correctness-harness runtime itself must stay within CI time budgets despite exercising the full system
  • Chaos-injection overhead must not itself mask or introduce false invariant violations
  • Soak-test infrastructure cost at sustained peak throughput

23.8 Edge Cases

  • A chaos scenario that overlaps two failure modes simultaneously, e.g. a broker outage during an active backfill
  • A correctness-harness run that itself hits a bug in the synthetic-data generator, producing a false leakage signal
  • A performance regression that only manifests under the specific combination of high backfill parallelism and live-streaming load

23.9 Failure Analysis

Failure class: the correctness harness itself produces a false positive or false negative. Detection: manual review triggered whenever the harness's pass/fail status changes without a corresponding code change. Recovery: treat the harness as a first-class piece of software subject to its own regression tests, not an infallible oracle.

23.10 Operational Notes

  • The correctness harness's pass/fail status is the single most important CI signal in the entire system — no other check overrides it
  • Publish soak-test resource-usage graphs (memory, lineage-graph growth, delta-log size) as a standing artifact for every release candidate
  • Archive every chaos-test run's full trace for forensic replay, since chaos failures are often non-reproducible on demand

26. Operational Readiness

Named metrics: leakage_violations_total, skew_rate, backfill_determinism_mismatch_total, backfill_throughput_rows_per_hour, watermark_lag_seconds, freshness_violations_total, quality_check_failures_total, pipeline_success_rate, scheduling_latency_seconds, consistency_lag_seconds, lineage_write_lag_seconds.

Tracing: end-to-end spans per pipeline run from trigger through materialization, with dedicated child spans for the pit-join step (label_time, admitted_event_time_max) and the dual-write step (offline commit token, online commit token), enabling a single trace to answer "did this run leak or skew."

Structured logging: JSON-only (ADR-21), correlation IDs and tenant IDs mandatory on every log line, run_id and dag_hash attached to every pipeline-execution log for lineage cross-referencing.

Dashboards: a leakage/skew dashboard (top-level, always visible) showing leakage_violations_total and skew_rate at zero as the expected steady state; a freshness dashboard per feature; a backfill-throughput and determinism dashboard; a lineage-graph growth dashboard; a scheduler fairness/queue-depth dashboard.

Alerting philosophy: a leakage-check failure or an offline/online-skew spike is the alert that matters most in this system — it pages immediately and is treated as a correctness incident, not an operational one. Freshness and drift alerts are second-tier: they page during business hours unless they threaten an SLO breach. Resource and scheduling alerts are third-tier: they inform capacity planning.

SLOs: control-plane availability 99.95%; zero label leakage (I1); offline/online consistency lag per §4; freshness per feature's declared FreshnessSlo; backfill determinism 100% (I3).

Incident response: named runbooks under docs/runbooks/ — leakage-incident.md (walks the §7 debugging methodology), skew-divergence.md (Phase 8 failure analysis), backfill-nondeterminism.md (Phase 7 root-cause tooling), stale-feature.md (Phase 10 attribution), drift-detection.md (Phase 10 drift triage).

Backup/restore: metadata-store WAL continuously replicated; lineage-graph snapshotted daily with point-in-time recovery; offline-store recovery delegated to Data-Lake-Table-Format-214's own durability guarantees; online-store recovery delegated to Feature-Store-122.

Deployment topology: Kubernetes-first, control plane as a small stateful StatefulSet, execution workers as an elastic Deployment/HPA pair for batch and streaming pools respectively.

Canary/rollback/migration: new transform versions deploy canary-first against a shadow (non-serving) online-write path, verified against the skew-sampling job before promotion; DAG-schema migrations are additive-only within a major version (§27); rollback reverts to the last immutable FeatureVersion (I5), which is always safe by construction.

27. Compatibility & Versioning

Feature-definition versioning: every FeatureVersion is immutable and content-hashed (I5, ADR-14); a breaking change always produces a new version, never a mutation.

Transform-language versioning: the DSL (Phase 6, ADR-13) is versioned independently of individual transforms; a DSL version bump must remain able to compile all previously-registered transform ASTs, or provide an explicit, tooled migration.

DAG-schema evolution: Dag and Node wire schemas (§11) evolve additively; unknown fields are ignored on read (protobuf-style forward compatibility), and a removal or type change requires a major version bump with a migration path documented in docs/adr/.

Offline/online store contract stability: the Source/Sink trait boundary (§11) and the Feature-Store-122 write-API contract (ADR-12) are treated as stable public interfaces; a breaking change to either requires coordinated version negotiation with Feature-Store-122's own compatibility guarantees.

Lineage-format versioning: lineage records (§11) are append-only and self-describing with a schema version field; historical lineage remains queryable across format versions via a read-time adapter layer.

API stability: the operator API (CLI/SDK) follows SemVer; a major version bump is required for any breaking change to the pipeline-definition surface.

Migration and deprecation: deprecated transform versions remain queryable (I5, I9) but are excluded from new scheduling after a documented sunset window; deprecation notices surface in cli sdk info and in the lineage-query API's metadata.

SemVer: applied uniformly across sdk-rust, the DSL, and the wire protocol; a MAJOR bump signals a breaking change to any of the stable contracts above.

28. Testing & Verification Strategy

Unit tests: per-crate coverage of dag-model, dep-resolver, pit-join, materialize logic in isolation.

Integration tests: end-to-end pipeline runs against a local docker-compose stack (Postgres metadata-store, Kafka), exercising the full scheduler-to-materialization path.

Property tests (ADR-24, proptest): a point-in-time join never includes a record newer than the label time — leakage is structurally impossible (I1); a backfill over a window reproduces the original streaming result byte-for-byte (I3); offline and online materialization agree for the same entity and timestamp (I2); the DAG scheduler respects all dependencies under randomized timing (I4).

The leakage-and-skew correctness harness (Phase 11, §23) is the primary named CI gate: it generates labeled data with known temporal structure, runs training and serving, and asserts zero leakage and zero skew — this is the single check that blocks every release.

Differential testing: batch vs. streaming codegen output compared against each other (Phase 6, I2) and the pit-join as-of result compared against a reference as-of-join implementation.

Fuzzing (ADR-25): cargo-fuzz targets the DAG/transform-definition parser (Phase 0/6), feeding malformed pipeline definitions to catch parser crashes or unsafe acceptance.

Chaos testing: source outages, late data past the watermark, and worker failures mid-backfill (Phase 11, §23.2), each tied to a named FM- class in §25.

Deterministic replay: production-incident inputs replayed offline to reproduce a bug bit-for-bit, used both for debugging and as regression fixtures.

Soak testing: 72-hour sustained peak-throughput runs (Phase 11) validating no unbounded resource growth.

Fault injection: metadata corruption, delayed heartbeats, broker disconnects, partial checkpoints, and clock skew, each mapped to a §25 failure class.

Perf-regression gating: every release candidate is checked against the §30 M1... targets; a regression beyond tolerance blocks merge.

Each verification layer ties to specific invariants (I1-I13) and to the named fixtures enumerated in each phase's N.5 subsection.

29. Build & Release Engineering

Reproducible builds: pinned toolchain, cargo --locked, deterministic build timestamps (ADR-28) — required so that a determinism-harness mismatch (I3) is trusted as a code bug, not a build artifact.

Artifact signing: all release artifacts (container images, CLI binaries) are signed; signatures verified at deployment time.

SBOM: generated per release via cargo deny plus a container-image SBOM tool; retained alongside release artifacts for supply-chain auditability (T10).

Release channels: dev, staging, stable, LTS — mirroring the canary/rollback model in §26.

CI/CD topology: build -> lint/clippy/cargo deny -> unit/integration tests -> the leakage/skew correctness gate (§23, §28, blocking) -> performance-regression gate (§30, blocking) -> artifact build/sign -> SBOM attach -> deploy to dev, promote on green.

Version stamping: every binary embeds its git commit hash, DSL version, and wire-schema version for runtime introspection (cli version --verbose).

Provenance/attestation: build provenance attested via SLSA-style metadata attached to each release artifact, recording the exact CI job and inputs that produced it.

Dependency auditing: cargo deny runs on every CI build, blocking on any known-vulnerable or disallowed-license dependency (ADR-30).

30. Performance Engineering

Methodology: the point-in-time-join cost is the dominant compute in the system and is profiled first (entities × average history depth); backfill parallelism is tuned against the worker-pool ceiling (I11); streaming state size is tracked against active-key cardinality; materialization write throughput is benchmarked against the freshness SLO it must sustain; batch/stream engine overhead (delegated to DataFusion/Spark and Flink respectively, ADR-04/ADR-05) is profiled at the connector boundary; tail latency (p99, not just p50) is the primary acceptance metric throughout, since a single slow partition or hot entity is what actually causes SLO breaches in production.

31. Scalability Analysis

What stays constant: the pit-join as-of algorithm's per-entity cost given entity-key partitioning (§15); the DAG-model's compile-time validation cost per node, which does not depend on data volume.

What grows, with Big-O: point-in-time joins are the expensive part, growing roughly as O(entities × avg_history_events) per label batch — the dominant cost in the system (M1); backfill wall-clock cost grows linearly in window_size × DAG_node_count ÷ worker_parallelism (§34); streaming state memory grows with active key cardinality, O(active_keys × state_bytes_per_key); lineage-graph storage grows with O(features × versions × avg_edges_per_version).

Named bottlenecks: the metadata-store's single-writer WAL for high-frequency scheduling decisions; the lineage-store's write path under high node-execution throughput (FM-10); the pit-join engine for "hot entities" with unusually long histories; checkpoint-barrier propagation across a large streaming partition fan-out.

Scaling backfills: increase worker parallelism up to the admission-controller ceiling (I11); partition the backfill window into smaller sub-windows to parallelize I/O against the offline store; shard by entity-key range for embarrassingly parallel history-independent transforms.

Scaling streaming workers: shard by source-partition key, scale the worker pool with Kafka/Pulsar partition count, and bound per-partition state to avoid a single hot partition dominating checkpoint time.

Batch/stream unification cost: maintaining one DSL that compiles to two backends (Phase 6) costs compile-time complexity and a mandatory differential-harness run on every change, but this cost is fixed and amortized, whereas the skew risk of two hand-maintained implementations grows unboundedly with pipeline count.

Practical ceilings: 10,000 DAG nodes per pipeline and 3 years of backfillable history are the practical ceilings at the current metadata-store and lineage-store design (§4); beyond those, the levers are metadata-store sharding by namespace, lineage-graph partitioning by feature-family, and the deferred adaptive DAG/join-order optimization (PhaseDeferred, §1).

32. Mental Models & First Principles

MM1. A feature pipeline's one job is to never let the future leak into the past — every hard bug is a timestamp that crossed the label boundary (Sculley et al.).

MM2. Training and serving skew is guaranteed unless one definition generates both paths, so the architecture must make two code paths impossible, not merely tested.

MM3. A backfill is time travel, and time travel only works if your transforms are pure functions of their inputs.

MM4. Watermarks are a bet, not a fact — they estimate completeness, and every system built on them needs an explicit policy for when the bet is wrong (Akidau et al.).

MM5. Lineage is not documentation, it is the only reliable way to answer "why is this feature wrong" after the fact.

MM6. Freshness is a promise made to a consumer, not a nice-to-have — treat an SLO breach with the same operational severity as a bug.

MM7. Incremental materialization is an optimization layered on a correctness baseline (full recompute), never a replacement for it — that is the entire reason reconciliation exists.

MM8. The offline store and the online store are two views of one truth; if they can diverge, the architecture has already failed — no amount of after-the-fact monitoring fixes that.

Uber Michelangelo established the reference architecture for an end-to-end ML feature platform, but its batch and streaming compute paths remain separately maintained, leaving a residual skew risk that FPOS's single-definition model (Phase 6) is designed to close entirely.

Airbnb Chronon (successor to Zipline) is the closest architectural sibling to FPOS: its central contribution is a point-in-time-correct join computed from one transform definition for both offline and online paths, which is exactly the load-bearing mechanism this blueprint's Phase 3 and Phase 6 formalize and extend with an explicit determinism and lineage layer.

Tecton packages a managed, cloud-hosted version of the same computation-plus-consistency idea, trading operational control for convenience; FPOS is architected as the self-hosted, from-scratch equivalent of that computation layer.

Feast is the key store-side contrast named in §1: Feast deliberately does not compute features, it only stores and serves them — this is the precise split FPOS assumes when it delegates serving to Feature-Store-122 and keeps all computation, scheduling, and correctness guarantees for itself.

TFX contributes the data-validation model (Breck et al.) that FPOS's quality crate (Phase 10) adopts directly, but TFX is a training-pipeline validation library, not a feature-computation-and-serving orchestrator, so it is a component-level rather than architectural-level comparison.

34. Back-of-Envelope Capacity Model

  1. Point-in-time-join compute: 50,000,000 entities × 200 avg history events/entity × 50ns/event compare = 500,000,000,000 ns = 500 s of raw single-threaded compute for one full offline join pass; distributed across 500 batch workers, 500 s ÷ 500 = 1 s wall-clock per full pass.

  2. Backfill wall clock: a 90-day, 2,000,000,000-row backfill window at the declared 50,000,000 rows/hour/worker ceiling (§4) with 64 workers gives 64 × 50,000,000 = 3,200,000,000 rows/hour aggregate capacity; 2,000,000,000 ÷ 3,200,000,000 ≈ 0.625 h raw I/O time; applying a 4x overhead factor for as-of-join and materialization-write cost yields ≈ 2.5 h, within the §4 target of < 4 h.

  3. Streaming state memory: 10,000,000 active entity keys × 2 KB avg state/key = 20 GB aggregate state, sharded across streaming workers, e.g. 20 workers × 1 GB each.

  4. Materialization write throughput for the freshness SLO: to keep 95% of features fresher than 5 min (§4) across 50,000,000 entities updated on average hourly, sustained write rate ≈ 50,000,000 ÷ 3,600 ≈ 13,900 writes/s, well inside the M7 headroom.

  5. Offline/online consistency-lag budget: dual-write fan-out adds an estimated 200-800 ms serialization-and-network hop per batch commit, consistent with the < 30 s median target (§4) with wide margin for retry/backoff.

  6. Lineage-graph storage at the §4 ceiling: 10,000,000 feature-version nodes × 100 avg edges/node × 64 bytes/edge = 64,000,000,000 bytes = 64 GB for the full edge set.

  7. Single-worker sustainable data volume: given the 50,000,000 rows/hour/worker backfill ceiling sustained across a 24 h window, one worker sustains up to 1,200,000,000 rows/day; hitting the aggregate 5,000,000 rows/s target (§4) then requires 5,000,000 × 86,400 ÷ 1,200,000,000 ≈ 360 workers at full-day sustained throughput, comfortably inside the §4 worker-count ceiling of 2,000.

36. Alternative Architectures (Roads Not Taken)

Alt A: Batch-only pipeline
[Lake/Warehouse] -> [Airflow DAG] -> [Spark Batch Job] -> [Offline Table]
                                                        -> (periodic export) -> [Online Cache]

Winning regime: pipelines with no low-latency serving requirement and a daily/hourly cadence, e.g. a monthly risk report. Real embodying system: dbt-plus-Airflow batch ELT pipelines. Why rejected here: online features go stale between batch runs, violating the freshness SLO (§4, I6), and there is no watermark-based streaming freshness path at all.

Alt B: Streaming-only pipeline
[Kafka/Pulsar] -> [Flink Job: windows + watermarks] -> [Online Store]
                                                     -> (replay from cold storage) -> [Offline Table]

Winning regime: pipelines where freshness dominates and deep-history reprocessing is rare, e.g. real-time fraud signals with short retention. Real embodying system: pure Flink-based feature computation (Carbone et al.). Why rejected here: backfilling months or years of history through a purely streaming engine is operationally expensive, and full-history batch training-table generation becomes second-class.

Alt C: Inline compute at serving time
[Request] -> [Serving Service: compute feature on demand] -> [Response]
                        (no materialization, no pre-computation)

Winning regime: rarely-read, cheap-to-compute features where any staleness is unacceptable, e.g. a trivial real-time inventory lookup. Real embodying system: request-time feature computation as used in some low-feature-count online-only recommender stacks. Why rejected here: recompute-per-request cost and latency do not scale to FPOS's throughput targets (§4), and every request pays the full transform cost with no reuse.

Alt D: Lambda architecture (separate batch + speed layers)
[Batch Layer: Spark]  --\
                         >-- [Serving Layer: merge] -> [Online Store]
[Speed Layer: Flink]  --/

Winning regime: legacy systems that already have separate, independently-evolved batch and streaming codebases and cannot yet unify them. Real embodying system: the classic Lambda architecture (batch layer, speed layer, serving layer) popularized before the Dataflow Model. Why rejected here: this is precisely the two-codepath skew risk that FPOS's unified batch/stream transform definition (Phase 6, P2) exists to eliminate — Lambda architectures are the historical embodiment of the training/serving-skew problem this project targets (Kleppmann; Akidau et al.).

38. Glossary

Feature — a computed value derived from raw data, used as model input. Feature pipeline — the DAG of transforms that produces a feature from its sources. Feature store — the system that stores and serves computed features (Feature-Store-122; explicit non-goal of FPOS). DAG — directed acyclic graph, the pipeline's dependency structure. Transform — a versioned, pure function producing one feature from its inputs. Materialization — the act of committing a computed feature value to a store. Incremental materialization — updating only the delta since the last materialized state. Full materialization — recomputing and replacing an entire window's output. Backfill — replaying a transform over a historical window. Point-in-time correctness — the guarantee that a join uses only data known as of the label's timestamp. As-of join — a join that selects the most recent record at or before a given timestamp. Label leakage — a training feature that incorporates information not available at prediction time. Training/serving skew — divergence between the feature values computed offline for training and online for serving. Event time — the timestamp at which an event actually occurred. Processing time — the timestamp at which a system observes/handles an event. Watermark — an estimate of the point below which no more late data is expected. Windowing — grouping events into fixed, sliding, or session intervals for aggregation. Late-arriving data — an event that arrives after its window's watermark has passed. Lineage — the recorded provenance chain from a feature value back to its raw sources. Feature version — an immutable, content-hashed instance of a feature's definition and output. Freshness SLO — a declared bound on how stale a materialized feature may be. Data drift — a statistically significant change in a feature's distribution over time. Schema validation — checking that data conforms to a registered structural contract. Offline store — the batch-oriented store used for training-data generation. Online store — the low-latency store used for serving (Feature-Store-122). Batch/stream unification — compiling one transform definition to both batch and streaming execution targets. Lambda architecture — the classic pattern of separate batch and speed layers, rejected by FPOS's unified model. Determinism — the property that a function always produces the same output for the same input. Idempotency — the property that repeating an operation has no additional effect beyond the first application. Exactly-once semantics — a guarantee that an effect is applied precisely once despite retries. Commit token — a unique identifier used to detect and reject duplicate materialization writes. Admission control — gating dispatch of new work against available capacity. Backpressure — a signal that propagates upstream to slow producers when downstream capacity is exceeded. Fairness scheduling — allocating scheduling capacity across tenants to prevent starvation. Dependency resolver — the component that computes a valid execution order from a DAG. Topological sort — an ordering of DAG nodes such that every dependency precedes its dependents. Cycle detection — identifying an invalid circular dependency in a DAG. Entity key — the identifier (e.g., user ID) a feature is computed per. Session window — a window that closes after a period of inactivity. Sliding window — an overlapping window advancing by a period shorter than its size. Fixed window — a non-overlapping window of constant size. Allowed lateness — the configured grace period during which late data is still admitted into a window. Checkpoint — a durable snapshot of execution/streaming state used for recovery. Reconciliation job — a periodic job comparing incremental state against a full recompute. Skew-sampling job — a periodic job comparing offline and online materialized values for equality. Purity lint — a static check rejecting non-deterministic constructs in a transform. Differential testing — comparing two implementations' outputs on the same input to detect divergence. Chaos testing — deliberately injecting failures to validate recovery behavior. Soak test — a sustained-load test run over an extended duration to detect slow degradation. Replay hash — a content hash used to verify that a backfill reproduces an original run exactly. Cold start — a first-time backfill or materialization with no prior baseline to compare against. RTO — recovery time objective, the maximum acceptable time to restore service after a failure. RPO — recovery point objective, the maximum acceptable data loss measured in time. SLO — service-level objective, a measurable target for a system property. SBOM — software bill of materials, an inventory of a build's dependencies. Provenance — the verifiable record of how and from what an artifact or value was produced. Tenant isolation — the guarantee that one tenant's execution or data cannot affect or be observed by another.
