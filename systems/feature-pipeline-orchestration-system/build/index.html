⬜ Phase 0 — Skeleton, DAG Model, and CI §12

Objectives
  • Establish the Rust workspace and crate boundaries (§10)
  • Implement the DAG/Node/Edge/Transform types (§11) with static acyclicity checks (I4)
  • Stand up CI with the leakage/skew correctness gate placeholder (ADR-26)
  • Build shared telemetry, config, and error-taxonomy primitives (common)
  • Establish reproducible-build tooling (ADR-28)
Deliverable

A compiling workspace with a validated DAG model, cycle detection, CI green on every commit, and structured telemetry emitted from a minimal health-check service.

Acceptance
  • 100% of injected cyclic-DAG fixtures rejected at compile-time validation (I4)
  • dag_hash is byte-identical across 1,000 repeated compilations of the same DAG definition (P3, feeds I3)
  • CI green rate > 99% over 50 consecutive commits
  • Service startup < 2 s with structured logs and trace export validated
Fixtures
  • fixtures/dag/cyclic-simple.yaml — direct two-node cycle
  • fixtures/dag/cyclic-transitive.yaml — cycle via three hops
  • fixtures/dag/valid-diamond.yaml — the worked DAG example from §8
  • fixtures/hash/repeat-compile-1000.bin — determinism-of-hash regression
Pitfalls
  1. Treating dag_hash as a nice-to-have instead of the load-bearing input to Phase 7's determinism check
  2. Allowing floating-point or HashMap-iteration-order non-determinism into the hash computation
  3. Skipping cycle detection for "obviously fine" hand-written example DAGs
  4. Under-specifying the error taxonomy early, forcing breaking changes later (I10-adjacent risk)

⬜ Phase 1 — Dependency Resolver and Topological Scheduler §13

Objectives
  • Convert a validated Dag into a topological execution order
  • Implement the scheduler's time, event, and backfill trigger model (ADR-03)
  • Implement bounded admission control and backpressure (P13, ADR-29)
  • Persist every scheduling decision to a WAL for reconstruction (I13)
Deliverable

A scheduler that turns a resolved DAG into a dependency-respecting, fairness-aware, admission-controlled dispatch stream, with every decision replayable from the WAL.

Acceptance
  • Scheduling latency (trigger to dispatch) p95 < 200 ms, p99 < 750 ms (§4)
  • Zero dispatches of a node ahead of an unmaterialized dependency across 100,000 randomized DAG/timing fuzz runs (I4)
  • WAL replay reconstructs an identical dispatch order for a fixed input trace (I13)
  • No tenant starves another under a 10x load-imbalance fixture (fairness)
Fixtures
  • fixtures/scheduler/dependency-violation-attempt.bin
  • fixtures/scheduler/starvation-load.bin
  • fixtures/scheduler/wal-replay-determinism.bin
  • fixtures/scheduler/backfill-trigger-overlap.bin
Pitfalls
  1. Priority inversion between backfill and live-trigger traffic
  2. Queue growth without bound during a trigger storm (violates P13/ADR-29)
  3. Dispatching a node whose dependency is Stale, not just checking for Materialized (subtle I4/I12 interaction)
  4. WAL sequence gaps under concurrent writers
  5. Heartbeat storms overwhelming the control plane at high worker counts

⬜ Phase 2 — Batch Execution Engine §14

Objectives
  • Implement exec-batch: execute a transform's batch codegen target against lake/warehouse partitions
  • Support offline (training-table) computation and lay groundwork for backfill reuse (Phase 7)
  • Integrate with connectors for lake/warehouse reads (ADR-11)
  • Establish lineage-capture hooks at the execution boundary (groundwork for Phase 9)
Deliverable

A working batch execution engine that runs a topologically-ordered DAG's batch codegen target end-to-end against lake/warehouse sources and produces lineage-stub records.

Acceptance
  • Sustained batch throughput >= 5,000,000 rows/s aggregate across the worker fleet at target worker count (§4)
  • Node-level recompute-on-failure succeeds without operator intervention for single-worker failures
  • Zero lost committed partitions across 10,000 injected worker-kill fuzz iterations
Fixtures
  • fixtures/batch/recompute-on-worker-kill.bin
  • fixtures/batch/partition-write-idempotency.bin
  • fixtures/batch/large-fanout-diamond.yaml
Pitfalls
  1. Full-DAG recompute on a single leaf-node failure instead of lineage-scoped recovery (Zaharia et al.)
  2. Partition writers that are not idempotent under retry (sets up an I8 violation later)
  3. Treating batch throughput numbers from a small fixture as representative of the 10,000-node ceiling
  4. Silent schema coercion on read from the offline store

⬜ Phase 3 — Point-in-Time-Correct Joins (the Anti-Leakage Core) §15

Objectives
  • Implement pit-join: the as-of join engine enforcing I1 (zero label leakage)
  • Formalize the point-in-time join semantics from §8 as an executable operator
  • Build the leakage-detection assertion library used by every subsequent phase's fixtures
  • Establish the accuracy-illusion regression fixture as a permanent CI citizen
Deliverable

A point-in-time join engine that is structurally incapable of admitting a leaking row, with the deliberately-leaking naive join retained solely as a negative fixture demonstrating the accuracy illusion (Chronon/Zipline's point-in-time join is the reference model).

Acceptance
  • 0 leakage violations across the full leakage-fixture corpus, including 1,000,000 randomized entity/event/label-time fuzz combinations (I1)
  • The deliberately-leaking naive join fixture reproduces the accuracy-illusion pattern from §8 (inflated offline metric, admitted event_time > label_time), giving the harness a known-bad baseline
  • As-of join latency scales sub-linearly in total history size given entity-key partitioning (validated against the §31 Big-O model)
Fixtures
  • fixtures/pit-join/leakage-fuzz-1000000.bin — randomized entity/event/label-time leakage sweep
  • fixtures/pit-join/accuracy-illusion.yaml — the §8 worked example, both correct and naive results recorded
  • fixtures/pit-join/tie-break-same-timestamp.bin — two feature events at exactly label_time
  • fixtures/pit-join/no-prior-value.bin — entity with no feature event before label_time
Pitfalls
  1. An off-by-one on the <= vs. < boundary at event_time == label_time (must be an explicit documented policy, not an accident)
  2. Assuming a source is pre-sorted by event time and skipping the as-of selection's correctness check
  3. Leaking through a dependency's dependency — a leaking join two hops upstream still leaks into the final feature, so the full lineage chain must be validated, not just the immediate join
  4. Letting the naive join fixture bit-rot instead of running it every CI cycle as the negative baseline
  5. Ignoring clock skew between source systems when comparing event_time to label_time

⬜ Phase 4 — Incremental vs. Full Materialization §16

Objectives
  • Implement materialize's core write path supporting both MaterializationMode::Incremental and ::Full
  • Implement the incremental/full decision logic from the §8 decision table
  • Establish idempotent commit semantics (I8) ahead of Phase 8's offline/online split
  • Build compaction/reconciliation jobs that periodically verify incremental state against a full recompute
Deliverable

A materialization writer that supports both modes with idempotent, exactly-once commits, and a reconciliation job proving incremental and full materialization agree on sampled windows.

Acceptance
  • Zero duplicate commits across 50,000 injected retry/replay fuzz iterations (I8)
  • Incremental vs. full reconciliation diff = 0 rows across all sampled windows in the conformance corpus (P9)
  • Materialization write throughput sufficient to meet the online freshness SLO (§4) under peak load
Fixtures
  • fixtures/materialize/duplicate-commit-retry.bin
  • fixtures/materialize/incremental-full-reconciliation.bin
  • fixtures/materialize/mode-selector-decision-table.yaml
Pitfalls
  1. Incremental delta application that isn't associative/commutative, producing order-dependent results
  2. Compaction jobs that race with in-flight incremental writes
  3. Choosing incremental mode for a transform whose determinism hasn't yet been verified, against the §8 decision table's guidance
  4. Reconciliation jobs expensive enough that operators disable them, silently losing the P9 guarantee

⬜ Phase 5 — Streaming Engine with Event-Time and Watermarks §17

Objectives
  • Implement exec-stream: the streaming codegen target's runtime over Kafka/Pulsar
  • Implement watermark tracking and windowing per the Dataflow Model (Akidau et al.)
  • Extend pit-join to operate against streaming state (shared with Phase 3)
  • Establish checkpoint-based exactly-once semantics for streaming state
Deliverable

A streaming execution engine that tracks event-time watermarks per partition, windows data per the Dataflow Model, and reuses the Phase 3 point-in-time join engine for online feature computation.

Acceptance
  • Streaming end-to-end latency (event to materialized feature) p95 < 2 s, p99 < 5 s (§4)
  • Watermark lag < 10 s under normal load, alerting at 60 s (§4, I7)
  • Zero watermark regressions across 10,000 injected out-of-order/partition-rebalance fuzz iterations (I7)
  • No duplicate commits during simulated broker failover (I8)
Fixtures
  • fixtures/stream/watermark-regression.bin
  • fixtures/stream/late-event-past-watermark.json
  • fixtures/stream/partition-rebalance-during-checkpoint.bin
  • fixtures/stream/offset-divergence.bin
Pitfalls
  1. Using wall-clock arrival time as a stand-in for event time under load (ADR-07 violation)
  2. Watermark computation that regresses after a partition rebalance (I7 violation)
  3. Checkpoint barriers that stall indefinitely behind a single slow partition
  4. Applying pit-join's as-of semantics against streaming state without accounting for watermark-bounded completeness, admitting a technically premature join result

⬜ Phase 6 — Unified Batch/Stream Transform Definitions §18

Objectives
  • Implement sdk-rust's single transform-definition DSL compiling to both exec-batch and exec-stream targets (ADR-13, P2)
  • Eliminate the two-codebase skew risk structurally, not by convention
  • Extend the DAG compiler (Phase 0) to type-check a transform against both codegen targets at registration time
Deliverable

A single transform-definition language whose batch and streaming codegen targets are generated from one typed AST, with a differential harness proving output equivalence.

Acceptance
  • 0 skew incidents across 5,000 differential-test fixtures comparing batch vs. streaming output for the same DSL transform (I2, P2)
  • 100% of purity-lint violations (wall-clock/random/network calls) rejected at DSL compile time (ADR-10)
  • DSL compile time for a 100-node pipeline < 1 s
Fixtures
  • fixtures/dsl/batch-stream-differential-5000.bin
  • fixtures/dsl/purity-violation-wallclock.dsl
  • fixtures/dsl/purity-violation-random.dsl
  • fixtures/dsl/nested-aggregation-windowed.dsl
Pitfalls
  1. Letting the streaming backend special-case a construct the batch backend can't express, immediately reopening the two-codebase skew risk
  2. Purity linting that catches obvious violations but misses indirect ones, such as a library function that internally reads the clock
  3. Treating the differential harness as optional once "it passed once" — codegen backends can regress independently
  4. Under-designing the DSL's join surface so engineers reach for a raw join outside pit-join out of convenience

⬜ Phase 7 — Backfill with Determinism Guarantees §19

Objectives
  • Implement the Backfill execution path (§11) reusing the Phase 2/Phase 6 transform code, not a bespoke backfill engine (ADR-09)
  • Enforce and verify determinism (I3) via replay-hash comparison against original streaming/batch runs
  • Support parallelized backfill across historical windows up to the 3-year ceiling (§4)
Deliverable

A backfill mechanism that replays the exact transform code path used in live execution, verified deterministic via replay-hash comparison, parallelized within resource bounds.

Acceptance
  • Backfill throughput >= 50,000,000 rows/hour per worker (§4); a 2B-row/90-day window completes in < 4 h at 64 workers
  • 100% of backfill replay-hash comparisons match for all transforms passing the Phase 6 purity lint (I3)
  • 0 backfill runs exceed their declared resource ceiling across 1,000 injected fuzz iterations (I11)
Fixtures
  • fixtures/backfill/replay-hash-mismatch-nondeterministic.bin
  • fixtures/backfill/90-day-window-parallel-64.bin
  • fixtures/backfill/killed-backfill-resume.bin
  • fixtures/backfill/overlap-with-live-run.bin
Pitfalls
  1. A transform that passes the Phase 6 purity lint but is still non-deterministic through an unlinted path, e.g. iteration order over an unordered collection
  2. Backfill parallelism configured without regard to the admission controller's ceiling, causing a resource-exhaustion incident (T-class threat, §24)
  3. Resuming a killed backfill from a checkpoint that doesn't account for a partially-committed materialization
  4. Silently allowing a backfill to overwrite a newer, live-computed value for the same window

⬜ Phase 8 — Offline/Online Materialization Consistency (Feeding the Feature Store) §20

Objectives
  • Implement the dual-write path from materialize to both the offline store (Data-Lake-Table-Format-214) and the online store (Feature-Store-122's write API)
  • Enforce I2 (offline/online agreement for the same entity and timestamp) as a structural property, not a reconciled-after-the-fact one
  • Establish the skew-sampling verification job as a continuous background process
Deliverable

A dual-write materialization path where offline and online values for the same entity and timestamp are provably equal by construction, continuously verified by a skew-sampling job, and where online-store unavailability never blocks offline correctness.

Acceptance
  • Skew rate = 0 across the full skew-sampling corpus under normal operation (I2)
  • Offline/online consistency lag < 30 s median, < 5 min p99 (§4)
  • Offline commit succeeds and is durable even when the online store (Feature-Store-122) is fully unavailable for up to 1 hour (buffered retry)
Fixtures
  • fixtures/consistency/skew-sample-entity-timestamp.bin
  • fixtures/consistency/online-store-outage-buffered-retry.bin
  • fixtures/consistency/consistency-lag-distribution.bin
Pitfalls
  1. Letting the online-store writer apply any transform-specific logic that differs even slightly from the offline writer, reopening P2/I2
  2. Treating "eventually consistent" as license to skip the skew-sampling job — consistency lag must be bounded and measured, not assumed
  3. Coupling offline commit success to online-store availability, violating the delegation boundary (§1)
  4. Silent data loss in the buffered-retry path during an extended online-store outage

⬜ Phase 9 — Feature Versioning and Lineage §21

Objectives
  • Implement lineage: the append-only lineage graph capturing feature-version provenance (I9)
  • Implement full feature versioning with immutability enforcement (I5)
  • Enable lineage queries answering "which model, which run, which source version" for any feature value
Deliverable

A queryable, append-only lineage graph and an immutable feature-versioning system that together make any feature value's provenance fully reconstructable.

Acceptance
  • 100% of materialized feature values have a complete, queryable lineage chain to their ultimate raw sources (0 orphaned lineage records)
  • Lineage-graph query latency for a 10-hop provenance chain < 200 ms at the §4 scale ceiling
  • 0 successful mutations of a published FeatureVersion across fuzz testing (I5)
Fixtures
  • fixtures/lineage/deep-provenance-chain-10hop.bin
  • fixtures/lineage/immutable-version-mutation-attempt.bin
  • fixtures/lineage/schema-breaking-change-no-migration.yaml
  • fixtures/lineage/orphaned-record-detection.bin
Pitfalls
  1. Capturing lineage asynchronously/best-effort such that a fast-failing run leaves an incomplete record, violating the audit-completeness goal
  2. Allowing a "quick fix" mutation of a published feature version under operational pressure, defeating I5's entire purpose
  3. Lineage-graph queries that silently truncate deep provenance chains instead of erroring or paginating explicitly
  4. Schema-compatibility diffing that only checks field presence, missing type-narrowing changes that are technically breaking

⬜ Phase 10 — Data-Quality Validation and Freshness SLOs §22

Objectives
  • Implement quality: schema validation and distribution-drift detection modeled on TFX Data Validation (Breck et al.)
  • Implement FreshnessSlo enforcement (I6) gating the online-store publish path
  • Establish drift and freshness as first-class, continuously monitored properties per feature
Deliverable

A continuous data-quality and freshness monitoring subsystem that halts propagation of invalid or stale features before they reach serving.

Acceptance
  • Data-quality-check latency (schema + drift), p95 < 500 ms per batch/micro-batch (§4)
  • 95% of features fresher than 5 min, 99.9% fresher than 15 min, measured continuously (§4, I6)
  • 100% of injected schema-break and drift fixtures detected and halted at the boundary (P11)
Fixtures
  • fixtures/quality/schema-break-injected.json
  • fixtures/quality/distribution-drift-injected.bin
  • fixtures/quality/freshness-slo-breach.bin
  • fixtures/quality/null-rate-anomaly.bin
Pitfalls
  1. Drift thresholds tuned so loose they never fire, or so tight they alert-fatigue operators into ignoring them
  2. Freshness-SLO gating that blocks the online store but doesn't clearly flag the fallback last-known-good value as stale to downstream consumers
  3. Quality checks that run after materialization commits instead of gating it, violating P11's "halt at the boundary"
  4. Treating a one-time drift spike the same as a sustained drift trend, missing genuine data-source problems in the noise

⬜ Phase 11 — End-to-End Correctness Benchmark, Chaos, and Performance Hardening §23

Objectives
  • Build the leakage-and-skew correctness harness as the system's primary named CI gate (§28)
  • Run chaos testing across every failure mode identified in Phases 0-10
  • Perform final performance hardening against the §4/§30 targets
Deliverable

A production-readiness gate combining the leakage/skew correctness harness, chaos testing, and performance-regression gating, all wired into CI as blocking checks.

Acceptance
  • 0 leakage violations and 0 skew violations across the full correctness-harness run, including every chaos scenario (I1, I2)
  • System survives all §25 failure-mode injections without manual intervention beyond documented recovery procedures
  • 72-hour soak test at peak §4 throughput with 0 invariant violations and no unbounded resource growth
  • 0 performance regressions beyond tolerance against the §30 M1... baseline
Fixtures
  • fixtures/e2e/correctness-harness-full-run.bin
  • fixtures/e2e/chaos-source-outage-mid-run.bin
  • fixtures/e2e/chaos-worker-failure-mid-backfill.bin
  • fixtures/e2e/soak-72h-peak-throughput.bin
  • fixtures/e2e/deterministic-replay-production-incident.bin
Pitfalls
  1. Running the correctness harness against synthetic data that doesn't actually exercise realistic leakage-prone patterns — it must include adversarially-constructed temporal structures
  2. Chaos scenarios that are too gentle to actually trigger the failure paths they claim to test
  3. Performance-regression gating with a tolerance loose enough to let a slow creep through release after release
  4. Treating a clean soak-test run as sufficient without also validating resource-usage stability over the full 72 hours, since a slow leak may not manifest in the first hour
