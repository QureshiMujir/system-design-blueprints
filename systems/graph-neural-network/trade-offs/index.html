Language

Chosen

Python 3.11+

Rejected

Alt-A: Spectral GNN with Full Laplacian Eigenbasis

Input graph G  -->  Compute Laplacian L = D - A
                -->  Eigendecompose: L = U Λ Uᵀ
                -->  Spectral filter: y = U · g(Λ) · Uᵀ · x
                      where g(Λ) is a learned diagonal filter
                -->  Node predictions

Regime where it wins: graphs where the spectral structure is the direct object of interest (e.g. graph signal processing, community detection via spectral clustering), and N is small enough that eigendecomposition (O(N³)) is tractable.

Real system that embodies it: Bruna et al. (2014) "Spectral Networks on Graphs" (ICLR 2014) — the original spectral GNN; also the full-graph Fourier convolution variant in Defferrard et al. (2016) before ChebNet's polynomial approximation.

Why this blueprint rejected it: eigendecomposition is O(N³) and produces a graph-specific basis; any new graph requires recomputation. The spectral filter does not generalize inductively to unseen graphs or nodes. The MPNN framework (Gilmer 2017) provides strictly greater scalability and generalization with no loss in expressivity for the tasks in scope. Deferred explicitly in §1.3 and §1.8.

Alt-B: Static-Graph Computation (No Dynamic Tape)

Define model as a static computation graph (DAG) once:
  Layer 1: Z1 = sym_norm(A) @ X @ W1
  Layer 2: Z2 = sym_norm(A) @ relu(Z1) @ W2
  Loss: cross_entropy(Z2[train_mask], y)

Compile graph -> run forward + backward via pre-compiled vjp schedule
No dynamic tape recording per forward pass

Regime where it wins: when the GNN architecture is fixed (same graph, same topology, same layer count), a compiled static graph avoids the per-forward tape overhead and enables aggressive kernel fusion (XLA, TorchScript). Wins in production inference with a frozen model on a fixed graph.

Real system that embodies it: TensorFlow 1.x (graph mode), TorchScript, JAX jit with static shapes, and the original Kipf GCN implementation (tkipf/gcn) in TF1.

Why this blueprint rejected it: message passing is data-dependent — the graph topology determines the computation structure, and in the neighbor-sampling case (Phase 7) the computation graph literally changes per minibatch. A static graph cannot represent this. The dynamic tape (ADR-4) is the only representation that handles data-dependent topology without manual re-specialization.

Alt-C: Dense Adjacency Matrix Approach

Precompute: A_norm = D^-1/2 @ (A + I) @ D^-1/2   # (N, N) dense float64
Each layer:
  H_new = relu( A_norm @ H @ W )                   # (N,F) = (N,N)@(N,F)@(F,F')
Readout: softmax( H_L )

Regime where it wins: small, nearly-complete graphs (N ≤ 500, edge density > 50%) where BLAS dgemm on the dense A_norm×H matmul has better cache utilization than scattered index operations, and where memory is not a constraint. Also wins in any setting where Â must be used repeatedly across many epochs (precomputed once, reused cheaply).

Real system that embodies it: Kipf's original pygcn implementation uses a scipy sparse matrix multiplication but can be run with dense NumPy for small graphs; several tutorial implementations materialize dense Â explicitly.

Why this blueprint rejected it: the §4.1 constraint table sets N≤10⁵ and E≤10⁶. Dense Â at N=10⁵ requires 80 GB of RAM (Capacity Model entry 10). The pedagogical goal requires the sparse path to be the primary path so that the library scales beyond toy examples. Dense adjacency is available as a degenerate case but is not the default.

Alt-D: Per-Node Python Loop (No Vectorized Gather/Scatter)

Structure (per-node scatter-free dataflow, one node at a time):
  for each node v:  neighbors(v) = {src : edge dst == v}
                    agg(v)       = Σ over neighbors(v) of X[src]   # manual sum
                    H_new(v)     = relu( (agg(v) + X[v]) @ W )
Contrast: N separate neighborhood reductions vs 1 gather + 1 segment_sum

Regime where it wins: for a debugger or interactive trace, a per-node loop makes the computation maximally inspectable — every node's neighborhood is explicit. Correct for tiny conformance tests.

Real system that embodies it: most early tutorial implementations of GCN (e.g. cs224w Stanford course notebooks) use explicit Python loops over nodes for pedagogical clarity.

Why this blueprint rejected it: a Python loop over N=2708 Cora nodes is ~100–1000× slower than vectorized gather/scatter because each iteration dispatches a Python function call and a NumPy slice. More critically, there is no path to integrate this with a tape-based autodiff: the loop body would need to be recorded per-iteration, producing a tape of N entries rather than 1 gather + 1 scatter_add. The gather/scatter abstraction (P2, P3, ADR-6) is both faster and the only form the tape can differentiate efficiently.
