In one paragraph

This is a Python library, built on NumPy alone, that trains neural networks on graphs, such as a citation graph of papers or a set of molecules (§1.1, §2.2). It writes its own gradient engine instead of borrowing one, and it expresses four well-known layer types (GCN, GraphSAGE, GAT, GIN) as small variations of one shared step: collect neighbours' features, combine them, update the node (§1.1, P2). It covers node classification, link prediction and graph classification (§1.1). Its promise is that the same graph, model, seed and hyperparameters give the same parameters and predictions on the same NumPy/BLAS build (§1.1, ADR-27). It is a teaching and portfolio library, run in one process on one host with no server (§1.4, §1.5).

The problem, concretely

In a GNN the computation is shaped by the graph's wiring: features are gathered along edges and scattered into nodes, so the work is data-dependent rather than a fixed tensor program (§1.10). The blueprint's answer is to store the wiring as a list of edges (edge_index) and let every layer work edge by edge through one gather-message-aggregate-update pipeline (§8.1, §8.2, §2.1).

Training makes it harder. To learn, you need a gradient of the loss with respect to every weight. Hand-deriving that gradient for each layer is error-prone: a hand-coded gradient that disagrees with the forward pass trains a different, wrong model while the forward tests still pass (P6). The most common silent mistake is summing neighbours' messages with a plain assignment, which keeps one incoming message per node and drops the rest (P4). A third trap is depth: stack many propagation steps and every node's features drift toward the same value, so accuracy falls as layers are added (MM4, §2.1). The design is organised around catching each of those errors with an executable test (§2.3, §7).

How it works, end to end

Follow one training epoch of the default 2-layer GCN on the Cora citation graph (§4, §8.11, §8.6). Cora here means 2708 nodes, 5429 edges, 1433 features per node, 7 classes (§8.11).

Diagram adapted from §3.1 (boxes only, arrows show the call direction), drawn and coloured by role:

  1. gnn.cli starts a run, for example train --dataset cora --model gcn --layers 2 --hidden 16 --epochs 200 --seed 7 --out run.npz (§1.4). gnn.train takes over (§3.2).
  2. gnn.data loads the dataset and builds a Graph: features X, edge_index (a 2-row array of source and destination nodes), optional edge features, labels y and boolean train/val/test masks (§3.2, §8.1). gnn.graph validates every index and shape (I13).
  3. gnn.graph adds self-loops and computes the normalised adjacency once, with a per-edge weight of 1/√(d_i d_j) (§8.4, §8.3, I7).
  4. The GCNConv layers (gnn.layers) are MessagePassing subclasses. gnn.message runs gather, message, aggregate, update; the layer overrides only the message and update steps (§3.2, P2). Each weight matrix is a Parameter that gnn.nn's Module registry hands to the optimiser (§3.2). Between the two layers sit ReLU and, in training, dropout (§8.6).
  5. Every operation is recorded on a tape by gnn.autodiff, so the loss can be differentiated without hand-written gradients (§3.2, P6). gnn.core supplies the stable softmax and the finite-guards (§3.2, P5, P8).
  6. gnn.loss computes cross-entropy restricted to the 140 training nodes (§8.6, §8.11).
  7. gnn.autodiff sweeps the tape backwards, gnn.optim applies the update, and the next epoch begins (§3.2). gnn.train stops early on the validation metric and writes an NPZ checkpoint plus JSON metadata with the seed (§3.2, ADR-25).

For graph classification the path differs at one box. BatchedGraph glues many small graphs into one large graph with no edges between them, so a single message-passing pass processes the whole batch, and gnn.pool then reads out one embedding per graph using a per-node graph-id array (§8.9, §3.2).

The core ideas

Message passing: one step that every layer reuses (§8.2, §8.3)

A layer is one straight-line pass over (X, edge_index, edge_attr) (§8.2). The blueprint's pseudocode, copied exactly from §8.2:

propagate(X, edge_index, edge_attr) — one straight-line pass, no branching:
  src, dst  = edge_index                                     # (E,), (E,)
  x_j       = gather(X, src)                                 # (E,F) source features per edge
  x_i       = gather(X, dst)                                 # (E,F) destination features per edge
  m         = message(x_i, x_j, edge_attr)                   # (E,F') per-edge messages
  aggr      = aggregate(m, dst, N, reduce="sum")              # (N,F') segment reduce
  result    = update(aggr, X)                                # (N,F'') new node features

In plain words: for each edge, copy the sender's features (gather), turn them into a message, add up all messages that land on the same receiving node (aggregate, a segment reduction), then combine the total with the node's own features (update) (§8.2, §8.5). The four layers differ only in those three hooks (§8.3, P2):

Layer message aggregate update
GCN norm_weight · (W x_j) sum (weighted) identity (+bias)
GraphSAGE-mean x_j mean W·[x_i ‖ mean_j]
GAT α_ij · (W x_j) sum identity
GIN x_j sum MLP((1+ε)·x_i + Σ_j x_j)

(§8.3; the GraphSAGE-pool row is omitted here.) The base class owns gather, scatter and shape checks, so a layer never writes its own neighbourhood loop (§8.2, P2, P11). That is why the same layer runs full-batch, mini-batched and neighbour-sampled (§8.2).

Gather and scatter are each other's gradient, and the tape accumulates (§8.5, P3, P4)

Reverse-mode differentiation (autodiff) records each operation on a tape, then replays it backwards. Each recorded operation carries a vector-Jacobian product (vjp), the rule that turns an output gradient into input gradients (§3.2, §8.5). The blueprint's two rules (adapted from §8.5: comments and the "adjoint duality" label trimmed):

gather:      Y = X[idx]
scatter_add: out[k] = Σ_{e : dst[e]=k} vals[e]       # accumulate into node k, never overwrite (P4,I3)
  d/dX  of  gather(X, idx)      = scatter_add(grad_Y, idx, N)
  d/dvals of scatter_add(vals)  = gather(grad_out, dst)

Forward, a node's feature is copied out to each of its outgoing edges (gather). Backward, the gradients coming back along those edges must be summed into that node (scatter-add). The reverse is also true (§8.5, MM1). The blueprint calls this duality exact, not approximate (MM1). The same accumulate-not-overwrite rule holds for the tape itself: if one sub-expression is used twice, its two gradient contributions must be summed, otherwise shared values get wrong gradients (MM6, I4). segment_max is the exception that selects: its gradient goes only to the edge that won the max, like max-pooling (§8.5). The safety net is grad_check, which compares the tape's gradient against central finite differences at rtol 1e-5 (I4, §13).

Normalising the adjacency so repeated propagation stays stable (§8.4, MM3, I7)

If you multiply features by the raw adjacency again and again, nodes with many neighbours blow the numbers up (§8.4, MM3). GCN instead uses symmetric normalisation: Â = D̃^-1/2 (A+I) D̃^-1/2, where A+I adds a self-loop to every node and D̃ is the degree matrix after that (§8.4). Each edge carries weight 1/√(d_i d_j), which balances the pull of hubs (MM3, §8.3). The blueprint states that this keeps the spectral radius of Â at or below 1, so repeated multiplication does not blow up (§8.4, MM3, I7). An isolated node has degree 0, which becomes 1 after the self-loop, so it is safe (§8.4, §8.12). The blueprint is not consistent about row normalisation D̃^-1(A+I): §8.4 defines D̃ = D+I, yet its row-normalisation row says degree 0 gives a divide-by-zero and needs the guard d = max(d,1) (§8.4, §14.2). Propagation is done sparsely, by gather plus segment-sum over the edges, never by a dense N×N matrix multiply when E is much smaller than N² (§8.6, P13, MM2).

Attention over edges, with a softmax that cannot overflow (§8.7, P5, I11)

GAT lets the network learn how much each neighbour matters. For each edge it scores the pair, then normalises the scores over all edges arriving at the same destination so they sum to one (edge softmax) (§8.7, §3.2):

e_ij = LeakyReLU( a_h^T [Wx_i ‖ Wx_j] )
α_ij = segment_softmax(e_ij, dst)
H_h  = segment_sum(α_ij * Wx_src, dst, N)

(adapted from §8.7, one head; the separate m_e line is folded into the last line). Raw exp(logits) overflows for moderate scores and turns every attention weight into NaN, so the softmax subtracts a maximum before exponentiating (P5, §8.7). The maximum is taken per destination (§8.7, I11); the design target is no overflow for logits up to ±700 (§4, M3 in the Performance Engineering table). Heads are concatenated in hidden layers and averaged in the output layer (§8.7).

Sum, mean and max: why GIN uses a sum (§8.8, MM5)

If a node has two identical neighbours, a mean or a max returns the same answer as for one such neighbour; a sum does not (§8.8, MM5). The Weisfeiler-Lehman test (WL test, a graph-isomorphism heuristic) distinguishes graphs by the multiset of their neighbourhoods, and sum aggregation preserves that multiset, so the blueprint says GIN with a sum is as discriminative as that test (§8.8, MM5, ADR-11). GIN's update is H_l = MLP_l( (1+ε_l) · H_{l-1} + segment_sum( gather(H_{l-1}, src), dst, N) ) (§8.8). Phase 8's acceptance includes a fixture where sum separates "two identical neighbours" from "one" and mean/max cannot (§19).

Oversmoothing: depth that hurts (MM4, §2.1)

Each propagation step is a low-pass filter. With enough of them, all node representations converge toward a degree-weighted constant that carries no local information (MM4, §2.1). The blueprint's prediction: test accuracy rises and then falls as layers are added, independent of model capacity (MM4). To tell it from vanishing gradients, watch two signals: per-layer feature norm or Dirichlet energy (squared feature differences across edges) and per-layer gradient norm (P12, §23, Glossary). The remedies are residual connections, jumping-knowledge concatenation, EdgeDropout (DropEdge) and fewer layers (§23, ADR-15).

The trade-offs — where engineers disagree

Dynamic tape versus a compiled static graph (ADR-4)

Chosen: a dynamic Wengert tape, which works through data-dependent topology and is "simplest correct" (ADR-4, ADR-3). Rejected: source transformation and static graphs (ADR-4; Alt-B in Alternative Architectures). When the rejected choice is right: source transform (JAX, Zygote) wins when the computation graph is fixed and JIT compilation for GPU/TPU throughput is the goal (ADR-4).

Precision: float64 everywhere (ADR-5)

Chosen: float64, for gradient-check fidelity and to avoid accumulation error in scatter (ADR-5, §1.3). Rejected: float32. When the rejected choice is right: any production training setting where memory and throughput dominate, with gradient-check fidelity enforced at higher precision only once (ADR-5).

Sparse edge lists versus a dense adjacency matrix (ADR-7)

Chosen: COO edge list plus on-demand CSR, giving O(E) memory and compute when E is much smaller than N² (ADR-7, P13). Rejected: a dense N×N matrix. When the rejected choice is right: small, nearly complete graphs (N up to a few hundred, density above 50%) where dense BLAS beats scattered index operations (ADR-7; Alt-C gives N ≤ 500).

Symmetric versus row normalisation (ADR-9)

Chosen: symmetric D̃^-1/2(A+I)D̃^-1/2, for its spectral-radius bound and stability (ADR-9, I7). Rejected: row-norm only, or none. When the rejected choice is right: row (random-walk) normalisation, when the graph is directed and a diffusion interpretation is preferred over symmetric spectral properties (ADR-9). Row-norm is also described as the SAGE-mean equivalent (§8.4).

Sum versus mean aggregation in GIN (ADR-11)

Chosen: sum plus an MLP with ε, for WL-expressiveness (ADR-11, §8.8). Rejected: mean or max. When the rejected choice is right: mean wins when the task depends on density or an average rather than a count, for example a graph-level property that scales with edge density, not absolute neighbour count (ADR-11).

Full-batch plus neighbour sampling (ADR-17)

Chosen: full-batch training plus GraphSAGE neighbour sampling, because it scales and is inductive (ADR-17). Rejected: subgraph samplers (Cluster-GCN, GraphSAINT), which are deferred (ADR-17, §1.3). When the rejected choice is right: Cluster-GCN wins when the graph is too large even for neighbour sampling's exponential fan-out growth (the blueprint's example is OGB-Papers100M) and partition-level cache reuse is needed (ADR-17). Sampling is an estimator: sampled accuracy is required to land within 3% of full-batch (§18, M7 in the Performance Engineering table).

Determinism: same platform only (ADR-27)

Chosen: single-platform seed-determinism, because scatter-add and BLAS reduction order make bit-exact cross-platform output out of scope (ADR-27, §1.1). Rejected: bit-exact cross-platform reproduction. When the rejected choice is right: a regulatory or safety-critical system where byte-for-byte identical outputs across hardware are a compliance requirement (ADR-27).

Roads not taken

Spectral GNN with a full Laplacian eigenbasis (Alt-A in Alternative Architectures): wins when the spectral structure is the object of interest, such as graph signal processing or spectral clustering, and N is small enough for an O(N³) eigendecomposition. It was rejected because the basis is specific to one graph and does not generalise to unseen graphs; ChebNet is deferred (§1.3, §1.8).

A static compiled graph (Alt-B): wins for a frozen model on a fixed graph in production inference, where fusion avoids per-forward tape overhead. Rejected because sampling changes the computation graph per batch (Alt-B in Alternative Architectures).

Dense adjacency (Alt-C): wins for small nearly complete graphs where BLAS cache use is good and where Â is reused across many epochs. Rejected as the default because of the §4 size ceilings (Alt-C, Capacity Model item 10); kept as a degenerate case.

A per-node Python loop (Alt-D): wins as a debugging aid, since every neighbourhood is explicit, and for tiny conformance tests. Rejected because it is slow and gives the tape one entry per node instead of one gather and one scatter (Alt-D in Alternative Architectures, P2, P3).

The deferred register (Deferred Features Register, §1.8) lists eight features, each with the trigger that would promote it: spectral GNNs, relational GNNs (RGCN), subgraph samplers, LSTM or set-attention aggregators, GPU or SIMD sparse kernels, forward-mode plus exact Hessian, graph generation, and distributed training. Two examples of triggers: subgraph samplers come in when neighbour sampling's per-minibatch cost or variance becomes the bottleneck on a large graph, and distributed training when a graph and model exceed single-host RAM even after neighbour sampling (Deferred Features Register).

What must never be false

  • I1: a layer's forward is the exact published formula. Noticed by a unit test against hand computation (§7).
  • I2: gather's vjp is scatter_add and scatter_add's vjp is gather. Noticed by gradcheck on gather and scatter (§7).
  • I3: scatter_add and segment_sum accumulate duplicate destinations, so no message is dropped. Noticed by a test where many edges target one node (§7).
  • I4: every parameter gradient matches finite differences of the loss within tolerance (rtol 1e-5). Noticed by the grad_check harness, which the blueprint calls the highest-leverage gate (§7).
  • I5: node-level layers are permutation-equivariant. Noticed by a permute-nodes equality test (§7).
  • I6: graph readout is permutation-invariant. Noticed by a permute-nodes invariance test (§7).
  • I7: Â is symmetric (and row sums go to 1 for row-norm). Noticed by a symmetry and eigen-bound test (§7).
  • I8: aggregation does not depend on edge order. Noticed by a shuffle-edges equality test (§7).
  • I9: loss, activations and gradients are finite at every step. Noticed by a finite-guard that raises NonFiniteError and aborts (§7, P8).
  • I10: dropout and BatchNorm differ between train and eval, and eval is deterministic. Noticed by a mode-toggle test (§7).
  • I11: softmax and segment_softmax are stable. Noticed by an extreme-logit unit test (§7).
  • I12: the RNG is seeded and explicit, so runs reproduce. Noticed by a seed-replay equality test (§7).
  • I13: edge_index lies in [0, N) and shapes are consistent. Noticed by bounds and shape checks raising GraphError or ShapeError (§7).
  • I14: SGD and Adam match the reference math (bias correction, momentum). Noticed by stepping the optimiser on a quadratic with a known closed-form trajectory (§7).

What breaks in production

The library is a local tool, so "production" here means a training run that quietly goes wrong. The blueprint's recovery rule: correctness failures such as NaN, out-of-bounds indices, dropped messages, label leakage and non-reproducibility fail loud and abort; quality failures such as not-learning and oversmoothing surface as telemetry and runbook guidance, not silent fixes (Failure Modes & Recovery, P8, P12).

  • Not learning. Symptom: flat loss or accuracy. Causes: bad learning rate, wrong init, a dead ReLU, or a mask leak. Detection: loss and accuracy curves. Recovery: tune learning rate or init and check masks, using per-layer gradient norms as forensics (Failure Modes & Recovery, "Not learning").
  • Oversmoothing. Symptom: accuracy drops as depth grows. Cause: repeated low-pass filtering. Detection: feature-norm or energy telemetry. Recovery: fewer layers, residual or jumping-knowledge connections, DropEdge (Failure Modes & Recovery, "Oversmoothing"; MM4).
  • NaN loss or activation. Symptom: the run aborts. Causes: log(0), an unstable softmax, overflow. Detection: NonFiniteError with layer and epoch context. Recovery: fix init or learning rate and compute the loss in log-space (Failure Modes & Recovery, "NaN loss/activation"; I9, P8).
  • Wrong neighbourhood. Symptom: plausible-looking but wrong output. Causes: a source/destination swap or a sampler remap bug. Detection: the analytic-mean and equivariance fixtures. Recovery: fix the gather or the sampler (Failure Modes & Recovery, "Wrong neighborhood").
  • Dropped messages. Symptom: underperformance. Cause: scatter overwrote instead of accumulating. Detection: the scatter-accumulate fixture. Recovery: use add.at or bincount (Failure Modes & Recovery, "Dropped messages"; P4, I3).
  • Sampler corruption. Symptom: high-variance training. Cause: a node-id remapping off-by-one, which the Phase 7 pitfalls list says cross-links features silently. Detection: the sampled-versus-full accuracy band. Recovery: fix the remapping (Failure Modes & Recovery, "Sampler corruption"; §18).
  • Bad optimiser step. Symptom: slow or unstable training. Cause: Adam's bias correction missing. Detection: the trajectory fixture. Recovery: fix the update math (Failure Modes & Recovery, "Bad optimizer step"; I14).

Threats a reader should know (Threat Model). The blueprint says the realistic risks are robustness and resource exhaustion, not privilege escalation, because graph data and config run in-process with the caller's trust (Threat Model). Out-of-bounds indices are rejected at graph build time with a GraphError (Threat Model, "OOB index"; I13). NaN/Inf poisoning is stopped by finite-guards and log-space maths (Threat Model, "NaN/Inf poisoning"). Memory exhaustion from a dense adjacency or huge graph is answered by the sparse path and a pre-allocation check (Threat Model, "Memory exhaustion"; P13). Label leakage, where validation or test nodes sit in the loss mask, is caught by a mask-overlap check before training (Threat Model, "Label leakage"). An untrusted checkpoint is handled by using NPZ arrays only, with no code-executing pickle (Threat Model, "Untrusted checkpoint"; ADR-25).

How it compares

  • PyTorch Geometric relies on C++/CUDA scatter extensions for GPU throughput, at the cost of a non-trivial build chain. That is the right call when GPU training at scale is the constraint, which this library excludes by design (Comparative Architecture, §1.3).
  • DGL separates its message-passing interface from the backend (PyTorch, TF, MXNet) and uses C++ SpMM kernels. It fits large heterogeneous workloads where kernels and backend flexibility matter more than being readable (Comparative Architecture).
  • Spektral hosts on TensorFlow/Keras, which wins when the rest of the pipeline is already TensorFlow and layer.call/model.fit consistency matters more than a flexible message-passing abstraction (Comparative Architecture).
  • NetworkX plus NumPy by hand makes no autodiff investment. That is right for pure graph analytics such as centrality or pathfinding, and it loses on any learning task for lack of a gradient path (Comparative Architecture).

Questions to test yourself

  1. Why is the gather/scatter_add adjoint duality exact, not approximate, and what happens to gradient correctness if you implement scatter_add's vjp as scatter_add instead of gather? — Hint: §8.5 and Phase 2 (§13), then the Failure Modes table.
  2. GIN's expressivity guarantee requires sum aggregation. A colleague argues that mean aggregation with a very large hidden dim approaches sum in expressivity. Formally characterize when this is true and when it fails, citing the WL connection. — Hint: §8.8, ADR-11 and MM5.
  3. Why does segment_softmax require a per-destination max subtraction, and why is global max subtraction strictly insufficient for the GAT case? — Hint: P5, §8.7 and I11.
  4. The Adam optimizer has a bias-correction term for both first and second moment estimates. If you omit the first-moment correction only, how does this change the effective step size in the first few training steps, and what reference trajectory test would catch it? — Hint: Phase 10 (§21), I14.
  5. Describe the Dirichlet energy as an oversmoothing metric: its formula, what value it approaches as depth → ∞, and how EdgeDropout (Rong 2020) measurably slows the convergence rate. — Hint: Phase 12 (§23) and MM4.

If you only remember three things

Every GNN layer is the same gather-message-aggregate-update step with different hooks, and the gradient of gather is scatter-add and vice versa, so any layer's gradient can be computed with one gather and one scatter on the tape (P2, P3, MM1). Normalise the adjacency, subtract the maximum before a softmax, and accumulate rather than overwrite: skip the first and features blow up at hubs, skip the second and attention turns to NaN, skip the third and messages are silently dropped (MM3, P5, P4). Depth is not free: repeated propagation smooths node features toward a constant, so watch feature norms and gradient norms instead of adding layers (MM4, P12).

Words used here

  • Message passing: each node gathers messages from its neighbours, combines them, and updates itself (§8.2).
  • Gather: copy rows of the feature matrix out to edges by index; its gradient is scatter-add (§8.5).
  • Scatter-add: accumulate values into destination rows, summing duplicates (§8.5, P4).
  • Segment reduction: sum, mean or max of values grouped by a segment index such as the destination (Glossary).
  • Vjp: the per-operation rule that turns an output gradient into input gradients (Glossary).
  • Tape: the recorded list of operations replayed backwards to get gradients (§3.2).
  • Symmetric normalisation: Â = D̃^-1/2(A+I)D̃^-1/2, which keeps repeated propagation stable (§8.4).
  • Edge softmax: attention scores normalised over each node's incoming edges (§8.7).
  • Permutation equivariance: relabel the nodes and the outputs relabel identically (P7).
  • WL test: a graph-isomorphism heuristic that upper-bounds GNN expressivity (Glossary, MM5).
  • Oversmoothing: repeated propagation drives node features toward a constant (MM4).
  • Transductive / inductive: training and inferring on one fixed graph, versus generalising to unseen nodes or graphs (Glossary).
  • Neighbour sampling: take a bounded random set of neighbours per node per layer, for scale (Glossary, MM8).
