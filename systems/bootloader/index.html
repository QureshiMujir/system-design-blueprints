3. Architectural Overview

└─────────────────────────────────────────────────────────────────────┘

Firmware box — the only code that ever calls BIOS interrupts or UEFI protocol methods directly; everything downstream is firmware-agnostic (trust boundary + concurrency boundary: single-threaded, no interrupts enabled after Phase 2 stage-1). Mode/Handoff shim — the irreversible transition boundary; once past it, no rollback to a lower privilege/mode is attempted. Disk/filesystem reader — a persistence boundary that is read-only end to end (I10); the loader never becomes a write amplifier. Config/Menu — the only interactive/human boundary; bounded input, bounded render time (§4). Measured/Secure verify — the security trust boundary; nothing downstream of it runs unverified bytes (P3, I6). Kernel image loader — protocol boundary: three wire formats normalized to one internal HandoffState. A/B + jump — the point of no return; after the jump, the loader's memory is either freed or reclassified and never touched again (I2).

Memory Map Schemas

E820 entry (BIOS INT 15h, AX=0xE820), 20–24 bytes:

struct E820Entry {
    base_addr: u64,
    length: u64,
    kind: u32,          // 1=usable 2=reserved 3=ACPI-reclaim 4=ACPI-NVS 5=bad
    ext_attributes: u32, // present only if returned size == 24 (ACPI 3.0)
}

UEFI EFI_MEMORY_DESCRIPTOR (GetMemoryMap), fixed 40 bytes (padded):

struct EfiMemoryDescriptor {
    kind: u32,           // EfiLoaderCode, EfiConventionalMemory, ...
    pad: u32,
    physical_start: u64,
    virtual_start: u64,
    number_of_pages: u64,
    attribute: u64,      // EFI_MEMORY_WB/WT/RUNTIME/...
}

MemoryMap (Core Schema §11) normalizes both into one internal representation (P7): a sorted, non-overlapping list of (base, length, class) ranges, class ∈ {Usable, Reserved, AcpiReclaim, AcpiNvs, Bad}.

ELF64 / Kernel Handoff

ELF64 header fields load-bearing for boot: e_ident[EI_CLASS]=ELFCLASS64, e_type=ET_EXEC, e_machine=EM_X86_64, e_entry, e_phoff, e_phnum. Program headers of type PT_LOAD give (p_vaddr, p_paddr, p_filesz, p_memsz, p_flags); the loader copies p_filesz bytes from the image and zero-fills the remaining p_memsz - p_filesz (BSS). I8 requires e_entry to fall within some PT_LOAD's [p_vaddr, p_vaddr+p_memsz).

Multiboot2 Boot Information

Passed to the kernel in EAX (magic 0x36D76289) and EBX (physical address of the info structure):

struct Mb2Info {
    total_size: u32,
    reserved: u32,
    // followed by a tag stream, 8-byte aligned, each:
    //   tag_type: u32, tag_size: u32, tag_data: [u8; tag_size-8]
    // terminated by a tag with type=0, size=8
}

UEFI Boot Protocol (Worked Example)

Booting a signed Linux bzImage on UEFI, end to end:

  1. Firmware LoadImage + StartImage on the loader's PE32+ binary.
  2. Loader opens EFI_SIMPLE_FILE_SYSTEM_PROTOCOL on the ESP, reads bl-config's menu file via bl-fs-fat32.
  3. Operator selects the default entry (menu-ui, ≤ 100 ms render, §4).
  4. bl-measure extends PCR 4 with the kernel image hash (P9, I7).
  5. bl-verify checks the PKCS#7 signature over the same hash (I6).
  6. bl-image-bzimage parses the bzImage header, builds boot_params.
  7. Loader calls GetMemoryMap, then ExitBootServices(ImageHandle, MapKey) (I1, bounded retry ≤ 5, I13).
  8. Loader jumps to the kernel's protected-mode entry per the Linux x86 Boot Protocol register contract (Documentation/x86/boot.rst).

Malformed-Input Example

A Multiboot2 tag with tag_size extending past total_size: the parser must reject with a named error (Mb2Error::TagOverrun) before dereferencing any byte past the info structure's declared bound — never a raw pointer walk that trusts tag_size (the BootHole/CVE-2020-10713 lesson, P3).

Failure-Path Example

ExitBootServices returns EFI_INVALID_PARAMETER (stale MapKey — a console print between GetMemoryMap and ExitBootServices allocated memory and invalidated the map, violating I1). The loader re-issues GetMemoryMap, retries ExitBootServices (retry count now 1 of 5, I13). After 5 exhausted retries: fatal halt, diagnostic code E-EBS-RETRY printed to console + serial (Operational Readiness, §24).

Design principles (§6)

  • P1 — Firmware behind a trait. No firmware-specific call outside a Firmware trait impl. Tradeoff: an indirection layer on every disk/console op. Operational implication: one crate per firmware backend (ADR-02). Violate it and BIOS/UEFI code intermixes, breaking the differential suite (§21).
  • P2 — Read-only until handoff. No persistent write paths except the signed A/B metadata (Phase 8). Tradeoff: no in-place repair of a corrupt filesystem. Violate it and I10 breaks, invalidating the entire threat model's "loader cannot brick storage" claim.
  • P3 — Verify before parse. Signature/measurement precedes any untrusted-format parsing. Tradeoff: verification of the whole image before any lazy/partial parse. Violate it and BootHole/BootStomp-class parser bugs become pre-auth (Threat Model T1/T3).
  • P4 — Deterministic memory layout. Same input → identical physical addresses. Tradeoff: no ASLR-style loader self-randomization. Violate it and fuzz findings stop reproducing, and measured-boot PCR values stop being comparable across boots.
  • P5 — Fail loud, fail safe. Any inconsistency halts to a diagnosable state, never a silent continue. Tradeoff: some transient errors that could be retried instead abort. Violate it and operators lose the signal that distinguishes "hardware hiccup" from "corrupted chain."
  • P6 — Explicit mode transitions. Real→protected→long mode is an atomic, logged sequence, never partially applied. Tradeoff: no incremental/lazy paging setup. Violate it and I3/I4 break — a kernel entered in an inconsistent CPU state.
  • P7 — One memory-map source of truth. The last GetMemoryMap/E820 snapshot is canonical; nothing re-derives it. Tradeoff: any allocation after the snapshot forces a re-snapshot (I1). Violate it and the kernel receives a memory map inconsistent with what firmware actually owns.
  • P8 — Time-budgeted critical path. Every stage carries an explicit ms budget (§4), CI-gated. Tradeoff: engineering time spent on benchmarking harnesses. Violate it and boot-time regressions ship silently.
  • P9 — Measurement before execution. A PCR extend precedes execution of any loaded component (TCG SRTM order). Tradeoff: measurement adds latency (§4, ≤ 15 ms/event) to every stage. Violate it and the measured-boot chain of custody has a gap an attacker can exploit (TOCTOU, Threat Model T9).
  • P10 — A/B atomicity via ping-pong. Never a window where both BCB slots are simultaneously invalid. Tradeoff: double the metadata writes. Violate it and I5/I11 break — a power-loss mid-write can strand the device unbootable.
  • P11 — Small, auditable TCB. no_std, no heap allocation in the verify/measure critical path (Phase 7). Tradeoff: fixed-capacity buffers instead of dynamic allocation. Violate it and the TCB size argument in the Threat Model (§22) no longer holds.
  • P12 — Protocol-agnostic handoff boundary. Multiboot2's tag list and Linux boot_params are alternate encodings of one internal HandoffState; the loader never branches deep logic per protocol. Tradeoff: one extra serialization step per format. Violate it and three parallel, drifting handoff implementations accumulate.
  • P13 — No hidden retries. Every retry loop has a bounded, logged count (e.g. ExitBootServices ≤ 5, I13). Tradeoff: an operator sees a retry-exhausted halt instead of an infinite hang. Violate it and a stale-memory-map loop can spin forever with no operator signal.
  • P14 — Recovery is a first-class boot path. The recovery/failsafe menu entry is built and conformance-tested from Phase 8 on, not bolted on at the end. Tradeoff: recovery-path code must track every upstream format/verify change. Violate it and the one path meant to save a bricked device is the least-tested code in the system.
