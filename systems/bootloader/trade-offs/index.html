Decisions (§9) · 24 ADRs

ADR-01

Language & runtime

Chosen

Rust 1.78+, no_std, custom target spec

Rejected

C; Zig; Ada/SPARK

When the rejected choice is right

C wins when integrating unmodified vendor firmware SDKs that only ship C headers

Why: memory safety in ASN.1/config parsing (P3, P11); ecosystem parity with ref-impls

ADR-02

Primary firmware target

Chosen

UEFI

Rejected

BIOS-only

When the rejected choice is right

BIOS-only wins for legacy embedded boards with no UEFI firmware option at all

Why: UEFI is the shipping baseline on hardware built since ~2012

ADR-03

Filesystem support

Chosen

FAT32 + ISO9660, read-only

Rejected

ext4; btrfs; write support

When the rejected choice is right

ext4 wins when the loader must read a separate /boot on a Linux-root-only appliance with no ESP

Why: FAT32 is UEFI-ESP-mandatory; ISO9660 covers optical/USB install media (P2, I10)

ADR-04

Kernel image formats

Chosen

ELF64 + Multiboot2 + Linux bzImage

Rejected

PE (Windows kernels) only

When the rejected choice is right

PE wins when the sole target is a Windows-family kernel handoff

Why: covers Linux, BSD/microkernel (Multiboot2), and generic ELF targets (P12)

ADR-05

Signature format

Chosen

PKCS#7 detached SignedData

Rejected

raw Ed25519 signature; X.509-only chain w/o PKCS#7 wrapper

When the rejected choice is right

raw Ed25519 wins in a closed embedded fleet with no UEFI Secure Boot interop requirement

Why: matches UEFI Secure Boot's existing db/dbx cert-chain model (I6)

ADR-06

A/B metadata format

Chosen

32-byte BCB, ping-pong slots

Rejected

single-slot with journal; three-slot

When the rejected choice is right

three-slot wins when field-return telemetry shows single ping-pong insufficient under repeated brownouts

Why: fits one sector; matches Android BCB precedent (P10, I5)

ADR-07

Splash rendering

Chosen

double-buffered GOP framebuffer

Rejected

single-buffer; text-only

When the rejected choice is right

text-only wins on firmware lacking GOP (serial-console embedded targets)

Why: tear-free at 60 FPS (I12, §4)

ADR-08

Recovery path

Chosen

first-class recovery/failsafe menu entry from Phase 8

Rejected

recovery bolted on post-release

When the rejected choice is right

bolted-on recovery wins only for a disposable prototype that will not reach production deployment

Why: P14 — recovery must be conformance-tested, not assumed

ADR-09

Internal handoff representation

Chosen

one HandoffState, serialized per protocol at the boundary

Rejected

per-protocol handoff logic duplicated

When the rejected choice is right

duplicated logic wins for a loader supporting exactly one protocol forever

Why: P12 — avoids three drifting implementations

ADR-10

Image load addressing

Chosen

Rejected

When the rejected choice is right

self-randomization wins if the loader itself becomes a named attack target needing layout hiding

Why: P4 — fuzz/measured-boot reproducibility

ADR-11

Conformance baseline

Chosen

Rejected

When the rejected choice is right

spec-only wins when GRUB2's own behavior deviates from spec and that deviation must not be replicated

Why: GRUB2 is the de-facto production bootloader; behavioral parity is the real bar

ADR-12

Continuous fuzzing

Chosen

Rejected

When the rejected choice is right

34. Alternative Architectures (Roads Not Taken)

Alternative A — Scriptable configuration (GRUB2/U-Boot model).

┌──────────────┐     ┌────────────────────┐
│ Firmware     │────▶│ Turing-complete    │──▶ kernel
└──────────────┘     │ config shell/VM    │
                      └────────────────────┘

Regime where it wins: heterogeneous fleets needing runtime-conditional boot logic without rebuilding the loader (distro-agnostic GRUB2 deployments). Real system: GRUB2's grub.cfg scripting engine, U-Boot's command shell. Rejected here because a Turing-complete pre-auth parser is the exact attack surface BootHole exploited (P3, §22 T1) — this design's static declarative config (ADR of the config parser) trades runtime flexibility for a bounded, fuzzable, auditable parser.

Alternative B — Dynamic Root of Trust (DRTM / Intel TXT / AMD SKINIT).

┌──────────┐  SENTER/SKINIT  ┌───────────────────┐
│ Untrusted│───────────────▶ │ Hardware-enforced │──▶ measured kernel
│ pre-boot │  (late launch)  │ minimal CPU state │
└──────────┘                  └───────────────────┘

Regime where it wins: a threat model that must not trust any pre-boot firmware, including this loader itself (Flicker, McCune et al. 2008; OSLO, Kauer 2007). Real system: Flicker's TXT-based late launch. Rejected here (ADR-16) because it requires specific CPU/chipset support absent on much fielded hardware, and this project's SRTM chain already covers the stated threat model (tampering detectable via PCR divergence, T10) at far broader hardware compatibility.

Alternative C — Firmware-embedded loader (coreboot payload model).

┌───────────────────────────────────┐
│ coreboot (romstage+ramstage)      │
│  └── payload = this loader, baked │
│      into the firmware image      │
└───────────────────────────────────┘

Regime where it wins: fully-owned hardware (embedded appliances, cloud server fleets) where the vendor controls both firmware and payload and wants a single flashable image. Real system: coreboot with a custom payload. Rejected here because the primary deployment model (§1) targets commodity UEFI/BIOS hardware the project does not control the firmware of — a payload-embedded design would require a coreboot port per board, which the ESP/MBR-installable model (ADR-02) avoids entirely.

Alternative D — Network-first boot (PXE/HTTP boot as the primary path).

┌──────────┐   DHCP/PXE   ┌──────────────┐   HTTP/TFTP   ┌────────┐
│ Firmware │─────────────▶│ Network stack│──────────────▶│ Kernel │
└──────────┘              └──────────────┘               └────────┘

Regime where it wins: diskless data-center fleets provisioning kernels centrally (common in large-scale cloud/HPC deployments). Real system: iPXE, UEFI HTTP Boot. Rejected here (deferred, §35) because the stated scope (§1) is a locally-installed, disk-resident loader with A/B update semantics that presume local storage; network boot is a materially different trust and availability model (a network outage becomes a boot-blocking failure) left to a future, explicitly separate design.
