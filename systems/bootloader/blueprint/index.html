1. Goal & Scope

Specify a bootloader that takes a machine from firmware power-on to a running kernel across both legacy BIOS and UEFI firmware, in Rust, covering the full chain: firmware POST → stage-0 load → (BIOS) real→protected→long mode transition or (UEFI) boot-services-driven load → memory-map acquisition (E820 / GetMemoryMap) → kernel image parse (ELF64, Multiboot2, Linux bzImage) → measured/signed verification (TPM PCR extend, PKCS#7) → ExitBootServices → boot-info handoff → kernel entry — with A/B slot tracking and failsafe recovery as first-class boot paths, not add-ons.

Phase-0 deliverable (numbered modules, matching Repository Layout §10):

  1. bl-core — Firmware trait, MemoryMap, HandoffState, error types.
  2. bl-firmware-uefi — UEFI Boot/Runtime Services backend.
  3. bl-fs-fat32 — read-only FAT32 reader (ESP access).
  4. bl-image-elf — ELF64 kernel parser + loader.
  5. bl-menu-ui — text-mode boot menu.
  6. bl-sim — deterministic simulator exercising every System Invariant (§7).
  7. conformance/buckets/ — the Phase-0 fixture set (§17.5 equivalent seed).

System boundaries. Provides: firmware abstraction, disk/filesystem read, kernel image parsing (ELF64/Multiboot2/bzImage), signature verification, TPM measurement, boot-info handoff, A/B slot selection, recovery menu, conformance harness. Delegates: kernel-side init (mm/scheduler/drivers), firmware POST itself, disk write paths (none — read-only by design, P2), TPM chip firmware. Does NOT provide: a general-purpose shell, network stack, disk encryption, a package manager, GPU drivers for the splash beyond a linear framebuffer.

Non-goals. Not a general PXE/network-boot stack (deferred, §35); not a write-capable filesystem; not a hypervisor loader; not a virus scanner.

Deployment model. A signed UEFI PE32+ application (primary) or a BIOS MBR+stage-1.5 chain (legacy/rescue) installed to the ESP or MBR gap; invoked once per power cycle by firmware; terminates by jumping to the kernel (never returns except on fatal error → recovery menu).

Target users/operators. OS distributors shipping signed kernels; embedded-appliance vendors needing A/B field updates; kernel developers needing a conformant, inspectable reference loader for QEMU/OVMF testing.

What later phases unlock. Phase 0–1 unlock a bootable "hello" on OVMF; Phase 2–3 unlock real hardware boot (BIOS and UEFI); Phase 4–6 unlock loading a real signed Linux kernel; Phase 7 unlocks Secure/measured boot; Phase 8 unlocks field-safe A/B updates; Phase 9 unlocks release-grade differential conformance against GRUB2.

Language: Rust, no_std, custom target spec. Rationale: memory safety in a domain (pointer arithmetic over physical memory, ASN.1 parsing of attacker-influenced signature blobs) where C/C++ bootloaders have shipped the exact CVE classes this project must avoid (CVE-2020-10713 "BootHole", a GRUB2 grub.cfg parser buffer overflow). Rejected: C (memory-unsafe in the two highest-risk components — ASN.1/config parsing); Zig (immature no_std UEFI/BIOS target ecosystem as of this writing); Ada/SPARK (proven safety story but ref-implementation ecosystem — GRUB2, Limine, U-Boot — and hiring pool are C/Rust, hurting differential-test and audit parity, ADR-01).

Prerequisites. x86-64 privilege levels and paging (Intel SDM Vol. 3); ELF64 and PE32+ object formats; UEFI Boot/Runtime Services semantics; TCG measured-boot (PCR/TPM) fundamentals; FAT32 on-disk layout.

Estimated timeline. Phase 0: 2 weeks. Full system (Phases 0–9): 7 months.

Deferred features, each registered in the Deferred Features Register (§35):

  • Network/PXE boot — PhaseDeferred("§35")
  • ext4 root-partition read — PhaseDeferred("§35")
  • GPT-only enforcement (reject MBR) — PhaseDeferred("§35")
  • LUKS-encrypted root unlock — PhaseDeferred("§35")
  • Dynamic Root of Trust, DRTM/Intel TXT — PhaseDeferred("§35")
  • Windows PE kernel-format loading — PhaseDeferred("§35")
  • Secure Boot key enrollment / MOK UI — PhaseDeferred("§35")

2. Why Build This

A bootloader is the one program every OS depends on yet almost none of its engineers understand end to end. It is the concentrated intersection of privilege-level transitions (real→protected→long mode, Intel SDM Vol. 3 §9), two independent firmware ABIs (BIOS INT-services vs UEFI Boot/Runtime Services), three kernel image formats with incompatible handoff contracts (ELF64, Multiboot2, Linux bzImage), and a security chain (Secure Boot + measured boot) that must be correct with zero retries — a bug here is not "restart the request," it is "the machine will not boot."

Building this teaches: physical-memory bring-up before any allocator exists; the exact sequence in which mode transitions become irreversible (GDT before CR0.PE, page tables before EFER.LME, per P6); why "verify before parse" (P3) is the single lesson BootHole and BootStomp both teach; and why A/B update systems (Android's Boot Control Block ancestry) are a distributed-consensus problem compressed into 32 bytes of flash (I5, I11).

It cross-links to coreboot (firmware/payload boundary — same lesson as P1's Firmware trait), GRUB2 (multi-format kernel loading — same problem as Phase 6's Multiboot2/bzImage split), systemd-boot (minimal UEFI boot-manager scope discipline), and U-Boot (embedded staged loading — the ancestor of this project's A/B design, Phase 8). The calibration value: after this, a distributed-systems engineer can read a kernel panic's registers and know whether the bootloader's handoff was wrong before the kernel ever ran a line of its own code.

What Mastery Looks Like:

  • Trace a cold boot from POST to kernel _start citing the exact firmware call, register, or page-table write at each step (Phase 0–3, §12–§15).
  • Explain why ExitBootServices can fail and design the bounded-retry fix without introducing an unbounded loop (I13, Phase 3, §15).
  • Derive the GDT/page-table/EFER.LME ordering for long-mode entry from first principles, not memorization (Phase 2, §14, P6, I3, I4).
  • Diagnose a BootHole-class parser vulnerability by inspection and name the structural mitigation this design uses instead (Phase 6, §18, P3).
  • Design a measured-boot PCR allocation and defend it against a TOCTOU attack on the measure-then-execute boundary (Phase 7, §19, P9, I7).
  • Reason about A/B rollback safety as a monotonic-counter consensus problem and identify the exact power-loss window it must survive (Phase 8, §20, I5, I11).
  • Run a differential-conformance argument against a real system (GRUB2) and explain every intentional divergence (Phase 9, §21, ADR-11).

Firmware box — the only code that ever calls BIOS interrupts or UEFI protocol methods directly; everything downstream is firmware-agnostic (trust boundary + concurrency boundary: single-threaded, no interrupts enabled after Phase 2 stage-1). Mode/Handoff shim — the irreversible transition boundary; once past it, no rollback to a lower privilege/mode is attempted. Disk/filesystem reader — a persistence boundary that is read-only end to end (I10); the loader never becomes a write amplifier. Config/Menu — the only interactive/human boundary; bounded input, bounded render time (§4). Measured/Secure verify — the security trust boundary; nothing downstream of it runs unverified bytes (P3, I6). Kernel image loader — protocol boundary: three wire formats normalized to one internal HandoffState. A/B + jump — the point of no return; after the jump, the loader's memory is either freed or reclassified and never touched again (I2).

6. Design Principles

  1. P1 — Firmware behind a trait. No firmware-specific call outside a Firmware trait impl. Tradeoff: an indirection layer on every disk/console op. Operational implication: one crate per firmware backend (ADR-02). Violate it and BIOS/UEFI code intermixes, breaking the differential suite (§21).
  2. P2 — Read-only until handoff. No persistent write paths except the signed A/B metadata (Phase 8). Tradeoff: no in-place repair of a corrupt filesystem. Violate it and I10 breaks, invalidating the entire threat model's "loader cannot brick storage" claim.
  3. P3 — Verify before parse. Signature/measurement precedes any untrusted-format parsing. Tradeoff: verification of the whole image before any lazy/partial parse. Violate it and BootHole/BootStomp-class parser bugs become pre-auth (Threat Model T1/T3).
  4. P4 — Deterministic memory layout. Same input → identical physical addresses. Tradeoff: no ASLR-style loader self-randomization. Violate it and fuzz findings stop reproducing, and measured-boot PCR values stop being comparable across boots.
  5. P5 — Fail loud, fail safe. Any inconsistency halts to a diagnosable state, never a silent continue. Tradeoff: some transient errors that could be retried instead abort. Violate it and operators lose the signal that distinguishes "hardware hiccup" from "corrupted chain."
  6. P6 — Explicit mode transitions. Real→protected→long mode is an atomic, logged sequence, never partially applied. Tradeoff: no incremental/lazy paging setup. Violate it and I3/I4 break — a kernel entered in an inconsistent CPU state.
  7. P7 — One memory-map source of truth. The last GetMemoryMap/E820 snapshot is canonical; nothing re-derives it. Tradeoff: any allocation after the snapshot forces a re-snapshot (I1). Violate it and the kernel receives a memory map inconsistent with what firmware actually owns.
  8. P8 — Time-budgeted critical path. Every stage carries an explicit ms budget (§4), CI-gated. Tradeoff: engineering time spent on benchmarking harnesses. Violate it and boot-time regressions ship silently.
  9. P9 — Measurement before execution. A PCR extend precedes execution of any loaded component (TCG SRTM order). Tradeoff: measurement adds latency (§4, ≤ 15 ms/event) to every stage. Violate it and the measured-boot chain of custody has a gap an attacker can exploit (TOCTOU, Threat Model T9).
  10. P10 — A/B atomicity via ping-pong. Never a window where both BCB slots are simultaneously invalid. Tradeoff: double the metadata writes. Violate it and I5/I11 break — a power-loss mid-write can strand the device unbootable.
  11. P11 — Small, auditable TCB. no_std, no heap allocation in the verify/measure critical path (Phase 7). Tradeoff: fixed-capacity buffers instead of dynamic allocation. Violate it and the TCB size argument in the Threat Model (§22) no longer holds.
  12. P12 — Protocol-agnostic handoff boundary. Multiboot2's tag list and Linux boot_params are alternate encodings of one internal HandoffState; the loader never branches deep logic per protocol. Tradeoff: one extra serialization step per format. Violate it and three parallel, drifting handoff implementations accumulate.
  13. P13 — No hidden retries. Every retry loop has a bounded, logged count (e.g. ExitBootServices ≤ 5, I13). Tradeoff: an operator sees a retry-exhausted halt instead of an infinite hang. Violate it and a stale-memory-map loop can spin forever with no operator signal.
  14. P14 — Recovery is a first-class boot path. The recovery/failsafe menu entry is built and conformance-tested from Phase 8 on, not bolted on at the end. Tradeoff: recovery-path code must track every upstream format/verify change. Violate it and the one path meant to save a bricked device is the least-tested code in the system.

Memory Map Schemas

E820 entry (BIOS INT 15h, AX=0xE820), 20–24 bytes:

struct E820Entry {
    base_addr: u64,
    length: u64,
    kind: u32,          // 1=usable 2=reserved 3=ACPI-reclaim 4=ACPI-NVS 5=bad
    ext_attributes: u32, // present only if returned size == 24 (ACPI 3.0)
}

UEFI EFI_MEMORY_DESCRIPTOR (GetMemoryMap), fixed 40 bytes (padded):

struct EfiMemoryDescriptor {
    kind: u32,           // EfiLoaderCode, EfiConventionalMemory, ...
    pad: u32,
    physical_start: u64,
    virtual_start: u64,
    number_of_pages: u64,
    attribute: u64,      // EFI_MEMORY_WB/WT/RUNTIME/...
}

MemoryMap (Core Schema §11) normalizes both into one internal representation (P7): a sorted, non-overlapping list of (base, length, class) ranges, class ∈ {Usable, Reserved, AcpiReclaim, AcpiNvs, Bad}.

ELF64 / Kernel Handoff

ELF64 header fields load-bearing for boot: e_ident[EI_CLASS]=ELFCLASS64, e_type=ET_EXEC, e_machine=EM_X86_64, e_entry, e_phoff, e_phnum. Program headers of type PT_LOAD give (p_vaddr, p_paddr, p_filesz, p_memsz, p_flags); the loader copies p_filesz bytes from the image and zero-fills the remaining p_memsz - p_filesz (BSS). I8 requires e_entry to fall within some PT_LOAD's [p_vaddr, p_vaddr+p_memsz).

UEFI Boot Protocol (Worked Example)

Booting a signed Linux bzImage on UEFI, end to end:

  1. Firmware LoadImage + StartImage on the loader's PE32+ binary.
  2. Loader opens EFI_SIMPLE_FILE_SYSTEM_PROTOCOL on the ESP, reads bl-config's menu file via bl-fs-fat32.
  3. Operator selects the default entry (menu-ui, ≤ 100 ms render, §4).
  4. bl-measure extends PCR 4 with the kernel image hash (P9, I7).
  5. bl-verify checks the PKCS#7 signature over the same hash (I6).
  6. bl-image-bzimage parses the bzImage header, builds boot_params.
  7. Loader calls GetMemoryMap, then ExitBootServices(ImageHandle, MapKey) (I1, bounded retry ≤ 5, I13).
  8. Loader jumps to the kernel's protected-mode entry per the Linux x86 Boot Protocol register contract (Documentation/x86/boot.rst).

Malformed-Input Example

A Multiboot2 tag with tag_size extending past total_size: the parser must reject with a named error (Mb2Error::TagOverrun) before dereferencing any byte past the info structure's declared bound — never a raw pointer walk that trusts tag_size (the BootHole/CVE-2020-10713 lesson, P3).

Failure-Path Example

ExitBootServices returns EFI_INVALID_PARAMETER (stale MapKey — a console print between GetMemoryMap and ExitBootServices allocated memory and invalidated the map, violating I1). The loader re-issues GetMemoryMap, retries ExitBootServices (retry count now 1 of 5, I13). After 5 exhausted retries: fatal halt, diagnostic code E-EBS-RETRY printed to console + serial (Operational Readiness, §24).

13. Phase 1 — Core Types, Firmware Trait & Memory Map Model

13.1 Objectives

13.2 Detailed Implementation Steps

Implement the types exactly as declared in §11, fixed-capacity (no heap, P11): MemoryMap holds MAX_MEM_RANGES = 128 entries (E820/UEFI typically report 20–40 on commodity hardware; 128 gives 3× headroom). Firmware::exit_boot_services takes self by value (I2 — the type system, not a runtime check, makes a post-exit call to boot services a compile error, per ADR-01's memory-safety rationale). Write bl-sim's assert_i1 to replay a two-call memory_map() sequence and assert the second snapshot is used verbatim by any downstream consumer (P7).

13.3 Deliverable

bl-core compiles standalone; unit tests cover MemoryMap normalization from both a synthetic E820 table and a synthetic UEFI descriptor array, proving both map to the same MemClass values for equivalent inputs.

13.4 Acceptance Criteria

100% of bl-core unit tests pass; assert_i1 and assert_i2 (I1, I2, §7) both report PASS under bl-sim; MemoryMap struct size ≤ 2,064 bytes (128 × 16-byte MemRange + 16-byte header, fixed per P11).

13.5 Conformance Fixtures

fixtures/memmap/e820-typical.bin — a 24-entry synthetic E820 table; expected: 24 MemRange entries, classes matching a hand-verified table. fixtures/memmap/uefi-typical.bin — analogous UEFI descriptor array. fixtures/memmap/e820-overflow.bin — 200 entries (exceeds MAX_MEM_RANGES); expected: FwError::Unsupported, not a buffer overrun.

13.6 Pitfalls

  • Firmware::memory_map() returning a snapshot that callers then cache across an exit_boot_services call reintroduces the I1 hazard the type signature was designed to prevent — code review must reject any MemoryMap stored outside the immediate call site until re-snapshotted.
  • A trait method returning a non-Send type silently blocks a future concurrent conformance-runner design; Firmware: Send is asserted at the trait bound from commit one.

13.7 Performance Concerns

MemoryMap normalization is O(n log n) (sort for overlap detection, P7); at n ≤ 128 this is sub-microsecond and not on the critical path budget (§4) — no further optimization needed at this phase.

13.8 Edge Cases

Two E820 entries reporting overlapping ranges with different kind (a known BIOS quirk) — normalization must pick the more restrictive class (Reserved over Usable) rather than the last-seen entry, or a kernel could receive a memory range firmware actually reserved.

13.9 Failure Analysis

An Unsupported error from memory_map() on a firmware reporting > 128 ranges is a hard stop (not a partial map) — a partial map silently violates P7 and is strictly worse than a clean abort with diagnostic E-MEMMAP-OVERFLOW.

13.10 Operational Notes

14. Phase 2 — BIOS Real-Mode Boot & Mode Transition

14.1 Objectives

Implement the BIOS path: 16-bit real-mode stage-0 (MBR, ≤ 440 bytes, §4) and stage-1.5 (≤ 32,256 bytes) that together perform the real→protected →long mode transition (P6) before handing off to bl-core Rust code. Constraint introduced: this is the one phase touching raw assembly-level CPU state directly (I3/I4/I9).

14.2 Detailed Implementation Steps

Stage-0 (MBR): loads stage-1.5 from the track-0 gap via INT 13h extended reads. Stage-1.5: builds a minimal GDT (null, code32, data32, code64, data64 descriptors, I4), sets CR0.PE=1 and far-jumps to reload CS with the 32-bit code selector (real→protected, per Intel SDM Vol. 3, section 9.9, applying P6). Builds identity-mapped page tables for the low 1 GiB (PML4→PDPT→PD, 2 MiB pages, ADR-13), sets CR4.PAE=1, writes EFER.LME=1 via wrmsr to MSR 0xC0000080, sets CR0.PG=1 (protected→long, per SDM Vol. 3, section 9.8.5, I3), far-jumps to the 64-bit code selector. Control transfers to bl-firmware-bios's Rust entry point, which constructs a Firmware impl (P1) reading via INT 13h.

14.3 Deliverable

A bootable MBR+stage-1.5 chain that reaches 64-bit long mode with a working Firmware implementation, verified by bl-sim's assert_i3, assert_i4, assert_i9 against a recorded CPU-state trace from the SeaBIOS conformance run.

14.4 Acceptance Criteria

assert_i3/assert_i4/assert_i9 all PASS under bl-sim (§7); stage-0 binary size ≤ 440 bytes (verified by size check in CI, §4); stage-1.5 binary size ≤ 32,256 bytes; mode-transition sequence completes in < 5 ms p50 on SeaBIOS (contributes to the M1 500 ms total budget, §28).

14.5 Conformance Fixtures

conformance/buckets/firmware-bios/mode-transition.fixture — asserts GDTR, CR0, CR4, EFER register values at each named checkpoint match the expected sequence. fixtures/mode/missing-page-tables.bin — a crafted stage-1.5 binary with CR0.PG set before page tables are built; expected: triple-fault detected by the OVMF/SeaBIOS test harness's reset counter, documented as an intentional negative test (I3 violation proof).

14.6 Pitfalls

  • Enabling long mode without setting up the GDT and paging first triple-faults the CPU with no diagnostic output possible (P6) — the fix is the strict order: page tables → CR4.PAE → EFER.LME → CR0.PG → far jump, never reordered, per ADR-13.
  • Real-mode segment:offset addressing accidentally left in a helper function called post-CR0.PE=1 silently reads the wrong physical address (I9) — caught only by bl-sim's static-review assertion, since the CPU will not fault on it.
  • A page-table structure placed above 4 GiB physical is unreachable by a 32-bit-mode page-table-base write to CR3 — allocate tables in the first 1 MiB.

14.7 Performance Concerns

The mode-transition sequence itself is CPU-cycle-cheap (a few hundred cycles for register writes); the dominant real cost is the INT 13h disk reads for stage-1.5 (BIOS disk I/O has no DMA fast path on most implementations) — budget accordingly against M2 (§28).

14.8 Edge Cases

A BIOS that does not support INT 13h extended reads (LBA) falls back to CHS addressing, which cannot address beyond ~8 GiB — documented as an explicit unsupported-hardware boundary (Compatibility & Versioning, §25), not a silent truncation.

14.9 Failure Analysis

A triple-fault during mode transition resets the CPU with zero diagnostic capability (no console yet) — the only forensic artifact available is bl-sim's recorded trace from the last passing CI run, which is why bl-sim asserts every checkpoint in isolation before any hardware boot is attempted (Testing & Verification Strategy, §26).

14.10 Operational Notes

This phase has no post-deployment operational surface (it runs once, pre-console); its only "telemetry" is the CI trace. Any change to the GDT/page-table layout is a breaking change to bl-firmware-uefi's long-mode assumptions too (Phase 3) and must be reviewed against ADR-13.

15. Phase 3 — UEFI Firmware Backend

15.1 Objectives

Implement Firmware for UEFI (bl-firmware-uefi) atop EFI_BOOT_ SERVICES/EFI_RUNTIME_SERVICES, including the GetMemoryMap → ExitBootServices sequence (I1, I2, I13). Constraint introduced: this crate is the only place UEFI protocol pointers are dereferenced (P1, P11).

15.2 Detailed Implementation Steps

Wrap EFI_SYSTEM_TABLE.BootServices calls: AllocatePages, LocateProtocol (Simple File System, Block I/O, GOP, TPM2, Loaded Image — bounded to ≤ 16 concurrent handles, §4), GetMemoryMap. UTF-8 → UTF-16LE null-terminated conversion for console_print (bounded buffer, P11). Implement exit_boot_services per I2's consuming signature: loop {GetMemoryMap; attempt ExitBootServices; on EFI_INVALID_PARAMETER (stale MapKey), retry} bounded at 5 (I13, P13, applying the Bulygin et al. 2015 CanSecWest lesson that firmware memory-map timing is adversarial-adjacent even without malice). On exhaustion, halt with diagnostic E-EBS-RETRY (§24).

15.3 Deliverable

bl-firmware-uefi compiles for x86_64-unknown-uefi and passes the firmware-uefi conformance bucket on OVMF, including a successful ExitBootServices under both a clean first-attempt and a forced-retry scenario.

15.4 Acceptance Criteria

conformance/buckets/firmware-uefi/ 100% green on OVMF; console print latency < 10 µs/character p50 (UEFI console overhead, M-series §28); ExitBootServices succeeds within 5 retries in 100% of 10,000 fuzzed memory-layout-drift trials (fixtures/uefi/ebs-retry-fuzz.corpus); zero EFI_BOOT_SERVICES calls observed post-exit in bl-sim trace (I2).

15.5 Conformance Fixtures

conformance/buckets/firmware-uefi/ebs-clean.fixture — no memory churn between GetMemoryMap and ExitBootServices; expects success on attempt 1. conformance/buckets/firmware-uefi/ebs-retry.fixture — injects one allocation between the calls; expects success on attempt 2. conformance/buckets/firmware-uefi/ebs-exhaust.fixture — injects churn on every attempt; expects halt with E-EBS-RETRY after exactly 5 attempts, not a hang.

15.6 Pitfalls

  • ExitBootServices requires the MapKey from the most recent GetMemoryMap call; any allocation between the two (including a console print that triggers an internal firmware allocation) invalidates it — the fix is to call GetMemoryMap last, immediately before ExitBootServices, with no intervening calls (I1).
  • UEFI strings are UTF-16LE, null-terminated — printing a raw UTF-8 buffer through the console protocol produces console garbage, not an error; a conformance fixture must render and byte-compare the actual console output to catch this class.
  • LocateProtocol for GOP can return EFI_NOT_FOUND on serial-only firmware — this is not an error, it is the ADR-21 text-mode-default fallback path, and must not be logged as a failure.

15.7 Performance Concerns

GetMemoryMap cost scales with map-entry count (typically 20–60 descriptors on commodity UEFI firmware); calling it twice per boot (pre-flight + final) is within the M9 ExitBootServices < 10 ms budget (§28) but a third call for any reason would risk the total boot-time budget (§4) — code review flags any new GetMemoryMap call site.

15.8 Edge Cases

A firmware implementation whose ExitBootServices succeeds but leaves one runtime-service call (SetVirtualAddressMap) required before certain runtime services work correctly — documented as a per-firmware quirk table in docs/runbooks/ (Operational Readiness, §24), not silently worked around in code.

15.9 Failure Analysis

Exhausting the 5-retry budget on ExitBootServices is a fatal, diagnosable halt (E-EBS-RETRY, console + serial, ADR-22) rather than an infinite loop — blast radius is this boot attempt only; the next power cycle re-runs from POST with no persisted bad state (I2 ensures no boot-services handle survives to poison a retry).

15.10 Operational Notes

Telemetry: boot.memmap.key_mismatch counter (I1, §7) is emitted on every retry and should alert if its rate exceeds 1% of boots in fleet telemetry (Operational Readiness, §24) — a persistently high rate indicates a firmware bug worth a vendor report, not a loader bug.

16. Phase 4 — Disk & Filesystem Reader

16.1 Objectives

Implement read-only FAT32 (bl-fs-fat32) and ISO9660 (bl-fs-iso9660) readers atop the Firmware::read_disk primitive (P1, P2, I10). Constraint: no write path exists anywhere in either crate — enforced by the trait surface itself, not a runtime check.

16.2 Detailed Implementation Steps

FAT32: parse the BPB (BIOS Parameter Block) for cluster size and FAT location; walk the FAT chain cluster-by-cluster; reassemble Long File Name (LFN) directory entries, which are stored in reverse order (last physical entry is the first logical fragment) — applying P2 (no write path) and the FAT spec's LFN checksum field to detect a corrupt chain before trusting a reassembled name. ISO9660: parse the Primary Volume Descriptor, walk the path table. Both expose one common FileReader trait method surface consumed identically by Phase 5/6 loaders (P1-adjacent abstraction discipline).

16.3 Deliverable

bl-fs-fat32 reads arbitrary files from a FAT32-formatted ESP image under OVMF; bl-fs-iso9660 reads files from an ISO9660 image; both green on their conformance buckets.

16.4 Acceptance Criteria

Read a 1 MiB file from FAT32 in < 50 ms p50 (M5, §28); read a 1 MiB file from ISO9660 in < 60 ms p50; a corrupted FAT chain (fixture below) produces FsError::ChainCorrupt, never a hang or wrong-data read; LFN reassembly round-trips 20 named fixtures with names up to 255 UTF-16 code units.

16.5 Conformance Fixtures

conformance/buckets/fs-fat32/lfn-reassembly.fixture — 20 files with long names of varying fragment counts; expects exact name match. conformance/buckets/fs-fat32/corrupt-chain.fixture — a FAT table with a cluster pointing to itself (cycle); expects FsError::ChainCorrupt within a bounded cluster-visit count, not an infinite walk. conformance/buckets/fs-fat32/large-file.fixture — a 32 MiB file; expects correct read within the M5-adjacent time budget scaled linearly.

16.6 Pitfalls

  • FAT32 cluster size varies per volume (the BPB declares it — 4 KiB to 64 KiB is common); hardcoding a cluster size silently misreads every volume formatted differently than the dev fixture.
  • LFN entries are stored in reverse fragment order; reassembling them in physical-storage order instead of reversed produces a scrambled filename that still "looks like" a valid string — a subtle, non-crashing bug caught only by exact-match conformance fixtures.
  • A self-referential FAT chain (corruption or malice) walked without a visited-cluster bound loops forever — bound every chain walk at MAX_MEM_RANGES-scale cluster count (analogous discipline to I13).

16.7 Performance Concerns

Cluster-chain walks are inherently sequential (each entry names the next); read-ahead/prefetch of the next cluster while processing the current one hides most of the per-cluster INT13h/Block I/O latency, keeping the M5/M6 budgets achievable without a full async I/O model (out of scope per P11's no-heap-runtime discipline).

16.8 Edge Cases

A FAT32 volume with the "dirty bit" set (unclean previous unmount) is read-only-safe to read regardless (P2) but the loader logs a warning, since the filesystem's consistency is not guaranteed by the driver that left it dirty.

16.9 Failure Analysis

A FsError::ChainCorrupt on the menu config file itself (not a kernel image) degrades to the recovery path (P14, Phase 8) rather than a hard halt, since a corrupt config is recoverable via the failsafe entry while a corrupt kernel image is not.

16.10 Operational Notes

No filesystem write path exists to roll back (P2); "migration" for this crate means only the read-format version support matrix documented in Compatibility & Versioning (§25) — e.g., FAT32 with exFAT-adjacent extensions is explicitly unsupported and documented, not silently misread.

17. Phase 5 — ELF64 Kernel Loader & HandoffState

17.1 Objectives

Implement bl-image-elf: parse an ELF64 kernel image, load PT_LOAD segments to their declared physical addresses, validate the entry point (I8), and populate the internal HandoffState (P12, I14).

17.2 Detailed Implementation Steps

Validate e_ident magic + EI_CLASS=ELFCLASS64 + e_machine=EM_X86_64 before touching any other field (P3-adjacent — validate structure before trusting offsets). Walk e_phoff/e_phnum program headers; for each PT_LOAD, copy p_filesz bytes from the image buffer to p_paddr and zero-fill the remaining p_memsz - p_filesz (BSS). Assert e_entry falls within some PT_LOAD's [p_vaddr, p_vaddr+p_memsz) range before accepting the image (I8, enforced in bl-sim's assert_i8). Populate HandoffState fully (I14) — every field either a real value or an explicit None, never left as zeroed-but-meaningful memory.

17.3 Deliverable

bl-image-elf loads a real statically-linked ELF64 test kernel (a minimal Rust no_std binary built as part of the fixture set) and bl-sim confirms HandoffState is fully populated before the (stubbed, this phase) jump.

17.4 Acceptance Criteria

assert_i8 and assert_i14 PASS (§7); load a 10 MiB ELF64 image in < 150 ms p50 (contributes to M2's 200 ms bzImage-equivalent budget, §28, scaled for format overhead); 100% of conformance/buckets/ image-elf/ fixtures green, including the malformed-entry-point negative fixture below.

17.5 Conformance Fixtures

conformance/buckets/image-elf/minimal-kernel.fixture — a real minimal ELF64 kernel; expects successful load + correct entry address. fixtures/elf/entry-out-of-range.bin — e_entry set outside every PT_LOAD range; expects ElfError::EntryOutOfRange (I8 negative test), never a jump attempt. fixtures/elf/oversized-phnum.bin — e_phnum claiming more headers than the file contains; expects ElfError::Truncated, not an out-of-bounds read.

17.6 Pitfalls

  • Trusting e_phnum without checking it against the actual file length invites an out-of-bounds program-header read on a truncated or malicious file — bound every header read against the known file size before dereferencing (the BootHole/CVE-2020-10713 lesson applied to a different parser, P3).
  • Copying p_filesz bytes but forgetting to zero the BSS region (p_memsz - p_filesz) leaves stale loader memory visible to the kernel as if it were zero-initialized data — a classic information-disclosure-adjacent bug class.

17.7 Performance Concerns

Segment copies are the dominant cost (memory-bandwidth bound, not CPU-bound); batching all PT_LOAD copies before any BSS zero-fill maximizes sequential-write locality and stays within the M2-adjacent budget.

17.8 Edge Cases

Overlapping PT_LOAD segments (a malformed or adversarial image) — the loader must detect overlap before copying and reject with ElfError::OverlappingSegments, since a naive last-write-wins copy order could let one segment silently corrupt another's data.

17.9 Failure Analysis

Any ElfError at this phase aborts the boot attempt for this entry and falls through to the menu (or recovery entry if this was the default, P14) — it never partially populates HandoffState and attempts a jump regardless (I14 is all-or-nothing).

17.10 Operational Notes

loader.entry.out_of_range and loader.elf.truncated counters (§7, I8) feed the same fleet dashboard as Phase 3's memory-map counters (Operational Readiness, §24); a spike after a kernel-package update indicates a build-system regression upstream, not a loader defect.

18. Phase 6 — Multiboot2 Protocol & Linux bzImage Loader

18.1 Objectives

Implement bl-image-multiboot2 and bl-image-bzimage, both converging on the same HandoffState as Phase 5 (P12) via format-specific serializers in bl-handoff.

18.2 Detailed Implementation Steps

Multiboot2: validate the header magic 0xE85250D6 in the kernel image and the boot-info magic 0x36D76289 at handoff time; walk the tag stream, bounds-checking each tag_size against the info structure's total_size before advancing (P3, directly applying the malformed-input discipline from §8's worked example). bzImage: parse the Linux boot header, branch on header.version to determine which boot_params fields are valid for this protocol version (older protocol versions omit newer fields entirely — reading them is UB, not just wrong), load the compressed kernel and initramfs per the Linux x86 Boot Protocol (Documentation/x86/boot.rst), and set registers per the documented hand-off contract. Both loaders build one HandoffState internally and serialize it to the wire format at the last possible step (P12, ADR-09).

18.3 Deliverable

bl-image-multiboot2 boots a Multiboot2-compliant test kernel; bl-image-bzimage boots a real Linux kernel under OVMF, both verified against HandoffState completeness (I14).

18.4 Acceptance Criteria

Load a 10 MiB Multiboot2 kernel in < 200 ms p50 (M2, §28); load a 10 MiB bzImage in < 200 ms p50 (M2); a Multiboot2 tag with tag_size exceeding total_size is rejected with Mb2Error::TagOverrun in 100% of fixtures/mb2/tag-overrun.corpus (500 fuzzed cases); a bzImage header with header.version below the field being read is rejected with BzError::ProtocolTooOld.

18.5 Conformance Fixtures

conformance/buckets/image-multiboot2/real-kernel.fixture — a real Multiboot2-compliant microkernel test image. conformance/buckets/ image-bzimage/linux-lts.fixture — a real long-term-support Linux kernel build; expects boot to a documented "kernel alive" serial marker. fixtures/mb2/tag-overrun.corpus — 500 cargo-fuzz-generated truncated tag streams (ADR-12); expects clean rejection, zero panics.

18.6 Pitfalls

  • Multiboot2's tag list is variable-length and some tags are order-dependent (e.g. the memory-map tag must be consumed before certain later tags reference offsets relative to it) — a parser that assumes tag-order independence silently mis-decodes a spec-compliant but unusually-ordered kernel image.
  • Reading a bzImage boot_params field gated to protocol version 2.10 on a 2.05 image reads past the header's actual populated region into whatever memory follows — the fix is a strict version-gate table checked before every field access, not just at parse entry.
  • The kernel's embedded version string is informational only; using it to select the protocol path instead of header.version silently mis-parses images with a spoofed or stale version string.

18.7 Performance Concerns

Both formats' parse cost is dominated by tag/field-count, not image size — a pathological tag stream with thousands of zero-length tags (still within total_size) could add per-tag dispatch overhead; the fuzz corpus (18.5) includes such adversarial-shape inputs to catch this before it threatens the M2 budget.

18.8 Edge Cases

A Multiboot2 image declaring a memory-map tag that conflicts with the firmware's own GetMemoryMap/E820 report (Phase 1/3) — the loader trusts the firmware-reported map (P7) and treats the kernel-declared one as informational only, logging a mismatch rather than acting on it.

18.9 Failure Analysis

A rejected image at this phase never reaches HandoffState construction (I14's all-or-nothing guarantee, same as Phase 5) — the boot attempt falls through to the menu/recovery path (P14) with a named diagnostic (E-MB2-TAGOVERRUN / E-BZ-PROTOVER).

18.10 Operational Notes

Both loaders share bl-handoff's serializer telemetry (handoff.protocol tag on every emitted metric, Operational Readiness §24), letting a fleet dashboard distinguish Multiboot2-path boots from bzImage-path boots for capacity and regression analysis.

19. Phase 7 — Measured & Secure Boot

19.1 Objectives

Implement bl-measure (TPM 2.0 PCR extend) and bl-verify (PKCS#7 signature verification), enforcing P3 and P9 as the trust boundary before any kernel byte executes (I6, I7).

19.2 Detailed Implementation Steps

bl-measure: before loading the selected BootEntry's image bytes, compute their SHA-256 hash and issue a TPM2 PCR_Event/PCR_Extend to PCR 4 (kernel measurement, per TCG PC Client Platform Firmware Profile), recording a PcrEvent (§11) in the TCG event log — applying P9 and the Parno/McCune/Perrig "Bootstrapping Trust" model of chained measurement. bl-verify: parse the PKCS#7 detached SignedData structure (ASN.1 DER, via the vendored parser, ADR-18); extract the signer's certificate; walk the chain to a trust anchor in the UEFI db variable, rejecting any certificate present in dbx at any level (revocation, per the UEFI Secure Boot model); verify the signature over the same hash bl-measure computed (I6, applying P3 — this whole phase runs before Phase 5/6's format-specific parsing of the same bytes, per the BootStomp/BootHole "verify before parse" lesson, ADR-05).

19.3 Deliverable

bl-verify accepts a validly-signed test kernel and rejects a tampered one, both proven under OVMF with a populated db/dbx; bl- measure writes a PCR event visible via tpm2_pcrread in the QEMU swtpm conformance harness (per the vTPM paper's virtualized-TPM testing model, Berger et al. 2006).

19.4 Acceptance Criteria

Verify a 4 MiB image in < 50 ms p50 (M3, §28: ~10 ms SHA-256 + ~5 ms RSA-2048 + ~5 ms ASN.1 parse + margin); PCR extend completes in < 15 ms p50 per event (M-series); 100% of conformance/buckets/verify/ fixtures (valid, tampered, revoked-cert, expired-chain) produce the exact expected VerifyError variant or success; assert_i6/assert_ i7 PASS under bl-sim.

19.5 Conformance Fixtures

conformance/buckets/verify/valid-signature.fixture — a correctly signed test kernel; expects success. conformance/buckets/verify/ tampered-image.fixture — one byte flipped post-signing; expects VerifyError::HashMismatch. conformance/buckets/verify/revoked- cert.fixture — signer cert present in dbx; expects VerifyError::Revoked even though the signature itself is cryptographically valid. conformance/buckets/measure/pcr-order. fixture — asserts the PCR extend event precedes the verify-success event in the TCG log timestamp order (I7 ordering proof).

19.6 Pitfalls

  • ASN.1 DER parsing has many edge cases (indefinite-length BER smuggled into a DER context, oversized length fields); the vendored parser (ADR-18) rejects any non-canonical DER encoding rather than attempting best-effort tolerance, closing a class of parser-confusion attacks documented in the Matrosov/Rodionov/Bratus Rootkits and Bootkits Secure Boot bypass chapters.
  • Trust-anchor selection must check both db (allowed) and dbx (revoked) — checking only db re-opens exactly the BootHole revocation gap (a signature valid per db but later revoked via dbx must still be rejected).
  • Verifying the signature before computing the measurement (reversing P9's order) reintroduces the TOCTOU window Flicker (McCune et al.
    1. and the SRTM literature exist to close — measurement must be committed to the TPM before the bytes are trusted for anything else.

19.7 Performance Concerns

RSA-2048 verification is the more expensive of the two crypto operations (~5 ms) but SHA-256 over the full image dominates at 4+ MiB (~10 ms) — hashing incrementally while the image streams in from disk (overlapping Phase 4's I/O with hashing) is the primary lever if M3's 50 ms budget is threatened by larger kernel images.

19.8 Edge Cases

A QEMU swtpm-backed TPM under CI behaving subtly differently from a discrete hardware TPM (timing, PCR-reset semantics on VM restart) is a known virtualization-fidelity gap (per the vTPM paper, Berger et al. 2006) — documented explicitly so a CI-green result is never mistaken for hardware-TPM-equivalent proof.

19.9 Failure Analysis

A VerifyError of any variant aborts the boot attempt with zero partial trust extended — no PCR extend for a failed-verify path is retroactively "un-measured" (measurements are append-only by TPM design); the operator sees a clear diagnostic distinguishing HashMismatch (tampering) from Revoked (policy) from ChainNotTrusted (provisioning issue), each with a different runbook (Operational Readiness, §24).

19.10 Operational Notes

verify.result and measure.pcr.extend_before_exec (§7, I7) feed security dashboards distinct from the performance dashboards (§24); a Revoked spike across a fleet after a dbx update is expected and documented, not paged as an incident.

20. Phase 8 — A/B Slot Tracking & Failsafe Recovery

20.1 Objectives

Implement bl-ab (BootControlBlock ping-pong slot tracking, I5, I11) and bl-recovery (the failsafe menu entry, P14), completing the A/B update and rescue story.

20.2 Detailed Implementation Steps

bl-ab: read both BcbSlot locations; the slot with the higher generation and a valid crc32 is authoritative (I5). If trying_slot != 0xFF: successful_boots == 0xFF promotes it to active; otherwise increment successful_boots, and at ≥ 5 (the RTO bound from §4) revert active_slot to the other slot and clear trying_slot (P10, applying the Android BCB-ancestry design named in §2). Writes alternate between the two BcbSlot locations (ping-pong, P10) — never a single in-place overwrite, so a power-loss mid-write leaves one slot with the prior valid generation intact. rollback_counter (I11) is compared, never decremented, on every read; a slot whose image reports a lower counter than the BCB's stored value is refused. bl-recovery: a BootEntry with a distinct kernel/ initramfs path from the normal entries, booted with single-user- equivalent arguments, always present in the menu regardless of A/B state (P14).

20.3 Deliverable

bl-ab correctly promotes, increments, and rolls back across a simulated multi-boot sequence in bl-sim; bl-recovery's entry boots successfully even when both normal A/B slots are marked failed.

20.4 Acceptance Criteria

BCB read+decision completes in < 10 ms p50 (M7, §28); assert_i5/ assert_i11 PASS under bl-sim across a 1,000-boot simulated sequence including 50 injected power-loss-mid-write events (fixtures/ab/power-loss.corpus); rollback triggers at exactly successful_boots == 5, never earlier or later; a rollback-counter downgrade attempt is rejected in 100% of fixtures/ab/downgrade. corpus (200 cases).

20.5 Conformance Fixtures

conformance/buckets/ab/ping-pong-power-loss.fixture — power-loss injected mid-write to one BcbSlot; expects the other slot's prior generation to remain valid and readable (I5). conformance/buckets/ab/ rollback-threshold.fixture — five consecutive un-confirmed "trying" boots; expects reversion to the previous active slot on the fifth. conformance/buckets/ab/downgrade-rejected.fixture — an image reporting a lower rollback_counter than stored; expects boot refusal (I11).

20.6 Pitfalls

  • A single BCB write is non-atomic at the sector level (a power cut mid-sector-write corrupts that copy) — the ping-pong pair (P10) exists precisely so this always leaves one valid copy; a "just add a checksum, skip the second slot" shortcut reintroduces the exact bricking risk the design exists to prevent.
  • Forgetting to compare crc32 on read and trusting the higher-generation slot unconditionally means a corrupted-but- higher-generation slot (a torn write that happened to bump the counter before corrupting the payload) is selected as authoritative — both checks are required, generation is a tiebreaker, not a correctness proof.
  • Recovery entry paths sharing code with the normal-boot signature verifier (correct, P3 still applies) but not sharing the A/B slot logic — a recovery boot must not itself increment successful_boots or it corrupts the very rollback accounting it exists to bypass.

20.7 Performance Concerns

Two small (36-byte) sector reads plus a CRC32 computation is microsecond-scale; the < 10 ms M7 budget has wide margin, reserved for a future NVRAM-backed alternative under a different ADR (ADR-20's rejected alternative) without a redesign.

20.8 Edge Cases

Both BcbSlot copies simultaneously invalid (never-provisioned device, or corruption beyond ping-pong's tolerance) — falls back to the documented default (active_slot = A, per I5's stated fallback), never an undefined/uninitialized read.

20.9 Failure Analysis

A rollback event (I11 trigger) is not itself a boot failure from the operator's perspective — it is the recovery from one; telemetry distinguishes ab.rollback.counter increments (expected under normal field operation) from E-AB-BOTH-INVALID (an actual provisioning defect requiring a service action, Operational Readiness §24).

20.10 Operational Notes

bcb-tool (Repository Layout §10, tools/) lets an operator dump and force BCB state during field debugging (documented in the "A/B not rolling back" runbook, §24); every bcb-tool write goes through the same ping-pong path as the loader itself — no operator tool bypasses P10.

21. Phase 9 — Conformance, Differential Testing & Release Hardening

21.1 Objectives

Assemble the full conformance suite, the GRUB2 differential corpus (ADR-11), the 24-hour fuzz canary (ADR-12), and release-engineering gates (reproducible builds, signing) — the phase that proves the whole system, not just each crate in isolation.

21.2 Detailed Implementation Steps

Curate a kernel corpus (a matrix of Linux LTS versions × Multiboot2 test images × ELF64 test binaries) booted under both this loader and a pinned GRUB2 build (ADR-11); diff observable behavior (boot success, cmdline propagation, initramfs presence) — not implementation internals, since scope intentionally differs (ADR-11's rationale). Wire cargo-fuzz targets from every earlier phase's parser (Multiboot2 tags, bzImage header, PKCS#7/ASN.1, FAT32 LFN, ELF program headers) into one CI-gated 24-hour canary (ADR-12, M10 §28) plus a fast per-commit 5-minute subset. Wire reproducible-build verification (ADR-23): byte-identical output across two independent CI runners for the same commit.

21.3 Deliverable

conformance/buckets/differential-grub/ green across the full kernel corpus; the 24-hour fuzz canary running continuously in a scheduled CI job with zero unexplained panics; a signed, reproducible release artifact for both the UEFI and BIOS binaries.

21.4 Acceptance Criteria

Differential corpus run completes in < 10 minutes in CI (M-series adjacent); 0 behavioral divergences from GRUB2 on shared-scope features, or each divergence explicitly documented and accepted (ADR-11); 0 panics across the 24-hour fuzz canary (M10, §28); two independent CI runners produce byte-identical release artifacts (ADR-23).

21.5 Conformance Fixtures

conformance/buckets/differential-grub/corpus-manifest.yaml — the full kernel × format matrix with expected-behavior annotations. fuzz/regression/ — every crash the 24-hour canary has ever found, replayed on every subsequent commit (regression-proofing per Testing & Verification Strategy, §26). fixtures/release/reproducibility. fixture — two independent build outputs; expects identical SHA-256.

21.6 Pitfalls

  • GRUB2 has features this project intentionally never implements (scripting, network boot pre-Phase-9 scope) — a differential test that flags "GRUB2 supports X, we don't" as a failure conflates scope difference with behavioral divergence; the manifest (21.5) distinguishes the two explicitly.
  • A fuzz canary that reports "0 panics" because it stopped running hours ago (a silently-hung fuzzer, not a clean corpus) is a false green — the CI job asserts a minimum executions-per-second floor throughout the 24 hours, not just a final exit code.

21.7 Performance Concerns

The differential corpus's 10-minute CI budget is dominated by QEMU boot-cycle overhead (POST + firmware init per kernel under test, not loader logic) — parallelizing corpus entries across CI workers is the primary lever, not optimizing the loader further.

21.8 Edge Cases

A kernel in the corpus that boots successfully under GRUB2 only because GRUB2 silently tolerates a spec violation this loader correctly rejects (P3's stricter parsing) — documented as an intentional, accepted divergence (ADR-11's "Rejected Alternatives" column already anticipates spec-only conformance being the wrong bar in isolation).

21.9 Failure Analysis

A reproducibility mismatch between the two CI runners is treated as a release blocker, not a curiosity — root causes are almost always non-deterministic build metadata (timestamps, absolute paths); the fix belongs in Build & Release Engineering (§27), never suppressed by excluding the differing bytes from the comparison.

21.10 Operational Notes

The differential and fuzz results are published per-release in CHANGELOG.md (§10) alongside the harness evidence table (this document's closing comment); a release that has not passed both gates in the current CI run is never tagged, regardless of urgency.

Structured logging. Console + serial dual sink (ADR-22); every fatal halt prints a named diagnostic code (E-EBS-RETRY, E-AB-BOTH-INVALID, E-MB2-TAGOVERRUN, E-BZ-PROTOVER) cross-referenced in docs/runbooks/.

Dashboards & alerting philosophy. Fleet-level rate dashboards for each counter above; alert if boot.memmap.key_mismatch rate > 1% of boots (Phase 3, §15.10) or ab.rollback.counter increments exceed 0.1% of boots (the RTO budget, §4). Cosmetic classes (FM-5) are dashboarded but never paged.

SLOs. ≤ 0.1% of boots require manual recovery (§4); p99 boot time ≤ 900 ms; 0 unexplained fuzz-canary panics per release (M10).

Incident response. A E-EBS-RETRY or E-AB-BOTH-INVALID spike across a fleet triggers the corresponding runbook (below); a Revoked signature spike after a dbx update is expected, not an incident.

Named runbooks (full text in docs/runbooks/, summarized §36 of the original draft, consolidated here): "stuck at boot menu" (FM-1), "signature verification fails" (FM-4), "A/B not rolling back" (FM-3).

Backup/restore. The loader itself holds no user data to back up; its own binary + BCB are restorable from the signed release artifact (Build & Release Engineering, §27) and a factory-default BCB.

Deployment topology. One loader binary per firmware type (UEFI/ BIOS) written to the ESP/MBR region at OS-image build time; updates ship as a new signed loader binary alongside a kernel A/B update.

Canary/rolling-upgrade/rollback/migration strategy. New loader binaries roll out via the same A/B slot mechanism as kernels (Phase 8); a loader-level rollback uses the identical BCB rollback-counter machinery (I11) — there is no separate loader-update path to maintain.

25. Compatibility & Versioning

Wire compatibility. HandoffState (§11) is the internal contract; its per-protocol serializations (Multiboot2 tag stream, Linux boot_params, ELF-adjacent minimal contract) each follow their external spec's own versioning, not this project's — a spec revision (e.g. a new bzImage header.version) is handled by extending the version-gate table (Phase 6, §18.2), never by breaking older versions.

Storage compatibility. The BootControlBlock layout (§11) is append-only from ADR-06's locked 32-byte layout; a future field addition uses the 16-byte padding region rather than reordering existing fields, preserving field offsets for any already-deployed BCB.

Filesystem read compatibility. FAT32 read support explicitly excludes exFAT-adjacent extensions (Phase 4, §16.10); ISO9660 excludes Joliet/Rock Ridge extensions in Phase-0..9 scope (documented, not silently misread) — an explicit compatibility matrix lives in docs/runbooks/.

API stability. The Firmware trait (§11) is the one crate-boundary API every backend must implement identically; adding a method is a minor version bump requiring every existing backend (bl-firmware- bios, bl-firmware-uefi) to implement it before the workspace builds.

Deprecation policy. A deprecated kernel-format loader (none currently) would ship one release cycle emitting a warning telemetry event before removal, per SemVer minor→major transition rules.

SemVer policy. Workspace-wide single version number (ADR-24's single-workspace rationale); breaking changes to HandoffState, BCB, or the Firmware trait are major-version bumps; new kernel-format support is a minor bump; bug fixes are patch bumps.

Rolling-upgrade guarantees. A loader update and a kernel update can land in the same A/B cycle or independently; the BCB's rollback counter (I11) is the sole cross-component compatibility gate — an old loader must never be asked to boot a kernel whose format it predates without an explicit compatibility check at signing time (documented operator responsibility, since the loader cannot know about kernel formats introduced after its own build).

26. Testing & Verification Strategy

Unit tests — per-crate, covering MemoryMap normalization (§13), struct layout invariants (§11), and parser boundary conditions in isolation (every crate in §10).

Integration tests — the conformance buckets (§10, conformance/ buckets/), each phase's N.5 fixtures, run under QEMU+OVMF/SeaBIOS.

Property-based testing — MemoryMap normalization is checked against the property "output ranges are sorted, non-overlapping, and cover the same total address space as the input" across randomly generated E820/UEFI descriptor tables.

Differential testing — against GRUB2 (ADR-11, Phase 9 §21) on the curated kernel corpus, the highest-value test given GRUB2's production maturity.

Fuzzing — cargo-fuzz targets on every untrusted-input parser (Multiboot2 tags, bzImage header, PKCS#7/ASN.1, FAT32 LFN, ELF program headers, config file), continuous 24-hour canary (ADR-12, M10).

Chaos / fault injection — simulated power-loss mid-BCB-write (Phase 8, §20.5), simulated ExitBootServices memory churn (Phase 3, §15.5), simulated TPM communication timeout (Phase 7).

Deterministic replay — bl-sim (§7) replays a fixed input sequence and asserts all fourteen System Invariants on every commit; any CI failure reproduces byte-for-byte locally.

Soak testing — the 24-hour fuzz canary doubles as a soak test for memory-safety regressions under sustained adversarial input.

Conformance gating — every phase's fixtures (N.5) plus the differential corpus (§21) must be green before merge; performance regression gating ties each M-series target (§28) to a CI failure, not a warning.

Every invariant in §7 has at least one exercising test named above; every phase's N.5 fixtures are the concrete instances of this strategy.

27. Build & Release Engineering

Reproducible builds. Pinned rustc toolchain (ADR-23), no build.rs codegen variance, no embedded build timestamps; two independent CI runners must produce byte-identical artifacts (FM-10, §23) before a release tag is cut.

Artifact signing. Release binaries (UEFI PE32+ and BIOS MBR/ stage-1.5) are signed with the project's release key via the same PKCS#7 format the loader itself verifies (Phase 7, §19) — dogfooding the verifier's exact code path.

SBOM. Generated per release from the Cargo dependency graph; audited against RUSTSEC advisories as part of the release gate.

Release channels. stable (differential + 24h-canary green), nightly (per-commit conformance green, canary optional) — mirroring the two-tier cadence common to GRUB2/systemd-boot release practice.

CI/CD topology. GitHub Actions matrix: build → unit → conformance (OVMF+SeaBIOS) → differential (§21) → fuzz-fast-subset → (nightly) 24-hour canary → reproducibility check → sign → publish.

Version stamping. SemVer (§25) embedded in the binary's PE/COFF version resource and a parallel BUILD_PLAN.md-tracked changelog entry.

Provenance/attestation. Release artifacts carry a SLSA-style provenance statement: source commit, builder identity, build parameters — verifiable independently of the signing key.

Dependency auditing. cargo audit gated in CI; any dependency with a no_std-incompatible transitive requirement fails the build (P11's small-TCB principle enforced mechanically, not just by review).

28. Performance Engineering

Benchmarking/profiling methodology. Criterion-based microbenchmarks in bl-bench (§10) for parser/verify/measure hot paths; end-to-end timing via the per-stage trace (Operational Readiness, §24) run under QEMU on pinned CI hardware for cross-run comparability.

Allocation analysis. no_std, no heap in the critical path (P11) — allocation analysis reduces to fixed-capacity buffer sizing review (MAX_MEM_RANGES, MAX_PHDRS, etc., §11), checked at compile time via const assertions on struct sizes.

Lock/cache analysis. Single-threaded, no locks exist pre-handoff (the mode/handoff shim, §3, is inherently serial); cache-locality concerns are limited to sequential segment copies (Phase 5, §17.7) and cluster-chain walks (Phase 4, §16.7), both already read-ahead-optimized.

Syscall/firmware-call overhead. UEFI Boot Services calls dominate overhead versus BIOS INT-services (Phase 3 vs Phase 2); the ≤ 16 concurrent-handle budget (§4) bounds LocateProtocol call count.

Tail-latency analysis. p99 boot time (900 ms, §4) is driven by cold-cache disk reads (Phase 4) and ExitBootServices retries (Phase 3); both are the named bottlenecks in Scalability Analysis (§29).

29. Scalability Analysis

What stays constant. Per-boot cost is independent of fleet size — this is a single-machine, single-boot-attempt system with no shared coordination state across devices (unlike a distributed system, the "scaling" axis here is image size and firmware call count, not concurrent load).

What grows, and the Big-O. Kernel/initramfs size (§4 ceilings: 64 MiB / 128 MiB) scales disk-read and verify time roughly linearly (O(n) in image bytes for both hashing and segment copy, §28); memory- map entry count scales MemoryMap normalization at O(n log n) (§13.7) but n is bounded ≤ 128 by hardware reality, not by this design.

Named bottlenecks in order. 1) disk I/O (Phase 4, dominant at 150–200 ms of the 500 ms budget); 2) signature verify + measurement (Phase 7, ~65 ms, CPU-bound); 3) firmware call overhead (GetMemoryMap/ExitBootServices, Phase 3, ≤ 10 ms but latency- sensitive to firmware quirks); 4) segment copy (Phase 5/6, memory- bandwidth-bound, rarely the limiter at current size ceilings).

Horizontal/vertical scaling. Not applicable in the traditional sense (one loader instance per boot, one boot per machine); the closest analogue is fleet-wide rollout scaling, which is the A/B mechanism's job (Phase 8) — each device scales its own update independently, with no central coordinator in the loader's scope.

Sharding/partitioning. N/A — no partitioned data structure exists; the closest concept is the two BCB slots (A/B), which are a ping-pong pair, not a shard.

Coordination overhead. Zero — the loader never coordinates with another running instance; the entire design is single-actor, single-attempt per boot (P5's "fail safe" principle depends on this).

The practical ceiling and the levers beyond it. The practical ceiling is disk throughput at a given kernel/initramfs size: at the 64 MiB / 128 MiB ceilings (§4) and typical NVMe throughput (~2 GB/s), disk read time is ~96 ms — well under the 150–200 ms modeled (which assumes slower SATA/eMMC-class storage as the design baseline). The lever beyond the ceiling is not loader redesign but raising the image- size ceilings in §4, which would need re-deriving the entire p50/p99 budget chain (Back-of-Envelope Capacity Model, §32) before being accepted as a new constraint.

30. Mental Models & First Principles

  1. MM1 — "The memory map is a lease, not a fact." The firmware's memory map is valid only until the next allocation; treating it as a permanent fact (instead of re-checked immediately before use) is the exact bug class behind ExitBootServices failures. Predicts: any code path that calls an allocating function between "get map" and "use map" will eventually break. Bug class without it: silent memory-ownership desync between loader and kernel. Applied in §15 (Phase 3), I1.
  2. MM2 — "A mode transition is a one-way door." Real→protected→long mode is not reversible mid-sequence; there is no partial state that is both valid and useful. Predicts: any attempt to "check and retry" mid-transition is meaningless — the only correct unit of retry is the whole sequence, from a known-good starting state. Bug class without it: triple-faults from partially-applied CPU state changes. Applied in §14 (Phase 2), P6, I3/I4.
  3. MM3 — "Trust is measured before it is spent." A component must be measured (PCR-extended) before its bytes influence anything, because measurement after execution cannot un-happen the execution. Predicts: any "verify, then optionally measure" ordering has a TOCTOU window. Bug class without it: an attacker wins the race between measurement and use. Applied in §19 (Phase 7), P9, I7, MM3 draws directly on Parno/McCune/Perrig's bootstrapping-trust chain model.
  4. MM4 — "A/B is consensus with two replicas and no network." The BCB ping-pong is a miniature Paxos-adjacent problem: exactly one value must be authoritative even under a crash at any write boundary. Predicts: any single-copy "just write it" design has a crash window with no valid state. Bug class without it: bricked devices on power-loss. Applied in §20 (Phase 8), P10, I5.
  5. MM5 — "The parser is the trust boundary, not the binary." A correctly-signed binary can still contain a parser that is unsafe to run before verification completes — the boundary is bytes not yet verified, not files not yet loaded. Predicts: any lazy/streaming parse-then-verify design reintroduces pre-auth code execution. Bug class without it: BootHole/BootStomp-style pre-auth RCE. Applied in §22 (Threat Model, T1/T2), P3.
  6. MM6 — "Firmware is a foreign, adversarial-quality API, not a trusted subroutine." Firmware bugs (stale map keys, GOP quirks, inconsistent ExitBootServices timing) are common enough to design around defensively, even absent malice. Predicts: any code assuming firmware behaves per spec on every implementation will eventually hit a real-hardware counterexample. Bug class without it: field failures that never reproduce in the reference QEMU/OVMF environment. Applied in §15 (Phase 3), §22 (T7), the Bulygin et al. 2015 literature.
  7. MM7 — "Every retry loop is a bet against an unknown clock." A retry without a bound is a bet that some external condition resolves in finite time — a bet the loader cannot verify. Predicts: unbounded retries eventually manifest as unexplained field hangs. Bug class without it: a device that "just sits there" with no diagnostic. Applied in P13, I13, §23 (FM-2).
  8. MM8 — "The kernel format is an encoding, not an identity." ELF64, Multiboot2, and bzImage are three encodings of the same underlying handoff intent (entry point + memory + cmdline); treating them as fundamentally different problems duplicates logic that should be shared. Predicts: a design with three independent handoff implementations will drift and diverge over time. Bug class without it: a field only populated correctly for one format silently missing in another. Applied in §17/§18 (Phase 5/6), P12.

GRUB2 chose maximal feature breadth (scripting, filesystem count, theming) over minimal TCB — it wins wherever an operator needs runtime- configurable boot logic across heterogeneous distros, at the cost of exactly the parser-attack-surface class BootHole (CVE-2020-10713) exploited. Limine chose a from-scratch multi-protocol design over Multiboot2-only compatibility — it wins for hobbyist/research kernels wanting a modern handoff contract without GRUB2's legacy weight, at the cost of a smaller reference-kernel ecosystem. systemd-boot chose radical scope minimalism (UEFI-only, no scripting) — it wins for distros that have already standardized on UEFI and want the smallest possible boot manager, at the cost of zero legacy-BIOS or embedded-board support. Das U-Boot chose a scriptable shell and broad peripheral driver support over TCB minimalism — it wins in embedded/SoC bring-up where the same binary must probe unknown board variants at runtime, at the cost of a large, harder-to-audit attack surface for a threat model (this project's) that assumes signed, known-shape images only.

32. Back-of-Envelope Capacity Model

Chained from §4 (System Constraints):

  1. Kernel disk-read time = image size ÷ storage throughput = 64 MiB ÷ 2 GB/s (NVMe) ≈ 32 ms (best case); ÷ 300 MB/s (SATA/ eMMC baseline assumed by §4's 150–200 ms budget) ≈ 213 ms (worst case within budget).
  2. Initramfs disk-read time = 128 MiB ÷ 300 MB/s ≈ 427 ms worst case — exceeds the naive 150–200 ms line item in §28's timing breakdown, which is why the breakdown states "kernel + initramfs" combined and assumes typical initramfs staging overlaps kernel verify (§19); this derivation shows the 128 MiB initramfs ceiling (§4) requires overlap/pipelining, not sequential reads, to hold M1.
  3. SHA-256 hash time = image size ÷ hash throughput ≈ 4 MiB ÷ (~400 MB/s software SHA-256) ≈ 10 ms, matching §4's stated verify-time component.
  4. RSA-2048 verify time ≈ 5 ms, a fixed per-signature cost independent of image size (public-exponent verify is cheap versus sign) — matches §4/§28's stated figure.
  5. Total verify+measure time = hash (10 ms) + RSA verify (5 ms) + ASN.1 parse (~5 ms) + PCR extend (≤ 15 ms, M11) ≈ 35 ms best case, 65 ms accounting for TPM SPI-bus latency — matches §28's 65 ms breakdown line.
  6. Peak resident memory = kernel (64 MiB) + initramfs staging window (16 MiB, not the full 128 MiB — streamed, not fully buffered) + loader working set (16 MiB: page tables, BCB, ASN.1 scratch) = 96 MiB, matching §4's stated ceiling exactly.
  7. BCB storage overhead = 2 slots × (32 B BCB + 4 B generation header) = 72 bytes, well under one 512-byte sector (§4).
  8. Framebuffer memory = width × height × bytes-per-pixel = 1920 × 1080 × 4 ≈ 8.3 MiB per buffer; double-buffered (ADR-07) ≈ 16.6 MiB total — within the 96 MiB peak-memory ceiling with margin for the loader working set.
  9. Framebuffer fill time = buffer size ÷ memory bandwidth ≈ 8.3 MiB ÷ 30 GB/s ≈ 0.28 ms — confirms M8's 60 FPS (16.7 ms/frame budget) has roughly 60× headroom for a full-buffer redraw.
  10. UEFI concurrent handle budget = 6 required protocols (Disk I/O, Block I/O, GOP, Simple Text In/Out, TPM2, Loaded Image) × up to 2–3 instances each in a multi-disk system ≈ 12–18, justifying §4's ≤ 16 stated ceiling as a tight-but-sufficient bound, not an arbitrary round number.
  11. Total boot time reassembly = firmware load (125 ms midpoint) + loader init (50 ms) + disk read (32–213 ms) + verify/measure (35–65 ms) + handoff (10 ms) + ExitBootServices/jump (≤10 ms) ≈ 262–473 ms — consistent with M1's 500 ms p50 target and confirming the modeled p99 (900 ms, M12) has roughly 2× margin over the worst-case sum above for firmware-side variance.
  12. Fuzz canary throughput needed for meaningful 24h coverage = assuming a minimum useful executions-per-second floor of 500/s (per ADR-12's continuous-canary rationale) × 86,400 s ≈ 43.2M fuzz executions per canary run — the concrete number behind §21.6's "minimum executions-per-second floor" CI assertion.

34. Alternative Architectures (Roads Not Taken)

Alternative A — Scriptable configuration (GRUB2/U-Boot model).

┌──────────────┐     ┌────────────────────┐
│ Firmware     │────▶│ Turing-complete    │──▶ kernel
└──────────────┘     │ config shell/VM    │
                      └────────────────────┘

Regime where it wins: heterogeneous fleets needing runtime-conditional boot logic without rebuilding the loader (distro-agnostic GRUB2 deployments). Real system: GRUB2's grub.cfg scripting engine, U-Boot's command shell. Rejected here because a Turing-complete pre-auth parser is the exact attack surface BootHole exploited (P3, §22 T1) — this design's static declarative config (ADR of the config parser) trades runtime flexibility for a bounded, fuzzable, auditable parser.

Alternative B — Dynamic Root of Trust (DRTM / Intel TXT / AMD SKINIT).

┌──────────┐  SENTER/SKINIT  ┌───────────────────┐
│ Untrusted│───────────────▶ │ Hardware-enforced │──▶ measured kernel
│ pre-boot │  (late launch)  │ minimal CPU state │
└──────────┘                  └───────────────────┘

Regime where it wins: a threat model that must not trust any pre-boot firmware, including this loader itself (Flicker, McCune et al. 2008; OSLO, Kauer 2007). Real system: Flicker's TXT-based late launch. Rejected here (ADR-16) because it requires specific CPU/chipset support absent on much fielded hardware, and this project's SRTM chain already covers the stated threat model (tampering detectable via PCR divergence, T10) at far broader hardware compatibility.

Alternative C — Firmware-embedded loader (coreboot payload model).

┌───────────────────────────────────┐
│ coreboot (romstage+ramstage)      │
│  └── payload = this loader, baked │
│      into the firmware image      │
└───────────────────────────────────┘

Regime where it wins: fully-owned hardware (embedded appliances, cloud server fleets) where the vendor controls both firmware and payload and wants a single flashable image. Real system: coreboot with a custom payload. Rejected here because the primary deployment model (§1) targets commodity UEFI/BIOS hardware the project does not control the firmware of — a payload-embedded design would require a coreboot port per board, which the ESP/MBR-installable model (ADR-02) avoids entirely.

Alternative D — Network-first boot (PXE/HTTP boot as the primary path).

┌──────────┐   DHCP/PXE   ┌──────────────┐   HTTP/TFTP   ┌────────┐
│ Firmware │─────────────▶│ Network stack│──────────────▶│ Kernel │
└──────────┘              └──────────────┘               └────────┘

Regime where it wins: diskless data-center fleets provisioning kernels centrally (common in large-scale cloud/HPC deployments). Real system: iPXE, UEFI HTTP Boot. Rejected here (deferred, §35) because the stated scope (§1) is a locally-installed, disk-resident loader with A/B update semantics that presume local storage; network boot is a materially different trust and availability model (a network outage becomes a boot-blocking failure) left to a future, explicitly separate design.
