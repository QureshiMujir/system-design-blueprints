⬜ Phase 0 — Repository & Correctness Kernel Bootstrap §12

Objectives

Stand up the reproducible-build repository skeleton (§10) plus the correctness kernel: trace propagation, schema registry, and CI enforcement, before any domain service exists.

Deliverable

A reproducible repository that builds every Phase-0 module (§1) under CI enforcement, with end-to-end trace propagation verified on a synthetic request.

Acceptance
  • CI green on a clean checkout, container digest reproducible bit-for-bit across two builds.
  • SBOM generated per build and attached to the release artifact.
  • Trace propagation verified against fixture fixtures/otel/basic-trace.json (a full span tree with ≥4 hops).
  • API p99 latency of the empty gateway health route < 900 ms under 1,000 rps synthetic load (M3).
Fixtures
  • fixtures/build/reproducible-build.lock
  • fixtures/otel/basic-trace.json
Pitfalls
  • Non-hermetic builds (network access during cargo build) silently break reproducibility.
  • Dependency drift between Cargo.lock and CI cache leads to false-green builds.
  • Inconsistent lint rules across crates hide P11 violations.

⬜ Phase 1 — Identity & Tenant Isolation §13

Objectives

Implement auth-service: organizations, RBAC, OIDC federation, API tokens, scoped permissions, and row-level tenant isolation — the enforcement point for P4 and I5.

Deliverable

A multi-tenant identity subsystem where cross-tenant access is structurally blocked, not merely checked in application code (P4).

Acceptance
  • Cross-tenant access blocked in 100% of a 500-case adversarial fixture suite (T3).
  • RBAC integration tests pass, including inheritance-cycle rejection.
  • Token rotation validated: an old token is rejected within 5s of rotation.
  • Metadata-DB failover completes in < 60 s (M9) without dropping in-flight auth checks.
Fixtures
  • fixtures/auth/cross_tenant_denied.json
  • fixtures/auth/role_cycle_rejected.json
Pitfalls
  • Permission-cache staleness after a revoke (must invalidate synchronously, not on TTL alone).
  • JWT clock skew between api-gateway and auth-service nodes.
  • Role-escalation bugs from an unbounded inheritance graph (T7).

⬜ Phase 2 — Dataset & Asset Registry §14

Objectives

Implement dataset-service: scalable dataset metadata, multipart object ingestion, dedup, content-address validation, and cold-tier lifecycle transitions, at the 5-billion-asset scale target (§4).

Deliverable

A petabyte-capable asset-ingestion pipeline with deduplication and a versioned dataset log.

Acceptance
  • 10,000,000-asset ingestion test completes with zero hash-validation failures (I9).
  • Duplicate suppression rate ≥ 99.9% on a fixture set with known duplicates.
  • Storage amplification stays under 2.7x including replicas and indexes (§4).
Fixtures
  • fixtures/dataset/dedup_10m.json
  • fixtures/dataset/version_log_replay.json
Pitfalls
  • Multipart-upload completion races (MinIO reference lesson, §5) without explicit fencing.
  • Metadata hot partitions from sequential-ID assets (mitigated by UUIDv7, ADR-21).

⬜ Phase 3 — Task Orchestration Engine §15

Objectives

Implement task-service: fencing-token lease management, fair scheduling, priority/SLA routing, and worker-heartbeat tracking, sustaining 50,000 concurrent annotators (§4).

Deliverable

A distributed orchestrator sustaining the concurrency target with deterministic replay of lease-grant history.

Acceptance
  • Lease-conflict rate < 0.001% of claims under a 50,000-worker synthetic load (M10).
  • Queue fairness validated: no org starved for > 3x its fair share over a 1-hour window.
  • Lease-grant replay from the event log reproduces identical grant sequences (P1, P12).
Fixtures
  • fixtures/task/lease_expiry.json
  • fixtures/task/fairness_1h.json
Pitfalls
  • Lease orphaning when a worker heartbeat is delayed by GC/scheduler jitter on the client side.
  • Scheduler starvation from an unbounded high-priority queue (P2 violation).
  • Clock drift between task-service nodes affecting TTL expiry judgment.

⬜ Phase 4 — Annotation Runtime & Realtime Collaboration §16

Objectives

Implement annotation-service and realtime-gateway: annotation CRUD across all six schema types (§8), autosave, revision history, and collaborative editing at 120,000 concurrent websocket sessions (§4).

Deliverable

A production annotation runtime supporting bbox/polygon/segmentation/keypoint/NER/ transcription with realtime collaborative presence.

Acceptance
  • Autosave recovery validated: a killed client session resumes with zero payload loss against fixtures/annotation/autosave_recovery.json.
  • Revision replay deterministic (P1) across 10,000 fuzz-generated revision chains.
  • Annotation save p95 latency < 120 ms (M1) at 50,000 concurrent annotators.
  • Websocket fanout p95 (event to client) < 150 ms (M11) at 120,000 sessions.
Fixtures
  • fixtures/annotation/revision_replay.json
  • fixtures/annotation/autosave_recovery.json
  • fixtures/annotation/conflict_merge.json
Pitfalls
  • Websocket fanout pressure hot-spotting one popular dataset "room" onto one pod (FM-7).
  • Serialization overhead from an oversized Segmentation mask sent inline instead of by reference (§11 stores mask_ref, not inline bytes, for exactly this reason).

⬜ Phase 5 — Review, QA & Consensus §17

Objectives

Implement review-service: golden-set validation, consensus aggregation, inter-annotator agreement metrics, and reviewer escalation — the enforcement point for I8 and I11.

Deliverable

A reproducible consensus and QA subsystem whose aggregated label and agreement score are deterministic for a fixed vote set and algorithm version (I11).

Acceptance
  • Agreement metrics reproducible: recomputing kappa/alpha from stored raw votes matches the persisted agreement_score to 1e-6 (I11).
  • Escalation replay deterministic against fixtures/review/escalation_replay.json.
  • Review-transition p95 latency < 300 ms (M2).
  • EM convergence validated on a fixture with known per-annotator error rates within 2% of ground truth.
Fixtures
  • fixtures/review/consensus_em_convergence.json
  • fixtures/review/kappa_alpha_reference.json
  • fixtures/review/escalation_replay.json
Pitfalls
  • Treating raw percent agreement as a quality signal on a skewed label distribution — inflated by chance agreement (ADR-18, MM6).
  • Feeding an adversarial or malfunctioning labeling function's votes into consensus unsandboxed (T11).

⬜ Phase 6 — Workflow Engine (DAG Compiler) §18

Objectives

Implement workflow-service: a declarative-DAG-to-FSM compiler enforcing deterministic replay (P1) of annotation pipelines.

Deliverable

A declarative workflow-execution engine whose replay is bit-for-bit deterministic given the same event history.

Acceptance
  • Invalid transitions rejected 100% of the time against fixtures/workflow/ transition_fixtures.json (I7).
  • Replay consistency validated: 10,000 randomly reordered-then-corrected event streams produce identical final states (P1).
  • Workflow-transition rejection rate exposed as workflow_transition_rejections (I7).
Fixtures
  • fixtures/workflow/transition_fixtures.json
  • fixtures/workflow/replay_determinism.json
Pitfalls
  • A compiled FSM with an unreachable terminal state (caught by dag_validate.rs).
  • A timeout implemented as a sleep rather than a deadline event — breaks P1 replay.

⬜ Phase 7 — Search, Analytics & ML-Assisted Labeling §19

Objectives

Implement search-service (secondary indexing, operational analytics) and ml-assist-service (prediction ingestion, active-learning sampling) as an eventually-consistent projection layer over the metadata-of-record (§8).

Deliverable

An eventually-consistent, rebuildable search/analytics projection plus an active-learning loop with reproducible sample-priority scoring.

Acceptance
  • Search-indexing lag < 10 s at steady-state ingestion rate (M5, §4).
  • Query p95 < 250 ms (M6) against a 100M-document index fixture.
  • Prediction latency p95 < 500 ms (M7).
  • Human-correction lineage preserved: 100% of overridden pre-labels retain a parent_revision link to the model prediction in fixtures/ml/override_lineage.json.
Fixtures
  • fixtures/search/indexing_lag.json
  • fixtures/ml/active_learning_replay.json
  • fixtures/ml/override_lineage.json
Pitfalls
  • Treating the search index as a source of truth instead of a rebuildable projection (violates §8 consistency semantics).
  • An unlogged active-learning score, making "why was this asset prioritized" unanswerable (MM8, I14).

⬜ Phase 8 — Audit, Compliance & Immutable Ledger §20

Objectives

Implement audit-service: an append-only, cryptographically hash-chained log with retention enforcement and legal-hold support, enforcing I2 and P3 for every mutating write in the system.

Deliverable

A tamper-evident, legally defensible audit trail covering every mutation in the system.

Acceptance
  • Tamper checks validated: any single mutated byte in a stored record is detected by chain-verification against fixtures/audit/tamper_detect.json.
  • Replay verification passes: reconstructing the last 24 hours of state from the audit log matches the live metadata DB.
  • Audit write commit latency p95 < 50 ms (M12).
Fixtures
  • fixtures/audit/tamper_detect.json
  • fixtures/audit/chain_replay_24h.json
Pitfalls
  • A concurrent writer bypassing the single-writer append path (FM-12) breaks the hash chain.
  • Retention-sweep jobs racing an active legal hold (must check hold status before purge).

⬜ Phase 9 — Observability, Reliability & Enterprise Hardening §21

Objectives

Deliver production-grade telemetry, resilience engineering, multi-region failover, and air-gapped enterprise-edition support — the final gate before the 9–14 month enterprise release (§1).

Deliverable

A multi-region-capable, chaos-tested, air-gapped-deployable production system meeting every §4 SLO under injected failure.

Acceptance
  • Alert routing validated: a synthetic Sev-1 injected fault pages the correct on-call rotation within 2 minutes.
  • Failure-injection tests pass across all 12 FM-# classes (§23) with the documented auto/manual recovery path exercised.
  • Regional failover completes within the 30-minute RTO (M8) with zero data loss verified against the audit chain (I2).
  • Rolling upgrade completes with zero downtime measured at api-gateway (P8).
Fixtures
  • fixtures/chaos/kafka_partition_kill.json
  • fixtures/failover/regional_rto.json
Pitfalls
  • Alert fatigue from paging on ticket-worthy degradation trends instead of user-visible impact (§24 alerting philosophy).
  • A chaos experiment run against production without a scoped blast radius.
