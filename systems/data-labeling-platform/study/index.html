Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does the search index never become the source of truth, and what breaks if it did? (§8, §29)
  2. What prevents a worker whose lease expired mid-write from corrupting an AnnotationRevision? (§11, §15, I12)
  3. Why is Dawid-Skene EM preferred over majority vote, and under what annotator-count regime does that preference invert? (§17, ADR-16)
  4. What is the difference between "eventually consistent" and "soft state," and why does presence get the weaker guarantee? (§8, I13)
  5. Why can't the metadata DB simply be sharded by task_id instead of organization_id? (§7, §29)
  6. What forces recovery to be metadata-first with lazy asset rehydration rather than a full data restore? (§21, §32)
  7. Why does audit-log immutability require a database-role-level restriction rather than an application-level check? (§7, I2)
  8. What happens to an in-flight SubmitRevision when its fencing token is stale, and why is silently accepting it worse than rejecting it? (§8, I12)
  9. Why does Krippendorff's alpha exist when Cohen's kappa already corrects for chance agreement? (§17, ADR-18)
  10. What is the actual failure mode if a labeling function (ADR-17) is compromised, and how far does the blast radius extend? (§17, §22, T11)
  11. Why is the workflow engine an internal FSM compiler instead of adopting Temporal outright, given Temporal already solves durable execution? (§5, ADR-14)
  12. What specific property of an event makes it safe to replay twice, and where is that property enforced? (§11, P9)
  13. Why does export require snapshot-transaction fencing instead of a simple point-in-time read? (§8, I4)
  14. What is the actual mechanism by which replay_divergence_total going nonzero pages an engineer, and why is that different from an ordinary error-rate alert? (§18, §24)
  15. Why is the search-service isolated onto its own analytics cluster rather than colocated with the annotation hot path? (§24, P10)
  16. What happens when a schema-registry compatibility check rejects a producer's deploy, and who is responsible for the fix? (§25, FM-10)
  17. Why does the active-learning loop fall back to random sampling instead of blocking task creation when the scorer is down? (§19, FM-11)
  18. What distinguishes a Sev-0 incident from a Sev-1 in this system, concretely, using the invariant table? (§7, I5)

30. Mental Models & First Principles

MM1 — Every distributed lease is a bet against a clock you don't control. Predicts that lease systems need fencing tokens, not just TTLs. Bug class without it: split-brain writes after a paused worker resumes past its TTL. Resolving §15 / I12 / I3.

MM2 — Consensus is a model of annotators, not a vote count. Predicts Dawid-Skene beats majority vote once annotators have skewed skill/error rates. Bug class without it: systematically wrong labels from a confidently-wrong majority. Resolving §17 / ADR-16.

MM3 — An event log is the database; the tables are just a cache of it. Predicts that any projection (search index, analytics view) must be fully rebuildable from the log. Bug class without it: an unrebuildable search index after drift, with no recovery path. Resolving §8 / §29 / FM-5.

MM4 — Backpressure delayed is backpressure denied. Predicts that admission control placed downstream of the true bottleneck always arrives too late to prevent damage. Bug class without it: OOM at annotation-service instead of a clean 429 at api-gateway. Resolving §4 / P2.

MM5 — Tenant isolation is a database property, not an application habit. Predicts that app-layer-only isolation eventually leaks under one missed WHERE clause. Bug class without it: a cross-tenant read via a forgotten filter. Resolving §7 / I5 / T3.

MM6 — Agreement metrics must correct for chance before they mean anything. Predicts raw percent agreement overstates quality on a skewed label distribution. Bug class without it: shipping a "95% agreement" golden set that is actually near chance. Resolving §17 / ADR-18.

MM7 — A schema is a contract with your own future deploys. Predicts breaking changes surface as consumer crashes weeks later, not at commit time. Bug class without it: a silent incompatible field removal breaking a downstream export job. Resolving §11 / I10 / P8.

MM8 — Active learning only helps if the score is reproducible. Predicts that an unlogged model score makes audits and regressions indistinguishable. Bug class without it: "why was this asset prioritized" has no answer six months later. Resolving §19 / I14.

Required reading (§5)

Books

  • Designing Data-Intensive Applications (Kleppmann) — ch. 5–11 (replication, partitioning, transactions, consistency, batch/stream processing) — extract: the consistency-model vocabulary used throughout §8. Applied in §8 / Phase 4 (§16).
  • Database Internals (Petrov) — storage-engine and indexing chapters — extract: B-tree vs. LSM tradeoffs informing PostgreSQL vs. search-index split. Applied in §9 / Phase 2 (§14).
  • Release It! (Nygard) — stability-pattern chapters (circuit breaker, bulkhead, timeout) — extract: bulkhead isolation per tenant. Applied in §6 (P4) / Phase 1 (§13).
  • Kubernetes in Action (Lukša) — operators and StatefulSet orchestration chapters — extract: operator pattern for Kafka/Postgres lifecycle. Applied in §10 / Phase 0 (§12).
  • Streaming Systems (Akidau, Chernyak, Lax) — event-time/watermark chapters — extract: watermark-based lag detection used for search-index staleness. Applied in Phase 7 (§19).
  • Site Reliability Engineering (Google) — SLO and error-budget chapters — extract: the page-vs-ticket alerting philosophy. Applied in §24 / Phase 9 (§21).
  • Rust for Rustaceans (Gjengset) — ownership/async chapters — extract: bounded-channel backpressure idioms. Applied in §6 (P2) / Phase 0 (§12).
  • Content Analysis: An Introduction to Its Methodology (Krippendorff) — reliability-metric chapters — extract: Krippendorff's alpha for mixed measurement levels. Applied in Phase 5 (§17).

Papers

  • DeCandia et al. — "Dynamo: Amazon's Highly Available Key-value Store" (SOSP 2007) — contribution: quorum replication and vector-clock conflict resolution. Applied in §7 (I1) / Phase 4 (§16) annotation-revision conflict resolution.
  • Chang et al. — "Bigtable: A Distributed Storage System for Structured Data" (OSDI 2006) — contribution: sparse column-family storage at scale. Applied in Phase 7 (§19) search projection design.
  • Ghemawat, Gobioff, Leung — "The Google File System" (SOSP 2003) — contribution: chunked, replicated large-object storage. Applied in §9 (ADR-06) / Phase 2 (§14).
  • Corbett et al. — "Spanner: Google's Globally Distributed Database" (OSDI 2012) — contribution: TrueTime-bounded external consistency. Applied in §29 / Phase 9 (§21) multi-region discussion.
  • Armbrust et al. — "Delta Lake: High-Performance ACID Table Storage over Cloud Object Stores" (VLDB 2020) — contribution: append-only transaction-log protocol for versioned datasets. Applied in Phase 2 (§14) dataset versioning.
  • Ongaro, Ousterhout — "In Search of an Understandable Consensus Algorithm (Raft)" (USENIX ATC 2014) — contribution: leader election and log replication model. Applied in Phase 1 (§13): replica promotion sequencing for metadata-DB failover (M9).
  • Ratner, Bach, Ehrenberg, Fries, Wu, Ré — "Snorkel: Rapid Training Data Creation with Weak Supervision" (VLDB 2017) — contribution: labeling functions + generative model for combining noisy label sources. Applied in §9 (ADR-17) / Phase 5 (§17).
  • Dawid, Skene — "Maximum Likelihood Estimation of Observer Error-Rates Using the EM Algorithm" (Journal of the Royal Statistical Society, Series C, 1979) — contribution: EM-based label aggregation modeling per-annotator error rates. Applied in §9 (ADR-16) / Phase 5 (§17).
  • Cohen, J. — "A Coefficient of Agreement for Nominal Scales" (Educational and Psychological Measurement, 1960) — contribution: chance-corrected pairwise agreement (kappa). Applied in §9 (ADR-18) / Phase 5 (§17).

Reference Implementations

  • CVAT (github.com/cvat-ai/cvat) — study cvat/apps/engine task-orchestration models — lesson: task/job/segment hierarchy for video chunking; pitfall: monolithic Django ORM makes horizontal sharding hard past single-node Postgres. Applied in Phase 3 (§15).
  • Label Studio (github.com/HumanSignal/label-studio) — study its labeling-config XML/plugin architecture — lesson: declarative, per-project annotation-schema definitions; pitfall: schema validation happens client-side only, weakening server-side guarantees. Applied in §11 / Phase 4 (§16).
  • doccano (github.com/doccano/doccano) — study its NER span-annotation data model — lesson: simple (start, end, label) span representation generalizes well; pitfall: no built-in inter-annotator agreement tooling. Applied in §8 / Phase 4 (§16).
  • Temporal (github.com/temporalio/temporal) — study service/history workflow-execution engine — lesson: event-sourced workflow state with deterministic replay; pitfall: operating a general-purpose workflow engine is heavier than this platform's narrower FSM needs (ADR-14). Applied in Phase 6 (§18).
  • OpenTelemetry Collector (github.com/open-telemetry/opentelemetry-collector) — study the receiver/processor/exporter pipeline — lesson: pluggable telemetry pipeline design; pitfall: misconfigured batch processors silently drop spans under backpressure. Applied in §24 / Phase 0 (§12).
  • MinIO (github.com/minio/minio) — study its S3-API-compatible erasure-coding layer — lesson: content-addressed object abstraction over erasure-coded shards; pitfall: multipart upload completion races need explicit fencing. Applied in §9 (ADR-06) / Phase 2 (§14).
