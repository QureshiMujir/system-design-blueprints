In one paragraph

A data-labeling platform coordinates people, helped by models, who attach labels to images, video, text, audio and documents (§1). The blueprint's reason it matters: model quality is bounded by the quality of the curated labeled data (§2). This design is a multi-tenant, Kubernetes-native system of eleven numbered backend services plus a React editor, with design targets of 50,000 concurrent annotators and 120,000 concurrent realtime sessions (§1, §4). Per-tenant isolation is "a structural, not procedural, guarantee" (§1, I5). Alongside it, a lease with a fencing token stops stale writers (I12), and a statistical model of annotators replaces vote counting (ADR-16). ML engineers, data-operations teams, auditors and platform operators use it, in the cloud or self-hosted (§1).

The problem, concretely

Picture one annotation task. A worker claims it, pauses past the time the claim was good for, the lease expires and the task is reassigned. Then the first worker resumes and submits (§8). If the lease is only a timer, that paused worker's write lands after its TTL has passed: the "split-brain writes" bug class MM1 names (MM1). The blueprint calls this the "canonical case" its fencing rule exists to prevent (§8, I12). Its fix is that every claim carries a number that only goes up (a fencing token), and the store refuses a write carrying an older number (I12, §36).

Scale makes each such problem sharper. The same mutable records must be strongly consistent (task metadata), eventually consistent (search), low-latency (realtime fanout) and append-only (audit) at once (§2). Counting votes gives "systematically wrong labels from a confidently-wrong majority" when annotators differ in skill (MM2). Tenant isolation done only in application code "eventually leaks under one missed WHERE clause", and cross-tenant leakage is Sev-0 (MM5, I5). A search index that cannot be rebuilt has "no recovery path" after it drifts (MM3, FM-5). Each of these pressures has its own mechanism below.

How it works, end to end

Follow one task from claim to archive through the boxes of §3. The diagram below is drawn from the §3 diagram, with boxes merged to save space, coloured by role.

  1. Edge. The api-gateway is the only box facing the public network. It terminates TLS, applies per-org rate limits, validates the JWT and propagates trace context. Every internal hop then authenticates with mTLS plus service tokens (§3).
  2. Identity. auth-service evaluates roles (RBAC), federates with the customer's identity provider over OIDC, syncs users by SCIM and invalidates its permission cache on a role or grant change (§3, §13.2).
  3. Assets. dataset-service takes multipart uploads against the S3 API, deduplicates by SHA-256 and applies lifecycle policies that move objects to a cold tier (§14.2, I9).
  4. Claim. workflow-service compiles declarative pipelines into state machines (§3). task-service grants the lease, with fair, priority and SLA-aware scheduling (§3, §15). The task goes Created to Assigned when the lease is acquired (§8).
  5. Edit. The annotator opens the task (InProgress). realtime-gateway carries cursors, locks and presence over WebSocket, and presence is advisory only (§3, I13). Saves go to annotation-service, which validates the payload against the schema and writes a revision whose payload is immutable once written (§3, §8, §11, I10).
  6. Review. A submitted task is routed to QA (ReviewPending). review-service scores consensus, computes agreement and escalates below-threshold items (§3, §8, §17).
  7. Fan-out. Services publish to the Kafka event-bus, whose partition key is the aggregate id, so one aggregate's events stay in order (§3, I6). audit-service keeps the hash-chained log. search-service and ml-assist-service sit behind the bus and build the search projection and the active-learning sampling (§3, §19).
  8. End. When the retention window elapses the task goes Approved to Archived, guarded by "legal hold absent" (§8, §20).

PostgreSQL is the strongly consistent metadata of record; object storage holds content-addressed raw assets, the cold tier and exports (§3). The hot path (Postgres, Redis) and the cold path (archive tier) never share a latency budget (§3, P10).

The blueprint describes the audit write in two ways that it does not reconcile. P3 and §20.2 require every mutation of a revision, review decision or lease to commit "with an audit event in the same transaction boundary" (P3, §20.2). The §3 diagram places audit-service downstream of the Kafka event-bus (§3).

The core ideas

A lease plus a number that only goes up (§8, ADR-20, I3, I12, MM1)

A lease is a temporary exclusive claim on a task (§36). MM1 puts it as "every distributed lease is a bet against a clock you don't control" and predicts that lease systems need fencing tokens, not just TTLs (MM1). So each grant also carries a fencing token, and Postgres does a compare-and-swap (CAS) that accepts the write only if its token is at least the stored one (§8, I12). The blueprint's own trace, drawn from §8:

The two examples §8 walks through next:

Case What happens Result (§8)
Stale writer A SubmitRevision arrives with fencing_token=41 after the lease was re-issued at 42 (worker paused, lease expired, reassigned) annotation-service rejects the write; stale_lease_write_rejected_total counts it (I12)
Lost grant task-service crashes after LeaseGranted but before the client receives AssignmentPayload the 90 s TTL expires with no heartbeat, orphaned_task_leases fires, the lease is invalidated and the task returns to Created (I3, FM-4)

The record behind it is LeaseRecord {task_id, worker_id, fencing_token, acquired_at, ttl_seconds}, with the token typed LeaseToken(u64) (§11). The lease lives in Redis for millisecond renewal; the token check lives in Postgres so it blocks stale writes after failover (ADR-20). Task ownership during an active lease must be singular (I3).

Phase 3 lists the traps: a client heartbeat delayed by GC or scheduler jitter orphans a lease, and clock drift between task-service nodes skews TTL expiry judgment (§15.6). A client that retries a claim after a slow response is safe, because the claim is idempotent via the fencing token (§15.8). The conflict budget is below 0.001% of claims under a 50,000-worker synthetic load, gated at Phase 3 (M10, §15.4).

The task lifecycle as a table you can replay (§8, §18, I7, P1, P12)

The task lifecycle is a plain table of (from, event, to, guard) rows, and an FSM validator (a checker for a finite-state machine) rejects any transition not in it (§8, I7). The full table from §8:

From Event To Guard (§8)
Created AssignmentPayload issued Assigned lease acquired (I3)
Assigned annotator opens task InProgress session token valid
InProgress SubmitRevision Submitted schema validation passes
Submitted routed to QA ReviewPending consensus threshold not yet met
ReviewPending consensus/adjudication passes Approved agreement at or above the project threshold (ADR-18)
ReviewPending consensus/adjudication fails Rejected none
Rejected requeue Requeue, then Created retry budget not exhausted (P2)
Approved retention window elapses Archived legal hold absent (§20)

P1 requires that replaying the event log produce identical FSM states, and P12 that every aggregate's current state be "a pure fold over its event history" (P1, P12). P1 forbids wall-clock-dependent branching in guards, so a timeout is an explicit deadline event, never a sleep (P1, §18.2). A timeout written as a sleep is a named Phase 6 pitfall because it breaks replay (§18.6).

workflow-service compiles a declarative pipeline into the WorkflowDefinition states and transitions table (§11, §18.2). Its validator rejects cycles and unreachable states (§18.2). Two edge cases show the shape of the checks: a workflow that names a TaskState outside the compiled state set, and a compensation action firing twice under at-least-once delivery, which P9 dedup guards (§18.8). Phase 6 proves replay with 10,000 randomly reordered-then-corrected event streams that must reach identical final states (§18.4). If two replicas still disagree, replay_divergence_total goes nonzero and pages, because it implies a P1 violation (§18.10, FM-6).

The event log is the database (§8, §19, MM3, P9, I6, FM-5)

MM3 says "an event log is the database; the tables are just a cache of it", and predicts that any projection (a derived view such as the search index or an analytics view) must be fully rebuildable from the log (MM3). Every event travels in one wrapper (§11):

Field of EventEnvelope<T> Role (§11)
event_id dedup key component (P9)
aggregate_id Kafka partition key (I6)
occurred_at timestamp
schema_version explicit event versioning (I10, P8)
payload the event body

Using aggregate_id as the partition key keeps one aggregate's events in order (I6). Every consumer dedupes by (aggregate_id, event_id), which turns Kafka's at-least-once delivery into effectively-once at the application layer; without it, duplicate delivery double-counts usage metering (P9). A replayed task-completion event is one of the malformed inputs that must be rejected (§8, P9). Event schemas evolve strictly by adding new optional fields; a breaking change needs a new event type (§25).

Consistency is chosen per subsystem: metadata strong, search eventual within the 10 s lag target, analytics asynchronous materialization, presence soft state (§8). The search index is never treated as the source of truth (§19.6). If a projection drifts, the symptom is query results missing recently approved annotations. A projection-count mismatch against the source of truth detects it; incremental catch-up replay is automatic, and the manual path is a full rebuild from the event log (FM-5, §19.9).

Consensus as a model of annotators (§17, ADR-16, ADR-18, I11, MM2, MM6)

Instead of counting votes, review-service uses Dawid-Skene aggregation, an expectation-maximisation (EM) method that models per-annotator error rates instead of giving every vote equal weight (ADR-16, §17.2). MM2 predicts it beats majority vote once annotators have skewed skill or error rates (MM2). Agreement is reported with chance-corrected statistics: Cohen's kappa for pairs and Krippendorff's alpha for many annotators (ADR-18). MM6's warning case is "shipping a '95% agreement' golden set that is actually near chance", because raw percent agreement overstates quality on a skewed label distribution (MM6).

A ConsensusRecord stores the task id, the algorithm (DawidSkene or MajorityVote), the algorithm version, the raw votes, the aggregated label and the agreement score (§11). I11 requires the score to be deterministic for a fixed annotator set and algorithm version, with the version pinned on every ReviewDecision (I11). Phase 5 checks it by recomputing kappa/alpha from stored raw votes and matching the persisted agreement_score to 1e-6 (§17.4). It also checks EM on a fixture with known per-annotator error rates, which must be recovered within 2% of ground truth (§17.4).

§17.2 adds a majority-vote fallback for the fewer-than-3-annotator regime, where EM has too few data points to converge (§17.2, ADR-16). §17.9 applies the fallback automatically below the annotator-count threshold and escalates to a senior reviewer above it (§17.9, FM-8). Labeling-function votes can join the same raw_votes, each sandboxed (§17.2, T11). Agreement is not the whole check: if all annotators agree on a value a golden-set check later shows wrong, the item goes to escalation regardless of its agreement score (§17.8). Each ReviewDecision carries a prior_hash and an Ed25519 signature, so who approved what can be reconstructed (§11, I8).

Tenant isolation lives in the database (§13, P4, I5, MM5, T3, T9)

Every query carries organization_id, and row-level security (RLS) in Postgres enforces it, "never application code alone" (P4). Objects get namespace-segregated prefixes (I5). The cost is a tenant column and a policy on every table. In return, cross-tenant joins are structurally impossible (P4).

The threat it answers is tenant breakout through a crafted org_id or dataset_id in a request (T3). RLS blocks that read inside the database, cross_tenant_read_denied_total counts it, and §13.10 alerts on any cross-tenant denial separately from ordinary permission denials (I5, §13.10). The same rule covers search, where the tenant filter is injected by the server and never supplied by the client (T9). Every log line also carries organization_id (§24).

Two Phase 1 cautions: the permission cache must invalidate synchronously on a revoke, not on TTL alone (§13.6), and RLS evaluation on hot tables must not push API p99 past 900 ms (§13.7, M3). Phase 1 proves isolation with a 500-case adversarial fixture suite that must block 100% of cross-tenant access (§13.4).

A hash chain nobody can quietly edit (§20, I2, P3, FM-12)

Each audit record is linked by prior_hash, so any tamper is detectable by chain verification, down to a single mutated byte in a stored record (§20.2, §20.4). The log is append-only at the database-role level, with no UPDATE or DELETE grants (I2, §20.2). Every mutating write path (annotation revision, lease grant, review decision, RBAC grant) emits an audit event (§20.2, P3). The extra durable write per mutation means audit-service throughput must scale with annotation throughput, with a p95 commit target below 50 ms (P3, M12).

The chain has one writer path. A concurrent writer that bypasses it breaks the chain, and there is no safe auto-recovery: the operator forks the chain from the last verified record and files an incident (§20.6, §20.9, FM-12). Verification runs nightly, and its own pass or fail is an audited event (§20.10). Phase 8 also replays the last 24 hours of state from the audit log and must match the live metadata DB (§20.4).

A legal hold overrides retention expiry for a matter (§20.2). A retention sweep must check hold status before it purges (§20.6), and a hold placed on a record already past its retention window wins (§20.8).

The trade-offs — where engineers disagree

Lease mechanism: Redis TTL lease plus Postgres fencing token (ADR-20)

Chosen: Redis TTL lease plus a Postgres fencing token, for millisecond lease renewal plus a token that blocks stale writes after failover (ADR-20). Rejected: ZooKeeper, or pure Postgres advisory locks (ADR-20). When the rejected choice is right: ZooKeeper, when the organisation already runs a ZooKeeper ensemble for pre-KRaft Kafka (ADR-20).

Label aggregation: Dawid-Skene EM (ADR-16)

Chosen: Dawid-Skene EM, which models per-annotator error rates instead of equal-weight votes (ADR-16). Rejected: majority vote, or the Snorkel generative model (ADR-16). When the rejected choice is right: majority vote, for golden-set bootstrap tasks with fewer than 3 annotators, where there are too few points for EM (ADR-16).

Workflow engine: an internal FSM compiler (ADR-14)

Chosen: an internal FSM compiler, for a reduced operational dependency surface and deterministic replay (ADR-14). §18.2 says its replay tooling is informed by Temporal's event-sourced history model, while keeping the FSM narrower on purpose. Rejected: Temporal or Cadence (ADR-14). When the rejected choice is right: Temporal, for long-running (more than days) durable timers across worker fleets (ADR-14).

Event bus: Kafka (ADR-04)

Chosen: Kafka, for replayability, partitioned ordering and long retention for audit replay (ADR-04). Rejected: RabbitMQ or NATS (ADR-04). When the rejected choice is right: NATS, for low-volume single-region deployments that need sub-5ms fanout (ADR-04).

Metadata database: PostgreSQL (ADR-03)

Chosen: PostgreSQL, for transaction isolation levels, row-level security and JSONB (ADR-03). Rejected: MySQL or CockroachDB (ADR-03). When the rejected choice is right: CockroachDB, when true active-active multi-region writes are mandatory (ADR-03). §33 question 20 asks why such writes were deliberately deferred.

Agreement metric: kappa plus alpha (ADR-18)

Chosen: Cohen's kappa (pairwise) plus Krippendorff's alpha (multi-annotator), which correct for chance agreement on skewed label distributions (ADR-18). Rejected: raw percent agreement (ADR-18). When the rejected choice is right: raw percent agreement, for a quick non-technical dashboard where kappa confuses reviewers (ADR-18).

ID generation: UUIDv7 (ADR-21)

Chosen: UUIDv7, which is time-ordered for index locality and globally unique without coordination (ADR-21). It is also the named mitigation for metadata hot partitions from sequential-ID assets (§14.6, §29). Rejected: auto-increment int64, or ULID (ADR-21). When the rejected choice is right: auto-increment, for a single-writer legacy import table (ADR-21).

Roads not taken (§34, §35, §29)

CRDT-based collaborative annotation (§34): clients merge edits locally with no central lease. It wins for real-time multi-cursor document editing with no single-writer requirement, as in Figma's multiplayer engine or Automerge-based editors. It is rejected because polygon vertex conflicts and mask edits have no clean merge semantics, and the audit chain of custody needs one authoritative revision writer per task (I8).

Serverless, event-driven functions (§34): it wins for bursty, low-baseline workloads with no sustained connection requirement. It is rejected because the platform needs long-lived stateful websocket connections, and cold-start tail latency conflicts with the save target (M1). §34 states that need as "sustaining 50,000 concurrent websocket sessions (§4)", while §4 lists 120,000 concurrent websocket sessions and 50,000 concurrent annotators (§4, §34).

A blockchain audit ledger (§34): it wins in multi-party trustless settings, such as consortium data-sharing across independent organisations. It is rejected because a single organisation's audit trail needs no Byzantine-fault-tolerant consensus; an append-only hash-chained log gives equivalent tamper-evidence at a fraction of the latency and operational cost (I2).

A single-binary monolith (§34): it wins for small teams with fewer than 100 concurrent annotators and a single tenant. It is rejected because the §4 scale target needs independent scaling and failure domains per service, and a monolith couples search-service's load to annotation-service's availability, violating P10.

Deferred features (§35): synthetic data generation, federated workforce routing, offline-first annotation and live collaborative video segmentation each sit behind a PhaseDeferred hook with an un-defer trigger. For example, offline-first annotation waits until a field-deployment customer requires annotation without connectivity (§35). Horizontal sharding of the metadata DB by organization_id is also deferred until a single org's metadata volume alone threatens the ceiling, since sharding trades away single-transaction cross-entity queries (§29).

What must never be false

  • I1: revision IDs are monotonic per task, enforced by a Postgres sequence and a task_id partition constraint. Noticed by replay_divergence_total; telemetry revision_gap_total (§7). §11 types the ID as RevisionId(Uuid), "monotonic per TaskId (I1)", and ADR-21 picks UUIDv7 for IDs (§11, ADR-21).
  • I2: audit records are immutable (no UPDATE/DELETE grants). Noticed by storage_hash_mismatch_total; telemetry audit_write_rejected_total (§7).
  • I3: only one worker owns a task during an active lease. Noticed by orphaned_task_leases; telemetry lease_conflict_total (§7).
  • I4: export snapshots are consistent, fenced at a fixed LSN. Noticed by export_checksum_mismatch_total; telemetry export_snapshot_age_seconds (§7).
  • I5: tenant data stays isolated, by RLS and namespace-segregated object prefixes. Noticed by cross_tenant_read_denied_total; telemetry authorization_denied_total (§7).
  • I6: events stay in order per aggregate, via the partition key. Noticed by out_of_order_event_total; telemetry consumer_lag (§7).
  • I7: workflow transitions are always valid, checked by the FSM validator. Noticed by workflow_transition_rejections; telemetry fsm_reject_total (§7).
  • I8: review approvals are traceable via a signed chain of reviewer_id plus prior hash. Noticed by review_chain_break_total; telemetry review_signature_invalid_total (§7).
  • I9: object references are content-addressed, SHA-256 checked on write and read. Noticed by storage_hash_mismatch_total; telemetry hash_validation_latency_ms (§7).
  • I10: schema changes stay compatible, via a registry compatibility check. Noticed by schema_incompatible_total; telemetry schema_registration_rejected_total (§7).
  • I11: the consensus score is deterministic for a fixed annotator set and algorithm version. Noticed by consensus_replay_mismatch_total; telemetry consensus_score_variance (§7).
  • I12: only one lease token is active per (task, attempt), enforced by a Postgres compare-and-swap. Noticed by stale_lease_write_rejected_total; telemetry fencing_token_mismatch_total (§7).
  • I13: presence is soft state and never authoritative; annotation-service treats it as advisory. Noticed by presence_authority_violation_total; telemetry presence_reconnect_total (§7).
  • I14: active-learning selection is reproducible for a fixed model snapshot and seed, since (model_version, seed, score) is stored with each queued sample. Noticed by al_selection_replay_mismatch_total; telemetry al_queue_depth (§7).

What breaks in production

  • FM-4: tasks stuck in Assigned. A worker crashed mid-lease or missed a heartbeat. The expired-heartbeat detector and orphaned_task_leases flag it; TTL expiry invalidates the lease and requeues automatically, and an operator can force-invalidate a lease batch (§23).
  • FM-5: search misses recently approved work. The projection consumer lagged or crashed. A projection-count mismatch against the source of truth flags it; incremental catch-up replay is automatic, and the manual path is a full rebuild from the event log (§23).
  • FM-6: two replicas disagree on a workflow state. The cause is a non-deterministic FSM guard (a P1 violation) or a missed event. replay_divergence_total detects it, and there is no auto-recovery: an operator rolls back to the last agreed checkpoint and replays (§23). Any nonzero value pages (§18.10).
  • FM-7: realtime latency climbs and presence events drop. One popular dataset room is hot-spotting one pod. A per-pod websocket_sessions skew alert catches it; sessions rebalance by consistent hashing automatically, or an operator shifts room ownership (§23).
  • FM-8: consensus will not converge. Too few annotators per item, or an adversarial annotator, makes EM fail to converge or oscillate. A consensus_score_variance threshold breach detects it; the system falls back to majority vote "below N annotators", or an operator escalates the item to a senior reviewer (§23, ADR-16).
  • FM-9: an export contains partly committed revisions. A snapshot-fencing race at the MVCC boundary. export_checksum_mismatch_total detects it, and the export retries at a fresh snapshot LSN automatically (§23, I4).
  • FM-11: no new priority samples. The ML-assist scoring endpoint is unavailable, so active-learning queue depth grows. An al_queue_depth alert plus a stale model_version detects it. Sampling falls back to random automatically and never blocks task creation; an operator then restarts ml-assist-service and backfills scores (§23, §19.10).
  • FM-12: audit chain verification fails at a record. A concurrent writer bypassed the single-writer append path. review_chain_break_total or storage_hash_mismatch_total detects it. There is no auto-recovery: the operator forks the chain from the last verified record and files an incident (§23, §20.9).

Threats worth knowing (§22):

  • T2, crafted media meant to crash the decoder. Defence: sandboxed decoding, hash-gated before decode (I9).
  • T3, tenant breakout through a crafted org_id or dataset_id in a request. Defence: namespace isolation plus RLS (P4, I5).
  • T9, crafted search queries probing another tenant's index. Defence: a server-injected tenant filter, never client-supplied.
  • T10, a compromised credential used for mass export. Defence: export quotas and anomaly detection on volume per org.
  • T11, an untrusted labeling function run against organisation data. Defence: sandboxed execution that is resource-limited and has no network (ADR-17).

How it compares

  • Label Studio chose an XML labeling-config language so non-engineers can define new label types without a deploy, at the cost of pushing schema validation partly to the client. That suits rapid-prototyping teams iterating on their label taxonomy weekly (§31).
  • CVAT chose to chunk video into jobs and segments stored as first-class database rows, with job-level locking and no live cursors. That suits frame-accurate video QA, where segment-level reviewer assignment matters more than realtime collaboration (§31).
  • SageMaker Ground Truth chose a fully managed AWS-only service with opaque work-team routing, trading self-host and air-gap capability for zero infrastructure ownership. That suits a team already committed to AWS with no compliance requirement to self-host (§31).
  • Scale AI chose to make the platform inseparable from a managed annotation workforce, SaaS only. That suits teams that want to buy labeled data as an outcome rather than operate a labeling platform (§31).

Against all four, this design chooses Dawid-Skene plus kappa/alpha consensus, a fencing-token lease, Postgres plus S3 plus Kafka, a self-hostable and air-gapped profile, and a declarative FSM workflow (§31).

If you only remember three things

A lease is only safe with a fencing number the store checks on every write, because a timer alone cannot stop a paused worker (MM1, I12). Consensus is a model of annotators, not a vote count, and its result must be recomputable from the stored raw votes (MM2, I11). The event log is the database: search and analytics rebuild from it, tenant isolation is a database property rather than an application habit, and the audit chain makes tampering detectable (MM3, MM5, I2).

Words used here

  • Annotation revision: an immutable labeled-state snapshot for one task (§36).
  • Lease / fencing token: a temporary exclusive claim on a task, plus a monotonic number that invalidates stale writes after reassignment (§36).
  • Dawid-Skene model: an EM-based way to combine labels by modelling each annotator's error rates (§36).
  • Cohen's kappa / Krippendorff's alpha: chance-corrected agreement statistics, pairwise and multi-annotator (§36).
  • Golden dataset: a verified reference set used to check annotator and reviewer quality (§36).
  • Weak supervision / labeling function: combining noisy, non-ground-truth label sources into one signal, and a programmatic vote source that feeds it (§36).
  • Projection: a derived, query-optimised, rebuildable view of the event log, such as the search index (§36).
  • Replay: deterministic reconstruction of state from an event history (§36).
  • Soft state: transient, reconstructable state with no correctness authority, such as presence (§36).
  • Row-level security (RLS): a database-enforced per-row access policy keyed on tenant (§36).
  • Content-addressed storage: objects referenced and validated by the hash of their bytes (§36).
  • Backpressure / admission control: signalling that a queue cannot take more, and rejecting excess load at the edge instead of buffering it (§36).
  • Legal hold: a retention override that prevents deletion of records under a legal matter (§36).
  • Expand-contract migration: an additive-then-subtractive schema change that preserves compatibility during rolling upgrades (§36).
