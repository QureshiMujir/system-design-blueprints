Project Number: 257

Project Name: Data Labeling Platform from Scratch

Status: specification — locked

1. Goal & Scope

Build a production-grade, multi-tenant data-labeling platform that orchestrates distributed human (and model-assisted) annotation across image, video, text, audio, and document modalities, with consensus-based quality control, an active-learning feedback loop, immutable audit, and versioned dataset export, engineered to sustain 50,000 concurrent annotators and 120,000 concurrent realtime sessions (§4) while holding per-tenant isolation as a structural, not procedural, guarantee (I5).

Phase 0 deliverable — repository skeleton + correctness kernel, as numbered modules:

  1. api-gateway — edge trust boundary, TLS termination, routing
  2. auth-service — RBAC, OIDC federation, tenant isolation
  3. dataset-service — asset ingestion, dedup, lifecycle
  4. task-service — lease manager, fair scheduling
  5. annotation-service — revision DAG, autosave, schema validation
  6. realtime-gateway — websocket sessions, presence, cursors
  7. workflow-service — DAG compiler, FSM execution
  8. review-service — consensus aggregation, agreement metrics, escalation
  9. search-service — incremental indexing, query API
  10. ml-assist-service — prediction ingestion, active-learning sampling
  11. audit-service — hash-chained append-only log, legal hold
  12. libs/protocol, libs/storage, libs/auth, libs/tracing, libs/schema — shared crates
  13. web-client — annotation editor (React + TS)
  14. admin-console — operator UI
  15. cli-tooling + conformance/ — operator CLI and fixture suite

System boundaries — provides: task orchestration, annotation persistence, consensus/QA, workflow DAGs, dataset versioning and export, audit, RBAC/tenant isolation, observability. Delegates: model training (to an external ML platform), GPU scheduling (to Kubernetes device plugins / an external scheduler), IdP identity storage (to the customer's OIDC provider), long-term cold-tier durability (to S3/GCS beneath the object-storage adapter, ADR-06). Does NOT provide: AutoML pipeline orchestration, a GPU cluster scheduler, federated training infrastructure, or consumer social features.

Non-goals: general-purpose ML training platform; AutoML; GPU cluster scheduler; federated training infrastructure; consumer-facing social collaboration tooling.

Deployment model: Kubernetes-native; multi-region capable; cloud-first with a self-hostable enterprise edition; an air-gapped deployment profile (ADR-11, ADR-23).

Target users: ML engineers, data-operations teams, security auditors, platform operators, enterprise customers, external annotation vendors.

Language: backend Rust (deterministic memory safety, no GC pause at p99, strong serialization via Protobuf, ADR-01/ADR-13); frontend TypeScript + React (canvas-annotation ecosystem maturity, ADR-02); infra tooling Go + Bash (Kubernetes operator ecosystem). Rejected: Go for the annotation core (GC pause risk against the <120ms p95 save target, §4); Java (JVM warm-up and heap tuning cost against the 4GB worker memory ceiling, §4).

Prerequisites: distributed systems, networking, async runtimes, database internals, transaction isolation, object-storage semantics, event-driven architectures, search indexing, WebSocket fundamentals, Kubernetes operations, RBAC models, observability engineering, queueing theory, storage engines.

Timeline: Phase 0 MVP 10–12 weeks; production hardening 5–7 months; multi-region enterprise release 9–14 months.

Deferred features (registered in §35, resolved anchors real): synthetic data generation PhaseDeferred("§19"); federated workforce routing PhaseDeferred("§15"); on-device (offline-first) annotation PhaseDeferred("§16"); live collaborative video segmentation PhaseDeferred("§16").

2. Why Build This

Unique systems knowledge: this is one of the few project classes that forces simultaneous mastery of (a) strong-consistency transactional metadata, (b) eventually-consistent search projections, (c) low-latency realtime fanout, and (d) an append-only audit ledger — all against the same mutable domain objects. Most distributed-systems projects pick one consistency regime; this one requires composing three deliberately, at the boundaries defined in §8.

Architectural/historical significance: annotation infrastructure became foundational to modern AI because model quality is bounded by curated labeled-data quality — Snorkel (Ratner et al., VLDB 2017) formalized this by treating labeling itself as a programmable, auditable pipeline rather than an ad hoc spreadsheet exercise. Enterprises with security, workflow, or compliance constraints (finance, health, defense) routinely build internal tooling rather than adopt a SaaS platform, which is why this class of system recurs across large organizations.

Cross-links to sibling systems: Label Studio and CVAT solve the annotation-editor and plugin-architecture problem this platform must also solve (§31); Temporal solves the durable workflow problem this platform intentionally solves narrower and in-house (ADR-14); Kafka and Dynamo (papers, §5) inform the event-bus and lease-store designs; Elasticsearch/OpenSearch inform the projection-consistency tradeoffs of §8; Delta Lake's transaction-log protocol informs the dataset-versioning approach of Phase 2 (§14).

Calibration value: implementing this platform requires balancing consistency, latency, human workflow ergonomics, cost efficiency, and operational visibility under concurrent mutation pressure — the same balancing act as any large-scale human-in-the-loop system (fraud review, content moderation, clinical adjudication).

What Mastery Looks Like

  • Can explain, for any write path, which consistency regime applies and why (metadata: strong; search: eventual; analytics: async materialized; presence: soft-state) — tied to Phase 0 (§12) and Phase 4 (§16).
  • Can implement a fencing-token lease manager that survives worker crash-during-lease without double-assignment — tied to Phase 3 (§15).
  • Can implement Dawid-Skene EM label aggregation from raw annotator votes and reproduce its score deterministically — tied to Phase 5 (§17).
  • Can compile a declarative annotation-workflow DAG into a replayable FSM and prove replay determinism under event reordering — tied to Phase 6 (§18).
  • Can reconstruct a search index from the event log after a demonstrated drift incident — tied to Phase 7 (§19).
  • Can produce a tamper-evident hash-chained audit log and verify it end-to-end — tied to Phase 8 (§20).
  • Can operate a multi-region failover drill that meets the <30 min RTO (§4) — tied to Phase 9 (§21).

api-gateway — TLS termination, per-org rate limiting, JWT validation, trace-context propagation; the sole ingress trust boundary (I5, T3, T4). auth-service — RBAC evaluation, OIDC federation, SCIM sync, permission-cache invalidation (I5, T5, T7). realtime-gateway — websocket session state, collaborative cursors, annotation locks, low-latency fanout; presence is soft state (I13). workflow-service — compiles declarative pipelines into executable FSMs (P1, ADR-14). task-service — the orchestrator: fencing-token leases, fair/priority scheduling, SLA dispatch (I3, I12, ADR-20). annotation-service — revision DAG persistence, autosave checkpoints, schema-validated payloads for bbox/polygon/segmentation/keypoint/NER/ transcription (§8, §11). review-service — consensus scoring (Dawid-Skene EM, ADR-16), agreement metrics (Cohen kappa / Krippendorff alpha, ADR-18), escalation. event-bus (Kafka, ADR-04) — durable, replayable, partition-key-ordered transport (I6). audit-service — append-only, hash-chained, immutable (I2, P3). search-service — eventually consistent projection (§8) rebuildable from the event log (FM-5). ml-assist-service — prediction ingestion and active-learning sampling with reproducible scoring (I14). PostgreSQL — strongly consistent metadata of record (ADR-03). Object storage — content-addressed raw assets, cold tier, exports (I9, ADR-06). Trust boundary: only api-gateway faces the public network; every internal hop authenticates via mTLS + service tokens. Concurrency boundary: optimistic concurrency on revisions, pessimistic fencing-token leases on assignments, snapshot isolation on exports (§11). Persistence boundary: hot path (Postgres/Redis) vs. cold path (object storage archive tier) never share a latency budget (P10).

6. Design Principles

P1 — Deterministic Workflow Execution. Rule: replaying the event log must produce identical FSM states. Tradeoff: forbids wall-clock-dependent branching in FSM guards. Operational implication: timers are explicit deadline events, never sleep. Violating it breaks: replay-based forensics (§23) and consensus recompute (I11) both become unusable.

P2 — Backpressure Everywhere. Rule: every queue (Kafka partition, Redis stream, in-process channel) exposes bounded capacity plus admission control. Tradeoff: producers see explicit rejection instead of unbounded buffering. Operational implication: overload sheds at api-gateway, not at the worker. Violating it breaks: unbounded queue growth escalates to OOM and cascading failure (FM-7).

P3 — Auditability Before Convenience. Rule: no mutation to AnnotationRevision, ReviewDecision, or a task lease commits without an audit event in the same transaction boundary. Tradeoff: one extra durable write per mutation. Operational implication: audit-service throughput must scale with annotation throughput (M12). Violating it breaks: compliance — an unauditable state change is a legal-hold gap.

P4 — Tenant Isolation Is Mandatory. Rule: every query carries organization_id and is enforced by row-level security, never application code alone. Tradeoff: every table needs a tenant column plus policy. Operational implication: cross-tenant joins are structurally impossible. Violating it breaks: cross-tenant leakage — a Sev-0 incident (I5, T3).

P5 — Observability by Default. Rule: every request propagates W3C trace context end to end, including into object-storage spans. Tradeoff: instrumentation overhead on the hot path. Operational implication: error traces are sampled at 100%. Violating it breaks: incidents become unreconstructable postmortems.

P6 — Crash-Only Recovery Semantics. Rule: services restart from durable state; there is no in-memory-only recovery path. Tradeoff: all critical state must live in Postgres, Kafka, or object storage. Operational implication: no correctness path depends on graceful shutdown. Violating it breaks: kill -9 mid-deploy corrupts in-flight work.

P7 — Bounded Memory Ownership. Rule: no unbounded in-memory queue or cache; every buffer has an eviction or backpressure policy. Tradeoff: some throughput loss versus unlimited buffering. Operational implication: the 4 GB worker ceiling (§4) must be provable, not empirical. Violating it breaks: a large dataset upload OOMs annotation-service.

P8 — Schema Evolution Must Be Explicit. Rule: every schema change ships migration metadata plus a compatibility check (ADR-13, I10). Tradeoff: slower schema iteration. Operational implication: rolling upgrades depend on this. Violating it breaks: silent consumer breakage during a rolling deploy.

P9 — Idempotent Event Consumption. Rule: every consumer dedupes by (aggregate_id, event_id). Tradeoff: an extra dedup-table lookup per event. Operational implication: Kafka's at-least-once delivery becomes effectively-once at the application layer. Violating it breaks: duplicate delivery double-counts billing/usage metering.

P10 — Storage Tier Awareness. Rule: the hot path (Postgres/Redis) and the cold path (object-storage archive tier) never share a latency budget. Tradeoff: explicit lifecycle transitions instead of one uniform store. Operational implication: cold-tier reads are async with a distinct SLA. Violating it breaks: an export job blocking on a cold-tier read exceeds the <5s export-startup target (§4, M4).

P11 — Operational Simplicity Over Cleverness. Rule: prefer a debuggable mechanism (an FSM table, a SQL constraint) over a theoretically optimal but opaque one. Tradeoff: leaves some performance headroom unclaimed. Operational implication: on-call engineers can reason about the system at 03:00. Violating it breaks: an unstaffable single point of tribal knowledge.

P12 — Replayability First. Rule: every aggregate's current state is a pure fold over its event history. Tradeoff: the event store grows without bound (mitigated by snapshotting). Operational implication: incident reconstruction (§23) and consensus recompute (I11) both depend on this. Violating it breaks: "why did this happen" has no answer.

Malformed-input example: a SubmitRevision arrives with fencing_token=41 after the lease was re-issued at 42 (worker paused, lease expired, reassigned). annotation-service rejects the write (stale_lease_write_rejected_total, I12) rather than accepting a stale payload — this is the canonical case P1/I12 exist to prevent.

Failure-path example: task-service crashes after LeaseGranted but before the client receives AssignmentPayload. The lease TTL (90s) expires with no heartbeat; orphaned_task_leases fires; the lease manager invalidates and the task returns to Created for re-claim (I3, FM-4).

Other malformed cases requiring rejection: duplicate revision IDs (I1), stale review references (I8), expired presigned upload URLs (rejected by dataset-service, §14), orphaned websocket sessions (I13), invalid ontology references (schema validation, I10), replayed task-completion events (P9).

Consistency semantics by subsystem: metadata (Postgres) — strong; search index — eventually consistent, bounded by the §4 10s lag target; analytics views — asynchronous materialization; websocket presence — soft-state eventual consistency (I13).

  revision_id: RevisionId,
  task_id: TaskId,

  worker_id: UserId,

  ttl_seconds: u32,
}

struct ConsensusRecord {             // owned by review-service (ADR-16, I11)
  task_id: TaskId,
  algorithm: ConsensusAlgorithm,     // enum { DawidSkene, MajorityVote }
  algorithm_version: SemVer,
  raw_votes: Vec<AnnotatorVote>,
  aggregated_label: LabelId,
  agreement_score: f32,              // kappa or alpha, per ADR-18
}

struct ReviewDecision {
  decision_id: ReviewDecisionId,
  task_id: TaskId,
  reviewer_id: UserId,
  outcome: ReviewOutcome,            // enum { Approved, Rejected }

}

  workflow_id: WorkflowId,
  states: Vec<TaskState>,
  transitions: Vec<(TaskState, EventKind, TaskState)>,
}
struct EventEnvelope<T> {            // event-bus wire wrapper (I6, P9)
  event_id: EventId,
  aggregate_id: Uuid,                // Kafka partition key
  occurred_at: Timestamp,
  schema_version: SemVer,
  payload: T,
}

enum StorageError { HashMismatch, StaleFencingToken, SchemaIncompatible, QuotaExceeded }

Ownership semantics: task leases owned by task-service; revision payloads immutable once written; object references content-addressed (I9); search projections rebuildable (§29, FM-5).

Concurrency semantics: optimistic concurrency for revisions (I1); pessimistic fencing-token leases for assignments (I3, I12); snapshot isolation for exports (I4).

Compatibility guarantees: Protobuf field additions are backward compatible (ADR-13); storage migrations are append-only; event versioning is explicit via schema_version (I10, P8).

17. Phase 5 — Review, QA & Consensus

17.1 Objectives

Implement review-service: golden-set validation, consensus aggregation, inter-annotator agreement metrics, and reviewer escalation — the enforcement point for I8 and I11.

17.2 Detailed Implementation Steps

  • Implement golden-dataset validation against a curated reference set.
  • Implement consensus scoring (src/consensus.rs) via Dawid-Skene EM (Dawid & Skene 1979, §5; ADR-16), modeling per-annotator error rates rather than equal-weight votes.
  • Implement a majority-vote fallback path for the <3-annotator regime where EM has too few data points to converge (ADR-16 "when rejected wins" column; FM-8).
  • Implement agreement metrics (src/agreement.rs): Cohen's kappa for pairwise agreement (Cohen 1960) and Krippendorff's alpha for multi-annotator/mixed-measurement-level agreement (Krippendorff 1980) — ADR-18.
  • Optionally ingest Snorkel-style labeling-function votes (Ratner et al. 2017, ADR-17) as additional weak-supervision sources into the same ConsensusRecord.raw_votes (§11), each sandboxed per T11.
  • Implement reviewer escalation workflows (src/escalation.rs) for below-threshold agreement.
  • Sign each ReviewDecision into the chain (prior_hash + signature, §11) — enforces I8.

17.3 Deliverable

A reproducible consensus and QA subsystem whose aggregated label and agreement score are deterministic for a fixed vote set and algorithm version (I11).

17.4 Acceptance Criteria

  • Agreement metrics reproducible: recomputing kappa/alpha from stored raw votes matches the persisted agreement_score to 1e-6 (I11).
  • Escalation replay deterministic against fixtures/review/escalation_replay.json.
  • Review-transition p95 latency < 300 ms (M2).
  • EM convergence validated on a fixture with known per-annotator error rates within 2% of ground truth.

17.5 Conformance Fixtures

  • fixtures/review/consensus_em_convergence.json
  • fixtures/review/kappa_alpha_reference.json
  • fixtures/review/escalation_replay.json

17.6 Pitfalls

  • Treating raw percent agreement as a quality signal on a skewed label distribution — inflated by chance agreement (ADR-18, MM6).
  • Feeding an adversarial or malfunctioning labeling function's votes into consensus unsandboxed (T11).

17.7 Performance Concerns

  • EM iteration cost scaling with raw_votes cardinality per task; bounded iteration count with a convergence-tolerance cutoff.

17.8 Edge Cases

  • All annotators agree but on a value later shown wrong by a golden-set check (systemic bias, not a disagreement problem — routed to escalation regardless of agreement score).
  • A reviewer's chain signature fails verification after a key-rotation event (I8).

17.9 Failure Analysis

Consensus non-convergence (FM-8) triggers the majority-vote fallback automatically below the annotator-count threshold and escalates to a senior reviewer above it.

17.10 Operational Notes

Expose reviewer-throughput and consensus_score_variance metrics; a variance spike without a matching deploy indicates either adversarial annotators or a labeling-function regression.

25. Compatibility & Versioning

Wire protocols versioned via schema_version on every EventEnvelope (§11); Protobuf field additions are backward compatible (ADR-13); a producer's schema registration is rejected before rollout if it is not backward-compatible with the last registered version (I10, FM-10).

Storage/schema evolution: migrations are append-only and, where feasible, reversible (expand-contract pattern, P8); a migration that cannot be made reversible requires an explicit sign-off recorded in docs/adr/.

API stability: OpenAPI 3.1 contract (§5) versioned by SemVer; backward compatibility maintained for one major version.

Rolling-upgrade guarantees: supported within N-1 versions; an upgrade spanning N-2 is rejected (§21.8 edge case) because dual-write validation cannot be proven safe across two incompatible schema generations simultaneously.

Deprecation policy: 90-day minimum notice; compatibility shims maintained through the deprecation window; every deprecation is announced via CHANGELOG.md and tracked until its shim is removed.

Event-schema evolution: strictly append-only (new optional fields only); a breaking change requires a new event type, not a mutation of an existing one — this is what keeps I10 provable by a registry compatibility check rather than by convention.

29. Scalability Analysis

Constant regardless of scale (O(1) amortized): permission-cache lookup (auth-service, once warm); fencing-token compare-and-swap per lease claim; hash-chain append per audit record.

Grows with scale: metadata-DB row count (O(n) in asset/task/revision count) — the named bottleneck first to hit a ceiling (below); Kafka partition count (must grow with sustained event throughput, §32); OpenSearch shard count (grows with document count, tuned to avoid the shard-imbalance ceiling below).

Named bottlenecks, in the order they are hit as load scales past the §4 targets:

  1. PostgreSQL metadata hotspots — a single hot partition (e.g. one enormous project) can saturate one shard before the cluster-wide budget is reached; mitigated by UUIDv7 key distribution (ADR-21) and per-org partitioning.
  2. Kafka partition skew — an uneven aggregate_id distribution concentrates load on few partitions; mitigated by partition-count sized to worst-case single-tenant throughput, not average.
  3. Websocket fanout pressure — a single high-collaboration "room" concentrates fanout onto one realtime-gateway pod (FM-7); mitigated by consistent-hash rebalancing.
  4. Search shard imbalance — a single tenant's document volume outgrows its shard's target size; mitigated by tenant-aware shard routing.

Horizontal scaling: stateless API layers (api-gateway, auth-service) scale by pod count alone; partition-aware workers (task-service consumers) scale by Kafka partition count; sharded event consumers scale search-service/audit-service ingestion independently of the metadata DB.

Vertical scaling: NUMA-aware queue pinning for image-decode pipelines (§4); dedicated ingest memory pools for dataset-service multipart handling.

Practical ceiling and levers beyond it: the PostgreSQL metadata DB is the first hard ceiling (bottleneck 1, above); the lever beyond it is horizontal sharding of the metadata DB by organization_id — deferred until a single-org's metadata volume alone threatens the ceiling, since sharding trades away single-transaction cross-entity queries (§8 hierarchy) for throughput.

30. Mental Models & First Principles

MM1 — Every distributed lease is a bet against a clock you don't control. Predicts that lease systems need fencing tokens, not just TTLs. Bug class without it: split-brain writes after a paused worker resumes past its TTL. Resolving §15 / I12 / I3.

MM2 — Consensus is a model of annotators, not a vote count. Predicts Dawid-Skene beats majority vote once annotators have skewed skill/error rates. Bug class without it: systematically wrong labels from a confidently-wrong majority. Resolving §17 / ADR-16.

MM3 — An event log is the database; the tables are just a cache of it. Predicts that any projection (search index, analytics view) must be fully rebuildable from the log. Bug class without it: an unrebuildable search index after drift, with no recovery path. Resolving §8 / §29 / FM-5.

MM4 — Backpressure delayed is backpressure denied. Predicts that admission control placed downstream of the true bottleneck always arrives too late to prevent damage. Bug class without it: OOM at annotation-service instead of a clean 429 at api-gateway. Resolving §4 / P2.

MM5 — Tenant isolation is a database property, not an application habit. Predicts that app-layer-only isolation eventually leaks under one missed WHERE clause. Bug class without it: a cross-tenant read via a forgotten filter. Resolving §7 / I5 / T3.

MM6 — Agreement metrics must correct for chance before they mean anything. Predicts raw percent agreement overstates quality on a skewed label distribution. Bug class without it: shipping a "95% agreement" golden set that is actually near chance. Resolving §17 / ADR-18.

MM7 — A schema is a contract with your own future deploys. Predicts breaking changes surface as consumer crashes weeks later, not at commit time. Bug class without it: a silent incompatible field removal breaking a downstream export job. Resolving §11 / I10 / P8.

MM8 — Active learning only helps if the score is reproducible. Predicts that an unlogged model score makes audits and regressions indistinguishable. Bug class without it: "why was this asset prioritized" has no answer six months later. Resolving §19 / I14.

32. Back-of-Envelope Capacity Model

  1. Total object-storage footprint. 5,000,000,000 assets (§4) × ~2 MB average (mixed image/video/document) ≈ 10 PB raw. With storage amplification < 2.7x (§4, replicas + indexes): 10 PB × 2.7 ≈ 27 PB provisioned.
  2. Event-bus steady-state throughput. 50,000 concurrent annotators (§4) × 1 autosave event / 3 s ≈ 16,667 events/s. At ~1 KB/event: 16,667 × 1 KB ≈ 16.7 MB/s steady; with 5x headroom for burst: ~85 MB/s provisioned Kafka throughput.
  3. Websocket fanout bandwidth (baseline). 120,000 sessions (§4) × 1 presence heartbeat / 5 s × 200 bytes ≈ 4.8 MB/s baseline. With an average 20-collaborator fanout multiplier per shared "room": up to ~96 MB/s peak fanout (M11 latency target must hold at this volume).
  4. Postgres connection budget. Assume ~200 stateless API/worker pods × 20 connections each = 4,000 connections — exceeds Postgres's practical per-instance connection ceiling, forcing a pooling layer (pgbouncer) ahead of the metadata DB (informs §29 bottleneck 1).
  5. Audit-log growth per year. 50,000 annotators × ~5 audit events/min × 60 × 24 × 365 min/yr ≈ 131 billion events/year. At ~300 bytes/event: ≈ 39 TB/year appended; × 7-year retention (§4) ⇒ ~275 TB retained for audit alone.
  6. Search-index absorption capacity. Matching the annotation-submit rate (~16,667/s from step 2) against the < 10 s indexing-lag target (M5) means the index pipeline must sustain a burst queue of up to ~166,700 documents before backpressure engages.
  7. Worker memory headroom. 4 GB ceiling per worker (§4); a decode-pipeline peak of ~50 MB per image tile × 8 concurrent tiles = 400 MB, leaving ~3.6 GB headroom for buffers, runtime, and connection pools — validates P7's "provable, not empirical" requirement.
  8. File-descriptor budget per realtime-gateway pod. 200,000 FD budget/node (§4); 120,000 websocket sessions spread across ~40 realtime-gateway pods ⇒ 3,000 sessions/pod; at ~3 FDs/session (socket + timer + buffer) ⇒ ~9,000 FDs/pod, well under budget.
  9. Cold-recovery RTO plausibility check. Restoring 27 PB (step 1) from a cross-region replica at a realistic inter-region link (~10 Gbps ≈ 1.25 GB/s) would take > 200 days for a full data restore — incompatible with the < 30 min RTO target (§4, M8). This forces the design conclusion in Phase 9 (§21.7): recovery must be metadata-first with lazy asset rehydration, not a full-data replay.
  10. Lease-conflict budget. At 50,000 concurrent leases and the < 0.001% conflict target (M10): 50,000 × 0.00001 = ≤ 0.5 conflicts/sec tolerated at steady state — this bounds how much fencing-token CAS overhead (ADR-20) the system can absorb before M10 is at risk.

34. Alternative Architectures (Roads Not Taken)

1. CRDT-based collaborative annotation (no central lease).

Show the original text diagram
Client A --\                    /-- Client B
            \                  /
             v                v
        [Local CRDT replica] [Local CRDT replica]
             \                  /
              \--- merge <----/    (no central authority)

Regime where it wins: real-time multi-cursor document editing with no single-writer requirement. Real system: Figma's multiplayer engine / Automerge-based editors. Rejected because: structured geometric annotations (polygon vertex conflicts, mask edits) have no clean merge semantics, and audit chain-of-custody (I8) needs one authoritative revision writer per task, not a converged-but-untraceable merge result.

2. Fully serverless / FaaS event-driven architecture.

Show the original text diagram
API Gateway -> [Lambda: on-task-event] -> [Lambda: on-review-event] -> ...

Regime where it wins: bursty, low-baseline-load workloads with no sustained connection requirement. Real system: serverless ETL patterns on AWS Lambda + Step Functions. Rejected because: sustaining 50,000 concurrent websocket sessions (§4) needs long-lived stateful connections FaaS platforms don't hold efficiently, and cold-start tail latency conflicts with the <120ms save target (M1).

3. Blockchain / DLT-based immutable audit ledger.

Show the original text diagram
[Validator 1] --consensus--> [Validator 2] --consensus--> [Validator 3]
       \_______________ hash-chained block ______________/

Regime where it wins: multi-party trustless environments (consortium data-sharing across independent organizations). Real system: Hyperledger Fabric-style permissioned ledgers. Rejected because: a single-org audit trail needs no Byzantine-fault-tolerant consensus — an append-only, hash-chained Postgres/Kafka log (I2) gives equivalent tamper-evidence at a fraction of the latency and operational cost.

4. Monolithic single-binary deployment.

Show the original text diagram
+----------------------------------------------+
| single Rust binary: gateway+auth+task+annot.  |
|  (internal module boundaries, one process)    |
+----------------------------------------------+

Regime where it wins: small teams, <100 concurrent annotators, single-tenant. Real system: early CVAT deployments (single Django app, §5). Rejected because: the §4 scale target (50,000 annotators, multi-tenant, multi-region) needs independent scaling and failure domains per service — a monolith couples search-service's load to annotation-service's availability, violating P10.
