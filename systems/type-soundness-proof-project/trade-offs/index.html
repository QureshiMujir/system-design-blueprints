Decisions (§9) · 25 ADRs

ADR-01

Implementation language + edition

Chosen

Rust, edition 2021, MSRV 1.78

Rejected

OCaml/Haskell; C/C++; reuse Coq/Lean/Agda

When the rejected choice is right

OCaml/Haskell wins when the object language is itself functional and the metatheory is a direct GADT or data-type proof that can be extracted to compiled code (e.g., a certified compiler like CompCert). Reusing Coq/Lean wins when the team's goal is the fastest-to-formal-proof path and "from-scratch" is not a learning objective.

Why: Kernel is a hot, recursion-heavy checker where one soundness bug invalidates every proof → memory safety + exhaustive match on Term/Type/KTerm/Derivation is decisive. de Bruijn → usize; shift/subst total fns the borrow checker keeps honest. Haskell laziness complicates the strict kernel; C/C++ unsafe term graphs in the TCB unacceptable; reusing a prover defeats the from-scratch goal (that is #280). 1.78 = floor for let-else, OnceLock, edition-2021 captures; no nightly in the build.

ADR-02

Workspace decomposition

Chosen

Seven crates: tsp-syntax, tsp-term, tsp-rules, tsp-kernel, tsp-meta, tsp-test, tsp-cli

Rejected

One monolithic crate; two crates (lib+bin); fewer merged crates (e.g. fold tsp-meta into tsp-kernel)

When the rejected choice is right

A monolith wins when the whole codebase is trusted equally (no trust boundary to enforce) and compile times matter more than auditability — e.g., a research prototype where every line is reviewed before any commit. Fewer crates win when the team is one person and the proof layer is small enough to fold into the kernel without exceeding the LoC budget.

Why: Crate boundaries make the TCB auditable: tsp-kernel compiles with zero deps on tsp-meta/tsp-test/tsp-cli, so "what must be trusted" = one crate. Dependency DAG cli → {meta,test} → {rules,kernel} → {term,syntax} (kernel depends only on core/alloc). Monolith hides the trust boundary; merging meta into kernel would let proof-construction code touch the checker's internals.

ADR-03

Object-term binding representation

Chosen

de Bruijn indices (Var(usize)); shift(t,d,cutoff), subst(t,j,s), structural alpha_eq

Rejected

Named variables + capture-avoiding rename; locally-nameless (named free / de Bruijn bound); HOAS / PHOAS; co-de-Bruijn

When the rejected choice is right

Locally-nameless wins for mechanized System F-sub metatheory (POPLmark) where human-readable proofs matter and the open/close overhead is justified by proof ergonomics. HOAS/PHOAS wins when the meta-language is a dependently-typed proof assistant (Coq, Agda) and α-renaming is handled by the host binder — irrelevant in a standalone Rust kernel. Named variables win for a pedagogical interpreter where variable names are the primary debugging surface.

Why: alpha-equivalence becomes structural (alpha_eq = == on the tree) → no rename, no freshness oracle, no capture by construction. Substitution lemma proof then mirrors tsp-term::subst/shift line-for-line — the crux invariant (ADR-12). Named binding needs gensym + capture checks (subtle, untestable boundary). Locally-nameless adds a second sort of variable + open/close bureaucracy for no metatheory payoff at STLC scale. HOAS leaks the meta-binder into the object language and blocks alpha_eq as data.

ADR-04

Proof discipline of the kernel

Chosen

Proof-term CHECKING — a lambda-Pi / LF core that type-checks a supplied proof term (infer_type/check_type)

Rejected

Tactic-based interactive proof; automated proof SEARCH; SMT-backed checking

When the rejected choice is right

Tactic-based proof wins when the team's bottleneck is authoring proof terms for large inductive proofs (e.g., Preservation over a 10-former language with 50+ cases) — a tactic engine reduces per-case boilerplate by generating proof terms automatically. SMT-backed checking wins when the propositions are quantifier-free arithmetic or bit-vector predicates where automated search is complete and the prover is trusted independently.

Why: Curry-Howard: Prop = KType, Proof = KTerm; "valid" ⇔ check_type(ctx, term, goal) accepts. Checking is small, total, decidable, and auditable; search/tactics need a large engine in the TCB and are explicit NON-GOALS (#280 = interactive prover, #278 = proof search/SMT). The framework's deliverable is checked metatheory, not discovered metatheory.

ADR-05

Logical framework / kernel calculus

Chosen

lambda-Pi (LF, à la Edinburgh LF / LambdaPi): KTerm = Var|Sort|Pi|Lam|App, Sort = Type|Kind, Type : Kind

Rejected

Calculus of (Inductive) Constructions; pure System F-omega; first-order logic + sequent rules; HOL

When the rejected choice is right

CIC (Coq's kernel) wins when the object language requires strong eliminators for data types (e.g., induction over natural numbers inside the proof term), or when the metatheory includes impredicative Prop. System F-omega wins when the metatheory stays purely prenex-polymorphic and no dependent types are needed. HOL wins when automation is the priority and the judgments do not need to internalize derivation trees.

Why: lambda-Pi is the minimal dependently-typed core that expresses judgments-as-types and Pi (= dependent implication / forall) — exactly what STLC metatheory needs (Harper-Honsell-Plotkin, Twelf, LambdaPi tutorial). CIC is far larger than the proof obligations warrant (bigger TCB). FOL/HOL can't internalize derivation trees as terms. Two-universe Type:Kind (no Kind:Kind) keeps it predicative-enough and consistent for this use; no Kind:Kind (Girard's paradox) — locked.

ADR-06

Trusted Computing Base size + isolation

Chosen

TCB = tsp-kernel only, target ≤ 1500 LoC (stretch ≤ 1000), no external deps beyond core/alloc

Rejected

Trust the whole workspace; trust tsp-rules (executable checker) as authoritative; allow std in the kernel

When the rejected choice is right

Trusting the whole workspace wins only when every line of code is formally verified or manually reviewed at the same rigor as the kernel — a realistic posture for a solo researcher but not for a team. Allowing std in the kernel wins when the kernel must perform I/O (e.g., a kernel-as-a-service with a verified transport layer). Trusting tsp-rules wins when the executable checker has itself been machine-verified (e.g., via a separate Coq proof of infer's soundness).

Why: Soundness of the entire project rests on the kernel: GRAVEST failure = kernel accepts an ill-typed KTerm (silently validates a false theorem). Smaller + dependency-free ⇒ humanly auditable + fuzzable (ADR-19). tsp-rules::infer is convenience, NOT trusted (a bug there yields a stuck checker, not a false theorem). no_std + alloc forbids accidental I/O / clock / RNG inside the trust boundary.

ADR-07

Kernel checking algorithm

Chosen

Bidirectional infer_type / check_type

Rejected

Full type inference (Hindley-Milner / unification-based); checking-only (no infer mode); elaboration with metavariables

When the rejected choice is right

Elaboration with metavariables wins when the proof language has a human-facing surface syntax where explicit annotations are ergonomically unacceptable (e.g., a user-facing proof assistant like Lean 4, where implicit arguments drive the experience). Full inference wins when the language is simply-typed and HM is complete — relevant for the object language's infer in tsp-rules, but not for the kernel's dependent Pi-types.

Why: Bidirectional is the standard minimal-TCB design (LambdaPi tutorial): infer synthesizes for eliminators/vars, check for introductions, switching at the annotation/App boundary. Full inference for dependent types is undecidable and needs unification + metavariables = large, error-prone TCB. Annotations on Lam/Pi are cheap (proof terms are generated by tsp-meta, not hand-written), so demanding them costs nothing and shrinks the kernel.

ADR-08

Definitional equality / conversion

Chosen

equal(ctx,a,b) via whnf — beta + alpha; eta optional (feature-gated eta)

Rejected

Full normalization-by-evaluation (NbE) then syntactic ==; untyped beta only, no whnf sharing; eta always-on

When the rejected choice is right

NbE wins when the kernel must check intensional type equality under function type in a system with large proofs of functional extensionality — the canonical NbE advantage. Eta-always-on wins when the object language encodes everything via function types and proof terms regularly produce eta-expanded forms (common in the CIC tradition). Untyped beta only wins for a checked-proof pipeline where all proof terms are already in beta-normal form on entry.

Why: Conversion only needs enough reduction to compare heads, so whnf-then-recurse-on-spine is minimal and lazy (avoids normalizing under unreached binders). Eta makes equal heavier and its termination argument subtler → default OFF, behind eta feature, enabled only where a proof needs it; documented in the TCB audit. Full NbE is more machinery in the TCB than STLC metatheory conversions require. Conversion is part of trust — kept tight.

ADR-09

Judgment encoding into the kernel

Chosen

Shallow LF-style judgments-as-types (object Has-Type/Step as kernel inductive signatures + eliminators)

Rejected

Deep embedding (object syntax/derivations as a kernel Inductive datatype with a well_formed predicate); axiomatic/postulated lemmas

When the rejected choice is right

Deep embedding wins when the object language is itself a dependently-typed language and the metatheory requires induction over a data type (not just a type family) — the standard choice in Coq developments for languages with binders (e.g., PLFA). Axiomatic/postulated lemmas win in a prototype phase where proof-term authoring is deferred and the goal is to test whether the statement is the right one before committing to a full proof.

Why: LF tradition: an object judgment is a type family, an inference Rule is a constant, a Derivation is a term — adequacy is immediate and the kernel checks tree validity for free (Twelf-style). Deep embedding duplicates Term/Derivation inside the kernel and forces a re-proved check_deriv in the TCB. Axioms are forbidden: every lemma is a checked term, never postulate (would defeat soundness).

ADR-10

Executable artifacts beside the relations

Chosen

Ship executable infer/step (tsp-rules) AND check_deriv next to the inductive Rules

Rejected

Relations only (no executable checker); executable checker as the sole authority (no proofs)

When the rejected choice is right

Relations-only wins when the project is purely a formal proof development with no user-facing CLI (e.g., a Coq contribution to a proof library). Executable-only wins when fast development iteration is the priority and the team plans to add proofs later — acceptable for a prototype, not for the Phase 13 "done" gate.

Why: Executable infer/step/check_deriv give an oracle to test against (Phase 3/4) and feed tsp-test's generator, but they are explicitly NON-trusted (ADR-06): correctness of the metatheory comes from tsp-meta proofs, not from infer. Relations-only loses the testable oracle + the CLI typecheck/step; checker-only loses the machine-checked guarantee. We keep both and pin which is authoritative.

ADR-11

Reduction-order + semantics style

Chosen

Small-step, call-by-value, evaluation-context / congruence formulation; step(e) -> Option<Term> (None = value/stuck)

Rejected

Big-step / natural semantics; small-step call-by-name; abstract machine (CEK/CK)

When the rejected choice is right

Big-step wins for a language where type safety is stated via logical-relation termination arguments (Girard's method for System F) rather than the progress+preservation decomposition. Call-by-name wins for a lazy language where step models Haskell/GHC semantics. An abstract machine (CEK) wins when the implementation target is an efficient bytecode interpreter and the metatheory is proved separately via a certified compiler correctness argument.

Why: Small-step is the form progress + preservation are stated/proved over (TAPL, Software Foundations); call-by-value matches the references stretch (a store needs CBV order) and canonical-forms reasoning. Evaluation contexts factor congruence cleanly and prep the Redex layer (ADR-16). Big-step can't state progress (no "stuck" notion); CBN complicates the references extension; an abstract machine is more state than the metatheory needs. Determinism of step proved (optional, Phase 4).

ADR-12

shift/subst as total functions

Chosen

shift/subst are pure, total, panic-free fns; the substitution lemma proof mirrors them exactly

Rejected

Partial subst returning Result; in-place mutation; memoized/interned term sharing in v1

When the rejected choice is right

In-place mutation wins when subst is the inner loop of an efficient kernel that must avoid allocation pressure (e.g., a production type-inference engine processing millions of terms per second) and all subst call sites have been proved safe by a prior analysis. Memoized sharing wins at Phase 13 benchmark time, after the correctness gate, once criterion data shows allocation pressure is the bottleneck — exactly the ADR-21 sequencing.

Why: The substitution lemma (Gamma,x:S ⊢ e:T ∧ Gamma ⊢ v:S ⇒ Gamma ⊢ [v/x]e:T) is the crux; an off-by-one in shift breaks it (and only it). Totality means the proof and the code share one recursion structure → a tsp-test differential check can pin them together. Result-subst would force error-handling into the lemma statement. Interning is a later optimization (ADR-21) gated on benchmarks, never in v1 (sharing bugs in the TCB-adjacent core are not worth it early).

ADR-13

Assurance model

Chosen

Dual guard: kernel-checked proofs (tsp-meta) + Redex-style property tests (tsp-test)

Rejected

Proofs only; tests only; proofs + manual review only

When the rejected choice is right

Proofs-only wins when the proof development is done in a full proof assistant where the executable checker is extracted from the proof (CompCert model) — then the checker and the proof are the same artifact. Tests-only wins for a language design phase where the calculus is changing rapidly and investing in full proofs would be invalidated each iteration.

Why: Proofs give certainty for the modeled language; randomized/exhaustive tests give fast falsification + confidence the model matches the executable infer/step. A correct language ⇒ tester only Pass; a broken rule MUST be caught by BOTH (kernel: proof no longer checks; tester: shrunk counterexample) — the dual-guard contract (ADR-14). Tests catch modeling bugs proofs can't see (e.g. encoder ≠ infer); proofs catch what finite testing misses. Neither alone is sufficient.

ADR-14

Broken-rule demonstration as a first-class artifact

Chosen

A deliberately unsound typing rule is a checked-in fixture; CI asserts kernel proof FAILS and tsp-test returns a shrunk CounterExample

Rejected

Document the failure only; only the tester demonstrates it; only the kernel demonstrates it

When the rejected choice is right

Documentation-only wins when the unsoundness is too subtle for a finite tester to find in the size budget (e.g., a bug that only appears at term depth ≥ 1000) and the proof failure is the only practical detector. Tester-only wins for a rule that is computationally obvious but formally complex to disprove — a useful intermediate state during proof development.

Why: Makes the dual guard executable and regression-proof (Phase 12): a "negative" conformance test that both pillars react. The proof must fail to type-check (not error spuriously) and the tester must produce a minimal witness via the Shrinker. Doc-only / single-pillar can't prove the guards actually fire; this is the load-bearing demonstration that the framework detects unsoundness.

ADR-15

Generator / shrinker design

Chosen

Type-directed, size-bounded generator of well-typed Terms + a structural Shrinker (TestResult = Pass(u64)|CounterExample(Term, Witness))

Rejected

Untyped term generator + filter-by-typecheck; grammar-only random terms; no shrinker

When the rejected choice is right

An untyped generator wins when the soundness property being tested is syntactic (e.g., parser round-trip, pretty-printer correctness) and any term — typed or not — is a valid input. Grammar-only terms win for a surface-syntax fuzzer targeting parse robustness, not semantic properties. No-shrinker wins only in a continuous fuzzing regime where a crash corpus is replayed and minimized offline by an independent tool.

Why: Type-directed generation (build a term for a goal type) yields a high density of well-typed terms (filtering untyped terms is exponentially wasteful at depth). Size bound caps blow-up + makes runs reproducible (seeded). The Shrinker reduces a failing Term to a minimal counterexample (smaller subterms / constructor collapse), and Witness records which property failed (progress vs preservation) + the offending step — essential for diagnosing the broken rule (ADR-14).

ADR-16

Property semantics tested

Chosen

Exactly the two soundness properties: check_progress(e) (closed well-typed ⇒ value ∨ steps) and check_preservation(e) (well-typed ∧ step ⇒ same type)

Rejected

Ad-hoc invariants; round-trip parse/print only; confluence/normalization

When the rejected choice is right

Confluence testing wins when the operational semantics is nondeterministic (e.g., concurrent/interleaved semantics) and the safety property is confluence of reduction paths rather than single-step preservation. Normalization testing wins when the language is known terminating and the goal is measuring reduction cost distributions rather than soundness.

Why: These are the theorems tsp-meta proves, so the tester checks the same statements ⇒ direct cross-validation (Phase 11: tester and proofs agree on the sound language). Round-trip/confluence are off-target (confluence/normalization not claimed; STLC normalizes but it is a NON-GOAL to prove here). Tester reuses the executable infer/step as oracle (ADR-10).

ADR-17

Error-handling contract

Chosen

Result<_, KernelError|TypeError|DerivError|ParseError> everywhere; kernel NEVER panics and NEVER accepts an ill-typed term; #![deny(clippy::unwrap_used, clippy::panic, clippy::expect_used)] in tsp-kernel

Rejected

panic!/unwrap on malformed input; Option without error reason; exceptions-as-control-flow

When the rejected choice is right

Panic-on-invalid wins in a setting where all inputs are pre-validated by a trusted layer before reaching the kernel (e.g., an embedded RTOS where a panic triggers a safe system reboot rather than arbitrary behavior). Option-only wins for a minimal pedagogical implementation where error messages are irrelevant and the focus is the core algorithm.

Why: Two locked kernel invariants: no panic on adversarial KTerm (a panic = DoS, found by fuzzing ADR-19) and no false accept (the soundness invariant). Errors carry a kind (ParseErrorKind::{UnexpectedToken,UnknownSort,BadBinder,MalformedRule}, KernelError, …) for diagnostics + conformance assertions. The clippy denies make "the kernel cannot unwrap" a compile-time guarantee, not a code-review convention.

ADR-18

Reference oracle / ground truth

Chosen

Pin behavior to TAPL + Software Foundations: STLC rules, progress/preservation statements, references + System F as in TAPL; POPLmark as a scope yardstick

Rejected

Invent bespoke rules; derive semantics ad hoc; match one textbook loosely

When the rejected choice is right

Bespoke rules win when the object language is a novel calculus (e.g., a new effect system or capability type system) with no prior mechanization — the "from-scratch metatheory" use case where the project is the reference, not a downstream consumer of existing literature.

Why: The metatheory must be recognizably correct: rule shapes, the canonical-forms lemma, and the progress/preservation statements follow TAPL chs. 8–9, 13, 23 and Software Foundations' mechanized versions verbatim, so reviewers can diff against the literature. POPLmark (System F-sub binding/metatheory) sets the adequacy bar for the binding representation (ADR-03). Bespoke rules would make "is this the right theorem?" unanswerable.

ADR-19

Fuzzing

Chosen

cargo-fuzz (libFuzzer) targets on tsp-kernel (infer_type, whnf, equal) + tsp-syntax parser; assert no panic & no false-accept; corpus checked in

Rejected

No fuzzing; only unit tests; AFL (extra toolchain)

When the rejected choice is right

AFL wins when the target runs in a language/environment where cargo-fuzz/libFuzzer integration is unavailable (e.g., a kernel module, a C extension, or a Rust no_std binary that cannot link libFuzzer's runtime). No-fuzzing wins only for a short-lived prototype where the threat model does not include adversarial inputs and the deployment is air-gapped.

Why: The two kernel invariants (ADR-17) are exactly fuzzing targets: feed arbitrary/structured KTerms and assert never panics and never accepts ill-typed (cross-checked: if infer_type returns Ok(ty) then check_type(_, t, ty) must also accept — internal consistency). cargo-fuzz is the idiomatic Rust harness (no extra toolchain vs AFL). Differential fuzzing also pins infer(rules) vs the kernel encoding. Phase 13 gate.

ADR-20

Benchmarking

Chosen

criterion micro-benchmarks: kernel proof-check time, whnf/equal cost, proof-term size, tsp-test throughput; tracked vs targets

Rejected

#[bench]/nightly; ad-hoc Instant timing; no benchmarks

When the rejected choice is right

#[bench]/nightly wins in a development environment where nightly Rust is already required (e.g., a project using other nightly features) and the overhead of pulling in criterion is undesirable. Ad-hoc Instant timing wins for a one-off profiling session where reproducibility across runs is irrelevant and a single wall-clock sample is the only goal.

Why: criterion gives stable statistics on stable Rust (no nightly, per ADR-01) with regression detection. Locked targets (Phase 13): kernel check of the STLC preservation+progress proof < 50 ms; whnf amortized O(spine); proof-term size for STLC soundness ≤ ~5k KTerm nodes; tsp-test ≥ 10k well-typed terms/s; kernel peak memory < 64 MB on the largest checked proof. Numbers are the "done" gate, not vanity.

ADR-21

Performance-optimization policy

Chosen

Correctness-first: no interning, no NbE, no caching in v1; optimizations are post-benchmark + must not enlarge the TCB

Rejected

Premature interning/hash-consing of KTerm; eager full normalization caches; arena allocation in the kernel from day 1

When the rejected choice is right

Hash-consing from day 1 wins when the performance target is known in advance to be unachievable without sharing (e.g., a production LF kernel checking million-node proof terms in a CI pipeline), and the hash-consing layer is itself formally verified or small enough to audit. Arena allocation wins for a kernel embedded in a time-critical real-time system where heap fragmentation is a safety concern.

Why: A sharing/caching bug inside the TCB can cause a false accept (ADR-06) — far costlier than slowness. So Box-based trees + naive whnf ship first; any optimization (e.g. interned KTerm, memoized whnf) is justified by a criterion regression (ADR-20) and re-fuzzed (ADR-19). The kernel stays small/auditable over fast.

ADR-22

Dependency policy (esp. the TCB)

Chosen

tsp-kernel/tsp-term/tsp-syntax = no_std + alloc, ZERO external crates; non-TCB crates: dev-deps only (criterion, proptest-style, cargo-fuzz); strict cargo-deny (licenses, advisories, bans)

Rejected

Liberal use of serde, parser/proptest crates as normal deps; macro-heavy frameworks; FFI

When the rejected choice is right

Liberal dependencies win when the kernel is already independently verified (e.g., by a proof of its Rust code in Verus or Creusot), so additional crate dependencies cannot introduce undetected unsoundness. serde as a normal dep wins when the primary interface to the kernel is a persistent proof store that must serialize/deserialize KTerm values across process boundaries.

Why: Every dependency in the TCB is code you must trust unsoundly-or-not → the kernel takes none. Outside the TCB, test/bench/fuzz deps are dev-dependencies (never linked into tsp release / never into tsp-kernel). cargo-deny in CI bans new transitive deps, denies copyleft, fails on RUSTSEC advisories. Keeps the audit surface and supply-chain risk minimal.

ADR-23

CI pipeline

Chosen

GitHub Actions: fmt --check → clippy -D warnings → cargo test --workspace → conformance suite → cargo-deny → fuzz-smoke (bounded) → criterion regression; matrix {MSRV 1.78, stable}; Dockerfile-pinned toolchain

Rejected

Local-only checks; single-toolchain CI; no conformance/fuzz in CI

When the rejected choice is right

Local-only checks win in an offline or air-gapped environment where CI infrastructure is unavailable. Single-toolchain CI wins for a project with a single consumer who controls both the compiler and the deployment environment and can tolerate manual MSRV verification.

Why: Soundness is a gate, not a hope: CI must run the conformance suite (proofs check; broken variants rejected; tester ⇔ proofs agree — ADR-14/16), a bounded fuzz smoke (regression on the checked-in corpus), and benchmark thresholds. MSRV-vs-stable matrix prevents accidental newer-feature use (ADR-01/24). Dockerfile pins the exact toolchain so the TCB builds bit-reproducibly for audit.

ADR-24

MSRV stability guarantee

Chosen

MSRV 1.78 pinned in rust-toolchain.toml + asserted in CI; bumping MSRV is itself an ADR

Rejected

Track latest stable; allow nightly features; unpinned toolchain

When the rejected choice is right

Tracking latest stable wins when the project depends on a rapidly-evolving standard library API (e.g., a systems crate for a new hardware platform) and MSRV pinning would require maintaining backports. Nightly features win when the project is a Rust compiler plugin or internal tooling that already requires nightly for procedural macros or ABI reasons.

Why: A trusted-base project must build on a fixed, audited compiler; silent MSRV creep changes the compiler the TCB's soundness implicitly relies on. Pinning + a CI MSRV job makes any required-feature bump an explicit, reviewed decision (new ADR), not drift. No nightly ⇒ no feature(...) in the TCB.

ADR-25

Licensing

Chosen

MIT OR Apache-2.0 (dual), per-crate license field + LICENSE-MIT/LICENSE-APACHE at workspace root

Rejected

GPL/AGPL; single MIT; proprietary/unlicensed

When the rejected choice is right

GPL/AGPL wins when the goal is ensuring that all downstream improvements to the kernel are contributed back to the public (e.g., an academic project funded with a requirement that derived tools remain open). Proprietary wins when the kernel is a commercial component of a verified-software toolchain where the trust boundary must be contractually owned rather than community-reviewed.

Why: Rust-ecosystem default dual license = maximal downstream reuse + patent grant (Apache-2.0) while staying permissive (MIT). Copyleft would deter use as a metatheory dependency and is denied by cargo-deny (ADR-22). Education/reference-oriented project (TAPL/Software-Foundations lineage) ⇒ permissive is the right posture.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alternative A — Coq-Based Development (Extract to Rust)

  Coq source (.v files)
      |
      | Coq kernel (CIC, ~15k LoC OCaml)
      v
  Certified Preservation / Progress theorems
      |
      | extraction + FFI bridge
      v
  Rust executable (extracted OCaml or Rust via coq-of-rust)

Rationale for rejection: Extraction bridges the correctness gap via an unverified extractor (Coq's extraction to OCaml is trusted but the OCaml→Rust bridge is not). The project's learning goal — owning every layer from inference rule to kernel check — is defeated if the kernel is Coq's. The resulting "Rust" binary trusts Coq's kernel, OCaml's runtime, and the extraction pass: three trust points instead of one. The TCB cannot be audited by a Rust developer without Coq expertise.

When this wins: A production certified compiler (CompCert style) where the primary value is a deployable, extracted artifact that inherits Coq's formal soundness. Not a learning-oriented proof framework.

Alternative B — Typed-Racket / PLT Redex as the Ground Truth

  PLT Redex model (Racket)
      |--- define-language / reduction-relation (STLC + extensions)
      |--- redex-check (randomized; automatic counterexample search)
      |--- term → term' judgment traces
      v
  Rust reimplementation cross-checked against Redex oracle
  redex-check → finds counterexample → Racket shrinks → outputs Term as S-expr
                                                             |
                                                          FFI/stdio pipe
                                                             |
                                                        Rust tsp-test

Rationale for rejection: PLT Redex gives strong empirical evidence but no formal proof. The project requires a machine-checked proof term, not just "no counterexample found in 10^6 trials." Redex has no notion of a proof kernel or proof term; adding one would require building exactly what this project builds. The cross-language FFI pipe is an audit liability.

When this wins: Rapid language prototyping where rules change daily and the overhead of maintaining a formal proof would invalidate the proof on every iteration. Redex is the right tool for exploring semantics before committing to a formal development.

Alternative C — Logical Relations / Step-Indexed Semantics

  Object language: STLC + extensions
      |
      | define: V_n[[T]] (values safe for n steps at type T)
      |         E_n[[T]] (expressions safe for n steps at type T)
      v
  Fundamental lemma: (|- e:T) → e ∈ E_ω[[T]]   ← machine-check this

Real system embodying it: RustBelt (Jung et al., POPL 2018) proves type-soundness-plus-safety for a realistic subset of Rust using Iris's step-indexed logical relations in Coq — exactly the V_n[[T]]/E_n[[T]] machinery sketched above, scaled to a language with unsafe code and ownership.

Rationale for rejection: Logical relations are the right tool for stronger properties (e.g., parametricity, full abstraction, contextual equivalence) but add significantly more proof obligation for basic progress+preservation. The step-indexed version requires an auxiliary numeric argument in every proof step, bloating proof terms and the kernel. For STLC soundness, the syntactic progress+preservation approach (Wright-Felleisen, P4) is strictly simpler and more auditable. The kernel would need a richer type theory (Sigma types for the step index) or a bespoke induction principle.

When this wins: Soundness proofs for impredicative type systems (System F with full parametricity) or for concurrent/separation-logic extensions where the syntactic approach fails — RustBelt's target (unsafe pointer aliasing, interior mutability) is exactly the regime the syntactic approach cannot reach. Step-indexing is also the right model for blame in gradual typing.

Alternative D — Isabelle/HOL + Nitpick Integration

  Isabelle/HOL theory files
      |--- inductive Has_Type, Step (standard HOL encoding)
      |--- Nitpick (counterexample search; model-finding)
      |--- Isar proof scripts → kernel-checked HOL proofs
      v
  Machine-checked progress + preservation in HOL

Rationale for rejection: HOL has no dependent types — encoding judgments-as-types (the LF/propositions-as-types discipline) requires a shallow embedding and a universe of encodings that adds proof overhead vs. the lambda-Pi approach. Nitpick provides counterexample search analogous to tsp-test but is more powerful (finite model-finding) while being more opaque (the counterexample is a Isabelle model, not a concrete Term). The learning goal of building a lambda-Pi kernel from scratch is not served by delegating to Isabelle's kernel.

When this wins: When the team is already expert in Isabelle/HOL and the object language is first-order (no binding), or when the metatheory requires classical logic (excluded middle) that constructive type theory rejects.
