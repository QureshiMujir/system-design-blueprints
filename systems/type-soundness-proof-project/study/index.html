Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. The substitution lemma's kernel proof term mirrors tsp-term::subst line-for-line. If there is an off-by-one bug in shift that is compensated by an equal off-by-one in the lemma's encoding, can the kernel detect it? What is the only mechanism that would catch such a paired error? (Synthesize §7 INV-7 and §19 Phase 7.)
  2. Why does whnf reduce only to weak-head normal form rather than full normal form, and what would go wrong if equal instead normalized both sides fully before comparing? Give a concrete KTerm where full normalization would change the termination behavior. (Synthesize §17 Phase 5 and Performance Engineering §31.5.)
  3. infer_type and check_type are the trusted functions. progress_statement and preservation_statement are untrusted producers. If preservation_statement returns a KTerm that is the proposition "True" (trivially provable), check_type will accept the proof. What is the only mechanism in this architecture that would catch this vacuity, and in which phase does it fire? (Synthesize §18 Phase 6 and §17 Phase 5; cf. Failure Modes & Recovery F9.)
  4. The dual-guard design says a broken rule must be caught by BOTH guards. Construct a minimal broken typing rule where the PLT-Redex tester would find a counterexample but the kernel proof would continue to typecheck. Explain which architectural invariant this scenario violates and what the fix is. (Synthesize §7 INV-10 and §24 Phase 12.)
  5. The Shrinker must preserve the falsified property (INV-14). Describe a shrinking strategy that could produce a term that no longer fails the property — a "spurious minimization" — and explain which property of the Shrinker's inner loop prevents it. (Synthesize §7 INV-14 and §23 Phase 11.)
  6. tsp-kernel is no_std + alloc. What concrete classes of unsoundness does this constraint prevent beyond the obvious "no I/O"? Name three. (Synthesize §17 Phase 5 and §9 ADR-06/ADR-22; cf. Threat Model T3/T6.)
  7. The whnf step budget is a named constant. If a well-typed preservation proof term genuinely requires more than the budget to normalize (e.g., a deeply nested conversion in System F), what is the observable symptom, what does check_type return, and what is the correct operational response? (Synthesize §17 Phase 5 and §7 INV-2; cf. Threat Model T2.)
  8. Phase 6's encoding uses shallow LF-style judgments-as-types rather than a deep embedding. Explain the adequacy obligation: what must be true of the encoding for check_type's acceptance of a proof term to imply the mathematical statement of preservation? (Synthesize §18 Phase 6 and §5 Required Reading P2.)
  9. The tsp-test generator is type-directed. A naive implementation might call infer on each generated term to verify it. Why would that be an architectural error? What property of the generator makes calling infer as a post-hoc validator unnecessary and detecting if it were ever needed? (Synthesize §23 Phase 11 and §7 INV-9; cf. Mental Models & First Principles MM7.)
  10. equal(ctx, a, b) is called inside check_type. Both take a &Ctx. Explain why equal must receive the same context that check_type is operating under, and give a concrete counterexample where passing an empty context to equal would cause check_type to accept an ill-typed term. (Synthesize §17 Phase 5 and §7 INV-11.)
  11. The kernel uses de Bruijn indices for KTerm variables. tsp-term uses de Bruijn indices for Term variables. These are two independent nameless namespaces. When tsp-meta encodes a Term inside a KTerm proof term, what is the precise invariant that must hold between the two index namespaces, and how would a violation manifest? (Synthesize §18 Phase 6 two-zone de Bruijn and §7 INV-3/INV-4.)
  12. cargo-fuzz asserts two properties on the kernel: (a) no panic, and (b) no false accept. Property (b) requires a notion of "true type" for the fuzz-generated KTerm — but the kernel cannot be queried twice with a different oracle. What is the operationalized version of property (b) actually checking, and why is it a sound approximation? (Synthesize §25 Phase 13 and §9 ADR-19; cf. Threat Model T1.)
  13. The substitution lemma's Lam case requires weakening. Trace exactly which KTerm constructor sequence appears in the proof term for the Lam case of the substitution lemma, naming each K-rule used. (Synthesize §19 Phase 7 and §17 Phase 5 K-rules.)
  14. A reviewer proposes adding a K-Let rule to tsp-kernel to speed up certain proof terms by avoiding explicit beta-substitution. What is the TCB-audit cost of this change, what is the minimal set of re-verification steps required before merging, and is there an alternative that avoids changing the kernel? (Synthesize §17 Phase 5 and Compatibility & Versioning §28.3.)
  15. The conformance suite in Phase 13 asserts that tester verdicts and kernel proofs agree on the sound language. If a new object-language extension (say, references) is added and the tester finds a counterexample while the kernel still accepts the proof, enumerate all possible root causes in order of likelihood, and describe the diagnostic procedure for each. (Synthesize §22 Phase 10 and §25 Phase 13.)
  16. Why is Type:Kind (two universes, not one) the minimum stratification required for the STLC metatheory encoding? What goes wrong with a single-universe Type:Type system (Girard's paradox), and why is the STLC proof development safe from it? (Synthesize §17 Phase 5 and §9 ADR-05.)
  17. The Shrinker outputs a minimal CounterExample(Term, Witness). What property of "minimal" is actually guaranteed — lexicographic size, canonical form, or something else — and how does this property affect the usefulness of the counterexample as a regression fixture? (Synthesize §23 Phase 11 and §7 INV-14.)
  18. Explain why tsp-rules::infer and tsp-kernel::infer_type are both bidirectional but for different reasons. What would happen if tsp-rules::infer used full Hindley-Milner unification instead? (Synthesize §15 Phase 3 and §17 Phase 5.)
  19. The whnf memo is scoped to one check_type invocation and cleared between calls. Why is a global memo (persisting across top-level check_type calls) unsound, and under what conditions would it be safe to extend the memo scope? (Synthesize §17 Phase 5 and Performance Engineering §31.5.)
  20. The tsp binary has four subcommands: check, test, typecheck, step. Of these, exactly one involves the TCB. The others are all untrusted. Precisely characterize which subcommand(s) invoke tsp-kernel and in which call-stack position, and explain what a bug in a non-TCB subcommand can and cannot do to the soundness guarantee. (Synthesize §3 Architectural Overview and §11 Core Schema 11.7.)
  21. The broken-rule conformance fixture is checked into the repository. Describe the exact CI assertion made about this fixture: what does conformance/run.rs assert, what does it call on the kernel, and what does it call on tsp-test? What would a false-positive CI green mean? (Synthesize §24 Phase 12 and §25 Phase 13.)
  22. Phase 13 fuzzes the kernel with cargo-fuzz. What is the relationship between the fuzz corpus and the conformance suite? Could the fuzz harness replace the conformance suite, or vice versa? Justify your answer. (Synthesize §25 Phase 13 and Testing & Verification Strategy §29.5/§29.6.)
  23. The criterion bench CI gate fails on a >15% regression of check_type latency. A new proof term for System F parametricity passes Phase 12 correctness checks but causes a 20% regression in macro_stlc. Is this a blocker? What is the correct escalation path? (Synthesize §24 Phase 12 and Performance Engineering §31.8.)
  24. alpha_eq(a, b) is defined as structural equality on de Bruijn terms and is equivalent to PartialEq. The blueprint says alpha_eq is "kept as a named function" for documentation + property-test purposes. Write a property-based test that could detect a divergence between alpha_eq and the derived PartialEq implementation, and explain under what circumstance such a divergence would indicate a real semantic bug. (Synthesize §13 Phase 1 and §7 INV-4.)
  25. The Phase 7 substitution lemma is described as "the crux." Given only the statement of preservation (subject reduction), derive which lemmas must exist before preservation can be proved, and show the logical dependency chain from shift correctness through to the final preservation_statement that check_type accepts. (Synthesize §19 Phase 7 and §20 Phase 8.)

Mental Models & First Principles

The core intuitions that prevent architectural mistakes. Each model is numbered MM1…MM8 and maps directly to a load-bearing design decision.

MM1 — The TCB Is a Trust Multiplier, Not a Feature Set. Every line inside tsp-kernel multiplies the blast radius of an undetected bug: one unsound line in infer_type silently validates every false theorem the rest of the workspace produces. The kernel is not a place to add features; it is the place where the cost of code is highest. The correct mental model: adding 10 lines to the kernel is architecturally more expensive than adding 1000 lines to tsp-meta. Without this model, a developer adds a convenience rule (e.g. K-Let) straight into the kernel and silently doubles the audit surface. Applied in §17 Phase 5 (kernel budget) and §7 INV-12 (TCB boundary minimality).

MM2 — de Bruijn Indices Are a Substitution-Lemma Contract. Var(n) does not mean "the nth variable in scope" — it means "count n binders outward to find the binding site." The shift(t, d, cutoff) function adjusts free indices that cross a binder boundary. The substitution lemma (Phase 7) is a theorem about subst and shift, so any off-by-one in the cutoff arithmetic produces a provably-false lemma that check_type will accept — the bug is in the statement, not the proof. The mental model: shift is the mathematical dual of a lambda abstraction; every time a binder is introduced, indices must shift to stay consistent. Without it, a developer "fixes" a capture bug by patching subst alone and never notices the lemma statement drifted too. Applied in §13 Phase 1 (shift/subst laws) and §19 Phase 7 (substitution lemma).

MM3 — Propositions Are Types, Proofs Are Programs. A Prop is literally a KType (a KTerm of Sort::Type). A Proof is a KTerm that the kernel accepts at that KType. "Does this proof term typecheck?" and "is this proposition true?" are the same question. The consequence: there is no second logic engine, no separate evaluator — only check_type. Mistaking KTerm for a data structure rather than a proof term is the source of encoding bugs in tsp-meta. Applied in §17 Phase 5 (Curry-Howard mapping) and §18 Phase 6 (judgments-as-types encoding).

MM4 — The Kernel Decides Definitional, Not Propositional, Equality. equal(ctx, a, b) answers "are a and b the same type up to beta-reduction?" — not "are they provably equal by some equational theory." A proof term for preservation does not need to prove that two types are equal; it needs to be at a type where the kernel can compute them equal via whnf. This means proof terms for the substitution lemma grow with the number of beta steps needed to witness the conversion, not with the depth of the equational proof. Without this model, a developer expects equal to discharge arbitrary propositional equalities and is surprised when a semantically-true-but-not-beta-convertible pair is rejected. Applied in §17 Phase 5 (whnf/equal) and §7 INV-11.

MM5 — The Dual Guard Is an Independence Requirement. tsp-meta and tsp-test are not redundant — they check different things. A kernel proof establishes certainty for the modeled language; a PLT-Redex-style test establishes that the executable infer/step is consistent with the model. A bug in the encoding of progress_statement can produce a vacuously provable but semantically empty proposition that the tester will immediately find as a counterexample on the sound language. Agreement between the two guards is stronger evidence than either alone. Without it, a reviewer treats a passing kernel proof alone as sufficient and never runs the falsification suite that would catch an encoder bug. Applied in §7 INV-10 and §24 Phase 12 (broken-rule demonstration).

MM6 — Small-Step Semantics Exposes Stuckness; Big-Step Hides It. Progress says: a well-typed term is either a value or can step. This is only expressible in a small-step formalism because big-step e ⇓ v has no notation for "stuck before reaching a value." Evaluation contexts encode congruence without case-splitting on every intermediate form; adding a new term former means adding one evaluation context clause, not patching every congruence rule. This is why step(e) -> Option<Term> is the right abstraction: None is the stuck-term witness Progress forbids. Without this model, a developer picks big-step semantics and then cannot state progress at all. Applied in §16 Phase 4 (the stepper) and §21 Phase 9 (Progress).

MM7 — Type-Directed Generation Is Asymptotically Superior to Filter-and-Reject. The density of well-typed terms among all terms of size n falls exponentially with n under a naive grammar. At size 20, fewer than 1 in 10^4 random terms may typecheck. Type-directed generation builds a term for a given type by construction, maintaining 100% acceptance rate regardless of size. The mental model: a Generator is a proof-term synthesizer that works in reverse — given a goal Type, produce a Term that infer will accept at that type, without ever calling infer on the result. Without it, a developer builds a generate-and-filter tester that times out before finding a single interesting counterexample. Applied in §23 Phase 11 (Redex-style testing harness) and §7 INV-9.

MM8 — The Substitution Lemma Is the Bottleneck of Every Extension. Every time a new term former is added to the object language (nat, bool, prod, sum, ref, ∀), the substitution lemma gains one new case. Preservation's beta/App case always reduces to "apply the substitution lemma." This means the marginal cost of extending the calculus is dominated by adding one substitution case and one preservation case — O(L) per former, O(L²) total over L formers. Architecturally, the lemma library is the load-bearing layer that must be designed to accommodate extension without touching the TCB. Without this model, a developer underestimates the cost of "just adding references" and is surprised when the substitution lemma's case count explodes. Applied in §19 Phase 7 (substitution lemma) and §22 Phase 10 (language extension).

  Γ(n) = A                  ──────────────── (K-Sort)        Γ ⊢ A : Type    Γ,A ⊢ B : s
  ──────────── (K-Var)      Γ ⊢ Type : Kind                  ─────────────────────────── (K-Pi)
  Γ ⊢ n : A                                                  Γ ⊢ Pi A B : s

  Γ ⊢ A : Type    Γ,A ⊢ b : B            Γ ⊢ t : Pi A B    Γ ⊢ u : A
  ─────────────────────────── (K-Lam)    ────────────────────────────── (K-App)
  Γ ⊢ Lam A b : Pi A B                   Γ ⊢ App t u : [u/0] B

  Γ ⊢ t : A    Γ ⊢ B : s    equal(Γ, A, B)        (* conversion: well-typedness up to definitional equality *)
  ─────────────────────────────────────────── (K-Conv)
  Γ ⊢ t : B

Conversion/normalization obligations (per P6/P8): whnf reduces head beta-redexes to weak-head normal form; equal(Γ,a,b) decides definitional equality (beta; eta optional) — MUST be sound (never equate distinct types) since (K-Conv) is the load-bearing rule whose unsoundness silently validates false theorems.

S5 — Soundness statements (normative targets; W&F P4, B2). tsp-meta must produce KTerm Props matching these, accepted by tsp-kernel:

Progress      ⊢ e : T  ⟹  is_value(e)  ∨  ∃ e'. e ⟶ e'            (closed e)
Preservation  ⊢ e : T  ∧  e ⟶ e'  ⟹  ⊢ e' : T
Soundness     ⊢ e : T  ⟹  e never reaches a stuck non-value      (corollary, Phase 10)
Subst lemma   Γ,x:S ⊢ e:T  ∧  Γ ⊢ v:S  ⟹  Γ ⊢ [v/x]e : T          (crux; mirrors tsp-term::subst)

Conformance: every spec rule above has a corresponding Rule in tsp-rules and a checked clause in tsp-meta; the Phase 12 deliberately broken rule is a single edit to S1/S2/S3 that BOTH the kernel (proof fails) and tsp-test (shrunk CounterExample) must catch.

Glossary · 48 terms · site-wide glossary

Type soundness
"Well-typed terms never get stuck": for closed e with |- e : T, evaluation either diverges or reaches a value, never a stuck term. The top-level theorem; corollary of Progress + Preservation. Stated in tsp-meta, proved as a kernel-checked Proof.
Progress
If |- e : T (closed) then is_value(e) OR ∃ e'. e --> e'. Proof by induction on the typing derivation; uses the canonical forms lemma to fix the shape of each subterm's value. preservation's twin; progress_statement(lang) -> KTerm.
Preservation
aka subject reduction. If |- e : T and e --> e' then |- e' : T. Induction on typing/step derivation; the beta/elimination case discharges via inversion + substitution lemma. preservation_statement(lang) -> KTerm.
Subject reduction
Synonym for Preservation (never used as a distinct concept here).
Canonical forms lemma
A closed value of type Bool is TmTrue/TmFalse; of Arrow(S,T) is a Lam; of Nat is Zero/Succ; etc. Inverts "value at type" → constructor. canonical_forms in tsp-meta; feeds Progress.
Inversion lemma
From a typing judgment for a compound term, recover typings of its subterms (e.g. |- App(f,a):T ⇒ ∃ S. |- f:Arrow(S,T) ∧ |- a:S). inversion in tsp-meta; feeds Preservation.
Substitution lemma
THE crux: Γ,x:S |- e:T and Γ |- v:S ⇒ Γ |- [v/x]e : T. Its kernel proof mirrors tsp-term::subst/shift index arithmetic exactly — an off-by-one in shift breaks the lemma. substitution in tsp-meta.
Weakening
Adding an unused binding to the context preserves typings: Γ |- e:T ⇒ Γ,x:S |- shift(e,1,0):T (under de Bruijn, weakening shifts indices). weakening in tsp-meta; prerequisite of substitution.
Small-step semantics
Reduction as a single-redex relation e --> e'; iterate to evaluate. Implemented by step(e: &Term) -> Option<Term> in tsp-rules (None = value or stuck). The canonical operational model here.
Big-step semantics
Evaluation-to-value relation e ⇓ v in one judgment. NOT the primary model; mentioned only as the alternative to small-step. Soundness here is phrased over small-step.
Evaluation context
A term with one hole [·] marking the next redex (E ::= [·] | App(E,e) | App(v,E) | If(E,e,e) | Succ(E) | ...). Encodes congruence/search rules so step reduces left-to-right, call-by-value. tsp-rules, Phase 4.
Value
A fully-reduced term: Lam, TmTrue, TmFalse, numerals (Zero/Succ of values), pair/inj of values. Decided by is_value(t: &Term) -> bool in tsp-term. Progress's left disjunct.
Stuck term
A closed, non-value term with step(e) == None (e.g. If(Zero, ...)). Type soundness ⇒ no well-typed closed term is ever stuck. The failure state soundness forbids.
Simply-typed lambda calculus (STLC)
The base object language: Term/Type with Var/Lam/App + Arrow. The textbook calculus whose soundness is proved first (Phases 1–9), then extended.
System F
Polymorphic lambda calculus (universal types). Stretch object language: Type::All/TyVar, type abstraction/application. Phase 12 stress option; brings parametricity as a further stretch.
de Bruijn index
Nameless variable: Var(usize) = number of binders between use and its binder. Eliminates alpha-renaming. The representation in tsp-term::Term::Var; indices are usize.
Shift
shift(t,d,cutoff) -> Term: add d (an isize) to every free index ≥ cutoff; cutoff rises by 1 under each binder. Adjusts indices crossing a binder. The off-by-one hotspot.
Capture-avoiding substitution
subst(t,j,s) -> Term = [s/j]t: replace free index j with s, shifting s under each binder it descends. Capture is automatic given correct shift. Mirrored by the substitution lemma.
Alpha-equivalence
Equality of terms up to bound-variable renaming. Under de Bruijn it is structural equality — alpha_eq(a,b) is a plain recursive Term/Type comparison. tsp-term::alpha_eq.
Judgment
An atomic assertion in an inductive relation, e.g. Has-Type(ctx,e,T) or Step(e,e'). Judgment { form: Atom, args: Vec<Term> } in tsp-rules.
Inference rule
Premises ⊢ conclusion, named: Rule { name, premises: Vec<Judgment>, conclusion: Judgment }. Object-language typing/step rules are Rule data; parsed by tsp-syntax.
Derivation
A finite proof tree: a Rule instance with subderivations for each premise. Derivation { rule, subderivations, conclusion }; validity decided by check_deriv(d,rules) -> Result<(),DerivError>.
Inductive relation
A relation defined by a finite set of inference rules, closed under those rules (smallest such). Typing and --> are inductive relations realized as Vec<Rule>.
Logical framework (LF)
The Edinburgh LF: a dependently-typed metalanguage for encoding judgments and derivations as types and terms. tsp-kernel is an LF-style lambda-Pi core; object judgments are LF inductive signatures (Phase 6).
lambda-Pi
The dependently-typed lambda calculus (Π-types) underlying LF. Realized by KTerm { Var, Sort, Pi, Lam, App } with Sort { Type, Kind } (Type : Kind). The kernel's term language. Written "lambda-Pi", never with Greek.
Pi type / dependent function type
Pi(A, B) = the type of functions from x:A to B where B may mention x. Encodes implication (non-dependent Pi) and universal quantification (∀). KTerm::Pi(Box<KTerm>,Box<KTerm>).
Proof term
A KTerm whose type (a KType) is the proposition it proves. "Valid proof" ≡ check_type(ctx, term, prop) succeeds. A Derivation is reified into a proof term in Phase 6.
Proposition (Prop)
A KType viewed logically. Proof { goal: KTerm, term: KTerm } packages term : goal for the kernel to check.
Propositions-as-types
The discipline mapping logic to types: implication→Pi/Arrow, ∀→Pi, conjunction→pair, etc.; a theorem is a KType, its proof a KTerm. The encoding strategy of tsp-meta.
Curry-Howard
The proofs-as-programs correspondence underpinning propositions-as-types; "proving" = "constructing a well-typed proof term the kernel accepts."
Trusted computing base (TCB)
The code whose correctness is assumed, not checked: here exactly tsp-kernel (infer_type/check_type/whnf/equal). Kept small + audited (target low-hundreds of lines); a TCB bug that accepts an ill-typed proof term silently validates a false theorem — the gravest failure.
Bidirectional type checking
Split into infer_type(ctx,t) -> KTerm (synthesize a type) and check_type(ctx,t,ty) (check against a given type). Avoids guessing Pi domains; the kernel's checking algorithm (Phase 5).
Definitional equality / conversion
equal(ctx,a,b) -> bool: types/terms equal up to beta- (and optionally eta-) reduction. Used by check_type to compare expected vs actual types. Decided via whnf.
Weak-head normal form (whnf)
whnf(t) -> KTerm: reduce only until the outermost constructor is exposed (don't normalize under it). The engine of equal and bidirectional checking; lazy enough to terminate on the propositions we encode.
Eliminator / induction principle
The recursion/induction scheme for an LF inductive signature; lets a proof case-split and recurse over a derivation. Generated in Phase 6; how Progress/Preservation "do induction on the derivation."
Property-based testing
Generate many inputs, assert a property holds (PLT-Redex style). tsp-test: Generator of size-bounded well-typed terms feeds check_progress/check_preservation; complements proofs with fast falsification.
Counterexample shrinking
On failure, the Shrinker minimizes the offending Term to a smallest still-failing witness. TestResult::CounterExample(Term, Witness) where Witness records which property broke + how.
Store typing
A typing context for the mutable store (heap) Σ mapping locations→types; needed so Ref soundness is preserved across allocation/update. Phase 12 references stretch.
Parametricity
Uniform behavior of System F polymorphic functions ("theorems for free"). Stretch goal layered on the System F extension; not required for the soundness gate.
LangDef
The parsed object-language definition: { sorts, grammar, judgments, rules } in tsp-syntax. The .lang input the CLI checks/tests against.
Atom
An interned identifier used for sorts, judgment forms, and rule names (Judgment.form, Rule.name).
Type
Object-language types in tsp-term: Base, Arrow, Prod, Sum, Ref, plus All/TyVar (System F).
Term
Object-language terms in tsp-term: Var (de Bruijn), Lam/App, TmTrue/TmFalse/If, Zero/Succ, growing with products/sums/refs.
Context
The object typing context Γ (a de Bruijn list of Type) consumed by infer(ctx,e) -> Result<Type,TypeError>. Distinct from the kernel's Ctx.
KTerm / KType
Kernel terms and their types (a KType is itself a KTerm). The lambda-Pi syntax checked by the trusted infer_type/check_type.
Ctx
The kernel context: a de Bruijn list of KTerm types. Distinct from object Context.
tsp (binary)
The tsp-cli executable. Subcommands: check (a LangDef + its soundness proof through the kernel), test (randomized soundness), typecheck (object infer), step (object reduction).
Dual-guard design
A deliberately broken typing rule must be caught by BOTH tsp-kernel (its Proof no longer check_types) AND tsp-test (a shrunk CounterExample). The cross-check validating Phase 12.
