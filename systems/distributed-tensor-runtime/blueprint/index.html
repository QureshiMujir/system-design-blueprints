351 — Distributed Tensor Runtime

Goal: Implement, from scratch in Rust, a distributed tensor compute runtime: n-dimensional tensors sharded across a device mesh, a sharding-spec type system (replicated / sharded / partial) with an SPMD partitioner that propagates shardings and inserts the collectives needed to reshard, a collective-communication engine built from scratch over a custom transport (ring / tree / recursive-halving-doubling allreduce, allgather, reduce-scatter, broadcast, all-to-all), an execution engine (op DAG, scheduler, compute/communication overlap, streams), per-rank local kernels that delegate dense math to #349 BLAS, and a coordination/fault layer (rank bootstrap, barriers, failure detection). Crates: tensor-core / mesh / collectives / transport / exec / partition / kernels / runtime / cabi / bench / conformance. It models the NCCL + Mesh-TensorFlow/GSPMD + Horovod family — not a dense BLAS (#349, a dependency), a sparse engine (#350), a parameter server (#250), an inference router (#326), or a training framework (#115, which would sit on top of this). Correctness is validated against a single-process reference (run the same program with mesh size 1) and MPI-semantics differential tests; performance against collective bandwidth/latency cost models.

1. Goal

1.1 Engineering Definition

  • Build a from-scratch distributed tensor runtime: device mesh + sharding spec → SPMD partitioner (resharding via collective insertion) → from-scratch collective engine over a custom transport → execution engine (DAG, scheduler, overlap) → per-rank local kernels (delegating dense math to #349).
  • Numerics: IEEE-754 f32/f64/bf16 (bf16 for ML payloads); collective reductions are sum/max/min/prod.
  • Concurrency model: SPMD — every rank runs the same program over its shard; the runtime makes data placement explicit.

1.2 System Boundaries

  • In scope: device mesh abstraction; sharding-spec type system + propagation; SPMD partitioner + resharding; collectives (allreduce/allgather/reduce-scatter/broadcast/all-to-all/barrier) with ring + tree + recursive-halving-doubling algorithms; a reliable ordered transport (framing, rendezvous, flow control) over TCP; op DAG + scheduler + compute/comm overlap; distributed matmul, elementwise, reductions; rank bootstrap + barrier + failure detection; deterministic execution mode.
  • Out of scope (non-goals): dense kernels → #349 (dependency; per-rank compute); sparse → #350; autograd/training loop → #115/#112 (built on top); model-serving routing → #326; MoE expert routing → #325 (a consumer); a tensor compiler/fusion → #249/#307; RDMA/InfiniBand transport → PhaseDeferred("FINAL_BLUEPRINT §23.2"); GPU device backend / NCCL-on-GPU → PhaseDeferred("§24.2"); elastic membership / checkpoint-restart training → PhaseDeferred.

1.3 Deployment Model

  • A Rust library + a per-rank runtime daemon; processes launched one-per-device across hosts (a dtr-run --hosts ... --np N launcher, MPI-mpirun-like). Bootstrap via a rendezvous endpoint (a coordinator address). Shared-nothing between ranks except the network. A CLI dtrctl for mesh inspection, collective micro-benchmarks, and a single-process simulation mode.

1.4 Target Users

  • Engineers building distributed training/inference who must understand how allreduce, sharding, and overlap actually work; learners internalizing SPMD + collective algorithms + the resharding problem.
  • Downstream portfolio: #115 Distributed Training (data/model/ZeRO parallelism expressed as shardings + collectives over this), #325 MoE (all-to-all expert dispatch), #326 Inference Router, #250 Parameter Server (an alternative paradigm to compare).

1.9 Recommended Language & Rationale

  • Rust. (a) It is simultaneously a systems-networking project and a numerical one — Rust serves both (async transport + intrinsic-level local kernels); (b) ownership/Send/Sync make the per-rank concurrency (network threads, compute threads, stream queues) auditable; (c) reuses #349 for per-rank dense math and #350-style patterns; (d) no GC pauses to perturb collective latency tail; (e) extern "C" ABI so #115 (Python training) can drive it.
  • Rejected: C/C++ + MPI (MPI is the thing we're learning to build — using it defeats "from scratch"; C++ is the NCCL/Gloo language but ABI/build pain); Go (great for the transport/coordinator, GC jitter hurts collective tails; weaker numeric/intrinsic story); Python (orchestration only — too slow for the data plane); Erlang (great failure model, wrong for high-bandwidth tensor data plane).

1.10 Prerequisites

  • Distributed systems (consensus-free coordination, failure detection, rendezvous); networking (TCP, framing, flow control, bandwidth/latency, RTT); collective-algorithm theory (ring/tree/RHD, the α–β cost model); parallel ML systems (data/model/pipeline parallelism, ZeRO); concurrency (async I/O, streams, overlap). Strongly recommended prior: #349 BLAS (dependency), #179 MPI (collective semantics), #33 TCP/IP / #155 gRPC (transport), #197 SWIM (failure detection), #115 Distributed Training (the motivating workload).

2. Why Build This

2.1 Unique Knowledge Taught

  • Collective algorithms from first principles. Why ring allreduce is bandwidth-optimal (2(N−1)/N · data moved, independent of latency for large messages) and tree/RHD win for small messages (latency log N vs N). The α–β (latency–bandwidth) cost model that predicts the crossover.
  • The sharding/resharding problem (GSPMD/Mesh-TF). How a sharding spec annotates which tensor axis lives on which mesh axis, and how the partitioner infers shardings through ops and inserts collectives to reconcile mismatches (e.g. a sharded-contraction matmul needs a reduce-scatter or allreduce).
  • Compute/communication overlap. Why naive "compute then communicate" wastes half the time, and how streams + dependency scheduling hide communication behind compute.
  • Distributed determinism & failure. Why floating-point reductions must fix an order to be reproducible across runs, and what "a rank died" means when there is no shared memory.

2.2 Why It Matters

  • Every large-model training/inference system (Megatron, GSPMD/JAX, DeepSpeed, NCCL-backed PyTorch) is this: tensors sharded over a mesh, glued by collectives, overlapped with compute. The allreduce is the single most important operation in distributed deep learning. Understanding it is understanding how models scale past one device.

2.3 Engineering Muscles

  • Network data-plane engineering (framing, flow control, zero-copy paths); distributed-protocol design (rendezvous, barriers, failure detection); collective-algorithm implementation + cost modeling; concurrency for overlap; type-system design (the sharding spec); SPMD reasoning; differential testing across world sizes; bandwidth/latency benchmarking.

2.4 Production Concepts Exercised

  • Topology-aware collectives; SPMD partitioning + collective insertion; compute/comm overlap & streams; fail-stop detection + bounded recovery; deterministic distributed numerics; reproducible multi-host benchmarking.

2.5 Cross-Links

  • #349 BLAS — dependency; the per-rank local matmul/elementwise compute.
  • #179 MPI — collective semantics reference (we re-derive its algorithms); #33 TCP/IP / #155 gRPC — transport lineage; #197 SWIM — the failure detector.
  • #115 Distributed Training / #325 MoE / #326 Inference Router — consumers that express parallelism as shardings + collectives over this runtime.
  • #250 Parameter Server — the contrasting (centralized) paradigm.
  • #321 DPDK / #322 kernel-bypass / #323 io_uring — the high-performance transport directions (RDMA deferred but lineage noted).

2.6 Calibration Value

  • You leave able to read NCCL, Gloo, Mesh-TensorFlow, and GSPMD and explain every collective algorithm, sharding annotation, and overlap decision — and to reason about why a distributed training job is communication-bound and how to fix it.

2.7 The communication wall — the defining constraint

  • #349 (dense) is compute-bound; #350 (sparse) is local-memory-bandwidth-bound; this runtime is network-bound — the scarce resource is inter-rank bandwidth and latency.
  • Consequence 1: the collective is the unit of cost. A training step's wall-clock is often compute + Σ collective_time, and at scale the second term dominates.
  • Consequence 2: algorithm choice is message-size-dependent (ring for bandwidth, RHD/tree for latency) — there is no single best collective.
  • Consequence 3: overlap is the primary lever — communication that runs concurrently with compute is effectively free; the goal is to hide ≥ 80 % of it.
  • Consequence 4: the partitioner's sharding choices set the communication volume before any byte moves — a bad sharding inserts O(N) traffic that no transport tuning can recover.
  • Consequence 5: topology matters — inter-node links are scarcer than intra-node; hierarchical collectives exploit that.
  • This single fact reorganizes every decision in the runtime and is the sharpest contrast with #349/#350.

2.8 What Mastery Looks Like

  • Derive the ring/RHD crossover for any cluster. Given measured α, β, and N, produce the message-size threshold D* where ring and RHD cost the same, and explain why ring wins above it despite having worse latency — P4 (§4.1, §8.4).
  • Trace the full life of a gradient allreduce. Starting from "local backward pass completes on rank r," narrate every invariant that fires (I1 arg check, I4 bytes, I6 reduce order, I5 cross-rank identity, I12 failure guard) through to "optimizer step runs" — P3/P9 (§3.4, §7).
  • Partition a 2-D matmul by hand. For a given mesh shape and ShardSpec, derive which collectives the partitioner must insert, choosing between allreduce, reduce-scatter, and all-to-all, and explain the cost difference — P6 (§8.3, §8.10).
  • Diagnose a comm-bound training job. Given CollTrace output showing overlap %, per-collective bytes, and achieved bandwidth, identify whether the bottleneck is volume (bad sharding), algorithm mismatch (wrong ring/RHD choice), or insufficient overlap (scheduler issue), and prescribe the fix — P9/P12 (§4.2, Performance Engineering).
  • Explain distributed determinism honestly. Articulate the difference between cross-rank identity (always required, I5) and cross-run reproducibility (optional, I6), why floating-point order matters, and what "deterministic mode" costs in pipelining freedom — P3/P8 (§8.12).
  • Design the bootstrap protocol. Sketch the three phases (register, exchange, agree), explain why the coordinator must leave the data path after bootstrap (principle 9), and identify the O(N) scaling pressure and the mitigation for N > 1024 — P2 (§8.13, §4.3).
  • Reason about overlap ceilings. Given compute time C and comm time K for a layer, compute the maximum achievable speedup, the minimum achievable wall-clock, and the condition under which adding bandwidth helps more than adding overlap — P9 (§4.2, MM4).
  • Evaluate a "rejected" architecture choice. For any ADR in §9, name a real regime where the rejected option would win (e.g., C++ wins when the team must integrate with cuBLAS/NCCL directly), explaining why the winning condition does not apply here — P0/P12 (§9 ADR table).

3.2 Box Narratives

  • dtr facade. Entry points: declare a DeviceMesh, annotate tensors with ShardSpec, build/submit an op graph, run it SPMD. Validates mesh/shard consistency. Thin orchestration.
  • tensor-core. Tensor<T> = dense n-dim array (shape, strides, dtype, device handle), local to a rank. DeviceMesh = an n-dim grid of ranks with named axes (e.g. {"data":4, "model":2}). ShardSpec maps each tensor dimension to a mesh axis or "replicated"/"partial". ShardedTensor = a logical (global-shape) tensor + its ShardSpec + the local shard each rank holds. The vocabulary every other crate speaks.
  • partition. The SPMD partitioner. Given an op graph with input shardings, it infers output shardings (propagation rules per op), detects mismatches (an op needs operands in a different sharding than they're in), and inserts collectives to reshard (e.g. a contraction over a sharded axis emits a reduce-scatter or allreduce; a sharded→replicated change emits allgather). This is the GSPMD/Mesh-TF heart — the hardest, most distinctive subsystem.
  • exec. Builds the op DAG (local ops + inserted collectives), schedules it respecting dependencies, assigns ops to streams (independent ordered queues), and drives execution SPMD across ranks. The scheduler is where compute/comm overlap is realized.
  • collectives. The from-scratch collective engine. Each collective has multiple algorithms: ring (bandwidth-optimal, large msgs), tree / recursive-halving-doubling (latency-optimal, small msgs), selected by a cost model (α latency + β/bandwidth × bytes). allreduce = reduce-scatter + allgather (the ring decomposition). All built on transport point-to-point.
  • kernels. Per-rank local compute: elementwise (add/mul/activation), reductions (local part of a distributed reduce), and matmul → delegated to #349. The numeric substrate; collectives glue the local results.
  • transport. Reliable, ordered, framed messaging between ranks: connection setup, a rendezvous protocol for buffer matching (sender/receiver agree on a transfer), flow control (bounded buffers, backpressure), and multiple independent streams (so a collective on one stream doesn't head-of-line-block another). TCP now; RDMA-like verbs deferred. The data plane.
  • runtime. Process/rank lifecycle: bootstrap (every rank discovers the world via a coordinator/rendezvous address), assigns rank/world_size, provides a barrier, and runs a failure detector (heartbeat/SWIM-style). On a rank failure: fail-stop detection + a clean abort with diagnostics (in-job recovery deferred).
  • bench / conformance. Collective bandwidth/latency harness (vs the cost model + the bandwidth-optimal bound); single-process oracle (run the same graph with world_size=1 — the trusted result); MPI-semantics differential tests; fault-injection (kill a rank, drop messages, reorder, delay).

3.3 Boundaries

  • Trust boundary: the network (other ranks) and the C ABI. Messages are framed + length-checked; a peer can be slow, dead, or (in the threat model) send malformed frames. Within a job all ranks are trusted as cooperative but not as reliable.
  • Concurrency boundary: per rank — network I/O threads, compute threads (#349 pool), and the stream queues. Collectives and local compute overlap across streams.
  • Numerical boundary: collective reduction order. A tree/ring reduction sums in a topology-determined order → result depends on world size + algorithm → documented; a deterministic mode fixes a canonical order (I-class invariant) at a performance cost.
  • Coordination boundary: the rendezvous/coordinator (bootstrap + membership) is the one semi-central component; the data plane is fully peer-to-peer.

3.4 Data-flow walk — one data-parallel training step (SPMD)

  1. Bootstrap (once): every rank joins the world via the coordinator, gets rank/world_size, agrees on the mesh {"data":N} (I13).
  2. Each rank holds replicated weights + a distinct batch shard (ShardSpec: weights Replicated, batch Sharded(data)).
  3. Forward + backward run as local ops (matmul → #349) on the rank's shard → produces local gradients in Partial(sum) state (each rank has a partial gradient).
  4. The partitioner inserted an allreduce over the data axis to turn Partial(sum) gradients into Replicated averaged gradients (§8.3).
  5. collectives::allreduce_ring runs (cost-model may pick RHD for small tensors); result bit-identical on all ranks (I5); bytes/rank = 2(N−1)/N·D (I4).
  6. The scheduler overlapped the allreduce of earlier-computed gradients with the still-running backward of later layers (P9) → comm hidden behind compute.
  7. Each rank applies the (identical) averaged gradient → weights stay replicated/consistent.
  8. The failure detector ran throughout; a dead rank would fail-stop the step (I12). CollTrace recorded each allreduce's algorithm/bytes/bandwidth/overlap.

3.5 Per-rank concurrency model (threads, streams, pools)

  • Network I/O threads (a small pool) drive the transport: send/recv, framing, acks, flow control — async, never blocking compute.
  • Compute threads = #349's pool, running local kernels; coordinated with the network pool so factorization-style nested parallelism does not oversubscribe cores (ADR-25).
  • Streams are logical ordered queues (comm streams + compute streams); the scheduler maps independent ops to different streams to realize overlap (I10).
  • The executor thread walks the DAG, posts ready ops to streams, and tracks completion (I11).
  • The failure-detector thread sends/receives heartbeats out-of-band (its own control stream) so a busy data plane never delays detection (I12).
  • Synchronization: per-stream order is implicit; cross-stream order is only via explicit DAG dependencies (CollHandle::wait) — no hidden global locks on the data path (principle 9).
  • This separation (I/O ≠ compute ≠ scheduling ≠ detection) is what lets communication and computation truly overlap.

4.1 Worked collective cost (the ring/RHD crossover)

  • Model: T = α + β·n per message; for N ranks reducing D bytes.
  • Ring allreduce: T_ring ≈ 2(N−1)·α + 2·(N−1)/N·D·β (+ reduce γ). Latency term scales O(N); bandwidth term → 2D·β (N-independent, optimal).
  • RHD allreduce: T_rhd ≈ 2·log₂N·α + 2·(N−1)/N·D·β. Latency term O(log N); same bandwidth term.
  • Crossover: ring and RHD share the bandwidth term, so the choice is driven by the latency term: RHD wins whenever 2log₂N·α < 2(N−1)·α, i.e. essentially always on latency — but ring's simpler pipelining + better cache/overlap behavior makes it win for large D in practice; RHD wins for small D (latency-dominated). The select() function computes the crossover D* from the measured α,β.
  • Numeric example: N=64, α=5 µs, β=1/(10 GB/s). Small D=1 KB: latency dominates → RHD (2·6·5µs=60µs vs ring 2·63·5µs=630µs). Large D=100 MB: bandwidth dominates (≈2·100MB·β≈20ms) → ring (simpler, overlaps better).
  • Implication: the §4 targets are stated against the bandwidth-optimal bound for large D and the log-latency bound for small D — the cost model must be calibrated per cluster (P4), never hardcoded.

4.2 Worked overlap budget (why ≥ 80 % hidden is the target)

  • A step's wall-clock with perfect overlap is max(compute, comm); with no overlap it is compute + comm.
  • Suppose backward compute = 40 ms and gradient allreduce comm = 30 ms. Serial: 70 ms. Fully overlapped: max(40,30)=40 ms → 1.75× speedup; the 30 ms of comm is free.
  • But overlap requires independent work to hide behind: gradients for layer L can allreduce while layer L−1's backward runs (reverse-order availability). The scheduler exploits exactly this (P9).
  • Overlap % = hidden_comm / total_comm. At 80 %, effective comm = 0.2·30 = 6 ms → wall-clock ≈ max(40, 40+6) ≈ 46 ms (vs 70 ms serial).
  • Ceiling: if comm > compute, even perfect overlap leaves comm − compute exposed → the workload is comm-bound, and the only fix is reducing volume (partitioning, P6) or raising bandwidth (topology/transport, P12).
  • This is why §4 targets ≥ 80 % overlap and near-optimal collective bandwidth — the two levers multiply.

4.3 Failure-detection budget (the detection-vs-false-positive tradeoff)

  • Detection time ≈ k · heartbeat_interval (k = suspicion confirmations). Smaller heartbeat/k → faster detection but more false positives (a slow rank wrongly declared dead).
  • Example: heartbeat=200 ms, k=3 → detection ≈ 600 ms (< the §4 "3×heartbeat" bound) with low false-positive rate via SWIM indirect probes.
  • The cost of a false positive is high (the whole job fail-stops), so the default leans conservative; the cost of slow detection is a hung job — both are bounded, never unbounded (principle 8, I12).
  • The bound holds independent of N because heartbeats use the SWIM gossip pattern (O(1) load per rank), so detection time does not grow with world size.

6. Design Principles

  1. SPMD: one program, explicit data placement. Every rank runs the same graph; the runtime makes "which rank holds which shard" explicit via ShardSpec. Violation: implicit/rank-conditional logic → unscalable, undebuggable code.
  2. Collectives compose from point-to-point; allreduce = reduce-scatter + allgather. Build the zoo from a small primitive set. Violation: monolithic per-collective code → no reuse, no algorithm-swapping.
  3. Algorithm selection is cost-model-driven, never hardcoded. Ring for bandwidth (large msgs), tree/RHD for latency (small msgs); pick via α–β. Violation: one algorithm always → 10× slow on the wrong message size.
  4. Overlap communication with computation by default. Streams + dependency scheduling hide comm behind compute. Violation: serial compute-then-communicate → ~2× slowdown on comm-bound workloads.
  5. Backpressure everywhere in the transport. Bounded buffers, flow control, credit-based sends. Violation: unbounded send queues → OOM under a slow receiver; latency collapse.
  6. Sharding is a type; the partitioner reasons about it. Mismatches are resolved by inserting collectives, never by silent gathers. Violation: hidden full-replication → memory blowup, accidental O(N) traffic.
  7. Determinism on demand: reductions have a fixed canonical order in deterministic mode. Violation: topology-dependent reduction order presented as reproducible → unrepeatable training, untestable.
  8. Fail-stop with bounded detection; never hang silently. A dead/slow rank is detected within a bound and the job aborts cleanly with diagnostics. Violation: unbounded waits → a job hung for hours on one dead rank.
  9. The data plane is peer-to-peer; coordination is minimal and explicit. Only bootstrap/membership touches the coordinator; data never routes through a central node. Violation: central data routing → bottleneck, single point of failure.
  10. Delegate local compute to #349; the runtime owns placement and movement, not arithmetic. Violation: re-implementing GEMM → drift, wasted effort, worse numerics.
  11. Observability of every byte moved and every collective. Emit per-collective algorithm, bytes, duration, achieved bandwidth, overlap %. Violation: opaque collectives → can't diagnose comm-bound jobs.
  12. Stable wire compatibility. The frame/protocol format is versioned; mixed-version ranks negotiate or refuse. Violation: silent protocol drift → corruption across a rolling upgrade.
  13. Bounded memory: stream collectives in chunks. Ring buffers sized O(chunk), not O(message). Violation: materializing full buffers → OOM on large tensors.
  14. Correctness anchored to the single-process oracle. world_size=1 must produce the reference result (within numeric bounds) for every program. Violation: no oracle → distributed bugs are undebuggable.

8. Domain Model — Mesh, Sharding, Collectives, Execution

8.1 Device mesh

  • A DeviceMesh is an n-dimensional grid of ranks with named axes, e.g. {"data":4, "model":2} over 8 ranks.
  • Rank r has mesh coordinates (r // 2, r % 2) (row-major over axes).
  • Named axes let a ShardSpec say "shard tensor dim 0 over the data axis" without hardcoding rank arithmetic (Mesh-TF model).
  • A collective runs over a subset of axes (a "process group" = the ranks sharing all other coordinates), e.g. allreduce over model = each data-row reduces independently.

8.2 Sharding spec (the type)

  • ShardSpec maps each tensor dimension to one of: a mesh axis (sharded — the dim is split across those ranks), Replicated (every rank has the full dim), or Partial(op) (each rank holds a partial reduction-pending value, e.g. after a local contraction, awaiting allreduce).
  • Example: tensor [1024, 512], mesh {"data":4,"model":2}, spec [data, Replicated] → each rank holds [256, 512].
  • Validity (I2): a sharded dim's size must be divisible by the mesh-axis size; each dim maps to ≤ 1 axis.
  • Partial is the key insight: distributed contraction produces partial sums that must be resolved by a collective before the value is "real" replicated/sharded data.

8.3 Resharding (the partitioner's job)

From → To Collective inserted
Sharded(axis) → Replicated allgather over axis
Replicated → Sharded(axis) local slice (no comm)
Partial(sum) → Replicated allreduce over axis
Partial(sum) → Sharded(axis) reduce-scatter over axis
Sharded(axis A) → Sharded(axis B) all-to-all (axis swap)
Replicated → Partial (illegal; partial only arises from compute)
  • The partitioner walks the op graph, infers each op's output sharding from its inputs (propagation rules), and where an op needs an operand in a different spec than it currently has, inserts the resharding collective (I3). This is GSPMD's core loop.

8.4 Collective algorithms + cost model

  • α–β (Hockney) model: a message of n bytes costs α + β·n (α = latency, β = 1/bandwidth). Reductions add γ·n compute.
  • Ring allreduce: reduce-scatter (N−1 steps, each sends D/N) + allgather (N−1 steps) → moves 2(N−1)/N·D bytes/rank, time ≈ 2(N−1)·α + 2(N−1)/N·D·β. Bandwidth-optimal (Patarasuk–Yuan); latency grows with N → bad for small D.
  • Recursive halving-doubling (RHD) allreduce: log₂N steps → latency ≈ 2·log₂N·α + 2(N−1)/N·D·β. Latency-optimal; best for small D, power-of-two N.
  • Tree broadcast/reduce: log₂N latency.
  • Bruck / all-to-all: log₂N steps (small) or direct (large).
  • Selection: crossover where ring_time = rhd_time → small msgs RHD/tree, large msgs ring (the cost model computes it, ADR-driven).

8.5 Worked allreduce (ring, N=4, D=4 chunks)

Each rank splits its buffer into N=4 chunks. Reduce-scatter phase (3 steps): rank r sends chunk
(r−step) to (r+1), adds received chunk → after 3 steps each rank owns the full sum of one chunk.
Allgather phase (3 steps): circulate the completed chunks → all ranks have all reduced chunks.
Bytes/rank moved = 2·(3/4)·D = 1.5D. Result identical on every rank (I5).

8.6 Execution: op DAG, streams, overlap

  • A program is an op DAG: local ops (matmul, add, …) + inserted collectives, with data dependencies.
  • The scheduler assigns ops to streams (independent ordered queues); ops on different streams run concurrently if no dependency links them.
  • Overlap: issue a collective on a comm stream, then run independent compute on a compute stream while it's in flight; the dependency edge forces the consumer to wait for both. Hides comm behind compute (principle 4).
  • Determinism (I6): the DAG topological order + fixed reduction order make execution reproducible in deterministic mode.

8.7 Wire protocol (transport)

  • Frame: [magic | version | type | stream_id | seq | length | checksum | payload].
  • Types: Rendezvous (sender/receiver match a transfer), DataChunk, Ack, Credit (flow control), Control (barrier, heartbeat), Bye.
  • Reliability: per-stream sequence numbers + acks; checksum detects corruption (I7); retransmit on loss (over TCP, mostly for completeness/RDMA-future).
  • Flow control: credit-based; in-flight bytes ≤ window (I8) → backpressure.

8.8 State machines

  • Rank lifecycle: Bootstrapping → Joined(rank,world) → Running → {Draining → Exited | Failed}.
  • Collective: Posted → (algorithm steps) → Complete; on peer failure → Aborted.
  • Connection: Connecting → Established → {Closing → Closed | Broken}; broken → failure detector.

8.10 Worked example — tensor (model) parallelism via SUMMA

  • Goal: Y = X · W where W [K,M] is too big for one rank; shard W over the model mesh axis.
  • Mesh {"model":P}; W spec [Replicated, Sharded(model)] → rank p holds W[:, p·M/P : (p+1)·M/P].
  • X is Replicated; each rank computes Y_p = X · W_p (local #349 GEMM) → Y is [Replicated, Sharded(model)] (no comm for the forward column-parallel matmul).
  • The next layer's row-parallel matmul produces Partial(sum) → the partitioner inserts an allreduce over model (the Megatron pattern: one allreduce per transformer block in forward, one in backward).
  • Contrast with §3.4 data parallelism: data-parallel shards the batch and allreduces gradients; model-parallel shards the weights and allreduces activations — both are ShardSpec + inserted collectives over different mesh axes.
  • Combined (2-D mesh {"data":N,"model":P}): both patterns compose — the partitioner handles each axis independently. This is how #115 would express 3-D parallelism on top of this runtime.

8.12 Determinism — what is reproducible, and what is not

  • Floating-point reduction is not associative, so a sum's result depends on the order of addition. Ring and RHD sum in different topology-determined orders → results differ at the last bits (within the error bound, principle 7).
  • Default mode: results are within the documented numeric bound but not bit-identical across world sizes / algorithms — honest, and matches #349's contract (assert bounds, not bits).
  • Deterministic mode (JobConfig.deterministic): the runtime reduces in a single canonical order (e.g. always rank-ascending tree) regardless of the chosen transport algorithm → bit-identical across runs and world sizes (I6), at a measured performance cost (less overlap/pipelining freedom).
  • Cross-rank identity is always required (I5): within a single run, every rank must end a collective with the same bits — this is enforced by algorithm symmetry + a cross-rank hash check, independent of det-mode.
  • NaN/Inf propagate per IEEE in both modes; det-mode keeps even NaN-position reproducible.
  • Use cases: det-mode for debugging, regression golden hashes, and reproducible research; default mode for production throughput.

8.13 Bootstrap & rendezvous protocol

  • Every rank starts with the coordinator address + the expected world_size + the mesh shape (from JobConfig/env, set by the launcher).
  • Phase 1 (register): each rank connects to the coordinator and registers (host, listen_port); the coordinator assigns a unique rank ∈ [0,world_size) once all have arrived (or a timeout fires → fail).
  • Phase 2 (exchange): the coordinator broadcasts the full rank → (host,port) table; ranks open peer connections lazily (on first communication) or eagerly per a ring/mesh neighbor set.
  • Phase 3 (agree): an all-agree check confirms every rank sees the same world_size/mesh/version (I13/I14); any disagreement → abort (no split-brain start).
  • Scaling: all-to-coordinator is O(N); for large N the table broadcast uses a tree, targeting < 5 s at N ≤ 1024.
  • After bootstrap the coordinator leaves the data path entirely (it only participates again in failure notification, P10) — the data plane is pure peer-to-peer (principle 9).

8.14 All-to-all and the MoE dispatch pattern (a key consumer)

  • All-to-all is the collective where each rank sends a distinct chunk to every other rank — the inverse of allgather (which sends the same data to all).
  • It implements resharding across axes (Sharded(A) → Sharded(B), §8.3): re-laying-out a tensor so a different dimension is the sharded one.
  • The motivating consumer is #325 Mixture-of-Experts: tokens are routed to experts that live on different ranks. The dispatch is an all-to-all (send each token to its expert's rank), expert compute is local (#349), then a second all-to-all combines results back.
  • Algorithm choice (P4): Bruck (log₂N steps, more bytes) for small per-rank chunks; direct (N−1 sends, minimal bytes) for large chunks — selected by the cost model.
  • Imbalance hazard: MoE routing is data-dependent → some experts (ranks) receive far more tokens (load imbalance) → the all-to-all becomes straggler-bound. The runtime exposes per-rank byte counts so the consumer can detect and rebalance (capacity factor) — but the policy lives in #325, not here.
  • This is why all-to-all is a first-class collective (not an afterthought): an entire class of models depends on it, and it stresses the transport (N² communication pattern) and the failure/straggler paths harder than allreduce.

13.2 Detailed Implementation Steps

  • transport::frame — frame format (§8.7): magic/version/type/stream/seq/length/checksum. (ADR-20, I7, I14, principle 12)
  • transport::conn — connection setup/teardown; per-peer connection pool. (ADR-6, principle 9)
  • transport::reliability — per-stream seq numbers, acks, checksum verify (I7), retransmit. (I7, ADR-20)
  • transport::flow_control — credit-based window; in-flight bytes ≤ window (I8); backpressure. (ADR-13, I8, principle 5)
  • transport::stream — multiplex independent ordered streams over a connection (avoid head-of-line blocking). (I10, ADR-25, §3.5)
  • transport::rendezvous — sender/receiver match a transfer before bulk data. (§8.7, §8.13)

This two-phase handshake prevents head-of-line blocking between a large (100 MB) and a small (1 KB) message on the same connection — without it, a large in-flight transfer would stall a latency-sensitive control message behind it. The rendezvous frame itself is tiny and travels on the control stream; only DataChunk frames carry payload bytes.

14. Phase 2 — Point-to-point primitives + barrier + bootstrap

14.1 Objectives

  • Build the collective building blocks: typed send/recv over the transport, a barrier, and the rank-bootstrap/world-setup path (I13).

14.2 Detailed Implementation Steps

  • collectives::p2p — typed send/recv/sendrecv over transport, with dtype/count framing. (I7, §11.4, ADR-4)
  • collectives::barrier — dissemination barrier (log₂N rounds, I9). (Ben-Ari 2006, I9, §4 constraint row 7)
  • runtime::bootstrap — every rank connects to the coordinator/rendezvous endpoint, gets a unique rank + world_size, exchanges peer addresses, agrees on the mesh (I13). (ADR-18, §8.13, I13, §4.3)
  • runtime::coordinator — the rendezvous service (membership only; not in the data path). (principle 9, ADR-18, §8.13)
  • Arg-consistency check (I1): hash (op,dtype,count,…) and exchange at collective entry to catch mismatches without deadlock. (I1, §7, Hoefler et al. §5.2.9)
  • Dissemination barrier algorithm detail (Ben-Ari 2006, I9, §4 constraint row 7): in round r, rank i exchanges a notification with rank (i + 2^r) mod N; after ceil(log₂N) rounds every rank has received a notification that originated from every other rank (by transitivity of the doubling). For non-power-of-2 N a "butterfly + cleanup" variant is used: the first floor(log₂N) rounds handle the power-of-2 prefix, then a cleanup round handles the remaining ranks. This is why the barrier achieves O(log N) rounds while being correct for arbitrary N — a detail that a naive tournament barrier gets wrong.

15. Phase 3 — Ring collectives: reduce-scatter, allgather, allreduce

15.1 Objectives

  • Implement the bandwidth-optimal ring algorithms: reduce-scatter, allgather, and allreduce (= reduce-scatter + allgather), chunked and streamed (I4).

15.2 Detailed Implementation Steps

  • reduce_scatter (ring) — N−1 steps; each step send chunk to (r+1), receive from (r−1), reduce locally (I4). (Patarasuk & Yuan 2009, Chan et al. 2007, I4, §8.4)
  • allgather (ring) — N−1 steps circulating completed chunks. (Chan et al. 2007, principle 2, I5)
  • allreduce_ring — compose the two; chunk the buffer into N pieces; pipeline steps. (Patarasuk & Yuan 2009, §8.5, I4, I5, ADR-5)
  • reduce_ops — Sum/Max/Min/Prod with fixed accumulation order (I6). (ADR-16, I6, principle 7, §8.12)
  • Stream chunks (bounded ring buffers, principle 13); overlap send/recv/reduce within the ring. (principle 13, I8, ADR-13)
  • Chunk-pipeline overlap within the ring (Patarasuk & Yuan 2009, §8.5, principle 13): while step k's received chunk is being reduced (γ·chunk_bytes of compute), step k+1's send can be in flight simultaneously. This hides the reduction compute (γ) behind the network transfer (β), and is precisely why the ring's effective wall-clock approaches the pure bandwidth bound 2·(N−1)/N·D·β in practice — the γ term vanishes when the chunk size is tuned so that γ·chunk ≤ β·chunk (i.e. the reduction is faster than the transfer, which is true for CPU addition on modern hardware). Chunk size tuning is therefore not just a memory trade-off but a latency-hiding decision.

15.3 Deliverable

  • Ring allreduce/allgather/reduce-scatter; examples/allreduce; result identical on all ranks (I5).

15.4 Acceptance Criteria

  • Result matches the np=1 oracle (sum of all ranks' inputs) within numeric bounds; bit-identical across ranks (I5).
  • Bytes moved/rank == 2(N−1)/N·D (I4); ≥ 90 % of the bandwidth-optimal bound for large D.
  • Reduction order fixed/reproducible (I6).

15.5 Conformance Fixtures

  • collectives/allreduce_ring_vs_oracle.json, collectives/ring_byte_count.json, collectives/allreduce_cross_rank_hash.json (I5).

15.6 Pitfalls

  • Chunking with non-divisible D → uneven last chunk; handle remainder.
  • Reduction order must be fixed (which operand first) for determinism (I6) and cross-rank identity.
  • Pipelining bugs (step k+1 starting before k's data arrives) → use per-step dependencies.
  • Deadlock if all ranks send before receiving — use sendrecv or non-blocking.

15.7 Performance Concerns

  • Ring is bandwidth-optimal but latency = 2(N−1)·α → poor for small D (P4 adds RHD).
  • Overlap reduce-compute with the next send (hide γ behind β).
  • Chunk size tuning: too small → α-dominated; too large → less overlap.

15.8 Edge Cases

  • N=1 (no-op); N=2 (single exchange); D < N (some chunks empty); NaN in reduction (propagate).

15.9 Failure Analysis

  • Cross-rank divergence (a bug makes ranks disagree) → cross-rank hash compare (I5) catches it → abort.
  • A rank stalls mid-ring → the whole ring stalls → failure detector (P10) bounds it.

15.10 Operational Notes

  • CollTrace (algo=ring, bytes, bandwidth, reduce_order_id); tools/coll_trace.
  • This is the most important operation — document its cost model in docs/performance/collective-cost-model.md.

16. Phase 4 — Latency-optimal algorithms + broadcast/all-to-all + cost-model selection

16.1 Objectives

  • Add recursive-halving-doubling allreduce, tree broadcast/reduce, and all-to-all; calibrate the α–β cost model and implement automatic algorithm selection (principle 3).

16.2 Detailed Implementation Steps

  • allreduce_rhd — recursive halving (reduce-scatter) + recursive doubling (allgather), log₂N steps. (Thakur et al. 2005, §8.4, §4.1, ADR-5)
  • broadcast_tree — binomial-tree broadcast; tree reduce. (Thakur et al. 2005, §8.4, principle 2)
  • all_to_all — Bruck (small) / direct (large) for axis-swap resharding. (Thakur et al. 2005, §8.14, ADR-5)
  • cost_model — NetParams calibration (measure α, β via a ping/bandwidth probe); cost() per §8.4. (§4.1, §11.5, ADR-5, principle 3)
  • select — pick algorithm by message size vs the cost-model crossover; CollAlgo::Auto. (§4.1, ADR-5, principle 3, Thakur et al. 2005)
  • Non-power-of-2 N handling (RHD fallback / 3-2 elimination). (Thakur et al. 2005 §4.2, §16.6)
  • RHD algorithm recursive structure detail (Thakur et al. 2005, §4.2, §8.4): in the halving phase, pairs (0, N/2), (1, N/2+1), … exchange half their buffer and reduce locally; after log₂N steps each rank holds the complete reduction of exactly 1/N of the buffer (a non-overlapping, non-repeating partition). The doubling phase then distributes these partial results: each rank sends its completed piece to its partner, receiving the partner's piece, doubling the amount of completed data per round until all ranks have all pieces. For non-power-of-2 N, the "extra ranks" (ranks ≥ 2^floor(log₂N)) send their data to partner ranks before the halving phase and receive the result after the doubling phase — these extra ranks participate in neither phase directly, which is why they must be handled as a separate pre/post step and why an off-by-one in the extra-rank index computation produces a silent wrong result on a subset of ranks.

16.3 Deliverable

  • Full collective set with Auto selection; dtrctl coll-bench shows the ring/RHD crossover.

16.4 Acceptance Criteria

  • RHD allreduce beats ring for small D; ring wins for large D; Auto picks within 10 % of optimal at the crossover.
  • All collectives match the oracle; broadcast/all-to-all correct across all roots/axes.
  • Cost model predicts measured times within tolerance (calibrated).

16.5 Conformance Fixtures

  • collectives/rhd_vs_ring_crossover.json, collectives/broadcast_roots.json, collectives/all_to_all.json, collectives/cost_model_calibration.json.

16.6 Pitfalls

  • RHD assumes power-of-2 N → fallback for arbitrary N (the subtle part).
  • Cost-model calibration drifts with network conditions → re-probe; expose override.
  • all-to-all is O(N²) messages naively → Bruck for small, direct for large.
  • Tree broadcast root != 0 → rotate the tree.

16.7 Performance Concerns

  • The crossover point depends on α/β/N — must be measured per cluster, not assumed.
  • Bruck all-to-all: log₂N steps but more bytes; direct: N messages but minimal bytes.

16.8 Edge Cases

  • Non-power-of-2 N; single-element messages (pure latency); N=2; D huge (chunking).

16.9 Failure Analysis

  • A mis-calibrated cost model picks the slow algorithm (correct but slow) → cost-model fixture + bench gate; override available.

16.10 Operational Notes

  • CollTrace.algo records the chosen algorithm; document the selection thresholds and how to recalibrate NetParams.

17. Phase 5 — Sharding spec system + propagation rules

17.1 Objectives

  • Implement sharding propagation: given input shardings, infer each op's output sharding per op-specific rules — the input to the partitioner.

17.2 Detailed Implementation Steps

  • mesh::propagation — per-op sharding rules: elementwise (sharding flows through), matmul (contraction over a sharded axis → Partial; batch/free axes shard independently), reductions, reshapes. (Xu et al. 2021 §3, Shazeer et al. 2018, ADR-8, §8.2)
  • Sharding inference: forward-propagate from annotated inputs; identify where the inferred spec is ambiguous or conflicting. (Xu et al. 2021, ADR-9, principle 6)
  • Partial arises from contraction over a sharded axis (the key rule, §8.2). (§8.2, MM3, principle 6)
  • Conflict detection (an op's operands have incompatible shardings) → flagged for resharding (P6). (I3, ADR-9, §8.3)

17.3 Deliverable

  • Sharding propagation over a graph; examples/reshard shows inferred specs per op.

17.4 Acceptance Criteria

  • Propagation matches hand-derived shardings on 100 % of the ≥ 12 canonical op configurations in partition/propagate_matmul.json and partition/propagate_elementwise.json.
  • Partial correctly produced by sharded-contraction matmul in every one of the 6 §8.3 resharding-table transitions.
  • Conflicts detected, not silently resolved (deferred to P6 insertion), verified via partition/partial_from_contraction.json.

17.5 Conformance Fixtures

  • partition/propagate_matmul.json, partition/propagate_elementwise.json, partition/partial_from_contraction.json.

17.6 Pitfalls

  • Matmul sharding rules are subtle: which output axis inherits which input sharding; contraction → Partial.
  • Ambiguous propagation (multiple valid specs) → choose by a cost heuristic or require annotation.
  • Reshape/transpose remap mesh axes → easy to get wrong.

17.7 Performance Concerns

  • Propagation is cheap graph analysis; the choice of sharding determines later communication volume (the real cost).

17.8 Edge Cases

  • Fully replicated graph (no comm); fully sharded; a dim sharded over multiple axes (disallowed, I2).

17.9 Failure Analysis

  • A wrong propagation rule → wrong collective inserted → wrong result → vs np=1 oracle (I3) + per-op fixtures.

17.10 Operational Notes

  • tools/dag_viz annotates each op with its inferred ShardSpec; document the propagation rules per op.

18. Phase 6 — SPMD partitioner: resharding + collective insertion

18.1 Objectives

  • The partitioner: walk the graph, and wherever an op needs an operand in a different sharding than it has, insert the resharding collective (§8.3, I3). The GSPMD heart — the hardest subsystem.

18.2 Detailed Implementation Steps

  • partition::reshard — for each (current spec → required spec) pair, emit the right collective (allgather / reduce-scatter / allreduce / all-to-all / slice) per §8.3. (Xu et al. 2021, §8.3, I3, ADR-9)
  • partition::collective_insert — rewrite the op DAG inserting reshard ops on the relevant ProcessGroup. (§8.3, §11.3, I3, principle 6)
  • partition::partitioner — the driver: propagate (P5) → detect mismatches → insert → produce a fully-specified SPMD graph. (Xu et al. 2021, GSPMD §3, ADR-9, I3)
  • Optimization: minimize inserted communication (e.g. defer allgather, fuse reshards). (principle 3, MM1, §2.7 consequence 4, Narayanan et al. 2021)

18.3 Deliverable

  • A partitioned SPMD graph for distributed matmul / data-parallel / model-parallel programs; runs and matches the oracle.

18.4 Acceptance Criteria

  • Every op receives operands in its required sharding (I3); result == np=1 oracle within #349's numeric bounds, verified across all 6 resharding transitions in the §8.3 table (partition/reshard_all_cases.json).
  • Distributed matmul (sharded contraction) inserts the correct allreduce/reduce-scatter in 100 % of partition/distributed_matmul.json cases.
  • Data-parallel (replicated params, sharded batch) and model-parallel (sharded weights) both work, each verified on ≥ 3 mesh shapes (partition/data_parallel.json, partition/model_parallel.json).

18.5 Conformance Fixtures

  • partition/distributed_matmul.json, partition/data_parallel.json, partition/model_parallel.json, partition/reshard_all_cases.json (§8.3 table).

18.6 Pitfalls

  • Choosing the cheapest resharding (allgather vs all-to-all vs reduce-scatter) — the wrong choice is correct but slow.
  • Partial→Replicated needs allreduce; Partial→Sharded needs reduce-scatter — confusing these gives wrong results.
  • Insertion order / fusing reshards without changing semantics.
  • A reshard on the wrong process group (axis) → wrong ranks communicate → wrong result.

18.7 Performance Concerns

  • Communication volume is determined here — the partitioner's choices dominate distributed performance.
  • Minimize/fuse collectives; prefer reduce-scatter+allgather over allgather+allreduce where cheaper.

18.8 Edge Cases

  • Already-correct sharding (no insertion); chained reshards (collapse); a program needing all-to-all (axis swap).

18.9 Failure Analysis

  • A wrong insertion is the highest-severity correctness bug → vs np=1 oracle across world sizes (I3) + the full §8.3 case fixtures + cross-rank hash (I5).
  • docs/failure-analysis/ for partition bugs.

18.10 Operational Notes

  • CollTrace.reshard_inserted + the chosen collectives logged per op; dag_viz shows the partitioned graph; document the resharding decision table.

19. Phase 7 — Distributed ops: matmul, elementwise, reductions (kernels + #349)

19.1 Objectives

  • Implement the distributed ops the partitioner emits: distributed matmul (SUMMA-style / sharded contraction), elementwise, and distributed reductions — local compute via #349, glued by collectives.

19.2 Detailed Implementation Steps

  • kernels::matmul_bridge — local matmul = #349 GEMM over MatViews; distributed matmul = local GEMM on shards + the inserted collective (reduce-scatter/allreduce for the contracted axis). (ADR-10, principle 10, §8.10, Golub & Van Loan ch.1)
  • SUMMA: broadcast row/col panels along mesh axes, local GEMM, accumulate — the canonical 2D distributed matmul. (Golub & Van Loan, §8.10, Narayanan et al. 2021, ADR-10)
  • kernels::elementwise — local elementwise on shards (sharding flows through, no comm). (principle 1, §17.2 propagation, ADR-10)
  • kernels::reduce_local — the local part of a distributed reduction; the collective completes it. (§8.4, Chan et al. 2007, I6, principle 2)
  • Integrate with the partitioner: distributed op = local kernel + reshard collectives. (I3, §18.2, principle 6)

19.3 Deliverable

  • Distributed matmul + elementwise + reduction over a mesh; examples/distributed_matmul; matches oracle.

19.4 Acceptance Criteria

  • Distributed matmul result == np=1 oracle within #349's bounds across mesh shapes.
  • Per-rank GEMM ≥ 80 % local peak (reuse #349); for compute-bound shapes, comm is not the bottleneck (with overlap, P9).
  • Elementwise/reduction correct under all shardings.

19.5 Conformance Fixtures

  • exec/distributed_matmul_shapes.json, exec/summa.json, exec/elementwise_sharded.json, exec/reduction_partial.json.

19.6 Pitfalls

  • SUMMA panel broadcast vs the contraction collective — get the mesh-axis roles right.
  • Local shard shapes must be consistent for the GEMM (the partitioner guarantees this).
  • Mixed dtype (bf16 compute, f32 accumulate) — define and test.
  • Numerical: distributed reduction order differs from single-process → within bounds, det-mode for bit-identity.

19.7 Performance Concerns

  • Compute-bound shapes: comm should overlap (P9); comm-bound shapes: minimize collective volume (P6).
  • #349 efficiency per rank is the local lever; collective bandwidth the global one.

19.8 Edge Cases

  • 1×N / N×1 meshes (1-D parallelism); tiny matrices (comm-dominated); large K contraction (the reduce dominates).

19.9 Failure Analysis

  • A distributed-op bug → wrong result, hard to localize → np=1 oracle + per-shape fixtures + cross-rank hash.

19.10 Operational Notes

  • Trace per-op local GEMM GFLOP/s + collective bandwidth; document SUMMA and the sharded-contraction patterns.

20. Phase 8 — Execution engine: op DAG + scheduler

20.1 Objectives

  • Build the executor: turn a partitioned graph into a scheduled execution respecting dependencies (I11), assigning ops to streams (I10).

20.2 Detailed Implementation Steps

  • exec::graph — the op DAG (local + collective ops, dependency edges). (§11.7, principle 1, ADR-3)
  • exec::scheduler — topological order; assign independent ops to different streams; ready-queue execution. (I10, I11, ADR-12, §3.5)
  • exec::stream_exec — per-stream ordered execution; cross-stream ordering only via explicit deps (I10). (I10, principle 4, §8.6)
  • exec::executor — the SPMD driver: every rank runs the same scheduled graph over its shards. (ADR-3, principle 1, §3.5)
  • Dependency tracking: an op runs only when all deps (local + collective completion) are satisfied (I11). (I11, §8.6, §8.11)

20.3 Deliverable

  • Execute a multi-op partitioned graph (e.g. a small transformer layer's matmuls + allreduces) SPMD; matches oracle.

20.4 Acceptance Criteria

  • Result == np=1 oracle for multi-op graphs of ≥ 10 ops (I11), verified via exec/dag_multi_op.json.
  • Independent ops scheduled on separate streams (I10); dependencies respected in 100 % of exec/dependency_order.json and exec/stream_assignment.json cases.

20.5 Conformance Fixtures

  • exec/dag_multi_op.json, exec/dependency_order.json, exec/stream_assignment.json.

20.6 Pitfalls

  • Missing a dependency edge (collective completion → consumer) → use-before-ready → wrong result.
  • Stream assignment that accidentally serializes everything (over-conservative deps).
  • Collective completion signaling (async) → the consumer must wait correctly.

20.7 Performance Concerns

  • Scheduling quality determines overlap opportunity (P9); a serial schedule wastes the network.
  • Ready-queue overhead small vs op cost.

20.8 Edge Cases

  • Single-op graph; fully serial graph (chain); fully parallel (independent ops); a cycle (reject — must be a DAG).

20.9 Failure Analysis

  • A scheduling/dependency bug → nondeterministic wrong result → DAG dependency assertions (I11) + oracle + det-mode golden.

20.10 Operational Notes

  • tools/dag_viz shows the scheduled DAG + stream assignment; CollTrace/op timing per stream.

21. Phase 9 — Compute/communication overlap + streams

21.1 Objectives

  • Realize overlap: hide collective communication behind independent computation via streams + dependency-aware scheduling (principle 4) — the headline perf lever (≥ 80 % comm hidden).

21.2 Detailed Implementation Steps

  • exec::overlap — schedule a collective on a comm stream, then run independent compute on a compute stream while it's in flight; the consumer waits on both. (principle 4, I10, I11, §4.2, MM4)
  • Async collectives: post + wait (non-blocking) so compute proceeds during communication. (§11.11, ADR-12, §8.11, Sergeev & Del Balso 2018)
  • Tensor/collective fusion (Horovod-style): batch small collectives to amortize α. (Sergeev & Del Balso 2018, §4.1, ADR-5)
  • Coordinate the #349 compute pool with the network threads (no oversubscription, ADR-25). (ADR-25, §3.5, principle 10)

21.3 Deliverable

  • Overlapped execution; bench shows comm hidden behind compute; speedup vs the serial schedule.

21.4 Acceptance Criteria

  • ≥ 80 % of overlappable communication hidden (measured: total time vs max(compute, comm)).
  • Correctness unchanged vs P8 (overlap doesn't reorder dependent ops, I11).
  • Fusion reduces small-collective overhead measurably.

21.5 Conformance Fixtures

  • exec/overlap_correctness.json (== oracle), exec/overlap_speedup.json, exec/collective_fusion.json.

21.6 Pitfalls

  • Overlap that violates a dependency → wrong result (the classic correctness-vs-speed trap) — deps are sacred (I11).
  • Stream/resource contention (comm and compute both want memory bandwidth).
  • Fusion changing reduction order → det-mode must still be reproducible.
  • Async collective completion races.

21.7 Performance Concerns

  • The win is bounded by min(compute_time, comm_time) — fully comm-bound graphs can't overlap away all comm.
  • Stream count vs contention; chunk size affects overlap granularity.

21.8 Edge Cases

  • No independent compute to overlap (serial chain → no win); comm ≫ compute (comm-bound, limited win); single stream.

21.9 Failure Analysis

  • An overlap bug is a heisenbug (timing-dependent wrong result) → dependency assertions + det-mode golden + stress under load.
  • docs/runbooks/comm-bound-job.md: measure overlap %, increase it or reduce comm volume.

21.10 Operational Notes

  • CollTrace.overlapped_ns (comm hidden); document the overlap model and fusion thresholds in docs/performance/overlap.md.

22. Phase 10 — Failure detection + bounded recovery (fail-stop)

22.1 Objectives

  • Detect a dead/non-responsive rank within a bound and fail-stop the job cleanly with diagnostics (principle 8, I12). In-job recovery/elasticity deferred.

22.2 Detailed Implementation Steps

  • runtime::failure_detector — heartbeat (SWIM-lite, #197): periodic pings, suspicion, confirmation; detect within k·heartbeat (I12). (ADR-15, I12, §4.3, Tanenbaum & van Steen ch.6)
  • Integrate with collectives: a stalled collective queries the detector; a dead peer → abort the collective, not hang. (I12, principle 8, §8.8 collective state machine)
  • Clean abort: propagate failure to all ranks (via coordinator/gossip), each dumps diagnostics (which collective, which peer, in-flight state). (ADR-14, principle 8, I12)
  • Timeouts on barrier/collective/transport tied to the detector. (I9, I12, principle 8, §4.3)

22.3 Deliverable

  • Kill a rank mid-job → detected within the bound → all ranks abort cleanly with a diagnostic; examples/fault tests.

22.4 Acceptance Criteria

  • A dead rank detected within < 3×heartbeat (I12); the job never hangs silently.
  • All surviving ranks receive the failure notification and abort cleanly with consistent diagnostics.
  • A slow (not dead) rank is not falsely killed below threshold (tunable).

22.5 Conformance Fixtures

  • fault/kill_rank_mid_allreduce.json, fault/slow_rank_no_false_positive.json, fault/clean_abort_diagnostics.json.

22.6 Pitfalls

  • False positives (a slow rank declared dead) → tune suspicion + confirmation (SWIM's indirect probes).
  • Failure during failure-handling (cascading) → bounded, idempotent abort.
  • Split detection (some ranks think a peer is dead, others don't) → confirmation round.
  • Distinguishing "dead" from "slow network" is fundamentally ambiguous → bound + document.

22.7 Performance Concerns

  • Heartbeat overhead small; detection latency vs false-positive rate is the tradeoff (the SWIM tuning).

22.8 Edge Cases

  • Coordinator dies (vs a worker); network partition (split-brain — abort all, document); simultaneous multi-rank failure.

22.9 Failure Analysis

  • Silent hang is the worst outcome → timeouts everywhere tied to the detector (I12); docs/runbooks/hang-diagnosis.md + docs/failure-analysis/straggler.md.
  • In-job recovery (continue with fewer ranks / restore checkpoint) is explicitly deferred (PhaseDeferred).

22.10 Operational Notes

  • RuntimeTrace.detect_ms, rank_dead; document the heartbeat/suspicion tuning and the abort protocol.

Compatibility & Versioning

  • Wire protocol: versioned frames; the version is negotiated at handshake (I14); incompatible peers refuse to join (no silent corruption). Wire version is tracked separately from the library SemVer (ADR-29).
  • C/Python ABI: function signatures, error codes, handle semantics frozen (SemVer-major to change).
  • Collective semantics: mirror the MPI standard (ordering, root, reduce ops) — stable.
  • Numeric behavior: inherits #349 — backward-error bounds, not bit-reproducibility across world sizes/algorithms; deterministic mode (fixed reduction order) is a stable, bit-reproducible contract. Changes within bounds = minor + CHANGELOG.
  • Sharding spec: the ShardSpec model + propagation rules are stable; new ops extend, don't break (#[non_exhaustive]).
  • Mesh API: named-axis model stable.
  • Deprecation: one minor-version warning cycle; mixed-version within a job is not supported (rolling restart, not rolling upgrade).
  • ABI stability matrix: libdtr.so exports are stable within a major version; new exports are additive. The dtr.h header is the source of truth — it is generated from the Rust types, not hand-maintained. Any change that would alter a sizeof(DtrHandle) or a function signature triggers a major bump.
  • Behavioral compatibility: algorithm selection (ring vs RHD vs tree) is an implementation detail, not a behavioral contract — the runtime may change which algorithm it selects as the cost model is recalibrated, without a version bump, as long as the result is still within the documented numeric bounds and the bytes-moved constraint (I4) is preserved.

Testing & Verification Strategy

  • Single-process oracle (the backbone): every program run at world_size=1 is the trusted result (principle 14).
  • Differential across world sizes: run at {1,2,4,8,…}, compare to the oracle within bounds; cross-rank hash for collective identity (I5).
  • MPI-semantics tests: collective behavior vs the MPI standard (ordering, roots, reduce ops).
  • Property (proptest): sharding propagation rules; resharding-collective selection (§8.3); cost-model monotonicity.
  • Fuzz (cargo-fuzz): frame parser, shardspec validation, reshard planner, cost model (I7/I2/I15); ASAN/Miri.
  • Fault injection: kill/drop/delay/reorder/corrupt/slow (seeded, reproducible) → assert detection + clean abort (I7/I12).
  • Concurrency: TSan on the executor/streams/transport; overlap correctness vs oracle (I11); deadlock detection (timeouts).
  • Determinism: golden hashes per (program, mesh, algorithm) in det-mode (I6).
  • Multi-rank harness: docker-compose N-container cluster for CI; real multi-host nightly.
  • Soak/chaos (deferred): long fault soak, large-N multi-host → PhaseDeferred.
  • Performance regression: collective bandwidth/latency + overlap gates. A 5% regression in ring allreduce bandwidth-%-of-bound or in overlap% blocks merge; a 10% regression in barrier latency or detection time triggers a mandatory investigation before merge.
  • Test isolation: every multi-rank test uses a fresh coordinator and ephemeral ports (no shared state between test cases); the docker-compose harness assigns a unique network per test run to prevent cross-test interference. The RUST_LOG=dtr=debug flag enables per-rank structured logging for post-mortem diagnosis of any flaky multi-rank test.

Performance Engineering

  • Cost model first: every collective placed against the α–β model + the bandwidth-optimal bound; the ring/RHD crossover is the canonical tuning artifact.
  • Profiling: distributed timeline (merged per-rank traces), network counters (bandwidth, retransmits), perf on the data plane, flamegraphs.
  • Overlap analysis: measure comm hidden behind compute (overlapped_ns / comm_ns); the headline lever (≥ 80 %).
  • Transport tuning: socket buffers, TCP_NODELAY for control, multiple connections for bandwidth, zero-copy writev.
  • Collective tuning: chunk size, stream count, fusion thresholds, hierarchical (intra/inter-node) topology.
  • Local compute: delegate to #349; per-rank GEMM efficiency is its own lever.
  • Determinism cost: det-mode (fixed reduction order) has a measured overhead — reported. On comm-bound workloads the overhead can be 5–15% (less pipelining freedom); on compute-bound workloads it is negligible. Always benchmark before disabling in production.
  • Roofline model: for each collective, plot achieved bandwidth vs message size against the α–β model prediction. A point far below the roofline indicates a transport bug, a serialization bottleneck, or a miscalibrated NetParams. A point above the roofline indicates measurement error (warmup missing, clock skew).
  • Scaling efficiency: defined as speedup(N) / N; ideal = 1.0. Communication overhead drives this below 1 — the partitioner (P6) and overlap (P9) are the tools to recover it. Track scaling efficiency at N = {2, 4, 8, 16, 32, 64} in the nightly bench suite.
  • Targets: §4 (M1–M12) — enforced by the multi-host bench gate. Regressions ≥ 5% against M1 (bandwidth-%-of-bound) or M4 (overlap%) block merge; a ≥ 10% regression against M9 (failure detection time) or M7 (barrier latency) triggers a mandatory investigation before merge.

Scalability Analysis

  • Collective scaling: ring allreduce moves 2(N−1)/N·D bytes/rank → bandwidth term is N-independent (good), latency term grows O(N) (bad for small D) → RHD/tree for small D; hierarchical collectives for multi-level networks are the large-N lever.
  • The communication wall: as model/data scales, communication volume can dominate compute → overlap (P9) + partitioning choices (P6) + topology-aware collectives (P12) are the escapes; beyond that, the network is the ceiling.
  • Bootstrap/coordinator scaling: all-to-coordinator is O(N) → tree/gossip bootstrap for large N (target < 5 s at N≤1024); the coordinator is bootstrap-only (not in the data path).
  • Failure-detection scaling: SWIM-style gossip is O(1) load/rank, detection time O(log N) — scales.
  • Partitioner scaling: graph analysis is cheap; the quality of sharding/resharding choices determines communication volume (the real scaling factor).
  • What does NOT scale here (by design): a single rank's local compute (that is #349's job, per-rank); sparse (that is #350). This runtime scales the gluing of many local computes.
  • Memory scaling: collectives stream in O(chunk) buffers (I8/principle 13); sharding keeps per-rank tensor memory O(global/N).
  • Transport scaling: a single TCP connection per peer pair saturates at ~25 GB/s; multiple connections per peer (P12) scale to 100+ Gb/s links. The credit/window (I8) must scale with BDP = link_BW × RTT — a window calibrated for 1 GbE will starve a 100 GbE link.
  • Determinism scaling: the canonical reduction order in det-mode is rank-ascending; this order is a global barrier over all ranks → det-mode does not scale as well as default mode. For large N, det-mode latency grows O(N) in the worst case; the trade-off is always documented (§8.12, ADR-16).
  • Algorithm-selection scaling: the cost-model crossover D* = α·N/β grows with N — at N=1024 the crossover is ~128× the N=8 crossover, meaning ring is preferred for a much wider range of message sizes at large N. This is a structural property of the α–β model (§4.1, MM5) and must be re-calibrated when N changes significantly.

Mental Models & First Principles

MM1: ShardSpec is a type, not an annotation — the partitioner is a type-checker inserting collectives where types mismatch.

  • Predicts: every Partial→Replicated transition MUST emit an allreduce; no exceptions.
  • Bug class without it: silent full-replication (gather without acknowledgment) → O(N) hidden traffic.
  • Applies at: §8.3, P6 (§18).

MM2: Allreduce = reduce-scatter + allgather — these are not two algorithms, they are one algorithm split into two phases.

  • Predicts: ring allreduce's bandwidth optimality (2(N−1)/N·D bytes/rank) follows directly from the two-phase decomposition.
  • Bug class without it: monolithic allreduce implementations that cannot be split for ZeRO-style optimizer sharding.
  • Applies at: §8.4, P3 (§15), §5.2 paper 3.

MM3: Partial is a reduction-pending state, not a value — a tensor in Partial(sum) state cannot be read until it's been reduced.

  • Predicts: any op consuming a Partial without a preceding allreduce/reduce-scatter is a correctness bug.
  • Bug class without it: using a local GEMM output (which is Partial after a sharded contraction) as if it were a replicated value → wrong numerics that are numerically plausible and hard to detect.
  • Applies at: §8.2, §8.3, P5 (§17), P6 (§18).

MM4: Overlap ceiling theorem — the maximum speedup from hiding communication is bounded by max(compute, comm)/serial_time; when comm > compute the job is comm-bound and overlap alone cannot save it.

  • Predicts: overlap % is a useful metric only when compute ≥ comm; otherwise the fix is reducing communication volume.
  • Bug class without it: over-investing in overlap infrastructure on a comm-dominated workload while neglecting partitioning quality.
  • Applies at: §4.2, P9 (§21), §2.8.

MM5: α–β crossover is cluster-specific — there is no universal "ring is always best" rule; the message-size threshold D* only exists when α and β are measured for the actual cluster.

  • Predicts: a cost model hard-coded to one cluster's parameters will pick the wrong algorithm on a different cluster.
  • Bug class without it: choosing ring for all messages on a high-latency WAN cluster (where RHD is 10× faster for small gradients).
  • Applies at: §4.1, §8.4, P4 (§16), ADR-5.

MM6: The coordinator must leave the data path — a coordinator that stays in the data path becomes a bottleneck and a single point of failure; it is useful exactly during bootstrap (O(N) table exchange) and failure notification, and nowhere else.

  • Predicts: any design where allreduce bytes route through the coordinator will not scale past ~100 ranks.
  • Bug class without it: adding "convenient" coordinator-mediated synchronization to the hot path → serialization bottleneck.
  • Applies at: §8.13, principle 9, P2 (§14), P10 (§22).

MM7: Determinism vs reproducibility are orthogonal concerns — cross-rank identity (I5: all ranks end a collective with the same bits) is an algorithmic property enforced by symmetry; cross-run reproducibility (I6: same result on a second run) requires fixing the reduction order. You can have I5 without I6 (nondeterministic but consistent within a run).

  • Predicts: a non-deterministic mode that passes all cross-rank hash checks is still non-reproducible across runs with different world sizes.
  • Bug class without it: assuming cross-rank identity implies cross-run reproducibility → training runs that diverge on restart.
  • Applies at: §8.12, §7 I5/I6, P3 (§15), P13 (§25).

MM8: The transport is a contract, not a detail — the wire protocol's frame format, versioning, checksum, and flow-control semantics are load-bearing; changing them silently breaks mixed-version clusters during rolling upgrades.

  • Predicts: any frame field change without a version bump will corrupt data in production.
  • Bug class without it: "quick fix" that changes message encoding without bumping the wire version → silent data corruption during a rolling restart.
  • Applies at: §8.7, principle 12, I7/I14, P1 (§13).

NCCL 2.x chose to be a pure collective library with no sharding model: the GPU driver and topology detection are its unique value, and it delegates the "which collective to insert" question entirely to the caller (cuDNN, NCCL-PyTorch). Its lack of a sharding spec is not an oversight — NCCL's callers (PyTorch, Megatron) supply the placement logic.

Gloo made the opposite bet from NCCL: prioritize portability over peak performance. Its TCP transport and flat algorithm selection mean it works anywhere, but it cannot exploit NVLink topologies and its per-call manual selection requires the caller to know message sizes at compile time. It wins for CPU-only clusters and for PyTorch's CPU backend where a simpler dependency is worth more than 10% extra bandwidth.

MPICH is the reference implementation of MPI collectives and its coll/ module is the most complete algorithm zoo in existence — Rabenseifner's allreduce, Bruck's all-to-all, and a cost-model selector tuned over decades of HPC measurements. It wins on HPC CPU clusters where the MPI standard compliance is non-negotiable and the algorithm library depth matters. Its weakness is that it has no sharding/partitioner concept: the application manages data layout manually.

Mesh-TensorFlow + GSPMD is the direct intellectual ancestor of this runtime's §8.1–§8.3: named mesh axes and automatic collective insertion via XLA compiler passes are exactly the model we replicate. It wins at Google scale on TPUs where the ICI interconnect and XLA's whole-program optimization make the compiler-driven approach vastly more powerful than any hand-tuned collective schedule. The XLA coupling is deep — HLO passes, TPU ICI semantics, and the XLA device mesh are inseparable from the sharding logic.

PyTorch FSDP + DTensor operationalized ZeRO-3 as a production training primitive and introduced the DeviceMesh + Placement API that directly influenced §11.2 of this runtime. It wins for PyTorch-native teams where the framework integration (autograd, optimizer hooks) is more valuable than a from-scratch transport. Its limitation is that FSDP's collective schedule is fixed (reduce-scatter in backward, allgather in forward) and the DTensor API, while general, is not yet a full SPMD partitioner in the GSPMD sense.

Back-of-Envelope Capacity Model

Derived from §4 System Constraints. Symbols: N = world size, D = tensor bytes, α = per-message latency (s), β = 1/bandwidth (s/byte), chunk = ring buffer size (bytes).

1. Ring allreduce bytes/rank Formula: 2·(N−1)/N·D Example: N=64, D=1 GB → 2·63/64·1e9 = 1.969 GB moved per rank. This is essentially 2D for large N, and it is N-independent in the limit — the key bandwidth-optimality result.

2. Ring allreduce time (bandwidth-dominated) Formula: 2·(N−1)/N·D·β Example: N=64, D=1 GB, link=25 GB/s (β=40 ps/byte) → 1.969e9 · 40e-12 = 78.7 ms. At 90% efficiency (§4 target) this is ~87 ms wall-clock.

3. RHD allreduce time (latency-dominated) Formula: 2·log₂N·α Example: N=64, log₂64=6, α=5 µs → 2·6·5e-6 = 60 µs for a small (1 KB) message. Compare ring for the same message: 2·63·5µs = 630 µs — RHD is 10× faster on latency-dominated workloads.

4. Crossover message size D* Ring and RHD share the same bandwidth term; the choice is driven by the latency term. Ring's latency = 2(N−1)·α; RHD's latency = 2·log₂N·α. The practical crossover where ring's bandwidth efficiency starts justifying its higher latency is empirically: D* ≈ α·N / β (ignoring constants). Example: N=64, α=5µs, β=40ps/byte → 5e-6·64 / 40e-12 ≈ 8 MB. Below 8 MB prefer RHD; above prefer ring. This number must be measured per cluster — it varies by 10× between a 1 GbE LAN and a 200 Gb/s InfiniBand fabric.

5. Per-rank tensor memory (sharded) Formula: global_bytes / N Example: 7B parameter model, f32 (4 bytes/param) = 28 GB total; N=64 → 28e9/64 = 437 MB per rank. This is the ZeRO-3 parameter sharding budget. At N=512 it drops to 54 MB/rank — fitting comfortably in CPU DRAM even for large models.

6. Overlap opportunity Formula: min(compute_time, comm_time) / serial_time Example: backward=40 ms, allreduce=30 ms, serial=70 ms → min(40,30)/70 = 42.9% max speedup from overlap; wall-clock floor = max(40,30) = 40 ms (vs 70 ms serial = 1.75× speedup). When comm > compute, say backward=25 ms and allreduce=45 ms: floor = 45 ms, overlap saves only 25/70 = 35.7% — the job is comm-bound and needs less communication, not more overlap.

7. Transport in-flight bytes (flow control window) Formula: window_bytes ≥ 2 × BDP where BDP = link_BW × RTT Example: 25 GB/s link, RTT=200µs → BDP = 25e9·200e-6 = 5 MB; recommended window = 10 MB. Setting the window too small (< BDP) starves the pipe; too large risks OOM under a slow receiver. The JobConfig.window_bytes default is 2×BDP of the expected cluster.

8. Barrier latency (dissemination) Formula: log₂N · (α + small_msg_time) Example: N=64, α=5µs, 8-byte msg at 25 GB/s (negligible) → 6·5µs = 30 µs. This is the §4 "O(log N) rounds" target. Compare a naive all-to-coordinator barrier: N·α = 64·5µs = 320 µs — 10× worse, and it scales O(N).

9. Bootstrap table size Formula: N · (hostname + port) ≈ N · 64 bytes Example: N=1024 → 1024·64 = 65 KB — tiny; the O(N) cost is in the coordinator fan-out (N TCP connections + N×64 bytes broadcast), not in the data volume. For N=1024, a 1 Gbit coordinator link can broadcast the table in 65e3·8 / 1e9 = 0.5 ms — the latency cost (N serial round trips) dominates, motivating the tree-broadcast for large N (§8.13, §4.3).

10. Failure detection latency Formula: k · heartbeat_interval Example: k=3, heartbeat=200ms → 600 ms detection bound. SWIM indirect probes reduce false positives without changing the detection bound — a slow rank is probed via a third party before being declared dead. At N=1024, gossip-style SWIM disseminates failure information in O(log N) = ~10 gossip rounds at heartbeat_interval each → ~2 s for full dissemination at 200 ms intervals. The §4 target of < 3×heartbeat is for detection, not full dissemination.

              [Parameter Server]
                      │
     ┌──────────────┬─┴──────────────┐
   pull           pull             pull
  worker_0      worker_1         worker_N

Winning regime: Sparse/embedding gradient updates where only a fraction of parameters change per step — recommendation models with O(10^10) sparse embedding lookups. Each worker touches a tiny subset, so allreduce is wasteful; the PS sends only the touched rows. Also wins when workers are heterogeneous (different speeds) because the PS can batch updates asynchronously.

Real system: Google DistBelief (Dean et al. 2012), Petuum (Ho et al. 2013), MXNet KVStore.

Why rejected: Synchronous dense gradient allreduce (the dominant pattern for transformer training) is more efficient as a peer-to-peer ring — no bottleneck server. The PS is a bandwidth bottleneck at scale. This project's goal is to build the collective substrate, not the parameter storage layer. #250 in the portfolio is the PS — the two are complementary, not competing.

Alt 2: MPI-style Communicator (Static Allocation + Library Call)

  [MPI_Comm_world]  ─── pre-allocated, static rank assignment
  rank_0  rank_1  rank_2  rank_3
    │       │       │       │
  MPI_Allreduce(comm, buf, count, MPI_FLOAT, MPI_SUM)
    │       │       │       │
  [opaque: ring/RHD/tree/Rabenseifner per msg size]
    │       │       │       │
  [return: all ranks have reduced result]

Winning regime: HPC scientific codes where (a) a portable, standard-compliant API is required, (b) the implementation quality of OpenMPI/MPICH is unmatched, and (c) the application manages data layout manually. Also wins for learning collective algorithms without building the full runtime.

Real system: Open MPI, MPICH, Intel MPI.

Why rejected: Using MPI would defeat the "from scratch" learning goal (#179 is the MPI study project). MPI has no sharding-spec or partitioner concept. The Rust/C++ boundary friction is real. MPI's communicator model doesn't compose as cleanly with a typed ShardSpec system. This runtime re-derives MPI's semantics (§5.4) without taking MPI as a dependency.

Alt 3: Actor-Model Collective Runtime (Ray-style)

  GradientWorker.remote()   GradientWorker.remote()
        │                           │
        └──── ray.get(allreduce) ───┘
                     │
           [Ray Object Store / GCS]
           (shared object refs, not ring buffers)
                     │
        ┌────────────┴────────────┐
  Worker.reduce()          Worker.reduce()
  (actors own shards;      (actors own shards;
   futures resolve           futures resolve
   collectively)              collectively)

Winning regime: Heterogeneous, dynamically-sized pipelines where rank count changes mid-job (elastic training), tasks have variable duration and work-stealing is valuable, and the collective is a small fraction of work (sparse MoE, RL, simulation + ML hybrid workloads). Also wins for fault tolerance: actor death restarts one actor, not the whole job.

Real system: Ray (Moritz et al. 2018, OSDI), Ray Train, Alpa's inter-op planner.

Why rejected: Actor-model overhead (object store serialization, GCS metadata) is measurable on the hot path of a synchronous allreduce. GC/scheduling jitter hurts collective latency tails. The actor model does not map cleanly to SPMD — every rank runs the same program; there is no per-actor heterogeneous logic. Rust ownership + async streams gives us the needed concurrency without the actor overhead.

Glossary

  • α–β (Hockney) model — T(n) = α + β·n per message (α latency, β = 1/bandwidth); basis for algorithm selection.
  • Allgather — every rank ends with the concatenation of all ranks' data.
  • Allreduce — every rank ends with the reduction (sum/max/…) of all ranks' data; = reduce-scatter + allgather.
  • All-to-all — each rank sends a distinct chunk to every other rank (axis swap).
  • Barrier — no rank proceeds until all arrive.
  • Bootstrap / rendezvous — the process by which ranks discover each other and agree on the world.
  • Broadcast — one rank's data sent to all.
  • Bruck algorithm — a log₂N-step all-to-all / allgather (latency-efficient for small messages).
  • Chunk — a sub-piece of a tensor circulated in a ring/streamed collective (bounds memory, enables overlap).
  • Collective — a communication operation involving a group of ranks.
  • Collective fusion — batching multiple small collectives into one larger call to amortize the α latency overhead; analogous to Nagle's algorithm for TCP; implemented in P9 (§21).
  • Cost model — analytic prediction of a collective's time (§8.4).
  • DeviceMesh — an n-dim grid of ranks with named axes.
  • DTensor — PyTorch's DeviceMesh + placement-spec API (introduced PyTorch 2.0); the closest publicly available analogue to this runtime's §11.2 types.
  • Deterministic mode — fixed reduction order → bit-reproducible across runs.
  • Fail-stop — on a rank failure, the job halts cleanly (vs continuing degraded).
  • FSDP (Fully Sharded Data Parallel) — PyTorch's ZeRO-3 implementation: reduce-scatter gradients during backward, allgather parameters during forward; expressed as ShardSpec transitions in this runtime.
  • Failure detector — heartbeat/SWIM mechanism bounding how fast a dead rank is noticed.
  • Flow control — credit/window scheme bounding in-flight bytes.
  • GPUDirect — NVIDIA technology enabling direct RDMA transfers between GPU memory and NIC, bypassing the CPU; deferred in this runtime (§24.2, ADR-7).
  • Overlap — running computation concurrently with in-flight communication.
  • Partial — a sharding state meaning "reduction pending" (after a sharded contraction).
  • Partitioner — infers shardings + inserts resharding collectives (GSPMD).
  • Process group — the subset of ranks participating in a collective (a mesh-axis slice).
  • Rank / world size — a process's id in [0,N) / the number of ranks N.
  • Rendezvous — the handshake where sender and receiver agree on a buffer transfer before bulk data moves; prevents unbounded buffering; implemented in §8.7, §8.13, P1 (§13).
  • Recursive halving-doubling (RHD) — latency-optimal (log N) allreduce.
  • Reduce-scatter — reduction whose result is scattered (each rank gets one piece).
  • Reshard — change a tensor's sharding (emits a collective, §8.3).
  • Ring algorithm — bandwidth-optimal collective circulating chunks around a logical ring.
  • ShardSpec — per-dimension sharding annotation (Replicated/Sharded/Partial).
  • SPMD — single program, multiple data: every rank runs the same program over its shard.
  • Straggler — a slow rank that delays a collective/barrier.
  • Stream — an independent ordered execution/communication queue (enables overlap).
  • SUMMA — scalable universal matrix multiply (2D distributed GEMM).
  • Transport — the reliable ordered messaging layer (TCP here).
  • Wire protocol — the versioned, checksummed frame format defined in §8.7; negotiated at handshake (I14); changes require a wire-version bump to preserve mixed-version compatibility.
  • ZeRO (Zero Redundancy Optimizer) — Rajbhandari et al. 2020 (SC); shards optimizer state (ZeRO-1), gradients (ZeRO-2), and parameters (ZeRO-3) across ranks; expressed as reduce-scatter + allgather patterns over this runtime's collectives; a primary consumer pattern for #115.
