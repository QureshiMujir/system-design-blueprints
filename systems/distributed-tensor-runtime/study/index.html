Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. A training job on N=128 ranks spends 35% of step time in allreduce and 65% in backward compute. You have budget to either (a) double the network bandwidth or (b) implement tensor fusion + overlap. Which do you choose and why? (§4.2, §8.4, §21, MM4)
  2. A rank produces a tensor in Partial(sum) state after a sharded matrix contraction. The partitioner has a choice: insert allreduce (→ Replicated) or reduce-scatter (→ Sharded). What decides which to insert, and what is the memory and bandwidth cost difference between the two choices for a 256 MB gradient tensor on N=32 ranks? (§8.3, §8.4, §18, MM1)
  3. You observe that ring allreduce on your cluster achieves only 60% of the bandwidth-optimal bound. Walk through the four most likely causes and how §4 + §8.7 + §13 would diagnose each. (§4, §8.4, §8.7, §13, §24)
  4. Explain why world_size=1 is a correct oracle for testing the distributed runtime even though it exercises no collective code paths. What class of bugs does it catch vs miss? (§1.11, §3.4, §12, §25, principle 14)
  5. A RHD allreduce on N=48 ranks (non-power-of-two) produces a wrong result on some ranks. List the algorithmic edge cases that must be handled and which fixtures test them. (§8.4, §8.5, §16, §25, I5)
  6. The SPMD partitioner inserts an all-to-all where you expected a reduce-scatter. Trace the sharding spec transition that mandates all-to-all vs reduce-scatter. Under what mesh configuration does this arise? (§8.2, §8.3, §8.14, §18, MM1)
  7. A job hangs silently 30 minutes in. Describe the full diagnosis tree using §22 + §8.8 + the runbooks — which telemetry signals you check first, what each signal rules in or out. (§7 I9/I12, §8.8, §22, Operational Readiness, MM6)
  8. You need to add a new dtype (fp8) to the runtime. List every place in the codebase (§10, §11, §7) that must change and every invariant that must be re-validated. (§7, §10, §11, §13, ADR-17)
  9. Compare the communication pattern of data parallelism, tensor (model) parallelism, and pipeline parallelism as expressed as ShardSpecs + inserted collectives over this runtime. Which uses allreduce, which uses reduce-scatter+allgather, which uses point-to-point? (§3.4, §8.3, §8.10, §18, §5.2 papers 7/8)
  10. A production job's overlap% drops from 78% to 31% after a model architecture change that added a large attention layer. Using §4.2 + §21 + CollTrace, diagnose whether this is a scheduling issue or a compute/comm ratio issue, and prescribe the fix. (§4.2, §8.6, §21, Operational Readiness, MM4)
  11. The wire protocol needs a new frame type for a future RDMA path. Walk through the change management: which invariants, ADRs, and compatibility guarantees govern the process, and what wire version bump is required. (§8.7, §9 ADR-20/29, §11.6, Compatibility & Versioning, I14)
  12. You are debugging a test where det-mode produces different golden hashes on the second run. What is the minimal set of conditions that guarantee cross-run reproducibility, and which of those conditions is most likely violated? (§8.12, §7 I5/I6, §15 P3, §25, MM7)
  13. Gloo uses a flat algorithm-selection policy per call site; MPICH uses a cost-model-driven adaptive policy; NCCL uses empirical auto-tuning. Justify why this runtime uses the cost-model approach (ADR-5) and identify the one regime where empirical auto-tuning would strictly win. (§5.3, §5.5, §8.4, §9 ADR-5, Comparative Architecture Table)
  14. A ShardSpec has tensor dim 0 sharded over the data axis and dim 1 sharded over the model axis. The next op is a matmul contracting over dim 1. What does the partitioner infer as the output ShardSpec, and what collective does it insert? Derive the bytes moved for a 512×256 tensor on a 4×4 mesh. (§8.2, §8.3, §17, §18, Back-of-Envelope Capacity Model)
  15. The bootstrap coordinator is a single point of failure. For N=1024 ranks, quantify the bootstrap latency (§4.3 + Capacity Model), explain why making the coordinator highly available would complicate the protocol, and justify why the current design is acceptable. (§4.3, §8.13, §14, Back-of-Envelope item 9, ADR-18)
  16. Compare the failure detection semantics of fail-stop (this runtime), checkpoint-restart (deferred), and elastic training (deferred). For each, state the assumption about job duration and failure frequency that makes it the right choice. (§4.3, §22, Deferred Features Register, ADR-14/15, MM6)
  17. A collective arg-mismatch (I1) is detected at runtime. Explain why the detection mechanism (arg-hash exchange) does not itself deadlock, and what happens if the detection message is lost or the detecting rank is the one that dies. (§7 I1, §8.9, §14, §22, I12)
  18. The ring allreduce implementation chunks a 1 GB tensor into 64 pieces for N=64. A reviewer asks: why not chunk into 1000 pieces for finer-grained pipelining? Derive the trade-off in terms of α, β, and overlap granularity. (§8.4, §8.5, §15, §4.1, MM5)
  19. GSPMD/JAX pjit and Mesh-TensorFlow implement the same sharding propagation concept this runtime uses. What specific decisions in their implementations are XLA-specific and would not port cleanly to a Rust/CPU runtime? (§5.2 papers 4/5, §5.3, §5.5, §8.1–§8.3, Comparative Architecture Table)
  20. After adding pipeline parallelism on top of this runtime (as #115 would do), a microbatch bubble appears. Explain why pipeline bubbles are a property of the consumer (#115), not this runtime, and what primitives this runtime must expose so #115 can minimize bubbles. (§1.2, §3.4, §8.6, §11.7, §21, ADR-3) ---

Mental Models & First Principles

MM1: ShardSpec is a type, not an annotation — the partitioner is a type-checker inserting collectives where types mismatch.

  • Predicts: every Partial→Replicated transition MUST emit an allreduce; no exceptions.
  • Bug class without it: silent full-replication (gather without acknowledgment) → O(N) hidden traffic.
  • Applies at: §8.3, P6 (§18).

MM2: Allreduce = reduce-scatter + allgather — these are not two algorithms, they are one algorithm split into two phases.

  • Predicts: ring allreduce's bandwidth optimality (2(N−1)/N·D bytes/rank) follows directly from the two-phase decomposition.
  • Bug class without it: monolithic allreduce implementations that cannot be split for ZeRO-style optimizer sharding.
  • Applies at: §8.4, P3 (§15), §5.2 paper 3.

MM3: Partial is a reduction-pending state, not a value — a tensor in Partial(sum) state cannot be read until it's been reduced.

  • Predicts: any op consuming a Partial without a preceding allreduce/reduce-scatter is a correctness bug.
  • Bug class without it: using a local GEMM output (which is Partial after a sharded contraction) as if it were a replicated value → wrong numerics that are numerically plausible and hard to detect.
  • Applies at: §8.2, §8.3, P5 (§17), P6 (§18).

MM4: Overlap ceiling theorem — the maximum speedup from hiding communication is bounded by max(compute, comm)/serial_time; when comm > compute the job is comm-bound and overlap alone cannot save it.

  • Predicts: overlap % is a useful metric only when compute ≥ comm; otherwise the fix is reducing communication volume.
  • Bug class without it: over-investing in overlap infrastructure on a comm-dominated workload while neglecting partitioning quality.
  • Applies at: §4.2, P9 (§21), §2.8.

MM5: α–β crossover is cluster-specific — there is no universal "ring is always best" rule; the message-size threshold D* only exists when α and β are measured for the actual cluster.

  • Predicts: a cost model hard-coded to one cluster's parameters will pick the wrong algorithm on a different cluster.
  • Bug class without it: choosing ring for all messages on a high-latency WAN cluster (where RHD is 10× faster for small gradients).
  • Applies at: §4.1, §8.4, P4 (§16), ADR-5.

MM6: The coordinator must leave the data path — a coordinator that stays in the data path becomes a bottleneck and a single point of failure; it is useful exactly during bootstrap (O(N) table exchange) and failure notification, and nowhere else.

  • Predicts: any design where allreduce bytes route through the coordinator will not scale past ~100 ranks.
  • Bug class without it: adding "convenient" coordinator-mediated synchronization to the hot path → serialization bottleneck.
  • Applies at: §8.13, principle 9, P2 (§14), P10 (§22).

MM7: Determinism vs reproducibility are orthogonal concerns — cross-rank identity (I5: all ranks end a collective with the same bits) is an algorithmic property enforced by symmetry; cross-run reproducibility (I6: same result on a second run) requires fixing the reduction order. You can have I5 without I6 (nondeterministic but consistent within a run).

  • Predicts: a non-deterministic mode that passes all cross-rank hash checks is still non-reproducible across runs with different world sizes.
  • Bug class without it: assuming cross-rank identity implies cross-run reproducibility → training runs that diverge on restart.
  • Applies at: §8.12, §7 I5/I6, P3 (§15), P13 (§25).

MM8: The transport is a contract, not a detail — the wire protocol's frame format, versioning, checksum, and flow-control semantics are load-bearing; changing them silently breaks mixed-version clusters during rolling upgrades.

  • Predicts: any frame field change without a version bump will corrupt data in production.
  • Bug class without it: "quick fix" that changes message encoding without bumping the wire version → silent data corruption during a rolling restart.
  • Applies at: §8.7, principle 12, I7/I14, P1 (§13).

5.3 Reference Implementations

  • NCCL (NVIDIA) — ring/tree allreduce, topology detection, the channel/chunk model. Study; do not copy. Lesson: chunking + multi-channel overlap. Pitfall: GPU/CUDA-specific (we defer GPU). [applied: §8.4 (algorithm selection), §16 (P4 chunking model), ADR-1]
  • Gloo (Facebook) — CPU collectives over TCP; the closest to our setting. Lesson: algorithm selection + transport abstraction. [applied: §3.2 (transport box narrative), §13 (P1 transport abstraction), ADR-6]
  • MPICH / Open MPI (coll/ modules) — the canonical collective algorithm implementations + selection logic. Lesson: the algorithm zoo + cost-model thresholds. [applied: §8.4 (cost-model thresholds), §16 (P4 algorithm selection), ADR-5]
  • Mesh-TensorFlow / JAX pjit/GSPMD — sharding spec + partitioner. Lesson: propagation rules + collective insertion. Pitfall: deeply tied to XLA. [applied: §8.1–§8.3 (mesh/shardspec/resharding), §17–§18 (P5/P6 partitioner), ADR-8/9]
  • PyTorch c10d / ProcessGroup — the collective API + rendezvous. Lesson: API shape, bootstrap. [applied: §11.4 (Collectives trait API shape), §14 (P2 bootstrap), ADR-18]
  • Horovod — tensor fusion + the negotiation/coordination for which tensors to allreduce. Lesson: fusion + scheduling. [applied: §21 (P9 overlap/fusion), ADR-12]

Glossary · 38 terms · site-wide glossary

α–β (Hockney) model
T(n) = α + β·n per message (α latency, β = 1/bandwidth); basis for algorithm selection.
Allgather
every rank ends with the concatenation of all ranks' data.
Allreduce
every rank ends with the reduction (sum/max/…) of all ranks' data; = reduce-scatter + allgather.
All-to-all
each rank sends a distinct chunk to every other rank (axis swap).
Barrier
no rank proceeds until all arrive.
Bootstrap / rendezvous
the process by which ranks discover each other and agree on the world.
Broadcast
one rank's data sent to all.
Bruck algorithm
a log₂N-step all-to-all / allgather (latency-efficient for small messages).
Chunk
a sub-piece of a tensor circulated in a ring/streamed collective (bounds memory, enables overlap).
Collective
a communication operation involving a group of ranks.
Collective fusion
batching multiple small collectives into one larger call to amortize the α latency overhead; analogous to Nagle's algorithm for TCP; implemented in P9 (§21).
Cost model
analytic prediction of a collective's time (§8.4).
DeviceMesh
an n-dim grid of ranks with named axes.
DTensor
PyTorch's DeviceMesh + placement-spec API (introduced PyTorch 2.0); the closest publicly available analogue to this runtime's §11.2 types.
Deterministic mode
fixed reduction order → bit-reproducible across runs.
Fail-stop
on a rank failure, the job halts cleanly (vs continuing degraded).
FSDP (Fully Sharded Data Parallel)
PyTorch's ZeRO-3 implementation: reduce-scatter gradients during backward, allgather parameters during forward; expressed as ShardSpec transitions in this runtime.
Failure detector
heartbeat/SWIM mechanism bounding how fast a dead rank is noticed.
Flow control
credit/window scheme bounding in-flight bytes.
GPUDirect
NVIDIA technology enabling direct RDMA transfers between GPU memory and NIC, bypassing the CPU; deferred in this runtime (§24.2, ADR-7).
Overlap
running computation concurrently with in-flight communication.
Partial
a sharding state meaning "reduction pending" (after a sharded contraction).
Partitioner
infers shardings + inserts resharding collectives (GSPMD).
Process group
the subset of ranks participating in a collective (a mesh-axis slice).
Rank / world size
a process's id in [0,N) / the number of ranks N.
Rendezvous
the handshake where sender and receiver agree on a buffer transfer before bulk data moves; prevents unbounded buffering; implemented in §8.7, §8.13, P1 (§13).
Recursive halving-doubling (RHD)
latency-optimal (log N) allreduce.
Reduce-scatter
reduction whose result is scattered (each rank gets one piece).
Reshard
change a tensor's sharding (emits a collective, §8.3).
Ring algorithm
bandwidth-optimal collective circulating chunks around a logical ring.
ShardSpec
per-dimension sharding annotation (Replicated/Sharded/Partial).
SPMD
single program, multiple data: every rank runs the same program over its shard.
Straggler
a slow rank that delays a collective/barrier.
Stream
an independent ordered execution/communication queue (enables overlap).
SUMMA
scalable universal matrix multiply (2D distributed GEMM).
Transport
the reliable ordered messaging layer (TCP here).
Wire protocol
the versioned, checksummed frame format defined in §8.7; negotiated at handshake (I14); changes require a wire-version bump to preserve mixed-version compatibility.
ZeRO (Zero Redundancy Optimizer)
Rajbhandari et al. 2020 (SC); shards optimizer state (ZeRO-1), gradients (ZeRO-2), and parameters (ZeRO-3) across ranks; expressed as reduce-scatter + allgather patterns over this runtime's collectives; a primary consumer pattern for #115.
