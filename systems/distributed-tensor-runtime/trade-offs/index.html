1

Language

Chosen

Rust 2021

Rejected

C++/MPI, Go, Python

When the rejected choice is right

C++ wins when the team already owns an NCCL/cuBLAS build system or must write CUDA kernels directly (CUDA C++ toolchain integration is trivial); Go wins for coordinator/rendezvous-only services where GC jitter is irrelevant

Why: systems+numeric; no GC jitter; reuse #349 (§1.9)

2

Workspace

Chosen

Cargo, 10 crates

Rejected

monolith

When the rejected choice is right

A monolith wins for a solo proof-of-concept where compile-time layering is less valuable than compile-speed and grep-ability; or when all crates are always co-released and never individually versioned

Why: transport↛partition layering

3

Parallel model

Chosen

SPMD

Rejected

master/worker; actor

When the rejected choice is right

Master/worker wins for centralized parameter-server topologies (#250) where the workload is inherently asymmetric; actor model (Ray-style) wins for heterogeneous, highly dynamic pipelines where rank count changes mid-job

Why: scales; matches GSPMD/MPI

4

Build collectives from

Chosen

point-to-point primitives

Rejected

per-collective monoliths

When the rejected choice is right

Per-collective monoliths win when you need a single ultra-optimized allreduce for a fixed hardware/algorithm (e.g., NCCL's ring for NVLink) and algorithm-switching is never required

Why: composition (principle 2)

5

allreduce algorithms

Chosen

ring + RHD + tree, cost-model select

Rejected

ring-only

When the rejected choice is right

Ring-only wins when you have empirically verified that all your workloads are large-message (compute-bound GEMM gradient allreduce on wide models) and the cost-model selection overhead is measurable

Why: message-size optimality (principle 3)

6

Transport

Chosen

custom reliable over TCP

Rejected

raw MPI; gRPC; QUIC

When the rejected choice is right

Raw MPI wins when the goal is consuming collectives, not building them (e.g., building a training framework on top of an existing runtime); gRPC wins when the control plane is complex enough that HTTP/2 multiplexing and generated stubs add real value

Why: from-scratch; control; RDMA later

7

RDMA / IB

Chosen

deferred PhaseDeferred

Rejected

now

When the rejected choice is right

RDMA wins immediately in a production HPC environment (InfiniBand cluster) where TCP cannot saturate the available bandwidth and kernel-bypass latency dominates; GPUDirect enables zero-copy GPU↔NIC transfers unavailable over TCP

Why: scope; TCP first

8

Sharding model

Chosen

named-axis mesh + ShardSpec (Replicated/Sharded/Partial)

Rejected

rank-arithmetic sharding

When the rejected choice is right

Rank-arithmetic sharding wins for simple single-axis data-parallel workloads where named axes add no value and the programmer controls the exact rank-to-shard mapping directly (simpler code, lower abstraction overhead)

Why: Mesh-TF/GSPMD; composable

9

Partitioner

Chosen

sharding propagation + collective insertion

Rejected

manual collective calls

When the rejected choice is right

Manual collective calls win when the program is small and well-understood (a fixed 2-layer model with known sharding) and the programmer needs exact control over which collective fires when — auto-insertion adds debug opacity in that regime

Why: GSPMD automation (principle 6)

10

Local compute

Chosen

delegate to #349

Rejected

reimplement

When the rejected choice is right

Reimplementing wins when you need hardware-specific intrinsics or memory-layout optimizations that #349's API cannot express (e.g., fused allreduce-scatter with a custom accumulator), or when #349's ABI is too unstable to depend on

Why: no duplication (principle 10)

Device backend

Chosen

CPU now; GPU deferred

Rejected

GPU now

When the rejected choice is right

GPU-first wins when the production target is exclusively GPU clusters and CPU correctness is never exercised — the only justification for this project would be if no CPU test infrastructure exists at all

Why: scope; CPU correct first

12

Overlap

Chosen

streams + dependency scheduler

Rejected

serial

When the rejected choice is right

Serial wins for debugging and conformance testing: a deterministic serial schedule makes wrong results trivially reproducible without heisenbug timing sensitivity; also correct for pipelines where compute ≪ comm and no independent work exists

Why: hide comm (principle 4)

13

Flow control

Chosen

credit-based, bounded window

Rejected

unbounded

When the rejected choice is right

Unbounded wins in a zero-copy RDMA environment where the NIC handles back-pressure in hardware and the application buffer is pre-registered — the software credit accounting overhead is then pure cost

Why: no OOM (principle 5, I8)

14

Failure model

Chosen

fail-stop + bounded detection

Rejected

elastic/recovery now

When the rejected choice is right

Elastic/recovery wins for very long-running jobs (days/weeks) where restart cost is prohibitive and checkpointing + partial recovery is cheaper than restarting from scratch; Elastic wins in cloud environments with frequent preemptions

Why: scope; detect not hang (principle 8)

15

Failure detector

Chosen

heartbeat (SWIM-lite, #197)

Rejected

none; full SWIM

When the rejected choice is right

Full SWIM wins in large (N > 10k) clusters where the gossip dissemination delay matters and indirect probing is essential for correctness at scale; "none" wins for a single-host multi-process test setup where OS process death is immediately observable

Why: bounded, simple

16

Determinism

Chosen

fixed reduce order + det-mode

Rejected

nondeterministic

When the rejected choice is right

Fully nondeterministic wins when maximum throughput is the only metric and no reproducibility requirement exists — e.g., reinforcement learning with stochastic policies where numerical differences are swamped by reward variance

Why: reproducible (principle 7, I6)

17

dtypes

Chosen

f32/f64/bf16

Rejected

f32-only

When the rejected choice is right

f32-only wins in scientific computing (climate modeling, PDE solvers) where bf16's reduced exponent range is unacceptable and ML-style inference accuracy trade-offs are irrelevant

Why: ML payloads need bf16

Bootstrap

Chosen

coordinator/rendezvous endpoint

Rejected

static hostfile only

When the rejected choice is right

Static hostfile wins in a fixed HPC allocation where ranks never change, IPs are pre-assigned, and adding a coordinator service introduces a deployment dependency that the cluster scheduler does not support

Why: dynamic, mpirun-like

Error handling

Chosen

Result<_,DtrError>; codes at ABI

Rejected

panic across FFI

When the rejected choice is right

Panic-across-FFI wins only when the caller is also Rust and the entire stack is compiled together as one binary — then catch_unwind overhead is pure waste and panics unwind cleanly

Why: FFI safety (I15)

Wire protocol

Chosen

versioned, checksummed frames

Rejected

unversioned

When the rejected choice is right

Unversioned wins in a tightly-controlled single-team deployment where all ranks are always upgraded atomically and the checksum overhead is measurable on the critical path (e.g., 100 Gb/s+ RDMA where software checksum wastes cycles)

Why: upgrade safety (principle 12, I14)

Threading

Chosen

own pools (net + compute), coordinate #349

Rejected

rayon-only

When the rejected choice is right

Rayon-only wins when the workload is compute-only (no network) and work-stealing across all threads is more efficient than separately managed pools — i.e., when there is nothing to overlap

Topology awareness

Chosen

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt 1: Parameter Server (Centralized Push/Pull)

  worker_0  worker_1  ... worker_N
     │          │              │
     └──────────┴──── push ────┘
                      │
              [Parameter Server]
                      │
     ┌──────────────┬─┴──────────────┐
   pull           pull             pull
  worker_0      worker_1         worker_N

Winning regime: Sparse/embedding gradient updates where only a fraction of parameters change per step — recommendation models with O(10^10) sparse embedding lookups. Each worker touches a tiny subset, so allreduce is wasteful; the PS sends only the touched rows. Also wins when workers are heterogeneous (different speeds) because the PS can batch updates asynchronously.

Real system: Google DistBelief (Dean et al. 2012), Petuum (Ho et al. 2013), MXNet KVStore.

Why rejected: Synchronous dense gradient allreduce (the dominant pattern for transformer training) is more efficient as a peer-to-peer ring — no bottleneck server. The PS is a bandwidth bottleneck at scale. This project's goal is to build the collective substrate, not the parameter storage layer. #250 in the portfolio is the PS — the two are complementary, not competing.

Alt 2: MPI-style Communicator (Static Allocation + Library Call)

  [MPI_Comm_world]  ─── pre-allocated, static rank assignment
  rank_0  rank_1  rank_2  rank_3
    │       │       │       │
  MPI_Allreduce(comm, buf, count, MPI_FLOAT, MPI_SUM)
    │       │       │       │
  [opaque: ring/RHD/tree/Rabenseifner per msg size]
    │       │       │       │
  [return: all ranks have reduced result]

Winning regime: HPC scientific codes where (a) a portable, standard-compliant API is required, (b) the implementation quality of OpenMPI/MPICH is unmatched, and (c) the application manages data layout manually. Also wins for learning collective algorithms without building the full runtime.

Real system: Open MPI, MPICH, Intel MPI.

Why rejected: Using MPI would defeat the "from scratch" learning goal (#179 is the MPI study project). MPI has no sharding-spec or partitioner concept. The Rust/C++ boundary friction is real. MPI's communicator model doesn't compose as cleanly with a typed ShardSpec system. This runtime re-derives MPI's semantics (§5.4) without taking MPI as a dependency.

Alt 3: Actor-Model Collective Runtime (Ray-style)

  GradientWorker.remote()   GradientWorker.remote()
        │                           │
        └──── ray.get(allreduce) ───┘
                     │
           [Ray Object Store / GCS]
           (shared object refs, not ring buffers)
                     │
        ┌────────────┴────────────┐
  Worker.reduce()          Worker.reduce()
  (actors own shards;      (actors own shards;
   futures resolve           futures resolve
   collectively)              collectively)

Winning regime: Heterogeneous, dynamically-sized pipelines where rank count changes mid-job (elastic training), tasks have variable duration and work-stealing is valuable, and the collective is a small fraction of work (sparse MoE, RL, simulation + ML hybrid workloads). Also wins for fault tolerance: actor death restarts one actor, not the whole job.

Real system: Ray (Moritz et al. 2018, OSDI), Ray Train, Alpa's inter-op planner.

Why rejected: Actor-model overhead (object store serialization, GCS metadata) is measurable on the hot path of a synchronous allreduce. GC/scheduling jitter hurts collective latency tails. The actor model does not map cleanly to SPMD — every rank runs the same program; there is no per-actor heterogeneous logic. Rust ownership + async streams gives us the needed concurrency without the actor overhead.
