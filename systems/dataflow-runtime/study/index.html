32. Mental Models & First Principles

The compressed intuitions a principal engineer holds about this system. Each: the insight, what it predicts, the bug you write without it, and where this blueprint applies it.

MM1 — A frontier is a promise about input completeness, not a clock

  • Insight. A frontier (watermark) at location l does not say "the time is now T"; it says "no input with time < T will ever again arrive at l." It is a lower bound on future arrivals, derived from upstream capabilities + path summaries — not a wall-clock reading.
  • Predicts. Late data is normal and expected; the watermark is a tunable guess about how late data can be. A "perfect" watermark is impossible without bounding source lateness.
  • Bug without it. You treat the watermark as the current time, flush windows on processing-time, and silently drop valid out-of-order data — or you assume frontiers can move backward to "fix" things and corrupt closed results.
  • Applied. Progress tracking (§16), windowing/watermarks (§19), invariant I1 (§7.1), principle P2.

MM2 — Backpressure is a promise about memory, transmitted backward as credit

  • Insight. Credit is downstream telling upstream "I have N buffer slots free." Flow control is the inverse of dataflow: data flows forward, permission flows backward. A bounded system is one where every producer waits for a consumer's promise before emitting.
  • Predicts. The slowest operator sets the rate of the whole pipeline (it is the one not granting credit). Queue depth pinned at capacity = you found the bottleneck. Unbounded buffers convert a slow consumer into an OOM.
  • Bug without it. You buffer "just in case," load skew fills the buffer, and a single slow sink exhausts host memory (Class C, §25).
  • Applied. Channels/backpressure (§14), invariant I8 (§7.8), principles P1/P4; contrast with Reactive Streams demand (§5.4).

MM3 — A capability is a reference count on a logical time

  • Insight. Holding a Capability<t> keeps the pointstamp count for t at ≥ 1, which keeps the frontier from advancing past t. Dropping it is a destructor that decrements that count. Capabilities are RAII over logical time, exactly as Arc is RAII over memory.
  • Predicts. A stuck frontier is a leaked capability (someone holds a time they should have dropped); a premature flush is a capability dropped too early (use-after-free of a logical time).
  • Bug without it. You emit at a time after dropping its capability → emit at a closed time → safety violation (I3, §7.3); or you never drop → liveness stall (§7.7).
  • Applied. Capability model (§8.5), progress (§16), principle P6, invariants I3/I4.

MM4 — Logical time is a lattice, and a scalar timestamp is the degenerate case

  • Insight. Timestamps form a partial order with joins/meets. A flat event-time u64 is the totally-ordered special case; iteration adds a coordinate (Product<T, loop>) making times genuinely incomparable. A frontier is therefore an antichain, not a number.
  • Predicts. Anything that needs cycles or multi-dimensional incremental updates cannot use a scalar watermark — it needs the product order. Forcing a total order breaks iteration termination.
  • Bug without it. You model time as u64, then iteration livelocks because you cannot express "round i of outer time t" as a distinct, ordered point.
  • Applied. Timestamps (§8.3), antichains (§8.4), iteration (§18), principle P12, ADR-08/ADR-09.

MM5 — "Exactly-once" is about effects, not delivery

  • Insight. No system delivers each record exactly once over a lossy channel. Exactly-once means the externally observable effect equals a non-failing run: achieved by a consistent-cut snapshot + deterministic replay + idempotent/transactional sinks. Records may be reprocessed; effects are not double-applied.
  • Predicts. You cannot get exactly-once with a non-idempotent, non-transactional sink, no matter how good the runtime is. Dedup tables are a different (unbounded-state) design (MillWheel).
  • Bug without it. You implement at-least-once + a dedup set, the dedup set grows without bound, and non-idempotent sinks still double-emit on recovery.
  • Applied. Snapshots/exactly-once (§20), principle P7, invariant I6; contrast MillWheel record-IDs (§5.2).

MM6 — Alignment is the price of a consistent cut

  • Insight. A barrier on one input is meaningless; a consistent global state requires waiting for the barrier on all inputs (alignment) so that pre-barrier and post-barrier records are cleanly separated. Alignment time is bounded by the slowest input — so skew directly inflates checkpoint latency.
  • Predicts. An idle input stalls alignment forever unless it advances a watermark/barrier; checkpoint p95 tracks input skew, not average load.
  • Bug without it. You snapshot on the first barrier, fold post-barrier data into pre-barrier state → inconsistent cut → double/lost counts on restore (I9, §7.9).
  • Applied. Snapshots (§20), invariant I9, state-machine §8.9; the Chandy-Lamport marker rule (§5.4).

MM7 — On a no-GC runtime, tail latency is scheduling + contention, never the collector

  • Insight. With Rust + buffer pools, the hot path is allocation-free, so p99 is dominated by activation-queue latency, channel CAS contention, and cache misses — not stop-the-world pauses. This is the whole reason to reject the JVM here (ADR-01).
  • Predicts. A p99 spike correlates with a hot channel (false sharing, credit thrash) or an unfair scheduler, and is found with perf c2c / off-CPU profiling — not with GC logs.
  • Bug without it. You chase phantom "GC-like" pauses, add more buffering (making it worse), instead of fixing false sharing with CachePadded (ADR-07).
  • Applied. Constraints §4.2, Performance Engineering (§30), principle P11; USE method (§5.1).

MM8 — Progress must be tracked per frontier, not per record

  • Insight. If every record emitted a progress message, progress traffic would equal data traffic (O(records)) and melt the system. The pointstamp protocol aggregates produced/consumed deltas into ChangeBatches per pointstamp, so progress cost is O(active pointstamps) — independent of record volume.
  • Predicts. The cost of progress tracking scales with graph activity (open times × locations × workers), not throughput; a fan-in storm is a progress-traffic problem, fixed by batching, not by faster data paths.
  • Bug without it. You report progress per record, and a wide fan-in produces an O(records) gossip storm that pegs CPU (§8.10, Class C).
  • Applied. Progress (§16), broadcast batching (§17), constraint §4.6, threat "Resource exhaustion (CPU)" (§24).

MM9 — Determinism is a debugging tool, bought with scheduling discipline

  • Insight. If the same input + offsets + graph always produces the same output (modulo declared wall-clock triggers), then every bug is reproducible by replay and every snapshot is verifiable by recompute. Determinism is purchased by stable per-key order and a controlled logical-time scheduler.
  • Predicts. Any divergence between two replays, between fused and unfused, or between worker counts, is a bug — this gives you a free differential oracle.
  • Bug without it. Non-deterministic operator order makes snapshots differ across replays; you cannot validate exactly-once or reproduce a heisenbug.
  • Applied. Principle P3, deterministic sim (ADR-19), testing strategy (§28), fused-vs-unfused differential (§28).

MM10 — Shared-nothing symmetry makes distribution a transport problem

  • Insight. Because every worker runs the same graph and they communicate only via channels + progress gossip, the in-process and cross-host cases run the identical protocol; only the channel implementation changes (in-memory vs TCP). The hard distributed algorithm (progress) is already solved at N=1-in-process.
  • Predicts. Going multi-host adds serialization, RTT, and failure detection — but no new progress semantics. If your single-process design needs a shared mutable graph, you have already blocked distribution.
  • Bug without it. You bolt shared state across workers, reintroduce locks/races, and the §23 distributed step requires a protocol rewrite instead of a transport swap.
  • Applied. Principle P13, worker model (§3.2, §11.8), distributed phase (§23), Alternative Architectures (§36).

Glossary (§38) · 48 terms · site-wide glossary

Dataflow graph
Directed graph G=(V,E) of operators (vertices) and typed edges (streams); the program (§8.1).
Operator (vertex)
Unit of computation; implements Operator::schedule; a state machine Idle→Runnable→Running→Blocked (§8.7).
Edge / Channel
Typed connection carrying Message<D> between operator ports; bounded, credit-backpressured (§11.5).
Stream<S,D>
Compile-time-typed handle to an edge in scope S carrying record type D; combinator entry point (§11.4).
Message<D>
Batched unit on a channel: {time:T, data:Vec<D>, from:WorkerId}; default batch 1024 (§8.6).
Timestamp (T)
Element of a partial order / lattice; logical time of a batch; may be partially ordered (§8.3, §6.12).
Partial order
a ⪯ b defined by PartialOrder::less_equal; incomparable times coexist (§8.3).
Lattice
Partial order with join/meet + least element; the algebra of timestamps (§11.1).
Product<O,I>
Nested-scope timestamp; inner coordinate = loop counter; partially ordered (§8.3).
Antichain<T>
Minimal set of pairwise-incomparable times; representation of a frontier (§8.4).
Frontier
Antichain of times that MAY still appear at a location; advances monotonically (§6.2, §7.1).
Pointstamp
(LocationId, T) pair; the unit tracked by the progress protocol (§8.4).
ProgressUpdate
(Pointstamp, delta:i64); +1 produced / −1 consumed; the gossip wire type (§11.3).
Capability<T>
Right to emit at times ⪰ its time on a port; keeps a pointstamp open; downgrade/drop (§8.5, §6.6).
Path summary
Function T→T transforming a timestamp along a path; identity by default, +1 on feedback (§8.3).
Reachability
Build-time table of minimal path summaries between locations; decides what can still arrive (§8.4).
Progress tracking
The timely protocol deriving frontier advancement from produced/consumed counts (§16, §3.2).
Notification
Callback fired when an input frontier passes a requested time; drives window/aggregate flush (§7).
Worker
OS thread owning a shard (full graph copy + state partition + channel endpoints), WorkerId 0..N (§11.8).
Shard
A worker's slice: its copy of the graph + the key-partition of state it owns.
Scheduler
Per-worker cooperative loop over an activation queue; fairness + parking + quiescence (§3.2).
Activation queue
Set of Runnable operators awaiting scheduling; idempotent activate via queued bit (§11.8).
Quiescence
State where no operator is runnable and no progress is pending; basis for termination (§2).
Backpressure
Credit-based flow control; producer blocks when downstream credit exhausted (§6.1, §3).
Credit
Atomic count of buffer slots a producer may use; granted on consumer buffer return (§3.2).
Exchange / shuffle
Edge that partitions records by key hash across workers; Pact defines the partition fn (§17, §11.5).
Pact
Partitioning contract {partition fn, kind:Pipeline|Exchange}; single source of truth for routing + state ownership (§7.11).
Keyed state
Per-key operator state KeyedState<K,V>, partitioned by the exchange key (§11.6).
State backend
Abstraction over keyed-state storage; in-memory in P0; persistent deferred (§11.6).
Watermark
A frontier in event time emitted by sources; signals event-time progress (§18 (Phase 8)).
Window
Bounded grouping of event-time records (tumbling/sliding/session); flushed on trigger (§18 (Phase 8)).
Trigger
Condition firing a window emission; event-time at window close by default (§18 (Phase 8)).
Lateness
Allowed delay past watermark for late records; beyond it → drop/side-output (§7.4).
Side-output
Secondary stream for late/dropped records; never merged into closed windows (§18 (Phase 8)).
Checkpoint barrier
CheckpointBarrier{epoch} injected at sources; flows with data; aligns at operators (§20, §11.7).
Alignment
Waiting for a barrier on all inputs before snapshotting → consistent cut (§7.9, §20).
Asynchronous barrier snapshot (ABS)
Flink's aligned-barrier checkpoint algorithm (Chandy-Lamport derived) for exactly-once (§20).
Consistent cut
Global state reflecting exactly the input prefix up to a barrier on every source (§7.9).
Epoch
Monotonic checkpoint identifier; durable when all sinks ack (§11.7).
Snapshot / restore
Serialize state at a barrier; deserialize on recovery + replay offsets → exactly-once (§20).
Exactly-once
External effects equal a non-failing run: no duplicates, no losses (§6.7, §7.6).
Idempotent / transactional sink
Sink that dedupes by key or 2-phase-commits aligned to epoch; required for exactly-once (§20).
Operator fusion
Inlining a stateless chain into one monomorphized loop, eliding dispatch/channels (§21).
Skew
Imbalance of per-key/per-worker load; the key streaming pathology (§6.6, §22).
Frontier lag
Wall-clock minus event-time frontier; primary streaming-health signal (§4.3, §22).
Crash-only
Only correct shutdown path is crash + restore-from-snapshot (§6.10).
Correctness fault
Trusted-code invariant violation → fail-fast → abort+restore; distinct alert class (§6.14, §26).
PhaseDeferred
Marker for capabilities intentionally out of P0 scope (e.g. distribution §23, persistent state).
