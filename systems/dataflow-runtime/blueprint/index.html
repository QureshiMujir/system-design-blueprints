1. Goal

1.1 What Is Being Built

A dataflow execution runtime: computation expressed as a directed graph of operators (vertices) connected by typed edges (streams). The runtime schedules operator execution, moves data along edges, enforces backpressure, supports stateful operators, and tracks progress via logical timestamps and frontiers in the timely-dataflow tradition — including cyclic / iterative dataflow with strictly-advancing loop coordinates.

Concretely, you build:

  • A graph builder API that constructs a typed dataflow DAG (and loop contexts) before execution.
  • An operator abstraction (Operator trait) with schedule / on_input / on_notify semantics.
  • A push-based dataflow engine where upstream operators push batches downstream, gated by credit/frontier backpressure.
  • A progress tracker implementing the timely pointstamp protocol (produced/consumed counts, capabilities, frontiers as antichains).
  • Keyed state for stateful operators (aggregation, joins, windows).
  • Asynchronous barrier snapshots (Flink ABS / Chandy-Lamport) for exactly-once semantics under restore.
  • Windowing + watermarks for event-time streaming with bounded out-of-order tolerance.
  • Data-parallel workers (one per core) with exchange/shuffle by key.
  • An observability surface: throughput, queue depth, frontier lag, skew.

The runtime is the execution substrate beneath a stream-processing or incremental-computation system — not the query language, not the planner, not the storage.

1.3 Explicit Non-Goals

  • Not a SQL engine. No parser, planner, optimizer, catalog. Operators are hand-built or library-provided; you do not compile relational algebra.
  • Not a full Apache Flink / Spark. No cluster manager, no resource negotiation (YARN/K8s), no SQL/Table API, no savepoint format compatibility.
  • Not a distributed system in P0. Multi-process workers, network exchange, and cross-host progress are PhaseDeferred("FINAL_BLUEPRINT §23").
  • Not a persistent storage engine. State lives in memory; durable state backends are deferred.
  • Not a general actor framework. Operators are dataflow vertices with progress semantics, not arbitrary message-passing actors.
  • Not an ML graph executor. TensorFlow-style autodiff and tensor kernels are out of scope (though the graph-execution lineage is shared; §2).

1.4 Deployment Model

  • Embeddable library (dfr-core + crates): host process constructs a dataflow, spawns workers, feeds inputs, drains outputs. Lifecycle owned by the host.
  • Local multi-worker runner (dfr-cli): launches N worker threads on one machine, wires intra-process exchange channels, runs an example dataflow from a description file.
  • Workers are symmetric: every worker runs a copy of the full operator graph; data is partitioned across workers by exchange edges.
  • The runtime is a passive library between worker::execute calls: it does not own a global event loop beyond the worker threads it spawns.

1.5 Target Users

  • Stream-processing engineers building the layer beneath a Flink/Materialize-class system.
  • Incremental-systems engineers (differential dataflow, incremental view maintenance) needing progress tracking and iteration.
  • Runtime/scheduler engineers who want a precise model of push-based execution, backpressure, and frontier-driven termination.
  • Operators running streaming jobs who need to reason about frontier lag, skew, and checkpoint overhead.

1.10 Recommended Language — Rust + Exact Rationale

Rust. Locked.

  • Zero-cost abstractions — operator traits, iterators, and generic timestamps compile to tight loops; no virtual-dispatch tax on the hot path when operators are monomorphized/fused (§21).
  • Ownership for buffer reuse — batches (Vec<D>) are moved between operators; buffer pools recycle allocations without GC. Ownership statically prevents two operators mutating the same batch.
  • No GC pauses — low-latency dataflow cannot tolerate stop-the-world pauses; p99 latency stays bounded. (Contrast: JVM Flink fights GC tuning.)
  • Send/Sync — the type system enforces which state crosses thread/worker boundaries; exchange channels move Send data; per-worker state need not be Sync.
  • Fearless concurrency — worker-per-core threads with compiler-checked data-race freedom.
  • Precedent — Timely Dataflow and Differential Dataflow are Rust; the design vocabulary (capabilities, antichains, exchange) maps directly.

Rejected: C++ (manual lifetime management, weaker move-safety, no borrow checker for buffer aliasing); Go (GC pauses, no zero-cost generics pre-generics-maturity, goroutine scheduler opaque to backpressure); Java/Scala (GC, boxing of timestamps, JIT warmup); OCaml (GC, weaker SIMD/cache control).

1.11 Prerequisites

  • Graph theory — DAGs, topological order, strongly connected components (for cycle detection / loop scopes).
  • Scheduling — work queues, fairness, parking/unparking, cooperative scheduling.
  • Lattices / partial orders — joins/meets, antichains, the product order on timestamps; this is the mathematical core of progress tracking.
  • Streaming semantics — event time vs processing time, watermarks, windows, triggers, lateness.
  • Concurrency — MPSC/SPSC queues, memory ordering (acquire/release), false sharing, lock-free ring buffers.
  • Distributed snapshots — Chandy-Lamport, Flink ABS; consistent cuts.
  • Helpful: prior portfolio work on 105 Stream Processing Engine, 129 Async Runtime, 54 Scheduler, 376 Chandy-Lamport Snapshot.

2. Why Build This

2.1 Unique Systems Knowledge Taught

  • Dataflow graph execution — turning a static operator graph into a running, scheduled computation; activation lists; operator state machines.
  • Progress tracking — the timely pointstamp protocol: how a runtime knows that no more data will ever arrive at or below a given logical timestamp at a given graph location, without central coordination per record.
  • Frontiers and antichains — representing "the set of times still possible" as a minimal antichain in a partial order; computing frontier advancement from produced/consumed counts.
  • Backpressure — credit/frontier-based flow control that keeps queue depth bounded under arbitrary load skew, and the deadlock hazards it introduces in cycles.
  • Exactly-once snapshots — aligned barrier injection producing a consistent cut; restore semantics; why "exactly-once" is about effects, not delivery.
  • Windowing / watermarks — reconciling unbounded out-of-order event streams with finite, emittable results; trigger semantics; bounded lateness.

2.5 Calibration Value

Building this permanently raises capability in: distributed-systems correctness reasoning (consistent cuts, monotone progress), concurrency engineering (lock-free channels, memory ordering), and systems performance (batching, cache, tail latency). Progress tracking in particular is a "calibration" problem: it is easy to get 90% right and have it deadlock or leak frontiers under the diamond pattern; getting it provably right is a staff-level milestone.

2.6 What Mastery Looks Like

After building this runtime you can demonstrably:

  • Derive frontier advancement from produced/consumed counts and prove it never closes a time early under the diamond/fan-in pattern — the Naiad protocol, built in Phase 5 and exercised in Phase 7.
  • Place a fusion or alignment boundary correctly — know exactly which operator boundaries must stay discrete for progress and snapshots (exchange, stateful, loop, sink) and why, from Phase 9 and Phase 10.
  • Reason about exactly-once as an effect property, not a delivery property — design idempotent/transactional sinks and a consistent cut, built in Phase 9.
  • Size a bounded-buffer cycle so it cannot deadlock — compute the in-flight reserve a feedback cycle needs, from Phase 7 and the backpressure model of Phase 3.
  • Diagnose a streaming stall in one metric — read frontier lag, queue depth, and skew to localize a stuck capability or hot key, from Phase 11.
  • Choose the latency/throughput point on the design spectrum — articulate why record-at-a-time beats micro-batch here and when the reverse holds, from Phase 2, Phase 6, and the Alternative Architectures section (§36).
  • Implement a lock-free MPSC ring with correct memory ordering and validate it under loom, from Phase 3.

3.2 Per-Box Detail

Graph Builder / Dataflow API (dfr-core). Constructs the dataflow once, before execution, as a typed builder. You open a Scope, add operators via combinators (map, filter, exchange, enter/leave for loops), and connect typed edges; each edge carries a phantom record type D and a timestamp type T. The builder records operators, edges, exchange pacts (partitioning functions), and loop scopes, then finalizes an immutable runtime graph. No data flows here. The builder enforces type compatibility at compile time (edge Stream<S, D>), assigns each operator a LocationId, and computes the static topology the progress tracker needs (the summary of timestamp transformations along each path; §8). Violating immutability post-build (mutating the graph during execution) is forbidden — the progress protocol assumes a fixed topology.

Operator (vertex) abstraction. The unit of computation. Implements the Operator trait: schedule(&mut self, ctx) is the activation entry point; the operator drains input ports, processes batches, pushes to output ports, and manipulates capabilities (proof it may still emit at a timestamp). An operator is a small state machine — Idle, Runnable, Running, Blocked (§8.7). It holds input frontiers (what times can still arrive), output capabilities, and optionally a KeyedState handle. Operators are pure with respect to their declared state: all mutable state lives in the keyed-state handle so snapshots capture it (Design Principle §6). A misbehaving operator that mutates hidden global state breaks exactly-once.

Edges / Channels (dfr-channels). Move Message<D>{time, data, from} between operators. Intra-worker edges are bounded MPSC ring buffers with credit-based backpressure: a downstream operator grants credits; upstream blocks when credits are exhausted. Inter-worker edges are exchange channels that partition records by a key function (shuffle), one logical channel per (src_worker, dst_worker, edge). Channels also carry progress messages (produced/consumed pointstamp deltas) interleaved with data, so the progress tracker observes the same ordering. The channel layer is where backpressure, batching, and (eventually) serialization live. Unbounded channels would violate the bounded-resource invariant (§7); cyclic bounded channels create deadlock risk (§8.10).

Scheduler (dfr-scheduler). Each worker runs a cooperative scheduler over its operators. Maintains an activation queue of Runnable operators; pops one, calls schedule, and the operator processes available input and returns. Activation is triggered by: new input arriving, downstream credit freeing, a notification firing, or a frontier advancing. The scheduler enforces fairness (no operator starves), parks the worker thread when nothing is runnable and no progress is pending, and integrates with the progress tracker to know when the dataflow is quiescent (all frontiers empty → termination). Unfair scheduling causes head-of-line blocking and frontier-lag spikes (§22).

Worker (dfr-scheduler::Worker). A thread owning a shard: a complete copy of the operator graph plus the per-worker partition of state and the worker's endpoints of every exchange channel. Workers are symmetric and identified by WorkerId 0..N. The worker drives the scheduler loop, services exchange channels (push outgoing, pull incoming), participates in the progress protocol (broadcasts/receives pointstamp deltas), and triggers checkpoints. Workers communicate only via channels + progress gossip — no shared mutable graph state — which is what makes the design distributable later (§23).

Progress Tracker (dfr-progress). Implements the timely pointstamp protocol. Tracks, per Pointstamp{location, timestamp}, a count of outstanding work (produced − consumed). When the count at a pointstamp reaches zero and nothing upstream can produce it (per the path summaries), that pointstamp is closed; the operator's input frontier advances. Frontiers are antichains (minimal sets of incomparable timestamps). The tracker turns local produced/consumed deltas (possibly from remote workers) into frontier updates that drive operator activation and notifications. This is the correctness heart of the system: a bug here either deadlocks (frontier never advances) or violates safety (frontier advances prematurely → a notification fires before all data arrives → wrong results).

State Backend (dfr-state). Stores keyed operator state: KeyedState<K, V>, partitioned by the same key/hash used for exchange so a worker owns the state for the keys routed to it. Provides get/insert/remove, iteration for window flush, and snapshot/restore hooks (serialize the partition into a checkpoint; deserialize on recovery). P0 is in-memory (hashmaps + arena). The backend must support point-in-time consistency: at a barrier, the snapshot reflects exactly the input prefix up to that barrier (§7 invariant). Persistent/incremental backends (RocksDB) are deferred.

Snapshot / Checkpoint Coordinator (dfr-snapshot). Drives asynchronous barrier snapshots (Flink ABS, derived from Chandy-Lamport). Periodically injects CheckpointBarrier{epoch} records at sources. Barriers flow with the data; each operator, on receiving the barrier on all input channels (alignment), snapshots its state and forwards the barrier. When all sinks acknowledge epoch e, the snapshot is complete and durable. On recovery, the runtime restores every operator's state from the latest complete snapshot and resumes sources from the recorded offsets → exactly-once effects. Misaligned or tampered barriers (§24) break the consistent-cut guarantee.

Input / Source. Operators with no dataflow inputs. They pull from an external source (in P0: an in-memory iterator, generator, or file), wrap records in Message<D>, hold capabilities for the timestamps they will emit, push batches downstream, and advance watermarks (event-time sources). Sources are also where checkpoint barriers are injected and where offsets are recorded for replay. A source that drops its capability too early closes a frontier prematurely (safety bug); too late and the frontier stalls (liveness bug).

Output / Sink. Operators with no dataflow outputs. They drain incoming batches and perform side effects (print, collect, write). A probe is a special sink that exposes the current input frontier to the host (so the host can ask "has time T fully passed?"). Sinks under exactly-once must be idempotent or transactional (two-phase commit aligned to checkpoints) — otherwise restore double-emits side effects (§20).

Observability (dfr-metrics + tracing). Emits per-operator, per-worker metrics: records/s throughput, channel queue depth, frontier lag (wall-clock − frontier event-time), skew (max/min per-key load across workers), activation counts, checkpoint duration and alignment time, state size. Tracing spans wrap operator schedule calls and checkpoint epochs. This is the operator's only window into a running dataflow; without frontier-lag and skew it is impossible to diagnose stalls or hot keys (§22, §26).

4. System Constraints

All targets assume single-host, modern x86-64 (8–32 physical cores), DDR4/DDR5, NVMe local disk for checkpoints. P0 = single process, N = worker count.

6. Design Principles

Each principle is referenced throughout the blueprint by name.

6.1 Backpressure Everywhere

Statement. Every channel is bounded; producers block (or shed via credit exhaustion) when downstream cannot keep up. There is no unbounded buffer anywhere on the data path.

Tradeoff. Bounded buffers can cause cyclic deadlock (§8.10) and reduce peak throughput vs unbounded buffering; you trade peak burst absorption for bounded, predictable memory.

Operational implication. Queue depth is a first-class metric (§22). Sustained max-depth = the bottleneck operator; you scale or fuse it.

Violation breaks. An unbounded buffer turns load skew into OOM; a single slow sink can exhaust host memory. The bounded-resource invariant (§7) fails.

6.2 Progress Is Monotonic; Frontiers Never Regress

Statement. A frontier (the antichain of times still possible at a location) only ever advances in the partial order; it never moves backward. Produced/consumed counts are conserved.

Tradeoff. Monotonicity forbids "un-closing" a timestamp; late data beyond the watermark must be dropped or side-output (§19), not retroactively merged into closed results.

Operational implication. Frontier lag is monotone-progress health; a stalled frontier (§25) is a liveness incident.

Violation breaks. A regressing frontier causes a notification to fire, then more data to arrive at the "closed" time → duplicated or corrupted results; exactly-once is lost.

6.3 Determinism and Replayability

Statement. Given the same input stream, offsets, and graph, the runtime produces the same output (modulo declared non-determinism like wall-clock triggers). Sources record offsets; replay reproduces runs.

Tradeoff. Determinism constrains scheduling freedom (e.g., per-key processing order must be stable); some optimizations (racing two operators) are disallowed on deterministic edges.

Operational implication. Bugs are reproducible via deterministic replay (§28); incident forensics replays the exact input prefix.

Violation breaks. Non-deterministic operator order makes snapshots inconsistent across replays; you cannot validate exactly-once or debug heisenbugs.

6.4 Bounded Resource Usage

Statement. Memory, channel depth, in-flight batches, and active pointstamps are all bounded by configuration, not by input volume.

Tradeoff. Hard bounds can backpressure or (future) spill; you never let the runtime grow without limit.

Operational implication. Memory ceilings are enforced; crossing them triggers backpressure (and later, spill), never OOM-kill.

Violation breaks. State or window leak (§15, §19 pitfalls) → unbounded memory → host OOM → worker crash → recovery storm.

6.5 Operator Purity for Snapshotting

Statement. All mutable operator state lives in the declared KeyedState/operator-state handle. Operators do not mutate hidden global or thread-local state on the data path.

Tradeoff. Some convenient patterns (static caches, ambient counters) are forbidden or must be declared as state; ergonomic cost.

Operational implication. A snapshot of declared state fully captures the operator; restore is total.

Violation breaks. Hidden state is not snapshotted → after restore the operator's behavior diverges → exactly-once violated, results wrong, undebuggable.

6.6 Capability-Based Timestamps

Statement. An operator may emit a record at timestamp t only while it holds a capability for t. Capabilities are the only mechanism that keeps a frontier open. Dropping a capability is a promise: "I will never again emit at or below this time."

Tradeoff. Capability bookkeeping is extra code on every emit path; mistakes are subtle.

Operational implication. Outstanding capabilities are inspectable; a stuck frontier traces to an operator holding a capability it should have dropped.

Violation breaks. Holding too long → frontier stalls (liveness). Dropping too early → emit at a closed time → safety violation (§7).

6.7 Exactly-Once via Barriers, Not Retries

Statement. Exactly-once effects are achieved by consistent-cut snapshots + deterministic replay + idempotent/transactional sinks — not by deduplicating retried records.

Tradeoff. Requires alignment overhead and transactional sinks; not "fire and forget."

Operational implication. Recovery restores a snapshot and replays from recorded offsets; sinks commit aligned to epochs.

Violation breaks. Treating exactly-once as at-least-once + dedup leaks state (dedup tables grow unbounded) and fails for non-idempotent sinks.

6.8 Observability by Default

Statement. Every operator and channel emits throughput, queue depth, frontier, and (where relevant) skew and checkpoint metrics with no extra code from the operator author.

Tradeoff. Metric collection costs cycles and memory; sampled/aggregated to keep overhead < 2% (§30).

Operational implication. A new operator is observable the moment it is added; no "add metrics later."

Violation breaks. A stall or skew in an unobserved operator is invisible; MTTR explodes.

6.9 Static Topology

Statement. The dataflow graph is fixed at build time. No operators or edges are added/removed during execution (P0).

Tradeoff. No dynamic rescaling or runtime graph mutation in P0 (deferred); simpler, provably-correct progress tracking.

Operational implication. Rescaling requires stop-restore-from-snapshot (deferred rescaling, §27).

Violation breaks. The progress protocol's path summaries assume fixed topology; mutating mid-run corrupts frontier computation.

6.10 Crash-Only Semantics

Statement. The only shutdown path that must be correct is crash + recover-from-snapshot. There is no separate "clean shutdown" correctness requirement beyond draining.

Tradeoff. No elaborate graceful-shutdown protocol; you invest in fast, correct recovery instead.

Operational implication. kill -9 a worker; supervisor restarts; restore from latest complete snapshot.

Violation breaks. If recovery is only correct after clean shutdown, real crashes (OOM, panic) lose data.

6.11 Move, Don't Copy

Statement. Batches are moved between operators (Rust ownership); buffers are recycled via pools. Copies happen only at exchange (serialization) boundaries.

Tradeoff. Ownership discipline complicates fan-out (a batch consumed by two downstreams needs Rc/clone or split); explicit.

Operational implication. Allocation rate is a metric; steady-state alloc/free should approach zero on the hot path.

Violation breaks. Per-record allocation tanks throughput and spikes tail latency (allocator contention).

6.12 Logical Time Is a Partial Order

Statement. Timestamps are elements of a partial order (a lattice), not necessarily totally ordered. Frontiers are antichains. Iteration adds a coordinate (loop counter) to the product order.

Tradeoff. More complex than scalar timestamps; required for cyclic dataflow and multidimensional incremental computation.

Operational implication. Tooling must render antichains, not single numbers, for frontiers.

Violation breaks. Forcing a total order breaks iteration progress and differential-dataflow-style timestamps.

6.13 Symmetric Workers, Shared-Nothing

Statement. Every worker runs the same graph; workers share no mutable memory; they communicate only via channels and progress gossip.

Tradeoff. Symmetric design wastes nothing on a coordinator but requires distributed progress aggregation even in one process.

Operational implication. Adding a worker = adding a thread + rewiring exchange; the distributed (§23) path reuses the identical protocol.

Violation breaks. Shared mutable graph state across workers reintroduces locks, data races, and blocks distribution.

6.14 Fail Fast on Invariant Violation

Statement. Internal invariant violations (negative progress count, frontier regression, capability under-count) panic with diagnostics in debug, and emit a fatal metric + structured log + controlled abort in release — never silently continue.

Tradeoff. A bug crashes the worker (then recovers via §6.10) rather than producing wrong-but-running output.

Operational implication. "Correctness fault" is a distinct, paged alert class (§26).

Violation breaks. Silently continuing past a progress-count corruption yields irreproducible, wrong results that are nearly impossible to debug.

7. System Invariants

Each invariant: statement → why → enforced where → detection → telemetry → recovery → debugging.

7.1 Progress Monotonicity (Frontier Never Regresses)

  • Statement. For each location l, frontier(l) only advances in the partial order; no time once removed reappears.
  • Why. Notifications/window flush rely on "closed ⇒ no more data ≤ t". Regression ⇒ late data after flush ⇒ wrong results.
  • Enforced. dfr-progress::FrontierTracker::apply_update rejects updates that would re-open a closed time; antichain merge is monotone.
  • Detection. Assertion new ⪰ old on every frontier mutation; debug panics, release emits progress.regression.total + abort.
  • Telemetry. frontier.advance.count, frontier.regression.total (must stay 0), per-location frontier gauge.
  • Recovery. Correctness fault ⇒ controlled abort ⇒ restore from last complete snapshot (§6.10).
  • Debugging. Replay (§28) the pointstamp delta log; bisect to the update that regressed; inspect path summaries (§8.4).

7.2 Pointstamp Count Conservation (Non-Negative)

  • Statement. For every Pointstamp, cumulative produced − consumed ≥ 0 at all times; a count reaches 0 exactly once before close.
  • Why. A negative count means consumed-before-produced ⇒ frontier computed from corrupt counts ⇒ premature close.
  • Enforced. ProgressTracker adds signed deltas; checked-sub in debug; per-pointstamp i64 with underflow guard.
  • Detection. count < 0 ⇒ panic(debug)/fatal-metric(release).
  • Telemetry. pointstamp.count.negative.total (0), pointstamp.active.gauge.
  • Recovery. Abort + restore.
  • Debugging. Dump active pointstamp table; correlate produced vs consumed per edge; usually a missing consumed report or double produced.

7.3 Capability Discipline (Emit Only Under Held Capability)

  • Statement. An operator emits at time t ⇒ it currently holds Capability whose time ⪯ t.
  • Why. Capabilities are the only thing keeping a frontier open; emit without one ⇒ emit at a closed time (violates 7.1).
  • Enforced. OutputHandle::session(cap) requires a &Capability<T>; give(t, d) debug-asserts cap.time ⪯ t.
  • Detection. Session API makes it unrepresentable to emit without a cap; debug assert on the ⪯ check.
  • Telemetry. capability.outstanding.gauge per operator; capability.illegal_emit.total (0).
  • Recovery. Abort + restore.
  • Debugging. A stuck frontier ⇒ list operators holding caps ≤ stuck time (probe + capability dump).

7.4 No Late Message Past a Closed Frontier

  • Statement. No data message arrives on an edge at a time already removed from that edge's input frontier.
  • Why. Defines exactly-once + notification correctness.
  • Enforced. Implied by 7.1+7.3 (if upstream can still send t, t is in the frontier). Receiver debug-asserts msg.time is ⪰ current frontier-not-yet-closed.
  • Detection. Receiver-side assert; in event-time streams, beyond-watermark records routed to lateness side-output (§19), not an error.
  • Telemetry. message.late.total (0 on internal edges), records.dropped_late.total (event-time, allowed).
  • Recovery. Internal late ⇒ correctness fault. Event-time late ⇒ drop/side-output per policy.
  • Debugging. Trace the source's capability lifecycle; check watermark generator.

7.5 Deterministic Per-Channel FIFO

  • Statement. Messages on a single channel are delivered in send order; per-key processing order is stable across replays.
  • Why. Determinism/replayability (§6.3); snapshot consistency across reruns.
  • Enforced. SPSC/MPSC rings preserve order; exchange uses a stable hash + per-(src,dst) FIFO subchannel.
  • Detection. Sequence numbers per channel in debug; gap/reorder ⇒ assert.
  • Telemetry. channel.reorder.total (0), per-channel high-water sequence.
  • Recovery. Reorder is a channel bug ⇒ abort.
  • Debugging. Compare two replays' per-key output order; diverge ⇒ a non-FIFO path or unstable hash.

7.6 Exactly-Once Effects on Recovery

  • Statement. After restore from snapshot S + replay from recorded offsets, external effects equal a non-failing run: no duplicates, no losses.
  • Why. Core fault-tolerance contract.
  • Enforced. Aligned barriers ⇒ consistent cut (§20); idempotent/transactional sinks commit aligned to epoch (§21 sinks).
  • Detection. End-to-end conformance: inject crash, compare sink output to golden (§20.5).
  • Telemetry. checkpoint.complete.total, recovery.total, sink.duplicate.detected.total (0).
  • Recovery. Itself the recovery mechanism; failed checkpoints are discarded, last complete one used.
  • Debugging. Verify barrier alignment per operator; verify sink 2PC pre-commit/commit log vs epoch.

7.7 Scheduler Liveness (No Deadlock, No Starvation)

  • Statement. If any operator can make progress, some operator is scheduled; if the dataflow can advance a frontier, it eventually does.
  • Why. Bounded buffers + cycles risk deadlock (§8.10); unfair scheduling risks starvation.
  • Enforced. Activation queue + parking only when no operator is runnable AND no progress pending; cycle buffers sized with reserve (§18); fair round-robin/aging.
  • Detection. Watchdog: if now − last_frontier_advance > stall_threshold and queues non-empty ⇒ stall alert (§25).
  • Telemetry. scheduler.park.total, operator.activation.count, frontier.stall.seconds.
  • Recovery. Stall ⇒ dump runnable set + channel credits + frontiers; deadlock ⇒ abort+restore; tune buffer reserve.
  • Debugging. Deadlock signature: all operators Blocked on credit in a cycle; starvation: one operator's activation count flat while inputs grow.

7.8 Bounded Buffers / Backpressure Always On

  • Statement. Every channel buffer ≤ its configured capacity; producers cannot exceed it.
  • Why. Bounded-resource invariant (§6.1, §6.4); prevents OOM.
  • Enforced. Credit accounting in dfr-channels; send returns Pending when no credit.
  • Detection. queue.depth > capacity ⇒ assert; never observed in correct code.
  • Telemetry. channel.queue.depth.gauge, channel.backpressure.seconds.
  • Recovery. Sustained max depth ⇒ scale/fuse the bottleneck (operational, not a fault).
  • Debugging. Find max-depth channel = bottleneck; check downstream operator activation/throughput.

7.9 Snapshot Consistency (Consistent Cut)

  • Statement. A completed snapshot reflects exactly the input prefix up to its barrier on every source — a consistent global cut.
  • Why. Exactly-once depends on it; an inconsistent cut double-counts or loses in-flight records.
  • Enforced. Alignment: an operator snapshots only after the barrier arrives on all inputs; pre-barrier in-flight records are part of upstream's snapshot, not buffered into post-barrier state (aligned mode).
  • Detection. Per-snapshot checksum of (state size, record counts) vs an independent replay-based recomputation in conformance.
  • Telemetry. checkpoint.alignment.ms, checkpoint.state.bytes, checkpoint.inconsistent.total (0).
  • Recovery. Inconsistent snapshot rejected; not marked complete; previous one retained.
  • Debugging. Inspect barrier-alignment log per operator; verify no post-barrier data folded pre-barrier.

7.10 Loop Timestamp Strictly Increases on Feedback

  • Statement. Every traversal of a feedback edge strictly increments the loop coordinate; the product order guarantees termination when the loop frontier empties.
  • Why. Without strict increment, a cycle's frontier never advances ⇒ non-termination / livelock.
  • Enforced. LoopVariable::feedback applies Timestamp::loop_increment (path summary +1 on the inner coordinate); builder rejects a cycle lacking a feedback summary with a positive increment.
  • Detection. Build-time: cycle without strict-increase summary ⇒ GraphError::UnboundedCycle. Runtime: loop frontier non-advancing watchdog.
  • Telemetry. loop.iteration.max.gauge, loop.frontier.advance.count.
  • Recovery. Build error rejects the graph; runtime stall ⇒ stall handling (§7.7).
  • Debugging. Print loop frontier per iteration; confirm increment applied; check Iterate termination predicate.

7.11 State Partition ↔ Exchange Key Agreement

  • Statement. A worker owns the keyed state for exactly the keys routed to it by the exchange partitioner; no key's state lives on two workers.
  • Why. Stateful correctness + snapshot completeness; split state ⇒ lost updates or double-counts.
  • Enforced. Same hash/partition function used for exchange routing and state partition ownership; one source of truth (Pact).
  • Detection. Debug assert: on keyed access, partition(key) == self.worker_id.
  • Telemetry. state.foreign_key_access.total (0), state.keys.gauge per worker.
  • Recovery. Mismatch ⇒ correctness fault ⇒ abort.
  • Debugging. Compare partitioner used by exchange vs state; a rescale or hash change is the usual culprit (rescaling deferred, §27).

7.12 Build-Time Type Soundness on Edges

  • Statement. An edge connecting output port of type Stream<S,D> to an input expecting D' compiles only if D == D' and scopes match.
  • Why. No runtime type errors on the data path; zero-cost.
  • Enforced. Rust generics + phantom types in dfr-core; connect is generic over D.
  • Detection. Compile time.
  • Telemetry. n/a (compile).
  • Recovery. n/a.
  • Debugging. Type error points to the mismatched combinator.

8.2 Execution Model (Locked: Push)

  • Push, not pull. Upstream produces batches and pushes downstream; downstream applies backpressure via credits. Pull/demand model deferred (PhaseDeferred("FINAL_BLUEPRINT §8")).
  • A record is a token (dataflow lineage); operator "firing" = activation (schedule).
  • Batches amortize per-record overhead; default batch 1024 records.

8.3 Logical Time, Timestamps, Partial Order

  • Timestamp T: element of a partial order with a least element and a join (lattice). Examples:
    • Root scope: u64 epoch (event-time millis or sequence) — totally ordered.
    • Nested loop scope: Product<Outer, u64> where the u64 is the loop counter — partially ordered.
  • PartialOrder::less_equal(a,b) defines a ⪯ b. Incomparable times coexist in a frontier.
  • Path summary: a function S: T → T describing how a timestamp is transformed traversing a path (identity on most edges; +1 on a loop-back edge's inner coordinate).

8.4 Frontier, Antichain, Pointstamp

Antichain<T> = minimal set {t1..tk} : no ti ⪯ tj for i≠j
Frontier(l)  = antichain of times that MAY still appear at location l
Pointstamp   = (location: LocationId, time: T)
ProgressUpdate = (Pointstamp, delta: i64)   // +1 produced, -1 consumed
  • A pointstamp is closed when its outstanding count is 0 AND no upstream pointstamp can reach it (via path summaries) with time ⪯.
  • Closing a pointstamp may advance one or more downstream frontiers.
  • Reachability: precomputed at build time — for each pair of locations, the minimal path summaries; used to decide what can still arrive.

8.5 Capability Model

Capability<T> : grants right to emit at times ⪰ self.time at a specific output port
  - clone(t')  where t' ⪰ self.time → new capability at t' (downgrade)
  - downgrade(t')                    → move this capability forward to t' ⪰ time
  - drop                              → promise: no more emits at ≤ time on this port
holding a Capability keeps the corresponding pointstamp count ≥ 1

State-transition (capability lifecycle):

From Event To Effect on progress
none source emits epoch e hold cap(e) produced(loc, e) += 1
hold cap(e) downgrade(e+1) hold cap(e+1) produced(e+1)+=1, consumed(e)+=1
hold cap(e) clone for output hold cap(e)×2 produced(e)+=1
hold cap(e) drop none consumed(e)+=1 → may close e

  flat_map: ["a","b","a"] → Message{0,[a,b,a]}; consumed(src,0)/produced(fm,0)

  Source downgrades cap(0)→cap(1): produced(src,1)+=1, consumed(src,0)+=1
  ...counts propagate; pointstamp (src,0) count → 0
t=epoch 0 closes (no op can produce ≤ 0):
  frontier at aggregate input advances past 0 → NOTIFICATION fires for epoch 0
  aggregate flushes {a:2,b:1} at time 0; drops cap(0); produced(agg,0)/sink
  sink prints (a,2),(b,1) for epoch 0

11. Core Schema and Core Types

Lightweight signatures only (no bodies). For each: ownership, mutation, concurrency, persistence, serialization, compatibility.

11.1 Timestamp / Order Traits (dfr-core::timestamp)

trait PartialOrder { fn less_equal(&self, other: &Self) -> bool; }
trait Lattice: PartialOrder { fn join(&self, &Self) -> Self; fn meet(&self, &Self) -> Self; fn minimum() -> Self; }
trait Timestamp: PartialOrder + Lattice + Clone + Ord + Hash + 'static {
    type Summary: PathSummary<Self>;   // how this timestamp transforms along a path
}
trait PathSummary<T> { fn results_in(&self, src: &T) -> Option<T>;   // None = unreachable
                       fn followed_by(&self, &Self) -> Option<Self>; }
struct Product<O, I> { outer: O, inner: I }   // nested-scope timestamp (loop coord = inner)
type RootTime = u64;                          // epoch / event-time at root scope
  • Ownership. Value types, Clone. Mutation. Immutable; transformations produce new values. Concurrency. Send + Sync (plain data). Persistence. Serialized in snapshots/messages. Serialization. Stable encoding (fixed-width or varint); versioned. Compatibility. Timestamp type is part of the graph type; changing it is a breaking change.

11.2 Frontier / Antichain / Capability (dfr-progress)

  fn insert(&mut self, t: T) -> bool;                   // true if it changed the antichain
  fn less_equal(&self, t: &T) -> bool;                  // some element ⪯ t

  // Drop impl: decrements pointstamp count (consumed += 1)
  • Ownership. Capability owns a reference-counted hold on a pointstamp; Drop releases it. Mutation. downgrade moves time forward only. Concurrency. Capabilities are per-operator (worker-local), not Sync; progress deltas crossing workers go via broadcast. Persistence. Held capabilities at a barrier are part of operator snapshot state. Serialization. Capability = (port, time); reconstructed on restore. Compatibility. Internal; not a wire type.

Single-threaded per worker; cross-worker deltas arrive via channels and are applied in the worker loop (no shared mutation). Persistence. Tracker state is derivable from operator caps + in-flight; not separately snapshotted (rebuilt on restore). Serialization. ProgressUpdate is the wire type for gossip (§23). Compatibility. Gossip format versioned.

12. Phase 1 — Graph Construction API, Typed Edges, Operator Trait

12.1 Objectives

  • Builder DSL constructs an immutable RuntimeGraph of operators + typed edges before any execution.
  • Operator trait + Stream<S,D> typed edge handle; connect() compile-time type-checked (§7.12).
  • Scope/Region/LocationId/OperatorId/PortId/WorkerId assigned; topology + path summaries computed for the tracker (§8.4).
  • Constraint introduced: static topology (§6.9) — graph frozen at build(); no mutation during execution.
  • No scheduling, no data movement yet. Output is a graph you can inspect and DOT-export.

12.2 Detailed Implementation Steps

Theory anchors: P9 (Static Topology), P12 (Logical Time Is a Partial Order), ADR-08 (timestamp/lattice traits), I12 (build-time type soundness on edges); the reachability precompute is the build-time half of the Naiad progress protocol (ADR-10).

  • dfr-core/builder.rs: GraphBuilder::new() → scope(|s| …) → returns RuntimeGraph (frozen per P9). Records operators, edges, exchange pacts, scope nesting.
  • dfr-core/stream.rs: Stream<S,D>{scope, source:(OperatorId,PortId), _pd}. Combinator entry points (map,filter,flat_map,inspect,exchange,probe) register an operator + wire one edge, return a new Stream with the next D.
  • dfr-core/operator.rs: trait Operator{ schedule(&mut, &mut SchedulerCtx)->Activity; name()->&str }; OperatorInfo{id,scope,inputs,outputs}; ports allocated per operator.
  • dfr-core/scope.rs: Scope trait, root scope (RootTime=u64), child scope adds Product<O,I>; enter/leave reserved for Phase 7.
  • dfr-core/location.rs: newtype IDs (OperatorId(u32), PortId(u32), LocationId{op,port}, WorkerId(u32)); monotonic allocators.
  • dfr-core/summary.rs: per-edge PathSummary (identity default); build-time reachability precompute: for each (src loc, dst loc) the minimal summary; store as Reachability table consumed by dfr-progress.
  • dfr-core/error.rs: GraphError{UnboundedCycle,TypeMismatch,DuplicatePort,EmptyScope}; build() validates: no dangling ports, every operator reachable from a source, cycles only inside loop scopes (deferred check stub now, enforced Phase 7).
  • dfr-cli/dot.rs: walk RuntimeGraph → Graphviz DOT (operators=nodes, edges labeled with D typename + pact kind).
  • Instrumentation: builder emits graph.operators.gauge, graph.edges.gauge; tracing span around build().

13. Phase 2 — Single-Threaded Push Scheduler + Operator Activation

13.1 Objectives

  • Execute an acyclic graph end-to-end on one worker: push batches source→sink.
  • Worker::execute/step, ActivationQueue, operator state machine (§8.7), quiescence detection.
  • Message<D>{time,data,from} + buffer pool (move-don't-copy, §6.11); default batch 1024.
  • Constraint introduced: cooperative scheduling — operators yield; no preemption; fairness baseline.

13.2 Detailed Implementation Steps

Theory anchors: P11 (Move, Don't Copy) — batches move through the buffer pool; I7 (scheduler liveness, no deadlock/starvation); ADR-04 (custom cooperative scheduler, not async) and ADR-05 (worker-per-core threads). The push/firing model is the dataflow-token tradition (§5.2 Dataflow Architectures; §8.2).

  • dfr-scheduler/worker.rs: Worker{id,peers:1,graph,activation,channels,…}; execute() loops step() until quiescent (no runnable op, no pending progress).
  • dfr-scheduler/activate.rs: ActivationQueue{ready:VecDeque<OperatorId>, queued:BitSet}; activate(op) (idempotent via queued bit), next().
  • dfr-scheduler/schedule.rs: pop op → build SchedulerCtx (input/output handles) → call Operator::schedule → interpret Activity{Active→re-queue, Idle→park-eligible, Blocked→await credit}.
  • dfr-core InputHandle::next() drains one Message from an input port; OutputHandle::session(cap).give(t,d) pushes downstream (cap mechanics stubbed until Phase 5 — Phase 2 uses a single implicit epoch).
  • dfr-channels/pool.rs: BufferPool recycles Vec<D>; give pulls a buffer, fills, pushes; receiver returns buffer after drain.
  • Activation triggers wired: producing onto an edge activates the consumer; Phase 2 has no credit yet (bounded channels arrive Phase 3) — use a simple bounded vec to avoid unbounded growth meanwhile.
  • Quiescence: step() returns false when activation.ready empty; execute exits. Instrumentation: operator.activation.count, scheduler.step.total, span per schedule.

13.3 Deliverable

  • Word-count topology (single implicit epoch) runs source→sink on one worker; sink collects correct multiset of records. dfr-cli run examples/word_count.rs prints output.

13.4 Acceptance Criteria

  • cargo test -p dfr-scheduler: a 4-operator chain over 1M records yields exact expected output; terminates (quiescent) deterministically.
  • Throughput ≥ 5M records/s unfused stateless map on one core (§4.1); per-batch processing < 20 µs p50 (§4.2).
  • Buffer pool: steady-state allocations/sec ≈ 0 after warmup (alloc counter flat).
  • No operator starves over a 10M-record run (every op's activation count > 0; min/max activation ratio bounded).

13.6 Pitfalls

  • Double-activation (op queued twice) → wasted scheduling or reentrancy. Root cause: missing queued bit check. Detect: assert idempotent activate; operator.activation.count spikes.
  • Lost wakeup: producer pushes but does not activate consumer → stall at quiescence with data buffered. Detect: quiescence watchdog asserts all channels empty; dump non-empty channels.

  • Avoid Box<dyn Operator> virtual dispatch cost where fusion (Phase 10) can inline; Phase 2 accepts boxed dispatch (≥5M/s target reflects that).

13.8 Edge Cases

  • Single record (batch of 1) → no batch-size assumptions break.

  • Operator that emits nothing (pure filter rejecting all) → downstream sees flush/close, quiesces.
  • Re-entrant activation during schedule (op activates itself) → bounded by queued bit; must not infinite-loop.

13.9 Failure Analysis

  • Breaks: lost wakeup → silent stall (data buffered, scheduler parks). Detection: quiescence-with-nonempty-channel assert; scheduler.park.total rises while records.out flat. Blast radius: whole job stalls. Containment: watchdog (§7.7) escalates to stall alert. Recovery (P0 single-thread): none automatic — bug fix; later phases add restore. Visibility: dump runnable set + channel depths. Postmortem: trace which give failed to activate.

  • Deployment: dfr-cli run. Rollback: revert operator code. Compatibility: execute/step embedding API stabilized here (§11.8).

14. Phase 3 — Channels, Bounded Buffers, Backpressure

14.1 Objectives

  • Replace stopgap vecs with bounded SPSC/MPSC rings + credit-based backpressure (§6.1).
  • Enforce bounded-buffer invariant (§7.8): producer blocks (ChannelError::WouldBlock) when credit exhausted.
  • Integrate credit-freeing into activation: returning a buffer downstream re-grants credit → activates a blocked producer.
  • Constraint introduced: every data edge is bounded; queue depth ≤ capacity, observable.

14.2 Detailed Implementation Steps

Theory anchors: P1 (Backpressure Everywhere) and P4 (Bounded Resource Usage); I8 (bounded buffers / backpressure always on); ADR-06 (custom ring) and ADR-07 (atomics + CachePadded). Lock-free ring + memory ordering follow Herlihy & Shavit ch. 10–11 (§5.1); credit vocabulary from Reactive Streams (§5.4, MM2).

  • dfr-channels/ring.rs: bounded SPSC and MPSC rings; CachePadded head/tail (avoid false sharing, ADR-07); acquire/release ordering documented per field; capacity = power-of-two for mask indexing.
  • dfr-channels/credit.rs: Credit{available:AtomicI64}; producer try_acquire() (single CAS, <10 µs §4.4); consumer release(n) on buffer return.
  • dfr-channels/pushpull.rs: Push::push(Option<Message>) returns Pending when no credit; Pull::pull() returns Option<&mut Message>; None = flush/close.
  • dfr-channels/lib.rs: Bounded<T>{ring,credit}; wire into OutputHandle/InputHandle so give respects credit and parks the operator (Activity::Blocked) on exhaustion.
  • Scheduler: blocked-on-credit operators move out of ready; release re-activates them. Track channel.queue.depth.gauge, channel.backpressure.seconds.
  • Memory-order tests: loom (or hand-modeled) on ring + credit for SPSC/MPSC; assert no lost messages, FIFO (§7.5).

14.3 Deliverable

  • A slow sink applies backpressure upstream; queue depth stabilizes at capacity instead of growing; throughput throttles to sink rate; no OOM. Demonstrated via a rate-limited sink example.

14.4 Acceptance Criteria

  • Sustained overload (source ≫ sink): max queue depth ≤ configured capacity for the entire run; memory flat (§4.7); no monotone growth (§4.4 stability).
  • FIFO per channel verified by sequence-number test (channel.reorder.total == 0, §7.5).
  • Credit grant latency p99 < 10 µs (microbench).
  • Backpressure does not deadlock the acyclic graph (Phase 7 handles cyclic deadlock); liveness test passes.

14.5 Conformance Fixtures

Fixture Purpose Expected

credit_latency.bench credit CAS p99 < 10 µs

14.6 Pitfalls

  • Credit leak: consumer forgets to release on some path → producer stalls forever with capacity free. Detect: credit.available stuck low while depth low; assert credits conserved (granted = released + outstanding).
  • Double-release → credit > capacity → buffer overflow / invariant break. Detect: queue.depth > capacity assert (§7.8).
  • False sharing on head/tail → throughput cliff. Detect: perf counters (cache-line bounces); fix CachePadded.
  • Memory-ordering bug (relaxed where acquire/release needed) → lost/duplicated message, ABA. Detect: loom model; FIFO seq test.
  • Spin without backoff on full ring → CPU burn. Use exponential backoff / park (crossbeam Backoff).

14.7 Performance Concerns

  • Single CAS per credit op; avoid fences on the common path. Batch credits (grant N at once) to amortize.
  • Ring indexing via power-of-two mask, no modulo. Keep Message small; payload is Vec<D> (pointer), not inline.
  • Backpressure signaling must not thrash activation: hysteresis (re-activate when credit ≥ threshold, not on every single release).
  • Tail latency: blocked→unblocked transition cost dominated by activation enqueue; keep O(1).

14.8 Edge Cases

  • Capacity 1 channel → degenerate but must work (strict ping-pong).
  • Producer and consumer both fast → credits never exhaust; no backpressure overhead beyond CAS.
  • Close (push(None)) while credit-blocked → flush semantics; consumer drains then sees close.
  • MPSC fan-in with one slow producer → other producers unaffected; per-producer credit independent.
  • Integer overflow on credit/sequence counters → use i64/wrapping with guard; assert non-negative (§7.2 analog).

14.9 Failure Analysis

  • Breaks: credit accounting bug → either stall (leak) or overflow (double-release → corruption). Detection: credit-conservation assert + depth>cap assert. Blast radius: one edge → stalls its consumer subtree, or corrupts that channel. Containment: fail-fast (§6.14) on overflow. Recovery (P0): bug fix. Visibility: per-channel depth + credit gauges, backpressure seconds. Postmortem: correlate stalled producer with consumer release path.

14.10 Operational Notes

  • Metrics: channel.queue.depth.gauge, channel.backpressure.seconds, credit.available.gauge, channel.reorder.total(0). Max-depth channel = bottleneck (operator runbook backpressure_deadlock.md).
  • Tuning knob: per-edge capacity (batches × records). Default 16×1024 (§4.4).
  • Deployment/rollback unchanged (library). Compatibility: channel capacity is config, not API; ring memory model is internal but documented (unsafe audited, ADR-23).

16. Phase 5 — Progress Tracking (Pointstamps, Capabilities, Frontiers, Antichains)

The correctness heart of the system (Naiad / Timely). Track frontiers, not per-message. A bug here either deadlocks (frontier never advances) or violates safety (frontier advances prematurely → notification fires before all data arrives → wrong results). This is the staff-level milestone (§2.5).

16.1 Objectives

  • Implement the timely pointstamp protocol: produced/consumed counts → frontier computation (§8.4).
  • Antichain<T>, Frontier, Capability<T> (downgrade/drop), ProgressTracker (update/propagate).
  • Capability-based emit (§6.6); frontiers as antichains (§6.12); progress monotonicity (§7.1) and count conservation (§7.2) enforced.
  • Drive operator input frontiers so downstream knows "no more data ≤ t" — replacing Phase 4's eager emit.
  • Constraint introduced: progress is decentralized, batched (track frontiers not per-record); never per-message gossip storm (§8.10).

16.2 Detailed Implementation Steps

Theory anchors: this is the Naiad pointstamp protocol (McSherry et al., SOSP 2013; ADR-10). P2 (Progress Is Monotonic), P6 (Capability-Based Timestamps), P12 (Logical Time Is a Partial Order); I1 (progress monotonicity), I2 (count conservation), I3 (capability discipline). Antichain/lattice algebra from Davey & Priestley ch. 1–2 (§5.1); ADR-09 (Antichain representation).

  • dfr-progress/antichain.rs: Antichain<T>{SmallVec<[T;4]>}; insert (drop dominated, keep minimal), less_equal(&T), frontier(); ChangeBatch<T>{Vec<(T,i64)>} compaction (sum deltas per time, drop zeros).
  • dfr-progress/frontier.rs: Frontier/MutableFrontier with ChangeBatch; FrontierTracker::apply_update rejects regressions (assert new ⪰ old, §7.1).
  • dfr-progress/capability.rs: Capability<T>{time,port,tracker:Weak}; downgrade(t') (t'⪰time): produced(t')+1, consumed(time)+1; delayed(t') clone; Drop → consumed(time)+1. Holding a cap keeps the pointstamp count ≥1 (§7.3).
  • dfr-progress/pointstamp.rs: Pointstamp{location,time}; signed i64 count table; checked-sub underflow guard (§7.2).
  • dfr-progress/reachability.rs: runtime reachability over build-time path summaries (PathSummary::results_in/followed_by); answers "can any pointstamp ⪯ p still be produced upstream?".
  • dfr-progress/tracker.rs: update(ProgressUpdate) applies delta; propagate() closes pointstamps whose count=0 AND no upstream reach → emits FrontierChange per location → activates operators / fires notifications (Phase 7 consumes notifications fully).
  • Wire OutputHandle::session(cap) to require &Capability (§7.3 unrepresentable-illegal-emit); give debug-asserts cap.time ⪯ t.
  • Sources hold caps and downgrade to advance epochs; sinks/probe expose input frontier to host.
  • Property tests (proptest): random DAGs + delta streams → frontier monotone, counts conserved, eventual quiescence (conformance/progress/).

16.3 Deliverable

  • Word-count emits on frontier advance (notification), not eagerly: epoch N's results flush exactly when frontier passes N. probe lets the host ask "has time T fully passed?" and get a correct yes/no.

16.4 Acceptance Criteria

  • Diamond / fan-in fixture: frontier advances correctly (no premature close, no stall) — the canonical subtlety (§2.5, §8.10).
  • Property tests: across 10k random graphs+delta streams, frontier.regression.total==0, pointstamp.count.negative.total==0, all reach quiescence.
  • Progress-tracking round (local delta → frontier update) < 1 ms typical, < 10 ms under heavy fan-in (§4.3).
  • Notification → operator activation < 50 µs p50 (§4.2).

16.6 Pitfalls

  • Diamond premature close: closing a join's frontier before both branches reported consumed → notification fires early → wrong/partial results. Root cause: reachability misses one path summary. Debug: dump per-location reachable set; replay delta log.
  • Capability held too long → frontier stalls (liveness). Debug: list operators holding caps ≤ stuck time (§7.3 telemetry).
  • Capability dropped too early → emit at closed time (safety, §7.4). Debug: capability.illegal_emit.total; trace source cap lifecycle.

  • Antichain not minimal (kept a dominated element) → frontier over-conservative → false stall, or wasted comparisons. Assert minimality post-insert.
  • followed_by summary composition wrong → reachability under/over-estimates → deadlock or premature close. Unit-test summary algebra exhaustively.

16.7 Performance Concerns

  • propagate cost O(active pointstamps), not O(records) — batching (ChangeBatch) is mandatory (§4.6).
  • Antichain ops on small frontiers (typ. ≤4) → SmallVec inline, no heap. Large frontiers (iteration, multidim) → watch O(k²) comparisons.
  • Reachability precompute amortizes; runtime queries are table lookups. Cache the "can-still-arrive" result per (location, frontier) where possible.
  • Progress messages interleave with data on the same channel ordering (§8.6) — keep them cheap; do not block data on progress.

16.8 Edge Cases

  • Multiple incomparable times at one frontier (partial order) → antichain with >1 element; notifications fire per closed time.
  • Frontier already empty (no caps) at start → location immediately quiesced.
  • Concurrent downgrade of cloned capabilities → produced/consumed must net correctly (each clone independently tracked).
  • Loop coordinate (Phase 7) makes times partially ordered → tracker must not assume total order (test with Product).
  • Delta arriving for a closed pointstamp → invariant violation (late, §7.4) → fail-fast.
  • Underflow: consumed before produced → count<0 → RuntimeFault::NegativeCount (§7.2).

Containment: correctness fault → controlled abort → restore (§6.10). Recovery: restore from snapshot (Phase 9); fix tracker. Visibility: per-location frontier gauge, active-pointstamp table, regression/negative counters. Postmortem: deterministic replay (§28) of the pointstamp delta log; bisect to the regressing/closing update; inspect path summaries.

  • Metrics: frontier.advance.count, frontier.regression.total(0), pointstamp.active.gauge, pointstamp.count.negative.total(0), capability.outstanding.gauge, per-location frontier gauge, frontier.stall.seconds.
  • Tooling: tools/frontier_viz/ renders antichains + frontier lag (text/SVG) — operators cannot read raw antichains otherwise (§3.2).
  • Runbook frontier_stall.md: stuck frontier → dump caps ≤ stuck time + reachable upstream set.

17. Phase 6 — Data-Parallel Workers + Exchange/Shuffle by Key

17.1 Objectives

  • Multiple symmetric workers (one-per-core, §6.13); each runs a full copy of the graph over a key-partition of data.
  • Exchange/shuffle: partition records by key hash; one logical subchannel per (src_worker,dst_worker,edge) (§3.1).
  • Distributed progress: workers gossip per-pointstamp produced/consumed deltas (batched, §16); aggregate frontiers across workers.
  • State partition ↔ exchange key agreement (§7.11) now non-trivial (N partitions).
  • Constraint introduced: shared-nothing; workers communicate only via channels + progress broadcast. Intra-process first, then TCP groundwork (network transport itself deferred, §23).

17.2 Detailed Implementation Steps

Theory anchors: P13 (Symmetric Workers, Shared-Nothing); I11 (state partition ↔ exchange key); the decentralized produced/consumed gossip is the distributed half of the Naiad pointstamp protocol (ADR-10; Naiad, SOSP 2013); ADR-12 (exchange serialization, free in-process).

  • dfr-channels/exchange.rs: Pact{partition:fn(&D)->u64, kind:Exchange}; route each record to partition(key) % peers; one SPSC subchannel per (src,dst); preserve per-subchannel FIFO (§7.5).
  • dfr-scheduler/worker.rs: spawn N Worker threads, WorkerId 0..N; each owns its shard + its endpoints of every exchange channel; optional core pinning (NUMA-local state, §4.8).
  • dfr-operators/exchange.rs: operator wrapper that pushes outgoing partitioned batches and pulls incoming from peers; integrates credit per subchannel (backpressure across workers).
  • dfr-progress/broadcast.rs: batched progress gossip — each worker broadcasts its ChangeBatch of pointstamp deltas; tracker aggregates remote + local before propagate. Frontier is the meet across workers' contributions.
  • dfr-state: N partitions; partition(key)==self.worker_id enforced on keyed access (§7.11); state for a key lives on exactly one worker.
  • Quiescence/termination now global: a frontier is closed only when all workers report no outstanding work ≤ t (cross-worker progress).
  • Intra-process transport now; dfr-channels exposes a transport trait so TCP (§23) drops in later. Instrumentation: exchange.records.total, skew gauge (max/min per-worker load), progress.broadcast.bytes.

17.3 Deliverable

  • Word-count runs on N workers with exchange-by-word; aggregate throughput scales ~linearly with cores (to memory-bandwidth / fanout limits, §31); output identical to single-worker (determinism, §6.3).

17.4 Acceptance Criteria

  • Aggregate throughput scales ≥ 0.7×N up to 8 cores on a uniform-key workload (§4.1, §31); exchange ≥ 8M records/s/core in-process (§4.1).
  • Output multiset identical across N=1,2,4,8 (determinism) for the same input.
  • state.foreign_key_access.total == 0; every key's state on exactly one worker (§7.11).
  • Cross-worker frontier advances correctly (global termination); no premature close with idle workers.

17.6 Pitfalls

  • Inconsistent partition fn between exchange and state ownership → split state, lost updates (§7.11). Detect: foreign-key-access assert. Root cause: two hash impls; enforce single Pact source of truth.
  • Progress gossip storm: broadcasting per record → network/CPU melt (§8.10). Fix: batch ChangeBatch, coalesce per round.
  • Cross-worker deadlock: exchange backpressure + symmetric fan-in → all workers blocked on each other. Detect: all-Blocked watchdog (§7.7). Mitigate: sufficient subchannel credit; (cycles handled Phase 7).
  • Skew straggler: one worker hot (hot key) → tail latency, frontier lag. Detect: skew gauge; mitigate rekey/salt (§22, runbook key_skew.md).
  • Non-deterministic exchange order (e.g. racing pulls) → output diverges across runs. Pull in a fixed worker order; stable hash.
  • %peers vs power-of-two mask inconsistency on rescale → key moves workers (rescaling deferred, §27).

17.7 Performance Concerns

  • Exchange = hash + partition + copy/serialize. In-process: move/Rc, no serialize (ADR-12). Hash is the cost; prehash keys, cheap hash (§4.1 = 8M/s/core target includes hash+partition).
  • False sharing across worker subchannels → CachePadded per endpoint.
  • NUMA: cross-node exchange costs bandwidth (§4.8); co-locate partners; pin workers.
  • Progress broadcast bytes scale with active pointstamps × workers; batch + compact (ChangeBatch) to keep progress.broadcast.bytes low.
  • All-to-all fanout is O(N²) channels → memory + scheduling overhead at high N (§31 ceiling).

17.8 Edge Cases

  • N=1 → exchange degenerates to identity (self-channel); no regression vs Phase 5.
  • All records one key → one worker does all work; others idle but must still advance frontier (global termination).
  • Worker with empty partition → must still gossip "nothing outstanding" so global frontier advances (else stall, §6.6).
  • Partition fn returns out-of-range → modulo guard; assert < peers.
  • Odd record count not divisible by N → uneven but correct partitioning.
  • Clock skew across workers irrelevant — event time via watermarks, not wall clock (§4.8).

17.9 Failure Analysis

  • Breaks: split-state (wrong partition fn) → silent wrong results; cross-worker deadlock → hang; gossip storm → throughput collapse. Detection: foreign-key assert, all-Blocked watchdog, broadcast-bytes gauge. Blast radius: whole job (correctness or liveness). Containment: fail-fast on foreign access; stall escalation. Recovery: restore (Phase 9). Visibility: skew gauge, per-worker frontier, exchange counts, broadcast bytes. Postmortem: compare partition fns; per-worker frontier trace to find the lagging/idle worker.

17.10 Operational Notes

  • Metrics per worker: exchange.records.total, skew.gauge (max/min per-worker load), progress.broadcast.bytes, per-worker frontier + throughput. Skew is the key streaming pathology (§22).
  • Deployment: dfr-cli spawns N workers; docker-compose.yml multi-worker demo. Core pinning optional flag.
  • Rollback: worker count is config; safe to change between runs (no persisted partition map in P0; rescaling deferred §27).
  • Compatibility: exchange Pact + progress gossip format versioned; the transport trait is the seam for distributed (§23).

18. Phase 7 — Iteration / Feedback Edges + Progress in Cycles

18.1 Objectives

  • Nested loop scopes with Product<Outer,Inner> timestamps; the inner coordinate is the loop counter (§8.3, §6.12).
  • Feedback edges with a strictly-increasing path summary (+1 on inner coord, §7.10); enter/leave/loop_variable/connect_loop builder surface (§8.1 EBNF).
  • Progress tracking in cycles (the Naiad contribution): frontier advances and the loop terminates when the loop frontier empties (§7.10).
  • Notifications fully consumed here: per-iteration flush on loop-frontier advance.
  • Constraint introduced: every cycle must contain a feedback edge with a positive increment; builder rejects unbounded cycles (GraphError::UnboundedCycle, §8.10).

18.2 Detailed Implementation Steps

Theory anchors: P12 (Logical Time Is a Partial Order) — iteration adds the Product inner coordinate; I10 (loop timestamp strictly increases on feedback); in-cycle progress is the headline Naiad contribution (ADR-10; Naiad, SOSP 2013) and the Product-lattice model is shared with Differential Dataflow (CIDR 2013).

  • dfr-core/scope.rs: child loop scope; enter(stream) lifts T→Product<T,0>; leave(stream) projects back to outer once inner frontier empties.
  • dfr-operators/iterate.rs: loop_variable(summary) creates a feedback handle; connect_loop(stream,lvar) wires the back edge applying Timestamp::loop_increment (+1 inner).
  • dfr-core/summary.rs: cycle detection at build — a strongly-connected component must include a feedback summary that is strictly increasing on the inner coordinate; else GraphError::UnboundedCycle(ScopeId).
  • dfr-progress: reachability now handles cyclic summaries (composition followed_by until it stops decreasing/loops); frontier in a cycle is the antichain over Product times.
  • Termination: loop frontier empties when no Product{*,i} pointstamp can be produced; leave emits results and closes the outer time.
  • Iteration cap (optional loop(max)): a guard summary that refuses to increment past max (forces termination); loop.iteration.max.gauge.
  • Notifications: operator requests notification at time t; tracker fires when input frontier passes t (per iteration). Used by reduce/window to flush.
  • Buffer reserve in cycle channels to avoid deadlock (§7.7): a cycle's bounded channels need headroom for in-flight feedback batches.
  • Examples: connected_components.rs, reachability (iterative).

18.3 Deliverable

  • Iterative connected-components / reachability runs to a fixed point and terminates; each iteration's frontier advances; final result correct. Loop frontier introspectable per iteration.

18.4 Acceptance Criteria

  • Connected-components on a fixture graph converges to the correct labeling and terminates (loop frontier empties).
  • loop.frontier.advance.count strictly increasing per iteration; no livelock.
  • Build rejects a feedback edge lacking strict increment (GraphError::UnboundedCycle) — negative test.
  • No cyclic deadlock under bounded buffers with the configured reserve (liveness test, §7.7).

Fixture Purpose Expected

iteration/no_increment.json bad feedback UnboundedCycle at build
iteration/loop_max.json capped loop terminates at max; gauge = max

18.6 Pitfalls

  • Feedback without strict increment → loop frontier never advances → non-termination/livelock (§7.10). Detect: build-time SCC summary check; runtime loop-stall watchdog.
  • Cyclic deadlock: bounded channels in a cycle all full, no operator can drain → no progress (§7.7, §8.10). Detect: all-Blocked-in-cycle signature. Mitigate: per-cycle buffer reserve sized to max in-flight.
  • Reachability non-termination: composing cyclic summaries that never stop → infinite precompute. Bound composition (detect summary fixpoint); reject diverging summaries.
  • Notification fires per record not per iteration → over-flush. Tie notification to loop-frontier advance, not data arrival.
  • Product order misuse: treating inner coord as total/independent of outer → wrong frontier. Test partial-order semantics explicitly.
  • Inner frontier never projected to outer on leave → outer time stuck. Ensure leave closes outer when inner empties.

18.7 Performance Concerns

  • Cyclic progress = more propagate rounds (one per iteration boundary); keep ChangeBatch compaction tight (§16.7).
  • Iteration adds antichain elements (one per active iteration coord) → larger frontiers → O(k²) antichain ops; cap active iterations.
  • Feedback batches re-enter the scheduler → activation churn; batch feedback records.
  • Loop buffer reserve trades memory for deadlock-freedom; tune per cycle depth.

18.8 Edge Cases

  • Zero-iteration loop (predicate false immediately) → enter+leave with no feedback; terminates at iteration 0.
  • Infinite loop guarded only by max → terminates at max (gauge = max), result may be partial (documented).
  • Nested loops (loop within loop) → Product<Product<T,I1>,I2>; order is lexicographic-ish product; test 2-level nesting.
  • Single record looping forever (no increment bug) → caught by §7.6 watchdog.
  • Empty loop body → identity; passes through with +1 only on feedback.

18.9 Failure Analysis

  • Breaks: non-termination (no increment) → hung job consuming CPU; cyclic deadlock → hung job idle. Detection: loop-stall watchdog, all-Blocked-in-cycle, build-time SCC check. Blast radius: the loop scope (and anything downstream of leave). Containment: build rejection (pre-exec) or stall escalation → abort+restore. Recovery: fix summary / increase reserve; restore. Visibility: loop.iteration.max.gauge, loop.frontier.advance.count, per-iteration loop frontier. Postmortem: print loop frontier per iteration; confirm increment applied; inspect SCC summaries.

18.10 Operational Notes

  • Metrics: loop.iteration.max.gauge, loop.frontier.advance.count, per-iteration loop-frontier gauge, cyclic-channel depth.
  • Tooling: frontier_viz renders Product antichains (multi-coordinate) so operators can see iteration progress.
  • Deployment/rollback: library; loop max is a safety knob operators can set. Compatibility: loop scope + connect_loop are SDK API (§27). Cite Naiad SOSP 2013 for the in-cycle progress model.

19. Phase 8 — Windowing + Watermarks (Event-Time Streaming)

Reference: The Dataflow Model (VLDB 2015). Reconcile unbounded out-of-order event streams with finite, emittable results (§2.1).

19.1 Objectives

  • Event-time semantics: records carry event time; sources emit watermarks (event-time progress) that drive frontiers.
  • Window operators: tumbling, sliding, session; triggers on watermark passing window end; bounded lateness + side-output.
  • Watermark = a frontier in event time; window flush is notification-driven (Phase 7) at window close (§6.2 monotonicity → late data dropped/side-output, not retro-merged).
  • Constraint introduced: no late message past a closed frontier on internal edges (§7.4); beyond-watermark event-time records are explicit lateness, not faults.

19.2 Detailed Implementation Steps

Theory anchors: P2 (Progress Is Monotonic) — a watermark is a monotone event-time frontier; P6 (Capability-Based Timestamps) — sources downgrade caps to the watermark; I4 (no late message past a closed frontier). The window/trigger/lateness model is The Dataflow Model (Akidau et al., VLDB 2015); watermark semantics also draw on MillWheel (VLDB 2013).

  • dfr-operators/source.rs: event-time source assigns event_time per record; emits periodic watermarks; advances its capability to the watermark (closes earlier event times).
  • dfr-operators/window.rs: WindowSpec{kind:Tumbling|Sliding|Session, size, slide, gap}; assign records to window(s) keyed by (key, window); accumulate in KeyedState (§15); on watermark ≥ window-end, trigger → flush → drop window state.
  • Trigger taxonomy (from Akidau): event-time (default), early/late firings (config), accumulation mode (discarding/accumulating) — implement event-time + discarding first; others gated config.
  • Lateness: allowed_lateness; records with event_time < watermark − lateness → records.dropped_late.total or side-output stream (§7.4); never fold into closed window.
  • Idle-source watermark advance (§8.10): an idle input must still advance its watermark (e.g. via processing-time fallback) or downstream windows never close.
  • Session windows: merge on gap; state holds open sessions per key; merge logic on each record; flush on gap timeout (watermark).
  • Instrumentation: window.open.gauge, window.flush.total, records.dropped_late.total, frontier.lag (wall-clock − watermark, §4.3).

19.3 Deliverable

  • Windowed aggregation over an out-of-order event-time stream produces correct per-window results, flushed at window close; late records beyond lateness are side-output or counted. examples/windowed_agg.rs.

19.4 Acceptance Criteria

  • Tumbling/sliding/session windows match golden over an out-of-order fixture with controlled lateness.
  • Frontier lag < 2× max watermark interval under healthy load (§4.3).
  • Late record (beyond allowed lateness) is dropped/side-output, never merged into a closed window (§6.2); records.dropped_late.total matches expected.
  • Window state bounded by active windows × keys (§4.7); flushed windows free state (no leak).

19.6 Pitfalls

  • Idle source stalls watermark → windows never close (liveness). Detect: frontier.lag grows unbounded with one input idle. Fix: idle-detection → advance watermark (§8.10).
  • Late data merged into closed window → wrong results, monotonicity violation (§6.2). Enforce: window state dropped at flush; late → side-output.
  • Window state leak: session windows never flushed (gap never reached) → unbounded state (§6.4). Detect: window.open.gauge monotone. Fix: watermark-driven gap timeout.
  • Sliding window over-allocation: record in many overlapping windows → state blowup. Bound slide/size ratio; document cost.
  • Watermark too aggressive → drops valid late data (correctness/business cost); too conservative → high latency. Tune per stream; expose lag metric.
  • Per-window key explosion (high cardinality × many windows) → memory. Use window-key compound state; evict on flush.

19.7 Performance Concerns

  • Window assignment per record (esp. sliding) → hot loop; precompute window bounds; avoid per-record allocation.
  • Flush at window close iterates state for that window → O(keys in window); batch flush at notification.
  • Watermark propagation = frontier update per hop (§4.3); keep cheap (it is a ChangeBatch).
  • Session merge is the costliest (state mutation per record); index sessions per key for O(1) lookup.

19.8 Edge Cases

  • Record exactly at window boundary → assign per half-open convention [start,end); test boundary.
  • Empty window (no records) → no flush (or empty flush per config); no state.
  • All records late → all side-output; windows empty.
  • Watermark regress attempt (source bug) → rejected (§7.1 monotonicity); fail-fast.
  • Out-of-order within lateness → folded correctly before close.
  • Sliding with slide > size (gaps) or slide=size (tumbling degenerate) → handle uniformly.

19.9 Failure Analysis

  • Breaks: idle-source watermark stall → no output (liveness); late-merge → wrong windows (safety). Detection: frontier.lag gauge, monotonicity assert, window.open.gauge. Blast radius: windowed operator + downstream. Containment: lateness policy (drop/side-output); idle-watermark advance. Recovery: restore (Phase 9). Visibility: frontier lag, dropped-late counter, open-windows gauge. Postmortem: trace watermark per source; identify the lagging/idle input.

19.10 Operational Notes

  • Metrics: frontier.lag (primary streaming-health gauge), window.open.gauge, window.flush.total, records.dropped_late.total, watermark-per-source gauge.
  • Frontier lag is the #1 operational signal (§22, §26); alert on sustained lag > threshold (runbook frontier_stall.md).
  • Tuning: window size/slide/gap, allowed lateness, watermark interval — all config, not API.
  • Compatibility: WindowSpec + trigger config are SDK API (§27). Cite The Dataflow Model (VLDB 2015) + MillWheel (VLDB 2013) for watermark semantics.

20. Phase 9 — Fault Tolerance: Asynchronous Barrier Snapshots + Exactly-Once

Reference: Lightweight Asynchronous Snapshots (Flink ABS, 2015), derived from Chandy-Lamport (TOCS 1985). Exactly-once is about effects, not delivery (§6.7).

20.1 Objectives

  • Asynchronous barrier snapshotting: inject CheckpointBarrier{epoch} at sources; align barriers at operators; snapshot keyed state; complete when all sinks ack (§3.2 coordinator).
  • Consistent cut (§7.9) → restore from latest complete snapshot + replay source offsets → exactly-once effects on recovery (§7.6).
  • Crash-only recovery (§6.10): kill -9 a worker → supervisor restarts → restore.
  • Exactly-once sinks: idempotent or transactional (2-phase commit aligned to epoch); source offset replay.
  • Constraint introduced: all operator state already in KeyedState (§6.5) → snapshot is total; sinks must be idempotent/transactional.

20.2 Detailed Implementation Steps

Theory anchors: Flink ABS (Carbone et al., 2015) derived from Chandy-Lamport (TOCS 1985); P7 (Exactly-Once via Barriers, Not Retries), P5 (Operator Purity for Snapshotting), P10 (Crash-Only Semantics); I6 (exactly-once effects on recovery), I9 (snapshot consistency / consistent cut); ADR-30 (versioned framed snapshot format).

  • dfr-snapshot/barrier.rs: coordinator injects CheckpointBarrier{epoch,ts} at all sources periodically; barriers flow with data, interleaved on channel ordering (§8.6).
  • dfr-snapshot/align.rs: per-operator AlignState{Normal, Aligning{seen:BitSet,epoch}, Snapshotting{epoch}} (§8.9, §11.7). On barrier on input i: mark seen; when all inputs seen (alignment) → snapshot state → forward barrier → ack. Aligned mode: pre-barrier in-flight is upstream's snapshot, not folded post-barrier (§7.9).
  • dfr-snapshot/coordinator.rs: Coordinator{in_flight:HashMap<Epoch,AckSet>, last_complete}; trigger()/ack(op,epoch)/complete(epoch); epoch durable when all sinks ack.
  • dfr-snapshot/store.rs: snapshot store on local disk; framed magic+version+CRC (ADR-30); SnapshotMeta{epoch,source_offsets,ops,crc,version}.
  • dfr-snapshot/recover.rs: on restart, restore each operator's KeyedState from latest complete epoch; reset sources to recorded offsets; rebuild progress tracker from restored caps (§11.3).
  • Exactly-once sinks: IdempotentSink (dedup by deterministic key) and TransactionalSink (pre-commit on snapshot, commit on epoch-complete, abort on recovery of uncommitted) — 2PC aligned to checkpoint (§6.7).
  • Source offsets: sources record consumed offset per epoch in SnapshotMeta; replay from there on restore (deterministic replay, §6.3).
  • Instrumentation: checkpoint.complete.total, checkpoint.alignment.ms, checkpoint.state.bytes, recovery.total, sink.duplicate.detected.total(0), checkpoint.inconsistent.total(0).

20.3 Deliverable

  • A running dataflow checkpoints periodically; injecting a crash (kill -9) and restarting restores state + replays offsets; sink output equals a non-failing run (no dup, no loss). examples/exactly_once_sink.rs.

20.4 Acceptance Criteria

  • Crash-restore conformance: inject crash at random points; sink output multiset == golden non-failing run (exactly-once effects, §7.6).
  • Checkpoint overhead < 5% steady-state throughput degradation (§4.5); barrier alignment p95 < 50 ms (no skew, §4.5).
  • RTO < 30 s for ≤ 10 GB state (P0 local disk, §4.5).
  • Snapshot consistency: independent replay-recompute matches snapshot checksum (checkpoint.inconsistent.total==0, §7.9).

20.5 Conformance Fixtures

Fixture Purpose Expected

snapshot/consistent_cut.json replay checksum checksum matches recompute

20.6 Pitfalls

  • Barrier never aligns: one idle input → operator waits forever (§8.10). Detect: checkpoint.alignment.ms watchdog → CheckpointError::AlignTimeout → abort epoch, retry. Fix: idle-source watermark/barrier.
  • Hidden state not snapshotted (operator purity violated, §6.5) → restore diverges → exactly-once lost. Detect: replay-checksum mismatch. Enforce: all state in KeyedState.
  • Non-idempotent sink under recovery → double side-effect. Use idempotent/transactional sinks; sink.duplicate.detected.total must be 0.
  • Post-barrier data folded pre-barrier (alignment bug) → inconsistent cut, double/lost counts (§7.9). Enforce aligned-mode buffering.
  • Snapshot corruption (partial write, bit rot) → CorruptSnapshot on restore. CRC + versioned frame (ADR-30); fall back to prior complete epoch.
  • Checkpoint interval too tight → overhead > 5%; too loose → large RTO. Tune; expose overhead metric.

20.7 Performance Concerns

  • Snapshot is O(state bytes); large state → long alignment-blocked write. Asynchronous snapshot (copy-on-write or background flush) keeps overhead < 5% (§4.5); incremental/persistent backend deferred.
  • Alignment blocks the fastest inputs to wait for the slowest → skew inflates alignment time (§4.5). Skew metric flags it.
  • Disk write bandwidth bounds checkpoint duration → RTO; local NVMe assumed (§4).
  • 2PC sink adds commit latency at epoch boundary; amortized over checkpoint interval.

20.8 Edge Cases

  • Crash during snapshot write → incomplete epoch discarded (not marked complete); prior epoch used (crash-only, §6.10).
  • Crash during alignment → restart from prior complete epoch; in-flight barriers re-injected.
  • Two overlapping epochs in flight → coordinator tracks per-epoch AckSet; aligned barriers keep them separate.
  • Source cannot replay (offset gone) → unrecoverable for that source; alert; bounded by source durability (out of P0 for non-replayable sources).
  • Empty state snapshot → valid; meta records zero bytes.
  • Clock skew on barrier ts → cosmetic only; epoch is logical, not wall-clock-ordered.

20.9 Failure Analysis

  • Breaks: inconsistent cut → silent exactly-once violation (worst); align timeout → checkpoint never completes (no recovery point); corrupt snapshot → restore fails. Detection: consistency checksum, alignment watchdog, CRC. Blast radius: fault-tolerance guarantee (correctness on recovery) for the whole job. Containment: reject inconsistent/corrupt snapshots; retain prior; abort+retry on timeout. Recovery: restore from last complete epoch + offset replay. Visibility: checkpoint complete/duration/alignment/inconsistent metrics, recovery counter. Postmortem: per-operator alignment log; sink 2PC pre-commit/commit log vs epoch (runbook checkpoint_failure.md, recovery.md).

20.10 Operational Notes

  • Metrics: checkpoint.complete.total, checkpoint.alignment.ms, checkpoint.state.bytes, recovery.total, sink.duplicate.detected.total(0), checkpoint.inconsistent.total(0).
  • Runbooks: checkpoint_failure.md (align timeout, corruption), recovery.md (restore procedure). Backup = snapshot store; restore-testing in CI (§28 chaos).
  • Deployment: supervisor restarts crashed workers; checkpoint interval config. Rollback: restore from a prior epoch. Compatibility: snapshot format versioned; restore tolerates older versions per §27; not Flink-savepoint compatible (§5.4). Cite Flink ABS + Chandy-Lamport; cross-link 376.

21. Phase 10 — Operator Fusion + Scheduler Optimization

21.1 Objectives

  • Operator fusion: inline chains of stateless operators (map→filter→map) into one monomorphized loop → eliminate per-record dispatch + channel overhead (§4.1 fused ≥ 20M/s vs unfused ≥ 5M/s).
  • Scheduler optimization: group scheduling (Drizzle, SOSP 2017) to cut activation/coordination overhead; activation aging for fairness.
  • Constraint introduced: fusion must preserve semantics, frontier/progress behavior, and snapshot boundaries (fused group is one operator for state purposes).

21.2 Detailed Implementation Steps

Theory anchors: P11 (Move, Don't Copy) and ADR-01 zero-cost monomorphization make fusion free of dispatch; P6/I3 (capability discipline) define which boundaries must stay discrete; group scheduling is Drizzle (Venkataraman et al., SOSP 2017). Fusion preserves I1 (progress monotonicity) — frontier behavior must be identical fused vs unfused.

  • dfr-scheduler / dfr-operators: fusion pass over RuntimeGraph — detect maximal chains of pipeline (non-exchange, stateless, single-in/single-out) operators; replace with a fused operator whose schedule runs the composed closure over a batch without intermediate channels.
  • Preserve a fusion boundary at: exchange edges, stateful operators, loop scope edges, sink/probe — these stay discrete (progress + snapshot need them).
  • Monomorphization: fused closures compile to a tight loop (zero-cost, §1.10); avoid Box<dyn> within a fused group.
  • dfr-scheduler/activate.rs: group scheduling — schedule a fused group / co-scheduled set in one activation; aging counter prevents starvation (§7.7).
  • Progress: a fused group reports produced/consumed at its boundaries only (internal times pass through); reachability summaries composed across the fused chain at build.
  • Instrumentation: operator.fused.count, operator.dispatch.elided.total, before/after throughput in bench.

21.3 Deliverable

  • A stateless chain runs fused: ≥ 20M records/s/core vs ≥ 5M unfused (§4.1); output identical to unfused; progress/frontier behavior unchanged.

21.4 Acceptance Criteria

  • Fused stateless map/filter chain ≥ 20M records/s/core (§4.1); per-record dispatch elided (counter).
  • Output byte-identical fused vs unfused for all fixtures (semantics preserved).
  • Frontier/progress and snapshot results identical fused vs unfused (boundaries preserved).
  • No starvation under group scheduling (activation aging test, §7.7).

21.5 Conformance Fixtures

Fixture Purpose Expected
fusion_chain.json map→filter→map fused output == unfused; ≥20M/s
fusion_boundary.json chain with exchange in middle fusion stops at exchange
fusion_stateful.json stateful in chain not fused across stateful op
fusion_snapshot.json snapshot of fused group restore identical to unfused
sched_aging.json uneven cost groups no starvation

21.6 Pitfalls

  • Fusing across an exchange or stateful op → breaks partitioning/snapshot boundary → wrong results. Enforce fusion-boundary rules; assert no fusion crosses them.
  • Fusion changes frontier reporting → progress bug. Compose summaries correctly; conformance compares frontier traces fused vs unfused.
  • Over-fusion hurts latency (a long fused chain delays partial output / backpressure granularity). Cap fused chain length; keep backpressure observable at boundaries.
  • Monomorphization code bloat / compile-time blowup (deep generics, the Timely pitfall, §5.3). Bound generic depth; measure compile time.
  • Group scheduling starves a co-scheduled member → fairness loss. Aging counter; per-operator activation parity check.

21.7 Performance Concerns

  • Fusion's win is eliminating channel push/pull + dispatch per record; measure with criterion before/after.
  • Cache locality improves (data stays in registers/L1 across fused ops). Watch instruction-cache pressure from huge fused loops.
  • Group scheduling cuts activation-queue churn; measure operator.activation.count reduction.
  • Tail latency: fused chains reduce per-hop variance but a long chain raises per-activation cost — balance.

21.8 Edge Cases

  • Single-operator "chain" → no fusion, no regression.
  • Chain entirely stateless but ending in a sink → fuse up to sink boundary.
  • Fused chain with a filter rejecting all → empty output propagated; downstream sees close.
  • Branch (fan-out) in the middle → fusion stops at the branch (single-out requirement).
  • Loop scope edge inside a chain → fusion stops at scope boundary.

21.9 Failure Analysis

  • Breaks: fusion across a boundary → wrong results or broken snapshot; starvation under group scheduling. Detection: fused-vs-unfused conformance diff; activation-parity check. Blast radius: correctness of fused operators / fairness. Containment: fusion-boundary asserts; conformance gate in CI. Recovery: disable fusion (config flag) → fall back to unfused (always-correct baseline). Visibility: operator.fused.count, dispatch-elided counter, per-op activation counts. Postmortem: compare frontier/output traces; bisect fusion groups.

21.10 Operational Notes

  • Metrics: operator.fused.count, operator.dispatch.elided.total, throughput before/after, activation counts.
  • Fusion is an optimization with a correct fallback: a config flag disables it (unfused is the reference, §6.3 determinism). Use the flag to bisect fusion bugs.
  • Deployment/rollback: fusion flag per job. Compatibility: fusion is internal; does not change SDK API or wire/snapshot format. Cite Drizzle (SOSP 2017) for group scheduling.

22. Phase 11 — Observability (Throughput, Queue Depth, Frontier Lag, Skew)

Observability by default (§6.8): a new operator is observable the moment it is added. Operators' only window into a running dataflow (§3.2).

22.1 Objectives

  • Per-operator, per-worker metrics surface: throughput, queue depth, frontier lag, skew, activation counts, checkpoint duration/alignment/state size (§3.2).

22.6 Pitfalls

  • Metric cardinality explosion (per-key labels) → memory + scrape cost. Aggregate per-operator/worker, never per-key labels; sample latency.
  • Hot-path contention on a shared counter → false sharing / throughput hit. Per-worker counters, CachePadded, aggregate at scrape.
  • Frontier-lag computed wrong (processing vs event time confusion) → misleading dashboard. Define lag = wall − event-time frontier explicitly.
  • Tracing every schedule → overhead blows the 2% budget. Sample spans (e.g. 1%); always-on counters, sampled spans.
  • Skew gauge misattributes (counts records not work) → misleading. Define skew on the bottleneck dimension (records or bytes), documented.

22.7 Performance Concerns

  • Atomic increment per record is the hot-path cost; relaxed ordering for counters (eventual scrape accuracy is fine). Batch-increment per schedule (add N once), not per record.
  • Histogram update cost → use HDR-style bucketed histogram with cheap bucket index.
  • Scrape is pull-based off the hot path; serialization cost amortized at scrape interval.
  • Frontier-lag/skew computed at progress-round granularity, not per record.

22.8 Edge Cases

  • No traffic → throughput 0, frontier lag = wall − last watermark (grows if idle; expected).
  • Single worker → skew gauge = 1 (degenerate); no false alert.
  • Very high throughput → counter wrap (use u64; wrap is millennia at realistic rates).
  • Scrape during checkpoint → metrics consistent (atomic reads); alignment-ms reflects in-progress epoch.
  • Operator added at build → metrics auto-registered (no per-op wiring, §6.8).

22.9 Failure Analysis

  • Breaks: missing/incorrect metric → blind operators → MTTR explodes (§6.8 violation). Detection: metrics-smoke conformance ensures presence; overhead bench ensures cost. Blast radius: operability, not correctness (data path unaffected). Containment: metrics are read-only side-channel; a metrics bug never corrupts data. Recovery: fix exporter/registry; no data impact. Visibility: the meta-question — self-monitoring (exporter up gauge). Postmortem: the dashboards are the postmortem substrate; ensure historical retention.

22.10 Operational Notes

  • Metrics: the full set — throughput, channel.queue.depth, frontier.lag, skew, operator.activation.count, checkpoint duration/alignment/bytes, state size, all §7 counters.
  • Dashboards: per-operator throughput + queue depth; frontier lag timeline; skew heatmap; checkpoint duration/overhead. Alerts: sustained frontier lag, sustained max queue depth, skew threshold, *.regression/negative/illegal/inconsistent > 0 (correctness-fault page, §26).
  • Deployment: Prometheus scrape + Grafana; DOT for topology. Rollback/compat: observability is additive, never API/wire-breaking.

23. Phase 12 — Distributed Multi-Process Workers (PhaseDeferred)

PhaseDeferred("FINAL_BLUEPRINT §23"). Deferred; specified for completeness. The shared-nothing symmetric-worker design (§6.13) makes this a transport + bootstrap problem, not a protocol change: the identical progress + exchange protocols run over the network.

23.1 Objectives

  • Extend workers across multiple processes/hosts: network exchange transport + cross-host progress gossip aggregation.
  • Cluster bootstrap (worker discovery, group membership), failure detection, and rescaling via stop-restore-from-snapshot.
  • Constraint: reuse §17 protocols verbatim over a network transport (the dfr-channels transport trait seam, §6.2); add no new progress semantics.

23.2 Detailed Implementation Steps

Theory anchors: P13 (Symmetric Workers, Shared-Nothing) is what makes distribution a transport problem, not a protocol change — the Naiad gossip (ADR-10) runs verbatim over the network; ADR-13 (TCP framing), ADR-12 (serialization at the now-real boundary); I5 (per-channel FIFO) must survive the network.

  • Network transport behind the dfr-channels transport trait: TCP + length-prefixed frames (ADR-13); bincode/abomonation serialization (ADR-12) at the now-real network boundary.
  • Cross-host progress: dfr-progress/broadcast.rs gossips ProgressUpdate batches over the network; aggregate remote frontiers identically to intra-process (§6.2).
  • Cluster membership/bootstrap: static config first, then a discovery mechanism; WorkerId global across hosts; all-to-all (or topology-aware) exchange wiring.
  • Failure detection: heartbeats; a dead worker → job-level restart from last complete snapshot (§20) — no partial-worker recovery in first cut.
  • Rescaling: stop → snapshot → restart with new worker count → restore with re-partitioned state (requires the deferred state-rescale, §27).
  • Persistent/remote state backend (RocksDB-style, remote snapshot store) — also deferred here (§37).

23.3 Deliverable

  • (Deferred) Word-count + windowed-agg run across ≥ 2 hosts with network exchange; exactly-once preserved across host crash; throughput scales across hosts to network-bandwidth limits.

23.4 Acceptance Criteria

  • (Deferred) Output identical to single-host for the same input (determinism across distribution).
  • Cross-host exactly-once: host crash + restart restores; sink output == golden.
  • Aggregate throughput scales across hosts until network bandwidth / exchange fanout saturates (§31).
  • Progress gossip bandwidth bounded (batched); no per-record network progress (§8.10).

23.6 Pitfalls

  • Network reorder/partial frame → channel FIFO/decode break (§7.5). Length-prefixed framing + sequence; reject malformed (fuzz message_decode).
  • Progress gossip flood over WAN → bandwidth blowup. Batch + compact ChangeBatch; coalesce per round.
  • Partition/network partition (split-brain) → divergent progress. Job-level restart from snapshot; no independent-progress during partition (consistency over availability for correctness).
  • Serialization cost now real (was free in-process) → throughput drop at exchange. Zero-copy/abomonation; batch.
  • Clock skew across hosts → irrelevant for event time (watermarks), but heartbeat timeouts need tolerance.
  • Rescale state mismatch → keys land on wrong host. Requires deferred consistent state-rescale (§27); reject mismatched partition counts otherwise (§4.8 / §7.11).

23.7 Performance Concerns

  • Network exchange dominated by serialization + RTT (§4.2 +1 exchange hop budgets assume in-process; network adds RTT). Batch aggressively; pipeline.
  • Cross-host progress round latency bounded by network RTT (§4.3 < 10 ms heavy fan-in → revisit for WAN).
  • All-to-all O(N²) connections across hosts → connection-table + fanout limits (§31).
  • Backpressure now spans the network (credit over TCP) → larger feedback latency; size network credits for bandwidth-delay product.

23.8 Edge Cases

  • Single host (degenerate) → identical to Phase 6 (in-process).
  • Slow/lossy link → TCP handles loss; backpressure throttles; frontier lag rises (observable).
  • Host join/leave mid-run → not supported in first cut; stop-restore.
  • Asymmetric host capacity → skew across hosts; rekey/scale (§22).
  • Network partition healed → restart from snapshot, not merge.

23.9 Failure Analysis

  • Breaks: split-brain progress → divergent/wrong frontiers; network corruption → decode faults; gossip flood → bandwidth collapse. Detection: decode CRC/framing, gossip-bytes gauge, heartbeat failure detector. Blast radius: the distributed job. Containment: job-level restart from snapshot on host failure/partition; reject malformed frames. Recovery: restore from last complete epoch (§20) cluster-wide. Visibility: per-host frontier/throughput, gossip bandwidth, link health. Postmortem: per-host progress trace; identify diverged/lagging host.

23.10 Operational Notes

  • (Deferred) Metrics add per-host/per-link: network throughput, gossip bandwidth, RTT, heartbeat health. Deployment: multi-host topology (docker-compose → real orchestration deferred). Rollback: worker/host count is config; rescale via stop-restore. Compatibility: network framing + gossip format versioned (§23, §27); reuses §17 protocols unchanged. 25. Failure Modes & Recovery

Taxonomy by class. Each: symptoms → root causes → detection → automatic recovery → manual recovery → operator actions → forensic artifacts → long-term mitigation.

Class A — Correctness Faults (trusted-code invariant violation)

  • Members: progress regression (§7.1), negative count (§7.2), illegal emit (§7.3), foreign-key access (§7.11), channel reorder (§7.5), inconsistent snapshot (§7.9).
  • Symptoms: fatal metric > 0; debug panic; subtly wrong results before detection.
  • Root causes: progress-tracker bug, channel memory-order bug, fusion-boundary bug, partition-fn mismatch.
  • Detection: invariant asserts (debug panic / release fatal metric + abort, §6.14).
  • Automatic recovery: controlled abort → supervisor restart → restore from last complete snapshot (§20).
  • Manual recovery: deterministic replay (§28) to reproduce; fix; re-deploy.
  • Operator actions: page (correctness-fault alert class, §26); capture forensic dump before restart.
  • Forensic artifacts: pointstamp delta log, active-pointstamp table, capability dump, per-operator alignment log.
  • Long-term mitigation: property tests (§5.4), differential fused-vs-unfused, loom/Miri on channels.

Class B — Liveness Faults (stall / deadlock / starvation)

  • Members: frontier stall (§7.7), cyclic deadlock (§7.7, §8.10), watermark stall on idle source (§8.10), starvation (unfair scheduling).
  • Symptoms: throughput→0 while inputs buffered; frontier lag grows unbounded; scheduler.park.total rises with records.out flat.
  • Root causes: capability held too long, bounded-cycle exhaustion, idle source not advancing watermark, scheduling unfairness.
  • Detection: stall watchdog (now − last_frontier_advance > threshold with non-empty queues); all-Blocked-in-cycle signature; activation-parity check.
  • Automatic recovery: none for true deadlock (abort+restore); idle-source watermark auto-advance recovers watermark stall.
  • Manual recovery: dump runnable set + credits + frontiers; increase cycle buffer reserve; tune fairness.
  • Operator actions: runbook frontier_stall.md / backpressure_deadlock.md.
  • Forensic artifacts: runnable-set snapshot, per-channel credits/depth, per-location frontier, caps ≤ stuck time.
  • Long-term mitigation: cycle reserve sizing, idle-source detection, aging scheduler.

Class C — Resource Faults (memory / CPU / FD)

  • Members: state/window leak (§6.4), progress storm (§8.10), buffer-pool exhaustion, FD exhaustion (channels/sockets §23).
  • Symptoms: memory monotone rising, CPU pegged on progress, OOM-kill risk.
  • Root causes: unbounded keys (no window/eviction), per-record progress, over-fusion, leak.
  • Detection: state.bytes/state.keys monotone gauges, progress.broadcast.bytes high, memory ceiling crossings.
  • Automatic recovery: memory ceiling → backpressure (spill deferred); progress batching caps CPU.
  • Manual recovery: add windowing/eviction; tune batch; reduce fusion length.
  • Operator actions: runbook key_skew.md (if skew-driven), capacity review.
  • Forensic artifacts: top-N keys by state size, per-operator memory, progress-msg rate.
  • Long-term mitigation: windowing discipline, spill backend (deferred), state TTL.

Class D — Checkpoint / Recovery Faults

  • Members: align timeout (§20.6), snapshot corruption, source non-replayable, recovery failure.
  • Symptoms: no new complete checkpoint; restore fails; RTO exceeded.
  • Root causes: idle input, partial write, lost offsets, store IO error.
  • Detection: checkpoint.alignment.ms watchdog → AlignTimeout; CRC → CorruptSnapshot; restore checksum.
  • Automatic recovery: abort+retry epoch; fall back to prior complete epoch; reject corrupt.
  • Manual recovery: runbook checkpoint_failure.md / recovery.md; restore a specific epoch.
  • Operator actions: verify store health, source durability.
  • Forensic artifacts: epoch ack log, alignment log, snapshot meta + CRC, 2PC sink log.
  • Long-term mitigation: idle-source barrier, incremental/persistent backend (deferred), restore drills in CI.

Class E — Input / Data Faults (untrusted)

  • Members: malformed source records, late event-time data, decode errors.
  • Symptoms: decode-error counter rises; dropped-late counter rises.
  • Root causes: bad upstream data, out-of-order beyond lateness, schema drift at source.
  • Detection: source.decode.error.total, records.dropped_late.total.
  • Automatic recovery: drop/side-output per policy (not a fault, §7.4); never crash.
  • Manual recovery: adjust lateness/schema; inspect side-output.
  • Operator actions: review side-output stream; alert if drop rate high (business policy).
  • Forensic artifacts: side-output records, decode-error samples.
  • Long-term mitigation: schema validation at source, dead-letter side-output.

26. Operational Readiness

  • Metrics strategy. Atomic per-(operator,worker) counters/gauges/histograms (§22); Prometheus pull (ADR-15). Golden signals: throughput, queue depth, frontier lag, skew, checkpoint duration/overhead, correctness-fault counters.
  • Tracing strategy. tracing spans on schedule (sampled 1%) + checkpoint epochs (always); span fields = op, batch, duration, out count. Off-CPU via perf (§30).
  • Structured logging. JSON logs; correctness faults log full forensic context (delta log handle, caps, frontiers) before abort.
  • Dashboard design. Per-operator throughput + queue-depth panels; frontier-lag timeline; skew heatmap (worker × key-group); checkpoint duration/alignment/overhead; correctness-fault counters (must be 0).
  • Alerting philosophy. Page on: any correctness-fault counter > 0 (Class A), sustained frontier stall (Class B), sustained max queue depth, checkpoint failure (Class D), memory-ceiling crossings (Class C). Ticket (not page) on: skew threshold, elevated late-drop rate (Class E).
  • SLO definitions. Availability (job uptime), freshness (frontier lag < target, §4.3), exactly-once (zero dup/loss), RTO < 30 s (§4.5). Error budget = freshness-violation minutes.
  • Incident response. Runbooks: frontier_stall.md, backpressure_deadlock.md, checkpoint_failure.md, key_skew.md, recovery.md. Each: signature → dump commands → likely cause → remediation.
  • Backup strategy. Snapshot store is the backup; retain last N complete epochs; restore-test in CI (§28 chaos).
  • Restore testing. Periodic crash-restore drill (chaos) validates RTO + exactly-once; non-prod restore from prod snapshot.
  • Deployment topology. Single host, N worker threads (P0); supervisor restarts crashed workers. Multi-host deferred (§23).
  • Canary / rolling / rollback. Canary a new operator/config on a sample; rolling upgrade = stop-restore-from-snapshot (static topology, §6.9); rollback = restore prior epoch + prior binary.
  • Migration strategy. State schema migration via versioned snapshot format (§27); topology changes require stop-restore (rescaling deferred).
  • Compatibility strategy. See §27 — wire/snapshot/API versioning.

27. Compatibility & Versioning

  • Wire compatibility (intra-process P0 / network deferred §23). Message framing, ProgressUpdate gossip, exchange Pact encoding are versioned (magic+version). In-process P0 uses moves (no serialize); the versioned wire format matters when network transport lands (§23). Same-minor versions interoperate; major bumps are breaking.
  • Storage / snapshot compatibility. Snapshot framed magic+version+CRC (ADR-30); SnapshotMeta.version. Restore tolerates older snapshot versions within the same major (forward-compatible reads); newer snapshots are not readable by older binaries (no backward). State schema evolution: additive fields with defaults; renames require a migration shim keyed by stable state name (§4.2).
  • Schema evolution (operator state). Named state (StateBackend::keyed(name)) is the stable identity; adding state is compatible; removing/renaming requires migration. Value types evolve via the versioned snapshot codec.
  • API stability. Operator trait, Stream combinators, Worker::execute/step, Capability, Frontier, window/loop combinators are the SDK surface. Semver: breaking changes only on major; deprecate with one-minor overlap.
  • Migration guarantees. A snapshot taken by version X restores on X and X+minor; cross-major requires an offline migration tool. Topology/parallelism changes require stop-restore (rescaling deferred §27).
  • Deprecation policy. Mark deprecated APIs one minor before removal; document in CHANGELOG.md; provide replacement.
  • Semantic versioning. MAJOR.MINOR.PATCH: MAJOR = wire/snapshot/API break; MINOR = additive; PATCH = fixes. Cargo.lock pinned (ADR-28).
  • Rolling-upgrade guarantees. P0: no live rolling upgrade across versions (static topology + in-memory state); upgrade = drain/snapshot → deploy → restore. Live rolling upgrade is a deferred capability tied to §23.

31. Scalability Analysis

  • Bottlenecks. (1) Progress tracking under wide fan-in / many active pointstamps — O(active pointstamps), batched (§16.7). (2) Exchange fanout O(N²) channels at high N. (3) Key skew → one hot worker (§6.6). (4) Memory bandwidth on stateless throughput. (5) Checkpoint alignment under skew (§20.7).
  • Scaling ceilings. Single host: workers ≤ #physical cores (typ. ≤ 64, §4.6); aggregate throughput bounded by memory bandwidth (stateless) or exchange fanout (shuffle-heavy). Beyond that → multi-host (§23).
  • Horizontal scaling. Add workers (P0) / hosts (§23 deferred); shared-nothing symmetric design (§6.13) → near-linear until exchange/progress overhead dominates (~0.7×N at 8 cores, §6.4).
  • Vertical scaling. More cores per host → more workers; NUMA-pin to keep state local (§4.8); memory bandwidth is the wall.
  • Sharding / partitioning. Data partitioned by key hash via exchange Pact; state co-partitioned (§7.11). Partition count = worker count (P0); rescaling deferred (§27).
  • Replication pressure. No data replication in P0 (fault tolerance via snapshot, not replicas); snapshot store IO bandwidth bounds checkpoint frequency.
  • Coordination overhead. Progress gossip = O(active pointstamps × workers); batched/compacted (ChangeBatch). Group scheduling (Drizzle, §21) cuts per-batch coordination.
  • Network fanout (deferred §23). All-to-all O(N²) connections + serialization cost; topology-aware exchange + batching needed at scale.
  • Scheduler saturation. Activation-queue churn at high operator count; fusion (§21) reduces operator count on the hot path; aging keeps fairness O(1).
  • Storage growth. Snapshot store grows with state size × retained epochs; prune old epochs; incremental checkpoints deferred.
  • Metadata scaling. Reachability table O(V·E) at build (§1.6); progress count table O(active pointstamps); both bounded and batched.

32. Mental Models & First Principles

The compressed intuitions a principal engineer holds about this system. Each: the insight, what it predicts, the bug you write without it, and where this blueprint applies it.

MM1 — A frontier is a promise about input completeness, not a clock

  • Insight. A frontier (watermark) at location l does not say "the time is now T"; it says "no input with time < T will ever again arrive at l." It is a lower bound on future arrivals, derived from upstream capabilities + path summaries — not a wall-clock reading.
  • Predicts. Late data is normal and expected; the watermark is a tunable guess about how late data can be. A "perfect" watermark is impossible without bounding source lateness.
  • Bug without it. You treat the watermark as the current time, flush windows on processing-time, and silently drop valid out-of-order data — or you assume frontiers can move backward to "fix" things and corrupt closed results.
  • Applied. Progress tracking (§16), windowing/watermarks (§19), invariant I1 (§7.1), principle P2.

MM2 — Backpressure is a promise about memory, transmitted backward as credit

  • Insight. Credit is downstream telling upstream "I have N buffer slots free." Flow control is the inverse of dataflow: data flows forward, permission flows backward. A bounded system is one where every producer waits for a consumer's promise before emitting.
  • Predicts. The slowest operator sets the rate of the whole pipeline (it is the one not granting credit). Queue depth pinned at capacity = you found the bottleneck. Unbounded buffers convert a slow consumer into an OOM.
  • Bug without it. You buffer "just in case," load skew fills the buffer, and a single slow sink exhausts host memory (Class C, §25).
  • Applied. Channels/backpressure (§14), invariant I8 (§7.8), principles P1/P4; contrast with Reactive Streams demand (§5.4).

MM3 — A capability is a reference count on a logical time

  • Insight. Holding a Capability<t> keeps the pointstamp count for t at ≥ 1, which keeps the frontier from advancing past t. Dropping it is a destructor that decrements that count. Capabilities are RAII over logical time, exactly as Arc is RAII over memory.
  • Predicts. A stuck frontier is a leaked capability (someone holds a time they should have dropped); a premature flush is a capability dropped too early (use-after-free of a logical time).
  • Bug without it. You emit at a time after dropping its capability → emit at a closed time → safety violation (I3, §7.3); or you never drop → liveness stall (§7.7).
  • Applied. Capability model (§8.5), progress (§16), principle P6, invariants I3/I4.

MM4 — Logical time is a lattice, and a scalar timestamp is the degenerate case

  • Insight. Timestamps form a partial order with joins/meets. A flat event-time u64 is the totally-ordered special case; iteration adds a coordinate (Product<T, loop>) making times genuinely incomparable. A frontier is therefore an antichain, not a number.
  • Predicts. Anything that needs cycles or multi-dimensional incremental updates cannot use a scalar watermark — it needs the product order. Forcing a total order breaks iteration termination.
  • Bug without it. You model time as u64, then iteration livelocks because you cannot express "round i of outer time t" as a distinct, ordered point.
  • Applied. Timestamps (§8.3), antichains (§8.4), iteration (§18), principle P12, ADR-08/ADR-09.

MM5 — "Exactly-once" is about effects, not delivery

  • Insight. No system delivers each record exactly once over a lossy channel. Exactly-once means the externally observable effect equals a non-failing run: achieved by a consistent-cut snapshot + deterministic replay + idempotent/transactional sinks. Records may be reprocessed; effects are not double-applied.
  • Predicts. You cannot get exactly-once with a non-idempotent, non-transactional sink, no matter how good the runtime is. Dedup tables are a different (unbounded-state) design (MillWheel).
  • Bug without it. You implement at-least-once + a dedup set, the dedup set grows without bound, and non-idempotent sinks still double-emit on recovery.
  • Applied. Snapshots/exactly-once (§20), principle P7, invariant I6; contrast MillWheel record-IDs (§5.2).

MM6 — Alignment is the price of a consistent cut

  • Insight. A barrier on one input is meaningless; a consistent global state requires waiting for the barrier on all inputs (alignment) so that pre-barrier and post-barrier records are cleanly separated. Alignment time is bounded by the slowest input — so skew directly inflates checkpoint latency.
  • Predicts. An idle input stalls alignment forever unless it advances a watermark/barrier; checkpoint p95 tracks input skew, not average load.
  • Bug without it. You snapshot on the first barrier, fold post-barrier data into pre-barrier state → inconsistent cut → double/lost counts on restore (I9, §7.9).
  • Applied. Snapshots (§20), invariant I9, state-machine §8.9; the Chandy-Lamport marker rule (§5.4).

MM7 — On a no-GC runtime, tail latency is scheduling + contention, never the collector

  • Insight. With Rust + buffer pools, the hot path is allocation-free, so p99 is dominated by activation-queue latency, channel CAS contention, and cache misses — not stop-the-world pauses. This is the whole reason to reject the JVM here (ADR-01).
  • Predicts. A p99 spike correlates with a hot channel (false sharing, credit thrash) or an unfair scheduler, and is found with perf c2c / off-CPU profiling — not with GC logs.
  • Bug without it. You chase phantom "GC-like" pauses, add more buffering (making it worse), instead of fixing false sharing with CachePadded (ADR-07).
  • Applied. Constraints §4.2, Performance Engineering (§30), principle P11; USE method (§5.1).

MM8 — Progress must be tracked per frontier, not per record

  • Insight. If every record emitted a progress message, progress traffic would equal data traffic (O(records)) and melt the system. The pointstamp protocol aggregates produced/consumed deltas into ChangeBatches per pointstamp, so progress cost is O(active pointstamps) — independent of record volume.
  • Predicts. The cost of progress tracking scales with graph activity (open times × locations × workers), not throughput; a fan-in storm is a progress-traffic problem, fixed by batching, not by faster data paths.
  • Bug without it. You report progress per record, and a wide fan-in produces an O(records) gossip storm that pegs CPU (§8.10, Class C).
  • Applied. Progress (§16), broadcast batching (§17), constraint §4.6, threat "Resource exhaustion (CPU)" (§24).

MM9 — Determinism is a debugging tool, bought with scheduling discipline

  • Insight. If the same input + offsets + graph always produces the same output (modulo declared wall-clock triggers), then every bug is reproducible by replay and every snapshot is verifiable by recompute. Determinism is purchased by stable per-key order and a controlled logical-time scheduler.
  • Predicts. Any divergence between two replays, between fused and unfused, or between worker counts, is a bug — this gives you a free differential oracle.
  • Bug without it. Non-deterministic operator order makes snapshots differ across replays; you cannot validate exactly-once or reproduce a heisenbug.
  • Applied. Principle P3, deterministic sim (ADR-19), testing strategy (§28), fused-vs-unfused differential (§28).

MM10 — Shared-nothing symmetry makes distribution a transport problem

  • Insight. Because every worker runs the same graph and they communicate only via channels + progress gossip, the in-process and cross-host cases run the identical protocol; only the channel implementation changes (in-memory vs TCP). The hard distributed algorithm (progress) is already solved at N=1-in-process.
  • Predicts. Going multi-host adds serialization, RTT, and failure detection — but no new progress semantics. If your single-process design needs a shared mutable graph, you have already blocked distribution.
  • Bug without it. You bolt shared state across workers, reintroduce locks/races, and the §23 distributed step requires a protocol rewrite instead of a transport swap.
  • Applied. Principle P13, worker model (§3.2, §11.8), distributed phase (§23), Alternative Architectures (§36).

Naiad / Timely Dataflow. The intellectual parent — the pointstamp protocol, capabilities, antichains, and cyclic dataflow all originate here (SOSP 2013). Its distinguishing decision is to make iteration a first-class, low-latency primitive via the product timestamp, which no mainstream micro-batch system matches. DFR is essentially "Timely's core, re-specified with a production fault-tolerance and observability skin." Google Dataflow / MillWheel. MillWheel (VLDB 2013) chose per-record acknowledgements + persistent (Bigtable-backed) state + record-ID dedup for exactly-once, rather than global consistent-cut snapshots. This trades higher per-record overhead and a storage dependency for fine-grained recovery without a global barrier — attractive when state is huge and a stop-the-world checkpoint is unaffordable. The Dataflow Model paper (VLDB 2015) then unified its windowing/triggers/watermarks semantics, which DFR adopts in §19. It wins when state vastly exceeds RAM and global checkpoints are too coarse.

Spark Structured Streaming. The fundamentally different choice: micro-batch execution (discretized streams), where a stream is a sequence of small deterministic batch jobs. This yields trivial fault tolerance via RDD lineage recompute and reuses the entire batch engine, at the cost of a latency floor set by the batch interval (~100 ms+). Its later continuous-processing mode narrows the gap. It wins when throughput and exactly-once simplicity matter more than sub-100 ms latency, and when a team already runs Spark for batch (see Alternative Architectures, §36).

34. Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from the System Constraints (§4). Symbols: N = workers, B = batch size (1024, §4.4), cap = channel capacity in batches (16, §4.4).

  1. Per-core stateless throughput → host throughput. §4.1 gives 20M rec/s/core fused. On a 16-core host with §6.4's ~0.7×N scaling efficiency: 20M × 16 × 0.7 ≈ 224M rec/s aggregate fused stateless ceiling, before memory-bandwidth saturation.

  2. Channel buffer memory per edge. §4.4: cap × B × sizeof(record). For a 64-byte record: 16 × 1024 × 64 B = 1 MiB per edge direction. A 50,000-edge graph (§4.6) at one buffer each = 50,000 × 1 MiB = 48.8 GiB worst case — which is why most edges are pipeline (fused, no buffer) and only exchange/stateful boundaries hold full buffers. This derivation is why fusion (§21) is a memory lever, not just a CPU one.

  3. Exchange bandwidth (in-process). §4.1: 8M rec/s/core through exchange. With a 64-byte payload: 8M × 64 B = 512 MB/s/core of shuffle movement. On 16 cores all shuffling: ≈ 8.2 GB/s — within DDR4/DDR5 bandwidth (~20-50 GB/s), so in-process exchange is not bandwidth-bound until ~half the cores shuffle simultaneously (confirms §4.8's memory-bandwidth wall).

  4. Keyed-state RAM. State = keys × sizeof(K + V). For 10M distinct keys with a 16-byte key + 32-byte accumulator: 10M × 48 B ≈ 458 MiB/worker. With per-worker baseline < 16 MB (§4.7), state dominates memory — confirming state, not runtime overhead, sets the memory ceiling (MM2, P4).

  5. Checkpoint bytes. Snapshot size ≈ Σ keyed-state across operators. For 8 stateful operators each holding the 458 MiB above: 8 × 458 MiB ≈ 3.6 GiB/worker. Across 16 workers: ≈ 57 GiB total — well over the 10 GB RTO bracket (§4.5), so RTO of 30 s applies only to small state; large state needs incremental checkpoints (deferred; Scalability §31 "Storage growth").

  6. Checkpoint write time → RTO. §4.5: RTO < 30 s for ≤ 10 GB on local NVMe. NVMe write ≈ 2 GB/s, so restoring 10 GB ≈ 10 / 2 = 5 s of pure IO, leaving ~25 s for process restart + tracker rebuild + offset replay — confirming the 30 s budget is IO-bound and realistic for ≤ 10 GB, infeasible for the 57 GiB of step 5 without incremental restore.

  7. Checkpoint overhead fraction. §4.5 caps overhead at 5%. If async snapshot of 3.6 GiB/worker at 2 GB/s takes ~1.8 s, then to stay under 5% the checkpoint interval must satisfy 1.8 s / interval ≤ 0.05 → interval ≥ 36 s. This derives the minimum sane checkpoint interval from state size and disk bandwidth, rather than asserting it.

  8. Progress-message volume. MM8: progress cost is O(active pointstamps), not records. With P active pointstamps and N workers gossiping each round, broadcast = P × N × sizeof(ProgressUpdate). For P = 1000, N = 16, 16-byte updates: 1000 × 16 × 16 B = 256 KiB/round — negligible versus 224M rec/s of data (step 1), confirming the design's claim that progress is cheap when batched (§4.6).

  9. Alignment time under skew. §4.5: p95 < 50 ms (no skew). Alignment waits for the slowest input's in-flight to drain: ≈ cap × B / throughput_slow. At cap×B = 16,384 records and a slow input at 3M rec/s (keyed, §4.1): 16,384 / 3M ≈ 5.5 ms — under budget; but a 10× skewed input drops to ~55 ms, exceeding p95, which is exactly why skew is the named checkpoint bottleneck (§20.7, MM6).

  10. Watermark lag from buffering. Lag ≥ in-flight buffered time. With cap × B = 16,384 records per hop and a 4-hop chain at 5M rec/s: 4 × 16,384 / 5M ≈ 13 ms of structural lag — comfortably within §4.3's "< 2× watermark interval" if the watermark interval is ≥ 10 ms, and the reason batch size trades latency for throughput (§4.4).

  11. Exchange channel count (scaling ceiling). All-to-all exchange = N² subchannels per exchange edge (§3.1). For N = 64 (§4.6) and 5 exchange edges: 64² × 5 = 20,480 subchannels — each with a 1 MiB buffer (step 2) = 20 GiB just in exchange buffers, which is the concrete form of the O(N²) ceiling (§31) that pushes toward topology-aware exchange at high N.

  12. FD budget (distributed, §23). Network exchange opens one socket per (src,dst) pair: N × (N−1) FDs per host group. For N = 64: 64 × 63 = 4,032 sockets — within a typical 65,536 FD limit, but the O(N²) growth means a 256-worker cluster needs ~65,280 FDs, hitting the limit and forcing connection multiplexing (a §23 design constraint).

36. Alternative Architectures (Roads Not Taken)

Four fundamentally different architectures for the same problem — not parameter tweaks. Each: sketch, regime where it wins, the real system embodying it, why this blueprint rejected it.

36.1 Micro-batch (discretized streams)

  stream ──► [ batch_0 ] ─job─► result_0
            [ batch_1 ] ─job─► result_1     each batch = a full deterministic
            [ batch_2 ] ─job─► result_2     batch DAG; recovery = recompute via lineage
            interval = T (e.g. 100 ms+)
  • Wins when. Throughput and fault-tolerance simplicity dominate sub-100 ms latency; a team already runs a batch engine and wants streaming "for free" by reusing it; exactly-once falls out of deterministic recompute with no barrier protocol.
  • Real system. Spark (Discretized Streams, SOSP 2013) / Spark Structured Streaming.
  • Why rejected. The batch interval is a hard latency floor; iterative/low-latency workloads (a core DFR goal, §1, MM4) cannot tolerate it. DFR chooses record-at-a-time (Phase 2, §13) precisely to get µs–ms latency, accepting the complexity of progress tracking and barrier snapshots in exchange.

36.2 Lambda architecture (batch + speed layers)

  source ──┬─► BATCH layer  (recompute truth, high latency) ──┐
           │                                                  ├─► serving view (merge)
           └─► SPEED layer  (approximate, low latency)  ──────┘
  • Wins when. You need both an authoritative reprocessable batch result and a fast approximate view, and are willing to maintain two codebases for the same logic; historically common before strong-exactly-once streaming existed.
  • Real system. The classic Lambda pattern (Marz), often Hadoop/Spark batch + Storm speed layer.
  • Why rejected. Two implementations of the same computation is a maintenance and correctness hazard (the views can disagree). DFR's exactly-once streaming (§20) makes the batch layer redundant for correctness — this is precisely the "Kappa" critique. DFR is a single-codepath streaming runtime by design (P3 determinism gives reprocessing without a separate batch layer).

36.3 Pull-based / demand-driven dataflow

  sink "pull()" ◄── operator ◄── operator ◄── source
     demand flows BACKWARD; data is produced only when requested
     (laziness; natural backpressure = absence of demand)
  • Wins when. Consumers are slow and bursty and you want zero speculative work; the demand signal is the backpressure, with no explicit credit accounting; elegant for interactive / query-driven evaluation.
  • Real system. Reactive Streams / RxJava-style demand; classic lazy-evaluation dataflow.
  • Why rejected. Pull adds a request round-trip on the hot path (latency) and complicates progress tracking — the frontier protocol assumes upstream pushes and reports produced counts. DFR locks push (§8.2, PhaseDeferred("FINAL_BLUEPRINT §8")) and recovers pull's backpressure benefit via credit (MM2), keeping the data path one-directional and the progress protocol simple.

36.4 Centrally-coordinated progress (single watermark authority)

  worker_0 ─┐
  worker_1 ─┼─► COORDINATOR ─► broadcasts one global watermark ─► all workers
  worker_2 ─┘   (aggregates per-worker progress centrally)
  • Wins when. Worker count is small and a single authoritative watermark is far simpler to reason about and debug than distributed count reconciliation; the coordinator is not yet a bottleneck.
  • Real system. MillWheel's low-watermark aggregation has a central flavor; many simpler stream processors use a coordinator.
  • Why rejected. A central coordinator is a scaling bottleneck and a single point of failure, and it breaks the shared-nothing symmetry (P13, MM10) that makes DFR distributable by transport swap alone. DFR uses decentralized pointstamp gossip (§16, ADR-10) so progress scales with the workers and the same protocol survives the move to multi-host (§23).

Backpressure Credit-based flow control; producer blocks when downstream credit exhausted (§6.1, §3).
Credit Atomic count of buffer slots a producer may use; granted on consumer buffer return (§3.2).
Exchange / shuffle Edge that partitions records by key hash across workers; Pact defines the partition fn (§17, §11.5).
Pact Partitioning contract {partition fn, kind:Pipeline|Exchange}; single source of truth for routing + state ownership (§7.11).
Keyed state Per-key operator state KeyedState<K,V>, partitioned by the exchange key (§11.6).
State backend Abstraction over keyed-state storage; in-memory in P0; persistent deferred (§11.6).
Watermark A frontier in event time emitted by sources; signals event-time progress (§18 (Phase 8)).
Window Bounded grouping of event-time records (tumbling/sliding/session); flushed on trigger (§18 (Phase 8)).
Trigger Condition firing a window emission; event-time at window close by default (§18 (Phase 8)).
Lateness Allowed delay past watermark for late records; beyond it → drop/side-output (§7.4).
Side-output Secondary stream for late/dropped records; never merged into closed windows (§18 (Phase 8)).
Checkpoint barrier CheckpointBarrier{epoch} injected at sources; flows with data; aligns at operators (§20, §11.7).
Alignment Waiting for a barrier on all inputs before snapshotting → consistent cut (§7.9, §20).
Asynchronous barrier snapshot (ABS) Flink's aligned-barrier checkpoint algorithm (Chandy-Lamport derived) for exactly-once (§20).
Consistent cut Global state reflecting exactly the input prefix up to a barrier on every source (§7.9).
Epoch Monotonic checkpoint identifier; durable when all sinks ack (§11.7).
Snapshot / restore Serialize state at a barrier; deserialize on recovery + replay offsets → exactly-once (§20).
Exactly-once External effects equal a non-failing run: no duplicates, no losses (§6.7, §7.6).
Idempotent / transactional sink Sink that dedupes by key or 2-phase-commits aligned to epoch; required for exactly-once (§20).
Operator fusion Inlining a stateless chain into one monomorphized loop, eliding dispatch/channels (§21).
Skew Imbalance of per-key/per-worker load; the key streaming pathology (§6.6, §22).
Frontier lag Wall-clock minus event-time frontier; primary streaming-health signal (§4.3, §22).
Crash-only Only correct shutdown path is crash + restore-from-snapshot (§6.10).
Correctness fault Trusted-code invariant violation → fail-fast → abort+restore; distinct alert class (§6.14, §26).
PhaseDeferred Marker for capabilities intentionally out of P0 scope (e.g. distribution §23, persistent state).
