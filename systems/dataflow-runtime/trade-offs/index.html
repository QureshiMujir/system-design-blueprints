Decisions (§9) · 30 ADRs

01

Implementation language

Chosen

Rust (stable, edition 2021)

Rejected

C++, Go, Java/Scala, OCaml

When the rejected choice is right

JVM (Java/Scala) wins when the team must reuse the vast Flink/Kafka/Beam ecosystem and JIT warmup is amortized over long-running jobs; Go wins for a smaller team prioritizing build speed and operational simplicity over p99 tail latency

Why: Zero-cost abstractions, ownership for buffer reuse, no GC pauses, Send/Sync, Timely precedent (§1.10)

02

Build system

Chosen

Cargo workspace, multi-crate

Rejected

Bazel, single crate

When the rejected choice is right

Bazel wins in a polyglot monorepo with remote caching across thousands of targets where Cargo's per-crate model does not scale

Why: Native, reproducible; workspace = clean crate boundaries (§1.6)

03

Dependency policy

Chosen

Minimal, vetted; cargo-deny gate

Rejected

Liberal deps

When the rejected choice is right

Liberal deps win for a prototype optimizing time-to-first-demo over audit surface and long-term maintenance

Why: Supply-chain (§29); hot path stays std + tiny crates

04

Async/runtime model

Chosen

Custom cooperative scheduler (no async/await on data path)

Rejected

Tokio on the hot path, Rayon

When the rejected choice is right

Tokio wins when the workload is IO-bound (network sources/sinks dominate) rather than CPU-bound compute, so the reactor's readiness model fits and bespoke scheduling is wasted effort

Why: Need explicit activation + backpressure; async hides scheduling we must control

05

Threading

Chosen

OS threads, worker-per-core, optional pinning

Rejected

Green threads, thread pool per op

When the rejected choice is right

A per-operator thread pool wins when operators block on external IO of wildly different latencies and you want the OS to oversubscribe cores

Why: Predictable, NUMA-pinnable; one scheduler loop per worker

06

Channels (intra-worker)

Chosen

Custom bounded SPSC/MPSC ring (dfr-channels)

Rejected

crossbeam-channel, std mpsc

When the rejected choice is right

crossbeam-channel wins when you do not need progress-message interleaving and want a battle-tested channel without owning unsafe ring code

Why: Need credit/frontier backpressure + progress interleave; control over memory order

07

Concurrency primitives

Chosen

std::sync::atomic, crossbeam-utils (backoff, CachePadded)

Rejected

Mutex on hot path

When the rejected choice is right

A Mutex wins for cold-path structures (config, coordinator metadata) where contention is near-zero and lock-free code's complexity is not worth it

Why: Lock-free credits/progress; CachePadded avoids false sharing

08

Timestamp/lattice traits

Chosen

Custom PartialOrder/Lattice/Timestamp traits

Rejected

concrete u64 only

When the rejected choice is right

Concrete u64 wins for a pure acyclic event-time pipeline with no iteration, where the generic lattice machinery is dead weight (MM4)

Why: Required for partial orders + iteration product order (§6.12)

09

Frontier representation

Chosen

Antichain<T> (sorted small-vec) + change tracking

Rejected

bitset, single scalar

When the rejected choice is right

A single scalar wins when time is guaranteed totally ordered (no nested scopes), making the frontier one number and comparisons O(1)

Why: Antichains are the correct abstraction (§8.4); small-vec for typical small frontiers

10

Progress protocol

Chosen

Timely pointstamp (produced/consumed counts + reachability)

Rejected

central coordinator, vector clocks

When the rejected choice is right

A central coordinator wins at small scale (few workers) where a single authoritative watermark is simpler to reason about than distributed count reconciliation (MillWheel's model)

Why: Decentralized, scales, batchable; the proven design (Naiad)

State backend (P0)

Chosen

In-memory KeyedState (hashbrown maps + arena)

Rejected

RocksDB now

When the rejected choice is right

RocksDB wins when state exceeds RAM (tens of GB/worker) or incremental checkpoints are needed to keep checkpoint bytes sub-linear in state size (§34 ceiling)

Why: Latency; persistence deferred (§37)

Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Micro-batch (discretized streams)

  stream ──► [ batch_0 ] ─job─► result_0
            [ batch_1 ] ─job─► result_1     each batch = a full deterministic
            [ batch_2 ] ─job─► result_2     batch DAG; recovery = recompute via lineage
            interval = T (e.g. 100 ms+)
  • Wins when. Throughput and fault-tolerance simplicity dominate sub-100 ms latency; a team already runs a batch engine and wants streaming "for free" by reusing it; exactly-once falls out of deterministic recompute with no barrier protocol.
  • Real system. Spark (Discretized Streams, SOSP 2013) / Spark Structured Streaming.
  • Why rejected. The batch interval is a hard latency floor; iterative/low-latency workloads (a core DFR goal, §1, MM4) cannot tolerate it. DFR chooses record-at-a-time (Phase 2, §13) precisely to get µs–ms latency, accepting the complexity of progress tracking and barrier snapshots in exchange.

Lambda architecture (batch + speed layers)

  source ──┬─► BATCH layer  (recompute truth, high latency) ──┐
           │                                                  ├─► serving view (merge)
           └─► SPEED layer  (approximate, low latency)  ──────┘
  • Wins when. You need both an authoritative reprocessable batch result and a fast approximate view, and are willing to maintain two codebases for the same logic; historically common before strong-exactly-once streaming existed.
  • Real system. The classic Lambda pattern (Marz), often Hadoop/Spark batch + Storm speed layer.
  • Why rejected. Two implementations of the same computation is a maintenance and correctness hazard (the views can disagree). DFR's exactly-once streaming (§20) makes the batch layer redundant for correctness — this is precisely the "Kappa" critique. DFR is a single-codepath streaming runtime by design (P3 determinism gives reprocessing without a separate batch layer).

Pull-based / demand-driven dataflow

  sink "pull()" ◄── operator ◄── operator ◄── source
     demand flows BACKWARD; data is produced only when requested
     (laziness; natural backpressure = absence of demand)
  • Wins when. Consumers are slow and bursty and you want zero speculative work; the demand signal is the backpressure, with no explicit credit accounting; elegant for interactive / query-driven evaluation.
  • Real system. Reactive Streams / RxJava-style demand; classic lazy-evaluation dataflow.
  • Why rejected. Pull adds a request round-trip on the hot path (latency) and complicates progress tracking — the frontier protocol assumes upstream pushes and reports produced counts. DFR locks push (§8.2, PhaseDeferred("FINAL_BLUEPRINT §8")) and recovers pull's backpressure benefit via credit (MM2), keeping the data path one-directional and the progress protocol simple.

Centrally-coordinated progress (single watermark authority)

  worker_0 ─┐
  worker_1 ─┼─► COORDINATOR ─► broadcasts one global watermark ─► all workers
  worker_2 ─┘   (aggregates per-worker progress centrally)
  • Wins when. Worker count is small and a single authoritative watermark is far simpler to reason about and debug than distributed count reconciliation; the coordinator is not yet a bottleneck.
  • Real system. MillWheel's low-watermark aggregation has a central flavor; many simpler stream processors use a coordinator.
  • Why rejected. A central coordinator is a scaling bottleneck and a single point of failure, and it breaks the shared-nothing symmetry (P13, MM10) that makes DFR distributable by transport swap alone. DFR uses decentralized pointstamp gossip (§16, ADR-10) so progress scales with the workers and the same protocol survives the move to multi-host (§23).
