113 — BPE Tokenizer

Project Number: 113

Project Name: BPE Tokenizer

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade byte-level Byte-Pair-Encoding tokenizer in the GPT-2 / tiktoken / HuggingFace-tokenizers / SentencePiece / fastBPE lineage: a system that (a) trains a byte-level BPE vocabulary over corpora larger than RAM, in parallel across cores and shards, (b) encodes and decodes text losslessly and deterministically, (c) applies a GPT-2-style regex pre-tokenizer with pluggable alternatives, (d) isolates special tokens via a trie at the input boundary, and (e) ships an on-disk vocabulary that round-trips byte-identically with both OpenAI's .tiktoken format and HuggingFace's tokenizer.json format. Language: Rust 1.75 (edition 2021) — rationale: the training path is rayon-data-parallel, the encode path is a non-allocating hot loop unsuited to a GC, and one toolchain removes the FFI-boundary bug class a C++-trainer/Rust-encoder split would introduce (see ADR-01). Rejected languages: C++ (two memory models, two build systems — the fastBPE precedent); Python (encode hot path cannot hit 100+ MB/s in CPython even with array); Go (GC pauses violate the p99 encode-latency budget of §4; no unsafe-free zero-copy arena story as ergonomic as Rust's).

Phase-0 deliverable — numbered modules (crate = Cargo package; §10 gives full layout):

  1. bpe-core — TokenId, Vocab, MergeTable, SpecialToken, error types (§11.1–§11.4).
  2. bpe-pretok — Pretokenizer trait + WhitespacePretokenizer (Phase-0 placeholder).
  3. bpe-trainer — single-threaded in-memory training loop (pair-count → merge).
  4. bpe-encoder — quadratic-but-correct encode/decode (no arena, no priority queue yet).
  5. bpe-cli — bpe train / bpe encode / bpe decode subcommands, one-off JSON format.

System boundaries. Provides: byte-level training, encoding, decoding, two on-disk formats, a pluggable pre-tokenizer, special-token isolation, BPE-dropout. Delegates: model architecture, embedding tables, and downstream inference — this system emits TokenId streams and nothing past that boundary. Does NOT provide: a unigram-LM tokenizer (Kudo & Richardson 2018's alternative path — deferred, PhaseDeferred("§36")), sentence-boundary detection, text normalization beyond optional NFC (ADR-13), or a training-data curation pipeline.

Non-goals. Multi-lingual joint-BPE curriculum design; tokenizer-aware model architecture changes; a hosted training service. This is a library + CLI, not a SaaS.

Deployment model. A cdylib/rlib Rust library consumed directly, via pyo3 Python bindings (bpe-py), or via wasm-bindgen browser bindings (bpe-wasm, encode-only — the trainer needs threads and streaming I/O the WASM sandbox does not give it, PhaseDeferred("§9")). Training runs as an offline batch job (bpe-cli train); encoding runs in-process inside a model-serving pipeline or a browser tab.

Target users/operators. ML infra engineers building or auditing an LLM pipeline's tokenizer; the "operator" persona debugs a production encode/decode mismatch with bpe inspect and bpe diff (§26.6 CLI reference).

What later phases unlock. Phase 0 unlocks a correct-but-slow reference. Phases 1–2 unlock production encode speed. Phase 3–4 unlock training at scale with determinism. Phases 5–6 unlock ecosystem interoperability. Phase 7–8 unlock special-token safety and further speed. Phase 9 unlocks multi-TB training. Phase 10 unlocks regularization. Phase 11 unlocks the hardening bar that gates a 1.0 release.

Prerequisites. The byte-level vs. character-level distinction; priority queues and amortized-heap analysis; UTF-8 and Unicode general categories; the regex/fancy-regex syntax; one prior throwaway BPE implementation (this blueprint is the production rebuild, not the first encounter with the algorithm).

Estimated timeline. Phase 0: 1 week. Full system (Phases 0–11): 16 weeks (~4 months), detailed per-phase in Appendix B.

2. Why Build This

Every LLM pipeline has a tokenizer at its mouth: the function from bytes to ids. A vendored tiktoken blob or an opaque tokenizer.json pulled from a hub turns every downstream debugging session into "the model produced wrong logits and I cannot tell whether it was the prompt, the tokenization, or the weights." Writing the tokenizer converts that black box into a merge-table dump, a pre-token trace, and a fix (Karpathy's minbpe motivation, restated at systems scale).

The lineage is small and load-bearing: Gage (1994) published byte-pair encoding as a data-compression scheme; Sennrich, Haddow & Birch (2016 ACL) adapted it to neural machine translation; Radford et al. (GPT-2, 2019) moved it to byte-level, closing the unk-token gap forever; Kudo & Richardson (2018 EMNLP) generalized the subword problem with SentencePiece and the unigram alternative; OpenAI shipped tiktoken as a fast Rust-cored encoder; HuggingFace shipped tokenizers with a richer pluggable surface. None of these, alone, is what we build — tiktoken does not train; HuggingFace's training and encode are different code paths; SentencePiece ships a different on-disk format and a no-pre-tokenization philosophy; minbpe is a teaching artifact, not a production system. This blueprint is the synthesis: train like HuggingFace, encode like tiktoken, read on disk like both.

The byte-level invariant (§8.1) is the load-bearing decision this project teaches end to end: a char-level BPE emits unk on unseen codepoints; a byte-level BPE never does, because the 256-byte alphabet is closed under UTF-8. The cost — merges may cross UTF-8 boundaries, a token need not be a whole codepoint — is mild; the benefit — universal, lossless coverage — is total. Building this system by hand teaches subword modeling's real tradeoff space, not just the GPT-2 answer to it: cross-links to sibling systems in this portfolio include the LSM-tree project (external-sort/merge discipline reused in Phase 9), the lock-free queue project (the arena + lazy-invalidation discipline reused in Phase 2), and the wire-protocol/serialization project (the two-format compatibility discipline reused in Phases 5–6).

What Mastery Looks Like — after building this, the reader can:

  • Explain why byte-level BPE has no unk token and what it costs in merge quality (Phase 0, §12).
  • Design and defend a lock-free-adjacent, arena-backed hot loop with amortized O(log n) merges (Phase 2, §14).
  • Reason about determinism-under-parallelism as a first-class training requirement, not an afterthought (Phase 3–4, §15–§16).
  • Read and write both tiktoken and tokenizer.json on-disk formats from the byte level up (Phase 5–6, §17–§18).
  • Defend the trie-based special-token isolation design against the regex-augmentation trap (Phase 7, §19).
  • Build and validate a hand-rolled DFA against a regex reference via differential testing (Phase 8, §20).
  • Scale training past single-machine RAM with an external-sort discipline (Phase 9, §21).
  • Gate a systems project on a conformance suite and fuzz harness before calling it 1.0 (Phase 11, §23).

Seven properties, referenced throughout: (1) Bytes are ground truth — text is decoded once into &[u8] at the boundary; ids 0..256 are the byte alphabet, ids >=256 are learned merges (§8.1, I1). (2) The pre-tokenizer is a regex, not a tokenizer — its only job is to bound where BPE may not merge across (§8.3, P2). (3) The BPE merge is greedy, deterministic, priority-driven — lowest-rank pair wins, ties break left-most (§8.4, I6). (4) Special tokens bypass BPE entirely — matched by trie before pre-tokenization, never after (§8.5, P6, I5). (5) Training and encoding share the merge table, not the code — a trained tokenizer is a pure value (§11.2–§11.3, P7). (6) The encode hot path is allocation-free per pre-token — the EncoderScratch arena amortizes to one allocation per program run (P11, M3). (7) The trust boundary is at the SpecialTrie — everything past it is untrusted bytes; everything before Optional-kind special matching is where prompt-injection defenses live (T3, §19.3).

6. Design Principles

  1. P1 — Byte-level invariant. The alphabet is the 256 byte values; every input maps to &[u8]; no unk token exists. Tradeoff: merges may cross UTF-8 boundaries. Violating it (e.g. char-level fallback) reintroduces unk and breaks I1.
  2. P2 — Pre-tokenizer bounds, never tokenizes. The regex only prevents cross-run merges; it never assigns ids. Violating it (letting the regex assign ids) collapses the pre-tokenizer and BPE stage into one, breaking format compatibility (§17–§18).
  3. P3 — Determinism guarantee. Same merge table + same bytes ⇒ same Vec<TokenId>, on every machine, thread count, and version, except the seeded encode_with_dropout. Enforced by I7.
  4. P4 — Streaming-corpus support. Training working-set is O(vocab_size + active_pretokens), never O(corpus_size). Violating it caps trainable corpus size at RAM (breaks §4's 100 GB target).
  5. P5 — Format compatibility, exactly two. .tiktoken and tokenizer.json, both emitted and loaded from one Tokenizer value (ADR-08). A third format is scope creep and an interoperability trap.
  6. P6 — Special-token isolation. Specials are matched by trie before pre-tokenization, never inside the regex. Violating it chops literal special-token bytes into regex runs and BPE merges them wrongly (§19.5's regex-augmentation trap).
  7. P7 — Training/encode symmetry. The value that trains is the value that encodes; no separate "trained model" object with divergent state. Violating it risks train/serve skew.
  8. P8 — Regex-engine choice is an ADR, not an accident. fancy-regex for lookaround (ADR-04); the DFA (Phase 8) is a documented, feature-flagged optimization of the same contract, never a silent behavior change.
  9. P9 — Vocabulary stability (append-only). A (pair, rank) once in the table never moves; wire compatibility is a determinism guarantee across versions (I8).
  10. P10 — Memory-safe parallelism via sharding, never locking across a task boundary. The pair-count map is sharded by pair_hash % N; no lock is held across a rayon task boundary (ADR-07). Violating it (a global mutex) makes the lock the bottleneck.
  11. P11 — No-allocation hot path. One call to encode allocates exactly the output Vec<TokenId>; all intermediate state is arena-backed and thread-local (M3). Profile-guided via dhat (Phase 2 gate).
  12. P12 — Locale-neutral. No behavior depends on OS locale; no to_lowercase/ to_uppercase; explicit Unicode flags only. Violating it makes tokenization machine-dependent, a determinism (I7) breach.
  13. P13 — Fail closed on malformed on-disk state. A reader returns a typed Error, never panics, on a malformed .tiktoken/tokenizer.json line (I12). Violating it turns a corrupt file into a process crash instead of an operator-visible error.

8. Domain Model

8.1 Byte-level alphabet

The alphabet is TokenId(0)..TokenId(256), identity-mapped to byte values (I1). Display-only, the on-disk formats render bytes 0–32/127–160/173 via a "printable-ish" remap to U+0100+ (the GPT-2 convention, tiktoken/HF-compatible) so bpe inspect output is human-legible; the identity mapping underneath never changes. PRINTABLE_BYTES = the 188 byte values 33–126, 161–172, 174–255 that map to themselves.

8.2 Training: pair-count → merge

State table (per training epoch):

Step Input state Operation Output state
1 raw corpus stream pre-tokenize (§8.3), dedup to (bytes, count) ShardedCorpus
2 ShardedCorpus per-shard adjacent-pair count (rayon fan-out) per-shard PairCounts
3 per-shard PairCounts reduce: pick global top pair, tie-break by I9 (pair, count)
4 (pair, count) if count < min_pair_count: stop; else mint TokenId, MergeTable::push new merge, rank r
5 new merge apply in place across all shards; emit ±count deltas for neighbor pairs updated ShardedCorpus, PairCounts
6 updated state repeat from step 3 until vocab.len() == target_vocab trained Vocab + MergeTable

Worked example (toy corpus "aaab" x3, "abab" x2, min_pair_count=2): byte ids a=97,b=98. Pair counts: (97,97)→3, (97,98)→5, (98,97)→2. Merge 1: (97,98)→TokenId(256) ("ab"), rank 0 (highest count 5). Re-scan: "aaab"→[97,256,... ] becomes [97,97,256] per token; "abab"→[256,256]. New pair counts: (97,97)→3 (unchanged, no a,a pair touched), (97,256)→3, (256,256)→2. Merge 2 (tie between (97,97)@3 and (97,256)@3, I9 tie-break picks lexicographically smaller (97,97)): mint TokenId(257) ("aa"), rank 1. Training halts at target_vocab or when the max remaining count < min_pair_count.

Malformed-input example: a pre-token whose byte sequence is not valid UTF-8 at a chunk boundary (a corpus reader split mid-codepoint) is handled by re-validating at the &str boundary per §8.3 — the trainer operates on &[u8] post-pre-tokenization and never requires codepoint alignment past that point, so a split multi-byte sequence degrades to two shorter pre-tokens rather than corrupting state (I12's discipline applied to the trainer, not only the readers).

Failure-path example: if counts.top() returns a pair whose count was already decremented to zero in a prior shard's delta but not yet reduced (a race in delta application order), the sharded-reduce-then-apply ordering in step 5→3 (never concurrent) makes this unreachable by construction — deltas are folded into the global PairCounts before the next top() call, per ADR-07's "no lock across a task boundary, but reduce before the next read" discipline.

8.3 Pre-tokenization regex

GPT-2 pattern: 's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+ (EBNF-equivalent below). The pre-tokenizer trait contract: yields (start, end) byte offsets into input that partition it — every byte in exactly one pre-token, in order (P2).

pretoken     ::= contraction | word | number | punct-run | ws-trailing | ws-run
contraction  ::= "'s" | "'t" | "'re" | "'ve" | "'m" | "'ll" | "'d"
word         ::= [" "]? letter+          ; letter = \p{L}
number       ::= [" "]? digit+           ; digit  = \p{N}
punct-run    ::= [" "]? (not-space-letter-digit)+
ws-trailing  ::= space+                  ; lookahead: not followed by non-space
ws-run       ::= space+

8.4 Encode via merge application

Inside one pre-token: build a doubly-linked list of byte-level TokenIds in an arena; seed a priority queue with every adjacent pair that has a MergeTable entry, ordered (rank, insert_seq); pop the lowest-rank valid entry, fuse the pair, push newly adjacent candidate pairs, repeat until the queue is empty (I6). State per merge step:

Field Meaning
rank merge's position in training emission order (lower = higher priority)
left_node / right_node arena indices of the two nodes being fused
insert_seq monotonic counter breaking rank ties deterministically, left-to-right
live false once a node has been fused away; queue entries referencing it are stale

8.5 Vocab & special tokens

Vocab = {bytes: Vec<Vec<u8>>, by_bytes: HashMap<Vec<u8>, TokenId>, specials: BTreeMap<TokenId, SpecialToken>}. A SpecialToken is {id, bytes, kind} where kind ∈ {Regular, Optional}. Regular specials (e.g. <|endoftext|>) are always matched by SpecialTrie::scan; Optional specials are matched only when the caller's AllowedSpecial set includes them — the default caller posture for untrusted text is AllowedSpecial::Default with Error on an unexpected literal special-token sequence (the prompt-injection defense, T3).

12.1 Objectives

Stand up the full repository (§10) as stubs; ship a single-threaded, quadratic-but-correct training + encode/decode path; prove the byte-level round-trip on a toy corpus. No parallelism, no priority queue, no GPT-2 regex yet — those are later phases. This phase exists so every later phase lands on working scaffolding, per §7's "Phase 0 stands up the repo skeleton + correctness kernel" contract.

12.2 Detailed Implementation Steps

Land every file/dir in §10 as a stub (empty lib.rs, placeholder Makefile targets shelling to cargo). Implement bpe-core's TokenId/Vocab/MergeTable/SpecialToken (§11.1–§11.4) as compile-only definitions — only Vocab::new_byte_alphabet() (P1, I1) has a body. Implement bpe-pretok::WhitespacePretokenizer (split on \s+) as the Phase-0 placeholder pre-tokenizer (P2). Implement bpe-trainer single-threaded: read corpus into a String, pre-tokenize, byte-encode each pre-token, build HashMap<(TokenId,TokenId), u64> pair counts, loop find-highest→merge→update (§8.2's state table, steps 3–6, serialized) until target_vocab or no pair >= min_pair_count (ADR-20). Implement bpe-encoder's O(n²) reference encode (repeatedly apply lowest-rank applicable merge with a linear scan — ADR-05's rejected alternative, intentionally, for Phase 0 only) and decode (concatenate vocab.bytes_of(id), lossy UTF-8). Implement bpe-cli's train/encode/decode subcommands against a one-off JSON format (replaced by §17–§18).

12.3 Deliverable

make bootstrap && make build && make test green; cargo run --example hello-world trains a 306-token vocab (256 + 50 merges) on a 10,240-byte Lorem Ipsum fixture, encodes "hello world", "the quick brown fox", and an emoji string, decodes each, and asserts byte-exact round-trip (I10).

12.6 Pitfalls

The byte alphabet must be initialized exactly once (I1); a bug that re-inserts ids <256 after a Vec::clear() makes id 0 mean two bytes and silently diverges every later encode. min_pair_count defaults to 2 (a hapax pair compresses nothing) — do not default to 1. Resist shipping the GPT-2 regex here; if the smoke test fails, the bug must be isolated to the training loop, not entangled with regex correctness (Phase 1).

12.7 Performance Concerns

O(n²) per-pre-token encode is acceptable only because the corpus is 10 KB; do not benchmark this phase's throughput — Phase 2 sets the real M1/M2 targets.

12.8 Edge Cases

Empty input string (encode → empty Vec, decode → empty string). A pre-token of length 1 (no merge possible, output is exactly its byte id). A corpus with zero mergeable pairs (min_pair_count never satisfied) — trainer halts at 256-token vocab, not an error.

A malformed fixture file (non-UTF-8 Lorem Ipsum) fails make test with a Utf8 error (I12), never a panic; blast radius is contained to the one test binary; operator re-generates the fixture from conformance/corpora/ascii/README.md's recipe.

quadratic-vs-heap-100k.bin — 100K arbitrary inputs; expected: identical Vec<TokenId> from both encoders. dhat-zero-alloc.json — dhat snapshot; expected: 0 blocks in encode_one_pretoken steady state.

14.6 Pitfalls

Lazy-invalidation missing the next == right_node clause merges across an already-merged span silently (I6 violation) — the three-clause check is mandatory, not two. insert_seq is required for determinism (I7); without it, BinaryHeap's tie-break is undefined and violates I6's left-most rule. EncoderScratch must be thread-local, not stack-local — the RefCell borrow is the cheap path (P11).

14.7 Performance Concerns

Arena growth is amortized (grows at most once per thread lifetime); cache locality favors the Vec<Node> arena over boxed linked-list nodes (CLRS-style analysis, §5); the heap's insert_seq field adds 4 bytes per entry, negligible against the win of deterministic tie-breaking.

14.8 Edge Cases

A pre-token where every adjacent pair has the same rank tie (pathological but possible with a degenerate merge table) — insert_seq guarantees a deterministic, left-to-right drain order. A single-byte pre-token — queue seeded empty, output is the one byte id, no merge loop runs.

14.9 Failure Analysis

An EncoderScratch arena that fails to grow (allocation failure under extreme memory pressure) propagates as a Result::Err from encode_into, never an abort — detection via the process's standard OOM telemetry; recovery is caller-level backoff, not encoder-level.

14.10 Operational Notes

bpe-bench's encode_throughput and memory_per_call benchmarks become CI gates from this phase onward (§30); a regression >5% blocks merge without an ADR sign-off.

15. Phase 3 — Parallel Training & Sharded Pair-Count Reduce

15.1 Objectives

Parallelize training across cores (P4, P10, ADR-07); replace Phase-0's single-threaded loop with a rayon-driven, sharded-reduce pipeline meeting the M6 throughput target.

15.2 Detailed Implementation Steps

Implement PretokShard/ShardedCorpus (§11.7-adjacent, bpe-trainer/src/shard.rs): deduplicate pre-tokens to (bytes, count) pairs, partition into n_shards (Blandy/Orendorff/ Tindall rayon patterns, §5). Implement PairCounts sharded by xxh3_64(pair) % n_shards (ADR-11, ADR-07 — ties broken later by I9, not here). Implement train_loop (bpe-trainer/src/merge_loop.rs): initial parallel pair-count via par_iter, then the repeat-until-target_vocab loop — counts.top(), mint merge, par_iter_mut apply-in-place across shards emitting ± deltas, fold deltas into PairCounts before the next top() call (the "reduce before next read" discipline resolving §8.2's failure-path analysis). Wire a parity test against Karpathy's minbpe (§5) on a 10K-document corpus.

15.3 Deliverable

A trainer completing a 32,000-vocab run over a 1 GB corpus in ≤10 minutes on 16 cores; merge table matches minbpe's on the parity corpus.

15.4 Acceptance Criteria

Training throughput: 1 GB corpus, 32K vocab, ≤10 min on 16 cores (M6, hard CI gate on a benchmark runner); merge-table equality vs. minbpe 100% on the 10K-document parity corpus (named fixture conformance/corpora/roundtrip/minbpe-parity-10k.bin); byte-identical merge table across 1/4/16 thread counts on a fixed-seed corpus (I7).

15.5 Conformance Fixtures

minbpe-parity-10k.bin — expected: merge-table equality with minbpe reference output. thread-count-determinism.bin — same corpus trained at 1/4/16 threads; expected: byte-identical MergeTable (I7, I9).

15.6 Pitfalls

Determinism under parallelism is load-bearing (P3): tie-breaking must be lexicographic on (left_id, right_id) (I9), never "first observed" (that depends on rayon's scheduler and corpus-reader chunk size — nondeterministic). The delta FxHashMap should be clear()d and reused between epochs, not reallocated (large corpora produce millions of entries/epoch). A decrement to zero must remove the entry from PairCounts, not leave a phantom zero (top() would otherwise return it).

15.7 Performance Concerns

The merge-update phase dominates at large vocab sizes (each merge touches every shard); shard count should scale with core count, not corpus size, to keep per-shard update cost bounded.

15.8 Edge Cases

A corpus where ids = [A, A, A] and the merge pair is (A, A) — correct result is [merged, A] (first two fuse, trailing A is a new pair start), not [merged, merged]; proptest covers this explicitly (per Phase-3's parity suite). A corpus that ties at every epoch — I9's rule resolves it deterministically.

15.9 Failure Analysis

A rayon worker panic inside par_iter_mut propagates as a poisoned task and surfaces as a Result::Err from train(), never a silent partial-merge state — the whole train() call fails atomically; the caller retries from the last checkpoint (Phase 9 adds checkpointing for multi-hour runs).

15.10 Operational Notes

TrainerProgress callbacks (epoch, vocab_size, last_pair, last_count, elapsed_ms) are the operator's live-progress signal; bpe train --verbose streams them to stderr as structured log lines.

16. Phase 4 — Deterministic Tie-Breaking & Merge-Selection Hardening

16.1 Objectives

Close Phase 3's tie-breaking gap explicitly (I9) and harden MergeTable::push against duplicate pairs (I13, ADR-05's uniqueness precondition for encode-time rank lookups).

16.2 Detailed Implementation Steps

Implement PairCounts::top()'s tie-break: iterate all shards, track (best_pair, best_count), replace on count > best_count || (count == best_count && pair < best_pair) (I9, lexicographic on (u32, u32)). Document that the reduce order across shards is itself deterministic (shard-id order, not scheduler order — P10). Implement MergeTable::push rejecting a duplicate (left, right) with Error::DuplicateMergePair (I13, ADR-19's no-panic discipline). Add the encode-time note that rank ties cannot occur once I13 holds — the insert_seq field (Phase 2, I6) exists only for pairs at equal rank inserted at different queue-life points, an unrelated case.

16.3 Deliverable

A test suite proving tie-breaking is deterministic across shard counts and across repeated runs with engineered multi-way ties.

16.4 Acceptance Criteria

Two trainer runs with different shard counts (4 vs. 16) on the same corpus produce byte-identical merge tables (I7, I9) — 100% match, named fixture conformance/corpora/roundtrip/shard-count-determinism.bin; an engineered 5-way-tie corpus produces the documented lexicographic winner every run (10/10 repeated runs); MergeTable::push rejects 100% of duplicate-pair injection attempts in the unit suite.

16.5 Conformance Fixtures

shard-count-determinism.bin — expected: identical merge table at 4 vs. 16 shards. five-way-tie.bin — a corpus engineered so 5 pairs tie at every epoch; expected: lexicographic winner per I9, every run.

16.6 Pitfalls

"First observed wins" is a tempting but wrong tie-break (some reference tools use it) — it is not deterministic across thread counts because observation order depends on rayon's scheduler and the corpus reader's chunk size. minbpe's tie-break is first-observed, so exact parity with minbpe is only well-defined on corpora engineered to avoid ties (documented in conformance/corpora/README.md, not a Phase-4 defect).

16.7 Performance Concerns

The tie-break comparison (pair < best_pair) is O(1) per candidate; it does not change the overall O(shards × pairs-per-shard) cost of top().

16.8 Edge Cases

A count that appears in only one shard vs. spread across all shards — the reduce must still find the true global max, not a per-shard local max (a common off-by-reduce-scope bug).

16.9 Failure Analysis

If two chats/processes race to call MergeTable::push with the same pair concurrently (should be structurally impossible — training is single-writer), the second call's Err surfaces immediately rather than corrupting ordered; blast radius is one failed train() call.

16.10 Operational Notes

bpe diff (§26.6) uses the documented tie-break rule to explain why two merge tables trained on similar corpora diverge at a specific rank — an operator-facing debugging feature this phase unlocks.

17. Phase 5 — The tiktoken On-Disk Format

17.1 Objectives

Ship a reader/writer for OpenAI's .tiktoken line format (ADR-08, P5, P7); establish parity against the four vendored reference vocabularies.

17.2 Detailed Implementation Steps

Implement write_tiktoken (bpe-format-tiktoken/src/writer.rs): for each merge in rank order, emit base64(bytes) rank (RFC 4648 standard/padded per §5); the byte alphabet (ids 0..256) is implicit and never written. Implement read_tiktoken: parse line-by-line, reject any rank <256 (Error::MalformedLine, I12/ADR-19), reconstruct (left, right) for each merged-bytes entry via find_pair_for_bytes — try every prefix/suffix split already present in the in-progress vocab, and where more than one split is valid, pick the split whose right-hand id has the lowest rank (the documented tiktoken-compatible tie-break, tiktoken reference per §5). Wire the parity harness against third_party/{r50k,p50k,cl100k,o200k}_base.tiktoken (ADR-23) on the tiktoken-parity conformance bucket.

17.3 Deliverable

A reader loading cl100k_base.tiktoken (~100K merges) in ≤1 s; a writer that round-trips a trained tokenizer through .tiktoken with byte-identical merges and encodes.

17.4 Acceptance Criteria

Load time for cl100k_base.tiktoken ≤1 s (named benchmark, hard gate); round-trip (train → write_tiktoken → read_tiktoken → encode) byte-identical to direct-encode on a held-out 10K-document corpus (I11); parity vs. the OpenAI reference encoder 100% on all four vendored vocabularies (tiktoken-parity bucket, 4 sub-buckets).

17.5 Conformance Fixtures

cl100k-load-1s.bin — timing fixture; expected ≤1 s. tiktoken-parity/{r50k,p50k,cl100k, o200k}.expected.bin — captured reference-encoder output; expected: 100% id match.

17.6 Pitfalls

find_pair_for_bytes is genuinely ambiguous when multiple prefix/suffix splits are already in the vocab — the documented resolution (lowest right-hand rank) must match what the reference tool effectively encodes, or parity silently breaks on a subset of merges. Standard vs. URL-safe base64 are different alphabets — .tiktoken uses standard/padded (RFC 4648); the wrong flavor produces decode errors on bytes ending +///=. A rank sequence with a gap (256, 257, 259 skipping 258) is malformed and must be rejected (I12), not silently renumbered.

17.7 Performance Concerns

Loading 100K merges means 100K find_pair_for_bytes calls; each is bounded by pre-token length (typically <20 bytes) against an already-built partial vocab — O(merges × avg_token_len), not quadratic in vocab size.

17.8 Edge Cases

A .tiktoken file with a comment line (# ...) or blank line — both ignored per the format spec (§26.7). A file with non-space whitespace (tab, CR) inside a data line — rejected as malformed (I12), never silently trimmed.

17.9 Failure Analysis

A truncated .tiktoken file (process killed mid-write) fails on the last incomplete line with MalformedLine, never corrupting the entries parsed so far — the caller's recovery path is "re-train or re-fetch," documented in docs/runbook/train-a-vocab.md.

17.10 Operational Notes

bpe convert --in foo.tiktoken --out foo/tokenizer.json (§26.6, built in Phase 6) depends on this phase's reader; docs/runbook/migrate-tiktoken-to-hf.md is drafted here.

18. Phase 6 — The HuggingFace tokenizer.json Format

18.1 Objectives

Ship a reader/writer for the HF tokenizer.json schema subset this system supports (ADR-08, P5, P7); prove format-equivalence with .tiktoken (I11).

18.2 Detailed Implementation Steps

Implement HfTokenizer/HfModel::BPE schema (§18.1 below is the wire spec, not §11's runtime types) in bpe-format-hf/src/model.rs: vocab (display-string → id), merges ("left right" strings in rank order), dropout/unk_token/byte_fallback fixed to null/null/false (this system's byte-level-total design has no unk, P1). Implement read_tokenizer_json: parse JSON, reverse the display-char mapping (§8.1/§13.2's display_char_to_byte, ADR-14) for every vocab entry with id >= 256, rebuild MergeTable by joining each merges line against vocab, reject a merges entry whose left/right is absent (Error::UnknownToken). Implement write_tokenizer_json as the inverse, plus the ByteLevel pre_tokenizer/decoder pair matching the HF GPT-2 convention. Wire the hf-parity conformance bucket against third_party/gpt2_tokenizer.json.

18.3 Deliverable

A reader loading HF's gpt2/tokenizer.json and encoding a held-out corpus identically to the reference tokenizers Rust crate; a bpe convert CLI subcommand bridging both formats.

18.4 Acceptance Criteria

hf-parity bucket 100% on the GPT-2 held-out corpus; format-roundtrip (.tiktoken → tokenizer.json → encode) byte-identical to direct .tiktoken encode on the same corpus (I11, named fixture conformance/corpora/format-roundtrip/tiktoken-to-hf-10k.bin); JSON whitespace may differ, but every encoding-relevant field is preserved (documented diff policy).

18.5 Conformance Fixtures

hf-parity/gpt2.expected.bin — captured HF tokenizers crate output; expected 100% id match. tiktoken-to-hf-10k.bin — round-trip corpus; expected byte-identical encode both directions.

18.6 Pitfalls

The byte-display mapping (§8.1) is the most common bug source: a token [0x20, 0x68, 0x65, 0x6c, 0x6c, 0x6f] (" hello") displays as "Ġhello" in tokenizer.json; an unreversed mapping loads a vocab missing " hello" and containing the display string instead, silently breaking every downstream encode. vocab and merges must agree — a merges entry referencing a byte-string absent from vocab is a load-time error, not a skip.

18.7 Performance Concerns

JSON parsing of a ~100K-entry vocab is dominated by serde_json deserialization, not by the display-mapping reversal (O(1) per entry via the baked table, ADR-14) — no special optimization needed at this phase's scale.

18.8 Edge Cases

A tokenizer.json with a non-BPE model.type (e.g. Unigram) — rejected at load with a typed error, not partially loaded (this system supports BPE models only, §1 non-goals). A pre_tokenizer sequence longer than the single-element ByteLevel we emit — documented as a PhaseDeferred("§18") surface, not silently ignored.

18.9 Failure Analysis

A tokenizer.json with a vocab/merges mismatch fails at load with Error::UnknownToken (I12); the operator's recovery path is bpe diff against the last-known-good file to isolate which entries changed.

18.10 Operational Notes

docs/architecture/on-disk-formats.md documents both schemas side by side from this phase onward; bpe convert's exit code 3 (§26.6) signals a conformance-level failure distinctly from I/O errors (exit 2).

19. Phase 7 — Special Tokens & the Byte-Trie

19.1 Objectives

Implement SpecialTrie (§11.8, P6, ADR-09) and the input-boundary scan that isolates special tokens from both the regex pre-tokenizer and BPE (I5); implement the Regular/Optional prompt-injection defense (T3).

19.2 Detailed Implementation Steps

Implement the R-way trie (Sedgewick & Wayne Section 5.2, per §5) over [u16; 256] children arrays, accept: Option<TokenId> per node (bpe-special/src/trie.rs). Implement SpecialTrie::scan as a longest-prefix-match walk from every unmatched position (bpe-special/src/scan.rs): non-overlapping SpecialSpans in input order (I5). Wire encode_with_allowed (§11.6) and AllowedSpecial::{Default, All, Set, None} (P6's trust-boundary contract, §3's diagram); the default posture for untrusted input is Default with Error on a disallowed literal special sequence — never All (T3). Integrate the scan into BpeEncoder::encode_into's Pass 1 (Phase 2's stubbed SpecialTrie::empty() is replaced here).

19.3 Deliverable

A working special-token pipeline: <|endoftext|> and family bypass BPE entirely when allowed; a fuzz target proving the regex pre-tokenizer never observes special-token bytes.

19.4 Acceptance Criteria

Scan throughput ≥100 MB/s single core, 16-special-token list (§4 gate, named benchmark); <|endoftext|> encodes to exactly 1 id when allowed, to len(bytes) byte ids when disallowed (100% pass on special-tokens conformance bucket); overlapping specials (<|im_start|> vs. <|im_start|>system) resolve to the longest match, 100% of engineered overlap cases.

19.5 Conformance Fixtures

special-tokens/overlap-matrix.bin — every (input, allowed_special setting) combination; expected ids per cell. special-tokens/endoftext-bypass.bin — expected: single id, never decomposed bytes, when allowed.

19.6 Pitfalls

Folding the special-token alternation into the pre-tokenization regex is the classic mistake (rejected explicitly at ADR-09): a literal <|endoftext|> would chop into <,|,endoftext, |,> and BPE-merge wrongly. The [u16; 256] node is 512 bytes; with 16 typical specials the trie is ~100 KB — acceptable, but a 1000+-special deployment should switch to a sparse representation (PhaseDeferred("§19") — documented, not built in current scope).

19.7 Performance Concerns

The scan is O(input_len) with a small constant (one 512-byte array lookup per byte in the worst case of a long partial match); the 100 MB/s target holds because most bytes exit the trie walk within 1–2 steps (specials are short relative to typical input).

19.8 Edge Cases

A special-token byte sequence that straddles a chunk boundary in a streaming reader — the scan operates on the fully-buffered input for a single encode call, so no straddling occurs within one call; cross-call streaming is a documented non-goal (§1).

19.9 Failure Analysis

An AllowedSpecial::Default caller encountering a disallowed literal special sequence gets Error::DisallowedSpecial { bytes } (I12) — detection is immediate and typed; recovery is the caller's choice among Error/Tokenize/Strip response modes (§8.5).

19.10 Operational Notes

docs/architecture/special-tokens.md documents the trust-boundary diagram (§3); T3 in the Threat Model (§24) cross-references this phase as the structural mitigation for prompt injection via literal special-token strings in user text.

20. Phase 8 — The DFA Pre-Tokenization Splitter

20.1 Objectives

Ship a hand-rolled DFA (P8, ADR-04's documented optimization path) implementing the GPT-2 pattern at 2.5–5× fancy-regex's throughput, behind a feature flag, without changing the pre-tokenizer contract (§11.5).

20.2 Detailed Implementation Steps

Construct the DFA offline in build.rs from a Rust description of the pattern's 14 states (Start; apostrophe-suffix; letter/number/punctuation runs; whitespace-trailing vs. whitespace-run, mutually exclusive) — generated code checked into dfa_splitter_generated.rs (Korpela's Unicode-property-class discipline, §5). Bake Unicode \p{L}/\p{N} membership into a static bit array covering planes 0–1 (17,408 u64s) rather than parsing UnicodeData.txt at runtime. Implement the \s+(?!\S) lookbehind as DFA state: track "currently in whitespace," and on the first non-whitespace transition retroactively commit the prior run as \s+(?!\S) (or as plain \s+ if a boundary condition applies). Feature-flag the module (features=["dfa"], ~200 KB generated code) so default builds stay on fancy-regex. Wire the parity::regex-vs-dfa conformance bucket.

20.3 Deliverable

A DfaSplitter byte-identical to Gpt2Pretokenizer on the 10K-document parity corpus, at the higher throughput target.

20.4 Acceptance Criteria

Throughput ≥500 MB/s ASCII, ≥250 MB/s mixed-Unicode single core (M4, M5 — hard CI gate under the dfa feature); 100% span parity vs. Gpt2Pretokenizer on the 10K-document corpus (named fixture conformance/corpora/unicode/regex-vs-dfa-10k.bin); zero divergences found by the regex_vs_dfa fuzz target after a 3-hour nightly run.

20.5 Conformance Fixtures

regex-vs-dfa-10k.bin — expected: identical spans, both engines. dfa-fuzz-corpus/ — seed corpus for the differential fuzz target.

20.6 Pitfalls

Anything past 2 Unicode planes in the bitmask wastes binary size on scripts no realistic corpus tokenizes — cap at planes 0–1 deliberately (a documented, not accidental, coverage limit). The whitespace-trailing state is the trickiest: it must distinguish "whitespace run followed by EOF/non-whitespace" from "whitespace run immediately followed by more whitespace," exactly mirroring \s+(?!\S) vs. \s+.

20.7 Performance Concerns

The DFA trades ~200 KB of generated code and a one-time build-time cost for a 2.5–5× runtime win; this is a good trade only when the encode hot path (not build time) is the bottleneck metric — documented as the reason the feature is opt-in, not default.

20.8 Edge Cases

A supplementary-plane character (emoji) spanning 4 UTF-8 bytes — the DFA's leading-byte sub-classification must route all 4 continuation bytes correctly to stay in the letter/number/ punctuation state as appropriate; a fuzz target specifically targets 4-byte sequences.

20.9 Failure Analysis

A DFA/regex divergence found by the parity fuzz target blocks the dfa feature from being promoted to default (never silently shipped); the fix path is: isolate the diverging input, add it to regex-vs-dfa-10k.bin, patch the DFA state table, re-run the full parity corpus.

20.10 Operational Notes

benchmarks/regex_engine.rs reports both engines side by side in benchmarks/results/; bpe train --pretok gpt2 --features dfa is the documented opt-in invocation.

21. Phase 9 — Streaming & Large-Corpus Training

21.1 Objectives

Break Phase 3's implicit RAM-resident assumption (P4); make training scale to corpora larger than RAM via external sort, meeting the M7 target (100 GB, ≤4 h, 32 cores, 64 GB RAM).

21.2 Detailed Implementation Steps

Implement StreamingCorpus::build_dedup_table (bpe-trainer/src/stream_reader.rs, Kleppmann's SSTable/external-sort discipline per §5): Pass 1 streams the corpus, pre-tokenizes, emits (pre-token, 1) records to length-prefixed temp-file runs; Pass 2 external-sorts via rayon::par_sort in-memory runs plus an N-way min-heap merge across run files, run-length- encoding equal keys into (bytes, count). Feed the resulting DedupTable (RAM-resident if it fits, else mmap'd) into the unmodified Phase-3 train_loop (P7 — training and encode share state, not code paths, and this phase changes only the corpus-ingestion path). Document the scratch-directory free-space requirement (60–80% of pre-tokenized corpus size) in the runbook.

21.3 Deliverable

A trainer producing a 50K-vocab tokenizer over a 100 GB corpus in ≤4 h on 32 cores / 64 GB RAM, with peak RAM bounded by I3.

21.4 Acceptance Criteria

100 GB corpus, 50K vocab, ≤4 h wall time, 32 cores, 64 GB RAM (M7, hard gate on the streaming benchmark); peak RSS ≤2× dedup-table size regardless of raw corpus size (I3, dhat-verified); merge-table equality vs. the in-RAM Phase-3 trainer on a 10 GB synthetic corpus (named fixture conformance/streaming/10gb-parity.bin).

21.5 Conformance Fixtures

streaming/10gb-parity.bin — expected: merge table identical to in-RAM trainer on the same corpus. streaming/scratch-exhaustion.bin — a corpus sized to fill a constrained scratch volume; expected: a typed I/O error, not a silent truncation.

21.6 Pitfalls

O_DIRECT is tempting for the external-sort merge phase; resist — the page cache helps sequential run reads, and posix_fadvise(POSIX_FADV_SEQUENTIAL) is the correct hint instead. Trainers have died at hour 3 from /tmp filling up — the 60–80% free-space rule belongs in the runbook, checked before a multi-hour run starts, not discovered mid-run.

21.7 Performance Concerns

The merge phase is I/O-bound, not CPU-bound; shard count for the initial pass should be sized to keep each in-memory run within a single-digit-GB budget so rayon::par_sort stays cache- friendly.

21.8 Edge Cases

A corpus so skewed that one pre-token dominates 90% of occurrences — the dedup table still holds one entry with a large count; the merge loop is unaffected (it operates on counts, not raw occurrence lists).

21.9 Failure Analysis

A crash mid-external-sort leaves partial run files in the scratch directory; recovery is restart-from-Pass-1 (no partial-run resumption in this phase's scope, PhaseDeferred("§21") for checkpointed resumption).

21.10 Operational Notes

docs/runbook/train-a-vocab.md gains the streaming-training procedure, including the scratch-space precheck; TrainerProgress.elapsed_ms becomes operationally meaningful at this scale (a 4-hour run needs live progress, not just a final callback).

22. Phase 10 — BPE-Dropout & Subword Regularization

22.1 Objectives

Implement encode_with_dropout (Provilkov et al. 2019 per §5, ADR-10) as an encode-time regularizer: each candidate merge is skipped with probability p, seeded for determinism (P3's documented exception).

22.2 Detailed Implementation Steps

Implement encode_with_dropout(input, p, seed) (bpe-encoder/src/dropout.rs): seed a Xoshiro256++-family PRNG from seed; in the priority-queue drain loop (§8.4, Phase 2), before applying a popped merge, sample Bernoulli(p) and continue (skip, leave the linked-list structure unchanged) on a hit — the skipped pair is not re-queued (this encode call's outcome only; a different pre-token occurrence gets its own independent sample). Bound p to [0.0, 1.0]; warn (not error) above 0.5 since the output degenerates toward the byte-level alphabet. Assert encode_with_dropout(input, 0.0, seed) == encode(input) byte-for-byte.

22.3 Deliverable

A dropout-aware encode path that is byte-identical to the plain encoder at p=0, and reproducible per (seed, p, input) triple.

22.4 Acceptance Criteria

p=0 byte-identical to encode on the full 100K-input regression corpus (100% match); 1,000 runs of encode_with_dropout(input, 0.1, random_seed) produce no two identical outputs (statistical, false-positive rate documented ≤0.1%) and every output decodes back to the input (I10); dropout-encode throughput within 20% of plain encode (named benchmark benchmarks/dropout_overhead.rs).

22.5 Conformance Fixtures

dropout/p0-identity.bin — expected: byte-identical to encode. dropout/seed-reproducibility. bin — same (input, p, seed) triple, 100 repeated calls; expected: identical output every time.

22.6 Pitfalls

BPE-dropout is a training-time regularizer in Provilkov et al.'s original design; shipping it as an encode-time option (so callers can apply it without retraining) does not reproduce the paper's exact reported numbers unless the downstream model is also trained under dropout — document this distinction loudly, it is a common misreading. Skipping a merge does not require re-queuing the skipped pair's neighbors — the pair simply does not fuse for this call.

22.7 Performance Concerns

The Bernoulli sample is O(1) per popped queue entry; the 20% overhead budget accounts for the PRNG call, not for any structural change to the merge loop.

22.8 Edge Cases

p very close to 1.0 — nearly every merge is skipped, output approaches the raw byte-level alphabet; correct but uninteresting, and the warn-above-0.5 threshold flags likely misuse. p exactly 0.0 — must take the identity fast path, not merely converge to it statistically.

22.9 Failure Analysis

An out-of-range p (negative or >1.0) is rejected at the API boundary with a typed error before any PRNG call — never silently clamped (P13's discipline extended to configuration, not just on-disk data).

22.10 Operational Notes

bpe encode --dropout 0.1 --seed 42 is the CLI-level exposure (§26.6); the reproducibility guarantee (I7's seeded exception) is documented explicitly in docs/sdk/ since callers building data-augmentation pipelines depend on it.

conformance.report.json itself (schema-validated against report_schema.json) is the aggregate fixture; each bucket's own named fixtures are listed in their originating phase (§12.5–§22.5).

23.6 Pitfalls

proptest's shrinking toward minimal failing inputs tends to land on UTF-8 sub-codepoint edge cases — do not special-case these away; they are exactly the bugs worth finding. The conformance corpus accumulates over releases; a bucket failing on the current corpus but passing on the prior tagged corpus is a real regression signal, not noise — track it, do not suppress it.

23.7 Performance Concerns

The fuzz/property-test suite runs on a fixed CI time budget (3 h per target); target selection (which invariant each fixture stresses) matters more than raw iteration count within that budget.

23.8 Edge Cases

An arbitrary byte sequence that is valid UTF-8 but decodes to zero codepoints under any pre-tokenizer pattern (empty input after trimming) — the round-trip property must still hold trivially (empty in, empty out).

23.9 Failure Analysis

A fuzz-found crash auto-files a GitHub issue (via the nightly workflow) with the minimized reproducer attached; the triage path is: add the reproducer to the relevant fixture directory, write a regression test, fix, re-run the full 12-hour budget once before closing.

23.10 Operational Notes

conformance.report.json is uploaded as a GitHub Actions artifact on every PR (§28); the 1.0 release tag (§29) is gated on two consecutive clean nightly fuzz runs plus a fully green conformance report — the release engineer checks both before cutting the tag.

27. Compatibility & Versioning

The 0..256 byte-alphabet reservation (I1) is a permanent wire commitment; widening it is a breaking change requiring a major version bump. MergeTable is append-only (I8, P9): a tokenizer.json/.tiktoken produced by version N decodes identically on version N+k for any k, forever — this is the determinism-as-wire-compatibility guarantee (P9). SemVer applies to the bpe-core/bpe-encoder/bpe-trainer public API surface (§11); a breaking change to any signature in §11 is a major bump. The two on-disk formats (ADR-08) each carry their own version field where the upstream spec defines one (tokenizer.json's "1.0"); this system tracks upstream format revisions as they occur and documents any deviation as an ADR. Rolling upgrade: since encoding is a stateless library call, a serving fleet may run mixed library versions during a rollout as long as they load the same on-disk vocab — I7's determinism guarantee is what makes this safe. Deprecation policy: a Pretokenizer variant is never removed, only added to (PretokKind::Custom is the escape hatch); a deprecated CLI flag warns for one minor version before removal.

28. Testing & Verification Strategy

Unit tests per crate exercise §11's types directly (e.g. MergeTable::push's duplicate rejection, I13). Integration tests (tests/integration/) exercise cross-crate flows (the Phase-0 hello_smoke.rs, §12.3). Property tests (proptest) cover every invariant in §7 not already exercised by a fuzz target (§23.2): I7 (thread-count determinism), I10 (round-trip), I5 (special-token non-overlap). Differential tests compare this system's output against minbpe (§15), tiktoken (§17), and HuggingFace tokenizers (§18) on held-out corpora. Fuzzing (cargo-fuzz, ADR-18) covers the four targets in §23.2, gated at 3h per-PR / 12h nightly. Chaos/fault injection: the streaming trainer (§21) is tested under simulated scratch-disk exhaustion (FM-3) and rayon worker panics (FM-5). Deterministic replay: a fixed TrainerConfig + corpus + seed always reproduces the same MergeTable (I7, I9) — this is the replay contract the parity tests lean on. Soak testing: the nightly 12h fuzz run and a weekly 100 GB streaming-training soak run (§21) are the two long-running verification jobs. Every conformance bucket (§23.2's conformance/runner) is a performance-regression gate too: a bucket that passes correctness but regresses M1–M10 by >5% blocks merge without an ADR (§29).

31. Scalability Analysis

Constant regardless of scale: encode allocation count (M3, one output Vec); the byte alphabet size (256, I1). Grows with input: encode time, O(pre-token length) per pre-token via the priority-queue merge loop — O(n log n) worst case per pre-token (ADR-05), O(total input length) overall. Grows with corpus size: training time — bounded by I3's dedup-then-train discipline to O(unique_pretokens × avg_merges_touching_each), not O(raw_corpus_size) past the initial pre-tokenization pass. Named bottlenecks, in order: (1) the merge-update phase at large vocab sizes (§15.7, every merge touches every shard); (2) the external-sort merge phase at multi-TB scale (§21.7, I/O-bound); (3) JSON parsing for tokenizer.json loads at very large vocab sizes (§18.7, serde_json-bound). Horizontal scaling: training shards across cores within one machine (rayon, ADR-07); cross-machine sharding is a documented non-goal (§1) — the streaming design (§21) targets single-machine scale-up to 100 GB, not scale-out. Vertical scaling: more cores linearly reduces M6/M7 up to the point the merge-update phase's shard-fanout overhead dominates (empirically past ~64 shards per the Phase-3 benchmark). Coordination overhead: the sharded pair-count reduce (§15.2) is the only cross-shard coordination point per epoch — its cost is O(n_shards), independent of corpus size. The practical ceiling: a single machine's RAM bounds the dedup pre-token table (I3); beyond that, the lever is mmap-backed DedupTable storage (§21.1) trading RAM for page-fault latency, or, un-built, cross-machine sharding (PhaseDeferred("§31"), a future direction not in this system's current scope).

32. Mental Models & First Principles

  1. MM1 — A pre-token is a merge arena, not a string. Once bytes enter the BPE loop they are arena-indexed nodes, never re-touched as &str. Predicts: any bug report mentioning "codepoint boundary" inside the merge loop is a category error. Bug class without it: accidental UTF-8 re-validation inside the hot path. Applied at §8.4, §14.
  2. MM2 — Rank is time. A merge's rank is literally "when training minted this token" — lower rank = earlier = higher encode priority. Predicts: two tokenizers with the same vocab but different training-corpus order can have different ranks and thus different encodes even on identical vocab contents. Bug class without it: assuming vocab-set equality implies encode-equality. Applied at §8.4, §9 (ADR-05).
  3. MM3 — The trie is a trust boundary, not a feature. Everything before SpecialTrie::scan is untrusted; everything after is tokenizer-internal. Predicts: any special-token bug report is either "the trie let something through it shouldn't" or "the trie ate bytes it shouldn't have" — never a BPE bug. Bug class without it: prompt-injection via regex-augmented specials (rejected at ADR-09). Applied at §3, §19, §24 (T3).
  4. MM4 — Determinism is a wire-compatibility guarantee, not a nicety. P9/I8's append-only MergeTable means "same input, same output, forever" is a promise to every downstream consumer who persisted an id. Predicts: any proposal to "just re-tie-break ties differently" is a breaking change requiring a major version bump. Bug class without it: silent train/serve skew after a library upgrade. Applied at §7 (I7–I9), §27.
  5. MM5 — Sharding beats locking when the update is commutative-ish. The pair-count delta (§15.2) is fold-associative across shards; a lock would serialize what sharding parallelizes. Predicts: any "just add a mutex" PR to the trainer is a regression, not a fix. Bug class without it: lock-contention collapse under high core counts. Applied at §9 (ADR-07), §15.
  6. MM6 — The byte level is the only level with no escape hatch. Every other segmentation (pre-tokenizer, special tokens, merges) can fail closed to "just bytes." Predicts: any "impossible to tokenize" bug report is a bug, not an expected outcome — P1 guarantees total coverage. Bug class without it: an unk-token reintroduction disguised as an edge case. Applied at §2, §8.1.
  7. MM7 — A format reader that panics is a format the ecosystem cannot trust with adversarial input. P13/I12's fail-closed discipline is what lets bpe-cli sit at a trust boundary (loading vocabs from arbitrary sources) safely. Predicts: any reader PR with an .unwrap() on file-derived data is a security regression, not a style nit. Applied at §9 (ADR-19), §24 (T1, T2).
  8. MM8 — Streaming is a two-pass discipline, not a single loop with a smaller buffer. Pass 1 (dedup) and Pass 2 (train) are separable because the trainer only needs (bytes, count), not corpus order (§8.2). Predicts: any attempt to "stream training directly" without the dedup pass re-derives an O(corpus_size)-working-set trainer, defeating the point. Applied at §21.

34. Back-of-Envelope Capacity Model

  1. Encode throughput floor (M1) = 200 MB/s ⇒ a 1 GB prompt corpus encodes in 1e9 / 2e8 = 5 s single-core.
  2. DFA throughput ceiling (M4) = 500 MB/s ⇒ the same 1 GB corpus in 1e9 / 5e8 = 2 s — the 2.5× win the DFA (§20) buys.
  3. Encode p99 latency (§4) for a 1 KB input at M1's 200 MB/s floor: 1024 bytes / 2e8 B/s = 5.12 µs theoretical; the stated 60 µs p99 budget leaves ~12× headroom for queueing/priority- queue overhead (§14) — this is why §4's number is 60 µs, not 5 µs.
  4. Training wall-clock (M6): 1 GB corpus, 16 cores, target ≤10 min ⇒ required aggregate throughput ≥ 1e9 bytes / 600 s = 1.67 MB/s per core-equivalent minimum, well under M1's single-core encode floor — training's pair-count-and-merge loop is the bottleneck, not raw byte throughput, hence the separate M6 target rather than reusing M1.
  5. Dedup pre-token table size (I3, §21): a 10 GB corpus with ~10–50M unique pre-tokens at ~30 bytes average (bytes + count + hash overhead) ⇒ 30M pretokens × 30 bytes = ~900 MB, comfortably under 64 GB RAM even at 2× peak (I3).
  6. 100 GB streaming corpus (M7): at the same dedup ratio (~1:20 raw-to-unique), dedup table ≈ 100GB / 20 × 30bytes/pretoken_avg_ratio ≈ ~9 GB — well under the 64 GB RAM budget, confirming M7's memory feasibility before the mmap fallback is ever needed.
  7. Special-token scan cost (M8): 100 MB/s floor, 16 tokens averaging 12 bytes ⇒ trie depth ≤12 ⇒ worst-case per-byte cost is one [u16;256] lookup per trie level ⇒ 100MB/s is achievable when most bytes exit within 1–2 trie steps (§19.7's non-match-fast-path claim).
  8. Trie memory (§19.6): 16 specials × 512 bytes/node × ~12 nodes/token average ⇒ 16 × 512 × 12 ≈ 98 KB — matches the "~100 KB" figure asserted at §19.6, derived here rather than asserted there.
  9. cl100k_base load time (M10): ~100,277 merges, each requiring one find_pair_for_bytes scan bounded by average token length (~4 bytes) against a growing vocab ⇒ 100,277 × O(4) ≈ 400K basic ops, comfortably inside the 1 s budget even accounting for base64 decode and I/O.
  10. Fan-out × rate ceiling for encode-serving: at M1's 200 MB/s per core and a typical 512- byte prompt, one core serves 2e8 / 512 ≈ 390,625 prompts/s theoretical ceiling before any model-inference cost dominates — this bounds how much tokenizer throughput ever matters relative to the downstream model's own latency.

Every number above chains from §4's constraint table; none is asserted without the arithmetic shown.

36. Alternative Architectures (Roads Not Taken)

Alt-1 — No pre-tokenization, unigram-LM segmentation (SentencePiece's path).

Show the original text diagram
raw text -> NFKC normalize -> unigram Viterbi segmentation -> ids
            (no regex boundary; whole input is one segmentation problem)

Regime where it wins: languages without whitespace-delimited words (CJK, Thai) where a GPT-2 regex actively fragments meaningful units. Real system: Google SentencePiece (Kudo & Richardson 2018, §5). Rejected here because ecosystem compatibility with GPT-lineage checkpoints (ADR-03) requires the regex boundary this system ships; a from-scratch, CJK-first project should choose Alt-1 instead.

Alt-2 — WordPiece-style greedy longest-match, not rank-priority merges.

Show the original text diagram
word -> try longest known subword prefix -> emit -> repeat on remainder
        (greedy, no priority queue, no merge-rank table)

Regime where it wins: a fixed, small vocabulary trained once, where greedy segmentation's simplicity outweighs BPE's compression-optimality. Real system: BERT's WordPiece tokenizer (Wu et al. 2016, §5). Rejected here because greedy longest-match does not compose with this system's append-only, rank-ordered MergeTable (P9) — WordPiece has no notion of merge rank at all, only a static vocabulary, which breaks the training/encode symmetry principle (P7) this design is built around.

Alt-3 — Suffix-array-based linear-time BPE training.

Show the original text diagram
corpus -> suffix array + LCP array -> pair frequencies via array scan
          (no explicit pair-count hash map; frequency derived from array structure)

Regime where it wins: extremely large single-pass corpora where the sharded-hash-map reduce (§15) becomes memory-bound before it becomes compute-bound. Real system: linear-time BPE implementations built on suffix automata (the algorithmic lineage bpeasy-style trainers draw from). Rejected here because the sharded pair-count-map design (ADR-07, ADR-11) is simpler to reason about under rayon's work-stealing model and already meets M6/M7; a suffix-array rewrite would be justified only if M7's 100 GB ceiling needed to grow by another order of magnitude.

Alt-4 — Character-level tokenization, no BPE at all.

Show the original text diagram
raw text -> Unicode scalar values -> ids directly (one id per codepoint)
            (no merges, no training, no vocab beyond Unicode's codepoint space)

Regime where it wins: small models and short-context tasks where vocabulary compression matters less than eliminating an entire subsystem (no trainer, no merge table, no format compatibility story). Real system: char-level nanoGPT-style toy models. Rejected here because it fails the compression and cross-lingual-efficiency goals that motivate BPE at all (§2) — sequence lengths balloon, and the entire point of this project (teaching production-grade subword tokenization) would be moot.

38. Glossary

  • Alphabet — the closed set of 256 byte values, ids 0..256, that every input decomposes into before any merge (§8.1).
  • AllowedSpecial — the caller-supplied policy (Default/All/Set/None) governing which special tokens may be matched in a given encode call (§8.5).
  • Arena — the pre-allocated backing store (Vec<Node>) for the intrusive doubly-linked pre-token structure, avoiding per-merge heap allocation (§11.6).
  • BPE (Byte-Pair Encoding) — the algorithm that iteratively replaces the most frequent adjacent symbol pair with a new symbol (Gage 1994; Sennrich et al. 2016).
  • BPE-dropout — Provilkov et al.'s regularization technique: skip a candidate merge with probability p during encode (§22).
  • Byte-level BPE — BPE applied over the 256-byte alphabet rather than characters, closing the unk-token gap (Radford et al., GPT-2).
  • Corpus — the training text, consumed as a stream (CorpusInput) rather than fully materialized (§11.7, §21).
  • DFA splitter — the hand-rolled finite-automaton pre-tokenizer implementing the GPT-2 pattern at higher throughput than fancy-regex (§20).
  • Dedup table — the deduplicated (pre-token bytes, count) structure training operates over instead of raw corpus order (§8.2, §21.1).
  • Determinism — the guarantee that a fixed merge table and input bytes always produce the same output, across machines/threads/versions (I7, P3).
  • Display mapping — the GPT-2-style remap of non-printable byte values to U+0100+ codepoints for human-legible vocab inspection, distinct from the underlying identity byte map (§8.1).
  • Encode — the process of turning &str/&[u8] input into a Vec<TokenId> (§8.4, §11.6).
  • EncoderScratch — the thread-local arena + priority queue + byte buffer reused across encode calls to avoid allocation (§11.6, P11).
  • Fixture — a named, versioned test input/expected-output pair in conformance/corpora/ (§12.5 et seq.).
  • fancy-regex — the Rust regex engine with lookaround support, used for the default GPT-2 pre-tokenizer (ADR-04).
  • Fuzz target — a cargo-fuzz harness exercising one invariant under adversarial mutation (§23.2).
  • GPT-2 pattern — the specific regex 's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+ (§8.3).
  • Lazy invalidation — the priority-queue technique of leaving stale entries in place and checking validity only at pop time (§14.2, I6).
  • Merge — a (left, right) -> merged_id rule with a rank, produced by training (§8.2, §11.3).
  • MergeTable — the append-only, rank-ordered collection of all learned merges (§11.3, P9).
  • Pair-count map — the sharded (TokenId, TokenId) -> u64 frequency structure driving merge selection during training (§8.2, §15.2).
  • Parity test — a differential test asserting byte-identical output between this system and a reference implementation (minbpe, tiktoken, HF tokenizers) (§15, §17, §18).
  • Pre-token — a contiguous byte span the pre-tokenizer regex yields, inside which BPE may freely merge (§8.3, P2).
  • Pretokenizer — the trait abstracting the pre-tokenization strategy (GPT-2/Llama3/ Whitespace/UAX29/DFA) (§11.5).
  • Priority queue — the binary heap ordering candidate merges by (rank, insert_seq) for the encode-time greedy loop (§14.2, ADR-05).
  • Rank — a merge's position in training emission order; lower rank = higher encode priority (§8.2, I8).
  • Reduce (sharded) — folding per-shard pair-count deltas into the global PairCounts before the next top() read, never concurrently with it (§15.2, P10).
  • Round-trip — decode(encode(s)) == s for valid UTF-8 s; the system's core correctness contract (I10).
  • Shard — a partition of the deduplicated corpus (or the pair-count map) processed independently by one rayon task (§15.2, ADR-07).
  • SpecialToken — a literal byte sequence matched at the input boundary, bypassing BPE entirely (§8.5, §11.4).
  • SpecialTrie — the R-way byte-trie performing longest-prefix-match special-token scanning (§11.8, §19.1).
  • Streaming training — the two-pass (dedup, then train) discipline enabling corpora larger than RAM (§21, MM8).
  • Tie-break — the deterministic lexicographic rule ((left_id, right_id) ascending) resolving equal-count pairs during training (I9, §16.1).
  • TokenId — the u32 newtype identifying a byte or a learned merge (§11.1).
  • .tiktoken format — OpenAI's line-oriented on-disk vocabulary format: base64(bytes) rank per line (§17, §26.7).
  • tokenizer.json format — HuggingFace's JSON on-disk schema for a BPE model plus pre-tokenizer/decoder/added-tokens metadata (§18.1).
  • Vocab — the id↔bytes bidirectional mapping plus the special-token registry (§11.2).
  • Wire compatibility — the guarantee that a serialized vocab decodes identically forever, independent of library version (§27, P9).
