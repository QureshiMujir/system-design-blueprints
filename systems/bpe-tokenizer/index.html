In one paragraph

A byte-level BPE tokenizer turns text into the list of integer ids a language model reads, and turns those ids back into the same text without loss. This design is a Rust library plus a command-line tool (§1). It trains a vocabulary over corpora larger than RAM, encodes and decodes deterministically, isolates special tokens such as <|endoftext|> before any merging, and reads and writes both OpenAI's .tiktoken format and HuggingFace's tokenizer.json format (§1). Its defining commitment is that the 256-value byte alphabet is closed and never resized, so no "unknown token" can exist (§4, P1). ML infrastructure engineers run it: training as an offline batch job, encoding inside a serving pipeline or a browser tab (§1).

The problem, concretely

Every language-model pipeline has a tokenizer at its mouth: the function from bytes to ids. If you only use a vendored blob or an opaque file pulled from a hub, a bad model output leaves you unable to tell whether the prompt, the tokenization or the weights caused it (§2). Owning the tokenizer turns that into a merge-table dump and a pre-token trace (§2). Four pressures shape the design.

First, coverage. A tokenizer working on characters emits an unk (unknown) token for a codepoint it never saw in training. A tokenizer working on bytes never does, because the 256 byte values are closed under UTF-8 (§2, §8.1). The price is that a merge may cross a UTF-8 boundary, so a token need not be a whole codepoint (§2).

Second, safety at the input edge. If the special-token spelling <|endoftext|> is folded into the splitting regex, the literal gets chopped into <, |, endoftext, |, > and the pieces are merged wrongly (§19.6). Worse, a user whose text contains that literal could truncate or hijack a downstream prompt (T3).

Third, no single existing tool covers it: tiktoken does not train, HuggingFace's training and encode are different code paths, and SentencePiece ships a different format (§2). Fourth, training must not need the whole corpus in RAM (P4, §4), and the same merge table and bytes must give the same ids everywhere, because downstream consumers persist ids (P3, MM4).

How it works, end to end

Follow one piece of text through the boxes of §3's diagram, encode side first:

  1. Special-token scan (SpecialTrie, crate bpe-special). The input is untrusted until it passes this box. A longest-match scan peels off any allowed special token as a single id and passes everything else on (§3, §8.5, I5).
  2. Pre-tokenizer (Pretokenizer trait in bpe-pretok). A regex (default GPT-2 pattern, run by fancy-regex) cuts the remaining text into pre-tokens. Its only job is to mark where merges are not allowed to cross; it never assigns ids (§3, §8.3, P2, ADR-04).
  3. Byte-level encoder. Each pre-token becomes a run of byte ids; byte i is id i (§3, §8.1).
  4. Merge loop (bpe-encoder, with a thread-local EncoderScratch arena). Adjacent ids are fused by learned merges, lowest rank first, until none apply (§3, §8.4, P11).
  5. The result is a Vec<TokenId>. Decoding is the inverse, and decode(encode(s)) == s must hold for valid UTF-8 (I10).

Training runs offline on the other half of §3's diagram: stream the corpus, pre-tokenize and count per shard, reduce to the top pair with a deterministic tie-break, apply the merge, repeat to target_vocab, then serialize to .tiktoken or tokenizer.json (§3, §8.2). The trainer lives in bpe-trainer. Its output, a MergeTable plus Vocab, is a plain value the encoder also uses; training and encoding share the table, not code (§3, P7). bpe-format-tiktoken and bpe-format-hf write and read it, bpe-cli exposes bpe train|encode|decode|inspect|convert|diff, and bpe-py and bpe-wasm are bindings, the WASM one encode-only (§1, §10).

The core ideas

The byte alphabet: ids 0 to 255 are the bytes themselves (§8.1)

The vocabulary starts as 256 entries, TokenId(0)..TokenId(256), identity-mapped to byte values and immutable after Vocab::new_byte_alphabet() (§8.1, I1). Every id from 256 up is a learned merge (§3). Because every input is just bytes, nothing is "untokenizable": byte level is the one level with no escape hatch needed (MM6, P1). For human-readable dumps only, the on-disk formats show non-printable bytes through a remap to U+0100 and above (the GPT-2 convention); the identity map underneath never changes, and the 188 byte values in PRINTABLE_BYTES map to themselves (§8.1).

Training: count pairs, merge the top pair, repeat (§8.2)

A pair is two adjacent ids. Training repeatedly finds the most frequent pair and gives it a new id. Per epoch (§8.2):

Step What happens Result
1 pre-tokenize the corpus stream; dedup to (bytes, count) ShardedCorpus
2 count adjacent pairs per shard (rayon fan-out) per-shard PairCounts
3 reduce: pick the global top pair, ties broken by I9 (pair, count)
4 if count < min_pair_count stop; else mint a TokenId and MergeTable::push new merge at rank r
5 apply the merge in place everywhere; emit plus/minus count deltas for neighbouring pairs updated corpus and counts
6 repeat from step 3 until vocab.len() == target_vocab trained Vocab and MergeTable

The blueprint's own toy run (§8.2): corpus "aaab" three times and "abab" twice, min_pair_count=2, bytes a=97, b=98. It states first-round counts (97,97)→3, (97,98)→5, (98,97)→2, so merge 1 is (97,98)→TokenId(256) ("ab") at rank 0. After re-scanning, "aaab" is [97,97,256] and "abab" is [256,256], with counts (97,97)→3, (97,256)→3, (256,256)→2. Merge 2 is a tie between (97,97) and (97,256) at 3; the I9 tie-break picks the lexicographically smaller (97,97), minting TokenId(257) ("aa") at rank 1. Note: the example's first-round counts and its garbled "aaab" re-scan line are logged in blueprints/ERRATA.md.

The blueprint gives two different stopping rules. I2 says merges.len() == target_vocab - 256 - specials.len() when the trainer terminates (§7). §8.2 says training halts at target_vocab or when the best remaining count falls below min_pair_count (step 4), and §12.8 says a corpus with no mergeable pair halts at a 256-token vocab, "not an error". The blueprint does not reconcile the two.

Pre-tokenization: where merges may not cross (§8.3)

The splitter's contract is that it yields (start, end) byte offsets that partition the input: every byte lands in exactly one pre-token, in order (§8.3, P2). The GPT-2 pattern recognizes, in order: contractions ('s, 't, 're, 've, 'm, 'll, 'd), a word (letters with an optional leading space), a number (digits with an optional leading space), a run of punctuation, and two kinds of whitespace run (§8.3). The trailing-whitespace rule needs a lookaround, which is why fancy-regex is chosen over the plain regex crate (ADR-04). ADR-04, §13.6 and §20.2 call \s+(?!\S) a lookbehind, while §8.3's grammar labels it a lookahead. A hand-built DFA can later replace the regex as a feature-flagged speedup under the same contract (P8, §20).

Encoding: fuse pairs in rank order inside one pre-token (§8.4)

Inside one pre-token the encoder keeps the ids in an arena-backed doubly-linked list and seeds a priority queue (a binary heap) with every adjacent pair that has a merge entry, ordered by (rank, insert_seq) (§8.4, ADR-05, ADR-06). It pops the lowest-rank entry that is still valid, fuses the pair, pushes the newly adjacent pairs, and repeats until the queue is empty (§8.4, I6).

Field Meaning (§8.4)
rank position in training emission order; lower means higher priority
left_node / right_node arena indices of the two nodes being fused
insert_seq monotonic counter that breaks rank ties left to right
live false once a node has been fused away; queue entries pointing at it are stale

Stale entries are not removed from the heap; they are checked when popped (lazy invalidation, §14.2, §38). Rank is time: it records when training minted the merge, so two vocabularies with the same contents but different training order can encode differently (MM2). The loop is O(n log n) against Phase 0's O(n²) encoder (§14.1). It allocates only the output vector, because scratch state is thread-local and reused (P11, §14.2). §14.2 states the pop-time check as live && next == right_node, while §14.6 calls it a "three-clause check" and FM-1 "I6's 3-clause check"; none of the three names a third clause.

Special tokens: a trie at the trust boundary (§8.5)

Vocab holds the id-to-bytes tables plus a map of SpecialToken {id, bytes, kind}; kind is Regular or Optional (§8.5). Regular specials such as <|endoftext|> are always matched by SpecialTrie::scan; Optional ones only when the caller's AllowedSpecial set includes them (§8.5). For untrusted text the default posture is AllowedSpecial::Default, which returns an error on an unexpected literal special sequence (§8.5, T3). The caller may then choose Error, Tokenize or Strip (§19.9). The scan is a longest-prefix walk producing non-overlapping spans (§19.2).

Phase 7's examples (§19.4): <|endoftext|> encodes to exactly 1 id when allowed and to len(bytes) byte ids when disallowed; with <|im_start|> and <|im_start|>system both defined, the longer one wins. Everything before the trie is untrusted and everything after is internal, so special-token bugs are either "let through" or "ate bytes", never BPE bugs (MM3).

Training at scale: shards instead of locks, fixed tie-breaks, two passes (§8.2, §15)

Pair counts are split across shards by xxh3_64(pair) % n_shards, and each shard is updated by its own rayon task with no lock held across tasks (ADR-07, §15.2, P10). After applying a merge, each shard emits plus/minus deltas that are folded into the global PairCounts before the next top() call (§15.2), which is what makes the "stale count" race unreachable by construction (§8.2). Sharding wins over locking when updates fold associatively (MM5).

Determinism needs a fixed tie rule: equal-count pairs break by (left_id, right_id) ascending (I9), never "first observed", which would depend on rayon's scheduler and chunk size (§15.6). The cross-shard reduce order is by shard id, not scheduler order (§16.2). For corpora larger than RAM, §21.2's Pass 1 streams and pre-tokenizes the corpus into (pre-token, 1) temp-file runs, Pass 2 external-sorts and merges those runs into (bytes, count) records, and the unchanged Phase-3 train_loop then runs over that DedupTable (§21.2). MM8 names the two passes differently: Pass 1 is "dedup" and Pass 2 is "train" (MM8).

The trade-offs — where engineers disagree

Alphabet: bytes, not characters (ADR-02)

Chosen: byte-level, so there is no unk and UTF-8 is closed (§9). Rejected: char-level. When the rejected choice is right: a closed, single-script corpus such as pure ASCII logs, where char-level's simplicity wins because there is no coverage gap to close.

Splitting: the GPT-2 regex by default (ADR-03)

Chosen: the GPT-2 regex, for compatibility with existing GPT-lineage checkpoints (§9). Rejected: SentencePiece-style no pre-tokenization, and WordPiece greedy matching. When the rejected choice is right: a from-scratch model with no compatibility requirement benefits from SentencePiece's cleaner no-pre-tokenization story (§9); §36 adds that languages without whitespace-delimited words, such as CJK and Thai, are where a GPT-2 regex actively fragments units.

Merge selection at encode time: heap, not scan (ADR-05)

Chosen: a binary heap, O(log n) amortized, so long pre-tokens such as URLs or base64 blobs scale (§9). Rejected: a linear scan, O(n) per merge. When the rejected choice is right: pre-tokens capped near 8 bytes (some CJK segmenters), where the scan's lower constant factor wins (§9).

Training reduction: shards, not one mutex (ADR-07)

Chosen: rayon with pair counts sharded by hash and no cross-task lock, because a lock becomes the bottleneck under contention (§9). Rejected: a global mutex on one HashMap. When the rejected choice is right: a single-core CI smoke-test build, which has no contention to avoid. ADR-07 adds that the mutex "is what Phase-0 uses" (§9), while §1 and §12.2 describe the Phase-0 trainer as single-threaded over a plain HashMap, with no mutex mentioned.

Special tokens: a byte trie, not regex alternation (ADR-09)

Chosen: a byte trie at the input boundary, keeping special-token and pre-tokenization concerns separate (§9, P6). Rejected: a regex-augmented pre-tokenizer. When the rejected choice is right: the ADR names no regime where regex augmentation wins; a system with zero special tokens needs no trie at all, and the advice there is to skip the trie, not to augment the regex (§9).

Roads not taken

Unigram segmentation with no pre-tokenization (§36, Alt-1): SentencePiece's path, where the whole input is one segmentation problem. It wins for languages without whitespace-delimited words; it is rejected for GPT-lineage compatibility (ADR-03), but a from-scratch CJK-first project should pick it.

WordPiece-style greedy longest match (§36, Alt-2): no priority queue and no merge-rank table. It wins for a small vocabulary trained once, where simplicity beats compression optimality. It is rejected because it does not compose with the append-only, rank-ordered MergeTable (P9, P7).

Suffix-array linear-time training (§36, Alt-3): pair frequencies derived from an array structure, with no pair-count hash map. It wins when the sharded-map reduce becomes memory-bound on very large single-pass corpora. It is rejected because the sharded design is simpler under rayon and already meets M6 and M7; it would be justified only if M7's 100 GB ceiling grew another order of magnitude.

Character-level tokenization with no BPE (§36, Alt-4): one id per codepoint, no trainer, no merge table. It wins for small models and short contexts where removing a whole subsystem matters more than compression. It is rejected because sequence lengths balloon (§36, §2).

Deferred register (§37): parked items with explicit un-defer triggers, among them a unigram tokenizer, a WASM-hosted parallel trainer, checkpointed streaming resume, a sparse SpecialTrie above about 1,000 specials, and cross-machine sharding (only past 100 GB-class streaming, M7).

What must never be false

Each line: the rule, then the detection check and the telemetry counter (§7). A deterministic runner, conformance/runner, drives one assertion per invariant at every CI run (§7, §28).

  • I1: ids 0 to 255 are the bytes, identity-mapped and immutable. Property test over all 256 values; vocab.reserved_range_violations.
  • I2: the merge count equals target_vocab - 256 - specials.len() when training ends. Phase 4 assertion; trainer.final_vocab_delta.
  • I3: training peak RAM is at most twice the dedup pre-token table. dhat peak-RSS harness; trainer.peak_rss_bytes.
  • I4: a loaded vocab is immutable, and a reader crash never corrupts it. File-hash check on load; vocab.load_checksum_mismatch.
  • I5: no special-token span is ever seen by the pre-tokenizer or by BPE. Fuzz target special_token_scan; encode.special_bypass_count.
  • I6: merges apply lowest rank first, ties broken left-most. Property test against minbpe; encode.tie_break_events.
  • I7: encode(bytes) is identical across thread count and machine for one merge table. proptest at 1, 4 and 16 threads; encode.nondeterminism_alerts (should be 0).
  • I8: a (pair, rank) entry is never mutated or removed once pushed. Append-only assertion; merge_table.mutation_attempts.
  • I9: equal-count pairs break by (left_id, right_id). Cross-thread-count parity test; trainer.tie_break_count.
  • I10: decode(encode(s)) == s for all valid UTF-8. proptest and the roundtrip conformance bucket; conformance.roundtrip_failures.
  • I11: save then reload in either format gives byte-identical encode output. CI gate conformance/format-roundtrip; conformance.format_roundtrip_failures.
  • I12: a reader never panics on malformed input; it returns a typed Error. Fuzz target format_roundtrip; reader.malformed_input_errors.
  • I13: MergeTable::push rejects a duplicate (left, right) pair. Phase 4 unit test; merge_table.duplicate_rejections.

What breaks in production

  • FM-1: an encode call panics. Cause: a violated arena invariant or unchecked slice index. Detected by fuzz or property-test failure and crash telemetry. No automatic recovery, since a panic is always a defect; patch the invariant check and add a regression fixture (§25).
  • FM-2: two training runs at different thread counts diverge. Cause: the I9 tie-break skipped or applied inconsistently across shards. Detected by the thread-count-determinism conformance bucket. Recovery: bisect with bpe diff and patch PairCounts::top (§25).
  • FM-3: the streaming trainer dies mid-run. Cause: scratch directory exhausted (T9) with no free-space precheck. Seen as a non-zero exit and an I/O error. Recovery: provision scratch space and restart from Pass 1, since checkpointed resume is deferred (§25, §37).
  • FM-4: a reader rejects a vocab file it should load. Cause: a malformed line, rank gap or vocab/merges mismatch. It returns a typed Error rather than panicking (P13). Recovery: inspect with bpe inspect or bpe diff, then regenerate or patch the file (§25, I12).
  • FM-10: a tokenizer.json load yields a different vocab than expected. Cause: a vocab/merges cross-reference mismatch. Detected as Error::UnknownToken at load or by hf-parity; load fails closed. Recovery: diff the two sections and patch the writer that produced them (§25, §18).

Threats worth knowing (§24):

  • T1 a crafted .tiktoken file with a multi-GB line, met by a per-line length cap and streaming reads (ADR-12); T2 is the same attack on tokenizer.json with a huge entry count.
  • T3 literal special-token text in untrusted input hijacking a prompt, met structurally by the trie boundary (P6) plus AllowedSpecial::Default erroring on unexpected literals.
  • T4 token-count amplification, inputs that never merge; the throughput floors (M1, M2) bound the cost and output size stays O(input length).
  • T7 corpus poisoning that skews merges toward attacker-chosen tokens, met by provenance logging and diffable merge tables (bpe diff).
  • T9 disk exhaustion from a compressed corpus that expands past scratch space, met by a pre-flight free-space check.

How it compares

  • OpenAI tiktoken is encode-only with no training and no special-token trie, trusting the caller for correctness. That fits a user who only consumes vocabularies someone else trained (§33).
  • HuggingFace tokenizers makes normalizers, pre-tokenizers and post-processors pluggable trait objects and trains single-process. That fits supporting dozens of heterogeneous model families in one library where a non-allocating hot path matters less (§33).
  • Google SentencePiece does no pre-tokenization, treats the whole input as one sequence, and ships a protobuf .model format. That fits languages without whitespace-delimited words (CJK), where a GPT-2-style regex does harm (§33).
  • fastBPE is char-level with OpenMP threads and a plain-text codes file. That suited single-script corpora when it was written, where byte level's UTF-8 safety bought nothing (§33).

If you only remember three things

The vocabulary starts as the 256 bytes and only ever grows by appended merges, which is why no unknown token exists and why ids stay valid forever (P1, P9, MM4). Special tokens are matched by a trie before any regex or merging, so the trust boundary is structural rather than a validation checklist (P6, MM3). Training scales by sharding counts and breaking ties by a fixed lexicographic rule, so the same corpus yields the same merge table at any thread count (ADR-07, I9, MM5).

Words used here

  • Token / TokenId: the integer a piece of text maps to; ids 0 to 255 are bytes, higher ids are merges (§8.1, §11.1).
  • Byte-level BPE: merging frequent adjacent pairs, starting from the 256 byte values (§38).
  • Merge: a rule "left id, right id gives new id" with a rank (§38).
  • Rank: when training minted a merge; lower rank is applied first when encoding (§38, MM2).
  • Pre-token: a span cut by the splitter inside which merges may happen (§8.3).
  • fancy-regex: the Rust regex engine with lookaround that runs the GPT-2 pattern (ADR-04).
  • Arena: a pre-allocated array holding the linked-list nodes, so merging does not allocate (§38).
  • Lazy invalidation: leaving stale queue entries and checking them only when popped (§38).
  • Special token: a literal such as <|endoftext|> matched at the input boundary, bypassing BPE (§8.5).
  • Shard: one partition of the corpus or pair-count map, handled by one rayon task (§38).
  • Tie-break: the fixed rule that picks among equal-count pairs, (left_id, right_id) ascending (§38, I9).
  • BPE-dropout: skipping a candidate merge with probability p at encode time, seeded (§38, §22).
  • Wire compatibility: a serialized vocab decodes identically forever across versions (§38, P9).
  • Round-trip: decode(encode(s)) == s for valid UTF-8 (§38, I10).
