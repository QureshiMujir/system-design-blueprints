34. Back-of-Envelope Capacity Model

  1. Encode throughput floor (M1) = 200 MB/s ⇒ a 1 GB prompt corpus encodes in 1e9 / 2e8 = 5 s single-core.
  2. DFA throughput ceiling (M4) = 500 MB/s ⇒ the same 1 GB corpus in 1e9 / 5e8 = 2 s — the 2.5× win the DFA (§20) buys.
  3. Encode p99 latency (§4) for a 1 KB input at M1's 200 MB/s floor: 1024 bytes / 2e8 B/s = 5.12 µs theoretical; the stated 60 µs p99 budget leaves ~12× headroom for queueing/priority- queue overhead (§14) — this is why §4's number is 60 µs, not 5 µs.
  4. Training wall-clock (M6): 1 GB corpus, 16 cores, target ≤10 min ⇒ required aggregate throughput ≥ 1e9 bytes / 600 s = 1.67 MB/s per core-equivalent minimum, well under M1's single-core encode floor — training's pair-count-and-merge loop is the bottleneck, not raw byte throughput, hence the separate M6 target rather than reusing M1.
  5. Dedup pre-token table size (I3, §21): a 10 GB corpus with ~10–50M unique pre-tokens at ~30 bytes average (bytes + count + hash overhead) ⇒ 30M pretokens × 30 bytes = ~900 MB, comfortably under 64 GB RAM even at 2× peak (I3).
  6. 100 GB streaming corpus (M7): at the same dedup ratio (~1:20 raw-to-unique), dedup table ≈ 100GB / 20 × 30bytes/pretoken_avg_ratio ≈ ~9 GB — well under the 64 GB RAM budget, confirming M7's memory feasibility before the mmap fallback is ever needed.
  7. Special-token scan cost (M8): 100 MB/s floor, 16 tokens averaging 12 bytes ⇒ trie depth ≤12 ⇒ worst-case per-byte cost is one [u16;256] lookup per trie level ⇒ 100MB/s is achievable when most bytes exit within 1–2 trie steps (§19.7's non-match-fast-path claim).
  8. Trie memory (§19.6): 16 specials × 512 bytes/node × ~12 nodes/token average ⇒ 16 × 512 × 12 ≈ 98 KB — matches the "~100 KB" figure asserted at §19.6, derived here rather than asserted there.
  9. cl100k_base load time (M10): ~100,277 merges, each requiring one find_pair_for_bytes scan bounded by average token length (~4 bytes) against a growing vocab ⇒ 100,277 × O(4) ≈ 400K basic ops, comfortably inside the 1 s budget even accounting for base64 decode and I/O.
  10. Fan-out × rate ceiling for encode-serving: at M1's 200 MB/s per core and a typical 512- byte prompt, one core serves 2e8 / 512 ≈ 390,625 prompts/s theoretical ceiling before any model-inference cost dominates — this bounds how much tokenizer throughput ever matters relative to the downstream model's own latency.

Every number above chains from §4's constraint table; none is asserted without the arithmetic shown.
