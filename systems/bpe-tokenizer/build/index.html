⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the full repository (§10) as stubs; ship a single-threaded, quadratic-but-correct training + encode/decode path; prove the byte-level round-trip on a toy corpus. No parallelism, no priority queue, no GPT-2 regex yet — those are later phases. This phase exists so every later phase lands on working scaffolding, per §7's "Phase 0 stands up the repo skeleton + correctness kernel" contract.

Deliverable

make bootstrap && make build && make test green; cargo run --example hello-world trains a 306-token vocab (256 + 50 merges) on a 10,240-byte Lorem Ipsum fixture, encodes "hello world", "the quick brown fox", and an emoji string, decodes each, and asserts byte-exact round-trip (I10).

Acceptance

examples/hello-world passes as tests/integration/hello_smoke.rs; round-trip is byte-exact for all 3 fixture strings; ADR-01, ADR-02, ADR-11, ADR-14, ADR-20, ADR-21, ADR-22 filed under docs/adr/; BUILD_PLAN.md shows Phase-0 Status: complete.

Fixtures

conformance/corpora/ascii/lorem-10k.txt (10,240 bytes) — purpose: Phase-0/Phase-3 smoke corpus; expected: 306-token vocab, byte-exact round-trip on the 3 hello-world strings.

Pitfalls

The byte alphabet must be initialized exactly once (I1); a bug that re-inserts ids <256 after a Vec::clear() makes id 0 mean two bytes and silently diverges every later encode. min_pair_count defaults to 2 (a hapax pair compresses nothing) — do not default to 1. Resist shipping the GPT-2 regex here; if the smoke test fails, the bug must be isolated to the training loop, not entangled with regex correctness (Phase 1).

⬜ Phase 1 — Byte-Level Alphabet Finalization & GPT-2 Pre-Tokenizer §13

Objectives

Replace WhitespacePretokenizer with Gpt2Pretokenizer (P2, ADR-03, ADR-04); finalize the byte-alphabet display mapping (§8.1); ship Llama3Pretokenizer as a second concrete Pretokenizer to prove the trait (§11.5) is genuinely pluggable.

Deliverable

Gpt2Pretokenizer producing byte-identical spans to HuggingFace's GPT-2 tokenizer on the 10K corpus; benchmarks/regex_engine.rs measuring throughput.

Acceptance

Pre-tokenization span parity 100% on the 10K-document corpus (named fixture conformance/corpora/unicode/pretok-parity-10k.bin); throughput ≥ 100 MB/s ASCII, ≥ 50 MB/s mixed-Unicode single core (M1/M2 predecessors, tightened at Phase 8); partition test — every input byte in exactly one pre-token, in order.

Fixtures

pretok-parity-10k.bin — 10K documents; expected: span-for-span match vs. HF GPT-2 tokenizer. malformed-utf8-boundary.bin — chunk-split mid-codepoint; expected: no panic, re-validated at &str boundary (I12).

Pitfalls

\s+(?!\S) requires lookbehind the stdlib regex crate rejects at compile time (ADR-04) — a regex::Regex::new attempt wastes an afternoon. fancy-regex's Unicode tables track Unicode version; pin Cargo.lock and document the version (a silent bump shifts \p{L} membership).

⬜ Phase 2 — Encode Hot Path: Arena, Doubly-Linked Pre-Token, Priority Queue §14

Objectives

Replace Phase-0's O(n²) encoder with the O(n log n), allocation-free hot path (P11, ADR-05, ADR-06); this is the phase that makes §4's M1–M3 targets reachable.

Deliverable

encode_into verified zero-allocation per pre-token on a 10K-pre-token batch; a differential test asserting output equality between the Phase-0 quadratic encoder and the Phase-2 heap-driven encoder on a 100K-input corpus.

Acceptance

Encode throughput ≥ 200 MB/s ASCII, ≥ 100 MB/s mixed-Unicode single core (M1, M2 — hard CI gate in benchmarks/encode_throughput.rs); zero heap allocations per pre-token in encode_into steady state (M3, dhat-verified); Phase-0-vs-Phase-2 output equality 100% on the 100K-input corpus (named fixture conformance/corpora/roundtrip/quadratic-vs-heap-100k.bin).

Fixtures

quadratic-vs-heap-100k.bin — 100K arbitrary inputs; expected: identical Vec<TokenId> from both encoders. dhat-zero-alloc.json — dhat snapshot; expected: 0 blocks in encode_one_pretoken steady state.

Pitfalls

Lazy-invalidation missing the next == right_node clause merges across an already-merged span silently (I6 violation) — the three-clause check is mandatory, not two. insert_seq is required for determinism (I7); without it, BinaryHeap's tie-break is undefined and violates I6's left-most rule. EncoderScratch must be thread-local, not stack-local — the RefCell borrow is the cheap path (P11).

⬜ Phase 3 — Parallel Training & Sharded Pair-Count Reduce §15

Objectives

Parallelize training across cores (P4, P10, ADR-07); replace Phase-0's single-threaded loop with a rayon-driven, sharded-reduce pipeline meeting the M6 throughput target.

Deliverable

A trainer completing a 32,000-vocab run over a 1 GB corpus in ≤10 minutes on 16 cores; merge table matches minbpe's on the parity corpus.

Acceptance

Training throughput: 1 GB corpus, 32K vocab, ≤10 min on 16 cores (M6, hard CI gate on a benchmark runner); merge-table equality vs. minbpe 100% on the 10K-document parity corpus (named fixture conformance/corpora/roundtrip/minbpe-parity-10k.bin); byte-identical merge table across 1/4/16 thread counts on a fixed-seed corpus (I7).

Fixtures

minbpe-parity-10k.bin — expected: merge-table equality with minbpe reference output. thread-count-determinism.bin — same corpus trained at 1/4/16 threads; expected: byte-identical MergeTable (I7, I9).

Pitfalls

Determinism under parallelism is load-bearing (P3): tie-breaking must be lexicographic on (left_id, right_id) (I9), never "first observed" (that depends on rayon's scheduler and corpus-reader chunk size — nondeterministic). The delta FxHashMap should be clear()d and reused between epochs, not reallocated (large corpora produce millions of entries/epoch). A decrement to zero must remove the entry from PairCounts, not leave a phantom zero (top() would otherwise return it).

⬜ Phase 4 — Deterministic Tie-Breaking & Merge-Selection Hardening §16

Objectives

Close Phase 3's tie-breaking gap explicitly (I9) and harden MergeTable::push against duplicate pairs (I13, ADR-05's uniqueness precondition for encode-time rank lookups).

Deliverable

A test suite proving tie-breaking is deterministic across shard counts and across repeated runs with engineered multi-way ties.

Acceptance

Two trainer runs with different shard counts (4 vs. 16) on the same corpus produce byte-identical merge tables (I7, I9) — 100% match, named fixture conformance/corpora/roundtrip/shard-count-determinism.bin; an engineered 5-way-tie corpus produces the documented lexicographic winner every run (10/10 repeated runs); MergeTable::push rejects 100% of duplicate-pair injection attempts in the unit suite.

Fixtures

shard-count-determinism.bin — expected: identical merge table at 4 vs. 16 shards. five-way-tie.bin — a corpus engineered so 5 pairs tie at every epoch; expected: lexicographic winner per I9, every run.

Pitfalls

"First observed wins" is a tempting but wrong tie-break (some reference tools use it) — it is not deterministic across thread counts because observation order depends on rayon's scheduler and the corpus reader's chunk size. minbpe's tie-break is first-observed, so exact parity with minbpe is only well-defined on corpora engineered to avoid ties (documented in conformance/corpora/README.md, not a Phase-4 defect).

⬜ Phase 5 — The `tiktoken` On-Disk Format §17

Objectives

Ship a reader/writer for OpenAI's .tiktoken line format (ADR-08, P5, P7); establish parity against the four vendored reference vocabularies.

Deliverable

A reader loading cl100k_base.tiktoken (~100K merges) in ≤1 s; a writer that round-trips a trained tokenizer through .tiktoken with byte-identical merges and encodes.

Acceptance

Load time for cl100k_base.tiktoken ≤1 s (named benchmark, hard gate); round-trip (train → write_tiktoken → read_tiktoken → encode) byte-identical to direct-encode on a held-out 10K-document corpus (I11); parity vs. the OpenAI reference encoder 100% on all four vendored vocabularies (tiktoken-parity bucket, 4 sub-buckets).

Fixtures

cl100k-load-1s.bin — timing fixture; expected ≤1 s. tiktoken-parity/{r50k,p50k,cl100k, o200k}.expected.bin — captured reference-encoder output; expected: 100% id match.

Pitfalls

find_pair_for_bytes is genuinely ambiguous when multiple prefix/suffix splits are already in the vocab — the documented resolution (lowest right-hand rank) must match what the reference tool effectively encodes, or parity silently breaks on a subset of merges. Standard vs. URL-safe base64 are different alphabets — .tiktoken uses standard/padded (RFC 4648); the wrong flavor produces decode errors on bytes ending +///=. A rank sequence with a gap (256, 257, 259 skipping 258) is malformed and must be rejected (I12), not silently renumbered.

⬜ Phase 6 — The HuggingFace `tokenizer.json` Format §18

Objectives

Ship a reader/writer for the HF tokenizer.json schema subset this system supports (ADR-08, P5, P7); prove format-equivalence with .tiktoken (I11).

Deliverable

A reader loading HF's gpt2/tokenizer.json and encoding a held-out corpus identically to the reference tokenizers Rust crate; a bpe convert CLI subcommand bridging both formats.

Acceptance

hf-parity bucket 100% on the GPT-2 held-out corpus; format-roundtrip (.tiktoken → tokenizer.json → encode) byte-identical to direct .tiktoken encode on the same corpus (I11, named fixture conformance/corpora/format-roundtrip/tiktoken-to-hf-10k.bin); JSON whitespace may differ, but every encoding-relevant field is preserved (documented diff policy).

Fixtures

hf-parity/gpt2.expected.bin — captured HF tokenizers crate output; expected 100% id match. tiktoken-to-hf-10k.bin — round-trip corpus; expected byte-identical encode both directions.

Pitfalls

The byte-display mapping (§8.1) is the most common bug source: a token [0x20, 0x68, 0x65, 0x6c, 0x6c, 0x6f] (" hello") displays as "Ġhello" in tokenizer.json; an unreversed mapping loads a vocab missing " hello" and containing the display string instead, silently breaking every downstream encode. vocab and merges must agree — a merges entry referencing a byte-string absent from vocab is a load-time error, not a skip.

⬜ Phase 7 — Special Tokens & the Byte-Trie §19

Objectives

Implement SpecialTrie (§11.8, P6, ADR-09) and the input-boundary scan that isolates special tokens from both the regex pre-tokenizer and BPE (I5); implement the Regular/Optional prompt-injection defense (T3).

Deliverable

A working special-token pipeline: <|endoftext|> and family bypass BPE entirely when allowed; a fuzz target proving the regex pre-tokenizer never observes special-token bytes.

Acceptance

Scan throughput ≥100 MB/s single core, 16-special-token list (§4 gate, named benchmark); <|endoftext|> encodes to exactly 1 id when allowed, to len(bytes) byte ids when disallowed (100% pass on special-tokens conformance bucket); overlapping specials (<|im_start|> vs. <|im_start|>system) resolve to the longest match, 100% of engineered overlap cases.

Fixtures

special-tokens/overlap-matrix.bin — every (input, allowed_special setting) combination; expected ids per cell. special-tokens/endoftext-bypass.bin — expected: single id, never decomposed bytes, when allowed.

Pitfalls

Folding the special-token alternation into the pre-tokenization regex is the classic mistake (rejected explicitly at ADR-09): a literal <|endoftext|> would chop into <,|,endoftext, |,> and BPE-merge wrongly. The [u16; 256] node is 512 bytes; with 16 typical specials the trie is ~100 KB — acceptable, but a 1000+-special deployment should switch to a sparse representation (PhaseDeferred("§19") — documented, not built in current scope).

⬜ Phase 8 — The DFA Pre-Tokenization Splitter §20

Objectives

Ship a hand-rolled DFA (P8, ADR-04's documented optimization path) implementing the GPT-2 pattern at 2.5–5× fancy-regex's throughput, behind a feature flag, without changing the pre-tokenizer contract (§11.5).

Deliverable

A DfaSplitter byte-identical to Gpt2Pretokenizer on the 10K-document parity corpus, at the higher throughput target.

Acceptance

Throughput ≥500 MB/s ASCII, ≥250 MB/s mixed-Unicode single core (M4, M5 — hard CI gate under the dfa feature); 100% span parity vs. Gpt2Pretokenizer on the 10K-document corpus (named fixture conformance/corpora/unicode/regex-vs-dfa-10k.bin); zero divergences found by the regex_vs_dfa fuzz target after a 3-hour nightly run.

Fixtures

regex-vs-dfa-10k.bin — expected: identical spans, both engines. dfa-fuzz-corpus/ — seed corpus for the differential fuzz target.

Pitfalls

Anything past 2 Unicode planes in the bitmask wastes binary size on scripts no realistic corpus tokenizes — cap at planes 0–1 deliberately (a documented, not accidental, coverage limit). The whitespace-trailing state is the trickiest: it must distinguish "whitespace run followed by EOF/non-whitespace" from "whitespace run immediately followed by more whitespace," exactly mirroring \s+(?!\S) vs. \s+.

⬜ Phase 9 — Streaming & Large-Corpus Training §21

Objectives

Break Phase 3's implicit RAM-resident assumption (P4); make training scale to corpora larger than RAM via external sort, meeting the M7 target (100 GB, ≤4 h, 32 cores, 64 GB RAM).

Deliverable

A trainer producing a 50K-vocab tokenizer over a 100 GB corpus in ≤4 h on 32 cores / 64 GB RAM, with peak RAM bounded by I3.

Acceptance

100 GB corpus, 50K vocab, ≤4 h wall time, 32 cores, 64 GB RAM (M7, hard gate on the streaming benchmark); peak RSS ≤2× dedup-table size regardless of raw corpus size (I3, dhat-verified); merge-table equality vs. the in-RAM Phase-3 trainer on a 10 GB synthetic corpus (named fixture conformance/streaming/10gb-parity.bin).

Fixtures

streaming/10gb-parity.bin — expected: merge table identical to in-RAM trainer on the same corpus. streaming/scratch-exhaustion.bin — a corpus sized to fill a constrained scratch volume; expected: a typed I/O error, not a silent truncation.

Pitfalls

O_DIRECT is tempting for the external-sort merge phase; resist — the page cache helps sequential run reads, and posix_fadvise(POSIX_FADV_SEQUENTIAL) is the correct hint instead. Trainers have died at hour 3 from /tmp filling up — the 60–80% free-space rule belongs in the runbook, checked before a multi-hour run starts, not discovered mid-run.

⬜ Phase 10 — BPE-Dropout & Subword Regularization §22

Objectives

Implement encode_with_dropout (Provilkov et al. 2019 per §5, ADR-10) as an encode-time regularizer: each candidate merge is skipped with probability p, seeded for determinism (P3's documented exception).

Deliverable

A dropout-aware encode path that is byte-identical to the plain encoder at p=0, and reproducible per (seed, p, input) triple.

Acceptance

p=0 byte-identical to encode on the full 100K-input regression corpus (100% match); 1,000 runs of encode_with_dropout(input, 0.1, random_seed) produce no two identical outputs (statistical, false-positive rate documented ≤0.1%) and every output decodes back to the input (I10); dropout-encode throughput within 20% of plain encode (named benchmark benchmarks/dropout_overhead.rs).

Fixtures

dropout/p0-identity.bin — expected: byte-identical to encode. dropout/seed-reproducibility. bin — same (input, p, seed) triple, 100 repeated calls; expected: identical output every time.

Pitfalls

BPE-dropout is a training-time regularizer in Provilkov et al.'s original design; shipping it as an encode-time option (so callers can apply it without retraining) does not reproduce the paper's exact reported numbers unless the downstream model is also trained under dropout — document this distinction loudly, it is a common misreading. Skipping a merge does not require re-queuing the skipped pair's neighbors — the pair simply does not fuse for this call.

⬜ Phase 11 — Fuzzing, Property Testing & Conformance Hardening §23

Objectives

Reach the "no panic, no UB, no round-trip failure, no parity drift" bar across arbitrary input before calling the system 1.0; this phase is the release gate, not a feature.

Deliverable

Four fuzz targets runnable via cargo fuzz run <target>; a conformance.report.json-emitting runner wired into CI as a hard gate; a nightly 12-hour fuzz job auto-filing an issue on any crash.

Acceptance

Zero panics across a 3-hour CI fuzz budget per target (hard gate, RUSTFLAGS="-C debug-assertions" per ADR-18); conformance.report.json shows failed: 0 across all 9 buckets (ascii, unicode, roundtrip, tiktoken-parity, hf-parity, special-tokens, dropout, streaming, format-roundtrip) on every merged PR; nightly 12-hour fuzz run produces zero new crashes for two consecutive nights before a release tag.

Fixtures

conformance.report.json itself (schema-validated against report_schema.json) is the aggregate fixture; each bucket's own named fixtures are listed in their originating phase (§12.5–§22.5).

Pitfalls

proptest's shrinking toward minimal failing inputs tends to land on UTF-8 sub-codepoint edge cases — do not special-case these away; they are exactly the bugs worth finding. The conformance corpus accumulates over releases; a bucket failing on the current corpus but passing on the prior tagged corpus is a real regression signal, not noise — track it, do not suppress it.
