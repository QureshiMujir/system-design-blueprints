Project Number: 172

Project Name: Game Engine Core (ECS + Main Loop)

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

A from-scratch game engine core in Python: an archetype-based Entity-Component-System (ECS) with dense per-archetype component storage, a system scheduler that infers safe parallel execution from statically-declared read/write access sets, a fixed-timestep simulation loop decoupled from a variable-rate render loop via state interpolation, a typed double-buffered event/message bus, a handle-based resource/asset manager with reference counting and hot reload, a scene graph with transform hierarchy and dirty-flag propagation, a data-driven prefab/serialization layer, and a frame-profiling harness. This is the substrate every game subsystem plugs into — not a game.

Phase-0 deliverable, as packages:

  1. gecore.entities — entity allocator, generational handles.
  2. gecore.storage — archetype registry, dense columns, archetype graph.
  3. gecore.query — query engine, filters, change detection.
  4. gecore.scheduling — system descriptors, access analysis, schedule/stage graph.
  5. gecore.loop — fixed/variable main loop, tick accumulator, interpolation.
  6. gecore.events — typed double-buffered event bus.
  7. gecore.resources — resource/asset manager, handles, hot reload.
  8. gecore.scenegraph — transform hierarchy, dirty propagation.
  9. gecore.serialization — prefab format, MessagePack/JSON codecs, versioning.
  10. gecore.profiling — frame profiler, conformance harness.
  11. gecore.seams — physics and render integration contracts only (no physics/render logic).

Boundaries. Provides: entity/component storage, query engine, scheduler, main loop, event bus, resource manager, scene graph, prefab/serialization, profiler, the seam contracts consumed by sibling engines. Delegates: rigid-body dynamics, collision detection, and constraint solving to Physics-Engine (#171), which reads Transform/GlobalTransform and writes back through a RigidBodyHandle component and the PhysicsSync schedule stage (§3, §8, ADR-18); rasterization and the render pipeline to Software Rasterizer (#169), which consumes an immutable RenderFrame snapshot produced by an Extract stage (§3, §8, ADR-19). Does NOT provide: collision detection, rasterization, audio DSP, networking/replication transport, a scripting VM, or an editor GUI.

Non-goals. Rendering pixels; solving constraints; audio; network replication; a visual editor; a general scripting language runtime (a script-hook seam is deferred, PhaseDeferred("§37")).

Deployment model. An importable library (pip install gecore), embedded in a host process. A headless mode runs the World and Schedule with no render seam attached (servers, CI, tests); there is no daemon, no network listener, no service boundary of its own.

Users/operators. The game engineer composing systems and prefabs on top; the engine maintainer debugging the scheduler or storage; the CI operator gating merges on the conformance and performance suites (§28, §30).

What later phases unlock. Phase 6 (§18) makes Physics-Engine's fixed-tick dynamics safe to interleave with gameplay systems; Phase 9 (§21) makes Software Rasterizer's extract step well-defined; Phase 10 (§22) makes a shippable save format and deterministic replay possible; a sample game and a native execution core are unlocked but out of scope (PhaseDeferred("§37")).

Language + rationale. Python 3.12: CPython's data model (__slots__, the buffer protocol, array/numpy structured arrays) is sufficient to express dense archetype columns; the language's introspection and dynamic typing make the query/scheduler access-analysis machinery (§8, §11) short to write and easy to teach, which is the actual point of this blueprint. Honest cost: the Global Interpreter Lock (GIL) means CPU-bound systems do not gain wall-clock speedup from threads (§9 D.4, ADR-08); Python's tracing garbage collector introduces non-deterministic pause latency (§4 states the tolerance explicitly). Mitigations: the scheduler's access-analysis API (§11, Phase 6) is designed so a native execution core (Cython/Rust extension implementing the same Access/Schedule contract) can replace the pure-Python executor later without changing system authoring (PhaseDeferred("§37")); per-frame allocation is minimized (pooled CommandBuffers, batched structural changes, gc.freeze() after warm-up per ADR-08) to bound GC pause frequency. Rejected languages: Rust — the correct choice for a production engine (see Bevy) but this project's value is teaching ECS/scheduler/data-oriented-design mechanics with maximum introspectability, which Python provides more directly; C++ — manual memory management cost is not justified by the pedagogical goal here.

Prerequisites. Cache/memory-hierarchy reasoning (Hennessy & Patterson, §5); CPython object model and GIL semantics; basic transform math (matrices, quaternions) — deferred in depth to Physics-Engine (#171) and Software Rasterizer (#169).

Timeline. Phase 0: 2 weeks. Full 12-phase system (Phase 0–Phase 11): 7–9 months part-time.

Deferrals. PhaseDeferred("§37") — native execution core; scripting-hook seam; full editor GUI; networked/lockstep replication transport; a shipped sample game. All registered in §37.

2. Why Build This

  • Learn ECS as a column-store database with a frame-rate deadline, not a class hierarchy.
  • Learn scheduler design: static access analysis, conflict graphs, safe parallelism — directly transferable to any data-parallel runtime.
  • Learn why simulation must run on a fixed timestep and why coupling it to render rate breaks determinism (Fiedler, §5).
  • Learn data-oriented design under a language (Python) that actively resists it — the friction teaches the principle better than a language that gives you structs-of-arrays for free.
  • Learn resource-lifetime management with generational handles instead of raw references.
  • Learn scene-graph dirty propagation as a general incremental-recomputation pattern.
  • Cross-links: Physics-Engine (#171) and Software Rasterizer (#169) are the two consumers this blueprint's seams are built for; NUMA Memory Manager and Cache Coherence Protocol blueprints cover the memory-hierarchy reasoning in more depth than repeated here.

What Mastery Looks Like

  • Explain why an entity is index+generation and never a pointer, and reproduce the failure a pointer-based design hits (Phase 0, §12).
  • Derive the archetype-move cost for adding a component and know when sparse-set beats it (Phase 1, §13; §36).
  • Build a query engine whose iteration cost is linear in matching entities, not total entities (Phase 2, §14).
  • Explain why systems declare data access statically instead of the scheduler inferring it from runtime traces (Phase 6, §17; P6).
  • Derive the fixed-timestep accumulator's spiral-of-death clamp and why render must interpolate, never adapt to the simulation (Phase 4, §16; P2).
  • Reason about hot reload without invalidating in-flight handles (Phase 8, §19; ADR-13).
  • Explain why structural changes are deferred to a sync point and what breaks if they aren't (Phase 5, §17; I4).
  • Run a deterministic-replay differential test and interpret a divergence (Phase 10, §21; §28).

Platform/Window Layer — trust boundary for raw OS input; converts to typed PlatformEvents, never touches the World directly. Main Loop — owns the persistence-free frame lifecycle state machine (§8.11); the only place real time crosses into simulation time. Scheduler — pure function of SystemDescriptor access sets to a Schedule; concurrency boundary is here, not in World. World / ArchetypeRegistry — the single mutable state owner; a persistence boundary only via the serialization layer. CommandBuffer — the queue where concurrency resolves back to single-writer semantics before any archetype move. EventQueue — a lossy, bounded, two-frame channel; not a durable log. ResourceManager — the asset trust boundary: file-watch and deserialization inputs are untrusted (§24). SceneGraph — a derived-data cache invalidated by dirty flags, never a second source of truth. Prefab/Serialize — the only durable-persistence boundary; MessagePack/glTF cross the process boundary. Profiler — read-only observation, never mutates World state. Physics/Render seams — protocol boundaries to sibling engines; this blueprint owns only the component/stage contract, not the algorithms behind it.

6. Design Principles

P1 — Components are data, systems are behavior. A component with a method is a design defect: it hides an access pattern the scheduler cannot see, forcing either a scheduler exception or a silent race. Tradeoff: pure-data components require systems for every behavior, more boilerplate. Operational implication: code review rejects any method on a component beyond __eq__/__repr__.

P2 — Simulation runs on a fixed timestep; the renderer interpolates, never the reverse. Coupling simulation rate to display rate makes physics non-deterministic across hardware. Violating it: a game that "feels different" on a 144 Hz monitor than a 60 Hz one, and lockstep replay diverges immediately (§8 accumulator algebra, Phase 4 §16).

P3 — An entity reference is a generational handle, never a pointer. The alternative is a use-after-free you cannot see: a stale Entity silently pointing at a reused slot. Enforced by I1; detection is a generation mismatch, not a segfault.

P4 — Storage layout is the whole performance story. Same-type components live together in dense columns; iterating a query touches only the bytes it needs. Violating it (component-per- object storage) drops cache hit rate an order of magnitude (§34).

P5 — Structural changes are deferred to a command buffer, applied at a defined sync point. Mutating archetype membership mid-iteration invalidates the iterator silently. Enforced by I4; detection is a mid-iteration archetype-generation check that raises CommandReplayError.

P6 — Systems declare data access statically; the scheduler infers parallelism. Inferring access from runtime traces is unsound (a conditionally-executed write is invisible until it happens). Static declarations at SystemDescriptor registration make the DAG buildable once, verifiable, and testable in isolation (P6, I3, ADR-07).

P7 — Determinism is the default execution posture, not an opt-in mode. Fixed timestep + insertion-order-stable system ordering + seeded per-stream RNG together make "same inputs, same outputs" the normal case. Breaking any one silently breaks replay and lockstep (§27, ADR-20).

P8 — Ordering is explicit, never magic. Stages provide coarse ordering; within a stage, only declared data conflicts or explicit .before()/.after() edges impose order. An engine that infers "system A probably wants to run before B" is undebuggable.

P9 — Assets are handles, never raw objects. A Handle decouples "the game holds a reference" from "the bytes are loaded"; hot reload swaps bytes behind a stable handle without invalidating holders. Skipping this makes hot reload require restarting every subsystem that cached a raw pointer (P9, ADR-09/ADR-13).

P10 — Change detection is a tick comparison, not a value diff. Comparing values for every component every frame is O(total data); comparing a per-column change tick against a system's last-run tick is O(1) per query and catches every write, no exceptions (§8, ADR-06).

P11 — Scene-graph propagation is incremental, driven by dirty flags. Recomputing every GlobalTransform from the root every frame is O(nodes) regardless of what moved; dirty propagation is O(changed subtree) (I6, Phase 9 §20).

P12 — Fail loud in development, degrade predictably in release. Debug builds assert every invariant (I1–I14) eagerly; release builds strip assertions but keep the recovery paths of §25 — an engine that panics identically in both modes has no operational story.

P13 — Query-engine and scheduler complexity live in the engine, not in game code. A system author writes a plain function with typed parameters; the engine, not the author, resolves access sets, iteration strategy, and parallel safety (P6, P13, §11).

P14 — Be honest about Python's concurrency model. The GIL means threads do not parallelize CPU-bound systems; the scheduler's contract is designed to be substrate-agnostic (native core swap-in later) rather than to fake parallelism with threads today (§1, ADR-08, §31 Amdahl reasoning).

8.5 Command-buffer contract

CommandBuffer holds Command variants: Spawn(Bundle), Despawn(Entity), Insert(Entity, ComponentId, bytes), Remove(Entity, ComponentId), SetParent(Entity, Entity). Applied FIFO per system, systems applied in the stage's declared execution order (deterministic, P7); applied exactly at the stage's sync point (I4), never mid-system.

8.6 Fixed-timestep accumulator algebra

accumulator ← accumulator + min(real_dt, MAX_FRAME_DT)          // I5 clamp on input
n ← 0
while accumulator ≥ tick_dt and n < MAX_TICKS_PER_FRAME:
    simulate(tick_dt); accumulator ← accumulator − tick_dt; n ← n + 1
if n = MAX_TICKS_PER_FRAME and accumulator ≥ tick_dt:
    accumulator ← 0                                              // spiral-of-death clamp
alpha ← accumulator / tick_dt                                    // interpolation factor, [0,1)
render_state ← previous_state + alpha × (current_state − previous_state)

8.7 Event-bus delivery semantics

Double-buffered per EventId: send(e) appends to current; read() iterates previous ++ current; a Last-stage swap_buffers moves current → previous, clears the new current — visible for exactly two frames (I8), then dropped (never a durable log).

8.8 Resource-handle and refcount model

ResourceHandle{index, generation} indexes an AssetSlot{refcount, generation, LoadState, bytes}. acquire increments refcount; release decrements (I9). Hot reload increments AssetSlot generation without changing index; holders detect staleness by comparing their handle's generation against the slot's on next access and re-resolve.

8.9 Scene-graph dirty-propagation rules

Writing Transform.local sets the entity's dirty flag; propagation marks every descendant dirty transitively (transitive closure over Children, bounded by §4 depth ceiling). PostUpdate's propagate_transforms system visits dirty nodes in parent-before-child (topological, depth-order) sequence, recomputing GlobalTransform = parent.GlobalTransform × local_matrix; a node with neither its own nor an ancestor's dirty flag set is skipped (memoization, P11).

8.10 Malformed-input examples

  • Prefab referencing an unregistered component name → PrefabValidationError at PrefabLoader.validate, no partial entity created (I11).
  • Prefab declaring SetParent(child, child) or a parent cycle → CyclicParentError, the whole prefab load aborted, not partially applied (I12).

12. Phase 0 — Skeleton + Entity Allocator + CI

12.1 Objectives

Stand up the repo skeleton (§10), the packaging (pyproject.toml), CI (§10 .github/workflows/), and the correctness kernel: EntityAllocator with generational handles. No storage, no scheduler yet — this phase proves the identity model (§8.1) in isolation.

12.2 Detailed Implementation Steps

Implement gecore.entities.entity.Entity as a packed 64-bit int per §8.1's bit layout (I1). Implement EntityAllocator (§11) with meta: list[EntityMeta] and free: list[u32]; spawn() pops from free or appends, despawn(e) validates generation (I1), increments it, pushes the index to free. Apply P3 (never a pointer) by construction — Entity carries no reference to storage. Wire pyproject.toml (ADR-01 Python 3.12), pytest+Hypothesis (ADR-24), and ci.yml (ADR-26 OS×version matrix). Add the generation-wrap guard (I14): a per-slot counter that raises a warning telemetry event, never silently reuses past GENERATION_WRAP_CEILING.

12.3 Deliverable

gecore.entities importable; pytest green in CI on the OS×Python matrix; a script (examples/headless_tick_demo, stub) that spawns 1,000 entities, despawns 500, respawns 500, and asserts no stale handle resolves.

12.4 Acceptance Criteria

1,000 spawn / 500 despawn / 500 respawn cycle completes in ≤ 5 ms; zero stale-handle resolutions across 10,000 randomized spawn/despawn sequences (Hypothesis property, fixture entity_allocator_property.py); CI matrix (3 OS × 2 Python minor versions) green.

12.5 Conformance Fixtures

  • fixtures/entity_alloc_basic.json — spawn/despawn/respawn sequence, expected final live-set.
  • fixtures/entity_alloc_stale_handle.json — a handle held across despawn; expected StaleHandleError on lookup.
  • fixtures/entity_alloc_generation_wrap.json — forced wrap at a lowered test ceiling; expected generation_wrap_warning telemetry, slot retirement (I14).

12.6 Pitfalls

  • ABA via generation reuse — manifests as a stale handle silently matching a new entity; root cause: generation not bumped on despawn; debug via the entity_alloc_stale_handle fixture; signal: entity.stale_lookup should be nonzero, not the bug passing silently; recovery: assert generation bump happens before the slot re-enters free.
  • Free-list ordering causing cold-cache thrash — manifests as random-looking archetype row reuse later (Phase 1); root cause: LIFO vs FIFO free-list choice affects locality; debug via allocation-order tracing; signal: uneven archetype.row_count growth; recovery: prefer LIFO (most-recently-freed reused first) for cache warmth.
  • Off-by-one in the generation-wrap ceiling — manifests as a valid old handle briefly matching post-wrap; root cause: comparing > instead of >= at GENERATION_WRAP_CEILING; debug via the wrap fixture at a lowered ceiling; recovery: fix comparator, add regression fixture.

12.7 Performance Concerns

EntityAllocator.meta as a flat list avoids per-entity heap objects; spawn/despawn are O(1) amortized. Free-list as a Python list used as a stack (LIFO) avoids O(n) pop-from-front cost.

12.8 Edge Cases

Despawning an already-despawned entity (generation mismatch → StaleHandleError, not a crash); spawning past 2**32 total allocations without any despawns (index space exhaustion — document as the practical entity ceiling, cross-refs §31); despawn during iteration is not possible yet (no queries exist this phase) but the API is shaped to route through CommandBuffer from Phase 5 onward (P5) so no direct-mutation API is exposed even now.

12.9 Failure Analysis

A corrupted free list (duplicate index) would double-issue an Entity — detected by an assertion in debug builds comparing len(meta) against live-count + len(free); blast radius is local to EntityAllocator; recovery is to rebuild the allocator from the last known-consistent meta snapshot (no such snapshot exists pre-Phase-10, so this phase's CI treats the assertion failure as a hard test failure, not a runtime recovery path).

12.10 Operational Notes

Structured logging (ADR-21) emits entity.spawn/entity.despawn at debug level only (volume); entities.generation_wrap_warning at warning level always. No deployment topology yet (library, not a service). CI artifact: the fixture pass/fail table, archived per run for regression triage.

13. Phase 1 — Component Storage & Archetypes

13.1 Objectives

Implement dense per-archetype column storage and the archetype graph (§8.2). Prove P4 (storage layout is the whole performance story) and I2 (dense/contiguous) and I7 (memoized edges) with a working insert/remove path, still single-threaded, no queries yet.

13.2 Detailed Implementation Steps

Implement ComponentInfo registration (gecore.storage.component) assigning ComponentId sequentially, capped at the §4 ceiling (4,096); zero-sized types (is_zst) get a length-only column (no backing array) per the ZST optimization referenced in the original engine lineage. Implement Archetype (§11) with columns: dict[ComponentId, Column], each Column backed by a numpy structured array (ADR-02) sized to the archetype's row capacity, doubling on overflow. Implement ArchetypeRegistry.get_or_create(signature) — signature is the sorted ComponentId tuple (§8.2); implement add_edge/remove_edge memoization (I7, P4) so a repeated component-add/remove transition for the same source archetype is an O(1) dict lookup, not a signature recomputation. Insert/remove use swap-remove (I2): removing row r copies the last row's data into r and truncates, updating the moved entity's EntityMeta.location.

13.3 Deliverable

gecore.storage supports: register up to 100 component types, create archetypes, insert/remove components on live entities, with the archetype graph correctly memoized. A microbenchmark (benchmarks/query_throughput_bench.py, storage-only mode) reports row-insert/remove throughput.

13.4 Acceptance Criteria

Insert/remove round-trip (add Health, remove Health) returns an entity's row to a byte-identical archetype-relative state as before the round-trip on 10,000 randomized entities (property test, ties to I7 and the ADR-05 rationale); archetype-transition lookup after the first occurrence is O(1) — measured at ≤ 200 ns per subsequent transition (archetype_edge_bench.py); zero orphaned rows after 50,000 randomized insert/remove operations (archetype_stress.json).

13.5 Conformance Fixtures

  • fixtures/archetype_migration_basic.json — the §8.2 worked example, expected final archetype and row.
  • fixtures/archetype_edge_memoization.json — repeated transitions, expected O(1) after first.
  • fixtures/archetype_swap_remove.json — remove a middle row, expected last-row relocation and EntityMeta update (I2).
  • fixtures/archetype_malformed_signature.json — an unregistered ComponentId in a requested signature, expected ComponentNotRegisteredError.

13.6 Pitfalls

  • Archetype fragmentation from many rare component combinations — manifests as archetype count approaching the §4 ceiling with few rows each; root cause: too many near-unique entity compositions; debug via archetype.count gauge trend; signal: archetype.row_count median dropping toward 1; recovery: consolidate rare marker components into a bitset resource instead of per-entity archetype-differentiating components (documented pattern, not automatic).
  • Swap-remove reindex bug — manifests as a "ghost" entity whose EntityMeta.location still points at a stale row after a neighbor removal; root cause: forgetting to update the moved entity's metadata, only the removed one's; debug via the swap-remove fixture; recovery: always update both the removed and the relocated entity's metadata atomically.
  • ZST column miscount — manifests as row-count drift for archetypes containing only zero-sized components; root cause: a length-only column not incrementing alongside real columns; debug via a ZST-only archetype fixture; recovery: track row count on Archetype itself, not derived from any one column's length.

13.7 Performance Concerns

Column pre-sizing (doubling growth) amortizes insert cost to O(1); numpy structured arrays keep same-type fields contiguous (P4, Drepper §5) — cross-column access (two different components) is still two separate cache lines, which is why query iteration order (Phase 2) matters more than storage alone.

13.8 Edge Cases

Removing the only remaining component from an entity (moves it to the empty-signature archetype, not deleted — despawn is separate); adding a component the entity already has (no-op, must not double-insert); an archetype signature collision from insertion order — mitigated because signatures are stored sorted, so add-order never creates duplicate archetypes for the same set.

13.9 Failure Analysis

A corrupted column length (out of sync with Archetype.entities) surfaces as an index error on next access — caught at the Archetype row-count assertion (debug), degrades in release to a ArchetypeMismatchError rather than an out-of-bounds read; forensics: dump the archetype's signature, row count, and each column's length for the postmortem template (§10 docs/ failure-analysis/).

13.10 Operational Notes

archetype.count and archetype.row_count (per-archetype) exported as metrics (§26); the archetype-fragmentation-cleanup runbook (§10) documents the consolidation pattern above. No rollback concept yet (single-process, in-memory only until Phase 10 serialization).

14. Phase 2 — Query Engine & Iteration

14.1 Objectives

Build the typed query engine (§8.3): With, Without, Optional, Changed, Added filters, matched against the archetype cache (ADR-05), with iteration cost linear in matching entities (P13).

14.2 Detailed Implementation Steps

Implement QueryFilter/Query (§11); Query.matched_archetypes computed once against the registry and cached; invalidated by an ArchetypeRegistry version counter bumped on get_or_create of a genuinely new archetype (ADR-05) — not on every insert/remove, since those reuse existing archetypes after the first occurrence (I7). Implement change detection (gecore.query.change_detection) per ADR-06: each column carries a per-row change tick, bumped on write; Changed<T>/Added<T> compare against the querying system's last_run_tick (P10). Iterate matched archetypes in registration order (P7 determinism) — never a hash-order-dependent iteration.

14.3 Deliverable

Query objects usable standalone (no scheduler yet — Phase 3 wires them into systems); a benchmark demonstrating linear-in-matching-entities iteration cost independent of total world size.

14.4 Acceptance Criteria

Query over 100,000 matching entities among 1,000,000 total iterates at ≥ 50M component-reads/sec per core (§4 M1, query_throughput_bench.py); Changed<T> filter correctly yields zero results on a second identical-tick query with no intervening write (change_detection_no_write.json); query-cache invalidation triggers exactly once per genuinely new archetype across 10,000 randomized structural operations (query_cache_invalidation_property.py).

14.5 Conformance Fixtures

  • fixtures/query_with_without_optional.json — matrix of filter combinations against a fixed archetype set, expected matching entity sets.
  • fixtures/query_changed_added.json — write-then-query and query-then-write-then-query sequences, expected Changed/Added results.
  • fixtures/query_cache_invalidation.json — new archetype created mid-run, expected cache refresh on next query call.

14.6 Pitfalls

  • Iterator invalidation from a structural change mid-query — manifests as a skipped or duplicated entity when a system spawns/despawns while iterating; root cause: queries not yet gated behind the command-buffer sync point (fixed in Phase 5, but this phase must not expose a direct-mutation path that could trigger it); debug via a fixture that attempts mutation during iteration and expects it routed to a CommandBuffer instead; recovery: no direct mutation API surfaced from Query at all.
  • Stale query cache after silent archetype creation — manifests as a query missing newly-matching entities; root cause: cache invalidated on the wrong counter (row count instead of archetype count); debug via query_cache_invalidation fixture; recovery: invalidate strictly on ArchetypeRegistry version, not row mutations.
  • False Changed positives from write-without-modification — manifests as systems reacting to no-op writes; root cause: bumping the tick on every __setitem__ regardless of value equality; debug via a fixture writing the same value twice; recovery: accepted tradeoff per ADR-06 (documented, not silently "fixed" — see ADR-06's rejected-alternative column).

14.7 Performance Concerns

Query iteration walks archetypes smallest-columns-first is unnecessary for archetype storage (unlike sparse-set, §36) since matching archetypes are pre-filtered; the cost model is sum(matching_archetype.row_count), independent of non-matching archetypes or total entity count — this is the concrete difference from the rejected sparse-set alternative (ADR-03).

14.8 Edge Cases

A query matching zero archetypes (empty iteration, not an error); a query whose filter set references an unregistered ComponentId (raises ComponentNotRegisteredError at query construction, not at iteration); Changed<T> queried by a system that has never run before (last_run_tick = 0, everything counts as changed — documented, not a bug).

14.9 Failure Analysis

A cache-invalidation miss silently under-reports entities rather than crashing — the most dangerous failure mode in this phase because it is silent; mitigated by the query_cache_invalidation_property test running on every commit (§28) rather than relying on manual review; forensics: query.stale_iteration telemetry (I10) flags this at runtime too.

14.10 Operational Notes

query.stale_iteration and per-query matched-archetype-count exported as metrics; query construction logged at debug level with its filter signature for correlation with slow-frame traces (§26 tracing spans, per-system, cross-ref ADR-22).

15. Phase 3 — System Registration & Serial Schedule

15.1 Objectives

Introduce SystemDescriptor, Stage, Schedule (§11) and a purely serial executor — systems run in declared order within a stage, no parallelism yet (that's Phase 6). Prove the stage pipeline (§3 main-loop stages) end to end for the first time.

15.2 Detailed Implementation Steps

Implement SystemDescriptor.access as a declared, not inferred, Access (P6) — the system author states reads/writes explicitly at registration (auto-derivation from function type hints is a later ergonomic layer, not a phase-3 requirement, to keep this phase's scope to the scheduling contract itself). Implement Stage as an ordered list of SystemDescriptors; implement Schedule.build() performing the topological sort using explicit_before/explicit_after edges only (data-conflict-based edges arrive in Phase 6, ADR-07); raise ScheduleCycleError (I13) on a cyclic constraint. Wire the canonical stage order from §3: First, PreUpdate, FixedUpdate, Update, PostUpdate, Extract, Render, Last.

15.3 Deliverable

A Schedule executing a fixed stage order, serially, against a World; a demo registering movement_system and print_system (per the salvaged original demo intent) both running in declared order every call.

15.4 Acceptance Criteria

A 100-system schedule builds (topological sort) in ≤ 5 ms (§4); a deliberately cyclic before/after constraint raises ScheduleCycleError naming the exact cycle (schedule_cycle_detection.json); system execution order is byte-identical across 100 repeated runs of the same schedule (determinism check, ties to P7/ADR-20 even before parallelism exists).

15.5 Conformance Fixtures

  • fixtures/schedule_serial_order.json — a declared .before()/.after() chain, expected execution order.
  • fixtures/schedule_cycle_detection.json — a 3-system cycle, expected ScheduleCycleError with the named cycle.
  • fixtures/schedule_stage_pipeline.json — one system per canonical stage, expected stage-order execution.

15.6 Pitfalls

  • Implicit ordering assumption — manifests as "it worked in dev, broke after a refactor"; root cause: relying on registration order instead of an explicit .before()/.after(); debug via re-running with registration order shuffled in CI (a determinism-canary fixture); recovery: require explicit edges for any order-sensitive pair (P8).
  • Missing dependency edge causing a silent ordering bug — manifests as inconsistent output depending on unrelated registration changes; root cause: an order requirement was never declared because it "usually worked"; debug via the shuffled-registration canary; recovery: code-review checklist item, not automatically detectable in phase 3 (Phase 6's conflict analysis catches the data-dependent subset).
  • Cycle detection false negative on self-referential edges — manifests as a system declared .before(itself) not raising; root cause: self-edges excluded from the cycle walk; debug via a dedicated self-edge fixture; recovery: explicitly reject self-edges at registration time.

15.7 Performance Concerns

Topological sort is O(systems + edges), dominated by edge count from explicit constraints (this phase) — Phase 6 adds data-conflict edges which can grow O(systems²) in the worst case (mitigated there by per-ComponentId conflict indexing, not pairwise comparison).

15.8 Edge Cases

Zero systems registered (empty schedule runs as a no-op, not an error); two systems with identical names (allowed — SystemId is the identity, name is metadata only, but a warning is logged for operator clarity); a system registered in a stage that doesn't exist (raises at registration, not silently dropped).

15.9 Failure Analysis

A schedule that fails to build (cycle) must fail at Schedule.build() time, before the main loop starts — never partially built and run; forensics: the cycle error includes every SystemId and name in the cycle, formatted for direct pasting into a bug report.

15.10 Operational Notes

scheduler.build_failures metric (I13 telemetry); schedule-build is logged once at startup (info level) with total system/stage counts, not per-frame (it doesn't rerun per frame in this phase's serial model). No hot-reload of schedules yet (that would require re-deriving the DAG mid-run — deferred, PhaseDeferred("§37")).

16. Phase 4 — Fixed/Variable Main Loop With Interpolation

16.1 Objectives

Implement TickAccumulator and the frame lifecycle state machine (§8.6, §8.11): fixed-rate FixedUpdate decoupled from variable-rate Update/Render, with interpolation alpha (P2, Fiedler §5). This is where the salvaged original engine's central insight is formally specified.

16.2 Detailed Implementation Steps

Implement TickAccumulator.advance(real_dt) exactly per the §8.6 display equations, including the MAX_FRAME_DT input clamp and the MAX_TICKS_PER_FRAME spiral-of-death clamp (I5). Implement the main-loop state machine (§8.11) as an explicit state object, not an implicit while True: — each state transition is inspectable for the profiler (Phase 11, ADR-23). Store both "previous" and "current" values for components flagged interpolatable (initially Transform only) so Extract (§3) can compute render_state = previous + alpha × (current − previous) per §8.6. Cite P2 and I5 inline at every accumulator-touching step.

16.3 Deliverable

A runnable loop (examples/headless_tick_demo) printing tick count at a configurable fixed rate while a separate configurable render rate logs interpolated positions; demonstrates the update/ render rate decoupling the original salvaged blueprint described only informally.

16.4 Acceptance Criteria

At a simulated 200 ms single-frame stall, the accumulator clamp (I5) engages within one frame — no more than MAX_TICKS_PER_FRAME fixed updates run, accumulator truncated to zero, one loop.overrun_count telemetry event emitted (fixed_update_spiral_clamp.json); interpolation alpha lands in [0, 1) across 10,000 randomized real_dt sequences (property test); at a fixed 60 Hz tick and simulated variable 30–240 Hz render rate, position error between the interpolated and analytically-expected position stays ≤ 1e-4 units (interpolation_accuracy.json).

16.5 Conformance Fixtures

  • fixtures/fixed_update_spiral_clamp.json — an artificial 200 ms stall, expected clamp engagement and telemetry.
  • fixtures/interpolation_accuracy.json — a known linear-motion entity, expected interpolated position within tolerance across sampled render rates.
  • fixtures/loop_state_machine_transitions.json — a full frame trace, expected exact state sequence per §8.11.

16.6 Pitfalls

  • Spiral of death — manifests as the engine appearing to "freeze" while running fixed updates back-to-back; root cause: simulation cost per tick exceeding tick_dt under sustained load; debug via loop.overrun_count trending upward; signal: FrameStats.overrun_count; recovery: I5 clamp engages automatically, but sustained triggering requires reducing per-tick system cost (§30), not just tolerating the clamp.
  • Time accumulating during pause — manifests as a burst of catch-up ticks on unpause; root cause: real_dt still accumulating while time.scale = 0; debug via a pause/unpause fixture; recovery: reset the accumulator to zero on pause/unpause transitions, documented as an explicit state-machine edge, not left implicit.
  • Interpolating a non-interpolatable component — manifests as jitter on a component that never stores a "previous" value (e.g. a discrete AnimationFrame index); root cause: applying the interpolation formula to a component that shouldn't be interpolated; debug via visually inspecting jitter in the demo; recovery: interpolation opt-in per component type, not global.

16.7 Performance Concerns

Doubling interpolatable-component memory (previous + current) is a deliberate tradeoff (§8.6); only components the render seam actually reads (initially just Transform) opt in, bounding the memory cost; the accumulator itself is O(1) per frame regardless of tick count.

16.8 Edge Cases

real_dt of exactly zero (no-op frame, no fixed updates, alpha unchanged); a single frame whose real_dt exceeds MAX_FRAME_DT × MAX_TICKS_PER_FRAME (clamp engages on both the input and the iteration count, documented as double-bounded); a render rate higher than the tick rate (alpha varies smoothly frame to frame, this is the common case, not an edge case, but tested explicitly at 240 Hz render / 60 Hz tick).

16.9 Failure Analysis

An exception inside a FixedUpdate system mid-catch-up-loop must not leave the accumulator in an inconsistent state — the accumulator decrement happens unconditionally after the stage attempt, whether or not the stage's systems all succeeded (partial-tick semantics documented, cross-ref FM-9); the Recovering state transition (§8.11) is entered with the remaining ticks-owed preserved so no simulated time is silently lost or duplicated.

16.10 Operational Notes

Per-stage timing recorded in FrameStats.stage_timings_us (ADR-23); loop.overrun_count and tick/render-rate ratio exported as metrics (§26); the frame-spike-diagnosis runbook (§10) starts from this phase's telemetry.

17. Phase 5 — Command Buffers & Deferred Structural Change

17.1 Objectives

Implement CommandBuffer/Command (§8.5, §11) and route every structural mutation (spawn/despawn/insert/remove/reparent) through it, applied only at a stage sync point (I4, P5). This closes the direct-mutation gap left open since Phase 0.

17.2 Detailed Implementation Steps

Implement the five Command variants exactly as in §11; each system receives its own CommandBuffer (owner_system: SystemId) rather than a shared one, so ordering is deterministic per P7 — buffers applied in the stage's declared system order, FIFO within a buffer (§8.5). Implement the sync point as a Stage-level apply_commands() call inserted after all systems in the stage have run (never mid-stage); this is the enforcement point for I4. Reject any attempt to mutate World structurally outside a CommandBuffer at the API layer (no back door). Wire SetParent to run the I12 cycle check (ancestor walk) before enqueueing, not after — a caught cycle never enters the buffer.

17.3 Deliverable

Systems can spawn/despawn entities and add/remove components; a demo system spawns an entity when an external event flag flips, another despawns entities older than N ticks — both routed through command buffers, both taking effect only at the stage boundary.

17.4 Acceptance Criteria

10,000 randomized command sequences (spawn/despawn/insert/remove/reparent) applied at a sync point produce zero orphaned rows and zero EntityMeta inconsistencies (command_buffer_stress.json); a SetParent cycle is rejected with CyclicParentError before any buffer entry is created (zero side effects on rejection, set_parent_cycle_rejection.json); command application order for a 50-system stage is byte-identical across 100 runs (determinism, P7).

17.5 Conformance Fixtures

  • fixtures/command_buffer_stress.json — 10,000 randomized mutations, expected zero inconsistencies.
  • fixtures/set_parent_cycle_rejection.json — an attempted parent cycle, expected rejection with no partial state change.
  • fixtures/command_buffer_apply_ordering.json — multiple systems' buffers in one stage, expected FIFO-per-buffer, stage-order-across-buffers application.

17.6 Pitfalls

  • Forgotten flush leaving inconsistent state — manifests as an entity appearing "half spawned" (allocated but no components); root cause: a Spawn command's bundle insertion split across two apply passes; debug via command_buffer_apply_ordering fixture; recovery: a Spawn command carries its full initial bundle atomically, never a bare allocate-then-insert sequence.
  • Command ordering ambiguity across systems — manifests as nondeterministic final state when two systems' commands conflict (e.g. both despawn the same entity); root cause: undefined cross-buffer ordering; debug via the ordering-stress fixture; recovery: stage-declared system order is the tiebreak (P7); a double-despawn is idempotent (second is a no-op on an already-freed generation, not an error).
  • Iterator invalidation from a structural change mid-query — now structurally impossible by construction (no mutation API reachable mid-iteration) rather than merely avoided by convention; regression-tested by attempting the old direct-mutation call path and asserting it does not exist (api_surface_test.py, not a fixture but a static test).

17.7 Performance Concerns

Per-system CommandBuffer allocation is pooled (ADR-08 allocation-budget rationale, §4 ≤ 64 KB/ frame net) — buffers reused across frames rather than reallocated; command application batches archetype moves per source archetype to amortize the swap-remove cost (§13) across many commands touching the same archetype in one sync point.

17.8 Edge Cases

A command referencing an entity despawned earlier in the same buffer (later commands referencing it are no-ops, not errors — I1's generation check catches this uniformly); an Insert for a component the entity already has (overwrite semantics, not a duplicate); a Remove for a component the entity doesn't have (no-op, not an error, to keep command application robust to speculative/defensive game code).

17.9 Failure Analysis

A malformed command (e.g. a component value that fails a schema check during Insert) aborts just that command, logs the failure, and continues applying the rest of the buffer — bounded blast radius per command, not per buffer (contrast with Phase 10's whole-prefab-abort semantics, which is a stronger guarantee for a different failure domain); forensics: failed commands recorded in FrameStats for the frame they were attempted in.

17.10 Operational Notes

commands.applied_per_frame metric (I4 telemetry); command-buffer pool size exported as a gauge (ties to the ≤ 64 KB/frame allocation budget, §4); no operator-facing rollback yet (in-memory only until Phase 10).

18. Phase 6 — Access Analysis & Safe Parallel Scheduling

18.1 Objectives

Extend Schedule.build() (Phase 3, §15) with data-conflict-derived edges from Access (§8.4, P6), producing Stage.parallel_groups. Prove I3 (no conflicting concurrent access) mechanically, not by convention, per Herlihy & Shavit (§5) correctness reasoning.

18.2 Detailed Implementation Steps

For every pair of systems in a stage, compute conflict per the §8.4 matrix (read/write, write/write conflict; read/read and disjoint-component pairs do not); index conflicts by ComponentId (not pairwise O(systems²) comparison at scale — a per-component "who writes this" map bounds the check to O(systems × accessed-components), citing Herlihy & Shavit's lock-free data-structure conflict-indexing pattern, applied here to schedule build). Merge data-conflict edges with Phase 3's explicit edges into one DAG; topological "layering" (Blumofe & Leiserson §5 work-stealing lineage — though v1's executor is single-threaded per ADR-08, the layering algorithm is the same one a work-stealing scheduler would consume) produces parallel_groups: each group is a list of SystemIds that could run concurrently given only their declared access. v1 executes groups serially within a group too (ADR-08 honesty: no GIL-parallel speedup yet) but the grouping itself is the artifact a future native core consumes unchanged.

18.3 Deliverable

Schedule.build() emits parallel_groups per stage; a benchmark demonstrating the group assignment for the §8.4 worked example (movement, apply_damage, regen, ai_think, render_extract_prep) exactly matches the documented grouping.

18.4 Acceptance Criteria

The §8.4 worked example produces the documented 4-group layering exactly, verified by scheduler_worked_example.json; a deliberately conflicting pair (two systems both writing Transform, no explicit order) raises at Schedule.build() with both system names named (scheduler_conflict_detection.json) — I3 enforced, not merely documented; DAG build for a 2,048-system schedule (§4 ceiling) completes in ≤ 5 ms (scheduler_build_scale_bench.py).

18.5 Conformance Fixtures

  • fixtures/scheduler_worked_example.json — the §8.4 five-system example, expected exact parallel-group assignment.
  • fixtures/scheduler_conflict_detection.json — two conflicting writers, expected build failure naming both systems.
  • fixtures/scheduler_disjoint_parallel.json — N systems touching disjoint components, expected a single parallel group of size N.

18.6 Pitfalls

  • Two systems writing the same component undetected — manifests as a data race (silent corruption) if this check regresses; root cause: a bug in conflict indexing (e.g. treating Optional<T> writes as reads); debug via scheduler_conflict_detection plus an adversarial fuzzed-access-set test; recovery: I3 must be a build-time hard failure, never a runtime best-effort check.
  • False sharing between parallel systems writing adjacent columns — manifests as unexpectedly poor throughput once a native core (deferred) actually parallelizes groups; root cause: two disjoint-component writers landing on the same cache line because columns for small components pack tightly; debug via a padding experiment in the native-core prototype (out of this phase's scope, documented pitfall for §37's deferred native core; the pure-Python v1 is immune since it never truly runs two writers concurrently, ADR-08).
  • Cost-blind grouping — manifests as a "parallel" group whose members have wildly different costs, so v1's serial-within-group execution wastes the grouping's intent; root cause: grouping is access-based only, not cost-aware; debug via FrameStats.stage_timings_us per system; not fixed in v1 (documented as a deferred refinement, PhaseDeferred("§37"), since a native executor is a prerequisite for it to matter).

18.7 Performance Concerns

Per-ComponentId conflict indexing bounds build cost to O(systems × accessed-components) instead of O(systems²); this is the concrete Herlihy & Shavit-style structural argument, not an assertion — verified by scheduler_build_scale_bench.py at the 2,048-system ceiling (§4).

18.8 Edge Cases

A system declaring zero component access (a pure-resource system, e.g. a UI-time system) — always groups freely with any component-accessing system, conflicts only on declared resource access; a system whose access set changes between registrations (e.g. re-registered with different Access) — treated as a distinct SystemDescriptor, no stale-access-set carryover; an empty stage (zero systems) produces zero groups, not an error.

18.9 Failure Analysis

A conflict-detection false negative is the single most dangerous defect class in this phase — silent data corruption, not a crash; mitigated by treating I3 as a property test run against randomly generated access sets on every commit (§28), not only the worked-example fixture; forensics: scheduler.conflicts_detected telemetry should read zero in production — any nonzero reading here would indicate the check ran and worked, a nonzero escaped conflict would only show up as a downstream data-corruption symptom (documented gap, mitigated by the property test's breadth, not eliminated in principle).

18.10 Operational Notes

scheduler.build_failures and scheduler.conflicts_detected metrics; schedule build is logged once at startup with group sizes per stage (info level) for operator visibility into how much "free" parallelism the current system set actually has, ahead of the native-core work that would exploit it.

19. Phase 7 — Event Bus

19.1 Objectives

Implement the typed, double-buffered EventQueue (§8.7, §11), wired to the Last stage's mandatory swap (I8). Prove two-frame visibility and no double-delivery.

19.2 Detailed Implementation Steps

Implement EventQueue.send(event) appending to current; EventQueue.read() returning previous ++ current (chain, not concatenation-copy, to avoid per-read allocation, §4 allocation budget); swap_buffers() invoked exactly once by the Last stage's built-in system (not user-schedulable, enforcing I8 by construction rather than convention). Register Time and KeyPress-class events as the first concrete EventIds to validate the demo path salvaged from the original blueprint's Phase 6 intent. Bound each queue's current length (§4 backpressure, ADR-31): past a configured cap, oldest-in-current entries are dropped with a events.dropped_count telemetry increment — never an unbounded queue.

19.3 Deliverable

A Time resource updated every frame via an event-like tick notification, and a KeyPress event sent by the platform layer and consumed by a demo system within the same and next frame only.

19.4 Acceptance Criteria

An event sent in frame N is readable in frames N and N+1, absent in frame N+2, across 10,000 randomized send/read interleavings (event_two_frame_visibility.json); sustained 1,000,000 events/sec/type for 60 seconds does not exceed the §4 allocation budget (≤ 64 KB/frame net new heap, event_throughput_bench.py); backpressure drop-oldest engages correctly at the configured cap with accurate events.dropped_count (event_backpressure.json).

19.5 Conformance Fixtures

  • fixtures/event_two_frame_visibility.json — send/read timing matrix, expected visibility window.
  • fixtures/event_backpressure.json — a burst exceeding the queue cap, expected drop-oldest and telemetry.
  • fixtures/event_swap_ordering.json — verifies swap_buffers runs exactly once per frame regardless of system count (I8).

19.6 Pitfalls

  • Event drop under high frequency going unnoticed — manifests as gameplay bugs from "missing" input events; root cause: backpressure drop-oldest silently discarding without the consumer checking events.dropped_count; debug via the backpressure fixture; recovery: telemetry is always emitted on drop, documented as a required dashboard signal (§26), not merely available.
  • Event leak from nobody reading a type — manifests as steady per-frame allocation growth for an unread EventId; root cause: current still accumulating even with zero readers; debug via per-EventId queue-length metrics; recovery: the two-frame double-buffer bounds this regardless (I8) — worst case is one frame's worth of unread events, not unbounded growth, which is the structural fix over an unbounded log.
  • Double-swap from a mis-scheduled Last-stage duplicate — manifests as events disappearing one frame early; root cause: a second system accidentally also calling swap_buffers; debug via event_swap_ordering fixture; recovery: swap_buffers is not exposed as a schedulable system at all, only the engine-internal Last-stage hook calls it (API-level prevention, not a runtime check).

19.7 Performance Concerns

read() as a chained iterator (not a copy) avoids O(queue size) allocation per read call; the backpressure cap bounds worst-case memory regardless of producer burst rate; per-event serialized payload size directly trades against the §4 1M events/sec/type target (larger payloads reduce sustainable throughput proportionally).

19.8 Edge Cases

Zero readers for an EventId for its entire lifetime (allowed, bounded by two-frame window, no leak); a system reading events from a type it never registered interest in (returns empty, not an error — reading is not access-controlled, only writing is tracked for scheduler conflicts since event reads are inherently safe to share, §8.4); an event payload exceeding a configured max size (rejected at send() with a logged warning, not silently truncated).

19.9 Failure Analysis

A queue-cap misconfiguration (too low) causes silent gameplay-relevant drops — detection relies on the events.dropped_count dashboard signal (§26) rather than a crash, since drop-oldest is by design a graceful-degradation path, not a failure; forensics: per-EventId drop history retained in FrameStats for the frame the drop occurred.

19.10 Operational Notes

events.dropped_count, per-EventId queue length, and swap-count metrics exported (§26); event throughput dashboards feed the frame-spike-diagnosis runbook when a burst correlates with a frame-time spike.

20. Phase 8 — Resource Manager, Handles & Hot Reload

20.1 Objectives

Implement ResourceHandle/AssetSlot/LoadState (§8.8, §8.12, §11) with refcounting (I9) and filesystem-watch-triggered hot reload (ADR-13) meeting the §4 100 ms propagation target.

20.2 Detailed Implementation Steps

Implement AssetSlot per §11 with refcount: u32 guarded against underflow (I9); acquire()/ release() are the only refcount mutators. Implement the state machine exactly per §8.12: Unloaded → Loading → Loaded, Loaded → HotReloadPending → Loading (generation bump, not index change, per P9/ADR-11), Loaded → Evicting → Unloaded on refcount zero. Background loading runs on a dedicated loader thread pool (I/O-bound, so the GIL cost is acceptable per ADR-08's honest carve-out — CPU-bound systems don't get this, I/O-bound loading does); the watcher (watchdog library, ADR-13) posts HotReloadPending transitions onto the main-thread state machine rather than mutating AssetSlot from the watcher thread directly (single-writer discipline, consistent with P6/I3's spirit even outside the ECS proper). Handle staleness: a holder compares its ResourceHandle.generation against the current AssetSlot.generation on every access and re-resolves on mismatch (P9).

20.3 Deliverable

Load a glTF-referenced texture-class asset from disk (ADR-12); edit the source file; the running demo observes the Loaded state with a bumped generation within the §4 100 ms target, without any holder crashing on the old handle.

20.4 Acceptance Criteria

Cold load of a 1 MB texture-class asset completes at p99 ≤ 50 ms off the main thread (asset_load_latency_bench.py, §4); hot-reload propagation from filesystem event to Loaded state observed at ≤ 100 ms across 100 trials (hot_reload_latency.json); 10,000 randomized acquire/release sequences produce zero refcount underflow and correct eviction timing (refcount_stress.json, I9).

20.5 Conformance Fixtures

  • fixtures/asset_load_cold.json — a fresh load, expected state transitions and latency bound.
  • fixtures/hot_reload_latency.json — a file-watch-triggered reload, expected propagation time and generation bump.
  • fixtures/refcount_stress.json — randomized acquire/release, expected zero underflow, correct eviction.
  • fixtures/asset_load_malformed.json — a corrupt glTF file, expected Failed state with AssetLoadError, no partial AssetSlot.

20.6 Pitfalls

  • Hot reload leaving dangling handles — manifests as a holder reading freed bytes; root cause: swapping bytes in place instead of bumping generation; debug via the hot-reload fixture with a holder that deliberately delays its next access past the reload; recovery: never mutate bytes behind an unchanged generation — bump-then-swap, always (P9, ADR-13).
  • ABBA deadlock between loader thread and main thread — manifests as a hang under concurrent load-and-access; root cause: the loader thread holding a lock the main thread also wants while waiting on the loader; debug via a stress test with simultaneous acquire-during-load; recovery: the loader thread never blocks on main-thread state — it posts a completed AssetSlot payload onto a lock-free single-producer queue the main thread drains at a defined point (PreUpdate).
  • Asset load cycle (A references B, B references A) — manifests as infinite recursive load requests; root cause: cyclic asset dependencies in glTF/prefab references; debug via a deliberately cyclic fixture; recovery: cycle detection at reference-resolution time, Failed state with a named cycle in AssetLoadError, symmetric to I12's scene-graph cycle rejection.

20.7 Performance Concerns

Loader thread pool sized to avoid oversubscription against Python's GIL-bound main thread (I/O wait releases the GIL naturally, so this is one of the few places extra threads genuinely help, ADR-08); refcount operations are O(1) atomics-free since they only ever execute on the main thread (single-writer, no lock needed).

20.8 Edge Cases

acquire() racing an in-progress Evicting transition (I9 race guard: transitions back to Loaded, the eviction is cancelled, not raced past); a hot-reload event for an asset with zero current holders (reloads anyway if AssetSlot still exists, since a future acquire should see fresh bytes, cheap enough not to special-case); a reload that fails mid-load (state remains Loaded with the old bytes and generation, failure logged, not silently swapped to garbage).

20.9 Failure Analysis

A malformed or malicious asset (T2, T3) must fail closed — Failed state, AssetLoadError, never a partially-populated AssetSlot a holder could read; blast radius is the one asset, not the process, because deserialization runs in a restricted parser (no arbitrary code execution path, ADR-12's glTF/MessagePack choice explicitly avoids formats like pickle for this reason).

20.10 Operational Notes

assets.refcount_underflow, per-asset LoadState, and hot-reload latency histograms exported (§26); the asset-load path is the primary attacker-facing surface documented in the Threat Model (§24 T1–T3).

21. Phase 9 — Scene Graph & Transform Propagation

21.1 Objectives

Implement Transform/GlobalTransform/SceneNode (§8.9, §11) with dirty-flag propagation (P11, I6), enforcing acyclic parenting (I12) and the §4 depth ceiling.

21.2 Detailed Implementation Steps

Implement SceneNode.parent/children as component data (ADR-14, not a standalone tree); implement SetParent (already a Command since Phase 5) to perform the I12 ancestor walk before commit. Implement propagate_transforms as a PostUpdate-stage system (.after() all Update-stage transform writers, enforcing I6 by explicit ordering, P8) that visits dirty roots and their descendants in depth order (breadth-first by SceneNode.depth, per §8.9), computing GlobalTransform.matrix = parent.GlobalTransform.matrix × local_matrix(Transform); nodes with neither their own nor an inherited dirty flag are skipped (memoization, P11, Nystrom §5 Dirty Flag). Depth is tracked incrementally on SetParent (not recomputed from scratch) and capped at the §4 64-level ceiling, rejecting a SetParent that would exceed it.

21.3 Deliverable

A parent/child entity chain (5 levels) where moving the root propagates correctly to every descendant's GlobalTransform within the same PostUpdate pass; a demo showing a static subtree skipped entirely by the dirty-flag memoization.

21.4 Acceptance Criteria

A 10,000-node scene graph with 1% of nodes dirtied per frame propagates in ≤ 2 ms (transform_propagation_bench.py, ties to §4/§30); zero stale GlobalTransform reads across 10,000 randomized reparent-then-query sequences (transform_staleness_property.json, I6); a SetParent cycle attempt is rejected with CyclicParentError and zero graph mutation (scenegraph_cycle_rejection.json, reusing I12's contract from Phase 5, now exercised through the scene-graph-specific path).

21.5 Conformance Fixtures

  • fixtures/transform_propagation_basic.json — the 5-level chain, expected propagated matrices.
  • fixtures/transform_propagation_memoization.json — a static subtree alongside a dirtied one, expected the static subtree's propagation step count of zero.
  • fixtures/scenegraph_depth_ceiling.json — an attempted 65-level chain, expected rejection.
  • fixtures/scenegraph_cycle_rejection.json — reparenting an ancestor to its own descendant, expected CyclicParentError.

21.6 Pitfalls

  • Stale world transform after reparenting — manifests as a render/physics read of a GlobalTransform computed before the reparent took effect; root cause: propagate_transforms scheduled before, not after, the systems that call SetParent; debug via the staleness property test; recovery: I6's explicit .after() ordering constraint, verified by the fixture, not merely intended.
  • Dirty-flag propagation missing a grandchild — manifests as a child's GlobalTransform updated but a grandchild's not; root cause: single-level dirty marking instead of transitive closure over Children; debug via a 3+-level fixture with only the root dirtied; recovery: dirty marking walks the full descendant set on any ancestor's local-transform write.
  • Depth-tracking drift after repeated reparenting — manifests as the depth ceiling rejecting valid reparents or admitting cycles past the intended limit; root cause: incremental depth update not recomputed on every SetParent, only inherited from the old parent; debug via a repeated-reparent stress fixture; recovery: recompute depth as new_parent.depth + 1 on every successful SetParent, not carried over.

21.7 Performance Concerns

Propagation cost is O(dirty subtree size), not O(total nodes) (P11) — verified directly by transform_propagation_memoization's zero-step assertion on the static subtree; matrix multiplication for propagation uses the same numpy-backed columns as general storage (ADR-02), avoiding a second data representation for scene-graph math.

21.8 Edge Cases

A root node with no parent (identity propagation, GlobalTransform = local_matrix); despawning a parent without despawning children (children become root nodes with parent = None, not silently dangling — documented API contract, "despawn recursively" is a separate command sequence the caller must issue explicitly, not automatic, since automatic cascade could itself trigger runaway structural changes the command-buffer batching (§17) isn't sized for); two SetParent commands for the same child in one buffer (last one wins, FIFO order, per §8.5).

21.9 Failure Analysis

A propagation bug that produces a wrong (but not obviously invalid) matrix is silent corruption — mitigated by the property test comparing propagated results against an independently computed reference matrix chain for randomized hierarchies, not just the fixed fixture; forensics: the replay-divergence runbook (§10) applies here too, since transform divergence is a common root cause of replay mismatches (§28).

21.10 Operational Notes

Propagation time and dirty-node count per frame exported as metrics (§26); the archetype-fragmentation-cleanup runbook cross-references this phase because Transform/SceneNode combinations are a common source of archetype proliferation if scene depth varies widely across entity types.

22. Phase 10 — Prefabs, Serialization & Deterministic Replay

22.1 Objectives

Implement Prefab (§8.10, §11), the MessagePack/JSON codecs (ADR-16), name-keyed component references (ADR-17), and the deterministic-replay contract (P7, ADR-20) end to end.

22.2 Detailed Implementation Steps

Implement PrefabLoader.validate performing the I11 component-registration check and the I12 cycle check on children before any entity is spawned (whole-prefab-abort semantics, distinct from Phase 5's per-command bounded-blast-radius — a stronger guarantee appropriate to a durable load boundary, per Bilas's data-driven object system, §5). Implement save/load as a full World snapshot: every ComponentInfo-registered, serializable component walked per entity, entity references (e.g. SceneNode.parent) remapped through a save-local index table rather than persisting raw Entity values (which are allocator-instance-specific). Implement deterministic replay: record the initial World snapshot plus the ordered input-event stream; replay re-runs the Schedule from the snapshot consuming the recorded events; a divergence is detected by comparing a periodic state hash (component bytes, in canonical per-archetype order) against the recorded run's hash at the same frame number (ADR-20, tools/replay_diff.py).

22.3 Deliverable

Save a running 10,000-entity scene to MessagePack; quit; reload; verify entity-for-entity component equality (modulo non-serializable resources, e.g. a live socket); replay a recorded 100-frame input stream against a fresh World built from the same snapshot and get a bit-identical final state hash.

22.4 Acceptance Criteria

Save/load round-trip of 100,000 entities × 5 components completes in ≤ 200 ms MessagePack (§4, serialization_roundtrip_bench.py); JSON debug path completes within 5× that bound; a malformed prefab (unregistered component or a parent cycle) aborts the entire load with zero entities spawned (prefab_malformed_rejection.json, I11/I12); a 100-frame deterministic replay produces a bit-identical state hash on 3 consecutive runs (deterministic_replay_bitwise.json, directly gates §28's differential-testing requirement).

22.5 Conformance Fixtures

  • fixtures/prefab_save_load_roundtrip.json — 10,000-entity round-trip, expected component equality.
  • fixtures/prefab_malformed_unknown_component.json — named per §8.10, expected PrefabValidationError, zero entities spawned.
  • fixtures/prefab_malformed_cyclic_parent.json — named per §8.10, expected CyclicParentError, zero entities spawned.
  • fixtures/deterministic_replay_bitwise.json — 100-frame recorded input, expected bit-identical hash across repeated replays.
  • fixtures/prefab_schema_version_migration.json — an old-schema-version prefab, expected successful migration per §27.

22.6 Pitfalls

  • Entity references in serialized data resolving to the wrong entity — manifests as a Parent reference pointing at an unrelated entity after load; root cause: persisting raw Entity values instead of remapping through a save-local index; debug via the round-trip fixture with a deliberately reordered reload; recovery: always remap through the save-local index table, never trust a raw Entity across allocator instances.
  • Non-determinism smuggled in via floating-point order-of-operations — manifests as replay divergence despite fixed timestep and stable system order; root cause: a system summing forces in a non-fixed order (e.g. iterating a Python set, whose order is not insertion-stable) — IEEE 754 (§5) addition is not associative; debug via tools/replay_diff.py bisecting the first divergent frame; recovery: every order-sensitive accumulation iterates a stable, documented order (archetype row order, never a hash-based container).
  • Save/load with non-deterministic RNG state — manifests as behavior diverging after a save/load cycle even without a bug in the world state itself; root cause: RNG streams not included in the snapshot; debug via a load-then-replay fixture; recovery: seeded per-stream RNG state (ADR-20) is itself a serialized resource.

22.7 Performance Concerns

MessagePack's compactness directly drives the ≤ 200 ms/100k-entity target (§4, §34); the whole-prefab-validate-before-spawn approach costs an extra full pass over the prefab's declared components before any mutation, traded deliberately against the alternative of a cheaper partial-validate that risks partial spawns (rejected, see I11's enforcement point).

22.8 Edge Cases

A prefab with zero components (a bare marker entity, valid); a save file from a newer schema_version than the running engine understands (rejected with a named AssetLoadError/migration-required message, never a best-effort partial parse, §27); a replay whose recorded input stream is shorter than the requested frame count (replay halts at the last recorded frame, does not fabricate input).

22.9 Failure Analysis

A replay divergence is the highest-value forensic signal this engine produces — replay_diff.py bisects to the first divergent frame and the first divergent component, then cross-references FrameStats for that frame to identify the offending system; the replay-divergence runbook (§10, §26) is built around exactly this tool.

22.10 Operational Notes

Save/load latency and replay-divergence-bisection time exported as metrics; docs/runbooks/ replay-divergence.md documents the tools/replay_diff.py workflow end to end; prefab schema-version distribution across a save corpus is tracked to plan deprecation (§27).

23. Phase 11 — Profiling Harness, Conformance Suite & Perf Hardening

23.1 Objectives

Implement FrameStats (§11) as an always-on ring buffer, the conformance-suite runner (gecore.profiling.conformance), and close the performance-hardening loop against every §4/§30 target with CI-gated regression detection.

23.2 Detailed Implementation Steps

Implement FrameStats as a fixed-capacity ring buffer of per-frame stage_timings_us, overrun_count, and last_exception, populated by lightweight span hooks at each stage boundary (ADR-22/ADR-23) — the hooks are the same instrumentation points every prior phase's telemetry referenced (I1–I14's "Telemetry" column, §7), now aggregated into one queryable structure. Implement conformance.py as a runner that executes every named fixture from every phase's N.5 section against a fresh World/Schedule, asserting the recorded expected output, and reports a single pass/fail table (this is the mechanical backbone of §28's testing strategy). Wire benchmarks/query_throughput_bench.py and siblings into perf-gate.yml (§10, ADR-26) comparing against the §30 M-table with a defined regression threshold (≥ 10% regression on any M# fails the gate, per Herlihy & Shavit-informed correctness-over-speed priority, P1 mission preamble).

23.3 Deliverable

gecore.profiling.conformance runs every fixture referenced across Phases 0–10 (≥ 40 named fixtures) and reports pass/fail; perf-gate.yml blocks a PR that regresses any M# target beyond threshold; a profiler dashboard (docs/performance/benchmarks.md) renders the M-table trend over the last 30 CI runs.

23.4 Acceptance Criteria

100% of named fixtures from Phases 0–10 pass under the conformance runner (conformance_full_suite.json, this phase's own gate); frame-time p99 for a 100,000-entity, 50- system reference scene stays ≤ 16.6 ms at 60 Hz target tick rate over a 10-minute soak (soak_10min_frametime.json, §30 M-table); zero memory growth beyond 5% over a 60-minute soak run with steady entity count (soak_60min_leak_check.json, ties to §4 allocation budget and I9).

23.5 Conformance Fixtures

  • fixtures/conformance_full_suite.json — meta-fixture aggregating every named fixture from Phases 0–10, expected 100% pass.
  • fixtures/soak_10min_frametime.json — sustained reference-scene run, expected p99 bound.
  • fixtures/soak_60min_leak_check.json — long-run memory-growth bound.
  • fixtures/perf_regression_canary.json — a deliberately regressed build, expected the gate to fail (a negative-control fixture proving the gate actually detects regressions).

23.6 Pitfalls

  • A conformance runner that "passes" because a fixture silently didn't execute — manifests as false confidence; root cause: a typo'd fixture path or a swallowed exception in the runner itself; debug via perf_regression_canary and an equivalent conformance negative-control fixture that must fail; recovery: the runner asserts a minimum expected fixture count (≥ 40) and fails loudly if fewer ran.
  • Profiling overhead itself causing the regression it measures — manifests as span instrumentation adding measurable per-system overhead at the 2,048-system ceiling (§4); root cause: span creation cost scaling with system count; debug via an instrumentation-on/off differential benchmark; recovery: sampling (ADR-22) rather than exhaustive per-call tracing once system count is high.
  • Soak-test archetype fragmentation — manifests as gradually increasing frame time over a long run despite constant entity count; root cause: transient component combinations during the run leaving behind low-population archetypes (FM-1); debug via archetype.count trend over the soak window; recovery: cross-refs the archetype-fragmentation-cleanup runbook (§10), exercised for real here for the first time under sustained load.

23.7 Performance Concerns

This phase is where every earlier phase's isolated microbenchmark gets checked against the integrated, whole-engine frame budget (§4, §34) — a system that met its own N.7 concerns in isolation can still blow the frame budget in combination; the soak fixtures exist specifically to catch that composition failure.

23.8 Edge Cases

A fixture that passes individually but fails only under the full-suite's shared World state (state leakage between fixtures — the runner resets World/Schedule between fixtures specifically to rule this out, documented as a runner correctness requirement, not merely a convenience); a benchmark run on CI hardware with unpredictable neighbor-noise (mitigated by a median-of-5-runs comparison against the M-table baseline, not a single sample).

23.9 Failure Analysis

A perf-gate false negative (regression that slips through) is bounded by the perf_regression_ canary negative control running on every gate change; a soak-test crash (rather than a graceful degradation) is treated as a P0 defect regardless of root cause, since the whole point of Phases 0–10's recovery paths (FM-1 through FM-12, §25) was to make crash-free degradation the norm.

23.10 Operational Notes

The M-table trend dashboard (docs/performance/benchmarks.md) is the primary operational artifact of this phase; CI failure on perf-gate.yml links directly to the specific M# row that regressed and the fixture that demonstrated it, closing the loop from §4's constraints table through to a CI-enforced guarantee.

26. Operational Readiness

Metrics (named, exported per §4/§30): frame-time percentiles (p50/p95/p99) per stage; loop.overrun_count; archetype.count and per-archetype row_count; query.stale_iteration; entities.spawn_rate; assets.refcount_underflow; events.dropped_count; allocation bytes/frame; GC pause histogram (gen-0/gen-1/gen-2 counts and durations).

Tracing. Per-system, per-frame spans (ADR-22), sampled once system count exceeds a configured threshold to bound instrumentation overhead (§23.6); spans correlate SystemId, stage, and duration, feeding directly into FrameStats.

Structured logging (ADR-21): JSON-formatted, never string-interpolating untrusted content (T12); levels: debug (per-entity spawn/despawn), info (schedule build, asset state transitions), warning (backpressure drops, generation-wrap), error (validation failures, exceptions).

Dashboards. Frame-time percentile trend; archetype count/fragmentation trend; asset load/ hot-reload latency histograms; event drop rate; GC pause histogram — all backed by the M-table (§30) so a dashboard threshold breach maps directly to a named M#.

Alerting philosophy. Alert on trend (archetype count approaching ceiling, refcount leak trend) before threshold breach, not only on breach — most failure classes here (§25) are gradual, not instantaneous.

SLOs, expressed as frame-time budgets: p99 frame time ≤ 16.6 ms at the reference scene (100k entities, 50 systems, §23.4); tick-budget adherence ≥ 99.9% of ticks completing within tick_dt before the I5 clamp engages.

Incident response. A frame-time SLO breach routes to frame-spike-diagnosis; a replay mismatch routes to replay-divergence; sustained archetype growth routes to archetype-fragmentation-cleanup (all three under docs/runbooks/, §10).

Backup/restore of saves. Save files are content-addressed by their checksum (T6 mitigation); restore is load-time schema-version migration (§27) plus checksum verification, never a best-effort partial load.

Deployment topology. Embedded library — no independent deployment unit; "canary" in this context means running the conformance + soak suite (§23) against a release candidate before publishing (§29), not a live traffic-split rollout.

Rollback/migration. A regressed release is rolled back by re-pinning the prior SemVer tag (§27, §29); a save-format migration is one-directional forward (old saves load into new engines, never the reverse) per the compatibility contract (§27).

27. Compatibility & Versioning

Component schema evolution. Each ComponentInfo carries a schema_version; a save/prefab referencing an older version is migrated via a registered per-component migration function chain (v1→v2→...→current) at load time; a version newer than the running engine understands is rejected (§22.8), never best-effort parsed.

Prefab/asset format versioning. Prefab.schema_version and glTF's own version field are both checked; MessagePack payloads carry an engine-format version distinct from the component schema version (two independent version axes, both SemVer-tracked).

System-registration API stability. SystemDescriptor/Access/Schedule (§11) are the stable public surface; adding a new Access field is a minor-version change (additive); changing Access's conflict semantics (§8.4) is a major-version change.

Determinism guarantees across versions/platforms. A save/replay recorded on version N replays bit-identically on version N only; cross-version replay is not guaranteed (floating-point libm differences across platforms, per IEEE 754 §5, are explicitly out of the determinism guarantee — documented, not silently assumed away). Cross-platform determinism (same version, different OS/CPU) is guaranteed only when both use the same compiled numpy BLAS backend (pinned per ADR-26's matrix).

API stability / migration tooling. scripts/gen_component_registry.py regenerates the ComponentId table deterministically from ComponentInfo declarations, ensuring the same source always produces the same ids across a rebuild; tools/replay_diff.py doubles as a migration verification tool (replay an old save through a migration, compare against a golden post-migration hash).

Deprecation. A deprecated ComponentInfo schema version is supported for migration for at least 2 minor versions past its replacement, then migration support is dropped in a major version bump (documented in CHANGELOG.md).

SemVer 2.0.0 policy (§5 RFCs): MAJOR — breaking Access/Schedule/save-format changes; MINOR — additive component/system API; PATCH — bug fixes with no schema or API change.

Rolling-upgrade guarantees. None across major versions (this is an embedded library, not a live service) — an upgrade requires the host process to restart; within a minor version, save compatibility is guaranteed forward-only.

28. Testing & Verification Strategy

Unit. Per-module tests for EntityAllocator, Archetype, Query, Schedule, CommandBuffer, EventQueue, AssetSlot, SceneNode, Prefab codecs — one file per module under a mirrored tests/ tree (not shown in §10 as it's generated per package, conventionally tests/<package>/test_<module>.py).

Integration. Full-stage pipeline runs (Phase 3 onward) exercising the canonical stage order end to end against multi-system schedules.

Property-based (Hypothesis, ADR-24), directly tied to invariants:

Property Invariant
a stale handle never resolves I1
add-then-remove returns an entity to its original archetype I7
a parallel-grouped schedule produces bit-identical results to a fully serial ordering on the same inputs I3, P7
the fixed-step accumulator conserves simulated time (sum of consumed ticks × tick_dt ≤ total real_dt consumed, within the I5 clamp) I5

Differential. Serial-execution vs. parallel-grouped-execution result comparison (Phase 6, §18.4); a shared fixture scenario compared against Bevy/EnTT's documented semantics for archetype-move and query-matching behavior where directly comparable (used as a sanity check on this blueprint's own semantics, not a compatibility requirement).

Fuzzing (Atheris, ADR-25): PrefabLoader.validate and the MessagePack/JSON decoders are the fuzz targets (T1); corpus seeded from conformance/fixtures/prefab_malformed_*.json.

Chaos. Fault injection during the frame lifecycle: kill the loader thread mid-load (expect Failed state, §20), truncate a save file mid-read (expect a checksum failure, T6), inject a raised exception in a randomly chosen system (expect FM-9's bounded recovery).

Deterministic replay with divergence detection. §22's replay contract, run as a scheduled CI job against a growing corpus of recorded sessions; any divergence blocks release (§29).

Soak. 60-minute steady-state run watching for archetype fragmentation (FM-1) and memory leak (FM-7) — §23.4's soak_60min_leak_check.

Fault injection. Asset missing at load time (expect Failed, not a crash); hot reload firing mid-frame (expect the reload queued to the next PreUpdate, not applied mid-stage).

Conformance. §23's full fixture suite, run on every commit, gating merge.

Perf-regression gating. perf-gate.yml (ADR-26) compares every M# (§30) against the last known-good baseline; ≥ 10% regression on any row fails the gate (§23.2).

29. Build & Release Engineering

Reproducible builds. pyproject.toml pins exact dependency versions with content hashes; gecore's own build is a pure-Python wheel (no compiled extension in v1, ADR-02) so build reproducibility reduces to dependency-hash reproducibility, verified in CI.

Artifact signing. Release wheels signed (Sigstore-style keyless signing) before publishing; signature verified by the release workflow before any tag is finalized.

SBOM. Generated per release from the locked pyproject.toml dependency graph, published alongside the wheel (feeds T8's dependency-audit mitigation).

Release channels. stable (tagged SemVer releases), nightly (main-branch builds, conformance- gated but not perf-gated as strictly — a looser threshold to keep nightly builds available for active development).

CI/CD topology. ci.yml (lint + unit + integration matrix), perf-gate.yml (benchmarks vs. M-table), fuzz.yml (scheduled corpus run), release.yml (build, sign, SBOM, publish) — §10.

Version stamping. gecore.__version__ set from the release tag at build time, embedded in save-file headers (§27) so a load can report exactly which engine version produced a save.

Provenance/attestation. Release workflow emits a build-provenance attestation (source commit, build environment, dependency hashes) alongside the SBOM.

Dependency auditing. A scheduled CI job (ADR-26) checks pinned dependencies against a known- vulnerability feed; a hit blocks the next release until re-pinned or waived with a documented justification.

Asset-pipeline determinism. glTF/MessagePack asset imports produce byte-identical output for byte-identical input across platforms (verified by a fixture comparing import output hashes across the OS matrix, ADR-26) — a prerequisite for the deterministic-replay guarantee (§27) to extend to asset-dependent state.

30. Performance Engineering

Methodology. Cache-locality analysis is the primary lens (P4, Drepper §5): every benchmark reports not just throughput but the implied bytes-per-entity touched, cross-checked against §34's capacity model. Allocation is tracked per-frame via tracemalloc-based sampling in benchmark mode (not production, to avoid its overhead skewing the numbers it measures). GIL contention is measured directly by comparing single-threaded vs. thread-pool-wrapped execution of the same CPU-bound system set — the honest expectation (ADR-08, P14) is near-zero improvement, and the benchmark exists specifically to keep that claim checked rather than assumed. Tail latency is always reported as a full percentile histogram (p50/p95/p99/p99.9), never an average — an average frame time can hide a spiral-of-death-adjacent p99 tail entirely.

31. Scalability Analysis

Constant vs. growing. Query iteration cost is O(matching entities), constant with respect to total world size (§8.3, verified §14.4) — the defining scalability property of archetype storage. Archetype-transition cost is O(1) amortized post-memoization (I7). Scene-graph propagation is O(dirty subtree), not O(total nodes) (I6, P11). What genuinely grows: per-frame allocation with event volume (bounded by ADR-31 backpressure); archetype count with component-combination diversity (bounded by the §4 ceiling, mitigated per FM-1); scheduler DAG build cost with system count (bounded O(systems × accessed-components), §18.7).

Named bottlenecks, in order. (1) The GIL — the dominant bottleneck for CPU-bound system throughput in v1 (ADR-08, honest per P14); no amount of storage-layout optimization changes this until a native core ships (PhaseDeferred("§37")). (2) Archetype fragmentation (FM-1) — the dominant correctness-adjacent scalability risk, since it degrades gracefully (worse cache locality) rather than failing outright. (3) Command-buffer application batching cost at very high structural-change rates (§17.7). (4) Serialization round-trip time at very large entity counts (§22.7, linear in entity×component count).

Parallel scaling limits / Amdahl reasoning. The serial sync points — command-buffer application (§17), event-queue swap (§19), transform propagation ordering (§21) — are the sequential fraction Amdahl's law bounds total speedup against, once a native parallel executor exists. Given a stage where 80% of declared system access is conflict-free (parallelizable) and 20% is serialized at the sync point, Amdahl's law bounds speedup to 1/(0.2 + 0.8/N) — approaching 5× as core count N grows large, never more, regardless of core count added. v1 has zero cores of real speedup by design (ADR-08) — this bound is the target the deferred native core is evaluated against, not a currently-realized number.

Archetype-count explosion risk. Worst case 2^(registered component types) archetypes if every subset of components appears on some entity; practical bound is the number of actually observed component-set combinations in a real game, typically two to three orders of magnitude below the theoretical ceiling (§34 derives the concrete bound from §4's numbers).

Practical entity ceiling and levers beyond it. The stated 1,000,000-entity ceiling (§4) is bounded by EntityAllocator index space (2^32, far beyond it) and, practically, by per-entity memory (§34) and query-throughput budget within the frame budget — the lever beyond 1M is either reducing average components-per-entity, sharding the World (out of scope, PhaseDeferred ("§37")), or the native execution core removing the GIL-bound serial ceiling on system throughput.

32. Mental Models & First Principles

MM1 — An ECS is a column-store database with a frame-rate deadline. Queries, indexes, and locality reasoning transfer directly from database engineering. Predicts: a query's cost model is "which columns does this touch," not "how big is the world." Without it, engineers treat components as a random-access object graph and are surprised cache misses dominate. Resolved in §8.3, §14, P4.

MM2 — A fixed timestep makes simulation a pure function of tick count, not of the machine it ran on. Predicts: determinism and lockstep replay are achievable only when the timestep is fixed and the render rate never feeds back into it. Without it: physics that behaves differently on a 240 Hz monitor than a 60 Hz one. Resolved in §8.6, §16, P2.

MM3 — An entity handle is a foreign key with a generation column, not a pointer. Predicts: detecting a dangling reference is a version compare, never a segfault. Without it: use-after-free- class bugs that manifest as silent data corruption instead of a crash. Resolved in §8.1, I1, P3.

MM4 — A scheduler is a static analysis of declared effects, not a runtime race detector. Predicts: safe parallelism must be provable before any system runs, not discovered by testing under load. Without it: races that "usually don't happen" in CI and then happen in production. Resolved in §8.4, I3, P6.

MM5 — Dirty-flag propagation is incremental recomputation — the same principle behind spreadsheet recalculation and reactive UI diffing. Predicts: cost tracks the changed subtree size, never total graph size. Without it: O(everything) recompute code that works in a demo and falls over at real scene sizes. Resolved in §8.9, I6, P11.

MM6 — A resource handle decouples "the game holds a reference" from "the bytes exist" — the same separation a file descriptor makes from an inode. Predicts: hot reload is safe exactly when code holds handles, never raw pointers/bytes. Resolved in §8.8, P9, §20.

MM7 — Backpressure is a choice of failure mode, not the absence of one. An "unbounded" queue doesn't avoid failure, it just moves it to an OOM crash instead of a bounded, telemetred drop. Predicts: every queue in the system needs an explicit cap and an explicit drop policy. Resolved in §8.7, ADR-31, FM-11.

MM8 — Determinism is a system-wide discipline, not a single mechanism. Fixed timestep, stable system order, seeded RNG, and floating-point-associativity discipline all have to hold simultaneously; one non-deterministic component anywhere breaks replay everywhere. Resolved in §22, §27, FM-10.

Bevy made archetype storage and a native (Rust, no-GIL) multi-threaded executor the default from day one — it wins wherever true multi-core speedup on CPU-bound systems matters more than introspectability, which this blueprint explicitly trades away per ADR-08.

EnTT made sparse-set storage the default, optimizing for O(1) structural change over iteration locality — it wins in workloads (roguelikes, prototyping tools) where component sets churn every frame more than they're iterated.

Unity DOTS/Entities made chunk-based archetype storage paired with a Burst-compiled native job system the default — it wins when a large existing engine (rendering, physics, tooling) must be retrofitted with ECS performance without discarding the surrounding ecosystem, at the cost of a years-long dual-model migration (§5 Reference Implementations pitfall).

Flecs made query caching and relationship/hierarchy traits first-class — it wins when the domain model itself is graph-like (tags, relationships, prefab inheritance) beyond a simple component set, at the cost of a larger, later-stabilizing core API surface.

Godot made the scene tree — not an ECS at all — the primary abstraction, with a servers/ scene-tree split decoupling rendering from gameplay nodes — it wins for editor-first, artist- driven workflows where node inheritance maps directly onto how non-programmers think about a scene, at the cost of the cache-locality and bulk-iteration performance an ECS provides at scale.

34. Back-of-Envelope Capacity Model

  1. Frame budget. 1000 ms ÷ 60 fps = 16.6 ms/frame (§4). Reserving 20% for sync points (command application, event swap, transform propagation) leaves 13.3 ms for system bodies; across 50 systems (§4 ceiling used for the reference scene) that's 13.3 ÷ 50 ≈ 0.266 ms/system average budget.
  2. Per-entity memory. §4 targets ≤ 256 bytes/entity at a 10-component average. 10 components × ~24 bytes average (a mix of a 40-byte Transform, 8–16-byte scalars, and zero-sized markers averaging the set down) = 240 bytes, + ~16 bytes archetype/row overhead (entity id + row index) = 256 bytes — matches the §4 target exactly by construction.
  3. Cache-line efficiency. 64 bytes/cache line ÷ 40 bytes (Transform) ≈ 1.6 transforms per line; iterating 100,000 Transforms touches 100,000 ÷ 1.6 ≈ 62,500 cache lines ≈ 4 MB of traffic — at a conservative single-core effective bandwidth of ~20 GB/s (Hennessy & Patterson, §5), that's 4 MB ÷ 20 GB/s ≈ 0.2 ms, well inside the 0.266 ms/system budget from step 1.
  4. Query iteration cost vs. frame budget. M1 (§30) targets ≥ 50M component-reads/sec/core, i.e. 20 ns/read. A query over 100,000 matching entities reading 2 components each: 100,000 × 2 × 20 ns = 4 ms — inside the 16.6 ms frame budget with margin for the remaining ~49 systems.
  5. Archetype-count worst case. Theoretical ceiling is 2^(registered component types); at the §4 ceiling of 4,096 component types that number is astronomically larger than any real game ever reaches. The practical bound is the number of actually-observed component-set combinations, typically 50–500 for a real game — the §4 archetype ceiling of 4,096 leaves an 8×–80× safety margin over typical observed counts before FM-1's fragmentation risk engages.
  6. Command-buffer memory per frame. Worst-case burst: the T4 spawn-rate cap (illustrative 1,000 spawns/frame) × 256 bytes/entity (step 2) = 256 KB for that burst frame — treated as a bounded exception to, not part of, the steady-state ≤ 64 KB/frame (M12) accounting.
  7. Event-queue memory. M7's 1,000,000 events/sec/type ÷ 60 fps ≈ 16,667 events/frame × 32 bytes/event average payload ≈ 533 KB/frame uncapped — this is why ADR-31's backpressure cap exists: capping realistic sustained volume at 2,000 events/frame × 32 bytes = 64 KB/frame brings it back under the M12 steady-state allocation budget.
  8. Simulation catch-up ticks after a stall. A 200 ms stall ÷ 16.6 ms tick_dt ≈ 12 ticks owed; with MAX_TICKS_PER_FRAME clamped at 5 (I5), the engine runs 5 ticks and discards the remaining 7 ticks' worth (≈ 116 ms) of simulated time rather than freezing — the concrete arithmetic behind the §8.6 spiral-of-death clamp.
  9. Serialization throughput requirement. 100,000 entities × 5 components × ~50 bytes/component (MessagePack-compact) ≈ 25 MB raw. Meeting the M10 target (≤ 200 ms) requires ≥ 25 MB ÷ 0.2 s = 125 MB/s effective throughput — comfortably below MessagePack reference-implementation throughput (typically several hundred MB/s), confirming the target has real margin.

35. Hard Questions (Self-Examination)

  1. Why must structural changes go through a CommandBuffer instead of mutating archetypes directly during iteration, and what specifically fails if the sync point is skipped? (§8.5, §17)
  2. How does the archetype-graph edge cache turn a transition lookup into O(1), and what invalidates that cache? (§8.2, §13)
  3. Using the accumulator algebra, derive why the renderer must interpolate rather than the simulation adapting its own timestep. (§8.6, §16)
  4. Why does per-column change-tick comparison dominate full value diffing as component count grows, and what false positive does it accept in exchange? (§8.3, §6 ADR-06 rationale is in §9)
  5. Why is the scheduler's conflict analysis bounded to O(systems × accessed components) rather than O(systems²), and what data structure makes that possible? (§18, §5)
  6. Why is generation-bump-then-swap the only safe hot-reload sequence, and what breaks under swap-then-bump? (§8.8, §20)
  7. Why must scene-graph propagation run after every system that could move a Transform in the same frame, and what regression class does violating this produce? (§8.9, §21, §25 FM-8)
  8. Why does this blueprint reject archetype storage's theoretical worst case (2^component-types archetypes) as a practical concern, and what actually bounds the real number? (§31, §34)
  9. Given Amdahl's law and the declared serial sync points, what is the maximum speedup a future native parallel executor could achieve for an 80%-conflict-free stage, and why does v1 realize none of it? (§31, §9 ADR-08)
  10. Why is a stale Entity handle detected by a generation mismatch rather than a runtime crash, and what would go wrong if Entity were a raw pointer instead? (§8.1, §7 I1)
  11. Walk the archetype-migration worked example and explain which invariant breaks if the swap-remove step is skipped. (§8.2, §7 I2)
  12. Why does event backpressure choose drop-oldest over an unbounded queue, and what failure mode does the unbounded alternative actually produce? (§8.7, §25 FM-11, §34)
  13. Why must deterministic replay's state hash be computed in canonical per-archetype row order rather than component-value order? (§22, §25 FM-10)
  14. Compare the archetype and sparse-set storage models' add/remove-vs-iterate tradeoff, and state the regime where each wins. (§36, §9 ADR-03)
  15. Why does the scheduler's grouping algorithm remain valuable even though v1's executor never actually parallelizes anything? (§18, §9 ADR-08)
  16. Derive the per-entity memory number in §34 from the component-count and average-size assumptions in §4, and state what would change it. (§4, §34)
  17. Why is a prefab load's failure semantics ("abort the whole load") deliberately stronger than a single command's failure semantics ("skip just that command"), and what breaks if a prefab load used the weaker guarantee? (§17, §22)
  18. Why does the physics integration seam give Physics-Engine sole write access to Transform during the PhysicsSync stage rather than sharing it with gameplay systems, and what scheduler mechanism enforces that? (§8, §9 ADR-18, §7 I3)

36. Alternative Architectures (Roads Not Taken)

1. Classic OOP scene-graph with inheritance-based game objects.

        GameObject
       /    |      \
  Character  Prop   Trigger
     |
  Enemy (virtual update(), virtual render())
     |
  Goblin  ── FlyingGoblin (multiple-inheritance problem)

Winning regime: small teams, editor-first, artist-driven workflows where node inheritance maps directly to how non-programmers reason about a scene. Real embodying system: Godot's scene tree (§33), early Unity's GameObject/MonoBehaviour model. Rejected here because virtual dispatch and per-object heap allocation defeat the cache-locality model (P4) this blueprint's throughput targets (§4) depend on, and inheritance hierarchies don't compose (the "flying goblin" problem).

2. Sparse-set ECS instead of archetypes.

SparseSet<Transform>: sparse[entity_id] -> dense_index -> Transform
SparseSet<Velocity> : sparse[entity_id] -> dense_index -> Velocity
add/remove: O(1) swap in one sparse set; iterate: jump across sets per entity

Winning regime: high structural churn relative to iteration — markers toggled every frame, roguelike per-turn component swaps. Real embodying system: EnTT (§5, §33). Rejected here because this blueprint's target profile (§1) is iteration-heavy steady-state simulation, where archetype's contiguous per-type columns win on throughput (§36 table, ADR-03).

3. Immediate-mode / data-flow engine with no persistent entity store.

frame(state_in, input) -> (state_out, render_commands)
// no World, no Entity table — every frame reconstructs everything it needs

Winning regime: tools and editors, or games whose entire state is small enough to recompute every frame without cost (turn-based board games, simple UI-driven apps). Real embodying system: Dear ImGui (the immediate-mode paradigm, widely used inside game-engine tooling). Rejected here because recompute-everything is incompatible with the million-entity, dirty-propagation-based scalability model (P11, §4) this blueprint targets.

4. Actor-model engine — each entity an independent message-driven process.

Entity_i: mailbox <- messages; process() -> new_state, outbound_messages
// no shared World; entities communicate only via message passing

Winning regime: distributed/networked simulation where entities genuinely run on different machines, or need hard per-entity failure isolation (e.g. sharded server-side simulation). Real embodying system: the actor model itself, as realized by Erlang/OTP, applied in some distributed game-server architectures. Rejected here because per-entity mailbox dispatch overhead is incompatible with the §4 throughput targets (M1, §30) — dense-column reads are orders of magnitude cheaper than per-entity message dispatch, and the model discards P4's cache-locality premise entirely.

38. Glossary

  • Entity — an opaque 64-bit handle (32-bit index + 32-bit generation) identifying a row across archetype storage (§8.1).
  • Component — a plain-data type stored in a dense column per archetype; never carries methods (P1).
  • System — a scheduled function with a statically-declared Access set (P6).
  • Archetype — a unique component-set signature; entities sharing one share dense column storage (§8.2).
  • Archetype graph — the memoized add/remove transition edges between archetypes (I7).
  • Sparse set — an alternative component-storage model, entity-id-to-dense-index per component type; rejected here for archetype storage (ADR-03, §36).
  • Dense column — contiguous per-component storage within one archetype (P4).
  • Generational index — an index+generation pair used to detect stale references (I1).
  • Query — a typed, cached iteration request over archetypes matching a QueryFilter (§8.3).
  • Query filter — a With/Without/Optional/Changed/Added matching predicate (§8.3).
  • Change detection — per-column tick comparison flagging writes since a system's last run (ADR-06).
  • Command buffer — a per-system queue of deferred structural changes (§8.5).
  • Sync point — the stage boundary at which command buffers are applied (I4).
  • Structural change — spawn, despawn, insert, remove, or reparent — anything altering archetype membership.
  • Fixed timestep — a constant simulation tick duration, decoupled from render rate (P2).
  • Accumulator — the real-time-to-simulation-time buffer driving fixed ticks (§8.6).
  • Interpolation alpha — the fractional position between two simulation ticks used for rendering (§8.6).
  • Spiral of death — unbounded accumulator growth when simulation cost exceeds the tick budget (I5).
  • Scene graph — the parent/child transform hierarchy expressed via components (ADR-14).
  • Dirty flag — a per-node marker triggering incremental transform recomputation (P11).
  • Transform propagation — recomputing GlobalTransform from Transform along a dirty scene-graph subtree (§8.9).
  • Prefab — a data-driven, versioned entity template referencing components by name (ADR-17).
  • Resource handle — a refcounted, generational reference to an asset's bytes (§8.8).
  • Hot reload — swapping an asset's bytes behind a stable handle via a generation bump (ADR-13).
  • Data-oriented design — organizing storage by access pattern rather than by object identity (P4).
  • False sharing — two logically-independent writers contending for the same cache line (FM-5).
  • Amdahl's law — the bound on parallel speedup imposed by a computation's serial fraction (§31).
  • Determinism — same inputs producing bit-identical outputs across runs (P7).
  • Replay divergence — a state-hash mismatch between a recorded and replayed run (FM-10).
  • Zero-sized type (ZST) — a marker component with no data, stored as presence-only (§13).
  • Event bus — the typed, double-buffered inter-system message channel (§8.7).
  • Double buffering — maintaining "current" and "previous" copies to give a bounded visibility window.
  • Backpressure — a bounded queue's explicit drop/reject policy under overload (ADR-31).
  • Refcounting — tracking live references to an asset to decide eviction timing (I9).
  • LoadState — an asset's lifecycle stage: Unloaded/Loading/Loaded/HotReloadPending/Failed/ Evicting (§8.12).
  • FrameStats — the always-on per-frame profiling ring buffer (§23).
  • Tick rate — the fixed simulation frequency, e.g. 60 Hz (§4).
  • GIL (Global Interpreter Lock) — CPython's single-thread-executes-bytecode-at-a-time constraint (ADR-08).
  • Work stealing — a scheduling strategy where idle workers pull tasks from busy ones' queues (§5, Cilk).
  • Topological sort — ordering a DAG's nodes so every edge points forward, used in Schedule.build (§15, §18).
  • Conflict graph — the graph of systems whose declared Access sets conflict (§8.4).
  • Parallel group — a set of systems provably safe to run concurrently (§18).
  • Extract stage — the snapshot step producing an immutable RenderFrame for the render seam (ADR-19).
  • RenderFrame — the immutable, interpolated-state package handed to Software Rasterizer (#169).
  • PhysicsSync — the stage synchronizing Transform with Physics-Engine's (#171) rigid-body state (ADR-18).
  • RigidBodyHandle — the opaque component linking an entity to Physics-Engine's body store.
  • SemVer — Semantic Versioning 2.0.0, the version-number contract (§27).
  • MessagePack — the binary serialization format used for prefabs/saves (ADR-16).
  • glTF — the Khronos scene/mesh interchange format used at the render seam (ADR-12).
  • Canonical order — the fixed, deterministic per-archetype row iteration order required for replay bit-equality (§22).
