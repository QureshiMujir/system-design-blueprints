Decisions (§9) · 26 ADRs

ADR-01

Language

Chosen

Python 3.12

Rejected

Rust; C++

When the rejected choice is right

Rust wins when the deliverable is a production, performance-first engine (see Bevy)

Why: teaching-optimized introspectable ECS/scheduler mechanics (§1)

ADR-02

Numeric core strategy

Chosen

numpy structured arrays per archetype column, array.array fallback for scalar-only columns

Rejected

pure Python lists of objects; Cython from day one

When the rejected choice is right

Cython wins once profiling (§30) shows the pure-Python scheduler loop, not storage, is the bottleneck

Why: dense, cache-friendly, vectorizable columns without a build step

ADR-03

Component storage layout

Chosen

archetype (table) storage

Rejected

sparse-set (EnTT-style); bitset-per-component

When the rejected choice is right

sparse-set wins when structural churn (add/remove) vastly outpaces iteration, e.g. markers toggled every frame

Why: iteration-heavy workloads dominate game loops (§36)

ADR-04

Entity ID encoding

Chosen

64-bit int = 32-bit generation + 32-bit index

Rejected

128-bit UUID; pointer-based handle

When the rejected choice is right

UUID wins in a distributed multiplayer authority model needing global uniqueness without a central allocator

Why: fits a Python int natively, hashable, generation check is one compare

ADR-05

Query caching

Chosen

archetype-set cache invalidated on new-archetype creation

Rejected

recompute matching archetypes every query call

When the rejected choice is right

recompute-every-call wins in a REPL/debug tool where correctness-under-hot-edit matters more than throughput

Why: archetype creation is rare relative to query calls (§34)

ADR-06

Change-detection mechanism

Chosen

per-column change tick compared to system's last-run tick

Rejected

full value diff each frame

When the rejected choice is right

value diff wins when component equality is cheaper than a tick compare AND false-positive ticks (write-without-change) must be eliminated

Why: O(1) per row vs O(component size) per row (P10)

ADR-07

Scheduler design

Chosen

explicit stages + inferred read/write dependency graph within a stage

Rejected

fully explicit manual ordering; fully inferred whole-schedule graph (no stages)

When the rejected choice is right

fully explicit ordering wins in a small, fixed pipeline (e.g. a 6-system tool) where the DAG-build cost isn't worth it

Why: stages give coarse deterministic sync points; inferred intra-stage graph gives free parallelism (P8)

ADR-08

Parallelism model

Chosen

single-threaded pure-Python executor in v1; access-analysis API substrate-agnostic for a future native core

Rejected

thread pool releasing the GIL per-system; multiprocessing worker pool

When the rejected choice is right

multiprocessing wins for a small number of genuinely heavy, infrequent systems (e.g. navmesh rebake) run off the hot path

Why: GIL prevents true CPU-bound thread speedup (P14); multiprocessing's IPC serialization cost exceeds most systems' per-frame budget

ADR-09

Structural-change strategy

Chosen

command buffer, applied at stage sync point

Rejected

immediate mutation with iterator-safety locks

When the rejected choice is right

immediate mutation wins in a single-threaded scripting console where no query is concurrently iterating

Why: avoids iterator invalidation without lock overhead (I4, P5)

ADR-10

Event-bus model

Chosen

typed, double-buffered, per-EventId queue

Rejected

pub/sub with per-listener callback

When the rejected choice is right

callback pub/sub wins for cross-cutting UI event wiring where deterministic replay isn't required

Why: double-buffering gives deterministic two-frame visibility without callback ordering hazards

ADR-11

Resource handles & lifetime

Chosen

refcounted generational ResourceHandle

Rejected

raw shared references (Python object identity)

When the rejected choice is right

raw references win for engine-internal singletons that never hot-reload (e.g. a fixed config object)

Why: supports hot reload without invalidating holder identity (P9)

ADR-12

Asset format

Chosen

glTF 2.0 for scenes/meshes (render seam); MessagePack for engine-native prefab/save

Rejected

custom binary mesh format; Protocol Buffers

When the rejected choice is right

Protocol Buffers wins when cross-language schema evolution tooling matters more than load simplicity

Why: glTF is the real interchange format the render seam (#169) expects; MessagePack is compact and schema-light

ADR-13

Hot reload

Chosen

filesystem watch (watchdog) + generation-bumped handle invalidation

Rejected

polling mtime each frame; no hot reload

When the rejected choice is right

mtime polling wins on filesystems without inotify/kqueue support (some network mounts)

Why: watch is event-driven, meets the 100 ms §4 target without per-frame stat() cost

ADR-14

Scene-graph representation

Chosen

component-based (Parent, Children on entities) + no separate tree object

Rejected

a standalone tree data structure outside the ECS

When the rejected choice is right

a standalone tree wins when the graph must be manipulated by non-ECS-aware tooling (e.g. an external DCC importer)

Why: keeps the graph queryable via the same ECS query engine (P13)

ADR-15

Transform update strategy

Chosen

dirty-flag propagation, topological (depth) order

Rejected

full recompute every frame; lazy pull-on-read

When the rejected choice is right

full recompute wins when most nodes move every frame anyway (e.g. a particle-heavy scene), removing propagation-order bookkeeping cost

Why: O(changed subtree) vs O(all nodes) (P11)

ADR-16

Serialization format

Chosen

MessagePack primary; JSON for debug/human diff

Rejected

JSON primary; a custom binary format

When the rejected choice is right

JSON-primary wins for a tool prioritizing diffability in version control over load speed

Why: MessagePack is compact, standard, and language-agnostic (§5 RFCs)

ADR-17

Prefab model

Chosen

data-driven file referencing component schemas by name + version

Rejected

code-generated prefab classes

When the rejected choice is right

code-generated classes win when compile-time type-checking of prefab fields matters more than data-driven flexibility

Why: matches Bilas's data-driven object system lesson (§5); no rebuild to add a prefab

ADR-18

Physics integration seam

Chosen

opaque RigidBodyHandle component + PhysicsSync stage

Rejected

Physics-Engine writes Transform directly every physics step

When the rejected choice is right

direct-write wins only if Physics-Engine is guaranteed the sole writer of Transform for the entity's lifetime (no gameplay override ever)

Why: keeps a single writer of Transform per frame, avoiding a race with gameplay systems (I3)

ADR-19

Render integration seam

Chosen

extract-and-snapshot pattern producing an immutable RenderFrame

Rejected

render seam reads live World state directly

When the rejected choice is right

direct-read wins in a strictly single-threaded, single-rate (no interpolation) toy renderer

Why: avoids a render-thread/sim-thread data race and decouples render cadence from sim cadence (P2)

ADR-20

Determinism policy

Chosen

fixed timestep + stable system order + seeded per-stream RNG

Rejected

wall-clock-driven variable timestep, unordered parallel execution

When the rejected choice is right

variable timestep wins for a non-replayable single-player game with no determinism requirement at all

Why: required for lockstep replay and reproducible tests (P7, §27)

ADR-21

Logging

Chosen

structured logging (stdlib logging + JSON formatter)

Rejected

plain-text print logging

When the rejected choice is right

plain-text wins for a quick prototype with no log-aggregation pipeline

Why: machine-parseable for CI and the profiler correlation (§26)

ADR-22

Tracing

Chosen

per-system, per-frame spans, sampled (OpenTelemetry-compatible)

Rejected

no tracing, only aggregate counters

When the rejected choice is right

aggregate-only wins when span overhead itself threatens the frame budget on very low-power targets

Why: pinpoints which system caused a frame-time spike (§26, FM-1)

ADR-23

Metrics/profiling

ring-buffer FrameStats + a phase-by-phase timer

Rejected

When the rejected choice is right

Testing

Fuzzing

Rejected

CI/CD

36. Alternative Architectures (Roads Not Taken)

1. Classic OOP scene-graph with inheritance-based game objects.

        GameObject
       /    |      \
  Character  Prop   Trigger
     |
  Enemy (virtual update(), virtual render())
     |
  Goblin  ── FlyingGoblin (multiple-inheritance problem)

Winning regime: small teams, editor-first, artist-driven workflows where node inheritance maps directly to how non-programmers reason about a scene. Real embodying system: Godot's scene tree (§33), early Unity's GameObject/MonoBehaviour model. Rejected here because virtual dispatch and per-object heap allocation defeat the cache-locality model (P4) this blueprint's throughput targets (§4) depend on, and inheritance hierarchies don't compose (the "flying goblin" problem).

2. Sparse-set ECS instead of archetypes.

SparseSet<Transform>: sparse[entity_id] -> dense_index -> Transform
SparseSet<Velocity> : sparse[entity_id] -> dense_index -> Velocity
add/remove: O(1) swap in one sparse set; iterate: jump across sets per entity

Winning regime: high structural churn relative to iteration — markers toggled every frame, roguelike per-turn component swaps. Real embodying system: EnTT (§5, §33). Rejected here because this blueprint's target profile (§1) is iteration-heavy steady-state simulation, where archetype's contiguous per-type columns win on throughput (§36 table, ADR-03).

3. Immediate-mode / data-flow engine with no persistent entity store.

frame(state_in, input) -> (state_out, render_commands)
// no World, no Entity table — every frame reconstructs everything it needs

Winning regime: tools and editors, or games whose entire state is small enough to recompute every frame without cost (turn-based board games, simple UI-driven apps). Real embodying system: Dear ImGui (the immediate-mode paradigm, widely used inside game-engine tooling). Rejected here because recompute-everything is incompatible with the million-entity, dirty-propagation-based scalability model (P11, §4) this blueprint targets.

4. Actor-model engine — each entity an independent message-driven process.

Entity_i: mailbox <- messages; process() -> new_state, outbound_messages
// no shared World; entities communicate only via message passing

Winning regime: distributed/networked simulation where entities genuinely run on different machines, or need hard per-entity failure isolation (e.g. sharded server-side simulation). Real embodying system: the actor model itself, as realized by Erlang/OTP, applied in some distributed game-server architectures. Rejected here because per-entity mailbox dispatch overhead is incompatible with the §4 throughput targets (M1, §30) — dense-column reads are orders of magnitude cheaper than per-entity message dispatch, and the model discards P4's cache-locality premise entirely.
