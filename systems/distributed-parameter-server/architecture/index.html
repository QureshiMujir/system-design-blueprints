3. Architectural Overview

                          [ Coordinator ]
                    (membership, shard-map, epochs)
                               |
   =========================  RPC BOUNDARY  =========================
   |                                                                 |
[ Worker Push/Pull Client ]  <====  push(grad) / pull(keys)  ====>   |
   |                                                                 |
   v                                                                 |
[ Consistency-Model Controller ]   (BSP barrier | ASP | SSP clock)   |
   |                                                                 |
   v                                                                 |
[ Compression Codec ]   (quantize / top-k sparsify / error-fb)       |
   |                                                                 |
   ========================  SHARD BOUNDARY  =========================
   |                                                                  |
   v                                                                  |
[ Hash Ring ]  --consistent-hash(key)-->  [ Server Shard 0 .. N-1 ]
                                                    |
                                                    v
                                    [ Aggregation / Optimizer Engine ]
                                                    |
                                                    v
                                    [ Replication / Failure-Recovery ]
                                            |                |
                                            v                v
                                [ Checkpoint Store ]   [ Elastic Membership Manager ]
                                                                |
                                                                v
                                                        (registers with Coordinator)

Coordinator. Publishes cluster membership, the current hash-ring epoch, and the shard-to-node map; never touches parameter data on the hot path (P10).

Worker Push/Pull Client. The worker-SDK half of the RPC boundary: batches gradients, issues push/pull calls, and applies the active consistency model's wait/no-wait semantics before returning control to the training loop.

Consistency-Model Controller. Enforces BSP's global barrier, ASP's no-wait pass-through, or SSP's per-worker clock and staleness bound (I1, §8.2).

Compression Codec. Quantizes or sparsifies the gradient payload before it crosses the shard boundary, carrying forward an error-feedback residual (I10, §8.5).

Hash Ring. Maps every parameter key deterministically to a primary shard and its R-1 replicas using consistent hashing with virtual nodes (Karger et al. 1997).

Server Shard. Owns a KeyRange of the parameter space, both dense and sparse; the unit of placement, replication, and failure (P4).

Aggregation/Optimizer Engine. Combines concurrently-pushed gradients from N workers and applies the optimizer update (SGD/momentum/Adam) to the shard's parameter and optimizer-state vectors (§8.4).

Replication/Failure-Recovery. Keeps R replicas of each shard consistent and promotes a replica to primary on failure without losing a committed update beyond the last checkpoint (I4).

Checkpoint Store. Persists periodic immutable snapshots of parameter and optimizer state for recovery and cold restart (I11).

Elastic Membership Manager. Drives the add/remove-node protocol, re-owning KeyRanges on the hash ring without dropping or duplicating a key (I6).

8. Domain Model

8.1 Push/Pull API Contract

Operation Input Output Dense/Sparse Semantics
push(WorkerId, ParamId, KeyRange, Gradient) gradient tensor or key-value deltas Ack(Version) both applied to aggregator, exactly once (I2)
pull(WorkerId, ParamId, KeyRange) requested key range PullResponse(Version, Values) both version obeys active consistency model (I1, I9)
push_sparse(WorkerId, ParamId, Vec<Key>, Vec<Gradient>) sparse key list + deltas Ack(Version) sparse only touched keys transmitted (P2)
pull_sparse(WorkerId, ParamId, Vec<Key>) sparse key list Vec<(Key, Value, Version)> sparse per-key version, not whole-tensor
barrier(WorkerId, Round) round number BarrierAck n/a BSP-only global synchronization point

8.2 Consistency-Model Spectrum

Model Staleness Definition Convergence Guarantee Clock Mechanism
BSP 0 — every pull sees all prior-round pushes matches single-node SGD (synchronous) global round barrier
ASP unbounded — pull sees whatever is currently applied converges under bounded-delay assumptions (Recht et al. 2011; Dean et al. 2012) none (pass-through)
SSP bounded by S ticks converges within an error term proportional to S (Ho et al. 2013) per-worker scalar clock, min-clock gates staleness

SSP staleness bound, display equation:

clock_fastest(w) - clock_slowest(w) <= S
pull(w, t) returns version v such that v.clock >= clock(w) - S

Worked example: S = 4. Worker A is at clock 12 (fastest); worker B is at clock 7. Since 12 - 7 = 5 > S = 4, the SSP controller throttles worker A's next push/pull until B advances to clock >= 8, at which point 12 - 8 = 4 <= S and A proceeds. This is the mechanism by which a straggler bounds — but does not indefinitely stall — the fastest worker (P3, I1).

8.3 Sharding and Placement

hash_ring: [0, 2^64) populated with V virtual nodes per physical shard
key -> hash(key) -> first virtual node clockwise -> owning ShardId
replica set: next R-1 distinct physical shards clockwise from owner

Worked mapping: key emb_47231 hashes to ring position 0x7fa2.... Walking clockwise, the first virtual node belongs to Shard-14; the next two distinct physical shards clockwise are Shard-19 and Shard-03, giving replica set {Shard-14 (primary), Shard-19, Shard-03}. Rebalancing example: adding Shard-40 inserts its V virtual nodes into the ring; only keys whose ring position now falls between Shard-40's virtual nodes and their immediate clockwise predecessor move — consistent hashing bounds this to roughly 1/N_shards of the keyspace (Karger et al. 1997), not a full reshuffle.

8.4 Aggregation and Optimizer Update

Given N workers pushing gradients g_1 .. g_n for parameter theta in a round:

g_agg = (1/N) * sum(g_i)                         // mean aggregation
m_t   = beta1 * m_(t-1) + (1 - beta1) * g_agg     // Adam first moment (server-side)
v_t   = beta2 * v_(t-1) + (1 - beta2) * g_agg^2   // Adam second moment (server-side)
theta_t = theta_(t-1) - lr * m_t / (sqrt(v_t) + eps)

Under ASP/SSP, N in the mean is the count of contributions actually received within the round/clock window, tracked per I12 to avoid double counting.

8.5 Gradient Compression

Scheme Mechanism Bandwidth Ratio Accuracy Cost Error Feedback
None (fp32) full-precision transmit 1x none n/a
QSGD quantization stochastic k-bit quantization (Alistarh et al. 2017) 4x-8x bounded variance, unbiased not required (unbiased)
Top-k sparsification transmit only top-k magnitude entries (Lin et al. 2018) 8x-32x biased if residual dropped required (I10)
Sparsification + error feedback top-k plus carried residual 8x-32x near-zero at moderate k with feedback accumulator per worker

8.6 Failure Recovery and Elastic Membership (sequence tables)

Shard-failure recovery:

Step Actor Action
1 Coordinator detects missed heartbeat from Shard-primary
2 Coordinator increments membership epoch (I8), selects freshest replica
3 Replica promoted to primary, resumes serving from last WAL-durable state
4 Coordinator publishes updated shard map
5 Workers refresh shard map, redirect push/pull

Elastic node-add:

Step Actor Action
1 New node registers with Coordinator, requests ring join
2 Coordinator computes virtual-node insertion, new epoch
3 Affected shards stream owned-key subset to new node
4 Coordinator publishes new shard map once transfer acks complete
5 Workers refresh shard map; in-flight requests to moved keys retried against new owner

8.7 Training-Step Lifecycle (state machine)

IDLE -> COMPUTE_GRADIENT -> PUSH -> [BSP: WAIT_BARRIER | ASP: none | SSP: WAIT_CLOCK]
     -> PULL -> APPLY_LOCAL -> IDLE
FAILURE at any state -> RETRY (bounded) -> IDLE | ABORT_STEP

8.8 Malformed and Failure Examples

  • A straggler exceeding the staleness bound: SSP controller throttles per §8.2's worked example; if the straggler never recovers, the coordinator flags it for straggler mitigation (Phase 10) rather than stalling the cluster indefinitely.
  • A shard failure mid-push: the push is not acked; the worker retries against the promoted replica (I2 ensures no double-apply even if the original push had partially landed in the WAL before failure).
  • A rebalance racing a push: the push is buffered against the old owner until the new shard map is published, then replayed against the new owner (I6).
  • A stale pull under ASP causing divergence: illustrated as a failure-path example below.
  • A compression scheme that biases the gradient: top-k sparsification without error feedback silently drops small-magnitude updates every round, producing a systematic bias detectable only by comparing against the uncompressed baseline (I10 exists specifically to prevent this).

Failure-path example: under ASP with no staleness bound, worker W pulls theta at global step 1000, computes a gradient against it, but by the time it pushes, 50 other workers have already advanced theta past step 1050. W's gradient is now computed against a 50-step-stale base. Left unbounded, this is exactly the noise Hogwild!/Downpour tolerate empirically (Recht et al. 2011; Dean et al. 2012) but SSP exists (§8.2) to bound it explicitly when unbounded staleness degrades convergence unacceptably.

8.9 Compound Interaction Example: Replication Under SSP Rebalance

A worked interaction showing why I1, I4, and I6 must compose rather than be reasoned about independently:

Step State Invariant at risk
1 Cluster runs SSP with S=4; worker A at clock 12, worker B (slowest) at clock 9 I1 (3 <= 4, no throttle yet)
2 Shard-9's primary fails mid-round; Coordinator begins replica promotion (Phase 7) I4 (must not lose committed updates)
3 Operator concurrently triggers a node-add rebalance touching Shard-9's key range (Phase 8) I6 (ownership must stay singular)
4 Epoch mechanism (I8) serializes: promotion completes at epoch e+1 before the rebalance's join is admitted at epoch e+2 I3, I8 (no dual-primary, no stale epoch wins)
5 Worker B, still slow, advances to clock 10; A is now at clock 13, gap is 3, still under S=4 I1 holds throughout the compound event

This is the concrete justification for §20.6 pitfall 2 (a rebalance racing a Phase-7 failover) and for treating epoch (I8) as the single serialization point across replication and elastic membership rather than inventing a second ad hoc lock.
