1. Goal & Scope

Build, from scratch in Rust, a distributed parameter server (PS): a cluster of sharded key-value servers holding the parameters (and server-side optimizer state) of a large ML model, exposing a push/pull RPC API to a pool of worker nodes that compute gradients locally and exchange them with the servers under a configurable consistency model — bulk-synchronous-parallel (BSP), fully asynchronous (ASP), or bounded-staleness stale-synchronous-parallel (SSP). The server aggregates gradients pushed concurrently by workers, applies an optimizer update (SGD, momentum, Adam) to its shard of the parameter vector, and serves updated or bounded-stale values back on pull, while a consistent-hashing placement layer with replication survives shard failure and an elastic membership protocol lets servers and workers join or leave without halting training. This is the canonical Li et al. 2014 OSDI parameter-server architecture, built independently down to the wire protocol, sharding logic, consistency clock, compression codec, and recovery layer.

Phase-0 deliverable (crate list):

  1. ps-proto — wire types, push/pull message schema, protocol versioning.
  2. ps-transport — gRPC transport, framing, backpressure.
  3. shard-core — Shard, ShardId, KeyRange, single in-memory dense store.
  4. hash-ring — consistent-hashing placement, virtual nodes.
  5. server-node — single-shard server binary: apply push, serve pull.
  6. worker-sdk — push/pull client library.
  7. coordinator — membership registry, shard-map publication.
  8. bench-harness — throughput/latency micro-benchmark scaffold.
  9. conformance-suite — fixture-driven push/pull contract tests.
  10. ci-pipeline — build/test/lint gates.

Boundaries.

Provides:

  • parameter storage and sharding,
  • push/pull serving,
  • gradient aggregation,
  • server-side optimizer state,
  • consistency-model enforcement (BSP/ASP/SSP),
  • replication and shard-failure recovery,
  • elastic membership,
  • gradient compression,
  • checkpointing,
  • straggler mitigation.

Delegates:

  • gradient computation (the forward/backward pass) to the worker and the framework it embeds,
  • model definition and graph construction to the framework,
  • loss/metric computation to the training loop.

Does NOT provide:

  • an autograd engine,
  • a compiler or graph optimizer,
  • GPU kernels,
  • a full training framework,
  • a distributed filesystem,
  • dataset loading.

Non-goals. This is not Distributed-Training-115 (the general distributed-training orchestration harness) and it is not a collective/all-reduce library (Horovod/NCCL-style ring all-reduce, Sergeev & Del Balso 2018):

  • those architectures have NO central server: every worker holds the full model and gradients are reduced peer-to-peer with no shard ever existing;
  • this project is deliberately the opposite architecture: a central sharded store that workers push gradients to and pull parameters from;
  • the contrast is load-bearing throughout this document — the PS wins on sparse/embedding-heavy models and elastic worker pools (§31, §33, §36); all-reduce wins on dense models at homogeneous, stable scale;
  • this blueprint is not a full training framework, not an autograd engine, and not a replacement for Distributed-Training-115's job orchestration.

Consistency models supported:

  • BSP — a global barrier; every pull in round t sees all pushes from round t-1 (Li et al. 2014 OSDI, Chilimbi et al. 2014 Project Adam).
  • ASP — a pull returns whatever is currently applied server-side, no barrier, no staleness bound (Dean et al. 2012 Downpour SGD; Recht et al. 2011 Hogwild!).
  • SSP — a pull may lag the fastest worker's clock by at most S ticks (Ho et al. 2013).

Deployment model:

  • a cluster of stateful server-shard processes, each owning a KeyRange partition of the parameter space and replicated R-way;
  • a lightweight coordinator publishing membership and the shard map;
  • a worker library linked into training processes;
  • workers and servers are separate process pools, typically on separate hosts, connected by gRPC.

Users/operators:

  • ML infrastructure engineers integrating the worker SDK into a training loop;
  • cluster operators sizing shards and replicas and running elastic scale events;
  • runtime developers extending the consistency or compression layer.

Later phases unlock:

  • sparse/embedding push-pull (Phase 4),
  • asynchronous and SSP training (Phases 5-6),
  • replicated fault-tolerant shards (Phase 7),
  • elastic rebalancing (Phase 8),
  • bandwidth-efficient compressed gradients (Phase 9),
  • a distributed convergence benchmark with chaos hardening (Phase 11).

Rust and rationale:

  • predictable tail latency without GC pauses — the p99 pull-latency target in §4 is incompatible with stop-the-world collection;
  • fearless concurrency for the per-shard aggregation path;
  • zero-cost prost/bincode serialization;
  • a mature async runtime (Tokio) for gRPC fan-in at 100k concurrent streams.

Rejected languages:

  • Go — GC pauses violate the p99 pull-latency target (§4);
  • C++ — memory-safety risk in a service parsing untrusted worker input over the network (§24 threat model);
  • Python — throughput floor incompatible with the GB/s aggregation target (§4, §30).

Prerequisites:

  • distributed systems (replication, partitioning, consensus — Kleppmann);
  • stochastic gradient descent and its asynchronous-convergence theory (Bertsekas & Tsitsiklis);
  • consistency models (linearizability vs. bounded staleness);
  • consistent hashing (Karger et al. 1997);
  • gRPC and Protocol Buffers as an RPC/serialization substrate.

Timeline:

  • Phase 0-3 (single-shard BSP, sharding, server-side aggregation) — 10 weeks;
  • Phase 4-6 (sparse parameters, ASP, SSP) — 10 weeks;
  • Phase 7-9 (replication, elasticity, compression) — 10 weeks;
  • Phase 10-11 (checkpointing/stragglers, benchmark/chaos hardening) — 6 weeks.

Deferrals:

  • PhaseDeferred("§9 ADR-08 RDMA transport") — zero-copy RDMA transport, deferred until the gRPC transport's bandwidth ceiling is measured in Phase 11.
  • PhaseDeferred("§31 PS-vs-all-reduce hybrid") — a hybrid PS/all-reduce mode for mixed dense/sparse models, deferred pending the crossover analysis in §34.
  • PhaseDeferred("§36 sharded-optimizer ZeRO-style partitioning") — full ZeRO-style optimizer-state sharding as an alternative default, deferred until the classic-PS optimizer-state placement (ADR-09) is load-tested.
  • PhaseDeferred("§24 T1 Byzantine-robust aggregation") — Byzantine-fault-tolerant gradient aggregation beyond T1's gradient-norm-clipping mitigation, deferred until the honest-failure recovery model (Phase 7) is hardened.

Coordinator. Publishes cluster membership, the current hash-ring epoch, and the shard-to-node map; never touches parameter data on the hot path (P10).

Worker Push/Pull Client. The worker-SDK half of the RPC boundary: batches gradients, issues push/pull calls, and applies the active consistency model's wait/no-wait semantics before returning control to the training loop.

Consistency-Model Controller. Enforces BSP's global barrier, ASP's no-wait pass-through, or SSP's per-worker clock and staleness bound (I1, §8.2).

Compression Codec. Quantizes or sparsifies the gradient payload before it crosses the shard boundary, carrying forward an error-feedback residual (I10, §8.5).

Hash Ring. Maps every parameter key deterministically to a primary shard and its R-1 replicas using consistent hashing with virtual nodes (Karger et al. 1997).

Server Shard. Owns a KeyRange of the parameter space, both dense and sparse; the unit of placement, replication, and failure (P4).

Aggregation/Optimizer Engine. Combines concurrently-pushed gradients from N workers and applies the optimizer update (SGD/momentum/Adam) to the shard's parameter and optimizer-state vectors (§8.4).

Replication/Failure-Recovery. Keeps R replicas of each shard consistent and promotes a replica to primary on failure without losing a committed update beyond the last checkpoint (I4).

Checkpoint Store. Persists periodic immutable snapshots of parameter and optimizer state for recovery and cold restart (I11).

Elastic Membership Manager. Drives the add/remove-node protocol, re-owning KeyRanges on the hash ring without dropping or duplicating a key (I6).

6. Design Principles

  • P1. The parameter server trades consistency for throughput on a documented spectrum — BSP is correct-but-slow, ASP is fast-but-noisy, SSP bounds the staleness so convergence still holds (Ho et al. 2013); the model picks a point and states its convergence implication (§8.2).
  • P2. Sparse (embedding) parameters dominate real models, so the push/pull API is range- and key-based, not whole-model, because moving the whole model every step is the bottleneck the PS exists to avoid (P2, §11, Phase 4).
  • P3. A straggler must never stall the fastest worker beyond the staleness bound, so the clock, not the slowest node, gates progress (I1, Phase 6, Phase 10).
  • P4. A shard is the unit of ownership, replication, and failure; nothing about placement is per-key at the concurrency-control level (I3, §8.4).
  • P5. Every push must be idempotent under retry — the aggregation must apply an update exactly once even if the RPC is retried (I2).
  • P6. Compression is a lossy transform with a measurable accuracy cost; it must never be adopted without a stated variance/bias bound (QSGD, Alistarh et al. 2017) (§8.5, Phase 9).
  • P7. Elastic membership changes must never drop or duplicate ownership of a key mid-rebalance (I6, Phase 8).
  • P8. Optimizer state (momentum, Adam moments) lives with the parameter it governs so a shard failure recovers both atomically (I5, ADR-09).
  • P9. Backpressure must be explicit and bounded at every queue — an unbounded push queue is an unbounded staleness violation waiting to happen (§7, §30).
  • P10. The coordinator holds membership and placement metadata only; it must never sit on the parameter-data hot path (§3).
  • P11. Checkpointing must be non-blocking with respect to push/pull serving; a checkpoint that stalls training defeats its own purpose (Phase 10).
  • P12. Every consistency model must be testable against a single-node SGD baseline within a stated numerical tolerance; "converges" is not a claim without that comparison (§28).
  • P13. Replication must tolerate the loss of any single shard's primary without operator intervention within the RTO target (§4, I4).
  • P14. A worker's staleness clock advances only on a committed pull, never on a send — clocks must reflect observed, not attempted, state (§8.2).

8.2 Consistency-Model Spectrum

Model Staleness Definition Convergence Guarantee Clock Mechanism
BSP 0 — every pull sees all prior-round pushes matches single-node SGD (synchronous) global round barrier
ASP unbounded — pull sees whatever is currently applied converges under bounded-delay assumptions (Recht et al. 2011; Dean et al. 2012) none (pass-through)
SSP bounded by S ticks converges within an error term proportional to S (Ho et al. 2013) per-worker scalar clock, min-clock gates staleness

SSP staleness bound, display equation:

clock_fastest(w) - clock_slowest(w) <= S
pull(w, t) returns version v such that v.clock >= clock(w) - S

Worked example: S = 4. Worker A is at clock 12 (fastest); worker B is at clock 7. Since 12 - 7 = 5 > S = 4, the SSP controller throttles worker A's next push/pull until B advances to clock >= 8, at which point 12 - 8 = 4 <= S and A proceeds. This is the mechanism by which a straggler bounds — but does not indefinitely stall — the fastest worker (P3, I1).

8.3 Sharding and Placement

hash_ring: [0, 2^64) populated with V virtual nodes per physical shard
key -> hash(key) -> first virtual node clockwise -> owning ShardId
replica set: next R-1 distinct physical shards clockwise from owner

Worked mapping: key emb_47231 hashes to ring position 0x7fa2.... Walking clockwise, the first virtual node belongs to Shard-14; the next two distinct physical shards clockwise are Shard-19 and Shard-03, giving replica set {Shard-14 (primary), Shard-19, Shard-03}. Rebalancing example: adding Shard-40 inserts its V virtual nodes into the ring; only keys whose ring position now falls between Shard-40's virtual nodes and their immediate clockwise predecessor move — consistent hashing bounds this to roughly 1/N_shards of the keyspace (Karger et al. 1997), not a full reshuffle.

8.4 Aggregation and Optimizer Update

Given N workers pushing gradients g_1 .. g_n for parameter theta in a round:

g_agg = (1/N) * sum(g_i)                         // mean aggregation
m_t   = beta1 * m_(t-1) + (1 - beta1) * g_agg     // Adam first moment (server-side)
v_t   = beta2 * v_(t-1) + (1 - beta2) * g_agg^2   // Adam second moment (server-side)
theta_t = theta_(t-1) - lr * m_t / (sqrt(v_t) + eps)

Under ASP/SSP, N in the mean is the count of contributions actually received within the round/clock window, tracked per I12 to avoid double counting.

Shard-failure recovery:

Step Actor Action
1 Coordinator detects missed heartbeat from Shard-primary
2 Coordinator increments membership epoch (I8), selects freshest replica
3 Replica promoted to primary, resumes serving from last WAL-durable state
4 Coordinator publishes updated shard map
5 Workers refresh shard map, redirect push/pull

Elastic node-add:

Step Actor Action
1 New node registers with Coordinator, requests ring join
2 Coordinator computes virtual-node insertion, new epoch
3 Affected shards stream owned-key subset to new node
4 Coordinator publishes new shard map once transfer acks complete
5 Workers refresh shard map; in-flight requests to moved keys retried against new owner

IDLE -> COMPUTE_GRADIENT -> PUSH -> [BSP: WAIT_BARRIER | ASP: none | SSP: WAIT_CLOCK]
     -> PULL -> APPLY_LOCAL -> IDLE
FAILURE at any state -> RETRY (bounded) -> IDLE | ABORT_STEP

8.8 Malformed and Failure Examples

  • A straggler exceeding the staleness bound: SSP controller throttles per §8.2's worked example; if the straggler never recovers, the coordinator flags it for straggler mitigation (Phase 10) rather than stalling the cluster indefinitely.
  • A shard failure mid-push: the push is not acked; the worker retries against the promoted replica (I2 ensures no double-apply even if the original push had partially landed in the WAL before failure).
  • A rebalance racing a push: the push is buffered against the old owner until the new shard map is published, then replayed against the new owner (I6).
  • A stale pull under ASP causing divergence: illustrated as a failure-path example below.
  • A compression scheme that biases the gradient: top-k sparsification without error feedback silently drops small-magnitude updates every round, producing a systematic bias detectable only by comparing against the uncompressed baseline (I10 exists specifically to prevent this).

Failure-path example: under ASP with no staleness bound, worker W pulls theta at global step 1000, computes a gradient against it, but by the time it pushes, 50 other workers have already advanced theta past step 1050. W's gradient is now computed against a 50-step-stale base. Left unbounded, this is exactly the noise Hogwild!/Downpour tolerate empirically (Recht et al. 2011; Dean et al. 2012) but SSP exists (§8.2) to bound it explicitly when unbounded staleness degrades convergence unacceptably.

8.9 Compound Interaction Example: Replication Under SSP Rebalance

A worked interaction showing why I1, I4, and I6 must compose rather than be reasoned about independently:

Step State Invariant at risk
1 Cluster runs SSP with S=4; worker A at clock 12, worker B (slowest) at clock 9 I1 (3 <= 4, no throttle yet)
2 Shard-9's primary fails mid-round; Coordinator begins replica promotion (Phase 7) I4 (must not lose committed updates)
3 Operator concurrently triggers a node-add rebalance touching Shard-9's key range (Phase 8) I6 (ownership must stay singular)
4 Epoch mechanism (I8) serializes: promotion completes at epoch e+1 before the rebalance's join is admitted at epoch e+2 I3, I8 (no dual-primary, no stale epoch wins)
5 Worker B, still slow, advances to clock 10; A is now at clock 13, gap is 3, still under S=4 I1 holds throughout the compound event

This is the concrete justification for §20.6 pitfall 2 (a rebalance racing a Phase-7 failover) and for treating epoch (I8) as the single serialization point across replication and elastic membership rather than inventing a second ad hoc lock.

15.8 Edge Cases

  • A round with zero contributors (all workers stalled) — aggregator must not divide by zero.
  • A push arriving after its round has already been aggregated and applied (late push under BSP timeout from Phase 1).

15.9 Failure Analysis

  • Failure: optimizer-state checksum mismatch detected on shard restart.
  • Detection: I5's checksum-mismatch counter.
  • Recovery: replay from the last WAL-durable atomic record; if WAL is also corrupt, fall back to the last committed checkpoint (I11, forward reference to Phase 10).

15.10 Operational Notes

Export aggregation_contributor_count and optimizer_state_checksum_mismatches_total from this phase; both feed the §26 dashboards and the Phase 11 chaos-test assertions.

16. Phase 4 — Sparse / Embedding Parameters

16.1 Objectives

Implement the sparse/embedding parameter path (push_sparse/pull_sparse, §8.1) so only touched keys are transmitted, per P2's founding rationale for the entire PS architecture.

16.2 Detailed Implementation Steps

  • Implement sparse-store's SparseParam (§11) as a per-shard key-value map, distinct storage from DenseParam but sharing the same KeyRange/placement machinery from Phase 2 (ADR-07).
  • Implement push_sparse/pull_sparse RPCs (§8.1) transmitting only the referenced key list, not the full embedding table.
  • Extend the aggregator (Phase 3) to accumulate per-key sparse gradients rather than a dense tensor sum.
  • Extend optimizer state (Adam moments) to a sparse Map<Key, MomentState> so untouched embedding rows carry zero storage/update cost (ADR-09).
  • Benchmark push/pull bytes-on-wire for a 100M-row embedding table touched by 0.01% of keys per step against the MXNet KVStore row_sparse_pull reference behavior (§5).

16.3 Deliverable

A sparse embedding table (>=100M rows) served correctly under concurrent sparse push/pull from multiple workers, with per-key optimizer state.

16.4 Acceptance Criteria

  • Bytes-on-wire for a sparse push touching 0.01% of a 100M-row table is within 2x of the theoretical minimum (touched-keys x row-width), not proportional to table size (P2).
  • Sparse pull p99 latency < 35 ms at 4096 concurrent workers (§4 target), each requesting <= 1000 keys.
  • Sparse Adam moment state differential-matches a single-node sparse-Adam reference within 1e-5 (extends P12 to the sparse path).

  • fixtures/sparse/embedding_100m_rows_push_pull.json
  • fixtures/sparse/sparse_adam_differential.json
  • fixtures/sparse/zero_touch_storage_cost.json

16.6 Pitfalls

  1. Accidentally materializing the full embedding table when computing a partial pull response (defeats the entire point of P2).
  2. Sparse and dense paths diverging in hashing/placement logic, breaking a single key's consistent shard ownership (I3) across the two representations.
  3. Per-key optimizer-state map growth without an eviction/compaction story, silently inflating shard memory over a long-running job.
  4. Sparse gradient aggregation naively iterating all keys in the shard rather than only the touched set, turning an O(touched) operation into O(shard size).

16.7 Performance Concerns

  • Hash-map overhead per sparse key access vs. array indexing for dense — profile and consider a specialized concurrent hash map for the hot path.
  • Serialization overhead of a sparse key list at high fan-in (4096 workers x up to 1000 keys each per round).

16.8 Edge Cases

  • A pull for a key never before pushed (must return a defined default/zero embedding row, not an error).
  • Two workers touching disjoint keys in the same shard concurrently (must not serialize on a shard-wide lock, only per-key or per-bucket).

16.9 Failure Analysis

  • Failure: sparse optimizer-state map grows unbounded under a job with a long-tail key distribution.
  • Detection: shard memory watermark alert (feeds §4's per-shard memory constraint).
  • Recovery: operator-triggered compaction pass evicting cold keys per a documented staleness policy, logged for audit.

16.10 Operational Notes

Track per-shard sparse key cardinality and touched-key ratio per round as first-class metrics; both are needed to size shard memory correctly under §4's constraints as embedding tables grow.

17. Phase 5 — Asynchronous (ASP) Mode

17.1 Objectives

Implement fully asynchronous training: pulls return whatever is currently applied server-side, with no barrier and no staleness bound, matching Dean et al. 2012's Downpour SGD and grounded in Hogwild!'s lock-free convergence argument (Recht et al. 2011).

17.2 Detailed Implementation Steps

  • Extend consistency's ConsistencyModel::Asp variant (§11, ADR-05) as a pass-through: no barrier wait, no clock check on pull.
  • Ensure the aggregator (Phase 3) applies each push immediately on arrival under ASP rather than buffering for a round boundary (contrast with BSP's I9).
  • Implement the lock-free/fine-grained-locked update path per shard so concurrent asynchronous pushes do not serialize on a single mutex (Hogwild!'s lock-free argument, applied at the shard-partition granularity here rather than truly lock-free memory, since correctness under I2/I5 still requires atomicity per key).
  • Build the ASP convergence-vs-BSP comparison harness on the toy problem and a larger benchmark model (feeds Phase 11's convergence gate).
  • Document, in docs/performance/, the observed convergence noise introduced by ASP relative to the BSP baseline from Phase 1 (§8.8's failure-path example made empirical).

17.3 Deliverable

An ASP training mode selectable via ConsistencyModel::Asp, benchmarked against the Phase 1 BSP baseline on the same toy and benchmark models.

17.4 Acceptance Criteria

  • ASP throughput >= 2x BSP throughput at 16 workers on the benchmark model (no barrier wait cost, §8.2).
  • ASP converges to within a documented, bounded loss-gap of the BSP baseline on the benchmark model (numeric target set from the Phase 5 benchmark run, recorded in docs/performance/asp_vs_bsp.md).
  • Zero deadlocks or livelocks detected under a 24-hour ASP soak with 64 concurrent workers.

17.5 Conformance Fixtures

  • fixtures/asp/no_barrier_immediate_apply.json
  • fixtures/asp/convergence_vs_bsp_benchmark.json
  • fixtures/asp/concurrent_push_stress_64_workers.pb

17.6 Pitfalls

  1. Assuming ASP is "just BSP without the barrier" in the aggregator's code path — the immediate-apply semantics change contributor-counting (I12) and dedup (I2) timing assumptions.
  2. Introducing a data race on the parameter array under concurrent unsynchronized writes while chasing Hogwild!-style lock-freedom too literally — Hogwild!'s theoretical justification tolerates rare overwrites for dense SGD, but the PS's exactly-once (I2) and optimizer-consistency (I5) invariants still require per-key atomicity.
  3. Failing to bound ASP's implicit staleness at all, producing divergence on models where Hogwild!'s sparsity assumption does not hold (motivates Phase 6's SSP).
  4. Not instrumenting per-push apply latency, making the ASP-vs-BSP throughput comparison unverifiable.

17.7 Performance Concerns

  • Per-key atomic update contention when multiple workers target overlapping dense ranges concurrently.
  • Cache-line contention (false sharing) on adjacent parameter array elements under high ASP push concurrency.

17.8 Edge Cases

  • A push arrives for a key mid-optimizer-update on that same key from a different worker (I5 must still hold post-update).
  • A worker under ASP never calls barrier (must simply be a no-op, not an error, since ASP has no barrier concept).

17.9 Failure Analysis

  • Failure: ASP benchmark shows divergence beyond the documented bound.
  • Detection: the Phase 11 convergence-benchmark CI gate (§28) fails.
  • Recovery: fall back to SSP with a tuned bound (Phase 6) for that workload rather than shipping unbounded ASP, documented as an operational recommendation in §26.

17.10 Operational Notes

Publish the ASP-vs-BSP throughput and convergence comparison as a standing dashboard; operators choosing a consistency model for a given job need this data, not a folklore recommendation.

18. Phase 6 — Bounded-Staleness SSP with the Clock

18.1 Objectives

Implement Stale Synchronous Parallel (Ho et al. 2013): a per-worker scalar clock, a global staleness bound S, and a controller that throttles the fastest worker rather than the slowest (P3, I1).

18.2 Detailed Implementation Steps

  • Implement consistency's ConsistencyModel::Ssp { bound } with per-worker Clock tracking (§11, ADR-06).
  • Implement the staleness-bound check on pull: pull(w, t) returns a version with clock >= clock(w) - S (§8.2 equation).
  • Implement the throttle path: when clock_fastest - clock_slowest > S, block the fastest worker's next pull until the slowest advances (§8.2 worked example, reproduced as an executable fixture).
  • Wire clock advancement strictly on committed pull, not on push send (P14) — verify with a fixture that a worker retrying a send does not double-advance its clock.
  • Extend the ASP/BSP differential-convergence harness (Phase 5) to include SSP at multiple bound values (S=0 degenerates toward BSP-like behavior, S=infinity toward ASP) and confirm the expected monotonic convergence-vs-throughput tradeoff.

18.3 Deliverable

An SSP mode with a configurable staleness bound, demonstrated throttling a fast worker against a deliberately slow one, and a convergence-vs-S sweep.

18.4 Acceptance Criteria

  • At S=4, a worker running 5 ticks ahead of the slowest is throttled within one pull call (§8.2 worked example reproduced exactly).
  • I1 (no pull staler than S) holds with zero violations over a 100,000-round stress run at S in {0, 2, 4, 8, 16}.
  • The convergence-vs-S sweep shows monotonically improving convergence (decreasing loss-gap vs. BSP baseline) as S decreases, matching Ho et al. 2013's qualitative claim.

18.5 Conformance Fixtures

  • fixtures/ssp/staleness_bound_throttle_s4.json
  • fixtures/ssp/clock_advance_on_pull_not_push.json
  • fixtures/ssp/convergence_sweep_s_0_2_4_8_16.json

18.6 Pitfalls

  1. Advancing the clock on push-send instead of pull-commit (violates P14), making the staleness bound measure the wrong thing.
  2. Computing clock_fastest - clock_slowest using a stale cached view of other workers' clocks instead of the coordinator's authoritative minimum, producing spurious throttling or missed violations.
  3. Deadlocking all workers at S=0 if S=0 is implemented as "wait forever" instead of "behave like BSP's round barrier" — S=0 has a well-defined non-deadlocking semantics that must be tested explicitly.
  4. Treating a crashed worker's frozen clock as legitimately "slowest," stalling the entire cluster indefinitely — needs a liveness timeout (foreshadows Phase 10's straggler mitigation, not fully solved here).

18.7 Performance Concerns

  • Global min-clock computation cost as worker count grows — avoid an O(workers) scan per pull; maintain an incrementally-updated minimum.
  • Throttle-wait bookkeeping overhead must stay negligible relative to actual pull latency at low S.

18.8 Edge Cases

  • Exactly clock_fastest - clock_slowest == S (boundary, must NOT throttle — only > S throttles per §8.2).
  • A worker's clock that never advances due to a bug elsewhere (must not be silently tolerated as "slow"; feeds Phase 10's straggler-vs-failure distinction).

18.9 Failure Analysis

  • Failure: I1 violation detected (a pull served staler than S).
  • Detection: staleness-bound violation counter (§7 I1 row).
  • Recovery: reject the pull, force the worker to wait for a fresh minimum-clock recompute, and flag the incident for forensic replay since I1 is a correctness invariant, not a soft target.

18.10 Operational Notes

Publish staleness_ticks_observed as a histogram from this phase forward; it is the primary signal for choosing S in production and the direct input to Phase 10's straggler-tolerance tuning.

19. Phase 7 — Replication and Shard-Failure Recovery

19.1 Objectives

Implement R-way shard replication and automatic primary-replica failover so a shard failure loses no committed update beyond the last checkpoint (I4) within the RTO target (§4).

19.2 Detailed Implementation Steps

  • Implement replication's synchronous-ack replica protocol (ADR-10): a push is acked to the worker only after the primary and a write-quorum of replicas have durably applied it.
  • Implement replica-lag tracking and the freshest-replica-selection logic used on primary failure (§8.6 shard-failure sequence table).
  • Implement the coordinator's failure-detection heartbeat and epoch-fenced promotion (I3, I8) — a demoted former-primary must reject further writes once a higher epoch is observed.
  • Implement WAL replay on the promoted replica to reconstruct any in-flight state not yet reflected in its applied parameter/optimizer values (I7).
  • Chaos-test: kill the primary of a live shard mid-push-storm and verify recovery within the RTO target with zero committed-update loss (I4), differentially checked against a no-failure control run.

19.3 Deliverable

A replication factor R=3 cluster surviving an injected primary-shard kill with automatic promotion and zero committed-update loss.

19.4 Acceptance Criteria

  • Shard-failure recovery (heartbeat-miss to promoted-and-serving) completes in < 10 seconds (§4 RTO target), measured over 50 injected-kill trials.
  • Zero committed-update loss (RPO=0) detected across all 50 trials (I4), verified by comparing promoted-replica state against a pre-kill WAL tail checksum.
  • Zero dual-primary conditions (I3) detected during any promotion, verified by the epoch-fencing audit.

19.5 Conformance Fixtures

  • fixtures/replication/primary_kill_mid_push_storm.yaml
  • fixtures/replication/epoch_fencing_dual_primary_attempt.json
  • fixtures/replication/wal_replay_after_promotion.bin

19.6 Pitfalls

  1. Acking a push to the worker before the write-quorum of replicas has durably applied it, silently reducing the effective replication factor under load (violates ADR-10's stated guarantee).
  2. A demoted former-primary continuing to accept writes from workers with a stale shard map, producing split-brain (I3) — the epoch check must be enforced at the shard, not only at the coordinator.
  3. Replica-lag measurement using wall-clock timestamps under clock skew (§4's clock-skew tolerance) instead of a monotonic sequence/LSN comparison.
  4. Promoting a replica that is not actually the freshest (a stale replica promoted while a fresher one is merely slow to report lag), losing committed updates in violation of I4.
  5. WAL replay on promotion re-applying already-applied entries, violating I2's exactly-once guarantee across a failover boundary.

19.7 Performance Concerns

  • Synchronous replica-ack latency added to every push under ADR-10 — measure and report as a documented p99 pull/push-ack latency cost, not hidden.
  • Replica catch-up bandwidth during heavy write load competing with foreground push/pull traffic.

19.8 Edge Cases

  • Simultaneous failure of the primary and one replica (must degrade gracefully at R=3, not lose data if at least one replica survives with the latest committed WAL entry).
  • A network partition isolating the primary from all replicas but not from workers (must not let the isolated primary keep acking writes that cannot reach quorum).

19.9 Failure Analysis

  • Failure: dual-primary detected during a promotion race.
  • Detection: I3's dual-primary-conflict alert.
  • Recovery: fence the lower epoch immediately, replay the higher-epoch primary's WAL as authoritative, and run the ownership-audit sweep (I6, Phase 2) to confirm a single consistent view before resuming traffic.

19.10 Operational Notes

Publish replica_lag_ms and RTO-per-incident as standing metrics; the shard-failure-recovery runbook under docs/runbooks/ is written against this phase's chaos-test results, not against theory.

20. Phase 8 — Elastic Add/Remove-Node Rebalancing

20.1 Objectives

Implement the elastic membership protocol (§8.6 node-add sequence table) so servers can join or leave the cluster during live training without dropping or duplicating key ownership (I6) or halting workers.

20.2 Detailed Implementation Steps

  • Implement membership-elastic's join protocol: coordinator registration, virtual-node insertion into the HashRing (Phase 2), epoch bump (I8, ADR-04).
  • Implement owned-key streaming from affected shards to the new node before the new shard map is published, so the map-publish moment is atomic with respect to data availability.
  • Implement the leave/drain protocol: a departing node streams its owned keys to their new owners and only deregisters after the coordinator confirms all transfers acked.
  • Extend worker-sdk's shard-map refresh to handle in-flight requests to keys mid-transfer (buffer-and-retry against the new owner, per §8.6 step 5).
  • Re-run Phase 2's ownership-audit sweep after every elastic event as a mandatory CI gate for this phase, not an optional check.
  • Chaos-test: add and remove nodes repeatedly during a live SSP training run (Phase 6) and verify zero I1/I6 violations and bounded convergence impact.

20.3 Deliverable

A cluster that scales from 8 to 16 shards and back during a live training run with zero dropped/duplicated keys and a measured rebalance-convergence time.

20.4 Acceptance Criteria

  • Elastic add/remove-node convergence (join request to shard-map-published) completes in < 30 seconds for a 64-shard ring (§4 target).
  • Zero unowned or double-owned keys (I6) detected across 100 consecutive add/remove events.
  • Training throughput degradation during a rebalance event stays within a documented, bounded percentage (recorded from the Phase 8 benchmark run) rather than an unbounded stall.

20.5 Conformance Fixtures

  • fixtures/elastic/add_node_8_to_9_shards.json
  • fixtures/elastic/remove_node_drain_protocol.json
  • fixtures/elastic/repeated_scale_events_ownership_audit.json

20.6 Pitfalls

  1. Publishing the new shard map before owned-key streaming completes, creating a window where the new owner is authoritative but empty (violates I6 in spirit even if the audit technically passes momentarily).
  2. Racing a rebalance against an in-flight Phase 7 failover — the epoch mechanism (I8) must serialize these, not assume they never coincide.
  3. A departing node deregistering before all transfer acks are confirmed, losing keys mid-drain.
  4. Worker-side shard-map cache not invalidating promptly on epoch bump, causing a burst of ShardUnavailable errors right after a scale event.

20.7 Performance Concerns

  • Owned-key transfer bandwidth competing with foreground push/pull traffic during a large rebalance — needs explicit rate limiting, not best-effort.
  • Virtual-node ring recomputation cost at high shard counts (revisit Phase 2's incremental-insert implementation under real elastic load).

20.8 Edge Cases

  • Two nodes joining simultaneously (concurrent epoch bumps must serialize, extending Phase 2's edge case to the live elastic path).
  • A node leaving while it is the sole surviving replica for some key range mid-drain (must be rejected or deferred until replication is restored, interacting with Phase 7's I4).

20.9 Failure Analysis

  • Failure: a rebalance races a Phase-7 failover, producing an ambiguous shard map.
  • Detection: ownership-audit sweep failure immediately post-event.
  • Recovery: halt further rebalance/failover activity, run the audit to determine the authoritative epoch, and replay from the higher-epoch coordinator state before resuming.

20.10 Operational Notes

21. Phase 9 — Gradient Compression (Quantization, Sparsification, Error Feedback)

21.1 Objectives

Implement the compression codec stack (§8.5): QSGD-style quantization, top-k sparsification, and error feedback, each with a measured bandwidth-vs-accuracy tradeoff (Alistarh et al. 2017; Lin et al. 2018).

21.2 Detailed Implementation Steps

  • Implement compression's Compressor trait (§11) with a quantization codec following QSGD's stochastic k-bit scheme, preserving its unbiasedness property (Alistarh et al. 2017) — no error feedback required for this codec (§8.5 table).
  • Implement a top-k sparsification codec (Lin et al. 2018) that carries a per-worker ErrorFeedback residual forward (I10) rather than dropping untransmitted entries.
  • Wire the codec selection into push's client-side path (ADR-13) and the corresponding server-side decode.
  • Benchmark bytes-on-wire reduction and top-1/loss accuracy delta for each codec against the Phase 3/6 uncompressed baseline, at multiple compression ratios (4x, 8x, 16x, 32x).
  • Verify I10 with a fixture that deliberately drops residual injection and confirms the resulting measurable bias, then confirms the bias disappears when residual injection is restored.

21.3 Deliverable

Selectable quantization and sparsification codecs with error feedback, each benchmarked for bandwidth savings and accuracy cost against the uncompressed baseline.

21.4 Acceptance Criteria

  • QSGD quantization achieves >= 4x bandwidth reduction with < 1% top-1 relative accuracy degradation on the benchmark model (§4 compression target).
  • Top-k sparsification with error feedback achieves >= 8x bandwidth reduction with < 1% degradation; without error feedback, the fixture in §21.2 must show materially worse degradation, proving I10's necessity.
  • Zero silent residual-drop events (I10) detected over a 24-hour run with sparsification enabled.

21.5 Conformance Fixtures

  • fixtures/compression/qsgd_quantization_ratio_sweep.json
  • fixtures/compression/topk_with_without_error_feedback.json
  • fixtures/compression/residual_injection_bias_proof.json

21.6 Pitfalls

  1. Implementing top-k sparsification without error feedback "to keep it simple," silently reproducing the exact bias I10 exists to prevent.
  2. Applying quantization's stochastic rounding with a biased random-number source, breaking QSGD's unbiasedness guarantee in a way that will not show up in a quick smoke test.
  3. Comparing compressed-vs-uncompressed accuracy on too few training steps to detect a slow-accumulating bias — the benchmark must run long enough for error feedback's correction to matter.
  4. Storing the error-feedback residual per-shard instead of per-worker, corrupting the correction when multiple workers touch the same key (residual is a per-source correction, not a per-destination one).

21.7 Performance Concerns

  • Quantization/decompression CPU cost on the server's hot aggregation path — must not offset the bandwidth win with a compute bottleneck (§30).
  • Residual-vector storage growth for sparsification at high worker counts.

21.8 Edge Cases

  • A gradient with all-zero entries under top-k (degenerate case, must not error).
  • A worker that never contributes again after accumulating a large residual (stale residual handling policy must be explicit).

21.9 Failure Analysis

  • Failure: accuracy degradation exceeds the 1% target at the configured compression ratio in production.
  • Detection: convergence-benchmark CI gate (§28) or the accuracy-delta dashboard (§26).
  • Recovery: operator reduces the compression ratio or disables compression for the affected job, per the divergence-triage runbook.

21.10 Operational Notes

Publish error_feedback_residual_norm and the accuracy-delta-vs-ratio curve as standing dashboards; compression is opt-in per ADR-13's "when the rejected choice wins" column and operators need the data to decide.

22. Phase 10 — Checkpointing and Straggler Mitigation

22.1 Objectives

Implement non-blocking checkpointing (P11) of parameter and optimizer state, and straggler mitigation building on Phase 6's SSP clock and Phase 1's BSP round-timeout groundwork.

22.2 Detailed Implementation Steps

  • Implement checkpoint's chunked immutable-manifest format (ADR-14, §11 Checkpoint), writing checkpoints without blocking push/pull serving (P11).
  • Implement checkpoint-restore: reconstruct Shard state (dense, sparse, optimizer) from the manifest, verified against I11's immutability guarantee.
  • Implement straggler's detection logic atop the SSP clock (Phase 6): a worker whose clock has not advanced within a liveness timeout is distinguished from a merely-slow worker (extends Phase 6's §18.6 pitfall 4).
  • Implement backup-worker support (ADR-15 secondary lever): the coordinator may admit a redundant worker for a straggling partition's work, with I12 preventing double-counting of whichever contribution lands first.
  • Benchmark checkpoint write/restore time against the §4 target (2 TB checkpoint) and the straggler-tolerance target (up to 3x median step time under SSP).

22.3 Deliverable

Non-blocking checkpoint/restore at the §4 target size, plus straggler detection and backup-worker mitigation demonstrated against an injected slow worker.

22.4 Acceptance Criteria

  • Checkpoint write for a 2 TB model completes without push/pull latency (p99) regressing beyond 10% of baseline during the write (P11 verified numerically).
  • Checkpoint restore for a 10 TB model completes in < 10 minutes (matching the salvaged constraint from the prior draft, retained here).
  • A worker injected at 3x median step time is tolerated under SSP without violating I1, and its backup-worker contribution (if admitted) is never double-counted (I12).

22.5 Conformance Fixtures

  • fixtures/checkpoint/nonblocking_write_2tb.json
  • fixtures/checkpoint/restore_10tb_under_10min.json
  • fixtures/straggler/injected_3x_slow_worker.yaml
  • fixtures/straggler/backup_worker_no_double_count.json

22.6 Pitfalls

  1. Checkpoint writes taking a shard-wide lock that stalls push/pull, violating P11 even if the manifest format itself is chunked correctly.
  2. Restoring a checkpoint that is marked committed but was actually torn by a mid-write crash — I11's immutability guarantee must be paired with a checksum verified on every read, not just on write.
  3. Confusing a hard-failed worker with a merely-slow one in the straggler detector, triggering backup-worker admission for a worker that will never return and wasting redundant compute indefinitely.
  4. Admitting a backup worker without a clear precedence rule for whichever result lands first, creating a race that can double-count under load (I12).

  • Checkpoint write bandwidth contending with foreground replication traffic (Phase 7) — needs explicit prioritization.
  • Backup-worker redundant compute cost vs. the throughput it recovers — must be measured, not assumed net-positive.

22.8 Edge Cases

  • A checkpoint triggered mid-rebalance (Phase 8) — must capture a consistent view or explicitly defer.
  • A straggler that recovers on its own just as a backup worker is admitted (both results must resolve to exactly one applied contribution, I12).

22.9 Failure Analysis

  • Failure: checkpoint restore fails checksum verification.
  • Detection: I11's checksum-verification-on-read.
  • Recovery: fall back to the prior committed checkpoint generation per the checkpoint-restore runbook, documented in docs/runbooks/.

22.10 Operational Notes

The straggler-mitigation and checkpoint-restore runbooks under docs/runbooks/ are written and rehearsed in this phase; both are exercised again, under chaos, in Phase 11.

  • Recovery: bisect to the offending change via the CI history, revert or retune the codec's compression ratio, and re-run the gate before merge — this is the concrete mechanism behind ADR-13's "when the rejected choice wins" tradeoff becoming an operational decision.

27. Compatibility & Versioning

Push/pull API versioning: every PushRequest/PullRequest carries a protocol-version field (§11, introduced Phase 0); the server rejects an unsupported version rather than silently misinterpreting it.

Parameter/optimizer-state format versioning: OptimizerState's serialized form is versioned independently of the wire protocol so an optimizer-kind addition (e.g., a future optimizer beyond Adam/momentum) does not require a protocol bump.

Checkpoint format versioning: the chunked-manifest format (ADR-14) embeds a format version in its manifest header; checkpoint's restore path supports reading at least one prior major format version to allow rolling upgrades across a checkpoint boundary.

Worker-server protocol compatibility across versions: a rolling upgrade must support one minor-version skew between workers and servers at all times, verified by a dedicated conformance fixture pairing an old worker-sdk build against a new server-node build.

Consistency-model configuration stability: ConsistencyModel is a per-job configuration, not a wire-protocol concern; changing it mid-job is unsupported and rejected explicitly rather than silently producing undefined behavior.

API stability and deprecation: breaking changes to ps-proto follow a deprecate-then-remove cycle spanning at least one minor release, announced in CHANGELOG.md.

SemVer: crates follow SemVer; a protocol-version bump in ps-proto is a major-version event for that crate specifically, independent of the workspace's overall version.

30. Performance Engineering

Methodology:

  • communication is the dominant cost in a naive parameter server (§8.4, §31) — the compute (optimizer update) is O(shard size) while communication is O(model size x workers) absent sharding and compression;
  • overlap compute and communication where the aggregator can begin applying earlier-arrived pushes while later ones are still in flight;
  • prefer batching pushes (ADR-19) over per-key RPCs;
  • treat RDMA/zero-copy as a deferred lever (PhaseDeferred("§9 ADR-08 RDMA transport")) rather than a Phase 0-9 dependency;
  • treat the compression ratio (Phase 9) as a tunable bandwidth/accuracy dial, not a fixed default;
  • treat tail latency (p99/p999) as a first-class target distinct from mean throughput, since a straggler's impact under SSP (Phase 6) is a tail-latency phenomenon by definition.

31. Scalability Analysis

What stays constant as the cluster grows, provided shard count scales with model size:

  • per-shard memory footprint (bounded by design, §4);
  • per-key lookup cost (O(1) amortized via consistent hashing, §8.3).

What grows, with Big-O:

  • for a naive (unsharded, uncompressed) PS, communication per training step grows as O(model_size x workers) — every worker pushes and pulls the full model every step — which is exactly the bottleneck this project's sharding (Phase 2) and compression (Phase 9) exist to avoid (P2, §34);
  • for all-reduce, communication per worker per step is O(model_size) regardless of worker count (the ring-all-reduce bound, §34);
  • this is why all-reduce scales better for dense models at homogeneous scale — the PS-vs-all-reduce crossover is a direct function of sparsity and elasticity requirements, not raw model size alone (§33, §34).

Named bottlenecks:

  • metadata/coordinator fan-out at very large node counts (ADR-18's rationale for a lightweight, non-consensus coordinator caps this);
  • hotspot shards under skewed key-access patterns (mitigated by virtual-node count, Phase 2, and monitored via shard_key_share_skew);
  • checkpoint bandwidth at multi-TB model sizes (Phase 10);
  • compression codec CPU cost competing with aggregation CPU at very high push rates (§21.7).

The PS-vs-all-reduce crossover, stated honestly:

  • at large scale with a fully dense model and a stable, homogeneous worker pool, all-reduce (Horovod, §33) generally outperforms a classic parameter server, because all-reduce's O(model_size) per-worker communication with no central bottleneck beats the PS's central-shard fan-in even after sharding;
  • this is why many large dense-model training runs in industry use all-reduce, not a PS;
  • the PS remains the better architecture when the model is sparse (embeddings dominate the parameter count, §8.3/Phase 4), when the worker pool is elastic (Phase 8), or when a non-uniform per-key consistency/staleness policy (SSP, Phase 6) is required — capabilities all-reduce's synchronous collective model does not naturally provide.

Scaling workers and shards:

  • worker count scales push/pull fan-in against a fixed shard count until aggregation CPU or ingress-queue depth (I13) becomes the bottleneck (§30 M4/M5);
  • shard count scales to reduce per-shard load and memory (§4) but increases coordinator/hash-ring metadata size and elastic-rebalance cost (§20.7);
  • the practical ceiling is where rebalance-convergence time (M7) or metadata fan-out exceeds the operational SLO.

Practical ceilings and levers beyond them:

  • this design's practical shard-count ceiling is set by the coordinator's non-consensus metadata design (ADR-18) — beyond a few thousand shards, PhaseDeferred("§9 ADR-18 gossip membership")-style decentralized membership becomes the lever;
  • the practical worker-count ceiling is set by per-shard ingress fan-in — the lever beyond it is deeper sharding (finer KeyRanges) or a hybrid PS/all-reduce split (PhaseDeferred("§31 PS-vs-all-reduce hybrid"), §1).

32. Mental Models & First Principles

  • MM1. Distributed SGD is a consistency-vs-convergence trade — staleness is noise deliberately injected to buy parallelism, and SSP is the knob that keeps the noise bounded enough to still converge (Ho et al. 2013).
  • MM2. The parameter server exists because moving the whole model every step is the bottleneck, so everything is about moving less: sharding (Phase 2), sparsity (Phase 4), and compression (Phase 9).
  • MM3. A parameter server centralizes state and an all-reduce does not, which is the entire architectural fork — the PS wins on sparse models and elasticity, all-reduce wins on dense models at homogeneous scale (§31, §33).
  • MM4. A shard is not a shortcut for "less data per node" — it is the unit at which ownership, replication, and failure are reasoned about; conflating shard boundaries with arbitrary key ranges breaks I3/I4 reasoning.
  • MM5. Exactly-once application (I2) is not a nicety — without it, every retry silently reweights the gradient mean, and the bug is invisible until convergence quietly degrades.
  • MM6. A straggler is not a failure; a stalled cluster is. SSP's entire design (P3) is a refusal to let the slowest node dictate the fastest node's pace beyond a bound.
  • MM7. Compression is a bias-injection decision, not a free lunch — QSGD's unbiasedness and sparsification's error feedback are two different answers to "how do we make the injected error tractable" (§8.5).
  • MM8. Elastic membership correctness is fundamentally an ownership-accounting problem (I6), not a networking problem — the hard part is proving no key is ever unowned or double-owned, not moving the bytes.
  • MM9. The coordinator's job is metadata, never data (P10) — the moment the coordinator sits on the push/pull hot path, it becomes the single bottleneck the sharded architecture was built to avoid.
  • MM10. Every consistency model is a bet about what workers will do between rounds — BSP bets nothing changes, ASP bets everything can change safely, SSP bets on a bounded amount of change; picking one without stating the bet is picking blind.

The Li et al. ps-lite parameter server is this project's direct architectural ancestor:

  • a central sharded key-value store with a push/pull API, BSP/ASP/SSP consistency options, and range-based sparse support;
  • its van transport layer and KVWorker/KVServer split are the pattern this blueprint's worker-sdk/server-node split follows.

TensorFlow's ParameterServerStrategy implements the PS pattern at the graph level:

  • places variables onto PS tasks via a partitioner;
  • validates this project's variable-partitioning-informs-KeyRange-sizing lesson (§5);
  • historically assumed a fixed worker/PS topology, motivating this project's explicit elastic-membership phase (Phase 8) as a deliberate improvement.

Horovod (and BytePS in its all-reduce mode) is the architectural opposite:

  • no central server, every worker holds the full model;
  • gradients are combined via a ring or tree collective with O(model_size) per-worker communication independent of worker count;
  • it is the canonical embodiment of the all-reduce contrast named throughout this document (§1, §31, §36);
  • it wins decisively for dense, homogeneous-scale training and loses on sparse embedding models and elastic worker pools, exactly the regime this project targets instead.

PyTorch DDP is another all-reduce-family system (built on NCCL's ring/tree collectives):

  • included because it is the default distributed-training path most engineers reach for first;
  • its RPC-based parameter-server tutorial (torch.distributed.rpc, §5) is a documented departure from DDP's own default architecture specifically to support the PS pattern for sparse or elastic workloads DDP itself does not handle well;
  • direct corroboration of this project's §1 non-goals framing.

DistBelief/Downpour SGD (Dean et al. 2012) is the historical predecessor to every modern PS in this table:

  • fully asynchronous (ASP), sharded parameter storage, no formal staleness bound;
  • proved a central sharded store could train at then-unprecedented scale before ps-lite formalized the abstraction (Li et al. 2014);
  • this project's Phase 5 ASP mode is a direct, independently-built descendant of Downpour's core idea.

Petuum/Bösen is included specifically because it is the SSP reference lineage:

  • built the staleness-bounded consistency model (Ho et al. 2013; Cui et al. 2014) that this project's Phase 6 implements independently;
  • demonstrates SSP as a production-viable middle ground between BSP's correctness and ASP's throughput, the exact spectrum this blueprint's §8.2 formalizes.

34. Back-of-Envelope Capacity Model

  1. Communication per step, naive PS.

    • Formula: 2 x model_bytes x workers (one push, one pull, full model, per worker).
    • Inputs: model_bytes = 2 x 10^11 (2 TB, §4), workers = 4096.
    • Computation: 2 x 2x10^11 x 4096 = 1.64 x 10^15 bytes/step.
    • Result: clearly infeasible without sharding/compression, which is exactly §31's point.

  2. Communication per step, ring all-reduce.

    • Formula: 2 x (N-1)/N x model_bytes per worker (the standard ring-all-reduce bound), independent of total worker count for large N.
    • Inputs: model_bytes = 2x10^11, N = 4096.
    • Computation: 2 x (4095/4096) x 2x10^11 ~= 3.999 x 10^11 bytes per worker per step.
    • Result (the crossover): all-reduce's per-worker cost is flat in N, and naive PS's per-worker cost is flat too (2 x model_bytes per worker), but the PS's aggregate cluster ingress (workers x 2 x model_bytes) grows linearly with N while all-reduce's aggregate traffic also grows with N but at a smaller constant; the PS's real win only appears once sharding divides model_bytes by shard count and sparsity divides it further by touched-key ratio (§8.3, §8.1).

  3. Per-shard memory.

    • Formula: model_bytes / shards x replication_factor.
    • Inputs: 2x10^11 bytes, 256 shards, R=3.
    • Computation: (2x10^11 / 256) x 3 = 2.34 x 10^9 bytes.
    • Result: ~2.3 GB per shard-replica, within the <= 8 GB target (§4).

  4. Pull latency under a bandwidth budget.

    • Formula: latency = payload_bytes / bandwidth_Bps.
    • Inputs: a 1000-key sparse pull at 256 bytes/key = 256,000 bytes, over a 25 Gbps (3.125 x 10^9 Bps) link.
    • Computation: 256000 / 3.125x10^9 ~= 82 microseconds transmission time.
    • Result: the bulk of the p99 target (35 ms, §4) budget is therefore queueing/serialization/RPC overhead, not raw transmission — why §30's methodology emphasizes batching and serialization efficiency over raw bandwidth.

  5. Staleness bound to hide a straggler.

    • Formula: ticks of lag per fast-worker step is roughly (straggler_step_time / median_step_time) - 1.
    • Inputs: median step time t, straggler running at 3t (§4/M12 target).
    • Computation: three fast-worker ticks pass per one straggler tick, i.e. up to 2 ticks of lag per fast-worker step.
    • Result: an SSP bound of S = 4-8 (§4) comfortably absorbs a 3x straggler for a handful of consecutive steps before throttling engages, matching the Phase 10 acceptance criterion.

  6. Compression bandwidth saving.

    • Formula: savings_bytes = (1 - 1/ratio) x naive_bytes.
    • Inputs: an 8x sparsification ratio on a 256,000-byte sparse pull payload.
    • Computation: savings = (1 - 0.125) x 256000 = 224,000 bytes.
    • Result: the transmitted payload drops to 32,000 bytes, at the documented < 1% accuracy cost (M9).

  7. Checkpoint time.

    • Formula: checkpoint_seconds = model_bytes / storage_bandwidth_Bps.
    • Inputs: 2x10^11 bytes, 10^10 Bps (10 GB/s) aggregate object-store write bandwidth.
    • Computation: 2x10^11 / 10^10 = 20 seconds.
    • Result: 20 seconds for a full checkpoint of the 2 TB model, well inside a 5-30 minute checkpoint interval (§4), leaving ample non-blocking write headroom (P11).

  8. Convergence-step overhead from staleness.

    • Formula: expected additional steps-to-target-loss scales with a small constant factor of the staleness bound S relative to BSP.
    • Inputs: Ho et al. 2013's own experiments show single-digit-percent step overhead at moderate S.
    • Computation: not closed-form — measured empirically per model.
    • Result: the Phase 6/Phase 11 convergence sweep (§18.4, §23.4) measures this concretely for this project's benchmark model rather than relying on the paper's numbers alone.

36. Alternative Architectures (Roads Not Taken)

Ring/Tree All-Reduce, No Central Server

Worker0 --ring--> Worker1 --ring--> Worker2 --ring--> Worker3 --ring--> Worker0
   ^                                                                       |
   +-----------------------------------------------------------------------+
   each worker holds the FULL model; gradients reduced peer-to-peer,
   no shard, no push/pull RPC boundary at all

Winning regime: dense models at homogeneous, stable worker-pool scale. Embodying system: Horovod (Sergeev & Del Balso 2018). Why rejected here: this blueprint's entire point is the sparse/embedding and elastic-worker regime (§1) where a central sharded store with a consistency-model spectrum is the load-bearing capability; all-reduce has no shard, no push/pull API, and no natural staleness-bound mechanism to reject.

Fully Synchronous BSP-Only Design

[Worker0] [Worker1] [Worker2] [Worker3]
    \         |         |         /
     \        |         |        /
      ------- GLOBAL BARRIER --------
                  |
            [Server Shards]
   simplest possible design: no clock, no ASP/SSP controller at all

Winning regime: small clusters where exact single-node-SGD reproducibility is a hard audit requirement and stragglers are rare. Embodying system: early TensorFlow PS deployments run in synchronous mode. Why rejected here: BSP-only forfeits the entire staleness-vs-throughput design space (§8.2) this project exists to explore, and is straggler-bound exactly as Phase 1's barrier-wait measurement (§13.7) demonstrates.

Decentralized Gossip-SGD, No Central Coordination

Worker0 <--gossip--> Worker1
   ^                    ^
   |                    |
   v                    v
Worker3 <--gossip--> Worker2
  no coordinator, no shard, each worker periodically
  averages parameters with a random peer

Winning regime: extremely large, unreliable, loosely-coupled worker pools (e.g., federated/edge settings) where even a lightweight coordinator (ADR-18) is an unacceptable single point of coordination. Embodying system: gossip-based decentralized SGD research systems (e.g., D-PSGD variants in the distributed-optimization literature). Why rejected here: this project's invariants (I3 single-primary-per-shard, I8 monotonic epochs) presuppose an authoritative membership view that gossip protocols deliberately avoid; adopting gossip would require re-deriving the entire invariant set from scratch.

Sharded-Optimizer / ZeRO-Style Partitioning

[Worker0: params+opt-state shard 0] [Worker1: shard 1] [Worker2: shard 2]
        all-reduce for gradients, but optimizer state
        lives on workers, partitioned, not on a central server

Winning regime: very large dense models where optimizer-state memory (not communication) is the binding constraint and workers themselves have ample memory to hold a shard of it. Embodying system: ZeRO-style optimizer-state sharding as used in large-scale dense-model training stacks. Why rejected here: this design still has no central parameter server — it is an all-reduce-family optimization — and moves optimizer-state placement to the workers, directly contradicting ADR-09's server-side colocation; deferred per PhaseDeferred("§36 sharded-optimizer ZeRO-style partitioning") rather than adopted, since it changes the architecture's fundamental fork (§1, MM3) rather than extending it.

38. Glossary

Term Definition
Parameter server a central sharded store of model parameters exposing push/pull to workers (Li et al. 2014 OSDI)
Push a worker's RPC delivering a gradient or delta to the server
Pull a worker's RPC retrieving current (or bounded-stale) parameter values
Dense parameter a fully-populated tensor stored as a contiguous array
Sparse/embedding parameter a parameter table addressed by key where most keys are untouched per step
Key range a contiguous partition of the key space assigned to one shard
Shard the unit of ownership, replication, and failure for a partition of parameters
Consistent hashing a placement scheme mapping keys to shards via a hash ring, bounding key movement on membership change (Karger et al. 1997)
Virtual node a hash-ring position representing a fractional slice of a physical shard, used to smooth load balance
Replication maintaining R copies of a shard for fault tolerance
Replication factor (R) the configured number of copies per shard
BSP (bulk-synchronous-parallel) a consistency model with a global round barrier
ASP (asynchronous-parallel) a consistency model with no barrier and no staleness bound
SSP (stale-synchronous-parallel) a consistency model bounding staleness by S clock ticks (Ho et al. 2013)
Staleness bound (S) the maximum permitted clock difference between the fastest and slowest worker under SSP
Clock a per-worker monotonic scalar tracking committed pulls
Vector clock a per-worker-keyed clock map used for causal/forensic tracking, not the SSP hot path
Gradient aggregation combining concurrently-pushed gradients (typically by mean) before applying an optimizer update
Optimizer state server-side auxiliary state (momentum, Adam moments) governing a parameter's update rule
Hogwild! the lock-free asynchronous SGD update pattern (Recht et al. 2011)
Gradient quantization reducing gradient precision (e.g., to k bits) before transmission (Alistarh et al. 2017, QSGD)
QSGD Quantized SGD, a specific stochastic quantization scheme with a proven unbiasedness/variance bound
Sparsification transmitting only the top-k magnitude gradient entries (Lin et al. 2018)
Top-k the sparsification selection rule retaining the k largest-magnitude entries
Error feedback carrying forward the untransmitted residual from compression into the next round to bound bias
Straggler a worker running significantly slower than its peers
Backup worker a redundant worker admitted to complete a straggling partition's work
All-reduce a collective communication pattern combining values across all participants with no central server
Ring all-reduce an all-reduce implementation passing data around a logical ring of workers, achieving O(model_size) per-worker communication
Elasticity the ability to add or remove nodes from a running cluster without halting it
Rebalancing redistributing key ownership across shards after a membership change
Checkpoint an immutable persisted snapshot of parameter and optimizer state
Convergence a training run's loss approaching a target value over time
WAL (write-ahead log) an append-only durability log written before a mutation is considered committed
Epoch a monotonically increasing membership/generation counter used to fence stale actors
Lease a time-bounded ownership grant preventing concurrent writers
Fencing token a mechanism preventing a stale owner from acting after a higher-epoch owner exists
Coordinator the lightweight service publishing membership and the shard map, holding no parameter data
Backpressure explicit, bounded flow control preventing unbounded queue growth
RTO (recovery time objective) the maximum acceptable time to recover from a failure
RPO (recovery point objective) the maximum acceptable committed-data loss on failure
Differential testing comparing this system's output against a reference implementation's output for equivalence
Property-based testing testing invariants across generated inputs rather than fixed examples
Chaos testing deliberately injecting failures (kills, partitions, stragglers) to verify recovery
Soak testing running a system under sustained load for an extended duration to catch slow-accumulating bugs
SemVer Semantic Versioning, the major.minor.patch versioning scheme
Backup-worker admission the coordinator's act of assigning a redundant worker to a straggling partition
Straggler-mitigation runbook the operational document (docs/runbooks/straggler-mitigation.md) covering detection and response
Shard map the coordinator-published mapping from ShardId to owning ServerNode
