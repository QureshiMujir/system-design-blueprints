Decisions (§9) · 29 ADRs

ADR-01

Implementation language

Chosen

Rust

Rejected

Go, C++, Python

When the rejected choice is right

Python wins for a single-node research prototype where iteration speed dominates and throughput is irrelevant

Why: GC-free tail latency, memory safety, zero-cost serialization

ADR-02

RPC transport

Chosen

gRPC over HTTP/2

Rejected

custom TCP protocol, RDMA

When the rejected choice is right

RDMA wins in a homogeneous InfiniBand cluster where sub-microsecond latency is required and hardware is fixed

Why: mature flow control, wide tooling, streaming support

ADR-03

Parameter architecture

Chosen

parameter server (central sharded store)

Rejected

all-reduce (no central server), hybrid

When the rejected choice is right

all-reduce wins for dense, homogeneous-scale training where every worker holds the full model (Horovod regime)

Why: matches sparse/embedding and elastic-worker requirements (§1)

ADR-04

Sharding scheme

Chosen

consistent hashing with virtual nodes

Rejected

static range partitioning, plain modulo hashing

When the rejected choice is right

static range partitioning wins for a fixed, never-elastic cluster with known key distribution ahead of time

Why: bounded key movement on rebalance (Karger et al. 1997)

ADR-05

Default consistency model

Chosen

SSP (configurable bound)

Rejected

BSP-only, ASP-only

When the rejected choice is right

BSP-only wins when exact reproducibility with single-node SGD is a hard requirement (e.g. regulated model audits)

Why: balances convergence guarantee against straggler tolerance (Ho et al. 2013)

ADR-06

Staleness clock mechanism

Chosen

per-worker scalar clock with global min

Rejected

vector clocks

When the rejected choice is right

vector clocks win when the recovery layer must also express causal history for debugging distributed transactions

Why: O(1) comparison suffices for scalar staleness (Ho et al. 2013 use scalar clocks)

ADR-07

Dense/sparse parameter representation

Chosen

dual representation (dense array + sparse key-value)

Rejected

dense-only

When the rejected choice is right

dense-only wins for small, fully-dense models (e.g. a CNN under 1B params) where sparse bookkeeping is pure overhead

Why: embeddings dominate real workloads (P2)

ADR-08

Transport for bulk transfer

Chosen

gRPC streaming (RDMA deferred)

Rejected

RDMA now

When the rejected choice is right

RDMA wins once bandwidth benchmarks (Phase 11) show gRPC saturating NIC capacity in production

Why: avoids RDMA hardware coupling in Phase 0-9

ADR-09

Optimizer state placement

Chosen

server-side (colocated with parameter)

Rejected

worker-side, hybrid

When the rejected choice is right

worker-side wins in a ZeRO-style design where optimizer state is deliberately sharded across workers, not servers

Why: atomic recovery of parameter+state together (I5, P8)

ADR-10

Replication strategy

Chosen

primary + R-1 synchronous-ack replicas

Rejected

asynchronous replication, no replication

When the rejected choice is right

asynchronous replication wins when replica-ack latency is unacceptable and a small RPO window is tolerable

Why: bounds RPO to zero committed-update loss (I4)

ADR-11

Failure-recovery approach

Chosen

replica promotion + WAL replay

Rejected

full checkpoint-only restore

When the rejected choice is right

checkpoint-only restore wins for infrequent, tolerable-downtime batch jobs where operational simplicity outweighs RTO

Why: seconds-scale RTO vs. minutes (§4)

ADR-12

Elastic membership protocol

Chosen

coordinator-driven epoch-fenced join/leave

Rejected

fully decentralized gossip membership

When the rejected choice is right

gossip membership wins at cluster sizes beyond a single coordinator's metadata fan-out (thousands of nodes)

Why: simpler correctness proof for I6/I8 at this cluster scale

ADR-13

Gradient compression

Chosen

quantization + top-k sparsification with error feedback

Rejected

no compression

When the rejected choice is right

no compression wins when the model is small enough that compute, not bandwidth, is the bottleneck

Why: bandwidth is the dominant cost at scale (§8.5, §31)

ADR-14

Checkpoint format

Chosen

chunked immutable manifests

Rejected

monolithic tar snapshot

When the rejected choice is right

monolithic tar wins for small models where manifest bookkeeping overhead exceeds its benefit

Why: resumable, parallelizable I/O (I11)

ADR-15

Straggler mitigation

Chosen

staleness bound (SSP) as primary lever, backup workers as secondary

Rejected

backup workers only

When the rejected choice is right

backup workers win when the straggler is a hard node failure, not merely slow, and SSP alone cannot recover the round

Why: staleness bound handles the common case without wasted redundant compute

ADR-16

When the rejected choice is right

ADR-17

Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Ring/Tree All-Reduce, No Central Server

Worker0 --ring--> Worker1 --ring--> Worker2 --ring--> Worker3 --ring--> Worker0
   ^                                                                       |
   +-----------------------------------------------------------------------+
   each worker holds the FULL model; gradients reduced peer-to-peer,
   no shard, no push/pull RPC boundary at all

Winning regime: dense models at homogeneous, stable worker-pool scale. Embodying system: Horovod (Sergeev & Del Balso 2018). Why rejected here: this blueprint's entire point is the sparse/embedding and elastic-worker regime (§1) where a central sharded store with a consistency-model spectrum is the load-bearing capability; all-reduce has no shard, no push/pull API, and no natural staleness-bound mechanism to reject.

Fully Synchronous BSP-Only Design

[Worker0] [Worker1] [Worker2] [Worker3]
    \         |         |         /
     \        |         |        /
      ------- GLOBAL BARRIER --------
                  |
            [Server Shards]
   simplest possible design: no clock, no ASP/SSP controller at all

Winning regime: small clusters where exact single-node-SGD reproducibility is a hard audit requirement and stragglers are rare. Embodying system: early TensorFlow PS deployments run in synchronous mode. Why rejected here: BSP-only forfeits the entire staleness-vs-throughput design space (§8.2) this project exists to explore, and is straggler-bound exactly as Phase 1's barrier-wait measurement (§13.7) demonstrates.

Decentralized Gossip-SGD, No Central Coordination

Worker0 <--gossip--> Worker1
   ^                    ^
   |                    |
   v                    v
Worker3 <--gossip--> Worker2
  no coordinator, no shard, each worker periodically
  averages parameters with a random peer

Winning regime: extremely large, unreliable, loosely-coupled worker pools (e.g., federated/edge settings) where even a lightweight coordinator (ADR-18) is an unacceptable single point of coordination. Embodying system: gossip-based decentralized SGD research systems (e.g., D-PSGD variants in the distributed-optimization literature). Why rejected here: this project's invariants (I3 single-primary-per-shard, I8 monotonic epochs) presuppose an authoritative membership view that gossip protocols deliberately avoid; adopting gossip would require re-deriving the entire invariant set from scratch.

Sharded-Optimizer / ZeRO-Style Partitioning

[Worker0: params+opt-state shard 0] [Worker1: shard 1] [Worker2: shard 2]
        all-reduce for gradients, but optimizer state
        lives on workers, partitioned, not on a central server

Winning regime: very large dense models where optimizer-state memory (not communication) is the binding constraint and workers themselves have ample memory to hold a shard of it. Embodying system: ZeRO-style optimizer-state sharding as used in large-scale dense-model training stacks. Why rejected here: this design still has no central parameter server — it is an all-reduce-family optimization — and moves optimizer-state placement to the workers, directly contradicting ADR-09's server-side colocation; deferred per PhaseDeferred("§36 sharded-optimizer ZeRO-style partitioning") rather than adopted, since it changes the architecture's fundamental fork (§1, MM3) rather than extending it.
