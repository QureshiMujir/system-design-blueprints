32. Mental Models & First Principles

  • MM1. Distributed SGD is a consistency-vs-convergence trade — staleness is noise deliberately injected to buy parallelism, and SSP is the knob that keeps the noise bounded enough to still converge (Ho et al. 2013).
  • MM2. The parameter server exists because moving the whole model every step is the bottleneck, so everything is about moving less: sharding (Phase 2), sparsity (Phase 4), and compression (Phase 9).
  • MM3. A parameter server centralizes state and an all-reduce does not, which is the entire architectural fork — the PS wins on sparse models and elasticity, all-reduce wins on dense models at homogeneous scale (§31, §33).
  • MM4. A shard is not a shortcut for "less data per node" — it is the unit at which ownership, replication, and failure are reasoned about; conflating shard boundaries with arbitrary key ranges breaks I3/I4 reasoning.
  • MM5. Exactly-once application (I2) is not a nicety — without it, every retry silently reweights the gradient mean, and the bug is invisible until convergence quietly degrades.
  • MM6. A straggler is not a failure; a stalled cluster is. SSP's entire design (P3) is a refusal to let the slowest node dictate the fastest node's pace beyond a bound.
  • MM7. Compression is a bias-injection decision, not a free lunch — QSGD's unbiasedness and sparsification's error feedback are two different answers to "how do we make the injected error tractable" (§8.5).
  • MM8. Elastic membership correctness is fundamentally an ownership-accounting problem (I6), not a networking problem — the hard part is proving no key is ever unowned or double-owned, not moving the bytes.
  • MM9. The coordinator's job is metadata, never data (P10) — the moment the coordinator sits on the push/pull hot path, it becomes the single bottleneck the sharded architecture was built to avoid.
  • MM10. Every consistency model is a bet about what workers will do between rounds — BSP bets nothing changes, ASP bets everything can change safely, SSP bets on a bounded amount of change; picking one without stating the bet is picking blind.

Reference Implementations

  • ps-lite / DMLC parameter server, src/ — the original C++ PS reference. Lesson: the push/pull API is key-range based, not whole-tensor. Pitfall: its van-transport is single-threaded per link; do not replicate that bottleneck (Phase 3).
  • MXNet KVStore, src/kvstore/ — dense+sparse push/pull atop ps-lite. Lesson: kvstore.row_sparse_pull is the sparse-pull template (Phase 4). Pitfall: KVStore's default aggregation is sum, not mean — a silent scale bug if copied carelessly (Phase 3).
  • TensorFlow ParameterServerStrategy / tf.distribute — graph-level PS placement. Lesson: variable partitioning strategy (min_max_variable_partitioner) informs KeyRange sizing (Phase 2). Pitfall: TF's PS strategy assumes a fixed worker count; elastic scaling was bolted on later (Phase 8).
  • PyTorch torch.distributed.rpc parameter-server tutorial and DistributedOptimizer — RPC-based PS pattern. Lesson: the RRef ownership model for remote parameter references (§11). Pitfall: naive RPC-per-parameter calls collapse under fan-in; batching is mandatory (Phase 0).
  • BytePS — bandwidth-aware communication scheduling, unifies PS and all-reduce paths. Lesson: server-side summation offload reduces worker CPU (Phase 3). Pitfall: its topology-aware scheduler assumes homogeneous NICs; heterogeneous racks need explicit modeling (Phase 10).
  • Petuum/Bösen — a bounded-staleness parameter server built directly on the SSP model (Ho et al. 2013; Cui et al. 2014). Lesson: SSP's staleness bound is exposed as a first-class scheduler parameter, not an afterthought (Phase 6). Pitfall: Bösen's staleness accounting assumes a cooperative worker; an adversarial or buggy worker can still stall the bound (informs T6).
  • DistBelief / Downpour SGD (Dean et al. 2012) — the historical ASP-mode PS predating ps-lite. Lesson: sharded parameter servers with fully asynchronous updates converge in practice at large scale despite no formal staleness bound (Phase 5). Pitfall: DistBelief's reported results are workload-specific; treat "it worked at Google's scale" as a data point, not a proof (§28's differential testing exists precisely to avoid this trap).

Glossary (§38) · 49 terms · site-wide glossary

Parameter server
a central sharded store of model parameters exposing push/pull to workers (Li et al. 2014 OSDI)
Push
a worker's RPC delivering a gradient or delta to the server
Pull
a worker's RPC retrieving current (or bounded-stale) parameter values
Dense parameter
a fully-populated tensor stored as a contiguous array
Sparse/embedding parameter
a parameter table addressed by key where most keys are untouched per step
Key range
a contiguous partition of the key space assigned to one shard
Shard
the unit of ownership, replication, and failure for a partition of parameters
Consistent hashing
a placement scheme mapping keys to shards via a hash ring, bounding key movement on membership change (Karger et al. 1997)
Virtual node
a hash-ring position representing a fractional slice of a physical shard, used to smooth load balance
Replication
maintaining R copies of a shard for fault tolerance
Replication factor (R)
the configured number of copies per shard
BSP (bulk-synchronous-parallel)
a consistency model with a global round barrier
ASP (asynchronous-parallel)
a consistency model with no barrier and no staleness bound
SSP (stale-synchronous-parallel)
a consistency model bounding staleness by S clock ticks (Ho et al. 2013)
Staleness bound (S)
the maximum permitted clock difference between the fastest and slowest worker under SSP
Clock
a per-worker monotonic scalar tracking committed pulls
Vector clock
a per-worker-keyed clock map used for causal/forensic tracking, not the SSP hot path
Gradient aggregation
combining concurrently-pushed gradients (typically by mean) before applying an optimizer update
Optimizer state
server-side auxiliary state (momentum, Adam moments) governing a parameter's update rule
Hogwild!
the lock-free asynchronous SGD update pattern (Recht et al. 2011)
Gradient quantization
reducing gradient precision (e.g., to k bits) before transmission (Alistarh et al. 2017, QSGD)
QSGD
Quantized SGD, a specific stochastic quantization scheme with a proven unbiasedness/variance bound
Sparsification
transmitting only the top-k magnitude gradient entries (Lin et al. 2018)
Top-k
the sparsification selection rule retaining the k largest-magnitude entries
Error feedback
carrying forward the untransmitted residual from compression into the next round to bound bias
Straggler
a worker running significantly slower than its peers
Backup worker
a redundant worker admitted to complete a straggling partition's work
All-reduce
a collective communication pattern combining values across all participants with no central server
Ring all-reduce
an all-reduce implementation passing data around a logical ring of workers, achieving O(model_size) per-worker communication
Elasticity
the ability to add or remove nodes from a running cluster without halting it
Rebalancing
redistributing key ownership across shards after a membership change
Checkpoint
an immutable persisted snapshot of parameter and optimizer state
Convergence
a training run's loss approaching a target value over time
WAL (write-ahead log)
an append-only durability log written before a mutation is considered committed
Epoch
a monotonically increasing membership/generation counter used to fence stale actors
Lease
a time-bounded ownership grant preventing concurrent writers
Fencing token
a mechanism preventing a stale owner from acting after a higher-epoch owner exists
Coordinator
the lightweight service publishing membership and the shard map, holding no parameter data
Backpressure
explicit, bounded flow control preventing unbounded queue growth
RTO (recovery time objective)
the maximum acceptable time to recover from a failure
RPO (recovery point objective)
the maximum acceptable committed-data loss on failure
Differential testing
comparing this system's output against a reference implementation's output for equivalence
Property-based testing
testing invariants across generated inputs rather than fixed examples
Chaos testing
deliberately injecting failures (kills, partitions, stragglers) to verify recovery
Soak testing
running a system under sustained load for an extended duration to catch slow-accumulating bugs
SemVer
Semantic Versioning, the major.minor.patch versioning scheme
Backup-worker admission
the coordinator's act of assigning a redundant worker to a straggling partition
Straggler-mitigation runbook
the operational document (docs/runbooks/straggler-mitigation.md) covering detection and response
Shard map
the coordinator-published mapping from ShardId to owning ServerNode
