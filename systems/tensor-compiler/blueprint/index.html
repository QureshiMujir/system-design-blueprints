249 — Tensor Compiler (XLA/TVM-like) from Scratch

Project Number: 249

Project Name: Tensor Compiler (XLA/TVM-like) from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition. A heterogeneous tensor compiler and runtime: it lowers a high-level tensor computation graph (ONNX-like op-graph or StableHLO-style dialect) through a canonical graph IR, a Tensor SSA IR, an algebraic optimization pipeline, a memory planner, and a schedule/lowering stage into backend-specific executable kernels (LLVM/CPU, CUDA/PTX, ROCm/HIP, experimental WASM SIMD), then executes those kernels through a runtime that manages device streams, buffers, and synchronization. It resembles the architectural role XLA, TVM, Glow, and Halide play for TensorFlow, generic DL frameworks, ONNX, and image-processing pipelines respectively — graph-in, optimized-native-code-out, with a deterministic, replayable pipeline in between. Every optimization decision is a graph rewrite with recorded provenance; every backend is a stable trait boundary; every artifact is content-addressed and immutable.

Phase 0 deliverable — crates stood up in §12:

  1. crates/common — shared IDs, config loading, error taxonomy scaffolding.
  2. crates/errors — structured error taxonomy shared by every downstream crate.
  3. crates/telemetry — metrics registry, tracing-span wrappers, structured JSON logging adapters.
  4. crates/graph-ir (skeleton) — arena-backed GraphNode type, deterministic hashing stub.
  5. crates/verifier (skeleton) — verifier-pass trait and CFG/dominance scaffolding, no passes wired yet.
  6. scripts/bootstrap.sh — deterministic toolchain pin, reproducible-build flag wiring.
  7. CI matrix (Linux x86_64, Linux AArch64) with clippy/fmt gates and reproducible-hash check.
  8. benchmarks/ harness scaffold wired to Criterion, empty benchmark stubs only.
  9. fuzz/ harness scaffold wired to cargo-fuzz/libFuzzer, empty targets only.
  10. SBOM generation step in the release workflow (deny.toml + cargo-audit).
  11. crates/cli — command skeleton (compile, run, inspect) with deterministic exit codes.

System boundaries.

  • Provides: frontend graph import (ONNX-like, StableHLO-like), canonical graph IR, Tensor SSA IR with effects and buffer-lifetime metadata, an algebraic rewrite/optimization pass framework, global shape/dtype inference, a static memory planner with alias analysis, a tiling/vectorization/fusion scheduler, LLVM-based CPU codegen (AVX2/AVX-512), CUDA/PTX and ROCm/HIP GPU backends, an experimental WASM SIMD backend, a runtime executor with stream and device-buffer management, deterministic replay, profiling/tracing, and a conformance/fuzzing suite.
  • Delegates: the final GPU driver/JIT-to-SASS translation to the vendor driver (ptxas/AMDGPU finalizer), ELF/relocatable-object linking on CPU to the host linker (ld/lld), physical register allocation on LLVM-targeted CPU paths to LLVM's own allocator, container-image reproducibility to a pinned base image, OS scheduling and paging to the kernel.
  • Does NOT provide (Phase 0 exclusions): training orchestration, distributed parameter synchronization, model-serving infrastructure, notebook UX, dataset management, cluster scheduling, a TPU backend, distributed graph partitioning across nodes, automatic data/model-parallel partitioning, search-based autotuning (Ansor-style), online adaptive recompilation, and production-grade WASM SIMD (kept experimental — see §35).

Non-goals: becoming a deep-learning training framework, providing a Python-first authoring DSL beyond a minimal graph-import shim, general-purpose JIT for arbitrary (non-tensor) programs, a cross-node execution scheduler, GUI/notebook tooling.

Deployment model: single-node compilation/runtime service (primary); offline ahead-of-time (AOT) compilation pipeline invoked from CI or a build system (secondary); embedded inference runtime linked into a host process (tertiary, artifact-loader-only, no compiler in-process); research experimentation environment for schedule/fusion exploration.

Target operators: infrastructure teams running model-compilation farms, platform engineers operating runtime deployments, benchmarking/optimization teams, GPU kernel developers validating backend parity.

What later phases unlock: Phase 1–3 (parser, SSA IR, shape/type system) unlock a verified, canonicalized IR that Phase 4's optimizer can safely rewrite. Phase 5 (memory planner) unlocks bounded-memory execution, a precondition for Phase 6's scheduler to reason about buffer locality during tiling. Phase 7–8 (LLVM/CPU, CUDA/ROCm) unlock the first end-to-end executable artifacts, which Phase 9 (profiling, replay, conformance hardening) turns into an operable, debuggable production pipeline.

Recommended language: Rust. Rationale: deterministic ownership semantics eliminate a whole class of aliasing bugs in a system where alias-safety (I3) is load-bearing; no GC pauses inside a latency-budgeted compile path (§4 p99 20 sec); mature, safe llvm-sys/inkwell-style FFI boundaries into LLVM; zero-cost abstractions keep hot pass loops allocation-free; a stable, serialization-rich crate ecosystem (serde, flatbuffers) matches the artifact-format needs of §11. Rejected: C++ — no memory-safety backstop for a codebase with pervasive raw graph-pointer aliasing (acceptable only where the team vendors LLVM/MLIR C++ passes directly without an FFI shim); Go — GC pauses are incompatible with the p95 20 µs runtime-dispatch target (§4) and Go lacks a mature LLVM codegen binding. Secondary languages: C++ for LLVM interoperability shims (isolated behind crates/backend-llvm, P14), Python for graph-import integration tests only (never in the compile hot path), CUDA/PTX for backend validation kernels.

Prerequisites: compiler construction (SSA, dominance, dataflow), LLVM internals, GPU execution models (warps, occupancy, memory coalescing), tensor algebra and broadcasting semantics, scheduling theory (loop tiling, polyhedral models), cache-aware and NUMA-aware optimization, SIMD programming, lock-free/structured concurrency, serialization formats, graph algorithms (dominance trees, interference graphs), memory allocators, kernel-launch semantics, ABI compatibility.

Estimated timeline: Phase 0 — 10–12 weeks. Full system (Phases 0–9) — 9–18 months. Research- grade optimization maturity (autotuning, PGO, cross-node partitioning — all deferred, §35) — 24+ months beyond that.

2. Why Build This

Tensor compilers sit at the densest intersection of compiler engineering, numerical computing, heterogeneous runtime systems, hardware-aware scheduling, and graph theory. Building one exercises multi-stage IR lowering, algebraic optimization, shape propagation, kernel fusion, static memory planning, vectorization, tiling, runtime dispatch, backend abstraction, and deterministic replay — in one pipeline, under one correctness discipline.

Historically important concepts exercised directly: polyhedral scheduling (Polly, Tensor Comprehensions), SSA construction and dominance, graph-rewrite systems, alias/dependence analysis, multi-stage lowering pipelines (MLIR's dialect layering), JIT/AOT ABI management, register-pressure tradeoffs, instruction selection. These are the same primitives that underlie XLA's HLO passes, TVM's Relay→TIR lowering, and Halide's schedule/algorithm separation — none of them are toy exercises; each has a documented, citable production lineage (§5).

Production engineering muscles this project forces: reproducible compilation (bit-identical artifacts for identical inputs), observability-first pass design (every pass emits spans), crash-analysis pipelines (PTX/LLVM-IR dump retention), deterministic execution replay (postmortem reconstruction of a divergent run), numerical-stability verification (optimizations must not silently change results beyond declared tolerance), and compatibility governance (versioned backend ABIs, append-only artifact schemas).

Related systems, and what transfers: vectorized query engines (columnar batch execution ≈ tensor-kernel execution), OS kernels (scheduler and allocator design ≈ memory planner and stream scheduler), distributed systems (graph partitioning semantics, deferred here but conceptually identical to sharding), GPU runtimes (stream/event synchronization), filesystems (artifact journaling and content-addressing), language runtimes (JIT execution, ABI boundaries between compiled units).

Calibration value. Completing this project permanently upgrades: performance engineering instincts (cache locality, occupancy, PCIe/NVLink amplification), compiler architecture judgment (when to canonicalize vs. specialize), GPU runtime systems fluency, low-level debugging under nondeterminism, optimization-pipeline design, systems observability discipline, and execution- determinism reasoning. It forces rigor around correctness invariants (§7), state-transition discipline (§8's compilation state machine), numerical consistency, concurrency boundaries (stream isolation, I7), and runtime safety (unsafe-code isolation, P14).

What Mastery Looks Like

  • Can explain why SSA dominance (I1) is a correctness invariant, not a style preference, and can point to the exact verifier pass that enforces it — competency gained in Phase 2 (§14).
  • Can design a shape-inference pass that resolves symbolic dimensions without infinite recursion and can name the termination argument — Phase 3 (§15).
  • Can write a rewrite pass with recorded provenance such that a divergent optimization run is 100% reconstructible from its replay log — Phase 4 (§16).
  • Can reason quantitatively about buffer-lifetime interference and produce a memory plan that measurably reduces peak allocation (a stated, derived percentage, not an adjective) — Phase 5 (§17).
  • Can distinguish schedule from algorithm (Halide's core insight) and apply it to justify why tiling/fusion decisions live in a separate IR layer from the numerical semantics — Phase 6 (§18).
  • Can trace a single kernel launch from Tensor SSA IR through LLVM IR to an object file and explain every ABI decision along the way — Phase 7 (§19).
  • Can diagnose a warp-divergence or occupancy collapse from a PTX dump and telemetry alone, without re-running the failing kernel — Phase 8 (§20).
  • Can reconstruct a nondeterministic optimizer crash byte-for-byte from a replay log and name the exact pass and node where divergence began — Phase 9 (§21).

Frontend Import Layer. Translates external graph representations (ONNX-like, StableHLO-like) into canonical graph IR. Trust boundary: external model artifacts are untrusted input and are rejected, not sanitized, on malformed structure (P7 fail-closed). Emits malformed_input_total.

High-Level Graph IR. Arena-owned tensor operations independent of execution details. Preserves shape semantics, broadcasting rules, symbolic dimensions, and operator purity flags. All optimization passes read/write this representation before SSA lowering.

Optimization Pipeline. Owns every correctness-sensitive graph mutation: constant folding, algebraic rewrite, dead-op elimination, CSE, fusion planning, layout rewrite. Every mutation emits replay provenance (P2) — this is the subsystem most likely to introduce silent numerical drift if unmonitored, hence I2/I8.

Tensor SSA IR. The canonical optimization substrate: SSA values with explicit lifetimes, memory effects, control regions, buffer aliasing, and scheduling constraints. Dominance (I1) is enforced here by a dedicated verifier pass, not by convention.

Memory Planner. Persistence boundary — buffer-lifetime analysis, interference-graph construction, static arena packing, and spill decisions are computed once and replayed deterministically; incorrect aliasing here is silent numerical corruption, not a crash (I3).

Scheduler / Lowering. Concurrency boundary — one worker pool per compilation task (bounded by §4's 128-worker ceiling) transforms SSA ops into tiled, vectorized, fused, backend-targeted execution plans.

Backend Abstraction Layer. Protocol boundary — a versioned trait (ADR-23) isolates frontend/optimizer semantics from backend-specific lowering, ABI generation, and instruction selection, so a new backend never touches the optimizer.

Artifact Generation. Immutable, content-addressed (BLAKE3, ADR-27) bundles: object files, PTX/HSACO, runtime metadata, symbol tables, debug maps, replay traces, compatibility manifests.

Runtime Engine. Loads artifacts, allocates device buffers, schedules execution streams, coordinates host/device synchronization. Stream-local state cannot leak across execution contexts (I7) — the concurrency boundary that isolates one tenant's kernel fault from another's.

Observability & Diagnostics. External interface — metrics, tracing spans, replay infrastructure, crash dumps, and numerical-verification tooling. Every compiler pass and every runtime dispatch emits a span; this subsystem is a consumer, never a mutator, of upstream state.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: identical inputs (graph + optimization level + shape bindings) must produce byte-identical artifacts. Tradeoff: forbids unordered hash-map iteration in any pass, costing a canonical-ordering wrapper everywhere. Operational: enables artifact caching by content hash. Violated: irreproducible benchmarks, replay divergence (I8), unbisectable crashes.
  • P2 — Replayability First. Rule: every optimization mutation emits a ReplayEvent (§11) before it commits. Tradeoff: replay-log write amplification on every pass. Operational: postmortem reconstruction of any past compilation. Violated: a compiler crash becomes unreproducible, FM-4.
  • P3 — Explicit Ownership. Rule: every IR node has exactly one logical owning arena. Tradeoff: cross-arena references require an explicit indirection (ReplayEvent.affected_nodes style IDs, not raw pointers). Operational: use-after-free and dangling-alias classes are eliminated at compile time. Violated: dangling references, alias corruption, scheduler inconsistency.
  • P4 — Backpressure Everywhere. Rule: every queue (compile-task queue, launch queue, replay-log writer) is bounded with an explicit drop/reject policy. Tradeoff: producers must handle rejection, not just enqueue-and-forget. Operational: bounds worst-case memory under load. Violated: unbounded queue growth turns a slow consumer into an OOM, FM-1.
  • P5 — Immutable Content-Addressed Artifacts. Rule: every compiled bundle is hashed (BLAKE3, ADR-27) and never mutated post-creation. Tradeoff: a one-bit fix requires a full rebuild, not a patch. Operational: safe artifact caching and deduplication by hash. Violated: silent artifact drift, I6 compatibility breakage.
  • P6 — Observability By Default. Rule: every pass and every runtime dispatch emits a tracing span, a metric, and a timing histogram bucket with no opt-in flag required. Tradeoff: baseline overhead on every hot path. Operational: root-cause analysis without redeploying an instrumented build. Violated: an incident with no trace is unbisectable and repeats.
  • P7 — Fail Closed. Rule: unknown ops, malformed metadata, or incompatible schema versions abort compilation immediately, never a best-effort partial lowering. Tradeoff: strictness rejects graphs a looser parser would silently mangle. Operational: no silently-wrong artifact is ever produced. Violated: a malformed graph compiles to numerically wrong code with no diagnostic, T1.
  • P8 — Numerical Stability Preservation. Rule: every optimization must preserve results within a declared tolerance (documented per rewrite rule). Tradeoff: some algebraically-valid rewrites (e.g. naive log(exp(x)) cancellation) are disallowed near overflow/underflow boundaries. Operational: differential testing against an unoptimized baseline is meaningful. Violated: silent accuracy regression indistinguishable from a training bug.
  • P9 — Stable Versioned ABI Boundaries. Rule: the RuntimeExecutor/GraphOp/backend traits (§11) are versioned and backward-compatible within a major version. Tradeoff: extending a trait requires a default-method or a new trait, not a signature break. Operational: a backend crate can be rebuilt and redeployed independently of the optimizer. Violated: RUNTIME_MISMATCH failures, I6.
  • P10 — Bounded Resource Usage. Rule: memory ceilings, recursion ceilings, and pass-iteration ceilings (§4) are enforced, not advisory. Tradeoff: a pathological graph is rejected rather than degrading gracefully. Operational: predictable capacity planning for compilation farms. Violated: resource exhaustion from an adversarial or pathological graph, T2.
  • P11 — Structured Concurrency. Rule: every worker's lifetime is a child of its spawning scope; no detached background task outlives its compilation session. Tradeoff: cancellation must propagate down the hierarchy explicitly. Operational: a cancelled compile leaks zero workers. Violated: leaked streams/threads outliving a crashed session, FM-2.
  • P12 — Crash-Only Components. Rule: every subsystem recovers exclusively through restart + replay, never through in-place repair of corrupted state. Tradeoff: no "heal in place" code path is maintained, simplifying the failure-handling surface. Operational: a crashed compiler worker is indistinguishable, post-restart, from one that never crashed. Violated: divergent recovery paths that themselves become a source of bugs.
  • P13 — Schema Evolution Discipline. Rule: serialized artifact/IR schemas are append-only field numbering (FlatBuffers, ADR-05); no field is ever renumbered or removed. Tradeoff: dead fields persist in the schema indefinitely. Operational: old artifacts remain loadable by newer runtimes. Violated: RUNTIME_MISMATCH, silent misinterpretation of a reused field number.
  • P14 — Isolation of Unsafe Code. Rule: unsafe Rust is permitted only inside audited backend shims (crates/backend-llvm, crates/backend-cuda, crates/backend-rocm), never in the optimizer, verifier, or scheduler. Tradeoff: FFI boundaries require explicit, hand-reviewed wrapper types. Operational: memory-safety bugs are triageable to a small, known surface. Violated: an unsafe backend escape corrupting unrelated compiler state, T5.
  • P15 — Measure Before Optimizing. Rule: no scheduling or codegen heuristic ships without benchmark evidence (Criterion, ADR-14) showing a measured improvement on the standard suite (§28). Tradeoff: slower iteration on "obviously good" ideas. Operational: the cost model stays grounded in reality, not intuition. Violated: a heuristic that regresses real workloads while looking correct on paper.

Edge cases pinned at the domain-model level (elaborated per-phase in §12–§21):

  • Malformed broadcast — [4, 8] + [7, 8] has no valid broadcast rule; expected outcome: verifier rejection with a T1-class diagnostic, never a silent shape coercion.

  • Replay divergence — non-deterministic pass ordering (violates I4) produces two different artifacts from one input; mitigation: pass-hash comparison during replay (I8) flags the run before it reaches an operator.

11. Core Schema & Types

GraphNode — owner: crates/graph-ir arena; mutation: append-only within a pass, replaced (not mutated in place) across passes; concurrency: read-only shared snapshots across worker threads, mutable only inside a pass-local arena; persistence: not directly serialized, canonicalized into TensorSSAValue before artifact emission; compatibility: internal-only, no cross-version contract.

struct GraphNode
  node_id: NodeId;
  op_kind: OpKind;
  input_edges: Vec<EdgeId>;
  output_edges: Vec<EdgeId>;
  shape: ShapeExpr;
  dtype: DType;
  attributes: AttrMap;
  effect_flags: EffectFlags;

TensorSSAValue — owner: crates/tensor-ir block graph; mutation: immutable once constructed (new values replace old on rewrite, P1); concurrency: safe to share read-only across the pass manager's worker pool; persistence: serialized into the artifact bundle's SSA section (FlatBuffers, ADR-05); compatibility: append-only field numbering (P13).

struct TensorSSAValue
  value_id: SsaId;
  producer_op: OpId;
  shape: ShapeExpr;
  dtype: DType;
  memory_class: MemoryClass;
  alias_group: AliasGroupId;

CompilerSession — owner: the invoking CLI/service call; mutation: mutable pass-local arenas scoped to the session, immutable graph snapshots shared outward; concurrency: one session per compilation task, up to the §4 128-worker ceiling; persistence: replay_writer field flushes to the bounded ring-buffer replay log (P2); compatibility: internal orchestration type, not serialized.

struct CompilerSession
  session_id: SessionId;
  graph_ir: GraphIrHandle;
  tensor_ir: TensorIrHandle;
  diagnostics: DiagnosticSink;
  metrics_registry: MetricsRegistry;
  replay_writer: ReplayWriter;

GraphOp — owner: op-kind-specific implementation registered in the op registry; mutation: pure functions over immutable inputs; concurrency: safe to invoke concurrently across independent nodes; persistence: not serialized (behavior, not data); compatibility: trait is versioned (P9), extended only via default methods.

trait GraphOp
  fn verify(&self, ctx: &VerifyCtx) -> VerifyResult;
  fn infer_shape(&self, ctx: &ShapeCtx) -> ShapeResult;
  fn lower(&self, ctx: &LowerCtx) -> LowerResult;
  fn estimate_cost(&self, ctx: &CostCtx) -> CostEstimate;

TensorBuffer — owner: crates/memory-planner allocation plan; mutation: allocation-class and lifetime fields fixed after planning, immutable at lowering time; concurrency: one buffer, one owning device stream at a time (I7); persistence: recorded in the artifact's allocation-map section; compatibility: append-only.

struct TensorBuffer
  buffer_id: BufferId;
  allocation_class: AllocClass;
  device: DeviceId;
  size_bytes: u64;
  alias_set: AliasSetId;
  lifetime_range: LifetimeRange;

BackendTarget — owner: shared enum consumed by scheduler and backend crates; mutation: immutable value type; concurrency: Copy, freely shared; persistence: serialized as a single artifact-header tag; compatibility: adding a variant is additive only (P13).

enum BackendTarget
  CpuX86,
  Cuda,
  Rocm,
  WasmSimd

SchedulerPlan — owner: crates/scheduler; mutation: constructed once per lowering pass, immutable thereafter; concurrency: shared read-only across backend codegen workers; persistence: serialized into the artifact's schedule-metadata section; compatibility: append-only.

struct SchedulerPlan
  tile_shape: TileShape;
  vector_width: VectorWidth;
  fusion_groups: Vec<FusionGroupId>;
  parallel_regions: Vec<ParallelRegion>;

ReplayEvent — owner: crates/replay event store; mutation: append-only, never rewritten; concurrency: single-writer per session, multi-reader for replay/inspection; persistence: append-only binary log (ADR-19-adjacent choice on replay encoding); compatibility: append-only field numbering.

struct ReplayEvent
  pass_id: PassId;
  timestamp: MonotonicNanos;
  transformation_hash: Blake3Hash;
  affected_nodes: Vec<NodeId>;

RuntimeExecutor — owner: crates/execution-engine; mutation: internal state machine transitions only through the trait's own methods; concurrency: one executor instance per runtime process, internally stream-parallel; persistence: not serialized (runtime-only behavior); compatibility: versioned trait (P9), backward-compatible within a major version.

trait RuntimeExecutor
  fn load_artifact(&mut self, bundle: &ArtifactBundle) -> LoadResult;
  fn allocate_buffers(&mut self, plan: &SchedulerPlan) -> AllocResult;
  fn execute(&mut self, stream: StreamId) -> ExecResult;
  fn synchronize(&mut self, stream: StreamId) -> SyncResult;

Compatibility guarantees: stable serialized field numbering across all FlatBuffers schemas (P13); append-only schema evolution, never a renumber or a field removal; backward-compatible runtime loaders that reject (not misinterpret) an artifact newer than the loader understands (I6).

12. Phase 0 — Repository Foundation & Correctness Kernel

12.1 Objectives

Stand up a deterministic, reproducible Rust workspace; establish CI, linting, and dependency-audit gates; wire the shared error taxonomy, telemetry scaffolding, and config loading every later crate depends on; stand up empty arena/verifier skeletons so Phase 1 has a compilable target. Introduces the constraint that nothing downstream may bypass the shared crates/errors taxonomy or emit unstructured logs (P6, ADR-09).

12.2 Detailed Implementation Steps

Initialize the Cargo workspace (Cargo.toml) with per-crate members matching §10; pin the Rust toolchain (rust-toolchain.toml, ADR-19 reproducibility); configure rustfmt/clippy as CI gates with zero-warning policy; add deny.toml for cargo-audit/cargo-deny license and advisory scanning (ADR-03); implement the error taxonomy in crates/errors as a closed enum hierarchy (Cooper & Torczon's IR-mutation-discipline framing, §5, applies directly to how error variants map onto pipeline stages); implement crates/telemetry metrics/tracing/logging adapters wrapping OpenTelemetry (ADR-10) and Prometheus (ADR-11); implement crates/common ID types (NodeId, SessionId, ArtifactId as newtype wrappers over u64/Blake3Hash) and config loading (TOML, ADR-20, superseded numbering — see §9 for the canonical ADR set); stand up crates/graph-ir and crates/verifier as compilable skeletons with no passes wired; write scripts/bootstrap.sh for deterministic toolchain install; configure the CI matrix (.github/workflows/ci.yml) for Linux x86_64 and AArch64 with a reproducible-binary-hash check (I13 groundwork); scaffold benchmarks/ (Criterion, ADR-14) and fuzz/ (libFuzzer, ADR-13) with empty targets that compile.

12.3 Deliverable

A runnable, empty-pipeline workspace: cargo build --workspace succeeds, cargo clippy --workspace -- -D warnings is clean, CI is green on both platforms, and a deterministic-build job reproduces an identical binary hash across two consecutive runs.

12.4 Acceptance Criteria

CI green on Linux x86_64 and AArch64; zero clippy warnings across all 20 crates; two consecutive release builds produce an identical BLAKE3 binary hash (ADR-27); cargo audit reports zero critical advisories; workspace cold build completes in < 5 minutes on the CI runner class.

12.5 Conformance Fixtures

  • fixtures/build/reproducible-build-001 — two builds from the same commit must hash-match.
  • fixtures/errors/error-taxonomy-001 — every error variant round-trips through structured JSON logging with all required fields (session_id, artifact_hash, backend_target, pass_id).
  • fixtures/build/toolchain-drift-001 — a deliberately mismatched toolchain version must fail CI with a named diagnostic, not a silent stale-cache success.

12.6 Pitfalls

  • Dependency drift. Manifestation: inconsistent binary hashes between two CI runs. Root cause: an unpinned transitive dependency resolved to a newer patch version. Debugging: diff Cargo.lock between the two runs. Signal: reproducible-build-001 fixture fails. Recovery: restore the known-good lockfile, re-pin via cargo update -p <crate> --precise.
  • Non-deterministic logging field order. Manifestation: structurally identical log lines hash differently. Root cause: HashMap-backed field ordering instead of a stable BTreeMap/ordered struct. Debugging: byte-diff two log lines for the same event. Signal: replay/log-hash fixtures intermittently fail. Recovery: switch to ordered field emission, add a lint rule forbidding HashMap in any serialized-log-adjacent type.
  • Silent clippy-allow creep. Manifestation: warnings reappear after a dependency bump. Root cause: a local #[allow(...)] masking a real issue instead of fixing it. Debugging: grep for #[allow( outside an explicit allowlist file. Recovery: CI gate on a tracked allowlist, not ad hoc inline suppressions.

12.7 Performance Concerns

Incremental-compilation caching (sccache) to keep CI wall-clock bounded as crate count grows; CI artifact reuse across the fmt/clippy/test/build stages to avoid four cold cargo invocations; linker choice (lld) for faster workspace-wide relink during iterative development.

12.8 Edge Cases

Cross-platform path separators in build scripts (scripts/bootstrap.sh must not assume /); missing LLVM installation on a fresh CI runner (must fail with a named, actionable diagnostic, not a generic linker error); an unstable/nightly-only compiler flag accidentally left in rust-toolchain.toml breaking the stable-channel gate.

12.9 Failure Analysis

Blast radius of a foundation-layer break is repository-wide: every downstream crate fails to build. Detection: CI red on the very first cargo build --workspace step. Containment: no merge to the default branch without a green foundation job (branch protection). Recovery: revert to the last known-good commit tagged by the reproducible-build job; postmortem records which pinned dependency or toolchain version changed.

12.10 Operational Notes

Metrics: build_duration_seconds, clippy_warning_count, dependency_audit_critical_total. Structured-log fields mandatory from this phase onward: session_id, artifact_hash, backend_target, pass_id (even when null, the field is present — P13 discipline starts here). Deployment: this phase produces no runtime artifact, only the build/CI substrate. Enforce signed commits and mandatory release tagging from Phase 0 onward; publish the SBOM (ADR-03) as part of every CI run, not only at release time.

13. Phase 1 — Graph IR & Frontend Import

13.1 Objectives

Implement the canonical arena-backed Graph IR and an ONNX-compatible (plus StableHLO-shaped) frontend parser. Establishes the trust boundary (§3) at which untrusted external graphs are validated or rejected before any optimizer code ever sees them (P7).

13.2 Detailed Implementation Steps

Define GraphNode arenas in crates/graph-ir/src/arena.rs with single-owner semantics (I12, P3); implement edge ownership as arena-local indices, never raw pointers; add shape-metadata storage (ShapeExpr, supporting both concrete and symbolic dimensions per the MLIR dialect- layering lesson, Lattner et al. 2021, §5); implement the parser tokenizer and ONNX-schema validator in crates/parser/src/onnx.rs and stablehlo.rs; add the graph verifier (crates/verifier/src/dominance.rs groundwork, full dominance check lands in Phase 2); implement broadcast-semantics canonicalization (rejecting [4,8]+[7,8]-shaped mismatches per §8); implement attribute normalization into AttrMap; implement deterministic graph hashing (crates/graph-ir/src/hash.rs, BLAKE3, feeds I13/ADR-27); add malformed-graph diagnostics wired to the Phase 0 error taxonomy; add cycle detection over the edge-index graph; implement a symbol table for named tensor inputs/outputs. Relay's operation-purity metadata (Roesch et al. 2018, §5) shapes the effect_flags field on GraphNode.

13.3 Deliverable

A parser that imports medium ONNX-like graphs (~50k ops) and serializes deterministic, hashed canonical Graph IR, with a verifier that rejects malformed input before it reaches the optimizer.

13.4 Acceptance Criteria

10,000 ONNX-conformance graphs from conformance/onnx/ import successfully; all malformed fixtures in fixtures/parser/ are rejected with a T1-class diagnostic; graph hashing is byte-for-byte deterministic across 3 repeated imports of the same input; parse throughput ≥ 100k nodes/sec (§4) measured on the 50k-op medium-graph benchmark.

13.5 Conformance Fixtures

  • fixtures/parser/malformed_cycle_graph.onnx — a cyclic op-graph; expects cycle-detection rejection.
  • fixtures/parser/invalid_broadcast_001.onnx — [4,8]+[7,8]; expects verifier rejection, no silent coercion.
  • fixtures/parser/symbolic_shape_001.onnx — a graph with an unresolved symbolic dimension binding; expects deferred-to-Phase-3 shape-solver handoff, not a Phase 1 crash.
  • fixtures/parser/replay_import_001.onnx — a known-good graph; import must be byte-identical across replay.

13.6 Pitfalls

  • Silent shape drift. Manifestation: two imports of the same graph produce different shape metadata. Root cause: inconsistent symbolic-dimension propagation order (violates I4). Debugging: diff canonical hashes across imports. Signal: replay_import_001 fixture fails. Recovery: enforce stable topological visitation order in the canonicalizer.
  • Arena fragmentation. Manifestation: memory overhead per node exceeds the 256 B budget (§4) under excessive node churn during canonicalization. Root cause: repeated allocate/free cycles instead of in-place arena compaction. Debugging: arena occupancy telemetry. Recovery: batch canonicalization rewrites and compact the arena once per pass, not per rewrite.
  • Unsupported-op silent pass-through. Manifestation: an op with no registered GraphOp impl is silently skipped rather than rejected. Root cause: a missing exhaustiveness check in the op registry lookup. Recovery: op registry lookup must be P7 fail-closed by construction — no default no-op fallback.

13.7 Performance Concerns

Arena allocation locality (contiguous Vec-backed arenas, not per-node heap allocations); parser streaming (avoid materializing the entire input buffer before tokenizing large ONNX files); hash- table collision rate in the symbol table under adversarially-named tensors.

13.8 Edge Cases

Recursive graph references (subgraph referencing an ancestor scope); unsupported/experimental ops outside the registered OpKind set; malformed tensor metadata (dtype/shape mismatch inside a single node's attributes); empty graphs (zero nodes) and single-node graphs as boundary cases for the cycle detector.

13.9 Failure Analysis

Detection: verifier failures and import-panic telemetry (malformed_input_total, T1). Blast radius is contained to the single import (P7), never propagating a partially-built graph downstream. Recovery: reject and return a CompileResponse with VERIFICATION_FAILED and structured diagnostics; the malformed input is persisted to a quarantine corpus for fuzz-seed reuse in Phase 9.

13.10 Operational Notes

Metrics: parser_nodes_per_second, malformed_input_total by op-kind. Tracing spans: parser.tokenize, parser.canonicalize, parser.hash. Structured-log fields add graph_hash. Deployment implication: the malformed-import corpus persists across restarts (bounded ring buffer, P4) for later fuzz-seed reuse; no migration concern yet — Graph IR is not directly serialized across versions.

14. Phase 2 — Tensor SSA IR & Verifier

14.1 Objectives

Lower canonical Graph IR into the Tensor SSA IR — the canonical optimization substrate (§3) — with a dominance-checking verifier and a textual printer for debugging and roundtrip testing. Introduces the SSA-dominance invariant (I1) as a hard gate before any optimization pass runs.

14.2 Detailed Implementation Steps

Define the SSA block graph (crates/tensor-ir/src/block.rs) with explicit control regions; implement the dominance-tree construction (crates/verifier/src/dominance.rs, the classical Cooper & Torczon algorithm, §5) enforcing I1; implement phi-like merge semantics at block boundaries for values reaching a join point; define the memory-effect system (effects.rs) tagging each TensorSSAValue with read/write/alias effects consumed later by the memory planner (I3 groundwork); implement the full verifier-pass suite (dominance, shape, effect well-formedness); build a textual IR printer (printer.rs) for deterministic debugging output; implement parser/printer roundtrip tests; define scheduling metadata placeholders on TensorSSAValue (consumed starting Phase 6, per Halide's schedule/algorithm separation, Ragan- Kelley et al. 2013, §5). MLIR's nested pass-manager scoping (§5) informs how the verifier suite is composed as an ordered, named pipeline rather than an ad hoc function chain.

14.3 Deliverable

A stable Tensor SSA IR with a dominance-verified block graph, a working textual printer, and roundtrip serialization fidelity measured against the Phase 1 corpus.

14.4 Acceptance Criteria

Dominance verification passes on 100% of the 10,000-graph conformance corpus; printer/parser roundtrip fidelity > 99.99% byte-identical reconstruction; zero unresolved SSA references across the corpus; verifier runs in < 200 ms on the 50k-op medium-graph benchmark.

14.5 Conformance Fixtures

  • fixtures/ssa/dominance_violation_001.ir — a hand-crafted use-before-definition; expects I1 rejection.
  • fixtures/ssa/alias_conflict_002.ir — two SSA values sharing an alias group without an explicit mark; expects verifier rejection (groundwork for I3, fully enforced in Phase 5). fixtures/ssa/roundtrip_regression_003.ir — a regression fixture from a prior printer bug; must roundtrip byte-identical.
  • fixtures/ssa/unreachable_block_004.ir — a block with no predecessor; expects a warning-class diagnostic, not a hard failure, since dead-code elimination (Phase 4) will remove it.

14.6 Pitfalls

  • SSA rewrite corruption. Manifestation: a rewrite updates a value but not its dominance-tree position. Root cause: dominance tree treated as a cache instead of being invalidated on block- graph mutation. Debugging: re-run the dominance verifier immediately post-rewrite in debug builds. Signal: dominance_violation_001-style fixture regressions. Recovery: invalidate and recompute the dominance tree on every block-graph structural change, never patch it in place.
  • Invalid dominance updates under block splitting. Manifestation: splitting a block for a later fusion pass (Phase 6) silently breaks dominance for values defined pre-split. Root cause: block split implemented before the dominance-tree update rule was specified. Recovery: block split is only ever performed through a single verified helper that atomically updates dominance.
  • Phi-node inconsistency at irregular merge points. Manifestation: a value reaching a merge from only one predecessor is treated as if reaching from both. Debugging: verifier's merge- completeness check. Recovery: reject incomplete merges at construction time, not at use time.

14.7 Performance Concerns

CFG traversal cost for dominance computation (target near-linear via the standard iterative algorithm, not naive fixed-point iteration); verifier scalability on 5M-node graphs (§4 ceiling); allocation pressure from block-graph restructuring during merge-semantics construction.

14.8 Edge Cases

Unreachable blocks (verifier warns, DCE removes in Phase 4); recursive effects (a subgraph whose effect set references its own not-yet-fully-constructed effect tag); dead SSA values with no consumer; zero-block or single-block degenerate graphs.

14.9 Failure Analysis

Blast radius of an undetected dominance violation is total optimization invalidation — every downstream pass assumes I1 holds. Detection: verifier_failure_total spike. Containment: the verifier runs as a mandatory gate between every optimizer pass invocation in CI (not just at IR construction), so corruption is caught at the introducing pass, not three passes later.

14.10 Operational Notes

Metrics: verifier_failure_total by check-kind (dominance/shape/effect), ssa_roundtrip_fidelity. Tracing spans: ssa.dominance_check, ssa.printer_roundtrip. Verifier metrics are mandatory in CI as a blocking gate, not an advisory dashboard. Structured-log fields add ir_node_count, block_count.

15. Phase 3 — Shape Inference & Type System

15.1 Objectives

Implement global shape inference over symbolic dimensions and a dtype lattice for mixed-precision graphs. Closes the [N,M]*[M,K] ambiguity class from §8 by either resolving every symbolic binding or rejecting the graph — never guessing.

15.2 Detailed Implementation Steps

Implement the symbolic-dimension engine (crates/type-system/src/shape_solver.rs) as a constraint graph over ShapeExpr terms; implement the dtype lattice (dtype_lattice.rs) with defined join/meet operations for mixed-precision promotion; implement partial shape propagation for graphs with legitimately dynamic (batch) dimensions; integrate the solver with the Phase 2 verifier so shape well-formedness is checked alongside dominance (I2); add runtime fallback guards for dimensions that remain symbolic until first execution (bounded by ADR-24's SSA-IR-form decision); implement shape-simplification passes that fold provably-equal symbolic terms. The constraint-graph solver borrows termination-argument discipline from classical dataflow-analysis fixpoint theory (Aho, Lam, Sethi & Ullman, §5) to guarantee the solver halts rather than recursing unboundedly on adversarial symbolic expressions (P10).

15.3 Deliverable

Full graph shape/dtype validation: every tensor in a compiled graph has either a fully resolved concrete shape or an explicitly bounded symbolic shape with a documented runtime-binding contract.

15.4 Acceptance Criteria

100% of symbolic constraints in the 10,000-graph corpus resolve or are explicitly and correctly rejected as ambiguous (zero silent guesses); solver termination guaranteed within a 10,000- iteration ceiling (P10, I11-adjacent); zero graphs reach Phase 4 with an unresolved runtime shape ambiguity.

15.5 Conformance Fixtures

  • fixtures/shapes/unresolved_binding_001.ir — [N,M]*[M,K] with M unbound; expects rejection, not a default binding.
  • fixtures/shapes/zero_dim_002.ir — a zero-dimension tensor; expects explicit lattice handling, not a divide-by-zero panic downstream.
  • fixtures/shapes/mixed_precision_003.ir — fp16/fp32 mixed graph; expects dtype-lattice-correct promotion.
  • fixtures/shapes/solver_ceiling_004.ir — an adversarially deep symbolic-recursion fixture; expects clean termination at the iteration ceiling with a diagnostic, not a stack overflow.

15.6 Pitfalls

  • Infinite symbolic recursion. Manifestation: solver never terminates on a self-referential symbolic expression. Root cause: no iteration ceiling enforced (P10 violation). Debugging: solver-iteration-count telemetry. Recovery: hard ceiling with a named diagnostic, never a silent hang.
  • Overflow during dimension multiplication. Manifestation: a large-batch symbolic product overflows u64 silently. Root cause: unchecked multiplication in shape-expression evaluation. Recovery: checked arithmetic with an explicit OOM/overflow diagnostic path, never wraparound.
  • Ambiguity masked by a permissive default. Manifestation: an unresolved dimension silently defaults to 1. Root cause: a convenience fallback added under deadline pressure, violating P7. Recovery: remove all implicit defaults; every unresolved binding is a hard rejection.

15.7 Performance Concerns

Constraint-graph complexity growth with graph size (target near-linear via incremental constraint propagation, not full re-solve per node added); shape-simplification pass cost on graphs with deep symbolic-expression trees.

15.8 Edge Cases

Zero-dimension tensors (empty batch); mixed-precision graphs crossing dtype-lattice boundaries; dynamic-shape speculative specialization — deliberately out of scope here, PhaseDeferred("§15"), registered in §35; negative or non-integer symbolic bounds supplied by a malformed frontend.

15.9 Failure Analysis

Detection: shape-solver deadlock/ceiling-hit telemetry. Blast radius: contained to the single graph's compilation (fail-closed, P7); no partial shape state leaks into Phase 4. Recovery: reject with VERIFICATION_FAILED and a shape-resolution trace attached for operator diagnosis.

15.10 Operational Notes

Metrics: shape_solver_iterations, shape_ambiguity_rejected_total. Tracing spans: shapes.solve, shapes.simplify. Emit full shape-resolution traces (not just pass/fail) so an operator can see exactly which constraint failed to close. Structured-log fields add unresolved_dims_count.

16. Phase 4 — Optimization Pass Framework

16.1 Objectives

Implement the pass manager and the core algebraic-optimization pass suite: constant folding, dead-op elimination, CSE, and fusion planning (legality analysis; scheduling/codegen fusion lands in Phase 6). Establishes replay-logged, deterministic pass ordering (I4, I5) as the correctness backbone for every mutation from here on.

16.2 Detailed Implementation Steps

Implement the pass registry and dependency graph (crates/optimizer/src/pass_manager.rs) with explicit pass-invalidation rules — a pass that mutates shape info invalidates the shape-analysis cache, never leaving it stale (I2); implement the rewrite engine (rewrite.rs) with each rule tagged with a numerical-tolerance annotation (P8); implement algebraic simplification, constant folding (constant_fold.rs), dead-op elimination (dce.rs), and CSE (cse.rs); implement canonicalization passes reusing the Phase 1 canonicalizer's stable-ordering discipline (I4); wire pass-replay logging (P2) so every mutation emits a ReplayEvent (§11) before committing. XLA's HLO-level algebraic simplification (openxla/xla xla/service/, §5) is the direct model for the rewrite-rule catalog's structure, adapted to this project's SSA form rather than XLA's HLO graph form.

16.3 Deliverable

A composable optimization framework producing deterministic, replay-reproducible pass output on the full conformance corpus, with fusion-legality analysis available for Phase 6 to consume.

16.4 Acceptance Criteria

Pass output is byte-identical across 3 repeated runs on all 10,000 corpus graphs; replay reconstruction of any single pass invocation succeeds with 100% fidelity; rewrite-rule catalog covers ≥ 40 named algebraic identities with documented tolerance annotations; zero rewrite- oscillation failures across a 72-hour soak (shared gate with §21).

16.5 Conformance Fixtures

  • fixtures/optimizer/rewrite_replay_001 — a known rewrite sequence; replay must reproduce the identical resulting IR hash.
  • fixtures/optimizer/cse_validation_002 — a graph with duplicated subexpressions; CSE must collapse them to a single value with no shape/dtype drift.
  • fixtures/optimizer/cyclic_rewrite_003 — a deliberately oscillating rewrite pair (A→B→A); expects oscillation detection, not an infinite pass loop (I11).
  • fixtures/optimizer/overflow_fold_004 — constant folding of an operation that would overflow; expects rejection of the fold, not a silently wrong folded constant.

16.6 Pitfalls

  • Invalidated analysis reuse. Manifestation: a pass reads a stale shape-analysis result after a preceding pass mutated shapes. Root cause: missing invalidation wiring in the pass dependency graph. Debugging: analysis-cache version-stamp mismatch assertion. Recovery: every analysis result carries a version stamp checked on read; stale reads abort rather than silently succeed.
  • Rewrite oscillation. Manifestation: two rewrite rules undo each other, looping until the iteration ceiling (I11). Debugging: replay-log diff shows the same node hash recurring. Recovery: rule-priority ordering plus a strict cost-decrease requirement per applied rewrite.
  • Fold-through-overflow. Manifestation: constant folding silently wraps an integer overflow into a wrong constant. Root cause: unchecked arithmetic in constant_fold.rs. Recovery: checked arithmetic; a fold that would overflow is simply not applied (P8).

16.7 Performance Concerns

Pass-graph recomputation cost when a single pass invalidates a broad analysis; allocation churn from rewrite rules that reconstruct nodes rather than mutating in place (deliberate — P1 — but must be arena-recycled, not heap-per-rewrite); rewrite-rule matching cost at 5M-node scale (§4), bounded by the ≥ 10k transformations/sec throughput target.

16.8 Edge Cases

Cyclic rewrite pairs (oscillation, I11); overflow-adjacent constant folds; CSE across control- region boundaries (must not merge values with different effect sets); profile-guided optimization feeding pass-ordering decisions is explicitly out of scope here, PhaseDeferred("§16"), registered in §35 — this phase's cost model is static only.

16.9 Failure Analysis

Detection: pass-crash replay support means every optimizer panic is preceded by a flushed replay segment (P2), so the exact input IR and pass sequence that caused it is always recoverable. Blast radius: contained to the single compilation session; the pass manager does not share mutable state across sessions. Recovery: replay the failing segment in isolation to reproduce and fix.

16.10 Operational Notes

Metrics: per-pass timing histograms (pass_duration_seconds{pass_id}), rewrite_applied_total, rewrite_oscillation_detected_total. Tracing spans: one span per pass invocation, parented to the session span. Structured-log fields add pass_id, rewrite_rule_id. Rollback implication: a regressed rewrite rule is disabled via the pass registry's feature-flag list, not a hotfix redeploy.

17. Phase 5 — Memory Planner & Alias Analysis

17.1 Objectives

Implement static memory planning: buffer-lifetime analysis, interference-graph construction, arena packing, spill decisions, and full alias-safety validation. Promotes the effect-tagging groundwork from Phase 2 into a hard, verified gate (I3, I10) before any buffer is scheduled for reuse.

17.2 Detailed Implementation Steps

Implement lifetime-interval analysis (crates/memory-planner/src/lifetime.rs) over TensorSSAValue def/last-use ranges; build the interference graph (interference.rs) — two buffers interfere if their lifetime ranges overlap and they are not proven alias-disjoint; implement arena packing (arena_pack.rs) via graph-coloring-style bin packing to minimize peak allocation (P10); implement the spill planner (spill.rs) for buffers that cannot be kept resident within the memory ceiling (§4); implement the alias-safety validator enforcing I3 — no mutable overlap unless explicitly marked in alias_group; add device memory classes (host, device-pinned, device-unified) and NUMA-aware host allocation (ADR-28, mimalloc) with pinned-memory handling for host-device transfer paths. The interference-graph construction directly reuses classical register-allocation graph-coloring theory (Cooper & Torczon, §5) applied to tensor buffers instead of machine registers.

17.3 Deliverable

A static allocation planner producing a verified, alias-safe memory plan with measured peak- allocation reduction versus an unplanned baseline, feeding directly into Phase 6's scheduler and Phase 7/8 backend codegen.

17.4 Acceptance Criteria

Peak memory reduction > 40% versus unplanned baseline allocation, measured on the standard GEMM/ conv/attention benchmark suite (§28); alias verifier reports zero violations across the full 10,000-graph corpus; memory-plan construction completes within the 5-sec p95 compile-latency budget (§4) for medium graphs.

17.5 Conformance Fixtures

  • fixtures/memory/overlap_violation_001.ir — two buffers with overlapping lifetimes and no alias mark; expects rejection.
  • fixtures/memory/spill_storm_002.ir — a graph with more live tensors than fit the memory ceiling; expects deterministic, bounded spill decisions, not an OOM.
  • fixtures/memory/numa_affinity_003.ir — a host-allocation-heavy graph; expects allocations local to the owning worker's NUMA node.
  • fixtures/memory/dynamic_expansion_004.ir — a tensor whose size grows at runtime past its planned allocation; expects a detected-and-rejected plan, not silent buffer overrun.

17.6 Pitfalls

  • Overlapping mutable buffers. Manifestation: two logically distinct tensors alias the same physical buffer without a mark. Root cause: an arena-packing bug reusing a buffer before its last use completes. Debugging: alias verifier's overlap report cross-referenced against the interference graph. Recovery: reject the plan, widen the interference edge, replan (I10 recovery path).
  • Spill storms. Manifestation: pathologically many buffers spill simultaneously, thrashing the slower storage tier. Root cause: arena-packing heuristic optimized for count, not for spill-cost weight. Recovery: cost-weighted packing that prioritizes keeping high-reuse buffers resident.
  • Device OOM despite a "verified" plan. Manifestation: the plan fits the declared ceiling but the actual device has less free VRAM (another tenant's context). Root cause: plan assumed 80% VRAM cap (§4) is always available. Recovery: runtime allocator must re-validate against live device free-memory at load time, not trust the compile-time plan blindly.

17.7 Performance Concerns

Allocation fragmentation from imperfect bin packing; cache locality of packed buffers (co-locating buffers with temporally adjacent access patterns); NUMA cross-node allocation cost when worker-to- node affinity is violated; interference-graph construction cost at 5M-node scale (§4).

17.8 Edge Cases

Dynamic tensor expansion beyond the planned size; device OOM at load time despite a compile-time- verified plan; zero-lifetime (immediately dead) buffers; pinned-memory exhaustion under high concurrent-compilation load (128-worker ceiling, §4).

17.9 Failure Analysis

Detection: replayable allocation maps mean any memory-plan failure can be replayed against the exact interference graph that produced it. Blast radius: an alias violation is silent numerical corruption if undetected — this is why the validator is a hard gate, not advisory. Recovery: reject-and-replan with reduced parallelism (fewer concurrent buffer-reuse candidates) if the first plan fails validation.

17.10 Operational Notes

Metrics: memory_plan_peak_bytes, alias_violation_total, spill_event_total. Export allocation heatmaps (buffer × time) for operator-facing visualization. Tracing spans: memplan.lifetime, memplan.interference, memplan.pack. Structured-log fields add peak_bytes, spill_count.

18. Phase 6 — Scheduler, Tiling & Kernel Fusion Lowering

18.1 Objectives

Transform verified, memory-planned Tensor SSA IR into execution-oriented schedules: loop-nest tiling, vectorization, thread/warp mapping, and kernel-fusion legality-to-decision promotion. Implements the schedule/algorithm-separation principle (§5, Halide) as a distinct IR layer from op semantics.

18.2 Detailed Implementation Steps

Implement loop-nest generation and the tile planner (crates/scheduler/src/tile_planner.rs) using polyhedral-model tiling informed by Tensor Comprehensions (Vasilache et al. 2018, §5); implement vector-width inference (vectorize.rs) targeting AVX2 baseline with AVX-512 opportunistic upgrade (§4); implement the parallel-region planner and GPU thread-mapping (thread_map.rs) producing SchedulerPlan.parallel_regions (§11); promote Phase 4's fusion-legality analysis into committed fusion-group decisions (fusion_legality.rs), gated by a static cost model (P15); implement reduction lowering (associative-reduction tree generation) and memory-locality scoring feeding tile-size selection. TVM's schedule-abstraction separation (Chen et al. 2018, §5) is the direct model for keeping SchedulerPlan a distinct, serializable artifact rather than baking tiling decisions into the SSA IR itself.

18.3 Deliverable

Executable lowering plans: vectorized CPU loop nests and valid CUDA/HIP launch-configuration candidates, both derived from the same SchedulerPlan structure, ready for Phase 7/8 codegen.

18.4 Acceptance Criteria

Vectorized CPU kernels generated for 100% of eligible ops in the conformance corpus; valid CUDA launch configurations (grid/block dims within device limits) for 100% of GPU-targeted graphs; fusion-legality analysis achieves ≥ 30% op-count reduction via fusion on the GEMM+activation benchmark chain; schedule construction stays within the 5-sec p95 compile budget (§4).

18.5 Conformance Fixtures

  • fixtures/scheduler/irregular_shape_001.ir — a non-tile-divisible tensor shape; expects a valid remainder-handling schedule, not a rejected compile.
  • fixtures/scheduler/fusion_legality_002.ir — two ops with an aliasing hazard between them; expects fusion rejection despite otherwise-favorable cost.
  • fixtures/scheduler/register_pressure_003.ir — a deeply unrolled reduction; expects tile-size backoff rather than register-pressure-induced spill explosion.
  • fixtures/scheduler/replay_schedule_004 — a known schedule decision; replay must reproduce an identical SchedulerPlan hash.

18.6 Pitfalls

  • Register-pressure explosion. Manifestation: an aggressively unrolled/fused kernel exceeds available registers, forcing spills that erase the fusion's benefit. Root cause: cost model ignores register-pressure estimate. Debugging: LLVM/PTX register-usage report cross-referenced against the schedule. Recovery: cost model incorporates an estimated register-pressure penalty (P15 — measured, not guessed).
  • Occupancy collapse. Manifestation: GPU kernel occupancy drops far below the 60% benchmark target (Phase 8 acceptance criterion) due to an oversized thread-block chosen by the tile planner. Debugging: Nsight occupancy report. Recovery: thread-mapping heuristic bounded by a measured occupancy model, not a fixed block size.
  • Non-divisible tiling silently dropping remainder elements. Manifestation: a tile size that doesn't evenly divide the tensor shape drops trailing elements. Root cause: missing remainder- loop generation. Recovery: every tiled loop nest generates an explicit remainder handler; this is a correctness bug, not a performance nit.

18.7 Performance Concerns

Branch divergence from irregular tiling on GPU warps; memory coalescing (contiguous access pattern selection in thread_map.rs); tile-size search cost bounded by the static cost model rather than exhaustive search — search-based autotuning (Ansor, Zheng et al. 2020, §5) is deliberately deferred, PhaseDeferred("§18"), registered in §35.

18.8 Edge Cases

Irregular tensor shapes with no clean tile factor; non-divisible tiling remainder handling; auto-parallelization across multiple devices is out of scope here, PhaseDeferred("§18"), registered in §35 — this phase schedules within a single target device only; fusion across a control-region boundary (rejected by construction, not attempted).

18.9 Failure Analysis

Detection: schedule-replay logs let a bad schedule decision be reproduced and diffed against a prior good one. Blast radius: a bad tile/fusion decision degrades performance, not correctness (fusion legality is verified before commit, I3-adjacent) — this phase cannot silently corrupt results, only under-perform. Recovery: fall back to the unfused, untiled baseline schedule if the optimized schedule fails a post-hoc sanity cost check.

18.10 Operational Notes

Metrics: fusion_group_count, estimated_occupancy_ratio, tile_size_selected. Export occupancy estimates per kernel for operator dashboards. Tracing spans: scheduler.tile, scheduler.fuse, scheduler.thread_map. Structured-log fields add schedule_hash.

19. Phase 7 — LLVM/CPU Backend Codegen

19.1 Objectives

19.2 Detailed Implementation Steps

Implement SchedulerPlan-to-LLVM-IR lowering (crates/backend-llvm/src/lower.rs) using LLVM IR as the backend target (ADR-23); implement calling-convention support matching the host System V (or platform-native) ABI; implement vector-intrinsic mapping from SchedulerPlan.vector_width to LLVM's AVX2/AVX-512 intrinsics (intrinsics.rs); wire register-allocation hooks to LLVM's own allocator (delegated per §1 boundaries); implement object emission (object_emit.rs) to ELF (ADR-16... — see §9's ABI/object-format decision, folded into artifact-format) with relocation handling and symbol resolution; preserve DWARF debug maps end-to-end from Tensor SSA IR source locations. Polly's polyhedral loop transformation directly on LLVM IR (Grosser et al. 2012, §5) informs how loop-nest metadata from SchedulerPlan is attached as LLVM loop metadata rather than re-derived by LLVM's own (weaker) loop analysis.

19.3 Deliverable

Runnable CPU executable artifacts: a compiled GEMM kernel passes a numerical-correctness benchmark against a reference (NumPy-equivalent) implementation, with ABI-conformant calling convention.

19.4 Acceptance Criteria

Matrix-multiply benchmark (benchmarks/gemm_bench.rs) passes correctness within a declared 1e-6 relative-tolerance bound (P8); ABI conformance validated against the platform calling convention for 100% of exported kernel entry points; object emission succeeds for 100% of the CPU-targeted conformance corpus; LLVM lowering completes in < 2 sec for the 50k-op medium-graph benchmark (§4).

19.5 Conformance Fixtures

  • fixtures/backend-llvm/invalid_ir_001.ll — a deliberately malformed LLVM IR fragment; expects LLVM's own verifier to reject it with a captured diagnostic dump, not a silent miscompile.
  • fixtures/backend-llvm/stack_misalign_002 — a kernel with a deliberately misaligned stack frame; expects detection via a sanitizer-instrumented debug build.
  • fixtures/backend-llvm/gemm_correctness_003 — the standard GEMM benchmark; expects numerical match within 1e-6 relative tolerance against a reference implementation.
  • fixtures/backend-llvm/replay_codegen_004 — a known lowering; replay must reproduce an identical object-file hash.

19.6 Pitfalls

  • Invalid LLVM IR from lowering. Manifestation: LLVM's verifier rejects generated IR. Root cause: a SchedulerPlan field (e.g. an out-of-range vector width) not validated before lowering. Debugging: capture the LLVM verifier dump (retained per docs/failure-analysis/). Recovery: add a pre-lowering SchedulerPlan validation pass that rejects invalid plans before they reach LLVM.
  • Stack misalignment. Manifestation: an intermittent SIGSEGV on vector-intrinsic-heavy kernels. Root cause: a calling-convention edge case for a vector-return-value function not matching the platform ABI. Debugging: sanitizer (ASan/UBSan) build reproduces deterministically. Recovery: ABI-conformance fixture added for the specific vector-width/return-type combination that failed.
  • Unsupported instruction on an older target CPU. Manifestation: a binary built assuming AVX-512 SIGILLs on an AVX2-only host. Root cause: target-feature detection not gating codegen. Recovery: runtime CPU-feature detection selects the correct pre-compiled kernel variant (I9 ABI-stability discipline extended to multi-target dispatch).

19.7 Performance Concerns

Instruction-cache pressure from over-large generated kernels; vector-lane underutilization when vector_width inference under-estimates available SIMD width; relocation/symbol-resolution overhead at link time for large kernel counts.

19.8 Edge Cases

Huge stack frames from deeply unrolled loops; unsupported instructions on a target below the AVX2 floor (§4, hard rejection, not silent fallback); a TPU backend and production-grade WASM SIMD hardening are both out of scope here, PhaseDeferred("§19"), registered in §35 — the WASM crate compiles a minimal, unoptimized fallback path only.

19.9 Failure Analysis

Detection: LLVM verifier dumps are retained (not discarded) on every rejection for postmortem triage. Blast radius: a bad codegen lowering affects only the artifacts built from it — artifacts are immutable and content-addressed (I13), so a bad build never silently overwrites a good one. Recovery: rebuild from the same Tensor SSA IR with the fixed lowering; the fix is always traceable to a specific SchedulerPlan/lowering-pass combination via replay.

19.10 Operational Notes

Metrics: llvm_lowering_duration_seconds, object_emit_failures_total. Preserve debug symbols (DWARF) in every artifact by default; stripping is an explicit opt-in for distribution builds only. Tracing spans: backend_llvm.lower, backend_llvm.emit. Structured-log fields add target_features, object_hash.

20. Phase 8 — CUDA/ROCm GPU Backend & Runtime Executor

20.1 Objectives

Implement PTX/HIP GPU lowering and the runtime executor that loads artifacts, manages streams and device buffers, and dispatches kernels. This is the phase where the artifact-generation and runtime-engine boxes of §3 both become real, executing code.

20.2 Detailed Implementation Steps

Implement the PTX emitter (crates/backend-cuda/src/ptx.rs) per the PTX ISA Specification (§5); implement the stream scheduler and device allocator (streams.rs, crates/execution-engine/src/ stream_manager.rs, device_alloc.rs) enforcing stream isolation (I7); implement launch- parameter planning and the occupancy estimator (occupancy.rs) per Kirk & Hwu's occupancy model (§5); implement synchronization barriers and async host-device memcpy scheduling; implement the shared-memory planner for GPU kernels; implement the HIP backend (crates/backend-rocm/src/hip.rs) targeting source-level CUDA-to-HIP portability (ADR-26); implement the runtime artifact loader (crates/runtime/src/loader.rs) enforcing I6 version rejection and the runtime ABI validator (abi.rs). Glow's graph-level backend-abstraction boundary (pytorch/glow lib/Backend/, §5) is the direct model for keeping RuntimeExecutor (§11) backend-agnostic at the trait level while CUDA/ROCm specifics stay inside their own crates.

20.3 Deliverable

GPU-executable kernels with correctness parity against the Phase 7 CPU backend, plus a running runtime executor capable of loading an artifact and dispatching it end-to-end with deterministic completion events.

20.4 Acceptance Criteria

Numerical correctness parity against the CPU backend within the same 1e-6 relative-tolerance bound (P8) across the full GEMM/conv/attention benchmark suite; measured occupancy > 60% on the standard benchmark set (§28); runtime dispatch latency p50 < 5 µs, p95 < 20 µs (§4); runtime crash recovery completes in < 5 sec (§4 runtime restart RTO).

20.5 Conformance Fixtures

  • fixtures/backend-cuda/warp_divergence_001 — a deliberately branchy kernel; expects a captured divergence-ratio metric, not a correctness failure (divergence is a perf signal, not a bug by itself, unless it also breaks I7).
  • fixtures/backend-cuda/bank_conflict_002 — a shared-memory access pattern with deliberate bank conflicts; expects detection via the occupancy/perf telemetry, informing the shared-memory planner's next iteration.
  • fixtures/runtime/device_reset_003 — a simulated mid-execution device reset; expects runtime restart within 5 sec and no cross-stream state leakage (I7).
  • fixtures/runtime/replay_execution_004 — a known execution trace; replay must reproduce identical completion-event ordering.

20.6 Pitfalls

  • Warp divergence. Manifestation: measured occupancy far below the 60% target despite a seemingly reasonable schedule. Root cause: data-dependent branching inside a kernel the scheduler treated as branch-free. Debugging: PTX dump plus Nsight divergence report. Recovery: schedule cost model penalizes known-divergent op patterns; fall back to a branch-free predicated variant.
  • Shared-memory bank conflicts. Manifestation: measured throughput far below the theoretical bandwidth for a kernel using shared memory. Root cause: stride pattern maps multiple threads to the same bank. Recovery: shared-memory planner pads/reorders layout to avoid the conflicting stride.
  • Stream leaks. Manifestation: runtime memory grows unbounded under sustained load. Root cause: a cancelled or errored execution path fails to release its stream back to the pool (P11 structured-concurrency violation). Debugging: stream-table occupancy telemetry. Recovery: every stream acquisition is scoped via a guard that releases on every exit path, including panic.

20.7 Performance Concerns

PCIe/NVLink transfer amplification from host-device memcpy on every dispatch that could instead be kept device-resident; kernel-launch overhead (§4's < 20 µs budget) under high stream-count fan-out (up to 4,096 streams); async-memcpy scheduling overlap efficiency against compute.

20.8 Edge Cases

Device reset mid-execution (driver-level recovery event); kernel timeout (a runaway kernel that never signals completion); distributed graph partitioning across multiple nodes and online adaptive recompilation are both out of scope here, PhaseDeferred("§20"), registered in §35 — this phase's runtime is single-node, single-artifact-per-load only; partial-graph execution after a mid-graph device fault.

20.9 Failure Analysis

Detection: PTX dumps are retained on backend failure for postmortem triage; GPU telemetry exports device-reset and kernel-timeout events distinctly from ordinary completion events. Blast radius: stream isolation (I7) bounds a single stream's fault to that stream; a device reset is contained to in-flight work on that device, not cross-device. Recovery: runtime restart (< 5 sec RTO, §4) reloads the immutable artifact and re-establishes streams from a clean state.

20.10 Operational Notes

Metrics: gpu_occupancy_ratio, kernel_launch_failures_total, device_reset_total, runtime_dispatch_latency_seconds. GPU telemetry exported per-device, per-stream. Tracing spans: backend_cuda.emit, runtime.dispatch, runtime.synchronize. Runtime dashboards are mandatory for production deployment, not optional.

21. Phase 9 — Profiling, Deterministic Replay & Conformance Hardening

21.1 Objectives

Implement the profiling/diagnostics suite (span instrumentation, flamegraph export, crash dumps) and the deterministic-replay event store, then harden the whole pipeline with large-scale fuzzing, property testing, and differential backend validation. This is the phase that turns every earlier phase's replay-logging discipline (P2) into an operable postmortem tool.

21.2 Detailed Implementation Steps

Implement span instrumentation (crates/profiling/src/span_recorder.rs) wrapping every pass and runtime dispatch (P6); implement the replay event store (crates/replay/src/event_store.rs) as an append-only binary log (ADR-05-adjacent format choice) and the divergence detector (divergence.rs) implementing I8; implement flamegraph export (flamegraph.rs) and a crash-dump format capturing IR state, replay offset, and pass lineage; implement memory-timeline recording and kernel-trace correlation across the CPU/GPU boundary; implement ONNX-corpus fuzzing, malformed-IR generators, property tests (rewrite idempotence, verifier invariants — ADR-12), differential backend validation (CPU vs. CUDA vs. ROCm numerical parity), deterministic-replay CI (every CI compilation is replayed and hash-compared), and chaos fault injection (forced device resets, allocator failures). Systems Performance's profiling methodology (Brendan Gregg, §5) directly shapes the flamegraph/tracing pipeline structure here.

21.3 Deliverable

A production-ready validation and diagnostics pipeline: every CI compilation is replay-verified, every backend is differentially validated against every other, and the fuzzing corpus runs continuously without a verifier crash.

21.4 Acceptance Criteria

Replay fidelity 100% across every CI-run compilation (§4 SLO, shared with §24); fuzz stability > 72 continuous hours with zero verifier crashes (ADR-13); differential CPU/CUDA/ROCm numerical parity within the 1e-6 tolerance bound (P8) across the full benchmark suite; end-to-end traces visible for 100% of sampled compilations.

21.5 Conformance Fixtures

  • fixtures/replay/corrupted_log_001 — a deliberately truncated replay log; expects a detected, diagnosed corruption, not a silent partial replay.
  • fixtures/replay/clock_skew_002 — replay events with out-of-order monotonic timestamps across a simulated clock-skew injection; expects I5 monotonicity-violation detection.
  • fixtures/conformance/malformed_nested_003.onnx — a deeply nested malformed graph; expects automatic minimization to the smallest failing subgraph.
  • fixtures/conformance/soak_72h_004 — the standing 72-hour continuous fuzz/compile soak fixture set, run nightly.

21.6 Pitfalls

  • Excessive telemetry overhead. Manifestation: span instrumentation itself measurably slows the pipeline below the p95 compile-latency budget (§4). Root cause: unsampled, unconditional span creation on a hot per-node loop. Recovery: sampling controls (mandatory, §21.10) reduce span-creation rate under load while preserving 100% coverage for CI-run replay verification.
  • Trace clock skew. Manifestation: spans from different threads appear out of causal order. Root cause: mixing monotonic and wall-clock timestamps across threads (ADR-20 violation). Recovery: enforce CLOCK_MONOTONIC exclusively for span ordering; wall-clock only for the human-facing log timestamp.
  • Flaky replay tests masking real nondeterminism. Manifestation: a replay-fidelity test fails intermittently and gets re-run until green. Root cause: hidden nondeterminism (e.g. an unordered iteration somewhere upstream) treated as test flakiness instead of a P1 violation. Recovery: any replay-fidelity failure is a blocking bug report, never a retry-until-green.

21.7 Performance Concerns

Tracing allocation overhead on span creation at high pass-invocation rates; replay-log write amplification under the bounded-ring-buffer retention policy (§4); CI runtime scaling as the conformance corpus and fuzz-seed corpus both grow monotonically over the project's lifetime.

21.8 Edge Cases

Corrupted replay logs (partial writes from a prior crash); malformed deeply-nested graphs; clock-skew-induced monotonicity violations (I5); a fuzz-discovered crash that cannot be minimized within a bounded time budget (escalates to manual triage rather than blocking CI indefinitely).

21.9 Failure Analysis

Detection: replay-divergence detection (I8) is the primary signal that something upstream violated determinism. Blast radius: a hardening-phase failure indicates a latent bug in an earlier phase, not a new bug introduced here — this phase's role is exposure, not containment. Recovery: automatic minimization of fuzz-discovered failures to the smallest reproducing fixture, filed with the exact phase and pass implicated.

21.10 Operational Notes

Metrics: replay_divergence_total, fuzz_crash_total, trace_span_count, soak_uptime_hours. Sampling controls are mandatory: 100% span capture for CI-run replay verification, configurable sampling for production-load tracing to stay under the telemetry-overhead budget. Nightly stress runs (72-hour soak) are a mandatory release gate, not advisory. Tracing spans: profiling.flamegraph, replay.divergence_check. Structured-log fields add replay_offset, fuzz_seed_id.

24. Operational Readiness

Metrics strategy. Every phase emits its own counters/histograms (cataloged per-phase in N.10); the aggregate SLO dashboard tracks compile_latency_seconds, pass_duration_seconds, runtime_dispatch_latency_seconds, kernel_launch_failures_total, allocator_fragmentation_ratio, replay_divergence_total. All metrics are Prometheus-scraped (ADR-11) with dimensional labels for backend_target, pass_id, phase.

Tracing strategy. Every compiler pass and every runtime dispatch produces a span (P6) carrying span ID, artifact hash, and pass-lineage metadata, exported via OpenTelemetry (ADR-10). Sampling is 100% for CI-run replay verification and configurable for production load (§21.10).

Logging. Structured JSON only (ADR-09), never plaintext in CI or production. Required fields on every log line: session_id, artifact_hash, backend_target, pass_id.

SLOs. Compilation success rate > 99% (measured against VERIFICATION_FAILED/LOWERING_FAILED/ BACKEND_FAILURE/OOM outcomes); replay fidelity 100% (I8, no exceptions); runtime crash-free execution > 99.95% (matches §4's runtime availability budget).

Deployment topology. Stateless compiler workers behind a task queue (bounded, P4); a shared content-addressed artifact object store (ADR-04); isolated runtime executors, one process per host device group, never sharing mutable state across executors (I7).

Rollback strategy. Artifacts are immutable (P5) — a rollback is always "load an older content-addressed artifact," never "revert a mutation." Runtime loaders are versioned (I6); a rollback that crosses an incompatible artifact-version boundary is rejected at load time, not half-applied.

25. Compatibility & Versioning

Wire compatibility. CompileRequest/CompileResponse (§11) schemas are backward compatible within a major version; a new optional field never breaks an older client (P13).

Storage compatibility. Artifacts remain readable across minor releases; a major-version artifact-format change requires an explicit migration tool, never an in-place reinterpretation.

Schema evolution. Append-only field numbering across every FlatBuffers schema (ADR-05, P13) — no field is ever renumbered or removed, only deprecated in documentation.

API stability. Backend traits (GraphOp, RuntimeExecutor, §11) are versioned (P9); extending a trait uses default methods, never a signature break within a major version.

Deprecation policy. Two-release minimum deprecation window for any field, metric name, or trait method before removal; deprecated items are flagged in CHANGELOG.md and emit a one-time warning telemetry event on first use per process.

26. Testing & Verification Strategy

Unit testing. Per-crate correctness: parser tokenization, verifier checks, allocator behavior, shape-lattice operations — one test module per source file in §10/§37.

Integration testing. End-to-end graph-to-execution round trips across the full pipeline, gated in CI on every merge.

Differential testing. Cross-backend numerical parity (CPU vs. CUDA vs. ROCm) within the 1e-6 tolerance bound (P8), run on the standard benchmark suite (§28) every release.

Property testing. Rewrite idempotence (proptest, ADR-12), verifier-invariant preservation under randomly generated well-formed IR, shape-lattice associativity/commutativity.

Fuzzing. Malformed-graph generation (frontend), malformed-SSA generation (post-Phase-2), continuous via libFuzzer (ADR-13), seeded from the quarantine corpus (T1, T9).

Chaos testing. Simulated device resets (FM-5), forced allocator failures, injected clock skew (ADR-20-adjacent), replay-log truncation (FM-6-adjacent).

Deterministic replay. Every CI compilation is replayed and hash-compared (I8); a replay-fidelity failure blocks the merge, never gets retried until green (FM-11).

Soak testing. 72-hour continuous compilation/fuzz workload, nightly, as a mandatory release gate (§21.10) — not an advisory dashboard.

29. Scalability Analysis

Bottlenecks. LLVM lowering throughput is the dominant single-threaded-per-graph bottleneck (§29/Q14); GPU launch serialization under high stream fan-out (§4's 4,096-stream ceiling); replay persistence IO under the bounded-ring-buffer retention policy at high transformation rates.

Horizontal scaling. Stateless compiler workers (§24) scale by adding worker processes up to the 128-worker ceiling (§4); each worker owns an independent CompilerSession with no shared mutable state, so horizontal scaling adds throughput linearly until FD/NUMA limits (C6, C11, §32) bind.

Vertical scaling. Parallel pass execution within a single session where the pass-dependency graph (§16) permits independent passes to run concurrently on disjoint subgraphs — bounded by the lock-contention ceiling (§4, < 2%).

Metadata scaling. Content-addressed artifact indexing (ADR-04) scales the artifact store independently of compilation-worker count; a relational catalog is deliberately rejected (ADR-04 6th column) until tenant count exceeds what filesystem/object-store indexing can serve.

30. Mental Models & First Principles

  • MM1 — Schedule Is Not Algorithm. Numerical semantics and execution strategy are orthogonal axes; predicts a fusion/tiling bug should never change results, only speed; without it: a correctness regression gets triaged as a performance regression; applies in §18.
  • MM2 — Determinism Is a Debugging Multiplier. A deterministic pipeline turns every bug into a replayable, bisectable artifact; predicts nondeterminism compounds — one unordered iteration poisons every downstream replay; without it: "worked on retry" bugs that never get root-caused; applies in §21.
  • MM3 — Alias Safety Is a Memory-Planning Property, Not a Type-System Property. Rust's borrow checker cannot see across the arena/IR boundary; predicts a memory-safe language does not imply an alias-safe compiler; without it: silent numerical corruption mistaken for a training instability; applies in §17.
  • MM4 — Cost Models Must Be Measured, Never Assumed. A heuristic that looks correct on paper can regress real hardware; predicts any unmeasured heuristic eventually regresses a real workload; without it: a "principled" tile-size formula ships slower than the naive default; applies in §18 and §28.
  • MM5 — Fail-Closed Beats Fail-Soft in a Compiler. A compiler's job is to refuse ambiguity, not resolve it silently; predicts every "helpful" default eventually produces a silently wrong artifact; without it: a compiler that "just works" on malformed input until it produces a wrong number; applies in §15 and §16.
  • MM6 — Immutable Artifacts Turn Caching Into a Correctness Tool. Content-addressing collapses "is this the same build" into a hash comparison; predicts any artifact-store mutation bug reintroduces every caching bug this design prevents; without it: stale-artifact-served-as-fresh incidents; applies in §20 and §27.
  • MM7 — Occupancy Is a Consequence, Not a Target. Occupancy is a downstream measurement of register pressure, shared-memory use, and divergence; predicts chasing occupancy in isolation produces an "occupied" but not faster kernel; without it: block-size tuning that looks good on the occupancy dashboard while wall-clock throughput stays flat; applies in §20.
  • MM8 — A Verifier Is Cheaper Than a Postmortem. Every invariant check added before a phase ships is orders of magnitude cheaper than reconstructing the same violation from an incident; predicts skipping a verifier pass to hit a deadline always costs more later; without it: a violation surfaces phases downstream as an unrelated-looking crash; applies in §14 and §21.

32. Back-of-Envelope Capacity Model

  • C1 — Node Overhead Budget. 5,000,000 nodes × 256 B/node = 1.28 GB IR overhead, inside the 8 GB §4 default ceiling, leaving 6.72 GB for buffers, arenas, and pass working sets.
  • C2 — Cold Parse Time. 5,000,000 nodes ÷ 100,000 nodes/sec = 50 sec worst-case cold parse, exceeding the p99 20 sec compile-latency budget (§4) ⇒ the largest graphs require streaming/incremental parse (§13).
  • C3 — Pass Budget Per Node. 10,000 transforms/sec × 20 sec p99 window = 200,000 transformations available, and 200,000 ÷ 5,000,000 nodes = 0.04 average transformations-per-node, forcing selective/greedy rewrite scheduling (§16) rather than exhaustive fixpoint iteration.
  • C4 — Memory-Plan Reuse Gain. 40% peak-reduction target (§17) applied to an illustrative 3.2 GB unplanned peak = 1.28 GB saved, landing at 1.92 GB peak, inside an 8 GB GPU's 80% VRAM cap (6.4 GB, §4).
  • C5 — Launch-Storm Ceiling. 4,096 max streams (§4) × 20 µs launch overhead (§4) = 81.92 ms worst-case fully-serialized launch storm, which async queue overlap (§20) must hide to keep the p95 20 µs per-op dispatch target intact.
  • C6 — FD Budget Per Worker. 8,192 max FDs (§4) ÷ 128 concurrent compilation workers (§4) = 64 FDs/worker average, covering artifact files, mmap segments, and telemetry sockets.
  • C7 — Max Artifact Size. 5,000,000 nodes × 256 B/node × 2.5x amplification ceiling (§4) = 3.2 GB maximum artifact-bundle size for the largest supported graph.
  • C8 — Composite Availability. 99.5% compiler availability × 99.95% runtime availability (§4) = 99.45% end-to-end compile-then-execute availability, ≈ 2,890 minutes/year combined downtime budget.
  • C9 — Worst-Case Recovery Chain. 30 sec compiler-crash RTO + 5 sec runtime-restart RTO + 60 sec replay-reconstruction RTO (§4) = 95 sec worst-case full recovery chain, inside a 5-minute operator escalation SLA.
  • C10 — Lock-Wait Ceiling. 2% lock-contention overhead ceiling (§4) × 5 µs p50 dispatch (§4) = 100 ns max amortized lock-wait per dispatch call, across up to 4,096 concurrent streams.
  • C11 — NUMA Arena Sizing. 128 compilation workers (§4) ÷ 8 NUMA nodes on a representative dual-socket host = 16 workers/node, and 8 GB ÷ 8 nodes = 1 GB max per-node arena size to avoid cross-node spill.
  • C12 — Replay Ring-Buffer Sizing. 10,000 transforms/sec optimizer ceiling (§4) × 60 sec replay-reconstruction window (§4) = 600,000 events, and 600,000 × 64 B/event = 38.4 MB bounded ring buffer per session, well inside the 8 GB memory ceiling.

34. Alternative Architectures (Roads Not Taken)

Alt A — Polyhedral-First Compiler

graph --> polyhedral model (iteration domains + schedule map) --> direct codegen
          (no separate heuristic tile-planner stage)

Regime where it wins: dense affine loop nests with regular access patterns — classical HPC kernels with no data-dependent control flow. Real system: Tensor Comprehensions (Vasilache et al. 2018, §5) and Tiramisu take this approach as their primary compilation strategy, not just a Phase-6 technique. Why this blueprint rejects it as the whole architecture: polyhedral model construction and scheduling scale poorly on irregular, control-flow-heavy ML graphs (attention with data-dependent masking, dynamic shapes) that dominate this project's target workloads; polyhedral techniques are retained as one tile-planner input (§18.2), not the compiler's spine.

Alt B — Interpreted / Bytecode Execution

graph --> bytecode VM --> dispatch loop interprets ops directly
          (no LLVM/PTX codegen stage at all)

Regime where it wins: rapid iteration and debugging where compile latency must be near-zero and peak throughput is secondary. Real system: ONNX Runtime's default CPU execution provider (interpreted op-kernel dispatch). Why rejected: interpretation overhead per op would violate the §4 runtime-dispatch p95 20 µs target at the scale of this project's target workloads (GEMM/conv/ attention benchmarks, §28); native codegen is required to hit the occupancy and throughput targets in §28's M6/M8.

Alt C — Single-IR-Layer Design

graph IR (with SSA-like def/use annotations bolted on)
   --> backend lowering directly
       (no distinct Tensor SSA IR stage)

Regime where it wins: a small, fixed backend set where dominance/effect tracking overhead isn't worth a second IR layer. Real system: Glow (pytorch/glow) goes straight from its single graph IR to backend lowering. Why rejected: I1 (dominance) and I3 (alias safety) need an explicit, independently-checkable SSA layer (§7); collapsing the layers would make the Phase 2 verifier (§14) inseparable from Phase 1's frontend trust-boundary logic, weakening the P7 fail-closed guarantee this project treats as non-negotiable.

36. Glossary

  • SSA — Static Single Assignment; every value is defined exactly once, enabling dominance- based correctness reasoning.
  • Dominance — CFG property: block A dominates block B if every path to B passes through A; governs SSA use validity (I1).
  • Fusion — combining adjacent kernels into one executable unit to eliminate intermediate materialization.
  • Tiling — partitioning a computation into cache- or register-sized blocks for locality.
  • Vectorization — SIMD transformation mapping scalar loop iterations onto vector lanes.
  • Occupancy — ratio of active GPU warps to the hardware maximum on a given multiprocessor.
  • Warp Divergence — GPU threads within a warp taking different execution paths, serializing otherwise-parallel work.
  • Alias Analysis — determining whether two memory references may overlap.
  • Interference Graph — graph whose edges mark buffers with overlapping lifetimes, used for allocation packing.
  • Spill — moving a value out of a fast storage tier (register/cache) to a slower one under pressure.
  • Replay Log — deterministic, append-only record of every transformation applied to an IR.
  • Shape Inference — deducing tensor dimensions, including resolving symbolic bindings.
  • Lowering — transforming a higher-level IR into a lower-level, more execution-oriented one.
  • Canonicalization — normalizing semantically equivalent IR into one stable form.
  • CFG — Control Flow Graph.
  • CSE — Common Subexpression Elimination.
  • DCE — Dead Code (Op) Elimination.
  • NUMA — Non-Uniform Memory Access; memory latency depends on which CPU socket issues the access.
  • ABI — Application Binary Interface; the calling-convention and layout contract between compiled units.
  • PTX — NVIDIA's intermediate GPU instruction set architecture, target of the CUDA backend.
  • HSACO — the compiled binary object format produced by the ROCm/HIP toolchain.
  • IR — Intermediate Representation.
  • HLO — High-Level Operations, XLA's graph-level IR.
  • Broadcast — implicit shape expansion rule for elementwise ops on mismatched-rank tensors.
  • Content Addressing — identifying an artifact by the hash of its contents rather than a mutable name/path.
  • Arena Allocator — a bump/pool allocator that owns a batch of same-lifetime objects together.
  • Bank Conflict — multiple GPU threads accessing the same shared-memory bank in one cycle, serializing the access.
  • Register Pressure — the degree to which live values exceed available hardware registers.
  • Backpressure — an explicit bounded-queue rejection/slow-down signal preventing unbounded buildup.
  • Structured Concurrency — a concurrency discipline where every task's lifetime is scoped to its spawning context.
  • Crash-Only Software — components designed to recover solely via restart, never in-place repair.
  • BLAKE3 — the cryptographic hash function used for content-addressing artifacts (ADR-27).
  • FlatBuffers — the zero-copy binary serialization format used for artifact bundles (ADR-05).
  • Sigstore — a keyless code-signing infrastructure backed by a public transparency log (ADR-17).
  • SBOM — Software Bill of Materials; a manifest of every dependency in a build.
  • Soak Test — a long-duration (72-hour) continuous workload run to surface rare/slow failures.
  • Differential Testing — comparing two independent implementations' outputs on the same input to detect divergence.
  • Property Testing — generating randomized inputs to check a general property rather than a fixed example.
  • Polyhedral Model — a mathematical (integer linear programming) representation of loop iteration spaces used for scheduling transformations.
  • Grid/Block Dimensions — the GPU kernel launch-configuration parameters controlling thread and thread-block counts.
  • Shared Memory — fast, on-chip, block-scoped GPU memory explicitly managed by the kernel.
  • HIP — AMD's CUDA-source-portable GPU programming model, target of the ROCm backend.
  • DWARF — a standard debugging-information format encoding source-line and symbol data.
  • ELF — Executable and Linkable Format, the object/executable file format on Linux targets.
  • Ring Buffer — a fixed-capacity circular buffer used here to bound replay-log retention.
