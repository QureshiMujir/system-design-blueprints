⬜ Phase 0 — Repository Foundation & Correctness Kernel §12

Objectives

Stand up a deterministic, reproducible Rust workspace; establish CI, linting, and dependency-audit gates; wire the shared error taxonomy, telemetry scaffolding, and config loading every later crate depends on; stand up empty arena/verifier skeletons so Phase 1 has a compilable target. Introduces the constraint that nothing downstream may bypass the shared crates/errors taxonomy or emit unstructured logs (P6, ADR-09).

Deliverable

A runnable, empty-pipeline workspace: cargo build --workspace succeeds, cargo clippy --workspace -- -D warnings is clean, CI is green on both platforms, and a deterministic-build job reproduces an identical binary hash across two consecutive runs.

Acceptance

CI green on Linux x86_64 and AArch64; zero clippy warnings across all 20 crates; two consecutive release builds produce an identical BLAKE3 binary hash (ADR-27); cargo audit reports zero critical advisories; workspace cold build completes in < 5 minutes on the CI runner class.

Fixtures
  • fixtures/build/reproducible-build-001 — two builds from the same commit must hash-match.
  • fixtures/errors/error-taxonomy-001 — every error variant round-trips through structured JSON logging with all required fields (session_id, artifact_hash, backend_target, pass_id).
  • fixtures/build/toolchain-drift-001 — a deliberately mismatched toolchain version must fail CI with a named diagnostic, not a silent stale-cache success.
Pitfalls
  • Dependency drift. Manifestation: inconsistent binary hashes between two CI runs. Root cause: an unpinned transitive dependency resolved to a newer patch version. Debugging: diff Cargo.lock between the two runs. Signal: reproducible-build-001 fixture fails. Recovery: restore the known-good lockfile, re-pin via cargo update -p <crate> --precise.
  • Non-deterministic logging field order. Manifestation: structurally identical log lines hash differently. Root cause: HashMap-backed field ordering instead of a stable BTreeMap/ordered struct. Debugging: byte-diff two log lines for the same event. Signal: replay/log-hash fixtures intermittently fail. Recovery: switch to ordered field emission, add a lint rule forbidding HashMap in any serialized-log-adjacent type.
  • Silent clippy-allow creep. Manifestation: warnings reappear after a dependency bump. Root cause: a local #[allow(...)] masking a real issue instead of fixing it. Debugging: grep for #[allow( outside an explicit allowlist file. Recovery: CI gate on a tracked allowlist, not ad hoc inline suppressions.

⬜ Phase 1 — Graph IR & Frontend Import §13

Objectives

Implement the canonical arena-backed Graph IR and an ONNX-compatible (plus StableHLO-shaped) frontend parser. Establishes the trust boundary (§3) at which untrusted external graphs are validated or rejected before any optimizer code ever sees them (P7).

Deliverable

A parser that imports medium ONNX-like graphs (~50k ops) and serializes deterministic, hashed canonical Graph IR, with a verifier that rejects malformed input before it reaches the optimizer.

Acceptance

10,000 ONNX-conformance graphs from conformance/onnx/ import successfully; all malformed fixtures in fixtures/parser/ are rejected with a T1-class diagnostic; graph hashing is byte-for-byte deterministic across 3 repeated imports of the same input; parse throughput ≥ 100k nodes/sec (§4) measured on the 50k-op medium-graph benchmark.

Fixtures
  • fixtures/parser/malformed_cycle_graph.onnx — a cyclic op-graph; expects cycle-detection rejection.
  • fixtures/parser/invalid_broadcast_001.onnx — [4,8]+[7,8]; expects verifier rejection, no silent coercion.
  • fixtures/parser/symbolic_shape_001.onnx — a graph with an unresolved symbolic dimension binding; expects deferred-to-Phase-3 shape-solver handoff, not a Phase 1 crash.
  • fixtures/parser/replay_import_001.onnx — a known-good graph; import must be byte-identical across replay.
Pitfalls
  • Silent shape drift. Manifestation: two imports of the same graph produce different shape metadata. Root cause: inconsistent symbolic-dimension propagation order (violates I4). Debugging: diff canonical hashes across imports. Signal: replay_import_001 fixture fails. Recovery: enforce stable topological visitation order in the canonicalizer.
  • Arena fragmentation. Manifestation: memory overhead per node exceeds the 256 B budget (§4) under excessive node churn during canonicalization. Root cause: repeated allocate/free cycles instead of in-place arena compaction. Debugging: arena occupancy telemetry. Recovery: batch canonicalization rewrites and compact the arena once per pass, not per rewrite.
  • Unsupported-op silent pass-through. Manifestation: an op with no registered GraphOp impl is silently skipped rather than rejected. Root cause: a missing exhaustiveness check in the op registry lookup. Recovery: op registry lookup must be P7 fail-closed by construction — no default no-op fallback.

⬜ Phase 2 — Tensor SSA IR & Verifier §14

Objectives

Lower canonical Graph IR into the Tensor SSA IR — the canonical optimization substrate (§3) — with a dominance-checking verifier and a textual printer for debugging and roundtrip testing. Introduces the SSA-dominance invariant (I1) as a hard gate before any optimization pass runs.

Deliverable

A stable Tensor SSA IR with a dominance-verified block graph, a working textual printer, and roundtrip serialization fidelity measured against the Phase 1 corpus.

Acceptance

Dominance verification passes on 100% of the 10,000-graph conformance corpus; printer/parser roundtrip fidelity > 99.99% byte-identical reconstruction; zero unresolved SSA references across the corpus; verifier runs in < 200 ms on the 50k-op medium-graph benchmark.

Fixtures
  • fixtures/ssa/dominance_violation_001.ir — a hand-crafted use-before-definition; expects I1 rejection.
  • fixtures/ssa/alias_conflict_002.ir — two SSA values sharing an alias group without an explicit mark; expects verifier rejection (groundwork for I3, fully enforced in Phase 5). fixtures/ssa/roundtrip_regression_003.ir — a regression fixture from a prior printer bug; must roundtrip byte-identical.
  • fixtures/ssa/unreachable_block_004.ir — a block with no predecessor; expects a warning-class diagnostic, not a hard failure, since dead-code elimination (Phase 4) will remove it.
Pitfalls
  • SSA rewrite corruption. Manifestation: a rewrite updates a value but not its dominance-tree position. Root cause: dominance tree treated as a cache instead of being invalidated on block- graph mutation. Debugging: re-run the dominance verifier immediately post-rewrite in debug builds. Signal: dominance_violation_001-style fixture regressions. Recovery: invalidate and recompute the dominance tree on every block-graph structural change, never patch it in place.
  • Invalid dominance updates under block splitting. Manifestation: splitting a block for a later fusion pass (Phase 6) silently breaks dominance for values defined pre-split. Root cause: block split implemented before the dominance-tree update rule was specified. Recovery: block split is only ever performed through a single verified helper that atomically updates dominance.
  • Phi-node inconsistency at irregular merge points. Manifestation: a value reaching a merge from only one predecessor is treated as if reaching from both. Debugging: verifier's merge- completeness check. Recovery: reject incomplete merges at construction time, not at use time.

⬜ Phase 3 — Shape Inference & Type System §15

Objectives

Implement global shape inference over symbolic dimensions and a dtype lattice for mixed-precision graphs. Closes the [N,M]*[M,K] ambiguity class from §8 by either resolving every symbolic binding or rejecting the graph — never guessing.

Deliverable

Full graph shape/dtype validation: every tensor in a compiled graph has either a fully resolved concrete shape or an explicitly bounded symbolic shape with a documented runtime-binding contract.

Acceptance

100% of symbolic constraints in the 10,000-graph corpus resolve or are explicitly and correctly rejected as ambiguous (zero silent guesses); solver termination guaranteed within a 10,000- iteration ceiling (P10, I11-adjacent); zero graphs reach Phase 4 with an unresolved runtime shape ambiguity.

Fixtures
  • fixtures/shapes/unresolved_binding_001.ir — [N,M]*[M,K] with M unbound; expects rejection, not a default binding.
  • fixtures/shapes/zero_dim_002.ir — a zero-dimension tensor; expects explicit lattice handling, not a divide-by-zero panic downstream.
  • fixtures/shapes/mixed_precision_003.ir — fp16/fp32 mixed graph; expects dtype-lattice-correct promotion.
  • fixtures/shapes/solver_ceiling_004.ir — an adversarially deep symbolic-recursion fixture; expects clean termination at the iteration ceiling with a diagnostic, not a stack overflow.
Pitfalls
  • Infinite symbolic recursion. Manifestation: solver never terminates on a self-referential symbolic expression. Root cause: no iteration ceiling enforced (P10 violation). Debugging: solver-iteration-count telemetry. Recovery: hard ceiling with a named diagnostic, never a silent hang.
  • Overflow during dimension multiplication. Manifestation: a large-batch symbolic product overflows u64 silently. Root cause: unchecked multiplication in shape-expression evaluation. Recovery: checked arithmetic with an explicit OOM/overflow diagnostic path, never wraparound.
  • Ambiguity masked by a permissive default. Manifestation: an unresolved dimension silently defaults to 1. Root cause: a convenience fallback added under deadline pressure, violating P7. Recovery: remove all implicit defaults; every unresolved binding is a hard rejection.

⬜ Phase 4 — Optimization Pass Framework §16

Objectives

Implement the pass manager and the core algebraic-optimization pass suite: constant folding, dead-op elimination, CSE, and fusion planning (legality analysis; scheduling/codegen fusion lands in Phase 6). Establishes replay-logged, deterministic pass ordering (I4, I5) as the correctness backbone for every mutation from here on.

Deliverable

A composable optimization framework producing deterministic, replay-reproducible pass output on the full conformance corpus, with fusion-legality analysis available for Phase 6 to consume.

Acceptance

Pass output is byte-identical across 3 repeated runs on all 10,000 corpus graphs; replay reconstruction of any single pass invocation succeeds with 100% fidelity; rewrite-rule catalog covers ≥ 40 named algebraic identities with documented tolerance annotations; zero rewrite- oscillation failures across a 72-hour soak (shared gate with §21).

Fixtures
  • fixtures/optimizer/rewrite_replay_001 — a known rewrite sequence; replay must reproduce the identical resulting IR hash.
  • fixtures/optimizer/cse_validation_002 — a graph with duplicated subexpressions; CSE must collapse them to a single value with no shape/dtype drift.
  • fixtures/optimizer/cyclic_rewrite_003 — a deliberately oscillating rewrite pair (A→B→A); expects oscillation detection, not an infinite pass loop (I11).
  • fixtures/optimizer/overflow_fold_004 — constant folding of an operation that would overflow; expects rejection of the fold, not a silently wrong folded constant.
Pitfalls
  • Invalidated analysis reuse. Manifestation: a pass reads a stale shape-analysis result after a preceding pass mutated shapes. Root cause: missing invalidation wiring in the pass dependency graph. Debugging: analysis-cache version-stamp mismatch assertion. Recovery: every analysis result carries a version stamp checked on read; stale reads abort rather than silently succeed.
  • Rewrite oscillation. Manifestation: two rewrite rules undo each other, looping until the iteration ceiling (I11). Debugging: replay-log diff shows the same node hash recurring. Recovery: rule-priority ordering plus a strict cost-decrease requirement per applied rewrite.
  • Fold-through-overflow. Manifestation: constant folding silently wraps an integer overflow into a wrong constant. Root cause: unchecked arithmetic in constant_fold.rs. Recovery: checked arithmetic; a fold that would overflow is simply not applied (P8).

⬜ Phase 5 — Memory Planner & Alias Analysis §17

Objectives

Implement static memory planning: buffer-lifetime analysis, interference-graph construction, arena packing, spill decisions, and full alias-safety validation. Promotes the effect-tagging groundwork from Phase 2 into a hard, verified gate (I3, I10) before any buffer is scheduled for reuse.

Deliverable

A static allocation planner producing a verified, alias-safe memory plan with measured peak- allocation reduction versus an unplanned baseline, feeding directly into Phase 6's scheduler and Phase 7/8 backend codegen.

Acceptance

Peak memory reduction > 40% versus unplanned baseline allocation, measured on the standard GEMM/ conv/attention benchmark suite (§28); alias verifier reports zero violations across the full 10,000-graph corpus; memory-plan construction completes within the 5-sec p95 compile-latency budget (§4) for medium graphs.

Fixtures
  • fixtures/memory/overlap_violation_001.ir — two buffers with overlapping lifetimes and no alias mark; expects rejection.
  • fixtures/memory/spill_storm_002.ir — a graph with more live tensors than fit the memory ceiling; expects deterministic, bounded spill decisions, not an OOM.
  • fixtures/memory/numa_affinity_003.ir — a host-allocation-heavy graph; expects allocations local to the owning worker's NUMA node.
  • fixtures/memory/dynamic_expansion_004.ir — a tensor whose size grows at runtime past its planned allocation; expects a detected-and-rejected plan, not silent buffer overrun.
Pitfalls
  • Overlapping mutable buffers. Manifestation: two logically distinct tensors alias the same physical buffer without a mark. Root cause: an arena-packing bug reusing a buffer before its last use completes. Debugging: alias verifier's overlap report cross-referenced against the interference graph. Recovery: reject the plan, widen the interference edge, replan (I10 recovery path).
  • Spill storms. Manifestation: pathologically many buffers spill simultaneously, thrashing the slower storage tier. Root cause: arena-packing heuristic optimized for count, not for spill-cost weight. Recovery: cost-weighted packing that prioritizes keeping high-reuse buffers resident.
  • Device OOM despite a "verified" plan. Manifestation: the plan fits the declared ceiling but the actual device has less free VRAM (another tenant's context). Root cause: plan assumed 80% VRAM cap (§4) is always available. Recovery: runtime allocator must re-validate against live device free-memory at load time, not trust the compile-time plan blindly.

⬜ Phase 6 — Scheduler, Tiling & Kernel Fusion Lowering §18

Objectives

Transform verified, memory-planned Tensor SSA IR into execution-oriented schedules: loop-nest tiling, vectorization, thread/warp mapping, and kernel-fusion legality-to-decision promotion. Implements the schedule/algorithm-separation principle (§5, Halide) as a distinct IR layer from op semantics.

Deliverable

Executable lowering plans: vectorized CPU loop nests and valid CUDA/HIP launch-configuration candidates, both derived from the same SchedulerPlan structure, ready for Phase 7/8 codegen.

Acceptance

Vectorized CPU kernels generated for 100% of eligible ops in the conformance corpus; valid CUDA launch configurations (grid/block dims within device limits) for 100% of GPU-targeted graphs; fusion-legality analysis achieves ≥ 30% op-count reduction via fusion on the GEMM+activation benchmark chain; schedule construction stays within the 5-sec p95 compile budget (§4).

Fixtures
  • fixtures/scheduler/irregular_shape_001.ir — a non-tile-divisible tensor shape; expects a valid remainder-handling schedule, not a rejected compile.
  • fixtures/scheduler/fusion_legality_002.ir — two ops with an aliasing hazard between them; expects fusion rejection despite otherwise-favorable cost.
  • fixtures/scheduler/register_pressure_003.ir — a deeply unrolled reduction; expects tile-size backoff rather than register-pressure-induced spill explosion.
  • fixtures/scheduler/replay_schedule_004 — a known schedule decision; replay must reproduce an identical SchedulerPlan hash.
Pitfalls
  • Register-pressure explosion. Manifestation: an aggressively unrolled/fused kernel exceeds available registers, forcing spills that erase the fusion's benefit. Root cause: cost model ignores register-pressure estimate. Debugging: LLVM/PTX register-usage report cross-referenced against the schedule. Recovery: cost model incorporates an estimated register-pressure penalty (P15 — measured, not guessed).
  • Occupancy collapse. Manifestation: GPU kernel occupancy drops far below the 60% benchmark target (Phase 8 acceptance criterion) due to an oversized thread-block chosen by the tile planner. Debugging: Nsight occupancy report. Recovery: thread-mapping heuristic bounded by a measured occupancy model, not a fixed block size.
  • Non-divisible tiling silently dropping remainder elements. Manifestation: a tile size that doesn't evenly divide the tensor shape drops trailing elements. Root cause: missing remainder- loop generation. Recovery: every tiled loop nest generates an explicit remainder handler; this is a correctness bug, not a performance nit.

⬜ Phase 7 — LLVM/CPU Backend Codegen §19

Objectives

Implement CPU code generation through LLVM IR: calling-convention support, vector-intrinsic mapping, object emission, and relocation/symbol handling, producing the first end-to-end runnable executable artifacts in the pipeline.

Deliverable

Runnable CPU executable artifacts: a compiled GEMM kernel passes a numerical-correctness benchmark against a reference (NumPy-equivalent) implementation, with ABI-conformant calling convention.

Acceptance

Matrix-multiply benchmark (benchmarks/gemm_bench.rs) passes correctness within a declared 1e-6 relative-tolerance bound (P8); ABI conformance validated against the platform calling convention for 100% of exported kernel entry points; object emission succeeds for 100% of the CPU-targeted conformance corpus; LLVM lowering completes in < 2 sec for the 50k-op medium-graph benchmark (§4).

Fixtures
  • fixtures/backend-llvm/invalid_ir_001.ll — a deliberately malformed LLVM IR fragment; expects LLVM's own verifier to reject it with a captured diagnostic dump, not a silent miscompile.
  • fixtures/backend-llvm/stack_misalign_002 — a kernel with a deliberately misaligned stack frame; expects detection via a sanitizer-instrumented debug build.
  • fixtures/backend-llvm/gemm_correctness_003 — the standard GEMM benchmark; expects numerical match within 1e-6 relative tolerance against a reference implementation.
  • fixtures/backend-llvm/replay_codegen_004 — a known lowering; replay must reproduce an identical object-file hash.
Pitfalls
  • Invalid LLVM IR from lowering. Manifestation: LLVM's verifier rejects generated IR. Root cause: a SchedulerPlan field (e.g. an out-of-range vector width) not validated before lowering. Debugging: capture the LLVM verifier dump (retained per docs/failure-analysis/). Recovery: add a pre-lowering SchedulerPlan validation pass that rejects invalid plans before they reach LLVM.
  • Stack misalignment. Manifestation: an intermittent SIGSEGV on vector-intrinsic-heavy kernels. Root cause: a calling-convention edge case for a vector-return-value function not matching the platform ABI. Debugging: sanitizer (ASan/UBSan) build reproduces deterministically. Recovery: ABI-conformance fixture added for the specific vector-width/return-type combination that failed.
  • Unsupported instruction on an older target CPU. Manifestation: a binary built assuming AVX-512 SIGILLs on an AVX2-only host. Root cause: target-feature detection not gating codegen. Recovery: runtime CPU-feature detection selects the correct pre-compiled kernel variant (I9 ABI-stability discipline extended to multi-target dispatch).

⬜ Phase 8 — CUDA/ROCm GPU Backend & Runtime Executor §20

Objectives

Implement PTX/HIP GPU lowering and the runtime executor that loads artifacts, manages streams and device buffers, and dispatches kernels. This is the phase where the artifact-generation and runtime-engine boxes of §3 both become real, executing code.

Deliverable

GPU-executable kernels with correctness parity against the Phase 7 CPU backend, plus a running runtime executor capable of loading an artifact and dispatching it end-to-end with deterministic completion events.

Acceptance

Numerical correctness parity against the CPU backend within the same 1e-6 relative-tolerance bound (P8) across the full GEMM/conv/attention benchmark suite; measured occupancy > 60% on the standard benchmark set (§28); runtime dispatch latency p50 < 5 µs, p95 < 20 µs (§4); runtime crash recovery completes in < 5 sec (§4 runtime restart RTO).

Fixtures
  • fixtures/backend-cuda/warp_divergence_001 — a deliberately branchy kernel; expects a captured divergence-ratio metric, not a correctness failure (divergence is a perf signal, not a bug by itself, unless it also breaks I7).
  • fixtures/backend-cuda/bank_conflict_002 — a shared-memory access pattern with deliberate bank conflicts; expects detection via the occupancy/perf telemetry, informing the shared-memory planner's next iteration.
  • fixtures/runtime/device_reset_003 — a simulated mid-execution device reset; expects runtime restart within 5 sec and no cross-stream state leakage (I7).
  • fixtures/runtime/replay_execution_004 — a known execution trace; replay must reproduce identical completion-event ordering.
Pitfalls
  • Warp divergence. Manifestation: measured occupancy far below the 60% target despite a seemingly reasonable schedule. Root cause: data-dependent branching inside a kernel the scheduler treated as branch-free. Debugging: PTX dump plus Nsight divergence report. Recovery: schedule cost model penalizes known-divergent op patterns; fall back to a branch-free predicated variant.
  • Shared-memory bank conflicts. Manifestation: measured throughput far below the theoretical bandwidth for a kernel using shared memory. Root cause: stride pattern maps multiple threads to the same bank. Recovery: shared-memory planner pads/reorders layout to avoid the conflicting stride.
  • Stream leaks. Manifestation: runtime memory grows unbounded under sustained load. Root cause: a cancelled or errored execution path fails to release its stream back to the pool (P11 structured-concurrency violation). Debugging: stream-table occupancy telemetry. Recovery: every stream acquisition is scoped via a guard that releases on every exit path, including panic.

⬜ Phase 9 — Profiling, Deterministic Replay & Conformance Hardening §21

Objectives

Implement the profiling/diagnostics suite (span instrumentation, flamegraph export, crash dumps) and the deterministic-replay event store, then harden the whole pipeline with large-scale fuzzing, property testing, and differential backend validation. This is the phase that turns every earlier phase's replay-logging discipline (P2) into an operable postmortem tool.

Deliverable

A production-ready validation and diagnostics pipeline: every CI compilation is replay-verified, every backend is differentially validated against every other, and the fuzzing corpus runs continuously without a verifier crash.

Acceptance

Replay fidelity 100% across every CI-run compilation (§4 SLO, shared with §24); fuzz stability > 72 continuous hours with zero verifier crashes (ADR-13); differential CPU/CUDA/ROCm numerical parity within the 1e-6 tolerance bound (P8) across the full benchmark suite; end-to-end traces visible for 100% of sampled compilations.

Fixtures
  • fixtures/replay/corrupted_log_001 — a deliberately truncated replay log; expects a detected, diagnosed corruption, not a silent partial replay.
  • fixtures/replay/clock_skew_002 — replay events with out-of-order monotonic timestamps across a simulated clock-skew injection; expects I5 monotonicity-violation detection.
  • fixtures/conformance/malformed_nested_003.onnx — a deeply nested malformed graph; expects automatic minimization to the smallest failing subgraph.
  • fixtures/conformance/soak_72h_004 — the standing 72-hour continuous fuzz/compile soak fixture set, run nightly.
Pitfalls
  • Excessive telemetry overhead. Manifestation: span instrumentation itself measurably slows the pipeline below the p95 compile-latency budget (§4). Root cause: unsampled, unconditional span creation on a hot per-node loop. Recovery: sampling controls (mandatory, §21.10) reduce span-creation rate under load while preserving 100% coverage for CI-run replay verification.
  • Trace clock skew. Manifestation: spans from different threads appear out of causal order. Root cause: mixing monotonic and wall-clock timestamps across threads (ADR-20 violation). Recovery: enforce CLOCK_MONOTONIC exclusively for span ordering; wall-clock only for the human-facing log timestamp.
  • Flaky replay tests masking real nondeterminism. Manifestation: a replay-fidelity test fails intermittently and gets re-run until green. Root cause: hidden nondeterminism (e.g. an unordered iteration somewhere upstream) treated as test flakiness instead of a P1 violation. Recovery: any replay-fidelity failure is a blocking bug report, never a retry-until-green.
