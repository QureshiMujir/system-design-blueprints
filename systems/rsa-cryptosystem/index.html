In one paragraph

This is a design for an RSA library written from scratch in safe Rust: big-number arithmetic, key generation, the four RSA primitives, signature and encryption padding, and key file formats (§1). It follows PKCS #1 v2.2 and FIPS 186-5 (§1). It has no server and no daemon. It is linked into the caller's process, such as a TLS stack, a JWT verifier or an SSH agent (§1). Correctness and resistance to side channels are the product (§1). Its central rule: the time and memory-access pattern of every private-key operation depend only on the key size, never on the key or the message (§4, I5). The embedding application runs it and owns key storage, transport and sessions (§1).

The problem, concretely

RSA is still in every TLS certificate chain, every code-signing PKI, every JWT signed RS256 or PS256, and every S/MIME message (§2). The textbook formula is c = m^e mod n and m = c^d mod n, shown on tiny numbers p = 61, q = 53, e = 17, d = 2753 (§8.1, §8.5). The blueprint says it is never used directly (§8.1). Three naive shortcuts each fail in a specific way:

  • Fast but breakable. Splitting the private computation across the two primes makes it about four times cheaper (§32 item 6). It also creates one recombination step. If one half is corrupted by a voltage glitch, the result looks plausible but is wrong, and a single gcd against n exposes a prime factor (§8.2, §8.7, MM3). The blueprint's own two accounts differ on which prime (see "CRT decryption and its fault check" below).
  • Padding that round-trips but is not safe. A decoder that returns a different error for a bad label than for a bad padding boundary is a distinguishing oracle (§8.6). A padding variant can pass every round-trip test and still be broken, because the security proof assumes the exact byte layout (MM2).
  • Silence is also an output. "We never print the key" is not enough, because the order of operations inside the exponentiation is what a timing measurement observes (MM1), and an error path that differs in timing is itself an oracle (MM5).

The whole design answers those pressures structurally. The wrong function does not type-check (P6), and the safety checks have no off switch (§3, I6).

How it works, end to end

Follow one signature through the layers of §3's diagram, then its verification (§8.4):

 Caller (TLS stack, JWT verifier, SSH agent, S/MIME, ACME client)
   │  public API (Phase 9)
 Encoding layer   rsa-core::encoding   EMSA-PSS (default) | EMSA-PKCS1-v1.5 (verify-only default) |
                                       EME-OAEP (default) | EME-PKCS1-v1.5 (decrypt-only) | I2OSP/OS2IP
   │  RSAEP / RSADP / RSASP1 / RSAVP1
 Primitive layer  rsa-core::primitives  CRT private ops + fault check; blinding wrapper (Phase 7)
   ├─ Modular arithmetic  rsa-bignum   Montgomery multiply, mod_exp_ct (secret), mod_exp_pub (public)
   └─ Key generation      rsa-prime + rsa-core::key   Miller-Rabin, Lucas, FIPS 186-5 flow, CRT params
   │
 Bignum primitives  rsa-bignum   u64 limbs, extended-Euclid GCD/inverse, constant-time select, zeroizing
 Key export         rsa-keys (std-bound)   PKCS#1 / PKCS#8 / JWK / PEM
  1. The caller hashes the message (mHash = Hash(message), a 32-byte digest in the SHA-256 example), then EmsaPss::encode (in rsa-core::encoding) turns the digest and a random salt into an encoded message EM (§8.4 steps 1-2).
  2. OS2IP(EM) converts the bytes into a big integer m < n (§8.4 step 3). The primitive layer rejects any value >= n before exponentiating (I14).
  3. RSASP1 (in rsa-core::primitives) signs m. It runs CRT and blinding (§8.4 step 4, §16, §19) and calls the secret-exponent path mod_exp_ct in rsa-bignum (§16.2, P6).
  4. I2OSP(s) writes the signature as k bytes (§8.4 step 5).
  5. To verify, OS2IP reads the signature, RSAVP1 computes m' with the public-exponent path mod_exp_pub, and EMSA-PSS-Verify compares the result byte for byte (§8.4 steps 6-9, I11).
  6. The key itself was produced earlier by rsa-prime and rsa-core::key (§3). rsa-keys exports it as PKCS#1 DER, PKCS#8 DER, JWK or PEM (§3, ADR-14). rsa-cli is a thin keygen, sign, verify, encrypt, decrypt binary, and conformance/ runs the test-vector corpora (§1).

Three properties hold throughout (§3). The bignum layer is the foundation, so Phase 1 is differentially tested against num-bigint before anything is built on it. The private hot path is constant-time by the choice of algorithm, not patched afterwards. CRT decryption is the only place a single-bit fault can leak the key, so its defence is mandatory with no configuration flag (I6).

The core ideas

Textbook RSA on small numbers (§8.1, §8.5)

A key is n = p·q for two primes. The public exponent e and private exponent d satisfy e·d ≡ 1 (mod λ(n)), where λ(n) = lcm(p−1, q−1) is the FIPS-186-5-mandated choice (Carmichael function) (§8.1). The blueprint's classic walkthrough (§8.5):

Quantity Value
p, q 61, 53
n = p·q 3233
φ(n) = (p−1)(q−1) 60 · 52 = 3120
e 17 (gcd(17, 3120) = 1)
d = e⁻¹ mod 3120 2753
Encrypt m = 65 c = 65¹⁷ mod 3233 = 2790
Decrypt 2790²⁷⁵³ mod 3233 = 65

The blueprint labels these parameters illustrative only. Production keys are at least 2048-bit (§8.5, P9, ADR-12). The walkthrough computes d modulo φ(n) (§8.5), while §8.1 names λ(n) as the FIPS-186-5-mandated choice. Production encryption always wraps m in OAEP first (§8.5).

Montgomery form and the constant-time ladder (§8.1, §14.2, ADR-04, ADR-05)

The design avoids division in the hot loop (ADR-04). In Montgomery form a number a is stored as ā = a·R mod n with R = 2^(64·limb_count), and MontMul(ā, b̄) = a·b·R mod n is computed in O(limb_count²) word operations with no division (§8.1, ADR-04). The blueprint requires an odd modulus and rejects an even one with an error (§14.4).

Exponentiation then runs as a fixed-iteration Montgomery ladder (§14.2 step 3). For each bit of the secret exponent it does the same three things whatever the bit is: one constant-time conditional swap, one multiply, one square. The instruction count and memory-access pattern therefore do not depend on the bit (§14.2 step 3, I5). MM1 gives the reason: a private exponent is a secret schedule, not a secret number, and the sequence of operations is what a side channel sees (MM1).

The public path mod_exp_pub uses a windowed method, which the blueprint says is safe only because e or a signature under verification is public (§14.2 step 4, ADR-05). Two newtypes, SecretExponent and PublicExponent, make calling the fast path with a secret a compile error (§11, P6).

CRT decryption and its fault check (§8.2, §8.7, I6, MM3)

A private operation with (p, q, dP, dQ, qInv) computes the answer mod p and mod q separately and recombines (§8.2):

Step Computation Produces
1 m1 = c^dP mod p partial result mod p
2 m2 = c^dQ mod q partial result mod q
3 h = qInv · (m1 − m2) mod p correction term
4 m = m2 + h·q recombined result mod n
5 (I6) c' = m^e mod n; require c' = c fault check

§32 item 6 derives the speed-up: exponentiation cost scales with bit-length cubed, so two half-width exponentiations cost 2 × (1/2)³ = 2 × 0.125 = 0.25× one full-width exponentiation, about 4× faster (§32 item 6, §4). §8.2 words it differently: steps 1-2 are "each ~4× cheaper" than a full-width exponentiation, which does not match §32's 0.125× per half. The blueprint does not reconcile the two (§8.2, §32 item 6).

Step 5 is the price. Without it, a fault in m1 recombines into a consistent-looking but wrong result, and one gcd against n factors the key. The two accounts name different primes: §8.2 says gcd(m_faulty^e − c, n) recovers p, while §8.7 says gcd(s_faulty^e − message, n) shares the factor q. The blueprint states both and does not resolve them (§8.2, §8.7). With the check, the call returns Err(FaultInjection) and discards the value (§16.2 step 4, §11). It costs one public-exponent exponentiation, about 0.1 ms at 2048-bit, per private operation (P4).

Padding is part of the security proof (§8.3, MM2, I9, I10, I11)

Padding is the byte layout around m that the proofs assume (MM2). Both schemes share the mask function MGF1, a hash-based mask generator (§8.3). The layouts (§8.3, k = modulus bytes, hLen = hash length):

OAEP:  DB = lHash || PS || 0x01 || M ;  seed = random(hLen)
       maskedDB = DB XOR MGF1(seed, k-hLen-1) ; maskedSeed = seed XOR MGF1(maskedDB, hLen)
       EM = 0x00 || maskedSeed || maskedDB
PSS:   M' = 0x00 x8 || mHash || salt ;  H = Hash(M') ;  DB = PS || 0x01 || salt
       maskedDB = DB XOR MGF1(H, emLen-hLen-1) ;  EM = maskedDB || H || 0xbc

On the decode side, the OAEP decoder combines every validity check (leading byte, label hash, the 0x01 boundary) into one constant-time Choice and never branches on any single result (§18.2 step 2). On failure it returns a fixed-length decoy that depends only on the ciphertext, for example a truncated HMAC(fixed_key, ciphertext) (§18.2 step 2, I9). The caller cannot tell a wrong label from wrong padding by return value, error type or timing (§8.6). The PKCS1-v1.5 decoder does the same (I10), and v1.5 encryption is not implemented at all (§18.2 step 4, P3). Verification rejects any byte deviation from the canonical encoding, with no early accept (I11).

Blinding: hiding the real input from the clock (§19.2, P5, I7)

Even a constant-time ladder leaves a remote timing attack open, which blinding closes (ADR-07). Per call (§19.2 steps 1-2):

  1. Draw a fresh random invertible r from the caller's RNG.
  2. Compute c_blind = c · r^e mod n (a public-exponent operation) and run the CRT private operation on c_blind.
  3. Unblind with m = m_blind · r^{-1} mod n.

Where the fault check sits relative to unblinding is described two ways. §16.6 and §19.2 step 2 require it to run on the blinded intermediate, before unblinding, and §19.2 calls that step order security-critical. §8.7 instead describes the check on the returned signature, comparing s_faulty^e mod n with the original message representative. The blueprint does not reconcile the two (§8.7, §16.6, §19.2 step 2).

A property test checks that two calls with the same input but different r give identical unblinded output (I7, §19.4). The blueprint puts the cost at one extra modular exponentiation and one modular inverse per call (P5), and at most 0.15 ms at 2048-bit (§19.4).

Key generation is a rejection sampler (§15.2, MM6, I1-I4, I12)

Keygen proposes candidates and throws most of them away (MM6). Per §15.2:

  1. Trial-divide against primes up to 65,521, which removes about 87% of composites cheaply.
  2. Run Miller-Rabin (a probabilistic primality test) with the FIPS 186-5 Table A.1 round count: 27 rounds for 2048 to 3071 bits, 41 for 3072 and above (I12, P7).
  3. For the two nlen/2-bit primes, reject if |p−q| < 2^(nlen/2−100) (I4, Fermat factoring), or if p ≡ 1 or q ≡ 1 (mod e) (I2). Compute d = e⁻¹ mod λ(n) and reject d ≤ 2^(nlen/2) (I3, Wiener).
  4. Derive dP, dQ, qInv (§15.2 step 5). e is always 65537 and keygen() takes no e (P9).

The rare rejections are the security boundary. Skipping one silently narrows the guaranteed margin (MM6).

The trade-offs — where engineers disagree

Modular multiplication: Montgomery (ADR-04)

Chosen: Montgomery multiplication, for an O(k²) reduction with no division in the hot loop (§9, §8.1). Rejected: Barrett reduction, schoolbook division. When the rejected choice is right: Barrett wins when the same modulus is used for very few multiplications, because setup cost dominates (§9 ADR-04).

Secret exponentiation: constant-time ladder (ADR-05)

Chosen: the Montgomery ladder, which eliminates Kocher (1996)-class timing leaks by construction (§9, P6). Rejected: square-and-multiply, windowed-NAF for secrets. When the rejected choice is right: windowed-NAF wins for public-exponent-only workloads such as verify and encrypt, which the design does use for mod_exp_pub (§9 ADR-05, §14). The cost: private operations run about 4-10× slower than the fastest windowed method (P6).

Fault defence: always re-encrypt and compare (ADR-06)

Chosen: a mandatory re-encryption check (I6), which closes Boneh-DeMillo-Lipton (1997) at the algorithm level (§9). Rejected: no check (raw CRT), or a checksum-only check. When the rejected choice is right: no check wins only in a fault-free simulator or test harness explicitly excluded from production (§9 ADR-06).

Timing defence: blinding on top of the ladder (ADR-07)

Chosen: mandatory blinding (P5), which closes Brumley-Boneh (2003) beyond the ladder's guarantee (§9). Rejected: rely on the ladder alone. When the rejected choice is right: the ladder alone wins when the attacker has no network or co-residency access at all, such as an offline HSM with no shared clock (§9 ADR-07).

Signing default: PSS (ADR-10)

Chosen: RSA-PSS, with a provable existential-unforgeability argument (Bellare-Rogaway 1996) (§9, P2). Rejected: PKCS1-v1.5 signing. When the rejected choice is right: only for verifying or interoperating with a legacy peer that cannot upgrade (§9 ADR-10). The blueprint keeps v1.5 signing behind a legacy-pkcs1-sign feature flag (§17.2 step 5).

Encryption default: OAEP (ADR-11)

Chosen: RSA-OAEP, which is IND-CCA2 under the RSA assumption and closes Bleichenbacher (1998) (§9, P3). Rejected: PKCS1-v1.5 encryption. When the rejected choice is right: PKCS1-v1.5 decrypt (never encrypt) wins only for decrypting legacy ciphertexts, always behind the Bleichenbacher countermeasure (§9 ADR-11).

Roads not taken (§34, §35)

ECC-first design (§34 A): sign with Ed25519 instead of RSA. It wins on bandwidth- and CPU-constrained mobile and embedded targets and on any greenfield protocol, as in SSH Ed25519 host keys and TLS 1.3 defaults. It is rejected here because the project teaches bignum, CRT and padding-oracle mechanics that ECC's fixed-size field arithmetic does not exercise the same way, and because X.509 and JWT-RS256 legacy PKI still mandates RSA in many audited environments (§34 A).

Non-CRT private path (§34 B): one full-width constant-time exponentiation, with no recombination step. It wins in ultra-conservative FIPS-boundary or HSM firmware where the CRT fault surface must be removed structurally; some smartcard and EMV RSA implementations chose this. It is rejected here because the roughly 4× throughput cost (§32 item 6) is unacceptable for server-side TLS and JWT workloads (§34 B, §4).

HSM or PKCS#11-backed signing (§34 C): the key never leaves hardware. It wins in regulated environments (PCI-HSM, FIPS 140-3 Level 3+) and is the correct production choice for the highest assurance tier, but an opaque vendor boundary defeats the teaching purpose (§2), so it is deferred (§34 C, §35).

Post-quantum hybrid key transport (§34 D): an RSA-OAEP-wrapped key share plus an ML-KEM ciphertext. It wins for any new TLS or SSH deployment today, given harvest-now-decrypt-later, as in Chrome/BoringSSL's X25519Kyber768 hybrid. It is a distinct future project (§34 D, §35).

Multi-prime RSA and sub-quadratic multiplication (§35): multi-prime RSA has k−1 recombination points, each an independent fault surface, so it waits for a throughput need beyond about 4× CRT (MM8, §35). Karatsuba and Toom-Cook wait until profiling shows multiplication, not the exponentiation loop, dominates a private operation (§35).

What must never be false

Each line: the rule, then how the system notices and the telemetry name (§7).

  • I1: n = p·q for exactly two distinct primes of the configured size. Keygen self-check on bit_len(n); keygen.modulus_bits.
  • I2: gcd(e, λ(n)) = 1, so d exists. Explicit gcd check; keygen.gcd_reject_total.
  • I3: d > 2^(nlen/2), since a small d falls to Wiener's attack. Bound check; keygen.small_d_reject_total.
  • I4: |p − q| ≥ 2^(nlen/2 − 100), defeating Fermat factoring. Bound check; keygen.close_prime_reject_total.
  • I5: every private-exponent exponentiation is data-independent in time and memory access. dudect t-statistic ≤ 4.5 over 10^7 samples; timing.dudect_t_stat. CI blocks the merge, with no runtime recovery.
  • I6: every CRT private operation verifies its output by re-encryption. The re_encrypt(result) == input comparison; crt.fault_check_fail_total.
  • I7: every sign or decrypt blinds with a fresh random invertible r. Property test: different r, same unblinded output; blinding.rng_draw_total.
  • I8: RsaPrivateKey is zeroized on drop and never implements Debug or Display. Caught at compile time; no runtime telemetry.
  • I9: an OAEP decode failure gives a fixed-length, ciphertext-deterministic decoy, indistinguishable in timing. dudect on valid-vs-invalid; oaep.decode_timing_t_stat.
  • I10: PKCS1-v1.5 decode never reveals which check failed. Timing harness over the four Bleichenbacher oracle conditions; pkcs1.decode_timing_t_stat.
  • I11: verification rejects any byte-level deviation from the canonical encoding. Byte-exact comparison, no early accept; verify.reject_total by reason.
  • I12: the Miller-Rabin round count meets FIPS 186-5 Table A.1. Assertion at the call site, and the build fails otherwise; keygen.mr_iterations.
  • I13: every entropy-consuming function takes an explicit RngCore. Caught at compile time, since no default-RNG code path exists.
  • I14: the message or ciphertext representative is always < n. Explicit >= comparison before every exponentiation; primitive.range_reject_total.

What breaks in production

  • FM-1: key-correlated latency in sign or decrypt (§23). A non-constant-time regression in mod_exp_ct makes latency track key or exponent values. The dudect CI gate should catch it before release, and production latency-distribution alerting is the backstop. There is no auto recovery: roll back the release and fix it (§23 FM-1).
  • FM-2: a signature fails with FaultInjection. A voltage glitch, a cosmic ray or an active attack corrupted the CRT computation. crt.fault_check_fail_total goes nonzero and the operation returns Err, and the caller retries; §4 calls it a hard-fail return, never retried silently. Manual recovery: investigate the hardware and escalate if the rate stays nonzero (§23 FM-2, §4).
  • FM-3: a surge of malformed decryptions. Someone is probing for a Bleichenbacher or Manger oracle. The only signal is the undifferentiated encoding.decode_fail_total spike. The decoder is already oracle-safe (I9, I10), so the response is to rate-limit at the transport layer, outside this library (§23 FM-3).
  • FM-6: dudect or miri fails intermittently. It may be flaky infrastructure or a real nondeterministic bug. The blueprint says to treat intermittent dudect failures as real until proven otherwise (§23 FM-6).
  • FM-8: keygen never finishes. A degenerate or adversarial RNG never yields an acceptable candidate. It surfaces as KeyGenerationExhausted and the retry-ceiling counter, and returns Err instead of hanging (§23 FM-8, §11).
  • FM-9: a secret appears in a memory dump. The compiler removed an ad hoc zero-out as a dead store. The fix is to use zeroize-backed clearing everywhere and audit any hand-rolled clearing (§23 FM-9, MM7, ADR-22).
  • FM-10: the blinding factor r repeats. An RNG cache bug or a starved entropy source substituted a fixed fallback. The correctness property test would likely also fail, and the test harness has a dedicated repetition detector. Recovery: patch the wrapper and rotate keys used in the window (§23 FM-10).

Threats a reader should know (§22):

  • T2: remote timing attack on rsadp and rsasp1, answered by mandatory blinding (P5, I7).
  • T4: Bleichenbacher (1998) chosen-ciphertext attack on EmePkcs1V15::decode, answered by a branchless decode and deterministic decoy (I10). T5 is the same shape for OAEP, with a single Choice (I9).
  • T6: Bleichenbacher (2006) "loose verifier" forgery against EmsaPkcs1V15::verify, answered by byte-exact verification (I11), with recovery by pulling the release (§22 T6).
  • T7: weak or shared primes from a degraded RNG, answered by explicit RNG injection and a CI lint (P13, I13, §22 T7).
  • T11: private-key material leaking through logs or core dumps, answered by no Debug or Display and zeroize-on-drop (P11, I8).

How it compares

  • OpenSSL bet on ubiquity and wins where a FIPS 140-validated module boundary already exists and must not be re-certified (§31). The table shows it with optional blinding, historically off by default on some paths, and manual OPENSSL_cleanse calls instead of typed secrets (§31).
  • BoringSSL bet on deleting every non-essential option and wins in a large, homogeneous fleet where a narrow audited API matters more than configurability (§31). It uses fixed-window constant-time exponentiation, audited, where this design uses the ladder (§31, ADR-05).
  • RustCrypto rsa bet on safe Rust and interop with the RustCrypto traits, which suits projects already standardised on them (§31). This design avoids that trait ecosystem to keep its dependency list minimal (ADR-13, §31).
  • mbedTLS bet on small footprint and embedded-first use, with decades of embedded hardening (§31). This design's no_std bignum and prime crates target the same niche without mbedTLS's decade of embedded-deployment hardening (§31, ADR-02).

Questions to test yourself

  1. Why does CRT-accelerated decryption require a mandatory re-encryption check, and what exact arithmetic relationship connects a single-bit fault in m1 to full private-key recovery? — Hint: §8.2 step 4 and §8.7; compare which prime each section names.
  2. Derive the ≈4× CRT speedup from first principles using the modular-exponentiation cost model, and reconcile it with §4's stated non-CRT penalty figure. — Hint: §32 item 6 and §29's O(k³) note.
  3. Why is blinding necessary even though the Montgomery ladder is already constant-time over the exponent — what attack does blinding close that the ladder alone does not? — Hint: ADR-07, P5, and §19.1.
  4. Why must the Manger and Bleichenbacher countermeasures produce a fixed-length, ciphertext-deterministic fake output rather than merely "an error" — what channel remains open if the fake output were randomized per call? — Hint: §18.2 steps 2-3 and MM5.
  5. Using the Back-of-Envelope Capacity Model, compute how many RSA-2048 CRT decrypt operations 8 cores can sustain, then explain why this figure — not the keygen figure — determines the server-side TLS RSA-key-exchange ceiling. — Hint: §32 items 1-3 and §4.

If you only remember three things

A private key is used through a schedule of operations, and that schedule, not just the key value, is what an attacker measures, so the ladder fixes the schedule and blinding hides the input (MM1, ADR-05, ADR-07). CRT buys a 4× speed-up by creating one recombination point, so the re-encryption check is mandatory and has no flag (MM3, I6). Padding is the security proof's hypothesis, so OAEP and PSS are architectural defaults, and every failure path must look identical from outside (MM2, MM5, ADR-10, ADR-11).

Words used here

  • Modulus (n): the product of two primes p·q; with e it forms the public key (§36).
  • Carmichael function λ(n): the exponent modulus FIPS 186-5 mandates for d, tighter than Euler's totient (§8.1, §36).
  • Montgomery multiplication: division-free modular multiplication in the transformed form aR mod n (§8.1, §36).
  • CRT (Chinese Remainder Theorem): compute mod p and mod q separately, then recombine mod n (§36).
  • Fault-injection attack: deliberately corrupting a computation to learn the key from the faulty output (§36).
  • Blinding: randomising the input of a private operation with a fresh factor r and removing it afterwards (§36, I7).
  • OAEP / PSS: the default encryption and signature padding schemes (§36, ADR-10, ADR-11).
  • MGF1: the hash-based mask generator both schemes share (§36, §8.3).
  • Padding oracle: any observable difference that reveals whether padding was valid (§36).
  • dudect: a statistical timing test based on Welch's t-test (§36).
