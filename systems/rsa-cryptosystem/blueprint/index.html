1. Goal & Scope

Build, from first principles in safe Rust, a PKCS #1 v2.2 (RFC 8017) / FIPS 186-5-conformant RSA cryptosystem: arbitrary-precision (bignum) arithmetic, Montgomery-form constant-time modular exponentiation, probable-prime key generation, the four RSA primitives (RSAEP, RSADP, RSASP1, RSAVP1), CRT-accelerated private-key operations with a mandatory fault-injection defense, EMSA-PSS / EMSA-PKCS1-v1.5 signature encoding, EME-OAEP / EME-PKCS1-v1.5 (Bleichenbacher-safe) encryption encoding, mandatory blinding, and PKCS#1/PKCS#8/JWK/PEM key export. The system is a library (no network service, no daemon): correctness and side-channel resistance are the product; every operation is a pure computation over caller-supplied keys and messages.

Phase-0 deliverable (numbered modules/crates, workspace):

  1. rsa-bignum — no_std limb-level arbitrary-precision integer arithmetic.
  2. rsa-prime — no_std probable-prime generation (Miller-Rabin, Lucas, FIPS 186-5 procedure).
  3. rsa-core — no_std + alloc key types, the four RSA primitives, PSS/OAEP/PKCS1-v1.5 encoding.
  4. rsa-keys — std-bound PKCS#1/PKCS#8/JWK/PEM serialization.
  5. rsa-cli — a thin keygen/sign/verify/encrypt/decrypt binary.
  6. conformance/ — the Wycheproof / NIST CAVP-ACVP / RFC 8017 Appendix C test-vector runner.

System boundaries. Provides: bignum arithmetic; RSA-2048/3072/4096 keygen; RSA-1024 verify-only compatibility; RSAEP/RSADP/RSASP1/RSAVP1; EMSA-PSS and EME-OAEP as the recommended defaults; EME-PKCS1-v1.5 decryption with the Bleichenbacher countermeasure (legacy interoperability only); constant-time private-key arithmetic; CRT fault-injection defense; key serialization to four formats. Delegates: transport (TLS/SSH/etc. are callers, not part of this system); hashing primitives (SHA-2/SHA-3 come from an external, audited hash crate); the system RNG (OsRng/getrandom supply entropy; this system never seeds itself implicitly, P13/I13). Does not provide: a network service, a certificate authority, a key-management server, or any transport-layer protocol.

Non-goals (every one flagged with its Deferred Features Register anchor, §35): RSA-7680 / RSA-15360 keygen PhaseDeferred("§35"); multi-prime RSA (RFC 8017 Appendix A.1.4) PhaseDeferred("§35"); HSM/PKCS#11-backed key storage PhaseDeferred("§35"); FIPS 140-3 module-boundary certification code PhaseDeferred("§35"); fully constant-time key generation (the rejection sampler itself is not hardened) PhaseDeferred("§35"); post-quantum hybrid key transport PhaseDeferred("§35"); Karatsuba/Toom-Cook sub-quadratic multiplication PhaseDeferred("§35").

Deployment model. A statically linked Rust library embedded in the caller's process (TLS stack, JWT verifier, code-signing tool, SSH agent, ACME client). No independent process, no listening socket, no persistent storage owned by the library itself; the caller owns key storage, transport, and session state.

Target users/operators. Implementers embedding RSA in a larger protocol stack (TLS, JOSE/JWT, SSH, S/MIME, ACME/PKI tooling); security engineers auditing a from-scratch RSA implementation against CAVP/Wycheproof; on-call engineers debugging a production signature or decryption failure.

What later phases unlock. Phase 0–4 (§12–§16) unlock a correct, non-side-channel-audited RSA core (keygen, encrypt, decrypt, sign, verify against the primitives only, no encoding). Phase 5–6 (§17–§18) unlock interoperable, standards-conformant signatures and encryption. Phase 7 (§19) unlocks the side-channel and fault-injection hardening that makes the library production-safe. Phase 8–9 (§20–§21) unlock key interchange with the rest of the PKI/JOSE ecosystem and a usable public surface.

Recommended language: Rust 1.78+ (edition 2021). Rationale: memory safety without a garbage collector (predictable timing, no GC-pause side channel); no_std + alloc support for embedding in constrained targets; a mature constant-time ecosystem (subtle, zeroize, dudect); zero-cost abstractions keep the bignum hot path competitive with C. Rejected: C (the OpenSSL/BoringSSL/mbedTLS incumbent — memory-unsafe by default; every historical RSA CVE class in this domain, e.g. Heartbleed-adjacent buffer over-reads, is a class Rust's borrow checker removes at compile time). Go (GC pauses are an observable timing side channel on the exact hot path — mod_exp — that this system must keep constant-time; the standard library's math/big is not constant-time by design). Python (no realistic constant-time guarantee at the interpreter level; unusable for the private-key hot path). C++ (comparable memory-safety hazards to C without Rust's compiler-enforced guarantees; unsafe in this system is banned by ADR-15 specifically because C++ cannot make the same guarantee statically).

Prerequisites. Modular arithmetic (rings, Z/nZ, Euler's totient/Carmichael function); the Chinese Remainder Theorem; the Miller-Rabin primality test and its error-probability analysis; big-O analysis of schoolbook multiplication/division; the Bleichenbacher (1998) and Manger (2001) chosen-ciphertext attacks; enough Rust to reason about ownership, Send/Sync, and unsafe-free constant-time code.

Estimated timeline. Phase 0 (repo skeleton + correctness kernel): 1 week. Full system (Phase 0–9, all ten phases, conformance-gated): 4–6 months at a sustainable pace, or 4–6 weeks for a Phase-0-only drop that ships RSA-2048 keygen/sign/verify (PSS) plus the conformance harness.

2. Why Build This

RSA is the public-key algorithm the industry has spent a decade "deprecating" and still ships in every TLS certificate chain, every SSH host key that predates Ed25519 defaults, every code-signing PKI, every JWT signed RS256/PS256, every SAML assertion, every S/MIME message, every ACME-issued certificate not yet rotated to ECDSA. It is the one public-key algorithm an enterprise auditor recognizes without explanation, and the one every post-quantum migration is benchmarked against. Building it from bignum primitives up teaches modular arithmetic at production scale, the exact arithmetic mechanics of the Chinese Remainder Theorem, the gap between "textbook" and "IND-CCA2-secure" cryptography, and the discipline of constant-time implementation — skills that transfer directly to elliptic-curve, lattice, and pairing-based systems (Ed25519/EdDSA share the constant-time-scalar-multiplication lesson; ML-KEM shares the side-channel-hardened-encoding lesson; any HSM/PKCS#11 integration shares the CRT-fault lesson).

The reference implementations that ship the most RSA bytes in the world are C (OpenSSL, BoringSSL, mbedTLS, NSS) or C-adjacent (GMP). The few written in safe Rust (RustCrypto rsa, ring's internal RSA module) are the rare places the Bleichenbacher countermeasure, the Manger countermeasure, the constant-time bignum primitives, and the CRT fault-injection defense are legible at the source level without wading through decades of C preprocessor macros. Engineers who have configured RSA (rsa.generate_private_key(2048)) are common; engineers who have derived mod_exp from Montgomery's 1985 paper, validated it against NIST CAVP, and threaded fault-injection defenses through CRT-decrypt are rare. This project closes that gap: by Phase 9 (§21) the builder owns every arithmetic step between "32 raw bytes of entropy" and "a verified RS256 JWT signature," and can explain, line by line, why RSA-2048 is "good enough" today, why NIST's SP 800-131A floor rises to RSA-3072 in 2031, why CRT-decrypt is faster but more dangerous than non-CRT decrypt, and which exact function executes when a TLS 1.2 RSA-key- exchange handshake decrypts a premaster secret.

What Mastery Looks Like — after building this system, the engineer can:

  • Derive and implement Montgomery multiplication from the recurrence, not from a library call, and explain why it turns an O(n²) division into an O(n²) multiplication-only reduction (Phase 2, §14).
  • Generate a NIST-CAVP-conformant RSA keypair and explain every FIPS 186-5 rejection rule by the attack it closes, not by rote (Phase 3, §15).
  • Implement CRT-accelerated decryption with a fault-injection defense and explain the exact arithmetic fault that Boneh-DeMillo-Lipton (1997) exploits without it (Phase 4, §16).
  • Distinguish "textbook RSA" from an IND-CCA2-secure scheme by naming the exact padding-scheme property (PSS's salt / OAEP's double-masking) that the security proof depends on (Phase 5–6, §17–§18).
  • Reproduce the Bleichenbacher (1998) and Manger (2001) chosen-ciphertext attacks against a deliberately naive decoder, then close both with a branchless, timing-invariant decoder (Phase 6, §18).
  • Explain why blinding is necessary even when the exponentiation ladder is already constant-time, and reproduce the Brumley-Boneh (2003) timing attack this closes (Phase 7, §19).
  • Interoperate a from-scratch keypair with OpenSSL/BoringSSL across all four serialization formats (PKCS#1, PKCS#8, JWK, PEM) (Phase 8, §20).
  • Read the Comparative Architecture Table (§31) and redesign the system with a fundamentally different trust boundary (HSM-backed, ECC-first, or PQ-hybrid) knowing exactly what is traded (§34).

The scope is deliberately tight so it is finishable: no RSA-1024 keygen (verify-only, compatibility), no non-standard padding, no RSASSA-PKCS1-v1_5 signing for new code (verify-only), no FIPS 140-3 boundary code. RSA-2048/3072/4096 first; everything larger or structurally different is PhaseDeferred (§35). That focus is why the timeline is months, not years.

Three properties of this architecture hold throughout. First, the bignum layer is the foundation: a wrong limb-level add propagates to a wrong signature at every layer above it, so Phase 1 (§13) is differentially tested against num-bigint before anything else is built. Second, the private-key hot path (mod_exp_ct) is constant-time by construction — secret- dependent branches are eliminated at the algorithm choice (the Montgomery ladder), not patched in afterward. Third, CRT-based decryption is the only place in the stack that can leak the private key under a single-bit fault; the algorithm-level defense (re-encrypt and compare before returning) is architecturally mandatory and has no configuration flag to disable it (I6).

6. Design Principles

P1 — PKCS #1 v2.2 (RFC 8017) is the spec. Rule: anything not defined in v2.2 is not implemented. Tradeoff: no room for "improved" home-grown padding. Operational implication: every encoding decision cites an RFC 8017 section. Violated: interoperability silently breaks against any conformant peer.

P2 — RSA-PSS is the signing default. Rule: sign() without an explicit scheme argument produces PSS; PKCS1-v1.5 signing is exposed only behind a feature flag with a compile-time deprecation notice. Tradeoff: legacy interop requires an explicit opt-in. Operational implication: new integrations get the provably-secure scheme by default. Violated: silent regression to the scheme Bleichenbacher (2006) shows lazy verifiers accept forged instances of.

P3 — RSA-OAEP is the encryption default. Rule: PKCS1-v1.5 decryption is exposed only with the Bleichenbacher countermeasure permanently compiled in; PKCS1-v1.5 encryption is not exposed at all (there is no legitimate reason to produce new v1.5 ciphertexts). Tradeoff: callers decrypting legacy ciphertexts pay the (small) constant-output-shape cost. Operational implication: the padding-oracle surface is closed by construction, not by caller discipline. Violated: reintroduces the exact oracle Bleichenbacher (1998) exploited.

P4 — CRT decryption with fault-injection countermeasure is mandatory, unconditionally. Rule: every CRT-based private-key operation re-encrypts its own result and compares before returning; there is no configuration flag to skip this. Tradeoff: costs one public-exponent exponentiation (~0.1 ms at 2048-bit, §4) per private op. Operational implication: a hardware fault (voltage glitch, cosmic ray, deliberate glitching) produces a hard error, never a faulty-but-returned signature. Violated: reopens Boneh-DeMillo-Lipton (1997) — a single faulty signature reveals the private key via gcd.

P5 — Blinding is mandatory for every sign and decrypt call. Rule: the private exponentiation is computed on a randomized input (c·r^e mod n) and unblinded after; a fresh r is drawn per call, never cached or reused. Tradeoff: one extra modular exponentiation and one modular inverse per call. Operational implication: closes the timing side channel even across network round-trips. Violated: reopens Brumley & Boneh (2003) — remote timing attacks recover the key over a LAN in hours.

P6 — Every secret-dependent exponentiation runs the constant-time Montgomery ladder; window-NAF is exposed only for public exponents. Rule: mod_exp_ct and mod_exp_pub are distinct entry points; the type system (a SecretExponent vs PublicExponent newtype) makes calling the fast path with a secret a compile error. Tradeoff: private ops are ~4-10× slower than the fastest windowed method. Operational implication: no code review can "accidentally" introduce a timing leak by picking the wrong function; the wrong function does not typecheck. Violated: reopens Kocher (1996).

P7 — Miller-Rabin iteration count follows FIPS 186-5 Table A.1, never an ad hoc constant. Rule: the iteration count is computed from the requested modulus bit-length and target error probability (2^-100 minimum), per Damgård-Landrock-Pomerance (1993) bounds. Tradeoff: larger keys cost more Miller-Rabin rounds, slowing keygen. Operational implication: the error probability of a "prime" being composite is a documented, derived number, not folklore. Violated: an under-iterated test admits the Albrecht et al. (2018) adversarial pseudoprime class.

P8 — Both probable-prime and safe-prime generation are supported, selected by caller config. Rule: safe primes (p = 2p'+1, p' also prime) are offered for compliance regimes that mandate them even though this design's threat model shows no attack they close beyond probable-prime generation with FIPS 186-5's rejection rules. Tradeoff: safe-prime search is materially slower (rarer primes). Operational implication: a defense-in-depth / audit-checkbox option exists without being the default. Violated: N/A — this is an additive option, not a closed attack surface.

P9 — The public exponent is fixed to F4 = 65537 for key generation; other values are accepted only when verifying legacy keys. Rule: keygen() takes no e parameter. Tradeoff: callers requiring e=3 interop (deprecated) must fall back to a verify-only path. Operational implication: eliminates an entire attack-parameter dimension. Violated: small e reopens Coppersmith (1997)-class low-exponent attacks; oversized e buys nothing and slows every public op.

P10 — No unsafe anywhere in rsa-bignum or rsa-core. Rule: performance is recovered via #[inline(always)] and compiler auto-vectorization, never manual pointer arithmetic. Tradeoff: some hand-tuned-assembly speedups (as in GMP) are unavailable. Operational implication: the memory-safety guarantee that motivated Rust (ADR-01) is not silently opted out of in the one crate that handles secrets. Violated: reintroduces the exact bug class (buffer over-read, use-after-free) Rust was chosen to eliminate.

P11 — Secrets are typed and zeroized; RsaPrivateKey never implements Debug/Display. Rule: private-key-bearing types wrap zeroize::Zeroizing or derive ZeroizeOnDrop; the Debug/Display traits are never derived or implemented for them. Tradeoff: developer convenience ({:?} in a debugger) is sacrificed. Operational implication: a private key cannot leak into a log line by accident. Violated: a stray println!("{:?}", key) becomes a key- exfiltration incident.

P12 — Conformance is the contract: Wycheproof + NIST CAVP/ACVP + RFC 8017 Appendix C gate every release. Rule: CI fails the build if any corpus regresses. Tradeoff: the conformance corpus must be vendored and kept current. Operational implication: "it compiles" is never sufficient evidence of correctness. Violated: ships a cryptographic regression indistinguishable from a passing build.

P13 — Randomness is always caller-injected; no implicit OsRng. Rule: every function consuming entropy (keygen, sign, decrypt, OAEP encode) takes &mut impl RngCore explicitly. Tradeoff: callers must wire an RNG through every call site. Operational implication: tests are reproducible with a seeded RNG; production code is free to choose its own entropy-hardening (HMAC-DRBG over OsRng). Violated: reopens Heninger et al. (2012)'s shared-prime-from-weak-RNG disaster class, and makes tests non-reproducible.

P14 — Every public entrypoint returns a typed Result, never panics on adversarial input. Rule: malformed ciphertexts, signatures, or key material produce a documented RsaError variant; unwrap()/panic!() on caller-controlled data is a defect. Tradeoff: every call site handles an error path even for "should never happen" cases. Operational implication: a malformed message from an attacker is a Result::Err, not a denial-of-service crash. Violated: turns malformed input into a crash-based DoS, and (per P3/P4) a differential-timing error path can become an oracle if the error variant leaks distinguishing information.

8. Domain Model

8.1 Modular arithmetic — the ring Z/nZ

RSA operates over the multiplicative group of integers modulo n = p·q. Key equations, used throughout §14–§16:

  • Euler's totient: φ(n) = (p−1)(q−1).
  • Carmichael function (the tighter, FIPS-186-5-mandated choice): λ(n) = lcm(p−1, q−1).
  • Public/private exponent relation: e·d ≡ 1 (mod λ(n)).
  • Encryption/decryption: c = m^e mod n; m = c^d mod n (textbook form — never used directly; always through EME-OAEP/EME-PKCS1-v1.5, §18).
  • Montgomery form: for odd modulus n and R = 2^(64·limb_count), represent a as ā = a·R mod n; Montgomery multiplication computes MontMul(ā, b̄) = a·b·R mod n in O(limb_count²) word operations with no division (§14.2).

8.2 CRT decryption — equations and state

Given private key (p, q, dP, dQ, qInv) where dP = d mod (p−1), dQ = d mod (q−1), qInv = q^{-1} mod p, and ciphertext c:

Step Computation State produced
1 m1 = c^dP mod p partial result mod p
2 m2 = c^dQ mod q partial result mod q
3 h = qInv · (m1 − m2) mod p CRT correction term
4 m = m2 + h·q recombined result mod n
5 (I6) c' = m^e mod n; require c' = c fault-injection check

Steps 1–2 are each ~4× cheaper than a full-width exponentiation mod n (half the bit-length, cubed cost — derived in §32 #6), which is the entire performance motivation for CRT and, simultaneously, the entire fault-injection attack surface Boneh-DeMillo-Lipton (1997) exploited: corrupt only m1, and step 4 recombines a consistent-looking but wrong m, whose difference from the correct value shares a large factor with p — gcd(m_faulty^e − c, n) recovers p directly. Step 5 closes this by construction (I6).

8.3 Padding schemas

EME-OAEP encoding (RFC 8017 Section 7.1.1; k = modulus byte length, hLen = hash output length):

DB        = lHash || PS || 0x01 || M                (PS = zero bytes, pads to k-hLen-1)
seed      = random(hLen)
maskedDB  = DB XOR MGF1(seed, k-hLen-1)
maskedSeed= seed XOR MGF1(maskedDB, hLen)
EM        = 0x00 || maskedSeed || maskedDB

EMSA-PSS encoding (RFC 8017 Section 9.1.1; emLen = encoded message byte length):

mHash  = Hash(M)
M'     = 0x00 x8 || mHash || salt
H      = Hash(M')
DB     = PS || 0x01 || salt                          (PS = zero bytes)
maskedDB = DB XOR MGF1(H, emLen-hLen-1)
EM     = maskedDB || H || 0xbc

Both schemas share MGF1 (a hash-based mask generation function, RFC 8017 Appendix B.2.1) as their building block; both are "masking," not "encryption" — the security proof (Bellare-Rogaway 1996 for PSS; the OAEP IND-CCA2 reduction cited in Katz & Lindell for OAEP) depends on the exact byte layout above, which is why P1/P2/P3 forbid deviation.

8.4 Sequence — sign then verify (round trip)

Step Operation Data state
1 caller computes mHash = Hash(message) 32-byte digest (SHA-256 example)
2 EMSA-PSS-Encode(mHash, salt) → EM emLen-byte encoded message
3 OS2IP(EM) → integer m big integer < n
4 RSASP1(private_key, m) → s (CRT + blinding, §16/§19) big integer < n
5 I2OSP(s) → signature bytes k-byte signature
6 (verify) OS2IP(signature) → s big integer
7 RSAVP1(public_key, s) → m' big integer
8 I2OSP(m') → EM' emLen-byte candidate
9 EMSA-PSS-Verify(EM', mHash) → accept/reject boolean (I11: byte-exact)

8.5 Worked example (illustrative parameters only — production keys are ≥2048-bit per P9/ADR-12)

Classic small-parameter walkthrough (the standard pedagogical values): p = 61, q = 53, n = p·q = 3233, φ(n) = 60·52 = 3120, e = 17 (gcd(17, 3120) = 1), d = 17^{-1} mod 3120 = 2753. Encrypting m = 65: c = 65^17 mod 3233 = 2790. Decrypting: m = 2790^2753 mod 3233 = 65. This demonstrates the textbook primitive only (§8.1); production encryption always wraps m/c in EME-OAEP (§8.3) first.

8.6 Malformed-input example

An EME-OAEP ciphertext arrives with a corrupted label hash (lHash mismatch after unmasking). A naive decoder distinguishes "label hash mismatch" from "padding boundary 0x01 not found" via a different error return or a different number of comparisons — this is exactly the distinguishing oracle Manger (2001) exploits. The correct decoder (§18.2, I9) combines both checks into one constant-time Choice and returns a single, ciphertext-derived decoy value on either failure — the caller cannot distinguish "wrong label" from "wrong padding" from "corrupted ciphertext" by return value, error type, or timing.

8.7 Failure-path example

A single-bit fault flips one bit of m1 (§8.2 step 1) during signing — e.g., a voltage- glitching attacker targets the mod p exponentiation. Step 4 recombines a m_faulty that is wrong only in its residue mod p, consistent mod q. Without I6, the signer returns s_faulty; the attacker computes gcd(s_faulty^e − message, n), which shares the factor q, recovering the full factorization in one multiplication and one gcd. With I6 (§16 step 5), the signer's own re-encryption check (s_faulty^e mod n ≠ original message representative) fails before the value ever leaves the function, and the call returns Err(FaultInjection) — the attacker observes only a failed operation, no distinguishing arithmetic.

13. Phase 1 — Bignum Primitives

13.1 Objectives

Implement BigUint (§11) and the limb-level arithmetic (add, subtract, multiply, divide, compare, GCD, modular inverse) that every later layer depends on (P10: zero unsafe). This is the foundation the architecture diagram (§3) names first: a wrong carry here propagates to a wrong signature at every layer above.

13.2 Detailed Implementation Steps

  1. Implement limb.rs: u64 add-with-carry and multiply-with-carry as named primitives (not transcribed here per the no-code rule, §4 of the standard) — the algorithmic shape is schoolbook carry-propagation, O(1) per limb pair.
  2. Implement biguint.rs: BigUint as a little-endian Vec<u64> (§11); construction from/to big-endian bytes (I2OSP/OS2IP's underlying representation, used again in §18).
  3. Implement mul.rs: schoolbook multiplication, O(k²) in limb count k — Karatsuba is explicitly PhaseDeferred("§35"), per Knuth Vol. 2 Ch. 4.3.3's crossover analysis (not worth it below ~40 limbs, i.e. below ~2560-bit operands).
  4. Implement div.rs: schoolbook long division producing (quotient, remainder); used only for non-hot-path conversions (Montgomery reduction, §14, avoids division entirely).
  5. Implement gcd.rs: extended-Euclidean algorithm for GCD and modular inverse (mod_inverse, §11) — applied at keygen (I2, computing d) and CRT setup (q_inv, §16).
  6. Implement ct.rs: ct_select/ct_eq/ct_lt constant-time primitives (P6) — the building blocks Phase 2's ladder (§14) composes into mod_exp_ct.

13.3 Deliverable

A rsa-bignum crate whose arithmetic differentially matches num-bigint bit-for-bit, with property tests and a documented big-O cost model per operation.

13.4 Acceptance Criteria

  • 100,000 random (a, b) pairs satisfy (a + b) - b == a (property test, ADR-17).
  • 100,000 random (a, b, m) triples satisfy BigUint mul/div agree with num-bigint bit-for- bit (differential test, reference impl §5 GMP/num-bigint).
  • ct_select/ct_eq/ct_lt pass a dudect smoke run: |t| ≤ 4.5 over 10^5 samples (a cheap precursor to the full 10^7-sample gate at Phase 2, §14.4).
  • Zero unsafe blocks in rsa-bignum (P10, ADR-15), verified by cargo geiger in CI.

13.5 Conformance Fixtures

Fixture Purpose Expected Output

bignum_cross_numbigint.json differential mul/div vs num-bigint bit-identical

13.6 Pitfalls

  • Limb-wise carry propagation is the single largest bignum bug source (Knuth Vol. 2 Section 4.3.1 warns explicitly); cross-validate against num-bigint from the first commit, not at the end.
  • The "quotient == 0" branch in division is data-dependent on the divisor, which for RSA usage is always the (public) modulus — document explicitly that this branch is not a secret- dependent leak (contrast with I5, which governs the exponent, not the modulus).
  • ct_select implemented as if choice { a } else { b } compiles but is not constant-time — the compiler is free to branch; the correct form uses bitmask arithmetic (P6's rationale extends here even though the ladder itself is Phase 2).

13.7 Performance Concerns

Schoolbook multiplication is O(k²); for a 2048-bit modulus (k=32 limbs) this is ~1,024 word multiplications per full multiply — fast enough that Karatsuba's crossover (Knuth, §5) isn't reached until ~40 limbs, justifying ADR's implicit choice to defer it (§35). Division is used only off the hot path (never inside mod_exp_ct).

13.8 Edge Cases

  • Zero-length BigUint (value 0) must round-trip through from_be_bytes/to_be_bytes.
  • Maximum-length operands (4096-bit, 64 limbs) must not overflow Vec<u64> capacity arithmetic.
  • Divisor larger than dividend must return (0, dividend), never panic.
  • Subtraction producing a negative result on unsigned BigUint must be rejected by the type (no wraparound) — checked at the call site, not inside BigUint itself.

13.9 Failure Analysis

A carry-propagation bug manifests as a wrong BigUint value that is usually still internally consistent (both operands are limbs, so the type never panics) — meaning bugs here are silent until they produce a wrong signature or a failed conformance vector. Detection: the differential fixture (§13.5) against num-bigint on every CI run. Containment: no crate above rsa-bignum is exercised in CI until bignum_cross_numbigint.json passes. Recovery: bisect via the property-test seed that failed; quickcheck/proptest shrinking (ADR-17) narrows the failing input automatically.

13.10 Operational Notes

rsa-bignum emits no logs, metrics, or traces (ADR-25/ADR-29 — it is no_std, has no IO). Its only observability surface is its test/benchmark suite (rsa-bench/benches/mod_exp.rs depends on it starting Phase 2). No migration/compatibility concerns — BigUint's byte representation (to_be_bytes) is fixed from this phase forward and consumed unchanged by I2OSP/OS2IP in Phase 6 (§18).

14. Phase 2 — Montgomery Arithmetic & Constant-Time Exponentiation

14.1 Objectives

Implement Montgomery multiplication (ADR-04) and the constant-time Montgomery-ladder exponentiation (mod_exp_ct, ADR-05, P6, I5) that closes Kocher (1996). Implement the faster windowed public-exponent path (mod_exp_pub) for verify/encrypt. This phase's output is the single most security-critical function in the system.

14.2 Detailed Implementation Steps

  1. Implement MontgomeryParams::for_modulus (§11): compute n_inv_neg_mod_64 via Newton's- iteration-style bit-lifting (Menezes-van Oorschot-Vanstone Ch. 14, §5 Books) and r2_mod_n by repeated doubling/reduction.
  2. Implement mont_mul: the CIOS (coarsely integrated operand scanning) variant of Montgomery multiplication — O(k²) word operations, zero divisions (ADR-04's whole rationale).
  3. Implement mod_exp_ct as a fixed-iteration Montgomery ladder (P6, I5): for each bit of the secret exponent, perform one constant-time conditional swap (ct_select, §13) followed by one multiply and one square, regardless of the bit's value — the access pattern and instruction count are data-independent by construction (Kocher 1996 is closed here, not patched afterward).
  4. Implement mod_exp_pub using windowed sliding-NAF (safe only because the exponent — e or a signature under verification — is public, P6/ADR-05): ~4× faster than the ladder for e=65537.
  5. Wire the dudect timing harness (timing/runner) against mod_exp_ct with two exponent distributions (uniform-random vs. all-ones bit pattern) per Kocher (1996)'s attack model.
  6. Cross-validate mod_exp_ct and mod_exp_pub against num-bigint::ModPow for 100,000 random (base, exp, modulus) triples (ADR-17).

14.3 Deliverable

rsa-bignum::modular exposes mod_exp_ct/mod_exp_pub, both differentially correct against num-bigint, with mod_exp_ct passing the dudect constant-time gate (I5) in CI (timing.yml, ADR-18).

14.4 Acceptance Criteria

  • mod_exp_ct/mod_exp_pub agree with num-bigint::ModPow for 100,000 random triples, bit-for-bit.
  • dudect t-statistic ≤ 4.5 over 10^7 measurements (M10, §28) for mod_exp_ct, across both the uniform-random and all-ones exponent distributions.
  • mod_exp_pub is ≥ 3× faster than mod_exp_ct for a 17-bit exponent (e=65537) at 2048-bit modulus size (M9 vs. M8, §28).
  • MontgomeryParams::for_modulus rejects even moduli with Err (Montgomery requires odd n; RSA moduli are always odd, but the API must not silently misbehave on misuse).

14.5 Conformance Fixtures

Fixture Purpose Expected Output

14.6 Pitfalls

  • The ladder's conditional swap must be ct_select-based; a let tmp = r0; r0 = r1; r1 = tmp guarded by if bit reads the secret bit in the branch predictor — this is precisely the class MM1 (§30) names ("the schedule of operations is the secret, not just the value"). Cross-reference I5.
  • n_inv_neg_mod_64 requires n odd; a silent wraparound on even n produces wrong results without erroring — must be an explicit Err, not UB (P14).
  • Converting into Montgomery form (aR mod n) requires the input already be < n — a caller passing an out-of-range value produces silently wrong results unless I14's range check runs first (enforced at the primitive layer, §16, not here).

14.7 Performance Concerns

Montgomery reduction turns an O(k²) division into an O(k²) multiply-accumulate with no branches proportional to the modulus's bit pattern — the entire performance argument for ADR-04. mod_exp_ct's fixed-iteration-count cost (§4: ≤5 ms at 2048-bit) is strictly worse than mod_exp_pub's windowed cost (≤0.1 ms) by design (P6) — the two functions trade throughput for side-channel safety in opposite directions and must never be swapped by call site (enforced by the SecretExponent/PublicExponent newtype split, §11).

14.8 Edge Cases

  • Exponent = 0: mod_exp_ct(base, 0, n) must return 1 (mod n) without a divide-by-zero-shaped special case that would branch on the exponent's value.
  • Base ≡ 0 (mod n): must return 0 without an early-exit branch (early exit is itself a timing leak on the base, though the base is typically not secret in this system's call sites — still guarded for defense-in-depth).
  • Exponent with leading zero bits at the configured bit-length: the ladder's fixed iteration count must be over the maximum configured bit-length, not the exponent's actual bit-length, or the loop count itself becomes a timing leak.

14.9 Failure Analysis

A non-constant-time regression in mod_exp_ct (e.g., a "helpful" fast-path added later) is the single highest-severity defect this system can ship (§22 T1). Detection: timing.yml's dudect gate (I5) on every PR touching rsa-bignum::modular. Blast radius: every private-key operation in every downstream caller. Containment: the gate blocks merge; there is no runtime mitigation once a non-constant-time binary ships (this is a build-time invariant, not a recoverable runtime state, §7 I5's Recovery column: "no runtime recovery"). Forensic signal in the field: an abnormal, key-value-correlated latency distribution on production RSA sign/decrypt calls.

14.10 Operational Notes

timing/results/ archives every dudect run's t-statistic time series (M10, §28) so a slow drift (not just a hard threshold breach) is visible before it crosses 4.5. No user-facing telemetry (ADR-29 — this is a library); the CI artifact is the only "dashboard." No compatibility concerns: mod_exp_ct/mod_exp_pub signatures are internal to rsa-bignum and not part of the public API surface (Phase 9, §21, wraps them).

15. Phase 3 — Prime Generation & Key Generation

15.1 Objectives

Implement probable-prime generation (Miller-Rabin + optional Lucas, P7/P8) and the full FIPS 186-5 Appendix A.1.1.2 keygen procedure, producing RsaPrivateKey/RsaPublicKey (§11) that satisfy invariants I1–I4 and I12–I13.

15.2 Detailed Implementation Steps

  1. Implement trial_division.rs: sieve against primes up to 65,521, eliminating ~87% of composite candidates in microseconds before any Miller-Rabin round runs (§32 #7's density assumption).
  2. Implement miller_rabin.rs: the strong probable-prime test, iteration count computed from FIPS 186-5 Table A.1 (P7, ADR-09) — 27 rounds for 2048 ≤ |n| ≤ 3071, 41 rounds for |n| ≥ 3072 — per Damgård-Landrock-Pomerance (1993)'s error bound, never a hand-picked constant.
  3. Implement lucas.rs as an optional extra confidence pass (P8), guarding specifically against the adversarial pseudoprime class described in Albrecht, Massimo, Paterson, Somorovsky (2018).
  4. Implement generate.rs's FIPS 186-5 Appendix A.1.1.2 procedure: generate candidate p, q of nlen/2 bits each; reject |p−q| < 2^(nlen/2−100) (I4, defeats Fermat factoring); reject p ≡ 1 (mod e) or q ≡ 1 (mod e) (I2); compute n = p·q, λ(n) = lcm(p−1, q−1), d = e^{-1} mod λ(n) (§8.1); reject d ≤ 2^(nlen/2) (I3, defeats Wiener's attack, Coppersmith 1997's broader lattice-attack family).
  5. Compute CRT parameters dP = d mod (p−1), dQ = d mod (q−1), qInv = q^{-1} mod p (§8.2) via rsa-bignum::gcd::mod_inverse.
  6. Wire keygen's RNG parameter as &mut impl RngCore (P13, I13) — no code path in rsa-prime or rsa-core::key::generate may construct its own OsRng.

15.3 Deliverable

rsa_core::key::generate(bits, rng) -> Result<RsaPrivateKey, RsaError> producing NIST-CAVP- conformant keys at 2048/3072/4096 bits (ADR-12), with every FIPS 186-5 rejection rule enforced and unit-tested individually.

15.4 Acceptance Criteria

  • keygen(2048, rng) produces n with bit-length 2048 ± 1 in ≥ 99.9% of a 1,000-trial sample (a keygen that violates this is silently generating undersized keys).
  • Generated keys pass NIST CAVP KGV.rsp (Key Generation Validation) vectors.
  • The Albrecht et al. (2018) adversarial pseudoprime corpus (prime.adversarial.json) is rejected at the FIPS-186-5-mandated iteration count (27 rounds at 2048-bit) — zero false accepts across the corpus.
  • keygen(2048) median wall-clock ≤ 1.0 s, single core (§4, M1, §28).

15.5 Conformance Fixtures

Fixture Purpose Expected Output

prime_adversarial_albrecht2018.json adversarial pseudoprime corpus 100% rejected at 27 rounds
keygen_close_prime_reject.json forced |p-q| below threshold Err, resample (I4)
keygen_small_d_reject.json forced small d Err, resample (I3)

15.6 Pitfalls

  • Skipping the |p−q| rejection (FIPS 186-5 Appendix A.1.1.2 step 4.2) silently produces Fermat- factorable keys — MM6 (§30) names keygen as "a rejection sampler, not a formula"; skipping any rejection narrows the security margin invisibly.
  • Skipping the small-d rejection reopens Wiener's continued-fraction attack, part of the Coppersmith (1997)/Boneh (1999) attack family (§5 Papers #8, #9).
  • Using adversarially-structured random bases in Miller-Rabin (rather than uniformly random) is the exact gap Albrecht et al. (2018) exploit — bases must come from the same injected RngCore as everything else (I13), never a fixed sequence.
  • A keygen that internally calls OsRng::default() cannot be seeded for reproducible tests and reopens Heninger et al. (2012)'s shared-prime class if the OS entropy pool is degraded (I13).

15.7 Performance Concerns

Trial division removes the majority of composite candidates before the expensive Miller-Rabin step runs (§32 #7 derives ~101 Miller-Rabin-gated candidates per 1024-bit factor from the Prime Number Theorem's density estimate) — this ordering is the entire reason keygen meets the ≤1.0 s budget (§4, M1) rather than costing an order of magnitude more.

15.8 Edge Cases

  • Candidate p or q exactly at a bit-length boundary (all leading bits after the forced top-bit set) must still pass the bit-length acceptance check.
  • gcd(e, p−1) ≠ 1 (I2 violation) must trigger resampling of that prime alone, not the whole keypair, for efficiency — but the resample must draw fresh randomness, not retry the same candidate.
  • A caller-configured retry ceiling (KeyGenerationExhausted, §11) must trip if an adversarial or degenerate RNG never produces an acceptable candidate — this closes an otherwise-infinite loop from becoming a hang (P14).

15.9 Failure Analysis

A keygen that produces a factorable key (via a missed I4 or I3 rejection) is a silent catastrophic failure — the key looks structurally valid and passes format checks, but is weak. Detection: CAVP KGV.rsp conformance (§15.5) plus a dedicated property test asserting every invariant I1–I4 holds on every generated key, not just a sample. Blast radius: every signature/decryption ever performed with the weak key. Containment: none at runtime (this is a generation-time defect); the fix is exclusively in generate.rs's rejection logic. Recovery: rotate every key generated by the defective build (an operational, not algorithmic, recovery — documented in docs/runbooks/).

15.10 Operational Notes

Keygen emits a structured keygen.mr_iterations/keygen.*_reject_total counter set (§7's Telemetry column) without ever logging p, q, or d (ADR-25). Deployment note: keygen wall- clock is a caller-visible latency (interactive CLI use, §21); document the ≤1.0/4.0/12.0 s budgets (§4) so operators are not surprised by RSA-4096 keygen taking over ten seconds.

16. Phase 4 — RSA Primitives & CRT-Accelerated Private Ops

16.1 Objectives

Implement the four RFC 8017 primitives (RSAEP, RSADP, RSASP1, RSAVP1) with CRT acceleration (§8.2) and the mandatory fault-injection defense (I6, P4, ADR-06) that closes Boneh-DeMillo- Lipton (1997). This is the phase where the architecture diagram's (§3) "primitive layer" becomes real.

16.2 Detailed Implementation Steps

  1. Implement rsaep: c = mod_exp_pub(m, e, n) after checking m < n (I14); the public encryption/verification-adjacent primitive.
  2. Implement rsavp1: identical shape to rsaep, applied to a signature under verification.
  3. Implement rsadp following the §8.2 CRT state table exactly: m1 = mod_exp_ct(c, dP, p), m2 = mod_exp_ct(c, dQ, q), h = qInv·(m1−m2) mod p, m = m2 + h·q — every exponentiation here is over a secret exponent, so both calls go through mod_exp_ct (P6), never mod_exp_pub.
  4. Implement the mandatory re-encryption fault check (I6, ADR-06) as the unconditional final step of rsadp/rsasp1: c' = mod_exp_pub(m, e, n); if c' ≠ c (or, for signing, if re-verifying the signature fails), return Err(RsaError::FaultInjection) and discard m entirely — never return a value that failed its own check.
  5. Implement rsasp1 with the same CRT shape as rsadp, applied to the (already-encoded, §17) message representative.
  6. Enforce I14 (range check < n) as the first step of all four primitives, uniformly.

16.3 Deliverable

rsa_core::primitives exposing rsaep/rsadp/rsasp1/rsavp1, matching RFC 8017 Appendix C worked examples bit-for-bit, with the fault-injection check unconditionally active (no feature flag disables it, per P4).

16.4 Acceptance Criteria

  • All four primitives reproduce RFC 8017 Appendix C's example vectors exactly.
  • rsadp(rsaep(m)) == m for 1,000 random (key, m) pairs, property-tested (ADR-17).
  • A single-bit fault injected into m1 (simulated in the test harness) triggers Err(FaultInjection) in 100% of 1,000 trials — zero silent faulty outputs (I6).
  • rsadp/rsasp1 wall-clock ≤ 5.0 ms at 2048-bit (M3/M5, §28), confirming the CRT speedup derived in §32 #6 is realized, not just theoretical.

16.5 Conformance Fixtures

Fixture Purpose Expected Output

primitive_roundtrip_1k.json rsadp(rsaep(m))==m, 1K random pairs 100% identity

16.6 Pitfalls

  • The CRT recombination has a subtle off-by-one when m1 < m2: the correct form is (m1 + p − m2) mod p, not (m1 − m2) mod p, which can underflow on unsigned BigUint — this exact bug class is why §8.2's state table is written out explicitly.
  • The fault-injection check (step 4) must run before unblinding (Phase 7, §19) — checking after unblinding leaks the unblinded value on a fault, defeating the point of the check.
  • Reusing CRT intermediate values (m1, m2) across calls (e.g., an ill-considered cache) would reintroduce exactly the "no fresh randomness" class of bug that P5/§19 close for blinding — CRT intermediates are always recomputed per call.

16.7 Performance Concerns

The CRT path costs two half-width exponentiations plus a recombination and one full-width public exponentiation (the fault check) — §32 #6 derives this as ≈0.25× the cost of a single full-width private exponentiation, i.e. the ~4× CRT speedup (§4) minus the fault-check overhead (itself cheap: ≤0.1 ms at 2048-bit per M9, §28). Non-CRT decryption (the sole fallback path, retained only for keys missing CRT parameters on import, §20) costs the full 4× penalty (§4).

16.8 Edge Cases

  • Ciphertext exactly equal to n−1: must not overflow the range check (I14) or the CRT recombination's modular arithmetic.
  • A key imported without CRT parameters (legacy PKCS#1 encodings sometimes omit them, §20) must fall back to non-CRT mod_exp_ct(c, d, n) — slower (§4's 4× penalty) but still I5/I6-safe (the fault check still runs, just against a single exponentiation).
  • Re-encryption check failing due to a genuine hardware fault vs. a corrupted key object must be indistinguishable to the caller (both return FaultInjection) — distinguishing them would itself be an oracle.

16.9 Failure Analysis

A missed fault-injection check (I6 violation) is the single highest-severity defect below only a non-constant-time mod_exp_ct (§14.9) — Boneh-DeMillo-Lipton (1997) recovers the full private key from one faulty signature via gcd(s_faulty^e − m, n). Detection: the mandatory unit test crt_fault_injection_1bit.json (§16.5) plus code review enforcing "no #[cfg(feature = "skip_fault_check")] ever exists" (P4 — there is no flag to audit for). Blast radius: full private-key compromise, silently, the moment a single faulty signature is observed by an attacker. Containment: the check is unconditional in source; there is no runtime toggle to disable by mistake. Recovery: if a build is ever found missing the check, every key ever used with it must be treated as compromised and rotated.

16.10 Operational Notes

rsadp/rsasp1 emit crt.fault_check_fail_total (§7 I6 Telemetry) on every trip — a nonzero rate in production is an active-attack or hardware-fault signal, escalated per docs/runbooks/triage.md. No secret material appears in any emitted counter or log line (ADR-25). Compatibility: the CRT-vs-non-CRT fallback (§16.8) is transparent to callers — the public API (§21) does not expose which path executed.

17. Phase 5 — Signature Encoding (PSS & PKCS1-v1.5)

17.1 Objectives

Implement EmsaPss (default, ADR-10, P2) and EmsaPkcs1V15 (verify-only by default) per §8.3's schema and RFC 8017 Section 9, replacing Phase 0's placeholder smoke test (§12.2 step 4) with the real SignatureEncoding implementors (§11).

17.2 Detailed Implementation Steps

  1. Implement MGF1 (RFC 8017 Appendix B.2.1) as the shared mask-generation primitive both PSS and OAEP (§18) depend on.
  2. Implement EmsaPss::encode exactly per §8.3's schema: mHash = Hash(M), M' = 0x00×8 || mHash || salt, H = Hash(M'), masked DB, EM = maskedDB || H || 0xbc — the construction whose existential unforgeability Bellare & Rogaway (1996) prove (applied here, ADR-10).
  3. Implement EmsaPss::verify: recover salt from the unmasked DB, recompute H', compare to H — the comparison must be constant-time (I11) even though PSS's own security proof doesn't require it structurally; this system holds I11 uniformly across both schemes for defense-in-depth against implementation-level distinguishers.
  4. Implement EmsaPkcs1V15 verify-only: fixed ASN.1 DigestInfo prefix + hash + 0xFF padding; reject any byte-level deviation (I11) — this is precisely the discipline Bleichenbacher (2006)'s "loose verifier" paper shows implementations skip.
  5. Gate EmsaPkcs1V15::encode (signing) behind a legacy-pkcs1-sign feature flag with a compile-time deprecation notice (P2, ADR-10) — never the default entry point.
  6. Wire docs/adr/ADR-10.md and delete Phase 0's smoke-test placeholder (§12.6).

17.3 Deliverable

rsa_core::encoding::{EmsaPss, EmsaPkcs1V15} implementing SignatureEncoding (§11), passing RFC 8017 Appendix C and the full Wycheproof PSS/PKCS1 corpora including negative cases.

17.4 Acceptance Criteria

  • EmsaPss encode/verify reproduce RFC 8017 Appendix C examples exactly.
  • verify(encode(hash)) returns Ok(()) for 10,000 random (message, salt) pairs.
  • The Wycheproof rsa_pss_2048_sha256_mgf1_*_test.json corpus passes 100% including negative (invalid) cases — zero false accepts.
  • The 0xbc trailer byte and every Padding2 byte are verified bit-for-bit; a corpus of 200 synthetically corrupted encodings (one flipped byte each) is rejected 100%.

17.6 Pitfalls

  • Off-by-one in the Padding2/0x01 boundary byte accepts forged signatures — exactly Bleichenbacher (2006)'s "loose verifier" class; the fixture pkcs1v15_verify_corrupted_byte exists specifically to catch this.
  • Comparing the recomputed H' with a short-circuiting == on a byte slice (instead of a constant-time comparison) reopens a byte-at-a-time timing distinguisher on verification, even though PSS's core proof doesn't strictly require constant-time compare — I11 mandates it anyway (defense-in-depth).
  • EmsaPkcs1V15::encode being reachable without an explicit feature flag silently reintroduces the exact scheme RFC 8017 Section 13 recommends against for new signatures (P2).

17.7 Performance Concerns

MGF1's cost is linear in output length (emLen - hLen - 1 bytes for PSS's DB mask); at 2048-bit modulus size this is a handful of hash invocations, negligible next to the mod_exp_ct cost dominating rsasp1 (§16.7). No additional big-O concern beyond the underlying hash function's throughput.

17.8 Edge Cases

  • Salt length sLen = 0 (a valid PSS configuration per RFC 8017) must still encode/verify correctly — the salt-recovery step degenerates but must not panic.
  • emLen at its minimum valid value (hLen + sLen + 2) exercises the tightest DB packing; must not underflow the padding-length computation.
  • A PSS signature verified against the wrong hash algorithm (mismatched mHash length) must reject cleanly (Err(InvalidSignature)), not panic on a length-mismatched slice.

17.9 Failure Analysis

A EmsaPss::verify that accepts a structurally-invalid encoding (missing the 0xbc trailer, wrong Padding2 bytes) is a forgery-acceptance defect — the entire signature scheme's security collapses to "anything with the right hash passes." Detection: the Wycheproof negative-case corpus (§17.5) run on every CI build (ADR-16). Blast radius: every consumer trusting a signature verified by the defective build. Containment: I11 is tested explicitly per byte-position corruption, not just whole-message fuzzing, to catch single-byte regressions precisely. Recovery: any release found accepting a Wycheproof negative case is pulled and reissued; no signature verified by that release can be trusted retroactively.

17.10 Operational Notes

verify.reject_total (§7 I11 Telemetry) is tagged by rejection reason (bad_trailer, bad_padding2, hash_mismatch) for operator visibility, without ever logging the message or signature bytes themselves (ADR-25). Compatibility: EmsaPkcs1V15::verify remains available indefinitely for legacy interop (§1 non-goals scope only excludes signing with it, not verification) — versioned independently per ADR-19.

18. Phase 6 — Encryption Encoding (OAEP & PKCS1-v1.5 Bleichenbacher Defense)

18.1 Objectives

Implement EmeOaep (default, ADR-11, P3) with the Manger (2001) countermeasure (I9) and EmePkcs1V15 decode-only with the Bleichenbacher (1998) countermeasure (I10), per §8.3/§8.6's schema and malformed-input example.

18.2 Detailed Implementation Steps

  1. Implement EmeOaep::encode per §8.3: DB = lHash || PS || 0x01 || M, mask with MGF1 (shared with Phase 5, §17), producing EM = 0x00 || maskedSeed || maskedDB.
  2. Implement EmeOaep::decode with the Manger (2001) countermeasure (I9): unmask, then combine every validity check (leading byte, lHash match, 0x01 boundary presence) into a single constant-time Choice (via the subtle crate, ADR-13) — never branch on any individual check's result. On failure, produce a fixed-length, ciphertext-deterministic decoy (e.g. HMAC(fixed_key, ciphertext) truncated to the expected length) rather than a distinguishing error (§8.6's malformed-input example is exactly this path).
  3. Implement EmePkcs1V15::decode with the Bleichenbacher (1998) countermeasure (I10): constant-time unpadding; on any failure, return the same fixed-length deterministic decoy construction as OAEP (never a 0x02-specific error) — closing the exact oracle CVE-2017- 12373-class implementations reopen by checking only the leading 0x02 byte and treating the rest as "probably fine."
  4. Do not implement EmePkcs1V15::encode at all (P3) — no code path produces new PKCS1-v1.5 ciphertexts; the type exists for decode-only interop.
  5. Wire the Manger/Bleichenbacher timing harnesses (timing/runner) with the four documented Bleichenbacher oracle conditions and the OAEP valid/invalid distribution pair.

18.3 Deliverable

rsa_core::encoding::{EmeOaep, EmePkcs1V15} implementing EncryptionEncoding (§11), passing RFC 8017 Appendix C, full Wycheproof OAEP corpus, and both timing harnesses at |t| ≤ 4.5.

18.4 Acceptance Criteria

  • EmeOaep encode/decode reproduce RFC 8017 Appendix C examples exactly.
  • The Wycheproof rsa_oaep_2048_sha256_mgf1sha256_*_test.json corpus passes 100%.
  • Manger timing harness: 10^5 measurements of valid-vs-invalid OAEP decode show |t| ≤ 4.5.
  • Bleichenbacher timing harness: 10^5 measurements across the four documented oracle conditions show |t| ≤ 4.5 pairwise.
  • Zero code path returns a decode error variant more specific than MalformedEncoding (I9/I10) from either decoder.

Fixture Purpose Expected Output

oaep_wycheproof.json Wycheproof OAEP corpus 100% correct accept/reject

18.6 Pitfalls

  • The Manger countermeasure must be branchless start to finish — a single if valid { plaintext } else { Err(SpecificReason) } at the very end of an otherwise-constant-time function still leaks via the return path's instruction count; the decoy must be computed unconditionally and selected via ct_select (§13), never via control flow.
  • The Bleichenbacher fake output must be deterministic from the ciphertext (e.g. an HMAC of it), not freshly randomized per call — a randomized decoy lets an attacker replay the same ciphertext and observe different fakes, which is itself a (weaker but real) distinguishing signal.
  • Checking only the leading 0x00 0x02 bytes and treating the remainder as "probably padding" is real-world CVE-2017-12373-class laziness — every padding byte must be checked, combined into the single Choice.

18.7 Performance Concerns

Both decoders' constant-time discipline means their cost is always the worst-case cost (compute everything, discard on failure) — there is no fast-reject path, by design (that would be a timing leak). This makes decode cost predictable (bounded by mod_exp_ct dominating overall, §16.7) rather than variable, which is itself an operational property worth stating explicitly (predictable latency, not just "safe").

18.8 Edge Cases

  • Ciphertext decoding to a message longer than k − 2hLen − 2 bytes (OAEP's maximum) must be folded into the same single Choice as every other failure mode, not treated as a distinct early-reject case.
  • All-zero DB after unmasking (a degenerate but reachable state) must still route through the same constant-time check-and-decoy path.
  • A label mismatch (OAEP's optional associated data) must be indistinguishable from a lHash-computation failure or a padding-boundary failure (§8.6) — all three fold into one Choice.

18.9 Failure Analysis

A distinguishable failure mode in either decoder reopens the exact chosen-ciphertext oracle its countermeasure exists to close — Bleichenbacher (1998) needs roughly one bit of oracle information per query and a few thousand queries to recover a full plaintext; Manger (2001)'s variant is even more efficient. Detection: the timing harnesses (§18.5) plus a dedicated fuzz target (rsa-fuzz/fuzz_targets/decrypt_oaep.rs, decrypt_pkcs1.rs) asserting the returned RsaError variant is always exactly MalformedEncoding regardless of which internal check failed. Blast radius: full plaintext recovery of intercepted ciphertexts via repeated oracle queries — a network-facing catastrophe if this library backs a TLS/JWT decryption endpoint. Containment: I9/I10 are structural (no configuration disables the decoy path). Recovery: any release observed returning a distinguishing error is pulled; every ciphertext ever decrypted through it must be assumed potentially exposed to a patient attacker.

18.10 Operational Notes

Decode failures emit a single undifferentiated encoding.decode_fail_total counter (no reason tag, deliberately — a reason tag would itself leak the oracle to anyone with metrics access, ADR-25). Compatibility: EmePkcs1V15::decode remains available indefinitely for legacy ciphertext interop; there is no roadmap to remove it, only to never add new ciphertext production against it (P3).

19. Phase 7 — Randomness, Blinding & Side-Channel Hardening

19.1 Objectives

Wrap every private-key operation (rsadp, rsasp1) with mandatory blinding (P5, ADR-07, I7), closing Brumley & Boneh (2003) beyond what the constant-time ladder (§14) alone provides; codify the caller-injected-RNG discipline (P13, I13) as documentation and lints, not just code.

19.2 Detailed Implementation Steps

  1. Implement the blinding wrapper: draw a fresh, uniformly random, invertible r (via the caller's RngCore, I13); compute c_blind = c · r^e mod n (a public-exponent operation, mod_exp_pub); run the CRT private op (§16) on c_blind; unblind via m = m_blind · r^{-1} mod n (mod_inverse, §13) — applied identically to rsasp1's message representative.
  2. Sequence the fault-injection check (§16 step 4) to run on the blinded intermediate, before unblinding (§16.6's pitfall) — the wrapper's step order is itself security-critical.
  3. Add a dudect timing harness specifically isolating the blinding overhead (with vs. without blinding, at fixed key and message) to demonstrate I7 doesn't itself introduce a new timing signal correlated with r.
  4. Document the recommended production RNG pattern (docs/architecture/blinding.md): an HMAC-DRBG seeded from OsRng/getrandom, satisfying I13 without requiring every caller to re-derive DRBG hygiene from scratch.
  5. Add a clippy-style lint (checked in CI, ADR-18) that flags any call to OsRng::default() or thread_rng() inside rsa-core/rsa-bignum/rsa-prime — enforces I13 mechanically, not just by code review.

19.3 Deliverable

Every rsadp/rsasp1 call in the public surface is blinded by construction (no unblinded path reachable), with a dudect report showing the wrapper introduces no new distinguishable timing signal.

19.4 Acceptance Criteria

  • A property test asserts: two calls to rsadp/rsasp1 with the same (key, ciphertext) but different r draws produce identical unblinded output, for 1,000 random pairs (correctness of the blind/unblind algebra).
  • dudect t-statistic ≤ 4.5 over 10^7 measurements comparing blinded-call timing across two different secret exponents at fixed r-distribution (M10, §28) — confirms I5/I7 compose without reintroducing a leak.
  • The CI lint blocking implicit OsRng/thread_rng use fires on a deliberately introduced violation in a test fixture (lint self-test).
  • Blinding overhead ≤ 0.15 ms at 2048-bit (one extra mod_exp_pub + one mod_inverse, consistent with §4's ≤5.0 ms total private-op budget already including this cost).

19.5 Conformance Fixtures

Fixture Purpose Expected Output
blinding_correctness_1k.json same input, different r, 1K trials identical unblinded output
dudect_blinded_privateop.json timing across two secret exponents |t| ≤ 4.5, n=10^7
lint_implicit_rng_selftest.json deliberately violates I13 CI lint fires
blinding_overhead_bench.json with vs. without blinding cost delta ≤ 0.15 ms delta at 2048-bit

19.6 Pitfalls

  • Reusing r across calls (a tempting cache "optimization") defeats blinding entirely — MM1's "schedule vs. value" lesson generalizes: reuse turns a per-call random mask back into a fixed, learnable offset. r is drawn fresh, unconditionally, every call.
  • Computing r^{-1} before running the CRT op (rather than after) wastes the opportunity to overlap the inverse computation with the exponentiation, but more importantly, doing the unblind step before the fault check (§16.6) silently reopens the CRT fault-injection window this phase's ordering is designed to close.
  • A "smart" RNG wrapper that falls back to a weaker source when the primary is exhausted silently degrades I13's guarantee — the lint (§19.2 step 5) only catches direct misuse, not a degraded RNG hidden behind a trait object; document this residual risk explicitly rather than claim full coverage.

19.7 Performance Concerns

Blinding costs one mod_exp_pub (~0.1 ms, M9) plus one mod_inverse (O(k²) extended-Euclid, negligible next to exponentiation) per private op — a small, bounded, already-budgeted addition to the ≤5.0 ms total (§4). No amortization is possible without violating I7 (fresh r every call is the whole point).

19.8 Edge Cases

  • r = 1 (a degenerate but uniformly-possible draw) must still round-trip correctly through blind/unblind — no special-casing that would branch on r's value.
  • r not invertible mod n (probability ≈0 for uniform r and RSA-sized n, but must be handled) must trigger a resample of r, not a panic (P14) — this resample path itself must not become a new timing signal correlated with r's original (unlucky) value; document the negligible-probability residual risk rather than over-engineer a constant-time resample loop.
  • Concurrent calls to rsadp on the same RsaPrivateKey from multiple threads must each draw independent r values — the wrapper takes &self (I8's Send+Sync annotation, §11) and an exclusively-borrowed &mut impl RngCore per call, so concurrent callers each supply their own RNG handle (typically thread-local).

19.9 Failure Analysis

A blinding defect that silently omits the fresh-r draw (e.g., a caching bug) reopens Brumley & Boneh (2003)'s network timing attack, which historically recovered an OpenSSL RSA private key over a LAN in under two hours. Detection: dudect (§19.4) plus the correctness property test (§19.4, first bullet) — a stuck or reused r would also fail the correctness test if the bug is gross, but a partially stuck RNG (e.g., low-entropy fallback) requires the timing harness to catch, since correctness may still hold. Blast radius: private-key recovery given sustained network access to the signing/decryption endpoint. Containment: I7 has no configuration escape hatch. Recovery: rotate the key; audit the RNG supply chain for the deployment.

19.10 Operational Notes

blinding.rng_draw_total (§7 I7 Telemetry) counts draws without ever recording r's value. Operators should alert on rng_draw_total stalling (a stuck RNG manifests as a hang, not a crash — P14 aside, a blocked RngCore::fill_bytes call on a starved entropy pool is a real production hazard distinct from any cryptographic defect). No compatibility impact: blinding is internal to rsadp/rsasp1 and invisible at the public API (Phase 9, §21).

20. Phase 8 — Key Serialization (PKCS#1 / PKCS#8 / JWK / PEM)

20.1 Objectives

Implement the four KeyFormat (§11) implementors — Pkcs1, Pkcs8, Jwk, Pem (ADR-14) — so keys generated by Phase 3 (§15) interoperate with OpenSSL/BoringSSL and JOSE tooling.

20.2 Detailed Implementation Steps

  1. Implement Pkcs1 (RFC 8017 Appendix A.1): ASN.1 DER for raw RSA keys, n/e/d/p/q/dP/dQ/ qInv as INTEGERs — every RsaPrivateKey/CrtParams field (§11) maps one-to-one.
  2. Implement Pkcs8 (RFC 5958): PrivateKeyInfo wrapping the PKCS#1 payload with the RSA algorithm identifier OID 1.2.840.113549.1.1.1.
  3. Implement Jwk (RFC 7517/7518): JSON object with base64url-nopad-encoded n, e, d, p, q, dp, dq, qi fields — field names fixed by the RFC, not renamed.
  4. Implement Pem (RFC 7468): base64 standard encoding wrapped in -----BEGIN {PKCS1,PKCS8}-----/-----END----- armor around the corresponding DER bytes.
  5. Implement the ASN.1 unsigned-INTEGER high-bit rule correctly (§8.6-adjacent malformed- input class): a positive integer whose most significant byte has its high bit set requires a leading 0x00 byte to disambiguate sign — get this wrong and two different DER encodings silently represent the same modulus (or worse, a parser strips the 0x00 and corrupts n).
  6. Cross-format round-trip tests: PKCS#1 DER → PKCS#8 DER → PEM → parsed key → identity.

20.3 Deliverable

rsa_keys::{Pkcs1, Pkcs8, Jwk, Pem} implementing KeyFormat (§11), interoperating losslessly with OpenSSL-generated keys in both directions (cross.openssl fixture, ADR-17).

20.4 Acceptance Criteria

  • Round-trip (serialize → deserialize) produces a bit-identical key for all four formats, for 100 random keys per format.
  • Cross-format chain (PKCS#1 → PKCS#8 → PEM → parsed) is the identity for 100 random keys.
  • A key generated by this system's Phase 3 (§15), exported as PKCS#8 PEM, is accepted by openssl rsa -in key.pem -check (external differential check, ADR-17).
  • The ASN.1 high-bit disambiguation rule (§20.2 step 5) is exercised by ≥ 20 keys whose n's top byte has the high bit set — all round-trip correctly.

Fixture Purpose Expected Output

20.6 Pitfalls

  • Stripping a leading 0x00 "because it looks redundant" collides two distinct n values under one encoding — a parser must preserve it exactly per the ASN.1 INTEGER sign rule.
  • JWK requires base64url with no padding (BASE64URL_NOPAD); many general-purpose JSON/ base64 tools default to standard base64 with = padding — cross-validate against a real JOSE library, not just self-consistency.
  • PKCS#8's algorithm-identifier OID must be exactly 1.2.840.113549.1.1.1 (rsaEncryption); a typo'd OID produces a key OpenSSL silently refuses without an obviously diagnostic error.

20.7 Performance Concerns

Serialization/deserialization is off the hot path (called once per key load/store, not per operation) — no latency budget beyond "fast enough for CLI/config-load use," unlike §16's per-operation primitives. ASN.1 DER parsing is O(key size), negligible at RSA key sizes.

20.8 Edge Cases

  • A PKCS#1 DER blob missing the optional CRT fields (otherPrimeInfos/CRT parameters omitted by a non-conformant peer) must parse into an RsaPrivateKey that falls back to the non-CRT path at operation time (§16.8) rather than fail to parse.
  • A JWK missing the private fields (d, p, q, …) but present n/e must parse as a public-key-only JWK, not error.
  • An oversized DER length prefix (malicious or corrupted) must be bounds-checked before allocation, not trusted directly as an allocation size (a DoS vector via a claimed multi- gigabyte length).

20.9 Failure Analysis

A serialization bug that silently corrupts n (e.g., the ASN.1 high-bit issue, §20.6) produces a key that parses successfully but is subtly wrong — a signature made with it fails to verify against the intended public key, surfacing as a downstream interop failure far from the actual defect. Detection: the cross-format chain fixture (§20.5) plus differential testing against OpenSSL on every CI run. Blast radius: every consumer of a key exported by the defective version. Containment: n/a at runtime (a static-data defect, not a runtime one). Recovery: re-export affected keys from the in-memory RsaPrivateKey (which was never corrupted — only its serialization was) once the parser/encoder is fixed.

20.10 Operational Notes

Serialization emits no telemetry beyond a serialization.error_total counter tagged by format (ADR-25 — never logs key material). Compatibility & versioning: DER/PEM formats are wire formats fixed by external RFCs (RFC 5958/7468) and never change independent of this project; JWK follows RFC 7517/7518 verbatim. This system's own RsaPrivateKey/RsaPublicKey in-memory layout (§11) may evolve across SemVer-major versions (ADR-19) without affecting any wire format.

21.8 Edge Cases

  • CLI invoked with conflicting flags (e.g. --algo pss combined with a PKCS1-v1.5-only key import) must produce a clear, typed CLI error, not a downstream panic from the encoding layer.
  • A conformance vector file that is itself malformed (corrupted JSON) must fail the CI job loudly with a parse error, not silently skip that bucket.
  • A fuzz target that discovers a genuine crash must fail the 24-hour canary job (not just log a warning) — the canary is a release gate (ADR-16), not advisory.

21.9 Failure Analysis

A facade that leaks an internal type or a CLI that maps distinct errors to one generic message degrades operability rather than correctness — the cryptographic guarantees from Phases 1–7 remain intact, but the product built on top of them becomes harder to debug in the field. Detection: a dedicated "public API surface" snapshot test diffing the facade's exported symbol list across releases (catches accidental widening, ADR-19). Blast radius: integration friction and support burden, not key compromise. Containment: SemVer-major bump required for any intentional facade change. Recovery: yank and reissue a release that accidentally widened the surface, if caught before consumers depend on the leaked type.

21.10 Operational Notes

The conformance suite's report_schema.json output is the artifact operators/auditors consult to confirm a given release's exact vector-pass evidence (P12) — archived per release (§27).

24. Operational Readiness

Metrics. Every counter/gauge named in §7's Telemetry column and §22/§23's tables (keygen.*, crt.fault_check_fail_total, blinding.rng_draw_total, encoding.decode_fail_ total, verify.reject_total, timing.dudect_t_stat) is caller-visible only if the embedding application chooses to wire a metrics sink — the core crates themselves emit no runtime telemetry (ADR-29); these are the counter names and semantics a caller's instrumentation layer should expose.

Tracing. No distributed tracing inside rsa-core/rsa-bignum (pure synchronous compute, no IO to span, ADR-26). A caller wrapping a sign/decrypt call in its own trace span is sufficient; this library adds no internal span boundaries that could leak timing-correlated structure beyond what I5/I7 already guard against.

Structured logging. Governed by ADR-25: every log line a caller might emit around this library's calls must never include key material, plaintext, or ciphertext bytes — only operation name, RsaError variant (if any), and non-secret metadata (key size, algorithm).

Dashboards & alerting philosophy. Alert on: crt.fault_check_fail_total > 0 sustained (T3/ FM-2); timing.dudect_t_stat trending toward 4.5 in scheduled re-runs (early warning before a hard CI failure, FM-1); keygen.*_reject_total rates far outside the theoretical rejection probability derived in §32 #7 (possible RNG degradation, T7); fuzz canary job failure (FM-7/ FM-12) — page immediately, this blocks release.

SLOs. This is a library, not a service — SLOs are expressed as CI gate thresholds, not uptime: conformance suite 100% pass (§26); dudect |t| ≤ 4.5 (M10); fuzz canary zero panics (M12); keygen/private-op latency within §4's budgets (M1–M9).

Named runbooks (docs/runbooks/): triage.md (first-response for any T#/FM-# alert), timing-regression.md (bisecting a dudect threshold breach), conformance-failure.md (bisecting a vector regression).

Backup/restore. N/A — this library owns no persistent state; key backup/restore is the caller's responsibility (documented as an explicit boundary in §1).

Deployment topology, canary/rollback. Distributed as a versioned crate (ADR-19); the "deployment" is the caller's own release process consuming a new crate version. Rollback is a Cargo.lock pin to the prior version. No rolling-upgrade coordination needed (no shared mutable state across instances).

25. Compatibility & Versioning

Wire compatibility. PKCS#1/PKCS#8/JWK/PEM (§20) are external standards (RFC 8017 App. A, RFC 5958, RFC 7517/7518, RFC 7468); this project never diverges from them, so wire compatibility with OpenSSL/BoringSSL/any conformant JOSE library is permanent by construction, not a versioning decision this project makes.

API stability. The facade crate (§21.2) follows SemVer (ADR-19): a RsaError variant addition is a minor bump (additive); a signature change to any public function is a major bump; internal types (MontgomeryParams, SecretExponent, etc., §11) are never part of the SemVer contract and may change in any release (guarded by the facade snapshot test, §21.9).

Schema evolution. N/A for wire formats (external, fixed). The in-memory RsaPrivateKey/ RsaPublicKey layout (§11) may add fields (e.g. future multi-prime support, §35) only behind a major version bump if it changes existing field semantics, or a minor bump if purely additive and defaulted.

Deprecation policy. EmsaPkcs1V15::encode (legacy signing, gated since Phase 5, §17.2 step 5) carries a compile-time deprecation notice from its introduction and is never promoted to a default; it is never removed either, since removal would break legitimate legacy-interop callers who explicitly opted in — deprecation here means "never becomes the default," not "scheduled for deletion."

Rolling-upgrade guarantees. Since this is an embedded library with no shared state across processes, "rolling upgrade" reduces to: two processes running different (SemVer-compatible) versions of this crate can each independently generate/sign/verify/encrypt/decrypt without any cross-version protocol negotiation — every operation's wire output (a signature, a ciphertext, a serialized key) is fully defined by the external RFC, not by this crate's internal version.

Reproducible builds. rust-toolchain.toml pins the exact compiler version (ADR-01); Cargo.lock is committed for the rsa-cli/example binaries (library crates ship a lock-free Cargo.toml per Rust ecosystem convention, but CI additionally builds against a pinned lock for reproducibility verification).

SBOM. cargo-cyclonedx generates a software bill of materials per release, gated by deny.toml's license/advisory audit (ADR-13, ADR-23).

Release channels. crates.io is the sole distribution channel (ADR-19); no separate "nightly"/"beta" channel — SemVer pre-release identifiers (-alpha.N, -rc.N) serve that role within the same channel.

Version stamping. Each release embeds its crate version and Git commit hash into the rsa-cli --version output and the conformance report header, so a field-deployed binary's provenance is always recoverable.

Dependency auditing. cargo-deny (ADR-13) runs in CI against every dependency addition, checking license compatibility (ADR-23), known-advisory status (RUSTSEC), and a minimal- dependency-count policy (no transitive network-capable crates in rsa-bignum/rsa-core, consistent with the zero-FD constraint in §4).

28. Performance Engineering

Methodology. criterion (ADR-17) benchmarks every primitive named in §4/§16 on a fixed reference host; results are archived per release under benchmarks/results/ and diffed against the prior release to catch regressions before they reach production (tail-latency analysis via criterion's built-in percentile reporting, not just mean).

Allocation/lock/cache analysis. rsa-bignum avoids per-operation heap churn where possible (pre-sized Vec<u64> limb buffers); there is no lock contention anywhere in the core crates (no shared mutable state — every operation is a pure function over &self, I8's Send+Sync annotation). Cache-locality assumption: a 2048-bit operand (32×u64 = 256 B) fits comfortably in L1 (§4); 4096-bit operands (64×u64 = 512 B) still fit typical 32-64 KB L1 data caches with room for the Montgomery parameters alongside.

Syscall overhead. Zero syscalls in the core crates' hot path (no IO, §4) — the only syscall surface is the caller's RngCore implementation (typically one getrandom call per blinding draw / keygen candidate), outside this project's control.

29. Scalability Analysis

What stays constant. The number of modular exponentiations per operation (2 CRT half-width

  • 1 fault-check full-width for private ops; 1 for public ops) is fixed regardless of load — this system has no shared state that grows with request volume (contrast a database's index size).

What grows, and the Big-O. Per-operation cost grows O(k³) in modulus bit-length k (schoolbook Montgomery multiplication is O(k²) per multiply, and a fixed-iteration-count exponentiation performs O(k) multiplies, §32 #6) — moving from RSA-2048 to RSA-4096 (2× bit-length) costs roughly 8× per private op, consistent with the M3→M7 jump in §28's table.

Named bottlenecks, in order. (1) mod_exp_ct's fixed-iteration Montgomery ladder dominates every private op's wall-clock (§14.7) — the primary lever is CRT (already applied, §16.7) since sub-quadratic multiplication (Karatsuba) is deferred (§35) and wouldn't help below ~40 limbs anyway (§13.7). (2) Keygen's rejection-sampling retry count (§32 #7) is the primary lever for keygen latency — trial division (§15.7) is the mitigation already applied. (3) RNG throughput (one draw per blinding call, I7) is rarely the bottleneck at typical getrandom throughput but becomes one under RNG starvation (FM-10/T7).

Horizontal vs. vertical scaling. This library has no server-side state to shard — "scaling" means the caller's process fleet scales horizontally by simply running more instances, each independently CPU-bound on mod_exp_ct/mod_exp_pub (§32 #2's linear-in-cores derivation holds because there is zero cross-instance coordination, unlike a system with a shared lock or shared index).

Coordination overhead. Zero — no two calls to this library's functions from different threads/processes ever need to communicate (I8's Send+Sync note, §11). The only "shared" resource is the entropy pool (getrandom), which is OS-managed, not this library's concern.

Practical ceiling and levers beyond it. The practical throughput ceiling for a single host is cores × (1/private-op-latency) (§32 #2: 1,600 sign/s on an 8-core host at RSA-2048). Levers beyond that ceiling: (a) more hosts (horizontal, free of coordination cost, above); (b) HSM offload (§34's Alternative C) trades software throughput for hardware-backed throughput and a different trust boundary; (c) smaller keys (RSA-2048 vs. 3072/4096) trade security margin for an 8×-per-doubling throughput gain — not a lever this project exposes below its floor (ADR-12).

30. Mental Models & First Principles

MM1 — A private exponent is a secret schedule, not a secret number. The ladder consumes d's bits one at a time; the sequence of operations, not merely the stored value, is what a side channel observes. Predicts: any implementation that branches on individual bits of d leaks it bit-by-bit even if d is never printed or logged. Bug class without it: "I never log the key, so I'm safe" — misses that the exponentiation's own control flow is the leak. Applies in §14 (the ladder), §7 I5.

MM2 — Padding is the security proof's hypothesis, not decoration. OAEP/PSS's security proofs (Bellare-Rogaway 1996; the OAEP IND-CCA2 reduction, Katz & Lindell) assume the exact byte layout; moving one byte invalidates the proof even if the scheme "still round-trips" in functional tests. Predicts: a padding variant can pass every round-trip test yet be completely broken (Manger, Bleichenbacher). Bug class without it: treating padding as a serialization format rather than the mechanism that makes RSA IND-CCA2-secure. Applies in §17, §18, §8.3.

MM3 — CRT trades an arithmetic invariant for a fault-injection surface. Splitting a computation across p and q creates exactly one recombination point where corrupting either half alone produces a consistent-looking but wrong result — unlike a random error in the non-CRT path, which just produces obviously wrong output. Predicts: any optimization that "splits work" across independently-computed halves is exactly where to look for new fault-injection surfaces. Applies in §16, §22 T3, Boneh-DeMillo-Lipton (1997).

MM4 — A constant-time function is a claim about a sampled input distribution, not a universal property. dudect only tests the distributions fed to it; a function constant-time over "random exponent vs. random exponent" may still leak on an edge case (all-zero, all-ones, exactly n−1) never sampled. Predicts: constant-time bugs cluster at the boundaries of the value space. Applies in §14, §19's fixture design (§19.4/§19.8).

MM5 — An oracle doesn't need to say "yes" to leak — silence and timing are also outputs. Bleichenbacher/Manger show that any observable difference in an otherwise-silent failure path (timing, error type, downstream connection behavior) is itself the oracle. Predicts: "we don't return the padding error to the caller" is insufficient if the caller's own behavior still differs by branch. Applies in §18, §22 T4/T5.

MM6 — Key generation is a rejection sampler, not a formula. RSA keygen is "generate candidate, test, reject, repeat" — its running time is a random variable, and its rare rejection events (Fermat-close primes, Wiener-small d) are the security boundary, not an afterthought. Predicts: any keygen "simplification" that skips a rejection check silently narrows the guaranteed security margin. Applies in §15, §32 #7.

MM7 — Zeroize is a race against the optimizer, not just against the OS. A compiler may legally elide a memory write it can prove is dead; clearing a secret buffer requires either a volatile write or a crate (zeroize) that defeats dead-store elimination — "I overwrote it in source" is not the same claim as "it is cleared in the compiled binary." Applies in §11, §7 I8, §23 FM-9.

MM8 — Multi-prime and CRT are the same idea at different arity, but the fault surface grows with arity. Two-prime CRT has one recombination point; k-prime multi-prime RSA (RFC 8017 App. A.1.4) has k−1 recombination points, each an independent fault-injection surface — exactly why this project defers multi-prime (§35) despite its throughput appeal. Applies in §16, §34, §35.

OpenSSL made memory-safety/ecosystem-ubiquity its winning bet decades before Rust existed — it wins wherever a FIPS 140-validated module boundary already exists and must not be re-certified from scratch; this design cannot claim that regulatory inertia.

32. Back-of-Envelope Capacity Model

  1. RSA-2048 sign throughput per core = 1 / 5.0 ms (§4 CRT private-op target) = 200 sign/s per core.
  2. 8-core server sign throughput = 200 × 8 (§29: zero coordination overhead, linear scaling) = 1,600 sign/s — the practical ceiling named in §29.
  3. TLS RSA-key-exchange handshake capacity (1 decrypt per handshake) on the same 8-core host = 1,600 handshake/s, decrypt-bound (§32 #2 restated for the decrypt path, identical cost shape to sign per §16.2).
  4. RSA-2048 verify throughput per core = 1 / 0.10 ms (§4 public-op target) = 10,000 verify/s per core — 50× the private-op rate, consistent with the ~4-10× ladder-vs-window cost gap (P6) compounded with the CRT-vs-full-width gap (§32 #6).
  5. Memory for 10,000 concurrent loaded private keys = 10,000 × 2 KB (§4 memory-per-key) = 20 MB heap — the capacity-model input assumption from §4 made concrete.
  6. CRT speedup derivation: non-CRT cost is one full-width (k-bit) exponentiation; CRT cost is two half-width (k/2-bit) exponentiations. Schoolbook-Montgomery exponentiation cost scales O(bit-length³) (§29). Two half-width ops cost 2 × (1/2)³ = 2 × 0.125 = 0.25× the full-width cost → ≈4× speedup, matching §4's stated "~4×" non-CRT penalty exactly.
  7. Keygen retry-count derivation: by the Prime Number Theorem, a random odd 1024-bit number is prime with probability ≈ 1/ln(2^1024) ≈ 1/710. Trial division against primes < 65,521 removes ~87% of composites before the expensive Miller-Rabin step (§15.7), improving effective density roughly 7×: 710/7 ≈ 101 Miller-Rabin-gated candidates per 1024-bit prime factor, ×2 factors → ≈202 gated candidates per RSA-2048 keygen, which bounds the ≤1.0 s budget in §4/M1.
  8. Fuzz coverage budget: 2,000 exec/s (§4 fuzz throughput) × 86,400 s/day = ≈172.8M execs/day per core; a 30-day canary (M12) accumulates ≈5.18B executions.
  9. Conformance corpus size estimate: combined Wycheproof RSA-OAEP + RSA-PSS + RSA-PKCS1 corpora ≈ 3,000-5,000 vectors; at the §4/M11 ≤10-minute wall-clock budget, this allows ≈120-200 ms average budget per vector, including process/harness overhead.
  10. dudect sample-time budget: 10^7 measurements (§4) at an instrumented rate on the same order as the fuzz exec rate (§32 #8, ~2,000/s) ≈ ≈5,000 s (≈83 minutes) per constant-time gate run — explaining why timing.yml (§27) runs as a separate, longer-budget CI job than the fast per-PR ci.yml.

34. Alternative Architectures (Roads Not Taken)

A — ECC-first (Curve25519/Ed25519 + X25519) instead of RSA.

message -> Ed25519 sign (scalar mult on twisted Edwards curve) -> 64-byte signature
message -> Ed25519 verify (2 scalar mults + point equality) -> accept/reject

Regime where it wins: bandwidth/CPU-constrained mobile and embedded targets, any greenfield protocol (SSH Ed25519 host keys, TLS 1.3 defaults). Real system: libsodium / OpenSSH's default host-key algorithm / BoringSSL's Ed25519 path. Rejected here because this project is scoped specifically to teach bignum/CRT/padding-oracle mechanics (§2) that ECC's smaller, fixed-size field arithmetic does not exercise the same way, and because X.509/JWT-RS256 legacy PKI still mandates RSA in many audited environments.

B — Non-CRT, constant-time-only private-key path (no CRT acceleration at all).

c --(mod_exp_ct over full-width d, mod n)--> m     (no p/q recombination step at all)

Regime where it wins: ultra-conservative FIPS-boundary/HSM firmware where the CRT fault- injection surface (§22 T3) must be eliminated structurally, not mitigated by a re-encryption check — some smartcard/EMV RSA implementations historically chose exactly this. Rejected here because the ~4× throughput cost (§32 #6) is unacceptable for the server-side TLS/JWT workloads this design targets (§4).

C — HSM/PKCS#11-backed signing (private key material never leaves hardware).

caller -> PKCS#11 client (this crate's facade, thin) -> HSM (holds p,q,dP,dQ,qInv; does mod_exp)

Regime where it wins: regulated environments (PCI-HSM, FIPS 140-3 Level 3+) where key-extraction risk must be eliminated at the hardware boundary, not just the software boundary. Real system: AWS CloudHSM, YubiHSM 2, Thales Luna HSM. Rejected here because pushing all interesting arithmetic behind an opaque vendor boundary defeats this project's teaching purpose (§2), though it remains the correct production choice for the highest assurance tier — hence deferred (§35), not rejected outright.

D — Post-quantum hybrid key transport (classical RSA/ECC + ML-KEM).

client -> [RSA-OAEP-wrapped key_share_1 || ML-KEM ciphertext key_share_2] -> combined secret

Regime where it wins: any new TLS/SSH deployment today, given the harvest-now-decrypt-later threat to RSA-encrypted traffic. Real system: Chrome/BoringSSL's X25519Kyber768 hybrid TLS 1.3 key exchange (shipped 2023). Rejected here — this blueprint specifies classical RFC 8017 RSA only; hybrid PQ transport is a distinct future project, deferred (§35), not a variant of this one.

36. Glossary

ACVP — Automated Cryptographic Validation Protocol; NIST's automated successor to CAVP.

Barrett reduction — a modular-reduction technique using a precomputed reciprocal; rejected here in favor of Montgomery reduction (ADR-04) for the repeated-modulus RSA hot path.

Bleichenbacher attack — the 1998 chosen-ciphertext attack against PKCS#1 v1.5 decryption oracles; closed here by I10.

Blinding — randomizing a private-key operation's input with a fresh factor r to remove correlation between secret-dependent timing and the operation's true input; mandatory here (I7).

CAVP — Cryptographic Algorithm Validation Program; NIST's test-vector validation suite.

Carmichael function λ(n) — the smallest exponent m such that a^m ≡ 1 (mod n) for all a coprime to n; used in place of Euler's totient for the tighter FIPS-186-5-mandated d.

Chinese Remainder Theorem (CRT) — the number-theoretic result allowing computation mod p and mod q independently, then recombination mod n = p·q; the basis of §16's speedup.

Ciphertext — the encrypted representative c, always < n (I14).

Constant-time — an implementation property where timing/memory-access pattern is independent of secret data (I5, I9, I10); verified statistically via dudect.

Coppersmith's attack — lattice-based attacks recovering RSA parameters from partial information or exploiting small exponents; motivates ADR-08 and I3/I4.

CRT parameters (dP, dQ, qInv) — the precomputed values enabling CRT-accelerated private-key operations (§8.2, §11).

Decoy — the fixed-length, ciphertext-deterministic fake plaintext returned on decode failure (I9, I10), indistinguishable from a real result to the caller.

DER — Distinguished Encoding Rules; the canonical binary form of ASN.1, used by PKCS#1/8.

dudect — a statistical framework for detecting timing side channels via Welch's t-test.

EME (Encoding Method for Encryption) — RFC 8017's term for an encryption padding scheme (OAEP, PKCS1-v1.5).

EMSA (Encoding Method for Signatures with Appendix) — RFC 8017's term for a signature padding scheme (PSS, PKCS1-v1.5).

Euler's totient φ(n) — count of integers below n coprime to n; φ(n) = (p−1)(q−1) for RSA moduli.

Fault-injection attack — deliberately corrupting a computation (voltage glitch, etc.) to extract secret information from the faulty output; closed for CRT decryption by I6.

Fermat factoring — factoring n by searching near √n when p and q are close; closed by I4.

F4 (65537) — the fixed public exponent this project uses for keygen (ADR-08, P9).

I2OSP / OS2IP — Integer-to-Octet-String / Octet-String-to-Integer primitives (RFC 8017 §4), the byte↔integer boundary between wire formats and BigUint.

IND-CCA2 — indistinguishability under adaptive chosen-ciphertext attack; the security notion OAEP is designed to satisfy.

JWK (JSON Web Key) — RFC 7517's JSON key-interchange format.

Lucas test — a probabilistic primality test complementary to Miller-Rabin, guarding specifically against certain adversarial pseudoprimes (P8, §15).

Manger attack — the 2001 chosen-ciphertext attack against OAEP decryption oracles; closed here by I9.

MGF1 — Mask Generation Function 1 (RFC 8017 Appendix B.2.1); the shared hash-based masking primitive underlying both OAEP and PSS.

Miller-Rabin test — the probabilistic primality test used in key generation, iterated per FIPS 186-5 Table A.1 (P7, I12).

Modulus (n) — the product of two (or, deferred, more) primes; the public part of an RSA key together with e.

Montgomery multiplication — a division-free modular-multiplication algorithm operating in a transformed representation (aR mod n); the basis of mod_exp_ct/mod_exp_pub (§14).

OAEP (Optimal Asymmetric Encryption Padding) — the RSA encryption padding scheme this project defaults to (ADR-11), providing IND-CCA2 security under the RSA assumption.

Padding oracle — any observable channel (error type, timing) that reveals whether a decryption's padding was valid, enabling chosen-ciphertext attacks (Bleichenbacher, Manger).

PEM — Privacy-Enhanced Mail textual (base64) encoding of DER data (RFC 7468).

PKCS#1 — RFC 8017, the primary RSA specification this project implements; also the name of its raw-key DER encoding (§20).

PKCS#8 — RFC 5958's generic private-key DER container, wrapping PKCS#1 with an algorithm identifier.

PSS (Probabilistic Signature Scheme) — the RSA signature padding scheme this project defaults to (ADR-10), with a provable existential-unforgeability reduction (Bellare-Rogaway 1996).

RSAEP / RSADP / RSASP1 / RSAVP1 — RFC 8017's four primitive operations: encrypt, decrypt, sign, verify (§16).

Safe prime — a prime p such that (p−1)/2 is also prime; an optional, slower keygen mode (P8) offered for compliance regimes.

Salt (PSS) — the random value included in PSS's hashed pre-image, giving the scheme its probabilistic (non-deterministic) signatures (§17, Hard Question 17).

Timing attack — recovering secret information by measuring operation latency; the class Kocher (1996) and Brumley-Boneh (2003) demonstrate against naive RSA implementations.

Wiener's attack — a continued-fraction attack recovering d when it is too small relative to n; closed by I3.

Wycheproof — Google's project providing a large corpus of cryptographic test vectors, including deliberately malformed/adversarial cases, used throughout this project's conformance suite (§26).

Zeroize — overwriting secret memory on drop in a way that survives compiler dead-store elimination (MM7, I8, ADR-22).
