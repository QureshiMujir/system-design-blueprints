⬜ Phase 1 — Bignum Primitives §13

Objectives

Implement BigUint (§11) and the limb-level arithmetic (add, subtract, multiply, divide, compare, GCD, modular inverse) that every later layer depends on (P10: zero unsafe). This is the foundation the architecture diagram (§3) names first: a wrong carry here propagates to a wrong signature at every layer above.

Deliverable

A rsa-bignum crate whose arithmetic differentially matches num-bigint bit-for-bit, with property tests and a documented big-O cost model per operation.

Acceptance
  • 100,000 random (a, b) pairs satisfy (a + b) - b == a (property test, ADR-17).
  • 100,000 random (a, b, m) triples satisfy BigUint mul/div agree with num-bigint bit-for- bit (differential test, reference impl §5 GMP/num-bigint).
  • ct_select/ct_eq/ct_lt pass a dudect smoke run: |t| ≤ 4.5 over 10^5 samples (a cheap precursor to the full 10^7-sample gate at Phase 2, §14.4).
  • Zero unsafe blocks in rsa-bignum (P10, ADR-15), verified by cargo geiger in CI.
Fixtures
Fixture Purpose Expected Output
bignum_add_sub_identity.json 100K random (a,b) round-trip all pass
bignum_cross_numbigint.json differential mul/div vs num-bigint bit-identical
bignum_div_by_zero.json malformed: divisor = 0 Err, no panic (P14)
bignum_ct_select_dudect.json timing smoke test |t| ≤ 4.5, n=10^5
Pitfalls
  • Limb-wise carry propagation is the single largest bignum bug source (Knuth Vol. 2 Section 4.3.1 warns explicitly); cross-validate against num-bigint from the first commit, not at the end.
  • The "quotient == 0" branch in division is data-dependent on the divisor, which for RSA usage is always the (public) modulus — document explicitly that this branch is not a secret- dependent leak (contrast with I5, which governs the exponent, not the modulus).
  • ct_select implemented as if choice { a } else { b } compiles but is not constant-time — the compiler is free to branch; the correct form uses bitmask arithmetic (P6's rationale extends here even though the ladder itself is Phase 2).

⬜ Phase 2 — Montgomery Arithmetic & Constant-Time Exponentiation §14

Objectives

Implement Montgomery multiplication (ADR-04) and the constant-time Montgomery-ladder exponentiation (mod_exp_ct, ADR-05, P6, I5) that closes Kocher (1996). Implement the faster windowed public-exponent path (mod_exp_pub) for verify/encrypt. This phase's output is the single most security-critical function in the system.

Deliverable

rsa-bignum::modular exposes mod_exp_ct/mod_exp_pub, both differentially correct against num-bigint, with mod_exp_ct passing the dudect constant-time gate (I5) in CI (timing.yml, ADR-18).

Acceptance
  • mod_exp_ct/mod_exp_pub agree with num-bigint::ModPow for 100,000 random triples, bit-for-bit.
  • dudect t-statistic ≤ 4.5 over 10^7 measurements (M10, §28) for mod_exp_ct, across both the uniform-random and all-ones exponent distributions.
  • mod_exp_pub is ≥ 3× faster than mod_exp_ct for a 17-bit exponent (e=65537) at 2048-bit modulus size (M9 vs. M8, §28).
  • MontgomeryParams::for_modulus rejects even moduli with Err (Montgomery requires odd n; RSA moduli are always odd, but the API must not silently misbehave on misuse).
Fixtures
Fixture Purpose Expected Output
montgomery_cross_numbigint.json 100K triples vs num-bigint::ModPow bit-identical
dudect_mod_exp_ct_uniform.json timing, uniform exponent |t| ≤ 4.5, n=10^7
dudect_mod_exp_ct_allones.json timing, all-ones exponent |t| ≤ 4.5, n=10^7
mod_exp_even_modulus_reject.json malformed: even modulus Err, no panic
Pitfalls
  • The ladder's conditional swap must be ct_select-based; a let tmp = r0; r0 = r1; r1 = tmp guarded by if bit reads the secret bit in the branch predictor — this is precisely the class MM1 (§30) names ("the schedule of operations is the secret, not just the value"). Cross-reference I5.
  • n_inv_neg_mod_64 requires n odd; a silent wraparound on even n produces wrong results without erroring — must be an explicit Err, not UB (P14).
  • Converting into Montgomery form (aR mod n) requires the input already be < n — a caller passing an out-of-range value produces silently wrong results unless I14's range check runs first (enforced at the primitive layer, §16, not here).

⬜ Phase 3 — Prime Generation & Key Generation §15

Objectives

Implement probable-prime generation (Miller-Rabin + optional Lucas, P7/P8) and the full FIPS 186-5 Appendix A.1.1.2 keygen procedure, producing RsaPrivateKey/RsaPublicKey (§11) that satisfy invariants I1–I4 and I12–I13.

Deliverable

rsa_core::key::generate(bits, rng) -> Result<RsaPrivateKey, RsaError> producing NIST-CAVP- conformant keys at 2048/3072/4096 bits (ADR-12), with every FIPS 186-5 rejection rule enforced and unit-tested individually.

Acceptance
  • keygen(2048, rng) produces n with bit-length 2048 ± 1 in ≥ 99.9% of a 1,000-trial sample (a keygen that violates this is silently generating undersized keys).
  • Generated keys pass NIST CAVP KGV.rsp (Key Generation Validation) vectors.
  • The Albrecht et al. (2018) adversarial pseudoprime corpus (prime.adversarial.json) is rejected at the FIPS-186-5-mandated iteration count (27 rounds at 2048-bit) — zero false accepts across the corpus.
  • keygen(2048) median wall-clock ≤ 1.0 s, single core (§4, M1, §28).
Fixtures
Fixture Purpose Expected Output
prime_cavp_kgv.json NIST CAVP Key Generation Validation all generated keys validate
prime_adversarial_albrecht2018.json adversarial pseudoprime corpus 100% rejected at 27 rounds
keygen_close_prime_reject.json forced |p-q| below threshold Err, resample (I4)
keygen_small_d_reject.json forced small d Err, resample (I3)
keygen_bit_length_1000trial.json 1,000-trial bit-length sample ≥ 99.9% within 2048±1
Pitfalls
  • Skipping the |p−q| rejection (FIPS 186-5 Appendix A.1.1.2 step 4.2) silently produces Fermat- factorable keys — MM6 (§30) names keygen as "a rejection sampler, not a formula"; skipping any rejection narrows the security margin invisibly.
  • Skipping the small-d rejection reopens Wiener's continued-fraction attack, part of the Coppersmith (1997)/Boneh (1999) attack family (§5 Papers #8, #9).
  • Using adversarially-structured random bases in Miller-Rabin (rather than uniformly random) is the exact gap Albrecht et al. (2018) exploit — bases must come from the same injected RngCore as everything else (I13), never a fixed sequence.
  • A keygen that internally calls OsRng::default() cannot be seeded for reproducible tests and reopens Heninger et al. (2012)'s shared-prime class if the OS entropy pool is degraded (I13).

⬜ Phase 4 — RSA Primitives & CRT-Accelerated Private Ops §16

Objectives

Implement the four RFC 8017 primitives (RSAEP, RSADP, RSASP1, RSAVP1) with CRT acceleration (§8.2) and the mandatory fault-injection defense (I6, P4, ADR-06) that closes Boneh-DeMillo- Lipton (1997). This is the phase where the architecture diagram's (§3) "primitive layer" becomes real.

Deliverable

rsa_core::primitives exposing rsaep/rsadp/rsasp1/rsavp1, matching RFC 8017 Appendix C worked examples bit-for-bit, with the fault-injection check unconditionally active (no feature flag disables it, per P4).

Acceptance
  • All four primitives reproduce RFC 8017 Appendix C's example vectors exactly.
  • rsadp(rsaep(m)) == m for 1,000 random (key, m) pairs, property-tested (ADR-17).
  • A single-bit fault injected into m1 (simulated in the test harness) triggers Err(FaultInjection) in 100% of 1,000 trials — zero silent faulty outputs (I6).
  • rsadp/rsasp1 wall-clock ≤ 5.0 ms at 2048-bit (M3/M5, §28), confirming the CRT speedup derived in §32 #6 is realized, not just theoretical.
Fixtures
Fixture Purpose Expected Output
primitive_rfc8017_appendix_c.json all four primitives vs. RFC 8017 examples bit-identical
primitive_roundtrip_1k.json rsadp(rsaep(m))==m, 1K random pairs 100% identity
crt_fault_injection_1bit.json single-bit fault in m1, 1K trials 100% FaultInjection
primitive_out_of_range_reject.json m ≥ n malformed input Err, no panic (I14)
Pitfalls
  • The CRT recombination has a subtle off-by-one when m1 < m2: the correct form is (m1 + p − m2) mod p, not (m1 − m2) mod p, which can underflow on unsigned BigUint — this exact bug class is why §8.2's state table is written out explicitly.
  • The fault-injection check (step 4) must run before unblinding (Phase 7, §19) — checking after unblinding leaks the unblinded value on a fault, defeating the point of the check.
  • Reusing CRT intermediate values (m1, m2) across calls (e.g., an ill-considered cache) would reintroduce exactly the "no fresh randomness" class of bug that P5/§19 close for blinding — CRT intermediates are always recomputed per call.

⬜ Phase 5 — Signature Encoding (PSS & PKCS1-v1.5) §17

Objectives

Implement EmsaPss (default, ADR-10, P2) and EmsaPkcs1V15 (verify-only by default) per §8.3's schema and RFC 8017 Section 9, replacing Phase 0's placeholder smoke test (§12.2 step 4) with the real SignatureEncoding implementors (§11).

Deliverable

rsa_core::encoding::{EmsaPss, EmsaPkcs1V15} implementing SignatureEncoding (§11), passing RFC 8017 Appendix C and the full Wycheproof PSS/PKCS1 corpora including negative cases.

Acceptance
  • EmsaPss encode/verify reproduce RFC 8017 Appendix C examples exactly.
  • verify(encode(hash)) returns Ok(()) for 10,000 random (message, salt) pairs.
  • The Wycheproof rsa_pss_2048_sha256_mgf1_*_test.json corpus passes 100% including negative (invalid) cases — zero false accepts.
  • The 0xbc trailer byte and every Padding2 byte are verified bit-for-bit; a corpus of 200 synthetically corrupted encodings (one flipped byte each) is rejected 100%.
Fixtures
Fixture Purpose Expected Output
pss_rfc8017_appendix_c.json RFC 8017 App. C PSS vectors bit-identical
pss_wycheproof.json Wycheproof PSS corpus, incl. negative cases 100% correct accept/reject

Pitfalls
  • Off-by-one in the Padding2/0x01 boundary byte accepts forged signatures — exactly Bleichenbacher (2006)'s "loose verifier" class; the fixture pkcs1v15_verify_corrupted_byte exists specifically to catch this.
  • Comparing the recomputed H' with a short-circuiting == on a byte slice (instead of a constant-time comparison) reopens a byte-at-a-time timing distinguisher on verification, even though PSS's core proof doesn't strictly require constant-time compare — I11 mandates it anyway (defense-in-depth).
  • EmsaPkcs1V15::encode being reachable without an explicit feature flag silently reintroduces the exact scheme RFC 8017 Section 13 recommends against for new signatures (P2).

⬜ Phase 6 — Encryption Encoding (OAEP & PKCS1-v1.5 Bleichenbacher Defense) §18

Objectives

Implement EmeOaep (default, ADR-11, P3) with the Manger (2001) countermeasure (I9) and EmePkcs1V15 decode-only with the Bleichenbacher (1998) countermeasure (I10), per §8.3/§8.6's schema and malformed-input example.

Deliverable

rsa_core::encoding::{EmeOaep, EmePkcs1V15} implementing EncryptionEncoding (§11), passing RFC 8017 Appendix C, full Wycheproof OAEP corpus, and both timing harnesses at |t| ≤ 4.5.

Acceptance
  • EmeOaep encode/decode reproduce RFC 8017 Appendix C examples exactly.
  • The Wycheproof rsa_oaep_2048_sha256_mgf1sha256_*_test.json corpus passes 100%.
  • Manger timing harness: 10^5 measurements of valid-vs-invalid OAEP decode show |t| ≤ 4.5.
  • Bleichenbacher timing harness: 10^5 measurements across the four documented oracle conditions show |t| ≤ 4.5 pairwise.
  • Zero code path returns a decode error variant more specific than MalformedEncoding (I9/I10) from either decoder.
Fixtures
Fixture Purpose Expected Output
oaep_rfc8017_appendix_c.json RFC 8017 App. C OAEP vectors bit-identical
oaep_wycheproof.json Wycheproof OAEP corpus 100% correct accept/reject
oaep_manger_timing.json valid vs. invalid decode timing |t| ≤ 4.5, n=10^5
pkcs1v15_bleichenbacher_timing.json 4 oracle conditions, pairwise timing |t| ≤ 4.5 each pair

Pitfalls
  • The Manger countermeasure must be branchless start to finish — a single if valid { plaintext } else { Err(SpecificReason) } at the very end of an otherwise-constant-time function still leaks via the return path's instruction count; the decoy must be computed unconditionally and selected via ct_select (§13), never via control flow.
  • The Bleichenbacher fake output must be deterministic from the ciphertext (e.g. an HMAC of it), not freshly randomized per call — a randomized decoy lets an attacker replay the same ciphertext and observe different fakes, which is itself a (weaker but real) distinguishing signal.
  • Checking only the leading 0x00 0x02 bytes and treating the remainder as "probably padding" is real-world CVE-2017-12373-class laziness — every padding byte must be checked, combined into the single Choice.

⬜ Phase 7 — Randomness, Blinding & Side-Channel Hardening §19

Objectives

Wrap every private-key operation (rsadp, rsasp1) with mandatory blinding (P5, ADR-07, I7), closing Brumley & Boneh (2003) beyond what the constant-time ladder (§14) alone provides; codify the caller-injected-RNG discipline (P13, I13) as documentation and lints, not just code.

Deliverable

Every rsadp/rsasp1 call in the public surface is blinded by construction (no unblinded path reachable), with a dudect report showing the wrapper introduces no new distinguishable timing signal.

Acceptance
  • A property test asserts: two calls to rsadp/rsasp1 with the same (key, ciphertext) but different r draws produce identical unblinded output, for 1,000 random pairs (correctness of the blind/unblind algebra).
  • dudect t-statistic ≤ 4.5 over 10^7 measurements comparing blinded-call timing across two different secret exponents at fixed r-distribution (M10, §28) — confirms I5/I7 compose without reintroducing a leak.
  • The CI lint blocking implicit OsRng/thread_rng use fires on a deliberately introduced violation in a test fixture (lint self-test).
  • Blinding overhead ≤ 0.15 ms at 2048-bit (one extra mod_exp_pub + one mod_inverse, consistent with §4's ≤5.0 ms total private-op budget already including this cost).
Fixtures
Fixture Purpose Expected Output
blinding_correctness_1k.json same input, different r, 1K trials identical unblinded output
dudect_blinded_privateop.json timing across two secret exponents |t| ≤ 4.5, n=10^7
lint_implicit_rng_selftest.json deliberately violates I13 CI lint fires
blinding_overhead_bench.json with vs. without blinding cost delta ≤ 0.15 ms delta at 2048-bit
Pitfalls
  • Reusing r across calls (a tempting cache "optimization") defeats blinding entirely — MM1's "schedule vs. value" lesson generalizes: reuse turns a per-call random mask back into a fixed, learnable offset. r is drawn fresh, unconditionally, every call.
  • Computing r^{-1} before running the CRT op (rather than after) wastes the opportunity to overlap the inverse computation with the exponentiation, but more importantly, doing the unblind step before the fault check (§16.6) silently reopens the CRT fault-injection window this phase's ordering is designed to close.
  • A "smart" RNG wrapper that falls back to a weaker source when the primary is exhausted silently degrades I13's guarantee — the lint (§19.2 step 5) only catches direct misuse, not a degraded RNG hidden behind a trait object; document this residual risk explicitly rather than claim full coverage.

⬜ Phase 8 — Key Serialization (PKCS#1 / PKCS#8 / JWK / PEM) §20

Objectives

Implement the four KeyFormat (§11) implementors — Pkcs1, Pkcs8, Jwk, Pem (ADR-14) — so keys generated by Phase 3 (§15) interoperate with OpenSSL/BoringSSL and JOSE tooling.

Deliverable

rsa_keys::{Pkcs1, Pkcs8, Jwk, Pem} implementing KeyFormat (§11), interoperating losslessly with OpenSSL-generated keys in both directions (cross.openssl fixture, ADR-17).

Acceptance
  • Round-trip (serialize → deserialize) produces a bit-identical key for all four formats, for 100 random keys per format.
  • Cross-format chain (PKCS#1 → PKCS#8 → PEM → parsed) is the identity for 100 random keys.
  • A key generated by this system's Phase 3 (§15), exported as PKCS#8 PEM, is accepted by openssl rsa -in key.pem -check (external differential check, ADR-17).
  • The ASN.1 high-bit disambiguation rule (§20.2 step 5) is exercised by ≥ 20 keys whose n's top byte has the high bit set — all round-trip correctly.

serialization_roundtrip_100_per_format.json 100 keys × 4 formats 100% bit-identical round-trip

Pitfalls
  • Stripping a leading 0x00 "because it looks redundant" collides two distinct n values under one encoding — a parser must preserve it exactly per the ASN.1 INTEGER sign rule.
  • JWK requires base64url with no padding (BASE64URL_NOPAD); many general-purpose JSON/ base64 tools default to standard base64 with = padding — cross-validate against a real JOSE library, not just self-consistency.
  • PKCS#8's algorithm-identifier OID must be exactly 1.2.840.113549.1.1.1 (rsaEncryption); a typo'd OID produces a key OpenSSL silently refuses without an obviously diagnostic error.

⬜ Phase 9 — Public API, CLI & Conformance Harness Integration §21

Objectives

Assemble the top-level public surface (a single re-exporting facade over rsa-core/rsa-keys), ship rsa-cli, and wire the full conformance/fuzz/timing suite (§26) as the release gate (ADR-16) — the point at which the system is a usable, audited product rather than a set of crates.

Deliverable

A published rsa facade crate plus rsa-cli binary; a green conformance suite covering every bucket named in §26; a green 24-hour fuzz canary; both JWT interop examples producing tokens independently verifiable by a third-party JOSE library.

Acceptance
  • The full conformance suite (§26) completes in ≤ 10 minutes on an 8-core CI runner (§4, M11) with zero failing vectors across all buckets.
  • rsa-cli keygen --bits 2048 followed by sign/verify round-trips successfully in a shell script smoke test.
  • The 24-hour fuzz canary (fuzz.canary_24h, M12-adjacent) completes with zero panics across all six fuzz targets.
  • A JWT signed via jwt_rs256.rs verifies successfully against an independent, external JOSE library (differential interop check).

Fixture Purpose Expected Output

Pitfalls
  • A facade re-export that accidentally exposes an internal-only type (e.g. MontgomeryParams, §11) widens the public API surface beyond what ADR-19's SemVer policy intends to commit to — audit the facade's pub use list against §11's "internal vs. public" annotations explicitly.
  • A CLI that swallows a cryptographic RsaError into a generic "something went wrong" message loses the operator-actionable distinction between, say, KeyGenerationExhausted (retry) and a malformed key file (fix the input) — map RsaError variants to distinct CLI exit codes.
  • Running the fuzz canary for only a few minutes in CI (rather than the full 24-hour job on a scheduled/nightly runner) gives false confidence — the 24h/30d canaries (M12) must run on a schedule separate from the fast per-PR CI gate.
