4.1 Worked complexity derivation

W×H image, C connected components, L text lines, T recognizer time-steps/line, A alphabet size, B beam width:

  • Otsu: one histogram pass O(W·H) + O(256) threshold scan.
  • Sauvola (integral): integral image O(W·H); per-pixel O(1) window mean/std ⇒ O(W·H) independent of window size (vs naïve O(W·H·w²)).
  • Connected components: two-pass union-find, O(W·H·α) with path-compression+union-by-rank.
  • Deskew: N candidate angles × projection O(W·H) ⇒ O(N·W·H); coarse-to-fine cuts N.
  • CNN encode: convolution-as-GEMM via #349; per layer O(H·W·Cin·Cout·k²) → near-peak GEMM.
  • CTC forward-backward: lattice of 2·|label|+1 states × T frames ⇒ O(T·|label|) per line, log-space.
  • Greedy decode: O(T·A) argmax + O(T) collapse. Prefix-beam: O(T·B·A) extend + LM lookup.
  • Edit-distance correction: DAWG-walk with cutoff k ⇒ pruned O(|word|·k·branching). Constants dominated by #349 GEMM (CNN/BiLSTM) and #389 filter kernels; per-page cost is CNN-encode-bound at high DPI, layout-bound at low DPI.

4.2 The one defining property

OCR is a coordinate-preserving probabilistic transduction from a 2-D raster to a 1-D symbol sequence under a learned prior. Everything else follows: because it is coordinate-preserving, every box must invert back to source pixels (I1/I15, MM2); because it is probabilistic transduction, the recognizer emits posteriors, not characters, and CTC marginalizes the unknown alignment (MM3); because it runs under a learned prior, decode fuses an LM that can be tuned or removed (MM6). The single number that defines success is character error rate (CER) against ground truth — every other target in the table exists to protect it. These targets are gated as M1…M15 in §32.1; the §32.1 table is the CI-enforced view of this constraints table.

36. Back-of-Envelope Capacity Model

Numbers an expert computes before designing, each derived from the System Constraints (§4) with the formula shown. Assumptions: 300 DPI, A4 (8.27 × 11.69 in), Gray8, neural engine, the §4 targets.

  • (1) Pixels per page = (300 dpi)² × area = 300² × 8.27 × 11.69 in² = 90,000 × 96.7 ≈ 8.7 M px. → a page bitmap is the unit of work; everything else scales off this.
  • (2) Page bitmap memory = pixels × 1 byte (Gray8) = 8.7 M × 1 B ≈ 8.3 MB per page; the F32 normalized working copy of one line, not the page, is what the recognizer holds (memory ceiling O(W·H) page, §4). → confirms "stream pages, don't materialize batches."
  • (3) Integral-image memory = pixels × (sum u64 + sqsum u64) = 8.7 M × 16 B ≈ 139 MB. → the integral image, not the bitmap, dominates binarization memory; it is built then dropped before layout (MM1). A u32 sum would overflow at ~16 M px (I13) — hence u64 (§13.6).
  • (4) Connected-component pass cost = O(W·H·α(n)) ≈ pixels × ~2 (two-pass union-find) ≈ 8.7 M × 2 ≈ 17 M pixel-ops; at ~1 Gops/s effective for a memory-bound scan ≈ 17 ms. → CC is a real but sub-dominant slice; the cost driver at high DPI is CNN encode (§4.1, §33).
  • (5) Text lines per page ≈ page text-height ÷ line pitch. At 11 pt body, 1.2× leading, 300 dpi: line pitch ≈ 11 × 1.2 / 72 × 300 ≈ 55 px; usable text height ≈ 10 in × 300 = 3000 px ⇒ ≈ 55 lines/page. → the per-line parallel work-unit count; sets the thread-pool granularity (I11).
  • (6) Recognizer frames per line T = line width ÷ CNN total stride. Line width ≈ 6.5 in × 300 = 1950 px; typical CRNN downsample stride ≈ 4 ⇒ T ≈ 1950/4 ≈ 490 frames/line. → drives both CTC cost (7) and posterior memory (8).
  • (7) CTC forward-backward states per line = (2|l|+1) × T. A ~75-char line ⇒ (2×75+1) × 490 ≈ 151 × 490 ≈ 74 K lattice cells/line, O(T·|label|) (§4.1). → tiny vs CNN GEMM; confirms CTC is not the bottleneck, but its per-frame state update must be alloc-free (§32).
  • (8) Posterior memory per line = T × (|A|+1) × 4 B. Latin alphabet+digits+punct ≈ 90 symbols + blank ⇒ 490 × 91 × 4 B ≈ 178 KB/line. → tiny; 55 lines × 178 KB ≈ 9.8 MB if all held, but lines stream, so peak is O(threads × 178 KB).
  • (9) Throughput floor = §4 target ≥ 1 page/s single core ⇒ per-page budget ≤ 1000 ms; spread over ~55 lines ⇒ ≤ 18 ms/line amortized, consistent with the ≤30 ms/line latency target (§4) once layout/binarize overhead is added.
  • (10) Multi-core throughput = single-core × cores × scaling. §4 promises ≥ 0.8× linear ⇒ on 8 cores ≈ 1 × 8 × 0.8 ≈ 6.4 pages/s (lines are embarrassingly parallel, I11, §33).
  • (11) Neural model memory = §4 ceiling ≤ 20 MB (CNN+BiLSTM, f32). At 4 B/param ⇒ ≈ 5 M parameters budget — a small VGG-style CNN + a modest BiLSTM, mmap-shared read-only across all page/line tasks (§33).
  • (12) CNN encode cost (dominant term) = Σ_layers O(H·W·Cin·Cout·k²). One representative 3×3 layer at H·W ≈ 32×1950 (after early pooling), Cin=Cout=64 ⇒ 32×1950×64×64×9 ≈ 2.3 Gflop/layer; a ~6-conv stack ⇒ O(10 Gflop)/line via #349 GEMM. → this, not CTC or CC, is why §33 calls high-DPI pages "CNN-bound" and why batching lines into one GEMM (§24.7, §32) is the biggest single win.

36.1 What the numbers force (design consequences)

The capacity model is not decoration — each number closes off a design option:

  • (3) forces u64 integral sums. 8.7 M px × max gray 255 overflows u32 at ~16 M px; the integral image must use u64 (I13, §13.6) — a u32 would silently wrap on a large page.
  • (2)+(8) force page-streaming, not batch materialization. One 8.3 MB page plus O(threads × 178 KB) posteriors is bounded; materializing N pages × (bitmap+posteriors) is not (principle 12). The architecture streams pages by necessity, not preference.
  • (12) forces line-batching as the headline optimization. With CNN encode at O(10 Gflop)/line and 55 lines/page, the only way to hit M5 (≥1 page/s) on CPU is to batch lines into one #349 GEMM (§24.7) — per-line GEMM calls leave the FPU idle on call overhead.
  • (6) forces a documented receptive-field map. T ≈ W/stride ties every frame to an x-range; without the exact stride arithmetic (§19.2) glyph boxes (I1) cannot be back-projected — the capacity number is the box-provenance contract.
  • (10) sets the parallelism ceiling. ≥0.8× linear to 8 cores ≈ 6.4 pages/s is the realistic single-box throughput; beyond that the limit is memory bandwidth on pixel reads, and the lever is multi-process over pages (§33), not more threads per page.
