Alternative Architectures (Roads Not Taken)

Fundamentally different designs for the same goal — not parameter tweaks.

ALT1 — Pattern-matching / peephole decompiler (no SSA, no data-flow).

instructions ─► template matcher ─► canned C snippets ─► concatenate

Wins for very regular single-compiler output (one toolchain at -O0) where templates cover most code. Embodied by early/simple decompilers and many "quick C" plugins. Rejected because it breaks on optimized/irregular code and cannot prove semantics (no oracle, contra I4).

ALT2 — Symbolic-execution-driven decompiler.

entry ─► path explorer ─► per-path constraints ─► summarize ─► output

Wins for vulnerability research where feasible-path reasoning matters more than readable whole-function C. Embodied by angr. Rejected here because path explosion makes whole-function readable output impractical, and the machinery is far heavier than this goal (cf. Comparative Architecture Table).

ALT3 — LLVM-IR-backed decompiler.

instructions ─► lift to LLVM IR ─► LLVM opt passes ─► LLVM C backend ─► C

Wins when you want to reuse LLVM's optimizer and possibly recompile the result. Embodied by RetDec / mctoll. Rejected because the LLVM dependency is heavy, LLVM IR's abstraction discards machine detail useful for RE, and output quality is hostage to LLVM's C backend (contra ADR-002).

ALT4 — Whole-program / interprocedural decompiler.

call graph ─► interprocedural data-flow + type propagation across calls ─► per-fn output

Wins when cross-function type/alias precision is the product (production tools trend this way). Embodied by Hex-Rays/Ghidra at scale. Rejected (deferred) because per-function isolation (I11) is what keeps the basic tool simple and linearly scalable; whole-program is a deferred enhancement (see Deferred Features Register).
