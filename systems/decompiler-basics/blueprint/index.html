335 — Decompiler Basics from Scratch

Project Number: 335

Project Name: Decompiler Basics from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build a basic decompiler: lift a disassembled function (instructions + CFG from #334) into a register-transfer intermediate representation (IR), run data-flow analyses, recover types and variables, structure the unstructured CFG into high-level control flow (if/else, loops, switch), and emit readable pseudo-C. Input = #334's Vec<Instruction> + Cfg per function (symbolized via #333); output = an AST + pseudo-C listing approximating the original source semantics.

In scope: instruction→IR lifting (per-opcode semantics for the #334 x86-64 subset), CFG import + cleanup, SSA construction (dominance frontiers + φ), data-flow (def-use, liveness, reaching defs, constant/copy propagation, dead-code elimination), simple expression building + algebraic simplification, structural analysis (Cifuentes-style: natural loops, 2-/n-way conditionals, switch) with a goto fallback for irreducible graphs, basic type recovery (size + signedness + pointer-ness via constraints), variable recovery (stack slots + registers → named locals), and pseudo-C emission.

Explicit non-goals (PhaseDeferred("FINAL_BLUEPRINT §X.Y")): disassembly (input from #334, §1 non-goal); precise C++ class/template/exception recovery (PhaseDeferred("Full struct/array/C++ type recovery")); full type inference à la a production decompiler (Hex-Rays/Ghidra parity) (PhaseDeferred("Full struct/array/C++ type recovery")); recompilable/byte-exact output — output is readable, not a guaranteed-correct recompile (§1 non-goal); data-flow across function boundaries / whole-program (PhaseDeferred("Interprocedural / whole-program analysis")); obfuscation removal (see Threat Model).

Deployment model: library crate (decomp-core) + decomp CLI: takes a binary (via #333/#334) + a function address/name, prints pseudo-C + IR/CFG dumps. The capstone of the 333→334→335 reverse-engineering pipeline.

Target users: RE / security analysts reading stripped binaries; compiler/PL learners seeing codegen "in reverse"; anyone building the full pipeline 333→334→335.

Phase 0 deliverable (crates/modules):

  1. dec-ir — IR types: IrInsn, IrExpr, IrStmt, Value, IrCfg, Type.
  2. dec-lift — per-instruction lifter (#334 Instruction → IR with explicit flags/effects).
  3. dec-cfg — import #334 Cfg; compute dominators.
  4. dec-emit — minimal IR/pseudo-C printer.
  5. dec-cli (decomp) — pipeline a single function to IR + naive listing.

Later phases unlock: SSA (Phase 4), data-flow + propagation + DCE (Phase 5), expression building (Phase 6), type recovery (Phase 7), structuring (Phase 8–9), variable naming + emission polish (Phase 10), validation via re-disassembly/semantics (Phase 11–12).

Timeline: Phase 0 = 6–14 weeks; full = 6–9 months (structuring + type recovery are the long poles).

Recommended language: Rust (edition 2021, ≥1.78). Rationale: (a) algebraic data types model IR/AST/types precisely with exhaustive match; (b) the same workspace already holds #333 BinaryImage and #334 Instruction/Cfg — zero serialization across the pipeline; (c) ownership makes IR/SSA graph transforms explicit and aliasing-safe; (d) it shares analyses (SSA, dominators, DCE) conceptually with #30/#143/#43, reusable here; (e) proptest/fuzzing validate transforms preserve semantics. Locked ADR-001.

Prerequisites: SSA + dominance (Cytron et al.); data-flow analysis (Dragon §9); control-flow structuring (Cifuentes thesis); x86-64 instruction semantics (flags!); type systems basics (#238); #334 Instruction/Cfg; Rust enums/ownership.

2. Why Build This

  • Unique knowledge: the inverse of a compiler — recovering structure, types, and intent from flat machine code. It forces deep understanding of SSA, data-flow, dominance, and control-flow structuring all at once.
  • Historical/architectural: decompilation (Cifuentes 1994 → Hex-Rays → Ghidra) is RE's holy grail; even a "basic" decompiler exercises the full analysis stack that production tools scale up.
  • Engineering muscles: IR design; SSA construction (dominance frontiers, φ placement); fixed-point data-flow; type-constraint solving; the genuinely hard structuring problem (turning gotos into loops/ifs); semantics-preserving transforms.
  • Production concepts: IR invariants, fixed-point convergence, semantic preservation, irreducible-CFG handling, deterministic output.
  • Cross-links: #334 Disassembler (input), #333 ELF/PE (symbols/types hints), #143 SSA-Based Optimizer + #43 AST Optimizer + #30 Compiler (shared SSA/data-flow/AST machinery, run in reverse), #238 Hindley–Milner (type-recovery analogue), #51 JIT (codegen counterpart), #74 Debugger (variable/frame info).
  • Calibration: after this you understand compilers bidirectionally; you can read optimized assembly and reconstruct its source logic, and you grasp why decompilation is undecidable-in-general yet practical.

What Mastery Looks Like (competencies gained, each tied to a phase):

  • Flag-accurate lifting (Phase 0, Phase 2) — read any x86-64 sequence and state its exact effect on registers, memory, and EFLAGS, and know why dropped flags are the #1 decompiler bug.
  • SSA from first principles (Phase 1, Phase 4) — dominators, iterated dominance frontiers, φ-placement and renaming, verified — the machinery every modern compiler shares.
  • Monotone data-flow to a fixed point (Phase 5) — design a lattice + transfer function and prove it converges; recognize when an analysis would hang.
  • Semantics-preserving transformation (Phase 5, Phase 6, Phase 11) — prove a rewrite preserves behavior against a reference oracle — the discipline separating a trustworthy decompiler from a plausible one.
  • Control-flow structuring (Phase 8, Phase 9) — turn an unstructured CFG into loops/conditionals/switch, and know precisely when irreducibility forces a goto.
  • Constraint-based type recovery (Phase 7) — infer size/sign/pointer-ness by unification and know when to widen to unknown rather than guess.
  • Verifiable tools on untrusted input (Phase 12) — never-panic robustness, fuzzing, per-function isolation, deterministic output.

Per-box: Lifter — each machine instruction → explicit IR statements, including flag effects (the part beginners forget); memory accesses become typed loads/stores. CFG+Dominators — import #334's CFG, compute immediate dominators + dominance frontiers (Lengauer–Tarjan / Cooper-Harvey-Kennedy). SSA — place φ at dominance frontiers, rename to versioned values (Cytron). Data-flow — def-use chains, liveness, reaching defs; constant/copy propagation; dead-code elimination (esp. eliminating dead flag computations). Expression building — fold single-use SSA values into nested expressions; recover relational ops from cmp+flag+jcc patterns. Type recovery — generate size/sign/pointer constraints from usage, solve, assign types to stack slots + registers → variables. Structuring — turn the CFG into loops/conditionals/switch via dominators + interval analysis; emit goto only for genuinely irreducible regions. Emission — render the structured AST as readable pseudo-C with recovered names.

6. Design Principles

  1. Lift semantics fully, including flags. Every instruction's effect on registers, memory, and EFLAGS is modeled explicitly; flag-defining ops + the consuming jcc are later folded into a relational. Violation: dropping flags → wrong conditionals (the #1 beginner bug).
  2. SSA is the substrate. All analyses run on SSA; transforms preserve SSA + semantics. Violation: ad-hoc def-use → buggy propagation.
  3. Semantics preservation is the invariant. Every transform (propagation, DCE, structuring) preserves observable behavior; validated against an emulator (Phase 2/11). Violation: "decompiled" code that doesn't match the binary.
  4. Structure reducible graphs fully; goto only when forced. Reducible CFGs → goto-free loops/ifs; irreducible → minimal, localized gotos. Tradeoff: structuring complexity. Violation: goto-spaghetti output (useless) OR wrong structure (incorrect).
  5. Determinism. Same input ⇒ same IR/AST/pseudo-C; ordered φ, ordered names, stable iteration. Violation: non-reproducible diffs.
  6. Fixed-point analyses must converge. Monotone lattices + bounded iteration; every data-flow pass terminates. Violation: infinite analysis loop.
  7. Type recovery is best-effort + conservative. Recover size/sign/pointer where constraints allow; default to int/void*/unknown rather than guess wrong. Violation: confidently-wrong types mislead the analyst.
  8. Output is an approximation, labeled as such. Pseudo-C aids understanding; it is not a guaranteed recompile. Violation: false promise of correctness.
  9. Never panic on real #334 input. Odd/partial CFGs, indirect jumps, unknown instructions → typed handling (__unknown() intrinsic), not a crash. Violation: one weird function kills the tool.
  10. Idiom recovery over literal translation. Recognize compiler idioms (xor eax,eax→0, lea as arithmetic, test r,r; jz→if(!r), multiply-by-reciprocal→division). Violation: unreadable literal output.
  11. Per-function isolation. Each function decompiles independently (arena-scoped); no global mutable state. Violation: cross-function corruption; no parallelism.
  12. Layered + inspectable. Each stage (IR, SSA, post-DCE, structured AST) is dumpable. Violation: a black box no one can debug.

8. Domain Model

8.1 IR grammar (low register-transfer IR, SSA-able)

IrStmt  := Assign(Value, IrExpr) | Store(addr:IrExpr, val:IrExpr, size)
         | Branch(cond:IrExpr, t:Label, f:Label) | Jump(Label) | Call(target, args) | Ret(Option<IrExpr>)
         | Phi(Value, [(Value,Label)]) | Nop | Unknown(mnemonic)        // I9 fallback
IrExpr  := Val(Value) | Const(i128, size) | Load(addr, size)
         | Bin(op, IrExpr, IrExpr) | Un(op, IrExpr) | Cast(kind, IrExpr, to:Type)
         | Cmp(relop, IrExpr, IrExpr)
Value   := Reg(name, ssa_version) | Tmp(id) | StackSlot(off) | Flag(which, ssa_version)
op      := add|sub|mul|udiv|sdiv|and|or|xor|shl|lshr|ashr|...
relop   := eq|ne|ult| slt|ule|sle|...    ; recovered from flags + jcc (I1)

8.2 Flag modeling (the crux, I1)

x86 `cmp a,b` ⇒  ZF = (a-b)==0 ; SF = sign(a-b) ; CF/OF = borrow/overflow
   `jz L`     ⇒  Branch(ZF, L, fall)
fold (Phase 6):  cmp a,b ; jz L      →  Branch(Cmp(eq,a,b), L, fall)
            cmp a,b ; jl L      →  Branch(Cmp(slt,a,b), L, fall)   // SF≠OF
            test r,r ; jz L     →  Branch(Cmp(eq,r,0), L, fall)
dead flags after folding → eliminated by DCE (I11)

8.3 SSA + dominators (worked)

CFG:  B0 → {B1,B2} → B3        x defined in B1 and B2, used in B3
idom: idom(B3)=B0 ; DF(B1)=DF(B2)={B3}
φ:    B3: x3 = φ(x1:B1, x2:B2)   (placed at iterated DF of x's defs, I3)
rename: x@B1→x1, x@B2→x2, x@B3 use→x3

8.4 Structuring (Cifuentes intervals → high-level)

loop:    back-edge (n→h, h dom n) → natural loop {h..n}; pre-test→while, post-test→do-while
2-way:   block with two succs, common post-dominator m → if(cond){then}[else]{...}; join m
n-way:   jump-table block → switch(idx){ case k: ... }
seq:     single-succ chains → statement sequence
fallback: irreducible (no single header) → node-splitting or labeled goto (I8)

8.5 Worked example (function → pseudo-C)

asm (from #334):
  push rbp; mov rbp,rsp; mov [rbp-4],edi      ; param n → local
  cmp [rbp-4],0; jle .L2
  mov eax,[rbp-4]; imul eax,[rbp-4]           ; n*n
  jmp .L3
.L2: mov eax,0
.L3: pop rbp; ret
lift+SSA+fold+structure+type →
  int f(int n) {            // type recovered: param int, return int
      if (n > 0)            // cmp+jle folded → relational (I1), then-branch
          return n * n;     // imul idiom
      else
          return 0;         // xor/mov 0 idiom
  }

8.6 Malformed / hard-case examples

  • Unknown instruction from #334 ((bad)/unsupported) → IrStmt::Unknown → emitted as __unknown(/*opcode*/); analysis treats it as clobbering all (conservative, I9).
  • Indirect call (call rax) → Call(__indirect(rax), <unknown args>); arg recovery best-effort.
  • Irreducible CFG (overlapping loops, no single header) → node-split or localized goto L; (I8), still correct.
  • Self-reference via stack (recursion) → fine (per-function; call is opaque).
  • Optimized division-by-constant (multiply-by-magic + shift) → idiom-recognized → x / k (best-effort), else literal.
  • Variadic/odd calling convention → args under-recovered, flagged.
  • Tail call (jmp func) → return func(...); (best-effort) or goto/__tailcall.

Phase 0 — Skeleton, IR, Lifter (integer subset), CFG Import, Naive Emission, CLI

0.1 Objectives

Define the IR (dec-ir), lift the #334 integer subset to IR with explicit flag effects (I1), import the CFG + compute dominators, and emit a naive (unstructured, goto-per-edge) listing. Constraint: flags are modeled from the very first instruction lifted.

0.2 Detailed Implementation Steps

  • dec-ir: define IrStmt/IrExpr/Value/Type/IrCfg (§11) as #[non_exhaustive] enums (ADR-002, ADR-021); IrExpr/IrStmt carry no SSA versions yet (versions added in Phase 4). Each Value::Flag{which} is a first-class lvalue from day 0 (I1, MM2).
  • dec-lift::x64: one lifting rule per opcode in the #334 integer subset — mov/add/sub/lea/cmp/test/jmp/jcc/call/ret/push/pop → IR (Appendix D.2 is the normative table). lea lifts to arithmetic (add/shl), never a Load (pitfall 0.6). Sub-register writes (al/ax/eax) modeled as read-modify-write or conservative widen.
  • dec-lift::flags: each flag-defining op emits explicit Assign(Flag(ZF/SF/CF/OF), …) derived from Intel SDM semantics (ADR-003, I1); jcc lifts to Branch(Flag-expr, t, f), deferring relational folding to Phase 6 (MM2).
  • dec-lift::mem: memory operands → Load{addr,size} / Store{addr,val,size}; address expressions ([base+index*scale+disp]) lifted as IR arithmetic so later analyses see them uniformly.
  • dec-cfg::import from #334 Cfg; prune unreachable blocks first (pitfall 1.6); dominators via Cooper-Harvey-Kennedy (ADR-004, M4); store idom + child lists for the Phase 4 rename walk.
  • dec-emit: dump IR; naive C with a goto/label per CFG edge (correct, ugly) — the unstructured baseline Phase 8 replaces.
  • dec-cli: decomp fn <binary> <addr|name> → IR + naive listing, driving the full #333→#334→#335 pipeline (Appendix O); clap subcommands per ADR-017.

0.3 Deliverable

  • Lifts the integer subset; dec-emu (stub) confirms ≥10 hand vectors covering every opcode in Appendix D.2 (I1 spot-check, fixtures lift/mov_arith/lift/cmp_jcc/lift/mem_loadstore).
  • Naive output's control flow matches #334 CFG exactly (fixture pseudoc/naive_goto).
  • Dominator tree correct on fixtures cfg/idom_diamond/cfg/idom_loop (vs hand-computed).
  • Fuzz smoke: any #334 input → 0 panics over ≥1e5 seed executions (I9).

Phase 4 — SSA Construction (φ placement + renaming)

4.1 Objectives

Transform the IR into SSA: place φ at iterated dominance frontiers (I3), rename values to versioned defs (I2), verify single-assignment. SSA is the substrate for all later analyses (principle 2).

4.2 Detailed Implementation Steps

  • For each SSA variable — register, flag (MM2; forgetting flags here is the classic bug, 4.6), and stack-slot — collect def sites across blocks (Cytron et al. 1991, ADR-004).
  • Place φ at the iterated dominance frontier of each variable's def-set (Appendix H is the worked loop case); iterate because a φ is itself a def that can force more φ (I3, pitfall 4.6).
  • Rename via a dominator-tree DFS with per-variable version stacks: each def pushes a version, each use reads the stack top, φ operands are filled from the predecessor's exit version (Appendix P.1).
  • Keep memory out of scalar SSA — model it as Load/Store; memory-SSA is deferred (Deferred Features Register, pitfall 4.6).
  • dec-ssa::verify: assert exactly-one-def (I2) and φ-arity = predecessor count (I3); a violation is E.SSA_VERIFY (Appendix K.2), a hard CI gate — bad SSA poisons every later analysis (4.9, MM3).

4.3 Deliverable

decomp ssa <fn> prints SSA-form IR with φ nodes; verifier passes.

4.4 Acceptance Criteria

SSA verifier passes on 100% of fixtures (I2, fixture ssa/diamond_phi/ssa/loop_phi/ssa/nested/ssa/flags_ssa); φ count matches the iterated-DF count exactly (M5, I3); renaming correct vs the hand-traced example, byte-for-byte on ssa/golden_* (§8.3).

Phase 5 — Data-Flow: Liveness, Reaching Defs, Const/Copy Propagation, DCE

5.1 Objectives

Run the analysis suite on SSA via a monotone-lattice worklist (I5): liveness, reaching defs, def-use chains; then constant + copy propagation and dead-code elimination — crucially killing dead flag computations (I11). Every transform preserves semantics (I4).

5.2 Detailed Implementation Steps

  • dec-dataflow::lattice + worklist fixed-point framework behind the Analysis trait (ADR-005, §11): a monotone transfer over a finite-height lattice → guaranteed least fixed point (I5, MM5; Appendix I is the lattice catalog).
  • Liveness (backward, bitset lattice) + reaching defs (forward) + def-use chains; SSA makes each per-value rather than per-program-point, shrinking the work (MM3).
  • Constant propagation (fold operands that meet to a single Const) and copy propagation (collapse x = y), both safe under SSA because each value has one def (5.6).
  • dce: remove defs with no live use — trivial in SSA — and crucially eliminate dead EFLAGS left after relational folding (I11, M7; liveness must include flags or DCE wrongly drops a live flag, 5.6).
  • Re-run dec-ssa::verify and the emulator before/after each pass (I4, ADR-012): an injected unsound transform must be caught (Phase 2), making every optimization provably behavior-preserving (MM7).
  • Enforce monotonicity + an iteration cap of height × |blocks| (E4); exceeding it raises E.NONCONVERGENCE rather than hanging (I5, 5.6).

5.3 Deliverable

decomp ssa --opt <fn> shows propagated, DCE'd SSA — far fewer temporaries; dead flags gone.

5.4 Acceptance Criteria

Analyses converge within the height × |blocks| iteration cap (I5, fixture dataflow/nonconverge_guard); propagation+DCE preserve semantics on the emulator (I4, fixtures dataflow/const_prop/dataflow/copy_prop); dead-flag elimination removes ≥90% of lifted flag defs (M7, fixture dataflow/dce_flags); no live code removed (I11, 0 regressions on dataflow/liveness).

Recover basic types via constraint generation + solving (I10): operand sizes, signedness (from signed vs unsigned ops/branches), pointer-ness (from dereferences + pointer arithmetic). Conservative: default to unknown/int rather than guess wrong (principle 7).

7.2 Detailed Implementation Steps

  • dec-types::constraints: emit constraints from usage (load/store size → width; idiv/jl→signed; [p+k] deref→p:ptr; p+i*sz→element size).
  • dec-types::solve: unify (union-find over type vars); conflict → widen to unknown (I10), not error.
  • dec-types::recover: assign types to variables; propagate to params/return (ABI-aware).

7.3 Deliverable

decomp fn shows typed locals/params (int*, unsigned, char, long) where constraints determine them; unknown otherwise.

7.4 Acceptance Criteria

Recovered types consistent with all uses (0 unresolved conflicts survive, I10, fixture types/conflict_widen); matches source size/sign/ptr on fixtures types/ptr_deref/types/array_index/types/signed_div/types/width_from_load; conflicts safely widen to unknown every time (I10).

7.5 Conformance Fixtures

Fixture Purpose Expected

types/array_index p+i*sz deref p : ptr(elem sz), i : int
types/signed_div idiv/signed branch operand typed signed

7.6 Pitfalls

  • Union of conflicting types (int used as ptr) → widen, don't pick arbitrarily (I10).
  • Signedness from a single op is weak → require consistent evidence.
  • Pointer vs integer arithmetic ambiguity → deref is the strong signal.
  • Struct/array recovery beyond element size → out of scope (PhaseDeferred("Full struct/array/C++ type recovery")).

7.7 Performance Concerns

Union-find near-linear; constraints proportional to uses. Per-function.

7.8 Edge Cases

  • Unions / reinterpret casts → one storage, conflicting types → widen to unknown (I10).
  • void* / opaque pointers → pointer-ness known, pointee unknown.
  • Sign-extended loads (movsx) → narrower signed source inferred (Appendix F).
  • Float/int reinterpretation (movd/bit-cast) → distinct type domains, no unification.
  • Type used before its defining constraint → defer to fixed-point unification, not first-seen.

7.9 Failure Analysis

Confidently-wrong types mislead analysts → conservatism (widen to unknown) + consistency check (I10); differential vs source types reported, not gated hard (recovery is best-effort).

7.10 Operational Notes

Metrics: types_recovered, type_conflict(→widen), unknown_types. Output annotates confidence; int/void* are honest defaults.

Phase 8 — Structuring I: Loops + 2-Way Conditionals (reducible)

8.1 Objectives

Turn reducible CFG regions into structured loops (while/do-while/for) and if/else using dominators + intervals (I7), producing goto-free output for reducible graphs.

8.2 Detailed Implementation Steps

  • dec-struct::loops: identify natural loops from back-edges (latch → header where header dominates latch, MM6; Appendix E catalog); classify pre-test (while) vs post-test (do-while) by where the exit test sits; recover for (init/cond/step) only when init+step are clearly loop-local (8.6); mark loop-exit edges → break, latch edges → continue via post-dominators.
  • dec-struct::conditionals: a 2-way branch with a common immediate post-dominator m → if/else joining at m; collapse to if when one arm is empty; recover &&/|| by detecting short-circuit CFG chains feeding one target (8.6).
  • Build the Ast (§11) bottom-up over the interval/dominator tree: innermost loops + conditionals collapse to single Ast nodes, then their parents, until the whole function is one tree (Appendix E; this ordering is why correctness stays invariant, Hard Question 20).
  • Validate the structured form's IR against the emulator (I4): structure changes presentation, never behavior (MM7). Reducible regions must emit zero gotos (I7, M9); anything else is a structuring bug, not a goto license (8.9).

8.3 Deliverable

decomp struct <fn> emits structured AST → readable while/for/if with no gotos on reducible functions.

8.4 Acceptance Criteria

Reducible fixtures → 0 gotos (I7, M9, fixtures struct/while/struct/do_while/struct/for); loop/conditional shapes match source on fixture struct/if_else; structured output semantically equivalent to CFG (emulator, I4, fixture struct/golden_*).

8.5 Conformance Fixtures

Fixture Purpose Expected
struct/while / do_while pre/post-test loops correct loop kind; 0 gotos (I7, M9)
struct/for for-loop recovery init/cond/step recovered when loop-local
struct/if_else 2-way + join if/else at the immediate post-dominator
struct/short_circuit &&/`
struct/break_continue loop exits/latches break/continue via post-dominators
struct/golden_* golden pseudo-C emulator-equivalent to CFG (I4)

8.6 Pitfalls

  • Mistaking a loop exit for break vs normal exit → use post-dominators.
  • Short-circuit &&/|| look like nested ifs → recover compound conditions or accept nested ifs.
  • Multiple loop exits → may need a flag/goto for non-trivial exits.
  • for over-fitting → only when init/step are clearly loop-local.

8.7 Performance Concerns

Structuring is O(blocks) over the dominator/interval tree. Per-function.

8.8 Edge Cases

  • Infinite loop (no exit edge) → while (1) / for (;;).
  • Empty loop body → preserved (may be a delay/spin); not deleted.
  • Nested loops sharing an exit → post-dominator analysis disambiguates break targets.
  • continue to a latch vs fall-through → classified by edge target (latch = continue).
  • Multiple loop exits → secondary exits may need a flag or localized goto (defer to Phase 9 if non-trivial).

8.9 Failure Analysis

Wrong structure = wrong (or unreadable) code → emulator equivalence (I4) + goto-count check on reducible (I7).

8.10 Operational Notes

Metrics: loops_structured, conditionals_structured, unexpected_goto(0 on reducible). Structuring tree dumpable for debugging.

Compatibility & Versioning

SemVer (ADR-021) on Type, IrExpr, IrStmt, Ast, and the analysis traits. Rules: additive IR ops / expr kinds / AST nodes / type variants via #[non_exhaustive] → minor; variant-semantics change / field removal / trait-signature change → major. The pseudo-C output format is versioned independently (it is for humans; golden tests track it). The lifter's IR semantics are stable within a major version (a given instruction always lifts to behaviorally-equivalent IR). The decompiler pins #333 binparse-core and #334 disasm-core at compatible major versions; their API bumps cascade here. Output always carries an "approximation — not recompilable" header regardless of version (principle 8). New idioms/type rules/structuring patterns are additive (minor) and never silently change previously-correct output's semantics, only its readability.

  • Unit — per lifter rule (incl. flags), SSA φ/rename, each data-flow pass, each structuring pattern, type constraints.
  • Property (proptest) — SSA verifier (single-def, I2) on random CFGs; data-flow monotonicity/convergence (I5); "any (instrs,CFG) → output or typed error, never panic" (I9); determinism (I6).

Scalability Analysis

The unit is a function; scaling is fan-out across functions (independent, arena-isolated, Send — embarrassingly parallel; a whole binary's functions decompile concurrently). Bottlenecks: (1) SSA + data-flow on very large functions (super-linear in pathological cases — bounded by caps + SSA's sparsity); (2) structuring on irreducible/huge CFGs (node-split cap → goto); (3) type-constraint solving (near-linear union-find); (4) upstream #334 decode. Ceilings: a single 10k-instruction function's SSA/analyses dominate memory (arena-bounded, freed after); interprocedural/whole-program analysis is explicitly out of scope (PhaseDeferred("Interprocedural / whole-program analysis")) — keeping each function independent is what makes the tool scale. No shared mutable state, no persistence → linear with cores. Memory is per-function and reclaimed, so peak tracks the largest function, not the whole binary.

Mental Models & First Principles

The compressed insights an expert decompiler engineer holds. Each: the model, what it predicts, the bug class you write without it, and where this blueprint applies it.

  • MM1 — A decompiler is a compiler run backwards. Lifting = parsing; SSA/data-flow = the middle-end; structuring = the inverse of lowering; emission = the inverse of codegen. Predicts: every compiler analysis has a decompiler dual. Without it: you reinvent SSA/data-flow badly instead of borrowing 40 years of theory. Applied: §3, Phase 4–8.
  • MM2 — Flags are state; drop them and you lose the conditionals. cmp writes ZF/SF/CF/OF; jcc reads them. Predicts: the sign of every recovered </> lives in which jcc consumed the flags. Without it: inverted/garbage conditions — the #1 beginner bug. Applied: I1, §8.2, Appendix D.3.
  • MM3 — SSA makes data-flow sparse. One def per value makes def-use explicit; propagation/DCE become near-trivial. Predicts: O(program-points) analyses become O(values). Without it: quadratic def-use rebuilds and propagation across redefinitions. Applied: I2, Phase 4–5, Appendix I.
  • MM4 — φ lives at the iterated dominance frontier. A value defined in several blocks needs a merge exactly where their dominance ends. Predicts: too few φ = wrong values, too many = noise. Without it: ad-hoc φ that is both incorrect and bloated. Applied: I3, Phase 1/4, Appendix H.
  • MM5 — A monotone transfer on a finite-height lattice always terminates. Predicts: convergence is bounded by height × |blocks|; a hang means the transfer isn't monotone. Without it: data-flow that loops forever on adversarial input. Applied: I5, Phase 5, Appendix I.
  • MM6 — Reducibility is the line between structured and goto. A reducible CFG collapses to one node via interval analysis → goto-free; irreducible needs node-split or goto. Predicts: which functions can be made pretty. Without it: spaghetti output or wrong structure. Applied: I7/I8, Phase 8/9.
  • MM7 — Correctness ≠ resemblance. The contract is semantic equivalence to the binary, not similarity to the lost source. Predicts: optimized code legitimately decompiles to correct-but-different structure. Without it: you "fix" output to look like source and break it. Applied: I4, Phase 11, Appendix N.2.
  • MM8 — Types are evidence, not truth. Each use is a constraint; the type is the unification of all of them; conflict means widen, not pick. Predicts: confidently-wrong types come from trusting one weak signal. Without it: misleading declarations. Applied: I10, Phase 7, Appendix F.
  • MM9 — Single-use folding turns assembly into expressions. Substituting a value defined once and used once into its use builds nested expressions. Predicts: readability scales with safe fold opportunities. Without it: flat three-address soup. Applied: Phase 6, §6.2.
  • MM10 — Per-function isolation is the scaling primitive. Each function is an independent, arena-scoped, Send unit. Predicts: throughput scales linearly with cores and a bad function fails alone. Without it: cross-function corruption and no parallelism. Applied: I11/I12, Scalability Analysis.

Hex-Rays chose a proprietary microcode IR plus decades of hand-tuned heuristics → unrivaled output quality on real binaries; wins where commercial-grade readability and ISA/compiler breadth matter and source is gone.

Ghidra chose SLEIGH processor specs (data-driven lifting) → dozens of architectures from declarative files; wins when you must decompile exotic/embedded ISAs without writing a lifter per arch.

angr/VEX chose VEX plus symbolic execution → decompilation fused with constraint-solving and path exploration; wins for vulnerability research where feasible-path reasoning beats readability (cf. Alternative Architectures ALT2).

RetDec chose LLVM IR as backbone → reuses LLVM's optimizer and can in principle recompile; wins when you want recovered code fed back through a real optimizer/codegen (cf. ALT3, ADR-002).

Boomerang (historical) first demonstrated the full SSA-decompilation pipeline end-to-end and remains a clean algorithmic reference, though its code is dated; this blueprint follows its SSA-first structure while adding a semantics oracle it lacked (Phase 2).

The through-line: production tools buy breadth and quality with heavy IRs and proprietary heuristics; this blueprint trades that breadth for a self-contained, verifiable per-function pipeline whose every transform is proven against an emulator (MM7, I4) — the property none of the above expose publicly.

Back-of-Envelope Capacity Model

Numbers an expert computes before designing, derived from System Constraints (§4): p95 ≤ 100 ms per ≤500-insn function; memory ≤ 50× instruction count.

  • E1 — IR size per function: 500 insns × ~2 IrStmts/insn (flags add stmts) ≈ 1,000 IrStmts/fn.
  • E2 — IR/analysis memory per function: ~50 IR+SSA+fact words/insn × 8 B × 500 insns ≈ 200 KB/fn (within the 50× budget, §4).
  • E3 — φ count: ~30 live vars × ~2 avg iterated-DF size ≈ 60 φ/fn (M5).
  • E4 — Data-flow iterations: lattice height (~4) × |blocks| (~50) = ≤ 200 transfer evals worst case → tens of µs (M6).
  • E5 — Per-insn time budget: 100 ms / 500 insns = 200 µs/insn across the whole pipeline (M1).
  • E6 — Whole-binary fan-out: a /usr/bin program ≈ 2,000 functions; serial at 100 ms p95 = 200 s; on 16 cores ≈ 12.5 s (Scalability Analysis).
  • E7 — Memory peak = largest function (arena freed per fn): a 10k-insn outlier → 10,000 × ~400 B ≈ 4 MB peak, not the binary sum (E2, I11).
  • E8 — Validation cost: 10k random vectors/fixture × ~200 fixtures ≈ 2e6 emulator evals, off the hot path (Phase 2/11).
  • E9 — Fuzz budget: 1e9 execs / (≈5,000 exec/s/core × 16 cores) ≈ 3.5 h → fits a nightly (M11).
  • E10 — Dead-flag fraction: each arithmetic insn defines ~4 flags but ~1 is consumed → ~75% of flag defs are dead → DCE removes ~3 flag-defs/arith insn (M7).
  • E11 — SSA blow-up bound: worst-case φ count is O(vars × blocks); with ~30 vars and ~50 blocks the loose bound is 1,500, but iterated-DF minimality keeps the realistic count near E3's 60 — a 25× gap that justifies minimal (not maximal) SSA (ADR-004, M5).
  • E12 — Expression-fold compression: ~1,000 IrStmts (E1) with ~60% single-use values folded (MM9) → ~400 surviving statements/fn → roughly the line count of the emitted pseudo-C body before structuring collapses it further (Phase 6/8).

Alternative Architectures (Roads Not Taken)

Fundamentally different designs for the same goal — not parameter tweaks.

ALT1 — Pattern-matching / peephole decompiler (no SSA, no data-flow).

instructions ─► template matcher ─► canned C snippets ─► concatenate

Wins for very regular single-compiler output (one toolchain at -O0) where templates cover most code. Embodied by early/simple decompilers and many "quick C" plugins. Rejected because it breaks on optimized/irregular code and cannot prove semantics (no oracle, contra I4).

ALT2 — Symbolic-execution-driven decompiler.

entry ─► path explorer ─► per-path constraints ─► summarize ─► output

Wins for vulnerability research where feasible-path reasoning matters more than readable whole-function C. Embodied by angr. Rejected here because path explosion makes whole-function readable output impractical, and the machinery is far heavier than this goal (cf. Comparative Architecture Table).

ALT3 — LLVM-IR-backed decompiler.

instructions ─► lift to LLVM IR ─► LLVM opt passes ─► LLVM C backend ─► C

Wins when you want to reuse LLVM's optimizer and possibly recompile the result. Embodied by RetDec / mctoll. Rejected because the LLVM dependency is heavy, LLVM IR's abstraction discards machine detail useful for RE, and output quality is hostage to LLVM's C backend (contra ADR-002).

ALT4 — Whole-program / interprocedural decompiler.

call graph ─► interprocedural data-flow + type propagation across calls ─► per-fn output

Wins when cross-function type/alias precision is the product (production tools trend this way). Embodied by Hex-Rays/Ghidra at scale. Rejected (deferred) because per-function isolation (I11) is what keeps the basic tool simple and linearly scalable; whole-program is a deferred enhancement (see Deferred Features Register).

Appendix P — Algorithm Reference (step lists, not code)

P.1 SSA construction (Cytron)

  1. Compute dominator tree + dominance frontiers (Appendix H).
  2. For each variable v: at the iterated dominance frontier of v's def-blocks, insert v = φ(...).
  3. Rename: DFS the dominator tree with a per-variable version stack; each def pushes a new version; each use reads the stack top; φ operands filled from predecessor versions.
  4. Verify single-def + φ-arity (I2/I3).

P.2 Worklist data-flow (generic, I5)

  1. Initialize each block's fact to the lattice ⊤ (or ⊥ per direction).
  2. Push all blocks onto the worklist.
  3. Pop a block; recompute out = transfer(in); if changed, push successors (forward) / predecessors (backward).
  4. Repeat to fixpoint (guaranteed: monotone transfer + finite-height lattice).
  5. Assert iteration count ≤ height×|blocks| (else df_nonconvergence).

P.3 Structuring (Cifuentes interval method, Phase 8/9)

  1. Build intervals; form the derived sequence of graphs; if it collapses to a single node → reducible.
  2. Identify loops from back-edges (head dominates latch); classify pre/post-test; mark exits→break, latch edges→continue.
  3. Identify 2-way conditionals via immediate post-dominators → if/else; merge short-circuits.
  4. Identify n-way (jump table) → switch.
  5. Emit structured nodes bottom-up; for any region that never collapses (irreducible) → node-split (bounded) or labeled goto (I8).
  6. Validate the structured form's IR against the emulator (I4).

P.4 Type recovery (constraint solving, Phase 7)

  1. Walk IR; emit constraints (Appendix F) into a union-find of type variables.
  2. Unify; meet width/sign lattices; on conflict → widen to unknown (I10).
  3. Propagate across copies/φ and (via #333 signatures) across calls.
  4. Assign concrete types; under-constrained → conservative defaults.

P.5 Pipeline order (per function)

lift → import CFG → dominators/DF → SSA → {liveness, reaching} → const/copy prop → DCE → expr build/idioms → type recover → structure → coalesce/name → emit; validate(emulator) at lift and after each transform.
