109 — Deduplication Engine

Project Number: 109

Project Name: Deduplication Engine

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Definition. The Deduplication Engine is a content-addressed storage layer that sits between a producer (a backup client, a primary file system, an object-store ingest path) and a chunk store. It splits an input byte stream into variable-size chunks by content-defined chunking (CDC), addresses each chunk by a cryptographic fingerprint (SHA-256) over its bytes, stores each distinct chunk exactly once in an append-only container store, indexes the fingerprint → location mapping in a crash-safe on-disk B-tree, represents each ingested stream as an ordered manifest of fingerprints, and reclaims chunks no manifest references via a reference-tracing mark-and-sweep garbage collector. It supports inline dedup (fingerprint-before-write) and post-process dedup (write-then-dedup from staging), stacks per-chunk compression and encryption on the chunk path, and reports dedup ratio as a first-class, continuously measured metric.

Phase-0 deliverable (numbered modules):

  1. dedup-core — Fingerprint, Chunk, ChunkRef, Manifest, IndexEntry types.
  2. dedup-fastcdc — FastCDC chunker (gear hash, normalized chunking).
  3. dedup-hash — SHA-256 fingerprint wrapper.
  4. dedup-engine (in-memory dedup table variant) — Phase-0 stand-in for index + store.
  5. dedup-cli — dedup put, dedup version stub.
  6. dedup-conformance — harness skeleton + three passing Phase-0 buckets.

System boundaries.

  • Provides: chunking, fingerprinting, chunk storage, indexing, manifest construction/reconstruction, GC, scrubbing, compression, encryption, inline/ post-process modes, dedup-ratio measurement, distributed pool sharding (Phase 11).
  • Delegates: the on-disk B-tree (B-Tree project, rank 67), WAL durability (Write- Ahead-Log project, rank 71), manifest-of-manifests integrity proofs (Merkle-Tree project, rank 73 — used only where a manifest's integrity must be provable without shipping the full fingerprint list), the local on-disk substrate (File System project, rank 36), transport security for multi-host pools (TLS-SSL-Handshake project, rank 50), the distributed storage backend and erasure-coded durability (Distributed-File-System project rank 86, Erasure-Coding project rank 108 — Phase 11 only).
  • Does NOT provide: a backup scheduler/policy engine; a user-facing restore UI; block-level primary-storage dedup for a live mounted file system (that is the rank-36 project's concern if it chooses to consume this engine); multi-region active-active replication (Phase 11 gives sharding, not global replication).

Non-goals. Byte-level delta-compression of near-duplicate, non-identical chunks (xdelta/bsdiff family — a different technique, out of scope, see §38 Alternative Architectures); sub-millisecond synchronous inline dedup for primary-storage writes (the index-lookup cost puts this below the latency floor of §4); a general-purpose content-addressed KV store API for arbitrary application data (the manifest/chunk model is stream-shaped, not KV-shaped).

Deployment model. Single binary (dedup) per ingest host through Phase 10; a sharded multi-host pool from Phase 11 onward, fronted by an ingest-node shard router and backed by a distributed file system (rank 86) or an S3-compatible object store.

Target users/operators. Backup-tool authors embedding the engine as a library; storage-platform SREs operating a shared multi-tenant pool; primary-file-system engineers evaluating post-process dedup for a snapshot store.

What later phases unlock. Phase 2 (§14): crash-safe persistence. Phase 3 (§15): real chunk storage. Phase 4 (§16): the first end-to-end user-visible dedup. Phase 6 (§18): bounded storage growth. Phase 9 (§21): multi-tenant sharing. Phase 11 (§23): petabyte scale.

Recommended language: Rust (edition 2021). The chunker's gear-hash inner loop and the index's B-tree traversal are byte-level, allocation-sensitive hot paths; bytes::Bytes reference-counted buffer sharing avoids copies across the chunker → hasher → store pipeline (P4). sha2 and chacha20poly1305 (RustCrypto) are audited, memory-safe primitives — this matters directly because the entire correctness argument of the system rests on cryptographic fingerprints (I1). tokio gives the async I/O the container-store and index-service traits need without hand-rolled state machines. Rejected: Go — its GC pauses compound badly with this system's own mark-and-sweep GC (§18) running concurrently with a latency-sensitive ingest path. Rejected: C++ — memory safety in a hasher/index that is the sole arbiter of "these bytes are identical" is a liability class this project should not accept. Rejected: Java/JVM — the same GC-pause argument as Go, plus JNI overhead wrapping sha2/zstd.

Prerequisites. B-Tree (rank 67, index substrate), Write-Ahead-Log (rank 71, index durability), Merkle-Tree (rank 73, manifest-of-manifests hashing), local File System (rank 36, on-disk substrate), TLS-SSL-Handshake (rank 50, distributed-pool transport), Erasure-Coding (rank 108) and Distributed-File-System (rank 86, both Phase 11 only). Read Zhu et al. 2008 and Muthitacharoen et al. 2001 in full before Phase 1; skim Xia et al. 2016 before implementing Phase 1.

Estimated timeline. Phase 0: 2 weeks. Full system (Phase 0–13): 26–28 weeks (~7 months).

Deferred features (full table in Deferred Features Register, §39): BLAKE3 as an alternate hash PhaseDeferred("§11"); zstd dictionary training PhaseDeferred("§17.6"); a locality-preserving index cache and manifest delta-encoding PhaseDeferred("§16.6"); lock-free shard routing PhaseDeferred("§23.6"); cross-engine rechunking on import PhaseDeferred("§24.6"); GPU-accelerated chunking PhaseDeferred("§13.7"); cold-tier compaction PhaseDeferred("§22.6"); per-tenant key-rotation tooling PhaseDeferred("§21.10"); a Bloom-filter RAM prefilter ahead of the on-disk index PhaseDeferred("§36"); deepened erasure-coded parity under the distributed pool PhaseDeferred("§23").

2. Why Build This

A deduplication engine is the silent multiplier under every backup product, every "dedup-aware" primary file system, every snapshot system claiming "we only store changed blocks," every object store keeping many copies of the same training-data shard from billing many times over. When that multiplier is a closed vendor appliance, every "where did my storage go?" investigation ends at a support ticket. When it is one you wrote, the investigation ends at an index scan and a GC audit.

  • Unique systems knowledge. Content-defined chunking, rolling/gear hashing, RAM- bounded fingerprint indexing, and reference-tracing GC under concurrent mutation are a distinct cluster of techniques not taught by CRUD-application engineering.
  • Historical weight. LBFS (2001) introduced CDC to systems literature; Venti (2002) gave write-once content-addressed storage; Data Domain (2008) made dedup a commercial category. This project rebuilds the lineage's reference architecture from first principles.
  • Engineering muscles built. Crash-safe on-disk data structures (shared with the B-Tree and WAL projects, rank 67/71); concurrent mark-and-sweep reasoning (shared with any GC-bearing runtime); AEAD key-derivation design (shared with any multi-tenant encryption-at-rest system); capacity modeling under a hard RAM ceiling.
  • Cross-links. Shares its index substrate with the B-Tree project (rank 67) and its durability primitive with the Write-Ahead-Log project (rank 71); its manifest hashing with the Merkle-Tree project (rank 73); its distributed-pool backend with the Distributed-File-System (rank 86) and Erasure-Coding (rank 108) projects; its transport security with TLS-SSL-Handshake (rank 50).
  • Calibration value. The Phase-0 "second write of identical content stores zero new bytes" property is a sharp, unambiguous correctness bar — either it holds or it does not — making this an unusually good project for calibrating "am I actually building this correctly" against a self-verifying, quantitative signal (I10).

What Mastery Looks Like — after building this system, you can:

  • Explain why content-defined chunking, not fixed-size blocks, is the only way to preserve dedup ratio across edited files, and derive the edit-invariance argument (Phase 1, §13).
  • Design a crash-safe index whose recovery is a deterministic WAL replay, and prove the replay is idempotent (Phase 2, §14).
  • Reason about mark-and-sweep GC correctness under concurrent mutation, including the writer-pin defense against the classic "swept a live object" bug class (Phase 6, §18).
  • Derive a system's RAM ceiling from first principles and identify sharding as the only lever past it (Phase 11, §23; Back-of-Envelope Capacity Model, §36).
  • Design a per-chunk AEAD scheme that preserves deduplication across tenants without destroying confidentiality (Phase 9, §21).
  • Diagnose a live storage-amplification or dedup-ratio regression using the operational telemetry and runbooks this project ships (Operational Readiness, §28).

Six boxes, one paragraph each.

dedup-chunker. Dispatches to FastCDC (default) or Rabin (alternative, LBFS-faithful); both implement the Chunker trait (§11.6) and both must satisfy the edit-invariance conformance property (§13.5, §20.4). The chunker choice is a pool-wide, not per-stream, decision (§20.3) — its output is not dedup-compatible across chunkers.

dedup-hash. Wraps sha2::Sha256; a fingerprint is the chunk's address (P1, I1). This box is the system's entire correctness anchor: every later box assumes fingerprint equality implies byte equality (I2 is the fallback for the day that assumption is violated).

dedup-index + dedup-store. The index maps fingerprint → (container, offset); persisted via the rank-67 B-tree with rank-71 WAL durability (ADR-08/09, I7). The store holds chunk bytes in append-only, 16 MiB sealed containers (P4, I4) — new writes always append; nothing is mutated in place.

dedup-manifest. An ordered list of fingerprints reconstructing one producer stream. It is itself stored as a chunk (recursive addressing, §8.3) and is the sole reference set the GC traces from (P6, I5).

dedup-gc / dedup-scrub / dedup-compress / dedup-encrypt. Four independent, composable layers: GC reclaims unreferenced chunks (mark-and-sweep, ADR-04); the scrubber re-verifies every stored chunk's fingerprint on a schedule to catch bit-rot (§19); compression (zstd, default) and encryption (ChaCha20-Poly1305, opt-in) stack on the chunk write/read path in a fixed order (P9, I9, ADR-03).

dedup-distributed. From Phase 11 (§23) onward, shards the index by fingerprint prefix across ingest hosts and layers chunk storage on a DFS (rank 86) or S3-compatible backend; absent until then, the system is single-host.

6. Design Principles

  1. P1 — Fingerprint is identity. A SHA-256 over a chunk's bytes is its address, not its location. Tradeoff: collision resistance is assumed, not proven; I2 is the escape hatch. Operational implication: moving a chunk between containers never changes its identity, only its index entry. Violating it (e.g. trusting a producer-supplied fingerprint) reopens chunk-poisoning (T2).
  2. P2 — Content-defined chunk boundaries. Boundaries are chosen by a rolling/gear hash hitting a cut-point pattern, not by fixed offsets. Tradeoff: variable chunk sizes complicate container packing. Operational implication: dedup survives inserts/deletes mid-stream. Violating it (fixed-size chunking) collapses dedup ratio on any edited file (ADR-07).
  3. P3 — Variable chunk sizes within hard bounds. Min 16 KiB, average 64 KiB, max 256 KiB (I11). Tradeoff: the min bounds worst-case index growth on a degenerate input; the max bounds worst-case cache-eviction cost. Violating the max (no force-cut) risks an unbounded chunk that overflows the on-disk length field.
  4. P4 — The chunk store is append-only. New chunks append to the active container; sealed containers never mutate (I4). Tradeoff: reclaiming space requires an explicit compaction pass (§22), not in-place overwrite. Operational implication: crash recovery is a bounded forward scan, not a whole-structure fsck. Violating it (in-place mutation) destroys the sequential-write property that makes recovery cheap.
  5. P5 — The index is on-disk and crash-safe. Backed by a WAL (rank 71) ahead of a B-tree (rank 67, I7). Tradeoff: every insert pays one WAL append before the tree mutation. Operational implication: recovery is deterministic replay. Violating it (batched, unsynced writes) breaks the "we never re-store a chunk" guarantee (I1) on crash.
  6. P6 — The manifest is the only reference set. A chunk is alive iff some manifest reaches it (I5). Tradeoff: GC must walk the full manifest graph, not consult a cheap counter. Operational implication: deleting a manifest is O(1); reclaiming its exclusive chunks is deferred to the next GC cycle. Violating it (a secondary, independently-mutated liveness table) reintroduces the ref-count drift problem P7 exists to avoid.
  7. P7 — GC is mark-and-sweep, not reference-counted. Trace from live manifests; sweep the unreached (ADR-04). Tradeoff: GC pause/cycle cost vs. a ref-count's O(1) update but corruption-prone concurrent maintenance. Operational implication: GC is a schedulable batch job, not an inline cost on every delete. Violating it under high manifest churn is itself documented as the regime where ADR-04's rejected alternative wins.
  8. P8 — Inline vs. post-process is a mode, not a forked code path. Same chunker, hasher, index, store back both (ADR-10). Tradeoff: the shared abstraction must express both "dedup before write" and "dedup after write" without branching in the hot loop. Operational implication: one codebase, one conformance suite, two configurations. Violating it (forking) doubles the maintenance and bug surface.
  9. P9 — Compression is applied before encryption, never the reverse. Fixed pipeline order (ADR-03, I9). Tradeoff: an untrusted-compressor threat model (§38 Alt 3) cannot use this ordering. Operational implication: the compression-ratio dashboard is meaningful only under this order. Violating it silently collapses the compression ratio to ~1.0 (ciphertext is incompressible).
  10. P10 — Per-chunk AEAD keys derived by HKDF preserve cross-tenant dedup. Key = HKDF(pool_key, fp) (ADR-06, I8). Tradeoff: one HKDF-Expand per chunk vs. a single pool-wide key's zero marginal cost. Operational implication: tenants sharing a pool key can dedup against each other transparently. Violating it (pool-wide raw key) removes the per-chunk domain separation this design relies on for I8.
  11. P11 — Failures are first-class. Every failure path (torn append, dangling manifest, index desync) has a named recovery procedure, a conformance fixture, and a runbook entry. Tradeoff: more upfront design work per subsystem. Operational implication: on-call engineers have a documented procedure, not an ad hoc one. Violating it produces the exact "vendor support ticket" failure mode this project exists to avoid (§2).
  12. P12 — Delegate the index substrate; do not reinvent it. The B-tree (rank 67) is instantiated, not re-implemented (ADR-08). Tradeoff: this project inherits rank 67's API surface and any of its limitations. Operational implication: bug fixes and performance work in rank 67 benefit this project without a merge. Violating it (a bespoke B-tree) is scope creep this blueprint explicitly rejects.
  13. P13 — Fingerprint-index RAM is the primary bottleneck to design around. Every scaling lever (locality-preserving caching, sparse indexing, Bloom prefilters, sharding) exists because of this (MM2, §36). Tradeoff: RAM-saving techniques trade away exactness or add latency (a Bloom-filter prefilter risks false positives). Operational implication: capacity planning is index-RAM planning, not disk planning. Violating it (assuming disk is the bottleneck) leads to an OOM wall at scale (§33).
  14. P14 — Dedup ratio is a measured, reported, first-class metric. Not an incidental byproduct of storage savings (I10). Tradeoff: computing and exposing it costs a counter update per chunk. Operational implication: it is the operator's primary KPI and appears in every ingest report and dashboard. Violating it (no metric, just "storage looks smaller") reopens the "where did my storage go" investigation this project exists to close (§2).

Debugging methodology. 8. Domain Model

8.1 The chunk/fingerprint/manifest model

A stream (a file, a backup set, a snapshot) is cut into an ordered sequence of chunks by content-defined chunking. Each chunk's fingerprint (SHA-256) is its address (P1). The stream is represented by a manifest: an ordered list of fingerprints plus stream metadata (name, length, parent lineage). A manifest is itself stored as a chunk under its own fingerprint — the manifest layer is recursive: a "manifest of manifests" (a backup catalog referencing per-file manifests) is a first- class object with no separate storage mechanism.

8.2 Content-defined chunking

FastCDC (default, §13). A gear hash h accumulates per byte: h = (h << 1) + gear[byte], where gear is a fixed 256-entry table (Xia et al. 2016, §5). A cut point is declared when h & mask == 0; mask narrows below the target average size (biasing toward a cut) and widens above it (biasing away from the max) — this is "normalized chunking" (§13.3). A forced cut at CHUNK_MAX bounds worst-case chunk size (I11).

Rabin (alternative, §20). The fingerprint is the input, viewed as a polynomial over GF(2), reduced modulo a fixed irreducible degree-64 polynomial (Rabin 1981, §5). A 48-byte rolling window updates the fingerprint by one shift, one XOR, and one table lookup per byte (Muthitacharoen et al. 2001). A cut point is declared when the low 13 bits match a fixed pattern.

Chunker state-transition table (both chunkers share this shape):

State On Event Next State Emits
SCANNING (pos < min) byte consumed SCANNING — (gear/Rabin update skipped, §13.6)
SCANNING (min ≤ pos < max) h & mask == 0 CUT chunk slice [last_cut, pos]
SCANNING (min ≤ pos < max) mask test fails SCANNING —
SCANNING (pos == max) forced cut CUT chunk slice [last_cut, max]
CUT slice emitted SCANNING reset h = 0, last_cut = pos
SCANNING stream ends, pos > last_cut FINAL trailing partial chunk

8.3 The index and manifest recursion — worked example

Ingest stream S = "backup/2026-07-24/db.tar", 200 MiB. FastCDC emits chunks c1..c400 (~64 KiB average). For each ci: compute fp_i = SHA256(ci); look up fp_i in the index. Suppose c1..c380 are new (first-ever bytes) and c381..c400 are byte-identical to chunks from yesterday's backup (unchanged tail of the file). The engine writes c1..c380 to the store and inserts 380 new IndexEntry rows; for c381..c400 it performs zero writes, only 20 index lookups. The manifest M = [fp_1, ..., fp_400] is built, serialized (ADR-15: length-prefixed fingerprint array), and stored as chunk fp_M = SHA256(serialize(M)). IngestReport.dedup_ratio = bytes_in / bytes_stored = 200 MiB / (bytes of c1..c380) ≈ 5.26 for this stream in isolation (I10).

A backup catalog referencing 30 such per-file manifests is itself a manifest whose "chunks" are [fp_M1, ..., fp_M30] — the recursive case of §8.1. Dereferencing the catalog to reconstruct any file requires: catalog lookup → per-file manifest lookup → per-chunk lookups, at most 3 index hops.

8.4 Malformed-input example

A corrupted container footer (single bit flipped in the CRC32C field, §15.1) is detected at container-open time: the footer CRC32C recomputed over the container body will not equal the stored value. The container is marked suspect; reads against chunks inside it are refused (I4) until dedup fsck --repair (§25.1) either recovers the container from a replica (Phase 11) or the operator accepts the chunk range as lost. A dangling manifest — one whose fingerprint list contains an fp absent from the index (I3 violation, caused by an interrupted ingest, T9/FM-3) — is detected by fsck's manifest- dereference scan and quarantined; the manifest is not silently served with holes.

8.5 Failure-path example

Mid-ingest of S above, the process is killed after chunk c250 is fsync'd to the active container and its IndexEntry WAL-appended, but before the in-memory manifest builder (§16.2) flushes c251. On restart: the store's forward-scan recovery (§15.4) finds the container intact through c250's bytes (I4 holds); the index WAL replays cleanly through c250's insert (I7); no manifest for S was ever committed (the ingest pipeline commits the manifest strictly after all its chunks, §16.6), so S simply does not exist yet — the producer re-ingests S from the start, and c1..c250's identical bytes dedup for free (dedup ratio absorbs the retry cost, I10).

pub struct Fingerprint(pub [u8; 32]);          // I1: address = SHA-256(bytes)

impl Fingerprint {
    pub const ZERO: Self;

12. Phase 0 — Skeleton & Correctness Kernel

12.1 Objectives

Stand up the repository (§10) and land a Phase-0 kernel: dedup-core types, a real FastCDC chunker, a real SHA-256 wrapper, an in-memory dedup table, and the "second write of identical content stores zero new bytes" smoke test. No on-disk persistence yet — that is Phase 2.

12.2 Detailed Implementation Steps

Land the full repository tree (§10) in one commit; every crate gets a compiling stub lib.rs. Implement dedup-core's types (§11.1–§11.5) as compile-only definitions. Implement dedup-fastcdc as a real chunker: the 256-entry gear table (a const array, never generated at runtime — P1/P12 discipline applied to reproducibility), the normalized-chunking mask logic (P2, P3, Xia et al. 2016 §5), and the state machine of §8.2. Implement dedup-hash as a thin sha2::Sha256 wrapper producing Fingerprint values (I1, ADR-13). Implement an in-memory DedupTable (HashMap<Fingerprint, bytes::Bytes>) standing in for the Phase-2/3 index+store. Implement the ingest entry point and IngestReport (dedup ratio, I10, P14). Implement dedup-cli's put/version stub.

12.3 Deliverable

make bootstrap && make build && make test passes; dedup put - reads stdin, ingests, and prints an IngestReport. make conformance reports three Pass buckets (core_types, fastcdc_chunker, dedup_table) and every other bucket Deferred.

12.4 Acceptance Criteria

hello_dedup fixture: ingest a 10 MiB seeded-PRNG stream twice; bytes_after_second == bytes_after_first (exact equality, I10); dedup_ratio ≥ 100.0 on the second ingest. FastCDC throughput ≥ 1 GB/s single-core (M1, benchmarked on the same fixture). All eleven ADRs listed in §12.5 written under docs/adr/.

12.5 Conformance Fixtures

conformance/corpora/chunker/synthetic.bin (10 MiB seeded PRNG) — expected: stable boundary set, recorded reference. hello_dedup.rs (integration test) — expected: zero new bytes on repeat ingest. core_types unit fixtures — expected: Fingerprint::of round-trips against NIST FIPS 180-4 SHA-256 test vectors (§5).

12.6 Pitfalls

The gear table must be a const, not lazily constructed — a lazy_static table makes cross-host boundary reproducibility depend on constructor interleaving. The minimum-size-skip (pos < CHUNK_MIN ⇒ skip the gear update) is a >2× throughput optimization (§13.6) — omitting it in the Phase-0 draft is a common regression later phases silently inherit. Do not weaken the hello_dedup assertion to an approximate delta — it is load-bearing for I10. Resist putting the index on disk in Phase 0; the in-memory table is intentional until wire/on-disk formats stabilize (Phase 2).

12.7 Performance Concerns

The gear-hash inner loop is the hot path; its table (2 KiB) must stay L1-resident (§4). bytes::Bytes sharing avoids a copy between chunker output and hasher input (P4). No allocation should occur per-byte inside feed().

12.8 Edge Cases

An all-zero or all-identical-byte stream: FastCDC's mask test degenerates toward minimum- size chunks (documented, not a bug) — the hello_dedup fixture deliberately uses a seeded PRNG stream, not all-zeros, to exercise a realistic boundary distribution. Empty input (0 bytes): chunker emits zero chunks, finish() returns None. A single-byte input: emitted as one trailing partial chunk via finish().

12.9 Failure Analysis

Since Phase 0 has no persistence, "failure" here means a wrong dedup-ratio computation or a chunker table mismatch across builds — caught entirely by the conformance suite and CI (§12.5), not by a runtime recovery path (deferred to Phase 2/3).

12.10 Operational Notes

dedup version prints the on-disk/wire version stamp (dedup-core::version, §29) even though no on-disk format exists yet — this establishes the version-reporting convention every later phase reuses. No metrics are exported yet (Prometheus wiring lands Phase 4+, §28).

13. Phase 1 — FastCDC Chunker

13.1 Objectives

Harden the Phase-0 FastCDC chunker into a fully parameterized, conformance-pinned implementation: normalized chunking, tunable average size, and an edit-invariance conformance corpus.

13.2 Detailed Implementation Steps

Implement FastCdcParams { min, avg, max, mask_s, mask_l } (P3) with defaults (16 KiB, 64 KiB, 256 KiB) and asymmetric masks mask_s = (1<<17)-1, mask_l = (1<<15)-1 per the normalized-chunking construction (Xia et al. 2016, sec. 3.3, applying P2). The gear table (dedup-fastcdc/src/gear.rs) is derived once from a splitmix64 generator seeded 0xC0FFEE_FEEDFACE and committed as a const array — never regenerated at runtime (P1 discipline). Record the boundary output of three fixtures (lorem.txt, synthetic.bin, edited.bin) as the conformance corpus (§13.5); pin the chunker's output against them so any future boundary-distribution change is an explicit, reviewed, major-version event (§29).

13.3 Deliverable

A tuned FastCDC chunker exposed via the dedup-fastcdc crate, a recorded conformance corpus under conformance/corpora/chunker/, and a criterion benchmark (chunker_throughput) reporting throughput as a function of the avg parameter.

13.4 Acceptance Criteria

Sustained throughput ≥ 1 GB/s single-core (M1). edited.bin (synthetic.bin with a one-byte insert at offset 5000) dedups to ≥ 99% of synthetic.bin's chunk set — the edit-invariance property (I11 combined with P2). All emitted chunks satisfy CHUNK_MIN ≤ len ≤ CHUNK_MAX (I11) on every fixture.

13.5 Conformance Fixtures

lorem.txt (1 MiB deterministic text) — recorded boundary set. synthetic.bin (10 MiB seeded PRNG) — recorded boundary set. edited.bin (synthetic.bin + 1-byte insert at offset 5000) — expected: ≥ 99% chunk overlap with synthetic.bin past the insert point.

13.6 Pitfalls

The minimum-size skip is a >2× throughput win — the inner loop must not run the gear update while pos_in_chunk < min. The asymmetric masks are not "avg/4, avg*4" — read Xia et al. 2016's sec. 3.3 directly; guessing the construction produces a boundary distribution that looks plausible but fails the edit-invariance fixture. The forced cut at max is non-negotiable (I11); without it a pathological input produces an unbounded chunk that overflows IndexEntry.original_len's u32 at extreme scale.

13.7 Performance Concerns

Benchmark throughput vs. the avg parameter (chunker_throughput, M1). SIMD acceleration of the gear-hash update is a real lever but deferred (PhaseDeferred("§13.7"), GPU-accelerated chunking) until benchmarks show single-core throughput is the binding ingest bottleneck rather than the hasher or store (§4).

13.8 Edge Cases

A stream shorter than CHUNK_MIN: emitted whole as one trailing chunk via finish(). A stream that never hits a mask-test cut before max repeatedly: the forced-cut path is exercised on every chunk — verified by a dedicated all_forced_cuts.bin fixture.

13.9 Failure Analysis

A gear-table drift between hosts (e.g. a rebuilt binary with a different table) produces silently different boundaries and a collapsed dedup ratio across the fleet — not a crash, a quality regression. Detection: the conformance corpus check in CI (§13.5) catches this before release; in production, a sudden fleet-wide dedup-ratio drop (§28 dashboards) is the operator-visible symptom.

13.10 Operational Notes

dedup_chunker_throughput_bytes_per_second (gauge) is exported once Prometheus wiring lands (Phase 4, §28). The chunker version (gear-table hash) is stamped into every pool header (§29) so a mismatched fleet is detectable at dedup fsck time (§25.1).

14. Phase 2 — On-Disk Index & WAL Durability

14.1 Objectives

Replace the Phase-0 in-memory DedupTable with a crash-safe on-disk index: the rank-67 B-tree keyed by Fingerprint, durable via the rank-71 WAL (P5, ADR-08, ADR-09).

14.2 Detailed Implementation Steps

Instantiate BTree<Fingerprint, IndexEntry> from the rank-67 crate (P12 — delegate, do not reinvent) via dedup-index::service::IndexServiceImpl (§11.7). Every insert first wal.append(IndexWalOp::Insert{entry}), fsyncs, then mutates the tree (I7) — batched or O_DIRECT-deferred fsync is explicitly rejected as a correctness bug, not a performance choice, because I1's "we never re-store a chunk" guarantee depends on the index never losing an entry (Petrov, Database Internals ch. 7, §5). Checkpoint the tree every 5 minutes or 100 K ops (whichever first), truncating the WAL to post-checkpoint entries. The B-tree's 4 KiB page holds ~85 IndexEntry rows (48 bytes each) — a 100 M-fingerprint pool reaches depth 4–5 (§36 item 1).

14.3 Deliverable

An IndexServiceImpl that survives kill -9 and reconstructs a bit-identical tree via WAL replay; a benchmark suite reporting p50/p99 lookup latency and insert throughput.

14.4 Acceptance Criteria

Insert 1 M fingerprints, kill -9, restart: tree has exactly 1 M entries with recorded values (I7). Lookup p99 ≤ 1 ms warm against a 100 M-entry tree (M3, §4). Insert throughput ≥ 200 K ops/s sequential (M4). Pool open + 1 M-op WAL replay ≤ 30 s (§4).

14.5 Conformance Fixtures

crash_1m_inserts.fixture — kill mid-run, restart, assert exact entry count. wal_replay_ idempotent.fixture — replay a WAL segment twice, assert identical tree state (I7). btree_index conformance bucket — round-trip + scan-ordering assertions.

14.6 Pitfalls

An O_DIRECT/batched-fsync "optimization" silently reopens a correctness hole (I1) — do not add it without an explicit ADR overriding ADR-09. The checkpoint must be taken from a quiesced state (simpler) rather than attempted as a copy-on-write snapshot of a live tree (more complex, deferred). Recovery must be idempotent: an Insert logged but not yet applied before a crash must safely re-apply on replay — rank-67's insert-by-key API is idempotent by construction (I7).

14.7 Performance Concerns

Reads are lock-free against rank-67's RCU-shaped tree; writes hold the write lock only for a leaf split's duration (§11.7). WAL fsync frequency is the dominant insert-latency cost — batching multiple logical inserts behind one fsync (without weakening the per-insert durability guarantee) is the main lever if M4 is missed.

14.8 Edge Cases

A checkpoint that itself is torn (crash mid-write): the prior checkpoint remains valid and the WAL is replayed from it (I7 protects this). A WAL segment that grows past a configured size between checkpoints: forces an out-of-schedule checkpoint rather than unbounded WAL growth.

14.9 Failure Analysis

Index/WAL desync (FM-2): symptom is a post-crash entry-count mismatch; root cause is a torn checkpoint or truncated WAL segment; detection is the checkpoint-hash comparison at open; recovery replays from the last valid checkpoint; if that fails, the manual path rebuilds the index from a full chunk-store scan (slow, documented in the runbook, §28).

14.10 Operational Notes

dedup_wal_replay_seconds (histogram) and dedup_index_lookup_seconds (histogram) are the primary dashboards for this phase (§28). A checkpoint file's SHA-256 is recorded alongside it so fsck (§25.1) can detect a corrupted checkpoint independent of a crash.

15. Phase 3 — Append-Only Chunk Store

15.1 Objectives

Implement the real chunk store: 16 MiB sealed containers (ADR-22), a chunk-header CRC32C, a container-footer CRC32C, and forward-scan torn-append recovery (P4, I4).

15.2 Detailed Implementation Steps

Container layout: a 64-byte header (magic, version, container_id, sealed_at, chunk_count), a sequence of [chunk header (46 bytes: fp, original_len, stored_len, flags, crc32c) | chunk bytes] entries, and a 32-byte footer (CRC32C over header+body). ContainerStore::write appends header+bytes at the active container's current offset, fsyncs, updates offset/chunk_count, and seals (writes footer, fsyncs, opens a fresh active container) once offset ≥ 16 MiB (ADR-22). read resolves a ChunkRef to a pread at (container, offset) and verifies the chunk-header CRC32C before returning bytes (I1's storage-side half). The container footer's CRC32C is computed incrementally as chunks append (a running CRC32C state), a >10× speedup over computing it once at seal time.

15.3 Deliverable

A ContainerStore implementing StoreService (§11.7) sustaining ≥ 500 MB/s single-NVMe write throughput, with a torn-append recovery path exercised by a dedicated chaos test.

15.4 Acceptance Criteria

Write throughput ≥ 500 MB/s (§4). A process killed mid-write (between header+bytes write and fsync) truncates cleanly to the last good chunk on restart, and the index has zero dangling entries pointing past the truncation point (I4, since the index insert is gated on the fsync-confirmed write). A corrupted sealed container's footer is detected by dedup fsck (§25.1).

15.5 Conformance Fixtures

torn_append.fixture — kill mid-write, assert clean truncation + zero dangling index entries. corrupt_footer.fixture — flip a footer byte, assert fsck flags it (T1, I4). chunk_store conformance bucket — append/read/seal round-trip.

15.6 Pitfalls

The chunk-header CRC32C covers header+bytes, not bytes alone — a corrupted fp byte in the header must be as detectable as a corrupted payload byte. fsync on every chunk write is the correct default for I1's guarantee; an operator who configures batched fsync for throughput shifts the durability burden entirely onto the WAL replaying against a possibly-truncated store — correctness-preserving but slower to recover (§14).

15.7 Performance Concerns

Reads hit the OS page cache for warm containers; cold reads dispatch a pread. The running-CRC32C-during-append technique avoids an O(container size) pass at seal time — without it, sealing a 16 MiB container becomes a measurable throughput cliff every ~32 ms of sustained 500 MB/s writing.

15.8 Edge Cases

A container that seals exactly at a chunk boundary vs. mid-chunk-write: the store never splits a chunk across containers — a chunk that would overflow the 16 MiB boundary triggers a seal-then-open-fresh-container before that chunk is written, not after. Concurrent reads against a container mid-seal: readers see either the pre-seal or post-seal state, never a torn footer (the seal path is single-writer, §15.2).

15.9 Failure Analysis

Torn container append (FM-1): symptom is a recovery-log truncation message at startup; root cause is a crash/power-loss mid chunk-write; detection is the forward-scan hitting the first invalid chunk-header CRC32C; auto-recovery truncates to the last good chunk; no manual recovery is typically needed (T4).

15.10 Operational Notes

dedup_containers_total and dedup_active_container_bytes (gauges) track store growth (§28). The runbook "Ingest is slow" (§28) starts by checking store write throughput against M6 before looking upstream at the chunker or hasher.

16. Phase 4 — Manifests & Inline Ingest

16.1 Objectives

Wire Phase 1's chunker, Phase 2's index, and Phase 3's store into one ingest pipeline; ship the first end-to-end, user-visible feature: inline dedup with manifest construction (P6, P8, ADR-10).

16.2 Detailed Implementation Steps

ManifestBuilder (§11.5) appends each chunk's fingerprint in stream order as the pipeline progresses (applying P6: the manifest is under construction, not yet the GC's reference set until committed). The pipeline order is: chunk → fingerprint → index lookup → (hit: append fp to manifest) | (miss: compress → encrypt(if enabled) → store.write → index.insert → append fp to manifest). On finish(), the builder serializes the manifest (ADR-15) and inserts it as an ordinary chunk (§8.3's recursion). I3 is enforced here: the manifest is only committed after every one of its chunks is confirmed indexed — never before, or a crash mid-ingest leaves a dangling reference (§8.5 walks this failure path).

16.3 Deliverable

ingest_inline() (§11.7-style async entry point) producing a ManifestId + IngestReport from a byte stream; a benchmark measuring end-to-end throughput.

16.4 Acceptance Criteria

Ingesting the same 100 MiB stream twice produces zero new chunks on the second pass (I10). Ingesting two 100 MiB streams differing by one inserted 1 KB block yields ≥ 99% dedup ratio on the second (P2's edit-invariance carried through the full pipeline). End-to-end throughput ≥ 500 MB/s (M6, §4).

16.5 Conformance Fixtures

inline_ingest_repeat.fixture — ingest 100 MiB twice, assert zero new chunks. inline_ingest_edited.fixture — 100 MiB with a 1 KB mid-stream insert, assert ≥ 99% dedup ratio. inline_ingest conformance bucket — end-to-end invariant assertions (I3, I10, I11 jointly).

16.6 Pitfalls

The index lookup on every chunk is inline mode's bottleneck; a locality-preserving cache (Zhu et al. 2008, sec. 3.1, referenced from P13) is the standard remedy for streams with locality — deferred (PhaseDeferred("§16.6")) until benchmarks against M6 show it is needed. Manifest delta-encoding across snapshot generations is likewise deferred (PhaseDeferred("§16.6")) — both are registered in §39. The manifest must commit strictly after every one of its chunks is indexed (I3) — reordering "for simplicity" reopens T9/ FM-3.

16.7 Performance Concerns

bytes_stored in IngestReport includes post-compression overhead; bytes_in is pre-chunking stream size — the ratio is the operator's primary KPI (P14) and must be computed consistently everywhere it is displayed (§28).

16.8 Edge Cases

A stream that is empty (0 bytes): produces a manifest with zero chunks and total_len = 0 — a valid, if degenerate, manifest. A stream ingested concurrently with a GC cycle that started before the stream's manifest committed: the writer-pin (ADR-21, I6) protects the in-flight chunks from being swept.

16.9 Failure Analysis

A dangling manifest (I3 violation, FM-3): symptom is fsck reporting a manifest referencing a missing fingerprint; root cause is an interrupted ingest that (bug, not by design) committed early; detection via dedup fsck (§25.1); recovery quarantines the manifest — the producer must re-ingest the stream; the earlier chunks that did land dedup for free on retry (§8.5).

16.10 Operational Notes

dedup_bytes_in_total, dedup_bytes_stored_total, dedup_chunks_new_total, dedup_chunks_dup_total (all counters) are exported starting this phase (§28). The "Dedup ratio dropped" runbook (§28) begins by checking whether the chunker boundary distribution changed (§13.9) before assuming a genuine change in source-data redundancy.

17. Phase 5 — Per-Chunk Compression

17.1 Objectives

Insert the compression layer between the chunker/hasher and the store (P9, ADR-12), compounding with dedup: dedup removes cross-chunk redundancy, compression removes intra-chunk redundancy.

17.2 Detailed Implementation Steps

Implement ZstdCompressor (default, level 3), Lz4Compressor (feature-flagged, ADR-12), and NoopCompressor (§11.8). Insert compress() before store.write() and decompress() after store.read(), recording EntryFlags::COMPRESSED and both stored_len/original_len on the IndexEntry (§11.4). Enforce the incompressible guardrail: a chunk compressing to ≥ 95% of its original size is stored uncompressed — the read-side decompression cost is not amortized by negligible storage savings (applying P9's ordering discipline one level deeper).

17.3 Deliverable

A working compression layer measured against an enwiki-class 1 GiB corpus, with a benchmark reporting ratio and throughput at levels 1/3/6/11.

17.4 Acceptance Criteria

zstd level 3 reduces the 1 GiB corpus to ≤ 35% of original size (M7). A chunk compressing to ≥ 95% of original is stored uncompressed and EntryFlags::COMPRESSED is unset for it — asserted by a dedicated fixture.

17.5 Conformance Fixtures

enwiki_1gib.corpus (or a licensable equivalent synthetic corpus with comparable entropy) — expected ≤ 35% ratio at level 3. incompressible_chunk.fixture (already- compressed/random 64 KiB chunk) — expected: stored uncompressed, flag unset. compression conformance bucket — round-trip fixture.

17.6 Pitfalls

The dashboard's compression ratio is measured after dedup, not before — an operator seeing "20:1 dedup" and "2:1 compression" must be told explicitly these multiply to a "40:1 storage savings" figure (MM7); undocumented, this is a recurring support-ticket source. zstd dictionary mode gives a >2× ratio gain on small chunks — the 64 KiB average chunk size sits right at the boundary where dictionaries help, but the operator-facing dictionary-training surface is non-trivial and is deferred (PhaseDeferred("§17.6"), registered §39).

17.7 Performance Concerns

Benchmark compress/decompress throughput at levels 1/3/6/11 (compression_ratio benchmark) — level 3 is the default because the speed/ratio tradeoff favors it for the cold-storage-dominated workload this engine targets (ADR-12).

17.8 Edge Cases

A zero-length chunk (should be unreachable given CHUNK_MIN, but defensively handled): compression is a no-op, flag unset. A chunk whose compressed size is larger than original (adversarial or already-compressed input): the guardrail (§17.2) catches this identically to the ≥95% case.

17.9 Failure Analysis

A misconfigured pipeline enabling encryption before compression (violating I9/ADR-03, FM-9): symptom is a compression ratio near 1.0 unexpectedly; detection is startup config validation (which should refuse to start) plus a runtime ratio-anomaly alert as a backstop; recovery is an operator config fix.

17.10 Operational Notes

dedup_compression_ratio (gauge, I9) is exported per-pool. The "Dedup ratio dropped" runbook (§28) cross-checks this gauge to distinguish a compression regression from a genuine dedup-ratio regression.

18. Phase 6 — Garbage Collection

18.1 Objectives

Implement reference-tracing mark-and-sweep GC (ADR-04, P6, P7): reclaim chunks no live manifest reaches, safely under concurrent ingest (I5, I6).

18.2 Detailed Implementation Steps

Mark: starting from the set of live manifests, recursively dereference nested manifests (§8.3), marking every reached fingerprint in a bit vector (N_chunks / 8 bytes — §36 item 8; Jones/Hosking/Moss ch. 2–3, §5, informs the tracing-soundness argument). Sweep: iterate the index in fingerprint order; an entry not in the mark set gets EntryFlags::TOMBSTONE plus a Remove{fp} WAL op — bytes remain in the container until compaction (§22) reclaims them (P4's append-only discipline carried through GC). Concurrency defense (ADR-21): writers register a WriterPin for an in-progress manifest; the GC treats a pinned manifest's fingerprints as live for the pin's duration, releasing it on commit — this is I6's enforcement point.

18.3 Deliverable

A GarbageCollector implementation completing a full mark-and-sweep cycle on a 100 M-fingerprint pool with 1 K live manifests within the target below, plus a chaos test running concurrent ingest during GC.

18.4 Acceptance Criteria

Full cycle ≤ 5 minutes at 100 M fingerprints / 1 K manifests (M8). A chaos test writing new content during GC loses zero in-progress writes (I6). Two manifests sharing 90% of chunks: deleting one and running GC tombstones only the 10% exclusive set.

18.5 Conformance Fixtures

gc_concurrent_ingest.fixture (chaos) — GC + concurrent writes for a bounded window, assert zero loss. gc_exclusive_chunks.fixture — two manifests, 90% shared / 10% exclusive, delete one, assert only the 10% tombstoned. garbage_collection conformance bucket — mark/sweep correctness assertions (I5, I6).

18.6 Pitfalls

Tombstoning is logical, not physical — an operator seeing "GC reported 100 GiB tombstoned" while df shows unchanged usage must understand the two-phase model (documented in the runbook, §28; this is I5's visible-but-not-yet-reclaimed state). The mark bit vector must be keyed by fingerprint, not index offset — an offset-keyed vector breaks the moment compaction (§22) renumbers offsets between GC cycles. The writer-pin approach (ADR-21) blocks the sweep on long-running ingests; the operator's tuning lever is either running GC less often or splitting long ingests into smaller manifests.

18.7 Performance Concerns

The mark-phase bit vector is negligible RAM (§36 item 8: ~49 MiB at 390 M chunks) next to the index's own footprint (§36 item 1) — GC memory pressure is not the bottleneck; sweep I/O (an index scan) is. Throttle the sweep's read bandwidth the same way the scrubber is throttled (§19.7) if GC contends with foreground ingest.

18.8 Edge Cases

A manifest deleted mid-mark-phase: the mark phase has already captured the live-manifest snapshot at its start (an epoch), so the deletion is picked up on the next cycle, not retroactively — documented, not a bug. A pin that is never released (a crashed ingest task): see FM-8 (pin TTL expiry).

18.9 Failure Analysis

GC pin leak (FM-8): symptom is a GC cycle that never completes, with pin count monotonically growing; root cause is a crashed ingest task that never released its WriterPin; detection is a pin-age alert (held longer than the ingest timeout); auto- recovery is TTL-based forced pin release; manual recovery lets an operator force-clear a named pin via dedup gc --clear-pin.

18.10 Operational Notes

dedup_gc_tombstoned_total, dedup_gc_orphans_found, dedup_gc_pin_conflicts_total are exported (§28). dedup gc --dry-run (§25.2) reports what would be tombstoned without mutating state — the standard pre-flight check before a scheduled GC window.

19. Phase 7 — Scrubber & Integrity Verification

19.1 Objectives

Detect bit-rot before it propagates to the read path: a background loop that re-verifies every stored chunk's fingerprint on a schedule (I1's ongoing enforcement, T1).

19.2 Detailed Implementation Steps

Walk every chunk in every container on a configurable schedule (default: full pool once per 30 days). Per chunk: read bytes, verify the chunk-header CRC32C (fast, catches single-byte errors), decompress/decrypt to original bytes, recompute SHA-256, compare to the index entry's fp (I1). A mismatch after CRC32C passed is the multi-byte-flip case CRC32C alone misses (MM-relevant: a chunk never read for years can silently rot undetected without this loop). On mismatch: log a "fingerprint mismatch" alert; repair is operator-invoked (dedup repair <fp>, re-ingesting from a replica or upstream source — automatic in Phase 11's replicated pools, manual otherwise). Implement the weak- fingerprint fallback (§8, I2): on any write whose fingerprint already exists, an opt-in byte-compare (--collision-detect=byte-compare) distinguishes a true duplicate from an observed collision (T3); on mismatch, refuse the write and log the colliding pair for audit.

19.3 Deliverable

A throttled scrubber walking a 1 TiB pool within the target below, plus the collision- detection opt-in path.

19.4 Acceptance Criteria

Full 1 TiB pool walk ≤ 4.5 hours at a 70 MB/s throttle (M9, §36 item 9). A single flipped bit in a stored chunk is detected on the next scrub cycle. An injected fake SHA-256 collision (test-only API) is logged and the conflicting write refused.

19.5 Conformance Fixtures

bitflip_detect.fixture — flip one bit on disk, assert detection next cycle. fake_collision.fixture (test-only injection API) — assert refusal + audit log entry. scrubber conformance bucket — throughput + detection assertions.

19.6 Pitfalls

The scrubber must be throttled — unthrottled, it saturates disk bandwidth and starves the foreground read path; default 70 MB/s with operator override (§4). Trusting CRC32C alone (skipping the SHA-256 re-verify) misses multi-byte cosmic-ray-class corruption — CRC32C is checked on every read, but a chunk unread for years needs the scheduled full-pool walk regardless (T1).

19.7 Performance Concerns

Throttle bandwidth is the primary tuning lever (§4 FD/IO budget); the scrub cadence (default 30 days) trades detection latency against background I/O cost — both are operator-configurable.

19.8 Edge Cases

A container deleted between the scrubber's container-list snapshot and its scan of that container (raced with compaction, §22): the scrubber skips the now-missing container without alerting (expected, not corruption). A chunk flagged TOMBSTONE: skipped by the scrubber (dead chunks are GC's concern, not integrity's).

19.9 Failure Analysis

Fingerprint mismatch / bit-rot (FM-5): symptom is a scrubber alert; root cause is media decay or a cosmic-ray flip; detection is the scheduled SHA-256 re-verify; auto-recovery is none on a single-host pool (no replica); manual recovery is dedup repair <fp> from an external source, or accepted data loss if none exists.

19.10 Operational Notes

dedup_scrub_corrupt_chunks_total (counter) is the primary alert signal (§28). The runbook "Scrubber reported a corrupt chunk" (§28) is the operator's entry point into the repair path.

20. Phase 8 — Rabin Chunker (LBFS-Faithful Alternative)

20.1 Objectives

Implement the Rabin-fingerprint chunker (ADR-01's rejected-but-supported alternative) for operators who need LBFS-faithful boundaries (Muthitacharoen et al. 2001, Rabin 1981).

20.2 Detailed Implementation Steps

The Rabin fingerprint of a byte window is its value modulo a fixed irreducible degree-64 polynomial over GF(2) (0xbfe6b8a5bf378d83, documented in the LBFS source — a load-bearing constant, changing it changes every boundary in every pool using it). The rolling-window property (a 48-byte window, the LBFS default) costs one shift, one XOR, and one 256-entry table lookup (out_table/mod_table, both derived from the fixed polynomial) per extended byte. A cut point is declared when the low 13 bits match a fixed pattern (§8.2's shared state-transition table applies identically). Compatibility boundary: a Rabin-chunked pool and a FastCDC-chunked pool are not dedup-compatible — the chunker choice is stamped in the pool header (per-pool, not per-stream, applying ADR-01's rationale).

20.3 Deliverable

A working Rabin chunker in dedup-rabin, a conformance test against the published LBFS corpus, and a test proving both chunkers dedup correctly within their own pool but not across pools.

20.4 Acceptance Criteria

Sustained throughput ≥ 400 MB/s single-core (slower than FastCDC's M1 — the GF(2) inner loop is the bottleneck, as ADR-01 predicts). Boundaries on the LBFS reference corpus match the published paper's documented boundaries. Cross-chunker ingest of the same stream produces differing dedup ratios but each chunker dedups correctly within its own pool.

20.5 Conformance Fixtures

lbfs_reference.corpus — expected boundaries per Muthitacharoen et al. 2001. cross_ chunker_isolation.fixture — same stream, both chunkers, assert independent correctness. rabin_chunker conformance bucket.

20.6 Pitfalls

The irreducible polynomial is a wire-version constant, not a tunable — changing it is a major on-disk-version bump (§29), identical in kind to a gear-table change (§13.9). The 48-byte window is the literature reference; a smaller window is faster but produces worse boundary distributions — exposed as a tunable in a later extension of this phase, not Phase 8 itself.

20.7 Performance Concerns

The GF(2) modular reduction (one table lookup per byte, but over a costlier construction than gear-hash's simple add) is the throughput ceiling — 400 MB/s vs. FastCDC's 1 GB/s is the concrete, measured cost of LBFS-faithfulness (ADR-01's rationale, quantified).

20.8 Edge Cases

A stream shorter than the 48-byte window: the rolling fingerprint never fully populates; the chunker emits the whole stream as one trailing chunk (mirrors §13.8's FastCDC handling for consistency).

20.9 Failure Analysis

A pool accidentally mixing Rabin- and FastCDC-chunked ingests without the chunker-version stamp being checked: symptom is silently degraded dedup ratio (chunks from the two chunkers never collide); detection is the pool-header chunker-version check at ingest time (should refuse a mismatched chunker against an established pool); recovery is operator reconfiguration.

20.10 Operational Notes

dedup stats (§25.4) reports which chunker a pool uses; this is surfaced prominently because it is the single most consequential per-pool configuration choice after the hash algorithm.

21. Phase 9 — Per-Chunk AEAD Encryption

21.1 Objectives

Let the pool be shared across tenants without exposing chunk contents to each other: per-chunk AEAD with HKDF-derived keys (ADR-06, ADR-14, ADR-23, P10, I8).

21.2 Detailed Implementation Steps

Derive each chunk's key via HKDF-Expand(pool_key, info=fp, salt=[0x01]) (RFC 5869) — the salt is a fixed domain separator so this HKDF use cannot be confused with another use of the pool key (Aumasson, §5). Seal with ChaCha20-Poly1305 (RFC 8439, ADR-14) using a deterministic nonce (the fingerprint's low 12 bytes, ADR-23) and AAD [chunker_version | aead_version]. The dedup-preservation argument (I8): two chunks with identical plaintext have identical fp (SHA-256 collision resistance, P1) and therefore identical ciphertext under the same pool key (deterministic construction) — so the index lookup on fp continues to identify duplicates post-encryption. Nonce reuse, normally catastrophic for an AEAD, is safe here specifically because same-nonce implies same-key-same-plaintext by construction (documented explicitly in the threat model, T7, so a reviewer does not flag it as a bug).

21.3 Deliverable

An AeadCipher implementation (ChaCha20Poly1305Cipher, §11.8) wired into the write/read path behind EntryFlags::ENCRYPTED, with a fixed-vector conformance test for the key derivation.

21.4 Acceptance Criteria

Encrypt a 64 KiB chunk in ≤ 100 µs single-core (M10). Same plaintext under the same pool key always yields the same ciphertext (I8). A ciphertext authenticated under one pool key fails to authenticate under a different pool key (tenant isolation). A bit-flipped ciphertext is rejected by the Poly1305 MAC.

21.5 Conformance Fixtures

hkdf_fixed_vector.fixture — HKDF output against RFC 5869 test vectors plus this project's domain-separator salt. tenant_isolation.fixture — cross-pool-key authentication failure. bitflip_reject.fixture — MAC rejects a flipped ciphertext byte. encryption conformance bucket.

21.6 Pitfalls

The pool key must never be written to disk in the clear — HSM/KMS/env-var are the only supported sources, documented as the runbook's first chapter (§28, T7). Encrypting before compressing (violating I9/ADR-03) destroys the ratio — this is re-stated here because Phase 9 is where an implementer is most tempted to reorder for "simplicity."

21.7 Performance Concerns

ChaCha20-Poly1305 is chosen over AES-GCM specifically for CPUs lacking AES-NI (ADR-14); benchmark both if the deployment target has AES-NI available and FIPS mode is not required, to confirm ADR-14's assumption holds for that hardware.

21.8 Edge Cases

A pool-key rotation (planned or forced by a suspected leak, T7): every chunk's derived key changes, requiring a full re-encrypt pass — an expensive, deferred operator tool (PhaseDeferred("§21.10")). A tenant who does not hold the pool key: sees ciphertext only, by design (§1 non-goals boundary).

21.9 Failure Analysis

Encryption key derivation flaw (T7-adjacent): symptom would be a fixed-vector conformance failure; root cause would be an HKDF misconfiguration (wrong salt/info ordering); detection is the encryption conformance bucket run on every CI build; recovery before release is trivial (fix and re-run); post-release, it would require a pool-wide key-derivation migration (§29).

21.10 Operational Notes

Encryption is opt-in per pool at creation time; dedup stats reports whether a pool has encryption enabled. Per-tenant key-rotation tooling and UI are deferred (PhaseDeferred("§21.10"), registered §39) — Phase 9 ships the primitive, not the operator workflow around key lifecycle.

22. Phase 10 — Compaction

22.1 Objectives

Reclaim the bytes left behind by GC's logical tombstoning (§18.2): compact sealed containers whose live-byte ratio has fallen below a threshold (ADR-05, ADR-22).

22.2 Detailed Implementation Steps

Per sealed container, compute the live ratio (fraction of bytes not tombstoned); if below 50% (default), schedule compaction. The compactor reads live chunks, writes them to a fresh active container, and — the concurrency-critical step — atomically swaps each moved chunk's IndexEntry via a versioned CAS: read the entry (capturing its version), copy bytes, then compare-and-swap the entry's container/offset/version; a failed CAS (the entry was concurrently modified, e.g. by a writer or the GC) aborts and retries that chunk (applying I12). Readers holding a cached IndexEntry across a compaction that deletes their container see a NotFound from the store and re-lookup (the cache is advisory, never authoritative).

22.3 Deliverable

A Compactor reducing pool size proportionally to reclaimed tombstoned bytes, verified under a 1-hour chaos run with concurrent ingest and GC.

22.4 Acceptance Criteria

A 100 GiB pool at 50% tombstoned content compacts to ≤ 55 GiB within 30 minutes (M11). A 1-hour chaos test running compaction, GC, and ingest concurrently loses zero chunks (I12). A reader holding a stale IndexEntry cache across a compaction re-looks-up and succeeds.

22.5 Conformance Fixtures

compaction_1h_chaos.fixture — concurrent ingest+GC+compaction, zero-loss assertion. stale_cache_reread.fixture — reader survives a compaction underneath it. compaction conformance bucket — CAS-swap correctness.

22.6 Pitfalls

Compaction's bandwidth amplifies disk write load by the compacted container's live ratio — a pool compacting weekly at 50% live-ratio rewrites half the pool's bytes again every week; SSD endurance must be sized to this (§36 item 7, documented in the operator runbook, §28). The compaction-write-then-swap sequence must be atomic per chunk (I12) — a crash mid-sequence leaves bytes in the new container unreferenced (a space leak, not a correctness violation, self-healing on the next compaction pass) and the old entry pointing at a container that still exists until compaction completes; do not weaken the atomic swap. Cold-tier (e.g. Glacier-class) compaction targets are deferred (PhaseDeferred("§22.6"), registered §39).

22.7 Performance Concerns

The read-verify-write-CAS sequence per chunk is compaction's cost unit; batching multiple chunks' CAS attempts reduces per-chunk overhead without weakening the per-chunk atomicity guarantee.

22.8 Edge Cases

A container whose live ratio is exactly at the 50% threshold: compaction is scheduled (≥ threshold triggers, tie-breaks toward compacting — documented, not ambiguous). A CAS failure storm (many chunks in one container all racing a concurrent GC sweep): the compactor backs off and retries the whole container on the next scheduled pass rather than looping indefinitely.

22.9 Failure Analysis

Compaction data loss (FM-7, should be unreachable given correct atomic CAS): symptom would be a chaos-test failure or a missing chunk post-compaction; root cause would be a non-atomic swap bug; detection is the mandatory 1-hour chaos gate in CI (§30); manual recovery, if it ever occurred in production, restores from a pre-compaction container backup if retained (documented as a defense-in-depth, not a required feature).

22.10 Operational Notes

dedup_compaction_bytes_moved_total and dedup_compaction_cas_retries_total are exported (§28). The runbook "Compaction filled the disk" (§28) covers the emergency throttle and free-space-reserve procedure for the transient extra space compaction needs mid-run (old + new container coexist briefly).

23. Phase 11 — Distributed Pool Sharding

23.1 Objectives

Scale past a single host's index-RAM ceiling (§4, §36) by sharding the index across ingest hosts and layering chunk storage on a distributed backend (ADR-18, P13).

23.2 Detailed Implementation Steps

Shard the index by fingerprint prefix (Fingerprint::prefix64, §11.1); a 16-shard pool routes on the high 4 bits — a pure, deterministic function (I14). Each shard is an independent B-tree+WAL pair (Phase 2 reused per-shard, applying P12 recursively). Two storage backends: DfsPool writes containers to the rank-86 distributed file system at /dedup-pool/<container_id> (replication/durability/HA delegated, ADR-18); S3Pool writes to an S3-compatible bucket keyed by container_id, with the index entry's container field gated on an S3-confirmed write (defending against S3's eventual- consistency read-after-write lag, T11). A shard router on each ingest node dispatches lookups/inserts to the owning shard; a locality-preserving cache keyed by the manifest being ingested (Zhu et al. 2008, sec. 3.1, extending §16.6's deferred single-host cache to the cross-shard case) reduces cross-shard lookup amplification (Bhagwat et al. 2009's bin-routing idea informs this layer's design).

23.3 Deliverable

A DfsPool and an S3Pool backend, a deterministic shard router, and cross-shard manifest reconstruction (a manifest may reference fingerprints owned by multiple shards; reading it is one shard lookup, reconstructing its chunks up to N shard lookups, §8.3).

23.4 Acceptance Criteria

DfsPool ingests a 1 TiB workload at ≥ 200 MB/s aggregate across 4 ingest hosts (M12). Cross-shard manifests reconstruct correctly (fixture below). Shard routing is deterministic — the same fingerprint always resolves to the same shard on every host (I14).

23.5 Conformance Fixtures

cross_shard_manifest.fixture — a manifest spanning ≥ 3 shards, assert correct reconstruction. shard_routing_determinism.fixture — same fingerprint, multiple hosts, assert identical shard resolution. distributed_pool conformance bucket.

23.6 Pitfalls

Cross-shard lookup amplification is the obvious bottleneck — the locality-preserving cache (§23.2) mitigates it for streams with locality, which covers most real workloads. S3's eventual-consistency surface is small but real: a just-written object can briefly return NoSuchKey; the pool retries with backoff, and the index — never the store — is the source of truth for "did this write happen" (T11). Lock-free shard routing (replacing the parking_lot::RwLock-guarded HashMap router, which contends under high concurrency) is deferred (PhaseDeferred("§23.6"), registered §39). Deepened erasure-coded parity under the pool (beyond delegating whole-container durability to rank-86/108) is likewise deferred (PhaseDeferred("§23")).

23.7 Performance Concerns

Aggregate ingest throughput is bounded by the shard router's per-host dispatch cost plus the locality cache's hit rate — both are benchmarked against M12; a cache miss costs one full cross-host round trip, bounded by the §4 network-RTT budget (§36 item 10).

23.8 Edge Cases

A shard that becomes temporarily unreachable (network partition): ingests touching that shard's fingerprint range block or fail per the configured backpressure policy (not silently dropped — I3's referential-integrity requirement forbids partial manifests). A rebalance (adding a 17th shard) is out of Phase 11's scope — the routing function is fixed at pool-creation time; changing it is a major migration (§29, I14's recovery column).

23.9 Failure Analysis

Shard hot-spotting (FM-11): symptom is one shard's queue depth far exceeding others; root cause is fingerprint-prefix skew from adversarial or pathological input; detection is per-shard queue-depth comparison; there is no built-in auto-recovery; manual recovery rate-limits the offending producer or (deferred) adds shard rebalancing.

23.10 Operational Notes

dedup_shard_queue_depth (per-shard gauge) is the primary distributed-pool dashboard addition (§28). The Phase-11 deployment topology (Kubernetes StatefulSet, Helm chart at ops/helm/) is documented in the "Operations" material under Operational Readiness (§28).

24. Phase 12 — Interop Import & FUSE Export

24.1 Objectives

Make a new pool interesting on day one: import existing Restic/BorgBackup repositories, and expose a manifest as a mountable read-only file system via FUSE.

24.2 Detailed Implementation Steps

Import (dedup-import): read each foreign pack/repository file's chunks bit-for-bit (no re-chunking — the foreign chunker's boundaries are preserved as-is, since re- fingerprinting under this engine's hash would require re-chunking to get any dedup benefit at all, and that is out of scope for Phase 12), ingest each chunk under a foreign-chunker-version tag, and emit a manifest mapping the imported snapshot to this engine's fingerprints (leaning on ADR-15's rejected-CBOR case — a foreign-tag-bearing manifest is exactly the regime ADR-15 names for a schema'd format, §9). Export (dedup-fuse): a FUSE adapter translates read(offset, length) into the sequence of chunk fetches spanning that range (chunked at manifest boundaries, decompress+decrypt each), backed by the OS page cache for repeat/sequential reads.

24.3 Deliverable

A restic-import and borg-import CLI tool; a FUSE adapter mounting a manifest read-only such that cat/cp/md5sum work unmodified against it.

24.4 Acceptance Criteria

restic-import imports a 100 GiB Restic repository in ≤ 1 hour. borg-import imports an equivalent BorgBackup repository. A FUSE-mounted manifest passes an md5sum comparison against the original source file.

24.5 Conformance Fixtures

restic_import_100gib.fixture — timed import + content-hash verification. borg_import_ equiv.fixture — same, for BorgBackup. fuse_read_verify.fixture — mount, md5sum, compare to source.

24.6 Pitfalls

Foreign chunkers (Restic's Rabin variant, Borg's Buzhash) produce different boundaries than FastCDC — imported chunks live in their own chunker-version partition and do not dedup against native-FastCDC chunks of the same underlying content (documented as the operator's first question post-import). Re-chunking on import to fix this is deferred (PhaseDeferred("§24.6"), registered §39) — it is a real feature, not a rejected idea, just out of Phase 12's budget. FUSE's read API does not align to chunk boundaries; the adapter must correctly handle a read spanning a chunk-boundary midpoint.

24.7 Performance Concerns

Non-sequential FUSE read workloads pay a per-chunk lookup+fetch cost each; the page cache absorbs repeat/sequential access cheaply but does nothing for genuinely random access patterns — documented as a known limitation, not solved in Phase 12.

24.8 Edge Cases

A Restic repository using a pack format version this engine's importer does not recognize: the importer refuses with a clear version-mismatch error rather than silently misparsing pack contents. A FUSE read past end-of-file: returns a short read per standard POSIX semantics, not an error.

24.9 Failure Analysis

An interrupted import (killed mid-way through a large repository): symptom is a partially-populated pool with an incomplete manifest; detection is the importer's own manifest-commit-last discipline (mirroring I3 — no manifest commits until every foreign chunk it references is confirmed indexed); recovery is simply re-running the import (idempotent, since already-imported chunks dedup for free).

24.10 Operational Notes

Imported pools are tagged with their source chunker version in dedup stats output, so an operator immediately understands why cross-pool dedup ratio looks lower than expected for imported content.

25. Phase 13 — Operator Tooling

25.1 Objectives

Ship the operator surface a live pool needs: fsck, gc, scrub, and stats as first-class CLI commands, closing the loop on every invariant and failure mode named in earlier phases.

25.2 Detailed Implementation Steps

dedup fsck walks the pool checking: index entries pointing to nonexistent containers; containers whose footer CRC32C fails (I4); manifests referencing fingerprints absent from the index (I3); tombstoned entries GC missed (I5); chunks in containers no index entry references (orphans). Output is a JSON report plus a human-readable summary; --repair removes dead-container index entries and surfaces the rest for operator action. dedup gc runs the Phase-6 collector with --dry-run, --throttle <MB/s>, --verbose flags. dedup scrub runs the Phase-7 scrubber on demand. dedup stats reports pool size, unique-chunk count, dedup ratio (lifetime + 24 h), compression ratio, GC tombstoned count, scrub corrupt count, manifest count, container age distribution — matching the Prometheus dashboard line-for-line (P14's "measured, reported" discipline made concrete).

25.3 Deliverable

A complete dedup CLI operator surface: fsck, gc, scrub, stats, put, version, repair.

25.4 Acceptance Criteria

fsck checks a 100 M-fingerprint pool in ≤ 30 minutes. gc --dry-run completes in ≤ 5 minutes on the same pool. stats output matches the Prometheus dashboard values exactly (a CI assertion comparing the two, not just eyeballing).

25.5 Conformance Fixtures

fsck_100m_pool.fixture (timed, against a synthetic 100 M-entry pool). stats_dashboard_ parity.fixture — assert CLI and Prometheus report identical numbers at a fixed instant.

25.6 Pitfalls

fsck on a live pool is a bandwidth amplifier (every container's footer is read, every manifest dereferenced) — throttle it the same way the scrubber is throttled (§19.7). The "manifest references a missing fingerprint" check (I3 violation) is the most common operator-detected corruption in practice — an interrupted ingest that committed a manifest before all its chunks landed (should be prevented by §16.2's ordering, but fsck is the backstop); the repair path is "remove the manifest," and the underlying bytes are genuinely unrecoverable, but the rest of the pool remains intact.

25.7 Performance Concerns

fsck --repair's dead-container-entry removal is a single index scan; the manifest- dereference scan is the expensive part (one lookup per fingerprint per manifest) and is the primary target of the throttle flag.

25.8 Edge Cases

Running dedup gc and dedup fsck --repair concurrently: fsck's dead-container-entry removal must not race GC's own sweep — both take the index's standard concurrency discipline (I6-style pinning is not required here since fsck --repair only removes entries already known-dead, not live candidates).

25.9 Failure Analysis

An fsck run that itself crashes mid-report: no state is mutated until --repair is explicitly passed and each repair action is applied one index entry at a time — a crash leaves a partial report, not partial repairs; re-running fsck from scratch is always safe.

25.10 Operational Notes

dedup stats is the first command in every runbook in §28 — every operational investigation starts by establishing the pool's current numbers before diagnosing a delta.

Metrics (Prometheus, :9100/metrics): dedup_bytes_in_total, dedup_bytes_stored_total, dedup_chunks_new_total, dedup_chunks_dup_total, dedup_index_lookup_seconds (histogram), dedup_chunker_throughput_bytes_per_second (gauge), dedup_gc_tombstoned_total, dedup_scrub_corrupt_chunks_total, dedup_containers_total (gauge), dedup_active_container_bytes (gauge), dedup_compaction_bytes_moved_total, dedup_shard_queue_depth (per-shard gauge, Phase 11), dedup_wal_replay_seconds (histogram).

Tracing. OpenTelemetry spans (ADR-17) wrap every chunker invocation, index lookup/insert, and container write; span attributes carry the Fingerprint prefix and ManifestId for correlation.

Structured logging. JSON logs; every log line carries pool_id, stream (if applicable), and the relevant invariant/ADR ID when logging a violation or a decision point.

Dashboards. One dashboard per phase's primary metric group (ingest throughput, index latency, GC/compaction, scrub health, distributed-pool shard balance) plus one top-level "dedup ratio + storage savings" executive view (P14).

Alerting philosophy. Page on-call for: I1/I2/I3/I4 violations (any fsck-detected corruption class), a GC cycle exceeding 2× its M8 target, a scrub cycle falling behind its 30-day schedule by more than one week, and any FM-1..FM-12 class exceeding its baseline rate. Do not page for a single retried S3 call (T11) unless retries exhaust.

SLOs. Ingest p99 latency ≤ 2× M6's throughput-implied per-chunk latency; dedup_ratio monotonicity (I10) as a correctness SLO, not a performance one; pool availability ≥ 99.9% single-host, ≥ 99.95% distributed (Phase 11).

Incident response. Named runbooks (below) are the first response artifact; every incident review cites the invariant or failure-mode ID it maps to (§7, §27) for consistent postmortem taxonomy.

Named runbooks (docs/runbooks/): "Ingest is slow" (chunker throughput → index p99 → store write throughput, in that order); "Dedup ratio dropped" (chunker boundary distribution first, source-data change second); "Scrubber reported a corrupt chunk" (FM-5 repair path); "GC took too long" (manifest count, pin conflicts, shard distribution); "Compaction filled the disk" (emergency throttle, free-space reserve).

Backup/restore. The pool's own chunk store and index are the backup target of a higher-level system (out of this project's scope, §1 non-goals) — this engine documents how to snapshot a checkpoint + WAL + container set consistently, not how to schedule that snapshot.

Deployment topology. Single binary + Dockerfile through Phase 10; a Kubernetes StatefulSet (Helm chart, ops/helm/) for the Phase-11 distributed pool.

Canary / rolling-upgrade / rollback / migration. A new engine version is canaried against a single shard first (Phase 11) or a single-host staging pool (Phase 0–10); rollback is supported for any version that has not yet bumped the on-disk version (§29); a version bump requires the full migration procedure in §29.

29. Compatibility & Versioning

Wire versioning. dedup-proto's .proto messages (Phase 11) are versioned via a leading aead_version/chunker_version byte pair carried in every wire frame and every chunk's AAD (§21.2); old wire versions are decodable for at least 2 major releases.

Storage/schema evolution. The on-disk version (dedup-core::version) bumps on any of: the chunker's gear table or irreducible polynomial (§13, §20); chunk min/avg/max bounds (I11); the hash algorithm (SHA-256 → BLAKE3 is a major bump, §39); the container format (§15.1); the manifest format (ADR-15); the AEAD construction (§21). A bump is a major-version event (I13): the engine refuses to open a pool whose on-disk version exceeds its own.

API stability. IndexService/StoreService/ManifestService/Chunker/ Compressor/AeadCipher (§11) are the stable trait surface; additive changes (new methods with defaults) are minor; signature changes are major.

Migration. A hash-algorithm or chunker change requires a full pool re-ingest (no in-place migration is defined — the fingerprint space itself changes); a container- format or manifest-format change is handled by a one-time offline migration tool (deferred design, PhaseDeferred not applicable here since this is future-scoped tooling outside the current 14 phases, tracked in BUILD_PLAN.md instead).

Deprecation policy. A deprecated trait method or CLI flag survives 2 minor releases with a warning before removal.

SemVer policy. MAJOR.MINOR.PATCH on the on-disk/wire version pair; the crate versions in Cargo.toml follow standard Rust SemVer independently of the on-disk version.

Rolling-upgrade guarantees. Within Phase 11's distributed pool, shards may run different engine patch versions transiently during a rolling upgrade; minor-version skew across shards is supported for the duration of the upgrade window; major-version skew is not (I13 enforces this at the per-shard pool-open check).

30. Testing & Verification Strategy

Unit. Per-crate, per-type; every dedup-core type (§11) has fixed-vector and round-trip tests.

Integration. Cross-crate pipeline tests (§16's ingest pipeline end-to-end).

Property-based. The chunker's bound-respect (I11) and edit-invariance (§13.4) properties are checked via property tests generating randomized insert/delete edits.

Differential. The Rabin and FastCDC chunkers are differentially tested against each other's isolation property (§20.4) — never expected to agree on boundaries, but each must independently satisfy I11 and edit-invariance.

Fuzzing. dedup-fuzz targets: fuzz_fastcdc (arbitrary byte streams into the chunker), fuzz_container_parse (malformed container bytes into the store's reader), fuzz_manifest_codec (malformed manifest bytes into the ADR-15 codec) — all gated in security.yml (§10).

Chaos. Torn-write (§15.9), GC-race (§18.4), compaction-race (§22.4) — each a named CI job in chaos.yml, each mapped to an invariant (I4/I6/I12).

Deterministic replay. The dedup-conformance::sim simulator (§7's debugging methodology) drives all fourteen invariants from a fixed seed, logged on every run for bit-for-bit reproduction of a failure.

Soak. A 24-hour continuous-ingest + periodic-GC + periodic-scrub soak run is a release gate (release.yml), watching for slow leaks in pin registries (FM-8) or container-fd accounting.

Fault injection. Byte-flip injection (scrubber detection, §19.4), fake-collision injection (T3/FM-6), and forced-kill injection (torn-append/index-desync, FM-1/FM-2) are all first-class test-only APIs, not ad hoc debugging hacks.

Conformance. The bucket system (§7, one bucket per subsystem: core_types, fastcdc_chunker, rabin_chunker, sha256_hash, btree_index, chunk_store, manifest, inline_ingest, compression, garbage_collection, scrubber, encryption, compaction, distributed_pool, chaos) reports Pass | Fail(reason) | Deferred; every phase's N.5 fixtures feed a bucket.

Performance-regression gating. Every M1–M12 target (§32) is checked in CI on every release; a regression beyond 5% fails the release (release.yml).

This strategy ties directly back to the System Invariants (§7) and each phase's N.5 fixtures — no invariant exists without at least one fixture exercising it, and no fixture exists without a named invariant or acceptance criterion it verifies.

31. Build & Release Engineering

Reproducible builds. Nix flake (nix/flake.nix, ADR-20) pins the toolchain; sccache caches compilation across maintainer machines; a release build is bit- reproducible given the same Nix input hash.

Artifact signing. Release binaries are signed (minisign or cosign, keys held in the same KMS class as the pool key, T7's discipline extended to build artifacts).

SBOM. A CycloneDX SBOM is generated per release from Cargo.lock, published alongside the binary.

Release channels. stable (tagged releases only), nightly (main branch, best- effort). Distributed-pool operators (Phase 11) are advised to stay on stable.

CI/CD topology. ci.yml (build+unit+integration) → conformance.yml (full bucket run) → chaos.yml (1-hour chaos gate) → security.yml (fuzz+dependency audit) → release.yml (reproducible build+sign+SBOM+perf-regression gate) — each a required check before merge to main, with release.yml additionally required before a tag.

Version stamping. The on-disk/wire version (§29) and the build's git commit hash are both embedded in dedup version's output.

Provenance/attestation. SLSA-style build provenance is attached to release artifacts, recording the exact CI job and commit that produced them.

Dependency auditing. cargo audit runs in security.yml on every PR; a new transitive dependency touching dedup-core, dedup-hash, or dedup-encrypt (the cryptographic surface) requires an explicit ADR justifying it, per the terminology- and-decision discipline of §9.

32. Performance Engineering

Methodology. The USE method (Gregg, §5 books) — Utilization, Saturation, Errors — applied per subsystem: chunker CPU utilization, index-lock saturation, store fsync errors/latency. Profiling via perf/flamegraph on the chunker's gear-hash inner loop and the index's B-tree traversal (the two hottest paths per §4). Allocation profiling (dhat) confirms bytes::Bytes sharing (P4) actually avoids the copies it is designed to avoid. Lock-contention analysis (tokio-console) on the index's write lock (§14.7) and the Phase-11 shard router's RwLock (§23.6, motivating its deferred lock-free redesign). Tail-latency analysis (p99/p999) on index lookup and chunk-store writes, since both are user-facing latency contributors to end-to-end ingest (M6).

33. Scalability Analysis

Constant vs. grows. Chunk size distribution stays constant regardless of pool size (a property of the chunker, not the pool, P3). Index RAM grows O(N) in unique fingerprint count (§36 item 1) — this is the dominant growth term (P13, MM2). Chunk store disk usage grows O(N × avg_chunk_size / dedup_ratio) — sublinear in logical data ingested precisely because of deduplication (I10). GC mark-phase cost grows O(N) in chunks plus O(M) in manifest-graph size; sweep cost is O(N) (a full index scan).

Named bottlenecks in order: (1) index RAM (§4's defining property) — binds first, around 390 M chunks/host (§36 item 2); (2) index lookup latency under high cross-shard amplification (Phase 11, mitigated by locality caching, §23.6); (3) compaction write amplification at high tombstone churn (§36 item 7); (4) chunker single-core throughput (M1) — the least likely to bind first, since it is the cheapest to horizontally scale (one chunker instance per ingest stream, embarrassingly parallel).

Horizontal scaling. Sharding by fingerprint prefix (§23.2, I14) is the only lever past the index-RAM ceiling — it is horizontal by construction (each shard is an independent host-local pool).

Vertical scaling. More RAM per host raises the single-host ceiling linearly (§36 item 2's formula) but does not change the O(N) growth term — it only moves the bottleneck point, never removes it (P13).

Sharding/partitioning. Fingerprint-prefix partitioning (§23.2) is chosen over content-similarity partitioning (Extreme Binning's approach, Bhagwat et al. 2009) for simplicity and determinism (I14); the tradeoff is that similarity-aware partitioning could improve locality-cache hit rates further — a future direction, not this blueprint's choice.

Coordination overhead. Cross-shard manifest reconstruction (§23.3) is the only coordination point in the read path; the write path requires no cross-shard coordination (each chunk's shard is independently resolved and written).

Practical ceiling and levers beyond it. With 16 shards at 64 GiB RAM each, the pool supports roughly 16 × 390 M ≈ 6.2 B unique chunks before a 17th shard (and the un-deferred rebalancing tooling, §39) becomes necessary — the practical ceiling of this blueprint's design as specified; the lever beyond it is either more shards (requiring rebalancing) or a sparse/sampled index (Lillibridge et al. 2009, §5) trading exactness for RAM at a much higher shard count.

34. Mental Models & First Principles

  • MM1 — A fingerprint is not a name, it's a proof. Insight: content-addressing means the address is a claim about the content. Predicts: any two chunks with equal fingerprints are safely interchangeable. Bug class without it: engineers treating fingerprints as opaque IDs reintroduce location-addressing aliasing bugs. Resolving: §7 (I1), §11.
  • MM2 — The index is the pool's only expensive resource. Insight: disk is cheap; RAM for fingerprints is the binding constraint. Predicts: every scaling decision (sharding, sparse indexing) is really an index-RAM decision. Bug class without it: optimizing chunk-store throughput while ignoring index RAM hits an OOM wall at scale. Resolving: §4, §36.
  • MM3 — GC is a distributed-consensus problem in miniature. Insight: mark-and-sweep concurrent with writers is the same reachability-under-concurrent-mutation problem as a language runtime's concurrent GC. Predicts: writer-pin/epoch mechanisms mirror GC write-barriers. Bug class without it: naive GC that does not pin in-flight manifests loses just-written data. Resolving: §18, I6.
  • MM4 — Append-only turns crash recovery into arithmetic. Insight: an append-only container reduces "what got corrupted?" to "where did writing stop?" Predicts: recovery is always a forward scan to the first bad CRC, never a global repair. Bug class without it: in-place stores need a full-structure fsck; this design needs only a tail scan. Resolving: §15.4, §27.
  • MM5 — Compression and encryption commute in cost, not in effectiveness. Insight: pipeline order doesn't affect whether both operations succeed, but drastically changes the ratio. Predicts: any pipeline analysis must check operation order first. Bug class without it: silent ratio regressions from a reordered pipeline. Resolving: I9, §17.
  • MM6 — A manifest is a chunk about chunks. Insight: recursion is the same mechanism at every layer — a fingerprint addresses bytes, whether those bytes are file data or a list of fingerprints. Predicts: GC, storage, and versioning treat manifests uniformly with chunks. Bug class without it: special-casing manifest storage duplicates the store/index code path and doubles the bug surface. Resolving: §8, §16.2.
  • MM7 — Dedup ratio measures data, compression ratio measures entropy. Insight: the two ratios answer different questions and multiply, they don't add. Predicts: an operator dashboard must report both, never collapse them into one number. Bug class without it: support tickets from operators confused why "the one ratio" doesn't match. Resolving: §17.6, §28.
  • MM8 — Content-defined chunking trades determinism for boundary stability. Insight: CDC accepts unpredictable per-chunk sizes in exchange for boundaries that survive edits. Predicts: any workload with globally-shifting content must never use fixed-size chunking. Bug class without it: "optimizing" by switching to fixed blocks silently destroys dedup ratio on edited files. Resolving: I11, §13, ADR-07.

36. Back-of-Envelope Capacity Model

  1. Index RAM per 100 M chunks. IndexEntry ≈ 48 B raw; B-tree internal-node overhead ≈ 1.7× at rank-67's ~85-entries/leaf: RAM = N × entry_size × overhead = 100M × 48B × 1.7 ≈ 8.16 GiB (matches §4).
  2. Max chunks/host before resharding. Given 64 GiB host RAM, 50% budget for the index (32 GiB): N_max = RAM_budget / (entry_size × overhead) = 32GiB / 81.6B ≈ 390 M chunks.
  3. Unique-data capacity per host. At 64 KiB average chunk size: capacity = N_max × avg_chunk_size = 390M × 64KiB ≈ 23.8 TiB unique-chunk capacity per host.
  4. Logical (pre-dedup) capacity per host. At a representative 10:1 backup dedup ratio (Meyer & Bolosky 2011 range): logical_capacity = unique_capacity × dedup_ratio = 23.8 TiB × 10 ≈ 238 TiB addressable per host.
  5. Single-core ingest throughput ceiling. Serial pipeline stages (chunker ≈1.0 GB/s, hasher ≈1.2 GB/s): throughput = 1 / Σ(1/stage_i) = 1 / (1/1.0 + 1/1.2) ≈ 0.545 GB/s — consistent with the measured ≥500 MB/s target (M6, §4).
  6. Cached container FD footprint. cached_bytes = cached_fds × container_size = 64 × 16 MiB = 1 GiB of container data resident per host (§4 FD budget).
  7. Compaction weekly write amplification. Worst case, a container triggers compaction exactly at the 50% live-ratio threshold: bytes_rewritten = 0.5 × container_size = 8 MiB per compacted container; at compaction rate R containers/week, weekly_rewrite = R × 8 MiB — sizes SSD endurance planning (§22.6).
  8. GC mark-phase memory. mark_bits = N_chunks / 8 = 390M / 8 ≈ 48.75 MiB — negligible next to index RAM (item 1), consistent with the smaller-pool figure of 12.5 MiB at 100 M chunks.
  9. Scrub full-pool-walk time. scrub_time = pool_size / throttle_bw = 1 TiB / 70 MB/s ≈ 14,979 s ≈ 4.16 h — tight against the ≤4.5 h target (M9); documented as a deliberately narrow margin, not slack.
  10. Distributed shard-lookup RTT budget. p99_budget ≥ 2 × RTT + local_processing; solving for a 5 ms p99 target with ~0.5 ms local processing: RTT ≤ 2.25 ms — comfortably above typical intra-rack RTT (~0.1–0.5 ms), giving headroom (§4).

38. Alternative Architectures (Roads Not Taken)

Alt 1 — Fixed-block dedup (ZFS DDT style).

   write(offset, bytes) --> block-align to 4/8 KiB --> SHA-256 --> DDT lookup
                                                                       |
                                                        hit: bump refcount
                                                        miss: allocate + store

Regime where it wins: primary-storage block devices where the block layer already presents fixed offsets that never shift — CDC's edit-stability benefit (P2) is then moot. Real system: OpenZFS (ddt.c, §5). Rejection: this blueprint targets stream-level dedup across edited files/backups (§1), where fixed blocks collapse dedup ratio on any insert/delete (ADR-07).

Alt 2 — Similarity-based delta encoding (not exact dedup).

   new file --> similarity search (minhash/shingling) --> nearest existing file
                                                                |
                                              binary diff (xdelta/bsdiff) --> delta blob

Regime where it wins: near-duplicate but non-identical files (e.g. VM images with small config diffs) where exact-chunk dedup finds little redundancy but a byte-level diff finds much more. Real system: rsync's delta algorithm; xdelta/bsdiff-based tools. Rejection: this blueprint targets exact-chunk dedup with a simpler, index-lookup-based correctness argument (I1/I2); similarity search plus diffing is a much harder search problem with a fuzzier correctness story, deliberately out of scope (§1 non-goals).

Alt 3 — Client-side convergent encryption, server-blind dedup.

   plaintext --> key = H(plaintext) --> encrypt(plaintext, key) --> upload ciphertext
                                                                          |
                                                      server dedups ciphertext blindly

Regime where it wins: zero-trust storage providers who must never see plaintext or a plaintext-derived pool key. Real system: Tahoe-LAFS's convergent-encryption mode; some zero-knowledge backup services. Rejection: convergent encryption alone leaks a confirmation-of-file oracle (an attacker who guesses a plaintext can confirm its presence by computing the same key/ciphertext) — this blueprint's HKDF-from-pool-key design (ADR-06, ADR-23) requires possession of the pool key, closing that channel at the cost of requiring a trusted key-holding party rather than being fully server-blind.

40. Glossary

  • Chunk — a variable-size slice of an input stream, identified by its SHA-256 fingerprint.
  • Container — a 16 MiB on-disk file holding a sequence of chunks; sealed and immutable once full.
  • Fingerprint — the SHA-256 over a chunk's bytes; the chunk's address (P1).
  • Manifest — an ordered list of fingerprints reconstructing a stream; itself stored as a chunk (informally, a "recipe").
  • Pool — the collection of containers, index, and manifests forming one deduplication context.
  • Cut point — a stream offset at which the chunker declares a chunk boundary.
  • Dedup ratio — bytes_in / bytes_stored; always ≥ 1.0 (I10); higher is better.
  • Tombstone — a logical delete; the index entry is flagged, bytes remain until compaction.
  • GC (garbage collection) — the mark-and-sweep process reclaiming tombstoned chunks.
  • Scrub — the background re-fingerprint loop that detects bit-rot.
  • Content-Defined Chunking (CDC) — chunking by rolling-hash cut points rather than fixed offsets.
  • Fixed-size chunking — chunking at constant byte offsets; rejected by ADR-07 for edit-instability.
  • Gear hash — FastCDC's per-byte mixing function: h = (h << 1) + gear[byte].
  • Normalized chunking — biasing cut-point probability toward the average size via asymmetric masks.
  • Rabin fingerprint — a polynomial-modular rolling fingerprint over GF(2) (Rabin 1981).
  • Rolling hash — a hash function updatable in O(1) as a window slides over a stream.
  • Chunk store — the append-only container-based subsystem holding chunk bytes.
  • Index — the fingerprint → location (ChunkRef) mapping, backed by a B-tree + WAL.
  • B-tree — the balanced tree structure (rank-67 project) used as the index substrate.
  • WAL (Write-Ahead Log) — the durability primitive (rank-71 project) logging index mutations before they apply.
  • Checkpoint — a full snapshot of the index tree, truncating the WAL to post-checkpoint entries.
  • Sealed container — a container that has reached its size limit and become immutable.
  • Active container — the currently-appendable container accepting new chunk writes.
  • Compaction — rewriting a container's live chunks into a fresh container, reclaiming tombstoned space.
  • Live ratio — the fraction of a container's bytes belonging to non-tombstoned chunks.
  • Mark phase — the GC phase tracing reachability from live manifests.
  • Sweep phase — the GC phase tombstoning unreached index entries.
  • Writer pin — a registered in-flight manifest that the GC treats as live regardless of mark-phase timing (ADR-21).
  • GC epoch — the point-in-time snapshot of live manifests a mark phase traces from.
  • Inline dedup — fingerprinting and indexing a chunk before it is written.
  • Post-process dedup — writing a stream first, then chunking/indexing it from staging.
  • AEAD (Authenticated Encryption with Associated Data) — an encryption mode providing both confidentiality and integrity (e.g. ChaCha20-Poly1305).
  • HKDF — HMAC-based key derivation function (RFC 5869), used to derive per-chunk keys.
  • Nonce — the AEAD's per-message unique value; derived deterministically from the fingerprint here (ADR-23).
  • Domain separator — a fixed salt/label ensuring one HKDF use cannot be confused with another.
  • Convergent encryption — deriving an encryption key from the plaintext itself (rejected, §38 Alt 3).
  • Locality-preserving cache — a cache exploiting the tendency of a stream's chunks to reference recently-seen fingerprints (Zhu et al. 2008, sec. 3.1).
  • Sparse index — a RAM-bounded index technique sampling a subset of fingerprints (Lillibridge et al. 2009).
  • Shard — one independent, host-local index+store partition of a distributed pool.
  • Shard router — the component routing a fingerprint to its owning shard.
  • fsck — the operator tool auditing pool consistency against I1–I14.
  • Torn append — a chunk write interrupted by a crash before its fsync completed.
  • CRC32C — the Castagnoli CRC variant used for chunk-header and container-footer integrity checks.
  • Poisoning (chunk poisoning) — a malicious producer attempting to insert crafted bytes under a forged or colliding fingerprint (T2).
  • Collision (hash collision) — two distinct byte sequences sharing a fingerprint (T3, I2).
  • Byte-compare fallback — the opt-in insert-time verification distinguishing a true duplicate from an observed collision.
  • Segment — Data Domain's term for what this blueprint calls a chunk (§35).
