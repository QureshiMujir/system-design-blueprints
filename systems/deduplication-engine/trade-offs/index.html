ADR-01

Default chunker

Chosen

FastCDC

Rejected

Rabin

When the rejected choice is right

LBFS-compatibility-required pools, or archival fidelity requirements against a published LBFS corpus

Why: gear-hash inner loop has no GF(2) multiply; faster at comparable boundary quality (Xia et al. 2016)

ADR-02

Default hash

Chosen

SHA-256

Rejected

BLAKE3

When the rejected choice is right

ingest CPU-bound above ~2 GB/s/core and FIPS-140 is not required — BLAKE3's throughput dominates

Why: standardized, FIPS-auditable (FIPS 180-4); collision-resistance margin well studied

ADR-03

Pipeline order

Chosen

compress, then encrypt

Rejected

encrypt, then compress

When the rejected choice is right

compression performed by an untrusted third-party service that must not see plaintext — trades ratio for compressor-side confidentiality

Why: encrypted bytes are incompressible; order fixed (I9)

ADR-04

GC model

Chosen

mark-and-sweep from manifests

Rejected

reference-counted

When the rejected choice is right

extremely high manifest-churn workloads (thousands of snapshot deletes/sec) intolerant of GC-pause latency, paired with periodic mark-sweep reconciliation as backstop

Why: ref-counts are fast but corrupt easily under concurrent writers/snapshot deletes

ADR-05

Chunk store

Chosen

append-only + offline compaction

Rejected

in-place mutable store

When the rejected choice is right

spinning-media pools with abundant free space and no compaction budget, accepting fragmentation instead

Why: keeps the write path sequential; crash recovery is a bounded forward scan

ADR-06

Encryption key scheme

Chosen

per-chunk AEAD, HKDF(pool_key, fp)

Rejected

single pool-wide key

When the rejected choice is right

single-tenant pools where cross-tenant dedup is moot and per-chunk HKDF cost is pure overhead

Why: preserves cross-tenant dedup while still isolating key material per chunk

ADR-07

Chunk sizing

Chosen

variable 16 KiB / 64 KiB / 256 KiB

Rejected

fixed-size blocks (4/8 KiB)

When the rejected choice is right

primary-storage block devices where the block layer already presents fixed offsets and never shifts (ZFS's own regime, §35)

Why: edit-stable boundaries (P2); fixed blocks shift on any insert/delete

ADR-08

Index structure

Chosen

B-tree (rank-67)

Rejected

LSM-tree

When the rejected choice is right

write-dominated ingest with few repeat lookups (e.g. first full backup of a mostly-unique corpus) — LSM's write amplification profile wins there

Why: this workload is read-heavy after ingest; B-tree gives p99 lookup ≤ 1 ms (M3)

ADR-09

Index durability

Chosen

WAL (rank-71) ahead of B-tree

Rejected

copy-on-write / shadow paging

When the rejected choice is right

working set fits entirely in RAM and durability can relax to periodic snapshots (e.g. an ephemeral CI dedup cache)

Why: standard, well-understood crash-consistency technique (Arpaci-Dusseau, §5)

ADR-10

Inline/post-process

Chosen

one engine, two configurations

Rejected

forked codepaths

When the rejected choice is right

inline and post-process locking/backpressure semantics diverge so far (e.g. kernel-level primary path vs. userspace staging) that shared abstraction overhead dominates

Why: halves maintenance and bug surface (P8)

ADR-11

Async I/O

Chosen

tokio + bytes

Rejected

sync threaded I/O

When the rejected choice is right

a small, single-tenant, single-stream embedded client where async task-scheduling overhead exceeds its concurrency benefit

Why: bytes::Bytes buffer sharing avoids copies chunker→hasher→store (P4)

ADR-12

Compression

Chosen

zstd (level 3 default)

lz4

When the rejected choice is right

CPU-constrained edge ingest agents where lz4's 3–5× speed advantage matters more than ratio

Why: zstd's ratio at level 3 beats lz4 at all levels for cold-storage corpora; speed delta small

Container size

Chosen

fixed 16 MiB

Rejected

dynamic/tiered sizing

When the rejected choice is right

cold-archival pools writing very large sequential streams once, where 128 MiB+ containers reduce metadata/fsync overhead at the cost of coarser compaction

ADR-23

AEAD nonce

Chosen

deterministic, fingerprint-derived

Rejected

random nonce + stored-nonce

When the rejected choice is right

a threat model where fingerprint-derived determinism is itself an oracle (confirmation-of-file attack) — random nonces close that channel at the cost of dedup preservation

Why: same fingerprint ⇒ same plaintext ⇒ safe nonce reuse is impossible by construction (I8)

Why: tooling/interop; adequate for shard routing traffic

38. Alternative Architectures (Roads Not Taken)

Alt 1 — Fixed-block dedup (ZFS DDT style).

   write(offset, bytes) --> block-align to 4/8 KiB --> SHA-256 --> DDT lookup
                                                                       |
                                                        hit: bump refcount
                                                        miss: allocate + store

Regime where it wins: primary-storage block devices where the block layer already presents fixed offsets that never shift — CDC's edit-stability benefit (P2) is then moot. Real system: OpenZFS (ddt.c, §5). Rejection: this blueprint targets stream-level dedup across edited files/backups (§1), where fixed blocks collapse dedup ratio on any insert/delete (ADR-07).

Alt 2 — Similarity-based delta encoding (not exact dedup).

   new file --> similarity search (minhash/shingling) --> nearest existing file
                                                                |
                                              binary diff (xdelta/bsdiff) --> delta blob

Regime where it wins: near-duplicate but non-identical files (e.g. VM images with small config diffs) where exact-chunk dedup finds little redundancy but a byte-level diff finds much more. Real system: rsync's delta algorithm; xdelta/bsdiff-based tools. Rejection: this blueprint targets exact-chunk dedup with a simpler, index-lookup-based correctness argument (I1/I2); similarity search plus diffing is a much harder search problem with a fuzzier correctness story, deliberately out of scope (§1 non-goals).

Alt 3 — Client-side convergent encryption, server-blind dedup.

   plaintext --> key = H(plaintext) --> encrypt(plaintext, key) --> upload ciphertext
                                                                          |
                                                      server dedups ciphertext blindly

Regime where it wins: zero-trust storage providers who must never see plaintext or a plaintext-derived pool key. Real system: Tahoe-LAFS's convergent-encryption mode; some zero-knowledge backup services. Rejection: convergent encryption alone leaks a confirmation-of-file oracle (an attacker who guesses a plaintext can confirm its presence by computing the same key/ciphertext) — this blueprint's HKDF-from-pool-key design (ADR-06, ADR-23) requires possession of the pool key, closing that channel at the cost of requiring a trusted key-holding party rather than being fully server-blind.
