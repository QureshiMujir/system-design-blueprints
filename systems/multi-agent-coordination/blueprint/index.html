47 — Multi-Agent Coordination System

Project Number: 47

Project Name: Multi-Agent Coordination System

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

A Python-native multi-agent coordination kernel that turns a pool of single-agent runtimes (the Agentic-Framework at portfolio #26) into an orchestrated team. The kernel ships an orchestrator, a typed message bus, a shared blackboard, the contract-net protocol for task allocation, a DAG executor with persistent pause/resume, span-per-agent and span-per-message tracing, role-based arbitration policies, and a library of production patterns (code-review committee, research team, customer-support triage, software-engineering team). The auction-based market protocol, the distributed worker pool, and the hosted control plane are deferred surfaces tracked in the Deferred Features Register.

1. Goal & Scope

Goal. Build a single-process coordination kernel that orchestrates a team of single-agent runtimes into a workflow with hard budget caps, structured cancellation, full-fidelity tracing, and a conformance corpus that measures any implementation against recorded ground truth.

In scope (Phase 0):

  • A typed message bus (Pydantic envelopes, bounded queues, three delivery modes, dead-letter handling).
  • A Worker abstraction wrapping the Agentic-Framework runtime with typed I/O and per-message spans.
  • The contract-net protocol (announce / bid / award / result) with four award strategies.
  • A coordinator (orchestrator) with a budget watchdog, deadline watchdog, stuck-loop detector, and arbitration loop.
  • A DAG executor with branching, loops, persistent pause/resume, and streaming-through-graph.
  • A shared blackboard (concurrent KV with CAS, subscriptions, conflict detection, TTL, per-run isolation).
  • Per-agent episodic/semantic memory and team-level shared memory (backed by the Vector-Database at #47).
  • OpenTelemetry tracing (span-per-agent/message/tool), Prometheus metrics, and a cost ledger.
  • Four reference patterns: Debate, CodeReviewCommittee, ResearchTeam, CustomerSupportTriage, plus the larger SoftwareEngineeringTeam.
  • A REST + WebSocket boundary and a conformance suite of recorded multi-agent tasks.

Out of scope (deferred — see Deferred Features Register): distributed workers across machines, the auction-based market protocol, the inspector UI, the hosted control plane, Byzantine consensus over agent votes, multi-agent reinforcement learning, federated learning across agent fleets, agent auto-discovery over the network.

Scale target. A single Python process per orchestrator with a worker pool scaling to 100 concurrent agents on a single 64-core machine.

Estimated time. 4–6 months for the full plan; 4–6 weeks for a Phase-0 drop running a 5-agent debate end to end with the orchestrator, bus, contract net, DAG executor, blackboard, tracing, four reference patterns, and the conformance harness.

2. Why Build This

Multi-agent coordination is the production surface of every non-trivial agent system. A single agent solves a single-step task; an agent team solves a workflow. The teams that ship multi-agent systems in production have all been bitten at least once: a stuck-loop debate that consumed $200 of API budget before the operator noticed; a research team that hallucinated a manager and submitted a report to nobody; a code-review committee where the reviewer and author diverged on which diff was under review and the synthesis arrived at a recommendation against a different file; a support triage that cancelled the wrong child task because the cancellation token was scoped to the parent and not the conversation; a swarm where the blackboard's eventual-consistency window let two agents both claim the same task and then both write conflicting answers.

This project is the smallest kernel that still teaches the full surface. It owns the message bus, the orchestrator, the worker abstraction, the shared blackboard, the DAG executor, the tracing layer, the arbitration policies, the patterns library, and a conformance suite of 100 multi-agent tasks with recorded ground-truth outcomes.

The deliverable is small enough to actually finish. We do not implement training, reinforcement learning over agent policies, a distributed transaction protocol, or every topology. We target the production patterns above plus the swarm-with-blackboard topology. That tight focus is the only reason the timeline is 4–6 months rather than 4–6 years.

The reference systems are AutoGen (cleanest multi-agent surface shipping), MetaGPT (longest-running pattern library), ChatDev (cleanest software-engineering-team pattern), CAMEL (cleanest peer-to-peer dialogue), CrewAI (developer-experience target), LangGraph (cleanest DAG executor for agents), OpenDevin/OpenHands (cleanest software-engineering team in production), Anthropic's "Building effective agents" essay (calibration for which patterns to ship), the FIPA specifications (message-envelope reference), Smith's 1980 contract-net paper (task-allocation reference), and Wooldridge's MAS textbook (academic baseline).

What Mastery Looks Like

  • You can read a 5-agent debate trace top to bottom and locate the exact message where two agents diverged — without re-running it (Phase 8, Tracing).
  • You can state, before a run starts, the maximum dollars and seconds it can consume, and prove the watchdog enforces both (Phase 4, Coordinator).
  • You can explain why a blackboard write and a bus message are never interchangeable, and point to the type-level barrier that forbids the confusion (Phase 6, Blackboard).
  • You can design a new pattern as a Pattern dataclass + Graph and know it will fail at construction — not at first dispatch — if a role is missing (Phase 9, Patterns).
  • You can describe what a cancelled parent does to its children, and why the kernel never calls asyncio.Task.cancel() (Phase 4, Coordinator; Phase 1, Worker).
  • You can run the conformance suite and read a Deferred bucket as a first-class outcome, not a failure (Conformance, Phase 0).
  • You can compute the bus throughput ceiling and the per-task coordinator overhead from the §4 constraints before writing a line (Back-of-Envelope Capacity Model).

Application Layer. The user-facing surface: instantiate a Pattern, call coordinator.run(pattern, inputs), consume an AsyncIterator[Event]. No coordination logic leaks here.

Coordinator (Phase 4). The single orchestrator. Compiles a pattern into a DAG, runs the dispatch loop, owns the budget/deadline/stuck-loop watchdogs, and is the only place routing decisions are made.

Contract Net (Phase 3). Task allocation by announce/bid/award/result with timeouts. The default allocator; FIPA-shaped envelopes.

DAG Executor (Phase 5). Walks the compiled graph in topological order with branching, bounded loops, persistent state for pause/resume, and streaming through edges.

Message Bus (Phase 2). The only inter-agent channel. Typed Pydantic envelopes, bounded queues with backpressure, dead-letter on retry exhaustion, three delivery modes.

Worker (Phase 1). A thin wrapper around the Agentic-Framework runtime adding typed I/O and a per-message span. The kernel never reaches into the agent's tool registry or model provider.

Blackboard (Phase 6). Shared state, not communication. Concurrent KV with CAS, subscriptions, conflict detection, TTL, per-run isolation.

Per-Agent Memory (Phase 7). Episodic (verbatim log), semantic (distilled facts), shared (team knowledge base on the Vector-Database).

Tracing + Observability (Phase 8). OpenTelemetry spans mirroring the dialogue, Prometheus metrics, and a per-call cost ledger.

Three load-bearing properties: (1) the data path is one-way — tasks flow application→coordinator→workers, results flow back through the bus; messages between agents are always routed through the bus, never directly. (2) The worker abstraction is a thin wrapper; the kernel touches only the agent's message-handling surface. (3) Every cross-cut (tracing, cost, cancellation, budget) is owned by the coordinator and exposed by interface-bound calls elsewhere; no layer reaches across another.

These three properties are not decoration — each closes a known failure class. Property (1) is why the trace is complete: with all traffic through the bus, no agent dialogue can happen off-record (it forecloses the "hallucinated manager who reports to nobody" failure of §2). Property (2) is why the kernel can evolve independently of the model provider: nothing above the Worker line knows whether an agent calls one model or ten (it forecloses provider-coupling debt, the most common refactoring cost in pattern libraries). Property (3) is why budget, cost, and cancellation are enforceable at all: a cross-cut owned in one place can be guaranteed; a cross-cut scattered across layers can only be hoped for (it forecloses the "$200 stuck loop" failure of §2). Read top to bottom, the diagram is also the dependency order — each layer depends only on the layers below it, and the coordinator is the single layer that sees all of them.

6. Design Principles

Twelve principles every protocol, pattern, and API surface has been negotiated against. Each names the rule, the tradeoff, and how violating it breaks the system.

  • P1 — The single-agent loop is sacred. Rule: the kernel talks only to a Worker interface; it never reaches into an agent's tool registry, model provider, or memory store. Tradeoff: we cannot optimize across the agent boundary. Violation: the coordinator couples to a model provider and every provider change becomes a coordinator change.
  • P2 — One coordinator, many workers. Rule: workers never talk to each other directly; all inter-agent traffic goes through the bus and is observable from the coordinator. Tradeoff: an extra hop per message. Violation: routing decisions scatter, traces lose edges, and debugging requires reconstructing an invisible mesh.
  • P3 — Typed messages or no messages. Rule: every bus message is a Pydantic model with a stable schema; untyped JSON is rejected at the bus boundary. Tradeoff: schema-change friction. Violation: malformed payloads surface as runtime errors three hops downstream instead of at the sender.
  • P4 — The blackboard is for shared state, not communication. Rule: agents that need to talk send messages; agents that need to share an artifact write to the blackboard; the order in a handler is strict — receive, decide, emit, write. Tradeoff: two mechanisms to learn. Violation: the most common multi-agent bug — races debuggable only with the trace UI.
  • P5 — Cancellation is structured. Rule: cancellation is cooperative and follows AnyIO structured concurrency; a cancelled parent cancels its children, a cancelled child does not cancel its parent; never asyncio.Task.cancel(). Tradeoff: workers must await regularly. Violation: orphaned children leak FDs and half-written blackboard entries on cancellation.
  • P6 — Budgets are first-class. Rule: every run carries (max_cost_usd, max_wall_clock_s, max_steps, max_tokens); the watchdog checks before every dispatch and on a 1-Hz heartbeat; exhaustion is a clean shutdown. Tradeoff: a wakeup per second. Violation: a single stuck loop bills $200 before anyone notices.
  • P7 — Determinism where possible. Rule: given (pattern, inputs, seed, model_replays) the coordinator produces the same trace; LLM calls replay from a cassette in tests. Tradeoff: cassette maintenance. Violation: flaky conformance and irreproducible incidents.
  • P8 — No silent role hallucination. Rule: a worker that emits a message whose sender_role/sender_worker does not match its registration is rejected at the bus. Tradeoff: strict envelope construction. Violation: the model hallucinates a colleague and addresses messages into the void.
  • P9 — Span-per-agent, span-per-message, span-per-tool. Rule: the trace tree mirrors the agent dialogue. Tradeoff: span volume. Violation: the operator's primary debugging surface develops blind spots exactly where dialogues fork.
  • P10 — Patterns are typed. Rule: a Pattern is a dataclass; instantiating one missing a required role raises at construction, not at first dispatch. Tradeoff: less dynamism. Violation: the second-most-common bug — a referenced-but-unregistered worker fails mid-run.
  • P11 — The result is the only durable signal. Rule: heartbeats and acks indicate liveness, not completion; only a Result of-record completes a task. Tradeoff: occasional duplicate work after partition. Violation: a task that acked but never delivered is silently lost.
  • P12 — Defer, don't delete. Rule: every surface not shipping at Phase 0 lives behind a typed PhaseDeferred anchored at the Deferred Features Register, with an un-defer trigger. Tradeoff: dormant code paths. Violation: scope creep or, worse, silent half-implementations that fail in production.

These are enforced at the type level where possible, by code review where not.

8. Domain Model / Protocol / Data Model

The kernel's domain is a conversation among roles, mediated by the bus and the blackboard, allocated by the contract net. The unit of work is a task; the unit of communication is an envelope; the unit of shared state is a blackboard key.

8.1 The Envelope

Every message on the bus is wrapped in an Envelope (frozen). It carries identity (msg_id), the run/thread it belongs to (run_id, thread_id), reply linkage (parent_msg_id), provenance (sender_role, sender_worker), addressing (recipient_role, recipient_worker — None means broadcast/any), timing (sent_at, deadline), and a discriminated payload (payload_kind + payload validated against the kind's schema). Full signatures in §11.

8.2 Contract-Net Worked Example

A coordinator needs a 200-line patch reviewed. It announces to the reviewer role:

TaskAnnounce(task_id=T1, description="review patch P", eligible_roles=["reviewer"],
             deadline_for_bids=t0+2s, award_strategy="highest-confidence")

Three reviewers bid: Bid(T1, r1, cost=0.04, wall=8s, confidence=0.7), Bid(T1, r2, cost=0.05, wall=6s, confidence=0.9), Bid(T1, r3, …). At t0+2s the coordinator picks r2 (highest confidence) and awards Award(T1, awarded_to=r2, deadline=t0+62s, budget_usd=0.075). r2 returns Result(T1, r2, outcome="success", output={…}, cost_usd=0.048, wall=5.9s). The coordinator records the outcome, updates the ledger, and unblocks the downstream synthesiser node.

8.3 Contract-Net State Table

State Event Next state Action
ANNOUNCED bid received ANNOUNCED append bid
ANNOUNCED bid deadline elapsed, ≥1 bid AWARDED pick winner, send Award
ANNOUNCED bid deadline elapsed, 0 bids FAILED raise NoBidders; re-announce per retry policy
AWARDED Result(success) DONE record outcome, unblock downstream
AWARDED Result(failure/timeout/budget) FAILED re-announce (≤3); then escalate
AWARDED work deadline elapsed FAILED Cancel winner, re-announce
FAILED retry count > 3 ESCALATED promote to manager-choice, longer deadline
any run budget exhausted CANCELLED Cancel, clean shutdown

8.4 Malformed Input

  • Untyped/invalid payload: rejected at the bus send path (I1); mac_bus_invalid_total++; the send raises before the message reaches the wire.
  • Role hallucination: a reply whose sender fields do not match registration is dead-lettered (I2); the worker is flagged for arbitration.
  • Unknown payload_kind: the discriminator misses PAYLOAD_KINDS; the envelope is rejected as malformed.
  • Stale CAS version: a Write with a mismatched expected_version is rejected with a conflict; the loser retries (I6).
  • Bid after deadline: silently dropped (the worker is treated as having chosen not to bid); the timeout disambiguates crash from abstention.

8.5 Failure Path

When a winner crashes mid-task: heartbeats stop; after the work deadline the coordinator marks the task FAILED, emits Cancel (idempotent), and re-announces. If the crashed worker later returns a Result with the original msg_id, the duplicate is detected (I8) and dead-lettered. No double-completion occurs because only a Result of-record completes a task (P11/I8).

8.7 Dialogue Threading & Message Flow

A thread (thread_id) is a sub-conversation; the bus guarantees per-thread FIFO order (I7) and nothing across threads (ADR-21). A debate round is one thread; a code-review of one patch is one thread. Threads let two patterns run concurrently on the same coordinator without their messages interleaving incorrectly.

A single contract-net cycle threads through the system as:

coord ──TaskAnnounce(role)──▶ bus ──broadcast──▶ {workers in role}
{workers} ──Bid──▶ bus ──▶ coord   (collected until deadline_for_bids)
coord ──Award(winner)──▶ bus ──send_to──▶ winner
winner ──Result──▶ bus ──▶ coord ──▶ unblock downstream DAG node

Each arrow is one envelope and one span; parent_msg_id links the Bid to the TaskAnnounce, the Award to the winning Bid, and the Result to the Award, so the trace tree reconstructs the full cycle without re-running it (P9, MM8). The coordinator is on the receive side of every arrow that returns to it, which is what makes all inter-agent traffic observable (P2).

13. Phase 1 — Worker Abstraction

13.1 Objectives

Define the Worker boundary: a thin wrapper around an Agentic-Framework Agent that adds typed Pydantic I/O, a per-message OpenTelemetry span, role registration, permission scoping, and an idempotent handle(envelope) -> AsyncIterator[Envelope]. Scope: the seam itself, not agent internals (P1 — the kernel never reaches past this line).

13.2 Detailed Implementation Steps

Applies P1 (sacred loop), P8 (no role hallucination → I2), P9 (span-per-message), and the DSPy typed-signature approach (§5, ADR-05 controls the worker boundary).

class Worker(ABC):
    role: RoleId
    worker_id: WorkerId
    @abstractmethod
    async def handle(self, env: Envelope) -> AsyncIterator[Envelope]: ...   # receive; emit 0+ replies
    async def run(self, env: Envelope) -> AsyncIterator[Envelope]: ...       # wrapper: span + I2 enforcement

class LlmWorker(Worker): ...    # wraps an Agentic-Framework Agent (system prompt, tools, memory)
class ToolWorker(Worker): ...   # non-LLM (db query, http fetch, sandboxed exec); same interface

The run wrapper opens a span with attributes agent.role, agent.worker_id, message.payload_kind, message.run_id, and rejects any reply whose sender_role/sender_worker mismatch the registration (raises RoleHallucination, I2).

  1. Define the Worker ABC with handle (async generator) and run (span-adding wrapper).
  2. Implement LlmWorker over the Agentic-Framework agent; expose only handle.
  3. Implement ToolWorker for non-LLM workers with the same interface.
  4. Maintain role registration as dict[RoleId, list[Worker]] on the coordinator.
  5. In run, enforce I2 per emitted reply and close the span when the iterator is exhausted.
  6. Enforce per-tool permission scope (read-only / read-write / network / shell) at the tool-call boundary; an out-of-scope call quarantines the worker.
  7. Keep handle cooperative; CPU-bound work opts into anyio.to_thread.run_sync so cancellation propagates (P5).

Worker handler contract (worked). handle is an async generator, not a coroutine: it receives one Envelope and yields zero or more reply Envelopes. A reviewer worker receiving a TaskAnnounce yields one Bid; later, on its Award, it yields one Result; on a Speak it may yield nothing (it only listens). The strict in-handler order is receive → decide → emit → write (P4): the worker must finish emitting bus messages before touching the blackboard, so its observable communication and its state mutation never interleave. Because envelopes are frozen, the worker constructs new reply envelopes (copying run_id/thread_id, setting its own sender_*, a fresh msg_id, and parent_msg_id = the received msg_id); run then verifies the sender_* fields against the worker's registration (I2) before letting each reply onto the bus.

14. Phase 2 — Typed Message Bus

14.1 Objectives

Build the only inter-agent channel: typed Pydantic envelopes, bounded queues with backpressure, three delivery modes, dead-letter handling, schema validation on send, and per-thread FIFO ordering. Constraint: no hidden buffer ever absorbs a burst (I1, ADR-21).

14.2 Detailed Implementation Steps

Applies P3 (typed messages → I1), I7 (per-thread order), ADR-21 (per-thread FIFO, like Kafka per-partition), and the Hohpe & Woolf dead-letter-channel / idempotent-receiver patterns (§5). Cross-process transport rides on PubSub-Messaging (#58, ADR-04).

class Bus(ABC):
    @abstractmethod
    async def broadcast(self, role: RoleId, payload: BaseModel) -> None: ...
    @abstractmethod
    async def send_to(self, worker: WorkerId, payload: BaseModel) -> None: ...
    @abstractmethod
    async def receive(self, topic: str, key: Any | None = None) -> AsyncIterator[Envelope]: ...
    @abstractmethod
    async def dead_letter(self, env: Envelope, reason: str) -> None: ...

DeliveryMode = Literal["at-most-once", "at-least-once", "exactly-once-via-dedupe"]
  1. In-process bus: dict[RoleId, list[anyio.MemoryObjectSendStream]]; sends non-blocking up to queue depth (default 100), then backpressure (the sender awaits).
  2. Cross-process bus on #58: each role is a topic, each worker a consumer in the topic's group; identical envelope schema, transport-only difference (ADR-04).
  3. Delivery modes: at-most-once (fire-and-forget), at-least-once (ack after handling, default), exactly-once-via-dedupe (bounded LRU of recent msg_id, ADR-22).
  4. Dead-letter: a message exceeding three delivery attempts goes to a dead-letter topic with the original envelope and the failure reason; arbitration is consulted per new dead-letter.
  5. Validate every send against the payload_kind schema; invalid sends raise before the wire (I1).
  6. Preserve per-thread_id FIFO; no cross-thread order (ADR-21, I7).
  7. Apply backpressure at the sender; no hidden buffer absorbs bursts (P3).

Delivery-mode decision table. The default is at-least-once; operators deviate per this table:

Mode Guarantee Cost Use when
at-most-once may lose, never duplicate cheapest; no ack round-trip heartbeats, metrics, best-effort progress events
at-least-once never lose, may duplicate one ack per message the default; results, awards, anything load-bearing
exactly-once-via-dedupe never lose, never duplicate (within the LRU window) ack + bounded dedup store financial-shaped or idempotency-sensitive payloads

The "exactly-once" guarantee is bounded by the LRU window (ADR-22): a duplicate arriving after its msg_id ages out of the window is not caught; for audited messaging where that is insufficient, the deferred durable-dedup surface applies (ADR-22 "audited financial messaging favors durable dedup", Deferred Features Register).

14.6 Pitfalls

  • Letting the bus drop messages silently; every drop is mac_bus_dropped_total + a log line.
  • Using asyncio.Queue directly; mixing with AnyIO streams leaks FDs and reorders.
  • Trusting cross-process delivery to be exactly-once by default; it is at-least-once, dedup is opt-in.

14.7 Performance Concerns

Backpressure walkthrough. When a role's queue (default depth 100) fills, the next send does not buffer internally — it awaits on the AnyIO memory stream until a slot frees (P3). The sender (often the coordinator dispatching tasks) feels the pressure directly and slows its dispatch rate: a slow consumer throttles its producer instead of an unbounded queue growing until OOM. This is why the kernel forbids asyncio.Queue with an unbounded default. Per-envelope cost is dominated by Pydantic validation (~30 µs); internal, pre-validated envelopes use model_construct to skip re-validation on the hot path, which is what keeps the bus at the ≥ 50k env/s target (M7, Capacity #1) — GIL contention, not CPU, is the eventual ceiling.

14.8 Edge Cases

  • A burst arrives faster than the consumer drains: backpressure propagates to the sender (never an unbounded buffer); a coordinator that ignores the resulting slowdown will itself queue up dispatch requests.
  • A cross-process consumer group loses a member mid-broadcast: the remaining consumers absorb its share; no message is silently dropped (delivery-mode dependent).
  • A payload validates against its declared payload_kind but the discriminator itself is unknown: rejected as malformed (I1), never routed to a best-guess handler.
  • Clock skew between processes affects sent_at/deadline comparisons only at the receiver; the bus itself does not depend on synchronized clocks for ordering (FIFO is queue-position based, not timestamp based).

14.9 Failure Analysis

A dead-letter flood (many messages exceeding 3 attempts) is detected via mac_dead_letter_total's rate of change and triggers an operator alert (F3, §26); the dead-letter topic has its own backpressure so a flood degrades gracefully rather than cascading into the primary bus. A silently dropped message (a bug bypassing mac_bus_dropped_total) is the one failure mode Phase 2 cannot self-detect — mitigated by the property test asserting FIFO-preserving delivery for every interleaving (§29). Cross-process transport failure (the #58 broker unavailable) fails sends fast rather than buffering indefinitely, surfacing as a coordinator-visible error rather than a silent stall.

14.10 Operational Notes

Exit gate: bus.delivery is Pass; backpressure is observable; dead-letter handling fires at the third retry — this is what unblocks Phase 3 (contract-net announce/bid/award rides this bus).

15. Phase 3 — Contract-Net Protocol

15.1 Objectives

Implement Smith's announce/bid/award/result allocation with four award strategies, bid/work deadlines, and re-announcement on failure. Constraint: the allocator never blocks the bus (P2) and never double-completes a task (I8).

15.2 Detailed Implementation Steps

Applies the Smith 1980 protocol and FIPA-Contract-Net (§5, ADR-14), the state table in §8.3, and I8 (result-of-record). Award strategies map to the AutoGen orchestrator-workers calibration (§5).

async def run_contract_net(coordinator, task: TaskAnnounce, role: RoleId,
                           bid_window: timedelta = timedelta(seconds=2),
                           work_deadline: timedelta = timedelta(seconds=60)) -> Result: ...
def pick_winner(bids: list[Bid], strategy: str) -> Bid: ...   # lowest-cost | highest-confidence | first-acceptable | manager-choice
  1. Announce: broadcast a TaskAnnounce to the role (no specific recipient).
  2. Collect bids until deadline_for_bids using anyio.move_on_after; a worker that does not bid is silent.
  3. At the bid deadline, if zero bids → raise NoBidders and re-announce per retry policy; otherwise pick_winner per strategy.
  4. Emit an Award to the winner only (silence is the rejection signal for losers); set budget_usd with headroom (e.g. 1.5× the bid).
  5. Await the Result under anyio.fail_after(work_deadline); a missing result cancels and re-announces.
  6. Award strategies: lowest-cost (default), highest-confidence, first-acceptable (first over threshold), manager-choice (defer to the LLM-judge policy ranking, ADR-11).
  7. Re-announcement: a task failing three times escalates to the arbitration policy (§16.2), which promotes to manager-choice with a longer deadline (state table §8.3).

15.6 Pitfalls

  • Awarding before the bid deadline; the race lets a fast bidder win cheaply over better late bids.
  • Letting a losing bidder retain pre-allocated resources; the loser must release on award failure.
  • Treating silence as rejection without a timeout; the timeout disambiguates crash from abstention.

15.7 Performance Concerns

The bid window (default 2 s) is a direct multiplier on end-to-end task latency for every contract-net cycle in every pattern (§21) — M1's 60 s debate budget assumes ≤ 30 such cycles, so a bid window increase compounds across rounds. pick_winner is O(bidders) and never the bottleneck versus the LLM round-trip; the real cost driver is the number of workers eligible to bid (eligible_roles fan-out), which is bounded by the pattern's role cardinality (typically ≤ 5).

15.8 Edge Cases

  • A bid arrives at exactly deadline_for_bids: the boundary is inclusive-open (anyio.move_on_after cancels at the instant, so a bid racing the clock may or may not count — the protocol treats this as legitimate abstention either way, never an error).
  • Two workers submit numerically identical bids under lowest-cost: pick_winner breaks ties deterministically by bidder id lexical order, so replay is reproducible (P7).
  • A worker bids, is awarded, then crashes before its Result — handled identically to §8.5's failure path (work-deadline elapses, re-announce, duplicate result dead-lettered per I8 if it later arrives).
  • award_strategy="manager-choice" with no available judge worker: the coordinator raises at construction (pattern validation, I10), never at first dispatch.

15.9 Failure Analysis

Zero bidders (NoBidders, F10 in §26) re-announces per retry policy and, after 3 failures, escalates to manager-choice with a longer deadline — detected via the NoBidders exception surfacing in the trace, contained to the one task (siblings continue). A winner that never returns a Result is caught by the work-deadline watchdog (anyio.fail_after), which cancels and re-announces — the blast radius is one re-auction, not the run, because I8 guarantees the eventual late Result cannot double-complete the task.

16. Phase 4 — Coordinator (Orchestrator)

16.1 Objectives

Build the single orchestrator: run lifecycle, budget watchdog, deadline watchdog, stuck-loop detector + arbitration loop, structured cancellation, state persistence, and an output event stream. Constraint: every cross-cut (budget, cancellation, tracing) is owned here and nowhere else (§3 property 3).

16.2 Detailed Implementation Steps

Applies P2 (one coordinator), P5 (structured cancellation → I4), P6 (budgets → I3), P11/I8 (result-of-record), I14 (stuck-loop), ADR-12/ADR-13. The supervisor-worker topology follows Wooldridge (§5).

class Coordinator(ABC):
    @abstractmethod
    async def run(self, pattern: Pattern, inputs: dict[str, Any],
                  budget: Budget, deadline: timedelta) -> AsyncIterator[Event]: ...
    @abstractmethod
    async def cancel(self, run_id: RunId, reason: str) -> None: ...
    @abstractmethod
    async def resume(self, run_id: RunId, decision: Any) -> None: ...

class Budget(BaseModel):
    max_cost_usd: float; max_wall_seconds: float; max_steps: int; max_tokens: int

Event = (TaskAnnounced | BidReceived | Awarded | ResultReceived
         | BudgetWarning | StuckLoopDetected | Done)
  1. Lifecycle: a run is a RunId moving through init → compile-pattern → dispatch-loop → finish. The loop pulls tasks, runs contract-net, awaits results, pushes downstream tasks.
  2. Budget watchdog: a 1-Hz heartbeat checks the ledger against the budget plus a pre-dispatch check; exhaustion emits Cancel to every active task, awaits a 5-second cleanup window, and exits with BudgetExhausted (I3, P6).
  3. Deadline watchdog: per-task anyio.fail_after; an over-deadline task is cancelled and re-announced (§15).
  4. Stuck-loop detector: a sliding window of 10 messages; a repeated (sender, recipient, payload-hash) triggers the arbitration policy (retry / escalate / abort) (I14).
  5. Cancellation: AnyIO TaskGroup only; cancel the group and let children unwind (I4, ADR-12); never asyncio.Task.cancel().
  6. State persistence: every transition is recorded in the DAG persistence layer (Phase 5) so a crashed coordinator resumes (I9).
  7. Output streaming: emit AsyncIterator[Event]; the application renders progressively.

Arbitration policy detail. The arbitration policy is the kernel's response to ambiguity, consulted in four situations: a detected stuck loop (I14), a dead-letter event, a conflicting blackboard write that exhausted CAS retries (F5), and a contract-net task that failed three times (§15.2). The default policy is rule-based with an LLM-judge fallback (ADR-11):

Situation Rule-based first pass LLM-judge fallback Terminal action
Stuck loop if window repeats > threshold → abort judge decides retry / escalate / abort abort raises StuckLoop, run ends cleanly
Dead-letter if rate < N/min → log and continue judge inspects the failing message class alert operator on flood
CAS exhaustion retry up to N (default 3) judge picks a merge or a winner escalate the write to the operator
Repeated task failure promote to manager-choice, longer deadline judge ranks remaining bidders mark task FAILED, surface to application

The policy is itself a Worker-shaped surface (a manager LLM is a worker), so its judgments are recorded in the trace and the ledger and are subject to the same budget cap as the workers it arbitrates — the manager is never a free pass (P6). A human policy variant routes the same four situations to a HITL checkpoint instead of a manager LLM, for regulated deployments (ADR-11 "regulated decisions favor human-only").

16.8 Edge Cases

  • Budget exhaustion mid-in-flight-LLM-call: the call is not preemptible, so the worst-case overage is one call's cost/duration past the cap (Capacity #6) — the watchdog cancels everything else immediately and lets that one call's result land (dead-lettered if it arrives after Cancel).
  • A stuck-loop false positive (two agents legitimately repeat a phrase, e.g. agreeing "yes"): the sliding-window hash includes the full payload, not just intent, so an exact repeat is required — the window size (default 10, tunable to 5–100, Appendix C) trades early detection against false positives.
  • resume() called on a run_id with no persisted checkpoint: rejected with a clear error, never silently starts a fresh run under the old id.
  • Concurrent cancel() calls on the same run: idempotent — the second call is a no-op once the TaskGroup has already begun unwinding.

16.9 Failure Analysis

A stuck loop (F1) pauses and consults arbitration rather than aborting immediately, so a false positive costs one arbitration round-trip, not the run. A coordinator process crash mid-run (F7) is recovered via the DAG persistence layer (RTO ≤ 30 s, RPO ≤ 1 transition, I9) — see §17 for the resume mechanics this phase depends on.

17. Phase 5 — DAG Executor

17.1 Objectives

Compile a Pattern into a Graph and execute it: topological dispatch, branching, bounded loops, Postgres-persisted pause/resume, and streaming through edges. Constraint: RPO ≤ 1 transition, RTO ≤ 30 s (§4, I9).

17.2 Detailed Implementation Steps

Applies I9 (persist-before-ack), I11 (bounded loops), the LangGraph persistence/HITL model and the Reflexion critic-loop prior (§5). Postgres persistence per ADR-07.

@dataclass(frozen=True)
class Node:
    name: str; role: RoleId; input_schema: type; output_schema: type
    upstream: tuple[str, ...] = ()
    branch_on: Callable[[Any], str] | None = None
    loop_back_to: str | None = None
    max_iterations: int = 1
    terminate_when: Callable[[Any], bool] | None = None
    is_human_checkpoint: bool = False

@dataclass(frozen=True)
class Graph:
    nodes: tuple[Node, ...]; entry: str; exits: tuple[str, ...]
    def topological_order(self) -> list[str]: ...      # Kahn; raises on non-loop cycles
    def downstream(self, node: str, branch: str | None) -> list[str]: ...
  1. Compile a Pattern into a Graph of nodes (role, I/O schema, upstream deps); the graph is a DAG plus optional loop_back_to back-edges.
  2. Topological dispatch: a node fires when all upstream results exist; independent nodes fire in parallel (bounded by max parallelism, default 16).
  3. Branching: a node emits a BranchDecision selecting one of N downstream paths; unselected paths are pruned.
  4. Loops: a back-edge carries max_iterations and terminate_when; the executor exits at termination or the cap (I11).
  5. Persistence: record every dispatch and result in Postgres before acknowledgment (I9); resume from last state on crash.
  6. Pause/resume: a is_human_checkpoint node pauses, persists, and waits for an external Resume(node_id, decision); the application surfaces the pause.
  7. Streaming: edges carry typed messages; downstream nodes receive inputs as they arrive (a research node streams partials to a writer node).

Pause/resume vs loops. A is_human_checkpoint pause and a loop back-edge are distinct mechanisms sharing the persistence layer. A pause persists state and waits indefinitely for an external Resume(node_id, decision); the run consumes no budget while paused (wall-clock budget is checked against active dispatch time, not wall-time-while-paused, so a HITL run can sit overnight without tripping the watchdog). A loop, by contrast, re-dispatches immediately under the running budget until terminate_when or max_iterations. Confusing the two is a design error caught at construction because a checkpoint node has no loop_back_to (I10-shaped validation).

17.7 Performance Concerns

Readiness checks are O(in-degree) per node, evaluated only when an upstream result lands — never by polling — which is what keeps a 1000-node DAG at p99 ≤ 100 ms (M8, Capacity #5: ≤ 100 µs/node budget with mean in-degree < 4 across the reference patterns). Max parallelism (default 16, tunable 1–256, Appendix C) bounds concurrent dispatch to the worker-pool size; raising it past the pool size buys nothing and only adds scheduling overhead.

17.8 Edge Cases

Resume worked sequence. A coordinator persists a row per transition: (run_id, node_name, iteration, status, result_ref). Consider a ResearchTeam run that crashes after the writer's first draft but before the critic fires. On restart the resume probe reads the persisted rows: planner DONE, searcher.0..2 DONE, writer DONE (iteration 0), critic PENDING. The executor rebuilds in-memory graph state from these rows, sees the critic's upstream is satisfied, and dispatches the critic — no work before the writer repeats (RPO ≤ 1 transition, I9). If the crash lands mid-writer (writer PENDING, no result row), the writer is re-dispatched from scratch; its prior partial output, never persisted, cannot corrupt the run. Other edge cases: a branch node selecting an unregistered path fails at construction, not dispatch (I10); a loop whose terminate_when never returns true is force-exited at max_iterations (I11); concurrent independent-node dispatch racing the same Postgres connection pool is serialized by row-level locking, never a lost transition.

17.9 Failure Analysis

Persistence lag (Postgres write contention under high concurrency) is detected via mac_persist_lag_seconds and is the first bottleneck the kernel hits under load (§32) — mitigation order is raising the persist cadence knob, then separating the ledger's connection pool, then partitioning by run_id. A crash mid-dispatch (F7, §26) recovers via the resume probe above; a crash during the Postgres write itself (before commit) leaves the prior state intact (the transition simply never happened, RPO ≤ 1). An infinite loop that evades terminate_when due to a buggy predicate is still bounded by max_iterations (I11) — the hard cap is the backstop for a soft-logic bug.

18. Phase 6 — Shared Blackboard

18.1 Objectives

A concurrent-safe versioned KV store with CAS, prefix subscriptions, conflict detection, optional TTL, per-run isolation, and opt-in Postgres backing. Constraint: never a communication channel (P4).

18.2 Detailed Implementation Steps

Applies P4 (state, not communication), I6 (CAS-versioned), I12 (isolation), and the optimistic-concurrency model from Kleppmann (§5, ADR-15 sets the isolation default).

class Blackboard(ABC):
    @abstractmethod
    async def write(self, key: str, value: Any, expected_version: int | None) -> int: ...  # returns new version; raises Conflict
    @abstractmethod
    async def read(self, key: str) -> tuple[Any, int]: ...                                   # (value, version)
    @abstractmethod
    async def subscribe(self, key_prefix: str) -> AsyncIterator[tuple[str, Any, int]]: ...
    @abstractmethod
    async def expire(self, key: str, ttl: timedelta) -> None: ...
  1. Store: dotted-string keys (run.<run_id>.draft.v1), JSON-serialisable values; every write increments a per-key version.
  2. CAS: a Write with expected_version is rejected on mismatch (I6); used for optimistic concurrency between agents.
  3. Subscriptions: a worker subscribes to a key prefix and is notified on matching writes; used for writer→reviewer handoffs.
  4. Conflict detection: racing writes produce one winner (first commit) and one loser (Conflict); the loser may retry with the new version.
  5. TTL: optional per-key TTL with eviction on elapse; used for garbage-collecting stale drafts.
  6. Per-run isolation by default; a pattern may opt into a shared blackboard surviving across runs (I12).
  7. Persistence: in-memory default; opt-in Postgres backing for cross-restart durability (schema in migrations, ADR-07).

18.8 Edge Cases

CAS worked sequence. Two reviewers race to append to a shared review summary at key K:

Step Actor Operation Store version Outcome
1 r1 read K v3 gets (value, 3)
2 r2 read K v3 gets (value, 3)
3 r1 write K, expected_version=3 v3 → v4 success, now v4
4 r2 write K, expected_version=3 v4 Conflict (expected 3, found 4)
5 r2 read K v4 gets r1's value, version 4
6 r2 write K, expected_version=4 v4 → v5 success, now v5

Both updates land, in a deterministic order, with no lost update (I6). The retry at step 5–6 is the loser re-reading and merging against the winner's value — the store only guarantees a stale write cannot clobber a fresh one; the application decides the merge semantics. Other edge cases: a TTL key read exactly at expiry returns "not found" (eviction is checked on read, not just on a background sweep); a subscriber that joins after a write sees nothing retroactively (no implicit replay, §18.6); a cross-run read without opt-in is rejected at the ACL check regardless of whether the key exists (I12) — existence is not leaked to an unauthorized reader.

18.9 Failure Analysis

If r2 exhausts its CAS retry count (default 3) the write escalates to arbitration (F5, §26), which picks a merge or a winner rather than the run stalling indefinitely. A conflict storm (many writers on one hot key) is detected via mac_blackboard_conflict_total's rate and is contained by the bounded retry cap; blast radius is elevated latency on that key, not a stuck run. Postgres unavailability (when opted into durable backing) degrades the blackboard to in-memory read-only (F11) rather than blocking writes indefinitely.

20. Phase 8 — Tracing, Metrics, Cost Ledger

20.1 Objectives

Emit OpenTelemetry spans (run/task/message/tool), Prometheus metrics, and a per-call cost ledger; support trace export to common backends and trace replay/time-travel. Constraint: the trace tree mirrors the dialogue exactly (P9, MM8).

20.6 Pitfalls

  • Letting the exporter block the dispatch loop; it is async and bounded — overflow samples, never blocks.

20.7 Performance Concerns

Span emission uses an async, bounded buffer; overflow samples rather than blocks (§20.6), so tracing never appears on the coordinator's critical path. Ledger writes are batched per dispatch, not per token, so the cost ledger never gates the dispatch loop — the per-call tuple is buffered and flushed asynchronously (§31 hot-path budget).

20.8 Edge Cases

Span tree worked example. A single round of a 2-speaker debate produces this tree (one span per arrow in §8.7):

run.debate[run_id]
├─ task.round.0.speaker.0
│  └─ worker.speaker.0.handle  (Speak)   ──▶ tool.llm.call ($0.04)
├─ task.round.0.speaker.1
│  └─ worker.speaker.1.handle  (Speak)   ──▶ tool.llm.call ($0.05)
└─ task.round.0.judge
   └─ worker.judge.handle      (Vote)    ──▶ tool.llm.call ($0.03)

The tree mirrors the dialogue exactly: the operator reads it top-down to follow who spoke, in what order, and what each cost. A missing tool.llm.call child means an LLM call escaped the cost ledger (I13), which the conformance shape check catches. Branching from the judge node ("what if the judge had voted differently?") replays the recorded trace forward from that span with a substituted verdict — the time-travel debugging surface (§20.2 step 5). Other edge cases: an exporter buffer overflow under a fan-out pattern samples spans rather than dropping the run's trace entirely (the sample rate itself is recorded so completeness is auditable); a span whose parent span never closes (a crashed worker) is force-closed with a status=error attribute at run teardown.

20.9 Failure Analysis

Trace exporter overflow (F9, §26) is detected via the exporter's buffer drop count; recovery is sampling spans, never blocking dispatch. A cost-ledger write failure (Postgres unavailable) does not lose the underlying LLM call's accounting silently — the in-flight tuple is retried from the async buffer, and a sustained outage surfaces as a persist-lag metric, not a silent gap. A missing span in the debate fixture's tree is treated as a conformance FAIL (trace.coverage), not a warning, because MM8 makes the trace the primary debugging surface — any blind spot there is a blind spot everywhere.

20.10 Operational Notes

This phase is the observability surface; self-instrumentation tracks exporter buffer depth and drop counts. Exit gate: trace.coverage is Pass; span tree matches recorded shape; ledger preserves the full cost tuple — this is what unblocks Phase 9 (every reference pattern is measured through this trace and ledger).

Mid-run, any pattern's failure modes reduce to the underlying phase's failure modes (F1–F12, §26) — patterns introduce no new failure class of their own, only new graph shapes that exercise the existing ones (loops stress I11, HITL stresses the pause/resume path of §17).

22. Phase 10 — REST + WebSocket Boundary

22.1 Objectives

Expose the kernel over HTTP/WebSocket: REST routes, a per-run event stream, API-key auth with per-pattern ACLs, rate limiting, run isolation, and idempotent run creation. Constraint: the REST response never carries the full transcript (large output is fetched lazily).

22.2 Detailed Implementation Steps

Applies the Newman boundary/contract discipline (§5), ADR-09/ADR-10. mTLS is deferred (Deferred Features Register). REST: GET /patterns, POST /runs, GET /runs/{id}/events, POST /runs/{id}/cancel, GET/PUT /blackboard/{run}/{key}. WebSocket: one endpoint per run streaming Event payloads. Auth: Authorization: Bearer <key> with per-key pattern-level ACLs. Bodies are Pydantic-validated; the OpenAPI spec is generated from handlers.

  1. REST routes with Pydantic-validated bodies; OpenAPI generated from handlers (docs/api/openapi.yaml).
  2. WebSocket: a per-run endpoint streaming Events with a 30-second ping; used by the UI for progressive render.
  3. Authentication: API keys (stored hashed); per-key pattern-level ACLs. mTLS at the WS boundary is deferred — PhaseDeferred("Deferred Features Register").
  4. Rate limiting: per-key token bucket, burst 10 runs, sustained 1 r/s, configurable per key.
  5. Run isolation: cross-run access rejected at the planner; users see only owned runs; admin keys see all (I12).
  6. Idempotency: run creation accepts an Idempotency-Key; duplicates return the same run id.

Run lifecycle over HTTP (worked). A client starts and watches a run: POST /runs with {pattern, inputs}, an Authorization: Bearer key, and an Idempotency-Key; the server validates the key's ACL against the requested pattern, checks the token bucket, dedups on the idempotency key, and returns {run_id}. The client opens the WebSocket for that run_id and receives Events (TaskAnnounced, Awarded, ResultReceived, …, Done) as the coordinator emits them, with a 30-second server ping keeping the socket alive. POST /runs/{id}/cancel flips the coordinator to the budget-exhaustion-style clean shutdown for that run. Large output is fetched lazily per blackboard key via GET /blackboard/{run}/{key}, so a 10 MB draft never inflates a status poll.

22.6 Pitfalls

  • Forgetting the WebSocket heartbeat; idle sockets get killed by intermediaries — ping every 30 s.
  • Returning the full transcript in the REST response; it can be large — clients opt into the WS.
  • Running FastAPI in the coordinator's event loop; they run in separate threads with a bounded handoff queue.

22.7 Performance Concerns

The FastAPI process and the coordinator's asyncio event loop are separated by a bounded handoff queue, so a slow HTTP client cannot stall dispatch (mirrors the bus's own backpressure discipline, §14.7). The 30-second WebSocket ping is a fixed, small keep-alive cost independent of run size; rate limiting (burst 10, sustained 1 r/s per key, Appendix C) bounds the request-handling surface independent of the coordinator's own per-task overhead (M9).

22.8 Edge Cases

  • A client opens the WebSocket before POST /runs completes (race): the endpoint returns 404 until the run is registered, never a silently empty stream.
  • A Idempotency-Key replay arrives after the original run has already finished: the same run_id is returned regardless of the original run's outcome — idempotency is about request dedup, not outcome caching.
  • A rate-limited request (token bucket exhausted): returns 429 with a Retry-After header, never a silently dropped connection.
  • An admin key requesting a run owned by another user: permitted by design (I12 exempts admin scope); a non-admin key making the same request is rejected regardless of whether the run exists (no existence leak).

22.9 Failure Analysis

An ACL-denied cross-run access attempt (F6, §26) increments mac_acl_denied_total and is rejected at the planner — no partial data is returned before the rejection. A WebSocket connection drop (network blip) is the client's responsibility to reconnect; the server does not buffer missed events indefinitely — a reconnecting client should GET /runs/{id}/events for the events it missed rather than assume WS delivery is durable. A rate-limiter false positive (a legitimate burst) is mitigated by the per-key configurable burst allowance, distinguishing a misbehaving key from a bursty-but-legitimate one only by operator-set policy, not automatically.

23. Phase 11 — Distributed Workers (Deferred surface, contract frozen)

23.1 Objectives

Specify (not implement at Phase 0) a worker pool across machines: location-transparent registration, failure detection, partition handling, and sticky sessions. The full surface is deferred — see the Deferred Features Register. Constraint: the frozen contract must make scale-out additive later, never a rewrite (§32).

23.2 Detailed Implementation Steps

Applies P11/I8 (result-of-record under partition), Tanenbaum & Steen §8 (fault tolerance, §5). Transport on #58 (ADR-04). Reuses the §11 envelope and the §14 Bus ABC unchanged; registration is a Heartbeat-carrying join over the bus. No new public types at Phase 0; the distributed executor binds to the same Coordinator ABC.

  1. Worker pool across machines: a worker registers over the bus (same FIPA envelope); the coordinator is location-transparent.
  2. Failure detection: 5-second heartbeats; three missed heartbeats marks a worker dead and re-announces its in-flight task.
  3. Network partition: symmetric — each side assumes the other died; the coordinator re-announces lost tasks; on rejoin, the duplicate result is detected via msg_id and dead-lettered (I8).
  4. Sticky sessions: a pattern can pin a thread to one worker (stateful workers); sticky routing is coordinator-side; the bus is unaware.
  5. The full distributed pool is deferred — PhaseDeferred("Deferred Features Register"); Phase 0 ships the in-process variant.

23.6 Pitfalls

  • Trusting heartbeats over result-of-record; an acked-but-undelivered task must be re-issued (P11/I8).
  • Letting sticky sessions starve the queue; a crashed sticky worker orphans the thread — recover with a new sticky assignment.

23.7 Performance Concerns

Once un-deferred, per-machine heartbeat traffic (5 s interval, 100 workers/4 machines) adds a small, fixed background load to the bus (≈20 envelopes/s) — negligible against the 50,000 env/s ceiling (M7). The real cost of distribution is cross-machine latency added to every contract-net round-trip, which is why Capacity #10 (single-host saturation) shows the single-process kernel is not throughput-bound at Phase 0 — distribution buys nothing until the LLM-provider quota, not the kernel, is the bottleneck (MM3, §32).

23.8 Edge Cases

  • A worker's heartbeat is delayed by GC pause or scheduler contention, not an actual crash: the 3-missed-heartbeat threshold (15 s) is a tuned tradeoff, not a hard physical truth — a false-positive "dead" worker's in-flight task is re-announced and, if the original later returns a result, I8 dead-letters the duplicate (no double-completion regardless of the false positive).
  • A sticky-session worker crashes mid-thread: the thread is orphaned until a new sticky assignment recovers it — the thread's FIFO order (I7) is preserved across the reassignment because ordering is a bus property, not a worker property.
  • A partition heals and both sides have re-announced the same task independently: at most one Result of record survives (I8); the other is dead-lettered regardless of which side "recovers first."

23.9 Failure Analysis

A network partition (F8, §26) is symmetric by design — each side assumes the other died, re-announces, and lets I8's duplicate-detection resolve any double-work after healing; blast radius is bounded to the in-flight tasks on the partitioned side, not the whole run. Because this phase ships no running code at Phase 0, its only live failure mode is a conformance-runner defect: if distributed.partition fails to report Deferred cleanly (crashes instead), that is itself a Phase-0 regression against I15.

25. Threat Model

25.1 Trust Boundaries

  1. Inter-agent. Every message between agents is untrusted; a prompt-injected agent can emit a malicious message. The bus enforces schema (I1); the coordinator enforces role registration (I2).
  2. Tool. A worker's tool calls are untrusted; the per-tool permission scope applies at the wrapper (Phase 1).
  3. HTTP/WebSocket. Untrusted clients; authenticated API-keyed clients; authorised per-pattern ACL (Phase 10).
  4. External-data. Anything fetched from the internet is untrusted; the tool wrapper sanitises and arbitration is consulted on suspicious content.

25.2 Threats (≥10)

  1. Prompt injection between agents. Mitigation: provenance tags (sender_role/sender_worker); receivers treat untrusted sources with suspicion; arbitration escalates on detection.
  2. Role hallucination. Mitigation: the bus rejects the send (I2); arbitration consulted.
  3. Stuck loops. Mitigation: loop detector (I14) + budget watchdog (I3).
  4. Runaway costs. Mitigation: budget watchdog (I3), pre-dispatch + 1-Hz.
  5. Dead-letter flood. Mitigation: the dead-letter topic has its own backpressure; overflow triggers an operator alert.
  6. Cross-tenant data leakage. Mitigation: per-run isolation by default (I12); cross-run requires explicit opt-in.
  7. Replay attacks against persisted state. Mitigation: the persistence layer records task outcomes; restart skips completed tasks (I8/I9).
  8. Duplicate award after partition. Mitigation: msg_id dedup; the second result is dead-lettered (I8).
  9. Tool privilege escalation. Mitigation: per-tool scope enforced at the wrapper; out-of-scope calls quarantine the worker.
  10. PII leakage via logs. Mitigation: prompts at DEBUG only; INFO is metadata-only (Phase 20 pitfalls).
  11. API-key compromise. Mitigation: hashed storage, per-key ACLs, rotation API, rate limits.
  12. Resource exhaustion via run flooding. Mitigation: per-key token bucket (burst 10, sustained 1 r/s).

25.3 Deferred security surfaces

PhaseDeferred("Deferred Features Register") — per-key API rate limit at the gateway (for multi-tenant validation) and 30-day fuzzing of the bus envelope parser (a Sealed gate); mTLS at the WebSocket boundary.

Day-2 procedures.

  • Cost runaway response. Lower the per-key rate limit and the pre-dispatch budget threshold; if a single pattern is the culprit, disable it via its ACL while the trace is analyzed.
  • Capacity headroom. Alert at 70 concurrent runs (70% of the 100-agent ceiling); scale-out is the deferred distributed surface, so the near-term lever is shedding load via the rate limiter, not adding hosts.

28. Compatibility & Versioning

  • SemVer. The kernel follows SemVer. The §11 core types are stable across Phase 0; changing one is an ADR-shaped event and at least a minor bump.
  • Envelope evolution. New payload_kinds are additive (minor); changing an existing payload's required fields is breaking (major). Unknown kinds are rejected, never silently dropped (I1).
  • Wire schema. proto/messages.proto mirrors the Pydantic envelope for cross-language consumers; the proto and Pydantic schemas are kept in lockstep by a CI check.
  • Delivery-mode compatibility. Adding a delivery mode is additive; the default (at-least-once) is stable.
  • Pattern API. The Pattern protocol is stable; new patterns are additive. A pattern's role set may grow in a minor release if old call sites still construct.
  • Deprecation policy. A deprecated surface ships behind a warning for one minor cycle before removal in the next major; deferred surfaces are exempt (they were never shipped).
  • Conformance schema. conformance.report.json carries schema_version; the runner refuses to compare across incompatible schema versions.

Worked migration — adding a payload kind. Suppose a future pattern needs a Delegate payload (a worker hands a sub-task to another role mid-task). The migration is additive and minor: (1) add the Delegate(BaseModel) model and register it in PAYLOAD_KINDS; (2) commit its JSON schema under schemas/messages/delegate.json; (3) add the proto message to proto/messages.proto and pass the lockstep CI check; (4) add a core.types conformance case so round-trip is bit-identical. Older kernels reject Delegate envelopes as unknown kinds (I1) rather than mis-parsing them, so a mixed-version fleet degrades safely: a new-kernel sender talking to an old-kernel receiver sees its Delegate dead-lettered, never silently dropped.

Worked migration — changing an existing payload (breaking). Removing or renaming a required field on Bid is a major bump. The procedure: ship the new field as optional in version N (minor), dual-write both forms for one minor cycle, flip the default in N+1, and remove the old field in the next major. The conformance corpus is re-recorded for the new shape and the old cassettes are retired with provenance (§24.7). No in-flight run straddles the change because runs complete or resume under a single schema_version (§28 conformance-schema gate).

29. Testing & Verification Strategy

  • Unit. Each module's invariants (I1–I15) have targeted unit tests; envelope round-trip is property-tested for bit-identity (core.types).
  • Property. Hypothesis-driven tests for the bus (delivery ordering per mode), the blackboard (CAS linearizability under contention), and the DAG (no node fires before upstream readiness).
  • Integration. The five patterns run end to end against recorded cassettes in tests/integration/.
  • Conformance. The §24 suite is the gate for Done/Sealed; recorded corpora with ground-truth outcomes.
  • Determinism. Cassette replay makes LLM calls deterministic (P7); the structure (DAG shape, envelope, span tree) is asserted stable even when text varies.
  • Soak. A 24-hour 1 r/s mixed-pattern soak asserts zero unhandled exceptions and zero memory growth (M10).
  • Fuzzing (deferred Sealed gate). 30-day fuzzing of the bus envelope parser — PhaseDeferred("Deferred Features Register").
  • CI gates. pytest, ruff, mypy --strict, pyright, pip-audit, bandit; a conformance regression blocks merge.

The cassette discipline. Every recorded LLM interaction is stored as a (request_hash → response) cassette keyed on the normalized prompt. In tests, the worker's model client is swapped for a cassette client that raises on a cache miss — so a test can never silently fall through to a live model. Cassettes are regenerated only by an explicit make record-cassettes run against a real provider, reviewed in the PR, and committed; a drifting cassette is a reviewable diff, not a hidden flake.

What "deterministic structure" means. Under cassette replay, the same (pattern, inputs, seed) must reproduce the same DAG shape, the same envelope sequence per thread, and the same span tree shape. Text content of LLM outputs may vary if a cassette is regenerated, but the structure is asserted byte-stable. Conformance pattern buckets therefore assert on judged outcomes (majority-of-three-judge winner) at ≥80%, not on text equality (§24.2), which is why pattern tests tolerate model nondeterminism while structural tests do not.

Property-test invariants. The bus property test asserts that, for any interleaving of sends within one thread, deliveries are a prefix-preserving permutation that respects FIFO (I7). The blackboard property test asserts CAS linearizability: for any concurrent write schedule, exactly one writer at each version succeeds and every other receives Conflict (I6). The DAG property test asserts no node's handler is entered before all its upstream results are present (the readiness predicate is sound).

Performance method. Every M-target is measured against recorded LLM cassettes so the number isolates kernel overhead from model latency (P7). Hot paths and their budgets.

  • Envelope construction/validation (Phase 2). The dominant per-message cost. Internal, pre-validated envelopes use model_construct to skip re-validation; only envelopes crossing a trust boundary (from a worker, from HTTP) are fully validated. This keeps the bus at ≥ 50k env/s (M7).
  • Readiness checks (Phase 5). O(in-degree) per node, evaluated only when an upstream result lands — never by polling. This keeps 1000-node dispatch at p99 ≤ 100 ms (M8).
  • Ledger writes (Phase 8). Batched per dispatch, not per token, so the cost ledger never gates the dispatch loop; the per-call tuple is buffered and flushed asynchronously.
  • Span emission (Phase 8). Async, bounded buffer; overflow samples rather than blocks (§20.6), so tracing never appears on the critical path.

Regression guard. The nightly patterns.yml benchmark posts cost/wall/quality curves; a regression beyond the M-target tolerance opens an issue and is treated as a release blocker, not a warning.

32. Scalability Analysis

  • Vertical (Phase 0). A single coordinator process scales to 100 concurrent agents on a 64-core host. The bottleneck above ~50k envelopes/s is per-envelope Pydantic validation; mitigated by model_construct on the hot path for pre-validated internal envelopes.
  • DAG width. Parallelism is bounded by max-parallelism (default 16) and the worker pool size; a 1000-node DAG dispatches in p99 ≤ 100 ms because readiness checks are O(in-degree) per node, not O(nodes).
  • Blackboard contention. CAS contention on a single hot key degrades to retry storms; the F5 escalation path bounds retries; sharding hot keys by sub-prefix is the operator's lever.
  • Cost as the real scaling axis. Throughput is rarely the limit in production; dollars are. The budget watchdog and cost ledger make $/run the first-class scaling dimension.
  • Horizontal (deferred). Distributed workers across machines (Deferred Features Register) lift the single-host ceiling; the envelope/bus contract is already location-transparent (§23), so scale-out is additive, not a rewrite.
  • Persistence. Postgres write throughput bounds the persist-on-every-transition default; the tuning knob (persist every N transitions) trades RPO for throughput.

Single-host saturation model. With 100 concurrent agents and a mean LLM call of ~5 s, steady-state completion is ~20 tasks/s (Capacity #10). The bus at 50k env/s is 2500× over-provisioned, so the saturating resource is neither CPU nor the bus — it is the LLM provider's rate limit and the dollar budget. The practical ceiling on a single host is therefore set by (a) the provider's tokens-per-minute quota and (b) the operator's aggregate budget, not by the kernel. This is the central scaling insight (MM3): scaling the kernel horizontally buys nothing until the provider quota is the bottleneck, which is exactly when the deferred distributed surface un-defers (Deferred Features Register).

Where the kernel actually breaks first under load. As concurrency climbs toward the ceiling, the first observable degradation is Postgres write contention on the DAG-persistence table (every transition writes). The mitigation order is: (1) raise the persist cadence knob (every N transitions) trading RPO; (2) move the ledger to a separate connection pool so cost writes do not contend with state writes; (3) partition the persistence table by run_id. Only after these are exhausted does adding hosts help — and that requires the distributed surface.

Blackboard sharding. A single hot key under heavy CAS contention produces a retry storm bounded by the retry count (F5). The operator's lever is to shard the logical key by sub-prefix (run.<id>.draft.<shard>), trading a single linearizable point for N independently-versioned points — appropriate only when the agents genuinely write disjoint regions, never when they need a single agreed value.

Mental Models & First Principles

  • MM1 — Coordination is the product; the agent is a dependency. Predicts: most "multi-agent bugs" are coordination bugs, not model bugs. Without it you keep tuning prompts while a bus race eats your weekend. Applied in §2, Phase 4.
  • MM2 — A multi-agent system is a distributed system with an LLM-shaped failure injector. Predicts: every classic distributed-systems failure (partition, duplicate, lost update) reappears, plus prompt injection. Without it you under-build the dead-letter, dedup, and CAS paths. Applied in §25, Phase 2, Phase 6.
  • MM3 — Dollars are the tightest resource, not CPU. Predicts: the budget watchdog matters more than throughput optimization. Without it a stuck loop bills $200. Applied in §4, Phase 4, §32.
  • MM4 — Provenance beats trust. Predicts: you cannot make an LLM trustworthy, but you can tag every message with where it came from and enforce it. Without it, role hallucination and injection propagate silently. Applied in I2, §25.
  • MM5 — State and communication are different physics. Predicts: mixing the blackboard and the bus produces races debuggable only by trace archaeology. Without the separation you re-derive it after the first incident. Applied in P4, Phase 6.
  • MM6 — The result is the only truth; everything else is a hint. Predicts: heartbeats and acks tell you about liveness, never completion. Without it you lose acked-but-undelivered tasks on partition. Applied in P11/I8, Phase 11.
  • MM7 — Structured cancellation or leaks. Predicts: ad-hoc task.cancel() orphans children and leaves half-written state. Without TaskGroups you leak FDs and corrupt the blackboard. Applied in P5/I4, Phase 1, Phase 4.
  • MM8 — The trace is the source of truth for debugging, so build it first-class. Predicts: if a dialogue node has no span, it is invisible exactly when you need it. Without span-per-message you debug by re-running and praying. Applied in P9, Phase 8.
  • MM9 — Determinism is a testing strategy, not a runtime property. Predicts: you make tests deterministic with cassettes and assert structural stability, not text equality. Without it conformance is flaky and incidents are irreproducible. Applied in P7, §29.
  • MM10 — Defer with a typed anchor, never with a TODO. Predicts: an un-anchored deferral becomes scope creep or a silent half-feature. Without the register and PhaseDeferred, the Sealed gate is unenforceable. Applied in P12/I15, Deferred Features Register.

Back-of-Envelope Capacity Model

Each number is derived from the §4 System Constraints table.

  1. Bus throughput ceiling. Target ≥ 50,000 env/s (M7) on 64 cores ⇒ per-envelope budget = 64 cores / 50,000 = 1.28 ms-core/env. With Pydantic validation at ~30 µs/env and stream hand-off ~5 µs, headroom ≈ 1.28 ms / 35 µs ≈ 36×; the limit is GIL contention, not CPU.
  2. Coordinator overhead share. p99 ≤ 5 ms/task (§4) and a debate dispatches ~30 tasks (M1) ⇒ pure coordinator overhead ≤ 30 × 5 ms = 150 ms, i.e. < 0.3% of the 60 s wall budget — LLM latency dominates, as designed.
  3. Per-run memory. ≤ 8 MiB/run (§4); at 100 concurrent runs ⇒ 800 MiB run overhead + 150 MiB idle RSS = 950 MiB, comfortably under 256 GiB host RAM.
  4. FD budget. ≤ 512 FDs at 100 workers (§4) ⇒ ~5 FDs/worker (1 stream pair + Postgres pool share + exporter); a 100-worker host stays at ~10% of a 4096 soft-limit.
  5. DAG dispatch cost. 1000-node DAG, p99 ≤ 100 ms (§4) ⇒ ≤ 100 µs/node for readiness + topo bookkeeping; achievable because readiness is O(in-degree), and mean in-degree in the reference patterns is < 4.
  6. Budget-detection latency. 1-Hz heartbeat + pre-dispatch check (§4) ⇒ worst-case overage window = max(1 s heartbeat, one in-flight LLM call). For a $0.50 debate cap and ~$0.05 calls, at most one extra call ($0.05, 10%) can slip before Cancel.
  7. Cost per debate. M1 cap $0.50 over 30 tasks ⇒ ≤ $0.0167/task average; the 1.5× award headroom means the watchdog tolerates ~$0.025/task before pre-dispatch refusal.
  8. Soak footprint. 24 h at 1 r/s = 86,400 runs; with ledger rows ~300 B/call and ~10 calls/run ⇒ 86,400 × 10 × 300 B ≈ 260 MB/day of ledger — trivial for Postgres, retention default 90 days ⇒ ~23 GB steady state.
  9. Conformance wall-clock. 17 buckets, ~100 cases each, suite ≤ 60 min (M12) ⇒ ≤ 60 min / 1700 cases ≈ 2.1 s/case average against cassettes — feasible since no live LLM calls.
  10. Throughput vs concurrency. 100 workers × (1 / mean LLM latency ~5 s) ≈ 20 task-completions/s steady state; the bus (50k env/s) is 2500× over-provisioned relative to LLM-bound completion — confirming MM3 (dollars, not envelopes, bind).

Alternative Architectures (Roads Not Taken)

A. Peer-to-peer actor mesh (no central coordinator).

[agent]──msg──>[agent]
   │  \        /  │
   ▼   \      /   ▼
[agent]──msg──>[agent]      (mailboxes, location-transparent)

Wins when the topology is large, dynamic, and latency-sensitive, and you want no single bottleneck. Embodied by Akka / Erlang/OTP. Rejected because it violates P2: routing decisions scatter, traces lose edges, and budget/cost enforcement has no central choke point — exactly the operability the kernel is built to provide.

B. Shared-object-store dataflow (lineage re-execution).

[task]→[obj store]→[task]→[obj store]→[task]   (re-exec from lineage on failure)

Wins for massive data/ML task graphs where recomputation is cheap and the budget axis is dollars-of-CPU, not dollars-of-LLM. Embodied by Ray. Rejected because lineage re-execution of an LLM call re-bills the model; for LLM workloads the result-of-record + re-announce model (I8) is cheaper and the object store is overhead.

C. Static pub/sub graph (fixed topology, real-time).

[node]──topic──>[node]──topic──>[node]   (compile-time wiring, hard latency bounds)

Wins where the topology never changes and latency is hard-bounded (robotics, control). Embodied by ROS 2. Rejected because agent workflows are dynamic DAGs compiled per run with branching and loops; a static graph cannot express a critic that loops back N times with a runtime terminate_when.

D. Virtual-actor directory (on-demand activation across machines).

client→[grain directory]→activate [grain] on some host→persist state

Wins for elastic, stateful cloud services with many idle entities. Embodied by Microsoft Orleans. Rejected at Phase 0 because on-demand cross-machine activation is the deferred distributed surface; the single-process kernel needs no grain directory and gains nothing from one until scale-out un-defers (Deferred Features Register).

Glossary

  • Agent. A single-agent runtime from the Agentic-Framework (#26). The kernel sees only a Worker wrapper.
  • Arbitration policy. The kernel's response to ambiguity/conflict (stuck loops, dead-letter floods, conflicting writes). Default: rule-based with LLM-judge fallback.
  • At-least-once. Delivery mode (default): the consumer acks after handling; redelivery on no-ack.
  • At-most-once. Fire-and-forget delivery; no redelivery.
  • Award. The coordinator's selection of the winning bidder; step 3 of the contract net.
  • Backpressure. The sender awaits when a bounded queue is full; no hidden buffer absorbs bursts.
  • Bid. A worker's offer to take a task; step 2 of the contract net.
  • Blackboard. A shared versioned KV store for state more than one agent reads/writes; per-run by default.
  • Budget. The cap on a run: max cost, wall-clock, steps, tokens. Enforced by the watchdog.
  • Bus. The typed message channel; in-process by default, cross-process via #58.
  • Cancellation. Cooperative termination, AnyIO TaskGroup-shaped; parents cancel children, not vice versa.
  • CAS. Compare-and-set: a write carries an expected_version; mismatch is rejected.
  • Cassette. A recorded LLM-call replay used to make tests deterministic.
  • Contract Net. Smith's 1980 allocation protocol: announce, bid, award, result.
  • Coordinator. The single orchestrator: compiles patterns, dispatches, runs the contract net, watches budgets/deadlines, arbitrates.
  • Cost ledger. The per-call record of (provider, model, tokens, cost, run, task, role).
  • DAG. Directed Acyclic Graph (with optional back-edges marking loops); the internal form of a Pattern.
  • Dead letter. A message that exceeded its delivery attempts; stored on a separate topic.
  • Deferral. A surface not shipped at Phase 0, anchored via PhaseDeferred("Deferred Features Register").
  • Delivery mode. at-most-once / at-least-once / exactly-once-via-dedupe.
  • Determinism. Same (pattern, inputs, seed, replays) ⇒ same trace structure.
  • Envelope. The frozen wrapper around every bus message; carries identity, routing, timing, and a typed payload.
  • Episodic memory. A per-agent verbatim log of received/emitted messages.
  • Event. A coordinator output element (TaskAnnounced, Awarded, Done, …) streamed to the application.
  • Exactly-once-via-dedupe. Delivery mode using a bounded LRU of recent msg_ids to drop duplicates.
  • HITL. Human-in-the-loop: a DAG checkpoint that pauses for an external Resume.
  • Idempotency-Key. A header making run creation idempotent; duplicates return the same run id.
  • LLM-judge. An arbitration policy where a manager LLM ranks bids or verdicts.
  • Loop. A DAG back-edge with max_iterations and terminate_when.
  • Manager-choice. An award strategy deferring winner selection to the LLM-judge policy.
  • Pattern. A typed dataclass naming roles, the graph, and the default budget; the user-facing surface.
  • PhaseDeferred. The typed deferral exception; its string anchors at the Deferred Features Register.
  • Provenance. The sender_role/sender_worker tags carried by every envelope.
  • Result. The outcome of an awarded task; step 4 of the contract net; the only completion signal.
  • Role. A named registration on the bus; patterns declare roles, workers register against them.
  • Run. A single coordinator invocation, identified by a RunId.
  • Semantic memory. A per-agent distilled-fact store on the Vector-Database.
  • Shared memory. A team-level store on the Vector-Database.
  • Span. An OpenTelemetry trace node; the kernel emits span-per-run/task/message/tool.
  • Sticky session. Pinning all messages in a thread to one worker (stateful workers).
  • Stuck loop. A repeated (sender, recipient, payload-hash) tuple within the sliding window.
  • Subscription. A worker's registration to be notified on blackboard writes matching a prefix.
  • TaskAnnounce. Step 1 of the contract net: a broadcast to a role.
  • Thread. A sub-conversation identified by a ThreadId; per-thread FIFO order is guaranteed.
  • TTL. An optional per-blackboard-key expiry.
  • Watchdog. The budget/deadline enforcement loop (1-Hz heartbeat + pre-dispatch).
  • Worker. A Worker ABC subclass wrapping an Agent (LLM) or Tool (non-LLM).

Appendix C — Operator Tuning Guide (condensed)

A condensed version of docs/operator/tuning.md; the knobs an operator turns and the trade-offs each implies.

Budget watchdog. Heartbeat frequency default 1 Hz (range 0.5–10 Hz; higher catches runaways faster at the cost of wakeups). Pre-dispatch threshold default 80% of budget (below → dispatch; above → pause and consult arbitration).

Contract-net. Bid window default 2 s (range 1–10; shorter favors fast bidders, longer favors careful estimates). Award strategy default lowest-cost; manager-choice for high-stakes tasks. Re-announce threshold default 3 failures, then escalate to manager-choice.

DAG executor. Max parallelism default 16 (range 1–256, bounded by pool size). Persistence cadence default every transition (lower trades RPO for Postgres load). Loop max iterations default 5, per-pattern override.

Blackboard. CAS retry count default 3 (beyond N → escalate). TTL default off (per-key opt-in). Persistence default in-memory; Postgres for durability.

Cost ledger. Reporting cadence default per-call (per-batch trades resolution for load). Retention default 90 days, per-tenant override.

Tracing. Sampling rate default 1.0 (lower under load; the tree degrades gracefully). Exporter buffer default 1000 spans (overflow drops oldest with a metric).

Stuck-loop detector. Sliding window default 10 messages (range 5–100; smaller catches loops earlier at the cost of false positives). Detection threshold default 3 repeats, per-pattern override (debate needs a higher threshold than code review).

Appendix D — Compliance Mapping (non-normative)

Maps the kernel's surface to common compliance requirements. The mapping is non-normative; the kernel does not certify compliance but ships features that make it feasible. Gaps are tracked as PhaseDeferred("Deferred Features Register") call sites.

  • GDPR Art. 17 (Right to be forgotten). memory.delete(fact_id) removes a fact; retention SLA 30 days; ledger and trace exporter respect the same window.
  • GDPR Art. 20 (Data portability). The runs API returns every event in a run as portable JSON.
  • SOC 2 CC6 (Logical access). API-key auth; per-key pattern-level ACLs; per-key audit log.
  • SOC 2 CC7 (System operations). Prometheus metrics; OpenTelemetry tracing; structured logging; runbooks; on-call template.
  • HIPAA Security Rule, 45 CFR 164.312(b) (Audit controls). Per-key and per-pattern audit logs; the trace exporter is itself audit-logged.
  • PCI-DSS Req. 8 (Authenticate access). API keys stored hashed; rotation API; mTLS at the WebSocket boundary is deferred (PhaseDeferred("Deferred Features Register")).
