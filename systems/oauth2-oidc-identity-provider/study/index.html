  4. Why is pinning verify-alg to the resolved key — not the JWT header — sufficient to kill both alg:none and RS↔HS confusion, and where would a permissive library reintroduce each? (MM4 + I5 + P5 + §8.9 + Threat Model "Token forgery")

  8. What does sender-constraining a token (DPoP cnf.jkt / mTLS cnf.x5t#S256) actually defeat, what does it not defeat, and why is binding-without-enforcement merely cosmetic? (MM2 + P13 + I17/I18 + §11.6 pitfalls + Threat Model "Token theft")

Mental Models & First Principles

The compressed intuitions an expert IdP engineer holds. Each: the insight, what it predicts, the bug class you ship without it, and where this blueprint applies it.

MM1 — The browser is a courier you cannot trust; it may carry a claim ticket, never the valuables. A front-channel redirect is fully visible and tamperable (history, referer, logs, a malicious app on the same custom scheme). Insight: anything that crosses the browser must be useless to a thief on its own. Predicts: a token placed in a redirect (implicit grant) is a token leak waiting to happen; a code that is single-use, ≤60 s, and bound to a secret the browser never saw (PKCE verifier) is safe to send. Bug without it: you "optimize" by returning the access token directly to save a round-trip and create OAuth's original sin. Applied: §8.3 (front-channel sequence), Phase 3 (code issuance), Phase 4 (PKCE verify), ADR-22 (no implicit).

MM2 — A token is frozen authority; its only brakes are expiry and binding. Once minted, a bearer token is valid to whoever holds it until it expires or is revoked — and a stateless JWT cannot truly be revoked. Insight: you control blast radius up front (short TTL), or by tying the token to a key the holder must prove (DPoP/mTLS cnf), not after the fact. Predicts: "revoke this JWT now" is mostly a lie; the honest answers are short TTL + denylist-by-jti (best-effort) or sender-constraint. Bug without it: a 24-hour JWT access token that a single log leak turns into a day of account takeover. Applied: §4.1 (TTLs), P1, P13, Phase 6 (JWT-AT revocation gap), Phase 11 (cnf binding), MM6.

MM3 — kid makes a signing key a version pointer, so rotation is a deploy, not a flag day. Every JWS header names the key by thumbprint; verifiers select the key by kid, not by guessing. Insight: if old and new keys coexist in JWKS for ≥ max token TTL, every in-flight token keeps a resolvable verification key while new tokens use the new key. Predicts: rotation breaks only if you retire a key before its tokens expire (overlap < TTL) — the retire guard is the whole game. Bug without it: you "rotate" by overwriting the key and trigger a fleet-wide invalid_token 401 storm. Applied: §8.5 (rotation timeline), I8, P6, Phase 2 (rotation FSM), MM5.

MM4 — Trust the key's declared algorithm, never the attacker's JWT header. The alg in a JWS header is attacker-controlled input; the algorithm a token should be verified under is a property of the resolved key. Insight: pin verify-alg to resolve(kid).alg; treat alg:none and RS↔HS as category errors, not configurations. Predicts: every classic JOSE forgery (the alg:none bypass; RS256→HS256 confusion where the public key is used as an HMAC secret) is structurally impossible once the header alg is never consulted for the algorithm choice. Bug without it: a permissive library verifies with whatever the header says and accepts forged id_tokens. Applied: I5, P5, Phase 2 (alg pinning), §8.9 (alg attack rows), Required Reading (Boneh-Shoup, Katz-Lindell).

MM5 — Single-use is a write-once claim that must be settled by one atomic operation. "Consumed exactly once" across N stateless replicas is not an application check; it is a property of one conditional store mutation (DELETE … RETURNING / compare-and-set). Insight: read-then-act is a race; the store's transaction is the only arbiter that holds under concurrency. Predicts: any code/refresh consumption split into read + delete will double-redeem under load or a retry storm. Bug without it: two replicas each redeem the same code, minting two token sets from one authorization. Applied: I1, I9, Phase 4 (atomic consume), Phase 6 (atomic rotate), §8.10 (concurrent-code edge), MM3.

MM6 — Refresh rotation converts a silent theft into a loud, self-revoking event. If every refresh use rotates the token and an already-rotated token is presented, exactly one of {legitimate client, thief} is now holding a dead token — and the collision is observable. Insight: you cannot prevent refresh-token theft, but you can guarantee it surfaces (family revocation + audit) the moment both parties try to use the chain. Predicts: a non-rotating refresh token makes theft permanent and invisible; rotation bounds it to one rotation interval and emits a high-signal alert. Bug without it: a stolen refresh token mints access tokens forever and you never know. Applied: §8.4 (reuse-detection FSM), I9, P7, Phase 6, Phase 12 (anomaly), MM2.

MM7 — id_token answers who; access token answers what they may do; confusing them is a privilege error. The id_token (audience = the client, proves authentication to the RP) and the access token (audience = a resource server, authorizes API calls) are different credentials with different audiences and lifetimes. Insight: audience (aud) is the type tag; a resource server must reject an id_token, and an RP must not send an id_token to an API. Predicts: using an id_token as an access token (a real, recurring integration mistake) lets a credential meant only to prove identity act as an API key. Bug without it: an RS that accepts any signed JWT from the issuer authorizes id_tokens. Applied: §2.1, §8.2 (token formats), I6, Phase 5 (claims/audience), §17.6 (pitfall).

MM8 — The OP is server-authoritative; every client-supplied value is a request, not a fact. Scopes, redirect URIs, subject, audience, and grant are re-derived from registration and server-side state, never accepted as asserted by the client. Insight: the client says what it wants; the OP decides what is true (scope ⊆ registered, redirect ∈ registered set, code bindings from the stored record). Predicts: any branch that trusts a client assertion (a client-chosen scope, a client-chosen sub) is a privilege-escalation vector. Bug without it: "if scope is missing, grant all" or accepting a client-asserted subject. Applied: P11, I3, I14, Phase 1 (registry), Phase 3/Phase 4 (re-validation), §8.9.

MM9 — Defense against replay is layered; each control covers a different axis. state (RP CSRF/round-trip), nonce (id_token replay), jti (DPoP/assertion replay), single-use code, single-use user_code — distinct values guarding distinct flows, each backed by a bounded cache sized to its lifetime. Insight: no single value defends the whole protocol; remove one and a specific replay class reopens. Predicts: dropping nonce reopens id_token replay even with perfect state; an unbounded jti cache either leaks memory or evicts early and admits replay. Bug without it: you assume state "covers replay" and ship an id_token replay hole. Applied: P14, I12, I23, Phase 3 (state/nonce), Phase 11 (jti/DPoP), §4.1 (cache sizing).

MM10 — Fail closed: in identity, "allow on ambiguity" is "allow the attacker". Any unrecognized parameter combination, unverifiable signature, missing required field, or ambiguous state resolves to a precise typed rejection (RFC 6749 sec. 5.2), never a permissive fallback or a generic 500 that leaks state. Insight: the safe default in an authorization server is deny, and every denial maps to an exact error code so it is debuggable without leaking. Predicts: a default-allow arm or a catch-all match that silently accepts an unmodeled grant is the bug that becomes the breach. Bug without it: a permissive fallback authorizes a request the spec says to refuse. Applied: P9, the exhaustive idp-core enums (§11.1), Phase 0 (typed errors), the Failure Modes recovery philosophy (fail-closed sec. 5.2 refusals), every phase N.4.

Required reading (§5)

Books

  • Justin Richer & Antonio Sanso — OAuth 2 in Action (2017). The canonical implementer's book. Ch 3–5 (auth-code grant, building an AS), Ch 6 (tokens), Ch 9–10 (common vulnerabilities, PKCE), Ch 11 (OIDC), Ch 13 (JOSE/JWT). Extract: the AS state model and the attack→mitigation pairing. Applied in: §8 (protocol model), Phase 3/Phase 4 (auth-code), Phase 5 (OIDC). Primary reference.
  • Aaron Parecki — OAuth 2.0 Simplified (2018) + oauth.net. Concise endpoint/flow reference. Extract: precise parameter lists and the modern (PKCE-everywhere) flow shape. Applied in: §8.1 (endpoint taxonomy), Phase 3 (/authorize params).
  • Prabath Siriwardena — Advanced API Security: OAuth 2.0 and Beyond (2e, 2020). Ch on token types, introspection, DPoP/mTLS, FAPI. Extract: sender-constraint and resource-server interaction. Applied in: Phase 8 (introspection), Phase 11 (DPoP/mTLS).
  • Michael Schwartz & Maciej Machulak — Securing the Perimeter (2018). OP operations, deployment, Keycloak/Gluu. Extract: running an OP (sessions, logout, federation context). Applied in: Phase 10 (sessions/SSO/logout), Operational Readiness.
  • Neil Madden — API Security in Action (2020). Ch 6–7 (OAuth2, OIDC, tokens), Ch 11 (capabilities/macaroons context). Extract: token security, scoping, and the bearer-token threat. Applied in: §6 (P1 tokens-are-secrets), Phase 4/Phase 5 (token issuance/scoping).
  • Katz & Lindell — Introduction to Modern Cryptography (3e). Signatures (RSA/ECDSA), hash functions, MACs. Extract: the JOSE signing primitives' security foundations. Applied in: Phase 2 (idp-crypto/idp-jose sign/verify), §11.2.
  • Dan Boneh & Victor Shoup — A Graduate Course in Applied Cryptography. Ch on digital signatures + hash functions. Extract: why alg-pinning matters; signature existential unforgeability. Applied in: Phase 2 (alg pinning, I5), MM4.
  • Jim Manico & August Detlefsen — Iron-Clad Java / OWASP ASVS (web) (reference). Extract: CSRF, open-redirect, session-management controls that the browser-facing endpoints need. Applied in: Phase 11 (CSRF/clickjacking), Phase 10 (session cookies), I3/P2.
