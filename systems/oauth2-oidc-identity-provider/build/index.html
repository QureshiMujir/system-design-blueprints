⬜ Phase 0 — Workspace skeleton + HTTP server + endpoint surface + discovery §12

Objectives

Stand up the repo skeleton + correctness kernel: the 16-crate Cargo workspace (§1.6), the idp-core vocabulary (newtypes, closed enums, the RFC 6749 sec. 5.2 OAuthError taxonomy, the Clock/±60 s skew model — §11.1) compiled and locked, and CI (fmt+clippy -D+test, ADR-30) green on an empty tree. On that floor, build idp-http (TLS 1.3 termination, router, request parse/validate, security headers, CORS, error rendering, middleware skeleton) and idp-discovery (/.well-known/openid-configuration, /.well-known/oauth-authorization-server). Establish the trust boundary (P9, P11) and the two error shapes (JSON + redirect-error). All endpoints exist as routes returning typed stubs/not_implemented so the surface is fixed before behavior. The correctness kernel's smoke test is a deterministic round-trip of the error taxonomy and discovery document so every later phase inherits a stable contract.

Deliverable

A compiling 16-crate workspace with idp-core locked and CI green; a TLS server answering every endpoint with validated parsing; the two discovery documents return correct, config-derived metadata; cargo test -p idp-core -p idp-http -p idp-discovery green; curl https://localhost/.well-known/openid-configuration returns valid JSON.

Acceptance
  • Workspace builds with --locked; idp-core enums exhaustive (no catch-all arm); clippy -D warnings clean (ADR-30).
  • All §8.1 routes resolve; unknown route → 404, wrong method → 405, oversize → 400.
  • Discovery docs validate against OIDC Discovery / RFC 8414 schemas; issuer exactly matches config; every advertised endpoint URL is reachable.
  • Redirect-error encoder preserves state and appends iss (I22); JSON error sets Cache-Control: no-store.
  • TLS 1.3 only; HTTP downgrade refused on the TLS port.

Fixture Purpose Expected

vectors/discovery_as.json RFC 8414 shape schema-valid
vectors/error_redirect.json redirect-error format ?error&state&iss

Pitfalls
  • Reflecting an unvalidated redirect_uri in an error before client resolution = open redirect; never redirect pre-validation (P2,I3).
  • Discovery drift: hardcoding endpoints that diverge from the router silently misconfigures every client; derive from one source.
  • Missing Cache-Control: no-store on token/authorize responses leaks tokens to shared caches (P1).
  • CORS * with credentials enables cross-site token theft; strict allowlist only.

⬜ Phase 1 — Client registry §13

Objectives

Build idp-client: confidential vs public clients, static + dynamic registration (RFC 7591) + management (RFC 7592), exact-match redirect URIs (I3,P2), the four client-authentication methods (I13), and metadata validation with secret hashing (I10). Server-authoritative client state (P11).

Deliverable

Register clients statically (CLI/config) and dynamically (/register); authenticate clients via all four methods at a stub token endpoint; redirect matching enforced; cargo test -p idp-client green.

Acceptance
  • Exact redirect match: https://rp/cb registered ⇒ https://rp/cb?x=1 and https://rp/cb/ both rejected (I3).
  • Public client presenting a secret → invalid_client; confidential without auth → invalid_client (I13).
  • private_key_jwt with reused jti → rejected; with wrong aud → rejected.
  • Secret stored hashed; comparison constant-time (I10); dynamic registration round-trips metadata.

  • Normalizing the redirect URI (lowercasing host, stripping default port, decoding) before compare reintroduces the open-redirect gap; compare raw registered strings (I3).

⬜ Phase 2 — Key management + JWKS §14

Objectives

Build idp-keys + idp-jose: signing keypair generation (RS256/ES256/EdDSA), kid assignment (JWK thumbprint RFC 7638), /jwks.json publication, and the rotation state machine (introduce → dual-publish → activate → retire) that never breaks in-flight validation (I8,P6). Lock alg discipline: no alg:none, alg pinned to key (I5,P5).

Deliverable

Generate keys per alg, publish /jwks.json, sign + verify a JWT, and execute a full rotation with both keys in JWKS during overlap; cargo test -p idp-keys -p idp-jose green.

Acceptance
  • Round-trip sign→verify for RS256/ES256/EdDSA; cross-alg token rejected (I5).
  • alg:none JWT rejected; JWT whose header alg differs from the resolved key's alg rejected (I5,P5).
  • During rotation, a token signed by the old key still verifies while JWKS lists both; after retire_expired past overlap, old kid no longer resolves and JWKS drops it (I8).
  • kid is a stable RFC 7638 thumbprint; present in every JWS header (I7).
Fixtures
Fixture Purpose Expected
vectors/jws_rs256.json sign/verify match
vectors/jws_es256.json sign/verify match
vectors/jws_eddsa.json sign/verify match
vectors/alg_none_reject.json I5 rejected
vectors/alg_confusion.json RS/HS confusion rejected
vectors/jwks_thumbprint.json RFC 7638 kid exact
vectors/rotation_overlap.json I8 both verify in window
Pitfalls
  • Verifying with the header's alg (not the key's) is the alg-confusion CVE class; pin to key (I5).
  • Reusing a kid across two distinct keys breaks resolution; thumbprint makes kid content-addressed (collision-free).
  • Retiring a key before its tokens expire causes 401 storms at resource servers (I8); retire must check now > activate + max_ttl.
  • RSA PKCS#1 v1.5 vs PSS mismatch between sign/verify silently fails; pin per key.

⬜ Phase 3 — Authorization endpoint + auth-code grant §15

Objectives

Build idp-authz: /authorize with response_type=code, full parameter validation, state, mandatory PKCE (code_challenge+S256, RFC 7636, I4,P3), end-user authentication (login) + IdP session establishment, and single-use, ≤60 s authorization-code issuance bound to client_id+redirect_uri+code_challenge+scope+nonce (I1,I2). Emit iss response param (I22,RFC 9207).

Deliverable

A browser hitting /authorize with PKCE authenticates, (auto-)consents, and receives a redirect with code, state, iss; the code is stored single-use and fully bound; cargo test -p idp-authz green.

Acceptance
  • Missing/plain PKCE rejected by default (P3); S256 challenge stored.
  • Redirect code response includes state (echoed) + iss (I12,I22); code TTL ≤60 s, single-use, bound (I1,I2).
  • Bad redirect_uri/client_id → direct error (never redirect); other errors → redirect-error with state+iss.
  • scope not ⊆ registered → invalid_scope redirect-error (I14).
Fixtures
Fixture Purpose Expected
vectors/authorize_ok.json happy path code+state+iss
vectors/authorize_no_pkce.json P3 invalid_request
vectors/authorize_bad_redirect.json I3 direct 400
vectors/authorize_bad_scope.json I14 redirect invalid_scope
vectors/code_binding.json I2 bound fields present
Pitfalls
  • Issuing a code before validating the redirect URI = code leak to attacker URI (I3); validate first.
  • Forgetting to bind nonce into the code drops it from the eventual id_token (I6,I12).
  • Not echoing state enables CSRF on the RP (I12); always round-trip.
  • Long code TTL widens the replay/injection window; lock ≤60 s (§4.1).
  • Storing the PKCE verifier (not the challenge) at /authorize would leak it; store only the challenge (I4).

⬜ Phase 4 — Token endpoint + code exchange §16

Objectives

Build idp-grant /token for grant_type=authorization_code: client authentication (I13), atomic code consumption (I1), PKCE verifier check (I4), re-validation of all code bindings (I2), and issuance of an access token (JWT RFC 9068 or opaque) + refresh token, with RFC 6749 sec. 5.2 error responses. Clock discipline on issued tokens (I15,P15).

Deliverable

End-to-end auth-code+PKCE: a code from Phase 3 exchanges at /token for access (+refresh) tokens that verify against /jwks.json; replay/replayed-verifier rejected; cargo test -p idp-grant green.

Acceptance
  • Valid code + correct verifier + client auth → 200 with access token (verifiable), expires_in, token_type:Bearer.
  • Wrong code_verifier → invalid_grant (I4); reused code → invalid_grant + derived-token revocation (I1).
  • redirect_uri ≠ code's → invalid_grant (I2); public client w/o PKCE or w/ secret → invalid_client/invalid_request (I13).
  • JWT access token validates: iss, exp>iat, aud, signature, kid resolves (I7,I15).

⬜ Phase 5 — ID Token + OIDC Core §17

Objectives

Build idp-oidc: id_token claims (iss,sub,aud,exp,iat,auth_time,nonce,at_hash,c_hash,acr,amr) signed as JWS (I6); scope→claims mapping (openid profile email address phone); /userinfo (bearer access token → claims, RFC 6750); standard claims; public/pairwise subject derivation (I21); hybrid response_type=code id_token sketched.

Deliverable

/token for an openid-scoped flow returns an id_token that validates (iss/aud/exp/nonce/at_hash) against /jwks.json; /userinfo returns scope-appropriate claims; pairwise subjects differ per sector; cargo test -p idp-oidc green.

Acceptance
  • id_token validates: aud==client_id, iss==issuer, nonce echoed, exp>iat within skew, signature + kid (I6,I7,I15).
  • at_hash/c_hash match the issued access token / code (left-half SHA-256).
  • /userinfo returns only granted-scope claims (I14); sub matches the id_token sub.
  • Pairwise: two clients with different sector_identifier get different sub for the same user; same sector → same sub (I21).
Fixtures
Fixture Purpose Expected

vectors/userinfo_scoped.json I14 scope→claims

Pitfalls
  • Using id_token as an access token (or vice versa) — different aud, different purpose; resource servers must reject id_tokens.
  • Wrong at_hash (full hash vs left-half, wrong alg) breaks RP validation; follow OIDC exactly.

⬜ Phase 6 — Refresh tokens + rotation §18

Objectives

Build refresh-grant in idp-token/idp-grant: grant_type=refresh_token, rotation with reuse detection (replay of a rotated token revokes the whole family, I9,P7), sliding + absolute expiry, and the offline_access scope gate. The reuse-detection state machine (§8.4) is the security centerpiece.

Deliverable

A refresh token exchanges for a new access token + new refresh token (rotation); replaying an old refresh token revokes the family and is audited; expiry enforced; cargo test (refresh suite) green.

Acceptance
  • Each refresh use returns a new RT and invalidates the old (I9); old RT replay → family revoked + audited (P7).
  • Grace-window retry returns the same new RT idempotently (no false reuse).
  • Absolute + idle expiry both terminate the family (invalid_grant).
  • Refresh only issued when offline_access/policy permits; scope down-scoping honored (I14).
Fixtures
Fixture Purpose Expected
vectors/refresh_rotate.json I9 new RT, old invalid
vectors/refresh_reuse.json I9,P7 family revoked + audit
vectors/refresh_grace.json retry idempotent
vectors/refresh_expiry.json TTL invalid_grant
vectors/refresh_downscope.json I14 subset only
Pitfalls
  • Non-atomic rotation races duplicate the head or miss reuse; rotation must be one atomic store op (I9).
  • Too-tight grace window false-positives on legitimate retries (mass logout); too-loose lets an attacker use the window — tune Δt.
  • Forgetting to revoke derived access tokens on family revocation leaves valid ATs from a stolen RT (opaque ATs revocable; JWT ATs rely on short TTL — document the gap).
  • Not capping absolute lifetime makes refresh tokens effectively permanent.

⬜ Phase 7 — Consent §19

Objectives

Build consent in idp-session: a scope + claims consent screen, consent persistence per (sub, client, scope-set) (I20,P8), prompt=none|login|consent, max_age, remembered vs re-prompt logic, and the consent_required/login_required interaction errors. Consent is explicit, scoped, and auditable (P8).

Deliverable

First authorization shows consent; subsequent ones with unchanged scope are silent; prompt=consent re-prompts; prompt=none returns the correct interaction error; cargo test (consent suite) green.

Acceptance
  • Consent persisted per (sub,client,scope-set); re-prompt only when scope grows or prompt=consent (I20).
  • prompt=none + no session → login_required; + session but new scope → consent_required (I20).
  • max_age=0 forces re-auth even with a valid session.
  • Withdrawal revokes the client's tokens for that subject.

⬜ Phase 8 — Token introspection + revocation §20

Objectives

Build /introspect (RFC 7662: active flag + claims, caller authentication, I16) and /revoke (RFC 7009) in idp-grant. Support both the opaque-token store path and the JWT validation path, with caching/TTL. Revocation of a refresh token revokes its family (I9).

Deliverable

A resource server introspects an access token and gets active:true+claims; after /revoke, introspection returns active:false; refresh revoke kills the family; cargo test (introspect/revoke suite) green.

Acceptance
  • /introspect without caller auth → 401 (I16); valid AT → active:true+claims; expired/revoked → active:false.
  • /revoke of a refresh token revokes the family (I9); returns 200 even for unknown tokens (no oracle, P10).
  • Opaque and JWT paths both supported; cache respects TTL + invalidation on revoke.
Fixtures
Fixture Purpose Expected
vectors/introspect_active.json RFC 7662 active+claims
vectors/introspect_unauth.json I16 401
vectors/introspect_revoked.json post-revoke active:false
vectors/revoke_refresh_family.json I9 family gone
vectors/revoke_unknown.json P10 200 no oracle
Pitfalls
  • Unauthenticated introspection is a token-scanning oracle (I16); always require caller auth.
  • Returning detail for inactive tokens leaks token existence (P10); {active:false} only.
  • JWT access tokens can't be truly revoked without a denylist; document that short TTL is the primary mitigation, denylist is best-effort.
  • Caching introspection too long serves a revoked token as active; TTL < remaining life + invalidate on revoke.

⬜ Phase 9 — Additional grants §21

Objectives

Build client_credentials (machine-to-machine), the device authorization grant (RFC 8628: /device_authorization, user_code/device_code, polling with slow_down, I19), PAR (RFC 9126: /par → request_uri), and a token-exchange (RFC 8693) sketch. Explicitly deprecate implicit + ROPC with rationale (OAuth 2.1 / RFC 9700).

Deliverable

Acceptance
  • client_credentials: confidential-only, no user/refresh/id_token, scope ⊆ client scopes (I13,I14).
  • Device: polling faster than interval → slow_down; pending → authorization_pending; approved → tokens; expired → expired_token; user_code single-approval (I19).
  • PAR: request_uri single-use, expires; /authorize with it ignores other query params.
  • Implicit + ROPC → typed unsupported_* errors (documented).

⬜ Phase 10 — Sessions, SSO, logout §22

Objectives

Build idp-session session lifecycle, SSO across RPs, RP-Initiated Logout (/end_session), front-channel + back-channel logout, and OIDC Session Management (/checksession iframe + session_state). The IdP session is distinct from RP sessions and is the SSO anchor.

Deliverable

Logging in at one RP gives SSO at a second; /end_session logs out and notifies RPs (front + back channel); /checksession reflects session changes; cargo test -p idp-session green.

Acceptance
  • Second RP /authorize with existing session → no re-login (SSO), subject to prompt/max_age.
  • /end_session validates id_token_hint + exact post_logout_redirect_uri; ends IdP session.
  • Back-channel logout token is a valid signed JWT with sid/sub+events; front-channel iframes target registered URIs only.
  • session_state changes on login/logout (Session Management).

⬜ Phase 11 — Sender-constrained tokens + security hardening §23

Objectives

Build idp-security: DPoP (RFC 9449, I17), mTLS-bound tokens (RFC 8705, I18), exact redirect matching re-affirmed, mix-up mitigation (iss, RFC 9207, I22), mandatory PKCE re-affirmed, nonce/state replay protection, CSRF on browser forms, and rate-limiting + brute-force/credential-stuffing defenses (cross-link #39). This phase applies the OAuth 2.0 Security BCP (RFC 9700) end-to-end.

Deliverable

DPoP-bound and mTLS-bound access tokens issued + enforced; replayed DPoP jti rejected; rate limits + CSRF active; iss present everywhere; cargo test -p idp-security + security-regression suite green.

Acceptance
  • DPoP: token carries cnf.jkt; resource use without the matching key rejected; replayed jti rejected (I17).
  • mTLS: token carries cnf.x5t#S256; use without the matching client cert rejected (I18).
  • iss present in every authorization response (I22); PKCE mandatory (I4) re-verified; CSRF token required on browser POSTs.
  • Rate limits trip under brute force; credential stuffing locked out (#39).

Fixture Purpose Expected

  • DPoP without htu/htm/jti checks is replayable (I17); verify all three + freshness.

  • Metrics expose issuance-by-grant, error histogram, p50/p99 /token latency; tracing threads a full flow by one correlation id (#132).

⬜ Phase 13 — Conformance + interop + fuzzing §25

Objectives

Validate against OpenID Connect conformance profiles, interop vs real RP libraries + reference OPs (Keycloak/Hydra/node-oidc-provider), fuzz JWT/JWS + token-endpoint + authorize-query parsing, run security regression tests (auth-code injection, PKCE downgrade, token substitution, alg confusion), and soak/chaos. This phase is the release gate.

Deliverable

Passing OIDC Basic/Config/Dynamic conformance profiles; interop with ≥2 external RP libs + ≥1 reference OP; clean fuzz run; green security-regression suite; soak with bounded memory; conformance.report.json published.

Acceptance
  • OIDC conformance profiles pass (Basic + Config + Dynamic).
  • Interop: tokens accepted by external RP libs; our RP accepts reference-OP tokens (and vice versa).
  • Fuzz: zero panics/UB; all malformed input → typed errors (P9).
  • Every security-regression attack fails closed (auth-code injection, PKCE downgrade, token substitution, alg confusion, refresh reuse, mix-up).
  • Soak: stable RSS over ≥1 h; replay caches GC'd; no FD/connection leak.
