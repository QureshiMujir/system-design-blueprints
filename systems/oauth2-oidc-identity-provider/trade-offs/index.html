Alternative Architectures (Roads Not Taken)

Three fundamentally different architectures for the same "issue OAuth/OIDC tokens" problem — not parameter tweaks. Each: sketch, the regime where it wins, the real system that embodies it, why this blueprint rejected it.

Alt-Arch 1 — Headless AS with externalized login/consent (delegated UI).

  Browser ──/authorize──> [AS core (stateless)] ──redirect──> [Your Login+Consent App]
                                  ^                                   |
                                  |  login_challenge / consent_       | authenticates user,
                                  |  challenge (accept/reject) <──────+ collects consent
                                  |
  Browser <──code/redirect────────┘  (AS mints code/tokens after the app accepts)
        [AS keeps NO login UI; identity UX is the integrator's responsibility]

Regime where it wins: an organization that already owns its login experience and user store and wants the AS to be a pure, stateless protocol engine it can scale independently of UX. Real system: Ory Hydra (login/consent apps over a challenge/accept handshake). Why rejected here: the teaching goal is the complete issuer including the login/consent/session state machine (Phase 3, Phase 7, Phase 10); externalizing the UI would hide exactly the front-channel/consent/SSO reasoning this project exists to build, and split the system across a boundary the reader would not implement.

Alt-Arch 2 — Opaque tokens with mandatory central introspection (no stateless JWT validation).

  Client ──/token──> [AS] ── issues opaque AT (random handle) ──> Client
  Client ──AT──> [Resource Server] ──POST /introspect (AT)──> [AS] ──{active, scope, sub}──> RS
        [every API call consults the AS; no RS-side signature verification; instant revocation]

Regime where it wins: a single-tenant or tightly-coupled API platform where instant revocation is mandatory and every resource server can afford a synchronous call to the AS (or a short cache) — the AS is the live authority on every request. Real system: classic opaque-token deployments (the default in Ory Hydra and many gateway-fronted APIs; ADR-12 rejected-alternative). Why rejected as the default: it makes the AS a hot dependency on the resource-server critical path (a scaling + availability coupling, Capacity #7/Scalability Analysis) and loses interop with stateless RS libraries that expect RFC 9068 JWTs. This blueprint supports opaque + introspection (Phase 8) but defaults to JWT (ADR-12) for stateless validation; the alternative wins precisely when "revoke now" beats "validate offline."

Alt-Arch 3 — Macaroons / capability tokens with caveat-based attenuation.

  AS issues: M0 = MAC(root_key, "user=alice; aud=api")          (a capability)
  Client attenuates locally (no AS call):
       M1 = HMAC(M0, "scope=read")  then  M2 = HMAC(M1, "expires=+5m")
  Resource Server verifies the HMAC chain + checks each caveat is satisfied.
        [delegation/attenuation happens at the holder, offline; no per-derivation AS round-trip]

Regime where it wins: systems needing fine-grained, offline delegation where a holder must mint a strictly-weaker token for a downstream service without contacting the issuer (third-party caveats enable distributed authorization). Real system: Google's Macaroons (Birgisson et al., 2014) and their use in internal capability systems; Neil Madden's API Security in Action Ch 11 covers them (Required Reading #5). Why rejected: macaroons are not OAuth/OIDC — they break interop with every RP/RS that speaks JWT/JWKS and with the OIDC conformance suite (Phase 13), and the contract here is standards-conformant issuance (§1.1). They are the right answer to a different question (offline attenuation), which is why the model is worth holding (MM2) even though the architecture is not built.
