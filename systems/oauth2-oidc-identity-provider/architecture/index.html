3. Architectural Overview

3.2 Subsystem Descriptions

idp-http — The front door and the only code that touches the network. Terminates TLS 1.3 (via rustls), runs the axum/hyper router that maps the fixed endpoint surface to handlers, parses and validates every request (query/form/JSON/headers) before any handler sees it, and renders both error shapes the specs demand: the OAuth JSON error body ({"error":"invalid_request",...}) and the front-channel redirect-error (?error=...&state=...). Middleware layers attach a rate-limit decision (#39), extract DPoP proofs and mTLS client-cert thumbprints for downstream binding, open a trace span (#132) carrying a correlation ID, and enforce body/URL size limits (anti-DoS). It is the trust boundary: everything below assumes inputs are syntactically validated but semantically untrusted.

idp-discovery — Publishes the two metadata documents that let clients self-configure: /.well-known/openid-configuration (OIDC Discovery 1.0) and /.well-known/oauth-authorization-server (RFC 8414). Each advertises the issuer, every endpoint URL, supported response_types/grant_types/scopes/claims, signing algs (id_token_signing_alg_values_supported), code_challenge_methods_supported (S256), token-endpoint auth methods, and DPoP/PAR/device capabilities. The documents are derived from live config + the published JWKS so they never drift from actual behavior — a discovery lie is a conformance failure and a security risk (clients trust it).

idp-client — The client registry and the first line of redirect defense. Stores confidential and public client metadata (redirect URIs, grant/response types, scopes, auth method, jwks/jwks_uri for private_key_jwt, subject type, sector identifier). Implements exact-match redirect-URI comparison (full-string, including path/query, no wildcards or substring matches — I3). Supports static registration (config/admin CLI) and dynamic registration (RFC 7591 /register) + management (RFC 7592). Dispatches client authentication at the token endpoint across four methods (client_secret_basic, client_secret_post, private_key_jwt, tls_client_auth), comparing secrets in constant time and verifying private_key_jwt assertions against the client's JWKS.

idp-crypto — The cryptographic floor. Wraps vetted primitives — RSA (RS256: PKCS#1 v1.5 + PSS), ECDSA P-256 (ES256), Ed25519 (EdDSA), SHA-256/384/512 and SHA-3, HKDF, a CSPRNG for token/code entropy, ct_eq constant-time comparison, the PKCE S256 transform (BASE64URL(SHA256(verifier))), and a password-verifier hook (Argon2/bcrypt, cross-link #91). No protocol logic; it is the single audited surface for "which curve, which padding, which hash," and it never rolls its own primitive (RSA/EC/Ed via RustCrypto/ring). Reused conceptually from #88/#89/#90/#91.

idp-jose — The JOSE engine: JWS signing and verification, JWT claim-set construction and validation, JWK/JWKS encoding/decoding, and kid header binding. Its single most important job is algorithm discipline (I5): it rejects alg:none, pins the verification algorithm to the key's declared alg (never to the attacker-controlled JWT header), and refuses RS↔HS alg-confusion. It computes at_hash/c_hash (left-half SHA-256 of the token/code), and provides base64url codecs. JWE is sketched only. Every token format in the system serializes through here, so a JOSE bug is a system-wide break.

idp-keys — The signing-key lifecycle owner. Generates keypairs per algorithm, assigns each a stable kid (JWK thumbprint, RFC 7638), publishes the public halves as JWKS, and runs the rotation state machine: a new key is introduced (published in JWKS but not yet signing), then becomes active (signs new tokens) while the prior key keeps verifying until all tokens it signed have expired, then is retired (removed from JWKS). The overlap window (≥ max token TTL) is the invariant that makes rotation non-breaking (I8). Selects the active signing key and resolves any token's kid to a verification key.

idp-store — The persistence boundary. Defines traits — ClientStore, KeyStore, CodeStore, TokenStore (with refresh-family operations), SessionStore, ConsentStore, and ReplayCache (jti/nonce/code/user_code) — and provides an in-memory backend (tests/dev) and a Postgres backend (durable). It owns the two hardest semantics in the system: atomic single-use consumption (a code/refresh token is consumed exactly once even under concurrent replicas, via a conditional update / DELETE … RETURNING) and TTL-bounded GC of expired records and replay entries. Everything stateful flows through here.

idp-token — The token model and issuance core. Builds and issues all four token kinds: authorization codes (opaque, high-entropy, single-use, ≤60 s, bound to client_id+redirect_uri+code_challenge+scope+nonce), access tokens (JWT per RFC 9068 with typ:at+jwt, or opaque + introspection), id_tokens (JWS per OIDC), and refresh tokens (opaque, tracked in a family for rotation/reuse detection). Stamps TTLs, attaches the cnf confirmation claim for sender-constrained tokens, and enforces that scope granted ⊆ requested ⊆ registered (I14). Signs via idp-jose/idp-keys, persists via idp-store.

idp-authz — The /authorize endpoint and the start of every interactive flow. Validates parameters (client_id, redirect_uri, response_type, scope, state, nonce, code_challenge+code_challenge_method), resolves the client and exact-matches the redirect URI before doing anything else, captures and stores the PKCE challenge, triggers end-user login (via idp-session) and consent (via idp-session) as needed, then issues a single-use authorization code (via idp-token) and redirects back with code, state, and the iss response parameter (RFC 9207, mix-up mitigation). All errors after redirect-URI validation are returned as redirect errors; errors before it are direct (never redirect to an unvalidated URI).

idp-grant — The /token endpoint dispatcher plus /introspect and /revoke. Authenticates the client (via idp-client), dispatches on grant_type to handlers: authorization_code (consume code atomically, verify PKCE, re-check all bindings, issue tokens), refresh_token (rotate + reuse-detect), client_credentials, device-code polling, PAR consumption, and a token-exchange sketch. Emits RFC 6749 sec. 5.2 error responses (invalid_grant, invalid_client, unauthorized_client, unsupported_grant_type, invalid_scope). Introspection (RFC 7662) returns the active flag + claims to an authenticated caller; revocation (RFC 7009) invalidates a token (and, for a refresh token, its family).

idp-oidc — The OpenID Connect Core layer. Assembles the id_token (claims iss, sub, aud, exp, iat, auth_time, nonce, at_hash, c_hash, acr, amr), maps requested scopes to standard claims (profile→name/picture/…, email→email+verified, address, phone), serves /userinfo (bearer access token → claims), derives the subject identifier per subject_type (public or pairwise via sector identifier), and sketches the hybrid response_type=code id_token (front-channel id_token + c_hash binding the code). It depends on idp-token/idp-jose for signing and on idp-session for auth_time/acr/amr.

idp-session — The identity and consent state machine. Owns the IdP session (the user's authenticated session at the OP, distinct from any RP session), enabling SSO: a second RP's /authorize with an existing IdP session skips re-login. Persists consent per (sub, client, scope-set) so a returning user isn't re-prompted unless scope grows. Implements prompt (none→error if interaction needed, login→force re-auth, consent→force re-consent) and max_age (force re-auth if session older). Drives logout: RP-Initiated (/end_session with id_token_hint+post_logout_redirect_uri), front-channel (iframe-driven RP logout URLs), back-channel (signed logout token POSTed to RPs), and Session Management (/checksession iframe + session_state).

idp-security — The hardening layer that turns bearer tokens into sender-constrained ones and blocks the OAuth attack catalog. Implements DPoP (RFC 9449): verify the proof JWT (htu/htm match the request, jti unique via replay cache, signature over the client's ephemeral key), bind the issued token via cnf.jkt. Implements mTLS-bound tokens (RFC 8705): bind via cnf.x5t#S256 to the client-cert thumbprint. Wires the replay caches (jti/nonce/code/user_code), enforces mix-up mitigation (the iss response param), CSRF protection on browser-facing forms, and rate-limit policy (#39) against brute force / credential stuffing on /token, /authorize, /login.

idp-audit — The observability and forensics layer. Emits a structured, append-only audit log for every security-relevant event (code issued, token issued/refreshed/revoked, consent granted/withdrawn, login success/failure, key rotated, client registered), with correlation IDs that thread a single flow from /authorize to /token. Exposes token-issuance and error-rate metrics, anomaly hooks (refresh-reuse spike, redirect-mismatch spike, signature-failure spike), and tracing spans (#132). Never logs tokens, codes, or secrets in cleartext — only hashed/truncated identifiers (I11).

idp-core — The shared vocabulary that prevents drift. Defines the newtypes (ClientId, Sub, Jti, Kid, Cnf, Scope, ScopeSet), the closed enums (GrantType, ResponseType, TokenType, SubjectType, ClientAuthMethod, CodeChallengeMethod), the canonical error taxonomy (the RFC 6749 sec. 5.2 codes + OIDC error codes), the Clock/skew model (bounded ±60 s), and IdpConfig. Every other crate speaks these types, so an endpoint, a token, and a log entry all name the same client_id and the same error the same way.

idpd — The deployable artifact. Composes every crate into one server, loads IdpConfig, binds TLS, registers all routes, and serves; on the admin side it exposes a CLI for client CRUD, key rotation, token introspection, and consent revocation against the store. Handles graceful shutdown (drain in-flight requests, flush audit log). It is the only binary; everything else is a library.

8.4 Refresh-Token Rotation With Reuse Detection (state machine)

                refresh grant (present RT_n)
   [Active RT_n] ---------------------------> validate: RT_n is current head of family F?
        |                                          |
        |                              yes          | no (RT_n already rotated / unknown)
        |                                           v
        v                                   [REUSE DETECTED]
   issue RT_{n+1}, mark RT_n ROTATED,        revoke ENTIRE family F (all RTs + derived ATs),
   set head=RT_{n+1}; return new AT+RT       audit security event (P7,I9), respond invalid_grant
        |
        v
   [Active RT_{n+1}]   (grace window: a 2nd presentation of RT_n within Δt may be a network
                        retry → return same RT_{n+1} idempotently; beyond Δt → REUSE DETECTED)

  Absolute expiry (e.g. 30d from family origin) and idle/sliding expiry (e.g. 8h since last use)
  both terminate the family → [Expired] → invalid_grant. offline_access scope gates RT issuance.

8.5 JWKS Key-Rotation Timeline

 t0          t1                t2                         t3                t4
  |  K1 only  |  K1 + K2 (pub)  |  K1(verify) + K2(sign)   |  K2 only        |
  |           | INTRODUCE K2    | ACTIVATE K2 (sign new)   | RETIRE K1       |
  |           | JWKS=[K1,K2]    | JWKS=[K1,K2]             | JWKS=[K2]       |
  |  sign:K1  | sign:K1         | sign:K2                  | sign:K2         |
  |  verify:K1| verify:K1,K2    | verify:K1,K2             | verify:K2       |
  +-----------+-----------------+--------------------------+-----------------+
              ^ K2 published before use      ^ overlap window ≥ max token TTL ^
                (clients refresh JWKS,         (all K1-signed tokens expire     RETIRE only
                 cache by kid)                  before K1 removed) (I8)         after overlap

Rule (I8): retire(K1) only after now > activate(K2) + max_token_ttl. kid distinguishes keys; clients select the verification key by the token's kid header.
