Back-of-Envelope Capacity Model

The numbers an engineer computes before designing, each derived from the System Constraints (§4.1) with the formula shown. Round numbers; the point is the order of magnitude and the binding resource.

  1. Single-replica issuance ceiling (EdDSA). §4.1 targets ≥ 2,000 issuances/s (EdDSA). If /token p50 ≈ 15 ms is dominated by sign + one store write, then per core ≈ 1000 ms / 15 ms ≈ 66 issuances/s/core; to hit 2,000/s ⇒ 2000 / 66 ≈ 30 busy cores, i.e. the EdDSA target assumes a many-core box or that sign is well under 15 ms (EdDSA sign ≈ 50–80 µs, so sign is not the bottleneck — the store write is). Binding resource: store write latency, not crypto.
  2. Single-replica issuance ceiling (RS256). §4.1 targets ≥ 800/s (RS256). RS256 sign (2048-bit) ≈ 1–2 ms vs EdDSA ≈ 0.06 ms ⇒ ~20–30× costlier. 2000/s (EdDSA) ÷ ~2.5 ≈ 800/s — consistent with the RS256 target. Formula: throughput_RS256 ≈ throughput_EdDSA × (t_sign_EdDSA / t_sign_RS256). This is why ADR-7 prefers EdDSA.
  3. Token-endpoint bandwidth. A token response (access JWT + id_token + refresh + JSON envelope) ≈ 2 KB. At 2,000 issuances/s ⇒ 2 KB × 2000 = 4 MB/s ≈ 32 Mbit/s egress per replica — trivial; bandwidth is never the constraint for issuance (it can be for JWKS under cache miss — see #7).
  4. Replay-cache size for DPoP jti. §4.1: replay cache bounded by Σ(active token TTLs × rate). DPoP jti must be remembered for the proof freshness window (≈ 60 s, the skew bound I15). At, say, 2,000 proofs/s × 60 s = 120,000 live jtis; at ~64 B/entry ⇒ 120,000 × 64 B ≈ 7.7 MB. Formula: cache_entries = rate × window. Small — fits in memory; the concern is contention, not size (MM9, Phase 11).
  5. Authorization-code table working set. Codes live ≤ 60 s, single-use (§4.1, I1). At an interactive login rate of, say, 200 codes/s ⇒ 200 × 60 = 12,000 live codes at any instant; at ~512 B/record (bindings) ⇒ ≈ 6 MB. The code table is tiny and GC-dominated — sized by rate × 60 s, not by total logins.
  6. Refresh-family table growth. Refresh families persist for the absolute lifetime (§4.1: ≈ 30 d). With 100,000 daily active sessions each holding one family ⇒ over 30 d ≈ 100,000 × 30 = 3,000,000 live families; at ~256 B/row ⇒ ≈ 770 MB before GC. Formula: families ≈ DAU × abs_lifetime_days. This — not the code table — is the store's real footprint, and why partitioning/GC by expiry matters (Scalability Analysis).
  7. JWKS request load + cache payoff. Every resource server validating opaque-vs-JWT differs: JWT-validating RSes fetch /jwks.json and cache by kid. If 10,000 RS instances refresh JWKS every 10 min ⇒ 10,000 / 600 s ≈ 17 req/s — but a cache-miss storm at rotation (all refresh at once) could spike to thousands/s. §4.1 caps /jwks.json p99 < 5 ms via ETag + precompute; the ETag/CDN is what makes rotation safe at fleet scale (M4).
  8. Memory ceiling sanity. Live working set ≈ code table (#5, ~6 MB) + DPoP cache (#4, ~8 MB) + hot client cache + key set (a handful of KB). The durable refresh-family table (#6, ~770 MB) lives in Postgres, not the replica. So an idpd replica's RSS is dominated by tokio + connection pools + caches — comfortably within a small container; the database, not the replica, holds the state mass.
  9. Connection/FD budget. §4.1: FD budget bounded by connection pool + store pool. With H2 connection reuse, inbound FDs ≈ active client connections; outbound ≈ store pool size (e.g. 32–64) + Redis pool. Formula: FD ≈ inbound_conns + store_pool + replay_pool. Backpressure on pool exhaustion (§4.1) is the lever, not raising ulimit blindly.
  10. Startup budget. §4.1: startup < 2 s = key load (read N keys from store, ~ms) + store connect (pool warm, ~100s ms) + route registration (~ms). Store connection latency dominates startup, so a slow/cold database, not key generation, is the startup risk.
  11. Logout fan-out cost. §4.1 / Scalability: back-channel logout = N RP POSTs per logout. For a user with sessions at 20 RPs, one logout ⇒ 20 signed-JWT POSTs (each a sign ≈ 0.06 ms EdDSA + a network RTT). Formula: logout_work = sessions_per_user × (sign + RTT); bounded by async dispatch + per-RP timeout, so a slow RP cannot stall logout (Phase 10).
  12. Error-budget arithmetic (99.9% issuance). §4.1 availability 99.9% ⇒ 0.1% × 30 d ≈ 43 min/month of allowed issuance failure. At 2,000 issuances/s that budget is 2000 × 60 × 43 ≈ 5.2 million failed issuances/month before the SLO burns — which reframes "a brief store blip" as a quantifiable budget spend, gating the alerting in Phase 12 (M10–M12).
