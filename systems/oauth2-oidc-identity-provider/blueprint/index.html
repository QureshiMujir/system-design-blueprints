406 — OAuth2 / OIDC Identity Provider from Scratch

Project Name: OAuth2 / OIDC Identity Provider from Scratch

Status: specification — locked

1. Goal

1.1 Precise Engineering Scope

Build a self-contained, from-scratch OAuth 2.0 Authorization Server (AS) + OpenID Connect 1.0 Identity Provider (OP) in Rust — the server side that issues tokens, not the client/relying-party side that consumes them (the explicit contrast with project #49 Auth System, which builds the RP/consumer JWT+OAuth flow). The system implements the full issuance stack bottom-up: a TLS-terminated HTTP layer with a fixed endpoint surface (/authorize, /token, /userinfo, /introspect, /revoke, /jwks.json, /.well-known/openid-configuration, /.well-known/oauth-authorization-server, /register, /device_authorization, /par, /end_session); a client registry (confidential + public, static + dynamic RFC 7591/7592, exact-match redirect URIs, client authn via client_secret_basic/client_secret_post/private_key_jwt/tls_client_auth); a JOSE stack (JWS sign/verify, JWK/JWKS, JWA alg pinning) over hand-driven crypto (RS256 / ES256 / EdDSA); signing-key lifecycle with kid assignment, JWKS publication, and a rotation state machine that never breaks in-flight token validation; the authorization-code grant with mandatory PKCE (RFC 7636 S256), state, nonce, end-user login, IdP session establishment, and single-use, ≤60 s, tightly-bound authorization codes; the token endpoint with code exchange, PKCE verification, client authentication, and access-token issuance (JWT per RFC 9068 or opaque + introspection); OIDC Core id_token issuance (iss/sub/aud/exp/iat/auth_time/nonce/at_hash/c_hash), scopes (openid profile email address phone offline_access), and /userinfo; refresh-token rotation with reuse detection (replay of a rotated token revokes the whole family); consent (scope/claims screen, persistence, prompt/max_age); introspection + revocation (RFC 7662 / 7009); additional grants (client_credentials, device authorization RFC 8628, PAR RFC 9126, token exchange RFC 8693 sketched); sessions / SSO / logout (RP-Initiated, front-channel, back-channel, Session Management); and sender-constrained tokens (DPoP RFC 9449, mTLS-bound RFC 8705) plus the OAuth 2.0 Security BCP / OAuth 2.1 hardening set (mix-up mitigation via iss RFC 9207, replay defense, CSRF).

The contract is standards-conformant issuance: every token the OP mints validates under the OpenID Connect Core + OAuth 2.0 specifications and against the published JWKS, and every flow passes the relevant OpenID Connect conformance profile. Implicit and ROPC grants are explicitly deprecated (OAuth 2.1) and not shipped. The system is educational and NOT a hosted, audited production IdP — it terminates real TLS and implements real flows, but operational PKI, HSM-backed keys, and a hardened deployment are reference-grade and cross-linked, not productionized.

1.3 Non-Goals

  • No implicit grant (response_type=token) and no ROPC (password grant) — deprecated per OAuth 2.1 / RFC 9700; documented refusal with rationale (§21).
  • No HSM/KMS-backed signing or FIPS key custody — software keys only; vault/KMS integration is PhaseDeferred("§14") (cross-link #168).
  • No CA / PKI issuance for tls_client_auth/mTLS — the OP consumes client certs but does not run a CA; PhaseDeferred("§23") (cross-link #234).
  • No encrypted (JWE) id_tokens / request objects as a shipped path — JWE is sketched only; PhaseDeferred("§17").
  • No external IdP federation / social login / brokering — single local OP; PhaseDeferred("§22").
  • No full token-exchange (RFC 8693) delegation/impersonation matrix — sketched; PhaseDeferred("§21").
  • No multi-region active-active token replication — single-region store; horizontal read replicas only (Scalability Analysis).
  • No production rate-limiter / WAF / bot-defense — hooks + reference limiter only (cross-link #39); PhaseDeferred("§23").
  • No UI framework / SPA for login/consent — server-rendered minimal HTML forms; theming out of scope.

1.4 Deployment Model

  • Single server binary idpd — composes all crates, binds TLS, serves the full endpoint surface; configured by a typed IdpConfig (issuer URL, key dir, store DSN, token TTLs, allowed algs, feature flags).
  • Library crates — each subsystem (idp-jose, idp-keys, idp-token, …) is a separately testable crate; embedders can build a custom OP.
  • Pluggable store — idp-store exposes traits backed by an in-memory impl (tests/dev) and a Postgres impl (durable); the same code path, different backend.
  • Stateless horizontal scaling — multiple idpd replicas behind a load balancer share the store; signing keys distributed read-only; replay caches are shared (Redis-class) or store-backed.
  • Admin CLI (idpd subcommands) — client create|list|rotate-secret, key rotate|list, token introspect, consent revoke, serve. Single-process operations against the store.

1.6 Phase 0 Deliverable — Locked Crates

Public API signatures locked before implementation. Sixteen crates under a Cargo workspace:

  1. idp-core — shared vocabulary: newtypes (ClientId, Sub, Jti, Kid, Cnf, Scope, ScopeSet), enums (GrantType, ResponseType, TokenType, SubjectType, ClientAuthMethod, CodeChallengeMethod), Clock/Instant skew model, IdpConfig, the canonical OAuthError/OidcError taxonomy (RFC 6749 sec. 5.2 codes).
  2. idp-crypto — primitive wrappers: RSA (RS256, PKCS#1 v1.5 / PSS), ECDSA P-256 (ES256), Ed25519 (EdDSA), SHA-256/384/512 + SHA-3, HKDF, CSPRNG token entropy, ct_eq constant-time compare, PKCE S256 transform, password verifier hook (Argon2/bcrypt — cross-link #91).
  3. idp-jose — JOSE stack: JWS sign/verify with alg pinning (no alg:none, no alg confusion), JWT claim-set build/validate, JWK + JWKS encode/decode, kid header binding, base64url, at_hash/c_hash helpers, JWE (sketch).
  4. idp-keys — signing-key lifecycle: keypair generation per alg, kid assignment (thumbprint RFC 7638), JWKS publication, rotation state machine (introduce → dual-publish → sign-with-new → retire), key store, active/next/retiring selection.
  5. idp-store — persistence traits + backends (in-mem, Postgres): ClientStore, KeyStore, CodeStore, TokenStore (incl. refresh families), SessionStore, ConsentStore, ReplayCache (jti/nonce/code/user_code), TTL/GC.
  6. idp-http — axum/hyper server: TLS 1.3 termination, router, request parsing/validation, security headers, CORS policy, error rendering (OAuth JSON + redirect-error), middleware (rate-limit hook #39, DPoP/mTLS extraction, trace span #132).
  7. idp-discovery — /.well-known/openid-configuration (OIDC Discovery 1.0) + /.well-known/oauth-authorization-server (RFC 8414) metadata documents; advertises endpoints, algs, grant/response types, PKCE methods.
  8. idp-client — client registry: confidential/public, static + dynamic registration (RFC 7591) + management (RFC 7592), exact-match redirect URIs, client authn dispatch (4 methods), metadata validation, secret hashing.
  9. idp-token — token model + issuance + stores: access (JWT RFC 9068 at+jwt / opaque), refresh (+ rotation/reuse-detection family), id_token, authorization code; TTLs, binding (client/redirect/challenge/scope/nonce), cnf claim.
  10. idp-authz — /authorize: parameter validation, response_type dispatch, PKCE capture, state/nonce, login binding, consent gating, single-use code issuance, redirect-error encoding, iss response param (RFC 9207).
  11. idp-grant — /token dispatch + grant handlers (authorization_code, refresh_token, client_credentials, device, PAR-consume, token-exchange sketch) + /introspect + /revoke; RFC 6749 sec. 5.2 error responses.
  12. idp-oidc — OIDC Core: id_token assembly + claims, scope→claims mapping, /userinfo endpoint, auth_time/acr/amr, hybrid response_type (code id_token) sketch, pairwise subject derivation.
  13. idp-session — IdP session lifecycle, SSO across RPs, consent persistence per (sub, client), prompt=none|login|consent, max_age, RP-Initiated Logout (/end_session), front-channel + back-channel logout, Session Management (/checksession).
  14. idp-security — sender-constrained tokens (DPoP RFC 9449, mTLS-bound RFC 8705), mix-up mitigation (iss), replay caches wiring, CSRF, rate-limit policy, brute-force/credential-stuffing defenses (cross-link #39).
  15. idp-audit — structured audit logging (issue/refresh/revoke/consent/login events), token-issuance + error-rate metrics, anomaly hooks, tracing (cross-link #132), key-rotation events.
  16. idpd — server binary (compose + serve) + admin CLI (client/key/token/consent subcommands), config loading, graceful shutdown.

1.10 Language Selection — Rust

An IdP's correctness budget lives in three places: exhaustive protocol case analysis (every grant × client-type × auth-method × error-code combination, where a missed branch is a silent auth bypass), memory-safe parsing of fully untrusted input (every /authorize query, JWT header, JSON body, and client cert arrives from an attacker), and constant-time secret handling (client secrets, codes, tokens, PKCE verifiers). Rust delivers all three: exhaustive enum + match makes GrantType/ResponseType/ClientAuthMethod/error-code completeness a compile-time guarantee (no catch-all silently accepting a deprecated grant); the borrow checker + no-unsafe policy in parsers eliminates the buffer-overflow/UAF class that plagues C-based JOSE stacks; subtle::ConstantTimeEq makes secret comparison first-class; and the crypto ecosystem (ring/RustCrypto rsa, p256, ed25519-dalek, sha2, aes-gcm, hkdf, argon2) plus axum/hyper/tokio give a production-grade async HTTP server with zero GC pauses. Go is rejected: weaker enum exhaustiveness (no sum types) makes the grant/error matrix error-prone, and interface{}-style JOSE handling invites alg-confusion bugs. Java (the Keycloak ecosystem) is rejected for GC tail latency on the token hot path and a heavier runtime; its reflection-driven JOSE libraries have repeatedly shipped alg-confusion CVEs. Consistency with #49 Auth System (Rust) and the crypto suite (#88/#89/#90/#91) means the RP and OP sides share JOSE/crypto primitives and a single mental model. All sixteen crates are Rust (2021 edition).

2. Why Build This

2.1 Unique Systems Knowledge Taught

  • Why an authorization code exists at all (front-channel redirect cannot safely carry a token) and why it must be single-use, short-lived, and bound to client_id + redirect_uri + code_challenge + scope + nonce — the central structural fact of the auth-code grant.
  • How PKCE defends the code against interception on public clients (and, under OAuth 2.1, all clients) by binding the code to a secret the attacker never sees, and how S256 (not plain) is the only safe method.
  • How JWKS + kid rotation lets an OP change signing keys without a flag day: the dual-publish overlap window keeps every in-flight token verifiable until it expires.
  • Why refresh-token rotation with reuse detection turns a stolen long-lived credential into a detectable event: replaying a rotated token reveals theft and revokes the entire family.
  • The precise difference between authentication (OIDC id_token, "who the user is") and authorization (OAuth access token, "what the client may do") — and why conflating them (using an id_token as an access token, or vice versa) is a classic break.
  • How sender-constrained tokens (DPoP cnf.jkt, mTLS cnf.x5t#S256) downgrade a bearer token from "anyone who holds it" to "only the holder of the bound key/cert" — and why bearer tokens are otherwise the soft underbelly of OAuth.

2.2 Historical and Architectural Significance

OAuth 2.0 (RFC 6749, 2012) replaced password-sharing and OAuth 1.0's request-signing with bearer tokens and a redirect-based delegation model; OpenID Connect (2014) layered authentication (id_token, /userinfo) on top. The following decade was a steady accretion of security fixes encoded as RFCs: PKCE (7636, 2015) after auth-code interception on mobile; AS metadata (8414) and dynamic registration (7591); device grant (8628) for input-constrained devices; JWT access tokens (9068) for interoperable resource servers; PAR (9126) and JAR to move parameters off the front channel; DPoP (9449) and mTLS (8705) for sender constraint; the mix-up iss parameter (9207); and the Security BCP (RFC 9700) plus OAuth 2.1 consolidating "implicit and ROPC are dead, PKCE is mandatory, redirect URIs are exact-match." This project reconstructs that lineage as working code, making each fix legible as a response to a concrete attack. OIDC underpins essentially all modern federated login (Google, Microsoft, Okta, Auth0, Keycloak); building the OP side demystifies "Sign in with…" into endpoints, codes, signed claims, and key rotation.

2.3 Engineering Muscles Developed

  • Designing a protocol surface as state machines over untrusted HTTP input with exhaustive validation and fail-closed defaults.
  • Reasoning about front-channel vs back-channel trust: what may traverse a browser redirect (codes, never tokens) vs what stays server-to-server.
  • Operating a signing-key lifecycle as a live, zero-downtime rotation rather than a config edit.
  • Building transactional single-use semantics (code/refresh consumption) correct under concurrency and replay.
  • Encoding every security control as a testable invariant and a security-regression fixture (PKCE downgrade, code injection, alg confusion).
  • Treating audit logging as a first-class, tamper-evident product feature, not an afterthought.

2.4 Production Engineering Concepts Exercised

  • Zero-downtime key rotation with a published overlap window and explicit retirement.
  • Idempotent, atomic consumption of one-time credentials under concurrent replicas.
  • Bounded replay caches (jti, nonce, code, user_code) sized to token lifetimes, with GC.
  • Fail-closed error taxonomy: every rejection maps to a precise RFC 6749 sec. 5.2 code, never a generic 500 that leaks state.
  • Secret hygiene: hash client secrets, never log tokens, constant-time compare, short TTLs.
  • Conformance as a release gate: the OP is only "done" when it passes OIDC profiles and interops with real RP libraries.

2.6 Calibration Value

After this project, "Sign in with X" becomes a transparent pipeline: RP redirects the user to /authorize → OP authenticates + gets consent → OP issues a bound, single-use code → RP exchanges it at /token with its PKCE verifier + client auth → OP issues a signed id_token (who) + access token (what) + refresh token → RP calls /userinfo, validates the id_token against /jwks.json. The engineer can explain why a code (not a token) crosses the browser, why PKCE binds the code to the RP, why the id_token nonce must echo the request, how key rotation keeps old tokens valid, why refresh rotation detects theft, and can debug any failure by reading the audit log and tracing one state/jti across the flow. It is the definitive complement to #49: having built both sides, the engineer owns the entire OAuth/OIDC trust triangle.

2.7 What Mastery Looks Like

  • Design a front-channel/back-channel split from first principles — know precisely what may cross a browser redirect (a single-use bound code, never a token) and why, and encode it as exact-match redirect validation + code binding (Phase 3, Phase 4).
  • Operate a signing-key lifecycle as a live zero-downtime rotation, reasoning about the dual-publish overlap window vs. max token TTL so no in-flight token loses its verification key (Phase 2).
  • Implement atomic single-use consumption correct under concurrent replicas — a code consumed exactly once, a refresh token rotated exactly once — and prove it with interleaving property tests (Phase 4, Phase 6).
  • Build refresh-token rotation with reuse detection that turns a stolen long-lived credential into a detectable, contained event (family revocation) rather than a permanent silent compromise (Phase 6).
  • Enforce algorithm discipline in a JOSE stack — pin the verify alg to the resolved key, refuse alg:none and RS↔HS confusion — and explain each as a defense against a specific forgery CVE class (Phase 2).
  • Downgrade bearer tokens to sender-constrained ones (DPoP cnf.jkt, mTLS cnf.x5t#S256) and articulate exactly which theft scenarios that defeats and which it does not (Phase 11).
  • Treat conformance + interop as the definition of "done" — drive the system to pass external OIDC profiles and interoperate with real RP libraries and reference OPs, not just self-tests (Phase 13).
  • Make the system investigable — every security-relevant event audited with a correlation id threading /authorize→/token, with anomaly detectors on the theft/forgery signals (Phase 12).

3.2 Subsystem Descriptions

idp-http — The front door and the only code that touches the network. Terminates TLS 1.3 (via rustls), runs the axum/hyper router that maps the fixed endpoint surface to handlers, parses and validates every request (query/form/JSON/headers) before any handler sees it, and renders both error shapes the specs demand: the OAuth JSON error body ({"error":"invalid_request",...}) and the front-channel redirect-error (?error=...&state=...). Middleware layers attach a rate-limit decision (#39), extract DPoP proofs and mTLS client-cert thumbprints for downstream binding, open a trace span (#132) carrying a correlation ID, and enforce body/URL size limits (anti-DoS). It is the trust boundary: everything below assumes inputs are syntactically validated but semantically untrusted.

idp-discovery — Publishes the two metadata documents that let clients self-configure: /.well-known/openid-configuration (OIDC Discovery 1.0) and /.well-known/oauth-authorization-server (RFC 8414). Each advertises the issuer, every endpoint URL, supported response_types/grant_types/scopes/claims, signing algs (id_token_signing_alg_values_supported), code_challenge_methods_supported (S256), token-endpoint auth methods, and DPoP/PAR/device capabilities. The documents are derived from live config + the published JWKS so they never drift from actual behavior — a discovery lie is a conformance failure and a security risk (clients trust it).

idp-client — The client registry and the first line of redirect defense. Stores confidential and public client metadata (redirect URIs, grant/response types, scopes, auth method, jwks/jwks_uri for private_key_jwt, subject type, sector identifier). Implements exact-match redirect-URI comparison (full-string, including path/query, no wildcards or substring matches — I3). Supports static registration (config/admin CLI) and dynamic registration (RFC 7591 /register) + management (RFC 7592). Dispatches client authentication at the token endpoint across four methods (client_secret_basic, client_secret_post, private_key_jwt, tls_client_auth), comparing secrets in constant time and verifying private_key_jwt assertions against the client's JWKS.

idp-crypto — The cryptographic floor. Wraps vetted primitives — RSA (RS256: PKCS#1 v1.5 + PSS), ECDSA P-256 (ES256), Ed25519 (EdDSA), SHA-256/384/512 and SHA-3, HKDF, a CSPRNG for token/code entropy, ct_eq constant-time comparison, the PKCE S256 transform (BASE64URL(SHA256(verifier))), and a password-verifier hook (Argon2/bcrypt, cross-link #91). No protocol logic; it is the single audited surface for "which curve, which padding, which hash," and it never rolls its own primitive (RSA/EC/Ed via RustCrypto/ring). Reused conceptually from #88/#89/#90/#91.

idp-jose — The JOSE engine: JWS signing and verification, JWT claim-set construction and validation, JWK/JWKS encoding/decoding, and kid header binding. Its single most important job is algorithm discipline (I5): it rejects alg:none, pins the verification algorithm to the key's declared alg (never to the attacker-controlled JWT header), and refuses RS↔HS alg-confusion. It computes at_hash/c_hash (left-half SHA-256 of the token/code), and provides base64url codecs. JWE is sketched only. Every token format in the system serializes through here, so a JOSE bug is a system-wide break.

idp-keys — The signing-key lifecycle owner. Generates keypairs per algorithm, assigns each a stable kid (JWK thumbprint, RFC 7638), publishes the public halves as JWKS, and runs the rotation state machine: a new key is introduced (published in JWKS but not yet signing), then becomes active (signs new tokens) while the prior key keeps verifying until all tokens it signed have expired, then is retired (removed from JWKS). The overlap window (≥ max token TTL) is the invariant that makes rotation non-breaking (I8). Selects the active signing key and resolves any token's kid to a verification key.

idp-store — The persistence boundary. Defines traits — ClientStore, KeyStore, CodeStore, TokenStore (with refresh-family operations), SessionStore, ConsentStore, and ReplayCache (jti/nonce/code/user_code) — and provides an in-memory backend (tests/dev) and a Postgres backend (durable). It owns the two hardest semantics in the system: atomic single-use consumption (a code/refresh token is consumed exactly once even under concurrent replicas, via a conditional update / DELETE … RETURNING) and TTL-bounded GC of expired records and replay entries. Everything stateful flows through here.

idp-token — The token model and issuance core. Builds and issues all four token kinds: authorization codes (opaque, high-entropy, single-use, ≤60 s, bound to client_id+redirect_uri+code_challenge+scope+nonce), access tokens (JWT per RFC 9068 with typ:at+jwt, or opaque + introspection), id_tokens (JWS per OIDC), and refresh tokens (opaque, tracked in a family for rotation/reuse detection). Stamps TTLs, attaches the cnf confirmation claim for sender-constrained tokens, and enforces that scope granted ⊆ requested ⊆ registered (I14). Signs via idp-jose/idp-keys, persists via idp-store.

idp-authz — The /authorize endpoint and the start of every interactive flow. Validates parameters (client_id, redirect_uri, response_type, scope, state, nonce, code_challenge+code_challenge_method), resolves the client and exact-matches the redirect URI before doing anything else, captures and stores the PKCE challenge, triggers end-user login (via idp-session) and consent (via idp-session) as needed, then issues a single-use authorization code (via idp-token) and redirects back with code, state, and the iss response parameter (RFC 9207, mix-up mitigation). All errors after redirect-URI validation are returned as redirect errors; errors before it are direct (never redirect to an unvalidated URI).

idp-grant — The /token endpoint dispatcher plus /introspect and /revoke. Authenticates the client (via idp-client), dispatches on grant_type to handlers: authorization_code (consume code atomically, verify PKCE, re-check all bindings, issue tokens), refresh_token (rotate + reuse-detect), client_credentials, device-code polling, PAR consumption, and a token-exchange sketch. Emits RFC 6749 sec. 5.2 error responses (invalid_grant, invalid_client, unauthorized_client, unsupported_grant_type, invalid_scope). Introspection (RFC 7662) returns the active flag + claims to an authenticated caller; revocation (RFC 7009) invalidates a token (and, for a refresh token, its family).

idp-oidc — The OpenID Connect Core layer. Assembles the id_token (claims iss, sub, aud, exp, iat, auth_time, nonce, at_hash, c_hash, acr, amr), maps requested scopes to standard claims (profile→name/picture/…, email→email+verified, address, phone), serves /userinfo (bearer access token → claims), derives the subject identifier per subject_type (public or pairwise via sector identifier), and sketches the hybrid response_type=code id_token (front-channel id_token + c_hash binding the code). It depends on idp-token/idp-jose for signing and on idp-session for auth_time/acr/amr.

idp-session — The identity and consent state machine. Owns the IdP session (the user's authenticated session at the OP, distinct from any RP session), enabling SSO: a second RP's /authorize with an existing IdP session skips re-login. Persists consent per (sub, client, scope-set) so a returning user isn't re-prompted unless scope grows. Implements prompt (none→error if interaction needed, login→force re-auth, consent→force re-consent) and max_age (force re-auth if session older). Drives logout: RP-Initiated (/end_session with id_token_hint+post_logout_redirect_uri), front-channel (iframe-driven RP logout URLs), back-channel (signed logout token POSTed to RPs), and Session Management (/checksession iframe + session_state).

idp-security — The hardening layer that turns bearer tokens into sender-constrained ones and blocks the OAuth attack catalog. Implements DPoP (RFC 9449): verify the proof JWT (htu/htm match the request, jti unique via replay cache, signature over the client's ephemeral key), bind the issued token via cnf.jkt. Implements mTLS-bound tokens (RFC 8705): bind via cnf.x5t#S256 to the client-cert thumbprint. Wires the replay caches (jti/nonce/code/user_code), enforces mix-up mitigation (the iss response param), CSRF protection on browser-facing forms, and rate-limit policy (#39) against brute force / credential stuffing on /token, /authorize, /login.

idp-audit — The observability and forensics layer. Emits a structured, append-only audit log for every security-relevant event (code issued, token issued/refreshed/revoked, consent granted/withdrawn, login success/failure, key rotated, client registered), with correlation IDs that thread a single flow from /authorize to /token. Exposes token-issuance and error-rate metrics, anomaly hooks (refresh-reuse spike, redirect-mismatch spike, signature-failure spike), and tracing spans (#132). Never logs tokens, codes, or secrets in cleartext — only hashed/truncated identifiers (I11).

idp-core — The shared vocabulary that prevents drift. Defines the newtypes (ClientId, Sub, Jti, Kid, Cnf, Scope, ScopeSet), the closed enums (GrantType, ResponseType, TokenType, SubjectType, ClientAuthMethod, CodeChallengeMethod), the canonical error taxonomy (the RFC 6749 sec. 5.2 codes + OIDC error codes), the Clock/skew model (bounded ±60 s), and IdpConfig. Every other crate speaks these types, so an endpoint, a token, and a log entry all name the same client_id and the same error the same way.

idpd — The deployable artifact. Composes every crate into one server, loads IdpConfig, binds TLS, registers all routes, and serves; on the admin side it exposes a CLI for client CRUD, key rotation, token introspection, and consent revocation against the store. Handles graceful shutdown (drain in-flight requests, flush audit log). It is the only binary; everything else is a library.

6. Design Principles

P1. Tokens Are Bearer Capabilities — Treat Every Token As A Live Secret

A token (access, refresh, code) is a credential: anyone holding it wields its authority until expiry/revocation. Therefore: short TTLs, high entropy (≥256-bit), never logged in cleartext (I11), transmitted only over TLS, and (for high value) sender-constrained (P13). Tradeoff: short TTLs mean more /token traffic (refresh churn). Violation: logging an access token, or a 24-hour code, converts a log leak or a single interception into full account takeover.

P2. Exact Redirect-URI Matching — No Wildcards, No Substrings, No Normalization Tricks

The redirect_uri is compared by full-string equality against the client's registered set before any code/token is issued (I3). No prefix/suffix/wildcard/port-relaxation. Tradeoff: clients must register every exact URI (operational friction). Violation: substring or wildcard matching is the classic open-redirect → authorization-code exfiltration; an attacker registers https://evil.example/cb against a sloppy *.example rule and steals codes.

P3. PKCE Is Mandatory For Every Authorization-Code Flow

code_challenge+code_challenge_method=S256 is required at /authorize and verified at /token for all clients (public and confidential), per OAuth 2.1 (I4). plain is rejected unless an explicit legacy flag is set. Tradeoff: marginally more client work. Violation: without PKCE, an intercepted code (mobile redirect, logs, referer) is directly redeemable; PKCE binds the code to a verifier the attacker never sees.

P4. Authorization Codes Are Single-Use, Short-Lived, And Tightly Bound

A code is consumed exactly once (I1), lives ≤60 s, and is bound to client_id + redirect_uri + code_challenge + scope + nonce; /token re-checks every binding (I2). Replay of a consumed code revokes any tokens derived from it. Tradeoff: requires atomic consumption under concurrency. Violation: a reusable or unbound code enables code injection (inject a victim's code into the attacker's session) and replay.

P5. Sign Everything Verifiable; Pin The Algorithm To The Key, Never The Header

Every id_token and JWT access token is JWS-signed; verification uses the algorithm declared by the resolved key (via kid), never the JWT's own alg header; alg:none is always rejected; RS↔HS confusion is impossible (I5). Tradeoff: stricter than permissive libraries. Violation: trusting the header alg enables alg:none forgery and RS256→HS256 confusion (sign with the public key as an HMAC secret) — total id_token forgery.

P6. Key Rotation Never Breaks In-Flight Validation

Rotation is a state machine (introduce → dual-publish → sign-with-new → retire) with an overlap window ≥ max token TTL; the old key keeps verifying until its tokens expire (I8). Tradeoff: JWKS temporarily lists ≥2 keys; clients must handle multiple kids. Violation: removing a key while tokens it signed are still valid causes mass invalid_token 401 storms across all resource servers.

P7. Refresh-Token Rotation With Reuse Detection

Every refresh use issues a new refresh token and invalidates the old; the token is tracked in a family; presenting an already-rotated (invalidated) refresh token revokes the entire family and audits the event (I9). Tradeoff: state per family; legitimate races (network retry) can trip detection — mitigated by a short grace window. Violation: non-rotating refresh tokens make a single theft permanent and undetectable.

P8. Consent Is Explicit, Scoped, Persisted, And Auditable

The user explicitly grants a specific scope set to a specific client; consent is stored per (sub, client, scope-set) and re-prompted only when scope grows or prompt=consent (P8/I20). Tradeoff: a consent store + UI. Violation: silent or over-broad consent grants clients more authority than the user agreed to — a privacy and audit failure.

P9. Fail Closed — Reject On Ambiguity, Never Default-Allow

Any unrecognized parameter combination, missing required field, unverifiable signature, or ambiguous state results in a precise typed rejection, never a permissive fallback. Tradeoff: stricter clients break loudly (good). Violation: a default-allow branch (e.g. "if scope missing, grant all") is a privilege-escalation vector.

P10. Constant-Time Secret Comparison; No Secret-Dependent Branches Or Logs

Client secrets, codes, tokens, and PKCE verifiers are compared with ct_eq; secrets are stored hashed where applicable; no log line or error message varies on a secret's value (I10, I11). Tradeoff: no fast-path early-exit compares. Violation: a == on a secret is a timing oracle; an error that says "wrong secret" vs "unknown client" is a user-enumeration oracle.

P11. State Is Server-Authoritative; Clients Are Untrusted

The OP never trusts a client-supplied value as ground truth: scopes are re-validated against registration, redirect_uri against the registry, code bindings against the server-side code record. Tradeoff: more server-side state. Violation: trusting a client-asserted scope or subject lets a client escalate its own grant.

P12. Every Security-Relevant Event Is Audited With A Correlation ID

Code/token issuance, refresh, revocation, consent, login (success+failure), key rotation, and client registration emit structured audit events threaded by a correlation ID across /authorize→/token (I12-adjacent). Tradeoff: audit-write on the hot path (async-buffered). Violation: without audit, theft/abuse is invisible and incidents are un-investigable.

P13. Sender-Constrain High-Value Tokens Where Possible

Access/refresh tokens may be bound to a key (DPoP cnf.jkt) or cert (mTLS cnf.x5t#S256), so a stolen token is useless without the private key/cert (I17, I18). Tradeoff: clients must implement DPoP/mTLS; not all can. Violation: a pure-bearer high-value token, once stolen, is fully usable by the thief.

P14. Defense In Depth Against Replay

Multiple independent anti-replay controls: state (CSRF/binding), nonce (id_token replay), jti (DPoP/JWT replay), single-use code, single-use user_code — each with a bounded replay cache (I23). Tradeoff: several caches to size and GC. Violation: relying on a single control means one bypass is a full replay.

P15. Clock Discipline — Bounded Skew, Monotonic Issuance, Explicit Expiry

All time claims (exp/iat/nbf/auth_time) use a single Clock; validation tolerates ±60 s skew; exp > iat; issuance time is monotonic per key (I15). Tradeoff: rejects clients with badly-skewed clocks. Violation: unbounded skew tolerance lets long-expired tokens validate; zero tolerance breaks legitimate clients.

Invariant Enforcement Summary

I1/I2/I4 are enforced at the token endpoint by an atomic code consume (single-use) followed by a re-check of every binding and the PKCE verifier before any token is minted; replay of a consumed code triggers derived-token revocation. I3 is enforced at /authorize (and re-checked at /token) by full-string redirect comparison before issuance. I5/I6/I7/I15 are JOSE/keys invariants: alg pinned to the resolved key, alg:none refused, claim and expiry validation with bounded skew, kid resolution against the published JWKS. I8 is the rotation FSM's overlap-window guarantee. I9 is the refresh-family reuse-detection machine. I10/I11 are secret-hygiene invariants audited in CI (constant-time usage, no-token-in-logs scanner). I12/I14/I22 are server-authoritative round-trip and scope-subset checks plus the mix-up iss param. I16 gates introspection/revocation behind caller auth. I17/I18 are the DPoP/mTLS binding checks. I19/I20 are device-flow and consent state checks. I23 bounds every replay cache. The load-bearing set for "cannot forge or replay a token" is I1–I9 + I15 + I17/I18; the load-bearing set for "cannot steal a code/identity" is I2–I4 + I12 + I22.

8.4 Refresh-Token Rotation With Reuse Detection (state machine)

                refresh grant (present RT_n)
   [Active RT_n] ---------------------------> validate: RT_n is current head of family F?
        |                                          |
        |                              yes          | no (RT_n already rotated / unknown)
        |                                           v
        v                                   [REUSE DETECTED]
   issue RT_{n+1}, mark RT_n ROTATED,        revoke ENTIRE family F (all RTs + derived ATs),
   set head=RT_{n+1}; return new AT+RT       audit security event (P7,I9), respond invalid_grant
        |
        v
   [Active RT_{n+1}]   (grace window: a 2nd presentation of RT_n within Δt may be a network

  Absolute expiry (e.g. 30d from family origin) and idle/sliding expiry (e.g. 8h since last use)
  both terminate the family → [Expired] → invalid_grant. offline_access scope gates RT issuance.

12.1 Objectives

  • Cargo.toml workspace + idp-core (ids.rs/enums.rs/error.rs/clock.rs/config.rs/scope.rs, §11.1): lock the closed GrantType/ResponseType/ClientAuthMethod/OAuthError enums — exhaustive match makes the grant/error matrix compile-time-complete (ADR-1, P9); no alg:none/implicit/ROPC variants exist (P5, ADR-22).

  • http/headers.rs: Cache-Control: no-store on token responses (P1), Strict-Transport-Security, X-Content-Type-Options, frame policy; cors.rs: strict allowlist (no * for credentialed).
  • http/error_render.rs: OAuth JSON error ({error,error_description}) + front-channel redirect-error encoder; map OAuthError (sec. 5.2, ADR-24)→HTTP status + code; never redirect pre-validation (I3, P2).

  • discovery/oidc_config.rs + as_metadata.rs: build documents from IdpConfig + live JWKS URL (single source — no drift); advertise endpoints, S256 (I4), algs, grant/response types.

14. Phase 2 — Key management + JWKS

14.1 Objectives

Build idp-keys + idp-jose: signing keypair generation (RS256/ES256/EdDSA), kid assignment (JWK thumbprint RFC 7638), /jwks.json publication, and the rotation state machine (introduce → dual-publish → activate → retire) that never breaks in-flight validation (I8,P6). Lock alg discipline: no alg:none, alg pinned to key (I5,P5).

14.2 Detailed Implementation Steps

  • crypto/{rsa,ecdsa,eddsa}.rs: keygen + sign/verify for RS256 (v1.5/PSS), ES256 (P-256), EdDSA (Ed25519).
  • jose/jws.rs: compact JWS sign/verify; header carries alg+kid; verify resolves kid→key, uses the key's alg, rejects alg:none and alg≠key.alg (I5).
  • jose/jwk.rs+jwks.rs: encode public keys as JWK; jwks() document; jwk_thumbprint→kid.
  • keys/keygen.rs+kid.rs: generate per alg; assign thumbprint kid.
  • keys/rotation.rs: KeyState FSM; rotate(alg) introduces a new key (published, not signing), then activates (signs new), keeps old verifying; retire_expired(max_ttl,now) removes only after overlap (I8).
  • keys/select.rs: active_signer(); resolve(kid) for verification (I7).
  • keystore.rs: persist keys + states via KeyStore; load on startup.

14.3 Deliverable

14.4 Acceptance Criteria

  • Round-trip sign→verify for RS256/ES256/EdDSA; cross-alg token rejected (I5).
  • alg:none JWT rejected; JWT whose header alg differs from the resolved key's alg rejected (I5,P5).
  • During rotation, a token signed by the old key still verifies while JWKS lists both; after retire_expired past overlap, old kid no longer resolves and JWKS drops it (I8).
  • kid is a stable RFC 7638 thumbprint; present in every JWS header (I7).

14.6 Pitfalls

  • Verifying with the header's alg (not the key's) is the alg-confusion CVE class; pin to key (I5).
  • Reusing a kid across two distinct keys breaks resolution; thumbprint makes kid content-addressed (collision-free).
  • Retiring a key before its tokens expire causes 401 storms at resource servers (I8); retire must check now > activate + max_ttl.
  • RSA PKCS#1 v1.5 vs PSS mismatch between sign/verify silently fails; pin per key.

14.7 Performance Concerns

  • RS256 sign is the dominant /token cost (~ms); EdDSA is ~10–50× cheaper — prefer EdDSA where clients support it. JWKS serve is hot + static between rotations: precompute + ETag. Verification (ES256/EdDSA) is cheap; cache parsed JWKS by kid.

14.9 Failure Analysis

A JOSE/alg bug enables token forgery (catastrophic). Detection: alg-none/confusion fixtures + signature property tests + fuzz (jws_verify). Blast radius: every signed token system-wide. Containment: all signing/verify funnels through idp-jose; one audited surface. Forensics: rotation + sign events audited with kid.

14.10 Operational Notes

18. Phase 6 — Refresh tokens + rotation

18.1 Objectives

Build refresh-grant in idp-token/idp-grant: grant_type=refresh_token, rotation with reuse detection (replay of a rotated token revokes the whole family, I9,P7), sliding + absolute expiry, and the offline_access scope gate. The reuse-detection state machine (§8.4) is the security centerpiece.

18.2 Detailed Implementation Steps

  • token/family.rs: a refresh family = origin + chain of rotated tokens; FamilyId; head pointer; absolute + idle expiry timestamps.
  • grant/refresh_grant.rs: validate presented RT; TokenStore::rotate_refresh (I9) — if RT is the current head: issue new RT (new head), mark old ROTATED, issue fresh access token, update idle expiry; if RT is already ROTATED/unknown: reuse detected → revoke_family (all RTs + derived ATs) + audit security event + invalid_grant.
  • Grace window: a second presentation of the just-rotated RT within Δt (network retry) returns the same new RT idempotently (not reuse) (§8.10).
  • Expiry: enforce absolute cap (e.g. 30 d from origin) and idle/sliding (e.g. 8 h since last use); either → invalid_grant.
  • offline_access: only issue refresh tokens when granted (+ consent); confidential clients may get refresh without it per policy.
  • Down-scoping allowed on refresh (scope ⊆ original, I14); never up-scope.

18.3 Deliverable

A refresh token exchanges for a new access token + new refresh token (rotation); replaying an old refresh token revokes the family and is audited; expiry enforced; cargo test (refresh suite) green.

18.4 Acceptance Criteria

  • Each refresh use returns a new RT and invalidates the old (I9); old RT replay → family revoked + audited (P7).
  • Grace-window retry returns the same new RT idempotently (no false reuse).
  • Absolute + idle expiry both terminate the family (invalid_grant).
  • Refresh only issued when offline_access/policy permits; scope down-scoping honored (I14).

  • Non-atomic rotation races duplicate the head or miss reuse; rotation must be one atomic store op (I9).

Forensics: reuse events are high-signal audit records (likely theft) with family id + client + timestamps.

  • Re-enabling implicit "for compatibility" reopens token-in-URL leakage; keep refused (OAuth 2.1).

21.7 Performance Concerns

  • Device polling generates frequent /token hits; enforce interval, cheap pending response. PAR adds a store write + read but shrinks the front-channel URL (good for large requests/JAR). client_credentials is a single sign, no user lookup — fastest grant.

21.8 Edge Cases

  • Device code approved then polled after expiry (expired). User enters wrong user_code (retry + lockout). PAR request_uri reused (rejected). Token exchange with mismatched audience (sketch). client_credentials for a public client (rejected, I13).

21.9 Failure Analysis

Blast radius: device-flow clients / PAR users. Containment: interval/single-use enforced + audited. Forensics: audit device approvals + PAR consumption (P12).

22.1 Objectives

23. Phase 11 — Sender-constrained tokens + security hardening

23.1 Objectives

23.2 Detailed Implementation Steps

  • security/mtls_bind.rs: take the client-cert thumbprint (from idp-http mTLS extraction), bind cnf.x5t#S256 into the token (I18); verify on use.
  • security/mixup.rs: ensure the iss response param is always present (I22); document RP-side check.
  • security/replay_wiring.rs: wire ReplayCache for jti (DPoP, private_key_jwt), nonce (where one-time), single-use code/user_code (I23).

Threat Model

The OP is a high-value target: it mints credentials for every relying party and authenticates every user. The attack surface is (1) the front channel (browser redirects to/from /authorize, /end_session, /checksession — attacker can see/tamper URLs), (2) the back channel (/token, /introspect, /revoke, /par, /register, /device_authorization — attacker may be a malicious or compromised client), (3) untrusted token/JWT input (every JWS the OP verifies — client assertions, DPoP proofs, id_token_hint, logout tokens), (4) the user-credential surface (/login, device user_code), and (5) operator + supply chain (keys, secrets, dependencies). The core property: only the legitimate holder of a code/token/session can exercise its authority, and the OP can never be made to forge or mis-issue a token.

Backup / restore — durable store (clients, keys, families, consent, sessions) backed up; signing keys backed up (encrypted; vault-backed deferred #168). Restore: re-point replicas at restored store; verify JWKS + active key; replay caches rebuild (TTL-bounded). RPO=0 for committed tokens; RTO < 5 min.

Deployment topology — N stateless idpd replicas behind a TLS-terminating LB; shared store (Postgres primary + read replicas) + shared replay cache (Redis-class); keys distributed read-only to replicas; one replica leads scheduled rotation.

Canary / rolling upgrade / rollback — rolling replica replacement; canary one replica + watch issuance/error/latency; rollback = redeploy prior image (stateless). Schema migrations are additive + backward-compatible (expand/contract).

Migration / compatibility — discovery doc, token/claim formats, JWKS, and client/registration schema are the stable contracts; all versioned (see Compatibility Guarantees).

Testing Strategy

  • Unit — JWS sign/verify per alg, claim validation, PKCE transform, redirect exact-match, code binding, scope subset, rotation FSM transitions, consent compare, DPoP proof checks.
  • Integration — full flows: auth-code+PKCE → token → userinfo; refresh rotation; device flow; PAR; introspection/revocation; SSO + logout.
  • Differential / interop — our tokens accepted by external RP libraries (incl. #49's client); reference-OP (Keycloak/Hydra/node-oidc-provider) tokens accepted by our RP; claim-by-claim diffs.
  • Property (proptest) — code is single-use under interleavings (I1); PKCE verify iff SHA256(verifier)==challenge (I4); rotation keeps old tokens verifiable in-window (I8); refresh rotation invariants + reuse detection (I9); scope subset always holds (I14).
  • Conformance — OIDC Basic/Config/Dynamic profiles (release gate, Phase 13).
  • Security regression — auth-code injection, PKCE downgrade, token substitution, alg confusion (none, RS→HS), redirect tampering, refresh reuse, mix-up, introspection-oracle — each asserts fail-closed (no token issued).
  • Fuzzing (cargo-fuzz) — jwt_parse, jws_verify, authorize_query, token_body, jwks_parse, dpop_proof: no panic, typed errors only (P9).

Fundamental ceilings: the signing cost (RSA) caps single-replica issuance — mitigated by EdDSA and horizontal scaling; the shared store + replay cache are the real scaling limit (every issuance writes, every refresh rotates atomically, every proof checks the cache) — mitigated by read replicas, partitioning by expiry/family, and a sharded/Redis replay cache. JWKS/discovery scale trivially (static + cacheable). Atomic single-use consumption (I1, I9) is the coordination point that must hold across replicas — it relies on the store's transactional guarantee, so the store's write throughput + latency is the binding constraint at scale. Multi-region active-active (deferred) would require either a globally consistent token store or per-region issuance with reconciliation — a major design step, not a tuning knob.

Mental Models & First Principles

The compressed intuitions an expert IdP engineer holds. Each: the insight, what it predicts, the bug class you ship without it, and where this blueprint applies it.

MM1 — The browser is a courier you cannot trust; it may carry a claim ticket, never the valuables. A front-channel redirect is fully visible and tamperable (history, referer, logs, a malicious app on the same custom scheme). Insight: anything that crosses the browser must be useless to a thief on its own. Predicts: a token placed in a redirect (implicit grant) is a token leak waiting to happen; a code that is single-use, ≤60 s, and bound to a secret the browser never saw (PKCE verifier) is safe to send. Bug without it: you "optimize" by returning the access token directly to save a round-trip and create OAuth's original sin. Applied: §8.3 (front-channel sequence), Phase 3 (code issuance), Phase 4 (PKCE verify), ADR-22 (no implicit).

MM2 — A token is frozen authority; its only brakes are expiry and binding. Once minted, a bearer token is valid to whoever holds it until it expires or is revoked — and a stateless JWT cannot truly be revoked. Insight: you control blast radius up front (short TTL), or by tying the token to a key the holder must prove (DPoP/mTLS cnf), not after the fact. Predicts: "revoke this JWT now" is mostly a lie; the honest answers are short TTL + denylist-by-jti (best-effort) or sender-constraint. Bug without it: a 24-hour JWT access token that a single log leak turns into a day of account takeover. Applied: §4.1 (TTLs), P1, P13, Phase 6 (JWT-AT revocation gap), Phase 11 (cnf binding), MM6.

MM3 — kid makes a signing key a version pointer, so rotation is a deploy, not a flag day. Every JWS header names the key by thumbprint; verifiers select the key by kid, not by guessing. Insight: if old and new keys coexist in JWKS for ≥ max token TTL, every in-flight token keeps a resolvable verification key while new tokens use the new key. Predicts: rotation breaks only if you retire a key before its tokens expire (overlap < TTL) — the retire guard is the whole game. Bug without it: you "rotate" by overwriting the key and trigger a fleet-wide invalid_token 401 storm. Applied: §8.5 (rotation timeline), I8, P6, Phase 2 (rotation FSM), MM5.

MM4 — Trust the key's declared algorithm, never the attacker's JWT header. The alg in a JWS header is attacker-controlled input; the algorithm a token should be verified under is a property of the resolved key. Insight: pin verify-alg to resolve(kid).alg; treat alg:none and RS↔HS as category errors, not configurations. Predicts: every classic JOSE forgery (the alg:none bypass; RS256→HS256 confusion where the public key is used as an HMAC secret) is structurally impossible once the header alg is never consulted for the algorithm choice. Bug without it: a permissive library verifies with whatever the header says and accepts forged id_tokens. Applied: I5, P5, Phase 2 (alg pinning), §8.9 (alg attack rows), Required Reading (Boneh-Shoup, Katz-Lindell).

MM5 — Single-use is a write-once claim that must be settled by one atomic operation. "Consumed exactly once" across N stateless replicas is not an application check; it is a property of one conditional store mutation (DELETE … RETURNING / compare-and-set). Insight: read-then-act is a race; the store's transaction is the only arbiter that holds under concurrency. Predicts: any code/refresh consumption split into read + delete will double-redeem under load or a retry storm. Bug without it: two replicas each redeem the same code, minting two token sets from one authorization. Applied: I1, I9, Phase 4 (atomic consume), Phase 6 (atomic rotate), §8.10 (concurrent-code edge), MM3.

MM6 — Refresh rotation converts a silent theft into a loud, self-revoking event. If every refresh use rotates the token and an already-rotated token is presented, exactly one of {legitimate client, thief} is now holding a dead token — and the collision is observable. Insight: you cannot prevent refresh-token theft, but you can guarantee it surfaces (family revocation + audit) the moment both parties try to use the chain. Predicts: a non-rotating refresh token makes theft permanent and invisible; rotation bounds it to one rotation interval and emits a high-signal alert. Bug without it: a stolen refresh token mints access tokens forever and you never know. Applied: §8.4 (reuse-detection FSM), I9, P7, Phase 6, Phase 12 (anomaly), MM2.

MM7 — id_token answers who; access token answers what they may do; confusing them is a privilege error. The id_token (audience = the client, proves authentication to the RP) and the access token (audience = a resource server, authorizes API calls) are different credentials with different audiences and lifetimes. Insight: audience (aud) is the type tag; a resource server must reject an id_token, and an RP must not send an id_token to an API. Predicts: using an id_token as an access token (a real, recurring integration mistake) lets a credential meant only to prove identity act as an API key. Bug without it: an RS that accepts any signed JWT from the issuer authorizes id_tokens. Applied: §2.1, §8.2 (token formats), I6, Phase 5 (claims/audience), §17.6 (pitfall).

MM8 — The OP is server-authoritative; every client-supplied value is a request, not a fact. Scopes, redirect URIs, subject, audience, and grant are re-derived from registration and server-side state, never accepted as asserted by the client. Insight: the client says what it wants; the OP decides what is true (scope ⊆ registered, redirect ∈ registered set, code bindings from the stored record). Predicts: any branch that trusts a client assertion (a client-chosen scope, a client-chosen sub) is a privilege-escalation vector. Bug without it: "if scope is missing, grant all" or accepting a client-asserted subject. Applied: P11, I3, I14, Phase 1 (registry), Phase 3/Phase 4 (re-validation), §8.9.

MM9 — Defense against replay is layered; each control covers a different axis. state (RP CSRF/round-trip), nonce (id_token replay), jti (DPoP/assertion replay), single-use code, single-use user_code — distinct values guarding distinct flows, each backed by a bounded cache sized to its lifetime. Insight: no single value defends the whole protocol; remove one and a specific replay class reopens. Predicts: dropping nonce reopens id_token replay even with perfect state; an unbounded jti cache either leaks memory or evicts early and admits replay. Bug without it: you assume state "covers replay" and ship an id_token replay hole. Applied: P14, I12, I23, Phase 3 (state/nonce), Phase 11 (jti/DPoP), §4.1 (cache sizing).

MM10 — Fail closed: in identity, "allow on ambiguity" is "allow the attacker". Any unrecognized parameter combination, unverifiable signature, missing required field, or ambiguous state resolves to a precise typed rejection (RFC 6749 sec. 5.2), never a permissive fallback or a generic 500 that leaks state. Insight: the safe default in an authorization server is deny, and every denial maps to an exact error code so it is debuggable without leaking. Predicts: a default-allow arm or a catch-all match that silently accepts an unmodeled grant is the bug that becomes the breach. Bug without it: a permissive fallback authorizes a request the spec says to refuse. Applied: P9, the exhaustive idp-core enums (§11.1), Phase 0 (typed errors), the Failure Modes recovery philosophy (fail-closed sec. 5.2 refusals), every phase N.4.

Back-of-Envelope Capacity Model

The numbers an engineer computes before designing, each derived from the System Constraints (§4.1) with the formula shown. Round numbers; the point is the order of magnitude and the binding resource.

  1. Single-replica issuance ceiling (EdDSA). §4.1 targets ≥ 2,000 issuances/s (EdDSA). If /token p50 ≈ 15 ms is dominated by sign + one store write, then per core ≈ 1000 ms / 15 ms ≈ 66 issuances/s/core; to hit 2,000/s ⇒ 2000 / 66 ≈ 30 busy cores, i.e. the EdDSA target assumes a many-core box or that sign is well under 15 ms (EdDSA sign ≈ 50–80 µs, so sign is not the bottleneck — the store write is). Binding resource: store write latency, not crypto.
  2. Single-replica issuance ceiling (RS256). §4.1 targets ≥ 800/s (RS256). RS256 sign (2048-bit) ≈ 1–2 ms vs EdDSA ≈ 0.06 ms ⇒ ~20–30× costlier. 2000/s (EdDSA) ÷ ~2.5 ≈ 800/s — consistent with the RS256 target. Formula: throughput_RS256 ≈ throughput_EdDSA × (t_sign_EdDSA / t_sign_RS256). This is why ADR-7 prefers EdDSA.
  3. Token-endpoint bandwidth. A token response (access JWT + id_token + refresh + JSON envelope) ≈ 2 KB. At 2,000 issuances/s ⇒ 2 KB × 2000 = 4 MB/s ≈ 32 Mbit/s egress per replica — trivial; bandwidth is never the constraint for issuance (it can be for JWKS under cache miss — see #7).
  4. Replay-cache size for DPoP jti. §4.1: replay cache bounded by Σ(active token TTLs × rate). DPoP jti must be remembered for the proof freshness window (≈ 60 s, the skew bound I15). At, say, 2,000 proofs/s × 60 s = 120,000 live jtis; at ~64 B/entry ⇒ 120,000 × 64 B ≈ 7.7 MB. Formula: cache_entries = rate × window. Small — fits in memory; the concern is contention, not size (MM9, Phase 11).
  5. Authorization-code table working set. Codes live ≤ 60 s, single-use (§4.1, I1). At an interactive login rate of, say, 200 codes/s ⇒ 200 × 60 = 12,000 live codes at any instant; at ~512 B/record (bindings) ⇒ ≈ 6 MB. The code table is tiny and GC-dominated — sized by rate × 60 s, not by total logins.
  6. Refresh-family table growth. Refresh families persist for the absolute lifetime (§4.1: ≈ 30 d). With 100,000 daily active sessions each holding one family ⇒ over 30 d ≈ 100,000 × 30 = 3,000,000 live families; at ~256 B/row ⇒ ≈ 770 MB before GC. Formula: families ≈ DAU × abs_lifetime_days. This — not the code table — is the store's real footprint, and why partitioning/GC by expiry matters (Scalability Analysis).
  7. JWKS request load + cache payoff. Every resource server validating opaque-vs-JWT differs: JWT-validating RSes fetch /jwks.json and cache by kid. If 10,000 RS instances refresh JWKS every 10 min ⇒ 10,000 / 600 s ≈ 17 req/s — but a cache-miss storm at rotation (all refresh at once) could spike to thousands/s. §4.1 caps /jwks.json p99 < 5 ms via ETag + precompute; the ETag/CDN is what makes rotation safe at fleet scale (M4).
  8. Memory ceiling sanity. Live working set ≈ code table (#5, ~6 MB) + DPoP cache (#4, ~8 MB) + hot client cache + key set (a handful of KB). The durable refresh-family table (#6, ~770 MB) lives in Postgres, not the replica. So an idpd replica's RSS is dominated by tokio + connection pools + caches — comfortably within a small container; the database, not the replica, holds the state mass.
  9. Connection/FD budget. §4.1: FD budget bounded by connection pool + store pool. With H2 connection reuse, inbound FDs ≈ active client connections; outbound ≈ store pool size (e.g. 32–64) + Redis pool. Formula: FD ≈ inbound_conns + store_pool + replay_pool. Backpressure on pool exhaustion (§4.1) is the lever, not raising ulimit blindly.
  10. Startup budget. §4.1: startup < 2 s = key load (read N keys from store, ~ms) + store connect (pool warm, ~100s ms) + route registration (~ms). Store connection latency dominates startup, so a slow/cold database, not key generation, is the startup risk.
  11. Logout fan-out cost. §4.1 / Scalability: back-channel logout = N RP POSTs per logout. For a user with sessions at 20 RPs, one logout ⇒ 20 signed-JWT POSTs (each a sign ≈ 0.06 ms EdDSA + a network RTT). Formula: logout_work = sessions_per_user × (sign + RTT); bounded by async dispatch + per-RP timeout, so a slow RP cannot stall logout (Phase 10).
  12. Error-budget arithmetic (99.9% issuance). §4.1 availability 99.9% ⇒ 0.1% × 30 d ≈ 43 min/month of allowed issuance failure. At 2,000 issuances/s that budget is 2000 × 60 × 43 ≈ 5.2 million failed issuances/month before the SLO burns — which reframes "a brief store blip" as a quantifiable budget spend, gating the alerting in Phase 12 (M10–M12).

Alternative Architectures (Roads Not Taken)

Three fundamentally different architectures for the same "issue OAuth/OIDC tokens" problem — not parameter tweaks. Each: sketch, the regime where it wins, the real system that embodies it, why this blueprint rejected it.

Alt-Arch 1 — Headless AS with externalized login/consent (delegated UI).

  Browser ──/authorize──> [AS core (stateless)] ──redirect──> [Your Login+Consent App]
                                  ^                                   |
                                  |  login_challenge / consent_       | authenticates user,
                                  |  challenge (accept/reject) <──────+ collects consent
                                  |
  Browser <──code/redirect────────┘  (AS mints code/tokens after the app accepts)
        [AS keeps NO login UI; identity UX is the integrator's responsibility]

Regime where it wins: an organization that already owns its login experience and user store and wants the AS to be a pure, stateless protocol engine it can scale independently of UX. Real system: Ory Hydra (login/consent apps over a challenge/accept handshake). Why rejected here: the teaching goal is the complete issuer including the login/consent/session state machine (Phase 3, Phase 7, Phase 10); externalizing the UI would hide exactly the front-channel/consent/SSO reasoning this project exists to build, and split the system across a boundary the reader would not implement.

Alt-Arch 2 — Opaque tokens with mandatory central introspection (no stateless JWT validation).

  Client ──/token──> [AS] ── issues opaque AT (random handle) ──> Client
  Client ──AT──> [Resource Server] ──POST /introspect (AT)──> [AS] ──{active, scope, sub}──> RS
        [every API call consults the AS; no RS-side signature verification; instant revocation]

Regime where it wins: a single-tenant or tightly-coupled API platform where instant revocation is mandatory and every resource server can afford a synchronous call to the AS (or a short cache) — the AS is the live authority on every request. Real system: classic opaque-token deployments (the default in Ory Hydra and many gateway-fronted APIs; ADR-12 rejected-alternative). Why rejected as the default: it makes the AS a hot dependency on the resource-server critical path (a scaling + availability coupling, Capacity #7/Scalability Analysis) and loses interop with stateless RS libraries that expect RFC 9068 JWTs. This blueprint supports opaque + introspection (Phase 8) but defaults to JWT (ADR-12) for stateless validation; the alternative wins precisely when "revoke now" beats "validate offline."

Alt-Arch 3 — Macaroons / capability tokens with caveat-based attenuation.

  AS issues: M0 = MAC(root_key, "user=alice; aud=api")          (a capability)
  Client attenuates locally (no AS call):
       M1 = HMAC(M0, "scope=read")  then  M2 = HMAC(M1, "expires=+5m")
  Resource Server verifies the HMAC chain + checks each caveat is satisfied.
        [delegation/attenuation happens at the holder, offline; no per-derivation AS round-trip]

Regime where it wins: systems needing fine-grained, offline delegation where a holder must mint a strictly-weaker token for a downstream service without contacting the issuer (third-party caveats enable distributed authorization). Real system: Google's Macaroons (Birgisson et al., 2014) and their use in internal capability systems; Neil Madden's API Security in Action Ch 11 covers them (Required Reading #5). Why rejected: macaroons are not OAuth/OIDC — they break interop with every RP/RS that speaks JWT/JWKS and with the OIDC conformance suite (Phase 13), and the contract here is standards-conformant issuance (§1.1). They are the right answer to a different question (offline attenuation), which is why the model is worth holding (MM2) even though the architecture is not built.
