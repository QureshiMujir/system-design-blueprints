Project Number: 305

Project Name: Browser Rendering Engine

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch in Rust, an embeddable browser rendering engine that turns an HTML byte stream + CSS text into a deterministic RGBA framebuffer through a strict DAG: parse → cascade → layout → paint → composite → raster, driven by an incremental DocumentLifecycle with dirty-bit invalidation. Contract: fn render(html: &[u8], css: &[&str], viewport: Size) -> Canvas. Same (html, css, viewport, fonts) → byte-identical Canvas (§4.4). It is a rendering engine, not a JavaScript engine, network stack, or GPU compositor — those are adjacent, separately-scoped systems (#126/#259 own JS; networking is out of scope entirely).

1.1 Phase-0 deliverable — the nine render-* crates

  1. render-dom — HTML5 tokenizer + tree construction → Document/Node/Element, QualName/ Atom interning, QuirksMode.
  2. render-css — CSS Syntax L3 tokenizer + parser → StyleSheet/CssRule/Declaration, PropertyId registry, selector model.
  3. render-style — cascade, inheritance, ComputedStyle, StyleCache, StyleInvalidator.
  4. render-layout — BoxTree/LayoutBox/BoxKind, FormattingContext (BFC/IFC/FFC), FragmentTree/Fragment/LineBox, Au integer geometry.
  5. render-paint — DisplayList/DisplayItem, StackingContext, paint-order walk.
  6. render-compositor — Layer/LayerTree, layerization, composite().
  7. render-raster — RasterBackend, Canvas, scanline/edge-fill AA rasterizer, glyph blit.
  8. render-engine — RenderEngine, DocumentLifecycle, DirtyBits, FrameScheduler.
  9. render-cli — the rengine binary (render/dump/reftest/bench).

Phase-0 smoke gate: parse "<p>hi</p>", style + layout one block, raster a solid rect → valid PNG; DocumentLifecycle advances Loading → … → Composited.

1.2 System boundaries

Provides Delegates to Does NOT provide
DOM/CSSOM/cascade/layout/paint/composite/raster, incremental re-render, reftest conformance glyph shaping/bidi → #398; script/DOM-mutation API surface → #126/#259; selector-engine internals conceptually → #258 JS execution/event loop; HTTP fetch/networking; GPU raster; audio/video/<canvas>/WebGL; accessibility tree (#262)

Non-goals, stated once: full CSS property coverage (subset PropertyId registry only), full Unicode text shaping (mono bitmap glyphs only), GPU-backed raster (PhaseDeferred("§39")), animations/transitions beyond composite-only reuse hooks (PhaseDeferred("§39")).

1.3 Deployment model

Embeddable Rust library (render-engine exposes RenderEngine::render_frame() -> &Canvas) plus the rengine CLI. Headless use cases: screenshot capture, WPT/reftest harness, layout debugging, scraping a rendered layout. No window system, no GPU, no event loop required.

1.4 Target users / operators

Browser-engine engineers studying/extending a full pipeline; headless-render/screenshot-service engineers needing a deterministic, dependency-light renderer; tooling engineers building layout debuggers, CSS-conformance dashboards, visual-diff harnesses.

1.5 What later phases unlock

§13–16 (Phase 1–4): real DOM, CSSOM, cascade, computed values → a correctly styled tree. §17–19 (Phase 5–7): box generation + block layout (margin collapsing) + inline/line-breaking → real geometry. §20–21 (Phase 8–9): flexbox + positioned/fragmentation → FragmentTree complete. §22–23 (Phase 10–11): paint order + layerization + software raster → real pixels. §24 (Phase 12): incremental DirtyBits + FrameScheduler → cheap re-renders, subtree reuse. §25 (Phase 13): WPT reftest + html5lib conformance, differential pixel diff, fuzzing, criterion benches vs §4 targets.

1.6 Recommended language — Rust (edition 2021, MSRV 1.78)

Driver Rationale
Untrusted HTML/CSS on the parse hot path memory safety without a GC; no UAF/overflow on adversarial input
Box/fragment/display-list trees sum types (BoxKind, FragmentContent, DisplayItem) + exhaustive match catch unhandled cases at compile time
Cheap tree modeling arena (Arena<Node>) + typed index handles model node graphs with explicit, cycle-free ownership
Reference mapping Servo (script/style/layout_2020/gfx/webrender) is Rust → reference reading maps 1:1 onto these crates
Hot-path control manual allocation + cache layout for layout/raster inner loops; zero-cost integer geometry (Au)

Rejected: C/C++ — memory-unsafe on untrusted input, the exact class of CVE that dominates real browser-engine security advisories. Go — weaker sum types (no exhaustive enum dispatch for BoxKind/DisplayItem), GC pauses inside a 16.6 ms frame budget. TypeScript/JS — no allocation/cache control for the layout and raster inner loops; unsuitable for Au-integer determinism (§4.4).

1.7 Prerequisites

WHATWG HTML parsing spec (tokenizer states, insertion modes, foster-parenting, quirks); CSS 2.2, CSS Display 3, CSS Box, CSS Flexbox 1; tree/arena data structures; scanline/edge-list rasterization and coverage-based AA; rendering-pipeline lifecycle theory (clean/dirty phases, invalidation scoping, frame scheduling); html5lib tree-construction tests; Web Platform Tests reftests.

2. Why Build This

A rendering engine is the densest concentration of systems knowledge in client software: a multi-stage IR-lowering compiler (DOM → CSSOM → styled tree → box tree → fragment tree → display list → layer tree → pixels), a total-order constraint resolver (the cascade), a two-pass geometry solver (layout), and an incremental dataflow scheduler — all over one untrusted input stream, under a 16.6 ms frame budget. Building it from scratch forces mastery of the canonical interactive-graphics architecture that Servo, Blink, and WebKit all independently converge on.

2.1 Unique systems knowledge

Topic What you actually learn Where it lives
Multi-stage IR pipeline each stage owns a typed IR + arena; lowering is total and never reaches back upstream render-{dom,css,style,layout,paint,compositor,raster}
Lifecycle as a strict DAG DocumentLifecycle phases only advance; never paint before layout is clean render-engine
Invalidation engine DirtyBits set the earliest stale phase; InvalidationKind scopes the minimal subtree render-engine, StyleInvalidator
Cascade = priority sort winning declaration = lexicographic max over (origin+importance, specificity, source order) render-style::cascade
Two-pass constraint solve block width flows down from the containing block, height flows up from content render-layout block layout
Margin collapsing adjacent vertical margins merge (max of positives, min of negatives) — the classic correctness trap render-layout BFC
Stacking + paint order CSS 2.2 Appendix E: backgrounds → neg-z → block → floats → inline → pos-z render-paint
Layerization transform/opacity/will-change promote to Layer; composite-only change skips relayout+repaint render-compositor
Style sharing one ComputedStyle shared across siblings with equal cascade inputs — correctness gates reuse render-style

The deepest single lesson: the same tree is rebuilt and reused at five granularities. A class toggle may dirty only paint (color), only layout (width), or only composite (transform) — the engine must prove which. Incremental rendering is the whole game; a naive full re-render is the baseline every later phase must beat.

2.2 Why rendering engines matter — historically and architecturally

parse → style → layout → paint → composite is the canonical interactive-graphics architecture: every retained-mode UI toolkit, game-engine scene graph, and document renderer specializes it. Servo (Rust) is the direct reference; Blink (core/dom,core/css,core/layout,core/paint, cc/) and WebKit (WebCore render tree) prove the same shape independently — three teams converging on one architecture is strong evidence it is fundamental, not incidental. The web is the largest deployed surface of untrusted-input-to-pixels software; its hard-won invariants (lifecycle ordering, invalidation scoping, the cascade) are industry-portable, not browser trivia.

2.3 Engineering muscles exercised

Sum-type modeling (NodeData/BoxKind/FragmentContent/DisplayItem as exhaustive enums); arena allocation + id handles for cache-friendly, cycle-free trees; constraint solving via direct two-pass propagation instead of a general solver; spec-as-contract reading (WHATWG/CSS translated into state machines, validated against html5lib + WPT); hot-path discipline (integer Au kills float drift; benchmarking restyle/relayout/repaint independently); differential testing (reftests + per-pixel-tolerance diff; parser/layout fuzzing on adversarial input).

3. Architectural Overview

3.1 The pipeline at a glance

The engine is a strict, single-direction DAG: HTML+CSS bytes enter, an RGBA framebuffer exits. render-engine drives every box through a monotone DocumentLifecycle; no stage reaches forward into its consumer's state.

3.2 The three cross-cutting boundaries

Boundary Where Rule
Trust inputs to render-dom + render-css all bytes are hostile; parsers never panic/OOB/unbounded-recurse (P2); malformed input recovers per spec, never aborts
Concurrency layout + raster parsing is sequential (serial state machine); post-cascade ComputedStyle is immutable + Send+Sync; independent BFC subtrees layout on a work-stealing pool; raster tiles run in parallel; no shared mutable state crosses a thread
Persistence none arenas live in-process for the document's lifetime; the framebuffer (PNG via render-cli) is the sole durable artifact; no cache survives a process restart

3.3 Box-by-box responsibilities

render-dom — HTML front end. In: byte stream. Out: Document (arena of Node) + QuirksMode. Owns the ~70-state tokenizer and InsertionMode tree construction. Referenced later: §15 matches selectors against Element; §24 sets DirtyBits on mutation.

render-css — CSS front end. In: CSS byte streams. Out: StyleSheet{rules,origin}. Owns the CSS Syntax L3 tokenizer, the parser, and the PropertyId registry. Referenced later: §15 consumes SelectorList+Declaration.

render-style — the cascade engine. In: Document + matched StyleSheets. Out: one immutable ComputedStyle per element. cascade() orders declarations by origin→importance→specificity→ source order (I3); StyleCache shares styles across provably-equal inputs (I7). Referenced later: every layout box carries a ComputedStyleId.

render-layout — geometry. In: styled tree. Out: FragmentTree. Two trees: BoxTree (box generation, anonymous-box fixup) and layout(box_tree, viewport) -> FragmentTree, dispatched by FormattingContext (Block/Inline/Flex). All coordinates are Au (I5). Referenced later: §22 walks the FragmentTree; §24 reuses unchanged BFC subtrees.

render-paint — display-list builder. In: FragmentTree. Out: flat DisplayList. Emits items in CSS 2.2 Appendix E order (I8). Referenced later: §23 partitions items into Layers.

render-compositor — layer manager. In: DisplayList + StackingContext tree. Out: LayerTree. Layerization promotes transform/opacity/will-change subtrees (I9). Referenced later: §24's InvalidationKind::Composite advances only to Composited.

render-raster — software pixel backend. In: DisplayItems per layer. Out: Canvas{w,h,pixels}. Scanline/edge AA fill + mono glyph blit; the only stage using floating point. GPU raster is PhaseDeferred("§39").

render-engine — the orchestrator. Owns DocumentLifecycle (I1), DirtyBits, InvalidationKind scoping, and the FrameScheduler that coalesces invalidations into one lifecycle pass per frame.

render-cli — the rengine binary: render/dump/reftest/bench. A thin I/O shell; owns no rendering logic.

Hard envelopes, not aspirations. Page model = "5k-node page": 5,000 DOM nodes, ~20 KB CSS, viewport 1920×1080. §25 (Phase 13) benchmarks assert every row via criterion. Single-machine, in-process: no NUMA, no network, no FD budget (the engine consumes a byte slice + emits a Canvas; fetch is a non-goal owned by #126/#259).

4.2 Document-complexity caps (DoS bounds)

Cap Limit Why
Open-element/formatting stack 512 mis-nested <table>/<b> bombs in tree construction
Selectors per stylesheet 2¹⁶ bounds matching cost per element
Declarations per rule 4096 bounds cascade work

Exceeding a cap is a clean, defined error — never OOM or stack overflow (P10, I5).

4.3 CPU/cache assumptions and startup

Au integer math (P4) keeps layout branch-predictable and cache-friendly; arena+index handles (ADR-03) make tree walks near-sequential; tile-based raster sizes tiles to fit L2 (≤512 KB working set); StyleCache keeps the distinct-ComputedStyle working set ≪ node count. Zero global mutable init: the UA stylesheet parses once at RenderEngine::new (< 1 ms); no background threads spun at startup; first render_frame ready in < 1 ms excluding caller I/O.

4.4 Robustness posture and determinism

In-process library → "availability" means never crashing the host on adversarial input (P2). Parsers are total over arbitrary byte slices; unknown CSS drops the declaration, not the sheet; layout/paint are total over any well-typed BoxTree; no unsafe on parse/layout/paint hot paths except audited arena internals. Fuzzing (§25) asserts zero panics, zero OOM beyond §4.2 caps, bounded time on any input ≤ the caps. Determinism: same input bytes (HTML + CSS + viewport + fonts) → byte-identical Canvas/PNG on every run and platform; no wall-clock, no RNG, no hash-map iteration order, no thread-scheduling dependence in any pipeline output (P11, I10).

6. Design Principles

Thirteen non-negotiable principles (P1…P13), referenced by ID throughout §12–§39. Violations are correctness bugs, not stylistic nits.

ID Principle Rule Tradeoff Violation breaks
P1 Spec is the oracle WHATWG HTML + CSS 2.2/Display 3/Box/Flexbox 1 are normative; disputes resolve to spec text, validated by reftest against shipping engines spec fidelity over convenience — implement "useless-looking" quirks/foster-parenting cases an ad-hoc <table> parse without foster-parenting → misnested DOM → wrong box tree → unrecoverable reftest divergence
P2 Parsers never panic render-dom/render-css are total over untrusted bytes; malformed input yields a best-effort tree, never a crash error-recovery code costs more than terse parsing; every unwrap on the parse path is a review-blocker a truncated <!-- comment panics on OOB index → engine unusable on real-world HTML
P3 The lifecycle is a strict DAG DocumentLifecycle advances monotonically; a phase reads only strictly-earlier outputs; never paint before layout is clean no opportunistic "paint while styling" pipelining — clarity over latency building a DisplayList from a stale FragmentTree → geometrically wrong frame, no error raised
P4 Au integer geometry all layout coordinates are Au(i32), 1 px = 60 Au; floats appear only in raster coverage and transforms explicit rounding rules at unit boundaries f32 position accumulation → 1px seams → platform-dependent reftest failures
P5 Invalidate the minimum a mutation dirties the smallest subtree via InvalidationKind; never "mark whole document dirty" by default invalidation analysis (which properties affect layout/paint/composite) is intricate a color change treated as NEEDS_LAYOUT → full relayout per frame → animation jank
P6 Style sharing is correctness-gated StyleCache shares one ComputedStyle only when ALL cascade inputs are provably equal the share-eligibility check costs cycles; a false share is a silent bug, so the gate is conservative sharing across a :hover-differentiated pair → hovered element fails to restyle
P7 ComputedStyle is immutable after cascade layout/paint/composite read it; restyle produces a new ComputedStyle, never edits in place more allocation/churn on restyle patching a used value in place → every element sharing that style gets it silently wrong
P8 Anonymous boxes preserve box-model invariants a BlockContainer's children are all block-level or all inline-level; mixed children trigger anonymous-box fixup fixup complicates box construction inline text placed directly beside block siblings with no wrapper → BFC/IFC interleave incorrectly
P9 Layerize to make composite-only updates cheap transform/opacity/will-change subtrees promote to their own Layer layers cost memory; over-layerization wastes RAM, under-layerization forces repaint an opacity animation on a non-layerized subtree rebuilds the display list every frame
P10 Bounded document complexity explicit caps (§4.2) on depth/nodes/selectors/declarations; exceeding one is a defined, recoverable outcome rejects pathological documents a "real" browser might slowly render recursive-descent layout over a 100k-deep nest → native stack overflow
P11 Deterministic rendering identical input → byte-identical Canvas, every run and platform forbids order-dependent parallel-merge optimizations unless provably serial-equivalent iterating a HashMap of matched declarations during cascade → flaky reftests
P12 Observable pipeline every IR is independently dumpable (dom/css/style/box/fragments/display-list/layers) dump serializers add maintenance surface no dump fragments → a layout regression and a paint regression are indistinguishable from the PNG alone
P13 Crate boundaries enforce the DAG the nine render-* crates depend strictly downstream; no upward or cyclic dependency shared primitives (Au,Rect,Rgba) must live in the lowest crate that needs them render-style importing render-layout to "peek at used widths" → dependency cycle, DAG no longer compiler-enforced

8. Domain Model — HTML, CSS, and the Render Trees

Seven coupled data models, one per pipeline stage (§3): DOM (render-dom), CSSOM (render-css), ComputedStyle/styled tree (render-style), BoxTree+FragmentTree (render-layout), DisplayList (render-paint), LayerTree (render-compositor), Canvas (render-raster).

8.1 HTML model — tokenization + tree construction

Two coupled state machines (WHATWG HTML section 13.2): the tokenizer (bytes → tokens) and tree construction (tokens → DOM), sharing state (tree construction resets tokenizer mode for <script>/<style>).

Token = DOCTYPE{name,public_id,system_id,force_quirks}
      | StartTag{name:Atom, attrs:Vec<(Atom,String)>, self_closing:bool}
      | EndTag{name:Atom} | Comment(String) | Character(char) | EOF

InsertionMode = Initial | BeforeHtml | BeforeHead | InHead | AfterHead
              | InBody | Text | InTable | InCell | AfterBody | ...
Mode Token Action → next mode
Initial DOCTYPE set QuirksMode (8.1.1), → BeforeHtml
BeforeHead <head> push head → InHead
InHead <style>/<script> switch tokenizer RAWTEXT → Text
AfterHead <body> push body → InBody
InBody </p> if no p in scope, insert implied <p></p> then close
InBody <table> → InTable

Implied end tags: auto-close {dd,dt,li,option,optgroup,p,rp,rt} before certain insertions (<li>a<li>b auto-closes the first <li>). Foster parenting: mis-nested content inside <table> relocates before the table, not inside it.

8.2 CSS model — grammar + CSSOM

stylesheet      = { CDO | CDC | ws | at-rule | qualified-rule } ;
qualified-rule  = selector-list , declaration-block ;
declaration-block = "{" , { declaration , [ ";" ] } , "}" ;
declaration     = property , ":" , value , [ "!" , "important" ] ;
selector-list   = complex-selector , { "," , complex-selector } ;
complex-selector= compound , { combinator , compound } ;
combinator      = ">" | "+" | "~" | ws ;
compound        = [ type-sel ] , { id-sel | class-sel | attr-sel | pseudo } ;

Parse output (locked types): StyleSheet{rules:Vec<CssRule>, origin:Origin}; CssRule = Style(StyleRule)|Media|Import|FontFace; StyleRule{selectors:SelectorList, block:Vec<Declaration>}; Declaration{property:PropertyId, value:ComputedValue, important:bool}. The PropertyId registry maps each known property to {inherited, initial, applies_to}; unknown property names are dropped at parse time (8.6). Shorthand expansion (margin: 1px 2px → four longhands) happens before cascade.

8.3 The cascade — ordered tuple sort

CascadeKey = (origin_importance, specificity(a,b,c), source_order)   // descending wins (I3)
fn cascade(el, matched: &MatchedRules, parent: &ComputedStyle) -> ComputedStyle

Origin×importance precedence (highest first): Author !important > User !important > UA !important > Author normal > User normal > UA normal. Specificity (a,b,c): a=#id, b= class/attr/pseudo-class, c=type/pseudo-element, compared lexicographically. Source order: later declaration wins ties. Result = specified value per property; computed-value resolution (lengths → Au, colors → Rgba) yields ComputedStyle (§16). StyleCache shares one ComputedStyle across elements with identical (parent style, matched rules, inline) inputs (I7).

24. Phase 12 — Invalidation and incremental rendering

24.1 Objectives

Wire render-engine's StyleInvalidator (stub since §16) and DirtyBits/InvalidationKind (stub since §12) into a working incremental pipeline: a DOM mutation scopes to the minimal DirtyBits, the FrameScheduler coalesces all mutations between frames into one lifecycle pass, and unchanged subtrees (style, fragments, display items, layers) are reused frame-to-frame (P5, I11). This is the phase that proves I11 (incremental ≡ full re-render).

24.2 Detailed Implementation Steps

scheduler.rs: FrameScheduler batches set_dirty() calls, computes the union DirtyBits and the minimal lifecycle re-entry point per I1's min_phase_for(). dirty.rs's StyleInvalidator maps a mutation (class/attr/style/text/structure change) to affected elements via selector dependency tracking (from §16.2's dependency-key hooks); scoping rules follow §8.8's locked table exactly (color→NEEDS_PAINT, width/display→NEEDS_LAYOUT, transform/opacity on a layerized subtree→NEEDS_COMPOSITE only, per I9). Subtree reuse: arenas retain unchanged Ids across frames (ADR-03's stable index handles make this free).

24.3 Deliverable

render_frame() on a single mutated element re-runs only the dirtied phases; rengine bench --incremental reports per-mutation-class latency against §4's 16 ms floor.

24.6 Pitfalls

Under-invalidation (a missed selector dependency) is the gravest bug class in the whole engine — silently stale pixels with no crash to signal it; the dirty-twin test (I11) is the only reliable detector. 24.8 Edge Cases

A mutation during an in-flight render_frame() (re-entrancy) must queue for the next frame, not corrupt the current pass. Rapid toggling of the same property within one coalescing window collapses to its net effect (no wasted intermediate work). 33. Scalability Analysis

What stays constant vs grows: Au arithmetic cost is O(1) per operation regardless of document size; StyleCache lookup is O(1) amortized (hash + Bloom pre-filter). What grows with node count N: parse (O(N)), box generation (O(N)), layout (O(N) per formatting context, O(N log N) worst case for deeply nested margin-collapse chains), paint (O(fragments)), raster (O(pixels), independent of N once the display list is built). Named bottlenecks in order: (1) layout — the two-pass solve dominates at scale, especially deep BFC nesting; (2) raster — pixel count, not node count, bounds it, so it plateaus on large-but-simple pages; (3) cascade matching — bucketing (§15.2) keeps this sub-quadratic, but a stylesheet with R rules and no bucketable selectors degrades toward O(N×R). Horizontal scaling: not applicable (in-process library, one document per call); the scaling story is vertical — multi-core parallel layout/raster (PhaseDeferred("§39"), ADR-17). Sharding/partitioning: raster tiles (§23.2) are the one partitioned dimension shipped in v1. Coordination overhead: none at v1 (single-threaded); the deferred parallel-layout design must bound BFC-subtree coordination to avoid Amdahl's-law ceilings from serial cascade + serial tree-construction. Practical ceiling: the §4.2 caps (node count 2²⁰, depth 512) are the explicit ceiling; beyond it the engine degrades gracefully (clamp/ truncate) rather than failing. The lever beyond the ceiling is parallelism (deferred) — it moves the wall-clock ceiling without moving the correctness ceiling, which is already unconditional.

36. Back-of-Envelope Capacity Model

Every number below is derived from §4's constraints table, formula shown, not asserted.

  1. DOM arena memory = 5,000 nodes × <128 B/Node (§4 memory ceiling) = ≤ 640 KB for the node arena alone on the reference page.
  2. Canvas framebuffer size = 1920 × 1080 × 4 B/pixel (RGBA8) = ≈ 8.3 MB (matches §4.4's "~8.3 MB" 1080p figure).
  3. Resident-set budget check = 640 KB (nodes) + 8.3 MB (canvas) + StyleCache/BoxTree/ FragmentTree/DisplayList arenas ≈ well under the 64 MB ceiling (§4), leaving > 50 MB of headroom for the remaining arenas and the UA stylesheet.
  4. HTML parse wall-clock, 1 MB page = 1 MB ÷ 30 MB/s (M1) = ≈ 33 ms worst-case cold parse for a 1 MB document at the throughput floor.
  5. CSS parse wall-clock, 20 KB page CSS = 20 KB ÷ 50 MB/s (M2) = ≈ 0.4 ms — confirms CSS parse is not the pipeline's critical path at the reference page size.
  6. Full-pipeline budget decomposition = 50 ms cold (M3) ≈ parse (≈ 5 ms combined HTML+CSS at the above throughputs) + style (≤ 10 ms p99, §4.1) + layout (≤ 20 ms p99) + paint (≤ 7 ms p99)
    • raster (≤ 28 ms p99) — the p99 sum (≈70ms) exceeds the 50ms cold budget, which is why §4.1's figures are independent-stage p99s, not additive worst cases; the cold-budget gate (M3) is the one that must hold end-to-end, forcing p50-dominated behavior in practice.
  7. 60fps frame floor = 1000 ms ÷ 60 fps = 16.6 ms, rounded to the 16 ms incremental target (M5) — the frame budget every incremental mutation must fit inside.
  8. Node-count ceiling memory bound = 2²⁰ nodes (§4.2 cap) × 128 B = ≈ 128 MB worst-case node-arena size at the hard cap — this is why the cap exists: beyond it, the node arena alone would exceed the 64 MB steady-state budget (item 3) by 2×.
  9. Style-sharing savings, 5k-node page at 40% hit rate (§16.4 target) = 5,000 × 0.40 = 2,000 nodes whose ComputedStyle allocation is avoided — at a rough 200 B/style, that is ≈ 400 KB saved versus the no-sharing baseline.
  10. Raster fill-rate requirement = 1920×1080 px ÷ 16 ms (M10 raster p95, scaled to the incremental floor) = ≈ 8 Mpixel / 16 ms ≈ 0.5 Gpixel/s sustained fill rate needed from the scanline rasterizer to hit the incremental frame budget on a full-canvas repaint.
  11. Tile-parallel speedup ceiling = 8 cores (§4 hardware target) × (tile working set ≤ 512 KB L2, §4.3) → up to 8× raster throughput if tiles are perfectly independent, before Amdahl's-law-bound serial stages (parse, cascade) cap the end-to-end speedup.
  12. Fuzz coverage budget = 60 s smoke × 3 targets (§25 CI gate) = 180 CPU-seconds per CI run; nightly campaigns (fuzz.yml) run orders of magnitude longer against the same seed corpora to grow coverage without blocking every merge.

38. Alternative Architectures (Roads Not Taken)

A1 — Mutable render-object tree (WebKit-classic style), rejected in favor of the immutable box/fragment split (ADR-10).

DOM --style--> RenderObject tree (mutable in place: RenderBlock/RenderInline/RenderText)
                    |  layout() mutates x/y/w/h directly on the same nodes
                    v
                 paint() walks the same mutable tree

Regime where it wins: an engine migrating incrementally from a decades-old codebase, where a clean-slate immutable rewrite is not affordable — WebKit's WebCore/rendering is the real system that embodies this. Rejected here because in-place mutation conflates persistent structure with transient per-layout geometry, which defeats both fragmentation (one box → many fragments) and cheap incremental relayout (§9, ADR-10).

A2 — GPU-first display list (WebRender model), rejected in favor of software raster (ADR-11), deferred not abandoned (§39).

FragmentTree -> DisplayList -> GPU command batching -> shader-based tile raster -> compositor

Regime where it wins: any interactive browser targeting 4K/60fps on real hardware — WebRender (Mozilla, embodied in Firefox and Servo) is the real system. Rejected for v1 because it adds a GPU-driver dependency that breaks CI portability and reftest bit-exactness (I10); this design's DisplayList (§11) is intentionally WebRender-shaped so the GPU backend is a drop-in later (PhaseDeferred, §39).

A3 — Parallel-everything from day one (Stylo/Servo model), rejected in favor of single-threaded-first (ADR-17).

DOM --parallel restyle (rayon)--> styled tree --parallel layout (BFC subtrees)--> FragmentTree

Regime where it wins: a production engine under real page-load-latency pressure, where restyle of a 50k-node page must not block the main thread — Stylo in Firefox is the real system. Rejected for v1 because correctness-first sequencing is easier to prove invariant-by-invariant (§7) before introducing data races across StyleCache/arena mutation; the arena+index design (ADR-03) already makes the later parallel retrofit structurally possible without a rewrite.

A4 — Streaming/incremental parse-and-layout fusion (progressive rendering), rejected in favor of a batch-per-frame pipeline (ADR-06).

byte stream --(parse chunk)--> partial DOM --(layout chunk immediately)--> partial paint
   (repeat as bytes arrive, before the document is fully loaded)

Regime where it wins: a real user-facing browser on a slow network, where showing partial content immediately (progressive rendering) beats waiting for the full document — every shipping browser does this. Rejected here because the engine's input contract is a complete in-memory byte slice (§1.3, no networking/fetch in scope) — there is no "arriving bytes" event to fuse against, and adding one would entangle the deferred fetch/networking non-goal into the core lifecycle (I1).

40. Glossary

Anonymous box — a synthesized LayoutBox (no DOM node) inserted to preserve the invariant that a box's children are uniformly block-level or inline-level (I4). Atom — an interned string handle (Copy, pointer-equality) used for tag/attribute/keyword names to avoid repeated heap comparison. Au (app unit) — the integer layout-geometry unit; 1 CSS px = 60 Au (ADR-04). Bloom filter (ancestor) — a probabilistic pre-filter used by StyleCache to cheaply reject non-candidate style-sharing pairs before the exact-equality check (I7). BoxKind — the enum classifying a LayoutBox's generated type (BlockContainer, InlineBox, Flex, Text, Replaced, anonymous variants). BoxTree — the persistent, input-only tree of LayoutBoxes produced by box generation (§17). Cascade — the algorithm resolving competing CSS declarations to one winner per property via origin, importance, specificity, and source order (I3, §8.3). CascadeKey — the packed sort key (origin_importance, specificity, source_order) used to order matched declarations. Canvas — the RGBA pixel buffer produced by render-raster. ComputedStyle — the immutable, per-element resolved style value produced by cascade() (P7). ComputedValue — a single resolved CSS value (length, color, keyword, etc.) inside a ComputedStyle. CSSOM — the parsed CSS object model (StyleSheet/CssRule/StyleRule/Declaration) produced by render-css. DirtyBits — the bitset (NEEDS_STYLE|LAYOUT|PAINT|COMPOSITE) marking the earliest stale lifecycle phase (§7 I1, I9). DisplayItem — one paintable primitive (Rect, Border, Text, Image, clip push/pop) in a DisplayList. DisplayList — the flat, ordered list of DisplayItems produced by build_display_list (I8). DocumentLifecycle — the forward-only phase state machine (Loading…Composited) that render-engine drives (I1). Fixed-point (rejected here) — an alternative integer-geometry representation (16.16) rejected in favor of the simpler Au scheme (ADR-04). FormattingContext — the layout mode a box establishes for its in-flow children: Block (BFC), Inline (IFC), or Flex (FFC). Foster parenting — the HTML tree-construction rule relocating mis-nested <table> content to before the table rather than inside it (§8.1). Fragment — one piece of resolved geometry (Rect + content) produced by layout(); a single LayoutBox may produce multiple fragments (fragmentation, §21). FragmentTree — the throwaway, per-layout tree of Fragments (ADR-10). FrameScheduler — the component coalescing invalidations between frames into one lifecycle pass (§24). GlyphRun — a sequence of pre-shaped glyphs with position/metrics, consumed by paint/raster. Implied end tag — an HTML tree-construction rule that auto-closes certain open elements before inserting/closing another (e.g. <li> before a new <li>). InsertionMode — the HTML tree-construction state machine's current mode (InBody, InTable, etc.). InvalidationKind — the classification (Style/Layout/Paint/Composite) of what a mutation requires re-running (P5). Layer — a promoted subtree with its own cached display items, transform, and opacity, enabling composite-only updates (P9). LayerTree — the tree of Layers built by layerization (§23). LayoutBox — one node of the BoxTree; carries a BoxKind and a ComputedStyleId. LineBox — one line of inline content in an Inline Formatting Context, with a baseline and a list of GlyphRuns. Margin collapsing — the CSS 2.2 rule merging adjoining vertical margins by the signed-max formula (I6). Node — one entry in the DOM Arena; carries NodeData, parent/children, and DirtyBits. PropertyId — the closed enum indexing the CSS property registry (name, initial value, inherited flag). QuirksMode — the document-wide rendering mode (NoQuirks/LimitedQuirks/Quirks) selected from the DOCTYPE (§8.1.1). RasterBackend — the trait abstracting pixel-fill operations (fill_rect, fill_path, blit_glyph) over Canvas. Reftest — a differential test comparing this engine's rendered output to a reference image at a per-pixel tolerance (ADR-20). Specificity — the (a,b,c) selector-strength tuple (id-count, class/attr/pseudo-class-count, type/pseudo-element-count) used in the cascade. StackingContext — a nested paint-order grouping created by positioned/opacity/transform boxes with a z-index (§21). StyleCache — the component sharing one ComputedStyle across elements with provably-equal cascade inputs (I7). StyleInvalidator — the component mapping a DOM mutation to the minimal set of elements/ DirtyBits needing restyle (§24). StyleSheet — the parsed CSS document (rules, origin) produced by render-css. Tokenizer — the state machine converting a byte/character stream into a token stream (HTML or CSS). Tree construction — the HTML algorithm consuming tokens to build the DOM via InsertionMode. WPT (Web Platform Tests) — the cross-browser conformance test suite whose reftests validate this engine's layout/paint correctness (§25).
