4. System Constraints

Hard envelopes, not aspirations. Page model = "5k-node page": 5,000 DOM nodes, ~20 KB CSS, viewport 1920×1080. §25 (Phase 13) benchmarks assert every row via criterion. Single-machine, in-process: no NUMA, no network, no FD budget (the engine consumes a byte slice + emits a Canvas; fetch is a non-goal owned by #126/#259).

Tail drivers: deep margin-collapse chains (layout p99), large soft-wrap text (raster p99), many stacking contexts (paint p99). p99 ≤ ~3× p50 or it is a regression (gated in §32).

Exceeding a cap is a clean, defined error — never OOM or stack overflow (P10, I5).

4.3 CPU/cache assumptions and startup

Au integer math (P4) keeps layout branch-predictable and cache-friendly; arena+index handles (ADR-03) make tree walks near-sequential; tile-based raster sizes tiles to fit L2 (≤512 KB working set); StyleCache keeps the distinct-ComputedStyle working set ≪ node count. Zero global mutable init: the UA stylesheet parses once at RenderEngine::new (< 1 ms); no background threads spun at startup; first render_frame ready in < 1 ms excluding caller I/O.

4.4 Robustness posture and determinism

In-process library → "availability" means never crashing the host on adversarial input (P2). Parsers are total over arbitrary byte slices; unknown CSS drops the declaration, not the sheet; layout/paint are total over any well-typed BoxTree; no unsafe on parse/layout/paint hot paths except audited arena internals. Fuzzing (§25) asserts zero panics, zero OOM beyond §4.2 caps, bounded time on any input ≤ the caps. Determinism: same input bytes (HTML + CSS + viewport + fonts) → byte-identical Canvas/PNG on every run and platform; no wall-clock, no RNG, no hash-map iteration order, no thread-scheduling dependence in any pipeline output (P11, I10).

36. Back-of-Envelope Capacity Model

Every number below is derived from §4's constraints table, formula shown, not asserted.

  1. DOM arena memory = 5,000 nodes × <128 B/Node (§4 memory ceiling) = ≤ 640 KB for the node arena alone on the reference page.
  2. Canvas framebuffer size = 1920 × 1080 × 4 B/pixel (RGBA8) = ≈ 8.3 MB (matches §4.4's "~8.3 MB" 1080p figure).
  3. Resident-set budget check = 640 KB (nodes) + 8.3 MB (canvas) + StyleCache/BoxTree/ FragmentTree/DisplayList arenas ≈ well under the 64 MB ceiling (§4), leaving > 50 MB of headroom for the remaining arenas and the UA stylesheet.
  4. HTML parse wall-clock, 1 MB page = 1 MB ÷ 30 MB/s (M1) = ≈ 33 ms worst-case cold parse for a 1 MB document at the throughput floor.
  5. CSS parse wall-clock, 20 KB page CSS = 20 KB ÷ 50 MB/s (M2) = ≈ 0.4 ms — confirms CSS parse is not the pipeline's critical path at the reference page size.
  6. Full-pipeline budget decomposition = 50 ms cold (M3) ≈ parse (≈ 5 ms combined HTML+CSS at the above throughputs) + style (≤ 10 ms p99, §4.1) + layout (≤ 20 ms p99) + paint (≤ 7 ms p99)
    • raster (≤ 28 ms p99) — the p99 sum (≈70ms) exceeds the 50ms cold budget, which is why §4.1's figures are independent-stage p99s, not additive worst cases; the cold-budget gate (M3) is the one that must hold end-to-end, forcing p50-dominated behavior in practice.
  7. 60fps frame floor = 1000 ms ÷ 60 fps = 16.6 ms, rounded to the 16 ms incremental target (M5) — the frame budget every incremental mutation must fit inside.
  8. Node-count ceiling memory bound = 2²⁰ nodes (§4.2 cap) × 128 B = ≈ 128 MB worst-case node-arena size at the hard cap — this is why the cap exists: beyond it, the node arena alone would exceed the 64 MB steady-state budget (item 3) by 2×.
  9. Style-sharing savings, 5k-node page at 40% hit rate (§16.4 target) = 5,000 × 0.40 = 2,000 nodes whose ComputedStyle allocation is avoided — at a rough 200 B/style, that is ≈ 400 KB saved versus the no-sharing baseline.
  10. Raster fill-rate requirement = 1920×1080 px ÷ 16 ms (M10 raster p95, scaled to the incremental floor) = ≈ 8 Mpixel / 16 ms ≈ 0.5 Gpixel/s sustained fill rate needed from the scanline rasterizer to hit the incremental frame budget on a full-canvas repaint.
  11. Tile-parallel speedup ceiling = 8 cores (§4 hardware target) × (tile working set ≤ 512 KB L2, §4.3) → up to 8× raster throughput if tiles are perfectly independent, before Amdahl's-law-bound serial stages (parse, cascade) cap the end-to-end speedup.
  12. Fuzz coverage budget = 60 s smoke × 3 targets (§25 CI gate) = 180 CPU-seconds per CI run; nightly campaigns (fuzz.yml) run orders of magnitude longer against the same seed corpora to grow coverage without blocking every merge.
