Back-of-Envelope Capacity Model

All inputs are taken from §4 (System Constraints); arithmetic is shown.

  1. Entry size. Rect (4×f64 = 32 B) + child id (8 B) + padding → 40–80 B; take 80 B worst case (§4 node-overhead row).
  2. Fanout per 4 KiB page. M = floor((4096 − 16 header) / 80) = floor(51.0) = 51 → M=50 as configured (ADR-11). Formula: M = (page − header)/entry.
  3. Tree height, N=10M. Best case ceil(log_M N) = ceil(log₅₀ 1e7) = ceil(4.12) = 5; worst case using m=20: ceil(log₂₀ 1e7) = ceil(5.38) = 6 → height 5–6 (I2).
  4. Node count. At 70% insert occupancy: leaves = 1e7 / (0.7×50) = 1e7/35 ≈ 286 K; internal ≈ 286K/35 ≈ 8.2 K; total ≈ 294 K nodes.
  5. In-RAM size. Leaf entries = 1e7 × 80 B = 800 MB; internal ≈ 8.2K × 50 × 80 B = 33 MB → ≈ 833 MB < 2 GiB and ≈ 1.3× raw data (§4 "≤ 2× raw").
  6. Page-file size (STR, 95% occupancy). Leaf pages = 1e7/(0.95×50) = 210.5 K; +internal ≈ 4.4 K → 215 K pages × 4 KiB ≈ 880 MB ≈ 1.3× raw (§4 "≤ 1.5×").
  7. Cache residency. 256-page cache vs 215 K total pages = 0.12% resident — but top two levels (root + L1 ≈ 90 pages) fit entirely, so every query serves root+L1 from cache; misses/query ≈ height − cached_levels ≈ 6 − 3 = 3 page reads.
  8. Window-query work (1% selectivity, 1M). ≈ 10 K results; nodes visited ≈ results/occupancy ≈ 10000/35 ≈ 286 leaves + ancestors ≈ ~300 node visits; at p50 ≤ 500 µs → ~1.7 µs/visit budget.
  9. Insert budget. 100 K/s → 10 µs/insert; ChooseLeaf descends 6 levels → 1.6 µs/level; an enlargement scan of 50 entries ≈ 50 × ~30 ns ≈ 1.5 µs/level ✓.
  10. kNN heap size (k=10, 1M). ~hundreds of nodes visited × M entries pushed → peak heap ~few thousand × 16 B ≈ tens of KB — negligible RAM.
  11. Geohash precision. 12 chars × 5 bits = 60 bits → cell ≈ earth-span / 2³⁰ per axis ≈ 37 mm; encode ≥ 5M/s → 200 ns/encode for ~60 bit-ops ✓.
  12. STR build, 10M. sort dominates: O(N log N) ≈ 1e7 × 23 ≈ 2.3e8 comparisons; at ≥ 500 K objs/s → ~20 s; slice count P = ceil(sqrt(N/M)) = ceil(sqrt(2e5)) = 448.
