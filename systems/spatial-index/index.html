In one paragraph

A spatial index answers "which stored objects lie in this rectangle?" and "which k objects are closest to this point?" without looking at every object. This design is a Rust library of twelve crates, the last being a command-line tool (§1.1, §1.6). It holds three structures: an R-tree with the R*-tree improvements, a quadtree, and a geohash codec. A brute-force scan (sidx-oracle) checks every answer in tests (§1.1, P1). It is an embedded, single-process library with no server (§1.4). Library users and data-pipeline developers call it directly, and the blueprint also frames it as a way to learn tree internals (§1.5).

The problem, concretely

Picture 1 million stored objects, each with a bounding rectangle, and a window query at 1% selectivity (§4.1). The obvious answer is to test every object. The blueprint keeps exactly that scan as its correctness oracle and calls it "feasible only in tests", since it is O(n) per query (P1). The index's job is to avoid it: Capacity Model item 8 estimates about 10 thousand results and about 300 node visits for that query.

Getting the cheap answer right is hard for four reasons:

  • Silent wrongness. A dropped object produces a shorter list, not an error (P1, P11), so the design tolerates zero false negatives (§4.2).
  • Overlap. Overlapping boxes force search down many branches; 50% overlap on every level degrades toward a full scan while the tree still looks valid (P4, MM3).
  • Nearest neighbour must be exact. No approximation factor is acceptable (P5).
  • Cheap tricks fail at edges. A geohash turns proximity into a prefix scan, but adjacent cells can have different prefixes (MM7); a uniform grid overflows busy cells on skewed data (A3 in Alternative Architectures).

The out-of-scope list marks the boundary: no approximate nearest neighbour, no distributed index, no curved-earth distance, no topological predicates such as "touches" (§1.2, §1.3).

How it works, end to end

Follow one window query through the boxes of §3.1's diagram (trimmed here):

  objects (id + MBR / point)
  sidx-rtree (sidx-rstar split, sidx-bulk STR) | sidx-quadtree | sidx-geohash
     +--------- all entries carry an MBR (sidx-geom: union / overlap / MINDIST) ---------+
                               v
  sidx-query (Window | Intersect | Contains | Knn | Nearest)
     v                                        v
  window descent (prune by MBR overlap)   sidx-knn (best-first heap; MINDIST, MINMAXDIST)
     +-------------------+--------------------+
                         v
  results  <==verify==  sidx-oracle (brute-force scan; correctness gate)
                         v
  sidx-persist (page-aligned nodes)          sidx-cli (build / query / knn / bench)
  1. Types and geometry. sidx-core defines Point<D>, Rect (the bounding box, or MBR, minimum bounding rectangle), NodeId, DataId and Query, with no I/O (§3.2, §8.1). sidx-geom supplies the box algebra and the two distance bounds (§3.2).
  2. Dispatch. sidx-query routes a Query to the R-tree, R*-tree or quadtree, or to a geohash prefilter followed by a tree refine step. Predicate meaning lives in sidx-geom, not in any index (§3.2, P9).
  3. Descent. In sidx-rtree, a window search skips every child whose MBR is disjoint from the query rectangle and applies the real predicate to each object's own MBR at the leaves, never to a node's MBR. It returns Vec<DataId> (§3.2, §8.13, I4).
  4. How the tree got there. sidx-rtree owns an arena of RTreeNode, inserts with ChooseLeaf, and splits overfull nodes. sidx-rstar replaces the choose and split steps and adds forced reinsertion through the SplitStrategy enum. sidx-bulk builds a whole tree at once by sort-tile-recursive (STR) packing (§3.2).
  5. Nearest neighbours. sidx-knn runs a best-first search over a min-heap keyed by distance to each box (§3.2).
  6. Disk. sidx-persist writes each node into a fixed-size page behind an LRU cache, reached through a NodeStore trait so tests can swap in a Vec-backed store (§3.2).
  7. Checking. sidx-oracle answers the same queries by linear scan; a discrepancy is always a bug in the index (§3.2, I4, I5). sidx-cli offers build, insert, query, knn and bench (§3.2).

Window is an alias for Intersect here (§3.2, §8.13). Contains is stated two ways: the query rectangle contains the object (§3.2, P9, Glossary, Phase 3 acceptance) versus "obj.mbr contains R" (§8.13). Both are stated here as written.

The core ideas

R-tree: boxes inside boxes, kept balanced (§8.1, §8.3, §8.15, I1, I2, I3)

Every node holds between m and M entries, apart from the root (I3, P7). Each entry is a bounding box plus either a child node or a data id. Leaves sit at level 0, and every parent's box covers everything below it (I1, I2, §8.1). A node is in one of four states: EMPTY, UNDER (fewer than m, triggers a repair), NORMAL, or OVER (M+1 entries, which never persists past the operation that caused it) (§8.3). A root split adds one level (§8.3, P3). Because search prunes on the stored box alone, a box that is too small silently loses results; a box that is too large only costs speed (P2, P11, MM2). I11 therefore requires containment at all times, even where I1's exact tightness has not yet been restored.

ChooseLeaf descends by least area enlargement, then smallest area (§8.5). The quadratic split picks the two entries that waste the most space if kept together, then hands out the rest to whichever group grows less (§8.6.1). The blueprint's own trace has M=3, m=1, three entries and a fourth arriving (§8.15). The waste (combined area minus both areas) is 1 for E1+E2, 41 for E1+E3, 56 for E1+E4, 28 for E2+E3, 41 for E2+E4 and 1 for E3+E4, so E1 and E4 become the seeds. E2 joins E1's group (enlargement 5 against 41) and E3 joins E4's (5 against 40). The result is two leaves with boxes [0,0,3,3] and [5,5,8,8] under a new level-1 root whose box is [0,0,8,8] (§8.15, which also checks I1, I2, I3 and I7). One printed figure is off: §8.15 gives 41 for E2 joining the second group, which does not match the union box it names, [1,1,8,8] (area 49 in its own PickSeeds lines).

Delete runs CondenseTree: walk up from the leaf, remove any node under m, collect its entries, reinsert them at their own level, and collapse a root that is left with a single child (§8.7, P7). I7 requires that no object is lost or duplicated across any of this.

R*-tree: pay at insert time to get less overlap (§8.4, §8.5, §8.6.2, P4, MM3)

Query cost depends on how many boxes overlap the query, not on how many results come back (MM3). R* attacks overlap in three ways (§3.2, P4):

  1. Choose-subtree. When the children are leaves, pick the child whose overlap with its siblings grows least, with area enlargement as tie-break. Higher up, use area enlargement (§8.5).
  2. Split by margin first. Sort by each axis, add up the perimeters of the two groups over all split points, pick the axis with the smallest sum, then pick the split point with least overlap and break ties by area (§8.6.2).
  3. Forced reinsertion. On the first overflow at a level during one insert, remove the p entries farthest from the node's centre (p is 30% of M) and insert them again instead of splitting. A per-level flag limits this to once per level per insert, which is what stops an endless loop (§8.4, ADR-08, FM-9). The blueprint differs on which entries: "farthest" (§8.4, P4, Glossary) versus "the p closest-to-center entries" (§3.2); P4 also gives p = ⌈0.3×(M+1)⌉.

STR bulk loading: sorting instead of inserting (§8.8, P6, MM6)

For data known up front, the slice count is S = ceil(sqrt(n / M)). Sort all boxes by x-centre, cut them into S vertical slices, sort each slice by y-centre, pack consecutive groups of M into leaves, then repeat on the leaf boxes until one root remains (§8.8). With n = 10 million and M = 50 the blueprint gets 448 slices (Capacity Model item 12). The pay-off claimed is higher occupancy and a faster build than repeated insertion (P6, MM6). The cost is that all n objects must be in memory at once, and a tree built this way degrades as inserts accumulate, so the stated convention is to rebuild or switch to a dynamic tree (P6). Ties in both sorts are broken by DataId, so the same input always yields the same tree (P12, I10).

Best-first kNN: always expand the closest unexplored box (§8.9, §8.10, I5, I6, MM4)

MINDIST(p, R) is the distance from point p to the nearest point of box R. Clamp p's coordinates into R on each axis and measure; the answer is 0 when p is inside (§8.10). MINMAXDIST(p, R) is an upper bound on how far the nearest object inside R can be (§8.10, I6). The search keeps a min-heap of boxes ordered by MINDIST and a size-k max-heap of the best results so far. It pops the closest box; if that box's MINDIST is already beyond the current k-th result, it stops. Leaf entries compete for the result heap, and internal nodes push their children (§8.9). Ties break by DataId ascending (P5, I5). The pruning is sound only because MINDIST never exceeds the true distance (I6). The blueprint is inconsistent about MINMAXDIST: §8.9 says that if a node's MINMAXDIST is below the current k-th distance, at least one object there is definitely closer, while P5 says a node is skipped when the k-th distance is already below that node's MINMAXDIST. Both are stated as written.

Quadtree: cut space into four, repeatedly (§8.12, §3.2, I9)

A PR quadtree (point-region quadtree) splits a region into four equal quadrants at the midpoints: mid_x = (x1+x2)/2, mid_y = (y1+y2)/2 (§8.12). A leaf holds a bucket of points. When it exceeds capacity it splits into four children and redistributes (§3.2). I9 requires that the four children tile the parent with no gap and no overlap. A point exactly on a split line goes to the lower-index quadrant (§8.12). Unlike the R-tree it is not height-balanced (P3). Many identical points would split forever, so depth is capped and the collocated points pile up in one leaf at the cap (§3.2, §8.17, T13). The depth cap default is 32 (T13).

Geohash: a string prefix is a box (§8.11, I8, I12, MM7)

A geohash interleaves longitude and latitude bits, even positions longitude and odd positions latitude, most significant first, and writes 5 bits per character in a 32-letter alphabet that skips a, i, l, o (§8.11). Precision runs from 1 to 12 characters, so 60 bits at most (§3.2, T8). Decoding gives the cell rectangle. Longer hashes are smaller cells inside the same parent cell (§3.2, I8, I12). A rectangle query becomes a set of prefix ranges that any ordered key-value store can scan (§3.2, MM7). Neighbour cells need explicit boundary handling, including wrap-around at ±180° longitude (§8.11, §8.17). Precision-12 cell size is given three ways: 3.7 mm by 1.9 mm (§3.2), about 37 mm (Capacity Model item 11), under 0.04 m (Phase 10 acceptance).

The trade-offs — where engineers disagree

Node storage: a slab arena (ADR-06, MM8)

Chosen: the slab crate, which gives O(1) insert and remove with stable NodeIds (§9). Rejected: a raw Vec, which needs remapping on delete, and a typed arena. When the rejected choice is right: a raw Vec for append-only, bulk-built trees with no deletes, where compaction is free and id stability does not matter (§9). The blueprint is not uniform here: §8.18 describes an arena with push and swap-remove plus a remapping table, then points at "ADR-09" for the slab preference, while ADR-06 is the slab entry and ADR-09 is the kNN entry (§8.18, §9). I10 also speaks of a Vec-based arena.

Split default: R* (ADR-07)

Chosen: SplitStrategy::RStar by default, with quadratic and linear kept for comparison benchmarks, because it measurably reduces query fan-out (§9). Rejected: only quadratic, only linear. When the rejected choice is right: linear split for write-heavy ingest such as logging, where split cost dominates; quadratic where overlap is already inherently low (§9).

kNN algorithm: best-first (ADR-09, MM4)

Chosen: best-first branch and bound (Hjaltason and Samet 1999), exact, with the tightest known lower bound and better cache behaviour than depth-first for k above 1 (§9). Rejected: depth-first incremental search and approximate nearest neighbour. When the rejected choice is right: depth-first under tight memory, since it avoids a heap that grows with visited nodes; approximate search at high dimension or where approximate neighbours are acceptable (§9, portfolio item #255 in §1.2).

Geohash alphabet: standard base32 (ADR-13)

Chosen: Niemeyer's base32 alphabet, for compatibility with PostGIS, Elasticsearch and Redis and for prefix search in any sorted store (§9). Rejected: Morton (z-order) codes and Hilbert curves. When the rejected choice is right: Hilbert encoding when linear-order spatial clustering matters more than string-prefix interoperability and no external database interop is needed (§9).

Concurrency: single-threaded core (ADR-15)

Chosen: a single-threaded core with no async in library crates and an optional Arc<Mutex<>> wrapper in the CLI; mutation is not trivially parallel, and users can run query sets in parallel themselves (§9, §1.3). Rejected: Rayon parallel queries, async Tokio. When the rejected choice is right: Rayon for read-only analytical batches at high core counts; Tokio when the index sits behind a network service with many I/O-bound clients (§9). Other parts of the blueprint speak differently: the Comparative Architecture table and Scalability Analysis describe single-writer, multi-reader locking (RwLock<Arena>), while §1.3, §4.1 and the Deferred Features Register put multi-reader support in the future.

Roads not taken

A kd-B forest of immutable segments (A1, Alternative Architectures): buffer, write immutable segments, merge periodically. It wins for append-mostly, high-ingest data where rebuilding beats in-place mutation (Lucene/Elasticsearch BKD). It is rejected because this design targets dynamic insert and delete with low-latency updates (§4.1).

Space-filling curve plus B-tree (A2): key every point by its interleaved bits and range-scan the curve. It wins when an ordered key-value store already exists and spatial lookup must come with no new engine (MongoDB S2, geohash in Redis). It is rejected as the core because a query box maps to many disjoint curve ranges and exact kNN is awkward; geohash stays a secondary, interoperability layer (Phase 10).

Fixed grid / uniform cells (A3): hash each point into a cell. It wins for uniformly dense point data over a known extent, such as collision systems or particle simulations. It is rejected because real geographic data is skewed and range queries touch many empty cells.

R+-tree clipping (A4): cut an object that straddles a boundary and store it in both partitions. It wins for static, read-heavy workloads where removing multi-path descent beats storage and update cost. It is rejected because clipping duplicates objects (violating I7) and complicates delete.

Deferred register (Deferred Features Register): seven items wait for a trigger, among them SIMD box operations (a profile hotspot at 10 million objects or more), concurrent readers (read throughput is the bottleneck), geodesic distance, and Hilbert-curve packing (measured gain over STR).

What must never be false

Twelve invariants (§7). The audit for I1 is test-only; I11 is the production-safe check.

  • I1, tight boxes. Each node's box equals the union of its children's. Tests recompute unions and compare; mbr_mismatch_count counts mismatches.
  • I2, balance. All leaves at level 0. A walk expects one distinct leaf level; leaf_level_histogram should show only key 0.
  • I3, occupancy. Non-root nodes hold m to M entries, asserted after every mutation in tests; underflow_node_count and overflow_node_count gauges track it.
  • I4, queries are complete and sound. Detected by the oracle and index results having an empty XOR; the counters are test-only.
  • I5, kNN is exact. Compared element by element with the oracle's sorted list for k of 1, 10 and 100.
  • I6, distance bounds. MINDIST <= true nearest distance <= MINMAXDIST, property-tested on 100 thousand random triples.
  • I7, no object lost or duplicated. Full-scan count before and after each mutation, plus a seen-set; object_count gauge.
  • I8, geohash round trip. Decode of an encode contains the point; a fuzz of 1 million random tuples checks it. Its text says the precision p+1 hash is a prefix of the precision p hash, while its own parenthetical and I12 make the shorter hash the prefix of the longer (§7, I12).
  • I9, quadtree partition. Four children tile the parent exactly; asserted after every subdivision.
  • I10, determinism. Build twice, serialize, compare bytes in CI; no runtime telemetry.
  • I11, parent boxes contain children. The weaker form of I1 (containment, not equality), cheap enough for production; parent_containment_violation_count above zero is a top-priority bug.
  • I12, geohash prefix nesting. Any string with prefix s decodes inside decode(s), tested on random strings that never came from a real coordinate, which separates it from I8.

What breaks in production

The blueprint labels failure modes F1 to F14 in its "Failure Modes and Recovery" table. This explainer writes them FM-1 to FM-14 (F1 is FM-1, and so on). FM-1 to FM-4, FM-8, FM-10 and FM-12 list "None" as automatic recovery.

FM-1: queries miss objects (I1 broken). Symptom: a window query omits objects known to be in range and the oracle disagrees. Cause: a split or condense step failed to propagate a box change upward. Detection: post-operation invariant check in debug builds and the Phase 14 differential test. Recovery: rebuild the index from source data, then fix propagation and add a regression test.

FM-4: wrong kNN results (I5 broken). Symptom: top-k distances are not non-decreasing, or the oracle disagrees. Cause: a MINDIST formula error, a heap-ordering bug or inconsistent tie-breaking (T14 adds that float rounding can make MINDIST negative, answered by clamping to 0). Detection: the Phase 14 differential kNN test. Recovery: rebuild, fix, and add a monotonicity property test.

FM-5 and FM-11: corrupt or truncated page file. Symptom: page_crc_mismatch at startup and the index refuses to open. Cause: disk corruption, or an OS crash during a multi-page write without fsync. Detection: a CRC check on every page load plus the magic and version header. Recovery: restore from a backup snapshot; the long-term fix is staged writes with an atomic rename. The blueprint's page layout in §8.14 has no CRC field, although T4 and FM-5 rely on one (§8.14, T4).

FM-7: quadtree depth explosion. Symptom: stack overflow, memory growth, or an insert that hangs. Cause: many identical points or zero-area bounds. Detection: the depth cap and the quadtree_max_depth_reached_total metric, with an alert when it is above zero. Recovery: the cap stores overflow in a leaf list, and the data should be de-duplicated upstream.

FM-9: forced reinsertion loop. Symptom: an insert never returns and the CPU sits at 100% with recursive reinsertion on the stack. Cause: the per-level reinsertion flag is missing. Detection: a test timeout and an iteration counter. Recovery: break on a second attempt at the same level, kill the operation, and rebuild with the standard R-tree. Both T6 and FM-9 credit "I10" for the one-per-level rule, but I10 is the determinism invariant in §7 (§8.4, T6).

FM-12: duplicate ids in a result. Symptom: one DataId appears twice. Cause: a leaf reached through two overlapping parent boxes. Recovery: the row leaves open whether sidx-query or the caller removes duplicates. §4.2 gives duplicates a "Zero" tolerance yet puts de-duplication on the caller, and I5 requires "no duplicates" for kNN (§4.2, I5).

Threats a reader should know (Threat Model table):

  • T1: a NaN or infinite coordinate poisons box unions and distances. Point::new rejects non-finite values and no state changes (P8 names only NaN, and calls infinity a valid sentinel).
  • T4: malformed page bytes from truncation or bit flips. CRC and header checks abort the load, and recovery is a rebuild or backup.
  • T7: Knn(p, k=10^8) exhausting memory, answered by a configurable cap on k (default 10^6).
  • T9: a panic part-way through an insert leaving the arena half-changed, answered by mutating scratch state first and swapping on success.

  • Timeline. §1.8 says 4 to 6 months for the full project; Appendix B's total row says about 12 weeks.

How it compares

  • PostGIS GiST generalized the R-tree into a framework of callbacks (penalty, union, consistent), so one engine serves R-tree, B-tree and full-text indexes. That fits a database that needs many index types inside one transactional engine (Comparative Architecture).
  • SQLite R*Tree stores the tree as ordinary rows in a virtual table and inherits SQLite's transactions for free. It fits embedded single-file deployments, and offers range queries only, with no kNN (Comparative Architecture).
  • Lucene/Elasticsearch BKD-tree is an immutable, merge-on-write kd-B forest instead of a mutable R-tree, which fits append-mostly data at very high ingest (Comparative Architecture, A1).
  • MongoDB 2dsphere (S2) maps the sphere to a one-dimensional Hilbert order of cells stored in a B-tree, which suits curved-earth queries where flat boxes distort near the poles (Comparative Architecture, A2).
  • DuckDB spatial builds a static R-tree over column batches and pushes spatial tests into the vectorized scan, which suits bulk spatial joins on data loaded once (Comparative Architecture).

Questions to test yourself

  1. Best-first kNN (Phase 8) visits fewer nodes than depth-first (P-R3) yet both are correct — which invariant (I6) makes the pruning sound, and why? — Hint: §8.9, §8.10 and ADR-09.
  2. Why can't the single-writer/multi-reader model (ADR-15, §4) be relaxed to multi-writer without redesigning split propagation (Phase 4, I2)? — Hint: §8.3's state machine and MM5; note the concurrency wording differs between ADR-15 and the Comparative table.
  3. Geohash prefix scan misses results across cell boundaries (Phase 10, MM7). Derive the regime in which an application must fall back to the R-tree (Comparative). — Hint: §8.11 and §8.13's geohash column, plus I12 for what prefix nesting does guarantee.
  4. Reconcile STR's 95% occupancy target with quadratic-split's 50% guarantee (§4, ADR-07): which workload makes each correct, and how does occupancy feed back into height (Capacity Model)? — Hint: P6, §4.1's occupancy rows and Capacity Model items 3 and 6.
  5. How does forced reinsertion (p=30%, ADR-08, P-R2) reduce overlap without infinite looping? What role does the per-level flag play (Phase 6)? — Hint: §8.4, T6 and FM-9.

If you only remember three things

Every box in the tree must cover everything beneath it, because search trusts the stored box and silently drops what it cannot see (P2, P11, I11). Query cost is the number of boxes that overlap the query, so R* pays at insert time to shrink overlap and STR sorts at build time (MM3, MM6). Every answer is checked against a brute-force scan, because a wrong index returns a shorter list, not an error (P1).

Words used here

  • MBR: minimum bounding rectangle; the tightest axis-aligned box around some objects (Glossary).
  • R-tree: a height-balanced tree of boxes, like a B-tree for spatial data (Glossary, §2.2).
  • R-tree*: an R-tree with overlap-aware choose, split and forced reinsertion (Glossary).
  • Forced reinsertion: on first overflow, re-insert the p farthest entries instead of splitting (Glossary, §8.4).
