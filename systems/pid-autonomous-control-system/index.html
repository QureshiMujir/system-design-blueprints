In one paragraph

This is a control-systems engine written as a Rust library (§1). It builds the feedback loop: each tick it takes a state estimate and a reference and computes a bounded actuator command in fixed-step time (§1). It covers PID with the protections real hardware needs, auto-tuning, state-space design, a Kalman filter, linear model-predictive control and two path-following laws (§1). The same crates compile into firmware behind a real-time loop and into a host command-line tool, ctrlctl, for simulation, tuning and analysis (§1). Controls, robotics, embedded and autonomous-vehicle engineers run it (§1). Perception, path planning and heavy estimation are out of scope (§1).

The problem, concretely

You have a thermostat, a motor drive or a car's steering, and you want its output to follow a target (§2, §1). The obvious loop pushes back in proportion to the error, to its running sum and to its rate of change (Glossary "PID"). The blueprint's point is that a loop that "worked in sim" is not the same as one that "has 6 dB / 45° to spare" (§2). Each shortcut breaks in a different place:

  • Differentiating the error. A step in the target makes the derivative term spike (Principle 12, Glossary "Derivative kick"). The fix is to differentiate the measurement and low-pass it (§8.2).
  • Ignoring the actuator limit. The integral term keeps charging while the output is pinned, then overdrives it on release: lockout, limit cycling or dangerous overshoot (Principle 2, MM2).
  • Designing in continuous time, running in discrete time. A design sampled with forward Euler can be unstable in firmware though a fine-step simulation looked fine (MM3, Principle 4). The blueprint's own self-test is a Ziegler-Nichols PID that oscillates once the deployed Δt is 10 times larger (Hard Q1).
  • Letting the loop run late. The derivative and integral terms see the wrong Δt and the loop can diverge, so the deadline is a hard invariant (Principle 8, MM8, I3).
  • Letting a NaN through. A division by zero, an overflow or an ill-conditioned matrix can put a non-finite number on the actuator (Principle 14, I11, Failure Modes and Recovery).

The blueprint answers with a fixed-step executor, an always-on output stage, correct discretization, stability checks before deployment and a safe state for every fault (Principles 1, 3, 4, 7, 13).

How it works, end to end

One tick of the loop runs through the boxes of §3's diagram. The diagram below is the online half of it, lightly shortened:

 reference/trajectory r[k]
        │
        ▼
   feedforward (ctrl-ff) ──u_ff──┐
        │                         ▼
        └──► summing junction (e = r − x̂) ──► CONTROLLER: PID | LQR | MPC | track
                                                (ctrl-pid | ctrl-lqr | ctrl-mpc | ctrl-track)
                                                         │ u_raw
                                                         ▼
                                  actuator saturation + rate limit (ctrl-core)
                                                         │ u (applied)
                                                         ▼
                        PLANT: sim ẋ = f(x,u) via RK4 (ctrl-sim)  |  real: HIL (deferred)
                                                         │ y
                                                         ▼
                                              sensors (+ noise, in sim)  ──► z
                                                         │
        x̂ (state estimate) ◄── ESTIMATOR: Kalman / Luenberger (ctrl-kf / ctrl-lqr)
 (the whole region above runs inside the real-time loop, ctrl-rt, at fixed Δt)

The offline half (ctrl-sim plant model, ctrl-tune, synthesis in ctrl-ss/ctrl-lqr/ctrl-mpc, analysis in ctrl-bench/ctrl-cli) sits above a "deploy boundary"; params and gains are exported across it (serde), and analysis is the gate before deploy (§3).

One tick, per §8.14:

  1. Wait and sample. ctrl-rt waits for the fixed-step deadline and records wake_jitter, then sensors give z[k] (in simulation y plus configurable noise, bias or dropout) (§8.14, §3).
  2. Estimate the state. The estimator turns the last command and z[k] into x̂[k], in a block separate from the controller (Principle 5, §3), in ctrl-kf and ctrl-lqr.
  3. Fetch the reference r[k], possibly a trajectory point from the motion planner (§8.14, §2), and add optional feedforward from ctrl-ff, a model-based open-loop term (§3, §8.14).
  4. Run the control law. Every law implements Controller::update(ref, meas, dt) -> u, so PID, LQR, MPC and the trackers swap without touching the loop (Principle 15, §3).
  5. Saturate, rate-limit and feed back. The output passes ctrl-core's saturation and rate limit, then anti-windup is fed back u[k] − u_raw (§8.14, I1).
  6. Check, apply, account. is_finite on u[k] and enforcement of I1 (I11); apply u[k] to the plant; record tick_compute_us, check the deadline (I3) and emit telemetry (§8.14).

Underneath sit ctrl-signal (discretizers, filters) and ctrl-core (Vector<N>, Matrix<R,C>, saturation, errors); ctrl-track follows a planner's path by pure pursuit or Stanley (§1, §2, §8.11).

The core ideas

A PID that survives hardware: filtered derivative on the measurement (§8.2)

The three terms are a push proportional to the error (P), a running sum of the error (I) and a reaction to how fast the measurement moves (D); together they are a PID controller. The blueprint's discrete update (§8.2) is:

e_p = b*r - y                     // proportional error, setpoint weight b
P   = Kp * e_p
I  += Ki * e * dt                 // anti-windup may modify this (see §8.4)
d_y = (y - y_prev)/dt             // derivative of the MEASUREMENT, avoids kick
D   = filter(D_prev, d_y, Kd, N, dt)   // first-order low-pass, N e.g. 8..20
u_raw = P + I - Kd*D_filtered
u     = rate_limit(saturate(u_raw))

The filter has time constant Tf = Td/N (§8.2). The same gains can be written in three forms (parallel, standard/ISA, series), all first-class (§8.2). The blueprint's worked example (§8.12): a plant G(s) = 2 e^{−0.5s}/(3s+1) (gain K = 2, time constant τ = 3, dead time L = 0.5), tuned by Ziegler-Nichols open-loop, gives Kp = 1.2·τ/(K·L) = 1.2·3/(2·0.5) = 3.6, Ti = 2L = 1.0, Td = 0.5L = 0.25. The closed-loop step then shows about 10–20 % overshoot, settles in roughly 6–8 s and has zero steady-state error. A refined tuning (lower Kp, larger Ti) gives at most 5 % overshoot and a longer settle (§8.12, §4).

Anti-windup: the fuse on the integrator (§8.4, Principle 2, I2)

An integrator never forgets. While the actuator sits at its limit the plant stops responding, but the integrator keeps charging; when the limit releases, the stored charge overdrives the output (MM2). Two guards exist (§8.4):

  1. Clamping (conditional integration): freeze the integrator when u_raw is saturated and the error would push it further into saturation.
  2. Back-calculation: add (u − u_raw)/Tt to the integrator input, where Tt is a tracking time constant (rule of thumb Tt ≈ √(Ti·Td) or Ti/2…Ti). While saturated, u − u_raw is non-zero and unwinds the integrator smoothly.

Both bound the integral term (I2). Back-calculation recovers more smoothly and is the default; clamping is simpler and cheaper (§8.4, ADR-8). A rate limit is a nonlinearity the linear margin calculation does not see, so a design can pass its margin gate and still oscillate (MM7).

Discretization: the continuous design must survive sampling (§8.3, I7)

A computer controls at fixed instants, so a design made in continuous time has to be converted (discretization). The choice of conversion decides whether it stays stable (§8.3, Principle 4):

Method Map What the blueprint says
Forward Euler s ← (z−1)/Δt cheap, explicit; poles can leave the unit circle
Tustin (bilinear) s ← (2/Δt)·(z−1)/(z+1) preserves stability; warps frequency (prewarp fixes one frequency)
Zero-order hold (ZOH) A_d = e^{AΔt} exact for state-space under piecewise-constant input; needs a matrix exponential

MM3 says forward Euler sends some stable poles outside the unit circle for any Δt, and Tustin maps the whole stable half-plane onto the open unit disk. The same entry says forward Euler maps that half-plane to a circle of radius 1/2 centred at (1/2, 0), which lies inside the unit circle, while §8.3 calls backward Euler "always stable" and forward Euler able to "destabilize"; the blueprint leaves this unreconciled (MM3, §8.3). Phase 2's tests: ZOH of ẋ = −x at Δt = 0.1 gives A_d = e^{−0.1} to 1e-12, and Tustin of 1/s matches the bilinear formula exactly (Phase 2). A design-time and runtime check, Δt ≤ τ_min/10, catches sampling that is too slow (I12).

From a model to a gain, and from measurements back to the state (§8.5–8.8)

State-space writes the plant as ẋ = A x + B u, y = C x + D u (§8.1). Before designing anything, check that the inputs can steer every state: the plant is controllable iff rank[B, AB, …, A^{n−1}B] = n, and observable iff the matching matrix built from C has rank n (§8.5, Principle 10). This is a precondition, not an afterthought: Ackermann's formula and the Riccati equation both return a gain for a rank-deficient pair, and that gain cannot stabilize the uncontrollable mode, so the loop diverges along that eigenvector (MM10).

  • Pole placement (Ackermann, single-input): K = [0 … 0 1]·𝒞⁻¹·φ_d(A), where φ_d is the desired characteristic polynomial evaluated at A (§8.6). Phase 7's demo places poles at "-2,-3,-4,-5" to balance a linearized cart-pole (Phase 7).
  • LQR (linear-quadratic regulator): minimise J = ∫(xᵀQx + uᵀRu) dt with Q ⪰ 0, R ≻ 0; the optimum is u = −Kx, K = R⁻¹BᵀP, with P solving the algebraic Riccati equation AᵀP + PA − PBR⁻¹BᵀP + Q = 0 (§8.7).
  • Observer: x̂̇ = A x̂ + B u + L(y − C x̂), so the error obeys ė = (A−LC)e. Designing L is pole placement for (Aᵀ, Cᵀ) (duality), so the same tools work (§8.8, MM4).
  • Separation: K and L are designed independently and then composed (LQG), which is why the observer can later be swapped for a Kalman filter without touching K (§8.9, Principle 5).

Cost per tick (C2, §4): at n = 16, m = 4, 64 multiplies for Kx̂ plus about 256 operations for the observer, roughly 1.6 µs against the 10 µs LQR budget.

The Kalman filter and the question "can I trust my estimate?" (§8.9, I6)

When the sensors are noisy, the estimator predicts with the model and then corrects with the measurement (Kalman filter) (§8.9):

predict:  x̂⁻ = A x̂ + B u ;         P⁻ = A P Aᵀ + Q_k
update:   S = C P⁻ Cᵀ + R_k ;       K = P⁻ Cᵀ S⁻¹
          x̂ = x̂⁻ + K(z − C x̂⁻) ;   P = (I − K C) P⁻   (Joseph form for PSD safety)

The Joseph form keeps P symmetric and positive semi-definite (§8.9). The filter is optimal only for a correct linear model with Gaussian noise; when that fails, the normalized innovation squared (NIS) leaves its χ² distribution: persistently above its bound is what MM6 calls under-confident (Q/R too small), below is over-confident (MM6). Cost: the dominant term is two n×n×n products, 2n³; at n = 8 that is 1024 operations, about 5 µs; at n = 16 it is 8192, about 41 µs, over the 20 µs budget, so the blueprint falls back to a precomputed steady-state gain (a matrix-vector product of about 256 operations, about 1.3 µs) (C3, M3). The filter stays minimal and controller-facing; full sensor fusion is another project (§1, §2).

Linear MPC: re-plan every tick, apply only the first move (§8.10)

Model-predictive control (MPC) stacks the model over a horizon of N steps, chooses the input sequence that minimises Σ(xᵀQx + uᵀRu) + x_NᵀP_f x_N under limits, applies only the first input, shifts, and solves again next tick (receding horizon) (§8.10). Eliminating the states gives a condensed QP over the inputs alone: min ½ Uᵀ H U + (x₀ᵀFᵀ) U subject to A_c U ≤ b_c (§8.10). Starting each solve from the previous solution (warm start) keeps iteration counts low, and a terminal cost P_f taken from the Riccati solution gives nominal stability (MM5, §8.10).

The deadline is the hard part, so the blueprint caps solver iterations. With N = 20 and m = 2 there are D = N·m = 40 decision variables; H is 40×40 = 1600 f64 values, 12.8 KB (C4). One ADMM iteration costs about 2D² = 3200 operations, about 16 µs; with a 200 µs solve budget the cap is floor(200/16) = 12 iterations, while warm-started steady-state solves take 3–8 (C6). If the QP is infeasible, the controller softens constraints, falls back to the last feasible solution, then to the safe state (I10). The cap converts a latency-unbounded algorithm into a deadline-safe one at the cost of optimality (MM8, Threat Model "Compute/deadline budget").

The trade-offs — where engineers disagree

Language: Rust with a no_std core (ADR-1)

Chosen: Rust 2021, #![no_std] core with alloc optional, for safety, determinism and embeddability: no garbage collector, const generics for fixed-size math (ADR-1). Rejected: C/C++, Ada/SPARK, MATLAB codegen. When the rejected choice is right: C/C++ when integrating into an existing safety-certified codebase with qualified toolchains; Ada/SPARK when formal proof of absence of runtime errors is a certification requirement; MATLAB codegen for rapid algorithm prototyping by a controls team without embedded-software expertise (ADR-1).

Discretization default: Tustin (ADR-5)

Chosen: Tustin (bilinear) with optional prewarp, and ZOH for state-space, because it preserves the stability margins designed in continuous time (ADR-5, Principle 4, I7). Rejected: forward Euler as the default. When the rejected choice is right: when the loop is so fast that Δt is much smaller than the dominant time constant and the margin loss is negligible, so that the simplicity of s←(z−1)/Δt eases a safety audit; also for explicit integrators in the sim harness, where Tustin's extra accuracy is irrelevant next to RK4's (ADR-5).

QP solver: own ADMM plus active-set, OSQP optional (ADR-6)

Chosen: a dependency-light ADMM and active-set solver in ctrl-mpc, with an optional OSQP binding on the host, for a no_std core that is predictable, warm-startable and free of a C dependency (ADR-6). Rejected: a mandatory OSQP or qpOASES dependency. When the rejected choice is right: OSQP when the horizon is large (N·m > 200) and the dense condensed form becomes ill-conditioned, because its sparse ADMM scales better; qpOASES for low-dimensional, tightly constrained problems where the active-set method's exact solution in few iterations beats ADMM's approximate convergence (ADR-6).

Executor: an own fixed-step loop, not async (ADR-7)

Chosen: a fixed-step loop in ctrl-rt (busy-wait or timer-fed) with a pluggable clock trait, because async scheduling latency is nondeterministic and control needs a hard fixed step (ADR-7). Rejected: tokio/async. When the rejected choice is right: host-side orchestration such as the CLI's async I/O, log streaming and Prometheus export, where jitter is irrelevant; it is the right choice for all tooling that wraps the loop, just not inside it (ADR-7).

Roads not taken

Event-driven async controller (A1) wins for supervisory control with millisecond-to-second latency, but a queued task can wake late, breaking I3 and the fixed-Δt assumption (A1, ADR-7).

Centralized sparse MPC (A2) wins on strongly coupled multi-input plants such as refinery sections; it is rejected because the target is one actuator with n ≤ 32 and it needs a sparse solver with C FFI, against ADR-6 (A2).

Indirect adaptive control (A3) wins when the plant drifts too fast for manual retuning; rejected: stability needs persistent excitation and Lyapunov analysis beyond scope; gain scheduling and relay tuning cover the practical cases (A3).

Multiple-model observer bank (A4) wins under abrupt sensor or mode failure; it is rejected because it multiplies tick cost by the filter count and belongs in the sensor-fusion project (A4, §2).

Deferred register: nonlinear control, adaptive/robust control, nonlinear MPC, hardware-in-the-loop, system identification beyond FOPDT and a GUI are all out of scope, each with an un-defer trigger such as "Physical hardware target identified and HIL interface spec provided" (Deferred Features Register, §1).

What must never be false

All twelve are in §7; the first phrase after each ID is how the system notices a violation.

  • I1: u_applied in [u_min, u_max], |u[k]−u[k−1]| ≤ Δu_max. Post-clamp assert; sat_active, rate_active.
  • I2: the integral term is bounded. |I| ≤ I_max checked each tick; integral_value, windup_events.
  • I3: Δt is fixed and the deadline met. tick_compute_us, wake_jitter_us; deadline_miss_total.
  • I4: closed-loop poles are stable. Eigenvalue check on A−BK; max_pole_real, spectral_radius.
  • I5: zero steady-state step error with integral action. |e_ss| ≤ 1e-6 after settling; steady_state_error.
  • I6: observer error is stable and converges. Eig of A−LC, P bounded and PSD; estimator_residual, trace_P.
  • I7: discretization preserves stability. Continuous vs discrete poles compared; pole drift logged.
  • I8: output is deterministic given (init, reference, params, seed, scalar type). Re-run and hash u[k].
  • I9: no output jump on a mode or gain switch. |u[k]−u[k−1]| ≤ rate limit there; mode_switch_events.
  • I10: the MPC QP is feasible or has a fallback. Solver status each solve; qp_status, qp_iters.
  • I11: no NaN or Inf reaches the actuator. is_finite check before output; non_finite_events.
  • I12: sampling is fast enough. The Δt ≤ τ_min/10 heuristic; nyquist_margin.

What breaks in production

Each paragraph is from the Failure Modes and Recovery table.

  • Integral windup. Symptom: a large overshoot after sustained saturation. Root cause: weak or missing anti-windup, or Tt set wrongly. Detection: integral_value rising while sat_active. Recovery: clamping or back-calculation bounds the integral (I2); the manual fix is re-tuning Tt.
  • Loop overrun. Symptom: tick_compute_us above budget and the loop lagging. Root cause: a heavy MPC solve or host scheduling. Detection: deadline_miss_total and the jitter histogram (I3). Recovery: the iteration cap, shedding optional work and the safe state; pin a core to the loop or shorten the horizon.
  • Observer or filter divergence. Symptom: x̂ drifting from the truth. Root cause: wrong model or Q/R, a missed nonlinearity or a sensor fault. Detection: estimator_residual and NIS (I6). Recovery: reset P, gate outliers, predict-only on dropout; re-tune Q/R.
  • QP infeasibility. Symptom: qp_status = Infeasible and no command. Root cause: conflicting or tight constraints, or a disturbance outside the admissible set. Detection: the solver flag (I10). Recovery: soften, then use the last feasible solution, then the safe state.
  • Non-finite values. Symptom: garbage output. Root cause: division by zero, overflow or ill-conditioning. Detection: the per-tick is_finite guard (I11). Recovery: a safe output, fault latched.
  • Bump on switch. Symptom: a Δu spike at a mode or gain change. Root cause: missing preload or an unreset filter. Detection: Δu at mode_switch_events (I9). Recovery: bumpless preload sets the integral so u_raw matches u.

Threats to know (Threat Model; its trust boundary is the plant/sensor edge plus reference and config):

  • Reference injection: an attacker drives the actuator somewhere damaging. Mitigated by range and rate validation and a physical-limit clamp independent of the controller.
  • Sensor spoofing: falsified measurements hide a fault. Mitigated by Kalman innovation gating (NIS), plausibility checks and redundant-sensor cross-checks.
  • Deadline exhaustion: crafted input inflates MPC iterations. Mitigated by a hard iteration cap and a bounded horizon, with fallback from MPC to LQR and then the safe state.
  • Unsafe relay auto-tune: a relay experiment on an unguarded live plant swings past the safe envelope. Mitigated by saturation, a supervisor, bounded relay amplitude and abort on breach.

How it compares

  • OSQP chose a general sparse ADMM formulation that scales to thousands of variables without condensing, and it ships only a solver, not a control law. That fits long horizons (N·m > 200); the blueprint binds it optionally (ADR-6, Comparative Architecture Table).
  • PX4 Autopilot chose a cascaded PID hierarchy (position, velocity, attitude, rate) on NuttX with uORB messaging, and no MPC. That works for multirotors whose dynamics separate cleanly by timescale; this blueprint stays framework-free and law-agnostic (Comparative Architecture Table).
  • ros2_control chose a plugin controller lifecycle (configure, activate, deactivate) inside the ROS 2 executor, which is not hard-real-time by default. That suits robots already in ROS 2 that swap controllers at runtime; the blueprint's Controller trait borrows the lifecycle idea without the coupling (Comparative Architecture Table).
  • acados chose nonlinear MPC with the real-time-iteration scheme and code generation. That fits research or production on strongly nonlinear plants; this blueprint defers nonlinear MPC and stays linear, allocation-free and easier to audit (Comparative Architecture Table, Deferred Features Register).

Questions to test yourself

  1. A PID controller is tuned with the Ziegler–Nichols open-loop method on a FOPDT plant and performs well in simulation. After deployment, the loop oscillates. The Δt is 10× larger in the deployed firmware. What has failed, and which design principle and invariant were violated? — Hint: §8.3 and MM3; compare the invariant that compares continuous and discrete poles (§7).
  2. You are designing an LQR controller for a 4-state plant and the ARE solver returns a gain K without error. In closed-loop simulation the plant diverges along the second eigenvector. What is wrong, and which pre-design check would have caught this? — Hint: §8.5, §8.15 and MM10.
  3. You want to replace the Luenberger observer with a Kalman filter in an LQG design without touching the LQR gain K. Is this guaranteed safe? What theoretical property enables it, and what does the separation principle require for the swap to maintain stability? — Hint: §8.8, §8.9 and Principle 5.
  4. A pure-pursuit controller at v = 5 m/s with L_d = 2.5 m oscillates on a lane-change maneuver. The same gains at v = 15 m/s are stable. Explain the mechanism and specify the correct fix in terms of the L_d scheduling law. — Hint: §8.11 and capacity item C12.
  5. A controller must run at 10 kHz for motor control (§4 "motor/power" rate). The MPC with N=20, m=2 has a warm-started solve time of 200 µs. Is MPC feasible at 10 kHz? What does the Back-of-Envelope Capacity Model say, and which control law should be used instead? — Hint: §4 loop-rate and per-tick-budget rows, C5, and the Scalability Analysis.

If you only remember three things

The loop is a fixed-step pipeline whose output stage (saturate, rate-limit, finite-check) is always on, so every law behind the one Controller interface reaches the actuator bounded and finite (§3, Principles 3 and 15, I1, I11). Each main hazard has a named defence and an invariant that detects it: windup has back-calculation and I2, discretization has Tustin or ZOH and I7, a missed deadline has an iteration cap and I3 (Principles 2, 4, 8). Design before you deploy: check controllability, solve for the gain, discretize, then pass a margin gate of 45° and 6 dB, because "worked in sim" is not evidence (Principles 7, 10, §4, §2).

Words used here

  • PID: a controller that adds a push proportional to the error, to its running sum and to its rate of change.
  • Saturation: the hard clamp of the command to the actuator's [u_min, u_max].
  • Anti-windup: a guard that stops the integral term from charging while the actuator is clamped.
  • Derivative kick: the output spike from differentiating the error across a setpoint step.
  • Bumpless transfer: switching mode or gains without a step in the output.
  • Discretization: converting a continuous-time design into a per-tick update (Tustin, ZOH, Euler).
  • Phase margin / gain margin: how much extra lag or gain the loop tolerates before instability.
  • Controllability / observability: whether the inputs can steer, and the outputs reveal, every state.
  • LQR: the state-feedback gain that minimises a quadratic cost of state error plus control effort.
  • Observer: a model-based estimator that rebuilds the state from the measured outputs.
  • Kalman filter: a recursive predict-and-correct estimator that is optimal for linear-Gaussian noise.
  • MPC / receding horizon: re-solving a constrained optimization every tick and applying the first move.
