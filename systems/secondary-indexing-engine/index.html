In one paragraph

A secondary indexing engine keeps a sorted lookup table (secondary key to primary key) up to date over records that a host database owns and keeps changing, so that lookups by that second key stay fast and consistent (§1). It is a Rust storage engine built from a write-ahead log, an in-memory sorted table, immutable on-disk files, background merging and Raft replication (§1, §3, ADR-01). It ships as an embedded library, a single-node daemon or a replicated cluster (§1). Its design targets are 250,000 point writes/sec and 500,000 point reads/sec (§4). Operators, storage engineers and integrators run it beside the host database, never in place of it (§1).

The problem, concretely

The host database owns the records and changes them constantly. The engine must keep a second, sorted view of them current while taking 250,000 mutations per second (§1, §4). Two obvious designs each fail on one requirement, and a crash at the wrong moment adds a third pressure.

The first is to update the index in place, as a B-tree does, under one lock manager. That gives read-your-writes for free, but the write budget of 250,000 ops/sec needs sequential appends, not in-place page rewrites under a shared lock (Alt A in §34, ADR-04). The second is to acknowledge the write and update the index later through a change stream, as DynamoDB's global secondary indexes do. That isolates write latency, but it gives up the "strongly consistent secondary indexes" that §1 lists as required, and it breaks the rule that an acknowledged write is immediately visible through every index it maintains (Alt B in §34, §31, I5, I7).

The third pressure is the crash. If the process dies in the middle of swapping a set of merged files in for the old ones, readers must still see a complete, consistent file set and never a partial one (§8.8, I2). And if a leader acknowledges a write before a majority of replicas hold it, a leader crash loses an acknowledged write (I7, §33 Q1). The blueprint is organised around those pressures: a log that is durable before anything is visible, files that are never edited after they are published, and a metadata log that makes file-set changes all-or-nothing (§3.2, MM1, MM2, MM4).

How it works, end to end

One request travels through the boxes of §3.1, written in code font. Where a crate in §1's Phase 0 list has a name that corresponds to a box, it is given in parentheses; the blueprint itself does not state this pairing.

 Client Applications (untrusted)
     |                |
 Query API      Admin API                  <- protocol boundary
     +-------+--------+
        Request Coordination                 <- concurrency isolation boundary
        |                        |
 Query Runtime           Mutation Runtime
 Snapshot Manager        WAL Manager       <- persistence boundary (fsync)
 Iterator Engine         Memtable Engine
        +----------+-------------+
             Segment Manager
 Compaction Scheduler | Bloom Filter Runtime | Manifest Runtime
             Persistent Segments (mmap)        <- storage boundary
             Replication Runtime             <- network boundary
             Peer Nodes (Raft group)

A write goes down the right-hand column (§3.1, §3.2):

  1. Query API decodes the request, runs the authentication hooks (mTLS plus scoped token) and never touches storage directly. Admin API (admin-api) handles compaction control and repair on its own task pool, so an admin storm cannot starve queries (§3.2, I6).
  2. Request Coordination applies admission control and rate limiting, and every backpressure signal starts or ends here (§3.2, P4).
  3. Mutation Runtime assigns the sequence ID, a per-shard counter that only goes up, and fixes the order of writes (§3.2, I4, §11).
  4. WAL Manager (wal-engine) appends the record to the log and fsyncs it (§3.2, §13.2).
  5. Memtable Engine (memtable-engine), a lock-free skiplist, takes the record into memory. When it fills, it is frozen and flushed into a new file (§3.2, §14.2, §8.5).
  6. Segment Manager (segment-engine) owns those immutable files. Manifest Runtime (manifest-runtime) records which files are live. Compaction Scheduler (compaction-runtime) merges files in the background (§3.2, §17.2, §18.2).
  7. Replication Runtime (replication-runtime) ships the log to peers, and the write becomes visible only after a quorum acknowledges it (§3.2, §8.7, I7).

A read goes down the left-hand column (§8.6): client, Query API, snapshot acquire, iterator planning, bloom prefilter, segment merge, visibility filter, response encode. Snapshot Manager pins the generation the query will see, Iterator Engine (iterator-engine) merges every source behind one trait, and Bloom Filter Runtime skips files that cannot hold the key (§3.2, §8.6, §16.2). query-runtime does the planning and never imports a memtable- or segment-specific type (§19.2, §16.3). Metrics and traces come from metrics-runtime and tracing-runtime, and admin-api and operator-cli are the operator surfaces (§1, P6).

The core ideas

Durability before visibility: the write path (§8.7, I1, I7, MM1)

The leader's order is fixed at five steps: WAL append, fsync, replication enqueue, quorum acknowledgment, visibility publication (§8.7). No mutation may be query-visible before its log frame is fsynced (I1), and a client is told "done" only after fsync and a Raft quorum (I7). MM1 calls durability and visibility two clocks that compose in one direction only: a "fast path" that publishes before the fsync callback brings back acknowledged-write loss (MM1).

A log frame is a header (CRC32C checksum plus length) followed by the protobuf-encoded MutationRecord (sequence_id, operation = Put or Delete, primary_key, secondary_key, timestamp_ns, checksum) (§8.2, §8.3, ADR-23). Replay reads frames in order, stops at the first unrecoverable torn frame and reports the last valid LSN (§13.2). The three log fixtures pin this down (§13.5):

Log on disk What replay does
wal_valid.bin, 3 clean frames yields 3 records, no errors
wal_partial_frame.bin, last frame torn by a crash stops at the last complete frame and reports the truncation point
wal_crc_failure.bin, one bit flipped ChecksumMismatch at the exact frame offset; frames before it still replay (I12)

A frame whose declared length runs past the segment's remaining bytes is quarantined (§13.2). Fsyncs are batched up to the 256 MB buffer; per-record fsync is called out as syscall amplification (§13.7).

Files that are never edited: memtable to segment (§8.5, P5, I3, MM2)

New writes go to a sorted in-memory structure (memtable, a lock-free skiplist keyed by (secondary_key, sequence_id)) (§14.2). Every insert is charged against a 2 GB budget, and crossing 90% raises a flush signal (§14.2, §4). Freezing is an atomic pointer swap from "active" to "frozen", never a copy (§14.2). A segment then goes through the states of §8.5:

State Meaning
Mutable active memtable accepting writes
Frozen immutable, waiting for flush
Flushing segment file under construction
Published query-visible, after the manifest commit
Compacting being rewritten, still visible until the swap
Obsolete superseded, waiting for safe deletion

A segment (SSTable-style file) holds a header, sorted data blocks, a sparse block index, a bloom filter and a footer with checksum and version (§8.4). Before any manifest record may reference it, it is renamed into place and its directory is fsynced (§15.2). After that its bytes never change (I3, P5). MM2 names what this buys: concurrency bugs become lifecycle bugs, because the hard question moves from "torn read" to "who retires this file, and when" (MM2). Inside one memtable generation the highest sequence ID wins for a key, and a node is visible to a snapshot only if its sequence ID is at most the snapshot's upper bound (§14.2).

Reading a frozen moment: snapshots and the merge iterator (§8.6, §16.2, I5, I8, MM6)

A snapshot is a pair, an epoch and a sequence_upper_bound; it is reference-counted, immutable and never written to disk (§11). Acquiring one is an atomic epoch read plus a refcount increment, with no syscall, and is budgeted under 500 µs (§4). Once taken, the epoch must not change for the iterator's whole life, so a source added or removed later stays invisible to it (MM6, I10).

The merge iterator is a min-heap over one cursor per source: memtables, frozen memtables and segments, all behind one IndexIterator trait (seek, next, valid, key, value) (§16.2, §11). The heap is capped at the active source count, at most 8 levels, and must stay at most 8 entries regardless of the underlying source count (§16.2, §16.4, §4). Visibility is applied during the merge, not afterwards, and a Delete (tombstone) dominates every older write for the same key (§16.2, I8, §8.1). A bloom filter that answers "absent" lets the iterator skip that segment's heap slot entirely (§16.2). The merge breaks ties on sequence ID, which is what keeps scan order reproducible and replay byte-identical (§16.6, §33 Q6, P1).

Metadata that is all-or-nothing: the manifest (§17.2, I2, I13, MM4)

MM4 says a manifest is a write-ahead log for metadata. Each record is AddSegment, RemoveSegment or Checkpoint with a generation number that only increases (§11, §17.2, I13). A commit is write, fsync, then atomic rename of the manifest pointer file (§17.2). No segment is query-visible except through a committed record (§17.1, I2).

The blueprint's own crash trace: the process dies during compaction's manifest swap. On restart, orphan detection quarantines (rather than deletes) segment files the latest committed generation does not reference, the manifest rolls back to the last committed generation, and log/manifest replay does the rest, never leaving a partially visible file set (§8.8, §17.2). The manifest also tracks the oldest pinned snapshot's generation, which is the garbage-collection floor compaction needs (§17.2).

Paying read cost early: compaction (§18.2, I11, MM3, C5)

Compaction merges several segments into fewer, larger ones, so a lookup consults fewer files. MM3 puts it this way: deferring compaction does not remove the read cost, it postpones and compounds it (MM3). The scheduler scores each level (size-tiered within a level, leveled across levels), keeps a priority queue of jobs, and enforces the 8-level ceiling (§18.2, §4). It follows two safety rules. It never rewrites a segment a pinned snapshot still needs, and it drops a tombstone only once the tombstone's sequence ID is older than every pinned snapshot's floor (I11, §18.2). A minimum-age promotion rule means no segment waits more than N compaction cycles, which prevents the "cold tail never compacts" problem (§18.2). Compaction I/O runs on its own io_uring submission queue, apart from the log and query I/O lanes, so the log's fsync never queues behind it (§18.2, §13.2, P11).

The cost is write amplification (extra writes from rewriting data). C5 gives the arithmetic: 8 levels times a 10x fanout per level is 80x in the theoretical worst case, throttled to the 10x operating ceiling of §4 by the starvation-prevention policy of §18 (C5, §32).

Quorum as an exchange rate: replication (§20.2, I7, I9, MM5)

Raft (a consensus protocol for agreeing on one ordered log) ships ReplicationFrames derived one-to-one from log frames, so followers replay in the leader's order (§20.2, ADR-24, I9). A write's visibility is gated on quorum acknowledgment, which is I7 itself (§20.2, §8.7). MM5 states the price: each unit of consistency costs one round trip, so the write-latency floor is set by inter-zone RTT (2-10 ms in §4), not by CPU (MM5, §4). A follower that falls behind the retention window is caught up by snapshot, not by unbounded log replay (§20.2, §20.4). Each follower has a flow-control credit, so a slow follower pushes back on the leader's shipper instead of growing a queue (§20.2, ADR-21, P4). Followers move through Probe, Replicate and Snapshot states (§20.2). Replayed or forged append-entries are caught by term and sequence validation plus mTLS (T3).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust, because deterministic ownership removes a class of use-after-free and data-race bugs in the lock-free memtable and iterator paths (ADR-01, §1). Rejected: Go, C++, Java, Zig. §1 gives a reason for each, for example Go's GC pauses against the p99 point-lookup budget (§1, §4). When the rejected choice is right: Go, for a throwaway internal script where GC pause is irrelevant and iteration speed dominates (ADR-01).

Storage engine: LSM tree with immutable files (ADR-04)

Chosen: an LSM tree of immutable SSTables, because 250,000 ops/sec needs sequential append, not in-place page writes (ADR-04, §4). Rejected: a B+Tree alone (ADR-04, Alt A in §34). When the rejected choice is right: a read-dominated embedded workload with rare writes and hot range-scan locality, such as an embedded analytics cache (ADR-04).

The in-memory index: lock-free skiplist (ADR-08)

Chosen: a lock-free skiplist, because readers must traverse concurrently under backpressure (ADR-08, P4). Rejected: an AVL tree behind one global mutex (ADR-08). When the rejected choice is right: a single-writer, low-core-count embedded deployment where contention never materializes (ADR-08). The choice does not remove the need for epoch reclamation, which the blueprint treats as its own pitfall area (§33 Q12, §14.6).

Backpressure: credits at every producer boundary (ADR-21)

Chosen: credit-based flow control, because bounded memory requires every queue to be creditable (ADR-21, P3). Rejected: unbounded channels (ADR-21). MM7 says removing a backpressure signal only moves the failure downstream, and FM-5 is the case where a missing credit signal lets the WAL queue grow (MM7, FM-5). When the rejected choice is right: a low-volume admin control-plane RPC where flow-control machinery is pure overhead (ADR-21).

Log checksum: CRC32C (ADR-23)

Chosen: CRC32C, which is hardware-accelerated at WAL-append rates (ADR-23, §4). Rejected: SHA-256 (ADR-23). When the rejected choice is right: when the checksum must also serve as a cryptographic integrity proof, not just detect corruption (ADR-23).

Consensus: Raft (ADR-24)

Chosen: Raft, because I7 and I9 need a strong consistency guarantee (ADR-24, §7). Rejected: gossip-based eventual convergence (ADR-24). When the rejected choice is right: a purely advisory, staleness-tolerant metadata layer, not the write path (ADR-24). Note that §29 credits ADR-24 with capping voters at 3-7, which the ADR-24 row itself does not say (§29, §9).

Roads not taken

Alt A, a synchronous embedded B-tree (§34): wins on read-dominated workloads with modest writes, where heap and index share one lock manager and read-your-writes comes free. PostgreSQL's B-tree access method is the real-world example. Rejected here because of the 250,000 ops/sec budget (Alt A, ADR-04).

Alt B, an asynchronous coprocessor secondary index (§34): wins in multi-tenant, massive-scale systems where isolating base-table write latency from index cost matters more than immediate index consistency. DynamoDB's global secondary indexes embody it. Rejected here because I5 and I7 plus the "strongly consistent" requirement of §1 rule it out (Alt B).

Alt C, an inverted-index search layer (§34): wins for full-text, relevance-ranked search over mostly append-only documents. Lucene and Elasticsearch embody it. Rejected here because full-text ranking is a non-goal and posting lists do not fit the point and range shapes of §19 (Alt C, §1).

Deferred register (§35), each with its un-defer trigger: learned index structures (§16) when point-lookup p99 misses its budget despite bloom tuning (C3); HTAP-style analytical CDC ingestion (§20) when a consumer needs change-data-capture beyond log shipping; tiered cloud storage for cold segments (§15) when the segment mmap budget is chronically exceeded (§4); adaptive cache admission (§15) when the block-cache hit rate plateaus; compressed segment storage (§15) when write amplification or disk cost binds (C5); online repartitioning (§20) when single-shard throughput saturates the largest supported host (§35, §4).

What must never be false

Each line gives the invariant, how the system notices a violation (detection), and its telemetry (§7).

  • I1: nothing is query-visible before its log frame is fsynced. Noticed by replay validation comparing the log tail to the visible sequence; wal_fsync_before_visibility_violations.
  • I2: segment-visibility changes are atomic across the whole manifest. Noticed by checksum-verified commit replay; manifest_commit_atomicity_failures.
  • I3: a published segment is never modified in place. Noticed by a segment checksum re-scan; segment_mutation_after_publish.
  • I4: sequence IDs are strictly increasing and never reused per shard. Noticed by a gap/duplicate scan on replay; sequence_id_monotonicity_violations.
  • I5: a snapshot never sees a mix of two generations. Noticed by a cross-generation key check in differential tests; snapshot_generation_mix_detected.
  • I6: admin-path failures cannot block the query path. Noticed by correlating query latency with admin load; admin_query_isolation_breach.
  • I7: a write is acknowledged only after fsync and Raft quorum. Noticed by comparing the ack log with the quorum log; premature_ack_detected.
  • I8: a delete beats all older writes for the same key. Noticed by a differential test that hunts for resurrected tombstones; tombstone_ordering_violations.
  • I9: followers replay in the leader's order. Noticed by sequence-gap detection on the follower; replica_replay_order_violations.
  • I10: an iterator stays valid for as long as its snapshot is pinned. Noticed by a validity assertion on every step; iterator_snapshot_invalidation.
  • I11: compaction never rewrites a segment a pinned snapshot still needs. Noticed by a pre-compaction snapshot-set intersection check; compaction_snapshot_conflict.
  • I12: every checksum is verified before its bytes are trusted. Noticed by a CRC32C mismatch on read; checksum_mismatch_total.
  • I13: manifest generation numbers only increase and are never reused. Noticed by a generation-reuse scan on recovery; manifest_generation_reuse_detected.

The simulator holds exactly one assertion per invariant, checked on every simulated tick, so a violation reproduces byte-for-byte from the failing seed (§7).

What breaks in production

Each is drawn from §23. Note that the §23 table's header has seven columns while its rows have eight (a name column was added); the paragraphs below read the second cell as the failure's name.

  • FM-1, WAL corruption. Symptom: reads succeed but replay halts early and the WAL inspector reports a CRC mismatch. Cause: a torn write, sector misalignment or bad NVMe firmware. Detection: checksum mismatch on replay (I12). Recovery: truncate to the last valid frame and resume; operator-cli inspect wal --repair confirms the quarantine boundary (§23, §13.9).
  • FM-3, compaction crash or isolation failure. Symptom: compaction throughput drops to zero while queries carry on, if isolation holds. Cause: a panic in scoring or rewrite logic, or resource exhaustion in the compaction pool. Detection: the worker-panic metric and orphan-segment detection. Recovery: resume from the job checkpoint (§23, §18.2, P11).
  • FM-4, replica divergence. Symptom: a follower's state differs byte-for-byte from the leader's. Cause: nondeterministic ordering (a P1 violation) or out-of-order apply (an I9 violation). Detection: a per-follower sequence-gap or checksum-mismatch metric. Recovery: resync from a snapshot (§23, §20.2).
  • FM-5, backpressure collapse. Symptom: the WAL queue grows, memory climbs, latency spikes. Cause: a missing credit signal (P4) or an unthrottled slow follower. Detection: queue depth crossing its budget. Recovery: backpressure throttles the producer automatically; an operator can override the rate limit through the admin API (§23).
  • FM-6, memory leak or OOM. Symptom: RSS grows until the process is killed. Cause: unbounded memtable or iterator allocation (P3) or an epoch leak. Detection: the allocator-accounting metric exceeding its budget. Recovery: none automatic, restart the process and bisect with heaptrack if it recurs (§23, §14.6). §33 Q11 asks how to tell FM-5 from FM-6 early, since both show growing RSS.
  • FM-8, split brain. Symptom: two nodes briefly believe they are leader. Cause: late partition detection or a misconfigured lease timeout. Detection: the term-divergence metric and the I7 assertion. Recovery: the higher-term leader wins automatically (§23).
  • FM-9, segment bit rot. Symptom: a checksum failure on a background scan or read. Cause: a hardware bit flip or filesystem corruption. Detection: the background checksum scanner (§15.2, I12), which feeds the under-60-second detection budget (§4). Recovery: the segment is marked Obsolete and a repair job rebuilds it (§23).

Threats a reader should know (§22):

  • T3, a replayed or forged append-entries RPC, is answered by term and sequence checks plus mTLS between peers; the frame is dropped with no state change (§22, ADR-24, I9).
  • T4, a crafted log frame that crashes the replay scanner, is answered by a fuzz-tested scanner; the frame is quarantined and replay resumes from the last valid LSN (§22, ADR-13).
  • T6, a crafted segment file that causes an out-of-bounds read through mmap, is answered by a fuzz-tested reader and a footer-version check before the layout is trusted (§22, ADR-13).
  • T9, a flood that exhausts file-descriptor, memory or thread budgets, is answered by admission control and credit-based backpressure (§22, P4, ADR-21).
  • T11, a repair endpoint used to force-delete a live segment, is answered by capability-scoped tokens that allow repairs on quarantined segments only (§22, ADR-17).

Where the blueprint is not consistent with itself, both readings stand:

  • §4 says an open segment costs "one FD per open segment + socket", while C6 divides by 2 FDs per segment (data file plus sparse index) to reach 16,384, though §8.4 places the sparse block index inside the segment file; §29 repeats the 16,384 figure (§4, C6, §8.4, §29).
  • §4 derives 250,000 ops/sec as "256 MB WAL buffer / avg 1 KB mutation record ÷ 2 ms fsync window", while C4 divides 256 MB by 250,000 ops/sec to get 1.024 KB per write. The two are different derivations (§4, C4).
  • §4 states the 10x write-amplification ceiling as 8 levels with 10x fanout each, while C5 calls that product 80x and says policy throttles it to 10x (§4, C5). §18.4 then applies the C5 ceiling to read amplification (§18.4).
  • C7's 200,000 frames/sec is "above" the 250,000 ops/sec write ceiling only once batching amortizes at least 1.25 records per frame, yet C7 sizes a frame at about 1 KB, the size §4 and C4 give one record (C7, C4, §4).

How it compares

  • RocksDB left secondary-index maintenance to the embedding application, offering only an ordered key/range API. That is fine where the host already owns transactional semantics and wants a fast embedded substrate (§31).
  • Apache Cassandra chose eventually consistent local secondary indexes over synchronous maintenance. That is fine for write-heavy, availability-first workloads where a briefly stale secondary read is acceptable (§31).
  • DynamoDB propagates global secondary indexes asynchronously from the base-table write. That is fine where base-table write-latency isolation matters more than immediate read-your-writes on the index (§31, Alt B in §34).
  • PostgreSQL builds synchronous, transactional index maintenance into the same MVCC engine as the heap. That is fine where read-your-writes on the secondary index is a hard requirement (§31, Alt A in §34).
  • FoundationDB builds secondary indexing as a stateless layer over a synchronously replicated ordered key-value core. That is fine where several independent indexing schemes must share one strongly consistent substrate without each reimplementing consensus (§31).

Questions to test yourself

  1. I1 (§7) guarantees WAL-fsync precedes visibility on a single node — once replication (§20) is introduced, what additional mechanism closes the gap so a client-acknowledged write actually survives a leader crash, and why is I1 alone insufficient? — Hint: §8.7 gives the step order; §20.2 and I7 give the gate.
  2. §32's C6 derives a 16,384-segment ceiling from the FD budget in §4 — if compaction (§18) fails to keep segment count below that ceiling, which invariant in §7 fails first, and what is the observable symptom in §23? — Hint: C6, the FD row of §4 and the symptoms in §23.
  3. If you only remember three things

Make the write durable before anyone can see it, and make visibility a quorum decision, so a crash or a leader loss never takes back an acknowledged write (I1, I7, MM1). Never edit a published file and change the set of live files only through a checksummed, generation-numbered manifest commit, so readers always see one consistent generation and a crash mid-swap rolls back cleanly (I2, I3, I5, MM2, MM4). Compaction is read cost paid early at a bounded write-amplification price, and it must always yield to the live snapshots that still need the old files (MM3, I11, C5).

Words used here

  • Secondary index: a sorted map from a secondary key to the primary key of the record that has it (§1).
  • Primary key / secondary key: the host record's identifier, and the indexed value derived from the record (§8.1).
  • WAL (write-ahead log): an append-only log written and fsynced before a change becomes visible (§36, I1).
  • Memtable: the mutable in-memory sorted structure that takes live writes (§36, §14.2).
  • Segment / SSTable: an immutable, sorted, on-disk file (§36, §8.4).
  • Tombstone: a deletion marker that beats all older writes for its key (§36, I8).
  • Snapshot / epoch: a pinned point-in-time view, identified by a counter that only grows (§36, §11).
  • Manifest: the transactional log of which segments are live (§36, §17).
  • Compaction: merging segments into fewer, larger ones to cut read cost (§36, §18).
  • Bloom filter: a small structure that can say "definitely absent", used to skip file reads (§36, C3).
  • Write amplification: extra physical writes caused by rewriting data during compaction (§36, C5).
  • Quorum: a majority of Raft voters that must acknowledge before a write commits (§36, I7).
  • Backpressure: a downstream signal a producer must heed before sending more (§36, P4).
