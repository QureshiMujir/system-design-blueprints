⬜ Phase 0 — Workspace, Runtime & Correctness Kernel §12

Objectives

Stand up the deterministic build/runtime skeleton and the correctness kernel every later phase depends on: config loading, clock abstraction, error hierarchy, task supervision, and the deterministic-simulation test harness. Constraints introduced: no subsystem may call SystemTime::now() directly (ADR-20); no unbounded task spawn without a supervisor budget (P3); every crate must build under the pinned toolchain in rust-toolchain.toml.

Deliverable

A runnable runtime skeleton: cargo build --workspace succeeds, cargo test --workspace passes, the metrics endpoint (/metrics) serves an empty Prometheus registry, and structured JSON logs are emitted on startup with build_sha, rustc_version, and config_hash fields.

Acceptance
  • CI green on 3 consecutive commits with zero flakes.
  • Binary is bit-for-bit reproducible across 2 clean-room builds (sha256sum match, ADR-19).
  • Startup-to-ready time < 30 sec (§4 cold-startup budget).
  • conformance/config/config_valid.toml loads with zero errors; config_invalid_missing_port.toml rejects with a typed ConfigError::MissingField("port").
Fixtures
  • conformance/config/config_valid.toml — full valid node config; expected: loads, all fields populated.
  • conformance/config/config_invalid_missing_port.toml — missing required port key; expected: typed rejection, not a panic.
  • conformance/metrics/metrics_registry_snapshot.json — golden metrics-registry shape after zero-traffic startup; expected: exact metric-name set match (regression guard).
Pitfalls
  • Nondeterministic config-key iteration order leaking into a hash computed over config (root cause: using HashMap instead of BTreeMap; detect via replay diff; recover by switching to an ordered map — violates P1 otherwise).
  • Allocator fragmentation under repeated small-object churn in the supervisor task queue (root cause: jemalloc arena sizing defaults; debug via jemalloc-ctl stats; signal: RSS creep with flat live-set; recover by tuning arena count).
  • Unstable tracing span IDs across restarts breaking correlation in long-running incident timelines (root cause: span-ID generator seeded from wall clock instead of a persisted counter; detect via duplicate span IDs in OTLP export; recover by persisting the counter in the manifest).

⬜ Phase 1 — WAL Engine §13

Objectives

Implement crash-recoverable, durable append-only logging — the persistence boundary anchoring I1 and the ARIES-style recovery model (Mohan et al., 1992). Constraint introduced: no mutation may become query-visible before its WAL frame's fsync completes (I1).

Deliverable

A WAL subsystem that survives kill -9 at any byte offset and replays deterministically to the last fsync'd frame; operator-cli inspect wal <path> prints frame count, last LSN, and corruption status.

Acceptance
  • Zero acknowledged-write loss across 10,000 injected kill -9 crash points (§4 durability budget).
  • WAL append p99 < 2 ms at 250,000 ops/sec sustained (§4 throughput budget).
  • Replay of a 256 MB WAL completes in < 90 sec (§4 WAL-replay budget).
  • wal_crc_failure.bin is detected and quarantined, never silently accepted.
Fixtures
  • conformance/wal/wal_valid.bin — clean 3-frame log; expected: replay yields 3 records, no errors.
  • conformance/wal/wal_partial_frame.bin — torn final frame (simulated crash mid-append); expected: replay stops at last complete frame, reports truncation point.
  • conformance/wal/wal_crc_failure.bin — single bit-flipped frame; expected: ChecksumMismatch at the exact frame offset, replay of prior frames still succeeds (I12).
Pitfalls
  • fsync starvation when the IO scheduler lane is shared with compaction reads (root cause: missing IO isolation, P11 violation; detect via WAL-append p99 spiking during compaction; recover by enforcing the dedicated IO lane from §13.2).
  • Frame alignment bugs on non-512-byte-aligned appends causing partial-sector torn writes on power loss (root cause: skipping O_DIRECT alignment; detect via replay fixture wal_partial_frame.bin; recover by padding frames to sector boundaries).
  • Torn-append replay misclassifying a legitimately short final frame (end-of-log) as corruption (root cause: no explicit "log tail" marker; detect via false-positive corruption alerts on clean shutdown; recover by writing an explicit end-of-segment marker on graceful rotation).

⬜ Phase 2 — Memtable Engine §14

Objectives

Implement the mutable in-memory indexing structure: a lock-free skiplist with epoch-based reclamation (Herlihy & Shavit, 2012, ch. 14), satisfying P5's freeze-to-immutable transition and I10's iterator- validity guarantee. Constraint introduced: no subsystem may allocate memtable memory outside the 2 GB budget (§4) without triggering a flush.

Deliverable

A concurrent, lock-free mutable index that accepts 250,000 writes/sec from a single writer while serving unlimited concurrent lock-free readers, and freezes deterministically on flush trigger.

Acceptance
  • Zero use-after-free or ABA violations across a 24-hour loom-style concurrency stress run.
  • Freeze transition completes in < 1 ms and is observed atomically by all concurrent iterators (I10).
  • Memory accounting stays within 2 GB ± 1% under the write-throughput budget (§4).
  • duplicate_key_visibility.json resolves to the highest-sequence-ID record, verified byte-for-byte.
Fixtures
  • conformance/memtable/memtable_insert_replay.json — WAL-derived insert sequence; expected: post-replay memtable state matches golden key/value/sequence triples exactly.
  • conformance/memtable/duplicate_key_visibility.json — three writes to one key at increasing sequence IDs; expected: only the highest-sequence write is visible under any snapshot ≥ it.
Pitfalls
  • ABA hazards in CAS-based node insertion under high contention (root cause: reusing a freed node pointer before epoch advance; detect via the loom stress harness; recover by tightening the epoch-advance interval).
  • Epoch leaks when a reader task is cancelled mid-traversal without releasing its epoch guard (root cause: missing RAII drop on cancellation; detect via monotonically growing epoch-lag metric; recover by wrapping every iterator in a guard that releases on Drop).
  • Tombstone resurrection when a compaction merges an older segment after its tombstone's memtable generation was already flushed and discarded (root cause: tombstone GC racing flush; detect via the differential iterator test in §16; recover by delaying tombstone GC past the oldest pinned snapshot).

⬜ Phase 3 — SSTable Segment Engine §15

Objectives

Implement immutable, on-disk, mmap-backed segments — the Bigtable/LevelDB SSTable pattern (Chang et al., 2006; O'Neil et al., 1996) — satisfying P5 and I3. Constraint introduced: a segment's bytes never change after the manifest publishes it (I3); every read verifies a checksum before trusting bytes (I12, P10).

Deliverable

A queryable, immutable SSTable-equivalent segment format: operator-cli inspect segment <path> dumps header, block count, bloom-filter size, and footer checksum; range scans against a built segment return sorted, checksum-verified results.

Acceptance
  • Range scans over a 1M-key segment return results in sorted order with zero checksum failures.
  • Segment reopen after process restart is byte-for-byte deterministic (P1).
  • Bloom filter false-positive rate ≤ 1% at the configured bit budget (derived in C3, §32).
  • malformed_footer.bin and corrupted_bloom.bin are both rejected at open time, not at first read.
Fixtures
  • conformance/segment/segment_v1.bin — golden 3-block segment; expected: exact key/value/checksum round-trip.
  • conformance/segment/malformed_footer.bin — truncated footer; expected: SegmentOpenError:: InvalidFooter at open, not a panic mid-scan.
  • conformance/segment/corrupted_bloom.bin — bit-flipped bloom bitmap; expected: checksum mismatch detected before the filter is trusted for prefiltering (I12).
Pitfalls
  • mmap invalidation when a segment file is unlinked while a reader still holds a mapped view on Linux (root cause: not holding an open FD alongside the mapping; detect via SIGBUS under load; recover by keeping the FD open until the last mmap view is dropped).
  • Sparse-index drift when block boundaries shift between builder versions without a footer version bump (root cause: skipping ADR-adjacent versioning discipline; detect via the compatibility conformance suite in §25; recover by bumping the segment-format version).
  • Restart-point corruption causing incorrect prefix-decompression mid-block (root cause: off-by-one in restart-interval encoding; detect via the differential iterator test in §16; recover by rebuilding the segment from source WAL/memtable state).

⬜ Phase 4 — Iterator Runtime §16

Objectives

Build the unified k-way merge-iterator execution layer over memtables, frozen memtables, and segments — the single read path referenced from §3's Iterator Engine box — satisfying I5, I8, I10, and I11. Constraint introduced: an iterator must never allocate unbounded heap space regardless of fanout depth (P3 applied to iteration).

Deliverable

A single iterator implementation serving point lookups, range scans, prefix scans, and compound-key scans uniformly; query-runtime never imports a memtable- or segment-specific type.

Acceptance
  • Range scans over a 3-memtable + 5-segment fixture return deterministic sorted output with zero duplicate visibility violations across 1,000 randomized differential-test runs (§26).
  • Iterator heap allocation stays ≤ 8 entries regardless of underlying source count (§4 fanout bound).
  • Cancellation releases all resources within 1 scheduler tick, verified via range_scan_fixture.json.
  • tombstone_visibility.json never resurrects a deleted key under any snapshot taken after the delete's sequence ID.
Fixtures
  • conformance/iterator/range_scan_fixture.json — mixed memtable+segment range scan; expected: exact sorted key sequence, no duplicates.
  • conformance/iterator/tombstone_visibility.json — delete-then-read-under-old-and-new-snapshot case; expected: old snapshot sees the value, new snapshot sees nothing (I5 + I8 combined).
Pitfalls
  • Heap instability when two sources report equal keys but different sequence IDs and the comparator doesn't tie-break deterministically (root cause: comparator ignoring sequence ID, violating P1; detect via non-reproducible scan order across identical runs; recover by making sequence ID the tie-break key).
  • Iterator starvation when one source's seek cost dominates and blocks heap progress under a shared scheduler budget — mitigated by a per-source seek-time budget with cooperative yielding.
  • Stale snapshot reads when a snapshot's pinned epoch is not correctly propagated to a newly opened segment source added mid-scan by a concurrent flush (root cause: race between flush publication and iterator source enumeration; detect via I5 differential check; recover by re-enumerating sources under the manifest's generation lock).

⬜ Phase 5 — Manifest & Metadata Management §17

Objectives

Implement the authoritative storage-topology transaction log that makes every segment-visibility change atomic (I2, I13) — the manifest boundary called out in §3.2 as the sole authority for storage truth. Constraint introduced: no segment is ever query-visible except through a committed manifest record (I2).

Deliverable

A durable metadata subsystem where segment visibility transitions are atomic across crashes; operator-cli inspect manifest <path> dumps generation history, live segment set, and orphan list.

Acceptance
  • 100% of injected crash points during manifest commit (10,000 trials) recover to either the pre- or post-commit state, never a torn intermediate state (I2).
  • Manifest replay on a 100,000-segment history completes within the 30 sec cold-startup budget (§4).
  • Orphan detection correctly flags 100% of synthetically orphaned segments in manifest_partial_commit.bin-derived fixtures with zero false positives.
Fixtures
  • conformance/manifest/manifest_v1.bin — golden 50-generation history; expected: exact live-segment- set reconstruction.
  • conformance/manifest/manifest_partial_commit.bin — commit torn mid-write; expected: rollback to last valid generation, orphan segment flagged, no data loss (I2, I13).
Pitfalls
  • Split publication when two compaction jobs race to commit against the same generation number (root cause: missing single-writer serialization on manifest commits; detect via generation-collision assertion; recover by serializing all commits through one writer task).
  • Orphan leaks when the orphan scan runs before the manifest replay completes, missing segments referenced by a generation not yet loaded (root cause: ordering bug in startup sequence; detect via false-positive orphan reports after restart; recover by running orphan scan strictly after full replay).
  • Stale generation reuse after a rollback if the generation allocator isn't itself rolled back with the manifest (root cause: allocator state kept separate from manifest state; detect via I13 assertion; recover by deriving the allocator's next value from the replayed manifest, never from cached state).

⬜ Phase 6 — Compaction Runtime §18

Objectives

Implement multi-level, snapshot-safe compaction — the LSM merge-cost model formalized by O'Neil et al. (1996) — satisfying I11 (never rewrite a segment a pinned snapshot needs) while keeping write amplification within the C5 (§32) ceiling. Constraint introduced: compaction must never block or starve the query-serving path (P11).

Deliverable

An online compaction engine that reduces read amplification under sustained 250,000 ops/sec ingest without ever violating a pinned snapshot's view; operator-cli inspect compaction shows per-level debt and in-flight jobs.

Acceptance
  • Read amplification stays within the C5 (§32) derived ceiling (≤ 10× write amplification budget, §4) under 24-hour sustained-ingest soak testing.
  • Zero I11 (snapshot-safety) violations across 1,000 randomized concurrent compaction + long-running- snapshot differential-test runs (§26).
  • Compaction debt (bytes pending rewrite) converges to a steady-state bound within 15 minutes of a synthetic write-rate step change.
Fixtures
  • conformance/compaction/compaction_overlap_case.json — deliberately overlapping input-segment key ranges; expected: compaction detects and rejects, does not silently merge incorrectly.
  • conformance/compaction/tombstone_gc_case.json — tombstone older than the oldest pinned snapshot vs. tombstone newer than it; expected: only the former is pruned (I11).
Pitfalls
  • Compaction storms when the scoring function over-prioritizes one hot level, starving others (root cause: scoring normalization bug; detect via per-level debt divergence metric; recover by re- normalizing score against level target size, not absolute byte count).
  • Write stalls when compaction falls behind ingest and the memtable-flush path blocks waiting for level-0 headroom (root cause: missing backpressure signal from compaction debt to the Mutation Runtime, a P4 violation; detect via WAL-append latency correlating with compaction-debt metric; recover by wiring the credit-based backpressure from ADR-21 into the flush trigger).
  • Snapshot invalidation when a long-running snapshot's pin is not correctly consulted before a segment set is retired (root cause: race between §17.2's snapshot-reference update and the compaction scheduler's read of it; detect via I11 assertion; recover by making the snapshot-floor read and the compaction dispatch atomic under one lock).

⬜ Phase 7 — Query Runtime §19

Objectives

Implement the externally accessible query-execution surface — point/range/prefix/compound scans over the Iterator Runtime (§16) — under the tail-latency budgets in §4. Constraint introduced: a query must be cancellable and resource-bounded regardless of client behavior (P3, P4).

Deliverable

An externally accessible query interface serving point lookups, range scans, and paginated compound- key scans with snapshot isolation; query_point_lookup.json and range_scan_limits.json pass as conformance gates.

Acceptance
  • Point-read p50/p95/p99 within 1 ms / 5 ms / 20 ms (§4) at 500,000 ops/sec sustained load.
  • Range scans stable (no memory growth, no duplicate/missing keys) across a 1-hour soak with 20,000 scans/sec (§4).
  • Snapshot isolation verified: a scan started before a concurrent write never observes that write (I5), across 1,000 randomized differential-test runs.
  • range_scan_limits.json's max-page-size case is enforced server-side (rejects, does not silently truncate).
Fixtures
  • conformance/query/query_point_lookup.json — point lookup against a mixed memtable/segment state; expected: exact value + sequence ID match.
  • conformance/query/range_scan_limits.json — pagination at and beyond the max page size; expected: exact page boundaries, explicit rejection beyond the cap.
Pitfalls
  • Runaway scans with no bound on iteration count when a client omits a limit (root cause: missing server-side default cap; detect via query-duration outlier metric; recover by enforcing a default max-scan-count even when the client requests "unbounded").
  • Cancellation leaks when a cancelled query's iterator (§16.9) isn't actually dropped promptly because the executor task is blocked on a syscall (root cause: cancellation checked only at await points; detect via iterator_active_count staying elevated post-cancel; recover by adding a cooperative cancellation check inside the merge loop, not just at task boundaries).
  • Timeout mispropagation when a sub-call (e.g., a segment page fault) doesn't inherit the parent request's deadline (root cause: missing deadline threading through §16.2's source enumeration; detect via requests exceeding their stated timeout; recover by threading a Deadline through every iterator source).

⬜ Phase 8 — Replication Runtime §20

Objectives

Implement Raft-backed replicated durability (Ongaro & Ousterhout, 2014) — log shipping, quorum acknowledgment, and follower catch-up — satisfying I7 and I9. Constraint introduced: a write is acknowledged to a client only after WAL fsync and Raft quorum (I7).

Deliverable

A replicated indexing cluster: a 3-voter Raft group where a leader failure triggers election and continued service within the availability budget (§4); raft_leader_failover.json passes.

Acceptance
  • Follower convergence to the leader's exact key/value/sequence state verified byte-for-byte across 100 randomized partition-and-heal trials.
  • Zero acknowledged-write loss (§4) across leader-failover trials — I7 holds through every election.
  • Leader failover completes within the 5 sec max-replication-lag budget (§4) under normal partition scenarios.
  • replication_gap_fixture.json's induced gap triggers snapshot catch-up, not an unbounded log replay.
Fixtures
  • conformance/replication/raft_leader_failover.json — scripted leader crash + election; expected: new leader elected, no committed write lost, term strictly increases.
  • conformance/replication/replication_gap_fixture.json — follower offline beyond retention window; expected: snapshot-based catch-up, not a replay of a truncated log range.
Pitfalls
  • Replay divergence when a follower applies frames out of the leader's canonical order under concurrent log-shipper batches (root cause: batch reordering at the network layer; violates I9; detect via per-follower sequence-gap metric; recover by enforcing strict in-order apply with a per-follower sequence assertion).
  • Stale leaders continuing to accept writes after losing quorum due to a delayed network-partition detection (root cause: missing quorum-loss heartbeat timeout; detect via I7 assertion firing on a write acknowledged without live quorum; recover by shortening the leader-lease timeout).
  • Replication storms when many followers request snapshot catch-up simultaneously after a shared network partition heals (root cause: no admission control on snapshot-transfer requests; detect via leader IO-saturation metric; recover by rate-limiting concurrent snapshot transfers, ADR-21).

⬜ Phase 9 — Observability & Operational Readiness §21

Objectives

Implement production observability end-to-end (P6) — metrics, tracing, structured logs, dashboards, alerting, and incident runbooks — completing the Phase-0 deliverable list from §1. Constraint introduced: observability instrumentation itself must never affect the p99 query-latency budget (§4) by more than 2%.

Deliverable

An operationally observable platform: every subsystem in §3.2's diagram emits metrics, traces, and structured logs; the four dashboards in §21.2 are populated under synthetic load; runbooks exist for every §23 failure class.

Acceptance
  • 100% of critical request paths (point read, range scan, mutation apply, compaction job, replication apply) carry an unbroken trace span tree end-to-end.
  • Alerting validated: synthetic injection of each §23 failure class fires its corresponding alert within 60 sec (matching the §4 corruption-detection budget where applicable).
  • Instrumentation overhead measured at < 2% p99 latency delta versus an uninstrumented build (§4 budget compliance).
  • telemetry_snapshot.json and alert_trigger_fixture.json both pass as regression gates.
Fixtures
  • conformance/observability/telemetry_snapshot.json — golden metric/trace/log shape under synthetic load; expected: exact metric-name and span-name set match (regression guard against silent metric removal).
  • conformance/observability/alert_trigger_fixture.json — synthetic WAL-corruption and replication- gap injections; expected: corresponding alert fires within the budget window.
Pitfalls
  • Metrics cardinality explosion from an unbounded label (e.g., segment_id as a metric label instead of a log field) (root cause: no cardinality review gate in CI; detect via Prometheus TSDB size alert; recover by moving high-cardinality identifiers to structured-log fields, never metric labels).
  • Trace amplification when a single query request generates thousands of spans from a pathologically deep iterator fanout (root cause: missing span-sampling policy under high fanout; detect via OTLP export volume spike; recover by sampling spans below a configurable fanout threshold).
  • Missing correlation IDs when a background job (compaction, replication catch-up) isn't given a trace_id at all because it wasn't triggered by a client request (root cause: tracing bootstrap assumed a request origin; detect via untraceable incident timelines; recover by generating a synthetic root span for every background job).
