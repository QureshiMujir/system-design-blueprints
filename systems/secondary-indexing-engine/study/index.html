33. Hard Questions (Self-Examination)

  • Q1. I1 (§7) guarantees WAL-fsync precedes visibility on a single node — once replication (§20) is introduced, what additional mechanism closes the gap so a client-acknowledged write actually survives a leader crash, and why is I1 alone insufficient?
  • Q2. ADR-04 (§9) locks LSM+SSTable storage specifically to hit the write-throughput budget in §4 — why does that same choice force the read-amplification ceiling in §28 to be a compaction-scheduling concern (§18) rather than a segment-format concern (§15)?
  • Q3. Under P5 and I11 (§6, §7), what is the first invariant to break if a segment were allowed to be updated in place instead of rewritten by compaction, and which phase's (§18) acceptance criteria would first detect it?
  • Q4. §32's C6 derives a 16,384-segment ceiling from the FD budget in §4 — if compaction (§18) fails to keep segment count below that ceiling, which invariant in §7 fails first, and what is the observable symptom in §23?
  • Q5. MM5 (§30) claims the write-latency floor is bounded by inter-zone RTT, not CPU — reconcile this with M8's 2 ms WAL-append target (§28), a single-node non-replicated number: under what deployment mode (§1) does M8 alone determine write latency, and under what mode does MM5 dominate?
  • Q6. P1 (§6) requires byte-identical replay; §16's merge iterator breaks ties on sequence ID to satisfy this — what happens to that guarantee if two independent shards (§1's later-phase capability) must merge their outputs for a cross-shard scan, and where would the tie-break rule need to move?
  • Q7. §17's manifest generation numbers are strictly monotonic (I13) — what would break in §20's follower-catch-up snapshot mechanism if a follower's local generation counter were allowed to reset on restart instead of being replayed from the manifest?
  • Q8. §22's T3 (replay-attack mitigation via term/sequence validation) and §7's I9 (canonical replay order) both defend against out-of-order application — why is neither one alone sufficient, and what specific fault does the combination close that neither closes individually?
  • Q9. §28's M9 (500 µs snapshot-acquisition target) depends on the epoch-counter read in §13 being lock-free — trace what happens to M2 (500,000 ops/sec point-read target, §28) if that acquisition path ever needed a mutex, and which §9 ADR would have to be revisited.
  • Q10. §34's Alt B (async coprocessor GSI) is explicitly rejected for this blueprint's Phase 0–9 scope — under what future, later-phase requirement from §1 would that rejection need to be revisited, and which invariant in §7 would have to be relaxed first?
  • Q11. §23's FM-5 (backpressure collapse) and FM-6 (memory leak/OOM) look similar in symptom (RSS growth) — what specific telemetry from §24 distinguishes them fast enough to pick the right runbook before the process OOMs?
  • Q12. §9's ADR-08 chooses a lock-free skiplist for the memtable specifically citing concurrent-reader traversal — why does that same decision NOT eliminate the need for the epoch-reclamation pitfalls documented in §14, and what would eliminating epoch reclamation entirely require giving up?
  • Q13. §31 shows PostgreSQL choosing synchronous secondary-index maintenance inside one MVCC engine — why can this blueprint's design (§3) not simply copy that approach given that it also has an MVCC visibility model (§8), and what architectural fact in §3 makes synchronous in-engine maintenance the wrong fit here?
  • Q14. §35 defers "online repartitioning" to a later phase anchored at §20 — walk through why §20's replication core, not §18's compaction core, is the correct anchor for that specific deferred feature.
  • Q15. §26's differential-testing strategy compares memtable, segment, and WAL-replayed reconstructions of the same logical state — if all three agree but disagree with what a live snapshot iterator (§16) actually returned, which component is most likely wrong, and why does that ordering of suspicion follow from P1 and P8 (§6)?
  • Q16. §32's C3 sizes the bloom filter for a 1% false-positive rate — using C1 and C3 (§32) together, quantify what happens to the 8 GB memory ceiling (§4) if the target false-positive rate were tightened to 0.1% instead, and whether that would violate the C1 budget as currently derived.
  • Q17. §20's split-brain containment (FM-8, §23) relies on Raft's higher-term-wins safety property — under what specific §22 threat (not a normal partition) could an attacker exploit term escalation to force repeated, disruptive re-elections without ever winning quorum?
  • Q18. §11 documents SnapshotHandle as immutable and reference-counted with no persistence — if a future requirement demanded resuming a long-paginated query (§19) across a process restart, what would have to change about §11's type, and which invariant in §7 would that change put at risk?

30. Mental Models & First Principles

  • MM1 — WAL-Before-Visibility Is a Total Order, Not a Suggestion. Durability and visibility are two different clocks that compose in exactly one direction; predicts that any "fast path" publishing before the fsync callback reintroduces acknowledged-write loss; the bug class it prevents is a premature-ack race under load; applies in §12 and §13.
  • MM2 — Immutability Turns Concurrency Bugs Into Lifecycle Bugs. Making segments immutable moves the hard problem from "torn read" to "who retires this and when"; predicts that use-after-free bugs cluster at generation retirement, not at read time; the bug class it prevents is a reader holding a reference past its snapshot's epoch; applies in §14 and §15.
  • MM3 — Compaction Is Amortized Read Cost Paid Up Front. Deferring compaction doesn't remove read cost, it postpones and compounds it; predicts unbounded read amplification if compaction debt is ever allowed to grow without a starvation-prevention floor; the bug class it prevents is "compaction is just an optimization we can skip under load" thinking; applies in §18 and §28.
  • MM4 — A Manifest Is a WAL for Metadata. The same crash-consistency discipline that protects mutation data must protect segment-visibility metadata, twice; predicts that skipping fsync-before- commit on the manifest reintroduces exactly the bug class WAL engineering already solved; applies in §17.
  • MM5 — Quorum Is a Latency/Consistency Exchange Rate. Every unit of consistency purchased via Raft quorum (§20) is paid for in one round-trip of latency; predicts the write-latency floor is bounded below by inter-zone RTT, not by CPU; the bug class it prevents is expecting replication to be latency-free; applies in §20 and §4.
  • MM6 — An Iterator Is a State Machine Pinned to a Point in Time. A snapshot's epoch, once acquired, must be invariant for the iterator's whole lifetime; predicts that any source added or removed after acquisition must be invisible to that iterator; the bug class it prevents is mid-scan visibility leaks after a concurrent flush; applies in §16.
  • MM7 — Backpressure Debt Always Surfaces Somewhere. Removing a backpressure signal doesn't remove the underlying pressure, it just moves the failure downstream and delays detection; predicts that an unbounded "just buffering" queue always resolves as an OOM, never as steady-state stability; applies in §6 and §18.
  • MM8 — Observability Is Part of the State Machine, Not a Sidecar. A state transition with no emitted signal is indistinguishable from a hang during an incident; predicts every undebuggable 3am incident traces back to a silent transition; the bug class it prevents is instrumenting only the happy path; applies in §21.

5. Required Reading

Books

  • Designing Data-Intensive Applications — Martin Kleppmann (2017), ch. 3, 5, 7, 9: LSM/B-tree storage tradeoffs, replication log semantics, transaction isolation; applied in §13 and §20.
  • Database Internals, Vol. 1 — Alex Petrov (2019), ch. 2–4, 7: page organization, B-Tree vs LSM layout, immutable segment structures with iterator semantics; applied in §11 and §15.
  • Transaction Processing: Concepts and Techniques — Jim Gray and Andreas Reuter (1993), ch. 9–11: WAL ordering, ARIES-style recovery, checkpointing for crash-safety; applied in §12 and §17.
  • Systems Performance, 2nd ed. — Brendan Gregg (2020), ch. 6, 8, 14: CPU profiling, IO analysis, lock-contention flamegraph methodology; applied in §28.
  • Linux Kernel Development, 3rd ed. — Robert Love (2010), ch. 4, 15–16: scheduler and memory-management interaction patterns relevant to NUMA-aware allocation and io_uring; applied in §14 and §28.
  • The Art of Multiprocessor Programming, rev. ed. — Maurice Herlihy and Nir Shavit (2012), ch. 9, 14: lock-free skiplists and memory-reclamation techniques to extract for the memtable; applied in §14.

Papers

  • "Bigtable: A Distributed Storage System for Structured Data" — Chang et al., 2006, OSDI: SSTable architecture and compaction model → the segment/manifest split this blueprint copies; applied in §15 and §17.
  • "The Log-Structured Merge-Tree (LSM-Tree)" — O'Neil, Cheng, Gawlick, O'Neil, 1996, Acta Informatica: formal LSM architecture, merge cost model → derives the write-amplification budget; applied in §18 and §32.
  • "WiscKey: Separating Keys from Values in SSD-Conscious Storage" — Lu, Pillai, Gopalakrishnan, Arpaci-Dusseau, Arpaci-Dusseau, 2016, FAST: value-log separation and SSD write-amplification analysis → informs segment block/value layout; applied in §15.
  • "The Bw-Tree: A B-tree for New Hardware Platforms" — Levandoski, Lomet, Sengupta, 2013, ICDE: lock-free indexing structures via delta chains → alternative considered and rejected for the memtable; applied in §14 and §34.
  • "ARIES: A Transaction Recovery Method" — Mohan, Haderle, Lindsay, Pirahesh, Schwarz, 1992, ACM TODS: WAL-based recovery, redo/undo, checkpointing semantics → the recovery model; applied in §12 and §23.
  • "In Search of an Understandable Consensus Algorithm (Raft)" — Ongaro and Ousterhout, 2014, USENIX ATC: leader election, log replication, safety proof → the replication model; applied in §20.
  • "Dynamo: Amazon's Highly Available Key-value Store" — DeCandia et al., 2007, SOSP: quorum read/write and vector-clock reasoning → informs the quorum-acknowledgment design; applied in §20.
  • "Space/Time Trade-offs in Hash Coding with Allowable Errors" — Burton H. Bloom, 1970, Communications of the ACM: the original bloom-filter analysis → sizing formula used for the bloom filter runtime; applied in §15 and §32.

Reference Implementations

  • rocksdb/rocksdb — study db/version_set.cc, db/compaction/, table/block_based/: compaction scheduling and manifest/version-set semantics; pitfall: do not copy RocksDB's column-family multiplexing wholesale; applied in §17 and §18.
  • cockroachdb/pebble — study internal/manifest, internal/compaction: deterministic-testing harness structure and iterator-correctness fixtures; pitfall: Pebble's manifest format is not RocksDB-wire-compatible, do not assume drop-in compatibility; applied in §17 and §26.
  • tikv/tikv — study components/raftstore/, components/engine_traits/: Raft-to-storage-engine integration boundary; pitfall: TiKV's engine_traits assumes multi-region sharding from day one, do not over-apply it in Phase 0; applied in §20.
  • postgres/postgres — study src/backend/access/nbtree: MVCC visibility semantics for secondary index scans; pitfall: Postgres's heap-vs-index visibility-map optimization does not transfer to a segment-immutable LSM design, do not port it; applied in §16.
  • google/leveldb — study db/db_impl.cc, table/block_builder.cc: minimal LSM implementation and block-builder layout; pitfall: LevelDB's single-threaded compaction is a correctness simplifier, do not copy the single-thread limitation; applied in §15 and §18.

RFCs / Specifications

  • RFC 7540 — HTTP/2 framing that gRPC transport relies on; applied in §12 and §22.
  • RFC 9110 — HTTP Semantics, pins down header/status semantics used by the Admin API's HTTP surface; applied in §22.
  • Protocol Buffers Language Guide (proto3) — Google specification for wire encoding used by ADR-05; applied in §11 and §13.
  • OpenTelemetry Protocol (OTLP) Specification v1.0 — pins down span/trace export encoding used by the tracing runtime; applied in §21.

Glossary (§36) · 42 terms · site-wide glossary

SSTable
Immutable sorted-string table; this blueprint's segment format follows the pattern.
WAL
Write-ahead log; the durability boundary enforced by I1.
MVCC
Multi-version concurrency control; the visibility model underlying snapshots (§8, §16).
Tombstone
Deletion marker that dominates all older writes for its key (I8).
Snapshot
A pinned, consistent visibility boundary identified by an epoch (§11).
Manifest
The canonical, transactional segment-metadata log (§17).
LSN
Log sequence number; the WAL's per-frame position identifier (§11).
Bloom Filter
Probabilistic membership structure used to skip disk IO on negative lookups.
Replay
Deterministic reapplication of WAL mutations to reconstruct state (P1, P8).
Segment
An immutable, persistent, disk-backed storage file (§8.4).
Flush
The event of persisting a frozen memtable to a new segment.
Compaction
Multi-segment merge rewrite that reduces read amplification (§18).
Quorum
Majority acknowledgment among Raft voters required before a write commits (I7).
Fsync
Forced durability synchronization to stable storage.
Epoch
A monotonically increasing snapshot-generation counter (§13.2).
Read Amplification
Extra physical reads required to answer one logical lookup.
Write Amplification
Extra physical writes caused by compaction rewriting data (C5, §32).
Split Brain
Two nodes simultaneously believing themselves leader (FM-8).
Orphan Segment
A persisted segment not referenced by any manifest generation (§17.2).
Replay Divergence
A follower's reconstructed state mismatching the leader's (FM-4).
Sequence ID
Per-shard, strictly monotonic mutation-ordering counter (I4).
Visibility Epoch
The snapshot generation boundary a query is pinned to (§8.1).
Memtable
The mutable, in-memory indexing structure accepting live writes (§14).
Skiplist
The lock-free probabilistic data structure backing the memtable (ADR-08).
Restart Point
A periodic uncompressed key marker within a prefix-compressed block (§15.2).
Sparse Index
A block-level key index enabling binary-search segment lookup (§8.4).
Manifest Generation
A strictly increasing counter identifying one manifest transaction (I13).
Checkpoint
A manifest operation that compacts the transaction-log history for faster replay.
Follower Catch-Up
The process by which a lagging replica resynchronizes with the leader (§20).
Leader Lease
The timeout mechanism bounding how long a leader can act without quorum contact.
Term
A Raft logical clock incremented on every leader election (§20).
Append-Entries
The Raft RPC used to replicate log entries to followers (§20.2).
Backpressure
A downstream-pressure signal that a producer must observe before enqueueing more work (P4).
Admission Control
Rejecting or delaying new work once a concurrency or resource budget is reached (§19.2).
Bounded Memory
The principle that no subsystem allocates without an enforced quota (P3).
Crash-Only Software
A design discipline assuming unannounced termination at any point (P2).
Deterministic Simulation
A test methodology driving all subsystems through one logical clock to reproduce failures byte-for-byte (§26).
Differential Testing
Comparing independently-derived reconstructions of the same state for divergence (§26).
Fixture
A named, version-controlled input/expected-output pair used for conformance testing (§10, §37).
Trust Boundary
A point where input crosses from untrusted to trusted context (§3.2, §22).
Blast Radius
The scope of impact a given failure can have, bounded by failure-domain isolation (P11).
Un-defer Trigger
The concrete condition under which a deferred feature (§35) becomes in-scope.
