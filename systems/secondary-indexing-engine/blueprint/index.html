1. Goal & Scope

Engineering definition. A secondary indexing engine is a storage subsystem that maintains one or more derived, sorted projections (secondary_key -> primary_key) over a mutable primary keyspace, under a single-writer append-ordered mutation log, with snapshot-isolated reads, crash-safe recovery, and byte-identical deterministic replay. It is not a database: it owns index maintenance, storage layout, compaction, and query execution over indexes; it delegates transaction coordination, SQL semantics, and multi-region consensus to the host system.

Build a production-grade, embeddable and distributed secondary indexing engine capable of:

  • maintaining strongly consistent secondary indexes over mutable primary records,
  • point lookups, range scans, prefix scans, and compound-key scans,
  • ingesting high-throughput mutation streams with deterministic ordering,
  • online compaction and crash recovery with bounded RTO,
  • deterministic, byte-identical replayable indexing semantics,
  • pluggable storage engines behind a stable iterator trait,
  • snapshot-isolated read queries via epoch-based visibility,
  • integration with upstream databases or KV engines as a sidecar or embedded library.

The engine sits beside — never replaces — LSM KV stores, document databases, event stores, object metadata systems, distributed coordinators, and analytical ingestion pipelines. It is architected as a standalone daemon, an embeddable library (cdylib/staticlib via FFI), and a Raft-replicated distributed indexing cluster.

System boundaries.

Provides:

  • secondary index maintenance over an external primary keyspace,
  • write-ahead logging, memtable, immutable segment storage, and multi-level compaction,
  • an indexing scheduler with backpressure-aware admission control,
  • MVCC visibility tracking via epoch-pinned snapshots,
  • a query planner and unified iterator subsystem (point/range/prefix/compound),
  • bloom-filter existence prefiltering,
  • Raft-based replication log shipping and follower catch-up,
  • a full observability stack (metrics, tracing, structured logs),
  • deterministic replay for debugging and follower reconstruction,
  • online, backward-compatible schema evolution for secondary key definitions.

Delegates (does not provide):

  • SQL parsing or a relational query language,
  • distributed multi-shard transactions or two-phase commit,
  • OLAP vectorized execution or columnar storage,
  • arbitrary join processing across unrelated keyspaces,
  • end-user authentication/authorization platform (only wire-level mTLS + scoped tokens),
  • multi-region (WAN) consensus beyond a single Raft replication group.

Non-goals for Phase 0. Globally distributed replication; a cost-based query optimizer; adaptive (learned) indexing; GPU/SIMD vector execution; compressed posting lists; full-text relevance ranking; geospatial indexing; multi-tenant billing.

Deferred (registered in full in §35, same anchors used here):

  • learned index structures → PhaseDeferred("§16")
  • HTAP-style analytical CDC ingestion integration → PhaseDeferred("§20")
  • tiered cloud object storage for cold segments → PhaseDeferred("§15")
  • adaptive cache admission (ML-driven) → PhaseDeferred("§15")
  • compressed segment storage (block compression codecs) → PhaseDeferred("§15")
  • online repartitioning / distributed index shards → PhaseDeferred("§20")

Target operators. Phase-0 deliverable — the following crates/services must build, link, and pass conformance:

  1. core-runtime — shared types, config, clock abstraction, error hierarchy, task supervisor.
  2. wal-engine — append-only durable log with replay.
  3. memtable-engine — concurrent skiplist mutable index.
  4. segment-engine — immutable on-disk SSTable-style segments with bloom filters.
  5. iterator-engine — unified merge-iterator abstraction across memtable/segment tiers.
  6. manifest-runtime — transactional metadata log for segment visibility.
  7. compaction-runtime — multi-level compaction scheduler.
  8. query-runtime — point/range/prefix/compound query execution over snapshots.
  9. replication-runtime — Raft-backed log shipping and follower catch-up.
  10. metrics-runtime — Prometheus exporter and registry.
  11. tracing-runtime — OpenTelemetry span propagation.
  12. admin-api — compaction control, topology, segment diagnostics, repair.
  13. operator-cli — inspection, replay, and repair tooling.
  14. Deterministic replay harness + conformance-fixture suite (see §26).

What later phases unlock: distributed index shards, follower reads at the edge, tenant isolation, online repartitioning, adaptive (learned) indexing, compressed segment storage, transactional CDC ingestion from upstream databases.

Recommended language: Rust. Rationale — deterministic ownership semantics remove a whole class of use-after-free/data-race bugs in the lock-free memtable and iterator paths (§14, §16); low-level memory control is required for mmap-backed segment readers (§15); the tokio + io_uring ecosystem gives predictable tail latency under compaction pressure; cargo-fuzz and criterion give mature, zero-setup fuzzing/benchmarking; a stable C ABI via cdylib supports the embedded deployment mode. Rejected: Go (GC pause unpredictability collides directly with the p99 point-lookup budget under compaction pressure, §4); C++ (manual ownership makes the epoch-reclamation discipline in §14 error-prone at this team size); Java (heap amplification and GC interaction with mmap-backed segments defeats the read-amplification model in §15/§28); Zig (ecosystem immaturity for distributed tracing/metrics as of this writing makes §24 hard to satisfy without hand-rolled exporters).

Prerequisites. OS internals and virtual memory; page-cache behavior; lock-free concurrency and epoch reclamation; async runtimes; storage-engine internals (LSM trees, B+Trees); WAL and ARIES-style recovery; distributed systems and Raft consensus; binary serialization; TCP/HTTP2 internals; NUMA behavior; Linux perf tooling (perf, flamegraphs); tracing systems; crash consistency and filesystem semantics; SSD internals (FTL, write amplification); bloom filters and probabilistic data structures.

2. Why Build This

Systems knowledge developed: storage-engine internals; crash consistency and ARIES-style recovery; MVCC visibility semantics; compaction scheduling under backpressure; lock-free concurrent iteration; deterministic replay systems; Raft-based replication; snapshot-isolation semantics; low-latency query execution under tail-latency budgets.

Historical relevance. Secondary indexing is foundational to PostgreSQL's index access methods, RocksDB's ColumnFamily-based secondary index patterns, Cassandra's SSTable-backed local/SASI indexes, Lucene's segment architecture, FoundationDB's layered indexing, and DynamoDB's Global Secondary Indexes. This project reconstructs the mechanics behind all six from first principles: one mutation log, one MVCC visibility model, one compaction scheduler, one replicated log.

Engineering muscle developed: ownership discipline under unsafe-adjacent lock-free code; binary/wire compatibility management across rolling upgrades; storage-layout reasoning (block, bloom, footer); scheduler design under starvation constraints; performance analysis via flamegraphs and tail-latency histograms; observability engineering; failure-domain isolation; replay-based debugging; deterministic simulation testing.

Production concepts exercised: WAL replay under torn writes; compaction backpressure and write stalls; online secondary-key schema migration; replication-lag management; operator observability; rolling upgrades under wire-compatibility gates; storage-corruption detection and segment repair.

3.2 Subsystem Responsibilities

Client Applications — untrusted external producers/consumers over gRPC, embedded FFI, or a binary protocol. Every payload crosses a validation boundary before entering a runtime state machine.

Query API — query decoding, authentication hooks (mTLS + scoped token, §22), timeout propagation, request shaping, protocol negotiation. Never touches storage directly; every read goes through Request Coordination.

Admin API — compaction control, runtime metrics, replication topology, segment diagnostics, repair tooling. Isolated into a separate thread/task pool from query execution (I6, §7) so an admin storm cannot starve queries.

Request Coordination — the single concurrency-isolation boundary: snapshot acquisition, scheduler assignment, cancellation propagation, admission control, token-bucket rate limiting. All backpressure signals (P4, §6) originate or terminate here.

Query Runtime — point lookups, range/prefix/compound scans, merge iteration, MVCC visibility filtering, bloom prefiltering. Designed for O(1) bounded memory per in-flight query (§4).

Mutation Runtime — index mutation application, write sequencing, WAL append ordering, visibility timestamp (sequence ID) assignment. Guarantees deterministic mutation ordering (P1, §6).

Snapshot Manager — epoch-based reference tracking for consistent visibility windows: snapshot pinning, compaction-visibility safety, replay determinism. The sole authority for "what generation is visible now."

WAL Manager — append-only durability, segment rotation, checksum validation, replay scanning. Defines the crash-recovery boundary (I1, §7): nothing crosses it un-fsynced.

Memtable Engine — mutable in-memory indexing: lock-free skiplist writes, lock-free reads via epoch reclamation, immutable freeze transition on flush trigger.

Iterator Engine — one iterator trait (§11) implemented uniformly over memtables, frozen memtables, and persistent segments; the query runtime never special-cases a storage tier.

Segment Manager — SSTable-style lifecycle: file descriptors, mmap ownership, segment metadata, publication/retirement.

Compaction Scheduler — merge compactions, tombstone pruning, level balancing, rewrite prioritization, all snapshot-safe (never rewrites a segment a pinned snapshot still needs).

Bloom Filter Runtime — probabilistic existence checks that cut disk IO for point lookups on absent keys (ADR-04-adjacent design driver, §28).

Manifest Runtime — the canonical storage-topology log. Every segment-visibility transition is serialized through a manifest commit (I2, §7) — this is the atomicity boundary for the whole storage layer.

Persistent Segments — immutable, disk-backed, mmap-read files: sorted key blocks, sparse block index, bloom filter, checksum trailer, metadata footer (§8.4).

Replication Runtime — Raft integration, log shipping, snapshot replication, follower synchronization, replay-order verification.

Peer Nodes — remote members of the Raft replication group; the network trust boundary (§22) starts here.

Trust boundaries: Client Applications → Query/Admin API (untrusted input validation); Replication Runtime → Peer Nodes (mutually authenticated, still subject to term/sequence replay checks). Concurrency boundaries: Request Coordination (admission), Memtable Engine (epoch reclamation), Compaction Scheduler (IO isolation from query pool). Persistence boundary: WAL Manager and Manifest Runtime, the only two places an fsync is load-bearing for correctness. Protocol boundary: Query/Admin API (gRPC framing) and Replication Runtime (Raft RPC framing). Queues: the append-entries pipeline between WAL Manager and Replication Runtime, and the compaction job queue between Segment Manager and Compaction Scheduler.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every replay path must produce byte-identical logical state from the same WAL prefix · Tradeoff: forbids wall-clock timestamps, unordered-map iteration, and any nondeterministic tie-break in comparators · Operational: replay-based debugging becomes reliable and replicas provably converge · Violated: replay diverges from live state, and follower reconstruction silently drifts (FM-4, §23).
  • P2 — Crash-Only Semantics. Rule: every subsystem must assume unannounced termination at any instruction boundary · Tradeoff: no clean-shutdown-only code paths are permitted; startup recovery must be the only recovery path · Operational: one recovery code path to test instead of two · Violated: a "normal shutdown" path silently becomes the only tested path and crash recovery rots.
  • P3 — Bounded Memory Usage. Rule: no subsystem may allocate without a quota it can be charged against · Tradeoff: adds allocator-accounting overhead on every mutation · Operational: OOM becomes a config error, not a production incident · Violated: an unbounded memtable or iterator heap grows until the OOM killer fires mid-compaction (FM-6, §23).
  • P4 — Backpressure Everywhere. Rule: every producer must observe and react to downstream queue pressure before enqueueing more work · Tradeoff: adds latency under load in exchange for stability · Operational: WAL and replication queues degrade gracefully instead of falling over · Violated: WAL amplification cascades into OOM and replication collapse (FM-5, §23).
  • P5 — Immutable Persistent Structures. Rule: a published segment is never modified in place · Tradeoff: requires compaction to rewrite rather than patch, costing write amplification · Operational: lock-free reads and deterministic snapshots fall out for free · Violated: a live reader observes a torn segment write mid-mutation.
  • P6 — Observability by Default. Rule: every state transition emits a metric, a trace span, and a structured log field · Tradeoff: instrumentation overhead on the hot path (§28) · Operational: every incident is diagnosable from telemetry alone, without attaching a debugger to production · Violated: an operator cannot distinguish "slow" from "stuck" during an incident.
  • P7 — Explicit Ownership. Rule: ownership transfer of any buffer or handle must be visible in the type signature (owned vs. borrowed vs. ref-counted) · Tradeoff: more verbose APIs than "just pass a pointer" · Operational: use-after-free and double-free become compile-time errors, not runtime incidents · Violated: a segment mmap is unmapped while an iterator still holds a slice into it.
  • P8 — Replayability First. Rule: every mutation that reaches the memtable must be replayable from the WAL alone, with no side-channel state · Tradeoff: every in-memory structure needs a deterministic reconstruction path from WAL records · Operational: crash recovery and follower bootstrap share one code path · Violated: an in-memory-only counter (e.g., an approximate cardinality estimate) diverges silently after restart.
  • P9 — Stable Wire Compatibility. Rule: protocol evolution must preserve rolling upgrades across at least N and N+1 versions · Tradeoff: forbids removing or renumbering a protobuf field ever · Operational: a cluster can be upgraded one node at a time without a coordinated stop-the-world · Violated: a mixed-version cluster during rollout rejects valid RPCs and replication stalls.
  • P10 — Storage Corruption Detection. Rule: every persisted structure (WAL frame, segment block, manifest record) carries a checksum verified on every read · Tradeoff: CPU cost of CRC32C on every read path · Operational: silent bit-rot becomes a detected, alertable event instead of a wrong answer · Violated: a flipped bit in a segment block returns a wrong query result with no signal.
  • P11 — Isolation of Failure Domains. Rule: a failure in compaction, replication, or admin must not be able to terminate the query-serving path · Tradeoff: requires separate task pools/thread budgets per subsystem (§4) instead of one shared pool · Operational: a compaction panic degrades write throughput but reads keep serving · Violated: a single panicking compaction task takes down the whole process, including live queries (FM-3, §23).
  • P12 — Monotonic Visibility. Rule: a pinned snapshot's epoch never observes a partially-applied visibility transition · Tradeoff: requires the manifest commit to be atomic with respect to every concurrent snapshot acquisition · Operational: query results are always a consistent point-in-time view, never a torn mix of two generations · Violated: a range scan returns some keys from generation N and others from N+1, corrupting aggregate results downstream.

Debugging methodology: every invariant above has exactly one assertion in the deterministic simulator (§26) that fires the moment the invariant is violated, never downstream of it. The simulator drives all subsystems through a single logical clock so that a violation is reproducible byte-for-byte from the failing seed — one assertion per invariant, checked on every simulated tick, never sampled.

12. Phase 0 — Workspace, Runtime & Correctness Kernel

12.1 Objectives

Stand up the deterministic build/runtime skeleton and the correctness kernel every later phase depends on: config loading, clock abstraction, error hierarchy, task supervision, and the deterministic-simulation test harness. Constraints introduced: no subsystem may call SystemTime::now() directly (ADR-20); no unbounded task spawn without a supervisor budget (P3); every crate must build under the pinned toolchain in rust-toolchain.toml.

12.2 Detailed Implementation Steps

  • Initialize the Cargo workspace (Cargo.toml) with one member per crate in §10; pin the compiler via rust-toolchain.toml (ADR-19 reproducibility).
  • core-runtime/src/errors.rs: define the shared error hierarchy (RuntimeError, StorageError, ProtocolError) as enum signatures with #[non_exhaustive] for P9 wire-compatible growth.
  • core-runtime/src/clock.rs: define a Clock trait (now_ns(), monotonic_ns()) with a SystemClock and a FakeClock implementation — the P1/ADR-20 determinism anchor for every later timestamp.
  • core-runtime/src/supervisor.rs: task supervisor with a bounded spawn budget (I6-adjacent isolation precursor) and panic-policy hook per Herlihy & Shavit (2012) structured-concurrency practice.
  • core-runtime/src/allocator.rs: wire jemalloc (ADR-27) as the global allocator; expose fragmentation metrics.
  • core-runtime/src/config.rs: structured TOML config loader (ADR-25) with schema validation.
  • Configure CI (.github/workflows/ci.yml) to run unit + conformance + cargo-fuzz smoke (ADR-13, ADR-14).
  • Add the deterministic test runtime: a single logical-clock driver that runs every subsystem against FakeClock, satisfying the P1 determinism anchor for the whole simulator described in §7's closing paragraph.
  • Add fault-injection hooks (crash-point markers) consumed by the crash-simulation harness (§23).
  • Define repository conventions (module boundaries mirroring §10) and the docs pipeline.

12.3 Deliverable

A runnable runtime skeleton: cargo build --workspace succeeds, cargo test --workspace passes, the metrics endpoint (/metrics) serves an empty Prometheus registry, and structured JSON logs are emitted on startup with build_sha, rustc_version, and config_hash fields.

12.4 Acceptance Criteria

  • CI green on 3 consecutive commits with zero flakes.
  • Binary is bit-for-bit reproducible across 2 clean-room builds (sha256sum match, ADR-19).
  • Startup-to-ready time < 30 sec (§4 cold-startup budget).
  • conformance/config/config_valid.toml loads with zero errors; config_invalid_missing_port.toml rejects with a typed ConfigError::MissingField("port").

12.5 Conformance Fixtures

  • conformance/config/config_valid.toml — full valid node config; expected: loads, all fields populated.
  • conformance/config/config_invalid_missing_port.toml — missing required port key; expected: typed rejection, not a panic.
  • conformance/metrics/metrics_registry_snapshot.json — golden metrics-registry shape after zero-traffic startup; expected: exact metric-name set match (regression guard).

12.6 Pitfalls

  • Nondeterministic config-key iteration order leaking into a hash computed over config (root cause: using HashMap instead of BTreeMap; detect via replay diff; recover by switching to an ordered map — violates P1 otherwise).
  • Allocator fragmentation under repeated small-object churn in the supervisor task queue (root cause: jemalloc arena sizing defaults; debug via jemalloc-ctl stats; signal: RSS creep with flat live-set; recover by tuning arena count).
  • Unstable tracing span IDs across restarts breaking correlation in long-running incident timelines (root cause: span-ID generator seeded from wall clock instead of a persisted counter; detect via duplicate span IDs in OTLP export; recover by persisting the counter in the manifest).

12.7 Performance Concerns

  • Allocator fragmentation under sustained small-object churn (jemalloc arena tuning, §28).
  • Runtime task explosion if the supervisor budget (P3) is misconfigured too high for the core count.
  • Lock contention in the metrics registry under high-cardinality label churn — mitigated by sharding the registry per subsystem.

12.8 Edge Cases

  • Partial config overrides via environment variables conflicting with file values — precedence must be deterministic (env > file, documented, tested).
  • Panic during startup before the supervisor is installed — must still emit a structured log to stderr, not swallow the panic.
  • Duplicate metric registration from two crates registering the same metric name — must fail fast at startup, not silently overwrite.

12.9 Failure Analysis

Runtime-bootstrap failure blocks every higher-level subsystem — this is the single highest blast- radius failure in the system, containment is "the process never reaches ready state," and the detection signal is the readiness probe timing out. Forensics: startup logs plus the config_hash field pinpoint whether the failure is config-shape or environment-shape. No partial-degraded mode is possible or attempted at this phase — a Phase-0 failure is binary.

12.10 Operational Notes

Metrics: runtime_startup_duration_ms, runtime_task_spawn_total, allocator_fragmentation_ratio. Tracing spans: runtime.bootstrap, runtime.config_load. Structured-log fields: build_sha, config_hash, rustc_version. Deployment: single static binary; rollback is a binary swap plus restart, no migration needed at this phase.

13. Phase 1 — WAL Engine

13.1 Objectives

Implement crash-recoverable, durable append-only logging — the persistence boundary anchoring I1 and the ARIES-style recovery model (Mohan et al., 1992). Constraint introduced: no mutation may become query-visible before its WAL frame's fsync completes (I1).

13.2 Detailed Implementation Steps

  • wal-engine/src/frame.rs: define the WALRecord frame layout (§8.3, §11) — FrameHeader{crc32c, length} + protobuf MutationRecord payload; CRC32C per ADR-23.
  • wal-engine/src/writer.rs: async append queue with credit-based backpressure (P4, ADR-21); batches writes up to the 256 MB buffer budget (§4) before an fsync boundary.
  • wal-engine/src/rotation.rs: segment rotation policy and retention; sparse index for fast replay seek.
  • wal-engine/src/replay.rs: replay scanner implementing the ARIES redo pass — stops at the first unrecoverable torn frame and reports the last valid LSN (I4 monotonicity check during replay).
  • Add torn-write detection: a frame whose declared length exceeds remaining bytes in the segment is quarantined, not assumed corrupt-but-continuable.
  • Add sync batching and an IO-scheduler isolation lane so WAL fsync never queues behind compaction IO (P11 failure-domain isolation applied to IO scheduling).
  • Add the WAL inspector CLI subcommand (operator-cli/src/inspect.rs) and crash-simulation test fixtures via the Phase-0 fault-injection hooks (§12.2).
  • Add WAL archival hooks for cold retention beyond the active retention window.

13.3 Deliverable

A WAL subsystem that survives kill -9 at any byte offset and replays deterministically to the last fsync'd frame; operator-cli inspect wal <path> prints frame count, last LSN, and corruption status.

13.4 Acceptance Criteria

  • Zero acknowledged-write loss across 10,000 injected kill -9 crash points (§4 durability budget).
  • WAL append p99 < 2 ms at 250,000 ops/sec sustained (§4 throughput budget).
  • Replay of a 256 MB WAL completes in < 90 sec (§4 WAL-replay budget).
  • wal_crc_failure.bin is detected and quarantined, never silently accepted.

13.5 Conformance Fixtures

  • conformance/wal/wal_valid.bin — clean 3-frame log; expected: replay yields 3 records, no errors.
  • conformance/wal/wal_partial_frame.bin — torn final frame (simulated crash mid-append); expected: replay stops at last complete frame, reports truncation point.
  • conformance/wal/wal_crc_failure.bin — single bit-flipped frame; expected: ChecksumMismatch at the exact frame offset, replay of prior frames still succeeds (I12).

13.6 Pitfalls

  • fsync starvation when the IO scheduler lane is shared with compaction reads (root cause: missing IO isolation, P11 violation; detect via WAL-append p99 spiking during compaction; recover by enforcing the dedicated IO lane from §13.2).
  • Frame alignment bugs on non-512-byte-aligned appends causing partial-sector torn writes on power loss (root cause: skipping O_DIRECT alignment; detect via replay fixture wal_partial_frame.bin; recover by padding frames to sector boundaries).
  • Torn-append replay misclassifying a legitimately short final frame (end-of-log) as corruption (root cause: no explicit "log tail" marker; detect via false-positive corruption alerts on clean shutdown; recover by writing an explicit end-of-segment marker on graceful rotation).

13.7 Performance Concerns

  • Syscall amplification from per-record fsync instead of batched fsync (batching per §4 buffer budget is mandatory, not optional).
  • Queue saturation under burst writes exceeding the 256 MB buffer — must backpressure (P4) the Mutation Runtime, not silently drop.
  • Batching-latency tradeoff: larger batches raise throughput but risk breaching the 2 ms p99 append budget — tune batch window, not batch size, to the latency budget.

13.8 Edge Cases

  • Disk full mid-append — must fail the append with a typed error, never partially write a frame.
  • Partial fsync (kernel reports success but power loss occurs in the drive's write cache) — mitigated operationally by requiring hdparm-verified write-cache flush on target NVMe hardware, documented in the deployment runbook, not solvable in software alone.
  • Replay after a manifest rollback (§17) must re-derive the correct replay start LSN from the rolled- back manifest generation, not the pre-rollback one.

13.9 Failure Analysis

WAL corruption triggers degraded (read-only) recovery mode: writes are rejected until an operator confirms the quarantine boundary via operator-cli inspect wal --repair. Blast radius is bounded to the shard whose WAL is corrupt (P11); other shards keep serving. Detection is the I12 checksum- mismatch metric; forensics is the frame offset plus the wal_crc_failure.bin-style artifact retained for postmortem.

13.10 Operational Notes

Metrics: wal_append_latency_ms (p50/p95/p99), wal_fsync_duration_ms, wal_replay_duration_ms, wal_corruption_detected_total. Tracing spans: wal.append, wal.fsync, wal.replay. Structured-log fields: lsn, frame_length, crc32c. Rollback: WAL format version is in the frame header (P9); a rollback to a prior binary must refuse to read a newer frame version rather than misparse it.

14. Phase 2 — Memtable Engine

14.1 Objectives

Implement the mutable in-memory indexing structure: a lock-free skiplist with epoch-based reclamation (Herlihy & Shavit, 2012, ch. 14), satisfying P5's freeze-to-immutable transition and I10's iterator- validity guarantee. Constraint introduced: no subsystem may allocate memtable memory outside the 2 GB budget (§4) without triggering a flush.

14.2 Detailed Implementation Steps

  • memtable-engine/src/skiplist.rs: lock-free skiplist keyed by (secondary_key, sequence_id) with atomic CAS-based node insertion — the ADR-08 concurrency decision applied.
  • memtable-engine/src/epoch.rs: epoch-based reclamation (crossbeam-epoch pattern) so readers never observe a freed node; ties directly to I10 (iterator validity while snapshot pinned).
  • memtable-engine/src/freeze.rs: immutable freeze transition — an atomic pointer swap from "active" to "frozen," never a copy, preserving P5.
  • Add mutation batching at the Mutation-Runtime boundary before skiplist insertion, matching the WAL batch cadence from §13.2.
  • Add memory accounting: every insert increments an atomic byte counter charged against the 2 GB budget (P3); crossing 90% triggers a flush signal.
  • Add iterator integration implementing the IndexIterator trait from §11 directly over skiplist nodes.
  • Add visibility filtering: a node is visible to a snapshot iff its sequence_id <= snapshot.sequence_upper_bound (I5).
  • Add tombstone semantics: a Delete node dominates any older Put for the same key during merge (I8).
  • Add duplicate-key resolution: highest sequence_id wins per key within one memtable generation.
  • Add snapshot pinning integration with the Snapshot Manager (§13.2 of the architecture, §7 I10).

14.3 Deliverable

A concurrent, lock-free mutable index that accepts 250,000 writes/sec from a single writer while serving unlimited concurrent lock-free readers, and freezes deterministically on flush trigger.

14.4 Acceptance Criteria

  • Zero use-after-free or ABA violations across a 24-hour loom-style concurrency stress run.
  • Freeze transition completes in < 1 ms and is observed atomically by all concurrent iterators (I10).
  • Memory accounting stays within 2 GB ± 1% under the write-throughput budget (§4).
  • duplicate_key_visibility.json resolves to the highest-sequence-ID record, verified byte-for-byte.

14.5 Conformance Fixtures

  • conformance/memtable/memtable_insert_replay.json — WAL-derived insert sequence; expected: post-replay memtable state matches golden key/value/sequence triples exactly.
  • conformance/memtable/duplicate_key_visibility.json — three writes to one key at increasing sequence IDs; expected: only the highest-sequence write is visible under any snapshot ≥ it.

14.6 Pitfalls

  • ABA hazards in CAS-based node insertion under high contention (root cause: reusing a freed node pointer before epoch advance; detect via the loom stress harness; recover by tightening the epoch-advance interval).
  • Epoch leaks when a reader task is cancelled mid-traversal without releasing its epoch guard (root cause: missing RAII drop on cancellation; detect via monotonically growing epoch-lag metric; recover by wrapping every iterator in a guard that releases on Drop).
  • Tombstone resurrection when a compaction merges an older segment after its tombstone's memtable generation was already flushed and discarded (root cause: tombstone GC racing flush; detect via the differential iterator test in §16; recover by delaying tombstone GC past the oldest pinned snapshot).

14.7 Performance Concerns

  • Pointer chasing in skiplist traversal degrades cache locality versus a flat sorted array — accepted tradeoff for lock-free concurrent mutation (ADR-08).
  • Allocator contention on the hot insert path — mitigated by per-shard arena pools (ADR-27 jemalloc arenas).
  • Cache-line false sharing between the atomic byte-counter (§14.2) and adjacent skiplist metadata — padded to a cache-line boundary.

14.8 Edge Cases

  • Oversized keys (> 4 KB secondary key) — rejected at the Mutation Runtime boundary before reaching the memtable, not truncated silently.
  • High tombstone density (> 50% of live keys) — triggers an early compaction hint rather than waiting for the normal level-score trigger (§18).
  • Rapid freeze churn under bursty write patterns — bounded by a minimum inter-freeze interval to avoid flush-storm segment proliferation.

14.9 Failure Analysis

Memtable corruption (detected via an internal consistency assertion, not a checksum — memtables are never persisted directly) is isolated and recovered purely through WAL replay (P8): the frozen memtable is discarded and reconstructed from the WAL tail. Blast radius is bounded to the active shard; other shards' memtables are independent allocation domains.

14.10 Operational Notes

Metrics: memtable_bytes_used, memtable_flush_trigger_total, memtable_freeze_duration_ms, epoch_lag_max. Tracing spans: memtable.insert, memtable.freeze. Structured-log fields: generation_id, bytes_used, flush_reason. Compatibility: in-memory only, no wire or disk format, so no cross-version compatibility burden — reconstruction is always from the current WAL format.

15. Phase 3 — SSTable Segment Engine

15.1 Objectives

Implement immutable, on-disk, mmap-backed segments — the Bigtable/LevelDB SSTable pattern (Chang et al., 2006; O'Neil et al., 1996) — satisfying P5 and I3. Constraint introduced: a segment's bytes never change after the manifest publishes it (I3); every read verifies a checksum before trusting bytes (I12, P10).

15.2 Detailed Implementation Steps

  • segment-engine/src/block.rs: block format with restart points (LevelDB-style prefix-compressed keys within a block, per Petrov 2019 ch. 3); block size tuned against the page-cache line budget.
  • segment-engine/src/bloom.rs: bloom filter runtime per Bloom (1970) sizing formula, one filter per segment, false-positive rate tuned against the read-amplification target (§28, C3 §32).
  • segment-engine/src/builder.rs: segment builder — sorted-key streaming write, sparse block index, bloom filter, checksum trailer, metadata footer (§8.4).
  • segment-engine/src/reader.rs: mmap-backed reader with binary-search block lookup; page faults are charged against the 4 GB segment-mmap budget (§4).
  • Add atomic publication: a segment is renamed into place and fsync'd on its containing directory before any manifest record references it (I2/I3 ordering).
  • Add a corruption scanner (background, low-priority) that re-verifies every block checksum on a configurable cadence, feeding the < 60 sec corruption-detection budget (§4).
  • Add compatibility versioning in the footer: segment-format version field, backward-read support for the previous two major versions (§25).

15.3 Deliverable

A queryable, immutable SSTable-equivalent segment format: operator-cli inspect segment <path> dumps header, block count, bloom-filter size, and footer checksum; range scans against a built segment return sorted, checksum-verified results.

15.4 Acceptance Criteria

  • Range scans over a 1M-key segment return results in sorted order with zero checksum failures.
  • Segment reopen after process restart is byte-for-byte deterministic (P1).
  • Bloom filter false-positive rate ≤ 1% at the configured bit budget (derived in C3, §32).
  • malformed_footer.bin and corrupted_bloom.bin are both rejected at open time, not at first read.

15.5 Conformance Fixtures

  • conformance/segment/segment_v1.bin — golden 3-block segment; expected: exact key/value/checksum round-trip.
  • conformance/segment/malformed_footer.bin — truncated footer; expected: SegmentOpenError:: InvalidFooter at open, not a panic mid-scan.
  • conformance/segment/corrupted_bloom.bin — bit-flipped bloom bitmap; expected: checksum mismatch detected before the filter is trusted for prefiltering (I12).

15.6 Pitfalls

  • mmap invalidation when a segment file is unlinked while a reader still holds a mapped view on Linux (root cause: not holding an open FD alongside the mapping; detect via SIGBUS under load; recover by keeping the FD open until the last mmap view is dropped).
  • Sparse-index drift when block boundaries shift between builder versions without a footer version bump (root cause: skipping ADR-adjacent versioning discipline; detect via the compatibility conformance suite in §25; recover by bumping the segment-format version).
  • Restart-point corruption causing incorrect prefix-decompression mid-block (root cause: off-by-one in restart-interval encoding; detect via the differential iterator test in §16; recover by rebuilding the segment from source WAL/memtable state).

15.7 Performance Concerns

  • Page faults on cold mmap reads dominate p95/p99 latency (§4) — mitigated by bloom prefiltering before touching the mmap region at all.
  • Read amplification from block size too large relative to average value size — tuned against the segment-mmap page-cache budget (§4).
  • Branch prediction in binary-search block lookup — mitigated by a flat sorted index array rather than a pointer-chasing tree.

15.8 Edge Cases

  • Empty blocks (zero keys) at segment boundaries from a degenerate compaction input — must be skipped by the iterator, not treated as an error.
  • Giant keys near the 4 KB cap (§14.8) spanning multiple restart intervals within one block.
  • Overlapping key ranges between segments at the same level (should not occur post-compaction; the scanner flags this as a manifest-consistency violation, not a silent merge).

15.9 Failure Analysis

Segment corruption is quarantined before publication (the builder verifies its own output before the atomic rename in §15.2) and after publication via the background scanner. A corrupt published segment is marked Obsolete in the manifest and excluded from future reads while a repair job rebuilds it from still-valid overlapping segments or the WAL. Blast radius is the key range covered by that one segment.

15.10 Operational Notes

Metrics: segment_open_duration_ms, segment_page_fault_total, bloom_false_positive_rate, segment_checksum_failures_total. Tracing spans: segment.build, segment.open, segment.scan. Structured-log fields: segment_id, level, key_min, key_max. Migration: reading N-2 major format versions is mandatory during rolling upgrade (§25); writing is always current-version only.

16. Phase 4 — Iterator Runtime

16.1 Objectives

Build the unified k-way merge-iterator execution layer over memtables, frozen memtables, and segments — the single read path referenced from §3's Iterator Engine box — satisfying I5, I8, I10, and I11. Constraint introduced: an iterator must never allocate unbounded heap space regardless of fanout depth (P3 applied to iteration).

16.2 Detailed Implementation Steps

  • iterator-engine/src/heap.rs: min-heap ordering over per-source cursors, bounded to the number of active sources (≤ 8 levels per §4's write-amplification ceiling) — the P3 bounded-memory anchor for iteration.
  • iterator-engine/src/merge.rs: k-way merge implementing the IndexIterator trait (§11) uniformly across memtable, frozen-memtable, and segment sources — no storage-tier special-casing (architectural invariant from §3.2).
  • iterator-engine/src/visibility.rs: MVCC visibility filter applying I5 (no mixed generations) and I8 (tombstone dominance) at merge time, not as a post-filter pass.
  • Add seek optimization: bloom-prefiltered segment sources skip a heap slot entirely on a negative bloom check (ties to §15.2's bloom runtime).
  • Add iterator invalidation tracking tied to I10: an iterator holds a SnapshotHandle (§11) and asserts validity on every next() call.
  • Add prefix iteration and bounded reverse scans as specializations of the same merge core, not separate code paths (P1 — one deterministic ordering rule, not two).
  • Add cancellation support: a cancelled query's iterator releases its snapshot pin and heap allocation within one scheduler tick (ties to Request Coordination's cancellation propagation, §3.2).
  • Add replay fixtures validating iterator output against a WAL-replayed golden state (P8 applied to the read path).

16.3 Deliverable

A single iterator implementation serving point lookups, range scans, prefix scans, and compound-key scans uniformly; query-runtime never imports a memtable- or segment-specific type.

16.4 Acceptance Criteria

  • Range scans over a 3-memtable + 5-segment fixture return deterministic sorted output with zero duplicate visibility violations across 1,000 randomized differential-test runs (§26).
  • Iterator heap allocation stays ≤ 8 entries regardless of underlying source count (§4 fanout bound).
  • Cancellation releases all resources within 1 scheduler tick, verified via range_scan_fixture.json.
  • tombstone_visibility.json never resurrects a deleted key under any snapshot taken after the delete's sequence ID.

16.5 Conformance Fixtures

  • conformance/iterator/range_scan_fixture.json — mixed memtable+segment range scan; expected: exact sorted key sequence, no duplicates.
  • conformance/iterator/tombstone_visibility.json — delete-then-read-under-old-and-new-snapshot case; expected: old snapshot sees the value, new snapshot sees nothing (I5 + I8 combined).

16.6 Pitfalls

  • Heap instability when two sources report equal keys but different sequence IDs and the comparator doesn't tie-break deterministically (root cause: comparator ignoring sequence ID, violating P1; detect via non-reproducible scan order across identical runs; recover by making sequence ID the tie-break key).
  • Iterator starvation when one source's seek cost dominates and blocks heap progress under a shared scheduler budget — mitigated by a per-source seek-time budget with cooperative yielding.
  • Stale snapshot reads when a snapshot's pinned epoch is not correctly propagated to a newly opened segment source added mid-scan by a concurrent flush (root cause: race between flush publication and iterator source enumeration; detect via I5 differential check; recover by re-enumerating sources under the manifest's generation lock).

16.7 Performance Concerns

  • Heap allocation and rebalancing cost scales with source fanout — bounded by the 8-level ceiling (§4, C5 §32).
  • Branch misprediction in the visibility-filter hot path — mitigated by likely/unlikely hints on the common "visible, not tombstoned" branch.
  • Iterator fanout amplifies syscall/page-fault cost linearly with segment count at a given level — this is the direct driver of the compaction level-fanout choice in §18.

16.8 Edge Cases

  • Empty iterator chains (all sources exhausted or bloom-negative) must return a clean "no results," not an error.
  • Duplicate sequence IDs across two sources (should be impossible under I4; the merge asserts and fails loudly rather than silently picking one).
  • Rapid cancellation racing a concurrent flush publication — cancellation must win without leaking the snapshot pin.

16.9 Failure Analysis

Iterator-level corruption or panics are isolated to the single query request that triggered them (P11) — the panic is caught at the Query Runtime boundary, converted to a typed error, and does not affect other in-flight queries or the memtable/segment state underneath. Detection is the per-request error-rate metric; forensics replays the exact snapshot + source set from the request-scoped trace.

16.10 Operational Notes

Metrics: iterator_active_count, iterator_heap_depth, iterator_seek_duration_ms (histogram). Tracing spans: iterator.seek, iterator.merge_step. Structured-log fields: snapshot_epoch, source_count, cancel_reason. PhaseDeferred("§16") — learned index structures for seek optimization are deferred past Phase 0 scope; see §35 for the un-defer trigger.

17. Phase 5 — Manifest & Metadata Management

17.1 Objectives

Implement the authoritative storage-topology transaction log that makes every segment-visibility change atomic (I2, I13) — the manifest boundary called out in §3.2 as the sole authority for storage truth. Constraint introduced: no segment is ever query-visible except through a committed manifest record (I2).

17.2 Detailed Implementation Steps

  • manifest-runtime/src/manifest.rs: define the ManifestRecord transaction log (§11) — AddSegment, RemoveSegment, Checkpoint ops, binary-protobuf encoded (ADR-26).
  • manifest-runtime/src/generation.rs: strictly-increasing generation-ID allocator (I13); a generation number is never reused, mirroring the I4 sequence-ID discipline at the metadata layer.
  • manifest-runtime/src/orphan.rs: orphan-segment detection on startup — any on-disk segment file not referenced by the latest committed manifest generation is quarantined, not deleted immediately (safety margin for forensics).
  • Add transactional manifest writes: a manifest commit is itself WAL-style — write, fsync, then atomic rename of the manifest pointer file (ARIES checkpoint pattern, Mohan et al., 1992).
  • Add atomic swap + rollback handling: a failed commit rolls back to the last valid generation rather than leaving a half-written manifest (I2).
  • Add snapshot references: the manifest tracks the oldest pinned snapshot's generation so compaction (§18) knows the safe garbage-collection floor (I11 dependency).
  • Add manifest replay (startup path) and metadata inspection tooling (operator-cli inspect manifest).

17.3 Deliverable

A durable metadata subsystem where segment visibility transitions are atomic across crashes; operator-cli inspect manifest <path> dumps generation history, live segment set, and orphan list.

17.4 Acceptance Criteria

  • 100% of injected crash points during manifest commit (10,000 trials) recover to either the pre- or post-commit state, never a torn intermediate state (I2).
  • Manifest replay on a 100,000-segment history completes within the 30 sec cold-startup budget (§4).
  • Orphan detection correctly flags 100% of synthetically orphaned segments in manifest_partial_commit.bin-derived fixtures with zero false positives.

17.5 Conformance Fixtures

  • conformance/manifest/manifest_v1.bin — golden 50-generation history; expected: exact live-segment- set reconstruction.
  • conformance/manifest/manifest_partial_commit.bin — commit torn mid-write; expected: rollback to last valid generation, orphan segment flagged, no data loss (I2, I13).

17.6 Pitfalls

  • Split publication when two compaction jobs race to commit against the same generation number (root cause: missing single-writer serialization on manifest commits; detect via generation-collision assertion; recover by serializing all commits through one writer task).
  • Orphan leaks when the orphan scan runs before the manifest replay completes, missing segments referenced by a generation not yet loaded (root cause: ordering bug in startup sequence; detect via false-positive orphan reports after restart; recover by running orphan scan strictly after full replay).
  • Stale generation reuse after a rollback if the generation allocator isn't itself rolled back with the manifest (root cause: allocator state kept separate from manifest state; detect via I13 assertion; recover by deriving the allocator's next value from the replayed manifest, never from cached state).

17.7 Performance Concerns

  • Metadata fsync pressure: every commit is a synchronous durability point — batched under load via a commit-coalescing window, bounded so it doesn't breach the snapshot-acquisition latency budget (§4).
  • Manifest rewrite amplification if checkpoints are too infrequent, forcing long replay chains on startup — checkpoint cadence tuned against the 30 sec cold-startup budget.

17.8 Edge Cases

  • Manifest truncation (disk full mid-write) — must be detected as a torn commit, not accepted as a short-but-valid manifest.
  • Stale references from a segment deleted out-of-band (operator error, not through the manifest) — detected by the orphan/consistency scanner, alerted, not silently ignored.
  • Replay after a crash during a Checkpoint op specifically — the checkpoint itself must be idempotent to replay.

17.9 Failure Analysis

Manifest corruption triggers a read-only recovery mode cluster-wide for the affected shard: writes are rejected, reads continue against the last known-good generation, and an operator must run operator-cli inspect manifest --repair to confirm the rollback boundary before resuming writes. Blast radius is the shard; other shards' independent manifests are unaffected (P11).

17.10 Operational Notes

Metrics: manifest_commit_duration_ms, manifest_generation_current, orphan_segments_total. Tracing spans: manifest.commit, manifest.replay. Structured-log fields: generation, op_type, segment_id. PhaseDeferred("§15") — tiered cloud object storage for cold segments changes manifest record shape; deferred, un-defer trigger in §35.

18. Phase 6 — Compaction Runtime

18.1 Objectives

Implement multi-level, snapshot-safe compaction — the LSM merge-cost model formalized by O'Neil et al. (1996) — satisfying I11 (never rewrite a segment a pinned snapshot needs) while keeping write amplification within the C5 (§32) ceiling. Constraint introduced: compaction must never block or starve the query-serving path (P11).

18.2 Detailed Implementation Steps

  • compaction-runtime/src/scoring.rs: per-level compaction scoring (size-tiered within a level, leveled across levels), the classic RocksDB db/compaction/ scoring pattern (studied in §5, applied here per ADR-04's LSM choice).
  • compaction-runtime/src/scheduler.rs: job queue with priority by score; enforces the ≤ 8-level fanout ceiling (§4) that bounds both read amplification (§28) and iterator heap depth (§16.7).
  • compaction-runtime/src/throttle.rs: IO-isolated throttling — compaction IO runs in a separate io_uring submission queue from the WAL/query IO lanes (P11 applied to IO scheduling, echoing §13.6's WAL isolation).
  • Add tombstone pruning: a tombstone is only dropped once its sequence ID is older than every pinned snapshot's floor (I11, tracked via §17.2's snapshot-reference mechanism).
  • Add overlap detection: post-compaction segments at the same level must never have overlapping key ranges (I3-adjacent invariant, checked by the §15.9 background scanner).
  • Add compaction checkpoints so a crashed compaction job resumes rather than restarting from scratch.
  • Add snapshot-safe rewrites: before rewriting a segment set, the scheduler consults the manifest's oldest-pinned-snapshot floor (I11) and defers if a conflict exists.
  • Add starvation prevention: a minimum-age promotion rule guarantees no segment waits more than N compaction cycles regardless of score (avoids the classic "cold tail never compacts" LSM pathology).
  • Add cancellation support and compaction metrics.

18.3 Deliverable

An online compaction engine that reduces read amplification under sustained 250,000 ops/sec ingest without ever violating a pinned snapshot's view; operator-cli inspect compaction shows per-level debt and in-flight jobs.

18.4 Acceptance Criteria

  • Read amplification stays within the C5 (§32) derived ceiling (≤ 10× write amplification budget, §4) under 24-hour sustained-ingest soak testing.
  • Zero I11 (snapshot-safety) violations across 1,000 randomized concurrent compaction + long-running- snapshot differential-test runs (§26).
  • Compaction debt (bytes pending rewrite) converges to a steady-state bound within 15 minutes of a synthetic write-rate step change.

18.5 Conformance Fixtures

  • conformance/compaction/compaction_overlap_case.json — deliberately overlapping input-segment key ranges; expected: compaction detects and rejects, does not silently merge incorrectly.
  • conformance/compaction/tombstone_gc_case.json — tombstone older than the oldest pinned snapshot vs. tombstone newer than it; expected: only the former is pruned (I11).

18.6 Pitfalls

  • Compaction storms when the scoring function over-prioritizes one hot level, starving others (root cause: scoring normalization bug; detect via per-level debt divergence metric; recover by re- normalizing score against level target size, not absolute byte count).
  • Write stalls when compaction falls behind ingest and the memtable-flush path blocks waiting for level-0 headroom (root cause: missing backpressure signal from compaction debt to the Mutation Runtime, a P4 violation; detect via WAL-append latency correlating with compaction-debt metric; recover by wiring the credit-based backpressure from ADR-21 into the flush trigger).
  • Snapshot invalidation when a long-running snapshot's pin is not correctly consulted before a segment set is retired (root cause: race between §17.2's snapshot-reference update and the compaction scheduler's read of it; detect via I11 assertion; recover by making the snapshot-floor read and the compaction dispatch atomic under one lock).

18.7 Performance Concerns

  • Disk-IO amplification is the direct, measured cost of this phase — tracked against the C5 (§32) ceiling continuously, not just at soak-test time.
  • Cache churn: compacted segments evict hot block-cache entries for unrelated key ranges — mitigated by warming the cache with the new segment's first-touched blocks post-publication.
  • Scheduler imbalance across levels under skewed key distributions — mitigated by per-level worker budgets rather than one global worker pool.

18.8 Edge Cases

  • Compaction cancellation mid-rewrite (operator-triggered or shutdown) must leave the manifest in a consistent pre-compaction state (I2), never a half-published result.
  • Overlapping tombstones spanning a compaction boundary — the merge must preserve I8 ordering across the boundary, not just within one output segment.
  • Level saturation (a level's byte budget exceeded before the next compaction cycle runs) — triggers emergency promotion rather than waiting for the normal schedule.

18.9 Failure Analysis

A compaction-worker crash is recoverable via manifest replay (§17): the in-progress job's checkpoint (§18.2) lets it resume rather than restart, and the pre-compaction segment set remains valid and visible throughout (P11 — reads never see compaction as blocking). Blast radius is the affected level's compaction throughput, never correctness.

18.10 Operational Notes

Metrics: compaction_debt_bytes, compaction_jobs_active, compaction_write_amplification_ratio, compaction_starvation_age_max. Tracing spans: compaction.score, compaction.rewrite. Structured- log fields: level, source_segment_ids, target_level. PhaseDeferred("§15") — compressed segment storage codecs interact directly with compaction rewrite cost; deferred, see §35.

19. Phase 7 — Query Runtime

19.1 Objectives

Implement the externally accessible query-execution surface — point/range/prefix/compound scans over the Iterator Runtime (§16) — under the tail-latency budgets in §4. Constraint introduced: a query must be cancellable and resource-bounded regardless of client behavior (P3, P4).

19.2 Detailed Implementation Steps

  • query-runtime/src/planner.rs: translate a decoded query request into an iterator plan (source enumeration, bloom prefiltering decision, prefix/range bounds) — the query-side half of §16.2's merge core.
  • query-runtime/src/executor.rs: drive the planned iterator to completion or cancellation, applying timeout propagation from Request Coordination (§3.2) end-to-end, per Kleppmann (2017) ch. 9's consistency-under-timeout discussion.
  • query-runtime/src/pagination.rs: cursor-based pagination over a pinned snapshot (I10) so a paged scan cannot silently skip or duplicate keys across pages.
  • Add read admission control: a token-bucket limiter (ADR-21 credit model) gates new query admission once in-flight query count crosses the concurrency budget (§4, ≤ 128 threads).
  • Add query telemetry and tracing spans covering plan → snapshot-acquire → iterate → encode.
  • Add a query-cache hook point (result caching deferred past Phase 0; the hook exists, the cache does not).
  • Add backpressure signaling back to the Query API layer when admission control is saturated (P4).
  • Add result pagination limits (max page size) enforced server-side, not merely advisory.

19.3 Deliverable

An externally accessible query interface serving point lookups, range scans, and paginated compound- key scans with snapshot isolation; query_point_lookup.json and range_scan_limits.json pass as conformance gates.

19.4 Acceptance Criteria

  • Point-read p50/p95/p99 within 1 ms / 5 ms / 20 ms (§4) at 500,000 ops/sec sustained load.
  • Range scans stable (no memory growth, no duplicate/missing keys) across a 1-hour soak with 20,000 scans/sec (§4).
  • Snapshot isolation verified: a scan started before a concurrent write never observes that write (I5), across 1,000 randomized differential-test runs.
  • range_scan_limits.json's max-page-size case is enforced server-side (rejects, does not silently truncate).

19.5 Conformance Fixtures

  • conformance/query/query_point_lookup.json — point lookup against a mixed memtable/segment state; expected: exact value + sequence ID match.
  • conformance/query/range_scan_limits.json — pagination at and beyond the max page size; expected: exact page boundaries, explicit rejection beyond the cap.

19.6 Pitfalls

  • Runaway scans with no bound on iteration count when a client omits a limit (root cause: missing server-side default cap; detect via query-duration outlier metric; recover by enforcing a default max-scan-count even when the client requests "unbounded").
  • Cancellation leaks when a cancelled query's iterator (§16.9) isn't actually dropped promptly because the executor task is blocked on a syscall (root cause: cancellation checked only at await points; detect via iterator_active_count staying elevated post-cancel; recover by adding a cooperative cancellation check inside the merge loop, not just at task boundaries).
  • Timeout mispropagation when a sub-call (e.g., a segment page fault) doesn't inherit the parent request's deadline (root cause: missing deadline threading through §16.2's source enumeration; detect via requests exceeding their stated timeout; recover by threading a Deadline through every iterator source).

19.7 Performance Concerns

  • Serialization overhead in response encoding — mitigated by streaming protobuf encoding rather than buffering the full result set.
  • Heap churn from per-request allocation of iterator plans — mitigated by a plan-object pool sized to the concurrency budget (§4).
  • Scan amplification when a compound-key scan touches more sources than a single-key scan — bounded by the same 8-source fanout ceiling as §16.7.

19.8 Edge Cases

  • Malformed requests (invalid key-range bounds, negative page size) rejected at decode time, before snapshot acquisition.
  • Giant pagination windows requested by a misbehaving client — capped server-side (§19.2).
  • Stale snapshots: a paginated scan whose snapshot has aged past the retention floor (§17.2) returns SNAPSHOT_EXPIRED rather than silently re-acquiring a new, inconsistent one.

19.9 Failure Analysis

Query failures are isolated per request (P11, inherited from §16.9's iterator-level isolation) — a panic or error in one query's plan or execution never affects concurrent queries or the underlying storage state. Detection is the per-endpoint error-rate and p99-latency dashboards (§21); forensics uses the request-scoped trace span tree.

19.10 Operational Notes

Metrics: query_latency_ms (p50/p95/p99 histogram by query type), query_admission_rejected_total, query_cancellation_total. Tracing spans: query.plan, query.execute, query.encode. Structured- log fields: query_type, snapshot_epoch, page_cursor.

20. Phase 8 — Replication Runtime

20.1 Objectives

Implement Raft-backed replicated durability (Ongaro & Ousterhout, 2014) — log shipping, quorum acknowledgment, and follower catch-up — satisfying I7 and I9. Constraint introduced: a write is acknowledged to a client only after WAL fsync and Raft quorum (I7).

20.2 Detailed Implementation Steps

  • replication-runtime/src/raft_adapter.rs: integrate a Raft consensus core (ADR-24) — leader election, term validation, log-matching property enforcement.
  • replication-runtime/src/log_shipper.rs: append-entries pipeline shipping ReplicationFrame (§11) records derived 1:1 from WAL frames (§13.2), preserving I9's canonical replay order.
  • replication-runtime/src/quorum.rs: quorum tracking — a write's visibility publication (§8.7 step
    1. is gated on quorum acknowledgment, implementing I7 directly.
  • Add snapshot replication for follower bootstrap/catch-up when the log-shipping gap exceeds the retention window (ties to §17's manifest generation history).
  • Add leader-election hooks and follower catch-up state machine (Probe, Replicate, Snapshot per the Raft paper's follower states).
  • Add lag metrics and a flow-control credit system (ADR-21) so a slow follower backpressures the leader's log-shipper rather than growing an unbounded queue (P3, P4).
  • Add split-brain protection via term validation on every RPC (Raft safety property) and network retry policy with exponential backoff.
  • Add duplicate-frame detection (idempotent apply) and snapshot truncation once all followers have caught up past a given generation.

20.3 Deliverable

A replicated indexing cluster: a 3-voter Raft group where a leader failure triggers election and continued service within the availability budget (§4); raft_leader_failover.json passes.

20.4 Acceptance Criteria

  • Follower convergence to the leader's exact key/value/sequence state verified byte-for-byte across 100 randomized partition-and-heal trials.
  • Zero acknowledged-write loss (§4) across leader-failover trials — I7 holds through every election.
  • Leader failover completes within the 5 sec max-replication-lag budget (§4) under normal partition scenarios.
  • replication_gap_fixture.json's induced gap triggers snapshot catch-up, not an unbounded log replay.

20.5 Conformance Fixtures

  • conformance/replication/raft_leader_failover.json — scripted leader crash + election; expected: new leader elected, no committed write lost, term strictly increases.
  • conformance/replication/replication_gap_fixture.json — follower offline beyond retention window; expected: snapshot-based catch-up, not a replay of a truncated log range.

20.6 Pitfalls

  • Replay divergence when a follower applies frames out of the leader's canonical order under concurrent log-shipper batches (root cause: batch reordering at the network layer; violates I9; detect via per-follower sequence-gap metric; recover by enforcing strict in-order apply with a per-follower sequence assertion).
  • Stale leaders continuing to accept writes after losing quorum due to a delayed network-partition detection (root cause: missing quorum-loss heartbeat timeout; detect via I7 assertion firing on a write acknowledged without live quorum; recover by shortening the leader-lease timeout).
  • Replication storms when many followers request snapshot catch-up simultaneously after a shared network partition heals (root cause: no admission control on snapshot-transfer requests; detect via leader IO-saturation metric; recover by rate-limiting concurrent snapshot transfers, ADR-21).

20.7 Performance Concerns

  • Replication batching tradeoff: larger append-entries batches raise throughput but risk breaching the 5 sec max-lag budget (§4) under a slow follower.
  • Network fanout cost scales with voter count — bounded by the 3–7 voter range chosen in §4's availability model.
  • Follower disk pressure from snapshot catch-up competing with the follower's own local compaction — isolated via the same IO-lane discipline as §18.2.

20.8 Edge Cases

  • Clock skew between leader and followers must not affect Raft term/log-index correctness (P1 — no wall-clock dependency in the consensus core itself, only in the lease-timeout heuristic).
  • Partition healing racing an in-flight leader election — the Raft term-validation safety property (§20.2) resolves this without additional application-level logic.
  • Duplicate frames from a retried append-entries RPC — apply is idempotent keyed on (term, index).

20.9 Failure Analysis

Split-brain is contained through quorum enforcement (I7): a minority-partition leader cannot commit new writes because it cannot reach quorum, and it steps down once it detects a higher term. Blast radius during a partition is "reduced availability for the minority side," never a correctness violation. Detection is the term-divergence and quorum-loss metrics; forensics replays the Raft log around the partition window.

20.10 Operational Notes

Metrics: replication_lag_ms, raft_term_current, raft_leader_elections_total, follower_catchup_duration_ms. Tracing spans: replication.append_entries, replication.snapshot. Structured-log fields: term, leader_id, follower_id. PhaseDeferred("§20") — online repartitioning and distributed index shards build directly on this replication core; see §35.

21.9 Failure Analysis

Observability degradation must never impact the serving path (P11, P6) — a metrics-registry panic or an OTLP exporter outage is caught and contained at the observability boundary, logged once, and retried with backoff, while queries and writes continue unaffected. 24. Operational Readiness

Metrics strategy. Core dashboards track: WAL append latency (§13.10), compaction debt (§18.10), snapshot count and epoch lag (§16.10), query p99 (§19.10), replication lag (§20.10), segment-mmap page-fault rate (§15.10). Every metric maps 1:1 to a §4 budget or a §7 invariant so an operator can answer "are we inside spec" without cross-referencing code.

Tracing strategy. Every request-scoped operation carries trace_id, request_id, and shard_id (P6); every background job (compaction, replication catch-up) is given a synthetic root span (§21.6) so it is traceable even without a client-request origin.

Logging strategy. Structured JSON logs only, one schema shared across all crates (§21.2); no subsystem emits unstructured plain-text logs to stdout.

Backup strategy. Manifest snapshots (checkpointed per §17.2) plus WAL archival (§13.2 archival hooks) plus periodic full-segment checksum verification (§15.2 background scanner) together provide a point-in-time-restorable backup without a separate backup subsystem.

Rolling-upgrade strategy. Wire-compatibility gates (P9, ADR-05 protobuf field-append-only discipline) plus leader draining (a node is removed from the Raft voter set before restart, per §20) plus manifest-format compatibility validation (§25's N-2 read-compatibility window) together let an operator upgrade one node at a time with zero downtime, provided the compatibility window in §25 is respected.

On-call readiness. Every failure class in §23 has a corresponding runbook in docs/runbooks/ (§10); every runbook names the exact metric that fired, the exact operator-cli command to run, and the exact manual-recovery decision tree from §23's table.

25. Compatibility & Versioning

Wire compatibility. Protocol fields use explicit protobuf field numbers, reserved tags for removed fields (never reused), and forward-compatible decoding (unknown fields ignored, not rejected) — the direct implementation of P9 and ADR-05.

Storage compatibility. Segment and manifest readers support the previous two major format versions (N-2), matching the footer/record version fields defined in §11 and §15.2/§17.2. A reader encountering a version older than N-2 refuses to open rather than guess at layout; a reader encountering a version newer than itself also refuses rather than misparse (§13.10, §15.10).

Semantic versioning policy. MAJOR — any storage-format or wire-incompatible change (bumps the segment/manifest/WAL version fields). MINOR — additive, backward-compatible features (new optional protobuf fields, new metric names). PATCH — bug fixes with no format or behavior-contract change.

Rolling-upgrade compatibility matrix. A cluster running versions N and N+1 simultaneously must satisfy: N+1 readers can open N-written segments/manifests (backward read); N writers never need to read N+1-written structures (no forward-read requirement); Raft RPC framing (§20) is versioned independently of storage format so consensus survives a storage-format bump.

26. Testing & Verification Strategy

Unit testing. All parsing, comparator, and iterator logic is unit-tested in isolation, per crate (§10), with FakeClock (§12.2) driving any time-dependent path.

Deterministic simulation. The Phase-0 simulator (§12.2, §7's closing paragraph) drives every subsystem through a single logical clock with fault-injection hooks; every invariant in §7 has exactly one assertion checked on every simulated tick. This is the primary correctness gate, not a supplement to unit tests.

Integration testing. Multi-node Raft clusters (§20) are validated under docker-compose.yml (§10) topologies: 3-voter steady-state, leader failover, network partition and heal, rolling upgrade across adjacent versions (§25).

Differential testing. Iterator output (§16) is compared across three independently-derived paths for the same logical state: live memtable traversal, on-disk segment scan, and WAL-replayed reconstruction. Any divergence is a P1 violation and blocks release.

Fuzzing. cargo-fuzz targets (ADR-13): fuzz/wal_parser.rs, fuzz/manifest_parser.rs, fuzz/segment_reader.rs — each corresponds to an untrusted-input surface named in §22 (T4, T5, T6). Fuzzing runs nightly (.github/workflows/fuzz.yml, §10) with corpus persistence across runs.

Chaos testing. Injected disk failures (partial writes, ENOSPC), network partitions (leader isolation, symmetric/asymmetric partition), and process crashes (kill -9 at fault-injection points from §12.2) are run against the full replicated cluster, not just single-node unit scope.

Conformance suite. Every phase's named fixtures (§12.5 through §21.5) run as a single CI gate (conformance/, §10) on every commit — this is the terminology-lock enforcement mechanism: a fixture renamed in one phase and not the file inventory (§37) fails CI, not just this document's harness.

29. Scalability Analysis

Bottlenecks. Expected scaling ceilings, in order of first onset: compaction IO bandwidth (§18, C5 §32) saturates before CPU on write-heavy workloads; manifest serialization (§17) becomes a single-writer bottleneck above ~16,384 concurrently open segments (C6, §32); replication fanout (§20) degrades leader throughput linearly past 7 voters, which is why §9's ADR-24 caps the voter range at 3–7.

Horizontal scaling. Shard by secondary-key range or by tenant ID (§1 later-phase unlock); each shard is an independent WAL/memtable/manifest/Raft-group instance, so horizontal scaling is "run more of Phase 0–9" rather than a new architecture — the single-shard design in §3 is deliberately the unit of horizontal replication.

Vertical scaling. Additional NVMe devices raise the compaction-IO ceiling (§18's first bottleneck); larger page cache raises the effective segment-mmap hit rate (§15.7); more compaction workers raise throughput only up to the per-level worker-budget design in §18.7 — beyond that, horizontal sharding is the correct lever, not more threads on one shard.

Cross-shard query cost. A compound-key scan spanning multiple shards (a later-phase capability, §1) pays a fan-out cost proportional to shard count at the Request Coordination layer (§3.2) — bounded by the same 8-source heap-fanout discipline as §16.7, generalized from "8 segments" to "8 shard-local iterators."

30. Mental Models & First Principles

  • MM1 — WAL-Before-Visibility Is a Total Order, Not a Suggestion. Durability and visibility are two different clocks that compose in exactly one direction; predicts that any "fast path" publishing before the fsync callback reintroduces acknowledged-write loss; the bug class it prevents is a premature-ack race under load; applies in §12 and §13.
  • MM2 — Immutability Turns Concurrency Bugs Into Lifecycle Bugs. Making segments immutable moves the hard problem from "torn read" to "who retires this and when"; predicts that use-after-free bugs cluster at generation retirement, not at read time; the bug class it prevents is a reader holding a reference past its snapshot's epoch; applies in §14 and §15.
  • MM3 — Compaction Is Amortized Read Cost Paid Up Front. Deferring compaction doesn't remove read cost, it postpones and compounds it; predicts unbounded read amplification if compaction debt is ever allowed to grow without a starvation-prevention floor; the bug class it prevents is "compaction is just an optimization we can skip under load" thinking; applies in §18 and §28.
  • MM4 — A Manifest Is a WAL for Metadata. The same crash-consistency discipline that protects mutation data must protect segment-visibility metadata, twice; predicts that skipping fsync-before- commit on the manifest reintroduces exactly the bug class WAL engineering already solved; applies in §17.
  • MM5 — Quorum Is a Latency/Consistency Exchange Rate. Every unit of consistency purchased via Raft quorum (§20) is paid for in one round-trip of latency; predicts the write-latency floor is bounded below by inter-zone RTT, not by CPU; the bug class it prevents is expecting replication to be latency-free; applies in §20 and §4.
  • MM6 — An Iterator Is a State Machine Pinned to a Point in Time. A snapshot's epoch, once acquired, must be invariant for the iterator's whole lifetime; predicts that any source added or removed after acquisition must be invisible to that iterator; the bug class it prevents is mid-scan visibility leaks after a concurrent flush; applies in §16.
  • MM7 — Backpressure Debt Always Surfaces Somewhere. Removing a backpressure signal doesn't remove the underlying pressure, it just moves the failure downstream and delays detection; predicts that an unbounded "just buffering" queue always resolves as an OOM, never as steady-state stability; applies in §6 and §18.
  • MM8 — Observability Is Part of the State Machine, Not a Sidecar. A state transition with no emitted signal is indistinguishable from a hang during an incident; predicts every undebuggable 3am incident traces back to a silent transition; the bug class it prevents is instrumenting only the happy path; applies in §21.

  • DynamoDB — decoupled Global Secondary Index propagation asynchronously from the base-table write path; this wins wherever base-table write-latency isolation matters more than immediate secondary- index read-your-writes.
  • PostgreSQL — built synchronous, transactional index maintenance directly into the same MVCC engine as the heap; this wins wherever read-your-writes consistency on the secondary index is a hard application requirement.
  • FoundationDB — built secondary indexing as a stateless layer atop a synchronously-replicated ordered KV core; this wins wherever multiple independent indexing schemes must share one strongly- consistent substrate without each reimplementing consensus.

32. Back-of-Envelope Capacity Model

  • C1 — Node Memory Budget. 2 GB memtable + 4 GB segment mmap + 256 MB WAL buffer + 1.5 GB block/bloom cache headroom = 7.76 GB, inside the 8 GB §4 ceiling.
  • C2 — Memtable Entry Capacity. 2 GB memtable budget ÷ ~200 B/entry (MutationRecord + skiplist node overhead, §11) = 10,000,000 live entries per generation before freeze.
  • C3 — Bloom Filter Sizing. 10,000,000 entries/segment × 10 bits/entry (Bloom, 1970, ~1% target false-positive rate) = 100,000,000 bits = 12.5 MB/segment bloom filter, inside the 4 GB segment-mmap budget (C1) even across 300 concurrently open segments.
  • C4 — WAL Append Budget. 256 MB WAL buffer ÷ 250,000 ops/sec (§4 write throughput) = 1.024 KB average mutation-record budget per write before the buffer fills once per second.
  • C5 — Write Amplification Ceiling. 8 levels × 10× per-level fanout (leveled compaction, ADR-04) = 80× theoretical worst case, throttled to the ≤ 10× §4 operational ceiling by the starvation-prevention policy in §18.
  • C6 — Open-Segment Ceiling. 32,768 FD budget (§4) ÷ 2 FDs/segment (data file + sparse index) = 16,384 max concurrently open segments per node.
  • C7 — Replication Apply Headroom. 200 MB/sec replication-apply target (§4) ÷ ~1 KB average ReplicationFrame = 200,000 frames/sec follower-apply capacity, above the 250,000 ops/sec write ceiling (§4) only once batching amortizes ≥ 1.25 records/frame.
  • C8 — Cold-Startup Manifest Load. 30 sec cold-startup budget (§4) ÷ 16,384 max segments (C6) = 1.83 ms/segment manifest-load budget per entry.
  • C9 — Availability Budget. 99.95% availability (§4) = (1 − 0.9995) × 525,600 min/year = 262.8 min/year allowed unplanned downtime.

34. Alternative Architectures (Roads Not Taken)

Alt A — Synchronous Embedded B-Tree Secondary Index

     Write path                     Read path
   +-----------+                  +-----------+
   | App Txn   |                  | App Query |
   +-----+-----+                  +-----+-----+
         |                              |
         v                              v
   +-----------------------------------------+
   |   Single B+Tree page store (in-place)    |
   |   heap page  <-->  index page  (locked)  |
   +-----------------------------------------+

Regime where it wins: read-dominated workloads with modest write volume, where in-place page updates and heap/index co-location under one lock manager give read-your-writes consistency for free. Real system that embodies it: PostgreSQL's B-Tree access method (and, at smaller scale, SQLite). Why this blueprint rejects it: the §4 write-throughput budget (250,000 ops/sec) requires sequential append, not in-place page rewrites under a shared lock manager — the exact ADR-04 tradeoff.

Alt B — Asynchronous Coprocessor Global Secondary Index

   Base-table write path          Async propagation        Secondary index
   +----------------+     enqueue     +------------+   apply   +------------+
   | Base Table WAL |  ------------>  | Stream/CDC |  ------>  | GSI Store  |
   +----------------+                 +------------+           +------------+
        (ack here, before GSI apply completes)

Regime where it wins: multi-tenant, massive-scale systems where base-table write-latency isolation from secondary-index maintenance cost matters more than immediate index consistency. Real system that embodies it: DynamoDB's Global Secondary Indexes. Why this blueprint rejects it: I5 and I7 (§7) require a client-acknowledged write to be immediately snapshot-visible through every index it maintains; an async-propagated GSI model would relax exactly that guarantee, which §1 lists as a required capability ("strongly consistent secondary indexes"), not an optional one.

Alt C — Inverted-Index Segment Search Layer

   Document      Tokenize/Analyze     Posting Lists          Segment Merge
   +--------+  ------------------>  +---------------+  --->  +-------------+
   | Record |                      | term -> doc-id |        | Merged Index|
   +--------+                      +---------------+        +-------------+

Regime where it wins: full-text and relevance-ranked search over largely-append-only document corpora, where posting-list compression and relevance scoring dominate the design. Real system that embodies it: Apache Lucene (and Elasticsearch built atop it). Why this blueprint rejects it: §1's non-goals explicitly exclude full-text relevance ranking, and a posting-list/term-frequency model does not map onto the point-lookup and range-scan query shapes in §19 that this engine targets — adopting it would replace, not extend, the iterator model in §16.

36. Glossary

  • SSTable — Immutable sorted-string table; this blueprint's segment format follows the pattern.
  • WAL — Write-ahead log; the durability boundary enforced by I1.
  • MVCC — Multi-version concurrency control; the visibility model underlying snapshots (§8, §16).
  • Tombstone — Deletion marker that dominates all older writes for its key (I8).
  • Snapshot — A pinned, consistent visibility boundary identified by an epoch (§11).
  • Manifest — The canonical, transactional segment-metadata log (§17).
  • LSN — Log sequence number; the WAL's per-frame position identifier (§11).
  • Bloom Filter — Probabilistic membership structure used to skip disk IO on negative lookups.
  • Replay — Deterministic reapplication of WAL mutations to reconstruct state (P1, P8).
  • Segment — An immutable, persistent, disk-backed storage file (§8.4).
  • Flush — The event of persisting a frozen memtable to a new segment.
  • Compaction — Multi-segment merge rewrite that reduces read amplification (§18).
  • Quorum — Majority acknowledgment among Raft voters required before a write commits (I7).
  • Fsync — Forced durability synchronization to stable storage.
  • Epoch — A monotonically increasing snapshot-generation counter (§13.2).
  • Read Amplification — Extra physical reads required to answer one logical lookup.
  • Write Amplification — Extra physical writes caused by compaction rewriting data (C5, §32).
  • Split Brain — Two nodes simultaneously believing themselves leader (FM-8).
  • Orphan Segment — A persisted segment not referenced by any manifest generation (§17.2).
  • Replay Divergence — A follower's reconstructed state mismatching the leader's (FM-4).
  • Sequence ID — Per-shard, strictly monotonic mutation-ordering counter (I4).
  • Visibility Epoch — The snapshot generation boundary a query is pinned to (§8.1).
  • Memtable — The mutable, in-memory indexing structure accepting live writes (§14).
  • Skiplist — The lock-free probabilistic data structure backing the memtable (ADR-08).
  • Restart Point — A periodic uncompressed key marker within a prefix-compressed block (§15.2).
  • Sparse Index — A block-level key index enabling binary-search segment lookup (§8.4).
  • Manifest Generation — A strictly increasing counter identifying one manifest transaction (I13).
  • Checkpoint — A manifest operation that compacts the transaction-log history for faster replay.
  • Follower Catch-Up — The process by which a lagging replica resynchronizes with the leader (§20).
  • Leader Lease — The timeout mechanism bounding how long a leader can act without quorum contact.
  • Term — A Raft logical clock incremented on every leader election (§20).
  • Append-Entries — The Raft RPC used to replicate log entries to followers (§20.2).
  • Backpressure — A downstream-pressure signal that a producer must observe before enqueueing more work (P4).
  • Admission Control — Rejecting or delaying new work once a concurrency or resource budget is reached (§19.2).
  • Bounded Memory — The principle that no subsystem allocates without an enforced quota (P3).
  • Crash-Only Software — A design discipline assuming unannounced termination at any point (P2).
  • Deterministic Simulation — A test methodology driving all subsystems through one logical clock to reproduce failures byte-for-byte (§26).
  • Differential Testing — Comparing independently-derived reconstructions of the same state for divergence (§26).
  • Fixture — A named, version-controlled input/expected-output pair used for conformance testing (§10, §37).
  • Trust Boundary — A point where input crosses from untrusted to trusted context (§3.2, §22).
  • Blast Radius — The scope of impact a given failure can have, bounded by failure-domain isolation (P11).
  • Un-defer Trigger — The concrete condition under which a deferred feature (§35) becomes in-scope.
