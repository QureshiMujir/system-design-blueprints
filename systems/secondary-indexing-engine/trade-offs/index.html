Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Synchronous Embedded B-Tree Secondary Index

     Write path                     Read path
   +-----------+                  +-----------+
   | App Txn   |                  | App Query |
   +-----+-----+                  +-----+-----+
         |                              |
         v                              v
   +-----------------------------------------+
   |   Single B+Tree page store (in-place)    |
   |   heap page  <-->  index page  (locked)  |
   +-----------------------------------------+

Regime where it wins: read-dominated workloads with modest write volume, where in-place page updates and heap/index co-location under one lock manager give read-your-writes consistency for free. Real system that embodies it: PostgreSQL's B-Tree access method (and, at smaller scale, SQLite). Why this blueprint rejects it: the §4 write-throughput budget (250,000 ops/sec) requires sequential append, not in-place page rewrites under a shared lock manager — the exact ADR-04 tradeoff.

Alt B — Asynchronous Coprocessor Global Secondary Index

   Base-table write path          Async propagation        Secondary index
   +----------------+     enqueue     +------------+   apply   +------------+
   | Base Table WAL |  ------------>  | Stream/CDC |  ------>  | GSI Store  |
   +----------------+                 +------------+           +------------+
        (ack here, before GSI apply completes)

Regime where it wins: multi-tenant, massive-scale systems where base-table write-latency isolation from secondary-index maintenance cost matters more than immediate index consistency. Real system that embodies it: DynamoDB's Global Secondary Indexes. Why this blueprint rejects it: I5 and I7 (§7) require a client-acknowledged write to be immediately snapshot-visible through every index it maintains; an async-propagated GSI model would relax exactly that guarantee, which §1 lists as a required capability ("strongly consistent secondary indexes"), not an optional one.

Alt C — Inverted-Index Segment Search Layer

   Document      Tokenize/Analyze     Posting Lists          Segment Merge
   +--------+  ------------------>  +---------------+  --->  +-------------+
   | Record |                      | term -> doc-id |        | Merged Index|
   +--------+                      +---------------+        +-------------+

Regime where it wins: full-text and relevance-ranked search over largely-append-only document corpora, where posting-list compression and relevance scoring dominate the design. Real system that embodies it: Apache Lucene (and Elasticsearch built atop it). Why this blueprint rejects it: §1's non-goals explicitly exclude full-text relevance ranking, and a posting-list/term-frequency model does not map onto the point-lookup and range-scan query shapes in §19 that this engine targets — adopting it would replace, not extend, the iterator model in §16.
