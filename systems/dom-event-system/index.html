In one paragraph

When a user clicks a page, something has to decide which of the many registered handlers run, in what order, whether the event keeps travelling up the tree, and whether the browser's default reaction still happens. This design is a from-scratch Rust library of the WHATWG DOM Events algorithm that answers exactly that question for any host node tree (§1). It ships as seven evt-* crates plus a domevt command-line tool, with no HTML parser, JavaScript engine or rendering (§1.1, §1.2). It is meant to be embedded by browser-engine, headless-DOM and tooling engineers (§1.3), and its test bar is the WPT conformance suite (§2.5).

The problem, concretely

Take a button inside a div inside the document. The naive plan is to call the button's handlers and stop. The real model is a tree: the engine must also run handlers on the div and the document, once on the way down and once on the way back up (§2.1). A handler can also change the list being walked, by adding or removing handlers or firing another event mid-walk, which the blueprint calls the hardest mutate-during-iteration problem in the DOM (§2.1). Four more things break the naive plan:

  • Re-walking the ancestors for each phase costs O(depth squared) and gives wrong answers if the tree changed mid-dispatch (§6.3).
  • Shadow trees hide their insides. Pass a closed-shadow node out as event.target and an outside script sees what it must never see (§6.4, §2.1).
  • A passive handler promises not to cancel, so the compositor can scroll without waiting for JavaScript. If preventDefault still worked there, scrolling would block (§6.5, §2.1).
  • Script can dispatch its own events. If they could claim to be "trusted", synthetic clicks could trip actions meant only for real input (§2.2, §6.8).

How it works, end to end

Follow one click through the boxes of §3's diagram. Each box is a crate:

  1. evt-loop. A real user event arrives as a queued task. fire_event is the only producer of is_trusted = true, and each tick runs one task and then drains the microtask queue (§3.1). Script .dispatchEvent skips the queue and dispatches synchronously, untrusted (§3, §6.7, §6.8).
  2. evt-dispatch. dispatch() drives capturing, at-target and bubbling via invoke and inner_invoke, snapshots listeners, handles stop and cancel, and runs the activation hooks. It returns !canceled (§3.2).
  3. evt-path. It walks get_the_parent from the target to build the ordered EventPathItem list, applies retarget and serves composed_path. A non-composed event's path ends at the nearest shadow-including root (§3.3).
  4. evt-core. The types (Event, EventFlags, EventListener, the EventTarget trait, CallbackRef, Atom) plus add_event_listener and remove_event_listener (§3.4).
  5. evt-dom, evt-signal, evt-cli. A reference node arena that implements EventTarget (§3.6); the AbortController and AbortSignal whose abort algorithms remove listeners (§3.5); and the domevt tool with load, listen, dispatch, trace and bench (§3.7).

Everything below the host is untrusted: the tree, the re-entering listeners and the events. Event and listener lists are !Send, so there is one event loop per thread, no internal locks and no runtime persistence (§3).

The core ideas

Compute the path once, read it three ways (§8.3, §8.4, MM1)

build_event_path walks from the target to the root with get_the_parent, making one EventPathItem per node (§8.4). It runs once at the start of dispatch, and later tree changes do not alter it (§6.3, INV-01). The three phases are three reads of that list. Capturing visits root to target, excluding the target. At-target runs the target's own listeners, capture and non-capture together in registration order. Bubbling visits target to root, excluding the target, and only if event.bubbles (§8.3 steps D7-D9, §39); Appendix B's Phase 4 gate instead says capture then non-capture at the target (§41). Capturing visits exactly target_index items, and bubbling len - target_index - 1 (0 if not bubbling) (§16).

The blueprint is not consistent on the path's order. §8.4, §15 and §39 store it target first (index 0 is the target), while §3.3, MM1, F3 and Appendix B's Phase 3 gate describe it root first, and §16's capturing range [0, target_index) only works root first (§8.4, §15, §39, §3.3, §33, §26, §41, §16).

The blueprint's trace (§8.6): path document -> div#app -> button#btn, bubbles=true; the div has a capture listener and a bubble listener, and the button has two at-target listeners, the first calling stopPropagation.

Step currentTarget Listeners that run
Capturing document none
Capturing div#app its capture listener
At-target button#btn the first, then the second (it still runs)
Bubbling div#app, document skipped, STOP_PROPAGATION is set
End None activation behavior, after currentTarget and eventPhase reset (§8.3 D10, D11)

stopPropagation does not stop the other listeners on the current target; only stopImmediatePropagation does, and it also skips later path items (§8.6, §8.2). A target with no parent runs only the at-target step (§8.8).

Iterate a photograph, not the live list (§8.3, §8.8, MM2)

Listeners live in Rc<RefCell<Vec<EventListener>>> because a callback may add or remove listeners mid-dispatch (§8.4, ADR-05). inner_invoke takes a snapshot, then for each listener skips it if removed or if its capture flag mismatches the phase (except at the target), removes it from the real list first if once, sets IN_PASSIVE_LISTENER if passive, runs the callback, and stops early on STOP_IMMEDIATE_PROPAGATION (§8.3). The safety rule is never to hold a RefCell borrow across a callback (§6.2, INV-12).

A callback does this Result (§8.8)
removes itself removed=true on the real list; it already ran; later items skip it
adds a listener on the same target and phase not called this invoke; eligible on later items
is a once listener removed before its callback, so it fires once even if it re-dispatches
dispatches a different event allowed; the inner dispatch has its own DISPATCH flag and path
dispatches the same event Err(AlreadyDispatching); the original dispatch is unaffected

Duplicate adds are dropped by the key (type, callback identity, capture); passive, once and signal are not in it, and capture and bubble registrations of one function are separate entries (§8.4, §6.6, INV-04).

The blueprint is not consistent on snapshot cost. §6.2 counts one Vec clone per invoke and §16 allows one snapshot Vec per visited target; §4.2 and C5 require zero steady-state allocation with a reused buffer of inline capacity 8; §32 says the snapshot is a plain borrow where no mutation is possible; and §7.3 says snapshots are always owned clones, never borrows (§6.2, §16, §4.2, §35 C5, §32, §7.3). §4.2 calls that buffer thread-local-free scratch passed down the call stack, while §31.3 calls it a reused thread-local buffer (§4.2, §31.3).

Retargeting: show each listener only what it may see (§8.4, §8.5, MM3)

A shadow tree hides its insides. At each path item the engine swaps the real target for the nearest ancestor that item's listeners may see (retargeting). The rule (§8.4): retarget(a, b) starts at a, and while a's root is a shadow root and b is not inside that root, it moves a up to that root's host. For an item with invocation target A and a cross-tree node B, the exposed value is retarget(B, A) (§6.4).

The blueprint's example (§8.5): a click on button#btn inside closed shadow root SR_c of x-inner, which is slotted into the open shadow tree of x-outer.

Path item invocation_target exposed event.target
0 btn btn
1 SR_c (root of a closed tree) btn
2-5 x-inner, slot#so, section, SR_o x-inner
6-8 x-outer, div#app, document x-outer

At x-outer, event.target is x-outer, so btn and SR_c are never exposed; the value is recomputed only at host boundaries (§8.5). Applied as written, §8.4's rule stops at x-inner for items 6-8, because x-inner is a light child of x-outer and not inside a shadow root; the table says x-outer (§8.4, §8.5). Whether the path crosses at all depends on composed. If true, composedPath() from document is [x-outer, div#app, document] and from btn is the whole path. If false, get_the_parent returns None at SR_c, the path is [btn, SR_c], and composedPath() from document is empty (§8.7, INV-09). It is not cached, since it depends on the current currentTarget (C7, §8.7).

The blueprint is not uniform on argument order: §6.4 and MM3 say retarget(B, A), never retarget(A, B), but INV-08's detection column and ADR-10 write retarget(A,B) (§6.4, MM3, §7.2, ADR-10).

Flags are the state machine: stop, cancel, passive, activation (§8.2, §8.3, MM5)

Seven EventFlags bits plus the phase enum are the whole dispatch state (§6.16, §8.2), though §22's fire_event also sets an IS_TRUSTED flag that §8.2 does not list (§22):

Flag Meaning Set by (§8.2)
INITIALIZED may be dispatched constructor or init_event
DISPATCH in flight; re-entry guard dispatch entry; cleared on exit
STOP_PROPAGATION skip later path items stopPropagation
STOP_IMMEDIATE_PROPAGATION skip the rest of this target's listeners stopImmediatePropagation
CANCELED default action prevented preventDefault, only if cancelable and not passive
IN_PASSIVE_LISTENER current listener is passive inner_invoke, around that one callback
COMPOSED path may cross shadow roots constructor

defaultPrevented is CANCELED being set, and dispatch returns !CANCELED (§8.1, §8.3). In a passive listener preventDefault only emits a diagnostic (§8.8); the default-passive types are touchstart, touchmove, wheel, mousewheel (ADR-12). An event that is not INITIALIZED fails at D1 with Uninitialized (§8.3).

After the walk the engine resets currentTarget and eventPhase, then runs either the canceled-activation hook or the activation behavior; a legacy pre-activation hook runs before capturing (§8.3 D6, D10, D11). One guard object resets state on every return path (§7.3). A non-canceled checkbox click toggles checked once, a non-passive preventDefault suppresses the toggle, and a passive one does not (§21).

Run to completion, then settle: the event loop and trust (§22, §6.14, MM7, MM8)

evt-loop is host-driven and has no thread of its own (§22). One tick takes the highest-priority non-empty task source (UserInteraction, then Dom, Networking, Timer; FIFO within a source), runs that task, then performs a microtask checkpoint (§22). The checkpoint pops the microtask queue until empty, so a microtask queued during the drain runs in the same drain, and a performing_checkpoint flag makes a nested request a no-op (§22, INV-10). The blueprint's ordering test: task A queues microtasks m1 and m2, task B is queued, and the observed order is A, m1, m2, B (§22).

fire_event marks an event trusted and queues a Dom task that calls dispatch synchronously (§22). Script dispatchEvent always yields is_trusted=false, and the field is private with no public setter (§6.8, INV-11). Dispatch is synchronous and only firing is asynchronous (§6.7).

The trade-offs — where engineers disagree

Compute the path once (ADR-07)

Chosen: build the Vec<EventPathItem> once and index it in every phase, since the spec freezes the path and mid-dispatch tree changes must not alter visited targets (§9). Rejected: a lazy get_the_parent walk per phase (§9). When the rejected choice is right: fire-and-forget non-bubbling events on shallow trees (depth 2 or less), where building the Vec costs more than the at-target step; the blueprint says Blink does this for known leaf-only events (§9).

Listener lists as Rc<RefCell<Vec>> (ADR-05)

Chosen: ListenerListRef, modelling JavaScript's shared-mutable lists; RefCell gives runtime borrow checks and Rc fits the single-thread loop (§9). Rejected: &mut Vec, Box<[_]> and RwLock (§9). When the rejected choice is right: RwLock or Arc when registration must be thread-safe, such as a host that exposes addEventListener from worker threads, at the cost of atomics on a hot path this !Send design forbids (§9).

Exact retargeting, not a "no leak" heuristic (ADR-10)

Chosen: the spec's retarget with per-item adjusted and related targets, because closed-shadow encapsulation is observable and WPT-tested (§9). Rejected: a heuristic that tries not to leak (§9). When the rejected choice is right: an engine with zero closed shadow roots, such as an internal tool or a flat-DOM headless user agent, where the retarget math is dead weight (§9).

Opaque callback handles compared by identity (ADR-06)

Chosen: CallbackRef, since dedup needs callback identity and listeners are host JavaScript callables, not Rust closures (§9). Rejected: Box<dyn Fn(&Event)>, function pointers and trait objects (§9). When the rejected choice is right: Box<dyn Fn> in a pure-Rust embedding with no JavaScript host, such as a game or terminal UI, where closures are directly callable (§9).

One authority for trust (ADR-16)

Chosen: isTrusted=true only via fire_event, so synthetic events cannot forge it (§9). Rejected: a caller-settable flag, or trust decided by event type (§9). When the rejected choice is right: a trusted test harness replaying real user-agent events that must re-assert isTrusted=true, acceptable because no adversarial script runs in that process (§9).

A minimal host-driven loop (ADR-14)

Chosen: tick(), a task queue per source and one microtask queue, because a real scheduler is a non-goal (§9, §1.2). Rejected: a full HTML scheduler with rendering (§9). When the rejected choice is right: inside a complete browser engine (the blueprint names project 260) that owns rendering opportunities and requestAnimationFrame; a minimal loop cannot sequence paint (§9).

Roads not taken (§37, §38)

Flat delegation at the root (ALT-2, React SyntheticEvent) wins for a framework that owns a virtual tree and wants uniform behaviour, pooling and batched flushing; it gives up DOM-phase fidelity and shadow retargeting (§37).

Direct per-node handlers (ALT-3, Node.js EventEmitter) win for non-tree publish/subscribe such as streams, servers and actor mailboxes; without a path this would not be a DOM event system (§37).

A global event bus (ALT-4) wins for a closed system with fixed targets, such as a game input router; it cannot express capture, bubble, retargeting or composedPath(), and its global table clashes with the !Send design (§37).

Deferred features (§38) each wait for a trigger: input-device decoding for a host with hit-testing (project 260), real JavaScript-engine binding behind a real JS engine (project 259), full per-interface properties when a consumer needs coordinates or key codes, and render integration when the host needs requestAnimationFrame (§38).

What must never be false

Each invariant has a named enforcement site; debug builds panic on a violation, release builds degrade and trace (§7).

  • INV-01: the path is never changed after it is built. Noticed by a debug length-and-hash check at each phase edge; ERROR path_mutated (§7.2).
  • INV-02: no listener runs that was absent from the snapshot. Noticed by iterating a clone and re-checking removed; DEBUG invoke.snapshot with n_added (§7.2).
  • INV-03: a once listener is removed before its callback runs. Debug assert; once_removed equals adds (§7.2).
  • INV-04: listeners differing only in passive, once or signal are never distinct. Noticed by a scan for the triple before the push; listener.add_dup (§7.2).
  • INV-05: CANCELED is never set for a non-cancelable event or inside a passive listener. Noticed by the check in prevent_default; WARN prevent_default.ignored (§7.2).
  • INV-06: currentTarget, eventPhase never stay set after dispatch. Epilogue assert; dirty_epilogue (§7.2).
  • INV-07: an event with DISPATCH set, or not INITIALIZED, is never dispatched. The prologue returns Err; dispatch.reentrant_same_event or dispatch.uninitialized (§7.2).
  • INV-08: retarget never exposes a closed-tree node deeper than currentTarget. Noticed by a debug assert; ERROR path.retarget_leak, and release builds clamp to the boundary host (§7.2).
  • INV-09: a non-composed path never passes the target's shadow-including root. Debug assert; path.truncated (§7.2).
  • INV-10: no checkpoint starts while one runs. performing_checkpoint guard; checkpoint_reentry_suppressed (§7.2).
  • INV-11: is_trusted is true only via fire_event. Noticed by the private field and a grep of fire_event callers; loop.fire_event trusted=true (§7.2).
  • INV-12: list mutation never invalidates the in-progress snapshot. Noticed as a BorrowMutError, meaning some code held a borrow across a callback; listener.borrow_conflict (§7.2).

What breaks in production

Severity runs from S0 (privacy leak) to S3; each dispatch may emit a trace record per path item, and domevt trace rebuilds the invoke timeline from them (§26).

F6, retargeting leaks closed-shadow internals (S0, the gravest). An outside listener sees a closed-tree node in target, relatedTarget or composedPath(). Causes: swapped retarget arguments, shadow_adjusted_target not recomputed per item, inverted closed-tree gates. Detected by a CI-blocking leak oracle and WPT shadow-dom tests; recovery is fail-closed, exposing null or the host, never the inner node (§26).

F1, a listener does not fire (S1, top). The trace shows the path item but not the listener. Causes: a dedup-key mismatch from a cloned versus same CallbackRef, a capture listener queried in the bubble walk, or a snapshot taken after removed. Detected by WPT AddEventListener tests; fail loudly, domevt trace --listeners dumps the list (§26).

F2, a listener fires twice (S1). Causes: once not removed before the callback, or passive/once/signal wrongly in the dedup key. Detected by asserting at most 1 invoke per key and WPT once tests. No recovery (§26).

F9, nested-dispatch corruption (S1). Causes: same-event re-dispatch uncaught, a RefCell borrow held across a re-entering callback, or a snapshot aliasing the live list. Detected by the DISPATCH guard (AlreadyDispatching) and re-entrancy fuzzing; the guard rejects, and borrows are scoped before the callback (§26).

F10, microtask-checkpoint re-entrancy (S1). A callback that queues and drains recursively causes unbounded recursion or reordering. Detected by a re-entry-is-no-op assert and a microtask-from-microtask fixture; nested calls enqueue and do not drain (§26).

F11, event-loop starvation (S2). One source monopolizes tick, or microtasks never empty. Detected by a per-tick budget counter; recovery is round-robin or oldest-first across sources and a drain cap with a diagnostic (§26).

On microtask storms the blueprint gives several answers. §4.3 says the budget is a diagnostic only and never drops tasks; T7 says to stop draining at MAX_MICROTASKS_PER_CHECKPOINT and yield to the next tick; §22 calls an unbounded enqueuer a livelock and the host's problem; §6.14 and MM7 say the checkpoint drains to empty; §32 defers the remainder past a soft budget and F11 caps drain iterations. Task selection is a fixed priority in §22 but round-robin or oldest-first in F11 and round-robin or priority in §32. All are left unresolved (§4.3, §25.2, §22, §6.14, §33, §32, §26).

Threats worth knowing (§25.2):

  • T1, a deep-path denial of service, is met by MAX_PATH_DEPTH = 8192. On breach T1 rejects at build with an EventError, while §4.3 and §32 truncate the path and let dispatch complete (§25.2, §4.3, §32).
  • T3, runaway recursion from listeners that dispatch listeners, is capped at nesting depth 64. The cap has three names (MAX_NESTED_DISPATCH_DEPTH in §4.3, MAX_DISPATCH_DEPTH in §25.4, MAX_NESTED_DISPATCH in §32), and T3 describes a thread-local counter although §4 forbids thread-locals at load (§4.3, §25.4, §32, §4).
  • T4, a shadow leak, is met by the retarget invariant and composed_path gates; retarget_invariant_fail_total must be 0. T7, microtask starvation, is met by a 1<<20 per-checkpoint budget and the re-entry guard.
  • T12, a spoofed trusted event, is met by a private is_trusted set only by fire_event; spoofed_trusted_total must be 0.

The numbers

The latency, memory and cap figures are design targets (§4). The M1 to M11 benchmarks gate them in CI, failing on a p50 regression above 7% against the committed baseline (§31.1).

single target, 0 listeners < 80 ns < 300 ns < 1 µs
single target, up to 4 listeners, no bubble < 200 ns < 1 µs < 5 µs
bubbling, depth 100 < 6 µs < 20 µs < 60 µs
bubbling, depth 1000 < 60 µs < 200 µs < 600 µs
shadow retarget, depth 100, 4 boundaries < 12 µs < 40 µs not set

Path build is O(depth), once per dispatch (§4.1). Budgets and caps (§4.2, §4.3): an EventListener is at most 48 B, an EventPathItem at most 64 B, an Event at most 128 B plus its path Vec, and the inner_invoke snapshot makes zero steady-state allocations with inline capacity 8. MAX_PATH_DEPTH is 8192 (truncate with a diagnostic), MAX_LISTENERS_PER_TARGET is 65 536 (the add becomes a no-op), and nested dispatch depth is 64 (an AlreadyDispatching-class error).

Dedup is a linear scan, so registering L listeners on one target is O(L squared); the blueprint accepts that and defers an index (§35 C12, §32).

The blueprint disagrees with itself on some numbers, and both sides are given, unresolved:

  • Depth 1000. §4.1 sets bubbling at depth 1000 under 60 µs at p50, but M3 sets chain depth 1 000 under 0.9 µs, and M4 sets depth 10 000 under 9 µs, above the 8192 path cap (§4.1, §31.1, §4.3).
  • The empty dispatch. §4.1 sets 0 listeners under 80 ns, while M1 and the C4 note use under 200 ns for what looks like the same fixture (§4.1, §31.1, §35).

How it compares

§34 compares this engine with four real event systems.

  • The WHATWG DOM model (Blink, WebKit, Servo) is the target, not an alternative: the same three-phase model and retargeting. What those engines add, layout integration and a real scheduler, is this blueprint's non-goals (§34).
  • React SyntheticEvent delegates at the root, one real listener per type, then simulates capture and bubble over its own fiber tree. That suits a framework that owns a virtual tree and wants uniform behaviour, though it cannot give real DOM-phase fidelity or shadow retargeting (§34).
  • The jQuery event system keeps a parallel listener store with delegation, to smooth over inconsistent legacy engines. It predates shadow DOM and cannot honor closed-tree encapsulation (§34).
  • Node.js EventEmitter has no path, no phases and no propagation: a flat map of functions called in registration order, with an array copy on emit. That wins for non-tree publish/subscribe such as streams and servers (§34).

Questions to test yourself

  1. Why is the event path computed once and frozen, and what specifically breaks if you re-walk it per phase? — Hint: §6.3 states the principle, §8.3 shows the walks indexing one Vec, §4.1 the cost comparison.
  2. A listener removes a later listener on the same target mid-dispatch; another listener adds a new one. Which run this dispatch, and why is the answer different for removed vs added? — Hint: §6.10 and §8.3, then §8.8 and INV-02.
  3. For a click on a node inside a closed shadow tree, give event.target and composedPath() as seen from (a) inside that tree and (b) the document, and justify each from the retarget rule. — Hint: the worked examples in §8.5 and §8.7, then §6.4.
  4. Distinguish stopPropagation from stopImmediatePropagation by exactly which listeners and which path items each suppresses, and where in the walk each is checked. — Hint: §6.10, §8.3 and the sequence diagram in §8.6.
  5. Show the precise interleaving by which a task, the microtasks it enqueues, and a second task run — and why a microtask enqueued during the checkpoint still runs in the same checkpoint. — Hint: §6.14, §22 and INV-10.

If you only remember three things

Compute the propagation path once and read it three ways, because order and visibility follow from a frozen path (§6.3, MM1). Walk a snapshot, never the live list, because handlers legitimately change the list mid-walk (§6.10, MM2). Hand each listener only what it may see, with the retarget arguments the right way round, and let only the user-agent path mark an event trusted (§6.4, §6.8, MM3, MM8).

Words used here

  • Event path: the frozen list of path items from target to root, built once per dispatch (§39, §8.4).
  • Capture, at-target, bubbling: the three phases, walking down, at the target, then back up (§39).
  • Snapshot: the copy of a listener list that inner_invoke iterates instead of the live list (§39, §8.3).
  • Dedup key: (type, callback identity, capture), the identity of a listener (§39).
  • Retargeting: replacing a node with the ancestor a listener may see across a shadow boundary (§39).
  • Passive listener: a listener whose preventDefault is ignored so scrolling need not wait (§39).
  • Activation behavior: the default action run after dispatch when the event was not canceled (§39).
  • Microtask checkpoint: draining the microtask queue to empty after each task (§39).
