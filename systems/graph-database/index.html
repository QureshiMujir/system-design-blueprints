In one paragraph

A graph database stores things and the links between them, and answers questions such as "what is connected to what, and how cheaply can I follow it for ten hops" (§2). This design, graphd, is a single-node, native property-graph engine written in Rust (§1, ADR-01). It owns its pages, write-ahead log, snapshot-isolated transactions, indexes, an openCypher-subset query language, a graph-analytics runtime and the Bolt v4 network protocol (§1). Backend engineers modelling social, fraud, recommendation or dependency graphs would run it, and SREs would operate it (§1). Its defining bet: it is optimized for pointer-chasing reads over a durable, snapshot-isolated single-node store, not for horizontal write scale (§4).

The problem, concretely

Take MATCH (a:User)-[:FOLLOWS*1..3]->(b:User) RETURN b.name (§2). The blueprint's claim is that in a relational store, past three joins the planner stops helping, and a query that should read fifty rows becomes a hash join over half the table (§2). A graph database avoids this by making a node a pointer, not a row (MM1): finding a node's neighbours means following stored pointers, not searching a table or an index (P1).

Two other routes fail for specific reasons. A generic wide-column store (JanusGraph over Cassandra) turns adjacency into a keyed row scan and gives up the pointer chase (§35 AA1, §2). Recursive queries on a relational store make adjacency a join, and their depth costs "explode past a few hops" (§35 AA3).

A native store brings two more pressures. The process must survive kill -9 without losing committed work, so every change is logged before a page is touched (P5). Readers and writers must never block each other, so the design uses snapshots (§15.1, P4, P11).

How it works, end to end

Follow one query through the boxes of §3's diagram, drawn here (shortened, with the crate names from the §10 repository tree added, coloured by role):

The blueprint's own worked trace is MATCH (a:Person)-[:KNOWS]->(b:Person) RETURN b.name after inserting two :Person nodes, Ada and Grace, and one [:KNOWS] relationship (§8.6):

  1. Server. The message arrives as Bolt chunks, each a 2-byte length plus a PackStream body, ended by a zero-length chunk (§8.3). The session state machine rejects an illegal message with FAILURE (I10, §20.2).
  2. Query engine. The text becomes an AST, then a logical plan, then a physical plan (§3, §8.4). A malformed query fails in the parser with a positioned ParseError; nothing partial runs (§8.7).
  3. Execution runtime. NodeByLabelScan(Person) yields {Ada, Grace} in id order, then ExpandAll(OUT, KNOWS) walks Ada.first_rel, finds the KNOWS relationship to Grace and yields (Ada, Grace). Grace has no outgoing KNOWS, so she contributes no row. Then Projection(b.name) emits {"name": "Grace"}: one row (§8.6).
  4. Transaction manager. Every record the scan and expand touch is filtered through is_visible against the reader's snapshot, so a record whose creator has not committed relative to that snapshot is skipped (§15.1, §11.3, I4).
  5. Storage engine. The pointer chase itself happens in graphd-store over pages served by the page cache (§13.2, I1), and each page's checksum is verified on every disk read (I2, P3). Writes go through graphd-wal before any page is dirtied (I3).

The core ideas

Index-free adjacency on fixed-width records (P1, P2, I1)

The idea: a node record stores a pointer to its first relationship, and relationship records form a chain, so finding neighbours is following pointers (index-free adjacency, P1). For that to be cheap, every record has a fixed size, so a record id converts to a disk position by arithmetic with no directory to consult (P2).

Record Size Records per 8 KiB page
NodeRecord 40 B 204
RelRecord 88 B 92
PropertyRecord 64 B 127

(Sizes and per-page counts from §8.2; each page starts with a 32-byte header, and records start at byte 32, §13.6.) Position arithmetic: page_id = id / records_per_page and offset = id % records_per_page (§13.2).

A relationship record sits on two doubly-linked lists at once, one through its start node's start_prev_rel/start_next_rel and one through its end node's end_prev_rel/end_next_rel (§8.2). NodeRecord.first_rel is the entry point (§8.2, §13.2). neighbours_out walks the list in O(degree) pointer chases, and the acceptance test checks that graphd_adjacency_probe_count equals exactly degree per call (I1, §13.4). The price is random-access page churn at high degree (P1) and a cache-unfriendly access pattern at scale (MM8). Creating a relationship must patch both lists together: a half-patched pair is the dangling-adjacency failure (§13.6, §13.9, FM-8).

Write-ahead log and ARIES recovery (P5, I3, I8, P13)

The idea: before changing a page in memory, append a description of the change to a log and make the log durable. After a crash, the log is the truth and the cached pages are a rumour (MM2). Recovery is the ARIES algorithm: redo committed work, undo uncommitted work (P5, §14.1).

Each log record carries lsn, prev_lsn, txn_id, a type, a length, a payload with before/after images, and a CRC (§14.2). Every page header stores the LSN of the last record that dirtied it, and recovery replays a record only if the page's on-disk LSN is older, so applying redo twice equals applying it once (I8, P13, §14.2). A checkpoint writes CHECKPOINT_BEGIN, flushes dirty pages, then writes CHECKPOINT_END with the dirty-page table and active-transaction table, and recovery starts from the last CHECKPOINT_END (§14.2).

Three passes (§14.2): Analysis rebuilds the two tables from the last checkpoint to the end of the log; Redo replays every record newer than its page; Undo walks prev_lsn backwards for each uncommitted transaction, writing compensation records (CLRs) that are redoable but never undone.

Three-step trace from the blueprint (§8.8): a transaction's INSERT_PROP and COMMIT records are durable, but the process dies before the property page is flushed. (1) Analysis finds the transaction in the table as committed. (2) Redo replays INSERT_PROP because the page's on-disk LSN is older than the record's. (3) Undo does nothing for this transaction. The property is visible after restart (§8.8, §14.5).

Commits are batched: COMMIT records collect in a buffer and fsync fires at a 64 KiB threshold or a 1 ms timer, whichever comes first (group commit, §14.2). A torn record at the log tail is caught by its CRC and treated as the end of the log (§14.9, T9).

Snapshot visibility (I4, P4, P11)

The idea: a reader sees a frozen set of committed transactions, not a frozen clock reading (MM3). When a transaction begins it receives Snapshot{xmin, xmax, active}, where active is the set of transactions running at that moment (§11.3, §15.2, §37). Every record carries the id of the transaction that created it (xmin) and the one that deleted it (xmax, 0 if none) (§8.2). The visibility rule is a four-row decision table (§11.3):

Condition Visible?
creator is in active, or creator id is at or past the snapshot's xmax No: writer not committed relative to this snapshot
deleter id is 0 Yes
deleter is in active, or deleter id is at or past the snapshot's xmax Yes: deleter not committed relative to this snapshot
otherwise No: deleter is committed and visible

The active term is load-bearing: a bare (xmin, xmax) check wrongly treats a transaction that was running when the snapshot was taken as committed (§15.6, MM3).

Writes append a new version and stamp the old version's xmax; old versions are chained through prev_version and reads walk newest to oldest, returning the first visible one (§15.2, §8.2). At commit, if any version this transaction created has had its xmax set by another transaction, the commit fails: lost updates are rejected, but write skew (disjoint records, no direct conflict) is allowed (I5, P4, §15.2). The fixtures say it directly: the write-skew case commits both transactions, the lost-update case commits exactly one (§15.5). Garbage collection reads the oldest-active-snapshot pointer atomically before freeing anything, and never frees a version a live reader can see (I6, §15.2). A relationship is visible only if it and both endpoint nodes are visible (I7).

Where the blueprint is loose: §15.1 puts MVCC into "the property/node/relationship version chain", but §8.2 gives only PropertyRecord a prev_version link (NodeRecord and RelRecord carry xmin/xmax only), and §3 and §15.2 place the version chain in the property record (§15.1, §8.2, §3, §15.2).

From Cypher text to operators (P7, P8, P12)

The idea: a query is turned into a tree of small operators, each of which hands its caller one row at a time (Volcano pull model). Each operator exposes init, next and close (P7, §18.2). A consumer calls next only when it is ready, so backpressure is free inside one process (P12). The worked lowering from §8.4, copied:

AST                     Logical Plan                  Physical Plan
Match(a:Person)     ->  NodeByLabelScan(Person, a) ->  NodeByLabelScan(Person, a)
-[:KNOWS]->(b:Person)  Expand(a, OUT, KNOWS, b)     ->  ExpandAll(a, OUT, KNOWS, b)
Where b.age > 30    ->  Filter(b.age > 30)          ->  Filter(b.age > 30)
Return b.name       ->  Project(b.name)             ->  Projection(b.name)

The rule-based planner, the only one that ships (§18.1), applies a fixed set of rewrites: push predicates to the earliest operator that can evaluate them, push selections through joins, constant folding, splitting multi-part patterns into scans joined by Apply, and turning {name: 'Ada'} into an index seek (§18.2, ADR-09). Predicate push-down could not move Filter earlier in the example, because b only exists after Expand (§8.4). A variable-length pattern such as [:KNOWS*1..3] lowers to a bounded breadth-first search rooted at the bound end, reusing the §19 BFS mechanism (§18.2). The planner asks the index how many nodes match a label, answered from a maintained counter, so cardinality comes from the index and not from planner-side guesses (P8, §16.2).

The later cost-based planner is a Selinger-style dynamic-programming search over join orders, with cost formulas such as cost(Expand) = cost(input) + count(input)×avg_degree×READ_COST, budgeted at 1,000 candidate plans or 100 ms (§18.2). It is deferred (ADR-09, §36). The §3 diagram is looser: it labels the Phase 5-6 query engine "Rule-based + cost-based planner", while §18.1 ships the rule-based planner only and §1 lists a cost-based planner among the things not provided (§3, §18.1, §1).

Pregel and PageRank (MM6, ADR-15)

The idea: analytics run as rounds called supersteps, in the vertex-centric model known as Pregel (bulk-synchronous, MM6, §19.2). Messages are delivered at the start of the next superstep, with optional combiners that reduce messages bound for the same vertex before delivery (§19.2, §11.7). Thinking in supersteps rather than threads is what gives deterministic results, and mutating shared state mid-superstep causes races (MM6).

PageRank is the blueprint's example: an iterative power method with damping 0.85, at most 20 iterations and tolerance 1e-6 (§19.2). The step a fresh port gets wrong is dangling nodes: rank that would leak out of a node with no outgoing edges must be redistributed uniformly on every iteration, or ranks drift toward zero (§19.2, §19.6). A graph with zero edges converges to uniform rank in one iteration (§19.8). The acceptance bar is agreement with a NetworkX or Neo4j GDS reference within relative tolerance 1e-4 (§19.4).

Not everything scales: Brandes' betweenness is O(V·E), so exact betweenness is limited to subgraphs of at most 10,000 nodes (§19.7, §33 C9).

The trade-offs — where engineers disagree

Rust, with no garbage-collected runtime (ADR-01, ADR-02)

Chosen: Rust 2024 edition, native, because the borrow checker enforces the aliasing rules a page cache and a WAL writer need without a GC pause budget (§1, ADR-01, ADR-02). Rejected: C++ and the JVM (Java/Kotlin). When the rejected choice is right: C++ when a team already owns a mature arena/allocator stack and wants raw-pointer aliasing the borrow checker forbids; the JVM when pause-time SLAs are loose and the ecosystem (Lucene, Hadoop connectors) matters more than tail latency, which is Neo4j's trade (§9 ADR-01, ADR-02; §1).

Storage layout: pointers, not keys (ADR-03, ADR-04)

Chosen: index-free adjacency on an 8 KiB paged, record-oriented store with its own writer, for constant-time neighbour traversal (ADR-03, ADR-04, P1). Rejected: LSM-on-keys (ADR-03), or an LSM-backed page store (ADR-04). When the rejected choice is right: an LSM wins under extremely write-amplification-tolerant ingestion where traversal is rare (JanusGraph-over-Cassandra's regime), and an LSM-backed page store wins for random-point-lookup-heavy OLTP with little traversal (ADR-03, ADR-04).

Durability: a custom ARIES-style WAL (ADR-05)

Chosen: a custom write-ahead log with redo and undo, because crash recovery needs both, not "fsync and hope" (ADR-05, P5). Rejected: no WAL, relying on the OS page cache only. When the rejected choice is right: ephemeral analytics scratch space where durability is not required, as in GraphChi-style batch jobs (ADR-05). The blueprint also rejects Memgraph's snapshot-plus-optional-WAL stance because crash durability is a Phase-0 requirement (§32, P5).

Isolation: snapshot isolation by default (ADR-07)

Chosen: snapshot isolation, shipping lost-update protection (I5) without the abort-rate cost of the stronger level; Serializable Snapshot Isolation is deferred (ADR-07, §36). Rejected: Serializable Snapshot Isolation from day one. When the rejected choice is right: when the workload is dominated by read-write conflicts that show up as silent anomalies the application cannot detect, such as financial ledgers (ADR-07). The cost of the chosen side is real: write skew is possible and the blueprint says to document that snapshot isolation does not prevent phantoms (P4, §15.6).

Planner: rules first, costs later (ADR-09)

Chosen: a rule-based planner first, so a correct planner ships before a well-calibrated one (ADR-09, §18.1). Rejected: a cost-based planner from day one. When the rejected choice is right: when query shapes are known and stable in advance, such as a fixed 20-query dashboard, so the estimator can be hand-tuned before launch (ADR-09). The un-defer trigger is a cardinality error above 20% on skewed properties in benchmarks (§36).

Roads not taken

LSM-backed adjacency (§35 AA1) wins for write-heavy, distributed-from-day-one ingestion with secondary traversal (JanusGraph); rejected because it forfeits index-free adjacency (P1). A GraphBLAS matrix engine (§35 AA2) wins for matrix-shaped analytics at large scale on GPU/TPU-class hardware (RedisGraph); rejected because point traversal and transactional MATCH map poorly onto matrix operations (P4, P6, ADR-15). Relational emulation with recursive queries (§35 AA3) wins for a team with deep relational expertise and a light graph workload (Apache AGE); rejected because index-free adjacency needs native storage. A sharded MPP store (§35 AA4) wins when the graph exceeds one node from day one (TigerGraph); rejected for now because the reference graph fits on one node with tuning (§35 AA4, §33). The deferred register keeps exits open: SSI waits for observed write-skew anomalies, composite indexes for multi-column equality above 10% of the workload, and partitioning for a graph that provably outgrows one machine (§36).

What must never be false

  • I1: neighbours reachable in O(degree) pointer chases, never a B-tree probe. Seen via graphd_adjacency_probe_count (§7).
  • I2: every page read verifies its xxhash3-64 checksum. Seen via graphd_page_checksum_failures_total (§7, P3).
  • I3: a page is never dirtied before its WAL record is durable. Seen via code review, fuzzing, and WAL bytes versus dirty pages (§7).
  • I4: visibility follows the (xmin, xmax, active) rule. Seen via the write-skew fixture and graphd_mvcc_visibility_checks_total (§7).
  • I5: two writers on one record never both commit. Seen via the lost-update fixture and graphd_txn_conflicts_total (§7).
  • I6: GC never reclaims a version an active snapshot can see. Seen via graphd_oldest_snapshot_age_seconds (§7).
  • I7: a relationship is visible only if it and both endpoints are. Seen via store/endpoint-visibility.fixture (§7).
  • I8: redo applied twice equals redo applied once. Seen via graphd_recovery_redo_records_total (§7).
  • I9: index-entry visibility matches the store record. Seen via graphd_index_mvcc_mismatches_total (§7).
  • I10: the Bolt session never accepts an illegal transition. Seen via graphd_bolt_illegal_transitions_total (§7).
  • I11: ORDER BY returns the same order every run at one snapshot. Seen via graphd_query_result_hash in soak runs (§7).
  • I12: the free list never holds a live record id. Seen via graphd_store_double_alloc_detected_total (§7).
  • I13: cardinality estimates are non-negative and non-increasing as filters compose. Seen via graphd_plan_cardinality_estimate (§7).
  • I14: after recovery I1 to I13 hold within the recovery bound. Seen via graphd_recovery_duration_seconds (§7).

The conformance harness runs a seeded workload and asserts I1 to I14 in order after every operation; a failure halts, dumps the operation log, and the dump becomes a new regression fixture (§7).

What breaks in production

  • FM-1: a page fails its checksum. CorruptionError on a read, from bit rot, a torn write or bad RAM, detected by the checksum (I2). The page is quarantined; graphd-cli verify --repair rebuilds from the WAL if in range, else restore from backup (§24).
  • FM-3: recovery never finishes. The server restarts repeatedly and Analysis never completes, from a corrupted CLR or mis-set prev_lsn; detected when recovery exceeds the M8 bound. No automatic recovery (a design-time bug): inspect the LSN chain with graphd-cli dump-wal and patch forward from the last good checkpoint (§24, §14.6).
  • FM-4: version chains grow without bound. Memory and disk climb because a long-running transaction pins the oldest-snapshot pointer (I6); detected by the graphd_oldest_snapshot_age_seconds alarm. No automatic recovery, because GC must not race a live reader; an operator terminates the session (§24, §15.9).
  • FM-5: a plan blows up. A query never returns and CPU is pegged, from join-order search past its budget; detected when the 30 s query budget trips. The query is cancelled; the durable fix is usually a missing index or a rewrite (§24, §18.9).
  • FM-7: index and store disagree. A query returns or misses a row wrongly after a crash between INDEX_INSERT and its store commit; detected by schema-rebuild disagreement. Recovery is graphd-cli verify --rebuild-indexes (§24, I9).
  • FM-8: half a relationship link. After a crash one direction is patched and the other is not, from a non-atomic paired WAL record; graphd-cli verify walks both directions. Replay applies the paired record together, with --repair-adjacency for manual repair (§24, §14.8).

Threats to know (§23): T3, a plan-cost bomb, answered by a plan-cost cap of 1×10⁹. T6, resource exhaustion through a huge-fan-out *1..N path, answered by 30 s time and 1×10⁷ row budgets. T4, bit rot, answered by the checksum on every read (I2). T9, a torn WAL tail after power loss, answered by a per-record CRC that stops replay at the tear. T10, GC racing a slow reader, answered by the atomic oldest-snapshot read (I6). One mitigation, rejecting a join-free Cartesian query above a fan-out limit with a typed error, addresses both T6 and FM-5 (§18.6).

Loose cross-reference: §14.6 tags the torn log tail "FM-8/T9" and §14.9 tags it "T9, FM-8", but FM-8 in §24 is the half-patched adjacency link; the torn tail is threat T9 in §23 (§14.6, §14.9, §24, §23).

How it compares

  • Neo4j makes the same bet: fixed-width paged records, index-free adjacency, disk MVCC, a custom WAL plus ARIES, full Cypher and an enterprise causal cluster (§32). It proves that bet at production scale and pays for it in JVM GC-tail latency, the cost graphd avoids by using Rust (§32, ADR-02).
  • Memgraph keeps records in memory with in-memory MVCC and snapshots plus an optional WAL (§32). That suits workloads where durability can relax to periodic snapshots, a trade graphd rejects (§32, P5).
  • Dgraph uses posting lists, RAFT-replicated MVCC, GraphQL+ and native sharding (§32). That suits a graph that provably exceeds one machine before a planner exists (§32).
  • JanusGraph layers Gremlin over a pluggable wide-column store (§32). That suits reusing an existing Cassandra/HBase fleet, at the cost of index-free adjacency (§32, ADR-03).
  • RedisGraph stores an adjacency matrix (GraphBLAS), single-threaded per shard, persisted by RDB/AOF (§32). That suits PageRank-style analytics more than point traversal (§32, §35 AA2).

If you only remember three things

A graph database is a machine built so that a node is a pointer: neighbours come from chasing stored links in time proportional to the node's degree, not from probing an index (MM1, P1, I1). Durability and concurrency are layered on without giving that up: the log is the truth and pages are a rumour (MM2), and a snapshot is a frozen set of visible transaction ids, which is why the active set is in the rule (MM3, I4). Almost every deferred feature, from SSI and the cost-based planner to sharding, is deferred on purpose with a stated trigger, so the single-node engine is proven first (P14, §36, ADR-17).

Words used here

  • Property graph: nodes and relationships, each carrying typed key/value properties (§37).
  • Index-free adjacency: a node stores a direct pointer to its first relationship, so neighbours are found by pointer chase, not index probe (§37, P1).
  • Page cache: the fixed-size buffer pool between pages and disk (§37).
  • WAL: write-ahead log; every change is durable in the log before its page is dirtied (§37, P5).
  • LSN: log sequence number, a position in the WAL; each page remembers the last one that dirtied it (§37, §14.2).
  • ARIES: the analysis, redo and undo recovery algorithm (§37, §14.2).
  • CLR: compensation log record, a redo-only record written during undo (§37).
  • Checkpoint: a WAL marker saving the dirty-page and transaction tables to bound recovery time (§37).
  • MVCC / snapshot isolation: readers see a fixed snapshot without blocking writers, and writers conflict only on the same record (§37, P4).
