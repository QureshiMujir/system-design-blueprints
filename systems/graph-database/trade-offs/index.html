Decisions (§9) · 24 ADRs

ADR-01

Core language

Chosen

Rust (2024 edition)

Rejected

C++, JVM (Java/Kotlin)

When the rejected choice is right

C++ wins when a team already owns a mature arena/allocator stack and wants raw-pointer aliasing the borrow checker forbids (RedisGraph's GraphBLAS core)

Why: ownership-checked page cache/WAL without a GC pause budget

ADR-02

No managed runtime

Chosen

Native (no GC)

Rejected

JVM

When the rejected choice is right

JVM wins when pause-time SLAs are loose and the ecosystem (Lucene, Hadoop connectors) matters more than tail latency

Why: avoids Neo4j's GC-tail-latency budget entirely

ADR-03

Storage topology

Chosen

Index-free adjacency, record-oriented

Rejected

LSM-on-keys (cite LSM-Tree-Storage, this portfolio)

When the rejected choice is right

LSM wins under extremely write-amplification-tolerant ingestion where traversal is rare (JanusGraph-over-Cassandra's regime)

Why: constant-time neighbour traversal (P1)

ADR-04

Page-based store

Chosen

8 KiB paged store, own writer (cite B-Tree-Storage)

Rejected

LSM-backed page store

When the rejected choice is right

LSM-backed wins for random-point-lookup-heavy OLTP with little traversal

Why: shares the page format with the sibling B-Tree-Storage project

ADR-05

Durability mechanism

Chosen

Custom ARIES-style WAL (cite Write-Ahead-Log)

Rejected

no WAL, OS page cache only

When the rejected choice is right

OS-page-cache-only wins for ephemeral analytics scratch space where durability is not required (GraphChi-style batch jobs)

Why: crash recovery needs redo+undo, not fsync-and-hope

ADR-06

Page checksum

Chosen

xxhash3-64

Rejected

CRC32C

When the rejected choice is right

CRC32C wins where a hardware CRC32C instruction (SSE4.2) is guaranteed and checksums sit on a NIC/storage fabric's critical path

Why: fast, well-distributed on modern CPUs, no hardware dependency

ADR-07

Default isolation

Chosen

Snapshot isolation (SSI deferred, §36)

Rejected

Serializable Snapshot Isolation from day one

When the rejected choice is right

SSI-by-default wins when the workload is dominated by read-write conflicts that manifest as silent anomalies the application cannot detect (financial ledgers)

Why: ships correctness (I5) without the SSI abort-rate cost up front

ADR-08

Query language

Chosen

openCypher subset

Rejected

Gremlin, SPARQL, GQL-native

When the rejected choice is right

Gremlin wins when the workload needs imperative traversal composition across heterogeneous multi-model stores (TinkerPop's OLAP/OLTP split)

Why: public TCK, smaller surface to get bit-correct first

ADR-09

Planner strategy

Chosen

Rule-based first, cost-based later

Rejected

cost-based from day one

When the rejected choice is right

cost-based-first wins when query shapes are known and stable in advance (a fixed 20-query dashboard) so the estimator can be hand-tuned pre-launch

Why: ship a correct planner before a well-calibrated one

ADR-10

Wire protocol

When the rejected choice is right

a new protocol wins only when no existing driver ecosystem fits the data model at all (Dgraph's GraphQL+ hybrid)

Why: inherits every existing Bolt driver in every mainstream language

35. Alternative Architectures (Roads Not Taken)

AA1 — LSM-backed adjacency (JanusGraph-over-wide-column style).

Show the original text diagram
Client -> Query Layer -> Graph API adapter -> Wide-column store (Cassandra/HBase)
                                              (adjacency = keyed row scan, not pointer chase)

Regime where it wins: write-amplification-tolerant, horizontally-distributed-from-day-one ingestion where traversal is secondary to raw write throughput. Real system: JanusGraph. Rejected here because it forfeits index-free adjacency (P1, ADR-03) — the property this entire engine exists to provide.

AA2 — GraphBLAS adjacency-matrix engine (RedisGraph style).

Show the original text diagram
Client -> Cypher-like parser -> Linear-algebra IR -> Sparse matrix ops (GraphBLAS)
                                                      (traversal = matrix-vector multiply)

Regime where it wins: analytics workloads dominated by matrix-shaped operations (PageRank, similarity) at large scale on GPU/TPU-class hardware. Real system: RedisGraph. Rejected here because point-traversal-and-MATCH OLTP semantics (P4, P6) map poorly onto matrix operations, and single-row transactional updates are not GraphBLAS's strength.

AA3 — Relational emulation (property graph over a relational store with recursive CTEs).

Show the original text diagram
Client -> SQL/graph-extension layer -> Recursive CTE planner -> Relational row store
                                                                 (adjacency = join)

Regime where it wins: a team with deep existing relational operational expertise and a graph workload that stays light and secondary. Real system: Apache AGE (a PostgreSQL extension). Rejected here because index-free adjacency (P1) is structurally impossible without native storage, and recursive-CTE depth costs explode past a few hops (§2's opening argument).

AA4 — Sharded/distributed MPP graph store (TigerGraph style).

Show the original text diagram
Client -> Query Layer -> Distributed planner -> Shard 1 | Shard 2 | ... | Shard N
                                                 (Pregel-on-shards, vertex-cut partitioning)

Regime where it wins: the graph provably exceeds single-node RAM/disk from day one. Real system: TigerGraph. Rejected for Phase 0 because the Capacity Model (§33) shows the Reference Deployment Graph fits (with tuning) on one node, and cross-shard traversal coordination cost is not worth paying before the single-node engine is proven — distributed partitioning remains a registered deferral (§36), not an abandoned idea.
