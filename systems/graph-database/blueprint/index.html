1. Goal & Scope

graphd is a single-node, native property-graph database engine: it owns its page-based storage, its index-free adjacency representation, its write-ahead log and ARIES recovery, its snapshot-isolation MVCC, its secondary indexes, an openCypher-subset query language with a rule-based (later cost-based) planner and a Volcano pull-based execution runtime, a vertex-centric (Pregel-style) analytics runtime, and a Bolt-v4 wire protocol with gRPC/REST cohabitation. It is built to teach, end to end, why a graph database is a different machine than a relational store wearing a graph API.

Phase-0 deliverable (numbered list of crates/services that must exist and pass their tests by the end of Phase 0, §12):

  1. graphd-core — identifier types, error types (no storage logic yet).
  2. graphd-store — an in-memory MemStore implementing the Store trait (§11.9) at create_node / create_rel / read_node / neighbours_out granularity.
  3. graphd-cli — a hello-graph smoke-test binary.
  4. Repository scaffold — governance files, CI workflows, Makefile, Dockerfile (§10).
  5. graphd-conformance — an empty-but-wired conformance runner emitting a passing conformance.report.json for one no-op fixture.

System boundaries. Provides: a property-graph data model, ACID single-node transactions under snapshot isolation, an openCypher subset, five index types, ten graph algorithms, three wire protocols. Delegates: full-text tokenization/ranking to the sibling Search-Engine project's inverted-index crate (ADR-24); TLS termination to a reverse proxy in Phase 0 (mTLS is a deferred surface, §1.1). Does NOT provide: RDF/SPARQL, distributed partitioning, a cost-based planner, or encryption at rest in Phase 0 — all deferred (§1.1, §36).

Non-goals. Multi-model (document/key-value) storage in one engine (ArangoDB's bet, rejected — see Comparative Architecture Table, §32). A general-purpose OLTP row store. Training or inference of any kind. A distributed consensus layer (that is the Paxos project's job, not this one's).

Deployment model. A single graphd-server process per node, one database directory, optional read-replicas streaming the WAL (Phase-1+, §1.1). Operators run it under Kubernetes, systemd, or bare-metal; the reference deployment is a single 16–64 core node with local NVMe (§4).

Target users/operators. Backend engineers modelling relationship-heavy domains (social graphs, fraud rings, recommendation graphs, dependency graphs); SREs who must debug a slow traversal or a corrupted page at 3 a.m. using the runbooks in §25.

What later phases unlock. Phase 4 (§16) turns label/property lookups from O(n) scans into O(log n) probes. Phase 6 (§18) turns a declarative query into a plan an operator can read via EXPLAIN. Phase 7 (§19) turns "what's connected to what" into a callable analytics surface. Phase 8–10 (§20–§22) turn a library into a networked, observable service.

Language: Rust (2024 edition), locked at ADR-01. Rationale: the borrow checker enforces the aliasing discipline a page cache and a WAL writer require without a GC pause budget; the unsafe-free subset covers the record-layout code that would otherwise need C-style manual memory management. Rejected: C++ (ADR-01 — wins when a team already owns a mature arena/allocator stack and wants raw-pointer tricks the borrow checker forbids); the JVM (ADR-02 — wins when GC-pause SLAs are loose and the ecosystem, e.g. Lucene/Hadoop connectors, matters more than tail latency, which is exactly Neo4j's trade).

Prerequisites. Comfortable Rust (lifetimes, traits, async); systems engineering at the "why is a B-tree page-sized and an LSM not" level; the property-graph model (Neo4j or TinkerPop) and openCypher at the MATCH/WHERE/RETURN/CREATE/MERGE/DELETE level; write-ahead logging and ARIES-style recovery at the Database Internals level; enough graph theory to read a betweenness-centrality paper without flinching.

Estimated timeline. Phase 0: 1 week. Full plan (Phases 0–10): 22–26 weeks (~5–6 months) for one engineer at the pace implied by the per-phase week ranges in §12–§22.

2. Why Build This

Every backend eventually needs to answer "what is connected to what, and how cheaply can I follow it for ten hops." A relational store can model relationships, but past three joins the planner stops helping and the query that should read fifty rows becomes a hash join over half the table. A graph database is the machine whose internal data structures — index-free adjacency, a record-oriented store, a traversal-first execution model — are built for exactly that question.

This is the unique systems knowledge the project teaches: why Neo4j ships a paged record store and not an LSM (index-free adjacency, P1); why JanusGraph's storage abstraction over Cassandra/HBase costs the adjacency property the moment the store is generic (Comparative Architecture Table, §32); why Memgraph bet on in-memory MVCC instead of a disk-resident version chain; why TigerGraph wrote its own query language instead of adopting Cypher; and exactly which lines of code execute when a client issues MATCH (a:User)-[:FOLLOWS*1..3]->(b:User) RETURN b.name. There is nowhere left for magic to hide. It cross-links directly to the sibling B-Tree-Storage, LSM-Tree-Storage, Write-Ahead-Log, and Query-Planner projects in this portfolio — this project is where those four subsystems' lessons compose into one machine with a query language on top.

The calibration value: a graph database is small enough to finish in one plan (6 months, not years, §1) yet exercises storage, recovery, concurrency, query compilation, and distributed analytics — the full spine of "database engineer."

What Mastery Looks Like (5–8 named competencies, each tied to a phase):

  • Explain why index-free adjacency makes traversal O(degree) instead of O(log n), and defend that trade-off against an LSM-backed alternative (Phase 1, §13; Alternative Architectures §35 AA1).
  • Trace a crash mid-commit through the WAL to a correctly ARIES-recovered state without hand-waving the analysis/redo/undo passes (Phase 2, §14).
  • Derive, not recite, the snapshot-visibility formula and explain why the active-set term is load-bearing (Phase 3, §15; Mental Model MM3, §31).
  • Read a Cypher query and predict its logical plan, physical plan, and approximate cardinality before running EXPLAIN (Phase 5–6, §17–§18).
  • Implement PageRank correctly on the first try, including dangling-node redistribution, and explain why a naive textbook port is usually wrong here (Phase 7, §19).
  • Debug a Bolt driver hang by reading the session state machine, not the network bytes (Phase 8, §20).
  • Defend, with derived numbers, why this design chose single-node MVCC over distributed sharding for Phase 0 (Back-of-Envelope Capacity Model, §33; Alternative Architectures §35 AA4).

Three properties this diagram fixes for the rest of the document. First, storage is record-oriented and fixed-width for nodes/relationships with index-free adjacency: a node record holds a pointer to its first relationship; relationship records form a doubly-linked list per direction (P1, P2). 6. Design Principles

  1. P1 — Index-free adjacency is load-bearing. A node's neighbours are reachable by pointer chase, not a B-tree probe. Tradeoff: no secondary structure to keep in sync for traversal, at the cost of random-access page churn at high degree. Violating it (e.g. storing adjacency as a keyed lookup) turns every traversal into a probe and removes the engine's reason to exist.
  2. P2 — Records are fixed-width; properties are chained. Node/relationship/label records are fixed-width so record id resolves to id * record_size. Tradeoff: wasted padding bytes vs O(1) offset math. Violating it means variable offsets and a directory structure the page cache must consult before every read.
  3. P3 — One page format, one checksum. Every page is 8 KiB with a 32-byte header (magic, type, LSN, slot count, checksum) and an xxhash3-64 body checksum verified on every disk read. Tradeoff: 0.4% header overhead per page vs corruption detection. Violating it hides bit rot until a query returns wrong answers.
  4. P4 — Snapshot isolation is the default. Readers see the snapshot at transaction start; writers see their own writes plus that snapshot. Tradeoff: write skew is possible (accepted); lost update is not (rejected at commit). Violating it either serializes everything (throughput loss) or silently drops updates (correctness loss).
  5. P5 — The WAL is the source of truth. Every change is logged before the page is dirtied (write-ahead rule); recovery is "redo committed, undo uncommitted" (ARIES). Tradeoff: an fsync on the write path vs a database that can survive kill -9. Violating it makes crash recovery a coin flip.
  6. P6 — openCypher is the one query language. Not Gremlin, not GQL-native, not SPARQL. Tradeoff: a smaller, well-specified surface (public TCK) vs the imperative composability Gremlin offers. Violating it (shipping two first-class languages at once) forces two planners to stay semantically identical forever.
  7. P7 — The planner emits Volcano pull operators. Each operator is init/next/ close; the runtime is single-threaded per query in Phase 0. Tradeoff: simplicity and backpressure-for-free vs throughput left on the table until operator-level parallelism lands. Violating it (push-based execution) requires an explicit backpressure protocol from day one.
  8. P8 — Cardinality lives in the index, not the planner. The planner asks "how many nodes match label X" and the index answers from a maintained counter. Tradeoff: the index carries bookkeeping weight vs a planner that stays storage-agnostic. Violating it (planner-side heuristics) drifts from ground truth as the index is the only thing that is ever exactly right.
  9. P9 — Bolt is the wire format of record. gRPC and REST are convenience adapters over the same session machine. Tradeoff: adopting someone else's binary framing vs a from-scratch protocol. Violating it (inventing a new wire format) forfeits every existing Bolt driver.
  10. P10 — Determinism is default. Two reads of the same snapshot, or two runs of the same query at the same snapshot, return bit-identical results (row order excepted absent ORDER BY). Tradeoff: cardinality estimates must be pinned to the snapshot, not to wall-clock sampling. Violating it makes EXPLAIN a lie and a flaky conformance suite.
  11. P11 — Single writer per transaction, unlimited concurrent readers. A transaction's own writes are never contended by itself; other writers detect conflict only at commit (I5). Tradeoff: optimistic concurrency (retries) vs pessimistic locking (stalls). Violating it (locking on first write) turns every hot node into a serialization point.
  12. P12 — Backpressure is implicit in pull iteration. A consumer only calls next when ready; no explicit credit protocol exists inside one process. Tradeoff: simplicity vs the need for an explicit protocol once execution crosses a process/network boundary (Bolt's PULL n message is exactly that boundary crossing, §20).
  13. P13 — Recovery must be idempotent. Redo, applied twice, produces the same state as applied once (I8). Tradeoff: every WAL record must carry enough information (page LSN comparison) to become a no-op on replay. Violating it turns a second crash during recovery into data corruption instead of a safe retry.
  14. P14 — Every deferred surface gets an ADR and a register row. No feature is silently dropped; it is either built or explicitly deferred with an anchor in the Deferred Features Register (§36). Violating it is how a codebase accumulates undocumented scope gaps that surface as production surprises.

8. Domain Model

8.1 Property Graph Data Model

A node is (id, label-set, properties); a relationship is (id, type, direction, start-node, end-node, properties) — always directed and always typed, exactly one type per relationship. A property value is one of: null | bool | i64 | f64 | string | list | map | point | date | time | datetime | duration (the Bolt/PackStream structure set, §8.3). Pattern grammar (EBNF fragment, the Phase-5 parser target, §17):

Pattern       ::= PatternPart (',' PatternPart)*
PatternPart   ::= NodePattern (RelPattern NodePattern)*
NodePattern   ::= '(' Variable? Labels? Properties? ')'
RelPattern    ::= ('-' | '<-') '[' Variable? RelTypes? RangeLit? Properties? ']' ('-' | '->')
Labels        ::= (':' SymbolicName)+
RelTypes      ::= ':' SymbolicName ('|' SymbolicName)*
RangeLit      ::= '*' IntegerLit? ('..' IntegerLit?)?

8.3 Wire Protocol Frame Layout

Bolt v4 frames a message as a sequence of length-prefixed chunks terminated by a zero-length chunk; PackStream serializes the property-value set of §8.1 plus the Node/Relationship/Path structures.

Bolt chunk field Size Meaning
chunk_len 2 B big-endian byte count of the chunk body (0 = message terminator)
chunk_body chunk_len B PackStream-encoded bytes; a message may span many chunks

Session states (the I10 state machine, detailed in §20.2): Disconnected → Connected → Ready ⇄ Streaming, and Ready ⇄ TxReady ⇄ TxStreaming, with Failed/Interrupted as error states reachable from any state and requiring an explicit RESET to return to Ready.

8.4 Query Semantics — Logical → Physical Lowering (Worked Example)

MATCH (a:Person)-[:KNOWS]->(b:Person) WHERE b.age > 30 RETURN b.name lowers as:

AST                     Logical Plan                  Physical Plan
Match(a:Person)     ->  NodeByLabelScan(Person, a) ->  NodeByLabelScan(Person, a)
-[:KNOWS]->(b:Person)  Expand(a, OUT, KNOWS, b)     ->  ExpandAll(a, OUT, KNOWS, b)
Where b.age > 30    ->  Filter(b.age > 30)          ->  Filter(b.age > 30)

Predicate push-down (§18.2, ADR-09) would move Filter earlier only if age were bound before the expand; here it cannot, since b is produced by Expand.

8.6 Worked Example — End-to-End Trace

Ingest two :Person nodes (Ada, Grace) and one [:KNOWS] relationship, then run MATCH (a:Person)-[:KNOWS]->(b:Person) RETURN b.name. Trace: NodeByLabelScan(Person) yields {Ada, Grace} in id order → ExpandAll(OUT, KNOWS) walks Ada.first_rel (I1), finds the KNOWS relationship to Grace, yields (Ada, Grace) — Grace has no outgoing KNOWS so contributes no row → Projection(b.name) emits {"name": "Grace"}. One row.

8.7 Malformed-Input Example

MATCH (a)-[:KNOWS]->(b RETURN b.name (missing closing paren). The parser (§17.3) fails at the token following b, expected one of {')', ':', '{'}; graphd-cypher emits a ParseError{position: 27, expected: [...], found: "RETURN"} — no partial execution occurs.

8.8 Failure-Path Example

A transaction writes INSERT_PROP and COMMIT WAL records (durable), but the process is killed before the dirtied property page is flushed. Recovery: Analysis finds the transaction in the transaction table as committed; Redo replays INSERT_PROP because the on-disk page LSN is older than the record's LSN (I3, I8); Undo does nothing for this transaction. Post-recovery, the property is visible — exactly the ARIES contract (§14.5).

Condition Visible?
rec_xmin ∈ snap.active or rec_xmin ≥ snap.xmax No — writer not committed relative to this snapshot
rec_xmax == TxnId(0) (never deleted) Yes
rec_xmax ∈ snap.active or rec_xmax ≥ snap.xmax Yes — deleter not committed relative to this snapshot

13. Phase 1 — Paged Store, Fixed-Width Records, Index-Free Adjacency

13.1 Objectives

Replace MemStore with a durable-shaped (not yet WAL-durable) paged store: graphd-page's page cache, and graphd-store's NodeStore/RelStore/PropStore/dictionaries per the layouts in §8.2/§11.2. Constraint: no WAL yet (§14) — a clean shutdown/reopen must round-trip; crash-durability is explicitly out of scope until Phase 2.

13.2 Detailed Implementation Steps

Page cache (graphd-page::PageCache): fixed-capacity, hash-indexed buffer pool, CLOCK replacement with a dirty-page write-out preference; pinned frames never evicted; shared latch for reads, exclusive for writes (§11.2). Record stores: each of Node/Rel/Prop is a sequence of fixed-width records (P2) packed after the 32-byte page header; record id resolves to (page_id, offset) via page_id = id / records_per_page, offset = id % records_per_page, using the exact byte sizes and per-page counts derived in §8.2 (204 nodes/page, 92 rels/page, 127 props/page). Free list: a singly-linked list of free record ids, head stored in the store's page 0 header; allocate/free pop/push the head (I12). Index-free adjacency (I1, P1): NodeRecord.first_rel anchors a doubly-linked relationship list per direction (start_prev_rel/start_next_rel, end_prev_rel/end_next_rel, §8.2); neighbours_out/neighbours_in (§11.9) walk it in O(degree) pointer chases. Property store: a chain of PropertyRecords anchored at first_prop; values > 16 B overflow into a free-listed dynamic block store (block sizes 16/32/64/128/256/512 B, rounding up). Dictionaries: label, rel-type, and property-key stores are append-only (id, length-prefixed string) pairs, rebuilt into an in-memory hash table at startup.

13.3 Deliverable

A Store (§11.9) backed by pages that ingests and reads back nodes/relationships/ properties; a round-trip test ingesting 1,000,000 nodes and 5,000,000 relationships, clean-shutdown-and-reopen, with full read parity.

13.4 Acceptance Criteria

  • neighbours_out on the 1M/5M reference graph resolves in O(degree) pointer chases with zero B-tree probes (I1), measured via graphd_adjacency_probe_count staying at exactly degree per call.
  • Micro-benchmark benchmarks/micro/store.json records read_node/read_rel/ neighbours_out p99 and gates against M1 (< 50 ms single-hop at 1B-edge scale, extrapolated at this stage from the 1M/5M harness).
  • Records-per-page match §8.2 exactly: 204/92/127.

14. Phase 2 — Write-Ahead Log & ARIES Recovery

14.1 Objectives

Insert a WAL between the page cache and disk (P5, I3) and implement ARIES recovery (Mohan et al. 1992) so the engine survives kill -9. Constraint introduced: every store mutation from §13 must now route through a WAL record before the page is dirtied.

14.2 Detailed Implementation Steps

WAL record format (graphd-wal): lsn(8B) prev_lsn(8B) txn_id(8B) type(1B) len(3B) payload(len B) crc(4B); types BEGIN COMMIT ABORT INSERT_NODE UPDATE_NODE DELETE_NODE INSERT_REL UPDATE_REL DELETE_REL INSERT_PROP UPDATE_PROP DELETE_PROP CHECKPOINT_BEGIN CHECKPOINT_END; payloads carry before/after images (I3, P5). Group commit: transactions' COMMIT records accumulate in an in-memory buffer; fsync fires at a 64 KiB buffer threshold or a 1 ms timer, whichever first — this is the throughput lever against M6. Page LSN (I3, I8): every page header's lsn field (§11.2) records the last WAL record that dirtied it; recovery replays a record only if the page's on-disk LSN is older, making redo idempotent (P13). Checkpoint: writes CHECKPOINT_BEGIN, flushes all dirty pages, writes CHECKPOINT_END with the serialized dirty-page table and active-transaction table; recovery starts from the last CHECKPOINT_END, not the log head. ARIES recovery, three passes: Analysis (scan from last CHECKPOINT_END to log end, reconstruct the dirty-page and transaction tables), Redo (from the oldest recoveryLSN, replay every record whose LSN exceeds the page's on-disk LSN — idempotent per I8), Undo (for every non-committed transaction, walk prev_lsn backwards emitting compensation log records, CLRs, which are redoable but never themselves undone).

14.3 Deliverable

graphd-wal writer/reader wired into every Store mutation; ARIES recovery passing the crash fixtures; a torture test of 1,000 random transactions each kill -9'd at a random offset, restart, state-correctness assertion.

14.4 Acceptance Criteria

  • Recovery time on a 100M-edge graph < 30 s (M8), measured by benchmarks/macro/recovery.json.
  • WAL fsync p99 < 2 ms on reference NVMe (M6).
  • All 1,000 torture-test crash points recover to a state where I1–I14 hold (I14).

14.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/recovery/10-crash-mid-commit.replay COMMIT durable, page not flushed redo restores the page
conformance/corpora/recovery/11-crash-pre-commit.replay ABORT record missing undo via prev_lsn chain
conformance/corpora/recovery/12-checkpoint.replay recovery from last CHECKPOINT_END earlier records skipped

14.6 Pitfalls

  • Forgetting the crc on a WAL record — a torn tail write returns garbage without it, and that is the only signal that says "stop replay here" (feeds FM-8/T9).
  • Replaying a CLR as if it were undoable — CLRs are redo-only; a bug here causes recovery loops (FM-3).
  • Group-commit deadlock: the flush thread must never hold a page-cache latch — WAL flush strictly precedes page eviction, never the reverse.

14.7 Performance Concerns

fsync is the dominant cost on the write path; group commit amortizes it across concurrent committers. Checkpoint I/O competing with foreground writes for disk bandwidth (FM-11) — the checkpoint scheduler backs off past a dirty-page watermark.

14.8 Edge Cases

A crash exactly between CHECKPOINT_BEGIN and CHECKPOINT_END (recovery must fall back to the previous completed checkpoint); a WAL segment that ends mid-record (CRC catches it); two transactions racing to patch the same relationship's paired doubly-linked-list update (both halves must land in one WAL record, per the §13.6 pitfall's fix).

14.9 Failure Analysis

A torn write at the WAL tail (power loss mid-fsync) is detected by CRC mismatch and treated as end-of-log (T9, FM-8); a corrupted CLR causes a non-terminating recovery loop (FM-3), diagnosed via graphd-cli dump-wal inspecting the LSN chain.

14.10 Operational Notes

graphd_wal_bytes_written_total, graphd_wal_fsync_seconds (histogram, gates M6), graphd_pages_dirty (gauge, feeds the checkpoint scheduler). Runbook: docs/runbooks/ corruption.md covers a checksum-mismatch page; recovery duration is logged structurally per crash for the M8 gate.

15. Phase 3 — Snapshot-Isolation MVCC

15.1 Objectives

Insert MVCC into the property/node/relationship version chain (§8.2) so concurrent readers never block writers and vice versa (P4, P11). Contract: exactly the snapshot isolation of Berenson et al. 1995. Constraint introduced: every read path must now call is_visible (§11.3, I4).

15.2 Detailed Implementation Steps

Transaction lifecycle: BEGIN assigns a TxnId and a Snapshot{xmin, xmax, active} (I4); reads filter every candidate record through is_visible (§11.3); writes append a new version, setting the old version's xmax to the writer's TxnId. Version chain: PropertyRecord.prev_version links to the older version (§8.2); reads walk newest-to-oldest, returning the first version visible to the reader's snapshot; on abort the writer's version unlinks and frees back to the free list (I12). Conflict detection (I5, P11): at commit, if any version this transaction created has had its xmax set by another transaction, commit fails — write skew is permitted (disjoint records, no direct conflict), lost update is not. Garbage collection (I6): a version whose xmax predates the oldest active snapshot is unreachable by any live reader; GC atomically reads the oldest-active-snapshot pointer before reclaiming, then walks version-chain heads freeing reclaimable versions in the background, never blocking readers. Node/relationship visibility (I7): a relationship is visible iff its own record is visible and both endpoint nodes are visible — endpoint deletion after a relationship read begins must not surface a dangling reference.

15.3 Deliverable

Snapshot/is_visible (§11.3) reachable from every read path; a stress test of 256 concurrent writers and 64 concurrent readers at a fixed seed producing deterministic commit/abort decisions (P10).

15.4 Acceptance Criteria

  • Write-skew fixture commits both transactions; lost-update fixture rejects exactly one (I5).
  • GC never reclaims a version visible to an active reader across 10,000 seeded stress-test runs (I6) — zero graphd_mvcc_gc_races_total false negatives.
  • Endpoint-visibility fixture (I7) passes: a relationship whose endpoint is deleted by a later, still-invisible transaction is itself invisible.

15.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/mvcc/20-write-skew.snapshot two txns update disjoint records from stale reads both commit
conformance/corpora/mvcc/21-lost-update.snapshot two txns update the same record exactly one commits
conformance/corpora/mvcc/22-gc-races-reader.snapshot long-running reader concurrent with GC reader's snapshot stable throughout

15.6 Pitfalls

  • Forgetting the active set — a bare (xmin, xmax) check wrongly treats a transaction that was running when the snapshot was taken as committed (I4's exact failure mode).
  • GC racing the oldest-snapshot pointer — if that pointer is read non-atomically, GC can reclaim a version a reader is about to look at (I6, FM-4).
  • Assuming SI prevents phantoms — it does not; document this explicitly in docs/mvcc.md and defer SSI (§36) rather than silently claiming a stronger guarantee than is shipped.

15.7 Performance Concerns

Version-chain length under a hot, frequently-updated node grows linearly with update rate until GC catches up (§33, capacity number C7); long-running read transactions delay GC globally, since the oldest-active-snapshot pointer cannot advance past them.

15.8 Edge Cases

A transaction that begins, reads, and never commits or aborts (session leak) pins GC indefinitely (FM-4); a version chain long enough that a full scan for the visible version becomes the traversal's dominant cost; a relationship whose both endpoints are deleted by different, mutually-invisible transactions.

15.9 Failure Analysis

Unbounded version-chain growth surfaces as graphd_oldest_snapshot_age_seconds climbing (FM-4); the manual recovery path is identifying and terminating the offending long-running session via graphd-cli, logging its start time and a hashed query fingerprint for forensics.

15.10 Operational Notes

graphd_active_transactions (gauge), graphd_oldest_snapshot_age_seconds (gauge, alarms into docs/runbooks/triage.md), graphd_txn_conflicts_total (counter). GC runs as a background task, never on the commit critical path.

16. Phase 4 — Secondary Indexes & Cardinality

16.1 Objectives

Give the future planner (§18) something faster than a full label scan: a label B-tree, a property B-tree, a property hash, and a bulk-loaded R-tree (P8). Constraint: every index entry must be MVCC-aware (I9) — an index that returns a deleted row is a correctness bug, not a performance one.

16.2 Detailed Implementation Steps

Label index: a B-tree keyed by LabelId, valued by a node-id iterator, paged like the record stores (§13.2), MVCC-aware entries (xmin/xmax per entry), rebuildable via graphd-cli schema-rebuild. It also maintains a per-label count for O(1) cardinality (count(:Person) is one probe — the P8 contract). Property index (B-tree): keyed (LabelId, PropertyKeyId, Value), valued by node id; supports equality and range; single-key only in Phase 0 (ADR-21, composite deferred, §36). Property index (hash): same key shape, equality-only, for unique-constraint-style lookups — faster than the B-tree, no range support. Full-text: delegated to the sibling Search-Engine project's graphd-search crate when it lands (ADR-24) — not built bespoke here. Spatial (R-tree): bulk-load only in Phase 0 (ADR-22); incremental insert/delete deferred (§36); reuses the page format (§11.2). Index maintenance: every commit emits INDEX_INSERT/INDEX_DELETE WAL records per affected index (I3 extends to indexes); a bulk load emits one INDEX_BULK_LOAD record naming its rebuild source. Cardinality estimation (I13): the planner asks an index for its count; per-value selectivity approximates as count / distinct_values (a maintained counter); histograms for skewed distributions are a Phase-1+ surface (§36, Kossmann 2000's survey names this exact trade-off).

16.3 Deliverable

Label B-tree, property B-tree, property hash, R-tree-at-bulk-load; a test that MATCH (n:Person {name: 'Ada'}) resolves through the property hash in O(1) probes; a schema-rebuild path reconstructing every index from the store.

16.4 Acceptance Criteria

  • Property-hash equality lookup on the 1M-node reference set: ≤ 2 index probes (O(1)), measured against fixture index/hash-probe-count.fixture.
  • B-tree range scan returns rows in key order for 100% of conformance/corpora/index/ ranged-property.fixture cases.
  • schema-rebuild reconstructs all four index types from the store alone, verified byte-identical to the pre-rebuild index for a 10,000-node fixture graph.

17.1 Objectives

Turn Cypher source text into a semantically validated AST (§11.4) for the fixed Phase-0 clause subset (P6, ADR-08). Constraint: the subset must be exactly MATCH/ OPTIONAL MATCH/WHERE/WITH/RETURN/CREATE/MERGE/DELETE/DETACH DELETE/SET/ REMOVE/UNWIND/UNION/UNION ALL/CALL — paths up to length 8 fixed, * variable-length up to bound 6.

17.2 Detailed Implementation Steps

Lexer (graphd-cypher::lexer, hand-written): identifiers, keywords, numeric/string literals (with escapes), parameter markers ($param), punctuation, operators; consumes UTF-8; exact-match keyword table (match is reserved, match_count is a valid identifier). Parser (graphd-cypher::parser, nom combinators, ADR-13): implements the pattern EBNF of §8.1, extended for the full clause grammar (MATCH ReadingClause* UpdatingClause* RETURN? per the openCypher spec, §5); errors recover at clause boundaries, producing a partial AST with a ParseError node rather than aborting the whole parse (§8.7's worked example is this exact path). Semantic analysis (§11.4 annotation pass): binds every identifier to a slot, resolves labels/property keys/relationship types against the dictionaries (§13.2), type-checks expressions (numeric vs string vs node vs relationship), and rejects a CREATE pattern that reuses an unbound variable as a new relationship's start node.

18. Phase 6 — Logical/Physical Planner & Volcano Runtime

18.1 Objectives

Turn the AST (§17) into an executable physical plan (§11.5) and run it (§11.6). Constraint: Phase 0 ships the rule-based planner only (ADR-09); the cost-based planner is a named Phase-1+ surface (§36).

18.2 Detailed Implementation Steps

Logical planner: walks the AST, emitting LogicalOp (§11.5); each MATCH becomes NodeByLabelScan → Expand → Filter; OPTIONAL MATCH becomes that chain wrapped in Apply with an OptionalExpand leaf — never a plain outer join, because the right side must run in the left side's variable scope (exactly Apply semantics, P7). Rule-based optimizations (ADR-09): predicate push-down to the earliest operator that can evaluate a predicate; selection push-down through joins; constant folding; pattern decomposition (an N-pattern-part MATCH becomes N scans joined by Apply); index-hint extraction ({name: 'Ada'} resolves to NodeByPropertyHashSeek, not scan-then-filter, per P8/§16.2). Cost-based planner (deferred, ADR-09, §36): a Selinger-style (Selinger et al. 1979) dynamic-programming search over join orders, cost table cost(NodeByLabelScan) = count(label)×READ_COST, cost(Expand) = cost(input) + count(input)×avg_degree×READ_COST, cost(Filter) = cost(input) + selectivity×READ_COST, cost(Sort) = cost(input)+count(input)×log₂(count(input))×SORT_COST; budgeted at 1,000 candidate plans or 100 ms, whichever first. Physical planner: NodeByLabelScan may lower to AllNodesScan+Filter absent a label index; Expand lowers to ExpandAll (degree-based) or ExpandInto (both endpoints bound); Sort may lower to Top under a LIMIT. Volcano runtime (§11.6): each PhysicalOp implements Operator; single-threaded pull pipeline, backpressure implicit (P12). Variable-length paths (P7): [:KNOWS*1..3] lowers to a bounded BFS rooted at the bound endpoint, emitting one row per (start, end, path) triple up to the range bound — this is the §19 BFS mechanism reused as a physical operator, not a separate implementation.

18.3 Deliverable

The runtime executes the §17.1 clause subset end to end on the LDBC SNB SF1 dataset; the rule-based planner reproduces the openCypher reference plan shape for LDBC SNB interactive queries 1–7 (operator naming may differ); an EXPLAIN/PROFILE printer emitting the physical plan with cardinality estimates.

18.4 Acceptance Criteria

  • Six-hop traversal p99 on the reference deployment graph < 5 s (M2).
  • EXPLAIN output for LDBC SNB queries 1–7 matches the golden files in docs/architecture/plan-snapshots/ exactly at the operator-chain-shape level.
  • A MATCH with no join condition and a Cartesian fan-out estimate > 1×10⁹ rows is rejected with a typed CartesianExplosionError, not silently executed.

18.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/cypher-tck/match-where-return.feature §17.1 subset end to end TCK pass
conformance/corpora/ldbc-snb/short-1.json…short-7.json LDBC SNB short reads expected rows
docs/architecture/plan-snapshots/short-1.plan golden EXPLAIN output plan-shape match

18.6 Pitfalls

  • Cartesian products from a join-free query — reject above a configured fan-out threshold (default 1×10⁹) with a typed error rather than executing it (this is the single mitigation Hard Question 19, §34, asks about, resolving both T6 and FM-5).
  • Implementing OPTIONAL MATCH as a left outer join over Expand — wrong; it must be Apply-scoped (§18.2).
  • Emitting Sort + StreamingAggregation for RETURN COUNT(*) GROUP BY n.label — the planner must emit EagerAggregation (hash-aggregate); the input is unsorted.
  • Materializing every path in a variable-length traversal — a degree-100 graph at bound 6 materializes up to 10¹² paths if all are kept; stream and project at the consumer, never collect.

18.7 Performance Concerns

Join-order search cost grows combinatorially without the cost-based planner's DP memoization (deferred, ADR-09) — Phase 0's rule-based planner sidesteps this by never searching, at the cost of occasionally picking a suboptimal join order. Apply-nested OPTIONAL MATCH re-executes its right side once per left row — a per-row constant-factor cost that dominates at high left-side cardinality.

18.8 Edge Cases

A query with zero MATCH clauses (pure literal RETURN); a MATCH pattern with a relationship type list ([:KNOWS|:FOLLOWS]); a LIMIT 0; a variable-length path whose lower bound exceeds its upper bound (rejected at semantic analysis, §17.2, not the planner).

18.9 Failure Analysis

A planner cost blow-up (FM-5) — the per-query time budget (30 s, §4) trips and cancels the query, with the EXPLAIN plan and cardinality estimates archived for the operator to diagnose via docs/runbooks/slow-query.md; the durable fix is usually a missing index (§16) or a query rewrite, not a budget increase.

19. Phase 7 — Graph Algorithms & Pregel Runtime

19.1 Objectives

Ship the ten analytics kernels of §11.11, each callable from Cypher via CALL algo.<name>, plus the vertex-centric Pregel runtime (§11.7) they optionally run on. Constraint: exact correctness against reference implementations at named tolerances, not "looks about right."

19.2 Detailed Implementation Steps

BFS (P1's O(degree) adjacency, Cormen et al.): frontier queue plus a visited bitmap sized to the store's node high-water mark (never to a node's degree — a frontier-explosion pitfall below); algo.bfs(source, max_depth). DFS: stack-based, same bitmap, recursive variant for path recording, iterative for performance; algo.dfs(source, max_depth). Dijkstra: min-heap on (distance, node), edge weights from a configurable property key (default weight, fallback 1.0), rejects negative weights with a typed error (Bellman-Ford is the alternative, not shipped); algo.dijkstra(source). A*: Dijkstra plus a caller-supplied heuristic closure (haversine distance for geographic graphs read from lat/lon); algo.aStar. PageRank (Needham & Hodler 2019): iterative power method, damping 0.85, max 20 iterations, tolerance 1e-6, with explicit dangling-node rank redistributed uniformly each iteration (P10 determinism requires this be exact, not approximate); algo.pageRank. Weakly connected components: union-find over the edge list; strongly connected components (Tarjan) deferred to Phase-1+ (§36); algo. weaklyConnectedComponents. Louvain (Blondel et al. 2008): local-moving plus aggregation, two phases; Phase 0 ships to "passes the LDBC SNB community-detection sanity check on SF1," full multi-level hierarchy is Phase-1+; algo.louvain. K-shortest-paths (Yen 1971): built on Dijkstra, returns the top-k paths by total weight; algo.kShortestPaths. Betweenness (Brandes 2001) and closeness: Brandes' algorithm for betweenness (O(V·E), scoped per §33 capacity number C9 — not run on the full reference deployment graph), Floyd-Warshall fallback for closeness on small graphs; algo.betweenness/algo.closeness. Pregel runtime (§11.7, Malewicz et al. 2010): BSP supersteps, message delivery at the start of the next superstep, optional combiners; Phase 0 ships in-memory; the GraphChi (Kyrola et al. 2012) disk-friendly sliding-window variant is a Phase-1+ surface (§36) for graphs exceeding RAM.

19.3 Deliverable

Every algorithm in §19.2 callable from Cypher; the vertex-centric Pregel PageRank reproduces the direct-kernel PageRank to 1e-4 absolute error on LDBC SNB SF1.

19.4 Acceptance Criteria

  • PageRank matches a NetworkX (small-graph) or Neo4j GDS (large-graph) reference within rtol 1e-4 (M11).
  • BFS/Dijkstra/connected-components match the fixed KONECT/BFS reference fixtures exactly (bit-identical, per P10).
  • Betweenness/closeness run to completion on graphs ≤ 10,000 nodes within the 30 s per-query budget (§4); larger graphs require explicit sampling (a Phase-1+ surface, §36).

19.6 Pitfalls

  • PageRank dangling nodes leaking rank — redistribute uniformly every iteration or ranks drift toward zero (this is the single most common PageRank bug in a fresh port).
  • Frontier explosion in BFS at high degree — size the visited bitmap to the store's high-water mark, not the source's degree; reject expansions whose frontier exceeds 1×10⁹ with a typed error rather than allocating unbounded memory.
  • Running Dijkstra on negative-weight input — reject at the API boundary; do not silently produce wrong distances.

19.7 Performance Concerns

Brandes' betweenness is O(V·E) — intractable at the 1B-node/5B-edge reference scale (§33, C9); PageRank's dense rank vector costs one full edge-list pass per iteration (20 iterations × 5×10⁹ edges is the dominant cost, bounded by M11's gate); Pregel message buffers grow with fan-out per superstep, capped by the same frontier-explosion guard as BFS.

19.8 Edge Cases

A graph with zero edges (PageRank converges to uniform rank in one iteration); a disconnected graph (weakly-connected-components must report every singleton); a self-loop edge in Dijkstra (zero-cost cycle, must not infinite-loop the min-heap pops).

19.9 Failure Analysis

A kernel that silently returns wrong results without an error (e.g. missing dangling-node redistribution) is the worst failure class here because nothing crashes — it is caught only by the reference-tolerance conformance fixtures (§19.5), which is exactly why M11's rtol 1e-4 gate exists in CI, not just in a one-time manual check.

19.10 Operational Notes

Each algo.* call is traced as its own OpenTelemetry span (§21.3) with algorithm name and input size as attributes; long-running analytics calls (betweenness on a large graph) are subject to the same 30 s per-query budget (§4) unless explicitly run through graphd-bench's offline harness instead of a live query.

20. Phase 8 — Bolt v4 Server, gRPC, REST

20.1 Objectives

Expose the query engine (§17–§19) over the network: Bolt v4 as the primary wire protocol (P9, ADR-10), with gRPC and REST as thin adapters over the same session machine. Constraint: basic/none auth only in Phase 0 (ADR-23); mTLS/Kerberos/OIDC deferred (§36).

20.2 Detailed Implementation Steps

Bolt framing (§8.3, graphd-bolt): chunked messages terminated by a zero-length chunk; PackStream encodes the property-value set of §8.1 plus Node/Relationship/Path/ Date/Time/DateTime/Duration/Point structures; small integers in [-16, 127] encode inline (a naive always-long-form encoder is correct but 3–5× larger on the wire — a throughput regression, not a correctness one). Session state machine (§11.8, I10): states Disconnected → Connected → Ready ⇄ Streaming, Ready ⇄ TxReady ⇄ TxStreaming, with Failed/Interrupted reachable from any state; an illegal transition returns FAILURE and requires RESET — never silently queued (P9). Auth (ADR-23): basic and none modes only. gRPC (graphd-grpc): docs/api/graphd.proto defines BeginTx/CommitTx/ RollbackTx/Run/Pull/Discard, internally sharing the Bolt session machine — a thin adapter, not a parallel implementation. REST (graphd-rest, tower-http): POST /tx/{db}/commit (autocommit), POST /tx/{db} (begin explicit), POST /tx/{db}/{txid} (run in explicit txn), POST /tx/{db}/{txid}/commit, DELETE /tx/{db}/{txid} (rollback) — mirrors the Neo4j HTTP transaction API shape. Transaction stickiness: one Bolt session has at most one open transaction; a second BEGIN on the same session is a protocol error the state machine rejects (I10).

20.3 Deliverable

The Neo4j Java and Python drivers (pointed at this server's Bolt address) connect, authenticate, and run a Cypher query; curl -X POST .../db/neo4j/tx/commit -d '{"statements":[{"statement":"MATCH (n) RETURN count(n)"}]}' returns a valid response.

20.4 Acceptance Criteria

  • Bolt handshake-to-first-row latency p99 < 20 ms (M12).
  • Zero illegal-transition acceptances across the full bolt.protocol conformance bucket (I10) — 100% of conformance/corpora/bolt/*.fixture pass.
  • PackStream small-int encoding matches the pinned fixture form (not the always-long form) for 100% of conformance/corpora/bolt/run-pull-success.fixture byte comparisons.

20.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/bolt/handshake.fixture Bolt handshake bytes exact byte match
conformance/corpora/bolt/run-pull-success.fixture RUN + PULL, known response exact byte match, small-int form
conformance/corpora/bolt/run-failure.fixture a syntax-error response typed FAILURE message

20.6 Pitfalls

  • Always emitting PackStream's long-form integer encoding — technically valid, 3–5× larger, and the kind of regression that shows up only in throughput dashboards, not correctness tests.
  • Treating Bolt chunk boundaries as message boundaries — a message can span chunks; decoding must concatenate before parsing, never parse per-chunk.
  • Allowing a second open transaction per session — the session machine (I10) must reject it as a protocol error, not silently multiplex it.

20.7 Performance Concerns

PackStream encode/decode is on the hot path for every row; the small-int fast path (§20.2) is the single biggest wire-size lever. gRPC/REST adapters add one serialization hop over raw Bolt — acceptable since they are convenience surfaces, not the throughput-critical path.

20.8 Edge Cases

A client that sends PULL before RUN (illegal transition, I10); a REST request with a malformed JSON body; a gRPC client that never calls CommitTx or RollbackTx (the session times out and rolls back, feeding the transaction-lifecycle state machine of §8.5).

20.9 Failure Analysis

A Bolt session desync (FM-6) — driver hangs waiting for a response the server already sent as FAILURE — is diagnosed from the last-20-transitions session log; recovery is a client-side RESET or the operator bouncing the connection; the durable fix is always in the state machine, never a protocol-level retry hack.

20.10 Operational Notes

graphd_bolt_illegal_transitions_total (I10), graphd_bolt_frame_errors_total (T8), graphd_open_connections (gauge). docs/runbooks/triage.md covers a hung-driver report as its first named scenario.

26. Compatibility & Versioning

Wire compatibility: Bolt v4 is versioned per the upstream Bolt handshake negotiation; a server refuses an unsupported client version rather than guessing. Storage compatibility: the page format (§11.2) and record layouts (§8.2) carry an on-disk format version in the store header; a version bump requires an explicit migration tool, never an in-place silent reinterpretation. Schema evolution: the label/property-key/rel-type dictionaries (§13.2) are append-only, so adding a label or property key is always backward-compatible; removing one is not supported in Phase 0 (PhaseDeferred("§26") — online expand-contract migration, registered §36). API stability: the REST/gRPC surfaces (§20.2) follow SemVer; a breaking change bumps the major version and ships behind a new /v{n}/ path or .proto package. Rolling-upgrade guarantee: a read-replica (Phase-1+) may run one minor version behind the primary; a major-version gap is refused at the replication handshake (FM-9's lag alarm also fires here, since a refused replica reads as infinite lag). Deprecation policy: a deprecated Cypher clause or procedure emits a structured warning for two minor versions before removal, tracked in CHANGELOG.md.

30. Scalability Analysis

Stays constant: single-hop traversal latency (I1, O(degree) regardless of graph size); is_visible cost (I4, O(1) per version). Grows: version-chain length under hot-node update rate (O(updates since last GC epoch), §15.9); B-tree/hash index size (O(n) in indexed properties); recovery time (O(dirty-page-table size at last checkpoint), bounded by M8). Named bottlenecks, in order: (1) page-cache hit rate once the working set exceeds the 16 GiB default (§4, §33 C4) — the first wall almost every deployment hits; (2) WAL fsync throughput on spinning disks or under-provisioned cloud volumes (M6 assumes NVMe); (3) planner join-order search cost once the cost-based planner (Phase-1+) is enabled without histograms; (4) single-node CPU ceiling for O(V·E) analytics (betweenness, §19.7). Scaling levers, in order of the bottlenecks above: raise the page-cache ceiling or reduce the hot fraction (index more selectively); move to NVMe or batch commits harder; add histograms (§36) before enabling the cost-based planner at scale; sample instead of computing exact betweenness/closeness past a node-count threshold (§19.7). Horizontal vs vertical: Phase 0–10 scale vertically only (bigger node); horizontal scaling is read-replicas (Phase-1+, read-only) then distributed partitioning (Phase-2+, §35 AA4) — the latter adds cross-shard traversal coordination cost that this design deliberately avoids paying before the single-node engine is proven (§33's capacity ceiling justifies the sequencing). The practical ceiling for this architecture is the single-node page-cache/CPU envelope of §4; the lever beyond it is the deferred partitioning surface (§36), not a bigger box, once the Reference Deployment Graph (§4) itself outgrows one machine.

31. Mental Models & First Principles

  • MM1 — "A node is a pointer, not a row." Predicts why joins disappear in graph queries. Bug class without it: reintroducing hash-join thinking and indexing for traversal instead of using adjacency. Applies in §13, P1.
  • MM2 — "The WAL is the truth, the page cache is a rumor." Predicts recovery correctness. Bug class without it: writing pages before the WAL (violates P5/I3). Applies in §14.
  • MM3 — "A snapshot is a frozen set of visible transaction ids, not a frozen clock reading." Predicts why (xmin, xmax, active) and not (xmin, xmax) alone. Bug class without it: accepting a phantom-visible active transaction. Applies in §15, I4.
  • MM4 — "The planner is a search over a lattice of join orders." Predicts why cost-based planning is dynamic programming, not greedy. Bug class without it: exponential blow-up without memoization. Applies in §18, ADR-09.
  • MM5 — "A B-tree page split is not one write, it's a chain." Predicts why WAL log records must be grouped. Bug class without it: a partially-split tree visible after a crash. Applies in §16.
  • MM6 — "Pregel is BSP: think in supersteps, not in threads." Predicts deterministic analytics results. Bug class without it: races from mutating shared state mid-superstep. Applies in §19.
  • MM7 — "Bolt's state machine is the contract, not the bytes." Predicts why drivers crash on an illegal transition. Bug class without it: a server that accepts an out-of-order RUN. Applies in §20, I10.
  • MM8 — "Index-free adjacency trades storage locality for pointer-chase locality." Predicts why cache-unfriendly random access dominates at scale. Bug class without it: assuming sequential-scan performance for a traversal workload. Applies in §4, §30.

33. Back-of-Envelope Capacity Model

All numbers are derived from the §4 System Constraints table and the Reference Deployment Graph (1×10⁹ nodes, 5×10⁹ relationships).

  • C1 — Node store size = 1×10⁹ nodes × 40 B/node (§8.2) = 40 GB.
  • C2 — Relationship store size = 5×10⁹ rels × 88 B/rel (§8.2) = 440 GB.
  • C3 — Property store floor = 1×10⁹ nodes × 2 props/node (§4) × 64 B/prop (§8.2) = 128 GB, before dynamic-block overflow — total durable-store floor ≈ 608 GB (C1+C2+C3).
  • C4 — Page-cache pages for the M7 95%-hit-rate target = hot-set fraction (5%, assumed) × (C1+C2) ÷ 8 KiB/page = 0.05 × 480 GB ÷ 8,192 B ≈ 3.07 × 10⁶ pages ≈ 24 GB — this exceeds the 16 GiB default page-cache ceiling (§4), exposing a real operational tension the Capacity Model surfaces explicitly (resolved in §25: raise the ceiling or tune the hot-set fraction down).
  • C5 — WAL write bandwidth at an assumed 50,000 writes/s burst × 96 B/record (§14.2, header+small payload+CRC) = 4.8 MB/s, well under NVMe's ≥ 500 MB/s write floor (§4) — the WAL is not the bottleneck at this scale.
  • C6 — FD budget = 10,000 max sessions (§4) × ~6 FDs/session ≈ 60,000 FDs, against the 65,536 ulimit (§4) — a thin margin, an operational lever (raise the limit or cap sessions).
  • C7 — Transient GC memory = 1,024 max concurrent txns (§4) × ~10 versions/property before GC catches up × 1×10⁹ props × 64 B ≈ up to 640 GB transient in the worst case — the reason I6's continuous (not batched) GC exists.
  • C8 — Recovery redo time ≈ (dirty-page-table at last checkpoint, ~10% of an 8.8 GB 100M-edge slice ≈ 0.88 GB) ÷ 500 MB/s sequential NVMe ≈ 1.76 s, leaving comfortable margin under the 30 s M8 budget for the analysis and undo passes.
  • C9 — Betweenness cost (Brandes, O(V·E)) at Reference Deployment Graph scale = 1×10⁹ × 5×10⁹ ≈ 5 × 10¹⁸ operations — intractable, which is exactly why §19.7 scopes exact betweenness to ≤ 10,000-node subgraphs and defers sampling-based betweenness at scale (§36).
  • C10 — Bolt session memory = 10,000 sessions (§4) × ~64 KB/session buffer ≈ 640 MB, small against the 16 GiB page-cache budget.

35. Alternative Architectures (Roads Not Taken)

AA1 — LSM-backed adjacency (JanusGraph-over-wide-column style).

Show the original text diagram
Client -> Query Layer -> Graph API adapter -> Wide-column store (Cassandra/HBase)
                                              (adjacency = keyed row scan, not pointer chase)

Regime where it wins: write-amplification-tolerant, horizontally-distributed-from-day-one ingestion where traversal is secondary to raw write throughput. Real system: JanusGraph. Rejected here because it forfeits index-free adjacency (P1, ADR-03) — the property this entire engine exists to provide.

AA2 — GraphBLAS adjacency-matrix engine (RedisGraph style).

Show the original text diagram
Client -> Cypher-like parser -> Linear-algebra IR -> Sparse matrix ops (GraphBLAS)
                                                      (traversal = matrix-vector multiply)

Regime where it wins: analytics workloads dominated by matrix-shaped operations (PageRank, similarity) at large scale on GPU/TPU-class hardware. Real system: RedisGraph. Rejected here because point-traversal-and-MATCH OLTP semantics (P4, P6) map poorly onto matrix operations, and single-row transactional updates are not GraphBLAS's strength.

AA3 — Relational emulation (property graph over a relational store with recursive CTEs).

Show the original text diagram
Client -> SQL/graph-extension layer -> Recursive CTE planner -> Relational row store
                                                                 (adjacency = join)

Regime where it wins: a team with deep existing relational operational expertise and a graph workload that stays light and secondary. Real system: Apache AGE (a PostgreSQL extension). Rejected here because index-free adjacency (P1) is structurally impossible without native storage, and recursive-CTE depth costs explode past a few hops (§2's opening argument).

AA4 — Sharded/distributed MPP graph store (TigerGraph style).

Show the original text diagram
Client -> Query Layer -> Distributed planner -> Shard 1 | Shard 2 | ... | Shard N
                                                 (Pregel-on-shards, vertex-cut partitioning)

Regime where it wins: the graph provably exceeds single-node RAM/disk from day one. Real system: TigerGraph. Rejected for Phase 0 because the Capacity Model (§33) shows the Reference Deployment Graph fits (with tuning) on one node, and cross-shard traversal coordination cost is not worth paying before the single-node engine is proven — distributed partitioning remains a registered deferral (§36), not an abandoned idea.

37. Glossary

Index-free adjacency — a node stores a direct pointer to its first relationship; neighbours are found by pointer chase, not index probe (P1). Property graph — nodes and relationships each carrying an arbitrary set of typed key/value properties. Node record — the fixed-width on-disk representation of a node (§8.2). Relationship record — the fixed-width on-disk representation of a directed, typed relationship (§8.2). Property record — a chained, semi-variable-width record holding one property value (§8.2). Page cache — the fixed-capacity buffer pool mediating between pages and disk (§11.2). WAL — write-ahead log; every change is durable in the log before the page is dirtied (P5). LSN — log sequence number; a monotonic position in the WAL (§11.1). Checkpoint — a WAL marker recording the dirty-page and transaction tables to bound recovery time (§14.2). ARIES — the redo/undo/analysis recovery algorithm this engine implements (Mohan et al. 1992). Redo pass — replays committed-but-not-yet-flushed changes. Undo pass — rolls back uncommitted changes via compensation log records. Analysis pass — reconstructs the dirty-page and transaction tables from the last checkpoint. CLR (compensation log record) — a redo-only record produced during undo. MVCC — multi-version concurrency control; readers see a consistent snapshot without blocking writers. Snapshot isolation — the isolation level where reads see a fixed snapshot and writers conflict only on the same record (P4). Version chain — the linked list of a property's historical values (§8.2). xmin/xmax — the creating/deleting transaction ids stamped on every record. Active set — the set of transactions running when a snapshot was taken (I4). Write skew — an SI anomaly where two transactions' disjoint writes are individually consistent but jointly inconsistent; permitted under SI (I5). Lost update — two transactions overwriting the same record; rejected under SI (I5). Serializable Snapshot Isolation (SSI) — a stronger isolation level closing SI's anomalies (Cahill et al. 2008, deferred). Label index — a B-tree mapping label to node ids with a maintained count (§16.2). Cardinality estimation — predicting how many rows an operator will produce (P8). openCypher — the declarative graph query language this engine implements a subset of. AST — abstract syntax tree, the parser's output (§11.4). Logical plan — a storage-agnostic tree of relational-algebra-like operators (§11.5). Physical plan — the logical plan lowered to concrete, storage-aware operators (§11.5). Volcano iterator model — the pull-based init/next/close execution contract (§11.6). Predicate push-down — moving a filter as early as possible in the plan. Cost model — the formulas estimating an operator's execution cost (§18.2). Join order — the sequence in which pattern parts are combined; searched by the cost-based planner. Bolt protocol — the binary wire protocol this engine's primary driver interface implements (§8.3). PackStream — Bolt's serialization format. Session state machine — the finite-state contract governing a Bolt connection's lifecycle (I10). Pregel — the vertex-centric, bulk-synchronous-parallel analytics programming model (Malewicz et al. 2010). Superstep — one round of a Pregel computation. Combiner — a function reducing multiple messages to one vertex before delivery. PageRank — an iterative centrality algorithm modelling a random surfer; requires dangling-node redistribution (§19.6). Betweenness centrality — the fraction of shortest paths passing through a node (Brandes 2001). LDBC SNB — the Social Network Benchmark used as this engine's macro conformance/performance workload. TCK — technology compatibility kit; the openCypher conformance test suite. Checksum — the xxhash3-64 value verifying a page's integrity on read (I2). Group commit — batching multiple transactions' fsync calls to amortize durability cost (§14.2). Read replica — a read-only copy of the primary streaming and replaying its WAL (Phase-1+). RTO — recovery time objective; the bound on crash-recovery duration (§4, M8).
