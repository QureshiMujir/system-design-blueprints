Project Number: 123

Project Name: Recommendation Engine

1. Goal & Scope

A collaborative-filtering recommendation engine that predicts user-item affinity from a sparse interaction matrix and serves ranked top-N recommendations under a quantified latency budget. The system combines neighborhood methods, matrix factorization (closed-form ALS and gradient-based SGD/BPR), a two-stage candidate-generation-then-ranking serving path backed by an approximate nearest-neighbor (ANN) index, cold-start bridging via content features, popularity-bias mitigation, and closed-loop online evaluation (A/B testing) — treated as first-class deliverables, not afterthoughts bolted onto a trained matrix.

Phase-0 deliverable (numbered modules):

  1. recengine.data — event ingestion, chronological train/test split, sparse CSR matrix builder.
  2. recengine.baseline — global-mean and popularity-rank baseline recommenders.
  3. recengine.eval — offline evaluation harness: RMSE, precision@k, recall@k, NDCG@k, MAP@k.
  4. recengine.cli — command-line driver (recengine train, recengine eval) wiring 1-3 together.

System boundaries:

  • Provides: offline training for neighborhood CF, explicit ALS, implicit ALS, and SGD/BPR; an evaluation harness with correct temporal splits; a two-stage serving path (candidate generation → ranking → rerank) with an ANN index; cold-start fallback via content features; popularity-bias-aware reranking; an online A/B framework with rollback.
  • Delegates: the ANN algorithm itself (HNSW/IVF construction and query) is consumed as a library (hnswlib/faiss), never reimplemented (ADR-02); the stream-processing join engine is operated infrastructure, not built here; content-embedding encoders (text/image) are pretrained, fixed feature extractors, not trained in this repository.
  • Does NOT provide: a general ML platform, a feature-store product, a UI/dashboard product, training of the embedding encoders, distributed multi-node training (PhaseDeferred("§15")), or session/sequential modeling as the primary architecture (PhaseDeferred("§8")).

Non-goals: session-based/sequential recommendation as the primary model (PhaseDeferred("§8")); multi-node distributed ALS (PhaseDeferred("§15")); a generalized feature-store product (PhaseDeferred("§21")); a fully sharded embedding-table deep ranker (PhaseDeferred("§19")); sub-hour online-learning factor updates beyond nightly batch (PhaseDeferred("§21")); DPP-based reranking as the default (PhaseDeferred("§20")).

Deployment model: an offline batch-training job (nightly, orchestrated) producing a versioned ModelArtifact tarball; a stateless online serving fleet (gRPC) that loads the artifact and serves at the p99 budget in §4; a streaming join path for impression-click logging that feeds both the nightly retrain and the A/B evaluation harness (§21).

Target users/operators: ML engineers building the training pipelines; SRE/on-call engineers operating serving, rollback, and incident response; product managers configuring multi-objective weights and cold-start policy; data scientists running offline ablations against §17's harness.

What later phases unlock: Phase 1 (§13) unlocks fast fallback CF with no trained factor model; Phases 2-4 (§14-§16) unlock the factorization core; Phase 5 (§17) unlocks rigorous ranking evaluation; Phase 6 (§18) unlocks cold start; Phase 7 (§19) unlocks sub-millisecond candidate retrieval at catalog scale; Phase 8 (§20) unlocks bias-corrected multi-source ranking; Phase 9 (§21) unlocks safe online deployment with A/B testing and rollback.

Recommended language: Python 3.11, for orchestration, training drivers, and the evaluation harness. Every reference implementation in §5 (Surprise, LightFM, implicit, TensorFlow Recommenders) is Python-first, minimizing the translation gap between paper and code, and the NumPy/SciPy-sparse/pandas stack is the fastest iteration loop for the ALS/BPR math this blueprint specifies. The two places where wall-clock matters most — the ALS Gram-matrix solve (Phase 3, §15) and the online ranker's hot path (Phase 9, §21) — are specified with quantified performance targets (§4, §28) met via NumPy/BLAS vectorization and a Numba/Cython-compiled inner loop, not a second language, keeping the whole system in one runtime for a single-team, learning-focused build. Rejected: Scala/JVM (Spark MLlib's native language, ADR-05) — rejected because single-node performance at the target scale (§4: ≤50M interactions) does not need distributed shuffle, and JVM garbage-collection pauses are a tail-latency risk in the serving path (ADR-06); C++ — rejected because its recompile-cycle iteration cost outweighs the throughput gain at this data scale, though it is the right call past the scaling ceiling in §29; Go — rejected because its numerical/array ecosystem is immature relative to NumPy/SciPy for the factorization core.

Prerequisites: linear algebra (eigendecomposition, positive-definite matrices, Cholesky factorization), basic probability (Bayesian posteriors for cold-start bandits), big-O reasoning over sparse matrix operations, gradient descent and convex/biconvex optimization, HTTP/gRPC service basics.

Estimated timeline: Phase 0 — 1 week. Full system (Phases 0-9) — 10-12 weeks full-time, or 5-6 months for a 2-3 engineer team working part-time.

2. Why Build This

Recommendation engines sit at the intersection of applied linear algebra, information retrieval, and closed-loop ML systems. Building one from the interaction matrix up teaches four things a library call cannot: (a) why sparse linear algebra and Cholesky factorization matter operationally, not just as textbook math — the per-user ALS solve in Phase 3 is where 90%+ of training wall-clock lives, and understanding why explains every subsequent performance decision; (b) the difference between an offline metric and a causal online effect — the counterfactual gap (§17, §21) trips up every team shipping a recommender for the first time; (c) how two-stage retrieval architectures (candidate generation → ranking, §19-§20) generalize far beyond recsys — the identical pattern underlies search engines, ad auctions, and retrieval-augmented generation; (d) how feedback loops in ML systems manufacture their own training data and can silently collapse catalog diversity over months, a failure mode invisible to any single-day metric (§20, Threat Model T7).

Historically this traces to the Netflix Prize (2006-2009), which proved a single well-regularized matrix factorization beats hand-tuned heuristic similarity for the core recommendation problem (Koren-Bell-Volinsky 2009), and to the two-tower YouTube architecture (Covington et al. 2016) that set the template nearly every large-scale production recommender still follows.

The engineering muscles this builds: reading and re-deriving a closed-form linear-algebra update from a paper instead of copy-pasting a library call; designing an evaluation harness that resists its own biases (leakage, position bias, popularity confound); building a serving path with a hard latency budget and a two-stage architecture; and operating a system whose correctness partly depends on the distribution of its own past outputs (the feedback loop problem), which is a different discipline from testing a stateless function.

Cross-links to sibling curriculum systems: the ANN index (§19) is the identical technology as a standalone vector-search engine; the streaming join in the online-learning discussion (§21) is the same pattern as a change-data-capture pipeline; the A/B harness (§21) is the same infrastructure as a general experimentation platform; the Thompson-sampling exploration logic (§20) is the identical mathematics used in ad-serving pacing systems.

Calibration value: after building this, an engineer can look at any production recommender — a shopping "you may also like" rail, a video feed, a music "discover weekly" — and correctly infer its likely candidate-generation sources, its probable training objective, and its most likely failure mode, because the architecture space covered here is essentially all of it.

What Mastery Looks Like

  • Derive the implicit-ALS closed-form update from the confidence-weighted loss and explain why it parallelizes trivially across users (Phase 3, §15).
  • Explain, with the governing formula, why a random train/test split leaks future information in a temporal recommender and a chronological split does not (Phase 0, §12; Phase 5, §17).
  • Choose correctly between user-based CF, item-based CF, and matrix factorization for a given sparsity/catalog-size regime (Phase 1, §13; Comparative Architecture, §31).
  • Design a cold-start bridge that transitions a zero-history user to the personalized model without a hard cutover (Phase 6, §18).
  • Explain why click-through-rate-only optimization manufactures a feedback loop that narrows the catalog, and name at least two structural fixes (Phase 8, §20).
  • Compute, from first principles, the RAM and latency budget implied by a given catalog size and QPS target (Back-of-Envelope Capacity Model, §32).
  • Design an A/B rollback plan that recovers a bad model deploy in under ten minutes (Phase 9, §21).
  • Explain the offline/online evaluation gap and when inverse propensity scoring is required to trust an offline number (Phase 5, §17).

Event log & feature pipeline. Raw interaction events (view/click/play/purchase) are joined with the item catalog, deduplicated, and split chronologically (I2) into train/eval windows; no random shuffling touches this boundary (P2).

CSR interaction matrix. The canonical in-memory representation (§8.1) for every trainer in Phases 1-4; built once per offline rebuild, with an item-major transpose for the ALS item-update sweep (§8.1).

Neighborhood CF (Phase 1). A precomputed item-item or user-user similarity table; the fastest path to a working recommender and the fallback candidate source at serving time (P1, ADR-01).

Explicit / implicit ALS, SGD/BPR (Phases 2-4). Three factorization variants sharing the LatentFactors type (§11.4); explicit ALS minimizes RMSE on rated items, implicit ALS minimizes confidence-weighted squared error on binary preference, BPR minimizes a pairwise ranking loss.

Cold-start bridge (Phase 6). Projects content embeddings into the factor space for users/items with insufficient interaction history, and hands off to the personalized factor once a confidence threshold is crossed (P5).

ANN index (Phase 7). An HNSW index over the item factor matrix, consumed as a library (ADR-02), giving sub-millisecond approximate top-K retrieval at the recall floor in I8.

Ranker + rerank (Phase 8). Scores the unioned candidate set with a learned ranker, then corrects for popularity bias and applies a diversity constraint before the top-N response.

A/B evaluation loop (Phase 9). Every request logs an impression with trace_id and model_version; clicks join back to impressions; the aggregated online metric is the deploy gate (P10), and any regression triggers a documented rollback path (§21, §23).

All later sections stay consistent with this diagram: box names here match the module names in §10, the type names in §11, and the phase titles in §12-§21.

6. Design Principles

P1. Two-stage retrieval-then-rank is the default. A single model scoring every (user, item) pair on every request does not scale past a few hundred thousand items within a single-digit- millisecond p99. The two-stage split — a cheap candidate generator returning a few hundred items (§19), then an expensive ranker scoring them with the full feature vector (§20) — is the only architecture demonstrated to serve catalog scale within budget. Violating it (scoring the whole catalog per request) blows the latency budget in §4 by two orders of magnitude.

P2. Chronological split, never random. Random train/test splits leak future information: a click at t10 can land in train while a click at t5 lands in test, so the model "knows" the future when predicting the past. The only acceptable split is chronological (train before T, eval after T), enforced by I2. Violating it inflates offline NDCG by 5-10 points with no real-world meaning (§17.6, Pitfall).

P3. Implicit and explicit are different loss functions, not different data. A 3.5-star rating and a 40-second video play are both "signal," but explicit feedback wants squared error against a value, implicit feedback wants confidence-weighted preference against a binary label. Conflating them (treating play-count as a star rating) produces a miscalibrated confidence scale. Both paths are specified (§14, §15) and neither is deleted in favor of the other.

P4. Multi-metric evaluation, never a single number. RMSE measures rating-prediction accuracy; precision/recall/NDCG/MAP@k measure ranking quality; they can disagree (a model can lower RMSE while lowering NDCG@10). Every phase's evaluation report (§17) emits all of them; shipping on RMSE alone is a P4 violation and typically ships a worse top-N list.

P5. Cold start is a product decision before it is a model decision. What to show a new user is a business tradeoff (onboarding completion vs. first-week retention vs. conversion); the model side (content fallback, bandit transition, §18) implements the policy, but the policy's weights are config, owned by product. Do not let the cold-start algorithm become the cold-start policy.

P6. Popularity-bias correction is mandatory, not optional. Left uncorrected, negative sampling and click-trained rankers converge toward the head of the catalog (§20, Threat T7). The system carries a popularity-corrected negative sampler (§16), a diversity-aware reranker (§20), and an exploration term (§20) as load-bearing components, not later polish.

P7. Every candidate carries provenance. The Candidate type (§11.7) always records which retriever produced it. When offline and online metrics diverge, the first diagnostic question is "which source's candidates are winning?" — answerable only if provenance is captured from the start (I9 requires dedup preserves the winning source).

P8. ANN recall-vs-latency is a measured tradeoff, never assumed. ef_search (or equivalent) is tuned against the recall floor in I8 and re-verified on every index rebuild via the consistency harness (§19.5); it is never hand-set once and forgotten.

P9. Regularization matches sparsity, not a textbook default. ALS's lambda and BPR's L2 term are chosen against the measured density of the training matrix (§4: ≈0.25% on ml-25m); a value copied from a paper tuned on a denser dataset under-regularizes and overfits the long tail.

P10. Online A/B outranks offline metrics when they disagree. The offline metric (§17) is a proxy filtering which experiments reach A/B; the online metric (§21) is the deploy gate. A model that wins offline and loses online does not ship (P10 is why §21 exists as a phase, not a footnote).

P11. Model artifacts are versioned and rollback-capable in minutes. Every ModelArtifact (§11.11) carries a TrainMeta provenance block; the serving fleet switches active_model_version via a single config flip with a documented one-minute propagation (§21, RTO in §4).

P12. Every recommendation is explainable. For every served item, the system records the candidate source, the ranker score, and a trace_id (§11.7, §21) linking back to the impression log — required for the counterfactual evaluation in §17 and for incident response in §23.

8. Domain Model

8.1 The interaction matrix

The canonical representation is a sparse user-item matrix R of shape (n_users, n_items), stored as Compressed Sparse Row (CSR) for user-major access and as its transpose (CSC-equivalent) for item-major access — both are needed because the ALS user-sweep needs "all items for user u" and the item-sweep needs "all users for item i" (§15.2). Density on ml-25m is 25,000,095 / (162,541 × 62,423) ≈ 0.246%; every algorithm in this blueprint is chosen to scale with the 25M nonzeros (nnz), never the ~10.1B dense cells.

CSR layout:
  indptr  : int64[n_users + 1]     row-start offsets into indices/data
  indices : int32[nnz]             column index (ItemId) of each nonzero
  data    : float32[nnz]           raw interaction weight r_ui (not yet confidence-transformed)
row(u)  = indices[indptr[u] : indptr[u+1]], data[indptr[u] : indptr[u+1]]     # O(deg(u))
nnz     = indptr[n_users]
density = nnz / (n_users * n_items)

8.2 Explicit vs. implicit feedback and the confidence transform

Explicit feedback is a rating r_ui ∈ [r_min, r_max] (e.g., 0.5-5.0 stars); the model target is the rating value itself, and the loss is squared error (§14). Implicit feedback is a count or duration (clicks, plays, dwell_seconds) with no negative signal — absence of interaction means "unobserved," not "disliked." Hu-Koren-Volinsky (2008) resolve this by defining a binary preference p_ui = 1[r_ui > 0] and a confidence c_ui = 1 + alpha * r_ui, where alpha (default 40, tuned per §15.6) controls how strongly an observed interaction outweighs an unobserved one. Every (u, i) pair is used in training — including unobserved pairs at c_ui = 1, p_ui = 0 — which is the entire reason the closed-form solve in §15.2 exists: naive dense evaluation is O(n_users * n_items * rank), intractable at any real catalog size.

On MovieLens-25M, which is explicit-rating data, Phase 3 (§15) manufactures an implicit signal via r_ui = max(0, rating - 3.5) so ratings ≤ 3.5 become zero (no observed preference) — a documented, deliberate choice enabling direct comparison against the implicit reference library (§5) on the same dataset.

8.3 Neighborhood collaborative filtering

User-based CF predicts r_hat(u, i) = mean(r_u) + [sum_{v in N(u)} sim(u,v) * (r_vi - mean(r_v))] / sum_{v in N(u)} |sim(u,v)|, where N(u) is the k-nearest users by similarity who rated item i. Item-based CF (Sarwar et al. 2001) is the transpose: r_hat(u, i) = [sum_{j in N(i)} sim(i,j) * r_uj] / sum_{j in N(i)} |sim(i,j)|, using item-item similarity precomputed offline (cheaper at serve time since the item set is far more stable than the user set). Similarity metrics: cosine sim(a,b) = (a·b) / (||a|| ||b||) on the raw or mean-centered vectors; Pearson correlation (cosine on mean-centered vectors, penalizes rating-scale bias between users); adjusted cosine (centers each rating by its user's mean before computing item-item cosine — Sarwar et al.'s correction for the fact that item-item cosine ignores that different users rate on different scales); Jaccard (|N(a) ∩ N(b)| / |N(a) ∪ N(b)|, ignores rating magnitude entirely, useful for implicit/binary data). Full derivation and complexity table in §13.2.

8.4 Matrix factorization: ALS closed-form

Both explicit and implicit MF approximate R ≈ U V^T where U is (n_users, rank) and V is (n_items, rank). The implicit-ALS loss (Hu-Koren-Volinsky):

L(U,V) = sum_{u,i} c_ui * (p_ui - u_u . v_i)^2  +  lambda * (sum_u ||u_u||^2 + sum_i ||v_i||^2)

Fixing V and setting dL/du_u = 0 yields the per-user closed form (P9, I5 require lambda > 0 for the matrix below to be positive-definite):

u_u = (V^T C^u V + lambda*I)^-1  V^T C^u p(u)

Expanding V^T C^u V = V^T V + V^T (C^u - I) V, and noting (C^u - I) is zero except at u's observed items, the right side reduces to a computation over only nnz(u) items:

A = V^T V                                   # precomputed once per sweep, O(n_items * rank^2)
A += sum_{i in nnz(u)} (c_ui - 1) * v_i v_i^T   # rank-1 update per observed item, O(nnz(u)*rank^2)
A += lambda * I
b = sum_{i in nnz(u)} c_ui * v_i
u_u = cholesky_solve(A, b)                  # A is PD when lambda > 0 (I5)

Cost per iteration: O(nnz * rank^2 + (n_users + n_items) * rank^3) versus the naive O(n_users * n_items * rank) — for ml-25m at rank 64 this is the difference between seconds and hours. Explicit-ALS (§14) adds learned bias terms b_u, b_i and a global_mean, with target r_ui (not p_ui) and no confidence weighting (c_ui = 1 uniformly); the same Cholesky machinery applies with p_ui replaced by the residual r_ui - global_mean - b_u - b_i.

8.5 SGD and BPR

BPR (Rendle et al. 2009) reframes training as pairwise ranking: for an observed pair (u,i) and a sampled unobserved j, the loss is -log(sigmoid(u_u.v_i - u_u.v_j)) + lambda*(||u_u||^2 + ||v_i||^2 + ||v_j||^2). Gradients are closed-form and applied via SGD, one triple at a time, detailed in §16.2. Unlike ALS, BPR has no closed-form per-user solve; it is O(1) per triple, and convergence depends on learning-rate schedule and negative-sampling strategy (uniform vs. popularity-corrected, §16.2).

8.6 Candidate generation and ranking (two-stage)

A Candidate (§11.7) is an (item, score, source) triple; the candidate generator (§19) unions outputs from the ANN-backed factor retriever, a popularity retriever, a content-based retriever, and (post-Phase-6) the cold-start retriever, deduplicating by item_id (I9). The ranker (§20) scores the union with a richer feature vector (RankFeatures, §11.8) than any single retriever used, because the ranker's cost is paid once per candidate while the retriever's cost is paid once per catalog scan.

8.7 Cold start

New users: bootstrap a synthetic factor from onboarding signal (declared interests, demographic prior) by averaging matching items' factors; blend with the personalized factor by Bayesian shrinkage weighted by inverse interaction count until a confidence threshold (~10 interactions, tuned per §18.4) is crossed. New items: project a content embedding into factor space via a learned linear map V_content ≈ V_als @ W, trained on items with both signals (§18.2).

8.8 Worked example (tiny matrix)

Three users, four items, explicit ratings 1-5 (0 = unobserved):

        i0  i1  i2  i3
  u0  [  5,  0,  3,  0 ]
  u1  [  4,  0,  0,  2 ]
  u2  [  0,  5,  4,  0 ]

CSR for this matrix: indptr = [0,2,4,6], indices = [0,2, 0,3, 1,2], data = [5,3, 4,2, 5,4], nnz = 6, density = 6/12 = 0.5. Implicit transform with threshold 3.5: p_ui = 1[r_ui > 3.5] → (u0,i0)=1, (u1,i0)=1, (u2,i1)=1, (u2,i2)=1, all else 0; confidence c_ui = 1 + 40*r_ui for the observed entries, c_ui = 1 elsewhere. Item-item cosine similarity between i0 and i2 uses only users who rated both — here, only u0 (rated 5 and 3) — giving sim(i0,i2) = 1.0 from a single overlapping user, illustrating why item-item similarity needs a minimum-overlap floor (§13.6 Pitfall) to avoid spurious high-confidence similarities from sparse overlap.

8.9 Malformed-input example

A CSR built from a raw event stream containing a duplicate (user_id=7, item_id=3, ts=t1) record appearing twice (a common upstream at-least-once delivery artifact) produces indices containing 3 twice within the same row-slice for user 7. InteractionMatrix.__post_init__ (§11.3) does not by itself reject this (CSR permits repeated column indices per row), so I3's shape check passes while the data is wrong — the fix is a dedup pass in the loader keyed on (user_id, item_id, trace_id) before matrix construction (§12.2), not a matrix-level invariant; documented in §12.6 Pitfalls.

8.10 Failure-path example

If the ALS Cholesky solve receives a Gram matrix A that is not positive-definite (possible under float32 underflow when lambda is set below ~1e-6, violating the spirit though not the letter of I5), the solve raises rather than silently returning garbage; the trainer's recovery path (§15.9) retries once with lambda scaled ×10, and if that still fails, aborts the training run and emits als.non_pd_abort_total, per I5's Recovery column.

12.6 Pitfalls

Loading ratings.csv with pandas.read_csv default dtypes silently upcasts item_id to int64 even when int32 would fit, doubling CSR memory — pin dtypes explicitly. A duplicate event (§8.9) does not violate I3 (CSR tolerates repeated column indices per row) so it passes matrix construction silently; only the loader-level dedup catches it — do not rely on the matrix invariant to catch data-quality bugs. Sorting by ts with a stable sort matters when many events share a timestamp (batch-imported historical data) — an unstable sort can nondeterministically reorder same-timestamp events across the split boundary, violating P2/I2 in a way that is flaky in CI, not deterministic.

12.7 Performance Concerns

The transpose (CSC-equivalent) build is a counting sort, O(nnz), but a naive implementation that appends to Python lists rather than pre-allocating numpy arrays is 20-50x slower — allocate indices/data arrays sized to nnz up front. The chronological sort of 25M rows is the single largest one-time cost (~8s with numpy.argsort on ts.view(int64)); sorting on the datetime64 column directly rather than its int64 view is measurably slower due to per-element Python object overhead in older pandas versions.

12.8 Edge Cases

A user with exactly one interaction: included in train, excluded from the eval set (§12.2's three-interaction floor, formalized in Phase 5's evaluation protocol, §17.2). An item that never appears in train: n_items is still sized to include it (from the catalog, not just observed interactions) so a later cold-start retriever (Phase 6) can address it. Empty CSR row (a user present in the id-map but with zero interactions after filtering): row(u) returns two empty arrays, not an error — callers must handle the zero-length case explicitly (documented in §11.3).

12.9 Failure Analysis

If the split-boundary assertion (I2) fails in CI, the blast radius is total — every downstream phase's offline metric is untrustworthy until fixed, because leakage inflates every ranking metric uniformly and masks real regressions. Detection is automatic (CI gate blocks merge); containment is "no phase 1+ work proceeds on a red Phase-0 gate"; recovery is fixing the loader's sort/split logic and re-running the full invariant suite, not patching around the specific failing row.

12.10 Operational Notes

Emit ingest.rows_loaded_total, ingest.rows_deduped_total, split.train_rows / split.eval_rows as counters on every pipeline run, logged to docs/runbooks/phase0_run_log.md by the CI job. No production deployment in Phase 0 — this phase is offline-tooling only; rollback concerns begin at Phase 9 (§21).

13. Phase 1 — Neighborhood Collaborative Filtering

13.1 Objectives

Implement user-based and item-based CF (§8.3, Sarwar et al. 2001) as the first working recommender and the permanent fast-fallback candidate source (P1, ADR-01's rejected-alternative regime). Establish the similarity-metric library reused by later reranking (§20's cosine diversity term is the same code path).

13.2 Detailed Implementation Steps

Implement recengine/neighborhood/similarity.py: cosine, Pearson (mean-centered cosine), adjusted cosine (Sarwar's per-user-mean-centered item-item variant), and Jaccard (§8.3 formulas), each operating on InteractionMatrix rows/columns (§11.3) without densifying. Implement recengine/neighborhood/knn.py: item-based CF precomputes a top-K similarity table per item offline (P1 — item set is stable, precomputation amortizes); user-based CF computes similarity at request time over a candidate neighbor pool (bounded to the top-1000-most-active users to keep serve-time cost bounded, an explicit P9-adjacent tradeoff documented here). Both feed the Candidate type (§11.7) with source=neighborhood.

13.3 Deliverable

A trained item-item similarity table (artifacts/phase1/item_sim.npz) and a user-based CF path, both exposed through recengine.cli recommend --model itemcf --user <id>, producing a top-10 list with per-item similarity scores.

13.4 Acceptance Criteria

Item-based CF achieves Recall@50 ≥ 0.30 on the ml-25m chronological holdout (fixture conformance/ml25m_itemcf_baseline.json), beating the Phase 0 popularity baseline by at least 5 points of Recall@50; similarity-table build completes in ≤ 90 seconds for the full ml-25m catalog (62,423 items) at K=100 neighbors per item.

13.5 Conformance Fixtures

conformance/itemcf_tiny_matrix.json — the §8.8 worked-example 3-user/4-item matrix, with expected sim(i0,i2) = 1.0 documented as a known low-overlap artifact (§13.6); conformance/ user_cf_neighbor_pool.parquet — a fixture verifying the 1000-user neighbor-pool cap is applied deterministically (same input → same neighbor set).

13.6 Pitfalls

Item-item cosine on a low-overlap item pair (as in §8.8, where i0 and i2 share exactly one rater) produces a spuriously confident sim = 1.0 — the fix is a minimum-co-rating floor (default 5 co-raters) below which similarity is set to zero regardless of the raw cosine value; omitting this floor is the single most common item-CF bug reported in production postmortems. Pearson correlation on a user pair with fewer than 2 co-rated items is undefined (division by a zero-length variance) — guard explicitly, do not let NaN propagate silently into the ranking.

13.7 Performance Concerns

Naive item-item similarity is O(n_items^2 * avg_users_per_item) — intractable at 62K items. The standard mitigation (used here) is to compute similarity only for item pairs that share at least one co-rating, via an inverted index (user -> items), reducing the effective pair count by orders of magnitude on sparse data; this is the same sparsity-first principle as P9 and the CSR choice in §8.1.

13.8 Edge Cases

An item with only one ever-rating: excluded from the similarity table entirely (co-rating floor, §13.6, makes every similarity to it zero) — falls through to the popularity/content candidate sources instead (§19). A user with a neighbor pool entirely disjoint from their rated items' co-raters (extremely sparse activity): user-based CF returns an empty candidate list, and the candidate-gen union (§19.2) is responsible for backfilling from other sources.

13.9 Failure Analysis

A corrupted similarity table (e.g., a partial write from a killed offline job) produces a KeyError at lookup rather than a silent wrong answer, because the table is loaded as a single atomic artifact with a content hash (mirroring I12's pattern) — detection is immediate at load time, recovery is falling back to the previous similarity-table version, same mechanism as model rollback (P11).

13.10 Operational Notes

Emit itemcf.similarity_table_build_seconds, itemcf.min_corating_floor_applied_total. The similarity table is versioned alongside the model artifact so a rollback (§21) reverts both consistently.

14. Phase 2 — Explicit Matrix Factorization (Biased ALS)

14.1 Objectives

Implement explicit-feedback ALS with bias terms (Koren-Bell-Volinsky 2009): learn U, V, bu, bi, and global_mean minimizing regularized RMSE on observed ratings. This is the first true latent-factor model and the baseline that Phase 3's implicit variant is compared against on the same dataset.

14.2 Detailed Implementation Steps

Implement recengine/train/als_explicit.py. The per-user closed form (derived in §8.4, adapted for bias terms per P9/I5) solves u_u = (V^T V + lambda*I)^-1 V^T (r_u - global_mean - bu[u] - bi) where r_u is user u's observed rating vector restricted to rated items; biases are updated in an alternating sub-step: bu[u] = mean(r_ui - global_mean - bi[i] - u_u.v_i) over u's ratings, symmetric for bi. Regularization lambda (I5, ADR default 0.05 for the explicit path — higher than implicit's 0.01 because the rating scale has less redundant signal per cell) is validated > 0 at AlsConfig construction. Reuse the InteractionMatrix/CSR machinery from §12 unchanged (P9 — one sparse-matrix representation for every trainer).

14.3 Deliverable

A ModelArtifact (§11.10) with LatentFactors.bu/bi populated, trainable via recengine.cli train --model als_explicit --rank 64 --reg 0.05 --iters 15, and an EvalReport with a populated rmse field (the first phase where RMSE is meaningful — Phase 0/1 have no rating-value prediction).

14.4 Acceptance Criteria

RMSE ≤ 0.85 on the ml-25m chronological holdout (5-point scale) — comparable to published Netflix-Prize-era baselines for a rank-64 biased-MF model; NDCG@10 ≥ 0.30 (lower than the Phase 3 implicit target of 0.35, expected because explicit MF is not optimized for ranking, documented as an intentional comparison point); training completes 15 iterations in ≤ 3 minutes on 8 cores (§4 System Constraints row "Full ALS train time").

14.5 Conformance Fixtures

conformance/ml25m_explicit_rmse_gate.json — golden RMSE/NDCG numbers from a pinned-seed reference run, used as the CI regression gate; conformance/bias_term_degenerate_user.parquet — a synthetic user with only one rating, verifying bu computation does not divide by zero.

14.6 Pitfalls

Forgetting to subtract global_mean before computing the closed-form solve causes the model to fit U V^T against the raw rating scale (centered around 3.5, not 0), which the regularization term then penalizes asymmetrically — always center first (P9, ADR-08's rationale). Alternating biases and factors in the wrong order (updating bu/bi using stale factors from two iterations ago) slows convergence measurably without producing an obviously wrong answer — the correct order is bias-then-factor within each half-sweep, both computed from the current iteration's other values.

14.7 Performance Concerns

The bias update is O(nnz) per sweep, negligible next to the O(nnz*rank^2) factor solve — do not over-optimize it at the expense of the factor solve's cache locality (row-major V access pattern, matching the CSR layout in §8.1). Computing global_mean once and caching it (rather than recomputing per iteration) saves a full pass over 25M rows per sweep with zero cost to correctness since it is a training-set constant.

14.8 Edge Cases

A user with a single rating: their bu is fully determined by that one rating relative to global_mean + bi[item], giving zero residual after the first update — mathematically correct but means their factor u_u is regularized to near-zero (little signal to overcome lambda), correctly reflecting genuine uncertainty about that user's preferences (ties into cold-start motivation for Phase 6, §18). A rating exactly at the scale boundary (5.0 or 0.5): no special handling required, but the RMSE evaluator must not clip predictions to [0.5, 5.0] before scoring unless documented, since clipping changes the RMSE gate's meaning.

14.9 Failure Analysis

Divergent training (RMSE increasing after several iterations) most often traces to lambda set too low for the observed density (P9) — detection via the per-iteration objective log matching I5's monitoring pattern; recovery is aborting the run and re-launching with the documented default lambda=0.05, never silently continuing training hoping it self-corrects.

14.10 Operational Notes

Emit als_explicit.iter_rmse per iteration (training-set proxy, not the held-out gate) and als_explicit.train_wall_seconds. This phase produces an offline artifact only; it is not served directly (Phase 9, §21, serves whichever model is promoted, typically the Phase 8 ranker consuming Phase 3's implicit factors, not Phase 2's explicit ones — documented in ADR-08).

15. Phase 3 — Implicit-Feedback ALS

15.1 Objectives

Implement the confidence-weighted implicit-ALS solve (Hu-Koren-Volinsky 2008, §8.2/§8.4) as the system's primary candidate-generation model (ADR-01). This is the phase where 90%+ of training wall-clock lives system-wide, and where the sparsity-first design (P9, §8.1) pays off directly.

15.2 Detailed Implementation Steps

Implement recengine/train/als_implicit.py per the closed-form derivation in §8.4: precompute A0 = V^T V once per sweep (O(n_items*rank^2)), then for each user apply the rank-1 updates A = A0 + sum_{i in nnz(u)} (c_ui-1)*v_i v_i^T + lambda*I and b = sum_{i in nnz(u)} c_ui*v_i, solving u_u = cholesky_solve(A, b) (I5 guarantees A positive-definite since lambda > 0). This is P1's and ADR-01's central technique. Parallelize the per-user solves across nthreads (§11.5) since each user's solve is independent — the entire reason ALS scales the way it does (§8.4). Symmetric item-sweep swaps U/V roles and iterates the transposed CSR.

15.3 Deliverable

A ModelArtifact with implicit LatentFactors (no bias terms, per §8.4's note that confidence weighting absorbs popularity effects), trainable via recengine.cli train --model als_implicit --rank 64 --reg 0.01 --alpha 40 --iters 15, plus a full EvalReport including NDCG@10, Recall@50, MAP@10.

15.4 Acceptance Criteria

NDCG@10 ≥ 0.35 on the ml-25m chronological holdout (fixture conformance/ml25m_als_implicit_ ndcg_gate.json), matching the implicit reference library's ~0.36 within statistical noise (§5 Reference Implementations); full 15-iteration training completes in ≤ 3 minutes on an 8-core host (§4); Recall@50 ≥ 0.38.

15.5 Conformance Fixtures

conformance/ml25m_als_implicit_ndcg_gate.json — pinned-seed golden metrics, CI regression gate; conformance/confidence_histogram.json — expected c_ui distribution shape for the default alpha=40, used to detect an alpha misconfiguration (§15.6 Pitfall) before a full training run; conformance/non_pd_retry.json — a synthetic ill-conditioned matrix exercising the lambda-retry failure path (§15.9).

15.6 Pitfalls

An alpha tuned for one weight distribution (e.g., binary clicks in [0,1]) silently misbehaves on a different one (e.g., raw play-counts unbounded above): the confidence histogram (§15.5 fixture) should have most mass in the 5-10 range per I4's spirit — log it after every loader run and re-tune alpha per dataset, never assume the paper's default alpha=40 transfers. Initializing U/V with too-large Gaussian noise slows early-iteration convergence because the biconvex optimization (non-convex jointly, convex in each factor alone) is sensitive to the initial scale — the reference default is N(0, 0.01).

15.7 Performance Concerns

The per-user rank-1 update is O(rank^2) per observed item; at rank 64 and ~150 average items per user, that's ~614K flops/user/sweep — this dominates wall-clock and is the target of the "90%+ of training time" claim in §1/§15.1. Using a BLAS symmetric-rank-1-update routine (SYR) instead of a hand-written double loop, and exploiting matrix symmetry to halve the work, is the documented Phase-3.5 optimization follow-up (not required for the acceptance gate, but noted so it is not "discovered" later as a surprise).

15.8 Edge Cases

A user with zero observed items after the co-rating/dedup filtering (§12.6): their per-user solve degenerates to u_u = (A0 + lambda*I)^-1 * 0 = 0, the zero vector — correctly represents "no signal," and downstream candidate generation (§19) must not treat a zero factor as a valid personalized signal (falls to cold-start path, §18). Extremely high-degree users (a power user with 10,000+ ratings): the per-user solve cost scales linearly with nnz(u), so a small number of such users can dominate sweep tail latency — bucket and log the degree distribution (§15.10).

15.9 Failure Analysis

Cholesky failure (AlsError.NonPositiveDefinite) under float32 underflow when lambda is effectively too small relative to the confidence magnitudes: detection is the solver's own factorization check; recovery retries once with lambda scaled ×10 (documented in §8.10); a second failure aborts the training run and pages the on-call rotation via als.non_pd_abort_total, never silently falling back to a stale artifact without alerting.

15.10 Operational Notes

Emit als_implicit.iter_loss, als_implicit.user_sweep_seconds, als_implicit.item_sweep_ seconds, and als_implicit.user_degree_p99 (the power-user tail from §15.8). This artifact becomes the input to Phase 6's cold-start bridge and Phase 7's ANN index build — its train_meta.artifact_hash (I12) is what those phases pin against.

16. Phase 4 — SGD and Bayesian Personalized Ranking

16.1 Objectives

Implement BPR (Rendle et al. 2009, §8.5) as the pairwise-ranking alternative to ALS, to concretely test P10's claim that offline and modeling choices can trade off differently than expected — BPR directly optimizes ranking order rather than a pointwise reconstruction error.

16.2 Detailed Implementation Steps

Implement recengine/train/bpr.py. Training loop: sample user u, sample a positive item i from nnz(u), sample a negative j via popularity-corrected sampling (P(j) ∝ popularity(j)^0.75, ADR-11 — the word2vec-style correction that avoids ALS's implicit tendency to under-penalize popular false negatives, ties to P6); compute the closed-form gradient of -log(sigmoid(u_u.v_i - u_u.v_j)) + lambda*(||u_u||^2+||v_i||^2+||v_j||^2) (§8.5) and apply an SGD step with learning rate eta (default 1e-2, decayed). Track validation NDCG@10 every 100K steps; early-stop after three non-improving checks (P4 — an explicit non-accuracy stopping signal).

16.3 Deliverable

A LatentFactors artifact from the BPR path, interchangeable with §15's ALS output in every downstream consumer (candidate gen, §19) because both satisfy the same LatentFactors shape (§11.4); an ablation report comparing uniform vs. popularity-corrected negative sampling (ADR-11).

16.4 Acceptance Criteria

NDCG@10 within ±2 points of the Phase 3 implicit-ALS result on ml-25m (fixture conformance/ml25m_bpr_vs_als_ndcg.json) — documenting the expected near-tie on this dataset per §5's Required Reading note, rather than assuming BPR must win; training converges (validation NDCG plateau triggering early stop) within 10 epochs; popularity-corrected sampling must beat uniform sampling by ≥ 1 NDCG point on the tail-item Recall@50 segment (users whose ground-truth item is below the catalog's 80th popularity percentile).

16.5 Conformance Fixtures

conformance/ml25m_bpr_vs_als_ndcg.json — golden comparison numbers; conformance/negative_ sampling_ablation.json — uniform vs. popularity-corrected tail-Recall@50 comparison, the ADR-11 regression gate.

16.6 Pitfalls

Uniform negative sampling looks correct (loss decreases smoothly) while quietly underperforming on tail items because head items are oversampled as negatives relative to their true unpopularity — a smoothly decreasing loss curve is not sufficient evidence of a good sampler; always check the tail-segment metric, not just the aggregate (§16.4's explicit tail gate exists because of this). Sampling the negative j without excluding items already in nnz(u) (a "false negative") biases the gradient — always sample j from the complement of the user's observed set.

16.7 Performance Concerns

Each SGD step is O(rank) (three vector dot-products/updates), far cheaper per-step than ALS's per-user solve, but BPR needs millions of steps to converge versus ALS's ~15 full sweeps — overall wall-clock is comparable for ml-25m scale (§4), and this comparison is itself a documented data point in the phase's ablation report, not asserted a priori. Batching triples that share the same user u (common in a shuffle-free scan) lets the u_u gradient accumulate before a single write-back, reducing memory-write contention under parallel SGD.

16.8 Edge Cases

A user with only one observed item: every positive-sample draw for that user returns the same item, so the gradient signal for that user's factor is entirely about separating that one item from sampled negatives — correct but low-information, same underlying issue as §14.8's single-rating case. Numerical underflow in sigmoid(x) for very negative x (a badly initialized factor pair with a large negative dot-product gap): use the numerically stable log-sigmoid formulation, not a naive 1/(1+exp(-x)) that can divide by a subnormal float.

16.9 Failure Analysis

A training run whose validation NDCG never improves past the Phase 0 popularity baseline usually traces to a broken negative sampler (drawing negatives from the positive set) or a learning rate too high causing divergent updates — detection is the automated NDCG-vs-baseline comparison built into the training driver's post-run check; recovery is halting promotion of the artifact and filing docs/phase4_negative_result.md per P4's negative-results-must-be-written-down discipline.

16.10 Operational Notes

Emit bpr.step_loss (every 10K steps), bpr.validation_ndcg (every 100K steps), bpr.early_stop_epoch. BPR is retained as a documented alternative in the ADR table (ADR-09) but is not the default candidate-gen model (ADR-01); switching defaults requires a re-run of this phase's ablation with updated numbers, not a config flip alone.

17. Phase 5 — Ranking Evaluation Harness

17.1 Objectives

Build the full evaluation harness (P4: RMSE + precision/recall/NDCG/MAP@k, all with bootstrap confidence intervals) and the counterfactual/IPS machinery (P3, P8) that every later phase's acceptance gate depends on. This phase turns the metric stubs from §12 into the real, trusted measurement instrument for the rest of the system.

17.2 Detailed Implementation Steps

Implement recengine/eval/metrics.py fully: RMSE (sqrt(mean((r_hat-r)^2))) for the explicit path; precision@k = |relevant ∩ top_k| / k; recall@k = |relevant ∩ top_k| / |relevant|; NDCG@k = DCG@k / IDCG@k with DCG@k = sum_{j=1..k} (2^rel_j - 1)/log2(j+1); MAP@k = mean of per-user average precision at k. Enforce the three-training-interaction floor for eval-set users (§12.2, formalized here) and the top-K-excluding-train-history protocol. Implement recengine/ eval/ips.py: inverse propensity scoring reweighting weight = 1/propensity(position), clipped at 50 (P8, ADR-16). Implement recengine/eval/replay.py: off-policy counterfactual replay per Bottou et al.'s framework, dropping impressions where the compared model's top-K does not include the actual clicked item.

17.3 Deliverable

A fully populated EvalReport (§11.11) for every trained model in Phases 1-4, plus a comparison report (reports/phase5_model_comparison.html) showing RMSE, NDCG@10, Recall@50, MAP@10 side by side across popularity/itemCF/explicit-ALS/implicit-ALS/BPR (P4 — never a single-metric verdict).

17.4 Acceptance Criteria

NDCG@10 bootstrap CI width (hi95-lo95) ≤ 0.02 at 1000 resamples on the ml-25m eval set (fixture conformance/bootstrap_ci_width.json) — a CI too wide means the resample count or eval-set size is insufficient to trust any phase's acceptance gate; IPS-reweighted and unweighted NDCG@10 must be reported side-by-side for every online-eligible model, per P3, with the delta documented.

17.5 Conformance Fixtures

conformance/bootstrap_ci_width.json; conformance/ndcg_hand_computed.json — a 5-user toy example with NDCG@10 computed by hand, verifying the implementation against an independent calculation; conformance/ips_clip_boundary.parquet — propensities near zero, verifying the clip-at-50 behavior (§17.6).

17.6 Pitfalls

Computing NDCG over a top-K that includes items already in the user's train history inflates the metric because those items are trivially "relevant" in a memorization sense, not a generalization sense — always exclude train-history items from the candidate pool being ranked for eval (this is the "standard top-K-with-history-mask protocol" the harness enforces). Reporting only the uncorrected offline metric when propensities are known and available (skipping IPS, P3) produces an optimistic bias toward whatever policy generated the logged data.

17.7 Performance Concerns

Bootstrap resampling 1000 times over 150K+ eval users, each resample recomputing NDCG/Recall/MAP, is the harness's main cost — vectorize the per-user metric computation (batch matrix operations over the ranked lists) rather than a per-user Python loop, or the full report generation exceeds the CI time budget.

17.8 Edge Cases

A user whose entire test-set ground truth was excluded by the three-interaction floor: excluded from the eval report entirely, and the excluded-user count is logged (not silently dropped) so reviewers can sanity-check that the floor is not accidentally excluding a large fraction of users. A propensity of exactly zero (should be structurally impossible under a correctly randomized slice, but defensively handled): the IPS weight is defined as the clip ceiling (50), not inf.

17.9 Failure Analysis

A CI width blowing past the 0.02 gate on a previously-stable eval set signals either a bug in the resampling implementation or a genuine increase in metric variance (e.g., from a much smaller eval population after a filtering change) — detection is the automated gate; recovery is diffing the eval-set row count against the previous run before assuming a code bug.

17.10 Operational Notes

Emit eval.bootstrap_resamples_seconds, eval.excluded_user_count, eval.ips_clip_rate. Every phase from here forward (§18-§21) cites this harness's EvalReport as its acceptance-gate instrument; a change to the metric implementation itself requires re-running every prior phase's golden fixtures.

18. Phase 6 — Cold Start: Content & Hybrid Features

18.1 Objectives

Solve the two-sided cold-start problem (§8.7): a new user with no interaction history, and a new item with no engagement history. Implement the content-to-factor bridge and the Bayesian-shrinkage transition, per P5 (policy is product's, mechanism is ours).

18.2 Detailed Implementation Steps

Implement recengine/coldstart/content_bridge.py per ADR-17's locked content-fallback-plus-bandit strategy: given a frozen content embedding per item (pretrained text/image encoder, consumed not trained, per §1's delegation boundary), learn a linear projection W such that V_content ≈ V_als @ W via least-squares regression fit on items that have both an ALS factor (§15) and a content embedding — this is the mechanism, not a deep model, deliberately (P5: mechanism is ours, policy is product's; keeps the bridge auditable). New items get v_i = content_embedding_i @ W as a synthetic factor. Implement recengine/coldstart/bandit.py: per-item Beta-Bernoulli posterior (alpha_i, beta_i) for CTR, updated from the impression/click join (§21.4); at serve time this feeds the exploration term used in reranking (§20). For new users, bootstrap a synthetic u_u by averaging the factors of items matching onboarding signals (declared interests, country prior); blend with the personalized u_u from §15/§16 via shrinkage weight n/(n+k0) where n is observed-interaction count and k0 is a tuned prior-strength constant (default 10, per §18.4).

18.3 Deliverable

A cold-start-augmented candidate source (source=coldstart in Candidate, §11.7) integrated into the candidate-gen union (§19), plus a docs/phase6_bridge_quality.md report on the content-to- factor projection's reconstruction error on held-out warm items.

18.4 Acceptance Criteria

The content-to-factor projection's reconstruction error (||V_als - V_content@W||_F / ||V_als||_F) ≤ 0.35 on a held-out set of 1,000 warm items (fixture conformance/coldstart_ bridge_reconstruction.json); NDCG@10 for users with 1-5 interactions (the cold-start regime) improves by ≥ 3 points over the Phase 3 pure-ALS baseline restricted to the same user segment (fixture conformance/coldstart_segment_ndcg.json); the shrinkage transition threshold k0=10 is validated by a sweep showing NDCG for the 5-10-interaction segment is not statistically distinguishable from the fully-personalized segment beyond n=10.

18.5 Conformance Fixtures

conformance/coldstart_bridge_reconstruction.json; conformance/coldstart_segment_ndcg.json; conformance/new_item_zero_engagement.parquet — a synthetic new item with a content embedding but zero interactions, verifying it receives a nonzero synthetic factor and appears in candidate generation.

18.6 Pitfalls

Fitting the projection W on a training set of "warm items" that is itself a biased sample (items popular enough to have both signals are systematically different from the tail of genuinely new items) understates the bridge's real-world reconstruction error — document this selection bias explicitly in the phase report rather than presenting the reconstruction number as unqualified. Applying the Bayesian shrinkage using an interaction count that includes cold-start-bandit-driven exposure (rather than organic interactions only) can inflate apparent confidence prematurely — count only organic (non-bandit-boosted) interactions toward the shrinkage weight n.

18.7 Performance Concerns

The W projection fit is a one-time offline least-squares solve over ~50K warm items at the embedding dimensionality (typically 384-768 for a sentence-transformer) — a few seconds, negligible next to ALS training. The Beta-Bernoulli counter updates (Redis increments) are O(1) per event and must not become a bottleneck in the streaming join path (deferred online-learning consideration, §35).

18.8 Edge Cases

An item with a content embedding but that later accumulates enough organic engagement to have a well-estimated ALS factor of its own: the system must transition it off the synthetic content-bridge factor and onto its own learned factor at the next nightly rebuild — failing to do so means a well-known item is permanently served a stale synthetic approximation. A user whose onboarding signals match zero catalog items (an obscure declared interest with no tagged content): falls through to the pure popularity-by-context retriever, the documented last-resort (§8.7).

18.9 Failure Analysis

A degenerate projection W (e.g., fit on too few warm items, producing near-random synthetic factors) manifests as new items receiving essentially random candidate scores — detection is the §18.4 reconstruction-error gate on every retrain; recovery is widening the warm-item training set or falling back to a pure-popularity cold-start policy for new items until the bridge is re-validated.

18.10 Operational Notes

Emit coldstart.bridge_reconstruction_error, coldstart.bandit_transition_count (items crossing from cold to warm regime per day), coldstart.shrinkage_weight_p50. The cold-start policy (exact weighting, which onboarding signals to use) is a config value owned by product (P5); this phase ships the mechanism and sane defaults, not a fixed policy.

19. Phase 7 — Candidate Generation & ANN Index

19.1 Objectives

Replace brute-force top-K scoring with an HNSW-backed approximate nearest-neighbor index over the item factor matrix (P1, ADR-02), and build the multi-source candidate-generation orchestrator that unions ANN, popularity, content, and cold-start retrievers (§8.6).

19.2 Detailed Implementation Steps

Implement recengine/serve/ann_index.py: build an HNSW index (hnswlib, consumed per ADR-02) over LatentFactors.V at parameters M=16, ef_construction=200, serialized little-endian into the ModelArtifact tarball (§11.10, §21.2). Implement recengine/serve/candidate_gen.py: for a given user, query the ANN index with U[u] for 200 candidates, union with a popularity retriever's top-50 (7-day trailing impressions, excluding seen items), a content-based retriever's top-50 (cosine over content embeddings against the user's most recent interaction), and — post-Phase-6 — the cold-start retriever when the user/item falls below the interaction floor; deduplicate by item_id keeping first-source (I9, P7). Build the consistency harness (tests/integration/ test_hnsw_vs_brute.py): 10K random users, compare HNSW top-10 against brute-force top-10, assert Jaccard overlap ≥ 0.95 (I8).

19.3 Deliverable

A serving-ready candidate_gen() function returning a deduplicated Candidate[] list per request, an HNSW index artifact passing the I8 consistency gate, and a documented 200/50/50/(coldstart) retriever-mix configuration.

19.4 Acceptance Criteria

HNSW query p99 latency ≤ 1 ms on the ml-25m item catalog (62,423 items, rank 64) at ef_search=50 (fixture conformance/hnsw_p99_latency.json, §4); recall@10 vs. brute force ≥ 0.95 averaged over 10,000 random users (I8, fixture conformance/hnsw_recall_consistency.json); index build completes in ≤ 30 seconds (§4).

19.5 Conformance Fixtures

conformance/hnsw_recall_consistency.json; conformance/hnsw_p99_latency.json; conformance/candidate_dedup_provenance.parquet — verifies I9's first-source-kept rule with a crafted case where the same item appears from three retrievers with different scores.

19.6 Pitfalls

Setting ef_search too low to hit a latency target silently drops recall below the I8 floor — the two knobs must be tuned together against both the recall gate and the latency gate, never latency alone (P8). Rebuilding the HNSW index from a LatentFactors.V that has been mutated by a (deferred) streaming update without also rebuilding downstream candidate-source consistency checks produces a stale-vs-fresh mismatch between the index and the hot-factor cache — out of scope until the online-learning phase is un-deferred (§35), but documented here to avoid the mistake of wiring a live index update prematurely.

19.7 Performance Concerns

Brute-force scoring at 62K items costs ~8ms per user (single dot-product sweep); HNSW at ef_ search=50 costs ~0.5ms — the 15x speedup is what makes the rest of the serving budget (ranking, reranking) feasible within the p99 10ms target (§4). The index is mmap-loaded so multiple worker processes share memory rather than each holding a private copy — critical at the production-target catalog size (5M items) where a private-copy-per-process would exceed the host RAM budget.

19.8 Edge Cases

A brand-new item inserted into the index only at the next nightly rebuild (no live index mutation, ADR-21's rationale) — between rebuilds, new items surface only through the cold-start retriever (§18), not the ANN path; this gap is bounded by the nightly cadence (ADR-07) and documented, not silently absorbed. A user whose U[u] factor is the zero vector (cold user, §15.8): the ANN query against a zero vector returns an arbitrary (effectively random, by index-graph traversal order) set of items — candidate-gen must detect the zero-factor case and skip the ANN retriever for that user, deferring entirely to cold-start/popularity sources.

19.9 Failure Analysis

An I8 recall-consistency failure on a nightly rebuild blocks the deploy (per the gate's Recovery column) rather than shipping a degraded index silently — detection is automatic in CI; containment is that the previous artifact continues serving (I12's hash-verified load plus the rollback mechanism, ADR-24) while the index is retuned.

19.10 Operational Notes

Emit candgen.retriever_latency_ms{source}, candgen.union_size, candgen.dedup_rate, ann.recall_vs_brute_force. Index rebuild is part of the nightly artifact build (ADR-07); no separate deployment step.

20. Phase 8 — Two-Stage Ranking & Popularity-Bias Mitigation

20.1 Objectives

Score the unioned candidate set with a learned ranker over RankFeatures (§11.8), then correct for popularity bias and apply a diversity constraint before the final top-N — closing the loop on P6's mandatory bias-correction principle and P1's two-stage architecture.

20.2 Detailed Implementation Steps

Implement recengine/train/ranker.py: a logistic/FM ranker (ADR-03, ADR-10) over the flattened RankFeatures vector, trained on the impression+click log with downsampled negatives (10:1) and isotonic recalibration (ADR-12, I10) on a held-out validation slice. Implement recengine/serve/ rank.py: batched scoring of the candidate union from §19, reusing the dot_uv projection to avoid recomputing the user-factor component per candidate. Implement recengine/serve/rerank.py: Maximal Marginal Relevance (Carbonell-Goldstein 1998; ADR-13) — greedily pick the candidate maximizing lambda_mmr * relevance - (1-lambda_mmr) * max_similarity(selected), similarity = item factor cosine, lazily computed only against already-selected items (O(K*N) not O(N^2)); layer the Phase-6 Beta-Bernoulli exploration bonus (P6, ADR-14) into the relevance term before MMR runs, per the ordering rule in the domain notes (exploration first, diversity second, so MMR operates on the already-uncertainty-adjusted relevance signal).

20.3 Deliverable

A production-ready rank() + rerank() path serving top-10 lists with calibrated scores, provenance, and a diversity-relevance tradeoff report (docs/phase8_mmr_sweep.md) across lambda_mmr ∈ {0.5,0.6,0.7,0.8,0.9}.

20.4 Acceptance Criteria

Ranker AUC ≥ 0.75 on the held-out calibration slice (fixture conformance/ranker_auc_gate.json); NDCG@10 after reranking must not drop more than 3 points versus pre-rerank NDCG@10 at the default lambda_mmr=0.7 (fixture conformance/mmr_ndcg_cost.json) — documenting the diversity-relevance cost explicitly rather than shipping it silently; intra-list diversity (mean pairwise item-factor cosine distance) must improve by ≥ 15% versus the no-rerank baseline at the same lambda_mmr.

20.5 Conformance Fixtures

conformance/ranker_auc_gate.json; conformance/mmr_ndcg_cost.json; conformance/ popularity_bias_headcount.json — measures the fraction of top-10 slots occupied by the catalog's top-1% items pre- and post-bias-correction, the concrete P6 regression gate.

20.6 Pitfalls

Training the ranker on downsampled negatives without the isotonic recalibration step (skipping ADR-12/I10) produces a score that ranks correctly relative to itself but is miscalibrated in absolute probability, which silently breaks both the MMR relevance term's comparability across sessions and any later cross-model score comparison (I10 exists specifically to prevent this). Running MMR reranking before the exploration bonus is applied inverts the intended effect — newly-exposed uncertain items get diversified away before they ever get their uncertainty-driven boost, defeating the point of Phase 6's bandit (documented ordering rule, §20.2).

20.7 Performance Concerns

Batched ranker inference over ~300 candidates (200 ANN + 50 popularity + 50 content, per §19.2) at ~75-300 features is a few hundred microseconds via vectorized NumPy — well inside the 10ms budget (§4). The lazy MMR similarity computation (only against already-selected items) keeps rerank cost at O(K*N) for K=10 picks over N≈300 candidates, versus O(N^2) for a naive full-pairwise precomputation.

20.8 Edge Cases

Fewer than 10 candidates survive dedup (a very sparse catalog segment or heavy cold-start scenario): the response returns fewer than 10 items rather than padding with irrelevant filler — callers must handle a short list, documented in the RPC contract (§21.3). Two candidates with identical item factors (a near-duplicate catalog entry, e.g., two SKUs for the same physical item): MMR's similarity term correctly suppresses the second occurrence, which is the desired behavior, not a bug, but should be logged (rerank.near_duplicate_suppressed_total) since it may indicate a catalog data-quality issue worth fixing upstream.

20.9 Failure Analysis

A popularity_bias_headcount regression (top-1% items creeping back above the gate threshold) signals either an MMR lambda_mmr misconfiguration or a negative-sampling regression in the ranker's retraining — detection is the §20.5 fixture gate on every retrain; recovery is re-running the ADR-11 negative-sampling ablation before assuming the rerank stage alone is at fault, since both stages jointly determine the final distribution (Threat T7, §22).

20.10 Operational Notes

Emit ranker.auc, ranker.calibration_drift (I10's telemetry), rerank.intra_list_diversity, rerank.popularity_headcount_top1pct. This phase's output is what Phase 9 (§21) deploys and A/B tests; a ranker retrain does not bypass the Phase 9 rollout gate.

21. Phase 9 — Online Serving, A/B Testing & Rollback

21.1 Objectives

Deploy the pipeline behind a gRPC service, build the A/B traffic-splitting and counterfactual evaluation machinery (P3, P10), and make rollback a rehearsed, sub-ten-minute operation (P11, §4's RTO). This is the phase that makes the system trustworthy to operate, not just correct offline.

21.2 Detailed Implementation Steps

Implement recengine/serve/app.py: a gRPC service (proto3, ADR-22) exposing Recommend, Explain, Health; every response carries trace_id and model_version_served (I7). Implement the A/B traffic splitter: bucket = xxhash(user_id) % 100, sticky per experiment_id (I11, ADR-23), assignment logged as ExperimentAssignment (§11.12). Implement recengine/experiments/ counterfactual.py: replay evaluation per §17's harness, plus the IPS-weighted variant, answering "what would model B have done on model A's logged traffic?" (P3). Implement recengine/ experiments/rollback.py: a config flip of active_model_version with a documented 1-minute propagation TTL (ADR-24), rehearsed via a CI smoke test that flips between current and previous versions and asserts both serve correctly before every deploy.

21.3 Deliverable

A running gRPC service meeting the §4 latency budget, an A/B dashboard showing per-arm engagement metrics with bootstrap CIs, and a passing rollback drill in CI on every deploy — the RPC contract: RecommendRequest{user_id, k, context, already_seen, model_version_override, trace_id} → RecommendResponse{items[], model_version_served, trace_id, server_latency_us}.

21.4 Acceptance Criteria

End-to-end p50/p99 latency ≤ 4ms / ≤ 10ms under 2,000 req/s load (fixture conformance/serving_latency_load_test.json, §4); rollback drill completes and both model versions serve correctly within 60 seconds of the config flip (fixture conformance/ rollback_drill.json); A/B dashboard's per-arm NDCG delta must be reported alongside the online engagement-metric delta (P10 — never online-only or offline-only), with fixture conformance/ab_dashboard_smoke.json.

21.5 Conformance Fixtures

conformance/serving_latency_load_test.json; conformance/rollback_drill.json; conformance/ab_sticky_assignment.parquet — verifies I11 by replaying the same user across 100 requests spanning a simulated experiment window and asserting zero bucket flips; conformance/artifact_hash_mismatch.tar — a deliberately corrupted artifact, verifying I12's load-time abort.

21.6 Pitfalls

Changing the A/B bucketing hash function (even to a "better" one) without a migration plan re-randomizes every user's assignment, corrupting any in-flight experiment's sticky-assignment guarantee (I11) — hash-function changes require a documented migration window, never a silent swap. Treating the rollback config flip as instantaneous everywhere (ignoring config-propagation lag across serving replicas) can leave a fleet serving two model versions simultaneously for longer than the documented TTL — the drill (§21.2) exists specifically to catch this before production.

21.7 Performance Concerns

The gRPC service's per-request cost is dominated by candidate generation (§19, ~0.5-1ms) plus ranking (§20, sub-millisecond) plus reranking (§20, sub-millisecond) — the A/B bucketing and trace-id logging add negligible overhead (a hash computation and an async log write) but the log write must be non-blocking or it becomes the tail-latency contributor at p99.

21.8 Edge Cases

A request specifying model_version_override (for canary testing) that names a version not present in the artifact cache: the service must reject with a clear error rather than silently falling back to the active version, since silent fallback would corrupt canary-test data integrity. A rollback triggered mid-flight of an in-progress request: the request completes against whichever version it started with (recorded at assignment time), never switched mid-request — consistency of model_version_served within a single request is non-negotiable for I7's forensic value.

21.9 Failure Analysis

A load-test latency regression (p99 exceeding 10ms) blocks the deploy; detection is the CI gate (§21.4 fixture); containment is that the previous artifact remains active; recovery requires profiling which stage (candidate-gen, rank, rerank) regressed using the per-stage latency telemetry (§19.10, §20.10) before attempting a fix, since the three stages have different likely root causes (ANN misconfiguration vs. ranker feature-count growth vs. MMR similarity-matrix size).

21.10 Operational Notes

Emit serve.latency_us{stage}, ab.bucket_flip_total (I11 violation detector), rollback.drill_result, artifact.hash_mismatch_total (I12). The rollback runbook lives at docs/runbooks/rollback.md and is rehearsed, not merely documented — every deploy exercises it in CI per §21.2.

25. Compatibility & Versioning

Wire compatibility: the gRPC proto (ADR-22) follows proto3 field-addition-only evolution — new fields are optional with defaults, no field renumbering, ever. Storage compatibility: ModelArtifact tarballs are versioned by TrainMeta.model_version (semver + git sha); the loader (§21.2) rejects an artifact whose internal schema version (schema.json, §11.10) it does not recognize, rather than attempting a best-effort partial load. Schema evolution: the training-data parquet schema (§21.1-equivalent, §11.2) may add nullable columns without a version bump; removing or retyping a column requires a new schema major version and a documented migration in docs/interfaces/. API stability: Recommend/Explain/Health (§21.2) are stable RPCs; a breaking change requires a new service version (recengine.v2) served alongside v1 during a deprecation window. Deprecation policy: a deprecated field/RPC is documented in CHANGELOG.md with a removal-not-before date at least one quarter out. SemVer policy: MAJOR.MINOR.PATCH on the training/serving codebase itself; MAJOR bumps on breaking artifact-schema or RPC changes, MINOR on new features (e.g., a new candidate source), PATCH on bug fixes with no schema change. Rolling-upgrade guarantees: the A/B sticky-assignment mechanism (I11) and per-request model_version_served consistency (§21.8) mean two artifact versions can serve concurrently indefinitely without corrupting any single request's metrics.

26. Testing & Verification Strategy

Unit tests cover every pure function in §11's types (CSR row/transpose, similarity metrics, NDCG/RMSE computation) with hand-computed expected values (e.g., conformance/ndcg_hand_ computed.json, §17.5). Conformance: every phase's named fixtures (N.5) are re-run on every CI build. 29. Scalability Analysis

What stays constant: per-request candidate-gen and ranking cost (O(candidates * rank), independent of catalog size once the ANN index is built, §19.7). What grows: ALS training cost (O(nnz * rank^2), linear in interaction count, §15.7); HNSW index memory (O(n_items * rank) plus graph overhead, roughly 1.5-2x the raw factor size); similarity-table size for item-CF (O(n_items * K) with the co-rating floor bounding the effective pair count, §13.7). Named bottlenecks in order: (1) ALS per-user Cholesky solve past rank ~256 (§15.7, where BLAS-3 Cholesky cost becomes comparable to the rank-1 update cost); (2) single-node RAM for the CSR + transpose past ~200M interactions (§4, the threshold that triggers PhaseDeferred("§15")'s distributed-ALS option); (3) HNSW index memory past ~100M items (ADR-02's stated IVF-PQ crossover); (4) serving fleet CPU past the QPS ceiling in §4 (horizontal scaling absorbs this, the cheapest lever). Horizontal scaling: the serving fleet is stateless and scales linearly with QPS (mmap-shared index avoids per-process memory duplication, §19.7). Vertical scaling: ALS training benefits from more cores up to the per-user-solve parallelism ceiling (min(n_users, nthreads), §11.5). Sharding/partitioning: deferred (PhaseDeferred("§15")) — the distributed-ALS path partitions users and items across a cluster, following Spark MLlib's partitioned-Gramian approach (§5 Reference Implementations) once the single-node ceiling is crossed. Coordination overhead: a distributed ALS variant introduces a per-iteration all-reduce over the Gram matrix (rank x rank, cheap) but a per-iteration shuffle of factor updates (expensive) — this shuffle cost is exactly why single-node ALS is preferred below the RAM ceiling (ADR-05's rationale). The practical ceiling for this architecture, as specified, is roughly 200M interactions / 5M items on a single well- provisioned host (§4); the lever beyond it is the deferred distributed-ALS phase, not a rewrite of the serving architecture, which remains valid at any catalog size once candidates are ANN-indexed.

30. Mental Models & First Principles

MM1. A recommendation is a bet under uncertainty, not a fact. Every score is a point estimate with hidden variance; treating it as ground truth (rather than a posterior to be explored, §20) produces the pure-exploit collapse described in T7. Predicts: any system with no exploration term eventually narrows its own training distribution. Bug class without it: engineers "fix" a stale recommender by retraining more often, which does nothing, because the data itself has collapsed. Applied in §20 (Thompson sampling as the ranker's decision rule, not a bolt-on).

MM2. Sparsity is the whole game. Every design decision in this blueprint — CSR storage (§8.1), the ALS closed-form trick (§8.4), the co-rating floor (§13.6), the ANN index (§19) — exists because the interaction matrix is >99.7% empty (§4). Predicts: any algorithm whose cost scales with dense dimensions (n_users * n_items) is wrong for this problem by construction. Bug class without it: reaching for a dense-matrix library call that silently allocates 10GB for a 200MB problem. Applied in §8.1, §15.2.

MM3. Offline metrics measure agreement with a biased policy, not truth. Logged data only contains what a previous policy chose to show; a new policy is evaluated on a distribution shift from its own perspective. Predicts: an offline NDCG win does not guarantee an online win, and can even correlate negatively when the metric rewards agreement with the old policy's blind spots. Bug class without it: shipping on offline metrics alone and being surprised by an A/B loss. Applied in §17 (IPS/replay), P3, P10.

MM4. A trained factor is a compressed history, and compression forgets deliberately. Regularization (I5) is not noise-reduction incidental to the math; it is the explicit choice of how much individual-user idiosyncrasy to discard in favor of population-level structure. Predicts: too little regularization overfits sparse users' single ratings; too much erases genuine personalization. Bug class without it: tuning lambda by "what number felt reasonable" instead of by measured density (P9). Applied in §14.2, §15.2.

MM5. Two-stage retrieval trades recall for latency, and the trade is measured, not assumed. Candidate generation (§19) accepts a bounded recall loss (I8's 0.95 floor, not 1.0) in exchange for sub-millisecond query time; the ranker (§20) then recovers precision within the surviving candidates. Predicts: any attempt to push candidate-set size to zero-recall-loss defeats the latency purpose of having two stages at all. Bug class without it: endlessly widening the ANN candidate count "to be safe," destroying the latency budget it was built to protect. Applied in §19.6, P1, P8.

MM6. A feedback loop is a system training on its own opinions. Once a ranker's own output shapes what data it gets to learn from next (T7), the system is no longer a pure supervised learner — it is closer to a reinforcement-learning problem wearing supervised-learning clothes. Predicts: metrics can look stable while the underlying exposure distribution silently narrows. Bug class without it: monitoring aggregate CTR (which can stay flat) while catalog coverage collapses (§20.5's headcount gate exists to catch exactly this). Applied in §20, T7, P6.

MM7. Calibration and ranking are different properties of a score. A score can rank candidates correctly (high AUC) while being wildly wrong as a probability (miscalibrated) — and popularity- bias correction, cross-model comparison, and A/B deploy gates all depend on the probability being trustworthy, not just the order (I10). Predicts: a model that "looks great" on AUC can still break reranking logic that assumes calibrated inputs. Bug class without it: applying MMR's relevance-diversity tradeoff on an uncalibrated score, producing an unpredictable diversity effect. Applied in §20.2, ADR-12.

MM8. Every artifact needs a provenance trail or the system cannot explain or undo itself. TrainMeta (§11.10), trace_id (I7), and content-hashing (I12) exist together because explainability (P12), rollback (P11), and forensics (§23) are the same underlying requirement: given a served recommendation, reconstruct exactly which model, which candidates, and which score produced it. Predicts: a system without this trail cannot debug a single bad recommendation, let alone roll back a bad deploy in minutes. Bug class without it: an incident where nobody can say which model version served a given user an hour ago. Applied in §11.10, §21.2, §24.

32. Back-of-Envelope Capacity Model

All numbers chained from §4's constraint table (ml-25m reference: 162,541 users, 62,423 items, 25,000,095 interactions; production target: 20M users, 5M items, 200M interactions, rank=64).

  1. Matrix density = nnz / (n_users * n_items) = 25,000,095 / (162,541 × 62,423) ≈ 0.00246 (0.246%) — the number that justifies every sparse-storage decision in §8.1.
  2. Average interactions per user = nnz / n_users = 25,000,095 / 162,541 ≈ 153.8 — used in §15.5's confidence-histogram sanity check and §13.7's inverted-index sizing.
  3. CSR+transpose memory = 2 × [(n_users+1)×8 + nnz×4 + nnz×4] = 2 × [1.3MB + 100MB + 100MB] ≈ 402 MB — matches §4's "≤500MB" training-memory row with headroom for scratch buffers.
  4. Factor memory at rank 64 = (n_users + n_items) × rank × 4 bytes = (162,541 + 62,423) × 64 × 4 ≈ 57.6 MB — small relative to the CSR cost, confirming factors are never the training-memory bottleneck at this scale.
  5. Total ALS training flops (all 15 iterations, both sweeps) = 2 × iters × nnz × rank^2 = 2 × 15 × 25,000,095 × 4,096 ≈ 3.07 × 10^12 flops (3.07 TFlop). At the §4 target of ≤3 minutes (180s), this implies a sustained ≈17 GFlop/s effective throughput across 8 cores — plausible for NumPy/BLAS-vectorized rank-1 updates (§15.7), confirming the phase gate is achievable, not aspirational.
  6. HNSW query compute floor = log2(n_items) × M × rank × 2 = 15.9 × 16 × 64 × 2 ≈ 32,563 flops per query — nanoseconds of raw compute, meaning the measured ≤1ms p99 (§4, M5) is dominated by graph-traversal memory-access latency, not arithmetic, which is why ef_search tuning (§19.6) trades recall against cache-miss count, not flop count.
  7. Production-scale total artifact memory = factors (20M+5M)×64×4 ≈ 6.4GB + CSR+transpose at 200M interactions 2×[(20M+1)×8 + 200M×8] ≈ 3.5GB + HNSW index at ≈1.5× raw item-factor size (5M×64×4)×1.5 ≈ 1.92GB ≈ 11.8 GB total — comfortably inside §4's production ≤32GB training-memory ceiling, with headroom before PhaseDeferred("§15")'s distributed path is required.
  8. Serving throughput per host = cores / p50_latency = 8 / 0.004s = 2,000 req/s — derives exactly the §4 "max concurrency per serving host" row from the measured p50 latency, confirming horizontal scaling (adding hosts) is the correct lever past this ceiling (§29), not a per-host optimization chase.

34. Alternative Architectures (Roads Not Taken)

AA1 — Pure content-based, no collaborative signal.

 [item content features]--->[similarity engine]--->[per-user profile of liked content]--->[top-N]
                                                              ^
                                                    [explicit/implicit history]

Regime where it wins: an extremely sparse or brand-new catalog where collaborative signal barely exists yet (a B2B SaaS marketplace at launch). Real system: the original Pandora Music Genome Project (hand-annotated content features driving similarity, no collaborative signal at all). Rejected here because the target domain (§1) has enough interaction volume (§4) that collaborative signal is the stronger predictor once past the cold-start window (§18), and pure content-based recommendation cannot exploit the confidence-weighted implicit signal this blueprint centers on (P3).

AA2 — Fully online, no batch training.

 [click stream]-->[online learner: per-event gradient step]-->[live factors]-->[serving]
                                                                     ^
                                                       (no nightly batch rebuild at all)

Regime where it wins: a continuously evolving catalog/user base at massive scale where nightly batch latency (§4, ADR-07) is itself unacceptable staleness. Real system: TikTok's Monolith architecture (large-scale online learning with no batch-primary training path). Rejected here because it requires the streaming-join and online-learning infrastructure this blueprint deliberately defers (PhaseDeferred("§21"), §35) — the engineering cost is not justified at the target scale in §4, and the nightly-rebuild cadence (ADR-07) is sufficient for the target staleness tolerance.

AA3 — Graph-based random-walk recommendation.

 [bipartite user-item graph]-->[random walk with restart]-->[visit-frequency ranking]-->[top-N]

Regime where it wins: when rich graph structure beyond simple interactions exists (social connections, board/collection structure) and the walk can exploit second- and third-order relationships. Real system: Pinterest's Pixie/PinnerSage (random walks over the pin-board bipartite graph). Rejected here because the domain as scoped (§1) has no social or collection graph beyond the user-item interaction matrix itself — building the graph-walk machinery would duplicate what matrix factorization already captures from the same data, at higher serving cost.

AA4 — Explicit-only regression, no implicit path.

 [explicit ratings only]-->[biased-ALS RMSE minimization]-->[predicted rating]-->[rank by predicted rating]

Regime where it wins: a domain with only explicit ratings and genuinely no implicit signal at all (a legacy movie-rating site with no click/view logging). Real system: the original Netflix Prize competition harness itself (explicit ratings only, RMSE as the sole target). Rejected as the primary path here (though retained as Phase 2, §14) because ADR-08 documents that 95%+ of production interaction data is implicit-dominant, and an explicit-only system cannot exploit the confidence-weighting mechanism (§8.2) that this blueprint's primary candidate generator (ADR-01) depends on.

36. Glossary

ALS (Alternating Least Squares) — matrix-factorization training method alternating closed-form solves for user factors and item factors while holding the other fixed (§8.4, §14, §15).

A/B testing — randomized online comparison of two model versions on live traffic, the deploy gate per P10 (§21).

Adjusted cosine similarity — item-item cosine computed after centering each rating by its user's mean rating, correcting for per-user rating-scale bias (§8.3).

ANN (Approximate Nearest Neighbor) — a search structure (here, HNSW) trading a small recall loss for large latency gains versus brute-force search (§19).

Bandit (multi-armed) — an online decision framework balancing exploration and exploitation; here, Thompson sampling over a Beta-Bernoulli CTR posterior (§20).

Bias term (bu, bi) — per-user and per-item additive offsets in explicit-ALS, capturing rating tendencies independent of latent factors (§8.4, §14).

Bootstrap confidence interval — a resampling-based uncertainty estimate on a metric, used throughout §17's evaluation reports (P4).

BPR (Bayesian Personalized Ranking) — a pairwise ranking loss for implicit feedback (Rendle et al. 2009), the SGD-trained alternative to ALS (§8.5, §16).

Calibration — the property that a predicted probability matches observed frequency; enforced via isotonic regression (I10, ADR-12).

Candidate generation — the first serving stage: cheaply retrieving a bounded set of plausible items before ranking (§19, P1).

Chronological split — a train/test split by timestamp rather than random assignment, preventing future-information leakage (P2, I2).

Cholesky factorization — the matrix decomposition used to solve the per-user/per-item ALS linear system, requiring the matrix be positive-definite (I5, §8.4).

Cold start — the problem of recommending to users or items with little or no interaction history (§8.7, §18).

Collaborative filtering — predicting preference from patterns across many users' behavior, without relying on item content (§8.3, §13).

Confidence weighting — the c_ui = 1 + alpha*r_ui transform converting implicit signal strength into a per-observation training weight (Hu-Koren-Volinsky 2008, §8.2).

Content-based filtering — recommending based on item attributes (text, image, category) rather than collaborative signal (§18).

Counterfactual evaluation — estimating what a different policy would have done using logged data from the deployed policy, via replay or IPS (§17, P3).

Coverage — the fraction of the catalog ever surfaced by the recommender across users (§11.11).

CSR (Compressed Sparse Row) — the sparse matrix storage layout used for the interaction matrix (§8.1, §11.3).

Diversity (intra-list) — a measure of how dissimilar the items within one recommended list are to each other, traded against relevance by MMR (§20, P7).

Explicit feedback — a directly stated preference signal, typically a star rating (§8.2).

Feedback loop — the phenomenon where a model's own served output shapes the data it is next trained on, risking self-reinforcing bias (T7, MM6).

Global mean — the average rating across the entire training set, the baseline term in explicit-ALS (§8.4, §11.4).

HNSW (Hierarchical Navigable Small World) — the graph-based ANN index algorithm used for candidate retrieval (Malkov-Yashunin 2018, §19).

Hybrid recommender — a system combining collaborative and content-based signals, as in the cold-start bridge (§18).

Implicit feedback — an indirect preference signal inferred from behavior (clicks, plays, purchases) with no negative label (§8.2).

Inverse propensity scoring (IPS) — reweighting logged data by the inverse probability of the observed action, correcting for position/selection bias (§17.2, P3, ADR-16).

Isotonic regression — a non-parametric monotonic calibration method used to map raw ranker scores to calibrated probabilities (ADR-12, I10).

Item-based collaborative filtering — CF predicting from item-item similarity rather than user-user similarity (Sarwar et al. 2001, §8.3, §13).

Jaccard similarity — set-overlap similarity metric, |A∩B|/|A∪B|, ignoring rating magnitude (§8.3).

Latent factor — a learned low-dimensional vector representing a user or item in matrix factorization (§8.4, §11.4).

MAP@k (Mean Average Precision at k) — the mean, across users, of average precision computed over the top-k recommended list (§17.2).

Matrix factorization — approximating the interaction matrix as the product of two low-rank factor matrices (§8.4).

MMR (Maximal Marginal Relevance) — a greedy diversity-reranking algorithm trading relevance for dissimilarity from already-selected items (Carbonell-Goldstein 1998, §20, ADR-13).

Model artifact — the versioned, deployable bundle of factors, ranker, index, and provenance metadata (§11.10).

NDCG@k (Normalized Discounted Cumulative Gain) — a rank-aware ranking-quality metric normalized against the ideal ordering (§17.2).

Negative sampling — drawing unobserved (or non-positive) items during training to contrast against observed positives, with popularity correction to counter bias (§16.2, ADR-11, P6).

Neighborhood method — a family of CF algorithms (user-based, item-based) predicting from similarity-weighted neighbor ratings, without learning latent factors (§8.3, §13).

Pearson correlation — mean-centered cosine similarity, correcting for user rating-scale offset (§8.3).

Popularity bias — the tendency of click-trained systems to over-recommend already-popular items, addressed via sampling correction, reranking, and exploration (P6, T7, §20).

Position bias — the confound where higher-ranked slots receive more clicks regardless of true relevance, corrected via IPS (§17, ADR-16).

Precision@k — the fraction of the top-k recommended items that are relevant (§17.2).

Propensity — the probability that a given slot/position would be examined, estimated from a randomized traffic slice for IPS correction (§17.2, ADR-16).

Rank (latent dimension) — the dimensionality of the learned factor vectors (§11.5, §4).

Ranker — the second serving stage, scoring the candidate set with a richer feature vector than any single retriever (§20, P1).

Recall@k — the fraction of all relevant items that appear in the top-k recommended list (§17.2).

Regularization — the L2 penalty term (lambda) preventing overfitting in ALS/BPR, tuned to matrix sparsity (P9, I5).

Reranking — post-processing the ranker's scored list for diversity, freshness, or business rules before the final response (§20).

RMSE (Root Mean Squared Error) — the accuracy metric for explicit-rating prediction (§17.2, §14).

Sparsity/density — the fraction of the interaction matrix that is observed; the defining property shaping every algorithmic choice in this blueprint (§4, MM2, §32 item 1).

Thompson sampling — a Bayesian exploration policy sampling from a posterior (here, Beta) to balance exploring uncertain items against exploiting known-good ones (§20, ADR-14).

Trace ID — the identifier linking a served recommendation through impression, click-join, and counterfactual replay for explainability and forensics (I7, P12).

Train/test leakage — contamination of the evaluation set with information unavailable at prediction time, most commonly from a random (non-chronological) split (P2, §13.6-adjacent).

Two-stage retrieval — the candidate-generation-then-ranking architecture pattern underlying the whole serving path (P1, §3).

User-based collaborative filtering — CF predicting from similarity between users' rating patterns (§8.3, §13).
