In one paragraph

A journaling layer sits between a filesystem and a raw block device and makes a group of block writes all-or-nothing, even if the power fails mid-write (§1). It writes a description of the intended change into a fixed-size circular log, forces that log to disk, and only then lets the change reach its final location; after a crash, a scan of the log finishes or discards each change (§2, §8.3). It is not a filesystem: it owns no inodes, directories or allocator (§1). This design is a Rust library, or a standalone jbd daemon, with one writer process per journal, used by filesystem implementers and operated by SREs (§1).

The problem, concretely

Creating or changing a file touches several blocks: in the blueprint's example, an inode block and a file-content block (§8.6). Without a journal, a crash in the middle leaves a partially updated inode, a partially updated bitmap, and a directory entry that may or may not point at the new inode (§2). The post-crash repair tool (fsck) must then walk the whole device and guess the most plausible interpretation, and it is sometimes wrong (§2).

The fix, credited to Hagmann's 1987 Cedar paper, is to append a description of the intended change to a log, fsync the log, and only then do the change (§2). If the change is half-done after a crash, recovery finishes it from the log. If the log entry itself is half-done, recovery discards it and the change never happened (§2). One bit, "is the commit record durable?", decides which outcome you get (§2, I1).

The naive versions of this each fail in a specific way. Treating a write() that returned Ok as durable makes the bit meaningless (§2, MM1, MM3). An unbounded append-only log gives up predictable size and recovery time (§3, P2, ADR-03). One commit per fsync caps throughput at 1/L (§14.6). A stale log entry replayed over a block that was freed and reallocated silently restores old bytes (§19.6, T7). §2 calls group commit, checksums, revocation and the three modes engineering scaffolding around the one commit-record bit (§2).

How it works, end to end

Follow one transaction (a set of block writes committed together) through §3's boxes. The blueprint's own trace is transaction 42, which writes metadata block 100 and data block 500 in ordered mode (§8.6).

  1. Transaction manager (jbd-txn) hands out a TxnHandle, buffers the blocks written into it, allocates a monotonic TxnId, and passes the sealed transaction to the commit thread (§3, §8.1, §12.2, I6).
  2. Commit thread and group-commit window (jbd-commit in §3; §10 and §14.2 put the window manager in a separate jbd-group-commit crate) is the only writer to the journal (I10, P14). It gathers concurrent transactions inside a bounded window, calls the active mode strategy's pre-commit hook, writes descriptor, data and commit records, and issues one fsync (§3).
  3. Mode strategy (jbd-mode-ordered is the one wired in Phase 0) decides when data blocks hit their final location relative to the commit record (P4, §8.4, §1).
  4. Journal (jbd-journal) is a ring: block 0 is the superblock, the rest hold descriptor, data, commit and revoke records (§8.2). Head is the next-write cursor, tail is the oldest uncheckpointed transaction (§3, I7).
  5. Block device (jbd-block) is a trait with in-memory, file-backed and raw-device implementations plus a crash-injection decorator (§1, P11, ADR-05). Its flush() is the only durability primitive the layer relies on (I13).
  6. Checkpoint copies the committed blocks to their final locations, then advances the tail and records that in the superblock (§8.3, §13.2, I7, I9). Each transaction moves Running -> Locked -> Committing -> Committed -> Checkpointed (§8.1).
  7. Recovery (jbd-recover, jbd-replay) reads the superblock, builds the revocation set, scans forward, and replays every valid committed transaction. It is safe to run again after a crash during recovery (§3, I8).

commit_txn returns Ok(TxnId(42)) only after the journal fsync in step 6 of §8.6's trace (§8.6). A crash before that point discards the transaction entirely on recovery; a crash after it replays block 100 at recovery, and block 500 is already in place (§8.6, I1, I3).

The core ideas

The commit record is the pivot (§8.3, P1, I1)

The write-ahead discipline has three steps: describe every block write in the journal; make the descriptor, data and commit records durable with one fsync; only afterwards copy blocks to their final locations (§8.3). The design is redo-only (it never stores an undo image): a transaction that has not committed has never touched a final location, so there is nothing to undo (§8.3, P3). A transaction is durable if and only if its commit record is fsync'd, checksum-valid and chained to a valid descriptor (P1, I1). The commit record carries crc_over_txn, a checksum over the descriptor and every data block, plus crc_self over its own preceding fields (§11.4). The mental model is a coin flip resolved once: before the fsync returns the fate is undetermined; after, it is permanently one of two values (MM1). The blueprint names five crash shapes that every later phase tests (§12.8):

# Crash shape State on disk After recovery
1 pre-write transaction opened, no journal writes transaction does not exist
2 mid-data some data journaled, no descriptor orphaned data reclaimed by the filesystem above
3 pre-commit descriptor and data durable, no commit record discarded
4 post-commit-pre-flush commit record written, fsync in flight either outcome is correct; caller tolerates both
5 post-flush commit record durable applied

A ring with two cursors: head, tail and wrap-around (§8.2, P2, I7, MM2)

The journal is a fixed-size circular sequence of blocks (P2). Head advances on write and tail advances on checkpoint; the gap between them is exactly the uncheckpointed window (MM2). Before any write, the journal checks whether the target blocks intersect the uncheckpointed region and, if so, blocks until checkpoint advances the tail (§13.2, I7). That blocking is the price of a fixed size: predictable recovery time and write amplification, paid for with checkpoint-driven backpressure (P2, §4). In the default configuration the journal holds 128 MiB / 4 KiB = 32,768 blocks (§33 item 1). Records are fixed-width and byte-exact, so the recovery scan is deterministic rather than probabilistic (§13.2, ADR-14). One layout rule is worth knowing: a data block whose first four bytes equal the journal magic is zeroed on write, flagged ESCAPED in its descriptor tag, and restored on read, so recovery never mistakes payload for a record header (I11, §11.3, §13.2).

Three modes, one codebase (§8.4, P4, I3, I14)

The modes differ only in when data reaches its final location relative to the commit record (P4). Metadata atomicity is identical in all three (I14).

Mode Metadata journaled Data journaled Data flushed before commit Anomaly admitted (§8.4)
journal yes yes yes, in the same commit none; 2x write amplification
ordered (default) yes no yes none for data that metadata points at
writeback yes no no stale or leaked data bytes behind valid metadata

Ordered mode buys causality between data and metadata, not ordering between two data writes in the same transaction (MM4). In writeback mode the canonical anomaly is metadata claiming a size whose data bytes are whatever previously occupied the block, possibly from a deleted file (§17.8). Writeback needs an explicit --unsafe-writeback flag (§17.2, §17.10) and still keeps the metadata fsync barrier (§17.6, I13).

Group commit: one fsync for many transactions (§14.2, §14.6, P6, I12)

With fsync latency L, an ungrouped commit thread is capped at 1/L regardless of how many writers there are, because writers share one journal and cannot commit concurrently (§14.6). Group commit gathers whatever arrives within a window W, terminates the batch with one commit record whose checksum covers every descriptor and data block in it, and pays for one fsync (§14.2). Batch size is about N * W * r for N writers each at rate r, and throughput is (N*W*r)/W = N*r, linear in N up to max_batch (§14.6, §14.2).

Quantity Formula Blueprint's values
fsync latency L given about 200 us on NVMe (§14.6)
ungrouped ceiling 1/L about 5,000 txn/s (§14.6, §33 item 5)
batch at window close N*W*r 64 * 5 ms * 1/ms = 320 per fsync (§33 item 4)

The batch is atomic as a whole: a crash mid-batch discards every transaction in it, and each waiting writer sees an error or timeout and must retry (I12, §14.9). A solo committer exits the window early so it does not pay the full wait (§14.2). The price is latency variance: some writers wait up to the full window (MM6).

Recovery: two passes, restartable (§18.2, §18.8, I8, P10, P13)

Recovery is a seven-step procedure (§18.2): validate the superblock (refuse mount if its checksum fails); start at oldest_uncheckpointed; scan forward collecting every Revoke record; re-scan and apply each transaction with a valid commit record, skipping revoked blocks; flush; update and fsync the superblock; accept new transactions. The first pass builds the revocation set so the second pass can skip stale writes (§18.2, §18.6). The state machine is:

BuildRevocationSet, ReplayForward, FlushDevice and UpdateSuperblock can each be re-run from a crash with the same result, and a crash during recovery re-enters at SuperblockRead (§18.6, §18.8, I8). Once AcceptWrites is reached, a new crash is the next mount's recovery problem (§18.8). Cost is two full passes over the uncheckpointed region, linear in journal size (§18.7, P10). Recovery is a normal mode of operation, the third alongside append and checkpoint, and is tested as often as the happy path (P13, MM7).

Revocation: a tombstone, not a delete (§19.2, P8, I5, MM5)

Suppose block B is written by an older committed transaction, then freed and reallocated, and a newer transaction rewrites B. If the older transaction's descriptor is still in the journal (a wrap-around artifact), replaying it after the newer one would undo the newer write (§19.5). The fix is a Revoke record, emitted in the same transaction as the metadata change (§19.2). Recovery keeps a BTreeMap<BlockId, TxnId> (the RevokeTable) recording the highest revoking TxnId per block, and skips any replay the table says is revoked (§19.2, ADR-22, I5).

The skip rule is stated three ways. §19.2's is_revoked(block, txn) answers txn <= revoking_txn, which also covers the revoking transaction's own write. I5 uses a strict T1 < T2, and §19.5's fixture has T2 both revoke and rewrite B and expects T2's content after recovery (§19.4). §18.2 step 4 skips any block "revoked at or before that transaction's id". The blueprint does not reconcile them (§19.2, §19.5, §18.2, I5).

The table is coalesced at checkpoint: once a transaction is checkpointed, older revokes are implicitly satisfied (§19.2). A missing revoke is the most insidious bug class in the layer because recovery silently restores stale data while the filesystem looks healthy (§19.6, P8).

The trade-offs — where engineers disagree

Default consistency mode: ordered (ADR-01, P5)

Chosen: ordered, matching 15 years of ext4 operational experience (§9). Rejected: journal-default and writeback-default. When the rejected choice is right: journal-default for regulatory or database workloads that need byte-exact post-crash file size (§16.3); writeback-default for build systems that re-derive their outputs (§17.3).

Checksum: CRC32C (ADR-02, P7)

Chosen: CRC32C, hardware-accelerated and sufficient for accidental-corruption detection at this rate (§9). Rejected: SHA-256, or no checksum. When the rejected choice is right: SHA-256, under an active-adversary threat model; the blueprint defers it (§9, §21.6, §36). Note that ADR-02 cites T1 and T2 as that adversarial regime, while §23 lists CRC32C as the mitigation for T1 and T2; the blueprint does not reconcile the two (§9, §23).

Journal structure: a fixed-size circular log (ADR-03, P2)

Chosen: fixed-size ring, for predictable size and recovery time (§9, §4). Rejected: an append-only growing file, or a BTRFS-style B-tree log. When the rejected choice is right: append-only, when journal size truly cannot be bounded in advance, which §9 calls rare (an archival write-ahead log is its example).

Group-commit window: 5 ms default (ADR-04, MM6)

Chosen: 5 ms default, configurable 0 to 50 ms, JBD2's proven default (§9, §4). Rejected: fixed 1 ms, fixed 20 ms, or no window. When the rejected choice is right: 1 ms, for callers that are sensitive to sub-millisecond commit latency, such as application-level fsync at the database layer (§9). §14.7 adds that throughput-only callers want 20 to 50 ms.

Writer concurrency: one commit thread per journal (ADR-08, P14, I10)

Chosen: one commit thread, which removes concurrent-write-ordering bugs; group commit absorbs the throughput need (§9). Rejected: multiple concurrent writer threads. When the rejected choice is right: only with multiple independent journal regions; multi-journal sharding is deferred (§9, §30, §36).

Commit execution model: a synchronous thread (ADR-07, ADR-13)

Chosen: synchronous fsync on a dedicated std::thread, because fsync is physically synchronous (§9). Rejected: io_uring async submission from day one. When the rejected choice is right: once the kernel floor is 5.10 or later everywhere and the win is benchmark-proven (§9, §21.7, §36).

Roads not taken

Log-structured filesystem (§35 A1): the log is the filesystem. It wins on media with poor random-write performance (Sprite LFS, f2fs). Rejected because it replaces the whole storage layout and adds segment-cleaning latency spikes, while this layer's scope is journaling only (§35, §1).

Shadow paging / copy-on-write (§35 A2): no separate journal. It wins when snapshot-everywhere and full-tree checksumming are first-class (ZFS, BTRFS). Rejected because this layer journals around fixed final locations for a filesystem that owns its own allocator (§35, §1).

Soft updates (§35 A3): dependency-ordered in-place writes, no log. It wins when the write-twice cost of journaling (M5) is unacceptable and CPU for dependency tracking is available (FreeBSD FFS). Rejected because it is more complex than the commit-record pivot and composes less cleanly with group commit and an external journal (§35).

Application-level journaling (§35 A4): the caller owns a log. It wins for databases with their own write-ahead log, which is the writeback-mode use case (§35, §17.3). Rejected as the only mode because most callers do not want to build crash consistency themselves (§35).

Deferred (§36): HMAC journal authentication, multi-journal sharding, io_uring, a persistent-memory journal and a backup superblock, each with its own un-defer trigger (§36).

What must never be false

  • I1: a transaction is durable iff its commit record is fsync'd, checksum-valid and chained. Noticed by recovery re-validating the CRC on every commit record; jbd_commits_total (§7).
  • I2: no final-location write is claimed durable before its commit record is. Noticed by a code-review checklist and conformance; jbd_commit_latency_seconds (§7).
  • I3: in ordered mode, data flushes before the metadata commit record. Noticed by the mode_ordered bucket; jbd_ordered_flush_seconds (§7).
  • I4: recovery applies a transaction only if every checksum in its chain validates. Noticed as a CRC mismatch classified as a torn write; jbd_torn_writes_total (§7).
  • I5: a block revoked by a newer transaction is never replayed from an older one. Noticed by the revocation bucket; jbd_revoke_table_size (§7).
  • I6: TxnId is monotonic and never reused. Noticed by an assertion in the submit path; jbd_txn_id_gap_total (§7).
  • I7: the ring never overwrites a block of an uncheckpointed transaction. Noticed by a wrap-around check before write; jbd_journal_used_fraction (§7).
  • I8: recovering twice from the same pre-image yields the same post-image. Noticed by the recovery_idempotence bucket; jbd_recovery_seconds (§7).
  • I9: the superblock is updated and fsync'd strictly after the commit records it references are durable. Noticed by a code-review checklist; jbd_checkpoint_lag_txns (§7).
  • I10: exactly one commit thread writes a given journal. Noticed by a single-writer assertion (no telemetry; §7).
  • I11: a data block starting with the journal magic is escaped on write and restored on read. Noticed by the escape_rule bucket; jbd_escaped_blocks_total (§7).
  • I12: a group-commit batch is atomic: one commit record covers every transaction in it. Noticed by the group_commit bucket; jbd_group_commit_batch_size (§7).
  • I13: BlockDevice::flush() is the only durability barrier the layer trusts. Noticed by a device-conformance test at mount, which refuses mount if flush is unverifiable; jbd_flush_calls_total (§7).
  • I14: the active mode never breaks metadata atomicity, only data timing. Noticed by the mode-specific conformance buckets; jbd_commits_total{mode} (§7).

What breaks in production

  • FM-1 and FM-2: a block or commit record fails its CRC at recovery. A torn write from power loss, caught by a per-block CRC or crc_self mismatch. Recovery discards the owning transaction; jbd dump shows its boundary and jbd fsck-journal isolates the failing record (§24, I4).
  • FM-4: a gap between a descriptor and its expected data blocks. Cause is a lost write, where the device dropped it. The scan detects the missing journal block and discards the incomplete transaction; the data was never durable. jbd dump --pre-recovery shows the gap (§24, T5).
  • FM-5: checkpoint incomplete after a crash. Cause is power loss during checkpoint writeback. Detected when oldest_uncheckpointed is behind last_committed at mount. Recovery re-replays from the journal, which is safe because it is idempotent (§24, I8).
  • FM-6: begin_txn blocks indefinitely. The journal is full and checkpoint is not advancing. Detected by jbd_journal_used_fraction staying above 0.85. Recovery is a forced checkpoint, or jbd-cli compact-journal by hand; see docs/runbooks/journal-full.md (§24, I7).
  • FM-9: two recovery runs on the same pre-image give different post-images. A non-deterministic recovery bug. The recovery_idempotence diff check catches it. There is no auto-recovery: it is a code defect, fixed by patching and re-running conformance (§24, §18.9).
  • FM-12: some transactions in a batch look durable and others do not. The commit-record CRC does not cover the whole batch. Caught by the group_commit bucket's crash-mid-batch case; a code defect with no auto-recovery (§24, I12, §14.5).

Threats worth knowing (§23). T3 is a torn write from power loss, answered by per-block CRCs (P7). T5 is a lost write: the device acknowledges and then drops the write. The journal layer alone has no mitigation and relies on I13's flush contract (§23, MM3). T7 is a stale write replayed over a freed and reallocated block, answered by revoke records (I5). T8 is journal-full livelock under a write burst, answered by a bounded max_batch and checkpoint backpressure (I7). T12 is a crafted malformed record meant to crash the recovery parser, answered by bounds-checked decoding and a consistency check between MORE and tag_count (§8.7).

Where the blueprint disagrees with itself, both statements stand:

  • §33 item 7 calls about 30,500 txn/s, at 500 MB/s and 4-block transactions, "the real ceiling for typical workloads", while M3 and the Phase 2 criterion ask for at least 100,000 txn/s from 64 writers committing 4-block transactions on an NVMe-class device (§4, §14.4, §29).
  • §14.6 gives throughput as N*r, which for §14.4's 64 writers each committing every 1 ms falls short of §14.4's 100,000 txn/s; the same §14.6 paragraph and §33 item 6 instead multiply the 320-transaction batch by 5,000 fsyncs/s for 1,600,000 txn/s.
  • §33 item 4 and §14.6 put 320 transactions in each batch at N=64, while §14.2 caps a batch at max_batch of 256.
  • §18.4 asks a 128 MiB journal to recover in at most 0.25 s on a 500 MB/s device, the same figure §33 item 2 gives for one scan pass, while §18.7 says recovery makes two full passes.

How it compares

  • ext4 (JBD2) is the direct ancestor. Its distinguishing choice is defaulting to ordered mode for 15 or more years, which wins for general-purpose Linux filesystems with mixed workloads (§32, ADR-01).
  • XFS journals metadata only, with in-core log buffers that many CPUs write to concurrently before one flush. That wins for metadata-heavy workloads at very high concurrency, where it outperforms a single-commit-thread ring (§32).
  • ZFS (ZIL) rejected journal-plus-fixed-final-locations for copy-on-write everywhere, using the ZIL as a narrow synchronous-write accelerator with the transaction-group pipeline as the primary mechanism. That wins when end-to-end checksumming and snapshots are first-class (§32, §35 A2).
  • BTRFS (log tree) is also copy-on-write but keeps a lightweight metadata-only log tree to speed up fsync without a full tree commit. That wins for frequent small synchronous metadata updates, such as mail servers and VM images (§32).

Questions to test yourself

  1. Why does a crash between the data flush and the commit-record fsync in ordered mode never produce a "metadata points at garbage" state? — Hint: the worked trace in §8.6, then I3.
  2. Why is group commit's batch CRC coverage a correctness requirement and not merely a performance nicety? — Hint: §14.2 and I12; FM-12 shows the failure.
  3. Why must the superblock update strictly follow the commit records it references, and what specific recovery bug does reversing that order reintroduce? — Hint: I9 and the Phase 1 pitfalls in §13.6.
  4. Why does writeback mode's anomaly window exist even though metadata durability holds? What determines its size? — Hint: §17.1 and §17.8.
  5. Why is recovery required to be idempotent, and what real operational scenario makes that a load-bearing requirement rather than a theoretical nicety? — Hint: I8, the state machine in §18.8 and FM-9.

If you only remember three things

A transaction is atomic because of one bit, whether its commit record is durable, and everything else is scaffolding to make that bit trustworthy (§2, I1, MM1). The fixed-size circular log buys predictable recovery time and write amplification, paid for by checkpoint backpressure, and group commit amortises the single commit thread's fsync across many writers (P2, P6, §14.6). Recovery is a normal, constantly tested, restartable path, and the whole design rests on the device's flush() meaning what it says (P13, I8, I13, MM3).

Words used here

  • Transaction: a set of block writes committed together as the unit of durability (§8.1).
  • Journal: the fixed-size circular log of in-flight transactions, on the same device or an external one (§8.2).
  • Commit record: the journal record that marks a transaction durable; the pivot bit (I1, §11.4).
  • Descriptor record: the record that announces a transaction and lists its block tags (§11.3).
  • Write-ahead logging: making the log durable before the change it describes touches its final location (§8.3).
  • Checkpoint: copying committed blocks to final locations and advancing the tail, which frees journal space (§8.3, I7, I9).
  • Group commit: batching many transactions into one journal write and one fsync (§14).
  • Torn write: a write that started but did not finish before a crash, detected by checksum mismatch (I4, T3).
  • Revoke record: a tombstone telling recovery to ignore an older transaction's write to a block (§19, I5).
  • Escape rule: zeroing a data block's first four bytes if they match the journal magic, and restoring them on read (I11).
  • Superblock: journal block 0, the first thing recovery reads (§11.5).
  • Write amplification: bytes written to the journal plus final locations, relative to bytes the caller wrote (M5, §33 item 11).
