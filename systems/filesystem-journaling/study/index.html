Hard questions (§34)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does a crash between the data flush and the commit-record fsync in ordered mode never produce a "metadata points at garbage" state? (§8.6, §15.2, I3)
  2. What single field, if corrupted undetected, would make recovery replay a stale write over a fresh one? (§19.2, I5, T7)
  3. Why is group commit's batch CRC coverage a correctness requirement and not merely a performance nicety? (§14.2, I12, FM-12)
  4. Derive the journal-full backpressure onset point from the checkpoint throughput and the M7 stall target. (§13.7, §33 item 12)
  5. Why must the superblock update strictly follow the commit records it references, and what specific recovery bug does reversing that order reintroduce? (I9, §13.6)
  6. Why does writeback mode's anomaly window exist even though metadata durability holds? What determines its size? (§17.1, §17.8)
  7. Why is recovery required to be idempotent, and what real operational scenario makes that a load-bearing requirement rather than a theoretical nicety? (I8, §18.8, FM-9)
  8. What would break if the commit thread were not singular (ADR-08) but the group-commit window were removed? (§14.1, §30)
  9. Why does the escape rule zero the first 4 bytes rather than, say, prefixing an extra marker byte? What decoding ambiguity does the chosen approach avoid? (I11, §8.7, §13.6)
  10. Trace how a single-bit flip in a data block's payload propagates (or fails to propagate) into a detected torn write. (§21.2, I4, MM8)
  11. Why does journal mode's write amplification target (M5) sit near 2.05× rather than exactly 2×? (§33 item 11, §16.7)
  12. What is the structural reason multi-journal sharding cannot simply run N independent commit threads against one journal region? (I10, §30, §36)
  13. Why is the revoke table coalesced at checkpoint rather than left to grow indefinitely, and what specific metric would reveal a coalescing bug in production? (§19.2, §19.10, FM-10)
  14. Compare XFS's in-core log-buffer batching to this design's group-commit window: which concurrency assumption differs, and why does that matter at very high CPU counts? (§32, §14.2)
  15. Why does an external journal device below 4 MiB defeat the purpose of group commit? (§4, §20.6)
  16. What is the precise state-machine transition after which a crash becomes "the next mount's problem" rather than "this mount's recovery's problem"? (§18.8)
  17. Why does ZFS's ZIL not need an equivalent to this design's revoke records? (§32, §35)
  18. Derive, from the capacity model, why checksum overhead is measured as a fraction of throughput rather than an absolute per-block nanosecond count in the M6 acceptance gate. (§33 item 9, §21.4)
  19. Why must a snapshot request be rejected rather than queued if it arrives strictly between begin_txn and commit_txn? (§22.2, §22.8)
  20. What operational signal distinguishes FM-6 (journal-full livelock) from FM-10 (revoke table growth) even though both present as "the daemon is using more resources than expected"? (§24, §25.1)
  21. Why does the standard's soft-ceiling rule (no hard 3,000-line cap) matter for a blueprint like this one, given how many quantified derivations §33 alone requires? (§33, meta)
  22. Trace why a lying device (one that acks flush() without actually flushing) breaks every invariant in §7 simultaneously rather than just one. (I13, MM3, §23)

31. Mental Models & First Principles

MM1 — "The commit record is a coin flip resolved once." Before the commit fsync returns, the transaction's fate is undetermined; after, it is permanently one of two values. Predicts: any code path that treats a transaction as "probably committed" before fsync returns is a bug. Bug class without it: assuming write() returning Ok implies durability. Applies at I1, §8.6.

MM2 — "A journal is a state machine with two clocks: head and tail." Head advances on write, tail advances on checkpoint; the gap between them is exactly the uncheckpointed window. Predicts journal-full behavior without needing to trace code. Bug class without it: sizing a journal by transaction count instead of by head-tail gap under peak load. Applies at I7, §13.7.

MM3 — "fsync is a promise about a device, not about your code." The layer's entire correctness rests on BlockDevice::flush() meaning what it says (I13); no amount of application-level cleverness fixes a lying device. Bug class without it: debugging "recovery bugs" that are actually device firmware bugs (T5, FM-4). Applies at §8.5, §23.

MM4 — "Ordered mode buys causality between data and metadata, not intra-data ordering." Two data writes within one transaction have no ordering guarantee relative to each other, only relative to the commit record. Bug class without it: assuming ordered mode makes an application's own multi-write sequencing atomic. Applies at §15.6.

MM5 — "Revocation is a tombstone with a deadline, not a delete." A revoke record does not erase history from the journal; it tells recovery to ignore a specific stale write past a specific TxnId boundary. Bug class without it: expecting the journal to physically remove revoked entries immediately (it does not — checkpoint coalescing does, later, §19.2). Applies at I5, §19.2.

MM6 — "Group commit trades latency variance for throughput, bounded by a window." No free lunch: the price of amortizing fsync cost across writers is that some writers wait up to the full window. Bug class without it: tuning the window down to zero "for safety" and being surprised throughput collapses to the single-transaction ceiling (§14.6). Applies at §14.7.

MM7 — "Recovery is not exceptional, it is the third mode of normal operation." Alongside "append" and "checkpoint," "recover" is a first-class, constantly-tested code path, not a disaster-only corner (P13). Bug class without it: under-testing recovery relative to the happy path, the exact failure §16's motivating audit (BLUEPRINT_STANDARD.md §13.5) found in other blueprints. Applies at §18, §27.

MM8 — "Checksums convert corruption into loud failure, not into silent success." A CRC mismatch is always a discard, never a warning-and-continue (P7). Bug class without it: "fixing" a checksum failure by disabling the check instead of investigating the device. Applies at I4, §21.9.

5. Required Reading

Books

  • Arpaci-Dusseau, R. & Arpaci-Dusseau, A. — Operating Systems: Three Easy Pieces, ch. 42 "Crash Consistency: FSCK and Journaling." Extract: the FSCK-vs-journaling framing and the ordered-mode data/metadata ordering argument. Applied in §8, §15.
  • Gray, J. & Reuter, A. — Transaction Processing: Concepts and Techniques, ch. 8–9 (logging, recovery). Extract: the WAL protocol formalism and the log-sequence-number discipline this blueprint's TxnId mirrors. Applied in §8.3, §11.
  • Silberschatz, A.; Korth, H.; Sudarshan, S. — Database System Concepts, ch. "Recovery System." Extract: undo/redo logging and checkpoint theory; we build redo-only (I3). Applied in §8.3, Phase 6 (§18).
  • McKusick, M. K.; Neville-Neil, G.; Watson, R. — The Design and Implementation of the FreeBSD Operating System, ch. on FFS and soft updates. Extract: the soft-updates alternative to journaling; the basis for §35's rejected-alternative analysis. Applied in §35.
  • Giampaolo, D. — Practical File System Design with the Be File System, ch. on the BFS journal. Extract: a from-scratch journaling design distinct from JBD2; a second data point on descriptor/commit layout choices. Applied in §8.2, §9 (ADR-03).
  • Love, R. — Linux Kernel Development, ch. on the block I/O layer and page-cache writeback. Extract: the writeback path our checkpoint thread races against. Applied in §13.7, Phase 6 (§18).
  • Tanenbaum, A. & Bos, H. — Modern Operating Systems, ch. on file systems. Extract: the baseline consistency vocabulary (atomic rename, crash windows). Applied in §8.

Papers

  • Hagmann, R. — Reimplementing the Cedar File System Using Logging and Group Commit. SOSP 1987. The commit-record pivot and group commit both originate here. Applied in §2, §7 (I1), Phase 2 (§14).
  • Mohan, C. et al. — ARIES: A Transaction Recovery Method Supporting Fine-Granularity Locking and Partial Rollbacks Using Write-Ahead Logging. ACM TODS 1992. The formal WAL discipline (log before data; redo from a checkpoint). Applied in §8.3, Phase 6 (§18).
  • Rosenblum, M. & Ousterhout, J. — The Design and Implementation of a Log-Structured File System. ACM TOCS 1992. The contrast case: the log is the filesystem. Applied in §35.
  • Tweedie, S. — Journaling the Linux ext2fs Filesystem. LinuxExpo 1998. The JBD design document: three-mode triad, descriptor/commit/revoke layout, recovery algorithm. Applied in §8, §9 (ADR-01), Phase 1 (§13), Phase 6 (§18).
  • Mathur, A. et al. — The New ext4 Filesystem: Current Status and Future Plans. OLS 2007. JBD2's evolution: 64-bit block numbers, journal checksumming. Applied in §9 (ADR-02), Phase 9 (§21).
  • Sweeney, A. et al. — Scalability in the XFS File System. USENIX ATC 1996. The metadata-only physical-log alternative. Applied in §32.
  • Hellwig, C. — XFS: The Big Storage File System for Linux. LISA 2009. Retrospective on what XFS's log got right that JBD2 later adopted. Applied in §32.
  • Bonwick, J. & Ahrens, M. — Smokin' Mirrors (ZFS design note), 2003. The ZIL: COW everywhere plus a separate intent log. Applied in §9 (ADR-01 rationale), §32, §35.
  • Prabhakaran, V. et al. — Analysis and Evolution of Journaling File Systems. USENIX ATC 2005. The empirical study of ext3's three modes' actual crash behavior — the paper this blueprint's mode triad (§15–17) is validated against. Applied in §15, §16, §17.
  • Chidambaram, V. et al. — Optimistic Crash Consistency. SOSP 2013. Shows the data-before-commit ordering is often overly conservative; inspiration for the deferred fast-commit path. Applied in §21.6 (deferred), §26.
  • Pillai, T. S. et al. — All File Systems Are Not Created Equal: On the Complexity of Crafting Crash-Consistent Applications. OSDI 2014. The persistence-properties framing we adopt for our own durability contract. Applied in §1, §26.
  • Lu, L. et al. — A Study of Linux File System Evolution. FAST 2013. The bug-class distribution prior informing the test plan. Applied in §27.

Reference Implementations

  • Linux JBD2 (fs/jbd2/commit.c, recovery.c, revoke.c). The executable specification we measure against; not a runtime dependency. Lesson: the commit/checkpoint interleave. Pitfall: do not copy its historical use-after-checkpoint bug class verbatim. Applied in §13, §18, §19.
  • XFS (fs/xfs/xfs_log.c, xfs_log_recover.c). Lesson: metadata-only physical logging with in-core log buffers. Pitfall: its log format is not block-addressed the way JBD2 is — do not conflate the two layouts. Applied in §32.
  • ZFS ZIL (module/zfs/zil.c). Lesson: an intent log layered on a COW pool, not a circular ring. Pitfall: ZIL replay assumes pool-level COW semantics we do not have. Applied in §32, §35.
  • BTRFS log tree (fs/btrfs/tree-log.c). Lesson: a metadata-only log tree used to accelerate fsync atop a COW filesystem. Pitfall: its tree structure is not a fixed-size ring — do not import its reclamation model directly. Applied in §32.
  • JFS log (fs/jfs/jfs_logmgr.c). Lesson: a database-WAL-flavored design, closer to ARIES than to JBD. Applied in §5 (Books, Gray & Reuter cross-check), §32.
  • NTFS USN journal (Microsoft MSDN Library, NTFS internals documentation). Lesson: a user-space-visible change journal layered atop the metadata journal — a different consumption model than ours. Applied in §32.

RFCs / Specifications

  • IEEE Std 1003.1 (POSIX) — fsync()/fdatasync() semantics. The durability contract we build on top of and whose weaknesses (Pillai 2014) we must not amplify. Applied in §8.5, §26.
  • T10 SBC-3 — SCSI Block Commands, SYNCHRONIZE CACHE. The cache-flush command our BlockDevice::flush() ultimately issues. Applied in §8.5.
  • T13 ATA/ATAPI Command Set — FLUSH CACHE / FLUSH CACHE EXT, FUA bit semantics. The FUA write path our data-flush-before-commit ordering assumes. Applied in §8.5, Phase 3 (§15).
  • NVMe Base Specification — Flush command, Force Unit Access. The modern-device equivalent of the above two; our benchmark assumptions (§4) target NVMe-class devices. Applied in §4, §29.

Glossary (§37) · 35 terms · site-wide glossary

Checkpoint
: declaring a journal entry no longer needed because its writes are durable at their final locations; advances the journal tail (I7, I9).
Circular log / ring
: the fixed-size journal structure; head and tail cursors move through it modulo its size (P2).
Commit record
: the journal record marking a transaction durable; the system's single pivot bit (I1, §11.4).
Crash shape
: one of five named points at which a crash can occur relative to the commit path (§12.8).
CRC32C
: the Castagnoli CRC-32 variant used for all checksums in this layer (ADR-02).
Descriptor record
: the journal record announcing a transaction and listing its block tags (§11.3).
Escape rule
: zeroing a data block's first 4 bytes when they collide with the journal magic, restoring them on read (I11, §13.6).
External journal device
: a journal placed on a block device separate from the filesystem's data device (§20, ADR-10).
fsync
: the POSIX call this layer treats as (and maps BlockDevice::flush() onto) a durability barrier (I13, §8.5).
FUA (force unit access)
: a write flag requesting the device bypass its cache for that write, used as an optional latency optimization in ordered mode (§8.5).
Group commit
: batching multiple transactions into one journal write and one fsync (§14, Hagmann 1987).
Journal
: the circular log holding in-flight transactions, on the same device or an external one (§8.2).
Journal mode
: the consistency mode journaling both data and metadata (§16, I14).
Mode (consistency mode)
: one of journal / ordered / writeback (§8.4).
Ordered mode
: the default consistency mode; data flushed before the metadata commit record (§15, I3).
Recovery
: the mount-time scan-and-replay procedure restoring the journal's committed state to final locations (§18).
Replay
: applying a committed transaction's journaled blocks to their final locations (§18.3, jbd-replay).
Revocation set / revoke record
: the mechanism preventing an older transaction's stale write from overwriting a newer one after a free-and-reallocate (§19, I5).
Superblock (journal)
: the bootstrap block (journal block 0) recovery reads first (§11.5, §11.6).
TxnId
: the monotonic transaction identifier, never reused (I6, §11.1).
Torn write
: a write that started but did not complete before a crash, detected by checksum mismatch (I4, T3).
Transaction
: the unit of durability — a set of block writes committed atomically (§8.1).
Wrap-around
: the journal head passing the start of the ring, subject to the tail never-overwrite discipline (I7, §13.2).
Write amplification
: the ratio of bytes written to the journal plus final locations versus bytes logically written by the caller (M5, §33 item 11).
Write-ahead logging (WAL)
: the discipline of making the log durable before the change it describes touches its final location (§8.3, Mohan 1992).
Checksum coverage
: the exact byte range a given CRC field is computed over; a boundary bug here is FM-11 (§21.6).
Group-commit window
: the bounded accumulation interval during which transactions join a batch before it seals (§14.2, ADR-04).
Checkpoint lag
: the gap, in transactions, between the last committed and the oldest uncheckpointed transaction (jbd_checkpoint_lag_txns, §13.10).
RevokeTable
: the in-memory BTreeMap<BlockId, TxnId> backing the revocation set (§19.2, ADR-22).
ModeStrategy
: the trait abstracting the three consistency modes behind one commit path (§11.9, P4).
SnapshotHook
: the callback pair (before_commit/after_commit) integrating rank-111 snapshots with this layer's commit path (§22.2, ADR-11).
Quiesce-and-rewrite
: the resize/migration strategy of draining in-flight transactions before rewriting the journal region (§22.2, ADR-19).
features_compat/features_incompat/features_ro_compat
: superblock bitmasks gating optional and mount-blocking on-disk features (§11.5, §26).
IRON taxonomy
: Prabhakaran et al.'s classification of how filesystems handle latent disk errors, referenced for T6's detection framing (§5 Papers, §23).
Barrier
: a device-level ordering guarantee (flush/FUA) that a write preceding it is durable before a write following it is issued (§8.5).
