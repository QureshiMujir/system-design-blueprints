1. Goal & Scope

Build a pluggable, crash-consistent block-journaling layer — the JBD2 / XFS-log / ZIL lineage — that sits between a higher-level filesystem (the metadata + data producer) and a raw block device. The layer groups writes into atomic transactions, appends them to a fixed-size circular on-disk log guarded by checksummed descriptor / commit / revoke records, and replays that log deterministically at mount time so every acknowledged write survives an arbitrary power loss or kernel panic. The layer is not a filesystem: it owns no inode namespace, no directory tree, no block allocator. It owns exactly one contract: the mapping from "a set of block writes committed together" to "durable, correctly ordered, recoverable after a crash."

In-scope Phase-0 deliverable (numbered modules/crates):

  1. jbd-core — TxnId/BlockId/JournalRecord/state types (§11).
  2. jbd-block — BlockDevice trait + in-memory backend + crash-injection decorator.
  3. jbd-journal — in-memory circular log, byte-exact record layout (not yet persisted).
  4. jbd-txn — transaction manager: begin_txn / write_metadata / commit_txn / abort_txn.
  5. jbd-commit — single-transaction-per-commit thread (group commit is Phase 2).
  6. jbd-recover — forward-scan recovery producing a RecoveryReport.
  7. jbd-mode-ordered — the one mode-strategy wired at Phase 0.
  8. jbd-conformance — three fixture buckets exercising the above (§12.5).

System boundaries:

  • Provides: atomic multi-block transactions, write-ahead durability, deterministic crash recovery, three consistency modes, group commit, revocation, per-block checksums.
  • Delegates: block allocation, inode/directory semantics, encryption, compression, RAID/erasure coding — owned by the layer above (rank 36, Local File System) or below (rank 47, Block-Device Driver).
  • Does NOT provide: a POSIX filesystem interface, a page-cache layer, a network filesystem protocol, cross-mount application transactions.

Non-goals: general-purpose ACID database semantics (no SQL, no MVCC, no query planner); distributed consensus across journals on different hosts; encryption-at-rest (delegated to a dm-crypt-equivalent layer beneath us); becoming a log-structured filesystem — we journal around fixed final block locations, we do not replace them (contrast in §35).

Deployment model: an in-process Rust library linked into the rank-36 filesystem process, or a standalone jbd daemon fronting a raw block device for out-of-process callers. Single-writer-process per journal; no multi-host sharing of one journal instance.

Target users / operators: filesystem implementers building atop rank 36; SREs operating the resulting filesystem who reach for jbd dump / jbd fsck-journal / jbd replay during an incident.

What later phases unlock: group-commit throughput (§14), the full ordered/journal/writeback triad (§15–17), crash-proof recovery (§18), safe space reclamation under revocation (§19), bandwidth isolation via an external journal device (§20), tamper-evident integrity (§21), and copy-on-write snapshot composition plus online resize (§22).

Recommended language: Rust, edition 2021, toolchain 1.75. Rationale: the commit path is a correctness boundary where ordering bugs are memory-safety-adjacent (replaying a block after its backing allocation changed is a use-after-free in disguise); Rust's ownership model statically forecloses whole classes of concurrent-access bugs in the transaction manager, while std::thread interop cleanly expresses "async everywhere except the synchronous fsync boundary" (ADR-13). Rejected — C: no ownership checking; JBD2's own CVE history includes several use-after-checkpoint bugs this would reintroduce. Rejected — C++: weaker default safety, slower path to Miri-verified unsafe islands. Rejected — Go: GC pauses land on the commit-latency-sensitive path, and there is no #[repr(C)]-equivalent for exact on-disk layout control.

Prerequisites: block-layer fundamentals (queue depth, NCQ, FUA, cache-flush semantics); POSIX fsync/fdatasync semantics and their documented weaknesses (Pillai 2014, §5); write-ahead-logging theory (ARIES, Mohan et al. 1992); the distinction between "durable in the page cache" and "durable on the platter." Familiarity with the Local File System project (rank 36), the Write-Ahead Log project (rank 71), the Block-Device Driver project (rank 47), and the Crash-Recovery Theory project (rank 78) is assumed.

Estimated timeline: Phase 0 in 1–2 weeks; the full 11-phase system in 19 weeks (~4.5 months).

Deferred features (registered in §36): cryptographic journal authentication PhaseDeferred("§21.6"); multi-journal sharding PhaseDeferred("§30"); io_uring submission path PhaseDeferred("§21.7"); persistent-memory (DAX) journal PhaseDeferred("§21.8"); redundant backup superblock PhaseDeferred("§24").

2. Why Build This

A filesystem without a journal cannot be crash-tested honestly. A crash mid-write to an un-journaled FFS-style filesystem leaves a partially updated inode, a partially updated bitmap, and a directory entry that may or may not point at the new inode; the post-crash fsck walks the whole device and infers the most plausible interpretation — and is sometimes wrong. Hagmann's 1987 Cedar paper is the origin of the fix every production filesystem now uses: append a description of the intended change to a log, fsync the log, then perform the change. If the change is half-done after a crash, recovery finishes it from the log; if the log entry is half-done, recovery discards it and the change never happened. One bit — "is the commit record durable?" — decides between those two outcomes (I1, §7).

Everything else in this blueprint — group commit, checksums, revocation, the three-mode triad, an external journal device, snapshot integration — is engineering scaffolding around that one observation. Build the scaffolding wrong and the bit is meaningless; build it right and the filesystem above inherits crash consistency for free.

This is also the design lineage every contemporary storage system descends from or reacts against. ext3 (Tweedie 1998) and ext4 (Mathur et al. 2007) make JBD2 Linux's operational default. XFS (Sweeney et al. 1996; Hellwig 2009) journals metadata only, with a higher-throughput physical log. ZFS's ZIL (Bonwick & Ahrens 2003) and BTRFS's log tree push the same pivot into a copy-on-write world. Reading their source, after this blueprint, is a graduate course in operating-system durability rather than an opaque wall of C.

The engineering muscles this builds: reasoning about crash consistency as a state machine rather than a checklist; deriving throughput/latency trade-offs from first principles instead of copying a tuning guide; designing an on-disk format that is both compact and forward-compatible; writing a recovery path that is the most-tested code, not an afterthought. It cross-links directly to the Write-Ahead Log project (rank 71, shares the commit-record-pivot vocabulary), the Block-Device Driver project (rank 47, the flush() contract we depend on), the Crash-Recovery Theory project (rank 78, the formal model we mechanize), and the Backup-Snapshot project (rank 111, which hooks our commit path, §22).

What Mastery Looks Like

  • Explain, from the commit-record pivot alone, why a transaction is atomic without reading any code (I1, §7; §8.4).
  • Derive the ordered / journal / writeback trade-off triangle from first principles and pick the right mode for a workload (Phase 3–5, §15–17).
  • Design a group-commit window and justify its size from fsync latency and writer fan-in arithmetic (Phase 2, §14.6).
  • Diagnose a stale-replay bug from symptoms alone and name revocation as the fix (Phase 7, §19).
  • Read an unfamiliar journaling filesystem's source (XFS, ZFS ZIL, BTRFS log-tree) and map it onto this blueprint's vocabulary within an hour (§32 Comparative Architecture).
  • Reason about the crash-consistency of a proposed change to the commit path using the five-crash-shape taxonomy (Phase 0, §12.8).
  • Compute recovery time and journal-size sizing from device bandwidth alone (§33 Capacity Model).

Transaction manager (jbd-txn): owns TxnHandle lifetimes, buffers metadata/data blocks per open transaction, enforces I1/I6, hands sealed transactions to the commit thread.

Commit thread + group-commit window (jbd-commit): the sole writer to the journal (I10); batches concurrent transactions inside a bounded window (Phase 2), invokes the active mode strategy's pre-commit hook, writes descriptor + data + commit records, issues one fsync.

Journal — circular log (jbd-journal): fixed-size ring of journal blocks; head is the next-write cursor, tail is the oldest uncheckpointed transaction (I7); superblock at journal block 0 is the sole bootstrap pointer.

Block device (jbd-block): the trust and persistence boundary; a trait implemented by an in-memory backend (tests), a file-backed backend (Phase 1+), and — via rank 47 — a raw device backend. flush() is the only durability primitive the whole layer relies on (I13).

Recovery / replay (jbd-recover, jbd-replay): reads the superblock, builds the revocation set, forward-scans committed transactions, replays their blocks to final locations honoring revokes, and is idempotent under repeated crash-during-recovery (I8).

Five properties recur throughout this document: (1) the journal is a circular log with predictable size and recovery time, never an unbounded append-only file; (2) a transaction is the unit of durability — all-or-nothing, never half-applied; (3) writes do not reach final locations until the commit record is fsync'd — the WAL discipline (§8.3); (4) group commit amortizes one fsync over many concurrent transactions; (5) failures are first-class — the recovery path is the most heavily tested path in the system, not an exotic corner.

6. Design Principles

P1 — The commit record is the pivot. A transaction is durable iff its commit record is fsync'd, checksum-valid, and chained to a valid descriptor. Recovery applies a transaction iff, and only iff, that holds. Violating this collapses I1; every other invariant is downstream of it.

P2 — The journal is a circular log, fixed size. No runtime growth; online resize (§22) is quiesce-and-rewrite, never a stretchy ring. Trade-off: predictable recovery time and write amplification, at the cost of checkpoint-driven backpressure.

P3 — One transaction, one commit record, atomic apply. No half-applied transaction is ever observable by recovery. Violating this reintroduces exactly the fsck-guessing problem journaling exists to remove.

P4 — Three modes, one codebase. journal / ordered / writeback differ only in when data hits its final location relative to the commit record; the transaction manager, journal layout, and recovery code are shared. Violating this (forking the manager per mode) triples the maintenance and testing surface.

P5 — Ordered mode is the default. ext4's default for over a decade; ADR-01 records the rejected journal-default and writeback-default alternatives and the regimes where each wins.

P6 — Group commit is mandatory, not optional. Even a single writer collapses to one fsync per window; there is no "ungrouped" code path to maintain in parallel (§14).

P7 — Checksums everywhere, trust nothing from the device. Every journal block, every descriptor, every commit record carries CRC32C (§21); a mismatch is always treated as a torn write, never as "probably fine."

P8 — Revocation is first-class. A block journaled by an older transaction and later freed-and-reallocated must never be replayed over the newer write; §19 makes this a named record type, not an implicit convention.

P9 — The journal device is pluggable. The transaction manager never assumes same-device placement; §20 makes the external-journal-device case a configuration, not a rewrite.

P10 — Recovery is fast, deterministic, and idempotent. A crash during recovery must be safe to recover again (I8); recovery time must scale linearly with journal size, not with transaction count times journal size.

P11 — The block device is a trait, not a concrete type. Tests run against an in-memory implementation with a crash decorator; production runs file-backed or raw-device. This is what makes deterministic crash-injection testing possible at all (§27).

P12 — No unsafe outside two documented islands. O_DIRECT aligned buffers and the deferred io_uring path are the only unsafe in the codebase; the transaction manager, journal layout, commit thread, and recovery path are 100% safe Rust (ADR-12).

P13 — Recovery is a normal mode of operation, not an exotic corner. Every phase's conformance bucket includes a mount-after-crash case; recovery code is exercised as often as the happy path in CI (§27).

P14 — The commit thread is the sole writer to the journal. Serializing all journal writes through one thread removes an entire class of concurrent-write-ordering bugs at the cost of a single-thread throughput ceiling that group commit (P6) is designed to raise (ADR-08).

8. Domain Model

8.1 Transaction & Handle Model

A transaction is the unit of durability: a caller begin_txns a TxnHandle, adds metadata/data blocks and revoke lists to it, and commit_txns it. The handle is !Send — scoped to one thread to avoid cross-thread aliasing of the in-flight buffer list (§11.8). A transaction moves monotonically through TxnState: Running → Locked → Committing → Committed → Checkpointed, or Running/Locked → Aborted. Locked marks the moment the commit thread claims the transaction for the current group-commit window (§14); Committed marks the moment fsync returns; Checkpointed marks the moment the underlying writeback of every block in the transaction has completed and the journal entry can be reclaimed (I7).

8.2 On-Disk Layout

The journal is a circular sequence of fixed-size blocks: block 0 is the superblock (§11.5); blocks 1..capacity-1 are the ring, holding interleaved descriptor, data, commit, and revoke records (§11.3). A descriptor record announces a transaction and lists (BlockId, JournalBlockId, crc) tuples for the data that follows in subsequent journal blocks. A commit record marks the transaction's durability pivot (I1). A revoke record lists blocks a transaction has freed, instructing recovery to ignore any older transaction's write to those blocks (I5, §19).

8.3 Write-Ahead + Checkpoint Protocol

The WAL discipline (Mohan 1992; Gray & Reuter ch. 8): (1) every block write is first described in the journal; (2) the journal's descriptor + data + commit records are made durable via one fsync; (3) only afterward does checkpointing copy the blocks to their final locations and advance the journal tail (I7, I9). This blueprint is redo-only: the journal never stores an undo image, because a transaction that has not committed has never touched a final location (P1, P3) — there is nothing to undo.

8.5 Barriers, FUA, and Flush Ordering

BlockDevice::flush() (I13) must resolve to a real cache-flush primitive: SCSI SYNCHRONIZE CACHE (T10 SBC-3) or ATA FLUSH CACHE EXT (T13), or the NVMe Flush command. Ordered mode's data-write path additionally may use the FUA bit (force-unit-access) to avoid a second flush round-trip when the device supports it — an ADR-level tuning decision (§9, ADR-07), never a correctness requirement, since a plain write + flush is always sufficient.

8.6 Worked Example — Ordered-Mode Commit

Txn T42 writes metadata block 100 (inode) and data block 500 (file content) in ordered mode. Sequence: (1) data block 500 written to its final location; (2) flush(); (3) descriptor block for T42 written to journal, listing block 100's tag; (4) data record for block 100 written to journal; (5) commit record for T42 written to journal; (6) journal fsync(). Only after step 6 does commit_txn return Ok(TxnId(42)). A crash before step 6 discards T42 entirely on recovery (I1); a crash after step 6 replays block 100 to its final location at recovery, and block 500 is already there from step 1 (I3).

8.7 Malformed-Input Example

A descriptor record whose tag_count field claims 200 tags but whose block only has room for 136 (at 30 bytes/tag in a 4 KiB block, per §11.6) sets the MORE bit and continues in the next journal block; a decoder that does not honor MORE will read 64 tags of garbage past the block boundary. The conformance bucket record_decode (§12.5) fuzzes exactly this boundary and asserts the decoder rejects an inconsistent tag_count/MORE pairing without panicking (I4, H14 no-code — this is a decoding rule, not transcribed logic).

8.8 Failure-Path Example

Txn T7 commits (commit record durable) but the process crashes before checkpointing block 500 to its final location. At the next mount, recovery's forward scan (§18.1) finds T7's commit record, validates its CRC (I4), and replays block 500 from the journal to its final location — the same code path as a routine checkpoint, just triggered at mount instead of in the background. This is the reason recovery is P13 — "a normal mode," not a special one.

11. Core Schema & Types

Signatures only (no bodies), per the No-Code Rule (§4 of the standard). Each type's ownership/mutation/concurrency/persistence/serialization semantics are annotated inline.

11.1 Identifiers

struct TxnId(u64)              // monotonic (I6); durable in superblock; never reused
struct BlockId(u64)            // final-location block number on the data device
struct RecordId(u64)           // identifies one record within a transaction
struct JournalBlockId(u64)     // index within the circular journal ring

const BLOCK_SIZE_DEFAULT: u32 = 4096
const JOURNAL_SIZE_DEFAULT: u64 = 128 * 1024 * 1024   // 128 MiB
const JOURNAL_SIZE_MIN: u64 = 4 * 1024 * 1024         // 4 MiB

Ownership: Copy types, no allocation. Persistence: TxnId/JournalBlockId are durable fields inside JournalSuperblock (§11.5). Concurrency: immutable once assigned.

11.2 JournalMode & TxnState

enum JournalMode { Journal, Ordered, Writeback }         // §8.4
enum TxnState { Running, Locked, Committing, Committed, Checkpointed, Aborted }  // §8.1

Mutation: TxnState transitions monotonically, enforced by jbd-txn (P3, I1); no backward transition is representable. Serialization: JournalMode is durable in the superblock; TxnState is runtime-only, never serialized.

11.3 JournalRecord (on-disk record union)

enum JournalRecord {
    Descriptor { txn: TxnId, sequence: u32, tags: Vec<DescriptorTag>, crc: u32 },
    Data       { txn: TxnId, payload: Bytes },              // == block size
    Commit     { txn: TxnId, committed_at: i64, crc_over_txn: u32 },
    Revoke     { txn: TxnId, blocks: Vec<BlockId>, crc: u32 },
}

struct DescriptorTag { block: BlockId, journal: JournalBlockId, flags: u16, crc: u32 }

mod tag_flags {
    const ESCAPED:  u16 = 1 << 0    // I11
    const LAST_TAG: u16 = 1 << 1
    const MORE:     u16 = 1 << 2    // descriptor continues in next journal block (§8.7)
}

Persistence: byte-exact per §11.6; discriminant byte distinguishes the four kinds. Compatibility: additive-only field growth gated by features_compat/features_incompat in the superblock (§11.5).

11.4 CommitRecord (the pivot, detailed)

struct CommitRecord {
    magic: u32, record_kind: u8, txn: TxnId, committed_at: i64,
    data_block_count: u32, revoke_block_count: u32,
    crc_over_txn: u32,   // CRC32C over descriptor + every data block (I4)
    crc_self: u32,       // CRC32C over the record's own preceding fields
}

Ownership: written once by the commit thread (I10), read many times by recovery/tools; immutable after write. This is the type I1 is defined in terms of.

11.5 JournalSuperblock

struct JournalSuperblock {
    magic: u32, version: u32, block_size: u32, journal_blocks: u64,
    first_block: JournalBlockId, head: JournalBlockId, tail: JournalBlockId,
    last_committed: TxnId, oldest_uncheckpointed: TxnId, mode: JournalMode,
    features_compat: u32, features_incompat: u32, features_ro_compat: u32,
    uuid: [u8; 16], crc: u32,
}

Persistence: journal block 0; the sole bootstrap read at mount (§18.1). Mutation: updated, and fsync'd, strictly after every commit record it references is durable (I9).

11.7 Byte Layout — Descriptor, Commit, Revoke Records

Descriptor (one block):    0:1 discriminant=0x01 | 4:8 txn | 12:4 sequence
                            | 16:4 tag_count | 20:.. tags (30B each) | last:4 crc
Tag (30 bytes):             0:8 block | 8:8 journal | 16:2 flags | 18:4 crc | 22:8 pad
Commit (one block):         0:1 discriminant=0x03 | 4:8 txn | 12:8 committed_at
                            | 20:4 data_block_count | 24:4 revoke_block_count
                            | 28:4 crc_over_txn | 32:4 crc_self | 36:.. reserved
Revoke (one block):         0:1 discriminant=0x04 | 4:8 txn | 12:4 block_count
                            | 16:.. blocks (8B each) | last:4 crc

A transaction whose revoke list exceeds one block's capacity emits multiple Revoke records sharing the same txn (§19.2).

11.8 JournalService, BlockDevice, TxnHandle (public API surface)

trait JournalService: Send + Sync {
    fn begin_txn(&self) -> Result<TxnHandle>
    fn write_metadata(&self, txn: &TxnHandle, block: BlockId, payload: Bytes) -> Result<()>
    fn write_data(&self, txn: &TxnHandle, block: BlockId, payload: Bytes) -> Result<()>
    fn revoke_blocks(&self, txn: &TxnHandle, blocks: &[BlockId]) -> Result<()>
    fn commit_txn(&self, txn: TxnHandle) -> Result<TxnId>
    fn abort_txn(&self, txn: TxnHandle) -> Result<()>
    fn wait_checkpoint(&self, txn: TxnId) -> Result<()>
    fn recover(&self) -> Result<RecoveryReport>
}

trait BlockDevice: Send + Sync {
    fn block_size(&self) -> u32
    fn capacity_blocks(&self) -> u64
    fn read(&self, block: BlockId, buf: &mut [u8]) -> Result<()>
    fn write(&self, block: BlockId, buf: &[u8]) -> Result<()>
    fn flush(&self) -> Result<()>                          // I13, the sole durability primitive
    fn discard(&self, block: BlockId, count: u64) -> Result<()>   // default no-op
}

struct TxnHandle {
    id: TxnId, opened_at: Instant,
    journal: Arc<dyn JournalService>,
    blocks: Mutex<TxnBlocks>,          // !Send by construction (§8.1)
}
struct TxnBlocks {
    metadata: IndexMap<BlockId, Bytes>,
    data:     IndexMap<BlockId, Bytes>,
    revoked:  IndexSet<BlockId>,
}

Concurrency: JournalService implementations are Send + Sync; TxnHandle is confined to one thread. Compatibility: the trait is the conformance boundary (§27) — any implementation passing the conformance suite is a valid JournalService.

11.9 ModeStrategy

trait ModeStrategy: Send + Sync {
    fn name(&self) -> JournalMode
    fn pre_commit_data_writes(&self, txn: &TxnBlocks) -> ModeAction
    fn data_in_journal(&self) -> bool
}
enum ModeAction {
    WriteAndFlush(Vec<(BlockId, Bytes)>),     // ordered
    JournalAlongside(Vec<(BlockId, Bytes)>),  // journal
    None,                                      // writeback
}

Mutation: stateless strategy objects; selected once at mount, referenced by the commit thread on every commit_txn (P4).

    txns_scanned: u64, txns_replayed: u64, txns_skipped: u64,

}

Persistence: not durable itself; returned to the caller of recover() and logged/emitted as metrics (§25.1).

12.1 Objectives

12.2 Detailed Implementation Steps

Implement jbd-block's BlockDevice trait (§11.8, I13), an in-memory backend, and a deterministic crash decorator that drops writes past a configurable point. Implement jbd-journal as an in-memory ring using the exact §11.6/11.7 byte layout — not a Vec<Transaction> placeholder (P2). Implement jbd-txn's begin_txn/write_metadata/ commit_txn/abort_txn (I6 monotonic TxnId allocation). Implement jbd-commit as a single std::thread writing one descriptor+data+commit triple per transaction (I10; group commit is Phase 2, §14). Implement jbd-recover's forward scan (§18.1 preview) and jbd-replay. Wire jbd-mode-ordered as the only mode strategy (§11.9).

12.3 Deliverable

make test passes an integration test running the "Hello, journal" smoke test (§12.2 above); make conformance reports 3 buckets Pass, 9 Deferred (§12.5); ADR files for ADR-01, ADR-02, ADR-03, ADR-05, ADR-06, ADR-08, ADR-12, ADR-14, ADR-15, ADR-18 (§9) exist under docs/adr/.

12.4 Acceptance Criteria

make test exit code 0 with ≥1 passing integration test named hello_journal; the smoke test asserts report.txns_replayed == 1 after a simulated crash between commit and writeback; make conformance JSON shows "pass": 3, "fail": 0, "deferred": 9; zero unsafe blocks outside crates not yet implemented.

12.5 Conformance Fixtures

core_types — round-trips every §11 type through (de)serialization, rejects invalid discriminants. journal_basic — fresh journal accepts begin/write/commit/recover. hello_journal — the canonical fixture: 1024-block device, 128-journal-block ring, ordered mode, txn writing blocks 10/11/12, commit, crash before writeback, remount, recover, assert blocks 10/11/12 equal the committed payload.

12.6 Pitfalls

The crash decorator must be deterministic — same input sequence + same trigger point ⇒ same post-crash state, or the entire in-memory test strategy (P11) is worthless. Cutting corners on the byte-exact ring in favor of a Vec<Transaction> makes the Phase 1 on-disk transition a rewrite instead of a backend swap. Shipping group commit early (before Phase 2) adds complexity the smoke test does not need yet.

12.7 Performance Concerns

None load-bearing at this phase — in-memory only. Establish the benchmark harness shape (jbd-bench) now so Phase 1+ benchmarks slot in without redesign.

12.8 Edge Cases

The five crash shapes every later phase's tests parametrize over: (1) pre-write — txn opened, no journal writes yet, transaction does not exist post-recovery; (2) mid-data — some data blocks journaled, no descriptor yet, orphaned data reclaimed by the filesystem above; (3) pre-commit — descriptor+data durable, no commit record, transaction discarded; (4) post-commit-pre-flush — commit record written, fsync in flight, either outcome (applied or discarded) is correct and the caller must tolerate both; (5) post-flush — commit record durable, transaction applied on recovery. §12.5's hello_journal fixture covers shape 3 explicitly; later phases (§18) cover the rest exhaustively.

12.9 Failure Analysis

A non-deterministic crash decorator is the single failure that invalidates every later phase's crash tests — detect it by running the same fixture 100× and diffing post-crash images; any diff blocks the phase from closing. A byte-inexact in-memory ring (built as a Vec instead of the real layout) surfaces as a Phase 1 integration failure, not a Phase 0 one — the containment is catching it via a §11.6 round-trip test before Phase 1 begins.

12.10 Operational Notes

No production deployment at this phase. jbd-bin stub supports --version/--help only. BUILD_PLAN.md records Phase-0: complete; every crate not yet implemented carries a stub docstring naming its home phase section (§13 through §22) so BUILD_PLAN.md can be generated mechanically from the source tree.

13. Phase 1 — On-Disk Journal Layout & Superblock

13.1 Objectives

Persist the Phase-0 in-memory journal to a real block device with zero new transaction semantics — only persistence, using the exact §11.6/11.7 byte layout already exercised in-memory (P2).

13.2 Detailed Implementation Steps

Implement FileBackedBlockDevice in jbd-block (I13's flush() maps to fsync_all). Implement jbd-proto's bincode encode/decode with fixed-width integers (ADR-14) — variable- length encoding would make record sizes drift with values, making the recovery scan probabilistic instead of deterministic (I4). Implement the escape rule (I11) in jbd-proto: a data block whose first 4 bytes equal the journal magic is zeroed at write with the ESCAPED tag flag set, restored at read. Implement wrap-around discipline in jbd-journal: before any write, check whether [head, head+n) intersects [tail, head) (I7); if so, block until checkpoint advances tail. Implement the checkpoint thread that scans from tail forward and advances it once every metadata block of a transaction is durable at its final location, recording the advance in the superblock (I9).

13.3 Deliverable

A file-backed journal that survives kill -9 on the daemon process and reads back an identical byte image; the checkpoint thread visibly advances tail in jbd dump output.

13.4 Acceptance Criteria

A 1,000-transaction write-then-restart test finds every committed txn and discards every uncommitted one (0 false positives, 0 false negatives); a wrap-around test confirms in-place overwrites never corrupt an uncheckpointed transaction; an escape-rule test confirms a magic-colliding data block round-trips byte-identical through write→read.

13.5 Conformance Fixtures

superblock_round_trip — encode/write/read/decode produces an identical JournalSuperblock (§11.6). wrap_around — journal-full + checkpoint scenarios (corpus: conformance/corpora/wrap-around/). escape_rule — magic-colliding payload fixtures (corpus: conformance/corpora/record-decode/escape/).

13.6 Pitfalls

The superblock must be fsync'd after the commit records it points at (I9) — writing it first creates a window where recovery trusts a pointer to a non-durable commit, replaying a phantom transaction. The escape rule is easy to write wrong: validate the post-unescape CRC, not the on-disk (escaped) bytes, or every escaped block spuriously fails checksum validation (I4). bincode's default variable-length integers must be overridden to fixed-width (ADR-14) or record sizes become non-deterministic.

13.7 Performance Concerns

The wrap-around block-until-checkpoint path (I7) is the source of journal-full latency spikes (M7); a too-small journal makes this the bottleneck of the entire filesystem above. Checkpoint I/O competes with foreground commit I/O for device queue depth — the checkpoint thread should throttle under high commit load rather than starve it.

13.8 Edge Cases

A transaction whose descriptor tags overflow one block continues via the MORE flag (§11.3) — a decoder that ignores MORE reads garbage past the block boundary (§8.7). A crash exactly at the superblock-update boundary (I9) must leave the prior superblock valid — never a torn one. A journal sized below JOURNAL_SIZE_MIN (4 MiB, §4) must be rejected at format time, not discovered as a livelock at runtime.

13.9 Failure Analysis

A torn superblock write is the highest-severity failure this phase introduces: detection is the superblock's own CRC (§11.6); recovery falls back to refusing mount rather than guessing (§18.1 step 2). A checkpoint-thread crash mid-advance leaves tail stale but never corrupt — the next mount's recovery re-derives the correct state from the journal contents, not from the checkpoint thread's in-memory position (I8).

13.10 Operational Notes

jbd_journal_used_fraction and jbd_checkpoint_lag_txns (§25.1) are the two metrics an operator watches for journal-full risk. docs/runbook/journal-full.md documents the force-checkpoint-then-compact remediation path.

14. Phase 2 — Group Commit

14.1 Objectives

Batch concurrent transactions into one journal write and one fsync, raising the single-writer-thread throughput ceiling ADR-08 accepted in Phase 0/1 (P6).

14.2 Detailed Implementation Steps

Implement jbd-group-commit's window manager: a bounded accumulation window (default 5 ms, ADR-04) during which arriving transactions join the current batch, up to max_batch (256). A batch becomes one interleaved sequence of descriptors + data blocks terminated by one commit record whose crc_over_txn (I4) covers every descriptor and data block in the batch — the JBD2 choice (§9, ADR rationale) over one-commit-per-transaction, which would lose the throughput benefit because each commit record is itself an fsync boundary. Implement minimum-batch-size early exit: a solo committer does not pay the full window latency.

14.3 Deliverable

A commit thread that batches N concurrent commit_txn calls arriving within the window into one journal write, and returns each caller's Result<TxnId> only after the batch's one fsync completes (I1 applies per-transaction within the batch, I12 to the batch as a whole).

14.4 Acceptance Criteria

64 concurrent writers each committing a 4-block transaction at 1 ms intervals sustain ≥100,000 txn/s on an NVMe-class device (M3, §29); a window-close test asserts the batch contains exactly the transactions that arrived within the 5 ms window; a crash-mid-batch test asserts every transaction in an uncommitted batch is discarded on recovery (I12).

14.5 Conformance Fixtures

group_commit (corpus: conformance/corpora/group-commit/) — concurrent-writer scenarios at N ∈ {1, 8, 64, 256}, asserting one fsync per window and correct batch membership.

14.6 Pitfalls

A sleeping thread hides bugs for months — use std::thread::park_timeout with an explicit timeout, never spin on Instant::now(). The commit-record CRC must cover every byte recovery will read for the entire batch (I4) — a bug where it covers only the first transaction's descriptor surfaces only under torn-write tests, which are easy to skip in CI. A buggy caller submitting a duplicate TxnId must be rejected cleanly at submit time (I6), not crash the commit thread.

The arithmetic (Hagmann 1987; §2): with fsync latency L (≈200 µs NVMe), window W (5 ms), and N writers each at rate r (1 txn/ms), an ungrouped commit thread is bounded at 1/L ≈ 5,000 txn/s regardless of N — writers share one journal and cannot commit concurrently. With grouping, the batch at window close is ≈N·W·r transactions; one fsync durably commits the whole batch, so throughput is (N·W·r)/W = N·r — linear in N up to the max_batch ceiling. At N=64, this is 320 txns/fsync; at L=200 µs the commit thread manages ~5,000 fsyncs/s, i.e. ~1.6M txn/s algorithmic ceiling — the device's journal write bandwidth is the practical limiter (§33).

14.7 Performance Concerns

Window tuning is workload-dependent: sub-ms-latency callers want a 1 ms window (ADR-04 rejected-choice column); throughput-only callers want 20–50 ms. The commit_throughput benchmark (§29) emits the curve so operators tune with data, not guesswork.

14.8 Edge Cases

A transaction arriving just after the batch seals must wait for the next window, never be silently dropped into the sealed one. max_batch overflow under sustained pressure must seal and commit immediately rather than grow unbounded. A single-writer workload must not pay the full window latency (early-exit, §14.2).

14.9 Failure Analysis

A crash between "batch sealed" and "commit fsync returns" discards the entire batch (I12) — every writer in it observes commit_txn return an error or a timeout and must retry; this is the origin of the "either outcome is correct" contract in crash shape 4 (§12.8).

14.10 Operational Notes

jbd_group_commit_batch_size (histogram) is the primary throughput-health metric; a batch size collapsing toward 1 under concurrent load indicates a window misconfiguration or a device-latency regression, both alertable (§25.2).

15. Phase 3 — Ordered Mode

15.1 Objectives

Implement ordered mode correctly and make it the default (P5, ADR-01): every data block referenced by a transaction's metadata must be on disk before that transaction's commit record is written (I3).

15.2 Detailed Implementation Steps

Implement OrderedMode: ModeStrategy (§11.9) returning ModeAction::WriteAndFlush for every data block in the transaction. In commit_txn, the mode strategy's action executes before the descriptor/commit path: issue all data writes to the device, then one flush() (I13); only after that flush returns does the metadata commit path (descriptor + commit + fsync) proceed. This ordering is the data-write barrier that makes the "metadata points at uninitialized bytes" anomaly (Prabhakaran 2005) structurally impossible (I3, P1).

15.3 Deliverable

A jbd-mode-ordered crate wired as the mount default; a crash-consistency proof by inspection of the commit path's write ordering (§8.6 worked example).

15.4 Acceptance Criteria

A crash-injected test at every line of the commit path asserts the post-recovery state is always one of the two allowed states (§15.6); ordered-mode commit latency ≤2× the underlying device's flush latency (two pipelined flushes per commit, M1).

15.5 Conformance Fixtures

mode_ordered (corpus: conformance/corpora/mode-ordered/) — asserts I3 holds under every crash-injection point in the commit path.

15.6 Pitfalls

Flushing after every individual data write, instead of once after all of them, kills throughput — issue writes asynchronously, await all, flush once. Two transactions writing overlapping BlockIds must respect per-block recency: the data-flush phase must leave the most recent writer's bytes in place before that writer's commit, not an arbitrary interleaving. Ordered mode is not an intra-transaction data-ordering guarantee — callers needing that must fsync themselves (§17.1 draws the same boundary for writeback).

15.7 Performance Concerns

The data flush is where ordered mode pays its cost relative to writeback (§17); pipelining multiple in-flight data writes before the single flush is the primary lever (§29, data_flush_latency benchmark).

15.8 Edge Cases

A transaction with zero data blocks (metadata-only) skips the data-flush phase entirely — no spurious flush call. A data write that fails mid-flight (device EIO) aborts the transaction before any commit record is written (I3 is never violated because the commit path never starts).

15.9 Failure Analysis

Crash before the data flush completes: no commit record was ever attempted, transaction does not exist post-recovery (§8.6, crash shape 1/2). Crash between data-flush-complete and commit-record-fsync: commit record absent, transaction discarded, data blocks become orphans reclaimed by the filesystem above at next allocation (§8.6, crash shape 3). Crash after commit-fsync: fully durable, nothing to recover beyond replay of the metadata already in the journal (§8.6, crash shape 5).

15.10 Operational Notes

jbd_ordered_flush_seconds (histogram, I3's row in §7) is the metric that isolates ordered mode's specific cost; a --mode=ordered mount is the default and requires no operator opt-in flag, unlike writeback (§17.10).

16. Phase 4 — Journal Mode

16.1 Objectives

Implement journal mode: both metadata and data pass through the journal, giving the strongest guarantee in the triad at the cost of doubled write amplification (I14, §8.4).

16.2 Detailed Implementation Steps

Implement JournalModeStrategy: ModeStrategy (§11.9) returning ModeAction::JournalAlongside — data blocks are journaled with the same descriptor-tag + escape-rule (I11) treatment as metadata. Final-location writes for data happen only at checkpoint time, after the transaction is durable in the journal (§8.3), identical to the metadata checkpoint path already built in Phase 1 (§13.2).

16.3 Deliverable

A jbd-mode-journal strategy producing a journal that, on recovery, restores both data and metadata to the last committed state — used by callers needing byte-exact post-crash file size (ADR-01's "when the rejected choice wins" column).

16.4 Acceptance Criteria

A crashed transaction in journal mode replays byte-identical data and metadata versus the pre-crash committed state; journal-mode throughput ≤50% of ordered-mode throughput on a 4 KiB random-write workload (M5 write-amplification target, ≤2.05×).

16.5 Conformance Fixtures

mode_journal (corpus: conformance/corpora/mode-journal/) — asserts full data+metadata recovery fidelity.

16.6 Pitfalls

Data blocks in journal mode go through the same escape rule (I11) as metadata — omitting it for "just data" reintroduces the magic-collision misparse bug. The journal fills far faster under journal mode (every data byte is journaled, not just metadata) — the same wrap-around backpressure path (I7, §13.2) applies but triggers proportionally sooner; operators must size the journal larger for journal-mode workloads (§4 sizing table).

16.7 Performance Concerns

Every data byte is written twice — once to the journal, once to final location (M5). This is the explicit price of the strongest guarantee (§8.4); the benchmarks (§29) quantify it so the trade-off is a measured decision, not folklore.

16.8 Edge Cases

A data block larger than one journal block (not applicable at the default 4 KiB block-size parity, but relevant if the higher-level filesystem uses a larger logical block) must be chunked across multiple journal blocks with the same descriptor-tag chaining as any oversized descriptor (§13.8).

16.9 Failure Analysis

A torn write to a journaled data block is detected by the same per-block CRC as a metadata block (I4) — no special-casing. A crash mid-checkpoint (some but not all data blocks written to final locations) is safe: the journal still holds every block, and recovery simply re-replays from the (idempotent, I8) forward scan.

16.10 Operational Notes

journal mode is opt-in (--mode=journal); the runbook documents the 2× space/bandwidth cost explicitly so operators do not enable it by habit (contrast with ordered's no-opt-in default, §15.10).

17. Phase 5 — Writeback Mode

17.1 Objectives

Implement writeback mode: metadata-only journaling, the fastest and weakest mode in the triad, admitting the stale/leaked-data anomaly by design (I14).

17.2 Detailed Implementation Steps

Implement WritebackModeStrategy: ModeStrategy (§11.9, I14) returning ModeAction::None — no data tracking, no pre-commit data writes. The higher-level filesystem is responsible for writing data directly via BlockDevice::write outside the transaction's data-block tracking. Gate the mount option behind an explicit --unsafe-writeback confirmation flag in jbd-cli (§17.6) so the anomaly documented in Prabhakaran 2005 is never enabled by accident.

17.3 Deliverable

A jbd-mode-writeback strategy achieving the highest throughput of the triad; a runbook page (docs/runbooks/writeback-mode.md) documenting the security implication in explicit terms.

17.4 Acceptance Criteria

Writeback-mode throughput ≥1.5× ordered-mode throughput on a 4 KiB random-write workload; a crash test asserts metadata durability holds while explicitly not asserting data durability — the mode's contract, documented as such rather than treated as a bug.

17.5 Conformance Fixtures

mode_writeback (corpus: conformance/corpora/mode-writeback/) — asserts metadata-only durability and documents (does not "fix") the data anomaly window.

17.6 Pitfalls

A user who mounts writeback without reading the documentation will eventually observe the stale-data anomaly — the --unsafe-writeback flag requirement (§17.2) is the guardrail, not a suggestion. Writeback mode is not equivalent to ext4's data=writeback,nobarrier — the journal fsync barrier (I13) for metadata remains mandatory; only data ordering is dropped, never metadata durability (I14).

17.7 Performance Concerns

The anomaly window is exactly the interval between a data write being issued and it reaching the platter (§17.8) — writeback mode's speed comes from never waiting on that interval before committing metadata.

17.8 Edge Cases

The canonical anomaly: file metadata claims size 1 MiB durable, but the data bytes at offset 0..1 MiB may be whatever previously occupied that block — including bytes from a prior, unrelated, deleted file. This is the security-relevant case the runbook (§17.3) calls out explicitly; it is the reason ext3 deprecated writeback as its default (Prabhakaran 2005).

17.9 Failure Analysis

A crash in the anomaly window (§17.8) leaves metadata durable and data indeterminate; there is no journal-side detection of this because writeback mode, by construction, never tracked the data write (I14). The only mitigations are application-level (the caller's own fsync) or choosing ordered/journal instead.

17.10 Operational Notes

Writeback is opt-in only, requiring --mode=writeback --unsafe-writeback; jbd-cli rejects a bare --mode=writeback with a pointer to the runbook (§17.6), a deliberate asymmetry with ordered mode's default-on status (§15.10).

18. Phase 6 — Recovery & Replay

18.1 Objectives

Build the single most important code path in the layer: the one whose correctness is the union of every prior phase's correctness (P10, P13, I8).

18.2 Detailed Implementation Steps

Implement the recovery algorithm in jbd-recover: (1) read the superblock (§11.6), validate its CRC — refuse mount on failure; (2) start at oldest_uncheckpointed; (3) build the revocation set by scanning forward and collecting every Revoke record's blocks-and-txn pairs (I5, full detail §19); (4) re-scan forward, and for each transaction with a valid commit record (I4), apply its data blocks to final locations, skipping any block revoked at or before that transaction's id; (5) flush the device; (6) update and fsync the superblock's last_committed/oldest_uncheckpointed (I9); (7) accept new transactions. Implement jbd-replay's Replayer (§11.10's RecoveryReport is its output type). Implement torn-write detection as a checksum-validating reader (I4): every journal block's CRC is verified against its descriptor tag or commit-record crc_over_txn; a mismatch discards the owning transaction.

18.3 Deliverable

A recovery routine producing a deterministic RecoveryReport (§11.10); a state-machine model of recovery (§18.8) that is restartable at every step except the final "accept writes" transition.

18.4 Acceptance Criteria

A recovery-time benchmark confirms a 128 MiB journal (32,768 blocks at 4 KiB) recovers in ≤0.25 s on a 500 MB/s device, and a 1 GiB journal in ≤5 s (M4, §33 derivation); a torn-write test simulating a crash at every byte offset within a journal block produces the correct state at every offset; a double-recovery ("crash during recovery") test produces byte-identical post-images across two independent runs (I8).

18.5 Conformance Fixtures

torn_writes (corpus: conformance/corpora/torn-writes/) — partial writes at arbitrary offsets. recovery_idempotence — the double-recovery scenario. recovery-scan (corpus: conformance/corpora/recovery-scan/) — journal images at every recoverable state, one per crash shape (§12.8).

18.6 Pitfalls

Every prior phase's bugs surface here first — test every crash shape imaginable, then the ones not imagined. The two-pass scan (revocation set first, replay second) is the safe algorithm; a one-pass lazy-revocation variant is faster but subtle enough to defer until the two-pass version is shipped and proven (P10). Recovery must be idempotent by construction (I8) — a crash mid-recovery re-enters at SuperblockRead (§18.8) and must reach the same final state.

18.7 Performance Concerns

Recovery is two full passes over the uncheckpointed region of the journal — O(journal size), never O(transaction count × journal size). The recovery_throughput_under_load benchmark (§29) asserts this linear scaling explicitly at N ∈ {10, 100, 1000, 10000} pending transactions.

18.8 Edge Cases — Recovery as a State Machine

BuildRevocationSet, ReplayForward, FlushDevice, and UpdateSuperblock are all restartable — re-running any of them from a crash produces the same result (I8). Only AcceptWrites is non-restartable: once live, a new crash is the next mount's recovery problem (§18.9 diagnostic covers exactly this transition boundary).

18.9 Failure Analysis

Diagnosing recovery divergence (a non-deterministic recovery bug — the worst class): (1) capture the journal image at mount time; (2) run recovery, capture the post-image; (3) re-run recovery on the captured pre-image against a fresh device copy; (4) diff the two post-images. A nonzero diff is a recovery bug (FM-9, §24); the recovery_idempotence conformance bucket (§18.5) asserts this diff is always zero in CI.

18.10 Operational Notes

jbd_recovery_seconds (histogram) is the primary mount-time-SLO metric; jbd dump --pre-recovery (§20) is the operator's first diagnostic step on any recovery-divergence report (docs/runbooks/replay-divergence.md).

19. Phase 7 — Revocation Records

19.1 Objectives

Harden the revocation path Phase 6 introduced: guarantee a block freed and reallocated is never overwritten by an older, still-present journal entry's replay (I5, P8).

19.2 Detailed Implementation Steps

Emit a Revoke record whenever a block transitions from in-use to free with residual risk that an older transaction in the journal still holds a write for it — in practice, every unlink/truncate from the filesystem above, as part of the same transaction as the metadata change (I12 applies to this pairing too). Implement RevokeTable in jbd-recover as a BTreeMap<BlockId, TxnId> (ADR-22) tracking the highest revoking TxnId per block; is_revoked(block, txn) answers txn <= revoking_txn. Coalesce the table at checkpoint: once a transaction is checkpointed, every revoke older than it is implicitly satisfied (any older write to that block is already overwritten on disk), bounding table growth.

19.3 Deliverable

A revoke-record type wired through commit_txn and recover; a bounded, coalescing RevokeTable.

19.4 Acceptance Criteria

A free→reallocate→write→crash→recover test asserts the post-recovery state is the new content, never the stale one (the exact scenario in §19.5); revoke_table_scaling benchmark confirms O(R log R) build time at R ∈ {1, 100, 10⁴, 10⁶} revoke records, ≤1 s at R=10⁶ (M9).

19.5 Conformance Fixtures

revocation (corpus: conformance/corpora/revocation/): txn T1 writes block B (commits); B is freed and reallocated; txn T2 revokes B and rewrites it (commits); T1's descriptor survives in the not-yet-overwritten portion of the journal (a wrap-around artifact, §13.2); without revocation, recovery replaying T1 after T2 would undo T2's write — this fixture asserts the revoke table prevents exactly that (I5).

19.6 Pitfalls

A missing revoke is the single most insidious bug class in the layer (P8): recovery silently restores stale data, the filesystem looks healthy, and the corruption surfaces only when a user reads bytes that now belong to a deleted file (T7, §23). The revoke table can grow unbounded under sustained delete pressure absent coalescing (§19.2) — bound it with a high-water mark that forces an early checkpoint.

19.7 Performance Concerns

RevokeTable::add/is_revoked are O(log R) (BTreeMap, ADR-22); the build pass during recovery is O(R log R) total (M9). Coalescing at checkpoint keeps R bounded by recently-freed-block churn rather than lifetime delete volume.

19.8 Edge Cases

A block revoked by two different transactions keeps only the highest TxnId (§19.2's add semantics) — recovery only needs the most recent revoking boundary, not history. A revoke list exceeding one journal block's capacity spans multiple Revoke records sharing one txn (§11.7).

19.9 Failure Analysis

A torn write to a revoke record itself is detected by its own CRC (I4) exactly like any other record kind; a discarded (torn) revoke record means recovery may under-revoke — this is why §19.6 calls exhaustive testing (the §19.5 fixture family, plus §23's chaos bucket) mandatory rather than best-effort.

19.10 Operational Notes

jbd_revoke_table_size (gauge, I5's telemetry row) is the metric an operator watches for delete-heavy workload pressure; a sustained climb without checkpoint-driven drops indicates a stuck checkpoint thread (cross-reference jbd_checkpoint_lag_txns, §13.10).

20. Phase 8 — External Journal Device

20.1 Objectives

Support placing the journal on a separate block device from the filesystem's data, removing the same-device write-bandwidth tax (P9, ADR-10).

20.2 Detailed Implementation Steps

Extend JournalingLayer::mount to accept an optional journal-device path; the transaction manager holds two BlockDevice handles (data, journal) and is otherwise unaware which placement is active (P9). Add a features_compat superblock flag EXTERNAL_DEVICE (§11.5); a mount that finds the flag set but no external device path supplied must refuse to mount rather than silently half-mount. Implement jbd-cli's resize-journal and migrate-journal commands (§22.3 builds on this same dual-device plumbing for online migration).

20.3 Deliverable

A --journal-device mount option; jbd dump/jbd fsck-journal both work transparently against either placement.

20.4 Acceptance Criteria

An external-journal mount writing 1,000 transactions confirms the data device holds only final-location state and the journal device holds only journal records; a test that removes the journal device mid-mount asserts a clean mount failure (not a silent half-mount); external-journal mount overhead ≤10 ms versus same-device (M8).

20.5 Conformance Fixtures

external_journal (corpus: conformance/corpora/external-journal/ — reuses the group-commit and mode-ordered corpora against the dual-device configuration) — asserts end-to-end parity with same-device placement.

20.6 Pitfalls

Losing the journal device after mount but before checkpoint leaves the data device in an inconsistent state with no local recovery path — the documented remediation (docs/runbooks/external-journal-loss.md) is --no-recover plus the filesystem-above's own fsck, never a silent auto-repair. An external journal device below 4 MiB gives the group-commit window (§14) no room to amortize (§4).

20.7 Performance Concerns

External placement removes journal-write/data-write device contention (§13.7's checkpoint contention no longer shares queue depth with commits); the win is workload-dependent and measured, not assumed (§29 benchmark methodology, §20.4's M8).

20.8 Edge Cases

A migration from same-device to external mid-operation (§22.2) is a superset of this phase's mount-option change plus a copy step — this phase ships the mount-time plumbing; §22 ships the live migration.

20.9 Failure Analysis

A journal-device failure mid-commit is indistinguishable, from the transaction manager's point of view, from any other device I/O error on the journal BlockDevice — the same error-propagation path as a same-device failure (I13); operational severity is higher because there is no fallback placement.

20.10 Operational Notes

docs/runbooks/external-journal-loss.md is the on-call reference; the runbook explicitly states the data-loss scope (unflushed transactions only, per I1/I9) so the on-call engineer does not over- or under-estimate the blast radius.

21. Phase 9 — Full Checksumming

21.1 Objectives

Layer CRC32C checksums onto every surface the layer reads or writes, so corruption is never silently trusted from the device (P7, I4).

21.2 Detailed Implementation Steps

Implement jbd-checksum wrapping hardware-accelerated CRC32C (x86-64 SSE4.2 crc32q, aarch64 PMULL, falling back to software crc32fast). Wire per-surface coverage: superblock (entire block minus its own CRC field, §11.6), descriptor (header+tags), commit record (fields + crc_over_txn over the whole transaction), each data block (stored in its descriptor tag), revoke record (entire record). Every checksum is verified on read; a mismatch is always classified as a torn write (I4), never a warning-and-continue.

21.3 Deliverable

Typed checksum wrapper types (SuperblockCrc, DescriptorCrc, CommitCrc, DataBlockCrc) used identically across jbd-proto, jbd-recover, and jbd-cli fsck-journal.

21.4 Acceptance Criteria

A single-bit-flip mutation test on any journal block is detected and the owning transaction discarded (100% detection at this fault class); checksum CPU overhead ≤5% of journal throughput on a hardware-accelerated host (M6); per-block checksum cost ≤200 ns per 4 KiB block on x86-64 with SSE4.2.

21.5 Conformance Fixtures

checksum_failures (corpus: conformance/corpora/torn-writes/checksum/) — single-bit-flip mutations at every checksummed surface, asserting 100% detection.

21.6 Pitfalls

A checksum covering the wrong byte range is worse than no checksum — test boundary cases explicitly: a flip at the first covered byte, the last covered byte, and the byte just outside coverage (must not spuriously trigger). Hardware CRC32C uses a specific polynomial; using the older CRC32 polynomial breaks compatibility with the checksum semantics documented here (ext4 JBD2 has used CRC32C since 2010; this blueprint follows suit). Cryptographic authentication (HMAC-SHA-256) against an active adversary is out of scope here — PhaseDeferred("§21.6"), registered in §36, because the threat model (§23) excludes an adversary who can forge CRC32C-valid records at will.

21.7 Performance Concerns

CRC32C's hardware path is the reason it was chosen over SHA-256 (ADR-02) — the benchmark (checksum_overhead, §29) is the CI-gated proof that the cost stays under M6's 5% ceiling on supported hardware.

21.8 Edge Cases

A host without SSE4.2/PMULL falls back to software CRC32C — checksum_overhead must be re-measured on that path and may legitimately exceed M6's target, with the mount log recording which implementation is active. A checksum computed over a buffer that includes padding bytes must zero the padding deterministically, or two logically-identical records can produce different CRCs.

21.9 Failure Analysis

A checksum mismatch is always terminal for that record — the owning transaction is discarded (I4); there is no "probably fine" path. A systemic mismatch across many unrelated transactions is a signal to escalate beyond torn-write handling toward T3/T4/T6 (device-level failure, §23) rather than continue treating each occurrence as isolated.

21.10 Operational Notes

jbd_torn_writes_total (counter) crossing zero at any rate above baseline noise is an alert condition (§25.2); jbd fsck-journal's JSON report enumerates every checksum surface's pass/fail state per record for postmortem use.

22. Phase 10 — Snapshot Integration & Online Resize

22.1 Objectives

Wire the rank-111 Backup-Snapshot project's copy-on-write hook into the commit path (ADR-11), and support resizing or migrating the journal device without unmounting (P2's "resize is quiesce-and-rewrite, never a stretchy ring," ADR-19).

22.2 Detailed Implementation Steps

Implement SnapshotHook in jbd-snapshot: before_commit/after_commit callbacks invoked around every commit_txn, recording (block, pre-image) into the snapshot's COW map before the transaction's writes land. A snapshot's consistency point is defined as the TxnId of the most recently committed transaction at the moment the snapshot request lands (I6's monotonic ordering makes this well-defined); the layer rejects a snapshot request arriving strictly between begin_txn and commit_txn on another thread, forcing snapshot points to be transaction boundaries. Implement the online-resize algorithm: quiesce new begin_txn calls, drain in-flight transactions to checkpoint, write the new journal region (grow or shrink), update and fsync the superblock to point at it, resume. Implement migration (same-device ↔ external, §20) as resize plus a copy-then-repoint step, with rollback to the original journal if the new device fails mid-copy.

22.3 Deliverable

A SnapshotHook trait + SnapshotIntegration impl; jbd-cli resize-journal --size 256MiB and jbd-cli migrate-journal /dev/sdc1 commands.

22.4 Acceptance Criteria

A snapshot-then-10-commits test confirms the COW map holds every pre-image of every written block, and a subsequent restore is byte-identical to the pre-snapshot state; a resize from 128 MiB to 256 MiB loses zero transactions; a migration to a new device confirms durability on the new device post-migration; snapshot-hook overhead ≤5% added commit latency (M12).

22.5 Conformance Fixtures

snapshot_integration (corpus: conformance/corpora/snapshot/) — snapshot/COW-map/restore scenarios. Resize/migration fixtures live alongside external_journal (§20.5), parametrized by grow/shrink/migrate.

22.6 Pitfalls

The snapshot hook must not block the commit thread — submit the COW write asynchronously and let the commit proceed; a synchronous COW write on the hot path reintroduces exactly the per-fsync cost group commit (§14) exists to amortize away. A resize-shrink that cannot accommodate the currently uncheckpointed transactions must abort before quiesce, never mid-quiesce with data at risk. A migration whose new device fails mid-copy must roll back to the original journal as the source of truth, discarding the partial copy.

22.7 Performance Concerns

The quiesce-drain window (§22.2) is the filesystem-unavailable window during resize/ migration — bounded by in-flight-transaction checkpoint time, typically milliseconds to seconds; this is the operational cost quiesce-and-rewrite (ADR-19) accepts in exchange for resize-correctness simplicity over a live stretchy ring.

22.8 Edge Cases

A snapshot request arriving mid-transaction (between begin_txn and commit_txn on another thread) is rejected, not silently deferred (§22.2) — silent deferral would make the snapshot's consistency point ambiguous. A resize request arriving while a migration is already in flight must be rejected or queued, never interleaved (both are quiesce-exclusive operations).

22.9 Failure Analysis

A snapshot-hook crash mid-COW-write leaves the snapshot's COW map incomplete for that block — detected by the snapshot integration's own completeness check at restore time (out of this layer's direct scope, but the after_commit callback's failure must propagate as a transaction-level error, never a silent gap). A quiesce that never drains (a stuck transaction) is a livelock — bounded by a configurable quiesce timeout that aborts the resize/migration and resumes normal operation.

22.10 Operational Notes

docs/runbooks/ gains resize/migration procedures cross-referencing §20's external-device runbook; the rank-111 snapshot project's own FINAL_BLUEPRINT cross-references this phase's SnapshotHook API and per-transaction COW guarantee (ADR-11).

26. Compatibility & Versioning

Wire/storage format: versioned via JournalSuperblock.version (§11.5); features_compat / features_incompat / features_ro_compat bitmasks (JBD2-style) gate optional and mount-blocking features additively — a mount encountering an unknown features_incompat bit refuses to mount rather than guess. Schema evolution: new JournalRecord fields are additive-only, gated by a compat flag, per ADR-14. API stability: JournalService and BlockDevice (§11.8) are the conformance-suite-verified contract (§27); a breaking change to either is a major-version bump. Deprecation policy: a deprecated mount option or record kind remains readable for at least two major versions before removal. SemVer: the crate workspace follows SemVer; on-disk format compatibility is tracked independently via the superblock version field, not coupled to crate version numbers. Rolling-upgrade guarantee: an old-version binary must refuse to mount a newer-features_incompat journal cleanly (never silently corrupt it) — verified in superblock_round_trip (§13.5) extended with a version-mismatch case.

29. Performance Engineering

30. Scalability Analysis

What stays constant: per-block CRC cost (O(1) per block, hardware-accelerated, P7); commit thread count (always 1 per journal, I10 — the named bottleneck). What grows: recovery time (O(journal size), M4); revoke-table build time (O(R log R) in revoke-record count, M9); group-commit batch size (O(N·W·r) in writer count, up to max_batch, §14.6). Named bottlenecks in order: (1) the single commit thread's fsync rate (ADR-08) — the primary ceiling, raised by group commit (P6) but never eliminated; (2) journal device write bandwidth once group commit saturates fsync rate (§14.6's arithmetic); (3) checkpoint throughput relative to commit rate (§13.7) — if checkpoint falls behind, backpressure (I7) throttles new transactions. Horizontal scaling: not supported within one journal (I10 is a hard single-writer constraint); the practical lever beyond one journal is PhaseDeferred ("§30") multi-journal sharding — multiple independent journal regions, each with its own commit thread, registered in §36. Vertical scaling: faster device (lower fsync latency L, §14.6) directly raises the algorithmic throughput ceiling; more CPU cores do not help the commit thread itself (single-threaded by design, ADR-08) but do help checksum computation (P7, parallelizable across blocks) and checkpoint I/O concurrency. Coordination overhead: zero cross-journal coordination exists today (out of scope, §1); multi-journal sharding (deferred) would need to define per-shard vs. cross-shard transaction semantics before it could ship. The practical ceiling today is single-device fsync bandwidth (§33's capacity model quantifies it); the lever beyond that ceiling is external-journal placement (§20) or, longer-term, multi-journal sharding.

31. Mental Models & First Principles

MM1 — "The commit record is a coin flip resolved once." Before the commit fsync returns, the transaction's fate is undetermined; after, it is permanently one of two values. Predicts: any code path that treats a transaction as "probably committed" before fsync returns is a bug. Bug class without it: assuming write() returning Ok implies durability. Applies at I1, §8.6.

MM2 — "A journal is a state machine with two clocks: head and tail." Head advances on write, tail advances on checkpoint; the gap between them is exactly the uncheckpointed window. Predicts journal-full behavior without needing to trace code. Bug class without it: sizing a journal by transaction count instead of by head-tail gap under peak load. Applies at I7, §13.7.

MM3 — "fsync is a promise about a device, not about your code." The layer's entire correctness rests on BlockDevice::flush() meaning what it says (I13); no amount of application-level cleverness fixes a lying device. Bug class without it: debugging "recovery bugs" that are actually device firmware bugs (T5, FM-4). Applies at §8.5, §23.

MM4 — "Ordered mode buys causality between data and metadata, not intra-data ordering." Two data writes within one transaction have no ordering guarantee relative to each other, only relative to the commit record. Bug class without it: assuming ordered mode makes an application's own multi-write sequencing atomic. Applies at §15.6.

MM5 — "Revocation is a tombstone with a deadline, not a delete." A revoke record does not erase history from the journal; it tells recovery to ignore a specific stale write past a specific TxnId boundary. Bug class without it: expecting the journal to physically remove revoked entries immediately (it does not — checkpoint coalescing does, later, §19.2). Applies at I5, §19.2.

MM6 — "Group commit trades latency variance for throughput, bounded by a window." No free lunch: the price of amortizing fsync cost across writers is that some writers wait up to the full window. Bug class without it: tuning the window down to zero "for safety" and being surprised throughput collapses to the single-transaction ceiling (§14.6). Applies at §14.7.

MM7 — "Recovery is not exceptional, it is the third mode of normal operation." Alongside "append" and "checkpoint," "recover" is a first-class, constantly-tested code path, not a disaster-only corner (P13). Bug class without it: under-testing recovery relative to the happy path, the exact failure §16's motivating audit (BLUEPRINT_STANDARD.md §13.5) found in other blueprints. Applies at §18, §27.

MM8 — "Checksums convert corruption into loud failure, not into silent success." A CRC mismatch is always a discard, never a warning-and-continue (P7). Bug class without it: "fixing" a checksum failure by disabling the check instead of investigating the device. Applies at I4, §21.9.

ZFS/ZIL: rejected the "journal + fixed final locations" model entirely in favor of copy-on-write everywhere, with the ZIL as a narrow synchronous-write accelerator rather than the primary durability mechanism (the txg pipeline is) — the niche where that wins is workloads wanting full end-to-end checksumming and snapshot-everywhere semantics as a first-class property, not an add-on (§35 covers this as a rejected alternative architecture).

BTRFS/log tree: like ZFS, built on COW, but keeps a lightweight metadata-only log tree specifically to accelerate fsync without waiting for a full COW transaction commit — the niche where that wins is workloads with frequent small synchronous metadata updates (mail servers, VM images) atop a COW filesystem that would otherwise pay a full-tree-commit cost per fsync.

33. Back-of-Envelope Capacity Model

Chained from §4's constraint table; every number below shows its formula.

  1. Journal blocks at default size: journal_size / block_size = 128 MiB / 4 KiB = 32,768 blocks (§11.6's journal_blocks field, §18.4).
  2. Recovery scan time at default size: journal_size / device_bandwidth = 128 MiB / 500 MB/s ≈ 0.25 s (M4's basis, §18.4).
  3. Recovery scan time at 1 GiB: 1024 MiB / 500 MB/s ≈ 2.05 s, well inside the ≤5 s M4 target — the extra headroom absorbs the second (replay) pass.
  4. Group-commit batch size @ N=64, W=5 ms, r=1/ms: N · W · r = 64 · 5 · 1 = 320 transactions per fsync (§14.6).
  5. Fsync rate given L=200 µs: 1 / L = 1 / 200µs = 5,000 fsyncs/s (the commit thread's physical ceiling, §14.6).
  6. Algorithmic throughput ceiling: batch_size × fsync_rate = 320 × 5,000 = 1,600,000 txn/s — bounded in practice by journal write bandwidth, not this arithmetic (§14.6, §30).
  7. Journal write bandwidth ceiling in transactions/sec: device_bandwidth / (avg_txn_journal_bytes) = 500 MB/s / (4 blocks × 4 KiB) ≈ 30,500 txn/s at 4-block transactions — this, not item 6, is the real ceiling for typical workloads.
  8. Memory for revoke table at R=10⁶ entries: R × (sizeof(BlockId) + sizeof(TxnId)) = 10⁶ × 16 bytes = 16 MiB — comfortably inside the §4 64 MiB per-journal ceiling.
  9. Checksum throughput cost: overhead_fraction × device_bandwidth = 0.05 × 500 MB/s = 25 MB/s of "spent" bandwidth budget at the M6 ceiling.
  10. FD budget per mount: 1 (data device) + 1 (optional external journal device) = 2 FDs (§4).
  11. Write amplification in journal mode: (journal_bytes + final_location_bytes) / final_location_bytes ≈ (1 + 1 + descriptor_overhead) ≈ 2.05× (M5) — the 0.05 is descriptor/commit-record overhead relative to payload size at 4 KiB blocks.
  12. Journal-full backpressure onset: at 90% fill (§4's M7 trigger point) with a 128 MiB journal, the uncheckpointed region is 0.9 × 128 MiB ≈ 115 MiB — sized against expected checkpoint throughput to bound the M7 stall at ≤50 ms.

37. Glossary

  • Checkpoint: declaring a journal entry no longer needed because its writes are durable at their final locations; advances the journal tail (I7, I9).
  • Circular log / ring: the fixed-size journal structure; head and tail cursors move through it modulo its size (P2).
  • Commit record: the journal record marking a transaction durable; the system's single pivot bit (I1, §11.4).
  • Crash shape: one of five named points at which a crash can occur relative to the commit path (§12.8).
  • CRC32C: the Castagnoli CRC-32 variant used for all checksums in this layer (ADR-02).
  • Descriptor record: the journal record announcing a transaction and listing its block tags (§11.3).
  • Escape rule: zeroing a data block's first 4 bytes when they collide with the journal magic, restoring them on read (I11, §13.6).
  • External journal device: a journal placed on a block device separate from the filesystem's data device (§20, ADR-10).
  • fsync: the POSIX call this layer treats as (and maps BlockDevice::flush() onto) a durability barrier (I13, §8.5).
  • FUA (force unit access): a write flag requesting the device bypass its cache for that write, used as an optional latency optimization in ordered mode (§8.5).
  • Group commit: batching multiple transactions into one journal write and one fsync (§14, Hagmann 1987).
  • Journal: the circular log holding in-flight transactions, on the same device or an external one (§8.2).
  • Journal mode: the consistency mode journaling both data and metadata (§16, I14).
  • Mode (consistency mode): one of journal / ordered / writeback (§8.4).
  • Ordered mode: the default consistency mode; data flushed before the metadata commit record (§15, I3).
  • Recovery: the mount-time scan-and-replay procedure restoring the journal's committed state to final locations (§18).
  • Replay: applying a committed transaction's journaled blocks to their final locations (§18.3, jbd-replay).
  • Revocation set / revoke record: the mechanism preventing an older transaction's stale write from overwriting a newer one after a free-and-reallocate (§19, I5).
  • Superblock (journal): the bootstrap block (journal block 0) recovery reads first (§11.5, §11.6).
  • TxnId: the monotonic transaction identifier, never reused (I6, §11.1).
  • Torn write: a write that started but did not complete before a crash, detected by checksum mismatch (I4, T3).
  • Transaction: the unit of durability — a set of block writes committed atomically (§8.1).
  • Wrap-around: the journal head passing the start of the ring, subject to the tail never-overwrite discipline (I7, §13.2).
  • Write amplification: the ratio of bytes written to the journal plus final locations versus bytes logically written by the caller (M5, §33 item 11).
  • Write-ahead logging (WAL): the discipline of making the log durable before the change it describes touches its final location (§8.3, Mohan 1992).
  • Checksum coverage: the exact byte range a given CRC field is computed over; a boundary bug here is FM-11 (§21.6).
  • Group-commit window: the bounded accumulation interval during which transactions join a batch before it seals (§14.2, ADR-04).
  • Checkpoint lag: the gap, in transactions, between the last committed and the oldest uncheckpointed transaction (jbd_checkpoint_lag_txns, §13.10).
  • RevokeTable: the in-memory BTreeMap<BlockId, TxnId> backing the revocation set (§19.2, ADR-22).
  • ModeStrategy: the trait abstracting the three consistency modes behind one commit path (§11.9, P4).
  • SnapshotHook: the callback pair (before_commit/after_commit) integrating rank-111 snapshots with this layer's commit path (§22.2, ADR-11).
  • Quiesce-and-rewrite: the resize/migration strategy of draining in-flight transactions before rewriting the journal region (§22.2, ADR-19).
  • features_compat/features_incompat/features_ro_compat: superblock bitmasks gating optional and mount-blocking on-disk features (§11.5, §26).
  • IRON taxonomy: Prabhakaran et al.'s classification of how filesystems handle latent disk errors, referenced for T6's detection framing (§5 Papers, §23).
  • Barrier: a device-level ordering guarantee (flush/FUA) that a write preceding it is durable before a write following it is issued (§8.5).
