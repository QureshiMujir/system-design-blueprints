Decisions (§9) · 22 ADRs

ADR-01

Default consistency mode

Chosen

ordered

Rejected

journal-default; writeback-default

When the rejected choice is right

journal-default wins for regulatory/database workloads needing byte-exact post-crash file size (§16.3); writeback-default wins for build systems that re-derive outputs (§17.3)

Why: matches 15 years of ext4 operational experience (Prabhakaran 2005)

ADR-02

Checksum algorithm

Chosen

CRC32C

Rejected

SHA-256; no checksum

When the rejected choice is right

SHA-256 wins under an active-adversary threat model (T1, T2) — deferred (§21.6)

Why: hardware-accelerated on x86-64/aarch64, sufficient for accidental-corruption detection at this rate

ADR-03

Journal structure

Chosen

fixed-size circular log

Rejected

append-only growing file; B-tree log (BTRFS-style)

When the rejected choice is right

append-only wins when journal size truly cannot be bounded in advance (rare; e.g. archival WAL)

Why: predictable size + recovery time (§4)

ADR-04

Group-commit window

Chosen

5 ms default, 0–50 ms configurable

Rejected

fixed 1 ms; fixed 20 ms; no window

When the rejected choice is right

1 ms wins for sub-ms commit-latency-sensitive callers (application-level fsync at the DB layer)

Why: JBD2's proven default; §14.6 shows the throughput curve

ADR-05

BlockDevice abstraction

Chosen

trait + in-memory/file-backed/raw impls

Rejected

concrete struct only

When the rejected choice is right

a concrete struct wins only for a throwaway prototype with no crash-injection testing requirement — not applicable to this project

Why: in-memory backend is the only sane way to test torn writes without destroying real disks

ADR-06

Phase-0 journal persistence

Chosen

in-memory first, on-disk in Phase 1

Rejected

on-disk from day one

When the rejected choice is right

on-disk-first wins if the team has already solved the algorithm elsewhere and wants persistence risk retired first

Why: proves the algorithm before the disk introduces new failure modes

ADR-07

Commit path execution model

Chosen

synchronous fsync on a dedicated std::thread

Rejected

io_uring async submission from day one

When the rejected choice is right

io_uring wins once the kernel floor is ≥5.10 everywhere and the win is benchmark-proven (§21.7 deferred)

Why: fsync is physically synchronous; pretending otherwise is a category error

ADR-08

Journal writer concurrency

Chosen

one commit thread per journal

Rejected

multiple concurrent writer threads

When the rejected choice is right

multiple writers win only with multiple independent journal regions (§30 multi-journal sharding, deferred)

Why: serialized writer removes ordering bugs; group commit absorbs the throughput need

ADR-09

Revocation encoding

Chosen

separate Revoke record type

Rejected

revoke flags folded into the descriptor

When the rejected choice is right

folding in wins only for an extremely space-constrained journal format (not this one)

Why: keeps descriptor schema simple; recovery logic cleanly separable

ADR-10

External journal device

Chosen

Phase 8 (§20) opt-in feature

Rejected

same-device-only, no external option

When the rejected choice is right

same-device-only wins for single-spindle/single-namespace deployments where isolation buys nothing

Why: same-device is the simpler default; external device is a bandwidth-isolation feature

ADR-11

Snapshot integration

Chosen

Phase 10 hook into rank-111 (§22)

Rejected

no integration; snapshot reimplements its own logging

When the rejected choice is right

a fully separate snapshot log wins only if snapshot consistency requirements are looser than ours

Why: snapshots and journaling interact non-trivially at the commit boundary

ADR-12

unsafe scope

Chosen

confined to O_DIRECT buffers + deferred io_uring

Rejected

unsafe allowed anywhere for performance

When the rejected choice is right

broader unsafe wins only under extreme, benchmark-proven allocator pressure absent here

Why: 100% safe transaction manager/journal/recovery is worth the small perf cost

ADR-13

Async runtime split

Chosen

tokio for optional remote-journal RPC; std::thread for commit

Rejected

tokio everywhere including commit

When the rejected choice is right

full-tokio wins if the commit path is moved to io_uring (§21.7, deferred)

Why: fsync blocks; forcing it onto an async executor risks stalling the whole runtime

ADR-14

On-disk record encoding

Chosen

bincode + serde, fixed-width ints, discriminant byte

Rejected

JSON; protobuf

When the rejected choice is right

protobuf wins if cross-language journal readers become a requirement (not planned)

Why: byte-exact, versioned, forward-compatible decoders at low CPU cost

ADR-15

Per-block vs per-transaction integrity

Chosen

per-block CRC32C in descriptor tags

Rejected

per-transaction Merkle root

When the rejected choice is right

a Merkle root wins if partial-transaction integrity proofs must be shared with a third party

Why: Merkle root is expensive to build/verify; per-block CRC catches every torn write at lower cost

ADR-16

Observability stack

Chosen

OpenTelemetry tracing + Prometheus metrics

Rejected

logs only; custom metrics format

When the rejected choice is right

a bespoke format wins only inside an org with an existing non-Prometheus stack

Why: industry-standard, pull-based metrics fit the on-call workflow (§25)

ADR-17

Build reproducibility

Chosen

sccache + Nix flake dev shell

Rejected

plain cargo build, no pinning

When the rejected choice is right

plain cargo wins for a single-maintainer prototype with no reproducibility requirement

Why: reproducible builds across maintainer machines (§28)

ADR-18

License

Chosen

Apache-2.0

Rejected

MIT; GPL-2.0

When the rejected choice is right

GPL-2.0 wins if the project must live in-tree with the Linux kernel itself

Why: permissive, patent-grant clause suits a systems library meant for broad reuse

ADR-19

Online resize strategy

Chosen

quiesce-and-rewrite

Rejected

live stretchy ring

When the rejected choice is right

a stretchy ring wins only if sub-millisecond resize windows are a hard requirement (not ours)

Why: operationally proven (matches JBD2 resize); a stretchy ring is conceptually simpler but brittle under concurrent checkpoint

ADR-20

BlockDevice::flush() granularity

Chosen

whole-device flush, byte-granular write

Rejected

per-region/per-extent flush

When the rejected choice is right

per-extent flush wins on some enterprise SANs with cheap partial-barrier support (device-specific optimization, not assumed)

Why: coarser flush makes ordered mode's "data before commit" guarantee inexpressible

ADR-21

Testing philosophy

Chosen

deterministic crash-injection simulator as the primary correctness oracle

Rejected

relying on real-hardware power-cut testing only

When the rejected choice is right

real power-cut testing wins as a final pre-release validation pass, kept secondary to the simulator during day-to-day development (§27)

Why: real power-cut testing is slow, non-reproducible, and cannot enumerate every byte offset

ADR-22

Revoke-table backing structure

Chosen

BTreeMap<BlockId, TxnId>

Rejected

hash map; sorted vector

When the rejected choice is right

a hash map wins only if range-coalescing at checkpoint is dropped entirely from the design — not the case here (§19.2)

Why: ordered iteration needed for coalescing at checkpoint; O(log R) lookups are fast enough (M9)

35. Alternative Architectures (Roads Not Taken)

A1 — Log-structured filesystem (no separate journal; the log is the filesystem).

Show the original text diagram
[ writer ] -> [ append-only log segments ] -> [ segment cleaner ]
                         |
                         v
                 [ imap: inode -> segment,offset ]

Regime where it wins: write-heavy workloads on media with poor random-write performance (the original LFS motivation, Rosenblum & Ousterhout 1992, was spinning disks; it resurfaced for flash FTLs). Real system: the original Sprite LFS, and conceptually f2fs on Linux. Rejected here because it replaces the entire storage layout, not just the durability mechanism (§1's scope is a journaling layer, not a filesystem) — and segment cleaning (garbage collection) introduces its own latency-spike failure mode this blueprint does not want to own.

A2 — Shadow-paging / copy-on-write, no separate journal at all.

Show the original text diagram
[ writer ] -> [ new blocks (COW) ] -> [ new root committed atomically ]
                                              |
                                     (old root still valid until commit)

Regime where it wins: workloads wanting snapshot-everywhere and full-tree checksumming as first-class, not bolted on (exactly ZFS's and BTRFS's pitch, §32). Real system: ZFS, BTRFS. Rejected here per ADR-01's rationale and §1's non-goals: this project's contract is "journal around fixed final locations" for a filesystem that already owns its own allocator and inode store (rank 36) — retrofitting COW into that model is a different, larger project.

A3 — Soft updates (ordered in-place metadata writes, no log).

Show the original text diagram
[ writer ] -> [ dependency-ordered in-place writes ] -> [ no replay needed ]
                         |
                (write B only after A, tracked via dependency graph)

Regime where it wins: workloads where the write-twice cost of journaling (M5) is unacceptable and CPU budget for dependency tracking is available (McKusick et al., FreeBSD FFS). Rejected here: dependency-graph tracking is algorithmically more complex than the commit-record pivot (I1) and does not compose as cleanly with group commit (§14) or an external journal device (§20) — the trade this blueprint makes explicitly favors a simpler, more testable correctness argument over avoiding write-twice cost.

A4 — Application-level journaling (WAL owned by the caller, filesystem is a blob store).

Show the original text diagram
[ application ] -> [ app-level WAL ] -> [ raw writes via O_DIRECT, fsync by app ]

Regime where it wins: databases that already implement their own WAL (e.g. via O_DIRECT) and treat the filesystem purely as byte storage — exactly the writeback-mode use case this blueprint documents (§17.3) rather than rejects outright. Rejected as the only mode because most callers of rank 36 do not want to implement their own crash consistency — the whole point of this layer is to make that unnecessary by default (ordered mode, ADR-01).
