Project Number: 234

Project Name: Certificate Authority / PKI Infrastructure

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, in Rust, a production-grade Public Key Infrastructure: a hierarchical certificate authority comprising an offline root CA, one or more online issuing (intermediate) CAs, a registration authority (RA) validating CSRs and identity, a validation authority (VA) publishing CRLs and serving OCSP (with TLS 1.3 stapling support per section 4.4.2.1 of RFC 8446), an ACME (RFC 8555) automated-issuance endpoint, a certificate-path-building and RFC 5280 section 6 path-validation engine, Certificate Transparency (RFC 6962) log submission, and the audit/compliance instrumentation a real CA must carry to withstand a WebTrust-for-CAs audit. All private-key material is custodied behind a PKCS#11 HSM boundary; the system issues policy-gated, CT-logged, RFC 5280-conformant X.509v3 certificates and manages their full lifecycle (issuance, activation, renewal, revocation, expiry).

Phase-0 deliverable (crate/service architecture):

  1. pki-asn1 — minimal ASN.1/DER encode-decode primitives (own codec, ADR-02)
  2. pki-types — core domain types: Certificate, Csr, Crl, OCSP request/response, Sct, error taxonomy (§11)
  3. pki-hsm — PKCS#11 key-custody boundary and KeyHandle abstraction
  4. pki-root — offline root CA CLI + key-ceremony procedure (air-gapped)
  5. pki-ca — online issuing/intermediate CA signing pipeline
  6. pki-ra — registration authority: CSR intake, identity/domain validation
  7. pki-policy — issuance policy engine (profiles, constraints, quotas)
  8. pki-path — certificate-path building + RFC 5280 section 6 validation
  9. pki-crl — CRL/delta-CRL generator and publisher
  10. pki-ocsp — OCSP responder (RFC 6960) + stapling-artifact production
  11. pki-acme — ACME server (RFC 8555): account/order/authorization/challenge/finalize
  12. pki-ct — Certificate Transparency submitter, SCT collection (RFC 6962)
  13. pki-audit — append-only, hash-chained (tamper-evident) audit log
  14. pki-store — certificate/metadata database layer
  15. pki-lint — certificate-profile linter (zlint-style rule engine)
  16. pki-cli — operator tooling (issuance, revocation, ceremony playback)
  17. pki-conformance — NIST PKITS + zlint conformance harness (CI gate)

System boundaries:

  • Provides: root/intermediate CA hierarchy, CSR validation, policy-gated issuance, X.509v3 leaf/intermediate issuance, renewal, revocation (CRL+OCSP), path building/validation, ACME automated issuance, CT submission, HSM-backed signing, an audit trail.
  • Delegates: raw private-key storage and signing to a PKCS#11 HSM — this system never persists key material outside the KeyHandle abstraction (§11); DNS/HTTP challenge infrastructure for ACME dns-01/http-01 to the requester's own infrastructure; TLS termination and cipher-suite negotiation to the consuming service.
  • Does NOT provide: a TLS stack, a browser trust-store submission process, boot-time chain-of-trust verification, general secrets management, or IAM.

Non-goals (sibling contrasts, named):

  • Not TLS-Handshake (project 48): that project consumes certificates issued here and performs path validation at connection time inside a live handshake. This project is the issuing and lifecycle-management authority — it never negotiates a TLS session.
  • Not Secure Boot + PKI Chain (project 308, still open): that project is a boot-time chain of trust (firmware → bootloader → kernel signature verification). This project's chain is network-issuance-time (RA validates identity, CA signs, VA/OCSP/CRL serve revocation status over the network). Different threat model, different validity windows, different custody model.
  • Not a browser trust store: no root-program compliance program, no cross-signing negotiation with browser vendors (the Threat Model, §24, and ADR-24 discuss why real CAs care regardless).
  • This project's three load-bearing concerns, stated once and referenced everywhere: (1) the trust hierarchy and key custody (offline root, HSM boundary — P1, I4); (2) the issuance policy engine (P2, I3); (3) revocation freshness (P4, I4, I9). Everything else is scaffolding around those three.

Trust-hierarchy model: offline root CA (air-gapped, signs only intermediate certificates in witnessed ceremonies) → online issuing/intermediate CA(s) (network-connected, sign leaf certificates and CRLs, HSM-backed) → leaf certificates (server, client, code-signing, per IssuingProfile).

Deployment model: air-gapped root-CA workstation (no NIC, ceremony-only boot cycle); online RA/CA/VA/OCSP-responder/ACME-endpoint services in a clustered deployment behind a management-plane mTLS boundary; HSM either an on-prem PKCS#11 device or a cloud HSM with a PKCS#11 shim.

Users/operators: security engineers (ceremony custodians, m-of-n key holders), platform/SRE teams (online CA operations), compliance/audit teams (WebTrust evidence collection), automated clients (ACME-speaking services).

What later phases unlock: cross-signing support, PQC-hybrid certificate experiments, CRLite-style browser-push revocation, delegated/federated RA topology.

Recommended language: Rust. Rationale: memory safety without GC pauses for a long-running signing daemon; strong ownership semantics for key-material handling and zeroization; mature der/x509-cert- adjacent ecosystem for cross-checking a from-scratch codec; predictable latency tail for OCSP p99; strong FFI for PKCS#11 vendor SDKs; a mature async runtime (Tokio) for the online services. Rejected languages: Go — GC pauses complicate OCSP p99 latency and there is no compiler-enforced zeroization-on-drop equivalent to Rust's Zeroize trait, a real gap when handling key material — Go remains the right call for a low-security-sensitivity CLI wrapper around this system, e.g. a metrics-scraping sidecar. Java — JVM warm-up and GC pause tail latency is unsuitable for the OCSP SLA, and JCE-provider fragmentation across PKCS#11 vendors adds integration risk — Java is still the correct choice for EJBCA-style enterprise deployments that must integrate with an existing Java-shop identity stack. C / C++ — memory-safety risk directly inside the ASN.1/DER parser, historically the largest CVE source in PKI software (OpenSSL's CVE history) — C remains correct for a memory-constrained embedded HSM firmware target where Rust's runtime is unavailable.

Prerequisites: X.509/ASN.1/DER encoding; public-key cryptography (RSA, ECDSA, EdDSA); TLS handshake mechanics; distributed systems (queueing, backpressure); relational-database transactional semantics; the Linux security model (namespaces, seccomp); the PKCS#11 session model; threat modeling; supply-chain security.

Timeline: Phase 0 (skeleton + ASN.1/DER + CI): 3 weeks. Phases 1–4 (HSM boundary, root ceremony, intermediate issuance, leaf issuance): 10 weeks. Phases 5–7 (path validation, CRL, OCSP+stapling): 8 weeks. Phases 8–10 (ACME, CT, revocation lifecycle/audit): 9 weeks. Phase 11 (conformance/chaos/perf hardening): 4 weeks. Full system: ≈ 8 months.

Deferrals:

  • PhaseDeferred("§36") — decentralized web-of-trust mode (no hierarchical CA) — a research spike, not built.
  • PhaseDeferred("§36") — CRLite-style browser-push revocation distribution (A3).
  • PhaseDeferred("§27") — PQC-hybrid certificate signing (ML-DSA co-signature) — awaiting a ratified CA/Browser Forum Baseline-Requirements PQC profile.
  • PhaseDeferred("§37") — delegated/federated RA topology across trust domains.

2. Why Build This

  • Trust-anchor engineering: the hardest unrecoverable-failure class in security infrastructure — a wrong root decision is not undoable (DigiNotar, 2011).
  • ASN.1/DER as an attack surface: historically the largest CVE source in PKI software (OpenSSL parser CVEs) — forces defensive-parsing discipline from line one.
  • Policy-before-cryptography discipline: separating authorization from the signing act itself (P2).
  • Revocation is provably hard at internet scale — direct, first-hand encounter with the CRL/OCSP/short-lived-certificate tradeoff space (Ellison & Schneier's critique, §32).
  • Key-custody engineering: HSM/PKCS#11 boundary design, m-of-n ceremonies, zeroization guarantees.
  • Protocol-implementation discipline across six real RFCs simultaneously (5280, 8555, 6960, 6962, 2986, 5652) — forces interoperability thinking, not toy-example thinking.
  • Append-only, tamper-evident audit-log engineering — the compliance backbone of every regulated system.
  • Distributed-systems concerns under a hard security constraint: backpressure against a physically rate-limited HSM signer.

Historically foundational to: HTTPS, mTLS service meshes, code signing, secure email, VPNs, container/artifact signing, the CT-ecosystem monitoring stack.

Engineering muscles built: defensive parsing, protocol interoperability, cryptographic lifecycle management, audit-grade observability, security-first architecture, dual-control workflow design, deterministic-encoding engineering, failure-containment design.

Sibling/related systems: TLS-Handshake (48) — the consumer performing live path validation; Secure Boot + PKI Chain (308) — the boot-time analogue of the same trust-anchor problem; the public CT-monitor ecosystem; SPIFFE/SPIRE workload-identity systems.

Calibration value: materially upgrades capability in security architecture, protocol-compliance engineering, cryptographic-lifecycle reasoning, and audit/compliance-oriented system design — the actual day job of an engineer at a WebTrust-audited CA.

Offline Root CA (pki-root): signs only intermediate-CA certificates, exclusively during a witnessed key ceremony (§8, Phase 2/§14). Never network-connected; the air-gap boundary is the outermost trust boundary in the system (I4).

Root HSM / key-custody boundary: the root private key exists only inside a PKCS#11 token; it is never exported in usable form (P1, I4). The Ceremony Manager coordinates m-of-n custodian authentication before any signing operation is invoked.

Ceremony Manager: scripts and audio/video-records the ceremony procedure (§8), enforces m-of-n quorum, and produces the signed ceremony log consumed by the audit pipeline.

Online Issuing CA (pki-ca): the online trust boundary. Consumes validated IssuanceRequests from the RA, evaluates them against the Policy Engine's PolicyVerdict, and drives the Issuing HSM to produce signatures over canonical TbsCertificate bytes (P5). Horizontally scalable at the request-intake layer; cryptographically serialized per signing key at the HSM layer (P10).

Registration Authority (pki-ra): parses and validates CSRs (RFC 2986), authenticates the requester, validates domain/identity control (independently of ACME's own challenge-validation for ACME-sourced requests), and forwards a CertificateRequest to the Policy Engine. Never touches raw key material.

Policy Engine (pki-policy): deterministic, versioned evaluation of SAN scope, EKU scope, TTL bounds, tenant isolation, and issuance quotas against an IssuingProfile (P2). Produces a PolicyVerdict that must exist before any signing call (I3).

ACME Server (pki-acme): RFC 8555 account/order/authorization/challenge/finalize state machine; performs its own http-01/dns-01 domain-control validation before handing a validated order to the RA/Policy path.

CT Submitter (pki-ct): submits every issued certificate (or its precertificate) to ≥2 independent CT logs (RFC 6962) and records the returned SCTs before the certificate is released to the requester (P3, I9).

Certificate Database (pki-store): durable, transactional metadata store — issuance records, revocation state, policy-decision linkage, CT/SCT linkage. Certificates themselves may be blob-stored; metadata stays relational.

Audit Log (pki-audit): append-only, hash-chained event stream; every state-changing operation writes here before it is considered committed (P8, I2).

CRL Publisher (pki-crl) and OCSP Responder (pki-ocsp): the Validation Authority function. CRL Pub emits base/delta CRLs (RFC 5280 section 5) on a fixed cadence; the OCSP Responder answers per-certificate status queries (RFC 6960) and produces pre-signed responses consumable for TLS 1.3 stapling (RFC 8446 section 4.4.2.1). Both read revocation state from the Certificate Database and never write to it directly (I9).

6. Design Principles

P1 — Offline root isolation. The root private key never touches a network-connected system; it signs only intermediates, only inside a witnessed m-of-n ceremony. Violating this is an unrecoverable extinction event (DigiNotar). Tradeoff: every intermediate rotation requires physical ceremony logistics.

P2 — Policy before cryptography. Issuance authorization (PolicyVerdict) completes and is persisted before the signing call is invoked. Prevents accidental trust escalation from a signing-path bug. Operational implication: policy evaluation sits on the issuance-latency critical path (§4).

P3 — CT before release. Every issued certificate is submitted to ≥2 CT logs and its SCT recorded before the certificate is returned to the requester. Makes mis-issuance detectable by the whole ecosystem, not just this CA. Violating it converts a detectable mis-issuance into a silent one (Symantec 2017 distrust precedent).

P4 — Revocation must be fresh and checkable. A revocation nobody can verify in time is not a revocation. Motivates OCSP stapling and bounded CRL/OCSP freshness windows (I9).

P5 — Deterministic certificate construction. ASN.1/DER serialization of a given logical certificate is byte-for-byte reproducible. Non-determinism breaks signature verification, audit replay, and CT precertificate/certificate matching.

P6 — Fail closed on validation uncertainty. Any ambiguous parse, unresolvable policy input, or HSM-session doubt rejects issuance rather than proceeding. Prevents a silently-insecure certificate from ever existing.

P7 — Keys never leave the custody boundary. Private-key material lives exclusively inside the PKCS#11 token; the application process only ever holds a KeyHandle (P1 for the root, same rule for issuing keys). A key that leaves an HSM must be assumed compromised (MM2).

P8 — Append-only auditability. Every security-relevant operation emits an immutable, hash-chained event before that operation is considered committed. Missing audit coverage invalidates the compliance posture even if the operation itself was correct.

P9 — Serial-number unpredictability. Serials are generated from a CSPRNG with ≥ 64 bits of entropy (CA/Browser Forum BR requirement) to prevent collision and enumeration attacks.

P10 — Bounded concurrency at the HSM boundary. Signing queues are depth-limited; overload degrades to backpressure, never to unbounded HSM session growth (which starves or crashes the token).

P11 — Explicit trust boundaries. RA, CA, and VA are separated processes communicating over an authenticated, authorized protocol. Collapsing them (as some reference implementations do by default) removes the ability to reason independently about each boundary's compromise blast radius.

P12 — Immutable issuance records; crash-only components. Historical issuance metadata is never mutated in place — corrections are superseding events. Services recover purely through restart semantics; hidden mutable in-memory state is forbidden.

P13 — m-of-n control for high-risk operations. Root ceremonies and issuing-CA key rotation require quorum authorization from named custodians, never a single operator.

P14 — Short validity is a first-class alternative to revocation. Where the issuance profile allows it, a shorter validity window (90-day leaves) reduces reliance on revocation-checking infrastructure entirely — the tradeoff explored fully in §31 and §36.

Debugging methodology: a deterministic issuance-and-revocation simulator drives synthetic IssuanceRequest/RevocationRecord streams through the pipeline with one assertion per invariant (§7) firing on every transition; failures reproduce byte-for-byte via the recorded audit log (P8, P5).

8.2 CSR (PKCS#10, RFC 2986)

CertificationRequestInfo { version, subject, subjectPKInfo, attributes } signed by the requester's private key over the DER encoding of CertificationRequestInfo; attributes commonly carries the extensionRequest (SANs, EKU) the RA/policy engine may honor or reject.

8.3 CRL structure (RFC 5280 section 5) and delta-CRL model

CertificateList { tbsCertList, signatureAlgorithm, signatureValue }; tbsCertList { version, signature, issuer, thisUpdate, nextUpdate, revokedCertificates SEQUENCE OF { userCertificate, revocationDate, crlEntryExtensions }, crlExtensions }. Delta-CRL model: a base CRL published on the 24 h cadence (§4) plus a delta CRL (extension: delta-CRL indicator, OID 27) listing only entries revoked since the base — clients merge base+delta for a current view without refetching the full base every 4 h.

Step Message Fields
1 OCSPRequest tbsRequest { version, requestList SEQUENCE OF { reqCert { hashAlgorithm, issuerNameHash, issuerKeyHash, serialNumber } }, requestExtensions (nonce, RFC 6960 section 4.4.1) }
2 OCSPResponse responseStatus, responseBytes { responseType, response: BasicOCSPResponse }

5 (stapling) server pre-fetches BasicOCSPResponse and serves it via TLS 1.3 status_request (RFC 8446 section 4.4.2.1) inside the handshake — client never queries the OCSP responder directly

8.5 Path building and RFC 5280 section 6 path validation — named steps

  1. Path build: from leaf, walk AKI→SKI linkage (or AIA caIssuers) toward a configured TrustAnchor, producing a candidate ordered certificate list (PathBuilder).
  2. Initialize validation state: working_public_key, working_issuer_name, max_path_length, permitted/excluded_subtrees (empty), policy_set = {any-policy}.
  3. Per-certificate loop (leaf → anchor), each certificate checked against:
Check Rule
Signature working_public_key verifies this cert's signature
Validity current time ∈ [notBefore, notAfter]
Revocation CRL/OCSP status = good
Basic constraints / path length CA flag set for non-leaf; pathLenConstraint not exceeded (I11)
Name constraints subject name within permitted_subtrees, outside excluded_subtrees
Policy mapping certificatePolicies/policyMappings intersect policy_set, else policy set narrows
  1. Wrap-up: verify final policy_set non-empty if policy validation was required; verify anchor is a configured TrustAnchor.

Worked validation (3-cert chain): Root(CA=true,pathLen=2) → Intermediate(CA=true, pathLen=0) → Leaf(CA=false). Each signature check passes; each validity window nested correctly (I1); no name/policy constraints configured ⇒ ACCEPT.

Worked rejection: same chain, but Intermediate carries pathLenConstraint=0 and itself issued a further intermediate before the leaf ⇒ path length exceeded at step 3 ⇒ REJECT — basic-constraints violation (I11), telemetry pathlen_violation_total incremented.

8.6 ACME issuance flow (RFC 8555) — sequence table

Step Actor → Actor Message
1 Client → pki-acme newAccount (JWS-signed)
2 Client → pki-acme newOrder (identifiers list)
3 pki-acme → Client authorization per identifier, with challenges (http-01, dns-01)
4 Client → challenge endpoint fulfills http-01 (token at .well-known/acme-challenge/) or dns-01 (_acme-challenge TXT record)
5 pki-acme → challenge endpoint validates challenge out-of-band
6 Client → pki-acme finalize (CSR)
7 pki-acme → pki-ra/pki-policy/pki-ca forwards validated CertificateRequest
8 pki-acme → Client certificate download URL

8.7 Key hierarchy and ceremony procedure — named steps

  1. Custodian quorum authentication (m-of-n, P13) at the air-gapped workstation.
  2. Root key generation (or activation of an existing root key) inside the offline HSM; witnessed, video-recorded.
  3. Intermediate CSR generation on the online side, transported via write-once media across the air gap.
  4. Root HSM signs the intermediate certificate; output transported back the same way.
  5. Ceremony log (script + attestations) hashed and appended to pki-audit (P8).
  6. Root HSM returns to sealed storage; workstation powered off.

8.9 Malformed / attack examples

  • CSR requesting a SAN the requester does not control → blocked at I14 (RA/ACME independent validation).
  • Path containing a name-constraint violation (excluded subtree matched) → REJECT at step 3 of §8.5.
  • Revoked intermediate presented mid-chain → REJECT, revocation check at every non-leaf certificate, not just the leaf.
  • Expired root-to-leaf chain (any single certificate outside its validity window) → REJECT at validity check.
  • Policy-mismatch: leaf certificate asserts a certificatePolicies OID absent from the issuer's policyMappings and no anyPolicy present → REJECT at wrap-up.
  • OCSP replay: a captured "good" BasicOCSPResponse presented past its nextUpdate → REJECT at I13 (stale-serve check on the relying-party side, and blocked from being served by pki-ocsp in the first place).
  • Certificate lint failure: leaf certificate missing subjectKeyIdentifier or carrying a non-canonical DER length encoding → REJECT by pki-lint before release (P5, P6).

8.10 Failure-path example

Malformed CSR: (1) pki-ra's ASN.1 decoder rejects an indefinite-length BER encoding (DER requires definite lengths); (2) structured ValidationError returned; (3) audit event appended (P8); (4) RA's malformed-request counter increments; (5) caller receives a deterministic rejection code — no partial state is ever persisted (P12, I10).

12. Phase 0 — Skeleton, ASN.1/DER Codec, and CI

12.1 Objectives

Stand up the workspace skeleton (§10 crate list); implement a from-scratch, canonical-DER ASN.1 codec (pki-asn1, ADR-02) sufficient to decode/encode TbsCertificate, Csr, Crl, and OCSP messages; wire the CI pipeline (lint, unit, fuzz-smoke) that every later phase gates against.

12.2 Detailed Implementation Steps

  • Create the Cargo workspace with all 17 crates from §10 as empty skeletons with Cargo.toml dependency edges matching the architecture diagram (§3).
  • Implement pki-asn1: TLV (tag-length-value) reader/writer over &[u8], definite-length only (DER forbids BER indefinite length — enforced per P6/P5).

  • Implement canonical-DER re-encoding (P5): decode → in-memory struct → re-encode must be byte-identical to a conformant reference encoding (differential test vs. OpenSSL, ADR-26).
  • Implement TbsCertificate, Csr (CertificationRequestInfo, RFC 2986), base Crl (TbsCertList, RFC 5280 section 5), and OCSP request/response (RFC 6960) decode/encode using the codec above (§8.1–§8.4).
  • Add the pki-conformance skeleton with a PKITS-fixture loader (fixtures populated in Phase 11, §23).
  • Wire .github/workflows/ci.yml (lint via clippy, unit tests, cargo deny) and fuzz.yml (scheduled cargo-fuzz smoke run against the new decoders, ADR-27).
  • Add pki-audit skeleton: in-memory hash-chained log (durable backend lands Phase 10, §22) so every later phase can emit AuditEntry records immediately (P8).

12.3 Deliverable

A compiling workspace where pki-asn1 round-trips every fixture in /conformance/der/ byte- identically, and CI enforces it on every push.

12.4 Acceptance Criteria

  • 100% of 40 curated DER round-trip fixtures (conformance/der/*.der) pass byte-identity assertion.
  • cargo-fuzz smoke run: 30 minutes, zero crashes, zero out-of-bounds reads on the ASN.1 decoder (ADR-27).
  • Indefinite-length BER input is rejected on 100% of conformance/der/malformed-indefinite-*.der fixtures with PkiError::SerializationError.
  • CI green on clippy -D warnings and cargo deny check.

12.5 Conformance Fixtures

  • conformance/der/tbs-basic.der — minimal valid TbsCertificate round-trip.
  • conformance/der/malformed-indefinite-length.der — BER indefinite-length input, must reject.
  • conformance/der/csr-valid-basic.der — minimal valid PKCS#10 CSR.
  • conformance/der/crl-empty.der — CRL with zero revoked entries.
  • conformance/der/ocsp-request-basic.der — minimal OCSP request.

12.6 Pitfalls

  • BER/DER confusion: accepting indefinite-length encodings silently breaks canonical-DER guarantees (P5) — every decoder path must reject them explicitly, not just ignore them.
  • Integer sign-bit handling: ASN.1 INTEGER encodes sign via the leading bit — naive decoders misread large unsigned serials (I6) as negative.
  • BIT STRING unused-bits byte: a common off-by-one in keyUsage decoding.
  • Duplicate-extension ambiguity: RFC 5280 forbids duplicate extension OIDs — a permissive decoder that silently takes the last one masks a malformed/malicious certificate.

12.7 Performance Concerns

  • Allocation pressure from naive per-field Vec<u8> copies during decode — target zero-copy decode (borrow from the input slice) except where a canonical field is reconstructed for re-encoding.
  • Branch-heavy TLV tag dispatch — benchmark against a jump-table dispatch if profiling shows it dominates (§30).

12.8 Edge Cases

  • Empty SubjectAltName extension present but marked critical with zero GeneralName entries.
  • Zero-length subject DN (permitted only when subjectAltName is critical, per RFC 5280 section 4.1.2.6).
  • Negative or zero-length serial number — reject (I6 requires a valid CSPRNG-derived value).
  • BIT STRING with more unused-bits than remaining content bits — reject.

12.9 Failure Analysis

Malformed-input parsing failures must never leave the decoder in a state where subsequent bytes are misinterpreted (parser desynchronization) — every decode function returns a definite consumed-byte count or an error, never a partial success. Detection: differential fuzzing between pki-asn1 and OpenSSL's asn1parse on the same corpus surfaces desynchronization directly. Recovery: reject the whole input; no partial TbsCertificate is ever constructed.

12.10 Operational Notes

Export asn1_decode_error_total{reason} and asn1_decode_latency_seconds from the codec; every later crate's malformed-input counters (e.g. pki-ra's CSR-rejection counter) compose on top of this base metric. CI treats a new fuzz crash as a release blocker.

13. Phase 1 — Key Generation and the HSM/PKCS#11 Boundary

13.1 Objectives

Implement pki-hsm: the PKCS#11 session/slot manager, KeyHandle abstraction, and the signing-request path that every later signing crate (pki-root, pki-ca, pki-ocsp) depends on. Establish the key-custody boundary (P7, I4, I12) before any certificate is ever signed.

13.2 Detailed Implementation Steps

  • Wrap the pkcs11 FFI crate behind pki-hsm's own session-manager type; no other crate links PKCS#11 directly (P7, ADR-18).
  • Implement KeyHandle (§11): never exposes raw key bytes; supports RSA-4096, ECDSA P-256/P-384 (RFC 5758/3279), and Ed25519 (RFC 8032) key generation and CKA-derived attribute queries only.
  • Implement deterministic-ECDSA signing support (RFC 6979) as a configurable per-KeyHandle mode, verified against the RFC's own test vectors.
  • Implement bounded session-pool with FenceToken issuance (I12, P10) — a worker must hold a valid, unexpired fence token before invoking C_Sign.
  • Implement the zeroization wrapper for any transient buffer that does pass through process memory (e.g. the digest before signing) using compiler-enforced drop-time zeroing.
  • Add HSM-unavailable detection (session-open failure, token-removed events) surfaced as PkiError::HsmUnavailable with exponential backoff at the caller.
  • Add a software-simulated PKCS#11 token (SoftHSM2) as the Phase 1 integration-test backend; real vendor HSM integration is validated in Phase 11 hardening (§23).
  • Add HSM latency/throughput instrumentation (hsm_sign_latency_seconds, hsm_sign_throughput_total) feeding §4's HSM constraints directly.

13.3 Deliverable

A pki-hsm crate whose signing API is exercised end-to-end against SoftHSM2: key generation, deterministic-ECDSA signing, and session-fencing all verifiably correct.

13.4 Acceptance Criteria

  • RFC 6979 deterministic-ECDSA test vectors: 100% match against pki-hsm's signing output.
  • Bounded session pool: exactly 256 concurrent signing operations sustainable cluster-wide (§4) with zero session-exhaustion errors under a 500-request burst test.
  • Fenced-session conflict test: 1,000 concurrent workers racing for the same KeyHandle produce zero hsm_session_conflict_total false negatives (I12 property test).
  • HSM signing latency p50 ≤ 4 ms / p99 ≤ 15 ms against SoftHSM2 on reference hardware (§4).

13.5 Conformance Fixtures

  • conformance/hsm/rfc6979-ecdsa-p256.json — deterministic-ECDSA vector set.
  • conformance/hsm/session-exhaustion.json — burst-load scenario replay.
  • conformance/hsm/fencing-race.json — concurrent-fence-token race replay.
  • conformance/hsm/token-removed-midsign.json — HSM-unavailable-mid-operation scenario.

13.6 Pitfalls

  • Treating C_Login state as global mutable state shared across async tasks — PKCS#11 sessions are not implicitly thread-safe; each session must be explicitly owned (Rust Atomics and Locks, ch. 4, §5).
  • Assuming key generation is fast — RSA-4096 generation inside some HSMs takes seconds; never generate on the request-serving path.
  • Silent fallback to software signing on HSM error — an absolute prohibition (P7); the correct behavior is PkiError::HsmUnavailable, never a software key-material path.
  • Fence-token reuse after a worker crash — stale tokens must expire, or a recovered worker can collide with a new one (I12).

13.7 Performance Concerns

  • HSM signing is the global throughput bottleneck (§4, §30, §34) — session-pool sizing must never let queue depth outrun the 500 signs/sec/partition ceiling.
  • PKCS#11 FFI call overhead (context switch into vendor library) — batch digest preparation in Rust, minimize FFI round-trips per signature.

13.8 Edge Cases

  • HSM token physically removed mid-signature — must surface HsmUnavailable, not a panic.
  • Slot re-enumeration after HSM firmware update changes slot IDs — KeyHandle.slot_id must be re-resolved by label, not trusted as stable across restarts.
  • Concurrent key-generation requests for the same label — must be serialized/rejected, not silently overwrite.

13.9 Failure Analysis

An HSM outage (token unplugged, firmware panic, session pool exhaustion) degrades issuance to a queued/backpressured state (P10, ADR-31) rather than failing open. Detection: hsm_sign_error_total alarm plus session-pool-exhaustion telemetry. Blast radius: bounded to signing throughput — no key material is ever at risk during an availability failure because P7 forbids any software fallback path. Recovery: docs/runbooks/ocsp-outage.md and a parallel root-key-adjacent runbook cover session-pool reset and HSM failover procedures.

13.10 Operational Notes

Track hsm_sign_latency_seconds histograms per algorithm; alert on p99 latency degradation before it cascades into issuance-latency SLA breach (§4). Session-pool metrics feed the same dashboard used in Phase 4's intermediate-CA signing pipeline (§16).

14. Phase 2 — Self-Signed Root CA and the Key Ceremony

14.1 Objectives

Implement pki-root: root key generation inside the offline HSM, the self-signed root certificate, and the Ceremony Manager that scripts and records the witnessed m-of-n ceremony (P1, P13, §8.7).

14.2 Detailed Implementation Steps

  • Implement the Ceremony Manager state machine: custodian quorum authentication → root key generation/activation → self-signed root certificate construction → ceremony log finalization (§8.7 named steps).
  • Implement m-of-n quorum authentication (ADR-17) using a Shamir-style secret-sharing scheme for the custodian authentication material (not the root key itself, which never leaves the HSM per P1/P7).
  • Construct the self-signed root Certificate: basicConstraints{CA=true, pathLen=2} critical, keyUsage{keyCertSign, cRLSign} critical, subjectKeyIdentifier derived from the public key (RFC 5280 section 4.2.1.2 method 1).
  • Implement the write-once-media transport protocol for intermediate CSRs crossing the air gap (§8.7 step 3–4): checksum + operator dual-verification before any signing.
  • Implement ceremony-log hashing and append into pki-audit (P8) — the log becomes the first entries in the system's audit chain.
  • Add pki-cli ceremony-playback subcommand: replays a recorded ceremony log for audit verification without re-running any signing operation.
  • Add root-CRL generation (12-month cadence, §4) covering only intermediate-CA revocations — the root never revokes leaf certificates directly.

14.3 Deliverable

A reproducible, scripted root-CA ceremony that produces a self-signed root certificate and an audit-chained ceremony log, replayable via pki-cli ceremony replay.

14.4 Acceptance Criteria

  • Ceremony requires exactly the configured quorum (e.g. 3-of-5); 4 of 5 correct shares plus 1 incorrect share fails closed (P6) — zero successful activations below quorum in 100 simulated attempts.
  • Root certificate passes pki-lint with zero findings and validates under pki-path as a self-signed trust anchor (I5).
  • Ceremony log hash-chain verifies with zero gaps (I8) across 10 simulated ceremony runs.
  • End-to-end ceremony script completes in ≤ 45 minutes on reference hardware (operational target, not a correctness gate).

14.5 Conformance Fixtures

  • conformance/ceremony/quorum-3of5-success.json
  • conformance/ceremony/quorum-below-threshold.json — must fail closed
  • conformance/root/self-signed-valid.pem
  • conformance/root/self-signed-missing-ski.pem — must fail pki-lint

14.6 Pitfalls

  • Treating "witnessed" as merely "logged" — the ceremony log must capture custodian identity assertions independently verifiable later, not just a timestamp.
  • Reusing custodian secret shares across ceremonies — each ceremony must derive fresh authentication material to prevent replay of a captured share set.
  • Underestimating physical-security requirements — a "ceremony" run on a laptop with a network interface merely disabled in software is not air-gapped (P1 requires physical isolation).

14.7 Performance Concerns

Not throughput-sensitive (ceremonies are rare, §4) — the concern is procedural latency (minimize custodian time in the room) and the write-once-media transport's checksum verification overhead, which is negligible at CSR sizes.

14.8 Edge Cases

  • Custodian share presented twice in the same ceremony session — reject, do not count toward quorum twice.
  • Root key already exists (re-ceremony scenario, e.g. adding an additional intermediate) — must activate the existing key, never silently regenerate.
  • Ceremony interrupted mid-procedure (power loss) — must resume from the last audit-logged checkpoint, never from a partially-constructed certificate.

14.9 Failure Analysis

A failed ceremony (quorum not met, media checksum mismatch) leaves the root HSM in its pre-ceremony state — no partial key material, no partial certificate (P6, P12). Detection: ceremony state machine transition log. Recovery: re-run the ceremony from the last valid checkpoint; forensic review of the failed attempt's audit entries is mandatory before retry (P8).

14.10 Operational Notes

The ceremony log is the canonical evidence artifact for a WebTrust audit (§26, §28); store it in /docs/runbooks/key-ceremony.md-referenced cold storage with the same RPO=0 guarantee as the audit log itself (§4).

  • conformance/policy/tenant-escape.yaml — must deny
  • conformance/policy/wildcard-deny.yaml — must deny per default profile
  • conformance/csr/valid-intermediate-request.der
  • conformance/csr/malformed-extension-request.der — must reject at RA

15.6 Pitfalls

  • Ambiguous rule precedence when two PolicyRules match the same request with opposite actions — must be resolved by an explicit, documented deterministic ordering (most specific wins, ties deny), never left to map-iteration order.
  • Policy cache staleness after a profile version bump — every cached PolicyVerdict must carry the profile_hash it was computed against so stale caches are detectable.

  • Rule-graph traversal cost grows with profile complexity — benchmark against the 10 ms p99 budget (15.4) as profiles grow past ~50 rules.

  • Overlapping wildcard SAN policies from two different IssuingProfiles applied to the same tenant — must resolve deterministically, not by evaluation order.

15.9 Failure Analysis

A corrupted or unreachable policy engine forces issuance into a fail-closed freeze (P6) — the online issuing CA refuses every request rather than falling back to an unauthenticated default. Detection: policy-evaluation error-rate alarm. Recovery: restore pki-policy from its versioned config store; replay the frozen request queue only after policy health is confirmed via a synthetic-request healthcheck.

15.10 Operational Notes

Emit policy_evaluation_denied_total{reason} and policy_evaluation_latency_seconds; require every profile change to pass through pki-cli policy simulate in CI before deployment (ties to Phase 11's conformance gate, §23).

16.4 Acceptance Criteria

  • Sustained 50 certs/sec for 10 minutes with issuance latency p50 ≤ 200 ms / p99 ≤ 2 s (§4), zero duplicate serials (I6) across 30,000 issued certificates.
  • 100% of issued leaf certificates pass pki-lint with zero findings.
  • Idempotency property test: 1,000 retried requests with identical request IDs produce exactly 1,000 unique certificates, not 2,000 (I10).

16.5 Conformance Fixtures

  • conformance/leaf/server-auth-basic.der
  • conformance/leaf/unvalidated-san-attempt.json — must be blocked at I14
  • conformance/leaf/retry-same-request-id.json — idempotency replay
  • conformance/leaf/eku-outside-profile.json — must deny

16.6 Pitfalls

  • EKU scope creep: a profile that nominally restricts to serverAuth but a code path that defaults to anyExtendedKeyUsage when the field is absent — an automatic mis-issuance risk class (T2, CA/Browser Forum BR).
  • SAN canonicalization mismatches (case-folding on DNS names, IDNA encoding) causing policy checks and CT-log matching (Phase 9) to disagree on identity.
  • Assuming subjectKeyIdentifier uniqueness — it is a hash of the public key, not a request identifier; collisions across distinct requesters with distinct keys are expected and benign, but must never be conflated with serial uniqueness (I6).

16.7 Performance Concerns

  • Queue contention at the signing-consumer pool under burst load (200 certs/sec, §4) — benchmark backpressure activation (ADR-31) against the 2 s p99 ceiling.
  • pki-lint rule-evaluation cost added to the critical path — must stay within the 2 s p99 budget; profile lint rules for cost, not just correctness.

16.8 Edge Cases

  • Duplicate SAN entries within a single CSR — de-duplicate deterministically, never issue a certificate with repeated GeneralName entries.
  • CSR requesting an EKU combination nonsensical for its key algorithm (e.g. keyEncipherment on an Ed25519 key, which supports signing only) — reject at policy evaluation.
  • Clock skew between RA and issuing CA producing a notBefore in the past relative to the signing host's clock — bound by ADR-30's skew-rejection window.

16.9 Failure Analysis

An HSM slowdown cascades into queue growth and eventually backpressure rejection (P10) — by design, this fails closed rather than exceeding the 2 s p99 issuance-latency budget silently. Detection: queue-depth alarm precedes latency-SLA breach. Recovery: horizontal scale of RA/policy-evaluation tier does not help (the bottleneck is the HSM, §30) — the runbook path is HSM-partition failover, not application-tier scaling.

16.10 Operational Notes

Track issuance_latency_seconds histogram, issuance_queue_depth, and lint_finding_total{rule}; a nonzero lint_finding_total on a released certificate is a Sev-1 page (mis-issuance risk, T2).

  • conformance/pkits/name-constraint-excluded-subtree.der
  • conformance/pkits/policy-mapping-mismatch.der

  • Implementing name constraints as subject-only checks and forgetting subjectAltName entries must also be checked against permitted_subtrees (a historical class of real-world path-validation bugs).
  • Treating anyPolicy as always satisfying every certificatePolicies requirement even when inhibitAnyPolicy has activated — must respect the counter.
  • Off-by-one in path-length counting: self-issued (renewal) certificates do not count against pathLenConstraint per RFC 5280 section 6.1.4(k) — a common implementation bug.

17.7 Performance Concerns

  • Path building with a large AIA-fetch fallback fan-out can dominate latency — cache fetched intermediates aggressively; the common case (AKI/SKI linkage from local store) must dominate over the network-fetch fallback.

  • A chain where an intermediate is both a valid current cert and has a revoked predecessor with the same subject/key (renewal scenario) — must select correctly, not ambiguously.

17.9 Failure Analysis

Mitigation: the mutation-property-test gate (17.4) specifically targets false positives; any regression here blocks release regardless of other test results. Detection in production: differential shadow-validation against OpenSSL's verify on a sample of live traffic (§28). Recovery: emergency pki-path rollback to the last differentially-verified build.

17.10 Operational Notes

Export path_validation_result_total{outcome,reason}; feed the differential-shadow- validation mismatch rate into the same dashboard used for mis-issuance detection (§26).

  • Publishing a delta CRL without a matching base-CRL reference (the delta-indicator extension must name the exact base CRL number it extends) — a mismatch silently breaks client-side merging.
  • Forgetting reason-code propagation into crlEntryExtensions — some relying parties key behavior off revocation reason (e.g. certificateHold is reversible, unlike others per I9's monotonicity, which applies only to non-hold reasons).
  • CRL-signing-session contention with leaf-signing sessions starving the CRL publication schedule under load — must be isolated (18.2).

18.7 Performance Concerns

  • CRL generation cost scales with revoked-entry count — the motivating pressure for delta-CRLs and, at ecosystem scale, the alternative approaches discussed in §31/§36.
  • Serialization cost of a large TbsCertList — benchmark against the size ceiling (§4).

18.8 Edge Cases

  • A certificate revoked and then its issuing CA itself later revoked — CRL for the now-revoked intermediate must still be published (root-level CRL, §14) even though no new leaf-level entries are expected.
  • Revocation of a certificate that already expired naturally — permitted (some relying parties check CRLs even for cached/logged historical certs) but does not extend the CRL's practical lifetime obligation.
  • certificateHold reason followed by an unhold request — the sole exception to I9's monotonicity; validated in pki-audit as a superseding event (P12), never a mutation.

18.9 Failure Analysis

A stalled CRL publisher breaches the freshness bound (I7) silently unless monitored — detection is the revocation_freshness_violation_total metric (I7's own row) crossing zero. Recovery: docs/runbooks/mass-revocation.md's emergency-CRL-regeneration procedure forces an out-of-cycle publish.

18.10 Operational Notes

Alert on CRL age approaching nextUpdate (stale-cache risk, I13); dashboard CRL size trend against the §4/§34 ceilings to anticipate delta-CRL-insufficiency before it happens.

19. Phase 7 — The OCSP Responder and Stapling

19.1 Objectives

Implement pki-ocsp: pre-signed OCSP response generation (ADR-10), the request-serving path (RFC 6960, §8.4), and the artifact format consumed by TLS 1.3 stapling (section 4.4.2.1 of RFC 8446, RFC 6961 multi-stapling, ADR-11).

19.2 Detailed Implementation Steps

  • Implement pre-signed BasicOCSPResponse generation on a TTL refresh cycle (§4: cache TTL ≤ 10 min) for every active certificate, using pki-hsm sessions isolated from leaf/CRL signing (P10).
  • Implement the request-serving path: parse OCSPRequest (§8.4), look up CertID, serve the cached pre-signed response — no per-request HSM call (ADR-10, the throughput design).
  • Implement nonce handling (RFC 6960 section 4.4.1) with replay detection — pre-signed responses cannot embed a fresh nonce per request, so the responder documents (and the RA/ACME clients are configured for) nonce-less operation per common practice, with replay monitoring on any nonce that does appear.
  • Implement the stapling-artifact export path: format the pre-signed BasicOCSPResponse for direct consumption by a TLS terminator's status_request handling (the actual TLS handshake logic lives in TLS-Handshake, project 48 — this system only produces the artifact).
  • Implement on-demand fallback signing (ADR-10's rejected-alternative regime) for certificates not yet in the pre-signed cache (e.g. issued in the last TTL window) — bounded and rate-limited to avoid becoming an unbounded HSM-contention path.
  • Wire pki-path's revocation-check step to consult OCSP as an alternative/complementary source to the Phase 6 CRL cache.
  • Add horizontal-scaling support: OCSP responders are stateless read replicas of the pre-signed-response cache, fronted by a CDN-style edge layer (§31).

19.3 Deliverable

An OCSP responder sustaining the §4 QPS target, serving pre-signed responses within the freshness bound, with a working stapling-artifact export verified against a TLS 1.3 handshake fixture.

19.4 Acceptance Criteria

  • Sustained 20,000 req/sec across the responder fleet for 10 minutes, p50 ≤ 5 ms / p99 ≤ 50 ms (§4).
  • Zero stale-serve violations (I13) across a 24 h soak test against the 10-minute TTL.
  • Stapling-artifact fixture validates against a reference TLS 1.3 status_request decoder (RFC 8446 section 4.4.2.1 conformance).
  • On-demand fallback path stays within 1% of total request volume in steady state (cache effectiveness target).

19.5 Conformance Fixtures

  • conformance/ocsp/pre-signed-cache-hit.json
  • conformance/ocsp/on-demand-fallback.json
  • conformance/ocsp/stapling-artifact-tls13.bin
  • conformance/ocsp/stale-response-rejected.der

19.6 Pitfalls

  • Serving a cached response past nextUpdate under refresh-job failure — must fail closed (serve unknown or refuse) rather than serve stale good (I13, P6).
  • Nonce mismatches causing legitimate multi-stapling (RFC 6961) clients to be rejected — the multi-stapling path must handle the "no nonce" pre-signed-response case gracefully.
  • Underestimating refresh-job thundering-herd at TTL boundaries — stagger refresh schedules across the active-certificate population rather than a single synchronized refresh wave.

19.7 Performance Concerns

  • Pre-signing throughput must stay within HSM signing budget (§4, §34) — this is the central design tension resolved by ADR-10 (batch pre-sign vs. serve).
  • Edge-caching (§31) is what makes the 20,000 QPS target achievable without scaling HSM throughput linearly with request volume.

19.8 Edge Cases

  • A certificate revoked between pre-signed-response generations — served status is stale until next refresh; the refresh cadence must stay inside the freshness bound (I7) jointly with the CRL cadence.
  • Multi-stapling request for a certificate whose issuing chain includes more than one OCSP-relevant certificate (RFC 6961) — must staple all applicable responses, not just the leaf's.
  • Responder receiving a request for a certificate serial never issued by this CA — must return a well-formed unknown, not an error that leaks internal state.

19.9 Failure Analysis

An OCSP responder outage does not, by design, block TLS handshakes for clients relying on stapling with a still-valid cached response (graceful degradation) — but does block clients performing live OCSP queries. Detection: responder-fleet health check plus ocsp_request_error_total. Recovery: docs/runbooks/ocsp-outage.md — failover to a secondary responder region; if HSM-side pre-signing itself is down, serve the last-known valid pre-signed cache until it approaches nextUpdate, then fail closed.

19.10 Operational Notes

Track ocsp_cache_hit_ratio, ocsp_response_age_seconds, and ocsp_on_demand_fallback_total; the fallback counter trending upward is an early warning of pre-signing-pipeline degradation before it becomes a latency-SLA breach.

20. Phase 8 — The ACME Server (http-01 / dns-01)

20.1 Objectives

Implement pki-acme: the full RFC 8555 account/order/authorization/challenge/finalize state machine (§8.6), integrated with the RA/policy path (P2, ADR-12) rather than bypassing it.

20.2 Detailed Implementation Steps

  • Implement AcmeAccount creation with JWS-signed requests (JWK-derived key confirmation) per RFC 8555 section 7.3.
  • Implement AcmeOrder/AcmeAuthorization/AcmeChallenge state machines (§8.6, §11) with RFC 8555's exact status vocabularies (pending, processing, valid, invalid, ready, etc.).
  • Implement http-01 challenge validation: fetch http://<identifier>/.well-known/acme- challenge/<token> and compare against the expected key-authorization value (ADR-13).
  • Implement dns-01 challenge validation: query _acme-challenge.<identifier> TXT record and compare against the expected digest (ADR-13).
  • Implement replay-nonce issuance and single-use enforcement (RFC 8555 section 6.5) with a bounded nonce cache.
  • Wire finalize: validated order's CSR flows into pki-ra's intake path exactly as an RA-direct request would (Phase 3, §15) — ACME never calls pki-hsm or pki-policy directly, preserving P2/P11.
  • Implement rate limiting per account/identifier to bound ACME-abuse blast radius (T4, §24).
  • Add an interoperability test harness driving a real ACME client (e.g. a standard http-01/dns-01-capable client) against pki-acme in CI.

20.3 Deliverable

An ACME endpoint that completes a full issuance cycle with a real ACME client across both challenge types, producing a certificate indistinguishable (audit-wise) from an RA-direct issuance.

20.4 Acceptance Criteria

  • Real-client interoperability test passes for both http-01 and dns-01 in CI, 3 consecutive green runs.
  • Replay-nonce reuse attempt rejected in 100/100 trials (RFC 8555 section 6.5 conformance).
  • ACME-originated CertificateRequests produce identical PolicyVerdict/audit-chain shape to RA-direct requests in a differential comparison (P11 boundary-preservation check).
  • Challenge-validation timeout enforced at ≤ 10 s per attempt with a bounded retry count (prevents indefinite-pending orders).

20.5 Conformance Fixtures

  • conformance/acme/http01-success.json
  • conformance/acme/dns01-success.json
  • conformance/acme/replay-nonce-reuse.json — must reject
  • conformance/acme/malformed-jws.json — must reject

20.6 Pitfalls

  • JWS canonicalization mismatches between client and server JSON serialization — historically a real interoperability failure class across ACME implementations.
  • Treating challenge validation as a one-shot check — DNS propagation delay requires bounded retry with backoff, not an immediate single query.
  • Allowing an AcmeOrder to bypass the same SAN-validation-evidence linkage (I14) that RA-direct requests require — a boundary violation that would let ACME become a mis-issuance side-channel.

20.7 Performance Concerns

  • DNS/HTTP challenge-validation calls are external-network-bound — must not block the bounded signing-queue (Phase 4) waiting on external I/O; validation happens fully before the request reaches pki-ra.
  • JWS signature verification cost per request — negligible relative to HSM signing but benchmarked to confirm it never becomes the ACME-tier bottleneck.

20.8 Edge Cases

  • Client abandons an order mid-authorization — orders expire per a configured TTL, garbage-collected without leaving dangling AcmeChallenge state.
  • DNS TXT record present but for a stale/previous challenge token — must not false-positive validate against an old token value.
  • Wildcard identifier request (*.example.com) — dns-01 only per RFC 8555 section 7.1.3, http-01 must be rejected for wildcard identifiers.

20.9 Failure Analysis

ACME-abuse (mass low-value order creation, challenge-validation flooding) is contained by per-account/per-identifier rate limits (20.2, T4) — detection via acme_order_rate_limit_triggered_total. Recovery: docs/runbooks/acme-abuse.md covers account suspension and identifier-level quarantine without affecting RA-direct issuance capacity (P11 isolation).

20.10 Operational Notes

Track acme_challenge_validation_latency_seconds{type} and acme_order_completion_rate; maintain a rolling challenge-validation-failure log (separate from the general audit log, since most failures are benign client misconfiguration, not security events).

21. Phase 9 — Certificate Transparency Submission and SCT Handling

21.1 Objectives

Implement pki-ct: precertificate/certificate submission to ≥2 independent CT logs (RFC 6962), SCT collection, and the release-gating quorum check (P3, I2).

21.2 Detailed Implementation Steps

  • Implement the precertificate flow (RFC 6962 section 3.1): construct a poisoned precertificate (critical CT-poison extension), submit to logs, receive Sct per log, then construct the final certificate embedding the SCTs as an X.509v3 extension (RFC 6962 section 3.3) before it is ever released.
  • Implement CtLog registry (§11) with per-log public keys for SCT-signature verification — a log's returned SCT is verified locally before being trusted (P6, never trust an unverified SCT).
  • Implement the release-gate: block Issued → Active transition (§8.8) until ≥2 valid SCTs are recorded (I2) or a bounded submission-timeout triggers the held-retry path (§8.8's "Issued (held), retried" edge).
  • Implement submission-latency tracking against the §4 target (p95 < 2 s to first log; ≤ 500 ms p95 added to the issuance critical path for embedding).
  • Implement SCT embedding as an X.509v3 extension for the final certificate, and add support for OCSP-stapled SCT delivery (RFC 6962 section 3.3 alternative delivery, complementing Phase 7's stapling artifact) as the fallback delivery path when embedding is not feasible (e.g. precertificate-less flows).
  • Add CT-submission-outage handling: if fewer than 2 logs are reachable, hold release and page (P3 is load-bearing, not best-effort, per ADR-14).

21.3 Deliverable

Every certificate released by this CA carries ≥2 verified SCTs, verifiable independently against the public CT-log ecosystem's own mirrors.

21.4 Acceptance Criteria

  • 100% of certificates released in a 24 h soak test carry ≥2 valid, independently re-verifiable SCTs (I2).
  • CT submission p95 latency ≤ 2 s to first log; total added issuance latency p95 ≤ 500 ms (§4).
  • CT-log-outage simulation (1 of 3 configured logs down): issuance continues via the remaining logs meeting quorum; 2-of-3-down simulation: issuance holds and pages, zero certificates released below quorum in 50/50 trials.
  • SCT-signature verification rejects 100% of 20 tampered-signature fixtures.

21.5 Conformance Fixtures

  • conformance/ct/precert-submission-success.json
  • conformance/ct/quorum-not-met-hold.json
  • conformance/ct/tampered-sct-signature.der
  • conformance/ct/sct-embedding-valid.pem

21.6 Pitfalls

  • Submitting the final (non-poisoned) certificate to a log expecting a precertificate flow — protocol-sequence errors here can leak an unlogged certificate into circulation before SCTs are verified.
  • Trusting a log's SCT without local signature verification — a compromised or misbehaving log's unverified SCT would defeat the entire point of P3.
  • CT submission latency variance across logs causing the slowest reachable log to dominate p95 — implement per-log timeout with early quorum satisfaction (don't wait for all configured logs if quorum is already met).

21.7 Performance Concerns

  • CT submission is external-network-bound, parallel across configured logs — the critical-path budget (500 ms p95) requires early-return-on-quorum, not a serial submission loop.
  • SCT-signature verification cost is negligible (single ECDSA/RSA verify per log) relative to network round-trip time, which dominates.

21.8 Edge Cases

  • A CT log returns a malformed SCT structure — treated identically to a submission failure for quorum purposes, never partially trusted.
  • Precertificate submitted successfully but the final-certificate SCT-embedding step crashes before persistence — recovery must not re-submit (avoiding duplicate log entries) but must resume from the recorded SCTs (P12, idempotent resume).
  • Certificate renewal reusing the same key — CT logs treat it as a wholly new certificate/precertificate; no SCT reuse across distinct certificate serials.

21.9 Failure Analysis

A CT-submission outage below quorum halts issuance rather than releasing an under-logged certificate (P3, P6) — this is a deliberate availability/security tradeoff (§24, T6). Detection: ct_quorum_not_met_total alarm, page-immediately per §26's alerting philosophy (mis-issuance-adjacent). Recovery: docs/runbooks/ CT-log-outage procedure (fold into the ACME-abuse/mass-revocation runbook set, §26) — restore log reachability or reconfigure quorum against a temporarily-expanded log set, never lower the quorum requirement below 2 without an explicit, audited policy change.

21.10 Operational Notes

Track ct_submission_latency_seconds{log_id} and sct_verification_failure_total; dashboard per-log reliability to inform which logs remain in the configured quorum set over time.

22. Phase 10 — Revocation Lifecycle, Renewal, and the Audit Log

22.1 Objectives

Implement pki-audit's durable, hash-chained backend (replacing Phase 0's in-memory skeleton) and complete the certificate lifecycle state machine (§8.8): renewal and the full revocation-request/approval workflow with dual-control for high-privilege certificates (P13, I9).

22.2 Detailed Implementation Steps

  • Implement pki-audit's durable storage: append-only table with a monotonic sequence_id (I8) and previous_hash chaining (P8), backed by write-ahead-logged transactional storage for crash-safety.
  • Implement periodic hash-chain integrity verification (self-scan) as a scheduled job, surfacing audit_chain_gap_total (I8's detection column) on any discrepancy.
  • Implement the renewal workflow (§8.8: Active → Renewed → new Requested): a renewal request re-enters the full RA/policy/HSM pipeline (Phase 3/4) rather than shortcutting it — a renewed certificate is a new Certificate with a new serial (I6), linked to its predecessor for audit lineage only.
  • Implement the revocation-request/approval workflow: operator-submitted RevocationReason (§8.3) with dual-control approval required for CA-certificate revocations (as opposed to leaf revocations, which may be single-operator-approved per policy) — enforcing P13 at the revocation boundary, not just the ceremony boundary.
  • Implement certificateHold's reversible semantics (18.8) as the sole exception to I9, itself represented as a superseding audit event, never a mutation (P12).
  • Implement audit-log query/export tooling for compliance reporting (WebTrust evidence package assembly, §26, §28).
  • Wire revocation events to trigger both the Phase 6 CRL scheduler's next delta cycle and Phase 7's OCSP pre-signed-response invalidation for the affected serial.

22.3 Deliverable

A durable, tamper-evident audit log covering every phase's events from Phase 0 onward (replayed from the in-memory skeleton), plus a complete renewal and dual-control revocation workflow.

22.4 Acceptance Criteria

  • Crash-recovery test: kill pki-audit mid-write 50 times under fault injection — 0 corrupted or duplicate sequence_ids on recovery (I8).
  • Dual-control revocation: a single-operator revocation attempt against a CA certificate is rejected in 100/100 trials; a quorum-approved attempt succeeds in 100/100 trials (P13).
  • Renewal produces a new, unique serial (I6) linked to its predecessor in 100% of 1,000 simulated renewals, with zero validity-window overlap violating I1.
  • Revocation-to-CRL/OCSP-invalidation propagation completes within the §4 freshness bound in 100/100 trials (I7, joint with Phase 6/7).

22.5 Conformance Fixtures

  • conformance/audit/hash-chain-gap-injection.json
  • conformance/revocation/dual-control-single-operator-reject.json
  • conformance/revocation/certificate-hold-then-unhold.json
  • conformance/renewal/serial-uniqueness-1000.json

22.6 Pitfalls

  • Renewal implemented as an in-place mutation of the existing CertificateRecord instead of a new record with lineage linkage — violates P12 and breaks CT/SCT correctness (Phase 9 expects a distinct certificate per serial).
  • Dual-control bypass via a shared operator credential — quorum must be enforced by distinct cryptographic identities, not merely two API calls from the same session.
  • Audit hash-chain verification treated as a one-time startup check rather than a continuous scheduled job — corruption introduced mid-runtime (e.g. storage-layer bit rot) goes undetected until the next restart otherwise.

22.7 Performance Concerns

  • Audit-append serialization is a natural contention point under high issuance throughput (§4, §30) — benchmark the WAL-append path against the 50 certs/sec sustained target plus revocation/renewal traffic overhead.
  • Hash-chain integrity scans over a large log must be incremental (checkpoint-based), not a full-log rescan on every run.

22.8 Edge Cases

  • Renewal requested for a certificate already revoked — must reject; revocation is terminal for that serial (I9) regardless of renewal intent (the requester must obtain a wholly new certificate through normal issuance, not a "renewal" of a revoked one).
  • Concurrent revocation requests for the same serial from two operators — must resolve to a single audit event, not a duplicate/conflicting pair.
  • Audit-log storage approaching a retention-policy boundary — archival must complete before any deletion, and deletion of audit entries themselves is only ever permitted under the documented retention policy, never ad hoc (compliance requirement, §26).

22.9 Failure Analysis

Audit-log corruption (hash-chain gap) is treated as a compliance-severity incident even if no certificate-issuance correctness is affected — the audit trail's integrity is itself a WebTrust-relevant control (P8, §28). Detection: the continuous integrity scan (22.2). Recovery: forensic reconstruction from the last-known-good checkpoint plus cross-reference against independently-replicated audit-log copies (RPO=0 replication target, §4).

22.10 Operational Notes

Export audit_append_latency_seconds and audit_chain_verification_duration_seconds; schedule quarterly restore drills (§26) that specifically replay the audit log to confirm compliance-evidence export tooling still functions against the live schema.

23. Phase 11 — Conformance, Chaos, and Performance Hardening

23.1 Objectives

Run the full NIST PKITS path-validation suite and a complete zlint-style linting pass as CI-gated conformance; execute chaos scenarios (HSM unavailable, CT log down, OCSP responder failover); close out performance hardening against every §4/§30 target.

23.2 Detailed Implementation Steps

  • Complete pki-conformance's NIST PKITS fixture set (all ~400 published test cases) against pki-path, gating CI on 100% expected-outcome match against I5/I11 (extends Phase 5's initial 40% subset, §17).
  • Complete pki-lint's zlint-style rule catalog against real-world-observed mis-issuance patterns (EKU scope creep, missing SKI, non-canonical DER) documented across Phase 4/16's pitfalls (P5, P6, ADR-15).
  • Implement differential validation per ADR-26: run a sample of issued certificates through both pki-path and OpenSSL's verify, alerting on any disagreement (§28's differential gate, MM8).
  • Implement chaos scenarios: HSM-unavailable injection (Phase 1's HsmUnavailable path), CT-log-down injection (Phase 9's quorum-hold path), OCSP-responder-failover injection (Phase 7's fleet failover) — each run against the live staging topology, not mocked components.
  • Run soak tests: 7-day sustained issuance load at 50 certs/sec, 7-day sustained OCSP load at 20,000 QPS (§4, §28).
  • Complete perf-regression gating: every §30 M# target wired into CI as a Criterion-benchmark-backed gate, failing the build on regression beyond a defined tolerance.
  • Finalize reproducible-build and SBOM generation (§29) as a release-blocking CI stage.

23.3 Deliverable

A CI pipeline that gates every release on full PKITS conformance, zlint conformance, differential-validation agreement, chaos-scenario pass, and perf-regression thresholds — the system's production-readiness bar.

23.4 Acceptance Criteria

  • 100% pass rate on all ~400 NIST PKITS fixtures.
  • Zero zlint findings across a 10,000-certificate sample spanning every configured IssuingProfile.
  • Differential-validation disagreement rate = 0 across a 100,000-certificate sample against OpenSSL verify.
  • All three chaos scenarios recover within their documented RTO (§4: 15 min) with zero data loss beyond the documented RPO.
  • 7-day soak tests complete with zero SLA-budget breaches (§4: 99.95% issuance, 99.99% OCSP).

23.5 Conformance Fixtures

  • conformance/pkits/full-suite/ (≈400 fixtures, NIST-published)
  • conformance/lint/mis-issuance-patterns/ (EKU creep, missing SKI, non-canonical DER)
  • conformance/chaos/hsm-unavailable-recovery.json
  • conformance/chaos/ct-log-down-quorum-hold.json

23.6 Pitfalls

  • Treating "PKITS passes" as sufficient without the differential-validation cross-check — PKITS is necessary but not sufficient; a bug shared between pki-path and its own test fixtures would pass PKITS while still diverging from real-world relying-party behavior.
  • Running chaos scenarios only against mocked components — masks integration-level failure modes (e.g. real PKCS#11 session-teardown timing under an actual HSM outage).
  • Soak-test false confidence from a synthetic traffic pattern that doesn't match real request-size/SAN-count distributions.

23.7 Performance Concerns

This phase is the perf-hardening capstone: every M# target from §30 is validated here under sustained load, not just isolated benchmarks — the difference between a component-level pass and a system-level pass under contention (queue interactions, GC-free but allocator-pressure effects, HSM session-pool saturation).

23.8 Edge Cases

  • PKITS fixtures exercising obscure RFC 5280 corners (self-issued certificate chains, policy-mapping loops) that no hand-written test anticipated — this is precisely why the full suite, not a hand-picked subset, is the gate.
  • Chaos scenario overlap (HSM down and a CT log down simultaneously) — validated as a combined scenario, not just independently, since real incidents compound (§25).

23.9 Failure Analysis

A conformance or chaos-gate failure at this phase blocks release entirely — this phase has no "acceptable partial pass," reflecting that a CA's production-readiness bar is binary in a way most systems' is not (a mis-issuance is not a degraded experience, it is a security failure). Detection: CI gate itself. Recovery: the offending change is reverted, not patched-forward under time pressure.

23.10 Operational Notes

Publish the full harness results (PKITS/zlint/differential/chaos/soak) as a release artifact alongside the SBOM (§29); this bundle is the evidentiary basis for the next WebTrust audit cycle (§26, §28).

27. Compatibility & Versioning

X.509 profile versioning: every IssuingProfile is versioned and hash-referenced (ADR-16); a profile change never mutates historical PolicyDecision records (P12).

Algorithm agility / PQC-migration path: the signing-algorithm set (ADR-05) is abstracted behind KeyHandle/SignatureAlgorithm so a future ML-DSA co-signature (PhaseDeferred("§27")) adds a new enum variant, not a structural rewrite.

CRL/OCSP format stability: RFC 5280/6960 wire formats are treated as frozen external contracts; internal cache/serving optimizations (pre-signing, ADR-10) never alter the wire-visible response format.

ACME protocol version: pinned to RFC 8555; a future ACME extension (e.g. a new challenge type) is additive and gated behind capability negotiation already built into the protocol's directory-object mechanism.

CT log-version handling: CtLog registry entries are individually versioned per log's own API version; a log-API deprecation is handled per-entry, not system-wide.

CA/Browser Forum Baseline-Requirements compliance version: the pki-policy default profile is pinned to a specific BR version snapshot; profile updates track BR revisions explicitly, logged in BLUEPRINT_LOG.md-equivalent change history.

API stability: the management-plane API (mTLS-authenticated, ADR-22) follows SemVer; breaking changes require a major-version bump and an N-1 interoperability window.

Migration/deprecation: deprecated fields retained for 2 release cycles; destructive storage migrations require a prior archival snapshot (§26).

Rolling-upgrade guarantees: N-1 interoperability across RA/CA/VA/ACME/CT-submitter service versions during a rolling upgrade window.

Unit: pki-asn1 codec correctness, policy-rule evaluation, individual extension encode/decode.

30. Performance Engineering

Tail-latency analysis decomposes issuance p99 into policy-evaluation, HSM-queue-wait, and audit-append components (13.10, 22.7) to identify which sub-budget is closest to breach under load.

31. Scalability Analysis

What stays constant: per-certificate ASN.1 encode/decode cost (O(1) in chain length once built); per-request policy-evaluation cost (O(rules), bounded by profile size, not request volume). What grows: HSM signing load grows O(issuance rate) and is the hard ceiling (§4, §34) — no application-tier scaling relieves it, only more HSM partitions/higher-throughput hardware. OCSP QPS scales via pre-signed responses + CDN edge fan-out (O(1) marginal cost per additional edge node, decoupled from HSM throughput, ADR-10). CRL size grows O(revoked-certificate count) — the reason delta-CRLs exist (bounding per-cycle payload) and, at ecosystem scale, the reason the industry has moved toward short-lived certificates and CRLite-style approaches (PhaseDeferred("§36")) instead of ever-growing revocation lists.

Named bottlenecks in order: (1) HSM signing throughput (§4, §30, §34); (2) audit-append serialization under high issuance concurrency (FM-8); (3) CT-submission network round-trip latency on the issuance critical path (21.7); (4) CRL generation cost at very large revoked-population sizes (18.7).

Horizontal scaling: RA/policy/ACME/CT-submitter tiers are stateless and scale linearly; OCSP responders are stateless read replicas fronted by CDN-style edge caching (19.2, §31).

Vertical scaling: signing workers benefit from HSM partitions with higher per-partition throughput before horizontal HSM-fleet expansion is justified (cost/complexity tradeoff).

The revocation-scale problem: at internet scale, per-query OCSP and ever-growing CRLs both degrade — this is why the ecosystem has moved toward short-lived certificates (validity short enough that revocation checking becomes unnecessary, P14) and toward CRLite-style browser-side bulk revocation pushes (PhaseDeferred("§36"), explored fully in §36).

Practical issuance ceiling: bounded by configured HSM-partition count × per-partition throughput (§34's derivation). Practical validation ceiling: bounded by OCSP edge-fleet size, decoupled from issuance-side HSM constraints. The lever beyond both: adding HSM partitions (issuance side) and adding edge-cache capacity (validation side) — independent scaling knobs by design (P11's separation of concerns).

32. Mental Models & First Principles

MM1 — PKI moves trust, it does not create it. Every certificate is a signed assertion that some CA vouched for a binding; the whole system's security is the weakest CA a relying party trusts (Ellison & Schneier, 2000). Predicts: adding more CAs to a trust store reduces aggregate security unless each is independently held to the same bar. Bug class without it: treating cross-signing or a new intermediate as a purely administrative act rather than a trust-expansion decision. Applied in §1 (non-goals), §24 (T1/T2), ADR-21.

MM2 — A key that leaves its HSM is a key you must assume is compromised. The whole architecture (P7, I4, I12) is organized entirely around keys that never move. Predicts: any "emergency export" feature request is itself a security regression, not a convenience. Bug class without it: building a "backup the private key to a file, just in case" feature that becomes the actual attack surface. Applied in §9 (ADR-03), §13, §24 (T1, T11).

MM3 — Revocation is the hardest unsolved problem in PKI. Issuance is easy; un-issuing is nearly impossible at internet scale — which is why short-lived certificates win in practice (P14). Predicts: any revocation-freshness promise beyond what CRL/OCSP infrastructure can physically deliver is a false guarantee. Bug class without it: sizing an OCSP responder for average load instead of the freshness-bound-driven worst case (I7). Applied in §18, §19, §31, §36.

MM4 — Detectability is a security property, not an afterthought. CT (P3) doesn't prevent mis-issuance; it makes it discoverable by the whole ecosystem, converting a silent single-CA failure into a public, correctable one. Predicts: a CA without CT submission has a strictly worse security posture even if its issuance logic is bug-free, because it has no external check on that assumption. Bug class without it: treating CT submission as "just an audit nicety" rather than a load-bearing control. Applied in §21, §24 (T6), §6 (P3).

MM5 — Policy and cryptography are separate concerns that must never share a failure mode. A signing bug and an authorization bug are different bugs with different blast radii; conflating them (skipping policy evaluation "just this once" for a fast path) collapses that separation. Predicts: any code path that can reach pki-hsm without first producing a PolicyVerdict is a latent mis-issuance vulnerability regardless of how unlikely it seems. Bug class without it: an "emergency issuance" bypass route added under incident pressure that never gets removed. Applied in §6 (P2), §7 (I3), §15.

MM6 — A CA's trust hierarchy is a distributed system with a single non-redundant root of trust by design, not by accident. Unlike most distributed systems, adding redundant roots does not add resilience — it adds attack surface (MM1). The resilience strategy is instead procedural (ceremony discipline, m-of-n custody) rather than architectural (replication). Predicts: attempting to "solve" root-key availability with active-active root replication is solving the wrong problem. Bug class without it: designing root-key infrastructure using the same replication playbook used for the online tiers. Applied in §3, §14, §36.

MM7 — Every cryptographic protocol boundary is also an audit boundary. RA/CA/VA/ACME separation (P11) exists so that a compromise or bug at one boundary is independently attributable — the audit log (P8) is only as useful as the boundaries it can distinguish between. Predicts: collapsing two boundaries into one process for "simplicity" destroys forensic attributability even if functionality is unaffected. Bug class without it: an incident postmortem that cannot determine whether the RA or the policy engine made the wrong call, because they share one log stream with no boundary markers. Applied in §3, §7 (I3), §26.

MM8 — A validator's false-positive is categorically worse than its false-negative. Rejecting a valid certificate is an availability incident; accepting an invalid one is a security incident that may never be detected (T7, MM4 partially compensates but is not a substitute for correctness). Predicts: every path-validation ambiguity should be resolved by rejecting, never by a permissive default (P6). Bug class without it: a "be lenient for compatibility" patch to pki-path that quietly reintroduces a false-positive risk. Applied in §17 (17.9), §28.

34. Back-of-Envelope Capacity Model

  1. Issuance throughput from HSM signing rate. 500 signs/sec/partition (§4) × 1 sign/cert = 500 certs/sec/partition theoretical ceiling; at the sustained 50 certs/sec target (M1), the system runs at 10% of one partition's capacity, leaving headroom for burst (200 certs/sec, §4) without adding partitions.
  2. OCSP QPS served by pre-signed responses. Active-certificate population at steady state ≈ issuance rate × average validity ≈ 50 certs/sec × 90 d × 86,400 s/d ≈ 389M active certs. Check frequency (relying-party OCSP query rate, conservatively 1 query/cert/day) ⇒ 389M ÷ 86,400 s ≈ 4,500 req/sec baseline organic load — well under the 20,000 req/sec fleet target (M5), leaving headroom for stapling-adoption variance and burst.
  3. On-demand OCSP signing capacity (rejected-path comparison). At 500 signs/sec/ partition, on-demand signing for the same 4,500 req/sec baseline would consume 9 partitions' full capacity continuously — this is the arithmetic behind ADR-10's pre-signing decision: pre-signing decouples OCSP QPS from HSM throughput entirely.
  4. CRL size. Revoked-population estimate: 2% annual revocation rate × 389M active certs ≈ 7.8M revocations/year ≈ 21,370 revocations/day. At a conservative entry size of ~40 bytes/RevokedEntry (serial + date + reason), a base CRL covering a rolling 1-year revocation window ≈ 7.8M × 40 bytes ≈ 312 MB — far above the 2 MB target (M10), which is why the base CRL is scoped to currently-valid-lifetime revocations only (entries for certificates that have since expired naturally are pruned, §18.2), bringing the practical base CRL down to the certificates still within their 90-day validity window: 21,370/day × 90 d ≈ 1.92M entries × 40 bytes ≈ 77 MB — still requiring delta-CRL partitioning (§18) to hit the 2 MB per-cycle-delta target: 21,370 revocations/day ÷ 6 delta-cycles/day (4 h cadence, §4) ≈ 3,562 entries/delta × 40 bytes ≈ 142 KB, comfortably under the 200 KB delta-CRL ceiling (M10).
  5. Short-lived-cert issuance load as the revocation alternative. Active certs ÷ validity period = renewal-driven reissuance rate: 389M active ÷ 90 d ≈ 4.3M renewals/day ≈ 50 certs/sec sustained — this is already what M1's target represents; the derivation shows the 90-day-validity profile's steady-state issuance load equals its own renewal load, the arithmetic behind P14's tradeoff.
  6. CT-log submission volume. Issuance rate × logs per cert (≥2, I2) = 50 certs/sec × 2 ≈ 100 submissions/sec sustained, comfortably within any major CT log's published ingestion capacity.
  7. Database growth. 4.3M certs/day (item 5) × ≈2 KB metadata/cert (§4) ≈ 8.6 GB/day metadata growth, matching §4's stated ≤9 GB/day ceiling.
  8. Audit-log volume. At 1.5× the metadata rate (§4's stated ratio, covering the additional policy-decision/CT/revocation event records per certificate) ≈ 8.6 GB × 1.5 ≈ 12.9 GB/day, ≈ 4.7 TB/year before any compression — motivating the retention- policy and archival-tiering discussion in §26.
  9. Signing-queue depth under burst. At the 200 certs/sec burst ceiling (§4) against 500 signs/sec/partition capacity, one partition absorbs the burst with 60% headroom remaining — confirming a single HSM partition suffices up to 2.5× the stated burst target before a second partition is required.
  10. FD budget check. 20,000 req/sec OCSP fleet-wide ÷ (§4's per-responder 65,536 FD budget ÷ ~2 FDs/connection under HTTP keep-alive) ≈ requires ≥1 responder node to stay within budget at that connection model — in practice sized to 4+ nodes for availability (99.99% SLA, §4), not FD-budget necessity alone.

36. Alternative Architectures (Roads Not Taken)

A1 — Short-lived certificates with no revocation infrastructure at all.

Client --renew every 6h--> ACME Server --> Issuing CA (online, no offline root)
   ^                                              |
   +------------- new short-lived cert <----------+
   (validity so short that a compromised key self-expires
    before revocation would matter; no CRL, no OCSP)

Winning regime: fully automated, homogeneous fleets where every client can reliably renew on a tight schedule (container/service-mesh workloads). Real embodying system: the modern extreme end of the Let's Encrypt/Boulder trajectory combined with SPIFFE/SPIRE-style workload identity (certs valid for hours, not months). Rejected here because this project's leaf-validity range (§4: 90–398 days) and non-homogeneous client population (human users, legacy devices, code-signing) cannot guarantee renewal reliability tight enough to make revocation truly unnecessary — P14 is offered as an available profile, not the system's only mode.

A2 — Decentralized web-of-trust (PGP-style), no hierarchical CA.

Alice --signs--> Bob's key
Bob --signs--> Carol's key         (trust computed by path-length/
Carol --signs--> Alice's key        signature-count heuristics,
   (a mesh, not a tree; no root)     no single trust anchor)

Winning regime: peer communities where identity is socially verified and no institution is trusted to act as a universal introducer (classic PGP email use, some blockchain identity schemes). Real embodying system: OpenPGP's Web of Trust. Rejected here because enterprise/production PKI needs a deterministic, auditable, policy-enforceable trust decision at machine speed (RFC 5280 path validation, §8.5) — a social-trust heuristic cannot satisfy this project's compliance/audit requirements (§26, §28) or its machine-speed TLS-handshake consumers (project 48).

A3 — Browser-side revocation-push model (CRLite/OneCRL) instead of per-query OCSP.

CA revocation events --> Aggregator --> Compressed bloom-filter/
                                          cascade structure
                                              |
                                              v
                                    Pushed to every client
                                    periodically (no live query)

Winning regime: browser vendors controlling both the client population and the distribution channel, where eliminating live OCSP round-trips improves both privacy (no per-visit OCSP query leaking browsing history to the CA) and latency. Real embodying system: Mozilla's CRLite / Chrome's CRLSets (predecessor). Rejected here (deferred, PhaseDeferred("§36")) because this project does not control a browser-vendor-scale push-distribution channel to its relying parties — it is deferred as a future integration if the ecosystem's revocation-distribution model shifts further in this direction, not built as a primary mechanism now.

A4 — Fully offline/air-gapped issuance for a closed enterprise PKI, no ACME or public CT.

AIR-GAP BOUNDARY ================================
| Offline Root CA --> Offline Issuing CA         |
|        (all issuance happens inside the gap,   |
|         certificates physically carried out)   |
==================================================

Winning regime: classified/highly regulated closed networks with no path to a public CT ecosystem and no automated-renewal requirement (e.g. a government or industrial-control enclave). Real embodying system: closed-network defense-industry PKI deployments (not individually named/citable, but a well-documented deployment pattern in Adams & Lloyd, Understanding PKI, ch. 7). Rejected as this project's primary mode because the stated mission explicitly includes ACME automation and CT submission (§1) — but the architecture already supports operating any single issuing CA in this fully-offline mode as a configuration variant, since P11's separation means nothing structurally requires network connectivity at the issuing tier beyond what a given deployment chooses to expose.

38. Glossary

  • PKI — Public Key Infrastructure; the full set of roles, policies, and systems needed to create, manage, distribute, and revoke digital certificates.
  • Certificate Authority (CA) — an entity that signs certificates, vouching for the binding between a public key and an identity.
  • Root CA — the top-level, self-signed CA; the ultimate trust anchor of a hierarchy.
  • Intermediate CA — a CA certified by the root, sitting between root and issuing tiers.
  • Issuing CA — the online CA that signs end-entity (leaf) certificates directly.
  • Registration Authority (RA) — validates CSRs/identity before forwarding to the CA.
  • Validation Authority (VA) — publishes revocation status via CRL and/or OCSP.
  • X.509 — the ITU-T standard defining the certificate and CRL format used throughout.
  • DN (Distinguished Name) — the structured name identifying a certificate's subject or issuer.
  • SAN (Subject Alternative Name) — an extension carrying additional identifiers (DNS, IP, email, URI) bound to the certificate.
  • CSR (Certificate Signing Request) — a PKCS#10 structure a requester submits to obtain a certificate.
  • PKCS#10 — the standard defining the CSR format (RFC 2986).
  • DER (Distinguished Encoding Rules) — the canonical, deterministic subset of ASN.1 encoding used for certificates.
  • ASN.1 (Abstract Syntax Notation One) — the notation used to define the certificate, CRL, and OCSP message structures.
  • Trust anchor — a certificate configured as inherently trusted, the terminus of path validation.
  • Path building — assembling a candidate certificate chain from leaf to trust anchor.
  • Path validation — RFC 5280 section 6's algorithm confirming a chain is cryptographically and policy-wise acceptable.
  • Basic constraints — the extension declaring whether a certificate is a CA and its maximum path length.
  • Name constraints — the extension restricting the namespace a subordinate CA may issue into.
  • Key usage — the extension restricting the cryptographic operations a key may perform.
  • EKU (Extended Key Usage) — the extension further restricting a key's application purpose (e.g. serverAuth, clientAuth).
  • CRL (Certificate Revocation List) — a signed list of revoked certificate serials.
  • Delta CRL — a CRL listing only entries revoked since a referenced base CRL.
  • OCSP (Online Certificate Status Protocol) — a real-time certificate-status query protocol.
  • OCSP stapling — delivering a pre-fetched OCSP response during the TLS handshake itself, per RFC 8446 section 4.4.2.1.
  • CRLite — a browser-side bulk revocation-distribution mechanism compressing ecosystem-wide revocation state into a compact structure pushed to clients.
  • Revocation — the act of invalidating a certificate before its natural expiry.
  • Serial number — the CSPRNG-derived unique identifier of a certificate within its issuer's namespace.
  • ACME (Automatic Certificate Management Environment) — RFC 8555's protocol for automated certificate issuance.
  • Challenge — an ACME mechanism proving control over an identifier.
  • http-01 — an ACME challenge type proving control via an HTTP resource.
  • dns-01 — an ACME challenge type proving control via a DNS TXT record.
  • Certificate Transparency (CT) — RFC 6962's public, append-only log system for issued certificates.
  • SCT (Signed Certificate Timestamp) — a CT log's cryptographic receipt for a submitted certificate/precertificate.
  • CT log — an append-only, publicly auditable log accepting certificate submissions.
  • HSM (Hardware Security Module) — a hardened device that generates and custodies private keys, performing signing without exposing key material.
  • PKCS#11 — the standard interface for interacting with cryptographic tokens/HSMs.
  • Key ceremony — a scripted, witnessed procedure for generating or activating a root or intermediate key.
  • m-of-n control — a quorum authorization scheme requiring m of n designated custodians to jointly authorize a sensitive operation.
  • Cross-signing — having a certificate signed by two different issuing hierarchies to ease a trust-anchor transition.
  • Short-lived certificate — a certificate with a validity window short enough that revocation checking becomes largely unnecessary.
  • WebTrust for CAs — the AICPA/CPA Canada audit framework CAs undergo for public trust.
  • Baseline Requirements (BR) — the CA/Browser Forum's minimum issuance/operations standard for publicly-trusted certificates.
  • Mis-issuance — issuing a certificate in violation of policy, identity validation, or the requester's actual authorization.
  • AIA (Authority Information Access) — the extension pointing to the issuer's certificate and/or OCSP responder URL.
  • CDP (CRL Distribution Point) — the extension pointing to where a certificate's CRL can be fetched.
  • AKI/SKI (Authority/Subject Key Identifier) — extensions linking a certificate to its issuer's key and identifying its own key, used in path building.
  • Precertificate — a CT-poisoned, not-yet-final certificate submitted to obtain SCTs before the final certificate is issued.
  • Policy mapping — an extension permitting an issuer to declare one policy OID equivalent to another for path-validation purposes.
  • Air gap — physical network isolation preventing any connectivity to a system, used to protect the root CA.
  • Zeroization — deliberately overwriting sensitive memory (e.g. key material buffers) on release to prevent residual exposure.
  • Fencing token — a monotonically issued token preventing a stale worker from performing a conflicting operation after a handoff.
