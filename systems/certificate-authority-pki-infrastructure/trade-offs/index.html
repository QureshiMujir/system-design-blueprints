36. Alternative Architectures (Roads Not Taken)

A1 — Short-lived certificates with no revocation infrastructure at all.

Client --renew every 6h--> ACME Server --> Issuing CA (online, no offline root)
   ^                                              |
   +------------- new short-lived cert <----------+
   (validity so short that a compromised key self-expires
    before revocation would matter; no CRL, no OCSP)

Winning regime: fully automated, homogeneous fleets where every client can reliably renew on a tight schedule (container/service-mesh workloads). Real embodying system: the modern extreme end of the Let's Encrypt/Boulder trajectory combined with SPIFFE/SPIRE-style workload identity (certs valid for hours, not months). Rejected here because this project's leaf-validity range (§4: 90–398 days) and non-homogeneous client population (human users, legacy devices, code-signing) cannot guarantee renewal reliability tight enough to make revocation truly unnecessary — P14 is offered as an available profile, not the system's only mode.

A2 — Decentralized web-of-trust (PGP-style), no hierarchical CA.

Alice --signs--> Bob's key
Bob --signs--> Carol's key         (trust computed by path-length/
Carol --signs--> Alice's key        signature-count heuristics,
   (a mesh, not a tree; no root)     no single trust anchor)

Winning regime: peer communities where identity is socially verified and no institution is trusted to act as a universal introducer (classic PGP email use, some blockchain identity schemes). Real embodying system: OpenPGP's Web of Trust. Rejected here because enterprise/production PKI needs a deterministic, auditable, policy-enforceable trust decision at machine speed (RFC 5280 path validation, §8.5) — a social-trust heuristic cannot satisfy this project's compliance/audit requirements (§26, §28) or its machine-speed TLS-handshake consumers (project 48).

A3 — Browser-side revocation-push model (CRLite/OneCRL) instead of per-query OCSP.

CA revocation events --> Aggregator --> Compressed bloom-filter/
                                          cascade structure
                                              |
                                              v
                                    Pushed to every client
                                    periodically (no live query)

Winning regime: browser vendors controlling both the client population and the distribution channel, where eliminating live OCSP round-trips improves both privacy (no per-visit OCSP query leaking browsing history to the CA) and latency. Real embodying system: Mozilla's CRLite / Chrome's CRLSets (predecessor). Rejected here (deferred, PhaseDeferred("§36")) because this project does not control a browser-vendor-scale push-distribution channel to its relying parties — it is deferred as a future integration if the ecosystem's revocation-distribution model shifts further in this direction, not built as a primary mechanism now.

A4 — Fully offline/air-gapped issuance for a closed enterprise PKI, no ACME or public CT.

AIR-GAP BOUNDARY ================================
| Offline Root CA --> Offline Issuing CA         |
|        (all issuance happens inside the gap,   |
|         certificates physically carried out)   |
==================================================

Winning regime: classified/highly regulated closed networks with no path to a public CT ecosystem and no automated-renewal requirement (e.g. a government or industrial-control enclave). Real embodying system: closed-network defense-industry PKI deployments (not individually named/citable, but a well-documented deployment pattern in Adams & Lloyd, Understanding PKI, ch. 7). Rejected as this project's primary mode because the stated mission explicitly includes ACME automation and CT submission (§1) — but the architecture already supports operating any single issuing CA in this fully-offline mode as a configuration variant, since P11's separation means nothing structurally requires network connectivity at the issuing tier beyond what a given deployment chooses to expose.
