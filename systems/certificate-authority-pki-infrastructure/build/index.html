⬜ Phase 0 — Skeleton, ASN.1/DER Codec, and CI §12

Objectives

Stand up the workspace skeleton (§10 crate list); implement a from-scratch, canonical-DER ASN.1 codec (pki-asn1, ADR-02) sufficient to decode/encode TbsCertificate, Csr, Crl, and OCSP messages; wire the CI pipeline (lint, unit, fuzz-smoke) that every later phase gates against.

Deliverable

A compiling workspace where pki-asn1 round-trips every fixture in /conformance/der/ byte- identically, and CI enforces it on every push.

Acceptance
  • 100% of 40 curated DER round-trip fixtures (conformance/der/*.der) pass byte-identity assertion.
  • cargo-fuzz smoke run: 30 minutes, zero crashes, zero out-of-bounds reads on the ASN.1 decoder (ADR-27).
  • Indefinite-length BER input is rejected on 100% of conformance/der/malformed-indefinite-*.der fixtures with PkiError::SerializationError.
  • CI green on clippy -D warnings and cargo deny check.
Fixtures
  • conformance/der/tbs-basic.der — minimal valid TbsCertificate round-trip.
  • conformance/der/malformed-indefinite-length.der — BER indefinite-length input, must reject.
  • conformance/der/csr-valid-basic.der — minimal valid PKCS#10 CSR.
  • conformance/der/crl-empty.der — CRL with zero revoked entries.
  • conformance/der/ocsp-request-basic.der — minimal OCSP request.
Pitfalls
  • BER/DER confusion: accepting indefinite-length encodings silently breaks canonical-DER guarantees (P5) — every decoder path must reject them explicitly, not just ignore them.
  • Integer sign-bit handling: ASN.1 INTEGER encodes sign via the leading bit — naive decoders misread large unsigned serials (I6) as negative.
  • BIT STRING unused-bits byte: a common off-by-one in keyUsage decoding.
  • Duplicate-extension ambiguity: RFC 5280 forbids duplicate extension OIDs — a permissive decoder that silently takes the last one masks a malformed/malicious certificate.

⬜ Phase 1 — Key Generation and the HSM/PKCS#11 Boundary §13

Objectives

Implement pki-hsm: the PKCS#11 session/slot manager, KeyHandle abstraction, and the signing-request path that every later signing crate (pki-root, pki-ca, pki-ocsp) depends on. Establish the key-custody boundary (P7, I4, I12) before any certificate is ever signed.

Deliverable

A pki-hsm crate whose signing API is exercised end-to-end against SoftHSM2: key generation, deterministic-ECDSA signing, and session-fencing all verifiably correct.

Acceptance
  • RFC 6979 deterministic-ECDSA test vectors: 100% match against pki-hsm's signing output.
  • Bounded session pool: exactly 256 concurrent signing operations sustainable cluster-wide (§4) with zero session-exhaustion errors under a 500-request burst test.
  • Fenced-session conflict test: 1,000 concurrent workers racing for the same KeyHandle produce zero hsm_session_conflict_total false negatives (I12 property test).
  • HSM signing latency p50 ≤ 4 ms / p99 ≤ 15 ms against SoftHSM2 on reference hardware (§4).
Fixtures
  • conformance/hsm/rfc6979-ecdsa-p256.json — deterministic-ECDSA vector set.
  • conformance/hsm/session-exhaustion.json — burst-load scenario replay.
  • conformance/hsm/fencing-race.json — concurrent-fence-token race replay.
  • conformance/hsm/token-removed-midsign.json — HSM-unavailable-mid-operation scenario.
Pitfalls
  • Treating C_Login state as global mutable state shared across async tasks — PKCS#11 sessions are not implicitly thread-safe; each session must be explicitly owned (Rust Atomics and Locks, ch. 4, §5).
  • Assuming key generation is fast — RSA-4096 generation inside some HSMs takes seconds; never generate on the request-serving path.
  • Silent fallback to software signing on HSM error — an absolute prohibition (P7); the correct behavior is PkiError::HsmUnavailable, never a software key-material path.
  • Fence-token reuse after a worker crash — stale tokens must expire, or a recovered worker can collide with a new one (I12).

⬜ Phase 2 — Self-Signed Root CA and the Key Ceremony §14

Objectives

Implement pki-root: root key generation inside the offline HSM, the self-signed root certificate, and the Ceremony Manager that scripts and records the witnessed m-of-n ceremony (P1, P13, §8.7).

Deliverable

A reproducible, scripted root-CA ceremony that produces a self-signed root certificate and an audit-chained ceremony log, replayable via pki-cli ceremony replay.

Acceptance
  • Ceremony requires exactly the configured quorum (e.g. 3-of-5); 4 of 5 correct shares plus 1 incorrect share fails closed (P6) — zero successful activations below quorum in 100 simulated attempts.
  • Root certificate passes pki-lint with zero findings and validates under pki-path as a self-signed trust anchor (I5).
  • Ceremony log hash-chain verifies with zero gaps (I8) across 10 simulated ceremony runs.
  • End-to-end ceremony script completes in ≤ 45 minutes on reference hardware (operational target, not a correctness gate).
Fixtures
  • conformance/ceremony/quorum-3of5-success.json
  • conformance/ceremony/quorum-below-threshold.json — must fail closed
  • conformance/root/self-signed-valid.pem
  • conformance/root/self-signed-missing-ski.pem — must fail pki-lint
Pitfalls
  • Treating "witnessed" as merely "logged" — the ceremony log must capture custodian identity assertions independently verifiable later, not just a timestamp.
  • Reusing custodian secret shares across ceremonies — each ceremony must derive fresh authentication material to prevent replay of a captured share set.
  • Underestimating physical-security requirements — a "ceremony" run on a laptop with a network interface merely disabled in software is not air-gapped (P1 requires physical isolation).

⬜ Phase 3 — CSR Intake, the Policy Engine, and Issuing Intermediates §15

Objectives

Implement pki-ra (CSR intake/identity validation) and pki-policy (deterministic issuance policy evaluation), then use the online issuing HSM to sign the first intermediate CA certificate from a root-ceremony-produced CSR (§8.7 step 3–4 completed end-to-end).

Deliverable

An intermediate CA certificate signed by the offline root (via the Phase 2 ceremony transport) and activated online, with the RA/policy path enforced for every subsequent request — verifiable by attempting (and having rejected) an out-of-policy request.

Acceptance
  • 100% of 25 curated policy fixtures (conformance/policy/*.yaml) produce the expected PolicyVerdict (allow/deny) deterministically across 3 repeated evaluations.
  • Tenant-isolation property test: 10,000 randomized cross-tenant SAN requests, zero tenant-escape approvals (I3, I14).
  • Intermediate certificate passes pki-lint with zero findings and validates under pki-path as chaining to the Phase 2 root (I5).
  • Policy evaluation p99 latency ≤ 10 ms (feeds §4's issuance-latency budget).
Fixtures
  • conformance/policy/tenant-escape.yaml — must deny
  • conformance/policy/wildcard-deny.yaml — must deny per default profile
  • conformance/csr/valid-intermediate-request.der
  • conformance/csr/malformed-extension-request.der — must reject at RA
Pitfalls
  • Ambiguous rule precedence when two PolicyRules match the same request with opposite actions — must be resolved by an explicit, documented deterministic ordering (most specific wins, ties deny), never left to map-iteration order.
  • Policy cache staleness after a profile version bump — every cached PolicyVerdict must carry the profile_hash it was computed against so stale caches are detectable.
  • Conflating "RA validated identity" with "policy authorized issuance" — these are separate gates (P2); collapsing them removes the audit trail's ability to distinguish failure causes.

⬜ Phase 4 — Leaf Issuance and the v3 Extension Profile §16

Objectives

Extend pki-ca to issue leaf (end-entity) certificates with the full v3 extension profile (§8.1) under IssuingProfile control, at the sustained throughput target (§4).

Deliverable

A leaf-issuance pipeline sustaining the §4 throughput target end-to-end (RA → policy → HSM sign → lint → store → audit), verified against a load-generation harness.

Acceptance
  • Sustained 50 certs/sec for 10 minutes with issuance latency p50 ≤ 200 ms / p99 ≤ 2 s (§4), zero duplicate serials (I6) across 30,000 issued certificates.
  • 100% of issued leaf certificates pass pki-lint with zero findings.
  • Idempotency property test: 1,000 retried requests with identical request IDs produce exactly 1,000 unique certificates, not 2,000 (I10).
  • Zero SANs issued outside validation_evidence scope across 5,000 randomized fuzz requests (I14 property test).
Fixtures
  • conformance/leaf/server-auth-basic.der
  • conformance/leaf/unvalidated-san-attempt.json — must be blocked at I14
  • conformance/leaf/retry-same-request-id.json — idempotency replay
  • conformance/leaf/eku-outside-profile.json — must deny
Pitfalls
  • EKU scope creep: a profile that nominally restricts to serverAuth but a code path that defaults to anyExtendedKeyUsage when the field is absent — an automatic mis-issuance risk class (T2, CA/Browser Forum BR).
  • SAN canonicalization mismatches (case-folding on DNS names, IDNA encoding) causing policy checks and CT-log matching (Phase 9) to disagree on identity.
  • Assuming subjectKeyIdentifier uniqueness — it is a hash of the public key, not a request identifier; collisions across distinct requesters with distinct keys are expected and benign, but must never be conflated with serial uniqueness (I6).

⬜ Phase 5 — Certificate-Path Building and RFC 5280 Section 6 Validation §17

Objectives

Implement pki-path: path building from a leaf certificate to a configured TrustAnchor, and full RFC 5280 section 6 validation (§8.5) including name constraints and policy mapping (I5, I11).

Deliverable

A pki-path validator that accepts every valid chain and rejects every single-field mutation of it (property test), passing the initial PKITS subset wired in this phase.

Acceptance
  • 100% pass rate on the ~40 initial NIST PKITS fixtures wired this phase (conformance/pkits/basic-*); full suite gated in Phase 11 (§23).
  • Mutation property test: given 50 valid chains, mutate exactly one field per trial (1,000 trials) — 100% of mutated chains rejected with a correct PathFailure reason.
  • Worked 3-cert chain (§8.5) accepts; worked path-length-violation chain (§8.5) rejects with PathFailure::PathLengthExceeded.
  • Path-validation p99 latency ≤ 25 ms for a 4-certificate chain (feeds TLS-Handshake project 48's consumption budget).
Fixtures
  • conformance/pkits/basic-valid-chain.der
  • conformance/pkits/pathlen-overflow.der
  • conformance/pkits/name-constraint-excluded-subtree.der
  • conformance/pkits/policy-mapping-mismatch.der
  • conformance/pkits/expired-intermediate.der
Pitfalls
  • Implementing name constraints as subject-only checks and forgetting subjectAltName entries must also be checked against permitted_subtrees (a historical class of real-world path-validation bugs).
  • Treating anyPolicy as always satisfying every certificatePolicies requirement even when inhibitAnyPolicy has activated — must respect the counter.
  • Off-by-one in path-length counting: self-issued (renewal) certificates do not count against pathLenConstraint per RFC 5280 section 6.1.4(k) — a common implementation bug.

⬜ Phase 6 — CRL Generation and Publication §18

Objectives

Implement pki-crl: base and delta CRL generation (RFC 5280 section 5, §8.3) on the §4 cadence, integrated with pki-path's revocation-check step (Phase 5) as the first live revocation source.

Deliverable

A CRL publication pipeline where a revoked certificate appears in the next scheduled delta CRL and is rejected by pki-path's live revocation check within the freshness bound.

Acceptance
  • Revocation-to-CRL-appearance latency ≤ 4 h (next delta-CRL cycle, §4) in 100/100 simulated revocation-then-publish trials.
  • Base CRL size stays ≤ 2 MB and delta CRL ≤ 200 KB at a simulated 500,000-entry revoked-certificate population (§4, §34).
  • pki-path correctly rejects a revoked-then-presented certificate within one publication cycle in 100% of the PKITS revocation fixtures wired this phase.
  • CRL signature verifies against the issuing CA's public key in 100% of generated CRLs.
Fixtures
  • conformance/crl/revoke-then-verify.json
  • conformance/pkits/revoked-intermediate.der
  • conformance/crl/delta-crl-merge.der
  • conformance/crl/oversized-entry-count.json — triggers size-ceiling alert
Pitfalls
  • Publishing a delta CRL without a matching base-CRL reference (the delta-indicator extension must name the exact base CRL number it extends) — a mismatch silently breaks client-side merging.
  • Forgetting reason-code propagation into crlEntryExtensions — some relying parties key behavior off revocation reason (e.g. certificateHold is reversible, unlike others per I9's monotonicity, which applies only to non-hold reasons).
  • CRL-signing-session contention with leaf-signing sessions starving the CRL publication schedule under load — must be isolated (18.2).

⬜ Phase 7 — The OCSP Responder and Stapling §19

Objectives

Implement pki-ocsp: pre-signed OCSP response generation (ADR-10), the request-serving path (RFC 6960, §8.4), and the artifact format consumed by TLS 1.3 stapling (section 4.4.2.1 of RFC 8446, RFC 6961 multi-stapling, ADR-11).

Deliverable

An OCSP responder sustaining the §4 QPS target, serving pre-signed responses within the freshness bound, with a working stapling-artifact export verified against a TLS 1.3 handshake fixture.

Acceptance
  • Sustained 20,000 req/sec across the responder fleet for 10 minutes, p50 ≤ 5 ms / p99 ≤ 50 ms (§4).
  • Zero stale-serve violations (I13) across a 24 h soak test against the 10-minute TTL.
  • Stapling-artifact fixture validates against a reference TLS 1.3 status_request decoder (RFC 8446 section 4.4.2.1 conformance).
  • On-demand fallback path stays within 1% of total request volume in steady state (cache effectiveness target).
Fixtures
  • conformance/ocsp/pre-signed-cache-hit.json
  • conformance/ocsp/on-demand-fallback.json
  • conformance/ocsp/stapling-artifact-tls13.bin
  • conformance/ocsp/stale-response-rejected.der
Pitfalls
  • Serving a cached response past nextUpdate under refresh-job failure — must fail closed (serve unknown or refuse) rather than serve stale good (I13, P6).
  • Nonce mismatches causing legitimate multi-stapling (RFC 6961) clients to be rejected — the multi-stapling path must handle the "no nonce" pre-signed-response case gracefully.
  • Underestimating refresh-job thundering-herd at TTL boundaries — stagger refresh schedules across the active-certificate population rather than a single synchronized refresh wave.

⬜ Phase 8 — The ACME Server (http-01 / dns-01) §20

Objectives

Implement pki-acme: the full RFC 8555 account/order/authorization/challenge/finalize state machine (§8.6), integrated with the RA/policy path (P2, ADR-12) rather than bypassing it.

Deliverable

An ACME endpoint that completes a full issuance cycle with a real ACME client across both challenge types, producing a certificate indistinguishable (audit-wise) from an RA-direct issuance.

Acceptance
  • Real-client interoperability test passes for both http-01 and dns-01 in CI, 3 consecutive green runs.
  • Replay-nonce reuse attempt rejected in 100/100 trials (RFC 8555 section 6.5 conformance).
  • ACME-originated CertificateRequests produce identical PolicyVerdict/audit-chain shape to RA-direct requests in a differential comparison (P11 boundary-preservation check).
  • Challenge-validation timeout enforced at ≤ 10 s per attempt with a bounded retry count (prevents indefinite-pending orders).
Fixtures
  • conformance/acme/http01-success.json
  • conformance/acme/dns01-success.json
  • conformance/acme/replay-nonce-reuse.json — must reject
  • conformance/acme/malformed-jws.json — must reject
Pitfalls
  • JWS canonicalization mismatches between client and server JSON serialization — historically a real interoperability failure class across ACME implementations.
  • Treating challenge validation as a one-shot check — DNS propagation delay requires bounded retry with backoff, not an immediate single query.
  • Allowing an AcmeOrder to bypass the same SAN-validation-evidence linkage (I14) that RA-direct requests require — a boundary violation that would let ACME become a mis-issuance side-channel.

⬜ Phase 9 — Certificate Transparency Submission and SCT Handling §21

Objectives

Implement pki-ct: precertificate/certificate submission to ≥2 independent CT logs (RFC 6962), SCT collection, and the release-gating quorum check (P3, I2).

Deliverable

Every certificate released by this CA carries ≥2 verified SCTs, verifiable independently against the public CT-log ecosystem's own mirrors.

Acceptance
  • 100% of certificates released in a 24 h soak test carry ≥2 valid, independently re-verifiable SCTs (I2).
  • CT submission p95 latency ≤ 2 s to first log; total added issuance latency p95 ≤ 500 ms (§4).
  • CT-log-outage simulation (1 of 3 configured logs down): issuance continues via the remaining logs meeting quorum; 2-of-3-down simulation: issuance holds and pages, zero certificates released below quorum in 50/50 trials.
  • SCT-signature verification rejects 100% of 20 tampered-signature fixtures.
Fixtures
  • conformance/ct/precert-submission-success.json
  • conformance/ct/quorum-not-met-hold.json
  • conformance/ct/tampered-sct-signature.der
  • conformance/ct/sct-embedding-valid.pem
Pitfalls
  • Submitting the final (non-poisoned) certificate to a log expecting a precertificate flow — protocol-sequence errors here can leak an unlogged certificate into circulation before SCTs are verified.
  • Trusting a log's SCT without local signature verification — a compromised or misbehaving log's unverified SCT would defeat the entire point of P3.
  • CT submission latency variance across logs causing the slowest reachable log to dominate p95 — implement per-log timeout with early quorum satisfaction (don't wait for all configured logs if quorum is already met).

⬜ Phase 10 — Revocation Lifecycle, Renewal, and the Audit Log §22

Objectives

Implement pki-audit's durable, hash-chained backend (replacing Phase 0's in-memory skeleton) and complete the certificate lifecycle state machine (§8.8): renewal and the full revocation-request/approval workflow with dual-control for high-privilege certificates (P13, I9).

Deliverable

A durable, tamper-evident audit log covering every phase's events from Phase 0 onward (replayed from the in-memory skeleton), plus a complete renewal and dual-control revocation workflow.

Acceptance
  • Crash-recovery test: kill pki-audit mid-write 50 times under fault injection — 0 corrupted or duplicate sequence_ids on recovery (I8).
  • Dual-control revocation: a single-operator revocation attempt against a CA certificate is rejected in 100/100 trials; a quorum-approved attempt succeeds in 100/100 trials (P13).
  • Renewal produces a new, unique serial (I6) linked to its predecessor in 100% of 1,000 simulated renewals, with zero validity-window overlap violating I1.
  • Revocation-to-CRL/OCSP-invalidation propagation completes within the §4 freshness bound in 100/100 trials (I7, joint with Phase 6/7).
Fixtures
  • conformance/audit/hash-chain-gap-injection.json
  • conformance/revocation/dual-control-single-operator-reject.json
  • conformance/revocation/certificate-hold-then-unhold.json
  • conformance/renewal/serial-uniqueness-1000.json
Pitfalls
  • Renewal implemented as an in-place mutation of the existing CertificateRecord instead of a new record with lineage linkage — violates P12 and breaks CT/SCT correctness (Phase 9 expects a distinct certificate per serial).
  • Dual-control bypass via a shared operator credential — quorum must be enforced by distinct cryptographic identities, not merely two API calls from the same session.
  • Audit hash-chain verification treated as a one-time startup check rather than a continuous scheduled job — corruption introduced mid-runtime (e.g. storage-layer bit rot) goes undetected until the next restart otherwise.

⬜ Phase 11 — Conformance, Chaos, and Performance Hardening §23

Objectives

Run the full NIST PKITS path-validation suite and a complete zlint-style linting pass as CI-gated conformance; execute chaos scenarios (HSM unavailable, CT log down, OCSP responder failover); close out performance hardening against every §4/§30 target.

Deliverable

A CI pipeline that gates every release on full PKITS conformance, zlint conformance, differential-validation agreement, chaos-scenario pass, and perf-regression thresholds — the system's production-readiness bar.

Acceptance
  • 100% pass rate on all ~400 NIST PKITS fixtures.
  • Zero zlint findings across a 10,000-certificate sample spanning every configured IssuingProfile.
  • Differential-validation disagreement rate = 0 across a 100,000-certificate sample against OpenSSL verify.
  • All three chaos scenarios recover within their documented RTO (§4: 15 min) with zero data loss beyond the documented RPO.
  • 7-day soak tests complete with zero SLA-budget breaches (§4: 99.95% issuance, 99.99% OCSP).
Fixtures
  • conformance/pkits/full-suite/ (≈400 fixtures, NIST-published)
  • conformance/lint/mis-issuance-patterns/ (EKU creep, missing SKI, non-canonical DER)
  • conformance/chaos/hsm-unavailable-recovery.json
  • conformance/chaos/ct-log-down-quorum-hold.json
Pitfalls
  • Treating "PKITS passes" as sufficient without the differential-validation cross-check — PKITS is necessary but not sufficient; a bug shared between pki-path and its own test fixtures would pass PKITS while still diverging from real-world relying-party behavior.
  • Running chaos scenarios only against mocked components — masks integration-level failure modes (e.g. real PKCS#11 session-teardown timing under an actual HSM outage).
  • Soak-test false confidence from a synthetic traffic pattern that doesn't match real request-size/SAN-count distributions.
