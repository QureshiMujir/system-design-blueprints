Decisions (§9) · 26 ADRs

ADR-01

Extension language

Chosen

Pure Python + Triton kernels

Rejected

Rust/PyO3 LoRA layer, C++ extension

When the rejected choice is right

An embedded/edge deployment with no Python runtime, where a static Rust binary is the actual requirement

Why: GEMMs already run in cuBLAS/Triton; a systems language adds build cost with no measured speedup

ADR-02

Phase-0 target modules

Chosen

q_proj, v_proj only

Rejected

all-linear, qkvo

When the rejected choice is right

A fine-tune must shift MLP-stored factual knowledge (domain-vocabulary infusion) — all-linear wins

Why: Hu et al., section 7.1: q,v closes 80% of the full-fine-tune gap at r=8

ADR-03

Default rank/alpha

Chosen

r=8, α=16 (α=2r)

Rejected

r=32/64, α=r

When the rejected choice is right

High intrinsic-dimensionality tasks (multi-task instruction mixtures) benefit from r=32–64

Why: PEFT-community convention, cheap ablation starting point

ADR-04

Dropout placement

Chosen

On input to A

Rejected

Between A and B, none

When the rejected choice is right

Extremely small datasets (<200 examples) underfit with any dropout — 0 wins

Why: Regularizes the low-rank projection without perturbing the α/r merge math

ADR-05

Checkpoint format

Chosen

safetensors

Rejected

pickle, PyTorch .bin

When the rejected choice is right

Disposable single-session research notebooks with no sharing, where the safety guarantee has no payoff

Why: No arbitrary code execution at load; HF PEFT's default

ADR-06

Adapter config schema

Chosen

Rejected

ADR-07

QLoRA base quantization

Chosen

Rejected

When the rejected choice is right

Inference-only serving with no further fine-tuning, where GPTQ/AWQ calibration beats NF4 at fixed bit-width

ADR-08

Chosen

Rejected

When the rejected choice is right

Short runs (<500 steps) where the EMA hasn't stabilized — fixed-rank LoRA is more stable

Why: Zhang et al.: redistributes budget to modules that need it

38. Alternative Architectures (Roads Not Taken)

Alt-1 — Full-model distillation to a smaller dense student.

teacher (base+adapter, large)  --distill(logits/hidden)-->  student (small, dense)

Regime where it wins: inference cost dominates and a large one-time offline distillation budget is affordable. Real system: DistilBERT-lineage and Alpaca-style distillation pipelines. Rejection reason: loses per-tenant customization and hot-swap (§24); a distilled student requires full retraining per update, defeating the 1–100 MB incremental-update story (§4) this blueprint is built around.

Alt-2 — Full fine-tuning with ZeRO-Infinity CPU/NVMe offload instead of PEFT.

GPU HBM <-> CPU RAM <-> NVMe   (ZeRO-Infinity tiered offload, all params + optimizer state)

Regime where it wins: a domain shift so large that a rank-bounded adapter genuinely cannot reach it (rare in practice per Hu et al.'s ablations) and a large compute budget is available. Real system: DeepSpeed ZeRO-Infinity full fine-tunes. Rejection reason: 100–1,000× storage and serving cost per tenant (a full checkpoint vs. an adapter, §4), and no hot-swap story at all.

Alt-3 — Mixture-of-LoRA-Experts (LoRA-MoE), token-level adapter routing.

token -> router -> {adapter_1, adapter_2, ..., adapter_k}  (weighted combination per token)

Regime where it wins: multi-domain single-tenant serving needing per-token specialization within one request. Real system: research systems in the LoRAHub/MoLE lineage. Rejection reason: added routing complexity and inference latency are not justified for this blueprint's production shape — one active adapter per tenant request (§24) — where the isolation and latency guarantees of a single-adapter dispatch are simpler to make and to audit (T3).

Alt-4 — Soft-prompt-only tuning as the sole PEFT method.

[virtual_1]...[virtual_k] + real_tokens  ->  frozen base  ->  output

Regime where it wins: extremely large models (>50B) where Lester et al. show prompt-tuning closes the gap to full fine-tuning. Real system: prompt-tuning as used in production on PaLM-class models at Google. Rejection reason: underperforms at <10B scale (Lester et al., section 4), which is this blueprint's primary Phase 0–6 target range — a single-method engine would underperform LoRA/DoRA across the majority of this blueprint's target model sizes.
