118 — LoRA / Fine-Tuning Engine

Project Number: 118

Project Name: LoRA / Fine-Tuning Engine

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a parameter-efficient fine-tuning (PEFT) engine that wraps a frozen, read-only base causal-LM with a configurable set of low-rank and additive adapters — LoRA, QLoRA, AdaLoRA, DoRA, IA3, prompt-tuning, prefix-tuning — trains only the adapter parameters against a label-masked instruction/chat loss, and serves the result either merged (adapter-free, zero-overhead inference) or hot-swapped (many adapters, one resident base model, per-request selection). The system is the mechanism by which a 1–100 MB adapter checkpoint substitutes for a multi-gigabyte full fine-tune while remaining bit-tolerant equivalent to it under merge (I6, §7).

Phase-0 deliverable — numbered modules:

  1. peft_engine.types — LoraConfig, AdapterMethod, TaskType (§11).
  2. peft_engine.adapters — LoraLinear and the Adapter base contract (§11, §13).
  3. peft_engine.model_prep — the replacer, freeze pass, target-module registry (§14).
  4. peft_engine.dataset — instruction/chat loaders, collator, label-mask (§15).
  5. peft_engine.chat_templates — the Jinja-template registry and render engine (§15).
  6. peft_engine.training — the driver composing rank-114's TrainingLoop (§16).
  7. peft_engine.training.checkpoint — adapter-only save/resume (§17).
  8. peft_engine.cli — train, inspect entry points (§12).
  9. conformance/corpora/gradient_isolation — the frozen-base invariant fixtures (§12.5).

System boundaries.

  • Provides: adapter injection/removal, adapter-only optimizer construction, label-masked instruction training, adapter-only checkpointing, merge/unmerge, multi-adapter serving, quantized (QLoRA) training, eval-during-train.
  • Delegates: gradient accumulation, mixed precision, gradient clipping, LR scheduling, and checkpoint-resume mechanics to the rank-114 Training-Loop project (P12, §6); tokenizer plumbing to the rank-38 Tokenizer project; checkpoint sharding and on-disk layout to the rank-36 File-System project; multi-GPU process-group orchestration to FSDP/DeepSpeed (Phase 13, §25); base-model architecture definitions to the rank-22 Transformer project.
  • Does NOT provide: base-model pretraining, RLHF/DPO post-training (PhaseDeferred("§8")), a hosted multi-tenant control-plane UI, tokenizer training, dataset curation/labeling tooling, or a general-purpose model registry beyond the adapter table (§24).

Non-goals: full-parameter fine-tuning as a first-class path (Alt-2, §38); a single "one true adapter method" — the engine is deliberately a toolbox; real-time online/continual learning during serving.

Deployment model: a training job runs as a single process (Phase 0–8) or a FSDP/DeepSpeed process group (Phase 13) on GPU hosts with local or S3-mirrored datasets; the serving layer runs as a long-lived process holding one base model and a hot-swappable adapter table, fronted by an HTTP/gRPC router (§24).

Target users/operators: ML engineers running fine-tune experiments; platform engineers operating multi-tenant adapter-serving fleets; on-call engineers debugging divergent training runs or cross-tenant serving incidents.

What later phases unlock: QLoRA (Phase 7) unlocks 65–70B-parameter fine-tuning on a single 48 GB GPU; AdaLoRA (Phase 8) unlocks budget-aware rank allocation; DoRA (Phase 9) unlocks closing the residual LoRA-vs-full-fine-tune quality gap; IA3/prompt/prefix (Phase 10) unlock the minimum-parameter regime; merge/export (Phase 11) unlocks adapter-free batch inference; multi-adapter serving (Phase 12) unlocks hundreds-of-tenants-per-GPU deployment; distributed training (Phase 13) unlocks fine-tuning models too large for one GPU even under QLoRA.

Recommended language: Python 3.11 (PyTorch 2.3+, Triton for fused kernels). Rationale: the entire PEFT/LLM ecosystem this engine must interoperate with — HuggingFace transformers, PEFT, bitsandbytes, DeepSpeed, FSDP, Axolotl, Unsloth — is Python-native; the GEMMs that dominate wall-clock (the BAx low-rank product, the base Wx) already execute in cuBLAS/ Triton, not host-language code, so a systems language buys negligible throughput while costing interop. Rejected: Rust (a PyO3 LoRA extension was prototyped; ADR-01 — build-tooling cost with no measurable forward/backward speedup since GEMMs are not host-language-bound); C++ (would require re-hosting the entire transformers model zoo, an unbounded maintenance liability); Julia (strong numerics story, negligible ecosystem overlap with the checkpoint/ quantization formats this project must consume). Triton, not CUDA C, is used for the Phase-9/13 fused kernels (ADR-17) because it compiles in-tree without a separate toolchain.

Prerequisites: the Transformer project (rank 22, base-model architecture); the Training-Loop project (rank 114, AMP/accumulation/clipping substrate); the Tokenizer project (rank 38, chat-template token plumbing); the File-System project (rank 36, checkpoint sharding); the Distributed-Training project (rank 90, FSDP/DeepSpeed integration, Phase 13); the Quantization project (rank 121, NF4/GPTQ/AWQ primitives under QLoRA). Read Hu et al. 2021 end to end before starting; skim QLoRA, AdaLoRA, DoRA before Phase 7–9.

Estimated timeline: Phase 0 in 1 week (rank-8 LoRA on q,v of a 124M-parameter base, <10 MB checkpoint, gradient-isolation invariant asserted); full system (Phase 0–13) in 7–8 months.

Deferred features (full table: Deferred Features Register, §39): RLHF/DPO training PhaseDeferred("§8"); LoRA-MoE token-routing PhaseDeferred("§38"); full-model distillation export PhaseDeferred("§38"); sub-4-bit edge export PhaseDeferred("§19"); public adapter-hub service PhaseDeferred("§26"); native vLLM/TGI serving integration PhaseDeferred("§24"); speculative decoding with adapters PhaseDeferred("§35"); federated multi-org co-training PhaseDeferred("§31").

2. Why Build This

  • The unique systems knowledge it teaches: how a 7-billion-float optimization problem collapses to a 3-million-float one without losing most of the quality — the actual linear-algebra and systems mechanics of parameter-efficient adaptation, not the API call.
  • Why it matters architecturally: LoRA is the first PEFT method to make "one base model, many customers" an operationally cheap deployment shape; every serving system built since 2022 (vLLM multi-LoRA, Predibase LoRAX, S-LoRA) is answering the scheduling/isolation problem this blueprint's Phase 12 specifies.
  • Why it matters historically: it is the pivot point between "fine-tuning means renting a cluster" (2018–2021) and "fine-tuning fits on a laptop GPU" (2023–). QLoRA (Dettmers et al.
    1. is the paper that made a 65B fine-tune a single-GPU weekend project.
  • The engineering muscles it builds: frozen-parameter graph construction and optimizer scoping; label-mask correctness under tokenizer offset ambiguity; lossless weight-merge reasoning under floating-point tolerance; quantization/adaptation composition; multi-tenant GPU-resident state isolation.
  • Cross-links to sibling systems: the Training-Loop project (rank 114) supplies the substrate this project must not reimplement (P12, §6); the Quantization project (rank 121) supplies NF4/GPTQ/AWQ that QLoRA (Phase 7) composes with; the Distributed-Training project (rank 90) supplies FSDP/DeepSpeed that Phase 13 integrates; the KV-cache/serving project (rank 96, if built) is the natural neighbor of Phase 12's hot-swap router.
  • Calibration value: this is one of the few blueprints where every claim is independently checkable against a public paper and a public reference implementation (PEFT, Unsloth, Axolotl) — a rare closed-loop calibration opportunity for both the author and the reviewer.

What Mastery Looks Like — after building this, the reader can:

  1. Derive the trainable-parameter count and checkpoint size for any rank/target-module combination from first principles (Phase 0, §12; Back-of-Envelope Capacity Model, §36).
  2. Explain why B is zero-initialized and why that is a correctness property, not a convenience (Phase 1, §13; MM2, §34).
  3. Compose quantization and adaptation without special-casing either (Phase 7, §19; MM4, §34).
  4. Reason about AdaLoRA's importance-score pruning as regret-minimization under a rank budget, and predict when it underperforms fixed-rank LoRA (Phase 8, §20; MM6, §34).
  5. Explain the DoRA magnitude/direction split and predict which task classes benefit most (Phase 9, §21; MM7, §34).
  6. Design a multi-tenant, hot-swap adapter-serving system with the same isolation guarantees a connection-pooled multi-tenant database would require (Phase 12, §24; MM8, §34).
  7. Debug a diverged training run, a cross-tenant serving leak, and a merge-corruption incident from first telemetry principles (Failure Modes & Recovery, §27).
  8. Defend, with real regimes, every rejected alternative in the ADR table (§9) and the Alternative Architectures section (§38).

Base model box — loaded once, read-only for the life of the process; requires_grad=False is set at injection time, not merely "by convention" (I1, §7). Replacer/freeze box — the only code path permitted to mutate the module tree; installs one of LoraLinear / AdaLoraLinear / DoraLinear / IA3Linear per matched target module (§11, §14). Chat template box — a pure function from (conversation, tokenizer) to (input_ids, labels); the template name travels with the checkpoint, never with the base model card (P3, §6). Training driver box — never re-implements AMP/accumulation/clipping (P12, §6); the concurrency boundary is exactly rank-114's TrainingLoop internals, opaque to this project. Checkpoint box — the persistence boundary; the only artifact written to durable storage by default is adapter tensors + metadata (P9, §6). Merge box vs. AdapterStore box — the two production exit paths: merge trades hot-swap flexibility for zero-overhead single-tenant inference; the store trades a small per-token overhead for many-tenants-per-GPU (§38, Alt discussion). All later sections stay consistent with this diagram; a section that contradicts a box here is a defect.

6. Design Principles

  1. P1 — Adapter-Only-Trainable. Rule: every base parameter has requires_grad=False set at injection time; the optimizer is built from filter(lambda p: p.requires_grad, ...). Tradeoff: forecloses any recipe that wants to unfreeze a base layer implicitly. Operational implication: a single unit test at training start (I1, §7) is sufficient to catch every violation. Violating it: optimizer state balloons silently, VRAM budget (§4) blown, no error until OOM.
  2. P2 — Label-Masking-Is-Correct-Not-Approximate. Rule: prompt, scaffolding, and padding tokens carry label -100; only assistant-response tokens contribute to loss. Tradeoff: requires the chat-template engine to emit the mask, adding a coupling. Violating it: the model learns to predict user turns, not to follow instructions — a silent quality bug, not a crash.
  3. P3 — Chat-Template-Is-Data-Not-Code. Rule: the template name is stored in the adapter checkpoint; inference reads it from there, never from the base-model card. Tradeoff: one more field in AdapterMeta (§11). Violating it: FM-5 (§27), the most common LoRA-deployment bug in production.
  4. P4 — Base-Frozen-By-Default-Unfreeze-Is-Explicit. Rule: any unfrozen base parameter (e.g. embeddings for vocabulary extension) requires an explicit embeddings_trainable=true recipe flag. Tradeoff: vocabulary-extension recipes need one more line. Violating it: I1's frozen-param scan produces false positives/negatives depending on which list it trusts.
  5. P5 — Merge-Is-Lossless. Rule: W' = W + s·BA reproduces the unmerged forward within 1e-6 absolute tolerance at the same dtype (I6, §7). Tradeoff: merge-then-quantize must be a separate, explicitly lossy operation with its own calibration (§23). Violating it: FM-4 (§27), silent output drift after merge.
  6. P6 — Multi-Adapter-Isolation. Rule: two mounted adapters never share A/B tensor storage; a request's forward touches exactly one adapter's tensors. Tradeoff: per-adapter memory is not shared even when two adapters are numerically similar. Violating it: T3/FM-8 (§26/§27), a cross-tenant data leak.
  7. P7 — QLoRA-Compatible-Forward. Rule: LoraLinear composes with a Params4bit base without special-casing; dequantization happens beneath the adapter, not inside it (MM4, §34). Tradeoff: the adapter forward cannot assume a dense nn.Linear base. Violating it: Phase 7 (§19) becomes a fork of Phase 1 (§13) instead of a composition.
  8. P8 — Target-Module-Config-As-Data. Rule: which modules receive adapters is declared in LoraConfig.target_modules, resolved via the per-architecture registry (§11.7), never hardcoded per model family. Tradeoff: a new architecture needs a registry entry before it works. Violating it: ADR-25's rejected alternative (graph autodetection) reappears as ad hoc per-model branches.
  9. P9 — Save-Only-Adapter. Rule: the default checkpoint contains adapter tensors + config + chat template + tokenizer reference; base weights are never written by the training driver. Tradeoff: a "save full merged model" path (§23) is opt-in, not default. Violating it: checkpoint size stops being bounded by adapter rank (§4).
  10. P10 — Eval-During-Train. Rule: validation loss every 100 steps, perplexity every 500, downstream metrics end-of-epoch (§4 cadence); a run that cannot report validation loss is misconfigured, not "just running." Tradeoff: eval wall-clock is a tax on every run (M12, §32). Violating it: overfitting (§18, Phase 6) is detected only after the run ends, if at all.
  11. P11 — Reproducible-By-Config. Rule: one YAML recipe fully specifies a run; git SHA, package versions, recipe hash, and seed are stamped into checkpoint metadata (I12, §7). Tradeoff: no shell-flag overrides at run time. Violating it: FM-11 (§27), a resumed run that cannot be shown to be the same experiment.
  12. P12 — Substrate-Delegation. Rule: gradient accumulation, mixed precision, gradient clipping, LR scheduling, and checkpoint-resume mechanics are rank-114's TrainingLoop; this project supplies only the Trainable adapter surface. Tradeoff: this project cannot diverge from rank-114's substrate semantics without an ADR. Violating it: duplicated, untested AMP/accumulation logic — the single highest-risk reimplementation bug class.
  13. P13 — Zero-Init-B. Rule: B is initialized to zero (never A) so the adapter contributes exactly zero at step 0 (I3, §7; MM2, §34). Tradeoff: A's Kaiming init alone determines the initial gradient direction. Violating it: the wrapped model does not behave identically to the unwrapped base at step 0, breaking the "wraps an existing model" promise.
  14. P14 — Quantization-Is-Orthogonal-To-Adapter-Math. Rule: NF4 dequantization is a property of the base layer's storage, invisible to the adapter forward's algebra (MM4, §34). Tradeoff: the adapter library cannot assume a fixed base dtype. Violating it: a quantization-aware adapter fork per method, quadrupling the maintenance surface across LoRA/AdaLoRA/DoRA/IA3.

These IDs (P1…P14) are referenced throughout §12–§25 (each phase's N.2) and in the ADR table (§9).

8. Domain Model

Low-rank adapter equation (LoRA, Hu et al. 2021). For a frozen linear y = Wx with W ∈ R^{out×in}, the adapted forward is:

y = W x + s · B (A x)              s = α/r  (default)  or  α/√r  (rsLoRA, ADR-03)
A ∈ R^{r×in}   (down-projection, Kaiming-init)
B ∈ R^{out×r}  (up-projection, zero-init — I3, P13)

Merge / unmerge (P5, I6).

merge:    W' = W + s·B@A                      (in place, destructive; original W discarded
                                                unless the caller preserves it)
unmerge:  W  = W' - s·B@A                     (requires the original A, B retained)

AdaLoRA SVD-form (Zhang et al. 2023). BA is reparameterized as P · diag(E) · Q with P ∈ R^{out×r}, E ∈ R^{r} (learned singular values), Q ∈ R^{r×in}. The importance score per singular index k is an EMA of |E_k · ∂L/∂E_k|; every N steps the bottom-k% indices by importance are zeroed and excluded from future gradient updates (I11 enforces the resulting rank never grows back).

DoRA decomposition (Liu et al. 2024). V = W + s·BA (the LoRA-augmented direction); W_eff = m ⊙ (V / ‖V‖_c) where m is a learned per-column magnitude vector initialized to ‖W‖_c (column norm of the original base weight, ADR-09) and ‖·‖_c is the column-wise norm. LoRA is applied to the direction term only; the magnitude is a separate, small (out_features) trainable vector.

IA3 (Liu et al. 2022). Three learned per-channel scale vectors l_k, l_v, l_ff, applied element-wise to the key projection output, the value projection output, and the FFN intermediate activation respectively: y = W x ⊙ l. No rank decomposition, no A/B pair.

NF4 quantization (Dettmers et al. 2023). Each weight block of 64 elements is quantized to a 4-bit NormalFloat code via a fixed lookup table NF4[0..15] chosen so each code is equiprobable under a zero-mean unit-variance normal; per-block absmax is stored in fp32 (or, under double quantization, itself 8-bit-quantized in blocks of 256, cutting the effective constant overhead from 0.5 to 0.127 bit/parameter). Dequantization at forward time is w ≈ absmax · NF4[code].

Training-loop state machine.

Worked example. Rank-8 LoRA on q_proj (in=out=4096): trainable params per instance = 2·r·in = 2·8·4096 = 65,536, versus the full matrix's 4096·4096 = 16,777,216 — a 256× reduction per matrix (generalized in §36 #1 to the whole model).

Malformed-input example. Failure-path example. A model_prep.replacer regression that wraps a target module without clearing requires_grad on its base weight is caught by I1's step-0 param-scan before step 1 runs; the run halts with FreezeViolationError("base_model.layers.7.self_attn.q_proj.weight"), naming the exact leaked parameter path (§27, FM-1 contrast: this is a pre-flight abort, not a mid-run divergence).

11.2 Adapter (base contract)

class Adapter(nn.Module, ABC):
    base: nn.Module            # the wrapped frozen layer; never copied, held by reference
    method: ClassVar[AdapterMethod]

    @abstractmethod
    def forward(self, x: Tensor) -> Tensor: ...

    @abstractmethod
    def merge_into_base(self) -> None: ...   # P5: must satisfy I6 within 1e-6

    @abstractmethod
    def trainable_parameters(self) -> Iterator[nn.Parameter]: ...

    @abstractmethod
    def step0_equivalence_delta(self) -> Tensor: ...  # I3 conformance hook

Ownership: base is a reference into the frozen model tree, never a copy (P1). Mutation: merge_into_base is the only sanctioned in-place mutation of base.weight, and only once (P5). Concurrency: forward is reentrant and thread-safe under PyTorch's autograd; merge_ into_base is not concurrency-safe and must hold an exclusive lock in serve.AdapterStore. Persistence: adapters serialize only their trainable tensors (P9). Compatibility: every concrete adapter implements all four abstract methods identically across AdapterMethod variants — no partial implementations.

11.3 LoraLinear

class LoraLinear(Adapter):
    method: ClassVar[AdapterMethod] = AdapterMethod.LORA
    r: int
    alpha: int
    scaling: float
    lora_A: nn.Parameter   # (r, in_features) — Kaiming or PiSSA init
    lora_B: nn.Parameter   # (out_features, r) — zero-init (I3, P13)
    dropout: nn.Module

    def __init__(self, base: nn.Linear, r: int, alpha: int,
                 dropout: float, init: str = "kaiming",
                 use_rslora: bool = False) -> None: ...
    def forward(self, x: Tensor) -> Tensor: ...     # y = base(x) + scaling*dropout(x)@A^T@B^T
    def merge_into_base(self) -> None: ...          # base.weight += scaling * B @ A (§8)

Ownership: lora_A/lora_B are the only trainable tensors; base is read-only (P1, P7). Mutation: merge_into_base zeroes lora_A/lora_B after folding into base.weight to prevent double-counting on a subsequent forward. Concurrency: safe for concurrent forward across requests when not concurrently merging (I7). Persistence: lora_A/lora_B are the only tensors written to the safetensors payload (P9). Compatibility: shape is fully determined by (r, in_features, out_features), checked against LoraConfig at load (I9).

11.4 AdaLoraLinear, DoraLinear, IA3Linear

class AdaLoraLinear(Adapter):
    method: ClassVar[AdapterMethod] = AdapterMethod.ADALORA
    P: nn.Parameter        # (out_features, r)
    E: nn.Parameter        # (r,) — learned singular values, pruning target (I11)
    Q: nn.Parameter        # (r, in_features)
    ranknum: nn.Parameter  # non-trainable, current active rank

    def forward(self, x: Tensor) -> Tensor: ...       # y = base(x)+ (α/ranknum)·(x@Q^T*E)@P^T
    def orth_regularization(self) -> Tensor: ...       # ‖P^TP−I‖²+‖QQ^T−I‖² (§20.2)

class DoraLinear(Adapter):
    method: ClassVar[AdapterMethod] = AdapterMethod.DORA
    lora_A: nn.Parameter
    lora_B: nn.Parameter
    magnitude: nn.Parameter   # (out_features,) — init = ‖base.weight‖_c (ADR-09)

    def forward(self, x: Tensor) -> Tensor: ...  # V=W+s·BA; y=linear(x, m*(V/‖V‖_c))

class IA3Linear(Adapter):
    method: ClassVar[AdapterMethod] = AdapterMethod.IA3
    scale: nn.Parameter       # (out_features,), init 1.0

    def forward(self, x: Tensor) -> Tensor: ...  # y = base(x) * scale

Ownership/mutation/concurrency/persistence as §11.2/§11.3, specialized per method. E's pruning (AdaLoraLinear) is the only trainable tensor that shrinks its effective footprint mid-run (I11); magnitude (DoraLinear) and scale (IA3Linear) never change shape. Compatibility: AdaLoraLinear checkpoints carry ranknum so a resumed run restores the exact pruned budget, not the initial one.

    embedding: nn.Embedding    # (num_virtual_tokens, hidden_size)

                 init_from_vocab: Optional[Tensor] = None) -> None: ...
    def forward(self, batch_size: int, device: torch.device) -> Tensor: ...

    num_virtual_tokens: int
    num_layers: int
    num_heads: int
    head_dim: int

Ownership: both encoders own their embeddings/MLP fully (no wrapped base, unlike §11.3–4). Mutation: none outside training. Concurrency: forward is stateless given batch_size/ device, safe to call concurrently. Persistence: entire module state dict is the checkpoint payload for these methods (still bounded — num_virtual_tokens is O(10–100)). Compatibility: PrefixEncoder's output shape is coupled to the base model's (num_layers, num_heads, head_dim) — a checkpoint trained against one base architecture is not portable to another.

19.1 Objectives

Implement the paged-optimizer integration (CPU-offload on VRAM pressure, Dettmers et al., section 4) as an training.optimizer flag, not a separate optimizer implementation. Paged-optimizer CPU-offload activity should be monitored (PCIe transfer volume) since excessive paging indicates the VRAM budget is mis-sized for the recipe, not that paging itself is broken.

19.8 Edge Cases

Gradient checkpointing recomputes the forward during backward — if the paged optimizer is mid-page-out when recomputation needs the dequantized weights, the interaction must not deadlock or silently use stale pages; this is tested by qlora/grad_leak_with_checkpointing under synthetic VRAM-pressure injection. A base model with some layers already in bf16 (mixed-precision base, e.g. a partially-quantized checkpoint) must be explicitly rejected — Phase 7 requires a uniformly NF4-quantized base, not a per-layer mix.

19.9 Failure Analysis

FM-10 (QLoRA throughput collapse) is detected via the M5 perf-regression CI gate, not via correctness tests — it is a performance failure class, not a correctness one, and its recovery is operational (verify the bitsandbytes CUDA build) rather than a code rollback.

19.10 Operational Notes

Metrics: nf4_dequant_throughput_gbps, paged_optimizer_page_out_count, quantized_grad_leak_count (I10). The oom-during-train.md runbook (§10) is extended with a QLoRA-specific branch: check paged-optimizer activity before assuming a hard VRAM ceiling was exceeded.

20. Phase 8 — AdaLoRA: SVD Reparameterization & Budget Pruning

20.1 Objectives

Implement AdaLoRA's SVD-form adapter (P·diag(E)·Q) and its importance-score-driven, monotonically-shrinking rank-pruning schedule (Zhang et al. 2023), letting the optimizer redistribute a fixed total rank budget across modules (I11).

20.2 Detailed Implementation Steps

Implement AdaLoraLinear (§11.4) with the SVD-form forward and the orth_regularization auxiliary loss term (encourages P, Q orthogonality so the SVD form stays meaningful, ADR-08). Implement the importance score as an EMA of |E_k · ∂L/∂E_k| per singular index k (§8 domain model). Implement the pruning scheduler: every N steps, zero the bottom-k% indices by importance and exclude them from future gradient updates, enforcing I11's monotonic-non-increase invariant. Wire the pruning budget as a decaying schedule (start above target rank, shrink to target by a configured step) per ADR-08's "start larger, prune down" policy.

Final per-module rank distribution is non-uniform (at least 2 modules differ in final rank by ≥2), demonstrating actual budget reallocation, not a degenerate uniform prune. orth_regularization loss term decreases by ≥30% from its step-0 value by end of training (evidence P/Q are trending toward orthogonal, per ADR-08's rationale).

20.7 Performance Concerns

The importance-score EMA update and the orthogonality regularizer both add per-step compute proportional to r² per module (the P^TP and QQ^T products) — for large initial rank budgets this is a measurable tax vs. plain LoRA's per-step cost; budget it separately from M1/M2's plain-LoRA overhead targets.

20.8 Edge Cases

A module whose importance score is pruned to rank 0 must be handled as a true no-op (bypass its forward contribution entirely), not as a degenerate rank-0 matrix multiply that still costs a kernel launch. 20.9 Failure Analysis

20.10 Operational Notes

Metric current_rank_budget_by_module dashboarded per training run; a rank-budget-over-time plot is the primary debugging artifact referenced when 20.9's FM-7 is suspected.

21. Phase 9 — DoRA: Weight-Decomposed Low-Rank Adaptation

24.7 Performance Concerns

Heterogeneous-adapter batched inference (24.2, serve.batched) requires per-row adapter dispatch inside the batched GEMM rather than a single shared weight matrix — this is structurally more expensive per token than a homogeneous (single-adapter) batch, and is benchmarked separately from M1/M2's single-adapter overhead targets (§35's comparative discussion of vLLM's approach to this same tradeoff).

24.8 Edge Cases

A request naming an adapter_id that was never mounted (typo, stale client cache) must return a clear 404-equivalent, not silently fall back to the base model unadapted (a correctness trap disguised as graceful degradation). Two requests racing to mount the same adapter concurrently must not double-mount (I7's tensor-id-uniqueness check must be atomic w.r.t. concurrent mount calls, not just w.r.t. sequential ones).

24.9 Failure Analysis

FM-8 (cross-tenant contamination) and T10 (use-after-unmount) are Phase-12's two critical failure classes; both have kill-and-page auto-recovery (no silent degraded-mode continuation) because the blast radius (leaked generation content across tenants) is a security incident, not a mere availability one.

24.10 Operational Notes

Metrics: adapter_table_size, swap_race_count (I14), cross_tenant_mismatch_count (T3/FM-8), use_after_unmount_count (T10). Every mount/unmount is audit-logged with tenant id, adapter name, and timestamp — the primary forensic artifact for any Phase-12 incident review.

25. Phase 13 — Distributed Training & Fused Kernels

25.1 Objectives

Scale training beyond a single GPU via FSDP/DeepSpeed ZeRO (rank-90 project integration) and close the remaining throughput gap with Unsloth-style fused Triton kernels (ADR-17), enabling 70B-class QLoRA fine-tuning across multiple GPUs at ≥85% scaling efficiency (M11).

25.2 Detailed Implementation Steps

Integrate rank-90's FSDP/DeepSpeed process-group orchestration with the adapter-only optimizer construction (I2) — the sharding strategy must shard base-model weights (frozen, no optimizer state) differently from adapter weights (trainable, full optimizer state per shard-owning rank), since naively sharding both identically wastes communication on parameters with no gradient. Implement checkpoint sharding/gathering so save_adapter (§11.9) still produces one consolidated adapter-only checkpoint regardless of world size. Implement the fused Triton LoRA forward/backward kernel (peft_engine_triton.lora_fwd/lora_bwd, §10) that fuses the base GEMM and the low-rank delta into one kernel launch (Unsloth's technique, §5), reducing the memory round-trip M1/M2 measure. Implement QLoRA+FSDP composition (P7 extended to the distributed case — NF4 dequantization must happen per-shard, not after an all-gather that would defeat the memory savings).

25.3 Deliverable

peft-engine train recipes/llama3_70b_qlora_fsdp.yaml runs across 8 H100s via FSDP with QLoRA enabled; the fused Triton kernel path is benchmarked against the unfused Phase-1 path on the same hardware.

25.4 Acceptance Criteria

Scaling efficiency from 4→8 H100s ≥ 85% (M11, measured as throughput(8)/(\N2×throughput(4))). Fused Triton kernel reduces adapter forward+backward overhead (M1/M2 combined) by ≥ 30% versus the unfused Phase-1 implementation at equal rank/target-modules. Checkpoint save from an 8-way-sharded run produces byte-identical adapter tensors to an equivalent single-GPU run (sharding-transparency check).

25.6 Pitfalls

Sharding base-model weights and adapter weights with the same FSDP wrapping policy wastes communication bandwidth all-gathering frozen parameters that carry no gradient — the fix is a custom wrapping policy that treats adapter parameters as a distinct, fully-replicated-or- sharded-independently group (25.2). Applying the fused Triton kernel to AdaLoraLinear or DoraLinear without accounting for their different forward shapes (SVD-form vs. magnitude-direction) either produces wrong outputs silently or fails to compile — Unsloth's own kernels are LoRA-specific for this reason (§5 pitfall note), and this project's fused kernels are likewise implemented per-method, not generically.

25.7 Performance Concerns

NF4 dequantization under FSDP must happen after the shard-local all-gather of that shard's quantized weights, not globally, or the memory-savings argument for combining QLoRA with FSDP collapses back to full-precision-equivalent peak memory. Fused-kernel compilation time (Triton JIT) is a cold-start cost (§4's startup budget) — cache compiled kernels across process restarts, not just within a process.

25.8 Edge Cases

An 8-GPU run where one GPU fails mid-training (hardware fault, not a software bug) must be detected by the rendezvous timeout (T11/FM-9) and either checkpoint-and-abort or, if configured, resume on a reduced world size — Phase 13 supports checkpoint-and-abort as the default; elastic world-size resume is out of scope (tracked in the Deferred Features Register, §39, if demand emerges). A fused-kernel path that silently falls back to the unfused implementation on an unsupported GPU architecture must log this fallback loudly (extends FM-10's "silent degradation" concern to the kernel-fusion case specifically).

25.9 Failure Analysis

FM-9 (distributed training hangs at rendezvous) is Phase 13's primary failure class; NCCL timeout (default 1800 s) triggers a bounded 2x-retry-with-backoff before escalating to a halted job with a per-rank rendezvous log for manual network-policy review (T11).

25.10 Operational Notes

Metrics: per-rank rendezvous_auth_failure_count (T11), nf4_dequant_throughput_gbps per shard, fused_kernel_fallback_count. The distributed-training runbook cross-references FM-9's NCCL_DEBUG=INFO guidance and T11's shared-secret rendezvous token rotation procedure.

29. Compatibility & Versioning

Wire compatibility: the adapter checkpoint format (safetensors + adapter_config.json, ADR-05/ADR-06) is versioned via AdapterMeta.package_version (§11.10); a load-time migration table maps old schema versions to the current one, additive-fields-only within a minor version (§1's "additive fields only" rule from §11.1). Storage compatibility: the training checkpoint's resume fields (optimizer_state, rng_state, §17.2) are versioned independently from the distribution fields, since resume compatibility is a stricter, shorter-lived guarantee than distribution compatibility. Schema evolution: a new AdapterMethod variant (e.g. a future PEFT technique) is additive — existing checkpoints never need re-encoding. API stability: the CLI surface (train/eval/merge/serve/inspect, §10) follows SemVer; a breaking CLI-flag change requires a major version bump and a deprecation-cycle warning for one minor version prior. Migration: peft-engine inspect --migrate upgrades an old-schema checkpoint's adapter_config.json in place, re-validating I9's shape-assert post-migration. Deprecation policy: a deprecated recipe field is accepted with a warning for 2 minor versions, then rejected. SemVer policy: MAJOR for checkpoint-format-breaking changes, MINOR for new adapter methods/target-module registry entries, PATCH for bugfixes with no schema impact. Rolling-upgrade guarantees: the serving layer supports mixed-version AdapterStore instances during a rolling deploy — an adapter checkpoint's package_version is checked against the serving binary's supported range at mount time (I9-adjacent check), refusing an incompatible mount rather than loading it partially.

33. Scalability Analysis

What stays constant: trainable-parameter count and checkpoint size as base-model size grows, for a fixed rank/target-module choice — the defining decoupling (§4). What grows: base-model VRAM footprint (O(params), linear); attention FLOPs (O(seq²·layers)); the AdapterStore's index/metadata overhead (O(mounted_adapters), sub-linear in bytes but linear in table-lookup cost). Named bottlenecks in order: (1) base-model VRAM at fixed precision — the first ceiling hit, mitigated by QLoRA (Phase 7); (2) NF4 dequantization throughput (M5) — the second ceiling, since every forward pays this cost; (3) hot-swap table lookup / AdapterStore contention at high mount counts (§32) — the third ceiling, at the multi-tenant serving extreme; (4) distributed rendezvous/all-gather overhead at 8+ GPU scale (M11) — the fourth ceiling, for the largest base models. Horizontal scaling: adding more serving replicas behind the router (§24) scales tenant throughput linearly until per-replica VRAM is saturated (M10's 500-adapter figure is a per-replica budget, not a global one). Vertical scaling: QLoRA (Phase 7) is the primary vertical-scaling lever — it moves the ceiling from "model fits in VRAM at bf16" to "model fits in VRAM at NF4," a 4× improvement in addressable base-model size per GPU. Sharding/partitioning: FSDP shards the base model's read-only weights across ranks (Phase 13); adapter weights are small enough to replicate fully per rank rather than shard, avoiding unnecessary all-gather traffic on the trainable parameters (§25.6). Coordination overhead: rendezvous + gradient all-reduce dominate distributed coordination cost; because only adapter gradients all-reduce (not base gradients, by I1/I2), this coordination volume is orders of magnitude smaller than a full-fine-tune's all-reduce traffic at the same base-model size — the second-order scalability benefit of PEFT beyond checkpoint size. Practical ceiling and levers beyond it: at current single-host 8×H100 scale, ~70B QLoRA is the practical ceiling (§4); levers beyond it are further quantization (sub-4-bit, PhaseDeferred("§19")) or additional node scale-out (not specified in this blueprint — a rank-90 Distributed-Training project concern beyond FSDP/DeepSpeed single-node topology).

34. Mental Models & First Principles

  • MM1 — "A LoRA adapter is a rank-constrained gradient sketch, not a smaller model." Predicts why merging is lossless and why rank choice trades expressivity for parameter count. Bug class without it: treating adapters as independently-trainable mini-networks expected to generalize without the frozen base. Applies in §8 (Domain Model), §23 (Phase 11 merge).
  • MM2 — "Zero-init B makes the adapter a no-op at step 0, not an approximation of one." Predicts step-0 forward equivalence is exact (I3), not approximate. Bug class: initializing both A and B nonzero and being surprised training starts from a perturbed model. Applies in §11.3 (Core Schema), §12 (Phase 0).
  • MM3 — "The optimizer only sees what requires_grad exposes it to." Predicts that freezing is a graph-construction-time decision, not a training-time flag. Bug class: freezing base params after building the optimizer, leaking stale param groups (I2). Applies in §7 (I1/I2), §12 (Phase 0).
  • MM4 — "Quantization and adaptation are orthogonal axes." Predicts QLoRA's forward composes cleanly (dequantize base, then add the adapter delta) without special-casing. Bug class: writing adapter-quantization-aware code paths instead of composing two independent transforms. Applies in §6 (P14), §19 (Phase 7).
  • MM5 — "The chat template is part of the model's contract, not a serving convenience." Predicts template/adapter coupling is load-bearing and that decoupling them is a deployment bug waiting to happen. Bug class: assuming any "close enough" template works at inference. Applies in §6 (P3), §7 (I5), §15 (Phase 3).
  • MM6 — "Importance-score pruning is regret minimization under a rank budget." Predicts AdaLoRA's monotonic-shrink behavior and why growing rank mid-run breaks the metaphor. Bug class: expecting AdaLoRA to reallocate rank upward to a module that later needs more. Applies in §7 (I11), §20 (Phase 8).
  • MM7 — "Magnitude and direction are separable levers on the same weight." Predicts why DoRA closes the LoRA-vs-full-fine-tune gap where plain LoRA cannot: full fine-tuning moves both magnitude and direction, LoRA moves only direction implicitly through BA. Bug class: expecting plain LoRA to match full-fine-tune quality on magnitude-dominated tasks. Applies in §21 (Phase 9).
  • MM8 — "Multi-adapter serving is a scheduling problem wearing a machine-learning costume." Predicts that hot-swap latency, isolation, and VRAM budgeting are the same problems as connection pooling and tenant isolation in any multi-tenant system. Bug class: under-investing in AdapterStore's concurrency correctness because "it's just ML weights." Applies in §7 (I7/I14), §24 (Phase 12).

36. Back-of-Envelope Capacity Model

  1. Trainable params, r=8 q+v, 8B-class base (32 layers, hidden 4096, GQA kv-dim 1024). Formula: r·(in_q+out_q+in_v+out_v)·layers = 8·(4096+4096+4096+1024)·32 = 8·13,312·32 = 3,407,872 ≈ 3.4 M — 0.043% of an 8 B base (chained from §4's parameter-range row).
  2. Adapter checkpoint size, bf16. 3.4 M params × 2 bytes = 6.8 MB — within §4's 1–100 MB band, at the low end (chained from #1).
  3. Optimizer state size, AdamW fp32 (adapter-only). 3.4 M × 2 (momentum+variance) × 4 bytes = 27.2 MB — negligible next to the base model's 16 GB (chained from #1).
  4. VRAM, LoRA bf16 training, 8B base, batch 4 × seq 2048, grad-checkpointed. Base weights: 8×10⁹ × 2 bytes = 16 GB. Adapter+optimizer: 6.8 MB + 27.2 MB ≈ 34 MB (negligible). Activations with checkpointing: ≈ 6–8 GB at this batch/seq. Total ≈ 22–24 GB — fits §4's ≤24 GB single-consumer-GPU ceiling (chained from #1, #3, §4).
  5. VRAM, QLoRA NF4, 70B base, batch 1 × seq 1024. Base: 70×10⁹ × 0.5 byte = 35 GB. Double-quant constant overhead: 70×10⁹ × 0.127 bit / 8 ≈ 1.1 GB. Adapters+optimizer: tens of MB (negligible at this scale too). Activations with checkpointing: ≈ 8–10 GB at batch 1/seq 1024. Total ≈ 45–46 GB — fits §4's ≤48 GB single-GPU ceiling (chained from §4's double-quantization row).
  6. Max concurrent adapters, H100 80GB, r=8 q,v/8B base. Theoretical: (80 GB − 16 GB base) / 6.8 MB ≈ 9,412 adapters. Practical operational budget (§4, M10): ≥ 500 — an 18× headroom margin reserved for KV-cache and per-request activation memory shared across tenants, plus AdapterStore index/table overhead (chained from #2, §4).
  7. Wall-clock per epoch, Phase-0-scale Alpaca-cleaned fine-tune. 52,000 examples × ~350 avg tokens ≈ 18.2 M tokens; at M4's 3,500 tok/s floor: 18.2×10⁶ / 3,500 ≈ 5,200 s ≈ 87 min per epoch on a single H100 (chained from §4's M4 row).
  8. Hot-swap latency budget vs. request latency. M7's 15 ms swap is 15 / 500 = 3% of a typical 500 ms p99 generation-request budget — the swap cost is amortized, not a dominant tail-latency contributor (chained from §4's M7 row).
  9. FSDP 4→8 H100 scaling. At M11's ≥85% efficiency floor, 8-GPU wall-clock for a fixed workload is 4-GPU-time / (2 × 0.85) ≈ 4-GPU-time / 1.7 — not the naive /2 an ideal linear scaling would predict (chained from §4's M11 row).

38. Alternative Architectures (Roads Not Taken)

Alt-1 — Full-model distillation to a smaller dense student.

teacher (base+adapter, large)  --distill(logits/hidden)-->  student (small, dense)

Regime where it wins: inference cost dominates and a large one-time offline distillation budget is affordable. Real system: DistilBERT-lineage and Alpaca-style distillation pipelines. Rejection reason: loses per-tenant customization and hot-swap (§24); a distilled student requires full retraining per update, defeating the 1–100 MB incremental-update story (§4) this blueprint is built around.

Alt-2 — Full fine-tuning with ZeRO-Infinity CPU/NVMe offload instead of PEFT.

GPU HBM <-> CPU RAM <-> NVMe   (ZeRO-Infinity tiered offload, all params + optimizer state)

Regime where it wins: a domain shift so large that a rank-bounded adapter genuinely cannot reach it (rare in practice per Hu et al.'s ablations) and a large compute budget is available. Real system: DeepSpeed ZeRO-Infinity full fine-tunes. Rejection reason: 100–1,000× storage and serving cost per tenant (a full checkpoint vs. an adapter, §4), and no hot-swap story at all.

Alt-3 — Mixture-of-LoRA-Experts (LoRA-MoE), token-level adapter routing.

token -> router -> {adapter_1, adapter_2, ..., adapter_k}  (weighted combination per token)

Regime where it wins: multi-domain single-tenant serving needing per-token specialization within one request. Real system: research systems in the LoRAHub/MoLE lineage. Rejection reason: added routing complexity and inference latency are not justified for this blueprint's production shape — one active adapter per tenant request (§24) — where the isolation and latency guarantees of a single-adapter dispatch are simpler to make and to audit (T3).

Alt-4 — Soft-prompt-only tuning as the sole PEFT method.

[virtual_1]...[virtual_k] + real_tokens  ->  frozen base  ->  output

Regime where it wins: extremely large models (>50B) where Lester et al. show prompt-tuning closes the gap to full fine-tuning. Real system: prompt-tuning as used in production on PaLM-class models at Google. Rejection reason: underperforms at <10B scale (Lester et al., section 4), which is this blueprint's primary Phase 0–6 target range — a single-method engine would underperform LoRA/DoRA across the majority of this blueprint's target model sizes.

40. Glossary

Adapter — a small set of trainable parameters wrapping a frozen base layer. Adapter-only checkpoint — a saved artifact containing only adapter tensors + metadata, not base weights (P9). AdapterMeta — the per-adapter metadata record (§11.10). AdapterStore — the GPU-resident, hot-swappable table of mounted adapters (§11.10, §24). AdaLoRA — a PEFT method reparameterizing BA as an SVD form with importance-driven rank pruning (Zhang et al. 2023). Alpha (α) — the LoRA scaling numerator; combined with rank to form the scaling factor. Base model — the frozen, pretrained model an adapter wraps. bitsandbytes — the native library supplying NF4 quantization and paged optimizers. Block-wise quantization — quantizing weights in fixed-size blocks (e.g. 64 elements) with a per-block scale constant. Chat template — a named Jinja-format function rendering a conversation to tokens+labels. Checkpoint hash / recipe hash — a SHA-256 of the canonical recipe YAML, stamped for reproducibility (I12). Conformance fixture — a named input/expected-output pair asserting one invariant or acceptance criterion. Double quantization — quantizing the quantization constants themselves, reducing QLoRA's per-parameter overhead. DoRA — Weight-Decomposed LoRA; splits a weight into magnitude and direction, adapting direction via LoRA (Liu et al. 2024). Fan-in/fan-out (fan_in_fan_out) — a flag for Conv1D-style layers (GPT-2) whose weight axes are transposed relative to nn.Linear. FSDP — Fully Sharded Data Parallel, a PyTorch-native distributed training strategy. Grouped-query attention (GQA) — an attention variant with fewer key/value heads than query heads, reducing KV-projection parameter count. Gradient accumulation — summing gradients across micro-batches before an optimizer step, to simulate a larger effective batch. Gradient checkpointing — trading recomputation for memory by not storing all activations for backward. Hot-swap — serving a request against a dynamically selected adapter without merging it into the base. IA3 — Infused Adapter by Inhibiting and Amplifying Inner Activations; three learned per-channel scale vectors (Liu et al. 2022). Injection point — the specific linear layer (e.g. q_proj) an adapter wraps. Invariant — a property (I#) that must hold at all times, enforced and telemetered (§7). Label mask — the -100-valued positions in a training example's labels, excluded from loss. LoRA — Low-Rank Adaptation; the W+ (α/r)BA decomposition (Hu et al. 2021). Merge — folding an adapter's delta into the base weight, producing a dense, adapter-free model (P5). Mixed precision — training with a lower-precision compute dtype (bf16/fp16) and higher-precision accumulation. Multi-adapter serving — one resident base model serving many adapters concurrently (§24). NF4 — 4-bit NormalFloat, an information-theoretically optimal 4-bit code for normally-distributed weights (Dettmers et al. 2023). Orthogonality regularizer — AdaLoRA's auxiliary loss term encouraging P/Q orthogonality. Paged optimizer — an optimizer whose state pages out to CPU RAM under GPU memory pressure. PEFT — Parameter-Efficient Fine-Tuning, the umbrella term for LoRA/AdaLoRA/DoRA/IA3/ prompt/prefix methods. Perplexity — the exponentiated average negative log-likelihood, an eval metric. PiSSA — Principal Singular values and Singular vectors Adaptation, an alternative LoRA init from the base weight's SVD. Prefix-tuning — prepending learned per-layer KV-cache prefixes via a reparameterization MLP (Li & Liang 2021). Prompt-tuning — prepending learned soft-token embeddings to the input (Lester et al. 2021). Rank (r) — the inner dimension of the low-rank decomposition BA. Recipe — a YAML file fully specifying a training run (ADR-18). Reparameterization trick — generating a prefix via an MLP rather than optimizing it directly, for training stability. rsLoRA — rank-stabilized LoRA, using α/√r scaling instead of α/r. safetensors — a checkpoint format with no arbitrary code execution at load. Scaling factor (s) — the multiplier (α/r or α/√r) applied to the adapter's output. Sequence packing — concatenating short examples to fill the context length for throughput. SFT — Supervised Fine-Tuning, training on labeled instruction/response pairs. Target module — a named linear layer eligible for adapter injection (e.g. q_proj, v_proj). Triton — a Python-embedded language for writing fused GPU kernels, used for Phase 13's fused LoRA kernels.
