140 — Text Editor Buffer

Project Number: 140

Project Name: Text Editor Buffer

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Definition. Build a production-grade text-editor buffer subsystem — the mutable text-sequence data structure underlying any code editor, IDE, or text-processing tool — that stores an evolving byte sequence under concurrent read/write pressure, exposes insert/delete/slice at O(log n) or better, maintains an incrementally-updated line index, converts positions across five coordinate systems (byte offset, Unicode codepoint, UTF-16 code unit, grapheme cluster, line+column), maintains a coalescing undo/redo history with structural sharing, keeps sticky anchors/marks correct across edits, streams multi-hundred-megabyte files through load/save without materialising the whole file in RAM, and emits an ordered edit-event stream to downstream consumers (syntax highlighter, LSP position synchroniser, CRDT/OT collaboration layer) without those consumers re-deriving a diff — implemented as three interchangeable backends (gap buffer, B-tree rope, piece table) proven behaviourally identical by a differential conformance harness.

Phase-0 deliverable — the following crates scaffolded, compiling, and CI-gated (bodies land in later phases; §12–§21 detail each):

  1. teb-core — typed positions, TextBuffer trait, edit/anchor/observer/snapshot/line-index type vocabulary, error taxonomy.
  2. teb-gap — gap-buffer backend crate (implemented Phase 2, §14).
  3. teb-rope — B-tree rope backend crate (implemented Phase 3, §15).
  4. teb-piece — piece-table backend crate (implemented Phase 4, §16).
  5. teb-positions — typed position-conversion service (implemented Phase 1/6 material folded into §13).
  6. teb-undo — undo/redo stack crate (implemented Phase 6, §18).
  7. teb-io — streaming load/save and encoding crate (implemented Phase 8, §20).
  8. teb-bench — Criterion benchmark harness.
  9. conformance-cli — differential and fixture test runner (skeleton in Phase 0, exercised every later phase).

System boundaries.

  • Provides: byte-accurate text storage/mutation; five-coordinate position mapping; O(log n) line indexing; coalescing undo/redo; sticky anchors; ordered edit-event fan-out with back-pressure; streaming load/save; UAX #29-correct grapheme segmentation; an edit log shaped for external CRDT consumption.
  • Delegates: visual layout and BiDi reordering (UAX #9) to the host renderer; glyph shaping/rendering to the host; syntax parsing to a tree-sitter-style consumer fed by the observer protocol; LSP wire framing to a synchroniser built on top of teb-positions; network transport and conflict resolution for collaborative editing to an external CRDT/OT engine consuming the edit log (§21).
  • Does NOT provide: a GUI or terminal renderer, a full CRDT/OT implementation, an LSP server, a syntax-grammar engine, spell-check, autocompletion, or multi-cursor input handling (multi-cursor is a host feature built on the anchor API, §19).

Non-goals: rendering, networked collaboration transport, spell-check, autocompletion, multi-cursor input semantics, syntax highlighting logic, LSP protocol framing.

Deployment model: embedded library (Rust crate), statically linked into a host editor process. No network service, no daemon, no persistence layer beyond host-directed load/save calls. Single process; internally thread-safe via Send + Sync trait bounds so a host may run the buffer on one thread while observers run on others.

Target users / operators: editor and IDE implementers integrating a buffer subsystem; LSP-tooling authors needing UTF-16-correct position sync; CRDT/OT researchers needing a buffer that emits a causally-orderable edit log. "Operator" in the runbooks (§24) is the host integration engineer debugging a production editor under a live user session.

What later phases unlock: Phase 3 (§15, B-tree rope) unlocks bounded worst-case latency regardless of edit locality, needed once a host serves IDE-scale files with non-local edit patterns (refactors, multi-file search-replace). Phase 4 (§16, piece table) unlocks sub-250ms open of 200MB files by keeping original bytes immutable and mmap-able. Phase 9 (§21) unlocks CRDT-ready collaborative editing without further buffer changes, by making every edit pure, ordered, invertible, and causally addressable.

Recommended language: Rust. Rationale: no GC pause can appear in the edit hot path, which §4 bounds at p99 < 1 µs for a 1 MB rope insert — a stop-the-world pause of even 1 ms is a thousandfold violation; Send + Sync trait bounds give a compile-time proof of the thread-safety the observer protocol (§21) depends on; zero-cost trait dispatch lets three backend representations share one call-site without a runtime tax; the memchr and simdutf8 crates give SIMD-accelerated line-scanning and UTF-8 validation without hand-written intrinsics. Rejected: C/C++ — manual memory management across three recursive tree backends is exactly the CVE class (use-after-free, buffer overrun) that repeatedly hit native text-buffer modules in Atom and early VSCode; Go — GC pauses of 1–10 ms routinely appear under allocation pressure and violate the p99 edit-latency budget (§4); Java/JVM — GC plus JIT warm-up is unsuitable for an embedded library with a cold-start budget (§4, startup < 50 ms); Swift — the cross-platform mmap/SIMD ecosystem for this domain is immature relative to Rust's memmap2/simdutf8.

Prerequisites (systems knowledge required): balanced tree structures (B-trees, red-black trees) and their rebalancing invariants; amortized analysis (the gap buffer's amortized-O(1) argument); UTF-8/UTF-16 encoding and codepoint/surrogate-pair mechanics; Unicode text segmentation (UAX #29 grapheme clusters); persistent/immutable data structures and structural sharing; mmap and page-cache behaviour under concurrent file access.

Estimated timeline: Phase 0 (repository skeleton + correctness kernel) — 2 weeks. Full system (Phases 0–9) — approximately 4 months at one senior engineer full-time, consistent with the phase-line budgets in Appendix B.

Deferred features (every item anchored via PhaseDeferred("§35") to the Deferred Features Register, §35, which resolves): a full CRDT convergence engine (RGA/Logoot/Yjs-class); an LSP server implementation; a syntax-highlighting/parsing engine; BiDi visual-layout computation; GUI or terminal rendering; network transport for collaborative sync; cross-process-restart persistent snapshot serialization; a wasm32 build target; a C ABI surface (teb-ffi).

2. Why Build This

Unique systems knowledge. This is the smallest system that forces reconciliation of three competing correctness/performance regimes in one API: amortized-O(1) locality-exploiting mutation (gap buffer), worst-case-O(log n) mutation independent of edit pattern (B-tree rope), and immutable-original/append-only-delta mutation (piece table) — while a single typed-position layer, a single undo model, and a single observer protocol sit uniformly on top of all three without leaking backend-specific assumptions.

Why it matters architecturally / historically. Every long-lived production editor has rewritten its buffer at least once under load it did not originally design for: Emacs has kept a gap buffer for over 40 years precisely because most editing is spatially local; VSCode migrated from an AVL-tree rope to a piece tree in 2018 after measuring a large-file open-time regression (VSCode engineering blog, §5); Atom's DisplayBuffer and IntelliJ's Document/run-tree each made a different tradeoff in the same design space. The buffer is the one subsystem every other editor feature (rendering, LSP, search, collaboration) is downstream of — get its asymptotics wrong and every feature above it inherits the defect.

Engineering muscles built. Amortized-vs-worst-case tradeoff reasoning under a concrete workload; typed-unit API design that makes an entire bug class a compile error; back-pressured event-fan-out protocol design; streaming I/O design under mmap/page-cache constraints; differential testing across multiple structurally distinct implementations of one contract.

Cross-links to sibling systems. The rope's subtree-summary aggregation (§8) is the same technique LSM-tree storage engines use for range aggregates over sorted runs. The line-index B+-tree (§17) is structurally a database secondary index. The edit log (§21) and its causal deps field share the shape of a distributed database's write-ahead log feeding a replication protocol. The observer back-pressure design (§21) solves the same fast-producer/slow-consumer problem as a message queue.

Calibration value. A candidate who has built this buffer can be handed any "maintain an incrementally-updated aggregate over a mutable sequence under concurrent access" problem — a text buffer, a metrics rollup, a CRDT sequence, a database index — and reason correctly about amortized cost, worst-case bounds, and observer consistency from first principles.

What Mastery Looks Like

  • Derive, from the System Constraints table (§4) alone, which of the three backends a given workload should use, and defend the answer with the Comparative Architecture Table (§31) — built across Phases 2–4 (§14–§16).
  • Explain why a bare usize position parameter is a latent bug generator and design a typed-unit API that makes the bug class a compile error — Phase 1 (§13).
  • Predict, without running a benchmark, which backend degrades under an alternating-ends edit pattern and by how much, from the amortized-vs-worst-case argument alone — Phase 2/3 (§14–§15).
  • Design an incrementally-maintained aggregate (the line index) that never requires a full rescan, and prove its correctness with a from-scratch-recount differential check — Phase 5 (§17).
  • Design an event-fan-out protocol with per-subscriber back-pressure that makes "the highlighter is one edit behind" structurally impossible — Phase 9 (§21).
  • Reason about crash-safety for an in-memory mutable structure that must survive a mid-save crash without corrupting the file on disk — Phase 8 (§20).
  • Explain exactly why VSCode abandoned its rope for a piece tree and why Emacs never abandoned its gap buffer, using the Back-of-Envelope Capacity Model (§32) to justify both numerically.

Boxes, one paragraph each:

Host Application. Owns the Box<dyn TextBuffer>; issues mutations and reads only through the trait (§11); never reaches into backend internals. Concurrency boundary: the host may run on any thread, but a given buffer instance's mutation calls are not internally synchronized — the host serializes writers (I7, §7).

Backend. Exactly one of gap buffer, rope, or piece table is live per buffer instance; all three share the TextBuffer trait and are proven behaviourally identical by the differential harness (§26). Persistence boundary: only the piece table holds a direct relationship to on-disk bytes (the immutable original_buf, possibly mmap'd); the other two fully materialise content in-process.

Line Index Sidecar. A B+-tree of cumulative line-feed counts, owned by teb-core, mutated by every backend through one entry point (apply_edit); never mutated directly by a backend reaching into its internals (P5, I3).

Position Converters. A stateless service layered over &dyn TextBuffer; converts between the five typed coordinate systems; the only place conversion logic lives (P1, P2).

Undo/Redo Stack. Optional, attached by the host; owns EditGroups with precomputed inverses and explicit coalescing rules (P7, §18).

Anchor Store. An interval-indexed structure of sticky offsets; updated synchronously on every edit before the edit is considered complete (P6, I6).

Observer Fan-out. The sole mutation-export mechanism (P5); a trust boundary — host-supplied observer callbacks must not re-enter the buffer (T4, §22) — and a concurrency boundary between the mutation thread and async subscriber threads.

teb-io. The persistence boundary to the file system; owns encoding detection, BOM handling, streaming chunked reads, and atomic-rename saves (§20).

External consumers. Downstream of the observer protocol; out of this project's scope, but the edit log's shape (Phase 9, §21) is designed so a CRDT/OT layer can consume it without buffer changes.

6. Design Principles

  1. Typed positions, never bare integers (P1). A position is one of ByteOffset, CharOffset, Utf16Offset, GraphemeOffset, LineCol; implicit coercion across types is a compile-time error. Tradeoff: wider API surface, more conversion call-sites. Operational implication: position-confusion, historically the largest editor bug class, becomes structurally unrepresentable. Violation breaks: an LSP synchroniser silently drifts on every non-ASCII line.

  2. UTF-8 internal, UTF-16 only at the LSP boundary (P2). The buffer never stores UTF-16 or Latin-1 internally; conversion happens at teb-positions. Tradeoff: every LSP round-trip pays a conversion. Operational implication: one conversion path to audit, not N. Violation breaks: silent double-encoding on save.

  3. No silent denormalization (P3). Bytes that go in come out bit-identical on save; no BOM stripping, no line-ending conversion, unless the host opts in via BufferConfig. Tradeoff: the buffer cannot "clean up" a file automatically. Operational implication: diffs against the on-disk file are always faithful. Violation breaks: an editor that silently rewrites a vendored file's line endings on open, corrupting a checked-in diff.

  4. All operations O(log n) or better, one documented exception (P4). The gap buffer's amortized-O(1)-at-the-gap guarantee is published and bounded; every other operation on every backend is O(log n) worst case. Tradeoff: the rope/piece backends pay a constant-factor tax the gap buffer does not. Operational implication: a host can reason about worst-case latency without backend-specific caveats except the one documented gap-buffer case. Violation breaks: an unbounded backend turns a 200 MB refactor into a multi-second stall.

  5. The observer protocol is the only mutation export (P5). Backends never expose internal handles; downstream consumers reconstruct state from EditEvents. Tradeoff: consumers cannot cheaply peek at backend internals for debugging. Operational implication: every consumer sees the same edit stream, so there is one source of truth for "what changed." Violation breaks: a highlighter that reads backend internals directly desyncs the moment the backend is swapped.

  6. Anchors are sticky, not stable (P6). An anchor's byte offset changes as edits land; stickiness (StickyLeft/StickyRight/Surround) is chosen per anchor at creation. Tradeoff: three flavours to implement and test instead of one. Operational implication: every editor's anchor semantics (cursor, selection, bookmark) is expressible without a special case. Violation breaks: a bookmark that silently points at the wrong line after an edit upstream of it.

  7. Undo is structural, not character-by-character (P7). EditGroup is the atom of undo; coalescing rules are explicit (§18). Tradeoff: coalescing logic is another surface to get right. Operational implication: undo feels like a human edit, not a keystroke replay. Violation breaks: undoing a paste requires N keystrokes-worth of undo presses.

  8. Streaming load and save (P8). A large file is usable for reads while it loads and editable while it saves, via a snapshot taken at save-start. Tradeoff: the IO layer is stateful and more complex than "read the whole file." Operational implication: a 200 MB file does not freeze the editor UI thread. Violation breaks: opening a large log file blocks the user for the full read duration.

  9. Differential testing is the specification (P9). Every behavioural test runs against all three backends; disagreement is a failing test, not a documented quirk. Tradeoff: triples test execution time. Operational implication: "the backends disagree" becomes structurally impossible in a shipped release. Violation breaks: silent behavioural drift between backends that a host relies on being interchangeable.

  10. Reproducibility is a feature (P10). Every fuzz and bench harness records its random seed; every run is replayable. Tradeoff: seed-capture plumbing in every harness entry point. Operational implication: a CI-only failure is always locally reproducible. Violation breaks: an unreproducible fuzz finding that cannot be triaged.

  11. One mutation entry point per aggregate (P11). The line index has exactly one mutator, apply_edit; no backend recomputes or duplicates line-counting logic. Tradeoff: every backend must funnel through the shared sidecar rather than optimizing its own count. Operational implication: a line-index bug has one place to look. Violation breaks: two backends silently disagree on line numbers after the same edit sequence.

  12. Backpressure over silent drop (P12). An async observer that falls behind either blocks the bounded channel or explicitly increments a drop counter; it never silently loses events. Tradeoff: a slow observer can throttle the whole edit path if configured to block. Operational implication: "the highlighter missed an edit" is observable via telemetry, never silent. Violation breaks: a syntax highlighter that renders stale code with no indication anything is wrong.

  13. Crash safety over save throughput (P13). Autosave and atomic-rename-on-save take precedence over raw write speed. Tradeoff: a save is at least one extra fsync and rename versus a naive overwrite. Operational implication: a crash mid-save never corrupts the on-disk file. Violation breaks: a power loss during save truncates the user's file.

  14. Typed, non-panicking errors on host input (P14). Every public enum is #[non_exhaustive]; every fallible operation returns a typed error; the buffer never panics on host-supplied input, only on internal invariant violation in debug builds. Tradeoff: every call site must handle a Result. Operational implication: a malformed host call degrades gracefully instead of crashing the process. Violation breaks: one bad LSP request from a misbehaving client crashes the whole editor process.

  15. Save atomicity via rename, never via careful write ordering (P15). A save always writes to a temp path and renames over the target; the original file is never a direct write target (I11, I15). Tradeoff: one extra fsync/rename per save. Operational implication: a crash at any point during save leaves either the old file intact or the new one complete — never a hybrid. Violation breaks: a power-loss event during save truncates or corrupts the user's file irrecoverably (MM8).

  16. Bounded integer fields with explicit rejection, never silent wraparound (P16). Every length/offset field with a fixed integer width (u32 piece lengths, gap sizes) is checked at construction and growth; an operation that would overflow is rejected with a typed error rather than silently wrapping (I16). Tradeoff: an extra bounds check on every growth path. Operational implication: a pathological paste is rejected cleanly instead of corrupting offset arithmetic. Violation breaks: a length overflow silently aliases two unrelated pieces of content, a corruption class with no error signal at the moment it occurs.

8. Domain Model

8.1 Backend structural models

Backend Storage shape Mutation cost (local) Mutation cost (far) Immutable region
Gap buffer (§14) one Vec<u8> + a gap Range O(1) amortised (memcpy into gap) O(n) (move_gap, one copy_within) none
B-tree rope (§15) B-tree, branching 8, leaves 4–8 KiB UTF-8 chunks, Summary{bytes,chars,utf16,lines} per node O(log n) always O(log n) always none (COW spine on snapshot)
Piece table (§16) immutable original_buf + append-only add_buf + red-black tree of Piece{buf_tag,start,len,line_feeds} O(log n) tree splice, ≤3 pieces touched O(log n), same bound original_buf (never mutated)

8.2 Position / index mapping model

Coordinate Backing structure Conversion cost Notes
ByteOffset native storage offset O(1) canonical coordinate; all others derive from it
CharOffset chunked traversal O(distance) amortised via cursor codepoint count, not byte count
Utf16Offset chunk utf16 summary O(log n) via summary, O(1) via cursor BMP codepoint = 1 unit, non-BMP = 2 (surrogate pair)
GraphemeOffset UAX #29 state machine over chunks O(distance), not summary-cacheable a chunk boundary can split a cluster; caching is unsound (§13.6)

8.3 Edit application state machine

Every insert / delete / replace transitions through the same ordered steps regardless of backend, gated by the invariants of §7:

Step State Action Guard
1 Received Validate ByteRange within [0, len]; reject if it splits a UTF-8 codepoint I2
2 Validated Locate the mutation site (move gap / descend B-tree / find pieces to split) backend-specific
3 Located Mutate backend storage —
4 Mutated Recompute node summaries / call LineIndex::apply_edit I3, I9, I10
5 Indexed AnchorStore::apply_edit shifts or collapses anchors in range I4
6 Anchored If undo attached: append EditGroup with precomputed inverse I5
7 Logged Allocate the next EditId; fan out EditEvent to observers I6, I12
8 Delivered Return EditId to the host —

A failure at step 1 aborts before any mutation (no partial state); a failure at any later step is a debug-build panic (an internal invariant violation, never triggered by host input per P14).

8.4 Anchors / marks model

Stickiness table (P6, I4), restated as the transition each flavour undergoes for an edit at [a, b) relative to an anchor at offset o:

Stickiness o < a o in [a, b), insert at a (b=a) o in [a, b), delete [a,b)
StickyLeft unchanged stays at a (insert lands to its right) collapses to a
StickyRight unchanged shifts to a + len(insert) collapses to a
Surround{start,end} unchanged each endpoint uses its own flavour both endpoints inside ⇒ range collapses to empty at a

Anchors with o > b always shift by the edit's net length delta; this row is identical across all three flavours and omitted from the table for density.

8.5 Worked example

Buffer content (7 codepoints, 8 bytes): "café!\n" → bytes 63 61 66 C3 A9 21 0A (é is U+00E9, 2-byte UTF-8, 1 UTF-16 unit, 1 grapheme). Host calls insert(ByteOffset(5), "!!")(inserting two ! right before the existing !):

  1. Step 1: ByteOffset(5) is a valid codepoint boundary (byte 5 is the start of !, byte 4 was the last byte of é) — passes I2.
  2. Step 2–3 (rope example): descend to the single leaf (buffer fits in one 4 KiB chunk); splice "!!" into the chunk at byte 5.
  3. Step 4: leaf Summary updates: bytes += 2, chars += 2, utf16 += 2, lines += 0; interior summaries (none here, single leaf) unaffected. LineIndex::apply_edit shifts the recorded line-feed position at byte 7 to byte 9.
  4. Step 5: no anchors registered in this example — no-op.
  5. Step 6: if undo attached, EditGroup{ops: [Insert{at:5, content:"!!"}], inverse: [Delete{range:5..7}]} is pushed.
  6. Step 7: EditId(N+1) allocated; EditEvent{id, op, before_len:8, after_len:10} fanned out.
  7. Result: "café!!!\n", 10 bytes, byte_to_line_col(ByteOffset(9)) == LineCol{line:0, col:9}, byte_to_utf16(ByteOffset(9)) == Utf16Offset(9) (all codepoints so far are BMP).

8.6 Malformed-input example

Host calls delete(ByteRange{start: ByteOffset(3), end: ByteOffset(4)}) on the original "café!\n". Byte 3 is 0xC3 (the first byte of é's two-byte encoding) and byte 4 is 0xA9 (its continuation byte); the requested range removes only the lead byte, which would leave a dangling continuation byte at the new offset 3 — an invalid UTF-8 sequence. Step 1 of §8.3 rejects the call: I2 fires, the buffer returns EditError::Utf8Boundary{offset: ByteOffset(3)}, no mutation occurs, no EditId is allocated, and no observer is notified. The host is expected to snap the range to the nearest codepoint boundary and retry (documented in docs/runbooks/ per §24).

8.7 Failure-path example

A host saves a 200 MB buffer (P13, §20). teb-io streams the BufferSnapshot to buffer.tmp in 64 KiB chunks; the process is killed (OOM-killer, power loss) after 150 MB is written, before the atomic rename. On restart: the original buffer.txt is untouched (I11 — the rename never happened, so the original path was never the write target); teb-io's open path finds the orphaned buffer.tmp, verifies it against a size/checksum recorded in the autosave journal (§20.10), determines it is a partial write, and discards it; if autosave was enabled, the host recovers the last complete autosave checkpoint plus any journalled edits since that checkpoint (FM-7, §23), typically losing at most the coalesce window's worth of unsaved edits (≤1 s of typing, per P7's coalescing default).

8.8 Rope worked example (leaf split and summary propagation)

Consider a rope (branching factor 8, ADR-03) whose root has two leaf children: Leaf A = "The quick brown fox jumps over" (31 bytes, Summary{bytes:31, chars:31, utf16:31, lines:0}) and Leaf B = " the lazy dog.\n" (15 bytes, Summary{bytes:15, chars:15, utf16:15, lines:1}); the root's own summary is the component-wise sum, Summary{bytes:46, chars:46, utf16:46, lines:1} (MM3 — a summary is a monoid). Host calls insert(ByteOffset(31), " and cat") — exactly at the leaf boundary. Step 2 of §8.3 descends to Leaf A (the insertion point is at its end); Leaf A grows to 39 bytes, still within [2048, 8192]'s lower bound trivially (small example; in production leaves stay 4–8 KiB), so no split is needed — but if this insert had instead been a 9,000-byte paste, Leaf A would exceed the 8 KiB ceiling (§15.2) and split into two sibling leaves, promoting a new internal node if the root's child count would otherwise exceed 8 (ADR-03). Step 4 recomputes Leaf A's summary to Summary{bytes:39, chars:39, utf16:39, lines:0} and the root's summary bottom-up to Summary{bytes:54, chars:54, utf16:54, lines:1} (I10) — no other leaf is touched, demonstrating the O(log n) locality of the summary-recomputation walk (§15.2, MM3).

8.9 Piece-table worked example (piece split under a mid-string edit)

original_buf = "The quick brown fox" (20 bytes) loaded as a single piece P0{buf:Original, start:0, len:20, line_feeds:0}; the tree has one node, subtree_bytes = 20. Host calls insert(ByteOffset(4), "very "). Step 2 of §8.3 locates the split point inside P0 at relative offset 4; P0 splits into P0a{buf:Original, start:0, len:4} ("The ") and P0b{buf:Original, start:4, len:16} ("quick brown fox"); the inserted text is appended to add_buf at offset 0 and referenced by a new piece P1{buf:Add, start:0, len:5, line_feeds:0} ("very "); the tree becomes P0a → P1 → P0b in-order (three pieces from one, matching §16.2's "at most 3 pieces touched" bound for an insert). Step 4 recomputes subtree_bytes bottom-up to 25 (I9); original_buf itself is never mutated — only the tree and add_buf grew, matching the "immutable original, append-only delta" property that makes the piece table win the "open huge file, edit small" workload (§2, VS Code reading §5).

8.10 Cross-backend equivalence example (the differential harness's core claim, by hand)

Starting from the empty buffer, apply the sequence [insert(0, "café"), insert(4, "!"), delete(0..1)] to a gap buffer, a rope, and a piece table independently. Gap buffer: "café" → "café!" → "afé!" (delete removes the leading "c", 1 byte). Rope: identical sequence produces the same content via leaf mutation and summary update at each step (§8.8's mechanism at a smaller scale). Piece table: insert(0,"café") creates one add-buffer piece; insert(4,"!") appends to the same add-buffer piece (contiguous append, no split needed since the insertion point is at the piece's end); delete(0..1) splits the piece to drop its first byte. All three report slice(ByteRange{0, 5}) == "afé!" and len_bytes() == ByteOffset(5) — the byte-for-byte agreement P9 mandates and the differential harness (§26) checks mechanically for every fixture, not just this one by-hand trace.

8.11 Undo-coalescing worked example

A host types "cat" one keystroke at a time with an attached UndoStack (default UndoConfig, §18.2):

Keystroke Elapsed since previous CoalesceKey Stack action
insert(0, "c") — (first edit) {line:0, direction:Right} opens EditGroup#1
insert(1, "a") 0.2 s {line:0, direction:Right} matches #1's key, within 1 s window → coalesces into #1
insert(2, "t") 0.3 s {line:0, direction:Right} coalesces into #1

After the third keystroke, EditGroup#1.ops = [Insert{0,"c"}, Insert{1,"a"}, Insert{2,"t"}] and EditGroup#1.inverse = [Delete{0..1}, Delete{1..2}, Delete{2..3}] computed at each step (I5). A single undo() call applies the inverse ops in reverse, removing "t", then "a", then "c" — restoring the empty buffer in one host-visible undo step, not three, which is exactly P7's "undo is structural, not character-by-character" principle made concrete.

13.1 Objectives

14. Phase 2 — Gap Buffer Backend

14.1 Objectives

Implement teb-gap as the first real TextBuffer backend: a single contiguous Vec<u8> plus a gap Range, delivering the amortized-O(1)-at-the-gap guarantee that is the documented exception to P4.

14.2 Detailed Implementation Steps

GapBuffer { data: Vec<u8>, gap: Range<usize>, line_index: LineIndex, revision: Revision, observers: ObserverFanout } (§11.7 LineIndex, §11.5 ObserverFanout). move_gap(target) is the hot path: a single copy_within on data, lowering to memmove (P4 exception, documented). The gap grows on demand (next power of two when full, via Vec::reserve — never reserve_exact, to let the allocator batch, per Finseth's gap-buffer treatment, §5). UTF-8 boundary enforcement follows the edit state machine (§8.3 step 1): a delete that would split a codepoint returns EditError::Utf8Boundary (I2). Every mutation calls line_index.apply_edit (P11, I3) before returning the EditId.

14.3 Deliverable

teb-gap implements TextBuffer with unsafe confined to two audited blocks (move_gap's copy_within, and iter_chunks' known-valid &str construction); compiles standalone with no dependency on teb-rope/teb-piece; a Criterion baseline reports insert-at-gap, insert-far-from-gap, delete-at-gap, delete-far-from-gap on 1 KB / 1 MB / 100 MB synthetic buffers.

14.4 Acceptance Criteria

Insert-at-gap p50 < 100 ns, p99 < 200 ns on a 1 MB buffer (§4, M1); the 1,000,000-random-edit line-index drift fixture (line-index-1m-drift.yaml) reports zero drift (I3); the differential fixture set in conformance/buckets/basic/ passes byte-for-byte against RefBuffer (§12.2).

Fixture Purpose Expected Output

  • Forgetting to call line_index.apply_edit on every code path drifts the index silently; the 1M-edit differential fixture is the trip-wire (I3).
  • move_gap(target) with target inside the gap itself is meaningless input from a confused caller; clamp rather than panic (P14).
  • Growing data with reserve_exact instead of reserve causes pathological reallocation churn under repeated small grows — use reserve (ADR-15 spirit, small-value inlining reasoning applies to buffer growth too).

14.7 Performance Concerns

14.8 Edge Cases

An insert exactly at the gap boundary when the gap is fully exhausted (size 0) must trigger the grow-then-insert path atomically, not a two-step operation a concurrent read could observe mid-way (I7 — single-writer makes this safe by contract, but the code must not yield between grow and insert); a delete range spanning the entire buffer content must leave a valid (possibly maximal) gap, not a corrupt Range.

14.9 Failure Analysis

A hostile or pathological edit pattern (alternating far-apart offsets) forces move_gap on every single edit — the gap buffer's well-known worst case. This is not a bug: it is documented behaviour (P4's exception) surfaced via the M1/M2 performance targets (§29) and the conformance suite explicitly tests for the presence of this degradation, not its absence, as a regression guard against an accidental "fix" that changes the amortized-cost contract.

14.10 Operational Notes

15. Phase 3 — B-Tree Rope Backend

15.1 Objectives

Implement teb-rope: a B-tree with branching factor 8 (ADR-03), interior nodes carrying additive Summary{bytes, chars, utf16, lines}, leaves holding 4–8 KiB validated UTF-8 chunks, delivering the worst-case-O(log n) guarantee (P4) independent of edit locality — the Boehm-Atkinson-Plass rope generalised to a B-tree per the Ropey/xi-rope reference implementations (§5).

15.2 Detailed Implementation Steps

RopeBuf { root: Arc<Node>, line_index: LineIndex, revision: Revision, observers: ObserverFanout }; Node::Internal { summaries: SmallVec<[Summary;8]>, children: SmallVec<[Arc<Node>;8]> } / Node::Leaf { chunk: SmolStr, summary: Summary }. Summary is monoid-additive (component-wise sum, per Crowley's structural survey, §5); an edit walks the spine, replaces the affected child via Arc::make_mut (copy-on-write when a snapshot holds a reference, per the Driscoll-Sarnak-Sleator-Tarjan persistence paper, §5), and recomputes summaries bottom-up (I10). Rebalance when a leaf falls outside [2048, 8192] bytes or an interior node falls outside [4, 8] children (ADR-03); rebalance moves O(log n) nodes amortised. A snapshot is an O(1) Arc<Node> clone of the root (I8); subsequent edits clone only the affected spine.

15.3 Deliverable

teb-rope implements TextBuffer and BufferSnapshot; rebalance thresholds are named constants in node.rs, tunable for the Phase-13-era re-bench (ADR-03's "when rejected wins" clause); a proptest-based property test generates random edit sequences and asserts equivalence against RefBuffer after every step.

15.4 Acceptance Criteria

  • Arc::make_mut clones the whole spine when a snapshot is alive — bounded (one chunk per level) but not free; benchmarks must include the "active snapshot" workload explicitly, not just the no-snapshot case.
  • A leaf chunk type that copies bytes without re-validating UTF-8 on construction is a footgun; SmolStr validates, a hand-rolled inline chunk might not.
  • Changing the branching factor without re-running the Phase-13 benches violates ADR-03's locked rationale; any change requires a superseding ADR.

15.7 Performance Concerns

15.8 Edge Cases

An edit that lands exactly on a leaf boundary must not create a zero-length leaf; a rebalance triggered by a delete that empties a leaf must merge with a sibling, not leave a dangling empty node; an Arc<Node> whose strong count never reaches zero due to a missed drop in the rebalance path is a silent memory leak, not a crash — the differential suite alone cannot catch this, so a dedicated leak-detection soak test is required (§27).

15.9 Failure Analysis

A rebalance bug that drops an Arc<Node> reference without correctly updating summaries silently corrupts the tree — reads return wrong content or wrong line numbers without any panic. validate_invariants() (I10) catches this in debug/test builds; in release, the conformance suite's differential check against the gap-buffer backend (§26) is the safety net, and any release-mode occurrence is classified FM-3 (§23) — a summary-consistency failure.

16.1 Objectives

Insert cost is dominated by the tree walk to locate the split point, not the splice itself (300 ns p50 target, §4 M4); open cost is dominated by the line-feed scan (SIMD-accelerated via memchr, shared with teb-io, §20) rather than the mmap call itself. After a long editing session, piece count can grow into the tens of thousands; lookup stays O(log n) but the constant grows — the Comparative Architecture Table (§31) documents this against the rope's bounded-depth alternative.

16.8 Edge Cases

A piece whose len would overflow u32 (a single piece larger than 4 GiB) is rejected at construction — pieces are capped and a large insert is internally chunked; a delete that exactly consumes a piece must remove it from the tree, not leave a zero-length piece; concurrent external truncation of the mmap'd file during an active read must not be observable as a memory-safety violation (16.9).

16.9 Failure Analysis

An mmap'd original_buf that is truncated by another process (e.g. git checkout rewriting the file mid-session) produces SIGBUS on the next page fault into the truncated region — a process-fatal signal, not a recoverable Rust panic. Mitigation: teb-io (§20) holds an advisory file lock by default, or the host opts into MmapPolicy::AllowConcurrent and accepts the risk with a documented fallback to read-into-Vec (ADR-13's rejected-alternative regime). This is FM-3-adjacent but classified separately as T5/FM-9 (§22–§23) because the failure mode is OS-signal-level, not an internal invariant violation.

16.10 Operational Notes

PieceTree::pretty_print() renders piece boundaries; PieceTree::dump_dot() emits Graphviz DOT for offline inspection of a misbehaving tree. Deployment note: hosts running on network filesystems should default MmapPolicy away from mmap (ADR-13's "when rejected wins" clause) — document this in the host integration guide (§24).

17. Phase 5 — Line Index Sidecar

17.1 Objectives

Harden LineIndex (§11.7) from Phase-0 stub to a fully incremental B+-tree sidecar shared by all three backends (P11), maintaining line⇄byte mapping in O(log n) with zero full rescans after the initial load.

17.2 Detailed Implementation Steps

Internal nodes hold cumulative (bytes, lines) counts (ADR-07); leaves hold a sorted list of u32 line-feed offsets relative to a LEAF_CHUNK_BYTES = 4096 chunk, fanout NODE_FANOUT = 32. byte_to_line_col(off) descends by cumulative byte count then binary-searches the leaf's line-feed list — O(log n) (I3). apply_edit(op) locates the affected chunk(s), splits/merges as needed, adjusts the local line-feed list, and walks up adjusting cumulative counts — O(log n) amortised, O(k) additional for a k-line-feed paste. On load, the index is built single-pass: 64 KB chunks scanned with memchr::memchr_iter(b'\n', chunk) (shared SIMD path with teb-io, §20). CRLF is counted as one line feed (\n only); a line_text() accessor strips terminators, line_text_with_terminator() preserves them — old-Mac bare-\r files are not counted as line feeds by default (host opt-in conversion lives in teb-io, §20).

17.3 Deliverable

LineIndex::validate(buf) performs a from-scratch recount and compares against the maintained counts (I3); wired into every conformance run in debug builds, disabled in release for performance. The 1,000,000-random-edit drift fixture passes with zero divergence.

17.4 Acceptance Criteria

byte_to_line_col on a 100 MB / 1M-line buffer: p50 ≤ 50 ns, p99 ≤ 100 ns (§4, M5); index build on a 200 MB file: ≤ 200 ms on reference hardware (§4); the 1,000,000-random-edit drift fixture (line-index-1m-drift.yaml, shared with §14.5) reports zero drift across all three backends.

17.5 Conformance Fixtures

Fixture Purpose Expected Output
line-index-1m-drift.yaml 1,000,000 random edits vs. brute-force recount 0 drift (I3)
line-index-chunk-boundary.yaml edit spanning two adjacent chunks consistent counts post-edit
line-index-crlf-vs-lf.yaml mixed CRLF/LF file LF-only line-feed counting confirmed
line-index-build-200mb.bench cold index build on a 200 MB file ≤ 200 ms

17.6 Pitfalls

  • An edit crossing a chunk boundary left half-updated (only one of the two affected chunks touched) is the single most common line-index bug; apply_edit has a dedicated cross-boundary branch and the property test exercises it explicitly.
  • Counting \r\n as two line feeds double-counts Windows-style files; the index counts \n only, with \r handling delegated to the display layer (line_text_with_terminator).
  • Old-Mac bare-\r line endings are invisible to this index by design; a host serving such files must opt into teb-io's conversion-on-load (§20), not expect the index to detect them.

17.7 Performance Concerns

apply_edit for a single-line insert costs ≈80 ns p50; a multi-line paste costs that plus ≈30 ns per line feed inserted — a 30,000-line-feed paste (a large log file) without the bulk-update path would cost 30,000 individual tree walks (≈3 s); the bulk path applies the diff in one spine walk (≈50 ms), a 60x difference that is the load-bearing optimization of this phase.

17.8 Edge Cases

A buffer with zero line feeds (total_lines == 0) must report line_count() == 1 (the implicit first line); a delete that removes every line feed in the buffer must collapse the index to a single leaf with an empty line-feed list, not a tree of empty leaves; a leaf that would grow past 2 × LEAF_CHUNK_BYTES from a single large paste must split during the same apply_edit call, not defer to a later rebalance pass.

17.9 Failure Analysis

A bug in chunk splitting that loses one line-feed position produces a buffer where every line number past the bug is off-by-one — silent, and it looks like correct output until a host queries a far-away line number. Debug builds catch this immediately via validate(buf) after every edit (I3); in release, it surfaces as FM-2 (§23) — a line-index drift failure class — with the from-scratch recount as the recovery path.

17.10 Operational Notes

LineIndex::pretty_print() renders the tree; LineIndex::audit_chunk(chunk_id) dumps a single chunk's line-feed list when a regression localises to one region of a large file. Telemetry: teb_line_index_drift_total (I3) should be a permanent zero in production dashboards (§24); any nonzero value is a release blocker.

18. Phase 6 — Undo/Redo History

18.1 Objectives

Implement teb-undo: a coalescing undo/redo stack of EditGroups (§11.3) with precomputed inverses, giving structural (not per-keystroke) undo (P7) tuned to feel like Emacs by default (§5 Finseth reading, applied here) while remaining host-configurable.

18.2 Detailed Implementation Steps

UndoStack { undo: Vec<EditGroup>, redo: Vec<EditGroup>, config: UndoConfig }; UndoConfig { coalesce_window: Duration /* default 1s */, coalesce_same_line_only: bool /* default true */, coalesce_only_inserts: bool /* default true */, max_undo_groups: usize /* default 10_000 */ }. Coalescing rule set (P7): (1) two adjacent insert groups coalesce iff their CoalesceKeys agree on line and direction and the timestamp gap is under coalesce_window; (2) a delete group never coalesces with an insert group; (3) a non-edit action (selection change) forces the next edit to open a new group — but per the documented pitfall (§18.6), selection change does not by itself clear the redo stack, only a new edit does; (4) max_undo_groups is enforced by ring-buffering, silently dropping the oldest group beyond the limit, with truncated: bool surfaced via UndoStats. Each EditGroup's inverse is computed at edit time (when offsets are known-valid), never re-derived at undo time (I5).

18.3 Deliverable

teb-undo as a standalone crate the host opts into via buf.attach_undo() — the buffer itself carries no built-in undo (separation of concerns, per the architecture in §3). A "checkpoint" API records a named position in the stack (used for "mark saved" semantics, §25).

18.4 Acceptance Criteria

The "1,000 random edits + 1,000 random undos + 1,000 random redos" fixture asserts final state matches the buffer's net edit count exactly (I5); a coalescing fixture typing "hello world" character-by-character within the coalesce window restores the entire word in one undo step; push cost p50 ≤ 200 ns; pop (actual undo apply) cost p50 ≤ 1 µs on a rope backend for a typical 16-op group.

18.5 Conformance Fixtures

Fixture Purpose Expected Output
undo-redo-net-effect.yaml 1,000 edits + 1,000 undos + 1,000 redos final state == net-edit-count state (I5)
undo-coalesce-word.yaml character-by-character typing within 1s window single undo restores whole word
undo-truncation.yaml exceed max_undo_groups UndoStats.truncated == true, oldest group dropped
undo-checkpoint.yaml checkpoint set, edits applied, checkpoint queried checkpoint position resolves correctly

18.6 Pitfalls

  • Coalescing two inserts spanning a line boundary reads as one edit but is semantically two; coalesce_same_line_only defaults true to prevent this.
  • An EditGroup whose inverse references stale offsets (computed after later edits shifted them) corrupts the buffer on redo — the inverse must be captured at edit time, not lazily.
  • Clearing the redo stack on every selection change (not just on a new edit) is a common but surprising design: a user who hits Ctrl-Z, clicks elsewhere to look around, then hits Ctrl-Y expects the redo to still work — the default policy is "only a new edit clears redo."

18.7 Performance Concerns

Push cost is dominated by cloning an EditGroup with up to ~16 ops (≈200 ns); pop cost is dominated by the underlying backend's edit cost applying the inverse ops (≈1 µs on a rope, §15's M3 figure), not by the undo stack's own bookkeeping — the stack itself contributes negligible overhead relative to the backend mutation it triggers.

18.8 Edge Cases

An undo requested with an empty undo stack must return a typed UndoError::Empty, never panic (P14); a redo requested immediately after a fresh edit (not after an undo) must be a no-op returning UndoError::NothingToRedo, since the fresh edit already cleared the redo stack; a coalesced group whose combined byte range would itself split a UTF-8 codepoint on inverse-application is prevented at the source (each constituent EditOp already satisfied I2 individually).

18.9 Failure Analysis

A truncated undo stack (past max_undo_groups) cannot restore full history beyond the ring-buffer window — this is a documented, host-visible limit (UndoStats.truncated), not a silent data-loss bug; the host is expected to surface it in its UI if the user attempts to undo past the boundary. Classified FM-4 (§23) — bounded-history exhaustion, not corruption.

18.10 Operational Notes

UndoStack::dump() (test-only) prints every group with timestamp and CoalesceKey, the first tool for diagnosing "why did my undo merge with the previous edit." No persistence by default — undo history does not survive a process restart unless the host explicitly serializes EditGroups (ADR-19) alongside its own session state; this is a documented limitation, not a deferred feature (it is a host-integration choice, §24).

19. Phase 7 — Anchors & Marks

19.1 Objectives

Implement AnchorStore (§11.4) as an interval-indexed structure of sticky offsets that survive every edit (P6), giving cursors, selections, and bookmarks a correct, O(log n + k)-updated position without each consumer re-deriving offset math.

19.2 Detailed Implementation Steps

AnchorStore { by_offset: BTreeMap<ByteOffset, SmallVec<[AnchorId;2]>>, anchors: HashMap<AnchorId, Anchor>, next_id: u64 }. apply_edit(op) implements the transition table of §8.4: for Insert{at, content} of length L, anchors < at unchanged, anchors > at shift by +L, anchors == at resolve per stickiness; for Delete{range:[a,b)}, anchors < a unchanged, anchors ≥ b shift by -(b-a), anchors inside [a,b) collapse to a (StickyLeft/StickyRight) or empty-collapse (Surround, both endpoints inside). The BTreeMap keeps the walk restricted to anchors in the edited range — O(log n + k), not O(n) over every registered anchor (critical once a host pins ~1,000,000 bookmarks, per §4's anchor-count constraint).

19.3 Deliverable

AnchorStore lives in teb-core, updated synchronously by every backend on every edit before the edit is considered complete (I4); the host may subscribe to anchor-change notifications via a dedicated EditEvent::AnchorMoved variant on the observer protocol (§21).

19.4 Acceptance Criteria

The "1,000 anchors, 100,000 random edits" fixture asserts every anchor's offset matches a brute-force recomputation after every edit (I4), with zero mismatches; apply_edit on a buffer with 1,000,000 anchors and a small localized edit completes in ≤ 1 µs (only anchors in the affected range are touched, per §4's anchor-count constraint).

19.5 Conformance Fixtures

Fixture Purpose Expected Output
anchor-brute-force-100k.yaml 1,000 anchors, 100,000 random edits vs. brute force 0 mismatches (I4)
anchor-sticky-left-right.yaml insert exactly at anchor offset, both flavours matches §8.4 transition table
anchor-surround-collapse.yaml delete range containing both Surround endpoints collapses to empty at range start
anchor-1m-scale.bench 1,000,000 anchors, localized edit ≤ 1 µs per edit

19.6 Pitfalls

  • A naive O(n) walk over every registered anchor per edit is fine under ~1,000 anchors but collapses under ~1,000,000 (a host pinning every search-result match, say); the BTreeMap range-restricted walk is not optional at scale.
  • A zero-length insert is contractually forbidden upstream (EditError::EmptyEdit, P14) — handling it gracefully in the anchor path is not "extra robustness," it should be unreachable by construction.
  • A host that wants "notify me when this range disappears" needs the explicit Surround flavour; StickyLeft/StickyRight alone silently collapse without a distinguishable "you were deleted" signal — document the choice per anchor at creation time.

19.7 Performance Concerns

apply_edit's cost is O(log n + k) where n is total anchor count and k is the number of anchors actually in the edited range — for the overwhelmingly common case (a small edit, a handful of nearby anchors), this is effectively O(log n) with a small constant, independent of how many anchors exist elsewhere in the buffer (the M11-adjacent target in §29 assumes this locality).

19.8 Edge Cases

Two anchors at the exact same offset with opposite stickiness must both resolve independently and correctly on the same edit (no aliasing bug from sharing a BTreeMap bucket); a Surround anchor whose two endpoints are constructed in reversed order (stick_end offset less than stick_start offset) is rejected at creation, not silently tolerated as an inverted range; an anchor removed (AnchorStore::remove) mid-edit-batch must not be visited by that batch's apply_edit — removal takes effect immediately, not at the next edit boundary.

19.9 Failure Analysis

An anchor-update bug manifests as a cursor or bookmark that silently drifts to the wrong location after an upstream edit — the most user-visible bug class this phase exists to prevent, because it produces no error, only wrong behavior a human notices minutes later. Detection: the brute-force differential fixture (19.5) in CI; in production, teb_anchor_drift_total (I4 telemetry) should be a permanent zero, with any nonzero value classified FM-5 (§23).

19.10 Operational Notes

AnchorStore::dump() (test-only) prints every anchor and its current offset — the first tool when a host reports "my bookmark moved to the wrong place." No persistence by default; a host that needs anchors to survive a restart serializes Anchor values itself (ADR-19) alongside session state, the same pattern as undo history (§18.10).

20. Phase 8 — Streaming I/O & Large-File Handling

20.1 Objectives

Implement teb-io: streaming chunked load/save so a 200 MB file is usable for reads while loading and editable while saving (P8), plus encoding detection, BOM handling, and crash-safe atomic save (P13, I11).

20.2 Detailed Implementation Steps

LoadStrategy::{Eager, Streaming{chunk_size}, Mmap}; LoadOptions{ strategy, encoding: Encoding, line_endings: LineEndingPolicy, bom_policy: BomPolicy }. load_streaming(path, opts) reads in 64 KiB chunks, validates UTF-8 incrementally with simdutf8 (carrying up to 3 bytes of decoder state across a chunk boundary so a split multi-byte codepoint is never misread), and appends to the backend while progressively feeding LineIndex via memchr::memchr_iter (shared path with §17). save_streaming(buf, path, encoding) takes a BufferSnapshot at save-start (I8), streams it to a temp file in 64 KiB chunks, and atomically renames over the target on success — the buffer remains editable during save because the snapshot, not the live buffer, is what's being written (P13, I11). Non-UTF-8 files are decoded via encoding_rs on load and carry an original_encoding tag for faithful round-trip on save (P3). BOM presence is recorded in BufferMetadata and re-emitted on save unless bom_policy = Strip; the BOM itself is never part of buffer content.

20.3 Deliverable

teb-io as a standalone crate; a "200 MB file open in ≤ 250 ms" benchmark on reference hardware passes (§4, M7); a "save while editing" fixture inserts 1,000 edits during an in-flight save and asserts the saved bytes match the pre-save snapshot exactly, while the live buffer reflects all 1,000 post-snapshot edits.

20.4 Acceptance Criteria

200 MB UTF-8 load p50 ≤ 250 ms on x86_64 with simdutf8 SIMD acceleration, ≤ 500 ms p99 (§4, M7); 200 MB save p50 ≤ 300 ms (§4, M8); the "every supported encoding round-trip" fixture (load → edit → save → reload) matches the original modulo intentional edits, for every encoding in the supported set; the atomicity fixture (20.3) shows zero torn writes across 100 injected-crash trials.

20.5 Conformance Fixtures

Fixture Purpose Expected Output
io-200mb-open.bench cold open of a 200 MB UTF-8 file p50 ≤ 250 ms (M7)
io-save-during-edit.yaml 1,000 edits fired during an in-flight save saved bytes == pre-save snapshot; live buffer has all edits
io-encoding-roundtrip.yaml load/edit/save/reload across every supported encoding byte-identical modulo edits
io-bom-preserve.yaml UTF-8 file with EF BB BF BOM BOM preserved on save (default policy)
io-crash-injection.yaml simulated crash after partial temp-file write original file untouched (I11)

20.6 Pitfalls

  • Validating UTF-8 per-chunk without carrying decoder state across the boundary can misclassify a valid multi-byte codepoint split across two 64 KiB reads as invalid; the validator must carry up to 3 bytes of pending state.
  • Detecting a BOM by inspecting only the first 3 bytes misclassifies some Latin-1 files that happen to start with the same byte pattern; the default policy is BOM-detection restricted to declared/detected UTF-8 only.
  • simdutf8's acceleration is x86-specific; aarch64 falls back to the scalar validator (§4's ~600 ms aarch64 load-time note is the direct consequence, still within budget but worth documenting for operators comparing hardware).

20.7 Performance Concerns

The 200 MB open is dominated by the UTF-8 validation and line-feed scan, both SIMD-accelerated and both memory-bandwidth-adjacent; on aarch64 without simdutf8's x86 path, open time roughly doubles (still within the p99 budget, §4) but is a documented platform difference operators should expect, not a regression to chase.

20.8 Edge Cases

A file whose declared/detected encoding disagrees with its actual byte content (e.g. a mislabeled UTF-16 file) must not panic on decode failure — LoadOptions::on_decode_error offers "ask the host," "fallback to Latin-1," or "fail loudly," and the default is "fail loudly" (fail-closed, matching P3's byte-faithful philosophy); a save interrupted by disk-full mid-write must leave the original file untouched (I11) because the write target is always the temp file, never the original path directly.

20.9 Failure Analysis

A crash mid-save leaves an orphaned, partially-written temp file — never a corrupted original, because I11's atomic-rename contract means the original path is only ever touched by the rename itself, which is atomic at the filesystem level on POSIX and NTFS. Detection: the next load_streaming call on that path finds no temp file issue (the original is intact); a separate autosave-journal mechanism (§8.7's worked failure path) is what recovers unsaved edits, which is orthogonal to save-atomicity. Classified FM-7 (§23).

20.10 Operational Notes

IoEvent traces every chunk read/written — the first diagnostic when a load or save appears to stall; a stalled load on a network filesystem is usually the OS page-cache/readahead interaction (§5's Linux fs/iomap.c/mm/filemap.c reading, applied here), not a bug in teb-io itself. Deployment note: the autosave journal (referenced in §8.7 and formalized as a Deferred Feature in §35 for cross-restart persistence) is distinct from save-atomicity and must be documented separately for host integrators (§24 runbook crash-during-save.md).

21. Phase 9 — Observer Protocol, Unicode Correctness & CRDT-Ready Edit Log

21.1 Objectives

Finalize ObserverFanout (§11.5) as the sole mutation-export mechanism (P5) with strict per-EditId ordering (I6) and per-subscriber backpressure (P12); close out grapheme-cluster correctness (UAX #29, I13) across chunk boundaries; and add the optional append-only EditLog that makes the buffer CRDT-ready without implementing CRDT semantics itself (per the Shapiro et al. and Roh et al. readings, §5).

21.2 Detailed Implementation Steps

ObserverFanout{ syncs: Vec<Arc<dyn EditObserver>>, asyncs: Vec<(SubscriptionId, Sender<EditEvent>)>, next_id: u64 }. Sync delivery calls on_edit on the mutating thread in registration order; ObserverError::Backpressure from a sync subscriber is fatal (the sync contract is "block until ack"); Refused(_) rolls the edit back and returns EditError::ObserverRefused to the host; Fatal(_) unsubscribes that observer and continues (I14 forbids re-entrant calls back into the buffer from within on_edit, enforced via a debug-mode thread-local flag). Async delivery uses crossbeam-channel::bounded(queue_depth) per subscriber (ADR-23); a full channel either blocks (default) or drops with a counted signal, per subscriber policy. EditLog{ site_id: SiteId, counter: u64, log: Vec<LogEntry> } with LogEntry{ id: EditId, op: EditOp, deps: SmallVec<[EditId;4]>, site_id, timestamp } — deps are the causal parents an external CRDT/OT layer (Wagner & Graham's incremental-parsing shape applies equally to tree-sitter observers here, §5) needs for convergence; the buffer computes and records deps, but implements no transform or merge logic itself (explicitly delegated, §1). Grapheme correctness: the UAX #29 state machine (§13.2) is re-verified here against chunk-crossing sequences specifically — a ZWJ or regional-indicator sequence split across a rope leaf or piece-tree piece boundary must carry state across the boundary (I13).

21.3 Deliverable

ObserverFanout embedded in every backend; a replay_subscriber test fires a recorded edit trace into a fresh fanout and asserts every subscriber sees an identical ordered sequence; EditLog is enabled via BufferConfig::enable_edit_log and a "replay the log on a fresh buffer to reach the same state" fixture passes.

21.4 Acceptance Criteria

Fanout to 8 sync + 8 async subscribers on one edit: p50 ≤ 500 ns (§4, M11); the ordering-invariant fixture (two subscribers, 10,000 edits) shows zero reordering (I6); the UAX #29 chunk-boundary corpus (grapheme clusters deliberately split across leaf/piece boundaries) shows zero incorrect breaks (I13); EditLog replay reaches byte-identical state to the original run across 100 randomized replay trials.

Fixture Purpose Expected Output

21.6 Pitfalls

  • A sync observer holding a mutex the host also holds deadlocks the moment the host calls back into the buffer from a different code path; the trait contract forbids sync observers from holding host-visible locks, and debug builds detect re-entrancy via I14's thread-local flag, but a lock held outside the buffer's own re-entrancy detection is a host-side bug the buffer cannot catch mechanically.
  • A flaky async subscriber that silently drops events under load is exactly the bug class ADR-23's default-to-block policy eliminates; a host that explicitly wants drop-oldest for a best-effort consumer must opt in per subscriber, not get it by accident.
  • Caching grapheme-cluster boundaries at the chunk-summary level (the same trap flagged in §13.6) resurfaces here specifically for chunk-crossing sequences — the fixture uax29-chunk-boundary.yaml exists because this is the one place a chunk-oblivious implementation silently breaks.

21.7 Performance Concerns

Fanout cost to 8 sync subscribers is dominated by the sync callbacks themselves, not the fanout bookkeeping (§4, M11); a sync observer that takes 10 ms per edit directly sets the edit's observed p50 to 10 ms — this is a documented pass-through cost, not a fanout inefficiency, and the conformance suite includes a fixture that exercises exactly this case (§21.9). EditLog overhead is ≈80 bytes/edit; at 1M edits that is 80 MB, garbage-collectible once every observer has caught up (EditLog::gc(min_observed_id)).

21.8 Edge Cases

An observer that unsubscribes itself from within its own on_edit callback must not corrupt the subscriber list being iterated (a classic mutate-while-iterating hazard); an EditId collision across two replicas in a multi-writer CRDT scenario (outside this project's single-writer invariant I7, but relevant to EditLog consumers) is prevented by site_id namespacing being non-optional whenever the log is enabled; a deps list that fails to transitively include every causal parent breaks external CRDT convergence — the buffer documents this contract but, per §1's delegation boundary, does not and cannot enforce a property that belongs to the external CRDT layer.

21.9 Failure Analysis

A sync observer that blocks for an extended period (a pathological highlighter doing synchronous I/O, say) directly stalls every subsequent edit on that buffer instance — classified FM-6 (§23), detected via teb_observer_callback_duration_seconds telemetry exceeding a documented threshold, with the operational remedy being to move that subscriber to async delivery, not to change the buffer's contract. An external CRDT layer that misorders edits (violating causal deps) produces divergence between replicas; out of this project's scope to fix, but the EditLog's explicit deps field is designed specifically to make such a bug diagnosable rather than a mystery.

21.10 Operational Notes

ObserverFanout::dump() (test-only) lists every subscriber and its delivery mode. Telemetry: teb_observer_out_of_order_total (I6) and teb_reentrant_observer_total (I14) are permanent-zero production metrics (§24); any nonzero value pages the on-call per the incident-response runbook slow-observer.md. EditLog is the integration point named throughout §1, §5, and §34 for a future CRDT/OT layer — this phase closes the buffer's contribution to that story; the layer itself is PhaseDeferred("§35").

Incident response. Each runbook: symptom → likely FM class → immediate mitigation → root-cause investigation steps → the specific telemetry query to confirm.

Backup/restore. The buffer itself holds no durable backup; the host-level autosave journal (§8.7, §20.9) is the backup mechanism, checkpointed at the undo system's coalesce boundaries by convention (so a restore point aligns with a natural undo boundary).

Deployment topology. Embedded library — "deployment" means a host application's release cadence, not a service rollout. There is no server-side canary; the equivalent discipline is the Compatibility & Versioning policy (§25) that lets a host pin a teb-* version and upgrade deliberately.

Rolling upgrade / rollback / migration. A host upgrades teb-* crate versions independently of any running buffer instance (in-process library, no live migration needed); the SemVer policy (§25) is what makes an upgrade safe. A "rollback" is a Cargo.lock revert plus a host redeploy — no buffer-level migration exists because no cross-process buffer state persists across a version bump (per the documented no-persistence-by-default stance of §18.10/§19.10).

25. Compatibility & Versioning

Wire/storage compatibility. The buffer has no network wire format (§1 delegation). The one on-disk artefact is the file the host saves (byte-faithful per P3) — compatibility here means "the bytes we write are the bytes any other tool can read," not a proprietary format.

Schema evolution. EditOp, Stickiness, ObserverError, and every other public enum are #[non_exhaustive] (P14, ADR-06) so a minor version may add a variant without breaking a match in downstream code that already has a wildcard arm; a host matching exhaustively without a wildcard accepts the SemVer-minor risk knowingly.

API stability. TextBuffer, BufferSnapshot, and EditObserver trait methods are additive-only within a major version (new methods ship with a default implementation, §11.2's compatibility note); removing or changing the signature of an existing method is a major-version-only change.

Migration. There is no data migration between versions because the buffer holds no cross-process persistent state by default (§18.10, §19.10); a host that has built its own persistence atop serde-serialized EditGroup/Anchor/EditLog values (ADR-19) is responsible for its own migration path, documented as a host-integration concern, not a teb-* one.

Deprecation policy. A deprecated API is marked #[deprecated(since = "x.y.z", note = "...")] for at least one minor version before removal in the next major version; CHANGELOG.md (Keep a Changelog format) records every deprecation and removal.

SemVer policy. Patch: bug fixes, no API change. Minor: additive API (new #[non_exhaustive] variants, new default-implemented trait methods, new crate features). Major: any breaking change to TextBuffer, BufferSnapshot, EditObserver, or the typed-position types (§11). The rope's Summary field set (§15.2) and the piece table's Piece layout (§16.2) are internal and not covered by SemVer — only the public trait surface is.

Rolling-upgrade guarantees. Because the buffer is an embedded library with no persisted cross-process state by default, "rolling upgrade" reduces to "the host can bump the teb-* dependency version and recompile" — the guarantee that matters is that a minor-version bump never requires a code change at any call site that already tolerates #[non_exhaustive] types correctly.

26. Testing & Verification Strategy

Unit tests. Per-crate, exercising each type's contract in isolation (e.g. LineIndex::apply_edit against a hand-built tree).

Integration tests. Per-backend, exercising the full TextBuffer trait surface end to end (conformance/buckets/basic/, §10).

Property tests. proptest-generated random operation sequences (insert/delete/replace/undo/redo) checked against invariants I1–I14 after every step (§15.3, §16.3); the shrinker produces a minimal reproducing case on failure, the same artifact FM-12's forensics rely on.

Differential tests. The DifferentialDriver (conceptually introduced in §8.1, concretized here) runs an identical operation sequence against RefBuffer (§12.2) and all three real backends in lockstep; any divergence is a failing test with a minimal-reproducing trace — this is P9 made mechanical.

Fuzzing. Six cargo-fuzz targets, each seeded from the conformance corpus: insert_delete (internal consistency under random edits), position_roundtrip (all five coordinate conversions), line_index (drift-freedom, I3), observer_replay (ordering, I6), differential (cross-backend convergence, P9), streaming_load (streaming vs. eager load equivalence, §20). Every target runs 5 minutes per PR (fuzz.yml) and continuously for 24 hours in a scheduled soak job.

Chaos / fault injection. The crash-injection fixture (io-crash-injection.yaml, §20.5) simulates process death at randomized byte offsets during save; the mmap-truncation fixture (piece-mmap-truncate.yaml, §16.5) simulates a concurrent external truncation.

Deterministic replay. conformance-cli --mode simulate --seed <N> replays any recorded operation sequence byte-for-byte identically (P10) — the same mechanism used for both fuzz-finding triage and the 24-hour soak canary.

Soak testing. A 24-hour synthetic-keystroke soak run (Phase 0's correctness-kernel gate, §12.4, extended across all real backends once they land) asserts zero invariant violations and no memory growth beyond the expected snapshot/log accounting (FM-11's boundary).

Conformance gating. Every bucket in conformance/buckets/ (§10) must report 100% pass before a release; a bucket at Deferred carries an explicit anchor into the Deferred Features Register (§35) rather than being silently skipped.

Performance-regression gating. Every M-target (§28) is measured by cargo bench on every PR touching a backend crate; a regression beyond the noise floor (3%) is flagged for review, beyond 5% fails the PR (§28's regression policy, applied continuously from Phase 0 onward once benches exist).

Release channels. main branch is the development channel; tagged releases (vX.Y.Z) are the stable channel published to crates.io; no separate "nightly" channel exists for this library (embedded-library consumers pin exact versions per §25).

Provenance / attestation. release.yml publishes build provenance (source commit SHA, builder identity, build environment) alongside the crates.io artifact, following the SLSA-adjacent practice of recording exactly what produced the binary.

Dependency auditing. cargo audit runs in CI on every PR against the RustSec advisory database; a new advisory affecting a pinned dependency blocks merge until triaged.

28. Performance Engineering

Methodology. Every backend's benchmark suite runs on the pinned reference hardware (§4: 16-core x86_64, 32 GB DDR5, NVMe SSD, Linux 6.6) via criterion (ADR-16), recording p50/p99/mean/max/stddev per workload, committed to docs/performance/perf.md per release.

Allocation analysis. heaptrack/dhat profiling on the standard workload set identifies unexpected allocation in the hot path (insert/delete); the small-value inlining policy (ADR-15) is the primary lever when allocation dominates.

Lock/contention analysis. The buffer itself has no internal lock on the mutation path (single-writer, I7); contention analysis instead targets the async-observer channel (crossbeam-channel::bounded) under multi-subscriber fanout (§21.7).

Cache analysis. perf stat cache-miss counters validate the rope's branching-factor-8 choice (ADR-03) against its L1-line-grouping rationale; a regression in cache-miss rate after a rebalance-threshold change is the trigger for revisiting ADR-03.

Syscall analysis. strace -c on the streaming load/save path (§20) confirms chunk-sized reads/writes match the configured 64 KiB granularity, not smaller syscalls that would amplify overhead.

Tail-latency analysis. Every M-target below records p99 alongside p50 specifically because tail latency, not median, is what a user perceives as a "hitch" — the 16 ms frame budget (§3's defining property) is a p99, not p50, constraint.

29. Scalability Analysis

What stays constant. Per-edit latency stays O(log n) (rope, piece) or amortised O(1) (gap, local edits) regardless of total session length (P4); observer fan-out cost stays O(subscriber count), independent of buffer size (§21.7).

What grows, and its Big-O. Memory grows O(n) with content size across all backends, with the constant-factor overhead documented in §4 (gap ≤10%, rope ≤25%, piece ≤8%); anchor-store update cost grows O(log n + k) with total anchor count n and in-range anchor count k (§19.7); piece-table piece count grows with edit count (not just content size) and its lookup constant grows correspondingly (§16.7's "tens of thousands of pieces" note) — the named bottleneck of the piece backend under long editing sessions.

Named bottlenecks, in order. (1) Piece-table piece-count growth under sustained editing (§16.7) — mitigated by the rope's bounded-depth alternative when a session is edit-heavy rather than open-heavy. (2) Grapheme-cluster iteration cost (O(distance), not cacheable, §13.7) — mitigated by PositionCursor amortisation for the common sequential-scan pattern. (3) Sync-observer callback duration directly gating edit latency (§21.7, FM-6) — mitigated by moving slow consumers to async delivery.

Horizontal / vertical scaling. There is no horizontal scaling within one buffer instance — the unit of scaling is the host process running one buffer per open file (§1's deployment model); vertical scaling (larger buffers) is bounded by the 4 GiB addressable limit (§4) and by available RAM for the fully-materialised gap/rope backends (the piece backend's mmap'd original is the exception, §16.2).

Sharding / partitioning. Not applicable to a single in-process buffer; a host serving many open files partitions naturally at the file level, each an independent buffer instance with no shared state (no coordination overhead between instances).

Coordination overhead. Zero between buffer instances (fully independent); within one instance, the single-writer invariant (I7) means there is no internal coordination cost to model — the host's own threading model is the only coordination surface, and it is external to this system.

Practical ceiling and the levers beyond it. The practical ceiling is the 4 GiB addressable limit (§4) combined with available RAM for two of the three backends; the lever beyond it is the piece table's mmap-based approach, which decouples buffer size from RAM residency for the immutable original content — the documented reason the piece backend is recommended for the largest files (§16.2, Comparative Architecture Table §31).

30. Mental Models & First Principles

  • MM1 — A position is a coordinate system, not a number. Five coordinate systems exist because five different consumers (renderer, LSP client, regex engine, human, database) each have a legitimate, different unit of "where." Predicts: any bare-integer position parameter is a latent bug generator. Bug class without it: an LSP offset silently drifts on every non-ASCII line. Applied in §13.

  • MM2 — Amortized cost is a bet on locality; worst-case cost is insurance against its absence. The gap buffer bets that edits cluster near the cursor; the rope insures against the bet failing. Predicts: which backend wins for a given edit-pattern workload, without running a benchmark. Bug class without it: choosing the gap buffer for a refactor-heavy IDE and being surprised by O(n) stalls. Applied in §14, §15, §31.

  • MM3 — A summary is a monoid, and every subtree is just a fold. The rope's and piece-table's Summary/subtree counters are associative aggregates; any monoid-additive property can be maintained incrementally in O(log n). Predicts: which future per-node aggregates (e.g. a "diagnostics count") could be added cheaply, and which (e.g. "is this range currently selected," not associative) could not. Bug class without it: recomputing an aggregate from scratch on every query. Applied in §8.1, §15.2, §17.2.

  • MM4 — The observer is downstream of a single source of truth, never a second writer. A one-way edit-event flow is what makes multiple consumers provably consistent with each other. Predicts: any two-way channel between a backend and a consumer will eventually desync. Bug class without it: "the highlighter is one edit behind." Applied in §21.

  • MM5 — Immutability at the boundary buys cheap snapshots. The piece table's immutable original and the rope's Arc-based structural sharing both trade a small append/clone cost for O(1) snapshotting. Predicts: any fully-mutable-in-place structure (a raw Vec<u8> with no COW) pays O(n) to snapshot. Bug class without it: an undo implementation that full-copies the buffer per edit group. Applied in §15.2, §16.2, §18.2.

  • MM6 — Stickiness is a declared policy, not a physical property of the offset. The same numeric byte offset behaves differently under an insert depending on a stickiness flag chosen at anchor-creation time. Predicts: any anchor system without explicit stickiness will surprise a host at the exact moment of a boundary-adjacent edit. Bug class without it: a bookmark that silently jumps to the wrong side of an insertion. Applied in §19.

  • MM7 — Grapheme boundaries are stateful, not memoizable per chunk. UAX #29 boundary determination can require lookback/lookahead across an arbitrary distance (ZWJ sequences, regional indicators). Predicts: any chunk-summary cache of grapheme counts is wrong at some boundary, however rare. Bug class without it: mis-rendered emoji sequences exactly at a rope-leaf or piece boundary. Applied in §13.2, §21.2.

  • MM8 — Crash safety is bought with an extra rename, not an extra write. Atomicity comes from the filesystem's rename guarantee, not from careful ordering of writes to the original file. Predicts: any save implementation that writes-then-truncates the original path directly cannot be made crash-safe no matter how careful the write ordering is. Bug class without it: a truncated user file on power loss mid-save. Applied in §20.2.

Ropey made the choice to ship only a rope, accepting the local-edit constant-factor tax everywhere, in exchange for one code path and no differential-testing burden; it wins in the niche of "a Rust library consumer who wants one dependable data structure and does not need the gap buffer's typing-locality speed or the piece table's huge-file-open speed."

Emacs' gap buffer made the choice to never generalize beyond one backend across four decades, betting that typing-locality dominates essentially all real editing; it wins in the niche of "a general-purpose, non-IDE editor where files are small-to-medium and edits are overwhelmingly local," at the cost of the well-known O(n) far-jump case this project documents as a first-class, tested behavior (§14.9) rather than an accepted quirk.

Xi-editor's rope made the choice to generalize the rope's per-node summary into a pluggable Metrics trait (multiple simultaneous metrics per node) rather than a fixed Summary struct; it wins whenever a host needs to add a new per-node aggregate (e.g. a custom fold) without modifying the tree implementation, at the cost of a more complex generic-metrics API than this project's fixed four-field Summary (§15.2).

Zed's sum-tree generalizes the same subtree-summary pattern into a reusable generic B-tree usable for any summary type across the whole editor (not just text), including selections and diagnostics; it wins whenever an editor wants one generic aggregating-B-tree primitive reused across multiple subsystems, at the cost of a less text-specialized API than this project's dedicated rope.

32. Back-of-Envelope Capacity Model

Every number below is derived from the System Constraints table (§4), formula shown, not asserted.

  1. Max addressable buffer size. 2^32 bytes = 4,294,967,296 bytes ≈ 4 GiB — direct consequence of u32 piece offsets (§11.3 Piece.len: u32, referenced in §4's max-buffer-size row).
  2. Rope memory footprint at 100 MB content. 100 MB × (1 + 0.25 overhead) = 125 MB — from §4's "Rope ≤25%" overhead row.
  3. Piece-table memory footprint at 200 MB content. 200 MB × (1 + 0.08) = 216 MB — from §4's "Piece ≤8%" overhead row.
  4. Anchor-store footprint at 1,000,000 anchors. 1,000,000 × ~40 bytes/Anchor (id 8B + offset 8B + stickiness ~9B + alignment/label overhead ~15B) ≈ 40 MB — from §11.4's Anchor field layout and §4's "≥1,000,000 anchors" constraint.
  5. EditLog size for a 2-hour session. 5 edits/s × 7,200 s × 80 bytes/entry (M14) ≈ 2.88 MB — from §28's M14 target and a typing-rate assumption consistent with §18's 1-second coalesce window.
  6. Async-observer queue memory ceiling. 8 subscribers × 1,024 queue depth × 64 bytes/EditEvent ≈ 512 KB — from §4's "≤8 async subscribers" row and §11.3's EditEvent field sizes.
  7. Line-index memory at 100 MB / ~24,414 leaves. (100 MB / 4,096-byte LEAF_CHUNK_BYTES) × ~300 bytes/leaf ≈ 7.3 MB — from §17.2's LEAF_CHUNK_BYTES = 4096 constant.
  8. 200 MB file-open time decomposition. 200 MB / ~4 GB/s SIMD throughput (memchr/simdutf8) ≈ 50 ms for UTF-8 validation, another ≈50 ms for the line-feed scan, leaving ≈150 ms of the 250 ms p50 budget (M7, §28) for I/O and allocation — derived directly from §4's M7 row and §20's SIMD-throughput claims.
  9. Default FD ceiling. 4 concurrent large-file opens × 2 fds/open (file + mmap region) = 8 fds — from §4's "≤4 concurrent large-file opens" and "1 fd per file + 1 per mmap region" rows.
  10. Undo-stack memory ceiling. 10,000 max_undo_groups × ~640 bytes/group (16 ops × ~40 bytes/op) ≈ 6.4 MB — from §18.2's max_undo_groups: usize = 10_000 default and EditOp's field layout (§11.3).
  11. Piece count after a long edit-heavy session. At worst 4 new pieces per edit (§16.2's delete-splits-4 bound), so 100,000 edits × 4 ≈ 400,000 pieces; at ~48 bytes/PieceNode (§16.2's field layout), that is 400,000 × 48 bytes ≈ 19.2 MB of tree overhead alone — the numeric basis for §16.7's/§29's "piece-count growth" named bottleneck.
  12. Edit-latency budget as a fraction of the 60 Hz frame. 16 ms frame budget / 1 µs worst-case rope p99 insert (M3) ≈ 16,000× headroom for a single edit — derived directly from §3's frame-budget rationale and §28's M3 target, quantifying just how much margin the p99 latency target leaves for the renderer's own work in the same frame.

34. Alternative Architectures (Roads Not Taken)

Alternative 1 — Single monolithic B-tree rope, no gap/piece backends.

┌─────────────────────────────┐
│ Host                        │
└──────────────┬───────────────┘
               │ TextBuffer trait
┌──────────────▼───────────────┐
│ One B-tree Rope (only)       │
└───────────────────────────────┘

Regime where it wins: a library consumer who wants exactly one dependency and no differential-testing burden across backends. Real system: Xi-editor (shipped only its rope). Why rejected here: loses both the gap buffer's typing-locality speed (§14) and the piece table's huge-file-open speed (§16); §31's Comparative Architecture Table shows both wins are real and workload-dependent, so this project chose workload-honest engineering over single-backend simplicity (§1).

Alternative 2 — CRDT-native sequence as the primary internal representation (not an external layer).

┌─────────────────────────────┐
│ Host / remote peers          │
└──────────────┬───────────────┘
               │ ops with per-character IDs
┌──────────────▼───────────────┐
│ RGA/Logoot-style sequence     │
│ (tombstones retained forever) │
└───────────────────────────────┘

Regime where it wins: a collaborative-first editor where every edit is inherently multi-writer from the first keystroke. Real system: Yjs, Automerge (text CRDTs). Why rejected here: the single-writer invariant (I7) and O(log n) local-edit performance are cheaper to guarantee without permanent per-character tombstone metadata, which would violate this project's memory-overhead budget (§4, ≤25% for the rope) for the common single-user case; this project instead makes the buffer CRDT-ready (§21's EditLog) without paying the CRDT tax when no collaboration is happening.

Alternative 3 — Pure event-sourced log, no mutable in-memory tree at all.

┌─────────────────────────────┐
│ Host                         │
└──────────────┬───────────────┘
               │ append-only op log
┌──────────────▼───────────────┐
│ Fold(log) → current content   │
│ (recomputed per query)        │
└───────────────────────────────┘

Regime where it wins: audit-heavy or replay-heavy tools where "what did the buffer look like at edit #4,000" matters more than steady-state edit latency. Real system: WAL-replay-based "time travel" debugging tools. Why rejected here: folding the entire log to materialize current state is O(edit count), violating P4's O(log n)-or-better principle for ordinary interactive editing.

Alternative 4 — Doubly-linked list of lines (classic line-oriented editor internals).

┌───────┐    ┌───────┐    ┌───────┐
│ line 0 │──▶│ line 1 │──▶│ line 2 │──▶ …
└───────┘    └───────┘    └───────┘

Regime where it wins: a strictly line-oriented tool where "line" is the only addressable unit (a line-based diff viewer, not a general text editor). Real system: early Unix ed/sed-style line editors. Why rejected here: within-line random access degrades to O(line length), and the structure offers no sub-line position model — it cannot support the five-coordinate typed-position system (§13) this project requires for LSP/renderer/regex consumers.

36. Glossary

  • Add buffer — the piece table's append-only buffer that every edit's inserted bytes land in; never moved, never compacted (§16.2).
  • Anchor — a sticky byte offset that survives edits according to a declared stickiness policy (§11.4, §19).
  • AnchorStore — the interval-indexed structure holding every registered anchor for a buffer instance (§11.4).
  • Autosave journal — the host-level append-only recovery log that restores unsaved edits after a crash, distinct from save-atomicity (§8.7, §20.9).
  • B+-tree — the balanced-tree structure backing the line index; internal nodes hold cumulative counts, leaves hold sorted line-feed positions (§17).
  • B-tree rope — this project's rope backend: a B-tree with branching factor 8 whose leaves hold UTF-8 chunks (§8.1, §15).
  • Backend — one of the three interchangeable TextBuffer implementations: gap buffer, B-tree rope, piece table (§3).
  • Backpressure — the mechanism by which a slow async observer either blocks the bounded channel or explicitly signals a drop, never silently losing events (P12).
  • BOM (Byte Order Mark) — an optional leading byte sequence indicating encoding/endianness; stripped from buffer content and re-emitted on save per policy (§20.2).
  • BufferSnapshot — an immutable, cheaply-obtained view of a buffer at a fixed Revision (§11.6).
  • ByteOffset — the canonical typed position: a byte index into the buffer's UTF-8 content (§11.1).
  • CharOffset — a typed position expressed in Unicode codepoints, never used for storage (§11.1).
  • Chunk — a contiguous slab of UTF-8 bytes; the rope's leaf unit and the natural granularity of ChunkIter (§8.1, §11.2).
  • Coalescing — merging adjacent EditGroups into one undo step under explicit rules (P7, §18.2).
  • CoalesceKey — the (line, direction) pair used to decide whether two edit groups coalesce (§11.3).
  • CRDT (Conflict-free Replicated Data Type) — a class of data structures that converge under concurrent, unordered edits; this project is CRDT-ready, not CRDT-implementing (§21, §5).
  • Deferred feature — a capability explicitly out of this project's scope, anchored in the Deferred Features Register (§35).
  • Differential test — a test that runs one operation sequence against multiple backends (or against RefBuffer) and asserts identical output (P9, §26).
  • EditGroup — the atomic unit of undo: a coalesced sequence of EditOps plus its precomputed inverse (§11.3).
  • EditId — a monotonically increasing token identifying and ordering edits within one buffer instance (§11.3, I12).
  • EditLog — the optional append-only record of every edit with causal deps, consumed by an external CRDT/OT layer (§21.2).
  • EditOp — an atomic mutation: Insert or Delete (§11.3).
  • EditEvent — the observer-visible record of one applied edit, carrying before/after buffer length (§11.3).
  • Gap — in the gap buffer, the contiguous run of unused bytes between the two content regions (§8.1, §14.2).
  • Gap buffer — a buffer backend maintaining an unused gap near the cursor for amortized-O(1) local edits (§14).
  • GraphemeOffset — a typed position counting user-perceived grapheme clusters, per UAX #29 (§11.1, §13).
  • Grapheme cluster — one or more Unicode codepoints perceived as a single character by a user; boundary rules defined in UAX #29 (§5, §13.2).
  • I7 (single-writer invariant) — the contract that at most one mutation is in flight per buffer instance at a time (§7).
  • Invariant — a system property (I1–I14) that must hold after every operation, with a defined detection and recovery path (§7).
  • Leaf — a rope's or line index's terminal node holding actual content or line-feed positions, as opposed to an aggregating interior node (§8.1, §17.2).
  • LineCol — a typed position expressed as (LineIdx, ByteOffset-within-line) (§11.1).
  • LineIdx — a zero-based typed line number (§11.1).
  • LineIndex — the B+-tree sidecar mapping line numbers to byte offsets and back, shared by all three backends (§8.1, §17).
  • Observer — a downstream consumer of EditEvents, delivered either synchronously or asynchronously (§11.5, §21).
  • ObserverFanout — the structure that dispatches EditEvents to every registered observer in EditId order (§11.5, §21.2).
  • Original buffer — in the piece table, the immutable (optionally mmap'd) bytes of the file as loaded (§8.1, §16.2).
  • Piece — a reference (buf_tag, start, len, line_feeds) to a contiguous run of bytes in either the original or add buffer (§11 note, §16.2).
  • Piece table — the data structure (older name) later refined into the piece tree; first used in Bravo (§5, §8.1).
  • Piece tree — the red-black-tree-indexed piece-table variant this project implements, matching VS Code's design (§16).
  • PositionCursor — a cached traversal position that amortises sequential byte↔grapheme/UTF-16 conversion to near O(1) per step (§13.2).
  • Revision — a monotonic counter incremented on every edit; a buffer's logical clock, used to key snapshots (§11.6).
  • Rope — the 1995 Boehm-Atkinson-Plass data structure; in this project, generalized to a B-tree with chunked leaves (§5, §15).
  • Site ID — a per-replica identifier namespacing EditIds in the optional EditLog to prevent cross-replica collisions (§21.2).
  • Snapshot — see BufferSnapshot.
  • Sticky offset — a position that survives edits per a declared stickiness (StickyLeft/StickyRight), as opposed to a raw offset that would silently become wrong (§11.4, §19).
  • StickyLeft / StickyRight / Surround — the three anchor stickiness flavours (§8.4, §11.4).
  • Summary — the small fixed-size additive aggregate (bytes, chars, utf16, lines) maintained on every rope/piece-tree node (§8.1, §11).
  • UAX #29 — the Unicode Annex defining grapheme-cluster boundaries, implemented exactly by this project's segmentation code (§5, §13, I13).
  • UTF-16 code unit — a 16-bit unit of UTF-16 text; one per BMP codepoint, two (a surrogate pair) per supplementary-plane codepoint (§8.2, §11.1).
  • Utf16Offset — the typed position counting UTF-16 code units, needed at the LSP boundary (§11.1, §5).
