Decisions (§9) · 27 ADRs

ADR-01

Implementation language

Chosen

Rust 1.78+

Rejected

C/C++, Go, Java/JVM, Swift

When the rejected choice is right

A JVM/Go host already paying GC cost elsewhere, where FFI-to-Rust overhead exceeds the GC pause it would avoid

Why: No GC pause in the p99 < 1 µs edit path (§4); compile-time Send+Sync proof

ADR-02

Backend strategy

Chosen

Three interchangeable backends (gap, rope, piece) behind one trait

Rejected

Ship rope only

When the rejected choice is right

A size-constrained embedded/WASM target where one backend's binary size is the deciding factor

Why: Workload-honest engineering; differential-tested interchangeability (P9)

ADR-03

Rope branching factor

Chosen

B = 8

Rejected

B = 4, 16, 32

When the rejected choice is right

B = 16 wins on hardware with larger cache lines or very deep trees, per the Phase 13 (§21 hardening note) re-bench

Why: Matches L1-cache-line grouping on target x86_64/ARM64 (§4)

ADR-04

Piece-table balance structure

Chosen

Red-black tree

Rejected

AVL tree, B-tree, skip list

When the rejected choice is right

A B-tree-backed piece table wins once node-visit cost dominates rotation cost, at very large piece counts

Why: O(log n) with cheaper single/double rotations than AVL

ADR-05

Internal text encoding

Chosen

UTF-8

Rejected

UTF-16, UTF-32, Latin-1

When the rejected choice is right

UTF-32 wins for a fixed-width-position specialised engine where O(1) codepoint indexing outweighs 4x memory

Why: Matches Rust str; minimal memory footprint; WHATWG/RFC 3629 aligned

ADR-06

Position API

Chosen

Five typed offset kinds, no implicit coercion

Rejected

Bare usize + doc-comment convention

When the rejected choice is right

A throwaway internal prototype not yet exposed externally, where conversion boilerplate outweighs the safety win

Why: Compile-time elimination of the largest editor bug class (P1)

ADR-07

Line-index structure

Chosen

B+-tree sidecar

Rejected

Count-on-demand scan, per-line Vec<usize>

When the rejected choice is right

A per-line Vec<usize> wins under 64 KiB (e.g. a single config file) where scan cost is lower than tree overhead

Why: O(log n) line⇄byte always, independent of file size

ADR-08

Observer delivery

Chosen

Sync + async, per-subscriber back-pressure

Rejected

Single fire-and-forget pub/sub

When the rejected choice is right

Fire-and-forget wins in a throwaway REPL/scripting context with one always-caught-up consumer

Why: Prevents "highlighter is one edit behind" structurally (P5, P12)

ADR-09

Anchor stickiness

Chosen

Three flavours (StickyLeft/StickyRight/Surround)

Rejected

Single sticky-right-only model

When the rejected choice is right

Sticky-right-only wins for a minimal read-only viewer needing only a scroll position

Why: Expresses every editor's cursor/selection/bookmark semantics (P6)

ADR-10

Undo model

Chosen

EditGroup with explicit coalescing rules

Rejected

Per-keystroke undo, snapshot-per-edit

When the rejected choice is right

Snapshot-per-edit wins for a small notebook-cell editor where memory is cheap and simplicity matters more

Why: Feels like Emacs by default, tunable per host (P7)

ADR-11

Load strategy

Chosen

Streaming with progressive line-index build

Rejected

Eager full-file read

When the rejected choice is right

Eager read wins under ~1 MB, where streaming bookkeeping costs more than the time it saves

Why: Buffer usable mid-load on large files (P8)

ADR-12

Correctness strategy

Chosen

Differential testing across all three backends

Rejected

Independent per-backend test suites

When the rejected choice is right

Independent suites win once a backend is deprecated/frozen and no longer needs cross-backend equivalence

Why: Structurally guarantees interchangeability (P9)

ADR-13

Piece-table original-buffer access

Chosen

mmap

Rejected

Always read-into-Vec

When the rejected choice is right

Read-into-Vec wins on a network filesystem where page faults are slower than one sequential read, or when the source file may be deleted mid-session

Why: Avoids materialising 200 MB twice in RAM

ADR-14

Crate topology

Chosen

Cargo workspace, path-only internal deps

Rejected

Independently published crates from day one

When the rejected choice is right

Independent publishing wins once teb-core stabilises and external consumers need independent SemVer

Why: Simpler versioning during active development

ADR-15

Small-value representation

Chosen

smallvec/smol_str inlining

Rejected

Always-heap Vec/String

When the rejected choice is right

Always-heap wins when buffers are uniformly large, removing the inline-check branch entirely

Why: Avoids allocation on small chunks/ops, the common case

ADR-16

Benchmarking tool

Chosen

criterion

Rejected

Hand-rolled timing loops, iai

When the rejected choice is right

iai (instruction-count) wins in a noisy CI environment where wall-clock variance drowns the signal

Why: Statistical rigor, HTML reports, CI integration

ADR-17

Fuzzing tool

Chosen

cargo-fuzz (libFuzzer)

Rejected

AFL++, proptest-only

When the rejected choice is right

AFL++ wins when persistent-mode throughput matters more than Rust ergonomics, e.g. a dedicated fuzzing farm

Why: Coverage-guided, integrates with cargo directly

ADR-18

Structured logging

Chosen

tracing

Rejected

log crate, println!

When the rejected choice is right

Plain log wins for the deferred no_std embedded variant (§35) where span overhead is unwanted

Why: Spans model the edit pipeline naturally (request→validate→mutate→index)

ADR-19

Serialization

Chosen

serde

Rejected

Hand-rolled binary format, protobuf

When the rejected choice is right

protobuf/flatbuffers win once the edit log crosses a network boundary to an external CRDT service needing schema evolution

Why: Derive-based; matches JSON conformance fixtures

ADR-20

CI/CD topology

Chosen

GitHub Actions

Rejected

Self-hosted Jenkins, CircleCI

When the rejected choice is right

Self-hosted runners win once benchmark reproducibility requires pinned dedicated hardware (§4)

Why: Free for open source; native matrix builds across 5 OS/arch targets

ADR-21

Licensing

Chosen

Dual Apache-2.0 OR MIT

Rejected

GPL, proprietary

When the rejected choice is right

GPL wins if the goal were copyleft propagation into every embedding host — explicitly not a goal (§1)

Why: Rust-ecosystem norm; unblocks embedding in proprietary editors

ADR-22

Causal/ordering token

Chosen

Monotonic EditId (u64)

Rejected

Wall-clock timestamp, UUID

When the rejected choice is right

A hybrid logical clock wins once true multi-writer (multi-process) causality is needed beyond the single-writer invariant I7

Why: Cheap total order, no clock-skew exposure, matches I12

ADR-23

Async observer overflow policy

Chosen

Block (back-pressure) by default

Rejected

Drop-oldest, drop-newest

When the rejected choice is right

Drop-oldest wins for a best-effort telemetry/analytics observer where losing old events is acceptable and blocking edits is not

Why: Correctness over liveness by default (P12)

ADR-24

Unsafe-code gating

Chosen

cargo miri test on every unsafe block in CI

Rejected

Manual unsafe review only

When the rejected choice is right

Manual review alone wins for a one-off internal tool where Miri's 10–50x slowdown makes CI infeasible

Why: Catches UB that cargo test alone misses

ADR-25

Grapheme segmentation implementation

Chosen

Vendored, version-pinned UAX #29 state machine in teb-positions

Rejected

Depend on unicode-segmentation directly, re-implement per Unicode release

When the rejected choice is right

Depending on unicode-segmentation directly wins for a smaller project that does not need to gate Unicode-version upgrades behind its own conformance corpus

Why: Pinning lets the conformance corpus (I13) and the implementation move together under one ADR-gated upgrade

ADR-26

UTF-8 validation acceleration

Chosen

simdutf8 with scalar fallback

Rejected

Always-scalar validation, hand-written SIMD intrinsics

When the rejected choice is right

Always-scalar wins on a target where simdutf8's SIMD path is unavailable and the maintenance cost of a second code path is not justified (e.g. a niche embedded target)

Why: SIMD throughput on x86_64 without unmaintainable hand-written intrinsics

ADR-27

Error-type granularity

Chosen

Distinct typed errors per subsystem (EditError, IoError, PositionError, UndoError)

Rejected

One flat BufferError enum for everything

When the rejected choice is right

A single flat error enum wins for a minimal host integration that only ever logs-and-ignores errors, where per-domain matching adds no value

Why: Lets a host match on the specific failure domain without a catch-all Other(String) arm

34. Alternative Architectures (Roads Not Taken)

Alternative 1 — Single monolithic B-tree rope, no gap/piece backends.

┌─────────────────────────────┐
│ Host                        │
└──────────────┬───────────────┘
               │ TextBuffer trait
┌──────────────▼───────────────┐
│ One B-tree Rope (only)       │
└───────────────────────────────┘

Regime where it wins: a library consumer who wants exactly one dependency and no differential-testing burden across backends. Real system: Xi-editor (shipped only its rope). Why rejected here: loses both the gap buffer's typing-locality speed (§14) and the piece table's huge-file-open speed (§16); §31's Comparative Architecture Table shows both wins are real and workload-dependent, so this project chose workload-honest engineering over single-backend simplicity (§1).

Alternative 2 — CRDT-native sequence as the primary internal representation (not an external layer).

┌─────────────────────────────┐
│ Host / remote peers          │
└──────────────┬───────────────┘
               │ ops with per-character IDs
┌──────────────▼───────────────┐
│ RGA/Logoot-style sequence     │
│ (tombstones retained forever) │
└───────────────────────────────┘

Regime where it wins: a collaborative-first editor where every edit is inherently multi-writer from the first keystroke. Real system: Yjs, Automerge (text CRDTs). Why rejected here: the single-writer invariant (I7) and O(log n) local-edit performance are cheaper to guarantee without permanent per-character tombstone metadata, which would violate this project's memory-overhead budget (§4, ≤25% for the rope) for the common single-user case; this project instead makes the buffer CRDT-ready (§21's EditLog) without paying the CRDT tax when no collaboration is happening.

Alternative 3 — Pure event-sourced log, no mutable in-memory tree at all.

┌─────────────────────────────┐
│ Host                         │
└──────────────┬───────────────┘
               │ append-only op log
┌──────────────▼───────────────┐
│ Fold(log) → current content   │
│ (recomputed per query)        │
└───────────────────────────────┘

Regime where it wins: audit-heavy or replay-heavy tools where "what did the buffer look like at edit #4,000" matters more than steady-state edit latency. Real system: WAL-replay-based "time travel" debugging tools. Why rejected here: folding the entire log to materialize current state is O(edit count), violating P4's O(log n)-or-better principle for ordinary interactive editing.

Alternative 4 — Doubly-linked list of lines (classic line-oriented editor internals).

┌───────┐    ┌───────┐    ┌───────┐
│ line 0 │──▶│ line 1 │──▶│ line 2 │──▶ …
└───────┘    └───────┘    └───────┘

Regime where it wins: a strictly line-oriented tool where "line" is the only addressable unit (a line-based diff viewer, not a general text editor). Real system: early Unix ed/sed-style line editors. Why rejected here: within-line random access degrades to O(line length), and the structure offers no sub-line position model — it cannot support the five-coordinate typed-position system (§13) this project requires for LSP/renderer/regex consumers.
