⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the Cargo workspace (§10), all nine crates/binaries as compiling stubs, CI on five OS/arch targets (ADR-20), and a minimal correctness kernel: a String-backed RefBuffer reference implementation of TextBuffer used as the ground truth every later differential test (P9, §26) compares against, plus the debug-only validate() hooks (I3, I9, I10) wired as no-ops until Phases 3–5 populate them.

Deliverable

A workspace that builds on Linux x86_64/aarch64, macOS x86_64/aarch64, and Windows x86_64 via ci.yml; conformance-cli --mode simulate runs against RefBuffer alone (no real backend yet) and reports green; docker-compose up starts a local dev container with the toolchain pinned.

Acceptance

cargo build --all-targets and cargo clippy --all-targets -- -D warnings both return 0 on all 5 CI matrix entries; cargo fmt --check returns 0; cold workspace build completes in < 90 s on a 16-core x86_64 CI runner (§4 startup budget context); conformance-cli --mode simulate --backend ref --ops 10000 exits 0 with zero invariant violations recorded.

Fixtures
Fixture Purpose Expected Output
workspace-metadata.json cargo metadata lists exactly 9 workspace members member count == 9
ref-buffer-smoke.yaml 100 scripted inserts/deletes against RefBuffer final content matches expected string byte-for-byte
ref-buffer-malformed.yaml delete crossing a UTF-8 boundary (§8.6 example) EditError::Utf8Boundary returned, no mutation
ci-matrix-report.json replay of a CI run's matrix results all 5 targets pass
Pitfalls
  • Pinning different serde versions per crate breaks Cargo feature unification silently; use workspace.dependencies and serde = { workspace = true } everywhere (ADR-14).
  • An uncommitted Cargo.lock diverges across machines and causes CI-only flakes; commit it (ADR-14 note).
  • RefBuffer's naive O(n) insert/delete is intentionally slow — a contributor "optimizing" it defeats its purpose as an independent oracle; document this explicitly in its module doc comment.

⬜ Phase 1 — Core Types & Position Model §13

Objectives

Lock the type vocabulary (§11.1–§11.3) in teb-core with zero behaviour beyond construction and the TextBuffer trait's default methods; implement the teb-positions conversion service (§11's typed positions made concrete) so byte↔char↔UTF-16↔grapheme↔line-col conversion has exactly one implementation (P1, P2, P11) that every future backend calls, never reimplements.

Deliverable

teb-core compiles with zero unsafe and zero unimplemented!; teb-positions implements all eight conversion functions against &dyn TextBuffer; PositionCursor demonstrates O(1)-amortised sequential conversion in a Criterion micro-benchmark.

Acceptance

cargo doc --no-deps --workspace returns 0 missing-doc warnings; the compile-fail suite's negative cases fail to compile (asserted via trybuild); a round-trip property test asserts char_to_byte(byte_to_char(off)) == off for 10,000 random offsets with zero failures; byte_to_grapheme matches the UCD GraphemeBreakTest.txt corpus (I13) with zero deviations across its ≈890 test cases.

Fixtures
Fixture Purpose Expected Output
compile-fail/coerce-byte-to-char.rs ByteOffset↔CharOffset implicit coercion fails to compile
positions-roundtrip.yaml 10,000 random byte offsets round-tripped through all 5 kinds 0 mismatches
uax29-corpus full UCD GraphemeBreakTest.txt replay 0 deviations (I13)
utf16-surrogate-pair.yaml non-BMP codepoint (e.g. U+1F600) UTF-16 length reports 2 units, not 1
Pitfalls
  • pub use re-exporting both a flat and a nested path lets downstream imports drift between the two; pick the flat re-export and document it (the project's terminology-lock discipline: one canonical name per module/type/file, used identically everywhere).
  • Caching grapheme counts on chunk summaries looks like a free win but is unsound across a chunk boundary that splits a ZWJ or regional-indicator sequence — Positions::byte_to_grapheme must not assume chunk-aligned summaries for graphemes (I13).
  • EditId(u64) looks unbounded but a fuzz run can allocate hundreds of millions of IDs in minutes; the wrap-on-overflow policy (ADR-22) needs an explicit decision recorded, not an implicit wrapping_add.

⬜ Phase 2 — Gap Buffer Backend §14

Objectives

Implement teb-gap as the first real TextBuffer backend: a single contiguous Vec<u8> plus a gap Range, delivering the amortized-O(1)-at-the-gap guarantee that is the documented exception to P4.

Deliverable

teb-gap implements TextBuffer with unsafe confined to two audited blocks (move_gap's copy_within, and iter_chunks' known-valid &str construction); compiles standalone with no dependency on teb-rope/teb-piece; a Criterion baseline reports insert-at-gap, insert-far-from-gap, delete-at-gap, delete-far-from-gap on 1 KB / 1 MB / 100 MB synthetic buffers.

Acceptance

Insert-at-gap p50 < 100 ns, p99 < 200 ns on a 1 MB buffer (§4, M1); the 1,000,000-random-edit line-index drift fixture (line-index-1m-drift.yaml) reports zero drift (I3); the differential fixture set in conformance/buckets/basic/ passes byte-for-byte against RefBuffer (§12.2).

Fixtures
Fixture Purpose Expected Output
gap-basic-ops.yaml insert/delete/replace against RefBuffer byte-for-byte match
line-index-1m-drift.yaml 1,000,000 random edits, recount comparison 0 drift (I3)
gap-utf8-boundary.yaml delete splitting a codepoint (§8.6 example) EditError::Utf8Boundary
gap-alternating-ends.yaml worst-case gap-thrash pattern documented O(n)-per-edit behaviour, no panic
Pitfalls
  • Forgetting to call line_index.apply_edit on every code path drifts the index silently; the 1M-edit differential fixture is the trip-wire (I3).
  • move_gap(target) with target inside the gap itself is meaningless input from a confused caller; clamp rather than panic (P14).
  • Growing data with reserve_exact instead of reserve causes pathological reallocation churn under repeated small grows — use reserve (ADR-15 spirit, small-value inlining reasoning applies to buffer growth too).

⬜ Phase 3 — B-Tree Rope Backend §15

Objectives

Implement teb-rope: a B-tree with branching factor 8 (ADR-03), interior nodes carrying additive Summary{bytes, chars, utf16, lines}, leaves holding 4–8 KiB validated UTF-8 chunks, delivering the worst-case-O(log n) guarantee (P4) independent of edit locality — the Boehm-Atkinson-Plass rope generalised to a B-tree per the Ropey/xi-rope reference implementations (§5).

Deliverable

teb-rope implements TextBuffer and BufferSnapshot; rebalance thresholds are named constants in node.rs, tunable for the Phase-13-era re-bench (ADR-03's "when rejected wins" clause); a proptest-based property test generates random edit sequences and asserts equivalence against RefBuffer after every step.

Acceptance

Insert p50 < 500 ns, p99 < 1 µs on a 100 MB rope (§4, M3); slice(range) for a 4 KiB range < 1 µs; memory overhead ≤ 25% over raw bytes; the differential suite (§26) passes identically to the gap-buffer backend on every shared fixture; validate_invariants() (I10) reports zero summary mismatches across the 1,000-edit-after-snapshot fixture.

Fixtures
Fixture Purpose Expected Output
rope-vs-gap-differential.yaml full basic-bucket replay on both backends identical output (P9)
rope-snapshot-validity.yaml snapshot taken, 1,000 edits applied, snapshot re-read snapshot content unchanged (I8)
rope-summary-invariant.yaml validate_invariants() after 10,000 random edits 0 mismatches (I10)
rope-alternating-ends-bench worst-case-for-gap workload rope outperforms gap-buffer baseline
Pitfalls
  • Arc::make_mut clones the whole spine when a snapshot is alive — bounded (one chunk per level) but not free; benchmarks must include the "active snapshot" workload explicitly, not just the no-snapshot case.
  • A leaf chunk type that copies bytes without re-validating UTF-8 on construction is a footgun; SmolStr validates, a hand-rolled inline chunk might not.
  • Changing the branching factor without re-running the Phase-13 benches violates ADR-03's locked rationale; any change requires a superseding ADR.

⬜ Phase 4 — Piece Table Backend §16

Objectives

Implement teb-piece: an immutable, optionally mmap'd original_buf plus an append-only add_buf, indexed by a red-black tree of Piece records (ADR-04), delivering the "open a huge file, make small edits" workload win documented by the VSCode piece-tree migration (§5 reading, applied here).

Deliverable

teb-piece implements TextBuffer and BufferSnapshot; the red-black tree is hand-rolled (no external crate, per ADR-04's rotation-cost rationale); a "captured edit trace" replay test loads a real large-file edit trace and replays it, asserting the final buffer matches byte-for-byte against RefBuffer.

Acceptance

Insert p50 < 300 ns, p99 < 800 ns on a 200 MB original + small add-buffer (§4, M4); open-a-200MB-file p50 < 250 ms (§4, M7); memory overhead ≤ 8% over raw bytes after a typical editing session; the red-black-tree property test (black-height invariant, no two consecutive red nodes, every leaf black) passes after 10,000 random edits with zero violations.

Fixtures
Fixture Purpose Expected Output
piece-vs-rope-differential.yaml full basic-bucket replay, piece vs. rope identical output (P9)
piece-rb-tree-property.yaml red-black invariants after 10,000 edits 0 violations
piece-summary-invariant.yaml subtree summary consistency (I9) 0 mismatches
large-2gib.bin + large-file-open.yaml open/edit a 2 GiB original buffer opens within budget, edits correct
piece-mmap-truncate.yaml original file truncated by another process mid-session (T-class scenario) IoError, not SIGBUS (see 16.9)
Pitfalls
  • The red-black rotation routines are the most bug-prone code in the project; the property test (16.4) is non-optional, not a nice-to-have.
  • NodeId as u32 (for cache-friendly Slab indexing) caps the tree at 2^32 nodes; the test harness asserts the slab count never exceeds 2^31 as an early-warning margin.
  • An mmap'd original_buf truncated by another process produces SIGBUS on read; §16.9 documents the guard.

⬜ Phase 5 — Line Index Sidecar §17

Objectives

Harden LineIndex (§11.7) from Phase-0 stub to a fully incremental B+-tree sidecar shared by all three backends (P11), maintaining line⇄byte mapping in O(log n) with zero full rescans after the initial load.

Deliverable

LineIndex::validate(buf) performs a from-scratch recount and compares against the maintained counts (I3); wired into every conformance run in debug builds, disabled in release for performance. The 1,000,000-random-edit drift fixture passes with zero divergence.

Acceptance

byte_to_line_col on a 100 MB / 1M-line buffer: p50 ≤ 50 ns, p99 ≤ 100 ns (§4, M5); index build on a 200 MB file: ≤ 200 ms on reference hardware (§4); the 1,000,000-random-edit drift fixture (line-index-1m-drift.yaml, shared with §14.5) reports zero drift across all three backends.

Fixtures
Fixture Purpose Expected Output
line-index-1m-drift.yaml 1,000,000 random edits vs. brute-force recount 0 drift (I3)
line-index-chunk-boundary.yaml edit spanning two adjacent chunks consistent counts post-edit
line-index-crlf-vs-lf.yaml mixed CRLF/LF file LF-only line-feed counting confirmed
line-index-build-200mb.bench cold index build on a 200 MB file ≤ 200 ms
Pitfalls
  • An edit crossing a chunk boundary left half-updated (only one of the two affected chunks touched) is the single most common line-index bug; apply_edit has a dedicated cross-boundary branch and the property test exercises it explicitly.
  • Counting \r\n as two line feeds double-counts Windows-style files; the index counts \n only, with \r handling delegated to the display layer (line_text_with_terminator).
  • Old-Mac bare-\r line endings are invisible to this index by design; a host serving such files must opt into teb-io's conversion-on-load (§20), not expect the index to detect them.

⬜ Phase 6 — Undo/Redo History §18

Objectives

Implement teb-undo: a coalescing undo/redo stack of EditGroups (§11.3) with precomputed inverses, giving structural (not per-keystroke) undo (P7) tuned to feel like Emacs by default (§5 Finseth reading, applied here) while remaining host-configurable.

Deliverable

teb-undo as a standalone crate the host opts into via buf.attach_undo() — the buffer itself carries no built-in undo (separation of concerns, per the architecture in §3). A "checkpoint" API records a named position in the stack (used for "mark saved" semantics, §25).

Acceptance

The "1,000 random edits + 1,000 random undos + 1,000 random redos" fixture asserts final state matches the buffer's net edit count exactly (I5); a coalescing fixture typing "hello world" character-by-character within the coalesce window restores the entire word in one undo step; push cost p50 ≤ 200 ns; pop (actual undo apply) cost p50 ≤ 1 µs on a rope backend for a typical 16-op group.

Fixtures
Fixture Purpose Expected Output
undo-redo-net-effect.yaml 1,000 edits + 1,000 undos + 1,000 redos final state == net-edit-count state (I5)
undo-coalesce-word.yaml character-by-character typing within 1s window single undo restores whole word
undo-truncation.yaml exceed max_undo_groups UndoStats.truncated == true, oldest group dropped
undo-checkpoint.yaml checkpoint set, edits applied, checkpoint queried checkpoint position resolves correctly
Pitfalls
  • Coalescing two inserts spanning a line boundary reads as one edit but is semantically two; coalesce_same_line_only defaults true to prevent this.
  • An EditGroup whose inverse references stale offsets (computed after later edits shifted them) corrupts the buffer on redo — the inverse must be captured at edit time, not lazily.
  • Clearing the redo stack on every selection change (not just on a new edit) is a common but surprising design: a user who hits Ctrl-Z, clicks elsewhere to look around, then hits Ctrl-Y expects the redo to still work — the default policy is "only a new edit clears redo."

⬜ Phase 7 — Anchors & Marks §19

Objectives

Implement AnchorStore (§11.4) as an interval-indexed structure of sticky offsets that survive every edit (P6), giving cursors, selections, and bookmarks a correct, O(log n + k)-updated position without each consumer re-deriving offset math.

Deliverable

AnchorStore lives in teb-core, updated synchronously by every backend on every edit before the edit is considered complete (I4); the host may subscribe to anchor-change notifications via a dedicated EditEvent::AnchorMoved variant on the observer protocol (§21).

Acceptance

The "1,000 anchors, 100,000 random edits" fixture asserts every anchor's offset matches a brute-force recomputation after every edit (I4), with zero mismatches; apply_edit on a buffer with 1,000,000 anchors and a small localized edit completes in ≤ 1 µs (only anchors in the affected range are touched, per §4's anchor-count constraint).

Fixtures
Fixture Purpose Expected Output
anchor-brute-force-100k.yaml 1,000 anchors, 100,000 random edits vs. brute force 0 mismatches (I4)
anchor-sticky-left-right.yaml insert exactly at anchor offset, both flavours matches §8.4 transition table
anchor-surround-collapse.yaml delete range containing both Surround endpoints collapses to empty at range start
anchor-1m-scale.bench 1,000,000 anchors, localized edit ≤ 1 µs per edit
Pitfalls
  • A naive O(n) walk over every registered anchor per edit is fine under ~1,000 anchors but collapses under ~1,000,000 (a host pinning every search-result match, say); the BTreeMap range-restricted walk is not optional at scale.
  • A zero-length insert is contractually forbidden upstream (EditError::EmptyEdit, P14) — handling it gracefully in the anchor path is not "extra robustness," it should be unreachable by construction.
  • A host that wants "notify me when this range disappears" needs the explicit Surround flavour; StickyLeft/StickyRight alone silently collapse without a distinguishable "you were deleted" signal — document the choice per anchor at creation time.

⬜ Phase 8 — Streaming I/O & Large-File Handling §20

Objectives

Implement teb-io: streaming chunked load/save so a 200 MB file is usable for reads while loading and editable while saving (P8), plus encoding detection, BOM handling, and crash-safe atomic save (P13, I11).

Deliverable

teb-io as a standalone crate; a "200 MB file open in ≤ 250 ms" benchmark on reference hardware passes (§4, M7); a "save while editing" fixture inserts 1,000 edits during an in-flight save and asserts the saved bytes match the pre-save snapshot exactly, while the live buffer reflects all 1,000 post-snapshot edits.

Acceptance

200 MB UTF-8 load p50 ≤ 250 ms on x86_64 with simdutf8 SIMD acceleration, ≤ 500 ms p99 (§4, M7); 200 MB save p50 ≤ 300 ms (§4, M8); the "every supported encoding round-trip" fixture (load → edit → save → reload) matches the original modulo intentional edits, for every encoding in the supported set; the atomicity fixture (20.3) shows zero torn writes across 100 injected-crash trials.

Fixtures
Fixture Purpose Expected Output
io-200mb-open.bench cold open of a 200 MB UTF-8 file p50 ≤ 250 ms (M7)
io-save-during-edit.yaml 1,000 edits fired during an in-flight save saved bytes == pre-save snapshot; live buffer has all edits
io-encoding-roundtrip.yaml load/edit/save/reload across every supported encoding byte-identical modulo edits
io-bom-preserve.yaml UTF-8 file with EF BB BF BOM BOM preserved on save (default policy)
io-crash-injection.yaml simulated crash after partial temp-file write original file untouched (I11)
Pitfalls
  • Validating UTF-8 per-chunk without carrying decoder state across the boundary can misclassify a valid multi-byte codepoint split across two 64 KiB reads as invalid; the validator must carry up to 3 bytes of pending state.
  • Detecting a BOM by inspecting only the first 3 bytes misclassifies some Latin-1 files that happen to start with the same byte pattern; the default policy is BOM-detection restricted to declared/detected UTF-8 only.
  • simdutf8's acceleration is x86-specific; aarch64 falls back to the scalar validator (§4's ~600 ms aarch64 load-time note is the direct consequence, still within budget but worth documenting for operators comparing hardware).

⬜ Phase 9 — Observer Protocol, Unicode Correctness & CRDT-Ready Edit Log §21

Objectives

Finalize ObserverFanout (§11.5) as the sole mutation-export mechanism (P5) with strict per-EditId ordering (I6) and per-subscriber backpressure (P12); close out grapheme-cluster correctness (UAX #29, I13) across chunk boundaries; and add the optional append-only EditLog that makes the buffer CRDT-ready without implementing CRDT semantics itself (per the Shapiro et al. and Roh et al. readings, §5).

Deliverable

ObserverFanout embedded in every backend; a replay_subscriber test fires a recorded edit trace into a fresh fanout and asserts every subscriber sees an identical ordered sequence; EditLog is enabled via BufferConfig::enable_edit_log and a "replay the log on a fresh buffer to reach the same state" fixture passes.

Acceptance

Fanout to 8 sync + 8 async subscribers on one edit: p50 ≤ 500 ns (§4, M11); the ordering-invariant fixture (two subscribers, 10,000 edits) shows zero reordering (I6); the UAX #29 chunk-boundary corpus (grapheme clusters deliberately split across leaf/piece boundaries) shows zero incorrect breaks (I13); EditLog replay reaches byte-identical state to the original run across 100 randomized replay trials.

Fixtures
Fixture Purpose Expected Output
observer-ordering-2sub-10k.yaml 2 subscribers, 10,000 edits identical ordered recordings (I6)
observer-refusal-rollback.yaml subscriber returns Refused edit rolled back, no content change
uax29-chunk-boundary.yaml grapheme clusters split across chunk boundaries correct breaks (I13)
editlog-replay-100x.yaml replay edit log on fresh buffer, 100 trials byte-identical state each time
observer-reentrancy-guard.yaml sync observer attempts to call back into the buffer rejected via debug thread-local flag (I14)
Pitfalls
  • A sync observer holding a mutex the host also holds deadlocks the moment the host calls back into the buffer from a different code path; the trait contract forbids sync observers from holding host-visible locks, and debug builds detect re-entrancy via I14's thread-local flag, but a lock held outside the buffer's own re-entrancy detection is a host-side bug the buffer cannot catch mechanically.
  • A flaky async subscriber that silently drops events under load is exactly the bug class ADR-23's default-to-block policy eliminates; a host that explicitly wants drop-oldest for a best-effort consumer must opt in per subscriber, not get it by accident.
  • Caching grapheme-cluster boundaries at the chunk-summary level (the same trap flagged in §13.6) resurfaces here specifically for chunk-crossing sequences — the fixture uax29-chunk-boundary.yaml exists because this is the one place a chunk-oblivious implementation silently breaks.
