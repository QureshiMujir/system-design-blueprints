In one paragraph

An LLM forgets everything between calls, so an agent needs somewhere to keep what it has seen and a way to pull the right pieces back into a limited prompt. This design is that place: a Rust library linked into the agent's own process, with a crash-safe record store, four kinds of search combined into one ranking, background summarising, deliberate forgetting, and a packer that fits results into the model's token budget (§1.1, §1.4). The agent only calls remember() and recall() (plus forget() and reflect()) (§1.6). The model itself stays outside, behind an abstract LlmIface trait (§1.1). It is a single-node, single-writer design (§1.3, §1.4).

The problem, concretely

The blueprint's worked example: an agent stores "User prefers dark mode" and must find it again later when asked about "UI preferences" (§8.16). The blueprint names what goes wrong with a naive store.

If the agent is told "stored" before the write is durable, a crash leaves it believing something that is not true, and the loss is silent (P1). The prompt has a fixed size: one 10 K-token transcript stored as a single memory can use up the whole budget and leave no room for anything else (MM6). A bare TTL deletes valuable old knowledge on a fixed date, however important or often used (MM7). Fusing raw scores from different searches breaks when one scale shifts, for example BM25 after a vocabulary change (MM3). One global index with no namespace filter leaks one user's memories to another (P7).

So the subsystem has to be durable, searchable several ways at once, bounded in size, and strict about what it removes and why (§1.1, P5, P11).

How it works, end to end

Follow one remember() and one recall() through the boxes of §3.1:

  1. Entry. mem-api validates the namespace and session and hands the observation to mem-ingest; one worker drains the channel so WAL order is preserved (§8.3, §3.2, §3.10).
  2. Extract and dedup. LlmIface::extract_facts() returns facts, then a content-hash check against the store; a hit bumps access_count and returns the existing id (§8.3).
  3. Chunk and embed. mem-embed splits the text and embeds each chunk, using an LRU cache keyed by content hash to skip repeat calls (§8.3, §3.5).
  4. Write. mem-store appends OP_BEGIN_INGEST, writes the record, fsyncs per the SyncPolicy, calls mem-index::insert on four indices, appends OP_RECORD_COMMITTED and returns Ok(MemoryId) (§8.3).
  5. Search. mem-retrieve embeds the query if needed and runs four lanes in parallel in mem-index: vector (HNSW), BM25, recency and importance (§8.4, §3.6).
  6. Fuse and diversify. Reciprocal rank fusion merges the lists, mem-store supplies the full records, filters and as_of apply, then MMR and an optional LlmIface::rerank() hook (§8.4).
  7. Pack. mem-context packs the ranked records inside the token budget, moving the lowest-priority working memories to long-term storage on overflow (§3.7, §8.7).
  8. Background. mem-consolidate summarises and merges, mem-forget decays, evicts and tiers, and mem-telemetry taps every path while no crate depends on it (§3.8, §3.9, §3.11).

The core ideas

The log is the truth, the store is a cache (§8.3, §8.10, MM1)

Write down what you are about to do in an append-only diary first, and treat everything else as something you can rebuild from it. The diary is the write-ahead log (WAL); if the store and the WAL disagree, the WAL wins (MM1, P2). remember() returns Ok only after the entry is fsynced under the configured policy (P1, I1).

Each entry is framed as entry_len: u32, op_type: u8, a bincode payload and a crc32c: u32 over the op type and payload (§8.10). Recovery has five steps (§8.10):

  1. Find the last OP_CHECKPOINT and replay from that LSN.
  2. Check each entry's CRC32c; skip a corrupt one with a warning and a metric.
  3. Apply entries in order, ignoring those for already-committed records.
  4. Abort any OP_BEGIN_* with no matching *_COMMITTED or *_FAIL.
  5. Rebuild the indices from the replayed committed records.

The crash trace (§8.18): the process dies after OP_BEGIN_INGEST is on disk but before OP_RECORD_COMMITTED. Replay classifies it as an incomplete ingest, tombstones any partial record, marks an orphaned embedding for GC and bumps recovery_aborted_ingests_total. §8.18 says no index was mutated before OP_RECORD_COMMITTED, so the indices stay consistent (§8.18); §8.3's write sequence, step 4 above, calls mem-index::insert before appending that entry (§8.3).

Four lanes, one ranking: reciprocal rank fusion (§8.4, §8.5, MM3)

Vector similarity, BM25, recency and importance live on different scales, so each lane contributes only its rank. This is reciprocal rank fusion (RRF) (MM3, §8.5): RRF_score(d) = Σ_i w_i / (k_rrf + rank_i(d)), with k_rrf = 60 by default (§8.5). The weights are w_recency = recency_bias, w_importance = importance_bias, and 1.0 - recency_bias - importance_bias for each of the vector and BM25 lanes (§8.5). A bug that inflates BM25 scores 100x has no effect on the fused output, and a new lane needs no renormalising (MM3). When the query terms appear in no document, every BM25 score is 0 and that lane counts as absent from the fusion (§8.13).

The worked trace (§8.16): ask for "UI preferences" with k=5. Each lane fetches 20 candidates (k*4 in §8.4). M1 heads all four lists, with component scores vec 0.92, bm25 0.78, recency 0.95 and importance 0.7, and the trace gives its fused score as 0.89 (§8.16). §8.5 defines the fused score as the sum of w_i / (60 + rank_i) over the lanes (§8.5).

Ties are broken by score DESC, id ASC using f32::total_cmp, so a fixed index state and query always give the same list (I4, P4).

Diversity: do not return five copies of the same thing (§8.6)

Maximal marginal relevance (MMR) picks results one at a time, scoring each candidate as λ · sim(d, q) - (1-λ) · max sim(d, r) over results r already chosen (§8.6). λ = 1 is pure relevance and λ = 0 maximum diversity; the default is 0.5, set per Query (§8.6). Similarity is cosine, and the cost O(k · |S| · D) is called acceptable for k ≤ 50, |S| ≤ 200 (§8.6). The optional rerank hook runs after MMR (§8.4).

Fit the memories into the prompt: a knapsack with a hard wall (§8.7, MM6, I5)

Working memory is a ring buffer of 32 ids by default (§8.7). Assembly (§8.7):

  1. Rank working memories by (salience DESC, last_access DESC).
  2. Pack greedily until one more would exceed max_tokens - reserved.
  3. On overflow, evict the lowest-priority working memories to long-term storage with OP_EVICT_TO_LONGTERM(id) in the WAL.
  4. Add retrieved long-term memories the same way, and return a ContextPacket with tokens_used.

The context never exceeds max_tokens (I5), and reserved tokens stay held back for the system prompt (§3.7). Without a token counter, 4 characters per token is the estimate (§3.7). Oversized records get different answers: if all records exceed the budget, §3.7 returns the highest-salience one plus a truncation marker; a single record over the available tokens gets MemError::RecordExceedsBudget(id) in §8.7 and §8.17, and is truncated or skipped in MM6.

Forgetting on a curve, never silently (§8.9, MM7, I2)

Each record gets a decay score, a weighted sum (§8.9): w_r · recency + w_s · salience + w_a · access_frequency, defaults 0.4 / 0.4 / 0.2, where recency = exp(-λ_r · days_since_last_access) and λ_r = 0.1, a half-life the blueprint states as about 7 days (§8.9). Thresholds place a record in the hot, warm or cold tier; at or below the cold threshold it becomes an eviction candidate (§8.9).

The worked case (§8.16): at 48 hours M1 scores 0.4 · exp(-0.1 · 2) + 0.4 · 0.7 + 0.2 · 0.1, which the blueprint writes as about 0.63, above warm_threshold (0.4), so the trace keeps M1 Active/Hot. At day 30 the score drops below warm_threshold and M1 moves to the Warm tier (OP_TIER_CHANGE); at day 90, if its TTL is 90 days, OP_EVICT(M1, reason=ttl) removes it from the indices (§8.16). Every removal is logged with a reason before the record leaves the store (I2, P11).

The blueprint is inconsistent here:

  • Formula. §8.9 gives a weighted sum, but §21 says "multiplicative, not additive" and MM7 writes D = salience × recency × frequency (§8.9, §21, MM7).
  • Tiers. The warm tier is "mmap only" in §8.9, "mmap + index but lower priority" in §3.9 and "cold pages, index stale" in §21 (§8.9, §3.9, §21).

Consolidation: summarise safely, even after a crash (§8.8, MM5, I12)

Four background jobs exist: Summarize (episodic memories to one semantic memory), Reflect (a higher-order insight), Merge (near-duplicates to one record) and LinkGraph (entity co-occurrence to links); the scheduler's priority is Merge, then Summarize, then Reflect (§8.8). The key property is idempotency: before writing a reflection, the job checks whether a record with the same derived_from set exists and skips if so, so a retry after a crash is harmless (I12, MM5). A job goes Queued, Running, then Done or Failed; Failed returns to Queued while retries remain, else Abandoned with an alert (§8.8). The retry limit is 3 in §8.8 and §8.17 but up to 5 in §3.8 and §4.4 (§8.8, §8.17, §3.8, §4.4).

The trade-offs — where engineers disagree

Custom WAL instead of an embedded database (ADR-10)

Chosen: an append-only WAL with CRC32c per entry and a configurable fsync policy, because it gives exact control over operations like OP_CONSOLIDATED and OP_EVICT, and SQLite is too opaque for partial-entry recovery (§9). Rejected: SQLite WAL, RocksDB, sled, redb (§9). When the rejected choice is right: SQLite wins when the team wants a mature, audited, full-ACID embedded store with SQL access and will accept its opacity to avoid maintaining a custom WAL. RocksDB wins when write amplification at more than 100k writes/s makes a single-file WAL a bottleneck and LSM compaction parallelism is needed (§9).

Build HNSW in-house (ADR-06)

Chosen: a built-in HNSW behind a pluggable AnnBackend trait, avoiding unsafe FFI by default; pure Rust is judged sufficient up to 10M vectors, with FAISS behind a feature flag (§9). Rejected: FAISS via FFI, hnswlib via FFI, Annoy, ScaNN (§9). When the rejected choice is right: FAISS wins above about 10M vectors when GPU compression is needed to keep index memory down. hnswlib wins when benchmarks show the pure-Rust index is the bottleneck. ScaNN wins when quantization-aware retrieval is the main latency lever (§9).

Hand-rolled BM25 (ADR-07)

Chosen: a small in-house BM25 inverted index, since only a score and a posting list are needed and it keeps the dependency surface minimal (§9). Rejected: tantivy, meilisearch, Lucene via FFI (§9). When the rejected choice is right: when requirements grow to fielded queries, phrase proximity, fuzzy match, facets or multi-language analysis, tantivy's tested segment architecture pays off (§9).

Read through mmap, write with pwrite (ADR-11)

Chosen: memmap2 for reads and pwrite for writes; mmap amortises read cost on the retrieval hot path, and pwrite avoids the complexity of writing through a mapping (§9). Rejected: plain read() syscalls, SQLite blobs (§9). When the rejected choice is right: read() wins where the environment forbids mmap (some seccomp profiles, strict WASM, SELinux policies). SQLite blobs win when access is random with no locality and SQL indexing over blob metadata is preferred (§9).

The LLM behind a trait (ADR-09)

Chosen: an LlmIface trait for summarize, extract, reflect and rerank; tests inject a mock, real implementations live in separate crates (ADR-09); embeddings use LlmIface::embed(), no default provider (ADR-08). Rejected: a hard-coded OpenAI or Anthropic SDK, or LangChain (ADR-09). When the rejected choice is right: a hard-coded OpenAI SDK wins when the product targets only that platform, no provider switch is planned and the team wants fewer layers. LangChain wins when orchestration already depends on it (ADR-09). For embeddings, a hard-coded ONNX runtime wins when the deployment is air-gapped, a remote API cannot meet a sub-5 ms budget and the model is fixed (ADR-08).

Roads not taken (Alternative Architectures, Deferred Features Register)

Postgres-backed store (Alt-1) wins for small teams, a corpus up to 5M records, existing Postgres skill and a recall SLA of 50 ms p99 or looser. It loses here because a Postgres round trip fits badly with a 25 ms p99, and the custom ops have no natural SQL form. The example is getzep/graphiti (Alt-1).

SQLite in WAL mode (Alt-2) wins when ACID durability and mature FTS5 BM25 are wanted without a custom WAL. It loses here because embeddings must be BLOBs, FTS5's tokenizer cannot be swapped, and OP_CONSOLIDATED and OP_EVICT need triggers to express (Alt-2).

RocksDB LSM backend (Alt-3) wins above 10K records/s sustained, above 50M records, with multi-threaded writes. It loses here on C++ FFI build cost and an implicit WAL that is not replayable at the application level, and 10M records or fewer does not need it (Alt-3).

External vector database (Alt-4) wins when memory is a cloud service, the team lacks Rust and provider SLAs cover durability (LangChain with Pinecone). It loses here: 5-50 ms per call against a 25 ms p99, and no control over WAL semantics, consolidation order or decay (Alt-4).

Deferred features each wait for a trigger (Deferred Features Register): federation (PhaseDeferred("15.x")) for two deployments in one organisation that must share semantic memories; replication (16.x) for HA with RTO under 60 s and RPO under 5 s; RBAC (17.x) for untrusted multi-tenant clients; streaming ingest (18.x) above 1,000 observations/s; graph retrieval (19.x) for multi-hop beyond §8.15's BFS; remote ANN (20.x) beyond the single-node HNSW ceiling.

What must never be false

  • I1 durability: once remember() returns Ok, its WAL entry is fsynced and survives a crash. Noticed by kill -9 replay tests and wal_flush_failures_total (§7.1).
  • I2 no silent loss: a record leaves the retrievable set only by forget(), TTL or decay, each logged with a reason first. Noticed by mem-cli audit --evictions and evictions_total{reason} (§7.2).
  • I3 embedding-record consistency: every retrievable record's embedding_ref resolves in the ANN index. Noticed by mem-cli fsck; index_dangling_refs_total and index_orphan_nodes_total stay at zero (§7.3).
  • I4 determinism: fixed index state plus query gives an identical ranked list. Noticed by the mem-bench golden-set test and retrieval_nondeterminism_events_total (§7.4).
  • I5 context budget: assembled tokens never exceed max_tokens. Noticed by an assert in the assembler and context_overflow_events_total (§7.5).
  • I6 monotonic ids and time: MemoryId and created_at never go backwards in a process. Noticed by the WAL reader's ULID check and monotonicity_violations_total (§7.6).
  • I7 namespace isolation: an operation on namespace A never touches B, enforced at storage and index layers. Noticed by an integration test and cross_namespace_access_attempts_total (§7.7).
  • I8 WAL append-only: no entry is modified or deleted before a verified checkpoint. Noticed by the O_APPEND flag, mem-cli inspect-wal and wal_bytes_reclaimable (§7.8).
  • I9 salience range: Salience stays in [0.0, 1.0], never NaN or Inf. Noticed by salience_out_of_range_total and mem-cli fsck --check-salience (§7.9).
  • I10 counts match: per namespace and kind, live records equal indexed entries. Noticed by mem-cli fsck --count-check and index_count_mismatch_total (§7.10).
  • I11 TTL: a record is not returned after created_at + ttl. Noticed by a ttl=1s unit test and ttl_expired_total; a lagging sweep shows in ttl_pending_count (§7.11).
  • I12 consolidation idempotency: re-running a job creates no duplicate reflection. Noticed by a twice-run unit test and consolidation_dedup_hits_total (§7.12).

What breaks in production

F1, the WAL cannot be written. remember() returns MemError::StorageWrite and the WAL stops growing; causes are a full disk, filesystem error, fd exhaustion or a permissions change. Detected by mem_store_wal_write_errors_total. It retries with backoff and, on a full disk, triggers compaction; an operator frees space and restarts. Mitigation is an alert at 80% disk (F1).

F2, recovery finds partial frames. After a restart corrupt_frames > 0 and some records are missing, because of a power loss mid-frame. Recovery skips the frame and rebuilds the indices, and the records in that frame are lost, which the blueprint calls the last-record durability window (F2). I1 says a write acknowledged with Ok survives any single-node crash (I1), and §8.3 also allows a relaxed SyncPolicy::Batched(interval) timing contract (§8.3).

F3, index and store disagree. recall() returns a record the store lacks, or misses a stored one, after a compaction crash between the index update and the store update. Detected by mem_index_dangling_entries_total. A background scan removes dangling entries and re-indexes the rest; the store is authoritative (F3, I3, I10).

F4, the embedding provider fails. Recovery retries with jitter, then uses a cached embedding if the content hash matches, otherwise stores the record without an embedding_ref, retrievable by BM25 only; mem-cli embed backfill re-embeds later (F4). §3.5 and §4.4 also store it without an embedding; §8.3's failure path writes OP_INGEST_ABORTED and commits no record (§3.5, §4.4, §8.3).

F5 and F6, the LLM or the HNSW index fails. On an LLM failure, ingest stores the raw content with an extraction-pending flag and retries later, and consolidation re-queues with backoff; extraction failure never blocks durability (F5). A corrupt HNSW index makes vector recall empty and drops mem_index_ann_accuracy_p50; the system marks it invalid, falls back to BM25 plus recency, and an operator rebuilds from the stored embeddings (F6, §4.4).

F8, premature eviction. Agents report missing memories and mem_forget_evictions_total spikes without operator action, from a too-aggressive decay model, salience not updated on access, or a TTL set too short. The eviction audit log shows each reason, and evicted records are archived so mem-cli forget restore can recover one (F8, I2).

F9, a namespace breach. An agent retrieves another namespace's records through a bug in the NsId filter. There is no automatic recovery. The response is to invalidate sessions and audit the query logs, and the long-term fix is to enforce the predicate at the lowest index-scan layer (F9, I7).

Threats worth knowing (Threat Model, Attack Surface Inventory):

  • Oversized content is a DoS and out-of-memory risk; a configurable cap, 64 KB by default, rejects it with MemError::PayloadTooLarge.
  • A forged NsId is a privilege-escalation attempt; it is validated against the authenticated session token at the mem-api boundary.
  • Prompt injection through stored content: the LLM prompt template is static, agent content goes into a delimited data field, and output that fails the schema parse is rejected.

How it compares

letta (MemGPT). It has no WAL (in-memory Python dicts plus optional SQLite), no vector search (tiering by recency only), and manual delete or the context-window limit for forgetting. It showed that a tiered working/archival split is the right abstraction for in-context memory, which this design implements durably (Comparative Architecture Table, §2.2).

getzep/graphiti (Zep v2). It sits on PostgreSQL with pgvector and tsvector full-text, extracts bi-temporal facts and has no decay model. Alt-1 describes the regime where that wins: small teams, a corpus up to 5M records, a recall SLA of 50 ms p99 or looser (Alt-1).

mem0. It uses SQLite without WAL mode, a separate vector database, no keyword search or fusion, and TTL as the only forgetting. Alt-4 names where an external vector database wins: memory as a cloud service with scaling and durability left to the provider (Alt-4).

FAISS + Postgres. It has Postgres ACID for metadata with FAISS snapshotted externally, no fusion (the application merges two queries) and no decay. The combination wins above 10M vectors or when the team needs SQL over memory metadata (Comparative Architecture Table, ADR-06).

Questions to test yourself

  1. "An operator sets RRF k=10 (instead of the default 60) on a namespace. Explain what happens to the fusion score distribution, which retrieval lane is most affected, and whether MRR@10 is likely to increase or decrease for a corpus where vector similarity scores are highly concentrated near 0.9." Hint: the formula and constant are in §8.5; MM3 explains why ranks are fused.
  2. "I4 (Retrieval Determinism) states "identical index state + Query → identical ranked set". A new engineer adds a HashMap<MemoryId, f32> intermediate to the RRF fusion step. Why does this break I4, how would the differential harness in Phase 13 detect it, and what is the minimum code change to restore determinism?" Hint: the tie-break is in §8.5, I4 in §7.4, and P4.
  3. "A reflection job over 50 episodic records creates 1 semantic record. That semantic record then becomes eligible for a second reflection cycle, creating another semantic record derived from the first. Over 100 consolidation cycles, what is the maximum chain depth of derived_from links? What prevents unbounded reflection amplification?" Hint: job kinds are in §8.8; I12 and MM5 cover idempotency.
  4. "For query Q, the vector ANN lane returns [A, B, C, D, E] and the BM25 lane returns [F, G, H, I, J] — completely disjoint. What does RRF fusion return? Is this a problem, and what does it indicate about the embedding model and/or the BM25 index?" Hint: compare §8.5 with the lanes in §8.12 and §8.13.
  5. "A record R is forget()-ed. R appears in Provenance.derived_from of 15 other records (it was a source for 15 reflections). What does the system do with those 15 records? Is there a cascade delete? What invariant governs the answer?" Hint: the stale-reference rule is in §8.15, and I2 in §7.2.

If you only remember three things

The log comes first: nothing is acknowledged until it is in the WAL, the store and indices can always be rebuilt from it, and nothing leaves memory without a logged reason (I1, I2, MM1). Retrieval fuses ranks, not scores, so four lanes with incompatible scales still produce one deterministic ordering (MM3, I4). The model stays outside the library, and the prompt budget is a hard wall: the assembler moves working memories to long-term storage before anything is cut (P10, I5, §3.7).

Words used here

  • Write-ahead log (WAL): the append-only diary of every change, written before the change is applied (MM1, §8.10).
  • Embedding: a fixed-size vector of numbers for a text's meaning, stored apart from the record (§8.1).
  • HNSW: a layered graph that finds approximately nearest vectors quickly (MM2, §8.12).
  • BM25: a keyword scoring formula from term frequency, rarity and document length (§8.13).
  • RRF (reciprocal rank fusion): merging ranked lists by summing w / (k + rank) per list (§8.5, MM3).
  • MMR (maximal marginal relevance): choosing results that are relevant but unlike those already chosen (§8.6).
  • Consolidation: background work that turns episodic memories into summaries, reflections and merges (§8.8).
  • Namespace (NsId): a structural partition; every WAL entry, record and index entry is keyed by it (MM8, I7).
  • LlmIface: the trait through which all model calls go; no model lives in the library (§1.1, P10).
