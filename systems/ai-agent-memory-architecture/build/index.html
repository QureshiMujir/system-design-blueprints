⬜ Phase 0 — Skeleton — crates, core types, in-memory store, remember()/recall() exact-match round-trip (no embeddings) §12

Objectives
  • Cargo workspace: 13 crates (mem-core, mem-store, mem-index, mem-embed, mem-ingest, mem-retrieve, mem-consolidate, mem-forget, mem-context, mem-api, mem-telemetry, mem-cli, mem-bench).
  • Stabilize every canonical spine type: MemoryId, MemoryRecord, MemoryKind, Salience, Embedding, Provenance, Query, RetrievalResult, ContextBudget, NsId, MemError.
  • In-memory RecordStore (HashMap-backed), correct CRUD, no persistence yet.
  • Wire remember() → mem-ingest (passthrough, no extraction/embed) → mem-store (in-memory), and recall() → mem-retrieve (exact-match/linear scan) → Vec<RetrievalResult>.
  • All cross-crate calls synchronous Result<_, MemError> this phase; async trait boundaries defined, not yet exercised. No file I/O, no embeddings, no background threads — round-trip correctness only.
Deliverable
  • cargo build --workspace clean, zero clippy::all warnings; cargo test --workspace 100% pass.
  • mem-cli remember "hello world" prints inserted MemoryId; recall "hello" prints JSON record.
  • All canonical types serde-serializable; operator inspects store via CLI; tracing spans on remember/recall visible at RUST_LOG=trace.

Pitfalls
  • Clock skew on created_at: NTP slew moves SystemTime::now() backward → non-monotonic MemoryId vs timestamp; fix: track last_assigned_millis, clamp forward; signal mem_id_clock_clamp_total>0.
  • RwLock write starvation: std::sync::RwLock prefers readers on Linux → writer (insert/remove) p99 spikes under read-heavy load; recover via parking_lot::RwLock (fair policy).
  • scan_ns full-table O(n): scans all records not ns-targeted; recall latency grows with total store size not ns size; fix: enforce by_ns index in retriever.
  • Arc<MemoryRecord> refcount churn: scan_ns clones one Arc per record per call (profiler-hot, not incorrect); mitigate by batching into one Vec and passing a slice.
  • MemoryId(Ulid) serde asymmetry: string in JSON, u128 in bincode — inconsistent fixture format; document the chosen encoding in mem-core/SERIALIZATION.md.
  • query.k == 0: silently returns empty vec (caller may misread as "no results"); enforce k >= 1 at the API boundary, else MemError::InvalidQuery.

⬜ Phase 1 — Durable store — append-only WAL + record store, mmap, fsync policy, crash recovery, compaction; durability invariants §13

Objectives
  • Replace Phase-0 in-memory HashMap backend with a durable, crash-safe mem-store engine.
  • Deliver: append-only WAL (fsync-per-commit or group-commit policy), mmap-backed record store, crash recovery via WAL replay, compaction (rewrite live records, truncate WAL).
  • Durability invariant: remember() returning Ok survives process kill + restart; record store fully rebuildable from WAL replay.
  • No-silent-loss invariant: eviction/removal logged with reason before execution.
  • Constraints introduced: async tokio::fs I/O on WAL path; parking_lot::RwLock replaces std::sync::RwLock on StoreInner; compaction runs as tokio::task::spawn_blocking.
  • Phase-0 in-memory path retained as InMemoryBackend for unit tests and embedded use.
Deliverable
  • cargo test -p mem-store 100% pass including crash-recovery and compaction tests.
  • mem-cli gains --durable --data-dir <path> flag; records survive process restart.
  • Operator can inspect wal.bin with mem-cli wal-dump --data-dir <path> (prints seq, op, id).
  • mem-cli snapshot --data-dir <path> exports all live records as NDJSON + SHA256 checksum.
  • Metrics emitted: wal_append_latency_us, compaction_duration_ms, recovery_entries_replayed, store_live_records.

Pitfalls
  • Partial fsync on power loss: sync_data() flushes pages but not the directory entry; records.bin can be absent after a rename-then-crash — fix: fsync the parent directory after atomic rename.
  • mmap + O_DIRECT aliasing: page cache and mmap aren't O_DIRECT-safe together; WAL uses BufWriter<File> only, record store uses mmap only (never both on one fd).
  • Compaction rename race: crash between records.tmp→records.bin and WAL truncation leaves both files; recovery detects records.tmp + missing Checkpoint and re-runs compaction from WAL.
  • DashMap iteration during compaction: concurrent inserts mutate mid-scan; take a full read guard across all shards for the compaction snapshot phase.
  • Unbounded WAL growth: low delete-rate workloads never cross deleted_ratio; add wal_max_bytes as a second compaction trigger (documented Phase-1 constraint).
  • BufWriter does not fsync on drop: panic mid-write leaves data unflushed — explicit flush()+sync_data() in WalWriter::commit(), Drop impl warns if unflushed.
  • mmap growth: MmapMut needs a known size at map time; pre-allocate 64 MB chunks, ftruncate+remap on overflow, track mmap_remap_total.

Pitfalls
  • Dim-guard race on first insert: two concurrent inserts on an empty store could both pass a dim==0 check; fix with OnceLock<usize> so the first winner sets dim atomically.
  • Cache keyed on text only: provider switch without cache flush returns stale wrong-model vectors — key must be SHA256(text||model_id), plus a flush_model(model_id) API.
  • Overlap slicing on multibyte chars: byte-offset slicing can split a UTF-8 sequence — always slice at char_indices() boundaries.
  • embed_batch partial failure: mid-batch provider error with partial writes already applied — make the batch transactional (allocate IDs, call provider, write all-or-none).
  • embeddings.bin grows unbounded: Phase 2 does not compact it; orphaned vectors accumulate — track embed_store_orphan_bytes, compaction lands Phase 4.

  • BPE tokenizer init cost (50–200 ms): cache the TextChunker instance, never reconstruct per record.

⬜ Phase 3 — Vector ANN index (HNSW) — graph build/insert, k-NN search, recall/latency tradeoffs, on-disk persistence of the graph §15

Objectives

  • Scope: layered graph construction, insert, search, delete-by-marking, on-disk persistence (snapshot+WAL delta), recovery, namespace isolation.

Pitfalls
  1. Stale entry-point after delete: entry point soft-deleted → search returns empty/wrong; detect via hnsw.entry_point.deleted>0; recover by scanning layer-max nodes for the first live one, updating atomically.
  2. Write-lock contention under bulk insert: full-GraphInner write lock serializes inserts (bidirectional edges need mutability); shard by node-id range (16 shards, independent RwLock); watch hnsw.lock.wait_ms.
  3. WAL replay divergence on partial fsync: power loss mid-write leaves a partial tail; CRC/length mismatch detects it; truncate at last valid CRC boundary, log wal.truncated_bytes.
  4. Recall degradation at high tombstone ratio: deleted nodes still occupy neighbor slots, reducing effective M; recall@10 drops past ratio>20%; trigger compaction (rebuild excluding tombstones) at ratio>0.15.
  5. ef_construction vs. recall regression: lowering it for speed permanently starves affected nodes of shortcuts; enforce ef_construction >= 2*M at config validation.
  6. L2-norm underflow: an all-zero embedding (failed embed call) yields 0/0 NaN cosine distance, collapsing search; validate |emb|>1e-6 at insert, else MemError::InvalidInput.
  7. Snapshot size explosion: storing full embeddings in-snapshot would be ~6 GB at 1M×D=1536; snapshot topology only (neighbor lists+level), fetch vectors from mem-store on reload — target <200 MB at 1M nodes.

Pitfalls
  • LlmIface timeout cascade: slow extract_facts exhausts the concurrency semaphore, stalling ingest (queue depth spikes) — per-call timeout (10s default) + circuit-breaker on repeated failures.
  • Bloom filter saturation: ~10M inserts push FP rate above threshold, silently dropping valid records — watch dedup_bloom_fp_rate, rotate filter, log rejects for audit.
  • Embed-before-dedup ordering: embedding before the cheap hash check wastes LlmIface calls on exact dupes — hash dedup first, then vector near-dup, embed only survivors.
  • ConflictResolver race: concurrent observe() for the same entity can both resolve to Append — serialize the resolve+store step with an entity-keyed DashMap<EntityId,Mutex<()>>.
  • FsyncPolicy::Never misconfigured in prod: silent data loss on crash — reject Never unless an explicit allow_loss=true flag is set; alert on wal_fsync_skipped_total>0.

  • Criterion baseline stale: if committed baseline was produced on a faster machine, PR from slower CI always fails regression check. Fix: store baseline with machine fingerprint; skip regression if fingerprint differs; always update baseline on main merge.
  • Conformance test order dependence: durability_roundtrip leaves a WAL file; next test inherits corrupted state. Fix: each conformance test runs in tempdir; teardown deletes temp dir unconditionally.
  • MockLlmIface non-uniform embeddings: hash-derived embeddings may cluster in embedding space, inflating HNSW recall artificially. Fix: apply random rotation matrix (fixed seed) to spread embeddings uniformly; verify distribution in differential/corpus_1k.json via variance check.
  • TTL arithmetic overflow in fuzzer: Duration::MAX + now overflows in naive expiry check. Fix: saturating add in expiry calculation; fuzz target asserts no panic with Duration::MAX TTL.
