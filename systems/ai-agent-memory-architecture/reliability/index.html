7. System Invariants

7.1 I1 — Durability Invariant

  • Statement: If remember() returns Ok(MemoryId), the corresponding WAL entry is fsync'd (or fdatasync'd) to durable media and is recoverable after any single-node crash.
  • Why: Agents rely on Ok as a durable-write confirmation; silent loss breaks agent reasoning chains.
  • Enforced in: mem-store WAL writer; flush policy gate before Ok propagates to mem-api.
  • Detection: Post-crash WAL replay in integration test with kill-9 injection; wal_flush_failures_total counter.
  • Telemetry: wal_flush_latency_us histogram; wal_flush_failures_total; wal_bytes_written_total.
  • Recovery: Unsynced entries never acked → no phantom records; replay from last synced entry is safe idempotent.
  • Debug: mem-cli replay --verify walks WAL, checks each entry's CRC32, reports gaps; compare with record-store state.

7.2 I2 — No-Silent-Loss Invariant

  • Statement: A MemoryRecord transitions out of the retrievable set only via explicit forget(), TTL expiry, or decay eviction; every transition is written to WAL with a typed reason code before the record is removed.
  • Why: Unexplained memory disappearance corrupts agent reasoning; required for auditable forget in regulated systems.
  • Enforced in: mem-forget eviction paths; mem-store delete entry; WAL entry type EvictRecord { id, reason, ts }.
  • Detection: mem-cli audit --evictions <namespace> replays WAL and outputs full eviction log; unit test verifies every delete path emits WAL entry before removing.
  • Telemetry: evictions_total{reason} counter; evictions_batch_size histogram.
  • Recovery: WAL is the authoritative eviction log; record store reconciles on replay.
  • Debug: If a record is missing unexpectedly, mem-cli lineage <id> + eviction log identifies the reason and timestamp.

7.3 I3 — Embedding–Record Consistency Invariant

  • Statement: For every retrievable MemoryRecord, its embedding_ref resolves to a valid vector in the ANN index. No dangling embedding_refs; no orphan index nodes without a corresponding live record.
  • Why: Dangling refs return stale vectors in retrieval; orphan nodes inflate recall and corrupt score distributions.
  • Enforced in: mem-store + mem-index compaction runs atomically (stage new index segment, swap, GC old within a single compaction transaction); delete path removes from both.
  • Detection: mem-cli fsck performs full consistency scan; index_dangling_refs_total gauge; index_orphan_nodes_total gauge — both must be zero.
  • Telemetry: compaction_embedding_mismatches_total; fsck_duration_ms.
  • Recovery: mem-cli fsck --repair re-indexes records missing from ANN; removes orphan nodes; emits repair WAL entries.
  • Debug: Discrepancy between record-store count and index node count → trigger fsck; diff output identifies specific MemoryIds affected.

7.4 I4 — Retrieval Determinism Invariant

  • Statement: For fixed index state S and Query Q, recall(Q) always returns identical ranked list with identical scores. Tie-break: score DESC, id ASC using f32::total_cmp for NaN-safe total order.
  • Why: Non-determinism makes quality regressions impossible to bisect; A/B testing of retrieval changes requires a stable baseline.
  • Enforced in: mem-retrieve fusion pipeline; mem-index HNSW search (fixed ef_search, fixed entry point seed); BM25 scorer (deterministic IDF computation).
  • Detection: mem-bench golden-set test: record ranked list for N queries at a fixed snapshot; assert identical on re-run.
  • Telemetry: retrieval_nondeterminism_events_total (incremented if golden-set test diverges in CI).
  • Recovery: Not applicable — non-determinism is a code bug; fix source of randomness (HashMap ordering → BTreeMap; float reordering → total_cmp).
  • Debug: Bisect by disabling individual retrieval components (vec / bm25 / recency / importance) until non-determinism disappears; check HashMap → BTreeMap in fusion accumulators.

7.5 I5 — Context-Budget Invariant

  • Statement: The token count of the assembled context returned by mem-context is always ≤ ContextBudget.max_tokens. Overflow triggers working-memory eviction (lowest priority first) to long-term store before assembly completes.
  • Why: Exceeding the LLM context window causes truncation or API errors at the agent level; the memory subsystem must never hand the agent an oversized context.
  • Enforced in: mem-context assembler token-counting loop; eviction triggered inline before returning context.
  • Detection: context_overflow_events_total counter; assert in assembler that returned token count ≤ budget.
  • Telemetry: context_assembled_tokens histogram; context_evictions_total; context_budget_utilization gauge.
  • Recovery: On overflow, evict lowest-salience working memories to episodic store, log eviction, retry packing.
  • Debug: context_assembled_tokens p99 approaching max_tokens → increase budget or reduce k in recall; distinguish "budget too small" from "retrieval returns too much".

7.6 I6 — Monotonic ID / Time Invariant

  • Statement: MemoryId(Ulid) values are monotonically non-decreasing within a process. created_at timestamps are monotonically non-decreasing. Neither is modified after initial write. as_of queries: results contain only records with created_at ≤ as_of.
  • Why: ULID sort order is used for recency index and WAL ordering; as-of time-travel correctness depends on monotonic created_at.
  • Enforced in: mem-core ULID generator (monotonic mode); mem-store WAL writer (asserts monotonicity before append); as-of query filter in mem-index recency index.
  • Detection: WAL reader checks ULID sequence on replay; monotonicity violation → WAL corruption error; monotonicity_violations_total counter.
  • Telemetry: ulid_generation_collisions_total (same-millisecond increments); clock_skew_ms gauge.
  • Recovery: Monotonicity violation in WAL replay → abort replay, report corruption range, require manual inspection; cannot silently skip.
  • Debug: mem-cli inspect-wal --check-monotonicity reports first violation; correlate with system clock NTP logs.

7.7 I7 — Namespace Isolation Invariant

  • Statement: A read or write operation with NsId(A) never returns, modifies, or evicts records belonging to NsId(B) where A ≠ B. Enforced at storage and index layers, not only at API layer.
  • Why: Multi-tenant deployments require hard data isolation; API-layer-only enforcement is trivially bypassed by direct store access.
  • Enforced in: mem-store key format includes NsId prefix; mem-index query always filters by NsId; mem-api validates NsId on every call.
  • Detection: Integration test: write record in NsId(A); assert recall in NsId(B) returns empty; cross_namespace_access_attempts_total counter (should always be zero after enforcement; non-zero = bug).
  • Telemetry: cross_namespace_access_attempts_total; namespace-scoped records_total gauge.
  • Recovery: Cross-namespace access is a code bug → panic in debug builds; return MemError::NamespaceViolation in release builds + alert.
  • Debug: cross_namespace_access_attempts_total > 0 → grep for NsId construction without caller-supplied value; check namespace propagation through async tasks.

7.8 I8 — WAL Append-Only Invariant

  • Statement: The WAL is strictly append-only. No WAL entry is ever modified or deleted before a compaction checkpoint. Compaction creates a new checkpoint file; old WAL segments are deleted only after the checkpoint is fsync'd and verified.
  • Why: Any in-place WAL modification can corrupt the recovery log; old segments must survive until new checkpoint is proven valid.
  • Enforced in: mem-store WAL writer (O_APPEND open flag; no seek-and-write); compaction: fsync checkpoint → verify → unlink old segments.
  • Detection: WAL writer opens file with O_APPEND | O_CREAT; mem-cli inspect-wal detects non-monotonic offsets.
  • Telemetry: wal_segment_count; wal_bytes_reclaimable (bytes in pre-checkpoint segments).
  • Recovery: If checkpoint verification fails, retain old WAL segments; retry compaction; never proceed to segment deletion without verified checkpoint.
  • Debug: Segment count growing without compaction → check compaction job is running; check wal_bytes_reclaimable trend.

7.9 I9 — Salience Range Invariant

  • Statement: Salience(f32) is always in [0.0, 1.0] and is never NaN or Inf. Violated values cause panic! in debug and MemError::InvalidSalience in release after logging.
  • Why: Salience drives ranking and eviction priority; out-of-range values corrupt sort orders and eviction decisions silently.
  • Enforced in: Salience::new(f32) -> Result<Salience, MemError> constructor validates range; LlmIface response parsing clamps before constructing Salience.
  • Detection: salience_out_of_range_total counter; mem-cli fsck --check-salience scans record store.
  • Telemetry: salience_distribution histogram (p5/p50/p95); salience_out_of_range_total.
  • Recovery: On read, out-of-range Salience triggers fsck on the affected record; operator decides to recompute or tombstone.
  • Debug: Out-of-range Salience almost always from LlmIface returning un-normalized importance scores; add clamp + log in LlmIface adapter.

7.10 I10 — Index–Store Record Count Invariant

  • Statement: For each (NsId, MemoryKind) partition: the count of live records in the record store equals the count of indexed entries across all indices (ANN + BM25 + recency + importance). Discrepancy > 0 indicates a consistency bug.
  • Why: Over-indexing returns phantom results; under-indexing causes retrieval misses on valid memories.
  • Enforced in: Ingest and delete are always two-phase: WAL entry → store write → index write (all in a logical transaction); compaction syncs counts.
  • Detection: mem-cli fsck --count-check computes per-partition counts and diffs; index_count_mismatch_total gauge.
  • Telemetry: store_record_count{ns, kind} gauge; index_entry_count{ns, kind, index_type} gauge; index_count_mismatch_total.
  • Recovery: mem-cli fsck --repair re-indexes records missing from indices; tombstones index entries without backing records.
  • Debug: Mismatch after crash → likely partial index write before WAL-based index recovery; check index recovery path in mem-index startup.

7.11 I11 — TTL Expiry Invariant

  • Statement: A MemoryRecord with ttl: Some(d) is not returned by recall() after created_at + d. Expired records are tombstoned (eviction WAL entry) and excluded from all index queries. Tombstoning is lazy (at query time) or eager (TTL sweep), but never retroactively absent from WAL.
  • Why: TTL is a user-visible contract; returning expired memories breaks agent trust in temporal accuracy.
  • Enforced in: mem-index query filter checks created_at + ttl ≤ now; mem-forget TTL sweep marks expired records.
  • Detection: Unit test: create record with ttl=1s; sleep 2s; assert recall returns empty; ttl_expired_total counter.
  • Telemetry: ttl_expired_total; ttl_sweep_duration_ms; ttl_pending_count gauge.
  • Recovery: If TTL sweep falls behind, query-time filter is the safety net; alert on ttl_pending_count > threshold.
  • Debug: Expired records appearing in results → check query-time TTL filter is applied before score fusion, not after.

7.12 I12 — Consolidation Idempotency Invariant

  • Statement: Re-running a ConsolidationJob with the same input MemoryIds and the same LlmIface response produces the same output MemoryRecord (deterministic by job content, idempotent by dedup on derived_from set). Re-running does not create duplicate reflection memories.
  • Why: Consolidation jobs may be retried after failure; duplicates inflate the memory store and corrupt salience distributions.
  • Enforced in: mem-consolidate dedup check: before writing reflection record, query for existing records with matching derived_from set; skip if found.
  • Detection: Unit test: run consolidation job twice with MockLlmIface; assert record count unchanged on second run.
  • Telemetry: consolidation_dedup_hits_total; consolidation_jobs_total{status}.
  • Recovery: If duplicate reflection records exist (detected by fsck), tombstone duplicates (keep highest-salience); log repair action.
  • Debug: Rising consolidation_dedup_hits_total with no new memories → consolidation job is being retried excessively; check job queue and LlmIface error rate.
